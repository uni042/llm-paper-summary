# A Dynamic LLM-Powered Agent Network for Task-Oriented Agent Collaboration

> 動的エージェントネットワーク（Dynamic LLM-Powered Agent Network、DyLAN）は、時間展開した協調グラフでエージェントの寄与を測り、事前にチームを選抜し、本番中にも低評価のエージェントを外して呼出しを削減する方式である。

## 概要

複数の大規模言語モデル（large language model、LLM）エージェントが相互に回答を批評する方式では、エージェント数と通信の組合せを固定すると、対象タスクに無関係な役割まで毎回呼び出すことになる。さらに、あるエージェントの出力が直接最終回答に採用されなくても、後段のエージェントがそれを利用して正しい回答へ到達する場合があるため、単一ラウンドの回答品質だけでは貢献を測りにくい。

DyLANは協調過程を時間展開順伝播網（temporal feed-forward network、T-FFN）として表し、チーム最適化（team optimization）とタスク解決（task solving）を分ける。前者では候補全員の予備協調から後向きに貢献度を伝播し、タスクに有用なエージェントを選ぶ。後者では選んだエージェントを実行し、途中のLLMランカーが低評価の応答を次時刻から外し、十分な回答一致があれば早期終了する。

COLM 2024掲載版の評価では、HumanEvalの単一実行がPass@1 73.2、1 API呼出しであるのに対し、DyLANは82.9、平均16.85呼出しとなる。WebShopの報酬は直接実行50.6から68.3へ改善するが、呼出しは14.52から24.85へ増える。したがって単一LLMより安い方式ではなく、他の多段協調方式と比較したときの品質・呼出し数の取引関係を改善する研究である。

## 問題設定

固定型の討論や役割分担では、ある課題に不要な専門家が存在しても所定のラウンド数だけ処理が続く。役割名を人手で選ぶだけでは、その役割が実際に貢献する保証もない。タスクが変わると最適な役割の組合せも変わるため、協調結果を見ずに事前に全員を固定することが非効率になる。さらに多数のエージェントの回答を単純に連結すると、誤った中間回答が後続へ影響する場合もある。

本研究は、エージェントの参加者集合と通信グラフを動的に変更しながら、後段へ間接的に寄与した回答を評価することを目指す。協調の各時刻をグラフの層、エージェントを節点、前時刻から次時刻へ渡る回答を有向辺として表す。この表現により、実行時の前向きメッセージ伝播と、予備試行後の貢献度を測る後向きメッセージ伝播を一つのグラフ上で扱える。

## 手法

### 1. 時間展開順伝播網としての協調

T-FFNの第t層にはその時刻の各エージェントに対応する節点がある。辺は前時刻のエージェントから応答や批評を受け取る経路であり、節点の処理は元の課題と受け取ったメッセージを組み合わせて新しい回答を生成する。エージェントはLLMでもツールでもよい。LLMの場合は役割別のプロンプトを作って推論し、ツールの場合は必要な構造化入力を渡して結果を受け取る。

この設計では、固定した討論、コード作成とレビュー、複数の専門家による改善を同じグラフ形式で表せる。各節点の出力は次の層へ伝わり、最終層の候補回答から最終出力を選ぶ。グラフを層ごとに展開することで、どのエージェントがいつ参加し、どの回答を参照したかを明示できる。

### 2. 実行中のチーム再編成

タスク解決では追加のLLMランカーが同一時刻の回答を比較し、上位のエージェントだけを次の時刻に残す。これは応答を並べ替えるだけでなく、次層へ接続する節点と辺の集合を変更する処理である。低評価の枝を以後の推論から除くため、固定した人数を最大ラウンドまで毎回実行する方式よりAPI呼出しを減らせる可能性がある。ただしランカー自体の呼出しと、その評価の誤りという追加費用がある。

同じ時刻の回答の3分の2超が一致した場合には早期終了する。これは回答の一致を正しさの代理指標とする経験的な停止規則であり、数学的な正答保証ではない。異なるエージェントが同じ誤答へ収束すれば早期終了はむしろ不利になる。最大時刻の上限も設け、合意できない場合に無制限に続けない。

### 3. 後向き重要度によるチーム選抜

チーム最適化では候補エージェント全員で予備試行を行い、T-FFNを記録する。各節点は前段から受け取った応答を評価し、前段節点から後段節点への貢献を表す重みを作る。最終層の貢献を初期化し、後段の重要度と辺の評価重みを掛けて前段へ集約する。これを時刻の逆順に繰り返すことで、最終回答に間接的に役立った節点にも重要度を伝える。

同一エージェントの時刻別貢献を集計した値をエージェント重要度（Agent Importance Score）と呼ぶ。候補の中からこの値が大きい上位k人を選び、以後の本番タスク解決で利用する。教師付きの正解寄与ラベルは不要だが、予備試行とLLMによる評価を行う費用が必要となる。同じ分野で選抜結果を何度も再利用する場合には費用を償却できるが、一度しか使わない問い合わせでは事前選抜が総費用を増やし得る。

### 4. 二段階の実行順序と出力

最初にタスクまたは分野に応じた候補役割を用意し、予備試行で協調グラフを得る。次に各節点から後段へ渡った回答の評価を使って重要度を後向きに集計し、タスク別の小さなチームを作る。本番では選抜チームで前向きに協調し、各時刻のLLMランカーが低評価枝を外す。回答が一致した場合は終了し、そうでなければ上限時刻まで進める。

最終出力は問題に対する回答であり、追加で選抜されたチームと実行時の通信グラフが得られる。基盤LLMの重み、注意カーネル、KVキャッシュの表現は変更しない。計算効率の改善は、モデルを一回呼ぶ時間の短縮ではなく、何回・どの順序でモデルを呼ぶかの制御から生じる。

## 評価条件

コード生成はHumanEval 164問のPass@1、意思決定はWebShopの50環境で報酬と成功率、一般推論はMMLUの57科目のテスト集合から5分の1を標本抽出した正答率、算術推論はMATHの5000問を評価する。主実験はGPT-3.5系を基盤とし、GPT-4-0613による追加評価もある。比較には単一実行、LLM Debate、LLM-Blender、Reflexion、LATS、CAMEL、AgentVerse、BOLAAなどを用いる。費用指標は主としてタスク解決段階のLLM API呼出し数であり、トークン数やGPU実行時間そのものではない。

## チーム選抜と構成要素除去

HumanEvalのコード生成では、候補12人から8人へ選ぶことでPass@1が76.2から82.9へ、API呼出しが23.04から16.85へ変わる。WebShopでは8人から4人へ選ぶことで報酬53.0から68.3へ、呼出し32.03から24.85へ変わる。MMLUでは7人から4人へ選ぶと正答率69.5から70.5へ、呼出し8.30から4.39へ変わる。人数を減らした方が良い例があるのは、役割の不一致や低品質な中間回答の干渉を減らせるためと解釈できる。

構成要素除去では、MATHの早期終了を外すと呼出しが7.15から13.00へ増え、正答率は35.7から35.0へ変わる。MMLUでは4.39から13.00へ増え、正答率は70.5から70.1へ変わる。早期終了は主に呼出し削減へ寄与する。一方、チーム再編成を外すとHumanEvalは82.9から76.2へ、WebShop報酬は68.3から66.0へ低下する。特にコード生成では低評価の枝を途中で外すことが品質にも影響している。

特定科目ではcollege mathematicsが40.0から65.0へ改善し、25.0ポイント差となる。ただしこれはMMLU全体の平均改善ではなく、科目別に見た大きな例である。主実験の全体平均は66.4から70.5への4.1ポイント改善であり、全科目で25ポイント改善するという意味ではない。役割選択の利益は分野によって異なり、候補役割がどれも課題に合わない場合には改善が小さい。

## 既存研究との差

固定人数の討論や固定役割のコードレビューは、通信グラフと参加者を事前に決める。DyLANは予備試行で後向きの貢献度を測って「誰を残すか」を選び、本番中にランカーが「いつ残すか」を更新する。時間展開グラフを使うことで、後段へ間接的に貢献した回答も評価対象にできる。これはLLMの重み量子化やGPUカーネルの高速化とは異なり、上位のエージェント呼出しグラフを再構成する研究である。

## 限界と未評価事項

エージェント重要度はLLMの相互評価に依存し、評価器の偏りや誤判定を含む。回答一致による早期終了は誤答への合意でも発動し得る。コード生成で回答の一致を測る指標としてBLEUを使うことには限界があり、より適切なコード類似度指標が必要な可能性を著者も挙げる。候補エージェントが対象分野に合わなければ、選抜してもチームの品質が十分に上がらない。

主な費用はAPI呼出し数であり、モデルごとのトークン長、料金、並列実行時の壁時計時間、GPU配置、キュー待ち、KVキャッシュ共有は直接測定していない。チーム最適化の予備試行にも費用がかかるが、主な表では本番タスク解決段階の呼出しを報告する。そのため、単発の問い合わせに対する総費用の削減や、低レベル推論基盤の速度改善をこの結果から推定することはできない。
