# TALE：トークン適応低階数KVキャッシュ近似と復元省略

## 概要
大規模言語モデルの自己回帰生成は過去のキー・バリューをKVキャッシュとして保持することで重複計算を省く。しかし系列長、層数、同時要求数に比例してキャッシュが増え、GPU高帯域メモリの収容能力を制限する。既存の低階数近似では全トークンに一律の階数を与え、生成に重要な接頭辞や直近トークンまで同じ精度で削る。さらに、キーとバリューを先に近似すると、その誤差が後段の表現に波及し、圧縮行列を注意計算前に元の次元へ戻す処理が転送・演算を増やす。TALEは重要度に応じて異なる階数を割り当て、必要になるまで近似を遅らせ、圧縮表現のまま注意を計算する。多段量子化を併用したLlama-3.1-8Bでは9.14倍のKV圧縮率を報告し、GSM8K正答率は非圧縮の81.65%に対して81.88%である。これは単一試行での数値であり、0.23ポイント差を有意な改善と解釈しない。

## 問題設定と技術背景
通常の注意は、新しいクエリと過去のキーの内積から注意重みを作り、重み付きバリュー和を出力する。キャッシュを省けば毎回過去のキーとバリューを再計算しなければならないが、保存すると長文脈で容量が逼迫する。トークン削除は容量を直接減らせる一方、後から必要になる情報を復元できない。量子化は各要素のビット幅を減らすが、極端な低ビットでは近似誤差が累積する。低階数分解は特徴次元の冗長性を利用できるが、同じ階数をすべての位置に適用すると重要度の不均一性を無視する。

低階数化でK≈ABと表現したとき、通常の実装が毎ステップABを復元してからクエリと積を取るなら、圧縮したはずのテンソルを一時的に再展開する。特に長文脈ではこの復元のメモリ読み書きが律速になる。また回転位置埋め込み（RoPE）を施したキーは、一般には線形変換をクエリ側へ簡単に吸収できない。この非可換性を無視すると正しい位置依存の注意を壊すため、キーとバリューの扱いを分ける必要がある。

## 手法：入力から出力まで
### 1. トークン重要度別の階数配分
TALEは過去トークンを同等に扱わず、先頭の注意シンクと直近のトークンを重要領域とみなす。中間領域は低い階数、重要領域は高い階数で近似する多段構造を作る。入力は系列中のトークン位置、重要領域の幅、各段階の階数であり、出力は階数が異なる圧縮KV表現である。注意シンクは後続の多数のクエリが強く参照しやすい先頭位置、直近領域は局所依存に必要な位置である。どちらも低階数化し過ぎると後続の注意重みと生成品質を損ねる。階数配分はトークンを完全に捨てない点で単純な間引きと異なるが、重要度がこの位置的な仮定に従わない課題では精度低下の余地がある。

### 2. 遅延近似と誤差の伝播抑制
従来の積極的な低階数化では、キーやバリューを作る直後に圧縮表現へ変換し、その近似済みの状態を後続の処理でも使う。TALEは必要になる局面まで近似を遅らせ、表現を作る時点で不要な誤差を導入しない。入力はモデルが生成した通常のKV状態、出力は注意で利用する時点に応じた圧縮状態となる。重要度別階数と組み合わせることで、生成前半から誤差を何度も積み重ねる危険を抑える。低階数分解の準備や状態管理自体は無料ではなく、保存期間と変換時点の設計が重要になる。

### 3. 復元なしの注意計算
圧縮したバリューを元の特徴次元へ展開せず、クエリ・注意重み・射影行列の積の順序を変更して出力を直接計算する。行列積の結合順序を入れ替えられる部分では、圧縮次元のまま計算を進めるため、一時的なフル次元のキャッシュ復元を避けられる。RoPE付きキーでは同じ変換が成立しない場合があり、論文はキー側の低階数化を控える条件を明示する。すなわち、復元省略の利点をすべてのキー・バリューに無条件で適用したという主張ではない。

### 4. 重要度別の多段量子化
さらに低階数近似だけでなく、重要度の低い領域を低ビット、高い領域を高ビットで量子化する。実験設定では2ビットと4ビットを併用し、キーにも量子化を適用して容量を減らす。これによりバリュー低階数化とキー量子化が補完関係になる。量子化は離散化誤差を追加するため、圧縮率だけでなく生成正解率、長文脈の情報検索能力、実際の注意カーネルの速度を別々に測定する。

## 評価条件
| 項目 | 原著で確認した条件 |
|---|---|
| 主モデル | Llama-3.1-8B-Instruct、Mistral-7B-Instruct-v0.3。別途Llama-2-7Bなどで注意カーネル測定 |
| 実行基盤 | 主評価は単一H100 80GB GPU。モデル規模汎化の一部は別条件 |
| データ | GSM8K、LongBenchのLCC・MultiNews・Qasper・QMSum・RepoBench-P・SAMSum・TREC・TriviaQA、ARC-Challenge・HellaSwag・MMLU |
| 比較対象 | 無圧縮16ビット、Attention Sink、KIVI、HQQ、Palu、ShadowKV、FlashAttention |
| 圧縮設定 | 先頭保持数α=4、p=0.1、r0=全階数の50%、2/4ビットの多段量子化 |
| 長文脈測定 | 512K、1M、2M、4Mなどの系列長を注意ヘッド単位でも測定 |
| 測定上の注意 | 品質実験は原著記載で各設定1回。注意ヘッド遅延とモデル全体の処理量は別指標 |

## 評価結果
| 条件・指標 | 比較対象 | TALE | 解釈 |
|---|---:|---:|---|
| Llama-3.1-8BのKV圧縮率 | 無圧縮1.00倍 | 9.14倍 | 圧縮率は容量比であり速度倍率ではない |
| GSM8K正答率 | 無圧縮81.65% | 81.88% | ほぼ同水準。単一測定で優越性は断定しない |
| GSM8K正答率 | Palu 28.58%（8.89倍圧縮） | 81.88%（9.14倍圧縮） | 一律低階数化との差が顕著 |
| LongBenchの8課題平均 | 無圧縮48.78 | 48.79 | 長文脈の総合品質をほぼ維持 |
| ARC/HS/MMLU平均 | 無圧縮61.39 | 61.41 | 重要度別圧縮でも選択式課題を維持 |
| Mistral-7B GSM8K | Palu 28.13% | 44.88% | 同程度の圧縮率で品質差が残る |
| Mistral-7B LongBench平均 | Palu 49.47 | 52.59 | モデルを変えても差を確認 |
| Llama-3.1-8B・2M文脈の注意ヘッド遅延 | 従来注意 | およそ半減 | 注意ヘッド単体であり配信全体の速度ではない |
| Llama-3.1-8B・最大系列長 | FlashAttention | 約1.5倍の長さを収容 | H100 80GBのメモリ容量制約下での比較 |

圧縮率と精度を同時に読むと、Paluは8.89倍という近い圧縮率でGSM8K正答率が28.58%まで落ちる。TALEの81.88%との差は単なる容量削減ではなく、どの位置の情報をどの階数で残すかという設計が効いていることを示す。KIVI（2ビット）は8.00倍圧縮で79.91%、HQQは同じ8.00倍で76.73%であり、TALEが低ビット化だけに依存していないことも分かる。

長文脈では復元を伴うPaluが遅くなる一方、TALEは圧縮表現のまま注意を処理できる。論文の「最大2倍の遅延短縮」は特定の長文脈注意計算での比較であり、常にモデル全体が2倍になるという意味ではない。バッチ拡大によるモデル全体の処理量向上は別途測定されている。4M系列長で従来方式がメモリ不足になる条件も示すが、4Mをすべての実用モデルでそのまま扱える保証ではない。

## 既存研究との差と限界
Attention Sinkはトークン削除、KIVIとHQQは量子化、Paluは低階数分解、ShadowKVはCPUへの退避も用いる。TALEはそれらの一つを置き換えるだけではなく、重要度別の階数、近似適用時点、復元を省いた計算、ビット配分を一つの経路に統合する。特にRoPE付きキーの制約を明示し、キーまで一律に低階数化して理論上の圧縮率を稼がない点が重要である。

一方、重要トークンの定義は先頭と末尾の傾向に依存し、中央に散在する証拠や複雑な検索で同じ利得が得られるとは限らない。H100での単一GPU評価を他のGPU・CPU退避構成へそのまま移せない。圧縮の前処理、モデル全体の品質、長文脈注意カーネル、バッチ処理量は異なる測定である。論文はコード公開を述べるが、今回は公式URLの実体を確証できず、`code` は未確認としている。


## 実装判断と比較上の注意
TALEの圧縮率9.14倍は、同一のキー・バリューを16ビットで保持する基準に対する保存量の比である。モデルの重み、演算時の中間活性化、カーネル作業領域まで同率で小さくなるという意味ではない。長文脈で得られる速度利得は、圧縮率そのものより、圧縮表現を再展開せずに注意を計算できるかに強く左右される。比較対象のPaluでは圧縮後の復元費用が長文脈で顕在化し、Llama-2-7Bの2M系列長では遅延がほぼ倍になる条件がある。TALEは逆に注意ヘッド遅延を減らすが、この測定は単一ヘッドの構成を切り出したものなので、モデル全体のバッチ形成、トークン間の依存、GPU間通信を含めた配信遅延を直接保証しない。

長文脈に対する頑健性は、先頭の注意シンクと直近トークンを高階数で保存することに依存する。途中に重要な根拠が散らばる場合、中央を一律に低階数化する設計では十分に保持できない可能性がある。LongBenchの平均値が維持されても、個別課題の点数には差がある。例えばQasperでは無圧縮15.60に対してTALE17.35だが、QMSumは23.80に対して24.25、RepoBench-Pは52.38に対して51.03であり、平均値だけから全課題で無損失と断言できない。モデル規模、文脈長、バッチ、量子化ビットの組合せを変更する場合には、重要度配分の再調整と評価が必要になる。
