# Strata: Hierarchical Context Caching for Long Context Language Model Serving

## 書誌情報
- canonical identity: `arXiv:2508.18572`
- 著者: Zhiqiang Xie, Ziyi Xu, Mark Zhao, Yuwei An, Vikram Sharma Mailthody, Scott Mahlke, Michael Garland, Christos Kozyrakis
- 初回公開: 2025-08-26
- 一次資料: https://arxiv.org/abs/2508.18572

## 概要
長文脈サービングでは、再利用可能な鍵・値キャッシュ（KV cache）をGPU高帯域メモリだけに置けないため、CPUメモリやSSDへ階層化する。しかしPagedAttention型の小ページ配置はGPU内メモリ利用には有利でも、CPU→GPUへ戻すと数KB単位の断片転送になり、PCIe帯域を使い切れない。論文のLooGLEプロファイルでは、通常のSGLangオフロードでprefill時間の74%がKV転送待ちとなり、スループットが最大4倍悪化する。

Strataはこの問題を「ページを大きくする」ことで解かない。ページを大きくするとキャッシュ一致粒度が粗くなり、Mistral-24B/ShareGPTでは最大ページ条件で平均TTFTが最大2倍、P90が2.9倍まで悪化する。そこで小ページを保ったままGPU補助I/Oで大量の細粒度コピーを並列化し、さらにロード時間を計算と同じ第一級資源として扱うスケジューラを導入する。

## 問題設定
従来の階層キャッシュは、次層のKVロードを現在層のprefill計算へ重ねればI/Oを隠せると仮定する。しかし「長い再利用context＋少量の新規token」ではロード量に対して計算が少なく、I/Oが隠れない。最適化I/Oを使っても論文の観測では最大24%のprefill時間がロード待ちになる。

また小ページはキャッシュhit率に有利だが、転送サイズが小さい。8192 token分のKVをpage size 32でCPUからGPUへ移す例ではPCIe 5.0理論帯域の約22%しか使えず、Grace-Hopperの高帯域接続では利用率が約5%まで落ちる。Strataはキャッシュhit率とI/O帯域の二者択一を避ける。

## 手法
### GPU補助I/O
`cudaMemcpyAsync`を小ページごとに大量発行する代わりにCUDAカーネルを起動し、多数threadが128 byte程度の小片をregister経由でsourceからdestinationへstreamする。CPU側のI/O発行並列性ではなくGPU自身の大量threadを使うため、小ページを連続大ページへ再構成せず転送並列性を得られる。

I/O kernelは計算kernelと資源競合するため、Strataは少数の大きなCUDA blockへ限定する。H200のmicrobenchmarkではCPU→GPUロードに2 block×1024 threadを使う設定で約50 GB/sを得つつ、prefillへの干渉5%未満、decodeへの干渉10%未満に抑える。backup側はcritical pathではないため1 blockを使う。

### レイアウト分離とHiRadixTree
GPUではattention kernelに都合のよいlayer-first配置を保ち、CPU/下位層ではI/Oに適した配置を別に持つ。GPU補助I/O kernel内で軽量なlayout変換を行うため、GPU側のPagedAttentionページ構造をそのままCPU側へ強制しない。HiRadixTreeはSGLangのRadixTreeを拡張し、各KV pageの所在を追跡するpage tableとして機能する。

### キャッシュ認識スケジューリング
待ちrequestごとに必要なKVロード量と新規prefill計算量を見積もり、I/Oを覆えるだけの計算を持つrequestを組み合わせる。ロード待ちを完全に隠せない場合はdecode batchなど補完taskを挿入し、GPUがI/O完了待ちで遊ぶ時間を減らす。さらに同じ未ロードcontextへ複数requestが集中するdelay hitを避け、重複prefillを抑える。

## 評価条件
| 項目 | 条件 |
|---|---|
| 実装 | SGLangベース、production deploymentあり |
| 比較 | vLLM + LMCache、TensorRT-LLM、SGLang系 |
| モデル例 | Qwen2.5-14B、Llama-3.1-8B、Mistral-24B |
| ハードウェア例 | NVIDIA H200、PCIe 5.0、Grace-Hopper、AMD ROCm互換確認 |
| ワークロード | LooGLE、ShareGPT等の長文脈／共有context |
| 主要指標 | TTFT、throughput、I/O bandwidth、stall割合、cache hit |

## 主要結果
| 条件 | 結果 | 意味 |
|---|---:|---|
| 長文脈 | vLLM+LMCache比TTFT最大5×改善 | 階層cache loadをcritical pathから削減 |
| 長文脈 | TensorRT-LLM比最大3.75×高速 | I/Oとschedulerの共同最適化効果 |
| 8192 token/page 32 | 従来転送はPCIe 5.0の約22% | 小ページ断片化が帯域を浪費 |
| Grace-Hopper | 従来利用率約5% | 高帯域ほど発行粒度不足が顕在化 |
| GPU補助I/O | 約50 GB/s、prefill干渉<5% | 少数SM利用でI/Oを並列化 |
| 大ページ化 | 平均TTFT最大2×、P90最大2.9×悪化 | 単純なpage拡大はhit率を損なう |

## 既存研究との差
LMCacheやCachedAttentionは階層KV再利用を提供するが、Strataは「小ページ転送そのものの帯域利用」と「load量を考慮したbatch形成」を同時に扱う。単なるcache容量拡張ではなく、CPU-GPU bandwidthをschedulerの資源モデルへ入れる点が中心である。

## 限界
主対象はprefill支配の長文脈・再利用context workloadであり、短いsingle-turnや長decode主体では利得構造が異なる。GPU補助I/OはSM資源を消費するため割当を誤ると計算kernelを妨害する。SSD等のさらに遅い層はqueue待ち中のbest-effort prefetchを使うため、すべてのstorage latencyを完全に隠せるわけではない。
