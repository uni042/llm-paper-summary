# WnW：音声LLMのKVキャッシュを生成中にCPUから呼び戻す

## 概要

長い音声を入力して逐次文字起こしする音声LLMでは、音声トークンがKVキャッシュの大部分を占める。従来のKV圧縮は、プリフィル時の注意スコアで重要な音声位置を選び、残りを削除したままデコードを続ける。しかし長時間音声の文字起こしでは、最初の出力トークンは音声冒頭を参照し、後続の単語を生成するにつれて必要な音声位置が時間方向へ移動する。プリフィル時の順位で固定的に削除すると、後で必要になる音声位置を復元できない。

WnW（Waxing-and-Waning KV cache）は、音声KVヘッドをanchor、tidal、fixedの3役へ分類する。anchorは全音声KVをGPUに残し、生成中の注意から現在読んでいる音声領域を示す。tidalは選択済みKVをGPUに残し、未選択分をCPUに保持して必要なチャンクだけ呼び戻す。fixedはプリフィル時に選んだ部分だけGPUに残し、残りを完全に捨てる。これにより、**GPU上のKV保持率を低くしながら、デコード中の参照位置の移動に追従**する。

Voxtral-mini-3bのLibriSpeech-LongでGPU上の音声KV保持率が約22%のとき、WnWのWERはtest-clean 6.23、test-other 8.87で、無圧縮の6.79、8.86に近い。対照的に静的圧縮方式の一部は生成停止に失敗しWERが100を超える。ただし24Bでは無圧縮との差が大きくなり、CPUに保存したKVと転送の費用も必要である。

## 問題設定：プリフィルの注意は後続の音声参照を予測しない

音声LLMの入力は、波形から変換された大量の音声トークンとテキスト指示で構成される。長時間の文字起こしでは、入力音声全体をプリフィルした後に、文字列を左から右へ生成する。生成中の各単語は、音声の対応する時間区間を参照するため、重要なKV位置は固定されない。

著者らはVoxtralとLibriSpeech-Longの音声で、最初の回答トークンの注意と、デコード全体で累積した注意を比較した。プリフィルの注意は音声冒頭の注意シンクに集中するが、デコード全体の注意は音声の前半・後半に広く分散する。両者の上位重要位置のJaccard重なりは低く、プリフィルだけで選んだトークンが後の生成に十分とは限らない。音声KVの全位置を永続削除する方式では、この誤りを訂正する手段がない。

テキストの一般的なKV圧縮と異なり、文字起こしでは音声トークンと発話単語に時間順序がある。生成が進むにつれて、現在参照する音声位置も概ね前へ進む。この構造を使えば、毎ステップの注意から次に必要な音声チャンクを予測してCPUから取り戻せる。ただし全ヘッドのKVをCPUに残すと保存容量と転送が増えるため、どのヘッドに復元機能を与えるかも重要である。

## 手法：音声への依存度と損失感度でヘッドを3分類

### 1. Voice Score（VS）：実際の発話区間を見ているか

オフライン校正では、WhisperXによる単語時刻アラインメントを利用し、ある回答トークンが対応する音声時間区間を特定する。各注意ヘッドについて、上位に注意した音声位置のうち、そのトークンの発話区間に入る割合を求める。回答トークン、校正サンプル、GQAで同じKVを共有するクエリヘッドを通じて集約し、KVヘッド単位のVSとする。

VSが高いヘッドは、回答の単語と対応する音声区間をよく参照する。文字起こしが進めば重要な音声位置も移るため、VSが高いヘッドは生成中の参照領域を追跡する候補となる。しかしVSだけでは、そのヘッドのKVを削除したときにモデルの損失がどれだけ悪化するかは分からない。

### 2. Head Sensitivity（HS）：音声KVが正答損失へどれだけ効くか

HSは回答トークンの交差エントロピー損失を各ヘッドの音声キーに関して微分し、勾配の大きさを音声位置・トークン・サンプルにわたり平均して求める。高HSのヘッドでは音声KVの変更が損失に影響しやすい。著者はVSとHSを組み合わせた重要度で、単に音声を見ているだけのヘッドと、正答に重要な音声KVを持つヘッドを区別する。

まず重要度上位をvoice headsとし、残りをfixedへ分類する。voice headsのさらに上位の少数をanchorへ割り当て、残りをtidalとする。anchorは音声KVを全量GPUに保持し、生成中の音声参照を観測する。tidalはGPUとCPUにKVを分割して、anchorの観測を使って動的に復元する。fixedは初回の部分保持を固定する。これによりCPUへのオフロード対象を、生成中の位置変化が品質へ効くヘッドへ集中できる。

### 3. プリフィルで音声区間ごとの初期保持を保証

音声位置を時間順に複数のセグメントへ分け、各セグメント内でプリフィル注意が高い位置を選ぶ。全音声位置から上位を一括選択すると、音声冒頭の注意シンクが予算を使い切り、後半セグメントが完全に空になる危険がある。WnWはセグメントごとに保持枠を設けることで、音声全体に初期のGPU常駐位置を分散させる。

anchorは全量をGPUへ残す。tidalでは初期選択分をGPUに置き、残りの正確なKVをCPUに退避して後から復元できるようにする。fixedでは未選択分を破棄する。CPU側へ置くのは再計算した近似ではなく元のKVなので、呼び戻し時には値そのものを復元できる。ただしCPUメモリの容量とホスト・デバイス間の転送が必要になる。

### 4. デコード中のチャンク再取得と失効

デコードの各ステップでanchorヘッドの音声位置への注意を集約し、チャンク単位の重要度を計算する。重要度はそのステップでリセットされるため、以前に参照した音声区間の累積注意に引きずられない。スコアの高いチャンクを選び、tidalヘッドについてCPUに残した未選択KVをGPUへ転送する。

後続ステップで重要度が下がったチャンクは、一定の猶予を置いてGPUから削除する。ただしCPU上の元データは保持され、再び重要になれば呼び戻せる。このGPU上の増減がWnWの名称の由来である。チャンクは隣接区間を重ねる設計で、選択が境界で振動しても必要な音声位置を失いにくくする。固定的に圧縮する方式と異なり、音声を読み進める生成の時間的な動きに対応する。

## 評価条件と比較の公平性

| 項目 | 条件 |
|---|---|
| 主なモデル | Voxtral-mini-3b-2507、Qwen2.5-Omni-3B |
| 拡張評価 | Voxtral-Small-24B |
| 英語ASR | LibriSpeech-Long test-clean 270件、test-other 207件、最大約4分の音声 |
| 言語・タスク転移 | LongSpeechの仏語ASR、英→仏音声翻訳、各200件 |
| ドメイン転移 | PriMock57の模擬医療診察音声 |
| 校正 | LibriSpeech-Long dev-cleanの独立50件 |
| 復号 | bf16重み、greedy decoding、各モデル標準のチャットテンプレート |
| 比較方式 | 無圧縮、Ada-KV、AudioKV、ArkVale、AffPool（音声トークン統合） |
| 圧縮範囲 | **音声トークン領域のみ**。指示テキストと生成トークンは全保持 |
| 主指標 | Word Error Rate（WER、低いほど良い）、GPU上音声KV保持率、転送量、デコード遅延 |

公平比較のため、Ada-KV、AudioKV、ArkValeも音声KVだけを圧縮するよう実装を調整している。元実装の全系列圧縮とは条件が異なる点に注意が必要である。WERは句読点等を正規化し、生成が止まらない方式の挿入誤差を抑えるため**正解のトークン長で出力を打ち切ったWER**を用いる。したがって元論文のWERや、非打切りWERとそのまま比較できない。

## LibriSpeech-Longの主な定量結果

### Voxtral-mini-3b

| 方式 | GPU音声KV保持率 | test-clean WER | test-other WER |
|---|---:|---:|---:|
| Full Cache | 100% | 6.79 | 8.86 |
| WnW | 約79.8% | 6.72 | 8.84 |
| WnW | 約60.0% | 6.71 | 8.84 |
| WnW | 約40.9% | 6.64 | 8.81 |
| WnW | 約22.3% | 6.23 | 8.87 |
| Ada-KV | 目標20% | 199.24 | 198.55 |
| AudioKV | 目標20% | 192.58 | 195.53 |
| ArkVale | 目標20% | 11.74 | 14.75 |

WnWはGPU上の音声KVを約22%に抑えても無圧縮に近いWERを維持した。test-cleanで無圧縮より小さいWERが出ているが、これは「圧縮が音声認識を改善する」と一般化する証拠ではない。著者はgreedy decodingの変動とWERの打切り条件に照らして、この小差を品質差の証拠とみなしていない。対照的にAda-KVとAudioKVは低保持率で生成停止に失敗し、正解長に打ち切ってもWERが100を超える。

ArkValeはCPUへ退避したKVを再取得できるため、静的圧縮より品質を保つが、20%では11.74/14.75でWnWより悪い。単にCPUから呼び戻せれば十分ではなく、現在生成している単語に対応した音声領域を**いつ**呼び戻すかが重要である。

### Qwen2.5-Omni-3Bと24Bでの負の結果

Qwen2.5-Omni-3Bでは無圧縮WERが13.87/16.80で、GPU保持率約21.8〜22.0%のWnWは15.31/18.42だった。Voxtralほど完全には品質を維持できず、test-cleanで1.44ポイント、test-otherで1.62ポイント悪化した。それでも同条件のAda-KV 116.04/119.86、AudioKV 131.30/128.27、ArkVale 16.99/21.16より低いWERを示した。

Voxtral-Small-24Bの20%条件では、無圧縮5.70/8.37に対しWnWは11.29/16.63となり、品質差は大きい。ArkVale 15.60/22.20、Ada-KV 110.51/113.05、AudioKV 95.02/98.74よりは良いが、**24Bでも無圧縮品質をほぼ維持した**と表現するのは不適切である。モデル規模が大きくなると、同じ保持率で品質を保つ難しさが残る。

### トークン統合方式AffPoolとの比較

Voxtral-mini-3bのAffPoolは20%保持でWER111.63/113.25、40%で67.08/75.14、60%で10.04/11.00、80%で6.47/8.94だった。プリフィルで音声トークンを統合してしまう方式は、後から必要な細部を元のKVとして復元できない。WnWの20%で6.23/8.87という結果との差は大きい。ただしAffPoolは入力トークン自体を減らしてプリフィル演算も削減するため、同じGPU上KV保持率でも最適化する処理の範囲が異なる。

## 言語・タスク・ドメインの一般化

20%保持率のLongSpeech仏語ASRでは、Full CacheのWER20.42に対してWnWは22.68、ArkValeは28.63、Ada-KVは112.91、AudioKVは105.00だった。英→仏音声翻訳のBLEUではFull Cache38.48、WnW38.21、ArkVale35.40で、WnWの低下は0.27ポイントだった。PriMock57の模擬診察ASRではFull Cache WER23.47、WnW24.23、ArkVale32.45、Ada-KV106.43、AudioKV103.83である。

校正を英語LibriSpeechから仏語LongSpeechへ切り替えた再実験では、英語test-clean WERが6.20→6.24、test-otherが8.85→8.89、仏語が22.43→23.55と変化した。tidalヘッドは85中76が一致し、anchorは5中2が一致した。少数のanchor選択が変わっても品質が大きく崩れない一方、仏語校正へ変えれば必ず仏語性能が改善するわけではない。

## アブレーションと実行時費用

20%保持率のVoxtral-mini-3bで、音声セグメントごとに初期保持位置を選ぶ方式のWERは9.78、全音声から一括で上位位置を選ぶ方式は13.11だった（当該アブレーションの構成条件）。セグメント枠がないと冒頭の注意シンクへ予算が偏り、後半区間の初期GPU常駐位置を失いやすい。

ヘッド分類の重要度にVSとHSの積を使う構成のWERは9.78、HSのみでは36.41、VSのみでは124.66だった。音声区間へ注意しているだけでは正答に重要とは限らず、損失感度が高いだけでも生成中に参照する音声位置を追跡できるとは限らない。両方を組み合わせて、CPU復元を与えるべきヘッドを選ぶ必要がある。

チャンクサイズの感度実験では、0.96秒でWER6.45、1.92秒で6.29、標準4秒で6.23、5.76秒で6.26、7.68秒で6.23だった。anchorヘッド数を1〜20へ変えてもWERは約6.20〜6.23であり、単一の厳密なパラメータ設定だけで成立する方式ではない。

CPU→GPU転送はtidalヘッド数に比例する。35 tidalヘッドで0.05MB/step・27.2ms/token、235ヘッドで1.04MB/step・27.8ms/tokenだった。著者の測定では転送増分に比べてデコード時間の変化は小さいが、CPUメモリの確保、ホスト・デバイス帯域、GPUへの転送スケジューリングは導入時に別途検証する必要がある。

## 既存研究との差

SnapKV、H2O、Ada-KV、AudioKV等の静的方式は、プリフィルまたは初期の注意で一度選んだKV位置を永続的に保持し、捨てた位置を後から取り戻せない。ArkValeやQuestのようなCPU退避・再取得方式は復元可能性を持つが、WnWは**音声の時間順序と単語対応を利用して、重要なヘッドの復元タイミングを生成中に決める**点に特徴がある。

さらに全ヘッドを同じ保存方式にせず、少数のanchorへ全量GPU保持を与え、品質に効くtidalへCPU退避・復元を与え、残りfixedを永久削除する。これによりCPU保持容量を無条件の完全ミラーより抑えられるが、fixedで捨てた情報は復元できない。GPU上の保持率だけでなく、CPU上の保持量もシステム全体のメモリ費用に含めるべきである。

## 限界

評価は主にオフラインの文字起こしと音声翻訳であり、リアルタイムに音声が到着し続けるストリーミング認識や、音声に対する自由質問・対話・要約の品質は検証されていない。Whisperのようなcross-attention型、transducer型、状態空間モデル型の音声システムは、同じ形の長さ依存の音声KVを持たないため、WnWの機構をそのまま適用できない。

オフライン校正には単語時刻の強制アラインメントと損失勾配が必要で、モデルを変更した際にはヘッド役割を再計算する必要がある。音声トークンの時間構造が弱い非転写タスクでは、anchorの注意が意味のある生成フロンティアを示すとは限らない。24Bモデルでは20%保持で無圧縮からのWER悪化が顕著であり、3Bの良好な結果を全規模へ一般化できない。

CPU→GPU転送は著者の測定条件では小さかったが、帯域の競合、PCIe環境、複数同時要求、CPU容量の不足などは未評価である。転送と注意計算をCUDA stream等で重ねる最適化も未実装であり、GPU保持率の削減だけを実サービスのスループット向上倍率とみなすことはできない。また非音声テキストKVを全保持するため、生成が長くなると総KV使用量は増え続ける。
