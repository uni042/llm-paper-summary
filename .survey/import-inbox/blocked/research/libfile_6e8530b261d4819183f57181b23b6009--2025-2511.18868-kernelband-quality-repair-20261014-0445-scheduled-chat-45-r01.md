# KernelBand：GPUカーネルの最適化候補をハードウェア実測と多腕バンディットで選ぶ

## 概要

GPUカーネルは、注意計算、行列積、正規化、融合演算などの処理をGPU上で実行する小さなプログラムであり、大規模言語モデル（LLM）の推論効率を左右する。高性能な実装では、演算量だけでなく、レジスタ圧迫、共有メモリ、キャッシュ利用、メモリ帯域、スレッド配置を同時に考える必要がある。コード生成LLMは動作するプログラムを作れるが、生成した候補のうちどの変形を試すべきかという探索判断は必ずしも得意ではない。

**KernelBand**は、この探索判断を文脈付き多腕バンディット（contextual multi-armed bandit、MAB）へ置き換える方式である。現在のカーネル候補と、タイル化・ベクトル化・演算融合などの戦略の組を一つの選択肢として扱う。似た実行挙動を持つ候補をまとめ、ハードウェアの律速に合わない戦略を除外した上で、過去の成功率と未探索の可能性の両方から次の候補を決める。LLMは選ばれた変形をコードとして実装し、コンパイルと正当性検査を通ったものだけが性能評価の対象となる。

183個のTritonカーネルを使った実機評価で、A100では正しく動く最適化候補を得られた課題の割合79.8%、元のカーネルに対する速度の幾何平均1.91倍となった。比較するGEAKはそれぞれ48.0%、1.34倍である。RTX 4090では1.74倍対1.44倍、H20では1.45倍対1.06倍だった。これらは個別カーネル最適化の評価であり、LLMサービングの初回トークン遅延や同時要求スループットを直接測定した結果ではない。

## 問題設定と背景

### コード生成と性能探索は異なる問題

同じ計算を行うGPUプログラムでも、タイルサイズ、メモリアクセス順序、演算の融合範囲、レジスタの使い方によって速度が大きく変わる。LLMがある実装を出力した後、次にどの変形を試すかを言語的な直感だけで決めると、既に飽和している資源を改善しようとしたり、同じ局所最適の周辺を繰り返し探索したりする。コードの構文が正しいことと、対象GPUで速いことは独立した性質である。

著者らは最適化を有向グラフとして表す。頂点は正しく動くカーネル、辺はあるカーネルへ一つの最適化戦略を適用して新しい候補を生成する操作である。目標は、対象GPUで実行時間が最小となる正しい頂点を見つけること。探索中は新しい候補が増えるため、選べる「候補×戦略」の組も増え続ける。固定個数の選択肢を持つ通常のバンディットとは違い、探索空間が実行に伴って拡大する。

### 多腕バンディットの意味

多腕バンディットでは、これまで高い報酬を得た行動を再び選ぶ**活用（exploitation）**と、まだ十分試していない行動を選ぶ**探索（exploration）**を両立させる。KernelBandでは、ある候補カーネルに戦略を適用し、実行時間が短縮した割合を報酬にする。失敗や性能悪化には報酬0を与える。ある選択肢の平均改善率が高くても、試行回数が少ない別の選択肢には不確実性に応じた探索価値が残る。

ただし、すべての候補に独立した統計を持つと選択肢の数が増え過ぎる。そこで著者らは、実行挙動の近い候補では同じ最適化が効きやすいという仮定と、ハードウェアの理論限界が改善幅の上限を与えるという仮定を利用する。この二つの仮定のもとで、候補空間をクラスタへ圧縮し、物理的に見込みの薄い変形を事前に除外できる。

## 手法

### 1. 実行特性を5次元へ写す

各カーネルの特徴ベクトルは、正規化した実行時間、スレッド当たりのレジスタ数、ブロック当たりの共有メモリ、スレッドブロックの次元、理論占有率（occupancy）の5項目からなる。占有率は、GPUの演算器に同時滞在できるスレッドブロックの割合に関係し、レジスタや共有メモリの使い過ぎで低下する。実行時間だけでは、速くない理由が計算能力不足なのか、メモリ待ちなのか、資源不足による並列度の低下なのか判別しにくい。

これとは別に、NVIDIA Nsight Computeでストリーミングマルチプロセッサ（SM）、主記憶（DRAM）、二次キャッシュ（L2）のスループットをピーク比として測定する。この三つは、どの資源が律速しているかを示す**ハードウェア署名（hardware signature）**である。特徴ベクトルは似た候補をまとめるため、署名は戦略を採用するか除外するために使う。両者は役割が異なる。

### 2. 動的クラスタ化で探索空間を圧縮

探索で増えた候補を、実行特徴ベクトルに対するKMeans法でクラスタ化する。標準設定は3クラスタで、10反復ごとに再クラスタ化する。各クラスタに属するカーネルは似た律速を持つとみなし、戦略の成功率をクラスタ単位で集計する。新しい候補が増えても、すべての候補×戦略を独立した腕として追跡する必要がなくなる。

Nsight Computeによる詳細プロファイルは一回あたり約10秒と高価であるため、各クラスタの代表カーネルだけをプロファイルし、その署名をクラスタ内の選択判断に用いる。これにより、候補が増えるたびに全てを詳細計測する負担を避ける。代表が十分似ていることが前提であり、クラスタ内部の異質性が大きければ誤った除外が起こり得る。著者らはクラスタの大きさと再クラスタ化間隔の感度を別途評価している。

### 3. ハードウェア制約付きの選択

最適化戦略は6種類で、タイル化（tiling）、ベクトル化（vectorization）、演算融合（fusion）、パイプライン化（pipeline）、演算順序変更（reordering）、アクセス・配置変更（access and layout）からなる。各戦略が改善を狙う資源を対応付け、代表カーネルの対象資源が75%以上飽和している場合、その戦略を選択肢から外す。これは理論的な改善余地を簡単な実測上限で近似する方法である。

残ったクラスタ×戦略の組に対し、上側信頼限界（upper confidence bound、UCB）を用いる。各組の平均報酬へ、試行回数が少ないほど大きい探索項を加える。論文の標準探索係数は2.0である。選ばれたクラスタ内からは、対象資源に残る余力が大きいカーネルほど高い確率で候補を抽出する。つまり「どの変形を」「どの実装へ」適用するかを、ハードウェア実測に基づいて段階的に選ぶ。

LLMへ選んだカーネルと変形戦略を渡し、新しいTritonコードを生成する。コードはまず実行可能か確認し、次に数値結果が元の実装と一致するか検証する。正しい候補だけを計測し、元の候補からの実行時間短縮率を報酬として更新する。最後に、見つかった正しいカーネルの中から最速のものを返す。コンパイル不能な候補や誤答する候補は速度が良くても採用されない。

### 4. 理論的な保証の読み方

原著は、戦略の期待改善率がハードウェア限界で上から抑えられること、実行特徴ベクトルが近いカーネルでは期待改善率も近いというリプシッツ連続性（Lipschitz continuity）を仮定する。このとき、平均後悔（regret、最善行動を選ばなかったための期待報酬差）の上界は、反復数 $T$、クラスタ数 $K$、許容戦略数、クラスタの直径に依存する形で表せる。主な項は $\sqrt{K|S_{valid}|\log T/T}$、近似誤差項はクラスタ直径に比例する。

これは「任意のGPUカーネルで必ず最適解に到達する」証明ではない。実行挙動が似ていても最適化の効果が大きく違う場合や、代表プロファイルがクラスタを代表しない場合は仮定が崩れる。探索回数を増やすほど推定誤差は下がるが、クラスタが粗すぎれば近似誤差が残る。この二つの交換条件を明示した点が、単なるLLMの反復修正手法との差である。

## 評価条件

| 項目 | 原著の設定 |
|---|---|
| 対象 | 修正済みTritonBench-G、183個のカーネル、13種類の演算カテゴリ、難易度5段階 |
| 対象GPU | GeForce RTX 4090、NVIDIA H20、NVIDIA A100 |
| ソフトウェア | CUDA 12.1、Triton 3.3.0、scikit-learn KMeans、Nsight Compute |
| コード生成モデル | 主にDeepSeek-V3.2。追加でGPT-5、Claude Opus 4.5、Gemini 3 Flash |
| 比較方式 | GEAK（反復改善エージェント）、Best-of-N（独立生成した候補の最速を選択） |
| 探索予算 | 1課題20反復、拡張感度評価では40反復 |
| クラスタ | 標準3個、10反復ごとに再計算、飽和判定75% |
| 正当性 | 実行エラー検査、torch.allcloseによる数値等価性検査 |
| 計測 | 各候補を10以上の入力形状で測定、形状別時間の合計比から課題速度倍率を算出 |
| 追加評価 | 50カーネルの代表部分集合でモデル・探索回数・クラスタ数・費用を比較 |

ここで**正しい実装率（Correct）**は、指定反復数の中で少なくとも一つ正しい候補を得られた課題の割合である。**高速化成功率（Fast@1）**は、最良の正しい候補が基準より速い課題の割合で、失敗課題は0として数える。**幾何平均速度倍率（geometric mean speedup）**は、各課題の基準実装に対する速度倍率の積の平均に対応し、極端な値の影響を抑える。表の標準方式では正しい候補が得られた課題だけを平均するため、正しい実装率も合わせて読まなければならない。反復数に対する曲線では、失敗・悪化を1倍へ戻すフォールバック方式も使っており、二つの平均を混同しない。

## 評価

### GPU別の速度・正当性・成功率

| GPU | 方法 | Correct (%) | Fast@1 (%) | 正しい課題での幾何平均速度倍率 |
|---|---|---:|---:|---:|
| RTX 4090 | Best-of-N | 31.1 | 10.0 | 0.96倍 |
| RTX 4090 | GEAK | 55.6 | 31.1 | 1.44倍 |
| RTX 4090 | KernelBand | 77.8 | 43.3 | **1.74倍** |
| H20 | Best-of-N | 29.3 | 15.9 | 0.99倍 |
| H20 | GEAK | 49.4 | 23.8 | 1.06倍 |
| H20 | KernelBand | 79.3 | 57.3 | **1.45倍** |
| A100 | Best-of-N | 31.2 | 16.8 | 0.98倍 |
| A100 | GEAK | 48.0 | 38.7 | 1.34倍 |
| A100 | KernelBand | 79.8 | 60.1 | **1.91倍** |

A100では幾何平均速度倍率がGEAKの1.34倍から1.91倍へ上がり、差は約42.5%である。正しい実装率も48.0%から79.8%へ上がる。RTX 4090でもGEAKの1.44倍に対し1.74倍、H20では1.06倍に対し1.45倍となる。最適化対象は注意、行列積、正規化、融合などの個別Tritonカーネルであり、これらの倍率をそのままLLM生成速度へ当てはめることはできない。

### 難易度とハードウェア適応

A100の難易度別では、容易なL1～L2でKernelBandの幾何平均2.23倍、GEAKは1.09倍、中程度L3で2.05倍対1.18倍、難しいL4～L5で1.75倍対1.54倍だった。全体の改善は難易度の低い課題だけによるものではないが、最難度群では差が小さくなる。RTX 4090では融合を選ぶ割合が18.5%、H20では12.8%であり、H20ではタイル化が10.0%、RTX 4090では7.6%だった。戦略配分がGPUごとの律速に応じて変わることを示す。ただし、この違い自体が最適化の因果的な証明ではなく、性能結果と組み合わせた傍証である。

### 反復数・クラスタ数の感度

50カーネルのH20部分集合で40反復まで探索すると、Best-of-Nは約1.05倍、GEAKは約1.13倍で早期に頭打ちとなる一方、KernelBandは39反復時に1.71倍まで伸びた。20反復時は1.48倍で、GEAKを37%上回る。クラスタ数が1～2の少数では10反復以下の短い予算に有利だが、20反復以上では3クラスタが有利になる。30反復時は3クラスタ1.66倍、2クラスタ1.58倍、5クラスタは1.54倍と、分割し過ぎると各選択肢の試行回数が不足する。したがって「クラスタを増やせば常に良い」わけではない。

### コード生成モデルを変えた場合

| コード生成LLM | Best-of-N | GEAK | KernelBand | KernelBand Correct / Fast@1 |
|---|---:|---:|---:|---|
| DeepSeek-V3.2 | 1.10倍 | 0.95倍 | **1.52倍** | 85.0% / 67.5% |
| GPT-5 | 1.14倍 | 1.07倍 | **1.72倍** | 81.6% / 65.3% |
| Claude Opus 4.5 | 1.17倍 | 1.30倍 | **1.82倍** | 89.8% / 73.5% |
| Gemini 3 Flash | 1.20倍 | 1.21倍 | **1.48倍** | 70.8% / 45.8% |

これは代表50カーネル部分集合でのモデル別比較であり、183件の全体表とは母集団が異なる。より高性能なコード生成モデルだけに依存せず、同じ探索制御が複数のLLMへ適用できることを示す。ただし、モデル間の費用やAPI制限が同じという意味ではなく、絶対速度倍率もモデルにより変化する。

### 戦略の成功率と探索費用

タイル化は選択頻度10.0%、成功率14.4%と失敗しやすいが、成功した変形のうち最終最速カーネルへ寄与した割合は61.5%と高い。ベクトル化は成功率57.1%だが最終最速への寄与は17.1%、融合は成功率75.0%、最終寄与55.2%である。成功しやすさと大きな改善を生む可能性が一致しないため、バンディットによる探索・活用の配分に意味がある。

原著の反復時間内訳では、LLM呼出しを直列化するとその時間が約87%を占める。まとめて推論すると、コンパイル34%、実行30%が大きな割合を占め、1反復の実効壁時計時間は129秒と報告する。固定費用0.50米ドル/カーネルの比較では、KernelBandが1.83倍、GEAKが1.35倍、Best-of-Nが1.22倍で、速度改善効率はGEAKより約35%高い。これは「最適化処理に支払う費用」当たりの最終カーネル性能であり、完成カーネルを運用する際のGPU利用料金を直接35%削減した値ではない。

### 構成要素除去から分かること

原著は、バンディット方策をLLMの言語的推論へ置き換えると速度倍率が0.97倍まで低下し、基準カーネルより遅くなることを示す。これにより、性能改善の中心が単にコード生成LLMを使うことではなく、ハードウェア情報と試行履歴を使って変形を選ぶ方策にあると分かる。クラスタ化、プロファイルに基づく除外、バンディット方策は独立した小技ではなく、拡大する候補集合から有望な探索を選び続けるために連動する構成要素である。

## 既存研究との差

GEAKはLLMが生成したコードを反復改善するエージェントであり、Best-of-Nは独立候補を複数生成して最速を選ぶ。どちらも有効なカーネルを見つけ得るが、KernelBandほど実行挙動に基づく探索方策を明示的に持たない。KernelBandは「LLMへ何を生成させるか」という前段の意思決定を最適化するため、特定のコード生成モデルへ依存しない。訓練によってGPUカーネル生成能力を高めるTritonRLなどとも、生成器自体を変えるか、生成器の探索を制御するかという違いがある。

また、従来の自動チューニングはタイルサイズなどの固定されたパラメータ集合を探索することが多い。KernelBandでは新しいカーネルが生成されるたびに探索空間が拡大する。そのため、候補の実行特徴をクラスタ化して過去の成功情報を共有し、物理的に効果の薄い変形を排除するという二つの工夫が必要になる。

## 限界

第一に、理論保証はハードウェアの改善上限と実行特徴空間での報酬の滑らかさという仮定に依存する。レジスタ数や占有率が似ていても、データ依存分岐やメモリアクセスの局所性が異なる場合、同じ最適化が効くとは限らない。第二に、75%という飽和判定は固定しきい値であり、測定ノイズやクラスタ代表の偏りによって、有効な戦略を早期に除外する危険がある。

第三に、実験対象は修正済みTritonBench-Gの183カーネルと3種類のNVIDIA GPUに限られる。CUDA以外のバックエンド、AMD/Intel GPU、マルチGPU通信カーネル、実サービスの多要求同時実行まで一般化した実測はない。第四に、正当性検査はtorch.allcloseと複数形状に基づくもので、全ての入力形状・数値境界条件・競合状態で完全に正しいことの形式的証明ではない。

第五に、最適化そのものにコード生成LLMの費用、コンパイル時間、プロファイル時間がかかる。カーネルを一度だけ実行する用途では、最適化に支払った費用を回収できない可能性がある。第六に、幾何平均速度倍率は正しい候補を得られた課題に条件付けられており、失敗課題を含む実運用性能の解釈にはCorrectとFast@1を併記する必要がある。

第七に、対象カーネルの改善をLLM推論エンジン全体の性能へ換算するには、対象カーネルが全処理時間のどれだけを占めるか、前後のデータ転送や同期がどの程度残るかを測る必要がある。原著はその統合ベンチマークを示していないため、vLLMやSGLangの配信性能が1.91倍になるとは結論できない。
