# VPP：長文脈の分割済み入力処理における仮想パイプライン並列

## 研究の目的と対象

本論文は大規模言語モデルの長い入力を分割して先行処理する分割済み入力処理（chunked prefill）に、モデル層を装置へ割り当てるパイプライン並列（pipeline parallelism; PP）を組み合わせたときの装置待ちを減らす研究である。入力の事前処理（prefill）は多数トークンを同時に計算するため、長い要求が装置を占有すると後続要求の最初のトークンまでの時間（time to first token; TTFT）や他要求の復号間隔に影響する。入力をチャンクへ分けると短い要求を途中へ差し込めるが、複数装置を直列に通るチャンク間には新たな負荷不均衡が生まれる。

通常の分割済み入力パイプライン並列（chunked prefill pipeline parallelism; CPP）はチャンクのトークン数を固定する。しかし因果注意では後半チャンクほど、それ以前の長い鍵値キャッシュ（KV cache）を参照する。したがって同じトークン数でも後半チャンクの注意計算時間が長く、前半チャンクと後半チャンクが同じ速度で進まない。これが段間の待機、いわゆるパイプラインの空白（pipeline bubble）を作る。

動的分割済み入力パイプライン並列（dynamic chunked prefill pipeline parallelism; DCPP）は、各チャンクの処理時間が近くなるよう後半チャンクのサイズを小さくする。著者の測定では、長文脈では分割数が増えることで小さな演算の起動回数、スライス操作、装置間転送が増加し、負荷均衡による節約を上回った。VPPはチャンクの大きさを固定したまま、**実行段の並べ方**を変えて異なる長さの処理を相殺するという発想である。

## 主要機構：入力・処理・出力

### 1. 固定長チャンクの処理時間がほぼ線形に増えることを利用する

同じ長さの入力チャンクを `C_0, C_1, ...` とし、各チャンクの各仮想段での処理時間を `τ_k ≈ (k+1)t` と近似する。`t` は先頭チャンクの一段あたりの時間である。後半ほど参照する過去の鍵値が長くなるため、注意計算が支配的な構成ではこの増加傾向が現れる。これは厳密な計算量恒等式ではなく、論文が測定から採用したスケジューリング上の近似である。

従来は時間が同じになるようチャンク境界を変更する。提案方式はチャンクを固定したまま、遅い中央処理と、前後の軽い処理を別装置で同時に進める。入力は固定長のチャンク列と層割当て、出力は各チャンクが順に通る仮想段の実行順序である。チャンク境界の再推定や動的な分割に伴う細粒度演算を増やさずに、計算負荷の増加規則を利用する。

### 2. 二つの物理段に四つの仮想段をV字配置する

論文の基本構成は物理パイプライン段 `pp0` と `pp1` の二つである。モデルを四つの仮想段 `s0,s1,s2,s3` に分割し、入口 `s0` と出口 `s3` を `pp0` に、中央の `s1,s2` を `pp1` に置く。各チャンクは `pp0(s0) → pp1(s1,s2) → pp0(s3)` と折り返して処理される。これがV字仮想段巡回（V-shaped virtual-stage traversal）である。

中央段がチャンク `C_k` の `s1,s2` を処理する時間は約 `2(k+1)t`。その間、入口・出口を担当する物理段は前のチャンク `C_(k-1)` の出口処理と、次のチャンク `C_(k+1)` の入口処理を実行できる。両者の時間はそれぞれ `kt` と `(k+2)t` で、合計は `2(k+1)t` になる。中央段の処理時間とほぼ一致するため、後半チャンクの長い注意処理を、隣接チャンクの軽い処理で埋められる。

この一致は重要な設計条件でもある。専門家混合（mixture of experts; MoE）の専門家並列（expert parallelism; EP）による固定費が小さく、注意時間が主に支配する場合に成立しやすい。注意の計算量が接頭辞長にあまり依存しない疎注意モデルや、専門家通信の比重が大きい構成では線形近似が崩れ、段間待ちが再発し得る。

### 3. 非同期通信と局所実行順序の入替え

V字配置では中間活性化を二つの物理段の間で往復させる。同期送受信だけを用いると、両装置が互いの転送完了を待つ場面ができ、計算時間を埋めても通信待ちが残る。そこで非同期通信版（VPP-Async）は、物理段上で前チャンクの出口段と次チャンクの入口段の実行順序を入れ替える。必要な接頭辞鍵値が既に用意されているという依存条件を守ったうえで、片方が計算している間にもう片方の通信を進める。

論文実装では二つの交互のHCCL通信グループを使って双方向の一対一送受信を行い、相互待ちを防ぐ。制御面はPythonで実装し、vLLM V1の実行機構を二つの待ち行列へ拡張する。最初の仮想段を待つバッチと、折返し後の後半段を待つバッチを分離し、進行中バッチを追加で一つ保持する。非同期タスクを利用するため、スケジューラ全体を通信完了まで停止させない。

### 4. 要求をまたぐ詰め込みで排出時の空白を埋める

一つの長い要求の末尾では、最後のチャンクがV字経路を抜けるまで、片方の装置に処理すべき仕事がなくなる。非同期通信だけではこの排出空白（drain bubble）を消せない。次の要求が既に待機している場合、次要求の軽い先頭チャンクを前要求の末尾空白に差し込む要求間パイプライン詰め込み（pipelined packing）を行う。

これにより、前要求のパイプライン排出と次要求の充填を重ねる。次要求が存在しない単発処理ではこの追加利得は期待できず、複数要求が流入するサービングで効果が出る。論文はV字配置だけの版、非同期通信追加版、要求間詰め込みまで含む完全版を分けて構成要素除去評価を行っている。

### 5. 実装境界

実装はvLLM-Ascend上のPython制御面とPyTorch、HCCLによる通信で構成され、注意カーネルや専門家カーネルを一から置き換える方式ではない。モデル層のV字折返し配置、仮想段の状態機械、非同期転送の制御が主な変更点である。層を不均等に割り当てる機能や利用者指定の層範囲にも対応する。論文が公開先として明記するのは `RookieCoder-Camera/vllm-ascend` の `vpp-dev` ブランチであり、標準のvLLMや標準のvLLM-Ascend本流へ統合済みとは主張しない。実験はAscend NPU環境であり、CUDA上の通常vLLMにそのまま適用できるとは限らない。

### なぜ動的分割が逆転負けするのか

著者の動機付け評価ではDeepSeek-V3.1の512K入力で、固定CPPの呼出し回数が22に対して動的DCPPは97に増えた。動的方式は空白時間を38.64秒から20.47秒へ削減したが、計算時間は252.59秒から279.07秒、露出通信は16.67秒から22.68秒へ増えた。合計は307.90秒から322.22秒へ悪化し、初回トークン遅延は約4.65%長くなった。これは負荷均衡だけを最適化すると、演算粒度の細分化に伴う損失を見落とすことを示す。

| パイプライン空白 | 20.47秒 | 0.39秒 | **-20.07秒** |
| 露出通信 | 22.68秒 | 30.63秒 | **+7.95秒（悪化）** |
| プロファイラ上の正味差 | — | — | **-40.36秒** |
| 注意カーネル | 228.13秒 | 233.08秒 | **+4.96秒（悪化）** |
| Sliceカーネル | 22.90秒 | 5.18秒 | **-17.72秒** |
| MatMulV3 | 13.06秒 | 2.54秒 | **-10.52秒** |

注意カーネルの合計時間はむしろ約2.17%増えている。したがって「注意演算自体が高速になった」と説明するのは誤りである。動的分割の細粒度化によって生じたスライスと行列積の固定費が減り、空白が大幅に短縮した結果、通信の露出増加を上回った。動的方式はVPPの約4.8倍のカーネル呼出しと約4.7倍のホスト起動を実行していた。

**負の結果も重要である。** VPPはDCPPより露出通信が7.95秒、約35%増加した。補助的な全体収集通信（AllGather）は呼出し回数が減ったにもかかわらず、一回あたりの平均遅延が増え、全体の補助通信時間が悪化した。一方、計算と重なった通信時間は0.01秒から32.86秒へ増え、重畳比率は0.05%から51.75%へ上がった。通信を単純に減らす設計ではなく、通信が待ちとして表に出る時間を管理する設計である。

### 構成要素除去とチャンク長感度

DeepSeek 256K、32Kチャンク、同時3要求の比較では、V字配置だけの版に非同期通信を追加すると終端遅延が3.13%改善し、さらに要求間詰め込みを加えると基準のV字配置に対して6.89%改善した。空白比率は11.0%→8.3%→2.4%と段階的に低下する。計算時間自体の差は最大0.82秒（0.42%）で、利得の主体がカーネル高速化ではなくスケジュール改善であることを裏付ける。非同期通信により露出通信は48%減り、重畳比率は0.02%から54.03%へ増えた。要求間詰め込みは境界の空白時間を33.2%削減した。

チャンク長の8K〜32K探索では、**24Kが多くの条件で最良**だった。文脈長を割り切らないチャンク長にすると末尾が小さなチャンクになり、排出期間の空白へ収まりやすいからである。これは単純に大きなチャンクほどよい、または常に均等に分割するのがよいという考えに反する。例外としてDeepSeekとGLMの64K入力では、パイプラインが定常状態へ入る前に処理が終わり、小さいチャンクの方が有利になった。

## 既存研究との差

**通常CPP**は入力を細分化して他要求と交互に処理するが、固定長チャンクの後半ほど遅くなる問題を残す。**DCPP**は実行時間を予測してチャンク長を動的に変えるが、長文脈で呼出し数と通信境界を増やす。本研究は固定長のまま層配置と実行順を変えるため、均衡化と演算粒度の維持を両立しようとする。

**従来のパイプライン並列のマイクロバッチ制御**は学習時の充填・排出や段間待ちを改善するが、本研究の特徴は因果注意の接頭辞長に伴うチャンク遅延増加を利用し、前後のチャンクをV字配置の二つの物理段で組み合わせる点にある。**単純な非同期通信**だけでは排出空白は埋まらず、**要求間詰め込み**だけでは段間の計算不均衡は残る。三機構を区別して評価した点がシステム上の貢献である。

## 適用限界・再現条件

1. **線形遅延増加の仮定**：固定長チャンクの注意時間が接頭辞長とともにほぼ線形に増えることがV字均衡の根拠である。疎注意を使うGLM-5.2では増加が鈍化し、長い入力で空白が再発する。異なる注意方式へ同じ配置を適用する場合は遅延形状を再測定する必要がある。
2. **実験は二つの物理パイプライン段**：四仮想段のV字配置はPP2の評価であり、より深いパイプラインや異種装置の最適な段配置は未確立である。
3. **装置依存**：実装は16基のAscend 910C、HCCL、vLLM-Ascendを対象とする。NVIDIA CUDA、ROCm、CPU推論、異なる相互接続で同じ性能差が得られるとは限らない。
4. **入力処理限定の測定**：出力を1トークンに固定しており、長い応答の復号を含む端から端までの実サービング指標は追加検証が必要である。
5. **短文脈の負の結果**：Qwenの短い入力ではCPPより最大6.8%低速。活性パラメータが少なく計算が短いと、仮想段制御の固定費が相対的に大きい。
6. **通信の増加**：V字折返しは双方向転送を伴い、露出通信が増える条件がある。計算との重畳で隠せることが前提であり、通信帯域が狭い構成での優位性は未証明。
7. **要求間詰め込みの前提**：後続要求が待機していない単発処理では、排出空白へ次要求を入れる効果が得られない。
8. **実装公開先の区別**：論文が示す開発ブランチの存在は確認できるが、標準vLLMの正式機能として導入済みであるという証拠ではない。

## 実装者向けの検証手順

再現時は同じモデル・並列度・チャンク長でCPP、DCPP、VPPを比較し、チャンクごとの注意時間が本当に線形増加するか確認する。次に段間空白、露出通信、カーネル起動回数、ホスト起動回数を個別に計測する。V字配置だけ、非同期通信追加、要求間詰め込み追加の三構成を比較すれば、どの改善が自分の装置で効くか判断できる。特に疎注意、低活性パラメータ、短文脈、後続要求なしの条件を別々に測り、論文の最大13.1%だけで採否を決めない。通信が増えても全体が速くなるかを確認するには、通信の総量だけでなく、計算と重なった時間とクリティカルパス上の露出時間を区別する必要がある。
