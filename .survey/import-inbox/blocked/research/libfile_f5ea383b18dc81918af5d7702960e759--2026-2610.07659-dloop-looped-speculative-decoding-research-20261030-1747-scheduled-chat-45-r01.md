# DLoop：複数draft blockを一度のtarget検証へまとめる投機的復号

## 概要

投機的復号では軽量な下書きモデルが候補トークンを生成し、大きな対象モデルがまとめて検証する。標準方式は「ドラフトを一段実行→対象で検証」を交互に繰り返すため、ドラフトが非常に高精度で全候補が採択される場合でも、ブロックごとに対象の順伝播 passが必要となる。対象の検証はドラフトに比べて高コストであり、検証トークン数が多少増えても一回の順伝播 passの時間は大きく増えない。この性質を利用し、**検証前に複数のドラフト段を連続実行する**のがDLoopである。

従来の適応型 ドラフト 長さは、autoregressive drafterの生成を途中で打ち切ることには有効だが、並列 drafterでは1 ブロックの順伝播 passがすでに実行されているため途中停止してもドラフト計算を削減できない。さらに並列 drafterは、未検証トークンに対応する対象 隠れ 状態を持たず、次ブロックを条件付けると学習時と異なる入力分布になる。DLoopは推論時の信頼度 ゲートと学習時のloop-aware 学習を組み合わせ、autoregressive/並列の両方へ適用する。

研究の対象は対象モデルを変更しない無損失 投機的復号である。ここで無損失とは、検証時に標準の受理率 規則を適用することで**対象が定める出力分布を維持する**ことを意味する。ドラフトが常に正しい、あるいは生成テキストの意味的正確性が向上するという意味ではない。DLoopは追加のドラフト 順伝播 passを支払い、より高価な対象 順伝播 passの回数を減らす計算交換である。

## 標準方式との違い

### 通常のdraft–verify交互実行

一回のドラフト 段がk個の候補を生成すると、対象はこれらを一括検証し、先頭からa個を採択したあと対象由来のbonus トークンを一つ生成する。標準方式では1回の検証から最大k+1 トークンが得られる。たとえk個すべて採択されても、次のドラフト 段の前に検証が挟まる。EAGLE-3のようなautoregressive drafterも、DFlashやDSparkのような並列 drafterも、この交互構造のコストを持つ。

DLoopは1回の検証がS個のドラフト 段、合計Sk個の候補を扱う。全採択なら一回の検証で最大Sk+1 トークンを得る。S回の標準検証と比べると中間のbonus トークンをS-1個得る機会は失うが、代わりに対象 順伝播 passをS-1回省略できる。実際に採択されるトークン数はゲートの誤判定に左右され、早い段の候補が拒否されれば後続段で生成した候補はすべて捨てられる。この無駄がDLoopの主要なトレードオフである。

### Confidence-gated drafting loop

各ドラフト 段の出力トークンについて、ドラフトが付与した対数確率ℓ_iを合計し、ブロック 信頼度 c_s = Σℓ_iを計算する。c_sが固定閾値g以上なら次の段を続け、下回ればそこまでの候補を対象へまとめて検証する（§3.2、式2）。対数確率は非正なので、ブロック内に低信頼トークンがあると和が下がる。これは最初の拒否以降を破棄する検証規則と整合する。ゲート自体に新たな学習ヘッドは不要で、すでに計算済みのlog probabilityを集計する。

この閾値は実行前に選ぶハイパーパラメータであり、完全な自動最適化ではない。論文はg∈{-0.25,-0.5,-0.75,-1.0}を掃引し、8ベンチマーク平均高速化倍率で選択する。多くの構成では-0.5、EAGLE-3とQwen3-8Bの組合せでは-0.75を使用する。gを下げてloopを長くすると平均採択長は増えても、後続候補の破棄とドラフト時間が増えて速度は悪化し得る。Appendix A.7.1はその具体的な負の結果を示す。

### 未検証tokenのhidden stateとloop-aware training

通常のドラフト 段は対象が計算済みの隠れ 状態を入力として使える。しかし2段目以降のトークンはまだ対象検証前なので、対応する対象 隠れ 状態は存在しない。DLoopは、既存の対象側接頭辞 隠れ 状態に、先行ドラフト 段自身が生成した隠れ 状態を連結して次段へ渡す（式3）。これにより新しい対象 順伝播 passなしで複数段を進められるが、通常の下書きモデルはその長い自己状態の連鎖を学習していない。

loop-aware 学習は追加段数S-1を1〜Nからサンプルし、最初の段には対象側接頭辞を、以降にはドラフト自身の隠れ 状態連鎖を与える。損失は最初の段のCEと最後の段のCEの平均とし、中間段は隠れ 状態を供給するが損失を掛けない（§3.3、式4）。最初の段の品質を維持しつつ、最も長い連鎖を通った難しい最後の段へ学習信号を与える狙いである。既存下書きモデルの構造やパラメータ数は変えず、追加の対象 順伝播 passも必要としない。一方でドラフトの再学習コストは確実に発生する。

論文はN=3を採用し、追加段を1〜3段学習させる。Appendix A.7.3ではNを5へ増やしても一貫した改善はなく、学習時間・メモリが増える。中間段へもCEを掛けるmid-CEは採択長と高速化倍率を下げ、DSparkのN=5ではOOMになる。**中間監督を増やせば良くなるわけではない**という負の結果が明確である。

## 実装と評価プロトコル

対象対象はQwen3-4B/8B、Qwen3.5-9B、Gemma-4-12B。ドラフト方式はEAGLE-3、DFlash、Domino、DSpark、モデル付属のMTP moduleで、DFlashとDominoのブロック サイズは16、DSparkは7、Qwen3.5-9BのMTPは3、Gemma-4-12BのMTPは6。tree 検証も元の方式に従い、DFlashはDDTreeの最大256 nodes、Domino/DSparkはDARTreeの64 nodesを使用する。異なるtree budgetの比較を、ドラフト algorithmだけの純粋な優劣と混同しない。

公開済み下書きモデルの重みからloop-aware 学習を1 epoch実施する。PerfectBlendの130万user プロンプトに対し、各対象モデルが生成した応答を教師として使用する。MTP専用の学習recipeがない構成ではEAGLE-3のrecipeを流用するため、モデル付属MTPと専用ドラフトの学習条件は完全には一致しない。学習を含む追加準備コストは、推論時の高速化倍率と別に扱う。

評価はGSM8K、MATH-500、AIME25の数学3件、HumanEval、MBPP、LiveCodeBenchのコード3件、MT-Bench、Alpacaのチャット2件の計8件。通常の主結果はgreedy 復号（temperature 0）で、Appendixにはtemperature 1の採択長も掲載する。Appendix A.1ではGSM8K/MATH-500/MBPP/LCB/Alpacaはそれぞれ128 標本、AIME25は30、HumanEvalは164、MT-Benchは80を使用し、shuffle 乱数種 0、thinking mode無効、システム プロンプトなしとする。したがって論文の8件平均は各タスク全件を等重みで評価した大規模production トレースではない。

すべての学習・通常評価はNVIDIA H100 80GB、bf16で実施。主指標は一回の対象検証で平均採択されるトークン数τと、対象単独autoregressive 復号比の実時間 高速化倍率。τの増加率と実際の速度増加率は異なる。追加ドラフト時間が大きければτが増えても速度は上がらない。Appendix A.3にはSGLangでのconcurrency 1〜32のスループット測定もあり、単一要求とバッチ運用の差を確認できる。

## 評価結果：採択長とwall-clock speedup

| Target・ドラフト方式 | 通常方式（τ / 高速化倍率） | DLoop追加（τ / 高速化倍率） | 比較 |
|---|---|---|---|
| Qwen3-4B / EAGLE-3 | 6.92 / 3.35× | **9.63 / 3.77×** | τ+39%、速度+12.5%程度 |
| Qwen3-4B / DFlash | 6.10 / 4.19× | **7.21 / 4.67×** | 速度約+11.5% |
| Qwen3-4B / Domino | 7.08 / 4.38× | **7.90 / 4.58×** | 速度約+4.6%と改善幅は小さい |
| Qwen3-4B / DSpark | 5.47 / 3.77× | **8.59 / 4.76×** | 速度約+26.3% |
| Qwen3-8B / DSpark | 5.58 / 3.81× | **9.08 / 4.82×** | 速度約+26.5% |
| Qwen3.5-9B / MTP | 3.32 / 1.55× | **6.70 / 2.18×** | τ約2倍、速度約+40.6% |
| Gemma-4-12B / MTP | 4.86 / 3.17× | **7.50 / 3.68×** | 速度約+16.1% |

Table 1の速度は**対象単独autoregressive 復号に対する倍率**である。DLoopの「5〜41%改善」は、同じドラフト方式にDLoopを追加する前後の高速化倍率倍率の比であり、対象単独比で5〜41倍という意味ではない。たとえばQwen3-4B/DSparkは3.77×から4.76×で、改善は(4.76/3.77−1)≈26.3%となる。MTPのQwen3.5-9Bは1.55×から2.18×なので約40.6%である。

採択長τの増加は速度改善の必要条件とは限らない。Dominoではτが7.08→7.90と伸びても速度は4.38→4.58×で約4.6%にとどまる。ドラフト 順伝播 passの追加コストがあるからである。チャットでは数学より全採択率が低く、DLoopの改善幅も小さい。Table 1のQwen3-4B/DSparkで数学高速化倍率は4.36→6.02×だが、チャットは2.62→2.71×にとどまる。用途ごとの改善率の差は大きい。

### Ablation：loop単独と再学習の相乗効果

Table 2ではloopだけ、loop-aware 学習だけ、両方を分けて比較する。Qwen3-4B/DFlashは通常4.19×、loopのみ4.16×、学習のみ4.23×、両方で4.67×。loop単独ではわずかに遅くなるが、再学習と組み合わせると改善する。Gemma-4-12B/MTPも通常3.17×に対してloopのみ2.90×と**明確に逆効果**であり、両方を適用して3.68×になる。したがって「信頼度 ゲートだけ付ければ既存下書きモデルが高速化する」とは言えない。未検証状態の連鎖を学習することが重要である。

Appendix A.4ではQwen3-4B/DSparkでドラフト 段回数が91,851→114,391（+24.5%）に増える一方、対象 検証は91,851→70,978（-22.7%）となる。tree 検証込みではドラフトが+37.9%、検証が-26.9%。より安いドラフトを多く実行して高価な検証を減らす、という機構が実際の実行回数で裏付けられる。Appendix A.5ではQwen3-4B/H100、1024-トークン 接頭辞でDSparkのドラフト時間がS=1の3.90msからS=4の15.04msへ増える一方、検証は22.45→24.32msと比較的小幅である。ゲート時間は1 loop最大0.33msと記載される。

### 同時実行時の負の結果

SGLangでQwen3-8Bを提供したAppendix A.3のMATH-500 スループットでは、DFlashがconcurrency 1で907 tok/s、DLoop追加で972 tok/sへ改善する。しかしconcurrency 16では9,484→9,189 tok/s、32では11,810→11,139 tok/sへ**低下**する。HumanEvalでもconcurrency 32で9,451→9,104 tok/sへ低下する。DSparkではMATH-500の32並列で12,265→12,820 tok/sと改善するが、HumanEvalの32並列は10,926→10,825 tok/sへわずかに悪化する。単一要求の高い高速化倍率は高並列時の高いスループットを保証しない。

これはGPUが大きなバッチで飽和すると、追加ドラフトがバッチ容量を消費し、対象検証回数削減の利得が相殺されるためと論文は説明する。また各要求のloop深さSが異なるため、ドラフト側は不均一な長さの実行となり、paddingの無駄または動的再編成のスケジューリング費用が必要になる。これらはproduction 推論提供へ統合する際の未解決の実装課題である。

## 限界・サーベイでの解釈

第一に、DLoopの無損失性は対象の検証規則を維持することに依存する。信頼度 ゲートは採択を予測するだけであり、誤予測した候補は対象が拒否する。したがって品質を下げずに高速化できるが、採択率の低いタスクではドラフトを余分に実行して損をする。全タスクで一定の利得があるとは限らない。

第二に、loop-aware 学習は追加パラメータを必要としないが、既存ドラフト重みの再学習を要する。PerfectBlend由来130万プロンプトと対象応答の生成、1 epochの追加学習は無償ではない。モデル固有のドラフト ヘッドやMTPに公式の学習recipeがない場合は別方式を流用しており、他のモデル familyへの適用時に同じ性能が得られるかは未検証である。

第三に、ゲート閾値はベンチマークで事前に選択しており、入力分布・GPU負荷・バッチ数に応じてオンラインで自動再調整する仕組みではない。Appendix A.7の閾値掃引は採択長と速度のトレードオフを示し、深いloopほど良いという単純な関係を否定する。N=5や中間段監督も追加コストに見合う改善がなかった。

第四に、主要実験はH100 80GB、bf16、比較的小さな対象モデル（4B〜12B）に限られる。70B級対象、低帯域のコンシューマGPU、CPUオフロード、MoEの専門家 入替え、ネットワーク越しのドラフト/対象分離などでは、ドラフトと対象の相対コストが変わる。これらの環境に5〜41%をそのまま外挿しない。高並列でスループットが逆転する実測は特に重要である。

第五に、実装URLはarXiv v2で「will be available」と記載されているため、`code`に著者指定URLを記録しつつ、現時点で公開済み・再現済みとは判定しない。評価のサンプル数、ゲートの掃引値、モデルの学習recipeとバッチ条件を合わせて独立再現する必要がある。

本研究は、EAGLE-3などのドラフトの予測能力を直接高める研究とは異なり、**対象検証の発火タイミングをドラフト ブロック単位で最適化する制御手法**である。高い全採択率と対象 順伝播 passの相対的高コストが揃う場合に有利で、推論サーバーの高負荷領域ではbatchingと一体で評価する必要がある。
