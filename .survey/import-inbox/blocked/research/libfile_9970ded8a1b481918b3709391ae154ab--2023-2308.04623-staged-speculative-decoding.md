# Accelerating LLM Inference with Staged Speculative Decoding

## 書誌情報
- 著者: Benjamin Spector, Chris Re
- canonical identity: `arXiv:2308.04623`
- 公開: 2023-08-08、ES-FOMO at ICML 2023
- 一次資料: https://arxiv.org/abs/2308.04623

## 概要

小batchの自己回帰decodeでは、1 token生成するたびに大きなmodel weightを読み直すため算術強度が低く、GPU演算器よりmemory bandwidthが先に飽和する。論文のGPT-2 Large 762M・RTX 4090例ではbatch 1の算術強度は約1で、約1.4 GFLOP/tokenしかないにもかかわらず150 token/s、GPU計算利用率0.13%に留まる。

通常の投機的復号（speculative decoding）は、小さいdraft modelが数tokenを先読みし、大きいoracle modelが一括検証することでweight読出し1回あたりの確定token数を増やす。ただし1本の候補列を長くすると、draftとoracleが連続して一致する確率が指数的に下がり、batchを大きくしても利得が飽和する。またdraft model側も小batchではmemory-boundであり、長い候補列を作る時間が無視できなくなる。

Staged Speculative Decodingは、候補を1本の列ではなくtreeにし、同じ深さで複数候補をoracleへまとめて検証する。さらにoracle→draftの1段だけでなく、draft modelをさらに小さいdraft²で投機実行する。評価では762M oracle、40M draft、Katz backoff trigram draft²を使い、HumanEvalの164 promptでdeterministic時475 token/s、baseline 150 token/sに対して3.16倍、通常speculative 350 token/sに対して1.36倍を得た。

## 問題設定

通常speculative decodingの効率は、draft modelの速度とoracleとの一致率の積で決まる。大きいdraftは一致率が高いが生成costも高く、小さいdraftは安いがrejectが増える。論文ではoracleの15〜20分の1程度が経験的に良いとしつつ、speculative batchを大きくするとdraft側の生成時間がoracle検証より支配的になることを問題視する。

また候補を1本のsequenceにすると、深さdまで全tokenが一致する確率が急速に下がる。そこで「深く1本」へ計算を使う代わりに、浅い位置で第2・第3候補へ枝分かれさせる方が、oracle 1回あたりに受理される期待token数を増やせる。

## 手法

### 1. Tree-structured speculative batch

draft modelのtop候補を一本道にせず、複数token列をtreeとして構築する。長い末端へ計算を集中させず、序盤で幅を持たせることで、oracleが実際に選ぶpathがbatch内に含まれる確率を上げる。

treeにはleafが多いため、draft modelを実行するのは主にinternal nodeで済み、oracleへ渡す候補数に対するdraft計算回数を減らせる。また同じdepthのnodeは並列にdraftへ通せるため、小draft自身の算術強度も上げられる。

### 2. Tree attentionの実装

oracle検証では各candidateが自分のancestorだけを見る必要がある。論文はdecode attentionを、既存KV cacheへのcross-attentionとbatch内self-attentionに分け、position embeddingとcausal maskをtree構造に合わせて設定する。

batch全体で生成された新KVは一旦別領域へ保持し、oracleでsampleされた実pathに対応するsliceだけをmain KV cacheへappendする。これにより候補枝を並列検証しても最終生成分布を変えない。

### 3. Staged Speculation

draft model自身の候補生成もmemory-boundなので、さらに小さいdraft² modelでdraftを投機実行する。最終構成は `oracle → draft → draft²` の3段で、各段の安いmodelが次段のweight読出し回数を減らす。

実験ではoracleにGPT-2 Large 762M、draftにGPT-2 40M、draft²にKatz backoff trigramを使用する。trigramはdraft modelからtemperature 1.5で2時間生成した120M tokenを使って構築されている。

### 4. Lossless verification

最終tokenはすべてoracle modelによって検証される。deterministic decodingではoracleと一致するbranchだけをcommitし、sampling時もrejection samplingの考え方を維持するため、速度向上のためにoracle出力品質を近似へ置き換える方式ではない。

## 評価条件

| 項目 | 条件 |
|---|---|
| oracle | Python subset of The Stackでfine-tuneしたGPT-2 Large 762M |
| draft | GPT-2 40M |
| draft² | Katz backoff trigram |
| GPU | quiesced NVIDIA RTX 4090 |
| workload | HumanEval 164 prompts |
| sampling | deterministic、top-k (`k=50`, `T=1`) |
| 比較 | token-by-token baseline、通常speculative decoding |
| 指標 | token/s、相対memory bandwidth、prompt別speedup |

## 主要結果

| 条件 | Baseline | 通常Speculative | Staged | 読み取り |
|---|---:|---:|---:|---|
| deterministic throughput | 150 token/s | 350 token/s | 475 token/s | baseline比3.16×、通常speculative比1.36× |
| top-k throughput | 150 token/s | 219 token/s | 298 token/s | baseline比1.98×、通常speculative比1.36× |
| deterministic相対bandwidth | 1.00 | 0.31 | 0.23 | oracle weight読出しあたり確定token数を増加 |
| top-k相対bandwidth | 1.00 | 0.48 | 0.35 | stochastic rejection下でもbandwidth削減 |

samplingではdraft候補のrejectが増えるためdeterministicより倍率が下がるが、それでもstaged方式は通常speculativeを上回る。promptごとの効果幅は大きく、論文では現実的promptで2倍程度から最大10倍まで振れると報告する。空白や定型codeのような低entropy部分はtrigramでも当たりやすく、難しいtokenほど大きいmodelへ委ねられる。

## 既存研究との差

通常のspeculative decodingは「1つのdraft modelが1本の候補列を作る」。本研究は候補集合をtree化して横方向の可能性を増やし、さらにdraft自体を別のspeculatorで高速化するため、候補構造とmodel階層の両方を多段化する。

量子化やFlashAttentionのように1回のmodel forwardを軽くする方式とは異なり、Staged Speculationは高価なmodel forward 1回で複数tokenを確定させることでmemory bandwidth消費を減らす。そのため小batch・memory-bound条件で特に意味があり、他のkernel/quantization最適化と原理的に併用できる。

## 限界

評価oracleは762M GPT-2 Largeで、現在の数十B級LLMや大規模serving batchではない。論文自身も小batch・端末内推論を対象としており、batchが大きくcompute-boundになるserver workloadへ同じ倍率を外挿できない。

実装にはPython infrastructure由来の約35% overheadがあり、絶対値は実装品質にも左右される。一方でより大きいmodelなら固定overheadを償却しやすいという見込みは示すが、本論文では大model実測をしていない。

効果は生成entropyに強く依存する。低entropyなcode/whitespaceでは小modelが多くのtokenを当てられる一方、高entropy生成ではoracle依存が増え、speedupが縮む。top-k samplingで3.16倍から1.98倍へ落ちる結果もこの制約を示す。
