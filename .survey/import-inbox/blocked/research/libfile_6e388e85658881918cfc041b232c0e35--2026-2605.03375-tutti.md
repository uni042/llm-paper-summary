# Tutti: Making SSD-Backed KV Cache Practical for Long-Context LLM Serving

## 概要

接頭辞 キャッシュは過去に計算した鍵値キャッシュ（KV キャッシュ）を再利用して長いプロンプトの再プリフィルを避けるが、長文脈・多セッションではHBMやホスト DRAMに履歴を保持し切れない。NVMe SSDは容量単価が低い一方、従来のSSD-backed キャッシュは断片化したGPU ブロックを大量の小I/OとしてCPUから発行するため、GPU Direct Storage（GDS）を使ってもCPUのsubmission/completion処理とI/O jitterがGPU 待ちを生む。

TuttiはHBMとSSDの間のdata pathだけでなくI/O 制御 pathもGPU中心へ移す。GPU-native KV object storeで推論engineのブロック粒度とストレージ objectを一致させ、GPU版io_uring（gio_uring）で非同期I/Oを発行し、層ごとの計算余裕時間を利用するslack-aware スケジューラでI/O カーネルと推論カーネルを重ねる。vLLMへ統合した実機評価では、GDS版LMCacheに対して厳しいSLO下の最初のトークンまでの時間（Time to First Token; TTFT）を78.3%削減し、許容リクエスト rateを2倍、推論提供 コストを27%削減した。

## 問題設定

NVMeを単にKVの下位階層として追加しても速くならない。vLLMのKVは小さいpage/ブロックに分かれ、SSD側の大きな連続I/O粒度と一致しない。CPUがブロックごとのI/Oを発行すると、SSD自体に帯域余力があってもsubmission queueを十分に埋められず、GPUは必要KVの到着を待つ。

またI/O カーネルを無条件にGPUで走らせるだけでは、推論カーネルとSM・メモリ資源を奪い合う。Tuttiは「CPUを外す」だけでなく、KV object粒度とI/Oを出す時刻の両方を推論engineに合わせる。

## 手法

### GPU-centric KV object store

TuttiのGPU fileは推論engineのKV ブロックをobjectとして表し、各fileを `2 × layer × block` の形へ対応させる。各層のkey/valueがobjectになり、Tensor-Stripe layoutで複数NVMeへ配置する。複数SSDではround-robinにobjectを散らし、aggregate 帯域を使う。

起動時にNVMe file プールを事前確保し、ランタイムでは空GPU fileを選んでhash mappingを付けるだけにする。file作成・解放などのmetadata処理をリクエスト critical pathから外す。GPU virtual addressからPCI-visible physical addressへのmappingも起動時に準備して再利用する。

### GPU io_uring

gio_uringはCPU側io_uringに相当するsubmission/completion処理をGPUから行えるようにし、CPUが個々のKV I/Oを仲介しない。CPUは層ごとにI/O カーネルを非同期読み込みする役割へ縮小される。I/Oとcompute用GPU資源を分割し、両カーネルを並行実行する。

この設計は「GDSならCPUを完全に外せる」という前提を否定する。GDSでもI/O initiationがCPU中心なら小I/Oの制御費が残るため、Tuttiはストレージ 制御 planeまでGPU側へ移す。

### slack-aware I/O scheduling

offline プロファイリングで各層のI/O slack、すなわち必要KVが到着するまでに計算と重ねられる時間を推定する。スケジューラはこの窓へSSD transferを置き、早すぎるI/OによるGPU資源競合と、遅すぎるI/Oによる待ちの双方を避ける。

object storeが「何をまとめて運ぶか」、gio_uringが「誰がI/Oを発行するか」、slack スケジューラが「いつ運ぶか」を担当し、三つを組み合わせてSSD 遅延を隠す。

## 評価条件

|項目|条件|
|---|---|
|CPU|64-core Intel Xeon 6530|
|ホスト メモリ|512 GB、tiered構成では256 GB pinned DRAM|
|GPU|2× NVIDIA H100 80 GB|
|SSD|4× Solidigm D7-PS1010 7.68 TB、GPUごと14 TB volume|
|ランタイム|vLLM 0.12.0 / 0.17.0 + LMCache比較|
|モデル|主にLlama3-8B 1 GPU、GLM-4-9B-Chat-1Mは2 GPU テンソル 並列|
|ワークロード|LEval 3K〜200K トークン、LooGLEは100K超を多く含む|
|arrival|複数sub-datasetをround-robin、Poisson到着|
|比較|HBM、LMCache-DRAM-LW、LMCache-SSD、LMCache-GDS|
|指標|TTFT、inter-トークン 遅延、キャッシュ 命中、ストレージ 帯域、GPU バブル、コスト|

## 主要結果

|条件|指標|比較|Tutti|読み取れること|
|---|---|---|---|---|
|新vLLM、高負荷|TTFT|LMCache-GDS|78.3%削減|CPU/GDS I/O pathがcompute高速化後ほど顕在化|
|新vLLM、高負荷|TTFT|LMCache-DRAM-LW|69.1%削減|大容量SSDの高命中率とGPU I/O重畳でDRAM 階層も上回る|
|SLO制約|achievable リクエスト rate|GDS-backed 比較対象|2×|SSD I/O 待ち削減が許容負荷を拡大|
|コスト評価|推論提供 コスト|比較構成|27%削減|DRAM容量増設ではなくSSDを使う容量単価の利得|
|LEval|キャッシュ 命中|HBM/DRAM/SSD|8% / 53% / 84%|大容量SSDが再利用可能接頭辞を保持|
|LooGLE|キャッシュ 命中|HBM/DRAM/SSD|4% / 24% / 86%|100K超の文脈でDRAM不足がより強く表れる|

論文はSSD-backed TuttiがDRAM-backed LMCacheに近い推論性能を達成しながら、SSD容量を使えることを強調する。性能差はSSDそのものがDRAMより速いからではなく、キャッシュ 命中率の容量効果とI/O critical pathの削減を合わせた結果である。

## 既存研究との差

LMCache-SSDは標準非同期I/O、LMCache-GDSはCPU bounce バッファを避けるがI/O制御はCPUに残る。TuttiはGPU object abstractionとgio_uringによりsubmission/completionまでGPU中心にし、さらに推論層のslackへI/Oを配置する。

HBM/DRAMだけを使う接頭辞 キャッシュと比べると、Tuttiは高速階層の容量不足による再計算をSSD容量で避ける。KV量子化や追い出しのようにキャッシュ内容を近似せず、保存階層とI/O経路を変える方式である。

## 限界

現在のremote multi-ノード pathは最適化されておらず、CPU interfaceでGPU fileをホスト メモリへ読み、RDMAで別ノードへ送る。この部分はTuttiのGPU-centric 局所 SSD pathと異なりCPU オーバーヘッドが残る。著者はGPU-initiated RDMAを将来課題としている。

主要評価はLlama3-8Bの単一GPUで、1M 文脈モデルは2 GPU テンソル 並列の追加評価である。NVMeの種類・本数、PCIe topology、キャッシュ 再利用率が変われば利得も変わる。SSD miss時の再計算や、共有接頭辞が少ないワークロードでは大容量階層の価値が下がる。
