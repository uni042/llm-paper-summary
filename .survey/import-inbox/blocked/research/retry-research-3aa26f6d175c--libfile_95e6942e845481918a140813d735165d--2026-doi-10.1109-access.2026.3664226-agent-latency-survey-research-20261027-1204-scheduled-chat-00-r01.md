# Minimizing Response Latency in LLM-Based Agent Systems: A Comprehensive Survey

## 書誌・対象範囲

Park、Lee、ParkによるIEEE Access掲載の2026年の総説である。研究対象は、言語モデル単体の生成時間ではなく、LLMを意思決定器として使うエージェントがユーザーの要求を受け取ってから最終的な応答または行動を返すまでの**端から端までの応答時間**である。計画の再生成、外部API、検索メモリ、ツールの実行待ち、複数エージェントの同期が加わるため、モデルのトークン生成を2倍速くしても、エージェント全体の所要時間が半減するとは限らない。

本論文の中心的貢献は、新しい単一カーネルやスケジューラを提案することではない。既存の高速化研究を、LLM内部、エージェント制御、サービング・ハードウェア、複数エージェント協調という四層へ配置し、どの遅延成分を短縮するか、どの代償を伴うかを横断的に比較する点にある。さらに、基礎推論技術の補助実験を著者自身が行っているため、引用した既存研究の結果と自前の測定値を区別して読む必要がある。

## 概要

エージェントの応答遅延は、LLMのプリフィルと逐次デコードだけで決まらない。計画を何度も作り直すとLLM呼出し回数が増え、ツールが逐次実行されればネットワーク待ちが足し合わされる。サービング基盤でキューに入れば最初のトークンが出る前に待機し、複数エージェントが互いの完了を待つと計算資源が空いていても総時間が伸びる。本論文は、このように原因が異なる遅延を一つの指標へ混ぜずに分解している。

補助実験では、NVIDIA L4上のQwen2.5-7B-Instructで、FP16とINT4の比較において生成所要時間が15.48秒から6.29秒へ短縮し、報告上の生成速度が16.54から40.70 token/sへ上がった。KVキャッシュの有無を比較すると、総生成時間は約24.3%減った一方、初回トークンまでの時間は79.04 msから192.44 msへ悪化した。バッチ数1と8の比較では、全体スループットが16.52から122.39 token/sへ上昇した。これらは異なる実験条件・測定軸であり、単一のエージェントに三つを掛け合わせた改善倍率ではない。

## 問題設定：遅延を何に分解するか

論文はLLMエージェントの時間を、モデル実行、フレームワーク内の計画・判断、外部ツール・通信、基盤の待機や資源競合に分解する。これらの区分は分析のためのものであり、複数段階の逐次実行、並列化されたツール呼出し、繰り返しループがあると単純な固定和だけでは正しい総時間を表せない。したがって実測すべきなのは、各段階の累積時間と、依存関係を考慮したクリティカルパスである。

モデル側の代表指標はTTFT（要求受信から最初の生成トークンまで）とTPOT（後続トークン一個あたりの時間）である。プリフィルは入力長とモデル計算量に強く依存し、デコードは重み・KVキャッシュの読み出し帯域に制約されやすい。ただし、TTFTとTPOTはエージェント全体の応答完了時間とは異なる。エージェントが10回モデルを呼び、各呼出しの間にツールを実行するなら、各回のTTFT・TPOTに加えてツール待ちと制御処理を考える必要がある。

論文が例に用いる診断エージェントでは、ガイドライン検索、予約照会、薬剤相互作用確認という複数の外部処理がある。互いに独立なら、逐次実行では各ツール時間を加算するのに対し、並列実行では最も遅いツールの完了が待ち時間を支配する。ただし起動・集約・エラー処理の費用が追加され、ツール間の依存がある場合は無条件に並列化できない。この例は構成の説明であり、論文の全ユースケースに共通する実測速度倍率ではない。

## 手法の整理：基盤LLM推論

### 量子化と計算資源

量子化は重みや活性値、KVキャッシュを低ビット表現へ写像する。重みを小さくするとGPUメモリに収まるモデルの規模が増え、メモリ帯域が律速となるデコードでは読み出すバイト数が減る。ただし、低ビット整数を演算時に展開するカーネルが遅ければ、メモリ削減がそのまま生成速度へ結びつかない。GPTQのような事後量子化と、学習中に誤差を考慮する量子化認識学習は、精度維持の方法と導入費用が異なる。

論文はOPT-175Bの既報を引用し、GPTQによる3ビット化で一トークンあたり230 msから71 msへ短縮した例を挙げる。しかし、比較されるFP16は5台のA100、量子化側は1台のA100という条件差があり、同一GPU数での純粋なカーネル速度比と解釈してはならない。また、低ビット化は複雑な推論・正確性を要するエージェントで誤答率を増やし得るため、速度だけで採否を決めない。

### 剪定、早期終了、注意機構

剪定は重要度の低い重み、層、ヘッド、トークンを削り、モデルを実行する演算量やメモリ量を減らす。ただし不規則な疎性はハードウェアの密行列積カーネルに適合せず、演算回数が減っても実測が速くならないことがある。早期終了や層スキップは、入力に応じて不要な層の計算を省くが、難しい入力ほど通常経路へ戻る必要があり、終了判定器の費用も加わる。

注意最適化では、FlashAttentionが中間注意行列を外部メモリへ書き戻さずタイル単位で正規化を更新し、長文脈の転送を減らす。KVキャッシュの圧縮・削除は別の操作であり、前者は注意演算中の入出力、後者は過去トークンの状態を保持する容量と読み出し量を変える。重要トークンを誤って捨てると長距離参照に失敗するため、単なるキャッシュ使用量削減と回答品質の維持を同時に評価する必要がある。

### 投機的復号とKVキャッシュ

投機的復号は小型ドラフトが先に複数トークンを予測し、大型ターゲットが一括検証することで逐次ターゲット呼出しを減らす。ドラフトが速くてもターゲットとの分布がずれて受理率が低ければ、ドラフト生成と検証の追加費用で利得が消える。量子化でドラフトとターゲットの出力分布が変わる場合、単独では有効だった二つの最適化を併用すると速度が悪化し得るという指摘がある。

KV管理は、重要度に応じたエントリ削除、低ビット圧縮、接頭辞共有、ページ単位の非連続配置などに分けられる。PagedAttentionはメモリの断片化を抑え、同じメモリ容量でより多くの要求を保持しやすくする一方、過去の情報を選別して捨てるアルゴリズムとは異なる。論文が引用するvLLMの2～4倍のスループットは別研究の8台A100を用いた条件付き結果であり、本総説のL4実験から直接得た値ではない。

## 手法の整理：エージェント制御とツール

計画処理では、複雑な目標を段階的な小タスクへ分割する階層計画や、軽量な「速い思考」と大型モデルの「遅い思考」を入力の難しさで切り替える構成が紹介される。全要求に最大モデルで長い計画を作らせる代わりに、簡単な操作は低コスト経路へ流す。入力分類の誤りで重要な判断を軽量経路へ送ると再試行・品質問題が生じるため、経路選択器の誤判定率と実行時間を含めて評価する必要がある。

ツール呼出しでは、独立な外部APIを並列起動し、遅い一件の完了を待つ構造へ変える。不要なツールを呼ばない選択器、構造化した引数と結果、複数段階の操作をまとめる実行計画も対象になる。構造化メッセージはLLMによる曖昧なテキスト解釈や確認の往復を減らすが、スキーマ維持とエラー時の回復を必要とする。総時間を減らすには、APIそのものの遅延と、失敗した場合の再実行・再計画まで測ることが重要である。

コンテキストとメモリの最適化では、検索した文書や履歴を毎回全文で再投入せず、重要な部分だけ選択する。これにより入力トークン数とプリフィル時間を抑えられるが、必要な情報を落とすとモデルの誤答が増えて再検索が必要になり、端から端までの時間はむしろ増える。長文脈エージェントの評価では、単一ターンのTTFTとタスク成功率を別々に報告すべきである。

## 手法の整理：サービング基盤と複数エージェント

サービング層では、継続的バッチ処理が要求ごとに異なる生成長を吸収し、GPUの遊休時間を減らす。複数要求をまとめることで全体のtoken/sは上がり得るが、キュー時間と個々の要求のテール遅延が改善するとは限らない。プリフィルとデコードを異なるGPUへ分離する構成、負荷に応じた配置、KVキャッシュのページ管理などは、計算・メモリ・通信のどこが律速かによって有効性が変わる。

複数エージェントでは、自由形式の対話を繰り返して役割や仕様を交渉すると、LLM呼出しと同期が増える。MetaGPTのような役割・標準作業手順・構造化成果物に基づくパイプラインは、下流担当が何を入力として受け取るかを先に決めることで交渉を減らす。一方、未知の状況へ即興で方針を変える能力は、ChatDevのような対話型構成が優位になり得る。同期を減らす非同期実行も、古い状態を参照した再作業を増やすなら全体最適にはならない。

## 評価条件と結果の区別

著者らによる補助実験の共通条件は以下の通り。これは文献から引用したOPT-175BやMetaGPTの数字とは別の測定である。

| 項目 | 論文記載の条件 |
|---|---|
| GPU | NVIDIA L4、24GB GDDR6、Ada Lovelace |
| CPU・ホスト | Intel Xeon 2.20GHz、8 vCPU、32GB RAM |
| ソフトウェア | PyTorch 2.9.1、Transformers 4.47.0、比較対象にvLLM |
| モデル | Qwen2.5-7B-Instruct |
| 生成設定 | 1要求につき50トークン、貪欲復号 |
| バッチ実験 | 32テストプロンプト、バッチサイズ1・2・4・8 |
| 評価軸 | 生成所要時間、token/s、TTFT、TPOT、バッチ効率、GPUメモリ |

### 著者による補助実験

| 比較 | 主な実測 | 解釈 |
|---|---|---|
| FP16 → INT4 | 総時間15.48→6.29秒、16.54→40.70 token/s | L4上の特定モデル・実装条件で量子化により約2.46倍の時間短縮、約2.39倍のtoken/s |
| KVキャッシュなし → あり | 総生成時間約24.3%減、TPOT 80.57→58.25 ms | デコード反復の再計算を避ける効果 |
| KVキャッシュなし → あり | TTFT 79.04→192.44 ms | キャッシュ確保などの初期費用により、最初のトークンは遅くなる場合がある |
| バッチ1 → 8 | 16.52→122.39 token/s、約7.4倍 | 32プロンプトを処理する設定での全体スループット改善 |
| バッチ1 → 8 | 論文報告の平均要求時間3026.54→408.53 ms | 測定の要求単位とバッチ構成を固定した比較。一般的なオンラインサービスのp99短縮を意味しない |
| バッチ1 → 8 | GPUメモリ14.20→14.24 GB | この小規模な条件でメモリ増加は小さい。最大同時要求や長文脈での上限は別問題 |

量子化実験の「2.46倍」は15.48/6.29に対応するが、報告されたtoken/sの比は40.70/16.54で約2.46倍となる。原著の本文には「2.39倍」という表現もあり、単純な商と一致しない。速度比は元の絶対値を優先して読み、原著の丸め・集計の定義が完全に同じとは断定しない。KVキャッシュ比較ではTTFT悪化とTPOT改善が同時に成立しており、生成トークン数が少ない場合と多い場合で採用判断が変わる。

### 引用文献由来の比較値

| 研究・条件 | 数値 | 注意点 |
|---|---|---|
| GPTQ、OPT-175B | 3bitで230→71 ms/token、WikiText2のPPLはFP16 8.34、4bit 8.37、3bit 8.68 | 別論文の既報値。モデル、GPU台数、品質指標がL4実験と異なる |
| vLLM、OPT系列 | 既存方式比2～4倍のスループット | 8台A100などの条件付きであり、Qwenの著者実験とは別 |
| MetaGPTとChatDev、SoftwareDevの7タスク平均 | 541秒と762秒、約29%の完了時間短縮 | 先行研究の比較結果。自由形式の会話と構造化手順の違いを含む |
| 同上、出力の実行可能性・手修正 | 3.75対2.25（4段階評価）、0.83対2.5回 | 生成後の手修正費用も含む「隠れた遅延」の説明材料 |

これらの比較を同一グラフの同一軸で合算してはならない。GPU・モデル・バッチ・入力長・タスクの成功基準が異なる。とくにMetaGPTとChatDevの結果はソフトウェア開発という構造化しやすい領域に依存し、一般の探索型エージェントで29%の改善を保証するものではない。

## 負の結果と適用限界

第一に、低ビット量子化や剪定は計算資源を削減するが、エージェントの最終的な正答率や信頼性を落とす可能性がある。単体推論の速度だけを測っても、誤答後のツール再呼出し、追加検証、人的修正まで含む総所要時間を評価できない。GPTQの3bitと4bitでPPLが異なるように、メモリ削減と品質の間に明示的な交換条件がある。

第二に、KVキャッシュの補助実験ではTPOTが改善してもTTFTは悪化した。これは短い出力を要求するエージェントでは、キャッシュ準備の固定費用が相対的に大きいことを示す。長い生成を繰り返す場面での有利さと、短い呼出しの初動遅延を同一視できない。

第三に、バッチ処理の報告は特定の固定プロンプト集合で得た結果であり、実サービスの到着率変動、長短混在、SLO制約、p95/p99遅延、プリフィルとデコードの資源競合まで網羅した評価ではない。高いtoken/sが利用者ごとの応答改善を意味するかは、待ち行列と負荷分布を含めて別途確認する必要がある。

第四に、総説の四層は有用な整理軸だが、論文ごとの条件が異なるため、各高速化技術の効果を直接比較する統一ベンチマークではない。例えばモデル量子化、ツール並列化、複数エージェントの通信最適化は互いに異なる操作を減らす。二つ以上を組み合わせると、投機的復号の受理率変化やKV削除による精度劣化のような相互作用も生じる。

第五に、複数エージェントの評価はソフトウェア開発などの代表事例に偏る。構造化したパイプラインは固定的な役割と依存関係が明確な作業に適するが、探索的な問題、予期しないツール結果、頻繁な方針転換には柔軟性の損失が生じる。論文自身も、細粒度の通信時間・同期待ち・再作業を横断比較できる標準的な評価体系が十分でない点を課題としている。

## 既存研究との差と実装への示唆

単一の高速化論文が「どのカーネルを速くするか」を扱うのに対し、この総説は「どの層の時間がユーザーの総遅延を支配するか」を先に決める立場を取る。推論が支配的なら量子化やKV管理を、ツール待ちが支配的なら独立処理の並列化を、キューが支配的ならバッチや要求配置を、同期が支配的なら役割分担と非同期通信を検討する。これらを区別しない最適化では、局所速度が上がっても利用者の体感は変わらない。

実装者が利用する際は、各段階の開始・終了時刻を計測し、TTFT、TPOT、外部API待ち、エージェントの計画回数、ツール再試行回数、GPUキュー時間、総タスク完了時間を別々に記録するのが適切である。そのうえで、タスク成功率を固定したときの総時間とコストを比較する。これは論文の分類枠から導かれる運用上の示唆であり、著者が全組合せを実験で検証したという意味ではない。
