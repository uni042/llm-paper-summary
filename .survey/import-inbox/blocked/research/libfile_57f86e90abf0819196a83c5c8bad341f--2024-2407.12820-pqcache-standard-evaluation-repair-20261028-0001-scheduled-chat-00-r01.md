# PQCache：積量子化検索で必要な過去KVだけをCPUから取り出す

## 概要

長文脈推論では過去トークンのKVキャッシュが大きくなり、GPUメモリに収まらないとCPUへ退避する必要がある。全KVを毎回GPUへ戻せば通信が膨らみ、古いKVを静的に削除すれば後で必要になった情報を参照できない。PQCacheはこの問題を**現在の問い合わせに対する過去キーの近似検索**として捉え、検索用の小さな積量化コードだけを使って重要なトークンを選ぶ。

選ばれたトークンの元のキー・バリューをCPUからGPUへ取得し、初期・直近KVとともに注意計算する。検索索引の近似と、実際の注意計算に使うKVの量子化は別である。Llama-3.1-8B、128K文脈のInfiniteBenchでは、過去トークンの1/10を選ぶ条件で平均46.80、PyramidKV(C)の44.74に対し約4.60%の相対スコア改善を示すが、Fullの47.63より低い。

## 問題設定

KVを圧縮する方法には、古いトークンを削除する方式、直近や先頭のトークンを優先して残す方式、クエリに応じて重要トークンを選ぶ方式がある。静的削除では後から重要になるトークンを失う。一方、各デコードステップで全トークンの高精度キーとの内積を計算して重要度を決めるなら、候補選択そのものが大きな計算・通信負担になる。

PQCacheは、重要候補の**順位付けだけなら元キーの高精度表現を全部使わなくてよい**と考える。CPUに元KVを残しつつ、小さな検索索引で関連トークンを絞る。元KVを残すため、以前は不要だったトークンが新しい問い合わせで重要になれば再取得できる。これはGPU上の常駐KVと計算対象を減らす設計であり、CPUを含むシステム全体のKV容量を1/10にする方式ではない。

## 手法

### 積量子化によるキーの近似検索

各層・KVヘッドのキーをm個の部分ベクトルへ分割し、それぞれをK-Meansで`2^b`個のセントロイドにクラスタリングする。各トークンには部分空間ごとのセントロイドIDをbビットのコードとして記録する。現在のクエリを同じ部分空間に分割し、クエリと各セントロイドの内積を先に計算する。

過去トークンの近似内積は、そのトークンのコードで対応する内積値を引き、m個の部分空間分を合計して求める。高次元の元キー全体と毎回内積を取るより小さな検索費で上位k候補を選べる。選択後にはCPUに保存した元のキー・バリューをGPUへ戻すため、低bit化したキーを直接最終Attentionへ入力する方式ではない。ただしPQコードは近似であり、上位候補の順位を誤れば重要トークンを選び損ねる。

### プリフィルの非同期CPUオフロードとK-Means

GPUで各層のQ/K/Vを計算した後、キーとバリューを非同期にCPUへ送り、その間GPUは同じ層のAttentionやFFNを進める。CPUは受け取ったキーをKVヘッド・部分空間ごとに並列クラスタリングし、検索用コードとセントロイドを作る。十分に長い文脈ではGPU側のAttention計算が文脈長の二乗に近く増えるため、線形に近いCPU転送・クラスタリングの費用を重ねやすい。

短文脈では逆にCPU側のK-Meansが遅延の支配要因になり得る。著者はGPU計算時間を文脈長の二次式、CPUクラスタリングを文脈長と反復数の関数で近似し、GPU計算中に隠せる範囲へK-Means反復数を調整する。反復を減らし過ぎると検索品質が落ちるため、索引精度とプリフィル待ち時間の交換条件がある。

### 初期・中間・直近の三領域KV管理

初期トークンと直近トークンはGPU上に置き、各ステップの注意計算へ直接参加させる。中間トークンの元KVはCPUに保持し、現在のクエリからPQ索引で選んだ候補だけをGPUへ取得する。直近窓から押し出されたトークンは、索引コードを作ってCPUへ退避する。これにより、過去の中間KVを固定的に削除せず、クエリが変わるたびに参照対象を選び直せる。

セントロイドは文脈長に依存しない小さなテーブルであり、デコード時にGPUへ常駐させられる。コードは文脈長に比例するが元のFP16キーより小さい。各層の計算中に次層のコードをCPUからGPUへ先読みし、クエリ生成後に近似スコアを計算する。検索結果が決まってから必要な元KVをCPUから取得する部分は完全には重畳できず、残る通信遅延になる。

### ブロックキャッシュによる転送削減

頻繁に選ばれる中間KVはGPU上のブロックキャッシュに保持する。トークン単位で細かく管理すると更新費が大きいため、128トークンのブロックを単位にする。LRUとLFUを比較し、4Kトークンのキャッシュ・32ブロックでは約0.6のヒット率を報告する。キャッシュが当たればCPUから同じKVを繰り返し転送せずに済むが、ブロック内の不要トークンまで保持する費用もある。

## 評価

### 評価条件

| 項目 | 原著・既存mainの条件 |
|---|---|
| モデル | 主にLlama-3.1-8B、128K。Mistral-7BとLlama-3.1-70Bも追加評価 |
| 課題 | LongBench、InfiniteBench、針探索、GSM8K |
| 選択率 | 過去トークンの1/5、1/10 |
| LongBenchの索引 | m=2、b=6、追加通信量は元キーの1/128相当 |
| InfiniteBenchの索引 | m=4、b=8、追加通信量は元キーの1/64相当 |
| 比較対象 | Full、Oracle、H2O、SnapKV、PyramidKV、InfLLM、SPARQ |
| ハードウェア | RTX 4090 24GB、Xeon Gold 6330×2、CPUメモリ500GB、PCIe 1.0 x16想定 |
| 指標 | ベンチマーク平均スコア、TTFT/TT2T/TPOT、キャッシュヒット率 |

LongBenchとInfiniteBenchでは追加通信量の予算が異なるため、両者の平均スコアを同一通信費の実験として比較してはいけない。Oracleは理想的な選択の参照条件であり、実運用の検索方式と同じ費用を負うわけではない。タスクごとのスコアはF1、ROUGE、正答率等の混合であり、全てを単一の正答率として解釈しない。

### LongBenchの個別品質と平均

| 課題 | Full | PQCache 1/5 | PQCache 1/10 |
|---|---:|---:|---:|
| Qasper | 44.79 | 44.93 | 44.36 |
| MultiFieldQA | 54.63 | 55.11 | 54.97 |
| HotpotQA | 55.81 | 55.60 | 56.35 |
| QMSum | 25.11 | 25.67 | 25.24 |
| TREC | 72.50 | 72.50 | 72.00 |
| LongBench全体平均 | 47.37 | 47.29 | 47.19 |

1/10の選択率でも全体平均47.19はFullの47.37に近いが、同等性の厳密な証明ではない。HotpotQAのように選択的注意がFullを上回る条件がある一方、QasperやTRECでは下回る。1/10での比較方式最高平均45.42に対する相対改善は約3.90%で、速度改善率ではない。

### InfiniteBenchの1/10選択率

| 方式 | 平均スコア |
|---|---:|
| Full | 47.63 |
| Oracle | 47.60 |
| SnapKV(C) | 44.71 |
| PyramidKV(C) | 44.74 |
| PQCache | 46.80 |

PyramidKV(C)44.74からPQCache46.80への改善は2.06スコア点、相対約4.60%である。論文の「+4.60%」はこの相対スコア差を指し、推論速度やメモリ削減率ではない。1/5条件での比較方式に対する平均改善は+1.50%と報告され、選択率によって比較条件が変わる。

### 質問位置・長文脈・70Bの頑健性

質問を入力の先頭へ移すLongBench評価では、6課題平均がSnapKV(C)30.29、PyramidKV(C)29.97、PQCache32.44となる。問い合わせ位置を変えても検索し直せることが有利だが、PQCache自体も通常配置よりスコアが低下するため位置に完全不変ではない。針探索は最大約131Kトークンで評価され、全長・全位置で100%成功したと一般化してはいけない。

Llama-3.1-70Bの128K LongBenchではFull平均52.89に対し、PQCacheのCPU資源を半分にした条件52.88、同程度のCPU資源では52.86と報告する。これは品質が近い結果であり、70Bを単一の24GB GPUに載せて同じ速度で推論できたという結果ではない。

### キャッシュ・重畳の速度と負の結果

GPUキャッシュなしに対し、4KトークンのブロックキャッシュでTPOTを26.3%、8Kで32.8%短縮した。これは**出力1トークン当たり時間**であり、TTFTや全要求のエンドツーエンド遅延ではない。索引構築が第1トークン後に待ちを生む場合があるため、論文はTTFTだけでなくTT2Tも観測する。GPU計算中にK-Meansを隠せない短文脈、低いキャッシュヒット率、CPU-GPU帯域不足では効果が小さくなる。

MInferenceと併用したInfiniteBench平均は40.18で、PQCache単独47.31、MInference単独41.04より低い。二つの疎化方式を組み合わせても品質利得は単純に加算されない。検索用コードをより大きくして追加通信量を増やす感度評価でも、SPARQが改善する場合があり、PQCacheが全予算で最良とは限らない。

## 既存研究との差

SnapKVやPyramidKVは観測窓や過去の重要度からKVを残すが、静的な削除では後から重要になったトークンを再取得できない場合がある。PQCacheはCPU上に元KVを保持し、現在のクエリで候補を選び直す。KIVIのような低bit KV値量子化と違い、主な量子化対象は**検索用の索引**であり、選択後のAttentionは元のKVを使う。SPARQの部分次元による候補選択とは異なり、学習済みセントロイドと短いコードを使うため、索引の先読みやブロックキャッシュと組み合わせやすい。

## 限界と適用条件

検索用PQコードは近似であり、重要トークンを取り逃がす可能性がある。K-Meansの反復数、部分空間数、ビット幅、選択率は精度・検索時間・転送量の交換条件を持つ。CPUに元KVを保持するため、システム全体のKVメモリが選択率と同じ比率まで減るわけではない。検索後のCPU→GPU転送は完全には隠せず、CPUメモリ容量とPCIe帯域が必要になる。

実験の主構成はRTX 4090 24GB、Xeon Gold 6330×2、500GBのCPUメモリであり、RAM32GBや12GB VRAMの環境で同じ128K文脈を実行できるとは限らない。著者実装READMEもGPU計算能力8.0以上、VRAM24GB以上を前提としている。長い生成で索引のセントロイドが陳腐化する可能性があり、一般的な長時間会話での再構築方針は十分に検証されていない。
