# LogQuant：遠方の重要KVを底2間引きで保護する2bit量子化

## 概要

KVキャッシュの圧縮では、全トークンを同じ精度で保存する必要はない。しかし、直近トークンだけを高精度に保つ方式は、遠くにある重要な事実を低精度化してしまう。過去の注意重みから重要トークンを予測する方式も、生成が進むと注意先が変わるため誤予測し得る。LogQuantは、注意の高い位置が最近ほど密、古い文脈ほど疎に現れるという観測を用い、**高精度で残す位置を時系列に沿って底2の規則で間引く**。それ以外のKVは削除せず、2bitへ量子化する。

提案の核心は、(1)注意スパイクの位置分布を利用した高精度保持位置の選択、(2)定期的に古い高精度窓を半分へ間引くオンライン更新、(3)Key/Valueを対応させて並べ替えても注意の重み付き和が不変という性質を利用したキャッシュ配置、(4)Hugging Face `Cache`とQuantoを使った実装、の四点である。量子化ビット幅を2へ落とすこと自体より、**どの位置のKVをBF16のまま残すか**が既存のKiViとの差になる。

Llama-3.1-8B-InstructのGSM8Kでは、BF16 71.42、2bit KiVi 18.04、2bit LogQuant 40.41であり、KiVi比では大幅改善するもののBF16からの損失も大きい。H100の48GBメモリ制約下では、バッチ数を約60%増やし総スループットを約25%改善した。これはHugging Faceの生成パイプライン、入力平均512・最大出力2000、Llama-3.1-8Bという条件の結果であり、全モデル・全サービング基盤に適用できる倍率ではない。

## 問題設定と観察

自己回帰推論では各層の過去Key/Valueを保持する。KVのメモリ量はトークン長、層数、KVヘッド数、ヘッド次元、数値精度に比例し、長文脈・多数の同時要求ではモデル重み以外の大きなメモリ負担となる。2bitへ量子化すればBF16の16bitに比べて生データのビット幅を8分の1にできるが、スケールやゼロ点、元精度で残すトークン、実行時の一時バッファを含むため、**実際の総VRAMが必ず8分の1になるわけではない**。

従来のKiVi系は直近Rトークンを高精度に保ち、より古いKVを量子化する。これは最近の局所情報には有利だが、長い入力の冒頭や中ほどにある重要情報を特別扱いできない。H2Oのように過去の注意スコアから重要度を選ぶ方式は、注意先が生成ステップごとに変化すると誤った位置を選ぶ。論文図2はGSM8KとOpenBookQAで連続する生成ステップの高注意位置が変わることを示す。したがって過去スコアの順位を将来の正解と仮定しない方式が必要になる。

著者はLlama-3系のGSM8Kにおいて、注意スパイクの位置が最近に密集し、距離が大きいほどまばらになる傾向を観測した（図1）。この傾向は高精度保持位置を一定間隔で均一に選ぶより、最近は密・遠方は疎に選ぶ設計を支持する。ただしこれは**経験的な注意分布の観測**であり、すべてのモデル・質問で厳密な対数分布に従うという証明ではない。

### sink tokenを高精度に残すだけでは足りない

文脈の最初の数トークンは注意を多く集めることがある。そこで最初の2トークンをBF16に保つ実験を行ったが、表1ではLlama-3.1-8BのGSM8KがKiVi2bitの18.04から18.49へわずか+0.45、Qwen1.5-7Bでは39.80から39.42へ-0.38となった。両条件とも直近128トークンは高精度に保持している。したがって「注意スコアが高いsinkだけ保護すれば2bit量子化の品質が回復する」という単純な説明は成り立たない。

## 手法：底2の高精度窓と低精度KV

### 1. どの位置を高精度で残すか

窓長Wを定め、最近の連続領域には高精度トークンを多く残す。古い領域では1つおき、さらに古い領域ではより粗い間隔で位置を選ぶ。こうして最近から遠方へ移るにつれて、選択密度が概ね2分の1ずつ減る構造を作る。論文§2.2はこの方式をKiViの最近3W、StreamingLLMの最近3W＋冒頭sink、H2Oの過去注意重みに基づく上位3Wと比較する。図4の注意カバレッジでは、同じ高精度保持予算でLogQuantが遠方の高注意位置をより多く拾うことを示す。

ここでいう高精度選択は、**選ばなかったトークンを注意から消す**操作ではない。選ばれたトークンはBF16など元の精度で保持し、選ばれなかったトークンもINT2へ量子化して注意計算に参加させる。したがって「高精度トークンの選択」と「KV自体の削除」を混同しないことが重要である。

### 2. 生成中の更新アルゴリズム

Algorithm 1では、高精度KVの列Aと新トークンa*を入力とする。高精度保持列の長さが3W未満なら新トークンを末尾へ追加する。3Wへ達したときは、古い2Wの高精度トークンを`A[0:2W:2]`で1つおきに残してWへ減らし、直近のWをそのまま残す。続けて新トークンを追加する。高精度から外したKVは量子化側へ移される。

この操作を繰り返すと、古い領域ほど複数回の間引きを経験するため、高精度位置の密度が底2の階段状に下がる。高精度トークン数は概ね2W〜3Wの範囲で変動し、量子化イベント時には古い2WをWへ縮める。KiViの高精度窓が0〜Rの範囲で変動するという原著の比較に対し、LogQuantは比較的安定した高精度予算を保つ。ただし3Wを超えないというのは**高精度保持トークンの予算**であり、量子化済みの全KVを含む総トークン数ではない。

公平比較ではKiViの高精度予算Rに対しW=floor(R/3)を選ぶ。R=128ならW=42で、LogQuantの最大高精度保持は3W=126となり、KiViの128より少ない。R=192、256でも同様に高精度予算を超えないよう調整する。これにより「LogQuantのほうが単に高精度トークンを多く保持したから精度が良い」という解釈を避ける。

### 3. なぜ削除より量子化か

注意出力は`softmax(QKᵀ)V`であり、全ての過去位置へのスコアを正規化して重み付き和を作る。トークンを削除すると、その位置への寄与だけでなくsoftmaxの正規化母数も変わる。量子化なら値に誤差が入るものの、位置自体は残る。論文図5と表2では、Llama-3.1-8B/GSM8Kの注意分布に対するL1誤差が、LogQuant2bit 432.50、KiVi2bit 556.10、LogQuant位置選択によるeviction 1076.70、KiVi eviction 1612.56であった。これは**注意分布のL1誤差**であり、GSM8Kの正答率やモデル全体の精度そのものではない。

この結果は、同じ選択規則でも不要と判定したKVを完全削除するより、2bitで保持するほうが元の注意分布を保ちやすいことを支持する。反面、量子化した全トークンを読み戻すため、evictionと違って注意の対象トークン数自体は減らない。高速化には量子化メモリ削減と、復号・配置の実装効率が必要である。

### 4. KVの順序を変えても出力を保てる条件

decodeの単一クエリに対し、KとVの**同じトークン順列**Pで両方を並べ替えれば、注意重みの順序も同じだけ変わり、重み付き和は不変になる。原著式(3)はこの対応関係を利用する。高精度KVを連続領域に、量子化済みKVを別の連続領域にまとめ、元の絶対位置順を保たず格納することで、アクセスや変換を単純化できる。

ただしこれは**すでに位置情報を反映したKを対応するVと同時に並べ替える**場合の注意集約の性質である。位置埋め込みを適用する前のトークン順序を任意に変更しても同じモデルになる、という主張ではない。Kだけ並べ替えてVを並べ替えなければ、当然ながら重み付き和の対応が壊れる。causal maskや位置依存の追加バイアスがあるprefill全体にも無条件に拡張しない。

### 5. 実装と追加費用

著者はHugging Face `transformers`の`Cache`クラスを拡張し、量子化バックエンドとしてQuantoを利用する。Keyはchannel単位の量子化、量子化グループサイズ64、主要評価はINT2である。公開実装には`QuantoLogQuantizedCache`と設定クラスがあり、`nbits=2`、`window_length`、計算dtypeなどを指定できる。通常の`generate`へ`past_key_values`として渡せるため、モデル本体を再学習せず推論時に使える点はHHSTのような学習済み疎構造と異なる。

一方、一定間隔での高精度窓の間引き、低精度側への移動、スケール保持、復号時のdequantizationが追加費用となる。原著§3.2.4は、HFパイプラインが元のKVをすぐ解放しない場合があり、メモリ削減を制限すること、復号処理がスループットを削ることを明示する。量子化値のまま注意計算する融合カーネルは今後の課題であり、論文の報告倍率を「完全融合済みの最適実装」とみなしてはならない。

## 定量評価

### 1. 2bitでの数学・コードの品質保持（表4）

| モデル・タスク | BF16 | KiVi2bit | LogQuant2bit | 解釈 |
|---|---:|---:|---:|---|
| Llama-3.1-8B / GSM8K | 71.42 | 18.04 | **40.41** | KiViの2.24倍の正答率だがBF16から31.01ポイント低下 |
| Llama-3.1-8B / Code Completion | 59.78 | 43.06 | **52.09** | KiViより9.03ポイント高いがBF16より7.69ポイント低い |
| Llama-3.1-8B / Few-shot | 61.21 | 52.50 | **56.42** | 改善はあるが元精度未達 |
| Qwen2-7B / GSM8K | 52.99 | 3.71 | **34.34** | KiViの大幅劣化を緩和するがBF16には届かない |
| Phi-3-mini / GSM8K | 80.29 | 12.59 | **51.86** | 小型モデルでも相対改善、絶対損失は大きい |
| Qwen1.5-14B-AWQ / Code | 57.47 | 37.48 | **49.37** | 2bit同士では改善、BF16に未達 |

論文の「40〜200%改善」は、同じ2bit・同じキャッシュ予算の比較対象に対する**相対的な品質改善**を強調したものである。Llama-3.1-8B/GSM8Kの18.04→40.41は約124%の相対増だが、BF16の71.42には大きく届かない。したがって「2bitでもほぼ無損失」とは言えない。GSM8KやCodeのように精度劣化が顕著なタスクで、既存2bit方式より損失を減らすという結果である。

### 2. 2bitと4bitの違い（表3）

Llama-3.1-8BのLongBenchでは、Single-Document QAがBF16 47.71、KiVi2bit 38.89、LogQuant2bit 41.91、LogQuant4bit 47.73である。Synthetic TasksではBF16 67.78、KiVi2bit 45.02、LogQuant2bit 52.51、LogQuant4bit 67.68である。Code CompletionはBF16 59.78、KiVi2bit 43.06、LogQuant2bit 52.10、LogQuant4bit 59.57である。

4bitでは元精度に近い条件が多いが、2bitでは差が大きい。これはLogQuantがビット幅を極端に下げても情報損失を消す方式ではなく、同じビット幅で**どこを高精度に保護するか**を改善する方式であることを示す。4bitを使える容量があるなら、2bitの最大圧縮率と品質を比較して選ぶ必要がある。

### 3. 他モデル・他タスクへの一般化（表4・図7）

Qwen1.5-7B-AWQのGSM8KはBF16 56.18、KiVi2bit 39.27、LogQuant2bit 49.28である。Qwen1.5-14B-AWQのSynthetic Tasksは61.33→46.85（KiVi）→52.17（LogQuant）となる。Qwen2-7BのMulti-Document QAはBF16 33.35、KiVi 12.35、LogQuant 28.28である。モデルごとのGQA構成、KVヘッド数、課題の重要情報の位置分布により量子化損失の大きさは異なる。

著者はQwen2-7BやPhi-3-miniのような小型モデル、またKVヘッド数が少ない構成で低ビット化の損失が大きいと論じる。LogQuantはその損失を軽減するが、完全には回復しない。図7は複数圧縮率でのGSM8K比較を示し、同じ圧縮率での優劣を評価するための補助証拠である。数学・コード以外の要約では、そもそも量子化の影響が小さく、改善幅も限定的である。

### 4. 注意分布の誤差とeviction（表2）

| 方式 | 元の注意分布に対するL1誤差 |
|---|---:|
| LogQuant2bit | **432.50** |
| KiVi2bit | 556.10 |
| LogQuant選択規則によるeviction | 1076.70 |
| KiVi選択規則によるeviction | 1612.56 |

高精度位置の選択規則だけでなく、選択外のKVを**削除するか、低ビットで残すか**が重要であることを示す。ただしL1誤差は最終タスクの正答率ではなく、特定のモデル・データセットで測った注意分布の近似誤差である。削除方式は注意の計算量自体を減らせる利点があるため、品質・速度・メモリの三軸で比較する必要がある。

### 5. H100のメモリ・スループット（図8）

H100の48GBメモリ制約でLlama-3.1-8B、平均入力512、最大出力2000を生成する実験では、LogQuant2bitはBF16キャッシュに対し、同じメモリ上限で収容できるバッチ数を約60%増やし、総スループットを約25%高めた。**25%は単一要求のトークン遅延が25%改善したという意味ではない**。大きなバッチを収容できることによる総処理量改善であり、量子化・復号の追加処理が残る。

また本文は「H100 48G MIG」と「single NVIDIA H100 GPU」を併記する。これは48GB相当のMIGメモリ上限下での評価として扱い、フルH100 80GBを自由に使える条件と混同しない。図8はバッチとメモリ・処理量の関係を示すが、原著本文はすべてのバッチ点の厳密な数値表を与えていない。図から推測した個別TPSを確定値として記載しない。

## 既存研究との差

**KiVi**はKのchannel単位・Vのtoken単位などの低ビットKV量子化を利用し、直近の高精度窓を維持する。LogQuantの差分は量子化そのものではなく、古い重要位置を含む**高精度保持トークンの時系列配置**と、その更新を一定予算で行うことである。同じ2bit・同程度の高精度保持予算でGSM8KやCodeの損失を減らしたことが根拠となる。

**StreamingLLM**はattention sinkと最近の窓を保つことで長期生成のメモリを一定化するが、間の古い文脈を捨てる。LogQuantは遠方の一部位置をBF16で残し、それ以外も2bitで保持するため、保持する文脈情報とメモリ費用の性質が異なる。**H2O/Keyformer/SnapKV**のような注意履歴による重要位置選択と比べ、LogQuantは生成ごとに注意重みから重要度を再予測する必要がない。ただし、入力内容に依存しない規則なので、重要位置が対数的に分布しないタスクでは優位性が小さくなる可能性がある。

**KV eviction**は削除したトークンを以後の注意から除くため演算量を減らせるが、元の注意分布から大きく離れる場合がある。LogQuantは全トークンを低精度または高精度で残すため、品質の保持を重視する一方、低ビットキャッシュの読み出し・復号が必要になる。どちらが良いかは、必要な品質とハードウェアの律速がメモリ容量なのか注意計算なのかで変わる。

## 限界・負の結果・再現性

第一に、2bitの絶対精度低下は依然として大きい。Llama-3.1-8BのGSM8KはBF16 71.42に対し40.41であり、Qwen2-7BやPhi-3-miniでも元精度との差が残る。「KiViより良い」ことと「品質をほぼ損なわない」ことは異なる。数学、コード、合成課題のような精密情報が必要な用途では、4bitやより高精度の選択が適切な場合がある。

第二に、底2の位置選択は注意スパイクの経験的分布を利用するため、遠方の少数の重要情報が規則的な高精度位置から外れた場合、低精度化による誤差が残る。入力の意味内容や質問の変化を追跡して重要度を更新する機構ではない。対数的な重要位置の分布が崩れるドメインでは、著者の平均改善を保証できない。

第三に、HF `Cache`実装では量子化前のKVが直ちに解放されない場合があり、理論ビット幅どおりのピークVRAM削減が得られない。dequantizationも推論時間を消費する。論文は量子化値を直接使う融合注意カーネルを将来課題としており、既にその最適化を実現したと解釈してはいけない。

第四に、位置の並べ替え不変性は対応するKとVを同じ順序で並べ替える場合の注意集約に限る。RoPE等の位置情報を反映する前の入力系列を任意に変更できるわけではない。量子化・復号時のscale管理、異なるattention実装、GQA/MQAの共有KV、特殊な位置バイアスを持つモデルでは、追加の検証が必要である。

第五に、H100の速度結果はHugging Face生成パイプラインと特定のバッチ・出力長であり、vLLM、SGLang、TensorRT-LLM、複数GPU、12GB GPUで同じ改善を示すものではない。ワークショップ採録の公開研究であり、幅広い実運用トレースや長期会話の品質、独立再現までを保証するものではない。
