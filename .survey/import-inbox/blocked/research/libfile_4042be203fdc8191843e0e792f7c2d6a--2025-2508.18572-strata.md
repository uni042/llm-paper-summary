# Strata: Hierarchical Context Caching for Long Context Language Model Serving

## 概要

長文脈LLMでは、再利用可能な接頭辞や文書のキー・バリューキャッシュ（KV cache）を保存するとプリフィル再計算を避けられる。しかし長い文脈のKVはGPUの高帯域メモリ（HBM）へ収まりきらず、CPUメモリやSSDなどの下位階層へ退避する必要がある。Strataが対象とするのは、この階層キャッシュからGPUへKVを戻す処理自体が新たな律速になる状況である。Llama-8Bでは40 GBのHBMでも約0.3M token分のKVしか保持できず、長文脈サービスでは下位階層利用が常態化する。

既存システムではページ化注意（PagedAttention）に合わせてKVを1〜32 token程度の小ページへ分割する。この粒度はGPUメモリ利用率や接頭辞一致率には有利だが、数KB級の小さな `cudaMemcpyAsync` を大量発行するとPCIeを飽和できない。論文の測定では8192 tokenのKVをpage size 32でCPUからGPUへ戻す際、PCIe 5.0の理論帯域の約22%しか使えず、Grace-Hopperの高帯域接続では利用率が約5%まで下がる。さらに長いキャッシュを読む時間が新規tokenのプリフィル計算より長くなると、層単位でI/Oを計算へ重ねても待ち時間が残る。

Strataはこの二つを別機構で解く。データ面ではGPU支援I/Oを使い、GPUスレッド自身が登録済みCPUメモリとGPUメモリ間の小断片を並列搬送する。制御面ではキャッシュ認識スケジューラが、要求ごとの「読み込むKV量」と「新規プリフィル計算量」を同時に見てバッチを構成し、I/Oを計算で隠せない場合にはデコードなど別の有用処理を差し込む。SGLang上に実装され実運用にも配備され、長文脈ベンチマークでvLLM + LMCacheより初回トークン時間（Time-To-First-Token; TTFT）を最大5倍短縮し、NVIDIA TensorRT-LLMより最大3.75倍高速化する一方、短文脈性能は悪化させない。

## 問題設定

階層KVキャッシュには、容量と転送効率の相反がある。大きな連続ページにすれば1回のI/Oサイズが増えてPCIe帯域を使いやすいが、接頭辞一致がページ境界に制約されるためキャッシュ命中率が下がる。StrataのMistral-24B + ShareGPT測定ではpage sizeを1から1024 tokenへ増やすと、最大設定で平均TTFTが最大2倍、P90 TTFTが最大2.9倍に悪化した。したがって「ページを大きくして転送を効率化する」だけではキャッシュ再利用の利点を失う。

一方、小ページを維持すると転送命令が細粒度になり、CPU側の発行並列性やCUDA driver queueの制約から十分な同時I/Oを作れない。PCIe 5.0で理論帯域の75〜80%を使うには1〜2 MB級の転送が必要なのに対し、KVページは数KB級になり得る。このため従来のDMA中心経路では、論理的には大量データを読む処理でも物理的には多数の小転送へ分断される。

さらに、転送帯域だけ改善してもスケジューリング問題が残る。Qwen2.5-14BとLooGLEのプロファイルでは、従来型SGLangの階層キャッシュでプリフィル時間の最大74%がKV転送待ちとなり、処理量が最大4分の1へ低下する。Strataの高速I/Oを使っても条件によって最大24%の待ちが残るため、「I/Oを速くする」と「I/Oを隠せる仕事を同時に選ぶ」の両方が必要になる。

## 手法

### GPU支援I/O

通常の `cudaMemcpyAsync` をページごとにCPUから発行する代わりに、StrataはCUDAカーネルを起動し、数千GPUスレッドが小さなデータ片をsourceからregisterへ読み、destinationへ書き出す。source/destinationはGPU global memoryまたは登録済みpinned CPU memoryであり、128 byte程度の粒度でも並列アクセスできる。CPUの数十程度のI/O並列性に依存せず、GPUの大量threadをI/O発行主体として使うことで、小ページを維持したまま帯域利用率を上げる。

ただしI/O kernelがGPU全体を占有するとプリフィル・デコードkernelと競合する。そこでStrataは少数の大きなCUDA blockだけを起動し、hardware schedulerがI/O処理を少数のStreaming Multiprocessor（SM）へ閉じ込めるようにする。さらにcache bypass命令でcache pollutionを抑える。H200上のmicrobenchmarkでは、1024 threadのblockを2個だけ使う設定でCPU→GPU転送が約50 GB/sに達し、同時実行するprefillの性能低下を5%未満、decodeを10%未満に抑えた。実システムではcritical pathのloadに2 block、非criticalなbackupに1 blockを既定値とする。

### GPUと下位階層のレイアウト分離

GPU上ではattention kernelが扱いやすいlayer-first・小ページ配置を維持する一方、CPUメモリやストレージではI/O効率に適した配置を使う。GPU支援I/O kernelは搬送時に軽量なlayout変換を行えるため、GPU側のページ粒度を大きくしてキャッシュ命中率を犠牲にせず、下位階層では連続性を高められる。

SSDなどさらに遅い階層からのcache hitが分かると、Cache Controllerは要求が待ち行列にいる間にhost memoryへbest-effort prefetchする。要求がdispatchされた時点で未完了なら、その時点までにhost/GPUへ到達した部分を利用する。この設計は予測不能なstorage latencyをGPU実行のcritical pathへそのまま載せないためのものである。

### HiRadixTreeとCache Controller

StrataはSGLangのRadixTreeを拡張したHiRadixTreeを持ち、各KV pageがGPU、CPU、storageのどこに存在するかをmetadataとして管理する。要求が到着するとschedulerはこの情報からcache hit量、GPUへloadすべきtoken量、新規にprefillするtoken量を見積もる。

選ばれたbatchはGPU executorへ渡されると同時にCache Controllerへload requestが送られる。prefill中はlayerごとに必要なKVが到着していることを同期し、完了後は要求をcontinuous batchingのdecode batchへ合流させる。新しく生成したKVのbackupと下位階層へのevictionはCache Controllerが非同期に進める。

### キャッシュ認識スケジューリング

従来schedulerはGPU計算量とHBM容量を主資源としてbatchを作るが、StrataはCPU-GPU帯域とcache load時間も一級資源として扱う。長いcached contextを読む要求だけを同じbatchへ集めると全要求がI/O待ちになるため、十分な新規prefill計算を持つ要求を組み合わせ、load時間をcomputeで覆えるようにする。

それでもI/Oが長くstallを避けられない場合、同一GPU上でdecode batchなどの補完処理を走らせる。Strataはprefill/decodeを同一GPUへ置く構成を採用しているため、prefillがcache arrivalを待つ区間をdecodeに転用できる。単なる優先順位付けではなく、「cache loadとprefill computeを釣り合わせるbatch形成」と「残余stallへ別taskを差し込む」の二段でGPU idleを減らす。

### delay hitの抑制

同じcontextを参照する複数requestが、最初のcache miss解決前にbatchへ入ると、同じprefixを複数回prefillするdelay hitが発生する。非同期schedulerでは次batchを現在batchの終了前に作るため、このmiss windowがbatch実行時間まで伸びる。HiRadixTreeの状態と進行中load/prefillをschedulerが参照することで、同じcache objectに対する重複仕事を避ける。

## 構成要素から分かること

Strataの結果は「GPU copy kernelが速い」だけでは説明できない。GPU支援I/Oは小ページを保ったまま帯域利用率を上げるため、キャッシュ命中率と転送効率の従来の相反を緩める。しかし高速I/O後にも最大24%のstallが残る測定があり、schedulerがI/O量をbatch形成へ入れる必要性を示している。

逆にschedulerだけでも、物理I/OがPCIe帯域の22%程度しか使えない条件では隠せる時間に限界がある。データ面の帯域改善と制御面の仕事混合が相互補完することがStrataの中心である。

## 既存研究との差

LMCacheやCachedAttentionなど既存の階層KV cacheは、CPU memoryやstorageへKVを退避して容量を増やし、layer-wise transferとcompute overlapで復元時間を隠す。Strataは長文脈ではload時間がprefill computeを上回るため、この前提が崩れることを測定し、CPU-GPU帯域そのものをschedulerの資源モデルへ追加する。

PagedAttentionとの関係では、小pageを捨てて連続bufferへ戻すのではない。小pageがGPU memory utilizationとprefix matchingに必要であることを前提に、GPU threadによる細粒度I/Oと階層ごとのlayout分離で転送側を合わせる。このためattention kernel向けのGPU layoutとstorage向けlayoutを同一にする必要がない。

## 限界

主対象は長いcached contextを持ち、prefillが大きいworkloadである。短文脈、長いdecode主体、cache reuseがほぼないsingle-turn workloadは論文自身が中心対象ではない。短文脈性能を悪化させないことは評価されているが、最大5倍・3.75倍の利得がその領域でも得られるわけではない。

GPU支援I/Oは少数とはいえSM、register、実行cycleを消費する。H200 microbenchmarkではprefill <5%、decode <10%の干渉に抑えているが、別GPU、別kernel構成、GPUが完全飽和したworkloadでは最適block数を再調整する必要がある。ROCm互換の実装にも言及されるが、主要headline評価はNVIDIA系platform中心である。

storage prefetchはbest-effortであり、SSDやremote storageの大きく変動するlatencyを完全に隠せる保証はない。またproduction配備の記載はあるものの、公開論文のbenchmarkがすべてのproduction traffic分布を代表するわけではない。
