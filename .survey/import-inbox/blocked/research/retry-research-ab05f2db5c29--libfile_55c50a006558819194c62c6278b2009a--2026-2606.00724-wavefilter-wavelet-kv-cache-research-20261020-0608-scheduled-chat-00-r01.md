# WaveFilter：ウェーブレット誘導KV選別による拡散型LLMの長文脈推論

## 書誌情報

Jinnan Yang、Yan Wang、Zhen Bi、Kehao Wu、Xiaojie Li、Jungang Lou、Zechao Li、Jing Liuによる2026年のプレプリント（arXiv:2606.00724v1）。対象は、マスクされた複数位置を反復的に更新する**拡散型大規模言語モデル（diffusion LLM）**である。一般的な自己回帰型モデルにおける単純な過去KVの追記方式とは、再利用できる状態と更新対象が異なる。著者は長文脈での精度維持を主目的に、既存の高速なKV再利用方式へ追加できるWaveFilterを提案した。一次資料は15ページの論文PDFであり、手法節、評価表、構成要素の感度分析、付録の実行条件を照合した。

## 概要

離散拡散型LLMは、一度に複数のマスク位置を推定して段階的に文章を完成させる。全位置を毎段階計算すれば長い文脈ほど費用が大きくなるため、Fast-dLLMやElastic-Cacheのような鍵・値キャッシュ（key-value cache、以下KVキャッシュ）の再利用法が用いられる。しかし既存方式を長文脈へ延ばすと、必要な位置の情報を十分に保持できず、単純な速度向上と引き換えに回答品質が低下する。

WaveFilterは、キャッシュ内の鍵（key）系列を**離散ウェーブレット変換（discrete wavelet transform、DWT）**で低周波の短い系列へ変換する。圧縮した鍵と現在の問い合わせ（query）の関連度を計算し、重要そうな領域だけを元系列へ戻す。その領域でさらに細かい解像度のDWTと重要度選別を繰り返し、最終的に残った元の位置から鍵と値を取り出して疎な注意計算を実行する。モデルの追加学習を必要とせず、既存のキャッシュ方式に後付けできることが設計上の特徴である。

結果の読み方には注意が必要である。LLaDA-8B-InstructとFast-dLLMのLongBench Qasperでは、正答率が**22.03→28.73**と6.70ポイント改善した一方、処理量は**15.01→6.80トークン/秒**と約54.7%低下した。Elastic-Cacheを使う別課題では精度と速度がともに改善する例もある。論文は「WaveFilterを追加すれば一律に高速化する」とは実証しておらず、精度・生成ステップ数・選別費用の三者の関係を評価する研究と理解するのが適切である。

## 問題設定と対象範囲

### 反復生成におけるKV再利用

初回の反復では、入力系列全体の各位置から問い合わせ行列Q、鍵行列K、値行列Vを計算する。後続反復では新たに生成・更新すべき位置の問い合わせを計算し、以前に保存した鍵・値を参照することで、毎回すべての位置の注意演算を繰り返す費用を抑える。論文の式(1)〜(4)は、初回に全位置のKVをキャッシュし、後続反復では更新位置のKVを反映する計算を示す。

ただし、拡散モデルでは自己回帰生成のように「確定済みの過去トークンは不変」という前提をそのまま適用できない。反復的な予測の変化により、過去の隠れ状態や重要な参照位置の扱いが性能へ影響する。既存の高速化方式は短い入力では有効でも、長い入力で必要な鍵・値を欠落させると、正しいトークンの確定まで追加の反復が必要になったり、最終回答が誤ったりする。

### 著者が狙うボトルネック

長い入力の全KVに問い合わせを当てて重要位置を探すと、選別自体が重くなる。反対に固定割合で一律に削ると、問い合わせの答えに必要な狭い領域を落としやすい。WaveFilterは、粗い表現で全体を安く走査し、選ばれた領域だけを高解像度で調べる**粗密二段階探索（coarse-to-fine retrieval）**を採用する。ここで圧縮は主に重要位置を探すための中間表現であり、最終的な注意へ渡す値行列までウェーブレット係数へ置き換えるわけではない。

## 手法：論文の演算順に沿った解説

### 1. 鍵系列の多重解像度表現

離散ウェーブレット変換では、低域通過フィルタと高域通過フィルタを用いて系列を近似成分と詳細成分に分解する。論文の式(5)は、低周波係数Aと高周波係数Dを畳み込みと間引きで得る形を示す。近似成分に同じ処理を繰り返せば、系列長が各段でおおむね半分となり、B段後の低周波系列は元の長さの約1/2^Bになる。

WaveFilterが入力するのは、反復時刻t−1、層lに保存されている**プロンプト位置の鍵行列**である。論文の式(6)ではこの鍵をB段DWTへ通し、圧縮後の鍵 `K_low^(B)` を作る。高周波成分を落とした低周波系列を、全文の粗い意味地図として用いる。たとえばB=2ならプロンプト側の鍵系列の長さは約4分の1になり、全位置を直接照合するより少ない候補単位を比較できる。

低周波成分は質問と関係する領域の探索用であり、これだけで元トークンの細かな差異を完全に再現できるとは限らない。特に短い数値、固有名詞、局所的な証拠が高周波成分に依存する場合、粗い段階で誤って落とす危険がある。このためWaveFilterは粗い結果を最終決定とせず、次段の再帰的な局所化を設けている。

### 2. 圧縮領域の問い合わせ依存重要度

現在の生成位置集合に対応する問い合わせ行列 `Q_t,l` と、圧縮鍵 `K_low^(B)` の内積をとり、次元数dの平方根で規格化してソフトマックスを適用する（論文式(7)）。これにより、問い合わせ位置と粗い候補領域の関連度行列 `A_t,l^(B)` を得る。圧縮系列の長さが短いため、全文の全鍵に対して同じ計算をする場合より比較対象が少ない。

次に関連度行列を列方向に集約し、各圧縮領域が現在の問い合わせ群にとってどれだけ重要かを表すスコア `W_t,l^(B)` を作る（式(8)）。ここでは「列ごとの重要度を得る」という演算目的が重要である。PDF中の式(8)は添字の記載に不整合があるように読めるため、実装時は式(7)で定義された行列の形状を基準に、**問い合わせ軸を集約して圧縮鍵の領域軸を残す**よう確認する必要がある。本文にない厳密な次元の補正を論文の確定仕様として扱わない。

重要度の上位割合 `m_B` に対応する領域を上位K件選別し、候補集合 `J_B` とする（式(9)）。この段階の出力は元のKVそのものではなく、「詳細確認すべき粗い領域の番号」である。小さい `m_B` は探索費用を下げるが見落としを増やし、大きい値は情報を多く残す代わりに後段の費用を増やす。

### 3. 領域の逆写像と再帰的な精密化

粗い領域番号 `J_B` を、元のプロンプト系列における位置集合へ戻す。論文式(10)は、各領域が覆う `2^B` 個の元位置を列挙する写像を示す。ここで抽出した鍵の部分系列へ、今度はB−1段のDWTを適用し、より細かい解像度の低周波表現を作る（式(11)）。

新しい候補系列に対して、再び問い合わせとの関連度、列方向集約、上位領域選別を行う。この処理をBからB−1、さらに1まで繰り返すと、最初は全文の大まかな区間だけを見ていた探索が、徐々に個別トークンに近い位置へ絞られる。前段で候補外となった領域は後段の演算に入らないため、**最初の選別が誤っている場合は後段で救済できない**。これは多段階検索の根本的な品質制約である。

段数Bが大きいほど最初の圧縮は強くなるが、変換・照合・選別を繰り返す回数も増える。著者の感度分析ではB=2または3で精度が高い条件が多く、B=4では情報損失と処理費用が問題となる。最終的な既定値はB=2である。

### 4. 元の鍵・値から疎なKVキャッシュを構築

最後の候補位置集合 `μ_0` を用いて、保存済みの**元の**鍵行列と値行列から必要位置だけを索引抽出する。これらに現在の生成位置側の鍵・値を連結し、疎な鍵 `K_sparse` と疎な値 `V_sparse` を構築する。現在の問い合わせは、この疎なKVへ注意を適用して文脈表現を得る（論文3.2節末）。

鍵側のDWTは「どの元位置を残すか」の選別に使われ、値側には最終的な位置集合を適用する。したがって最終出力の値ベクトルは元キャッシュ由来であり、低周波ウェーブレット係数をそのまま注意の値として代用する方式ではない。注意の候補数が減ることで後段の計算は軽くなり得るが、WaveFilter自体のDWT、関連度計算、索引抽出、再帰処理の費用が加算される。最終速度はその差引きで決まる。

### 5. 既存方式との接続と実装上の分岐

論文はWaveFilter単体を独立した生成モデルとして評価していない。Fast-dLLMとElastic-Cacheを土台とし、既存方式のキャッシュ再利用にWaveFilterの重要位置選別を組み込む。したがって結果の差分は「基盤方式そのものの速度」と「WaveFilterを追加した場合の精度・速度」の両方で読む必要がある。

生成トークンの確定には、Fast-dLLM由来の信頼度閾値εを使う**信頼度認識型復号（confidence-aware decoding）**を採用している。確信度が閾値を超えたトークンを動的に選ぶため、WaveFilterが誤ったKVを残すと正しい確定までの反復回数が変化し、逆に重要KVを残せれば反復回数が減ることがある。単なる「キャッシュを短くした割合」と処理量が単調に対応しない理由の一つである。

## 定量結果：精度の改善と速度の交換条件

### LongBench：同じ基盤方式への追加効果

以下の正答率は論文表1の値、処理量はトークン/秒である。いずれも同一モデル・同一課題でWaveFilterの有無だけを比較した。

| モデル・課題 | 追加先 | WaveFilterなし：正答率 / 処理量 | WaveFilterあり：正答率 / 処理量 | 追加による変化 |
|---|---|---:|---:|---|
| LLaDA / Qasper | Fast-dLLM | 22.03 / 15.01 | **28.73 / 6.80** | 精度+6.70ポイント、処理量約54.7%減 |
| LLaDA / MultiFieldQA | Fast-dLLM | 24.25 / 11.59 | **26.37 / 7.42** | 精度+2.12ポイント、処理量約36.0%減 |
| LLaDA / 2WikiMultihopQA | Fast-dLLM | 3.69 / 12.87 | **4.95 / 8.66** | 精度+1.26ポイント、処理量約32.7%減 |
| LLaDA / PassageCount | Fast-dLLM | 1.03 / 8.30 | **1.90 / 5.27** | 精度+0.87ポイント、処理量約36.5%減 |
| LLaDA / TREC | Fast-dLLM | 33.03 / 0.89 | **31.10 / 0.52** | **精度−1.93ポイント、処理量約41.6%減** |
| LLaDA / MultiFieldQA | Elastic-Cache | 21.34 / 10.42 | **24.38 / 10.88** | 精度+3.04ポイント、処理量約4.4%増 |
| LLaDA / PassageRetrieval | Elastic-Cache | 21.56 / 5.32 | **21.94 / 5.11** | 精度+0.38ポイント、処理量約3.9%減 |

たとえばQasperでは、Fast-dLLMを使わないLLaDAの正答率は24.64、処理量は2.56である。Fast-dLLMは15.01へ大きく高速化するが正答率を22.03へ下げ、WaveFilter追加後は正答率が28.73へ回復する一方で処理量は6.80になる。**元モデルよりは約2.66倍速いが、Fast-dLLM単独よりは遅い**。この二つの比較軸を混同して「WaveFilterが2.66倍高速化」と説明するのは誤りである。

またElastic-Cacheは、表1で多くの課題がメモリ不足（OOM）のため欠測である。数値が存在する少数の課題だけを使って全課題での優位性を主張できない。LongBenchの課題によっては精度も速度も悪化しており、単調な改善方式ではない。

### RULER：4Kと8Kで変わる性質

RULERの表2は長さ4K・8Kの各10課題を比較している。長さの増大によりFast-dLLMとElastic-Cacheの正答率が落ちるケースがあり、WaveFilterはその一部を回復する。ただし課題によっては回復幅が小さいか、逆に悪化する。

| 長さ・課題 | 基盤方式 | WaveFilterなし：正答率 / 処理量 | WaveFilterあり：正答率 / 処理量 | 評価上の含意 |
|---|---|---:|---:|---|
| 8K・vt | Fast-dLLM | 19.08 / 17.58 | **21.56 / 13.11** | 精度+2.48ポイント、処理量約25.4%減 |
| 8K・vt | Elastic-Cache | 25.72 / 11.57 | **26.04 / 8.99** | 精度+0.32ポイント、処理量約22.3%減 |
| 8K・s1 | Fast-dLLM | 45.40 / 17.06 | **47.80 / 3.58** | 精度+2.40ポイントだが処理量約79.0%減 |
| 8K・m2 | Fast-dLLM | 40.60 / 11.53 | **38.60 / 7.05** | 精度−2.00ポイント、処理量約38.9%減 |
| 4K・m2 | Fast-dLLM | 88.00 / 22.95 | **85.80 / 13.91** | 精度−2.20ポイント、処理量約39.4%減 |
| 4K・cwe | Elastic-Cache | 16.50 / 9.03 | **16.95 / 7.44** | 精度+0.45ポイント、処理量約17.6%減 |

8K・vtの基盤LLaDAは正答率40.60である。Fast-dLLM単独の19.08に対してWaveFilterの21.56は改善だが、**密な基盤モデルとの差19.04ポイントは残る**。Elastic-Cacheの場合も25.72→26.04で改善幅は0.32ポイントにとどまる。したがって「長文脈劣化を解消した」と言い切らず、**一部を緩和した**と評価すべきである。

| MultiFieldQA＋Elastic：B=2、率0.5 | **24.38** | **10.88** | **57.45** | 図3内で良好な組合せ |
| MultiFieldQA＋Elastic：B=4、率0.3 | 22.47 | 8.06 | 78.38 | 深すぎる探索と強い削減で費用増 |

重要な点は、**処理量と総実行時間が必ずしも同じ順序にならない**ことである。論文付録の総生成トークン数も方式間で異なるため、出力トークン数と推論反復回数が変わると、単位時間当たりの処理量が高くても総時間が短いとは限らない。QasperのB=1、保持率0.4は10.19トークン/秒だが42.80分、B=2、保持率0.4は6.80トークン/秒でも36.28分となっている。生成トークン数・反復回数を固定した純粋なカーネル速度比較ではないことを明示しておく。

著者はB=2を既定値とし、保持率はデータセットに合わせて調整する。保持率が小さすぎると正答に必要な情報を失い、確定までの反復が増えて処理量が落ちる。大きすぎると不要なKVを再投入して注意計算が重くなる。図3は、適切な設定が両極端の間にあることを示しているが、全課題へ通用する単一の最適保持率は示していない。

## 既存研究との差分

**Fast-dLLM**は、拡散型LLMの反復生成で再計算を減らすためのキャッシュと信頼度認識型復号を組み合わせる。**Elastic-Cache**も拡散型LLMのキャッシュ再利用を扱う。両者の主眼は再利用による推論費用削減であり、WaveFilterは「何を残せば長文脈の質問に答えられるか」という問い合わせ依存の位置選別を追加する。つまり、生成方式そのものを置き換えるのではなく、キャッシュの参照集合を改善する補助機構である。

一般的なトークン削減や注意スコアに基づくKV間引きとの違いは、**最初から全位置に高解像度の注意を計算せず、低周波へ圧縮した鍵の領域スコアから始める**点にある。粗い候補の位置を元の系列へ戻して高解像度で再評価するため、長文脈で重要領域が局在するという構造を利用する。波形の周波数分解をそのまま言語の意味の完全な分離と見なしているわけではなく、実際の有効性は実験に依存する。

自己回帰型LLMのKV削減方式へ直接適用できるとは限らない。WaveFilterの評価は拡散型LLMの複数反復・更新位置・信頼度認識型復号を前提とする。既存のGPU推論基盤に組み込む場合も、DWTと段階的索引選択のGPU実装費用、既存キャッシュのメモリ配置、生成反復の同期点を別途評価する必要がある。

## 限界・負の結果・再現上の注意

1. **速度の一律改善はない。** LongBench QasperでFast-dLLM単独15.01→追加後6.80トークン/秒、RULER 8K・s1では17.06→3.58と、追加の選別費用が大きい条件がある。基盤の密なモデル比では依然高速でも、最適化済みキャッシュ方式に対しては減速することが多い。
2. **精度の一律改善もない。** LongBench TRECの33.03→31.10、RULER 4K・m2の88.00→85.80など悪化例がある。重要位置の粗い選別で必要情報を失うこと、閾値と保持率が課題依存であることが想定される。
3. **密なモデルとの差が残る。** RULER 8K・vtではLLaDAの40.60に対してWaveFilter＋Fast-dLLMは21.56、＋Elastic-Cacheは26.04である。著者の「劣化を緩和」は「元の品質を回復」と同義ではない。
4. **ベースラインの欠測がある。** LongBenchのElastic-Cache行は多くの課題でメモリ不足のため「—」になっている。欠測をゼロや劣位と見なして平均することはできない。
5. **最終キャッシュ長・帯域削減の網羅的な測定ではない。** 論文の主要表は正答率と処理量、付録は総トークン数と総時間である。選別の演算内訳やメモリ帯域の絶対節約を直接示す詳細なシステム測定として読むべきではない。
6. **1台のA800上でのオフライン評価である。** バッチ混在、GPU間通信、KVページ断片化、連続バッチング、サービス水準目標を含む本番運用の効果は検証していない。
7. **DWTの近似に関する前提がある。** 鍵ベクトルの低周波成分が問い合わせに重要な領域を示すという仮説は、細部の識別や局所的な事実抽出では破綻し得る。早い段階で落とした領域は再帰的な詳細探索では回復できない。
8. **モデル間の一般化は限定的である。** LLaDA-8B-InstructとDream-v0-Base-7Bで検証しているが、任意の拡散モデルや自己回帰モデルへの移植可能性、量子化KVとの相互作用は未実証である。
9. **公式コードは未確認。** 本文に実装の構成はあるものの、公式リポジトリURLは確認できなかった。アルゴリズムの詳細、式(8)の添字、保持率の課題別設定は再現時に追加確認が必要となる。

## 実装を検討する際の検証順

まずFast-dLLMを同じモデル・入力長・信頼度閾値で再現し、キャッシュ追加前後の精度と処理量を別々に計測する。次にWaveFilterの低周波鍵を生成するDWT処理、粗い関連度計算、上位領域選別、細かい解像度への逆写像、元KVの索引抽出をそれぞれ独立に計測する。追加した選別費用が節約した注意計算より大きければ、論文表1のように精度が上がっても処理量が下がる。

実装上は、段数Bと保持率を固定した上で、選別位置集合の正しさを高密度注意の参照と比較することが重要である。特に固有名詞や数値のような局所的な答えを含むRULER・LongBench課題で、粗い段階の取りこぼし率を測ると、速度低下の原因がDWTの計算費用なのか、情報欠落による反復増加なのかを分離しやすい。これは論文の測定をそのまま引用したものではなく、論文の機構と負の結果から導いた実装時の追加検証案である。
