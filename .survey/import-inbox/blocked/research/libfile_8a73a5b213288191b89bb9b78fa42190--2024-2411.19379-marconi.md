# Marconi: Prefix Caching for the Era of Hybrid LLMs

## 概要
ハイブリッドLLMは注意層の間に状態空間モデル（SSM）等の再帰層を挟み、長文脈の計算量と状態容量を減らす。しかしprefix cacheでは、注意層のKVは系列軸で切り戻せるのに対し、SSM状態は履歴を1個の状態へin-place更新するため、長い系列の最終状態から途中prefixの状態を復元できない。任意prefix再利用のため一定間隔でSSM状態をcheckpointすると、ほとんど再利用されない巨大状態がcacheを圧迫する。

Marconiはradix treeで過去requestのprefix関係を追跡し、将来再利用の可能性が高い位置だけSSM状態を保存する。退避時には単なる最終使用時刻ではなく、cache 1 byte当たりに再計算を何FLOP省けるかを評価する。MLSys 2025版ではtoken hit率を平均4.5〜34.4倍改善し、P95の最初のトークンまでの時間（TTFT）を36.1〜71.1%、絶対値で103.3〜617.0 ms削減する。

## 問題設定
注意層ではprefixのKVがtoken列として保存されるので、1…q tokenのcacheから1…p tokenだけを残す切り出しが可能である。SSMでは過去を固定サイズ状態へ畳み込み、次tokenごとに上書きするため、この操作ができない。将来どのprefixが共有されるか不明な状態で全checkpointを残すと、SSM層が多いハイブリッドモデルほどcacheが膨らむ。

論文の例ではblock size 32でKV token blockの25.0%が再利用される一方、SSM状態の再利用は0.4%に留まり65.3倍の差がある。7Bモデル・10K tokenでは細粒度checkpointによる状態が17.4 GBとなり、同規模Transformerの3.3倍に達する。したがって「prefixを細かく切ればhit機会が増える」というTransformer向け方針が逆にcache thrashingを起こす。

## 手法
### 再利用形態に基づくadmission
Marconiは共有prefixを、system prompt等の入力だけが共有される場合と、会話履歴のように入力＋過去出力が共有される場合へ分ける。後者は通常、前回の最後の生成tokenから会話を継続するので、各系列の最後のdecode状態を必ず候補にする。前者は複数requestで同じprefixが現れることをradix treeから検出する。

### speculative insertionとcheckpoint
新しい入力をprefillする前にradix treeへ投機的に挿入し、既存系列との共有で新しい中間分岐点が生まれるかを確認する。分岐点になったprefixだけSSM checkpointを作る。chunked state passing対応SSMでは近いchunk境界の状態を物質化し、非対応モデルでは必要に応じ二段prefillで正確なprefix状態を得る。

### KVとSSM状態の一体管理
prefix hitは全層が同じprefixを表現できなければ成立しないため、KVだけhitしてSSM状態がないcache entryは利用できない。Marconiはradix treeの同じnode/edgeで注意層KVとSSM状態を対応付け、prefix単位で一体的に管理する。

### FLOP-aware eviction
KVは系列が長いほど容量も再計算削減量も概ね増えるが、SSM checkpointは系列長と無関係に固定サイズである。そこでMarconiはrecencyだけでなく、entryを残すことで省けるprefill FLOPを占有メモリで正規化した価値を使う。短いprefixのhit数を多少犠牲にしても、長いprefixの再計算を避けるentryを優先できる。

## 主要結果
|条件|指標|Marconiの結果|解釈|
|---|---|---|---|
|複数workload/モデル|token hit率|基準比平均4.5〜34.4倍|低再利用SSM checkpointを排除できる|
|同条件|P95 TTFT|36.1〜71.1%削減|hit増加がprefill待ち短縮へ変換|
|同条件|P95 TTFT絶対差|103.3〜617.0 ms削減|倍率だけでなく実遅延でも改善|
|block size 32の分析|KV/SSM再利用率|25.0% / 0.4%|従来の一律checkpointの浪費を実測|
|7B・10K token分析|cache容量|17.4 GB、同規模Transformer比3.3倍|SSM checkpointがcacheを圧迫|

マイクロベンチマークではcontextが長い、SSM層比率が高い、SSM状態次元が大きいほどMarconiの利得が増える。これはハイブリッド化が進むほど従来cacheのSSM checkpoint費用が増えるためである。

## 既存研究との差
vLLMやSGLangのprefix cacheはTransformerのKVをtoken block単位で管理し、任意prefixへ切り戻せることを暗黙に利用する。Marconiはこの前提が成立しないSSM状態を扱い、どの位置をcheckpointするか自体をcache admission問題へ変える。radix treeも単なるlookup索引ではなく、共有prefixを事前検出してcheckpoint生成を決めるために使う。

## 限界
入力だけの共有prefixは2回目の出現で初めて共有を認識し、その回でcheckpointを作るため、実際に再利用できるのは原則3回目以降となる。任意prefixを全てcheckpointしないため、未知の一度限りの分岐には従来の細粒度cacheより弱い。二段prefillが必要なSSMではcheckpoint作成費用も増える。
