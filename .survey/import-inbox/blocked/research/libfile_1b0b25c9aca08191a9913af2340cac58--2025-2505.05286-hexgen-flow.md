# HEXGEN-FLOW: Optimizing LLM Inference Request Scheduling for Agentic Text-to-SQL

## 概要
エージェント型Text-to-SQLでは、1件の自然言語質問がschema検索、候補生成、検証、修正など複数段のLLM呼び出しへ展開される。各呼び出しは独立ではなく、前段の出力が次段を解放する有向依存を持つ。さらに企業クラスタではA100、L40、A6000のような世代・性能の異なるGPUが混在し、利用者ごとにend-to-endのサービス水準目標（SLO）が異なる。

HEXGEN-FLOWはこのworkflowを単発request列として扱わず、query全体の進捗と残りdeadlineをスケジューリングへ入れる。中央dispatcherがrequestの計算量と各model instanceの能力・queueを見て配置し、instance内ではurgencyに基づき待ちrequestを継続的に並べ替える。CHESS workflowとvLLMを用いた異種GPU評価では、vLLM比でSLO deadlineを最大1.67倍厳しくして同等達成率を維持し、throughputを最大1.75倍改善した。

## 問題設定
通常のLLMサービングは各requestを独立とみなし、到着順、token長、batch形成などを最適化する。しかしagentic workflowでは前段が遅れると後段の開始時刻も遅れ、同じ100 msの遅延でもworkflow初期と終盤ではend-to-end deadlineへの影響が異なる。

異種GPUでは同じprompt/output長でも処理時間が異なる。round-robinで均等にrequest数を割り振ると、重いstageが遅いGPUへ集中したり、高性能GPUが軽いrequestで埋まったりする。さらに各model instanceが自分のqueueしか見ないと、query全体の残り時間を考慮できない。

## 手法

### workflow依存追跡
中央coordinatorはText-to-SQL queryを複数stageの依存グラフとして追跡する。前提stageが完了したrequestだけをdispatch可能にし、互いに独立な枝は同時に解放する。これにより依存関係を壊さず、workflow内に存在する並列性を明示的に利用する。

### workload-balanced dispatcher
新しく実行可能になったrequestについて、入力token、予測出力token等から計算需要を推定する。一方、各model instanceについてGPU種類、既存queue、処理能力から供給能力を表す。dispatcherは単純なrequest数ではなく「要求workload / instance capacity」を均すよう配置する。

この方式では計算の重いstageをA100等へ寄せ、軽いstageをL40/A6000の空きへ送れる。論文のcase studyではround-robinが各instanceへ均等件数を配るのに対し、workload-balanced方式はstage別に大きく偏った配置を選び、異種性能を利用している。

### urgency-guided local queue
一度instanceへ送ったrequestは、局所queue内でurgencyに基づいて並べ替える。urgencyはqueryの残りdeadline、workflow進捗、予測実行時間を反映し、待ち時間が増えてslackが減ると優先度が上がる。中央で頻繁にin-flight requestを移動するのではなく、globalは新着配置、localは細粒度deadline制御を担当する。

### シミュレーションによる係数調整
workload balanceとurgencyの重みを決める係数は負荷・hardware構成によって最適値が変わる。HEXGEN-FLOWは実クラスタで大量試行せず、軽量simulationで候補係数を評価してlive servingへ適用する。論文は複数trace・Hetero-1/Hetero-2で係数感度とsimulation tuningの妥当性を調べる。

## 評価条件

|項目|内容|
|---|---|
|workflow|CHESS Text-to-SQL|
|推論engine|vLLM、continuous batching|
|Hetero-1|A100 + A6000、各種2 model instance|
|Hetero-2|A100×2 instance + L40×1 + A6000×1|
|Homo|A100のみ4 instance|
|各instance|4 GPUを割当、モデル提供はtensor parallelismを利用|
|負荷|3種trace、複数query arrival rate、multi-tenant SLO|
|比較|vLLM等の既存スケジューリング|
|指標|end-to-end latency/SLO達成率、throughput、配置分布|

## 主要結果

|条件|比較|結果|意味|
|---|---|---|---|
|複数trace・異種GPU|vLLM|deadlineを最大1.67倍、平均1.41倍厳しくして同等SLO達成|workflow-aware schedulingでtail余裕を増やす|
|複数負荷|vLLM|throughput最大1.75倍、平均1.65倍|異種GPUの処理能力をrequest数ではなくworkloadで使い分ける|
|Hetero-2 case study|round-robin|重いstageをA100へ偏らせる配置|workload-balanced dispatcherの動作を確認|
|係数感度|固定係数|trace/hardwareで最適値が変化|simulation tuningが必要な理由|

SLO改善は単一LLM callのカーネルを速くした結果ではなく、query全体のcritical pathへ資源を優先して待ち時間を減らした結果である。特に複数利用者が異なるdeadlineを持つ場合、local urgency queueが「先に来たrequest」より「残りslackが小さいrequest」を前へ出す。

## 既存研究との差
vLLM等のcontinuous batchingは独立requestのGPU利用率を高めるが、複数callから成るworkflow全体のdeadlineや依存関係を直接管理しない。一般的なload balancerもinstance queueを均すことはできるが、stageごとのtoken workloadとGPU種類の処理能力差を同時に扱わない。

agentic serving研究に対してHEXGEN-FLOWはText-to-SQLという具体的なmulti-stage workflowを対象に、global配置とlocal deadline queueを分離した二段階制御を実装し、異種GPU環境でend-to-end SLOまで測る点が特徴である。

## 限界
評価workflowはCHESSベースのText-to-SQLであり、tool latencyが支配的なweb agentや、分岐・反復回数が大きく変動する一般agentへ同じ予測精度が得られるとは限らない。request workloadと実行時間の推定誤差が大きいと、global配置とurgencyの双方が誤る。

local queueはdispatch後のrequestを別instanceへ再移動しないため、到着後に負荷が急変した場合は初期配置の誤りを完全には修正できない。simulation tuningもtrace分布が変われば再調整が必要であり、係数選択自体がゼロコストではない。
