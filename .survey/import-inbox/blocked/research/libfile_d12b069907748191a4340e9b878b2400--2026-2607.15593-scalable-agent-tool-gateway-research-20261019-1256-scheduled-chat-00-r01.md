# Scalable LLM Agent Tool Access in the Cloud

## 概要

本研究は、エージェント型大規模言語モデル（LLM）がクラウド上の数千の操作を外部ツールとして使う際、ツール一覧をそのままモデルの文脈へ渡す設計が限界に達する問題を扱う。対象はモデルの重みや注意計算を直接高速化する方式ではなく、モデルが次に呼ぶべきツールを決定するための**推論周辺の通信・検索・ルーティング基盤**である。著者らはモデル文脈プロトコル（Model Context Protocol; MCP）のゲートウェイを実運用し、従来のAPIをMCPに変換しながら、問い合わせに関連する少数のツールだけを提示する構成を提案した。

従来の「利用可能な全ツールのスキーマを毎回プロンプトに含める」方式では、ツール数が増えるほど入力トークン、推論遅延、誤選択が増える。論文の測定では、Qwen3-MAXに120ツールを与えるだけで選択処理が100秒を超え、180ツールでは200秒を超える例がある。また複数のMCPサーバー複製へ直接接続する場合、状態を持つセッションをどの複製へ送るかをエージェント側で管理する必要が生じる。

提案システムは①OpenAPIからMCPへの変換と複数転送方式の吸収、②入口・出口認証とツール単位の権限管理、③密ベクトル検索と字句検索を統合したツール推薦、④セッション情報を共有した状態付き経路選択を一つのゲートウェイへ集約する。Alibaba Cloudの3,616ツールを用いた実験では、上位15件に正解ツールが含まれる再現率（Recall@15）が98.2%、モデルが最終的に正しいツールを選ぶ精度が81.6%である。別のエージェント選択実験では全ツール提示の平均55.7秒・505.86千トークンを、推薦上位15件の提示によって6.2秒・21.22千トークンへ削減した。

ただし、状態付きルーティングのための集中セッション情報参照は実際の律速となる。ゲートウェイを4複製へ増やした実験で、単一複製時6.81ミリ秒だった応答時間の99パーセンタイルが55.61ミリ秒へ悪化している。**ツール選択の推論費用を下げる効果と、状態付きネットワーク中継の費用は別々に評価すべき**ことが重要な結果である。

## 問題設定と既存方式の限界

MCPはエージェントからツールサーバーへの一覧取得（List Tools）と実行（Call Tool）を統一するが、旧来のOpenAPIサービスが自動的にMCP対応になるわけではない。MCPには従来のHTTPとサーバー送信イベント（Server-Sent Events; SSE）を併用する方式と、単一エンドポイントのStreamable HTTPがあり、転送形式や認証方式も異なる。クラウド事業者が数万の既存API操作を個別に改修するのは高コストである。

ツールの数を単にモデルの文脈へ載せる方法には二つの制約がある。第一に、ツール定義のスキーマが入力トークンを占有する。論文の例ではVPCの120ツールを展開すると、トークナイザーによって5.6万〜16.6万超のトークンが必要になる。第二に、長い一覧からモデル自身に検索させると選択の遅延・精度が悪化する。ToolBenchで全ツール提示の選択精度は15ツール時92.4%から640ツール時78.2%へ低下した。実運用のツール一覧では、752件以上で実験モデルの文脈窓に収まらない条件がある。

さらにMCPのツールサーバーが状態を持つ場合、セッション開始を担当したバックエンドと後続の呼び出し先が一致しなければならない。通常のL7負荷分散器はHTTPヘッダーや経路を基に振り分けるが、MCPでは実行対象がJSON-RPCの本文内にある。クライアントとサーバーの双方が複製され、SSEの長寿命接続まで存在すると、単純なラウンドロビン転送では応答経路の整合が保てない。

## 手法：エージェント要求の処理経路

### 1. OpenAPI操作のMCP化とプロトコル適応

ゲートウェイは既存API仕様の各操作を**1操作につき1個のMCPツール**へ対応付ける。登録時にOpenAPI定義から操作名、説明、引数スキーマを抽出し、MCPのList ToolsとCall Toolに対応するメタデータと変換規則を生成する。曖昧なAPI記述を補う場合のみ、事前処理でLLMを使って説明を補強し、実際の呼び出し経路は決定的な変換規則で実行する。入力はAPI仕様とMCPのJSON-RPC要求、出力は既存APIに適したHTTP呼び出しと正規化したMCP応答である。

通信経路では、ゲートウェイがJSON-RPC本文から対象ツールを読み取り、バックエンド種別と転送方式を付与し、必要ならAPI呼び出しへ書き換えて転送する。MCPのHTTP+SSEとStreamable HTTPの橋渡しもここで行う。データ層の「どの操作を実行するか」と転送層の「どう接続するか」を分離しているため、転送仕様が変わってもAPI操作ごとの変換規則を全面改修する必要がない。論文ではGoによる本体約8,000行とWebAssemblyの変換器約6,000行を本番L7基盤へ組み込んだ。

### 2. ツール推薦：意味検索と字句検索の融合

エージェントに全ツールを列挙せず、ゲートウェイは検索用の**Tool Searchを通常のMCPツールとして公開**する。エージェントはユーザーの意図をクエリとしてCall Toolを実行し、返された少数の候補スキーマを使って次のツールを選ぶ。既存のList Tools自体に非標準の検索パラメータを追加しないため、MCPクライアントとの互換性を保てる。

ツール登録時には二つの索引を作る。意味索引はツール名・説明を事前学習済み符号器で密ベクトル化し、自然言語の言い換えを近傍検索する。字句索引は名前・パラメータ名・リソース識別子を全文索引化し、BM25で一致度を測る。問い合わせ時には近似最近傍探索（Approximate Nearest Neighbor; ANN）とBM25が別々に候補を返し、その和集合を**逆順位融合（Reciprocal Rank Fusion; RRF）**で統合する。順位を使うことで両検索器の生スコア尺度が異なっていても結合できる。融合後の上位K件だけがモデルに提示される。

この分離は重要である。密ベクトルだけでは製品IDやパラメータ名の完全一致を取りこぼしやすく、字句だけでは「仮想ネットワークを作る」のような言い換えに弱い。実運用の3,616ツールでは複合方式のRecall@15が98.2%、密検索のみのRAG-MCPは83.1%、ToolLLMは78.6%、BM25は67.7%であった。推薦器をLLMで動かさず決定的な検索処理にしたことも、選択時の追加推論遅延を抑える理由である。

### 3. 認証・ツール単位の権限制御

入口ではAPIキー、OAuth、JWTなどで利用者を認証し、出口ではその利用者に対応するバックエンド側の認証情報へ変換する。List Tools、Call Tool、Tool Searchのそれぞれに対して利用者ごとの公開・実行権限を判定し、許可されないツールを推薦結果にも出さない。バックエンド自体に認証機構がない場合は、ゲートウェイ経由以外のアクセスを制限することが前提となる。

この設計では、ツール一覧の候補を絞るだけでなく、**検索段階の可視性と実行段階の許可を同じ利用者IDへ結び付ける**。したがって推薦エンジンの高速化だけを独立導入しても、この論文の多利用者環境での機能を再現したことにはならない。

### 4. セッション固定と複製ゲートウェイ間の整合

ゲートウェイはクライアントに返すフロント側セッションIDと、バックエンドが発行するセッションIDを別々に管理する。初回接続時に前者を生成し、対象MCPサーバーへ接続した時点で後者との対応を集中セッション保存領域（Session Metadata Store）へ登録する。後続の呼び出しが別のゲートウェイ複製へ到着しても、この対応表を参照すれば同じバックエンドセッションへ転送できる。

さらにフロント側セッションIDから経路用ハッシュ（Routing-Hash）を生成してバックエンドサービスへ送る。サービス内の複製選択はこのハッシュで一貫した振り分けを行うため、ゲートウェイ側で各バックエンド複製の増減を直接追跡する必要がない。HTTP+SSEのように応答を元の長寿命接続へ戻す必要がある場合は、発行先のゲートウェイ複製と実際の処理複製が異なることがある。その際だけ発行元へ要求または応答を中継する発行購読方式（Publish/Subscribe; Pub/Sub）を利用する。

この仕組みは状態を維持できる反面、集中保存領域への問い合わせと複製間転送を増やす。論文の運用上の教訓として、セッションIDに所有ゲートウェイのヒントを埋め込み、集中参照を減らす改良案が示されるが、**その方式は提案・進化中の設計であり、既存の集中方式と同じ本番評価済み完成機能として扱わない**。

### 5. 依存ツールの補完と問い合わせキャッシュ

ツール推薦で最終操作だけが返ると、必要な事前操作が不足する。例えばロードバランサー作成の前にVPCとVSwitchを作る必要がある。著者らは登録時にツールスキーマの外部キー関係を解析し、トポロジカルソートで依存ツールの有向非巡回グラフ（DAG）を組み立てる**知識キャッシュ（Knowledge Cache）**を追加した。問い合わせ時に上位候補へ依存チェーンを併合するため、エージェントが推論をもう1周して不足ツールを探す回数を削減する。

また本番問い合わせを224個の意図クラスタに分けたところ、上位10クラスタがトラフィックの80.2%を占めた。そこで〈問い合わせ、ツール集合〉の対を最近使用時刻で追い出す方式（Least Recently Used; LRU）で保持し、命中時には推薦器を省略する。別途、IDだけが与えられる曖昧な問い合わせでは、ID形式から対象資源種別を推定する書き換え規則を自動抽出し、LLMの書き換え器へ渡す。これは単純な意味検索が不得意な、識別子しかない入力への対策である。

この表の速度倍率は異なる層の測定を混同してはならない。**8.9倍はツール選択の所要時間、23.8倍はツール選択に使ったトークン数、202〜243ミリ秒は検索器単体の遅延、数ミリ秒はゲートウェイ中継の応答時間**である。LLM自体のトークン毎秒やKVキャッシュの圧縮率を改善したという結果ではない。

### 構成要素と負の結果の読み取り

推薦器の密検索と字句検索を比較した実験は、両者の補完関係を直接示す。学習済みToolLLMは学習対象のToolBenchでほぼ完全な再現率を示す一方、本番3,616ツールでは78.6%へ低下する。対して再学習なしの複合検索は98.2%を維持するため、**ベンチマーク固有の学習が本番カタログへ移らない**という実務上の差が見える。

状態付きルーティングでは、複製を増やすと必ず速くなるわけではない。単一複製時の平均応答時間4.59ミリ秒のうち3.45ミリ秒がセッション管理で、4複製時には集中保存領域へのキャッシュミスで平均16.26ミリ秒に悪化する。状態なしの比較ではこの傾向が見られず、集中セッション管理がボトルネックである。論文の本番スケールアウト図では約7ミリ秒の安定した応答時間も示すが、**その本番トレースと4複製の状態付き負荷実験を同じ測定条件として相殺しない**。

依存チェーン補完は、推薦の正解率とは別の「実行に必要なツールが全部揃うか」を測る。3,616ツールの条件で単純推薦の前提ツール完全性24.5%が、知識キャッシュでは100%になる。一方、依存関係がスキーマから十分に抽出できることが前提であり、任意の動的依存や副作用の安全性まで保証する結果ではない。

## 既存研究との差

通常のL7負荷分散器はHTTPのヘッダーやパスで振り分けるが、MCPのツール実行先はJSON-RPC本文とセッション状態を解釈しなければ決まらない。本研究はプロトコル変換、本文解釈、認証、セッション固定を共有中継点へ移し、MCPクライアント側の負担を減らす。ツール推薦の既存方式RAG-MCPは密検索中心、ToolLLMはベンチマークで訓練された検索器であるのに対し、提案方式は意味・字句の複合検索を本番の変更されるツール一覧へ適用する。

推論サービングの従来研究がモデル実行のスケジューリングやKVキャッシュを直接最適化するのとは異なり、本論文はエージェントの**ツール発見・呼び出しに伴うモデル推論の回数と文脈消費**を減らす。したがって基盤LLMの推論エンジンそのものを高速化する論文とは分けて位置付けるのが適切である。

## 限界・実装状況

評価はAlibaba Cloudのツール体系、トレース、認証・転送基盤を中心としている。3,616ツールでのRecall@15や81.6%の選択精度は、このカタログと問い合わせ分布における値であり、他事業者のAPI、異なる言語、より深いツール依存関係への一般化は別途検証が必要である。ツール推薦に使う検索器は独立マシンで動き、モデル側の推論時間やネットワーク往復をすべて消せるわけではない。

集中セッション管理には遠隔参照遅延と外部保存領域への依存があり、ゲートウェイを複製すると尾部遅延が悪化する条件が明示されている。所有者情報をセッションIDへ埋め込む設計は今後の改善案であり、論文の既存方式の弱点を解消済みと解釈しない。さらに著者らはOpenAPI 3.0/3.1の多数操作を検証したが、非同期・ストリーミング操作のサポートは限定的と述べる。完全なAPI互換性やあらゆるツール実行の成功率を保証した実験ではない。

公式公開コードのURLは一次資料中で確認できなかった。Go本体とWebAssembly変換器は著者らの本番環境に実装されているが、一般利用者が同じ機能を再現できるオープンソース実装の存在は未確認である。
