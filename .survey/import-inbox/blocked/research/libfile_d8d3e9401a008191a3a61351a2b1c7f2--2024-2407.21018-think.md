# ThinK: Thinner Key Cache by Query-Driven Pruning

## 概要
KVキャッシュの大きさはbatch、系列長、layer、head、head内channel次元の積で増える。H2OやSnapKVは主に系列長方向で不要tokenを削り、KIVI等はbit幅を下げる。一方、ThinKはkey tensorのchannel次元そのものに注目する。著者らはkey channelの大きさが強く偏り、attention weightにも低rank構造があることから、全channelを各tokenについて保存する必要はないと考える。

ThinKは各attention headについて、最近のqueryが各key channelを通じてattention scoreへどれだけ寄与するかを測り、重要channelだけを残す。token evictionとは異なる軸なのでH2O/SnapKVと併用でき、量子化とも併用できる。LLaMA-3とMistralの長文評価では40% key-channel pruningで品質を維持または改善する条件が多く、KIVI併用時にはpeak memoryを2.8倍削減する。

## 問題設定
key/valueは概ね `B×S×L×N×D` の状態を持つ。従来のKV evictionは系列長 `S`、layer sharingは `L`、量子化は各要素のbit数を削るが、head内次元 `D` は固定のまま残る。

しかしattention scoreは `QK^T` で決まるため、あるquery集合に対してほとんど寄与しないkey channelが存在すれば、そのchannelを保存・読出し続ける必要はない。単純なkey magnitudeだけで削ると、値が小さくてもqueryと強く整合するchannelを落とすため、ThinKはquery依存の寄与を直接評価する。

## 手法

### channel pruningの目的関数
head `i` のquery `Q_i` とkey `K_i` に対し、保持channelを対角binary selection matrix `S` で表す。ThinKは元のattention logit `Q_i K_i^T` と、削減後 `Q_i S (K_i S)^T` のFrobenius norm差を最小化するようchannelを選ぶ。保持数はpruning ratio `λ` から固定される。

全組合せ探索は高価なので、各channel `j` の寄与 `||Q_i[:,j] K_i[:,j]^T||_F` をscoreとして上位`T` channelをgreedyに残す。出力はpruned key cacheとbinary channel maskであり、次のattention計算では同じmaskをquery側にも適用して次元を合わせる。

### 観測query
将来queryは未知なので、現在までの最近のquery窓を観測値としてscoreを作る。これはSnapKV等が観測窓から重要tokenを推定する発想をchannel方向へ適用したものだが、選ぶ対象はtoken位置ではなく各headのfeature channelである。

query分布が変われば重要channelも変わり得るため、観測窓が将来を代表することが前提になる。論文は低rank性と実測のchannel magnitude偏りから、この近似が長文taskで成立することを検証する。

### token evictionとの併用
H2O/SnapKVで系列長方向のtoken数を減らした後、残ったkeyのchannelをThinKでさらに削る。二つのmaskは異なる次元へ作用するため、同じKV-size条件でもメモリを追加削減できる。LongBenchでは`λ=0.4`が安定し、より強い`λ>=0.5`では小KV-sizeで品質低下が目立つ。

### KIVI量子化との併用
KIVIはkeyをchannel単位、valueをtoken単位に低bit量子化する。ThinKは量子化前後で不要key channelを落とし、保存する量子化要素数自体を減らす。論文の実装図ではprefill/decode双方でpruningとquantizationを接続し、単なる理論メモリ式ではなくpeak GPU memoryとbatch sizeを測る。

## 評価条件

|項目|内容|
|---|---|
|モデル|LLaMA-3-8B-Instruct、LLaMA-3-70B、Mistral-7B-Instruct-v0.2|
|task|LongBench、Needle-in-a-Haystack等|
|組合せ|H2O、SnapKV、KIVI + ThinK|
|KV-size|128 / 512 / 1024 / 2048等|
|主pruning ratio|λ=0.4、0.5、0.6等|
|評価軸|task score、peak memory、最大batch size|

## 主要結果

|条件|結果|意味|
|---|---|---|
|SnapKV/H2O + ThinK、λ=0.4|多くのLongBench条件で元方式と同等以上|channel削除が単なる品質損失ではなくnoise除去にもなる|
|LLaMA-3-70B|40% key channel pruningでもSnapKVと同等以上|8Bだけの現象ではない|
|KV-size 2048、λ=0.4|LLaMA-3-8B full KVを上回る条件|token+channel選択で不要状態を除ける|
|KIVI + ThinK|peak memory 2.8倍削減|token/bit軸とは別の削減を積み上げられる|
|単一GPU|KIVIのbatch拡大4倍→ThinK併用5倍|メモリ削減が実際の同時処理数へ変換される|
|λ>=0.5 + 小KV-size|accuracy低下|tokenとchannelを同時に削り過ぎると情報不足になる|

Needle-in-a-HaystackではLLaMA-3-8BのSnapKVがKV-size 128で79.6、512で90.2に対し、ThinK `λ=0.4`併用は79.6、90.3でほぼ維持する。強い削減率では小さなKV budgetほど悪化し、削減軸同士の相乗的な情報損失が限界になる。

## 既存研究との差
H2OやSnapKVは「どのtoken位置を残すか」を選ぶ。ThinKは同じtokenを保持したまま「key vectorのどのchannelを残すか」を選ぶため、両者は直交する。KIVIは保存要素の精度を下げるのに対し、ThinKは保存要素数を減らす。

低rank projection方式は固定または学習した低次元空間へkeyを写すが、ThinKは既存モデルを再学習せず、実際のqueryからheadごとにbinary channel maskを選ぶ。したがってquery適応性を得る代わりに、mask計算と観測queryへの依存が追加される。

## 限界
重要channelは観測queryから推定するため、将来queryの分布が大きく変わるとmaskが不適切になり得る。multi-requestで将来queryが未確定のprefix cacheを一度だけ作る用途では、query依存性がcache再利用を難しくする。

keyよりvalueのchannel magnitudeは均一で、論文自身もvalue channel pruningの方が難しいと報告する。LLaMA-3-8Bではkey/value双方30%削減でも許容可能だが、Mistralではvalue削減による軽い品質低下が見られる。したがってheadlineの安定した結果は主としてkey cache pruningに対するものである。
