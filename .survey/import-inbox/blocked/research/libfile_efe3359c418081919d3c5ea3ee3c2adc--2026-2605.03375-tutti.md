# Tutti: Making SSD-Backed KV Cache Practical for Long-Context LLM Serving

## 概要

長文脈の接頭辞キャッシュはHBMやCPU DRAMを超え、NVMe
SSDへKVキャッシュを置く必要が出る。しかしGPU Direct
Storage（GDS）を使ってデータ本体をGPUへ直送しても、I/O発行・完了管理をCPUが担うと、小さなランダムI/Oの大量発行でCPUが律速しGPUが待つ。TuttiはHBM↔SSDのクリティカルなデータ経路とI/O制御経路からCPUを外す。

GPUネイティブobject storeでvLLMの分散KV blockを大きなI/O単位へ束ね、GPU
io_uringでGPU自身がNVMeキューを操作し、層ごとの余剰SM時間へI/Oを配置する。2台のH100
80GBと4台のSolidigm NVMe
SSDで、GDS対応LMCacheより厳しいSLO条件のTTFTを最大78.3%削減し、1秒TTFT
SLOで処理可能要求率を2倍、サービングコストを約27%削減する。

## 問題設定

SSDは容量単価が低いが、vLLMのKVはGPU上で細粒度ページに分散する。従来のCPU中心ストレージ経路では、各I/Oのdescriptor作成・submission・completion処理がCPUへ集中し、SSD自体の帯域を使い切れない。GDSもCPU
bounce bufferは避けるが、I/O開始の制御までGPU化するわけではない。

さらにGPUからI/Oカーネルを動かせば解決するわけでもない。I/OカーネルはSMを使い、同時read/writeはPCIeやSSD帯域を奪い合う。長いI/Oカーネルを無条件で走らせると、埋め込み・正規化・行列積など推論カーネルを遅らせる。

## 手法

### GPUネイティブobject store

vLLMの論理KV
blockをGPU側objectとして扱い、断片的なGPUアドレスをNVMeが扱いやすい大きな転送へまとめる。GPU
file poolは層単位の `retrieve_layer` / `store_layer`
を提供し、vLLMのKVConnectorから呼び出す。これにより推論の層進行とKV転送の粒度を揃える。

### GPU io_uring

CPU側のI/O発行を避けるため、GPU上にsubmission/completion
queueを置き、GPUカーネルがNVMe commandを非同期発行する。各GPUへ独立queue
pairを割り当てるので、多GPUでもCPUの共有キューを経由しない。prototypeではSSD1台あたり各GPU32
queueを用意し、帯域を飽和できる。

### slack-aware I/O scheduling

モデル・入力長・prefix長ごとに、各層でSMと帯域に余裕がある時間窓をオフライン計測しlookup
tableへ保存する。実行時はcritical
pathのreadを優先し、次のslackへ収まるI/O
command数だけ発行する。writeはread後へ回し、prefill中に収まらなければdecodeや後続requestの空きへ遅延する。read/writeを無条件に重ねないことで、I/O同士と推論カーネルの競合を避ける。

### 多GPU・クラスタ拡張

tensor parallelismでは各vLLM GPU processにTutti
instanceを対応させ、ローカルNVMeを独立利用する。ノード間はMooncakeをmetadata/control
planeとして使い、ローカルreplicaを優先する。現prototypeのremote
pathはGPU
fileを一度hostへ読みRDMA転送するため、ローカル経路ほどCPUフリーではない。

## 評価条件

  項目           内容
  -------------- ------------------------------------------------
  CPU/メモリ     64-core Intel Xeon 6530、512GB
  GPU            2×H100 80GB
  SSD            4×Solidigm D7-PS1010 7.68TB
  host tier      pinned DRAM 256GB、GPUあたりSSD volume 14TB
  モデル         Llama3-8B、長文脈拡張でGLM-4-9B-Chat-1M
  ソフトウェア   vLLM 0.12.0/0.17.0、LMCache各tier
  ワークロード   LEval 3K--200K、LooGLE 100K超を含む
  比較           HBM、LMCache-DRAM-LW、LMCache-SSD、LMCache-GDS

## 主要結果

vLLM
0.17.0の高負荷LEvalで、TuttiはTTFTをDRAM比69.1%、GDS比78.3%削減した。1秒TTFT
SLOでは要求率がDRAM比50%、GDS比100%高い。LooGLE 0.6
RPSでもGDSのTTFTはTuttiの約2.63倍である。

microbenchmarkでは長いcontextのretrieveが25.9GB/sに達し、同じ2
SSDのLMCache-GDS約11.9GB/sに対して最大2.08倍。128K総入力でprefixを変える試験ではGDS比5.8〜61.4%
TTFTを短縮し、16K〜96K
prefixではDRAMを最大13.4%上回る。ただしprefix再利用が96Kを超えほぼI/O律速になるとDRAMが再び最大20.6%速い。

2GPU・4SSDのGLM-4-9B-Chat-1Mでは、GDSは512K/640Kでstaging
bufferによるOOMに失敗したが、Tuttiは640Kまで完走しTTFT
1.2秒を報告する。LooGLE 0.5 QPSのコストはLMCache-GDSより約27%低い。

## 既存研究との差

LMCache-SSDは標準非同期I/O、LMCache-GDSはデータ転送でCPU bounce
bufferを避けるが、I/O control pathにはCPU処理が残る。TuttiはGPU側object
abstractionとGPU
io_uringでcommand発行までGPUへ移し、さらにI/Oカーネル自身が推論を邪魔しないよう層別slack
schedulerを組み合わせる。

## 限界

remote replica取得は現状CPU host
memoryを経由してRDMAするため、ノード間経路は完全GPU駆動ではない。slack
tableはモデル・system構成ごとのoffline
profilingを要する。極端にprefix再利用率が高く計算がほぼ残らない条件ではI/Oを隠すslackが消え、DRAMより遅くなる。評価はH100と特定enterprise
NVMe中心である。
