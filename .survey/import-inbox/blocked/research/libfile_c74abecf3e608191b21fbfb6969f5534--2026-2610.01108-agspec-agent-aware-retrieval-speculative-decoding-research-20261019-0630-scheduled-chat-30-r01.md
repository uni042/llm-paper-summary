# AgSpec：コードエージェントの作業履歴と役割に合わせる検索型投機的復号

## 概要

コード修正エージェントは、同じファイルを繰り返し読み、以前の修正案を手直しし、実行ログや差分パッチを何度も出力する。この性質は、既に存在する文字列から次の候補トークンをコピーし、対象モデルにまとめて検証させる検索型投機的復号（retrieval-based speculative decoding）に向く。しかし既存方式は、現在のモデル呼出しの入力だけを検索したり、固定のコード集合だけを検索したりするため、前の試行や閲覧したリポジトリファイルを十分に利用できない。さらに、ファイルを読んだ形と差分パッチとして書く形が異なると、同じコードでもトークン列が一致せず検索に失敗する。

AgSpecは検索器そのものを変更せず、検索対象の構成と候補長の制御を変更する。セッション履歴、閲覧した作業ファイル、事前構築した参照集合を分離して保持し、ファイルは差分パッチの行頭記号を付けた形でも索引化する。検索された続きの長さをそのまま投機長とせず、役割ごとの過去の受理長から上限を設定し、直近の対象モデルによる検証結果で長さの倍率を更新する。

著者はvLLM上の二種類の検索器にAgSpecを組み込み、SWE-bench VerifiedとTeamBenchで評価した。自己回帰生成と比較した生成処理量は、バッチサイズ1で2.27〜4.37倍、バッチサイズ16で1.08〜4.76倍で、比較した従来方式の最速値に対する平均改善は18.0%だった。ただし測定対象は**入力処理を除く生成段階の処理量**であり、リポジトリ修正タスク全体の終了時間が同倍率で短縮することを意味しない。

## 問題設定：検索できる文字列と受理される長さ

投機的復号では、安価な候補生成器が次の$K$トークンを予測し、対象モデルがそれらを並列に検証する。候補が連続して受理されれば、その分だけ対象モデルの逐次実行回数を減らせる。検索型では小型の別モデルを実行せず、現在の生成文脈の末尾に一致する文字列を過去のテキストから探し、その後続部分を候補としてコピーする。候補の採用可否は対象モデルが決めるため、標準的な検証規則を守れば検索器は出力の確率分布を変更しない。

ただし「既存文字列が検索対象にあること」と「実際に生成する文字列とトークン単位で一致すること」は別の条件である。例えば、エージェントが`return x`という行をファイルから読んだ後、統一差分（unified diff）形式でその行を出力すると、保持行には先頭の空白、削除行には先頭のマイナス記号が付く。元ファイルだけを索引化すると、差分として出力される行頭トークンが異なるため、長い一致が得られない。ファイル内容が入力長制限で切り落とされた場合も、現在の入力だけを検索する方式ではそのファイルを見つけられない。

また、コードエージェントは一つの質問に複数回のモデル呼出しとツール実行で応える。場所を探す役割、修正コードを書く役割、テストを実行してログを読む役割では、コピーしやすい文字列の種類と長さが異なる。再試行が進むほど過去の修正案が蓄積するため、同じ役割でも何ターン目かによって受理されやすい長さが変わる。固定の候補長は、この違いを無視する。

候補が長すぎると、後半の誤ったトークンまで検証する費用が増える。特に同時実行バッチが大きい場合、検証する候補位置の増加はGPU計算量を押し上げ、受理長が少し伸びても生成処理量が悪化する。したがってAgSpecは、検索できる後続テキストを増やす問題と、検索できた候補を何トークン検証するかという問題を分離して解く。

## 手法

### 1. 三つの検索対象集合

AgSpecはセッション集合$\mathcal S_s$、作業空間集合$\mathcal W_r$、全体参照集合$\mathcal G$を区別する。$\mathcal S_s$は一つの作業セッションにおける入力、ツール出力、生成済みトークンをモデル呼出しやエージェントの境界を越えて保持する。$\mathcal W_r$は、そのセッションで開いたリポジトリファイルを保持する。$\mathcal G$は別の課題から事前に構築した固定の参照文を保持する。

この分離には寿命と安全性上の意味がある。セッション集合と作業空間集合は現在の作業に強く関係するが、セッション終了時に破棄する。一方、全体参照集合は別セッションでも共通であり、内容が現在のリポジトリに関係する保証はない。著者の実装ではセッション集合へ各入力の末尾2,048トークンと生成トークンを追加する。作業空間集合は閲覧されたファイルを追加し、入力からその内容が切り落とされても検索可能な状態を保つ。

各復号ステップで検索器は、現在の文脈末尾と一致する最長の接尾辞を三集合から探し、それぞれの一致長$m_{\mathcal S}$、$m_{\mathcal W}$、$m_{\mathcal G}$を返す。セッションと作業空間では長い一致を優先し、同長ならセッションを選ぶ。全体参照集合を選ぶには、局所集合の最長一致より$\delta$トークン以上長いことを要求する。式では$m_{\mathcal G}>\max(m_{\mathcal S},m_{\mathcal W})+\delta$の場合だけ全体参照集合を使う。実験設定の$\delta$は5である。

この規則は、巨大な全体集合に偶然存在する一致が、現在の作業に関連する局所一致を押しのけることを抑える。各集合内に同じ接尾辞の出現箇所が複数ある場合、全体・セッション集合では続く3トークンの頻度が高い出現群を優先し、同率なら新しい出現を選ぶ。作業空間集合では最初の出現を選ぶ。候補の検索結果は、選ばれた出現の直後のトークン列である。

### 2. 作業ファイルを出力形式で索引化

作業ファイルを最初に開いたとき、AgSpecは元のファイル内容に加え、エージェントが実際に出力する形式へ変換した複製も登録する。統一差分で編集するエージェントなら、各行に空白を付けた版とマイナス記号を付けた版を用意する。元のファイルを検索できる状態も維持するため、差分ではない通常の引用・説明にも対応できる。

ファイル全体をツール呼出しの引数として書き戻すエージェントなら、改行や引用符のエスケープを含め、その呼出しで出力する形の複製を追加する。変換は、エージェントの編集方式が事前に分かっていることを利用する。各モデル呼出しのたびに同じファイルを再索引化するのではなく、セッション中に最初に開いたときに登録する。

この機構の効果は、まだ修正案がセッション履歴に蓄積していない最初のターンで大きい。後のターンでは、過去に出力した差分パッチそのものがセッション集合へ入るため、出力形式での追加索引化の相対的な利点は小さくなる。作業ファイルの索引化は「ファイルの内容を推測する」機構ではなく、既に読んだ実データを出力表現に合わせて検索可能にする処理である。

### 3. 役割別の投機長上限

検索器が長い後続候補を見つけても、その全長を検証することが得とは限らない。AgSpecは、対象モデル$M$とエージェント役割$a$ごとに、過去の実行軌跡を再生して「検索した候補が何トークン連続して実際の出力と一致したか」という再利用可能長$R$を集める。$k$番目の候補が受理される確率$\Pr(R\ge k\mid M,a)$を推定し、その候補位置を検証する限界費用に見合う確率$\lambda$を超える最大の$k$を上限$K_{max}^{(M,a)}$とする。

式は$K_{max}^{(M,a)}=\max\{k:\Pr(R\ge k\mid M,a)\ge\lambda\}$である。例えば11番目の候補が12%の確率で受理され、12番目は9%、限界費用に対応する損益分岐確率が10%なら、11トークンまでを検証する方が得である。ここで$\lambda$は固定の普遍定数ではなく、対象モデルの1ステップ時間、候補位置を一つ増やしたときの検証費用、平均受理数を使った事前の費用測定から求める。

この上限は役割固有の安定した違いを捉える。例えば、ファイルの場所を短く報告する役割と、長い既存コードを差分として出力する役割では、最適な上限が違う。上限を設定するだけではセッション内の変動に追いつけないため、次のオンライン調整を組み合わせる。

### 4. 検証結果からのオンライン長さ調整

復号ステップ$i$での一致長を$m_i$、現在の役割$a_i$の倍率を$\alpha^{(a_i)}$とし、候補長を$K_i=clip(round(\alpha^{(a_i)}m_i),1,K_{max}^{(M,a_i)})$で決める。検索で実際に後続トークンが$\ell_i$個しかない場合は、$D_i=\min(K_i,\ell_i)$個だけを提示する。既存の検索器自身がさらに厳しい候補長制御を持つ場合は、その上限も尊重する。

対象モデルが連続して受理した候補トークン数を$A_i$とすると、AgSpecは$\alpha^{(a_i)}\leftarrow\alpha^{(a_i)}+\eta(\tau-\mathbf 1[A_i<D_i])$で倍率を更新する。$\mathbf 1$は、候補を最後まで受理できなかった場合に1となる指示関数である。全受理が続くと倍率が増え、途中棄却が続くと倍率が減る。これにより、受理できる候補長がターンごとに変わることへ追随する。

著者はこの更新を、正規化された受理可能長の分位点を追う確率的な更新として解釈する。初期倍率は1.0、更新幅$\eta=0.5$、倍率の範囲は0.05〜12.0である。上限で打ち切られた候補が全受理された場合は、実際にもっと長く受理できたか不明なため更新しない。倍率はサーバー起動時に初期化し、その後はセッションを越えて持続する。したがって役割の統計がサーバー全体の利用傾向を反映する点は、セッションごとに破棄する検索対象集合と異なる。

### 5. 一回のコード修正セッションでの流れ

ユーザーがリポジトリの不具合修正を依頼すると、場所を探すエージェントがファイルを開く。AgSpecはそのファイルの元の内容と、差分形式で出力する場合の変換済み内容を作業空間集合へ追加する。次の修正役が以前に読んだコード行をパッチとして出力し始めると、検索器は差分形式の文字列から続きの候補を取得できる。対象モデルが候補を検証し、受理した分だけ出力が進む。

修正が失敗してテストログが戻ってきた場合、そのログと以前の修正案はセッション集合へ残る。再試行の修正役は、最初の呼出しの入力長から既に消えた古い試行内容も検索できる。候補が受理されやすいターンでは倍率が伸び、検証失敗が多いターンでは短くなる。これらは既存の接尾辞オートマトンや接尾辞木の検索アルゴリズムを置き換えず、検索対象と候補長制御を周辺から改善する。

## 主要結果

### 1. 生成処理量と受理長

| 比較条件 | 結果 | 読み方 |
|---|---|---|
| 主評価2種、3モデル、バッチ1 | 自己回帰比2.27〜4.37倍 | 最小・最大は評価設定間の幅 |
| 同じ主評価、バッチ16 | 自己回帰比1.08〜4.76倍 | バッチが大きくても常に4倍以上ではない |
| 主評価全体 | 最速の従来方式より平均18.0%高い処理量 | 最高または次点の処理量を全設定で達成 |
| SAM-Decodingへの追加 | 処理量平均+64.6%、受理長は約2倍 | 元の検索器は呼出しを越える履歴を十分使わない |
| SuffixDecodingへの追加 | 処理量平均+16.5%、受理長+18.5% | 元の検索器が既に履歴と可変候補長を持つため追加利得は小さい |
| SWE-bench・Gemma3-27B・バッチ16 | SAM系の自己回帰比2.72倍→3.61倍 | AgSpecの周辺方針で既存検索器の効率を改善 |
| LiveCodeBench・バッチ1 | 自己回帰比4.87〜7.94倍 | リポジトリなしでもセッション履歴を使える |
| Terminal-Bench・バッチ1 | 最速従来方式比+9.3〜27.2% | 明示的な複数エージェントがなくても有効 |

生成処理量は、モデルがトークンを生成する部分に限定している。ツールの実行、テスト、ファイル操作、エージェント間の待ち時間は別に存在する。受理長（AL）が長いほど対象モデルの逐次呼出しを減らしやすいが、候補を長くしすぎると棄却トークンの検証費用が増えるため、受理長だけを最大化すれば最速になるわけではない。

### 2. 検索対象を増やす効果

| 構成要素 | 観測結果 | 因果的な解釈 |
|---|---|---|
| 現在呼出しの検索対象をセッション全体へ拡張 | 受理長1.6〜2.1倍 | 前の試行・ツール出力を再利用できる |
| 作業空間集合を単独追加 | 受理長+26〜47% | ファイルが入力から消えても検索可能 |
| セッション集合に作業空間集合を追加 | 受理長+2.2〜7.0% | セッション履歴で覆えない未出力コードを補完 |
| 三集合の合計 | 全体参照集合のみの受理長の2.9〜4.8倍 | 検索可能な文脈の拡大が大きい |
| ファイルを差分形式でも索引化、初回ターン | 修正役の受理長+13〜39% | 元ファイルとパッチの行頭トークン差を解消 |
| 同じ変換、5ターン目 | 追加利得は3%以下 | 過去のパッチがセッション集合へ蓄積する |
| セッション集合を各呼出しに限定 | 受理長−39.3〜51.4% | 呼出しを越えた履歴の保持が本質的 |
| セッション集合を役割ごとに分割 | 受理長−1.4〜2.3% | 他役割の出力も再利用価値がある |

これらの検索対象の除去実験は、主に既存の実行軌跡を再生する方式で得た受理長である。実際のGPU生成処理量の増分と同一視しない。全体参照集合の優先度を下げる閾値$\delta$を0、2、5、8、12と変えても一致率は比較的安定しており、著者設定の5が唯一の最適値というわけではない。3モデルでは2が最も高い一致率を示した。

### 3. 候補長制御と棄却費用

| 条件 | 固定候補長 | AgSpecの動的制御 | 結果 |
|---|---|---|---|
| Devstral・SWE-bench、バッチ1 | 32は8より14%高速 | 8より25%高速 | 候補を長くする効果があるが無制限には不要 |
| 同条件、バッチ16 | 32は8より30%低速 | 8より16%高速 | 大きなバッチでは棄却候補が負担になる |
| バッチ1の受理長 | 固定32で6.0 | AgSpecで5.5 | 受理長が少し短くても処理量は高い |
| バッチ16の受理長 | 固定32で10.3 | AgSpecで10.4 | 同程度の受理長でも棄却数が違う |
| 1ステップの棄却候補数 | 固定32で11〜26 | AgSpecで最大6 | 余分な検証計算を減らす |
| SAM系・バッチ16 | 元方式の棄却率 | AgSpecで12.0〜39.8ポイント低下 | 投機を控えるのではなく候補を適正長へ調整 |

固定32とAgSpecの比較では、AgSpecは固定32が受理するトークンの83〜89%を維持しながら、棄却する候補を大きく減らした。ターンが進むにつれて、投機長は序盤の約10トークンから5ターン目の約21トークンへ増えた。セッション履歴が蓄積するほど検索候補が有用になることと、オンライン制御がその変化へ追随することを示す。

## 既存研究との差

PLDは現在の入力に対するn-gram一致を用いる。RESTは固定の外部参照集合から候補を取得する。SAM-Decodingは接尾辞オートマトンを用い、SuffixDecodingは接尾辞木で長い一致を探す。FastCoderはプロジェクト内のデータや検証済み候補を追加するが、AgSpecはさらに「セッションを越えない履歴」「閲覧した作業ファイル」「差分としての出力形式」を区別し、候補長を役割と検証結果に合わせて調整する。

EAGLE-3は別の学習済み候補生成器を用いる投機的復号方式であり、AgSpecは検索だけで候補を作るため追加の下書きモデルを必要としない。反面、検索対象に有用な文字列が存在しない場合は長い候補を生成できない。コードやログの反復が多い条件で特に有効な方式であり、自然言語の自由な創作や未知の内容の生成へ同じ倍率を一般化できない。

AgSpecの二つの貢献は独立した周辺方針として設計されている。検索対象の拡大は「候補が見つからない」という問題を減らし、投機長制御は「見つかった候補を検証しすぎる」という問題を減らす。既存の検索器を置き換えないため、接尾辞オートマトンと接尾辞木の両方で同じ方針を使える点が実装上の利点である。

## 限界・注意点

第一に、評価はコードエージェントの生成処理量であり、最終的なコード修正成功率、テストの実行時間、ファイル入出力、エージェント間の調整時間を含む全体の高速化ではない。主評価は各ベンチマーク30課題であり、巨大な実運用リポジトリ、数百ターンの長期セッション、分散サーバーでの検索索引の同期について同じ利得を示したわけではない。

第二に、セッション集合と作業空間集合はメモリを消費し、ファイルの出力形式別複製は索引構築費用を増やす。著者は固定の参照集合を事前に作成し、作業空間集合をセッション内で増やす方式を評価した。大量のファイルを開く環境での索引容量・構築遅延や複数セッション間での共有を無制限に拡大できると考えるべきではない。

第三に、役割別上限の事前測定はモデル・役割・バッチ条件に依存する。モデルやエージェントの編集形式が変わると、候補の一致長と検証費用の関係も変わり得る。オンライン倍率はセッションを越えて持続するため、異なる利用者や課題分布が交互に到来する場合は、共有した倍率の適応が新しい分布に追いつくか検証が必要である。

第四に、差分パッチ形式の複製は編集方式を事前に知っていることを前提とする。独自のツール引数形式や構造化編集形式では、適切な変換器を追加しなければならない。検索候補がない場合や短い一致しかない場合は、対象モデルの通常生成に戻り、検索型投機の利得は小さい。

第五に、実験はRTX PRO 6000 Blackwell 96GBの単一GPU、vLLM 0.17.1、貪欲復号、指定の量子化済みモデルである。大きなバッチでの検証費用が結論を左右するため、異なるGPUやモデルの検証カーネル、温度付き標本抽出では損益分岐値を再測定する必要がある。公式コード公開URLは原著中で確認できず、vLLM上流にAgSpecが標準搭載されたという意味ではない。
