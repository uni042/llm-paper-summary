# Minstrel：エッジSLMの入力長・生成長に応じたprefill/decode最適化の選択

## 概要

Minstrelは、小型言語モデル（SLM）のエッジ推論を最適化するとき、データセンター向けLLMで有効だった高速化がそのまま最適とは限らないという問題を扱う。一般的なLLM推論の改善策にはprefillの並列処理を速くするものと、逐次decodeを速くするものがある。しかし、スマートフォンやデスクトップ上のエージェントでは、短い追加プロンプトを繰り返し送り、比較的長い構造化応答を生成する場合がある。共通のKVキャッシュを再利用するなら、実際に新しくprefillするトークン数は元の会話全体より小さい。

本研究は、プロンプト長lpと生成長ldを入力とする実機較正済みの遅延予測モデルを作り、各アプリケーションでprefillとdecodeのどちらを改善すると全体レイテンシをより大きく削減できるかを評価する。プロファイル対象は5種類の1〜3B級SLMと、RTX 3070搭載デスクトップおよびJetson Orin AGXである。推論実行にはllama.cppを使用し、短い入力長の範囲でprefillとdecodeの線形モデルを学習する。

主な発見は、短い生成ではprefillの高速化が効きやすい一方、生成が長くなるとdecodeの反復時間が全体を支配することである。著者は前者をP-Zone、後者をD-Zoneと呼び、アプリケーションの入力・出力長の分布に基づいて最適化の優先順位を決める。ただし本文の速度向上曲線は「各フェーズの時間を仮に50%削減した場合」の予測であり、特定のprefill最適化器やdecode最適化器を実装して実測した改善倍率ではない。

## 問題設定

prefillは入力トークンをまとめて処理し、KVキャッシュと最初の出力トークンを作る段階である。decodeは過去のKV状態を参照しながら一トークンずつ次の出力を生成する段階で、生成長が伸びるほど繰り返しが増える。大きなデータセンター向けモデルでは、長文入力や高並列バッチを前提にした最適化が有効だが、エッジのSLMはアプリケーションの種類、入力の短さ、生成の長さ、再利用可能な共通プレフィックスによって負荷が変わる。

著者は、従来のエッジ異種アクセラレータ研究が長いプロンプトと1〜2トークン程度の短い出力でprefillの利得を強調する一方、実際のエージェントの生成長分布を十分に扱わないことを問題視する。例えば短い命令からJSONやツール引数を数十〜数百トークン生成する場合、prefillが多少速くなっても、全体時間の大半はdecodeに残る可能性がある。共通プロンプトをキャッシュするアプリケーションならなおさらである。

本研究は特定のアプリケーションの品質やエネルギーを最適化するのではなく、あるモデル・ハードウェアの組合せで、指定された入力長と出力長に対して遅延を予測し、仮定したフェーズ高速化の投資効率を比較する。モデルのアーキテクチャ変更や専用NPUカーネルの実装を直接提案するものではない。

## 手法

### 1. 実測値からprefillとdecodeの遅延式を学習する

Minstrelの入力は、モデルとハードウェアの組合せ、実効プロンプト長lp、期待する生成長ldである。prefillの遅延を t_pp(lp)=θ0 lp+θ1、decodeの遅延を t_d(lp,ld)=θ2 lp+θ3 ld+θ4 とする。エンドツーエンドの推定遅延は二つの和である。係数θ0〜θ4は対象モデルを実機で実行したプロファイルから、平均二乗誤差を最小化する線形回帰で求める。

prefill式がldに依存しないのは、prefillは最初の出力トークンを生成した時点で終わるからである。decode式にlpが残るのは、decode中に参照するKVキャッシュの長さが初期プロンプト長にも依存するためである。これらの式は計算量の厳密な理論式ではなく、著者が想定する短い入力のSLMワークロードに対して実機で較正する近似である。

一つのモデルを別のハードウェアへ移す場合、係数を使い回すのではなく再度プロファイルする。デスクトップとJetsonでは同じ入力・生成長でも傾きが異なり、生成が長いほど両者の遅延差が広がることが図4に示される。性能予測をモデルだけの属性にせず、ハードウェアとの組合せとして保持する点が重要である。

### 2. KV再利用後の実効プロンプト長を使う

Minstrelは入力長を、アプリケーションが本当に新規prefillするトークン数として扱うことを想定する。共通のsystem promptや過去の会話文脈をKVキャッシュから再利用できるなら、その部分を毎回処理する前提で入力長を設定してはいけない。たとえば長い固定指示を含むアプリケーションでも、二回目以降は短い差分だけを処理するなら、prefill高速化の効果は初回より小さくなる。

この実効長の考え方により、エッジのエージェントのような繰り返しタスクと、一回だけ長文を投入する文書要約タスクを区別できる。前者はD-Zoneへ入りやすく、後者はP-Zoneへ入りやすい。ただしMinstrel自身が共有KVを検出・管理・圧縮するわけではない。KV再利用が成立するか、どの程度の入力が再計算されるかは外部アプリケーションとランタイムの前提である。

### 3. レイテンシ制約への適合を判定する

学習した推定エンドツーエンド時間がアプリケーションの許容遅延t_lim以下なら適合、超えるなら不適合とする。これにより、特定のモデルとエッジ機器が「この長さのプロンプトから、この長さの回答を、何秒以内に返せるか」を事前に見積もる。たとえば許容5秒なら、入力長と生成長の二次元平面上で実行可能な領域を推定できる。

この判定は期待値に基づくものであり、確率的な最悪遅延やtail latencyの保証ではない。アプリケーションの生成長がばらつくなら、平均だけでなく長めの生成長を入力して余裕を見込む必要がある。モデルの正答率やタスク成功率を評価するものでもない。

### 4. 仮定したフェーズ短縮率から全体利得を計算する

prefill時間を倍率opt_pp、decode時間をopt_dで短縮できると仮定し、改善後の時間をopt_pp×t_pp + opt_d×t_d とする。元の推定時間を改善後の時間で割った値が予測高速化倍率である。著者は片方だけを最適化する場合を取り上げ、prefillだけを半分にした場合とdecodeだけを半分にした場合を比較する。

重要なのは、opt_pp=0.5は「prefillを2倍高速にする技術を実装した」という意味ではないことだ。あくまで同じ予測モデルに二つの仮想的な改善を適用し、どちらに投資する価値が大きいかを診断する。二つの候補のうち全体高速化倍率が大きい側を選び、その選択領域をP-ZoneまたはD-Zoneとして表示する。

## 評価条件

| 項目 | 原著の設定 |

| デスクトップ | Intel i9-10900 CPU + NVIDIA RTX 3070 GPU |

| 推論ランタイム | llama.cpp |

| 出力長 | 0〜256、512、1024トークンを含む複数条件 |

| 最適化感度分析 | prefillのみ0.5倍、decodeのみ0.5倍を比較 |
| 主指標 | prefill/decode/総レイテンシ、仮定上の全体高速化倍率 |

図4は、短いプロンプト長32で生成長を変えた5モデルの実測値、Llama3Bでプロンプト長を変えた実測・予測、デスクトップとJetsonの比較を含む。図5と図6は、その実測値で較正したモデルから得られる仮想的なフェーズ最適化の効果を示す。実測の遅延と、仮想的な最適化後の高速化予測を区別して解釈する。

## 定量結果

### 1. 実測遅延と線形モデルの対応

図4(a)はプロンプト長32で生成長を増やすと、5モデルの実測遅延がほぼ線形に増えることを示す。図4(b)ではLlama3Bの出力長を10に固定し、入力長1〜1500でprefill側の増加を調べる。図4(c)では入力長700と1400の条件で、生成長を変えた予測と実測を比較する。Jetsonはデスクトップよりdecodeの傾きが大きく、長い出力ほど両機器の遅延差が拡大する。

原著図4(c)の例では、Llama3Bのデスクトップで生成長500の予測約5秒と実測約5秒が近い。一方、Jetsonで生成長500の予測約14秒と実測約13秒には約1秒の差がある。生成長1000ではデスクトップ予測約9秒・実測約9.5秒、Jetson予測約25秒・実測約24秒である。これらは図から読み取る代表値であり、全モデル・全入力長での予測誤差の統計値ではない。

原著図4(b)のプロンプト長別の曲線では、短い入力で定数項の影響が大きく、線形モデルの予測が実測を外す条件もある。たとえばデスクトップの入力長100で予測約0.03秒に対し実測約0.12秒、Jetsonでは予測約0.15秒に対し実測約0.28秒という値が図の表現から読み取れる。したがって線形近似は全領域で高精度とは限らず、特に短い入力では固定オーバーヘッドの較正が重要になる。

### 2. prefillだけを改善した場合の限界

図5(a)はLlama3.2-1Bについて、prefillを半分にできると仮定したときの全体高速化を、生成長を変えながら示す。生成が短い場合には改善が見えるが、生成が100トークン以上へ伸びると、調べた入力長の多くでprefill最適化の効果が急速に薄れる。入力長が長いほどprefill改善の余地は増えるものの、生成長が大きければdecodeが全体時間を支配する。

図5の結果はモデルの実測処理時間の比率から生じるもので、prefill最適化が技術的に不可能であるという意味ではない。たとえprefillが大幅に速くなっても、残ったdecode時間が大きければエンドツーエンドの利得が小さいというAmdahl則に近い性質を示している。入力長と生成長の両方を見ずにprefill専用アクセラレータへ投資する危険性がある。

### 3. decodeだけを改善した場合の利得

図5(b)ではdecode時間を半分にする仮定を置く。短い入力では生成が比較的短くてもdecode最適化が有利になり、長い入力でも生成が100トークン以上になるとdecode側の利得が大きくなる。図5(c)は二つの仮定のうち大きな高速化を選ぶことで、短い生成ではP-Zone、長い生成ではD-Zoneが現れることを示す。

図5(d)〜(h)ではGemma、Phi、Qwen、Llama3B、Llama1Bに同じ比較を適用する。モデルによって境界は変わるが、生成長が増すにつれてprefill改善の利得が頭打ちになり、decode改善が優勢になるという傾向は共通する。著者は図5の例で概ね100トークン前後を切替の目安として述べるが、これは特定のモデル・機器・仮定した50%短縮率の条件であり、全SLMに共通の閾値ではない。

### 4. 最適化対象を選ぶための感度分析

Minstrelは一つの固定モデル・機器を選ぶだけでなく、許容遅延やアプリケーションの入力長・出力長の分布に対して、どちらのフェーズを改善すれば最も大きな利得が得られるかを計算できる。例えば共通プロンプトのKVが再利用され、実効入力長が短くなるエージェントでは、P-ZoneからD-Zoneへ移ることがある。逆に長い文書を毎回一から読み、短いラベルだけを返す用途ならP-Zoneに入りやすい。

これらの予測は最適化手法の選択を助けるが、実際のカーネル最適化が同じ50%短縮を達成するか、消費電力や精度を維持できるかは別問題である。モデルの推定時間と実装可能な最適化率を混同してはいけない。

## 既存研究との差

SplitwiseやHeteroLLM、llm.npuなどは、prefillとdecodeの計算特性に応じて異種ハードウェアへ処理を分配する。Minstrelはその前段階として、対象アプリケーションの入力長・生成長を考慮すると、そもそもどちらのフェーズの改善を優先すべきかを診断する。長い入力・短い出力のベンチマークだけで得た知見を、短い追加プロンプト・長い出力のエッジエージェントへそのまま当てはめないという点が特徴である。

LLMCompassなどのRooflineベースの分析はハードウェアとモデルの性能を理論的に説明するが、Minstrelは実機から得た係数を使ってアプリケーションの入力長と生成長の二次元空間へ予測を展開する。特定のハードウェアの理論ピークだけでなく、実測から得たprefill/decodeの傾きを用いるため、アプリケーション単位のレイテンシ制約を扱いやすい。

本研究の寄与は新しい推論カーネルの高速化やKVキャッシュ管理ではなく、性能測定結果を利用して最適化優先度を決めるモデルである。サーベイでは、エッジSLMの性能モデリング、ワークロード依存の最適化選択、prefill/decode分離の設計判断に関連する研究として位置付けられる。

## 限界と再現上の注意

第一に、線形モデルは短い入力でフィードフォワード処理が主導的という前提に依存する。入力が非常に長くなると注意計算の二乗項が無視できなくなり、モデルの予測は崩れる。実験のプロンプト長は主として1〜1500トークンであり、128Kなどの長文入力へ外挿してはならない。著者自身も長いプロンプトでは線形モデルが注意の二乗スケーリングを捉えないと述べる。

第二に、評価したハードウェアはRTX 3070デスクトップとJetson Orin AGXの二つであり、スマートフォンのNPUや新世代のGPU、CPU専用構成への一般化は未検証である。実行ランタイムはllama.cppで、カーネル、量子化設定、スレッド、GPUオフロードの違いが係数を変える。別環境での利用には再プロファイルが必要である。

第三に、速度向上の分析はprefillまたはdecodeを仮に半分へ短縮した場合の予測であり、実装済みの高速化結果ではない。推論精度や応答品質も最適化の評価対象ではない。どの方式が現実に50%短縮できるか、必要な追加メモリや開発費用は評価されていない。

第四に、MinstrelはTransformerブロック内の各フェーズの時間を係数として扱う。投機的復号のように別の草稿モデルを追加する方式、複雑なバッチスケジューリング、通信・CPU処理の重複などは単純な係数で表現しにくい。著者は投機的復号について上限・下限の見積りには利用可能と述べるが、具体的なドラフトモデルの受理率や追加費用を測るものではない。

第五に、エッジではエネルギーと熱制約が重要だが、現行のMinstrelはエネルギーを予測しない。長時間連続推論によるサーマルスロットリング、電池消費、推論のtail latencyも主要な検証対象ではない。アプリケーションに組み込む場合は、実機の熱・電力・応答長分布を別途計測すべきである。

第六に、KVキャッシュの共有によって実効プロンプト長が短くなるという仮定は、アプリケーションとランタイムが実際に共有プレフィックスを再利用できる場合に限られる。プロンプトが少しでも異なる、キャッシュが追い出される、モデルが切り替わるといった場合には再prefillが必要となるため、P-Zone/D-Zoneの境界が変わる。従って実際のキャッシュ命中率を測らずに短い実効入力長を仮定してはいけない。
