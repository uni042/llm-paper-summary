# Strata: Hierarchical Context Caching for Long Context Language Model Serving

## 概要
長文脈LLMでは、再利用可能な接頭辞や文書のKVキャッシュを保持すれば事前充填（prefill）の再計算を避けられるが、GPU HBMだけでは容量が足りない。論文の例では40GB HBMでもLlama-8BのKVは約0.3M tokenしか保持できず、CPU DRAMやSSDなど下位階層への退避が必要になる。Strataは、この階層化後に新たな律速となる「細かく断片化したKVページの転送」と「キャッシュ読込を計算で隠せないバッチ」を対象にする。

既存のPagedAttention系は1～32 token程度の小ページでGPUメモリ断片化とキャッシュ命中率を改善する一方、CPU–GPU転送では1回の転送サイズが小さすぎる。Llama-3.1-8Bの8192 token分KVをpage size 32で読む実験ではPCIe 5.0理論帯域の約22%しか使えず、Grace-Hopperの高帯域リンクでは利用率がさらに約5%まで落ちる。StrataはGPU自身を細粒度I/Oの実行主体にして転送並列度を上げ、メモリ階層間で同一ページ配置を要求しない設計にする。

## 問題設定
単純にページを大きくすれば転送効率は上がるが、キャッシュ照合粒度が粗くなり再利用率が下がる。Mistral-24B/ShareGPTでpage sizeを増やす実験では、平均TTFTが最大2倍、P90 TTFTが最大2.9倍へ悪化した。したがって「GPU側は細粒度ページを保ちたい」と「I/O側は大きな転送を好む」を同時に満たす必要がある。

もう一つの問題は、キャッシュ読込がprefill計算より長い場合である。従来スケジューラはlayer Nの計算中にlayer N+1のKV読込を隠せると仮定するが、長いcached contextと少量のnew tokenの組合せでは成立しない。Strataの最適化I/Oを使っても最大24%のprefill時間がI/O stallになる例があり、CPU–GPU帯域をGPU計算・HBMと同じ第一級資源として扱う必要がある。

## 手法
### GPU支援I/O
Cache Controllerは小さな`cudaMemcpyAsync`をCPUから大量発行する代わりにCUDA kernelを起動する。数千threadがsourceのGPU global memoryまたはregistered pinned CPU memoryから小chunkをregisterへ読み、destinationへstreamする。128 byte程度の粒度から効率化できるため、KVページを大きくせず転送並列度を確保できる。転送kernelに与えるblock数は多すぎるとprefill/decodeとGPU資源を競合するため、I/O帯域と計算干渉の交換条件を測って設定する。

### GPU/CPUレイアウトの分離とHiRadixTree
GPU HBMのPagedAttention向け配置とCPU側の退避配置を同一にせず、Cache Controllerが階層ごとの配置を管理する。SGLangのRadixTreeを拡張したHiRadixTreeはtoken idに加えGPU/CPU上のindexやhit countなどを保持し、要求がどの階層にどれだけ命中するかをSchedulerへ渡す。これによりGPU側の細粒度割当を保ったまま、下位階層では転送に適したデータ配置を選べる。

### キャッシュ認識スケジューリング
要求到着後、Schedulerは進行中batchの実行中に待ち要求のprefill計算量とKV読込量を見積もる。次batchでは、I/O時間を隠せるだけのnew-token計算を組み合わせ、load-boundにならないよう計算と帯域需要を釣り合わせる。読込stallが避けられない場合はdecode batchなど相補的な仕事を挿入してGPUを遊ばせない。

### delay hit対策と実行フロー
同じcontextへの複数要求が、最初のcache miss解決前に同じbatchへ入ると重複prefillが起こる。StrataはHiRadixTreeの状態更新とbatch形成を連携させ、このdelay hitを抑える。prefill完了後はcontinuous batchingでdecode batchへ統合し、Cache Controllerは新規KVを下位階層へ非同期backup/evictする。つまりデータ面のI/Oと制御面のschedulerを分離しつつ、同じcache metadataで接続する。

## 評価条件
|項目|内容|
|---|---|
|実装|SGLangベース、実運用環境にも展開|
|主なGPU|8× NVIDIA H200/NVLink構成を含む|
|ホスト|Intel Sapphire Rapids、1.6TB DRAM|
|モデル例|Qwen2.5-14B、Mistral-24B、Llama-3.1-8B|
|データ|LooGLE、NarrativeQA、ReviewMT、ShareGPT|
|比較|vLLM + LMCache、TensorRT-LLM、SGLang系|
|主要指標|TTFT、throughput、I/O stall、帯域利用率、cache hit rate|

## 主要結果
vLLM + LMCacheとの比較では長文脈workloadのTTFTを最大5倍短縮し、TensorRT-LLMに対して最大3.75倍の高速化を報告する。短文脈では階層I/O最適化が不要な場合でも性能を悪化させないことを設計目標として確認している。

ボトルネック分析では、通常のSGLang offloadでLooGLEを処理するとprefill時間の74%がKV転送待ちとなり、throughputが最大4倍低下する。GPU-assisted I/Oだけで小転送問題を減らしても最大24% stallが残るため、I/O kernelだけでなくschedulerとの協調が必要だという設計根拠になっている。

## 既存研究との差
LMCache等の階層キャッシュは容量拡張を提供するが、Strataは小ページを維持したままGPU-assisted I/Oで転送効率を上げる点と、schedulerがcache load量を明示的に資源需要として扱う点を結合する。CachedAttentionのlayer-wise overlapのように「計算でI/Oを隠せる」ことを前提にせず、隠せないbatchでは別仕事を挿入する。

## 限界
主対象はcached contextが長くprefill比率が高いworkloadである。短いcontext、長いdecode、single-turnなどでは階層KV読込が支配的でない。GPU-assisted I/O kernelは計算kernelとSM等の資源を競合するため、block数を増やせば常に良いわけではない。また評価は特定のGPU/CPU interconnectとSGLang統合に依存し、別アクセラレータやネットワーク越しの遠隔メモリでは再調整が必要になる。
