# MiniPIC: Flexible Position-Independent Caching in <100LOC

## 概要
通常の接頭辞 キャッシュは、過去要求と完全に同じ接頭辞を共有するときだけKVキャッシュを再利用しやすい。検索拡張生成（RAG）やagentic ワークロードでは、同じ文書、コード file、tool descriptionのような再利用可能spanがプロンプト中の異なる位置へ現れるため、内容が同じでもpositionが違うだけで再プリフィルが必要になる。既存の位置非依存キャッシュ（Position-Independent Caching; PIC）はこの問題を解くが、server内部へ大規模な変更を入れるか、KVをserver外へ置いてホスト-to-device転送を発生させる実装が多い。

MiniPICはvLLMの既存KV管理を保ちながら、位置符号化前のKをキャッシュし、注意機構 カーネル内でリクエストごとのlogical positionに基づきRoPEを適用する。さらにブロック-aligned padding、span separator（SSep）、プロンプト depend（PDep）の3 primitiveだけでhashingとブロック-level causal 依存関係を制御し、Block-Attention、EPIC、Prompt Cacheなど異なるPIC方式を同じrunning vLLM instanceで表現する。2WikiMultihopQAではinterleaved スケジューラと組み合わせ、比較対象 vLLM比プリフィル スループット 49%改善、cached spanのtime-to-first-トークンを最大2桁短縮、worst-case オーバーヘッド 5.7%を報告する。

## 問題設定
RoPEを使うTransformerではKへposition-dependentな回転が入る。内容が同じspanでもプロンプト中の開始位置が変わればKが変わるため、通常のKV キャッシュ entryをそのまま別位置へ移せない。RAGで検索文書の順序が変わる、agentが同じtool definitionを別文脈へ挿入する、といっただけでキャッシュ missになる。

PICでは「spanの内容」と「今回の論理位置」を分離する必要がある。同時に、既存vLLMのpaged KV管理、hash-based 接頭辞 キャッシュ、CPU オフロードなどを壊さず実装しなければ、キャッシュ再利用で節約したプリフィルより管理・転送コストが大きくなる。

## 手法
### 位置符号化前KV
MiniPICはKをRoPE適用前の形でKV キャッシュへ保存する。注意機構実行時にキャッシュからK tileを読み出し、そのリクエストが現在spanへ割り当てたlogical positionを使ってカーネル内でRoPEを適用する。これにより同じcontent-derived Kを別の絶対位置へ再利用できる。VはRoPE対象ではないため同様の位置依存変換を必要としない。

### 3つのprimitive
ブロック-aligned paddingは再利用spanをvLLMのキャッシュ ブロック境界へ合わせ、既存ブロック管理とhashを使いやすくする。SSepはspan境界を示してhashing上の独立性を作る。PDepはあるプロンプト部分がどの先行spanへ依存するかを表し、単純接頭辞とは異なるブロック-level causal 注意機構 structureを構成する。これらを組み合わせることで、個別PIC論文ごとに別serverを作らず複数方式を表現できる。

### 既存vLLMとの統合
core engine変更を100行未満へ抑え、重い変更はcustom 注意機構 backend側へ局所化する。KV 状態をserver外へexport/importする方式と異なり、vLLM自身のキャッシュ residencyとCPU オフロード機構を使えるため、再利用のたびにホスト-to-device copyを必須にしない。

## 評価条件・主要結果
| 観点 | 条件・結果 |
|---|---|
| 実装 | vLLM、core変更100 LOC未満 + custom 注意機構 backend |
| 対応 | Block-Attention、EPIC、Prompt Cacheを同一instanceで実現 |
| ワークロード | 2WikiMultihopQAを含む再利用span ワークロード |
| プリフィル スループット | interleaved スケジューラで比較対象 vLLM比+49% |
| TTFT | cached spanで最大2 orders of magnitude短縮 |
| uncached span | linear プリフィル scalingを維持 |
| worst-case オーバーヘッド | 5.7% |

49%はキャッシュ可能spanを含むinterleaved ワークロードでのプリフィル スループット改善であり、全トークンが未キャッシュの場合の純注意機構 カーネル高速化ではない。2桁TTFT短縮もキャッシュ 命中時の効果である。

## 既存研究との差
既存PICは個別方式ごとにserver内部へ専用実装を入れるか、KVを外部キャッシュ serviceへ移して再注入する傾向がある。MiniPICは「unrotated K + logical positions」と3 primitiveを共通基盤にし、複数PIC semanticsを既存vLLM キャッシュ managerの上へ載せる。研究上の新規性だけでなく、実装変更量と既存オフロードとの共存を明示的な設計目標にしている。

## 限界
キャッシュ 命中が少ないワークロードでは位置非依存化の追加処理が純オーバーヘッドとなり、論文でもworst case 5.7%を報告する。再利用単位をブロックへ合わせるpaddingはトークン増加を伴い得る。RoPE適用位置を注意機構 backendで扱うため、対応backend・カーネルへの実装が必要であり、全推論エンジンへ無変更で移植できるわけではない。また利得はspan反復率、span長、プロンプト構造に強く依存する。
