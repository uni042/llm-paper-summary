## 概要

短い系列で学習された大規模言語モデル（LLM）へ学習時よりはるかに長い文脈をそのまま与えると、未知の位置表現と大量の無関係tokenによる注意散漫が問題になる。継続事前学習は高価で、短文脈能力を変化させる可能性もある。一方、滑動窓注意（sliding-window attention）は計算量を抑えられるが、窓外の情報を捨てるため長距離依存を復元できない。

InfLLMは局所窓から追い出されたKVを削除せず、ブロック単位の文脈メモリへ保存する。各stepでは現在queryに関連する少数ブロックだけを検索し、初期token・局所tokenと結合してattentionする。Mistral-7B-Instruct-v0.2では16Kの実効窓で∞-Bench平均57.7を示し、32K sliding-window方式の約21.5〜21.6を大きく上回る。追加学習なしで1,024K tokenまで長距離依存を処理できることも示す。

## 問題設定

全履歴を通常attentionへ入れると計算量とKVメモリが増え、学習時文脈長を超えた位置もモデルにとって分布外になる。逆に古いtokenをすべて捨てれば、後で必要になる情報へアクセスできない。必要なのは「遠い履歴を保持するが、毎step全件は読まない」メモリである。

token単位で全履歴を検索すると、各attention headごとに膨大な検索対象が生じ、関連度計算と非連続メモリアクセスが新しい律速になる。InfLLMは長文の局所的意味一貫性を利用してtokenをブロックへまとめ、検索粒度を粗くする。

## 手法

### 局所窓と文脈メモリ

過去KVを初期token、局所token、両者の間にあるevicted tokenへ分ける。初期tokenはsystem prompt等を保持するため常駐し、直近の局所tokenは通常attentionへ残す。窓外へ出たevicted tokenだけを文脈メモリへ移す。

各計算stepでは、初期token、検索で選んだ文脈メモリ、局所tokenを連結して現在のKV cacheを構成する。検索が空ならStreamingLLM等と同じく遠距離情報を失うため、文脈メモリが長距離依存を補う役割を持つ。

### ブロック単位メモリと代表token

過去KVを既定128 tokenの連続ブロックへ分ける。各ブロックで、局所窓内の後続queryからどれだけattentionを受けたかを表す代表スコアを計算し、上位4 tokenをブロック表現として残す。追加encoderは使わない。

現在queryと各ブロックの代表keyとの内積和を関連度とし、上位メモリ単位だけを読み込む。Mistral設定ではstepごとに96ブロック、Llama-3では32ブロックを選ぶ。token全件検索より比較回数を減らし、選択後のKVも連続ブロックとして読みやすい。

### 位置表現の再利用

検索されたブロックは元系列上では離れた位置にあり、その絶対距離をそのままRoPEへ入れると学習範囲外になる。InfLLMは局所窓より遠いメモリtokenの相対距離を局所窓サイズへ固定し、既知の位置範囲へ写像する。

### CPUオフロードとGPU cache

全メモリ単位はCPUメモリへ置き、代表tokenと現在必要なブロックだけGPUへ保持する。隣接tokenは似たブロックを参照しやすいため、GPU側に最長未使用（Least Recently Used; LRU）cacheを設けて再利用する。論文では100K tokenを26GB VRAMで処理でき、cache miss率も低いと報告する。

## 評価条件

| 項目 | 条件 |
|---|---|
| base model | Mistral-7B-Instruct-v0.2、Llama-3-8B-Instruct |
| 元の最大文脈 | Mistral 32K、Llama-3 8K |
| benchmark | ∞-Bench、LongBench |
| ∞-Bench平均長 | 145.1K token、95 percentile 214K |
| local window | 4K |
| memory block | 128 token、代表token 4 |
| encoding chunk | 512 token |
| acceleration | 全baselineでFlashAttention |
| 最大外挿 | 1,024K token |

## 主要結果

| 条件 | baseline | InfLLM | 読み取れること |
|---|---:|---:|---|
| Mistral / ∞-Bench平均 | StreamingLLM 21.5 | 57.7 | 遠距離memory retrievalが滑動窓の情報欠落を補う |
| Mistral / retrieval KV task | H2O 2.6 | 96.8 | 単純evictionより必要KVの再取得が有効 |
| Llama-3 / ∞-Bench平均 | StreamingLLM 16.3 | 45.0 | 8K学習モデルでも長文脈へ外挿 |
| 100K token | — | 26GB VRAM | CPU memory + GPU cacheで容量を制限 |
| 1,024K token | — | 長距離依存を保持 | 百万token級へtraining-freeに拡張 |

位置補間だけのNTK/SelfExtendは一部retrievalでは高得点だが、モデル・taskにより大きく崩れる。InfLLMは長い系列をstreaming処理しながら、関連ブロックを選択的に復帰させることで、長文脈能力と計算・GPUメモリの両方を扱う。

## 既存研究との差

StreamingLLM/LM-Infiniteは局所窓外を捨てるため遠距離情報を再利用できない。H2O等のKV evictionも不要と判定したtokenを失う。InfLLMは窓外KVをCPU側メモリへ残し、queryごとに必要なブロックを戻す。継続学習型の長文脈拡張と違い、モデルweightを更新しない。

## 限界

CPUオフロードを使うため、GPU cache missが増える分布では転送overheadが増える。代表tokenでブロック関連度を近似するため、代表tokenが捉えない局所情報を含むブロックを取り逃す可能性がある。最大1,024Kまでの能力を示すが、全taskでfull attention相当を保証するものではない。また検索・cache管理を実行系へ統合する必要があり、標準attention kernelだけで完結する方式ではない。
