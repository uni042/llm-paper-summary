# CCQ：コードブックを保存せずに2ビット級のLLM重みを復号する

## 概要

2bit級の重み量子化では、単純な整数丸めでは表現可能な値が少なすぎて精度が大きく落ちる。ベクトル量子化なら複数重みを一つの符号へまとめられるが、推論時に符号から高次元ベクトルを復元するコードブック参照が必要となる。ランダムなメモリアクセスはGPU上で局所性を壊し、量子化で削減した重み転送量の利益を相殺し得る。

CCQ（Convolutional Code Quantization）は、通信路符号化で用いられる畳み込み符号の状態遷移を重みベクトルの符号化へ転用する。隣接する状態のビットが重なることを利用し、複数の量子化重みを少数ビットへ詰める。復号は巨大な表を検索するのではなく、符号のビットシフトとマスク、通常のスケール復元で行う。さらに符号形式を混ぜるHybrid Encoding、符号値の分布を利用するCode Cluster、スケール圧縮を組み合わせ、実効2.06～2.75 bit/weight（bpw）を実現する。

原著Table 2ではDeepSeek-V3-0324の8bit版642GBに対し、CCQ 2.06bpw版は184GBで、GSM8K/C-Eval/MMLU平均が90.01から87.76へ低下する。ERNIE-4.5-300B-A47BではWINT8の281GB・平均89.39に対し、WINT2（CCQ）の89GB・平均87.36となる。**圧縮率は大きいが精度は完全には維持されない**。またカーネル速度は演算種別で異なり、GEMVでは標準WINT2よりCCQが遅い例もあるため、量子化後のモデル容量と実生成速度を混同してはならない。

## 問題設定：低ビット化と復号速度の衝突

通常のスカラー量子化は、重みをグループごとにscale/zero-pointで整数へ写し、INT8/INT4/INT2として保存する。4bitでは精度を維持できても2bitでは四つの量子化値しか持てず、外れ値に範囲を合わせると通常の値を細かく表せない。GPTQは逆Hessian情報を使って丸め誤差を補償し、AWQは重要な重みを保護するが、2bit級では限界がある。

一方、AQLM、QuIP#、VPTQのようなベクトル量子化では、複数重みをまとめて高次元コードブックの一要素へ対応付ける。圧縮後の重みはインデックスとして保存でき、スカラー2bitより高い近似能力を得られる。ただし推論時にインデックスでコードブックを検索すると、GPUメモリの不規則アクセスとデータ依存の復号が生じる。特に大量のMoEエキスパートを同時に処理する際、復号カーネルの非効率が推論速度を支配し得る。

CCQの設計目標は、**複数重みをまとめて圧縮する表現力**と、**スカラー量子化に近い規則的な復号**を両立させることにある。圧縮した符号をビット演算だけで元の整数列へ戻せるなら、コードブックの保存もランダム参照も不要になる。重みの保存形式、符号化時の探索、実行時の復号の三つを一体で設計する点が重要である。

## 手法

### 1. 畳み込み符号の重複状態を利用する

CCQは符号構成を`(L, N, S)`で表す。Lは各状態のビット数、Nは一度に符号化する状態数、Sは隣接状態間で新たに追加する遷移ビット数である。隣接状態は`L-S`ビットを共有するため、N個のLビット値を単純に`L×N`ビットで保存する代わりに、初期状態Lビットと残りN-1回の遷移ビットだけで表せる。

必要な符号長は`T = L + (N-1)S`となる。原著Figure 1の`(L=2,N=3,S=1)`では、3状態の系列を4bitで表せる。`00→01→10`のような遷移が符号として一意に復元できる。符号空間は`2^T`個のN次元整数ベクトルからなるが、**実行時にそのベクトル表を保持する必要はない**。符号のビット位置から各整数を直接取り出せるためである。

たとえば`(L=4,N=3,S=2)`ではT=8となり、3個の4bit整数を8bitで保存できる。生の符号部分だけなら8/3=2.67bpw相当であり、4bitスカラー表現より約33%小さい。ただしこの構造は任意の整数三つを自由に表せるわけではない。状態間のビット重複により候補ベクトルが制限されるため、重みの分布によっては誤差が増える。これを後段のグループ別探索とscale最適化で抑える。

### 2. グループ単位の最小二乗符号探索

元の重み行列Wをグループへ分割し、各グループのscaleを求める。符号構成に従って生成できる候補ベクトルを整数領域で列挙し、scaleを掛けて元の浮動小数点領域へ写す。各N次元重みベクトルvについて、候補C_iとの二乗誤差`||v-C_i||²`が最小となる符号インデックスを選ぶ（原著Algorithm 1）。

この探索は量子化時のオフライン計算である。選ばれたインデックス自体が畳み込み符号のビット列なので、推論時には候補ベクトルを再探索しない。各グループのscaleとzero-pointを使って復号された整数を元の重み値へ戻す。グループ化は外れ値の影響を局所化し、グループ全体を一つのscaleで近似する誤差を抑える。Nで割り切れないグループはゼロ埋めする。

ただしオフライン探索は各ベクトルと候補集合の距離を比較するため、通常の最近傍丸めより計算費用が大きい。著者は推論時の低遅延を優先しており、量子化処理の総所要時間や大規模モデル全体の再量子化運用費用を、推論速度の数字と取り違えてはいけない。

### 3. Hybrid Encoding：符号長を実データ型へ合わせる

単一の符号構成を変えるだけでも2bit台の圧縮率を作れるが、GPUメモリへ格納するには8bit/16bitなどのデータ型に合わせる必要がある。符号長が中途半端なら未使用ビットが増え、理論bpwより実際の保存効率が悪化する。また圧縮率を上げるためNを大きくしすぎると、状態間の相関制約が増えて量子化誤差が大きくなる。

CCQは一つのグループ内で異なる符号構成を混ぜる。原著§3.2では`(3,3,2)`と`(3,4,2)`を組み合わせ、合計7個の整数を16bitに格納する。符号だけなら16/7=2.28bpwとなる。これは単一の長い符号を無理に使う代わりに、短い符号を組み合わせてデータ型の境界に合わせる設計である。

推論時にはそれぞれの符号部分を定められたシフト量で取り出す。通常のベクトル量子化のように各符号が指す別のコードブック行を読む必要はない。ただし構成ごとに異なるシフト・マスクを実装する必要があり、どの形式でも同一のカーネルが最適になるわけではない。

### 4. Code Cluster：符号の分布を利用して2bit級へ

さらに圧縮するには、畳み込み符号の全ビット列をそのまま保存する代わりに、実際に使われる符号値の分布を利用する。原著Figure 3では、出力チャネルごとの符号値が概ね正規分布に近いことを観測する。そこで`(L=6,N=4,S=3)`で符号化した値を、チャネル単位のscaleとzero-pointでUINT8の0～255へ一様量子化する。これにより4個の重みの符号を1バイトへ格納でき、符号本体は2bpwとなる。

一般の非線形クラスタリングを行うと、クラスタIDから代表値を得るためのテーブル検索が再び必要になる。CCQのCode Clusterは符号値を線形なscale/zero-pointで復元するため、UINT8から広い整数領域へ戻した後もビットシフトで各状態を抽出できる。原著Algorithm 3ではまず`round(qw × s_code + zp_code)`で符号を復元し、続いてシフトとマスクで重み整数を得て、最後にグループscaleを掛ける。

Code Clusterは追加の符号量子化を行うため、精度低下の可能性がある。符号値の分布が正規分布から外れるチャネルでは、一様量子化の効率も変わり得る。したがって「コードブックなし」とは追加誤差なしという意味ではなく、**実行時の不規則な参照をなくす**という意味である。

### 5. Scale最適化とscale保存の圧縮

グループごとのscaleを固定したままでは、符号探索後の再構成誤差が残る。原著§3.4では復号済み整数`W_q`に対して、`Σ(W_i-W_qi S)²`を最小化するscaleを解析的に求める。微分をゼロとすると`S = Σ(W_i W_qi) / Σ(W_qi²)`となり、選ばれた符号に合わせてグループのスケールを更新できる。これは重み整数を変えずに再構成誤差を下げる操作である。

多数の小さなグループではscale自体の保存費用が無視できない。CCQは出力チャネル単位のsuper scaleを用いて各グループのscaleを低ビット化する。さらに、64重みを`(4,3,2)`で符号化すると最後の符号に未使用ビットが生じるため、その隙間に量子化scaleを埋め込む。Hybrid Encodingでも同様に余剰ビットを使える。一方Code Clusterでは未使用ビットがなく、scaleを別途ロードする必要がある。

このため**理論符号幅と実効保存bpwは異なる**。原著Table 1では、通常符号2.75bpw、Hybrid Encoding2.5bpw、Code Cluster2.06bpwという実効値を示す。2.28bpwや2.00bpwは符号本体だけを見た値であり、scale等のメタデータを含めたモデル容量を見積もる場合は実効値を使う必要がある。

### 6. GPUでの復号とMoE実行

通常符号・Hybrid Encodingでは、圧縮符号を読み、`(qw >> shift) & mask`で整数値を抽出し、zero-pointとscaleで浮動小数点重みへ戻す。原著Table 1は`(4,3,2)`のshift `[4,2,0]`とmask `0xF`、Hybrid Encodingのshift `[13,11,9,6,4,2,0]`とmask `0x7`を示す。Code Clusterでは符号値の再展開が一段増え、shift `[9,6,3,0]`、mask `0x3F`を使う。

著者はGEMVをTritonカーネルで比較し、MoEのGrouped-GEMMについてはvLLMのwna16演算へCCQを移植する。GEMVは小バッチで重み転送が支配的になりやすく、Grouped-GEMMは多数エキスパートの行列演算をまとめる。復号の追加命令とメモリ転送削減の比率が異なるため、両演算での性能差は一致しない。これが本論文の性能評価を読むうえで最も重要な実装上の境界である。

## 方式別の交換条件

| 方式 | 圧縮の要点 | 推論時の費用 | 主なリスク |
|---|---|---|---|
| GPTQ/AWQ 4bit | スカラー量子化、重み補正 | 規則的な低ビット復号 | 2bitでは精度劣化が大きい |
| VPTQ等のベクトル量子化 | コードブックIDで複数重みを表現 | 不規則なコードブック参照 | GPUのメモリ局所性が悪化 |
| CCQ通常符号 | 状態の重複ビットを保存から除外 | シフト・マスク・scale | 符号候補が制約される |
| CCQ Hybrid Encoding | 異なる符号長を組み合わせて16bit等へ格納 | 複数のシフト設定 | 実装が複雑、scaleの配置が必要 |
| CCQ Code Cluster | 符号値をUINT8へ再量子化 | 符号復元＋シフト＋scale | 追加の量子化誤差、scale別ロード |

## 既存研究との差

QTIPのようなトレリス符号化では、状態遷移を使って重み列を近似するが、符号復元の計算や複雑な変換が推論費用となる。CCQは複数重みを短い状態列として扱い、符号の重複ビットをシフトで復元できる形に限定する。ベクトル量子化の「複数値をまとめて選ぶ」考え方と、スカラー量子化の「規則的な復号」を接続する点が独自性である。

またCode Clusterは一般的なk-meansのように非線形な代表ベクトル表を使わず、符号値の一様量子化でUINT8へ写す。符号の分布を利用するが、復号をテーブル参照へ戻さないことが重要である。Hybrid Encodingとscale圧縮は、理論的な符号長だけでなく実際のバイト境界やscaleメタデータまで含めてモデル容量を減らす設計である。

## 限界・負の結果・再現上の注意

第一に精度は完全には維持されない。DeepSeek-V3の2.06bpwで平均2.25ポイント、ERNIE-4.5の2bitで平均2.03ポイント下がる。特にC-EvalとMMLUで落ち込みが大きい。量子化により重みを小さくできても、複雑な指示追従や知識課題で品質低下が起き得る。

第二に実測カーネル性能の結果は一様ではない。GEMVではCCQは標準WINT2より遅い条件が複数ある。Grouped-GEMMでの利得を、そのまま単一要求の全生成速度へ外挿してはいけない。復号時のscaleロード、Code Clusterの二段階復号、Triton実装の最適化余地が残る。

第三に主評価はDeepSeek-V3-0324とERNIE-4.5-300B-A47Bという巨大MoEである。著者もdenseモデルでの2bit量子化、QTIP/VPTQとの大規模比較を将来課題としている。MoEエキスパートの分布やチャネルごとの符号分布が違うモデルでは、Code Clusterの効率が変わる可能性がある。

第四に量子化はグループごとに候補符号を探索するため、オフライン変換費用が発生する。モデルを頻繁に更新する運用では変換時間・作業メモリも評価すべきだが、論文の主要な性能表は推論時カーネルの計測であり、全モデルの変換時間の比較ではない。

第五に原著§7は、ERNIEの第6 MoE層だけWINT4へ戻すと品質を維持しやすいという観測を示し、層別の動的ビット割当を今後の課題とする。これは重要な負の結果であり、全層を一律2bitにすることが最適とは限らない。既存の学習済みモデルの特定層が量子化誤差に敏感なら、層別に精度を変える設計が必要になる。

第六にH20で89GBの重みを収容できるという結果は、同GPUのKV容量、ランタイム一時領域、同時要求数をすべて含む保証ではない。まして12GBクラスのコンシューマGPUでこのモデルを単独実行できるという意味ではない。単一GPU化の意義は、複数GPUへ重みを分散する際の通信と配置の負担を減らせることにある。
