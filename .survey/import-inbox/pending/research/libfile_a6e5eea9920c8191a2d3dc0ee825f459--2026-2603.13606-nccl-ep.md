# NCCL EP: Towards a Unified Expert Parallel Communication API for NCCL

> MoEのdispatch/combineをNCCL Device APIへ統合し、GPU起動のNVLink/RDMA通信をデコード向けLLとプリフィル向けHTの共通APIで提供する。

## 概要

混合専門家モデル（Mixture of Experts; MoE）の専門家並列では、各トークンをルータが選んだ専門家GPUへ送るdispatchと、専門家出力を元のトークン順へ集約するcombineが必要になる。通常のAllToAllと違い、宛先と通信量がforwardごとに変わり、人気専門家へ負荷が偏るため、均一な集合通信では効率が悪い。このためDeepEP等はGPU起動通信を独自実装してきたが、NCCLとは別の通信スタック・APIを必要とする。

NCCL EPは、NCCL 2.28以降のDevice APIを基盤に、`ncclEpDispatch` と `ncclEpCombine` をNCCL内の専門家並列APIとして提供する。デコードの小バッチ向け低遅延（Low-Latency; LL）モードはNVLinkとRDMAを直接使う全対全経路、高スループット（High-Throughput; HT）モードはノード内NVLinkで集約してからノード間RDMAへ送る階層経路を採る。長寿命の通信バッファ・接続はgroup、forwardごとのtop-kルーティング状態はhandleへ分け、動的MoE通信でも初期化費用を償却する。

NVIDIA EOSのH100 80GBクラスタでDeepEPと比較すると、LL dispatchは2〜8ノードで同等以上、1ノードでは約4%遅い。combineは1〜4ノードで5〜12%遅れ、8ノードで収束する。さらにvLLM 0.10へ統合した端から端評価では、NCCL EPはDeepEPより出力スループットが7〜10%低く、トークン間遅延（Inter-Token Latency; ITL）／出力1トークン時間（Time Per Output Token; TPOT）も7〜9%悪い。論文はこの差を隠さず、combine overheadを主要因の一つとして今後の最適化対象にしている。

## 問題設定

MoEでは専門家をGPU間へ分散するため、トークンの隠れ状態を専門家配置先へ送る必要がある。ルーティングは入力依存なので、GPU A→Bへ何トークン送るかは毎forwardで変わる。さらにtop-kルーティングでは一つのトークンを複数専門家へ複製し、combine時には重み付きで戻す。固定サイズを前提とする通常集合通信より、宛先別の可変サイズ・同期・reduceが複雑になる。

DeepEPやpplx-kernelsはこの不規則性へGPU起動通信で対応するが、NVSHMEMやIBGDA等を含む専用スタックになる。NCCL EPの狙いは、NCCLが既に持つトポロジ認識、ネットワークプラグイン、フレームワーク接続を使いながら、MoE特有の細粒度dispatch/combineをDevice APIで実現することにある。

またプリフィルとデコードでは最適通信が違う。デコードは1〜128トークン程度の小バッチで遅延が重要だが、プリフィル／学習は4096トークン以上の大バッチで帯域利用率が重要になる。NCCL EPはこの二条件を別アルゴリズムにしつつ、呼び出し側APIを共通化する。

## 手法

### group / handleによる状態分離

`ncclEpGroup_t` は通信バッファ、接続、アルゴリズム設定など複数forwardで再利用する資源を持つ。対して `ncclEpHandle_t` は、そのforwardのtop-k専門家割当などルーティング状態を保持する。1モデルにつきgroupを作り、各MoE層・forwardでhandleを作成してdispatch→専門家FFN→combineを行う。

この分離により、動的ルーティングのたびにRDMA接続や大きなバッファを作り直さない。combineはhandleに残るrouting stateを使ってdispatchの並べ替えを逆変換し、top-k重みがあれば加重reduceして元トークン順へ戻す。学習ではforwardからbackwardまでhandleを保持し、推論ではcombine後に破棄する。

### GPU起動NVLink / RDMA

同一NVLink domain内ではLoad/Store Accessible（LSA）を使い、GPU kernelが相手GPUメモリへ通常のload/storeでアクセスする。H100ではNVLink双方向900 GB/sが対象になる。ノード間ではGPU-Initiated Networking（GIN）のput/getとsignal/waitを使い、CPU proxy threadをデータ経路から外す。

LL kernelは宛先が同じNVLink domainならNVLink、外ならGIN RDMAを選ぶ。GPU側で通信開始と同期を制御できるため、MoEのトークン単位の不規則な宛先決定をCPUへ戻さず処理できる。NVLinkが無い場合はPCIeへfallbackする。

### LLモード

LLは推論デコード向けで、少数トークンを低遅延に全対全転送する。受信側は専門家majorな3次元配置を使い、受信後そのままgrouped GEMMへ渡しやすくする。dispatch/combineにはsend-onlyとcompleteを分けるstaged executionもあり、送信開始後にGPU資源を解放して他計算と重ねられるAPIを持つ。

通信バッファはDeepEP型の `O(E·B·P)` 配置をそのまま使わない。元方式は各expert×送信rankへ最大batch分のslotを予約するため、多数expertで空きが増える。NCCL EPはheaderへrouting情報を入れ、dispatchを宛先rank単位へまとめてbufferを `O(N·B·P)` へ縮小する。論文はlocal expert数Lに比例する分を削減できるとしている。

### HTモード

HTはプリフィルと学習の大バッチ向けで、まずNVLink domain内でトークンを集約し、その後ノード間RDMAを行う階層通信を使う。出力は受信トークンを連結した2次元配置とし、専門家ごとのtoken countを別tensorで渡す。LLの固定上限bufferより、実際の受信量に応じた大バッチ処理を優先する。

ただし論文v3時点ではHT kernelの性能最適化と評価は継続中で、公開評価の中心はLLである。HTをAPIとして実装していることと、DeepEP等に対するHT性能優位を実証したことは区別する必要がある。

### vLLM / Megatron-LM統合

vLLMでは既存All2All backendへ `nccl_high_throughput` / `nccl_low_latency` として追加され、FusedMoE層のprepareでdispatch、finalizeでcombineを呼ぶ。LL/HTのlayout差は共通buffer wrapperが吸収し、per-expert token countをGEMMへ渡してpadding計算を避ける。

一方、現行vLLM統合の通信streamは正しさを優先した同期実装で、通信は前計算を待ち、計算も通信を待つ。staged API自体は重畳を支援するが、評価版統合が完全に非同期重畳を実現しているわけではない。この実装上の差が端から端性能を読む際の重要な制約である。

## 主要結果

| 条件 | 指標 | NCCL EP | DeepEP | 読み取れること |
|---|---|---:|---:|---|
| LL dispatch、1 node | kernel throughput | 約4%低い | 基準 | 小規模ではまだ優位でない |
| LL dispatch、2〜8 nodes | kernel throughput | 同等以上、8 nodesで明確な優位 | 基準 | GPU起動NCCL経路が大規模dispatchで競争力 |
| LL combine、1〜4 nodes | kernel throughput | 5〜12%低い | 基準 | combineが残る弱点 |
| vLLM、8 GPUs | output throughput | 755.1 tok/s | 811.2 tok/s | 端から端ではDeepEPが約7%高い |
| vLLM、16 GPUs | output throughput | 586.1 tok/s | 634.0 tok/s | scaleしても差が残る |
| vLLM、32 GPUs | output throughput | 563.3 tok/s | 617.0 tok/s | 約9%差 |
| vLLM、32 GPUs | p99 TTFT | 769.1 ms | 809.9 ms | throughputは低いがtail TTFTはこの条件で良い |
| vLLM全scale | ITL/TPOT | DeepEPより7〜9%悪い | 基準 | combine overhead等が実サービス性能へ残る |

カーネル比較には測定方法の差もある。NCCL EPはkernel launchを含むhost-side C API時間、DeepEPはPyTorch KinetoのGPU kernel時間であり、NCCL EP側が不利な計測である。また大規模時はネットワーク競合等で最大5%の変動があると報告される。

## 既存研究との差

DeepEPは専用のdevice-initiated MoE通信ライブラリとして高性能だが、NCCL EPは同種のdispatch/combineをNCCL本体のDevice API上へ持ち込む。これによりNCCLのトポロジ検出とネットワークpluginを利用し、C/Pythonの統一APIからLL/HTを切り替えられる。

通常NCCL集合通信との差は、全rankへ均一量を送るAllToAllをそのまま使わず、top-k routing、可変token数、expert別reduceをhandleに保持する点にある。つまりNCCL EPは「MoEを既存AllToAllで実行する」層ではなく、MoE固有の通信semanticをNCCLへ追加する。

## 限界

最も明確な限界は、端から端のvLLM評価でDeepEPにまだ負けていることである。論文はthroughput 7〜10%、ITL/TPOT 7〜9%の差を認め、LL combine overheadを一因として挙げる。API統合性が高いことと、現時点で最速であることは同義ではない。

HTは実装されMegatron-LMにも統合されているが、v3時点でHT kernel評価・最適化は継続中である。そのためプリフィル／学習向けHTの性能をLL結果から推測してはいけない。

また評価はNVIDIA H100/NVLink/InfiniBandとNCCL Device APIを前提とする。異種GPUや他社acceleratorへそのまま移植できる一般通信抽象ではない。vLLM統合も現状は通信・計算を同期させており、staged APIが持つ重畳可能性を完全には使っていない。
