# On Evaluating Performance of LLM Inference Serving Systems

## 概要

本論文は新しい推論カーネルや要求スケジューラを発明するのではなく、**大規模言語モデル（LLM）の推論サービングシステムを、何と、どの条件で、何の指標によって比較すれば誤解を避けられるか**を検討する評価方法論である。論文の本文HTMLでは題名が「On Evaluating Performance of LLM Inference Systems」と短縮されているが、arXiv書誌上の題名と正規識別子は上記のとおりである。既存の12システムの評価報告を読み、比較の公平性、評価設定、指標の設計という三軸から八種類の評価上の失敗を整理する。さらに投機的復号を題材に、中央値だけでは性能改善と誤認し得る条件を実測で示す。

主要な実験例は、Llama-3 70B、H100 GPU 4台、ShareGPT4要求トレース、到着率0.25要求/秒という条件である。投機的復号の出力トークン当たり時間（TPOT）は中央値で約1.3倍良くなる一方、99パーセンタイルでは約1.16倍悪くなる。受理された候補トークンがまとめて出るため、トークン間隔の約75%がほぼゼロになることも、対話が常に滑らかになる証拠ではない。最初のトークンまでの時間（TTFT）は草案モデルの追加前処理により悪化する。この一組の実験で、平均生成速度・末尾の停滞・初回応答性が異なる方向へ動くことを示している。

本研究の価値は特定方式の新たな高速化倍率ではなく、既存論文の数値を読解するときに、その数値が利用者の実際の待ち時間をどこまで表しているかを判別する点にある。既存方式への評価は公開された資料に基づく著者らの分類であり、12方式すべてを同一装置で再実装・再測定した比較実験ではない。この区別は結論の適用範囲を決める。

## 問題設定

### 一つの要求に性質の異なる処理が混在する

自己回帰LLMへの要求は、到着後の待ち行列・スケジューリング時間 $T_s$、入力を一括処理する事前計算時間 $T_p$、出力トークンを逐次生成する復号時間 $T_d$ に分けられる。入力長 $N_p$ が長いと事前計算の演算負荷が増え、出力長 $N_d$ が長いと鍵・値キャッシュ（KVキャッシュ）を繰り返し読み出す復号時間が増える。計算律速の事前計算と帯域律速になりやすい復号を同じ平均遅延にまとめると、何が改善したのかを特定しにくい。

本論文が区別する主要指標は、TTFT=$T_s+T_p$、最終トークンまでの時間（TTLT）=$T_s+T_p+T_d$、個々の出力トークン間隔（TBT）、平均復号時間TPOT=$T_d/N_d$、正規化された全体遅延=($T_s+T_p+T_d$)/$N_d$、および所定のサービス水準目標（SLO）を満たせる最大要求到着率である。TTFTが低くても生成途中で停止すれば対話体験は悪く、TPOTが低くてもスケジューリング待ちが長ければ利用者は応答開始まで待たされる。論文はこれらを別々に測ることを求める。

### 実際の要求長はサービス間で大きく異なる

論文表1が引用する公開運用トレースでは、Azure Code 2024の入力中央値は1,928トークン、出力中央値は8トークンである。一方Azure Conv 2024は入力928、出力41、Mooncakeは入力6,345、出力30である。入力長の99パーセンタイルもそれぞれ7,685、6,683、61,616と異なる。単一の短い対話データだけで最適化を評価すると、長い入力の事前計算やKVメモリ容量が支配的な運用環境へ結果を一般化できない。逆に長文要約で優れた方式が短い対話で最も良いとも限らない。

加えて、符号生成の補助機能なら完成までのTTLTが重要だが、対話ではTTFTとTBTの滑らかさが重要になる。要求到着率を上げたときの遅延分布も変化するため、利用者が許容しない長い待ち時間で初めて出るスループットの最大値を、実用容量と混同すべきではない。

## 手法

### 三軸・八類型による評価監査の設計

本研究の入力は、Orca、vLLM、Sarathi-Serve、DistServe、dLoRA、S-LoRA、L2R、MuxServe、SpotServe、LoongServe、NanoFlow、Splitwiseの公開論文・補足資料と、各論文に記載された比較条件・評価指標である。著者らは各システムについて八つのチェック項目を表2で○／×に整理し、そこから八つの失敗類型を説明する。**八類型は問題を説明する粒度、八項目は個別論文を判定するチェック表の列**であり、同一の件数ではない。付録Aには各方式をどう判定したかの具体的な理由がある。

第一軸の**比較の公平性**では、①実装の差とアルゴリズムの差の混同、②比較対象のパラメータ調整不足を点検する。新方式だけ新しい通信実装や高速カーネルを使っている場合、観測された差をスケジューラの貢献と呼べない。たとえばNanoFlowは全体として1.91倍の処理量改善を報告しているが、構成要素除去実験によって中核の小分け処理の寄与は16%であり、残りの大部分はシステム実装上の最適化に帰属する、と本論文は説明する。これはアルゴリズムの価値がないという意味ではなく、因果的な帰属を分ける必要があるという指摘である。比較対象側のバッチ数や分割事前計算のチャンク長も同程度に調整すべきである。

第二軸の**評価設定**では、③古いモデル構造への偏り、④実運用を代表しない要求分布、⑤実用上の遅延上限を無視した改善を点検する。たとえば通常の多頭注意（MHA）とグループ化問い合わせ注意（GQA）ではKVキャッシュの容量要件が異なる。論文が紹介するDuoAttentionの例では、KV削減倍率がMHAで2.55倍、GQAで1.67倍となる。MHAだけでメモリ最適化を検証すると、新しいモデル構造では効果が縮む可能性を見落とす。LoongServeの長文脈条件で入力トークン当たり正規化遅延が数百ミリ秒という例も、絶対TTFTに換算すると対話用途では実用的でない可能性を示す。

第三軸の**指標設計と解釈**では、⑥目的に対応しない不透明な指標、⑦中央値やP99だけへの集約、⑧トークン数で割る正規化が待ち時間を隠す問題を点検する。要求間で出力長が異なると、総遅延の総和を全出力トークン数で割った値は、実際のどの利用者の待ち時間とも一致しない。TBTの全分布や複数パーセンタイルを併記し、初回待ちと復号途中の停滞を別々に示す必要がある。

### 個別論文の判定を再現可能にする手順

表2の各○／×は「その方式が良いか悪いか」という最終評点ではない。たとえばvLLMについて、Orca・FasterTransformer・vLLMを共通実装基盤で比較した点は実装公平性として肯定する一方、比較対象のバッチ設定や使用モデルの偏り、短い入力中心のトレース、中央値偏重は別項目で問題視する。DistServeについては現実的なTTFT/TPOT制約とSLO達成率を肯定しながら、異なる実装基盤の比較、比較対象の調整情報不足、二番目のトークンの遅れをTPOT平均が隠し得ることを指摘する。

このように、各方式の論文から①比較対象のコードベースと最適化の差、②各設定値の調整、③モデル構造、④入力・出力長の分布、⑤絶対的な遅延上限、⑥何を測る指標か、⑦分布のどの部分を表示したかを抽出し、項目ごとに根拠を付ける。付録Aは判定過程を公開することで、単なる主観的なランキングにならないようにしている。ただし各判定は著者らの解釈を含むため、別条件で再測定した確定順位ではない。

### 投機的復号を使った指標の反例

投機的復号では小さな草案モデルが複数トークンを先読みし、大きな対象モデルがまとめて検証する。複数候補が受理されると短時間で多くのトークンが出るが、検証に失敗すると草案生成と検証の計算を行った後に少数のトークンしか確定しない。したがって平均的な出力トークン当たり時間が短くなっても、トークン間隔は一様に短縮しない。

著者らは同じワークロードについて、TBTの累積分布、TPOTの中央値と末尾、初回応答TTFT、期限内に所定量のトークンを生成できるかを表す流暢性指標（Fluidity Index）を突き合わせる。測定対象の切り替えによって「高速」と「停滞が増えた」が同時に成立することを確認し、単一の正規化値で性能の良し悪しを断定しないというチェックリストの有効性を具体化する。

## 主要結果と解釈

第一に、性能の改善倍率は、同じ実装基盤、同じ程度の設定調整、同じモデル構造・要求負荷を比較した場合に初めて技術的な帰属を論じやすい。論文の表2・付録Aは、著名なサービング方式であってもすべての評価項目を満たしているわけではないことを明示した。これは各方式の研究成果を無効化する主張ではなく、報告された改善を別環境へ移す際に不足情報を点検するための指針である。

第二に、平均TPOTと利用者が感じる生成の滑らかさは一致しない。投機的復号の図3では、多数のほぼゼロ間隔のトークンが中央値を引き下げる一方、検証が失敗する区間で長い停止が残る。P99、TBTの分布、期限達成率を併記することで、平均値では隠れる交換条件が可視化される。

第三に、事前計算と復号の最適化は対象の要求分布によって重要度が変わる。長い入力を処理するMooncake型のトレースと短い出力を返すコード補完型トレースでは、同じTPOT改善がTTLTやSLO達成率へ与える影響は異なる。論文は単一の固定要求長を使うベンチマークを否定するのではなく、目的とする運用領域との対応を示すことを要求している。

## 既存研究との差

vLLM、Orca、Sarathi-Serve、DistServeなどの研究は、各々のスケジューリング、ページ管理、事前計算と復号の分離などを設計・実装し、選んだ指標で性能を測る。本論文はそれらの新たな置換実装ではなく、**異なる研究の評価方法そのものを比較するメタ評価**である。先行方式の実装公平性や負荷分布の記載を横断的に検査し、推論が事前計算と逐次復号の二段階であることに固有の評価の落とし穴を整理する点が寄与である。

特に、スループットと平均遅延の二軸だけでは投機的復号のような不均一な生成を捉えられないことを実験で示す。TBT、TTFT、TPOT、SLO達成容量、流暢性指標を別の目的に対応させて併記するという提案は、単一の「より速い」という主張を監査可能な複数の観測へ分解する。

## 限界

- 12システムの○／×は公開論文と補足資料の読み取りに基づく。すべてを同じ装置・同じ実装・同じ時期のコードで再測定したものではなく、著者らの判断基準や公表情報の充実度が結果に影響する。
- 投機的復号の実験例はLlama-3 70B、H100 4台、ShareGPT4、0.25要求/秒の条件に限られる。別の草案モデル、受理率、GPU構成、出力長、到着率、分散構成で1.3倍・1.16倍という比が維持されるとは主張できない。
- 流暢性指標は生成の期限達成を測るが、ユーザーごとの主観評価や応答内容の正しさを直接測るものではない。速度の評価方法論から生成品質の改善は導けない。
- 本研究は特定の新しいGPUカーネルや推論エンジンを提供しない。測定規範の有用性を示す研究であり、実装へ適用するには対象サービスのSLO、要求トレース、比較対象の設定を別途収集する必要がある。
- 一つの数値に全てを集約する代替指標を提示したわけではない。絶対TTFT、個々のTBT、末尾分布、要求率に対する容量を併記すること自体が、報告と再現実験の負担を増やす。

## 再現・利用のための確認項目

論文の提案を新しいLLMサービング方式の評価へ適用する際は、比較対象のソフトウェア版と最適化の有無、GPU構成とモデルの注意方式、入力・出力長の分布、要求到着率、バッチ形成・事前計算分割の設定、TTFT/TBT/TPOT/TTLTの絶対値と複数パーセンタイル、SLOを満たす最大負荷、生成停止の頻度をそれぞれ明記する。モデル構造がGQAやMoEへ変わるとKV帯域や専門家転送の律速も変わるため、旧モデルで得た改善倍率をそのまま移さない。論文の三軸・八失敗類型を「評価表の検査項目」として使うのが適切である。
