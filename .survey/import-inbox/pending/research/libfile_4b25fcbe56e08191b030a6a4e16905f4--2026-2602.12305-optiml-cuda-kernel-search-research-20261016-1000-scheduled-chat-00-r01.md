# OptiML：CUDAカーネルの生成と実機フィードバック付き探索を統合する

## 概要

OptiMLは、自然言語で記述されたGPU演算または既存のCUDAカーネルを入力として、機能的に正しく、かつ実行速度の速いCUDAプログラムを生成・改善するシステムである。言語モデルに一度コードを書かせるだけでは、コンパイル失敗、スレッド間競合、数値誤差、メモリ転送過多、レジスタ圧迫などが残りやすい。さらに、実機の速度はGPUアーキテクチャと入力形状に依存するため、ソースコードの見た目から高速化の成否を正確に予測することは難しい。

OptiMLは処理を二段階へ分ける。**OptiML-G**は複数のコード生成モデルの内部表現を協調させて初期CUDAコードを作り、**OptiML-X**はコンパイル・機能検証・GPUプロファイリングを伴うモンテカルロ木探索（Monte Carlo Tree Search; MCTS）でそのコードを改良する。既存コードが入力の場合は生成段階を省略し、OptiML-Xだけを適用できる。候補は実測値で比較し、正しさを満たさないものを棄却する。

著者はNVIDIA A100 80GBで5種類の代表的カーネルを測定し、生成と最適化の統合構成が、既存のコード生成モデルや後処理最適化だけの場合より良い成績を示したと報告する。ただし、本論文はCUDA演算の最適化を扱う研究であり、**LLM全体のトークン生成速度や学習スループットを直接測定したものではない**。カーネル単体の改善を、サービング全体の同倍率の高速化と読み替えてはならない。

## 問題設定

GPUカーネル最適化は、単一のパラメータを少しずつ調整する滑らかな最適化ではない。タイル寸法、スレッドブロック構成、共有メモリへのステージング、ロードの合体、ループ展開、ワープ単位の演算などが互いに影響し、ある変換がメモリトラフィックを減らしてもレジスタ数を増やして並列実行率を下げることがある。局所的に遅くなる編集を経由して、次の編集で高速な実装に到達する場合もある。

既存のコード生成モデルは正しさと高速性を同時に保証できず、単純な後処理探索も初期プログラムの構造が悪いと探索しにくい。OptiMLの問題設定は、`自然言語仕様 → 実行可能な初期コード → 検証付き高速化` または `既存CUDAコード → 検証付き高速化` という二つの経路を同じ最適化器で扱うことである。

最適化目的は候補カーネルの実測実行時間 `T(P)` を最小化することだが、制約として機能の正しさとハードウェア上の安全条件を要求する。例えば速くても結果が誤る実装、過大なレジスタ使用で実行資源を枯渇させる実装、極端にメモリ転送量が増える実装は採用しない。

## 手法：OptiML-Gによる初期コード生成

### 複数の凍結専門モデルを選ぶ

自然言語の要求 `D` を受け取ると、凍結した埋め込み器で要求を固定長ベクトル `z` に変換する。軽量なルータ `rθ(z)` が候補のコード生成モデルを評価し、上位K個を有効化する。最高得点のモデルを主担当とし、最終的なコードのトークン生成はそのモデルが行う。

論文の実験で使う専門モデルはQwen2.5-Coder-7B、HPC-CoderV2-6.7B、StarCoder2-7Bである。いずれも既存のモデル重みを凍結して利用し、ルータと表現変換部だけを学習する。単に各モデルに別々のコードを生成させて最良を選ぶ方式とは異なり、途中層で内部表現を交換する点が特徴である。

### 中間層での潜在表現協調

各専門モデルのTransformer層を複数の連続したスタックへ区切り、境界で隠れ状態を共通の潜在次元へ射影する。主担当モデルの表現を問い合わせとし、全有効モデルの表現をキー・値として**交差注意（cross-attention）**を計算する。その結果を主担当モデルの元の次元へ戻して残差加算する。

数式では、モデルmの隠れ状態 `h_m^l` を `z_m^l = FwdProj_m^l(h_m^l)` へ写し、主担当 `m*` が `CrossAttn(z_m*^l, Concat(z_m^l), Concat(z_m^l))` を実行し、`h_m*^l ← h_m*^l + RevProj_m*^l(o_m*^l)` と更新する。これにより複数モデルが学んだ実装方針をトークン列の生成前に共有する。

学習損失は自己回帰言語モデル損失に、ルータのエントロピー、専門モデルの使用均衡、摂動に対するルーティング整合性の正則化を加える。離散的な専門モデル選択の勾配にはGumbel-Softmaxの直通推定器を用いる。基盤モデルを再学習せず、追加部品だけを学習する設計である。

ただし「一回の前向き計算で出力する」という説明は、主担当モデルだけがコードトークンを最終出力するという意味であり、**有効化された全専門モデルの計算が無料になるわけではない**。潜在協調のために複数モデルの層を実行する追加費用がある。OptiML-Gの推論費用と生成されたカーネルの実行時間は区別すべきである。

## 手法：OptiML-Xによる検証付き探索

### 1. カーネル抽出と実行仕様の推定

OptiML-XはCUDAソースから `__global__` 関数を検出し、カーネル単位に最適化する。自然言語の仕様が与えられない既存コードでも動作するよう、引数がポインタかスカラか、型、入出力バッファ形状、典型的な問題サイズなどをコードから推定する。推定結果をもとにGPUバッファを確保し、入力を初期化してカーネルを起動する実行ハーネスを自動生成する。

ここは再現性の弱点にもなる。元のコードだけから推定した実行仕様が実際のAPI契約と違えば、テストで正しく見える実装でも利用者の想定する入力領域では誤動作する可能性がある。論文も実行仕様の推定と検査範囲を分けて扱っている。

### 2. 多段階の正しさ検査

正しさの検査はL0・L1・任意のL2という三段階で行う。**L0**は小規模入力による起動失敗、NaN、明白な形状不一致の検出、**L1**は複数サイズ・乱数種・数値許容誤差を変えた反復試験である。**L2**は演算の意味が十分に推定できる場合だけ、対称性、置換に対する不変性、スケーリング則などの変形関係を確認する。

L2はすべてのカーネルに自動で適用できるものではないため、意味が不明確なら空でもよい。一方、L0/L1を失敗した候補は探索報酬を実質的な負の無限大として扱い、採用対象から除外する。nvccによるコンパイルが失敗した場合は、言語モデルでエラーを解釈して実行ハーネスを修復する。論文の評価では修復回数上限を3とする。

### 3. GPUプロファイリングによる状態の表現

コンパイルと正しさ検査を通過した各候補について、CUDAイベントによる実行時間とNsight Computeのハードウェアカウンタを測定する。指標にはSM、DRAM、テクスチャ経路の理論上限比（SOL）、DRAM転送バイト数、L1セクタ数、実行命令数、活動ワープ数、レジスタ数などを含む。

カーネルの遅さを単なる「時間」という1値に縮約せず、**どの資源が律速になっているか**を言語モデルに伝える。例えばL1セクタ数が大きければアクセスの合体・局所性の改善、命令数が多ければループ展開や索引計算の簡素化、レジスタ圧迫が強ければタイルや一時変数の見直しを提案する。

測定は候補の実行時間とプロファイラを別パスで行う。これはプロファイリング自身が実行時間へ与える干渉を避けるためである。ただし、カウンタは性能の原因を直接証明するものではなく、観測されたボトルネックの代理指標である。

### 4. モンテカルロ木探索で複数段階の編集を探す

各ノードは `(CUDAコード, 実測時間, プロファイル指標)` を持つプログラム状態で、辺は言語モデルが提案した具体的な編集を表す。モンテカルロ木探索では、訪問済みの有望な枝と、まだ試していない枝を上限信頼値（UCT）で釣り合わせる。

子ノードcの選択指標は `UCT(c)=Q(c)/N(c)+α√(ln N(parent)/N(c))` であり、第一項は観測された平均報酬、第二項は探索のための加点である。候補の編集はタイリング、共有メモリへのステージング、ロードのベクトル化、ループ展開、起動設定、ワープ単位演算などから生成する。探索深さは実験では最大6、UCTの探索係数は1.4とする。

貪欲探索と違い、ある編集で一時的に遅くなっても、その状態から次の編集を加えて高速化できる可能性を残す。反面、各候補にコンパイル・テスト・実測が必要であり、探索予算が増えるほど最適化時の計算費用も増加する。

### 5. 実時間と代理指標を組み合わせた報酬

報酬は実行時間の改善を中心とし、ハードウェア指標の改善とLLM審査員による妥当性評価を補助信号として足す。形式は `R=β_time r_time + β_proxy r_proxy + β_llm r_llm - p_guard` である。代理報酬にはSM/DRAM/TEX利用率の改善、DRAMバイト数・L1セクタ数・命令数の減少を使い、改善率はクリップして極端な値の影響を抑える。

律速が演算側かメモリ側かによって代理指標の重みを変える。さらにレジスタ溢れによるローカルメモリ使用、過剰なレジスタ数、ベースライン比で極端に増えたメモリ転送や命令数には罰則を与える。審査員は「この編集が本当に観測した律速を改善しているか」をコードと測定値から判定し、KEEPまたはDISCARDを返す。

重要なのは、審査員の主観的評価だけで正しさを決めないことである。L0/L1に失敗すれば即棄却し、性能の主目的は実測時間に置く。最終出力はKEEP判定を通った候補のうち報酬が高い編集系列を選び、適格な候補がなければ元のカーネルを返す。

## 主要結果：代表カーネルの時間と速度比

表1はGPT-5.1の生成のみ、GPT-5.1生成コードへOptiML-Xを適用した場合、OptiML-G+X統合の場合を比較する。コンパイル失敗のある演算では生成のみの時間が存在しないため、成功した後処理方式を基準にした倍率と区別する。

|---|---:|---:|---:|---|
| 行列積 | 7.20 | 4.62 | 4.40 | 7.20/4.40 ≈ 1.64倍 |
| 3D最大プーリング | CF | 6.09 | 5.62 | 6.09/5.62 ≈ 1.08倍 |
| 多頭自己注意 | CF | 7.90 | 6.85 | 7.90/6.85 ≈ 1.15倍 |
| ReLU | 7.50 | 4.87 | 4.49 | 7.50/4.49 ≈ 1.67倍 |
| カテゴリ交差エントロピー | CF | 6.90 | 6.40 | 6.90/6.40 ≈ 1.08倍 |

上表は論文表1の測定値を転記したもので、異なる演算の時間を足して「LLM全体の速度」にしてはいけない。行列積とReLUでは生成のみから明瞭な改善があり、3D最大プーリングや自己注意などは**生成のみではコンパイルに失敗**するため、後処理で実行可能な候補に到達したこと自体が重要である。

行列積では、GPT-5.1生成のみのSM利用率指標71.26が統合構成81.17へ増加し、L1セクタ数408が282へ、実行命令数419が381へ減少した。自己注意ではGPT-5.1+XのDRAM転送代理指標1117、L1セクタ4213、命令数2094に対し、統合構成は1064、3961、2012である。これらは局所性・融合・命令列の改善と整合的だが、カウンタだけで特定の編集が原因だと証明したわけではない。

### 自然言語からのコード生成成功率

ParEvalでのPass@kは、k個の候補のうち少なくとも1つが正しさの試験を通る確率を表す。OptiML-G単独のPass@1/5/10は**12.17% / 27.08% / 33.33%**、GPT-5.1は10.46% / 24.71% / 32.26%である。Pass@1での差は1.71パーセントポイントであり、1.71倍という意味ではない。

コード生成だけでは全体の成功率が高いとは言えない。例えばOptiML-GのPass@1は約12%にとどまり、正しさ検査を通らないコードが多数存在する。統合パイプラインでの性能向上を、生成モデルがほぼ確実に正しいコードを出すという意味に解釈してはならない。

### 5タスクの正しさと高速化を合わせた評価

5タスクの部分集合で最良k候補を選ぶ評価では、OptiML-G+XのPass@1/5/10が**85% / 100% / 100%**、Speedup@1/5/10が**1.18 / 1.26 / 1.30倍**である。GPT-5.1生成のみではPass@1/5/10が40% / 40% / 40%、速度比は1.00倍。GPT-5.1+Xでは80% / 100% / 100%、速度比1.10 / 1.16 / 1.19倍となる。

ここでのSpeedupは解けたタスクに対する幾何平均であり、演算ごとの基準はGPT-5.1が成功した場合はそのコード、失敗した場合はGPT-5.1+Xである。**ParEvalの生成単体Pass@1=12.17%と、5タスク部分集合の統合Pass@1=85%は母集団も手順も異なる**ため、同一試験で72.83ポイント改善したと述べるのは不適切である。

## 先行研究との差

KernelBenchやParEvalはコード生成の正しさ・速度を評価する基盤である。AutoTriton、Geak、Astraなどは言語モデルと自動探索によるGPUカーネル改善を目指す。OptiMLの特徴は、自然言語からの初期実装生成に潜在空間で協調する複数専門モデルを用い、その後の編集を**コンパイルとテストを通過した実機プロファイル**に基づく探索木へ落とす点である。

単一のモデルによる最適化は、最初のコード構造が悪いと大幅な書き直しを要する。OptiML-Gが最初から改良しやすい実装を作り、OptiML-Xが実機指標を見て編集することで、生成と後処理を別々に行うだけの場合より良い探索初期値を得る。ただし、追加の専門モデル実行と学習・探索費用を払っているため、システム全体の費用対効果はカーネルを何回再利用するかに左右される。

## 限界・失敗例・再現上の注意

**コンパイルとツールチェーン**：CUDA APIの誤用、アーキテクチャ指定の不一致、レジスタ・共有メモリ資源の上限によって候補がコンパイルできない場合がある。LLMによる修復は上限付きであり、全候補の救済を保証しない。

**機能的な正しさ**：L0/L1のランダム試験に合格しても、未試験の入力形状、境界条件、極端な値、競合条件では誤動作する可能性がある。特に浮動小数点演算の順序を変える最適化では、誤差許容範囲を実アプリケーションに合わせて検証する必要がある。L2の変形試験は意味を推定できる演算に限られる。

**性能測定**：プロファイラのカウンタはアーキテクチャや指標定義に依存し、測定ノイズもある。利用率が高いことは必ずしも短時間であることを意味しない。報酬は実時間を主目的とするが、代理指標に過適合した編集が発生する可能性がある。著者はこのためメモリ転送・命令数の異常増加やレジスタ溢れへの罰則を導入している。

**探索費用**：最適化中にはLLM呼び出し、nvcc、GPUテスト、Nsight Compute計測を多数繰り返す。1回しか実行しないカーネルでは、最適化に使った計算資源を回収できない可能性がある。探索木の深さや予算を増やしても、すべてのタスクで同じ高速化が得られるわけではない。

**ハードウェア一般化**：評価はA100 80GBとCUDA 12.6に限定される。RTX 4070 Super、H100、Blackwellなどで同じ編集が最良とは限らない。SM占有率、メモリ階層、共有メモリ容量、コンパイラ最適化が異なるため、別環境では再プロファイリングが必要である。

**推論・学習全体への外挿**：最適化した演算がLLM全体の時間の一部しか占めない場合、Amdahlの法則により全体の改善は限定される。例えば時間の20%を占める演算を1.5倍速くしても、他が不変なら全体は `1/(0.8+0.2/1.5)≈1.071` 倍にとどまる。この例は論文の測定値ではなく、結果を実システムへ適用する際の計算例である。

**コード公開状況**：一次論文には擬似コード、実験設定、専門モデル名、指標の定義があるが、OptiML本体の公式公開リポジトリURLは本文から特定できない。実装の再現可能性をコード公開済みと断定しない。
