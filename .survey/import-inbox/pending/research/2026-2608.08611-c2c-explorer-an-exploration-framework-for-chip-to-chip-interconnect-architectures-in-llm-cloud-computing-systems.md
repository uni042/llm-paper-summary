# C2C-Explorer: An Exploration Framework for Chip-to-Chip Interconnect Architectures in LLM Cloud Computing Systems

> 言語モデルの通信トレースからチップ間トラフィックを作り、512チップまで扱える混成シミュレータで評価し、ベイズ探索で接続構成を絞り込むことで、有効スループットとメモリを同時に改善する構成を短い反復で見つける設計探索の研究。

## 概要

大規模言語モデルが単一チップへ収まらなくなると、複数の処理チップを束ねる構成が前提になり、チップ間通信が性能を支配する。論文の冒頭では、学習では通信が反復時間の90%を超える例、推論でも遅延の50%を超える例が示されている。ところがチップ間接続の設計は難しい。現実の言語モデルらしい通信負荷を作ること、大規模構成をハードウェア水準で正確に模擬すること、指数的に大きい設計空間を効率よく探すことの3つが同時に必要だからである。汎用のネットワークシミュレータは言語モデル特有の集合通信パターンをそのまま扱えず、サイクル正確な模擬は規模が大きくなると遅すぎる。

本論文の枠組みはこの3点を1つの流れに接続する。並列化フレームワークから得た通信トレースを物理的なポート対応へ分解してトラフィックを作り、スイッチ型と全結合型の接続を最大512チップまで模擬できるシミュレータで評価し、複数の指標を重み付きスコアへまとめて適応ベイズ探索で次の候補を選ぶ。代表的な定量結果として、FPGAベースの試作機との比較で端から端の時間誤差は2.46%から8.23%に収まり、サイクルとイベントを混ぜたモデルにより模擬は純粋なサイクル正確方式より最大7.8倍速くなった。さらに32チップで671B級モデルの推論を扱う事例では、最悪の実行可能構成と比べて有効スループットが44.1%改善し、メモリ指標が98.4%減る構成が見つかり、探索は約20回の評価で収束した。これは実機の推論高速化ではなく、設計段階で良い構成へ早く到達するための枠組みの評価である。

## 問題設定

チップ間接続の設計変数には、フレームの大きさや分割の単位といったパケット化、どの宛先を先に送るかというスケジューリング、バッファや帯域の配分といった資源配分がある。これらが組み合わさると候補数は数千規模になり、全てを実機で試すことはできない。模擬で代替するにも、負荷が現実とずれれば結論がずれる。言語モデルの通信は並列化方式に強く依存し、データ並列やテンソル並列では全削減や全対全といった集合通信の形が変わり、専門家の振り分けでは不均一なトラフィックが生じる。さらに規模が大きくなると、サイクル単位で全てを追う模擬は時間がかかりすぎ、粗い模擬では尾遅延や公平性が見えなくなる。本論文の問題設定は、負荷生成、模擬、評価、探索を分断せず、ワークロードからハードウェアまでの最適化の流れとして一体で作ることにある。通常の仕組みでは各段階が別々の道具で担われ、途中の変換で現実性が失われがちだったことへの対処である。

## 手法のあらまし

流れは4段階である。第1に、並列化フレームワークの通信トレースを入力し、物理的な接続構造とポート対応に従ってチップ間のフローへ分解する。第2に、7段のパイプラインを持つシミュレータが、プロトコルのトランザクション水準で通信を進め、スループットと遅延と公平性とバッファ使用量を出す。第3に、評価器がこれらの指標を正規化して重み付きの単一スコアへまとめる。事例ではスループットに40%、尾遅延に25%の重みが置かれた。第4に、適応ベイズ探索が初期の種まき評価の後にガウス過程の代理モデルを学習し、改善期待量が大きい候補を次に選ぶ。得られた規則で候補空間を絞ることもでき、事例では2394通りから1152通りへ減った。出力は最良構成と、その性能内訳の報告書である。

## 手法

### 1. ワークロード駆動のトラフィック生成 — 集合通信を物理フローへ分解する

この機構が観測するのは、並列化フレームワークが出す集合通信のトレースである。保持する状態は、接続のトポロジーとポート対応表であり、どの論理的な通信がどの物理リンクを通るかを決めるために使う。処理としては、全削減や全対全といった操作を送信元と宛先の組へ展開し、メッセージの大きさと発生順序を保ったままチップ間のフロー列へ変換する。選択するものは通信そのものではなく、その物理的な実現経路である。

減るボトルネックは、合成的な一様トラフィックで設計して実負荷で外すという不整合である。追加で消費する資源はトレースの取得と分解の前処理であり、規模が大きい場合はトレース量自体が大きくなる。誤った対応付けをした場合、つまりポート対応が実際の配線と違う場合は、混雑するリンクの予測がずれ、探索全体の結論が歪む。そのため論文は次のシミュレータ検証とセットでこの段階を位置付けている。感度評価ではフローの大きさの不均衡を、最大と最小の比で1倍、4倍、64倍と変えた条件も扱っており、不均一な負荷でも評価できることが前提になっている。

### 2. 混成サイクル・イベントシミュレータ — 精度を保って規模を扱う

第2の機構が観測するのは生成されたフロー列と接続構成である。保持する状態は、各ポートのパイプライン段階、バッファの占有、クレジットによる流量制御の状態である。処理は7段のパイプラインで進み、パケット化の段階、スケジューリングの段階、資源配分の段階がそれぞれ評価軸に対応する。模擬の方式として、細部が必要な部分はサイクル水準で、粗くてよい部分はイベント水準で進める混成モデルを採用し、スイッチ型と全結合型の両方を最大512チップまで扱う。

この機構が選択するのは模擬の粒度であり、転送するのはフローではなく模擬上のパケットである。減るボトルネックは、サイクル正確な模擬の実行時間であり、実測で最大7.8倍の高速化が得られ、並列度が4から512へ上がる範囲で1.1倍から7.8倍の高速化が報告されている。追加で消費する資源は、混成化による近似の管理であり、精度は別途検証が必要になる。検証ではFPGA試作機を基準として複数の通信パターンで平均誤差が4.39%、2.46%、8.23%だった。誤差が最も大きいパターンでも1割未満に収まることが、探索の前提としての信頼性を支えている。粒度を粗くしすぎれば尾遅延のような細部が消えるため、論文は精度検証を枠組みの一部として組み込んでいる。

### 3. 指標評価器と適応ベイズ探索 — 数千通りから20回で当たりを引く

第3の機構が観測するのはシミュレータが出す5つの観点、すなわちスループット、中央値遅延、尾側の遅延、公平性、バッファ使用量である。保持する状態は評価済み構成とそのスコアの履歴であり、ガウス過程の代理モデルが未評価構成の見込みを推定するために使う。処理としては、各指標を正規化して重み付き合計のスコアにし、まず規則に基づく種まきで有望な領域を押さえ、次に改善期待量が最大の候補を順に評価する。選択するのは次に模擬すべき構成であり、削除するのは見込みの低い構成である。事例では、分割単位がフレーム長の2倍以上という規則で候補が2394通りから1152通りへ減り、全タスクが20回以内の評価で収束した。

減るボトルネックは探索の試行回数であり、全探索が不可能な空間でも現実的な時間で結論へ届く。追加で消費する資源は代理モデルの学習と各候補の模擬実行である。誤予測時の挙動として、代理モデルが見込みを外しても、その構成の実測スコアが履歴へ戻されてモデルが更新されるため、誤りは次の選択へ反映される。ただし重みの置き方が結論を左右する。スループットを重視する重みでは尾遅延の悪い構成が選ばれ得るため、論文は用途に応じて重みを変えることを前提とし、事例の重みも明示している。感度分析ではパラメータごとに平均スコアと信頼区間を示し、どの設計変数が効くかを読み取れるようにしている。

### 4. データと制御の流れ

設計者はモデルと並列化設定と接続の候補範囲を与える。トラフィック生成器が実負荷由来のフローを作り、シミュレータが候補構成ごとに性能を出し、評価器がスコア化し、探索器が次の候補を選ぶ。この循環が収束するまで回り、最後に最良構成と内訳が出力される。個別の設計知見も得られており、例えばフレーム長は1KBから8KBまでは有効スループットが急に伸びて飽和すること、分割単位はフレーム長の約2倍で飽和すること、スケジューリングでは量子を2KBとする不足ラウンドロビン方式が往復方式の約1.99倍の有効スループットを示す一方、量子を8KBへ広げると行列の先頭ブロッキングで4.06%悪化することが報告されている。

|---|---|---|---|---|

## 評価

### まず見るところ

結論は2層ある。第1にシミュレータ自体が実機試作に対して1割未満の誤差で、しかも最大7.8倍速いため、探索の道具として使えること。第2に、その道具で探索すると最悪構成と比べて有効スループットとメモリの両方を大きく改善する構成が約20回で見つかることである。品質の面ではモデルの出力には触れないため生成品質への影響はない。メモリの98.4%削減は、バッファ配分の指標上の削減であり、実チップのメモリ容量そのものの削減ではない点に注意が要る。評価の強さは、精度検証、規模の拡張性、個別パラメータの感度、実ワークロード事例まで含む点にある。一方で全ては模擬上の結果であり、見つかった構成を実チップで製造して測ったわけではない。

## 既存研究との差

既存の接続シミュレータは、固定したフリット単位の模擬や、言語モデルの通信トレースへの非対応、尾遅延の分析不足といった制約があった。本論文は、言語モデルのトレース対応、トランザクション水準の模擬、動的なフレーム構成、クレジット方式の流量制御、スイッチ型対応を1つの枠組みに揃え、さらに探索までを接続した点が差である。言語モデル推論のシミュレータが計算側を扱うのに対し、本論文はチップ間通信のハードウェア設計そのものを対象にする点でも位置付けが異なる。つまり何を動かす研究かで言えば、実行時のスケジューリングではなく、設計時に接続構成を選ぶ研究である。

## 限界・実装状況

限界として、結果はシミュレーション上のものであり、最適構成の実チップ検証は行われていない。試作機との誤差も最大で8.23%あり、僅差の構成同士の順位は誤差の範囲で入れ替わり得る。スコアの重み付けは用途依存であり、重みを変えれば最適構成も変わるため、結論の一般化には注意が要る。対象プロトコルとトポロジーは論文が扱う範囲に限られ、他の接続方式への適用は未評価である。実装状況としては、コードが公開されており、会議への採択も本文に明記されている。実推論基盤へ組み込まれる種類の成果物ではなく、設計支援の道具としての公開である。

## 一般的な実装上の含意

大規模システムの設計では、負荷の現実性、模擬の精度、探索の効率のどれか1つが欠けても結論が実務で使えなくなる。3点を一体の流れとして作り、模擬の精度を実機試作で先に担保してから探索へ進む順序は、他のハードウェア探索にも転用できる。また、設計変数ごとに飽和点を特定しておくと、候補空間を規則で削って探索を速くできる。最良対最悪の利得は空間の広さを示す数字であり、既定構成との差と分けて読むべきだという点も、評価の読み方として一般的である。
