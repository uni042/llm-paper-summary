# AEGIS: Scaling Long-Sequence Homomorphic Encrypted Transformer Inference via Hybrid Parallelism on Multi-GPU Systems

## 概要

AEGISは、完全準同型暗号（fully homomorphic encryption; FHE）で暗号化した入力を復号せずにTransformerへ通す際、複数GPUへ暗号文を分配する方法を最適化するシステムである。暗号化推論では、通常の行列テンソルに加えて、暗号多項式の係数、剰余数系（residue number system; RNS）の法、暗号文のスロット配置が計算と通信の依存関係を決める。一般的なテンソル並列をそのまま適用すると暗号文を丸ごと複製し、暗号ライブラリの法ごとの並列だけを使うと鍵切替のためのGPU間同期が多発する。AEGISはTransformerのトークン・行列積の意味と、暗号文のRNS依存性を同時に解析して、通信を必要な場所だけへ制限する。

中核は三つの処理である。第一に、暗号文の同一法に依存する多項式断片を局所化する「法の一貫性」を優先する。第二に、同じトークンや出力群に属する断片をなるべく同一GPUへ置き、暗号化FFNと注意層の集合通信を削る。第三に、鍵切替、回転、暗号化行列積の順序を依存関係を壊さない範囲で並べ替え、残る集合通信をGPU計算と重ねる。暗号文を平文へ戻したり、セキュリティ要件を緩めたりする方式ではない。

BERT-BaseをSST-2で評価した結果、2GPUのRTX A6000環境では単GPU比で約1.85〜1.86倍、4GPUのA100環境では約3.82〜3.87倍の高速化を報告する。4GPUのスケーリング効率は最大96.62%とされる。一方、暗号化推論の絶対遅延は大きく、4×A100で2048トークンの実行に5036.1秒を要する。したがって本研究の「高速化」は、非常に重い暗号化Transformer推論の複数GPU分散を改善するものであり、平文LLM配信の通常の応答速度と同一視できない。

## 問題設定

クラウド側へ平文の入力を送る推論では、事業者が入力を観察できる。FHEでは利用者が入力を暗号化し、サーバーは暗号文のまま加算・乗算などを行い、利用者が返答を復号する。論文は半正直（semi-honest）サーバーを仮定し、128ビット相当の暗号強度を対象とする。Transformerを暗号上で実行するには、非線形関数を多項式近似し、乗算により失われる暗号のノイズ余裕をブートストラップで回復する必要がある。

CKKSは近似数値演算に用いられる準同型暗号方式で、暗号文の多項式を複数の素数法で表す。各素数法の断片はRNSのlimbと呼ばれる。法の積である暗号文の法連鎖は演算可能な深さを決め、乗算や回転、鍵切替によって断片間の依存関係が生じる。これらの断片をGPUごとに機械的に均等配分すると、鍵切替のたびに全GPUから情報を集め直す必要がある。逆に、平文テンソルの列を分割するように暗号文を分割すると、スロット単位の部分結果が一つの暗号文内に混在し、無効なスロットまで含めた通信が必要になる。

原著の第3節では、128トークンの暗号化BERT-Baseで活性値666.89MB、事前符号化重み10.64GB、利用者固有の鍵20.45GBを要する例を示す。2048トークンでは活性値だけで52.95GBとなり、48GBのGPU一枚へ収まらない。導入部では長い入力に対する符号化重みと暗号化活性値が合計で数百GB規模になることを説明する。通常のBERTの重み容量やKVキャッシュとは桁違いの暗号化データが分散実行の対象である。

暗号化した1024トークンの送信は、原著の例では平文の数MBに対して暗号化後約1.3GBとなる。集団通信では転送量がさらに増えるため、単にGPUを増やすと通信待ちのため遅くなることさえある。実際、既存のlimb並列は2GPUで単GPUより遅くなる例を示す。AEGISの問題設定は、暗号化によって発生する多次元の依存関係を保存しつつ、必要な通信量とGPU間の待ち時間を減らすことである。

## 手法

### 1. アプリケーション依存と暗号依存の共同解析

AEGISはTransformerの演算グラフを暗号演算へ変換した後、さらに暗号多項式の命令へ展開する過程で、どの断片が同じGPUに置かれるべきかを解析する。原著第4.1節の基本規則は、法連鎖の依存性を第一優先とし、同じトークンに属する暗号断片の局所性を第二優先とすることである。これにより、鍵切替時のRNS断片の再集合と、トークンごとの部分結果の集約が異なるGPU間にまたがる回数を減らす。

単純な法ごとの並列では、同じトークンを構成する複数の法の断片が各GPUへ散らばる。暗号の回転や再線形化にはこれらの断片の結合が必要であり、分散の利得を通信が打ち消す。単純なテンソル並列では、同じ出力へ寄与する重み群がGPU間に散り、暗号文の空きスロットまで送ることになる。AEGISは両方の条件を満たす断片配置をコンパイル時に選び、通常のテンソル形状だけでは見えない通信依存を可視化する。

### 2. FFNの出力群に基づく配置

原著第4.2節は、FFNの重みを単純な行・列で分割する代わりに、同じ出力群へ寄与する暗号化重みの断片を同一GPUへ集める。CKKSでは、同じ出力の暗号文スロットへ部分結果を加算する必要があるため、平文のAllGatherに相当するつもりの分割が、暗号上では大きなAllReduce相当の通信へ変わる場合がある。出力群を局所化すれば、各GPUが自分の担当する出力暗号文を完成でき、通信は入力活性値の取得へ限定できる。

各GPUは担当する出力群の重みを保持し、通信専用ストリームで必要な暗号化入力をAllGatherしながら、手元の重みとの多項式乗算を進める。通信と計算を重ねることで、すべての入力が到着するまで演算器を遊ばせずに済む。二つのFFNの間のGELU多項式近似は、対応する暗号文を局所保持しているためGPU内で実行でき、追加の集合通信を要しない。配置規則を守らないと1024トークンの線形層ごとに約3.8GBの余分な通信が生じる例を原著は示す。

### 3. 注意層の分割と必要最小限の集合通信

原著第4.3節では、各GPUが手元のQとKの断片を使って回転・乗算・累積を行い、部分的な注意得点を計算する。注意得点は埋め込み次元全体の集約を必要とするため、GPU間の通信を完全に消すことはできない。AEGISは部分得点をReduceScatterで分配し、各GPUが担当する注意位置のsoftmax多項式近似を局所計算できるようにする。その後、正規化した得点をAllGatherして必要な位置へ配布し、各GPUが手元のVとの積を計算する。

この経路では、注意層ごとに主要な集合通信をReduceScatterとAllGatherへ限定し、暗号化されたK・Vの完全複製や、softmaxの中間値を全GPUへ繰り返し集める操作を避ける。分散するのは注意得点と出力に必要な暗号文の断片であり、通常の平文注意で使う単純なQKVテンソル並列と同一ではない。トークン内の断片が同じGPUにそろっていれば局所集約を先に行い、複数GPUへ分かれているときだけ関係するGPU間へ集合通信を挿入する。

### 4. 多項式命令の順序変更と通信重畳

原著第4.4節では、暗号の回転・鍵切替・多項式積の依存関係を調べ、独立な回転オフセットや部分積の処理順を入れ替える。元の順序ではReduceScatterやAllGatherを待つため計算が止まるが、先に実行可能な多項式演算を進め、通信が到着する間に別の部分を計算すれば待ち時間を隠せる。図8は、異なるGPUが異なる回転範囲を先行計算し、次の集合通信と重ねる例を示す。これは通信量そのものを削る配置最適化とは別の寄与である。

実装ではPythonのモデルをtorch.fxで追跡して暗号化中間表現へ下ろし、暗号演算をRNS多項式命令へ展開する。法とトークンの依存を見て集合通信を挿入し、通信費用と演算遅延を考慮した静的な実行計画を作る。原著はコンパイル時の依存解析と通信挿入が0.7秒未満であると報告する。推論時は各要求の暗号鍵を対象GPUへ配置し、事前に作った決定的な計画に従って実行する。オンラインで推論中に新しい分割を探索する方式ではない。

## 評価条件

| 項目 | 条件 |
|---|---|
| モデルと課題 | 暗号化BERT-Base、SST-2。精度0.923、F1 0.929 |
| 入力長 | 128、256、512、1024、2048トークン |
| 2GPU環境 | RTX A6000 48GB×2、NVLink |
| 4GPU環境 | A100×4、NVLink。図13と本文の実時間評価 |
| 暗号方式 | CKKS、128ビット強度、スロット数2^15、多項式次数2^16、1661ビットの法、35段と4つの特別素数 |
| 実装 | LibTorch、LiberateFHEのCUDAバックエンド、torch.fxによるコンパイル変換 |
| 比較 | 平文向けテンソル並列の直接適用、HEBooster、Cinnamon、Hydra |
| 指標 | GPU間通信量、各層のスケーリング効率、単GPU比の全体速度、GPU当たり最大メモリ、絶対実行秒数 |

比較方式は同じ暗号演算基盤と、遅延再線形化・遅延再スケーリングなど共通のコンパイラ最適化を使用する。異なる暗号パラメータや別のモデルへ結果を移すときは、鍵切替頻度、暗号文のスロット数、法の長さ、GPU間帯域が変わる点に注意する。平文BERTの遅延と暗号化BERTの遅延は比較対象ではない。

## 主要結果

### 通信量と最適化要因

原著第5.2節の通信量測定では、AEGISはFFNのGPU間転送を788.65MB、注意層を2459.66MBへ抑える。HEBoosterの対応する値は61735.77MBと63395.76MBで、暗号の鍵切替を跨ぐ通信が支配的になる。CinnamonやHydraも一部を改善するが、前者は非線形部の通信、後者は暗号化入力の複製が残る。絶対通信量は入力長や暗号設定に依存し、全条件で同じMB数になるわけではない。

2GPUのアブレーションでは、配置最適化が128トークン時の速度改善の76.27%、2048トークン時の88.26%を占め、演算順序変更はそれぞれ23.73%、11.74%を占める。長い入力では注意演算と暗号文通信が支配的になり、残る通信を隠すよりも、そもそも通信させない配置の寄与が大きい。原著要旨の「FFNで最大57.9%、注意層で最大81.3%の通信削減」は、選択した先行方式・入力条件との比較であり、HEBoosterとの上記MB比率とは同一の比較ではない。

### GPU数に対する速度と効率

| 比較条件 | 原著の値 | 解釈 |
|---|---:|---|
| 2GPU AEGIS、128トークン | スケーリング効率92.98% | 理想の2倍に対して約1.86倍の速度 |
| 2GPU AEGIS、128〜2048トークン | 単GPU比1.850〜1.860倍 | 長さが増えても大きく劣化しない |
| 4GPU AEGIS、128〜2048トークン | 単GPU比3.823〜3.865倍 | 理想の4倍に近いが絶対遅延は大きい |
| 4GPU AEGIS、最大 | 効率96.62%、速度3.86倍 | 最大値は選択条件での値 |
| 2GPU HEBooster、128トークン | 単GPU比約0.637倍 | GPUを増やすと逆に遅い |
| 2GPU Hydra、128トークン | 約1.512倍 | AEGISより低く暗号文複製も必要 |

原著表3では、2GPU時のFFN・注意・softmax・ブートストラップの効率を分けて示す。AEGISのsoftmax効率は89.32%、Hydraは40.52%であり、非線形演算を跨ぐ暗号文通信の削減が全体速度へ寄与している。表中の「スケーリング効率」は、単GPU比の高速化倍率をGPU台数で割った値である。例えば2GPUで約1.86倍なら効率は約93%であり、倍率そのものが92.98倍という意味ではない。

### 絶対遅延とメモリ制約

4GPU A100の実時間は、128トークンで192.8秒、512トークンで544.2秒、2048トークンで5036.1秒である。2048トークンの実行は約84分であり、現在の平文LLM推論に比べて暗号化の負担が極めて大きいことを示す。速度倍率だけを示すと実用的な低遅延システムと誤認されるため、原著の絶対値を併記する必要がある。

メモリについては、AEGISは2GPUで17.14〜47.15GB/台、4GPUで14.55〜30.82GB/台の範囲を報告し、2048トークンまでの評価を可能にする。暗号文を各GPUに複製する方式では長い入力でメモリ不足となり、HydraやCinnamonは4GPUでも512トークンを超えると実行可能性が制約される。HEBoosterは分散したメモリ使用量ではAEGISに近いが、通信による実行時間の悪化が大きい。つまりメモリ節約と速度改善は別の評価軸であり、AEGISは両者の両立を狙う。

### 負の結果と評価の境界

平文向けのテンソル並列を暗号化推論へ直接適用すると、2GPUでの速度は約0.997倍にとどまり、計算の重複で効率が悪い。HEBoosterは暗号の法ごとに均等分割してメモリを節約するが、鍵切替の通信により単GPUより遅くなる。CinnamonはFFNでは改善するが、注意層の非線形演算で待ちが残る。これらはGPUを追加するだけでは暗号化Transformerがスケールしないという問題設定を裏付ける。

また、論文の図12・13にはメモリ不足で実行できない条件があり、一部の曲線には推定・外挿値が含まれると注記されている。実測できない条件を実測の速度改善と混同してはならない。実験対象はBERT-BaseのSST-2であり、生成LLMの長時間デコードや多人数同時サービングの実測結果ではない。

## 既存研究との差

HEBoosterなどのRNS法ごとの並列は、暗号文の数学的な構造に沿ってGPUを割り当てるが、Transformerがどのトークンや出力次元を集約するかを十分に利用しない。Hydraなどの暗号化テンソル並列はアプリケーションの形状を考慮するが、暗号文を複製したり非線形演算で法の断片を再集合したりする必要がある。AEGISはこの二つの視点を統合し、法連鎖とトークンの局所性を同時に満たす配置を選ぶ。

また、暗号演算の行列積を単体で高速化する研究と異なり、AEGISは暗号化演算を複数GPUへ配置するためのコンパイル時のスケジューリングに焦点を当てる。鍵切替・回転・softmax・FFNの演算順序を再配置して、残る通信を計算と重ねる。暗号方式の変更や近似精度を下げることで性能を稼ぐのではなく、同じ暗号計算をより少ないGPU間通信で実行することが差分である。

## 限界

第一に、評価対象は暗号化BERT-Base/SST-2である。モデルが小さくても暗号文は巨大だが、ここでの性能を数十億〜数千億パラメータの生成LLM、鍵値キャッシュを保持する長時間デコード、混合専門家モデルの配信へ直接一般化することはできない。論文が主に扱うのはTransformerの暗号化された一括入力処理であり、平文の生成サービングと律速箇所が異なる。

第二に、4GPUで3.86倍の高速化が得られても、2048トークンで5036.1秒という絶対遅延は依然として大きい。GPUを増やすことによる装置費用、暗号鍵の配置費用、利用者側の暗号化・復号の総遅延、複数要求を混ぜたスループットは、この測定から十分には判断できない。リアルタイム対話へ適用可能と結論するのは早い。

第三に、128ビット強度のCKKSと特定の法連鎖、スロット数、暗号演算実装に依存する。暗号の深さ、ブートストラップ頻度、モデル構造が変われば、法の局所性とトークン局所性の最適な配置も変わる。動的な実行時再配置ではなく、コンパイル時に決めた計画を用いるため、入力形状やGPU数が変わる運用での柔軟性は別途検証が必要になる。

第四に、メモリ不足の比較条件には推定・外挿の図示が含まれる。スケーリング効率と単GPU比の速度は、異なるGPU型番やNVLink速度に依存する。2GPUのA6000と4GPUのA100の数値を同一GPUで台数だけ増やした純粋な強スケーリングとして比較してはならない。
