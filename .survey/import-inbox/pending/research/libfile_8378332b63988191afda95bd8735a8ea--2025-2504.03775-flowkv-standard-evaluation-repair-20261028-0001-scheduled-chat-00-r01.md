# FlowKV：KV転送の起動回数を減らし、P/Dノード負荷を均衡させる

## 概要

LLM推論でプリフィル（P）とデコード（D）を別GPUへ分けると、それぞれに適した計算資源を割り当てられる。しかしプリフィルで生成したKVキャッシュをデコードGPUへ移送する必要があり、KVが多数の非連続物理ブロックに散らばっていると、転送カーネルの起動回数が大きな固定費になる。さらにP/DのGPU数を固定すると、到着要求の入力長・出力長によって片側だけが混雑する。

FlowKVは、**KVのメモリレイアウト・ブロック割当・転送単位を一体で設計**し、NCCL通信の細粒度呼出しをまとめる。これに、全体負荷に応じたP/Dノードの役割切替を組み合わせる。既存mainの一次論文照合済み記録によれば、L20単機のKV転送遅延をvLLM-Disagg比96.8%削減し、LongBenchの要約タスクではvLLM同居実行比15.2〜48.9%のエンドツーエンド遅延短縮を報告する。

本稿は既存main原稿（Git blob `aa9fe403ef83e02005f32a63385df5196070e7bf`）の標準評価見出し欠落を修正する**構造修復候補**である。実験値・条件は既存原稿から継承し、別の実験を新規に実施したものではない。

## 問題設定

PagedAttentionは要求ごとのKVを固定長の物理ブロックへ柔軟に割り当てる。これはGPUメモリの利用率に役立つが、ある要求のKVが多数の離れたアドレスへ分散しやすい。通信ライブラリNCCLが連続領域を送受信する場合、レイヤー別・K/V別・ブロック別に通信を発行すると、通信量に比べて起動回数が大きくなる。細かな通信カーネルは推論カーネルとGPU資源を奪い合い、単に通信帯域の高い機器へ置き換えても問題が解決しない。

またP/D分離の比率を固定した場合、入力が長い要求の集中ではPが、出力が長い要求の集中ではDがボトルネックになる。片側に空きGPUがあっても役割を変更できなければ、クラスタ全体のスループットは伸びない。FlowKVはKV移送の固定費と、P/D役割の静的配置という二つの問題を同時に扱う。

## 手法

### ブロック優先KVレイアウト

通常の層優先配置を、論文が示す`(L, 2, B, H)`から`(B, L, 2, H)`のようなブロック優先配置へ変更する。ここでLは層、2はK/V、BはKVブロック、Hはブロック内データを表す。これにより、同じブロックに属する全層のK/Vが連続領域へ集まり、一つのブロックを転送するためにレイヤーごとに別のNCCL送信を起動する必要が減る。

この変更は転送前の単純な一時コピーではない。KVを書き込むプリフィル側と、受け取ったKVを読むPagedAttention側のインデックス・カーネルも整合させる。そうしなければ通信のための再配置が追加コピーや一時メモリを必要とし、転送削減の利益が薄れる。

### 連続セグメント割当と送受信区間の整列

空きKVブロックを個別に割り当てず、連続する空き範囲をセグメントとして管理する。新規要求には可能な限り少数の連続範囲を渡し、解放時には隣接空き区間を併合する。これにより、時間経過とともに物理ブロックが散在して転送回数が増える事態を抑える。

送信直前には、送信側と受信側のブロックID列を照合し、**両側で同時に連続している最大区間**を見つける。片側だけ連続でも一つの送受信にまとめられないため、双方の区間情報を用いることが重要である。連続区間を一つのNCCL操作にまとめれば、レイヤー×K/V×ブロック単位の細粒度送受信を大きな転送へ集約できる。断片化が強い場合には区間が短くなり、呼出し数削減の効果も小さくなる。

### 負荷適応型P/Dスケジューリング

全体制御器は、P/D双方の待ち行列、KVキャッシュ使用率、GPU利用率、メモリ帯域利用率、送信待ち行列、トークン予算などを観測し、短期的な揺れを平滑化して負荷点数を作る。通常時は接頭辞KVの再利用やTTFTを考慮してPノードを選び、そこからのKV転送時間が小さいDノードを選ぶ。

片側だけ過負荷になった場合は、各ノードに設けたP/D両方の局所スケジューラの優先役割を一時的に切り替える。両側の負荷が長時間高い、あるいは需要が極端に低い場合は、ノード数の増減も行う。役割切替はスケジューリング周期単位で行われるため、短い負荷変動に過剰反応しないための閾値・平滑化が必要になる。論文の係数は実験に合わせて設定され、任意の到着分布で最適とは限らない。

### データ経路と制御経路の分離

全体制御器は要求のP/D経路を決め、局所複合スケジューラは各ノードの実行を管理する。KV転送モジュールは同一機内ならIPC、構成に応じてRDMAまたはNCCLを選ぶ。NCCL経路ではブロック優先レイアウト、連続セグメント割当、双方向区間整列の順に通信起動を集約する。従って、通信の固定費削減とGPUの遊休抑制は独立した構成要素であり、総合スループットの向上をどちらか一つの効果へ帰属させてはいけない。

## 評価

### 評価条件

| 項目 | 論文の条件 |
|---|---|
| 単機・同種GPU | NVIDIA A100-SXM4-80GB×8、NVLink接続 |
| 異種GPU | L20 48GB×4、H20 96GB×8の2サーバー、ENI接続 |
| モデル | Llama-3.1-8B-Instruct、Llama-3.1-70B-Instruct |
| 比較対象 | vLLM同居実行、vLLM-Disagg、Mooncake、DistServe、層単位転送 |
| 合成要求 | 入力1K/5K/10K、出力256トークン、100要求、ポアソン到着0.1〜2.0 RPS |
| 転送単体 | 8B、1P1D、入力500〜12000、出力100トークン |
| 実ワークロード | LongBench要約のgov_report、multi_news、qmsum |

8Bの同種構成は2 GPUの1P1D、70Bは8 A100を用いたテンソル並列4の2ノード相当で比較する。異種構成ではP=L20/D=H20と逆配置を比較する。これは論文に記載された実GPU評価であり、ネットワーク帯域や長期本番クラスタの障害挙動まで網羅するものではない。

### 主要結果

| 指標 | 結果 | 比較条件 |
|---|---|---|
| KV転送遅延（単機） | 平均96.8%削減、31.5倍 | L20、8B、1P1D、vLLM-Disagg比 |
| KV転送遅延（異種2機） | 平均92%削減、12.6倍 | L20/H20、8B、vLLM-Disagg比 |
| NCCLカーネル呼出し | 23,469回→1回 | 層単位転送に対する連続区間集約の理想的条件 |
| 合成負荷のスループット | 平均25%増 | A100、8B、vLLM同居実行比 |
| 分離推論方式とのスループット | DistServe比95%、Mooncake比40%、vLLM-Disagg比35%増 | A100同種構成、合成負荷 |
| LongBench要約のエンドツーエンド遅延 | 48.9%、29.4%、15.2%短縮 | P=L20/D=H20、vLLM同居実行比、3タスクの順 |

最大の96.8%削減は**KV転送だけの遅延**であり、モデル全体の応答時間が96.8%減ったという結果ではない。転送を大きな一回へ集約しても、プリフィル計算、デコード計算、要求待ち行列が残る。LongBenchの全体遅延短縮が15.2〜48.9%にとどまるのはこのためである。スループットの向上にはP/D分離と負荷適応制御も含まれるため、転送カーネル単独の高速化倍率として読まない。

### 負の結果と境界条件

LongBenchのqmsumでは遅延短縮15.2%で、gov_reportの48.9%より小さい。異種GPUでP/Dの配置を逆転すると、デコードにH20を使う構成より不利となり、論文はgov_reportで34.67%、multi_newsで40.1%、qmsumで8.8%の配置差を報告する。Mooncakeが長い入力で一部Failureとなる条件もあり、すべての比較で同じ要求範囲を完走できたわけではない。

KVの物理断片化が強いと連続区間が短くなり、23,469回から1回という極端な削減は再現できない。負荷点数の重みと閾値は実験的に選ばれ、未知の到着率変動では役割切替が振動する可能性がある。大規模クラスタの通信輻輳、長時間運転での区間維持、障害時の再構成は十分に検証されていない。

## 品質への影響

本方式はKVの物理配置・転送単位・処理ノードの役割を変更するが、KVの量子化、トークン削除、モデル重みの近似を導入しない。原理上は生成分布を変えないシステム最適化である。ただし論文は生成品質の独立した同等性ベンチマークを主結果として提示しておらず、実装バグの不存在まで実証するものではない。

## 既存研究との差

DistServeやSplitwiseがP/D分離と段階別資源配分を、MooncakeやMemServeがKVを中心とした分散保存・転送を扱うのに対し、FlowKVはPagedAttention上の**物理KVレイアウトとNCCL起動粒度**を直接最適化する。連続区間の割当・送受信双方の整列まで一貫して設計する点、各ノードがP/Dの両方を実行できる複合スケジューラを持つ点が差分である。

## 限界と適用条件

対象はLlama-3.1の8B/70B、A100/L20/H20、単機または2サーバー規模である。ENIの詳細な帯域・遅延条件、大規模な多テナント環境、長期のメモリ断片化とスケジューラ閾値感度は十分に示されない。公開コードURLも既存mainの一次資料照合記録では確認されておらず、他のvLLM版への移植工数は不明である。
