## 概要

混合専門家（Mixture-of-Experts; MoE）は総パラメータを増やしながら、各tokenで一部expertだけを実行することで、dense modelより計算量を抑えられる。しかし公開MoEの多くはweightだけが公開され、学習data、routing設計、失敗した設定、checkpoint、logが不足し、なぜその構成が選ばれたかを再現しにくかった。

OLMoEは総6.9Bパラメータのうち1 token当たり1.3Bを活性化する完全公開MoEである。各MoE層に64個の細粒度expertを置き、routerがtokenごとに上位8 expertを選ぶ。5.1T tokenを事前学習し、同程度のactive parameterを持つ公開model群で最高水準を示す。さらにexpert粒度、共有expert、routing方式、sparse upcycling、補助損失を一つずつ変える制御実験と、学習中のexpert専門化解析を公開する。

## 問題設定

MoEの推論costはactive parameterで概ね決まる一方、全expert weightはmemoryへ保持する必要がある。したがって「総容量を増やせる」という利点と、「routing、load balance、expert配置、weight memoryが複雑になる」という負担が同時にある。

特に、expertを何個に分けるか、何個を同時活性化するか、tokenがexpertを選ぶかexpertがtokenを選ぶか、共有expertを置くか、といった選択は互いに影響する。OLMoEは完成modelだけでなく、これらを制御実験で比較し、MoE設計の再現可能な証拠を作ることを目的とする。

## 手法

### 1. 細粒度64 expert・top-8活性化

OLMoE-1B-7Bは各MoE層に64個の小さいexpertを持ち、各tokenで8個を活性化する。総parameterは6.9B、active parameterは1.3Bである。大きな少数expertより細粒度にすることで、tokenごとに組み合わせられるexpert集合を増やしつつ、1 tokenの実行量を抑える。

routerは入力表現から64 expertのlogitを計算し、top-8のsoftmax重みでexpert出力を加重和する。したがってSwitch Transformerのtop-1より1 token当たりのexpert計算は増えるが、より細かな専門化と組合せが可能になる。

### 2. dropless token-choice routing

最終構成は各tokenが自分のtop-k expertを選ぶtoken-choiceで、容量超過tokenを捨てないdropless routingを使う。expert側が受け入れるtokenを選ぶexpert-choiceとも比較し、最終的にはtoken-choiceを採用した。

負荷偏りを抑えるためload-balancing lossを重み0.01で加え、router logitの過大化を抑えるz-lossを0.001で加える。cross entropyと合わせてrouterの学習を安定させる。

### 3. scratch事前学習と公開性

dense modelからexpertを複製するsparse upcyclingも比較するが、十分なcompute budgetではscratchからMoEを学習する構成を採用する。OLMoE-Mix約4.06T token相当のsource mixtureを用い、実際には5.1T tokenまで学習する。

model weightだけでなく、data、code、途中checkpoint、training logを公開する。このため最終性能だけでなく、routingがいつ固定化し、どのexpertがどのdomain/tokenへ専門化したかを学習過程に沿って調べられる。

### 4. routing専門化の解析

学習途中checkpointで同じ入力がどのexpertへ送られるかを追跡する。top-8集合は事前学習の1%、約20B token時点ですでに最大約60%が最終routingと一致し、40%時点では最大約80%へ達する。後段layerほど早く飽和し、第1層は遅い。

またexpert同士の共活性、domain specialization、vocabulary specializationを測定し、expertがランダムな計算分割ではなく入力domainや語彙に応じた役割を形成することを示す。

## 主要結果

| 条件 | 結果 | 意味 |
|---|---:|---|
| 同active規模model比較 | OLMoEが最高水準 | 1.3B activeでも総容量6.9Bを利用 |
| OLMoE-Instruct | AlpacaEval 84% | Llama2-13B-Chat等の大型dense modelも上回る |
| top-8 routing、20B token | 最大約60%飽和 | expert割当が学習初期から形成 |
| top-8 routing、40%学習時点 | 最大約80%飽和 | 後半は既存専門化を精緻化 |
| expert構成 | 64中8 active | 細粒度routingを採用 |
| auxiliary loss | load balance 0.01 / z-loss 0.001 | dropless routingの偏り・安定性を制御 |

Instruction modelではSFT後にDPOを適用し、測定したmodel群で最高の平均性能を得る。論文は、共有expertが必ずしも有効でないこと、sparse upcyclingの利得がcompute budgetに依存することなど、最終設計に採用しなかった結果も報告する。

## 推論システム上の意味

OLMoEはサービングsystemそのものではないが、推論時には1 tokenにつき8/64 expertだけを実行するため、active computeと総weight memoryが分離する。これはexpert parallelism、expert cache/offload、all-to-all通信、load balanceを考える際の代表的な実model構成である。

一方、6.9B全weightを保持する必要はあるため、dense 1B modelと同程度の演算量でもmemory footprintは同じではない。論文自身も、同程度active parameterのdense modelに近い推論costでありながら、総7B相当のGPU memoryが必要になると明記する。

## 既存研究との差

Switch Transformerはtop-1 routingでMoEを単純化し、MixtralやDeepSeekMoE等は高性能なopen-weight MoEを提供した。OLMoEの中心的差は、最終weightだけでなく学習data、code、logs、途中checkpointと設計実験まで公開し、expert設計・routing・専門化を再現可能にした点にある。

また最終構成は64個の細粒度expertから8個を選び、共有expertを使わない。これは少数大型expertやshared expertを採る別系統MoEとの具体的な設計差になる。

## 限界

MoEはactive computeを抑えても全expert weightのmemoryを必要とし、分散推論ではexpert routingに伴う通信が発生する。本論文はmodel設計・学習・解析が中心で、vLLM等のサービングruntime上でのTTFT、TPOT、all-to-all通信量を主評価していない。また制御実験は設定ごとにbase modelが変わる場合があり、著者自身も全hyperparameter選択の普遍的最適性を保証しないとしている。
