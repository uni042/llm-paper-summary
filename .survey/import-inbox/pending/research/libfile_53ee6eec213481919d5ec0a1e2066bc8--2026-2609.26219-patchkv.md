# PatchKV: Efficient KV Cache Recovery for Dynamically Edited LLM Contexts

## 概要
長時間動くLLM agentではtool resultやmemoryを文脈中央へ差し替えつつ、その後ろの長いsuffixはtoken列として同じまま残ることがある。しかしprefixが変わるとsuffix hidden stateの因果履歴も変わり、編集長が変われば回転位置埋め込み（Rotary Position Embedding; RoPE）の位置もずれる。したがってtoken IDが同じでも古いKVをそのまま再利用できない。

PatchKVは隣接するcontext versionをexact prefix、edited span、aligned suffixへ分解し、suffixのうち実際に再計算すべきblockだけをrepairする。残りはCPU DRAMへ退避していたKVをmixed precisionで復元し、dequantization、RoPE補正、paged KV配置を融合する。

## 問題設定
full suffix recomputationは正確だが長いprefillをやり直す。Direct KV Reuseは速いがstale causal stateを伝播する。CacheBlend等の選択的再計算は改善するが、編集位置からのdriftと遠距離の重要tokenを同時に扱い、CPU転送量も抑える余地がある。

## 手法
### Dirty region予測
offlineで編集前後をpaired prefillし、suffix距離とstate driftの関係をmodel別にprofileする。runtimeでは編集長等から局所dirty boundaryを予測し、編集直後の高drift領域を必ずrepair setへ入れる。

### 非局所attention block
局所driftだけでは遠方のinstructionやretrieved factを落とすため、保存済みattention statisticsから高影響blockを少量追加する。repair setはpaged executionへ合わせてblock boundaryへ丸める。既定block sizeは32 token。

### Mixed-precision restore
repairしないsuffix blockには保存時に固定したFP16、K8/V8、K8/V4等のprecision tagを使う。fused restore pathでdequantization、position shiftに伴うkeyのRoPE correction、KV-page placementをまとめる。valueは位置だけでは補正できず、causal content差が大きいblockはrepair側へ回す。

## 評価条件
| 項目 | 条件 |
|---|---|
| model | Qwen3-32B、GLM-4-9B、Llama-3.3-70B |
| workload | HotpotQA-E、2WikiMQA-E、TriviaQA-E |
| hardware | 8×NVIDIA A800 |
| software | PyTorch 2.7、Transformers 5.3、Accelerate 1.14 |
| offload | CPU DRAM |
| baseline | full suffix recomputation、Direct KV Reuse、CacheBlend |
| 指標 | resume TTFT、F1、CPU transfer量 |

## 主要結果
full suffix recomputationに対するmean resume time-to-first-token（TTFT）高速化は2.51〜3.85倍、CacheBlend比では1.26〜2.06倍。9設定中6設定でCacheBlend以上のF1、残り3設定も1.36 point以内に収まる。

mixed-precision transportはFP16 restore比でmean resume TTFTを15.0%短縮し、F1低下は0.35 point。INT8比でも5.6%高速でF1差0.05 point以内。一方uniform INT4はさらに3.5〜3.7%速いがF1を1.15 point失う。

8K-token KV checkpointの例ではFP16が2007.8 MiB・344.4 msなのに対しPatchKV policyは799.4 MiB・158.0 ms。Qwen3-32B 10K contextでattention profilingは122.9〜125.2 ms、resume時repair-set constructionは2.62〜3.30 msである。

## 既存研究との差
prefix cacheは中央編集後のsuffixを再利用できない。CacheBlendはlayer-wise drift等で部分再計算するのに対し、PatchKVは「編集近傍のvalidity repair」と「遠距離のgeneration influence」を分け、さらにunrepaired blockのtransport precisionまで共同設計する。

## 限界
dirty-regionの遷移距離はmodel依存で、model-specific offline calibrationが必要である。prototypeのoffload tierはCPU DRAMであり、NVMe/CXL等の階層では転送と融合kernelの最適点が変わる。保存attention statisticsも追加metadataを必要とする。attention fractionやblock sizeを増やせば品質が単調に上がるわけではなく、workloadごとのtrade-offが残る。
