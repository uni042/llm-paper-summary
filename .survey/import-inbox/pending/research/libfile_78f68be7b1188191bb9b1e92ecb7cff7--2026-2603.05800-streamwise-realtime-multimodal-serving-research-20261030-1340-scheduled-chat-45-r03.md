# StreamWise：LLMから動画までの異種生成パイプラインをリアルタイム配信する

## 概要

LLM単体の推論高速化が進んでも、音声・画像・動画を含む生成アプリケーションのエンドツーエンド遅延が同じ割合で短縮するわけではない。動画生成は画像生成や音声合成より高い計算費用を持ち、複数モデルの依存関係を含む。ポッドキャスト動画のように、ユーザーが再生を開始した直後から映像を継続供給するには、全動画の生成完了を待つバッチ方式では不十分である。

StreamWiseは、**脚本LLM、TTS、画像生成、動画生成、音声同期、upscalingを一つのDAGとして管理**し、モデルごとに適切なGPUへ配置する。モデル並列・内容並列・spot GPU・異種ハードウェアを組み合わせ、締切に近い冒頭シーンへ多くの資源を割り当てる。さらに再生開始時は低画質で先に配信し、後半のシーンを順次高画質へ切り替える。

10分のポッドキャスト動画を生成する場合、A100だけの安価な構成は25ドル未満だが約1.4時間かかり、リアルタイムではない。StreamWiseは高価なGPUを組み合わせ、画質を適応させることで、45ドル未満で1秒未満の見かけの再生開始遅延を報告する。ただしその1秒未満は**500msのタイトルスライドを先に配信する**仕組みを含み、生成動画本体が1秒で完成するという意味ではない。

## 問題設定：複数モデルの遅延を足し合わせるだけでは足りない

入力は研究論文やニュースのテーマで、複数人物が会話する10分の動画を出力する。処理は脚本生成、TTS、画像生成、画像の切出し、動画生成、VAE復号、音声・動画の同期、upscaling、ストリーム配信からなる。モデルの出力は次のモデルの入力になるが、全動画を完成させてから次へ進む必要はなく、シーン単位で依存関係が解けた部分から並列に進められる。

従来のバッチ処理は全段階が終わるまで待つため、再生開始まで数十分以上かかることがある。GPUを大量に追加すれば開始遅延を減らせるが、同じモデルを過剰に複製すると費用が大きい。モデルごとに演算密度、メモリ容量、バッチ効率、GPU通信の要件が異なるため、単一GPU種類への均一配置は最適とは限らない。

StreamWiseは「最初の動画フレームをいつ見せられるか」（TTFF）と、「後続フレームを再生速度以上で継続供給できるか」を別々に扱う。品質も解像度・denoising step数・upscalingの有無で調整し、遅延・費用・画質のPareto最適点を探索する。最終動画の全体品質だけでなく、**冒頭で許容する低画質の時間**が重要な設計変数になる。

## 手法：モデルとコンテンツを並列化する

### 1. DAGを構成するモデル群

Gemmaが脚本を生成し、Kokoroが音声を合成する。Fluxはシーンの基礎画像を生成し、YOLOは切出しや構図の調整に使う。Hunyuan+FramePackが潜在空間で動画の下絵を作り、VAEが復号する。Fantasy Talkingは音声と映像を同期させ、Real-ESRGANが解像度を高め、StreamCastがシーンを連結して配信する。これらはすべて同じGPU上で逐次実行する必要はなく、シーンごとに並列化できる。

各モデルの処理時間、GPUメモリ、起動・転送費用をプロファイルし、どのGPU種類へ何個のモデル複製を置くかを決める。特に動画生成が支配的なため、LLMのトークン生成だけを高速化しても全体への影響は小さい。原著の測定では**LLM段階は全実行時間の1%未満**で、LLM向けのprefill/decode分離をそのまま導入してもTTFFや費用の改善はほとんどない。

### 2. 内容並列とモデル並列

同じ動画の複数シーンを別GPUで同時に生成する内容並列を使う。各シーンの依存関係を追跡し、冒頭シーンを優先して完成させる。モデル並列では動画モデルを複数GPUに分散し、重い段階の処理時間を短縮する。これらを組み合わせると、最初のシーンが完成する前に後半の全シーンを待つ必要がなくなる。

GPU配置では、安価なA100を多数使うだけでなく、TTFFに敏感な冒頭の重い処理へH100/H200/GB200などを割り当てる。GPUのレンタル単価が高くても、必要な時間だけ使えば総費用が下がる場合がある。spotインスタンスも利用するが、中断時の再実行や期限への影響を考慮する必要がある。

### 3. 画質適応とupscaling

著者は高画質を20 denoise step・1280×800、中画質を10 step・640×400、低画質を5 step・320×200で定義する。冒頭は低画質で生成してTTFFを短くし、再生中に中画質へ、さらに高画質へ切り替える。低画質のまま全編を出すのではなく、再生開始後10～20秒で中画質、45秒以内に高画質へ到達し、動画全体の90%以上を高画質で提供する。

さらにタイトルスライドと音声導入を約500ms先に配信し、ユーザーに再生開始を知らせる。これにより見かけのTTFFを1秒未満にできる。ただしタイトルスライドは**生成された動画本体のフレームではない**。ユーザーが最初の高画質シーンを見るまでの遅延は別に測る必要がある。

### 4. 費用と締切を考慮した資源配置

各モデルの候補GPU種類・複製数・並列度・spotの利用・品質設定を組み合わせ、指定したTTFFや継続再生SLOを満たす最小費用の配置を探索する。全組合せを厳密に解くと計算量が大きいため、著者はgreedyな割当てと分離配置を使う。最適割当ての全探索はgreedyより100倍以上遅く、オンラインの要求処理には適さない。

単一要求の最小費用だけでなく、複数要求が同時に来る場合はモデル複製を共有できるかも考える。Kokoroなど軽量モデルは同じGPU上で複数要求をまとめやすいが、Fantasy Talkingのような重い動画モデルはリアルタイムSLOを満たすため要求ごとに専用複製が必要になることがある。モデルの並列性の違いが全体費用を決める。

## 評価条件

| 項目 | 内容 |

| アプリ | 10分のポッドキャスト動画生成、他にSlide/Chat等のマルチモーダルワークフロー |
| モデル | Gemma、Kokoro、Flux、YOLO、Hunyuan+FramePack、Fantasy Talking、Real-ESRGAN |
| GPU | A100、H100、H200、GB200など異種GPUの候補を比較 |
| 画質 | 低320×200/5 step、中640×400/10 step、高1280×800/20 step |
| 主指標 | TTFF、全動画生成費用、再生SLO、GPU数、エネルギー、QPM別スケール |
| 比較 | Naive逐次実行、LLM向け異種配置方式を改変したHexGen/Helix、単一動画モデルを模したmonolithic構成 |
| 評価 | モデルごとのプロファイルを用いた配置・費用評価とシステム実装。大規模QPMの費用は複製数に基づく計画値を含む |

費用はクラウドのGPUレンタル単価と実行時間に依存し、地域・spot価格・モデルのバージョンが変われば再現値も変わる。動画品質はdenoise stepと解像度で段階を定義しており、ユーザーによる主観評価の同一スコアではない。

## 主要結果：リアルタイム性と費用

| 構成・条件 | TTFF/生成時間 | 費用 | 注意 |
|---|---|---|---|
| A100のみの最安構成 | 10分動画を約1.4時間で生成 | 25ドル未満 | リアルタイム再生には間に合わない |
| 低画質開始 | TTFF 3秒未満 | 0.5ドル/分未満 | 低画質320×200・5 stepで開始 |
| 画質適応 | 10～20秒で中画質、45秒以内に高画質 | 50ドル未満 | 動画の90%以上を高画質で提供 |
| タイトルスライド導入 | 見かけのTTFF 1秒未満 | 高品質構成で45ドル未満 | 500msの非生成スライドを先行配信 |

原著Figure 8、13。A100のみの構成が安価でも、ユーザーが待てる時間に間に合わないため、TTFF SLOを守る用途では別の構成が必要になる。逆にリアルタイムを要求しないバッチ生成なら、A100のみの構成が経済的である。**安い構成と速い構成を同じ指標で順位付けしない**ことが重要である。

GPUをH100などへ変更し、モデルを分離し、spotを使い、upscalingを追加する各要素がPareto曲線を改善する。upscalingを外すとTTFFと費用が悪化し、spotを使わないと費用が増える。A100のみではTTFFを30秒未満にできない条件があり、高価なGPUの短時間利用が必要になる。GB200はさらにTTFFを減らせるが時間単価が高く、15秒未満など極めて厳しい目標を除けばH100より費用対効果が悪い。

## 評価結果：エネルギーと複数要求でのスケール

原著Figure 14では、A100のみの構成はH100中心の構成より約2倍のエネルギーを使う。H100と少数のA100を組み合わせた構成はTTFF1分未満で約2kWhを消費し、Naive方式は最も省エネな構成でも10kWh超、最速構成では50kWh超となる。これは特定の10分動画ワークフローの測定・モデル化であり、すべての動画生成方式で同じkWhになるわけではない。

複数要求では、軽量モデルを共有することで複製数を抑える。1QPMのときの最小複製数で費用は1,200ドル/時未満、100QPMへ増やすとモデルごとに必要な複製数が増える。Kokoroは1→100QPMで費用増加が約43倍にとどまる一方、Fantasy Talkingは要求ごとの専用複製が必要で、スケールのボトルネックになる。Naiveは同じスループット・遅延を維持するために5.6倍の費用が必要と報告する。

さらに要求の3分の1がリアルタイム、3分の1がSLOを50%緩和、3分の1がバッチという混合条件では、締切の緩い要求を後回しにできるため、全要求リアルタイムSLOと比べて追加37.9%の費用削減を報告する。Naive比では9.1倍の費用削減となる。ただしこれらは要求到着・GPU単価・モデル複製数の仮定に依存し、任意の本番ワークロードでの保証値ではない。

## 評価結果：アブレーションと負の結果

- **LLM単体の最適化は効果が小さい**：脚本生成LLMは全実行時間の1%未満で、prefill/decode分離だけではTTFFや費用がほぼ改善しない。ボトルネックは動画・音声生成にある。
- **A100だけではリアルタイムが難しい**：最安25ドル未満でも10分動画に約1.4時間かかる。最小費用と締切達成は異なる。
- **GB200は常に最適ではない**：速いが単価が高く、15秒未満など極端なTTFFを狙う場合以外はH100より費用対効果が低い。
- **upscalingを外すと費用も遅延も悪化する**：低解像度で先に生成してからupscaleする構成の方が、全シーンを最初から高解像度で生成するより効率的。
- **monolithicモデルでは柔軟性が失われる**：単一動画モデルを模した構成でもStreamWiseの配置最適化はNaive比3.5倍の費用削減を示すが、モジュール化した完全ワークフローではさらに2.7倍の費用削減・4.3倍の遅延短縮を得る。異なるモデルを異なるGPUへ配置できることが重要。

## 限界：既存研究との差

LLMサービング研究はprefill/decodeの分離、KVキャッシュ管理、バッチングを改善するが、動画・音声・画像モデルのDAG全体を最適化するものではない。StreamWiseはモデルの特性を分け、重い動画生成へ資源を集中し、軽いTTSやLLMは共有する。モデルの実行段階とコンテンツのシーンを同時に並列化する点が特徴である。

ただし評価はポッドキャスト動画を中心とした限られたワークフローで、動画モデルや音声モデルの世代が変わればボトルネックも変わる。TTFF1秒未満はタイトルスライドを先に見せる工夫を含むため、**最初の実生成映像が1秒で出るという性能保証ではない**。低画質開始によるユーザー体験の受容度や、画質の時間的な不均一性について大規模な主観評価は行っていない。

spot GPUの中断、クラウド地域間転送、GPU予約の失敗、モデルロードのコールドスタート、長期運用の信頼性などは実際の本番サービスで別途検証が必要である。数百GPUを使う構成の費用は実測とプロファイルに基づく計画値を含むため、全ての候補を実際に同時起動した証拠とは区別すべきである。

本研究の教訓は、マルチモーダルアプリケーションでは**最も遅い段階の最適化と、ユーザーが何を最初に見られるか**が重要であり、LLMのtoken/sだけではエンドツーエンド体験を評価できないという点である。GPU配置・内容並列・画質適応を組み合わせ、TTFF、継続再生、費用、画質を別々に測る必要がある。
