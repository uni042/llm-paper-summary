# NCCL EP: Towards a Unified Expert Parallel Communication API for NCCL

## 概要
MoEではtokenを選択expertのあるGPUへ送るdispatchと、expert出力を元のtoken順へ戻すcombineが必要になる。通信は不規則なall-to-allで、復号の小batchでは固定遅延、プリフィルの大batchでは帯域利用率が重要になる。

NCCL EPは専用MoE通信libraryで行われてきたGPU起点RDMAをNCCL Device API上へ構築し、ncclEpDispatchとncclEpCombineへ統一する。低遅延（LL）と高処理量（HT）の二モードを持ち、同じAPIで推論段階に合わせて通信アルゴリズムを変える。

## 問題設定
通常のcollective APIは規則的な通信に強いが、MoE routingでは各rankから送るtoken数と宛先が入力ごとに変わる。CPU制御へ戻るたびに小batch復号の遅延が増える。

一方、大batchを低遅延用の直接meshで送ると多数の小messageが帯域を使い切れない。復号とプリフィル/学習では最適な通信形が異なる。

## 手法
### 統一dispatch/combine API
長寿命のncclEpGroupがexpert数、rank、最大token数、mode等を保持する。各forward passではroutingのtop-k indexから一時的ncclEpHandleを作り、対応するdispatchとcombineで同じrouting状態を共有する。

### LLモード
1〜128 token程度の小batchを想定し、GPU起点でRDMAとNVLinkの直接all-to-all meshを使う。dispatchとcombineのbufferを二重化し、一方を通信中に他方を準備して固定待ち時間を隠す。

### HTモード
4096 token以上の大batchでは、まずNVLink domain内でtokenを集約し、node間へ送るmessageを大きくしてRDMA帯域を使う。node到着後に必要rankへ分配する階層構造である。

### NCCL Device API
GPU kernelから通信を起動し、NCCLのトポロジ認識とGPU-Initiated NetworkingのPUT/GET、Wait/Signalを利用する。CPU round-tripを避けながらNCCLの既存platform対応へ乗せる。

## 評価条件
|項目|内容|
|---|---|
|GPU|NVIDIA H100 cluster|
|通信|NVLink + multi-node RDMA|
|LL workload|約1〜128 token|
|HT workload|約4096 token以上|
|統合|vLLM、Megatron-LM系|
|指標|dispatch/combine kernel性能、端から端まで推論|

## 主要結果
論文はH100 multi-nodeでLL kernelが既存専用MoE通信実装に対して競争力ある性能を示し、vLLMへ統合した端から端までの結果も提示する。重要なのは単一kernelの最高値より、LLとHTを別libraryへ分けず同じNCCL API/資源管理モデルで扱える点である。

LLでは小messageの遅延を、HTでは階層集約による帯域利用を最適化するため、同じMoE dispatchでもbatch規模に応じて律速へ合わせた経路を選ぶ。

## 既存研究との差
DeepEP等の専用libraryが示したGPU起点MoE通信を、NCCL Device API上の正式なdispatch/combine抽象へ持ち込む。専用network stackを別管理する代わりに、NCCLのトポロジ認識と現行/将来NVIDIA platformへの対応を再利用する。

## 限界
主対象はNVIDIA GPU/NCCL環境であり、異種acceleratorやNCCL外network stackには直接適用できない。LL/HTの境界はworkloadとcluster topologyで変わり、1〜128/4096+は代表領域であって普遍的閾値ではない。通信libraryの研究なのでexpert計算自体やrouting品質は改善しない。
