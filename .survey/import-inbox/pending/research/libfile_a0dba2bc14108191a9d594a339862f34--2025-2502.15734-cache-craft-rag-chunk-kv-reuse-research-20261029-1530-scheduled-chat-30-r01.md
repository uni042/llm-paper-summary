# Cache-Craft：RAGの文書断片KVを文脈変化に応じて修復・再利用する

## 概要

検索拡張生成（RAG）では、利用者の質問に応じて文書を断片単位で検索し、複数断片をプロンプトへ連結して大規模言語モデルへ渡す。同じ知識ベースを使う多数の要求では、人気の断片が繰り返し取得される。しかし質問ごとに断片の組合せと並び順が変わるため、同じ先頭トークン列だけを共有するprefix cacheでは、その再利用機会を十分に活用できない。

Cache-Craftは、各文書断片を処理したときのKVキャッシュを独立した再利用対象として管理し、先行文脈が変わった場合の影響を推定する。再利用が安全でない断片を無条件に流用するのではなく、過去の注意量、先行断片の一致と順序、断片内部への注意量を使い、必要なトークンのKVだけを再計算して補正する。質問が注目しない断片では、途中層から再計算を止める仕組みもある。さらに複数の文脈で作られた同じ断片のKV変種を管理し、再利用可能性の高いものを残す。

LLaMA-3-8Bと70Bを使った実運用RAGトレースでは、prefix cache比でGPUの冗長計算を51%削減し、連続バッチ条件でスループット約1.6倍、応答遅延約2倍の改善を報告した。これは全トークンを厳密に再計算した場合と完全に同じ回答を保証する結果ではない。論文では、再計算を30%に制限した条件で、完全再計算を基準とするROUGE F1の約90%を維持したと説明している。速度と品質を同時に評価する必要がある。

## 問題設定と観測

RAGの推論では、検索した断片を大量に含む入力のprefillが高価になる。著者らの企業向けシステムSys-Xでは、入力トークンの多くを検索断片が占め、prefillは全体推論時間の約55.4%、Sys-Yでは約76%を占める。別の実験ではLLaMA-3-70Bの長いプロンプトでprefill時間が大きく増える。出力が短くても、入力の注意計算を毎回やり直すと最初のトークンまでの時間が支配的になる。

Sys-Xでは過去に処理済みの断片が繰り返し現れ、著者らは月間120億トークン超の再処理を観測した。一方、先頭から完全に一致するprefix cacheの対象は要求のごく一部であり、実運用では要求の8%、prefillトークンの18%程度にとどまった。断片単体なら再利用される頻度が高いのに、断片の組合せと順序を一つのキャッシュ鍵にすると、可能な組合せが爆発してヒットしにくくなる。

ただし文書断片のKVは、その断片だけから計算されるわけではない。因果注意によって断片内のトークンは、それより前に置かれた断片へも注意を向ける。同じ断片Cを異なる先行断片の後ろへ置いた場合、KVが変わり得る。位置埋め込みを調整するだけでは、先行文脈に依存して形成された内容表現を復元できない。Cache-Craftの課題は、どの断片を再利用し、どの部分を再計算すれば回答品質の低下を抑えられるかを推定することである。

## 手法

### 1. 文書断片と先行文脈を持つKV変種を保存する

Cache-Craftは、ある文書断片を以前の要求で処理したときのKVを、そのときの先行断片情報、注意量の統計、再利用頻度などのメタデータとともに保存する。同じ文書断片でも先行文脈が異なるとKVが異なるため、必要に応じて複数の変種を持つ。新しい質問で断片を検索したら、既存の変種のうち新しい先行文脈と最も相性が良いものを選ぶ。

これは検索文書の埋め込みキャッシュではなく、Transformer各層の注意計算で得られた鍵・値の状態を再利用する仕組みである。出力トークンのdecode時に使う通常のKVキャッシュとは用途が異なり、入力のprefillを短縮するために、過去の要求で形成された断片KVを現在の入力へ組み込む。

### 2. 先行文脈の一致度と順序差を評価する

著者らは、断片内部への注意の総量（intra-attention）と、先行断片から現在断片へ流れる注意の総量（inter-attention）を計算する。過去の先行断片と今回の先行断片がどの程度共通するかを、inter-attentionで重み付けした重複得点βとして定義する。単に共通断片の個数を数えるのではなく、以前のKV形成へ強く影響した断片が今回も存在するかを評価する。

さらに、同じ断片集合があっても順序が変われば因果注意の条件が異なる。そこで共通する先行断片の並びの差を、正規化したKendallの順位距離γで測り、βに(1−γ)を掛けた補正一致度β'を得る。共通する断片が多く、順序も近い場合は再利用しやすく、同じ集合でも順序が大きく変われば修復が必要になりやすい。検索順位をキャッシュに合わせて変更するのではなく、検索結果の順序を保ったままKVを修復する方針である。

### 3. Cache Context Impactで外部依存を測る

断片のKVがどの程度先行文脈へ依存するかを、外部への注意量と断片内部への注意量の比から測る。断片長による尺度の違いを補正し、層ごとの値を集計して、シグモイド変換したCache Context Impact（CCI）を作る。CCIが低ければ、断片は主に内部トークン同士の関係で表現されており、先行文脈が変わっても比較的再利用しやすい。CCIが高ければ過去の先行断片の影響が強く、今回の文脈と一致しないと品質低下が起こりやすい。

CCIだけで再利用可否を決めるのではなく、先行文脈の不一致度(1−β')と組み合わせる。文脈が強く依存していても先行断片がほぼ同じなら再計算量を減らせる一方、外部依存が小さい断片なら先行文脈が異なっても再利用可能性がある。これにより、断片単位で必要な修復費用を予測する。

### 4. 修復費用を見積もり、影響の大きいトークンだけ再計算する

Cache Fix Overhead（CFO）は、係数α、CCI、(1−β')の積で、断片のどの程度のトークンを再計算するかを決める。係数αは検証データ上で目標ROUGE F1を満たす範囲で再計算量が最小になるよう調整する。つまりαは普遍的な定数ではなく、許容する品質低下とワークロードに依存する。

再計算するトークンは無作為に選ばず、過去の先行断片からのinter-attentionが大きいものを優先する。CFOと断片長から再計算トークン数を決め、外部文脈に最も影響されたトークンのKVを現在の先行文脈で再構築する。残りのトークンのKVは保存済みのものを利用する。これにより、全トークンを再計算するよりGPU計算を節約しつつ、何も修復しない場合の品質劣化を減らす。

### 5. 質問が注目しない断片では途中層で修復を打ち切る

RAGでは、検索した断片すべてが最終回答に等しく寄与するわけではない。Cache-Craftは各層で質問から断片へ向かう注意を累積し、上位の注目断片集合が一定層数にわたり変わらなくなったら、それ以外の断片のKV再計算を打ち切る。LLaMA-3-8Bでは約80%の質問で10〜15層の間に注目断片を識別できたと報告する。

この早期終了は、文書断片の再利用を単に多くするだけでなく、修復に必要な計算を層方向にも削減する仕組みである。ただし質問と文書の関連性を注意量から推定するため、重要な断片が後段で初めて効く場合には誤って修復を打ち切る可能性がある。品質の検証を伴う調整が必要になる。

### 6. 変種の置換とGPU・CPU・SSD階層管理

同じ断片を複数文脈で保存するとキャッシュ容量が増える。Cache-Craftは、利用頻度だけでなくCFOで補正した再利用の有効性を重視して変種の優先度を更新し、保存枠が不足したら再利用効率の低い変種を追い出す。単純なLRUやLFUでは、頻繁にアクセスされても毎回大量の修復が必要な変種を過大評価するためである。

実装はvLLMへ統合され、GPU上のキャッシュ容量だけでなく、CPUやSSDへの保存と事前読み込みを扱う。キャッシュの転送がprefillの計算節約を上回ると逆効果になるため、階層からのロードを可能な範囲で重ねる。修復したKVは生成用キャッシュへ注入し、元の保存済み変種が新しい文脈で汚染されないよう扱う。ここまでを通じて、検索→変種選択→必要トークン修復→生成→保存・置換という要求単位の流れが成立する。

## 評価条件と結果

著者らは企業向けRAGのSys-XとSys-Y、公開RAGデータセット、LLaMA-3-8B/70Bを用いる。vLLMの連続バッチ実験では、8BをA100-80GB一台、70BをA100-80GB四台で実行した。品質はROUGE F1と人手による回答判定、性能はprefill計算量、TTFT、スループット、応答遅延などを使う。再計算割合は条件によって異なり、すべての実験が30%固定ではない。

| 比較・条件 | Cache-Craftの結果 | 解釈上の注意 |
|---|---|---|
| Sys-Xの冗長GPU計算 | prefix caching比51%削減、全再計算比75%削減 | キャッシュの命中・修復割合に依存 |
| 連続バッチ、LLaMA-3-8B/70B | prefix caching比スループット約1.6倍、応答遅延約2倍改善 | 実運用トレースとA100構成での値 |
| Sys-X、20%トークン再計算 | ROUGE約0.87、全キャッシュ無修復では約0.59 | 品質を犠牲にした完全再利用より高品質 |
| 2WikiMQA、30%再計算 | ROUGE F1 89.3%、Lingua2 32.1%、MapReduce 53.0% | 文脈を捨てる圧縮方式との比較 |
| SQuAD、30%再計算 | ROUGE F1 93.6%、Lingua2 45.2%、MapReduce 63.6% | トークン削除とKV再利用は処理内容が異なる |
| 人手評価、2WikiMQA | Cache-Craft 71.2%、無修復キャッシュ29.8%、全再計算76.9% | 250参加者を用いた評価 |
| 人手評価、SQuAD | Cache-Craft 78.9%、無修復キャッシュ53.1%、全再計算83.7% | 全再計算に完全一致したわけではない |

人手評価では、無修復のKVを再利用すると、2WikiMQAで約30%、SQuADで約53%の回答しか妥当と判断されなかった。Cache-Craftはそれぞれ約71%、79%まで回復するが、全再計算の約77%、84%にはなお及ばない。つまり本手法は厳密に同じ出力を保つキャッシュではなく、少量の再計算によって実用的な品質に近づける近似的再利用である。

性能についても、要求の到着率、バッチサイズ、入力長、検索断片の再利用率が大きく効く。論文ではSys-Xの連続バッチ実験で負荷別の速度向上を示し、さらに8B/70BでTTFT短縮の感度を評価する。長いprefillほど再利用の恩恵が大きい一方、断片の再登場が少ない新規知識ベースでは保存・探索・ロードの費用に見合わない可能性がある。

## 既存研究との差

RadixAttentionなどのprefix cachingは、同一の先頭トークン列を安全に共有できるため、基本的に再計算なしで品質を保ちやすい。しかしRAGでは検索断片の組合せが変わるため、同じ断片が後方に現れても再利用できない。Cache-Craftは断片単位のKVを先行文脈とともに管理し、文脈が変わった場合だけ一部を修復する点で異なる。

また、Lingua2やMapReduceなどのプロンプト圧縮は入力テキストを削除・要約することで計算量を減らす。Cache-Craftは元の文書断片トークンを保持しながらKV計算の一部を再利用するため、情報の削除による品質劣化とは異なる交換条件を持つ。Prefill-H2Oのように単純な高注意トークンだけを再計算する方法より、先行文脈の変化と断片への注目を組み合わせる点が特徴である。

## 限界

第一に、保存済みKVの外部文脈依存度を注意量から推定しており、実際の回答に重要な情報を完全に識別できる保証はない。無修復再利用より品質は改善しても、全再計算の人手評価へ完全には届かない。第二に、αの調整には品質目標を持つ検証データが必要で、未知ドメインへ移した場合は再調整が必要になり得る。第三に、人気の文書断片が繰り返し取得されるワークロードを主対象とするため、毎回ほぼ新規の断片しか来ない用途では再利用機会が減る。

第四に、断片KVを文脈ごとに複数保存するため、キャッシュの容量・索引・転送が増える。GPUメモリ不足でCPUやSSDから毎回大きなKVをロードする場合、計算節約が転送待ちに相殺される可能性がある。第五に、評価は指定されたLLaMA-3モデル、A100、RAGデータ、vLLM実装に依存し、すべての注意機構・モデルへ同じ速度と品質を保証しない。

最後に、原著は将来のオープンソース化を記しているが、本文から確定した公式コードURLを得られなかった。再現には保存メタデータ、注意統計、KV修復の実装と品質閾値の選定が必要になる。報告された1.6倍などの数値は特定の実運用RAGトレースにおけるシステム性能であり、単一のKV操作のマイクロベンチマーク倍率とは区別すべきである。
