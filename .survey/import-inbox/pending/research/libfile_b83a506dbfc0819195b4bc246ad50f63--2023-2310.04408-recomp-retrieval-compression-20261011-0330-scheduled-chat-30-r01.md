# RECOMP: Improving Retrieval-Augmented LMs with Compression and Selective Augmentation

## 概要

Xu、Shi、ChoiによるRECOMPは、検索拡張言語モデル（Retrieval-Augmented Language Model、RALM）の推論時に、検索した文書をそのままモデルの文脈へ連結する方式を改める。検索文書が長いほどモデルへ渡す入力トークンが増え、事前入力処理（prefill）にかかる計算量とメモリ帯域が増える。さらに、文書の中に回答と無関係な内容が多いと、情報量が増えたのに回答精度が低下することもある。本稿は、検索器が取得した文書集合をクエリに応じた短い自然言語要約へ変換してから、下流の言語モデルへ前置する。名称はRetrieve、Compress、Prependに由来する。

圧縮は単純な字数削減ではない。要約が下流タスクの正解出力に役立つかを学習信号に使う。抽出型圧縮器は文書内の一文を選び、生成型圧縮器は複数文書の情報を統合した短い要約を生成する。どちらも検索文書が役に立たない場合は前置する文脈を減らすことが目標で、生成型は明示的に空文字列を出せる。原著の実験はWikiText-103の言語モデル評価とNatural Questions、TriviaQA、HotpotQAの開放領域質問応答であり、検索文書トークン数とパープレキシティ、完全一致率、F1を比較する。

推論システムとの関係は、重みの量子化やGPUカーネル最適化ではなく、入力系列長の縮小による前処理負担の削減である。原著は文脈トークン数を主要な効率指標とするため、文書量が5%になったという数値をGPU実行時間が20倍速くなったと読み替えてはならない。圧縮器自体の推論・検索・生成費用を含めたエンドツーエンド（end-to-end）の待ち時間や処理率を統一環境で測定した研究でもない。この区別を前提に、入力長最適化と回答品質の交換関係を評価することが本稿の価値である。

## 問題設定と数式

入力を質問または既存文脈x、正解出力をy、検索済みの文書集合をD={d1,...,dN}とする。RECOMPは圧縮器cθを用いてs=cθ(x,D)を求め、下流モデルMへ[s;x]を渡してyを生成させる。下流Mは原則として凍結され、圧縮器側だけを学習する。検索器自体の改善は対象外で、検索文書が与えられることを前提とする。圧縮器の要求は、短いこと、正解生成に有効なこと、元の文書に忠実なことの三つである。

この三条件は必ずしも一致しない。正答に不要な背景を落とすと短くなるが、答えに必要な証拠を落とすと精度が下がる。生成型の要約では、文章が自然でも文書に存在しない事実を補う危険がある。したがって単なる一般要約モデルを使うのではなく、実際に下流モデルへ前置したときの正解尤度または正答率を利用して学習例を選別する。さらに、検索が邪魔な例ではsを空にし、検索結果を使わない選択的拡張（selective augmentation）を可能にする。

トークン効率は、検索文書をそのまま前置した際の追加トークン数に対する、圧縮後の追加トークン数の比で表す。例えば660トークンを36トークンにすれば36/660≈5.45%である。これは「94.5%の追加文脈を削減した」という意味であり、質問本体、少数例プロンプト、生成回答、検索器や圧縮器の計算は分母に入らない。KVキャッシュ量も圧縮された入力部分に対しては削減し得るが、最終的な生成長や圧縮器の内部キャッシュを含めた総量は別途計測が必要である。

## 手法

### 抽出型：正解尤度に基づく文選択

抽出型圧縮器は、入力クエリと検索文書内の各候補文を別々に符号化する二塔型エンコーダである。文とクエリの表現ベクトルの内積を関連度として計算し、上位の文を前置する。初期値にはContrieverの重みを使用し、圧縮器は約1億1000万パラメータである。推論時に大規模下流モデルへ各候補文を何度も投げるのではなく、小型エンコーダが文の順位を決める設計となる。

教師信号は一般的な意味類似度ではない。学習例(x,y)について、検索文書から得た候補文sjをそれぞれ[sj;x]としてMへ入力し、正解yの対数尤度log pM(y|[sj;x])を測る。最も尤度が高い文を正例にし、それより十分悪い候補を負例として選ぶ。負例は現行エンコーダの類似度が高いものから最大5件を選び、正例に対する内積が負例より高くなる対照損失で学習する。原著の損失は、正例の指数類似度を正例と負例の指数類似度の和で割った確率の負対数である。

この構成の意味は、検索器が上位に置いた文章と、実際に言語モデルが正解を出すのに有効な文章を区別することにある。検索器の関連度が高くても、文章が長すぎたり曖昧だったりすれば、回答モデルにとっては有益とは限らない。文単位に分割してタスク寄与を教師にすることで、入力長を減らしつつ正解に必要な情報を残そうとする。原著ではWikiText-103でBM25上位5文書から候補20文、質問応答ではContrieverで検索した上位5文書から候補20文を使い、各文にWikipediaページの題名を添えて文脈を補う。

抽出型は元文書から文をそのまま採るため生成型より虚偽情報を追加しにくいが、単一文が多段の推論根拠を表せない場合や、文の切り出しで指示語の参照先が消える場合は失敗する。また、原著の抽出型は出力文数を固定しており、学習した圧縮器が全例で自動的に空文字を返す仕組みではない。言語モデル・NQ・TriviaQAでは1文、HotpotQAでは2文を前置する。空文字を用いる選択的拡張は主として生成型の実装と分けて理解すべきである。

### 生成型：大規模教師からの蒸留と選択的拡張

生成型圧縮器は、クエリと上位5文書を入力して短い要約を生成するエンコーダ・デコーダであり、T5-largeの初期重みを用いた約7億7500万パラメータのモデルである。大規模教師としてgpt-3.5-turboを用い、複数の要約指示を与えて候補要約を作る。言語モデル評価では四種類の指示文を使用し、質問応答ではタスクごとに一種類の指示文を用いる。教師が出した文章を無条件に正解とせず、下流モデルMに前置したときの正解尤度または回答成績で候補を評価する。

訓練データを作る際、各候補要約sjをMに渡した成績と、検索文書を一切使わないM(x)の成績を比較する。最良の要約でも検索なしより悪ければ、教師ラベルを空文字にする。そうでなければ最良要約を学習ターゲットにする。この選別により、検索したが回答に役立たない文書を前置しない方策が蒸留される。原著ではWikiText-103の学習データの2%から教師要約を作り、NQとTriviaQAでは学習データを使用し、HotpotQAでは検索文書に正解が含まれる学習例56%に限って教師要約を生成してAPI費用を抑えている。

この学習経路には二つの費用がある。第一に、教師要約生成と候補評価で多数の下流モデル呼び出しが必要となる学習時費用である。第二に、実際の推論時にも圧縮器で上位文書を処理し要約を生成する追加費用である。原著は入力トークン削減を実証するが、後者の遅延を含む全体処理率が一律に向上したことを示していない。小型圧縮器を置く設計理由はこの費用を抑えるためであり、圧縮が常に無料であるという意味ではない。

### 既存方式との差分

比較対象は、検索文書をそのまま連結する方式、単語集合や固有表現だけを残す簡易圧縮、BM25・Contriever・DPRによる文選択、既存T5による一般要約、GPT-3.5要約である。加えて、下流モデルの正解を参照して最も有利な文または要約を選ぶ理想的なオラクルを上限参考として置く。オラクルは実運用時に正解yを知っているわけではないので、達成可能な実システムの速度・精度と同列に扱わない。

単語集合や固有表現だけを連結すると文章の意味的つながりが失われ、短くしても回答精度が落ちる。一般要約は人間が読みやすい文章を作れても、下流モデルが必要とする根拠を選べるとは限らない。RECOMPは「人間にとって良い要約」より「モデルの正解生成に寄与する短い文脈」を優先する。ソフトプロンプトによる非言語的圧縮と異なり、短い自然言語を出力するため、凍結済みの別モデルやAPI型のブラックボックスモデルへ転用しやすい。ただし転用時の正答率まで常に維持されるとは限らない。

## 評価

### 言語モデル：WikiText-103

言語モデルの評価はWikiText-103で行い、GPT-2（1億1700万）、GPT-2-XL（15億）、GPT-J（60億）の三モデルを用いる。圧縮器の学習時にはGPT-2を基準モデルとし、残り二モデルは転用先として評価する。検索にはBM25と2018年12月20日時点のWikipediaを使用し、100語単位の文書へ分割する。入力文脈と同じ記事を検索対象から除き、32トークンごとに検索する。原著表1は、検索証拠として前置する追加トークン数とパープレキシティ（PPL）を比較している。PPLは低いほど良い。

| GPT-2での条件 | 前置トークン数 | PPL | 注意点 |
| --- | ---: | ---: | --- |
| 検索なし | 0 | 37.84 | 言語モデル単体 |
| 上位1文書をそのまま前置 | 141 | 32.90 | 非圧縮の主要比較 |
| 上位5文書をそのまま前置 | 512 | 35.53 | 情報増加で逆に悪化 |
| 抽出型RECOMP | 31 | 33.67 | 一文を選択。上位1文書よりPPLが高い |
| 生成型RECOMP | 15 | 33.64 | 平均的な追加トークンが非常に少ない |
| 抽出型オラクル | 32 | 30.36 | 正解を参照した上限であり実運用不可 |
| 生成型オラクル | 68 | 30.67 | 同上 |

重要な負の結果は、GPT-2で非圧縮の上位1文書を使うPPL 32.90に対し、学習済み抽出型が33.67、生成型が33.64で、同じ品質を完全に維持したわけではないことである。代わりに追加文脈は141から31または15トークンに減る。上位5文書をそのまま入れるとPPLが35.53へ悪化するため、検索文書の量と品質は単調な関係ではない。GPT-2-XLでは生成型が15トークンでPPL 18.09、GPT-Jでは同じく15トークンで10.66となり、基準モデル以外にも転用できる傾向を示す。ただしオラクルとの隔たりは残る。

原著は抽出型が上位1文書比で約25%の文脈量、生成型がさらに少ない文脈量を実現したと述べる。生成型は必要なときだけ要約を前置し、言語モデル評価の約33%の例にだけ要約を付ける。空要約の存在が平均トークン数を押し下げるため、「毎回15トークンの要約を生成する」と解釈してはいけない。実際には空の例と非空の例が混在する。

### 開放領域質問応答：NQ・TriviaQA・HotpotQA

質問応答の下流モデルはFlan-UL2（200億パラメータ）で、Natural Questions（NQ）の開発集合、TriviaQAのテスト集合、HotpotQAの開発集合から無作為抽出した500例を評価する。検索器はMS MARCOで学習したContriever、コーパスはWikipediaである。質問前には5例の少数例プロンプトを置き、その平均長はNQ 110、TriviaQA 147、HotpotQA 149トークンである。表2の「前置トークン数」はこの少数例部分を含まず、検索文書に由来する追加部分のみを数える。

| 条件 | NQ 追加トークン / EM | TriviaQA 追加トークン / EM | HotpotQA 追加トークン / EM |
| --- | --- | --- | --- |
| 検索なし | 0 / 21.99 | 0 / 49.33 | 0 / 17.80 |
| 上位5文書をそのまま前置 | 660 / 39.39 | 677 / 62.37 | 684 / 32.80 |
| 抽出型RECOMP | 37 / 36.57 | 38 / 58.99 | 75 / 30.40 |
| 生成型RECOMP | 36 / 37.04 | 32 / 58.68 | 64 / 28.20 |
| 抽出型オラクル | 34 / 60.22 | 32 / 79.29 | 70 / 41.80 |

NQでは生成型が660から36トークンへ、約5.45%まで文脈を減らし、EMは39.39から37.04へ2.35ポイント低下する。TriviaQAでは677から32トークンへ約4.73%となり、EMは62.37から58.68へ3.69ポイント低下する。HotpotQAでは抽出型が684から75トークンへ約10.96%となり、EMは32.80から30.40へ2.40ポイント低下する。生成型はHotpotQAで28.20と抽出型より低く、複数文書にまたがる根拠の統合が難しいことを示す。これらは絶対的なEMポイント差であり、「2%の相対誤差」と表現しない。

F1でも原著表2は、NQの上位5文書48.28に対し抽出型44.22、生成型45.47、TriviaQAの上位5文書70.09に対し抽出型65.26、生成型66.34、HotpotQAの上位5文書43.90に対し抽出型40.14、生成型37.91を示す。生成型の圧縮率が高いから常に抽出型より正確とは言えない。特に多段推論のHotpotQAでは、短い生成要約が必要な関係を落とす可能性がある。

### 忠実性・転用性と誤答の分析

原著表3は、検索文書に正解がない場合でも、言語モデルが証拠文中の文字列を誤って回答へコピーする問題を分析する。NQで上位5文書をそのまま使うと、正解が証拠にない条件での証拠コピー頻度が81%であるのに対し、学習済み生成型RECOMPは39%と報告する。ただしコピー率だけでは回答の真偽は確定せず、正解が証拠にある場合に引用することはむしろ望ましい。原著は正解が証拠にある場合とない場合を分けて測っている。

表4の手動評価は、各データ集合で非空要約30例を抽出し、忠実性と質問に必要な情報の網羅性を三段階で評価したもの。生成型RECOMPの完全に忠実と判定された割合はNQ 80%、TriviaQA 83%、HotpotQA 67%であり、忠実かつ十分な情報を持つ「有用」割合は順に80%、77%、40%である。GPT-3.5による教師要約の「有用」割合は順に83%、83%、50%で、蒸留後の小型圧縮器は教師より劣る。特にHotpotQAでは非忠実33%と多く、生成要約の幻覚や根拠の欠落を無視できない。

転用性について、GPT-2で学習した圧縮器をGPT-2-XLとGPT-Jへ適用すると、言語モデルのPPLでは一定の有効性がある。一方、Flan-UL2で学習した質問応答用圧縮器をLLaMA-13Bへ移すと、データ集合によっては従来の圧縮基準方式を明確に上回らない。自然言語要約は形式上別モデルへ渡せるが、要約の最適性は下流モデルの知識と推論挙動に依存する。

## 実装上の意義とシステム的な考察

RECOMPが削減するのは、検索で見つけた文書を下流モデルへ読み込ませるときの文脈トークンである。自己回帰型Transformerでは入力長が短いほど前処理段階の注意計算とKV保存対象が減り得るが、圧縮器自体の計算、検索器の費用、生成型要約の復号、圧縮前文書の取得は残る。下流モデルが十分大きく検索文書が長い場合には利益が期待できるが、検索文書が短い場合や圧縮器が大きい場合には前処理節約が追加費用を下回り得る。原著の「6%」や「5%」はトークン量の比であり、エンドツーエンドの速度倍率ではない。

また、単純な文書トークン削減が、全ての質問で高い品質を維持する保証にはならない。質問に対する必要証拠の構造が、単一文で足りるのか複数文書の推論を要するのかで適した圧縮方式が変わる。抽出型は忠実性を維持しやすいが複数文書の統合に弱く、生成型は統合できる一方で根拠の幻覚がある。原著のオラクルが実方式よりかなり高いEMを示すことは、文書集合の中に有用な情報があっても学習済み圧縮器が必ずそれを選べるわけではないことを意味する。

既存のKVキャッシュ圧縮とは対象も処理段階も異なる。KV圧縮はモデルが処理した過去トークンの内部状態を減らすが、RECOMPはモデルへ入力する前に外部文書を短くする。モデルの重みを量子化する方式とも直交するため、理論上は組み合わせられる。ただし組み合わせた実装の性能・品質を原著は測っていない。検索頻度を減らす方式、キャッシュ済み検索結果の再利用、文脈の事前要約との統合も実装上の検討課題である。

## 限界

第一に、主たる効率評価は追加トークン数であり、圧縮器を含む実測のGPUメモリピーク、応答時間、スループット、エネルギー消費の統一比較がない。下流モデルに送る文脈が短いという事実から、システム全体の高速化率を推定することはできない。圧縮器の推論費用と生成型要約の復号費用、検索器の費用を合算した実装評価が必要である。

第二に、抽出型の選択数は固定であり、生成型の空要約は学習時に正解ラベルを使って決めている。実際の運用時に正解を知らない圧縮器が、全ての未知クエリで「検索が不要」を正しく判定できる保証はない。下流モデルが更新された場合や分布が変わった場合は、学習済みの有用性判断が古くなる可能性がある。

第三に、生成型要約の忠実性は完全ではない。手動評価は各集合30例と小規模で、HotpotQAでは忠実と判定された割合が67%、有用割合が40%に留まる。複数の検索文書から関係を組み立てる場合、誤った要約が確信度の高い誤答を誘発し得る。抽出型でも元文脈から文を切り離すと指示語の参照や条件が失われる。

第四に、言語モデルの転用はGPT-2からGPT-2-XL/GPT-Jで一定の成功があるが、質問応答のLLaMA-13Bでは不安定である。圧縮器が一つの下流モデルに最適化されているため、異なるモデル、検索器、コーパス、言語へ移したときの頑健性は未確定である。WikiText-103と英語Wikipedia由来の質問応答だけから、日本語長文、法令、コード、複雑なエージェント処理の品質を一般化できない。

第五に、原著の抽出型オラクルや生成型オラクルは正解yを参照して候補を選ぶため、実サービスにそのまま導入できない。オラクルのPPLやEMは探索余地を示す参考上限であって、RECOMPの実運用性能ではない。今後は、圧縮の追加費用と入力長節約の差、長い生成文におけるKV節約、信頼性を保つための根拠提示、検索結果の鮮度、低資源GPUでの実測を同時に評価すべきである。
