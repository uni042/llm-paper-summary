# The KV Cache Working Set: Online Capacity Planning for LLM Inference Systems

> Mattson stack algorithmでKVページのLRU距離をオンライン追跡し、多数の容量候補のヒット率と目標ヒット率を満たす最小KV working setを一度に推定する。

## 概要

エージェント型ワークロードでは、会話履歴、システムプロンプト、ツール出力が繰り返し入力されるため、prefix cacheがプリフィル計算を大きく削減できる。ただし、過去に作ったKVをすべて保持するには非常に大きなHBM・DRAM・SSD容量が必要になる。一方、容量を削りすぎると必要なprefixが退避され、ヒット率が急落する。

KVSETは「特定ワークロードで目標ヒット率を達成するために最低何ページのKVが必要か」をKVキャッシュの作業集合（working set）として定義し、実行中に推定する。個別のキャッシュサイズごとに同じトレースを何度もシミュレートする代わりに、一つのLRUスタックから複数容量のヒット・ミスを同時に導く。

## 問題設定

従来の容量計画では、例えば100GB、200GB、400GBのキャッシュを別々にシミュレートしてヒット率曲線を作れる。しかし候補容量が多く、要求列が長いオンラインLLMサービングでは計算量とメモリ量が増える。さらにエージェントの会話成長やツール呼び出しで局所性が変化するため、オフラインで一度決めた容量が将来も適切とは限らない。

必要なのは、要求を処理しながら現在の局所性を低オーバーヘッドで測り、例えば「90%ヒット率には何ページ必要か」を継続的に更新する仕組みである。

## 手法

### KVページ単位のMattson stack

KVSETは各KVページへの参照をLRU順序のスタックとして追跡する。あるページが再参照されたとき、そのページより新しく参照された一意ページ数がstack distanceになる。

容量CページのLRUキャッシュを考えると、stack distanceがC未満ならそのアクセスはヒットし、C以上ならミスになる。この性質を使えば、アクセスごとに全容量を独立シミュレーションせず、stack distanceからヒット率曲線を更新できる。

### prefix pageを考慮したworking set

LLMのprefix reuseでは、任意の一ページが残っていればよいわけではない。要求が必要とする接頭辞ページ群が利用可能であることが再利用量を決める。KVSETは目標ヒット率を満たすために必要なprefix pageのLRU深度を集計し、その最大深度から必要容量を求める。

これにより「現在のキャッシュが何%当たったか」だけでなく、「目標を満たすにはあとどれだけ容量を増やすべきか」という容量計画値へ変換する。

### オンラインとオフラインの共通分析

公開実装はオンライン要求を直接処理するモードと、保存済みトレースを再生するモードの双方を持つ。同じ分析器を本番観測と事前容量設計に使えるため、実配備のヒット率曲線と計画時の曲線を比較しやすい。

## 評価

| 項目 | 内容 |
|---|---|
| 入力 | 実運用LLMワークロードから収集したトレース |
| 検証 | 実際のキャッシュ配備で測ったヒット率・必要容量と比較 |
| 主要指標 | 容量ごとのヒット率、目標ヒット率を満たす最小容量、分析オーバーヘッド |
| 結果 | KVSETの推定値は実キャッシュ配備の測定値と近く一致 |
| 実装形態 | オンライン処理とオフライントレース再生をサポート |

この論文の主結果は新しいKV eviction policyのヒット率向上ではない。現在のアクセス局所性に対して「どれだけ置けば十分か」を推定し、過剰なHBM/DRAM/SSD確保と不足による再計算の間を定量化することにある。

## 既存研究との差

一般的なLRUキャッシュは与えられた容量で置換を行うが、KVSETは容量そのものを決める観測器である。prefix cacheの実装を置き換えず、既存のサービングシステムへ容量分析層として組み込める。

また、平均KV使用量やピーク量だけを見る容量計画と異なり、再利用局所性をstack distanceとして測るため、同じ総KV生成量でも再利用パターンが違うワークロードを区別できる。

## 限界・実装状況

推定はLRU型の再利用モデルを中心とするため、コスト認識置換や意味的キャッシュなど別ポリシーへそのまま当てはめるには拡張が必要になる。目標ヒット率自体を何%に設定すべきかは、GPU費用とプリフィル再計算費用を含む上位のSLO・費用モデルが決める必要がある。

## 一般的な実装上の含意

KV階層を設計するとき、容量を「最大同時トークン数」だけで決めるのではなく、実ワークロードの再利用距離分布から決めるべきである。特にエージェント型負荷では履歴が伸びても、再利用されるworking setが同じ割合で伸びるとは限らない。
