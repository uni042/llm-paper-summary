# Simthesizer: An Agent-Driven Simulation Framework for LLM Serving Systems

## 概要
LLM servingはcontinuous batching、prefill/decode分離、agentic workflowなど機構が急速に増え、既存simulatorの固定pipelineへ新機構を足すたび大規模改修が必要になる。Simthesizerは実システムを直接安くする手法ではなく、serving system研究の設計探索を高速化する基盤である。

## 手法
中核simulatorはrequest lifecycle、resource operation、scheduler/control decisionを一つのcomposable dynamic graphとして表現する。新しいserving機構を追加する際、固定されたmonolithic event loopへ特殊caseを埋め込む代わりに、既存componentを組み替えてgraphを拡張する。

Synthesizer agentは自然言語のfeature requestを受け、許可されたcomponent interfaceとguardrailの範囲でコードへloweringする。生成コードはsimulator固有のvalidation harnessでfidelityを検証し、単にcoding agentへrepositoryを自由編集させる方式を避ける。これにより新機構ごとに別simulatorを作らず、同一基盤を進化させる。

## 評価条件
|項目|条件|
|---|---|
|実機基準|vLLM-based serving system|
|比較simulator|LLMServingSim2.0、Vidur等|
|agent条件|同一coding agent/harnessでextension比較|
|指標|throughput誤差、simulation speed、拡張fidelity|

## 主要結果
Simthesizer上でagentが追加したextensionはvLLM実機に対して平均throughput error 2.51%で、既存simulator上へ同条件で追加したextensionの6.03%より小さい。同一workloadのsimulation speedはLLMServingSim2.0比最大284.96倍、Vidur比最大23.19倍だった。したがって高速化だけでなく、新機構追加後の実機追従性も主要な評価対象になっている。

## 既存研究との差
従来simulatorは対象systemのpipelineを人手で固定実装し、feature追加時に内部構造まで変更しやすい。Simthesizerはcontrol decisionを含むserving workflowを共通graphへ上げ、その上でagentに限定interfaceだけを操作させる。coding agentの能力そのものより、agentが安全に変更できるsimulation abstractionを設計した点が差である。

## 限界
実機fidelityはモデル化済みcomponentと校正範囲に依存し、未知のhardware bottleneckをagentが自動的に発見する保証はない。2.51%は評価したvLLM workloadの平均で、任意のdistributed deploymentへ普遍化できない。simulation speedの最大倍率も比較simulator・workload依存である。
