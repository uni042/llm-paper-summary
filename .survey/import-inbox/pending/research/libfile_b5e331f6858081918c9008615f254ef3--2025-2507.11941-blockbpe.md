# BlockBPE: Parallel BPE Tokenization

## 概要

LLMサービングではGPU上のモデル実行だけでなく、入力文字列をtoken ID列へ変換するトークン化も要求ごとに必要になる。既存のHuggingFace TokenizersやtiktokenはCPU向けに高度に最適化されているが、正規表現（Regex）による事前トークン化と、優先度付きキューを用いるBPEマージが中心であり、高バッチ推論ではCPU側がGPUへ入力を供給する速度を制約し得る。論文ではRegex事前処理がtokenization時間の最大75%を占める測定を示し、オンライン小バッチだけでなく大量要求をまとめる高スループット処理ではtokenizer自体をGPUへ移す余地があると問題設定する。

BlockBPEはBPEの語彙・merge tableを維持しつつ、CPUで扱いにくい逐次処理をGPU向けに組み替える。第1にRegex事前トークン化をバイト単位の事前トークン化と特殊token lookupへ置き換える。第2に1入力文字列を1 CUDA blockへ割り当て、隣接token pairのmerge rank探索を多数threadで並列実行する。第3に最小rankのpairを選んだ後、CCCLのブロック単位prefix scanでmerge後のwrite indexを計算し、token列をcompactionする。GPU上のmerge tableにはcuCollectionsの並行hashmapを使う。

この設計では、入力長をn、block sizeをB、各threadがstrideして処理する回数をd=seq_len/block_sizeとすると、blockが入力全体を覆えるd=1付近で最も有利になる。論文はIntel Xeon Platinum 8470とNVIDIA H100 SXM 80GBでGPT-2 tokenizerを使って評価し、高バッチ条件でtiktoken比最大2倍、HuggingFace Tokenizers比最大2.5倍のthroughputを報告する。一方、Regexを外すことはbit-for-bit互換ではない。Llama-3.1-8B-InstructではMMLU、GPQA、AGIEvalのaccuracyは概ね維持するが、数字の分割が重要なGSM8Kでは0.781から0.224へ低下する。この品質劣化はBlockBPEを「そのまま既存tokenizerと置換できる高速kernel」とみなせない重要な制約である。

## 問題設定

通常のBPEでは、入力文字列を初期token列へ分割した後、学習済みmerge tableから隣接pairのrankを調べ、最小rankのpairを順に結合する。素朴実装は各merge passで全隣接pairを走査するためO(n^2)になり得る。CPU実装はRegexで入力をword・number・punctuationなどのまとまりへ分割し、さらに優先度付きキューで次にmergeするpairを管理することでO(n log n)へ改善する。しかしRegexはbacktrackingと分岐が多く、GPUの多数threadへ均等に割り当てにくい。

このCPU中心設計は、1要求あたりの低遅延を重視する小バッチでは合理的でも、数百〜千規模の入力をまとめて処理するbatch inferenceでは別のボトルネックを生む。GPU上のモデル計算が高速化しても、token ID列の生成がCPUに残れば入力供給側のthroughputが追いつかない。論文はvLLMやSGLangのようなサービング基盤がモデル実行を高度に最適化してきた一方、batch tokenizationは相対的に未開拓だと位置付ける。

BlockBPEの狙いは、BPEをGPUへ単純移植することではなく、GPUで並列化しにくいRegexと逐次merge順序を再設計し、batch sizeが大きい領域でCPU tokenizerを上回ることである。ただしRegexが保持していた文字列境界規則を捨てるため、性能改善とtokenization fidelityの間に明示的なトレードオフが生じる。

## 手法

### バイト単位の事前トークン化

入力はUTF-8文字列、BPE vocabulary、特殊token集合である。既存CPU tokenizerはまずRegexで文字列を複数chunkへ切り分けるが、BlockBPEは各byteを直接初期tokenへ変換する。BOS/EOSなどモデル固有の特殊tokenについては別lookupを行い、単純なbyte splitで壊さないようにする。論文の実装ではこの段階をRustで実装し、byte列の走査とhashmap lookupへ処理を落としている。

この変更の利点は、深い分岐やbacktrackingを伴うRegex処理を外し、入力長に対して単純な処理へ変えられる点にある。論文の測定ではRegex事前処理が全tokenization時間の最大75%を占め、byte-level方式はこの事前処理部分で最大3倍高速である。一方でRegexが暗黙に保持していた数字・句読点・反復記号の境界は失われるため、後段BPEが同じmerge tableを使っても最終token列がCPU参照実装と一致しない場合がある。

### GPUブロック内の並列merge pass

各入力文字列に1 CUDA blockを割り当てる。thread iは現在のtoken iとi+1を読み、merge table Mからpairのrankをlookupする。各threadが得たrankからblock-wide reductionで最小rankを求め、そのrankに該当する位置をmerge対象としてmarkする。逐次CPU実装のように1 pairずつpriority queueから取り出すのではなく、pair評価を同一block内で並列に進めることが中心である。

merge後はtoken数が減るため、残存tokenのwrite位置を再計算する必要がある。BlockBPEはmergeされた位置を0/1でmarkし、CCCLのexclusive prefix sumを使ってcompaction後のindexを計算する。これにより、merge pairより右側のtokenを1つ左へ詰める処理をblock内並列scanとして実行する。merge rank lookupにはcuCollectionsのGPU常駐concurrent hashmapを利用する。

1 block = 1 stringとした理由は、block内threadなら同期が比較的安価で、複数blockをcooperative groupsで同期する設計を避けられるためである。入力長がblock size以下なら各threadがほぼ1位置を担当できるが、入力が長い場合はthread coarseningで1 threadが複数byteをstrideして処理する。

### 計算量とblock sizeの選択

理想化して入力長nに対しn threadを割り当てられれば、1 merge passのpair評価と最小値探索を並列化でき、全体をO(n)に近づけられる。実際のGPUでは1 blockあたりthread数に上限があり、論文ではd=seq_len/block_sizeとして、長い入力では各threadがd回strideするためO(nd)と整理する。d=1、すなわちblockが入力列をほぼ覆える場合が最も有利である。

ただしblockを大きくすると1文字列内部の並列性は増える一方、同時にresidentにできるblock数が減る。H100は最大block size 1024 threadで、論文は1024-thread blockなら114 SMに対応してbatch 114程度、256-thread blockなら1 SMあたりより多くのblockを置けるため最大528程度までbatchを増やせると説明する。このため小batch・長sequenceでは大きなblock、大batch・短sequenceでは小さなblockが有利になる。

## 主要結果

| 条件 | 指標 | 比較対象 | BlockBPE | 読み取れること |
|---|---|---|---|---|
| 高batch推論 | tokenization throughput | tiktoken | 最大2倍 | CPU tokenizerが入力供給の律速になる領域でGPU化が有効 |
| 高batch推論 | tokenization throughput | HuggingFace Tokenizers | 最大2.5倍 | Rust CPU実装より高いbatch並列性を利用できる |
| 小batch・長sequence（64×2048/4096） | merge time | block 256/512/1024 | block 1024が有利 | 1文字列内部の並列性を増やす方が効く |
| 大batch・短sequence（1024×128/256） | merge time | block 256/512/1024 | block 256が有利 | 小blockで同時resident block数を増やす方が効く |
| MMLU | accuracy | HF 0.692±0.018 | 0.681±0.018 | 一般言語taskでは品質差が小さい |
| GPQA | accuracy | HF 0.295±0.022 | 0.295±0.022 | token列similarity 0.989でもaccuracyは維持 |
| AGIEval | accuracy | HF 0.410±0.044 | 0.410±0.044 | 一般試験taskでは差が見られない |
| GSM8K | accuracy | HF 0.781±0.012 | 0.224±0.013 | 数字境界の違いが推論品質を大幅に破壊する |

throughputの利得は全条件で一様ではない。論文はbatch 256〜1024の高batch条件でBlockBPEが優位になると報告する一方、block sizeとsequence lengthの不一致ではthreadがstrideする回数dが増え、長sequenceほどruntimeが悪化する。したがって「GPU tokenizerなら常にCPUより速い」という結果ではなく、batch並列性を十分に使えるサービング条件が前提である。

品質面の結果はさらに重要である。MMLUではtoken列similarity 0.999でaccuracyが0.692から0.681へわずかに低下し、GPQAとAGIEvalは報告値上同一accuracyだった。しかしGSM8Kではsimilarity自体は0.989と高いにもかかわらず、accuracyが0.781から0.224へ落ちる。これは平均的なtoken一致率だけでは下流品質を保証できず、数字の境界のような少数の体系的な不一致が推論結果へ大きく影響することを示す。

## 既存研究との差

HuggingFace TokenizersとtiktokenはCPU上でRegex事前分割と効率的なBPE処理を行い、既存モデルのtokenizer規則との互換性を重視する。BlockBPEはこの互換性を完全には維持せず、Regexをbyte-level処理へ置き換えることでGPUで扱いやすい規則へ変更する。そのため新規性は単なるCUDA移植ではなく、「事前分割規則を簡略化してでもbatch throughputを取る」という設計判断と、BPE mergeをblock reduction・prefix scan・GPU hashmapへ分解した点にある。

NVIDIA cuDFにはGPU上のWordPiece tokenizationが存在するが、論文時点では完全なBPE pipelineではなく、文字列変換からtoken ID lookup、tensor出力までを一貫して提供するものではない。BlockBPEはdecoder-only LLMで一般的なBPEを対象に、tokenization pipeline全体をGPU batch inferenceへ接続することを狙う。

vLLMやSGLangなどの推論基盤はKVキャッシュ管理、batching、model executionを最適化してきたが、BlockBPEはその前段のtokenizerを対象にする。論文はこれらのserving engineへの統合を将来課題としており、報告されたtokenizer単体のthroughput改善を、そのままvLLM/SGLangのend-to-end throughput改善と解釈してはいけない。

## 限界

最大の制約はtokenization互換性である。Regexを除くため、`....` や `1000` のような入力で参照tokenizerと異なる分割が生じる。特にGSM8Kで56 percentage point超のaccuracy低下が出ており、数学・数値・構造化文字列を多く扱うサービスへそのまま適用するのは危険である。論文は代替事前トークン化方式の検討、またはbyte-level事前トークン化をpre-training時から使うことを将来方向として挙げる。

性能も高batch向けに偏っている。1 stringを1 blockへ割り当てるため、batchが小さいとGPU全体の並列性を埋めにくい。逆にsequenceがblock sizeを大きく超えると各threadのstride回数dが増え、merge passが遅くなる。block sizeを増やすと1文字列は速くなるがresident block数が減るため、batch並列性とのトレードオフがある。

評価はtokenizer microbenchmarkと下流task品質が中心であり、TensorRT-LLM、vLLM、SGLangへ統合したend-to-endサービングの初回トークン時間（Time To First Token; TTFT）やrequest throughputは未評価である。論文自身もこれらruntimeへの統合には大きなarchitecture変更が必要として将来課題に置く。したがって、tokenization単体で2〜2.5倍という値をLLMサービング全体の高速化倍率として扱うことはできない。
