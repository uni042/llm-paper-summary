# A Survey on Efficient Inference for Large Language Models

## 概要
本論文は大規模言語モデル（LLM）の推論効率化を、個別技法の羅列ではなく「なぜ遅いか」と「どの層で直すか」の二段構造で整理する。根本原因を巨大なモデルサイズ、系列長に対して二乗に増える自己注意、逐次的な自己回帰復号へ分け、それぞれが計算量、メモリアクセス量、メモリ容量を通じてlatency、throughput、storage、energyへ波及すると整理する。

対策taxonomyはデータ層、モデル層、システム層の3階層である。データ層はprompt/output token数や復号回数を減らし、モデル層は量子化・枝刈り・蒸留・効率的構造で1 token当たりの計算とweight/KVを減らし、システム層はoperator、memory management、batching、scheduling、distributed servingで同じモデルを効率よく実行する。既存surveyとの差は3層を同時に覆うだけでなく、代表的手法・frameworkを同一hardwareで比較する実験を含む点にある。

## 問題設定
70BモデルをFP16で保持するだけで140GBのVRAMを必要とし、論文の例では少なくとも24GB RTX 3090Tiを6基、または80GB A100を2基必要とする。2×A100でも1 token生成が約100msという例を挙げ、単にFLOPSを増やすだけではweight/KVのmemory trafficと自己回帰の逐次性を解消できないとする。

prefillはprompt全体を並列処理するため大きなGEMMを形成しやすい一方、decodeは各stepが小さくmemory-boundになりやすい。さらにrequestごとに出力長が異なるため、servingではKV cacheの断片化、batch内の終了時刻差、head-of-line blockingが追加される。論文はこの違いを、algorithmだけでなくruntimeを別階層として整理する根拠にする。

## 分類体系

### データ層
入力圧縮、出力組立、投機的復号など、モデル内部を大きく変更せず処理token数や対象モデルのforward回数を減らす。投機的復号では小型draftが複数tokenを提案し、target modelがまとめて検証するため、受理率が高いほど自己回帰step数を減らせる。一方、draft overheadと受理率が交換条件になる。

### モデル層
量子化、枝刈り、低ランク分解、知識蒸留、MoE、線形/疎注意、状態空間モデルなどを扱う。例えば低ランク分解はweight matrixを小さな行列積へ置換し、decodeで必要なweight trafficを減らす。論文はLoRDの16B→12.3B圧縮、SVD-LLMのwhiteningとlayer-wise recoveryなど、同じ「低ランク」でも誤差補償法が異なることまで分類する。

### システム層
operator/graph最適化、KV memory management、continuous batching、scheduling、分散prefill-decode分離を扱う。vLLMはKVをpageへ分割し、連続した巨大領域をrequestごとに予約せず物理blockへ動的mapする。LightLLMはtoken単位へさらに細粒度化する。Sarathi系は長いprefillをchunk化してdecode requestと混ぜ、iterationごとの負荷差を抑える。

分散系ではSplitwise、TetriInfer、DistServeがprefillとdecodeを別resourceへ分離する。これはprefillがcompute-oriented、decodeがmemory-orientedという性質差を、異なるhardware poolやschedulerで利用する発想として位置付けられる。

## 評価条件

| 項目 | 条件 |
|---|---|
| hardware | 単一NVIDIA A100 80GB |
| inference model | Llama2-7B |
| inference workload | batch 1、input 1K、output 128 |
| serving workload | ShareGPT |
| inference engines | HuggingFace、DeepSpeed、vLLM、OpenPPL、FlashDecoding++、LightLLM、TensorRT-LLM |
| serving指標 | 最大request throughput |
| speculative decoding | engine比較では無効化 |

## 主要結果

| framework | 単発推論 token/s | serving req/s | 主なsystem特性 |
|---|---:|---:|---|
| HuggingFace | 38.963 | — | 基準的実装 |
| DeepSpeed | 80.947 | 6.78 | blocked KV、split-and-fuse、decode優先 |
| vLLM | 90.052 | 7.11 | paged KV、continuous batching、prefill優先 |
| FlashDecoding++ | 106.636 | — | operator/graph/speculative対応 |
| LightLLM | 73.599 | 10.29 | token-wise KV、split-and-fuse |
| TensorRT-LLM | 92.512 | 5.87 | paged KV、continuous batching |

単発推論ではoperator/graphを強く最適化したFlashDecoding++とTensorRT-LLMが上位だが、servingではLightLLMが最大request throughputを得る。この違いは「1 requestのtoken/s」と「非同期request群のreq/s」が同じ最適化問題ではないことを示す。vLLM等のpaged memoryとcontinuous batchingはfragmentationとbatch occupancyを改善する一方、paged KVは不規則memory accessを生むため、PagedAttention/FlashInferのようなlayout-aware kernelが必要になる。

## 知見と既存surveyとの差
既存surveyの多くはcompression、model architecture、MLSysの一部など特定階層へ重点を置く。本論文はdata/model/systemを一つのtaxonomyへ統合し、さらに量子化やserving engineの実測比較を付ける。これにより「理論上memoryを減らす技法」と「実機throughputを上げるruntime」を同じ効率化として混同しにくい。

また、system-level optimizationは原理的にmodel accuracyを変えず適用しやすい一方、実運用ではJCT、throughput、fairnessなど複数目的が衝突すると指摘する。出力長予測を使うschedulerも予測精度が十分でなく、今後の改善余地として挙げる。

## 限界
surveyの比較実験は単一A100 80GB、Llama2-7B中心であり、multi-GPU、70B級、MoE、長文脈でframework順位が同じとは限らない。2024年前半までのsnapshotであるため、後発のdisaggregated servingや新しいattention kernelは継続更新が必要である。また異なるframeworkは内部kernelやdefault設定が異なり、表の数値を各frameworkの普遍的な性能順位と読むべきではない。
