# Strata: Hierarchical Context Caching for Long Context Language Model Serving

## 書誌情報
- 著者: Zhiqiang Xie, Ziyi Xu, Mark Zhao, Yuwei An, Vikram Sharma Mailthody, Scott Mahlke, Michael Garland, Christos Kozyrakis
- canonical identity: `arXiv:2508.18572`
- 公開: 2025-08-26
- 一次資料: https://arxiv.org/abs/2508.18572

## 概要

長文脈サービングでは、過去の接頭辞や会話履歴の鍵・値キャッシュ（KV cache）を再利用すると高価なプリフィル（prefill）の再計算を避けられる。しかしGPUの高帯域メモリ（HBM）だけでは容量が足りず、CPUメモリやSSDへ退避したKVを要求時に戻す階層キャッシュが必要になる。Strataが狙うのは「容量を増やす」こと自体ではなく、下位階層に置いたキャッシュを再利用するときの転送が新たなボトルネックになる問題である。

既存のページ化注意（PagedAttention）はGPU内の断片化を抑えるためKVを小ページへ分割するが、そのままCPU–GPU転送すると数KB級の小さなDMAが大量発生し、PCIe/NVLink帯域を使い切れない。論文では8,192 token分のKVをpage size 32で転送したときPCIe 5.0理論帯域の約22%しか使えず、Grace-Hopperではピーク帯域が高いぶん利用率が約5%まで落ちる例を示す。単純にページを大きくすると転送効率は上がるが、ShareGPTでは最大page sizeで平均TTFTが最大2倍、P90 TTFTが2.9倍に悪化し、キャッシュ一致粒度との交換条件が生じる。

Strataはこの矛盾を、GPU支援I/Oとキャッシュ認識スケジューリングの二層で解く。GPU支援I/OはCUDA kernelの多数threadに小さなKV断片のコピーを担当させ、GPU上のlayer-first配置とCPU/SSD側の転送向け配置をコピー中に変換する。スケジューラはCPU–GPU帯域も一級資源として扱い、KV読込時間を隠せるだけのprefill計算を同じバッチへ組み合わせ、隠し切れないI/O待ちにはdecode等の補完タスクを差し込む。

## 問題設定

階層KVキャッシュでは「再計算を避けたから速い」とは限らない。長いキャッシュをCPUから戻し、新規入力tokenが少ない要求では、layer N+1のKV転送をlayer Nのprefill計算で隠す従来の重畳方式が破綻する。論文のLooGLEプロファイルではSGLangのCPU offload条件でprefill時間の74%がKV転送待ちとなり、throughputが最大4倍低下した。I/O自体を最適化してもstallが最大24%残るため、転送機構だけでなくrequest batchingまで変える必要がある。

さらに、同じcache missを待っている要求が複数あると、最初のmissが解決する前に同じ接頭辞を再計算する「遅延ヒット（delay hit）」が起きる。非同期schedulerは次batchを現在batch実行中に準備するため、この窓をさらに長くする。Strataはキャッシュの所在、転送量、prefill計算量、decode作業を一緒に見て、I/O待ちを別の有用なGPU仕事へ置き換えることを目標にする。

## 手法

### 1. GPU支援I/O

通常の `cudaMemcpyAsync` をページごとに繰り返す代わりに、専用CUDA kernelを起動し、多数のthreadがsourceから小chunkをregisterへ読み、destinationへ書く。GPU側の細粒度は128 byte程度まで扱えるため、KV pageを大きくしてcache hit率を犠牲にせず転送並列度を増やせる。

ただしI/O kernelもSMやregisterを使うため、推論kernelと資源競合する。Strataは少数の大きなCUDA blockだけを割り当て、hardware schedulerにI/Oを少数SMへ局在させる。H200のmicrobenchmarkでは2 block×1024 threadで約50 GB/sを得ながらprefillへの干渉を5%未満、decodeへの干渉を10%程度に抑え、end-to-endでは全体影響を5%未満にしている。

### 2. GPUと下位階層のレイアウト分離

GPU上ではlayer-wise計算に合うlayer-first配置が都合よいが、CPUやSSDへのbulk I/Oでは同一pageの各layerを連続配置した方が大きな転送を作りやすい。StrataはGPU支援copy中にdestination offsetを変換し、GPU側とCPU/SSD側で別レイアウトを許す。

このため「計算効率のための小page・layer-first」と「I/O効率のための連続配置」を同時に満たせる。SSD等にあるcacheはqueue待ち中にhost memoryへbest-effort prefetchし、dispatch時点で使える範囲を利用する。

### 3. HiRadixTreeとCache Controller

SGLangのRadixTreeを拡張したHiRadixTreeが各KV pageの所在を追跡し、Cache ControllerがGPU HBM、CPU memory、storage間のbackup・eviction・loadを管理する。request到着時、schedulerはprefix hitだけでなく、hitしたpageがどのtierにあるかを把握できる。

これによりcache hitを単なる「計算削減量」ではなく「必要I/O量を伴う資源」としてschedulerへ渡す。prefill中はlayerごとに必要KVの到着を同期し、生成後のcache backupは非同期に下位tierへ流す。

### 4. キャッシュ認識スケジューリング

schedulerは待ちrequestの新規token計算量とcache load量を見積もり、I/O latencyを隠せるだけのprefill workを同じbatchへ入れる。cache loadが計算より長くなる場合は、空くGPU時間へdecode batchなどを差し込む。これによりprefill優先というSGLangの低TTFT方針を維持しつつ、I/O stallを無仕事時間にしない。

またcache miss解決中の同一prefix要求を考慮し、delay hitによる重複prefillを避ける。Strataの特徴は、I/O kernel単体の高速化ではなく、data planeのcache移動とcontrol planeのbatch形成を同じ帯域制約の下で設計した点にある。

## 評価条件

| 項目 | 条件 |
|---|---|
| 実装 | SGLangベース、GPU-assisted KV I/O、階層cache controller、cache-aware scheduler |
| 主ハードウェア | NVIDIA H200を含むPCIe/NVLink系構成。AMD ROCm backendにも対応 |
| モデル例 | Qwen2.5-14B、Mistral-24B、Llama-3.1-8B等 |
| workload | LooGLE、ShareGPT等の長文脈・共有context workload |
| 比較対象 | vLLM + LMCache、NVIDIA TensorRT-LLM、SGLang系baseline |
| 指標 | TTFT、throughput、cache hit率、I/O bandwidth、stall割合、短文脈性能 |

## 主要結果

| 条件 | 結果 | 意味 |
|---|---:|---|
| vLLM + LMCacheとの長文脈比較 | TTFT最大5×短縮 | 階層cache復元のI/Oとscheduling双方の改善 |
| TensorRT-LLMとの比較 | 最大3.75×高速化 | 高度に最適化されたserving engineに対しても長文脈で優位 |
| 8192-token KV、page size 32 | 従来転送はPCIe 5.0理論帯域の約22% | 小page DMAが帯域を使い切れない |
| Grace-Hopper系 | 従来方式の帯域利用率が約5%まで低下 | 高帯域interconnectほど細粒度I/Oの非効率が目立つ |
| GPU-assisted I/O microbenchmark | 約50 GB/s、prefill干渉<5% | 少数SMで細粒度転送を高並列化 |
| page size増大実験 | 平均TTFT最大2×、P90最大2.9×悪化 | pageを単純に大きくする解法はcache hit粒度を損なう |

短文脈では階層cacheのI/Oが支配的でないため、Strataは長文脈向け機構を入れても性能劣化を起こさないことを評価している。これは「常にoffloadする」のではなく、cache状態と資源量に応じて既存SGLangの通常経路を保つ設計による。

## 既存研究との差

LMCacheやCachedAttentionなどはKVをCPU/SSDへ拡張し、layer-wise overlapで復元待ちを隠す。一方Strataは、長context・少new-token条件ではcompute量が足りずI/Oを隠せないことを出発点にし、CPU–GPU bandwidthをschedulerの明示的資源へ格上げする。

PagedAttentionはGPU内メモリ利用率のため小pageを使うが、Strataはその小粒度を壊さず、GPU-assisted copy時のlayout変換で下位tierのI/O効率を回復する。したがって「page sizeを大きくして転送を速くする」方式とはcache hit率への影響が異なる。

## 限界

最大倍率は長文脈かつcache reuseが大きい条件の結果であり、すべてのrequestで5倍になるわけではない。cache reuseが少ないsingle-turn workloadやdecode主体の長出力では、Strataが最適化するCPU/SSDからのKV復元が支配項になりにくい。

GPU-assisted I/Oは推論kernelと同じSMを使うため、資源割当を誤ると干渉が起こる。論文はblock数をmicrobenchmarkで調整しており、GPU世代・interconnect・モデル構造が変われば最適quotaも変わり得る。

また、本方式は階層cacheを前提とするため、十分なHBMに全cacheが常駐する小規模環境では追加機構の利点が小さい。SSD/remote tierの遅延変動もCPU–GPU転送より大きく、best-effort prefetchで完全に隠せる保証はない。
