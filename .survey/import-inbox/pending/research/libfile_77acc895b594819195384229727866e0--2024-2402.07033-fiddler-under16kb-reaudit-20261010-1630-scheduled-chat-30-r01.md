# Fiddler：CPUとGPUのどちらでMoE専門家を実行するかを切り替える

## 概要

混合専門家モデル（Mixture-of-Experts; MoE）は、各トークンで選ばれる専門家が少ないため計算量は疎だが、モデル全体の専門家重みをGPUメモリに収めるのは難しい。GPUにない専門家が必要になるたびにCPUメモリから重みを転送すると、PCIeの帯域制約が生成を遅くする。一方、CPUへ重みを残してCPUで直接実行すれば転送は減るが、CPUは多数トークンの行列積をGPUほど高速に処理できない。Fiddlerは、この二つの実行経路の長所を入力トークン数に応じて使い分ける推論システムである。

Fiddlerでは、全トークンで必要な注意機構などの非専門家部分をGPUへ配置し、残りのGPUメモリに利用頻度の高い専門家を常駐させる。GPUにない専門家を実行するときは、専門家へ割り当てられたトークン数を見て、重みをGPUへ転送して計算するか、少量の活性値をCPUへ送ってCPU上で計算するかを選ぶ。少数トークンでは後者が有利で、多数トークンでは前者が有利になる。CPUを単なる低速な重み保管場所ではなく、第二の専門家演算器として利用することが特徴である。

原著のICLR 2025版は16ビット精度のMixtral-8x7Bを、Quadro RTX 6000とRTX 6000 Adaを使う二つの単一GPU環境で評価した。代表的な比較で通常の単一要求推論は1.26倍、長い入力のプリフィルは1.30倍、ビーム探索は11.57倍の改善を報告する。これらは異なる負荷・比較対象に対する結果であり、あらゆる推論が11.57倍速くなるという意味ではない。ルータが選んだ本来の専門家を実行するため、BuddyMoEのように専門家を別の専門家で近似する方式とも異なる。

## 問題設定

### 大きな専門家重みと小さな活性値

Mixtral-8x7Bでは、専門家一つが三つの大きな行列を持ち、16ビット精度の重み容量は300MBを超える。これを毎回CPUからGPUへ転送すると、少数トークンを処理するだけでも大きな固定費が発生する。一方、専門家へ渡す活性値は、トークンごとに隠れ次元4096のベクトルである。トークン数が小さければ、活性値をCPUへ送って専門家計算を実行し、出力をGPUへ戻すほうが、重み全体を移すより転送バイト数がはるかに小さい。

しかし入力が長いプリフィルやビーム探索では、一つの専門家が同時に多数のトークンを処理する。CPU側の行列積はトークン数にほぼ比例して遅くなるのに対し、GPUでは多数トークンをまとめて並列処理できる。重み転送の固定費を払ってもGPU計算のほうが短くなる交差点がある。したがって、CPU実行かGPU実行かをモデル全体で固定するのではなく、各専門家の現在の入力数に応じて切り替える必要がある。

### 既存方式が片方の利点しか利用しない問題

専門家オフロード方式は、CPUメモリに置いた重みを必要に応じてGPUへ持ち込み、GPUの高速演算を活用する。長いプリフィルでは有利でも、短いデコードでは重み転送が支配的になり得る。CPU中心の実行基盤は重み転送を減らせるが、長い入力や複数候補を同時処理するビーム探索ではCPUの計算能力が足りなくなる。Fiddlerは、GPUとCPUの速度曲線が交差することを前提に、両経路を同じ層内でも選べるようにする。

本研究はモデル重みの圧縮や専門家の削除を目的としない。元の専門家をCPUまたはGPUのどちらかで計算するので、数学的には同じモデルのルーティングを保つ。ただし実際の数値演算ではCPUとGPUの浮動小数点実装差があり得るため、「品質を意図的に近似しない」という意味での無損失と、全ビットが一致するという意味は区別する。

## 手法

### 1. 非専門家重みと人気専門家の初期配置

初期化時に、注意機構やルータなど全トークンが通る非専門家重みをGPUへ配置する。これらは毎トークン必要になるため、CPUへ退避すると繰り返しの転送や計算遅延が大きい。残りのGPUメモリへは、校正データで頻繁に選ばれる専門家を優先して配置する。専門家ごとの活性化頻度を事前に数え、常駐した専門家へのヒット率が高くなるよう選ぶ。

ここでの常駐集合は、実行時にすべての専門家を動的に入れ替える通常のキャッシュとは異なり、事前の人気度に基づく固定的な配置に近い。GPU容量が増えるほど常駐できる専門家数が増え、必要な専門家をGPU上で直接実行できる割合も高くなる。ただし校正データと本番入力の分布が変われば人気度の順位も変わり得るため、配置の効果はワークロード依存である。

### 2. ルータの出力から専門家ごとの入力数を得る

各MoE層ではルータがトークンを専門家へ振り分ける。Fiddlerはその結果を使い、専門家jへ割り当てられたトークン数sを数える。s=0ならその専門家は実行しない。重みが既にGPUにあれば転送せずGPUで実行する。重みがGPUにない場合だけ、CPU経路とGPU経路の予測遅延を比較する。

このsは、単一要求のデコードでは小さくなりやすいが、長い入力を一括処理するプリフィルや、ビーム幅の大きい探索では増える。同じ専門家でも時刻やバッチ構成によって最適な実行先が変わるため、専門家単位・実行単位で判断することが重要になる。単に「この層はCPU」「この層はGPU」と固定するより細かい制御である。

### 3. CPU経路：重みではなく活性値を往復させる

GPUにない専門家をCPUで計算する場合、GPU側のルータが生成した隠れ活性値をCPUへ送り、CPUメモリに常駐する専門家重みで行列積を実行する。計算後の出力活性値だけをGPUへ戻し、後続の注意機構や残差経路をGPUで続行する。数トークンなら転送する活性値は専門家重みの300MB超に比べて小さい。

原著の付録では、活性値転送はCPU経路の総遅延の1%未満となる条件を報告する。このときの主な費用はCPUの専門家行列積である。したがって、CPU経路の遅延はトークン数に応じて増えるが、重み転送という大きな固定費を払わずに済む。CPUメモリは単なる退避先ではなく、実際の演算を行う場所として利用される。

### 4. GPU経路：重み転送を大きな行列積で償却する

専門家へ多数のトークンが割り当てられた場合、CPUでそれぞれを計算すると時間が長くなる。この場合はCPUから専門家重みをGPUへ転送し、GPU上でまとめて行列積を実行する。重み転送の時間はトークン数に対してほぼ固定である一方、GPUの行列積は並列化効率が高く、CPU経路より増分費用が小さい。

FiddlerはGPU経路の遅延を「重み転送時間＋GPU計算時間」として見積もり、CPU経路の遅延と比較する。CPU経路がそれより長いならGPU経路を選び、短いならCPU経路を選ぶ。つまりGPUが計算に強いという事実だけで常にGPUを選ぶのではなく、必要な重みがGPUにあるかと、転送費用を何トークンで償却できるかを考慮する。

### 5. 交差点の遅延モデルと実行時判定

原著アルゴリズム1では、各専門家の入力数sについてCPU実行遅延cpu_lat(s)とGPU実行遅延gpu_lat(s)、重み転送時間trans_lat()を参照する。GPUに重みがない場合、cpu_lat(s)がgpu_lat(s)+trans_lat()より大きければGPU実行、それ以外ならCPU実行とする。CPU遅延はsにほぼ比例し、GPU遅延は対象の入力範囲ではほぼ一定と近似する。係数は初期化時に実機で測る。

この交差点はモデル・CPU・GPU・PCIeの組合せで変わる。CPUが高速でPCIeが遅ければCPU経路を選ぶ範囲が広がり、GPUが高速で転送帯域も大きければGPU経路を選ぶ範囲が広がる。特定のトークン数を固定の閾値として全機器に適用するのではなく、配備機器で測定した遅延を利用する点が本方式の実装上の要点である。

### 6. CPU側のAVX512-BF16専用カーネル

CPU経路を高速化するため、著者らはAVX512-BF16命令を用いる専門家計算カーネルを実装した。通常のPyTorch CPU演算をそのまま利用するより、専門家の行列積をCPUのベクトル演算器へ合わせることができる。CPU側の実行性能が改善すると、より多くのトークンをCPUで処理しても重み転送より短く済む可能性が高まる。

この点は、CPUに十分な演算命令とメモリ帯域があることを暗黙の前提にする。AVX512-BF16を持たないCPUで同じ速度を得られるとは限らず、別のCPUカーネルを使う場合は遅延モデルを再測定する必要がある。GPUメモリ容量だけでなく、CPUの演算能力が実行経路の選択を左右する。

### 7. CPUとGPUを併用する実行計画

同じMoE層でも、GPUに常駐している専門家はGPUで直接実行し、GPUにない専門家のうち入力が少ないものはCPUで、多いものはGPUへ転送して実行する。この組合せにより、CPUだけに全専門家を押し付けたり、GPUへの重み転送だけに依存したりすることを避ける。異なる専門家の処理をCPUとGPUで並行させることで、層全体の処理時間を短縮できる。

ただし、原著の主張は各専門家の実行先を遅延モデルで選ぶことであり、無制限の並列処理を保証するわけではない。CPU側の実行が遅れれば後続層の待ちが発生し、GPU側の重み転送が混雑すればGPU経路の費用が増える。実機の計測に基づく選択と、CPU・GPU間の仕事量の配分を一体として扱う必要がある。

## 評価

### 実験環境

| 項目 | 環境1 | 環境2 |
|---|---|---|
| GPU | Quadro RTX 6000 | RTX 6000 Ada |
| GPUメモリ | 24,576 MiB | 49,140 MiB |
| CPU | Xeon Gold 6126 | Xeon Platinum 8480+ |
| CPUコア数（原著表記） | 48 | 112 |
| PCIe | Gen3 x16 | Gen4 x16 |
| GPU常駐専門家 | 56/256 | 125/256 |

原著表1は上記二環境を用い、どちらもMixtral-8x7Bの16ビット重み全体をGPUへ収められない。モデルは32層に各8専門家を持つため、専門家総数は256である。評価にはShareGPTの会話データを使用し、複数の入力長・出力長とビーム幅で測る。著者らの主実装はPyTorchを基盤とし、CPU側に専用カーネルを組み込んでいる。

GPUメモリ容量の差は常駐できる専門家数に直接影響する。環境2は環境1より多くの専門家をGPUに置けるため、そもそもCPU経路や重み転送を必要とする頻度が低い。一方、CPUもPCIeも異なるため、両環境の絶対遅延差をFiddlerのアルゴリズムだけの効果とみなしてはならない。方式比較は同じ環境内の基準方式に対して行う。

### 単一要求のデコード

入力32、64、128、256トークンと、出力64、128、256、512トークンなどの条件を使い、通常の単一要求の完了時間を比較する。Fiddlerはllama.cppに対して平均1.26倍の高速化を報告する。短いデコードでは一つの専門家に入るトークン数が少ないため、重みをGPUへ転送するよりCPUで計算する経路が有利になりやすい。

この1.26倍は桁違いの速度向上ではないが、元の専門家を実行したまま重み転送待ちを抑えるという意味がある。比較基準のCPU/GPU層配置やGPUメモリの使い方に依存するため、llama.cppの全バージョン・全設定に対する一般的な倍率ではない。現在の量子化済みモデルと同じ条件でもない。

### 長いプリフィル

入力長512〜4096トークンのプリフィルでは、一つの専門家へ多数のトークンが流れ、CPU計算が重くなる。Fiddlerは入力数に応じてGPU経路を選ぶため、CPUで全部を計算する方式の弱点を避ける。既存原稿の比較ではDeepSpeed比で約1.07倍、Mixtral-Offloading比で約1.65倍の初回トークン遅延改善を報告している。原著要旨の「長いプリフィルで1.30倍」は複数条件・比較対象をまとめた代表値である。

ここでの評価指標は初回トークンまでの遅延であり、長い出力を最後まで生成した時間とは異なる。プリフィルでは入力トークンの処理が中心になるため、重み転送を一度行って多数トークンをGPUで計算する方が有利になる条件がある。Fiddlerは短いデコードでのCPU経路と、長いプリフィルでのGPU経路を同じ方式で切り替える点が重要である。

### ビーム探索と多トークン実行

ビーム幅4、8、12、16などのビーム探索では、複数の候補系列を同時に進めるため、一つの専門家が扱うトークン数が増える。Fiddlerはこの状況でGPU側の並列行列積を利用しやすく、llama.cppとの比較で最大11.57倍の高速化を報告する。これは、ビーム探索という多数トークンをまとめて扱う条件での結果である。

通常の単一系列デコードに対して11.57倍の高速化が出たわけではなく、ビーム探索時にCPU実行へ固定する方式との性能差が大きくなったと読むべきである。比較する際はビーム幅、入力長、出力長、GPUに常駐する専門家数を合わせる必要がある。ビーム探索自体の探索品質や生成品質を改善する新しい復号アルゴリズムを提案しているわけではない。

### 常駐専門家の選択と別ワークロード

原著の追加評価では、利用頻度で選んだ専門家のGPUヒット率は環境1で25.2%、環境2で53.0%となり、無作為配置の21.9%、48.8%を上回る。最低ヒット率の配置では18.7%、44.6%であり、事前の人気度計測が転送頻度を減らすことを示す。ただしヒット率が上がるだけで全高速化を説明できるわけではなく、ミスしたときにCPU計算へ切り替えられることも重要である。

ShareGPT以外の入力分布を用いた評価では、LMSYS-Chat-1Mでllama.cpp比約1.56倍などの改善が報告される。Phi-3.5-MoEを用いた別モデル評価ではDeepSpeed比平均約6.5倍という結果も示される。ただしモデル、精度、実行条件、比較対象が主実験と異なるため、これらをMixtral-8x7Bの通常デコード1.26倍と直接比較して優劣を論じるべきではない。

### どの費用を削減しているか

Fiddlerの主な利得は、GPUにない専門家を実行する際の重み転送を、少数トークンの場合には活性値転送とCPU計算へ置き換えることである。専門家のパラメータ数を減らすわけではなく、モデルの重みを量子化するわけでもない。全重みはCPUメモリに保持し、GPUメモリには頻繁に使う部分だけを置く。したがってGPUメモリの不足を補える一方、CPUメモリ容量が不足する構成を解決する方式ではない。

また、重みをGPUへ転送する経路が完全になくなるわけではない。プリフィルやビーム探索ではGPU計算のほうが有利になるため、あえて重みを転送する。CPU・GPUどちらを選ぶかは、転送費用と計算費用を合わせた総遅延で決まる。平均高速化倍率だけでなく、短いデコードと長いプリフィルで実行経路がどう変わるかを見ることが、この研究の評価では重要である。

## 既存研究との差

MoE-InfinityやMixtral-Offloadingのような専門家オフロード方式は、CPUメモリに重みを置いても、計算時には必要な重みをGPUへ転送することが中心となる。Fiddlerは、GPUへの重み転送が高価な場合にCPU側で専門家計算そのものを実行するため、転送するデータを大きな重み行列から小さな活性値へ切り替える。CPUとGPUの演算速度の差を入力トークン数の関数として扱う点が特徴である。

一方、llama.cppのように一部の層をCPUへ配置する方式は、GPUメモリ容量に応じた固定的な分割が中心となる。Fiddlerは、同じ専門家でも短いデコードと長いプリフィルで最適な実行先が異なることを利用し、ルータが決めたトークン数を見て動的に切り替える。さらにCPU側のAVX512-BF16専用カーネルを実装し、CPU実行の費用自体を下げる。

Fiddlerは本来の専門家をCPUかGPUのどちらかで実行するため、専門家を別の専門家で代替する近似方式とは異なる。重み圧縮や専門家削除を行わないので、品質を犠牲にして速度を得ることが主目的ではない。圧縮方式と組み合わせる余地はあるが、論文の主実験は16ビット精度のMixtralであり、量子化後の相乗効果を直接保証していない。

## 限界

Fiddlerの効果はCPUとGPUの演算能力、PCIe帯域、GPUメモリ容量に強く依存する。CPU側の専用カーネルはAVX512-BF16を用いるため、この命令を持たないCPUで同じ交差点や高速化倍率が得られるとは限らない。特に低性能CPUでは、活性値だけを転送してもCPU計算の時間が長くなり、GPUへ重みを転送する経路が有利になる範囲が広がる可能性がある。

主評価は単一GPUであり、モデル全重みをCPUメモリに保持できることを前提にする。CPUメモリ容量が足りずSSDやNVMeから重みを読み込む場合、ストレージI/Oが追加され、原著の遅延モデルだけでは十分ではない。またKVキャッシュのCPU退避、分散GPU間の専門家転送、大規模な連続バッチング、多数同時要求の干渉を直接最適化した研究ではない。

事前の専門家人気度による常駐配置は、校正データと本番ワークロードのルータ分布が似ていることを期待する。入力分野が変われば人気度が変化し、常駐ヒット率が低下する可能性がある。実行時のCPU/GPU選択はミス後の費用を減らせるが、人気度の推定が誤っていること自体を自動的に解消するわけではない。分布変化に合わせた常駐集合の再選択は別途必要となる。

CPU経路の計算時間を入力トークン数にほぼ比例、GPU経路をほぼ一定とする遅延近似は、原著の実験対象の範囲での経験モデルである。GPUが飽和する大きなバッチや、CPUのメモリ帯域が飽和する構成では単純な直線・定数の近似が崩れ得る。ハードウェアやモデル精度を変えると再プロファイルが必要であり、交差点を固定値として他環境へ移せない。

11.57倍という最大値はビーム探索での特定比較であり、通常の単一要求では平均1.26倍、長いプリフィルでは代表値1.30倍である。比較対象も条件によって異なるため、すべてを一つの基準方式に対する倍率と誤解してはならない。16ビットMixtralの結果を、量子化済みの現代のMoEや異なるCPU命令セットへそのまま適用することはできない。
