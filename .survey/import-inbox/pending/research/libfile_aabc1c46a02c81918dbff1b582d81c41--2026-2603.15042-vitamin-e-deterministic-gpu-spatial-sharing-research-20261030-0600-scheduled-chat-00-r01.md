# Vitamin-E：並列構造を変えずにGPUの物理SM割当を動的共有する

## 概要

GPUを複数ジョブで空間共有する際、空きSMに応じてカーネルのブロック構成や演算分割を変更すれば資源を使いやすい。しかし浮動小数点の加算・縮約順序が変わり、同じモデル・入力でも出力ビットが変化し得る。Vitamin-Eは、カーネル起動時のバイナリ・グリッド・ブロック・依存順序を固定したまま、各起動を利用可能な物理SM集合へ遅延結合する。物理幅は変えても論理的な並列構造は変えないという「parallel-structure invariant」を資源管理の契約にする。

2026年8月5日のarXiv v4で題名・方式が更新された同一論文である。旧v3のDetShareの実験数値をv4のVitamin-Eに混ぜない。v4はH20/H200で実機評価し、固定構造で決定的な処理のビット単位一致を確認した。学習同居で比較方式に対する幾何平均の合計正規化処理量1.38〜1.63倍、混在負荷の推論p99遅延8.1〜58.4%短縮、TPOT優先方策の違反率21.2〜46.1%低減を報告する。最大3.50倍という数字は全比較中の最も遅い基準方式との個別比較であり、常に最強基準に3.50倍という意味ではない。

## 問題設定

MPS・MIG・NVIDIA Green Contextsは元のカーネル形状を保てるが、プロセス・インスタンス・コンテキスト単位で長くSMを割り当てるため、要求や転送・同期フェーズに伴う短い空き時間を利用しにくい。一方、LithOSやμShareのようなカーネル構造を変える方式は、実行幅の変化に応じて分割や縮約木を変更する可能性がある。非結合的な浮動小数点加算では、異なる縮約順序が異なるビット列を生み、greedy decodeのargmaxまで変える場合がある。

対象は、同じ入力・同じGPU/ソフトウェア環境・同じ起動バイナリと論理並列構造・同じアプリケーションが要求するhappens-before順序で、もともと決定的な処理である。アプリケーション内部の競合や乱数、異なるGPU世代をまたぐ再現性まで保証するものではない。変えてよいのは物理SM割当と、依存関係のないready操作の実行タイミングである。

## 手法

### 1. vCtxが論理実行と依存関係を保持

仮想コンテキストvCtxは、アプリケーションから見えるCUDAストリーム、イベント、同期、カーネルの不変起動記述子を管理する。記述子には関数、引数の起動時値、グリッド・ブロック寸法、動的共有メモリ量、起動属性を格納し、スケジューラは書き換えない。ポインタ引数はポインタ値を複製するだけで、指すデバイスメモリの同期責任はアプリケーションに残る。

各論理操作の完了にトークンを割り当て、同じストリームの直前操作、イベント記録・待機、既定ストリームの意味からhappens-before有向非巡回グラフを作る。イベントを再記録しても過去のwaitが新しい世代へ付け替わらないよう、待機時点の世代トークンを固定する。前提トークンが満たされるまで操作はreadyにならないため、物理コンテキストを切り替えてもアプリケーションが指定した順序を維持できる。

### 2. pCtxが置換可能な物理割当を表す

物理コンテキストpCtxはGreen Contextとそのバックエンドストリームを含むが、論理ストリームやイベントの正本を持たない。空き、リース中、draining、予約中という状態を管理する。起動ごとにSM幅を変えても、元のカーネル記述子は同じであり、GPUハードウェアが同じ論理ブロックを異なるSM幅で複数waveに分けて実行する。

コンテキストを毎回作ると遅いので、buddy割当に似た階層プールを初期化時に事前生成する。階層ノードはSM集合と補集合の候補を持ち、祖先・子孫・補集合の重複リースを防ぐ。実行時にノードを作成・統合するわけではない。遅延に敏感なdecode用には一部SMを予約し、将来広いSM割当が必要と予測されたら重複するpCtxの新規投入ゲートを閉じて既存処理をdrainさせる。先行転送などの間に資源を準備し、待ちを隠す。

### 3. ready後の遅延結合とポリシー分離

依存トークンが満たされた操作だけをreadyキューに入れ、方策が物理資源を選ぶ。方策APIはPick（ready操作選択）、Select（適合pCtx選択）、Prepare（予測された将来要求に備えた予約・回収計画）である。実際のディスパッチャは、元記述子の実行互換性、依存完了、リース競合を再検査し、成功してから実行を確定する。送信失敗時はreadyに戻して再選択する。

Throughput-Orientedは事前測定したSM幅ごとの実行時間から、まず最大数のready操作へ最小SMを割り当て、残りSMを追加したときの正規化進捗の限界利得が高い操作へ順次配る。TPOT-Firstはdecode用の常設SM予約を持ち、次トークン期限に間に合わないと予測した要求へ広いpCtxを先行準備する。両方とも論理記述子は同じで、独立操作の優先順と物理割当だけを変更する。

### 4. 実装上の境界

約6千行のC++と千行のCUDAからなる試作は、LD_PRELOADで起動、イベント、ストリーム、メモリ操作を捕捉する。クライアントと調整デーモンは共有メモリ上のロックフリーリングで情報をやり取りし、デーモンがグローバルなpCtxリースを調停する。クライアント側の送信スレッドが記述子を変えずに実行する。CUDA Graphのリプレイは未対応で、評価でも無効化している。

## 評価

### 実機・比較条件

| 観点 | 原著の設定 |
|---|---|
| 学習同居・混在負荷 | 単一H20、分散学習は8台H20 |
| 決定性・サービング・管理オーバーヘッド | 単一H200 |
| 推論スタック | SGLang、Llama-3.1、CUDA Graph replay無効 |
| 学習・混在モデル | Qwen3.5/Qwen3のdense/LoRA/QLoRA/分散、ResNet/BERT学習とLlama3/GPT-J推論 |
| 比較 | 時間共有、MPS、MIG、Orion、Salus、再現実装LithOSなど |
| サービングトレース | Azure LLM Trace 2024、LongBench、BurstGPT |

### 決定性と生成結果

縮約カーネルとSplit-K GEMMを同じ入力で1000回比較すると、並列構造を再分割する処理では数値差が生じたが、Vitamin-Eは物理割当を変えてもビット単位で一致した。Llamaのgreedy decodeを100回繰り返す検証では、構造変更によるlogit差が100回中5回の選択トークン変更へ波及した。Vitamin-Eではlogit・確率・選択トークンの不一致が観測されなかった。これは「元から決定的な固定構造実行」の契約を満たす証拠であり、あらゆるCUDAカーネルの決定性を証明するものではない。

### 同居処理量とtail latency

| 条件 | 結果 | 解釈 |
|---|---|---|
| 学習同居8ワークロード | 基準方式比、合計正規化処理量の幾何平均1.38〜1.63倍 | 同居によるSM空きの再利用 |
| dense単一GPUで最強基準比 | 1.08〜1.11倍 | もともと高稼働率で余裕が小さい |
| オフロード・分散の変動が大きい条件 | 最強基準比最大1.84倍 | 通信・転送の待ち時間を利用 |
| 混在学習・推論 | 推論p99 8.1〜58.4%短縮、背景学習1.05〜1.36倍（幾何平均） | 予約・事前回収の効果 |
| 全比較の最大 | 学習処理量3.50倍、推論p99最大62.5%短縮、背景学習最大1.43倍 | 異なる条件・基準を混ぜて単一ケースとしない |

最大の分散学習ワークロードの正規化処理量は1.0未満にとどまり、SM割当だけではCPUオフロードや通信ボトルネックを解消できない。LithOSとの比較は著者らの再現実装であり、原版の全最適化が含まれるとは限らない。

### TPOTとTTFTのトレードオフ

TPOT-FirstはThroughput-Oriented比でTPOT SLO違反率をAzureで21.2%、LongBenchで23.4%、BurstGPTで46.1%低減した。BurstGPTではp90 TPOTが847.7msから262.9ms、p99が3893.0msから2844.0msへ下がる。一方でprefillを後回しにするため、BurstGPTのTTFT SLO違反率は4.33%から6.37%へ悪化する。AzureではTTFT違反率はほぼ変わらず、LongBenchでは小幅に悪化した。したがって「全ての遅延指標が同時に改善する」という主張ではなく、方策で目標を選べることが実証点である。

### 起動遅延とプール容量

H200上のBF16 GEMMでは、ネイティブp95が404µs、実行時にpCtxを生成すると2069µs、事前生成の平坦プール432µs、階層プール407µsであった。階層プールの上乗せは約0.7%である。最大構成で階層プールはGPUメモリ1163MiB・ホストRSS318MiB、比較したMPS-Poolは2533MiB・552MiBだった。ここでの「GPUメモリ容量1%未満」という記述はH200の容量に対する管理プールの割合であり、一般GPUへそのまま適用しない。

## 既存研究との差

MIGやMPSは論理構造を守りやすいが、長寿命コンテキストに資源を結び付ける。LithOS/μShareのような再分割方式は短い単位で資源を再配分できても縮約木を変え得る。Vitamin-Eは論理実行をvCtxに固定し、pCtxを差し替える中間層を導入することで、カーネル形状を変えない起動単位のSM割当を可能にした。再現性とGPU利用率の両立は、元のカーネルが決定的であるという限定の下で成立する。


## 技術的解釈と適用境界の詳細

### なぜ物理SM幅の変更だけならビット一致が可能なのか

GPUのブロックスケジューラは、カーネル起動時に指定された論理グリッドを、利用可能なSMへ順次配置する。SMが少なければブロックを複数のwaveで実行し、SMが多ければ同時に走るブロック数が増える。しかしカーネルが各ブロック内で実行する演算や、そのブロックが担当する要素の割当が固定なら、物理配置の変更そのものは演算式を変えない。Vitamin-Eはこの区別を利用し、元のカーネルバイナリB、並列構造C、アプリケーションが要求する依存関係Hを不変にしたまま、物理割当Pだけを変える。数値再現性はこの固定構造決定性という前提の上で成立する。

対照的に、GPUの空きSM数に合わせてSplit-Kの分割数や縮約のグループ化を変えると、同じ入力でも足し算の順番が変わる。浮動小数点演算は一般に結合則が成立しないため、丸め誤差が変化する。LLMのgreedy decodingではlogit上位2候補の差が小さいと、微小な差でargmaxが反転し、次のトークン以降の履歴も変わり得る。論文の5/100回のトークン変更はこの危険を具体的に示す。ただし全ての構造変更で必ず違いが出るわけではない。

### イベント世代と既定ストリームの扱い

CUDAのイベントは同じハンドルへ繰り返し記録されることがある。waitが指す記録世代を固定しないと、論理ストリームを別の物理ストリームへ移す途中で、待機先が後のイベントへ置き換わり得る。Vitamin-Eは記録時に不変の世代トークンを作り、waitがその世代へ依存するようにする。既定ストリームの同期意味もDAGへ取り込むため、物理コンテキストの変更が元のCUDAプログラムのhappens-before順序を破らない。この実装の難所は、単にSMを分割することではなく、元の論理依存を異なるバックエンドストリーム上で正しく再現する点にある。

### 事前作成プールとリースの意味

SM幅ごとに物理コンテキストを起動時に作成すれば、管理コストがカーネル遅延に直接乗る。原著のp95は404µsから2069µsへ悪化する。階層プールを事前に作ると、各候補の資源集合と競合関係を先に計算でき、ディスパッチ時はリースの可否を調べるだけになる。drainingは新しい仕事を受け付けないが、実行中の仕事を強制停止しない状態である。これにより、将来のdecodeのために資源を確保する際も既存処理の正しさを壊さない。予約・事前回収はtail latencyを守るが、同時に他ジョブの実行機会を減らすので、TPOT優先でTTFT違反が増えるというトレードオフが現れる。

### 性能値の集約に関する注意

1.38〜1.63倍は異なる比較方式に対する幾何平均の合計正規化処理量であり、最大3.50倍は全比較の中で最も遅い基準を含む個別条件である。混在負荷のp99改善8.1〜58.4%も基準方式ごとの幾何平均の範囲であり、62.5%は最大条件の値である。これらを単一の同じ比較条件に並べて「3.5倍の学習処理量かつ62.5%のp99改善」と断定してはならない。さらにH20での同居学習とH200でのサービングは異なるGPU上の別実験であり、同じカーネル負荷の総合スピードアップではない。

## 限界

CUDA Graphリプレイを無効化しているため、グラフ実行が標準のサービングスタックで同じ利得が得られるかは未検証である。物理SM分割だけを制御し、HBM帯域やPCIe・ネットワーク、メモリ分離・テナント間故障隔離を包括的に保証するわけではない。階層pCtxプールは初期化とメモリを消費し、実装の移植性はGPUのGreen Context等の資源分割APIに依存する。ポリシーの事前プロファイルが負荷分布から外れた場合は選択が最適でない可能性がある。推論のTPOTを優先すればTTFTが悪化する負の結果も原著で確認できる。
