# DySpec: Faster Speculative Decoding with Dynamic Token Tree Structure

> **一覧用要約**：DySpecは下書きモデルの確率分布から候補の受理見込みを近似し、受理後の子候補と拒否後の兄弟候補を優先度付きキューで動的に展開する。閾値付き層単位生成で下書き呼出しを抑え、Llama2-70BのCPUオフロード条件では対象モデル呼出し回数の削減により大きな速度改善を得る。

## 概要

本論文は、投機的復号に使う候補木を入力ごとに変えるDySpecを提案する。投機的復号は、小さな下書きモデルが先のトークン候補を生成し、大きな対象モデルがそれらを一度に検証する方式である。対象モデルが候補を受理できれば複数トークンを一度の高価な推論で確定できる。しかし、候補を単一系列や固定形状の木に配置すると、入力文脈や生成温度が変わっても同じ深さ・幅を使い続ける。確率が少数の語へ集中する文脈では深い枝が有利であり、候補が分散する文脈では兄弟候補へ予算を配るほうが有利になる。固定木はこの違いに対応しにくい。

DySpecの核は、下書きモデルが高確率を付けた候補ほど対象モデルにも受理されやすいという仮説と実験的相関である。対象モデルの真の受理確率は検証前には不明なので、下書き分布から得る代理値を使う。受理時に続く子候補と、拒否時に試す次の兄弟候補を、到達確率を含めて比較し、期待受理長への寄与が大きい候補を先に追加する。優先度付きキュー（最大ヒープ）を用いる貪欲展開で、同じ候補数でも高価値の枝へ検証予算を集中できる。

ただし候補を一個ずつ追加する方式では下書きモデルを候補数に比例して呼び出し、木を作るだけで遅くなる。著者らは選択優先度の単調性を利用し、閾値を超える候補を深さごとにまとめて生成する。これにより下書きモデルの前向き計算回数を候補総数から木の深さに近づける。木構築の管理部分はC++で実装し、Pythonによる細かな制御が新たな律速になることを避ける。

A100 40GB一基と32 CPUコアで、Llama-68Mを下書き器とするLlama2-7B/13B、およびLlama2-7Bを下書き器とするLlama2-70Bを評価する。特に70BをCPUメモリへ退避させた実験では、C4・温度0で通常自己回帰の5.59650秒/トークンに対しDySpecは0.53696秒/トークン、平均受理長9.10を示す。これは**CPUからの重み読み出しが極めて高価な対象モデル**での結果であり、70BをGPUへ完全常駐させた環境の普遍的な速度改善値ではない。

## 問題設定：固定木の候補予算が入力分布と噛み合わない

### 木構造の候補を検証する意味

通常の自己回帰生成では、対象モデルが次の一語を出すたびに前向き計算を一回行う。投機的復号では下書きモデルの提案を先に生成し、対象モデルがまとめて確認する。下書きが一つの候補系列だけを出す場合、途中で候補が拒否されると、それ以降の系列は採用できない。木構造なら同じ位置に複数の兄弟候補を持てるため、第一候補を外しても別候補を試せる。ただし一括検証できる候補数は有限であり、同じ候補予算をどの深さ・どの分岐に使うかが重要になる。

木状注意では、各候補は根から自分へ至る祖先だけを参照し、無関係な兄弟枝の未来を見ないようにする。対象モデルの検証後は、採否を対象分布と下書き分布の比で決め、拒否した場合には残差分布から補正サンプリングする。この規則を保てば、候補木の作り方を変えても対象モデルが定める出力分布を保てる。ただし木構築が確率を見た後でサンプルを恣意的に残す方式だと分布が偏るため、DySpecは**どの候補を採用するかではなく、どこで追加サンプリングを行うか**を選択する。

### 下書き分布と受理率の相関は近似である

原著§3では、下書き分布Dと対象分布Tの相違が大きくないという仮定を、KLダイバージェンス D_KL(D||T)≤c で説明する。高い下書き確率D[x]を持つ候補について対象確率T[x]が極端に小さいと、KLダイバージェンスへの寄与が大きくなる。そこで高いD[x]の候補は統計的に受理されやすいと予想する。図2はCNN/DailyMailで、下書き確率と対象分布、下書き確率と実測受理率の関係を示す。ただしこの議論は**分布が近いという前提と統計的傾向**であって、任意の入力・任意の候補で下書き確率が受理率と厳密に等しいという証明ではない。

標準的な投機的サンプリングでは、下書きでxを提案したときの受理確率はmin(1,T[x]/D[x])であり、拒否時には正規化した正の差分から補正候補を採る。DySpecはこの真の受理率を木構築時には知らないため、下書き確率を代理として使う。代理値の誤差は木の配置効率を下げる可能性があるが、対象モデルの検証と補正を省略するわけではないため、出力分布の保存という意味での正しさと区別する必要がある。

### なぜ深い枝と横の枝を同じ尺度で比べる必要があるか

あるノードへ到達するには、その祖先候補が受理され、同じ位置のそれ以前の兄弟候補が拒否されなければならない。深い枝の価値は親まで到達する確率で減衰する。横に新しい兄弟を追加する場合も、先行候補が拒否される確率を考慮しなければ、その候補が実際に検証される見込みを過大評価する。DySpecは両方を到達確率に換算し、木の深さと幅を共通の尺度で競わせる。

## 手法

### 1. 固定候補予算の期待受理長を定式化する

原著§4.1では、ある候補ノードt_iが受理されるまでの条件を、祖先の受理と先行兄弟の拒否の積で表す。各祖先aの受理確率をP(accept_a)、各先行兄弟sの拒否確率をP(reject_s)、現在ノードの受理確率をP(accept_i)とすれば、当該ノードが受理長に寄与する確率は、これらをすべて掛けた値になる。木全体の期待受理長は、その寄与を各候補について合計したものとして表される（原著式(2)）。真の受理率が不明なので、これらの積を下書き確率から推定する。

重要なのは、候補トークンの値を見てから「良さそうな値だけ採用する」と、サンプリング確率を変えてしまう点である。DySpecが選ぶのは、現時点で展開可能な候補位置と次にサンプリングを行う分岐である。サンプルされたトークン値は下書き分布に従う。こうして構築した木を、対象モデルの補正付き検証へ渡す。

### 2. 優先度付きキューで受理後の子と拒否後の兄弟を管理する

原著のアルゴリズム1は、候補位置の残差分布R、そこへ到達する見込みv、木内の位置情報を一つのヒープ要素として保持する。初期状態では根の次トークン分布Rとv=1を投入する。反復では最大のvを持つ展開候補を取り出し、残差分布Rから一語yをサンプルして木へ追加する。新たに二種類の展開候補をヒープへ戻す。

第一は**受理後の子候補**である。現在の語yが受理された場合に次位置へ進むので、到達見込みはv×R[y]となる。新しい接頭辞を下書きモデルへ入力して得た次トークン分布を子候補として保持する。第二は**拒否後の兄弟候補**である。現在の語yが拒否された場合、同じ位置で別の語を提案するため、到達見込みはv×(1−R[y])となる。残差分布からyの質量をゼロにし、残りを正規化して次の兄弟サンプリングに用いる。これにより、先に高確率語を試した後で次候補へ回る確率を過大評価しない。

ヒープに入る候補の優先度は展開するたびに増えない。受理側はR[y]、拒否側は1−R[y]を掛けるので、いずれも親のv以下となる。この単調性により、高優先度の展開位置を順に選べば、まだ選ばれていない候補より期待寄与の大きいものから木へ追加される。原著はこの代理期待受理長に関して貪欲構築が最適となる条件を付録Dで論じる。**対象モデルの未知の真の受理確率に対して無条件に最適**という意味ではない。

### 3. ヒープの計算量と下書きモデルの呼出し回数は別の費用

候補数をNとすると、優先度付きキューの追加・取り出しは一回あたり対数時間であり、木構築の管理計算量はO(N log N)となる。しかし、子候補の次トークン分布を得るために毎回下書きモデルを呼ぶと、前向き計算が最大N回必要になる。原著§4.3は、対象モデル一回の時間T_t、下書きモデル一回の時間T_dを使い、素朴な貪欲構築の反復費用をO(N log N+T_t+N T_d)と整理する。受理長が増えてもN T_dが大きければ、単位出力トークン時間の改善は頭打ちになる。

管理計算自体もPythonで細かな分岐や残差分布更新を繰り返すと高くつく。著者らはこの部分をC++で実装し、木構築処理のCPU側の制御を軽くした。図4の実測では、68M→7B/13Bの条件で木構築部分は全反復時間の2%未満と報告される。これは下書きモデルの前向き計算費用まで2%未満という意味ではなく、木を管理する追加処理の比率である。

### 4. 閾値を使って同じ深さの候補をまとめて生成する

原著§4.4は、逐次貪欲構築で選ばれる候補の優先度が単調に下がることを利用する。最終的に選ばれた候補は、ある閾値Cより大きい優先度を持つとみなせる。そこでCを先に定め、同じ深さで閾値を超える候補をまとめて展開する。これにより、木の各層をまとめて下書きモデルへ入力でき、前向き計算回数を候補数Nではなく深さDに近づけられる。理想化した反復費用はO(N log N+T_t+D T_d)となる。

著者らはCをおおむね1/n程度に置く運用を説明し、N=64では木の深さが通常10未満、N=768でも30未満となる例を挙げる。これは固定Nでの逐次貪欲展開と完全に同じ実行経路ではなく、候補数の厳密な制限を緩めて下書き生成を並列化する近似的な実装上の工夫である。閾値が高すぎると有用な候補を取り逃がし、低すぎると多くの候補を生成する。論文は実験で速度を示すが、閾値があらゆる分布で最適であるとまでは証明していない。

### 5. 木状注意と補正付きサンプリングで出力分布を維持する

生成した木の各ノードには、祖先にだけ注意を向けるマスクを割り当て、対象モデルが一括して候補の確率を計算する。検証は元の投機的サンプリング規則に従う。子候補の採否が決まれば次の深さへ進み、拒否時には残差分布に基づく兄弟候補や補正トークンを処理する。DySpecが変えるのは候補をどこに置くかであり、対象モデルの重み、注意機構、最終確率の定義ではない。

ただし、分布保存にはサンプリングと補正が正しく実装されていることが必要である。下書き候補の値に応じて木の一部だけを事後選別する方式では分布が偏る可能性があるため、原著付録Aは木構築と検証の関係を改めて説明している。この点は単なる高速化のための木探索ではなく、確率的生成アルゴリズムとして重要である。

### 6. 一反復の処理順と必要な状態

実行時には、まず現在の接頭文脈から下書きモデルが候補分布を計算する。次に木の位置、残差分布、到達見込みをヒープで管理し、受理後の子と拒否後の兄弟を展開する。閾値方式では同じ深さの展開候補をまとめて下書きモデルへ渡す。完成した候補木に祖先マスクを作り、対象モデルで一括検証する。対象側の確率に基づいて採否・補正を行い、確定した経路を次の反復へ渡す。管理状態としては候補木、優先度付きキュー、各位置の残差分布、サンプリング済み語と親子関係が必要である。これらはKVキャッシュをCPUへ退避する機構ではなく、候補生成の確率的制御に用いる状態である。

## 評価

### 実験環境と比較の公平性

| 項目 | 原著の条件 |
|---|---|
| 実機 | NVIDIA A100 40GB一基、CPU 32コア。70B対象ではCPUオフロードを利用。 |
| 対象モデル | Llama2-7B、Llama2-13B、Llama2-70B。 |
| 下書きモデル | 7B/13B対象にはJackFram/Llama68m、70B対象にはLlama2-7B。 |
| データセット | C4英語、OpenWebText、CNN/DailyMail。 |
| 入出力長 | 先頭128トークンを入力し、128トークンを生成。 |
| 温度 | 対象側は0と0.6を代表条件として比較、下書き温度は0.6。 |
| 検証木 | 主要表の候補数64。68M下書きの7B/13B実験では長さ128〜258の129種のCUDAグラフを利用。 |
| 比較方式 | 通常自己回帰生成、SpecInfer、Sequoia。 |
| 指標 | 一出力トークン当たりの秒数、括弧内は一検証で受理する平均トークン数。 |
| 70B固有条件 | 重みのCPU→GPU読み出しを重畳しても対象モデル一回の実行が約5秒、7B下書きは約25ms。 |

この設定は、生成トークン数を揃えた上で候補木の形状と受理長が遅延へ与える影響を見る。70BはA100 40GBに収まらないため、GPU常駐の7B/13Bと比較して律速が根本的に異なる。70Bで巨大な倍率が出た理由は、対象モデルの重み読み出しが非常に高価で、下書き候補を多少増やしても対象モデルの実行回数を減らす利得が上回るためである。

| C4・0 | 5.59650 | 1.14332 | 0.88920 | **0.53696（9.10）** |
| C4・0.6 | 5.34781 | 0.92829 | 0.94550 | **0.78912（6.21）** |

この表の最大の特徴は、7B/13Bよりはるかに大きい絶対遅延である。C4・温度0の5.59650秒から0.53696秒への短縮は、単位トークン時間で約10.42分の1である。原著の要旨は処理量最大9.1倍、遅延最大9.4倍という別の総括値も報告しており、表3の比率をそのまま要旨の指標に置き換えない。原著はCPUオフロード下の対象モデル一回を約5秒、下書きモデル一回を約25msと説明する。対象モデル呼出しの削減が速度を支配することが分かる。なお70Bでは可変長CUDAグラフの保持にGPUメモリが必要なため、7B/13Bと同じグラフ取得は使っていない。

### 構築費・木の大きさに関する観測

図4では、7B/13B条件の木構築管理時間は全実行時間の2%未満である。70B条件でも、下書き・対象モデルの前向き計算以外の部分は小さい。候補数N=64では木の深さが10未満となる例が示され、候補数を単純に64回の下書き呼出しへ対応させない閾値付き層生成の効果が説明される。これは、アルゴリズムの理論上のO(N log N)だけでは分からない実行時の重要な改善点である。ただし、GPUメモリの余裕、閾値の選択、下書きモデルの大きさによって費用の構成は変わる。

## 既存研究との差

SpecInferは木構造で候補を一括検証するが、DySpecは入力ごとの下書き分布に基づいて木の幅と深さを実行時に変える。Sequoiaは受理率の推定を使って木を最適化するが、DySpecは候補を順にサンプリングしながらヒープで次の展開位置を選び、閾値による層単位生成でその管理費を抑える点が特徴である。SpecTrは複数候補を出力分布を保って選ぶ別系統の方式であり、DySpecの主眼は同じ候補予算をどの枝へ配るかにある。

また、EVICTのように既に生成した木から検証すべき接頭部分を費用対効果で選ぶ方式とは異なる。DySpecは**候補木を構築する段階**で、期待受理長が大きい位置へ候補生成を集中する。原著の評価ではMoE特有の専門家活性化費用ではなく、密なLlama2系列の下書き生成費用と対象モデル検証回数が主要な対象である。二方式を同一の機構として説明しないことが重要である。

## 限界と適用条件

第一に、ドラフト確率を受理率の代理にできるという仮説は、下書き分布と対象分布が近いことに依存する。図2はその相関を示すが、未知のモデル組合せや分布ずれの大きい文脈では木の配置が最適とは限らない。高温度では確率が広がり、平均受理長が下がることも表1〜3で観測される。

第二に、候補数を増やせば必ず高速化するわけではない。素朴な貪欲構築では下書き呼出し回数がNに比例し、N T_dが律速になる。閾値付き層生成はこれをD T_dへ近づけるが、閾値の選び方によって木の大きさと期待受理長が変わる。原著は「閾値を事前に定めれば常に最適」という保証を与えていない。

第三に、70Bの大きな改善はCPUオフロードを使う特殊な対象モデル律速条件で得られた。単一A100 40GBの制約により70B重みをCPUから転送するため、一回の対象モデル推論が極端に高価である。多数GPUに常駐する70Bや高速な新世代GPUへ、そのまま倍率を外挿できない。

第四に、評価のモデル系列はLlama2に限られ、主なデータはC4、OpenWebText、CNN/DailyMailである。多数同時要求のサービング、最新MoE、長文脈、量子化済みモデル、エネルギー消費、複数GPU分散実行への一般化は原著の主要実測では示されない。実装の公式公開コードURLは今回確認した一次資料から確定できなかったため、`code: null` とし、存在しないと断定しない。

第五に、理論的な最適性は下書き確率を代理とする目的と特定の構築条件に関するものであり、真の対象分布を知ったときの全ての木形状・全ての実行環境での最適速度を保証するものではない。特に、対象モデルの検証費用が木形状によって大きく変わる場合は、期待受理長だけを最大化しても出力速度が最大になるとは限らない。原著の貢献は、候補生成と検証の費用を測定した条件で、固定木よりよい配置を実現したことにある。

## 再監査で確認した注意点

- ヒープの優先度は、単一候補の下書き確率だけでなく、祖先受理と先行兄弟拒否の到達見込みを含む。
- 木を構築する前に真の対象モデル受理確率を知るわけではない。下書き確率は統計的な代理である。
- 素朴な貪欲展開のN回の下書き呼出しと、閾値付き層単位生成のD回程度の呼出しを区別する。
- C4・70B・温度0の秒/トークンと、原著要旨の最大処理量・最大遅延倍率を同一指標として混同しない。
- 70BはCPUオフロードを用い、7B/13Bと同じCUDAグラフ構成ではない。
- サンプリング分布の保存は対象モデルの検証・残差補正に依存し、木構築の代理受理率が厳密という意味ではない。
