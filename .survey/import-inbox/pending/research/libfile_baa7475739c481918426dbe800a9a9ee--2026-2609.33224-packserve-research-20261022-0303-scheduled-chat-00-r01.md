# PackServe：KV再利用と生成遅延制約を両立するエージェント要求の集約

## 概要

PackServeは、エージェント型大規模言語モデル（LLM）の複数要求をGPU推論インスタンスへ振り分けるゲートウェイ型スケジューラである。エージェントの連続した要求は長い履歴やツール実行結果を共有するため、接頭辞のキー・バリューキャッシュ（KVC）を再利用できるGPUへ送ると事前処理（prefill）の再計算が減る。一方、各GPUの同時実行数を小さく保ち過ぎると、生成処理のバッチ化が進まず、同じ負荷を処理するために多数のGPUを稼働させることになる。

提案方式は、①接頭辞を失うことで増える事前処理費用を一定の予算内へ制限し、②事前処理と生成の干渉を考慮して生成トークン間遅延（time per output token、TPOT）を予測し、③目標を満たすインスタンスのうち現在の生成要求が多いものへ新規要求を集約する。64台のNVIDIA H20を使った再生実験では、比較方式より13.0～24.6%少ない稼働GPU時間で評価したTPOT目標を満たした。1000台超のGPUを持つ本番クラスタでは、従来のキャッシュ認識型負荷分散に比べ平均稼働インスタンス数が34.7%少なく、インスタンス当たり処理量が36.8%高かった。ただし**本番の平均初回トークン遅延（TTFT）は66.4%悪化**しており、資源削減を無償で得られるわけではない。

## 問題設定と実測に基づく動機

本研究は、事前処理と生成を同じGPUで実行する構成を対象とする。新規要求の事前処理が長いと、既に生成中の要求が次トークンを出すまでの間隔が伸びる。したがって、接頭辞KVを再利用できるかは新規要求のTTFTだけでなく、他要求のTPOTにも影響する。逆に同じGPUへ要求を集めれば、生成バッチが大きくなってGPU当たりの処理量は改善し得るが、KV読出し量と事前処理の干渉も増える。

著者が分析した本番トレースは14日間・約1,010万要求・14モデルに及ぶ。入力トークン量は出力の約192倍で、入力の77.7%がキャッシュから再利用可能だった。要求継続時間の78.4%は生成段階に属し、生成中の待ち時間を含むTPOTが体感遅延を左右する。一方、別の1日間のインスタンス負荷観測では、実行中の要求数中央値は1インスタンス当たり0.76件であり、TPOT目標までの余裕が大きかった。

これらは三つの要件を導く。まず共有接頭辞の再計算を避けること。次にタスク別に設定されたTPOTサービス水準目標（SLO）を満たすこと。最後に、その余裕を使ってGPUを集約し稼働時間を減らすことである。どれか一つだけを最適化すると、他の要件が損なわれる。キャッシュ命中率だけを最大化すると要求が広く分散し、TPOTだけを小さくするとGPUが遊び、集約だけを進めるとキャッシュが失われて事前処理が増える。

## 手法

### 1. ゲートウェイと共有状態

PackServeは推論エンジン内部を改造せず、到着した要求の送り先を決める分散ゲートウェイに実装する。複数のゲートウェイは共有メタデータサービスから各インスタンスの負荷、待機要求、生成中要求、KV命中見込みを取得する。要求の入力長と接頭辞キャッシュの所在から、送り先ごとの追加事前処理費用とTPOTを予測する。選んだインスタンスへ要求を送った後は、エンジン側の既存バッチ実行が処理を担当する。

ゲートウェイを分散配置するため、巨大な中央キューで全要求を逐次処理する必要がない。一方、共有メタデータが古い場合は予測と実際の負荷がずれる。実行中の要求移動、GPUの自動増減、事前処理と生成の物理分離は本研究の制御範囲外である。これらの制約を明示することで、クラスタ内の要求配置だけでどの程度の資源効率を改善できるかを測る。

### 2. 事前処理と生成の白箱性能モデル

要求の入力のうち既にキャッシュされた接頭辞長を$C$、新たに計算するトークン数を$N$とする。Transformerの事前処理では新規トークンに対する行列計算が$N$に、注意の相互作用が$NC+N^2$に概ね対応する。この構造から、設定$\theta$ごとの事前処理時間を$T_{pf}(N,C)\simeq\alpha_0+\alpha_1N+\alpha_2NC+\alpha_3N^2$で近似する。実装ではキャッシュ依存の実測差を補う項も追加し、冷キャッシュ、チャンク単位の命中、最大入力境界などを事前測定する。

生成側では、同時生成要求数を$B$、全要求の文脈トークン総量を$S$とし、一回の生成反復時間を$T_{iter}(B,S)\simeq\beta_0+\beta_1B+\beta_2S$で近似する。$B$の増加は行列計算のバッチ化に有利だが、$S$が増えるとKV読出し量が増える。さらに事前処理と生成が同居するため、要求のTPOTは純粋な生成反復時間に、事前処理による待ち時間を加えた値として予測する。単純にバッチサイズが大きいほど速いと決めるわけではない。

モデル係数はGPU、モデル、推論エンジン設定ごとにオフラインで測定する。生成段階の予測が大バッチで楽観的になりやすいため、実際の生成のみの反復時間と予測値の比を、バッチ区間ごとの指数移動平均で補正する。更新重みは0.02で、比と補正係数に上下限を設ける。この補正は生成カーネルの測定に対して行い、事前処理干渉は別の項で計算する。実行中にすべての要求の将来長を正確に知ることはできないため、予測には残差が残る。

### 3. KV再計算予算による候補制限

まずGPUメモリ容量と要求受入上限を満たすインスタンス集合を作る。次に各候補について、完全なキャッシュ命中時と比べてどれだけ事前処理が必要になるかを、前節のモデルで予測する。最良候補に対する余分な再計算費用を、完全命中と完全非命中の差で正規化した値$\rho$を計算し、$\rho\leq\eta$の候補だけを残す。$\eta$は利用者が許容する再計算予算である。

$\eta=0$なら最も再計算費用が小さい候補だけを残す。$\eta$を増やすとキャッシュが少ないインスタンスにも要求を送れるようになり、生成バッチを大きくしやすい。ただし過剰に緩めると失われた接頭辞を再計算する費用が生成バッチ化の利得を上回る。単なるキャッシュ命中率の固定閾値では、同じ80%の命中率でも入力長が異なる場合の再計算時間を区別できないため、モデルで推定した時間差を用いる点が重要である。

### 4. TPOT目標に基づく受入判定

キャッシュ条件を満たした各インスタンスについて、新規要求を加えた後の生成同時実行数、文脈総量、新規要求の事前処理時間を予測する。生成反復時間に、事前処理が既存要求へ与える干渉を出力長で償却した項を加え、予測TPOTが設定された目標より小さい候補だけを残す。ここで使うのは実行中の生成要求数だけではなく、待機要求も含めた近い将来の負荷見込みである。

TPOT条件を満たす候補がある場合、その中で現在の生成要求数が多いインスタンスを優先する。同数ならキャッシュ再利用の多さ、待機要求の少なさで順序付ける。これにより、空いているGPUへ均等に散らすのではなく、遅延制約を守れる範囲で生成バッチを太くする。条件を満たす候補が一つもない場合は、キャッシュ条件を満たす集合に対する負荷認識型の代替配置へ戻る。代替配置は要求拒否を減らすが、全要求のTPOTを必ず保証するわけではない。

### 5. バッチ化の理論的な利得と干渉

平均到着率$\lambda$、一要求の事前処理時間$T_{pre}$、生成バッチサイズ$b$、純粋な一反復時間$T_{iter}(b)$を考えると、均一な定常負荷の近似では$TPOT_{real}\simeq T_{iter}(b)/(1-\lambda T_{pre})$となる。生成バッチが大きくなるほど純粋な生成処理量は改善し得るが、同時に新規要求の事前処理が頻繁になれば分母が小さくなり、実時間の生成処理量は伸び悩む。

原著の単一インスタンス測定では、TPOT目標30msから50msへ相当する点で生成バッチが約2倍になり、純粋な生成処理量は40.4%増えたが、事前処理干渉を含む実時間処理量の増加は14.4%にとどまった。これがキャッシュ再利用を優先しながら集約する理由である。この式は均質・定常負荷の近似であり、異種の長文脈要求が混ざる実運用で厳密な遅延保証を与えるものではない。

## 評価

### 実験条件と測定指標

| 項目 | 原著の条件 | 注意点 |
|---|---|---|
| GPU | NVIDIA H20 64台、1台96GB | 4GPU×16インスタンス、テンソル並列4 |
| 推論エンジン | SGLang、事前処理・生成同居 | 事前処理チャンク8192トークン |
| モデル | MiniMax-M2.5 230B | 実機再生評価で使用 |
| キャッシュ | FP8 KV、GPU側約100万トークン/インスタンス、ホスト側HiCacheは3倍 | GPU内とホスト側の二層 |
| 再生負荷 | 7,258要求、1,704セッション、平均2.02要求/秒 | 本番由来の1時間、最初10分はウォームアップ |
| 平均入力・出力 | 入力62.5K、出力556トークン、再利用可能接頭辞52.1K | 長い共有接頭辞を持つ |
| 比較 | vllm-dp、LMetric、llm-d+ | llm-d+の予測器は著者のモデルへ置換した比較 |
| 目標 | TPOT 30msと50msを別々に測定 | 一分ごとの中央値のP90を主なSLO評価に使う |

成功率は容量不足や10分以内の無応答を失敗として数える。GPU時間は、少なくとも一要求が活動中のインスタンス時間にGPU台数を掛けた稼働GPU時間であり、クラスタに設置した物理GPU台数の削減を直接意味しない。TPOTは出力トークン間の遅延で、初回トークン遅延TTFTとは別の指標である。原著は要求単位の極端な末尾遅延も分析するが、主たるSLO適合の報告は**一分ごとのTPOT中央値の分布**に基づく。個々の要求の全トークンが30msまたは50msを必ず下回ったわけではない。

### 端から端までの比較

| 指標 | 提案方式の結果 | 比較上の注意 |
|---|---|---|
| TPOT目標30msでのP90分単位中央値 | 24.0ms | 設定目標より小さい |
| TPOT目標50msでのP90分単位中央値 | 44.7ms | 設定目標より小さい |
| 稼働GPU時間 | LMetric比13.0～21.1%減 | 目標別の比較 |
| 稼働GPU時間 | llm-d+比16.8～24.6%減 | 比較方式の予測器は著者方式に合わせた |
| キャッシュ命中率 | 79.5～80.2% | LMetric 81.0%、llm-d+ 74.1～74.3% |
| 生成処理量 | LMetric比50.1～90.8%増 | 純粋な生成時間当たりの比較 |
| TTFT中央値 | 1.4～1.6秒 | LMetricは約1.3秒 |
| TTFTのP90 | 37.6～38.4秒 | LMetricは42.8秒、llm-d+は30ms条件で32.9秒 |

全方式が同じ成功率ではない。キャッシュ非認識のvllm-dpはこの負荷で成功率が約24%と低く、その他の方式は99.9%超だったため、著者は主な性能比較をLMetricとllm-d+へ絞っている。LMetricはTPOTを10.5～15.6msと小さく保つが、余裕を使ってGPUを集約していない。llm-d+もTPOT目標を満たすが、余裕の小さいインスタンスを優先するため、生成バッチが必ずしも最大化されない。提案方式はTPOTを許容範囲まで使い、少数のGPUで多くの要求を処理する。

### 構成要素除去実験：三段階の必要性

| 条件 | 原著の結果 | 解釈 |
|---|---|---|
| 容量制約のみ／キャッシュ制約のみ | 失敗率29.9～31.9% | 過負荷を抑えられない |
| TPOT制約のみ | 失敗率0.8%、P90分単位TPOT 59.4ms | 過負荷は減るが50ms目標超過 |
| キャッシュ＋TPOT制約 | 命中率+8.4ポイント、P90分単位TPOT 43.8ms | 再計算による干渉を抑える |
| 完全方式の代替配置あり | P90分単位TPOT 44.7ms | 要求単位P99 TPOTは代替配置なし比11.6%低いが、目標達成率は1.7ポイント低下 |

この実験は、単に要求を詰め込むだけではなく、TPOT予測で過負荷を避け、さらにキャッシュ再利用を保って事前処理干渉を抑える必要があることを示す。代替配置は要求拒否や極端な末尾遅延を緩和するが、TPOT目標達成率を少し犠牲にする。つまり複数の指標の間に明確な交換関係がある。

### 再計算予算と予測器の検証

再計算予算$\eta$を0から0.4へ増やすと、キャッシュ条件を満たす平均候補数は4.1から6.7へ増え、命中率は80.4～81.2%を維持した。稼働GPU時間は41.9から38.5へ7.9%減った。一方、予算を1まで緩めると候補は15.9へ増えるが、命中率は72.9%へ低下し、$\eta=0.4$に比べて事前処理GPU時間が9.6時間増え、稼働GPU時間も23.7%増加した。キャッシュを犠牲にし過ぎると集約の利点が消えるという重要な負の結果である。

予測器の比較では、生成TPOTの絶対誤差中央値が白箱モデルで10.6ms、比較するXGBoost方式で17.9msだった。要求到着から配置決定までの平均遅延はそれぞれ1.9msと132.9msである。大バッチでのオンライン較正を加えると、純粋な生成反復時間の平均絶対誤差が5.96msから0.85msへ減少した。これらは推論の生成品質ではなく、スケジューラの予測精度と決定時間の結果である。

### 1000台超の本番クラスタでの結果

著者は約700Bモデルを扱う1000台超のGPUクラスタで、従来のキャッシュ認識型負荷分散と提案方式を、それぞれ6日間、曜日と時刻を揃えた計12日間で比較した。平均稼働インスタンス数は34.7%減少し、インスタンス当たりの要求処理量は36.8%増加した。週末のインスタンス削減率は54.2%、平日は26.7%であり、軽負荷ほど集約の余地が大きい。

一方、実行中要求数はインスタンス当たり約2.3倍になり、TPOT中央値は目標の79.8%以下に収まったものの、**平均TTFTは従来方式比66.4%増加**した。GPU削減の主張だけを取り出して遅延が全般的に改善したと書くのは誤りである。またこの本番比較は同一時刻の無作為な同時割当試験ではなく、別の6日間を比較している。著者は曜日と時刻を揃えているが、負荷内容の差などの交絡が完全に排除されたわけではない。

## 既存研究との差と限界

既存のキャッシュ認識型負荷分散は命中率と負荷を両立させるが、TPOTの余裕を積極的にGPU集約へ使わない。TPOTを重視する方式は予測器に基づき候補を絞るものの、キャッシュ再計算による事前処理干渉を十分に抑えられない場合がある。PackServeはキャッシュ再計算費用をまず制限し、その後TPOTを守れる候補の中で生成同時実行数を最大化するという順序を採用する。比較するllm-d+には著者自身の予測器を組み込んでいるため、比較結果はスケジューリング方針の差を中心に示すが、未改変llm-d全体との直接比較ではない。

本研究は事前処理・生成同居構成とインスタンス内の接頭辞KV再利用を前提とする。事前処理と生成を別GPUへ分離する方式では、同居に由来する干渉項が消える一方、KV転送と二つのキューを考慮した別モデルが必要になる。グローバルKVプールを使う場合も、キャッシュ所在と転送費用を含めた新たな配置判断が必要となる。ゲートウェイは要求の送り先を決めるだけで、エンジン内部のスケジューラやGPU台数の自動増減は変更しない。

予測は平均的な生成長やオフライン測定に依存し、将来の要求到着、極端な長文脈、急なモデル挙動の変化を完全に予測できない。TPOT目標を守ったという結果も分単位の中央値ベースであり、すべての要求の厳密な遅延保証ではない。資源削減の指標は稼働GPU時間であり、GPUの電力計測に基づくジュール削減や炭素排出削減と同一ではない。本番でTTFTが大幅に増加することを含め、実装時には利用者の初回応答待ちと資源費用の許容範囲を明確にする必要がある。
