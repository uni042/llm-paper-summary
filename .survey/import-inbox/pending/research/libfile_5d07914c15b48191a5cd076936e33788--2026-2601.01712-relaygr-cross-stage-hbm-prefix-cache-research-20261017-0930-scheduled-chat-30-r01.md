# RelayGR：推薦パイプラインをまたいでKVキャッシュを局所保持する先行推論

## 概要

本研究は、対話用大規模言語モデルそのものではなく、利用者の長い行動履歴をTransformer系の生成型推薦モデル（Generative Recommendation; GR）へ入力するオンライン推薦基盤を対象とする。推薦処理は候補検索、粗い選別、最終ランキングという複数段階で進む。最終ランキングの第99百分位遅延（P99）は数十ミリ秒しか許されない一方、推薦精度を高めるために数千トークンの利用者行動履歴を使うと、その計算だけで時間予算を使い切る。

RelayGRは、候補商品と無関係な長期行動列が入力の前半にまとまっていることに着目する。検索段階でこの接頭辞を先行推論し、各層の鍵・値キャッシュ（Key-Value Cache; KVキャッシュ）をアクセラレータの高帯域メモリ（High Bandwidth Memory; HBM）に一時保持する。候補選別が終わって最終ランキングを実行するときには、同じ計算を繰り返さず、そのキャッシュを利用して短期履歴と候補商品だけを処理する。

ただし、キャッシュの生成時点では最終ランキングを実行するサーバーが確定していない。別サーバーへ送ると通信遅延が厳しいP99制約を破り、全利用者分をHBMへ常駐させると容量が足りず、全要求を先行実行すると演算資源とPCIe帯域を圧迫する。そこでRelayGRは、選択的な先行実行、利用者IDによる同一インスタンスへの振分け、ホストメモリへの短期退避を一体で設計する。

著者はHuawei Ascend NPUを使う本番環境の模擬構成で実際の問い合わせを評価し、パイプライン全体のP99が135ミリ秒以下という制約下で、扱える行動系列長を最大1.5倍、サービス水準を満たす処理量を最大3.6倍にしたと報告する。これは**推薦モデル向けの分散推論基盤**での結果であり、通常のチャットLLMや汎用GPUで同じ倍率が得られたわけではない。

## 問題設定と前提

### 三段階の推薦処理と遅延予算

検索段階は大量の候補を集め、粗ランキングが候補を減らし、精ランキングが高精度なモデルで最終順位を決める。全体のP99は数百ミリ秒程度、精ランキングには数十ミリ秒しか割り当てられない。モデル単体の平均遅延が低くても、同時リクエストが増えるとCPU前処理、埋め込み取得、PCIe転送、NPU演算の待ちが重なり、P99が急増する。したがって最適化の目標は単一問い合わせの平均速度ではなく、**制約を満たした状態で処理できる問い合わせ数**である。

長期の行動履歴は、商品候補が決まる前から利用でき、数日〜数か月の閲覧・クリックを含む。短期行動と商品候補に依存する交差特徴は後で確定する。長期接頭辞に対するモデル計算は複数の候補を採点する際に再利用できるが、従来は精ランキング段階で毎回計算していた。

### 通常の接頭辞キャッシュとの違い

対話LLMの接頭辞キャッシュは、共通のシステム指示や定型文を複数要求で共有することがある。これに対し、推薦の長期行動履歴は利用者ごとに異なる。全利用者分を常駐させる方法は現実的でなく、キャッシュの主な再利用機会は、**同じ要求が検索からランキングへ進む数百ミリ秒の生存期間**、および同じ利用者が短時間で繰り返す要求である。

また、対話LLMの事前入力処理（prefill）と逐次復号（decode）は連続した二段階だが、推薦ではその間に候補検索と粗ランキングがあり、消費側のサーバーが後で決まる。RelayGRはこの「消費先が後から確定するキャッシュの生存期間管理」を中心課題とする。

## 手法

### 1. 先行推論の対象を決める系列認識型トリガー（Sequence-aware Trigger）

検索と並列に軽量な利用者行動メタデータを取得し、長期接頭辞の長さや特徴次元から、精ランキングをそのまま実行するとP99制約を破りそうな要求だけを選ぶ。短い履歴では先行推論をせず、通常経路へ送る。ここで全履歴を先に転送してしまうと、トリガー自体が帯域を消費するため、判断には長さなどの軽量情報だけを用いる。

選ばれた要求でも、先行推論を無制限に開始しない。専用インスタンス1台当たりの受入率をQ_admit、先行計算からランキングまでの時間をT_lifeとすると、同時に保持するキャッシュ数は概ねL=Q_admit×T_lifeで見積もれる。キャッシュ1個のP99容量をkv_p99、HBMの予約割合をr1とすれば、L×kv_p99≤r1×HBMを満たすように受入率を制限する。これは実際の使用量が分布することをP99値で保守的に扱う容量モデルであり、全要求の最悪値を厳密保証するものではない。

さらに、モデル実行枠1個の持続可能な先行処理量をQ_m、同時モデル枠をMとし、Q_admit≤Q_m×Mを課す。全ランキングインスタンス数N、専用割合r2なら、システム全体の先行実行能力はQ_max≤Q_m×M×r2×Nで上限を見積もる。容量と演算の両方を満たすように受け入れることで、先行実行が本来の精ランキングを圧迫する事態を避ける。

論文の説明例では、先行処理35ミリ秒、Q_m約30件/秒、M=5、HBM32GBのうち半分をキャッシュへ予約し、1件当たり0.1GBと仮定する。生存キャッシュ上限は160個、演算上限は150件/秒となる。専用インスタンスが100台中10台なら全体の演算上限は1,500件/秒である。これは容量制約と生存期間制約を理解するための例示であり、実験での最大処理量をそのまま表す数値ではない。

### 2. 利用者IDに基づく配置親和性ルーター（Affinity-aware Router）

選択された要求には、商品候補を含まない応答不要の先行実行信号を送る。この信号には利用者ID由来の一貫ハッシュ鍵（consistency-hash-key）を付け、専用ランキングインスタンスに長期接頭辞を計算させる。結果は利用者IDを鍵にして、そのインスタンスのHBMへ保持する。

その後、粗ランキングで候補商品が確定した精ランキング要求にも同じ一貫ハッシュ鍵を付ける。負荷分散器とゲートウェイが同じ鍵で振り分けるため、先行計算と精ランキングは同じ専用インスタンスへ到着する。これにより、**精ランキングの重要経路で別サーバーからKVキャッシュを取得しない**という不変条件を実現する。

専用インスタンスは通常インスタンスとサービス名で区別する。短い要求は通常サービスへ送り、長い要求を専用サービスへ送る。CPU処理とPCIe帯域の干渉を抑えるため、1サーバー上の専用インスタンス数を通常1〜2個程度に制限する。キャッシュ生成から消費までの短い時間だけHBMを利用するため、全利用者の履歴を長期間HBMに保持する必要はない。

サーバーの増減などで一貫ハッシュの対応が変わり、キャッシュを持たないインスタンスへ到着した場合は、遠隔キャッシュを待つのではなく、キャッシュなしの通常推論へ戻る。これは性能最適化を諦めるが、推薦結果を得るための正しさを保つ設計である。

### 3. ホストDRAMを使う容量拡張器（Memory-aware Expander）

同じ利用者が短時間に画面を更新すると、別の要求で同じ長期履歴を再び使える。HBMだけでは多数の利用者のキャッシュを長く保持できないため、精ランキングで使い終えたキャッシュを同一サーバーのホストDRAMへ退避させ、次の要求時にHBMへ戻せるようにする。別サーバーへの通信を避ける点が重要であり、DRAM→HBMの転送自体は追加費用になる。

同一利用者の複数要求が同時到着すると、何度も同じキャッシュをDRAMから転送する危険がある。RelayGRは利用者単位の直列化キューを用い、キャッシュの状態を変える操作を同時に1件までに制限する。精ランキング要求の前に疑似的な先行処理ステップを挿入し、HBMにあればそのまま進み、なければDRAMを確認する。最初の要求だけが再ロードを行い、後続要求はHBM上の結果を再利用する。

先行実行信号が遅れてランキング要求より後に到着する場合もある。疑似先行ステップと利用者単位の直列化によって、順序の入れ替わりを許容しながら重複した再ロードを抑える。論文は同じ利用者の一連の要求について、DRAM→HBMの再ロードを実質的に1回へ抑えることを狙う。DRAM再利用率が高くても無制限に転送してよいわけではなく、再ロードの同時実行数も制限する。

### 4. 全体の要求フローと追加費用

要求到着時、検索と並行してトリガーが長期履歴の長さを調べる。必要かつ容量・演算の余裕がある要求だけ、同じ利用者鍵で専用インスタンスに先行推論を指示する。先行推論は各層のKVキャッシュψ(u)を生成してHBMに置く。検索と粗ランキングの後、商品候補を持つ精ランキング要求が同じインスタンスに到着し、ψ(u)を再利用して残りの短期履歴・交差特徴・候補商品を処理する。必要に応じてキャッシュをローカルDRAMへ退避し、同じ利用者の次の要求に備える。

新たな費用は、検索中のメタデータ確認、先行推論用のCPU処理と埋め込み転送、専用インスタンスの確保、HBMの予約、DRAMへの退避・再ロード、利用者鍵による負荷分散の偏りである。先行推論が検索段階に収まらない場合や、キャッシュが消費前に失われる場合は、効果が小さくなる。RelayGRはこれらの費用を無視するのではなく、入場制御と局所配置で上限を与える。

## 評価

### 実験環境・測定指標

著者は本番の構成と同じ負荷分散器・ゲートウェイ・推薦段階を持つ模擬環境で、実際の問い合わせを用いて測定する。専用ランキングインスタンスはHuawei Ascend 910C NPUに対応し、他のAscend型も追加評価する。対象はHSTUとその変種、LongerとRankMixerを組み合わせた推薦モデルなどで、系列長は約1,000から数万トークン、特徴次元128〜1,024、層数は数層から十数層である。

| 項目 | 実験の条件・意味 |
|---|---|
| パイプライン全体のP99制約 | 135ミリ秒以下 |
| 精ランキングのP99予算の例 | 約50ミリ秒 |
| 成功率条件 | 99.9%以上 |
| 主要アクセラレータ | Huawei Ascend 910C NPU、他型でも追加評価 |
| 基準方式 | 精ランキング段階で長期履歴も含め全計算を行う |
| RelayGR（DRAMヒット0%） | 検索中に先行計算、HBM保持のみ |
| RelayGR＋DRAM | 同一サーバーDRAMで短期再利用、ヒット率を変化 |
| 代表的なKV容量 | HSTU、2Kトークン、8層、256次元、fp32で約32MB/要求 |
| 評価する性能 | 最大許容系列長、P99、SLO準拠スループット、先行・再ロード・ランキング各段の遅延 |

P99は遅い側の1%に注目する指標であり、平均遅延とは異なる。スループットは秒当たりの処理要求数（Queries Per Second; QPS）で、同時実行数と混同しない。高い同時実行数は計算資源を使い切るため、平均処理量が増えてもP99が悪化し得る。

### 最大許容系列長と同時処理量

図11(a)では、利用可能なホストDRAM約500GBを使って再利用率約10%を得た場合、P99≤135ミリ秒を満たす最大系列長が基準方式比で最大1.5倍になる。これは任意のモデルで系列長上限が常に1.5倍になるという意味ではなく、当該環境・負荷・DRAM予算での上限結果である。

図11(b)では、長期接頭辞を検索段階へ移したことで、同じP99制約を満たす同時実行要求数が基準方式の約2倍となる条件を報告する。図11(d)ではDRAM再利用を加えるとSLO準拠スループットが最大3.6倍となる。**同時実行数の倍率とスループットの倍率は異なる指標**であり、両者を同じ実験条件の同一値として扱わない。

キャッシュの配置親和性がない場合は、別サーバーからのキャッシュ取得が必要になる。図12の遠隔取得遅延は局所キャッシュ参照の数百倍になる場合があり、数十ミリ秒の精ランキング予算を容易に使い切る。これは、単なるキャッシュ容量の追加だけでなく、生成・消費先の一致が必要であることを裏付ける。

### 長い系列・同時負荷に対する感度

図13(a)では、6,000トークンを超えると基準方式は同じSLO下で数QPSまで低下するのに対し、DRAMヒット0%のRelayGRでも数十QPSを維持する条件がある。DRAMヒット率が高い場合には、8,000トークンを超えても数百QPSを維持する条件を報告する。ただし、100%ヒット率は十分な再利用を仮定した感度実験であり、一般的な本番トラフィックで常に実現できる値ではない。

図13(b)では、約15,000トークンまでの系列に対して、同時負荷のないキャッシュロードは20ミリ秒未満、キャッシュを使うランキングは10ミリ秒未満となる設定を示す。長期接頭辞を再計算する事前入力処理は系列長とともに重くなるが、既存キャッシュの転送はおおむねキャッシュサイズに比例するため、系列長が大きいほど相対的な利得が増える。ただし転送も同時要求が増えると競合する。

検索段階の余裕時間を増やすと、先行計算をより多く重ねられる。図13(d)では検索P99が100ミリ秒の設定で、最大同時実行数が基準方式の約5倍となる条件を報告する。これは検索時間を意図的に延ばせば常に有利という意味ではなく、検索段階に元からある計算余裕を使えるときに効果が増すという結果である。

### モデル規模・候補数・再利用率の影響

図14(a)では、通常約512候補の商品を扱うところ、2,048候補まで増やしてもキャッシュを使う精ランキング部分を10ミリ秒未満に抑える条件を示す。図14(c)では特徴次元1,024の条件で、基準方式のスループットが50QPS未満になる一方、RelayGRは少なくとも2倍、DRAMヒット100%条件では約3倍となる。

図14(d)では層数を倍にすると基準方式のスループットが約50%減るのに対し、DRAMヒット100%のRelayGRでは約14%の低下にとどまる条件がある。16層の設定では基準方式比4倍以上となる条件も報告する。これはキャッシュが有効な系列の前半を省けるためであり、層数の増加そのものを無料化するわけではない。

図14(b)では、DRAMヒット0%のRelayGRは追加の先行計算によってNPU使用率が上がる場合がある。高いDRAMヒット率は同じ計算を再利用して追加負荷を減らす。この結果は「先行計算を増やせば必ず計算資源が節約される」という単純な説明を否定し、**余剰の検索段階と再利用率の組合せ**が重要であることを示す。

## 既存方式との差と推論基盤への示唆

SplitwiseやDistServeなどの対話LLM向け分離サービングは、事前入力処理と逐次復号を異なる装置へ配置し、その境界でKVキャッシュを受け渡す。RelayGRの対象は、接頭辞を計算する検索段階と、実際に使う精ランキング段階の間に別の業務処理が入り、最終配置が後から決まる環境である。キャッシュを生成した瞬間には消費先が未確定であるため、同じ利用者鍵で後段を誘導する必要がある。

一般のLLMサービングへ転用できる概念は、①後段で再利用される接頭辞を前段の空き時間に先行計算する、②キャッシュ生存期間とHBM容量から受入率を制御する、③生成・消費要求を同一ノードへ配置する、④ノード内DRAMへ短期退避する、⑤同じキーの再ロードを単一化する、という設計である。ただし、推薦特有の「候補商品に依存しない長期履歴」と同じ構造が通常のチャットLLM要求に存在するとは限らない。**技術的な類似性と、チャットLLMでの実測効果を混同しない**ことが必要である。

## 限界と適用条件

**推薦用途への限定。** 実証対象は推薦モデルとAscend NPUを使う多段パイプラインである。一般的なLLM推論、NVIDIA GPU、複数ノードの対話生成、未知のKVキャッシュ実装で同じ倍率を保証するデータはない。公開コードや汎用ランタイムへの統合状況も一次論文本文だけでは確認できない。

**利用者ごとの再利用が前提。** 長期履歴が頻繁に変わる、モデル重みや埋め込みが更新される、候補依存の計算が接頭辞に混ざる、といった条件では同じKVキャッシュを使えない。論文は更新頻度の高い短期履歴を先行対象から外すことでこの問題を緩和するが、一般の全入力に対するキャッシュ有効性を保証するものではない。

**HBMとDRAMの追加費用。** HBM予約は通常要求が使える記憶領域を減らし、ホストDRAMの退避・再ロードはPCIe帯域を使う。DRAMヒット率が低いと追加計算だけが増えることがある。100%ヒット率の感度結果を実運用の平均値として採用してはいけない。

**配置変更と障害。** 同じ利用者鍵を一貫ハッシュで振り分けても、インスタンス増減・障害時にはキャッシュ生成先と消費先が一致しない場合がある。RelayGRは通常推論へのフォールバックで正しさを保つが、最適化効果は失われる。利用者単位の直列化は重複ロードを防ぐ反面、同一利用者の極端な同時アクセスで待ちが増える可能性がある。

**評価の公開範囲。** 本番模擬環境での実問い合わせ評価は実用的だが、トレース全体や実装コードが一般公開されているかは本調査では確認できない。図の倍率は条件付きの最大値であり、環境・モデル・再利用率を跨いで単一の平均倍率へまとめない。著者が示す長期接頭辞の再利用によるランキングスコアの誤差上限εも、全ての異なるモデルで同じεを証明する普遍的保証ではない。
