# XLM：非自己回帰言語モデルの訓練・評価・生成を統一する研究用基盤

## 概要

自己回帰言語モデルは左から右へトークンを追加する標準的な生成手順を持ち、共通の訓練・推論ライブラリを利用しやすい。これに対して、非自己回帰言語モデルにはマスク拡散、挿入型生成、編集型生成など複数の方式がある。方式ごとに入力データの加工、損失の計算、出力の反復処理、終了条件が異なるため、研究者は論文ごとに専用の訓練・生成コードを作りがちである。実装の違いが実験結果へ混ざり、同じデータセット上の比較や別方式への改造を難しくする。

XLMは、小規模な非自己回帰言語モデルを迅速に試作するためのPythonパッケージである。共通基盤の役割を、データを管理するDataModuleと、モデル・損失関数・予測器をつなぐHarnessへ絞り、方式固有の実装は別のクラス・別のディレクトリへ分離する。設定管理にはHydraを使い、設定ファイルでモデルやデータ整形器を切り替える。論文は挿入型言語モデルの構築手順を具体的に示し、StarEasyとLM1Bで複数方式の再現実験を行う。

重要なのは、**XLMが既存の拡散モデルを実行時に自動高速化するランタイムではない**ことである。研究者が異なる生成方式を同じ土台で比較できるようにするソフトウェア設計の貢献であり、vLLMやSGLangのような連続バッチ・KVキャッシュ管理・複数GPU分散推論を提供することが主目的ではない。論文に掲載された正答率や負の対数尤度は、基盤そのものによる速度改善を示す数値ではなく、共通基盤上で再現したモデル方式の結果である。

## 問題設定

### 方式ごとに変わるデータ、損失、復号

自己回帰モデルなら、入力列の次位置を予測する教師信号を作り、生成時に次トークンを繰り返し追加する。マスク拡散型では、入力の一部をマスクして復元対象とし、生成時に複数のマスク位置を反復して確定する。挿入型では、既存列のどこへ語を挿入するかと、どの語を入れるかを同時に選び、終了判定も行う。これらはネットワーク本体を共有できる場合でも、訓練データの整形と予測ループが大きく異なる。

既存の汎用深層学習ライブラリはデータローダー、最適化器、ログなどを提供するが、非自己回帰の生成方式を統一して比較するための規約は限定的である。論文が挙げる課題は、研究ごとに独立した実装を使うことによる重複開発、実験設定の不整合、データ整形と生成手順の再利用困難、論文の再現確認の負担である。XLMはこれらを共通の実行骨格と交換可能な方式固有部品に分ける。

### 設計方針と対象範囲

本方式は、すべての非自己回帰モデルを一つの巨大な継承階層に押し込むのではなく、組み合わせ（composition）を優先する。共通部分が方式固有のメソッドを呼び出し、方式側は必要な実装を自由に定義する。研究コードでは実装の複製を許す「分岐よりコピー」という方針も採る。一般的な製品コードの重複削減原則とは異なるが、実験用の方式固有コードを小さく独立させることを優先する。

対象は小規模な非自己回帰モデルの試作、訓練、評価、生成である。論文は大規模LLMを大量同時利用者へ提供するためのメモリ割当、要求スケジューリング、投機的復号器の自動統合、GPUカーネル最適化を主張していない。ここを区別しないと、ソフトウェアの再利用性を示す評価を推論処理能力の改善と誤読する。

## 手法

### 1. DataModuleとDatasetManagerの責務分離

データ側の中心はTextDataModuleで、PyTorch LightningのDataModuleを土台にする。DataModuleは複数のDatasetManagerを保持し、訓練、検証、試験、予測という実行段階に応じて適切な管理器を選ぶ。各DatasetManagerは、一つのデータセットの取得、前処理、キャッシュ、データローダー設定、バッチ整形器の管理を担当する。

一つのデータセットを複数の実行段階で再利用でき、逆に一つの段階で複数データセットを使うこともできる。たとえば訓練ではマスクを付与する整形器を使い、生成ではプロンプトだけを渡す整形器を使う。同じ原データを別の段階で使い回しつつ、生成方式によって必要なバッチ形式だけを差し替えられる。この設計は、データセットをモデルの内部へ直接埋め込む方式と異なる。

管理器は通常の配列型データセットと逐次読み込み型データセットに対応し、単一GPU、単一ノード複数GPU、複数ノードの訓練設定も受け付ける。ただし、複数GPUに対応するという実装上の機能は、特定の通信最適化や高いスケーリング効率を実測したことを意味しない。データの再利用と訓練設定の共通化が中心的な利点である。

### 2. Harnessによる方式固有部品の接続

HarnessはLightningModuleを継承し、モデル本体、損失関数、予測器、評価指標などのインスタンスを持つ。モデルの前向き計算はModelへ、損失計算はLossFunctionへ、反復生成はPredictorへ委譲する。共通Harnessは各方式の生成ループの詳細を知らず、対応する部品を呼び出すだけでよい。

例えば挿入型言語モデルでは、Modelが語彙予測と終了判定の出力を返す。LossFunctionは隠した語の交差エントロピーと、生成が終了しているかを判定する二値分類損失を計算する。Predictorは挿入位置と語彙を繰り返し選び、終了判定が成立したところで生成を止める。マスク拡散型へ変更する場合は、マスク位置の予測損失と反復マスク解除のPredictorへ置き換える。

方式固有の生成器をHarnessから切り離したため、推論アルゴリズムの変更は必ずしも学習ループ全体の変更を必要としない。逆に、同じモデル本体でも損失と予測器の組み合わせを変える実験ができる。ただし、互換性のない部品を自由に組み合わせても正しく動く保証はなく、バッチ形式や出力型の契約は実装者が管理する必要がある。

### 3. Hydra設定で部品を組み立てる

Hydraの設定にはモデル本体、モデル方式、データモジュール、整形器、予測器のクラスとパラメータを階層的に記述する。実行時に`hydra.utils.instantiate`で指定クラスを生成し、Harnessへ注入する。設定ファイルを切り替えるだけで、共通実行コードを変えずに別方式・別データセットへ移れる。モデルの独立性を保つため、方式ごとのPythonコードは別ディレクトリへ置く。

この動的なクラス生成は研究の柔軟性を高めるが、任意のPythonクラスを設定から読み込めるため、信頼できない設定ファイルを無検査で実行する用途には向かない。論文自身が研究コードでは柔軟性を優先する設計であると説明しており、運用上の安全性と研究開発の迅速性を区別する必要がある。

### 4. 挿入型モデルを例とする新方式の追加

論文はStarEasyという星型グラフの経路生成課題を使い、挿入型言語モデルを一から追加する流れを示す。最初に`xlm-scaffold ilm`で方式用のディレクトリと空の部品ファイルを生成する。Modelには語彙と停止の予測を、LossFunctionには語彙復元損失と停止判定損失を実装する。訓練用Collatorは正解経路の一部を隠して復元対象を作り、予測用Collatorは開始点・目標点・グラフの辺情報だけを入力へ置く。

Predictorは、現在の部分列をモデルへ渡して挿入位置と語彙を選び、停止が予測されるまで繰り返す。入力はグラフの辺集合、開始点、終点であり、出力は経路を表すトークン列である。モデル方式の各部品をHydra設定に登録すると、同じコマンド体系で訓練、評価、生成を切り替えられる。論文は一括の実行入口として`xlm job_type=[JOB_TYPE] job_name=[JOB_NAME] experiment=[CONFIG_PATH]`を示す。

この例は、非自己回帰の生成手順が標準の次トークン予測とは異なっても、共通の実験管理を使えることを示す。ただし、ひな型を生成しただけで損失や予測器の実装が不要になるわけではない。方式固有のアルゴリズムを研究者が記述しなければならない点は残る。

### 5. パッケージ分割と再利用

基盤は`xlm-core`として、参照モデルは別の`xlm-models`として公開される。参照実装を利用する研究者は、共通部品を読み込んで実験を始められる一方、独自の方式コードを単独パッケージとして配布することもできる。実装にはPyTorch、PyTorch Lightning、Hydraを利用し、既存の学習ログ、チェックポイント、評価処理と接続する。

この分割は「方式を比較するための共通実験基盤」と「方式固有のモデルコード」の境界を明確にする。推論基盤の観点では、復号器をPredictorとして交換できる点が関連する。しかしXLMの目的は低レベルのGPU実行計画やサービング性能の最適化ではなく、研究段階の反復開発と再現性を改善することである。

## 評価

### 何を測っているか

論文§6は、既存の自己回帰型、マスク言語型、マスク拡散型、挿入型をXLM上で実装し、先行研究の既報値に近い結果を再現できるかを検証する。評価は二種類あり、星型グラフの経路生成でのトークン正答率・系列正答率と、LM1Bでの生成文の負の対数尤度・エントロピーである。実装の再利用性の検証であり、モデル推論時間やGPU消費メモリの改善を定量的に比較する実験ではない。

| 評価項目 | 原著の設定 |
|---|---|
| 合成経路生成 | StarEasyのEasy・Medium・Hardの3難易度 |
| 比較モデル | 自己回帰ARLM、挿入型ILM、マスク言語MLM、マスク拡散MDLM |
| 経路生成指標 | トークン正答率、系列全体の正答率 |
| 言語生成 | LM1Bの非条件付き生成 |
| LM1Bのモデル | 12層Transformerを方式別に訓練 |
| 言語生成指標 | Llama 3.2 8Bで評価した負の対数尤度、生成文のエントロピー |
| 再現の目的 | 先行研究の既報結果と大きく矛盾しないことの確認 |
| 未掲載の主要指標 | 訓練時間、復号トークン/秒、端から端までの遅延、ピークVRAM、同時要求数 |

### StarEasyの再現結果

| モデル方式 | Easy系列/トークン | Medium系列/トークン | Hard系列/トークン |
|---|---:|---:|---:|
| 自己回帰型ARLM | 33.1 / 81.7 | 77.2 / 82.1 | 25.2 / 43.7 |
| 挿入型ILM | **100.0 / 100.0** | **100.0 / 100.0** | **97.5 / 98.2** |
| マスク言語型MLM | 100.0 / 100.0 | 83.1 / 98.0 | 25.3 / 79.6 |
| マスク拡散型MDLM | 100.0 / 100.0 | 36.5 / 90.6 | 21.0 / 54.9 |

表の単位は百分率である。EasyではILM・MLM・MDLMが全て100%を達成するが、HardではILMの系列正答率97.5%に対してMDLMは21.0%となる。これは**生成方式とタスクの相性の差**を示すものであり、XLMがMDLMをILMより遅く実行したことや、XLMがILMの正答率を改善したことを意味しない。論文は元の先行研究で報告された値とおおむね2%以内で一致したと述べ、再現基盤としての妥当性を主張する。

### LM1Bの生成結果

| 指標 | 原コーパス | ARLM | MDLM | ILM |
|---|---:|---:|---:|---:|
| Llama 3.2による負の対数尤度 | 3.71 | 3.94 | 4.81 | 4.72 |
| エントロピー | 3.08 | 3.12 | 3.70 | 2.81 |

12層Transformerを方式ごとに訓練して生成文を評価した。負の対数尤度が低いほど、評価器であるLlama 3.2が生成文を高確率と判断する傾向を示すが、これは人手による品質評価や生成速度ではない。ILMはMDLMより低い負の対数尤度を示す一方、エントロピーは低く、多様性に違いがある。生成分布の評価だけから各方式の長文推論品質やGPU処理能力を断定しない。

### 再現性に関する解釈

XLMの実験は、共通のデータ管理・実験実行・方式固有部品の交換によって、先行研究に近い結果を得られることを示す。単一のソフトウェア構成で異なる方式を比較できる利点はあるが、論文は「同じモデル・同じハードウェア・同じ条件でXLMを導入したら訓練時間が何%減った」という比較を行っていない。したがって、フレームワークの開発効率の主張は設計と実装例に基づくものであり、定量的な開発工数削減実験ではない。

## 既存研究との差

Hugging Face TransformersやPyTorch Lightningは広い範囲のモデル・学習手順を支える。vLLMなどの推論エンジンは自己回帰LLMの実行効率、要求処理、キャッシュ、GPU資源の利用を中心に設計される。XLMはこのいずれとも直接の性能競争を目指さず、**非自己回帰生成方式ごとの実験コードを小さな交換可能部品へ分ける**点を主題にする。

具体的には、データの前処理をDatasetManagerへ、方式固有の損失をLossFunctionへ、反復生成の停止・挿入・マスク解除をPredictorへ分離する。Hydra設定でこれらを接続し、実験入口とログ処理を共通化する。新しい生成アルゴリズムを評価する際、データセットやモデル本体を再利用しやすくなる。一方、GPUカーネルの融合、推論時のKVキャッシュ最適化、分散スケジューリングは別の基盤との統合が必要である。

## 限界と今後の適用範囲

**小規模モデルの研究用である。** 論文は非自己回帰モデルの試作を目的とし、数十Bパラメータのモデルや多数GPUの実運用を検証していない。DataModuleが複数GPUの訓練設定を受け付けることと、LLMサービングの高いスループットを保証することは異なる。マスク拡散の実装があるからといって、既存の大規模推論エンジンと同じ最適化が得られるわけではない。

**性能改善の因果評価がない。** StarEasyの正答率とLM1Bの負の対数尤度は、方式の再現結果である。XLM自体を使わない実装との処理時間、GPUメモリ、開発工数、デバッグ時間の定量比較はない。特に「非自己回帰モデルは並列生成できる」という一般論から、XLMを使えば実機で高速化すると推論してはいけない。

**設定の動的注入には安全上の注意が必要である。** Hydraのクラス生成は柔軟だが、信頼できない設定を受け取る公開サービスでは任意のコード読み込みにつながるおそれがある。研究環境の設定ファイルを信頼できることを前提とし、製品運用では権限・設定検証・実行環境の分離が必要になる。

**部品の型・バッチ契約は自動で整合しない。** Model、LossFunction、Predictorを交換可能にする設計でも、出力辞書の項目や入力形状、停止条件は方式ごとに異なる。研究者が適切なCollatorと損失・予測器を実装し、同じ意味の評価指標を選ぶ必要がある。共通Harnessがあるだけで異方式の品質比較が完全に公平になるわけではない。

**評価範囲と拡張計画を区別する。** 論文の付録では非テキストの系列、分子生成、追加モデル、FlexAttention等の拡張予定を述べるが、予定は実装済みの機能として扱わない。パッケージ公開時点と現行版のAPI互換性についても、利用前に公式リポジトリの更新を確認する必要がある。
