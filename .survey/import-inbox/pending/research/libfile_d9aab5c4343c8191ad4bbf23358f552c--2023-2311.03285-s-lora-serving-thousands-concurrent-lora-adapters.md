# S-LoRA: Serving Thousands of Concurrent LoRA Adapters

> KVキャッシュとLoRA重みを統一ページ管理し、異種アダプタ計算を専用カーネルでバッチ化して、単一基盤モデルから数千アダプタを同時提供する。

## 概要

低ランク適応（Low-Rank Adaptation; LoRA）は、基盤モデルの重みを固定したまま小さな低ランク行列だけを学習するため、利用者や用途ごとに多数の派生モデルを作りやすい。しかし推論時にLoRAを基盤重みへマージすると、アダプタごとに巨大な基盤モデルの複製が必要になり、別アダプタの要求を一つのバッチへまとめにくい。逆に要求ごとにアダプタを入れ替えると、GPUへの重み転送と直列化がスループットを制限する。

S-LoRAは基盤計算 `xW` とLoRA追加計算 `xAB` を分離する。全要求で共通する高価な `xW` は一つの大きな行列積へまとめ、要求ごとに異なる `xAB` だけを専用カーネルで処理する。全アダプタはホストメモリに置き、その時点の実行バッチで使うものだけGPUへ取り込む。この構造により「GPUに置けるモデル数」ではなく「ホストメモリに置けるアダプタ数」まで収容数を拡張する。

ただし動的アダプタはランクが異なり、KVキャッシュも系列長に応じて増減するため、単純な連続領域割当では断片化が大きい。S-LoRAは両者を同じページプールで管理する統一ページング（Unified Paging）を導入し、非連続ページから直接計算できる専用CUDAカーネルと、次バッチで必要なアダプタの先読みを組み合わせる。Llama-7B/13B/30B/70BをA10G/A100で評価し、単一A100 80GBのLlama-7Bでは2000アダプタでも約7.6 req/sを維持した。

## 問題設定

単一LoRAなら、低ランク更新 `AB` を基盤重み `W` に事前マージすれば推論時追加演算を消せる。しかし多数のLoRAを同時提供すると、マージ済み `W+AB_i` をアダプタ数だけ保持するか、要求のたびに加算・減算して入れ替える必要がある。前者はGPUメモリを基盤重みの複製で消費し、後者は異なるアダプタの同時実行を妨げる。

そこで `xW + xAB_i` をそのまま計算すれば基盤 `xW` はアダプタをまたいでバッチ化できるが、別の問題が生じる。各要求は系列長もLoRAランクも異なるため、通常のバッチGEMMへ詰めるとパディングが増える。またGPUに常駐できないアダプタを動的にロードすると、可変サイズのアダプタと成長するKVキャッシュが同じGPUメモリを奪い合い、断片化とI/O待ちが生じる。

複数GPUではさらに、基盤モデル用の既存テンソル並列へLoRAのA/B行列を素朴に追加すると余分な全収集（all-gather）や全削減（all-reduce）が増える。S-LoRAは計算、メモリ、通信を個別最適化するのではなく、多数アダプタを一つのオンラインバッチへ混在させることを前提に三者を合わせて設計する。

## 手法

### 基盤計算とLoRA計算の分離バッチ

各線形層を `xW + xAB` として実行し、基盤重み `W` の行列積は全要求をまとめた通常GEMMへ送る。アダプタ側だけ要求ごとのA/Bを参照するため、基盤モデルをアダプタ数だけ複製せずに済む。LoRA計算を追加する代わりに、より高価な基盤計算のバッチを大きくできるという交換条件である。

スケジューラは要求単位ではなく反復単位で実行バッチを更新する。空きができれば新規要求を追加し、終了要求を除く。アダプタ・クラスタリングでは同じアダプタの要求をまとめることで同時にGPUへ載せるアダプタ数を減らせるが、待ち時間や公平性を悪化させる可能性があるため、論文はクラスタ数を変えた構成要素除去実験も行う。

### 統一ページングとアダプタ先読み

統一ページングは、KVキャッシュ `(S,H)` とLoRA重み `(R,H)` が隠れ次元Hを共有することを利用し、H要素を1ページとする単一メモリプールへ両者を非連続に配置する。KVは系列長Sに応じてSページ、アダプタはランクRに応じてRページを消費する。これにより異なるランクのアダプタを出し入れしても大きな連続領域を要求せず、KVとアダプタの空き容量を固定分割しない。

全アダプタはホストメモリに保持し、現在のバッチに必要なものだけGPUプールへ載せる。現在バッチの実行中に待ち行列から次バッチで必要になりそうなアダプタを予測し、空きページへ先読みすることでPCIe転送を計算と重ねる。したがって収容可能アダプタ数はGPU容量ではなく主としてホストメモリ容量で決まる。

### 非連続・異種LoRA用カーネル

ページング後のアダプタは連続しておらず、ランクも要求ごとに異なる。S-LoRAはプリフィル用の多サイズ・バッチ収集行列積（Multi-size Batched Gather Matrix-Matrix Multiplication; MBGMM）と、デコード用の多サイズ・バッチ収集行列ベクトル積（MBGMV）を使い、非連続ページから必要な重みを集めながら演算する。

通常のバッチGEMMのように最大ランク・最大系列長へパディングしないため、異種アダプタが同一バッチに混在しても無駄な演算を抑えられる。実験ではTriton版に加えPunica由来カーネルを非連続メモリ・複数ランクへ拡張し、後者を使用している。

### LoRA向けテンソル並列

基盤モデルのMegatron型テンソル並列にA/B行列の分割を合わせる。LoRA中間表現のランクrは隠れ次元hよりはるかに小さいため、追加通信を大きな活性値ではなく小さなランク次元へ寄せる。論文の通信量解析では基盤側が `2(N-1)Bh/N`、LoRA追加分が `5(N-1)Br/N` となり、`r << h` なので追加通信を小さくできる。

Q/K/V投影と出力投影でも同じ考え方を使い、LoRA側の全収集・全削減の一部を基盤モデル側の通信へ融合する。評価ではLoRA通信あり／なしのスループット差が小さく、2 GPUから4 GPUへ増やすとメモリ律速の緩和により2倍超のスループット増加が観測された。

## 主要結果

| 条件 | 結果 | 解釈 |
|---|---:|---|
| A100 80GB、Llama-7B rank 8、5アダプタ | S-LoRA 8.05 req/s、vLLM-packed 2.04、PEFT 0.88 | 少数アダプタでも基盤計算の共有バッチ化が効く |
| 同、100アダプタ | 7.99 req/s、vLLM-packedはOOM、PEFT 0.25 | GPU複製方式は収容数で破綻 |
| 同、1000/2000アダプタ | 7.64 / 7.61 req/s | active adapter数が頭打ちになり、総アダプタ数増加の追加費用が小さい |
| Llama-13B、A100 80GB | 2アダプタ4.49 req/s、100で4.28、1000で3.96 | モデルが大きくてもホスト保持方式が拡張 |
| 最大比較 | vLLM-packed比最大4×、PEFT比最大30× | バッチ化・ページ管理・専用カーネルの複合効果 |
| 30B/70B複数GPU | 2→4 GPUでスループット2倍超 | メモリ律速緩和による超線形域を観測 |

統一ページングや専用カーネルを外した変種はスループットが低下し、アダプタ数が増えるほど差が明確になる。実トレースでも合成負荷と同じ傾向を示す。アダプタ・クラスタリングは小さいクラスタ数で改善する場合がある一方、効果は大きくなく、スケジューラ費用や公平性との交換条件がある。

## 既存研究との差

vLLMのページ化注意は動的KVキャッシュだけをページ管理する。S-LoRAは同じ隠れ次元を持つLoRA重みまで同一プールへ入れ、KVとアダプタ間でGPU空き容量を融通する。単純な「LoRA対応vLLM」ではなく、ホスト常駐・先読み・異種カーネルまで一体化している。

PEFTのようなアダプタ切替は同一アダプタの要求をまとめてから重みを交換するため、異なるアダプタ間の同時バッチ化を逃す。S-LoRAは基盤GEMMだけを共有し、低ランク追加計算を分離することで、異なるアダプタを同じ反復へ入れる。

## 限界

最大30倍はPEFTというサービング最適化を持たない比較対象に対する値で、vLLM-packedに対する最大値は4倍である。倍率だけを一般的なLoRAサービング方式すべてへの優位と解釈すべきではない。

全アダプタをホストメモリに置くため、総アダプタ数の上限は消えるのではなくGPU容量からホスト容量へ移る。先読みが外れる場合やPCIe帯域が不足する場合にはアダプタロード待ちが再び露出する。

評価の実トレースはChatbot Arenaの「異なる基盤モデル」を「異なるLoRAアダプタ」と見なして再構成したもので、実際の大規模LoRAサービスの人気分布そのものではない。またLlama-70B評価は論文独自の構成で、公式70Bと完全に同一ではない。
