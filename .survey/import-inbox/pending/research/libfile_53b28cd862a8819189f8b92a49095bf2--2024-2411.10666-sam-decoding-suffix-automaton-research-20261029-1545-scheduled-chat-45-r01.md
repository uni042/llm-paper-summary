# SAM-Decoding：接尾辞オートマトンによる検索型投機的デコード

## 概要

大規模言語モデルの自己回帰生成では、通常は一回の前向き計算で一つの次トークンを確定する。投機的デコードは、軽い手段で複数の候補トークンを先に提案し、元の大きなモデルがまとめて検証することで生成時間を減らす。候補を元モデルと整合する形で検証する限り、単純に小型モデルの出力を採用する場合と異なり、目標モデルの生成結果を保持できる。ただし、草案を作る別モデルの費用が大きかったり、候補が受理されなかったりすると高速化は縮む。

SAM-Decodingは、出力の一部が入力や過去の文章と一致するという性質を利用し、接尾辞オートマトン（Suffix Automaton、SAM）から草案を取得する方式である。静的な文章集合と、現在の入力・生成済み文章の双方を索引化し、直近系列と一致する最長の接尾辞を探す。一致箇所の後ろに続くトークンを草案として取り出し、必要ならトークン再利用法やEAGLE-2の草案へ切り替える。接尾辞リンクを用いる状態遷移は償却平均で一トークン当たり定数時間となり、固定長のn-gram探索より長い一致も扱える。

Vicuna-7B-v1.3、RTX A6000、バッチ1、貪欲生成のSpec-Benchで、通常生成比の速度倍率はPLDの1.56倍に対しSAM-Decodingが1.84倍だった。トークン再利用法併用では2.27倍、EAGLE-2併用では2.58倍となる。一方、検索元に似た文章が少ない課題では利益が小さく、HumanEvalではEAGLE-2に対する上積みが限定的である。静的索引の構築費用とコーパス依存性も運用上の重要な条件となる。

## 問題設定と先行研究

従来の検索型投機的デコードには、現在の入力内で一致するn-gramを探すPrompt Lookup Decoding（PLD）と、別の文章集合から候補を検索するRESTなどがある。PLDは現在の文章に似た表現があれば強いが、同じ系列内に候補が存在しない場合は検索に失敗する。RESTは外部文章集合を使えるが、静的な接尾辞配列と一致長の制限があり、生成中に伸びる文章を同じ構造へ効率よく取り込むのが難しい。

また、要約や検索拡張生成では元の文章を再利用する確率が高い一方、自由な対話や数学推論では草案の文字列一致が弱くなる。検索だけに依存する方式は、課題が変わると草案の受理率が落ちやすい。著者らは「検索元を二種類に増やす」「最長一致を効率よく更新する」「一致長に応じて別の草案生成方式へ逃がす」の三つをまとめて解決する。

接尾辞オートマトンは文字列に現れる部分文字列を状態と遷移で表現する索引である。状態は複数の部分文字列をまとめて持ち、`next`遷移で次のトークンへ進み、`link`でより短い接尾辞を表す状態へ戻る。文字列長Lに対する構築費用はO(L)で、生成時の増分遷移と接尾辞検索は償却平均O(1)とされる。ただし論文は一回の遷移の最悪計算量がO(L)となりうることも明示している。「あらゆる入力で厳密に定数時間」と解釈してはならない。

## 手法

### 1. 静的SAMと動的SAMを別々に持つ

静的SAMは、あらかじめ収集した文章集合を一つの参照文字列へ連結し、文の境界にEOS等の区切りを入れてオフラインで構築する。実験ではVicuna-7BがStanford Alpaca、GSM8K、Python指示データに対して生成した文章を材料とした。各状態には、その状態に対応する部分文字列の最も早い終了位置`min_endpos`を記録する。これにより、現在の末尾と一致する位置を見つけた後、その位置に続く文章を草案として切り出せる。静的SAMには頻出の後続状態を上位候補として持たせ、枝分かれする木構造の草案も構築できる。後続頻度の計算はオフラインなので生成時の費用に含めないが、索引構築と保管の費用がなくなるわけではない。

動的SAMは現在の入力文と、目標モデルが既に受理した生成結果を参照文字列として持つ。生成が進むたびに状態と索引を増分更新し、同じ回答内で繰り返す表現や入力から再利用できる文章を探す。静的SAMが一般的な外部表現を提供するのに対し、動的SAMは当該要求の文脈へ直接適応する。著者の切除実験では動的SAMを外したときの低下が大きく、動的文脈の寄与が支配的な条件が多かった。

### 2. 最長接尾辞一致から草案を生成する

各生成ラウンドでは、直近までの確定系列を二つのSAMへ入力し、現在の状態と一致長を更新する。新しいトークンの遷移が存在しなければ接尾辞リンクをたどって短い一致へ戻り、遷移可能な状態を探す。動的SAMでは`min_endpos`で特定した位置の後続nトークンを候補にする。静的SAMでは状態ごとの頻出後続を使い、Prim法で候補木を構成する。いずれも「元の文章に続いていたトークン」を草案にするだけで、目標モデルがその続きを選ぶと保証するものではない。

静的SAMと動的SAMの一致長をそれぞれl1、l2とする。動的な一致の方が受理されやすいという実測に基づき、静的側は`l1 > l2 + lbias`のときだけ優先する。`lbias`は静的文章が少し長く一致した程度では、現在の文脈からの候補を置き換えないための余裕である。検索元の選択が「最長の文字列を無条件に選ぶ」だけではない点が重要である。

### 3. 目標モデルによる一括検証と索引更新

候補の生成後、目標LLMが草案を一括評価し、元の生成規則と整合する接頭部分だけを受理する。受理したmトークンを確定系列へ追加し、静的SAMではそのトークンで状態遷移する。動的SAMでは状態を遷移させるとともに、各トークンを参照文字列と索引へ追加する。誤った候補の未受理部分は、確定した文章へ追加しない。これにより、投機的生成の高速化と、元モデルの検証を分離する。

一回の検索で長い草案を得ても、受理数が短ければ検証に要する計算が無駄になる。逆に、受理が長く続く課題では目標モデルの呼出回数を減らせる。したがって索引の検索時間だけでなく、草案の長さ、受理トークン数、目標モデルの検証費用を一緒に測る必要がある。

### 4. 補助投機方式との適応的切替

検索で十分長い一致が得られないときは、トークン再利用法またはEAGLE-2が作る草案を使う。トークン再利用法は生成中のトークン間の後続確率を記録して候補木を作るモデル不要の方式で、EAGLE-2は専用の小型デコーダを用いる方式である。SAM側の一致長と、補助方式に割り当てた仮想一致長`lthreshold`を比較して選択する。論文では補助方式ありの`lbias`と`lthreshold`を通常5に設定し、補助なしでは`lbias=0`とした。

この切替は、草案の実際の受理確率を学習したものではなく、一致長を信頼度の代理とするヒューリスティックである。文字列が長く一致しても次の単語の分布が変わることはある。著者らも将来の課題として、検索結果と補助草案の選択器を学習する案を挙げる。切替の追加効果は、補助方式単独の性能と検索元の分布に依存する。

| 観点 | 一次論文の設定 |

| GPU・CPU | NVIDIA RTX A6000 48GBを1基、20コアCPU |
| 実装 | PyTorch 2.3.0、Transformers 4.46.1、CUDA 12.1、半精度 |

| 比較対象 | PLD、REST、PIA、Lookahead、トークン再利用法、EAGLE-2 |

上記の実時間倍率は単一A6000、低バッチ条件での測定である。大量の同時要求を処理するサービングで同じ倍率を得たわけではない。RESTとLookaheadの一部は原著側の評価環境での数値を併記しているため、すべてが同一の完全な実装条件での直接比較ではないことにも注意が必要である。

## 主要結果

### 1. 三つの課題群のスループットと倍率

| 方式 | Spec-Bench 受理数/速度/倍率 | HumanEval 受理数/速度/倍率 | HAGRID 受理数/速度/倍率 |
|---|---|---|---|
| PLD | 1.75 / 59.02 / 1.56倍 | 1.65 / 59.04 / 1.52倍 | 2.03 / 44.11 / 1.29倍 |
| SAM-Decoding | **2.30 / 69.37 / 1.84倍** | **2.64 / 88.91 / 2.29倍** | **2.44 / 76.72 / 2.24倍** |
| トークン再利用法 | 2.83 / 69.65 / 1.84倍 | 2.78 / 75.44 / 1.94倍 | 2.88 / 66.17 / 1.93倍 |
| SAM＋トークン再利用法 | 3.03 / 85.73 / 2.27倍 | 2.94 / 95.08 / 2.45倍 | 3.23 / 87.93 / 2.57倍 |
| EAGLE-2 | 4.36 / 90.14 / 2.38倍 | 5.13 / 125.77 / 3.24倍 | 4.15 / 82.61 / 2.41倍 |
| SAM＋EAGLE-2 | 4.62 / 97.56 / 2.58倍 | 4.95 / 130.28 / 3.35倍 | 4.75 / 96.60 / 2.81倍 |

速度の単位はトークン/秒であり、受理数は一回の生成ラウンド当たりの平均である。Spec-BenchではPLDからSAM単独への速度改善が59.02から69.37トークン/秒で約17.5%となる。原著の「18%以上速い」という要旨はこの代表条件と整合するが、すべての課題・比較方式で同じ上積みを保証しない。

EAGLE-2はSAM単独より高速である。SAMの意義はEAGLE-2を一律に置き換えることではなく、検索でよい草案が得られるラウンドだけ上積みすることにある。Spec-BenchのEAGLE-2比は90.14から97.56トークン/秒、倍率2.38から2.58へ上がる。HumanEvalでは125.77から130.28への小幅増で、平均受理数はむしろ5.13から4.95へ減る。コード生成で同じ部分文字列をコピーする機会が少ないことが、上積みの小ささと関係する。

### 2. 課題別の有効範囲

公式実装のSpec-Bench表では、PLDは翻訳で通常生成比0.95倍となり、検索型草案が逆に遅くなる条件がある。SAM単独は翻訳1.20倍、対話2.07倍、要約2.43倍、質問応答1.62倍、数学1.91倍、RAG1.81倍だった。対話、要約、RAGのように入力や既存文書を繰り返し使う課題で効果が大きい。

トークン再利用法にSAMを加えたとき、対話は1.92から2.48倍、要約は1.96から2.86倍、RAGは1.68から2.14倍となる。EAGLE-2との併用では、同じ三課題で2.87から3.09倍、2.33から2.95倍、2.03から2.28倍となる。複数のモデル規模にわたるMT-Benchでも併用改善は見られるが、モデルが大きいほど静的文章集合との出力分布差が増えるため、公式実装は大規模モデルで静的SAMを切る設定を勧めている。

### 3. 静的・動的SAMの切除実験

| 構成 | Spec-Bench受理数 | 速度（トークン/秒） | 通常生成比 |
|---|---:|---:|---:|
| PLD | 1.75 | 59.02 | 1.56倍 |
| SAM完全版 | 2.30 | **69.37** | **1.84倍** |
| 静的SAMなし | 1.85 | 61.93 | 1.64倍 |
| 動的SAMなし | 1.63 | 50.37 | 1.33倍 |

静的索引を除いても通常生成比1.64倍が残るが、動的索引を除くと1.33倍へ落ちる。これは、入力と直前の生成から草案を作る経路が主な貢献を持つことを示す。ただし静的文章集合の品質や対象タスクを変えれば、二つの寄与の比率も変わりうる。静的SAMが常に不要だと結論づけるべきではない。

### 4. 草案長と切替閾値の感度

トークン再利用法併用時の切替閾値`lbias`と`lthreshold`を2から6へ動かすと、双方が5程度に達するまで受理数と速度が上がり、それを超えると低下する。草案長の感度では40トークン前後で約83.5トークン/秒に達し、70トークンへ伸ばすと約78トークン/秒へ下がる。長すぎる草案は検証に不要な候補を増やし、GPU資源と時間を消費するためである。したがって検索が定数時間であっても、草案を無制限に伸ばしてよいわけではない。

## 既存方式との差と実装状況

PLDは現在の入力内の固定長n-gram一致を調べ、RESTは外部文章集合の接尾辞配列を用いる。SAM-Decodingは静的文章集合と動的生成系列をともに接尾辞オートマトンで索引化し、最長接尾辞一致と増分更新を組み合わせる。状態に保持する最小終了位置から後続トークンを取り出す点と、静的・動的・補助草案の三経路を一致長で選択する点が具体的な差分である。EAGLE-2は専用の学習済み草案モデルを必要とするが、SAM単独は追加の草案用ニューラルモデルを必要としない。併用時はEAGLE-2の費用を残したまま、検索が有効なラウンドで追加改善を狙う。

著者らの公式コードは`https://github.com/hyx1999/SAM-Decoding`に公開され、静的SAMの構築スクリプト、動的SAMを使う実装、EAGLE-2とトークン再利用法の統合、評価用データの準備手順を含む。再現時は静的SAMの参照文章集合と目標モデルの出力分布を合わせる必要がある。公開コードがあることは確認できるが、現在の主要サービング基盤へ標準機能として統合されたことや、高同時接続での効果を証明するものではない。

## 限界と負の結果

第一に、検索型草案の受理率は対象タスクと参照文章集合の重なりに依存する。論文の静的文章集合はVicuna-7Bの生成結果に由来するため、別系列や大規模モデルへそのまま適用すると候補の分布がずれる。公式READMEは、大規模モデルでEAGLE-2と併用する場合には静的SAMを無効化した方が良いことがあると明記する。

第二に、補助方式への切替は一致長という一つの代理指標に基づくヒューリスティックである。長い一致が高い受理率を保証するわけではなく、課題やモデルが変われば最適閾値が変わりうる。第三に、単一RTX A6000、バッチ1、貪欲生成の実測から、複数GPUサービング、連続バッチ、複数同時要求、GPUメモリ逼迫時の利得は直接導けない。静的索引のサイズや構築時間を含む総資源費用を比較した結果も限定的である。

第四に、HumanEvalではEAGLE-2併用の平均受理数が5.13から4.95へ低下しており、速度の上積みも小さい。草案が実際に再利用できる文章を含むかどうかが重要で、検索型方式をすべての生成課題に適用すべきではない。草案長を40から70へ伸ばすと性能が悪化する感度実験も、単に長い候補を生成するだけでは高速化しないことを示す。
