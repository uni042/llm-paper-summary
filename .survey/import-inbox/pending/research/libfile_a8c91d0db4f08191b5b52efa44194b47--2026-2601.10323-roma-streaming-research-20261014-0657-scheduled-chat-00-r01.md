# ROMA：音声・動画ストリームを同期し、発話タイミングを独立して制御する対話モデル

## 概要

音声と映像を同時に理解する大規模言語モデル（Large Language Model; LLM）は、ユーザーから質問を受けた後に回答する受動的な対話に加え、動画を監視して特定イベントが起きたときだけ警告する能動的な対話を求められる。これらは単なる出力形式の違いではない。受動的な質問応答では問い合わせが届いた時点で既知の過去を説明すればよいが、能動的な警告・実況では、モデル自身が入力ストリームを逐次観察し、**いつ話し始めるか**を毎時刻判断する必要がある。

ROMAは、動画と音声を共通の時刻軸に整列した1秒単位のマルチモーダル入力として逐次処理し、言語生成とは独立した発話判定ヘッド（speak head）で発話開始の確率を予測する。映像は離散的なフレーム、音声は密な時間列であるため、単純なトークン連結では時刻の対応が曖昧になる。ROMAは時間整合した回転位置符号化（Time-aligned Multimodal RoPE; TMRoPE）をストリーミング入力へ適合させ、音声・映像・テキストを一つの因果的履歴として処理する。

推論では鍵値キャッシュ（KV cache）をストリーム全体で保持し、新しく到着した単位だけを符号化する。一次論文は、2フレーム/秒の映像サンプリングと画素数65536以下への縮小を用い、1秒のマルチモーダル単位の符号化に平均0.3697秒を要すると報告する。ただし、これは継続的な入力処理の平均時間であり、発話内容の生成時間、ネットワーク遅延、音声合成、極端に長い履歴を含むシステム全体の最悪応答遅延ではない。

能動的警告の評価ではOmniMMI-PAで37.50、StreamingBench-POで53.60、繰り返し警告のOVO-Bench-RECで33.81を報告する。YouCook2の実況開始時刻のF1は35.21で、比較するVideoLLM-onlineの18.82を上回る。一方、質問応答ではEgoSchemaが55.40とQwen2.5-Omniの58.40に及ばず、**自発的発話の改善が全ての理解能力を改善するわけではない**。

## 問題設定

リアルタイム動画理解は、将来の映像を参照せず、現在までに受信した入力だけから判断する因果的なオンライン処理である。通常の動画質問応答は動画全体を一括処理してから回答するため、時間的に後のフレームを先のイベントの判断に使えることがある。能動的警告ではそれは許されない。モデルは「転倒が発生したら知らせる」などの条件を最初に受け取り、フレームと音声が到着するたびに発話するか沈黙するかを決める。

この問題には二つの異なる難しさがある。第一に、映像は1秒内に数フレーム程度の離散入力であり、音声は数十ミリ秒ごとに変化する。両者を同じトークン時刻で表すと音声の細かな順序が失われる。第二に、言語生成モデルの次トークン予測だけで発話判定を兼用すると、言語的な続きやすさと、イベントが起きたかどうかという二値判定が競合する。何も起きていない時間に不必要な発話を生成したり、重要なイベントで沈黙したりする危険がある。

ROMAは、入力整列と発話時刻判定を別々の仕組みとして設計する。評価対象は、イベント発生時に警告する単発・反復警告、時間経過に合わせて実況する連続要約、過去の映像・音声に関する質問応答の三種類である。実験は従来別々に評価されていた指標を再整理し、発話開始の時刻精度と回答内容の品質を混同しないようにしている。

## 手法

### 1. 音声と映像を1秒ごとの同期単位に変換

ROMAはQwen2.5-Omniの入力形式を踏襲し、同じ1秒間に入った映像フレームと音声断片を一つの単位へまとめる。単位の概念的な並びは `<|vision_bos|> <|audio_bos|> [video tokens] [audio tokens] <|audio_eos|> <|vision_eos|>` である。新しい単位が届くたびに特徴を取り出して言語モデルへ渡し、過去に到着した単位は履歴として参照する。

時刻情報にはTMRoPEを用い、時間・高さ・幅の三軸位置識別子を与える。同じ1秒単位内の映像トークンには同じ時間識別子を与える一方、音声トークンには40ミリ秒刻みの細かな時間識別子を保持する。単位の先頭にある映像・音声開始記号には共通の基準時刻を与え、次の単位では前単位の最大位置識別子から時刻を継続する。この累積的な時刻割当てにより、断片ごとに位置が0へ戻って異なる時間の出来事を同時と誤認する問題を避ける。

これは動画をまとめて再符号化する方式ではない。現在の単位だけを順に投入し、過去の履歴はKVキャッシュから参照する。したがって入力到着に合わせて逐次実行できるが、ストリームが非常に長くなるとキャッシュ容量と文脈窓の制約が残る。

### 2. 発話判定ヘッドを言語生成から切り離す

ROMAは通常の言語生成ヘッド（LM head）と並列に、2層の多層パーセプトロン（Multi-Layer Perceptron; MLP）で構成した発話判定ヘッドを設ける。各1秒単位を処理した後、現在までの入力履歴を表す隠れ状態から、発話が必要である確率 `p_t` を出す。`p_t` が閾値を超えた場合だけ言語生成ヘッドを起動し、そうでなければ沈黙して次の入力を待つ。

発話判定の入力には最終層だけを使うのではなく、最後の4層（`K=4`）の隠れ状態を学習可能な重みで合成する。異なる層が時間的な重要性や高次の意味を異なる粒度で保持するため、複数層を統合する方が発話タイミングの信号が安定すると考える。これは、モデルが毎秒全文を生成してから不要な応答を破棄する方式と違い、**生成を開始するかどうかを低コストの二値判定へ分離する**設計である。

発話判定ヘッドを省いて特別な沈黙トークン `<|silence|>` の生成で判定する方式も構成要素除去実験で比較している。特別トークン方式は確率的な時刻スコアの取得に不向きであり、後述の単発・反復警告の成功率を大きく落とした。

### 3. 二段階の学習で入力形式と発話判断を順に獲得

新規の全モダリティモデルを一から学習するのではなく、既存の基盤モデルをストリーム入力へ適応させる。第一段階は受動的な質問応答データを1秒単位の連続入力へ再構成し、標準の次トークン予測損失 `L_LM` で微調整する。これにより、一括入力に最適化されていたモデルが、音声・映像の断片を時系列で受け取る形式に慣れる。両段階とも符号化器は固定し、それ以外の学習対象パラメータを調整する。

第二段階では能動的な警告と実況の教師データを使い、発話判定ヘッドを学習する。警告ではイベントの発生区間内を正例、実況では区間の切替点を正例として、時刻ごとに発話確率を教師あり学習する。発話すべき瞬間は大部分の沈黙時間に比べて少ないため、正例重み `w_pos=N_neg/N_pos` を使う加重二値交差エントロピー（Binary Cross-Entropy; BCE）損失 `L_time` を用いる。実験では `w_pos=3` を採用した。

発話時刻だけを学習すると回答内容の生成品質が劣化するため、第一段階の質問応答データを一部混ぜ、`L_total=L_time+λ L_LM` で発話判定と文章生成を共同最適化する。データ規模は能動的警告約2.7万、実況約10.9万、受動的質問応答約54万件である。質問応答には音声化した問い合わせも含め、テキスト指示だけではないストリーミング対話へ適応させる。

### 4. 推論時の持続的キャッシュと処理の重畳

推論では映像を毎秒2フレーム抽出し、各フレームを最大65536画素へ縮小する。各1秒単位を符号化してKVキャッシュへ追加し、発話判定確率を計算する。必要な場合だけ言語生成へ移る。論文のリアルタイム近似では、時刻 `t` の単位を処理している間に次の単位 `t+1` を取得するパイプライン化を用いる。発話は1区間につき最大25トークン（概ね1秒分）に制限し、長い発話は後続の単位へまたがって続ける。

この処理ではキャッシュに保存した過去の視覚・音声文脈を再計算しないため、毎秒動画全体を入力し直す方式より重複計算を避けられる。原著は単位当たり平均0.3697秒の符号化時間を報告するが、測定機材・負荷分布・生成中の干渉条件を揃えた他方式との実測高速化倍率は示されていない。**実時間で入力を追える可能性と、すべての状況で遅延が1秒以内に収まる保証は別物**である。

## 評価条件

| 項目 | 一次論文の内容 |
|---|---|
| 基盤 | Qwen2.5-Omni系の音声・映像入力表現を使用。追加の発話判定MLPを並列に配置 |
| ストリーム単位 | 1秒。映像は2 fps、音声の位置符号化は40ms刻み |
| 推論履歴 | 持続的KVキャッシュ。単位当たりの平均符号化時間0.3697秒 |
| 生成制約 | 1区間最大25トークン。長い応答は次区間へ持越し |
| 学習データ | 警告27K、実況109K、QA540K。二段階微調整 |
| 警告評価 | QVHighlights、Charades-STA、OmniMMI-PA、StreamingBench-PO、OVO-Bench-CRR/REC |
| 実況評価 | YouCook2、OVO-Bench-SSR。発話時刻F1、BERTScore、GPT-4o評価 |
| 受動的QA | OVO-Bench、StreamingBench、Video-MME、EgoSchema。音声問い合わせを含む |
| 比較 | VideoLLM-Online、MMDuet、Dispider、Qwen2.5-Omni、MiniCPM-o、VITA-1.5など。課題により比較対象が異なる |

静的な時間位置特定ではmAP・HIT@1や時間区間の重なりに基づく再現率を使い、オンライン警告ではモデルが発話した時刻が正解イベント区間内に入ったかを評価する。実況のF1は発話開始の時間窓一致であり、BERTScoreやGPT-4o評価は文章内容の一致・品質である。異なる指標を同じ「精度」として直接比較しない。

### 1. イベント検知と警告

|---|---:|---:|---|
| QVHighlights、mAP | MMDuet 31.3 | 53.7 | 時刻候補の順位付けを改善 |
| QVHighlights、HIT@1 | MMDuet 49.6 | 53.0 | 上位1時刻の正解率は小幅改善 |
| Charades-STA、R@0.5 | MMDuet 42.4 | 44.3 | 時間区間の位置特定 |
| Charades-STA、R@0.7 | MMDuet 18.0 | 19.9 | 厳しい重なり条件でも改善 |
| OmniMMI-PA、オンライン警告成功率 | MMDuet 22.00 | 37.50 | 単発警告で改善 |
| StreamingBench-PO、オンライン警告成功率 | MMDuet 29.44 | 53.60 | 自発的応答時刻を改善 |
| OVO-Bench-CRR | Dispider 48.75 | 35.42 | **比較方式に劣る** |
| OVO-Bench-REC | Dispider 18.05 | 33.81 | 繰返しイベントの警告で改善 |

ROMAは単発警告と繰り返し警告で強いが、OVO-BenchのCRRではDispiderに及ばない。したがって論文の「能動的課題で最先端」という総括は、全警告指標の一律最高値を意味しない。静的な時刻位置特定とオンラインでの即時発話は評価規則が異なるため、前者のmAPの高さから後者の誤警報率を推定することもできない。

### 2. 実況の開始時刻と文章品質

| 評価 | VideoLLM-online | MMDuet | ROMA |
|---|---:|---:|---:|
| YouCook2、発話時刻F1 | 18.82 | 17.81 | 35.21 |
| YouCook2、BERTScore | 0.82 | 0.83 | 0.83 |
| YouCook2、GPT-4o評価 | 0.17 | 0.23 | 0.39 |
| OVO-Bench-SSR、発話時刻F1 | 10.24 | 9.02 | 14.54 |
| OVO-Bench-SSR、BERTScore | 0.84 | 0.79 | 0.83 |
| OVO-Bench-SSR、GPT-4o評価 | 0.18 | 0.31 | 0.42 |

YouCook2では実況開始時刻のF1が約2倍に改善するが、BERTScoreはMMDuetと同程度である。OVO-Bench-SSRではBERTScoreがVideoLLM-onlineの0.84をわずかに下回る。これは発話する時刻を正確にする能力と、生成した文章の意味的な一致度が独立の評価軸であることを示す。GPT-4oによる文章品質評価は評価モデルに依存し、完全に客観的な人手評価と同一視できない。

### 3. 受動的な音声・映像質問応答

| モデル | Video-MME（字幕なし・音声質問） | EgoSchema（音声質問） |
|---|---:|---:|
| Qwen2.5-Omni | 20.50 | 58.40 |
| VITA-1.5 | 28.56 | 45.40 |
| MiniCPM-o | 19.37 | 55.20 |
| ROMA | 33.30 | 55.40 |

ROMAはVideo-MMEで比較方式より高い一方、EgoSchemaではQwen2.5-Omniを下回る。原著は通常のテキスト問い合わせではなく、合成した音声質問と音声・映像入力を用いるため、一般的な動画質問応答ベンチマークの公開スコアと直接比較できない。オンラインの過去文脈だけを使う条件も、動画全体を一括で与える条件とは違う。

### 4. 構成要素除去実験

発話判定ヘッドを取り除いて沈黙トークンを生成させると、OmniMMI-PAは37.50から12.50、StreamingBench-POは53.60から12.00、OVO-Bench-RECは33.81から6.46へ下がった。YouCook2実況の時刻F1も35.21から9.25へ下がり、発話時刻を言語生成と分離する設計の重要性が示された。

二段階学習をやめて全データを混ぜた単一段階学習にすると、RECは33.81から13.13、OVO-Bench-SSRの実況時刻F1は14.54から8.88へ低下する。まずストリーム入力形式へ適応し、その後に能動的な発話時刻を学ぶ順序が効果に寄与する。

最後の4層ではなく最終1層だけを発話判定に使うと、QVHighlights mAPは53.7から46.4、OmniMMI-PAは37.50から26.00、RECは33.81から24.32へ低下した。一方、StreamingBench-POは53.60から56.40へ改善する例もあり、複数層の集約がすべての指標で優位ではない。発話正例の重み `w_pos` は2・3・4を比較し、全体の折衷点として3を選択している。

## 既存研究との差

VideoLLM-Onlineなどの動画ストリーミング方式は視覚情報を継続的に取り込むが、音声の細かな時刻整列や、発話時刻の明示的な二値判定を必ずしも備えない。MMDuetやDispiderなどは能動的なイベント判断を扱うものの、ROMAはQwen2.5-Omni系の音声・映像表現を利用して、受動的な質問応答と能動的な警告・実況を同じストリーム処理へ統合する。

KVキャッシュ圧縮のようにメモリ使用量を直接減らす研究とは異なり、ROMAのシステム的な焦点は、入力を時間単位で分割して増分処理し、発話するかどうかを低コストのヘッドへ委譲する**推論制御**にある。生成を毎秒実行するのではなく、必要なタイミングに限定することで不要な発話を避けられる可能性がある。ただし、実際に節約したGPU時間・電力・トークン数を従来方式と同条件で比較した結果は提示されておらず、推論費用削減の倍率を独自に作ってはいけない。

## 限界と監査上の注意

- **長期記憶とキャッシュ容量**：持続的KVキャッシュで過去を再計算しないが、文脈窓は有限である。論文も数時間に及ぶ長期依存の保持を課題として認める。キャッシュ容量の上限や圧縮方針、長時間運用時の品質推移は評価されていない。
- **音声・映像の同期誤差**：1秒単位の入力整列と40msの音声時刻付与は、信号劣化・通信遅延・音声映像のずれを完全に補償するものではない。原著は音声・映像の非同期性を限界として挙げる。
- **実時間性の主張範囲**：1単位の平均符号化0.3697秒は、1秒以内に処理できる条件を示唆するが、音声合成、文章生成、最悪負荷、同時ユーザー数まで含めた端末・サービス全体の厳密な応答保証ではない。生成25トークン上限は品質・長さの交換条件を伴う。
- **発話閾値の依存性**：発話判定は確率閾値と短時間の平滑化に依存する。警告の見逃しと誤警報の費用は用途で異なり、単一閾値を全用途へ転用できない。論文の正例重みと層数の感度実験からも、発話の頻度・精度の交換条件が読み取れる。
- **評価指標の混在**：静的時刻検索のmAP、動的警告の成功率、実況の時刻F1、文章のBERTScore、GPT-4o評価、QA正答率は異なる。ROMAがCRRやEgoSchemaなど一部で最良ではない点を明記した。
- **実装公開状況**：論文はプロジェクトページを案内するが、この読解でモデル重みや学習・推論コードの配布状態を確認していないため、`code`は未確認（null）とした。実装の公開と一次論文の性能報告を混同しない。
- **プライバシー上の懸念**：常時入力を受ける能動的な音声・映像監視は無断監視やプライバシー侵害に転用され得る。論文は研究目的の利用と重要用途での人間による監督を求める。
