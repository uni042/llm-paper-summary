# LLMCompass: Enabling Efficient Hardware Design for Large Language Model Inference

## 概要
LLM推論アクセラレータを設計するとき、演算器数、メモリ種類・帯域、チップ面積、並列配置を変えるたびにRTL実装や実機評価を行うのは現実的でない。しかもLLMは層ごとにGEMM、attention、通信など性質の異なる演算を含み、同じハードウェアでもマッピング次第で性能が大きく変わる。LLMCompassは、ハードウェア記述から演算子性能を予測し、mapperが高速な配置・scheduleを探索し、面積ベースのcost modelで性能/コストまで比較する。

実機との比較では各種operator・input sizeの遅延誤差が平均10.9%、LLM推論全体では平均4.1%。4台のNVIDIA A100でGPT-3 175Bを実行する構成を、26,400回のmapper parameter searchを含めて汎用ハードウェア上16分以内でシミュレーションする。設計探索ではcompute capabilityを下げる、HBMを通常DRAMへ置き換える等の候補から、A100比最大3.41倍のperformance/costを示す設計を導く。

## 問題設定
従来のアクセラレータシミュレータは一般DNNを対象とするものが多く、LLMの巨大なweight footprint、autoregressive decode、tensor parallel通信を含む推論を高速かつ十分な精度で評価することが難しい。一方、実GPUだけで設計探索すると、存在しないメモリ構成や演算器比率を試せず、探索可能な点が市販品へ限定される。

LLM推論ではprefillとdecodeで演算特性が違う。大きな行列を処理するprefillは演算能力の影響が強い一方、decodeは小batchで重みを繰り返し読むためメモリ帯域の影響が強い。この違いを無視した単一peak FLOPS指標では、設計変更の価値を判断できない。

## 手法
### 性能モデル
LLMCompassは各operatorを対象ハードウェアへmappingした際の実行時間を推定する。計算資源、オンチップbuffer、外部memory bandwidthなどを設計パラメータとして扱い、単なるrooflineの上限値ではなく実行scheduleを含めてlatencyを評価する。

### Mapper
同じoperatorでもtile size、loop order、並列化方法によってdata reuseとmemory trafficが変わる。mapperは候補mappingを探索し、対象ハードウェアで性能が良いscheduleを選ぶ。GPT-3 175Bの4×A100例で26,400 roundsのparameter searchを含めても16分以内という速度は、hardware design space explorationを反復可能にするための重要な性質である。

### 面積・コストモデル
性能だけ高い巨大チップを選ぶのではなく、演算器やSRAM等が占める面積からcostを推定しperformance/costを比較する。これにより「HBMを増やす」「computeを増やす」といった直感的設計だけでなく、decodeが帯域律速ならcomputeを減らして面積・費用を下げる構成も候補になる。

## 評価条件・主要結果
| 観点 | 結果 |
|---|---|
| operator予測 | 実機比平均10.9% latency error |
| LLM E2E予測 | 平均4.1% latency error |
| 代表探索 | GPT-3 175B、4×NVIDIA A100 node |
| 探索量 | mapper 26,400 roundsを含む |
| simulation時間 | commodity hardwareで16分以内 |
| design探索 | A100比最大3.41倍 performance/cost |

4.1%という値は「提案アクセラレータが4.1%速い」という意味ではなく、LLMCompassの予測値と実機測定の誤差である。3.41倍は探索された設計の性能/コスト改善であり、単純なlatency倍率とは区別する必要がある。

## 既存研究との差
一般DNN向け性能モデルや単一operatorのanalytical modelに対し、LLMCompassはLLM workload、mapping search、area/costを一体化する。特に「存在するGPUのbenchmark」ではなく、未製造のhardware configurationをLLM推論全体で比較できる点がhardware/software co-designに向く。

## 限界
性能モデルは実機の全てのruntime効果を再現するわけではなく、kernel実装、cache挙動、collective library、software overheadが変われば誤差も変わる。探索結果は想定technology/cost modelに依存する。さらに2024年以降のMoE、disaggregated serving、speculative decoding、agentic workloadなどをそのまま代表するわけではなく、新しいoperatorや通信patternにはモデル拡張が必要になる。
