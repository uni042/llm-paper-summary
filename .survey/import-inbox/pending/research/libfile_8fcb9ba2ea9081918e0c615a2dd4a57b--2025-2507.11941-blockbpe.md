# BlockBPE: Parallel BPE Tokenization

## 概要

LLM推論の高速化はGPU上のTransformer計算へ集中しがちだが、高throughput batchでは入力文字列をtoken列へ変換するtokenizerもcritical pathになり得る。広く使われるHugging Face TokenizersやtiktokenはCPU中心で、byte-pair encoding（BPE）の前に正規表現によるpre-tokenizationを行う。GPUが多数requestを同時処理できるほど、serial/CPU側のtokenizationが供給律速になりやすい。

BlockBPEは正規表現pre-tokenizationを省略し、BPE mergeをGPU thread block内で並列化する。著者は既存方式を実質 `O(n log n)` の処理として捉え、局所的なmerge依存深さdが系列長nより十分小さいという現実的仮定の下で `O(nd)` に近い並列処理を構成する。高batch推論でtiktoken比最大2倍、Hugging Face Tokenizers比最大2.5倍のtokenization throughputを報告する。ただしregex境界を外すためtoken列が従来tokenizerと完全同一ではなく、生成品質に小さな低下を伴う。

## 問題設定

BPEは隣接symbol pairのうち語彙で高順位のmergeを繰り返し、最終token列を作る。素朴には「次にmergeすべきpairを探す→列を更新する」を逐次反復するため、同一文字列内部に依存関係がある。CPU実装はpriority queue等で効率化しても、requestごとの処理が細かく、高batch GPU inferenceへ十分な速度でtokenを供給できない。

さらに実用tokenizerはBPEの前にregexで文字列を単語・空白・記号等へ分割する。このpre-tokenizationはtokenization規則を安定させるが、複雑なregex engineはGPUへ素直に移しにくく、CPU runtimeの大きな部分を占める。BlockBPEは「既存token列との完全一致」を少し緩め、GPU並列性を優先する設計である。

## 手法

### 正規表現pre-tokenizationの除去

入力byte列をregexで細かなchunkへ切ってからBPEを行うのではなく、より直接的にBPE merge対象へする。これによりregex engineの逐次・分岐的処理をcritical pathから外し、GPUで統一的なdata-parallel処理を行いやすくする。

代償として、regex境界が強制していた「ここを跨いでmergeしない」という制約が変わり、標準tokenizerと異なるsegmentationが生じる。この差は単なる実装最適化ではなくモデルへの入力token列を変えるため、論文は小さいながら生成品質低下を明示している。

### thread block単位のBPE merge

各入力系列またはchunkをGPU thread blockへ割り当て、隣接pairのrank判定とmerge候補更新を並列に進める。完全に独立なmergeは同時実行し、競合する隣接mergeだけ依存順序を守る。GPUの多数threadで複数request・複数位置を同時処理することで、CPU tokenizerのrequest-level並列より細粒度な並列性を得る。

入力はbyte/symbol列とBPE merge table、出力はtoken ID列である。局所mergeの依存chain長をdとすると、n個のsymbolを全逐次処理するのではなく、独立位置をまとめて進められるため現実的条件で `O(nd)` と整理される。論文はdがnより十分小さいことを前提にnear-linearな挙動を狙う。

### batch推論との接続

BlockBPEの狙いは単一短文のtokenizer latency記録ではなく、多数requestをまとめて処理するserving前処理である。GPUへbatchとして入力を渡し、Transformer実行の前段でtokenization throughputを高める。モデル計算が高速化してCPU tokenizerが相対的に重くなる環境ほど価値が大きい。

一方、GPU tokenizer自体がdevice時間とmemoryを使うため、GPUがモデル計算で完全飽和している場合はresource競合が起こり得る。BlockBPEの最大倍率をLLM全体の生成throughput倍率へそのまま読み替えることはできない。

## 主要結果

| 比較対象 | 高batch条件での結果 | 意味 |
|---|---|---|
| tiktoken | throughput最大2倍 | CPU中心tokenizationに対するGPU並列化の効果 |
| Hugging Face Tokenizers | throughput最大2.5倍 | regex/pre-tokenizationを含む従来経路の律速を削減 |
| 標準tokenization | 小さな生成品質低下 | regex除去は完全に意味保存なkernel置換ではない |

最大2倍・2.5倍はtokenizerのthroughputであり、Transformer forward/decodeを含むend-to-end LLM serving全体の速度倍率ではない。tokenizationが全体の小部分しか占めないlow-batch条件ではAmdahlの法則によりシステム利得は小さくなる。

## 設計上の交換条件

regexを残したまま完全互換なGPU実装を目指すのではなく、regexを除くことで大きな並列性を得る点がBlockBPEの最も重要な設計判断である。したがって速度とtoken列互換性の間に明示的なtrade-offがある。既存checkpointは特定tokenizerで学習されているため、segmentation差が品質へ影響するかを速度と別に評価しなければならない。

またd≪nという複雑度上の仮定は、merge依存が局所的である通常入力を想定する。依存chainが長い特殊文字列では並列stage数が増え、near-linearな利点が縮む可能性がある。

## 既存研究との差

tiktokenやHugging Face Tokenizersは高度に最適化されたCPU/Rust実装だが、regex pre-tokenizationと逐次性の高いBPE処理を基本にする。BlockBPEは同じ実装をGPUへ単純移植するのではなく、regex段階自体を取り除き、アルゴリズムをthread blockでmerge可能な形へ再構成する。

LLM kernel最適化論文との差は、Transformer内部のattention/GEMMを触らず、requestがmodelへ入る前のtokenization pipelineを対象にする点である。モデルkernelが高速になるほど周辺処理が相対的に支配的になるというserving上の問題を扱う。

## 限界

最大の制約はtokenizer互換性である。regex pre-tokenizationを外すことで生成品質に小さな低下が生じるため、既存tokenizerとbit-exactなtoken ID列を要求するAPI、prompt cache key、課金・token count互換性ではそのまま置換できない場合がある。

評価のheadlineは高batch tokenization throughputであり、end-to-end request latencyやtokens/s全体が2〜2.5倍になるわけではない。low-batch、短prompt、GPU compute飽和条件ではCPU tokenizationが律速でなく、利得が縮む。

また論文のcomplexity改善は現実的なmerge依存深さの仮定に基づく。入力分布や語彙によって依存構造が変わるため、あらゆる文字列で同じ並列効率を保証するものではない。
