# 3bit量子化7BモデルのiPhone実行：prefill・decode・熱制御を分けて読む

## 概要

本論文は、2023年時点のiPhoneで7B級LLMをネットワーク接続なしに実行し、**CPU上のトークン選択、GPU上のプロンプト処理、GPU上の自己回帰デコード**を分けて比較した実測研究である。対象はiPhone 14、14 Pro、14 Pro Max、15、15 Pro Maxの五機種で、llama.cppとGGUFを利用し、orca_mini_v3_7Bを3bit small K-S量子化した約2.95GiBのモデルを使用する。iOS 17.1.xとMetalの同一ソフトウェア環境に揃え、熱状態が性能へ与える影響も調べた。

原著の重要な負の結果は、**最新のA17 Proを積むiPhone 15 Pro Maxが、CPUサンプリングでは約20%速い一方、生成トークンのGPUデコードでは五機種中最も遅かった**ことである。著者らは同機種の別個体でも再現を確認したが、原因を特定できなかった。GPUアーキテクチャ、Metalドライバ、シェーダ最適化不足などは仮説として挙げるにとどまる。この結果は「新しいSoCほど常にLLMのtokens/sが高い」という単純な予測が成り立たないことを示す。

また、iOSのthermal stateが上がると処理率が低下する。90秒の待機を挟めば熱状態を抑えられたが、実際の対話では非現実的な待ち時間となる。著者らは5秒間隔、3反復×3回の平均で機種間比較を行い、長時間連続使用の影響を完全に除去したわけではない。**本研究は新しい量子化方式の提案ではなく、既存モデル・実装を用いた端末ベンチマーク**である。

## 問題設定：スマートフォンでは容量だけでなく熱・GPU実装が制約になる

### 1. 7Bモデルを端末メモリへ収める

当時の7B級LLMをFP16で保持すると、重みだけで約14GBが必要になる。スマートフォンの共有メモリでは、OSやアプリの領域も確保しなければならず、実用上の常駐が難しい。量子化は重みの表現ビット幅を減らし、モデルファイルを小さくできる。本研究では3bit small K-SのGGUFを使い、モデルを2.95GiBに縮めることで、少なくとも6GiB RAMを持つ端末での実行を可能にした。

ただし、2.95GiBはモデルファイルの大きさであり、**ピークRAM使用量やKVキャッシュ込みの実行容量と同じではない**。量子化の品質損失、別ビット幅との精度・速度の比較、メモリ割当の詳細な内訳は本論文の主実験ではない。3bit化が他の量子化方式より最適という結論も導けない。

### 2. 一つのtokens/sでは推論全体を説明できない

推論には、(1)確率分布から次トークンを選ぶsampling、(2)入力プロンプトをまとめて処理するprefill、(3)過去の出力に依存しながら1トークンずつ生成するdecodeがある。samplingは主にCPUで実行し、prefillとdecodeはMetal GPUで実行した。prefillは入力をまとめて計算できるため、同じGPUでもdecodeより高いtokens/sを得やすい。decodeは過去のKVを読みながら逐次実行するため、メモリ帯域、シェーダ実装、カーネル起動の影響を受けやすい。

この三つをまとめて「LLMの速度」とすると、CPUのサンプリングが速いだけなのか、GPUのprompt処理が速いのか、実際にユーザーが読む生成速度が速いのか分からなくなる。原著は各段階を別々に測定した点に実用上の意義がある。逆に、**三段階の結果から実際の対話全体のTTFTやTPOTを直接復元できるとは限らない**。初期化やウォームアップ、入力長・出力長、OSのスケジューリングが異なるためである。

### 3. 熱制御による性能低下

iOSは電力と温度に応じてnominal、fair、serious、criticalの熱状態を管理する。負荷が高いとCPU/GPUの利用可能性能が制限され、同じモデルでも実行速度が変わる。ベンチマークが短いと高いピーク性能だけを観測し、継続的な対話で生じる性能低下を見落とす。反対に極端な長時間負荷を与えると、端末固有の冷却性能を測っていることになり、GPU実装そのものの比較と混ざる。

著者らはまず熱状態を人為的に変えて速度を調べ、次に要求間隔と反復数を変えて熱の上昇を観測する。最終的には3反復を一組として、測定中の熱状態の上昇を抑える条件を選ぶ。これは**機種間の比較条件を整える工夫**だが、現実の長い会話や連続生成の持続性能を十分に測る試験とは異なる。

## 手法：同一モデル・同一iOS条件で三段階を測る

### 1. ハードウェアとモデル

| 項目 | 原著の条件 |
|---|---|
| 端末 | iPhone 14、14 Pro、14 Pro Max、15、15 Pro Max |
| SoC | iPhone 14はA15、14 Pro/14 Pro Max/15はA16、15 Pro MaxはA17 Pro |
| RAM | 全機種6GiB以上 |
| OS | iOS 17.1.xに統一 |
| GPU実行 | Apple Metal。prefillとdecodeをGPUで実行 |
| CPU実行 | greedy samplingのトークン選択 |
| モデル | orca_mini_v3_7B（Llama 2系アーキテクチャ） |
| 圧縮 | GGUF 3bit small K-S、ファイル2.95GiB |
| 実行基盤 | llama.cppの2023年版 |
| コンテキスト/バッチ | 1024 / 512 |
| プロンプト | 固定質問「Why is the sky blue?」 |

A16を搭載する14 Pro、14 Pro Max、15はCPUコア数が同じ6、GPUは5コアである。A17 Proの15 Pro Maxは6コアCPU・6コアGPUとされる。したがってCPU sampling、GPU prefill、GPU decodeの差が、どのハードウェア段階で現れるかを比較できる。ただし、端末の冷却、筐体、クロック制御、メモリ帯域、GPUのドライバ実装まで完全に統制した実験ではない。

### 2. ウォームアップと反復設計

端末は100%充電、バックグラウンドアプリなし、同一iOS版とし、初回初期化や遅延ロードの影響を除くためウォームアップを行う。各反復で文脈をリセットし、同じ質問を与え、greedyで次トークンを選ぶ。Metalシェーダのスケジューリングに8スレッドを使う。反復間隔は5秒で、各機種3反復を3回実施し、合計9回の測定を平均する。

著者らは、90秒間隔なら熱状態がfairを超えないと観測したが、実際の対話では待機が長すぎるため採用しなかった。5秒間隔で3回程度の反復ならiPhone 14 Proの熱状態がnominalにとどまる一方、反復を増やすとfair/seriousの割合が増える。この設計は熱状態の差を抑えるが、**1日を通したバッテリー持続時間、発熱量、ワット数を測るものではない**。

### 3. 測定対象の区別

samplingは確率分布から最大確率のトークンを選ぶ操作であり、モデル全体のforwardではない。prefillは入力トークンをまとめてモデルへ通し、KVキャッシュを構築する。decodeは直前までのトークンに条件付けて次トークンを生成する。論文のFigure 3はこの三指標を機種ごとに並べている。数値の一部はグラフとして提示され、HTML本文には各機種の厳密なtokens/s数値表がないため、ここでは**図を読んで根拠のない小数値を補完しない**。

## 評価

### 1. 熱状態を変えたときの影響（原著Figure 1/2）

| 比較 | 原著の観察 | 注意点 |
|---|---|---|
| nominalからcritical | criticalでアプリ性能が大きく低下 | thermal stateはOS管理であり、GPU単独の熱だけではない |
| fairとserious | sampling・prefillでは差が比較的小さく、decodeで目立つ差 | iPhone 14 Proの実験。全端末の同一効果ではない |
| 90秒の反復間隔 | 反復回数を増やしてもfairを超えなかった | 実利用の対話間隔としては長すぎる |
| 5秒の反復間隔 | 3反復まではnominal、その後fair/seriousの割合が増加 | 端末・環境温度・負荷に依存 |

この結果は、短いベンチマークで観測した速度が継続使用で維持されるとは限らないことを示す。熱制御の影響は、特に逐次decodeの体感速度に現れやすい。著者らは測定の再現性を優先して反復数を制限したため、継続的な対話を何時間も行う条件での持続TPSは示していない。

### 2. CPU sampling（原著Figure 3）

A16搭載のiPhone 14 Pro、14 Pro Max、15はsamplingで近い結果となる。A15のiPhone 14はやや低いが、大差ではない。A17 Proの15 Pro Maxは他の端末より**約20%高いsampling処理率**を示した。これはCPUで行うgreedy samplingの比較であり、LLM全体の生成速度が20%高いという意味ではない。

samplingは語彙分布から最大値を探す比較的短い処理なので、GPUで行う大規模行列積やKV参照の費用を反映しない。端末間の体感差を判断するには、prefillとdecodeを別に確認する必要がある。著者らは別のサンプリング方式（top-k、top-p、temperature変更等）を評価していない。

### 3. GPU prefill（原著Figure 3）

GPUでのプロンプト処理では、A16搭載の三機種にも差が生じた。14 Proと15では処理率がやや低く、標準偏差も大きいと報告する。ただし、15 Pro Maxを除く機種の最高観測処理率は比較的近い。A17 Proの15 Pro Maxでは、prefillに大きな性能向上が見られた。

prefillは入力トークンをまとめて処理するため、GPUの並列計算性能が出やすい。ただし実験の固定質問は短く、コンテキスト上限1024である。128k文脈のprefillや複数要求の連続バッチングを評価した結果ではない。入力長が変われば行列演算の形とカーネルの支配要因も変わるため、同じ機種順位が保たれる保証はない。

### 4. GPU decode：A17 Proが逆転する負の結果

**iPhone 15 Pro Maxは、五機種中で最も低い自己回帰decode処理率**となった。著者らは同型の別端末でも再測定して同じ傾向を確認した。CPU samplingでは約20%優位で、GPU prefillでも大きな向上があったにもかかわらず、GPU decodeでは逆転した。この三段階の差こそ、本研究の中心的な実験的知見である。

著者らはA17 ProのGPUアーキテクチャ変更、ドライバ、Metalの回帰、当時のシェーダ最適化不足などを候補として挙げるが、**原因の切り分け実験を完了していない**。シェーダのプロファイルやGPUメモリ帯域の測定がないため、どれが主因かを断定できない。最新SoCだから生成が速いはずという前提で、当時の実装の速度を推定してはならない。

同じA16を積むiPhone 15と14 Proが似た特性を示したことは、GPU実装とSoCの組合せが重要であるという仮説に整合する。ただし筐体の冷却特性など他の要因も残る。著者らは今後のiOSでの再測定を求めており、2023年の異常が2026年にも残っていると主張してはいけない。

### 5. 数値として確定できる範囲

| 指標 | 原著から確認できる値・条件 |
|---|---|
| モデルファイル | 2.95GiB（3bit small K-S、orca_mini_v3_7B） |
| CPU samplingのA17 Pro優位 | 約20%（他端末に対して） |
| 反復回数 | 各端末3反復×3回＝9測定の平均 |
| 反復間隔 | 5秒（熱制御を考慮した最終設定） |
| 90秒間隔 | 熱状態がfairを超えない観察条件 |
| decodeの機種順位 | iPhone 15 Pro Maxが最低 |
| prefillの機種順位 | A17 Proが大きな性能向上 |
| 端末間の正確なTPS差 | Figure 3のグラフで提示。本文に厳密な全機種の数値表なし |

「A17 Proのdecodeが他端末の何%遅いか」を図から無理に小数値へ変換しない。確定できるのは順位と、sampling約20%優位という本文の記述である。別モデル・別ソフトウェアの測定値をこの実験へ混ぜない。

## 主要結果の解釈

第一に、端末でLLMを動かすためには、モデルファイルを小さくするだけでなく、**熱・電力制御を含む持続性能**を考える必要がある。短い負荷では高速でも、繰り返し対話するとthermal stateが変化し、特にdecodeの速度が低下し得る。単発のベンチマーク結果を持続TPSとして広告するのは不適切である。

第二に、**GPU世代とdecode性能は単調な関係ではない**。iPhone 15 Pro Maxはprefillが速い一方、decodeが遅かった。モデルの各処理段階は異なるカーネル形状とメモリアクセスを使うので、ハードウェアのピーク演算性能だけでは推論速度を予測できない。2023年のMetal実装が特定のGPUに最適化されていない可能性もあるが、実証されていない原因を断定しない。

第三に、3bit量子化は当時の6GiB級端末で7Bモデルを動かすための実用的な条件を作った。しかし原著は量子化方式の精度比較を行っておらず、生成品質の保持率も測定していない。メモリに収まることと、必要な回答品質を満たすことは別の評価軸である。

## 既存研究との差

SparseGPTやWandaなどの剪定研究、重み量子化研究は、モデルを小さくしながら精度を維持する方式そのものを提案する。本論文はそうした新方式を開発せず、**既存の量子化GGUFとllama.cpp/Metalを用いて、実機の各処理段階を比較**する。モデル・量子化・プロンプトを固定した上でSoCと熱状態の差を調べるため、最適化アルゴリズムの優劣ではなく実行環境の影響を評価する研究である。

現在のLLM推論基盤では、prefillとdecodeの分離、KVキャッシュ、カーネル選択、モデル量子化、熱制御は引き続き重要な設計項目である。しかし2023年のllama.cpp、Metal、iOS 17.1.xで観測した機種順位を、最新のllama.cppやMetal、2026年のiPhoneや別GPUへ外挿できない。むしろ本研究は、**実際に使うモデル・ランタイム・端末の組合せで再測定する必要性**を示す参考例である。

## 限界・負の結果・再現性

第一に、評価対象は単一の7Bモデルと3bit K-S量子化だけである。FP16、4bit、5bit、別のGGUF形式、別モデルの精度・速度・メモリの交換条件を比較していない。量子化による回答品質低下も評価していないため、「3bitが最も良い設定」という結論は出せない。

第二に、固定した英語質問一つ、コンテキスト上限1024、バッチ512、greedy、短い反復での比較である。長い文脈、長時間の連続生成、複数アプリが動く実環境、低バッテリー、異なる周囲温度、多言語・コード生成、ネットワークを使うハイブリッド推論は評価されていない。各端末の平均9測定は比較には有用だが、幅広い入力分布を代表するものではない。

第三に、Figure 3の機種別TPSはグラフ表示で、HTML本文に厳密な数値表がない。ここでは図からの概算を断定値として採用しなかった。論文はsampling約20%の差とdecodeの順位を明記するが、全ての機種間の統計的有意差、信頼区間、GPU周波数や消費電力の詳細を提示していない。

第四に、A17 Proのdecodeが最も遅い原因は未解決である。GPUアーキテクチャ、Metalドライバ、シェーダの未最適化、端末の熱設計などが候補だが、著者はどれが原因かを証明していない。二台で同じ傾向を確認したことは個体故障の可能性を減らすが、ソフトウェアの不具合を特定したわけではない。

第五に、thermal stateはOSが管理するため、外気温、充電状態、筐体、アプリの実装、他プロセスによって結果が変わる。90秒の待機で熱状態を抑えた結果は持続負荷における解決策ではなく、測定条件の調整に過ぎない。2026年の端末選定では同じベンチマークを最新OS・最新ランタイムで再実施する必要がある。
