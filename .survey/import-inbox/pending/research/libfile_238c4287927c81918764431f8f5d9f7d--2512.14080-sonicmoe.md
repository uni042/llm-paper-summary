## 概要

混合専門家（Mixture-of-Experts; MoE）はtokenごとに一部expertだけを実行し、総parameter数を増やしながらactive FLOPsを抑える。近年はexpertの中間次元を小さくしてexpert数を増やすfine-grained化と、総expert数に対して選択数を小さくする高sparsity化が進む。しかし前者はexpert処理に伴うactivationとmemory IOを増やし、後者はGrouped GEMMでexpertごとのtoken数をtile幅へpaddingする無駄を増やす。

SonicMoEは、backwardに必要なactivationを減らす再計算設計、global memory IOとtensor-core計算を重ねるkernel、token数をhardware tileへ合わせてroutingするtoken roundingを組み合わせる。fine-grained 7B MoEではactivation memoryを45%削減し、Hopper GPUでScatterMoE BF16 kernel比1.86倍のcompute throughputを報告する。64 H100で1日213B tokenを処理し、ScatterMoEが96 H100で225B tokenを処理する構成に近いtraining throughputを得る。

## 問題設定

MoE layerではrouterがtokenをexpertへ振り分け、expertごとに異なるtoken数の行列積を実行する。expert粒度を細かくすると同じactive parameter budgetでも多くのexpert処理が発生し、中間activationをbackwardまで保持するmemoryと読み書きが増える。

GPUのGrouped GEMMは任意token数を完全に効率よく処理できず、tile単位へ切り上げる。高sparsityでは1 expert当たりtoken数が少ないため、例えば実tokenがtile境界を少し超えるだけで次tileをほぼ空のまま実行し、routing上は疎でもhardware上のFLOPsを浪費する。

## 手法

### Memory-efficient MoE backward

通常のautogradが保存する中間activationを見直し、backward時に安価に再構成できる値は保持しない。forwardでのHBM書き込みと長時間保持するactivation量を減らし、fine-grained expertで膨らむmemory footprintを抑える。交換条件としてbackward時の再計算が増える。

### IO-compute overlap kernel

expert GEMMのtileを処理する間に次に必要なactivation/weightを非同期に読み込み、memory IOとtensor-core computeをpipeline化する。fine-grained MoEでは小GEMMが増えてmemory latencyを隠しにくいため、単にFLOPsを減らすのではなくdata movementを計算の背後へ隠す。

### Tile-aware token rounding

top-K routing後のtoken assignmentをそのままGrouped GEMMへ渡すとexpertごとのtoken数がtile境界から外れる。SonicMoEはrouting scoreを考慮しつつtoken countをtileに適した数へ丸め、paddingだけのtileを減らす。高sparsity条件ではvanilla top-K routingよりkernel executionをさらに1.16倍高速化し、downstream性能は同程度に保つ。

### Algorithm-kernel co-design

activation memory削減だけでは再計算costが増え、token roundingだけではIO律速が残る。SonicMoEは保存量、IO schedule、GEMM tile occupancyを同時に設計し、fine-grainedとhigh-sparsityという異なるMoE trendのbottleneckを1 kernel familyで扱う。

## 主要結果

fine-grained 7B MoEでactivation memoryを45%削減し、ScatterMoE BF16 MoE kernel比でcompute throughputを1.86倍にする。memory削減は単なるweight圧縮ではなく、training backwardまで保持する中間値を減らした結果である。

end-to-end trainingでは64 H100のSonicMoEが213B tokens/day、96 H100のScatterMoEが225B tokens/dayを処理する。GPU数が異なるため単純な1.86倍end-to-end比較ではないが、少ないGPUで近い総throughputを得ることを示す。

高sparsity設定ではtile-aware token roundingがvanilla top-K routingに対しkernel execution timeを追加で1.16倍高速化し、downstream性能を同程度に維持する。expert当たりtoken数が十分多くtileが自然に埋まる条件では、この追加利得は小さくなる。

## 既存研究との差

ScatterMoE等はexpert computationをGrouped GEMMへ効率的に写像する。SonicMoEはGEMM実装だけでなく、backward activation保存量とrouting後token countまでhardware tileを意識して変更する。したがってfine-grained MoEのIO問題とhigh-sparsity MoEのpadding問題を別々のpoint optimizationとして扱わない。

## 限界

主要kernel評価はHopper GPUを対象とし、tile size、非同期copy、tensor-core特性が異なるGPUで同じ倍率になるとは限らない。token roundingはroutingをhardware都合で調整するため、極端な設定ではexpert selection品質との交換条件が生じ得る。213B対225B tokens/dayはGPU数が64対96で異なる実用比較であり、同一GPU数の純粋speedupとして読んではならない。
