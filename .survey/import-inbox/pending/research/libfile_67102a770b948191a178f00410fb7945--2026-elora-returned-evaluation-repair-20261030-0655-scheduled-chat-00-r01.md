# ELORA：複数LoRAの依存関係を保ったGPUキャッシュ管理

## 概要

複数の低ランク適応（LoRA）を単一の基盤LLMで提供するサービスでは、リクエストに応じてアダプタを切り替えつつ、過去の会話のKVキャッシュを再利用する。ところがLoRAの重みと履歴KVを独立にLRU退避すると、対応するLoRAがGPU上にないKVだけが残り、実際には使えないキャッシュが容量を占める。著者らが測定したvLLMではGPU上のKVの平均42.4%がその状態だった。

ELORAはLoRAとKVの親子依存を木で表し、両者を共通のGPUブロックに置く。将来の要求で削減できるロード・再計算費用を見積もって保持・退避を決めるため、固定のLoRA/KV容量分割に伴う無駄も減らせる。H800上のLlama 8B・34B・70B、三種類の要求トレースで、vLLM比平均TTFT45.7%、平均TPOT37.8%の短縮、平均TTFT500ms未満の最大到着率78.9%増を報告した。これらはキャッシュ・スケジューリングのシステム効果であり、単体行列積の高速化ではない。

## 問題設定

LoRAは基盤モデルの重み行列へ低ランク差分を加える。差分が異なると隠れ状態や後続層の鍵・値が変わるため、同じトークン列の履歴KVでも異なるLoRA間で無条件に共有できない。同じLoRAの会話内では共通プレフィックスを共有できる一方、そのLoRA自体がGPUから退避していればKVだけを残しても要求を即座に再開できない。

従来のvLLM構成ではLoRA領域とKV領域を別々に予約し、各領域で独立に退避を判断する。LoRAが足りないときにKV側に空きがあっても融通できず、人気のアダプタや会話プレフィックスが変化すると、事前に選んだ分割比が適切でなくなる。LoRAの種類数とrank、会話履歴の長さ、リクエストの到着分布が変化する実運用では、固定分割と独立LRUの両方が障害になる。

この研究の目的は単なるKVヒット率最大化ではない。LoRAと対応する連続したプレフィックスKVが同時に利用できる状態を増やし、コールドロード、再prefill、待ち行列、同じGPU上でのdecodeへの干渉を減らすことである。GPUにデータが存在することと、要求の実行に利用できることを明確に区別する。

## 手法

### LoRAを親にした依存木

CPU側の仮想根の下へLoRAごとのノードを配置し、その配下にプレフィックスKVブロックを順につなぐ。新しい要求ではLoRA IDを特定してから対応枝で一致する最長プレフィックスを検索する。GPU上にある親LoRAと連続したKVは再利用し、不足するブロックはCPU側から非同期転送する。生成で新たにできたKVは同じ枝に接続し、利用頻度、直近アクセス時刻、容量と配置場所を更新する。

退避するときは葉側から、再ロードするときは親側から順に扱う。これにより親が不在なのに子だけがGPUに残る不整合を避ける。CPUメモリも満杯になれば低価値KVは完全削除され、その後の再訪にはprefillが必要になる。木はKVテンソル本体を保持せず、依存と配置のメタデータを管理する。

### LoRAとKVの統一GPUプール

vLLMのBlockManagerを拡張し、LoRAの低ランク行列をrank方向に分割してKVと互換な固定サイズのメモリブロックへ配置する。従来のLoRA専用20%・KV専用80%のような固定境界を除き、需要に合わせて両者へ容量を配分する。木のメタデータはCPU、実際のLoRA重みとKVはGPUのブロックに置くため、検索とデータ転送の責務を分離できる。

原著では木の最大サイズを676.5KB、木操作を1ms未満と報告する。管理状態の容量が小さいことは利点だが、PCIe経由の転送やGPUメモリ断片化まで無料になるわけではない。統一プールの効果はLoRAとKVのどちらが不足するかが時間的に変わる負荷で特に重要になる。

### 将来のLoRA種類数と保持価値

直近5秒のバッチサイズとLoRA別要求確率から、次のバッチで必要となる異なるLoRA種類数を予測する。LoRA iの要求確率をp_i、バッチサイズをBとすれば期待種類数は Σ_i[1−(1−p_i)^B] である。同一LoRAを使う要求が複数あっても種類数としては1つに数える。この予測に合わせてGPU上に置くLoRA数を調整する。

スワップ判断にはロード費用、訪問回数、最終アクセスからの時間を組み合わせた保持価値を使う。原著のRetain_Evalは cost_i × visit_i × (1−sigmoid(t_i)) の形であり、再ロードが高価で最近頻繁に使われたノードを高く評価する。100ms周期で候補を見直し、満杯なら価値の低い葉を退避し、余裕があれば価値の高い親から戻す。非同期転送を推論と重ねるが、急な人気変化では過去5秒の予測が外れ得る。

### 要求処理の一連の流れ

要求が到着すると、まずLoRA IDとプレフィックスを照合し、GPU上に親LoRAと必要KVが揃うか確認する。欠けている場合は保持価値を参照して空きブロックを確保し、依存順序に従ってLoRAとKVを戻す。利用可能なKVが短ければ残りをprefillし、decodeで生成したKVを木へ登録する。実行後は頻度・時刻を更新し、次の周期のスワップ候補に反映する。この処理がLoRA間の容量競合と、同一LoRA内のKV依存を同時に扱う点がELORAの中心である。

## 評価

### 実験環境と比較対象

| 項目 | 一次論文で確認した条件 |
|---|---|
| 実行基盤 | vLLMのBlockManagerを改造した連続バッチ処理 |
| GPU | NVIDIA H800 80GB。モデル規模に応じ1、4、8 GPU |
| ホスト | Xeon Platinum 8480CL、メインメモリ256GB、PCIe 5.0 |
| 基盤モデル | Llama3-8B、Llama2-34B、Llama3-70B |
| LoRA | 20、50、100種類。rank32または64 |
| トレース | チャットボットLMSYS-33K、翻訳OPUS-100、個人エージェントTaskmaster、到着分布にAzure Functions等 |
| 比較 | vLLM、S-LoRA。SGLangは評価時点のmulti-LoRAと履歴KV再利用の互換性問題により主要比較外 |
| 指標 | TTFT（最初のトークンまでの時間）、TPOT（出力トークン間時間）、P95/P99、許容最大到着率 |

同じアプリケーションでもモデル規模とLoRA種類数を変えて試し、各構成では到着率をELORAの許容最大負荷まで10段階で変化させている。論文の平均TTFTとTPOTは要求ごとの平均であり、最大負荷は**平均TTFTが500ms未満**である最大queries/sと定義する。この条件は「全要求のP99が500ms未満」という厳格なサービス水準とは異なるため、結果の解釈を分ける必要がある。各ケースは20回反復され、ELORAの標準誤差は平均1.7%と報告される。

### 遅延・処理可能負荷の主要結果

| 指標 | vLLM比 | S-LoRA比 | 評価上の意味 |
|---|---:|---:|---|
| 平均TTFT | 45.7%短縮 | 43.3%短縮 | コールドロードと再prefillを抑制 |
| 平均TPOT | 37.8%短縮 | 31.4%短縮 | 他要求のprefillがdecodeを阻害する時間を削減 |
| 平均TTFT500ms未満の最大到着率 | 78.9%増 | 49.9%増 | SLO条件付きで収容できる要求数が増加 |
| P95 TTFT | 76.1%短縮 | 68.7%短縮 | tailの初回応答待ちの改善 |
| P99 TTFT | 73.8%短縮 | 66.1%短縮 | 特に長い初回応答待ちの改善 |
| P95 TPOT | 62.1%短縮 | 58.9%短縮 | tailの出力間隔の改善 |
| P99 TPOT | 61.2%短縮 | 57.3%短縮 | tailの出力間隔の改善 |

主要結果はGPUカーネルの演算時間ではなく、サービング要求が実際に受ける待ち時間を測ったものである。TTFTの短縮はLoRAとプレフィックスKVの再ロード・再計算を抑えた効果に対応する。TPOTの改善は間接的で、従来方式でキャッシュを失った要求が追加prefillを実行すると、同じGPU上で並行decode中の別要求を待たせるためである。原著のprefill計算時間はELORAを1とした場合、vLLMで1.38倍、S-LoRAで1.87倍だった。したがってTPOT改善を「decodeカーネル自体の高速化」と読み替えてはならない。

### トレースごとの差、感度と内部指標

翻訳ワークロードでのvLLM比平均TTFT短縮は49.4%で、他の用途の平均43.8%より大きい。原著は翻訳のLoRA需要分布がより変動し、静的なLoRA/KV容量分割が不利になったことを理由としている。固定分割の最適比率がLoRA種類数20と50で変わる感度評価も、統一プールを導入する意義に対応する。ただし全ての負荷で同じ比率だけ改善するわけではない。

依存木の必要性を示す直接的な測定は、vLLMのGPU KV平均42.4%が対応LoRA不在で無効だったという観測である。スワッパの予測については、GPU常駐LoRA数が予測値の±5%に収まる時間が94.8%と報告される。この94.8%はLoRA数予測の適合度であり、要求のSLO達成率ではない。管理コストはCPU木の最大676.5KBと探索・更新1ms未満に加え、メタデータが16MBブロックあたり管理232B、スワッパ24Bと報告される。これらは制御メタデータの小ささを示すが、GPUとCPU間の転送費用を含む総コストではない。

原著の図12はTTFTを待ち行列・LoRAコールドスタート・KVコールドスタートに分けて示す。図13はGPUメモリ利用とLoRA/KVヒット率を比較するため、単なる平均遅延の数値だけでなく、どの待ち要因を削減したかを調べる材料になる。グラフから厳密な棒の値を読み取れない項目については新たな数値を作らず、本文の明記された測定だけを記録した。評価の中心は三用途・H800環境であり、PCIe帯域の低い環境や新規LoRAが突発的に増える環境で同じ改善を保証するものではない。

### 比較の公平性と結果の読み方

vLLMの主要比較はLoRA用GPU容量を固定比率で割り当てた設定を含む。もし負荷ごとに最適な静的比率を事前探索できれば、統一プールとの差が小さくなる場合がある。S-LoRAには履歴KV再利用機能の差があるため、ELORAとの差を純粋なスワップ方策の優劣と解釈できない。SGLangも同じ機能を揃えた直接比較ではない。加えて平均TTFT500msを守る最大負荷の増加は、人気の低いLoRAのP99遅延や公平性を自動的に保証しない。実運用で再現するならLoRA別の尾部遅延、再prefill率、CPU/GPU間転送量、KVの有効ヒット率を併せて測る必要がある。

## 既存研究との差

S-LoRAは多数のLoRAを効率よくオンラインロードし、異なるアダプタの要求を同一バッチで実行するが、過去の履歴KVをELORAと同じ形で再利用しない。vLLMは履歴KV再利用を持つものの、LoRAとKVの固定容量分割および独立LRUにより、両者の親子依存を保証しない。SGLangのRadixAttentionがプレフィックス木を扱うのに対し、ELORAは木の親階層へLoRA IDを組み込み、アダプタとKVの配置・入替えを統合する。推論演算子そのものを置換するのではなく、実行可能なキャッシュ集合を増やすメモリ管理・スケジューリング技術である。

## 限界

評価はH800とLlama 8B/34B/70B、LoRA20〜100種類、チャット・翻訳・個人エージェントの三用途に限定される。履歴KVをほぼ再利用しない要求や少数の固定LoRAだけを使う環境では、依存木・スワップ判断の費用に対する利益が小さくなる。直近5秒の需要統計は急なLoRA人気反転を捉えられず、誤予測時には不要なロードや退避が発生する。非同期転送は帯域消費を消さないので、ホストメモリやPCIeが逼迫する環境では尾部遅延が悪化する可能性がある。

CPUメモリも満杯なら低価値KVを破棄し、後の再訪時にprefillをやり直す。LoRA rank、KVの長さ、同一プレフィックスの再訪頻度、GPU/CPU容量比で利得は変わる。原著は回答品質の改善や、カーネル単体の演算高速化を示す研究ではない。平均TTFT500msの許容負荷が高くなっても、LoRA間の公平性や全要求の厳格なP99 SLOを直接証明したことにはならない。
