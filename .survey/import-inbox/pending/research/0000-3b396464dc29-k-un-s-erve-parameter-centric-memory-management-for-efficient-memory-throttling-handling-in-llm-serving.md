# KunServe: Parameter-centric Memory Management for Efficient Memory Overloading Handling in LLM Serving

> 負荷急増時に複製パラメータを選んで落としてGPUメモリを即座に空け、欠けた分は完全なコピーを持つGPU群とのパイプライン並列で補うパラメータ中心のメモリ管理で、尾部TTFTを最大72.2倍削減するサービング方式。

## 概要

大規模言語モデルのサービングは、生成中の状態であるKVキャッシュをGPUメモリに保持し続ける必要がある。実ワークロードの到着は平坦ではなく、急増時にはKVキャッシュ需要がメモリ上限を超える過負荷が起きる。すると新しいリクエストは空きが出るまで待ち行列に入り、最初のトークンが出るまでの時間であるTTFT（Time To First Token）が桁違いに跳ね上がる。従来の対策はKVキャッシュ中心で、キャッシュを落とす、別GPUへ移す、CPU側へ退避するといった方法だが、対象が進行中リクエストの状態であるため、落とせば再計算、移せば転送待ちが伴い、十分な量を速く空けられない。

本論文のKunServeは、空ける対象をパラメータへ変える。サービングでは同じモデルのコピーが複数GPUへ複製されるのが普通であり、パラメータはGPUメモリの大きな割合を占める。論文の集計では代表的モデルでパラメータが1GPUあたりの使用量の34から74パーセント級に及ぶ。過負荷時に複製の一部を選んで落とせば、クラスタ全体では完全なコピーがどこかに残る範囲で、大量のメモリを即座にKVキャッシュへ回せる。パラメータが欠けたGPU上のリクエストは、完全なコピーを持つGPU群とパイプライン並列で協調して実行する。

**代表結果:** 実トレースBurstGPTとShareGPTやLongBenchのワークロードで、vLLM、Llumnix、InferCeptと比較して尾部（P99）のTTFTを12.7から72.2倍削減し、サービス品質目標（SLO）違反も7.2から12.8パーセント下がった。待ち行列そのものを消すことで、尾部の遅延が支配的だった過負荷時の絵が変わる点が主張の中核である。

## 問題設定

資源の観点では、競合はGPUメモリをめぐるパラメータとKVキャッシュの取り合いである。パラメータ量は固定だが、KVキャッシュは同時リクエスト数と生成長に比例して伸びるため、急増時はキャッシュ側が上限を突き破る。ここでキャッシュ側をいじる従来法は、進行中リクエストの品質や遅延と、新規リクエストの待ち時間の交換になってしまう。落としたキャッシュは再計算が要り、退避したキャッシュは戻す転送が要り、どちらも過負荷を深める方向に働きかねない。一方パラメータはリクエストに依存しない共有物であり、複製がある限り一部を落としても情報は失われない。問題は、落としたGPUだけではモデルを実行できないことと、協調実行のパイプライン並列が新たな泡（アイドル時間）と通信を生むことである。本論文の設計は、この二つの代償を、落とす計画の作り方とバッチの組み方で抑えることに向けられる。

## 手法のあらまし

動作は三段階である。過負荷を検知したら、まず待ち行列のリクエストのメモリ需要を見積もり、協調するGPUの組をできるだけ小さく保つ貪欲な計画で、どの複製パラメータを落とすか決めて実行し、空いた物理メモリをKVキャッシュ側へ付け替える。次に、パラメータが欠けた状態への移行を、進行中リクエストのKVキャッシュの受け渡しと協調させて滑らかに行う。その後は、欠けたGPUのリクエストを完全なコピーを持つ組の中でパイプライン並列で実行し、マイクロバッチの組み方は実行時間の見積もりに基づいて先読みで均衡させる。負荷が収まればパラメータを動的に復元し、元の配置へ戻る。障害時にも復元経路が用意される。

## 手法

### 1. パラメータドロップとドロップ計画 — 空ける量と協調範囲の交換を解く

この機構が観測するのは、待ち行列全体のKVキャッシュ需要と、各サービングインスタンスのパラメータ配置である。保持する状態は、インスタンスを組にまとめたグループ構成と、各組で落としたパラメータの範囲である。処理は貪欲なグループ化であり、小さい組同士を優先して組み合わせ、組の中では冗長なコピーを落として、組全体としてはモデルの完全なコピーが揃うようにする。組を小さく保つ理由は、性能低下が協調に加わるインスタンス数、つまりパイプラインの段数と強く相関するためであり、必要量を満たす最小限の協調で止めることが利得を守る。これにより減るボトルネックは、空きメモリ待ちの待ち行列である。追加で消費する資源は、落とした分の再配置に伴う管理と、後段の協調実行の通信である。計画が需要を満たせない場合の挙動として、グループ化を繰り返して空きを増やすが、それでも不足すれば従来型の対処に委ねられる範囲が残る。空けた物理メモリはCUDAの仮想メモリ管理APIでパラメータ側の割り当てを外し、KVキャッシュ側へ張り替えるため、既存の最適化カーネルは変更なしに広くなったキャッシュを使える。

### 2. 状態移行とKVキャッシュ交換 — 落とす瞬間に進行中リクエストを壊さない

この機構が観測するのは、ドロップ前後で実行場所が変わるリクエストと、そのKVキャッシュの所在である。保持する状態は、移行対象リクエストのキャッシュと実行段階であり、処理はドロップの適用とキャッシュの受け渡しを協調させ、リクエストが欠けたパラメータ側で止まらないよう引き継ぐことである。パラメータ構成が変わる瞬間に実行中のリクエストを放置すれば、再計算や不整合が起きる。本方式は移行を一連の手順として設計し、通常状態から落とした状態へ滑らかに移ることを狙う。これにより減るボトルネックは、移行時の再計算と停止である。追加費用はキャッシュ転送であり、受け渡しの量が大きいほど移行は重くなる。誤った場合の扱いとして、復元経路とあわせて障害耐性が設計され、ホスト側メモリやストレージにパラメータの複製を保持することで、GPU側を落としても戻せることが保証される。

### 3. 先読みバッチ編成 — パイプラインの泡を潰す

この機構が観測するのは、待ち行列にあるリクエスト群のトークン構成と、マイクロバッチごとの実行時間の見積もりである。保持する状態はコストモデルであり、注意計算の実行時間を捉え直した見積もり式を持つ。処理は、バッチ全体を再帰的に二分し、各マイクロバッチの予測時間が均衡するまで分割する先読み型の編成で、分割は対数オーダーの計算でオンラインに解ける。パイプライン並列では段ごとの処理時間がばらつくと泡が増え、協調実行の利得を食う。トークン数ではなく予測時間で均衡させることで、プリフィルとデコードが混ざる実行パターンの下でも泡を抑える。これにより減るボトルネックはパイプラインのアイドル時間である。追加費用は見積もり計算そのものであり、モデルの精度がそのまま編成の質を決めるため、論文はコストモデルの正確さも別途評価している。見積もりが外れる条件では均衡が崩れ、泡が戻る境界がある。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| パラメータドロップ | 待ち行列の需要と複製配置 | 小さい組を貪欲に作り冗長コピーを落とす | 空き待ちの待ち行列 | 協調実行の通信が増える |
| 状態移行 | 進行中リクエストとKVキャッシュ | ドロップとキャッシュ受け渡しを協調 | 移行時の再計算と停止 | キャッシュ転送量 |
| 先読みバッチ編成 | トークン構成とコストモデル | 予測時間で均衡するよう再帰分割 | パイプラインの泡 | 見積もり誤差への依存 |

## 評価

結論は、空ける対象をKVキャッシュからパラメータへ変えることで、過負荷時の尾部遅延が桁違いに下がる、というものである。評価環境は二つのクラスタで、小規模側はA800 80GBを1台ずつ持つ8サーバ、大規模側はH800 80GBとNVLinkを持つ構成であり、モデルはQwen-2.5-14BとQwen-2.5-72B、ワークロードは実トレースBurstGPTを主軸にShareGPTとLongBenchを組み合わせる。主結果はP99 TTFTで比較対象比12.7から72.2倍の削減であり、SLO違反の低下も伴う。読み方として、平均ではなく尾部が大きく動くのは、待ち行列に入るリクエストが消えるためであり、過負荷でない通常時の性能改善を主張する結果ではない点に注意が要る。除去実験と個別評価では、コストモデルの正確さ、動的復元の有効性、極端なバースト下の挙動が分けて測られ、復元によって負荷収束後に元の性能へ戻ることが確認される。未評価の点として、KVキャッシュが特に大きい注意形式のモデルは意図的に選ばれておらず、その条件ではより効くと論文は述べるにとどまる。また協調実行はネットワーク性能に依存するため、相互接続が遅い環境での再現は別途の確認が要る。

## 既存研究との差

KVキャッシュを落とす・移す・退避する従来の過負荷対策との差は、空ける対象をリクエスト状態から共有パラメータへ変えた点にある。状態は落とせば失われるが、複製パラメータは落としてもクラスタ内に完全なコピーが残るため、即座に大きく空けられる。静的にパイプライン並列へ切り替えて空ける方法とも異なり、本方式は過負荷の検知に応じて動的に落とし、収束後に復元する。負荷分散で逃がす方式との差は、逃がし先の空きを待たず、その場のメモリ構成を変えて受け入れる点にある。

## 限界・実装状況

限界は、複製が存在しない単一配置では使えないこと、協調実行の効率が相互接続の帯域と遅延に依存すること、ドロップと復元の切り替え自体に移行費用があること、評価がQwen系2モデルと特定クラスタに限られることである。実装状況は、公式コードが公開され、仮想メモリの付け替えで既存カーネルを変更せずに使える設計であることが示される。EuroSys 2026への採録版が存在し、arXiv版が一次資料として読める。

## 一般的な実装上の含意

過負荷対策では、何を落とすかより先に、落としても失われないものがメモリの何割を占めるかを見るべきである。複製された共有物は、状態より安全に、大きく、速く空けられる候補になる。また動的な構成変更は、変更そのものより、進行中リクエストの状態移行と、元へ戻る復元まで含めて初めて実用になる。
