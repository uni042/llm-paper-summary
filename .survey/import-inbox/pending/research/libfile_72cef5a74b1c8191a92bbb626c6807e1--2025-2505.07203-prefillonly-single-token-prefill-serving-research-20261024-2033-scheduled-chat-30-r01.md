# PrefillOnly：単一トークン応答に特化した事前入力処理型LLM推論基盤

## 概要

PrefillOnlyは、推薦可否、信用審査、文書分類のように、長い入力を読ませても出力は「Yes」や「No」など1トークンで足りる用途に特化したLLM推論基盤である。通常の対話型LLMサーバは入力を処理した後、未知の長さの出力を何度も生成する。そのため全層の鍵・値キャッシュ（Key-Value cache; KVキャッシュ）を残し、複数要求の逐次生成をまとめる設計を採る。しかし単一トークン応答では後続の復号がなく、同じ要求のために全層のKVキャッシュを保存する利点がない。著者はこの違いを「事前入力処理のみの負荷（prefill-only workload）」と定義する。

提案方式は、非注意層の中間テンソルを小分け処理してGPUメモリのピークを抑える「ハイブリッド事前入力処理（hybrid prefilling）」、将来の要求で再利用し得る接頭辞のKVキャッシュを残して接尾辞部分を捨てる機構、接頭辞キャッシュの命中状況を毎回反映する要求完了時間（Job Completion Time; JCT）推定とスケジューリングを統合する。vLLMを基盤に実装し、長文入力の模擬負荷2種類、GPU構成4種類、LLMモデル3種類で評価した。原著は比較方式に対し、高負荷時に平均遅延と99パーセンタイル遅延を増やさず扱える要求数を1.4～4.0倍へ高めると報告する。これは「どんなLLM要求も4倍速くなる」という意味ではなく、特定の長文・1トークン応答負荷での処理能力の比較である。

## 問題設定

### 生成用サーバが保持する不要な状態

通常の自己回帰生成では、入力トークンに対する各注意層の鍵・値をGPUメモリへ置き、次の生成トークンから参照する。生成長が未確定である以上、KVキャッシュをすぐに破棄できない。一方、単一トークン分類では入力を一度順伝播して最後の位置の出力分布を計算すれば要求は終わる。推薦の例では「Yes」「No」に候補語彙を制限し、確率をスコアとして利用する。出力を自由文として数百トークン生成する必要がない。

原著の例ではLlama-3.1-8Bで10万トークンのKVキャッシュは約12GBに達する。長文の信用履歴を多数扱うと、モデル重みだけでなく、再利用しない要求固有のKVキャッシュがメモリ容量を圧迫する。通常の分割事前入力処理（chunked prefill）は入力を小分けにするが、後のチャンクが先のチャンクを参照するため過去チャンクの全層KVを保持する。テンソル並列化は通信を、パイプライン並列化は段間の空き時間を増やし、複数GPUへ分割すれば総処理量が必ず増えるわけではない。

### KVキャッシュだけを破棄しても解決しない

素朴にKVキャッシュを捨てても、順伝播中に非注意層が作る巨大な中間テンソルが残る。原著のLlama-3.1-8Bでは、32,768トークンの多層パーセプトロン（MLP）の中間形状が32,768×28,672となり、1層分のKVキャッシュより14倍大きい場合がある。KVキャッシュを単純に捨てるだけでは、NVIDIA L4上の最大入力長は約1.6倍しか伸びなかった。メモリのピークを決める箇所が、保持状態から一時作業領域へ移るためである。

### 完了時間が予測可能でも接頭辞キャッシュで変動する

1トークン応答なら入力長から計算仕事量を予測しやすい。短い仕事から処理する最短残仕事優先（Shortest Remaining Job First; SRJF）を利用できる。しかし、実際の所要時間は同じ接頭辞を持つ要求のKVキャッシュが残っているかで変わる。要求到着時に一度だけ所要時間を見積もると、その後のキャッシュ追加・追い出しに追従できず、命中できる要求を後回しにしてしまう。PrefillOnlyはメモリ削減と要求順序を別問題として扱わず、接頭辞再利用を前提に両者を結合する。

## 手法

### 1. 事前プロファイルと要求処理の全体経路

サーバは事前に許容したい最大入力長を受け取り、その長さの模擬要求をモデルへ通してGPUのピークメモリを測定する。モデル実行に必要な領域を先に確保し、残ったGPUメモリを再利用可能な接頭辞KVキャッシュへ割り当てる。これは固定量の全層KVをすべての要求に確保する方式とは異なり、最大入力長とキャッシュ容量の交換条件を運用者が指定する設計である。

実行時にはOpenAI互換のHTTP入口が入力をトークン化し、ZeroMQによる遠隔手続呼出し（RPC）で待機キューへ渡す。スケジューラは待機要求ごとの未キャッシュトークン数と待ち時間を評価し、1件を選んで実行器へ送る。実行器は後述のハイブリッド事前入力処理を行い、1トークン分の出力確率を返す。その際に将来再利用しやすい接頭辞KVを残し、接尾辞KVを破棄する。要求完了後にキャッシュ内容が変化するため、次の要求を選ぶ直前に待機中の全要求の所要時間を再計算する。

### 2. ハイブリッド事前入力処理

通常の注意層では、現在のトークンが過去のトークンを参照するため、入力をチャンクごとに独立実行できない。注意層そのものを細分化すると、過去チャンクのKVキャッシュを維持しなければならず、注意演算カーネルの効率も低下し得る。これに対してMLPや線形射影など、トークン位置間の通信を要しない非注意層の演算は、トークン方向に分割しても同じ出力を連結できる。

PrefillOnlyは注意層を通常どおり一括実行し、連続した非注意の線形演算だけを仮想的な大きな層へまとめ、その内部をチャンク単位で順に計算する。各チャンクの中間テンソルはチャンク終了時に解放でき、長い入力全体に対応するMLP中間テンソルを同時保持しなくてよい。注意層をチャンク化しないため、通常の分割事前入力処理と異なり、前チャンクの全層KVを残して次の順伝播を待つ必要がない。論文のLlama-3.1-8B、32,768トークンの測定ではピークメモリを約2GB削減した。

実装はPyTorchの計算グラフコンパイル機能 `torch.compile` によって行う。連続線形演算をまとめた仮想層をチャンク単位で実行し、最後に出力を再結合する。単純な連結では出力の一時複製が生じるため、形状から最終出力を先行確保し、各チャンクを直接書き込む。入力と出力の形状が同じ演算では、可能な範囲で入力メモリを出力へ再利用する。この先行確保と同一領域再利用は、チャンク化の利得を別の中間バッファが相殺しないようにする実装上の要点である。

### 3. 接頭辞を保持し接尾辞のKVキャッシュを破棄する

単一要求の後続復号は不要でも、別要求が同じユーザー履歴や共通指示を先頭に持つことがある。その場合、先に計算した接頭辞KVを再利用できる。したがって「すべて捨てる」方式は次要求の計算を増やす。PrefillOnlyはGPUの余裕に応じて接頭辞KVを残し、接尾辞トークンのKVを優先して破棄する。これにより、長い入力を一度だけ処理する能力と、共有接頭辞の再利用を両立する。

原著実装ではvLLMの滑動窓注意（sliding-window attention）向け抽象化を流用して接尾辞破棄を実現し、GPUカーネルを独自に書き換えていない。論文では、KVキャッシュをCPUへ退避する実装も理論上選べると述べるが、評価実装は破棄を採用している。CPU退避の帯域、遅延、復帰費用をこの研究が測定したと解釈してはならない。

### 4. 接頭辞命中を反映する完了時間の継続再推定

各待機要求について、入力トークン数 `n_input`、現在の接頭辞キャッシュに命中するトークン数 `n_cached`、待ち時間 `T_queue` を取得する。所要時間の予測関数 `get_jct(n_input, n_cached)` は、入力長と命中数を約1,000トークン刻みでプロファイルして線形回帰で作る。著者はQwen-32B FP8、A100 1基で、キャッシュに命中しないトークン数 `n_input - n_cached` と実測完了時間のピアソン相関が0.987であったため、未命中トークン数を既定の代理指標として使う。

スケジューラは各要求の `score = get_jct(n_input,n_cached) - λ T_queue` を比較し、最小のものを実行する。接頭辞が新しくキャッシュに載れば、その接頭辞を共有する待機要求の推定所要時間が縮み、次に選ばれやすくなる。逆にキャッシュが追い出された要求は優先度が下がる。待機時間に比例する補正項は、長い要求が永遠に後回しになる飢餓（starvation）を緩和する。係数λを大きくすると99パーセンタイル遅延は改善しやすいが、平均遅延は悪化する。評価の既定値はλ=500である。

原著の図示例では、AとD、BとCがそれぞれ接頭辞を共有し、キャッシュには1件分しか残せない。到着順や静的な最短仕事優先では接頭辞再利用が1回に留まる一方、継続再推定ではA→D→C→Bの順を選び2回再利用できる。この例は機構を示す説明図であり、そのまま全負荷で命中率が2倍になるという実測結果ではない。

### 5. 長文・計算律速に合わせた単一要求実行

一般的な自己回帰復号はモデル重みを繰り返し読み出すため、複数要求をまとめる連続バッチ化が有効である。著者は長い入力の事前入力処理は計算律速になりやすく、要求をまとめても演算量が増えるだけで総処理量の改善が乏しいと判断し、1回に1要求を実行する設計を採った。これにより完了時間に基づく細かな順序制御ができるが、短い入力でGPUを十分使えない場合にはバッチ化が有利になる可能性がある。論文の実験はこの短入力領域を直接比較していない。

## 評価

### 1. 実験条件と比較対象

論文の第7節は、実サービスの完全なログ再生ではなく、二つの用途を模擬した到着負荷を用いる。推薦負荷では20ユーザー、ユーザー当たり50候補、ユーザー履歴11,000～17,000トークン、候補記事約150トークンを想定し、同一ユーザー内で接頭辞を多く共有する。信用判定負荷では60ユーザー、各入力40,000～60,000トークン、ユーザー当たり1要求とし、接頭辞再利用より最大入力長を重視する。到着時刻はポアソン過程で生成し、到着率を変化させる。いずれも短い数百トークンの分類要求を中心とした評価ではない。

| 比較軸 | 実験設定 |
|---|---|
| GPU | 2×L4 PCIe（各24GB）、2×A100 PCIe（各40GB）、2×H100 PCIe（各80GB）、2×H100 NVLink（各80GB） |
| モデル | Llama-3.1-8B、DeepSeek-R1-Distill-Qwen-32BのFP8版、Llama-3.3-70BのFP8版 |
| 比較方式 | ページ管理注意（PagedAttention）、通常の分割事前入力処理、2GPUテンソル並列、2GPUパイプライン並列 |
| 指標 | 毎秒要求数（QPS）、平均要求遅延、99パーセンタイル遅延、最大入力長、GPUメモリ |
| 接頭辞キャッシュ | 提案方式と比較方式のすべてで有効 |
| 非並列方式の2GPU利用 | GPUごとに独立した実行器を置き、ユーザー識別子で同じ実行器へ配送 |
| 実装 | vLLMベース、Python約4,600行、既定の公平性係数λ=500 |

この比較では、2GPUを1要求に割り当てる並列方式と、各GPUで独立要求を処理する方式の違いが重要である。低負荷時の単一要求遅延と、同じGPU台数を使った総要求処理量を区別して読む必要がある。

### 2. 最大入力長とメモリ削減

原著表2の最大入力長（トークン）は次のとおりである。数値は該当モデルとGPU構成に依存し、モデル間の差を方式だけの差と解釈してはならない。

| 方式 | L4 | A100 | H100 |
|---|---:|---:|---:|
| ページ管理注意 | 24,000 | 11,000 | 15,000 |
| 分割事前入力処理 | 46,000 | 17,000 | 25,000 |
| パイプライン並列 | 72,000 | 38,000 | 183,000 |
| テンソル並列 | 195,000 | 77,000 | 238,000 |
| PrefillOnly | **130,000** | **87,000** | **97,000** |

L4では通常のページ管理注意の約5.4倍、A100では約7.9倍、H100では約6.5倍の最大入力長となる。一方、2GPUテンソル並列の方が最大入力長だけなら大きい条件もある。したがって「常に最長入力を扱える」という主張ではなく、**並列通信や注意層の分割に頼らず長文を扱えること**が利点である。図10の「7.9倍」はQwen-2.5-32B FP8、A100上の別の要素評価であり、表2の構成と混ぜて厳密な同一実験と見なさない。

### 3. 毎秒要求数と平均・裾遅延

図6と図7では、到着要求率を変え、平均遅延と99パーセンタイル遅延の両方を測定する。著者は高負荷条件で、比較方式より1.4～4.0倍の要求率を処理しつつ遅延を増やさないと報告した。推薦負荷では接頭辞キャッシュの枯渇が通常の分割事前入力処理の処理量を制限する一方、PrefillOnlyは再推定で命中可能な要求を優先する。信用判定負荷では長文を並列化せず処理でき、テンソル並列の全体通信やパイプラインの空き時間を回避できることが主要因となる。

ただし低QPSでは、複数GPUで1要求を同時処理する並列方式の方が要求遅延が小さくなる条件を原著自身が示している。PrefillOnlyは総処理量と高負荷時の遅延に重点を置いた設計であり、単発の最短応答時間を必ず最適化するものではない。図11では公平性係数を増やすと裾遅延が改善する代わりに平均遅延が悪化する。運用上はQPS、平均遅延、裾遅延を別々に管理する必要がある。

### 4. 構成要素と追加費用の読み方

図3の約2GBのピークメモリ削減は、32,768トークンのLlama-3.1-8Bを対象としたハイブリッド事前入力処理の測定であり、GPU総容量の削減率ではない。図10ではチャンク化、出力の先行確保、同一領域再利用の組合せによる最大入力長改善を示す。スケジューラの完了時間代理指標と実測の相関0.987はQwen-32B FP8、A100 1基の観測であり、他のモデル・GPUへ普遍的に保証される精度ではない。

原著にはキャッシュ命中率の例示があるが、継続再推定だけを静的SRJFと同一条件で分離して評価した包括的な構成要素除去表は提示されていない。複数の機構を組み合わせた総合改善を、それぞれの単独寄与として割り当てることはできない。出力品質は同じモデルの演算を並べ替える設計で大きく変更しない想定だが、アプリケーションの分類精度を多数の実データで比較した研究ではなく、主眼は推論基盤の速度とメモリにある。

## 限界・負の結果・再現性

第一に、対象は出力を1トークンへ制約できる識別的用途である。一般的な会話、長い推論過程、コード生成、逐次的な複数トークン生成ではKVキャッシュを後続復号で再利用するため、接尾辞KV破棄はそのまま適用できない。複数候補語が1トークンに収まらない分類ラベル、文章での根拠説明が必要な業務でも、問題設定を変更する必要がある。

第二に、評価の推薦負荷は約11,000～17,000トークン、信用判定負荷は約40,000～60,000トークンの模擬入力である。短い入力の大量分類をGPUでバッチ化する比較は十分ではない。1件ずつ実行する方針が短文・小モデルでも有利とは結論できない。実際の到着列や接頭辞共有分布が模擬条件と異なれば、キャッシュ再利用とSRJFの効果は変わる。

第三に、KVキャッシュの接頭辞保持はGPU空き容量を消費する。長い共有接頭辞が頻繁に再利用される場合には有利だが、接頭辞がほとんど共有されない場合には再推定の追加走査が利得を生みにくい。待機キュー全体を再評価する計算量、キャッシュ索引更新費用、`torch.compile`による初期コンパイル時間、実装の汎用性は論文の主要な定量評価対象ではない。

第四に、低負荷では2GPU並列方式の方が単発要求を速く返す条件がある。公平性係数を大きくすると平均遅延が悪化する。並列化不要を「並列化は常に悪い」と読み替えてはならない。GPU間が高速NVLinkで接続され、低遅延を最優先する場合にはテンソル並列化の方が適する可能性を著者も認めている。

第五に、評価はvLLM上の研究実装であり、著者は約4,600行のPythonコードを追加したと説明するものの、原著に検証可能な公開リポジトリURLを確認できなかった。推論エンジンのバージョン、カーネル、モデルの注意構造、GPUメモリ確保方式が変われば、ピークメモリや最大入力長は再測定が必要である。

## 既存研究との位置付け

ページ管理注意はKVキャッシュの断片化を抑え、連続バッチ化は生成段階のGPU利用率を高める。DistServeなどの事前入力・復号分離方式は、両段階のサービス水準目標を同時に満たすことを目指す。PrefillOnlyはそれらの汎用最適化を置き換えるのではなく、**復号が不要という用途の性質を利用して、不要な状態保持と不適切な要求順序を取り除く**点が異なる。KVキャッシュ圧縮・オフロードのように「必要な状態を小さく残す」方式ではなく、「その要求では後続利用しない状態を捨てる」方式である。ただし将来の別要求が共有する接頭辞だけは保持するため、全面破棄とも異なる。

システム実装への示唆は、単一トークン出力を契約で保証できる分類サービスなら、通常の自己回帰生成基盤と同じスケジューラやキャッシュ方針を使う必然性はないという点にある。既存GPUでの有効性を検討する際は、まず入力長分布、接頭辞共有率、単発遅延と総QPSのどちらを優先するかを測定すべきである。
