# DLoop：複数draft blockを一度のtarget検証へまとめる投機的復号

## 概要

投機的復号では軽量なdraft modelが候補tokenを生成し、大きなtarget modelがまとめて検証する。標準方式は「draftを一段実行→targetで検証」を交互に繰り返すため、draftが非常に高精度で全候補が採択される場合でも、blockごとにtargetのforward passが必要となる。targetの検証はdraftに比べて高コストであり、検証token数が多少増えても一回のforward passの時間は大きく増えない。この性質を利用し、**検証前に複数のdraft段を連続実行する**のがDLoopである。

従来のadaptive draft lengthは、autoregressive drafterの生成を途中で打ち切ることには有効だが、parallel drafterでは1 blockのforward passがすでに実行されているため途中停止してもdraft計算を削減できない。さらにparallel drafterは、未検証tokenに対応するtarget hidden stateを持たず、次blockを条件付けると学習時と異なる入力分布になる。DLoopは推論時のconfidence gateと学習時のloop-aware trainingを組み合わせ、autoregressive/parallelの両方へ適用する。

研究の対象はtarget modelを変更しないlossless speculative decodingである。ここでlosslessとは、検証時に標準のacceptance ruleを適用することで**targetが定める出力分布を維持する**ことを意味する。draftが常に正しい、あるいは生成テキストの意味的正確性が向上するという意味ではない。DLoopは追加のdraft forward passを支払い、より高価なtarget forward passの回数を減らす計算交換である。

## 標準方式との違い

### 通常のdraft–verify交互実行

一回のdraft stageがk個の候補を生成すると、targetはこれらを一括検証し、先頭からa個を採択したあとtarget由来のbonus tokenを一つ生成する。標準方式では1回の検証から最大k+1 tokenが得られる。たとえk個すべて採択されても、次のdraft stageの前に検証が挟まる。EAGLE-3のようなautoregressive drafterも、DFlashやDSparkのようなparallel drafterも、この交互構造のコストを持つ。

DLoopは1回の検証がS個のdraft stage、合計Sk個の候補を扱う。全採択なら一回の検証で最大Sk+1 tokenを得る。S回の標準検証と比べると中間のbonus tokenをS-1個得る機会は失うが、代わりにtarget forward passをS-1回省略できる。実際に採択されるtoken数はgateの誤判定に左右され、早い段の候補が拒否されれば後続stageで生成した候補はすべて捨てられる。この無駄がDLoopの主要なトレードオフである。

### Confidence-gated drafting loop

各draft stageの出力tokenについて、draftが付与した対数確率ℓ_iを合計し、block confidence c_s = Σℓ_iを計算する。c_sが固定閾値g以上なら次のstageを続け、下回ればそこまでの候補をtargetへまとめて検証する（§3.2、式2）。対数確率は非正なので、block内に低信頼tokenがあると和が下がる。これは最初の拒否以降を破棄する検証規則と整合する。gate自体に新たな学習headは不要で、すでに計算済みのlog probabilityを集計する。

この閾値は実行前に選ぶハイパーパラメータであり、完全な自動最適化ではない。論文はg∈{-0.25,-0.5,-0.75,-1.0}を掃引し、8ベンチマーク平均speedupで選択する。多くの構成では-0.5、EAGLE-3とQwen3-8Bの組合せでは-0.75を使用する。gを下げてloopを長くすると平均採択長は増えても、後続候補の破棄とdraft時間が増えて速度は悪化し得る。Appendix A.7.1はその具体的な負の結果を示す。

### 未検証tokenのhidden stateとloop-aware training

通常のdraft stageはtargetが計算済みのhidden stateを入力として使える。しかし2段目以降のtokenはまだtarget検証前なので、対応するtarget hidden stateは存在しない。DLoopは、既存のtarget側prefix hidden stateに、先行draft stage自身が生成したhidden stateを連結して次stageへ渡す（式3）。これにより新しいtarget forward passなしで複数stageを進められるが、通常のdraft modelはその長い自己状態の連鎖を学習していない。

loop-aware trainingは追加stage数S-1を1〜Nからサンプルし、最初のstageにはtarget側prefixを、以降にはdraft自身のhidden state連鎖を与える。損失は最初のstageのCEと最後のstageのCEの平均とし、中間stageはhidden stateを供給するが損失を掛けない（§3.3、式4）。最初のstageの品質を維持しつつ、最も長い連鎖を通った難しい最後のstageへ学習信号を与える狙いである。既存draft modelの構造やパラメータ数は変えず、追加のtarget forward passも必要としない。一方でdraftの再学習コストは確実に発生する。

論文はN=3を採用し、追加stageを1〜3段学習させる。Appendix A.7.3ではNを5へ増やしても一貫した改善はなく、学習時間・メモリが増える。中間stageへもCEを掛けるmid-CEは採択長とspeedupを下げ、DSparkのN=5ではOOMになる。**中間監督を増やせば良くなるわけではない**という負の結果が明確である。

## 実装と評価プロトコル

対象targetはQwen3-4B/8B、Qwen3.5-9B、Gemma-4-12B。draft方式はEAGLE-3、DFlash、Domino、DSpark、モデル付属のMTP moduleで、DFlashとDominoのblock sizeは16、DSparkは7、Qwen3.5-9BのMTPは3、Gemma-4-12BのMTPは6。tree verificationも元の方式に従い、DFlashはDDTreeの最大256 nodes、Domino/DSparkはDARTreeの64 nodesを使用する。異なるtree budgetの比較を、draft algorithmだけの純粋な優劣と混同しない。

公開済みdraft modelの重みからloop-aware trainingを1 epoch実施する。PerfectBlendの130万user promptに対し、各target modelが生成した応答を教師として使用する。MTP専用の学習recipeがない構成ではEAGLE-3のrecipeを流用するため、モデル付属MTPと専用draftの学習条件は完全には一致しない。学習を含む追加準備コストは、推論時のspeedupと別に扱う。

評価はGSM8K、MATH-500、AIME25の数学3件、HumanEval、MBPP、LiveCodeBenchのコード3件、MT-Bench、Alpacaのチャット2件の計8件。通常の主結果はgreedy decoding（temperature 0）で、Appendixにはtemperature 1の採択長も掲載する。Appendix A.1ではGSM8K/MATH-500/MBPP/LCB/Alpacaはそれぞれ128 sample、AIME25は30、HumanEvalは164、MT-Benchは80を使用し、shuffle seed 0、thinking mode無効、system promptなしとする。したがって論文の8件平均は各タスク全件を等重みで評価した大規模production traceではない。

すべての学習・通常評価はNVIDIA H100 80GB、bf16で実施。主指標は一回のtarget検証で平均採択されるtoken数τと、target単独autoregressive decoding比のwall-clock speedup。τの増加率と実際の速度増加率は異なる。追加draft時間が大きければτが増えても速度は上がらない。Appendix A.3にはSGLangでのconcurrency 1〜32のthroughput測定もあり、単一要求とバッチ運用の差を確認できる。

## 評価結果：採択長とwall-clock speedup

| Target・draft方式 | 通常方式（τ / speedup） | DLoop追加（τ / speedup） | 比較 |
|---|---|---|---|
| Qwen3-4B / EAGLE-3 | 6.92 / 3.35× | **9.63 / 3.77×** | τ+39%、速度+12.5%程度 |
| Qwen3-4B / DFlash | 6.10 / 4.19× | **7.21 / 4.67×** | 速度約+11.5% |
| Qwen3-4B / Domino | 7.08 / 4.38× | **7.90 / 4.58×** | 速度約+4.6%と改善幅は小さい |
| Qwen3-4B / DSpark | 5.47 / 3.77× | **8.59 / 4.76×** | 速度約+26.3% |
| Qwen3-8B / DSpark | 5.58 / 3.81× | **9.08 / 4.82×** | 速度約+26.5% |
| Qwen3.5-9B / MTP | 3.32 / 1.55× | **6.70 / 2.18×** | τ約2倍、速度約+40.6% |
| Gemma-4-12B / MTP | 4.86 / 3.17× | **7.50 / 3.68×** | 速度約+16.1% |

Table 1の速度は**target単独autoregressive decodingに対する倍率**である。DLoopの「5〜41%改善」は、同じdraft方式にDLoopを追加する前後のspeedup倍率の比であり、target単独比で5〜41倍という意味ではない。たとえばQwen3-4B/DSparkは3.77×から4.76×で、改善は(4.76/3.77−1)≈26.3%となる。MTPのQwen3.5-9Bは1.55×から2.18×なので約40.6%である。

採択長τの増加は速度改善の必要条件とは限らない。Dominoではτが7.08→7.90と伸びても速度は4.38→4.58×で約4.6%にとどまる。draft forward passの追加コストがあるからである。チャットでは数学より全採択率が低く、DLoopの改善幅も小さい。Table 1のQwen3-4B/DSparkで数学speedupは4.36→6.02×だが、チャットは2.62→2.71×にとどまる。用途ごとの改善率の差は大きい。

### Ablation：loop単独と再学習の相乗効果

Table 2ではloopだけ、loop-aware trainingだけ、両方を分けて比較する。Qwen3-4B/DFlashは通常4.19×、loopのみ4.16×、trainingのみ4.23×、両方で4.67×。loop単独ではわずかに遅くなるが、再学習と組み合わせると改善する。Gemma-4-12B/MTPも通常3.17×に対してloopのみ2.90×と**明確に逆効果**であり、両方を適用して3.68×になる。したがって「confidence gateだけ付ければ既存draft modelが高速化する」とは言えない。未検証状態の連鎖を学習することが重要である。

Appendix A.4ではQwen3-4B/DSparkでdraft stage回数が91,851→114,391（+24.5%）に増える一方、target verificationは91,851→70,978（-22.7%）となる。tree verification込みではdraftが+37.9%、verificationが-26.9%。より安いdraftを多く実行して高価な検証を減らす、という機構が実際の実行回数で裏付けられる。Appendix A.5ではQwen3-4B/H100、1024-token prefixでDSparkのdraft時間がS=1の3.90msからS=4の15.04msへ増える一方、verificationは22.45→24.32msと比較的小幅である。gate時間は1 loop最大0.33msと記載される。

### 同時実行時の負の結果

SGLangでQwen3-8Bを提供したAppendix A.3のMATH-500 throughputでは、DFlashがconcurrency 1で907 tok/s、DLoop追加で972 tok/sへ改善する。しかしconcurrency 16では9,484→9,189 tok/s、32では11,810→11,139 tok/sへ**低下**する。HumanEvalでもconcurrency 32で9,451→9,104 tok/sへ低下する。DSparkではMATH-500の32並列で12,265→12,820 tok/sと改善するが、HumanEvalの32並列は10,926→10,825 tok/sへわずかに悪化する。単一要求の高いspeedupは高並列時の高いthroughputを保証しない。

これはGPUが大きなバッチで飽和すると、追加draftがbatch容量を消費し、target検証回数削減の利得が相殺されるためと論文は説明する。また各要求のloop深さSが異なるため、draft側は不均一な長さの実行となり、paddingの無駄または動的再編成のスケジューリング費用が必要になる。これらはproduction servingへ統合する際の未解決の実装課題である。

## 限界・サーベイでの解釈

第一に、DLoopのlossless性はtargetの検証規則を維持することに依存する。confidence gateは採択を予測するだけであり、誤予測した候補はtargetが拒否する。したがって品質を下げずに高速化できるが、採択率の低いタスクではdraftを余分に実行して損をする。全タスクで一定の利得があるとは限らない。

第二に、loop-aware trainingは追加パラメータを必要としないが、既存draft重みの再学習を要する。PerfectBlend由来130万promptとtarget応答の生成、1 epochの追加学習は無償ではない。モデル固有のdraft headやMTPに公式の学習recipeがない場合は別方式を流用しており、他のmodel familyへの適用時に同じ性能が得られるかは未検証である。

第三に、gate閾値はベンチマークで事前に選択しており、入力分布・GPU負荷・バッチ数に応じてオンラインで自動再調整する仕組みではない。Appendix A.7の閾値掃引は採択長と速度のトレードオフを示し、深いloopほど良いという単純な関係を否定する。N=5や中間stage監督も追加コストに見合う改善がなかった。

第四に、主要実験はH100 80GB、bf16、比較的小さなtarget model（4B〜12B）に限られる。70B級target、低帯域のコンシューマGPU、CPUオフロード、MoEのexpert swap、ネットワーク越しのdraft/target分離などでは、draftとtargetの相対コストが変わる。これらの環境に5〜41%をそのまま外挿しない。高並列でthroughputが逆転する実測は特に重要である。

第五に、実装URLはarXiv v2で「will be available」と記載されているため、`code`に著者指定URLを記録しつつ、現時点で公開済み・再現済みとは判定しない。評価のサンプル数、gateの掃引値、モデルの学習recipeとバッチ条件を合わせて独立再現する必要がある。

本研究は、EAGLE-3などのdraftの予測能力を直接高める研究とは異なり、**target検証の発火タイミングをdraft block単位で最適化する制御手法**である。高い全採択率とtarget forward passの相対的高コストが揃う場合に有利で、推論サーバーの高負荷領域ではbatchingと一体で評価する必要がある。
