# CoCoScale: Leveraging Layer-wise Scaling to Unlock the Potential of Online LLM Serving

## 概要
オンラインLLM servingではモデルごとの人気が偏り、hot instanceだけがburstする。従来autoscalingはfull model replicaを追加するため、weight loadとCUDA Graph準備に数十〜数百秒かかり、短いburstへ間に合わない。

CoCoScaleはTransformer layerをcapacity scalingの単位にする。hot instanceの連続N層だけをidle GPUへ複製し、その部分だけdata parallelism Pを増やす。元GPUとreplicaへbatchを分割し、複製区間の入口と出口だけscatter/gatherするため、通信回数はNに依存せず2回に固定される。

## 問題設定
instance単位のscale-outは容量増分が1 GPU/1 modelと粗く、cold startも大きい。CoCoScaleは「必要な速度向上分だけlayerを複製する」非整数的なcapacity expansionを狙う。

## 手法
### Layer-wise replication
連続N層をP-wayで複製する。replicaは自身が担当するsub-batchのKV cacheをローカル保持し、decode中のcache coherence通信を避ける。構成変更時だけ既存KVを再分配する。

### 状態移送
weightはscatter-then-exchangeの双方向ring multicast、KVは細粒度chunk transferを用い、inter-token intervalへ転送を隠す。これにより単一source multicastの線形遅延と再送を抑える。

### Controller
各構成(N,P)についてcompute短縮とboundary communicationをモデル化し、SLOから必要speedupを逆算する。NVMLで70%未満のlow-load GPUをpool化し、capacity gapが大きいinstanceからgreedyに割り当てる。runtimeでは現在構成からL1距離が小さい候補を優先し、state migrationを最小化する。

## 評価条件
| 項目 | 条件 |
|---|---|
| GPU | 4×NVIDIA H20、NVLink |
| backend | Nano-vLLM |
| model | Qwen3-8B/14B/32B |
| traces | Alibaba 60分、Azure 130分 |
| Alibaba | avg 1.62 RPS、peak 11、SLO 30s |
| Azure | avg 7.09 RPS、peak 23、SLO 27s |
| baseline | static vLLM、Alibaba threshold autoscaler |

## 主要結果
Alibaba traceでCoCoScaleの平均latencyはQwen3-8B/14B/32Bで22.1/21.9/21.8秒、Alibaba autoscalerは30.7/30.3/27.5秒。Azureでは17.5/18.1/17.0秒に対し32.2/31.9/31.2秒で、平均latency削減はAlibabaで20.7〜28.1%、Azureで43.3〜45.7%となる。

全モデル・両traceでSLO attainmentは100%。Alibaba autoscalerはAlibaba traceで40.6〜90.7%、Azure traceでは0.8〜2.4%まで落ちる。Qwen3-32Bのscale-up P50は1.52秒に対しfull-instance起動は最大241.1秒で、97.9〜99.3%短縮する。隣接active instanceへのmigration干渉はthroughput変動3%未満。

## 既存研究との差
ServerlessLLM/BlitzScale等はfull-instance起動を速くするがscale unit自体はmodelである。CoCoScaleはlayer subsetを単位にする。TPのような各layer AllReduceではなくsegment boundaryだけ通信し、既存TPとも直交して組み合わせられる。

## 限界
評価は4×H20/NVLinkの同質clusterで、遅いPCIe/Ethernetではmigration latencyが比例して増える。論文自身もPCIe 4.0等の感度評価を将来課題とする。greedy allocationはglobal optimumを保証しない。またprototypeはNano-vLLMであり、vLLM/SGLang/TensorRT-LLMへのportabilityは設計上議論されているが同じ実測評価はない。
