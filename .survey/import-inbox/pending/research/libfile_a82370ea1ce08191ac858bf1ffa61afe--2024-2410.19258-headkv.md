# Not All Heads Matter: A Head-Level KV Cache Compression Method with Integrated Retrieval and Reasoning

## 概要
従来のKVキャッシュ圧縮は、層ごとに保持トークンを選ぶ方式が多く、同じ層内の注意ヘッドへほぼ同じ予算を与える。しかし注意ヘッドには、局所構文、位置、検索、推論など異なる役割があり、長文脈QAに重要なヘッドは均一ではない。HeadKVは圧縮単位を層からヘッドへ細分化し、重要ヘッドへより多くのKV予算を配る。

HeadKV-R2はさらに、単なる「needleを見つけられるか」だけでなく、文脈から必要情報を回収して回答推論へつなげる能力を使ってヘッド重要度を推定する。LongBench、LooGLE、長文脈能力試験、Llama-3-8B-Instruct、Mistral-7B-Instructなどで評価され、特にKVサイズ64/128の厳しい予算で強い。文脈QAでは完全キャッシュの1.5%だけを保持して97%の性能を維持する。

## 問題設定
KVキャッシュは系列長に比例して増え、長文脈要求の同時実行数を制限する。トークン重要度に基づく追放は有効だが、各ヘッドの役割差を無視して同じキャッシュ容量を割り当てると、重要な検索ヘッドが必要とする証拠を捨てる一方、重要度の低いヘッドへ余分な予算を使う。

また、単純な検索能力だけでヘッドを選ぶと「証拠位置へ注意するが、その情報を回答へ利用できないヘッド」まで高く評価し得る。HeadKV-R2は検索と推論を分離せず、文脈QAに対する実際の寄与から重要度を推定する。

## 手法
### ヘッド単位の予算配分
総KV予算を各層へ均等配分する代わりに、注意ヘッドごとの重要度に応じて保持数を変える。重要ヘッドにはより長い履歴を残し、寄与の小さいヘッドでは強く圧縮する。総予算を固定したまま資源を再配分するので、メモリ量を増やさず品質を改善できる。

### HeadKV
基本版HeadKVは、ヘッドごとの文脈処理能力を評価して予算配分へ反映する。各ヘッド内では既存のトークン選択規則を利用できるため、「どのヘッドへ何個残すか」と「そのヘッド内でどのトークンを残すか」を分離する。

### HeadKV-R2
R2版では、検索だけでなく推論まで必要な文脈QAを用いてヘッドの有用性を測る。これにより、単にneedle位置へ高い注意を出すヘッドではなく、最終回答へつながる情報処理を担うヘッドへ予算を寄せる。特に小さいKV予算では、少数の重要ヘッドを保護する効果が大きい。

### 推論時の流れ
事前に得たヘッド重要度から各ヘッドのキャッシュ上限を決め、デコード中はその上限に従ってKVを保持・追放する。総保持数は圧縮率で制御されるため、完全キャッシュと同じモデル重みを使いながらメモリだけを削減する。

## 評価条件

|項目|内容|
|---|---|
|モデル|Llama-3-8B-Instruct、Mistral-7B-Instruct等|
|ベンチマーク|LongBench、LooGLE、長文脈能力試験、文脈QA|
|重点予算|KV size 64 / 128など低資源設定|
|比較|層単位・注意スコア型のKV圧縮法|
|指標|タスク性能、完全KV性能に対する保持率|
|圧縮粒度|注意ヘッド単位|

## 主要結果
最も強い結果は、文脈QAで**完全KVの1.5%のみを保持しながら完全キャッシュ性能の97%を維持**した点である。LongBenchとLooGLEでも、KV size 64/128の低予算領域で強い基準法を上回る。これは圧縮率そのものより「予算をどのヘッドへ置くか」が重要であることを示す。

|条件|結果|読み取れること|
|---|---|---|
|文脈QA、1.5% KV|完全KV性能の97%|重要ヘッドへの集中で極端な圧縮に耐える|
|KV size 64/128|基準法より顕著に良好|小予算ほど均等配分の無駄が大きい|
|複数モデル|Llama-3-8B-Instruct / Mistral-7B-Instruct等で改善|特定アーキテクチャだけの現象ではない|
|LongBench / LooGLE|広い長文脈タスクで評価|単一needle検索だけに最適化していない|

## 既存研究との差
H2OやSnapKVなどは主にトークン側の重要度を改善するが、HeadKVはその前段に「ヘッド間の予算配分」という軸を追加する。KV-Compressのようなヘッド別圧縮と共通する問題意識を持つが、HeadKV-R2は検索と推論を統合した能力推定を重視し、長文脈QAに実際に寄与するヘッドを識別する点が特徴である。

## 限界
ヘッド重要度の事前推定が実運用の要求分布とずれると、予算配分が最適でなくなる可能性がある。極端な圧縮では重要ヘッド内でも必要トークンを失う余地があり、完全キャッシュと同一出力を保証する方式ではない。また、主評価は品質とキャッシュ量であり、大規模オンラインサービングにおける実測処理量・断片化・カーネル効率は別途検証が必要である。
