## 概要

Engram conditional memoryは、LLMが毎tokenで必要とする動的な計算と、頻繁には変わらない静的知識の参照を分離する設計である。知識を巨大なembedding tableへ移せば、Transformer本体のdense計算を増やさずモデル容量を拡張できる一方、そのtableは非常に大きくなり、GPU HBMや各サーバのローカルDRAMだけへ複製するのが難しくなる。

本研究はこの条件付きメモリをCompute Express Link（CXL）の共有メモリプールへ置く。Engram参照は全tableを順次走査するのではなく、tokenごとに少数entryを疎にlookupし、さらに将来参照をprefetchできる。このアクセス特性なら、遠隔GPU間のRDMAを使うより、load/store型で細粒度アクセスできるCXL memory expansionと相性がよいというのが中心仮説である。

提案システムはCXL接続された共有メモリへEngram tableを置き、SGLangの推論経路へ統合する。複数ホストから大容量tableを共有できるため、各ノードへ同じ知識メモリを複製する必要を減らせる。実機評価では、CXL poolを利用しながらローカルDRAMに近いend-to-end性能を達成し、推論性能を大きく損なわず条件付きメモリを容量・コスト面で拡張できることを示す。

## 問題設定

LLMのパラメータを増やす一般的な方法では、全tokenが巨大な重みを通過するため計算量とメモリ帯域の両方が増える。Engramは静的知識をembedding lookupへ切り出し、必要なentryだけを読むことで「容量」と「毎tokenの演算量」を分離する。しかし容量を増やすほどembedding tableの保存先が問題になる。

各推論サーバのDRAMへtableを複製すれば低遅延だが、クラスタ全体では同じデータのコピーが増えて容量効率が悪い。RDMA経由のremote memoryは共有しやすい一方、Engramのような小さく不規則なlookupではネットワーク操作の粒度と遅延が合わない。CXLはCPUのload/storeに近い粒度で外部メモリへアクセスでき、複数ホストからmemory poolを共有できるため、この中間領域を狙う。

## 手法

### CXL memory poolへのEngram配置

Engram table本体をローカルDRAMではなくCXL memory deviceへ配置する。推論ノードはCXL fabricを通じて必要なembedding entryを読み出し、Transformerの通常計算へ合流させる。これによりtable容量をホストごとのDRAM容量から切り離し、複数サーバで共有できる。

この配置の利点は容量だけではない。同じ巨大tableを各ノードへ複製しなくてよいため、クラスタ全体のメモリ費用を下げられる。一方CXLはローカルDRAMより遅延・帯域で不利なので、アクセスがdenseであれば性能を維持できない。Engramの疎lookupという前提が重要になる。

### 疎アクセスとprefetch

Engramは各tokenでtable全体を読むのではなく、条件に応じた少数entryだけを取得する。そのため必要帯域は「table総容量」ではなく、token throughput、1層当たり取得量、Engram層数で決まる。巨大tableでも同時に触るデータ量が小さければ、CXL帯域へ収めやすい。

さらに参照パターンをprefetchできる場合、CXLからの取得をTransformer計算と重ねて待ち時間を隠せる。CXL poolの追加遅延を完全になくすのではなく、疎な転送量と計算重畳によってcritical pathへの露出を抑える設計である。

### SGLang統合

論文はメモリmicrobenchmarkだけで終わらず、CXL EngramをSGLangへ統合してend-to-end推論を測る。ランタイム側がEngram lookup、prefetch、通常のLLM実行を協調させることで、外部memory poolが実際のtoken生成へ与える影響を確認する。

この統合により、CXLを単なる大容量ストレージとしてではなく、推論中に直接参照する階層メモリとして扱う。Engram tableを大きくしてもGPU側のdense weightを同じ割合で増やさずに済むため、条件付きメモリを持つ将来モデルの容量拡張手段になる。

## 評価

実験環境は、複数のサーバノード、NVIDIA L20 GPU、ローカル大容量メモリと、CXL switchを介した共有memory deviceから構成される。論文はローカルDRAM、CXL pool、RDMA等のメモリ経路を比較し、Engram accessの粒度に対する遅延・帯域と、SGLang統合時のend-to-end性能を見る。

| 観点 | 結果・評価目的 |
|---|---|
| メモリ配置 | Engram tableをCXL共有poolへ配置 |
| アクセス形態 | 少数entryの疎lookupとprefetch |
| ランタイム | SGLangへ統合 |
| 比較 | ローカルDRAM、CXL、遠隔memory方式 |
| end-to-end | CXL利用でもDRAMに近い推論性能 |
| 容量面 | 複数ノードでtableを共有し、複製量を削減 |

重要なのは「CXLがDRAMより速い」という結果ではない。CXLは追加hopを持つが、Engramのアクセス量が疎でprefetch可能なので、その遅延を実行へ露出させにくい。したがってDRAM近似性能はワークロード特性とランタイム統合の結果である。

## なぜ効くか

巨大な条件付きメモリでは、保存容量と実際の1 token当たりアクセス量が大きく異なる。dense layerなら全重みを毎回読むため低帯域tierへの退避は難しいが、Engramではごく一部のentryしか触らない。この疎性がCXLの帯域制約を緩和する。

また共有poolにすることで、クラスタの各サーバへ同一tableを複製する容量を削減できる。モデル本体のGPU HBM、ホストDRAM、CXL poolという階層を使い分け、頻繁に計算するdense weightは高速tier、巨大だが疎に読む知識tableは容量tierへ置く設計である。

## 既存研究との差

CPU DRAMやSSDへのLLM offloadは、dense weightやKV cacheの大きな連続転送を扱うことが多い。本研究はEngramという条件付きembedding tableの小粒度lookupへ焦点を絞り、そのアクセス形態にCXLを合わせる。

RDMAベースのremote memoryとも異なり、CXLは細粒度load/storeとmemory semanticsを提供する。論文は「遠隔に置けるか」だけでなく、Engramのminimal/discrete retrievalに必要な低遅延アクセスを比較軸にしている。

## 限界

本方式の利得はEngramの疎アクセスとprefetch可能性へ依存する。1 token当たり多数entryを読む構成や、予測不能でprefetchが効かないアクセスではCXL待ち時間が前面に出る。CXL fabric自体の帯域も共有資源なので、多数ノードが同時に高いlookup rateを要求すれば競合が起こり得る。

また評価はEngram-integrated LLMという特定の条件付きメモリ構造を対象としており、通常のdense Transformerの全重みをCXLへ置けば同じ性能になることを意味しない。CXL対応hardware、switch、NUMA配置も必要で、一般的なGPUサーバだけでソフトウェア変更のみから得られる利得ではない。
