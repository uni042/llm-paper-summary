# SimpleTool：関数名と引数値を独立系列として生成する低遅延関数呼出し

## 概要

SimpleToolは、大規模言語モデルによる関数呼出し（function calling）の待ち時間を減らすために、出力表現の圧縮と並列復号（parallel decoding）を一緒に設計した手法である。通常の関数呼出しは、関数名と引数をJSON形式などで1トークンずつ出力する。括弧・引用符・カンマ・キー名はほぼ既知であり、実際に推論すべき情報は関数名と引数値に集中している。SimpleToolはこの低情報量部分を専用トークンへ畳み込み、関数名と各引数値を別々の生成系列へ分ける。

例えば天気取得では、同じ質問とツール定義を前処理した後、`<function>`の系列で関数名、`<arg1>`の系列で都市、`<arg2>`の系列で日付、`<arg3>`の系列で単位を独立に生成し、最後に所定の関数呼出し形式へ組み立てる。全系列は共通の接頭辞鍵・値キャッシュ（KV cache）を使う。従来は全出力の長さに比例した待ち時間を要するが、SimpleToolでは概ね最も長い系列の長さが支配する。専用トークンは、構文の省略と系列ごとの生成対象指定という二重の役割を担う。

Qwen2.5の0.5B～14BとQwen3の4Bを使い、関数呼出し5ベンチマークで精度と速度を評価している。RTX 4090のvLLMでは2.7～4.4倍の速度向上、4bitの活性化非量子化重み（AWQ、W4A16）を用いたQwen3-4Bでは中央値61.2ミリ秒という結果を報告した。ただしこの倍率は元のQwenモデルによる逐次関数出力を基準にしたものであり、あらゆる自由文生成を同様に高速化するものではない。

## 問題設定

関数呼出しの出力は、一般的な自由文と異なり、すべてのトークンを生成し終えるまで実行できない。通常の対話なら逐次表示で体感遅延を緩和できるが、ロボット制御やゲーム内操作では完全な呼出し引数が揃わないと次の動作に進めない。例えば10Hzの制御には1回100ミリ秒程度以下の待ち時間が求められる。出力が短いので、投機的復号の草稿生成・検証の固定費用も相対的に大きく、長文生成向けの高速化が必ずしも効率的ではない。

原著は構造化出力を三つの種類に分ける。第一は括弧や区切り記号など形式だけで決まる構文トークン、第二はツール定義からほぼコピーできるキー名、第三は質問の意味を理解しなければ決められない関数名と引数値である。前二者の情報量は低い。さらに、よく設計された関数APIでは都市と日付のように引数値が入力質問からほぼ独立に推定でき、引数間の自己回帰依存が弱い。圧縮だけでは依然として残りの値を順次生成し、並列化だけでは不要な構文生成が残るため、二つを同時に使うのが論文固有の設計である。

## 手法

### 専用トークンによる構文圧縮とモード指定

SimpleToolは合計17種類の専用トークンを導入する。自然言語用の`<content>`と`</content>`、関数名用の`<function>`と`</function>`、引数1～6の開始・終了トークン12個、未使用引数用の`<|null|>`である。これらはJSONの区切りやキー名を生成する代わりに、どの情報を出力する系列かを指定する。関数の引数名や順序はツール定義と組立処理から復元するため、モデルは引数の値だけを生成すればよい。

表1の圧縮率は、従来形式の出力トークン数をSimpleToolの最長系列のトークン数で割った値である。両方式が正しい出力を生成した標本だけを使って計算しており、失敗した呼出しを除外した値である点に注意が必要である。モデル別の平均はQwen2.5-0.5Bで5.06倍、1.5Bで4.32倍、3Bで4.38倍、Qwen3-4Bで4.32倍、7Bで5.35倍、14Bで4.51倍、全体平均4.66倍だった。圧縮率は出力形式の削減であり、そのまま同倍率の実測推論高速化ではない。

### 共有接頭辞からの並列系列生成

入力質問とツール仕様を一度だけ事前充填（prefill）し、関数名用系列と各引数用系列に異なる専用トークンを追加する。各系列は同じ入力接頭辞の鍵・値キャッシュを参照し、専用トークン以降だけを独立に生成する。これにより、入力がLトークン、系列数がHなら、系列分岐時の追加KV保持量は共有接頭辞に対するHトークン程度で済む。全系列へ長い入力を複製して保持する設計ではない。

通常の自己回帰方式の待ち時間は、事前充填時間Tp、出力長N、1トークン当たり復号時間Tdを使って`Tp+N×Td`と近似できる。SimpleToolでは各系列iの長さNiに対し、`Tp+max(Ni)×Td`に近づく。実際には並列系列を一緒に計算する費用や系列ごとの長さのばらつきがあるため完全な等式ではない。論文は、重み読込が律速の小バッチ復号で余っているGPU演算器を複数系列の同時処理に使えることを根拠にしている。

付録Gの制御実験では0.5B～14Bの6構成で8系列を並列にすると、トークン当たり処理効率は平均93.0%を保った。これは「8系列でも1系列と完全に同じ費用」という意味ではなく、一定の追加負担が残ることを示す。大バッチでは演算器の余裕が減るため、同じ低負担の仮定が崩れやすい。

### 専用出力モードの学習

モデルは同じ入力から関数名・複数の引数・自然言語という異なる出力を返す必要がある。著者らは通常より容量の大きい低ランク適応（LoRA）を多層パーセプトロン部に適用し、専用トークンの埋込層も更新可能にする。各学習標本は同じ接頭辞と異なるモード指定トークンを持つ複数の系列へ展開し、系列別の損失を重み付けして学習する。出力の長さが短い系列と長い系列の損失寄与が不均衡にならないようにするためである。

関数呼出しデータは引数2～3個に偏り、引数0個・5個・6個の事例が少ない。SimpleToolは合成データを追加して引数個数の分布を補う。6個の引数系列で評価対象の関数呼出しの95.2%を覆うが、それ以上の引数を持つAPIは最後の系列へ複数引数を詰め込む必要があり、独立性と速度の利益が減る。未使用の引数系列は`<|null|>`で早期に終了できる。

学習はモデル内部の通常の出力表現を変えるため、単なる推論時のJSON後処理では実現できない。学習した専用トークンの意味、関数名・引数の位置対応、呼出し組立器が揃って初めて完全な関数呼出しとして利用できる。汎用の元モデルに専用トークンだけ追加しても同じ性能にはならない。

## 評価

### 設定と指標

評価モデルはQwen2.5-Instructの0.5B、1.5B、3B、7B、14BとQwen3-4B-Instruct。関数呼出しの精度は、関数名とすべての引数が正しい全体正答率と、関数名だけの正答率を分ける。評価集合はBFCL-v3の単一ターン部分集合、Mobile Actions、SealTools、OpenFunction-v1、ToolAlpacaの5件で、最後の3件はOthersとして集約している。Mobile Actionsの並列呼出しは複数ターン形式へ変換して評価した。推論遅延はRTX 4090とH100で、Transformers、vLLM、接頭辞キャッシュ、AWQの構成を分けて測定した。

| モデル（RTX 4090） | Transformersでの速度比 | vLLMでの速度比 | AWQ＋vLLMのP50 |
|---|---:|---:|---:|
| Qwen2.5-0.5B | 5.35倍 | 3.07倍 | 32.1 ms |
| Qwen2.5-1.5B | 3.32倍 | 3.46倍 | 39.4 ms |
| Qwen2.5-3B | 2.93倍 | 3.78倍 | 53.9 ms |
| Qwen3-4B | 2.83倍 | 3.88倍 | 61.2 ms |
| Qwen2.5-7B | 原著表3に値なし | 原著表3に値なし | 89.3 ms（図5では73.2msとの表記もあり、設定差の再確認が必要） |
| Qwen2.5-14B | 原著表3に値なし | 原著表3に値なし | 142.5 ms（図5では128.6msとの表記もあり、設定差の再確認が必要） |

この表の倍率は同じ実装系における通常Qwenの逐次関数呼出しを1とする。AWQ欄は量子化と並列復号を併用した絶対遅延であり、純粋な並列化単独の倍率とは区別する。原著の図1と表3で7B・14Bの絶対遅延が一致しないため、どちらかを都合よく採用して確定値とせず、表3と図5の違いを明示した。

### 精度の正負を含む比較

原著表2の平均全体正答率は、Qwen2.5-0.5Bで70.9→75.3%、1.5Bで78.7→79.2%、3Bで80.5→83.3%、Qwen3-4Bで83.2→86.0%、7Bで82.8→86.3%、14Bで82.0→85.5%となった。平均の関数名正答率も改善した。ただし全ベンチマーク・全モデルで単調に改善したわけではない。例えばQwen3-4BのBFCL Non-Liveは93.7→92.5%、BFCL Liveは77.9→76.4%、BFCL Execは94.6→89.9%と低下した。構造圧縮が全体平均で有利でも、個別の関数選択・引数生成の品質低下はあり得る。

| Qwen3-4Bの評価（全体正答率） | 元モデル | SimpleTool | 差 |
|---|---:|---:|---:|
| BFCL Non-Live | 93.7% | 92.5% | -1.2ポイント |
| BFCL Live | 77.9% | 76.4% | -1.5ポイント |
| BFCL Exec | 94.6% | 89.9% | -4.7ポイント |
| Mobile Actions | 68.0% | 84.5% | +16.5ポイント |
| Others | 82.0% | 86.6% | +4.6ポイント |
| 5群平均 | 83.2% | 86.0% | +2.8ポイント |

著者らが示す平均の改善と、BFCL Execの低下を同時に記録することが重要である。関数名だけ正しくても引数が違えば実際の呼出しは失敗するため、関数名正答率の高さを完全な動作成功率と取り違えない。

### Mobile Actionsでの外部モデル比較

Mobile Actionsはスマートフォン操作7種類、約9,600件からなり、公式テスト1,283件で遅延を評価した。ST-Qwen-0.5Bは未追加学習で69.3%の全体正答率となり、FunctionGemmaの58.0%を11.3ポイント上回った。公式学習分割を用いてLoRAランク64で追加学習した後は、ST-Qwenが86.2%、FunctionGemmaが85.0%だった。追加学習は3 H100時間未満と報告されるが、これをモデルの最初の専用モード学習まで含む総費用とは扱わない。

| Mobile Actions、RTX 4090・vLLM | P50 | P90 | 比較 |
|---|---:|---:|---|
| Qwen3-4B通常モデル | 468.5 ms | 667.0 ms | 基準1.0倍 |
| Qwen2.5-0.5B通常モデル | 110.1 ms | 154.0 ms | 基準比4.3倍 |
| FunctionGemma 270M | 61.1 ms | 139.5 ms | 基準比7.7倍 |
| ST-Qwen-0.5B | 51.0 ms | 74.5 ms | 基準比9.2倍 |

小さいFunctionGemmaよりパラメータが多いST-Qwenでも、並列系列化によって中央値と90パーセンタイル遅延を低くできた。P90はP50より実運用での待ち時間変動を示す指標であり、中央値だけで制御系の安定性を判断しないための比較である。なおモデルの安全性や実際のロボット動作成功率を直接測定した表ではない。

### 感度評価と構成要素

Qwen3-4B・BFCL-v3での低ランク適応のランク別正答率は64で85.5%、256で86.4%、512で85.3%、1024で87.0%である。最大ランク1024が最良だが、512は256より低く、単純な単調増加ではない。著者らの既定値は512。公開xLAMデータだけの学習は85.3%、Qwen3-235Bによる合成データを追加すると86.3%となり、+1.0ポイントの差を得た。これにより、引数個数の偏りを補う合成例が有効である一方、専用モード学習の容量が比較的大きいことも分かる。

図5dではQwen3-4B・AWQの有効系列数を変えたとき、P50は1系列49.6msから6系列69.6msの範囲で増加する。並列化の追加費用が「完全にゼロ」ではないことを示す測定である。付録Gの平均トークン当たり処理効率93.0%とも整合する。並列化だけで常に系列数に比例した高速化が得られるわけではなく、共有接頭辞と圧縮による出力長削減を合わせて初めて大きな効果になる。

## 限界と適用条件

第一に、引数の独立性は仮定である。ファイルパスと行番号、範囲の始点と終点、前段の関数結果に依存する後段引数などは別系列で無条件に生成すると整合性が崩れる。著者らは依存する引数を一つの系列へまとめる対処を挙げるが、その場合は並列性が下がる。APIの依存構造を無視した一般化はできない。

第二に、最大6引数の系列構成は評価対象の95.2%を覆うだけで、すべてのAPIを表現する固定上限ではない。超過引数を最後の系列へ詰めると出力が長くなり、最長系列が遅延を支配する。複雑な多段階ツール操作や多数の依存引数を持つシステムでは効果が小さくなる可能性がある。

第三に、推論を高速化するための専用学習は無料ではない。17個の専用トークンを追加し、埋込層の学習を許可し、同じ入力から異なる出力を作る複数系列を学習する。通常のLoRAより大きなランクを要する場合があり、各系列を独立標本として扱う学習計算は通常の微調整より重い。既存の任意のLLMへ追加学習なしに適用できる方式ではない。

第四に、RTX 4090・H100での測定をモバイル機器へそのまま外挿できない。論文は端末向け実装としてLiteRT、Core ML、ExecuTorch等への移植を将来課題とし、視覚言語モデル（VLM）への拡張も未実証としている。RTX 4090上の4Bモデル61.2msという値はGPUでの関数出力生成であり、カメラ入力・ツール実行・物理アクチュエータ応答まで含めた閉ループ遅延ではない。

第五に、原著の精度評価はBFCL-v3の単一ターン部分集合、Mobile Actionsの変換条件、残り3ベンチマークの集約に依存する。表2では一部のBFCL群で正答率が下がっており、平均の改善だけをもって全種類の関数呼出しで品質が保証されたと判断できない。30B以上のモデルで相対的な改善が残るかも未評価である。

## 実装・既存研究との関係

従来の投機的復号（speculative decoding）は草稿候補を目標モデルで検証することでトークン生成を減らすが、SimpleToolは「出力構造そのものを短くする」「互いに弱く依存する意味成分を同時に生成する」という別の軸で高速化する。著者らは付録Jで投機的復号との組合せも検討し、追加の前向き計算回数削減と93%超の受理率を示している。これを単独のSimpleTool速度倍率と掛け合わせた全システム倍率として断定しない。

制約付き復号（constrained decoding）を使う文法系の生成器はJSON構文の正しさを保証し得るが、通常は値を逐次生成する。SimpleToolは構文を専用モードで省略し、関数名と引数を並列に生成するため、構文制約方式とは異なる。ただし構造を組み立てる側の正しさと引数値の意味的整合性は別問題である。

著者の論文PDFには公式GitHub `HaxxorCialtion/SimpleTool` とモデル配布先 `Cialtion/SimpleTool` が掲載され、2026年10月15日時点でGitHubリポジトリが公開状態であることを確認した。コードの存在は研究の再現可能性を高めるが、全ベンチマークの同条件再現や端末実機の性能まで検証したことを意味しない。RTX 4090上のvLLM実装はユーザーのローカル環境にも近いが、GPU世代、量子化、入力接頭辞のキャッシュ条件が異なる場合の速度は個別測定が必要である。
