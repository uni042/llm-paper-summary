# [AAFLOW+] Stateful Operator Abstraction with Zero-Copy Distributed KV Cache Orchestration for Multi-Agent Workflows
## 概要
multi-agent workflowではplanner、retriever、solver、debate branchなどが同じ長いcontextを繰り返し読む。textだけを受け渡すと各agentが同じprefixをprefillし直す。AAFLOW+はKV cacheを「serving engine内部の副産物」ではなく、workflow graphが配置・転送・分岐できる第一級の分散状態へ昇格させる。

## 問題設定
local prefix cacheは同一engine内の共有には効くが、agentが別node/backendへ移ると状態を持ち越しにくい。長いRAG contextではprefillが最初のトークンまでの時間（TTFT）を支配し、branch数kなら同じprefillをk回払う。KVを送れば再計算を避けられるが、KV自体が大きいため低帯域networkでは転送の方が遅い。

## 手法
### stateful operator graph
通常のdata edgeに加えてstate edgeを持つgraphを構築し、operatorへinput/output KV stateを付与する。`materialize` はtextからKVを生成し、`transfer` はnode間移動、`fork` はbranch共有、`compose` は互換な状態の結合、`evict` は寿命終了stateを解放する。compiler/schedulerがdataとstateの依存を同時に見る。

### KV state metadataと互換性
state objectにはmodel/tokenizer構成、KV block、token range、位置情報、lineage、placement/ownershipを持たせる。別modelや位置互換性のないKVを誤再利用すると生成を壊すため、compatibility predicateを満たさない場合はtextからの通常prefillへfallbackする。

### transfer-aware scheduling
schedulerは `KV size / network bandwidth + resume overhead` とlocal prefill costを比較し、transferかrecomputeを選ぶ。高帯域では一度materializeしたstateをbranchへforkする方が有利だが、短contextや低帯域ではrecomputeへ戻せる。zero-copy data pathを前提にserialization/copy費用も減らす。

## 評価条件
|項目|条件|
|---|---|
|model|Mistral-7B、Llama-3-8B|
|workflow|multi-agent debate、tree/branch型workflow等|
|agent scale|最大16 agent|
|network|帯域を変化させる解析|
|評価形態|hardware microbenchmarkで較正した解析cost model|
|注意|主要aggregate latency/speedupは実Slurm wall-clock測定ではない|

## 主要結果
|指標|報告値|解釈|
|---|---:|---|
|TTFT|最大50.2倍短縮|長い共有prefixの再prefillを避ける|
|16-agent compute cost|最大7.63倍削減|branch数増加で共有効果が拡大|
|KV memory|1.72〜6.10倍削減|fork/ownership管理で複製を抑制|
|throughput|7.74倍超|解析model上のstateflow対textflow差|

重要なのは、これらのheadline値が「実装済み分散runtimeをend-to-end実測した速度」ではなく、実測microbenchmarkをparameterにしたcost modelのaggregate値である点である。したがって50.2倍等はシステム実測として解釈しない。

## 既存研究との差
vLLM/SGLangのprefix reuseはserving engine内のcache reuseが中心である。KVCOMMのようなcross-context KV communicationに対し、AAFLOW+はworkflow compilerからstate lifecycleを見せ、materializeからfork/transfer/evictまでoperator algebraとして統一する点を主張する。

## 限界
主要性能値は解析model依存で、実際のscheduler contention、NIC/GPU copy overlap、memory pressureを含むproduction runtimeでの再現性は未確立である。共有prefix・同一modelを中心にし、heterogeneous model間state変換、長いdecode、強いeviction pressureは限定的である。answer qualityへの大規模評価も不足する。
