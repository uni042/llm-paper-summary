# CTkvr：問い合わせ重心から候補を探しトークン単位で再選別する長文KV検索

## 概要

長文脈の大規模言語モデル（LLM）では、過去の鍵・値（KV）をすべてGPU上に保持すると、文脈長と同時要求数の積に応じてメモリ使用量が増大する。KVをCPUへ退避する方式はGPUメモリを節約できるが、生成の各ステップで必要なトークンを探す検索費用とCPU・GPU間の転送が新たな律速になる。ブロック単位の索引は検索が軽い反面、不要なKVをまとめて読み込みやすい。トークン単位の近似最近傍検索は精度が高い一方、長い系列の索引構築・更新と検索が高価になる。

CTkvrは、回転位置埋め込み（RoPE）後の位置が近い問い合わせベクトルは互いに似ており、重要な鍵の上位集合も重なりやすいという観測を利用する。事前入力処理（prefill）時に末尾側の問い合わせを重心として軽量な逆引き索引qcIVFを構築し、生成（decode）時には現在の問い合わせに近い重心だけを検索する。その重心に紐付いた鍵候補を重複除去して集め、CPU上で実際の注意得点に基づきトークン単位に再順位付けする。GPUに常駐させるのは初期と近傍のKVだけで、残りの大部分をCPU DRAMへ置く。

原著はLlama-3-8BとYi-9Bの96K文脈で、全KVをGPUへ置く方式に対し最大3倍・4倍の生成処理量を報告する。CPUへ計算を分散するため大きいバッチを処理できる点が主な利点である。ただし精度の低下は全条件で1%未満ではなく、128K文脈では数ポイント下がる。システム評価は高性能CPUと大量のDRAMを備える環境であり、一般的なGPU単体構成へそのまま外挿できない。

## 問題設定と観測

### ブロック索引とトークン索引の交換条件

ブロック検索は、数個から十数個の鍵をまとめて一つの代表ベクトルで検索する。実際に重要なのがブロック内の一部トークンだけであっても残りのKVまで扱うため、同じ疎性予算で品質を落としやすい。逆に全鍵を対象とするトークン検索は細かく選べるが、近似最近傍探索用の索引を全系列へ構築する費用が大きい。出力トークンが増えたり会話が進んだりすると、事前構築した索引の新鮮さも問題になる。

CTkvrは、検索対象の鍵集合そのものを一回で決めるのではなく、似た問い合わせが過去に参照した鍵の集合を再利用する。原著図2では、位置差が1K以内のRoPE後の問い合わせ同士のコサイン類似度が、多くのRULER課題で0.8を超える。さらに、問い合わせ同士の類似度が高いほど、上位5Kの鍵集合の重複率も高い傾向がある。これは全タスク・全位置で成立する厳密な同一性ではなく、近接した問い合わせを代表点として使う動機を与える経験的観測である。

### 代表点は鍵そのものではなく問い合わせ

一般的なIVF索引は鍵の分布をクラスタリングして代表点を作る。qcIVFは逆に、長文の末尾C個の問い合わせを代表点として採用し、それぞれが強く参照した鍵のIDを格納する。キー全体を反復クラスタリングする必要がないため、事前入力時に軽く構築できる。近い位置の問い合わせが似ているという観測を利用するため、系列先頭や無作為な位置を選ぶ場合とは品質が異なる。

## 手法

### 1. 事前入力時に問い合わせ重心の逆引き索引を構築

入力は各層の問い合わせ行列Q、鍵K、値Vである。末尾C個の問い合わせを重心として選び、各重心と全文脈の鍵の注意得点を計算する。グループ化問い合わせ注意（GQA）では複数問い合わせヘッドが一つのKVヘッドを共有するため、同一KVグループ内の得点を統合し、KVヘッドごとに上位ρ個の鍵IDを保存する。索引の概念的な形状はバッチ数×KVヘッド数×C×ρである。

この索引は重心から関連鍵への対応表であり、すべての鍵ベクトルのコピーを格納するわけではない。原著の例ではバッチ1、KVヘッド4、C=512、ρ=2560で索引が約20MBとなる。これに対し全文脈のKVはCPU側へ退避し、GPUには初期トークンと近傍トークンのKVを残す。128K文脈の例ではGPU上のKVを元の約5%へ縮める設定を示すが、これは索引やその他のモデル重みを含む総GPUメモリが5%になるという意味ではない。

### 2. 生成時に重心から鍵候補を再収集

新しい問い合わせqが到着したら、GPU側でqとC個の重心とのコサイン類似度を計算し、KVヘッドごとに近いC'個の重心を選ぶ。各重心が指す鍵IDの集合を結合して重複除去する。重複を含む理論上の候補数はρ×C'だが、実際の候補数は重複係数αにより`ρ×C'×α`程度になる。類似した重心が同じ鍵を参照しやすいので、αは多くの条件で0.5以下とされる。

候補を集める段階では、全文脈の鍵を一つずつ走査しない。現在の問い合わせに近い重心だけを見ればよいため、検索はC個の重心との比較と、選ばれた重心の鍵IDの集合処理で済む。ただし重心数や取得重心数を増やせば候補数が増え、後段のCPU計算も増える。索引の軽量性と最終品質は別々に調整する必要がある。

### 3. CPUで正確なトークン単位再順位付け

集めた鍵候補について、CPU側で現在の問い合わせとの注意得点を計算する。そこから最も得点の高いρ'個の鍵IDだけを選び、対応する鍵・値を取り出して疎な注意を実行する。単に候補に含まれた全KVで完全な注意を計算するより、値の重み付き和の対象を小さくできる。候補長をL_recall、最終長をL_rerankとすると、全候補での注意より、候補へのQK得点と最終ρ'個への注意を分離した方が値集約の費用を抑えられる。

原著は候補10K、最終1K程度の条件で、再順位付けによって生成時間を約40%減らせる例を示す。ただしこの数値はCPU側の疎注意処理と候補長の特定条件に依存する。最終出力は、GPU上の初期・近傍KVへの注意結果と、CPU上の検索されたKVへの注意結果を適切に統合したものである。GPUが全KVを毎回再取得する方式ではない。

### 4. 多ターン会話に対応する索引更新

最初に作った重心は、生成が進むにつれて現在の問い合わせから離れる。そこで再順位付けで新たに得られた問い合わせと鍵の対応を、先入れ先出し（FIFO）でqcIVFへ追加し、古い対応を除去する。更新を注意計算と非同期に重ね、生成の主経路へ追加遅延を載せにくくする。更新しなければ長い会話の後半で索引の参照先が古くなり、検索精度が落ちる。

この更新は単純な重心数増加ではない。C個という予算を維持したまま、新しい問い合わせに関係する鍵IDを反映する。更新費用が完全に隠蔽できるかはCPU・GPUの余裕と実装スケジューリングに依存するため、非同期と書かれていることだけで常にゼロ費用とみなしてはならない。

### 5. CPU/GPU協調実装

事前入力時にKVをGPU常駐分とCPU退避分へ分割する。生成時の重心検索はGPU、候補鍵の再順位付けと疎注意はCPU、常駐KVへの注意はGPUが担当する。原著は索引IDの重複除去と検索を高速化する約200行の専用CUDAカーネル、複数CUDAストリームによる重畳実行を説明する。KVの物理配置、CPU側の演算量、PCIe経路の転送を一体として設計して初めて処理量の利得を得られる。

このため、既存の単一GPU用注意カーネルへ重心索引だけを足しても、同じ結果にはならない。CPUの多数のコアとDRAM容量が資源として必要であり、GPUメモリの節約はシステム全体の無償のメモリ節約ではない。

## 評価

### 評価条件

| 項目 | 原著v1の条件 |
|---|---|
| 精度モデル | Llama-3-8B-262K、Yi-9B-200K |
| 精度課題 | RULER 8K〜128K、LongBench英語13データセット、Needle-in-a-haystack |
| 比較対象 | FullKV、SnapKV、Quest、ShadowKV、MagicPIG、全鍵走査のFlat |
| 主な検索設定 | `C=min(2048, context_length/16)`、C'=4、ρ=2.5ρ'、ρ'=512または1024 |
| システムモデル | Llama-3-8B、Yi-9B、96K文脈 |
| GPU | A6000 48GB、V100 32GB、A6000の使用可能容量を24GBに制限した模擬条件 |
| CPU | Intel Xeon w9-3495X、56コア、250GB DRAM |
| 主なシステム比較 | FullKV、vLLM、MagicPIG、再順位付けを除いたCTkvr |
| 主な指標 | RULER/LongBench品質、生成処理量、同時バッチ上限、索引構築時間 |

品質評価では最終検索トークン数ρ'を固定した比較が中心で、MagicPIGは固定疎性比率4%を採るため完全な同一予算比較ではない。96K文脈の処理量比較はGPUの容量条件に依存する。24GB条件は実際のRTX 4090や同等カードの測定ではなく、A6000のメモリ上限を制限した模擬である。CPU 250GBという大きなホストメモリを必要とする点にも注意する。

### RULER：平均値と128Kの悪化を分ける

| モデル・文脈 | FullKV | CTkvr（ρ'=1024） | 差 |
|---|---:|---:|---:|
| Llama-3-8B、8K | 90.97 | 90.14 | -0.83 |
| Llama-3-8B、64K | 83.06 | 83.38 | +0.32 |
| Llama-3-8B、128K | 79.65 | 76.60 | **-3.05** |
| Yi-9B、8K | 89.60 | 90.16 | +0.56 |
| Yi-9B、64K | 66.09 | 64.54 | -1.55 |
| Yi-9B、128K | 60.91 | 58.55 | **-2.36** |

原著表1の平均差はLlama-3-8Bで-0.74、Yi-9Bで-0.56と比較的小さい。しかし最長128Kではそれぞれ3.05、2.36ポイント低下する。要旨の「1%未満の品質低下」は平均的な条件の総括であり、最長文脈まで保証する主張ではない。ρ'=512ではLlama-3-8Bの128Kが74.82となり、FullKVとの差はさらに4.83ポイントへ広がる。厳しい予算では重要な鍵を検索し損ねる可能性がある。

同じ表ではShadowKVやQuestも文脈長が増えると品質低下が大きくなる傾向がある。CTkvrはトークン単位で正確に再順位付けするため、ブロック索引の余分な鍵を含める費用を抑える。一方、全鍵走査のFlatは高品質だが、長い文脈の全鍵へアクセスするため生成速度が課題となる。精度表だけで最良のサービング方式を決めるべきではない。

### LongBench：平均ほぼ同等でも個別課題は異なる

原著表2のLlama-3-8BではFullKV平均41.76に対しCTkvr512は41.73相当（差-0.03）、CTkvr1024は41.65相当（差-0.11）とほぼ同等である。Yi-9BではFullKV49.15に対しCTkvr512は49.27相当（差+0.12）、CTkvr1024は49.21相当（差+0.06）と小幅に上回る。これらの差は指標集計の変動範囲を超える有意差として検証されたものではない。

個別の長文検索、要約、コード補完では差の方向が異なる。Llama-3-8Bの複数文書QAはFullKV21.82に対しCTkvr1024が21.20、コード課題は49.50に対し50.29となる。Yi-9Bの複数文書QAは38.54に対し38.08で、わずかに低い。平均の「同等」は全てのサブタスクで無損失という意味ではない。

### 96K文脈の処理量とバッチ容量

| 条件 | 原著の報告 | 比較上の注意 |
|---|---|---|
| Llama-3-8B、96K | FullKV比で最大3倍の生成処理量 | GPU・CPU協調構成全体の利得 |
| Yi-9B、96K | FullKV比で最大4倍の生成処理量 | 同一モデル・ハードウェア条件内で比較 |
| Llama-3-8Bのバッチ上限 | FullKV比で最大10倍 | KVの大部分をCPUへ退避する容量効果 |
| Yi-9Bのバッチ上限 | FullKV比で最大20倍 | 高性能CPUと250GB DRAMを使用 |
| MagicPIG比 | 最大約2倍のバッチ上限と処理量 | 索引構造とCPU側の実装が異なる |
| 再順位付けあり／なし | 最大約2倍の処理量 | CPUの候補値集約を減らす効果 |

これらの倍率は原著図7の条件ごとの最大値であり、すべてのGPU構成で常に3倍・4倍になるわけではない。特にFullKVはGPU上のKV容量でバッチ数が制限されるため、CPUへ退避する方式は単独要求のレイテンシを改善しなくても総処理量を増やせる。処理量と一要求の応答時間を混同しないことが重要である。

### 索引構築、パラメータ、構成要素除去

原著図8ではFaissのHNSW、IVF、KMeansによる索引構築と比較し、CTkvrの軽量構築がそれぞれ最大50倍、1000倍、10000倍短い条件を示す。これは特定のFaiss実装と対象鍵数の比較であり、任意のANNライブラリより一律に高速という証明ではない。重心を最後のC個の問い合わせから直接選ぶため、反復クラスタリングを省けることが主因である。

重心数Cを増やすと検索品質は改善し、多くのRULER課題では約320重心付近で飽和するが、needle課題ではさらに増やす余地がある。取得する重心数C'を増やすと精度が上がる一方、CPU再順位付けの候補数が増え、処理量の低下がより大きい。原著図10はこの感度を示す。重心を系列末尾から選ぶ方式は、64Kの比較で無作為・先頭・等間隔より良い平均を示し、表4の平均83.35に対し等間隔81.98、無作為79.93、先頭75.60である。

動的重心更新（DCU）の効果は、多ターンの針探しで確認される。更新しない方式ではターンが進むほど精度が落ち、更新方式は新しい問い合わせに適応する。これは初期索引が長い会話の全段階で十分とは限らないことの直接的な証拠である。CPU側の再順位付けも、候補集合に対する全注意を避けるため、図11では最大約2倍のCPU側改善を報告する。

## 限界

第一に、近似検索である以上、必要な鍵を取り逃す可能性がある。RULERの128K条件ではFullKVより数ポイント悪化し、検索予算を小さくすると差が広がる。問い合わせの位置近接性が常に意味的な類似性を保証するわけではない。急激な話題転換、多ターンの長い出力、異なる位置符号化を使うモデルでは、同じ重心戦略が最適とは限らない。

第二に、CPU側へ移したKVの容量・演算・帯域は無償ではない。実験は56コアCPUと250GB DRAMを用い、CPUの注意計算とGPUの常駐KV注意を重ねる。CPUメモリ帯域や転送が不足する環境では、索引が軽くても全体の処理量が低下する可能性がある。24GB条件は実際の24GB GPUを使った計測ではないため、特定の消費者向けGPUへ倍率を直接当てはめない。

第三に、索引の構築・更新・重複除去・GPU/CPU並列処理は専用の実装を必要とする。論文は約200行のCUDAカーネルと複数ストリームを説明するが、公式コードの公開URLを確認できず、一般の推論フレームワークへの組込み費用を独立に検証できない。GPU上のKVページング、連続バッチ処理、メモリ断片化、他のCPU負荷との競合を含む実サービス評価は別途必要である。

第四に、原著HTMLの会議名・著作権・DOI欄は未入力のテンプレート文字列である。これを正式な査読会議の出版証拠と解釈せず、2025年12月17日のarXiv v1として扱う。品質結果の比較も、原著が示したモデル、検索予算、ハードウェア条件に限定する。

## 既存研究との差

QuestやShadowKVはブロックの重要度を推定してKVを読み、MagicPIGはハッシュ索引でトークンを選ぶ。CTkvrは鍵そのものを大規模にクラスタリングする代わりに、近い問い合わせが参照した鍵IDを再利用する。まず重心で候補を絞り、最後にCPUで実際の鍵と照合してトークン単位に選ぶため、ブロック索引の粗さと全鍵トークン索引の構築費用の中間を狙う。

本方式の価値は、圧縮率だけでなく、96K級の長文を複数要求で扱う際のGPU KV容量制約を緩和することにある。導入時にはGPU容量、CPU DRAM、CPU計算資源、GPU/CPU転送、検索予算、長文品質、索引更新の費用を一緒に測るべきである。論文の処理量倍率を単独GPUのカーネル速度と読み替えると、必要なシステム構成を見誤る。
