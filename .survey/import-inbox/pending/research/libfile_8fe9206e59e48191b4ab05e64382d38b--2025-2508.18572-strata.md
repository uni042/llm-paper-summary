# Strata: Hierarchical Context Caching for Long Context Language Model Serving

## 概要

長文脈LLMでは、再利用可能な接頭辞のキー・値（KV）キャッシュをGPU高帯域メモリ（HBM）だけに保持できない。CPU DRAMやSSDへ階層化すれば容量は増えるが、再利用時に大量のKVをGPUへ戻す必要がある。既存基盤はPagedAttention由来の1〜32トークン程度の小ページを多数転送するため、PCIeの帯域を使い切れない。さらに、キャッシュ読込をプリフィル計算で隠せるという前提のスケジューラは、長い既存文脈と短い新規入力の組合せで読込時間が計算時間を超えるとGPUを待たせる。

Strataはこの二つをデータ面と制御面から分けて解く。Strata Cache Controllerは、`cudaMemcpyAsync`を小ページごとに発行する代わりに少数のCUDAブロックから多数スレッドを動かすGPU補助I/Oを使い、断片化したKVを細粒度のまま高並列に移す。GPU側は計算向けの層優先配置を保ち、CPU/SSD側は転送向けのページ優先配置にして、I/Oカーネル内でアドレス変換する。Strata Schedulerは拡張RadixTreeであるHiRadixTreeからキャッシュ位置と読込量を把握し、遅延ヒットの延期、読込量と計算量を釣り合わせるバッチ形成、残るI/O待ちへのデコード挿入を行う。

SGLang 0.4.5上の実装をH200およびGH200で評価し、Llama-3.1-8B、Qwen2.5-14B、Llama-3.1-70Bと長文脈ワークロードを使用する。LooGLEでは同一の初回トークン時間（TTFT）条件で、Llama-70BにおいてSGLang-HiCacheおよびvLLM+LMCacheより最大5倍、TensorRT-HiCacheより3.75倍のスループットを得る。短文脈ShareGPTでは同等水準を維持する。これは単なるI/Oカーネル高速化ではなく、帯域をサービング資源として扱うスケジューリングとの組合せによる結果である。

## 問題設定

PagedAttentionは論理的に連続したKVを小さな物理ページへ分割し、GPUメモリ断片化を抑える。しかし階層キャッシュでは同じ小粒度が転送効率を悪化させる。論文の測定では、PCIe 5.0の理論帯域の75〜80%を得るには1〜2 MB程度の転送粒度が必要なのに対し、ページ単位KV転送は数KBになり得る。8192トークン分のKVをページサイズ32でCPUからGPUへ戻す場合、PCIe 5.0帯域利用率は約22%に留まり、GH200の高速なCPU–GPU接続では約5%まで下がる。

ページを大きくすれば転送は効率化できるが、接頭辞一致がページ単位なのでキャッシュ命中率が下がる。Mistral-24BとShareGPTの測定では、ページサイズを大きくすると平均TTFTが最大2倍、P90 TTFTが最大2.9倍へ悪化した。したがって「転送のためにページを粗くする」だけでは、階層キャッシュの再利用利益を失う。

もう一つの問題は読込待ちである。既存方式は次層KVのPCIe転送を現在層のプリフィル計算に重ねるが、既存キャッシュが長く新規トークンが少ない要求では、読込量に対して計算量が足りない。Qwen2.5-14BとLooGLEの例では、標準的な階層キャッシュでプリフィル時間の最大74%がKV転送待ちとなり、スループットが最大4分の1へ落ちる。I/O自体を最適化しても最大24%の停止が残るため、スケジューラ側で計算と転送を組み合わせる必要がある。

## 手法

### GPU補助I/O

Strataは小さな`cudaMemcpyAsync`を大量発行せず、GPU上にI/O専用カーネルを起動する。各スレッドがCPUの登録済み固定メモリまたはGPUメモリから小チャンクをレジスタへ読み、宛先へ書き出す。GPUの大量スレッドによって同時I/O数を増やし、128バイト程度の細粒度アクセスでも多数ページを並列転送できるため、キャッシュ命中率に有利な小ページを維持したまま帯域利用率を上げられる。

ただしI/Oカーネルもストリーミングマルチプロセッサ（SM）、レジスタ、実行サイクルを消費し、モデルカーネルと競合する。Strataは大きなCUDAブロックを少数だけ起動してI/O処理を少数SMへ寄せ、キャッシュを迂回する低レベル命令で汚染も抑える。H200の微視的評価では1024スレッド×2ブロックで約50 GB/sを得ながら、同時実行するプリフィルの性能低下を5%未満、デコードを10%未満に抑えた。既定ではCPU→GPU読込に2ブロック、非クリティカルなGPU→CPU退避に1ブロックを割り当てる。

### メモリ階層ごとの配置分離

GPU上では各層の計算が連続してKVへ触れるため、層優先配置がカーネル実装に適する。一方、CPUやSSDではページに属する全層データを連続させたページ優先配置の方が大きな連続転送を作れる。StrataはI/Oカーネルが転送時に宛先オフセットを計算し直すことで、GPUでは層優先、下位階層ではページ優先という異なる物理配置を許す。

SSDを使う場合、キャッシュ命中を検出した時点でSSD→CPUの機会的プリフェッチを始め、要求の待ち行列時間へ重ねる。実行開始時には途中までしか読めていなくても利用可能な部分を使う。ページ優先配置はページサイズ32・8192トークンのディスク読込で、層優先配置より最大4倍の遅延削減を示した。

### HiRadixTreeと遅延ヒット回避

制御面ではSGLangのRadixTreeをHiRadixTreeへ拡張し、各KVページがどの階層にあり、どれだけ読込が必要かをスケジューラから参照できるようにする。また、まだ生成中または待ち行列中で将来キャッシュになる接頭辞を一時ノードとして記録する。一時ノードには`in-queue`または`in-flight`を付ける。

同じ接頭辞を必要とする後続要求が一時ノードに100トークン以上一致すると、その要求を次のスケジューリング周期へ延期し、待ち行列先頭へ移す。先行要求が完了すると一時ノードは実KV位置を指す通常ノードへ変わり、後続要求は高価な重複プリフィルではなく新しく温まったキャッシュを利用できる。この遅延ヒット回避は要求を単に遅らせるのではなく、近い将来確定するキャッシュを待つことで重複計算を除く。

### 負荷均衡バッチとバブル充填

HiRadixTreeから各要求の「CPUから読むKV量」と「新規プリフィル計算量」を見積もり、バッチ全体の読込/計算比がハードウェア・モデル依存の閾値を超えないよう要求を選ぶ。既定閾値は100で、読込待ちが現れ始める実測点に対応する。同じ文脈を共有する要求はバンドル命中として優先的に同一バッチへ入れ、GPU上のKV再利用と転送削減を両立する。飢餓を避けるため、各バッチは待ち行列先頭要求から開始し、後回し要求の順序も保持する。

それでも読込時間が計算時間を上回る場合、Strataは準備済みプリフィルを待たせ、その空き時間にデコードバッチを実行する。KV読込は主にPCIe帯域、デコードは主にHBM帯域を使うため、資源競合が比較的小さい。これにより「I/Oを計算へ隠す」だけでなく、隠し切れない時間そのものへ別の有用計算を差し込む。

## 主要結果

| 条件 | 比較 | Strataの結果 | 解釈 |
|---|---|---|---|
| Llama-8B / LooGLE / H200 | SGLang-HiCache、vLLM-LMCache、TensorRT-HiCache | 同一TTFTで最大3.2×、2.6×、1.9× throughput | 長文脈でI/Oとスケジューリング双方が効く |
| Qwen-14B / LooGLE / H200 | 同上 | 最大3.9×、2.1×、1.9× | モデルが変わっても階層キャッシュ律速を緩和 |
| Llama-70B / LooGLE / H200 | 同上 | 最大5×、5×、3.75× | 4 GPUテンソル並列でも効果を維持 |
| Llama-8B / ReviewMT | vLLM-LMCache、TensorRT-HiCache、SGLang-HiCache | 最大2.3×、2.3×、1.7× | デコードが長くプリフィル比率が下がると利得は縮小 |
| NarrativeQA warm cache | vLLM-LMCache | 8B/14B/70Bで最大2.3×/2.6×/2.5× throughput | CPUキャッシュが温まった定常状態でも有効 |
| 構成要素除去 / Qwen-14B | SGLang-HiCache | scheduler単体最大1.8×、GPU補助I/O単体最大2.3× peak throughput | 低負荷は制御面、高負荷はI/O面の寄与が大きい |
| GH200 / Llama-8B / LooGLE | 標準DMA | 持続CPU–GPU帯域40→150 GB/s | 高速リンクはソフトウェア側I/O改善がないと活かし切れない |
| ディスク / 8192 token / page 32 | 層優先配置 | ページ優先配置で読込遅延最大4×短縮 | 階層ごとの配置分離がSSDにも効く |

長文脈階層キャッシュでは約95%のキャッシュ命中率を得ても、転送が遅ければ性能は出ない。Strataの構成要素除去では、低要求率ではスケジューリング単体の効果が大きいが、高要求率ではI/Oが支配的になりGPU補助I/Oが不可欠になる。これは二つの機構が同じ問題を重複して解くのではなく、負荷領域ごとに異なる律速を解いていることを示す。

キャッシュ距離を変えた評価では、同一文脈要求を近接させた最小距離条件で遅延ヒット回避がピークスループットを42%改善する一方、最大距離では同機構の利得が消える。逆にI/O改善はシャッフル条件で76%、最大距離で95%改善し、負荷均衡バッチがさらに11〜12%、バブル充填が3〜8%を加える。したがって各機構の有効性はアクセス局所性に依存する。

## 既存研究との差

CachedAttention、Pensieve、FlashGenなどはCPU等からKVを層ごとに読み、次層転送を現在層計算へ重ねる。Strataはこの重畳を維持しつつ、小ページ転送そのものをGPU補助I/Oへ置換し、さらに「読込を計算で隠せない」状態をスケジューラが明示的に検出する。従来の階層キャッシュがI/Oを背景処理として扱うのに対し、StrataはCPU–GPU帯域をバッチ形成時の第一級資源にする点が異なる。

MooncakeやMemServeは分散KVプールと大域的資源管理に焦点を置く。Strataは単一計算インスタンス内のメモリ階層と要求スケジューリングを対象とし、高速ネットワークを前提にしない。論文はこれら分散設計の転送エンジンと組み合わせ得るとするが、分散キャッシュ管理自体を置き換えるものではない。

また、ページを大きくして転送効率を上げる方式とは異なり、Strataは小ページを保ったままGPUスレッド並列性で転送を束ねる。そのため接頭辞一致の細粒度を犠牲にせず、GPU計算向け配置とCPU/SSD転送向け配置も分離できる。

## 限界

主対象は長文脈かつ接頭辞再利用があるワークロードである。短文脈ShareGPTでは他基盤と同等で、大幅な追加高速化は示さない。またReviewMTのようにデコード比率が高いとプリフィル・キャッシュ読込の支配度が下がり、LooGLEより改善倍率が小さくなる。

GPU補助I/Oは専用DMAではなくGPU計算資源を使うため、割当を増やしすぎるとモデルカーネルへ干渉する。H200の微視的評価でもデコードへの干渉はプリフィルより大きく、論文はブロック数を制限している。最適な読込/計算比閾値もハードウェアとモデルに依存し、プロファイルが必要である。

主要エンドツーエンド比較ではSSDを使っていない。SSDについては配置の微視的評価と機会的プリフェッチ設計を示すが、vLLM/LMCache/TensorRT-LLMを含む同一条件の完全なディスク階層サービング比較ではない。また単一計算インスタンスを中心に評価しており、ネットワーク越しの大規模分散KVプールにおける帯域競合や障害時挙動は主要評価範囲外である。

論文はSGLang 0.4.5を基盤とする2025年時点の実装であり、各サービング基盤の後続版で階層キャッシュやI/Oカーネルが改善された場合、比較倍率は変化し得る。一方、ページ断片化とI/O待ちを別々に扱う設計原理は、比較版固有の最適化とは切り分けて読む必要がある。
