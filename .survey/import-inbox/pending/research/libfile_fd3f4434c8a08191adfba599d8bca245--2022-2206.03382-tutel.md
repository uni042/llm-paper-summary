# Tutel: Adaptive Mixture-of-Experts at Scale

## 概要
混合専門家モデル（Mixture-of-Experts; MoE）は、各トークンを少数の専門家へだけ送ることで総パラメータ数を増やしても1トークン当たり計算量を抑える。しかし実際の専門家負荷はゲートの選択、top-k、capacity factor、入力分布によって変動し、論文では同一学習中でも必要expert capacityが最大4.38倍変化する。固定された専門家並列・モデル並列・通信パイプラインでは、その時点の負荷に適した実行形態を選べず、GPU計算とAll-to-All通信の双方が遊休する。

Tutelの中心であるFlexは、MoEパラメータと入力の配置を複数の並列方式で共有できる形へ統一し、テンソル移動なしで並列方式を切り替える。さらに通信と専門家FFNを重ねる適応パイプライン、Flexible All-to-All、二次元階層All-to-Allを組み合わせる。単一MoE層では16 A100で4.96倍、2048 A100で5.75倍の高速化、実アプリケーションのSwinV2-MoEではFairseq比で学習最大1.55倍、推論最大2.11倍を示す。

## 問題設定
MoE層ではゲートが各トークンの宛先expertを決め、dispatch All-to-AllでGPU間にトークンを移動し、各expertのFFNを実行した後、combine All-to-Allで出力を元GPUへ戻す。この経路では通信量とexpert当たりトークン数が入力ごとに変わる。固定並列方式P1/P2の比較では負荷条件によって優劣が逆転し、性能差は7.39〜27.76%に達する。

規模拡大では通信も悪化する。線形All-to-AllはGPU数が増えるほどpeer当たりメッセージが小さくなり、高速リンクを飽和させにくい。論文の典型設定ではAll-to-All比率が16 GPUの33.7%から256 GPUの56.7%へ増える。また通常All-to-Allの出力レイアウトをそのままFFNへ渡すと、2048 GPU時の小さな行列形状によりFFNが単一GPU比11.3倍遅くなる例を示す。

## 手法
### Flexible All-to-All
通常のAll-to-Allがworld size依存のレイアウトを生成するのに対し、Flexible All-to-Allは結合次元と分割次元を指定し、出力を `(local experts, global capacity, channel)` のようにworld sizeへ依存しない形へ保つ。必要なら固定tileへ分割する。これにより通信後のFFN行列形状が極端に細くなる問題を避け、後段計算を安定させる。

### 適応並列切替
Flexはexpert+data parallelとexpert+model parallelを、token feeding、gradient更新、parameter placementが互換になるよう再設計する。各GPUがZeRO型のparameter sliceを持つ共通配置を使うため、top-kやcapacity factorが変わって最適方式が変化しても、巨大なexpert重みを再配置せず実行方式を切り替えられる。単一MoE層ではこの適応切替単体で最大1.74倍の改善を報告する。

### 適応パイプラインと2DH All-to-All
通信とFFN計算をchunkへ分けて重ねるが、最適chunk数やAll-to-All方式は負荷と規模で変わる。Tutelは候補を実測・選択し、通信と計算の干渉まで含めてパイプラインを選ぶ。この機構単体で最大2.00倍。さらに二次元階層（2DH）All-to-Allは大規模クラスタを階層化して通信を構成し、2048 A100で従来dispatch比最大20.7倍、4096 GPUまでの実行を可能にする。

## 評価条件・主要結果
| 観点 | 条件・結果 |
|---|---|
| ハードウェア | Azure NDm A100 v4、16〜4096 A100規模 |
| 単一MoE層 | 16 GPUで4.96倍、2048 GPUで5.75倍 |
| 適応並列 | 最大1.74倍 |
| 適応パイプライン | 最大2.00倍 |
| All-to-All | 2048 GPUで最大20.7倍 |
| 実モデル | SwinV2-MoE、Fairseq比較 |
| E2E | 学習最大1.55倍、推論最大2.11倍 |

MoE層単体の大きな倍率と、実モデルのエンドツーエンド倍率は区別すべきである。前者はMoE部分のボトルネック除去効果、後者は非MoE層も含めた全体利得を示す。

## 既存研究との差
既存のGShard、Fairseq、DeepSpeed等はMoEを支援するが、並列化と通信方式が静的である。Tutelは「同じparameter/data layoutを複数実行方式で共有する」ことを先に設計し、負荷変化に応じた切替をparameter migrationなしで可能にした点が核である。またAll-to-Allを単なる通信primitiveとして扱わず、後段FFNのtensor shapeまで含めて共同設計する。

## 限界
主要な実アプリ評価はSwinV2-MoEであり、現代の生成LLMのdecode、小batch、KV cache、expert offloadを直接評価した論文ではない。推論2.11倍はMoE実行基盤として重要だが、LLMサービング全体のTTFT/TPOT改善を意味しない。また適応方式の利得はexpert負荷変動、ネットワーク規模、通信・計算比に依存する。
