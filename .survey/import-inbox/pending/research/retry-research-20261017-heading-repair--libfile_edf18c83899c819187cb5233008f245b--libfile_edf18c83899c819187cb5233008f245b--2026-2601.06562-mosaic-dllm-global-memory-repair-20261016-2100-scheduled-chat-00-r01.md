# Mosaic：拡散型LLMの長文脈推論を全体メモリ計画と動的ピーク制御で実現

## 概要

Mosaicは、拡散型大規模言語モデル（diffusion LLM、以下dLLM）における長文脈推論のメモリ不足を、通常の自己回帰型モデルとは異なる原因から捉え直した推論システムである。自己回帰型では過去トークンの鍵・値キャッシュ（KVキャッシュ）が蓄積するのに対し、双方向の拡散型推論では系列全体の表現が反復ごとに変わるため、毎回生成される中間活性値が大きな割合を占める。とくに語彙全体への出力スコア（logits）と全結合層（FFN）の中間出力が、未確定トークンの割合に応じて交互にメモリ使用量の山を作る。

提案方式は、未確定位置だけの出力スコア計算、演算グラフの明示登録、容量不足時だけ有効化する演算分割、仮想アドレスを利用した全体メモリ計画を組み合わせる。著者らはRTX 3090（24 GB）およびA100（40 GB）上でLLaDA-8B、Dream-7B、LLaDA-MoEを評価し、最大系列長が比較対象に応じて15.89～32.98倍、活性値の最大／平均メモリ比が平均2.71倍改善し、反復ごとの遅延も4.12～23.26%短縮したと報告する。ただし最大系列長を調べる実験には模擬入力を使用しており、極端な系列長での文章品質を示す結果ではない。

## 問題設定：KVキャッシュではなく一時活性値が律速になる

自己回帰型LLMでは、各復号ステップが新しいトークンを少数処理するため、以前のトークンに対応する鍵・値は再利用できる。系列が伸びると、この長寿命キャッシュが容量を圧迫する。PagedAttentionのようなページ管理は、この蓄積する状態の断片化を抑える設計である。dLLMでは複数のマスク位置を同時に推定し、次の反復では更新済み系列を再入力する。双方向注意により鍵・値も変わるため、従来の長寿命キャッシュを中心とした対策だけでは支配的なメモリ費用を除けない。

著者らの計測では、dLLMの出力スコア行列は系列長と語彙数の積に比例して大きくなるが、実際に次のトークンを採用するのはマスクが残っている位置だけである。すでに確定した位置に対する語彙全体のスコアを計算・保存することは不要であり、マスク位置が減るほど無駄が増える。一方、FFNはマスク率に関係なく系列全体を処理する。したがってマスク率が高い段階では出力スコア、低い段階ではFFNが最大メモリ需要を決める。固定的に一方だけ分割しても、別の演算が最大値を決める場合には効果がない。

もう一つの問題はメモリの断片化である。一般的な動的グラフ捕捉は演算を複数の部分グラフへ分断し、各部分が個別に確保した領域を全体で再利用しにくい。著者らは32K系列で確保済みメモリが理論的な最大需要を43.19%上回る例を示す。領域再利用のための確保キャッシュを無効にすると割り当て遅延が46～72%増えるため、単純に確保キャッシュを止めるだけでも解決しない。Mosaicは演算の生存期間と配置をモデル全体で決める。

## 手法

### 1. マスク位置限定の出力スコア計算（Mask-only Logits Kernel）

入力は全トークンの隠れ状態と、まだマスクされているトークン位置の索引である。通常の出力投影は全位置に対する行列積を行うが、Mosaicは索引を使って必要な行だけを読み出す収集・行列積融合カーネル（gather-GEMM fused kernel）を用いる。各GPU計算単位はタイル単位で索引を間接参照し、分散した隠れ状態をオンチップメモリへ取り込み、そのまま出力投影を実行する。別の大きな連続収集バッファをGPUの大域メモリへ作らない点が重要である。

出力はマスク位置に限ったスコアであり、確定位置の語彙スコアに要した演算と一時保存領域を削除できる。マスク率が高い初期反復では計算量がまだ大きいが、復号が進んでマスク位置が減るほど効果が大きくなる。論文はこの機構を含むシステムの遅延削減を報告する一方、4.12～23.26%を「このカーネル単体の高速化倍率」とはしていない。演算子単体の数値と全体遅延を区別する必要がある。

### 2. 演算グラフ登録器（Graph Registrar）

入力はモデルの演算順序、各演算の入力・出力依存関係、系列長などの可変次元である。Mosaicは動的捕捉任せにせず、`add_op()` で演算を、`add_alias()` で同じアドレスを使う入出力関係を、`add_barrier()` で分割実行中に保持すべき入力の生存期間を明示する。実行前にパラメータ化されたグラフのひな型を登録し、要求到着時に実際の系列長と分割数を代入する。

この出力は途中で切れない演算依存グラフであり、後段の全体メモリ計画と演算分割探索の共通入力になる。特に分割処理では同じ入力を複数チャンクが読むため、最初のチャンクが終わっただけで元データを再利用してしまうと誤動作する。障壁の明示は単なる高速化ではなく、メモリ生存期間の正しさを保証するためにも必要である。代償としてモデルごとの演算登録と、出力先を制御できる独自演算子の実装が必要になる。

### 3. 必要時だけ分割する最適化器（Lazy Chunking Optimizer）

入力は現在の総トークン数、マスク位置数、利用可能な物理メモリ容量、および登録済みグラフである。分割する候補は出力スコア計算とFFNで、分割数をそれぞれ `K_logits`、`K_FFN` とする。通常は分割を無効にして単一の大きな演算を実行し、メモリが足りない要求でのみ分割を有効にする。長い系列ほどGPUの計算が飽和するため、32K系列を4分割したときの追加遅延は出力スコアで0.5%未満、FFNで2%未満という観測が、この遅延抑制策の根拠になっている。

容量不足時には、現在最大の活性値を作る演算を特定し、その演算の分割数を1つ増やしてメモリ計画を再評価する。たとえば出力スコアが最大ならFFNを先に分割しても全体の最大使用量は変わらないため、そのような候補を探索しない。全組み合わせを総当たりするのではなく、最大値を決める演算だけを順に縮小する。計画上の最大値が容量に収まった時点で探索を終了し、分割不能な演算が最大値になっても収まらなければ実行不能と判断する。出力はその要求に適用する二つの分割数である。

この方式は、全系列に常時分割を適用して小規模要求まで遅くする欠点を避ける。ただし探索は要求ごとの状態に依存し、マスク率や利用可能容量が変化すると設定も変わる。また、分割できない部分の活性値が限界を決めた場合には、分割数を増やしても最大系列長を伸ばせない。

### 4. 全体メモリ管理器（Global Memory Manager）

登録済みグラフから各テンソルの生成時刻と最終利用時刻を求め、生存期間が重ならない領域を共有させる。単一要求計画器（single-request planner）はテンソルごとの大きさと開始オフセットを確定する。理論上の最適配置は整数線形計画として難しいが、Mosaicは先着適合方式（first-fit）を使う。著者らの比較では、整数線形計画器と同じ最大系列長を維持しながら、計画時間をその0.1～4.3%に抑えた。

連続した大きな物理領域を起動時に確保すると、短い要求で容量を浪費する。そこで仮想メモリ管理（VMM）によって大きな連続仮想アドレス範囲だけを予約し、要求ごとに計算した最大使用量に応じて物理ページを後から対応付ける。実行側には連続した作業領域として見えるが、物理メモリは必要量に限定される。各演算は事前に決めたオフセットへ直接書き込む独自のインプレース演算を使い、通常のPyTorch演算が出力ごとに新規領域を確保することを避ける。

四つの機構の接続は次のとおりである。モデルごとにグラフひな型を登録する。要求到着後、現在のマスク率と系列長から必要な分割数を探索する。その設定を含む全グラフでテンソル生存期間と配置を計画し、仮想アドレスへ必要な物理ページを対応付ける。各拡散反復ではマスク位置だけに出力スコアを計算し、必要なFFN・出力演算を分割しながら事前計画した作業領域を再利用する。個々の技法を独立に足しただけでなく、同じグラフを使って探索・配置・実行を一致させることが設計の核である。

評価の主眼は実機でのメモリ容量限界と1反復の遅延である。模擬入力による最大長の測定は、対応可能なメモリ配置を示すが、その長さでの文章生成の正確さや推論性能を示すものではない。また、GPU間通信、複数要求の大規模配信負荷、消費電力を主要な評価対象としていない。

ここで「79.0～197.1%増」「88.9～114.3%増」「221.3～673.3%増」は段階的に機構を加えた構成要素除去実験の寄与であり、同一の初期値に対して単純に足し合わせる数字ではない。また「15.89～32.98倍」は異なる比較対象に対する最大系列長の倍率であり、1回の生成がそれだけ高速になるという意味ではない。

動的ピーク制御が最大長に効く理由は、実行中のどの反復でも生じ得る最悪の一時メモリ需要を収めなければ実行できないためである。出力スコアの不要部分を消してもFFNが最大になればそこで頭打ちになるが、分割探索はその時点の最大演算を追加で縮小する。全体メモリ計画は、削減された理論ピークを物理メモリ確保の削減へつなげる役割を持つ。

## 既存方式との違い

PagedAttentionは主として自己回帰型の長寿命KVキャッシュの配置・再利用を改善する。Mosaicが対象とするのは拡散反復のたびに再生成される短寿命の活性値であり、問題となる状態の生存期間が違う。したがって、KVキャッシュを小さくする手法とMosaicは単純な代替関係ではない。

`torch.compile` を使う汎用のメモリ再利用は、演算グラフが部分ごとに分かれるとテンソルの生存期間をモデル全体で最適化できない。Mosaicは演算グラフ登録器で依存関係を明示し、分割演算を含めた全体の生存期間を先に決める。さらに一般的な固定分割と異なり、分割しないと実行できない長さに達した場合だけ、現在の最大活性値を作る演算を狙って分割する。仮想メモリ対応付けにより、要求長に応じた物理ページ確保と連続アドレス上での実行を両立させる点も特徴である。

## 限界

最大長評価は模擬入力であり、系列長を数十倍に伸ばしても言語モデルの文脈理解品質が維持されるとは示していない。論文の性能指標は最大系列長と拡散反復遅延であり、現実の長文書処理の正解率、同時配信要求数、端末環境での電力、複数GPUへの拡張を直接証明するものではない。利用者はメモリ上の実行可能性とモデル品質を別に検証する必要がある。

実装はvLLMの標準KVキャッシュ経路を使わず、独自の拡散推論処理とメモリ計画器、GPUカーネルを統合している。既存のvLLMを設定変更するだけで同等の改善が得られるわけではない。さらに、演算子の入力・出力依存関係を正確に登録し、出力先アドレスを指定できる実装が必要になるため、別モデルの演算構成に移植する場合にはグラフ登録と独自演算の対応が保守負担となる。

分割できない演算が最終的な最大値を決める場合には探索が実行不能を返す。また、短文脈では分割による起動費用が相対的に重いため、提案方式も分割を常時有効にしない。実験で使ったRTX 3090とA100以外のGPU、低帯域のホストオフロード、共有GPU環境では、演算分割の適正点と実際の速度利得を再計測する必要がある。

本論文のHTML一次資料では、Mosaic専用の公式公開コードURLを特定できなかったため `code: null` とした。これはコードが存在しないと断定する意味ではない。再現に当たっては、元のPyTorchモデル・vLLMの版、独自カーネル、仮想メモリAPI、分割探索の設定が必要であり、著者の実装が公開された場合は別途照合する必要がある。
