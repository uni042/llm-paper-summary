# FlashPrefill：長文脈の注意ブロック探索を高速化する適応型疎プリフィル

## 概要

FlashPrefillは、長文脈の大規模言語モデル（LLM）が入力全体を一度に処理するプリフィル段階を高速化する、動的な疎注意（sparse attention）の方式である。自己注意の計算は文脈長Lに対して原則O(L²)で増大し、256Kのような長い入力では注意演算子が大きな時間を占める。疎注意は重要なキー・クエリの組だけを計算して演算量を削減するが、重要な組を探すために密なスコア行列を作ったり、上位ブロックをソートしたりすれば、その探索費用が節約分を相殺する。短い4K～16Kの文脈で既存の動的疎注意が密注意より遅くなる場合があるのは、この前処理が無視できないためである。

本研究は、重要ブロックの探索そのものを高速化する。キーをブロックごとに平均し、クエリのタイルとブロック代表値の積から重要度を近似する。クエリ方向の最大値・指数和・正規化をGPU内の融合演算で処理し、巨大な中間スコア行列を主記憶へ書き戻さない。縦方向に共通する重要キー、因果的な斜線に沿う近傍キー、散在する高重要度のブロックを一つの探索経路で見つける。その後、最大スコアに比例する動的しきい値を用いて、ソートや累積和を行わずに重要度の低い長い裾を除外する。

原著のQwen3-30B-A3B-Instruct-2507を用いた注意演算子比較では、密なFlashAttentionに対して4Kで1.71倍、256Kで27.78倍の高速化を報告する。ただしこれは**注意演算子単体**の倍率であり、vLLMへ統合した先頭トークン遅延（Time To First Token、TTFT）の最大改善は7.22倍である。両者を同じ指標として扱ってはいけない。また注意を近似しているため、評価課題によっては完全注意より精度が下がる。品質を維持しつつ探索費用を抑えられる条件と、削りすぎて失敗する条件を分けて理解する必要がある。

この方式は、長文脈プリフィルにおける注意計算を対象とする。KVキャッシュの保存形式や重みの量子化、自己回帰デコードで一トークンずつ進む段階の演算を直接高速化するものではない。GPUの注意カーネルを置き換える推論基盤技術であり、入力長、注意パターン、モデル、実装バックエンドによって効果が変わる。

## 問題設定と設計方針

完全注意では各クエリが過去の全キーに対応するスコアを計算する。系列が長くなると、注意スコアの演算と中間データの読み書きが二次的に増える。長文脈では順伝播ネットワークやMoEの演算を効率化しても、注意がプリフィル時間の支配的な部分になり得る。固定の局所窓だけを残せば計算量は減るが、遠方にある重要な情報を見落としやすい。逆に入力ごとに重要ブロックを探索すれば精度を保ちやすいが、探索の費用が大きい。

既存の動的疎注意は、粗い注意スコアを求めた後に上位k個を選ぶ方式、または上位の累積確率が一定になるまで残す方式を用いる。上位k個の選択ではソートや選択演算が必要で、累積確率方式ではさらに累積和が必要となる。注意分布が長い裾を持つと、重要度の低いブロックまで固定数や確率質量の条件を満たすために残すことがある。結果として探索費用が高いのに疎性が不十分という二重の問題が生じる。

FlashPrefillは、注意の構造が入力ごとに変化することを前提に、縦縞、斜線、局所的なブロック集中という三種類の代表的パターンを統一して検出する。縦縞は多数のクエリが同じ重要キーへ注目する現象、斜線は近傍の相対位置へ注意が集中する現象、ブロック集中は離れた領域に重要度が局在する現象である。均等に配置したクエリ位置を観察すればこれらの大域構造を推定しやすいが、実装ではクエリをタイル化してまとめて処理し、平均化したキーとの積を融合縮約することで探索を高速化する。

## 手法

### キーのブロック平均による重要度近似

キー系列を一定長のブロックへ分割し、ブロック内のキーを平均して代表ベクトルを作る。あるクエリqと代表キーの内積を指数変換した値は、元の各キーとの指数スコアの幾何平均に相当する。真のブロック寄与は指数スコアの算術平均に比例するため、両者は一般には等しくない。原著はブロック内の分散が小さい条件では相対順位が概ね保たれることを根拠として、平均キーを重要度の代理値に用いる。幾何平均と算術平均の不等式から、代理値は対応する平均値を超えないが、分散が大きいブロックでは順位が変わり得る。したがってこの近似は厳密な注意計算の置換ではなく、重要候補を高速に絞るための近似である。

クエリの一部だけを間引いて全キーと比較する素朴な方式は、サンプル位置を外すと重要領域を見落とす。FlashPrefillはキーを平均化したうえでクエリ側をタイルとして処理し、タイル内のスコアを縮約する。これにより局所的な特徴をまとめて扱い、全クエリと全キーの密な組合せを計算する費用を避ける。探索結果は各クエリブロックとキーブロックの重要度に集約され、後段の疎注意カーネルへ渡される。

### 融合二次元縮約による中間メモリ削減

キーだけをブロック平均しても、各クエリと全キーブロックのスコアを一度主記憶へ保存すると、長さL、ブロック幅Bに対してO(L²/B)の大きな中間行列が発生する。FlashPrefillはこの行列を明示的に作らず、クエリタイルと平均キーブロックの積をGPUの高速な内部メモリで処理する。クエリ軸で最大値を求め、最大値を差し引いた指数和を同じ演算経路で計算する。原著式(1)・(2)はこの局所最大値と局所指数和を定義している。

異なるキーブロックのスコアを比較するには、局所最大値だけで正規化した値をそのまま使えない。そこで各クエリタイルについて全キーブロック間の最大値を取り、局所指数和を共通の尺度へ再調整してから、ブロック重要度の確率に相当する値を得る。原著式(3)・(4)の処理であり、数値の安定性を保ちながら比較可能なスコアへ変換する。必要な中間メモリをブロック対の数に抑えるため、長文脈でも探索が主記憶帯域を過度に消費しない。

### 最大値に基づく動的しきい値

各クエリブロックIに対して、キーブロックJの重要度をScore(I,J)とする。FlashPrefillは、各行の最大スコアに係数αを掛けた値をしきい値とし、`Score(I,J) < α × max_J Score(I,J)`を満たすブロックを削除する。上位k個のように残存数を固定せず、上位確率質量のようにソートと累積和を行わない。最大値の縮約と比較だけで選択できるため、GPU上で並列処理しやすい。

強い注意が少数のキーへ集中するクエリでは多くのブロックを削り、重要度が広く分散するクエリでは比較的多く残る。このため実際の疎性は層、注意ヘッド、入力、クエリ位置ごとに変わる。係数αを大きくすると疎性が高まる一方、中程度のスコアを持つ重要ブロックを失う危険も増える。原著の改善は、適応的なしきい値が品質と演算削減の妥協点を作れるという経験的結果であり、全入力で同じ品質を保証するものではない。

### 選択したブロックだけを計算する注意カーネル

探索で得たブロック位置を、後段の疎注意演算へ直接渡す。全ブロックを順番に訪問して不要なものを条件分岐で飛ばす方式では、削除したブロックについても位置計算や分岐の費用が残る。選択済みの位置へ直接アクセスすれば、残したブロックだけでクエリとキーの積、正規化、値との積を計算できる。探索、しきい値判定、実際の疎注意の合計時間が完全注意より短くなることが設計の目標である。

この実装はGPU上のタイル分割、内部メモリ容量、行列積演算、ブロック位置の参照方法に依存する。疎性が高い長文脈ほど有利だが、短い入力や小さいバッチでは探索固定費が目立つ可能性がある。原著は4Kでも完全注意より速い条件を示すが、全GPU、全モデル、全実装に一般化できるわけではない。

## 評価

### 比較条件と指標

中心となる演算子評価はQwen3-30B-A3B-Instruct-2507を用い、4K、8K、16K、32K、64K、128K、256Kの系列長を比較する。基準は密なFlashAttentionで、既存の動的疎注意方式や固定ブロック選択方式とも比較する。評価には、注意演算子の実行時間、探索と選択の内訳、vLLM統合時の先頭トークン遅延、長文脈課題の品質を使う。演算子単体の時間とモデル全体の応答時間は異なるため、数値を別表で扱う。

### 注意演算子の高速化（原著図3・図4）

| 文脈長 | 完全注意に対する演算子高速化 |
|---|---:|
| 4K | 1.71倍 |
| 8K | 2.79倍 |
| 16K | 4.48倍 |
| 32K | 6.94倍 |
| 64K | 11.45倍 |
| 128K | 18.67倍 |
| 256K | 27.78倍 |

32Kの代表的な演算子時間は完全注意約97.2ミリ秒に対しFlashPrefill約14.0ミリ秒、256Kでは約6044.1ミリ秒に対し約217.6ミリ秒である。文脈が長くなるほど完全注意の二次的な計算量が増えるため、重要ブロックだけを計算する方式との差が大きくなる。一方、4Kの1.71倍は、探索の固定費を抑えたことが短文脈でも効いているという主張に対応する。原著図4では、探索としきい値の時間が全体に占める割合も示される。

### vLLM統合の先頭トークン遅延（原著図2）

| 文脈長 | 先頭トークン遅延の高速化 |
|---|---:|
| 4K | 1.04倍 |
| 8K | 1.18倍 |
| 16K | 1.47倍 |
| 32K | 1.98倍 |
| 64K | 3.10倍 |
| 128K | 5.02倍 |
| 256K | 7.22倍 |

演算子で27.78倍でも、モデル全体では7.22倍にとどまる。埋め込み、順伝播ネットワーク、MoE、正規化、スケジューリングなど注意以外の時間が残るためである。4Kでは演算子が1.71倍でも先頭トークン遅延は1.04倍にすぎない。この差は、注意演算子だけを最適化してもシステム全体の速度改善には限界があることを示す。プリフィル高速化を報告するときは、必ず演算子かエンドツーエンドかを明示する必要がある。

### 探索方式の比較と疎注意カーネル（原著表1・表2）

原著表1はLlama-3.1-8B-Instructを用い、各方式で上位8ブロックを選ぶ条件を揃え、RULERの品質と探索時間を比較する。4Kで、クエリとキーの両方を平均する単純方式の品質指標は63.12、探索時間0.20ミリ秒、厳密なクエリを用いる方式は87.69・0.68ミリ秒、提案する融合ブロック近似は93.12・0.22ミリ秒である。64Kではそれぞれ24.32・0.63ミリ秒、73.26・18.26ミリ秒、76.08・2.21ミリ秒となる。提案方式は単純平均より品質を維持しつつ、厳密計算より探索を高速化している。

疎注意カーネル単体の比較では、残存密度60%の4Kで既存方式1.27ミリ秒に対し提案方式0.72ミリ秒、512Kで14990.36ミリ秒に対し11256.11ミリ秒である。密度6%では4Kで0.43対0.14ミリ秒、512Kで1513.66対1109.44ミリ秒となる。これは探索法だけでなく、選択ブロックへ直接アクセスするカーネル側にも利得があることを示す。ただしこれらは密度を固定した演算子比較であり、実運用時の動的なしきい値が常にその密度を実現するという意味ではない。

### 品質と負の結果

針探し評価では、Qwen3の長文脈で完全注意に近い検索挙動を示す。RULERやInfiniteBenchでも複数モデルを比較するが、完全注意と常に同一精度ではない。原著のInfiniteBenchではLlama-3.1系の平均が完全注意48.39に対してFlashPrefill46.32、Qwen3系が37.83に対して36.23へ下がる一方、Qwen2.5系は23.87に対して24.93へ上がる。評価課題によって得失があり、全タスクで無損失と断定することはできない。注意の分布が広く、多数の中程度のブロックが寄与する課題では、しきい値による削除が品質に影響する可能性がある。

## 既存研究との差

固定の局所窓や固定ブロック方式は探索費用が小さい一方、遠方の重要キーを取り逃がしやすい。既存の動的疎注意は重要ブロックを探せるが、探索用の粗い注意スコアの生成、ソート、累積和が短文脈では負担になる。FlashPrefillは、ブロック平均、融合二次元縮約、最大値に比例するしきい値、選択済み位置だけを計算するカーネルを一つの経路にまとめる。疎注意の「何を残すか」だけでなく、**残すブロックを決めるまでの費用**を削減することが主要な新規性である。

同じ疎性を固定する方式とも異なり、クエリごとのスコア分布に応じて残すブロック数を変える。重要度が集中するクエリでは強く削り、分散するクエリでは広く残すため、入力に応じた計算予算の配分となる。反面、係数αの調整が必要で、分布の変化に対する品質保証はない。

## 限界・負の結果

第一に、FlashPrefillは近似疎注意であり、削除したブロックの情報は後段の計算へ戻らない。平均キーによる代理スコアはブロック内の分散が大きいと順位を誤る可能性があり、最大値に比例するしきい値は中程度の重要度を持つ多数のキーをまとめて削除する危険がある。InfiniteBenchの一部モデルで平均スコアが下がる結果は、品質の損失が実際に起こり得ることを示す。

第二に、係数α、ブロック幅、クエリタイル、注意ヘッドの分布に性能が依存する。入力長が短い場合やGPUの行列積効率が異なる場合、探索の固定費が節約分を上回る可能性がある。原著の4Kでの1.71倍は特定のモデルと演算子環境の結果であり、全モデルの短文脈で同じ改善が得られる保証ではない。

第三に、演算子27.78倍とvLLM全体7.22倍は異なる指標である。前者をLLM全体の生成速度として引用すると過大評価になる。実際のサービスでは、同時要求数、KVキャッシュ管理、MoEの専門家配置、通信、スケジューラなどが性能を左右する。特にプリフィル以外の自己回帰デコードでは、同じ倍率を期待できない。

第四に、実装はGPU上の融合縮約と疎注意カーネルに依存する。別のGPU世代、異なるタイル形状、CPUや他の推論バックエンドへ移植した場合は、探索と演算のバランスを再測定する必要がある。モデルの品質維持も、長文脈検索・推論・マルチモーダル課題で別々に確認する必要がある。
