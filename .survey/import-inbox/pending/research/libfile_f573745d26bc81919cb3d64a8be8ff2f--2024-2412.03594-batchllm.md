# BatchLLM: Optimizing Large Batched LLM Inference with Global Prefix Sharing and Throughput-oriented Token Batching

## 概要
vLLMやSGLangは到着が逐次的なonline servingを主対象にし、共有prefixのKVをLRU系cacheで再利用する。一方、検索snippet生成やoffline rankingのようなlarge-batch処理では全request集合を実行前に把握でき、同じsystem promptやdocument prefixを多数requestが共有する。BatchLLMはこの「未来のrequestまで見える」条件を利用し、cache hitを受動的に待つのではなく共有prefixを大域的に確定してscheduleする。

システムは、共有prefixの明示抽出、throughput指向token batching、prefix共有attention kernelの水平融合という三段で構成される。microbenchmarkとindustry workloadでvLLM/SGLang比1.3〜10.8倍のend-to-end改善を報告し、特に共有度が高い長prefixで差が大きい。

## 問題設定
LRU cacheでは将来再利用されるKVでも、間に別requestが入れば退避され得る。large batchでは全requestが既知なので、本来は同じprefixを使うrequestを連続実行し、prefix KVを最後の利用まで保持してから即解放できる。またprefill中心の時間帯とdecode中心の時間帯が分離するとGPU利用率に谷が生じる。online向けschedulerは全batchの長さ情報を使わないため、この谷を積極的に埋めない。

共有prefixが多階層になると、そのまま全treeをcache管理するのはmetadataとkernel分岐が複雑になる。BatchLLMは再利用token数を保ちながら扱いやすいfirst-level prefixへ変換し、system全体を単純化する。

## 手法
### 大域prefix抽出と拡大
全promptからcompact prefix treeを作る。動的計画法で各nodeを評価し、複数階層の共有関係を、再利用token数が大きくなる単一のfirst-level shared prefixへまとめる。計算量はtree node数n、平均child数cに対してO(n c^2)で、論文のlarge workloadではprefix identification overheadは全実行時間の0.01%未満とされる。

### prefix group単位の寿命管理
同じprefixを共有するrequestをgroup化し、shared KVを一度だけ計算する。group内の最後のrequestが終わるまでKVを保持し、その時点で解放する。LRUのように再利用予定を知らずevictすることがないため、既知batchではcache hitを最大化できる。

### throughput指向token batching
schedulerはdecode queue、distinct prompt queue、common prefix queueを使い、GPUを満たすtoken batchを作る。request groupを`decode length / prefill length`の比率で並べ替え、decode比率が大きいgroupを先に進めることで、後続prefill chunkとdecode tokenを混ぜやすくする。request数ではなく利用可能memoryを基準にtoken batchを拡大し、GPU occupancyの谷を抑える。

### 水平融合prefix-shared attention
shared KVとrequest固有KVを別kernelで処理して後段で結合すると、large batchの短い処理単位でlaunch overheadとtail effectが増える。BatchLLMは両attentionを一つのTriton kernelへ水平融合し、同一launch内で処理する。hardwareごとにtile設定をauto-tuneする。

## 評価条件
|項目|内容|
|---|---|
|比較engine|vLLM、SGLang|
|GPU|NVIDIA A100、AMD MI200を含む|
|workload|共有prefixを変えるmicrobenchmark、検索系industry workload|
|モデル例|Qwen-2.5-7B等|
|主要変数|prefix長、sharing degree、prefill/decode長、batch規模|
|指標|throughput、token saving ratio、GPU utilization、end-to-end time|

## 主要結果
全体としてvLLM/SGLang比1.3〜10.8倍を報告する。16K tokenの共有prefixを16 requestで共有する高再利用条件ではvLLM比10.8倍となり、明示prefix管理によるtoken saving ratioは92.6%に達する一方、vLLMの受動cacheでは6.3%に留まる例が示される。

A100では代表的条件でvLLM比1.4〜3倍、SGLang比1.2〜2.5倍、MI200ではvLLM比最大4.1倍の改善が報告される。実業務のsnippet generationでもQwen-2.5-7Bでthroughput約30%改善を示し、prefix treeのfirst-level化が共有tokenの55%を捕捉して理論上限に一致する事例がある。

## 既存研究との差
PagedAttention系はmemory fragmentationを抑え、prefix cacheは過去requestとの再利用を可能にするが、未来のbatch全体は見ない。BatchLLMはoffline/large-batchという条件を明示的に利用し、prefixの発見、request順序、KV寿命、attention kernelを同じglobal planに結び付ける。したがってonline latency最適化とは目的関数が異なる。

## 限界
全request集合を事前に把握できることが大きな前提で、到着が未知なinteractive servingではglobal reorderをそのまま使えない。共有prefixが少ないworkloadでは主要な再利用利得が縮む。decode長推定が外れると比率順序の効果も低下する。また専用Triton kernelはhardware shapeへのauto-tuningが必要である。
