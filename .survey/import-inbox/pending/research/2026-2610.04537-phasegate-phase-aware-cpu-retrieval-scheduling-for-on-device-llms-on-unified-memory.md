# PhaseGate: Phase-Aware CPU Retrieval Scheduling for On-Device LLMs on Unified Memory

> 統合メモリ上でデコードが検索の干渉に弱いことを測り、プリフィルとデコードでCPU検索の同時実行上限を切り替えることで、遅延を守りながら検索処理量を2倍にした受付制御の研究。

## 概要

端末上の助手は、言語モデルの推論だけを動かすわけではない。文脈の検索、索引の保守、文書の解析、道具の実行がCPUで並行して走る。分離型のサーバーではCPU側のメモリとGPU側の高速メモリが別だが、アップルシリコンでは両者が同じメモリの池を共有するため、CPUの検索がたどる不規則な読みと、GPUが重みを流し読む処理が、メモリの応答を奪い合う。本論文はまず、この干渉が推論の段階で非対称であることを測った。検索の作業員を4件同時に動かすと、最初のトークンまでの時間は5.7パーセント増えるだけだが、出力トークンあたりの時間の95パーセント点は61パーセント増えた。プリフィルは入力をまとめて処理し重みの読みを使い回せるのに対し、デコードは1トークンごとに重み全体を流し読むため、帯域の奪い合いに弱い。提案する受付制御は、この段階を検索の受付の合図として使い、段階ごとに同時実行の上限を変える。代表結果として、基準構成では上限をプリフィル4件、デコード1件とし、遅延条件を満たす最良の固定方針の2.0倍の検索処理量を得た。

## 問題設定

通常の検索側の受け付けは、推論の開始から終了まで1つの上限を使う。しかし上限を1件にすると遅延は守れるが検索が進まず、2件にすると検索は進むが出力側の遅延条件を破る。つまり、固定の上限では、プリフィルの余裕とデコードの弱さの両方に同時には合わせられない。問題は帯域の総量ではなく、時間で変わる弱さに対して受付を合わせられるかにある。先行する帯域調整の研究はCPUの通信量そのものを絞り、計算の分割の研究はプリフィルをCPUとGPUへ分ける。本論文の対象は異なり、言語モデルの実行はGPUに置いたまま、独立したCPU検索をいつ何件まで受け付けるかだけを制御する。実行中の検索を途中で止めることはせず、境界をまたいで続く作業があるため、制御は受付の時点で効き、効果には移行の費用も含まれる。この条件の下で、段階という合図に本当に価値があるかを、時刻だけで同じ上限を切り替える対照と比較して切り分けることが、評価の中心になる。

## 手法のあらまし

流れは、調整、実行時、評価の3つでできている。調整では、段階ごとに同時実行数を変えて遅延を測り、検索なしの基準に対する上限、論文では1.25倍を条件として、段階ごとの上限の組を選ぶ。実行時には、現在の段階を見て、その上限までだけ新しい検索を受け付ける。実行中の検索は止めない。評価では、待ち行列が滞留した状態で検索の総処理量を測り、両方の遅延指標が条件を満たすかを見る。入力は段階の合図と調整済みの上限の組であり、出力は検索の処理量と遅延の釣り合いである。

## 手法

### 1. 段階ごとの同時実行上限 — 弱い時間帯だけを絞る

観測対象は、現在がプリフィルかデコードかという段階と、各段階での遅延の増え方である。保持する状態は段階ごとの上限の組だけであり、基準構成ではプリフィル4件、デコード1件が選ばれた。選択されるのは、新しい検索を受け付けるかどうかであり、処理は上限に達していれば待たせ、段階が変われば上限も変わる。これで減るボトルネックは、デコード中のメモリの奪い合いであり、プリフィルの余裕の時間に検索を進めることで、総処理量を戻す。追加で消費するのは調整の測定であり、上限の組は機器ごとに違うため、配備先ごとに測り直す必要がある。失敗条件は、段階の切り替わりをまたぐ長い検索であり、受付後に始まったデコードは、その検索が終わるまで干渉を受ける。論文はこの非割り込みの費用も実験で分けて測っている。

### 2. 調整の手順 — 遅延条件から上限を決める

上限は推測ではなく測定で決める。同時実行数を変えながら、最初のトークンまでの時間と出力トークンあたりの時間の95パーセント点を測り、検索なしの基準の1.25倍以内という条件を満たす最大の組を選ぶ。関係は単調とは限らず、付録では非単調な振る舞いも含めて調整の詳細が示される。この手順が効く理由は、干渉の強さが機器の冷却や構成で変わるため、式ではなく実測で境界を引くほうが確実だからである。逆に、調整は配備条件への依存を生み、背景の競合が変われば上限は古くなる。論文は、上限を状況に応じて自動で直す仕組みは評価しておらず、今後の課題として残している。

### 3. 段階を見ない対照による切り分け — 時刻ではなく段階が効くことの確認

提案法の価値が、単に上限を時間で変えたことにあるのか、段階に合わせたことにあるのかを分けるため、同じ2つの上限を調整から決めた予定で切り替え、段階を見ない対照が用意された。この対照は検索の処理量では提案法に近いが、出力側の遅延条件をすべての実行で破った。つまり、切り替えの平均的な量ではなく、切り替えの位相、つまり弱い時間帯に絞ることが効いている。この対照があることで、段階の合図そのものが制御の情報として価値を持つことが、相関ではなく比較として示される。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 段階ごとの上限 | 現在の段階と遅延の測定 | プリフィルで緩め、デコードで絞る | デコード中の帯域の奪い合い | 機器ごとの調整が必要 |
| 調整の手順 | 同時実行数を変えた遅延測定 | 条件を満たす最大の上限の組を選ぶ | 上限の根拠 | 背景競合の変化に弱い |
| 非割り込みの受付 | 実行中の検索 | 途中で止めず、新規の受付だけを絞る | 実装の単純さ | 境界をまたぐ作業の干渉は残る |

## 評価

### まず見るところ

- **結論:** 段階に合わせた受付は、遅延条件を守る固定方針より検索を2倍進められ、段階を見ない切り替えでは同じことができない。段階は受付の合図として使える。
- **速度・効率:** 改善は検索側の処理量であり、言語モデル自体が速くなるわけではない。遅延は条件内に収める側の量として扱われる。
- **品質:** 無損失である。生成の内容は変えず、遅延と処理量だけが議論の対象である。
- **評価の強さ／注意点:** 対照実験と別機器での再現があり、出力長や検索需要の間欠性も変えている。一方でモデルは1件、入力長も固定であり、自然な生成文での検証はない。

**数値の読み方。** 2.0倍は、条件を満たす固定方針の中の最良との比較である。条件を破る固定方針なら検索はもっと進むが、それは遅延を犠牲にした比較になる。また、出力が長くなってデコードの割合が増えると、プリフィルの余裕が減るため、利得は狭まることが出力長の実験で示されている。

## 既存研究との差

段階を分けるサービングの研究は、プリフィルとデコードを別の資源へ分けることで推論自体を最適化する。帯域調整の研究は、GPU実行中のCPUの通信量を予算で絞る。プリフィルをCPUとGPUへ分ける研究は、計算の置き場所を変える。本論文の差分は、言語モデルの実行には触れず、独立したCPU検索の受付だけを段階で制御する点と、その前提になる干渉の非対称を実測し、段階を見ない対照で合図の価値まで切り分けた点にある。

## 限界・実装状況

評価は1件の小型モデルと固定した入力長が中心であり、より大きなモデルや長い文脈、自然な生成文での挙動は示されていない。検索は読み取り専用の近傍探索であり、書き込みを伴う索引保守や、長い非割り込みの道具実行は対象外である。上限の組は機器ごとに調整が必要で、背景の競合が変わったときに自動で直す仕組みはない。冷却の違いやページングの影響を完全には分離できていないことも論文が認める。コードと実験の手順と結果は公開されている。

## 一般的な実装上の含意

共有資源の受付制御では、平均の負荷ではなく、最も弱い時間帯に合わせて絞り、余裕のある時間帯で進める設計が効く。そのためには、まず干渉が時間でどう変わるかを測ることが先であり、合図の価値は、合図を見ない対照と比較して初めて確かめられる。端末上の並行作業では、推論の段階のような安く得られる合図が、帯域の細かい計測なしでも制御に使える場合がある。
