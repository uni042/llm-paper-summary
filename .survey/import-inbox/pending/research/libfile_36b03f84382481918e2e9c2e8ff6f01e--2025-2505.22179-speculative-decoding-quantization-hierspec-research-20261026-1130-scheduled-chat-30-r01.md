# Speculative Decoding Meets Quantization：量子化と投機的デコードの干渉を避ける階層検証

## 概要

投機的デコードと量子化は、どちらもLLMの生成を高速化する代表的な方法である。量子化はモデル重みのメモリ転送量を減らし、投機的デコードは小型のドラフトモデルが予測した複数トークンを大きなモデルでまとめて検証することで、ターゲット重みを読み込む回数を減らす。しかし、両者を単純に組み合わせると、期待した高速化が得られないことがある。特に4ビット重み量子化されたモデルでは、木状の複数候補をまとめて検証する計算負荷が、量子化によって短くなった単一トークン生成時間に対して大きくなる。

本論文は、EAGLE-2と複数の量子化方式をC/CUDAの最適化実装で組み合わせ、ドラフト生成・受理長・検証費用を分解して原因を調べる。その結果、4ビット重みのターゲットモデルでは、木状ドラフトを大きなモデルへ直接検証させることが律速になると示す。これを解決するため、EAGLE-2が生成した木状候補を8B中間モデルで検証し、残った候補を系列ドラフトとして70Bターゲットへ渡す階層方式HierSpecを提案する。

W4A16のLlama-3-70Bを単一A100 80GBで動かしたSpecBenchの六種類の生成タスクでは、HierSpecの最良構成が平均98.19トークン/秒を達成した。これは同じW4A16モデルの通常の自己回帰生成比で2.78倍、最良のEAGLE-2比で1.31倍、通常の小型モデル投機的デコード比で1.21倍である。ただし、これは特定の70Bモデルと量子化カーネルでの実測であり、全ての4ビットモデルやGPUに同じ倍率を保証しない。

## 問題設定

自己回帰デコードでは、次のトークンを一つ生成するたびにターゲットモデルの重みを参照する。バッチが小さい場合、計算能力よりもメモリ帯域がボトルネックになりやすい。投機的デコードは、軽量モデルが複数トークンを先読みし、ターゲットモデルがまとめて検証する。候補が受理されれば、一回のターゲット実行で複数トークンを確定できる。量子化は、重みを低ビットにして読み込み量を減らすことで、ターゲットの単一トークン実行を短縮する。

一見すると二つの最適化は独立であり、単純に効果を掛け合わせられそうに見える。しかし投機的デコードは、ドラフトの生成費用と複数候補の検証費用を追加する。量子化によってターゲットの通常デコードが高速になるほど、この追加費用が相対的に重くなる。特にEAGLE-2は枝分かれした木状候補を作るため、ターゲットは一度の検証で多数の候補トークンを処理する。量子化済みの小さな行列演算は帯域を節約できても、木状候補をまとめて処理する演算量まで同じ比率で減るわけではない。

著者らはこの相互作用を調べるため、EAGLE-2とFP16、W8A8、W4A16、W4A8の複数量子化方式を組み合わせる。W8A8は8ビットの重みと活性化、W4A16は4ビット重みと16ビット活性化、W4A8は4ビット重みと8ビット活性化を意味する。量子化によるモデル品質の変化もあるため、速度だけでなくWikiText2のPPL、GSM8K、HumanEvalを測定している。

## 手法

### 1. 投機的デコードの時間分解

EAGLE-2では、軽量ドラフトモデルが木状の候補を生成し、ターゲットモデルがその木をまとめて検証する。ドラフト深さをd、木の候補数をn、期待受理長をτ(n,d)、ドラフトモデルの一回の生成時間をTd、ターゲットの単一トークン生成時間をTt、n候補をまとめて検証する時間をTv(n)とする。原著式(1)は、投機的デコードの一トークン当たり時間を、ドラフト費用d×Tdと検証費用Tv(n)の和を受理長τで割ったものとして表す。

この式から、受理長が大きくてもドラフトや検証が重ければ高速化しないことが分かる。良い投機的デコードには、受理長が十分長いこと、ドラフト生成がターゲットより軽いこと、そして複数候補の検証が単一トークン生成に比べて過度に高価でないことが必要である。量子化はTtを短縮するが、木状検証Tv(n)の計算費用は必ずしも同じ比率で短くならない。この非対称性が本研究の主要な着眼点である。

### 2. 量子化方式ごとの互換性を実測

著者らはLlama-3-8BとLlama-3-70Bを対象に、EAGLE-2を異なる精度のターゲットへ適用した。W8A8にはSmoothQuant、W4A16にはグループサイズ128のGPTQ、W4A8にはQoQやQQQの複数設定を利用する。W4A16の高速化にはMarlin系の量子化カーネルを使う。Python側のオーバーヘッドで比較が歪まないよう、EAGLE-2と量子化演算をネイティブC/CUDAへ統合して測定した。

EAGLE-2のドラフトモデルを安易に低ビット化すると受理率が下がるため、原著の互換性実験ではドラフト側をFP16に保つ条件を使う。これはターゲットだけを量子化した場合の追加費用を調べるための設計である。FP16のターゲットで速いEAGLE-2設定が、W4A16やW4A8でも最速とは限らない。木の候補数を増やせば受理長は増えるが、4ビットターゲットでは検証時間の増加が勝つ場合がある。

原著Figure 2・3では、木の候補数を変えながら受理長、検証時間と通常デコード時間の比、実際の高速化率を比較する。4ビット重みでは候補数を減らした方が速くなる条件があり、単に受理長を最大化する設計が不適切だと分かる。特に70BのW4A16では、系列状の候補を8Bモデルで作ってターゲットに検証させる通常の投機的デコードが、木状EAGLE-2を上回る条件がある。これは木状候補の検証負荷が主因であることを示す重要な比較である。

### 3. HierSpecの階層的な検証

HierSpecは、軽量ドラフト、8B中間モデル、70Bターゲットの三段階に分ける。第一段階ではEAGLE-2の軽量ドラフト機構が木状候補を作る。第二段階ではW4A16のLlama-3-8B中間モデルがその木を検証し、受理された経路を系列ドラフトへ変換する。第三段階ではW4A16のLlama-3-70Bターゲットが、系列ドラフトをまとめて検証する。大きなターゲットに木の全候補を直接渡さないことが本質である。

8B中間モデルは70Bターゲットより小さいため、木状検証に必要な計算を比較的低い費用で実行できる。中間モデルが木の枝を絞り、70Bターゲットには連続した系列として渡すことで、70B側では木状検証の追加計算を避けやすい。通常の系列ドラフト方式では8Bモデルが長い系列を一つずつ生成する必要があるが、HierSpecではその8Bモデル自体をEAGLE-2で投機的に進める。すなわち、木状ドラフトの効率を小型モデル側で使い、量子化された大きなモデル側では系列検証の低い計算負荷を使う。

二段階のドラフト長は独立のパラメータである。第一階層のEAGLE-2深さd1は3または4、最終ターゲットへ渡す系列ドラフト長dは6または7などを比較する。d1が大きいほど8B側の受理候補は増える可能性があるが、8B側の木状検証が長くなる。dが大きいほど70Bターゲットの検証一回で多くのトークンを受理できる可能性があるが、受理率が下がると無駄な検証が増える。両者の最適値は独立ではなく、ドラフト費用と受理長のバランスで決まる。

### 4. 速度とモデル品質の関係

投機的デコードは、ターゲットが検証する候補を採用するため、適切に実装すればターゲットの生成分布を維持できる。一方、ターゲットをFP16から4ビットへ量子化した時点で、元モデルの分布と精度は変化し得る。したがって、HierSpecの速度改善をFP16モデルの品質維持と同義にしてはいけない。原著Table 1ではW4A16のGPTQでもWikiText2のPPL悪化やGSM8K・HumanEvalの低下があり、回転を加えた量子化構成で改善する条件も示される。

例えばLlama-3-70BではFP16のWikiText2 PPLが5.32、GSM8Kが91.05、HumanEvalが78.65である。W4A16のGPTQ-g128ではそれぞれ5.86、89.31、75.00となり、GPTQ-g128+Rotでは5.89、90.22、76.22となる。速度の評価は量子化後のターゲットを基準とするため、これらの品質差は別途判断する必要がある。FP16の70BとW4A16の70Bを混同すると、量子化による速度改善と投機的デコードによる改善を二重に数えてしまう。

## 評価

### 実験環境と比較対象

| 項目 | 条件 |
|---|---|
| 主要ターゲット | W4A16 Llama-3-70B-Instruct |
| 中間モデル | W4A16 Llama-3-8B-Instruct |
| GPU | NVIDIA A100 80GB×1 |
| 評価集合 | SpecBenchの機械翻訳、複数ターン会話、RAG、数学、QA、要約の六種類 |
| 比較 | 通常自己回帰生成、通常の系列投機的デコード、EAGLE-2、HierSpec |
| ドラフト条件 | 通常方式のd=6/7、EAGLE-2のd=3〜6、HierSpecのd1=3/4とd=6/7 |
| 指標 | 平均受理長、トークン毎秒、ドラフト初期化時間、検証時間 |
| 追加検証 | Llama-3.3-70BとEAGLE-3を含む付録実験 |

この評価は単一GPU上でのデコード速度であり、複数ユーザーを同時に処理するサービングの総スループットではない。六種類のタスクを同じ重みで平均した結果を中心に比較する。量子化方式の比較にはFP16、W8A8、W4A16、W4A8が含まれるが、HierSpecの主要結果はW4A16の70Bターゲットである。精度条件を揃えずに異なる図の倍率を直接比較してはならない。

### HierSpecの主結果

| 方法 | W4A16 Llama-3-70Bでの評価 |
|---|---|
| 通常自己回帰 | 速度倍率の基準1.00倍 |
| EAGLE-2 | HierSpec最良構成より平均速度が低い |
| 通常の系列投機的デコード | HierSpec最良構成より平均速度が低い |
| HierSpec、d1=3、d=6 | **平均98.19 tok/s、通常自己回帰比2.78倍** |

原著Table 2の最良構成は第一階層の深さ3、最終系列長6である。この設定は最良のEAGLE-2に対して1.31倍、最良の通常系列投機的デコードに対して1.21倍の速度である。最良構成の平均受理長は5.28トークンで、受理長だけが最大の設定を選んでいるわけではない。d1=3・d=7でも平均98.00 tok/sと近い値が得られる一方、d1=4の設定では91.14や93.06 tok/sへ低下する。候補を多く作ることが必ずしも速度向上につながらないことを示す。

Figure 5ではEAGLE-2の木状検証が重い一方、通常の系列投機的デコードではドラフト生成が重い。HierSpecは小型モデル側で木状検証を行うため、最終ターゲットの検証時間を通常の系列方式に近づけながら、ドラフト生成費用を抑える。著者らの説明では、通常系列方式のドラフト時間はEAGLE-2の約1.93倍、EAGLE-2の検証時間は通常系列方式の約1.53倍となる条件がある。これらの倍率は特定のドラフト長における内訳であり、全体速度倍率とは異なる。

### ドラフト初期化費用と短文への注意

原著Table 3では、ドラフトの初期化に要する時間がタスクごとに大きく異なる。六タスク平均は通常の系列投機的デコードで73.4ms、EAGLE-2で6.4ms、HierSpecで76.4msと報告される。HierSpecは中間モデルの準備を伴うため、EAGLE-2単独より初期化費用が大きい。著者らはこの費用が長い生成では多数のデコード反復へ分散されると説明する。

したがって、表の98.19 tok/sはドラフト初期化の費用を全て含んだ任意の短文要求の完了時間を表すものではない。短い回答しか生成しないワークロードでは、初期化費用の増加がデコード速度の改善を打ち消す可能性がある。実サービスへ適用する場合は、平均生成長、ドラフトモデルのロード状態、ターゲットと中間モデルのメモリ常駐条件を考慮して、TTFTとE2E遅延も測定する必要がある。

### EAGLE-3を使う追加評価

付録ではEAGLE-3との比較も行う。W4A16 Llama-3.3-70Bの通常自己回帰を基準とした場合、EAGLE-3の良い設定は平均92.70 tok/s、2.63倍であり、HierSpecのd1=3・d=6設定は平均100.12 tok/s、2.84倍となる。これはEAGLE-3が進んだ後でも、中間モデルを用いた系列化が有効な条件があることを示す。ただし、Llama-3.3系列に対応する8Bモデルがないため、HierSpec側はLlama-3.1-8Bを中間モデルに使っている。比較条件が完全に同じではないことを原著も明記している。

### 量子化と投機的デコードの相性

4ビット重みのW4A16やW4A8は、FP16やW8A8よりターゲットの単一トークン生成を短縮する。しかし、EAGLE-2で木の候補数を増やすと、ターゲット側の検証が計算律速へ寄りやすい。量子化によって通常生成が速くなった分、検証とドラフトの相対費用が上昇する。これは、投機的デコードと量子化の高速化を単純に乗算できない理由である。

原著は木の候補数を減らすと4ビットモデルの速度が改善する例を示すが、候補を減らしすぎれば受理長が短くなる。HierSpecはこのトレードオフを、木状検証を小型モデルへ移し、大きなモデルの検証を系列化することで緩和する。設計の利点は「投機的デコードを使うこと」自体ではなく、量子化後のボトルネックに合わせて、どのモデルへどの形の候補を検証させるかを変える点にある。

## 既存手法との差

EAGLE-2は軽量ドラフトモデルが木状候補を作り、ターゲットがまとめて検証する。高精度のターゲットでは重み転送を一回で複数トークンへ分散できるため有効だが、4ビットターゲットでは木状検証の計算量が目立つ。通常の系列投機的デコードはターゲットの検証を軽くできるが、小型モデルが系列を順に作る費用が大きい。HierSpecは木状生成を小型モデル側で使い、その出力を系列へ変換してターゲットへ渡すことで、両方式のボトルネックを分離する。

QSpec、QuantSpec、ML-SpecQDなどは量子化をドラフトとターゲットの関係に組み込むが、本論文の中心は4ビット量子化された大きなターゲットに対する木状検証費用の問題である。したがって、最も重要な比較は同じW4A16ターゲット上で、EAGLE-2と通常系列投機的デコードとHierSpecを比較することである。モデル精度やドラフト長を変えた実験の数字を混在させると、どの機構の効果か分からなくなる。

## 限界・負の結果・適用条件

第一に、最良の速度結果は単一A100 80GBでのW4A16 Llama-3-70BとSpecBench六タスクの組合せである。異なるGPU、バッチサイズ、長い文脈、複数同時要求、異なる量子化カーネルではボトルネックが変わる。RTX 4070 SUPER 12GBのようなGPUでは、70Bターゲットと8B中間モデルを同じ構成で常駐させること自体が難しく、今回の実測値を直接移植できない。

第二に、HierSpecは中間モデルの重みと状態を追加で必要とする。モデルのロード費用、KVキャッシュ、ドラフト初期化時間、追加メモリ占有を含めた総費用を評価する必要がある。原著のデコード速度が高くても、短い出力では初期化費用を回収できない場合がある。特にドラフト初期化の平均76.4msはEAGLE-2単独の6.4msより大きい。

第三に、量子化によるモデル品質の低下は別問題として残る。Llama-3-70BのW4A16 GPTQ-g128は、FP16よりWikiText2 PPL、GSM8K、HumanEvalで劣る。HierSpecは量子化で失われた情報を回復するものではなく、量子化されたターゲットの検証結果を効率よく得る方法である。精度と速度のトレードオフを検討する場合は、量子化方式の選択を別途評価する必要がある。

第四に、受理長だけを最大化する設計は危険である。木の候補数を増やすと検証計算が重くなり、4ビットターゲットでは速度が低下する条件がある。中間モデルの選択とドラフト長の最適値もモデル規模やタスクで変わる。原著の最良設定d1=3、d=6を全環境の推奨値として固定すべきではない。

第五に、付録のEAGLE-3比較では中間モデルの系列がターゲットと異なる。論文が報告する2.84倍は、その条件での測定であって、全てのEAGLE-3実装に対する優位性を証明するものではない。実装の検証では、ドラフトの確率分布、受理判定、量子化誤差、乱数の扱いを確認し、ターゲット分布を意図せず変えていないことを検証する必要がある。
