# Green AI：コード補完LLMの入力・出力長と量子化がGPU推論エネルギーに与える影響

## 概要

コード補完のためにLLMをローカル実行する場合、モデルの正答率や生成速度だけでなく、入力文脈を処理するためのGPUエネルギーと、出力を逐次生成するためのGPUエネルギーを分けて評価する必要がある。リポジトリ全体から関連コードを集めて次の1行を補完する要求と、コードの途中に数百行を挿入する要求では、同じLLMでも計算の支配項が変わる。前者は長いprefillが中心であり、後者はdecodeで多数の出力トークンを生成する。

本論文は、25種類のオープンウェイトLLMをOllama上で動かし、コード補完の品質とGPU推論エネルギーを比較した実証研究である。RepoBenchでは2K～32Kトークンのリポジトリ文脈を与え、最大128トークンの次行補完を行う。McEvalではPython・Java・RustのFill-in-the-Middle（FIM）を入力約2Kトークン、最大1,300出力トークンで実行する。実験はA100 PCIe 80GB単基で実施し、GPU電力を100ms間隔で記録した。

主結果は、**長文脈の次行補完では入力長とモデル規模が重要で、長いコード生成では出力長とモデル規模が重要**という、ワークロード依存のエネルギー構造である。量子化モデル、とくにQ4は同一モデル系のFP16に比べて省エネルギーな傾向があり、品質とエネルギーのPareto前線へ頻繁に現れる。一方、最大モデル・最大コンテキストが必ずしも最良の補完品質をもたらさない。

この研究は新しい推論カーネルやスケジューラを提案したものではない。推論基盤の選定・量子化・プロンプト設計の費用を測定し、実装判断に使えるエネルギー上の経験則を示す。数値はNVMLによる**GPUのみの電力推定**であり、システム全体の電力量やCO2排出量を測ったものではない。

## 問題設定：コード補完には二つの計算形態がある

左から右へ生成するL2R補完は、リポジトリの別ファイル・関数・依存関係を参照して次の行を予測する。多くの入力トークンをprefillする一方、必要な出力は短い。入力が長くなると注意演算の計算量、KVキャッシュ容量、メモリ転送が増える。大きいモデルほど同じ入力長でも重み演算・データ転送が増えるため、単純に入力トークン数だけで費用を説明できない。

FIM補完は、前後のコード断片を与えて欠落した関数・文を埋める。入力は比較的短くても、生成するコードが長ければdecode反復が増える。各反復ではモデル重みとKVキャッシュを参照しながら次トークンを生成するので、出力トークン数と有効パラメータ数の組合せが効いてくる。両ワークロードを同じ平均J/tokenで比較すると、長文脈のprefill費用を短い出力トークン数で割ることになり、指標の解釈を誤る。

論文は次の問いを分ける。(1) モデル・言語・コンテキスト長によって、品質とエネルギーのPareto最適な組合せはどう変わるか。(2) 入力トークン、出力トークン、有効パラメータ数、量子化ビット幅のうち、エネルギーを強く説明する要因は何か。特にMoEでは総パラメータ数とトークンあたりに活性化するパラメータ数が異なるため、回帰では後者を用いる。

## 手法

### 1. OllamaとNVMLによるGPU電力量の推定

実行エンジンはOllama v0.13.0で、オープンウェイトのGGUFモデルをFP16、Q8、Q4などの形式で評価した。Ollamaを選んだ理由はローカル実行と複数量子化形式の取扱いが容易なことであり、他のエンジンより性能が優れていると実証したわけではない。実行ハードウェアはNVIDIA A100 80GB PCIe GPU、AMD 7313 CPU×2、RAM 1TB、AlmaLinux 8.10である。GPUに他のジョブを載せず、CPU governorをPerformanceへ固定して測定した。

GPU電力はNVMLのPythonバインディング`nvidia-ml-py 13.590.48`で**100msごとにサンプリング**した。GPUアイドル電力を340秒間、3,400点測って平均46.82Wとし、実行中の電力から差し引いて正味GPU消費電力を推定する。実行区間の平均正味電力に経過時間を掛けてWhへ換算する。各実験は3回実施して平均した。論文の追加検証では、電力時系列を積分する方法との違いは平均0.46%、最大2.3%だった。ただし測定対象はGPUであり、CPU・DRAM・PCIe・冷却装置の電力は含まれない。

同じコード補完でも、モデルによって出力トークン数が変わる。論文は実行全体のエネルギーWhと経過時間に加え、**生成トークンあたりのJ/token**を記録する。J/tokenは比較に有用だが、入力長が長い場合はprefillに消費したエネルギーも生成トークン数で割られるため、「1トークンを生成する純粋なdecode費用」ではない。入力・出力の役割を区別するため、後段の回帰分析を併用する。

### 2. RepoBench：長文脈で短い出力を生成する

RepoBenchのコード補完セットからCross-File-First、Cross-File-Random、In-Fileの3分割を使用した。前者は別ファイルの情報が初めて現れる行を補完する難しい設定であり、後二者は同一ファイル内に情報が存在するなど、依存関係の強さが異なる。文脈長は2K、4K、8K、12K、16K、24K、32Kの7段階で、各段階・分割から100例を選び、計2,100課題とした。ただし全モデルが32Kを扱えるわけではなく、長文脈の表は対応モデルの部分集合になる。

この課題ではベースモデルを使用し、温度0.2、top-p 0.95、最大出力128トークンに固定する。品質はNormalized Edit Similarity（ES）とExact Match（EM）で測定する。リポジトリの変数名・API名・コード規約に沿うことを重視するため文字列類似度は一定の意味を持つが、**実際にコンパイル・テストが成功するか**はRepoBenchの主評価では測っていない。長い文脈を与えることでESが改善する場合もあるが、常に改善するわけではない。

### 3. McEval：短い入力から比較的長いFIMを生成する

McEvalは40言語を扱うベンチマークだが、本研究はPython 340件、Java 355件、Rust 343件の計1,038件を採用した。入力文脈は2Kトークンを基準とし、最大出力を1,300トークンへ設定する。これは選んだ言語の正解コードの最大長（Python 1,227、Java 1,274、Rust 1,017トークン）を覆うためである。こちらは指示追従モデルを使い、生成コードを用意されたDocker環境で実行してテスト通過率Pass@1を測る。

RepoBenchとMcEvalでは、入力長、出力長、モデルの学習形態、品質指標が異なる。したがって、両者のESとPass@1を直接比較して「どちらが高品質」と結論づけることはできない。McEvalの言語ごとの問題集合も同一ではないため、言語別の総Whを単純に比較して言語の本質的なエネルギー費用を論じることも避ける。

### 4. エネルギーと品質のPareto分析・回帰

各モデル・量子化・言語・文脈長について、品質が高くエネルギーが小さい組合せをPareto前線として可視化する。ある構成が別構成より高い品質と低いエネルギーの両方で優れるなら、劣る構成は前線に残らない。これにより、最大モデルだけでなく小型・量子化モデルが実用的な候補になる条件を確認する。

エネルギーを説明する要因には入力トークン数、出力トークン数、active parameter count、入力×出力、入力×active parameter、出力×active parameterの交互作用を含める。回帰では各連続説明変数を標準化し、モデルファミリー単位のcluster-robust標準誤差を用いる。量子化ビット幅はQ4を基準とし、Q8・FP16の差を評価する。相関はSpearman係数、回帰は総GPUエネルギーWhを目的変数とする。観察研究であり、全ての因果効果を識別する無作為化実験ではない。

## 評価結果：タスク構造でエネルギーの支配項が変わる

### 1. McEvalの実測例（原著Table 1、FP16）

| モデル | Python Pass@1 | Python正味GPU Wh | Python J/生成token | Java Pass@1 | Rust Pass@1 |
|---|---:|---:|---:|---:|---:|
| qwen2.5-coder:1.5b | 56.97% | 16.64 | 1.04 | 65.07% | 54.81% |
| qwen3:4b | 76.06% | 31.44 | 2.17 | 68.17% | 70.26% |
| deepseek-coder-v2:16b | 73.64% | 30.98 | 1.58 | 89.30% | 78.13% |
| codegemma:7b | 68.18% | 66.32 | 3.51 | 66.76% | 63.26% |
| granite-code:20b | 64.24% | 166.91 | 7.75 | 65.92% | 63.26% |

ここでの`deepseek-coder-v2:16b`は総パラメータ数16BのMoEであり、active parameterは総数より少ない。PythonのPass@1ではQwen3-4Bが76.06%で、より大きなGranite-Code-20Bの64.24%を上回る一方、エネルギーは約5分の1である。ただしモデルの学習データ、アーキテクチャ、コード特化の程度が異なるため、「4Bというサイズが20Bより常に優れる」という一般法則ではない。

言語間のPass@1差についてはFriedman検定で有意差（χ²=40.36、p<0.001）が確認された。事後検定ではPythonとJavaの差は有意でなかった（p=0.90）が、両者はRustを有意に上回った。言語別課題が異なるため、この結果をRustの文法そのものが推論エネルギーを増やすという因果主張に置き換えない。

### 2. RepoBenchの長文脈費用（原著Table 2）

| モデル（FP16） | 文脈 | Python ES | Python GPU Wh | Python J/生成token |
|---|---:|---:|---:|---:|
| qwen2.5-coder:1.5b | 2K | 40.87 | 11.55 | 1.11 |
| qwen2.5-coder:1.5b | 8K | 38.44 | 16.56 | 1.26 |
| qwen2.5-coder:1.5b | 16K | 37.44 | 23.27 | 1.55 |
| qwen2.5-coder:7b | 2K | 47.94 | 32.58 | 3.17 |
| qwen2.5-coder:7b | 8K | 47.24 | 46.34 | 3.40 |
| qwen2.5-coder:7b | 16K | 43.74 | 62.70 | 3.85 |

Qwen2.5-Coder-7BのPython ESは2Kで47.94、16Kで43.74へ下がる一方、GPUエネルギーは32.58→62.70Whへ増える。長い文脈は常に有用な情報を増やすとは限らず、無関係なコードが増えることで品質が下がる可能性もある。ただし2K・16Kでは問題集合の構成も異なるため、この表だけから文脈長増加が品質低下を直接引き起こしたと断定してはならない。

同じモデル系でもエネルギー効率の順位は文脈長で変わる。原著は2B以下ではDeepSeek-Coder-1.3Bが12KまではQwen2.5-Coder-1.5BよりJ/tokenで有利だが、16Kでは順位が逆転すると報告する。4B級の比較でもDeepSeek-Coder-V2の軽量MoEとQwen3-4Bの順位が32Kで入れ替わる。モデル選択には**実際に使う入力長の分布**が必要である。

### 3. 相関係数：どの組合せが効くか（原著Table 3）

| 予測因子 | RepoBenchとのSpearman相関 | McEvalとのSpearman相関 |
|---|---:|---:|
| 入力トークン数 | 0.57 | 0.24 |
| 出力トークン数 | 0.40 | 0.36 |
| 有効パラメータ数 | 0.60 | 0.75 |

RepoBenchでは入力長と有効パラメータの積が最も強く相関する。一方McEvalでは出力長と有効パラメータの積が最も強い。これは長いprefillと長いdecodeという二つの実行形態の違いに整合する。ただし相関係数は因果効果ではなく、各モデル・課題の分布に依存する。

### 4. 標準化回帰と「出力1トークン＝入力121トークン」（原著Table 5）

| 標準化された説明変数 | RepoBench β（Wh） | McEval β（Wh） |
|---|---:|---:|
| 入力トークン | 22.976 | 0.427（p=0.882、非有意） |
| 出力トークン | 4.902 | 23.496 |
| 有効パラメータ数 | 26.604 | 27.259 |
| 入力×有効パラメータ数 | 9.788 | −0.562（非有意） |
| 出力×有効パラメータ数 | 1.448（非有意） | 15.674 |
| Q8（基準Q4との差） | +2.389 | +5.841 |
| FP16（基準Q4との差） | +3.008 | +21.947 |
| 決定係数R² | 0.961 | 0.940 |

RepoBenchで入力トークンが1標準偏差増えると、300課題にわたる集計入力は約1,316,931トークン増え、他の条件を統計的に調整したエネルギー増分は約22.98Whとなる。出力トークン1標準偏差は集計2,310トークンで約4.90Whの増分に対応する。著者らはこの回帰係数から、**同じ約23Whを増やすのに、入力なら約131万トークン、出力なら約10,857トークンで足りる**と計算した。比は約121:1であり、RepoBenchの測定条件では出力1トークンが入力約121トークンに相当するエネルギー費用になる。

重要なのは、この121倍を全モデル・全GPU・全ワークロードに共通する物理定数として使わないことである。標準化回帰の集計データから導いた近似であり、特定GPU・Ollama・入力/出力分布・量子化条件に依存する。個別モデルの純粋なdecode J/tokenを直接測った比率でもない。むしろ実務上は、入力が非常に長い場合でも出力長の制御が省エネルギーに効くことを示す経験則として読む。

McEvalでは入力トークンの係数は統計的に有意でなく、出力トークンと有効パラメータ数、出力×有効パラメータ数の係数が大きい。出力が長いタスクではdecode側が支配的になり、出力長が伸びるほど大きいモデルの費用が増える。FP16はQ4に対して有意にエネルギーを増やし、McEvalの回帰係数では+21.947Whである。これらの値は**モデルや課題を固定した実験の差分ではなく回帰の条件付き関連**であり、因果効果の確定値ではない。

## 既存研究との差と推論基盤への示唆

従来のコード補完研究はExact MatchやPass@1、開発者の受け入れ率など品質指標に偏りやすい。一般的なLLM省エネルギー研究は自然言語の短いQA、翻訳、汎用生成を扱うことが多い。本研究はリポジトリ文脈を読むL2R補完と、比較的長いコードを出力するFIM補完を同じGPU測定系で比較し、**prefill寄りとdecode寄りでエネルギー支配項が入れ替わる**ことを示す点に価値がある。

推論エンジンの選定では、モデルの最大コンテキスト長を大きくするだけでなく、関連ファイルを絞る検索・文脈選択、出力トークン上限、量子化方式を一緒に最適化する必要がある。RepoBenchの結果は、入力文脈を増やしても品質が必ず上がるわけではないことを示す。McEvalの結果は、出力が長い補完ではトークン生成数の制御がエネルギー費用へ大きく効くことを示す。ユーザーが実際に使うIDEの要求分布に合わせて、J/token、Wh/要求、成功率、p95/p99遅延を測ることが望ましい。

ローカル環境ではQ4がメモリ制約の緩和とGPUエネルギー削減に役立つ可能性がある。ただし量子化の実効速度・精度はGPUアーキテクチャ、量子化カーネル、GPU/CPUオフロード、モデルの活性パラメータ数で変わる。本論文はA100上のOllamaで測っており、別GPUや別バージョンのllama.cpp、vLLM、SGLangで同じ順位になることは検証していない。

## 限界と再現上の注意

第一に、NVMLが報告するGPU電力からアイドル電力を引いた値だけを測っている。CPU、DRAM、PCIe、ストレージ、冷却、電源効率は含まれない。CPU側で重みやKVをオフロードする環境では、GPU消費電力が減ってもシステム全体のエネルギーが減るとは限らない。GPU電力のサンプリングも外部の電力計ではなくソフトウェア測定である。

第二に、RepoBenchの長文脈条件ではOllama APIが一部の要求を不完全に処理することがあり、特に16Kを超える入力で影響が増えた。長時間の要求が欠落すると、その構成の総エネルギーが見かけ上低くなる。著者らは不完全な実行を手作業で確認し、生成トークンあたりのエネルギー集計から除外したが、完全な無欠測データではない。反復も各条件3回であり、細かい差の有意性には限界がある。

第三に、全モデルが32Kの入力を扱えるわけではない。RepoBenchの長文脈表はモデルの部分集合であり、長文脈でのエネルギー順位の逆転には、対応可能なモデルが変わる選択バイアスも関係しうる。言語別の課題集合も同一ではなく、RepoBenchのESとMcEvalのPass@1は異なる指標である。精度・エネルギーのPareto前線は比較対象の集合を変えれば動く。

第四に、回帰の残差分布には裾の正規性からの逸脱があり、著者らが試した対数変換・Gamma回帰でも診断は一貫して改善しなかった。標準化回帰の係数や121:1の比は観察されたワークロードの関連を表すもので、全モデルへ普遍的に外挿するべきではない。入力・出力長とモデル規模を独立に操作する統制実験が将来課題として挙げられている。

第五に、対象はPython・Java・Rustのコード補完であり、実際のIDEでの補完候補拒否、連続する対話、複数回の修正、ツール呼出し、RAGによる追加取得、複数GPUの負荷分散を含まない。エージェント型のコード生成ではツール実行やネットワーク待ちも総費用へ影響するため、今回のモデル別GPU Whだけでサービス全体の環境負荷を決められない。
