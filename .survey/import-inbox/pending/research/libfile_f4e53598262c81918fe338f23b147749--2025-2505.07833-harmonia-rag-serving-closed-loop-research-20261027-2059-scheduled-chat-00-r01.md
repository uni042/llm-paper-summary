# Harmonia：RAG全体の資源配分と期限制御を統合する分散サービング

## 概要

Harmoniaは、検索器、文書評価器、クエリ書換え器、生成LLMなどが条件分岐・再帰を通じて連携するRAGを、単一の最適化対象として扱う。従来のサービングでは各LLMのトークン生成を高速化しても、検索・文書評価・再試行の遅延が残る。Harmoniaは開発者のPythonワークフローからコンポーネント依存関係を抽出し、CPU/GPUとメモリを配置して、実行中の負荷や分岐頻度に応じて再配分する。さらに要求ごとの残り処理時間を予測し、SLO（サービス水準目標）期限に対する余裕が小さい要求を優先する。

原著v2（2026年6月4日更新）は、4サーバー、A100 80GB×8という原著のクラスタ記述、Intel Xeon Silver 4314、256GiB RAMで、Vanilla、Corrective、Self、Adaptiveの4種のRAGをLangChainとHaystackに対して比較する。最も複雑なSelf-RAGで処理量は最大2.04倍、Adaptive-RAGでSLO違反を最大78.4%削減した。一方、単純なVanilla-RAGでは飽和時の処理量利得が約3%に縮み、締切を守れる余裕がないほど負荷が高いと優先制御の改善が消える。高速化の対象はRAGワークフロー全体であり、単独LLMの1トークン生成が2.04倍になるという結果ではない。

## 問題設定

RAGは検索器のCPU処理、ベクトルDB、GPU上の生成器、別のLLMによる採点・書換えなど異質な処理から成る。単純な検索→生成では負荷が比較的安定していても、Corrective-RAGは文書品質によって検索や生成の経路が変わり、Self-RAGでは低品質の出力を検出すると再帰的に書換え・生成へ戻る。Adaptive-RAGは問い合わせの難度により、検索なし、単回検索、多段検索を切り替える。したがってコンポーネントごとの処理時間と呼出頻度は一定ではない。

CPU検索器が余裕を持っていてもGPU文書評価器が飽和すれば全体の処理量は増えない。逆に文書評価器を増やし過ぎると生成器にGPUを割り当てられず、ボトルネックが移動する。さらにストリーミングを細かくし過ぎると通信・スケジューリング費用が増え、パイプラインが過負荷のときには粗い転送が有利になる。個々のコンポーネントを独立に最適化しても、RAG全体の要求完了率やSLO違反は改善しない場合がある。

従来の命令型の分散処理はPythonの自由度が高い反面、ワークフローの全体像が不透明になり、将来の分岐負荷を見越した配置が難しい。一方、完全な静的データフローを要求する宣言型の設計は、RAGの条件分岐や再帰を自然に表現しにくい。HarmoniaはPythonの柔軟さを維持しつつ、資源配分に必要な粗い構造だけを抽出する。

## 手法

### 1. ワークフロー指定層：Python ASTから構成グラフを抽出

開発者は検索器やLLMなどのコンポーネントを`harmonia.make`で宣言し、`harmonia.capture()`の内側に通常のPython分岐・呼出しとして処理の流れを書く。例えばCorrective-RAGでは、検索結果をgraderへ渡し、不適切ならrewriterとweb検索へ進み、適切なら検索文書をそのまま生成器へ渡す。`harmonia.deploy`はこのワークフローを分散実行可能なサービスへ変換する。

HarmoniaはPythonの抽象構文木（AST）を静的にたどり、装飾されたRAGコンポーネントの呼出し位置から依存グラフを作る。オブジェクトのメモリ配置や全Python命令の機械語生成を解析するのではなく、どのコンポーネントからどこへ要求・データが流れるかという粗い関係だけを把握する。条件分岐や再帰があっても、中心となる依存骨格をDAG（有向非巡回グラフ）として扱い、実行回数の増幅や分岐確率を後段のモデルに組み込む。

### 2. 配置層：最大流と資源予算を結ぶ最適化

グラフの各ノード`i`を検索器・評価器・生成器等のコンポーネントとし、資源種別`k`ごとに単位資源当たり処理量`α(i,k)`、割当量`r(i,k)`、全体のCPU/GPU予算`C(k)`を定める。さらに各ノードの呼出し増幅率`γ(i)`と、枝`i→j`を通る確率`p(i,j)`を用いる。目的は各資源の総割当が予算を超えず、各ノードの流入要求が割当処理能力を超えない条件で、最終ノードへ到達する要求流量を最大化することだ。

初期の`α`、`γ`、`p`は代表サンプルのプロファイリングで推定する。原著はShareGPTのサンプル（例として100件）を使い、バッチサイズや構成ごとのコンポーネント処理量を測る。Gurobiで線形計画を解き、CPU検索器とGPU生成器を同一ホストに置くか、どの評価器を複製するか、どこにGPUを配るかを決める。ワークフローの論理仕様と物理配置を分離し、ノード内では共有メモリ、ノード間ではgRPCで中間出力を直接転送する。各ノードのRedisは一時出力の保管に使われる。

### 3. 実行制御層：負荷変化を監視する閉ループ再配分

起動時の配置は問い合わせ分布が変わると最適でなくなる。中央制御器はコンポーネントの実測処理量、各分岐の通過頻度、要求の再帰回数、現在の負荷を集め、`α`、`γ`、`p`を再推定する。原著実装では10秒ごとに別スレッドで線形計画を再計算し、2回続けて同じ割当が得られたときだけ再配分する。これにより短期の揺らぎによる頻繁な配置変更を抑える。

再帰を伴う状態付き要求については、現在空いているワーカーを選ぶだけでは不十分である。今は空いていても、直前に別段へ進んだ要求が戻ってくると同時に混雑するため、制御器は未完了の状態付き要求と再訪の予測を用いて行先を選ぶ。また転送チャンクの大きさを事前に測定した負荷別性能と照合し、混雑度に合わせて変更する。細かな転送で計算と通信を重ねる利点と、小さなチャンクが増やす制御費用の間で選択する。

### 4. SLO期限余裕の予測と優先送信

各要求の残り時間は、これまで通った段の実測値と残り経路の推定時間から予測する。例えば検索文書数が多ければgraderの入力が増え、後続LLMの時間も伸びやすい。Harmoniaは取得文書数やトークン数を説明変数とするオンライン線形回帰を維持し、要求が期限に間に合うまでの余裕（slack）を見積もる。余裕の小さい要求を各コンポーネントのキューで優先し、通信層にもその優先度を伝える。

中央制御器は処理の順序と行先を決めるが、大きな検索結果やLLM出力を常に中央へ集約するわけではない。データは基本的にワーカー間を直接移動し、条件分岐の判断に必要なときだけ制御器が結果を読む。この制御面とデータ面の分離により、要求ごとに中央が判断しても約2 msの制御遅延に抑えられると報告される。ただし、全要求が飽和で余裕ゼロに近い場合、優先順位を変えても処理能力自体は増えない。

## 評価

### 実験条件

| 項目 | 原著v2の条件 |
|---|---|
| ハードウェア | 4サーバー、各サーバーIntel Xeon Silver 4314 16コア×2とRAM 256 GiB。原著はA100 80GiB×8も記載（各サーバーへの配分は本文から断定しない） |
| ソフトウェア | Ubuntu 22.04.1、Linux 5.15、CUDA 12.3、Python約6,000行、gRPC/Redis |
| 比較 | LangChain、Haystack（Ray連携を含む実装） |
| 入力 | LMSYS-Chat-1Mから3,000会話、Poisson到着、Wiki-DPR約2,100万文書、検索件数k=100〜300 |
| RAGの種類 | V-RAG（直列）、C-RAG（条件分岐）、S-RAG（条件分岐と再帰）、A-RAG（複雑度で分岐し再帰） |
| 指標 | 完了要求/秒、SLO違反率、制御遅延、最適化時間、各コンポーネント処理量 |
| SLOの定義 | Harmoniaの低負荷時平均要求遅延の2倍を期限に設定 |

SLOは原著が定義した相対的な閾値であり、外部サービス契約における絶対時間を直接満たした証拠ではない。比較対象は同一RAG構成をLangChain/Haystackで実装した場合であり、生成モデル単体の推論速度比較ではない。

### ワークフロー別の主要結果

| ワークフロー | 対LangChain/Haystackの最大処理量改善 | SLO違反削減の代表結果 | 負荷条件・意味 |
|---|---|---|---|
| Vanilla-RAG | 最大約31%増 | 中負荷で約11.8%減 | 飽和時の処理量差は約3%、SLO改善も消える |
| Corrective-RAG | 最大1.98倍 | LangChain比最大約21%、Haystack比最大約18%減 | graderの負荷が大きく、配分調整が効く |
| Self-RAG | 最大2.04倍 | 最大41.3%減 | 再帰回数の違いが優先度調整の余地を生む |
| Adaptive-RAG | 最大1.48倍 | 最大78.4%減 | 単純要求と多段検索要求が混在し、経路差を利用できる |

原著Figure 9–11の最大値はそれぞれ特定の到着率における比較であり、4種のRAGすべてが2.04倍高速化するわけではない。SLO違反削減の78.4%もAdaptive-RAGの個別条件である。飽和したVanilla-RAGでは、どの要求を優先しても他の要求が期限超過になるため、優先制御の利点がほぼなくなる。これが「高負荷なら必ずSLO違反が減る」とは言えない直接の負の結果である。

### 資源配置と構成要素の寄与

C-RAGではgraderの実行時間がgeneratorの約1.8倍であることから、Harmoniaはgrader 5インスタンスとgenerator 3インスタンス（各1 GPU）を選んだ。検索器は4ノードへ配置する。S-RAGではgeneratorが律速で、criticは1トークン程度の判定で速いため、critic 2、generator 6、retriever 3の構成となる。A-RAGでは当初query classifier 5、generator 3、retriever 4を配置し、実行中にclassifier 4、generator 4へ変更した。これらは単にGPUを均等分割するのでなく、実測処理量と分岐率を使ってボトルネックへ資源を寄せる例である。

原著Figure 14の64 req/sでの構成要素除去では、オンライン資源再配分がC-RAG/S-RAG/A-RAGの性能改善に占める寄与を86.8%/78.5%/52.1%と報告する。一方、分岐のないV-RAGではオンライン再配分の寄与が小さい。通信チャンク長調整はV-RAGで全改善の56.2%を占め、他の3方式では約6%、5%、17%の改善寄与とされる。どの機構が効くかはRAGの構造により変わり、単一の最適化がすべてを支配するわけではない。

### 制御面の費用とCPU/GPU共置

| 項目 | 原著の数値 | 解釈 |
|---|---|---|
| 最大1,024 req/s時の中央制御遅延 | 2.3 ms未満 | 中央がデータ本体を通過させない設計の効果 |
| 資源配分の線形計画 | ノード数により約3.8〜31.3 ms、1,024ノードで約32 ms | 別スレッドで再計算。各トークンの推論遅延ではない |
| 単一ノードでのgRPC等の付加費用 | LangChain比平均約0.8% | 分散制御を導入する基本コスト |
| ChromaDB共置／単独 | 971.9 / 972.3 req/s | CPU検索器の性能差は小さい |
| vLLM共置／単独 | 127.6 / 128.3 req/s | GPU生成器の性能差は小さい |

共置実験はCPU集約型検索器とGPU集約型生成器の資源相補性を示すが、すべてのCPU/GPU混合処理が干渉しないと保証するものではない。例えばCPU側の前処理やメモリ帯域がGPUの入力供給を制限する構成は、この表の条件とは異なる。

### 限界・未検証事項

Harmoniaは構成要素の依存関係をASTから抽出できること、分岐率を実行履歴から推定できること、比較的安定したワークフロー骨格があることを前提とする。一般のエージェントがLLM出力に応じて予期しないツールや処理順を生成する場合、DAGの骨格を事前に決められず、著者自身が適用外と明記している。資源配分の最適性もプロファイル値に依存し、実行中に再推定する仕組みは誤差を減らすが完全には消さない。

SLO期限の設定はHarmoniaの低負荷平均遅延を基準にしており、現実の固定SLAや異なる品質保証へそのまま移せない。性能比較は4サーバーの大規模A100クラスタで行われ、単一GPU、家庭用GPU、ネットワークの極端な高遅延・低帯域、故障時の復旧挙動などへの外挿には注意が必要である。最大処理量とSLO違反削減の数字はそれぞれ別のワークロード・負荷点であり、両者が同時に最大になるとは示されていない。

## 既存研究との差

LangChain/HaystackはRAGコンポーネントの組合せを提供するが、Harmoniaはワークフロー全体の資源配分と実行中の期限管理まで引き受ける。RAG検索を先読みするTeleRAG、検索器を最適化するPiperRAG、推論を投機化するSpeculativeRAGなどの個別段階の高速化とは対象が異なる。Helixなどの異種GPU向け最大流配置に似た数学的発想を持つが、HarmoniaはCPU検索・GPU生成・分岐確率・再帰・要求増幅を含むRAG全体へ拡張している。

本論文の主要貢献はモデルの重みやAttentionカーネルではなく、**RAGサービスの配置・スケジューリング・通信・SLO管理の結合**である。コンポーネントの種類が多く、要求ごとの経路差が大きいほど中央制御の価値が出る一方、単純な直列RAGや飽和状態では改善が限定される。
