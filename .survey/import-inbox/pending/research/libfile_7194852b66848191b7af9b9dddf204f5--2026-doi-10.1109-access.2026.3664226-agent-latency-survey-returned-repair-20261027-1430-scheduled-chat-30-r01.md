# LLMエージェントの応答遅延を四層で捉える総説

## 書誌と対象範囲

Park、Lee、ParkによるIEEE Access 2026年の総説。対象はLLM単体の1回の生成時間ではなく、LLMを意思決定器として用いるエージェントが要求を受け取り、計画し、必要なツールを実行して最終結果を返すまでの**端から端までの応答時間**である。エージェントは複数回の推論、外部APIの待ち時間、メモリ検索、サービングのキュー、他エージェントとの同期を含むため、モデルのデコード速度だけではユーザーの体感遅延を説明できない。

本論文の貢献は新しいGPUカーネルの提案ではなく、既存の遅延削減策を「基盤LLM推論」「エージェント制御」「サービング・ハードウェア基盤」「複数エージェント協調」の四層に配置し、改善対象と副作用を比較できる分類体系に整理したことにある。さらにQwen2.5-7B-InstructをNVIDIA L4で動かす補助実験を行い、量子化、KVキャッシュ、バッチ化の代表的な交換条件を示す。これらの著者実測値と、GPTQ、vLLM、MetaGPTなどの引用論文由来の数値は厳密に区別しなければならない。

## 概要

LLMエージェントの遅延は、入力のプリフィル、自己回帰デコード、計画の再生成、ツールの実行、通信、要求待ち、協調の同期から構成される。各要素の処理を高速化しても、エージェント全体のクリティカルパス上になければ総時間の短縮は小さい。たとえば独立な三つの外部ツールを逐次呼び出す場合、待ち時間は概ね三つの所要時間の和になるが、並列呼出しなら最も遅い一件に支配される。逆に、ツール間に依存関係がある場合や並列化の起動費用が大きい場合は、同じ単純化が成立しない。

補助実験では、Qwen2.5-7B-InstructのFP16とINT4を比較して総生成時間が15.48秒から6.29秒へ短縮した。一方、KVキャッシュを有効にすると後続トークンの生成は速くなるが、TTFTは79.04ミリ秒から192.44ミリ秒へ増えた条件がある。バッチサイズ1から8への変更では全体スループットが16.52から122.39 token/sへ改善した。これらは異なる実験系列の結果であり、同じ要求に全倍率を掛け合わせてよいわけではない。<https://doi.org/10.1109/ACCESS.2026.3664226>

## 問題設定：モデルの速度とエージェント全体の遅延は異なる

基盤LLMの指標として、TTFTは要求から最初のトークンが得られるまでの時間、TPOTは後続トークンを一つ生成する平均時間を表す。プリフィルは入力長と行列積の計算量に左右され、デコードは重みやKVキャッシュのメモリ帯域が律速になりやすい。しかしエージェントが一つのタスクで何度もLLMを呼ぶ場合、TTFTとTPOTは各呼出しの一部しか説明しない。ツールのネットワーク待ち、計画の検証、検索、再試行を含めた総時間を測る必要がある。

著者はエージェントの時間を、モデル実行、計画・判断、外部ツール・通信、サービング待機、複数エージェント協調へ分解する。これらは原因別の分類であり、必ずしも互いに独立した時間の単純和ではない。ツールの並列実行や複数エージェントの同時処理がある場合、処理依存グラフの最長経路が総時間を決める。GPUの推論時間が短縮されても、他の処理がクリティカルパスを占めればユーザー応答はほとんど速くならない。

またスループットと個々の要求の遅延は別の指標である。大きなバッチはGPU使用率を上げて全体のtoken/sを改善できるが、個々の要求がキューで待つ時間や、p95/p99のテール遅延が同時に短くなるとは限らない。リアルタイムのエージェントでは平均値だけでなく、要求到着率、入出力長、サービスレベル目標、ツール実行の長い裾を含めて評価する必要がある。

## 手法

### 総説の分類体系と改善の作用点

### 文献調査と四層の分類

著者らはGoogle Scholar、arXiv、ACM Digital Library、IEEE Xploreを用い、LLMエージェントの遅延、KVキャッシュ、投機的復号、サービング、複数エージェント通信などの文献を探索した。主として2022年以降の査読論文と影響力のあるプレプリントを調べ、タイトル・要旨で候補を絞った後に本文を確認した。LLM学習だけを対象とするものや、実際のエージェント遅延への寄与が乏しい研究は対象から外す方針である。四層は「何を速くするか」という操作対象の分類であり、単一のシステムが複数層を横断して最適化することを妨げない。

| 層 | 主な遅延源 | 代表的な対策 | 同時に確認すべき代償 |
|---|---|---|---|
| 基盤LLM推論 | 重み・KVの読出し、逐次デコード | 量子化、剪定、疎注意、投機的復号、KV管理 | 品質劣化、候補棄却、追加カーネル |
| エージェント制御 | 計画反復、ツール選択、コンテキスト生成 | 階層計画、モデル振分け、ツール並列化、メモリ圧縮 | 誤選択、再計画、情報欠落 |
| サービング基盤 | キュー、GPU競合、バッチ形成、通信 | 継続的バッチ、要求配置、分散実行、専用アクセラレータ | テール遅延、通信・運用費用 |
| 複数エージェント | メッセージ往復、同期、役割調整 | 非同期実行、構造化メッセージ、階層協調 | 古い状態、再作業、柔軟性の低下 |

### 基盤LLM推論：重み、注意、デコードの律速を分ける

量子化は重みや活性値、KVキャッシュの表現ビット数を減らし、GPUメモリの使用量と転送量を抑える。デコードが重み読出し帯域で律速となる場合は高速化につながるが、低ビット値を演算時に展開する費用が大きければ速度改善は限定される。剪定は重み、層、ヘッド、トークンの一部を削減する。計算量が減っても不規則な疎行列がGPUカーネルに適合しなければ、実測の生成時間は短くならない。

FlashAttentionは注意行列の中間結果を外部メモリへ大量に書き出さず、タイル単位で正規化を更新することで注意計算のメモリ転送を削減する。一方、KVキャッシュ圧縮や削除は過去トークンの保持容量・読出し量を変える。両者は注意関連技術でも最適化対象が異なる。KVの重要トークンを誤って捨てれば長距離の情報検索を失敗するため、削減率だけでなく回答品質も測る必要がある。

投機的復号は、小型の候補生成器が複数トークンを先読みし、大型モデルが一括で検証することで逐次呼出しを減らす。候補が受理されるほど効果があるが、ドラフトと本体の予測が一致しない場合は棄却と再計算の費用が増える。量子化されたドラフトの出力分布が変わると受理率が下がる場合があり、個別に有効な最適化を重ねても必ずしも速くならない。PagedAttentionのようなページ管理はKVの断片化を減らすが、重要度に応じたKV削除とは別の仕組みである。

### エージェント制御：計画、ツール、記憶の費用を抑える

複雑な目標を段階的に分割する階層計画は、全体を毎回ゼロから再計画する費用を抑える可能性がある。簡単な判断は小型モデルに任せ、難しい入力だけ大型モデルへ送る構成は平均推論費用を減らす。ただし、ルーティングが誤って重要な要求を軽量経路へ送れば、品質低下や再試行が発生する。モデル選択器の実行費用と誤判定率も含めて測定すべきである。

外部ツールの利用では、ツール選択を明確にする構造化スキーマ、軽量な呼出しフレームワーク、標準作業手順、独立したAPIの並列実行が対象となる。論文の診断エージェントの例では、ガイドライン検索、予約照会、薬剤相互作用確認を逐次実行する代わりに、依存がないなら並列化できる。逐次では各ツール時間が加算されるが、並列では最長ツール時間と起動・集約費用が中心になる。ただし、ある結果が別の検索条件を決める場合は並列化できず、失敗時の再実行費用も増える。

記憶とコンテキストの最適化では、毎ターンすべての履歴や検索結果を再投入する代わりに、関連部分を抽出・要約する。入力トークン数が減ればプリフィルを短縮できるが、必要な情報を失うと再検索や誤回答が増える。したがって単一ターンのTTFT改善と、エージェントが最終目標を達成する成功率は分けて評価する必要がある。

### サービングと複数エージェント：全体のクリティカルパスを短縮する

継続的バッチ処理は、出力長の異なる要求をGPUへ詰め直して処理することで遊休時間を減らす。プリフィルとデコードを別GPUへ分離する構成は、それぞれの計算特性に合う資源配置を可能にする一方、KV転送やネットワーク通信の費用が増える。負荷に応じた要求配置やキャッシュ共有は、単一GPU内の計算だけでなくクラスタのキュー長やデータ移動を考慮する必要がある。

複数エージェントでは、自由形式の対話を何度も行うと、各担当が仕様を確認するたびにLLM推論と同期が増える。MetaGPTのように役割と標準作業手順、構造化成果物を先に決める構成は、下流の入力を明確化して不要な往復を減らす。一方、予想外の状況で柔軟に協議する能力が必要な場面では、自由形式の対話が有効なこともある。非同期化して待ちを減らしても、古い状態を基に作業してやり直しが増えるなら総時間の短縮にはならない。

## 評価

### 著者の補助実験と引用文献の結果を区別する

総説に含まれる数値は二種類ある。第一はParkらが自ら実施したQwen2.5-7B-InstructとL4の補助実験であり、第二はGPTQ、vLLM、MetaGPTなど別論文の実測結果を引用したものである。ハードウェア、モデル、バッチ、トークン長、成功条件が異なるため、二種類を同一条件の直接比較として扱うことはできない。特に「GPUのtoken/s」と「エージェント全体の完了時間」は測定対象が違う。

| 補助実験の条件 | 内容 |
|---|---|
| GPU | NVIDIA L4、24GB GDDR6 |
| CPU・メモリ | Intel Xeon 2.20GHz、8 vCPU、32GB RAM |
| ソフトウェア | PyTorch 2.9.1、Transformers 4.47.0、vLLMとの比較を含む |
| モデル | Qwen2.5-7B-Instruct |
| 生成 | 1要求あたり50トークン、貪欲復号 |
| バッチ | 32テストプロンプト、サイズ1・2・4・8 |
| 指標 | 生成所要時間、token/s、TTFT、TPOT、GPUメモリ、バッチ効率 |

### 著者による定量結果

| 実験 | 比較値 | どの主張を支えるか |
|---|---|---|
| FP16→INT4 | 総生成時間15.48→6.29秒 | L4の特定実装で低ビット化が生成時間を減らす |
| FP16→INT4 | 生成速度16.54→40.70 token/s | 同じ系列のトークン処理率の改善 |
| KVキャッシュなし→あり | 総時間約24.3%減、TPOT 80.57→58.25 ms | 過去KV再計算を避け、逐次生成を速める |
| KVキャッシュなし→あり | TTFT 79.04→192.44 ms | キャッシュ準備の初期費用が短い応答に不利な場合がある |
| バッチ1→8 | 全体16.52→122.39 token/s | 固定プロンプト集合でGPUの集約処理量が増加 |
| バッチ1→8 | 論文報告の平均要求時間3026.54→408.53 ms | 特定の計測定義下での平均でありオンラインp99ではない |
| バッチ1→8 | GPUメモリ14.20→14.24 GB | この短い入力・小規模条件ではメモリ増加が小さい |

INT4の生成時間の比15.48/6.29は約2.46、token/sの比40.70/16.54も約2.46である。原著の文章に2.39倍という別の表現がある場合は、絶対値から再計算した比と同一とは断定しない。測定対象の時間区間や丸め、集計方法に差がある可能性があるため、絶対値と条件を優先して記録する。量子化はモデルの誤答率を上げ得るが、ここでの生成速度だけではエージェントの最終タスク成功率を評価できない。

KVキャッシュの結果は、**TTFT悪化とTPOT改善が同時に起きる**ことを示す。後続トークンが多い要求ではTPOTの改善が初期費用を上回り得るが、非常に短い応答ではTTFTの増加が支配的になる。キャッシュの有無の比較を「すべての遅延が24.3%改善」と読むのは誤りである。バッチの結果も、32プロンプトの固定集合での全体処理量であり、ランダム到着の実サービスにおけるキュー待ち、p95/p99、サービスレベル目標の達成率を直接示すものではない。

### 引用研究からの定量結果

| 引用研究 | 数値 | 読解上の制約 |
|---|---|---|
| GPTQ、OPT-175B | 3bitで230→71 ms/token、WikiText-2 PPLはFP16 8.34、4bit 8.37、3bit 8.68 | GPU台数など比較条件が異なる既報値。L4のQwen実験ではない |
| vLLM、OPT系列 | 既存方式比2〜4倍のスループット | 8台A100などでの既報値。量子化実験とは別 |
| MetaGPT対ChatDev、SoftwareDevの7課題平均 | 541秒対762秒、約29%短縮 | ソフトウェア開発タスクの既報比較であり全エージェントへの保証ではない |
| 同じ協調比較 | 実行可能性3.75対2.25（4段階）、手修正0.83対2.5回 | 生成後の人手修正という隠れた費用も評価対象になる |

総説の分類体系は、個別方式の測定値を整理するための枠組みである。異なる研究の「2〜4倍」「29%短縮」を一つのエージェントへ足し合わせることはできない。モデル推論が速くなればツール呼出しの相対的な比率が増え、次に最適化すべき層が変わる。逆に、ツール並列化が成功すればモデル生成やキュー待ちがクリティカルパスへ浮上する。層をまたぐ評価では、各段階の時間分解とタスク成功率の両方が必要である。

### 調査範囲と評価の限界

著者の文献調査は主に2022年以降のLLMエージェントと周辺推論システムを対象とする。四層分類は遅延源を整理するには有効だが、各研究が同じワークロード、GPU、精度、品質制約で測定されているわけではない。引用数値の統計的な統合や、統一ベンチマークによる公平な総合順位を示すものではない。自前の補助実験も単一のQwenモデル、L4、短い生成設定を中心とするため、多数同時要求、長文脈、異種ツール負荷、分散マルチエージェントのp99を直接検証していない。

## 限界

### 負の結果と適用範囲

第一に、量子化や剪定はモデル推論を高速化しても、エージェントの最終正答率・安全性・信頼性を落とす可能性がある。誤答により再計画、追加検索、ツール再実行、人的修正が増えるなら、単体生成の高速化が総所要時間の短縮へ結びつかない。低ビット化を採用する際は、推論品質とタスク成功率を速度と同じ条件で確認する必要がある。

第二に、KVキャッシュの補助実験では後続トークン生成が速くなってもTTFTが悪化した。短い出力や対話的なエージェントでは初期費用が相対的に大きく、長い生成を繰り返す設定とは最適解が異なる。バッチ化は全体スループットを上げるが、要求到着率や長短混在、サービスレベル目標に対してテール遅延がどうなるかは別問題である。

第三に、ツール呼出しの並列化は独立なAPIにしか適用できず、前段結果に依存する後段呼出しでは同期が残る。エラー処理や再試行が多い場合、並列化の管理費用が大きくなる。メモリ圧縮も必要な事実を削除すれば、再検索や再計画の回数が増える。計画の軽量化は誤ったツール選択の危険を伴うため、処理時間だけでなく成功率と回復費用を測る必要がある。

第四に、複数エージェントの構造化協調は役割が明確なソフトウェア開発などでは有利だが、未知の問題へ柔軟に適応する場面では自由形式の対話が有効なこともある。非同期化は待ち時間を減らしても、古い情報を使った作業のやり直しが増える場合がある。固定された協調手順の高速化率を、任意の動的なマルチエージェント環境へ外挿するのは不適切である。

第五に、文献調査の対象と補助実験は有限であり、実運用でのネットワーク障害、ツールの長い裾、モデル品質の分布ずれ、ハードウェア世代差、負荷の急変を網羅しない。ハードウェア・ソフトウェア協調設計や動的オーケストレーションは将来の研究方向として挙げられるが、具体的な導入による性能改善が本論文で実証済みという意味ではない。

## 既存研究との差と利用上の意義

GPTQやFlashAttention、vLLM、個別のエージェントフレームワーク研究は、それぞれ特定の計算や管理機構を改善する。本総説はそれらを「何の遅延を削減するか」という共通軸に配置し、モデル単体の速度、システム全体のスループット、エージェントの完了時間を混同しない視点を与える。特に、量子化の高速化とKVキャッシュのTTFT悪化を同じ補助実験で示した点は、複数層の改善を組み合わせるときの注意事項を具体化している。

実務的には、エージェントの要求受付から完了までの時刻を記録し、モデルのプリフィルとデコード、ツール呼出し、待ち行列、協調待機を分離して測るべきである。その上でクリティカルパスにある遅延源から最適化し、品質低下・再試行・通信・人手修正を含めた総時間で比較する。この計測方針は総説の分類体系から導く利用上の指針であり、著者があらゆるエージェント実装に同一の高速化を実証したという主張ではない。
