# DEdit：後続候補を利用する反復ドラフト編集と投機的復号

## 概要

DEditは、自己回帰型の大規模言語モデルを高速化する投機的復号の**ドラフト生成側**を改良する。従来の並列拡散型ドラフトは、窓内の多数の候補トークンを一度の前向き計算で予測できる反面、各位置の予測が互いに独立しやすい。先頭付近に誤りが一つあれば、対象モデルによる接頭辞検証はそこで停止する。後続の候補に正しいトークンがあっても、検証に使われず廃棄される。この捨てられる情報を、**検証する前に前方位置の修正へ再利用する**ことが中心的な発想である。

DEditはマスク列から最初の候補を並列生成し、同じドラフトモデルで候補列全体を双方向に再予測する。後ろの位置の予測を前の位置の修正に利用できる点が、因果方向の補正方式と異なる。学習時にはProposalMixという混合入力を用い、誤りを直すだけでなく、すでに正しい接頭辞を壊さないように訓練する。対象モデルへ提出するのは最後に編集した候補だけであり、編集途中の候補を毎回対象モデルへ照会するわけではない。

著者の7課題マクロ平均では、Qwen3-4BとQwen3-8Bを対象とするgreedy復号で、自己回帰生成に対するエンドツーエンド速度倍率がそれぞれ**5.72倍と5.97倍**、1検証ラウンド当たりの平均前進トークン数が**7.58と7.75**であった。ただし比較方式は基本的に窓幅16、DEditの主要設定は窓幅32・合計3パスであり、同じ候補数・同じ計算費用の比較ではない。速度はNVIDIA H100 1枚、バッチサイズ1、ドラフトにCUDA Graph、対象モデルの検証にeager実行を用いた測定であり、高並列サービングへの外挿はできない。

## 問題設定と先行方式

通常の自己回帰生成では対象モデルが1回の復号で1トークンを確定する。投機的復号は小さな補助モデルが複数トークンを提案し、大きな対象モデルが一度に検証することで、対象モデルの高価な前向き計算を複数トークンに償却する。対象モデルの出力分布を保つ標準的な検証を前提とするため、ドラフトの誤りは最終回答の誤りではなく、受理長の短縮という速度損失として現れる。

ここで重要なのは、**個々の位置が正しいか**と**連続した接頭辞として受理できるか**が別であることだ。例えば候補が「正・正・誤・正・正」であれば、標準検証は最初の誤りで停止する。後方の二つの正解候補を先頭の修正に使えれば、次の検証で受理できる範囲が伸びる可能性がある。並列拡散型のDFlashは初期候補を一度に生成するが、この後方情報を初期誤りの修正に利用しない。Dominoは軽量の因果補正を導入するものの、後方の予測を前方位置へ伝えられない。DSparkは逐次補正と信頼度に応じた検証を使うため、ドラフト生成・検証の費用構成が異なる。

DEditは検証器そのものを置き換えない。従来の接頭辞検証を保ったまま、ドラフト生成と編集を同じモデルへ統合する。したがって受理率が増えても、追加のドラフトパスの時間が長ければ、壁時計の速度向上は小さくなる。原著が受理トークン数とエンドツーエンド速度倍率を別々に示す理由はここにある。

## 手法

### 1. 固定アンカーと並列初期ドラフト

対象モデルがすでに確定した出力文脈を`x`、そこから得られる特徴を`h(x)`とする。窓幅`W`の先頭には直前に確定したトークン`y0`をアンカーとして固定し、残る`W−1`位置をマスクで埋める。ドラフトモデル`qθ`は`x`と`h(x)`を条件に各マスク位置の語彙分布を並列予測し、argmaxによって初期候補列`z^(1)`を得る。この初期パスをP1と呼ぶ。

固定アンカーは、すでに確定した出力が編集によって変わらないことを保証する。対象モデル由来の特徴を利用するため、ドラフトは単独の無条件生成器ではない。DFlashと同系統の5層ドラフトを利用する点も、単純に別の巨大な編集モデルを追加する方式とは異なる。候補の後半はこの段階で前半候補を条件にしていないため、長い窓では一貫性が弱くなる可能性がある。

### 2. 双方向の反復編集と最終検証

P2では、P1が出力した**候補列全体**を次の入力とし、各位置を同時に再予測する。位置`i`の更新は、`i`より前の候補だけでなく、`i`より後ろの候補も参照する。P3以降も直前の候補列を入力として同じ更新を繰り返す。アンカー、対象モデルの既存文脈と特徴は固定したまま、ドラフト側の候補のみを更新する。全位置が毎パス編集対象であり、推論時に信頼度の低い位置だけを編集するゲートは設けない。

全パスで同一の`qθ`のパラメータを共有するため、編集回数を増やしても別個の編集モデルの重みは増えない。一方、**1パス追加するたびにドラフトの前向き計算が1回増える**。最後の候補列`z^(K)`だけを対象モデルへ渡し、対象モデルが最初の不一致までを受理する。受理したドラフトトークンが`a`個なら、対象モデル自身の追加1トークンを合わせて`a+1`個前進する。論文の指標`τ=E[a+1]`はこの追加分を含むため、単純な「ドラフトの受理個数」と混同してはならない。

後続位置が正しい場合でも、編集器が必ず前方誤りを修正できるわけではない。逆に後続の誤りを信じて正しい前方候補を壊す可能性もある。そこで単なるトークン単位の正解率ではなく、最初の不一致を減らし、受理接頭辞を延ばすための学習設計が必要になる。

### 3. ProposalMixによる共同学習

ProposalMixは、P1で予測した各位置の最大確率`c_i`を計算し、しきい値`η=0.5`より高い位置では**学習時の正解トークン**をP2入力に入れ、低い位置ではP1の予測トークンをそのまま使う。高信頼度の誤予測も正解に置換される一方、低信頼度の正解候補と誤り候補は残る。この混合によって、P2は信頼できる文脈を利用しながら、現実的な不完全ドラフトを修復する学習を行う。

正解トークンを混ぜるのは**学習入力の構成時だけ**である。実際の推論では未知の正解列は参照できず、直前パスのモデル予測だけを用いる。P1のargmax予測と信頼度マスクは勾配伝播から切り離し、P1とP2に対して正解位置への重み付き交差エントロピーをそれぞれ計算して合計する。先頭付近の誤りほど接頭辞検証を早く止めるため、位置の重みは`exp(-(i-1)/γ)`で減衰させる。ただし後方候補にも教師信号を与え、後続文脈として有用な予測を学ばせる。

共同学習はP1のマスクからの生成とP2の編集を**一つのモデル**で扱う。P3以降は追加の教師あり編集パスとして学習するのではなく、学習済みP2相当の編集演算を繰り返し利用する。したがってP3やP4での利得は推論時の反復によるものであり、別の編集モデルを追加学習した結果ではない。学習済みの処理を何度も反復すれば必ず速度が上がるわけではなく、追加計算の費用が最後に支配的になる。

### 4. 提案窓の拡張

基本窓幅`W=16`で収束したモデルを、`W=24`と`W=32`へそれぞれ独立に拡張し、各3,000ステップ追加学習する。窓を広げた後方位置にも教師信号を与えるため、位置減衰係数`γ`を16・24・32の窓幅に応じて7・11・15へ変更する。拡張用の20万例は主要学習コーパスから抽出される。

窓幅の拡張には二つの効果がある。対象モデルへ提出できる候補の最大数を増やす効果と、編集器が参照できる**後方文脈を増やす**効果である。DEditでは後者が重要で、単に候補を増やしたP1の受理長はほとんど伸びない一方、P2・P3の受理長は明確に増える。後方候補が有用でなければ窓を拡張しても利益はなく、追加学習と推論計算の費用が必要となる。

## 評価

### 対象モデル・ベンチマーク・実行条件

対象モデルはQwen3-4BとQwen3-8Bで、いずれも思考モードを無効化した。GSM8K、MATH-500、AIME25、HumanEval、MBPP、LiveCodeBench、MT-Benchの7課題を評価し、課題ごとの平均を等重みで集計する。主要比較用の学習コーパスはNemotron Post-Training Dataset v2とCodeAlpaca由来の約80万例であり、学習構成の除去実験には別の約10万例を使う。両コーパスを混同すると、ProposalMixの寄与と本実験の絶対速度を誤って比較することになる。

測定は**NVIDIA H100 1枚、バッチサイズ1、最大生成2,048トークン**。ドラフト生成はCUDA Graph、対象モデルの検証はeager実行であり、自己回帰基準も同じ実行方針で測る。greedyは温度0、確率的生成は温度1。確率的生成ではドラフトはargmax提案を続け、対象モデル側からサンプリングされたトークンとの一致に基づいて検証する。DFlash、Domino、DSparkの主要比較は窓幅16で、DEditは窓幅32のP3である。主表の速度差を、窓幅とドラフト演算量を厳密に揃えた比較と読まない。

| 対象モデル・greedy | 方式 | 自己回帰比の平均速度倍率 | 平均前進トークン数 τ |
|---|---|---:|---:|
| Qwen3-4B | DFlash | 4.81倍 | 5.89 |
| Qwen3-4B | DSpark | 4.99倍 | 6.91 |
| Qwen3-4B | Domino | 5.30倍 | 6.60 |
| Qwen3-4B | **DEdit P3** | **5.72倍** | **7.58** |
| Qwen3-8B | DFlash | 4.93倍 | 5.99 |
| Qwen3-8B | DSpark | 5.16倍 | 7.20 |
| Qwen3-8B | Domino | 5.56倍 | 6.79 |
| Qwen3-8B | **DEdit P3** | **5.97倍** | **7.75** |

これらは7課題マクロ平均であり、各タスクの速度がすべて5.72倍以上という意味ではない。例えばQwen3-4BのMATH-500ではDEditの速度8.18倍・τ10.67に対してDominoは7.21倍・τ8.87だったが、HumanEvalではDEdit4.95倍・τ6.48とDomino4.76倍・τ5.84で差は小さい。Qwen3-8BのMBPPではDEditのτ6.09がDSparkの6.23を下回り、HumanEval/MBPPでDSparkが上回るモデル・温度の組合せも存在する。

温度1の確率的生成では、DEditの平均速度倍率はQwen3-4Bで4.88倍、8Bで4.90倍に縮小する。greedyの5.72/5.97倍を確率的生成へそのまま当てはめられない。対象モデルの生成分布、問題の予測可能性、検証で一致する接頭辞長が結果に影響する。

### 窓幅と編集回数の切り分け

Qwen3-4B・greedyの原著Table 2(a)では、DEditのP1を窓幅16から32へ広げても平均τは**5.82→5.93**にしか伸びない。ところがP3では**6.87→7.58**となり、約10.3%伸びる。窓幅32でP2は7.12、P3は7.58であり、2回目の編集が約0.46トークンを追加する。窓幅16ではP2が6.63、P3が6.87で、同じ追加編集の利得は約0.24にとどまる。これは広い窓の後方候補が単なる追加提出候補だけでなく、前方位置を編集する文脈として効いていることを示唆する。

同じ窓幅32チェックポイントの編集回数比較（Appendix C.1）では、P1/P2/P3/P4の平均τが**5.930 / 7.123 / 7.577 / 7.770**へ増加する。一方、速度倍率は**4.737 / 5.478 / 5.724 / 5.735倍**で、P3からP4への伸びは約0.19%にすぎない。P4は測定上わずかに最速だが、著者はドラフトの前向き計算を1回減らしてP4速度の99.8%を保つP3を既定設定とする。受理長の単調増加を速度の単調な大幅改善と混同してはならない。

### ProposalMixと共同学習の除去実験

原著Table 2(b)は別の約10万例の学習条件で、同じ凍結DFlash初期提案を使って編集器の学習設計を比較する。共同学習とProposalMixの両方ありでは平均τ**5.499**、ProposalMixなしでは**5.355**、共同学習なしでは**5.414**、両方なしでは**5.242**だった。これらの数値を、約80万例の主要比較で得たτ7.58と同一の学習条件として直接比較しない。

ProposalMixの有無による編集結果の分布では、編集が受理接頭辞を短くしてしまうラウンドが**9.9%→4.7%**へ減り、5トークン以上伸ばすラウンドが**5.4%→6.7%**へ増えた。編集で受理長が増加するラウンドの比率自体は30.1%から28.8%へわずかに下がる。したがってProposalMixの主要な役割は編集の回数を増やすことではなく、既に正しい接頭辞を壊す編集を抑制し、効果の大きい修復を増やすことである。

### 後方文脈の寄与を直接調べる

後方に正しい候補が存在するほど、同じ提案列を編集したDEdit P2と因果補正器Dominoの受理長差が増える。原著Figure 3(b)では、受理接頭辞長を層別化した後、後方の正しい候補が1個増えるごとにDEditの優位が平均**0.140トークン**増え、95%信頼区間は**[0.130, 0.150]**だった。ただしこれは後方正解候補数との関連であり、単独で完全な因果効果を識別したものではない。

固定したDEdit重みと初期提案を用い、候補内の注意だけを双方向から因果マスクへ変更する介入実験では、一般7課題の先頭16候補において、双方向の方がP2で**0.222トークン**、P3で**0.290トークン**多く受理した。合成的なコピー中心タスクでは差がP2で0.724、P3で0.897とさらに大きい。先頭候補の誤り修復率と正しい接頭辞の保持率の双方で双方向が優れる。ただし編集器自体は双方向注意で学習しており、推論時だけ因果マスクへ変更することによる分布不一致が差の一部を説明する可能性がある。

## 限界・負の結果と実用判断

**比較設定の非対称性**が最大の注意点である。主要比較のDEditは窓幅32・3パス、競合方式は基本窓幅16の既定設定である。原著は窓幅を揃えた除去実験も示すが、主要な速度倍率をそのまま「同一演算量での優位」とは呼べない。加えてDEditは追加のドラフト計算を要するため、対象モデル検証が十分重く、ドラフトの追加費用を隠せる実行構成ほど有利になる。CPU側の先行enqueueとCUDA Graphを利用した今回の実装は、この費用の一部を隠している。

**本番サービングでの未検証**も重要である。評価はH100単体・バッチ1の単一要求で、連続バッチング、多数同時要求、複数GPU、複数ノード、長期的なKVメモリ競合、ドラフト学習コストの回収時間は直接測定していない。P4の受理長はP3より高くても、追加パスの壁時計利得はほぼ飽和する。確率的生成では平均倍率がgreedyより低く、コード課題では競合方式に劣る場合がある。将来の後方候補が誤っていれば編集の根拠自体が弱く、ProposalMixは有害な編集を半減させてもゼロにはしない。

**公開・再現性**について、原著v1の再現性節はコード・チェックポイント・評価スクリプトを将来公開すると述べる。今回照合した一次PDFには利用可能な公式コードURLが明記されていないため、frontmatterの`code`は推測で埋めず`null`とした。論文の数値は著者による測定であり、今回の監査は実験を再実行したものではない。

以上を踏まえると、DEditは並列ドラフトの**後続候補を前方修正に使う**という、DFlashの一括提案やDominoの因果補正とは異なる機構を提供する。重要なのは受理接頭辞の改善であり、どの実行環境でも約6倍の生成高速化が保証されるわけではない。採用時は対象モデル、候補窓幅、編集回数、ドラフトGPU費用、検証器の実行方式、負荷条件を揃えた測定が必要である。
