# Binary Block Masking：部分充填マスクを考慮するFlashAttentionのブロック実行

## 概要

Transformerの注意行列には、標準的な因果マスクだけでなく、異なる訓練系列を一つのテンソルへ詰めたpacked sequenceの境界、Longformerの局所窓、Medusa型投機的生成の候補木など、多様な構造化マスクがある。マスクで禁止されたQuery–Key組合せはsoftmaxへ寄与しないため、理論上はその演算を省略できる。しかし標準の密なFlashAttentionへ任意マスクを後付けするだけでは、禁止された領域も行列積を実行し、maskの読出しや条件分岐が増えてしまう。

SharmaとGeipingのBinary Block Masking（BinBlkMsk）は、FlashAttentionのブロック分割を活用し、**マスクに許可要素が一つもないブロックを実行せず、許可要素を含むブロックだけを処理する**方式である。任意マスクをブロックごとの0/1へ変換する前処理を行い、連続した全1領域のマスク読出しを省く派生形も導入する。疎行列の非ゼロ位置が散らばってブロック削減効果が弱い場合は、Reverse Cuthill–McKee（RCM）による並べ替えを検討する。

RTX 3060 6GB、BF16、Triton実装の注意カーネル比較では、Alpacaのpacked finetuning由来マスクで約9倍の実行時間改善を報告する。ただし比較対象のmask-unaware FlashAttentionは任意マスクを正しく反映した出力を生成しない。**9倍は特定の注意計算での速度比であり、同一正解を生成する二つのLLMサーバのTPS比較ではない。**またMedusaの小さな木マスクではPyTorch実装を基準にするなど、ケースごとに比較対象が異なる。

## 問題設定と先行方式の限界

### ブロック化された注意で「マスクを読むだけ」では速くならない

通常の注意はQ、K、Vから `softmax(QK^T/√d + mask)V` を計算する。FlashAttentionはQuery・Key・Valueをタイルに分割し、オンラインsoftmaxで注意行列全体をHBMへ書き戻さずに計算する。計算量が同じでもメモリ転送を減らすことで高性能になる。一方、任意マスクを各タイルで読み込み、禁止位置へ負の無限大を適用するだけでは、QK積そのものは残る。マスクの読み込みと条件処理の分だけ密なFlashAttentionより遅くなり得る。

マスクが疎であっても、要素単位で非ゼロが散らばっていると、どのタイルにも少なくとも一つの許可位置があり、タイル単位で省略できない。このため、疎性の比率だけでは高速化を予測できず、**どれだけのブロックが完全に0か、残るブロックの中に連続した全1領域があるか**が重要になる。

LongformerやBigBirdは注意先を局所窓・固定パターンへ制限する。MedusaやSpecInferでは投機候補の依存関係を木状マスクで表す。Packed fine-tuningでは、異なる文書のトークンが互いに注意しないよう対角ブロック状のマスクを作る。これらはマスクの形が異なり、単一の専用カーネルだけではすべてに対応しにくい。

### 正確性と高速性を区別する

原著のFlashAttentionベースラインは、任意の部分充填マスクを尊重しない。したがってベースラインの生の実行時間が短くても、対象マスクの注意を正しく計算できるとは限らない。BinBlkMskは任意マスクを正しく適用することを目的とし、Naive Attention Masking（すべてのタイルでmaskを読む単純拡張）も比較対象とする。

これは、ブロックをランダムに省略する近似注意とは異なる。全0マスクのブロックは数学的に寄与しないため省略できるが、非ゼロ要素があるブロックは内部のマスクを正しく適用する。正確なmask semanticsを維持することがアルゴリズムの要件である。

## 手法

### 1. マスクをBinary Block Matrixへ前処理する

長さNの注意マスクをQuery側ブロック幅B_Q、Key側幅B_Kに分割する。各ブロックに少なくとも一つの許可要素があれば1、全要素が禁止なら0を格納した `BinBlkMat` を作る。サイズはおおむね `ceil(N/B_Q)×ceil(N/B_K)` となり、元のN×Nマスクより小さい。

注意カーネルはQのブロックごとにKのブロックを走査し、BinBlkMatが0ならそのタイルのQK行列積・softmax更新・V積を省略する。1なら通常のブロック注意を実行し、元の要素単位maskで禁止位置を除く。BinBlkMatが1というだけで全要素を許可してよいわけではない。**ブロックの有無判定と、ブロック内部の厳密なマスク適用は二段階の処理**である。

マスクが固定ならBinBlkMatを事前計算して複数回使える。マスクが変化する場合でも、各ブロックの非ゼロ検査を並列化できる。同じマスクを多数の注意ヘッド・Transformer層が共有するなら前処理費用を償却しやすい。ただし要求ごとに異なる短いマスクを毎回作り直す場合、前処理が計算本体に対して大きくなる。

### 2. Dense Binary Block Masking：連続全1領域のmask読出しを省く

Packed sequenceの対角ブロックのように、許可位置が連続しているマスクでは、単にBinBlkMatで全0タイルを省略するだけでなく、全1の連続区間で要素単位maskを読む必要もない。原著は各Qブロックについて、連続全1ブロック数を示す`total_ones`と、その区間の開始位置を示す`offset`を作る。

Kブロックを走査するとき、`offset_i`から`offset_i+total_ones_i`の区間はすべて許可されるため、マスク読出しを省略する。区間外ではBinBlkMatを参照し、必要なブロックだけmaskを読む。これにより、HBMからのmask転送と分岐を減らす。ほぼ密なマスクでも、全1領域を素通りできる場合には密なFlashAttentionへ近い速度を保ちやすい。

この派生形は全1領域が連続しているという構造を利用する。非ゼロ位置が飛び飛びで、ほぼ全ブロックに少数の許可要素が散らばる場合、効果は限定される。連続性のない一般マスクにも正しく対応できるが、速度利得が大きいとは限らない。

### 3. 極端な疎マスクへのRCM並べ替え

非ゼロ要素がランダムに散ると、要素数としては疎でも多くのタイルが「少なくとも1要素を含む」状態になる。そこで疎行列をグラフとして見なし、Reverse Cuthill–McKee（RCM）で行・列の順序を並べ替えて非ゼロを対角付近へ集める。許可位置をより少数のタイルへ集中させれば、全0タイルを増やしてBinBlkMskの省略効果を高められる。

原著Figure 2は、RCMで必要ブロック数が約50%減る例と、合成マスクで約90%減る例を示す。ただしこれらは行列構造に依存する事例であり、任意の注意マスクで90%減らせるわけではない。Query・Key・Valueの順序と出力の復元も整合させる必要があり、並べ替えの前処理・データ移動費用を含むE2E比較が必要である。

### 4. 前処理と注意計算をどの粒度で共有するか

マスクが層間で同一なら、BinBlkMatと連続区間情報は一度生成して多層・多ヘッドへ使い回せる。原著の基本評価はbatch=4、32 attention headsであり、共有対象が多いため前処理が相対的に小さくなる。バッチ数1・ヘッド数1の単発演算では前処理の比率が大きい。これはオンラインLLMサービングの短い検証木を毎回更新する用途と、長いpacked学習を同じ倍率で扱えない理由でもある。

実装はTritonで記述され、CUDA専用の高度に調整されたFlashAttentionカーネルと同一の性能特性を持つとは限らない。原著は公平性のためTriton版FlashAttentionを比較対象に採用する。コード公開については本文で将来公開すると記されているが、確認したv2一次本文には公開済みの確定URLがない。

## 評価条件と定量結果

### 実験条件

| 項目 | 原著の設定 |
|---|---|
| GPU | NVIDIA RTX 3060、VRAM 6GB |
| データ精度 | Q/K/VにBF16 |
| 実装 | TritonのFlashAttention型注意、BinBlkMsk、Naive Attention Masking |
| 計測 | 100回の実行時間平均 |
| 基本負荷 | batch=4、attention heads=32 |
| 主なマスク | Medusa候補木、Alpaca packed fine-tuning、Longformerの窓・拡張窓・global |
| 指標 | 注意カーネルのforward/backward実行時間、mask前処理時間 |

原著の主な速度比較は注意演算に関するものであり、モデル全体の学習step時間や生成サーバのTTFT/TPOT、オンライン同時要求数を測定したものではない。Medusa候補木の例では4 heads×4 candidatesで340×340の小さいマスクを扱い、FlashAttentionが有利でないためPyTorchを基準とする。Alpaca packedとLongformerではTriton版FlashAttentionと比較する。異なる図の倍率を単純に横並びで比較してはならない。

### Alpaca packed fine-tuning

Alpacaのinstructionとinputを一つの入力にし、複数系列を一つの長い系列へpackする。系列境界を越える注意は禁止し、入力・出力を単純に連結する逐次因果マスクと、入力同士を双方向に許可し出力側を因果にする入力双方向マスクの二種類を評価する。どちらも非ゼロ領域が連続しやすく、Dense BinBlkMskの連続全1区間最適化が効く。

原著Figure 4では両マスクで**約9倍の注意演算時間改善**を報告する。これはpaddingを避けて複数系列を詰める利点と、マスクの無効ブロックを省く利点を組み合わせた結果である。注意演算の速度比を、AlpacaでLLMを完全に微調整する総学習時間の9倍高速化や、生成時TPSの9倍改善と解釈しない。またFlashAttention単体はこのマスクを正しく扱わないため、同一結果を保証するベースライン同士の厳密な速度比ではない。

### Medusa木マスクとLongformerマスク

Medusaの木マスクでは、候補トークンが祖先候補にだけ注意できるよう構造化する。候補木の枝数・深さによって許可ブロック数が変わり、BinBlkMskは無効ブロックを省略する。ただし340×340程度の小規模条件ではFlashAttention自体が有利でないため、PyTorchとの比較を行う。これを一般的な大規模LLMのMedusaデコード加速率へ直結させない。

Longformerのwindowed、dilated、globalの三マスクでも、BinBlkMskは無効ブロックを省く。windowedでは連続全1区間を利用するDense版、dilated/globalでは基本版を使う。原著Figure 5では各マスクでFlashAttention基準を上回ると報告するが、マスクの密度とブロック配置によって改善率は変わる。固定マスクを長い系列で繰り返し使う場合に前処理償却が有利である。

### 密・ほぼ密マスクでの負の結果

全1または通常の因果マスクでは、Dense版のmask読出し削減により標準FlashAttentionへ近い性能を維持する。ただし、**ほぼ全要素が許可されているのに非ゼロブロックが不連続に散るマスク**では、BinBlkMskが標準FlashAttentionより遅くなる可能性を原著は認める。マスクを正しく扱わないFlashAttentionが生の計算時間で勝っても、出力は目的のマスクと一致しない。Naive maskingを含む正しい出力同士の比較と、mask-unaware baselineとの参考比較を区別すべきである。

## 既存研究との違い・適用可能性

FlashAttentionの中心的な利点は、注意行列をHBMへ書かずにオンラインsoftmaxで計算するI/O効率である。BinBlkMskはこの性質を維持しながら、**マスクで完全に無効化されるタイルの計算自体を避ける**。両者は代替関係ではなく、同じブロック注意カーネルの異なる最適化軸である。ランダムにブロックを省く近似的なblock sparse attentionとは異なり、禁止されたブロックだけを省くためmask semanticsを保持する。

MedusaやSpecInferのような投機的デコードは、候補木の依存関係をmaskへ符号化する。この論文の方式は候補木の検証注意に使える可能性があるが、実サーバでの候補受理率、targetモデルの検証費用、draft生成費用、KV共有、連続バッチなどを合わせたE2E効果は示されていない。特に木が小さいと前処理の固定費が相対的に大きくなるため、9倍というAlpaca packedの倍率を転用しない。

Packed fine-tuningでは、同じ長いテンソルに独立系列を詰めてpaddingを減らし、系列間の情報漏洩を防ぐ必要がある。BinBlkMskはその境界を正確に尊重しながらFlashAttention型のI/O効率を利用できる。Longformerのような固定疎マスクでも、マスクを事前計算して複数層・headへ共有できる。ただし、Tritonカーネルの実装は特定GPU・ブロック幅・mask配置に依存し、既存のCUDA FlashAttention、FlashAttention-3、最新のvLLMへそのまま差し替えられるわけではない。

## 限界・未検証事項

第一に、計測対象は注意カーネル中心であり、LLM全体の学習・推論パイプラインの速度、TTFT、ITL、総TPS、複数要求間のスケジューリングを直接評価していない。モデルの重み行列積やデータ前処理が支配的な環境では、注意演算の9倍改善が総実行時間に及ぼす効果は小さくなり得る。

第二に、基本実験はRTX 3060 6GB・BF16・Triton実装である。H100、RTX 4070 Super、Ascend、AMD、CPUで同じ倍率が出る根拠はない。CUDA版FlashAttentionや最新カーネルとの厳密な比較は別途必要であり、Triton版FlashAttentionを比較対象にした結果をすべてのFlashAttention実装へ一般化しない。

第三に、ブロック単位の省略は「全0ブロックが多い」場合に効く。要素として疎でも非ゼロが全ブロックへ散る場合は利得が小さい。RCMで非ゼロを集める手法も、並べ替えと復元の費用、マスクの非対称性、動的変更への対応を要する。RCMの50～90%のブロック削減例を任意の疎マスクでの保証値として扱わない。

第四に、mask前処理は複数head・層で共有できる場合に償却される。毎回変わる小さな投機木や短い単発要求では、前処理時間が本体と同程度になることがある。原著Table 1の単一headと128head相当の比較は、共有の有無が実装上の重要な条件であることを示す。

第五に、mask-unaware FlashAttentionは一般の部分充填マスクを正しく計算しないため、単純な速度比較だけでは正しい代替方式に対する改善を証明できない。正確性を保つ比較にはNaive maskingなど、同じマスクを尊重する基準が必要である。原著の「最大9倍」はこの条件付きで読み、エンドツーエンドの性能保証として引用しない。

第六に、原著v2はコードの将来公開を述べるが、今回確認した一次本文には公開済み実装のURLがない。再現にはマスクの生成規則、ブロックサイズ、Triton版の実装、GPUのクロック・ドライバ、forward/backwardの計測境界を固定する必要がある。
