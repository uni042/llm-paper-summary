# DeepSeek-V4の圧縮注意に木構造投機的復号を適用する：枝別の因果性・状態隔離・受理後の再確定

## 書誌・位置付け

LiuとLiによる2026年9月21日公開のプレプリント（arXiv:2609.24698）。対象はDeepSeek-V4-Flashを動かすSGLang推論経路であり、既存のEAGLE/MTP系投機的復号を木構造へ拡張する際の**検証側の正しさと実行費用**を主題とする。新たな基盤モデルや学習済みドラフトを発表する論文ではなく、圧縮された履歴表現を持つターゲットモデルへ木構造の候補を安全に渡すためのシステム実装と実験である。2026年10月30日に原著PDF全11ページの方法、表1、図3・4、考察、限界を再照合した。

## 概要

通常の自己回帰生成では、ターゲットモデルが1トークンを出すたびに順伝播を実行する。投機的復号では軽いドラフトが複数候補を先読みし、重いターゲットが一度の検証で連続する候補を受理する。線形方式は候補を一本の鎖に並べるため、序盤で候補が外れると後続を活用できない。木構造方式は共通接頭辞から複数の分岐を保持し、同じ検証トークン予算で受理可能な経路を増やす。

しかしDeepSeek-V4の圧縮疎注意（CSA）と強圧縮注意（HCA）は、過去トークンのKVを独立に並べるだけでなく、オンラインで圧縮履歴を作って後続の注意へ再利用する。別の候補枝が同じ物理的バッファを更新すると、片方の枝にしか存在しないトークンの情報が他方へ混入する。著者は候補木に沿った因果検証、一時状態の隔離、受理経路だけの再確定をSGLangへ導入した。

8基のNVIDIA GPU上で、検証予算D=5、6、7、8、バッチ1〜64、GSM8K・MBPP・ShareGPTを比較した。表1ではD=8の線形受理長がそれぞれ2.842、2.678、2.393であるのに対し、木構造の代表設定は3.406、3.163、2.839に改善する。処理量の最大改善はShareGPT、D=6、バッチ4の18.5%であり、受理長の伸びがそのまま同率の処理量改善になるわけではない。D=5には負の条件もあり、D=6以降は処理量利得が頭打ちになる。

## 問題設定

### 一本の候補鎖と検証予算

EAGLE/MTP型のドラフトは、次に来るトークン候補を連続して提案する。線形鎖では先頭の誤予測によって後続候補が使えなくなるが、木構造は分岐ごとに異なる候補を残せる。ただしターゲットが一度に検証する候補数を無制限に増やすと、検証の演算量とメモリ使用量が増え、受理長の利得を打ち消す。そこで本稿は候補数をDで固定し、同じDの線形方式（top-k=1）と木構造方式（top-k=2）を比較する。候補の幅と深さの配分は、ドラフトの予測能力とターゲットの検証費用の双方に依存する。

### CSA/HCAが作る枝間の状態不整合

一般的なKVキャッシュは各トークンの状態を個別に扱えるが、DeepSeek-V4のCSA/HCAは文脈をオンラインで圧縮する。候補木をトークン順に平坦化して検証すると、物理的な順序と各トークンの論理的な祖先関係が一致しない。別の枝のトークンが見えてしまえば因果性を破り、受理されなかった枝の圧縮状態が永続キャッシュへ混ざれば次回以降の出力も汚染する。問題は単に枝を増やすアルゴリズムではなく、**ターゲット検証中に分岐した履歴を分離すること**である。

## 手法

### 1. draft extendとdraft decode：候補木の生成

最初に確定済みの接頭辞からドラフトを延長し、候補トークンを親子関係付きの木へ配置する。候補の数は検証予算Dを超えないよう枝刈りする。たとえば` s4_k1_d5 `は4ドラフトステップ、幅1、予算5の線形鎖であり、` s4_k2_d5 `は同じステップ数と予算で幅2の枝を持つ。候補木は単なるトークン集合ではなく、各トークンがどの親に従属するかを持つ。draft decodeでは候補の特徴表現を計算するが、ここで生成された全枝を確定した文脈として扱ってはいけない。

### 2. verify preprocess：論理的な祖先と物理配置を結ぶ

ターゲット実行の前に検証前処理を行い、候補木から必要な候補鎖、親子関係、因果的に可視な先祖集合、ターゲット検証用のメタデータを組み立てる。ターゲットが一括で複数枝を評価しても、ある枝のトークンはその枝の祖先だけを参照し、兄弟枝の情報を参照しないようにする。DeepSeek-V4の圧縮注意では、通常の三角因果マスクだけでは枝の祖先を表現できないため、枝別の因果可視性を明示的に保つ必要がある。検証前処理の出力が後続のターゲット検証へ渡される。

### 3. target verify：一時領域に分岐状態を隔離

ターゲットモデルは候補木を枝別の因果制約のもとで検証する。候補に対応するKVとCSA/HCAの圧縮履歴は、確定済みの永続キャッシュへ直接書き込まず、scratch領域に一時保存する。これにより、ある候補枝の圧縮更新が別枝の履歴へ漏れず、拒否された候補の状態も後続の生成へ持ち越されない。scratchの管理は通常の線形検証より余分な作業であり、枝数が増えるほど状態の分離・整理費用がかかる。したがって木の受理長が長くなっても、必ずしもターゲット実行時間が同率に短くなるわけではない。

### 4. accepted-path selectionと状態の再確定

検証結果から受理された経路を選択した後、**その経路に属するトークンだけ**を永続状態へ反映する。原著Figure 2では、KVに加えてCSA/HCAの圧縮状態、C4/C128固有の状態更新を受理経路に合わせてrefreshする。拒否された枝のscratch状態は破棄する。これによって次回のドラフト生成は、実際に受理された接頭辞に整合するKV・圧縮履歴から開始できる。候補木生成、検証前処理、枝別ターゲット検証、受理経路の再確定、次回SGLangスケジューリングという一巡が、著者の三段階投機的forwardの実体である。

### 5. 方式が効く条件と追加費用

幅を増やすと同じDで異なる候補経路を検証でき、先頭誤予測の影響を緩和する。しかし木の構築、分岐用のメタデータ、scratch領域、受理後の状態refreshが追加される。Dが小さいと分岐に使える余剰候補数が少なく、ほぼ線形鎖と同じ受理長なのに管理費用だけ増える。逆にDを増やしすぎると検証が計算律速に近づき、受理長が伸びても実際のトークン処理量が伸びにくくなる。著者はドラフト側の深さ適応（DSpark等）と検証側の圧縮状態管理は別の最適化軸であり、両者を共同で調整する余地があると位置付ける。

## 評価

### 測定環境・比較設計

| 項目 | 原著の条件 | 解釈 |
|---|---|---|
| ターゲット | DeepSeek-V4-Flash | 圧縮注意CSA/HCAを持つ特定実装 |
| ハードウェア | NVIDIA GPU 8基のマシン | GPU型番・相互接続の細部を原著は十分に開示しない |
| 検証予算 | D=5、6、7、8 | 線形と木構造で検証トークン数を一致 |
| バッチ | 1、2、4、8、16、32、64 | 受理長と実行処理量の依存性を分離 |
| タスク | GSM8K、MBPP、ShareGPT | 数学、コード、対話の生成特性を比較 |
| 主要指標 | 平均受理長、デコード処理量の相対変化 | 出力品質の正答率・電力・TTFTは主指標ではない |
| 比較方式 | top-k=1の線形鎖とtop-k=2の候補木 | 同一Dで候補の形だけを変更 |

受理長は1回の検証で平均何トークンを確定できるかを測る。一方、デコード処理量は一定時間内に実際に処理できた生成トークン数に関する指標であり、検証に追加の計算や状態管理が発生すれば受理長だけでは決まらない。原著は絶対的なtokens/sよりも、同じDの線形方式に対する相対改善を中心に報告する。したがって18.5%は特定設定の相対処理量改善であり、全てのGPU・バッチ・タスクで同じ改善を保証しない。

### 表1：受理長の定量比較

| D | 線形 GSM8K / MBPP / ShareGPT | 木構造の代表設定 | 木構造 GSM8K / MBPP / ShareGPT |
|---|---|---|---|
| 5 | 2.836 / 2.663 / 2.389 | s4_k2_d5 | 3.154 / 2.935 / 2.667 |
| 6 | 2.841 / 2.669 / 2.392 | s4_k2_d6 | 3.274 / 3.044 / 2.754 |
| 7 | 2.845 / 2.672 / 2.392 | s4_k2_d7 | 3.361 / 3.129 / 2.809 |
| 8 | 2.842 / 2.678 / 2.393 | s5_k2_d8 | 3.406 / 3.163 / 2.839 |

これらはバッチ1〜64の平均値で、個々のバッチでの受理長の変動幅は0.04未満と報告される。D=8のGSM8Kでは2.842から3.406へ約19.8%、MBPPでは2.678から3.163へ約18.1%、ShareGPTでは2.393から2.839へ約18.6%増える。絶対受理長はGSM8Kが高くShareGPTが低いが、相対的な木構造の利得は三タスクで近い。木の深さをさらに増やしても受理長がほとんど増えず、同一予算では浅く幅のある木が有利な範囲がある。ただしドラフト自体の能力が上がれば適切な深さも変わり得る。

### 図4：処理量の改善と悪化条件

原著のデコード処理量改善はD=5では平均約3〜5%、D=6では約8〜9%、D=7・8では約9〜10%で頭打ちになる。最大値はShareGPTのD=6、s3_k2_d6、バッチ4で+18.5%。一方、GSM8KのD=5、s4_k2_d5、バッチ1では−2.0%、MBPPの同設定・バッチ1では−1.5%、MBPPのバッチ64でも−0.8%となり、木構造が常に勝つわけではない。これは小予算では受理長の改善が枝別検証・状態隔離の追加費用を相殺できないことを示す。

D=6では浅い木のs3_k2が平均約13%の処理量改善、s4_k2が約9%、s5_k2が約4%となる。受理長は深さによって大きく変わらないので、追加の直列ドラフトステップが実行費用として効く。バッチ依存は逆U字で、D=6の平均利得はバッチ1で約8%、バッチ4で約11%、バッチ64で約7%と報告される。小バッチではターゲットのメモリ律速を受理長で償却しやすいが、大バッチでは検証する候補数が計算負荷となる。これらは同じ8GPU実験環境内の傾向であり、汎用のサービス負荷モデルへそのまま外挿しない。

### 何が検証され、何が検証されていないか

同一検証予算で木構造が線形より長い受理経路を得るという主張は、表1と図3で確認できる。追加管理費用を差し引いても処理量が改善する条件があることは図4で示される。ただし、本稿の実験は圧縮状態の枝間汚染が実際に起きた場合の誤差率を定量測定したアブレーションではなく、枝別状態を正しく扱う実装を前提に性能を比較する。状態隔離を外した実装との品質比較や、長期連続稼働時のP99遅延、TTFT、電力、メモリピーク、異種GPU間の比較は主要結果として提示されていない。生成内容のタスク正答率も主たる測定軸ではない。

## 限界・負の結果

第一に、最大18.5%の処理量改善はShareGPT、D=6、バッチ4の特定設定であり、平均値ではない。D=5には負の結果があり、Dを増やしてもD=6を超えると平均処理量改善はほぼ頭打ちになる。受理長を最大化することとデコード処理量を最大化することは異なる最適化問題である。

第二に、CSA/HCAの圧縮履歴を持つDeepSeek-V4-Flashの実装に合わせた状態管理であり、一般的なKVキャッシュを持つモデルへ同じ処理をそのまま移植する意味はない。別の圧縮・疎・階層注意では、どの状態をscratchに隔離し、受理後に再確定するかを個別に設計する必要がある。枝の幅が大きくなるとメタデータとscratch状態の管理費用も増える。

第三に、評価対象は3タスク、D=5〜8、バッチ1〜64、8GPUの単一系統であり、広いモデル規模、ネットワーク帯域、複数ノード、他の推論フレームワーク、運用中の要求混合、厳密なSLOへの一般化は未検証である。原著はターゲット検証側の実装知見を提供するが、全ての実サービスで木構造を常時有効化すべきだとは示していない。

## 既存研究との差・研究上の意味

SpecInfer、EAGLE-2、Sequoia等は候補木の生成や枝の選択を扱う。本稿の焦点は、候補木ができた後に**圧縮された履歴状態を持つターゲットへどう渡すか**である。DSparkはドラフト側の候補生成費用と深さの調整を主に扱うため、著者は両者を相補的とみなす。原著の観測からは、ドラフトの予測可能性、検証予算、木の深さ・幅、バッチによる計算律速の変化を一緒に最適化する必要がある。実装上の核心は、受理前の分岐状態を永続キャッシュへ混ぜないという整合性境界である。
