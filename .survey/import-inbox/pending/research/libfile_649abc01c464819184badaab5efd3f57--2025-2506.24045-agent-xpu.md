# Agent.xpu: Efficient Scheduling of Agentic LLM Workloads on Heterogeneous SoC


> 異種実行グラフとkernel粒度preemptionでNPU・統合GPUを段階別に協調させ、個人端末の反応型／能動型LLMフローを同時に処理する。

## 概要

個人端末のLLMエージェントでは、ユーザー操作に即応する反応型フローと、通知監視や情報整理のように背後で継続する能動型フローが同居する。前者は遅延が重要で、後者はスループットを重視する。従来の端末向け推論エンジンは単発要求や単一アクセラレータを前提にし、この混合重要度を扱いにくい。

Agent.xpuはCPU、統合GPU（iGPU）、NPUが共有DDRを使うSoCを実測し、演算子ごとのアクセラレータ適性、NPU/iGPU同時実行時の非対称な帯域競合、プリフィルとデコードで異なるbatch特性を抽出する。その結果を異種実行グラフ（heterogeneous execution graph; HEG）へ埋め込み、実行時に演算chunkをNPUまたはiGPUへ弾性的に割り当てる。

ランタイムは反応型を優先しつつ、kernel粒度のpreemptionとslack-aware piggybackingで空き時間へ能動型処理を差し込む。混合負荷では反応型平均遅延を91〜97%削減し、能動型throughputも基準比0.3〜58%改善する。別集計では能動型throughputが1.2〜4.9倍、iGPU利用率32.5〜37.1%削減、エネルギー効率26.8%改善と報告される。

## 問題設定

NPUは行列演算の効率が高い一方、静的形状や事前compileへの依存が強い。iGPUは動的shapeやcontinuous batchingに柔軟だが、消費電力が大きく、画面描画とも資源を競合する。単純にNPUだけ、iGPUだけへ固定すると一方の長所を使えない。

さらに両アクセラレータは共有DDRへアクセスする。実測では同時GEMM/GEMV時にNPU GEMVが12.0%、iGPU GEMMが37.3%低下する例があり、「空いている計算器へ仕事を投げる」だけでは帯域競合で逆効果になる。

プリフィルは単要求でも飽和しやすく、デコードは複数要求のbatch化が効く。したがって要求優先度だけでなく、推論段階と演算子特性まで含めて配置を変える必要がある。

## 手法

### 異種実行グラフ HEG

offline profilingで各演算groupのNPU/iGPU性能、転送・帯域特性を測り、HEGへ実行候補と予測costを注釈する。線形演算とLayerNorm、SwiGLU等をgroup化し、細かすぎるaccelerator往復を避ける。

token方向の演算はelastic chunkとしてcompileし、実行時にbackendとchunk sizeを変えられるようにする。動的sequenceへ強く依存する多頭注意はiGPU側へ寄せる。HEGは「モデルgraph」だけでなく「どの演算をどのxPUへ動かせるか」をschedulerへ渡す。

### 段階弾性 NPU-iGPU協調

プリフィルでは反応型要求にNPU+iGPUの弾性tensor並列を使い、初回トークン時間を短縮する。能動型プリフィルはNPU中心へ寄せ、iGPUを反応型やgraphicsへ残す。

デコードはsequence長が反復ごとに変わるためiGPUのcontinuous batchingへ集約する。これによりNPUの静的実行効率とiGPUの動的batch能力を、同じ要求の異なる段階で使い分ける。

### kernel粒度preemption

反応型要求が到着すると、能動型を要求単位で丸ごと中断するのではなく、現在kernelの終了点でpreemptする。chunkingにより個々のkernelを短くし、反応型が待つ最大粒度を抑える。

状態は共有メモリに残るため、能動型の計算を捨てず後から再開できる。単純なkill/restartより無駄計算を減らし、反応型のtail latencyを隔離する。

### slack-aware backfillと帯域認識dispatch

反応型要求のdeadlineまでに余裕がある区間を見つけ、能動型kernelをbackfillする。DDR圧力推定器が高負荷ならNPU/iGPUの同時実行を抑え、低負荷なら積極的に重ねる。

この制御により「優先要求を守るため背景処理を完全停止」せず、deadline slackとメモリ帯域を同時に使って能動型throughputを維持する。

## 評価条件

| 項目 | 内容 |
|---|---|
| ハードウェア | Intel Core Ultra系のCPU + NPU + iGPU共有メモリSoC |
| workload | 反応型 + 能動型のpersonal-agent混合負荷 |
| 比較 | 産業iGPU-only engine、NPU-iGPU静的tensor partition等 |
| 指標 | 反応型平均/P90遅延、能動型throughput、iGPU利用率、J/token |
| 推論段階 | prefillとdecodeを別配置・別batch方針で評価 |

## 主要結果

| 条件 | 結果 | 意味 |
|---|---:|---|
| 混合負荷 | 反応型平均遅延 91〜97%削減 | kernel粒度preemptionが背景負荷から前景要求を隔離 |
| 混合負荷 | 能動型throughput +0.3〜58% | 前景優先でもslack backfillで背景処理を維持 |
| 総括比較 | 能動型throughput 1.2〜4.9倍 | 静的/single-accelerator基準より資源利用を改善 |
| 資源 | iGPU利用率 32.5〜37.1%削減 | NPUへ適切な演算を逃がしgraphics競合を抑制 |
| エネルギー | J/token 26.8%改善 | iGPU過使用を避ける効果 |
| 同時GEMM/GEMV profile | NPU -12.0%、iGPU -37.3% | 帯域認識dispatchが必要な根拠 |

## 既存研究との差

クラウドLLM schedulerは独立GPUと高帯域相互接続を前提にしやすい。Agent.xpuはNPUとiGPUが同じDDRを奪い合い、graphicsとも競合するconsumer SoCを対象にする。

端末向け静的tensor partition方式とも異なり、要求の優先度、prefill/decode段階、DDR圧力に応じて実行graph上のmappingをrun-timeで変える。固定分割ではなくflow-level concurrencyが主対象である。

## 限界

評価は特定のIntel Core Ultra系SoCとそのNPU/iGPU特性に依存する。別vendorのNPU、離散GPU、専用HBMを持つ環境ではoffline profileとmappingを作り直す必要がある。

HEGのoffline profilingと複数backend compileが必要で、未知演算やmodel更新には準備費用がある。主評価は個人端末の少数混合フローであり、データセンター級の大batch・多数GPUクラスタを対象にした結果ではない。
