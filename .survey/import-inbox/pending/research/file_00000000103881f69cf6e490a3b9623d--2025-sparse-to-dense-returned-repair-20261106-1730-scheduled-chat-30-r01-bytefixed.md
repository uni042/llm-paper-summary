# Sparse-to-Dense: 動画LLMにおける疎注意ドラフトと完全注意検証

## 概要

本論文の対象は、動画の多数の視覚トークンを入力する大規模視覚言語モデルの**出力生成段階**である。動画の長さに伴って視覚トークン数が増え、復号時に過去の全トークンのキー・値（KV）を繰り返し読むと、メモリ帯域が律速となる。論文では視覚トークンが一万個以上になり得る一方、テキストトークンは百個程度という非対称性を動機にしている。入力の動画フレームを削除して質問応答の精度を近似的に維持する方式ではなく、**元の完全注意モデルで検証した出力を維持する**投機的復号を採用する点が重要である。

Sparse-to-Dense（StD）は同じモデルの重みを用いながら、疎注意で速く候補トークンを作るドラフト経路と、完全注意で候補を並列検証するターゲット経路を使い分ける。別の小型ドラフトモデルを訓練・常駐させる必要がなく、モデルパラメータ用の追加GPUメモリを避けられる。ただし、**全KVキャッシュそのものはGPU HBMに保持**するため、KV容量の削減やCPUオフロードを達成した論文ではない。削減するのは主にドラフト経路でのKV読み出し量である。

## 問題設定と観察

完全注意による自己回帰復号では、新しいトークンを一つ出すたびに、過去の動画・テキストのKVを参照する。動画由来の長い系列は各段階の読み出しを重くする。単純にKVを疎化したモデルだけで生成すれば高速になるが、選択しなかったトークンに依存する予測を失う可能性がある。したがって疎注意の近似出力をそのまま最終回答とするだけでは、元モデルと同じ出力を保証できない。

著者らはQwen2-VL-7Bを用いてMLVUおよびVideo-MMEの抽出例で観察し、上位の注意重みを持つ視覚KVだけを残した場合でも、次トークン予測が元モデルと一致する割合は平均95%超と報告する。この95%は**各トークン単独**の一致であり、連続した複数トークンがすべて一致する確率ではない。独立近似で5トークンなら0.95の5乗、約77%に下がる例を本文は挙げる。この性質こそ、疎注意のみで完結させず完全注意による検証を残す理由である。

## 手法

### 1. prefill時のテキスト誘導型視覚KV選択

入力を視覚トークン集合と後続のテキストトークン集合に分ける。prefill時に各テキストトークンから各視覚トークンへの注意重みを観測し、層ごとにテキスト側で平均した視覚トークンの注意得点を求める。その得点が高い上位K個の視覚トークンのKVをドラフト用に選択する。これにより、質問文などのテキストに関連しやすい動画部分を、動画全体の均一な間引きではなく**入力依存の注意分布**から特定する。

選択集合は層・KVヘッドによって異なり得る。Grouped Query Attention（GQA）の場合は同じKVヘッドを共有するクエリヘッド群の注意得点を集約して選択する。異なる層やヘッドの着目先を同一のグローバル集合へ無理に固定しないことが特徴である。選択はprefill時に一度行い、復号の各ステップで全視覚トークンを再評価する高価な動的選択を避ける。代償として、生成途中で質問への注目先が変化しても初期の視覚KV集合をそのまま使うことになる。

### 2. 疎注意ドラフトの自己回帰生成

元のモデルを完全注意モデルM、同一重みで選択済み視覚KVだけを読むモデルを疎注意モデルMsとする。Msは直前までに確定した文脈から、次の候補をγトークンだけ逐次生成する。視覚側では選択されたK個のKV、テキスト側では必要なテキストKVを参照する。多数の視覚KVを毎トークン読み直す完全注意に比べて、この経路の読み出し量は小さい。

ただし疎注意ドラフトは近似であり、生成した候補が完全注意の予測と異なることがある。疎経路での予測がどれほど正しいかは、視覚KV選択の妥当性と、複数候補の連続一致率に依存する。高速なドラフト生成だけを評価してもエンドツーエンドの改善は決まらず、後続の検証費用と受理長が重要になる。

### 3. 完全注意による並列検証と確定

完全注意のMが、ドラフトしたγトークンをまとめて並列検証する。候補列の先頭から元モデルの予測と一致する部分だけを受理し、最初の不一致以降は捨てる。検証で得られる元モデル由来の追加トークンも確定文脈へ付け加え、次のドラフトと検証を繰り返す。この手続きは、疎注意の誤予測が最終系列にそのまま残らないようにするためのものだ。

完全注意の検証は一度に複数候補を扱うので、全KVの読み出しを候補トークンごとに独立に繰り返すより効率化できる。論文の「lossless」は、疎注意で作った不正確なトークンを無検証で採用しない、という投機的復号の性質を指す。数値演算の実装差やサンプリング乱数の取り扱いまで無条件に全環境でビット単位同一と実証した意味には拡張しない。

### 4. KV読み出し量と成立条件

論文の簡略化したI/Oモデルでは、動画トークン数mv、テキストトークン数mt、選択視覚KV数K、ドラフト長γとすると、ドラフト読み出し量はγ(K+mt)、完全注意検証はmv+mtとなる。受理率をαとした平均読み出し量は、論文の近似で [γ(K+mt)+mv+mt]/(αγ) と表される。通常の完全注意の一トークン当たり読み出し量はmv+mtである。

したがって平均読み出し量の改善には、αが (K+mt)/(mv+mt)+1/γ より大きいことが必要となる。Kを小さくすればドラフトは軽くなるが、予測不一致が増えてαが下がり得る。逆にKを大きくすると候補は正確になるものの疎注意の利得が減る。γも長くすれば検証の償却が進むとは限らず、不一致後に捨てる候補が増える。理論式はKVアクセス量の説明であり、実時間の速度比はカーネル、バッチ、検証計算なども含めて実測で判断する必要がある。

## 評価条件と主要結果

実験はHugging Face Transformers上の実装で、NVIDIA A100 80GB GPUを使用する。モデルはLLaVA-OneVision-7BおよびQwen2-VL-7B-Instruct。動画理解データセットはMLVUとVideo-MMEの短・中・長動画区分を用いる。動画LLMにはchain-of-thought応答を促す。本文の主要設定はバッチサイズ8、Kとテキストトークン数の合計を1024、完全注意で一度に検証する候補長γ=9。実験は異なる乱数種で3回繰り返し、平均を報告する。

表1のAcc.は**ドラフト候補の受理率**であり、動画質問応答の正解率ではない。各方式は完全注意検証を使うため、著者らは最終回答の品質比較をこの表に載せていない。Speedupは通常復号を基準にした壁時計時間の倍率である。

| モデル・データセット | 方式 | ドラフト受理率 | 壁時計時間高速化 |
|---|---|---:|---:|
| Qwen2-VL-7B / MLVU | StD | 66.1% | **1.94倍** |
| Qwen2-VL-7B / MLVU | Streaming | 53.9% | 1.61倍 |
| Qwen2-VL-7B / MLVU | LayerSkip | 5.2% | 0.63倍 |
| Qwen2-VL-7B / Video-MME長 | StD | 81.8% | 1.70倍 |
| Qwen2-VL-7B / Video-MME長 | Streaming | 59.6% | 1.36倍 |
| LLaVA-OneVision-7B / MLVU | StD | 47.8% | 1.72倍 |
| LLaVA-OneVision-7B / Video-MME中 | StD | 52.1% | 1.83倍 |
| LLaVA-OneVision-7B / Video-MME長 | StD | 52.9% | 1.59倍 |

Qwen2-VLのMLVU条件でStDの1.94倍は、Streamingの1.61倍より高い。疎注意によるドラフト候補の一致率が高いほど、完全注意の一括検証を有効活用できるという機構を裏付ける。LayerSkipはドラフト単体が軽くても受理率が極端に低く、検証を含めると通常復号より遅い条件がある。これは、ドラフトを速くするだけでは十分でなく、元モデルとの予測分布の整合が重要であることを示す。

一方、MLVUにおけるLLaVA-OneVisionの受理率47.8%でも1.72倍となっており、受理率だけから実時間を一意に推測できない。モデル、動画長、疎注意の実行コスト、検証の並列性によって倍率は変わる。本文が示す平均受理長の比率62.2%と平均1.74倍という記述も、特定モデル・データセットの最大1.94倍とは区別する必要がある。

## 既存研究との差

従来の投機的復号では小型の別モデルをドラフトに使うことが多く、モデル重みの追加配置と訓練が必要になる。StDは**同一重み・異なる注意範囲**を利用するため、追加モデル重みを持たずにドラフトを構成できる。LayerSkipをドラフトにする比較では、層を飛ばすことによる予測差が大きく、受理率が下がる。Streaming型の疎注意ドラフトと比べても、StDはテキスト側の注意を使って視覚KVを選択するため、動画質問との関連性を反映できる。

通常のKV圧縮やトークン削除は、近似出力のまま最終回答を生成して品質が変わり得る。StDは疎注意を最終回答の生成器ではなく候補生成器として使い、完全注意を判定者にすることで、この品質と速度のトレードオフを変える。追加学習なしで既存の動画LLMへ組み込みやすい点は運用上の利点だが、実際の導入ではprefill時の注意統計の取得、層・ヘッド別の選択KVの管理、ドラフトと検証の制御が必要である。

## 限界と未評価事項

最大の限界は、**全KVキャッシュをHBMに保存し続ける**ことである。疎注意のドラフトは読み出し帯域を節約しても、動画の長さとバッチ数に比例してKV保存容量が増える問題を解決しない。論文もCPU側へのKVオフロードを将来課題として挙げているが、現行StDの実証結果ではない。

選択集合をprefillで固定するため、生成中に必要な視覚的証拠が移る場合はドラフトの一致率が下がり得る。長いドラフト列で一度誤予測すると後続候補が破棄され、候補生成の無駄が増える。K、γ、入力の視覚・テキスト比率の設定はI/O利得と受理率の両方を左右する。実験はA100 80GB、7B級の動画LLM、指定されたバッチとベンチマークに限られ、他GPU、異なる推論エンジン、大規模MoE、長い推論連鎖、CPUオフロード条件への性能外挿はできない。

また、本論文の評価は復号の壁時計時間とドラフト受理率を中心とする。全GPUメモリの削減、サービス全体の同時接続数、TTFT/TPOTのSLO達成、消費電力の低下を実証したものではない。最大1.94倍をすべての動画長・モデル・環境での保証値として扱わない。
