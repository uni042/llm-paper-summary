## 概要

通常の低bit KV量子化は保存容量を減らしても、attention scoreを計算する直前にkeyをFP16へ逆量子化し、全key vectorを演算器へ読み込む。このためedge deviceのようにDRAM帯域が小さい環境では、保存bit数ほどattention帯域が減らない。LOOKATは`QK^T`がqueryに対するinner-product similarity searchであることを利用し、vector databaseのproduct quantization（PQ）とasymmetric distance computation（ADC）をattentionへ持ち込む。

key vectorを複数subspaceへ分け、各subspaceを学習済みcodebookのindexだけで保存する。query到着時にはquery subvectorと全centroidの内積を小さいlookup tableへ先に計算し、各tokenのkey scoreは保存indexで表を引いて加算する。圧縮keyをFP16へ展開しないため、key帯域を直接減らせる。

## 問題設定

自己回帰decodeでは過去tokenのkey/valueを毎step参照するため、context lengthに比例してKV cacheの読み出し量が増える。INT4/INT8 scalar quantizationはcache storageを圧縮できるが、標準GEMM/attentionへ入れる前のdequantizationと展開後データ移動が残る。

LOOKATの狙いはkeyの数値を高精度に復元することではなく、attentionで重要な「どのkeyがqueryと近いか」という順位構造を圧縮表現のまま再現することにある。

## 手法

### Product Quantization

d次元keyをm個のsubvectorへ分割し、各subspaceにK個のcentroidを持つcodebookを学習する。各key subvectorは最も近いcentroidのindexだけを保存する。たとえば1-byte indexなら、FP16の64次元key全体を読む代わりに少数byteを読む。

### Asymmetric Distance Computation

queryは量子化せず高精度のまま使う。各query subvectorとcodebook centroidの内積を事前に`m×K`個だけ計算してlookup tableへ置く。tokenごとのattention scoreは、そのtokenが持つm個のcode indexで表を引き、値を加算して近似する。

この構造では全tokenのfull keyをDRAMから読む必要がなく、帯域costは主にcode index列になる。代わりにqueryごとのtable作成とlookup/addの計算が増え、memory-bound attentionをcompute寄りへ移す。

## 評価条件

| 項目 | 条件 |
|---|---|
| model | GPT-2 |
| 対象 | attention key cache |
| context | 最大1024 tokenまで検証 |
| 比較 | FP16、INT4/INT8 scalar quantization |
| 指標 | output cosine fidelity、KL divergence、Spearman rank correlation、top attention保持 |
| training | model retrainingなし、codebook calibrationのみ |

## 主要結果

64倍key圧縮のLOOKAT-2でoutput cosine fidelity 95.7%、32倍圧縮のLOOKAT-4で95.0%を報告する。全LOOKAT設定でattention rankingのSpearman相関は概ね0.95を超え、keyの絶対値再構成よりranking保持を狙う設計が機能する。

一方、context lengthを64から1024へ伸ばすとfidelityは低下し、長文脈ほど近似誤差が蓄積する。1024 tokenでもrank correlationは高い水準を保つが、評価はGPT-2規模であり、現代LLMの数万〜百万token contextを実証したものではない。

## 既存研究との差

KIVI等のscalar KV量子化はkey/valueの各数値を低bitへし、attention計算時に数値表現へ戻す。LOOKATはkeyをvector-search codeへ変換し、復元せずlookup tableから内積近似値を直接得る。このため「storage圧縮」だけでなくkey read bandwidthそのものを減らすことを目的にする。

## 限界

現行評価ではvalueはFP16のままで、KV cache全体が64倍になるわけではない。codebook品質はcalibration dataへ依存し、長contextではfidelity低下が観測される。また高速lookupを活かす専用kernel/NPU実装の実測latencyは十分検証されておらず、64倍という値はkey storage圧縮率であってend-to-end speedupではない。
