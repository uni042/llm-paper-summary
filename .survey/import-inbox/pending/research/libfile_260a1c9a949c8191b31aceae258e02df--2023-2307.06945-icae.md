# In-context Autoencoder for Context Compression in a Large Language Model

## 概要
長文脈LLMは入力token数に比例してprefill計算とKVキャッシュを増やす。文書を単純要約するとtoken数は減るが、後続taskに必要な細部を自然言語要約へ落とせない場合がある。In-context Autoencoder（ICAE）は、長いcontextを通常のtext tokenではない少数の学習済みmemory slotへ圧縮し、その連続表現を同じLLMが後続生成の条件として直接読む。

ICAEはLlamaを基盤に約1%の追加parameterで構成され、まずautoencodingと言語modelingの二目的で大量textを学習し、contextの内容をmemory slotへ詰める。その後instruction dataでfine-tuneし、圧縮memoryと質問から回答を生成できるようにする。論文は4倍context compressionを達成し、通常contextを直接入力する場合より推論latencyとGPU memoryを改善すると報告する。

## 問題設定
通常のTransformerではcontextをそのままtoken列として保持するため、同じ長文書を複数回利用すると毎回長いprefillが必要になる。KVキャッシュもtoken数に比例して増える。context windowを拡張するだけでは、保持できる長さは増えても計算・memory費用は解決しない。

必要なのは、後続LLMが意味情報を利用できる形でtoken列を短い内部表現へ変換することである。自然言語要約と異なり、ICAEは「人間が読める短文」を作る制約を持たず、LLMのhidden space上のmemory slotへ情報を圧縮する。

## 手法

### memory slotへの圧縮
ICAEは入力contextの後ろに少数の特別memory tokenを置き、encoder側処理で各memory tokenのhidden stateへcontext情報を集約する。このhidden stateを圧縮表現として保存し、元のcontext token列を後続LLMへ渡す代わりに使う。

圧縮率は元token数とmemory slot数の比で決まる。4倍圧縮なら、後続処理が読む条件系列をおおむね4分の1へ減らせる。これによりprefill attentionとKV保存対象を短くできるが、圧縮段階そのものの計算は必要である。

### autoencoding目的
事前学習の一つは、memory slotだけを条件に元contextを再構成するautoencodingである。圧縮表現が表面的なtopicだけでなく、元textを復元するのに必要な情報を保持するよう学習させる。

復元能力を強く要求することで、特定QA taskだけに必要な特徴へ過度に特化するのを避ける。一方、有限slotへ全情報を完全保存することはできず、圧縮率を上げるほど再構成誤差との交換条件が強くなる。

### language-modeling目的
もう一つの目的では、contextをmemoryへ圧縮した後、そのmemoryを条件に後続textを予測する。これは「元文を復元できる」だけでなく、「通常のLLM条件文脈としてmemoryを使える」ようにする役割を持つ。

autoencodingとlanguage modelingを組み合わせることで、memory slotを単なるencoder bottleneckではなく、生成LLMが直接消費できるin-context表現へする。基盤LLM全体を大きく作り直すのではなく、追加parameterは約1%に抑える。

### instruction fine-tuning
事前学習後、instruction dataでfine-tuneし、圧縮contextと質問・命令から望ましいresponseを生成するよう適応する。推論時にはcontextを一度memory slotへ圧縮し、そのslotとpromptをLLMへ条件として与える。

同じcontextを複数queryで再利用できる場合、圧縮memoryを使い回せれば長contextを毎回token列として再prefillする費用を避けられる。ただし論文の中心は表現学習であり、大規模multi-user serving cacheのschedulerまでは扱わない。

## 主要結果
|条件|結果|意味|
|---|---:|---|
|代表設定|4倍context compression|長contextを少数memory slotへ縮約可能|
|model overhead|約1%追加parameter|独立した大型encoderを追加しない|
|推論|latency改善|後続LLMが読む条件系列短縮が計算量へ反映|
|推論|GPU memory改善|短いmemory slotによりcontext保持費用を削減|

論文は圧縮memoryが単なる要約ではなく、元contextのmemorizationとinstruction応答の双方へ使えることを評価する。4倍という値は「weightを4分の1にする」のではなく、context representationの長さを4分の1相当へする圧縮率である。

速度面でも、contextを圧縮するencoder処理を含めるか、圧縮memoryを複数queryで再利用するかでend-to-end利得は変わる。したがってserving systemとしてのthroughput倍率と解釈してはいけない。

## 既存研究との差
自然言語summarizationは人間可読textへ圧縮するが、ICAEはLLM hidden state上のmemory slotへ圧縮するため、語彙tokenとして表現しにくい情報も保持できる。prompt compressionでtokenを選択・削除する方式とも異なり、複数tokenの情報を新しい連続表現へ集約する。

長context modelそのものを拡張する方式は元tokenを保持してattentionするが、ICAEは後続計算が見るsequenceを短くする。KV evictionとは異なり、過去tokenを重要度で捨てるのではなく、学習されたencoderでcontext全体を固定数memoryへ写像する。

## 限界
圧縮はlosslessではなく、memory slot数を減らすほど細部の復元・下流task品質が悪化し得る。圧縮器を学習するための追加pretraining/fine-tuningも必要で、既存任意LLMへ完全なtuning-free方式として適用するものではない。

一度しか使わない短contextでは圧縮処理の追加費用を回収しにくい。大規模servingでのcache eviction、multi-tenant scheduling、CPU/SSD offload等も論文の直接対象ではないため、4倍context compressionからproduction throughputを推定してはいけない。
