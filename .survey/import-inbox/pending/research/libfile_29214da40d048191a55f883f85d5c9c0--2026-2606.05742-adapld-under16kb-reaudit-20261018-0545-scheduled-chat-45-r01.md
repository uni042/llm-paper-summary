# AdaPLD：完全一致失敗の救済と分岐再利用による補助モデル不要の投機的復号

## 書誌・対象と再監査の境界

本稿はLiuらの2026年6月4日公開の一次論文「AdaPLD: Adaptive Retrieval and Reuse for Efficient Model-Free Speculative Decoding」（arXiv:2606.05742）に基づく。対象は自己回帰言語モデルの復号であり、入力文とそれまでに生成したトークンを再利用して次の候補を作る、補助ドラフトモデルを持たない投機的復号（model-free speculative decoding）である。対象モデルの重みを追加学習する方法でも、別の小型モデルを常駐させる方法でもない。既存の主流の一トークンずつの生成と同じ対象モデルを使い、候補木の検証によって一回の対象モデル順伝播で複数トークンを確定できる機会を増やす。

この再監査では既存GitHub論文の主要主張と定量結果を一次論文の方法節・実験節・限界節に照らして確認し、検索退避が発火する条件、分岐の構築、後続の一段拡張、対象モデルによる検証、負の結果の条件を明示した。従来原稿が既に良好な説明を含んでいることを前提に、実測条件を変えずに、監査証拠となる固定source Git blob SHAと再監査メタデータを付した。再監査の完成はLibrary保存・再取得検証までを意味し、GitHub本体への反映完了ではない。

## 問題設定：検索失敗と一本のコピー列

通常の自己回帰復号では、長さが増すたびに対象モデルの次トークン分布を一回ずつ求める。投機的復号は、先に候補トークン列を作って対象モデルの一括検証へ渡し、検証が成功した接頭部をまとめて受理することで逐次呼出回数を減らす。ただし、補助モデルを持たない方式では、候補列を安く構成するために過去の文脈から再利用できる場所を見つけなければならない。

従来のプロンプト検索型方式は、直近のトークンと同じトークンが過去の入力または生成履歴に現れた位置を探し、その直後のトークン列をそのまま候補としてコピーする。完全一致は精度が高く安価だが、言い換え・表記差・類義語により一致位置がゼロとなると候補が得られない。さらに一致位置が見つかっても、過去に実際に続いた一本の列だけを候補とするため、現在の文脈で妥当な別の続き方を捨てる。検索の再現率と、検索した位置から作る候補の多様性は異なる問題である。

AdaPLDはこの二段階を別々に改善する。検索では完全一致を既定とし、候補が空のときに限って意味類似度へ切り替える。候補構築では、選択位置の後続をコピーする主経路だけでなく、対象モデルの既存情報から複数の一歩目を分岐させ、各枝を再検索で一歩だけ延ばす。意味検索を毎回全面実行するのではない点、意味的に近い位置を無条件に長文コピーしない点が重要である。

## 手法：入力から検証まで

### 1. 検索メモリと完全一致の優先

復号時点iの検索メモリは、入力プロンプトxと生成済み列y_{<i}を連結したM_iである。問い合わせアンカーは最後に生成されたトークンa_i=y_{i-1}であり、過去メモリ中でM_{i,j}=a_iを満たす位置集合C_lexを作る。入力依存の要約・検索拡張生成ではプロンプト中に、長い推論では生成履歴中に再利用位置が見つかることがある。ここでの検索は文字列全体の意味を推定する処理ではなく、トークンIDの一致による位置候補の生成である。

### 2. 完全一致が空のときだけ意味検索へ退避

C_lexが空集合の場合だけ、対象モデルのトークン埋め込みeを使い、過去の各トークンとアンカーとの余弦類似度を計算する。閾値τ以上の位置をC_semとして採用する。C_lexが非空ならC_semを使わず、C_lexをそのまま候補とする。この順序は、意味検索を常時行う計算費と、完全一致が十分な場合の不必要な候補混入を避けるためである。意味検索の対象はトークン埋め込みであり、句全体の意味を理解する検索ではない。閾値を緩くすると候補は増えるが、不適切な位置も混じるため受理率や壁時計時間は単調に改善しない。

### 3. 隠れ状態を使った候補位置の再順位付け

候補位置集合が得られたら、対象モデルの隠れ状態を使って現在の文脈に近い位置を選ぶ。単に最新の一致位置を採用するのではなく、前置文脈を反映する表現の類似度により、次に続くトークン列が現在の文脈にも適合しそうな位置を選ぶ。この再順位付けはPLD+系の既存発想を引き継いでおり、AdaPLD固有の新規性は検索が空のときの意味退避と、選択後の分岐・後続再利用を統合する点にある。隠れ状態の取得・保持が追加費用ゼロというわけではない。

### 4. 主コピー列と一歩目の分岐候補

選択位置j*が完全一致由来なら、その位置に続く過去トークン列を最大コピー長まで取り、主候補列とする。一方、意味検索で選んだ位置は現在の末尾トークンと同じトークンでないため、その直後を主経路として無条件にコピーしない。代わりに、選択した過去接頭部までの対象モデルの次トークン分布から上位K候補を取り、別々の枝として構築する。完全一致由来の主経路がある場合は、主経路の先頭と同じ枝を重複して作らない。これにより「一度観測された続き方」以外も対象モデルへ検証させられる。

### 5. 各分岐を過去文脈から一段延長

分岐トークンbを新しい検索アンカーとし、同じ完全一致優先・意味退避を使って過去位置を探す。適合する位置があれば、その位置の次トークンを枝の二番目として追加する。ここでの後続延長は枝ごとに高々一トークンであり、無制限の探索木を再帰的に伸ばす設計ではない。枝の数K、主コピー長、閾値τは候補木の大きさと受理される平均トークン数の双方を変える。分岐を広げるほど対象モデルの検証が重くなるため、受理数最大化と速度最大化は一致しない。

### 6. 木状注意でまとめて検証し、対象モデルの出力を維持

主コピー列、分岐、各枝の後続を一つの候補木にまとめ、木状注意（tree attention）を用いて対象モデルの順伝播で検証する。検証に通った経路の接頭部だけを受理し、棄却時は通常の投機的復号の補正規則に従って対象モデルから確定トークンを得る。したがって速度改善は、低品質のトークンを強制的に採用する近似ではなく、対象モデルの分布を保ちながら順伝播回数を減らすことによる。実装では木状注意のマスク、枝ごとの位置対応、補正規則を誤るとこの性質が失われる。

## 評価：実験条件、比較対象、定量結果

### 実験設計

主実験の対象モデルはVicuna-v1.3の7B、13B、33Bで、NVIDIA H20を8基使うFP16推論である。温度T=0の決定的復号を主条件とし、補助ドラフトモデルを使わない自己回帰復号（AR）、PLD、PLD+、Token Recycling、SAM Decoding（SAMD）、Logitspecと比較する。入力依存生成はSpec-Benchの複数ターン会話・要約・検索拡張生成、編集はCodeEditorBenchのデバッグ・整形・翻訳・要件変更、推論はAIME 2024・MATH-500・MMLU-Proを使う。指標は生成処理量（トークン/秒）と同一対象モデルの自己回帰復号比の高速化倍率である。サービスの到着過程・待ち行列遅延を含む本番評価ではない。

| 項目 | 実験条件と読み方 |
|---|---|
| モデル | Vicuna-v1.3 7B / 13B / 33B |
| GPUと精度 | NVIDIA H20 ×8、FP16 |
| 生成 | 主実験は温度0、補助ドラフトモデルなし |
| 生成タスク | Spec-Bench：複数ターン会話、要約、検索拡張生成 |
| 編集タスク | CodeEditorBench：デバッグ、整形、翻訳、要件変更 |
| 推論タスク | AIME 2024、MATH-500、MMLU-Pro |
| 比較方式 | AR、PLD、PLD+、TR、SAMD、Logitspec |
| 指標 | 復号トークン/秒、ARに対する倍率。GPUカーネル単体時間とは別 |

### 入力依存生成の結果

原著表1の平均高速化は、7Bで2.27倍、13Bで1.98倍、33Bで1.74倍である。7Bでは自己回帰復号59.55トークン/秒に対し、提案法135.08トークン/秒、PLD+121.72、Logitspec123.17だった。13Bでは自己回帰47.87に対し提案94.88、33Bでは自己回帰27.43に対し提案47.70トークン/秒である。倍率がモデルサイズとともに必ず増えるわけではなく、タスク中の再利用機会と候補検証費用に依存する。

| Spec-Bench平均 | AR | PLD+ | Logitspec | AdaPLD |
|---|---:|---:|---:|---:|
| Vicuna-7B | 1.00倍 | 2.04倍 | 2.07倍 | **2.27倍** |
| Vicuna-13B | 1.00倍 | 1.78倍 | 1.76倍 | **1.98倍** |
| Vicuna-33B | 1.00倍 | 1.60倍 | 1.39倍 | **1.74倍** |

入力への依存が強い要約・検索拡張生成では過去文脈に再利用できる続きが多い。一方、複数ターン会話の最初のターンは入力から直接コピーできる箇所が少なく、再利用型方式の速度改善が限定的になり得る。会話履歴が蓄積すると、その履歴が次の検索メモリになる。

### 編集と推論の結果・負の条件

原著表2ではCodeEditorBenchの平均高速化が13Bで2.71倍、33Bで3.10倍となる。3.10倍は全評価で常に達成される倍率ではなく、33Bの編集課題の平均値である。7Bの編集ではAdaPLDが2.00倍に対してLogitspecが2.08倍であり、提案法が最速ではない。推論課題でも7BのAIME 2024ではAdaPLD 2.98倍に対しLogitspec 3.15倍、MATH-500ではAdaPLD 2.55倍に対しLogitspec 2.68倍である。13BのAIME 2024では提案法2.56倍、Logitspec2.33倍となり、優劣はモデルと課題に依存する。

| 条件 | AdaPLD | 主な比較・留保 |
|---|---:|---|
| CodeEditorBench平均・7B | 2.00倍 | Logitspec 2.08倍が上回る |
| CodeEditorBench平均・13B | 2.71倍 | PLD+ 2.41倍、Logitspec 2.21倍 |
| CodeEditorBench平均・33B | **3.10倍** | PLD+ 2.90倍、Logitspec 2.14倍 |
| AIME 2024・7B | 2.98倍 | Logitspec 3.15倍が上回る |
| MATH-500・7B | 2.55倍 | Logitspec 2.68倍が上回る |
| AIME 2024・13B | 2.56倍 | Logitspec 2.33倍 |

### 構成要素除去と感度

Vicuna-13Bの入力依存7課題をまとめた構成要素除去実験では、全機構の平均高速化は2.40倍である。分岐と後続延長を両方除くと2.18倍、後続延長のみ除くと2.37倍、意味検索退避を除くと2.24倍になる。従って、少なくともこの集計では分岐と検索退避の寄与が大きく、後続の一段延長は比較的小さいが正の寄与を持つ。要件変更では意味検索を外すと4.51倍から3.91倍へ落ち、表層一致で見つからない再利用候補を救済する意義が表れている。

| 構成 | 7課題平均 | 要件変更 |
|---|---:|---:|
| 全機構 | 2.40倍 | 4.51倍 |
| 分岐・後続延長なし | 2.18倍 | 4.22倍 |
| 後続延長だけなし | 2.37倍 | 4.51倍 |
| 意味検索退避なし | 2.24倍 | 3.91倍 |

分岐幅を2から64まで増やすと受理トークン数は増えやすいが、検証木の計算が重くなるため実時間の高速化は8～16程度で最大となり、64では悪化する。論文の既定分岐幅は8である。主コピー長を10から100へ伸ばしても受理長の利得は30程度で頭打ちとなり、既定長は30とされる。意味検索の閾値τも0.0～0.8で調べられ、受理率と速度は単調ではない。これらは「長い候補・多数の候補ほど常に速い」という誤解を避ける根拠である。

## 既存研究との差と導入時の検証点

PLD系の過去文脈コピーは補助モデルを必要としないが、完全一致した位置の後続を一本だけ採用する。PLD+は隠れ状態を使って候補位置を再順位付けするが、完全一致検索で候補が一つも得られない問題は解決しない。AdaPLDはこの空集合の場合に意味検索を使い、さらに同じ起点から複数の分岐候補を作る。対象モデルを使う通常の投機的復号の検証規則は保持するため、比較の焦点はドラフトの再利用可能性と検証コストである。

実装時は、(1)検索メモリが入力と生成履歴の両方を含むこと、(2)完全一致が存在する場合に意味検索へ不用意に移行しないこと、(3)意味検索位置の後続を無条件に主コピーしないこと、(4)主経路先頭と同一の枝を重複させないこと、(5)後続延長が一段で止まること、(6)木状注意と補正規則が対象モデルの分布を維持することを個別に検証する。候補生成にかかるCPU/GPU時間と対象モデル順伝播削減の差分を測らなければ、受理率が上がっても全体が速いとは限らない。

## 限界・負の結果

第一に、再利用できるアンカーや続きが入力と生成履歴に存在しない場合、意味検索で候補を増やしても有用な先読みは得られない。自由生成や短い会話の最初のターンでは、入力依存の要約・編集ほど大きな利得を期待しにくい。第二に、意味検索はトークン埋め込みの余弦類似度を用いる軽量な代理信号であり、句や構文の類似性を保証しない。誤った意味アンカーが増えると木の検証費用が無駄になる。

第三に、分岐幅・コピー長・後続延長・類似度閾値は実験で固定されたハイパーパラメータであり、GPU、モデル、ワークロードの変化に自動最適化されるわけではない。受理トークン数が増えても候補木が肥大化すれば速度は悪化する。第四に、実験は主にVicuna-v1.3、H20×8、FP16、温度0に限られる。別のモデル系列、量子化済み重み、RTX 12GB、長文脈でのキャッシュ管理、同時要求のバッチング、分散サービングの待ち行列遅延はこの測定から直接保証できない。

第五に、対象モデルの検証を使うことで分布を維持する設計であっても、木状注意マスクや棄却時の補正を正しく実装する必要がある。公式コードの正規公開URLを確認できないため、実機再現性は本稿の範囲では保証しない。原著の3.10倍をモデル一般の速度倍率として使わず、編集33Bの特定平均と、入力依存生成・推論課題での異なる倍率を区別する。
