# Libra：要求を任意のトークン位置で分割するLLMサービング

## 概要

大規模言語モデル（LLM）のオンライン推論は、入力全体を処理する事前計算（prefill）と、次のトークンを逐次生成する復号（decode）で計算資源の使い方が異なる。前者は演算集約的で、後者はモデル重みやキー・バリューキャッシュ（KVキャッシュ）の読み出しに支配されやすい。両者を同じGPUへ同居させると、長い入力処理が復号を待たせる。両者を別々のGPU群へ固定分離すると、入力長と出力長の比率が変化したとき、一方が過負荷でも他方のGPUが遊んでしまう。

Libraはこの二者択一を、**要求を任意のトークン境界で分割できる微小要求（micro-request）**へ一般化する。全体スケジューラが要求ごとの分割位置を選び、どのGPUにも入力処理・復号の混合部分を実行させる。局所スケジューラは復号のサービス水準を満たす範囲で入力トークンをバッチへ混ぜ、GPU間で必要になるKVキャッシュは小分けにして転送を演算と重ねる。

実機評価では、A100で固定同居方式より最大1.91倍、固定分離方式より最大1.61倍の有効処理量（goodput）を達成した。14Bモデルの混合負荷では収容能力が固定同居4.6要求/秒、固定分離5.9要求/秒に対してLibraは7.4要求/秒だった。一方、すべての指標が改善するわけではない。長い生成が中心のMini Reasoningでは初回トークン時間（TTFT）が固定分離の0.058ミリ秒に対し0.088ミリ秒となる条件が報告される。比較対象とサービス水準の定義を揃えて解釈する必要がある。

## 問題設定と既存方式の限界

従来の同居方式では、1台のGPUが入力処理と復号を連続バッチで処理する。入力処理を小片に分ける分割事前計算（chunked prefill）は割り込みの粒度を小さくできるが、負荷の混合自体は残る。固定分離方式は事前計算用GPUと復号用GPUを別の資源群へ割り当て、復号の遅延を守りやすい。しかし、入力が極端に長い要求と出力が極端に長い要求が混在すると、固定配分ではどちらかが不足し、他方が遊ぶ。

原著の表1はQwen 2.5-14BとA100 2基で、この交換条件を示す。入力8192・出力32トークンの負荷では、固定分離の事前計算側GPUのモデル演算利用率（MFU）が43.24%なのに対し、復号側は0.19%にとどまる。同居方式は1.49要求/秒で固定分離の0.83要求/秒を上回るが、99パーセンタイルのトークン間隔は352.93ミリ秒となり、100ミリ秒のサービス水準をほぼ守れない。固定分離は58.09ミリ秒で水準を守るが資源効率が低い。

問題は単に入力・出力の比率が予測できないことだけではない。Azure CodeとBurstGPTの要求トレースでは、入力優勢と復号優勢の時期が時間的に入れ替わる。固定GPU群の比率を事前に最適化しても、運用中に最適点が変化する。LibraはGPUの役割を固定せず、要求単位で分割位置を動かして、処理の遅い側が全体を律速する状態を減らす。

## 手法

### 1. 任意の境界で分割するFPS抽象

入力長を$P$、予測出力長を$D$とすると、要求の論理長は$L=P+D$である。Libraは$0\leq s\leq L$の分割点を選び、$1\ldots s$と$s+1\ldots L$の2つの微小要求へ分ける。$s=0$や$L$なら実質的に分割なし、$s=P$なら従来の入力・復号分離に一致する。$s>P$なら第1GPUが入力処理に加えて復号の一部を引き受け、$s<P$なら第2GPUが入力処理の後半も担当する。

この抽象の効果は、従来の同居と固定分離を**分割位置という連続した選択肢の特別な場合**として扱える点にある。例えば、入力1024・出力1024トークンをA100 2基で処理する実験では、入力末尾の位置1024で分割した場合の全体処理量は1.7要求/秒だった。Libraが選んだ位置1358では両GPUの処理量が約2.5要求/秒に均衡し、全体も2.5要求/秒となる（図5）。固定の段階境界が最適分割とは限らない。

ただし微小要求が別GPUで実行されると、その間でKVキャッシュを渡す必要がある。分割位置の自由度は、通信量とスケジューリング探索空間を増やす費用を伴う。Libraの後段2機構は、この自由度を実運用可能な費用へ抑えるために設計されている。

### 2. 全体スケジューラによる分割位置と配置の決定

全体スケジューラは、要求の入力長、概算の出力長、各GPUの現在負荷、最近の実行時間と利用率を入力とする。まず負荷が小さい2つの実行先を選び、同程度なら巡回方式で順番を決める。次に分割比$\phi=s/L$を入力末尾$P/(P+D)$から開始し、2つの実行先の予測完了時間$T_1,T_2$が近づく方向へ二分探索する。論文の実験設定では探索回数を最大6回に制限する。

予測器は事前に測ったバッチ性能の表を利用し、最近の実行進捗とGPUの計算・メモリ利用率で補正する。仮想バッチを順に進め、各要求へ入力片または復号トークンを割り当てて、残り仕事量と時刻を更新する。単純なトークン数比だけでなく、すでにGPUに並んでいる仕事の完了時間を推定するのが要点である。二分探索の停止条件は$|T_1-T_2|\leq\epsilon$という近似均衡で、全探索による厳密最適解ではない。

分割判断が高速でも、予測出力長が誤れば途中で仕事量の均衡が崩れる。Libraは予測を厳密値として固定せず、相対実行時間と最近の状態を再利用する。過小予測に備えて実装では20トークンの安全余裕を加える。出力長予測の誤差感度は評価節で別に測定されており、任意の分布ずれに頑健だと保証するものではない。

### 3. 局所スケジューラによるサービス水準を考慮したバッチ編成

各GPUの局所スケジューラは、待機中の入力片と復号要求を受け取り、直前のバッチの「入力トークン数、復号文脈長、同時復号数、実測時間」を性能表へ追加する。次のバッチでは遅延に敏感な復号要求を先に組み込み、その同時復号数と平均文脈長に応じて、追加しても99パーセンタイルのトークン間隔（TBT）がサービス水準を超えない入力トークン予算を決める。残りの予算だけ入力片をバッチへ追加する。

重要なのは「バッチサイズ」だけで制御しないことだ。入力トークン数が同じでも、同時復号数とKVキャッシュの文脈長によってメモリ読み出しが変わる。例えば、復号の文脈長1024の実験では適度な入力片を混ぜるとGPU演算利用率が上がる一方、同時復号要求が増えすぎると50ミリ秒の目標を超える。Libraは実測のバッチ形状を継続的に取り込み、許容できる入力片の大きさを更新する。

この制御を省いた構成要素除去実験では、Azure Code負荷の100ミリ秒水準を満たすトークンが52%にとどまる。局所制御を有効にすると99%へ改善した。全体分割だけでなく、GPU内の細かな混合バッチ制御が遅延達成率の主要因であることを示している。

### 4. KVキャッシュの分割転送と実装

要求をGPU間で分割すると、後段GPUは前段で生成されたKVキャッシュを必要とする。Libraは一括転送の完了を待ってから後段を開始するのではなく、KVキャッシュを複数の片に分け、RDMAで送りながら後段の計算と転送を重ねる。分割が細かいほど転送頻度が増すが、計算と通信を重ねることで露出する待ち時間を減らす。Mini Reasoningの実験では、分割転送なしのLibraに比べ、計算と重ならずに残る転送時間が94%減少した。

実装はvLLM上の約4000行のPythonを土台とし、全体スケジューラの重要な処理はC++で実装した。性能表はオフラインで対象GPUの入力片長、復号数、文脈長を変えながら測定する。つまり新しいGPUやモデルへ適用する際は、性能表の作成と通信経路の準備が必要になる。原著の付録は公式コードを将来公開すると記載するが、論文本文から公開URLは確認できない。

## 評価条件と比較の公平性

一次論文の§6と表1〜8を確認した。主実験はA100 80GBを4基ずつ搭載した2台のサーバーで、各サーバーはCPU 128基、メモリ1TB、200GbpsのRoCEネットワークインターフェース4本を備える。サーバー内GPU間にはNVLinkを使う。追加でH100でも評価する。Qwen 2.5の14B、32B、72Bを用い、Azure Code、BurstGPT、arXiv Summarization、Mini Reasoningの入力・出力長分布から到着要求を生成し、到着間隔はポアソン過程で与える。これは実サービスから取得したトレースを利用した**再生型負荷**であり、ライブサービスをそのまま運用した観測ではない。

| 項目 | 条件・定義 |
|---|---|
| 対象モデル | Qwen 2.5-14B / 32B / 72B |
| 主なハードウェア | 2台×A100 80GB×4基、RoCE 4×200Gbps/台、サーバー内NVLink |
| 追加ハードウェア | H100クラウド、厳しい50ms TBT条件も検証 |
| 比較対象 | vLLM 0.7.2の同居＋分割事前計算、改良された入力・復号分離 |
| 比較上の注意 | 同居側の入力片サイズは負荷ごとに256〜2048で調整。独立したSarathi-Serve/DistServe実装とは比較せず、vLLMの代表的構成を使用 |
| 要求分布 | Azure Code、BurstGPT、arXiv Summarization、Mini Reasoning。到着はポアソン過程 |
| 主な指標 | 100msの99パーセンタイルTBT水準下での有効処理量、収容能力、TTFT、達成率、GPU当たり有効処理量 |
| 主な変動要因 | 入力/出力長、モデル規模、負荷混合、分割位置、予測誤差、GPU数、サービス水準 |

有効処理量はサービス水準を満たす要求から生成されたトークン数/秒であり、**単なるトークン総数/秒とは異なる**。同居方式は水準を無視した総処理量が高くても、99パーセンタイルのTBTを大きく超えると有効処理量が下がる。固定分離はTBTを守りやすいが、遊休GPUによって収容能力が制限される。この違いを踏まえて比較する必要がある。

## 主要結果・構成要素除去・負の結果

### サービス水準下での処理量と収容能力

A100上の全負荷を通じ、Libraは同居方式に対して最大91%、固定分離方式に対して最大61%の有効処理量改善を報告する。14Bモデルの収容能力は、同居方式に対し平均2.37倍、固定分離に対し平均1.37倍だった。改善率は負荷・モデルによって異なり、これらは同一の条件で同時に出た値ではない。

| 条件・指標 | 固定同居 | 固定分離 | Libra | 備考 |
|---|---:|---:|---:|---|
| Qwen-14B、BurstGPT＋Azure Codeを半分ずつ混合、収容能力（要求/秒） | 4.6 | 5.9 | **7.4** | 同居比約60%、分離比約25%増 |
| 同上、有効処理量（トークン/秒） | 316.32 | 399.31 | **473.84** | 同居比約49%、分離比約20%増 |
| 4P1Dの非対称GPU配置、GPU当たり有効処理量 | — | 68.8 | **86.8** | 静的GPU配分との比較 |
| 2P1Dの非対称GPU配置、GPU当たり有効処理量 | — | 73.2 | **86.8** | より強い比較対象でも改善 |
| H100、Azure Code、50ms水準の有効処理量 | 259.7 | 397.2 | **608.0** | 100msの主実験とは別条件 |

分割位置を固定する方式が不利な理由は、例えば1024入力・1024出力の合成負荷で固定分離位置1024では1.7要求/秒だが、分割位置1358では2.5要求/秒になることから直接確認できる。これは特定の2GPU合成負荷での機構実験であり、一般的な全負荷の1.47倍改善を意味しない。

### 初回応答・バッチ制御・転送の代償

原著表2では、BurstGPTのTTFTは固定分離23.8ミリ秒からLibra12.6ミリ秒へ、arXiv Summarizationでは83.9から68.5ミリ秒へ改善する。一方、Mini Reasoningでは固定分離0.058ミリ秒に対してLibra0.088ミリ秒で、**初回トークンだけを見れば悪化する条件**がある。サービス水準を満たす全体の有効処理量と、各要求の初回応答は分けて評価すべきである。

局所スケジューラを外した条件ではTBT 100ミリ秒以内のトークンが52%で、局所制御を入れると99%になる。KVキャッシュの分割転送は非重複転送時間を94%削減した。全体スケジューラの費用は、Qwen-14BとBurstGPTの6〜16 QPSで要求全体の0.51〜0.09%、絶対時間では18ミリ秒未満だった。全体スケジューラ自体は軽量だが、転送を行うネットワークと事前の性能表を不要にするものではない。

### 予測誤差と多段分割

入力219、予測出力1467トークンの合成実験で、出力長の標準偏差を0から100へ増やすと、有効処理量は3606.93から3501.85トークン/秒へ約2.9%低下した。予測誤差の影響は小さいが、**この範囲を超える大きな分布ずれでの保証ではない**。思考過程のトークンと最終応答を区別するMini Reasoningでは、固定分離260.01、Libraの2分割336.16、3分割366.43トークン/秒だった。追加分割により遅延制約の緩い思考段階を別扱いでき、2分割よりさらに約9%改善した（論文本文の「さらに12%」という丸め表現と、表の数値から直接計算した比率は区別する）。

## 既存研究との差

Sarathi-Serveの分割事前計算は、同じGPU上で入力処理の塊を小さくする。一方DistServe型の分離は、GPU群の役割を入力処理用と復号用に固定する。Libraは**要求をどのトークンで分割するか**自体を最適化変数とし、同じGPU群が入力片・復号片を柔軟に処理できるようにする。さらに、全体の負荷均衡とGPU内のTBT制約付きバッチ編成を別々の階層で制御し、細かなKVキャッシュ移送を通信と演算の重ね合わせで支える。

最適な分割点を完全探索するのではなく、出力長の粗い予測、オフラインの性能表、最近の負荷情報を使った制限回数の二分探索へ落とす。これが現実的な要求受付遅延で動的な配置を行える理由である。性能上の利得は分割だけの成果ではなく、局所バッチ編成と転送隠蔽を含むシステム全体の効果として解釈すべきである。

## 限界と運用上の注意

第一に、LibraはGPU間のKVキャッシュ移送を前提とする。論文はRoCE/RDMAを備えるサーバー群で評価しており、低帯域の接続、ネットワーク競合、異種GPU、GPU障害時の移行まで同じ利得が成立するとは示していない。頻繁な分割は転送量を増やし、計算と重ねられない通信が増えれば性能は悪化し得る。

第二に、予測器は対象GPU・モデルに対する事前プロファイルと最近の実行情報を利用する。新モデルや実行基盤への移植では性能表の再測定が必要で、出力長予測の誤りに対する検証も標準偏差100までの限定された合成分布である。全体スケジューラの探索も最大6回の近似であり、最適解の保証ではない。

第三に、主評価はQwen 2.5系列とA100/H100の構成、4種類の負荷由来の再生要求、100ミリ秒（追加実験では50ミリ秒）のTBT制約に限られる。異なるアーキテクチャのモデル、推論品質への影響、クラスタ規模の大幅拡大、障害復旧、費用や電力の長期測定は主結果の対象外である。公開コードは原著付録で将来公開予定とされ、同じ環境での独立再現可能性も確認が必要である。

第四に、TTFTが悪化するMini Reasoningのような負の結果があり、低遅延が必要な指標がTTFTなのかTBTなのか、あるいは完了時間なのかで適切な配置方針は変わる。LibraはSLO付きの有効処理量を最大化する研究であって、すべての要求のすべての遅延指標を同時に最小化する研究ではない。
