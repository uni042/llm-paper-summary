# Network and Compiler Optimizations for Efficient Linear Algebra Kernels in Private Transformer Inference

> FHEによる暗号化Transformer推論のカーネルをOrion上で実装・計測し、BSGSが行方式の最大13.7倍、活性化枝刈りと線形統合でFFN遅延が11.46分の1になること、そして基本演算が演算強度約0.1でメモリ律速であることを示したプライベート推論の特性研究。

## 概要

LLMサービスは、利用者が質問をクラウドへ送り、クラウドが平文で処理する構造になっている。医療相談のような機微な入力では、この構造そのものがプライバシーの問題になる。完全準同型暗号（FHE）は、データを復号せず暗号化したまま計算できる暗号方式で、この問題への原理的な答えである。しかしFHEで使える演算は、暗号化ベクトルの要素ごとの加算、乗算、そして巡回回転に限られ、係数が数千ビット級の大きな整数多項式の演算を伴うため、通常の推論とは桁違いに遅い。プログラミングの難しさも高く、標準的なカーネルをこの制約の強い命令集合へ写像する作業が要る。

本論文は、PyTorchで書いたモデルをFHEで実行する基盤Orionの上で、暗号化Transformer推論に必要な線形代数カーネルを実装し、測り直す特性研究である。対象は、フィードフォワード（FFN）層の平文と暗号文の行列ベクトル積と、自己注意の注意スコア計算に要る暗号文同士の行列積である。行列ベクトル積では、行を詰める方式と対角方式のBSGS（baby-step giant-step）を比べ、BSGSがTransformer規模で最大13.7倍速いことを示す。ネットワーク側の最適化として、FFNの非線形活性化を取り除いて線形層を統合すると遅延は11.46分の1になる。代表結果としてもう1つ重要なのがルーフライン解析の結論で、FHEの基本演算はDRAM転送1バイトあたり約0.1整数演算という低い演算強度でメモリ律速であり、計算を増やしても速くならないこと、そして正準スロット符号化を超える符号化方式が必要だという方向性が示される。

## 問題設定

暗号化推論で余っているのは計算コアであり、足りないのはメモリ帯域と、深い計算を続けるための乗算レベルの予算である。CKKS方式では、暗号文同士の乗算や回転のたびにキー切り替えという重い処理が要り、回転量ごとに大きな切り替え鍵が要る。乗算を重ねるとノイズとスケールが育ち、リスケールでレベルを消費し、レベルが尽きれば高価なブートストラップで回復しなければならない。したがってカーネルの良し悪しは演算回数だけでは決まらず、回転の回数、消費する乗算レベル、ブートストラップの回数という複数の資源で決まる。行方式は内積を暗号文の中で完結させるため回転が多く2レベルを消費し、対角方式は内積を暗号文の間に広げることで回転を減らし1レベルで済む。この資源の違いがモデル規模とともに効いてくるのが本論文の出発点であり、さらにネットワーク構造そのもの（非線形関数の多項式近似がレベルとブートストラップを食うこと）も同じ物差しで見直す対象になる。

## 手法のあらまし

入力は暗号化されたトークン表現と、サーバ側が持つ平文の重み行列であり、出力は暗号化されたままの層出力である。FFNの線形変換については2方式を実装して比べる。行方式は行列の各行を平文へ詰め、暗号文と掛けてから回転と加算で内積を集約し、行ごとに繰り返す。BSGSは行列の一般化対角を平文へ詰め、回転で位置を合わせた暗号文と掛け、赤ちゃんステップと巨大ステップに分けて回転回数を平方根のオーダーまで減らす。自己注意の行列積については、行列積を行列の列と行の外積の和として表し、二進マスクで列と行を取り出して複製し、要素積を積み上げる方式をOrionへ追加する。ネットワーク側では、FFNのGeLUを取り除くことで多項式近似とその手前のブートストラップを消し、連続する2つの線形層を1つに統合する。最後に、基本演算の演算強度を実測してルーフライン上に置き、律速要因を特定する。

## 手法

### 1. 行方式とBSGS — 内積をどこで完結させるか

行方式が観測するのは行列の行単位の構造であり、各行を平文のスロットへ詰め、入力暗号文と要素積を取り、回転と加算の対数段数でスロット内の部分積を合計して内積を得る。これを行の数だけ繰り返し、結果を二進マスクで1つの暗号文へ統合する。必要な回転は2の冪だけなので切り替え鍵は少なくて済むが、回転の総数はスロット数とその対数の積のオーダーになり、乗算レベルも2つ消費する。BSGSは発想が逆で、行列の対角成分を詰めた平文と、回転で位置合わせした暗号文との積で内積を暗号文の間に構成する。回転を赤ちゃんステップと巨大ステップへ分解し、平文側の対角を事前に回転させて詰めることで、異なる回転と鍵の数をスロット数の平方根のオーダーまで減らし、消費レベルも1つで済む。減るボトルネックは回転に伴うキー切り替えとブートストラップの頻度である。追加費用は、平文側の事前回転と、方式ごとに必要になる鍵の管理である。規模が小さいうちは差が小さく、行列が大きくなるほど行方式は1つの平文へ詰められる行数が減り中間暗号文が増えるため、差が開く構造になっている。

### 2. 活性化の枝刈りと線形統合 — 非線形を消して層を畳む

FFNは上射影、GeLU、下射影からなるが、GeLUは127次の多項式で近似されており、高い乗算レベルと、その直前のブートストラップを要求する。本論文は先行研究に倣い、全FFNからGeLUを取り除き、残った2つの線形層を行列積で1層へ統合する。GPT-2では上射影が768次元から3072次元、下射影がその逆であり、統合後は768次元の正方行列1つになり、FFNのFLOPsは8分の1になる。効く理由は2つで、非線形の近似に要るレベルとブートストラップが消えることと、線形変換そのものの回数が減ることである。代償はモデルの表現力で、これは暗号化の近似ではなくモデル構造の近似である。論文はこの構成のモデルをCodeParrotの21億トークンで最初から学習し直して品質を測っており、既存モデルへ後から適用できる最適化ではない点に注意が要る。誤差の回復策として知識蒸留やエントロピー正則化が挙げられるが、本論文では評価されていない。

### 3. 暗号文同士の行列積 — 外積の和として注意スコアを作る

自己注意の注意スコアは、両方とも暗号文であるQとKの積であり、平文が混ざるFFNの変換とは別種のカーネルが要る。本論文の方式は、行列積を列と行の外積の和に分解し、各外積について、二進マスクとの平文・暗号文乗算で列と行を取り出し、回転と加算で全体へ複製し、暗号文同士の乗算で外積を作って積み上げる。必要な乗算レベルは2で、回転数は行列次元とその対数に比例する。対象は1つの暗号文へ収まる正方行列（次元128以下、スロット数2の15乗）に限られる。減るボトルネックは「このカーネルが存在しないため暗号化注意が組めない」という実装上の欠落であり、速度の絶対水準は依然として秒のオーダーである。追加費用は外積ごとのマスク乗算と複製回転で、次元が育つほど積み上げ回数が増える。

### 4. ルーフライン解析 — 律速要因を測って断定する

解析では、通常は浮動小数点演算で測る演算強度を、64ビット整数演算の回数をDRAM転送バイト数で割った量へ置き換える。演算回数はIntel PINによる動的計測、転送量はメモリコントローラのハードウェアカウンタで測り、暗号文同士の加算、乗算、回転という3つの基本演算について、乗算レベルを1から20まで振って遅延と合わせて記録する。乗算と回転ではキー切り替えが時間とメモリの両方を支配し、両者は似た特性になる。加算も含め全演算がメモリ律速側にあり、レベルが上がるほど演算強度は下がる。この測定により、「遅いのは計算が重いからではなく、暗号文と鍵のデータ移動が支配しているからだ」という主張が、印象ではなく数値で裏付けられる。

## 評価

### まず見るところ

- **結論:** カーネル方式の選択は規模が大きいほど効き、BSGSの優位は最大13.7倍に達する。ネットワーク側の枝刈りは遅延を11.46分の1にするが品質との交換であり、全体としては依然として実用的な遅延から遠いことが、著者ら自身の解析で示される。
- **速度・効率:** 絶対値は秒から分のオーダーである。GPT-2のFFNはトークンあたり16秒、注意の行列計算は平均2分、Llama 3 8B規模ではそれぞれ約15分と約5分（いずれも1ブロックあたり）と報告される。
- **品質:** 暗号化とカーネル方式は品質を変えない。品質が動くのは活性化枝刈りで、パープレキシティが2.688から3.342へ悪化する。
- **評価の強さ／注意点:** 方式比較、ネットワーク最適化、カーネル追加、律速解析という4層で一貫した測定をしている点は強い。一方でエンドツーエンドの暗号化推論の完成形の測定ではなく、カーネル単位の結果の積み上げである。

数値の読み方として最初に区別すべきなのは、相対改善と絶対水準である。BSGSの最大13.7倍はTransformer規模の線形変換での行方式との比較であり、その内訳は回転数に表れている。Llama 3のFFNでは行方式が24579回の回転を要するのに対しBSGSは272回で済み、回転に伴うキー切り替えが遅延を支配するFHEでは、この差がそのまま時間差になる。小さい行列では詰め込みの効率が良く差は小さいため、13.7倍という数値は「常に速い」ではなく「規模が育つほど開く」という傾向の最大値として読むべきである。逆に言えば、小規模な暗号化モデルの実験結果だけを見て方式差を判断すると、実運用規模での結論を誤る。

活性化枝刈りの結果は、遅延と品質の交換として率直に読む必要がある。層あたり遅延は、GeLUありの62.21秒から、GeLU除去で14.86秒、線形統合まで行うと5.43秒へ減り、合計で11.46分の1になる。内訳を見ると、GeLU除去の寄与が最も大きく、これは127次多項式の近似とブートストラップの除去が効いているためであり、統合の寄与はFLOPsを8分の1にすることに対応する。一方でパープレキシティは2.688から3.376へ上がり、統合では3.342とわずかに戻すものの、相対で約24パーセントの悪化が残る。論文は蒸留等で緩和できると述べるが実測はしておらず、この交換を受け入れられるかは用途依存である。また文脈長が小さい領域ではFFNが全体FLOPsの多数を占める（文脈長256では64パーセント）ため枝刈りの効果が大きいが、文脈が長くなれば自己注意側の比重が上がり、FFN最適化の相対的な効きは薄まる。層ごとの実験では、GeLUを残す層の位置による差は小さく、統合自体は追加の品質低下を招かないことも確認されている。

暗号文同士の行列積の結果は、絶対水準の厳しさを示すものとして読むのが適切である。GPT-2で系列長64の場合、行列積1回に67.2秒から172.2秒かかり、入力レベルが高いほど遅くなる。レベルは深い計算を続けるための資源であると同時に、暗号文のサイズと演算費用を押し上げる要因でもあり、深いネットワークほど1演算が高くなるという二重の不利がある。このカーネルの適用範囲は次元128以下の正方行列に限られ、現代的なLLMの注意をそのまま扱える規模ではない。したがってこの結果は「暗号化注意が動いた」という実装の前進であって、実用性能の到達ではない。

ルーフライン解析は、この論文で最も長く効く知見である。3つの基本演算はいずれもメモリ律速で、演算強度はDRAM転送1バイトあたり約0.1整数演算にすぎず、レベルが上がるほど下がる。乗算と回転はキー切り替えが支配的で特性が似る。この結論の含意は明確で、コア数や周波数を増やす計算側の投資では暗号化推論は速くならず、暗号文と切り替え鍵のデータ量そのものを減らす符号化方式の革新が要る、という方向へ研究資源を向けるべきだということである。測定条件はOpenFHE、48スレッド、周波数上限2.4GHz、ベクトル化無効という特定の構成であり、絶対値の一般性には留保が要るが、著者らは従来型のキー切り替えを使う他のライブラリでも傾向は続くと述べており、先行する特性研究とも一致する。未評価事項としては、エンドツーエンドの暗号化LLM推論の遅延と品質、GPUや専用アクセラレータ上での同じ解析、埋め込み参照を同型に実行した場合の費用、ソフトマックスや層正規化といった非線形カーネルの費用分離が挙げられる。特に埋め込みについては、多くの実装が平文側で済ませる前提を置いていることを論文自身が問題として指摘している。

## 既存研究との差

FHEコンパイラの研究は、パッキングの最適化やブートストラップ配置の自動化を中心に進んできた。本論文はOrionという既存基盤を使い、その上でカーネル方式の比較、ネットワーク構造の変更、カーネルの追加、律速解析を1つの物差し（回転数、レベル消費、演算強度）でつないだ点が異なる。プライベートTransformer推論の先行研究が非線形カーネルや通信削減に焦点を当てる中、本論文は線形代数の基本カーネルに立ち返り、方式選択だけで2桁近い回転数の差が出ることと、最終的な律速がメモリであることを示した。結論として新しい符号化方式の必要性を主張する点も、個別最適化の積み上げとは違う立場である。

## 限界・実装状況

- ハードウェア依存条件: ルーフラインの測定はCPU上のOpenFHEという特定条件であり、GPUや専用アクセラレータでは律速の姿が変わり得る。ベクトル化を無効にした測定条件も絶対値へ影響する。
- モデル／ワークロード依存条件: 品質評価はGPT-2規模を再学習した条件に限られ、大規模モデルでの活性化枝刈りの代償は未検証である。行列積は次元128以下に限られ、長い文脈や大きな隠れ次元は扱えない。
- 実装状況: カーネルはOrionへの追加として実装され、コードはOrionの公開リポジトリで提供される。エンドツーエンドの暗号化LLMサービスとして統合された形ではなく、埋め込み参照など前提として平文に置かれている部分が残る。
- 近似の品質リスク: 暗号化とカーネルは近似ではないが、活性化枝刈りはモデル構造の近似であり、パープレキシティの悪化を伴う。緩和策は提案のみで未評価である。

## 一般的な実装上の含意

律速要因を測らずに最適化すると、効かない資源へ投資することになる。本論文のルーフラインの結論は、暗号化推論に限らず、データ移動が支配的な推論基盤全般への警告として読める。もう1つの含意は、カーネルの方式選択は小規模実験では差が見えず、実運用規模で初めて差が開くことがあるという点である。方式の採否は目標規模の行列で測るべきであり、回転数やレベル消費のような構造的な量で比較すると、規模への外挿がしやすくなる。
