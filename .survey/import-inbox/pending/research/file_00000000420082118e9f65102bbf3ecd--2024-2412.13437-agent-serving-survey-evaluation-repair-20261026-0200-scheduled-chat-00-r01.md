# Deploying Foundation Model Powered Agent Services：エージェントサービングの階層的システムサーベイ

## 概要

本論文は、基盤モデル（Foundation Model、FM）を利用するエージェントをクラウド・エッジ環境で実際に提供するための技術を、ハードウェアからアプリケーションまで統合的に整理するサーベイである。エージェントは単発の文章生成とは異なり、計画、外部ツールの呼び出し、記憶の読み書き、複数モデルの連携を繰り返す。そのため、1回のモデル推論のトークン速度だけを最適化しても、サービス全体の応答遅延、コスト、信頼性は必ずしも改善しない。

著者らは、実行層、資源層、モデル層、エージェント層、アプリケーション層という階層で既存研究を整理する。実行層ではGPU/CPU/FPGA/ASIC/メモリ内演算、KVキャッシュと通信、資源層ではスケジューリング・弾力的スケーリング・並列化、モデル層では量子化・枝刈り・蒸留・トークン削減、エージェント層では計画・記憶・ツール、アプリケーション層ではバッチ処理とサービス品質を扱う。個々の最適化の利得を、エージェント全体の実行グラフと資源制約に接続する点が主な貢献である。

この論文は文献サーベイであり、独自の統一ベンチマークを使って「エージェントサービングが何倍速くなった」と実測したものではない。各節の表は既存研究の設計目標・対象環境・手法を分類するもので、異なるハードウェアやデータセットの報告値を直接比較する速度ランキングではない。

## 問題設定：モデル推論からエージェントサービスへの拡張

通常のLLMサービングは、入力のプリフィルと逐次デコードを処理し、初回トークンまでの時間、生成トークン間隔、要求スループットなどを管理する。一方、エージェントサービスでは、モデルが生成した中間判断に応じて外部APIを呼び、ツール結果を再入力し、場合によっては別のエージェントへ仕事を委譲する。したがって、一つの利用者要求は複数のモデル呼び出し、ネットワーク通信、状態更新を含む依存グラフとなる。

ここでボトルネックは層ごとに変わる。長い入力のプリフィルは計算資源を、逐次デコードは重みとKVキャッシュのメモリ帯域を圧迫する。複数モデルを同時に利用すると、GPU容量とモデル切り替えが問題になる。エッジ端末とクラウドを協調させる場合は通信遅延と帯域が支配的になり得る。外部ツールの応答が遅ければ、GPUの高速化だけではエンドツーエンド遅延を改善できない。

著者らはこの異質な制約を、モデル最適化と資源管理の両方を含むサービス設計として捉える。原著の図1・図2は、実行層の低水準最適化が上位の資源配分・モデル選択・エージェント構成を支え、アプリケーション層の品質要件へ結び付く構造を示す。これは単なるLLMアーキテクチャの一覧ではなく、実際に複数要求を受けるサービスの設計問題を分類する枠組みである。

## 手法

### 1. 実行層：演算・メモリ・通信の制約を分離する

原著§IIは、ハードウェアに近い最適化を演算、メモリ、通信、統合フレームワークに分ける。演算ではFPGA、ASIC、メモリ内演算（IMC）、CPU/GPUの違いを整理する。FPGAは構成変更に柔軟だが、TransformerのSoftmaxや正規化などの非線形演算を効率よく実装するには専用設計が要る。ASICは特定の演算に高効率だが、製造後の柔軟性に制限がある。IMCは演算器と記憶装置の間の転送を減らすが、精度・データ配置・対応演算に制約がある。GPUは大規模並列演算に強いが、低バッチデコードでは重み読み出しの帯域が律速になりやすい。

メモリの節では、プリフィルとデコードの資源特性を分け、PagedAttention、FlashAttention、MQA/GQA、CPU/GPUオフロードなどを紹介する。PagedAttentionはKVキャッシュのページ単位管理によって断片化と動的な要求長へ対応する。FlashAttentionは注意計算の中間行列を外部メモリへ書き戻す量を抑え、GPU内部の高速メモリを活用する。MQA/GQAは複数の問い合わせヘッドで鍵・値を共有し、デコード時のKV転送量を減らす。これらは同じ「メモリ最適化」でも、何を保持し、何を転送し、何を再計算するかが異なる。

MoEモデルでは、トークンごとに選ばれる専門家の重みをどこに置くかが重要になる。原著はEdgeMoE、MoE-Infinity、Fiddler、事前ゲート方式などを紹介し、専門家の再利用、予測、CPU/GPU協調を整理する。全専門家をGPUに置けない場合、ホットな専門家を常駐させるか、将来の選択を予測して先読みするか、CPUで一部を実行するかという選択になる。予測が外れるとPCIe転送や待ち時間が増えるため、モデルの構造と要求分布に合わせた運用が必要である。

通信最適化は、複数装置に分割したモデルやエッジ・クラウド協調で特に重要になる。計算時間だけを削っても、通信の待ち時間が増えれば総遅延は短縮しない。原著は計算資源とネットワーク資源を共同でスケジューリングする研究を整理し、異種環境での負荷変動に対応する必要性を強調する。統合フレームワークとしてはParrotやSGLangにも触れ、LLMプログラムの依存関係、KV再利用、制約付き生成やAPI投機実行を実行系と結び付けている。

### 2. 資源層：スケールと並列化の設計を分ける

原著§IIIとTable IIIは、クラウドとエッジでの資源配分を分類する。クラウド側にはClipper、InferLine、Clockwork、INFaaS、SHEPHERD、SpotServeなどが挙げられ、遅延、スループット、精度、費用、資源利用率を異なる目標として扱う。たとえばInferLineは長期的な容量計画と短期的な調整を分離する。INFaaSはモデル変種の選択とスケーリングを組み合わせ、同じ要求を異なる精度・計算費用のモデルへ割り当てる。これらの方式を「すべて同じLLMサービング負荷で評価した」と扱ってはいけない。

エッジ側では、CPU/GPUなどの装置性能が異なるうえ、端末数、ネットワーク品質、要求の到着率が変化する。中央集約のスケジューラは全体の見通しを得やすいが、制御通信や障害点を増やす。分散的な配分は局所的な変化に追従しやすいが、全体の最適性と整合性が課題となる。著者らはこれらを遅延・電力・費用・利用率の観点で比較し、環境ごとに制約が異なることを示す。

並列化の節（Table IV）は、データ並列、モデル並列、テンソル並列、系列並列を区別する。データ並列は要求群を複数の装置へ配るが、大きなモデルを各装置へ複製する必要がある。テンソル並列は行列演算を装置間で分割するため、各層の集合通信が必要になる。パイプライン並列は層を段階に分けるが、小バッチでは段階間の空き時間が問題になる。系列並列は入力トークン方向を分割する。どの方式が有利かはモデル規模、入力長、要求数、GPU間帯域と目標指標によって変わる。

### 3. モデル層：圧縮とトークン削減を分ける

原著§IVはLLM、指示調整モデル、マルチモーダルモデル、MoE、小型モデルを整理し、枝刈り、量子化、知識蒸留、モデル適応、トークン削減を検討する。枝刈りは計算する重みや構造を削るが、実際の速度は疎性を利用できるカーネルに依存する。量子化は重みや活性のビット幅を下げるが、低ビット演算器の対応や外れ値への感度が制約になる。蒸留は小型モデルを作れるが、教師モデルによる学習費用と性能の交換条件がある。

トークン削減は、モデルのパラメータを変えずに入力や中間表現の処理量を減らす。長いエージェント履歴やツール出力を全て毎回プリフィルすると、計算量とKV容量が増えるため、入力の圧縮・選別が有効になり得る。ただし重要な指示や外部ツールの根拠を失えば、回答品質と安全性が悪化する。圧縮率だけでなく、後続のタスク成功率と応答遅延を合わせて測る必要がある。

### 4. エージェント層：計画・記憶・ツールが推論要求を変える

原著§Vは、複数エージェントの協調、計画、記憶、ツール利用を主要構成要素として整理する。計画は一回のLLM生成で完結せず、実行結果を見て次の手順を選ぶことがある。記憶は会話や外部知識を保存し、必要な時点で再検索する。ツール利用はネットワーク呼び出し、API応答待ち、検証処理を追加する。複数エージェントが分担する場合、モデル間のメッセージと状態の共有が新しい通信負荷となる。

サービング側から見ると、エージェントの実行グラフには直列依存と並列化可能な部分が混在する。前のツール結果がないと次のモデル入力を作れない処理は直列であり、独立した検索や複数候補の評価は並列化できる場合がある。KVキャッシュを共有できる共通プロンプト、モデル切り替えの費用、ツールの遅延分布を考慮したスケジューリングが重要になる。原著の価値は、エージェントの推論能力と実行系の資源管理を別々に考えない枠組みを示す点にある。

### 5. アプリケーション層：バッチ処理とサービス品質

原著§VIのTable XIIIは、長さが異なる要求をまとめる際のパディングの無駄や、生成中に各要求の進行度が変わる問題を扱う。ORCAは要求単位ではなく反復単位のバッチ処理を採用し、生成中に完了した要求を取り除き、新しい要求を加える。入力長や生成長の違いを考慮するバッチ方式も整理される。これらはスループットを改善し得るが、長い要求が短い要求を待たせるなど、個別の遅延や公平性との交換条件がある。

エージェントアプリケーションでは、生成品質だけでなく、ツール実行の成功率、応答時間、失敗時の回復、要求の同時処理数が重要になる。著者らは多様なアプリケーションを列挙するが、アプリケーションの存在自体が特定のサービング方式の性能優位を示すものではない。モデル、ツール、ネットワーク、スケジューラを通したエンドツーエンドの評価が必要である。

本論文の主な発見は、低水準の演算最適化だけではエージェントのサービス品質を十分に説明できないことである。例えばKV再利用は複数要求で共通の入力を処理するときに効果があるが、外部ツールから戻る内容が要求ごとに異なると再利用可能な接頭辞が減る。GPUを増やすスケーリングは計算待ちを減らせても、外部APIの応答が遅ければ利用者の待ち時間は変わりにくい。これらは各層の機構から導かれるシステム上の含意であり、本論文が新規に実測した数値結果ではない。


### 文献分類から確認できる比較上の事実

原著Table IIIのクラウド側は、同じ「資源スケーリング」という名称でも、**モデルをどこへ置くか**と**何を予測して増減させるか**が異なることを示す。InferLineは低頻度の計画器で遅延SLOを満たす費用最小のパイプライン構成を求め、高頻度の調整器で到着率変動に応じた複製数を変更する。これに対してNexusは遅延制約を考慮した複数タスクのGPU同居を扱い、INFaaSはモデル変種の選択とスケーリングを結び付ける。いずれも「同じGPU、同じLLM、同じ到着トレースで速度比較した結果」ではない。原著Table IIIは**研究の目的・対象と採用した制御機構を比較する証拠**であり、方式間の定量的な勝敗を示す実験表ではない。

Table IVの並列化比較では、Megatron-LMが層内のテンソル並列を、DeepSpeed-Inferenceがテンソル・モデル・データ並列と異種メモリ、専用行列演算、演算融合を組み合わせる方式を代表する。DistServeはプリフィルとデコードを別のGPU群へ分け、SARATHIはプリフィルの小片とデコード要求を同じバッチに混在させる。これらの分類から、**演算の分割位置と通信・待ち時間の発生箇所が方式ごとに異なる**ことが読み取れる。一方、原著の表は各方式の測定モデル、GPU型番、入力長、出力長、同時要求数を共通条件に揃えていないため、表中の方式名だけを使って「DistServeがSARATHIより速い」といった順位付けはできない。

Table XIIIはバッチ処理の問題を三群に分ける。入力・出力長の不揃いにはORCAの反復単位スケジューリング、PiAの生成長予測、TurboTransformersの動的計画法による長さを考慮したバッチ形成が挙げられる。要求のサービス特性の違いにはClipperの動的バッチサイズと待機時間調整、モデル重み・LoRAアダプタの違いにはS-LoRAとPunicaの専用CUDAカーネルが挙げられる。この表からは、**長さの不均一性とアダプタの不均一性は異なる最適化問題**であることが分かる。長さを揃える方式の効果を、異なるLoRAを同時実行するカーネルの効果へ直接外挿することはできない。

著者らの§VII-Aでは、エッジ向けアクセラレータ研究の多くが固定されたLLMアーキテクチャを前提にし、視覚モデルとLLMを組み合わせたマルチモーダル構成や異種アクセラレータ間の共同最適化を十分扱っていないと指摘する。また、資源・モデル・トークン単位での弾力性に比べ、**エージェント層の弾力性**、すなわちAPI呼び出し、外部知識検索、推論手順、複数エージェント協調を負荷やタスクに応じて変更する仕組みが不足していると整理する。これらは原著の文献比較から導かれた定性的な課題であり、著者らが新しいエージェントスケジューラを実装して効果を実測したという意味ではない。

### 評価の空白と今後の比較設計

このサーベイ自体には、統一したモデル群・要求到着トレース・GPU/CPU構成・ネットワーク条件の下で五層を共同最適化した**独自のアブレーション実験はない**。したがって「実行層だけの最適化」「資源層を加えた最適化」「エージェント層の適応まで加えた最適化」を切り分けた速度差や費用差も提示していない。文献横断の分類表から性能を推定すると、評価環境と目的指標の不一致が交絡する。

本稿の分類を実際のサービング評価へ用いるなら、モデル単体のTTFT・TPOT、バッチ時の要求スループット、KV/重みのメモリ使用量、ネットワークと外部ツール待ち、要求全体の完了時間、エージェントタスク成功率を別々に記録し、同じ負荷で層ごとの追加効果を比較する必要がある。これは**本サーベイから導かれる評価設計上の提案**であって、原著に実測値が存在するという主張ではない。

## 既存研究との差

従来のLLM推論サーベイは、モデル推論の計算、メモリ、GPUカーネル、分散処理に焦点を当てることが多い。エージェントのサーベイは、計画、記憶、ツール利用、協調方式の機能面を中心に整理することが多い。本論文はこれらを接続し、エージェントが要求する複数段階の推論と外部操作を、エッジ・クラウドの資源配分、モデル圧縮、バッチ処理と一つの階層構造に位置付ける。

ただし、階層モデル自体は実行可能なスケジューラや最適化アルゴリズムではない。各層をどう共同最適化するか、どの負荷で何を優先するかについて、実装と定量評価が別途必要になる。既存のシステム研究とエージェント研究を同じ用語で比較するための概念的な枠組みとして読むのが適切である。

## 限界

原著§VIIは、異種エッジ装置での基盤モデル実行、マルチモーダル・MoEのエッジクラウド配置、エージェント専用サービング基盤を将来課題として挙げる。ASICは特定演算に強いがモデル変更に弱く、FPGAは柔軟だが非線形演算の実装が難しい。GPUとCPUの共同利用は容量制約を緩和する一方、通信帯域やデータ転送が新しい律速になる。MoEでは専門家の選択が動的なため、モデル配置を固定しても最適とは限らない。

本論文は2024年12月時点のサーベイであり、その後のモデル、GPU、推論フレームワークの更新を反映した最新のベンチマークではない。選定した文献群を統一条件で再実行しておらず、文献選定の網羅性を保証する体系的な検索・除外プロトコルも実験研究ほど明確ではない。対象はLLMだけでなく広義の基盤モデルや一般的なエッジ計算も含むため、全ての掲載方式が生成LLMのサービングで検証されているわけではない。

実運用の評価では、モデルの正答率、TTFT、TPOT、要求全体の完了時間、GPU/CPUメモリ、ネットワーク待ち、ツール失敗時の回復、費用、エージェントタスク成功率を分けて測る必要がある。エージェントの実行グラフに直列依存が多いと、GPUのトークン速度改善が全体遅延に反映されにくい。モデル単体の速度倍率とサービス全体の速度倍率を同一視しないことが、本論文の分類を活用する際の重要な注意点となる。
