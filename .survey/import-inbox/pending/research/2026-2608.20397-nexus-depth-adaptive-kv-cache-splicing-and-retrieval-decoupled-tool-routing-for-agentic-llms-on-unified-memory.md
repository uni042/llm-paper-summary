# Nexus: Depth-Adaptive KV-Cache Splicing and Retrieval-Decoupled Tool Routing for Agentic LLMs on Unified Memory

> ツール選択をスキーマプリフィルから検索で切り離し、引数生成は圧縮署名上で行うエージェント向けサービング試作。KV移植はRoPE位相ずれの境界つきで、深さ適応型再計算により出力の完全一致を保証する。

## 概要

Model Context Protocolを使うエージェントは、呼び出し可能なツールの説明であるJSONスキーマを毎ターン提示される。レジストリが数百ツールへ育つとスキーマがプロンプトを支配し、自己注意が系列長の二乗で効くため、スキーマの再エンコードだけで初回トークンまでの時間（TTFT）が膨らむ。素朴な最適化は、スキーマを一度だけKVブロックへコンパイルして使い回すことだが、本論文はこの移植が回転位置埋め込み（RoPE）の位置依存性に根本的に制約されることを示す。ある絶対位置向けに作ったブロックを別の深さへ置くと、キーに位相誤差が乗り、注意が軸から外れて読まれる。

Nexusの答えは二段構えである。主たる手段は、ツール選択そのものをスキーマのプリフィルから切り離すことにある。ツールの埋め込みをINT8量子化した意味ルックアサイドバッファを走査し、上位2件のマージンが較正済みしきい値を下回る2割だけクロスエンコーダへ回すゲートでツールを決め、引数はスキーマ全文ではなく中央値19トークンの圧縮テキスト署名の上で生成する。この経路は深さに依存せず、250ツールでもルーティング精度は約89パーセントを保ち、全スキーマを連結する比較対象は50ツールで文脈からはみ出して動作不能になる。副次的な手段としてKV移植も備えるが、固定位置では出力が完全一致する一方、外れた配置では発散が残るため、256トークンを超える接合では深さに応じて末尾の再計算割合を100パーセントまで引き上げ、全プリフィルとビット同一の出力を保証する。代表結果として、最初の引数トークンまでの時間は全スキーマ再プリフィルの737.3ミリ秒に対し443.8ミリ秒で1.66倍高速になり、主文脈のトークンを約80パーセント節約した。

## 問題設定

問題はコストの所在と、移植の信頼性の2つである。コスト面では、会話履歴に全ツールのスキーマ長が加わるため、ターンごとのプリフィル費用はレジストリ規模で増え続ける。全スキーマ連結は規模の時点で文脈窓へ収まらず、関連スキーマだけを検索してプリフィルする方式でも、選ばれたスキーマの再エンコードは毎ターン残る。信頼性の面では、既存のKV管理はブロックを計算された位置から動かさないことでこの問題を回避してきた。位置を動かす場合、RoPEの回転角は絶対位置で決まるため、コンパイル時の固定位置と実行時の配置位置の差に比例して位相誤差が周波数の高い次元対ほど速く蓄積する。再固定で相対回転は正確に戻せるが、ブロックが別の前文脈のもとで作られた事実までは消えず、小さな残余発散が残る。本論文は、この残余がどれほどで、修理にいくらかかり、そもそも接合へ依存しない経路が作れるかを順に問う。

## 手法のあらまし

リクエストが来ると、まずクエリを埋め込み、意味ルックアサイドバッファを走査してツールの候補を出す。上位2件のマージンが十分なら即決し、不足すればクロスエンコーダが再順位付けする。決まったツールについて、引数は圧縮した関数署名のテキストの上で、ツール名のトライによる有限状態機械マスクとJSON文法の制約のもとで生成される。並行して、スキーマのプリフィルを速くする必要がある場面では、オフラインでコンパイルしたKVブロックをライブ文脈へ書き込む接合を行う。配置が256トークン以内ならそのまま使い、超える場合は深さで決まる割合だけ接合したスキーマの末尾を無効化して再デコードし、継ぎ目を縫い合わせる。深さが増すほど再計算は全量へ近づき、出力は全プリフィルと同一になる。

## 手法

### 1. 意味ルックアサイドバッファとマージンゲート — 検索だけでツールを決める

入力はユーザクエリとツールレジストリである。各ツールの名前と説明を連結して埋め込み、INT8量子化して保持し、クエリ側の埋め込みとの内積を分岐なしのSIMD走査で計算する。名前がルーティング信号の主役であるため、名前と説明の両方を登録する点が効く。250ツールの実地走査は中央値17.6マイクロ秒、純粋なC++走査では8.25マイクロ秒で終わる。上位候補はマージンゲートを通る。上位2件のスコア差がしきい値0.0136を超えれば自動で確定し、下回れば微調整済みMiniLM級クロスエンコーダが再評価する。しきい値は敵対的ペアのマージンの20パーセンタイルへ較正され、クロスエンコーダは最も自信のない約2割の判断でのみ発火する。この経路はクエリの埋め込みとレジストリだけに依存し、会話の深さとは無関係であるため、文脈が深くなっても劣化しない。失敗条件は検索自体の天井で、紛らわしいツール同士の混同はゲートでも完全には除けない。

### 2. 圧縮IRとサイドカー — 引数生成を接合から外す

決まったツールの引数は、接合したKVの上ではなく、圧縮テキスト署名の上で生成する。JSONスキーマを、型のヒント付きの密な関数署名へ畳み、説明を切り詰めたものが圧縮中間表現であり、長さは中央値19トークン、99パーセンタイルでも32トークンにとどまる。主文脈へ載せる量が小さいためスキーマ肥大を避けられ、接合の位相ずれの領域にも踏み込まない。ツール名はラディックス・トライに対する有限状態機械でマスクされ、JSON引数はスキーマからコンパイルしたGBNF文法で制約される。ルーティング検証のために新しい系列で接合が必要な場合は、位置0から始まる一時サイドカー系列を使い、接合を常に出力完全一致の領域へ置く。複数ターンの指示対象を保つため、サイドカーには直近ターンを逐語で残し、大きなツールペイロードを短い意味的代替へ置き換えた剪定済みスライディングウィンドウを持たせる。

### 3. コンパイル済みブロックの接合と再固定 — 移植の実装

各スキーマはオフラインでAeonツールブロックへコンパイルされる。128バイトのヘッダーにRoPEの固定位置とスケーリング係数を記録し、ページ整列した連続なF16のキーと値のテンソルが続く。接合前にヘッダーのRoPE係数を実行時モデルと照合し、別のスケーリングで作られたブロックは注意を壊す前に拒否する。接合はキーと値の行を実行時カーソル位置のライブKVセルへ直接書き込み、その際、各キーをコンパイル固定位置から実行時位置へ再回転させて位相誤差の主部を取り除く。統合メモリ上では物理キャッシュへの直接コピーが可能なため成立する仕組みであり、トークン列しか受け付けないクラウドAPIや、転置されたストライド転送が不利な離散GPUでは接合を辞退してテキストプリフィルへ戻る、失敗したら閉じる側へ倒す設計である。

### 4. 深さ適応型の末尾再計算 — 決して劣化しない保証

再固定しても残る残余発散を消すため、接合したスキーマの末尾の一部を無効化して再デコードする。再計算割合は深さの関数で、256トークンまでは基礎値5パーセント、そこから深さに応じて線形に増え、係数Kで決まる倍率の深さで100パーセントへ達する。標準のK=4では1024トークンで既に全量再計算となり、接合の利得は消えるが、出力は全プリフィルとビット同一になる。より平坦なK=16では2048トークンでも再計算は49.3パーセントで、速度の利得が深くまで残る。ここで保証されるのは出力の忠実度、すなわち首位トークンの一致と分布の発散がほぼ0であることであり、遅延ではない。再計算の追加仕事のため、TTFTが同等をわずかに下回る深さも実測されている。散らした部分再計算による修理は、1024トークンで発散5.7ナッツという壊滅的な結果を残して廃止され、連続した末尾を修理する現行方式へ置き換えられた経緯も、この設計の根拠として報告されている。

### 5. 転置V接合とキャッシュライン硬化 — 統合メモリ向けの実装詳細

ソフトキャップ付き注意を持つGemma-2のようなモデルではFlashAttentionが使えず、値キャッシュがトークンを最内側にした転置レイアウトになる。固定ストライドの行優先コピーではこのレイアウトへ書けないため、ライブの値ストライドを検証してからストライド付き転置コピーを行うレイアウト対応の接合ルーチンを実装し、Gemma-2-9Bで忠実度を確認している。並行処理では、ターン全体を1つの粗い再入可能ロックで直列化し、ネイティブ側のミューテックスと競合する細粒度ロックを避けて決定的な出力を得る。ブロック割り当て器は128バイト境界へ整列させ、競合するミューテックスを専用のキャッシュラインへ置くことで偽共有を除く硬化も入っているが、論文はこれ単体の速度改善は主張していない。さらに、完全一致トークンの最長共通接頭辞で暖かい接頭辞を再利用するゼロ割り当てのラディックスキャッシュも備える。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 意味ルックアサイドバッファ | クエリ埋め込みとツール埋め込み | INT8走査で候補を出しマージンで確定か再評価かを分ける | ツール選択の費用と深さ依存性 | 検索の天井は残り、混同は消えない |
| 圧縮IR | 決まったツールのJSONスキーマ | 型ヒント付き署名へ畳んで主文脈へ載せる | 主文脈のトークン量 | 署名で落ちる意味は引数生成へ影響しうる |
| KV接合 | コンパイル済みブロックと配置位置 | 再固定しながらライブキャッシュへ直接書き込む | スキーマのプリフィル費用 | 統合メモリのローカル実行でしか成立しない |

## 評価

### まず見るところ

- **結論:** ルーティングの分離は規模に対して平坦に効き、接合は浅い深さでのみ速度の利得があり、深さとともに同等へ収束する。2つの負の結果がこの役割分担を裏づける。
- **速度・効率:** 最初の引数トークンまでは1.66倍高速で、深い接合のTTFT改善は中程度の深さで1.1から1.7倍、深い文脈では同等になる。
- **品質:** 接合は再計算により全プリフィルとビット同一を保ち、ルーティング精度は250ツールで約89パーセント、引数の指定項目の正しさはルーティング成功時に100パーセントだった。
- **評価の強さ／注意点:** 単一ホスト・単一モデルタプルの試作評価で、標本数は最大でも100件程度と小さく、数値の一般化は論文自身が制限している。

**数値の読み方。** TTFTの改善率は深さの関数として読む必要がある。浅い深さの1.63倍や1.73倍は再計算が5パーセントで済む領域の値で、再計算が100パーセントへ達した深さでは定義上プリフィルと同等になる。逆にルーティング精度はレジストリ規模に対してほぼ平坦であり、規模で崩れる全連結方式との対比が主張の中心である。

## 既存研究との差

PagedAttentionやRadixAttentionなどのKV管理は、断片化の除去や接頭辞共有でその場の再利用を行い、ブロックを別の位置へは動かさない。RAG-MCP等のツール検索はプリフィル前に効くが、選ばれたスキーマの再エンコードは残る。本論文の差分は、ブロックの位置移動という未踏の領域について忠実度の境界を実測で画定したことと、その境界を理由に、ルーティングと引数生成を接合経路から完全に分離し、接合を保証つきの副次的な加速へ格下げした設計判断にある。

## 限界・実装状況

最大の限界は評価範囲である。全ての定量結果がApple M4 Maxと1つのモデルタプルに限られ、標本数も小さい。深い接合は複数ターンの本番経路として未検証で、転置V接合は統合メモリ専用、クラウドと離散GPUはテキストプリフィルへ戻る。検索の天井も残り、紛らわしいツールの混同はゲートで除けない。実装はllama.cpp上のプロトタイプで、論文中に公式コードの公開URLは示されず、成果物は著者への請求で入手可能とされている。

## 一般的な実装上の含意

KVキャッシュの再利用を設計するときは、位置を動かすかどうかを最初に切り分けるべきである。動かす場合は、首位トークンの一致のような弱い指標ではなく分布の発散で忠実度を測り、修理費用が深さでどう増えるかを見積もる必要がある。また、安い代理指標でドリフトを予測する試みは実測で失敗しており、参照なしゲートへの依存は危険である。意味的な判断はテキストと検索の側へ寄せ、キャッシュ操作は保証が取れる範囲へ限定する分離は、他のエージェント基盤でも再利用できる。
