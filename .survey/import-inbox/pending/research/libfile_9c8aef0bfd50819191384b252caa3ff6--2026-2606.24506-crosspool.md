# CrossPool: Efficient Multi-LLM Serving for Cold MoE Models through KV-Cache and Weight Disaggregation

## 概要

多数のLLMを常時提供すると、少数の人気モデル以外は要求率が低い「cold
model」になる。MoEではFFN専門家重みが巨大で固定的なのに対し、KVキャッシュは要求がある間だけ増減する。各モデルへ最大KV容量を予約すると無駄だが、重みとKVを同じGPU
memory poolで共有するだけでは、重みがKV領域を圧迫し、MQA/MLAのようなKV
head数の少ないattentionでは低並列時に各requestから見えるKV容量も小さい。

CrossPoolはGPU群を**KV-cache pool**と**weights
pool**へ物理的に分ける。attentionと非FFN部分はKV側で実行し、MoEパラメータの大半を占めるFFNだけをweights側で実行する。pool間で移すのは文脈長とともに増えるKVではなくhidden
stateである。5台のA100
40GBでQwen3-30B-A3B、GLM-4.7-Flash、DeepSeek-V2-Liteを同居させ、kvcached比でP99
token間時間（Time Between Tokens; TBT）を最大10.4倍改善した。

## 問題設定

KV head数がGPU数以上ならtensor
parallelismで1要求が複数GPUのKV容量を利用できる。しかしMQA/MLAやhead数の少ないGQAではdata-parallel
replicaへ分かれ、低concurrencyでは要求が載ったreplicaのKV領域しか使えない。4GPUでMQAなら単一要求から見える容量が全体の1/4になる例が示される。

既存multi-LLM memory poolingは重みとKVを同じpoolに置くため、cold
modelの巨大な固定重みが一時的なKV領域と競合する。単にpoolを分けると今度は全層でattention↔FFN間のhidden-state通信が発生し、hostから細粒度にdispatchするとCUDA
graphの利点も失われる。

## 手法

### KV-cache plannerとvirtualizer

各モデルのprompt長、出力長、service time、arrival rate、token当たりKV
bytesを使ってaggregate KV需要を見積もり、共有poolのpage
budgetとrank配置を決める。異なるMHA/GQA/MQA/MLAのKV形状を同一固定配分で扱わず、cold
traffic全体の需要分布に合わせて容量を公開する。

### 重み/KV分離

KV poolにはattentionと非FFN module、KV pagingを置く。weights
poolには複数モデルのFFNを集約する。Qwen3-30B-A3Bでは29.0B/総FFN share
95.0%、GLM-4.7-Flashは28.3B/94.5%、DeepSeek-V2-Liteは14.9B/95.0%がFFNなので、巨大な固定部分をKV
poolから外せる。pool境界ではhidden stateだけを送るため通信量はbatch
token数×hidden dimensionで決まり、蓄積context長には比例しない。

### 層単位pipeline

request batchはKV poolでattentionを実行し、hidden stateをweights
poolへ送りFFNを計算し、結果をKV poolへ戻す。複数のin-flight
batchを層単位で組み、あるbatchの通信待ちを別batchのattention/FFN計算で重ねる。KV本体を遠隔参照しないため、decodeの毎tokenで巨大KVをpool境界越しに読むことを避ける。

### persistent kernelとcontrol lowering

attention subgraphとFFN subgraphを別々にgraph
captureし、GPU常駐persistent
kernelへhandleを渡す。GPU上のqueueをpollしてready batchを選び、graph
dispatch、pool間通信、state更新までGPU側で繰り返す。hostはadmissionやKV
page mappingなど粗粒度制御だけを担い、各layer
transitionでCPUへ戻らない。

## 評価条件

  項目            内容
  --------------- ---------------------------------------------------
  GPU             5×NVIDIA A100 40GB、NVLink
  対象モデル      Qwen3-30B-A3B、GLM-4.7-Flash、DeepSeek-V2-Lite
  総weight規模    3モデルで約154GB HBM
  実装            SGLang v0.5.10拡張
  比較            Static Partition、Chimera/kvcached
  短文/通常負荷   Vicuna ShareGPT、0.2〜1.0 RPS/model
  長文脈          LongAlign
  主指標          最大aggregate RPS、P95/P99 TBT、output throughput

## 主要結果

0.8 RPS/modelのShareGPTで、kvcachedに対するP99 TBT改善はQwen3-30B-A3B
7.6倍、DeepSeek-V2-Lite 10.4倍、GLM-4.7-Flash 7.3倍。1.0
RPSではそれぞれ2.1倍、5.0倍、2.2倍まで縮む。kvcachedはmulti-model
concurrencyでSM・memory bandwidth・KV容量の競合が増え、tail
latencyが悪化する。

LongAlignの長文脈評価では、Static
Partitionとkvcachedはper-model/per-replica
KV容量を使い切ると長いbinを処理できなくなる一方、CrossPoolは同じ5GPU予算で共有KV
poolを公開し、評価範囲全体で正の最大RPSを維持する。ただしStatic
Partitionは分離通信を持たないため、処理できる通常長requestでは最小latencyであり、CrossPoolの目的は単一モデルの絶対最小遅延ではなくcold
model群の長文脈容量との両立である。

## 既存研究との差

kvcached/ChimeraはGPU
memoryをelasticに共有するが、重みとKVを同じpoolに置く。CrossPoolは寿命と需要特性が異なる固定FFN重みと動的KVを別GPU群へ分離する。MegaScale-Infer等のattention/FFN分離は大規模MoEのthroughputが主目的だが、CrossPoolはcoldな複数モデルの共有KV容量を増やすことを主目的にする。

## 限界

A-to-FとF-to-Aのhidden-state転送は完全には隠れずクリティカルパスに残る。異なるモデルのattention/FFN時間差が大きいとpipeline
imbalanceが起き、短いstageが長いstageを待つ。現実装のgraph captureはcold
decodeで典型的なbatch
1〜4を主対象とする。prefillは別の時間多重化engineで処理し、評価もdecode側が中心である。
