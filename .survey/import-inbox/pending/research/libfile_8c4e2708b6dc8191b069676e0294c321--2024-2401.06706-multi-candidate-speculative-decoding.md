# Multi-Candidate Speculative Decoding

## 概要

通常の投機的復号（Speculative Decoding; SD）は、小さなドラフトモデルが複数トークンを先読みし、大きな対象モデルがその系列を1回の並列forwardで検証する。対象モデルの呼出回数を減らせる一方、先頭側の候補が棄却されると後続候補は使えない。このため、ドラフト長を単純に伸ばしても限界効用が急速に低下する。さらに対象モデルのfine-tuning、長いprompt、標準サンプリングなどでドラフトと対象モデルの出力分布がずれると受理率が低下し、SDの高速化も縮む。

Multi-Candidate Speculative Decoding（MCSD）は、系列長方向だけでなく候補方向にも余っている並列計算資源を使う。ドラフト生成の各位置で1候補ではなく複数候補を作り、候補木を対象モデルでまとめて検証する。単に候補を増やすだけでは対象モデルの分布を変えてしまうため、論文は対象分布を厳密に保存する多候補投機的サンプリング（Multi-Candidate Speculative Sampling; MCSS）を導入する。さらに重複候補を避ける非復元抽出版と、共有prefixのKVキャッシュ複製・転送を避ける木注意（Tree Attention）を組み合わせる。

4基のNVIDIA RTX A6000 48GBを使い、LLaMA/Vicuna 13B・33Bを対象モデル、LLaMA-68M/160MをドラフトモデルとしてAlpacaとWMT En-Deで評価した。LLaMA-68M→Vicuna-33B、標準サンプリングでは、最適な通常SDがAlpacaで1.34倍、WMTで1.14倍なのに対し、MCSDはそれぞれ1.73倍、1.42倍の実時間高速化を得た。通常SDが既に強いLLaMA-33B・Alpaca・argmaxでは2.89倍から3.06倍への改善に留まり、MCSDの価値はドラフトと対象の分布差が大きい条件ほど大きい。

## 問題設定

SDでは、長さγのドラフト系列を対象モデルが並列評価し、各位置を先頭から順に受理する。候補トークン x̃ は対象分布 p とドラフト分布 q の比に基づき `min(1, p(x̃)/q(x̃))` の確率で受理され、棄却時には残差分布から補正トークンを生成する。この補正により、ドラフトモデルを使っても最終出力は対象モデル単独と同じ分布になる。

性能を決める重要な量は、各位置の候補が通る確率である受理率 α と、対象モデル1回の検証blockから平均何トークン進められるかを表すblock効率 τ である。αが低いと先頭付近で検証が止まり、γを長くしても後半の計算は使われない。論文の測定ではLLaMA-68M→LLaMA-33BのargmaxでAlpacaのαは0.75だが、fine-tuned Vicuna-33Bでは0.52、WMTでは0.22まで下がる。標準サンプリングではさらに低下する条件がある。

この低受理率をドラフト系列の延長だけで補うと、後続位置は前位置が受理された場合しか到達できないため効率が悪い。MCSDは、同じ検証予算を系列長だけでなく候補幅へ割り当て、各位置で「どれか1候補が対象モデルに合う」確率を高める。

## 手法

### 多候補投機的サンプリング

各生成位置 i でドラフト分布 q から k_i 個の候補を作る。対象モデルは候補をまとめて評価し、検証器は候補を順に試す。候補が受理されるたびに、その候補を含む枝だけを次位置の検証へ残す。全候補が棄却された時点では残差対象分布からendpointトークンを生成してblockを終了する。

MCSSでは候補を1つ棄却するたび、対象側の残差分布を `max(p-q,0)` に基づいて正規化し直してから次候補を検証する。この反復によって複数候補を試しても、最終的に返されるトークン分布が対象モデルの p と一致することを付録で証明している。したがってMCSDは「複数候補の多数決」で品質を変える近似復号ではなく、対象分布を保ったまま受理機会を増やす方式である。

### 非復元抽出

同じqから独立にk個を抽出すると、kが大きいほど同一トークンが重複する。ある候補が一度棄却されると、そのトークンの残差対象確率は0になるため、同じ候補を再び試しても受理率を増やせない。そこで非復元抽出版は、選んだ候補のq確率を0にして残りを再正規化し、次候補を異なるトークンから選ぶ。

検証側も対象残差pだけでなく、選択済み候補を除いたドラフト残差qを更新する。この版についても対象分布pを保存することが証明されている。ただし実験ではk_iが小さいと重複自体が少なく、非復元抽出による追加改善は限定的だった。

### 候補木と木注意

候補を通常のbatchとして複製すると、全枝が同じ長いprefixを持つにもかかわらず、対象モデルとドラフトモデルのKVキャッシュを候補数だけ複製して各層へ転送する必要がある。MCSDは候補をk分木として1本の物理sequenceへ詰め、各tokenが自分の祖先だけを参照できるattention maskを作る。位置符号は元の枝上の位置を維持する。

これにより共通prefixと祖先tokenのKVを子孫間で共有できる。sequence自体は候補token分だけ長くなるため演算量は増えるが、論文ではprefixが候補列より通常かなり長いため、追加計算よりKV通信削減の方が大きいと説明する。構成要素除去でも木注意はblock効率τをほぼ変えずに実時間を改善し、通信削減が主要効果であることが確認されている。

### 候補予算の配分

γ個の位置で候補数を `k_1 × k_2 × ... × k_γ` とすると、候補木の総予算Kは積で増える。論文はK≤32、各k_iを1/2/4/8/16/32から探索する。同じKなら後段より前段へ候補を多く配る単調減少構成、例えば `4×2` が `2×4` より一貫して良い。後段へ到達するには前段受理が必要だからである。

一方、候補数を増やせば常に速くなるわけではない。13B評価では32候補予算は16候補よりblock効率が高いにもかかわらず、候補batchを処理する遅延が増えてwall-clock speedupは低下した。受理率曲線もk>32付近で飽和するため、幅の拡大には明確な逓減がある。

## 1回の生成block

現在のcontextからドラフトモデルが位置ごとに複数候補を生成し、候補木を構築する。木注意用maskによって各候補は自身の祖先だけを参照し、共有prefixのKVは複製しない。対象モデルが候補木全体を並列forwardし、各枝・位置の対象分布pを得る。検証器はroot側からMCSSを適用し、受理された候補の枝だけを次段へ進める。全候補棄却なら残差pからendpointを生成し、最後まで候補が生き残ればその枝に対応する対象分布から追加tokenを生成する。この一連の出力分布は対象モデル単独と同一である。

## 評価条件

| 項目 | 内容 |
|---|---|
| GPU | 1ノード、4×NVIDIA RTX A6000 48GB |
| 精度 | 半精度 |
| 対象モデル | LLaMA / Vicuna 13B・33B |
| ドラフトモデル | LLaMA-68M / LLaMA-160M。追加一般化評価でfine-tuned Vicuna draft、LLaMA2、OPT |
| 配置 | 13Bは1 GPU、33Bは2 GPU。ドラフトは対象モデルと同居し追加GPUなし |
| データ | Alpaca会話、WMT En-De翻訳 |
| 生成長 | 最大128 new tokens |
| 復号 | argmax（temperature 0）、標準sampling（temperature 1） |
| 候補予算 | `K=∏k_i ≤ 32`、`k_i ∈ {1,2,4,8,16,32}` |
| 指標 | 受理率α、block効率τ、wall-clock speedup |
| 比較 | autoregressive baseline、同じγのSD、最適γのSD |

## 主要結果

| 条件 | 最適通常SD | MCSD | 読み取れること |
|---|---:|---:|---|
| LLaMA-68M→LLaMA-33B、Alpaca、argmax | 2.89× / τ=3.70 | 3.06× / τ=3.93 | 元の受理率が高い条件では追加幅の利得は小さい |
| LLaMA-68M→Vicuna-33B、Alpaca、argmax | 1.70× / τ=2.03 | 2.06× / τ=2.56 | fine-tuningによる分布差でSDが弱くなると幅方向探索が効く |
| LLaMA-68M→Vicuna-33B、Alpaca、標準sampling | 1.34× / τ=1.58 | 1.73× / τ=2.10 | 低受理率条件で実時間差が拡大 |
| LLaMA-68M→Vicuna-33B、WMT、argmax | 1.15× / τ=1.29 | 1.45× / τ=1.73 | promptが長いWMTで通常SDが弱い条件を改善 |
| LLaMA-68M→Vicuna-33B、WMT、標準sampling | 1.14× / τ=1.31 | 1.42× / τ=1.70 | 厳しい組合せでも通常SDを上回る |
| LLaMA-160M→LLaMA-33B、Alpaca、argmax | 2.16× / τ=3.49 | 2.42× / τ=3.87 | 大きいdraftの追加latencyを受理率改善で一部相殺 |
| 構成要素除去、LLaMA-68M→LLaMA-33B、Alpaca、標準sampling | — | MCSS非復元+木注意 2.17×、木注意なし1.84× | 木注意はτを2.71→2.68とほぼ維持しつつ通信削減でwall timeを改善 |

一般化評価ではAlpacaでkを1から4へ増やすと、LLaMA-68M→LLaMA-13Bの標準sampling受理率は0.51→0.72、LLaMA2-13B-chatは0.35→0.57、OPT-125M→OPT-13Bは0.63→0.81へ改善した。fine-tuned Vicuna-68M draftでもVicuna-13Bのargmax受理率は0.56→0.76となり、ドラフトfine-tuningと多候補化を併用できる。

## 既存研究との差

通常SDは1位置につき1候補の一本道を検証し、受理率が低いと長いγを用意しても先頭棄却で後段を使えない。MCSDは同じ対象モデルforwardに候補幅を追加し、余っている並列予算を「さらに遠い未来」ではなく「同じ位置の別候補」へ配る。

複数候補を扱う先行方式には複数ドラフトモデルを使う方式やMedusaのように追加prediction headを学習する方式がある。MCSDは1つの既存ドラフトモデルから複数sampleを生成し、対象分布を保存する検証アルゴリズムを組み合わせるため、候補多様化のために複数モデルや対象モデルへの追加head学習を必須としない。またTree Attention自体を新規提案するのではなく、多候補SDで発生する共有prefixのKV複製問題を抑える構成要素として採用する。

## 限界

候補幅には計算・メモリ費用があり、Kを増やすほど高速になるわけではない。実験ではk>32で受理率改善が飽和し、32-budgetは16-budgetよりblock効率が高くてもwall-clock speedupが低い条件がある。したがって最適なk構成は対象モデル、ドラフトモデル、データ、sampling設定、hardwareのbatch並列性能に依存する。

利得も元のSD受理率に依存する。LLaMA→LLaMA、Alpaca、argmaxのように通常SDが既に2.89倍まで高速化できる条件ではMCSDは3.06倍で差が小さい。一方Vicuna、WMT、標準samplingでは差が大きい。MCSDは低受理率を改善する方式であり、あらゆる条件で大幅な追加高速化を保証するものではない。

主な実時間評価はRTX A6000の単一ノード、13B/33B級モデル、最大128生成tokenで行われている。より新しいGPU、大規模サービングbatch、70B超、長文脈生成で候補幅と木注意の費用がどう変わるかは本論文の主要評価範囲外である。
