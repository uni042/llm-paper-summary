# TyphoonMLA：共有prefixを計算効率の高いMLA形式で処理する推論カーネル

## 概要

TyphoonMLAは、DeepSeek-v3やKimi K2に採用される多頭潜在注意（Multi-Head Latent Attention、MLA）で、複数要求が同じ入力prefixを共有する場合のデコードを高速化する。MLAはKVキャッシュを低ランク空間に圧縮することで大域メモリからの転送を減らすが、一般的な復号用の吸収型（absorb）計算は演算律速になりやすい。共有prefixを多数の要求で再利用しても、圧縮KVの読み出し回数を減らすだけでは十分な速度向上を得られない。

提案方式はMLAの数学的に等価な二つの計算経路を使い分ける。共有prefixについては、低ランクKVを各ヘッドのK/Vに展開する素朴型（naive）注意を使い、要求固有のsuffixには圧縮KVを保った吸収型注意を使う。両者の出力は対数和指数（log-sum-exp、LSE）を使ってsoftmaxの分母を整合させて結合する。近似的なKV削除やモデル再学習を導入する方式ではない。

原著のカーネル実測は、Ascend NPUで最大3.0倍、GPUで最大3.24倍の注意処理量改善を報告する。ただし「モデル全体最大1.48倍」は、GPU上の注意時間の測定値とDeepSeek-AIが公表した他層のプロファイルを合成した**推定値**であり、128 GPUで全モデルを稼働させて直接測った速度ではない。HBM容量増分約3%も特定の384 NPU配置を仮定した解析である。測定値・推定値・メモリモデルを分けて解釈する。

## 問題設定

標準的な多頭注意では各ヘッドのKとVをトークンごとに保存するため、長文脈や大バッチではHBMの容量と帯域が制約になる。MLAは低ランク潜在ベクトルと位置埋め込み用の小さな成分を保持することで、この転送量を減らす。MLAの射影行列の掛け順を変えると、KVを展開した状態で標準的な注意を計算するnaive方式と、射影をQuery側・出力側に移して圧縮KVを読み込むabsorb方式の二つが得られる。

naive方式はヘッド当たりの注意計算が軽い一方、展開したK/Vを保持・読み出すのでメモリ帯域を消費する。absorb方式は転送するKVを減らす一方、Query側の積の次元が大きくなり演算回数が増える。単一要求の復号では後者が有利になりやすいが、共通のシステムプロンプトや同じ履歴から分岐した複数の候補を大バッチで同時処理すると、共有prefixに対するabsorbの演算を各要求で繰り返すことが無駄になる。

従来のprefix共有やページングは同じKVの重複保存・転送を避けるが、MLAのabsorbで生じる算術演算自体を削減するとは限らない。TyphoonMLAはこの計算律速と帯域律速の境界に着目し、共有prefixだけをnaiveへ切り替える。共通prefixが短い場合や要求数が少ない場合には、naiveの大きいKV読み出しが逆に不利になるため、条件に応じた切替も必要である。

## 手法

### 1. 共有prefixと要求固有suffixを異なる形式で保持

prefillでは、共通prefixと各要求の個別suffixを含む木状の入力集合を、prefixを認識するnaiveカーネルで処理する。MLAがもともと保持する低ランクの位置埋め込み成分（PE）と非位置埋め込み成分（noPE）を作り、共有prefixに対応する部分だけ上方射影で展開して各ヘッドのK/Vキャッシュを得る。この展開済み共有KVは複数のQueryから参照できる形で保存する。一方、要求固有のsuffixはPE/noPEの圧縮形式のまま保持する。

共有KVを展開して保存するため、absorb-onlyよりHBM使用量は増える。原著はprefillで既に行うnaiveの射影を利用するため、共有部分の上方射影自体に追加の演算を必要としないと説明する。ただし、展開結果を保存する容量、prefix管理、異なる形式を読み分ける処理は残る。共有prefixの長さと再利用要求数が損益を左右する。

### 2. デコードで二つの注意を別々に計算

デコードではQueryを位置埋め込み成分とそれ以外へ分割し、共有prefix側では展開済みK/Vを使うnaive注意を実行する。要求固有suffix側では、QueryにKVの上方射影の一部を吸収した表現を作り、圧縮されたPE/noPEキャッシュを使ってabsorb注意を実行する。absorb側の出力には必要な射影を戻す。前者は共有部分の演算数を、後者は非共有部分のKV転送量を抑える。

二つの部分注意は、それぞれ独立にsoftmaxで正規化される。共有側の出力を`O_N`、対数正規化量を`l_N`、非共有側の出力を`O_A`、対数正規化量を`l_A`とすると、全体の出力は概念的に`(exp(l_N) O_N + exp(l_A) O_A) / (exp(l_N)+exp(l_A))`となる。実装では数値安定性のため最大値を引いた指数を使う。単純な`O_N+O_A`では各部分の確率質量を正しく統合できない。原著Algorithm 1のCombineLSEはこの整合を保証するための処理である。

CombineLSEの計算量はQuery数と出力ヘッド次元に依存するが、KVの系列長には比例しない。長い共有prefixで削減できるQK/V演算に比べれば小さいものの、短い系列では相対的な固定費となる。数学的な等価性は近似的な注意削減を行わないことを意味するが、浮動小数点の演算順序が変わるためbit単位の同一性まで保証するものではない。

### 3. 演算量と帯域の解析

共有prefix長を`Ls`、個別suffix長を`Ln`、バッチを`B`、Query長を`Sq`、ヘッド数を`H`とする。原著Table 1はDeepSeek-v3の次元を代入した演算量の係数を示す。naiveの共有部分は`40×B×Ls`、absorbは`136×B×Ls`（いずれも1024単位のMAC）である。TyphoonMLAは共有側を40、非共有側をabsorbと同じ136にするので、共有側の積和演算数をabsorbの約1/3.4へ削減する。

他方、非共有側のHBM読み出し係数はnaiveの40に対してabsorb/TyphoonMLAが0.56であり、理論上の転送係数差は約70倍となる。これはカーネルが実際に70倍速いという意味ではなく、対象部分のメモリ読み出し量の解析である。両形式の利点を同時に得るには、共有prefixが大きく、十分なQueryが同時にそれを参照することが必要である。

### 4. 小バッチでのabsorbへのフォールバック

共有prefixの展開KVを読むnaive方式は、バッチが小さいと読み出し費用が大きくなる。原著はGPU/NPUの計算性能`T`、HBM帯域`M`、MLAのヘッド次元とQuery長から損益分岐バッチ`Bθ`を求め、これより小さい場合はabsorb-onlyを選ぶ。DeepSeek-v3と論文のAscend NPU（FP16理論376 TOPS/s、帯域1.8 TB/s）の組合せでは閾値が約61である。

この61は実験環境に依存するモデル上の閾値であり、別のGPUやモデルの固定設定として流用できない。実際のNPU遅延内訳図ではバッチ128未満をabsorbへ切り替えるため表示していない。小バッチのローカル対話では提案方式の利得がほとんど出ない可能性がある。モデルの重みを変えずに実行経路を切り替えられることが、品質を保ちながら負の条件を避ける設計上の要点である。

## 評価

### 評価環境・比較対象

| 項目 | 原著の条件 |
|---|---|
| 対象モデル | DeepSeek-v3、Kimi K2のMLA注意層 |
| NPU | Ascend、24 DaVinciコア、HBM 64GB、FP16理論376 TOPS/s、1.8TB/s |
| GPU | FP16理論1 PFLOPS/s、HBM帯域3.3TB/s（原著の記載値。機種名は補わない） |
| 実装 | NPUはCANN、CATLASS、TorchNPU。GPUはFlashInfer naive/absorbカーネル |
| 比較方式 | NPUはTorchNPU PagedAttentionMLAとCATLASS absorb-only。GPUはFlashMLAとFlashInfer absorb-only |
| ワークロード | MMLU、GSM8K、SimpleQAの質問を連続バッチで処理 |
| 共通prefix | Prompt A: 26,472、B: 7,069、C: 4,759トークン |
| バッチ | 64、128、256、512、1024。ページ型KVのブロック長128 |
| 実測指標 | 注意カーネルの層当たり生成トークン数/秒、NPUの注意内部時間 |
| 別途推定 | DeepSeek-v3の128 GPU構成での全体生成処理量、384 NPU配置のHBM容量 |

実験は、質問の処理が終わると次の質問を補充する連続バッチを模擬し、デコード反復全体で生成したトークン数を所要時間で割って注意カーネルの処理量を計算する。比較は最も良いベースラインに対して行う。これは全サービスのリクエスト到着分布、キュー待ち、通信を含むエンドツーエンドのSLO測定とは異なる。比較対象の一部がHBM不足で実行不能だった棒を、速度ゼロの測定値として解釈してはいけない。

### NPU・GPU注意カーネルの実測

Ascend NPU上ではDeepSeek-v3/Kimi K2、三つのデータセットと三種類のprefix長、バッチ64〜1024で、比較カーネル比約1.2〜3.0倍の処理量改善を報告する。共有prefixが長いPrompt Aで利得が大きく、Kimi K2はDeepSeek-v3よりヘッド数が少ないため、共有データ再利用の利点が大きいと著者らは説明する。これは層当たり注意処理量の測定であり、全モデルのtoken/sではない。

GPU実装はFlashInferのnaive/absorbカーネルを組み合わせ、FlashMLAおよびFlashInfer absorb-onlyと比較する。最大3.24倍はGPU上の注意カーネル処理量である。NPUとGPUでは使用するカーネル実装が異なるため、同じコードの単純な移植で得た倍率と解釈しない。さらに、共通prefixが短いPrompt Cでは、共有側の演算削減が全体注意時間に占める割合も小さくなる。

### 内部遅延内訳と理論解析の対応

原著Figure 4では、Kimi K2相当、共有prefix4096、非共有suffix512、バッチ1024の条件で、CATLASS absorb-onlyの注意部分が6.43ms、TyphoonMLAの共有naive部分が1.63ms、非共有absorb部分が1.06msであった。比較対象の共有部分を6.43−1.06=5.37msと推定すると、共有側の実行時間比は5.37/1.63≈3.29倍となる。これはTable 1の共有MAC係数136/40=3.4と整合するが、射影、結合、他層を含む全モデル速度が3.29倍になることを意味しない。

原著はバッチ128未満ではabsorb-onlyへ戻すため、この遅延内訳図には小バッチの棒を掲載していない。切替により不利な領域を避ける設計ではあるが、異なるハードウェアの小バッチで常に同じ閾値や速度を保証する実測ではない。データセットによってprefix共有の発生頻度が異なる場合のオンライン適応にも注意が必要である。

### 全体生成速度の推定値と負の条件

原著Table 3はDeepSeek-v3、GPU当たりバッチ128、128 GPUの想定構成について、注意層の実測時間とDeepSeek-AI公開の他層プロファイルを組み合わせて全体のトークン生成率（TGR）を推定したものである。値の意味を取り違えないよう、注意時間と全体時間を並べる。

| 共通prefix | FlashMLA注意/全体時間 | TyphoonMLA注意/全体時間 | FlashMLA TGR | TyphoonMLA TGR | 推定改善 |
|---|---|---|---:|---:|---:|
| A（26,472） | 99.1 / 127.2 ms | 58.1 / 86.3 ms | 1.01 kToken/s | 1.48 kToken/s | 約1.47倍 |
| B（7,069） | 34.5 / 62.6 ms | 25.9 / 54.0 ms | 2.04 kToken/s | 2.37 kToken/s | 約1.16倍 |
| C（4,759） | 26.9 / 55.0 ms | 22.0 / 50.1 ms | 2.33 kToken/s | 2.56 kToken/s | 約1.10倍 |

最大1.48倍という要旨の表現はAの丸めを含む全体TGR推定に対応する。共有prefixが短くなると推定改善は約1.10倍まで縮む。全体の他層（MoE、射影、集団通信など）は同じ時間のままという仮定を含み、128 GPUクラスタを実際に稼働させた結果ではない。したがって運用中の実測スループット、TTFT、TPOT、SLO達成率をこの表から確定することはできない。

### HBM容量とスケーリングの制約

共有prefixのKVを展開するため、HBM容量はabsorb-onlyより増える。原著Figure 5はDeepSeek-v3を384 NPUに配置し、expert parallelismとdata/tensor/sequence parallelism（それぞれ24/4/4の係数）を仮定して、バッチ4K〜32K、最大文脈32K〜256Kでメモリを解析する。共有prefixはPrompt Aを使用し、重み・KVはFP8を仮定する。著者の見積りでは追加HBMはおおむね3%以内である。

ただし、共有prefixを複数の物理コピーとして保存する場合、prefixが極端に長い場合、単一GPUへ多くの層を置く場合には増分が変わる。Figure 5の割合はあくまで指定された並列化・prefix共有条件の解析値であり、すべてのデバイスに普遍的な定数ではない。非共有suffixが長いほどabsorb側のKVが支配的になり、相対的な追加容量が小さくなるという仕組みを押さえる必要がある。

## 既存研究との差

FlashMLAやThunderMLAはabsorb形式のMLA注意を高速化するが、共有prefixを多数のQueryが使う場合の演算量削減を主眼にしない。TyphoonMLAはabsorbを捨てず、共有部分だけnaiveへ変えて演算律速の箇所を軽くする。FlashAttentionやFlashInferがMHA/GQAのメモリ移動を減らすのに対し、MLA固有の低ランク射影の掛け順を使い分ける点が新しい。

PagedAttentionやRadixAttentionはprefixの物理的な共有、ページ配置、再利用可能なKVの識別を扱う。TyphoonMLAはその上で動く注意計算の実装であり、prefix treeの管理や要求スケジューリングを置き換えない。Tensor parallelismとsequence parallelismとの互換性は述べられるが、異種GPU混在や大規模クラスタの通信・待ち行列まで最適化した研究ではない。

## 限界・品質への影響

提案方式の利得は、長い共通prefixを十分な数のQueryが同時参照することに依存する。共通prefixが短い、suffixが長い、prefix cacheが頻繁に失効する、少数同時要求しかない場合にはnaive経路を使う意味が薄い。論文の小バッチfallbackはこの負の条件への対処であり、全条件で一律に3倍高速化するという主張ではない。

KVを削除したり注意を近似したりせず、二つの数学的に等価なMLA形式を使うため、モデル重みや学習データを変えない。しかし数値演算順序による浮動小数点の差はあり得る。大量の下流タスクでの品質差、オンラインprefix共有率の変化、実際の通信・ロードバランス・混合prefill/decode下でのSLOは論文の主な実証対象ではない。注意層単体の性能を、実サービス全体の性能保証へ読み替えないことが重要である。
