# CalibQuant：視覚KVキャッシュの1bit量子化と注意スコア較正

## 概要

Insu Hanほか、*CalibQuant: 1-Bit KV Cache Quantization for Multimodal LLMs*、arXiv:2502.14882v2、2025年3月24日改訂。2025年2月のv1は「From 16-Bit to 1-Bit: Visual KV Cache Quantization for Memory-Efficient Multimodal Large Language Models」という別題で登録されていたため、worklistの古いタイトルを別論文と誤認しない。canonical identityは同じ **arXiv:2502.14882** である。

マルチモーダルLLMでは画像パッチや動画フレームに対応する視覚トークンが大量に生成され、デコード中のKey/Value（KV）キャッシュがGPUメモリを圧迫する。CalibQuantは視覚トークンのKVを極低bit整数で保持し、復元誤差を抑える注意スコア較正と、デコード演算を直接行うTriton kernelを組み合わせる。主張は、**視覚トークンのKVキャッシュを圧縮し、限られたメモリ予算下でバッチ数を増やしてデコードスループットを上げる**ことであり、モデル重みを1bit化する方式ではない。

主結果はCOCO Caption、DocVQA、MMBench-VideoとH100 80GBでのスループット評価である。InternVL2.5-8B、視覚トークン約3,328、デコードに使えるメモリ予算5〜30GBの実験では、1bit CalibQuantが16bitベースライン比約9.88〜11.24倍のスループットを示す。ただしこの倍率はメモリ予算を固定し、入る最大バッチをそれぞれ選んだ**デコード段階の総生成token/s**であり、単一要求のレイテンシ改善率や画像エンコーダを含むE2E高速化率ではない。

## 問題設定

自己回帰デコードでは過去トークンのKとVを保持し、各新トークンのqueryとの注意計算に再利用する。入力画像の高解像度化や動画の長時間化で視覚トークン数が増えると、キャッシュ容量は系列長に比例して増大する。キャッシュをFP16で保持すると、モデル重みと競合してバッチサイズが制限され、GPUメモリの不足がスループットを律速する。

既存の選択肢には、重要度の低い視覚トークンを削除する方式と、全トークンを残してKV値を低bitにする方式がある。前者は視覚情報を捨てるリスクを伴う。後者は1bitに近づくほど量子化誤差が大きく、注意スコアの極端な値を増幅しやすい。CalibQuantは**トークンの削除ではなく低bit表現の保持**を選び、視覚KVの分布に合わせたチャネル単位量子化と、softmax前の補正を設計する。

## 手法

### 1. KeyとValueのチャネル単位一様量子化

KeyキャッシュをK∈R^{n×d}とすると、nは視覚トークン数、dは各ヘッドの次元である。一般的なb-bit一様量子化では範囲[α,β]を2^b個の離散値へ写し、量子化整数を保存する。全要素で一つの範囲を使うと、外れ値を持つチャネルが量子化刻み幅を支配し、その他のチャネルの分解能が失われる。

CalibQuantは各チャネルiごとにα_i=min_j K_{j,i}、β_i=max_j K_{j,i}を求める。これによりチャネルごとの値域を使って量子化する。KIVIが言語モデルでKeyをチャネル単位、Valueをトークン単位に量子化したのに対し、CalibQuantは視覚KVでは**KeyとValueの双方をチャネル単位**にした方がよいと観測した。特に1bitでは各値は下限・上限の2候補へ写されるため、値域の取り方が出力誤差を大きく左右する。

### 2. Post-scalingでKeyの復元をquery側へ移す

チャネルごとの復元は k_deq = k_int⊙s + α（s=(β−α)/(2^b−1)）である。デコードで必要なq・k_deqは、代数的に (q⊙s)・k_int + q・α と等価になる。ここで**長い系列のKeyを全てFP16へ復元する代わりに、一つのquery側へscaleを掛けてから量子化整数と内積を取る**。queryはデコード時には基本的に新トークン1個なので、系列長nに比例する復元計算・メモリ転送を避けやすい。

これは数学的な式変形であり、元の浮動小数点Kを完全に再現することではない。量子化による情報損失は残る。Value側にも類似のpost-scalingを適用できる。重要なのは量子化されたK/Vを低bitのまま処理し、attention演算へ必要な補正を融合することで、圧縮によるメモリ利得を不要な復元で失わない点である。

### 3. Softmax直前のスコア較正

一様量子化の復元値は、特に1bitでは各チャネルの最小値か最大値に固定される。結果としてqK^T/√dの分布がFP16時より極端な値へ偏り、softmaxの確率質量が誤った位置へ集中する可能性がある。著者はInternVL2.5-8BのCOCO Caption例で、量子化前後のpre-softmaxスコア分布を比較し、単純量子化の外れ値増加を確認した。

CalibQuantは量子化後のスコア範囲[γ,δ]を、両端の補正量τ1,τ2で線形変換g(x)し、softmax(g(qK_deq^T/√d))を計算する。較正パラメータはτ1,τ2∈{0,1,2,3}をgrid searchし、選んだ値を入力・層・headにわたって固定する。図1ではスコア分布の過度な裾が抑えられ、図2では注意重みのMSEが単純量子化より小さくなると報告する。**1bitの値そのものを高精度へ戻すのではなく、最終的な注意確率の歪みを補正する**アプローチである。

### 4. Tritonによるpackingと融合kernel

1bitをそのまま扱う汎用の高速行列積命令がGPUに用意されているとは限らない。CalibQuantは複数の量子化値を8bit等の整数単位へpackingし、Triton kernelの内部でunpackと演算を融合する。Key側のqK_int^Tでは短いqueryを共有メモリへ保持し、圧縮Keyのタイルを順に読み出して内積を計算する。Value側のwV_intでは長い系列方向の重みwを共有メモリに保持し、細粒度にSMへ仕事を分配する。

アルゴリズム1・2は、前者のqK内積と後者の注意重み付きValue集約を別々に最適化する構造を示す。単に保存bit数を減らすだけではpacking/unpackingやscale計算の追加費用が速度を相殺し得るため、**kernel融合とメモリ読み出し削減が実測高速化の前提**になる。公式コードは著者のGitHub `insuhan/calibquant` へのリンクが一次論文に明記されている。

## 評価

### 実験環境・比較方法

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA H100 80GB |
| 対象モデル | LLaVA 1.5 7B/13B、InternVL2.5 8B/26B |
| 画質・文章生成 | COCO Caption：SPICE、BLEU、METEOR、ROUGE-L、CIDEr |
| 文書理解 | DocVQA（一次論文§5.2） |
| 動画理解 | MMBench-Video：Perception / Overall |
| 比較手法 | 16bit KVベースライン、KIVI、VLCache、CalibQuant（Ours） |
| 量子化bit幅 | 主に8/4/2/1bit。FP16を品質基準とする |
| 性能計測 | InternVL2.5 8B/26B、視覚トークン約3,328および8,192、GPUメモリ予算5〜30GB、予算内最大バッチのデコードtoken/s |

量子化対象は視覚KVである。全てのKVが常に1bitという意味でも、モデル重みが1bitになるという意味でもない。16bit→1bitなら視覚KVの**量子化値本体**の理論サイズは1/16だが、scale/bias、packing境界、非視覚KV、その他の活性・重みがあるため、実システムの総VRAMが必ず1/16になるわけではない。

### デコードスループット（§5.4・Figure 3）

| 条件 | FP16 | CalibQuant 1bit | 比較 |
|---|---:|---:|---|
| InternVL2.5 8B、視覚トークン約3,328、GPU予算5GB | 11.628 token/s | 126.582 token/s | 約10.89倍 |

論文本文は対象条件群で約9.88〜11.24倍とまとめる。上表の比は各セルから算出したもので、約10.89倍・11.24倍である。本文中に視覚トークン数が3329と表記される箇所がある一方、Figure 3では3328とされるため、**約3,328トークン**と表記し原著の不整合を記録する。

この比較はメモリ上限内に入る**最大バッチサイズをそれぞれ選んだ**生成token/sである。FP16の単一リクエストと1bitの単一リクエストを同じバッチで比較した純粋な演算速度倍率ではない。GPU全体の処理量、バッチ許容量、デコードkernel効率の複合効果として解釈する。5〜30GBはH100自体の物理VRAM容量ではなく、実験で課した予算である。

### アブレーションと未確認事項

原著§5.5ではスコア較正とValue側チャネル量子化の寄与を切り分けるアブレーションを実施し、§4.2の図では較正ありの注意スコア誤差が較正なしより小さいことを示す。校正値はgrid searchで選ばれた固定パラメータであるため、未知のモデル・タスクへそのまま移植して最適とは限らない。DocVQAも評価対象であるが、この原稿では表2の個別スコアを照合できていないため、未確認の値を記載しない。

## 既存手法との位置づけ

KIVIは一般LLM向けにKeyのチャネル量子化とValueのトークン量子化を使う。CalibQuantは画像由来の大量KVに着目し、Key/Value双方のチャネル量子化、query側へのscale移動、softmax直前の較正、Tritonの低bit fused kernelを組み合わせる。VLCacheのような視覚キャッシュ圧縮とも比較するが、トークンの削除による情報損失と、低bit値の丸め誤差は異なるトレードオフである。

CalibQuantは既存MLLMのアーキテクチャ変更を必要としないと述べるが、低bit packed KVと専用Triton演算を扱うための推論実装側の統合は必要になる。重み量子化・MoEルーティング・投機的復号の速度改善とは別の経路であり、他の方式と併用したときの加算的な倍率は原著からは分からない。

## 限界と実用上の注意

1. **1bitは常に無損失ではない**：InternVL2.5のCOCO Caption CIDErはFP16より低く、動画理解では1bit CalibQuantがVLCacheより低い。高圧縮時の品質劣化を許容できるかは用途依存である。
2. **視覚トークン優勢が前提**：著者は画像・動画トークンがテキストより多い状況を主対象とする。テキストのみの短文チャットや画像トークンが少ない要求で同じメモリ利得は期待できない。
3. **実測倍率の意味**：最大11.24倍はH100、特定モデル、メモリ予算固定、最大バッチ選択時のデコードtoken/s。エンドツーエンド応答時間、TTFT、単一リクエストのTPOT、画像エンコーダの処理時間を含む数値ではない。
4. **量子化以外のオーバーヘッド**：量子化のmin/max統計、scale/bias、packing、較正値の探索、kernelの統合が必要。1bitの理論的圧縮率を全GPUメモリの削減率へそのまま換算しない。
5. **再現性・外挿**：原著はH100 80GBで測定する。RTX 4070 Super等の別世代GPUではSM数、メモリ帯域、Triton kernel最適化、最大バッチ数が異なる。公開コードの存在と、特定のローカルGPUで再現したという事実を混同しない。
6. **較正の汎化**：τ1,τ2の探索集合は小さいが、モデル・層・headに共通の値を選ぶ設定であり、分布ずれに対する頑健性の限界が残る。
