# KVDrive：長文脈推論のための三階層KVキャッシュ管理

## 概要

KVDriveは、自己回帰生成中に蓄積される鍵・値キャッシュ（KVキャッシュ）をGPUの高帯域メモリ（HBM）だけでなく、CPU主記憶（DRAM）と不揮発性記憶装置（SSD）へ分散配置する推論基盤である。従来の疎注意による転送量削減は、毎トークンの重要KV選択、CPUからGPUへの取得、注意計算を順に待つ構造に阻まれる。疎性を強くするだけでは回答精度が落ちるため、重要KVをどれだけ再利用するか、取得待ちをどの計算と重ねるか、SSDから何を読むかを共同設計する必要がある。

本研究は、注意重みによるGPU内の窓キャッシュ、選択・取得・計算の分離並列化、SSDの疎ブロック転送を一つの実装に統合した。L20、H20、RTX 4090の三種類のGPUと、Llama、Qwen、Phiの長文脈モデルで検証し、既存方式に対して最大1.74倍の生成処理率を報告する。これは条件依存の最大値であって、全構成の平均値ではない。SSDまで拡張した場合はDRAMのみの構成より約40%遅くなるという容量と速度の交換条件も重要である。

## 問題設定

通常のTransformerでは、事前計算（prefill）で作成した各層の鍵と値を保持し、生成（decoding）時に新しい問い合わせが過去の鍵へ注意を向ける。必要容量は系列長と同時要求数にほぼ比例する。原著では、Llama-3-8Bを約10万トークン、バッチ8で動かす場合、KVだけで約100GBが必要となる例を示す。重みと一時作業領域も同じGPUメモリを使うため、48GBのL20や24GBのRTX 4090には全量を置けない。

Quest、ShadowKV、RetroInferなどは、現在の問い合わせに重要そうなKV塊だけを検索してホストから取得する。しかし索引探索と転送を毎段階繰り返すため、原著図4では選択と取得が合計で復号時間の約半分に達する例がある。注意対象が隣接トークンで重複するのに毎回キャッシュを捨てれば、不要な転送が繰り返される。さらにホストDRAMの容量まで使い切ると、SSDからの無作為読出しが性能を支配する。KVDriveは疎注意の精度改善自体ではなく、この階層間移動と実行待ちの削減を中心課題とする。

## 手法

### 1. 注意得点を用いる窓キャッシュ

復号段階で重要と判定したKV塊を、一回の注意計算だけで捨てずGPU内に複数段階分保持する。新しい問い合わせに対して索引から重要塊を選び、窓に既に存在する塊は再取得せず、欠損分だけDRAMまたはSSDから転送する。追い出すときは最終参照時刻だけを見る方式ではなく、現在の注意得点が低く次の段階でも重要でなさそうな塊を優先する。未来の注意重みを正確に予言する機構ではなく、直近の注意分布の時間的局所性を利用する設計である。

原著図3では、疎性予算6.25%の条件で窓を一段階保持しない状態から三段階相当へ広げると、ホストからGPUへの転送量が一段階当たり500MB超から12.5MB未満へ減る。これは転送バイト数の削減であり、生成速度が40倍になったという意味ではない。窓を大きくするとGPUの占有量や命中判定費用も増えるため、容量を無制限に割り当てるのではなく費用対効果を測定する。

### 2. 層と注意ヘッドごとの窓幅配分

注意の時間的局所性は層・ヘッドごとに異なる。各組 `(l,h)` と窓幅 `w` に対して、事前測定から転送削減利益と追加GPUメモリ費用を求め、合計メモリ予算内で利益が大きくなる組合せを選ぶ。原著はこの選択を多肢選択ナップサック問題として定式化する。実用的な大規模構成では、追加メモリ当たりの転送削減利益が高い層・ヘッドから窓を拡張する貪欲な近似を使う。

この設計は、全ヘッドに同じ窓幅を割り当てると、再利用の少ないヘッドへ無駄なメモリを使う問題を避ける。ただし配分はオフラインの観測に依存するため、モデルや入力分布が変わると最適な窓も変わる。原著の感度分析は、バッチ1とバッチ4で有利な窓幅が異なることを示している。

### 3. 選択・取得・計算の分離

KVDriveは、重要KVの選択（Selection: S）、キャッシュ命中判定とホストからの取得（Fetching: F）、注意とフィードフォワード計算（Computation: C）を分ける。従来はS→F→Cを全バッチで逐次実行するため、取得が終わるまでGPUが待つ。提案方式ではバッチを小さなマイクロバッチへ分割し、あるマイクロバッチのGPU側選択と、別のマイクロバッチのCPU側命中判定、さらに別のマイクロバッチの転送を重ねる。

注意すべき点は、論文第6.1節では**計算Cは全マイクロバッチの必要KV取得後に全バッチで実行する**と記述していることである。三段階がすべて独立したマイクロバッチ単位で進むと解釈するのは不正確である。計算中にはキャッシュ管理情報の更新を重ね、軽量キューと非同期転送で次段階へ接続する。選択の索引中心数、GPU窓の容量、マイクロバッチ幅を短い事前較正で共同調整し、索引探索時間・CPU判定時間・転送時間の均衡を取る。

### 4. 二段階索引と検索費用

索引では隣接するトークンの鍵を塊にまとめ、塊の平均鍵を代表値とし、さらに類似する代表値を上位の中心点へまとめる。問い合わせは上位の中心点で候補を絞ってから必要な塊を取得する。中心点を増やすと候補選択が細かくなる一方、索引容量と選択時間が増える。原著は単純な空間塊化と比較して、検索精度を大きく損なわず索引容量約半分・検索最大2倍の条件を報告する。これは索引部分の比較であり、システム全体の生成処理率が2倍という主張ではない。

### 5. SSDを含む三階層の協調

事前計算の最後に、末尾の観測窓の注意重みから接頭KVの重要度を推定する。全KVはSSDへ裏付けとして保存し、重要度の高い塊をHBM、次点をDRAMへ先に配置する。復号時にGPU窓で命中しない場合だけ下位階層から取得する。SSD上では同時参照されやすいKVを連続領域へまとめ、層・ヘッドごとに領域を分けて、小さな無作為読出しを連続読出しへ寄せる。層全体を毎回読み直すFlexGen型の転送と違い、必要な疎ブロックだけを対象とする。

SSDからのデータはDRAMのメモリ写像領域へ読み込み、再利用するページ固定バッファを経てGPUへ非同期転送する。頻繁に欠損する層・ヘッドへページ固定領域を優先配分する。これによりSSD容量を利用しつつ転送待ちを一部隠すが、SSD自体の帯域がDRAMと同等になるわけではない。初期重要度推定が外れれば追加のSSD読出しが発生する。

### 6. 要求処理の全体像

要求到着後、事前計算でKVを生成し索引を作り、SSDへ全量を退避して重要度に応じた高速階層の初期配置を行う。生成の各段階では、問い合わせから重要塊を選択し、GPU窓の命中を調べ、欠損分だけDRAMまたはSSDから取得する。マイクロバッチ間で選択・判定・転送を重ね、必要なKVが揃ってから全バッチで計算する。計算後は新しい注意得点で追い出し優先度を更新する。窓の再利用による転送量削減と、分離実行による待ち時間隠蔽が相補的に働く。

## 評価

### 実機環境と比較条件

| 項目 | 論文に示された条件 |
|---|---|
| GPU | L20 48GB、H20 96GB、RTX 4090 24GB |
| CPU・DRAM | L20はXeon Platinum 8457C・DDR5 100GB、H20はEPYC 9K84・200GB、RTX 4090はXeon Gold 6430・120GB |
| 保存装置 | NVMe U.2 SSD |
| モデル | Llama-3-8B-1048K、Qwen3-8B、Qwen3-14B、Phi-4-mini-instruct |
| 評価課題 | RULER、LongBench |
| 比較方式 | 全注意、FlexGen、Quest、ShadowKV、PQCache、MagicPIG、RetroInferなど |
| 実装 | PyTorch 2.3.0、Python 3.12、Ubuntu 22.04、CUDA 12.1 |
| 指標 | 出力トークン毎秒、正解率、KV転送量、命中率、処理段階別時間 |

実機比較ではGPUとホストの容量が異なるため、装置をまたぐ絶対処理率をアルゴリズム単体の性能差と読み替えない。疎注意を用いる比較方式では、先頭4トークンと直近64トークンをGPUに保持するなど、共通条件が設定されている。論文の比較実装は一部補助最適化を無効にしているため、別実装・別版での優劣を保証するものではない。

### 全体の生成処理率

| 条件 | 比較対象 | 結果 | 解釈 |
|---|---|---|---|
| L20、60k～360k文脈と複数バッチ | ShadowKV | 最大約70%向上 | GPU窓再利用と取得待ち隠蔽の共同効果 |
| H20およびRTX 4090 | 各条件で最良の既存方式 | 1.23～1.53倍 | 装置を変えても改善傾向を確認 |
| 論文全体の最良条件 | 既存方式群 | 最大1.74倍 | 特定条件の上限であり平均値ではない |
| DRAM＋SSDとDRAMのみ | 同一KVDrive構成 | SSD併用は約40%低速 | 容量拡張と速度の交換条件 |
| 疎性予算6.25%、窓0→3倍 | 同一方式の転送量 | 500MB超→12.5MB未満/段階 | 再利用による転送量削減、速度倍率ではない |

L20では文脈60k、90k、120k、240k、360kとバッチ8、4、4、2、2などの条件を含む。ShadowKV比の約70%改善は最大条件であり、短文脈・低バッチで同程度の改善が得られるとは限らない。FlexGen型の全KV転送は一部長文脈条件で1トークン毎秒未満まで低下し、MagicPIGは大規模索引がホストメモリを超えて起動できない場合がある。起動不能の比較方式と実際に同条件で動く方式の速度差は分けて読む必要がある。

### 構成要素除去と感度分析

原著の表3では、文脈120k・窓幅2・疎性予算2048・候補2560の条件で、注意得点による追い出しがLlama3-8Bの命中率を80.0%から81.5%、Qwen3-8Bを77.5%から79.0%、Phi-4-miniを78.0%から81.0%へ改善する。他方、Questに移植したPhi-4-miniでは90.7%から88.9%、ShadowKVでは86.1%から84.6%へ悪化する。追い出し方式がすべての索引・モデルに優れるわけではないことを示す負の結果である。

窓幅はバッチ1では小さい方が選択・判定費用を抑えやすく、バッチ4では大きい方が転送削減利益を得やすい。KV塊幅1、4、8の比較では、幅1は細粒度I/O、幅8は余分な転送が増え、幅4付近が有利な条件がある。索引中心点数は文脈60kで4096、120kで8192が有利という感度を報告し、中心点を8192から2048へ減らしても一部課題の精度を大きく損なわず索引容量を4分の1にできる。いずれも個別のモデル・課題・負荷に依存する観測である。

### 回答品質とSSDの代償

RULERとLongBenchの課題別正解率を全注意と比較する。例えばQwen3-8BではRULER平均が全注意73.94点に対してKVDrive68.07点、LongBench平均が全注意31.89点に対してKVDrive32.39点となる。後者ではわずかに上回る一方、前者では約5.87点低い。したがって「全注意と完全に同じ精度を保証する」という主張は不適切である。注意選択の誤りが頻出語抽出などの課題へ影響する可能性があり、課題ごとの結果を確認する必要がある。

SSD併用はDRAMのみの構成より約40%低速だが、DRAM容量だけでは扱えない長文脈・大バッチを実行できる。これはSSDが高速になったことを意味せず、重要度に基づく初期配置、連続読出し、疎転送、事前取得を組み合わせて容量拡張の代償を抑えた結果である。事前計算の遅延は原著図22で全注意基準とほぼ同程度の条件があるが、索引構築と退避があらゆる負荷で無料になるわけではない。

## 既存研究との差

Questは塊の最小・最大鍵、ShadowKVは塊平均などで重要KVを推定し、RetroInferやPQCacheは近似探索と一般的なキャッシュ方針を組み合わせる。これらは主に「どのKVを選ぶか」を改善する。KVDriveは選択したKVを複数段階再利用する窓、層・ヘッド別の窓配分、選択・判定・転送の非同期重畳、SSDの疎ブロック配置を追加する。InfiniGenの前層情報による予測先読みとは異なり、選択そのものと取得の処理を分離して待ちを減らす。FlexGenの層単位SSD読出しとは異なり、注意で必要な塊だけを転送する。

## 限界

注意得点の時間的局所性が弱い入力ではGPU窓の命中率が下がり、DRAMやSSDからの追加取得が増える。層・ヘッド別窓配分はオフラインの観測に依存するため、モデル・バッチ・文脈長・注意分布が変われば再較正が必要になる。索引の中心点数とマイクロバッチ幅にも、検索費用と転送隠蔽の交換条件がある。注意得点による追い出しをQuestやShadowKVへ移植すると、特定モデルでは命中率が悪化することが原著表3で示されている。

疎注意による品質低下が課題ごとに残る。SSDはDRAMより遅く、SSD併用で約40%の生成処理率低下を報告する。ページ固定バッファや連続領域配置、初期重要度推定は追加のホストメモリ・準備時間を要する。原著の実機評価は単一ノードのL20、H20、RTX 4090と四モデル系列を中心とし、多GPU分散、異種GPU間通信、SSD寿命や障害復旧などの運用条件は十分に実証していない。実装コードの行数は論文に記載されるが、公式公開リポジトリの所在は一次資料から確認できない。
