# OracleKV：将来の質問を知らないKVキャッシュ削減を質問分布の誘導文で改善する

## 概要

OracleKVは、長文を事前に読み込んでKVキャッシュを保存した後、将来の質問を受け取る推論システムで、どのKVを残すべきかという問題を扱う。多くのKV圧縮方式は、現在の質問やプロンプト末尾の観測窓から重要トークンを選ぶ。しかし、RAGの資料チャンクを先にキャッシュする場合や、長い会話文脈を複数の後続質問に使う場合、prefill時には将来の質問が不明である。質問に依存した重要度推定をそのまま使うと、後から必要になる情報を捨てる可能性が高い。

本論文は、将来の質問を直接知る代わりに、大規模なLLM利用者の対話から得られた質問カテゴリや関心対象の表層統計を文章化し、oracle guidanceとして長文の末尾へ追加する。モデルがこの誘導文へ向ける注意を利用して文脈トークンの重要度を推定し、KV予算内で上位を保持する。誘導文自身のKVは最終的に除外するため、利用者の質問をキャッシュに含める必要はない。

実験ではLlama-3.1-8B-Instruct、Qwen2.5-7B-Instruct、Mistral-7B-Instruct-v0.2で、LongBench、RULER、Needle-In-A-Haystack、SCBenchを評価した。Llama-3.1-8BのLongBench平均はKV予算10%でSnapKV 30.1に対しOracleKV 36.5、適応予算配分版は38.8である。一方、すべてのタスクで改善するわけではなく、コード生成のような専門的な質問や、誘導文が長い場合の追加prefill・メモリ費用が限界として残る。

## 問題設定

KVキャッシュは入力長に比例して増えるため、長文を多く保持する推論サーバではメモリを圧迫する。KV削減は不要とみなしたキー・値を捨てることでメモリを節約するが、どの位置が重要かは実際の質問に依存する。単発の長文質問応答では質問が既に与えられているため、質問と文脈の注意関係から選択できる。これに対して、事前キャッシュした資料へ後から複数の質問を投げる場合、重要な位置がまだ分からない。

著者らは、文脈だけを使って重要度を推定した場合と、質問を与えてから推定した場合の注意分布を比較する。質問ありで必要なKV位置と、質問なしで保持した位置が一致しないことが、質問非依存の圧縮が失敗する主な原因と考える。図3では、将来の質問に必要な回答位置が、純粋な文脈だけを見た重要度では削除され得ることを可視化している。

対象場面は、RAGで検索前に資料チャンクをprefillして保持する場合と、会話・長文ドキュメントの共通KVを再利用する場合である。OracleKVは質問そのものを予測する学習済みモデルではなく、質問の種類や利用者の情報要求に関する統計的な事前知識を与える。一般的な質問分布から作った誘導文が、未知の質問に対する情報保持の偏りを改善できるかが中心的な問いとなる。

## 手法

### 1. 質問分布を手設計の誘導文へ変換する

著者らは大規模LLM対話に関する既存の利用実態分析から、質問の種類と要求されやすい情報カテゴリの表層統計を抽出し、oracle guidanceと呼ぶ文章を手設計する。これは学習済みの小型予測器ではなく、一般的な質問の傾向をモデルへ提示するテキストである。具体的な将来の質問を知らなくても、文脈中のどの情報が利用されやすいかを間接的に表現する。

誘導文は長さLoを持ち、入力文脈Xctxの末尾に連結される。元の文脈を変換するのではなく、モデルが文脈に注意を向けるための追加の入力として機能する。実際の将来質問Xquesの代替としてこの誘導文を用いる点が、質問依存の観測窓方式との大きな違いである。誘導文の内容は一般的な質問分布に依存するため、専門領域や異なる利用者群へ移すときは調整が必要になる。

### 2. 誘導文から文脈KVへの注意を集計する

モデルは連結した文脈と誘導文をprefillし、各層・ヘッドで注意を計算する。重要度を求める際は、誘導文の位置から元の文脈位置へ向かう注意スコアを使い、誘導文トークンに対応する行を集計する。具体的には、誘導文の行範囲から文脈の列範囲への注意重みを加算し、文脈トークンごとにスコアを得る。KV保持予算をBとしたとき、このスコアの大きいB個の文脈KVを選択する。

ここで誘導文自身のKVは、質問応答に必要な元文脈の情報ではないため、最終的な保存対象から除外する。つまり誘導文は選択器を動かすための一時的な計算入力であり、長期に保持するキャッシュではない。誘導文を追加するためのprefillと注意計算は発生するので、精度改善は無料ではない。

### 3. 既存のKV予算配分方式と組み合わせる

OracleKVはKVの重要度を計算するデータレベルの介入であり、保持予算を層ごと・ヘッドごとにどう配分するかとは独立性がある。著者らはSnapKVのような一様な予算配分、PyramidKVのような層別配分、AdaSnapKV系のヘッド別配分との組合せを評価する。特にAda OracleKVは誘導スコアと適応予算配分を組み合わせた構成である。

この分離により、重要度推定を質問依存の観測窓から誘導文ベースへ変更しても、既存の予算配分ロジックをそのまま利用できる可能性がある。ただし既存の圧縮器と常に完全互換という意味ではなく、注意スコアの取り出し、KV選択、メモリ管理の実装を適合させる必要がある。原著は主に精度とprefill費用を評価しており、あらゆるランタイムでの実装容易性を保証していない。

### 4. 将来質問との一致を情報保持の観点から評価する

OracleKVの目的は、誘導文を与えた時点で将来の質問へ回答することではない。将来の質問が来たとき、必要な証拠位置が残っている確率を高めることである。質問が分からない時点で一般的な利用分布に合わせたKV集合を選ぶため、特定の質問への最適選択には届かない可能性がある。原著図2の「質問あり」条件は、このような質問非依存方式に対する上限的な参照として読むべきである。

## 評価条件

| 項目 | 原著の条件 |
|---|---|
| モデル | Llama-3.1-8B-Instruct、Qwen2.5-7B-Instruct、Mistral-7B-Instruct-v0.2 |
| ベンチマーク | LongBench、RULER、NIAH、SCBench |
| 比較方式 | H2O、StreamingLLM、SnapKV、PyramidKV、AdaSnapKV/AdaKV、DuoAttentionなど |
| KV予算 | 40%、10%を中心に、RULERでは100〜10%の感度を評価 |
| 方式 | 文脈末尾にoracle guidanceを追加し、誘導注意スコアで上位KVを保持 |
| 追加コスト | guidance長256から1024でのprefill時間・メモリ変化を測定 |
| 主指標 | 各タスクの回答品質、prefill時間、ピークメモリ、圧縮予算 |

LongBenchは単発の長文QAや要約を含み、SCBenchは共有文脈を使う複数ターン・複数要求を扱う。RULERやNIAHは厳密検索の難しさを調べる。これらは同じ評価ではないため、単発で良い方式が共有文脈でも良いとは限らない。実験の主な数値は、圧縮率を固定した際の回答品質である。

## 定量結果

### 1. LongBenchとSCBenchの平均

原著表1のLlama-3.1-8B-Instructについて、KV予算40%と10%での平均を比較する。LongBenchの平均とSCBenchの平均は別々に示す。下表の数字は原著のタスク平均であり、推論速度やメモリ削減率ではない。

| 手法 | KV予算 | LongBench平均 | SCBench平均 |
|---|---:|---:|---:|
| Full Cache | 100% | 45.7 | 25.8 |
| SnapKV | 40% | 42.9 | 23.7 |
| AdaSnapKV | 40% | 44.1 | 22.9 |
| OracleKV | 40% | 45.0 | 24.8 |
| Ada OracleKV | 40% | 44.9 | 24.9 |
| SnapKV | 10% | 30.1 | 21.7 |
| AdaSnapKV | 10% | 32.1 | 21.7 |
| OracleKV | 10% | 36.5 | 22.5 |
| Ada OracleKV | 10% | 38.8 | 23.3 |

Llama-3.1-8Bの10%予算では、OracleKVのLongBench平均36.5はSnapKVの30.1より6.4ポイント高い。Ada OracleKVは38.8で、AdaSnapKVの32.1より6.7ポイント高い。原著本文で述べる「6.7%」という改善表現は、表の数値からは百分率の相対改善ではなく約6.7ポイント差として読むのが適切である。SCBenchでは10%予算の差はOracleKV22.5対SnapKV21.7と小さく、単発のLongBenchほど劇的な改善ではない。

40%予算ではOracleKV45.0がFull Cache45.7に近づく一方、SCBenchでは24.8対Full Cache25.8となる。つまり高い圧縮率でも情報保持を改善するが、完全キャッシュと同等の品質を常に保証するわけではない。

### 2. モデルを変えたときの負の結果

原著表2ではMistral-7B-Instruct-v0.2の40%予算で、LongBench平均はSnapKV32.0に対してOracleKV32.7とわずかな改善である。SCBench平均はSnapKV18.7に対しOracleKV20.0で、改善幅は小さい。10%予算ではSnapKVのLongBench24.6に対しOracleKV26.1、SCBenchはSnapKV17.4に対しOracleKV18.6となる。

モデルによって効果が異なり、同じ誘導文を使えば必ず大幅に改善するとは言えない。また、個別タスクでは負の結果が存在する。Llama-3.1-8BのSCBenchで40%予算の多段推論や要約では、OracleKVが他の予算配分方式に負ける条件がある。これは一般的な質問分布から作った誘導文が、特定のタスクに必要な情報を十分に優先できないことを示す。

### 3. RULERとNIAHの検索耐性

RULERでは、NIAH-Single、NIAH-MultiKey、NIAH-MultiQuery、NIAH-MultiValue、Variable Tracingなど、異なる種類の検索を評価する。原著図5はLlama-3.1-8BとQwen2.5-7BについてKV予算を100%から10%へ減らした場合の品質を示す。OracleKVは複数のタスクで高い精度を維持するが、すべての検索で勝つわけではない。

付録表A8のLlama-3.1-8Bでは、KV予算10%のNIAH-Single S-1/S-2がOracleKVで100.0/100.0と高い一方、S-3は0.0に落ちる。同じ予算でNIAH-MultiKey MK-1は77.8、MK-2は3.0、MK-3は0.0となる。従って「10%でも検索精度をほぼ完全保持」という一般化は誤りであり、質問形式やneedle配置によって破綻する。特定の簡単な検索に強くても、複数キー・複雑な検索では情報が欠落する場合がある。

NIAHでは、SnapKV・PyramidKV・AdaSnapKVへoracle guidanceを組み合わせた場合の改善も評価される。これは誘導文を独立した選択信号として利用できることを示すが、グラフの各値はモデル・系列長・予算・needle位置の条件に依存する。単一のheadline改善値で全条件を代表させるべきではない。

### 4. prefill時間とメモリのトレードオフ

原著§3.2ではLlama-3.1-8Bの96K文脈、Qwen2.5-7Bの240K文脈でprefill時間とメモリを評価する。OracleKVはSnapKVやPyramidKVに近いピークメモリとTTFTを報告するが、誘導文を追加する分の計算費用はある。誘導文長を256から1024へ増やすと、メモリ使用量は1.63倍、prefill時間は1.18倍になると報告する。

この差は、長い誘導文が精度の改善を必ず保証するわけではないことと合わせて読む必要がある。圧縮によるKV容量削減を目的としても、選択時の一時メモリと追加prefillが大きくなるなら、端末やサーバのメモリ制約に悪影響を与える可能性がある。特に多数の文脈を事前キャッシュする用途では、各文脈に対する誘導文の追加費用が累積する。

### 5. ablationと感度評価

本文§3.3はmulti-key retrievalとsummarizationで設計選択の影響を調べたと記載し、詳細を付録に置く。重要な設計変数は誘導文の内容、長さ、KV予算、層・ヘッドへの予算配分である。誘導文を使わない純粋な文脈の注意分布では将来質問に必要な位置が十分に強調されないため、誘導文を追加して重要度を計算することが方式の中心的な寄与となる。

一方、誘導文の質問分布が実際のタスクと一致しない場合は、選択したKVが偏る。付録のコード生成等に関する議論は、一般利用の質問カテゴリを基にした誘導文が専門タスクの固有パターンを十分に表現できない可能性を示している。したがって誘導文の設計を変更した場合、品質改善と追加計算費用の両方を再評価する必要がある。

## 既存研究との差

SnapKVやPyramidKVなどは、モデル内部の注意分布や観測窓を用いて重要なKVを選ぶ。OracleKVは重要度計算の入力側を変え、将来質問の代わりに外部の質問分布を表すテキストを与える。これは新しいKVストレージ形式や低ビット量子化ではなく、どのKVを保持するかを決める信号の設計である。予算配分方式と分離できるため、既存の一様・層別・ヘッド別予算配分と組み合わせられる。

SharedContextBenchなどの研究が「質問が未知の共有文脈でKV圧縮は失敗しやすい」という評価上の問題を可視化するのに対し、OracleKVはその失敗を緩和する具体的な入力介入方式を提案する。両者は問題設定を共有するが、ベンチマークの構築と圧縮方式の改善という異なる寄与を持つ。

推論システムへの適用先は、RAGの資料キャッシュ、共有system prompt、複数ターンの文脈再利用などである。ただし実際のprefix cacheの索引、複数GPU間の転送、キャッシュ追い出しポリシー、同時要求のスケジューリングはOracleKVの中心的な評価対象ではない。

## 限界と再現上の注意

第一に、oracle guidanceは大規模な対話統計を参照して手設計される。利用者の質問分布が異なる専門領域や少数言語、コード生成、科学技術文書では、一般的な誘導文が適切な重要度を与えない可能性がある。論文のImpact Statementと付録は、タスク固有の利得と誘導文設計の一般化可能性を限界として挙げる。

第二に、誘導文は追加のprefill計算と一時的なKVを必要とする。長さを256から1024へ伸ばすとメモリ1.63倍、prefill時間1.18倍となるため、実際のTTFTとメモリ制約を測らずに圧縮率だけで採用してはならない。圧縮後の保持予算と、選択過程で必要なピークメモリは別指標である。

第三に、LongBench・SCBench・RULERの平均値を単純に比較することはできない。各タスクの評価尺度、系列長、質問数、モデル、予算配分が異なる。特にRULERではNIAHの一部タスクで非常に高い精度を維持しても、別の複数キー条件で0%に落ちる。個別タスクの負の結果を平均値で隠してはならない。

第四に、本文の「将来質問が不明」という設定は、事前キャッシュ時に質問を利用できない場面を想定する。質問を既に受け取っている場合は、質問依存の重要度推定の方が適切なこともある。OracleKVは正確な将来質問を推定するモデルではなく、一般的な質問分布から情報保持の偏りを与える方式である。

第五に、追加の誘導文が既存のキャッシュ管理・モデル実装へ与える影響はランタイム依存である。attention scoreの取得、圧縮のタイミング、層・ヘッド別予算、prefill時のピークメモリを揃えて評価する必要がある。論文が報告する精度改善から、サーバ全体のスループットやTPOT改善を推定してはいけない。

第六に、原著PDFは長い付録を含むため、主要な性能結論は本文の表1・図5〜7と付録の具体的なタスク別表を照合して解釈する必要がある。ここでは全付録の全条件を一つの平均へ統合せず、Llama-3.1-8Bの代表条件とMistralの反例、NIAHの失敗条件を分けて記録した。
