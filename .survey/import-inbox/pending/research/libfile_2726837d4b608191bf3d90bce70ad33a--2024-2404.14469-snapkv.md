# SnapKV: LLM Knows What You are Looking for Before Generation

> プロンプト末尾の観測窓から各注意ヘッドが生成中に参照する入力位置を事前推定し、近傍をまとめた重要KVだけを残して長文脈デコードを高速・省メモリ化する。

## 概要

長い入力を処理したLLMは、デコードの各ステップで過去の全キー・バリュー（KV）を参照する。KV容量は入力長に比例し、注意計算とメモリ読み出しも増える。SnapKVは、各注意ヘッドが生成中に繰り返し注目するプロンプト位置は比較的安定しており、その位置を生成前のプロンプト末尾にある短い観測窓から推定できるという経験的性質を使う。

観測窓のクエリから、それより前のプロンプトKVへの注意を集約して位置ごとの重要度を作る。重要位置の周辺も残るよう1次元プーリングでクラスタ化し、各ヘッドで上位位置を選ぶ。選択したKVと観測窓の完全KVだけを生成フェーズへ持ち越すため、モデル重みや学習を変更せずにKVを圧縮できる。

16K入力では完全KVの比較対象に対して生成を3.6倍高速化し、メモリ効率を8.2倍改善する。16種類の長系列データセットで比較可能な品質を維持し、Hugging Face実装を小変更した単一A100 80GB環境で最大380Kトークンを処理できると報告する。

## 問題設定

KV追い出し方式では、生成中に過去の注意統計を蓄積して重要位置を決めるものが多い。その場合、生成が始まるまでは十分な統計がなく、長いプロンプトのKVを初期状態で保持する必要がある。また全ヘッドで同じ重要位置を使うと、ヘッドごとの役割差を失う。

SnapKVは生成前の観測窓だけで重要度を測ることで、最初のデコードステップから圧縮済みKVを使う。さらにヘッドごとに保持位置を変え、注意パターンの差を残す。

## 手法

### 観測窓による投票

プロンプトを、圧縮対象となる前方部分と、末尾の短い観測窓へ分ける。観測窓の各クエリが前方キーへ向ける注意重みを位置ごとに集約し、その位置が今後の生成でも重要である可能性を表す投票値とする。

この処理は生成トークンをまだ一つも出していない時点で行える。したがって圧縮のために長い生成履歴を待つ必要がなく、最初のデコードから小型KVを利用できる。

### 重要位置のクラスタ化

単一点だけを上位選択すると、重要トークンの直前直後にある関連情報を落としやすい。SnapKVは1次元プーリングを注意重要度へ適用し、強い位置の周辺にもスコアを広げる。各注意ヘッドでこのクラスタ化スコアの上位k位置を選ぶ。

保持KVは「各ヘッドで選んだ前方位置」と「観測窓の全位置」から構成する。観測窓自体は最新の命令や質問を含む可能性が高いため圧縮しない。

### 生成フェーズ

以後のデコードでは圧縮済みKVだけを注意対象にする。モデルの射影重みや注意式は変更せず、KVのトークン軸だけを短くするため微調整は不要である。一方、最初の観測窓で重要と判定されなかった位置は後から参照できないので、注意パターンが生成途中で大きく変わるタスクが主なリスクになる。

## 評価条件・主要結果

| 項目 | 条件・結果 |
|---|---|
| モデル | LWM-Text-Chat-1M、LongChat-7B、Mistral-7B、Mixtral-8x7B、Command-R等 |
| GPU | 単一NVIDIA A100 80GBを含む |
| 品質評価 | 16長系列データセット、Needle-in-a-Haystack等 |
| 16K入力 | 生成3.6倍高速化 |
| メモリ | 16K条件で8.2倍のメモリ効率 |
| 最大文脈 | 単一A100 80GBで最大380Kトークン |
| 品質 | 16長系列データセットで完全KVと比較可能な性能 |

LongBench系の評価では大幅なKV削減でも品質を維持する条件が示される。380K処理可能という結果は「380倍高速化」ではなく、圧縮によってメモリ不足を回避し処理可能長を伸ばした容量面の結果である。

## 既存研究との差

H2Oなどは生成中の累積注意から重い打者（heavy hitter）を追跡するのに対し、SnapKVは生成開始前の観測窓だけで保持位置を決める。StreamingLLMのような固定的な注意シンク・近傍保持とも異なり、入力内容と注意ヘッドごとに保持位置が変わる。

## 限界

選択は生成前に一度行うため、長文生成の途中で参照対象が大きく変わる場合には保持集合が陳腐化する可能性がある。圧縮率を高めるほど重要位置の取りこぼしリスクが増える。完全KVと同一出力を保証する無損失方式ではなく、品質維持は観測窓から将来の注意を予測できるという性質に依存する。
