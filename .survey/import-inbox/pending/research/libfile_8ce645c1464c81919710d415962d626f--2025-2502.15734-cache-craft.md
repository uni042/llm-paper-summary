# Cache-Craft: Managing Chunk-Caches for Efficient Retrieval-Augmented Generation

## 概要
検索拡張生成（Retrieval-Augmented Generation; RAG）では、検索された複数文書chunkを質問とともにLLMへ渡す。同じchunkは別の質問でも繰り返し取得されるが、前に置かれた文書やchunk順序が変わると、そのtokenのKVは異なる文脈を反映する。通常のprefix cachingは先頭から同一なprefixしか再利用できず、chunkだけ同じでも再計算が必要になる。一方、過去のKVを無条件に使うとattention文脈が欠落して生成品質が落ちる。

Cache-Craftは文書chunkごとに事前計算KVを保持し、再利用時に「このchunkのどのtokenが新しい周辺文脈の影響を強く受けるか」を推定して、その一部だけを再計算する。再計算量を品質維持に必要な範囲へ絞り、cacheの保存・読出し・evictionもRAGの再利用価値に合わせる。LLaMA-3-8B/70Bを用いた本番workloadでは、prefix caching比で冗長計算を51%削減し、連続バッチ下のthroughputを1.6倍、end-to-end応答時間を約2分の1へする。

## 問題設定
RAGのprefillでは、検索文書が長いほどdecodeより大量のtokenを一度に処理する。production traceでは同じknowledge chunkが繰り返し現れるため、KVを再利用できれば大きな計算を省ける。しかしKVはtoken文字列だけの関数ではなく、それ以前のtokenへattentionした結果も含む。同一chunkでも前に置かれたchunkが違えば正しいKVは変わる。

完全再計算は正確だがreuse benefitを失い、完全reuseは速いが品質を損なう。Cache-Craftはこの二択を避け、文脈変化の影響が大きいtokenだけを再計算する。さらに再利用候補がGPU memoryを超えるため、どのchunk-cacheを保持するかも同時に解く必要がある。

## 手法

### chunk-cacheと再利用可能性判定
検索結果を文書chunk単位に分け、そのchunkのKVをcache objectとして管理する。新requestの検索結果とcache catalogを照合し、同一chunkの既存KVがあれば候補にする。prefix全体の一致を要求しないため、同じchunkがprompt中の別位置・別組合せで現れても再利用候補になる。

ただし位置や先行文脈が変わるほどKVの誤差は増える。Cache-Craftはchunk間attentionとtokenの文脈依存性を利用して、直接reuseできる部分と修復が必要な部分を区別する。

### 選択的再計算
再利用chunk内の全tokenを再計算するのではなく、新しい文脈から強く影響されるtokenを選び、そのKVだけを更新する。再計算されたtokenは新しい先行chunkをattentionできるため、古いcacheを新requestの文脈へ部分的に適応させる。再計算率を増やすほどfull recomputationへ近づいて品質は上がるが、計算節約は減る。

この機構は「古いKVを圧縮する」のではなく、保存済みKVを初期値として必要箇所だけ計算し直す。したがって品質・計算量の交換条件をtoken単位で調整できる。

### cache管理とoverlap
chunk-cacheには容量と再利用価値が異なるため、cache storeは将来のhit価値と再計算節約量を考えて保持・evictionする。必要なcacheをhost/storageからGPUへ読む場合も、他のprefillや連続バッチ処理と重ね、cache loading overheadがcritical pathへ露出しにくいようにする。

vLLMを基盤にすることで、通常のrequest batchingとKV memory managementの上へchunk reuseを追加し、単発microbenchmarkではなく同時requestのproduction workloadで評価している。

## 評価条件
|項目|条件|
|---|---|
|モデル|LLaMA-3-8B、LLaMA-3-70B|
|runtime|vLLMベース|
|workload|2WikiMQA、MuSiQue、SQuAD、DROP、本番RAG trace|
|比較|full recomputation、prefix caching、無修正cache reuse等|
|主要指標|冗長prefill計算、TTFT、end-to-end latency、throughput、生成品質|
|serving|連続バッチを含む|

## 主要結果
|条件|結果|意味|
|---|---:|---|
|prefix caching比|冗長計算51%削減|chunk単位reuseがprefix一致より多くの再利用を拾う|
|full recomputation比|冗長計算75%削減|選択的再計算で大部分のprefillを省ける|
|本番workload・continuous batching|throughput 1.6倍|cache reuseが同時request処理量へ反映される|
|同条件|end-to-end latency 約2倍短縮|単なるkernel時間でなく応答時間も改善|
|LLaMA-3-8B/70B|品質を維持しながら改善|部分再計算が無修正reuseの品質劣化を抑える|

長いprefillや大きいモデルほど、1つのchunkを再計算しない価値が大きくなる。一方、chunk再利用が少ないworkloadではcache hitが減り、選択・load管理の相対費用が増える。

## 既存研究との差
prefix cachingは先頭から同一なtoken列を再利用するため安全だが、RAGの文書順序変更に弱い。RAGCache等もknowledge cacheを扱うが、Cache-Craftは異なる文脈で作られたchunk KVをそのまま正しいと仮定せず、文脈依存tokenの部分再計算を明示的に入れる。KV圧縮手法とも異なり、容量を減らすよりprefill再計算そのものを避けることが中心である。

## 限界
再利用率が低いknowledge baseや、各chunkが先行文脈へ強く依存するrequestでは再計算率が上がり、利得が縮む。品質維持は選択器が影響tokenを適切に拾うことへ依存する。またcache store自体の容量・転送帯域が小さい場合、load/evictionが新たな律速になり得る。評価はRAG中心で、一般会話の任意middle-prefix reuseへそのまま一般化したものではない。
