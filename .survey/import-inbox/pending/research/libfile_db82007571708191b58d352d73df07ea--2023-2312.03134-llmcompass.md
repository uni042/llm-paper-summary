# LLMCompass: Enabling Efficient Hardware Design for Large Language Model Inference

## 概要
LLMCompassは、大規模言語モデル（LLM）の推論を実行する新しいアクセラレータ構成を、RTL実装やcycle-level simulatorを作る前に比較するためのハードウェア評価基盤である。LLMは巨大なGEMMだけでなく、prefillとdecodeで演算強度が大きく異なり、HBM容量・帯域、SRAM、演算器数、複数device間接続の組合せが性能とコストを左右する。従来のrooflineは速いが楽観的すぎ、cycle-level simulationは大規模LLMには遅すぎる。

LLMCompassはLLMの演算グラフがGEMM、softmax、layer normalizationなど規則的なdense operatorから成ることを利用し、cycleではなくtile単位で性能を模擬する。ハードウェア記述、operator shape、memory hierarchyを入力するとmapperがtile size・loop order・parallel mappingを探索し、latencyが最小となるscheduleを選ぶ。A100、MI210、TPUv3で検証した結果、operator latencyの平均誤差10.4%、LLM推論全体では4.1%で、4×A100上のGPT-3 175Bを26,400回のmapping探索込み15〜16分で評価できる。

## 問題設定
LLM用ハードウェアを比較する際、単純なピークFLOPSやHBM帯域だけでは実際のprefill/decode性能を予測できない。prefillは大きな行列積となり計算器とbufferを使いやすいが、1 tokenずつ進むdecodeはweight読み出しが支配し、演算器を増やしても利用率が上がりにくい。またHBMは高帯域だが容量とコストに制約があり、batchを増やしてcompute utilizationを上げようとするとKV cacheが増える。

cycle-accurate simulatorは詳細だが100K instructions/s未満のこともあり、175B級モデルと多数のmapping候補を探索するには現実的でない。逆にrooflineはmappingやmemory hierarchyの具体的なデータ移動を省略する。LLMCompassは両者の中間で、LLMに必要な粒度だけを残して設計空間探索を高速化する。

## 手法

### 一般化ハードウェア記述
計算core、vector lane、systolic array、register file、local/global buffer、off-chip memory、device間interconnectをパラメータ化し、GPUとTPU型設計を同じ抽象表現へ落とす。入力したoperatorを各memory levelへどうtile化するかをmapperが決めるため、特定ISAの命令列を用意する必要がない。

この抽象化は自由度を上げる一方、proprietaryな制御・cache挙動を完全再現しない。その誤差を実機検証で定量化し、設計探索用モデルとして許容できるかを判断する。

### 性能mapper
LLM operatorの規則的なmemory accessを利用し、tile shape、loop order、coreへの割当、tensor parallel構成を候補化する。各候補についてcompute時間とmemory transferを見積もり、性能最適なmappingを選択する。GPT-3 175Bの4×A100例では26,400候補を探索しても単一Xeon Gold 6242R coreで15〜16分に収まる。

prefillとdecodeは別のshapeとして評価される。論文の設計探索ではprefillをbatch 8・input 2048のGPT-3一層、decodeを1024番目token生成時として測り、両段階で最適なハードウェア特性が違うことを明示する。

### 面積・コストモデル
性能だけでなく、公開されたtransistor count、CACTIによるSRAM面積、annotated die photo、wafer cost、DRAM/HBM価格を組み合わせてdie areaとcostを推定する。GA100とAMD Aldebaranのdie area誤差は5.1%と8.1%で、性能/コストを同じ設計探索内で比較できる。

## 評価条件

| 項目 | 条件 |
|---|---|
| 実機検証 | NVIDIA A100、AMD MI210、Google TPUv3 |
| 大規模例 | GPT-3 175B、4-way tensor parallel |
| 模擬host | Intel Xeon Gold 6242R 3.10GHz 1 core |
| prefill分析 | GPT-3 1 layer、batch 8、input 2048 |
| decode分析 | 1024番目output token |
| 指標 | latency誤差、simulation時間、面積誤差、性能/コスト |
| 比較対象 | 実機、roofline/cycle-level手法との設計上の比較 |

## 主要結果

| 評価 | 結果 | 意味 |
|---|---:|---|
| operator latency | 平均誤差10.4% | tile-level抽象化でも個別演算を概ね再現 |
| LLM inference latency | 平均誤差4.1% | operator誤差がend-to-endで大きく累積しない |
| GPT-3 175B / 4×A100 | 15〜16分 | 26,400 mapping候補込みで設計探索可能 |
| GA100/Aldebaran面積 | 誤差5.1% / 8.1% | area/cost探索にも利用可能 |
| compute/buffer半減設計 | 元性能の95.3%維持 | decode中心では過剰computeを削れる |
| cost-oriented設計 | 最大3.41倍 performance/cost | DRAM等を含む別設計点がA100型より有利になり得る |

重要な負の結果は、throughput志向で大容量DRAMと大batchを使う設計では、GA100比で平均latencyが9.21倍悪化することである。weightをbatch当たり一度だけ読むことでthroughputは上がっても、batch増大でKV cacheと中間値のreadが増えるため、latencyとthroughputの交換条件は消えない。

## 既存研究との差
rooflineは演算強度と帯域から上限を高速に見るがmappingを粗く扱い、cycle-level simulatorは詳細だがLLM規模の探索が遅い。LLMCompassはLLMのdense operatorの規則性を利用し、tile-level mapping探索とarea/cost modelを結合する。さらに単なる評価器ではなく、そのモデルを使って「prefillはcompute/buffer、decodeはmemory bandwidth」というLLM固有の設計則を抽出し、新しいhardware構成まで探索する。

## 限界
性能モデルは公開情報と規則的なoperatorを前提とし、proprietary cache・scheduler・network contentionを完全再現するものではない。FlashAttentionのようなsoftware固有最適化はmemory access patternとしてモデル化可能とするが、論文の中心評価ではない。cost modelもIP、mask、packaging costを含まない。したがって3.41倍performance/costは実製品の総所有コストではなく、論文のモデル条件下の設計比較として読む必要がある。
