# GEMINI：CPUメモリの冗長チェックポイントで大規模分散学習を高速復旧する

## 概要

巨大な言語モデルの同期分散学習では、一部の計算機が故障すると残りの計算機も同じ学習時点へ戻る必要がある。従来の障害復旧は、遠隔の永続ストレージへ数十分〜数時間おきに保存したチェックポイントを読み戻すことに依存する。保存頻度を増やせば故障前に失う学習進捗は減るが、遠隔ストレージの集約帯域が不足すると保存そのものが長くなり、学習を妨げる。GEMINIは、GPU計算機が備える比較的大容量のCPUメモリと計算ノード間の高速ネットワークを、短期の障害復旧専用保存階層として使う。

提案は単なる「メモリへ保存する」という発想ではない。CPUメモリ上のコピーは計算機ごと失われる可能性があるため、GEMINIは**複製数とノード数に応じたチェックポイント配置**を計算する。また、学習の勾配同期・パラメータ取得とチェックポイント送信が同じネットワークを共有するため、**学習通信の空き時間を測定して分割転送を挿入**し、GPU間送信とGPUからCPUへの複写をパイプライン化する。復旧時にはローカルCPU、別ノードのCPU、遠隔永続ストレージの順に利用可能な完全な保存状態を探す。

原著の16台のp4d.24xlarge（計128基のA100）による1000億パラメータのGPT-2型学習では、1反復約62秒に対しメモリチェックポイント作成は3秒未満で、**毎反復保存**を実現した。高頻度の遠隔保存方式HighFreqと比べ、CPUメモリから復旧できる条件で平均無駄時間を13倍超削減する。これは学習反復の計算速度が13倍になるという意味ではなく、障害発生時に失う進捗と保存状態の読戻しに費やす時間の改善である。

## 問題設定：障害による無駄時間を何が決めるか

著者らは、障害時の無駄時間を「最後の利用可能なチェックポイントから障害までの再実行が必要な進捗」と「チェックポイント読戻し時間」の和として扱う。チェックポイントを作成する時間を `t_ckpt`、保存頻度を `f`、読戻し時間を `t_rtvl` とし、障害が保存間隔に一様に起こると仮定すると、平均無駄時間は `T_wasted = t_ckpt + 1/(2f) + t_rtvl` と書ける。保存処理が次の保存と重複できない条件では、保存間隔は少なくとも保存時間と学習反復時間の大きい方である。

遠隔永続ストレージを利用する既存方式では、ネットワーク越しの保存と読戻しが律速になる。原著は、20Gbpsの遠隔ストレージに対して大規模モデルのチェックポイント作成が42分を要する例を挙げる。頻繁に保存しようとしても帯域制約で実現できず、保存間隔を広げれば故障直前の多数の反復が失われる。GPU数の増加と学習期間の長期化は、これを一回限りの例外ではなく総GPU時間を圧迫する運用費用へ変える。

一方、GPU計算ノードにはGPUメモリより大きなCPUメモリがある。原著のp4d.24xlargeはGPUメモリが40GB×8に対しCPUメモリが1152GBであり、ノード間は400Gbpsの高速ネットワークで接続される。直近の復旧用状態をCPUメモリへ置けば、遠隔ストレージへの送信を毎回行わずに済む。しかしCPUメモリは永続保存ではない。計算ノード自体の故障で複製が失われる危険と、チェックポイント送信が学習通信を圧迫する危険を別々に解く必要がある。

## 手法

### 1. 障害復旧用と長期保管用を分離した階層保存

GEMINIは、短期の障害復旧用チェックポイントを各ノードのローカルCPUメモリと他ノードのCPUメモリに保存する。長期の実験再開、転移学習、デバッグなどに使う履歴は従来どおり遠隔永続ストレージへ低頻度で保存する。メモリ階層だけで全履歴を保持しようとはしない。障害復旧用の最新状態を短い間隔で上書きし、長期履歴の保存頻度とは独立させる。

各計算ノードの作業エージェントは、担当GPUの重みと最適化器状態をCPU側へ退避する。原著の実装では、完成済みチェックポイントと書込中チェックポイントを区別する二つのCPUバッファを設ける。これにより途中までしか転送されていない状態を誤って復旧に使わない。故障検出後はルートエージェントが共有の状態ストアを参照し、健全な計算ノードや交換ノードへ復旧元を指示する。

### 2. グループと環状配置を組み合わせる複製戦略

入力は学習に参加する計算機数 `N` と、各計算機のチェックポイント複製数 `m` である。`N` が `m` で割り切れるとき、計算機を `m` 台ずつのグループに分け、各計算機が自分のCPUメモリへ1複製、同じグループの残り `m−1` 台へ各1複製を配置する。これにより各計算機の保存・送信負担が揃い、同一グループの全ノードが同時に失われない限り、そのグループの状態を復旧できる。

`N` が `m` で割り切れない場合、先頭の完全グループには同じグループ方式を使い、端数を含む最後のグループでは環状に隣接する `m−1` 台へ複製する。これが混合配置である。原著の定理1は、割り切れる場合の配置がCPUメモリからの回復確率を最大化し、割り切れない場合にも通信時間を最小化しつつ最適値との差を上から抑えられることを示す。ただしこの保証は論文が定義したノード故障・複製配置のモデルに対するもので、同じラックや電源系統の相関故障を完全に排除する保証ではない。

例えば `N=16、m=2` の場合、2台が同時に失われてもCPUメモリから復旧できる確率は93.3%、3台なら80.0%と計算される。2台故障時の残り6.7%では、2複製が同時に消えた状態が生じる。環状配置と比べて、グループ配置は復旧確率を改善するが、CPUメモリの複製が絶対に失われないわけではない。復旧できない場合に備えた遠隔永続ストレージは引き続き必要である。

### 3. 学習通信の空き時間を使う分割転送

ZeRO-3の学習中には勾配同期やパラメータ取得が走る一方、GPUが演算している間にはネットワーク通信の空き区間がある。GEMINIは初期の約20反復を計測し、通信開始・終了時刻から各反復の空き区間を推定する。その区間にチェックポイント通信を割り当てれば、学習用の通信を待たせずに済む。空き区間の変動を見込んで、利用可能時間に係数 `μ` を掛けて保守的に予定する。

GPU全体の状態を一括で別GPUへ送ると、受信側の空きGPUメモリが足りずメモリ不足になる。原著のGPT-2 100Bでは1GPU分のチェックポイントが約9.4GBであり、全量を受信バッファに載せるのは現実的でない。GEMINIはGPU通信専用に128MBを確保し、これを複数の小バッファへ分割する。各区間の長さ、ネットワーク帯域、通信開始の固定費、残りの転送量を使って、どのサイズの塊を何個送れるかを決める。

受信した塊はGPUからCPUへコピーする。ここで単一バッファだと、CPUコピーが終わるまで次のネットワーク受信を開始できない。GEMINIは小バッファを交互に使用し、ある塊のGPU→CPU複写中に別の塊をGPU間通信で受信する。実験の構成要素比較では32MB×4の小バッファを使い、通信とコピーの重なりを増やした。出力はCPUメモリに保存された完全な複製と、学習通信を妨げにくい転送予定である。

空き時間だけでは全量を送れない条件もある。原著のアルゴリズムは残余を最後の区間へ割り当て得るため、その場合は学習反復が延びる。著者らは保存頻度を下げて費用を償却する選択を示す。したがって毎反復保存と性能無劣化は、評価した大規模モデルの通信空き時間が十分だったという条件付きの結果である。

### 4. 故障検出、整合した状態の選択、再起動

各ノードの作業エージェントは健全性を分散キー・値ストアへ更新し、ルートエージェントが異常を検出する。ルート側が故障した場合も、健全な作業ノードから新しいルートを選ぶ。クラウド事業者の計算機交換機構を利用し、交換ノードがどこからチェックポイントを取得すべきかを決定する。故障したノードがCPUメモリの複製を失っていなければローカルから、そうでなければ他ノードのCPUメモリから読む。

同時故障で必要な複製を失った場合、残存する一部の新しいメモリチェックポイントだけを混ぜて復旧することはできない。同期学習では全ノードの学習状態を同じ反復へ揃える必要があるため、遠隔永続ストレージに残る古い共通チェックポイントへ戻す。この後退を含めることで「どんな障害でもメモリから復旧できる」わけではない一方、最終的な復旧可能性を維持する。

## 主要結果

### 1. 保存時間と頻度、学習反復への影響

GPT-2 100Bを16台のp4dで学習した場合、1反復は約62秒である。GEMINIのCPUメモリ保存は3秒未満で、ネットワークの空き時間に重ねることで**毎反復保存**を実現した。HighFreqと比べて保存頻度は8倍、3時間間隔のStrawmanと比べて170倍超である。16台・400Gbpsの条件で、遠隔ストレージ保存に対する保存時間短縮は250倍超、100Gbpsに制限すると65倍であり、帯域とノード数に強く依存する。

100BのGPT-2、RoBERTa、BERTで、GEMINIを用いた50反復と通常DeepSpeedの50反復を比較したところ、学習反復時間に目立った増加はなかった。これは大規模モデルの通信空き区間が十分あったことを意味し、全ての学習ジョブで通信競合がなくなるという証明ではない。V100を用いるp3dn環境の10B、20B、40Bモデルでも同様の傾向が報告される。

### 2. 故障時の平均無駄時間と復旧確率

`N=16、m=2` では、2台同時故障時にCPUメモリから復旧できる確率が93.3%、3台では80.0%である。1台故障などメモリから復旧できる条件では、他ノードのCPUからチェックポイントを読む時間は3秒未満だった。原著の平均無駄時間の比較では、**HighFreq比で13倍超の改善**を報告する。一方、2台故障で複製を失う6.7%の条件では、遠隔保存へ戻るためStrawman相当まで悪化する。

この「平均無駄時間」は、論文の式(1)に従う保存間隔と読戻しの費用である。現実の障害で必要なノード交換、直列化、学習プロセス再初期化の全費用をそのまま表すものではない。原著の故障注入では検出に15秒、チェックポイント直列化に162秒、再起動のウォームアップに253秒を要した。クラウドの交換ノード確保にはさらに約4〜7分かかり、メモリから復旧できてもソフトウェア障害で約7分、ハードウェア障害で約12分の総費用が残る。

### 3. 通信重畳の構成要素比較

| 方式 | GPT-2 40B、16台のV100環境での観測 |
|---|---|
| チェックポイントなし | 反復時間の基準 |
| 反復先頭で同期的に保存 | 反復時間が10.1%増加 |
| 空き区間へ単純に塊を配置 | 最大空き区間1.6秒を満たすため2GB超のGPUバッファが必要となり、メモリ不足を生じる |
| 128MB単一バッファで分割、パイプラインなし | GPU→CPUコピー待ちにより反復時間が3.5%増加 |
| GEMINIの32MB×4バッファ | 転送とコピーを重ね、基準に近い反復時間を維持 |

この比較は、単に小分けにするだけでは不十分で、GPU間通信とCPUメモリへの複写を同時進行させる必要があることを示す。高速ネットワークだけでなく、GPUメモリの空き容量とバッファの再利用順序が実効性能を左右する。

### 4. 規模拡大と故障頻度のシミュレーション

原著は、実機測定した保存・復旧費用を入力として故障頻度と計算機数を変えたシミュレーションも実施する。16台のp4dで1日に8回故障する条件でも、GEMINIの実効学習時間比は障害なし基準に近いと報告する。1000台、1台あたり日次1.5%の故障率という仮定では、実効学習時間比は約91%で、HighFreqより54%高いとする。ただし**1000台の実クラスタで100Bモデルを学習して直接測った結果ではない**。故障分布、予備ノードの利用、クラウド交換待ち時間などの仮定を変えれば結果も変わる。

## 既存研究との差

CheckFreqなどの遠隔保存最適化は保存頻度を動的に選ぶが、遠隔ストレージの帯域制約自体は残る。DeepFreezeなどの非同期保存も永続ストレージへの書込みを中心とする。GEMINIは障害復旧用の短期状態を計算ノード群のCPUメモリへ移すため、容量と帯域の律速を別の階層へ移動する。チェックポイントを非可逆圧縮して保存量を減らす方式とも異なり、復旧状態の値を変える圧縮は行わない。

CPUメモリへの冗長保存自体は分散システムで知られているが、GEMINIは学習に参加する全ノードを使う場合の複製配置を解析し、学習通信とチェックポイント通信の干渉を避ける配置・転送を組み合わせる。特に「通信空き区間を測る→GPUの小バッファへ分割する→GPU間通信とGPU→CPUコピーを重ねる」という経路は、大規模モデルのGPUメモリ余裕が小さいという条件に即した設計である。

## 限界・負の結果・適用条件

第一に、CPUメモリ上の複製は永続ではない。同一グループ内の複数ノードが同時に失われれば、最新のメモリ状態を復元できず、古い永続チェックポイントへ後退する。93.3%という値は特定の16台・2複製・2台故障のモデルであり、ラック・電源・ネットワークの相関障害を含む一般的な耐障害率ではない。複製数を増やせば回復可能性は上がるが、CPU容量とネットワーク送信量も増える。

第二に、保存が学習性能を損なわない条件は通信の空き時間が十分あることである。高い通信負荷、別の並列方式、GPUメモリの不足、PCIe・ネットワーク帯域の低い環境ではチェックポイント送信が学習と競合する。論文のアルゴリズム自体も空き時間が不足すれば反復延長を許し、保存頻度を下げる。毎反復保存を普遍的に保証していない。

第三に、論文が最適化する平均無駄時間と、障害検出から学習再開までの壁時計時間は別物である。後者には直列化、計算ノード交換、プロセス再起動が含まれ、実測では数分かかる。保存・読戻しの改善倍率を、全障害復旧の待ち時間が常に13分の1になると解釈できない。

第四に、原著の実装は静的な計算資源で行う同期学習とDeepSpeed ZeRO-3を主対象とする。弾力的なノード増減、非同期学習、任意のパイプライン並列・テンソル並列での同等の性能は実証していない。論文は他の並列方式にも設計を適用できると述べるが、評価した環境と将来適用可能性を区別する。

第五に、実機の主評価は2023年時点のA100/V100クラスタとEFA接続である。小規模なローカル学習、Windows上の民生GPU、単一計算機、2026年の最新分散学習ランタイムに対する同じ改善倍率は示されていない。単一ノードでは複製を別ノードへ分散する意義も小さく、GEMINIの主目的であるクラスタ規模の障害復旧とは条件が異なる。

第六に、原著は障害時に失われた反復を減らすための状態保存を対象とする。学習済みモデルの推論スループットやKVキャッシュの圧縮を改善する論文ではない。CPUメモリを使うという共通点だけで、推論時の重みオフロードの性能と同一視しない。
