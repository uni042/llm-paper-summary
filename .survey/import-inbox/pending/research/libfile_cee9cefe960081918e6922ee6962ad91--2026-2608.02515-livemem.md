# LiveMem: Maintaining Memory State Continuity in Long-Running LLM Inference

## 概要
長時間動作するassistantやagentでは会話・観測列がcontext windowを超える。単純なtruncationは古い情報を失い、検索拡張生成（retrieval-augmented generation; RAG）は必要時に外部textを再取得できるが、モデル内部の計算状態をlifecycle全体で連続させるものではない。LiveMemはこの要件を「context turnover下の状態連続性」と定義する。

pretrained full-attention LLMへ固定容量のrecurrent memory side pathを追加し、主attentionはbounded KV windowだけを維持する。古いchunkがKVからevictされるときもside pathのmemory stateは次chunkへ継承される。memory-oriented post-trainingでこのstateを実際の回答に使うよう学習し、state-aware servingが要求をまたいでstate lifetimeを管理する。

LongMemEvalでは回答根拠がactive windowから完全に除去された条件でも、LiveMem-RLは16.5% accuracyを維持し、base model 3.1%、比較side-path 3.6%を上回る。evidence distance分析では根拠が最大64K token前にevictされた条件でも利用可能な情報が残ることを確認する。

## 問題設定
通常のKV cacheはactive contextのtokenごとに増えるため、無限lifecycleをそのまま保持できない。sliding windowは容量を固定できるが、window外へ出たtokenの計算表現を失う。summaryはtextへ情報を圧縮するため更新のたびに生成費と情報選択が必要で、RAGは外部indexへ保存された離散的な記録を再取得する。

LiveMemが求めるのは「過去textを必要時に再表示する」ことではなく、過去の処理結果を固定容量の内部stateとして次の推論へ連続させることにある。そのためstateは元tokenが解放された後もload-bearing、すなわち回答に実際に寄与する必要がある。

## 手法
### recurrent memory side path
各attention layerにGated DeltaNet-2系のrecurrent side branchを追加する。主経路は元のfull-attention能力をbounded window内で使い、side branchは過去chunkから得た情報を固定サイズstateへ更新する。state容量はlifecycle長に比例して増えない。

### context turnover
入力streamを処理し、主KV windowが容量へ達すると古い部分を解放する。解放前にその履歴はmemory side pathの更新へ反映され、次のchunkでは前chunkのstateを初期状態として処理を続ける。したがってKVのtoken lifetimeとmemory stateのlifetimeを分離する。

### memory-oriented post-training
side branchを付けるだけではbase LLMがそのstateを利用する保証がない。論文は古い根拠をactive contextから外した状態で回答を要求する学習を行い、state経由で必要情報を保持・利用するよう調整する。RL段階では回答正確性に基づくrewardを用い、固定容量内でtask-relevant情報を優先する。

### state-aware serving
serving runtimeは通常のKVと別にmemory stateをrequest/sessionへ対応付ける。新しいinteractionが来るたびにbounded contextとpersistent stateを読み、推論後に更新stateを保存する。これにより長い履歴text全体を毎回prefillし直さず、lifecycle継続を状態として表現する。

## 評価条件
|項目|内容|
|---|---|
|主対象|long-running assistant / agent inference|
|主要benchmark|LongMemEval、multi-question系長期記憶task|
|比較|base/truncated context、RAG、他intrinsic memory方式|
|重要試験|supporting evidenceをactive windowから完全evict|
|追加分析|evidence distance、最大64K token前のevicted evidence|
|性質|固定容量state + bounded KV window|

## 主要結果
|条件|結果|意味|
|---|---:|---|
|LongMemEval evidence-evicted|LiveMem-RL 16.5%|window外の根拠をstateから利用|
|同条件 base model|3.1%|bounded active contextだけでは大幅低下|
|比較side-path|3.6%|単にrecurrent branchを付けるだけでは不足|
|evidence distance|最大64K token前でも有効情報を確認|stateが直前chunkだけでなく長距離へ持続|
|2Wiki-MQ等|評価系でleading overall performance|複数情報を結ぶtaskでもstateが寄与|

## 既存研究との差
sliding-window attentionは計算量を抑えるがevicted tokenを忘れる。RAGは外部memoryからtextを検索してcontextへ戻す。LiveMemは外部text retrievalではなく、モデル内部のrecurrent stateをattention backboneと並行して保持する点が異なる。したがってRAGと排他的ではなく、正確な原文検索はRAG、継続的な内部状態はLiveMemという補完関係を想定できる。

## 限界
memory stateはlossyで、任意のrandom stringや過去文章の逐語的再構成を保証するarchiveではない。exact recallが必要な用途ではretrievalとの併用が必要になる。固定容量ゆえlifecycleが伸びても情報量を無限に保持できず、post-trainingで何を残すかを学習する設計に依存する。またbase backboneの位置表現やattention側制約は残り、side stateがそれらすべてを解消するわけではない。
