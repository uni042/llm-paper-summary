# FaaScale：重みの配信中から推論を始めるサーバレスLLMの動的スケールアウト

## 概要

FaaScaleは、サーバレスのLLM推論サービスでリクエストが急増した際、新しいGPUインスタンスへ巨大なモデル重みを転送し終えるまで推論を開始できないというcold startの問題を扱う。通常のモデル配信では、GPUノードが完全な重みを受け取ってからリクエストを処理する。Llama-70Bのようなモデルは重みだけで約140GBを必要とし、SSDやオブジェクトストレージから読み込むと数十秒以上の遅延が生じる。高頻度の突発負荷に備えてGPUを常時確保することは、サーバレスの費用効率を損なう。

著者らは、重みのブロックをGPU間でマルチキャストしながら、すでに一部のモデル層を受け取ったGPUを連結して一時的なpipeline parallel推論を開始する。これをpipelined multicast inferenceと呼び、PipeCastという仕組みで実装する。各GPUが全モデルを受信すると、一時的な分散パイプラインから通常のローカル実行へ切り替え、通信の追加費用をなくす。GPU・ホストメモリの階層を利用したモデル管理も組み合わせる。

Llama-2 7B/13B/70Bと最大12ノード・24台のNVIDIA H800を用いた実機評価では、従来のFaaSNet、NCCL、ServerlessLLMに比べてP90 TTFTが2.4〜5倍改善したと報告する。実際のBurstGPT到着トレースを使った30分のスケールアウト評価では、累積GPU時間を比較方式に対して17.8〜31.3%削減した。これはモデルの演算カーネルそのものを高速化した結果ではなく、モデル配信と実行を重ね、要求の待ち時間と過剰なGPU確保を減らしたシステム上の改善である。

## 問題設定

サーバレスLLMでは、多数の利用者が異なる基盤モデルや微調整モデルをAPI経由で呼び出し、プラットフォームが需要に応じてGPUを確保・解放する。リクエストの到着率は短時間で10倍以上に変動することがあり、必要なモデルのコピーを新しいノードへ急速に展開する必要がある。常時十分なコピーを持つ方式は低遅延だがGPUコストが高く、必要になってから重みをロードする方式は低コストだがcold startが長い。

モデルをローカルCPUメモリやSSDへキャッシュする方式にも限界がある。多数のモデルを同じGPUクラスタで提供すると、ホストメモリが全モデルを保持できず、頻繁な追い出しが発生する。原著のモデル保持時間の分析では、一定のキャッシュ設定で95%超のモデルが15秒未満でメモリから追い出される。別のトレースではSSDからのロードが全ロードの64%または36%に達する。これらは特定のトレースとキャッシュ設定での観測であり、あらゆるクラウドの普遍的なキャッシュミス率ではない。

ネットワーク上の別GPUから重みを配信すればSSD読み込みを避けられるが、従来のbroadcastやmulticastは配信完了を待ってから新しいコピーを実行する。FaaScaleの発想は、モデルを一時的に複数GPUへ分割配置し、その状態で推論を開始することで、重みの配信完了前にユーザーへ最初のトークンを返すことにある。

## 手法

### 1. ブロック単位の二項パイプライン・マルチキャスト

PipeCastはモデルの重みを細かいブロックへ分割し、複数の送信元・中継先を持つ二項パイプラインで配信する。各ノードは受け取ったブロックを隣接ノードへ転送し、別のブロックの受信と送信を並列化する。単一の送信元が全受信先へ同じデータを順番に送るより、クラスタの複数リンクを利用できる。通信にはGPUDirect RDMAを使い、GPU間のデータ移動をCPUメモリ経由のコピーなしで行う。

論文のk-way transmissionは、初期モデルコピーを保持する送信元グループの数kに応じて、重みブロックの配信順序を組み替える。k=1、2、4などの条件で、モデルの複製を効率的に拡大する。通信トポロジだけでなく、どの層がどのノードに到着したかを実行スケジューラへ伝え、一時的な推論パイプラインを構築できるようにする点が通常のマルチキャストとの違いである。

### 2. モデル配信中に動的な推論パイプラインを形成する

通常のモデルコピーでは、受信側が全ての層をロードするまで推論を開始できない。PipeCastでは、複数のノードに受信済みの異なる層が揃った段階で、ノードをつないだpipeline parallel実行を開始する。リクエストの中間活性値をノード間で送る必要はあるが、モデル重みの配信完了を待たずに生成を始められる。

一つの動的パイプラインがリクエストの全トークンを反復して処理するため、トークンごとにKVキャッシュを別のノードへ移動させる必要はないと著者らは説明する。各段階で必要な層のKVをその段階に置き、パイプラインを構成するノード間で中間活性値だけを交換する。これにより、重み配信中の一時的な推論能力を作る。

ただし分散パイプラインは無料ではない。段間同期と中間活性値の転送が追加され、図8ではkが大きいとスループット曲線に階段状の停滞が見える。これは一時的な分散実行の通信オーバーヘッドによる。したがってPipeCastは、分散推論を永久に使うのではなく、各ノードが全重みを受信した後は通常のローカル実行へ切り替える。

### 3. GPU・ホストメモリの局所性を利用する

FaaScaleはクラスタマネージャと各ノードのモデルマネージャを分け、どこにモデル重みが存在するかを管理する。GPUに完全なモデルがあれば即時利用し、ホストメモリにキャッシュされていればそこからロードする。ローカルキャッシュがない場合は、別のGPUからPipeCastでモデルを配信する。GPU常駐とホストキャッシュを組み合わせ、必ずしもSSDから再ロードしないようにする。

さらに重みをブロック単位で管理し、bulk transferに適したメモリ配置へ統合する。GPUメモリの事前確保によってモデル起動時の割当費用を減らす。これは、ネットワーク帯域だけを改善してもGPU側の細かいメモリ割当や転送準備が律速になることを避けるための設計である。

### 4. クラスタ全体の需要に合わせてコピーを増減する

クラスタマネージャはリクエスト到着率を観測し、必要なモデルコピーを持つノードを選び、モデルの転送と動的パイプライン形成を調整する。負荷が下がれば不要なGPUを解放する。単にモデルを素早く配信するだけでなく、配信途中から処理を開始できるため、スケールアウトの遅れによるキュー待ちを短縮し、需要減少後の過剰なGPU保持も抑える。

この方式は、推論カーネルの低ビット化やKV圧縮ではない。モデル重みを複製する際の通信と実行のスケジュールを変えるシステム設計であり、モデルの正答率や出力分布は基本的に既存のモデル実行に従う。

## 評価条件

| 項目 | 原著の条件 |
|---|---|
| モデル | Llama-2 7B、13B、70B |
| GPU | NVIDIA H800、最大24台 |
| クラスタ | 1GPU/ノード×最大12ノード、4GPU/ノード×最大6ノード |
| ネットワーク | 各ノード400Gb/s InfiniBand NIC、GPUDirect RDMA |
| k-way送信 | k=1、2、4 |
| 比較方式 | ServerlessLLM、FaaSNet、NCCL broadcastの適応版 |
| 動的トレース | BurstGPTの30分区間 |
| 指標 | モデル配信時間、スループットの立上り、TTFT/P90 TTFT、累積GPU時間 |

7Bと13Bは単一GPUへ全モデルを載せられる構成でノード間展開を試す。70Bは一ノード内の4GPUでモデルを保持し、ノード間でモデルコピーを増やす。すべての条件が同じGPU枚数・モデル並列度というわけではない。ServerlessLLMはローカルのホストメモリ・SSDキャッシュからロードし、FaaSNetとNCCLはネットワーク転送を使う。比較対象のデータ供給元が異なるため、単一の「通信アルゴリズムの優劣」だけを測ったものではない。

## 定量結果

### 1. モデルマルチキャストの時間

原著図7はモデルを複数ノードへ転送し終えるまでの時間を比較する。FaaScaleはFaaSNet比で最大1.82倍、NCCL比で最大1.53倍の転送高速化を報告する。7Bを少数ノードへ配信する場合は差が小さいが、70Bを4ノードへ配信する場合や13Bを12ノードへ配信する場合は、二項パイプラインによる帯域利用が効く。

この結果はモデル転送時間の比較であり、リクエストのTTFTや生成スループットと同一の数値ではない。FaaScaleの中心的な利点は転送を速くすることに加え、転送完了前から推論を始められることにある。

### 2. スループットの立上り

図8は高負荷でモデルコピーを増やす際のtokens/sの立上りを示す。7Bの例ではk=1で約0.6秒後にスケールアウトが始まり、k=4では約0.15秒へ短縮する。FaaSNetやNCCLはモデル転送が終わるまで受信先の推論能力が増えないが、FaaScaleは部分ロード済みノードの分散パイプラインで早期に処理を始める。

ただしk=2や4では、分散実行中の中間活性値転送と同期によって、スループット曲線が階段状に停滞する場合がある。著者は一時的な分散パイプラインのオーバーヘッドと説明しており、重み配信後のローカル実行へ切り替える設計が必要な理由となる。

### 3. TTFTとtail latency

図9は負荷を変えたときのTTFTと、特定RPSでの分布を示す。FaaScaleは一連の50リクエストを1.1秒で処理開始でき、FaaSNet比2倍、NCCL比1.4倍、ServerlessLLM比8倍の早さと報告する。論文全体の要約では、P90 TTFTの改善倍率を2.4〜5倍としている。前者は特定のバースト処理開始の比較であり、後者はP90の改善範囲であるため、同一の測定値として扱わない。

ServerlessLLMはSSDからモデルをロードする場合、転送完了まで待つためtail TTFTが悪化する。一方、GPU間配信を使う方式はSSDの読み込みを回避できるが、FaaScale以外は配信途中の推論ができない。したがってFaaScaleの利得には、ネットワークマルチキャスト、配信中の推論、モデル局所性を考慮したロードという複数要因が含まれる。

### 4. 実トレース下のGPU費用

原著§7.4はAzure OpenAI系のBurstGPTから30分のリクエスト到着トレースを取り出し、モデルコピーのスケールアウト・インを評価する。比較対象のGPU時間を累積した結果、FaaScaleはFaaSNet比17.8%、NCCL比18.1%、ServerlessLLM比31.3%少ないGPU資源を消費した。ゼロ秒でモデルをロードできる理想的なスケーリングに対しても、FaaScaleのGPU時間は4.3〜18.6%の差に収まると報告する。

ここでいう「コスト削減」は累積GPU時間を指し、クラウド事業者の課金単価、ネットワーク帯域料金、運用人件費、モデルストレージ料金を全て含むTCOではない。高帯域RDMAネットワークを新設する費用まで加味した経済評価でもない。

### 5. 失敗・弱点となる条件

小さいモデルを少数ノードへ配信する場合、FaaScaleのマルチキャスト利得は限定的である。またNCCLはGPUとNICのNUMA配置やトポロジに合わせた最適化があり、12ノード条件ではFaaScaleの相対利得が縮小する。さらに分散パイプライン実行中は中間活性値の転送・同期が追加されるため、ネットワーク帯域が低い環境やモデル分割が細かすぎる条件ではオーバーヘッドが増える。

ServerlessLLMのホストメモリキャッシュが高い確率で命中する場合、SSDロードの欠点は小さくなり、FaaScaleの差も縮小する可能性がある。実トレースのTTFT分布でもServerlessLLMの曲線が条件によって左へ寄ると原著は説明しており、常に最大5倍の差が出るという意味ではない。

## 既存研究との差

FaaSNetはサーバレス関数のコンテナ配信を効率化し、NCCLはGPU間の集合通信を最適化する。しかし両者はLLMの層構造を利用して、重みが完全に配信される前から一つのモデルを複数GPUで実行する設計ではない。FaaScaleはモデル配信順序と実行パイプライン形成を協調させることで、単なる転送高速化以上の利得を得る。

ServerlessLLMはモデル重みをホストメモリやSSDへキャッシュして起動時間を短縮する。FaaScaleもローカルキャッシュを利用するが、キャッシュミス時には別のGPUに存在するモデルコピーからRDMAでブロックを配信する。多数のモデルがホストメモリに収まらない多テナント環境で、単一ノードのキャッシュに依存しない点が違いである。

BlitzScaleなどの分散モデル起動方式はprefill/decode分離を前提とする場合があるが、FaaScaleは一般的なサーバレスLLM推論を対象に、モデル配信中の動的パイプラインを形成する。これは、P/D disaggregationやKVキャッシュの外部共有を直接改善する研究ではなく、モデルコピーのスケールアウトと初期推論を重ねる研究である。

## 限界と再現上の注意

第一に、実験環境は高帯域400Gb/s InfiniBandとGPUDirect RDMAを備えたH800クラスタである。一般的なEthernetや帯域の小さいエッジネットワークでは、重みのマルチキャストと中間活性値転送の費用が増えるため、同じ改善率を期待できない。GPU・NICのNUMA配置が性能へ影響することも原著が明示している。

第二に、評価モデルはLlama-2 7B/13B/70Bであり、MoE、巨大マルチモーダルモデル、複雑な推論グラフ、異種GPU構成での動的パイプラインを直接評価したわけではない。モデル層を順序良く分割できることが方式の重要な前提となる。モデルの量子化や重み共有がある場合はブロック転送の粒度と計算配置を再調整する必要がある。

第三に、比較方式の実装とロード元が異なる。ServerlessLLMはホストメモリまたはSSDを使い、FaaSNetとNCCLはGPU間RDMA転送を使う。FaaScaleは局所性を利用して両方を組み合わせる。したがって性能差を「同じデータ転送だけを何倍高速化した」と解釈せず、配信・実行・キャッシュ管理を合わせたシステム全体の比較とみなすべきである。

第四に、原著のGPU費用は累積GPU時間に基づく。RDMAネットワークの設備費、電力、ストレージ、クラスタマネージャのCPU費用、テナント間の公平性、課金単価は十分に含まれていない。実サービスのTCOへ換算するには、GPU単価だけでなくネットワークとストレージの費用を別途加える必要がある。

第五に、配信中の一時的なパイプラインには段間通信と同期の費用がある。重み配信が完了した後はローカル実行へ切り替えることでこの費用を避けるが、切替時の実行状態、障害復旧、GPU間の負荷不均衡を大規模本番環境でどう扱うかは追加検証が必要である。モデルの一部だけが届いた時点で推論を開始するため、パイプライン構成が成立するまでの待ちはゼロにはならない。

第六に、実トレース評価はBurstGPTの30分区間であり、別のモデル人気分布、長時間の需要変化、頻繁なモデル更新、ネットワーク障害、マルチテナントの競合を完全には代表しない。論文の最大改善値は評価条件に依存する。性能比較では、モデルの配信時間、スループット立上り、P90 TTFT、累積GPU時間を別々に扱うべきである。
