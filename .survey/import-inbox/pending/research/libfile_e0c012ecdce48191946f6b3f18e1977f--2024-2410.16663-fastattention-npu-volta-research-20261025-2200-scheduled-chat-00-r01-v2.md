# FastAttention：Ascend NPUとVolta GPUに適応したFlashAttention系カーネル

## 概要

本方式は、FlashAttention2で用いられるブロック分割・オンラインソフトマックス・演算融合の考え方を、Huawei Ascend 910B（NPU）とNVIDIA Volta世代のV100 GPUへ適応する推論システムである。従来のFlashAttention2/3は新しいNVIDIA GPUの命令やメモリ階層を前提とする部分があり、NPUや古いGPUへ同じカーネルを移すだけでは高い性能を得られない。本方式は、NPUの行列演算器とベクトル演算器と専用メモリ、V100のテンソル演算命令に合わせてデータ配置と通信を設計し直す。

Ascend 910Bでは、二段階タイル分割によって演算器間の同期とデータ転送を抑え、因果マスクを小さなテンプレートから生成する。複数NPUではブロックごとの全体集約通信を計算と重ねる。V100ではm8n8k4 行列積命令に合わせた共有メモリレイアウトを採用し、GPUメモリが不足する長文脈推論では一部の層のKVをCPUに置いてCPU側で注意演算を実行する。

原著はAscend 910Bの注意演算単体で単純実装比最大10.7倍、同環境のLLaMA2-7Bで最大5.16倍のトークン処理量を報告する。V100ではxformersの対応注意演算比最大1.43倍、8基のV100でFasterTransformerに組み込んだPanGu-38Bでは最大1.46倍のモデル全体の高速化を報告する。ただし、10.7倍は非融合の単純な注意演算との比較であり、すべてのGPU・モデルで10倍の生成速度が出るという意味ではない。

## 背景：高速注意演算の移植が難しい理由

標準的な注意演算は `softmax(QK^T / sqrt(d))V` であり、入力長が長いほどQKの中間行列が大きくなる。高速注意演算はQ/K/Vをブロック化し、オンラインソフトマックスを用いて中間行列を外部メモリへ全て保存しないことでI/Oを削減する。FA2はブロックの分割と並列度を改善し、新しいGPUのテンソル演算器と共有メモリを活用する。

しかしAscend NPUはGPUと異なり、行列積を行う行列演算器と要素演算を行うベクトル演算器が独立したバッファやデータ経路を持つ。GPU向けのブロック構造をそのまま用いると、行列演算器とベクトル演算器の間で細かい同期と転送が発生し、NPUの大きな一次キャッシュを活用しきれない。さらに複数NPUでは注意演算後の線形変換演算結果を全体集約通信する処理が律速になり得る。

Volta V100はTensor Coreを持つが、Ampere世代以降のm16n8k16/m16n8k8と異なるm8n8k4 行列積命令を使う。演算タイルの形状、各スレッドが持つ行列要素、共有メモリのレイアウトが違うため、FA2のカーネルを単純に再コンパイルしても実行できない。本方式はV100の命令形状に合わせて行列の並べ方を作り直す。

## 手法

### 1. Ascend NPUの二段階タイル分割

NPU上の基本実装ではQをAI Coreへ分配し、K/Vを系列長方向に小さなブロックへ分ける。行列演算器がQKの行列積を行い、ベクトル演算器が指数関数や正規化などの要素演算を処理する。小ブロックを順番に流すだけでは、行列演算器/ベクトル演算器間の転送と同期が多くなる。本方式は外側に大きなタイルを置き、その内部を小さなタイルへ再分割する二段階方式を採用する。

外側の大きなタイルは連続したデータ読み込みを増やし、同期回数を減らす。内側の小タイルは内部バッファ/一次キャッシュの容量制限を守りながら、行列演算器とベクトル演算器の演算をパイプライン化する。二重バッファリングによってデータ転送と計算を重ね、演算器の空き時間を減らす。原著の図9では、4K入力でPanGu-38Bの注意演算遅延が約26%、PanGu-71Bが約37%低下し、16K入力ではそれぞれ約38%、約45%低下する設定が示される。これは同じ方式のタイル設定比較であり、モデル全体の速度倍率ではない。

### 2. 因果マスクの小型化

因果注意演算では未来トークンを参照しないよう、下三角のマスクを使う。長い系列に対して完全なS×Sのマスクを保存すると、マスク自体が大きなメモリを消費する。本方式は最大ブロック幅Mに基づく小さな(2M)×(2M)のマスクテンプレートを用意し、各注意演算タイルに必要な部分マスクを生成する。全てが無効なタイルは演算を省略でき、全て有効なタイルではマスク加算を省ける。

原著はバッチ1、系列長64Kの完全なマスクに8GBが必要な条件に対し、M=512のテンプレートなら256KBで済む例を示す。これはマスクの記憶量の比較であり、KVキャッシュやモデル重みまで同じ割合で減るという意味ではない。また、無効タイルの計算省略は因果マスクの構造を利用するため、任意の注意マスクで同じ利得が得られるとは限らない。

### 3. 複数NPUのタイル単位の全体集約通信

複数NPUで注意演算と線形変換を実行した後、通常は演算を終えてから全体集約通信で部分結果を集約する。本方式はQをバッチ×系列長方向のブロックに分け、各ブロックで注意演算、線形変換、ブロック単位の全体集約通信を順次行う。あるブロックの通信中に別ブロックの計算を進め、NPUのSDMAを利用して演算と通信を重ねる。

この方式では通信を小さく分割し過ぎると帯域を十分に使えないため、ブロック幅の調整が必要になる。原著は最初のブロックの計算量を小さくして、最初の全体集約通信を早く始める工夫も示す。タイル単位の全体集約通信は二段階タイル分割に依存しており、原著のアブレーションでは全体集約通信だけを単独適用した比較はない。したがって「通信重畳単体で15倍」と解釈するのは不適切である。

### 4. Volta V100向け行列積命令レイアウト

V100のm8n8k4命令は、8スレッド単位のquadpairで行列要素を分担する。Ampere向けの行列積命令を前提とするFA2では、Q/K/Vのタイルを各スレッドへ割り当てる形が異なるため、共有メモリの配置と読み出しを設計し直す必要がある。本方式はV100の行列積命令形状に合わせて演算対象を配置し、オンラインソフトマックスを含む注意演算を実装する。

この部分はNPU向けの二段階タイル分割とは別のハードウェア固有最適化である。V100上の評価では比較カーネルの対応注意演算と比較し、因果マスクなしで2K入力1.03倍、4Kで1.06倍、8Kで1.12倍、16Kで1.17倍となる。因果マスクありでは最大1.43倍と報告する。短い系列では改善幅が小さいため、常に大幅な高速化が得られるわけではない。

### 5. CPU/GPU協調による超長文脈推論

GPUメモリが不足する場合、本方式は全層を一様にオフロードするのではなく、GPU容量から重み・中間表現・語彙行列・KVの必要量を見積もり、CPU側で注意演算を計算する層数L_CPUとGPU側で処理する層数L_GPUを決める。プリフィルではCPU担当層のKVを非同期にCPUへ移し、デコードではCPU側に保持したKVで注意演算を計算する。GPUには結果の小さなベクトルを戻し、FFNなど残りの計算を行う。

通常のKVオフロードは、デコードのたびに長いKVをGPUへ戻すため、PCIe転送量が系列長とともに増える。本方式はCPU上で注意演算を実行するため、GPUへ戻すデータを出力ベクトルに限定できる。CPU演算そのものは系列長とともに重くなるが、巨大なKVの往復転送を避けられる。原著はAVX512などのベクトル化とマルチスレッドを使う。CPUの演算能力が低い環境では、この方法が常に速いとは限らない。

### Ascend 910B：カーネルとモデル全体を区別する

| 比較 | 条件 | 原著の結果 |
|---|---|---|
| 単純注意演算に対する二段階タイル分割 | Ascend 910Bの演算単体 | 3.65～10.7倍 |
| 二段階タイル分割＋タイル単位の全体集約通信 | 複数NPUの注意演算＋線形変換＋通信 | アブレーション表で4.23～15倍（単純実装基準） |
| PanGu-38Bの8 NPU演算 | 入力2K～32K | 1.16～1.40倍 |
| PanGu-71Bの8 NPU演算 | 入力2K～32K | 7.4～26.1%改善（入力長ごとに異なる） |
| LLaMA2-7B生成throughput | Ascend 910B、入力512 | バッチ1：11.03→56.974 token/s |
| LLaMA2-7B生成throughput | 同、バッチ8 | 91.61→436.1 token/s |
| LLaMA2-7B生成throughput | 同、バッチ16 | 158.34→746.27 token/s |

単純注意演算実装とは、行列演算とソフトマックスを融合せず標準式のまま実行するベースラインである。10.7倍や15倍の倍率は、すでに高度に最適化された最新GPUカーネルに対する倍率ではない。LLaMA2-7Bのバッチ1では11.03から56.974 token/sへの改善で約5.16倍だが、バッチ16では約4.71倍である。モデルとバッチによって効果が変わる点を明示する必要がある。

### V100：比較カーネルとの比較と長文脈オフロード

| 項目 | 条件 | 原著の結果 |
|---|---|---|
| 比較カーネル比、因果マスクなし | V100、バッチ8、系列2K | 1.03倍 |
| 同 | 系列16K | 1.17倍 |
| 比較カーネル比、因果マスクあり | V100、系列最大16K | 最大1.43倍 |
| CPU/GPU協調と通常KVオフロード | PanGu-38B、8 V100、系列128K | CPU側注意演算 18.721ms、通常KV転送＋GPU演算27.698ms（原著表3） |
| 同 | 系列256K | CPU側注意演算 37.806ms、通常KV転送＋GPU演算54.92ms |
| FT全体 | PanGu-38B、8 V100 | 最大1.46倍高速化 |
| 最大入力長 | 同 | 通常構成16K、CPU/GPU協調付き256K |

128K入力の表3では、CPU側注意演算 18.66msと小さな結果転送0.061msを足して18.721msとなる。一方、通常オフロードのKVアップロード25.61msとGPU計算2.088msで27.698msとなる。256KではCPU側37.74ms＋0.066ms、通常オフロード50.81ms＋4.11msである。これらは一つのTransformer層の注意演算処理時間の比較であり、モデル全体の一トークン生成時間とは異なる。モデル全体のFT比較ではPanGu-38B最大1.46倍、PanGu-71B最大1.28倍と報告される。

## 負の結果・適用条件

短い系列のV100演算では比較カーネル比1.03倍にとどまり、演算を移植しただけで大きな改善が得られるわけではない。複数NPUの改善幅もモデルと入力長に依存し、PanGu-71Bでは2K入力7.4%改善という条件がある。原著は新しいAmpere/HopperのFlashAttention2/3をNPUやV100で直接実行できないため、同一GPU上で両者を比較することはしていない。従って現行の新しいNVIDIA GPU向け高速注意演算カーネルより本方式が優れるという結論は導けない。

CPU/GPU協調はGPUへ長いKVを戻す通信を減らすが、CPUで注意演算を計算する費用を払う。CPUのSIMD命令、メモリ帯域、CPU/GPU接続、層の配置が異なると効果が変わる。モデル重み、KV、語彙行列、中間バッファの容量を見積もって担当層数を決めるため、GPUメモリが十分な場合はCPU処理を行わない方がよい。256K入力は8基のV100を使う特定モデル・構成の上限であり、単一V100や別のモデルに一般化できない。

原著のDeepSpeed評価では8KでN/Aとなる条件があり、モデルの制約または実験中のシステムエラーが原因と記される。またPyTorchベースのDeepSpeedはFTより遅いと著者らが述べ、主な比較対象から外している。これは本方式のカーネル性能と、実行フレームワークの呼び出し・CUDA Graph・スケジューリングの差を区別すべきことを示す。

## 既存研究との差

高速注意演算はオンラインソフトマックスとブロック計算によって中間注意演算行列のI/Oを抑える。FA2は新しいGPUでの並列度を高める。本方式はその原理を異なる命令セットとメモリ階層へ移し、NPUでは二段階タイル分割・通信重畳、V100では行列積命令レイアウトを最適化する。さらにCPUで一部の注意演算を計算することで、KVの全量転送を回避する。このCPU/GPU協調は単なる高速注意演算の移植ではなく、KVをどこに置き、どこで注意演算を計算するかというオフロード方式の変更である。

## 限界と再現性

原著は2024年10月のarXiv v1であり、本文ではコードを今後公開予定と記載する。今回確認した一次資料から公式公開コードURLは確定できず、コードの独立再現は実施していない。評価はAscend 910BとVolta V100を対象とし、Ada世代や最新NPUへの速度優位を実測したものではない。さらに、モデルによってFTとPyTorchなど実行環境が異なるため、倍率を横断して比較すると誤解が生じる。

研究の実務的な示唆は、注意演算のアルゴリズムが同じでも、行列積命令、SRAM/一次キャッシュ、演算器間通信、全体集約通信、PCIe転送に合わせた実装で性能が大きく変わるという点である。低資源GPUの推論を考える場合、KVをGPUへ戻す方式とCPUで注意演算を計算する方式を、転送バイト数とCPU演算時間を含めて比較する必要がある。
