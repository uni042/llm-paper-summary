# Can Vision-Language Models Handle Long-Context Code? An Empirical Study on Visual Compression

## 概要

LongCodeOCRは、長大なプログラムの文脈を削除型のテキスト圧縮で短くする代わりに、コード全体を二次元画像へ描画し、視覚言語モデル（Vision-Language Model; VLM）で読ませる方式である。長いリポジトリの理解では、呼び出し側だけを残して定義側を削除するなど、断片的な情報選択によって依存関係が切れることがある。画像化は元の文脈を広く保持する一方、文字が小さくなり過ぎると演算子・識別子の読み間違いが生じる。論文はこの「文脈網羅性と記号忠実度の交換関係」を、コード要約、質問応答、ファイル内補完、リポジトリ横断補完の四つのベンチマークで検証する。

原著の主要結果は、平均圧縮率約1.7倍の長いモジュール要約で、LongCodeZipとQwen3-8Bの組合せがCompScore 50.40なのに対し、LongCodeOCRとQwen3-VL-8Bの組合せが87.25を記録したことである。コード補完では画像による広域情報保持が有利な条件もあるが、文字列の完全一致を要求する長いファイル内補完では性能が落ちる。100万トークンのコードを圧縮する前処理時間は、LongCodeZipの15,415.53秒に対して画像化は70.36秒であり、モデル推論を使わない圧縮工程の負荷が大幅に低い。

ただし、比較は単一モデルで入力表現だけを差し替えた完全な統制実験ではない。テキスト方式はQwen3-8B、画像方式はQwen3-VL-8BまたはGlyph 9Bを使用するため、入力表現とモデル能力の差が混在する。また70.36秒という値は画像化の前処理時間であり、VLMによる全体の推論完了時間ではない。

## 問題設定

大規模なコードベースには、APIの宣言、呼び出し箇所、設定、例外処理、型制約などがファイルをまたいで散在する。言語モデルへ全てのコードをそのまま渡すと文脈窓や注意計算の制約に直面する。既存の圧縮手法は関連度の高い関数やコード片を選んで残すが、ある定義が単独では低関連度に見えても、他の断片を理解するための必須条件である場合がある。こうした情報を削ると依存関係の閉包が破壊され、後段のモデルは失われた情報を回復できない。

原著Figure 1は、`SingleCellSelection`のコンストラクタ定義が圧縮時に削られ、呼び出し箇所だけを見たモデルが誤ったクラスを使う例を示す。関連度を推定するモデルが各断片の局所的な重要度を正しく評価していても、断片同士の組合せが必要な条件を見落とすことがある。この問題は、単純な入力長の削減率だけでは把握できない。

画像圧縮は、テキストを選別して捨てる代わりに、同じコードをより高密度の視覚表現へ移す。コードの構造や離れた定義を広く残せる一方、文字の判別精度が低下する危険がある。したがって、圧縮率が等しくても、要約のように大局的な構造理解が重要な課題と、完全一致が必要なコード補完では結果が異なるはずだ、という仮説を検証する。

## 手法

### 1. 入力のボトルネックをテキストから画像へ移す

LongCodeOCRは、(1) 長いコード文脈の受け取り、(2) 二次元画像列への描画、(3) 視覚言語モデルによる命令条件付きの回答生成、という三段階から成る。最初にコードベースや関連ファイルのテキストを集める。次にコードを複数ページの画像へ配置する。最後に、ユーザーの自然言語命令と画像をVLMへ入力し、要約、選択式回答、コード補完を生成する。圧縮の中心は、文字をトークン列として大量に持つ代わりに画像パッチへ集約することである。

この方式はソースコードの意味解析を行って不要な関数を削るものではない。テキスト圧縮では重要度の低い断片を破棄するため、いったん失われた定義を後段で参照できない。画像方式ではコードを広く残すので、空間的な位置やインデント、ブロック境界、関数間の距離といった情報も入力に残る。ただし画像の文字が読めなければ、存在していても使える情報にならない。広い網羅性と個々の文字の忠実度を同時に無限に高められるわけではない。

### 2. 視覚トークン予算と圧縮率の定義

元のコードのテキストトークン数を `|C_context|`、画像列を `v_1,...,v_n` とする。論文はVLMの画像パッチとプーリングを用いて、各画像の推定視覚トークン数を `τ(v_i)` と定義する。Qwen3-VL-8Bでは画像面積を `16×16×4` で割り、Glyphでは `14×14×4` で割った値を用いる。画像全体のトークン数は `|C_visual|=Σ_i τ(v_i)`、視覚圧縮率は `|C_context|/|C_visual|` となる。

テキスト圧縮では `|C_context|/|C_compressed|` を使う。ここで視覚トークン数は論文が採用した**推定式**であり、モデル内部のリサイズや全ての実行時のメモリ使用量を厳密に実測したものではない。異なるモデルの視覚トークンとテキストトークンの処理費用が完全に等しいとも限らないため、圧縮率が等しいだけで計算費用が同等と断定してはいけない。

### 3. テキスト圧縮の比較対象

主要な比較対象のLongCodeZipは、関数単位の候補を近似相互情報量（Approximate Mutual Information; AMI）で順位付けし、さらに細かい単位を0–1ナップサック最適化で選別する二段階方式である。これは関連度の高いコード片を残すには有効だが、候補を評価するためのモデル前向き計算が大量に必要になる。原著Table 1では、100万トークンで粗い選択が254.85秒、細かい選択が15,154.77秒、合計15,415.53秒を要する。細かい選択が支配的なため、圧縮前処理そのものが実運用のボトルネックになる。

LongCodeOCRは、重要度推定のために言語モデルを何度も呼ぶ工程を持たず、コードを画像化する。原著では100万トークンの圧縮が70.36秒で完了し、圧縮工程のLLM消費トークンは0と報告される。ここで0は圧縮工程のLLM呼び出し数に対応する値で、後段のVLM推論が0トークン・0費用で済むという意味ではない。

### 4. 情報漏洩防止と推論条件の統一

比較では長いコード文脈だけを画像へ変換し、タスク指示、質問、選択肢などの非コード情報はテキストのまま与える。ファイル内補完のLong Code Completionでは、補完対象の関数が入力末尾にあるため、画像化すると正解を露出させる危険がある。著者は補完対象関数を分離し、それ以前のコードだけを描画することで情報漏洩を避ける。各ベンチマークの圧縮率は固定し、推論の明示的な思考モードを有効化して、思考トークン上限を2,048とする。最終回答だけを評価し、中間の思考内容は採点しない。

## 評価

### 実験課題とモデル

原著は4つのコード理解課題を使う。Long Module Summarizationは長いモジュールの意味をまとめる139件（入力2,000トークン超）、LongCodeQAは98リポジトリ由来の443件の4択質問、Long Code Completionは5,000トークン超のPython補完500件、RepoBench-Pは外部ファイルの情報が必要なリポジトリ横断補完である。LongCodeQAには32K～1Mトークンの長さ別評価が含まれる。

| 課題 | データセット | 主な評価指標 | 目標平均圧縮率 |
|---|---|---|---:|
| 大局的な要約 | Long Module Summarization | CompScore | 約1.7倍 |
| コード質問応答 | LongCodeQA | 正答率 | 約1.6倍 |
| ファイル内コード補完 | Long Code Completion | 編集類似度（ES）・完全一致（EM） | 約2.0倍 |
| ファイル横断補完 | RepoBench-P | 編集類似度（ES） | 約2.0倍 |

テキスト入力側の主な基盤はQwen3-8Bで、視覚入力側はQwen3-VL-8Bと視覚圧縮向けに設計されたGlyph 9Bである。モデル系列とパラメータ規模を近づけてはいるが、画像処理能力や事前学習は同一ではない。したがって、観測された性能差には入力表現の違いだけでなく、VLMが視覚テキストの理解を学習している効果も含まれる。

### 長いモジュール要約：Table 3とTable 4

CompScoreはGPT-4o-miniを判定器にして、生成した要約と参照要約のどちらを好むかを順序を入れ替えて比較する0～100の尺度である。50は同等選好を意味し、数値が高いほど参照要約より選好されやすい。数学的な正答率や人手で検証した事実一致率ではない。

| 手法・基盤モデル | 平均圧縮率 | CompScore |
|---|---:|---:|
| 無圧縮・Qwen3-8B | 1.0倍 | 47.55 |
| ランダム行削除・Qwen3-8B | 1.7倍 | 52.07 |
| LongLLMLingua・Qwen3-8B | 1.7倍 | 45.76 |
| LLMLingua-2・Qwen3-8B | 1.7倍 | 58.18 |
| LongCodeZip・Qwen3-8B | 1.7倍 | 50.40 |
| LongCodeOCR・Qwen3-VL-8B | 1.7倍 | 87.25 |

同じ約1.7倍の圧縮率で、LongCodeOCRはLongCodeZipより36.85ポイント、LLMLingua-2より29.07ポイント高い。入力長を分けたTable 4でも、16K超の長い要約課題でLongCodeZipのCompScoreは40.06、LongCodeOCRは80.76であり、長い入力で差が広がる。Glyphの平均CompScoreは72.74で、画像方式でもVLMの種類によって性能が異なる。圧縮率の同等性は確認できるが、同一モデルでテキストと画像だけを交換した厳密な因果実験ではない。

### リポジトリ横断・ファイル内補完：Table 5とTable 6

RepoBench-Pの編集類似度は、約2.0倍圧縮でLongCodeZipが39.48、LongCodeOCRとQwen3-VL-8Bが50.22、Glyphが60.68である。外部ファイルの定義や呼び出し関係が重要なため、関連断片を削除しない視覚方式が有利になりやすい。一方、ファイル内補完のLCCでは、LongCodeZipの平均ES/EMが36.93/10.60、LongCodeOCRが42.21/12.00、Glyphが45.90/13.60となるが、最長区間では異なる傾向が見える。

特にLCCの16K超の区間で、Qwen3-VL-8Bの完全一致率は**2.08%**へ低下する。LongCodeZipの同区間は8.33%、Glyphは14.58%である。画像にコード全体が含まれていても、密な描画で記号を正確に復元できなければ、完全一致が必要な課題では不利になる。平均の編集類似度が高いことと、厳密なコード補完が成功することを混同してはならない。

### コード質問応答と100万トークン：Table 7・Table 8

LongCodeQAの標準的な32K～128K区間では、平均正答率がLongCodeZip 67.61%、LongCodeOCR 70.46%、Glyph 64.42%である。Glyphが必ず最高になるわけではなく、一般VLMのQwen3-VL-8Bが最も良い。超長文脈の512KではLongCodeZip 74.47%に対してLongCodeOCR 65.96%、Glyph 59.57%とテキスト方式が優位だが、100万トークンでは順位が逆転する。

| 100万トークンの方式 | 正答率 | 圧縮率 |
|---|---:|---:|
| LongCodeZip + Qwen3-8B | 64.00% | 3.0倍 |
| LongCodeOCR + Qwen3-VL-8B | 72.00% | 8.1倍 |
| LongCodeOCR + Glyph 9B | 70.00% | 12.2倍 |

100万トークンでは視覚方式が、より強い圧縮率で高い正答率を維持している。ただし各モデルの文脈制限に合わせて圧縮率が異なり、**同一圧縮率での公平な比較ではない**。50件という標本数も限定的であり、8ポイント差がすべてのリポジトリで再現する保証はない。原著Table 9の商用モデルとの比較も参考値であり、モデルの能力・入力制約・実装条件が完全に揃っているわけではない。

### 前処理の費用：Table 1

| 元のコード長 | LongCodeZip合計前処理 | LongCodeOCR画像化 | 前処理の倍率差 |
|---|---:|---:|---:|
| 8K | 26.97秒 | 0.84秒 | 約32.1倍 |
| 32K | 171.06秒 | 2.79秒 | 約61.3倍 |
| 128K | 2815.52秒 | 9.35秒 | 約301.1倍 |

この差は、LongCodeZipが多くの候補断片をモデル推論で採点するのに対し、画像化はLLM推論を呼ばずに前処理できるためである。100万トークンのLongCodeZipは約4.28時間、LongCodeOCRは約1.17分となる。ただし表は**圧縮工程の時間**であり、画像をVLMへ入力して最終回答が出るまでのエンドツーエンド遅延ではない。GPU上の視覚符号化や復号時間、モデルのメモリ占有量を含めた配信費用の比較は別途必要である。

### 圧縮率・描画条件の感度：Table 10・Table 11

RepoBench-Pの4K～8K区間でLongCodeOCRのESは、圧縮率1倍から5倍まで49.56、47.98、48.48、51.64、50.70と大きく崩れない。一方LCCでは同じ順に42.83、39.35、38.95、35.52、35.34へ低下する。大局的な依存関係を使う課題と、文字の厳密さを要する課題で、圧縮を強くしたときの劣化が異なる。

描画設定も無視できない。RepoBench-PではVerdanaとJetBrains MonoのESが51.63と50.98で近いが、LCCではJetBrains MonoのES/EMが41.75/12.78、Verdanaは39.35/11.11である。等幅フォントの方が細かい記号の復元に有利な可能性がある。2列レイアウトはRepoBench-PのESを51.63から49.19へ下げ、LCCのEMを11.11から10.00へ下げる。単純に詰め込めばよいのではなく、レイアウトの読みやすさが精度に直結する。

## 主要結果

長いコードの圧縮では、何を削るかだけでなく、**どの情報を入力内に残すか**が重要である。LongCodeOCRはコード全体を画像へ写すことで広域の依存関係を保持し、長いモジュール要約ではCompScoreを50.40から87.25へ改善した。100万トークンの質問応答ではLongCodeZipの64.00%に対して視覚方式が72.00%を記録し、圧縮率も3.0倍対8.1倍と高い。ただし512Kでは逆にLongCodeZipが優位であり、全ての長さ・課題で視覚方式が勝つわけではない。

圧縮工程の時間は100万トークンで15,415.53秒から70.36秒へ大幅に短縮する。一方、厳密なコード補完では文字の読取り誤差が律速となり、LCCの16K超でQwen3-VL-8Bの完全一致率が2.08%まで下がる。網羅性を重視する要約や横断的な質問応答と、記号精度を重視する補完では、適切な圧縮方式が異なる。

## 既存研究との差

LongCodeZipやLLMLingua系は、入力テキストから重要度の低い部分を削除して長さを減らす。これに対しLongCodeOCRは、コードの内容を残したまま入力表現を画像へ変換する。圧縮のためのLLM推論を省略できる点と、削除による依存関係の断絶を避けられる点が主な差である。ただし視覚トークンは無償ではなく、モデルの視覚符号化能力と画像解像度に依存する。

DeepSeek-OCRやGlyphなどの光学的文脈圧縮研究とは、コードという厳密な記号列への適用境界を、要約・質問応答・補完という異なる課題で評価した点が異なる。特に、全体像の保持に有利でも、演算子や識別子の再現性が必要な場面では画像化が危険になり得るという負の結果を含む。推論カーネル自体の計算量を減らす方式ではなく、入力表現と圧縮前処理を変える方式である。

## 限界

第一に、画像方式とテキスト方式で使用する基盤モデルが異なる。Qwen3-8BとQwen3-VL-8Bは同系列でも同一の重み・学習データではなく、観測された差を画像化の効果だけに帰属できない。第二に、圧縮率はモデル別のパッチ数から推定しており、画像のリサイズや実際の推論費用の全要素を含む測定ではない。第三に、CompScoreは第三者モデルの選好評価であり、厳密な機能正しさや人手検証と同じではない。

第四に、画像を高密度化すると文字の判読性が落ち、コード補完の完全一致率が悪化する。第五に、100万トークンの評価は50件であり、圧縮率も手法間で異なるため、一般的な精度優位を断定しにくい。第六に、Table 1の大幅な速度差は圧縮前処理だけであり、VLMの視覚符号化・復号を含む総応答時間や消費電力を測った結果ではない。最後に、実運用のIDEや多言語リポジトリで、構文の微妙な差を確実に復元できるかは追加検証が必要である。
