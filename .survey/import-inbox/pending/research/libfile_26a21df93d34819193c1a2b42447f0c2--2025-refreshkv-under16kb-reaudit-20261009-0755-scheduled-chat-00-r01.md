# RefreshKV：長文生成の途中で小さなKVキャッシュを更新する推論方式

## 概要

長い入力を読んで長い出力を生成するとき、生成の初期に重要だった入力位置が後半でも重要とは限らない。従来のKVキャッシュ削除方式は、プリフィル直後や過去の注意得点から残すトークンを選び、それ以外の鍵値を捨てる。短い回答ではこの選択が有効でも、文書を表へ変換する、複数段階の情報をたどる、長い要約を出すといった処理では、削除済みの位置が後から必要になる。その位置を復元できないため、長文生成が進むほど品質が悪化する。

RefreshKVは、**完全なKVキャッシュ `C_f` を消さずに保持**し、通常の生成では少数の入力位置からなる**部分キャッシュ `C_p`**だけを参照する。現在のクエリが直近の完全注意時と大きく異なる場合、完全なKVへ一度注意し、得られた注意得点から部分キャッシュを再構築する。これにより、普段は小さい集合への注意で計算と読出しを抑えつつ、後から重要になった位置へ戻れる。

原著の16K入力・Llama-3.1-8Bでは、Arxivデータの困惑度（PPL）がSnapKVの2.54に対してRefreshKV（クエリ確認間隔10）で2.32、デコード時間は6.77に対して6.33となった。HTMLからTSV表への変換ではH2OとSnapKVがF1=0となる条件で、RefreshKV（間隔5）がF1=17を得た。ただし**GPUメモリに保持するKV容量そのものは減らない**。この方式は容量削減ではなく、注意を実行する対象とその読出し頻度を削減する方式である。

## 問題設定と既存方式が失敗する理由

入力長を `L`、生成長を `N` とすると、通常の自己注意は各生成ステップで過去の多数の鍵値を読み出す。KVの記憶量は履歴トークン数に比例し、デコード時間にもHBMからのデータ移動が影響する。従来のStreamingLLMは初期の注意受け皿となるトークンと直近の窓を保持し、H2Oは累積注意の大きいトークンを優先し、SnapKVはプリフィル末尾付近の注意分布から重要位置を選ぶ。いずれも参照対象を減らすが、不要と判断して消した入力位置を後から戻すことはできない。

例えばHTML表の変換では、先に処理した列の情報と後で出力する行の情報が入力の異なる位置にある。最初の出力に関係する位置だけを保持すると、後半の行に必要な入力が残っていない可能性がある。原著の新規課題「鍵連鎖（Chain-of-key）」は、前に出力した鍵の末尾語から次の鍵を探すため、どの入力位置が必要かを生成開始前に決められない構造になっている。削除方式の弱点を、単純な一箇所検索ではなく段階的な情報参照として可視化する評価である。

RefreshKVは、完全注意を毎回行うのではなく、**重要位置の集合が変化したと推定されるときだけ再選択**する。全注意の費用と、部分注意の品質低下の間に交換条件があるため、いつ再選択するかが中心課題になる。

## 手法

### 1. プリフィルと二つのKVキャッシュ

最初に入力トークン `x_1,…,x_L` を通常の完全注意で処理し、全入力位置の鍵値を `C_f` に保存する。同時に、入力の最後のトークンがどの入力位置を参照したかという注意得点を利用し、上位 `K` 位置の鍵値を `C_p` に入れる。原著は近傍トークンの注意得点を最大値集約して位置を選び、局所的に重要な情報を見落としにくくしている。

グループ化クエリ注意（GQA）では、複数のクエリ頭が一つの鍵値頭を共有する。そこで同一グループ内のクエリ頭の注意得点を最大値で集約し、部分キャッシュに残す位置を決める。付録の比較では平均値集約や単一頭だけを使う選択より最大値集約が良い条件を報告している。この設計は、個別頭でだけ重要な位置が平均化によって埋もれることを避ける。

### 2. 通常ステップの部分注意

大半の生成ステップでは、`C_p` と生成済みの局所トークンを使って次のトークンを生成する。長い入力全体を毎回読まないため、注意の演算量とHBMからの鍵値転送量を削減できる。生成した新トークンの鍵値も部分キャッシュへ追加するが、部分キャッシュを無制限に大きくしないため、直近の完全注意で重要度が最も低かった位置を追い出す。

この処理だけを永続的に続ければ、初期に選んだ入力位置へ固定される点でSnapKVと同じ問題が残る。RefreshKVが異なるのは、後述の完全注意ステップで**元の入力を再び参照し、部分キャッシュの内容そのものを更新できる**ことである。

### 3. クエリ類似度による完全注意の起動

単純な固定間隔の更新では、話題や出力内容が変わらないときにも高価な完全注意を実行し、逆に急な参照先変更へ十分に追随できない。RefreshKVは、クエリ確認間隔 `S` ごとに、現在のクエリと直近の完全注意時のクエリのコサイン類似度を層ごとに計算する。原著ではクエリ頭の平均ベクトルを比較し、類似度が閾値 `s` より低い層で完全注意を選ぶ。

この判断は**各層ごと**に行われ、全層を同時に更新する固定周期とは異なる。類似度が高ければ過去の注意対象がまだ有効とみなし、部分キャッシュを使い続ける。低ければ参照すべき入力位置が変化した可能性があるため、完全注意を実行する。類似度の計算自体にも費用がかかるので毎トークンではなく `S` ステップごとに確認する。主実験では `S=5` または `10`、閾値はLlama-3.1-8Bで0.85、Qwen2-7Bで0.95である。

### 4. 完全注意と部分キャッシュの再構築

完全注意を行う前に、それまで部分注意で生成したトークンの鍵値を `C_f` に反映する。その後、完全キャッシュ全体へ注意して次のトークンを生成し、その注意得点から上位 `K` の入力位置を選び直して `C_p` を更新する。これにより、プリフィル時には重要でなかった入力位置も再び候補に入る。

この更新は単に「たまに完全注意で高品質なトークンを一つ生成する」ためではない。原著の構成要素除去実験では、完全注意ステップの出力を使わない変種でも、部分キャッシュの更新を維持すれば主要な品質が保たれた。一方、更新自体を取り除くと品質が大きく低下した。改善の中心は**生成中に重要位置を選び直すこと**である。

### 5. 計算量とメモリ容量を分けた理解

部分注意ステップでは参照する入力位置数を `L` から `K` 程度へ減らせるが、完全キャッシュ `C_f` は保持し続ける。したがって必要なKV記憶量は通常の完全注意と同程度であり、メモリ不足を直接解決する方式ではない。完全注意の頻度が増えるほど計算・読出し節約は小さくなり、頻度が低すぎれば参照先の変化に追随できず品質が落ちる。

長文入力の一部だけへ普段注意し、必要なときだけ全体へ戻るという構造は、KVを永久削除する方式とは資源上の前提が異なる。装置のHBM容量に十分な余裕があり、デコード中の注意計算やKV転送が律速になる条件で利点を期待できる。

## 評価条件

原著はモデル、文脈長、出力長、評価指標、比較方式を分けて報告している。主な実験は単一A100 80GB GPU、FlashAttention、貪欲復号で行われ、入力処理後の**デコード段階の実時間**を測る。完全な要求待ち時間や複数利用者のサービング処理量を測ったものではない。

| 項目 | 原著の設定 |
|---|---|
| 主なモデル | Llama-3.1-8B、Qwen2-7B。鍵連鎖では70B／72Bも使用 |
| GPU | 単一A100 80GB、FlashAttention |
| 言語モデル評価 | RedPajamaのArxiv／Book、16K入力、各100系列、末尾256トークンの困惑度 |
| 長入力・短出力 | RULER、32K入力、13種類の課題 |
| 長入力・長出力 | QMSum、GovReport、NovelSumm、HTML→TSV、鍵連鎖 |
| 部分KVの大きさ | 原則入力長の1/8、16KではK=2048。NovelSummではK=4096 |
| 比較対象 | 完全注意、StreamingLLM、H2O、SnapKV |

## 評価結果と解釈

### 1. 16K文脈の困惑度と時間

困惑度は正解トークンへの予測確率から計算され、低いほど予測品質が良い。原著表1の数値は次の通りである。

| モデル・方式 | Arxiv困惑度 | Book困惑度 | デコード時間 |
|---|---:|---:|---:|
| Llama-3.1-8B・完全注意 | 2.22 | 7.07 | 7.50 |
| Llama-3.1-8B・SnapKV | 2.54 | 7.78 | 6.77 |
| Llama-3.1-8B・RefreshKV（QC=5） | 2.27 | 7.31 | 6.67 |
| Llama-3.1-8B・RefreshKV（QC=10） | 2.32 | 7.41 | 6.33 |
| Qwen2-7B・完全注意 | 2.33 | 8.26 | 9.07 |
| Qwen2-7B・SnapKV | 2.80 | 9.18 | 6.09 |
| Qwen2-7B・RefreshKV（QC=5） | 2.39 | 8.55 | 6.71 |
| Qwen2-7B・RefreshKV（QC=10） | 2.49 | 8.72 | 6.33 |

LlamaではQC=10がSnapKVより**困惑度も時間も改善**する。一方QwenではRefreshKVの困惑度はSnapKVより良いが、デコード時間はSnapKVの6.09より遅い。この負の条件を省略して「全モデルで品質と速度を同時改善」とは言えない。QC=5は完全注意を増やして品質を改善する代わりに、QC=10より時間が増える傾向がある。

### 2. 長文生成での失敗回避

原著表2は、長い出力で重要位置が変化する課題を評価している。HTML→TSVでは、Llama-3.1-8Bの完全注意F1=33に対し、H2OとSnapKVは0、RefreshKV（QC=5）は17である。Qwen2-7Bでは完全注意24、H2OとSnapKVは0、RefreshKVは10である。完全注意との差は残るが、入力位置を再選択することで永久削除方式の破綻を部分的に回復する。

鍵連鎖では小型モデルが完全注意でも課題を解けないため、Llama-3.1-70BとQwen2-72Bで評価した。完全注意の有効連鎖長比は56／83、SnapKVは12／13、RefreshKV（QC=5）は25／24である。RefreshKVも完全注意には及ばないが、削除方式が2段階以上の連鎖をほとんど作れない条件で、参照先を更新できることを示す。

要約課題でも傾向は一様ではない。GovReportではLlama-3.1-8Bの完全注意ROUGE-L=34.11、SnapKV=28.06、RefreshKV（QC=5）=32.56で改善する。NovelSummのQwen2-7BではStreamingLLMが22.11、完全注意19.91、RefreshKV19.70となり、RefreshKVがすべての比較対象に勝つわけではない。

### 3. 動的更新と固定更新の比較

原著表3では、同程度の時間で更新のタイミングを変えた場合を比較する。Llama-3.1-8BのHTML→TSV（0.5K出力）では、固定間隔10がF1=17、時間1.40であるのに対し、動的QC=5はF1=30、時間1.40である。平均的な更新間隔は動的方式の方が長い14であり、必要な局面へ更新を集中させた効果を示す。

同じモデルのGovReportでは、固定間隔10のROUGE-L=32.30、動的QC=5は32.56で、時間は1.37対1.38と近い。すべての条件で大幅な差があるわけではないが、更新の必要性をクエリ変化から判断する設計は、単純な一定周期より費用と品質の配分を改善し得る。

### 4. 構成要素除去と継続事前学習

原著は、部分キャッシュを更新しない変種ではLlama-3.1-8BのArxiv困惑度が2.50となり、更新ありの2.32から悪化すると報告する。HTML→TSVでも更新なしはF1=0となる。一方、完全注意の出力を直接使わない変種でも主要指標を保てる。これは完全注意を一時的に行うこと自体より、**その注意得点を使って次の部分キャッシュを作り直すこと**が効いている証拠である。

さらに著者は、Llama-3.1-8Bを部分注意に近い条件で継続事前学習し、困惑度を改善する追加実験を行う。ただし、この学習時の設定は完全な動的RefreshKVそのものではなく、固定間隔の部分注意を模した簡略化である。既存モデルに学習なしで適用した結果と、追加学習後の結果を混同しない。

## 既存方式との相違

SnapKVやH2Oは、少ないKVだけを残すことで容量と計算の両方を減らすが、消した情報は戻せない。RefreshKVは**完全KVを保持したまま活動中の参照集合を小さくする**ため、容量面では不利だが、長い生成で参照先が変わる課題には強い。通常の完全注意は品質面の上限に近いが、毎回すべてのKVを読む費用がかかる。RefreshKVは両者の中間に位置する。

この違いは「KV圧縮」という語だけでは表せない。物理的に保持するKV容量、各ステップで注意するKV数、完全注意を実行する頻度を別々に評価する必要がある。RefreshKVが削減するのは主として後二者である。

## 限界と導入時の注意

第一に、完全キャッシュを保持するため、GPUのメモリ容量不足を直接解消できない。128K級の文脈や複数要求を同時処理する環境では、保持する全KVがHBM容量を圧迫し得る。CPUへのオフロードや別の容量削減方式と組み合わせる場合の転送費用は、この論文の主要評価範囲外である。

第二に、類似度閾値と確認間隔が性能を左右する。類似度が低くなるたびに全注意を行えば品質は改善し得るが、読み出し費用が増える。逆に更新を減らしすぎると、削除方式と同様に重要位置の変化へ追随できない。閾値はBookの保持データで調整しており、全言語・全モデル・全用途に最適な値を示したわけではない。

第三に、評価は主として単一A100上のデコード時間であり、GPUを複数台使う推論、要求待ち行列、異なる注意カーネル、キャッシュの配置変更、電力消費、連続バッチ処理などは網羅しない。QwenではSnapKVより遅い条件があり、長文要約でもすべての方式を上回るわけではない。品質と速度の交換条件を、実際のモデル・入力長・出力長で確認する必要がある。

第四に、鍵連鎖の改善は70B／72Bモデルの結果であり、8B／7Bモデルの通常評価と同じ設定ではない。異なるモデル規模の数値を同一の表で比較して、キャッシュ方式だけの効果と誤認しない。継続事前学習による改善も、推論時のみの方式の性能と分けて扱うべきである。
