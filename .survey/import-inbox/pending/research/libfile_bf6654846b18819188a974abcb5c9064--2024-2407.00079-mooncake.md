# Mooncake: A KVCache-centric Disaggregated Architecture for LLM Serving

## 概要
Mooncakeは、長文脈要求で支配的になるプリフィル計算とKVキャッシュ移動を、デコード処理から分離して扱う。Kimiの要求では入力が長く出力が比較的短いため、プリフィルは計算律速、デコードはメモリ律速になりやすい。両者を同じGPU群・同じ並列方式で処理すると、初回token待ち時間（TTFT）とtoken間待ち時間（TBT）の双方を守りながらGPU利用率を上げにくい。

Mooncakeはプリフィルpool、デコードpool、CPU DRAM/SSDを使う分散KVキャッシュ、GPUDirect RDMAベースのMessenger、全体を決めるConductorから構成される。Conductorは要求ごとに再利用できるprefix KV、各プリフィルinstanceのqueue、デコード側のbatch余力を観測し、KV再利用量だけでなくSLO違反を避けるよう配置する。公開traceは23,608要求、平均入力7,590 token、平均出力182 tokenで、prefix blockのhashも含む。

## 問題設定
プリフィルでは入力tokenを並列処理できる一方、attention計算量は文脈長とともに急増する。デコードでは1反復に各要求1 tokenずつ進むため、重みとKVキャッシュの読み出しが律速になりやすい。したがってプリフィルへ適した大きな計算並列度と、デコードへ適した連続バッチ処理は一致しない。

prefix KVを再利用すればプリフィル計算を削減できるが、遠隔DRAMからKVを取る時間がTTFTを悪化させる場合がある。逆にデコードbatchを大きくするとGPU利用率は上がるがTBTが悪化する。さらに実サービスではGPU不足により全要求を処理できないため、最終的に失敗する要求へプリフィル資源を費やすこと自体が損失になる。

## 手法
### 分散KVキャッシュとConductor
CPUメモリ上のKVはpaged blockとして保持し、prefixを含むhashで重複を識別する。MessengerがCPU/GPU・ノード間のKVをRDMAで移動する。Conductorは要求のprefix hashから最良一致候補を探し、queue待ちと残りプリフィル計算を見積もって、TTFT制約内でKV再利用と負荷分散を両立する。

hot blockは複数nodeへ複製し、cold blockは下位tierへ退避できる。単に「最もcache hitが多いnode」を選ばない点が重要で、remote KV転送の混雑やqueue増大でSLOを破る場合は再利用率を犠牲にして別instanceを選ぶ。

### チャンク化パイプライン並列
長文脈プリフィルを複数nodeへ広げる際、tensor parallelismをnode間へ延ばすと各層のcollective通信が重い。Mooncakeは入力を`prefill_chunk`以下へ分割し、異なるchunkをpipeline stageへ流すチャンク化パイプライン並列（CPP）を使う。cross-node通信をstage境界へ限定し、計算と重ねることで長文脈のTTFTを短縮する。

### 層単位プリフィルとKV転送
プリフィルは層ごとに進むため、各層のattention前に必要KVの非同期loadを待ち、計算後すぐその層の新KVを非同期storeする。次層の計算と転送を重ね、全層終了後に残りstoreだけを待つ。これによりプリフィルGPUが全requestのKVを長時間VRAMへ抱える必要を減らす。

### 過負荷時の早期拒否
プリフィル完了後にデコードslotが無ければ、それまでの計算が全損になる。Mooncakeは短期負荷と生成長を予測し、完走できない可能性が高い要求を早い段階で拒否する。単純な閾値拒否は負荷振動を起こすため、将来負荷を見積もる方式を採る。

## 評価条件
| 項目 | 条件 |
|---|---|
| workload | Kimi由来の匿名化・再生trace、公開sampleは23,608要求 |
| model | LLaMA2-70Bと同じ構造のdummy model |
| 主指標 | TTFT、TBT、SLOを満たして完了した要求の実効throughput |
| cache trace | 512-token blockのprefix hash |
| SLO例 | end-to-end評価でTTFT P90=10×、TBT P90=5× |
| 比較 | public dataset、simulated workload、real workload replay |

## 主要結果
| 条件 | 指標 | 結果 | 意味 |
|---|---|---|---|
| 特定simulated long-context | SLO内throughput | baseline比最大525%増 | KV再利用と分離配置が長文脈で効く |
| real workload | 処理可能要求数 | 75%増 | 実負荷traceでも容量向上 |
| 公開trace cache分析 | cache hit | 1,000→50,000 blocksで約30%→50% | prefix再利用には一定容量が有効 |
| block popularity | 再利用偏り | 50%以上のblockは未使用、一部は数万回参照 | hot block複製が転送集中を緩和 |

## 既存研究との差
プリフィル／デコード分離だけでなく、KVキャッシュ自体をCPU・DRAM・SSD・networkを跨ぐ独立資源として扱い、配置決定の中心へ置く。さらに「全要求を必ず処理する」前提を外し、過負荷時の早期拒否までサービング最適化へ含める点が実サービス指向である。

## 限界
評価はprivacy保護のため実ユーザーtokenを使わず、LLaMA2-70B相当dummy modelへのtrace replayである。したがってKimi本番modelそのものの数値ではない。最大525%も特定simulation条件の値で、すべての負荷で得られる倍率ではない。予測型早期拒否は生成長・短期負荷の予測誤差に影響される。
