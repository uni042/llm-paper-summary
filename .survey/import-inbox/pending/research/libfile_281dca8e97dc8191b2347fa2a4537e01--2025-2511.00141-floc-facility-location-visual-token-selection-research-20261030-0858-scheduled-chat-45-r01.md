# FLoC：長時間動画の視覚トークンを代表性と多様性で選ぶ学習不要の圧縮

## 概要

FLoCは、長い動画から得られる大量の視覚トークンを、限られた予算の中で代表性と多様性を保つように選択する手法である。動画をフレームごとに画像エンコーダへ通すと、長い時間にわたり同じ背景や物体を何度も表すトークンが発生する。すべてを視覚言語モデルへ入力すると、注意計算と鍵・値キャッシュの費用が大きくなる。一方、単純に間引くと、短時間だけ映る小さな物体や行動を失い、質問へ答えられなくなる。

著者らは施設配置問題で使われる被覆目的を採用する。選んだトークン集合が元の全トークンをどれだけよく代表するかを、各元トークンから最も似た選択トークンへの類似度の和で測る。似た背景を何度も選ぶより、未被覆の画像領域や異なる場面を代表するトークンを選ぶ方が得点が増える。最適な集合を厳密に探すのは難しいが、目的関数の劣モジュラ性を利用する遅延貪欲法で候補の再評価を減らす。

この方法は追加のニューラルネットワークを訓練せず、質問文にも依存しない。動画の視覚トークンを一度圧縮し、その後で異なる質問に再利用できる。Qwen2.5-VL-7Bで元の視覚トークンの1/8を保持したとき、四つの動画評価の平均は62.57であり、全トークン保持の64.64から低下するが、LongVUの60.91など多くの比較法を上回る。1/32保持では57.45へ低下し、圧縮を強めれば品質損失が増える。実際のGPU計測ではクラスタリングより圧縮処理が速いが、視覚モデル全体の応答時間が同じ倍率で改善するわけではない。

## 問題設定

長時間動画では、同じ部屋、人物、背景が多数のフレームに現れる。均一な時間間隔でフレームを抽出すると、変化の少ない区間へ予算を使い、短時間の重要な出来事を取り逃がす可能性がある。トークンを密度の高いクラスタの中心から選ぶ方法も、多数の似た背景をよく代表する一方、まれな物体を選びにくい。逆に外れ値の多様性だけを重視すると、動画の大部分を説明する典型的なトークンが不足する。

FLoCは、選択した集合が全トークンを広く覆うという目的を直接最適化する。選択後のトークンは通常の視覚エンコーダ出力であり、特別な潜在表現へ変換しない。既存の動画視覚言語モデルの入力にそのまま連結できる。モデルの重みや注意機構を改造しないため、複数のバックボーンへ移しやすい。ただし、質問を見てから重要度を決めるわけではないため、後から問われる非常に小さな対象が必ず残るという保証はない。

著者らが最適化するのは、画像の意味を完全に保存することではなく、選択集合が元トークン集合を類似度で覆うことだ。動画理解の正答率と被覆目的は関係するが同一ではない。理論上の近似保証を下流の質問応答精度の保証と混同しないことが重要である。

## 手法

### 1. 施設配置型の被覆目的

元の動画から得た視覚トークンの集合をV、残す集合をS、保持数の上限をKとする。各元トークンvについて、選択済みのトークンuの中で最も似たものの類似度を求め、それを全てのvについて合計する。類似度には正規化した特徴ベクトルのコサイン類似度を使う。選択集合に新しい代表点を追加すると、まだ十分に覆われていない元トークンの得点が増える。既に似た代表点がある場所へさらに選ぶ効果は小さくなる。

この性質は限界利得逓減、すなわち劣モジュラ性として知られる。すでに多くの代表点を選んだ集合へ追加する場合、少数しか選んでいない集合へ追加する場合より、同じ候補の追加利得は大きくならない。目的が単調な劣モジュラ関数である条件では、通常の貪欲選択が最適値の少なくとも約63.2%を達成するという古典的な近似保証がある。ただしこれは被覆目的の値に対する保証であり、動画の質問応答精度が63.2%以上になるという意味ではない。

### 2. 遅延貪欲法による候補選択

単純な貪欲法は、各段階で残る全候補を再評価するため、大量のトークンでは時間がかかる。FLoCは優先度付きキューに候補の限界利得の上界を保持し、最も有望な候補だけを取り出して現在の選択集合に対する利得を計算し直す。再計算した利得が他候補の上界を上回れば、その候補を採用できる。そうでなければ新しい上界でキューへ戻す。この仕組みで、多くの候補の不要な再評価を省く。

劣モジュラ性を使うため、古い限界利得が現在の利得の上界になることが重要である。実際の速度改善はデータの類似度構造と保持数に依存する。最悪の場合の計算量を常に小さくできるという保証ではなく、著者らが比較した動画トークン集合では候補の再評価が少なく済んだという実測結果である。

### 3. 時間ブロックへの分割

動画全体のトークンを一度に選ぶこともできるが、長時間動画では類似度の計算と候補管理が重くなる。FLoCは入力動画を一定の時間ブロックへ分け、各ブロックの中で予算に応じた代表トークンを選ぶ。選択結果を時系列に沿って連結し、ユーザーの質問文とともに視覚言語モデルへ渡す。これにより、非常に長い動画を小さな単位へ分割して処理できる。

ブロック長は手作業で決める重要な設定である。短いブロックでは計算が軽いが、同じ静止画面が複数ブロックに続くと、各ブロックで似たトークンを選んでしまう。長いブロックではより広い時間範囲の冗長性を減らせるが、候補数が増えて処理が重くなる。原著は動画の変化に応じてブロック長を自動調整する機構を完成させていない。場面切替の検出に合わせた可変ブロック長は今後の課題である。

### 4. モデルへの組込み

視覚エンコーダが出したトークンに対して選択を実施し、選ばれたトークンだけをテキストの質問と連結して動画言語モデルへ入力する。圧縮器を学習しないため、特定の質問への適合や追加学習データの偏りを避けられる。一方、動画の意味理解に関係する特徴が視覚エンコーダ内で十分に表現されていることを前提とする。特徴の類似度が実際の質問で必要な意味の違いを表していなければ、選択は最適な回答情報を保てない。

この方式は入力時の視覚トークン数を減らす。生成後にキャッシュを再構成するKVCapsuleなどとは異なり、選ばなかったトークンは言語モデルへ渡らない。従って圧縮率が高いほど入力処理の費用は減るが、削除した細部は後から復元できない。保存容量やKVの削減は、元の視覚トークン数に対する選択比率に依存する。

## 実験条件

| 項目 | 一次論文の設定 |
|---|---|
| 主なモデル | Qwen2.5-VL-7B、InternVL3-8B |
| 追加モデル | Qwen2-VL、LLaVA-Next-Video、Qwen2.5-VL-32B |
| 評価データ | Video-MME、MLVU、LongVideoBench、EgoSchema |
| 保持率 | 元の視覚トークンの1/8、1/16、1/32 |
| 比較方式 | LongVU、TS-LLaVA、DivPrune、DyCoke、PruneVID、STTM、Scissor、FastVIDなど |
| 処理速度比較 | K-means、K-medoids、スペクトルクラスタリング |
| 実行環境 | NVIDIA H100、lmms-eval、複数プロセスによる評価 |
| 長時間試験 | 1秒当たり1フレーム、最大7200フレーム、入力枠768フレームとの比較 |

主な評価は、元の全視覚トークンを使用したモデルを基準とし、同じ保持率へ圧縮した方式同士の正答率を比較する。平均点は四つの動画評価の単純平均であり、各評価の難しさや例数を調整した重み付き平均ではない。GPUの種類、動画長、視覚エンコーダのトークン数が変わると圧縮処理時間も変わるため、測定した秒数を一般的な処理時間とみなさない。

## 定量評価

### 保持率1/8の動画理解

| 方法 | Qwen2.5-VL-7Bの四評価平均 | InternVL3-8Bの四評価平均 |
|---|---:|---:|
| 全トークン保持 | 64.64 | 67.18 |
| LongVU | 60.91 | 64.69 |
| DivPrune | 60.94 | 64.01 |
| DyCoke | 61.09 | 64.28 |
| FastVID | 60.99 | 報告なし |
| FLoC | 62.57 | 65.65 |

FLoCはこの保持率で主要な比較法より高い平均を示すが、全トークン保持よりはQwen2.5-VLで2.07ポイント、InternVL3で1.53ポイント低い。したがって「ほぼ品質を保つ」と「完全に同じ品質である」は区別する。Qwen2.5-VLのVideo-MMEは全保持66.33に対しFLoC63.33、MLVUは70.31に対し68.81である。動画理解の難しい問題では、選択によって失われる情報が残る。

### 強い圧縮での損失

| 保持率 | Qwen2.5-VLのFLoC平均 | InternVL3のFLoC平均 |
|---|---:|---:|
| 1/8 | 62.57 | 65.65 |
| 1/16 | 60.09 | 63.79 |
| 1/32 | 57.45 | 61.44 |

保持率を1/8から1/32へ下げると、Qwen2.5-VLでは5.12ポイント、InternVL3では4.21ポイント悪化する。低い保持率でも多くの比較法を上回るが、元の動画情報を極端に減らすと精度が下がるという交換条件は残る。Qwen2.5-VLで1/32保持時のVideo-MMEは58.63、EgoSchemaは54.00であり、全保持の66.33、61.40から明確に低下している。

### 長時間動画へ入力を拡大した場合

1秒1フレームで最大7200フレームを扱う設定では、Qwen2.5-VL-7Bの三評価平均はFLoC67.03、DyCoke66.69、LongVU66.27、全保持の768フレーム条件65.82となった。Qwen2.5-VL-32BではFLoC70.63、DyCoke69.04、LongVU69.07、768フレームの全保持68.19である。この結果は、圧縮によってより長い動画の時間範囲を取り込めることが有利に働く例である。

ただし768フレームの全保持と7200フレームの圧縮は、同じ入力情報量を比較したものではない。圧縮アルゴリズム自体が元モデルより賢くしたと解釈せず、限られたトークン予算をより長い時間へ配分した効果を含む比較と見るべきである。より多くのフレームを読み込むことの利点と、トークン削除の損失を分けて評価する必要がある。

### 圧縮処理時間

| 方式・時間ブロック32 | 保持率1/32 | 保持率1/16 | 保持率1/8 |
|---|---:|---:|---:|
| K-means | 59.00秒 | 113.0秒 | 218.0秒 |
| K-medoids | 0.716秒 | 0.747秒 | 0.877秒 |
| スペクトルクラスタリング | 5.160秒 | 9.650秒 | 21.10秒 |
| FLoC | 0.413秒 | 0.475秒 | 0.527秒 |

この表は圧縮処理そのものの平均時間であり、視覚エンコーダや言語モデルの生成を含む端から端までの応答時間ではない。FLoCはクラスタリング方式より速いが、K-medoidsとの違いはK-meansほど大きくない。時間ブロックを長くするとFLoC自身の処理時間も増えるため、処理時間が入力長に無関係なわけではない。

### 追加分析と負の結果

施設配置の類似度をコサインとユークリッド距離で比較した実験では、保持率1/8のInternVL3の四評価平均はユークリッド66.20、コサイン65.65で、ユークリッドの方が0.55ポイント高かった。一方、1/16ではコサイン63.79、ユークリッド63.52、1/32ではコサイン61.44、ユークリッド60.47となり、高圧縮ではコサインが有利だった。著者らは複数の保持率にわたる安定性を重視してコサインを既定値とした。どの圧縮率でも常にコサインが最良と主張するのは誤りである。

定性的な例では、他の方式が落とした帽子やサングラスのような少数の特徴をFLoCが残し、質問に正しく答えられた例がある。ただしこれは代表例であり、全てのまれな物体を保証して選ぶわけではない。選択した特徴が視覚エンコーダの空間で他と似ている場合、質問上は重要な小さな違いが埋もれる可能性がある。

## 既存研究との差

均一フレーム抽出は時間方向の偏りを減らせるが、フレーム内の多数の似たパッチを削れない。K-meansは密なクラスタの中心をよく代表するが、まれな出来事を過小評価しやすい。DivPruneは多様性を重視するが、動画の大部分を説明する代表性を必ずしも保たない。FLoCは選択集合から全トークンへの最大類似度を合計するため、代表性と多様性の双方を目的関数に反映できる。

質問に依存する選択方式は、与えられた質問に重要なトークンへ予算を集中できるが、質問が変わると再圧縮が必要になる場合がある。FLoCは質問を見ずに一度だけ圧縮するため、同じ動画へ多数の質問を行う用途で再利用しやすい。ただし質問が既知なら質問依存方式の方が有利になる可能性はある。学習型の圧縮器と違い、追加訓練が不要であり、複数の動画言語モデルへ導入しやすい点も実用上の特徴である。

## 限界と今後の課題

最大の設計上の制約は、固定時間ブロック長を人手で選ぶ必要があることである。長いブロックでは広い時間範囲の重複を取り除けるが計算が増える。短いブロックでは処理が軽いが、同じ静止場面が複数ブロックへ分かれると、似たトークンが何度も選ばれる。動画の動きや場面転換に応じてブロック長を変える仕組みは未完成である。固定ブロックの性能を全ての動画へ一般化するのは適切でない。

第二に、施設配置の近似保証は被覆目的に関するもので、動画理解の正答率に対する保証ではない。極端な圧縮では元モデルより品質が下がる。質問に依存しない方式のため、動画中に一度しか映らない非常に小さな文字や物体を見落とす可能性がある。安全上重要な出来事の検出などでは、平均的な動画ベンチマークだけでなく、まれな事象の再現率を別途評価する必要がある。

第三に、処理速度の比較はH100上で測定した圧縮時間が中心であり、視覚エンコーダ、言語モデルの入力処理、生成、I/Oを全て含む総遅延を網羅しない。1/8保持は理論上視覚トークン数を八分の一にするが、GPU全体のVRAMや応答時間が八分の一になるわけではない。異なるGPU、入力解像度、動画長、バッチ処理での総費用を再測定する必要がある。
