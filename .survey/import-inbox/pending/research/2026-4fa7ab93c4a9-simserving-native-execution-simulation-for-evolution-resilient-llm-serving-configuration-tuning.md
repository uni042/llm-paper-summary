# SimServing: Native-Execution Simulation for Evolution-Resilient LLM Serving Configuration Tuning

> サービング管理ソフトウェアを再実装せずそのまま実行しGPU計算だけを遅延推定器へ替えることで、上流進化にずれない模擬を実現し、予測誤差を13.8パーセントから4.9パーセントへ下げた設定調整基盤。

## 概要

大規模言語モデルのサービスは、リクエストのスケジューリング、動的バッチング、メモリ管理などを決める大きな設定空間を持ち、設定の違いだけで最初のトークンまでの時間（TTFT）が最大67パーセント変わることが本論文の実証研究で示される。ところが実機のGPUクラスタで設定を総当たりに試すのは費用が高く、組み合わせ爆発のため現実的でない。そこで性能予測にシミュレータを使うが、従来のシミュレータはサービングフレームワークの複雑な制御ロジックを自分で書き直す再実装方式であり、ここに本論文が再実装の落とし穴と呼ぶ問題がある。書き直された複製は元の意味と少しずつずれ、しかも上流ソフトウェアが速く進化するたびに手作業で追随しなければならず、追随が止まれば予測誤差が広がっていく。

本論文はまず、連続する8世代のvLLM（v0.6からv0.13）に対してVidurの予測誤差が世代を追うごとに広がることを示し、忠実度の漂流を実測する。次に、性能の忠実度を支配するのはスケジューリングやKVキャッシュ管理を行うサービング管理ソフトウェアである一方、その実行時間は全体の10パーセント未満にすぎず、GPU計算が90パーセント超を占めるという非対称性を示す。この非対称性が提案の出発点になる。時間の大半を占めるGPU計算だけを推定へ置き換え、忠実度を決める管理ソフトウェアは本物をそのまま実行すれば、速さと正確さを両立でき、上流の変更も自動で取り込めるはずだという着眼である。

提案するSimServingは、無改変のサービング管理ソフトウェアをCPU上でネイティブ実行し、モデル実行の呼び出し点だけを差し替え可能な遅延推定器へ置き換えるハイブリッド模擬の枠組みである。推定器の標準実装は、プロファイルしたバッチ標本から学習するXGBoost回帰であり、特徴はプリフィルとデコードのトークン数やKVキャッシュ長などである。これに粒子群最適化（Particle Swarm Optimization; PSO）による設定探索を組み合わせ、サービス品質目標（SLO）の制約の下でスループットなどを最適化する。

**代表結果:** ネイティブなvLLMを正解とする予測誤差では、平均スループット予測誤差がVidurの13.8パーセントからSimServingの4.9パーセントへ下がり、模擬の壁時計時間はLMSYS-ChatのLlama-3.1-8Bで実機ベンチマーク533.61秒に対し25.19秒と最大21.18倍速くなった。設定調整では、SimServingが見つけた設定がVidur-SearchよりLlama-3.1-8Bで5.5パーセント、Qwen3-30B-A3Bで10.2パーセント高いスループットを実機で達成した。速くするための近似が、再実装をやめることでむしろ正確になる点が主張の中核である。

## 問題設定

資源の観点では、ボトルネックは二重である。一つは実機評価の費用で、高性能GPUの占有時間と設定空間の大きさが探索を妨げる。もう一つはシミュレータ側の保守費用と意味のずれである。vLLMのスケジューラはリクエストのプリエンプションに複雑な状態機械を持ち、メモリ管理は実行時のメモリ圧に応じたKVキャッシュのエビクション方針を持つ。こうした状態を持つ制御を再実装すると、プリエンプションのタイミングやエビクション判断の微妙な違いが積み重なって予測誤差になる。さらにvLLMは1年で8つの大きな版を出す速さで進化しており、再実装側の追随が止まった例として、Vidurのサービングロジックが公開以来ほぼ変わっていないことが挙げられる。

既存対策は、演算子単位のプロファイルとスケジューリング模擬を組み合わせるVidurやAPEXなどだが、いずれも管理ロジックの再実装を前提とするため、版が進むほど正解から離れる構造的な弱さを持つ。本論文の着眼点は、模擬すべき対象を分けることにある。忠実度に効くが安い管理ソフトウェアは実行し、忠実度への寄与が薄く高価なGPU計算だけを推定へ逃がす。この分担により、版の追随は上流コードをそのまま動かすことで自動化され、保守は計装点の維持と推定器の再プロファイルへ縮小される。

## 手法のあらまし

SimServingの実行は、対象フレームワークのモデル実行の入口で横取りすることから始まる。リクエスト列がネイティブの管理ソフトウェアへ入り、スケジューリング、バッチ形成、メモリ管理が実運用と同じコードで進む。各ステップでバッチが組み上がると、実際のGPU順伝播の代わりに、バッチの特徴を遅延推定器へ渡して予測実行時間を受け取り、模擬時計を進めて次のステップへ移る。生成されるトークンの中身ではなく、トークン数やキャッシュのメタデータと模擬タイミングが管理ソフトウェアへ返るため、制御フローは実機と同じ分岐をたどる。設定調整では、この模擬を適応度評価器としてPSOが候補設定を繰り返し評価し、早期棄却で見込みのない候補を切りながら探索する。vLLMではモデル実行の呼び出し点、MindIEでは生成トークンの呼び出し点に同型の横取りを置くことで、複数フレームワークへ同じ設計を適用している。

## 手法

### 1. ネイティブ実行の横取り — 管理ソフトウェアを実行しGPU計算だけを差し替える

この機構が観測するのは、各ステップで管理ソフトウェアが組み上げたバッチの構成であり、プリフィルのトークン数、デコードのトークン数、KVキャッシュ長などが特徴になる。保持する状態は、ネイティブのスケジューラとメモリ管理が持つ本来の状態そのものであり、模擬側で別途再現しない。処理は、モデル実行の入口で実計算を止め、特徴を推定器へ渡し、返ってきた予測遅延で模擬時計を進めることである。これにより減るボトルネックは、再実装の意味のずれと版追随の保守であり、管理ロジックの判断は定義どおり実物になる。追加で消費する資源は、管理ソフトウェアをCPUで実際に走らせる時間と、横取りのための小さな計装パッチの維持である。失敗条件として、制御フローが生成トークンの内容そのものに依存する文法誘導デコードのような手法では、ダミーのトークンで進める前提が崩れることが論文で明示される。また、対象フレームワークに明確なモデル実行の境界がない場合、横取り点の特定そのものが移植の費用になる。

### 2. 差し替え可能な遅延推定器 — XGBoostによるバッチ実行時間の回帰

この機構が観測するのは、実機でプロファイルした約1万件のバッチ標本であり、各標本の特徴と実測GPU実行時間の組から学習する。保持する状態は学習済みのXGBoostモデルであり、90対10で学習とテストに分けた標本で作られる。処理は、バッチ特徴を受けて実行時間を回帰予測し、模擬時計へ返すことである。プリフィルとデコードが混ざる混合バッチでは両者の資源競合を学習で捉えるため、演算子を分解して足し上げるVidurの構成型推定器より誤差が小さくなる。これにより減るボトルネックはGPU占有時間であり、1回の予測呼び出しは平均でミリ秒未満級の軽さにとどまる。追加費用は新しいハードウェアやモデルに対する再プロファイルであり、論文では約36分のプロファイルで平均絶対百分率誤差6.25パーセント級の推定器が得られるとする。誤予測時の挙動として、プロファイル範囲から遠いバッチ構成では誤差が増え、分布のずれに対する再学習が必要になることが脅威の節で述べられる。推定器は差し替え可能であり、Vidurの推定器や実機実行そのものを差した変種も評価され、枠組みと推定器の寄与を分けて測っている。

### 3. PSOによる設定探索と早期棄却 — 模擬を適応度評価器にする

この機構が観測するのは、各候補設定で模擬を回したときのスループット、TTFT、TPOT、成功率である。保持する状態は粒子の位置と最良記録であり、10粒子を5反復回し、適応度はスループット0.4、TTFT 0.2、TPOT 0.3、成功率0.1の重みで合成され、SLOを超える指標には指数的な罰則がかかる。処理は、候補を模擬で評価し、見込みのない候補を早期に棄却しながら粒子の群れをより良い設定へ寄せることである。これにより減るボトルネックは、格子探索が要する候補評価の総数と実機時間であり、50候補程度の評価で収束する結果が示される。追加費用は模擬そのものの計算であり、推定器版では調整全体がLlama-3.1-8Bで0.39時間まで縮む。誤った場合の挙動として、模擬の忠実度が低い探索では誤った設定へ収束する危険があるため、探索の質は前二機構の正確さに依存する構造であり、最終設定は実機ベンチマークで検証される。

## 評価

結論は、再実装をやめて管理ソフトウェアを実行するだけで、模擬の忠実度と設定探索の質が同時に上がる、というものである。忠実度では、2モデルと3ワークロードの全組合せでSimServingの予測誤差がVidurを下回り、特に遅延指標で差が大きい。例えばArXiv要約のLlama-3.1-8BではVidurのTTFT誤差116.2パーセントとTPOT誤差592.3パーセントに対し、SimServingは0.9パーセントと4.9パーセントにとどまる。これはスケジューリングの簡略化が遅延の尾を壊す一方、実物のスケジューラを動かせば尾まで再現されることを意味する。効率では、模擬時間の高速化がワークロードで3.46倍から21.18倍まで分布し、デコード主体のBWBで低いのは、短いステップが多く推定の累積オーバーヘッドが相対的に増えるためと説明される。読み方として、倍率はGPU計算の割合が高い条件ほど大きくなる。

設定調整の実機検証では、SimServing-XGBはLlama-3.1-8Bで毎秒6763.7トークン、Qwen3-30B-A3Bで毎秒3324.2トークンを達成し、Vidur-Searchの6410.0と3017.8をそれぞれ5.5パーセントと10.2パーセント上回り、SLO制約も満たした。調整の壁時計時間は、格子探索の24時間超や19.95時間に対し、推定器版で0.39時間と0.36時間まで縮む。推定器単体の精度は全ワークロードで平均絶対百分率誤差3.73から10.22パーセント、平均6.25パーセントであり、Vidurの構成型推定器より混合バッチで優れる。未評価の点として、制御された調整比較はvLLMだけであり、MindIEは産業導入の報告にとどまること、SGLangなど他フレームワークへの移植は今後の課題であることが明記される。

## 既存研究との差

VidurやAPEX、Frontierのような演算子プロファイル型シミュレータとの差は、管理ロジックを模擬するのではなく実行する点にある。従来方式は版の進化に手作業で追随しなければならず、その遅れが忠実度の漂流になる。本論文は追随そのものを不要にし、残る保守を計装点と推定器の再プロファイルへ限定した。設定調整の研究としては、安定した評価器を前提に探索法を競う流れに対し、進化するソフトウェアの下で評価器自体をどう正しく保つかという土台の問題を扱った点が異なる。

## 限界・実装状況

限界は、制御フローが生成内容に依存する手法ではダミートークンの前提が崩れること、推定器がプロファイル範囲外では誤差を増やすこと、制御された比較がvLLMに限られMindIEはAscend NPUのみで産業報告にとどまること、他フレームワークへの移植にはモデル実行境界の特定が要ることである。実装状況は、成果物がfigshareで公開され、ソースコード、実験スクリプト、vLLMとMindIEへの計装パッチと再現データを含むと記される。今後の方向として、LLM誘導の探索への置換、拡散モデルなど他推論系への適用、SGLangでの検証が挙げられる。

## 一般的な実装上の含意

速く進化するソフトウェアの性能を模擬するときは、全体を書き直すのではなく、忠実度を支配する安い部分を実行し、高価な部分だけを推定へ置き換える分担が有効である。その分担は、時間割合ではなく忠実度への寄与で決めるべきであり、本論文では時間の10パーセント未満の管理ソフトウェアが忠実度を支配していた。また、推定器は差し替え可能な部品として切り離すことで、枠組みの効果と推定器の効果を別々に検証できる。
