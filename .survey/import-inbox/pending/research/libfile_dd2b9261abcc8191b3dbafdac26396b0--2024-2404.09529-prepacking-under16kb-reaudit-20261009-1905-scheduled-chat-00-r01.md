# Prepacking：独立したプロンプトを同じ系列へ詰める事前入力高速化

## 概要

Prepackingは、長さの異なる複数の入力プロンプトを一括処理する際、短いプロンプトを最長プロンプトまでパディングすることで発生する無駄な計算とGPUメモリ消費を減らす方式である。各プロンプトを一つの箱に見立て、複数の短いプロンプトを同じ固定長の系列へ詰める。その際、別プロンプト同士が注意できない独立注意マスクと、各プロンプトの先頭で0から再開する位置番号を設定する。こうして物理的には一つの系列に連結しながら、論理的には独立した複数要求のキー・値キャッシュを一度の順伝播で作る。

論文は単一のNVIDIA A6000-48GBで、1.3Bから13Bまでのモデルを使って検証する。Hugging Faceの通常のパディング型プリフィルを基準に、最大6倍の高速化、MMLUを用いた1.3Bモデルで最大16倍のバッチ収容を報告する。ただし通常の実験で観測される事前入力時間と初回トークン時間の改善範囲は約1.6～3.5倍とされ、最大値だけで典型的な効果を代表させてはならない。比較対象は主にパディング型の実装であり、現代の可変長注意カーネルを備えた配信基盤すべてに同じ倍率で勝つことを意味しない。

Prepackingはモデルの重みや生成アルゴリズムを変更するのではなく、事前入力処理（prefill）のデータ配置を変える。元の要求ごとにキー・値キャッシュを取り出した後は、通常の自己回帰生成へ引き渡せる。したがって量子化のようにモデル表現を近似する方法でも、投機的復号のように出力生成を先読みする方法でもない。正確な要求分離を維持しながら無効トークンへの計算を避けることが目的である。

## 問題設定

通常の可変長バッチでは、入力系列の長さを `l_1,...,l_k` とすると、バッチ中の最大長 `m=max(l_i)` に合わせてすべての系列を長さmへそろえる。実トークンの総数が `L=sum(l_i)` でも、物理的な入力テンソルはk行×m列となる。長いプロンプトが一つあるだけで、残りの短いプロンプトが大量のパディングを持つことがある。注意マスクでパディングを意味的に無視しても、パディングに対応するテンソル形状が計算と中間メモリを増やす実装では費用が残る。

事前入力処理では、入力全体の問い合わせ・キー・値とMLPを計算し、生成時に再利用するキー・値キャッシュを構築する。パディングが多いとGPU上の行列演算と活性値メモリが無効領域へ使われる。初回トークン時間（time to first token; TTFT）にもこの処理が含まれるため、短い要求を多数まとめるワークロードでも、最長の一件によってバッチ全体の待ち時間が長くなり得る。

入力を長さ順に並べ替えて似た長さを同じバッチへ集める方法は、長さのばらつきを減らせるが、各バッチ内に残るパディングを消すわけではない。また実配信では将来到着する要求の長さを完全には知れない。Prepackingは到着済みの一バッチの中だけで、短い系列を長い系列の余白へ詰めることでこの問題を扱う。

## 手法

### 1. ビン詰めとして系列配置を決める

入力プロンプトを長さ `l_i` のアイテムとみなし、ビンの容量をバッチ内の最長プロンプト長mに設定する。目的は、すべてのプロンプトを入れるためのビン数rをできるだけ小さくすることである。各ビンには複数のプロンプトを連結して格納できるが、合計長はmを超えない。従来はk本の系列を処理するのに対し、Prepackingではr本の連結系列を処理し、通常 `r<=k` となる。

ビン詰め問題は一般に難しい組合せ最適化だが、論文は最初に長いアイテムから並べ、入る最初のビンへ順に配置するFirst-Fit Decreasingという近似法を用いる。最適な詰め方を必ず見つける保証はないが、実行時間が小さく、GPU計算前の前処理として扱いやすい。アルゴリズム1では、各ビンのプロンプト開始位置を記録し、後段の注意マスク、位置番号、キャッシュ分割へ渡す。

ビンの容量を最大長mにするのは、従来のバッチと同じ最大系列長を保つためである。連結によって個々の要求の実トークンを消すわけではなく、もともとパディングだった位置へ別の要求の実トークンを入れる。ビンの末尾に空きが残る場合はその部分だけパディングする。したがって理想的には、k行×m列からr行×m列へ計算対象の行数を減らせる。

### 2. 独立注意マスクで要求間の干渉を防ぐ

単純に二つのプロンプトAとBを連結すると、因果注意では後ろのBが前のAへ注意できる。これはBを単独で入力した場合と異なるキー・値キャッシュを作ってしまうため、そのままでは正しい事前入力処理ではない。Prepackingは各プロンプトの開始・終了位置を使い、同一プロンプト内の過去トークンへの注意だけを許可する。異なるプロンプト間の注意得点は遮断する。

数学的には、連結した系列の注意マスクを、各プロンプトに対応する下三角行列を対角ブロックとして並べた形にする。対角ブロックの外側は無効とする。これにより、各プロンプトは自身の過去だけを参照し、物理的な連結順序によって他の要求の情報が混入しない。図1は、単純な因果マスクと、要求ごとの独立マスクの違いを示している。

この処理が重要なのは、速度改善が意味的な近似によって得られたものではないという点である。要求間の注意を正しく遮断できれば、各プロンプトに対する注意の依存関係は元の単独処理と一致する。パディング削減だけを実装して独立マスクを省くと、生成結果の正しさが失われる。

### 3. 位置番号を各プロンプトで再開する

多くのモデルでは、トークンの位置が注意計算に影響する。例えば回転位置埋め込み（Rotary Position Embedding; RoPE）は位置番号に応じて問い合わせとキーを回転させる。Aの後ろへBを連結したとき、Bに全体の通し番号を割り当てると、Bを単独で処理した場合より大きい位置番号となる。独立注意マスクだけでは、位置表現の違いを取り除けない。

そこで各プロンプトの先頭を位置0として、内部の位置番号を0、1、2…と振り直す。連結されたビンの中で位置番号が何度も0へ戻る形になるが、要求間の注意を遮断しているため、互いに影響しない。論文の図1とアルゴリズム1は、独立注意マスクと位置番号再開を一体として扱う。片方だけを適用した構成は正しい事前入力とみなせない。

### 4. 要求ごとのキー・値キャッシュを取り出す

ビンをまとめてモデルへ通した後、出力されたキー・値キャッシュは連結系列の順序で並んでいる。Prepackingは記録していた各プロンプトの開始・終了位置を使い、キャッシュを元の要求ごとに分割する。分割したキャッシュを通常の生成処理へ渡せば、以後のデコードでは元の要求がそれぞれ独立にトークンを生成できる。

論文はこのキャッシュ展開の費用をプロンプト数に対して線形と整理し、事前入力の大きな注意・MLP計算に比べて小さいと論じる。ただし生成処理自体を高速化する機構ではないため、出力が長いワークロードでは全体の待ち時間に占める事前入力の割合が小さくなる。論文には生成段階の予備的な検討もあるが、中心的な定量評価は事前入力と初回トークン時間である。

### 5. 計算量の分析と成立条件

通常のパディング型事前入力を単純化して `O(km²)` とする。理想的にパディングがほとんどないビン詰めができる場合、ビン数は `r=L/m` となり、計算量は `O(rm²)=O(Lm)` となる。平均プロンプト長 `L/k` は最大長m以下なので、`O(Lm)` は通常の `O(km²)` より小さくなる。ビン詰め自体の費用は `O(k log k)` とされる。

ただしこの分析はGPUがバッチ間を完全に並列化できない条件を前提とする。GPUがk本の系列を完全に並列処理できるなら、行数を減らしても計算時間は同じになる可能性がある。論文はバッチ数が増えると実機で処理時間が伸びることを図2で示し、完全並列化が成立しない現実的なGPU条件での利得を説明する。逆にすべての系列が同じ長さでr=kとなる場合は、パディング削減による利得がなくなる。

## 評価条件

| 観点 | 論文での条件 | 注意点 |
|---|---|---|
| GPU | NVIDIA A6000、48GB、単一GPU | H100などへ倍率を直接適用しない |
| CPU | AMD EPYC Genoa 9124搭載サーバ | ビン詰め前処理を含む環境 |
| モデル | Sharded LLaMA 1.3B、LLaMA2-7B/13B、Mistral-7B | 複数の規模・構造を比較 |
| 重み精度 | 計算資源制約から4ビットまたは8ビット量子化 | 全条件がFP16モデルではない |
| 入力データ | MMLU、SAMSum、Alpaca、WikiText、Anthropic HH RLHF | 各データから1000件を抽出 |
| 比較対象 | 通常のフルパディング、長さ順バッチ、Prepacking | 主にHugging Faceのパディング実装 |
| 主指標 | 事前入力時間、初回トークン時間、ピークメモリ、収容バッチ数 | 出力品質の順位を比較する研究ではない |

論文は多様な長さ分布を得るため、複数の公開データセットからプロンプトを抽出する。タスクの正答率を競うのではなく、異なる長さの入力をまとめた際の計算効率を測る。したがってMMLUを使った評価で「正答率が向上した」と解釈してはならない。データセット名は主として入力長の分布を表す。

## 評価結果

### 事前入力時間と初回トークン時間

論文の第4.3節と図4では、Prepackingが通常のフルパディングより事前入力時間と初回トークン時間を短縮し、多くの条件で約1.6～3.5倍の改善を示す。導入部では最大6倍の改善を報告するが、これは特定のモデル・データセット・バッチ条件で得られた最大値である。全条件の平均改善が6倍という意味ではない。事前入力と初回トークン時間も完全に同じ指標ではなく、後者にはキャッシュの展開と最初のトークン生成が含まれる。

| 条件 | 報告された結果 | 解釈 |
|---|---:|---|
| 事前入力の最大高速化 | 最大約6倍 | パディング型の比較基準に対する特定条件 |
| 主な実験での事前入力・初回トークン時間 | 約1.6～3.5倍改善 | データセットとモデルによって変動 |
| LLaMA2-7Bの代表的な大バッチ条件 | 最大約4.5倍 | 入力長分散とバッチ数が大きい場合 |
| LLaMA系1.3Bの代表的な大バッチ条件 | 最大約6倍 | 最も利得が大きい条件の一例 |
| MMLU・1.3Bのバッチ収容数 | 最大16倍 | GPUメモリ制約の下での容量比較 |

入力長のばらつきが大きいほど、短いプロンプトのパディングを別要求で埋められる。バッチが大きいほどビン詰めの候補も増え、同じ最大長mに対して必要なビン数rを減らしやすい。逆に長さがそろっている場合や要求が少ない場合は、詰める余白が少ないため効果が小さくなる。速度改善の主因は入力長の分布とバッチ形成であり、モデル重みの圧縮ではない。

### GPUメモリとバッチ容量

論文の図5では、Prepackingが通常のフルパディングに比べてピークGPUメモリを減らし、同じGPU上でより多くの要求をまとめて処理できることを示す。MMLUを使ったLLaMA系1.3Bの構成では、メモリ不足になるまでに収容できるバッチ数が最大16倍となる。これは「モデルのパラメータ数を16分の一にした」結果ではなく、入力テンソルと事前入力の中間状態における無効領域を減らした効果である。

旧原稿には公開実装の一条件で平均0.441秒対2.299秒、ピーク約4.58GB対34.60GBという値があったが、今回確認した論文本文の主要表で同一の条件と数値を直接照合できなかったため、今回の再監査本文では実測の主結果として採用しない。数値を挙げる場合は、論文本文と実装のプロファイルを明確に区別する必要がある。

### 正確性とモデル出力への影響

Prepackingは、独立注意マスクと位置番号再開によって、個々のプロンプトが参照できる過去と位置情報を単独処理時に一致させる。論文のアルゴリズムは、パディング型の通常処理と同じキー・値キャッシュを作ることを意図している。したがって出力品質を落として高速化する近似量子化とは異なる。ただし浮動小数点演算の実装や演算順序による微小な数値差が絶対にないとまで一般化するのではなく、意味的な要求分離が維持される設計として理解する。

### 評価の限界から読み取れること

比較対象のフルパディングは、現代の可変長注意実装やページ化されたKV管理をすべて使う最適化済み配信基盤とは限らない。既にパディングをほとんど計算しない実装を基準にすれば、Prepackingの追加利得は小さくなる可能性がある。論文の最大6倍を、vLLMやSGLangの最新実装へそのまま適用することはできない。モデル規模、重み量子化、GPUメモリ、バッチ長分布が違えば測定結果も変わる。

## 既存研究との差

長さ順バッチングは、似た長さの要求をまとめてパディングを減らすが、各バッチの最長長までの余白は残る。Prepackingは複数の要求を一つの物理系列へ詰めるため、余白自体を別要求の有効トークンで埋められる。学習時の系列詰め込みと発想は近いが、推論では各要求のキー・値キャッシュを後段の生成へ独立に渡す必要があり、注意マスクと位置番号の再開、キャッシュ展開が不可欠である。

連続バッチングは、要求の到着や終了に応じて実行バッチを更新する仕組みであり、Prepackingのような同一事前入力呼出し内のパディング除去とは異なる。両者を組み合わせる余地はあるが、論文の測定は特定のパディング型基準に依存する。配信スケジューラとモデル内のテンソル配置を別々に考えることが、手法の位置付けを理解する上で重要である。

## 限界と未検証事項

利得は入力長のばらつきとバッチの大きさに強く依存する。すべてのプロンプトが同じ長さならビン詰めで行数を減らせず、追加の前処理費用だけが残る。ビン詰めは近似アルゴリズムなので最適な配置が常に得られる保証もない。ビン数を減らしても、GPUがすでに十分な並列度を持つ条件では時間の改善が小さくなる可能性がある。

独立注意マスクと位置番号再開を正しく扱えないモデルや注意カーネルへ適用すると、要求間の干渉や誤った位置表現が生じる。単に系列を連結するだけでは正しいキャッシュは作れない。キャッシュの展開にも境界情報とメモリ操作が必要であり、専用実装の保守費用はゼロではない。現代の可変長注意実装では、すでに無効トークンを省くための別経路があるので、重複した最適化にならないかを確認する必要がある。

主な評価は単一A6000と比較的古いLLaMA/Mistral系列の1.3B～13Bモデルである。複数GPU、非常に長い文脈、混合専門家モデル、厳格な応答遅延目標を持つ配信基盤へ同じ倍率を一般化できない。また主に事前入力と初回トークン時間を評価するため、出力トークン数が長く生成時間が支配するワークロードでは、全体の速度改善は小さくなり得る。

## 再監査での修正点

既存原稿の基本機構は妥当だったが、最長プロンプト長をビン容量とする理由、First-Fit Decreasingの近似性、独立注意マスクと位置番号再開の両方が必要な理由、キャッシュ展開の費用、計算量分析の前提を補った。実測については主な実験の約1.6～3.5倍と導入部の最大6倍を区別し、論文で確認できない実装プロファイル数値を一次論文の主結果として扱わないよう修正した。
