# KernelBench: Can LLMs Write Efficient GPU Kernels?

## 概要

KernelBenchは、言語モデルが機械学習の参照実装から、機能的に正しく、かつ実際のGPU上で速い計算カーネルを生成できるかを評価する公開基盤である。一般的なプログラム合成では単体試験に通ることを重視するが、GPUカーネルの実用性は入力形状、メモリ階層、並列実行、命令セットに左右される。KernelBenchは250件のPyTorch課題に対して、生成した実装をコンパイル・実行して出力を照合し、実行時間を参照実装と比較する。**正しくても遅い実装を成功とみなさない**ことが設計の中心にある。

著者は速度しきい値付き成功率 `fast_p` を導入した。2025年の原著でNVIDIA L40Sを用いた一回生成の評価では、推論能力の高いモデルでも、PyTorchの逐次実行（Eager）より速い正答を生成できる課題は多くなかった。例えばDeepSeek-R1の `fast_1` は単一演算12%、複合演算36%、モデル全体2%である。一方、実行エラーと性能解析器（profiler）の結果を10回まで返す反復改善では、同モデルの複合演算で36%から72%へ改善した。これは**10回の生成とGPU上の検証を許したときに少なくとも一つの正しい高速実装を見つけた割合**であり、一回の生成性能が72%になったわけではない。

## 背景と研究課題

GPUでは、同じ数学演算でもデータ配置と実行順序によって性能が大きく変わる。行列積の分割（tiling）、演算融合（operator fusion）、共有メモリの再利用、メモリアクセスの連続性、Tensor Coreの利用、非同期転送などは、単にPythonの計算式をCUDAへ書き換えるだけでは最適化されない。PyTorchの演算は内部で高度に最適化されたライブラリを呼ぶことが多く、手書きコードでこれを上回ることは難しい。カーネル生成の評価には、実行可能性、参照出力との一致、特定ハードウェアでの実測速度という三つの独立した軸が必要になる。

既存の一般コード生成ベンチマークは関数の単体試験通過を測ることが多い。一方、GPUカーネルでは入力形状が固定されているときの高速化も実務上重要であり、コンパイラが得意な単純演算と、人間が演算融合を設計できる複合演算では難しさが異なる。さらに、あるGPUで速いカーネルが別のGPUでも速いとは限らない。KernelBenchは参照PyTorchプログラムと入力仕様を与え、任意のCUDA系の実装を提出できる形にすることで、言語モデルの性能工学能力を測ろうとする。

## 手法

### 課題の構成と入出力契約

原著の250課題は、レベル1の単一演算100件、レベル2の複数演算列100件、レベル3の実用的なモデル構造50件に分かれる。レベル1には行列積、畳込み、活性化、正規化、損失関数が含まれる。レベル2には3～6演算を連結した、演算融合が有効になり得る課題がある。レベル3はAlexNetやMiniGPTなど、複数の層からなる構造を含む。後から公開された実装リポジトリにはレベル4などの拡張があるが、**原著の主実験は3レベル・250課題**であり、拡張後の課題数と混同しない。

各課題は `torch.nn.Module` に由来する参照クラス `Model`、具体的な入力を定義する `get_inputs()`、必要に応じて初期化引数を返す `get_init_inputs()` を持つ。言語モデルは置換クラス `ModelNew` を生成し、その中でCUDA、Triton、CUTLASS、PTXなどを利用できる。課題は単にGPUコードの文字列を出すことではなく、指定された入力で参照クラスと同じ計算結果を返す置換実装を作ることである。

### 機能正当性と速度の二段階検証

評価器は生成コードをコンパイルして、**5個のランダム入力**で参照実装との出力形状と数値を比較する。コンパイル失敗、メモリ違反、実行時エラー、数値の不一致は成功としない。機能正当性を通過した実装について、繰り返し実行した実時間を測り、参照PyTorchの時間との比率を求める。5個の入力での照合は形式的な同値性証明ではなく、指定された入力分布と許容誤差に対する実験的な検証である。

課題数を `N`、課題 `i` の生成実装の速度比を `s_i = t_ref,i / t_generated,i` とすると、`fast_p = (1/N) Σ_i 1[correct_i ∧ s_i > p]` と定義する。`fast_0` は機能正答率に対応し、`fast_1` は**参照実装より速く、しかも正しい**課題の割合を表す。しきい値 `p` を上げれば高速化要求は厳しくなる。`fast_1` が36%という数値は平均速度が1.36倍という意味ではない。速度の速い一部の課題が全体の平均値を押し上げることもないため、成功率と平均速度倍率を混同しない指標になっている。

### 一回生成と比較対象

主実験はNVIDIA L40Sを使い、簡単な加算カーネルの入出力例を一つ示したうえで、各課題につき貪欲復号（greedy decoding）で一回だけ生成する。比較対象はPyTorch Eagerと、標準設定の `torch.compile` である。両者は同じ基準ではなく、`torch.compile` はコンパイル済みでも小演算の実行時費用がEagerより大きいことがあり、生成カーネルの相対的な順位は比較対象によって変わる。測定GPU、入力形状、ソフトウェア版を記録しない成功率は他環境へ直接転用できない。

### 反復改善と探索量の分離

著者は、複数候補を独立に生成する反復標本化（repeated sampling）と、前回のコードを見せて修正させる反復改善（iterative refinement）を分けて比較した。反復改善では、前回生成コード `G` だけ、`G` に実行結果 `E` を加える条件、さらに性能解析情報 `P` を加える条件を用意する。コンパイラや実行時の失敗は具体的なエラーメッセージを返せるが、数値不一致の原因特定はより難しい。性能解析は、正しいカーネルでもメモリ待ちや演算配置の改善余地を見つける手掛かりとなる。

各課題で最大10回の生成・検証を行い、途中までに一つでも正しく速い実装が得られたかを測る。この設定は推論回数を増やす費用を許した**テスト時の探索**であり、同じ計算量で一発生成の性能が向上したという主張ではない。独立に100回標本化する実験は、フィードバックなしで探索数だけ増やした場合の上限を調べるために使う。

## 評価条件と主要結果

| 項目 | 原著の設定 |
|---|---|
| 課題 | レベル1：100、レベル2：100、レベル3：50、計250 |
| 主GPU | NVIDIA L40S。別GPUのA10G等でも比較 |
| 比較対象 | PyTorch Eagerと `torch.compile`（同一の成功率ではない） |
| 正当性 | 5個のランダム入力に対する参照出力照合 |
| 一回生成 | 簡単な例を一つ与えた貪欲復号、1課題1生成 |
| 反復 | 前回コード・実行結果・性能解析を組み合わせ、最大10回 |
| 主指標 | `fast_1`：機能的に正しく、かつ参照より速い課題の割合 |

### 一回生成での `fast_1`

以下は原著Table 3の**L40S・PyTorch Eagerを基準**とした割合である。

| モデル | レベル1 | レベル2 | レベル3 |
|---|---:|---:|---:|
| GPT-4o | 4% | 5% | 0% |
| OpenAI o1 | 10% | 24% | 12% |
| DeepSeek V3 | 6% | 4% | 8% |
| DeepSeek R1 | 12% | 36% | 2% |
| Claude 3.5 Sonnet | 10% | 7% | 2% |
| Llama 3.1 70B Instruct | 3% | 0% | 0% |
| Llama 3.1 405B Instruct | 3% | 0% | 2% |

レベル2でDeepSeek R1が36%と比較的高い一方、レベル3では2%に落ちる。これは複雑なモデル構造の置換が容易でないことを示す。`torch.compile` を基準にすると、例えばDeepSeek R1はレベル1/2/3で38%/37%/2%、o1は28%/19%/4%となる。比較対象によって数値が変わるので、表を使うときは必ず参照実装を明記する。

### 失敗原因とハードウェア依存

推論モデルはコンパイル・実行エラーを減らせる傾向があるが、**数値や出力形状の不一致は依然として残る**。GPU固有の命令を積極的に使う試みが、実行不能なコードを増やすこともある。DeepSeek R1はレベル1の行列積の約半数でワープ行列積命令（WMMA）を使おうとしたが、多くはコンパイルに失敗した。高度な命令を使ったというだけでは高速化に結び付かない。

同じ生成コードを別GPUで測ると相対性能が変わる。DeepSeek R1のレベル2では、L40Sでの `fast_1` は36%、A10Gでは47%だった。これはA10GがL40Sより常に速いという意味ではなく、**それぞれのGPU上のPyTorch参照実装に対する相対速度比**が変わったという結果である。GPUの命令能力やメモリ階層、参照実装の性能が異なるため、ある環境での成功率を別のGPUへ一般化できない。

### 反復改善の効果と負の結果

DeepSeek R1のレベル2で10回の反復を許すと、前回コードのみ `G` は44%、実行結果を加えた `G+E` は62%、さらに性能解析を加えた `G+E+P` は72%だった。一回生成の36%に比べて改善する。レベル1では12%から43%、レベル3では2%から18%へ改善した。ただしDeepSeek V3のレベル2では、`G+E+P` は6%であり、独立10回標本化の14%より低い。**フィードバックを増やせば必ず性能が上がるわけではなく、モデル側の修正能力と課題に依存する**。

DeepSeek R1はレベル1と2の90%超で10回以内に少なくとも一つの機能的に正しいカーネルを得たが、速い実装を得られた割合はそれより低い。機能正当性の達成と速度向上を分ける必要がある。またDeepSeek V3のレベル2は100回の独立標本化で `fast_1` が4%から37%まで上がった一方、レベル1の畳込みの34課題では100回試しても正しい解が得られなかった。探索数を増やすだけでは埋まらない体系的な弱点がある。

### 具体的な高速化事例と情報提供の逆効果

論文は一部の成功例として、演算融合によるGELUの2.9倍、Softsignの1.3倍、行列積・除算・総和・尺度調整の融合による2.6倍、共有メモリを使ったコサイン類似度の2.8倍、対角行列との積を要素単位の尺度変更に置き換えるアルゴリズムで13倍を報告する。これらは**個別課題の速度比**であり、250課題全体の平均高速化ではない。

タイル化や演算融合の手本を複数提示すると、モデルがより複雑な最適化を試すものの、実行エラーが増えて全体の `fast_1` が下がる条件もあった。ハードウェア仕様を提示しても、Llama 3.1 70BやDeepSeek V3では明確な改善が見られない。知識を与えることと、その知識を使って正しい高速コードを生成する能力は別問題である。

## 既存研究との差

KernelBenchは一般的なプログラム合成の正答率ではなく、実用的な機械学習演算の**数値的正しさとGPU上の実測速度を同時に要求**する。さらに実行・性能解析を次の生成へ返せるため、自動カーネル最適化エージェントの研究基盤になる。著者の公開実装は課題・実行・採点を提供するが、論文は全ての生成カーネルを実サービスへ組み込んだ推論遅延改善を示すものではない。

## 限界

正当性の検証は5個のランダム入力による近似的な判定であり、全入力について数学的同値を保証しない。固定形状に過適合したコードや、タイミング測定の抜け道による見かけ上の高速化にも注意が必要である。GPU型、ドライバ、CUDA版、PyTorch版、入力形状、比較対象の変更はスコアに影響する。原著の250課題は広範だが、すべてのLLM推論カーネルや新しいアクセラレータの命令を網羅するわけではない。

反復改善は10回分のモデル呼出し、コンパイル、GPU実行、性能解析を要するため、`fast_1` の向上は探索費用と引き換えである。論文が測るのはオフラインでカーネルを発見する能力であり、要求を受けるたびにカーネルを自動生成して実時間で配備する方式の性能ではない。実運用では別途、安全な検証、再現性、キャッシュ、移植性、生成したカーネルの保守が必要となる。

### 評価器の安全性と検証範囲

本ベンチマークの機能正当性は、参照コードと生成コードを同じランダム入力で比較する方式である。これは多くの明白な誤実装を排除できるが、未観測の入力や境界条件を網羅する証明ではない。生成コードが特定の入力形状にのみ適合した場合や、出力の数値許容差に依存する場合、測定された正答率が一般的なライブラリ実装の安全性を保証することはない。実務では、入力分布、精度形式、GPU型を変えた追加検証が必要である。

さらに性能測定には、コンパイル時間を含めるか、GPUのウォームアップをどう扱うか、非同期実行をどう同期して計時するかといった細部が影響する。論文の主指標はカーネル実行の実時間であり、生成モデルの推論時間や10回の試行の総費用を含むサービス全体の指標ではない。高速なカーネルを発見できたことと、発見に要する計算資源を回収できることは別の評価課題となる。

### モデルの改善に関する慎重な解釈

DeepSeek R1のレベル2で `G+E+P` が72%に達した結果は、モデルに実行結果と性能解析情報を返すと性能工学の試行錯誤を進められる可能性を示す。しかし、その72%は単一の最終生成が全課題の72%で速かったという意味ではなく、10回までの候補から一つでも条件を満たす実装があった割合である。しかもレベル3の成功率は18%にとどまり、複雑なモデル構造を正しく高速化する問題は残る。別モデルでは情報追加が逆効果になるため、最適な反復方策もモデルに依存する。

原著の公開時点と、現在の著者リポジトリの更新状況も区別する必要がある。後年の実装にはレベル4や追加の検証機能があるが、2025年の論文が報告した実験結果は3レベル250課題を対象とする。追加機能を使って再評価した場合、その結果は新しい実験として明記し、論文のTable 3の値と無条件に比較しない。
