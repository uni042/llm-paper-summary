# Vidur: A Large-Scale Simulation Framework For LLM Inference

> 演算子の入力依存性を利用して少数の実機測定から推論時間を推定し、要求到着・KVキャッシュ・並列実行まで再現するシミュレータ。実機測定との誤差と構成探索の費用を別々に検証する。

## 概要

大規模言語モデルの推論サービスを構築するとき、モデルの規模だけで最適なGPU構成は決まらない。テンソル並列数、パイプライン並列数、GPU種類、バッチ上限、スケジューラ、入力長と出力長の分布が相互に作用する。特にデコードは過去トークンの鍵・値（KV）キャッシュを毎回読み直し、プリフィルとは計算密度が異なる。ある負荷で最適だった構成を別負荷に使うと、同じLLaMA2-70Bでもコストが最大2倍変わることを論文は示す。

Vidurはこの構成探索を、GPU上で数百・数千通りの設定を実行する方法から、少数の実機演算子測定とイベント駆動シミュレーションへ置き換える。モデルの層構成から計測すべき演算子を抽出し、未測定の形状はランダムフォレスト回帰で時間を補間する。さらに要求振分け、バッチ形成、KVメモリ管理、パイプライン段内の実行を別々の階層で追跡する。出力は単なるトークン毎秒ではなく、先頭トークン待ち時間、トークン間時間、要求完了遅延、GPU利用率、KV容量利用率などである。

MLSys 2024の実機評価ではLLaMA2-7B/70B、InternLM-20B、Qwen-72Bと、会話・要約・長い出力の3種類の負荷を使う。静的要求のP95正規化実行遅延は最大3.33%の誤差、処理容量の85%を使うオンライン負荷では最大8.50%の誤差である。Vidur-SearchはLLaMA2-70Bの構成探索を96コアCPU約1時間で実施し、実機総当たりなら約42,000 GPU時間、約218,000米ドルと見積もる。ただし、これはシミュレータ自身が実機推論を高速化するという結果ではなく、**構成を評価するための探索費用**を削減した結果である。

## 問題設定と技術的背景

学習の一反復は比較的安定した計算形状で進むが、オンライン推論の一反復は直前に到着した要求と完了した要求によって構成が変わる。長い文章の最初の処理では注意演算の計算量が入力長に強く依存する。逐次生成では1要求につき新しいトークンは通常1個であり、以前のトークンに対応するKVキャッシュの読み込み量が支配的になる。異なる長さの要求を同じバッチへ入れると、単なる「バッチ数」では計算時間を説明できない。

実機の総当たりを避けるために、GPU演算子を一つの黒箱として回帰する方法も考えられる。しかし入力長、過去のKV長、要求数、並列分割、GPU種類を直積で列挙すると、測定空間が膨大になる。さらにCUDAカーネルはタイル境界や実行ウェーブ数で不連続に時間が変わるため、単純な滑らかな多項式近似では外す。逆に複雑なニューラル回帰器を使うと、少数測定からモデルを立ち上げる目的と矛盾する。

もう一つの問題は予測誤差の連鎖である。例えばある反復を数ミリ秒短く予測すると、その時刻までに到着している要求が変わり、次のバッチ、KVメモリ残量、待ち行列も変わる。したがってVidurが必要とするのは平均カーネル時間の近似だけではなく、状態を持つサービング処理の時系列再現である。

## 手法

### 1. モデル仕様からの演算子抽出と三分類

Vidurのモデル導入処理は、層数、隠れ次元、注意ヘッド数、KVヘッド数、テンソル並列の分割方式を記述した仕様を入力する。そこから線形演算、活性化・正規化、注意、集合通信、パイプライン送受信などの計測対象を作る。ここでモデル全体の入力長とバッチ数を単一の特徴量へ押し込まず、演算子が何に依存するかで三つに分ける。

第一のトークン単位演算子には全結合、活性化、正規化などが含まれる。これらの処理時間は主として現在の反復で扱う総トークン数と行列形状に依存し、過去の文脈長は直接必要ない。第二の系列単位演算子である注意は、今回処理するトークン数だけでなく過去の文脈長を読む。第三の通信演算子はall-reduce、all-gather、send/recvで、通信量と接続構成に依存し、モデル固有の語彙内容には依存しない。各分類に必要な入力だけを計測するため、計測点を減らせる。

テンソル並列では同じ層でも各GPUが担当する行列形状が変わる。Vidurはモデル仕様から分割後の形状を導き、単一GPU上で対応する計算を測定できるようにする。通信だけはGPU間の接続構成ごとに独立して測定する。これにより、モデルを異なるGPU数で実際に丸ごと動かして全設定を測る必要を小さくする。ただし未計測のGPU世代や通信トポロジに対して既存表がそのまま正確であるとは主張していない。

### 2. プリフィルとデコードで異なる注意時間の近似

プリフィル注意では要求ごとの入力長を `p_i` とすると、論文は全体の主要計算量が `Σ_i p_i²` に比例することを利用する。複数要求のプリフィルを、長さ `sqrt(Σ_i p_i²)` の単一要求に相当する測定形状へ写像する。単に入力長の総和を使うよりも、長い一要求の二乗計算量を適切に反映できる。これは注意カーネルの時間を推定するための等価入力であって、実際の要求を一つに連結する処理ではない。

一方、デコード注意では各要求が過去のKVキャッシュを読み込む。著者らは対象のPagedAttention v2やFlashDecodingのような系列並列化可能な注意実装で、要求間の長さの偏りがあっても、バッチ全体のKV読込総量が時間の有効な説明変数になると観察する。そこで個々の要求長の全組合せを測る代わりに総KV読込量を特徴量にする。この近似は、長い要求への並列化が不十分な別カーネルでは成立が弱くなる可能性がある。

### 3. 小規模実測とランダムフォレスト実行時間推定

実機プロファイラはPyTorch演算とCUDA計測機構CUPTIを利用して演算子時間を収集する。すべての行列サイズを測らず、測定済み点を教師データにして小型のランダムフォレスト回帰器を学習し、未測定の形状の時間を補間する。著者らは、多層パーセプトロンより少数の教師点で学習しやすく、多項式よりタイル・ウェーブ境界の段差を扱いやすいことを選択理由にする。

回帰器の出力は演算子種類・GPU・形状ごとの時間参照表に変換される。シミュレーションの各反復ではモデル層ごとの演算子時間と通信時間を参照し、現在のバッチ構成に応じて時間を進める。したがって新しいGPUで高精度に使うには新たなプロファイルが必要であり、GPUを一度も測らずに任意の機種へ一般化する方式ではない。

### 4. 三層イベント駆動スケジューラとKVメモリ

大域スケジューラは到着要求をレプリカへ振り分ける。ラウンドロビン、未完了要求数の少ないレプリカ選択、要求の割当を遅らせる状態依存型の振分けを扱う。振分けが終わると各レプリカのスケジューラが次反復のバッチを作り、同時にKVキャッシュの割当・解放・再開条件を処理する。KVに使える容量はモデルの重み、並列方式、GPUメモリの制約から計画器が計算し、メモリ管理器を介してバッチ方針へ渡す。

バッチ方針にはvLLM、Orca、FasterTransformer、Sarathi-Serve、LightLLMを実装する。例えばvLLM系はプリフィルを積極的に入れ、必要に応じて既存デコードを一時停止する。Sarathi-Serve系はプリフィルを小さく分割し、デコードと混在させてトークン間遅延を抑える。論文によれば、これらの方針は共通のメモリ管理APIを使い、それぞれ150行未満のPythonコードで表現された。

最後の段スケジューラはパイプライン並列時のマイクロバッチの段間依存を扱う。ある段の終了イベントが次段の開始可能時刻を決め、通信時間も反映する。論文時点の対応は同期パイプラインが中心で、非同期通信、系列並列、投機的パイプライン復号は将来拡張である。したがってVidurが出す遅延は、**選択したスケジューラと演算子モデルを忠実に実装できた範囲**の推定値である。

### 5. Vidur-BenchとVidur-Searchの接続

Vidur-Benchは実際のデータ集合から入力・出力トークン長の分布を抽出する。会話中心のLMSys-Chat-1M、長い入力を要約するArxiv-Summarization、長い出力が支配的なBilingual-Web-Bookを使い、同じモデルでも負荷特性を変えて測れるようにする。到着時刻は別に生成し、静的な全要求一括到着と、ポアソン到着を仮定したオンライン負荷を区別する。

Vidur-Searchはモデル、負荷、GPU候補、利用可能GPU総数、先頭トークン待ち時間（TTFT）とトークン間時間（TBT）の制約を受け取る。テンソル・パイプライン並列数、レプリカ数、スケジューラ、バッチ上限、プリフィル分割長を列挙し、各構成について到着率を二分探索する。待ち行列が発散しない最大要求処理率を求め、その値をGPU利用料金で割って「1ドル当たり要求処理率」を比較する。最大処理率の探索ではP99スケジューリング待ち時間5秒未満を容量判定の基準に使う。各構成の探索をCPUコアに並列化することで、GPUを占有する構成総当たりを回避する。

## 評価条件と主要結果

### 実機環境と負荷の定義

| 対象モデル | LLaMA2-7B、LLaMA2-70B、InternLM-20B、Qwen-72B | 小型から70B級までのモデル差を比較 |
| 実機GPU | Azure NC96ads A100 v4、4×A100 80GB/VM。別構成に4×H100 80GB/VM | 各VM内はNVLink接続。未知GPUへは外挿不可 |

| 会話負荷 | LMSys-Chat-1M、中央値入力417・出力141トークン | 短い生成を多数処理する条件 |

| 長出力負荷 | Bilingual-Web-Book、入力中央値2,396・出力中央値3,589。評価時は4Kへ切り詰め | デコードとKV参照が中心 |

| 探索制約 | TTFT P90 < 2秒、TBT P99 < 200ミリ秒、最大16 GPU | サービス品質を満たす1ドル当たり処理率を最適化 |

### シミュレーションの忠実度

| 比較条件 | 指標 | 実機に対する予測誤差 | 読み取れること |
|---|---|---|---|
| 静的・4モデル×3負荷 | P95正規化実行遅延 | 最大3.33% | 待ち時間を除いた反復実行の尾部遅延を高精度に再現 |
| 動的・容量85%・LLaMA2-7B/Arxiv-4K | 中央値正規化E2E遅延 | -8.50% | 小型モデルではCPU負荷等で誤差が大きい条件もある |
| 動的・容量85%・LLaMA2-70B/Chat-1M | 中央値正規化E2E遅延 | +2.46% | 大型モデルでは同じ負荷で誤差が小さい例 |
| 動的・容量85%・Qwen-72B/Chat-1M | 中央値正規化E2E遅延 | +3.29% | モデルごとに誤差符号と大きさが異なる |
| 動的・容量85%・LLaMA2-7B/BWB-4K | P95正規化E2E遅延 | -7.47% | 長出力負荷での尾部遅延も誤差ゼロではない |
| 容量点を超える過負荷 | 要求待ち時間 | 安定した誤差保証なし | わずかな時間予測差で待ち行列が急増する |

ここで正規化遅延は要求遅延を生成トークン数で割った量であり、GPUカーネル単体時間とは異なる。静的負荷ではスケジューリング待ちを除いた実行時間を、動的負荷では到着後の待ちを含む端から端までの遅延を測る。したがって静的P95の3.33%とオンラインの最大8.50%は異なる指標・条件であり、同一の誤差率として混ぜてはならない。オンラインで容量85%を選んだのは、過負荷に近づきすぎると僅かな予測差が待ち行列を発散させるためである。

### 配置探索の実用的な帰結

| 条件 | 指標 | 観測・推定値 | 意味 |
|---|---|---|---|
| LLaMA2-70Bの構成探索 | Vidur-Searchの計算時間 | 96コアCPU約1時間、時間単価約9.93米ドル | 探索そのものにGPUクラスタを専有しない |
| 同じ構成探索の実機総当たり | GPU時間・推定費用 | 約42,000 GPU時間・約218,000米ドル | 実機探索費用との対比であり推論実行速度ではない |
| 4モデル×3負荷の広い探索 | 全探索費用 | シミュレーション約125ドル、実機見積り約114万ドル | 多数のモデル・負荷組合せほど探索節約が効く |
| LLaMA2-70B会話負荷 | 選択された構成 | H100、PP2×TP2、Sarathi-Serve、チャンク512、バッチ256 | 入力・出力が短い負荷で選ばれた一例 |
| Qwen-72B要約負荷 | 選択された構成 | H100、PP1×TP4、Sarathi-Serve、チャンク512、バッチ128 | 同じGPUでもモデル・負荷で並列方式が変わる |
| LLaMA2-70B会話と長出力 | 最適バッチ上限 | 会話256、BWB 64 | 長いデコードでKV容量制約が強まる |
| LLaMA2-70Bで別負荷の最適構成を流用 | 費用比 | 最大2倍 | モデル名だけで構成を固定すると割高になり得る |
| LLaMA2-70B会話負荷 | TBT制約0.12→0.14秒 | 1ドル当たり処理率約0.07→0.13（約1.85倍） | わずかな遅延制約緩和で費用最適点が大きく動く |

同程度のパラメータ規模でもQwen-72Bは多頭注意（MHA）、LLaMA2-70Bはグループ化問い合わせ注意（GQA）を使うため、論文条件ではQwenのKVキャッシュ負荷が約8倍で、推論提供費用が約2倍になる。この比較は「72Bと70Bで重みサイズが似ているから同じGPU構成でよい」という単純な考え方への反例である。ただしモデルの実装、トークナイザ、GPU料金、入力・出力長分布が変われば倍率も変わるため、普遍的な価格比ではない。

## 既存研究との差

Daydream、Habitat、Proteusは深層学習の学習反復を主対象として、比較的安定した計算グラフの実行時間を予測する。VidurはLLM推論に固有のプリフィル・デコードの混在、要求ごとに変わるKVキャッシュ量、到着時刻に依存するバッチ形成、要求単位の遅延分布をモデル化する。演算子を単純に足し合わせるだけでは、待ち行列やメモリ不足による要求再開を再現できない点を重視する。

また、vLLMやSarathi-Serveなどは実際に要求を処理するランタイム／スケジューラであるのに対し、Vidurはそれらの方針を模擬して比較する道具である。Vidur-Searchの成果は、推論中にKVキャッシュを直接圧縮する方式やデコードカーネルを直接高速化する方式とは異なり、**負荷に応じて既存の最適化をどう組み合わせるか**を安価に選ぶ点にある。

## 限界・負の結果・適用範囲

第一に、演算子時間の予測精度は計測したGPU、CUDAカーネル、通信経路に依存する。新しい融合注意、異なるKV配置、非同期通信を導入した場合、既存の時間表をそのまま適用すると予測が崩れ得る。ランダムフォレストは測定点間の補間を助けるが、未測定のハードウェアを正確に外挿する保証はない。公式コードが公開されていても、特定のランタイム版と計測環境で再プロファイルする必要がある。

第二に、論文時点の段スケジューラは同期パイプラインを扱う。非同期通信、系列並列、投機的パイプライン復号は将来課題として挙げられており、そうした方式の実行を本論文の精度結果で保証できない。バッチ形成方針の再現度が低い場合も、カーネル時間が正確でも要求遅延は外れる。

第三に、過負荷付近のオンライン待ち行列は非線形である。最大容量に極めて近い到着率では、シミュレータと実機の処理時間がわずかに違うだけで待ち時間が大きく変わる。著者らが容量85%で評価したことを、容量100%でも同じ誤差上限を保証した結果と読み替えてはならない。

第四に、Vidur-Benchの負荷は公開データ集合の入力・出力長から構成したもので、実運用の複雑なマルチターン文脈再利用、ネットワーク障害、複数モデル混在、エネルギー消費までは十分に実測検証していない。論文ではクラスタの電力・エネルギー指標の追加も将来課題である。さらに探索費用の42,000 GPU時間と218,000ドルは構成総当たりを仮定した見積りであり、実際に同額を支払ったという実績ではない。
