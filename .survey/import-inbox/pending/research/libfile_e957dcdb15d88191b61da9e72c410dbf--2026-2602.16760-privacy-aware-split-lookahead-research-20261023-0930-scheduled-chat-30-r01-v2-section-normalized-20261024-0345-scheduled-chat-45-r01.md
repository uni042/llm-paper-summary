# Privacy-Aware Split Inference：広域ネットワーク越しの層分割推論と先読み復号

## 概要

本研究は、大規模言語モデルの一部の層をローカルGPUで実行し、計算量の大きい中間層をクラウドGPUへ委譲する「層分割推論（Split Inference）」のプロトタイプである。入力トークンをベクトルへ変換する埋め込み層、最後のTransformer層、出力語彙へ戻す言語モデルヘッドをローカルに置くことで、**生のトークンIDと埋め込み表はクラウドへ送らない**。クラウドへ渡すのは中間活性値であり、復号中のKVキャッシュは担当する層のある側で保持する。

問題は、生成の各トークンでローカル→クラウド→ローカルの往復通信が必要になることだ。往復遅延（Round-Trip Time、RTT）が約80ミリ秒の広域ネットワーク（Wide-Area Network、WAN）では、GPUが高速でも逐次生成は通信待ちに律速される。著者はヤコビ反復（Jacobi Iteration）から得たn-gram候補を使う先読み復号（Lookahead Decoding）を組み込み、1回の往復で複数トークンを確定させることで遅延を償却する。Mistral 7BおよびNeMo 12Bで実測し、攻撃者が中間活性から元トークンを推定できる危険性も評価した。

**重要な結論は、トークンを直接送らないことと、入力内容を復元できないことは同義ではない**という点である。著者の逆変換攻撃では、ローカルで2層処理した中間活性から元トークンを約59%回復できた。論文は暗号学的な機密性を証明しておらず、公開モデルの全重みをクラウドが入手できる場合には前提も弱くなる。

## 問題設定

大規模なモデルをクラウドAPIへ全量送信すればローカルGPU容量を節約できるが、入力と出力の機密性が課題となる。逆に全モデルをローカルで実行すればネットワーク上の情報漏えいは抑えられるが、VRAMの小さいGPUではモデルサイズが制限される。層分割推論はこの中間案として、トークン化・埋め込み・最終語彙変換だけをローカルに残す。従来の画像分類向け分割推論と異なり、自己回帰型LLMでは各生成トークンでネットワークを往復するため、RTTの固定費が大きい。

本研究の評価対象は、機密性の構造的境界、通信効率、GPU容量、推論速度、候補トークンの受理率である。目的は完全な暗号化推論の構築ではない。攻撃モデルは「クラウドは割り当てられた計算を正しく実行するが、観測した中間活性から入力を推定しようとする」という半誠実（Semi-Honest）モデルである。クラウドが計算結果を改ざんする、モデル重みを盗む、タイミング情報を悪用するといった能動攻撃は保証範囲外となる。

## 手法

### 1. 非対称な層分割

Mistral 7B Instruct（32層）では、ローカルRTX 3090がトークン埋め込み、層0〜1、層30〜31、RMS正規化、語彙出力ヘッドを実行する。クラウドA100は層2〜29の28層を処理する。NeMo 12B（40層）ではローカルが層0〜1と38〜39、クラウドが層2〜37を実行する。局所層は入力側と出力側に分散するため、入力トークンと出力トークンのどちらも生のIDをネットワークへ渡さない。

中間活性のサイズは7Bで4096次元×float16＝約8KB/トークン、12Bで5120次元×float16＝約10KB/トークンである。埋め込み行列や語彙ヘッドをローカルに置くことは、トークンIDを直接送らないという構造的性質を持つ。しかしクラウドが同一モデルの全層重みを入手できれば中間活性からの復元を試みられるため、著者はローカル側の層・埋め込みを組織固有に微調整する必要性を述べている。これは実装の付随条件ではなく、プライバシー上の主要な前提である。

### 2. 転送プロトコルとKVキャッシュ配置

ネットワーク転送には永続的なWebSocket接続と、長さ4バイトのヘッダ長、JSONヘッダ、float16の生テンソルを連結したバイナリ形式を使用する。ヘッダは形状、生成位置、KVキャッシュの巻戻し位置、必要に応じた注意マスクなどを含む。HTTPとbase64による初期実装からバイナリ転送へ変更することで、符号化と要求ごとの接続処理を削減した。7Bの通常生成では新しいトークンの約8KBだけを往復させ、過去全体の活性やKVキャッシュを毎回転送しない。

クラウド側の中間層のKVキャッシュはクラウド内で保持し、ローカル側の層のKVキャッシュはローカルで保持する。先読み復号で複数候補を検証した後に不採用位置を取り消すため、クラウドのセッション別KVキャッシュには切詰め・位置移動・注意マスク制御が必要になる。これは単に分割したモデルをRPCで呼び出すだけでは実現できない機構である。

### 3. 先読み復号による往復回数の削減

逐次復号は1トークン確定につき1回の往復を必要とする。ヤコビ反復だけで未来の複数トークンを同時更新する方式は、広域ネットワークでは収束までの往復回数が増えてかえって遅くなる場合がある。そこで先読み復号は反復中に現れたn-gram列を候補として蓄積し、後続ステップで複数位置をまとめて検証する。候補が受理されれば、1回の往復で1トークンを超えて確定できる。

このとき推測候補を正しいトークンとして無条件に採用してはいけない。ターゲットモデルの出力と照合し、拒否された候補の後続状態をロールバックする。複数位置を一括処理する際、PyTorchの標準的なis_causal=Trueだけでは既存KVキャッシュとクエリ位置の整列を誤ることがあるため、著者は各推測位置が確定済み位置と自分より前の推測位置だけを見る明示的な注意マスクを構成する。

### 4. 先読みの受理率と通信の交換条件

候補のn-gram長を大きくすると、1ステップで確定できるトークン数は増える可能性がある。しかし候補列の長さが増えるとクラウドの検証計算と送受信量も増えるため、受理率の増加が必ず処理量の増加になるわけではない。約80msのRTTでの実験では、n=3が最も高い平均トークン処理量を達成した。論文は損益分岐となる受理率をおおむね1.15〜1.20トークン/ステップと観察しているが、この閾値は通信環境とモデルの処理費用に依存する。

## 評価

### 評価条件

| 観点 | 条件 |
|---|---|
| ローカルGPU | NVIDIA RTX 3090 24GB、Manjaro Linux |
| クラウドGPU | NVIDIA A100 80GB PCIe、比較用RTX 4090 24GB |
| モデル | Mistral 7B Instruct v0.3、Mistral NeMo 12B Instruct |
| 通信 | 公衆インターネット上のSSHトンネル、往復遅延約78〜85ms |
| 生成方式 | 決定的な最大確率選択（Greedy Argmax） |
| 先読み比較 | 4種類のプロンプト、各2問、100トークン生成、n-gram長3〜7 |
| 速度指標 | 終端間のトークン/秒、ネットワーク・ローカル・クラウドの分解時間 |
| 機密性指標 | 中間活性からのトークン再構成攻撃の上位1位・5位正答率 |

### 主要結果

### 1. 推論速度とネットワーク律速

論文の段階的な最適化表では、初期HTTP+torch.saveの1.4トークン/秒から、バイナリWebSocketで7.8、同じクラウド条件の先読み復号で8.7トークン/秒へ改善する。**1.4から8.7への約6.2倍は、通信形式の改善と復号方式の改善を合算した値**であり、先読み復号単独の高速化ではない。通信形式を揃えた7.8対8.7の比較では約1.12倍である。別のクラウド提供者の経路では逐次復号が10.9、先読みを含む条件で13〜17トークン/秒となるが、提供者のRTTやGPUが異なるため、一つの要因だけに帰属できない。

| 条件 | トークン/秒 | 解釈 |
|---|---:|---|
| HTTP+torch.saveの初期系 | 1.4 | 旧転送方式を含む全体 |
| バイナリWebSocket | 7.8 | 転送方式改善後、逐次復号 |
| WebSocket＋先読み、A100 | 8.7 | 約85ms RTTでの測定 |
| 別提供者、逐次復号 | 10.9 | 通信経路・提供者変更を含む |
| 別提供者、先読み復号 | 13〜17 | プロンプト種類にも依存 |
| ローカルRTX 3090単独（7B） | 約39 | 全層ローカル実行の参照値 |

ローカル単独の約39トークン/秒に比べれば、層分割は依然として遅い。論文の価値は「クラウド分割がローカル単独より高速」という主張ではなく、モデルの一部しかローカルへ置けない場合に、入力を直接送らず実用的な対話速度へ近づけることにある。

逐次復号の内訳は7Bでネットワーク77.4ms、ローカルGPU26.2ms、クラウドGPU15.9ms、直列化1.0ms、合計120.2msである。ネットワークは全体の約64%を占める。12Bではネットワーク78.5ms、ローカル24.4ms、クラウド21.1ms、直列化1.0ms、合計124.7msである。7Bから12Bへモデル規模を増やしても速度低下が限定的なのは、この条件ではGPU計算よりRTTが支配的だからである。

### 2. n-gram長と受理率

| モデル | 方法 | 平均トークン/ステップ | 平均トークン/秒 |
|---|---|---:|---:|
| 7B | 逐次復号 | 1.00 | 8.3 |
| 7B | 先読み n=3 | 1.21 | 9.3 |
| 7B | 先読み n=6 | 1.25 | 9.1 |
| 7B | 先読み n=7 | 1.25 | 8.3 |
| 12B | 逐次復号 | 1.00 | 8.0 |
| 12B | 先読み n=3 | 1.21 | 8.7 |
| 12B | 先読み n=7 | 1.24 | 7.8 |

表は原著の節6.4から抽出した。長い候補は受理数を微増させるが、検証負荷が勝って処理量を下げる。コード入力では7Bのn=5で10.5トークン/秒、逐次8.3に対して1.27倍、12Bでは10.4対8.0で1.30倍だった。一方、12Bの創作文章では7.3対8.0と逆に遅い。論文の速度利得は文章種類によって符号が変わるため、全タスクに同じ倍率を適用できない。

### 3. 先読み復号の品質と数値差

4種類のプロンプトを各200トークン生成する比較で、逐次復号と先読み復号のトークン列は7B・12Bとも完全一致した。ただしログイット（Logit）の数値差はゼロではなく、原著表では最大差29.0（7B）、38.3（12B）、生成列の自己困惑度も逐次と先読みで異なる。著者はfloat16でのバッチ処理と逐次処理の丸め差に起因すると説明する。したがって「貪欲復号で観測されたトークン列が一致した」と「任意の確率的サンプリングで出力分布が厳密に一致する」は別の命題である。後者は本研究で実証されていない。

### 4. 中間活性からのトークン復元攻撃

| 入力側のローカル層数 | 上位1位復元率 | 上位5位復元率 |
|---:|---:|---:|
| 2 | 58.8% | 62.0% |
| 4 | 44.3% | 49.8% |
| 6 | 44.8% | 56.6% |
| 8 | 34.8% | 46.2% |

攻撃は中間活性とトークンIDの対応例から学習した3層MLPで、約1100例を学習・試験へ分けた小規模評価である。データが少なく実行間のばらつきは約±10%と報告される。2層で約59%も復元できることは、構造的にトークンを隠しても機密情報が活性へ残ることを示す。8層では約35%まで低下するが、ゼロにはならない。より強い文脈利用型攻撃や十分な学習データがあれば復元率が上がる可能性があり、この表は安全性の上限保証ではない。

### 5. 実測と推定の区別

12BまでのVRAMと処理量は実機測定である。7BのローカルVRAMは2.0GB、12Bは4.9GBだった。一方、70Bで約9GB、405Bで約20〜36GBというローカルVRAM、70Bで8〜9トークン/秒という先読み速度は**モデルからの推定値**であり、実測ではない。またRTT20msで7Bが18.6トークン/秒になるという値も、RTTと固定費用を分けた回帰モデルからの外挿である。論文はRTTモデルの交差検証誤差を先読みで4.5〜6.2%と報告するが、実際の低RTT環境で同じ速度が保証されるわけではない。

## 限界と安全性上の注意

最大の制約はプライバシー保証の弱さである。クラウドへトークンIDを直接送らない構造は成立するが、中間活性は可逆的な情報を含み得る。特に公開モデルの重みがクラウドから取得できる場合、著者が想定する「クラウドはローカルの埋め込み・初期層重みを知らない」という前提が崩れる。機密情報を扱う実運用では、ローカル層の非公開微調整、深い分割、差分プライバシーなどの追加措置が必要であり、それでも安全性は別途評価すべきである。

性能面では、WANのRTTと提供者の経路構成が主要な律速であり、GPUを高速化するだけでは改善が限定的となる。長いn-gramや確率的サンプリングでは先読みが遅くなる可能性がある。実験のプロンプトは少数で、負荷の高い同時リクエスト、長文脈、多人数共有、障害回復、クラウド悪意行動は十分に検証していない。モデルが大きくなればクラウドのKVキャッシュや多GPU通信も増え、単純なRTT外挿は過大評価になり得る。

## 実装上の含意

この方式は、ローカルGPU容量を抑えつつクラウドの中間層を使う場合、KVキャッシュを層の担当GPUに固定し、ネットワーク転送を活性値だけに限定する設計が有効であることを示す。同時に、先読み復号の価値は受理長だけでなく「1ステップ当たりの通信＋検証費用」とセットで測る必要がある。約80ms RTTではn=3の小さな候補が最良だったため、単純に大きな草稿を投げる設計は不適切である。

RTX 4070 Super 12GB級のローカルGPUに関しては、12Bで4.9GBという実測が容量面で参考になる。ただしその実測はRTX 3090 24GBとクラウドA100の組合せであり、Windows環境・異なるCUDAランタイム・実際のネットワーク条件での再現性を保証しない。構造的プライバシーを暗号化と混同せず、実データ投入前に中間活性の逆変換試験を行うべきである。
