# Mosaic：拡散言語モデルの動的メモリピークを全体計画で抑える長文脈推論基盤

## 概要

Mosaicは、拡散型大規模言語モデル（diffusion-based Large Language Model; dLLM）の長文脈生成で生じる、**鍵・値キャッシュではなく一時活性化が容量の限界になる**という問題を解く推論基盤である。通常の自己回帰型生成では既生成トークンの鍵・値（Key–Value; KV）を保存し、次のトークンでは新しい位置の計算を主に行う。対照的に、拡散型生成は未確定の複数トークンを反復して更新し、双方向注意を使うため、各反復で全系列の中間表現を再計算する。過去KVを長期保持する手法だけでは、この大きな一時メモリを削れない。

著者らは、一時活性化のピークが未確定トークン比率に応じて**語彙全体への出力スコア（logits）**と**前向きネットワーク（Feed-Forward Network; FFN）**の間を移ること、一般的なコンパイルとGPUメモリ割当てが計算グラフを分割し断片化を生むことを観察した。Mosaicは、必要なマスク位置だけの出力スコアを計算する融合カーネル、計算グラフの全体登録、ピークが収まらないときだけ有効化する分割実行、単一の仮想連続領域を用いる全体メモリ計画を組み合わせる。

原著のNVIDIA RTX 3090（24GB）とA100（40GB）、LLaDA-8B、Dream-7B、LLaDA-MoEの評価では、最大対応文脈長（Lmax）を非最適化PyTorch比32.98倍、vLLM移植版比26.74倍、コンパイル版比15.89倍に拡張したと報告する。活性化のピーク対平均比は平均2.71分の1となり、拡散1ステップの遅延も比較条件によって4.12～23.26%低減する。ただし**最大長の検証はダミー入力**であり、その長さで自然言語の生成品質が保たれたことを実証した数値ではない。

## 問題設定と従来方式の不足

### 1. KVキャッシュ主体の管理では一時活性化を抑えられない

自己回帰型言語モデルでは、因果注意のため既生成位置のKVが変化せず、系列長とともに増加する永続KVキャッシュが長文脈時の主要な容量要因になる。ページ単位の注意管理やKVの退避は、この前提に合わせて設計されている。一方、拡散型では一度に多くの位置を処理し、反復ごとに双方向の依存が変化するため、KVをそのまま再利用できない。活性化の再計算、FFNの中間幅、語彙数に比例する出力スコアのテンソルが大きくなる。したがって最適化対象を永続キャッシュから、反復内で生成・消費・解放されるテンソルの生存期間へ移す必要がある。

### 2. 未確定位置の割合で支配的なピークが切り替わる

拡散反復では、未確定位置の割合をマスク率 $r_m$ とすると、FFNは基本的に全系列へ適用されるが、次にトークンを選ぶために必要な出力スコアは未確定位置だけに対応する。$r_m$ が高い序盤では出力スコアが、低い後半ではFFNがメモリのピークになる。原著図3はLLaDA-8BとDream-7Bの128K文脈で、この入れ替わりを示す。FFNだけを常に分割しても、出力スコアが最大の反復ではピークが下がらない。逆も同じである。

### 3. 局所的なグラフ分割と断片化

一般的なPyTorchの動的コンパイルは、演算の互換性や動的形状のために実行を複数の部分グラフへ分けることがある。部分グラフ単位のメモリ再利用では、グラフをまたぐテンソルの生存期間と再利用可能領域を同時に計画できない。さらに割当器が複数の物理セグメントを保持すると、空きメモリの総量が十分でも大きな連続割当てに失敗する。原著図4では32K文脈の予約メモリが理論的ピークを43.19%上回る例が示され、図13の従来方式の予約量膨張率は21.78～78.33%に及ぶ。単純なカーネル高速化ではこの容量制約は消えない。

## 手法：入力から計画、実行までのデータフロー

### 1. マスク位置限定の出力スコア融合カーネル

入力は全トークンの隠れ状態、マスク位置を列挙する添字、および語彙射影重みである。通常の実装は全位置の出力スコアを計算するか、対象位置の隠れ状態を別の連続バッファへ集約してから行列積を行う。前者は不要なスコアを保存し、後者は集約用の大きな中間バッファを必要とする。

Mosaicは**散在位置の収集と行列積を融合（gather–GEMM fusion）**する。各GPU計算単位はマスク添字から元の隠れ状態を間接参照し、タイルをオンチップ領域へ読み込み、語彙射影との積を計算して対象位置の出力スコアだけを作る。処理済みのタイルは大域メモリに残さず破棄する。結果として出力スコアの要素数は全トークン数ではなく未確定トークン数に依存し、集約バッファの追加割当ても避けられる。原著はこの冗長計算削減が4.12～23.26%のステップ遅延短縮に寄与すると説明する。

### 2. 全体グラフ登録と生存期間の明示

全体メモリ計画に必要な入力は、演算の依存関係、テンソルの大きさ、生存開始と最後の使用位置である。Mosaicのグラフ登録器（graph registrar）は、`add_op` による演算登録、`add_alias` による入出力の同一領域指定、`add_barrier` による分割ループ中の入力保持などの記号的操作で、モデルのグラフを明示する。系列長のような入力依存の寸法は記号変数として保持し、要求到着時に具体化する。

この仕組みによって、動的なグラフ分割を挟まずに全演算の生存期間を一括解析できる。`add_barrier` が重要なのは、FFNや出力スコアを複数チャンクに分割した際、次チャンクでまだ必要な入力を早期解放しないためである。演算の単なる並び替えではなく、**どのテンソルをいつ上書きしてよいか**を安全に決めるための契約を登録している。

### 3. メモリ不足時だけ動かす遅延チャンク化

分割最適化器（lazy chunking optimizer）は、通常はFFNと出力スコアのチャンク分割を無効にしておく。要求の系列長・マスク位置数・使用可能メモリを観測し、分割しない計画でメモリが収まらないときだけ探索を開始する。候補設定は出力スコアのチャンク数 $K_{logits}$ とFFNのチャンク数 $K_{FFN}$ である。

探索では登録済みグラフに候補チャンク数を代入し、全体メモリ計画器で必要ピークを算出する。その時点でピークを作っている演算が出力スコアなら $K_{logits}$、FFNなら $K_{FFN}$ を1つ増やして再評価する。ピークが容量以内になれば停止し、分割できない他の演算が下限ピークとなって収まらなければ実行不能と判定する。**支配的でない演算を分割しても最大ピークが下がらない**という性質を使い、全組合せ探索を避ける。得られた設定は同じ要求の実行へ適用される。

分割の遅延費用は文脈長に依存する。原著図9では32K文脈を4チャンクに分けた場合、出力スコアの追加遅延は0.5%未満、FFNは2%未満だった。短い文脈では起動回数の増加が目立つため、分割を常時有効にするより必要時だけ使う設計が合理的である。ただし「分割は常に無償」という意味ではない。

### 4. 単一要求計画と仮想メモリ管理

全体メモリ管理器（global memory manager）は、要求に具体化した演算グラフの生存期間を分析し、各テンソルにワークスペース内のオフセットとサイズを割り当てる。生存期間が重ならないテンソルには同じ領域を再利用できる。理論上の最適配置は難しい組合せ問題だが、著者は最初に入る空き領域へ配置する先着適合（first-fit）を採用し、整数線形計画（Integer Linear Programming; ILP）による厳密解より低い計画費用を得る。

GPU側では仮想メモリ管理（Virtual Memory Management; VMM）を使う。起動時には大きな連続**仮想アドレス範囲**だけを予約し、要求ごとのピーク計画が確定してから必要な物理ページをその範囲へ結び付ける。短い要求にまで最大容量の物理メモリを事前占有しない。実行時には出力テンソルを新規確保する標準演算を、計画されたオフセットへ直接書き込むその場更新演算に置き換える。Dream特有の出力スコアのシフトと連結もトークン単位の省メモリ操作へ変える。これにより、全体で再利用可能な領域を確保しながら外部断片化を抑える。

### 5. オフラインとオンラインの境界

モデルごとに記号的グラフを登録するのはオフライン段階である。オンラインでは要求の系列長とマスク率を受け、チャンク設定を選び、単一ワークスペースの配置を計算し、物理ページを結び付けて実行する。元のvLLMの通常の自己回帰KVキャッシュ機構をそのまま使うのではなく、著者は公式PyTorchモデルをvLLMへ組み込み、拡散反復ごとのスケジューリングと可変長実行を追加した。したがって、Mosaicの実験結果を標準のvLLMの機能・性能として一般化してはならない。

## 評価結果と構成要素除去

### 1. 最大対応文脈長と遅延

| 条件・指標 | 比較対象 | 提案方式の結果 | 解釈 |
|---|---|---|---|
| 最大対応文脈長 $L_{max}$ | Native | 32.98倍 | 最適化前PyTorchに対する比。一般的な長文脈正答率の倍率ではない。 |
| 同 $L_{max}$ | Mosaic-Torch | 26.74倍 | vLLM移植の有無を揃え、メモリ最適化の効果を比較。 |
| 同 $L_{max}$ | Mosaic-Compile | 15.89倍 | 一般的なコンパイル最適化を追加した実装との比較。 |
| 活性化のピーク対平均比 | 従来方式 | 平均2.71分の1 | 分割とマスク限定計算により瞬間的な容量要求を平滑化。 |
| 1ステップ遅延、Dream・$r_p=0.1$ | Mosaic-Torch/Compileとの図11比較 | 平均4.12%短縮 | 低減が小さい側の代表例。 |
| 1ステップ遅延、LLaDA-MoE・$r_p=0.9$ | 同上 | 平均23.26%短縮 | 低減が大きい側の代表例。 |

32.98倍、26.74倍、15.89倍は**異なる比較対象に対する倍率**であり、足し合わせる数値ではない。最大文脈長を延ばす主因は、FFNまたは出力スコアのピークを要求時に分割し、同時に断片化を抑えたことである。遅延が改善した主因は、未確定でない位置の語彙射影を省くことと、動的グラフ取得に伴う費用を避けることにある。長い系列に対応できることと、1ステップが速いことは別の指標である。

### 2. 構成要素を順次追加した容量への寄与

| 累積導入の段階 | 原著図14で報告する $L_{max}$ の改善範囲 | 効き方 |
|---|---:|---|
| 全体メモリ管理器を追加 | 79.0～197.1%増 | 断片化を抑え、生存期間の異なる活性化を同一領域で再利用。 |
| マスク限定スコアを追加 | さらに88.9～114.3%増 | 既確定位置の巨大な語彙射影を作らずに済む。 |
| 遅延チャンク化を追加 | さらに221.3～673.3%増 | 最終的なメモリピークをFFN・出力スコアの分割で低下させる。 |

この表は段階的な構成要素除去実験の結果であり、各行を独立した同一基準の加算効果として読んではならない。分割可能なピークを下げた後は、分割できない演算のメモリが下限を決める。大きな倍率は主に最大長の能力改善であり、生成処理量の倍率ではない。

### 3. 探索・計画方式の比較と負の結果

遅延チャンク化を短い文脈でも常時使う固定分割方式（Mosaic-FC）に対し、必要時だけ分割するMosaicは32K以下の評価範囲で5.5～21.5%の遅延を短縮した。これは短文脈では分割のカーネル起動費用が無視できないことを示す。オンラインで全チャンク数の組合せを総当たりするMosaic-BFに対して、ピーク要因だけを増分探索する方式は同じ最大対応長を達成しながら、探索遅延を総当たりの0.28～0.32%に抑えた。短文脈の全体遅延では22.3～70.7%の低減が報告される。

メモリ配置を整数線形計画で最適化するMosaic-ILPに対し、先着適合方式は同じ最大対応長を得ながら、計画遅延をILPの0.1～4.3%へ下げ、全体遅延を7.1～36.7%短縮した。厳密な最適配置の計算費用が大きく、**より複雑な計画器が必ずしも推論全体に有利ではない**という負の結果である。著者の説明では、十分に分割した後のピークは非分割演算が決めるため、厳密配置と先着適合の最大長が一致しやすい。

### 4. 評価から言えること・言えないこと

測定は、単一GPUでの一時活性化の容量と拡散1ステップの実行遅延に焦点を当てる。論文が示す最大長は、通常のモデル訓練長を超えた**メモリ上の到達可能性**である。ダミー入力を使うため、超長文脈での指示追従、コード生成の正しさ、意味的一貫性、長い回答の最終品質が維持されると実証したものではない。また同時接続数を増やしたときの待ち時間、複数GPU間の転送、実サービスでの総要求処理量やエネルギー削減の数値を直接示していない。本文中の「品質を損なわない」は、主に出力スコアの不要位置を省き、同じ計算を分割することで数学的に同等の処理を目指す設計上の主張として理解すべきである。

## 既存研究との位置づけ

ページ単位のKV管理は、自己回帰型の過去KVが再利用可能という前提で有効である。Mosaicは拡散型の反復でKVが変わり、一時活性化が毎回再計算される前提へ最適化対象を移した。従来の一般的な生存期間解析や `torch.compile` はグラフが部分的に切れると全体再利用の機会を失う。Mosaicは記号的グラフを明示し、必要に応じてFFN・出力スコアを分割し、その分割を含む全体生存期間を計画する点に特徴がある。

重要なのは、Mosaicが「量子化で重みを小さくする」「過去のKVを圧縮する」「投機的復号で次の複数トークンを予測する」方式ではないことである。メモリ容量の主な削減対象は**一時活性化と出力スコア**であり、出力を生成するアルゴリズムを変更して予測分布を近似する手法ではない。この違いから、自己回帰型のKV退避・圧縮と同じベンチマークの倍率で直接比較するのは不適切である。

## 限界・実装時の注意

第一に、著者の最大長測定は学習時の文脈長を超えるダミー入力で行われた。メモリ不足にならず計算できることと、自然言語でその長さを有効利用できることは別である。超長文脈での正答率や推論品質、実際の長文書入力での性能を確認するには追加の評価が必要になる。

第二に、対象GPUはRTX 3090 24GBとA100 40GB、モデルはLLaDA-8B、Dream-7B、LLaDA-MoEである。異なる語彙数、FFN中間幅、マスク更新規則、GPUメモリ階層では支配的なピークと適切な分割設定が変わる。RTX 4070 Super 12GBや分散GPUで同じ最大長倍率が得られるとは断言できない。

第三に、分割は短い系列で追加起動費用を持つ。必要な場合だけ分割する方針がこの問題を緩和するが、オンライン探索、メモリ計画、仮想ページの結び付けにも費用がある。これらを含めたサービス全体の要求処理量、尾部遅延、複数要求の競合は論文の主要評価対象ではない。

第四に、記号的グラフ登録、分割に合わせた生存期間制約、独自のその場更新演算、仮想メモリ割当ては、既存モデルをそのまま呼び出すだけでは得られない。公式実装はvLLMの基盤を使うが、通常のKVキャッシュ経路を迂回する拡散型固有の改造が必要である。最新版のvLLMへ統合するときには、グラフの互換性、メモリ割当てAPI、モデルの演算変更、テストによる出力整合性を個別に検証する必要がある。

第五に、分割できない演算がメモリ下限を決めるため、チャンク数を無限に増やしても最大文脈長を無制限に延ばせない。仮想アドレス予約は物理メモリの増設ではなく、限られた物理ページを断片化させずに利用する仕組みである。モデル重みの容量と非分割演算のピークがGPU容量を超えれば実行不能になる。
