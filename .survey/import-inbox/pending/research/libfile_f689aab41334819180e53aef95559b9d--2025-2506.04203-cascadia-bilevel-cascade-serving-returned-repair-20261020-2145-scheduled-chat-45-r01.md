# Cascadia：モデルカスケードの要求振分けとGPU配置を共同最適化する配信基盤

## 概要

Cascadiaは、複数の大規模言語モデルを小さい順に組み合わせ、簡単な要求を小型モデルで完了し、難しい要求だけを大型モデルへ進めるカスケード型推論基盤である。小型モデルは速く安価だが難問では回答品質が落ちる。大型モデルは品質を高められるがGPUメモリと演算資源を多く使う。単に品質閾値で要求を振り分けるだけでは、実際の要求数や入力・出力長に合わせたGPU配置ができず、一部のモデルが過負荷になる。

Cascadiaの新規性は、要求振分けの閾値と、各モデルに割り当てるGPU数・並列化方式を同時に計画する点にある。配置側は混合整数線形計画（mixed-integer linear programming、MILP）を用い、データ並列、テンソル並列、パイプライン並列の組合せとGPU数を決める。振分け側はチェビシェフ誘導の品質制約付き探索で、どの要求を次の大型モデルへ進めるかを決める。振分けが変わるとモデルごとの負荷が変わり、配置を変えると各モデルの遅延が変わるため、両者を交互に最適化する。

原著は32基のNVIDIA H100 80GBを用い、DeepSeek蒸留7B/70BとDeepSeek 671Bの3段カスケードを評価した。単一モデルのSGLang配信と比較して、95%の要求が期限を守るために必要な遅延期限を最大4倍厳しくでき、処理量を最大5倍に増やした。既存のカスケード基盤CascadeServeとの比較では、遅延期限を最大2.5倍厳しくし、処理量を最大3.3倍に増やした。ただしこの倍率は、品質要求、負荷系列、比較基盤によって異なり、単一の設定で全指標が同時に最大改善したという意味ではない。

## 問題設定：振分けと配置の相互依存

モデルカスケードでは、入力要求を最初の小型モデルで処理し、判定器が回答品質を閾値以上と評価すればそこで終了する。閾値を厳しくすると大型モデルへ進む要求が増え、品質は改善するがGPUの負荷と遅延も増える。逆に閾値を緩くすると小型モデルで完了する要求が増える一方、難しい質問に対する品質が下がる。要求の難しさと回答品質の分布は、数学、コード生成、一般対話などの負荷で異なる。

配置側の問題は、同じGPU数でもモデルの大きさと入出力長によって最適な並列度が変わることである。入力の長い要求は事前入力処理（prefill）の計算が重く、出力の長い要求は逐次復号（decode）のメモリ帯域が支配的になる。671Bのモデルは単一GPUに収まらないためモデル並列が必要であり、7Bモデルは複製によって同時要求を増やせる。GPUを全モデルへ均等配分すると、重いモデルが待ち行列を形成し、軽いモデルに遊休資源が残る。

従来のCascadeServeは到着率などの負荷に基づきモデル配置と振分けを調整するが、Cascadiaは入力・出力長の分布、モデル規模、要求の品質分布、並列化方式を一緒に扱う。最適化するのは単一モデルのトークン毎秒だけでなく、カスケード全体の95百分位遅延と品質条件である。品質が満たされない高速な構成を選ばないことが重要になる。

## 手法：二層最適化の全体手順

### 1. 振分け閾値からモデル別負荷を推定する

カスケードのモデルを小さい順に `c_1, ..., c_C` とし、モデルiの回答を採用する品質閾値を `h_i` とする。すべての要求はまず `c_1` に入り、回答が閾値に届かなければ `c_2` へ進む。最後のモデルには次段がないため、閾値はC-1個である。これらの閾値をまとめたベクトルθが振分け方針となる。

論文の実装は、入力負荷から標本を取り、各モデルの回答品質の分布をあらかじめ評価する。任意の閾値θを仮定したとき、どのモデルが最終回答を担当するかを推定し、モデル別の到着率と入出力長の分布 `W={w_1,...,w_C}` を得る。これが配置最適化への入力になる。標本に含まれない難問が急増した場合には推定が外れるため、後述の再計画が必要になる。

### 2. GPU数と並列化方式を選ぶ配置ソルバ

配置ソルバは、総GPU数Nとモデル別負荷w_iを入力し、モデルiに何基のGPUを割り当てるかを決める。各モデルについて実行可能なGPU数fを列挙し、そのfでデータ並列（DP）、テンソル並列（TP）、パイプライン並列（PP）の候補を探索する。モデルを複数複製する場合は、複製ごとにTP×PPのGPU数を足し合わせ、割当fを超えない構成だけを許す。大規模モデルでは重みがGPUメモリに収まらない構成を除外する。

候補構成の95百分位遅延はScratchpad系の推論シミュレータで推定する。論文は入力長・出力長・到着率、バッチ化、待ち行列、並列度を考慮する。各モデルとGPU数fについて最良の並列化構成と遅延 `l_i(f)` を表に保存し、MILPの入力とする。つまりMILPが毎回GPUカーネルを実行して測定するのではなく、事前に求めた性能表から資源配分を選ぶ。

### 3. 混合整数線形計画による資源配分

二値変数 `x_{i,f}` はモデルiへf基のGPUを割り当てる場合に1とする。各モデルは一つの割当だけを選び、総割当が利用可能なGPU数Nに一致する制約を課す。全体の遅延Lは各モデルの推定遅延以上とし、目的をLの最小化にする。これにより、最も遅いモデルの待ち時間を抑える配分を求める（原著§3.2）。メモリ不足で実行できない組合せはx=0に固定する。

この方法の利点は、最適化の前にモデルごとの並列度を変えた性能を評価し、要求数が多いモデルへGPUを重点配分できることにある。一方、候補表の精度はシミュレータに依存する。通信帯域、GPU種類、モデルの演算特性が実機とずれると、MILPが数学的に最適でも実運用の最適構成とは限らない。

### 4. 品質制約付きの閾値探索

振分けソルバは、配置ソルバから得た遅延 `L(θ)` と、判定器が推定した品質 `Q(θ)` を使う。品質下限を `q_min` とすると、目的は概ね `J(θ)=L(θ)+μ max(0,(q_min-Q(θ))/(z_1^*-z_2^*))` である（原著§3.3）。分母は最大モデルのみを使う場合と最小モデルのみを使う場合の品質差で、異なる負荷で品質罰則の尺度をそろえる。μは品質下限を破る候補へ課す罰則の重みである。

このチェビシェフ誘導の探索では、単に品質と遅延の加重平均を最小化するのではなく、品質下限を破った構成へ罰則を与える。閾値を更新するとモデルごとの負荷が変わるので、配置ソルバを再実行して遅延を計算し直す。論文のAlgorithm 1は、標本負荷から品質・負荷分布を計算し、配置を求め、閾値を更新する操作を繰り返し、評価値が一定回数安定したところで終了する。

### 5. 実行時の振分けと再計画

最適化で得たθは要求の受付時に使う閾値であり、GPU配分・並列度は対応する配置計画である。推論時に各要求ごとにMILPを解くのではない。負荷分布が変化したときに新しい標本を集め、配置と閾値を再計算する。原著の実装例では5分ごとに50要求を標本化し、到着率や複雑さの変化が大きければ再計画を実行する。

この設計はモデル別の負荷の偏りを減らせるが、再配置にはモデル重みの移動、GPU割当変更、実行中要求の処理などの運用費用が生じ得る。論文は最適化計算時間と負荷変動時の性能を評価しているものの、任意のクラスタで重み移動や再配置が無償になると保証するものではない。品質判定器の呼出し費用も残る。

## 評価条件と比較対象

| 項目 | 一次論文の条件 |
|---|---|
| GPU | 4台のサーバ、各8基のNVIDIA H100 80GB、合計32基。サーバ内NVLink、サーバ間InfiniBand。 |
| モデル | DeepSeek蒸留7B、蒸留70B、671BのINT4 AWQ。別実験でLlama3-8B/70B。 |
| 判定器 | GPT-4oによる回答品質の0〜100点評価。判定器の遅延を実験に含める。 |
| 負荷 | MT-Bench由来の複数の要求系列。数学・コード・推論など、入出力長と難しさが異なる。 |
| 品質下限 | 70、80、85、90など。閾値と配置の最適解は品質下限に依存。 |
| 比較対象 | SGLang上の単一モデル、既存カスケード基盤CascadeServe。単一モデルにも並列化探索を適用。 |
| 主指標 | 95%の要求が期限を守るためのSLO Scale、処理量。SLO Scaleは単発要求の基準遅延を何倍に緩めるかを表す。 |
| 配置計画 | Scratchpad系シミュレータ、DP/TP/PP候補、MILP、チェビシェフ誘導の反復。 |

SLO Scaleが小さいほど厳しい期限で95%の達成率を維持できる。例えば基準のSLO Scaleが12で提案が3なら、提案の方が4倍厳しい期限を守れるという意味であり、平均要求遅延が必ず4分の1という意味ではない。判定器の品質スコアは人手正解率と同一ではなく、GPT-4oの評価分布に依存する。

## 主要結果：単一モデルおよび既存カスケードとの比較

原著§4.2では、単一モデル配信との比較でSLO期限を最大4倍、平均2.8倍厳しくでき、処理量は最大5倍、平均3倍と報告する。既存CascadeServeとの比較では、SLO期限は最大2.5倍、平均1.7倍、処理量は最大3.3倍、平均1.7倍である。一方、要旨と導入部の総括は「平均2.3倍の厳しいSLO、平均2.4倍の処理量」と記載する。平均値の集計範囲・比較対象が本文の内訳と明確に一致しないため、本稿では本文の比較対象別の数値を優先し、要旨の平均を同じ条件の数値として混ぜない。

具体例として、負荷系列3・品質下限85では単一DeepSeek-671Bが95% SLO達成のため11.88のSLO Scaleを要する一方、Cascadiaは3.75で済む。約3.17倍厳しい期限に相当する。負荷系列1・品質下限90ではCascadeServeの17.3に対しCascadiaは11.73で、約1.47倍厳しい期限を守れる。これらは図5に示された個別条件であり、すべての要求で同じ改善率が得られるわけではない。

モデル系列をLlama3-8B/70Bに変えた比較では、基準方式に対して最大3.8倍、平均2.6倍の改善を報告する。入力処理を分割するSarathi-Serveとの比較でも、対象条件では最大1.95倍、平均1.64倍の性能差を報告した。ただし各比較は別の実験条件であり、DeepSeek系列の最大5倍とLlama系列の最大3.8倍を同一の負荷で比較した結果ではない。

## 配置と振分けが連動することの実証

負荷系列1・品質下限90では、カスケードの3モデルが全要求の100%、94%、50%をそれぞれ処理し、GPUは4、8、20基に配分された。品質下限を85へ下げると、最大モデルが処理する割合は50%から21%へ減り、最大モデルの割当も20基から16基へ減った。品質閾値を緩めた結果、GPU配置も小型・中型モデル側へ移す必要があることを示す。

同じ負荷系列1・品質下限90で中型モデルにDP=2、TP=4を採用した構成を、DP=4、TP=2へ変更すると性能が33.7%低下した。品質下限85では中型モデルの最適な並列度がDP=6、TP=2へ変わる。つまり、ある負荷で最適だった並列度を品質条件の異なる負荷へ固定して使うことはできない。

構成要素除去実験では、モデルごとの並列度探索を一律の方式へ置き換えると性能が最大1.6倍、平均1.4倍悪化した。GPU配分を均等配分へ置き換えると最大2.1倍、平均1.7倍悪化した。負荷系列1・品質下限90では671Bに本来20基を配分するところ、均等配分では12基になり、最大モデルが律速となる。これらは並列度とGPU数の最適化に独立した寄与があることを示す。

## 計画計算の費用と変動負荷への適応

最適化計算は12コアCPUで、32基GPUの構成では20秒以内、80基GPUの構成でも1分以内に終了したと報告される。GPU推論の各トークンに対して20秒の追加費用がかかるのではなく、負荷分布が変わった際に配置計画を更新する費用である。頻繁に負荷が変わる環境では再計画の頻度と配置変更の実行費用を考慮する必要がある。

オンライン変動の評価では、負荷系列1→2→3を8分、16分、10分の区間で切り替え、品質条件を変えながら再計画する。Cascadiaは基準方式に対して最大4.4倍、平均2.2倍の性能改善を報告した。再計画が全ての負荷変化を予見するわけではなく、5分ごとの標本化と変化検出には遅れがある。急な瞬間バーストや、標本に現れない新しい要求種類に対する保証は別問題である。

## 限界・負の結果・適用判断

第一に、品質評価はGPT-4o判定器の0〜100点を基準とする。判定器のバイアス、別モデルによる判定、真のタスク正答率の差は分離して検証されていない。品質下限を満たすといっても、実際の利用者が求める品質を厳密に保証するわけではない。第二に、評価したのは32基のH100を中心とするGPU群であり、RTX 4070 Superのような単一GPUや低速なネットワークへそのまま移すことはできない。

第三に、MILPの遅延は性能シミュレータに依存する。モデル重みの配置、メモリ不足、TP/PPの通信、待ち行列を現実に近く再現できなければ、計画の性能予測は外れる。第四に、各要求が複数モデルを順に通るカスケードでは、途中モデルの回答生成と判定器の費用が発生する。小型モデルで終了する要求が少ない高難度負荷では、カスケードの余分な計算が不利になる可能性がある。

第五に、再計画は20秒〜1分程度の計算を要する。要求分布が秒単位で大きく変化する場合、計画が負荷変化に追従しない可能性がある。第六に、品質下限を厳しくしすぎれば大型モデルへ進む要求が増え、最適化してもGPU資源の限界を超え得る。第七に、本文と要旨で平均改善倍率の集計値が一致しないため、導入時の性能見積もりには各負荷条件の図と評価対象を参照する必要がある。

本研究は、推論要求の経路選択とGPU資源配分を一体化したモデルカスケード配信の論文として有用である。単純な要求ルーティングの精度だけでなく、入力・出力長、到着率、モデル規模、並列度、GPU数、品質下限を同じ計画へ入れる点が中心的な貢献である。一方、単一モデルの注意カーネルやKVキャッシュ圧縮そのものを高速化する方式ではなく、複数モデルを所有して配信する大規模基盤向けの設計である。
