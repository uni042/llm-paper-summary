# Judge Q: Trainable Queries for Optimized Information Retention in KV Cache Eviction

## 概要

長いプロンプトを扱うLLMでは、各Transformer層に保持するkey/value（KV）キャッシュが系列長に比例して増える。KV evictionは、以後の生成で重要でないと推定した位置を削除し、一定の保持トークン予算内で生成品質を保とうとする技術である。しかし、何を「重要」とみなすかは実際に生成されるトークンに依存する。従来のSnapKV、H2Oのprefill版、PyramidKVなどは入力末尾のqueryを使って過去位置を採点するため、質問が末尾にない入力や複数の離れた証拠が必要なタスクで、局所性バイアスが生じやすい。

Judge Qは、**将来生成する応答が入力のどこを見るか**を小さな学習可能query群で近似する。事前に応答トークンの注意分布を教師として用意し、プロンプト末尾へ付けるsoft tokenのembeddingだけを学習する。推論時には同じsoft tokenを付けて一度prefillし、soft tokenから入力全体への注意を集計してKVを削除し、soft token自体は破棄する。既存のattention重みや本体Transformerを再学習せず、削除位置の選択を改善する設計である。

重要なのは、**キャッシュの保持数を増やして品質を上げる手法ではない**点である。論文の主評価は同じKV保持数における正解率・タスクスコアであり、追加soft tokenによるprefill計算を含めた実機のTTFT、TPOT、メモリピークやスループットの改善を実証したものではない。

## 問題設定

### 末尾window依存の重要度推定

入力長をN、保持可能なKV位置数をBとすると、prefill時の静的削除はN個の候補からB個を選択する問題である。H2O系の注意集計、SnapKVのwindow観測とpooling、PyramidKVの層別予算はそれぞれ重要度推定を工夫するが、観測queryが末尾付近に偏れば、入力前半にしか現れない証拠やグローバルな関連を見落とす。冒頭に質問を移動したLongBench Single-QAのプロンプト変形実験（原著Figure 2）では、従来手法の劣化が強まる。これは削除対象がタスクに依存することを示す観察であり、すべての実際のユーザープロンプトで同程度の劣化が起こるとの証明ではない。

著者は、**実際の出力応答を既に知っていると仮定**し、その応答トークンのqueryを使って入力KVの重要度を評価すると、削除品質が大きく改善することを示す。原著Table 1でLlama-3.1-8B-InstructのLongBench平均は、Full KVが41.23、将来の応答を用いたFull KV-genが保持128/256/512で38.27/39.29/39.80である。一方、SnapKVは34.31/36.56/38.31。Full KV-genは未来情報を使う非実用のoracle比較であり、実行可能なJudge Qの結果と混同してはならない。またoracleの結果もFull KVの41.23には届かない。

### 生成応答の注意分布を学習する理由

最終的にKVを利用するのは生成時queryなので、学習時だけ利用できる応答を教師にして、推論時に観測可能な代理queryを作ればよい。単に先頭・末尾位置を保存するヒューリスティックとは異なり、生成のために必要な情報を、入力全体から抽出することが目的となる。ただし生成内容の分布が学習データと異なれば、代理queryの有効性は低下しうる。これは生成前の削除判断であり、将来のqueryが変化するオンライン環境を追跡する方式ではない。

## 手法

### 1. Soft tokenを語彙へ追加

モデルの語彙にn個の特殊な学習可能soft tokenを追加する。原著の実験ではn=32を選び、モデルの既存パラメータを固定して追加tokenに対応するembedding行のみ更新する。大きなTransformer全体のfinetuningを要しないため、学習可能パラメータは小さい。ただし推論時にはsoft tokenを実際に追加してforwardするので、追加トークン処理が完全に無料になるわけではない。token数を減らしすぎれば生成分布の表現力が下がり、増やしすぎれば学習・prefillコストが増える。

### 2. 応答分布と代理分布の整合

学習用データはpromptと、そのpromptに対してモデルが生成したresponseの組である。別々に`Concat(prompt, soft tokens)`と`Concat(prompt, response)`を作り、soft tokenおよび応答tokenから元のprompt位置へ向く注意をそれぞれ計算する。soft token方向と応答token方向で平均を取り、入力位置ごとの注意マップA_soft、A_respを得る。原著Eq.(3)〜(5)は両者の平均二乗誤差を最小化する。形式的には`L = mean((A_soft - A_resp)^2)`である。

応答tokenは教師分布を作るためにのみ必要で、サービス時の推論には入力しない。教師はモデルが自ら生成した応答に由来するため、正解ラベルそのものを蒸留しているわけではない。重要な情報の定義は、あくまで**当該モデルの応答時の注意**に依存する。生成モデルが誤った根拠へ注意する場合、それを教師として模倣する限界がある。

### 3. Prefill時のKV選別

推論ではprompt末尾へ学習済みsoft tokenを付け、そのsoft tokenのqueryから元の入力位置への注意マップを算出する。各入力位置の重要度を集計し、予算Bの上位位置に対応するkey/valueを保持する。選別後、soft token自身はキャッシュから取り除き、元のpromptの末尾から通常の自己回帰生成を継続する。したがって追加tokenを最終回答へ表示するものではない。

各層で同じ予算・選別条件をどう適用するかは既存の静的削除手法と合わせて実装される。原著は比較対象のlocal windowを32とし、Judge Qのsoft token数も32に揃えている。ただし「32個のsoft tokenを追加する」と「全層で32個のKVだけを保持する」は別であり、表のKV cache budget 128/256/512とは混同しないこと。

### 4. Oracleとの一致率による説明

原著Eq.(6)は、実際の応答を使って選んだKV位置集合I_respと、評価対象手法が選んだI_curの共通部分割合`|I_cur∩I_resp|/|I_resp|`をcritical key-value hit rateと定義する。これはモデルの最終正解率ではなく、未来情報を使う参照選択にどの程度近いかを示す補助指標である。原著Table 4では予算128/256/512でSnapKVが53.44/55.23/58.46%、Judge Qが61.37/62.34/65.06%。改善はそれぞれ7.93/7.11/6.60ポイントで、少なくとも評価された予算ではproxy queryが重要位置をよりよく近似している。

## 評価条件

主評価モデルはLlama-3.1-8B-InstructとMistral-7B-Instruct-v0.3。学習データはShareGPTの50,000サンプル（common 45,000、computer 5,000）から作り、promptとモデル生成responseを対応させる。比較はStreamingLLM、prefill対応のH2O、SnapKV、PyramidKVであり、LongBench、RULER、Needle-in-a-Haystackを使用。RULERでは8,192および32,768トークンの入力、KV保持数256/512/1,024を評価し、Table 3のテストサンプル数は100。Needleでは4,000〜32,000トークンを対象に証拠位置を10%刻みで動かす。

LongBenchのTable 2では、単一文書QA、多文書QA、要約、few-shot、合成タスク、コードなどをまとめた平均を掲載している。異なるタスク指標の単純平均であり、すべてのタスクで同一方向に改善するという意味ではない。生成継続の補助評価ではDeepSeek-R1-Distill-Llama-8Bを用い、MATH-500とAIME24を調べる。学習データ品質の実験はLlama-3.2-1B-Instructを使い、soft token数を変えた検証は5,000サンプルで行う。

## 評価結果

### 1. LongBench：同一保持予算での比較

Llama-3.1-8B-Instructの平均スコアはFull KVが41.23。保持128ではStreamingLLM 30.50、H2O 33.67、SnapKV 34.31、PyramidKV 34.08、Judge Q **35.90**。保持256では31.79/34.37/36.56/36.00に対しJudge Q **37.69**。保持512では32.64/35.30/38.31/37.58に対し**39.17**。SnapKVに対する差はそれぞれ+1.59、+1.13、+0.86ポイント。少予算ほど改善幅が大きいが、Full KVには及ばない。

Mistral-7B-Instruct-v0.3ではFull KVが46.01。保持128でSnapKV 39.75、Judge Q **42.38**（+2.63）。保持256では42.31対**43.51**（+1.20）、保持512では44.04対**44.48**（+0.44）。ここでも保持数が増えると差が縮小する。原著本文の「最大約2.6ポイント」はこの条件と整合する。

### 2. RULER：入力長と保持数の交差

Llama-3.1-8B、入力8,192・保持512のTable 3ではFull KV 87.18、SnapKV 62.76、PyramidKV 61.19、Judge Q **69.24**。SnapKVとの差は+6.48ポイントであり、Full KVとの差は17.94ポイント残る。入力32,768・保持512ではFull KV 78.82、SnapKV 57.87、Judge Q **63.08**（+5.21）。保持1,024でも67.55対61.64（+5.91）と差が残る。

Mistral-7B、入力8,192・保持256ではFull KV 81.87、SnapKV 42.44、Judge Q **52.72**（+10.28）。入力32,768・保持512ではFull KV 73.46、SnapKV 33.05、Judge Q **40.83**（+7.78）。大きな差がある一方、Full KVの品質からはかなり下がっている。原著の「3ポイント以上」は複数条件で成立するが、ベースラインの品質損失をゼロにするものではない。

### 3. Needle-in-a-Haystackと長い生成

原著Figure 4では、4K〜32Kの長さと異なるneedle深さを組み合わせた検索性能のヒートマップを示し、Judge Qが比較法より広い条件で成功する。図に数値表がない箇所を正確な成功率として再構成しない。Figure 4は品質指標であり、速度測定ではない。

DeepSeek-R1-Distill-Llama-8Bの生成継続実験（Table 5）は、MATH-500でSnapKV 52.4に対しJudge Q **55.0**、AIME24で31.1対**37.8**。ただしこの実験は一度生成した回答の一部を使ってKVを削除した後に続きを生成する特殊な設定で、オンライン運用での長時間安定性を直接示すものではない。保持予算はMATH-500で1,024、AIME24で3,072とし、平均出力長の25%を目安にしている。

### 4. アブレーションと失敗条件

Figure 5のデータ品質比較では、元データのreference responseよりモデル生成responseを教師にした方が良い。またWikipedia、GitHub、C4からのデータよりShareGPTを使う方が良いと報告する。教師の生成品質とドメイン分布が重要である。soft token数は32付近が学習費用と汎化の均衡点であり、常に多いほど良いわけではない。

LongBenchの個別列にはJudge QがSnapKVより悪い項目もある。例えばLlamaの保持512では2WikiがSnapKV 21.13に対してJudge Q 22.49で改善する一方、HotpotQA相当の列など複数で逆転が見られ、コードの一部ではSnapKVを下回る。したがって平均改善から全タスクで優位と結論しない。質問を冒頭へ移した場合の性能低下率はJudge Qで7%未満、比較法で約10%と記述されるが、入力分布の移動一般に対する保証ではない。

## 限界・負の結果

**第一に、追加prefillコストと推論速度の定量実測がない。** soft token 32個を通すため、長い入力では小さい相対負担であっても短い入力では追加計算が無視できない可能性がある。論文が示すのは同じKV保持数での品質改善であり、TPOT、TTFT、GPUメモリピーク、requests/s、CUDAカーネル単体速度などの数値を報告していない。メモリ節約率も保持予算からの理論的推測と、実際のフレームワーク割当て量を区別する必要がある。

**第二に、復号中の動的KV削除は未実装の研究課題である。** 原著結論ではstreaming KV evictionを今後の研究として明示する。現方式はprefill終了時に削除する静的処理が中心で、生成中に重要位置が変わるattention driftや、新しい生成tokenのキャッシュ成長を継続的に管理する仕組みは示していない。

**第三に、学習が必要である。** 追加embeddingだけとはいえ、対象モデルに合わせた教師応答の生成、注意マップ取得、MSE最適化が必要である。完全training-freeなSnapKVやStreamingLLMとは導入負担が異なる。別のモデル、別の言語、ツール使用やsystem promptを含む入力への移植は未評価であり、モデルごとに学習し直す可能性がある。

**第四に、未来応答を用いるoracleは実運用可能な上限ではない。** Table 1のFull KV-genは事後的に応答を知っており、Judge Qがこの上限に到達したわけでもない。教師応答が誤っている場合の学習バイアスや、後続の生成が教師と異なる場合のずれは残る。

**第五に、比較法の実装条件に依存する。** H2Oは原著そのままのオンライン方式ではなくprefill用の簡略化設定で比較される。PyramidKVの層別予算、SnapKVのpoolingとwindowの選択で順位が変わりうる。表のLongBench平均だけで異なる実装全体に対する普遍的優位を主張しない。

## 実装・運用上の示唆

既存のKV evictionを導入する際は、まず保持予算Bを固定し、質問が末尾にあるデータだけでなく、質問を冒頭へ移した入力、複数文書の跨ぎ参照、長い生成の途中で参照対象が変わる入力を評価するべきである。Judge Qの導入では、学習用prompt-responseの収集、soft token embeddingの追加と保存、prefillでのattention収集、層別KVのtop-k選択、soft token削除後の位置管理が必要となる。

Llama系モデルをvLLM/SGLangなどで配信する場合、単に生成プロンプトへ32文字列を追加するだけでは実装できない。soft tokenは専用embeddingを持つため、語彙拡張とattention mapの取得、KVブロック選択、positionの整合性が必要である。PagedAttentionの物理ブロック配置と論文上のトークン位置選択は別の層であり、選択位置が非連続でも実装上のメモリ断片化が残りうる。実装を評価するなら品質とともにTTFT・TPOT・ピークGPUメモリ・同時リクエスト数を測定する必要がある。

この研究の核心は**「未来の生成で必要な情報を事前に予測するための軽量な代理query学習」**であり、KVの量子化、低ランク化、圧縮表現を扱う手法とは直交する。保持位置を賢く選ぶ効果と、保持したKVを低bitで格納する効果は分けて評価するべきである。
