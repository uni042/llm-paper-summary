# 共有KVキャッシュで計算・共有の出自を保存する契約

## 概要

この論文は、推論エンジンの局所接頭辞キャッシュと外部の共有KVキャッシュを組み合わせた際に生じる、**同じトークン列なのに異なるKV状態を誤って共有する**という整合性欠陥を調べる。vLLMやSGLangは局所キャッシュの鍵にアダプタや共有領域の区別を持っていても、外部ストアの接続器がトークン列と粗いモデル名だけから鍵を再生成すると、その区別が消える。保存時と取得時の出自が異なるKVを読み込めば、要求したモデルの重みで生成していない文脈状態を用いて後続トークンを生成してしまう。

著者らはvLLMとSGLangの複数版、7系列12モデル（0.5B～32B）、160超の設定で現象を検証した。異なるアダプタのKVが混入すると、ある分類実験の正解率が0.94から0.64へ落ち、互換性のないKV表現では推論正解率が0になった。テナント分離用のソルトを共有鍵に含めない条件では、応答時間から被害者のプロンプトを93%の正確さで識別できた。これらは単なるキャッシュ命中率の問題ではなく、回答の正当性と情報分離に関わる。

解決策は、共有鍵に「計算結果を変える設定」と「共有を許す相手の範囲」を明示的に結合する**KV出自契約（KV provenance contract）**である。出自次元を追加できる登録表、長さ付きの正規符号化、安定した内容識別子、保存側と取得側の一貫した記述子伝播、欠落次元を検出する差分検査を組み合わせる。修正後は不正な共有を遮断し、同じ出自の再利用を維持した。確認された命中経路の遅延差は最大0.34ミリ秒で実行間変動より小さいが、異なる出自を分離するためストレージ容量は出自の種類数に応じて増える。

## 問題設定：局所鍵と外部鍵の意味のずれ

推論要求の入力接頭辞を処理するプリフィルでは、各層の鍵・値（KV）が生成される。後続の要求が同じ接頭辞を持つ場合、保存したKVを再利用すると最初のトークンまでの時間（TTFT）を減らせる。局所キャッシュは一つの実行主体の中で設定を管理できるが、LMCache、ファイルシステム接続器、HiCacheなどの外部共有層では、別の実行主体が書いた状態を別の実行主体が読む。

論文の再現例では、同じ基本モデルと同じトークン列を使い、書き手がアダプタA、読み手がアダプタBを使う。局所鍵は `(tokens, A)` と `(tokens, B)` で異なる一方、外部共有鍵が `hash(tokens, model_id)` なら一致する。読み手はAのKVを受け取った後、Bの重みでデコードする。キャッシュの中身はモデルの単なるテキスト表現ではなく、重みと計算精度に依存したテンソルであるため、同一文字列は互換性を保証しない。

計算上の出自には、低ランク適応（LoRA）アダプタ、重み量子化精度、モデル重みの版、KVの要素型や配置形式がある。これとは別に、テナントごとの共有許可を区切るソルトは、計算されたテンソルが同じでも共有してよいかを決める。重み版はローリング更新時に旧版と新版の実行主体が同時に生存するため重要である。さらに同じアダプタを別のファイル名で読み込んでも内容が同じなら再利用したい一方、同じパスのアダプタが上書きされた場合は再利用してはいけない。単なるローカル識別番号やパス文字列ではこの条件を同時に満たせない。

## 手法

### KV出自契約と共有鍵の構成

### 1. 計算整合性と共有許可の二つの不変条件

出自次元の集合を `D={d1,...,dn}`、トークン列を `x`、設定を `c` とする。契約は、同じ `x` について、異なる設定で作られたKVが異なる場合は共有鍵も異なること、共有許可がない設定間ではKVが偶然同一でも共有鍵を分離することを要求する。形式的には `KV(x,c1) != KV(x,c2) => Key(x,c1) != Key(x,c2)` と `not ShareAllowed(c1,c2) => Key(x,c1) != Key(x,c2)` である。これは鍵のハッシュが衝突しないという実装上の仮定を別途必要とする。

著者らは各次元に、異なる値を区別し、別の実行主体でも同じ値に同じ識別子を与える写像を要求する。各値を長さ付きで連結した正規記述子を暗号学的ハッシュへ通し、元の接続器が作る接頭辞鍵へ出自要約を組み込む。次元登録表へ新しい項目を足しても、接続器ごとに専用の鍵生成ロジックを書き直さなくてよい。逆に、登録表に含めなかった設定まで自動発見して守る方式ではない。

### 2. 実行主体の設定と要求ごとの設定を分ける

重み精度、重み版、KV表現は通常、一つの実行主体の寿命中は固定である。そこで起動時にこれらを要約し、接続器へ渡すモデル識別情報へ折り込む。特にKVの実際の要素型は起動引数 `auto` の文字列ではなく、確保後に決まった解決済みの型を使う。起動文字列が同じでも別の型に解決される場合を区別するためである。

アダプタとテナントソルトは要求ごとに変わるので、要求記録とともに伝播する。SGLangではアダプタのテンソル名、型、形状、バイト列、意味を持つ設定を指紋化し、実行主体内部の一時的なアダプタ番号をその指紋へ対応付ける。これにより同一内容を別パスへ配置した場合は共有でき、同一パスで内容が変われば分離できる。vLLM側は論文実装ではアダプタ名を安定識別子として用いており、識別子の選び方自体が保証範囲を決める点に注意が必要である。

### 3. 取得側と保存側で同じ記述子を使う

外部ストアへのアクセスは、プリフィル前に接頭辞を探すスケジューラと、計算後にKVを保存する実行主体の両方で発生する。前者だけにアダプタ識別子を足すと、後者の鍵と一致せず正当な共有も壊れる。論文実装は、要求記録にソルトとアダプタ識別子を確実に持たせ、両地点で同じ出自記述子から鍵を構築する。LMCacheでは固定長150バイトの鍵制限があるため、128ビット要約を22文字のBase64へ短縮し、代表的な鍵を89文字に収める。SGLang HiCacheでは保存・取得・昇格・再起動に共通する名前空間の種を更新する。

### 4. 差分欠落検査

テスト対象のトークン列を固定し、アダプタ、重み版、精度、KV型、ソルトのうち一つだけを変更する。その変更で生成KVが変わるのに共有鍵が同じなら、該当次元の結合が欠落していると判定する。共有許可だけが変わる場合も別途分離を確認する。実装の一部を意図的に外す除去試験では、重み版の省略が45ページ中42、KV表現の省略が45中45、アダプタ省略が43中42の異内容同鍵衝突を生んだ。対応する結合を戻すと検証対象の衝突は0になった。これは与えたテスト値についての検査であり、未知の次元を発見する万能検査ではない。

## 評価

### 評価環境と比較対象

| 観点 | 一次論文の条件 |
|---|---|
| 推論基盤 | vLLM 0.9.2、SGLang 0.5.20、旧版SGLang 0.5.8.post1も現象再現に使用 |
| 共有キャッシュ | LMCache、vLLMファイルシステム接続器、SGLang HiCache |
| モデル | 7系列12モデル、0.5B～32B、設定組合せ160超 |
| 検査方式 | 書き手が保存した後に別プロセスの読み手が取得。ストアなしの同一設定実行を正解参照とする |
| データ | ShareGPTの2,000会話、SST-2とIMDBの分類、GSM8Kの100問、構成した抽出・推論問題 |
| 主な指標 | 異出自KVの取得量、正解率、推論結果の反転、TTFT、ストア使用量、スループット |

同一設定の自分自身が書いたキャッシュを再取得する対照と、別設定が書いたキャッシュを取得する実験を分けている。ストアを無効化した読み手を正解参照とするため、異なる重みのモデルが元々別の回答を出すことと、誤った共有による差を区別できる。SGLangの組合せ試験では、同一設定の温まったキャッシュが5,376トークン分取得できるかも確認している。

### 定量結果と意味

| 条件・比較 | 修正前 | 出自結合後 | 解釈 |
|---|---:|---:|---|
| 異なるアダプタでの正解率（一例） | 0.64 | 正当な参照へ復帰 | 外部鍵衝突による回答破壊を除去 |
| 互換性のないKV表現の推論正解率 | 0 | 異出自取得を禁止 | 誤ったテンソル表現の読み込みを回避 |
| SGLang 0.5B、異出自5次元の取得 | 最大5,376トークンの誤取得 | 0トークン | 安全なミスを発生させる |
| 旧版重みが温めたストアへの新規実行主体の冷起動 | 正解率0.73 | 0.92 | ローリング更新時の古いKV流入を防ぐ |
| 新版割合25%のローリング更新 | 旧KV取得率0.24、正解率0.87 | 旧KV取得0、正解率0.92 | 混在期に効果が大きい |
| vLLMの確認済み共有ヒットのTTFT中央値 | 36.7 ms | 36.4 ms | -0.30 ms、実行間変動3.0 ms内 |
| SGLangの共有ヒットの平均遅延差 | 基準 | +0.34 ms | 反復変動3.0 msより小さい |
| vLLMの4種類の出自で12接頭辞を保持 | 214 MB（危険な重複排除） | 856 MB | 正しい分離により4倍の容量を使用 |

応答時間の変化は計測可能な範囲で小さく、要求単位の要約計算は12.7マイクロ秒だった。ただし「性能費用が常にない」という結論ではない。固定容量で異出自の正当な複製が増えた試験では、追い出しの連鎖によってTTFTが0.024秒から0.065秒へ悪化し、処理量が毎秒42件から15件へ落ちた。したがって正しさを回復する代償として、出自多様性に見合う共有ストア容量を確保する必要がある。

精度の悪化は次元やタスクにより異なる。重み精度の違いでは出力差があっても試験したタスクの正解率差が統計的に有意でない場合があり、重み版の違いでも同じ答えへ至る問題では影響が小さい。一方、アダプタを使った反対方針の感情分類や長い接頭辞に重要な情報が含まれる場合は顕著に悪化する。論文の数値をすべてのモデルで一定の悪化率と解釈してはいけない。

## 既存研究との差と限界

従来の接頭辞共有はトークン列が一致すれば計算を省けるという前提に立ちやすい。局所キャッシュは重みやアダプタの違いを扱えても、外部ストアが鍵を再導出する境界でその意味が落ちることが本論文の発見である。提案は新しいKV圧縮方式ではなく、**安全な再利用の等価関係を接続器間で保存する仕組み**である。とくにモデル更新、アダプタの入替、複数テナントで共有する実行基盤の運用に直結する。

評価は単一ホスト上の複数実行主体と独立した共有サーバーが中心で、実際の複数ホスト大規模クラスタにおける全ネットワーク条件を検証したものではない。出自登録表に存在しない次元、ハッシュ衝突、正しいアダプタ内容識別子を生成できない設定は契約の保証外となる。内容ハッシュの計算には、40MBアダプタで冷起動1.06秒、温起動0.060秒、0.5Bチェックポイントで1.35秒という初期費用がある。正当な出自ごとの容量増加と、固定容量での追い出し悪化も設計時に見込む必要がある。

## 接続器ごとの差分と実運用の境界

本研究は、すべての推論エンジンがまったく同じ次元を欠落させるとは主張していない。SGLang 0.5.20はテナントソルトを鍵に含め、起動時に登録されたアダプタを名前・パスに由来する識別子で分離する。一方で、同じファイルパスに新しいアダプタの重みを上書きすると、識別子が変わらないまま古いKVが読み出される。逆に同じ内容のアダプタを別パスへ置くと別の識別子になり、安全だが再利用の機会を失う。著者らの内容指紋は、この過剰分離と過小分離を同時に解消する。

SGLangの13種類の組合せを調べた表2では、重み版、重み精度、KV要素型、KV表現、アダプタの上書きなど、未結合時に異出自KVを読むか読み込み失敗する場合が、結合後は安全なミスへ変わる。一方、同じ出自の読み込みや、同一内容アダプタの再起動後の読み込みは維持される。重要なのは、外部ストアが返すKVの有無だけでなく、**取得後の回答がストアなしの正解参照と一致すること**を合格条件にしている点である。空の回答や読み込み失敗を、安全な成功として数えない。

テナントソルトの欠落は、モデルの数値精度とは別の共有許可違反を引き起こす。異なる顧客が同じプロンプトを入力していても、サービスの共有方針が禁止するなら別の鍵を使う必要がある。論文はこの違いを明示するため、KVの内容が同一かどうかを判定する計算不変条件と、共有可能かどうかを判定する許可不変条件を独立させた。したがって、将来のデータ所在地域や機密度などの共有方針も、安定識別子として登録できる設計となる。ただし、その方針を誰が宣言し、どの値を共有許可へ含めるかは運用者の責任として残る。

差分検査は、テスト対象の次元を一つだけ変えたとき、KV状態が変わるのに共有鍵が変わらない事例を発見する。モデルをローリング更新する場合、旧版のキャッシュが残っていることを意図的に再現し、更新後の実行主体が旧KVを読むかどうかを試験するのが有効である。本文では、冷起動時に100要求すべてが古いKVを読む条件で正解率が0.73まで下がり、出自結合後に0.92へ回復した。キャッシュの誤再利用は通常の単一モデル・単一プロセスのテストでは露見しにくいため、保存側と取得側を別プロセスにする試験構成そのものが重要な貢献である。
