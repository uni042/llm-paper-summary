# Paper quality responsibility split — Library-first v11

この文書は現行の論文品質責任を定義する。旧v10機械品質基準は
`.survey/legacy/quality-v10/` に退避済みであり、現行のGitHub公開・取り込み判定には使わない。

## 1. 原則

品質を二つに分ける。

1. **読解ワーカーの意味品質セルフチェック**
   - 論文を実際に読んだワーカーだけが判定・修正する。
   - 一次資料へ戻らないと修正できない項目は、GitHub側・アップロードワーカー側へ移さない。
2. **GitHub側の公開完全性チェック**
   - 論文を読み直さず機械的に確認できる形式・転送・同一性だけを見る。
   - 内容の良し悪し、説明量、手法の深さ、代表結果の妥当性などをFAIL条件にしない。
   - 例外として、日本語率は本文だけで機械判定・修正できるため従来の70%/80%基準を維持する。

アップロードワーカーは、読解内容を再監査したり、不足した科学的説明を推測で補ったりしない。

## 2. 読解ワーカーが自己チェックする意味品質

Libraryへ「完成」として保存する前に、読解ワーカー自身が一次資料と照合して次を確認する。

- 一次資料を必要範囲まで読み、canonical identity と対象論文が一致している。
- 推測や未確認の補完を事実として書いていない。
- `summary` と `list_summary` が論文固有で、題名の言い換えだけではない。
- 概要から、問題、提案、対象環境、代表的な結果または主要な発見が分かる。
- 手法は入力・観測、主要処理、出力、機構間の流れ、効く理由、主な失敗条件またはトレードオフを追える。
- 評価条件、比較対象、実機/シミュレーション等の前提を混同していない。
- 主要結果は条件・比較対象・意味を取り違えていない。
- 限界と既存研究との差が具体的である。
- 一次資料URLと書誌情報が確認できる。
- 保存前の成果Markdownが、必要な内容を意味的に説明できている。ファイルサイズ・文字数・段落数を数えて合否判定しない。

このセルフチェックは、読解中の文脈を保持しているワーカーがその場で修正できることを前提にする。

### 2.1 旧v10条件の扱い

GitHub側の機械FAILから撤廃した旧v10条件は、**Research読解ワーカーへの執筆目安・セルフレビュー条件としては残す**。ワーカーは監査スクリプトや文字数カウンタを必須実行せず、一次資料を読んだ文脈で「旧基準相当の十分な説明になっているか」を確認する。

- UTF-8 4,500 bytes以上相当の十分な成果量。
- 説明本文2,200文字以上相当の十分な説明量。
- 全体10段落以上相当の説明の厚み。
- 手法4段落以上相当の詳細さ。
- 主要機構が3個以上ある場合、各機構2段落以上相当の説明密度。
- `list_summary` は45〜180文字程度を目安とし、問題だけでなく具体的な貢献を一文で示す。
- 日本語化できる裸の英語専門語は原則残さない。
- 概要に代表的な定量結果、または主要な定性的発見を含める。
- 問題設定・新規性・手法・結果・限界・既存研究との差を内容上十分に扱う。
- 定量結果の条件、比較対象、指標、品質影響、負の結果やトレードオフを取り違えない。
- MoE-Infinityのお手本にならい、一次資料に複数の評価軸がある場合は代表結果1つだけで終えず、評価環境・baseline・絶対性能・相対改善・資源／品質・感度／スケーリング・ablation／内部指標・ウォームアップ・worst case・一般化限界を、報告されている範囲で拾う。
- 代表的な評価条件と代表的な評価結果は原則として表にまとめる。条件表は主要ハードウェア・モデル・ランタイム・ワークロード・バッチ／系列長等、結果表は条件・指標・比較対象・提案手法・改善／差・読み取れることを含める。

これらの数値は**厳密な機械合格線ではなく執筆時の目安**である。数値を満たすための水増しは行わず、意味品質を優先する。日本語率だけは例外で、GitHub反映側でも70%未満FAIL・70〜80% WARNとして機械判定する。

### 2.2 想定読者と専門背景の厚み

想定読者は、Transformer、生成、KVキャッシュ、混合専門家モデル（MoE）など**LLMの基本概念は知っているが、その論文が属する狭い専門分野は詳しくない読者**とする。

量子化、疎注意、投機的復号、サービング・スケジューリング、GPUカーネル、分散通信、オフロード、炭素最適化、ロボット制御など、論文理解に必要なサブ分野固有の前提は省略しない。単語の定義だけを置くのではなく、論文固有手法へ入る前に、必要な範囲で次の因果関係を説明する。

- その分野では通常どのような処理をしているか。
- どの資源・誤差・待ち時間・品質劣化が問題になるか。
- 既存の代表的な対処は何をするか。
- その既存対処が、この論文の対象条件ではなぜ不足するか。
- その不足を受けて、論文が設計空間のどこを変えるのか。

専門背景は一般的な教科書説明を長く挿入するためではなく、**論文固有の機構を理解するための足場**として書く。背景説明の直後には必ず「だから本論文では何を変えるのか」へ接続し、一般論だけで段落を終えない。

初出のサブ分野固有語は、略語展開だけでなく役割も一文以上で説明する。たとえば「MXFP4」「ルーフライン」「ReduceScatter」「attention sink」「非劣性」「閉ループ評価」などを、読者がその分野を知っている前提で裸のまま使わない。

評価節でも、指標名だけを並べず、その指標が何を測り、値が増減すると何を意味するかを専門外のLLM読者が追えるようにする。特にPPL、TTFT、TPOT、acceptance rate、HBM帯域、通信隠蔽率、タスク成功率など、その論文の結論を左右す指標は意味を本文中で説明する。

### 2.2 論文固有情報を先に抽出する執筆工程

Research読解ワーカーは、一次資料を読んだ直後に完成文章を書き始めず、まず**論文固有の事実を抽出してから本文を構成する**。最低限、次を確認する。

- この論文が解く具体的な問題と、既存方式のどこが不足するか。
- 主要機構ごとの論文中の固有名称、変数、行列、キャッシュ、スコア、アルゴリズム等。
- 各主要機構の **入力 → 処理 → 出力** と、前後の機構との接続。
- なぜその処理が対象ボトルネックへ効くのか。
- 追加される計算、状態、通信、メモリ、前処理等の費用。
- 失敗条件、誤予測時の挙動、品質低下条件、適用範囲。
- 評価環境、比較対象、絶対性能、相対改善、感度、ablation、内部指標、worst case、負の結果。
- 論文が評価していない事項。

抽出した固有事実を本文の骨格にする。一般的なLLM推論・GPU・量子化・キャッシュ・スケジューリングの説明を先に作り、後から論文名だけ差し替える書き方は禁止する。

### 2.3 主要機構は6観点で説明する

主要機構ごとに、一次資料に記載されている範囲で次を説明する。

1. 何のための機構か。
2. 何を入力・観測するか。
3. 内部で具体的に何をするか。
4. 何を出力・更新・配置・削減するか。
5. なぜ対象ボトルネックを改善できるか。
6. どの条件で利得が減るか、または追加費用が問題になるか。

「状態を観測する」「必要な資源を選ぶ」「品質を保護する」など、他の多数の論文にもそのまま適用できる一般文で主要機構を代替しない。論文中に方式名、モジュール名、変数名、行列名、キャッシュ名、スコア名、アルゴリズム名がある場合は、それを使って処理を具体化する。

### 2.4 一般論による水増しを禁止する固有性チェック

完成前に各段落について、**「論文名を別の論文へ置き換えてもほぼそのまま成立するか」**を確認する。

そのまま成立する段落は、次のいずれかを行う。

- 一次資料から論文固有の機構、数値、条件、用語を追加して具体化する。
- 背景説明として必要なら短縮する。
- 解説に不要なら削除する。

説明量の目安を満たすために一般論や同義反復を追加してはならない。同一またはほぼ同一の説明文を複数の主要機構へ反復することも禁止する。

### 2.5 評価を提案機構の証拠として対応付ける

評価結果は独立した数値一覧ではなく、本文で説明した提案機構のどの主張を裏付けるか対応付ける。可能な場合は、

**機構 → 評価条件 → 指標 → 結果 → 何が確認できるか**

の順で読者が追えるようにする。

代表的な評価条件・結果は表にまとめ、主要性能だけでなく、論文に存在する場合は感度評価、構成要素除去実験、内部指標、立ち上がり、最悪条件、品質影響も含める。論文に報告のない評価軸を一般論や推測で補わず、「論文では未評価」と明記する。

### 2.6 完成前の固有性セルフレビュー

Libraryへ完成成果として保存する前に、最低限次を読み返す。

- この論文固有の仕組みを本文だけから追えるか。
- 各主要機構の入力・処理・出力が分かるか。
- 主要機構が汎用的な三段階・四段階テンプレートへ置き換わっていないか。
- 同じ説明文が複数機構で反復されていないか。
- 評価条件、比較対象、指標、数値、結論が対応しているか。
- headline値1件だけで評価を終えていないか。
- 一次資料にない推測や一般論で説明量を増やしていないか。
- 効く条件だけでなく、効きにくい条件・追加費用も分かるか。

MoE-Infinityのお手本とは文章量や見出し数を比較するのではなく、**論文固有の内部機構を追えること、複数の評価証拠が条件付きで整理されていること、利得と限界の因果関係が説明されていること**を比較する。

## 3. 現行GitHub側で確認してよいもの

GitHub側の自動処理とアップロードワーカーは、次のような**論文再読を必要としない公開完全性**だけを検査する。

- UTF-8として読み取れる。
- YAML前付けが存在し、構文として読める。
- 公開・同一性に必要な `canonical_id`、`title`、`source`、`summary`、`list_summary` が存在する。
- Markdownコードフェンス等に明白な構文破損がない。
- 説明本文の日本語率を測り、**70%未満FAIL、70〜80% WARN、80%以上を目標**とする。書誌情報・一次資料・URL・コード等は比率計算から除外する。
- `list_summary` も日本語率70%/80%の同じ基準を適用する。
- canonical identity、既存path、blob SHA、重複、競合が整合している。
- 構造化レコードの各slotがJSON objectとして読み取れ、レンダラーが必要とする型を満たす。
- 書込み後にmainから同じpathを再取得でき、意図したidentity/contentが反映されている。

これらは科学的内容の再評価ではなく、転送・形式・同一性の確認である。

## 4. GitHub側から撤廃した旧品質FAIL

次は**現行GitHub側の公開条件ではない**。

- 4,500 bytes以上という公開ゲート
- 説明文2,200文字以上
- 説明10段落以上
- 手法4段落以上
- 主要機構ごとの段落数
- 裸の英語専門語0件
- `list_summary` の45〜180文字という長さの機械FAIL
- `list_summary` の意味品質をGitHub側で自動判定するFAIL
- 裸の英語専門語0件という独立FAIL
- 概要の代表結果を正規表現等で検出するFAIL
- 問題設定・新規性・手法・結果・限界の文字数下限
- 主要機構数の下限
- 定量結果やnegative result等の必須化
- アップロードワーカーが一次資料を再読しないと修正できないその他の意味品質FAIL

内容上の要件と旧v10の量的目安は、Research読解ワーカーのセルフチェックへ移して維持する。GitHub側の機械FAILへは戻さない。

## 5. 旧基準の復元

旧v10基準と当時の実装スナップショットは
`.survey/legacy/quality-v10/` に保存している。

復元するときは、単一閾値だけを戻して整合性を壊さず、同ディレクトリのREADMEに記録された対応ファイルを一式で確認する。

## 6. 現行監査スクリプト

`.survey/scripts/audit_paper_quality.py` と `.survey/scripts/paper_quality_gate.py` は、
名称互換のため残す。役割は**公開完全性（publication integrity）と日本語率**に限定する。
日本語率は70%未満FAIL・70〜80% WARNを維持するが、それ以外の意味品質を数値化したり、読解内容を再判定したりしない。

GitHub Actionsも現行の公開完全性回帰試験だけを実行し、旧一覧文・概要意味監査を公開条件にしない。
