# 朝の集約・更新・全体点検

### 3.3 朝モード
通常の精読・監査を一括処理せず、以下を行う。
1. `runtime.json` の `last_morning_report_cutoff` より後、今回開始時刻以前の推論論文追加・重要更新・系統変更を変更履歴から集約する。
2. 基盤ソフトウェア更新、主要LLM公開情報を確認する。
3. 補助プログラムで全体整合性点検・索引・一覧・比較表・進捗表示の生成を行う。
4. `maintenance-queue.json` のopen項目を古い順に処理する。README・件数・リンク・一言説明・派生索引は論文本文と識別索引から再構築し、修復成功後にresolvedへする。maintenance処理の失敗で保存済みcore成果を巻き戻さない。
5. `blockers.json` のopen項目を確認し、自力で解消できるようになったものは処理してcloseする。依然として外部条件・権限・利用者判断が必要なものは、問題・影響・試行済み対策・必要な対応を朝レポート用に要約する。
6. 各作業群を独立して扱い、1群の障害で他群を止めない。成功した範囲を保存・確認する。
7. 朝レポート生成可能範囲を確認して `runtime.json` の `last_morning_report_cutoff` を更新する。朝の更新確認では精読・監査の日次目標・plan・完了数を変えない。

## 11. 朝のみ：基盤ソフトウェア更新・主要LLM
`framework-updates/` と `llm-releases/` を公式資料に基づいて差分更新する。モデル対応追加だけ、軽微な互換性、能力不変の機器追加、単なるバグ修正は原則除外する。主要LLMは予告だけを公開済みとして扱わない。起動元の非公開重点条件は調査時だけ適用し、公開ファイルへ転記しない。

## 12. 朝のみ：全体整合性点検
全推論ページ、`paper-identity-index.json`、分割state、一覧を照合する。
確認項目：研究と有効パスの1対1対応、識別子重複・索引漏れ、属性形式、broken link、一言説明、Otherの位置、学習領域への意図しない変更、長期未完了、探索偏り、見送り矛盾、maintenance滞留、open blocker。

派生README・件数の不整合はmaintenanceへ集約して修復する。一次資料確認が必要な研究内容の問題は監査queueへ、外部対応が必要な問題だけblockersへ送る。

## 13. 集約報告
朝レポートは「新規推論論文 → 既存論文の重要更新 → 系統変更 → 基盤ソフトウェア → 新LLM → maintenance修復 → 未解決blocker」の順を基本とする。空項目は省略する。未解決blockerは問題、影響、対策候補、必要な外部対応を簡潔に示す。

## 記録整理
終了記録の保存を確認した後、終了済みの詳細記録のみ24時間で整理する。未解決の開始・途中記録は復旧確認まで残す。停止疑いと確認済み障害を区別する。通知や予定タスク自体は変更しない。
