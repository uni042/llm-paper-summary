# 朝の更新と集約

## 担当範囲

1. `last_morning_report_cutoff` より後、今回開始時刻以前の論文追加・重要更新・分類変更を変更履歴から集約する。
2. `framework-updates/` と `llm-releases/` の重要更新を公式資料で確認し、差分更新する。
3. 夜間点検の最新結果を読み、検査範囲、修復件数、未検査・未解決項目を報告に含める。結果がない、または途中ならその事実を示す。
4. `blockers.json` の外部対応が必要な残件を要約する。解決を確認できたものだけ閉じる。
5. 前回朝報告以降の `runs/`、`blockers.json`、`maintenance-queue.json` を見て、繰返し発生した手作業・取得制約・編集制約・検証漏れ・復旧負荷のうち、補助プログラムで明確に自動化できそうなものを抽出する。
6. 今回変更したファイルに限って保存前後の整合性を確認する。全リポジトリの再走査・一括再生成・記録整理は夜間に任せる。
7. 報告内容と保存を確認してから報告境界を更新する。報告保存に失敗した範囲を通知済みとして飛ばさない。

## 新着の判断

モデル対応追加だけ、軽微な互換性、能力不変の機器追加、単なる不具合修正は原則除外する。予告を公開済みと扱わない。利用者固有の監視条件は調査時だけ使い、公開ファイルへ転記しない。

## 補助プログラム提案

実行上の摩擦が補助プログラムで減らせる場合、朝報告へ最大3件まで「あると有効な補助プログラム」を添える。各案は `仮称 / 解決する問題 / 期待効果 / 優先度` を1〜2行で示す。

- 既に同等機能が `scripts/` にある場合は新規提案しない。既存ツールの拡張が適切なら「既存ツールの拡張」として示す。
- 一度きりの偶発障害より、複数回発生した手作業、長いファイルの編集、同じ検証の反復、状態同期、復旧、差分生成などを優先する。
- 期待効果が曖昧な案、単に実装を増やすだけの案は出さない。
- 朝報告での提案だけを理由に通常実行中に手順書や補助プログラムを自己変更しない。実装は利用者の指示がある場合に行う。
- 有用な新案がなければこの項目は省略する。

## 報告の順序

新規推論論文、既存論文の重要更新、分類変更、基盤ソフトウェア、新しい大規模言語モデル、夜間の修復・未検査範囲、外部対応が必要な問題、補助プログラム提案の順とし、空項目は省く。

各作業群は独立して扱う。朝の処理で日次計画・精読監査件数・目標を変更しない。通知時刻と条件は起動元を維持する。
