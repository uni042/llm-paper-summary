# 朝の集約・更新・全体点検

### 3.3 朝モード
通常の調査・監査の一括処理は実行せず、以下だけを行う。
1. 開始時刻を `morning_cutoff_at_start` として固定し、前回 `last_morning_report_cutoff` より後、今回開始時刻以前の推論論文の追加・重要更新・系統変更を実際の変更履歴から集約する。今回開始後の変更は次回分。締切が未設定なら、確認できる過去の朝レポートの締切を優先して復元する。復元不能なら今回開始の24時間前を初回の下限とし、初回集約範囲を明示する。未報告の古い重要変更が確認できた場合は追補として区別し、全履歴を毎朝再報告しない。
2. [第11章](morning.md)の基盤ソフトウェア更新、主要LLM公開情報を確認して反映する。
3. [第12章](morning.md)の全体整合性点検を行う。
4. 基盤更新・LLM更新・整合性修復を独立した作業群として扱い、1群の障害で他群を止めない。群ごとに[第9章](publishing.md)の検証・一括保存を行い、[第10章](completion.md)のログと朝レポートを作成する。
5. 朝レポートが正常に生成できた範囲を確認して `last_morning_report_cutoff` を今回開始時刻に更新する。レポート自体が失敗したら進めない。基盤更新等の一部失敗は明示し、推論論文の集約が成功していればその締切は更新可。
朝は処理件数設定・連続成功回数を変えず、既存の調査／監査キューを通常処理・並べ替えしない。点検で一次資料の再確認が必要な既存推論論文を見つけた場合は、重複を避けて監査キュー末尾へ追加可。保存済み成果との照合による復旧は可。

## 11. 朝のみ：基盤ソフトウェア更新・主要LLM
### 基盤ソフトウェア
`framework-updates/` の既存対象と構成を確認し、公式文書・開発元リポジトリ・公開版・変更提案（PR）を根拠に主要能力と最近の重要更新を差分反映する。
対象例：バッチ処理・スケジューリング、キャッシュ・メモリ・退避、量子化・投機的復号・MoE、並列化・分散実行、処理分離、カーネル・コンパイラ・通信・入出力、LoRA・追加学習・FSDP・ZeRO、強化学習用生成、複数媒体処理・API・モデル読込・配置。
学習領域の凍結は `papers/training/` に適用し、基盤ソフトウェアの重要機能の説明まで一律除外するものではない。
モデル対応追加だけ、許可リスト・会話形式追加、軽微な互換性、能力不変の対応機器追加、バグ・異常終了・正確性・安全性の修正だけは原則除外する。実装済み、未統合の提案、公開予定を区別する。

### 主要LLM
主要な公式公開を確認して `llm-releases/` を差分更新する。重要な重み公開モデルでは総／有効パラメータ数、MoE構成、入力長、対応媒体、利用許諾、入手先、llama.cpp・Ollama・vLLM対応、量子化時メモリ目安を確認できる範囲で記録する。推定は条件を付ける。
予告だけを公開済みとして扱わない。起動元に非公開の重点確認条件がある場合は調査時だけ適用し、優先理由や条件を公開ファイルへ転記しない。

## 12. 朝のみ：全体整合性点検
全論文の再精読はせず、全推論ページと識別索引・属性・一覧を照合する。
確認項目：研究と有効パスの1対1対応、識別子重複・索引漏れ・参照先欠落、一意件数と各一覧、属性形式と検証／監査情報の充足、壊れたリンク、一言説明、その他の位置・独立系統候補、学習領域への意図しない変更、長期未完了、探索経路の偏り、見送り記録の矛盾・再確認理由、ログと実績の整合。
識別重複は優先して内容を保全し統合・件数修復する。一次資料確認が必要なものは監査キュー末尾へ残す。形式点検だけで正式監査完了にしない。

## 13. 集約報告
### 朝レポート
「新規推論論文 → 既存論文の重要更新 → 系統変更 → 基盤ソフトウェア → 新LLM」の順。空項目は省略する。全項目に重要変更がなければその旨を短く記載する。
新規論文は題名、平易な一文要約、GitHubリンクを必須とし、必要なら手法・代表結果・差分を1〜3文追加する。学習論文や見送り一覧は通常報告に含めない。未完了・取得不能がある場合は、調査済みで変更なしだったものと区別する。

重複修復や識別索引の再構築で詳細な同一性判定が必要な場合だけ、[論文探索・監査](hourly.md) の第6章を追加で読み、その識別規則を使う。通常の毎時処理全体を朝に実行しない。
