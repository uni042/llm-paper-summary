# 毎時の論文探索・監査

### 3.2 毎時モード
[第5章](hourly.md)で今回の対象を固定して中間保存する。その後、次の巡回を対象が終わるまで繰り返す。
1. 調査1件（[第6章](hourly.md)）と監査1件（[第7章](hourly.md)）を処理する。前回監査の繰越または監査0件の実績があれば監査から始め、それ以外は調査から始める。片方がなくなれば残る側を進める。
2. その巡回で完了できた成果を整備（[第8章](publishing.md)）、検証し、論文・索引・一覧・状態をまとめて保存・確認する（[第9章](publishing.md)）。通常は2件分を1つの成果変更記録にする。片方が保留なら、もう片方の検証済み成果だけ保存可。
3. 確認済み成果だけキューから除き、次の巡回へ進む。完了した対象を同じ実行で再割当しない。
4. 全対象完了、または観測できる実行制約により次の巡回と保存を完了できない見込みなら、[第10章](completion.md)で終了状態を確定する。
調査を全件終えるまで監査を待たせない。巡回ごとに開始からの所要時間と直近の保存所要時間を確認する。実行期限が判明している場合は少なくとも直近の保存・確認に要した時間を終了処理用に確保し、不明な実行上限を捏造しない。中断兆候が出たら新しい精読を始めず保存を優先する。
- 引用・被引用探索に加え、arXiv、OpenReview、会議公式一覧など引用関係に依存しない新着探索も毎回行う。新着探索を朝だけに限定しない。
- 基盤ソフトウェア更新とLLM公開情報の確認は行わない。
- 論文1本、系統1つ、変更記録（commit）1つの完了だけを終了理由にせず、固定した対象の次の巡回へ進む。

## 5. 毎時の対象選定と中断対策
### 共通の選定規則
キューの既存順序を基本とし、再試行可能日時を迎えた項目を選ぶ。繰り返し取得できない項目だけで先頭が塞がらないよう、保留中項目を一時的に飛ばしてよいが削除しない。
同じ外部操作の一時的失敗は1実行につき追加1回まで再試行し、認証・権限不足は同じ呼出しを繰り返さない。候補単位で `attempt_count`, `last_error`, `next_retry_at` を必要時に記録する。3回の実行で連続して同じ取得失敗なら24時間保留し、他の対象を処理する。新しい資料や復旧が確認できれば早期再開可。品質上の見送りと技術的な保留を混同しない。

### 調査対象
1. `pending_research` 先頭から `research_batch_size` 件まで選ぶ。
2. 足りない分だけ新候補を簡易選別し、深く調べる合理性がある候補を補う。新規対象はキュー末尾へ追加する。
3. 有望候補が足りなければ設定数未満でよい。候補不足を埋めるために無関係な論文を追加しない。
4. キューで枠が埋まっていても独立新着源を簡易確認する。後で調べる価値がある候補は、識別照合のうえ未着手として末尾へ残し、今回の固定対象を際限なく増やさない。

### 監査対象
1. `pending_audit` 先頭から `audit_batch_size` 件まで選ぶ。
2. 足りない分は必ず既存推論論文から補う。監査可能な論文が設定数以上あれば設定数を割り当てる。キューが空であることだけを理由に監査0件にしない。
3. 優先順：監査形式の欠落／旧版 → 監査日欠落（一次確認から14日以内は原則後回し）→ 未採択・投稿中・出版状態不明 → 実装未確認／未公開など変化しやすいもの → 改訂の可能性 → 監査日が古いもの。同一系統への偏りを避ける。
4. 同じ研究を重複割当しない。調査と監査の両方に該当する場合、一次資料確認は共有してよいが、正式監査の全条件を満たす前に監査完了と数えない。

深い精読前に今回の固定対象と未着手を含むキュー全体を状態へ保存し、中間保存（checkpoint）の変更記録を作る。可能なら開始時刻付き `running` ログも残す。対象を固定できない／中間保存できない場合は、復旧可能な範囲を優先し、未保存のまま大量処理を進めない。

## 6. 論文調査と重複防止
### 6.1 精読前の照合
有効な識別索引 → 永続見送り記録 → 最近確認済み記録、の順に調べる。
- arXiv識別子は版番号を外して比較し、版は別に保存する。
- DOIはURL／`doi:`接頭辞を外し小文字化する。
- OpenReviewは公式URLから対応する安定識別子を確認する。
- 題名はUnicode・大小文字・空白・句読点を正規化し補助照合する。近い題名だけで同一研究と断定しない。
- 新しい正規識別子の優先順はarXiv → DOI → OpenReview → その他の安定識別子。一度付けた `canonical_id` は原則固定し、後で得た別識別子を別名として追加する。

### 6.2 新規作成の必須条件
作成前に `canonical_id`、arXiv基本識別子、正規化DOI、OpenReview識別子、別名を照合し、さらに題名の一致・類似候補を確認する。
- 識別子が既存研究に一致すれば新規作成禁止。既存ページの変更なし、更新、移動、統合として扱う。
- arXiv版・会議版・DOI版・題名変更は、同一研究なら1ページへ統合する。
- 題名類似や版対応が曖昧なら一次資料で確認する。索引が古い・照合不能・同一性不明なら新規作成を保留する。
- 見送り済みで重要な変化がなければ再精読しない。新版、採択・出版、大幅改訂、公式実装公開、除外理由を覆す資料がある場合に再確認可。採用へ移したら見送り項目を削除または `status: promoted` にする。

### 6.3 調査結果
一次資料確認を終えた候補を `added`（新規採用）、`updated`（既存更新）、`already_recorded`（既存・変更不要）、`not_selected`（見送り）のいずれかに確定する。一次資料未確認・判定途中は完了扱いせずキューへ残す。
`not_selected` は永続見送り記録へ保存する。重複を見送る場合は既存ページとの対応も残す。
探索は参考文献、被引用論文、独立新着源を組み合わせる。固定比率・件数ノルマは設けず、長期的な同じ引用鎖・情報源への偏りを補正する。

## 7. 正式監査の完了条件
以下を一次資料と現行ページで確認する。修正がなくても全項目を確認すれば完了。確認不能な項目は、不明である事実と確認先を明示する。必要な一次資料にアクセスできず確認自体ができない場合は未完了。
- 同一研究の識別と重複、書誌、著者・所属、公開・採択・出版状態、最終採択版、各公開版の対応、一次資料URL。
- 実装URL、公開状況、上流への統合状況。
- 主要性能値の出典位置、機器・モデル・データ・比較条件、評価方法、実装状態、シミュレーションと実機の区別。異なる版の評価値を混ぜない。
- 系統分類、READMEのリンク・件数・一言説明、既存研究との差と限界。
完了時だけ `last_audited: YYYY-MM-DD` と `audit_version: 1` を記録する（現行監査形式は1）。
新規登録や一次資料を実質再確認した重要更新では `last_verified: YYYY-MM-DD` を記録する。新規登録だけで監査済みにしない。変更なし監査では監査日だけを更新し、形式修正だけで一次確認日を更新しない。途中監査では監査済み情報を更新しない。
