# 毎時の精読・監査

## 3.2 精読・監査モード
1. `runtime.json` が指す最新の日次plan、該当queue、識別索引、成果を照合し、保存済み作業を復旧する。毎時の新規探索・対象補充は行わない。
2. 精読と監査の偏りを防ぐため、開始時と各1件の保存確認後に当日進捗率を比較する。精読側は一次資料本文を確認して結果保存まで完了した件数、監査側は正式監査完了件数をそれぞれ当日目標で割る。片側が概ね1件分を超えて先行している間は低い側を優先する。両側が同程度なら精読1本→監査1本を1巡回とする。
3. 精読は一次資料本文を読み、問題・新規性・手法・評価条件・結果・限界を確認する。選定時preflightが `available` でも取得経路が一時的に失敗した場合は、planに記録されたpreferred/fallbackを再確認する。双方取得不能なら同じ実行で打ち切り、`insufficient_primary_source` として永続見送りへ保存し、当日項目を決着させて次候補へ進む。
4. 監査は第7章の全条件を満たして初めて完了にする。保存・確認・終了記録の余裕がある限り次の対象へ進み、1本だけを終了理由にしない。
5. 当日分が完了した側は翌日まで対象を追加しない。次の選定枠を過ぎた古いplanに新規作業を開始しない。

## 5. 中断対策
論文自体の取得不能と、GitHub保存競合・認証・権限・実行基盤障害を分ける。前者は永続見送り、後者だけを `blocked` としてqueueへ残す。同じ外部操作の一時的失敗は1実行につき追加1回まで。

研究成果のcore保存が成功し、README・件数・派生一覧だけが失敗した場合は成果を巻き戻さない。`maintenance-queue.json` に対象path、検出時刻、根拠、次処理を追加し、同じ実行で次の論文へ進める。利用者判断や権限等が必要で自力解消できない場合だけ `blockers.json` へ追加する。

## 6. 論文調査と重複防止
### 6.1 精読前の照合
有効な識別索引 → 永続見送り記録 → `recently-checked.json` の順に調べる。
- arXiv識別子は版番号を外して比較し、版は別に保存する。
- DOIはURL／`doi:`接頭辞を外し小文字化する。
- OpenReviewは公式URLから対応する安定識別子を確認する。
- 題名はUnicode・大小文字・空白・句読点を正規化し補助照合する。近い題名だけで同一研究と断定しない。
- 新しい正規識別子の優先順はarXiv → DOI → OpenReview → その他の安定識別子。一度付けた `canonical_id` は原則固定する。

### 6.2 新規作成の必須条件
作成前に `canonical_id`、arXiv基本識別子、正規化DOI、OpenReview識別子、別名、題名類似候補を確認する。識別子が既存研究に一致すれば新規作成禁止。同一研究のarXiv版・会議版・DOI版は1ページへ統合する。

### 6.3 調査結果
一次資料確認を終えた候補を `added`, `updated`, `already_recorded`, `not_selected` のいずれかに確定する。`not_selected` は永続見送りへ保存する。一次資料取得不能は本文内容を推測せず `insufficient_primary_source` として記録する。

## 7. 正式監査の完了条件
一次資料と現行ページで、同一研究の識別、書誌、著者・所属、公開・採択・出版状態、最終採択版、一次資料URL、実装URL・公開状況、主要性能値の出典位置、機器・モデル・データ・比較条件、評価方法、実機／simulation、系統分類、既存との差と限界を確認する。

README・件数・一覧が古いこと自体は論文ページの正式監査を未完了にしない。論文ページと識別索引で分類・同一性を確認でき、README側だけが派生不整合ならmaintenanceへ送る。完了時だけ `last_audited` と `audit_version: 1` を記録する。
