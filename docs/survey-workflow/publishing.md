# 成果物の形式・保存・検証

## 8. 成果物の統一形式
### 論文ページ
1研究1Markdown。書誌、一文要約、問題、新規性、手法、評価条件、主要結果、限界、実装状況、既存との差、一般的な実装への示唆、引用関係、一次資料を記載する。
- 初出の専門用語は日本語を先に書き、英語を括弧併記する。固有名・ファイル名・識別子は維持する。
- 狭い方式名や略語だけで説明を済ませず、何を観測し、何を選択・移動・削減・予測し、何の費用を減らすかを平易に書く。
- 重み退避とKVキャッシュ退避、CPU主記憶とNVMe、他GPUのHBM、HBF、CXL、一般製品と専用・試作機器、模擬評価と実機評価を区別する。
- 主要数値は確認できる表・図・節を併記し、位置や値を推測しない。
- 冒頭の構造化属性に `canonical_id` と存在する各識別子を記載する。確認できる場合のみ `verified_arxiv_version`, `publication_version`, `source_last_revision`, `evaluation_type`, `implementation_status` を記録する。
- 属性整備は新規・正式監査・重要更新で触れた論文から行う。整合性点検だけで検証日を推測補完しない。

### 一覧と分類
- 系統にも論文にも必ず一言説明を付ける。論文本文の一文要約を一覧用説明の正本として同期する。
- `papers/inference/README.md` と `papers/README.md` の系統一覧：
  `- [系統名](path) — N本 — 一言説明`
- 各 `papers/inference/*/README.md` の論文一覧：
  `- YYYY-MM-DD — [論文名](file.md)`
  次行に `  - 一言説明`
- その他（Other）は常に最後尾。該当フォルダは `99-other-...`。明確な共通系統が3〜5本以上まとまったときだけ独立系統化を検討し、機械的に細分化しない。
- 分類変更は追加ではなく移動。旧パス削除、新パス作成、索引、旧・新系統一覧、上位一覧を同じ成果変更に含める。移動で総論文数を増やさない。
- 既存重複は内容を保全して適切な1ページへ統合し、有効パスを1つにする。
- 新規追加・削除・移動・統合に伴い、該当系統、推論一覧、`papers/README.md`、ルートREADMEの件数を同期する。件数はファイル作成数や従来の表示値ではなく、一意な研究数を根拠にする。学習系件数は参照のみ。

## 9. 検証・GitHubへの保存・保存確認
### 9.1 保存前検証
準備した変更後の全体像に対し、少なくとも今回変更対象と識別索引について確認する。
- 各正規識別子・arXiv基本識別子・DOI・OpenReview識別子に有効パスが最大1つ。
- 索引のパスが存在し、削除したパスを指していない。今回の新規ページは[第6章](hourly.md)を通過済み。
- 新規ページの正規識別子・一次確認日、正式監査完了ページの監査日・監査形式が適切。
- 見送り記録と採用状態、完了と未完了キューの整合。
- READMEリンクと一言説明、系統／推論／全体件数、その他の最後尾、学習領域の変更なし。
- 移動で総数が増えず、重複統合後は一意な研究数になっている。
矛盾は同じ実行で修復する。解決しなければ問題のある変更を公開せず、該当項目を未完了として残す。独立して検証済みの成果は保存してよい。

### 9.2 まとめて保存
- 精読は論文1件ごと、監査は別に1件ごと、選定は日次計画単位、朝の更新確認は独立作業群ごとに1つの成果変更記録へまとめる。1論文の本文・索引・一覧を別々に逐次保存する運用はしない。実行全体を最後まで保存せず抱え込まない。
- Gitデータ操作用APIが利用できるなら、最新HEADを基に変更内容を用意し、`create_tree → create_commit → update_ref` でまとめる。ローカルGitによる同等の一括保存も可。
- 論文、移動・削除、識別索引、一覧・件数、見送り記録、処理状態を整合した1つの変更集合にする。
- 同じパスへ並列書込みしない。公開直前にHEADの変化を確認し、競合時は最新HEADを読み直して変更を組み直す。他の実行の成果やキューを上書きしない。強制更新は禁止。先頭確認だけを排他制御と考えず、実際の更新は早送り限定（fast-forward only）で行う。競合時は最新状態へ自分の未反映差分だけを再適用し、識別重複とキューの完了を再照合する。自分が読んだ古い状態ファイル全体で置換しない。競合の再構成は1巡回につき2回までとし、続く場合はその巡回の公開を保留する。
- 一括保存が使えない場合のみ利用可能な安全な方法を用い、部分反映を復旧可能にする。使えない理由を記録する。
- 保存前検証を通過し保存も成功した研究だけを追加・更新・監査完了数へ算入する。単にページ作成を試みた件数は数えない。

### 9.3 保存後確認と終了記録
保存後の実際のHEAD・変更ファイルを読み、意図した成果と索引・一覧・件数が反映されていることを確認する。保存結果不明なら、成功とも未保存とも決めつけず実体を照合する。
各巡回の保存後に確認結果を保持する。実行の最後に実時刻を取得し、`last_run` と終了ログへ記録する。これは「成果保存・確認を終え、終了記録を始めた時刻」と定義する。開始時刻を終了時刻として転用しない。
成果自身の変更識別子や保存後確認結果は、保存前には確定できないため、必要な状態・終了ログだけを小さな追記変更として保存してよい。この終了追記は通常成果の一括保存ルールの例外。
終了記録の保存失敗だけを理由に、保存済み論文を再処理・再追加しない。
