# Survey status dashboard and continuous discovery design

## Goal

Add a repository-native `STATUS.md` that is regenerated from canonical survey state and summarizes the latest processing run plus rolling 24-hour activity, while hardening the discovery specialist so it keeps searching across independent axes until execution resources or durable-state guarantees genuinely prevent further useful work.

## Dashboard architecture

`STATUS.md` is generated by `.survey/scripts/build_status_dashboard.py`; it is never manually edited. The generator consumes repository-owned state only: `.survey/work-queue/run-ledger.json`, `.survey/work-queue/discovery-state.json`, `.survey/work-queue/next-jobs.json`, `.survey/work-queue/jobs/*.json`, `.survey/work-queue/maintenance-cycle.json`, `.survey/reports/consistency-latest.json`, and GitHub fallback inbox/archive counts. ChatGPT Library pending is not visible to GitHub Actions, so the page explicitly marks that component as unavailable instead of guessing.

The page shows: current candidate inventory and queue health; latest normal worker run; latest discovery round; rolling 24-hour discovery and processing funnel; high/low-yield discovery axes; recent completed and queued papers; blockers/repairs; maintenance/consistency status; and warnings for low inventory, repair backlog, blocked jobs, sustained duplicate-heavy discovery, or processing/discovery imbalance.

The generator uses the newest timestamp already present in its source state as the `as of` timestamp. A no-op Actions run must therefore reproduce identical Markdown and must not create an empty timestamp-only commit.

A 7-day comparison is shown only when sufficient retained history exists. Until then it says `履歴不足`. Run-ledger retention is expanded to at least 192 runs and discovery history retention to at least 256 rounds so the comparison becomes meaningful over time.

## Continuous discovery architecture

The specialist discovery worker remains separate from the normal paper worker. The normal worker keeps its existing discovery capability. Candidate inventory watermarks remain useful for prioritization, but for the specialist worker they are not stop conditions: even at or above target inventory it continues low-cost, high-value discovery while execution budget remains.

Soft failures never end the specialist run: an empty axis, all-duplicate axis, low acceptance rate, one inaccessible paper, one failed source, one rate-limited source, one write collision, or one transport failure causes retry/fallback/axis rotation as appropriate. The worker records every round through `discovery_stats`, uses recent duplicate/acceptance metrics to avoid mechanically repeating exhausted axes, and explores new papers, forward citations, backward references, adjacent systems fields, query expansion, and priority themes.

Hard stop conditions are deliberately narrow: canonical repository state cannot be read well enough to deduplicate safely; neither GitHub nor Library can durably save discovered candidate state; the platform/tool execution ceiling is reached; or the worker has reasonably exhausted all currently promising independent axes after rotation. There is no fixed round count or fixed candidate quota.

## Safety and consistency

GitHub Actions remains the single writer of `discovery-state.json`. Specialist and normal workers submit statistics with their discovery submissions. The dashboard is generated after queue processing and run-ledger recording, before the final helper commit, so the page and canonical state land together.

All new behavior is covered by regression tests. Dashboard tests use synthetic state fixtures and verify rolling windows, deduplication, warning logic, and deterministic output. Discovery-stat tests verify expanded retention and source-worker metadata compatibility without breaking older submissions.
