# 候補IDの正規事前検査と取り込み設計

## 状態

レビュー待ち。実装は本設計書の確認後に開始する。

## 目的

Libraryの共有 `accept-candidates.json` にある候補を、正式な事前検査へ通してからGitHubの通常Discovery提出へ渡す。候補ごとに、アップロードへ進むか、完全な正規本文との重複として整理するか、一次資料を確認できず利用者の指示に基づき候補ファイルから除くかを追跡できるようにする。

現在、26件のDiscovery原本を最新判定で統合し、390件のaccept候補を同ファイルへ復元済みである。初期処理単位はこの390件とする。

## 背景と制約

- `.survey/scripts/process_discovery_precheck.py` はschema v3の固定取得元を処理する。リクエスト内の手入力 `records` は拒否する。
- `.survey/scripts/queue_worker.py` は、専用ワークフローが生成した事前検査結果、正しい `request_id`、`result_path`、`receipt` と、結果の `allowed_records` に含まれる識別子を検証する。
- Discovery提出は1ファイルあたり候補0〜5件。提出を受けて既存キューがResearch処理を行う。
- 事前検査ワークフローは `.survey/work-queue/discovery-precheck/requests/*.json` を監視する。通常のGitHub提出経路とワークフロー成果物を再利用できる。
- Scheduled Chatワーカーの通常探索ルールは変更しない。新経路は通常チャットから既存候補を取り込む用途に限定する。
- 一次資料の内容確認は、メタデータAPIの応答だけで済ませない。API照合と論文の一次資料確認を別段階として扱う。

## 方式の比較

### 推奨：安定IDによる照合を既存事前検査へ追加

候補IDだけをリクエストに含め、許可された公式APIからID単位で情報を取得する。取得した正規IDが入力IDと一致した記録だけを標準結果へ含め、既存の重複除外、結果署名、提出検証へつなぐ。

Semantic Scholarの公式APIには複数論文IDの照合経路があり、公開仕様の例にarXiv IDが含まれる。<https://api.semanticscholar.org/api-docs/snippets>

### 接続経路と代替経路

| 用途 | 第一経路 | 代替経路 | 切替条件 |
|---|---|---|---|
| arXiv / DOIのメタデータ照合 | Semantic Scholarの複数ID取得API | 同APIの単一ID取得を順に実行 | 一括POSTが利用できない、または一部IDだけが失敗 |
| arXiv一次資料 | arXivの公式概要・PDF | arXiv公式APIのID照会後、概要・PDFを取得 | HTML/PDFの片方が利用できない |
| DOI一次資料 | DOIを出版社へ解決 | 取得済み公式メタデータが示す出版社ページ | DOIリダイレクトだけでは題名・IDを確認できない |
| OpenReview候補 | `GET /notes?id=<note-id>` | OpenReview公式フォーラムページ | API認証・公開取得条件により片方が使えない |
| 事前検査の起動 | 要求JSONのGitHub pushで自動起動 | 既存workflowの `workflow_dispatch` に要求パスを指定 | push後に該当runが始まらないと確認できた場合 |

一つ目の通信経路が失敗したら、同じ要求IDと同じ候補集合を保って代替経路を試す。成功した経路・切替理由を結果と作業報告へ残す。前の実行が継続中か確認する前に重複要求を作らない。

### 不採用：題名の通常検索

検索順位や表記揺れに左右され、同名・類似題名の誤一致を確実に排除しにくい。390件の既知候補を再照合する経路としては再現性が不足する。

### 不採用：手入力レコードや手作りの事前検査結果

現行schema v3の禁止事項とワークフローの作成者検証を迂回する。標準の事前検査結果・レシートを得られない。

## 提案する構成

### 1. 候補IDリクエスト

既存の事前検査リクエストに、専用の取得元と `identifiers` 配列を追加する。配列には正規化済みの安定IDだけを許可し、題名、要約、著者、出典URLなどの候補レコードを受け付けない。`records` は引き続き禁止する。

初期実装では1リクエスト最大100 IDとし、arXivとDOIを識別子形式ごとに検証する。OpenReview IDは別の公式照会経路を使用する。公式経路からID・題名・一次資料URLを確かめられない候補は「未解決」と記録し、通常結果へ含めない。OpenReviewの公式API仕様はID指定を定義しているが、実行環境からの公開取得可否は実装時に検証する。<https://docs.openreview.net/reference/api-v2/openapi-definition>

### 2. API照合と結果生成

取得アダプターは、固定された許可先に対してIDを問い合わせる。返却された正規IDを入力IDと照合し、違うIDや曖昧な検索一致を拒否する。ネットワーク障害・レート制限は候補の不一致と扱わず、再試行後も未確認なら保留する。

結果には各入力IDの状態を含める。

- `allowed`: ID一致、正規化済み候補として評価可能
- `filtered_by_snapshot`: 既存本文、処理中job、過去の判定などにより標準フィルターで除外。自動的に重複完了とは見なさず、正規本文・Research job・却下記録を別々に照合する
- `provider_unresolved`: 公式取得元が入力IDに対応する記録を返さない
- `provider_error`: 一時的な取得障害で判定未完了
- `intra_batch_duplicate`: 同じ要求内で同一identityとして統合

成功した検査結果は従来どおり専用ワークフローが保存し、`allowed_records` と `receipt` を生成する。レシートは入力ID、個別状態、許可レコード、既存スナップショットのコミットを含む結果を対象に計算する。

### 3. 通常提出への接続

事前検査の `allowed_records` だけを使い、通常のDiscovery提出を0〜5件単位で作成する。各提出はワークフロー結果の `request_id`、`result_path`、`receipt` を参照する。提出後は既存のqueue workerにResearch処理を任せ、候補一覧だけで完了扱いにしない。

`filtered_by_snapshot` の候補は正規本文、処理中Research job、過去の却下記録を個別に照合する。処理中jobがあれば結果確定まで候補を残す。却下記録は重複ではないため、既存の再評価規則に沿って処理できない限り候補を保留する。GitHubに同じ正規本文がある場合は本文と品質を監査し、品質不足なら同じ正規パスを補完する。品質基準を満たした本文をmainから再取得できた後に限り候補一覧から除く。

### 4. 一次資料の確認と候補整理

候補の処理完了条件は次のとおり。

1. 新規候補：一次資料の内容を確認し、標準Research処理・品質検査を通し、main上の正規本文を再取得してIDと内容を確認する。
2. 既存候補：同一IDの正規本文と内容を確認する。品質不足なら同じ本文を補完してから再取得確認する。
3. 処理中候補：既存のResearch jobを確認し、結果が確定するまで候補を残す。
4. 一次資料を確認できない候補：一時的なネットワーク障害と区別してから、利用者の明示指示に従い該当IDの候補レコードだけを削除する。
5. 判定未完了：候補レコードを残し、理由を記録する。

Libraryの3ファイルのうち変更するのは処理が確定した `accept-candidates.json` の該当レコードだけとする。GitHub mainからの再取得確認後に限り削除し、各バッチ前に最新版を読み直してID単位でマージする。

## エラー処理

- 1件のID不一致・API未登録が同じバッチの他候補を失敗させない。
- 429や通信障害は規定回数再試行する。再試行後も取得不能なら `provider_error` として保持する。
- 結果ファイルの作成者、レシート、要求IDが不正ならqueue workerは従来どおり提出を拒否する。
- Libraryの版競合時は最新版を読み直し、他workerの追加・変更を維持してマージする。
- GitHub書込み・再取得・Library更新の成否が不明なら候補を削除しない。

## 変更対象

- `.survey/scripts/discovery_provider_adapter.py`: 安定ID取得元とID照合。
- `.survey/scripts/discovery_search_filter.py`: 候補IDごとに既存スナップショットによる除外理由を対応付ける。
- `.survey/scripts/process_discovery_precheck.py`: リクエスト検証、個別状態、結果・レシート生成。
- `.survey/tests/test_discovery_provider_adapter.py` と事前検査・提出検証テスト: 正常系、ID不一致、未知ID、一部失敗、スナップショット理由対応、重複、レシート検証。
- `.survey/docs/survey-workflow/worker-router.md`: 通常チャットによる候補取り込み経路を明記し、Scheduled workerの既存ルールとの境界を記す。
- Libraryの `github-import-procedure.md`: 実装後、実際に成功・再取得検証できた手順と代替経路だけを追記する。
- `.github/workflows/discovery-precheck.yml`: 既存の要求監視で動作する限り変更しない。

## 検証方針

テストではAPI応答を模擬し、次を検証する。

1. 手入力レコードと任意URLは拒否される。
2. 要求IDと返却IDが一致する候補だけが評価可能になる。
3. 重複、処理中、未確認、取得障害が個別状態として区別される。
4. `allowed_records` とレシートが同じ標準形式で出力される。
5. queue workerは専用ワークフロー由来の結果と完全一致する候補だけを受理する。
6. 通常探索provider、既存固定ソース、Scheduled Chatの動作は維持される。

## 完了条件

- 全390候補が「標準提出済み」「品質を満たす同一正規本文を確認済み」「一次資料未確認として指示どおり削除済み」のいずれかになる。
- 処理中または一時障害の候補は残数として明示され、未処理を完了扱いしない。
- GitHub main再取得と候補ファイルの最終件数で結果を照合する。
- 実行で検証できた経路を、既存Library手順書へ反映する。
