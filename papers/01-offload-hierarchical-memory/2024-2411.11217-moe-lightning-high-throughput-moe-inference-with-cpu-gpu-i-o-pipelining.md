# MoE-Lightning: High-Throughput MoE Inference with CPU-GPU-I/O Pipelining

> expertの配置・ロード・GPU計算をデータ中心にpipeline化し、メモリ制約GPUでMoEのI/O待ちを隠す推論システム。

## 概要
MoE-Lightningは、低VRAM GPUで多数requestをまとめて処理する **offline / batch-oriented serving** を主対象にする。expert weightとKV cacheをCPU DRAMへ置き、GPUは主にMoE FFNを計算し、decode attentionはCPUで処理する。

単にCPUへoffloadするだけではCPU–GPU transferとCPU attentionが新しいbottleneckになるため、`CGOPipe` というpipelineでweight transfer、KV移動、CPU attention、GPU MoEを細かく重ねる。さらに `HRM（Hierarchical Roofline Model）` がhardwareとworkloadから、どの処理をCPU/GPUへ置き、batch / micro-batchをどう切るかを探索する。

SSD / NVMeは検索空間から明示的に除外され、**CPU DRAM ↔ GPU VRAM** のweight + KV offloadが対象である。

## 手法のあらまし

MoE-Lightningの核は、weightとKVを同じoffload対象としてまとめるのではなく、**転送方向・再利用周期・計算先が違うデータとして別々にpipeline化する**ことにある。

### 1. `CGOPipe`：CPU・GPU・I/Oを4種類のflowとして重ねる

論文の **CGOPipe（CPU-GPU-I/O Pipeline）** は、単純なlayer pipelineではなく、1 layer / 1 micro-batch内で発生する複数のdata movementを別streamとして重ねる仕組みである。

主に次の4種類を並行化する。

| Flow | 転送方向 | 目的 |
|---|---|---|
| QKV / KV保存 | GPU → CPU | decode attention用のKVをCPUへ置く |
| Attention出力 | CPU → GPU | CPU attention後のhiddenをGPUへ戻す |
| Weight prefetch | CPU → GPU | 次に必要なMoE weightを先読み |
| KV関連の次処理 | GPU ↔ CPU | 次micro-batchのKV入出力を先行 |

重要なのは、これらを一つの大きな同期copyとして扱わず、**依存関係がないものは別々に進める**ことである。

### 2. `Paged Weights`：expert weightを一括転送しない

巨大なexpert weightをlayer単位で一括copyすると、そのcopyが終わるまで次のGPU計算を始められない。

そこでMoE-Lightningはweightを **paged weights** として小さく分割し、micro-batch計算の合間に順番に運ぶ。

`weight page 1を転送 → micro-batch 1を計算 → page 2を転送...`

のように流すことで、weight transferの一部を他のcomputeへ隠す。

ここでの`page`はOS pageそのものではなく、pipelineで扱いやすいweight chunkという意味である。

### 3. CPU attentionを選ぶ理由

KV cacheをCPUへ置いたままGPU attentionを実行しようとすると、decode stepごとに大量のKVをGPUへ戻す必要がある。

MoE-Lightningは逆に、**KVがあるCPU側でattentionを実行し、attention出力だけGPUへ返す**。

つまりFiddlerが「expert weightを動かす代わりにactivationをCPUへ送る」のと似た考え方を、decode attentionへ適用している。

CPU側にはIntel MKLベースのcustom GQA kernelを実装し、decode attentionの低い算術強度をCPU memory bandwidthで処理する。

### 4. `HRM（Hierarchical Roofline Model）`：配置とbatch分割を同時に探索する

論文固有の **HRM** は、通常のroofline modelをGPU単体ではなく、GPU・CPU・CPU–GPU link・memory容量まで含む階層へ拡張したcost modelである。

探索変数には、

- attentionをCPU/GPUどちらで処理するか
- MoE FFNをCPU/GPUどちらで処理するか
- GPUへ静的に置くweight比率 `r_w`
- GPUへ置くKV比率 `r_c`
- batch size `N`
- micro-batch size `μ`

が入る。

論文ではこれを6-tupleのpolicyとして探索する。

単純に「VRAMが空くまでoffloadする」のではなく、**CPU FLOPS、GPU FLOPS、各memory bandwidth、PCIe bandwidth、capacityを同時に満たすpolicyを選ぶ**点が特徴である。

### 5. `Micro-batch`はI/Oを隠すための時間窓として使う

batchを複数のmicro-batchへ分けると、あるmicro-batchをGPUで計算している間に、別micro-batchのweight / KVを転送できる。

ただしmicro-batchを細かくし過ぎるとkernel効率が落ち、粗すぎると転送を隠す機会が減る。

MoE-LightningではHRMがこのtrade-offを含めて`μ`を選ぶ。

可変長requestでは単純にrequest数を均等分割せず、**token数が近くなるようmicro-batchを構成してpaddingを抑える**。

### 6. Policyはrequestごとに再探索しない

HRMの探索はruntime中の各requestごとに行うのではなく、model / hardware / workload条件に対して事前にpolicyを決め、そのpolicyを実行時に固定する。

これによりonline optimization overheadを避ける一方、workload分布やhardware条件が大きく変われば再探索が必要になる。

## 評価

### まず見るところ
- **結論:** CPU attentionとGPU MoEをmicro-batch pipelineで重ねると、低VRAM GPUでも高throughput servingを大きく伸ばせる。
- **実速度:** single T4/L4で最大10.3倍、複数baselineに対して数倍のthroughput改善を報告する。
- **品質:** 同じattention / expert計算を実行するためlossless。
- **メモリ・I/O:** expert weightとKV cacheをCPU DRAMへ置く。SSDは使わない。
- **注意点:** latency最小化よりbatch throughput向け。batch/contextが大きくなるとCPU attentionが新しいbottleneckになる。

### Headline throughput

| 条件 | 改善 |
|---|---:|
| Single T4 / L4、最大 | **10.3倍** |
| Padding込み、vs FlexGen | 最大3.5倍 |
| vs FlexGen(c) | 最大5倍 |
| vs DeepSpeed | 最大6.7倍 |

10.3倍は最良条件のheadlineであり、すべてのworkloadで同じ倍率ではない。

### MTBenchの代表例

| 方式 | Throughput |
|---|---:|
| MoE-Lightning(p) | **30.12 tokens/s** |
| FlexGen、同一policy | 16.816 tokens/s |
| FlexGen、元policy | 9.5 tokens/s |

MoE-Lightning(p)では `μ=36, N=504`。同じplacement policyをFlexGenへ与えても差が残るため、**policy探索だけでなくCGOPipe実装自体の寄与**もある。

### HELM / Summarizationの代表例

| 方式 | Throughput |
|---|---:|
| MoE-Lightning | **12.393 tokens/s** |
| FlexGen | 7.14 |
| FlexGen(c) | 4.307 |
| DeepSpeed | 1.447 |

長いpromptではI/O / attentionの占有が増えるため、CPU attentionとmicro-batch pipelineの設計差が出やすい。

### Multi-GPU scaling

Mixtral-8x22Bで4×T4と2×T4を比較。

| 比較 | Throughput改善 |
|---|---:|
| 4×T4 vs 2×T4 | 2.77〜3.38倍 |

2倍のGPU数に対し2倍以上伸びるsuper-linear領域があり、GPU追加でcache / overlap条件も改善するためと解釈できる。

### CPU attentionの限界

論文のcustom CPU attention kernelはKVをGPUへ転送する方式より3〜4倍速い条件を示すが、batchやcontextが大きくなるとCPU側のmemory bandwidth / computeが律速になる。

つまりKVをCPUへ置くこと自体が常に速いのではなく、**CGOPipeでCPU attentionを他のGPU計算へ隠せる範囲で有効**である。

### 評価上の制約

- offline / batch-oriented throughputが主目的。
- interactiveなbatch=1 latency最小化とは評価軸が異なる。
- CPU DRAMへ全モデル / KVを置ける容量が必要。
- Disk offloadは未実装・検索空間外。
- multi-node通信はHRMの中心対象ではない。
- KV sparsityなどの追加最適化は扱わない。
- policyはhardware / workloadごとに再探索が必要。
