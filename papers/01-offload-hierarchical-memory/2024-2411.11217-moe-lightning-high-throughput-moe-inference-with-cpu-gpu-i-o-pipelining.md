# MoE-Lightning: High-Throughput MoE Inference with CPU-GPU-I/O Pipelining

> expertの配置・ロード・GPU計算をデータ中心にpipeline化し、メモリ制約GPUでMoEのI/O待ちを隠す推論システム。

## 概要
対象はレイテンシ最小化より、同じGPUで多数要求を流すスループットである。CPU DRAMが十分に大きいサーバーを前提に、KVをGPUに残す従来構成の容量圧迫を解消する。ユーザー対話の低batch・短文だけでなく、長文要約や合成推論を含めて政策を比較する。
KVのCPU常置はGPUメモリを空ける一方、decode attentionのCPU演算を新たに発生させる。この交換をmicro-batchで隠せるかが成否を分けるので、単にCPUへKVを置けば速くなるという主張ではない。
MoE-Lightningは、低コストGPUでのoffline・batch-oriented高スループット推論に特化する。CPU memoryにexpert weightとKV cacheを置き、GPUはMoE FFNを主に計算、attentionはCPUで実行する構成を、CPU–GPU–I/OのCGOPipeで細粒度に重ね合わせる。重みはSSDへ逃がさずCPU DRAMに全体を保持する（論文はdisk offloadingを検索空間から明示的に除外）。prefillではGPU計算後にKV cacheをCPUへ置き、decodeではCPU attention、GPU post-attention/MoE FFN、weight転送を同時進行する。したがってweight offloadとKV cache offloadの双方を扱うが、KVをSSDへ保存する研究ではない。HRM（Hierarchical Roofline Model）がGPU/CPU FLOPS、GPU/CPU memory bandwidth、CPU–GPU bandwidth、GPU/CPU容量、batch/micro-batch、GPU常駐weight/KV比をもとに政策を探索する。
## 手法のあらまし
weightとKVを同じCPUへ置いても、両者の転送方向と再利用周期は異なるため、CGOPipeは一つのキャッシュとして扱わない。探索した政策はモデル・GPU・入力分布ごとに変わり、単一の常駐率を別ハードウェアへ移植できない。paddingを含む実際の長さも探索制約に入れる。
実行時にはこの政策を固定し、要求ごとの再最適化コストを避ける。
CGOPipeは、QKV結果のGPU→CPU、CPU attention後hiddenのCPU→GPU、次層weight transfer、次micro-batchのKV transferという4種の転送を、方向別の独立経路と非同期依存でスケジュールする。weight全体を一括で移すと次層の開始を塞ぐため、pipeline内micro-batch数に合わせてpaged weightsへ分割し、転送と中間結果を交互に流す。CPU側にはIntel MKLベースのcustom GQA kernelを実装し、decode attentionの低い算術強度をCPUへ移す。HRMは、attentionをCPU/GPU、MoE FFNをCPU/GPU、GPU静的weight比rw、GPU KV比rc、batch N、micro-batch μの6-tupleを制約付きで探索する。主設定はCPU attention（Ag=0）＋GPU MoE FFN（Fg=1）。可変長requestでは最長promptからtoken数が均等になるようmicro-batchを組み、paddingを抑える。KV cacheはCPUに常置し、GPUへ戻す方式よりCPU attentionを使って転送を減らす。
## 評価

### まず見るところ
- **結論:** CPU attentionとGPU MoEをmicro-batch pipelineで重ねると、低VRAM GPUでも高throughput servingをかなり伸ばせる。
- **速度・効率:** batchをまとめてI/Oと計算を隠せるoffline servingでは強いが、対話的な低batch latency最小化とは目的が違う。
- **品質:** 同じexpert・attention計算を実行するため品質は変えない。
- **メモリ・I/O:** expert weightとKV cacheをCPU DRAMへ置き、SSDは使わない。GPU VRAMを空ける代わりにCPU attentionの演算負荷が増える。
- **評価の強さ／注意点:** **実機**。CPU DRAM容量とCPU attention性能が十分なサーバー向けで、batch/contextが大きすぎるとCPU側が新しい律速になる。
