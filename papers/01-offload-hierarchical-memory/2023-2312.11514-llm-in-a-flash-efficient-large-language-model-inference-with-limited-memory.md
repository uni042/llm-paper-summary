# LLM in a Flash: Efficient Large Language Model Inference with Limited Memory

> Flashから必要な重み行列部分だけを読み、windowingとrow-column bundlingで端末上LLMのI/OとDRAM使用量を減らす手法。

## 概要
対象は端末内完結の推論であり、重みの正確な値を保持したまま読み出し量だけを削る点が要点である。従って疎性を持たない一般モデルではこの数値を期待できず、フラッシュの実効帯域と読み出し粒度が支配的になる。
LLM in a Flashは、GPU/CPUのDRAMにモデル全体を保持できない端末で、モデル重みをフラッシュ（実験ではSSD）に置き、必要な部分だけDRAMへ読み込む重みストリーミング方式を示した論文である。MoE専用システムではなく、OPT 6.7Bと、ReLU化して疎化したFalcon 7Bを対象に、FFNの活性化疎性を重みI/O削減へ転用する。著者らの観測ではOPTのFFNは97%、Falcon（sparsified）は95%が疎であり、各トークンで必要なニューロンはごく一部である。提案はモデル品質を再学習で変えるものではなく、既存のスパースな推論計算で必要な重み行・列のみを読む。評価はApple M1 Max（1 TB SSD、CPU、32-bit）とLinux＋RTX 4090 24 GB（BF16、GPU）で、モデルサイズのほぼ半分だけを計算用メモリに割り当てる。したがって、これはNVMe/フラッシュからのweight offloadであり、MoEのexpert cacheやKV cacheを主対象にした研究ではない。ただし論文はKV cache等にも同じ考えを一般化できると述べるだけで、KVを主評価したわけではない。
端末内でプライバシーを保ったまま大きなモデルを動かすことが狙いで、ネットワーク越しの分散推論や学習時のパラメータ配置はスコープ外である。「フラッシュ容量は大きいがランダムread帯域が低い」という性質を前提にするため、GPU HBMやCXLメモリの結果と単純比較できない。
## 手法のあらまし
フラッシュI/Oのレイテンシ（特に小さなランダムreadのfirst-byte待ち）と、DRAM/GPU計算のコストを含むロードコストモデルを作り、転送量とチャンクサイズを同時に最適化する。第一のwindowingは直近kトークンで使われたニューロンをDRAMに一時保持し、累積利用集合との差分だけを次トークンで読むスライディング窓である。第二のrow-column bundlingは、up-projectionの行とdown-projectionの列を隣接配置し、必要な要素を別々の小readにせず連結チャンクとして読む。低ランクpredictorはattention出力からReLU後にゼロになるup-projection要素を予測し、非ゼロ候補だけロードする。windowingと予測により各問い合わせでFFNの約2%だけをflashから読む。静的なDRAM事前確保で再配置も抑え、32スレッドread、macOSのF_NOCACHE／LinuxのDirectIOでOSキャッシュに依存しない測定を行う。予測が外れた場合の正確性を損なわないため、計算そのものは元の重みを使い、I/O対象を選択する設計である。row-column bundlingは余分なデータを読んで捨てる場合も、細切れreadを繰り返すより総時間が短いというストレージ固有のトレードオフを利用する。predictorはFFNを完全に置換するものではなく、候補要素を絞る補助計算であり、attention重みやembeddingは常駐させて読み戻しを避ける。
expertの再利用は同一要求内では強くても、要求を混ぜると平均化されるため、固定人気順だけでは十分でない。この性質が後続のMoE-Infinityの要求別トレースやFiddlerの実行時判断とは異なる研究動機になっている。
## 評価
理論的に、使用可能DRAMがモデルの約半分でもモデル全体の実行を可能にし、単純な「毎forwardで全重みを再ロード」方式に対して、論文要約の総合値ではCPUで4–5倍、GPUで20–25倍の高速化を報告する。Falcon 7B（M1 Max、window=4）では1トークン当たりflash load約161 ms、メモリ管理90 ms、合計約250 msで、ベースライン約2330 msの約9–10倍。4090側の16-bit構成ではflash load 40.5 ms、メモリ管理約40 ms、ベースラインのI/Oは2000 ms超であった。OPT/Falconの比較はper-token latency、C4検証から窓サイズを決め、論文はFlexGenと理論的な最低I/O（モデル半分を読む）を比較対象にする。限界は、単一系列・単一バッチ中心で、論文自身もバッチ、prompt処理、speculative decoding、電力・熱を未検討と認める点、PyTorch実装がアルゴリズム実証で低レベル最適化未実施である点である。公式の著者コードは確認できず、一次資料は[arXiv本文](https://arxiv.org/abs/2312.11514)と[Apple Researchページ](https://machinelearning.apple.com/research/efficient-large-language)である（第三者実装は論文公式ではない）。
M1 Maxの測定はOSバッファキャッシュを無効化した保守的な下限で、キャッシュを許せば値は変わり得る。評価指標は主にI/O＋管理＋計算の平均token latencyで、品質値は疎化Falconの前提に依存する。
