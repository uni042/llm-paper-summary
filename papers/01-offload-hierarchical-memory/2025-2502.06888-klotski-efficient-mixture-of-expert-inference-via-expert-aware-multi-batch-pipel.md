# Klotski: Efficient Mixture-of-Expert Inference via Expert-Aware Multi-Batch Pipeline

> 複数batchのhot expert計算でcold expertのCPU／SSD I/Oを隠し、巨大MoEを単一GPUで動かすexpert-aware pipeline。

## 概要
Klotskiは、GPU VRAMにexpert weightが収まらないMoEで、**複数batchを同時に流してGPU計算時間を長くし、その間にCPU RAM / SSDから次expertを読む**ことでI/O bubbleを隠す推論engineである。

Dense LLMならbatchを増やすほどweight再利用が効きやすいが、MoEではbatchを増やすとactive expert集合も広がり、単純なmulti-batch化だけではI/O量も増える。Klotskiはこの問題に対し、複数batchで共通して使われる**hot expertを先にGPUで計算し、その計算時間をcold expertのprefetch窓として使う**。

RTX 3090環境では実際のSSD（約1 GB/s read）まで含めて評価しており、CPU DRAMだけのoffloadより階層が深い。

## 手法のあらまし

Klotskiでは `batch group`、`two-level prefetch`、`hot expert prediction`、`expert-aware execution order` が重要な概念になる。

### 1. `Batch Group`：複数batchを一つのpipeline単位として扱う

Klotskiはbatchを単純に大きくするのではなく、複数のbatchをまとめた **batch group** をpipeline単位として扱う。

batch group内のbatch数を`n`とすると、`n`を増やすほどGPU計算時間が長くなり、その裏でweight I/Oを隠しやすくなる。

一方で、

- active expert数が増えて読むweightも増える
- KV cacheが増える
- VRAM使用量が増える

ため、`n`は大きければよいわけではない。

online plannerは各layerのcompute時間とI/O時間をprofileし、**I/O bubbleをほぼ隠せる最小の`n`**を選ぶ。

### 2. CPU RAMが十分な場合：1段先のweightをprefetchする

CPU RAMへmodel全体を保持できる場合は、GPUがlayer `i`を計算している間にlayer `i+1`で必要になるtensorをCPU→GPUへprefetchする。

これは通常のdouble-buffer的なpipelineだが、MoEでは全expertを読むのではなく、後述のhot expert予測を使って優先順位を付ける。

### 3. CPU RAMも足りない場合：`Two-Level Prefetch`

Klotskiの特徴的な点が、SSDまで使うときの **two-level prefetch** である。

CPU RAMには固定で`L` layer分程度のweight windowを持ち、同時に二つのprefetchを走らせる。

- GPU側：CPU RAMから近い将来のlayerを読む
- CPU側：SSDからさらに先のlayerをRAMへ読む

イメージとしては、GPUが`i+1`用weightをRAMから受け取っている間に、CPUがSSDから`i+L`用weightを先回りして読む。

これによりGPUが低速SSDを直接待つことを避け、**SSD → CPU RAM → GPU VRAM** の二段pipelineを形成する。

### 4. `Hot Expert Prediction`：全expertを先読みしない

multi-batchではactive expert数が増えるため、全候補をprefetchすると帯域を使い切ってしまう。

そこでKlotskiはofflineにexpert相関表を作り、直前layerのrouting履歴から現在layerでhotになりそうなexpertを予測する。

論文の主設定ではpath length `l=1`、つまり**直前layerのexpert選択だけ**を主な予測信号に使う。

複数batchのrouting傾向を集約し、「batch group全体で多く使われそうなexpert」を先に読むことで、少数tokenだけが使うcold expertのI/Oを後回しにする。

### 5. `Expert-Aware Execution Order`：hot expert計算をI/O隠蔽窓にする

通常はrouterが出したexpert順に近い形で計算してしまいがちだが、Klotskiは**GPUにすでにあるhot expertを先に計算**する。

そのhot expert計算中に、まだGPUにないcold expertをCPU / SSDからtransferする。

つまり実行順を、

`routing順` ではなく `I/Oを隠しやすい順`

へ並べ替える。

expert outputは最終的に元のtoken位置へ戻すため、計算順変更自体はmodel qualityを変えない。

### 6. 4本のCUDA streamを用途別に分ける

実装では少なくとも次のstreamを独立に動かす。

| Stream | 役割 |
|---|---|
| Weight prefetch | 次weightをCPU→GPUへ読む |
| Expert transfer | gate確定後の必要expertを補う |
| KV prefetch | 次micro/batch用KVを用意 |
| KV save | 計算済みKVを保存 |

weightとKVを同じcopy queueに詰めないことで、独立なI/Oを重ねる。

### 7. HQQ量子化とSparse Attentionは補助opt-in

Klotskiは4-bit HQQでweight transfer量を減らす構成や、StreamingLLM型のsparse attentionでmulti-batch時のKV cacheを抑える構成も評価する。

ただしこれらはpipelineそのものとは別の最適化である。

- HQQ → weight byte数を減らす
- sparse attention → KV容量を減らす
- Klotski pipeline → I/O待ちを計算へ隠す

と役割を分けて読む必要がある。

## 評価

### まず見るところ
- **結論:** multi-batchのhot expert計算をI/O隠蔽窓として使うと、CPU RAMだけでなく実SSDまで含むoffloadでも巨大MoEを単一GPUで動かせる。
- **実速度:** Mixtral-8x22BをRTX 3090で1.3 tokens/s超、H800で約53 tokens/sまで引き上げるablationを示す。
- **品質:** pipeline/cache/prefetch自体はlossless。4-bit量子化やsparse attentionを有効化した場合は別のquality trade-offがある。
- **メモリ・I/O:** **RTX 3090環境では実SSD 1 GB/sを使用**し、SSD→RAM→GPUの二段prefetchを評価。
- **注意点:** batch groupを増やすとKV cacheが膨らむため、I/O隠蔽とVRAM消費のtrade-offが強い。

| Model | 総parameter規模 | Precision |
|---|---:|---|
| Mixtral-8x7B | 約46.7B | BF16 / optional quantization |
| Mixtral-8x22B | 約141B | BF16 / optional quantization |

主条件はinput 512、output 32、batch 4〜64。

### 比較対象

| Baseline | 特徴 |
|---|---|
| Hugging Face Accelerate | 一般的offload |
| DeepSpeed-FastGen | serving runtime |
| FlexGen | multi-batch階層offload |
| MoE-Infinity | routing-aware expert cache |
| Fiddler | CPU/GPU expert execution切替 |

### Headline最大throughput改善

| 比較対象 | 最大speedup |
|---|---:|
| Accelerate | **85.12倍** |
| FastGen | **15.45倍** |
| FlexGen | **2.23倍** |
| MoE-Infinity | **19.06倍** |
| Fiddler | **9.53倍** |

非常に大きな倍率は、一部baselineが巨大22B MoEのSSD / low-memory条件でほぼI/O stallしていることも含む。通常のGPU-resident推論に対する85倍高速化という意味ではない。

### RTX 3090 / Mixtral-8x22B ablation

| 構成 | Throughput |
|---|---:|
| Simple pipeline | 0.01 token/s |
| + Multi-batch | 0.97 |
| + Hot-only prefetch | 1.127 |
| + Expert順序調整 | **1.325** |
| + Quantization | **1.366** |

最大のジャンプはmulti-batch化で、**GPU computeを長くしてSSD / CPU I/Oを隠す時間窓を作ること**がまず重要だと分かる。その後hot predictionと実行順序が上積みする。

### H800 / Mixtral-8x22B ablation

| 構成 | Throughput |
|---|---:|
| Simple pipeline | 1.149 token/s |
| + Multi-batch | 34.07 |
| + Hot-only prefetch | 44.17 |
| + Expert順序調整 | 52.85 |
| + Quantization | **53.125** |

H800ではCPU RAMが十分でdiskが主bottleneckではないため、主にCPU↔GPU pipelineとexpert-aware schedulingの効果を見る結果になる。

### Expert予測精度

論文では複数の予測指標を報告する。

| 指標 | 値 |
|---|---:|
| Layer内で必要expertを何らか先読みできた率 | 100% |
| Single sequence平均 | 42.24% |
| Hot expert選択精度 | 58.89% |

`100%`だけを見ると完全予測に見えるが、これは広い候補集合で必要expertをcoverした指標。実際に優先prefetchするhot expertの精度は約59%であり、指標を分けて読む必要がある。

### GPU memory削減

| 条件 | Memory削減 |
|---|---:|
| ほぼ全tensor offload | 94.1%以上 |
| 3090級の実用設定 | 約74.5%削減と報告 |

memoryを減らすほどI/O量は増えるため、throughputとセットで評価する必要がある。

### Large batch

batch 128でもFlexGenより約15%高いthroughputを報告する。ただしbatch groupを増やすとKV cacheが増加し、Fiddler / MoE-Infinityは22Bでbatch16付近が上限になった条件もある。

### 評価上の制約

- SSD性能はEnvironment 1の約1 GB/sに依存する。
- Environment 2はCPU RAMが十分で、disk I/O評価とは性質が違う。
- expert相関表はoffline warm-upが必要。
- routing patternが変わるとhot expert predictionが外れ得る。
- batch groupを大きくするとKV cache OOMが起こる。
- HQQ / sparse attentionを使う場合、pipelineとは別の品質影響がある。
- 実装はPyTorch + Hugging Face + FlexGen上の研究prototypeで、version差に注意が必要。
