# MLP-Offload: Multi-Level, Multi-Path Offloading for LLM Pre-training to Break the GPU Memory Wall

> optimizer stateをGPU・DRAM・NVMe・並列ファイルシステムへ多階層・多経路配置し、汎用HPC環境でLLM事前学習のI/Oを並列化する。

## 概要
MLP-Offloadは、LLM pre-trainingで最大容量を占めるFP32 optimizer stateをGPU、host DRAM、node-local NVMe、parallel file system／object storeへ分散するmulti-level, multi-path offloadingである。単純なGPU→CPU→SSDという一本の階層では、modelが大きくなるとlocal NVMe容量または帯域が飽和し、遠隔storageを使うとnetwork経路が新たなbottleneckになる。MLP-Offloadは複数tierと複数I/O pathを同時利用し、各subgroupのoptimizer更新をcache-friendlyな順序で処理する。登録済みSmart-Infinityのcomputational storage（ストレージ計算）方式を引用するが、専用CSD hardwareを必要とせず、既存HPC clusterのNVMeとshared PFSを使う点が対照的である。対象は学習時optimizer stateが中心で、MoE inferenceのexpert weight offloadやKV cache offloadではない。通常NVMe、VAST／Lustre系parallel storageを実機評価し、HBFではない。将来tierとしてCXLを議論し得る設計だが、主要結果はCXL実機によらない。SC 2025掲載で、40B〜280B級modelを少数GPUで扱うcapacityとtraining throughputの双方を示す。
## 手法のあらまし
model stateをsubgroupへ分割し、更新対象subgroupだけをGPU／CPUへstageする。optimizer stateはDRAMに収まる分をcacheし、残りをlocal NVMeまたはshared PFSへ配置する。PFSを単なるoverflow先ではなくvirtual third-level tierとして扱い、local disk経路とnetwork storage経路を並列利用する。tierごとのthroughputとconcurrency特性をprofilingし、queue depthや同時I/O数を別々に制御して、一方の混雑が全経路を止めないようにする。更新順序は再利用可能なstateがcacheに残るようsubgroup localityを優先する。gradientはGPUからFP16のまま退避し、CPUでoptimizer更新直前にFP32へ変換することで転送byte数を抑える。parameter read、gradient write、optimizer state read/writeをdouble bufferでoverlapし、複数pathへ分散する。GPU memory、DRAM、NVMe capacity、PFS bandwidthの違いを統一plannerで扱うが、near-storage computeは行わない。したがってSmart-InfinityのようにSSD側FPGA／processorでoptimizerを実行する方式とは異なり、汎用CPUと既設storageを活用するsoftware systemである。
## 評価

### まず見るところ
- **結論:** optimizer stateをDRAM・local NVMe・shared storageへ複数経路で分散すると、SSD offloadを単なる容量拡張ではなくthroughput改善にも使える。
- **速度・効率:** ZeRO-3より大きく高速化し、local tierだけでも改善が出る。
- **品質:** 学習アルゴリズム自体は変えないため品質は原則同等。評価は主にsystem metrics中心。
- **メモリ・I/O:** **通常NVMe＋parallel file system** を実機利用し、専用computational storageは不要。
- **評価の強さ／注意点:** **実機**。HPC向けで、shared PFSの帯域や他jobとのcontentionに強く依存する。consumer PCではlocal NVMe＋DRAM部分だけが該当する。

<details>
<summary>評価条件・詳細な数値を開く</summary>

40B〜280B modelを、4×H100 80GBのJLSE環境と4×A100 40GBのPolaris環境で評価する。各nodeは512GB RAM、RAID NVMe、VASTまたはLustre PFSを備える。DeepSpeed ZeRO-3に対して最大2.5倍、PFSを使わずlocal tierだけでも最大1.6倍高速化し、大規模modelのaggregate I/O throughputを約2倍に高めた。gradient accumulationを使う条件でも少なくとも40%高速で、単にcapacityを拡張するだけでなくiteration timeを改善する。実機測定でありsimulation-onlyではない。一般的なNVMeとshared storageを使うためHPCへの適用性は高いが、PFSが十分な帯域とisolated pathを提供することが前提で、他jobとのnetwork contentionが強いclusterでは性能予測が難しい。consumer PCではPFS経路を使えず、local NVMe＋DRAM部分だけの恩恵になる。qualityは学習アルゴリズムを変えないため同等とされるが、収束curveやdownstream scoreよりsystem metrics中心。artifactは公開されるが、DeepSpeedやcluster storage設定への統合作業は必要である。
