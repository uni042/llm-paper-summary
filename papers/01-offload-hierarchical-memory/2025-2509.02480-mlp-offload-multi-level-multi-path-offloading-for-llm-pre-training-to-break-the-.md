# MLP-Offload: Multi-Level, Multi-Path Offloading for LLM Pre-training to Break the GPU Memory Wall

> optimizer stateをGPU・DRAM・NVMe・並列ファイルシステムへ多階層・多経路配置し、汎用HPC環境でLLM事前学習のI/Oを並列化する。

## 概要
MLP-Offloadは、LLM pre-trainingで巨大になるFP32 optimizer stateを、GPU / host DRAM / node-local NVMe / shared parallel file systemへ分散するtraining systemである。

特徴は単純な「GPU→CPU→SSD」という一本のoffload chainではなく、**local NVMe pathとnetwork storage pathを同時に使うmulti-path構成**にある。local SSDのcapacityやbandwidthが足りない場合でも、PFSを単なるoverflow先ではなく並列に使える第三tierとして扱う。

対象はoptimizer state、parameter、gradientのtraining stateであり、MoE inferenceのexpert weightやKV cacheではない。専用computational storage hardwareは不要で、通常NVMeと既存HPC shared storageを使う。

## 手法のあらまし

MLP-Offloadの論文固有ポイントは、`multi-level` と `multi-path` を分けて考えると分かりやすい。

### 1. `Multi-Level`：stateを複数の容量tierへ置く

model / optimizer stateをsubgroupへ分割し、現在更新するsubgroupだけをGPU / CPUへstageする。

残りは、

| Tier | 役割 |
|---|---|
| GPU HBM | 今まさに計算するstate |
| Host DRAM | 再利用が近いstateのcache |
| Local NVMe | DRAMに入らない大容量state |
| Shared PFS / Object Store | local NVMeにも収まらないstate |

へ配置する。

ここでPFSはcheckpoint保存用だけではなく、**training iteration中に直接読むactive storage tier**として使われる。

### 2. `Multi-Path`：local diskとnetwork storageを同時に流す

通常の階層offloadでは、下位tierへ行くほど一つのpathを順番に通る。この場合local NVMeが詰まると全I/Oが止まる。

MLP-Offloadはlocal NVMe経路とPFS経路を独立queueとして扱い、parameter / optimizer stateを複数pathへ分散する。

つまりcapacityを増やすだけでなく、**aggregate I/O bandwidthを複数pathで足し合わせる**ことを狙う。

### 3. `Subgroup`単位でoptimizer updateをstageする

ZeRO系と同様にstateをsubgroupへ分割し、全model stateを同時にGPUへ戻さない。

あるsubgroupを更新するときだけ、

`storage → DRAM → GPU/CPU update → storage`

というstreamを流す。

subgroupを小さくすればpeak memoryは下がるがI/O request数が増えるため、cache localityとI/O効率のtrade-offがある。

### 4. `Cache-friendly update order`：次に使うstateをDRAMへ残す

subgroupの更新順序を固定のmodel順へするのではなく、DRAM cacheに残っているoptimizer stateを再利用しやすい順序へ寄せる。

これにより、直前に読んだstateをすぐstorageへ戻して再び読む、といったthrashingを減らす。

ここでのcacheはGPU expert cacheではなく、**training optimizer stateのhost-memory cache**である。

### 5. GradientをFP16のままoffloadする

optimizer updateは通常FP32 stateを使うが、gradientをGPUから退避する時点ではFP16のまま送り、CPUでoptimizer update直前にFP32へ変換する。

これによりGPU→CPU / storageへ流すgradient byte数を抑える。

数値計算の最終optimizer updateを低精度化するわけではなく、**transport representationだけを小さくする**設計である。

### 6. `Double buffering`でread / compute / writeを重ねる

parameter read、gradient write、optimizer state read/writeを別bufferへ入れ、あるsubgroupを計算している間に次のstateを読み、前のstateを書き戻す。

さらにlocal NVMeとPFSのqueue depth / concurrencyを別々にprofileし、一方のstorageが混雑してももう一方まで同期停止しないようにする。

### 7. Smart-Infinityとの違い

Smart-InfinityはSSD側に演算機能を持たせ、optimizer計算をstorage近傍で実行する。

MLP-Offloadはnear-storage computeを使わず、**普通のCPU + NVMe + shared storageをsoftware schedulingで並列利用する**。

したがって専用hardwareなしで導入しやすい代わりに、PFS/network bandwidthとCPU optimizer性能に依存する。

## 評価

### まず見るところ
- **結論:** optimizer stateをDRAM・local NVMe・shared PFSへmulti-pathで分散すると、capacityだけでなくtraining I/O throughputも改善できる。
- **Training throughput:** ZeRO-3比最大2.5倍、local tierだけでも最大1.6倍。
- **I/O:** aggregate throughputを約2倍まで高める条件を示す。
- **品質:** training algorithm自体は変えず、主評価はsystem性能。downstream accuracyの広範比較は中心ではない。
- **注意点:** HPC向け。shared PFS性能・network contentionに強く依存し、consumer PCでは主にDRAM + local NVMe部分だけが該当する。

### 実機環境

| 環境 | GPU | Host RAM | Storage |
|---|---|---:|---|
| JLSE | 4×H100 80 GB | 512 GB | RAID NVMe + VAST系shared storage |
| Polaris | 4×A100 40 GB | 512 GB | Local NVMe + Lustre系PFS |

40B〜280B級modelを評価する。

### 主な比較

| 条件 | MLP-Offloadの改善 |
|---|---:|
| vs DeepSpeed ZeRO-3 | **最大2.5倍** |
| PFSなし、local tierのみ | **最大1.6倍** |
| Aggregate I/O throughput | 約2倍 |
| Gradient accumulation条件 | 少なくとも約40%高速 |

PFSを使わなくても改善が残るため、利得がshared storage容量だけによるものではなく、subgroup scheduling / overlapにもあることが分かる。

### 何が速くなっているか

これはinference token/sではなく、**training iteration / throughput** の改善である。

特にmodelが大きくoptimizer stateがDRAMから溢れるほど、local NVMeとPFSを同時利用する価値が増える。

### Capacity面

40B〜280B級のstateを少数GPUで扱うことを示し、GPU / DRAMだけでは保持できないoptimizer stateをNVMe / PFSへ逃がす。

これはmodel parameterそのものを削減したのではなく、**training stateのresident locationを変えてcapacity wallを越えている**。

### 評価上の制約

- PFSに十分な帯域があるHPC clusterを前提とする。
- 他jobとのnetwork / storage contentionが強いと結果は変わる。
- consumer PCではshared PFS pathを再現できない。
- quality評価よりsystem throughput / I/Oが中心。
- DeepSpeed / cluster storageとの統合作業が必要。
