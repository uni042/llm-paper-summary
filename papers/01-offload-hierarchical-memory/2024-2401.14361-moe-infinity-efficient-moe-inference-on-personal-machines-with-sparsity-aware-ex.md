# MoE-Infinity: Efficient MoE Inference on Personal Machines with Sparsity-Aware Expert Cache

> sequenceごとのexpert活性局所性を使うsparsity-aware cacheと先読みで、個人PC上の階層メモリMoE推論を高速化するシステム。

## 概要
MoE-Infinityは、個人PCで典型的なbatch=1・単一ユーザーのdecodeでは、**同じrequestの中でexpert activation patternに局所性がある**ことを利用するMoE inference systemである。

expert weightの正本は主にhost DRAMへ置き、GPUにはdense weight、attention、KV cacheと一部hot expertだけを置く。単純LRUではなく、現在requestのrouting履歴から「この先どのexpertが再利用されそうか」を予測してprefetch / evictionを行う。

公開実装はSSDを含む階層にも対応するが、論文の主な実機結果は**CPU DRAM ↔ GPU VRAM**のexpert offloadとして読む方が正確である。KV cacheはGPUへ残すため、長文ではexpert cacheとは別にKV容量がbottleneckになる。

## 手法のあらまし

MoE-Infinityの独自性は、単純なexpert frequencyではなく、**requestごとのrouting pattern全体を行列として記録し、似た過去requestから未来のexpert利用を予測する**点にある。

論文中では `iEAM`、`rEAM`、`EAMC`、`pEAM` という似た名前が出てくるため、役割を分けて見ると理解しやすい。

### 1. `iEAM`：1 iteration分のexpert activationを記録する

**iEAM（iteration-level Expert Activation Matrix）** は、ある生成iterationで各layer・各expertへ何token流れたかを表す行列である。

ざっくり言えば、

`行 = MoE layer`、`列 = expert`、`値 = そのiterationで何token選ばれたか`

というrouting traceになっている。

単なる「expert 3がhot」という1次元frequencyではなく、**どのlayerでどのexpertが使われたか**を残すため、requestのrouting patternをより細かく表せる。

### 2. `rEAM`：request全体のrouting傾向を累積する

生成が進むたびにiEAMを足し合わせ、request単位で累積したものが **rEAM（request-level EAM）** である。

rEAMは「このrequestでは、全体としてどのlayerのどのexpertが使われやすいか」を表すfingerprintのような役割を持つ。

MoE-Infinityは、同じタスクや似たpromptではrEAMも似やすいと仮定する。

### 3. `EAMC`：過去requestのrouting patternを蓄積する

過去requestのrEAMをそのまま無制限に保存すると検索costが増えるため、論文では履歴集合を **EAMC（Expert Activation Matrix Cache / Collection）** として管理する。

過去のrEAMをK-meansでまとめることで、Switch系を除く多くのモデルでは1000系列をおよそ10〜30個程度の代表clusterへ圧縮できると報告している。

ここでK-meansを使う目的はexpertをcluster化することではなく、**似たrequest routing patternをまとめること**である。

### 4. 過去の似たrequestから未来routingを予測する

現在requestのiEAMをflattenし、EAMC中の過去patternとcosine距離で近いものを探す。

近い複数のrEAMを合成すると、「このrequestが今後どのexpertを使いそうか」という予測分布を作れる。

さらにMoE-Infinityは **layer-proximity係数** を掛ける。

これは、

- すぐ次のlayerの予測は重要
- かなり先のlayer予測は不確実

として、現在位置から遠いlayerほど予測weightを弱める仕組みである。

この最終的な予測行列が **pEAM（predicted EAM）** で、prefetchとcache evictionの判断に使われる。

### 5. `Sparsity-Aware Expert Cache`：LRUではなく未来再利用確率で追い出す

通常のLRUは「最後にいつ使ったか」でevictionするが、MoE-InfinityはpEAMから得た**将来再利用確率**も見る。

cacheが満杯の場合、

- 近いうちに再利用されそうか
- どのlayerに属するか
- 過去にどの程度cache hitしているか

などを組み合わせ、将来価値が低いexpertから追い出す。

特に初期layerはrouting predictionがまだ安定しにくいため、cache優先度を高める設計も入っている。

### 6. Prefetchが外れてもnative expertへfallbackする

pEAMはあくまでprefetch用であり、native routerを置き換えない。

予測が外れた場合は、実際にrouterが選んだexpertをhostからon-demand fetchして計算する。

したがって、

- hit / 正しいprefetch → latency削減
- miss / 誤prefetch → 同期fetchが発生して遅くなる

という関係で、**予測誤差は品質ではなくI/Oコストへ出る**。

### 7. この方式が効きやすいrequest分布

MoE-Infinityはrequest-level localityを前提にするため、同じ種類のtaskや似たpromptを繰り返す環境では履歴が効きやすい。

一方、毎回まったく異なるrequestが来るmulti-tenant servingでは、EAMCの代表patternが現在requestをうまく説明できず、利得が小さくなる可能性がある。

つまりglobal popularity cacheより適応的だが、**履歴が未来requestを代表すること**は必要になる。

## 評価

### まず見るところ
- **結論:** request単位のrouting patternを使ってexpert cache / prefetchすると、単純offloadよりTPOTを大きく減らせる。
- **実速度:** 1 GPUでも、モデルによっては4〜8 GPUで全weightを載せる構成へ近いlatencyを示す。
- **品質:** native routerと同じexpertを必ず実行するためlossless。
- **メモリ・I/O:** expertは主にCPU DRAM、GPUにはhot expertとKVを保持。論文の主結果をSSD実測と解釈しない方がよい。
- **注意点:** batch=1・類似requestの局所性が強いほど有利。long contextではGPUに残したKV cacheが別bottleneckになる。

主な比較対象はvLLM、Ollama / llama.cpp、DeepSpeed-Inference、Mixtral-Offloading、BrainStorm。

### 代表的なTPOT

prompt 512、decode 32の条件。

| モデル | MoE-Infinityの平均TPOT |
|---|---:|
| DeepSeek | 155 ms |
| Switch | 155 ms |
| NLLB | 531 ms |
| Mixtral worst case | 836 ms |

NLLBは全weightをGPUへ置く構成なら8 GPU、Switchは4 GPUを要する条件に対し、MoE-Infinityは1 GPUで近いlatencyを示す。

### 既存方式に対する改善

| 比較 | 結果 |
|---|---:|
| Mixtral offloading baseline | 約1.4倍改善 |
| 論文abstractの全モデル総括 | 既存方式比3.1〜16.7倍のper-token latency改善 |

3.1〜16.7倍という値はモデル・baselineをまとめた範囲であり、すべてのモデルで一律16倍になるという意味ではない。

### Long-context時の影響

LongBenchでcontext lengthを `2^12〜2^17` まで伸ばしている。

| 指標 | 結果 |
|---|---:|
| MoE-Infinityの追加latency | 最大137 ms |

長くなるほどKV cacheがGPU memoryを圧迫し、expert cacheへ使える余裕が減る。

一方vLLM側でKVもoffloadすると、KV transferとexpert fetchが帯域を競合するため、別の形でlatencyが増える。

### 履歴が馴染むまでの適応期間

| 項目 | 結果 |
|---|---:|
| 同一taskで安定するまで | 約50 request |
| worst-case overhead | 約5% |

EAMCが十分なrouting patternを持つまではcold-start的な期間がある。

### 予測patternの圧縮

| 元のrequest数 | 代表cluster数 |
|---:|---:|
| 1000系列 | 約10〜30 cluster（Switch等を除く） |

これはexpert数を減らしているのではなく、**request routing履歴の保存・検索量を減らしている**。

### 評価上の制約

- 1 GPU / low-batch中心。
- 同種requestの局所性を利用するため、request分布の変化に依存する。
- KV cacheはGPU常駐で、極端なlong contextではcapacity pressureが大きい。
- 公開OSS版と論文評価版には実装差があるとREADMEに明記されている。
- SSD対応は公開実装側にあるが、論文主結果を物理SSD streaming benchmarkとして扱わない方がよい。
