# MoNDE: Mixture-of-Experts Neural Network Inference with Near-Data Processing

> computational storage上でexpert計算を行うnear-data executionにより、巨大MoEのストレージ帯域とGPU転送を削減する方式。

## 概要
MoNDEは、cold expertのweightをGPUへ運ぶ代わりに、**expert weightが置かれているCXL memory device側でexpert GEMMそのものを実行する**near-data processing（NDP）方式である。

hot expertは従来通りGPUで実行し、少数tokenしか受けないcold expertはactivationだけをCXL deviceへ送り、device内LPDDRに常駐するweightで計算する。つまり、Fiddlerが「CPU DRAMにあるexpertをCPUで実行する」のに対し、MoNDEは**CXL memory deviceに演算器を載せ、その場で実行する**構成である。

対象はSwitch-Large-128とNLLB-MoE。GPU側profileは実機A100を使うが、MoNDE deviceそのものはcycle-level simulatorで評価しており、完成したCXL-NDP実機のbenchmarkではない。

## 手法のあらまし

MoNDEでは、weightを動かす従来方式を **PMove（Parameter Movement）**、activationだけを動かす提案側を **AMove（Activation Movement）** と呼んでいる。この二つをexpertごとに使い分けるのが中核である。

### 1. `PMove`：hot expertはweightをGPUへ持ってくる

従来のoffloadと同じく、GPUでexpertを計算する場合はexpert parameterをCXL memory側からGPUへ移す。

論文ではこのweight movementを **PMove** と呼ぶ。

データ量は概ねexpert weight sizeに比例し、式上は `2E d_model d_ff` に依存するため、expert数やFFN幅が大きいほど重い。

ただし多数tokenが同じexpertへ流れるhot expertなら、一度weightをGPUへ持ってきた後のGEMMで転送costを償却しやすい。

### 2. `AMove`：cold expertはactivationだけCXL deviceへ送る

cold expertへ1〜数tokenしか流れない場合、数百MB級weightをGPUへ送るのは割に合わない。

そこでMoNDEではhidden activationだけをCXL deviceへ送り、**weightはdevice内LPDDRに置いたまま**expert GEMMを実行する。

このactivation movementを **AMove** と呼ぶ。

データ量は概ね `2BS d_model` に依存し、batch / sequenceが小さいとPMoveよりかなり小さくなる。

つまり、

- PMove：大きなweightをGPUへ動かす
- AMove：小さなactivationをweightのある場所へ動かす

という反対方向のdata movementを使い分ける。

### 3. `Near-Data Processing (NDP)`：memory device側にGEMM engineを置く

MoNDEのCXL memoryは単なる容量拡張DRAMではない。

device内部にsystolic arrayとlocal bufferを持ち、host/GPUから `gemm` / `gemm+relu` のようなcommandを投げると、**LPDDRからweightを外へ出さずにdevice内で計算できる**想定になっている。

論文がモデル化するMoNDE deviceは、

- 8 memory channel
- 512 GB容量
- 合計約512 GB/s帯域
- 64個の4×4 systolic array
- 264 KB buffer
- 1 GHz

という構成である。

したがってこの結果を「普通のCXL RAMへoffloadしただけ」と読むのは正しくなく、**memory + computeを一体化した専用NDP hardware**が前提である。

### 4. `Hot Top-H`：何expertをGPU側へ回すかをruntimeで決める

全expertを固定的にGPU / NDPへ分けるのではなく、gate後に各expertへ流れるtoken数を見て、そのiterationでhotな上位 `H` expertsをGPU側へ回す。

残りのcold expertはAMove + NDPで実行する。

`H`は固定値ではなく、

- PCIe / CXL bandwidth
- NDPのmemory bandwidth
- activated expert数
- GPU / NDPの処理速度

から決める。

論文ではprofile結果を使って係数 `α` をauto-tuneし、GPUとNDPの完了時間が片側だけ長くならないよう調整する。

### 5. `GPU-MoNDE Load Balancing`：GPUとNDPを並列実行する

hot expertをGPU、cold expertをNDPへ送った後、両方を同時に走らせる。

layer全体は遅い側が終わるまで待つため、目的は単純にNDPへできるだけ多く投げることではなく、**GPUとNDPの処理時間を揃えてstragglerを作らないこと**である。

この協調構成が論文中の **MD+LB** に対応する。

### 6. なぜsmall-batch / encoder側で効きやすいか

cold expertに流れるtokenが少ないほどAMoveのdata量は小さく、PMoveの固定weight costとの差が大きくなる。

逆にbatchが大きくなって多くのexpertがhotになると、GPUへweightを送ってまとめて計算する方が有利になり、NDP側の相対利得は小さくなる。

つまりMoNDEは、**routing skewが強く、expertごとのtoken数が小さい場面ほど有利**な設計である。

## 評価

### まず見るところ
- **結論:** cold expertのweightをGPUへ運ばずCXL-NDP側で計算すると、特にencoder workloadのparameter movementを大きく減らせる。
- **実速度:** Switchでencoder 3.1倍、NLLBでencoder 6.7倍など大きな改善を示す一方、decoder側の改善は比較的小さい。
- **品質:** 同じnative expertを別deviceで実行するだけなのでlossless。
- **メモリ・I/O:** 通常CPU DRAMやSSDではなく、**CXL memory + 専用NDP compute**を想定。
- **評価の強さ／注意点:** **Simulationのみ**。A100 profileは実機だがMoNDE deviceはcycle-level modelで、512 GB/s級の将来hardware仮定を含む。

### 評価モデル

| モデル | Expert weight規模 | Routing | Dataset |
|---|---:|---|---|
| Switch-Large-128 | 約51.5 GB | 128 experts / top-1 | XSum |
| NLLB-MoE | 約103.1 GB | 128 experts / top-2 | FLORES-200 |

入力長512、batch sizeを変えて評価している。

### 比較構成

| 略称 | 内容 |
|---|---|
| GPU+PM | activated expert weightをGPUへ移して計算 |
| MD+AM | 全expertをMoNDE側でactivation movementにより計算 |
| MD+LB | Hot expertはGPU、cold expertはMoNDEで協調実行 |
| Ideal | 全weightがGPUにある理想上限 |

`MD+LB` が提案のGPU-MoNDE load balancingを含む主構成。

### 主なlatency改善

GPU+PMに対するMD+LBのspeedup。

| モデル | Encoder | Decoder |
|---|---:|---:|
| Switch-Large-128 | 3.1倍 | 1.1倍 |
| NLLB-MoE | 6.7倍 | 1.9倍 |

論文内の平均的なまとめでは、encoder約4.9倍、decoder約1.5倍。

encoder側の方が大きく伸びるのは、routing / token distributionとweight movementの条件がNDPに有利だからである。

### Abstractで示される最大値

| 比較 | 最大speedup |
|---|---:|
| Parameter-offloading baseline、encoder | 7.5倍 |
| Parameter-offloading baseline、decoder | 3.7倍 |

これは代表的な最大値で、全batch / 全modelの平均ではない。

### CPUでexpert計算する方式との比較

NLLBでCPU計算 + activation movementを使う構成と比べると、MoNDEは次の改善を報告する。

| 部分 | NDPのlatency改善 |
|---|---:|
| Encoder | 9.1倍 |
| Decoder | 1.9倍 |

この差の主因として、MoNDE側の想定memory bandwidthがCPUの約2.7倍であることが挙げられる。

### Hardware overhead

| 項目 | 値 |
|---|---:|
| NDP logicのarea overhead | 約3.0 mm² |

### 評価上の制約

- CXL-NDP deviceそのものは実チップ測定ではない。
- 512 GB/s級memory bandwidthを仮定する。
- hot/cold切替thresholdとauto-tuned `H` に性能が依存する。
- encoder / decoderを中心に評価し、online multi-user servingは扱わない。
- KV cache placementは対象外。
- 通常のCPU offload / SSD offloadとはhardware前提が大きく異なる。
