# ZeroLock: Concurrent Memory-Efficient LLM Training via Modular Update Decoupling

> モデルを複数chunkへ分け、各chunkを局所目的関数で独立更新することで、下流chunkの逆伝播待ちと長時間のactivation保持をなくし、pipeline並列学習のbubble・memory・通信待ちを減らすBP-free fine-tuning system。

## 問題設定

通常のpipeline parallelismでは、モデルを連続するlayer群ごとのstageへ分割しても、end-to-endの逆伝播（backpropagation; BP）を使う限りstage間には**update locking**が残る。上流stageは、自分のgradientを得るために下流stageのforwardとbackwardが進むのを待つ必要があり、その間はforward時のactivationも保持し続ける。

このため、

- stage間の待ちによるpipeline bubble
- 上流stageで長時間残るactivationによるpeak memory増加
- backward gradientをstage間で返す通信

が生じる。

ZeroLockは、単にschedulerを工夫してbubbleを詰めるのではなく、**chunk間の学習依存そのものを切る**ことでこの問題を扱う。最終目的はfine-tuning自体のmemory・throughput改善なのでTraining側に分類する。

CPU DRAMやSSD/NVMeへparameter・optimizer state・activationを退避するoffload方式ではない。主なmemory削減源は、下流のbackwardを待つためのactivation保持を不要にすることにある。

## 手法

### 1. モデルをchunkへ分割し、chunkごとに局所目的関数を持たせる

モデルを連続するTransformer layer群からなる複数chunkへ分割する。base weightは固定し、各layerにはLoRA parameterを入れる。

各chunkの出力hidden stateに、事前学習済みmodelの最終normalizationとLM headを使うreadout headを接続し、その時点でtoken予測分布を作る。

各chunkの局所lossは大きく2項からなる。

- **task term**: そのchunkの出力をground-truth tokenへ近づける
- **consistency term**: 直前chunkの出力分布と大きく食い違わないようにする

直前chunk側にはstop-gradientを入れるため、chunk間へbackward gradientを流さない。

### 2. chunk内ではBP、chunk間では更新を独立化する

ZeroLockは「gradient計算を一切しない」方式ではない。

- 同じchunk内部のlayer: 通常のBPでLoRAを更新
- 異なるchunk間: gradient依存を切り、各chunkが自分のlocal lossだけで更新

という構成である。

これにより、上流chunkは下流chunkのbackward完了を待たず、自分のlocal backwardへ進める。また、そのchunkのactivationは自分のlocal updateが終われば解放できる。

論文は、局所目的関数をglobal objectiveの更新として写像する解析を行い、一定の仮定の下で収束率が `Õ(1/√T)` となり、通常BPの `O(1/√T)` とpolylogarithmic factorだけ異なると示す。

### 3. Early Forwardingでhidden stateを先に下流へ送る

各stageは、

1. upstreamからhidden stateを受け取る
2. forwardを実行
3. **local backwardより先に**出力hidden stateをdownstreamへ渡す
4. 自分のlocal backwardとoptimizer updateを続ける

という順に動く。

downstreamは3の時点で処理を始められるため、upstreamのlocal backwardとdownstreamのforwardを重ねられる。

### 4. stage間通信はhidden stateだけにする

end-to-end BPではforward hidden stateに加えてbackward gradientもstage間で戻す必要がある。

ZeroLockではchunk間gradient依存を切るため、基本的にstage間で交換するのはforward hidden stateだけでよい。これが低帯域linkほど有利になる理由の一つである。

### 5. bounded bufferとstage単位checkpointで局所復旧する

各executorはupstreamから受け取ったhidden stateをbounded bufferへ保持する。さらに各stageがtrainable parameter、optimizer state、進行位置を独立checkpointする。

failure時は正常stageをglobal rollbackせず、失敗stageだけをcheckpointから戻し、bufferに残るhidden stateを使って必要なwindowだけreplayする。

つまりmemory効率化だけでなく、更新依存を切った構造をfailure recoveryにも利用している。

### 6. AndroidではExecuTorchを二段階実行へ拡張する

Android prototypeではExecuTorchを使う。通常のtraining PTEはforwardとbackwardを1 methodにまとめるため、hidden stateが外へ出るのはbackward後になりEarly Forwardingができない。

そこでforward hidden state生成後・parameter-gradient計算前に軽量markerを入れ、

- phase 1: markerまで実行してhidden stateを即時送信
- phase 2: 同じexecution stateから再開してlocal backwardとAdamW update

と分ける。転送とlocal backwardを重ね、cross-stage gradient RPCを不要にする。

## 評価

### まず見るところ

- **multi-GPU実機:** TinyLlamaを3 chunkへ分割し、各chunkをNVIDIA L40 GPU 1台へ配置。
- **LoRA:** server評価ではrank 4、scale 16。
- **data:** AG Newsの固定10,000 sample subset、sequence length 128。
- **baseline:** GPipe、1F1B、PipeDream。
- **最大stage memory:** `b/m = 8/4` 条件でPipeDream比26.5%削減。
- **throughput:** 同条件でPipeDream比4.9%向上。GPipe比55.8%、1F1B比62.8%向上。
- **failure recovery:** 1F1Bのglobal rollback/replayに対し、recovery latencyを2381.2 msから2013.1 msへ短縮し、transferを192 MiBから96 MiBへ半減。
- **Android実機:** TinyLlamaの3 chunkをNX809J、Lenovo L71091、Pixel 10 Pro XLへ配置し、128 sampleをfine-tuning。総wall-clock 1644.1 s、throughput 0.0779 records/s、各端末のpeak PSSは約3.4–3.8 GiB。

## 既存研究との差

GPipeや1F1Bは、stage実行順を工夫してもend-to-end BPの依存は残る。PipeDreamはweight stashingでpipelineをより非同期化するが、forwardとbackwardの整合を取るため複数versionのweightを保持し、依然としてbackward gradientがstage間を流れる。

ZeroLockはschedulerだけでなく**学習目的をchunk-localへ再構成**し、stage間のbackward dependencyをなくす点が異なる。

一方、完全なdense pre-trainingを対象にした一般手法というより、LoRAを用いたLLM fine-tuningとedge / collaborative trainingを主対象としている。

## 一般的な実装上の含意

この論文の重要な含意は、「pipeline bubbleはschedulerだけの問題ではなく、学習algorithmのdependency graphそのものを変えるとmemory・communication・recovery設計まで同時に変えられる」ことにある。

特に、

- activation lifetimeを短くする
- backward gradientのcross-stage transferをなくす
- forward transferとlocal backwardを重ねる
- stage-local checkpointで局所復旧する

という効果が同じdecouplingから得られる。

ただしlocal headの計算量や、中間representationを最終LM headで読めるという仮定、local objectiveによる最終品質差まで含めて評価する必要がある。

## 限界

- arXiv v1時点のpreprintで、最終採択版は確認できない。
- server実機評価はTinyLlamaと3×L40 GPUが中心で、数十〜数百B級modelや大規模clusterでのscalingは未検証。
- 主なtaskはAG Newsで、長文生成・instruction tuning・RL post-trainingなどへ同じ品質特性が成立するかは未確認。
- local readout headは中間hidden stateが最終headである程度解釈可能であることを前提とする。論文自身も複雑なgenerative taskでは成立しない可能性を指摘している。
- PipeDreamに対するthroughput改善はdefault条件で4.9%と比較的小さく、利点の一部はmemory削減・通信削減・failure recovery側にある。
- CPU DRAM / SSD / NVMe offloadは評価していない。

## 引用関係

ZeroLockはpipeline parallelismの代表的baselineとしてGPipe、PipeDream、1F1B系を直接参照し、さらにZero Bubble、DAPPLE、Chimeraなどのbubble削減・pipeline構成研究を関連研究として位置づける。

また、collaborative / edge trainingとしてConfidant、CollaPipe、SWARM parallelism、Petalsを参照する。これらに対しZeroLockは、placementやscheduleだけでなくchunk-local objectiveでbackward dependencyを切ることを主要差分としている。

repo内では本論文の追加時点でpipeline-parallel training専用系統がなかったため、関連研究群の明確な独立性に基づき `03-pipeline-parallel-modular-training/` を新設した。
