# NeMo-Aligner: Scalable Toolkit for Efficient Model Alignment

> 整合学習の複数モデルを分散配置し、TensorRT-LLM生成・非同期通信・重み再配置を統合して、PPOを1000 GPU級まで拡張する学習基盤。
## 書誌情報
- **著者**: Gerald Shen, Zhilin Wang, Olivier Delalleau, Jiaqi Zeng, Yi Dong, Daniel Egert, Shengyang Sun, Jimmy Zhang, Sahil Jain, Ali Taghibakhshi, Markel Sanz Ausin, Ashwath Aithal, Oleksii Kuchaiev
- **著者・所属**: NVIDIA
- **公開**: COLM 2024
- **種別**: Conference paper
- **対象**: LLM alignment、distributed training、RLHF、PPO、DPO、TensorRT-LLM
- **実装**: Apache 2.0で公開されたNeMo-Aligner実装。Megatron-LM、NeMo、Transformer Engine、TensorRT-LLM、PyTritonを組み合わせる。
## 概要
大規模言語モデルの整合学習では、強化学習、人間選好モデル、参照方策、生成処理を同時に扱うため、単純な分散学習だけでは多数GPUを効率良く使えない。本論文はNeMo-Alignerを提示し、Megatron-LMの3次元並列化、役割の異なるモデル間の非同期通信、推論時のTensorRT-LLM統合、重みの再配置と再フィットを組み合わせる。これによりPPOを中心とする整合学習を1000 GPU級まで拡張し、DPO、SteerLM、SPIN、LoRAにも同じ基盤を広げている。評価ではLlama 3 70Bで構成要素ごとの寄与とスケーリングを測り、Llama 3.1 405BのPPOを1008基のH100で実行可能であることを示した。

NeMo-Alignerの中心的な新規性は、整合アルゴリズム自体を変えるのではなく、PPOの異種段階を分散システムとして組み直した点にある。方策と参照方策、価値モデルと報酬モデルをそれぞれ同じ計算割当内で重み交換して共有し、別クラスタ間はPyTritonで非同期通信する。生成時だけTensorRT-LLM向けの推論配置へ再配置し、学習で更新された重みは再コンパイルせず再フィットする。これらをMegatron-LMのデータ・テンソル・パイプライン並列化の上へ統合し、DPO、SteerLM、SPIN、LoRAにも拡張可能な訓練器抽象化へまとめた。

代表結果として、PPO全体ステップ時間はLlama 3 70B方策+70B価値系、16+8ノード、大域ロールアウトバッチ128、BF16で8+4ノードで53.7秒に対して29.8秒、1.80倍高速化。ノード数倍増に対して完全線形ではないが、学習と生成の双方が短縮し、大規模PPOのスケーリングが成立する。
## 問題設定
人間フィードバックからの強化学習では、方策モデル、参照方策、価値モデル、報酬モデルという複数の大規模モデルを一つの学習反復で動かす。特にPPOでは、方策による応答生成、参照方策の対数確率、報酬推論、価値推論、方策と価値モデルの更新が相互依存し、通常の事前学習のように単一モデルへデータ並列化を適用するだけではGPUが待ちやすい。さらに生成は一トークンずつ進むため、学習用の高演算効率カーネルをそのまま使うと起動遅延とメモリ帯域が支配的になる。既存の整合学習ツールは使いやすさや手法の網羅性を提供していたが、数百B級モデルを1000 GPU規模で効率良くPPOするためのモデル間協調、生成最適化、並列構成の切替を一体として扱う点が不足していた。
## 新規性
NeMo-Alignerの中心的な新規性は、整合アルゴリズム自体を変えるのではなく、PPOの異種段階を分散システムとして組み直した点にある。方策と参照方策、価値モデルと報酬モデルをそれぞれ同じ計算割当内で重み交換して共有し、別クラスタ間はPyTritonで非同期通信する。生成時だけTensorRT-LLM向けの推論配置へ再配置し、学習で更新された重みは再コンパイルせず再フィットする。これらをMegatron-LMのデータ・テンソル・パイプライン並列化の上へ統合し、DPO、SteerLM、SPIN、LoRAにも拡張可能な訓練器抽象化へまとめた。
## 手法
### 手法のあらまし
処理は、まず事前学習済みまたは教師あり微調整済みモデルをMegatron-LM系の3次元並列化で配置するところから始まる。PPOでは方策モデルがプロンプトから応答を生成し、その応答について参照方策がKL罰則用の対数確率を、報酬モデルが報酬を、価値モデルが価値推定を計算する。NeMo-Alignerは四つのモデルを四つの独立サーバとして常駐させず、同一構造を持つ方策と参照方策を一つのジョブにまとめ、参照方策の重みをCPUへ退避して必要時に方策重みと交換する。同様に価値モデルと報酬モデルも組にする。方策側はPyTritonのクライアントとして価値・報酬側サーバへ非同期要求を送り、価値推論と学習を方策側の生成・学習と重ねる。生成段階では学習向け実装ではなくTensorRT-LLMを使う。開始時に推論エンジンを構築してメモリに保持し、生成時のメモリ余裕が許せばパイプライン並列を外してテンソル並列中心へ再配置する。学習で重みが更新された後はTensorRTの再フィット機能でエンジン内重みだけを更新し、毎反復の再コンパイルを避ける。応答長のばらつきでデータ並列ワーカー間に負荷差が出る場合はワーカープールが生成仕事を動的に配る。計算資源は、報酬・価値推論の時間と方策生成・参照推論の時間、価値学習と方策学習の時間がおおむね釣り合うように割り当て、片側待ちを抑える。このPPO基盤とは別に、DPOは選好対の対数確率差を直接学習し、SteerLMは属性条件付き教師あり学習、SPINは前世代自己生成応答と人間応答の選好学習として実装され、共通の訓練器抽象化を再利用する。

### 分散PPOモデル協調
方策・参照方策・価値・報酬の四役を、そのまま四つの巨大モデルとして同時常駐させるのではなく、同一構造の二組にまとめる。参照方策の重みはCPUへ退避し、必要な参照推論時に方策重みと交換する。価値モデルと報酬モデルにも同じ考え方を適用する。さらにPyTritonの非同期クライアント・サーバ通信を使い、方策側の生成・学習と価値側の推論・学習を重ねる。入力は生成済み応答や学習データ、出力は報酬・価値・更新済み重みであり、計算クラスタを分離できるため巨大モデルでも単一割当へ全役割を詰め込む必要がない。

### TensorRT-LLM生成統合と再配置
逐次生成は学習とは異なりカーネル起動遅延とメモリ帯域に律速されるため、方策の生成だけをTensorRT-LLMへ渡す。初回に推論エンジンを構築して保持し、生成時のメモリ条件が許す場合はパイプライン並列を除いてテンソル並列中心に再配置し、ノード間通信を減らす。学習後の新しい重みはTensorRTの再フィット機能で既存エンジンへ反映し、再コンパイル待ちを避ける。エンジンとKVキャッシュを保持する追加メモリは必要で、その分は学習活性値の再計算でピークを抑える。入力は各PPO反復で更新された方策重みとプロンプト、出力はロールアウト応答とその生成状態である。再配置によって学習時に必要だったパイプライン段間通信を生成時には削れるため、一トークンごとの通信待ちが減る。反対に405Bのようにモデルが単一ノードへ収まらない条件ではパイプライン並列を残す必要があり、この最適化の効果は小さくなる。

### 生成負荷分散と訓練器抽象化
生成応答の長さが異なると、固定バッチでは短い応答を担当したGPUが先に空き、最長応答を担当するGPUが終わるまで他の計算資源が待つ。NeMo-Alignerはワーカープールへ生成仕事を置き、早く空いたデータ並列ワーカーが追加の仕事を受け取れるようにして応答長の偏りをならす。入力は未処理の生成要求と各ワーカーの進捗、出力は再配分された生成仕事である。ただし小さいバッチでは負荷分散自体の管理費が元の不均衡を上回り、評価でも有意な改善が出なかった。上位層では共通の訓練器抽象化を設け、DPO派生法、SteerLM、SPINなどが既存の学習・検証・分散処理を再利用する。これにより巨大分散系の通信や並列処理を各整合アルゴリズムへ重複実装せず、新しい目的関数や学習手順へ拡張できる。

### 全体のデータ／制御の流れ
学習側はMegatron-LMとNeMoを基盤に、Transformer Engineの最適化カーネル、分散融合Adam、データ・テンソル・パイプライン並列を使用する。PPOでは方策側と価値・報酬側を別計算群として配置し、PyTritonで非同期接続する。生成経路だけTensorRT-LLMへ切り替え、再フィットで学習重みを同期する。計算群の大きさは両側の処理時間を釣り合わせるよう設定するため、単なるGPU追加ではなく段階間の均衡がスケーリングの前提になる。
## 評価条件
- **ハードウェア**: 主なPPOシステム評価は、1ノード8基のH100 80GB SXM、ノード内NVLink、ノード間InfiniBandで行う。Llama 3 70Bの方策・価値系では8+4、16+8、32+16、64+32ノードを比較し、最大768 GPUを使用する。Llama 3.1 405Bでは方策84ノード、価値側42ノード、合計1008 H100を使用する。
- **ソフトウェア**: Megatron-LMとNeMoを学習基盤とし、Transformer Engine、分散融合Adam、PyTriton、TensorRT-LLMとTensorRT再フィットを組み合わせる。DPO、SteerLM、SPIN、LoRAも同一ツールキットで実装される。
- **比較対象**: NeMo Generate without TensorRT-LLM integration、full-parameter SteerLM、Zephyr-7B-Beta、published SPIN result
PPOのスケーリングでは初回のTensorRT-LLMエンジン構築を除き、その後5ステップの平均と標準偏差で1ステップ時間を測る。70Bではロールアウト大域バッチ128の8+4対16+8ノード比較と、大域バッチ1024の16+8から64+32ノード比較を行う。構成要素アブレーションではTensorRT-LLM統合、推論時再配置、再フィット、非同期要求を一つずつ外す。品質面ではLlama 3 70B PPOをMT-BenchとGPT-4-Turbo判定で比較し、DPO、SteerLM、SPINについても各再現設定のMT-Benchを報告する。
実機GPU上の大規模評価であり、PPOシステムのスケーリングと主要最適化の寄与を直接測る。一方、中心的な性能測定はNVIDIA H100と同社ソフトウェア群に依存し、他GPUや異種クラスタへの一般化は実証していない。405B評価は実行可能性とステップ時間を示すが、70Bほど詳細な構成要素比較は行わない。
## 主要結果
70B PPOでは、方策8ノード・価値側4ノードから16+8ノードへ倍増すると1ステップ時間が53.7秒から29.8秒へ短縮し、全体1.80倍、生成2.05倍の高速化となった。大域バッチ1024では16+8から64+32ノードへ増やして190.4秒から56.9秒となり3.35倍高速化した。アブレーションではTensorRT-LLM生成統合を外す影響が最大で、最適構成53.7秒に対し372.2秒まで悪化する。405Bでは1008 H100でPPOを実行し164.6秒/ステップを報告する。したがって性能の主因はGPU数そのものではなく、生成専用実装、推論時の並列再配置、重み再フィット、非同期モデル間通信を組み合わせた点にある。

- PPO全体ステップ時間 / 29.8秒、1.80倍高速化 (比較対象: 8+4ノードで53.7秒; 条件: Llama 3 70B方策+70B価値系、16+8ノード、大域ロールアウトバッチ128、BF16) — ノード数倍増に対して完全線形ではないが、学習と生成の双方が短縮し、大規模PPOのスケーリングが成立する。

- 大規模PPO全体ステップ時間 / 56.9秒、3.35倍高速化 (比較対象: 16+8ノードで190.4秒; 条件: Llama 3 70B、64+32ノード、大域ロールアウトバッチ1024、合計768 H100) — 仕事量を増やすとデータ並列ワーカーへ十分な仕事を配れ、より大規模な計算資源を有効利用できる。

- TensorRT-LLM統合アブレーション / 372.2秒、最適構成の6.93倍の時間 (比較対象: 最適構成53.7秒; 条件: Llama 3 70B、8+4ノード、大域ロールアウトバッチ128) — PPOでは逐次生成が主要ボトルネックであり、学習向け生成実装をそのまま使うことが最大の性能損失になる。

- Llama 3.1 405B PPO / 164.60秒/ステップ (比較対象: 同一論文内の直接比較対象なし; 条件: 405B方策+405B価値系、84+42ノード、1008 H100、ロールアウト大域バッチ128、BF16) — 1000 GPU級で405Bモデルを方策と価値系の双方に使うPPOが実行可能であることを示すが、生成が140.10秒を占め依然として支配的である。

- LoRA SteerLM効率 / 最小GPU 32→8、同GPU数で5倍のサンプル/GPU/秒 (比較対象: 全パラメータSteerLM; 条件: Llama 2 70B、LoRA rank 32、BF16) — パラメータ効率の高い微調整により必要メモリと計算を大幅に下げつつ、MT-Bench 7.43対7.54と近い品質を維持する。

### 負の結果・境界条件
- スケーリングは常に線形ではない。70B・大域バッチ128ではノード増加に伴い各データ並列ランクのマイクロバッチ数が減り、パイプラインの充填・排出時間の割合が増えるため学習側の伸びが鈍る。TensorRTエンジンへの重み再フィット時間もノード増加でほぼ縮まず固定費になる。小さい大域バッチ128では動的ワーカープールの負荷分散は、元の不均衡より管理オーバーヘッドが大きく有意な高速化を示さなかった。405Bでは生成が単一ノードに収まらずパイプライン並列が必要で、応答長も平均916トークンと70Bの351トークンより長く、生成が主要ボトルネックとして残る。

### 結果の読み方
改善幅が大きいのは、PPOの時間の大半を占める生成経路を学習経路から切り離して推論専用に最適化したためである。さらに再配置は生成時の不要なノード間通信を減らし、再フィットは毎反復のエンジン再構築を避ける。非同期要求は方策側と価値側の待ちを隠すが、その寄与は生成最適化より小さい。仕事量が小さい場合は並列度を増やしても固定費が支配し、逆に大域バッチを増やすと多数ワーカーへ仕事を配れるため大規模構成の効率が上がる。
## 品質への影響
本手法は近似推論で速度と品質を交換する方式ではなく、主に実行系の最適化である。Llama 3 70B PPOではMT-Benchが開始SFTの7.96から8.13へ上がり、DPO再現では最終7.60、SteerLMのLoRAは全パラメータ7.54に対し7.43で著者がノイズ範囲と説明する。SPINの単一反復設定では7.04を報告し、比較対象のZephyr SFT 6.64および既報3反復SPIN 6.78を上回る。
## 既存研究との差
HuggingFace TRL、trlX、DeepSpeed-Chatのような既存整合ツールに対し、本研究は手法数の追加よりも数百B級モデルを多数GPUで動かすシステム設計を主眼とする。特に、PPOの四役モデルを二組へまとめた重み交換、別計算群間の非同期通信、学習と生成で並列配置を切り替える再配置、TensorRT-LLMエンジンの再フィットを一つの訓練ループへ統合し、それぞれの寄与を実機アブレーションで分離している点が特徴である。
## 限界
評価環境はH100、NVLink、InfiniBand、TensorRT-LLMなどNVIDIAのハードウェア・ソフトウェア構成に強く依存し、異種GPUや低帯域クラスタで同じ効率が得られるかは未評価である。PPOの詳細アブレーションは主にLlama 3 70Bで、405Bは実行可能性と時間内訳が中心である。生成エンジンをメモリへ常駐させるため追加メモリが必要で、活性値再計算との交換条件が生じる。405Bでは生成にパイプライン並列が必要で、生成時間が依然支配的である。動的生成負荷分散も小さいバッチではオーバーヘッドが利益を上回った。
## 実装状態
NeMo-AlignerはNVIDIAからApache 2.0で公開され、論文時点でSFT、PPO型RLHF、DPO、SteerLM、SPINと多くの手法のLoRA設定を実装する。コードはNVIDIA/NeMo-Alignerとして公開され、論文中では報酬モデルとPPO後モデルの公開先も示されている。
## 研究上の位置づけ
大規模言語モデル学習システムの中では、事前学習の並列化そのものではなく、整合学習特有の複数モデル・生成・学習が混在する反復を効率化する研究として位置付けられる。推論基盤TensorRT-LLMを学習ループ内のロールアウトへ組み込み、推論時だけ配置を変えるため、学習系と推論系の境界を跨ぐシステム設計の実例でもある。1000 GPU級の405B PPOを実証したことで、整合アルゴリズム研究を巨大モデルへ適用する際の実装上の基盤と、生成が残存ボトルネックになることの双方を示している。
