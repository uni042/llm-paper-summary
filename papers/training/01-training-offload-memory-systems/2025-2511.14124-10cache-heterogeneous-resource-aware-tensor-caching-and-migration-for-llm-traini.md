# 10Cache: Heterogeneous Resource-Aware Tensor Caching and Migration for LLM Training

> GPU・CPU DRAM・NVMeを3段のキャッシュとして使い、各テンソル（tensor）が次に必要になる時刻と役割に応じて、どの階層へ残すか・いつ先読みするかを決める学習システム。

## 概要

10Cacheは、単一GPUで大きなLLMを学習するとき、GPU・CPU DRAM・NVMe SSDを単なる「上から順にあふれたデータを置く場所」としてではなく、**速度と容量が異なる3段のキャッシュ（cache）**として扱う。

一般的なオフロードでは、GPUメモリが不足するとCPUへ、CPUも不足するとSSDへデータを移す。しかし、すべてのテンソルを同じ規則で追い出すと、少し後ですぐ必要になるデータまでSSDへ落ち、再読込待ちが増える。

10Cacheは、

- パラメータ（parameter）
- 勾配（gradient）
- 最適化状態（optimizer state）
- 活性値（activation）

について、**次にいつ使うか**と**どこで更新するデータか**を見て配置を変える。

たとえば、

- すぐ使うパラメータはGPUへ残す
- CPU最適化器が近く使う最適化状態はCPU DRAMへ残す
- しばらく使わない冷たいデータだけNVMeへ落とす

という考え方である。

論文の主眼は「NVMeを極端に速くすること」ではなく、**そもそもNVMeまで落とさなければならないデータを減らし、GPU/CPU側で再利用できる割合を増やすこと**にある。

TERAIOのようなGPUダイレクトストレージ（GPUDirect Storage; GDS）は使わず、NVMeからGPUへ戻す場合はCPU DRAMの一時バッファを経由する。

## 手法のあらまし

### 1. 最初に試運転（dry run）し、学習中のテンソル使用順を記録する

最初にモデルを1回試運転し、各テンソルについて、

- 実行順
- サイズ
- どの処理で使われるか
- 次にいつ使われるか

を記録した**実行表（execution table）**を作る。

LLM学習は、同じモデル構造・同じ形状であれば反復ごとの実行順が比較的安定している。そのため1回目に観測した使用順を、以後の追い出し（eviction）と先読み（prefetch）の予定へ利用できる。

### 2. GPU上に必要な時間帯を「活動窓（active window）」として扱う

各テンソルについて、次に使う直前から使用が終わるまでの「GPU上に必ず存在しなければならない時間帯」を**活動窓（active window）**とする。

活動窓が近いテンソルはGPUに残す価値が高く、次の使用まで遠いテンソルはCPUやNVMeへ移しやすい。

つまり単純な**最近使われた順（Least Recently Used; LRU）**ではなく、過去にいつ使ったかよりも**次にいつ使う予定か**を重視する。

### 3. テンソルの種類によって「置きたい階層」を変える

再利用までの時間が同じでも、テンソルの役割によって適した場所は異なる。

| Tensor | 優先配置 | 理由 |
|---|---|---|
| 直近で使うparameter | GPU | 順伝播・逆伝播で直接必要 |
| optimizer state | CPU DRAM | CPU optimizerが更新するため |
| 長時間使わないparameter/state | NVMe | 容量優先で退避可能 |
| temporary/activation | GPU/CPU | 生存時間と次回使用に応じて決定 |

したがって10Cacheは、**再利用距離だけでなく「どこで使うデータか」まで配置判断へ入れる**。

### 4. テンソルサイズに合った作業バッファを先に確保する

CPU↔GPUやNVMe↔CPU転送では、一時的な作業メモリが必要になる。

そのたびにメモリ確保・解放を行うと処理時間が増え、異なるサイズの確保を繰り返すと空き領域が細切れになる**断片化（fragmentation）**も起きる。

10Cacheはテンソルのサイズ分布を事前に見て、CPU側のピン留めバッファ（pinned buffer）やGPU側の空き領域をサイズ別に確保して再利用する。

これにより、毎回の`malloc/free`相当の処理と断片化を減らす。

### 5. 時計ではなく「どの層まで実行したか」を基準に先読みする

「前回は開始から20ms後にこのテンソルが必要だったから、今回も15ms後に先読みを始める」といった時刻ベースの制御は、OS処理やGPU負荷の揺れでずれやすい。

10Cacheはモデルの各層の前後で呼ばれる**フック（hook）**を使い、「現在どこまで計算が進んだか」を直接検知する。

そのため、

`layer Nに入った → layer N+kで使うtensorのprefetchを開始`

のように、実際のモデル実行順へ同期してデータ移動を開始できる。

これにより実行時間が多少揺れても、先読み時刻がずれにくい。

### 6. 最適化器更新には専用の先読み順序を使う

最適化状態は順伝播・逆伝播とは異なるタイミングで使われる。

10Cacheは、

- 現在更新している最適化状態をCPU DRAMへ残す
- CPUが現在の状態を更新している間に、次に必要な状態をNVMe→CPUへ読む

という処理を行う。

つまり**CPU最適化器の計算とNVMe読み込みを同時進行させる**ことで、SSD待ちを減らす。

### 7. NVMeはCPU DRAMを経由する

10CacheのNVMeからGPUへの経路は、

`NVMe → CPU temporary buffer → GPU`

である。

GDSのようにSSDとGPUを直接つなぐ方式ではない。

その代わり10Cacheは、

- GPUキャッシュの命中率を上げる
- CPUキャッシュの命中率を上げる
- NVMeへ落とすテンソル自体を減らす

ことで、遅い経路を使う回数を抑える。

ここでいう**キャッシュ命中（cache hit）**は、「必要なテンソルがすでにGPUまたはCPUに残っており、より遅い階層から読み戻さずに済む」ことを意味する。

## 評価

### まず見るところ

- **結論:** パラメータ・最適化状態・活性値を同じ規則でオフロードせず、次の使用時刻と役割に応じてGPU→CPU→NVMeへ配置すると、単一GPU学習の待ち時間を減らせる。
- **学習速度:** ZeRO-Infinity比で最大約2倍の学習高速化を報告し、一部モデル・GPU条件ではさらに大きい差が出る。
- **キャッシュ:** GPU/CPU側で必要なテンソルを再利用し、NVMeへの退避数と読み戻し回数を減らす。
- **入出力:** NVMe→CPU一時バッファ→GPUという通常の中継経路。GDSではない。
- **注意点:** 実行順が比較的固定された単一GPU学習が中心で、動的なMoE routingなどは対象外。

### ZeRO-Infinity比

OPT/BLOOM/Falcon-7Bでは、10Cacheのparameter+memory最適化構成がZeRO-Infinityに対して最大約2倍級の学習高速化を示す。

| GPU | ZeRO比speedup |
|---|---:|
| L40S | 2.60倍 |
| A100 | 2.82倍 |

### 他systemとの比較例

GPT-2 5.9BではStrongHold比でL40S 2.44倍、A100 4.17倍。

BERT/A40の特定条件では、三層キャッシュ構成がZeROの三層オフロードより非常に短いiteration timeを示す。

ただしこれは一般的に「常に19倍高速」という意味ではない。ZeRO側で必要データがGPU/CPUにほぼ残らず、NVMe読み戻しが頻発する条件に対し、10Cacheがキャッシュ命中でそれを避けた極端な比較例として読むのが適切である。

### Cache hit / NVMe spill

| 指標 | 傾向 |
|---|---|
| cache hit | modelにより大幅改善 |
| NVMe parameter数 | 約2.1〜6.7倍削減 |
| miss rate | 1%未満の条件あり |
| ZeRO miss | 約100%に近い条件あり |

論文要旨では、GPUキャッシュ命中率を最大86.6倍改善し、CPU/GPUメモリ利用率を最大2.15倍 / 1.33倍改善したと報告する。

### Resource utilization

OPT-13Bでは、

| System | CPU util | GPU util |
|---|---:|---:|
| ZeRO | 38% | 68% |
| 10Cache | 82% | 90% |

入出力待ちを減らし、CPU最適化器とGPU計算をより連続的に動かせている。

### Overhead

| 項目 | Epoch比 |
|---|---:|
| profile | 約1.09% |

### 制約

- 比較的静的な実行グラフを前提とする
- single-GPU評価が中心
- NVMeはCPU staging経由
- MoE routingのように実行経路がtokenごとに大きく変わる処理は対象外
- 最終task accuracyや長期収束は主評価ではない
