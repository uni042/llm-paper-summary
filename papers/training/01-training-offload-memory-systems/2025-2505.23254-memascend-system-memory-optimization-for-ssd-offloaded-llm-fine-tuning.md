# MemAscend: System Memory Optimization for SSD-Offloaded LLM Fine-Tuning

> buffer fragmentation削減・direct NVMe I/O・低精度optimizerを組み合わせ、SSD-offloaded LLM fine-tuningの容量と速度を改善する方式。

## 概要
MemAscendは、SSD offloadそのものより、**SSD offloadを支えるCPU側buffer管理がRAMを大量に浪費する問題**を扱う。

ZeRO-Infinity系ではweight・gradient・optimizer stateをNVMeへ逃がせても、pinned bufferやstaging領域が過剰確保されるとsystem RAMが先に尽きる。MemAscendはbuffer pool、pinned allocation、overflow check、NVMe I/O経路をまとめて軽量化する。

これはKV cacheやexpert pagingではなく、fine-tuning時のstatic stateとoptimizer I/Oのsystem-memory最適化である。

## 手法のあらまし

### 1. `adaptive buffer pool`

ZeRO-Infinityの固定bufferは最大tensorサイズに引きずられ、実際には使わない大きな領域を予約しやすい。

MemAscendはtensor size分布に合わせて複数サイズのpoolを作り、必要サイズに近いbufferを割り当てる。

論文では固定poolが13.05GiBを予約しながら同時使用3.81GiBという例があり、fragmentation削減が大きい。

### 2. `alignment-free pinned allocation`

通常のpinned allocatorはpower-of-two丸めやpage alignmentで余分なRAMを使う。

MemAscendはPCIe DMAに必要なpage-lockを保ちつつ、**実tensorサイズに近い領域だけを確保**する。

### 3. `fused overflow check`

NaN/Inf検出を複数passで行うと一時Boolean tensorが増え、peak RAMも増える。

MemAscendはoverflow判定を1 passへ融合し、中間tensorを減らす。

### 4. `Direct NVMe Engine`

通常filesystem/stagingを経由するI/Oでは、一時bufferとcopyが増える。

MemAscendはO_DIRECT系の低レベルI/Oを使い、余分なpage cacheやstagingを避ける。

ただし経路は基本的にNVMe↔CPU pinned buffer↔GPUで、GDSのGPU-NVMe direct pathとは異なる。

### 5. 任意の`bf16 optimizer`

追加optionとしてoptimizer stateや転送をbf16化し、I/O量をさらに減らす。

これは数値形式を変えるため、**buffer管理だけのlossless改善とは分けて評価する必要がある**。

## 評価

### まず見るところ
- **結論:** SSD offload時のCPU buffer浪費を減らすと、GPUではなくsystem RAMが先に尽きる問題をかなり緩和できる。
- **容量:** buffer wasteを平均5割超削減し、より長いcontext・大きいbatchまでfine-tuning可能。
- **学習速度:** losslessな主構成で数%〜十数%、bf16 optimizer併用ではさらに大きく改善。
- **I/O:** 通常NVMe＋CPU DRAM staging。CSD/GDS/CXLではない。
- **注意点:** bf16 optimizerのspeedupは数値形式変更を含む。

| Hardware | 改善 |
|---|---:|

### bf16 optimizer併用

| Hardware | 平均改善 | 最大 |
|---|---:|---:|
| 構成1 | 27.25% | 56.80% |
| 構成2 | 17.08% | 24.21% |

bf16 optimizerではI/O量を約58%削減するが、この改善はmemory managerだけの効果ではない。

### 容量拡張

128GiB system RAM条件ではbaselineがcontext 16K・batch4付近で制約される一方、MemAscendはcontext 131Kまたはbatch32まで拡張できる設定を報告する。

### 品質

OpenWebText 250 stepsではZeRO-Infinityとloss曲線がほぼ一致する。主構成のbuffer/I/O最適化は数値計算を変えない。

### 制約

- fine-tuning専用
- decode/KV/expert cacheは未評価
- direct NVMeでもGPU直結GDSではない
- 公式codeは未確認
