# MemAscend: System Memory Optimization for SSD-Offloaded LLM Fine-Tuning

> SSDへモデル状態を退避するLLM fine-tuningで、CPU側バッファの無駄・一時メモリ増加・NVMe入出力の余分なコピーを減らし、system RAM容量と学習速度を改善する方式。

## 概要

MemAscendは、SSDオフロード（SSD offload）そのものではなく、**SSDへデータを逃がすためにCPU側で確保する一時メモリが大量のRAMを浪費する問題**を扱う。

ZeRO-Infinity系では、重み（weight）・勾配（gradient）・最適化状態（optimizer state）をNVMe SSDへ退避することでGPUメモリ不足を避けられる。しかし実際の転送には、CPU DRAM上にデータを一時的に置くバッファが必要になる。

このバッファを「最大サイズに合わせて大きめに確保する」「転送しやすいサイズへ丸めて確保する」といった実装にすると、**実際のデータ量よりかなり多くCPU RAMを消費する**ことがある。その結果、GPUメモリもSSD容量も残っているのにCPU RAMが先に不足する。

MemAscendはこの問題に対して、

- データサイズに合ったバッファを割り当てる
- ピン留めメモリ（pinned memory）の過剰確保を減らす
- NaN/Inf検査用の一時メモリを減らす
- NVMe入出力の余分なコピーを減らす

という複数のsystem-memory最適化を組み合わせる。

対象は推論時のKVキャッシュやエキスパートページングではなく、**LLM fine-tuning時のモデル状態と最適化器入出力**である。

## 手法のあらまし

### 1. データサイズに近いバッファを使う「適応バッファプール（adaptive buffer pool）」

SSDオフロードでは、SSD↔CPU↔GPUのデータ転送に使う一時領域をあらかじめ複数確保しておくことがある。これを**バッファプール（buffer pool）**という。

単純な実装では、どのテンソルにも対応できるよう最大テンソルサイズに近い大きなバッファを複数用意する。しかし実際には小さいテンソルも多いため、使われない領域が大量に残る。

このように「メモリ自体は確保されているが、サイズの不一致や分割の都合で有効利用できない状態」を**断片化（fragmentation）**という。

MemAscendはテンソルのサイズ分布に合わせて複数サイズのバッファプールを作り、必要なデータサイズに近いバッファを割り当てる。

論文では、固定サイズ方式が13.05GiBを予約しながら同時に実使用しているのは3.81GiBだけ、という例を示す。つまりCPU RAM不足の一部は「必要なデータそのもの」ではなく、バッファ設計による余白から生じている。

### 2. ピン留めメモリ（pinned memory）の丸め込みを減らす

GPUとCPUの間で高速DMA転送を行う場合、OSが勝手に別の場所へ移動しないCPUメモリ領域を使う。これが**ピン留めメモリ（pinned memory）**である。

一般的なメモリアロケータは管理を簡単にするため、要求サイズを2のべき乗などへ丸めて大きめの領域を確保することがある。

たとえば130MBしか必要なくても256MB確保すれば、残り126MBはそのバッファでは使われない。

MemAscendの**アラインメント不要のピン留め割り当て（alignment-free pinned allocation）**は、GPU転送に必要なページ固定は維持しながら、実際のテンソルサイズに近い領域だけを確保してこの余分を減らす。

### 3. NaN/Inf検査を1回にまとめ、一時テンソルを減らす

混合精度学習では、勾配にNaNやInfが発生していないか確認し、数値計算が破綻していないかを判定する。

これを**オーバーフロー検査（overflow check）**という。

単純な実装で複数回テンソルを走査したり、判定ごとに大きなBooleanテンソルを作ったりすると、その一瞬だけCPUメモリ使用量が跳ね上がる。

MemAscendは複数の判定処理を1回の走査へまとめる**融合オーバーフロー検査（fused overflow check）**を使い、中間テンソルとピークRAM使用量を減らす。

### 4. NVMe入出力でOSの余分なキャッシュ経路を避ける

通常のファイル入出力では、アプリケーションが読み書きするデータをOSの**ページキャッシュ（page cache）**へ一度保持する場合がある。

SSDオフロードでは同じ巨大データを別の専用バッファにも持つため、ページキャッシュまで使うとCPU RAM消費やコピー回数が増えることがある。

MemAscendの**直接NVMeエンジン（Direct NVMe Engine）**は、`O_DIRECT`系の直接入出力を利用し、可能な範囲でOSページキャッシュを経由せず専用バッファとNVMeの間を読み書きする。

基本経路は、

`NVMe SSD ↔ CPUのピン留めバッファ ↔ GPU`

である。

したがって、SSDとGPUがCPU DRAMを経由せず直接通信するGPUダイレクトストレージ（GPUDirect Storage; GDS）とは異なる。

### 5. 任意でbfloat16へ低精度化し、最適化状態と入出力量をさらに減らす

MemAscendは追加オプションとして、最適化器（optimizer）関連のデータを**bfloat16（bf16）**で扱う方式も評価する。

bfloat16は通常の32-bit浮動小数点より1要素あたりのデータ量が小さいため、

- CPU RAM使用量
- SSD入出力量
- CPU↔GPU転送量

を減らせる。

ただしこれは、単にメモリ管理を改善するだけの変更とは違い、**学習で使う数値形式そのものを変える近似**である。

そのため論文の高速化を見るときは、

- バッファ管理や入出力経路を変えただけの構成
- bf16最適化器まで使った構成

を分けて解釈する必要がある。

## 評価

### まず見るところ

- **結論:** SSDオフロード時のCPUバッファ浪費を減らすと、GPUではなくsystem RAMが先に尽きる問題をかなり緩和できる。
- **容量:** バッファの無駄を平均55.7%削減し、より長い文脈長（context length）・大きいバッチまでfine-tuningできる。
- **学習速度:** 数値形式を変えない主構成で数%〜十数%、bf16最適化器併用ではさらに大きく改善する。
- **入出力:** 通常のNVMe＋CPU DRAM中継。CSD、GDS、CXLを使う研究ではない。
- **注意点:** bf16最適化器を使った高速化には低精度化の効果も含まれる。

### 容量拡張

128GiBのsystem RAMという条件では、baselineがcontext 16K・batch 4付近で制約される一方、MemAscendはcontext 131Kまたはbatch 32まで拡張できる設定を報告する。

これは「SSD容量が増えた」ためではなく、**SSDを使うためにCPU側で消費していた余分なRAMが減った**ことによる容量拡張である。

### 品質

OpenWebText 250 stepsではZeRO-Infinityと学習損失曲線がほぼ一致する。主構成のバッファ・入出力最適化は数値計算そのものを変えない。
