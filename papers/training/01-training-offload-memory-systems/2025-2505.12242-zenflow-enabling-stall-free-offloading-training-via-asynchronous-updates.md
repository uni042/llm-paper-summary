# ZenFlow: Enabling Stall-Free Offloading Training via Asynchronous Updates

> 重要な勾配だけをGPUで即時更新し残りをCPUで非同期蓄積・更新して、LLM fine-tuningのoffload stallを抑える方式。

## 概要
ZenFlowは、ZeRO-OffloadのようなCPU optimizer offloadで、GPUがCPUの更新完了を待つ時間を減らす方式である。

通常は全gradientをCPUへ送り、全parameterをCPU optimizerで同期更新してからGPUへ戻す。ZenFlowは、**学習への寄与が大きいgradientだけを毎step GPUで更新し、残りはCPU側で数stepまとめて遅延更新する**。

これによりCPU optimizerをcritical pathから外しやすくする。NVMeやactivation offloadではなく、主対象はGPU HBMとCPU DRAM間のgradient・parameter・optimizer stateである。

## 手法のあらまし

### 1. `selective update`

各weight matrixについてgradientのchannel-wise normを計算し、重要度の高い上位channelだけを選ぶ。

論文では、上位少数のgradientが全体のnormの大部分を占めるという偏りを利用する。

重要gradientはGPU上で毎step更新し、残りはCPUへ送る。

### 2. 全gradientをAllGatherしない

重要channel選択のためにfull gradient matrixをGPU間で集めると通信量が大きい。

ZenFlowは各channelのnormだけを共有する。たとえば4096×4096のgradient本体ではなく、4096要素程度のsummaryだけを交換する。

### 3. `delayed update`

非重要gradientは捨てず、CPU側で複数step蓄積してからoptimizer updateする。

このため完全同期SGD/Adamとは異なる**近似更新**になるが、重要gradientは常に最新状態で反映される。

### 4. double bufferingでCPU updateを隠す

CPU側は2つのgradient bufferを使う。

- buffer Aへ現在stepのgradientを受信
- buffer Bで前周期分のoptimizer updateを実行

を同時進行させ、GPU forward/backwardとCPU updateを重ねる。

### 5. `Zen-auto`

固定更新間隔では学習初期にstalenessが大きくなりやすい。

Zen-autoは初期を同期寄りにし、gradient変化が落ち着くと遅延更新間隔を広げる。つまり、更新頻度を学習進行に合わせて変える。

## 評価

### まず見るところ
- **結論:** 重要gradientだけ同期更新し、残りをCPUで遅延更新するとCPU optimizer待ちを大幅に減らせる。
- **学習速度:** ZeRO-Offload比平均約4.3倍、ZeRO-Infinity比平均約6.3倍。
- **品質:** 完全同期ではない近似だが、標準設定ではGLUE/lossをほぼ維持。
- **I/O:** CPU DRAM↔GPUのgradient/parameter/optimizer経路。NVMe/GDSは対象外。
- **注意点:** 更新間隔を長くしすぎるとstalenessで品質低下が出る。

### 実験環境

| 項目 | 条件 |
|---|---|
| GPU | 4×A100 80GB、4×H100 80GB |
| CPU | 64 core / 128 thread級 |
| CPU RAM | 1〜2 TB |
| Interconnect | NVLink + PCIe |
| Baseline | ZeRO-Offload、ZeRO-Infinity、StrongHold |

### End-to-end speedup

| 比較対象 | 平均speedup |
|---|---:|
| ZeRO-Offload | 4.3倍 |
| ZeRO-Infinity | 6.3倍 |
| 構成別 | 約2.9〜5倍 |

CPU:GPU時間比は7B/13Bで12:1超から1:1以下まで下がり、GPU stallを80〜85%以上削減する。

### 通信量

Top-k=10%、遅延更新間隔S=4では、ZeRO-Offloadの毎step通信に対して平均転送量をほぼ半減できる。

channel normだけを交換するため、重要gradient選択のためのGPU間通信もfull gradient収集より数千倍小さい。

### 品質

GLUE 4 taskとOPT loss曲線はZeRO-Offloadとほぼ一致する。

ただしS=16のように更新間隔を広げすぎると、3 epochで約0.02程度のaccuracy低下が観測される。

### 制約

- CPU optimizerがbottleneckになる環境ほど有利
- consumer CPUでは同じspeedupにならない可能性が高い
- selective GPU optimizer用の追加stateが必要
- NVMe、GDS、activation offloadは未評価
