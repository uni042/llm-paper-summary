# G10: Enabling An Efficient Unified GPU Memory and Storage Architecture with Smart Tensor Migrations

> テンソルの生存期間と次回利用時刻を実行グラフから求め、GPU・ホストメモリ・SSD間の退避と先読みを自動化して、ページフォルトと転送待ちを減らす学習システム。

## 概要
G10はGPUの限られたHBMをhost DRAMとflash SSDで透過的に拡張し、DNN training中のtensorを先回りして移動する統合GPU memory/storage architectureである。GPUメモリに収まらない全モデルを毎回ページフォルトでSSDから読むのではなく、compilerが実行グラフからtensorのサイズ、依存関係、active期間、次回使用時刻を抽出し、不要なtensorをhostまたはflashへ退避する。調査では各kernelでactiveなtensorは全体の10%未満（平均1%）で、多くのinactive期間はSSD latencyより長いことを示し、転送を計算と重ねられると主張する。

対象はBERT、ViT、ResNet、Inceptionv3、SENetなど一般DNN trainingで、MoE expert weightや生成時KV cacheを中心にした研究ではない。使うストレージは通常のNAND flash SSD（NVMe相当）であり、CXLメモリ、HBF、near-storage FPGAとは別階層である。G10はUVM page tableを拡張してGPU／host／flashのアドレスを一つの仮想空間に見せ、アプリケーションを変更せずにmigrationを実行する点が特徴である。

A100トレースとSSDシミュレータによる評価では、FlashNeuron比平均1.56倍、DeepUM+比平均1.31倍の学習スループットを示し、無限GPUメモリ想定の90.3%まで達した。

## 手法のあらまし

G10は **「tensorが次にいつ必要になるかをcompilerが知っている」** ことを、memory offloadのスケジューリングに使う。中核は `Tensor Vitality Analyzer`、`Smart Migration Scheduler`、`Unified Memory System` の3つである。

### 1. `Tensor Vitality Analyzer`：tensorの「使われていない時間」を求める

論文中の **tensor vitality** は、tensorの重要度ではなく、**実行中のどの期間にそのtensorがGPU上で必要か**を表す概念である。

実行グラフから各tensorについて、

- サイズ
- どのkernelが読む／書くか
- 最後に使われる時点
- 次に使われる時点
- その間のinactive interval

を抽出する。

G10の観察では、各kernel実行時に本当にactiveなtensorは全体の10%未満、平均では約1%しかない。つまり多くのtensorは「存在しているが、しばらく使わない」状態にある。

このinactive intervalが長ければ、いったんSSDへ追い出しても次回利用までに戻す時間を確保できる。

### 2. `Smart Migration Scheduler`：inactive時間から退避先を決める

schedulerは各tensorのinactive intervalとサイズ、GPU–host／GPU–SSDの帯域を見て、

- GPUに残す
- host DRAMへ退避する
- flash SSDまで退避する

のどれがよいかを決める。

考え方は単純で、**再利用までの猶予が短いtensorを遅いSSDへ送ると、戻すのが間に合わない**。そのため、

| Tensorの性質 | 主な配置先 | 理由 |
|---|---|---|
| すぐ再利用される | GPU | migrationする方が高くつく |
| inactive時間は短いがGPUを空けたい | Host DRAM | SSDより戻しやすい |
| 長時間使わない・大きい | SSD | 大きくGPU容量を空けられる |

という形で階層を使い分ける。

ここでのポイントはLRUのような「過去にいつ使ったか」ではなく、**実行グラフから「次にいつ使うか」を先に知っている**ことである。

### 3. `g10_pre_evict` / `g10_prefetch`：migrationを実行グラフへ埋め込む

G10はschedulerの判断をruntimeの場当たり的なpage fault処理に任せず、compiler段階で `g10_pre_evict` と `g10_prefetch` というmigration命令として実行列へ埋め込む。

- `g10_pre_evict`：まだGPUが逼迫する前にtensorの退避を開始する
- `g10_prefetch`：実際に必要になるkernelより前にtensorを戻し始める

runtime側のmigration handlerがDMAを発行し、GPU計算とtensor移動を重ねる。

したがってG10の本質は、**page fault後に対処するのではなく、将来の利用時刻から逆算して移動を始める**ことにある。

### 4. `Unified Memory System`：GPU / host / flashを同じ仮想空間として扱う

通常のUVMはGPUとCPU memoryを中心に扱うが、G10はpage tableを拡張してflash上のtensorも同じ仮想アドレス空間へ統合する。

アプリケーションから見るとtensorのアドレスは変わらず、実体だけが

`GPU HBM ↔ Host DRAM ↔ Flash SSD`

の間を移動する。

これによりモデル側のコードへ「このtensorは今SSDにある」といった配置ロジックを大量に書かずに済む。

### 5. `G10-GDS` / `G10-Host` / 完全版G10の違い

論文では効果を分離するため、構成を段階的に比較している。

| 構成 | 主な経路 | 何を見るための比較か |
|---|---|---|
| G10-GDS | GPU ↔ SSD | GPU–SSD直接migrationだけの効果 |
| G10-Host | GPU ↔ Host ↔ SSD | Host DRAMを中間bufferとして使う効果 |
| G10 | GPU / Host / SSDを統合管理 | scheduler＋階層配置全体の効果 |

Host DRAMは単なる通過点ではなく、**SSDでは復帰が間に合わないtensorを置く高速な中間tier**として働く。

なお、この研究はtraining tensor全般の寿命スケジューリングが対象で、LLM生成時のKV cache evictionやMoE expert cacheとは問題設定が異なる。

## 評価

### まず見るところ
- **結論:** tensorの次回利用時刻を使ってGPU・Host・SSD間の移動を先回りすると、page fault型や単純GPU–SSD offloadより待ち時間を大きく隠せる。
- **速度・効率:** FlashNeuron比平均1.56倍、DeepUM+比平均1.31倍で、理想的な無限GPU memoryの90.3%まで到達する。
- **品質:** 計算内容は変えずtensor配置だけを変えるため、アルゴリズム上の品質劣化はない。
- **評価の強さ／注意点:** **Simulationのみ**。A100のprofile traceとSSD-Simを組み合わせた結果で、実SSD・実PCIe・firmware込みのend-to-end測定ではない。

### 評価したモデル

| モデル | データセット |
|---|---|
| BERT | CoLA |
| ViT | ImageNet |
| InceptionV3 | ImageNet |
| ResNet-152 | ImageNet |
| SENet-154 | ImageNet |

FP32で、batch sizeはモデルごとに調整されている。

### 主なbaseline

| 方式 | 特徴 |
|---|---|
| Ideal | GPU memoryが無限にある理想上限 |
| Base UVM | page fault発生後にmigration |
| DeepUM+ | 過去の相関からprefetch |
| FlashNeuron | GPU–SSDを直接使うoffload |

G10と既存方式の大きな差は、**past access patternではなく実行グラフからfuture accessを取得すること**にある。

### 主な性能結果

| 比較 | G10の結果 |
|---|---:|
| vs FlashNeuron | **平均1.56倍** |
| vs DeepUM+ | **平均1.31倍** |
| Idealに対する性能 | **90.3%** |
| 個別benchmarkの最大高速化 | **1.75倍** |

単純なSSD offloadより高速というだけでなく、理想的に全tensorがGPUへ載る条件へかなり近づいていることが主張の中心である。

### Batch sizeやSSD帯域を増やした場合

| 条件 | 結果 |
|---|---:|
| batch拡大時、vs FlashNeuron | 最大2.67倍 |
| batch拡大時、vs DeepUM+ | 最大1.45倍 |
| Host memory追加、vs FlashNeuron | 平均1.33倍 |
| SSD 1〜4台 | 最大12.8 GB/s相当 |

SSD帯域を増やすと多くのbenchmarkはIdealの90〜100%へ近づく一方、BERTやViTではPCIeが次のbottleneckになる。

つまり、**SSDを速くすれば無限に伸びるわけではなく、階層間の最も遅いlinkへ律速点が移る**。

### Schedulerの予測誤差への耐性

| 条件 | 性能への影響 |
|---|---:|
| 利用時刻予測誤差 ±20% | 0.5%未満の性能低下 |

schedulerの予測が多少ずれても大きく崩れないと報告されている。ただしこれもsimulation上の感度分析である。

### SSD書き込み量

| 比較対象 | G10の書き込み削減 |
|---|---:|
| DeepUM+ | 1.37倍少ない |
| FlashNeuron | 2.20倍少ない |

不要なevict/reloadを減らすため、速度だけでなくflash write trafficも減る。

### 評価上の制約

- 全結果がprofile trace + simulatorに基づく。
- SSD bandwidth / latency / garbage collection / PCIe性能はモデル化された値。
- 対象は一般DNN trainingで、LLM servingやMoE routingは評価していない。
- KV cache、continuous batching、expert offloadの実測値ではない。
- NVMe/flashのcompiler-guided tensor migrationとして読むべきで、HBFやCXL memoryの実機結果と直接比較しない方がよい。
