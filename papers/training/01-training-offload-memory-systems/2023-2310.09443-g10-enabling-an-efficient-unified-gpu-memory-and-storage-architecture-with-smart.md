# G10：学習テンソルの生存期間に基づくGPU・ホスト・SSD統合メモリ

## 概要

G10が扱う問題は、深層学習の一反復で保持する全テンソルの容量がGPU搭載メモリを超えても、各演算器がその瞬間に使うテンソルの集合はずっと小さい、という差をどう利用するかである。GPUメモリをホストDRAMやSSDで拡張するだけでは、演算の直前に必要なデータがGPU上になければページ欠落（page fault）が発生し、GPUが転送を待つ。SSDの容量が十分でも帯域と遅延はGPUメモリと大きく異なるため、無計画な退避は処理率を落とす。G10はこの問題を、学習プログラムの計算グラフが持つ将来の使用時刻の情報から解く。

論文の第一の貢献は、学習用テンソルの生存期間解析器（Tensor Vitality Analyzer）によって各テンソルの活性区間、非活性区間、サイズ、依存関係をコンパイル時に抽出すること。第二は、GPU容量超過の緩和効果とGPU―ホスト／GPU―SSDの帯域負荷を一緒に評価する賢い移動計画器（Smart Tensor Migration Scheduler）である。第三は、GPU・ホスト・SSDを単一仮想アドレス空間で扱う統合メモリ機構（Unified Memory System）を用い、退避・先読み指示をアプリケーションの計算列へ組み込む点である。

評価はBERT、ViT、Inceptionv3、ResNet152、SENet154の**学習**を対象とし、A100から採取した特性とSSD等をモデル化したシミュレーションで行われた。主要結果はFlashNeuronに対する平均1.56倍、DeepUM+に対する平均1.31倍の処理率と、無限容量GPUメモリを仮定した理想構成の90.3%に相当する性能である。単一GPU上で大規模言語モデルを生成する実機試験や、生成中のKVキャッシュ退避の速度改善を報告したものではない。この対象範囲の区別が、推論システムへの応用可能性を判断するうえで重要になる。

## 問題設定と観測事実

従来の統合仮想メモリ（Unified Virtual Memory、UVM）はGPUとCPUの仮想アドレスを統一できるが、GPU上にないページを初めて参照した時点で転送するだけでは、必要なデータの到着まで演算が停止する。GPUからSSDへの直接転送（GPUDirect Storage）を使ってCPUによるコピーを減らしても、PCIeとSSDの帯域がGPU内メモリより低いという制約は残る。さらに、SSDから読み戻す時間を見込まずに大きなテンソルを退避すれば、空き容量の確保に成功しても後の演算で失速する。

原著第3節ではGPU A100でカーネル実行を測定し、BERT・ViT・ResNet152・Inceptionv3を含む学習のテンソル特性を調べた。活性テンソルとは、現在のカーネルの入力・出力としてGPU上に必要なテンソルを指す。多くのモデルでその瞬間の活性容量は全テンソル容量の10%未満、平均では約1%にとどまった。観測した最大カーネルの活性メモリは5.7GBであり、比較対象A100の40GBより小さい。**総保持容量がGPUメモリを超えること**と、**一つのカーネルの活性集合がGPUに入らないこと**は同じではない。

非活性期間は「現在使われていないが、将来再使用されるまで」の時間である。CNNでは非活性期間の60%超が約10の7乗マイクロ秒より長く、BERTやViTでは約半数が10の5乗マイクロ秒より長かった。SSDアクセス遅延を隠せる区間が存在する一方、テンソルサイズは数KB以下からGB級まで幅があり、短い非活性期間も混在する。したがって、単純に最も古いテンソルを追い出す最近最少使用（LRU）方式や、すべてをSSDへ移す固定方針では不十分である。

もう一つの観測は、学習中のGPUメモリ圧迫が時間とともに変わることだ。あるテンソルを退避すると、その区間の容量超過が減る一方、転送路の占有と先読み先の空き容量も変化する。個々の退避候補を独立に採点するだけでは後続の移動計画を最適化できないため、G10は一つの移動を選ぶたびに時間ごとのメモリ圧迫と帯域利用を更新する。

## 手法

### 1. テンソル生存期間解析器（Tensor Vitality Analyzer）

解析器は学習計算グラフの演算順と依存関係を読み、各テンソルの生成時点、最後の使用時点、使用されるカーネル、サイズ、複数の非活性期間を求める。モデル重みのように反復をまたいで存在する大域テンソル（global tensor）と、活性値や勾配のように反復内で生まれ最後の使用後に解放できる中間テンソル（intermediate tensor）を区別する。重みは順伝播と逆伝播の間だけでなく、反復境界をまたいで非活性になる場合もある。中間テンソルは最後の利用が終われば退避するのではなく解放できるため、寿命分類が無駄なI/Oを避ける前提になる。

各演算の実行時間はオフラインのカーネル計測から推定し、非活性期間の開始・終了を時間軸へ写す。これにより「次に使う直前にGPUへ戻せるか」「戻すにはGPU―SSDかGPU―ホストのどちらの転送路を使うべきか」を予測できる。ただし予測は固定された計算グラフと計測結果に依存するため、実行時の分岐や不規則な要求到着を同じ精度で扱えると証明したわけではない。

### 2. 容量圧迫と転送費用に基づく退避候補の選択

G10は時間tでGPU上に残るテンソル容量をメモリ圧迫量とし、容量上限を超える部分を減らすことを退避の利益と定義する。利益は「容量上限を超えていた面積」の減少量であり、単なるテンソルサイズだけでなく、どの程度長い区間で超過を緩和するかを含む。一方、費用はそのテンソルを退避し、再利用前に先読みするための転送遅延と帯域占有である。原著図7の候補比較では、容量超過を削る面積とI/O帯域の占有区間の比が選択を左右する。

計画器は、まず非活性期間の集合、時間ごとのメモリ圧迫曲線、GPU―SSDとGPU―ホストの帯域使用状況を持つ。候補の利益・費用を比較し、一つを選択したらこれら三つの状態を更新して次の候補を探す。容量圧迫が上限内に収まるか、利益のある候補がなくなるまで反復する。この逐次更新が、すべてのテンソルへ同一の静的優先度を付ける方式との相違である。容量超過が解消しても、帯域が競合すれば別の候補の利益が変わるため、計画全体を考慮する。

### 3. SSD優先とホストDRAMへの退避切替

退避先はSSDとホストDRAMの二択である。SSDは容量が大きいため基本的にはSSDを優先するが、SSD側の転送帯域が逼迫し、非活性期間内に往復転送を完了できない場合には、より高速なGPU―ホスト経路へ割り当てる。ホストメモリはSSDの単なる通過点ではなく、帯域要求が高いテンソルを短期間保持する独立した階層である。原著第4.3節では、SSDの大容量とホストの高帯域を組み合わせるためにこの選択を反復計画へ組み込んでいる。

この設計は、SSDへ移した容量だけを最大化する方針と異なる。たとえば大きなテンソルが長時間不活性でも、同時期に他のSSD転送が集中すれば再取得が間に合わない。逆に小さいホスト容量を無差別に消費すると、本当に高速復帰が必要なテンソルを置けなくなる。帯域を考慮した行先の選択により、後段のGPUカーネルを止めないことを優先する。

### 4. 最終安全時刻より前に開始する先読み（Smart Tensor Prefetching）

退避計画の段階では、次回の利用に間に合う最後の時刻で先読みを始めると想定する。しかし、カーネル実行時間や転送帯域の予測に少しでも誤差があれば、その時刻に始めた転送は間に合わない。G10は、退避計画後のGPUメモリに残る空き領域を利用し、先読みを可能な限り前倒しする。原著図8では、各テンソルの「最後に間に合う時刻」から時間を逆向きに探索し、全テンソルを保持できる空き容量がある最も早い安全な時点へ開始時刻を移す。

この処理は、無条件に先読みを早めるものではない。早く戻すほどGPUメモリの占有時間が延び、別のテンソルの配置を圧迫するため、容量曲線を壊さない範囲でのみ前倒しする。先読み対象を最終安全時刻順に処理することで、将来すぐ使うテンソルを遅らせない。予測が外れたときの停止を減らす代わりに、GPU空き容量を先に消費する交換条件がある。

### 5. 統合仮想メモリと実行列への組み込み

G10はGPUとCPUの統合仮想メモリ（UVM）を拡張し、ページ表の末端エントリにSSD上のページ位置も表現する。コンパイル済みプログラムへ事前退避命令 `g10_pre_evict` と先読み命令 `g10_prefetch` を挿入し、実行時は移動調停器（Migration Arbiter）と移動処理器（Migration Handler）が転送を発行する。アプリケーションは同じ仮想アドレスを参照し、物理的な格納先の違いを意識しなくてよい。原著図5と図9には、演算呼び出しの間にこれらの命令を挿入した例が示される。

実際の一反復では、計算グラフから必要テンソルを解析し、容量を超える区間に対して退避計画を作り、各テンソルの復帰時刻を前倒ししたうえで、計算と転送を並行させる。SSDが混雑すればホストDRAMを使い、GPUの空き容量があれば次の演算に必要なテンソルを早めに戻す。このように、解析器の出力が計画器へ渡り、計画器の命令が統合メモリの実行時転送を制御する一連の流れがG10の中核である。

## 評価

### 実験環境・比較対象

原著第7節は、GPU実機のカーネル実行特性を用いてUVMSmartを拡張したシミュレーションであり、GPUとSSDを接続した本番環境での実機処理率ではない。GPUの想定容量はA100の40GB、テンソル精度はFP32。SSDの遅延と帯域はSamsung Z-NANDを参考に設定され、GPU―ホスト／SSD間はPCIe帯域制約を受ける。学習タスクはBERT/CoLA、ViT/ImageNet、Inceptionv3/ImageNet、ResNet152/ImageNet、SENet154/ImageNetで、入力バッチはモデルごとに変更する。

原著図11では、ページ欠落後に対処するBase UVMが理想構成より大きく遅れる一方、G10は多くの条件で理想に近い。理想の90.3%という数値は、実機A100にSSDを増設したときの絶対トークン毎秒ではない。モデル別のバッチや学習処理率を揃えたシミュレーション上の正規化結果である。FlashNeuronは一部の大バッチViT・Inceptionv3で、単一カーネルが必要とする活性テンソルがGPU容量を超え実行できなかった。従って比較対象が実行不能な条件を含むことも、倍率の解釈では注意が必要である。

### 機構別評価：退避経路・GPU停止・移動量

原著はGPU―SSDのみのG10-GDS、ホストDRAMを加えたG10-Host、統合UVMまで加えた完全版G10を区別する。G10-GDSは多くのDNNで既存方式を上回るが、ResNet152ではDeepUM+に勝てない条件がある。ホスト経路を追加したG10-Hostでは同条件でDeepUM+比1.23倍となり、帯域を考慮したホストへの退避が必要であることを示す。完全版G10はUVM拡張によってソフトウェア処理やページ欠落の追加費用も抑える。単にSSDへ多く退避するだけでは最良にならないという負の結果を含む比較である。

原著図12は計算と移動の重なり、図13は理想より遅くなったカーネルの割合を比較する。Base UVMでは過半のカーネルがページ欠落の影響を受けるのに対し、G10で理想より遅くなるカーネルは1〜6%と報告される。図14では、従来の相関・履歴ベース方式が不要な退避を増やすこと、FlashNeuronが重みを移さないため将来の空きを十分作れない場合があることを確認できる。Transformer系のBERTとViTは転送帯域を強く要求し、G10はホスト経路を多用する一方、CNNではSSD側が半分以上の転送を担える条件がある。

### 感度分析：バッチ、ホスト容量、帯域、予測誤差

バッチを増やすと活性テンソルの総量と移動すべきデータが増え、受動的方式は転送待ちが拡大する。G10は図15でより大きなバッチまで理想構成に近い処理率を保つ。ただしバッチをさらに増やし、現在のカーネルと次のカーネルが同時に必要とするテンソル容量がGPU容量を超えると、先読みを完了する空間そのものがなくなり、G10でも停止は不可避になる。この条件はスケジューリングの巧拙だけでは解消できない。

図16・17ではホストDRAM容量を変えている。小さなバッチでは32GB程度のホストメモリで帯域利用が飽和するモデルが多いが、バッチ拡大に伴い移動テンソルが大きくなれば必要容量も増える。ホストを増やせば無制限に速くなるのではなく、GPU―ホストとGPU―SSDの転送路の飽和が次の制約になる。SSDを増設して総帯域を増やす感度実験でも、BERTやViTはPCIe側が律速となる条件がある。

原著の先読み時刻の推定誤差に関する実験では、予測に±20%程度の誤差がある場合も処理率低下は小さいと報告する。これは先読みを最終安全時刻より早める設計と整合するが、誤差の種類・分布や実際のI/O混雑が実環境と一致する保証ではない。平均性能だけでなく、転送待ちの残存と誤予測への頑健性を別の軸として読む必要がある。

### 品質への影響

G10はモデル重みや数値演算を近似・枝刈りする方式ではなく、テンソルの物理配置と移動時刻を変える方式である。原著の速度比較は学習処理率の比較であり、学習済みモデルの精度向上を主張していない。モデルの意味的品質を犠牲にして高速化する設計ではない一方、ストレージエラーや実装差に対する学習の信頼性を、実機で広く評価したと読むこともできない。

## 既存研究との差

Base UVMはページ欠落が起きてからGPU―ホスト間でデータを動かす。DeepUM+は過去のアクセス相関から次のページを推測する。FlashNeuronはGPU―SSD直接転送で一部の中間テンソルを退避するが、G10ほど詳細な将来の生存期間と帯域を一体で計画しない。G10はコンパイラの計算グラフから次の利用を知り、GPU容量超過を削る面積と転送路の占有を組み合わせて、退避するテンソル・階層・時刻を選ぶ。この「使用時刻の予測可能性を利用した事前計画」が、単なるSSD容量拡張との差である。

学習用メモリ管理という点では、G10は推論中のKVキャッシュ削減やMoE専門家の動的ロードとは別の問題を解いている。LLM推論への転用を考えるなら、要求到着順、文脈長、専門家活性、複数利用者のバッチ形成が変動する環境で、学習グラフに相当する先読み可能な将来情報をどう取得するかが新たな研究課題になる。論文はその転用の実測値を示していないため、G10の1.56倍という学習倍率をLLMサービングの倍率として流用してはならない。

## 限界・適用条件

第一に、性能評価はUVMSmartを拡張したシミュレータと実行特性の組合せである。実SSDの内部ガベージ収集、ファームウェア、PCIe競合、ホスト側の他処理による干渉を含む実サービスで、同じ処理率が得られると断定できない。第二に、計算グラフとカーネル時間が比較的予測しやすい学習を前提とする。動的制御フロー、入力依存の分岐、同時要求の変動が大きい推論サービングへはそのまま適用できない。

第三に、GPUに必要なテンソルを戻すための空き容量と帯域が物理的に不足する場合、どれほど優れた移動計画でも停止を避けられない。大バッチViTの転送要求、ResNet152におけるSSD単独方式の弱さ、ホストメモリの容量と帯域の交換条件は、提案方式の利得が一様でないことを示す。第四に、GPU・ホスト・SSDを統一するページ表や移動処理器の変更は、通常のGPUソフトウェア環境に何も追加せず導入できるという意味ではない。実装がハードウェア／ドライバの抽象化に依存する点も実運用上の制約となる。

最後に、論文の主要なモデルはBERT・ViT・CNNであり、生成型LLMのKVキャッシュ、分散MoE推論、複数GPU間の専門家配置、長文脈生成時のトークン遅延は評価していない。これらの課題への適用可能性はG10のメモリ階層設計から推測できる研究方向であって、原著が検証した結論ではない。公開コードの存在と、論文評価のシミュレーション中心という事実も区別する必要がある。
