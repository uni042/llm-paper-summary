# GreedySnake: Accelerating SSD-Offloaded LLM Training with Efficient Scheduling and Optimizer Step Overlapping

> 同じ層（layer）の全マイクロバッチ（microbatch）をまとめて処理して重みのSSD再読込を減らし、最適化器更新（optimizer step）の一部を次の学習反復と重ねることでI/O待ちを減らす方式。

## 概要

GreedySnakeは、パラメータ（parameter）・最適化状態（optimizer state）・活性値（activation）をNVMe SSDへ退避するLLM学習で、**同じ層の重みを小分けデータごとに何度もSSDから読み直す無駄**を減らすシステムである。

大きなバッチをGPUメモリへ一度に載せられない場合、複数の**マイクロバッチ（microbatch）**へ分けて順番に処理し、勾配を蓄積することが多い。

一般的な実行順では、

`microbatch 1を全layer → microbatch 2を全layer → ...`

と進む。GPUにモデル全体を残せないSSDオフロード環境では、次のマイクロバッチが同じ層へ戻る頃には、その層の重みがGPUから追い出されている。そのため同じ重みをSSDから何度も読み直すことになる。

GreedySnakeは実行順を入れ替えて、

`layer 1を全microbatch → layer 2を全microbatch → ...`

と処理する。一度読み込んだ層の重みを複数マイクロバッチで使い切ってから次の層へ移ることで、パラメータ読み込み回数を減らす。

さらに、反復末尾でまとめて行っていた最適化器更新の一部を次反復の順伝播と同時進行させ、CPU最適化器待ちも隠す。

## 手法のあらまし

### 1. 横方向スケジューリング（horizontal scheduling）：マイクロバッチを1個ずつ最後まで進める

従来方式は概ね、

`MB1: L1 → L2 → ... → LN`  
`MB2: L1 → L2 → ... → LN`

の順に処理する。

これは「1つのマイクロバッチをモデルの層方向へ横断させてから次へ進む」と考えると分かりやすい。

GPUに全パラメータを保持できない条件では、MB1のL1が終わった後にL1の重みを追い出し、かなり後でMB2がL1へ来たとき再びSSDから読む可能性が高い。

マイクロバッチ数が増えるほど、**同じ重みに対するSSD読み込み回数も増えやすい**。

### 2. 縦方向スケジューリング（vertical scheduling）：同じ層を全マイクロバッチで使い切る

GreedySnakeは順序を、

`L1: MB1 → MB2 → ...`  
`L2: MB1 → MB2 → ...`

へ入れ替える。

L1の重みをSSDから一度GPUへ読んだら、全マイクロバッチのL1処理に再利用してからL2へ移る。

ここでいう**縦方向（vertical）**は、モデルの層を縦に進むという意味ではない。**同じ層を固定して、マイクロバッチ側をまとめて処理する実行順**を指す。

主な利点は、重みのSSD再読み込みをマイクロバッチ数に比例して繰り返さずに済むことにある。

### 3. 代償として活性値（activation）を長く保持する必要がある

横方向の実行では、MB1のL1出力をすぐL2へ渡せる。

縦方向では、MB1のL1が終わっても、MB2、MB3...のL1処理が終わるまでL2へ進まない。そのためMB1のL1出力をより長く保存する必要がある。

つまり、

- パラメータ再利用は良くなる
- 活性値の生存時間（activation lifetime）は長くなる
- CPU/SSDへ保存する活性値量や入出力が増え得る

という交換条件がある。

GreedySnakeは活性値の非同期読み書きとバッファ管理を使い、この増加した入出力をGPU計算の裏へできるだけ隠す。

### 4. 依存関係DAGで「今実行できる処理」を管理する

パラメータ読み込み、活性値の読み書き、順伝播、逆伝播、最適化器更新には「この処理が終わるまで次は始められない」という依存関係がある。

GreedySnakeはこれを**有向非巡回グラフ（Directed Acyclic Graph; DAG）**として管理する。

DAGは、

- ノード：計算やI/Oタスク
- 矢印：先に終わっていなければならない依存関係

を表す図である。

固定した一本道で実行するのではなく、**必要な入力がそろったタスクから、利用可能なGPU・CPU・SSDバッファを使って進める**。

これにより、

- SSD read
- SSD write
- GPU compute
- CPU optimizer

を可能な限り同時に動かす。

### 5. 遅延最適化器ステップ（delayed optimizer step）：反復境界の待ち合わせを崩す

通常は反復`t`の逆伝播がすべて終わると、全パラメータの最適化器更新が完了するまで待ち、その後で反復`t+1`を始める。

この「全処理がそろうまで次へ進まない地点」を**バリア（barrier）**という。

しかし層ごとに見ると、反復`t+1`でその層を使う直前までに更新が終われば正しさは保てる。すべての層の更新を反復開始前に終える必要はない。

GreedySnakeはこの時間的な余裕＝**余白時間（slack）**を利用し、反復`t`の一部の最適化器更新を反復`t+1`の順伝播と重ねる。

これは更新を省略したり、古い重みのまま学習を続ける近似ではない。**依存関係上必要な時刻までに更新を終えるという条件を守りつつ、実行時刻だけ後ろへ動かす**。

### 6. 何を減らし、何が増えるか

| 項目 | 縦方向スケジュールの影響 |
|---|---|
| Parameter SSD read | 大幅に減る |
| Parameter reuse | 増える |
| Activation lifetime | 長くなる |
| Activation I/O | 増え得る |
| Optimizer barrier | overlapで減らす |

したがってGreedySnakeは単純な「重みをキャッシュする方式」ではなく、**重みI/Oを減らした結果増える活性値I/Oまで含めて、学習全体の実行順を組み直す方式**である。

## 評価

### まず見るところ

- **結論:** 同じ層の重みをマイクロバッチ間で使い回し、最適化器更新を次反復へ重ねると、SSDオフロード学習の反復時間を大きく短縮できる。
- **学習処理量:** ZeRO-Infinity比で約2倍前後、GPT-175Bでは最大2.53倍。
- **I/O:** パラメータ再読込を減らす代わりに活性値の生存時間は延びるため、活性値I/Oを非同期に隠せることが重要。
- **品質:** 数学的な依存関係を維持した実行順変更であり、学習アルゴリズムそのものは変えない。
- **注意点:** NVMeキュー深度、CPU側バッファ、CPU最適化器性能、勾配蓄積数に強く依存する。

これは推論token/sではなく、SSDオフロードされた**学習処理量（training throughput）**の改善である。

### なぜ大きいモデルほど効きやすいか

モデルが大きいほど、横方向スケジュールで同じパラメータをSSDから繰り返し読むコストが増える。

特にマイクロバッチが小さい条件では、GPU計算時間に対してパラメータ読み込み時間の割合が高く、縦方向で重みを再利用する効果が大きい。

### Optimizer overlapの意味

最適化器ステップを次反復へ押し出すことで、逆伝播終了後にCPU最適化器だけを待つGPUの空き時間を減らす。

ただしCPU更新が次反復で該当層を使う時刻までに終わらなければ、その場で待ちが発生する。そのためCPU性能も処理量へ直接効く。

### Activation側の副作用

縦方向スケジュールは活性値の生存時間を延ばすため、sequence lengthやmicrobatch数を増やすと活性値の保存量・I/O量も増える。

そのため、

- CPU DRAMバッファが小さい
- SSD write/readが遅い
- sequenceが非常に長い

条件では、パラメータI/Oの代わりに活性値I/Oが新しいボトルネックになり得る。

### 評価上の制約

- NVMe性能とqueue depthに依存する
- CPU optimizer性能に依存する
- host DRAM buffer容量が小さいとvertical scheduleの利点が減る
- downstream精度よりsystem throughput中心の評価
- cloud storage条件はlocal NVMeとI/O特性が異なる
