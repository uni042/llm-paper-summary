# GreedySnake: Accelerating SSD-Offloaded LLM Training with Efficient Scheduling and Optimizer Step Overlapping

> 同一layerの全microbatchをまとめる垂直スケジューリングと次iterationへのoptimizer重畳で、NVMeオフロード学習のI/O回数と待ち時間を減らす。

## 概要
GreedySnakeは、parameter / optimizer state / activationをNVMeへoffloadするLLM trainingで、**同じparameterをmicrobatchごとに何度も読み直すこと**と、iteration末尾のoptimizer stepがGPUを止めることを問題にする。

従来の`horizontal scheduling`では、microbatch 1を全layer通してからmicrobatch 2へ進むため、VRAMにlayer weightを残せない条件では同じlayer parameterをSSDからmicrobatch数だけ再ロードしやすい。

GreedySnakeは実行順を`vertical scheduling`へ変え、同じlayerを全microbatch分まとめて処理する。さらにoptimizer updateをiteration barrierへ固定せず、次iterationのforwardと重ねる。

対象はtraining stateの通常NVMe / cloud storage offloadで、推論時のexpert / KV cacheではない。

## 手法のあらまし

論文の中心は `horizontal vs vertical scheduling` と `optimizer-step overlapping` の2点である。

### 1. `Horizontal Scheduling`：通常のmicrobatch優先順

従来方式は概ね、

`MB1: L1→L2→...→LN`  
`MB2: L1→L2→...→LN`

の順でforwardし、backwardもmicrobatch単位で進める。

GPUに全parameterを保持できない場合、MB2がL1へ戻った時にはL1 weightがすでに退避されており、SSDから再ロードする可能性が高い。

つまりparameter I/O回数が**microbatch数に比例して増えやすい**。

### 2. `Vertical Scheduling`：layerを固定してmicrobatchをまとめる

GreedySnakeは順序を、

`L1: MB1→MB2→...`  
`L2: MB1→MB2→...`

へ入れ替える。

L1 weightを一度GPUへロードしたら、全microbatchで使い切ってからL2へ移るため、同じparameterのSSD readを大幅に減らせる。

ここでいう`vertical`はmodel graphの層方向ではなく、**layerを固定してmicrobatch軸を縦にまとめるschedule**を指す。

### 3. 代償：Activation lifetimeが長くなる

vertical scheduleでは、MB1のL1 outputをすぐL2へ渡さず、他microbatchのL1処理が終わるまで保持する必要がある。

そのためparameter reuseは良くなる一方、activationの生存期間が長くなり、CPU / NVMeへ保存するactivation量が増える。

GreedySnakeはこのtrade-offを、activation checkpointの非同期read / writeとbuffer schedulingで吸収する。

### 4. `Dependency DAG`でI/Oとcomputeの順序を管理する

parameter load、activation read/write、forward、backwardには依存関係がある。

GreedySnakeはこれらをDAGとして扱い、「必要な入力が揃ったtask」からbuffer容量内で実行する。

これにより単純な固定pipelineより、

- SSD read
- SSD write
- GPU compute
- CPU optimizer

を同時にbusyにしやすくする。

### 5. `Delayed Optimizer Step`：iteration barrierを崩す

通常はiteration `t`のbackwardが終わると全optimizer updateを完了し、その後iteration `t+1`へ進む。

しかしlayer / subgroupごとに見ると、gradientが揃ったstateは早めにCPUでupdateでき、**次iterationでそのparameterを使う直前までに更新が終わればよい**。

GreedySnakeはこのslackを使い、iteration `t`のoptimizer updateの一部を、iteration `t+1`のforwardとoverlapする。

これはoptimizerを省略・遅延学習する近似ではなく、依存関係を守ったまま**wall-clock上の配置だけを後ろへずらす**。

### 6. 何を減らし、何が増えるか

| 項目 | Vertical scheduleの影響 |
|---|---|
| Parameter SSD read | 大幅に減る |
| Parameter reuse | 増える |
| Activation lifetime | 長くなる |
| Activation I/O | 増え得る |
| Optimizer idle barrier | overlapで減らす |

したがってGreedySnakeはparameter I/Oだけを見た手法ではなく、**増えたactivation I/Oを隠せるかまで含むglobal schedule**である。

## 評価

### まず見るところ
- **結論:** layer weightをmicrobatch間で再利用し、optimizer updateを次iterationへ重ねると、SSD-offloaded trainingのiteration timeを大きく短縮できる。
- **Training throughput:** ZeRO-Infinity比で約2倍前後、GPT-175Bでは最大2.53倍。
- **I/O:** parameter再ロードを減らす代わりにactivation lifetimeは伸びるため、非同期activation I/Oが重要。
- **品質:** 数学的な依存関係を維持したschedule変更で、training algorithmは同じ。
- **注意点:** NVMe queue depth、host buffer、CPU optimizer性能、gradient accumulationに強く依存する。

### なぜ大modelほど効きやすいか

modelが大きいほど、horizontal scheduleで同じparameterをSSDから繰り返し読むcostが増える。特にmicrobatchが小さい条件ではcompute時間に対してparameter load比率が高く、vertical reuseの効果が大きい。

### Optimizer overlapの意味

optimizer stepを次iterationへ押し出すことで、backward終了後にCPU optimizerだけを待つGPU idle時間を減らす。

ただしCPU updateが次iterationの当該layer利用までに終わらない場合はstallするため、CPU性能もthroughputへ直接効く。

### Activation側の副作用

vertical scheduleはactivation lifetimeを延ばすため、sequence lengthやmicrobatch数を増やすとactivation storage / I/Oが増える。

そのためparameter read削減が大きくても、

- CPU DRAM bufferが小さい
- SSD write/readが遅い
- sequenceが非常に長い

条件ではactivation側が新しいbottleneckになり得る。

### 評価上の制約

- NVMe性能とqueue depthに依存する。
- CPU optimizer性能に依存する。
- host DRAM buffer容量が小さいとvertical scheduleの利点が減る。
- downstream精度よりsystem throughput中心の評価。
- cloud storage条件はlocal NVMeとI/O特性が異なる。
