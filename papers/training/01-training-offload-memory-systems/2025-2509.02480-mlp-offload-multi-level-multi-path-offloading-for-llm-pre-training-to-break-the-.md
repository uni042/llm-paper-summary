# MLP-Offload: Multi-Level, Multi-Path Offloading for LLM Pre-training to Break the GPU Memory Wall

> 巨大な最適化状態（optimizer state）をGPU・CPU DRAM・ローカルNVMe・共有ストレージへ分散し、複数の入出力経路を同時に使うことでLLM事前学習のI/O待ちを減らす方式。

## 概要

MLP-Offloadは、LLM事前学習（pre-training）で巨大になる**最適化状態（optimizer state）**を、GPUだけに置かず複数の記憶装置へ分散する学習システムである。

Adam系最適化器では、モデル重みに加えて勾配や複数の更新用状態を保持するため、学習時の必要メモリはモデル重みそのものより大きくなる。GPUメモリへ収まらない分をCPU DRAMやSSDへ逃がせるが、今度は入出力待ちが学習時間を支配しやすい。

MLP-Offloadの特徴は、単純な

`GPU → CPU DRAM → SSD`

という一本の経路だけを使うのではなく、

- ノード内のローカルNVMe SSD
- ネットワーク越しの共有ストレージ

を**同時に別経路として使う**点にある。

論文の言葉でいう、

- **多階層（multi-level）**：データを置ける記憶階層を増やす
- **多経路（multi-path）**：複数の入出力経路を同時に流す

は別の工夫である。

対象は学習時の最適化状態、パラメータ、勾配であり、推論時のMoEエキスパート重みやKVキャッシュではない。Smart-InfinityのようなSSD側演算装置も必要とせず、通常のCPU、NVMe、HPC共有ストレージを使う。

## 手法のあらまし

### 1. 多階層（multi-level）：状態を複数の容量層へ分散する

モデル状態を小さな**サブグループ（subgroup）**へ分割し、現在処理する部分だけをGPUやCPUへ読み込む。

残りは次のように配置する。

| 階層 | 主な役割 |
|---|---|
| GPU HBM | 今まさに計算する状態 |
| CPU DRAM | 近いうちに再利用する状態の高速な一時置き場 |
| ローカルNVMe | DRAMに収まらない大容量状態 |
| 共有PFS / Object Store | ローカルSSDにも収まらない状態、または追加のI/O経路 |

ここで**並列ファイルシステム（Parallel File System; PFS）**は、複数サーバーから同時アクセスできるHPC向けの共有ストレージである。

通常はチェックポイント保存先として使われることが多いが、MLP-Offloadでは**学習反復の途中で最適化状態を直接読み書きする活動中の記憶階層**として利用する。

### 2. 多経路（multi-path）：ローカルSSDと共有ストレージを並列に使う

階層を増やしても、すべてのデータが最終的に1本のローカルSSD経路を通るなら、そのSSDが帯域上限になった時点で性能は伸びない。

MLP-Offloadは、

- ローカルNVMeへの入出力
- ネットワーク経由PFSへの入出力

を独立したキューとして扱い、異なる最適化状態を別々の経路へ振り分ける。

つまりPFSは「ローカルSSDが満杯になったときだけ使う倉庫」ではなく、**ローカルSSDと同時に帯域を供給する第2の入出力経路**として使われる。

これにより、利用できる総入出力帯域（aggregate I/O bandwidth）を増やす。

### 3. サブグループ単位で必要な状態だけ読み込む

全モデルの最適化状態を一度にGPUへ戻すのではなく、更新対象を小さなサブグループへ分ける。

あるサブグループを更新するときだけ、概念的に

`storage → CPU DRAM → GPU/CPUで更新 → storage`

という流れを実行する。

サブグループを小さくすると、同時に必要なメモリは減る。一方で、

- 読み書き回数が増える
- 小さいI/Oが増えて帯域効率が落ちる

ため、細かく分ければよいわけではない。

これは**ピークメモリ削減とI/O効率のトレードオフ**になる。

### 4. CPU DRAMに残っている状態を先に更新し、再読み込みを減らす

ある最適化状態をストレージからCPU DRAMへ読んだ直後にまた追い出し、少し後ですぐ再読込すると無駄なI/Oが発生する。

MLP-Offloadは更新順序を調整し、CPU DRAMのキャッシュにすでに存在する状態をなるべく続けて利用する。

これが**キャッシュ再利用を優先した更新順序（cache-friendly update order）**である。

同じデータを短時間に何度も下位ストレージへ追い出して読み直す現象を**スラッシング（thrashing）**という。MLP-Offloadは更新順序の調整でこれを減らす。

ここでのキャッシュは推論時のエキスパートキャッシュではなく、**学習時の最適化状態をCPU DRAMへ一時保持するキャッシュ**である。

### 5. 勾配はFP16のまま運び、更新直前にFP32へ変換する

最適化器ではFP32の状態を使うが、GPUから勾配を退避する段階ではFP16のまま転送する。

これにより、同じ要素数でも転送バイト数を減らせる。

CPU側で最適化更新を行う直前にFP32へ変換するため、論文の狙いは最適化計算全体を低精度化することではなく、**転送時の表現（transport representation）だけを小さくすること**にある。

### 6. 二重バッファリング（double buffering）で読み込み・計算・書き戻しを重ねる

複数の作業バッファを交互に使い、

- 現在のサブグループを更新する
- 次のサブグループを読み込む
- 前のサブグループを書き戻す

という処理を同時に進める。

さらにローカルNVMeとPFSで、同時発行するI/O数やキューの深さを別々に調整する。

これにより一方のストレージが混雑しても、もう一方の経路まで一緒に停止しにくくする。

### 7. Smart-Infinityとの違い

Smart-InfinityはSSD側に演算機能を持つ装置を使い、最適化器計算の一部をストレージ近くへ移す。

MLP-Offloadはストレージ側演算（near-storage compute）を使わず、**通常のCPU＋NVMe＋共有ストレージをソフトウェアの配置とスケジューリングで並列利用する**。

そのため専用ハードウェアなしで構成できる一方、PFSやネットワーク帯域、CPU最適化器性能に依存する。

## 評価

### まず見るところ

- **結論:** 最適化状態をDRAM・ローカルNVMe・共有PFSへ分散し、複数のI/O経路を並列利用すると、容量だけでなく学習時の入出力処理量も改善できる。
- **学習速度:** ZeRO-3比最大2.5倍。共有PFSを使わないローカル階層だけでも最大1.6倍。
- **入出力:** 複数経路を使うことで合計I/O処理量が約2倍になる条件を示す。
- **品質:** 学習アルゴリズムそのものを変える研究ではなく、主評価はシステム性能。下流タスク精度の広範比較は中心ではない。
- **注意点:** HPC向けで、共有PFS性能やネットワーク混雑に強く依存する。一般PCで直接使えるのは主にDRAM＋ローカルNVMe部分である。

### 実機環境

| 環境 | GPU | Host RAM | Storage |
|---|---|---:|---|
| JLSE | 4×H100 80 GB | 512 GB | RAID NVMe + VAST系shared storage |
| Polaris | 4×A100 40 GB | 512 GB | Local NVMe + Lustre系PFS |

40B〜280B級モデルを評価する。

### 主な比較

| 条件 | MLP-Offloadの改善 |
|---|---:|
| vs DeepSpeed ZeRO-3 | **最大2.5倍** |
| PFSなし、local tierのみ | **最大1.6倍** |
| Aggregate I/O throughput | 約2倍 |
| Gradient accumulation条件 | 少なくとも約40%高速 |

PFSを使わなくても改善が残るため、利得は共有ストレージの容量追加だけではなく、サブグループの処理順やI/Oと計算の重ね合わせにも由来する。

### 何が速くなっているか

これは推論時のtoken/sではなく、**学習反復時間と学習処理量（training throughput）**の改善である。

特にモデルが大きく、最適化状態がCPU DRAMからもあふれるほど、ローカルNVMeとPFSを同時利用する価値が増える。

### Capacity面

40B〜280B級の学習状態を少数GPUで扱い、GPUやDRAMだけでは保持できない部分をNVMe/PFSへ置く。

モデルのパラメータ数を減らしているのではなく、**どの記憶階層へ常駐させるかを変えることで容量制約を越えている**。

### 評価上の制約

- 十分な帯域を持つPFSがあるHPCクラスタを前提とする
- 他ジョブとのネットワーク・ストレージ競合が強いと性能は変わる
- 一般PCでは共有PFS経路をそのまま再現できない
- 学習品質よりシステム処理量・I/Oが主評価
- DeepSpeedやクラスタストレージとの統合作業が必要
