# ZeRO-Infinity: Breaking the GPU Memory Wall for Extreme Scale Deep Learning

> 学習用のparameter・gradient・optimizer stateをGPUだけでなくCPU DRAMとNVMe SSDへ分割配置し、各nodeのSSD読込を並列化しながら必要なstateを先読みしてGPU計算と重ねることで、GPU memory総量を超える巨大modelを学習可能にするsystem。

## 概要

ZeRO-InfinityはZeRO-3を基盤に、学習中に保持する

- model parameter
- gradient
- optimizer state

の保存先をGPU HBMだけでなく、CPU DRAMと通常のNVMe SSDまで広げる。

大規模学習ではmodel weightそのものに加え、gradientやAdam等のoptimizer stateが大量のmemoryを使う。ZeRO-3はこれらをGPU間へ分割して重複を減らすが、modelがcluster全体のGPU memory総量を超えると、それだけでは収まらない。

ZeRO-Infinityは**今すぐGPUで使わないstateをCPU / NVMeへ置き、必要になる前にGPUへ戻す**ことで容量制約を緩和する。

ただしSSDを単なる巨大なoverflow領域として使うだけでは遅い。必要になってから、

`NVMe → CPU DRAM → GPU`

と順番に読み戻せばGPUがI/O完了を待つからである。

そこでZeRO-Infinityは、

1. model stateをnode間へ分割する
2. 各nodeが自分のNVMeから担当部分を同時に読む
3. 数layer先で必要なparameterを先読みする
4. SSD読込、CPU→GPU copy、GPU間通信を現在のGPU計算と同時進行させる

という設計を組み合わせる。

中心的な発想は、**遅いSSDを高速memoryの代用品にするのではなく、全nodeのI/O帯域を足し合わせ、転送時間を計算の裏へ隠して容量拡張として使うこと**である。

## 問題設定

大規模trainingでは主に、

- parameter
- gradient
- optimizer state
- activation

がGPU memoryを消費する。

ZeRO-3はparameter・gradient・optimizer stateをdata-parallel GPU間で分割するため、各GPUがmodel全stateを完全複製する必要をなくす。

しかし、それでも**全GPU HBMを合計した容量を超えるmodel**は保持できない。

CPU DRAMやNVMe SSDへstateを逃がせば容量は増えるが、今度はPCIeやSSD I/Oが新しいbottleneckになる。ZeRO-Infinityは、memory capacityとdata movementを別問題として扱わず、**どこへ置くかと、いつ戻すかを同時に設計する**。

## 手法

### 1. ZeRO-3の分割保存先をCPU / NVMeまで広げる

ZeRO-3ではmodel stateをGPU間へ**分割（partition）**し、各GPUは自分の担当部分だけを常時保持する。

あるlayerを計算するときは、必要なparameter shardをGPU間で集めて一時的に完全なparameterを作る。

ZeRO-Infinityでは、その分割stateの保存場所をGPUだけに限定せず、

- GPU HBM
- CPU DRAM
- NVMe SSD

まで広げる。

ZeRO-Offloadが主にoptimizer stateとoptimizer計算をCPUへ移すのに対し、ZeRO-Infinityは**parameter自体もNVMeまで退避できる**点が大きい。

### 2. 帯域重視の分割（bandwidth-centric partitioning）：全nodeのSSDを同時に使う

1台のnodeだけがparameter全体をSSDから読み、それを他GPUへ配る構成では、その1台のSSD / PCIe帯域が全体の上限になる。

ZeRO-Infinityはmodel stateをnode間へ分け、**各nodeが自分の担当parameterを自分のCPU / NVMeから同時に読み込む**。

その後、全収集通信（AllGather）で各nodeのparameter shardを集め、計算に必要な完全parameterを構成する。

これが論文の**帯域重視の分割（bandwidth-centric partitioning）**である。

node数を増やすと、GPU演算性能だけでなく、

- CPU memory bandwidth
- NVMe bandwidth
- PCIe bandwidth

もnode数分だけ並列利用できる。

論文では、1 DGX-2 nodeあたり約25 GB/sのNVMe bandwidthでも、64 nodeなら理論上のaggregate bandwidthが約1.6 TB/sになる例を示す。

つまり「1台のSSDを高速化する」のではなく、**多数nodeのSSDを同時に読むことで合計帯域を増やす**。

### 3. 重ね合わせ重視の設計（overlap-centric design）：必要になる前に先読みする

NVMe上のparameterを実際にGPU計算へ使うまでには、おおむね、

`NVMe → CPU DRAM → GPU → GPU間でparameter共有`

という複数段階がある。

これを現在layerの計算が終わってから始めると、すべてがGPUの待ち時間になる。

ZeRO-Infinityはforward / backwardのoperator順を追跡し、数operator先で必要になるstateを事前に読み始める。

たとえばGPUがlayer 10を計算している間に、

- layer 13のparameterをNVMe→CPUへ読む
- layer 12のparameterをCPU→GPUへ送る
- layer 11のparameter shardをGPU間でAllGatherする

といった処理を同時に進める。

論文の**重ね合わせ重視の設計（overlap-centric design）**は、このように異なる段階のI/Oと通信をGPU計算の裏へ隠す考え方を指す。

### 4. メモリ重視のタイル分割（memory-centric tiling）：1 layer自体が大きすぎても小分けして実行する

model全体を分割しても、1つの巨大linear layerだけでGPU memoryへ収まらない場合がある。

ZeRO-Infinityはこのようなoperatorを、小さい**タイル（tile）**へ分ける。

一度にGPUへ載せるのは1 tile分のparameterとactivationだけにし、

1. tile 1を読み込んで計算
2. tile 2を読み込んで計算
3. ...

と順番に処理する。

これが**メモリ重視のタイル分割（memory-centric tiling）**である。

tensor parallelismのように「1 layerを複数GPUへ恒常的に分割する」のではなく、**1 GPU上の作業集合（working set）をmemoryへ収まる大きさに切る**ことが目的である。

## 評価

主評価はNVIDIA DGX-2 clusterで、各node 16基のV100 32GB、最大32 node / 512 GPUまで使用する。対象はGPT系dense Transformerで、CPU DRAMとnode-local NVMe SSDをoffload tierとして使う。

### 主要結果

- 512 V100 GPUで、**32 trillion parameterまでtraining iterationが実行可能なmemory scalability**を実証。
- 400B〜20T parameterの条件で約37〜50 TFLOP/s/GPUを報告し、cluster全体では25 PFLOP/s超になる設定がある。
- 約500B modelでは、GPU-onlyの3D parallelismに近いthroughputを示す条件がある。
- 1T modelのscale-outでは、GPU数だけでなくCPU / NVMeのaggregate bandwidthも増えるため、GPU台数比以上に性能が伸びる領域を報告する。
- 単一DGX-2 nodeでも、GPU HBMだけには収まらない数百B〜1T級modelを実行できる構成を示す。

### 「32T modelを動かした」の意味

32Tという値は、32 trillion parameter modelを現実的なtoken budgetで最後までpre-trainingし、最終精度まで評価したという意味ではない。

論文が示したのは、**32T parameter規模でもtraining iterationを実際に成立させられるmemory scale**である。

したがって、

- memory scalability
- 1 iterationのsystem throughput
- 完全なend-to-end model training cost

は分けて読む必要がある。

## 既存研究との差

### ZeRO / ZeRO-Offloadとの違い

ZeROはmodel stateの重複をGPU間partitionで減らす。

ZeRO-Offloadはoptimizer stateとoptimizer計算を主にCPUへ移す。

ZeRO-Infinityはさらに、**parameterを含むmodel stateをCPU / NVMeまで広げ、全nodeのI/O帯域を並列利用する**。

### G10との違い

G10は実行graphからtensorの次回利用時刻を求め、GPU / CPU / SSDのどこへ置くかをtensor単位で決める。主評価はsimulation。

ZeRO-Infinityはdata-parallel partitionを利用し、**各nodeのCPU / NVMe帯域を合計して巨大trainingへ使うscale-out設計**が中心で、multi-node実機評価を行う。

### Smart-Infinityとの違い

ZeRO-InfinityではNVMe上のoptimizer stateを更新する際、storageとhost間のdata movementが残る。

Smart-Infinityは演算機能を持つstorage側でoptimizer updateを行い、このdata movement自体を減らす後続研究である。

## 限界

- NVMe I/O cost自体がなくなるわけではなく、十分な先読み時間とparallel I/OがないとGPU stallが発生する。
- 各nodeがlocal NVMeを持つclusterを強く想定しており、共有network storageでは同じscale-out bandwidthにならない。
- 主評価はV100 / DGX-2世代で、H100 / B200 / CXL memory世代ではGPU演算性能とI/O帯域の比率が異なる。
- dense GPT型model中心で、MoEではexpert routingとstate placementが追加要因になる。
- CPU / NVMe offloadを増やすほど、host RAM、PCIe、SSD endurance、storage contentionが新しい制約になる。

## 一般的な実装上の含意

ZeRO-Infinityの重要な点は、offload先を単なる遅いoverflow領域として扱わないことにある。

parameterをnode間へ分割し、**全nodeのNVMe→CPU→GPU pathを同時に使うことで、cluster規模とともにaggregate I/O bandwidthも増やす**。

さらに未来に必要なstateを先読みし、SSD read・host-to-device copy・GPU間collectiveを現在のGPU計算と重ねる。

この「容量を下位memoryへ拡張するだけでなく、data movementまでscheduleする」という設計は、後続のSSD-offloaded training研究の基礎になっている。
