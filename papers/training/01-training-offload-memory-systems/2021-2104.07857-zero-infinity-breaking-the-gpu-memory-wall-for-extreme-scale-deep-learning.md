# ZeRO-Infinity: Breaking the GPU Memory Wall for Extreme Scale Deep Learning

> 学習パラメータ・勾配・最適化状態をGPU、CPU DRAM、NVMe SSDへ分散し、各SSDの読み込みと先読みをGPU計算に重ねて、GPU総容量を超える巨大モデルを収める方式。

## 概要

ZeRO-InfinityはZeRO-3を基盤に、学習中に保持する

- モデルパラメータ
- 勾配
- オプティマイザ状態

の保存先をGPU HBMだけでなく、CPU DRAMと通常のNVMe SSDまで広げる。

大規模学習ではモデル 重みそのものに加え、勾配やAdam等のオプティマイザ状態が大量のメモリを使う。ZeRO-3はこれらをGPU間へ分割して重複を減らすが、モデルがcluster全体のGPU メモリ総量を超えると、それだけでは収まらない。

ZeRO-Infinityは**今すぐGPUで使わない状態をCPU / NVMeへ置き、必要になる前にGPUへ戻す**ことで容量制約を緩和する。

ただしSSDを単なる巨大なoverflow領域として使うだけでは遅い。必要になってから、

`NVMe → CPU DRAM → GPU`

と順番に読み戻せばGPUがI/O完了を待つからである。

そこでZeRO-Infinityは、

1. モデル 状態をnode間へ分割する
2. 各nodeが自分のNVMeから担当部分を同時に読む
3. 数層先で必要なパラメータを先読みする
4. SSD読込、CPU→GPU copy、GPU間通信を現在のGPU計算と同時進行させる

という設計を組み合わせる。

中心的な発想は、**遅いSSDを高速メモリの代用品にするのではなく、全nodeのI/O帯域を足し合わせ、転送時間を計算の裏へ隠して容量拡張として使うこと**である。

DGX-2の実機評価では、512基のV100で最大32兆パラメータ規模の学習反復を成立させた。Fig. 5(a)の評価では、0.5T〜20Tのモデルで約34〜49 TFLOP/s/GPUの学習処理量を示した。

## 問題設定

大規模学習では主に、

- パラメータ
- 勾配
- オプティマイザ状態
- 活性値

がGPU メモリを消費する。

ZeRO-3はパラメータ・勾配・オプティマイザ状態をdata-並列 GPU間で分割するため、各GPUがモデル全状態を完全複製する必要をなくす。

しかし、それでも**全GPU HBMを合計した容量を超えるモデル**は保持できない。

CPU DRAMやNVMe SSDへ状態を逃がせば容量は増えるが、今度はPCIeやSSD I/Oが新しいボトルネックになる。ZeRO-Infinityは、メモリ capacityとdata movementを別問題として扱わず、**どこへ置くかと、いつ戻すかを同時に設計する**。

## 手法

### 1. ZeRO-3の分割保存先をCPU / NVMeまで広げる

ZeRO-3ではモデル 状態をGPU間へ**分割（partition）**し、各GPUは自分の担当部分だけを常時保持する。

ある層を計算するときは、必要なパラメータ shardをGPU間で集めて一時的に完全なパラメータを作る。

ZeRO-Infinityでは、その分割状態の保存場所をGPUだけに限定せず、

- GPU HBM
- CPU DRAM
- NVMe SSD

まで広げる。

ZeRO-Offloadが主にオプティマイザ状態と最適化器計算をCPUへ移すのに対し、ZeRO-Infinityは**パラメータ自体もNVMeまで退避できる**点が大きい。

### 2. 帯域重視の分割（bandwidth-centric partitioning）：全nodeのSSDを同時に使う

1台のnodeだけがパラメータ全体をSSDから読み、それを他GPUへ配る構成では、その1台のSSD / PCIe帯域が全体の上限になる。

ZeRO-Infinityはモデル 状態をnode間へ分け、**各nodeが自分の担当パラメータを自分のCPU / NVMeから同時に読み込む**。

その後、全収集通信（AllGather）で各nodeのパラメータ shardを集め、計算に必要な完全パラメータを構成する。

これが論文の**帯域重視の分割（帯域-centric partitioning）**である。

node数を増やすと、GPU演算性能だけでなく、

- CPU メモリ 帯域
- NVMe 帯域
- PCIe 帯域

もnode数分だけ並列利用できる。

論文では、1 DGX-2 nodeあたり約25 GB/sのNVMe 帯域でも、64 nodeなら理論上のaggregate 帯域が約1.6 TB/sになる例を示す。

つまり「1台のSSDを高速化する」のではなく、**多数nodeのSSDを同時に読むことで合計帯域を増やす**。

### 3. 重ね合わせ重視の設計（overlap-centric design）：必要になる前に先読みする

NVMe上のパラメータを実際にGPU計算へ使うまでには、おおむね、

`NVMe → CPU DRAM → GPU → GPU間でparameter共有`

という複数段階がある。

これを現在層の計算が終わってから始めると、すべてがGPUの待ち時間になる。

ZeRO-Infinityは順伝播 / 逆伝播の演算子順を追跡し、数演算子先で必要になる状態を事前に読み始める。

たとえばGPUが層 10を計算している間に、

- 層 13のパラメータをNVMe→CPUへ読む
- 層 12のパラメータをCPU→GPUへ送る
- 層 11のパラメータ shardをGPU間でAllGatherする

といった処理を同時に進める。

論文の**重ね合わせ重視の設計（重畳-centric design）**は、このように異なる段階のI/Oと通信をGPU計算の裏へ隠す考え方を指す。

### 4. メモリ重視のタイル分割（memory-centric tiling）：1 layer自体が大きすぎても小分けして実行する

モデル全体を分割しても、1つの巨大linear 層だけでGPU メモリへ収まらない場合がある。

ZeRO-Infinityはこのような演算子を、小さい**タイル（tile）**へ分ける。

一度にGPUへ載せるのは1 tile分のパラメータと活性値だけにし、

1. tile 1を読み込んで計算
2. tile 2を読み込んで計算
3. ...

と順番に処理する。

これが**メモリ重視のタイル分割（メモリ-centric tiling）**である。

テンソル 並列化のように「1 層を複数GPUへ恒常的に分割する」のではなく、**1 GPU上の作業集合（working set）をメモリへ収まる大きさに切る**ことが目的である。

## 評価

主評価はNVIDIA DGX-2 clusterで、各node 16基のV100 32GB、最大32 node / 512 GPUまで使用する。対象はGPT系密 Transformerで、CPU DRAMとnode-局所 NVMe SSDをオフロード tierとして使う。

### 主要結果

- 512 V100 GPUで、**32 trillion パラメータまで学習 iterationが実行可能なメモリ scalability**を実証。
- 400B〜20T パラメータの条件で約37〜50 TFLOP/s/GPUを報告し、cluster全体では25 PFLOP/s超になる設定がある。
- 約500B モデルでは、GPU-onlyの3D 並列化に近いスループットを示す条件がある。
- 1T モデルのscale-outでは、GPU数だけでなくCPU / NVMeのaggregate 帯域も増えるため、GPU台数比以上に性能が伸びる領域を報告する。
- 単一DGX-2 nodeでも、GPU HBMだけには収まらない数百B〜1T級モデルを実行できる構成を示す。

### 「32T modelを動かした」の意味

32Tという値は、32 trillion パラメータ モデルを現実的なトークン budgetで最後までpre-学習し、最終精度まで評価したという意味ではない。

論文が示したのは、**32T パラメータ規模でも学習 iterationを実際に成立させられるメモリ scale**である。

したがって、

- メモリ scalability
- 1 iterationのシステム スループット
- 完全なエンドツーエンド モデル 学習 コスト

は分けて読む必要がある。

## 既存研究との差

### ZeRO / ZeRO-Offloadとの違い

ZeROはモデル 状態の重複をGPU間partitionで減らす。

ZeRO-Offloadはオプティマイザ状態と最適化器計算を主にCPUへ移す。

ZeRO-Infinityはさらに、**パラメータを含むモデル 状態をCPU / NVMeまで広げ、全nodeのI/O帯域を並列利用する**。

### G10との違い

G10は実行graphからテンソルの次回利用時刻を求め、GPU / CPU / SSDのどこへ置くかをテンソル単位で決める。主評価はシミュレーション。

ZeRO-Infinityはdata-並列 partitionを利用し、**各nodeのCPU / NVMe帯域を合計して巨大学習へ使うscale-out設計**が中心で、multi-node実機評価を行う。

### Smart-Infinityとの違い

ZeRO-InfinityではNVMe上のオプティマイザ状態を更新する際、ストレージとホスト間のdata movementが残る。

Smart-Infinityは演算機能を持つストレージ側で最適化器 更新を行い、このdata movement自体を減らす後続研究である。

## 限界

- NVMe I/O コスト自体がなくなるわけではなく、十分な先読み時間と並列 I/OがないとGPU 待ちが発生する。
- 各nodeが局所 NVMeを持つclusterを強く想定しており、共有ネットワーク ストレージでは同じscale-out 帯域にならない。
- 主評価はV100 / DGX-2世代で、H100 / B200 / CXL メモリ世代ではGPU演算性能とI/O帯域の比率が異なる。
- 密 GPT型モデル中心で、MoEでは専門家 ルーティングと状態 配置が追加要因になる。
- CPU / NVMe オフロードを増やすほど、ホスト RAM、PCIe、SSD endurance、ストレージ contentionが新しい制約になる。

## 一般的な実装上の含意

ZeRO-Infinityの重要な点は、オフロード先を単なる遅いoverflow領域として扱わないことにある。

パラメータをnode間へ分割し、**全nodeのNVMe→CPU→GPU pathを同時に使うことで、cluster規模とともにaggregate I/O 帯域も増やす**。

さらに未来に必要な状態を先読みし、SSD read・ホスト-to-device copy・GPU間集合通信を現在のGPU計算と重ねる。

この「容量を下位メモリへ拡張するだけでなく、data movementまでscheduleする」という設計は、後続のSSD-オフロード 学習研究の基礎になっている。
