# ZeRO-Infinity: Breaking the GPU Memory Wall for Extreme Scale Deep Learning

> parameter・gradient・optimizer stateをGPUだけでなくCPU DRAMとNVMe SSDへ分散し、各nodeのI/Oを並列利用しながら先読みとGPU計算を重ね、GPU memoryを超える巨大modelを学習可能にするtraining offload system。

## 概要

ZeRO-InfinityはZeRO-3を基盤に、parameter・gradient・optimizer stateの保存先をGPU群だけでなくCPU DRAMと通常のNVMe SSDまで広げる。GPU memoryへ常駐させる必要がないstateを外へ置き、必要になる前に戻すことで、cluster全体のHBM容量を超えるmodelを学習できるようにする。

単純なNVMe offloadではstorage→CPU→GPU転送がGPU計算を止める。ZeRO-Infinityは、同じdata-parallel groupの各nodeが自分のCPU / NVMeからparameterの一部分を同時に読み、その後GPU間通信で結合する。これによりnode数とともに使えるaggregate I/O bandwidthも増える。

さらにforward / backward中のoperator順序を追跡し、将来必要になるparameterのNVMe→CPU、CPU→GPU、GPU間collective communicationを現在のGPU計算と重ねる。目的は遅いmemoryを避けることではなく、**複数nodeのI/Oを並列化し、転送を計算の裏へ隠して容量拡張として使うこと**にある。

## 問題設定

大規模trainingではparameter、gradient、optimizer state、activationがGPU memoryを圧迫する。ZeRO-3はmodel stateをGPU間で分割するが、それでもaggregate HBMを超えるmodelは保持できない。

CPU DRAMやNVMeへ逃がせば容量は増える一方、必要になってから順番にdataを戻すとI/O待ちがcritical pathへ出る。ZeRO-Infinityはcapacityだけでなく、**CPU / NVMe帯域とGPU計算をどう重ねるか**を同時に扱う。

## 手法

### 1. ZeRO-3のpartitionをCPU / NVMeまで広げる

各GPUはmodel全体のcopyを常時持たず、自分が担当するpartitionだけを保持する。必要なlayerのparameterはforward / backward直前にGPU間で集める。

ZeRO-Infinityでは、このpartitionの保存先をGPUだけに限定せずCPU DRAMやNVMe SSDへ広げる。ZeRO-Offloadが主にoptimizer stateとoptimizer computationをCPUへ移すのに対し、ZeRO-Infinityはparameter自体もNVMeへ置ける。

### 2. 各nodeのI/Oを並列に使う

論文の **bandwidth-centric partitioning** は、1 nodeだけがparameter全体をstorageから読んで全GPUへ配るのではなく、各nodeが自分のpartitionを同時に読み込む仕組みである。

その後all-gatherで完全なparameterを構成するため、nodeを増やすとGPUだけでなくCPU memory / NVMe / PCIeのaggregate bandwidthも増える。公式説明では1 DGX-2 nodeあたり約25 GB/sのNVMe bandwidthでも、64 nodeならaggregate約1.6 TB/sになる例を示す。

### 3. 転送を先読みしてGPU計算と重ねる

NVMe上のparameterは概ね「NVMe→CPU→GPU→GPU間共有」の順で利用される。ZeRO-Infinityはforward / backwardのoperator列を実行時に追跡し、数operator先で必要になるparameterを先読みする。

現在layerをGPUで計算している間に、別layerのNVMe read、別layerのCPU→GPU copy、さらに別layerのGPU間communicationを進める。論文の **overlap-centric design** は、この複数段階のdata movementを直列に待たないための設計を指す。

### 4. 単一operatorが大きすぎる場合も分割する

単一linear layer自体がGPU memoryへ収まらない場合、model state全体をpartitionしても実行できない。

ZeRO-Infinityの **memory-centric tiling** は、大きいoperatorをGPUへ収まる小さいtileへ分け、tileごとにparameterを読みながら順番に計算する。tensor parallelismのようにoperatorを恒常的に複数GPUへ分割するのではなく、1 GPUで処理可能なworking setへ小分けするmemory対策である。

## 評価

主評価はNVIDIA DGX-2 clusterで、各node 16基のV100 32GB、最大32 node / 512 GPUまで使用する。対象はGPT系dense Transformerで、CPU DRAMとlocal NVMe SSDをoffload tierとして使う。

主要結果は以下。

- 512 V100 GPUで数十兆parameter規模までtraining iterationを実行し、32 trillion parameterまでmemory scalabilityを示す。
- 400B〜20T parameterで約37〜50 TFLOP/s/GPUを報告し、cluster全体では25 PFLOP/s超を維持する条件がある。
- 約500B modelではGPU-only 3D parallelismと近いthroughputを示す。
- 1T modelのscale-outでは、GPU数とともにCPU / NVMe aggregate bandwidthも増えるためsuper-linearなscaling領域を報告する。
- 単一DGX-2 nodeでも、GPU HBMだけでは保持できない数百B〜1T規模modelを扱える構成を示す。

32Tという値は、32T modelを実用的なtoken budgetでend-to-end pre-training完了したという意味ではなく、**training iterationを実際に動かせるmemory scaleを実証した結果**として読む必要がある。

## 既存研究との差

### ZeRO / ZeRO-Offloadとの違い

ZeROはmodel stateの重複をGPU間で分割する。ZeRO-Offloadはoptimizer stateとoptimizer computationを主にCPUへ移す。

ZeRO-InfinityはZeRO-3を基盤に、parameterを含むmodel stateをCPU / NVMeまで広げ、さらに各nodeのI/Oを同時利用してstorage bandwidthをaggregateする。

### G10との違い

G10は実行graphからtensorの次回利用時刻を求め、GPU / host / SSDのどこへ置くかをtensor単位で決める。主評価はsimulation。

ZeRO-Infinityはdata-parallel partitionを使い、**各nodeのCPU / NVMe帯域をaggregateして巨大model trainingへ使う**ことが中心で、実機multi-node評価を行う。

### Smart-Infinityとの違い

ZeRO-InfinityではNVMe上のoptimizer stateを更新するためにstorageとhost間のdata movementが残る。Smart-InfinityはFPGA付きcomputational storage側でoptimizer updateを実行し、このtransfer自体を減らす後続研究である。

## 限界

- NVMe利用時もI/O costは消えず、十分なprefetch windowとparallel I/OがないとGPU stallが発生する。
- local NVMeをnodeごとに持つclusterを前提とする部分が大きく、shared network storageでは同じbandwidth scalingにならない。
- 主評価はV100 / DGX-2世代で、H100 / B200 / CXL memoryではresource比率が異なる。
- dense GPT型model中心で、MoEや現代的architectureではstate sizeとcommunication patternが変わる。
- CPU / NVMe offloadを増やすほどhost memory、PCIe、SSD endurance、storage contentionが新しいconstraintになる。

## 一般的な実装上の含意

ZeRO-Infinityの重要な点は、offload先を単なる遅いoverflow領域として扱わないことにある。parameterをnode間へ分割し、**全nodeのNVMe→CPU→GPU pathを同時利用すればaggregate bandwidthを増やせる**。

そのうえで未来に必要なdataを先読みし、複数段階の転送を現在のGPU計算と重ねることで、slow tierの容量をtrainingへ使いやすくする。この設計原理は後続のSSD-offloaded trainingにも引き継がれている。
