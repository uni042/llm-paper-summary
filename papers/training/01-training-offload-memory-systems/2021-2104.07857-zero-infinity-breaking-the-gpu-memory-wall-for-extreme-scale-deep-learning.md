# ZeRO-Infinity: Breaking the GPU Memory Wall for Extreme Scale Deep Learning

## 書誌情報と位置付け

Samyam Rajbhandari、Olatunji Ruwase、Jeff Rasley、Shaden Smith、Yuxiong Heによる2021年の大規模学習システム研究である。高性能計算分野の国際会議SC 2021に掲載され、プレプリントはarXiv:2104.07857、正式版のDOIは10.1145/3458817.3476205である。著者らの実装はDeepSpeedに統合されている。今回の再監査では原著の方法・実機評価・構成要素除去実験を確認し、特に「32兆パラメータが載ること」と「20兆パラメータで高い処理率を測ったこと」を混同しないよう修正した。

この研究は推論用の専門家オフロードではなく、密な大規模モデルの**学習時**に必要なパラメータ、勾配、最適化器状態を階層メモリへ配置する仕組みである。現在の小規模GPU上でのLLM推論へ性能値をそのまま適用することはできないが、学習システムにおける分割配置、転送帯域の集約、先読みと演算重畳の原理を理解する基礎資料となる。

## 概要

大規模言語モデルを学習すると、重みだけでなく、逆伝播用の勾配、Adamなどの最適化器が保持する一次・二次モーメント、数値安定性のための高精度状態、活性値がメモリを消費する。単に重みがGPUへ収まることは学習可能性を意味しない。原著は混合精度Adam学習のモデル状態をパラメータ当たり約20バイトと数え、1兆パラメータで状態だけでも約20TB規模となることを示す。従来の三次元並列化はGPUメモリの総容量に依存するため、容量の増加がモデル規模の増加に追い付かなくなる。

ZeRO-Infinityは、ゼロ冗長最適化器（Zero Redundancy Optimizer、ZeRO）の第3段階で全モデル状態をデータ並列プロセス間に分割する設計を、GPUの高帯域メモリだけでなくCPUの主記憶、さらに不揮発性メモリ接続のSSD（NVMe SSD）へ拡張する。ただし低速なストレージへ保存するだけではGPUが待つため、各ノードの帯域を同時利用し、未来に必要なパラメータを先読みし、計算と転送を重ねる。個々の演算子が巨大でGPUへ収まらない場合は、演算をタイルに分割して作業集合を小さくする。

論文は32 DGX-2ノード、合計512基のV100 GPUで最大32兆パラメータのモデル規模を実証したと報告する。実測処理率の中心は最大20兆パラメータの設定であり、10兆時43、20兆時34 TFLOP/s/GPUとなる。512 GPUの一部設定では25 PFLOP/s超を達成する。大きなモデルを実際に数千億トークンまで学習し切ったという意味ではなく、モデル規模と反復処理率のシステム評価である。

## 問題設定

従来のデータ並列化では、各GPUがモデル全体の重みと勾配と最適化器状態を持つため、重複が大きい。ZeROの第1段階は最適化器状態、第2段階は最適化器状態と勾配、第3段階はこれらにパラメータを加えた三種類すべてを分割する。これによりGPU間の重複は減るが、クラスター全体のGPUメモリ総量を超えるモデル状態は依然として配置できない。

CPUやSSDを追加すれば容量の問題は緩和できるものの、演算に必要なデータがGPUへ届くまでに、NVMe読込、CPUメモリからGPUへの転送、GPU間でのパラメータ集約という複数の段階が必要になる。演算が終わってから逐次転送すると、GPU演算器が待機し、容量だけ増えても学習処理率が著しく落ちる。原著はメモリ容量の問題とデータ移動帯域の問題を一体として設計する必要があると主張する。

また、モデルを複数GPUへ分けても、単一の巨大な線形層を実行する瞬間に必要な重み・活性値・作業領域が一枚のGPUへ収まらない場合がある。従来はテンソル並列化などのモデル構造の変更が必要だったが、一般の研究者がモデルコードを書き換えずに大規模学習を行うには、演算子の作業集合を動的に小さくする仕組みも必要である。

## 手法

### 1. 全モデル状態の階層分割と無限オフロードエンジン

基本はZeRO-3のデータ並列分割である。各GPUは担当する重み断片を所有し、必要な層を計算する直前に他プロセスの断片を集合通信で集めて、その演算に必要な完全なパラメータを一時的に構成する。計算が終われば不要な完全コピーを解放し、勾配も分割して担当者へ戻す。この構造はモデル全体の完全な複製を各GPUに置かない。

ZeRO-Infinityの無限オフロードエンジン（Infinity Offload Engine）は、分割されたパラメータ・勾配・最適化器状態の置き場所をGPU、CPUメモリ、NVMeへ拡張する。ZeRO-Offloadが主としてCPU側へ最適化器状態・勾配を移すのに対し、ZeRO-Infinityでは巨大なパラメータ自体もNVMeへ逃がせる。保存容量を大きくするだけでなく、パラメータ断片を要求する演算の順序を追跡し、GPUへ戻す時期を制御する。

この方式ではGPUに全層を置く必要はない。たとえば層10を演算している間、層11のGPU間集合通信、層12のCPUからGPUへの転送、層13のNVMeからCPUへの読込を並列に進められる。必要なパラメータは直前にGPUへ揃え、演算が終われば下位階層へ戻す。従来の単純なCPU退避と異なり、データ移動の待ち時間を演算時間の背後へ隠すことが中心となる。

### 2. 帯域中心分割による集約I/Oの利用

単一ノードがすべてのパラメータをSSDから読み、他GPUへ配布する方式では、そのノードのSSD・PCIe帯域が全体の上限になる。帯域中心分割（bandwidth-centric partitioning）ではモデル状態をデータ並列ノードへ分割し、各ノードが担当する断片を自分のCPU・NVMeから同時に読み出す。その後、必要な層の重み断片をGPU間通信で集める。

原著の説明では一つのDGX-2ノードのNVMe帯域が約25GB/sでも、64ノードを並列利用すれば理論的な合計は約1.6TB/sとなる。重要なのはSSD一台の帯域が増えるわけではないことと、実効帯域が常に理論値へ到達するわけではないことである。データの分割、PCIeの同時利用、ノード間通信を整合させることで、GPU台数と一緒にI/O供給能力も増やす設計である。

勾配のCPU退避も同じ原理で、単一GPUのPCIeに集中させるより各GPUの経路を並列に使う。これにより、大規模化したときにデータ並列度を単に通信負荷として扱うのではなく、利用できるストレージ帯域の供給源としても活用できる。

### 3. 先読みと重畳の実行順序制御

重畳中心設計（overlap-centric design）では、演算子の実行順序から近い将来のデータ需要を予測し、SSD読込、ホストからGPUへの転送、集合通信を早期に起動する。演算を待たせず、転送を隠せるだけの計算区間を確保することが狙いである。順伝播と逆伝播では重みを再び使うタイミングが異なるため、利用順に合わせてキャッシュと先読みを行う必要がある。

原著の構成要素除去実験は、先読み・重畳を無効にすると小バッチ時の性能が大きく落ちることを示す。一方、バッチが大きく演算時間が長い場合には、転送を隠せる時間も長くなるため相対的な改善率が変わる。したがって、低速メモリへの退避が無料になるのではなく、必要な転送時間を演算とどれだけ重ねられるかが性能を決める。

### 4. メモリ中心タイル分割

巨大な線形演算子一つがGPUメモリへ収まらない場合には、メモリ中心タイル分割（memory-centric tiling）で演算子を数学的に等価な小さなタイルへ分解する。各タイルの重みと勾配だけをGPUへ置き、順に演算して解放する。タイル数を増やすほど同時に必要な作業領域を小さくできるが、タイルごとの転送と起動の費用が増えるため、無制限に細かくすれば速くなるわけではない。

原著はGPUメモリを意図的に2GBの連続領域へ断片化し、2GB超の確保を失敗させる条件でタイル分割の効果を測る。タイル分割なしでは隠れ次元8Kまでだったところ、分割係数16では64Kの巨大な隠れ次元を持つ単一層を学習できた。これは通常のTransformer全体を64Kの隠れ次元で高速学習したという意味ではなく、単一層の作業メモリ制約を分離した実験である。

### 5. 初期化時の分割とコード変更の最小化

学習を始める前にモデル全体を各プロセスで初期化すると、最初のメモリ割当てだけで失敗する。ZeRO-InfinityはPyTorchのモジュール初期化を包む仕組みを設け、サブモジュールを生成した直後にパラメータを分割する。完全なモデルを全プロセスで構築してから分割する方式と違い、初期化段階から各プロセスの必要メモリを抑える。

原著の5000億パラメータの例では、半精度のパラメータだけで約1TBとなり、各プロセスが完全なコピーを作る初期化は実行困難になる。サブモジュール単位で分割すれば、全体を完全複製せずに構築できる。これは学習中の状態退避とは別の、開始時のメモリ障害を防ぐための機能である。

### 結果を誤読しやすい三つの点

第一に、論文の図1にある「32兆、約50倍」はメモリに収容して学習反復を実行できるモデル規模の比較であり、同じGPU数で50倍高速という意味ではない。図5の高処理率測定は20兆までで、三次元並列化に対して約40倍のモデル規模という別の比較になる。32兆の完全な事前学習を終了して精度を評価したという主張でもない。

第二に、1兆モデルで64から512 GPUへ増やした際の超線形な伸びは、ノード当たりバッチを固定して総バッチを増やす**弱スケーリング**である。固定総バッチの強スケーリングでGPU台数以上に速くなったという結果ではない。GPU演算器と同時にホストのPCIe・NVMe帯域とCPU更新計算能力も増えたことが主要な説明である。

第三に、20兆モデルの処理率低下はNVMeを使ったことだけに帰属しない。10兆と20兆はどちらもNVMe退避を使うが、20兆では活性チェックポイントを保持するCPUメモリの制約でGPU当たりのバッチを小さくせざるを得なかった。転送の隠蔽に必要な演算量が減った結果であり、単純な「SSDが遅いから」という説明では不十分である。

## 既存研究との違い

ZeROの主な発想は、データ並列プロセス間でモデル状態を重複させずに分割することである。ZeRO-Offloadは最適化器状態と勾配をCPUへ逃がすが、パラメータは依然としてGPUメモリに依存する。ZeRO-Infinityはパラメータも含めた全状態をCPU・NVMeへ広げ、各ノードの帯域を集約して転送を計算と重ねる。従来の容量削減だけではなく、階層メモリを分散システムとして利用する点が特徴である。

三次元並列化はテンソル並列、パイプライン並列、データ並列を組み合わせ、巨大なモデルをGPUへ分配する。ZeRO-Infinityはモデル並列化のために各層のコードを書き換える負担を減らし、必要な状態を都度集合して演算する。タイル分割は単一層がGPUへ収まらない問題を扱うため、モデルのレイヤーをGPU間へ恒常的に切り分けるテンソル並列とは役割が異なる。

後続のG10は実行グラフに基づいてGPU・CPU・SSDのどこへテンソルを配置するかを最適化し、Smart-Infinityはストレージ側での最適化器更新によりデータ移動をさらに減らす。これらと比べると、本研究の中心はZeRO分割を多ノードへ拡張し、集約I/O帯域を利用することである。いずれも階層メモリを扱うが、最適化の単位と前提ハードウェアは同じではない。

## 限界と運用上の条件

第一に、NVMe・CPU退避の費用はゼロではない。十分な先読み距離がなく、バッチが小さくて演算時間が短い場合はGPUがデータ到着を待つ。原著でも活性チェックポイントをCPUへ移すと小さな隠れ次元で処理率が最大約1.2倍低下する条件がある。CPU側の容量が不足するとバッチを小さくせざるを得ず、20兆モデルのようにGPU当たりの演算効率が落ちる。

第二に、各ノードに十分なCPUメモリと高速な局所NVMeがあり、PCIeやノード間ネットワークを同時利用できることを前提とする。共有ネットワークストレージを一箇所から読む構成では、論文と同じ集約帯域が得られるとは限らない。SSDの書込み耐久性、ストレージ競合、CPU更新計算の余力も実運用では確認が必要である。

第三に、実測はV100・DGX-2世代の密なGPT型Transformerと系列長1024を中心に行われた。より新しいGPUや長文脈モデル、疎な専門家モデルでは演算と転送の比率が変わる。最新GPUへそのまま34〜49 TFLOP/s/GPUという数値を当てはめることはできない。推論時の重みオフロードにそのまま適用することも、勾配・最適化器状態のない別の処理であるため不適切である。

第四に、32兆の規模はシステムの収容・反復可能性を示したもので、最終学習品質や数か月単位の運用費用を示したものではない。数十兆規模を実際に収束まで学習するには、モデル状態が収まることとは別に莫大な総演算量が必要である。さらに原著自身も将来のGPU演算性能が10倍、100倍へ増える場合は、それに見合う低速メモリ帯域とGPU間帯域の増強が必要と予測している。

## 実装と再現可能性

著者の公式実装はDeepSpeedにあり、パラメータと最適化器状態をCPUまたはNVMeへ退避するZeRO Stage 3系の機能として利用できる。ただし現在のDeepSpeedは論文発表時から更新されているため、当時の実測性能を厳密に再現するには、SC21当時の実装とハードウェア構成を区別する必要がある。著者らはSC21用のコード・実験成果物も別途公開している。公開実装があることと、論文の全測定が任意の環境で再現できることは同義ではない。
