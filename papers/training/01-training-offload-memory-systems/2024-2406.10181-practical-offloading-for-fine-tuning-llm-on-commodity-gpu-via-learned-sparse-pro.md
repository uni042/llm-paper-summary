# Practical Offloading for Fine-Tuning LLM on Commodity GPU via Learned Sparse Projectors

> 疎な低次元projected updateをCPUへオフロードし、layer-wise転送とGPU計算を重ねてconsumer GPUでLLM学習を可能にする手法。

## 概要
LSP-Offloadは、24 GB級のconsumer GPUでLLM fine-tuningを行うため、**full-size optimizer updateをCPUへ送る代わりに、低次元へ射影した小さなupdateだけをCPU側で扱う**方式である。

対象はdense Transformerのfine-tuningで、MoE expert offloadや推論ではない。GPUはforward/backwardを担当し、CPUは低次元化したgradient/updateとoptimizer相当の状態を保持する。

主眼は、CPU offload時のPCIe転送量を減らしながら、単純な固定低ランク法より広い更新方向を徐々にカバーすることにある。

## 手法のあらまし

### 1. `Learned Sparse Projector（LSP）`

各layerの更新をそのままCPUへ送るのではなく、疎なprojector `P, Q` を使って低次元subspaceへ写す。

projector自体を疎にすることで、projection計算と保持コストを抑える。更新量は概ね `O((m+n)r)` で、元のfull matrixより小さい。

ここでのprojectorはLoRAのように固定した低ランクadapterを学習するものではなく、**gradient/updateを低次元表現へ変換するための計算経路**である。

### 2. projectorを定期的に変える

単一の低ランクsubspaceだけを使い続けると、更新可能な方向が固定される。

LSPでは一定stepまたは更新量に応じてprojectorを切り替え、異なるsubspaceで得たupdateを累積する。これにより、低rankの通信量を保ちながら、時間とともにより広い更新方向をカバーする。

### 3. `layer-wise scheduling`

CPU offloadでは、

- GPU→CPU転送
- CPU側update
- CPU→GPU転送

を直列に行うとGPUが待つ。

LSP-Offloadはlayer単位に処理を分け、**あるlayerのCPU update中に別layerのGPU計算を進める**。

論文ではこの重ね合わせによって、CPU処理がそのままstepのcritical pathになることを避けている。

### 4. CPUへ何を置くか

| 場所 | 主な役割 |
|---|---|
| GPU | forward / backward、projection |
| CPU DRAM | projected gradient / update、optimizer相当の状態 |
| SSD | 主memory tierとしては使用しない |

したがって、ZeRO-Infinity型のSSD offloadとは異なる。

### 5. `rank` と projector更新頻度がquality-costを決める

rankを大きくすると更新表現は豊かになるが、通信量と計算量も増える。projectorを頻繁に変えるとsubspace coverageは広がる一方、projector更新のoverheadが増える。

このため、VRAM容量だけでなくqualityとthroughputの両方で設定を選ぶ必要がある。

## 評価

### まず見るところ
- **結論:** full optimizerをGPUに載せず、projected updateだけCPUへ逃がしてlayer-wiseに重ねると、4〜24GB級GPUでもLLM fine-tuningを現実的にできる。
- **学習速度:** ZeRO-Offloadより同一PPL/epoch到達が大幅に早く、代表条件では約2倍。
- **品質:** full updateと厳密同一ではないが、GLUE/HumanEvalではZeROやLoRA/GaLoreと同等以上。
- **I/O:** CPU DRAM offload。SSD/NVMeは主tierではない。
- **注意点:** これはtraining結果であり、decode throughputの高速化ではない。

| Model | LSP | ZeRO | LoRA | GaLore |
|---|---:|---:|---:|---:|
| DeepSeek-Coder 1.3B | 45.6 | 45.5 | 39.3 | 36.4 |
| DeepSeek-Coder 6.7B | 66.4（15h） | 64.8（15h） / 66.7（30h） | — | — |

LSPは速度を上げても、評価範囲ではcode生成品質を大きく失っていない。

### Schedulingの寄与

| 項目 | 結果 |
|---|---:|
| layer-wise scheduling単独 | ZeRO比throughput +18% |
| iteration latency | 約50%削減 |
| native GPU比 slowdown | rank設定により約10.6〜16.7% |

### 制約

- sparse projection kernelの圧縮・展開がボトルネックになり得る
- CPU DRAM容量とPCIe帯域に依存
- rankやprojector更新頻度の調整が必要
- MoE expertやSSD offloadへ直接一般化した評価ではない
