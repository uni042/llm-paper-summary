# Practical Offloading for Fine-Tuning LLM on Commodity GPU via Learned Sparse Projectors

> full-size gradient / optimizer updateをCPUへ送る代わりに、小さい低次元表現へ圧縮して転送し、その圧縮方向を学習中に切り替えることで、PCIe trafficを減らしながらconsumer GPUでLLM fine-tuningする方式。

## 概要
LSP-Offloadは、24 GB級のconsumer GPUでLLM fine-tuningを行うため、**各layerの大きなgradient / update matrixをそのままCPUへ送らず、より小さい低次元表現へ変換してからoffloadする**方式である。

対象はdense Transformerのfine-tuningで、MoE expert offloadや推論ではない。GPUはforward/backwardと圧縮変換を担当し、CPUは低次元化したgradient/updateとoptimizer相当の状態を保持する。

主眼は、CPU offload時のPCIe転送量を減らしながら、単純に「常に同じ低rank方向だけ更新する」方式より多様な更新方向を時間とともにカバーすることにある。

## 手法のあらまし

### 1. `Learned Sparse Projector（LSP）`：大きなupdateを小さい座標へ写す

各layerの更新をそのままCPUへ送るのではなく、疎なprojector `P, Q` を使って低次元表現へ写す。

ここでいう **projector** は、元の大きなmatrixを「少数の代表方向だけで表した小さいmatrix」へ変換する写像である。LoRAのようにmodelへ固定adapterを追加するのではなく、**gradient/updateをCPUへ運びやすい小さい表現へ変換するための計算経路**として使う。

projector自体をsparse、つまり0要素が多い構造にすることで、projection計算と保持コストも抑える。更新量は概ね `O((m+n)r)` となり、元の `m×n` full matrixより小さい。

### 2. `rank` は「小さい表現に何方向残すか」

論文でいうrank `r` は、元の更新matrixを低次元化したときに**何本の更新方向を残すか**を表す。

- rank小 → 転送量・CPU state・計算量は小さいが、1回に表現できる更新方向が少ない
- rank大 → 元のgradientをより豊かに表現できるが、通信・計算量が増える

したがってrankは単なるmodel size parameterではなく、**qualityとoffload costの直接的なtrade-off knob**になる。

### 3. 同じ低次元空間へ固定せず、projectorを定期的に変える

単一の低ランク表現だけを使い続けると、学習中ずっと同じ少数方向しか更新できない。

LSPでは一定stepまたは更新量に応じてprojectorを切り替え、別の方向集合へgradientを写す。

論文の **subspace** は、この「今のprojectorで表現できる更新方向の集合」を指す。projectorを時間とともに変えることで、1 stepあたりは低rankの小さい通信量を保ちながら、学習全体ではより広い方向を更新できる。

### 4. LayerごとにCPU updateとGPU計算を重ねる

CPU offloadでは、

- GPU→CPU転送
- CPU側update
- CPU→GPU転送

を全layerについて直列に行うとGPUが待つ。

LSP-Offloadはlayer単位に処理を分け、**あるlayerの低次元updateをCPUで処理している間に、GPUでは別layerのforward/backwardを進める**。

論文のlayer-wise schedulingは、このようにlayerごとのCPU処理とGPU処理をずらして同時に走らせる仕組みである。

### 5. CPUへ何を置くか

| 場所 | 主な役割 |
|---|---|
| GPU | forward / backward、gradientの低次元化 |
| CPU DRAM | 低次元gradient / update、optimizer相当の状態 |
| SSD | 主memory tierとしては使用しない |

したがって、ZeRO-Infinity型のSSD offloadとは異なる。

## 評価

### まず見るところ
- **結論:** full optimizerをGPUに載せず、updateを低次元化してCPUへ逃がし、layerごとにCPU/GPU処理を重ねると、4〜24GB級GPUでもLLM fine-tuningを現実的にできる。
- **学習速度:** ZeRO-Offloadより同一PPL/epoch到達が大幅に早く、代表条件では約2倍。
- **品質:** full updateと厳密同一ではないが、GLUE/HumanEvalではZeROやLoRA/GaLoreと同等以上。
- **I/O:** CPU DRAM offload。SSD/NVMeは主tierではない。
- **注意点:** これはtraining結果であり、decode throughputの高速化ではない。

120時間固定ではLSPが約1.97倍多くepochを進めた。

### HumanEval

| Model | LSP | ZeRO | LoRA | GaLore |
|---|---:|---:|---:|---:|
| DeepSeek-Coder 1.3B | 45.6 | 45.5 | 39.3 | 36.4 |
| DeepSeek-Coder 6.7B | 66.4（15h） | 64.8（15h） / 66.7（30h） | — | — |

LSPは速度を上げても、評価範囲ではcode生成品質を大きく失っていない。

### Schedulingの寄与

| 項目 | 結果 |
|---|---:|
| layer-wise scheduling単独 | ZeRO比throughput +18% |
| iteration latency | 約50%削減 |
| native GPU比 slowdown | rank設定により約10.6〜16.7% |

### 制約

- sparse projection kernelの圧縮・展開がボトルネックになり得る
- CPU DRAM容量とPCIe帯域に依存
- rankやprojector更新頻度の調整が必要
- MoE expertやSSD offloadへ直接一般化した評価ではない
