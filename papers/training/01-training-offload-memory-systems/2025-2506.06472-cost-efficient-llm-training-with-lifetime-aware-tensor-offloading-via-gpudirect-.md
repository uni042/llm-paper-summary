# Teraio：テンソルの非活動期間を利用したSSD退避型大規模言語モデル学習

## 概要

大規模言語モデルの学習では、重み、勾配、最適化器状態、活性化がGPUの高帯域メモリを占有する。しかし、ある時点のGPU演算器が実際に使うテンソルは一部に限られ、多くのデータは次の利用まで長く待機する。従来のSSD退避方式はモデルの層やデータ種類を単位に大きな転送を行うことが多く、必要になる直前の読込が遅れてGPUを停止させたり、まだ使わないデータを早くGPUへ戻しすぎたりする。

Teraioは、**テンソルごとの活動・非活動期間を測定し、GPUメモリの容量制約とSSD帯域の両方を満たすように退避・先読み時刻を決める**学習システムである。最初の数回の学習反復でテンソルの大きさ、使用される演算、演算の所要時間を計測する。繰り返される学習の実行順序が安定していることを利用して、次の反復以降でどのテンソルがいつ不要になり、いつ必要になるかを予測する。

計画器は、長く使わない大きなテンソルを優先してSSDへ移し、次の利用時刻に間に合うよう先読みする。SSD帯域が飽和するときはCPUメモリも利用し、GPUが次の演算を始めるために必要な転送を優先する。実行器はGPUとSSDの直接入出力（GPUDirect Storage）を使い、ホストCPUを介した余分なコピーを減らす。対象は推論のKVキャッシュではなく、**学習中のテンソル全般**である。

論文の観察では、ある時点で活動中のテンソルは、評価したモデルでGPUメモリ容量の平均1.7%、最大でも14%未満だった。大きなテンソルの相当数は長い非活動期間を持ち、SSDへの退避をGPU演算と重ねる余地がある。H100 NVL 2基とSSD 8台の実機では、ZeRO-OffloadやZeRO-Infinityに対して平均1.47倍の学習スループットを報告する。無限GPUメモリを仮定した理想構成の80.7%という別の指標も示すが、これは比較対象のZeROに対する1.47倍と分母が異なる。

## 背景：テンソルの寿命とメモリ階層

### 活動中と非活動中の区別

あるGPUカーネルが入力または出力として利用するテンソルは、そのカーネルの実行中にGPUメモリへ存在する必要がある。一方、演算が終わってから次の演算に使われるまでの間、そのテンソルはGPUメモリに置かれていても演算には寄与しない。論文はこの時間を非活動期間と呼ぶ。たとえば順伝播で生成した活性化は逆伝播まで使われないことがあり、モデルの層が深く計算時間が長いほど、非活動期間が長くなる。

テンソルの活動期間は種類だけでは決まらない。重みや最適化器状態は反復をまたいで生存し、活性化や勾配は途中で生成・解放される。あるテンソルがGPUメモリに確保されている時間と、GPUが実際に参照する時間を混同すると、退避してよい区間を見逃す。TeraioはPyTorchの演算呼出しと通信・最適化器の操作を追跡し、テンソル識別子ごとに活動区間を求める。

論文の特性分析はLlama3-8B、Llama3-70B、GPT2-40B、T5-11Bを対象とし、2基のH100と2段のパイプライン並列を用いる。評価した全モデルで、活動中テンソルが必要とする容量はGPUメモリ容量の平均1.7%と小さい。一方、10MB～1GBの大きなテンソルが多く、これらの40%超は10⁴マイクロ秒、すなわち10ミリ秒を超える非活動期間を持つ。非活動期間が十分長ければ、SSDへの書込と次回利用前の読込をその間に収められる可能性がある。

### 容量だけでなく帯域が重要になる理由

SSDはGPUメモリより大容量で安価だが、帯域と遅延は不利である。全ての非活動テンソルをSSDへ追い出せばGPUメモリ容量は空くものの、次に使う時刻までに読戻せなければ演算器が待つ。逆に、すぐ使う小さなテンソルまで往復させると、節約できるメモリ量に比べて入出力費が大きくなる。退避先を決めるには、テンソルの大きさ、次回使用までの時間、SSDの空き帯域、GPUメモリが不足する時刻を同時に考慮する必要がある。

原著の屋根線モデルによる分析では、GPUごとに双方向32～48GB/秒程度の移動帯域があれば、評価対象の学習で理想に近い性能を得られると見積もる。ただしこれはカーネル時間を測定値で固定し、指定帯域での転送待ちをモデル化した**事前の性能推定**である。実機の2基H100評価で、各GPUに32～48GB/秒の実効帯域が常に得られたという意味ではない。

## 手法

### 1. PyTorchの演算からテンソル寿命を計測する

Teraioは、学習開始後の数反復でテンソルの大きさ、使用時刻、GPUカーネルの所要時間を記録する。全てのPyTorch演算子を個別に手書き改変するのではなく、演算子を自動生成する機構へ計測処理を挿入する。これにより、各演算子の入力・出力テンソルを活動中と認識できる。GPU間通信で使用するテンソルと、最適化器の状態確認で明示的に参照するテンソルについては、別途活動状態を記録する。

中間テンソルは生成から解放までの複数の活動区間の間を非活動期間として計算する。重みや最適化器状態のように反復をまたいで保持するテンソルでは、前反復の最終使用から次反復の最初の使用までを観察する必要がある。学習の実行グラフが反復間でほぼ同じなら、最初の数反復の観察を以後の反復の計画へ再利用できる。

この方法は静的な層単位の退避より細かいが、実行順序が大きく変化するモデルでは予測精度が低下し得る。可変長系列、条件分岐、動的ルーティングなどによって活動区間が変わる場合、計測した寿命をそのまま使うと先読みが遅れる可能性がある。論文の評価は、反復ごとの実行パターンが比較的安定した大規模言語モデル学習を対象としている。

### 2. 帯域を考慮して退避・先読みを計画する

計画器の入力は、テンソル識別子と容量、非活動区間、各GPUカーネルの実行時間、各時点のGPUメモリ要求量、利用できる移動帯域である。まずGPUメモリ容量を超える時刻を探し、そこを緩和できるテンソルの非活動区間を候補にする。単純に非活動区間の開始直後へ書込を置くのではなく、既に予約した入出力による帯域占有を考慮して、退避が完了する最も早い時刻と、読戻しを開始すべき最も遅い時刻を求める。

退避完了時刻が先読み開始時刻より前にあるときだけ、テンソルをGPUから外しておける区間が存在する。計画器はその区間内でGPUメモリの必要量が物理容量を超える時間を抽出し、テンソル容量にその時間の重みを掛けてメモリ圧迫の軽減効果を見積もる。原著のアルゴリズム1では、容量sと圧迫区間に含まれるカーネル時間の総和から便益を計算し、転送費用に対する比が大きい候補を順に採用する。

候補を一つ採用すると、退避と先読みの命令を計画へ追加し、その間のGPUメモリ要求量を減らすとともに、SSDの利用予定帯域を更新する。これをピークメモリ要求量がGPU容量以下になるまで繰り返す。候補を選ぶたびに帯域予約を更新するため、同じSSD帯域を複数テンソルが重複して使えると誤って見積もることを避ける。

### 3. SSDとCPUメモリを使い分ける

Teraioは大容量かつ低価格のSSDを基本の退避先として優先する。SSDへの書込・読込帯域が既存の計画で飽和した場合には、CPUメモリへ退避する選択肢を使う。CPUメモリはSSDより高速だが容量単価が高く、利用可能な容量にも上限があるため、利用者が設定した上限を超えて使わない。したがって「全テンソルをSSDへ送る」方式でも「常にCPUメモリが最速だから優先する」方式でもない。

計画器はSSDのみを使う構成と、SSDとCPUメモリを併用する構成の両方を扱える。SSDだけでも退避が間に合う短いモデルや小さなバッチでは、追加のCPUメモリを用意せずにGPU容量を拡張できる。モデルが大きく、SSD帯域が不足する場合はCPUメモリの追加帯域が役立つ。GPUの容量不足と転送帯域不足を区別して処理する点が重要である。

### 4. 先読みの期限と緊急転送

計画どおりに転送を重ねても、GPUが次に実行するカーネルに必要なテンソルがまだ戻っていない場合は待機が発生する。Teraioは、このようなカーネル開始を直接阻む転送を緊急扱いにし、他の非緊急転送より優先する。これにより、将来のメモリ圧迫を緩和するための退避と、直後の演算を進めるための先読みが競合した場合に、後者を優先できる。

ただし、緊急扱いにしても物理的なSSD帯域が増えるわけではない。容量制約を満たす候補がない、または必要な転送が完了しない場合、GPUカーネルは停止して待つ。原著はこの待機を例外ではなく、帯域・容量の制約下で起こり得る状態として明示している。したがって「SSD退避を完全に隠蔽する」という絶対的な保証ではなく、非活動期間と帯域の余裕を利用して待機を減らす方式と理解すべきである。

### 5. GPUとSSDの直接転送を実行する

実行時には、PyTorch内のハッシュ表でテンソル識別子から現在の所在とアドレスを引く。計画器が生成した退避・先読み命令に従い、GPUメモリ、CPUメモリ、SSDの間でテンソルを移動する。GPUとSSDの転送にはGPUDirect Storageを利用し、通常のSSD→CPUメモリ→GPUという二段階コピーを避ける。これによりホストCPUのコピー処理やメモリ帯域の負担を減らし、複数GPUと複数SSDで転送を並行させる。

原著は、各GPUにPCIe Gen5スイッチ経由で複数SSDを接続する構成を想定し、ホストCPU経由の転送が多GPU時の拡張性を阻むと説明する。一方、GPUDirect Storageを使うためには対応するGPU、SSD、ドライバ、ファイルシステム、PCIe経路が必要であり、通常のGPUメモリコピーと同じ汎用性ではない。CPUメモリとの転送も必要に応じて併用するため、CPUを全く使わないという意味でもない。

## 評価

### 実機と比較条件

| 項目 | 一次論文の条件 |
|---|---|
| GPU | H100 NVL 94GBを2基 |
| CPU | AMD EPYC 9334を2基 |
| CPUメモリ | DDR5を合計1.5TB搭載 |
| SSD | Samsung 990 PRO 2TBを8台、読込公称6.7GB/秒・書込6.5GB/秒 |
| GPUとSSD | PCIe Gen5、GPUごとにSSD 4台のRAID0を論理割当 |
| 実測転送帯域 | 各GPUへのテンソル移動は約16GB/秒の帯域 |
| ソフトウェア | PyTorch 2.5.0、TorchTitan |
| 学習モデル | Llama3-8B、Llama3-70B、Granite-code-base-8B |
| データと入力 | C4、バッチ16～128、系列長1024～8192 |
| 精度 | 比較の公平性のため全条件で単精度学習 |

比較対象はZeRO-Offload、ZeRO-Infinity、およびGPUメモリが無限大であると仮定した理想方式である。Teraio-SSDはSSDだけを退避先に使い、Teraio-MixedはSSDとCPUメモリを併用する。後者とZeRO-Infinityでは、比較の公平性のため利用可能なCPUメモリ量を揃えている。ZeRO側はテンソル並列を用い、CPU最適化器の費用を薄めるためにマイクロバッチを使う。

論文は混合精度学習ではなく単精度学習で比較した。TorchTitanとZeROの混合精度表現では、GPUに置く重み・勾配・最適化器状態のビット幅が異なり、メモリ要求量の差が比較を歪めるためである。活性化の再計算も、ZeROの速度を低下させることから比較では無効化している。これらの設定は、通常の最新LLM学習の最適化を全て有効にした場合の相対速度をそのまま示すものではない。

### 学習スループット

| 条件 | 結果 | 読み方 |
|---|---:|---|
| Llama系・Granite系の評価平均 | ZeRO系退避方式比1.47倍 | 複数モデル・設定の平均、全条件で同じ倍率ではない |
| 全モデルをまとめた理想比 | 無限GPUメモリ仮定の80.7% | 理想値の分母はZeROではない |
| ZeRO系に対する最大速度比 | 最大1.59倍 | 一部のモデル・入力条件での最大値 |
| Llama3-70B、ZeRO-Infinity | 理想比43.0% | 粗粒度退避と帯域制約で低い |
| Llama3-70B、Teraio-Mixed | 理想比59.7% | ZeRO-Infinity比1.33倍 |
| Llama3-8B、GPU容量を拡張してバッチ増 | スループット9%改善 | GPU容量が元々足りる場合でもバッチ増加に価値 |

Llama3-8BとGranite 8BではZeRO-Offloadの理想比がそれぞれ65.9%、65.5%と報告される。Teraioは非活動期間に合わせた転送で待機を減らし、Llama3-8BではSSDだけの構成でも理想に近い性能となる。一方、GraniteではSSDのみの構成はZeRO系に近い性能にとどまり、CPUメモリを併用する構成の方が理想に近づく。モデルのテンソル活動パターンが異なるため、SSDのみで常に十分とは限らない。

Llama3-70Bでは、ZeRO-OffloadはCPUメモリ容量不足で学習できない。ZeRO-InfinityはSSDを利用するため学習できるが、粗粒度の転送で帯域を十分に利用できず、理想比43.0%にとどまる。Teraio-Mixedでも理想比59.7%であり、無限メモリ相当の速度には達しない。これは大きなモデルでは転送帯域の不足がなお重要な律速になることを示す。

### 系列長とバッチサイズの影響

バッチサイズを増やしても、マイクロバッチの大きさを一定にして分割すれば、単一GPUが同時に保持するテンソル容量が比例して増えるとは限らない。したがって、評価ではバッチ増加が主に学習スループットへ影響する。一方、系列長を伸ばすと活性化が大きくなり、GPUメモリの必要量も増える。原著では系列長が3072を超える一部条件でZeRO-InfinityがGPUメモリ不足となるが、Teraioは非活動テンソルをより細かく退避することで対象の全設定を学習できた。

この結果は、最適化器状態や重みだけを退避する方式では活性化のピークに対処しきれないことを示す。Teraioがテンソルの種類に縛られず、活動区間を見て候補を選ぶ設計は、長文脈学習での容量不足にも有効である。ただし、系列長を伸ばせば転送量とGPU計算量の双方が変わるため、全設定で速度が理想値へ近づくという意味ではない。

### SSD台数とCPUメモリ容量

図9では、GPUごとに使うSSD台数とCPUメモリの上限を変えて学習速度を測る。Llama3-8BはSSD 2台とCPUメモリ64GBでも理想に近い速度を達成する。Llama3-70BではSSD 2台・CPUメモリ512GBの構成が、SSD 4台・CPUメモリ1024GBの構成の73.1%のスループットを維持した。つまり、装置を半分に減らしても速度が半分になるとは限らず、テンソル寿命に応じた計画によって限られた帯域を使える。

ZeRO-Infinityは比較した条件でLlama3-8Bに170GB、Llama3-70Bに770GBのCPUメモリを要したと原著は述べる。TeraioはGPUのメモリ圧迫を直接緩和できる候補を選び、CPUメモリの必要量を抑える。もっとも、実験機には1.5TBのCPUメモリが搭載されており、図9の容量は利用上限を変えた測定である。搭載物理メモリ量と実際の退避に使うメモリ量を区別する必要がある。

### 費用対効果

論文の表2はLlama3-70Bの学習に必要な装置の価格を比較する。H100を2基搭載したサーバーは約84,139.9米ドル、CPUメモリを1TBに増やしたサーバーは約91,047.9米ドル、SSD 8台の合計は約1,360米ドルとしている。全テンソルをGPUメモリに置くための純GPU構成は、H100を8基搭載するサーバー2台で約499,591.4米ドルと見積もる。

この前提では、Teraio-SSDは純GPU構成に対して装置購入費を約5.88分の1、Teraio-Mixedは約5.41分の1へ抑える。ここでの5.88倍・5.41倍は**購入費の比較**であり、学習時間が5.88倍短いという意味ではない。ZeRO-OffloadおよびZeRO-Infinityに対する費用効率は、それぞれ約1.45倍、1.47倍と報告されるが、価格と性能を組み合わせた指標である。運用時の電力、故障、SSD書換え寿命、クラウド利用料金などを全て含む総保有費用の実測ではない。

## 既存研究との差

ZeRO-Offloadは主としてGPUとCPUメモリの間で学習状態を移し、ZeRO-InfinityはSSDまでメモリ階層を拡張する。しかし、層単位の転送では、GPUが次に使うテンソルの時刻とSSD帯域を細かく反映できない場合がある。Teraioはテンソル識別子ごとに活動期間を計測し、容量不足が生じる時間を緩和する便益に応じて退避候補を選ぶ点が異なる。

Smart-Infinityは計算機能付きSSD内で最適化器更新を実行してホストとの状態転送を減らす。一方、Teraioは通常のPCIe接続SSDを使い、更新演算をSSDへ移すのではなく、**どのテンソルをいつ移すか**を最適化する。両者はSSDを使う学習という点で近いが、必要なハードウェアと通信削減の仕組みが異なる。SSDTrainなどの活性化退避方式とも、活性化だけでなく重み・勾配・最適化器状態を活動期間で扱う点が違う。

## 限界と適用範囲

第一に、テンソル活動パターンが学習反復間で安定していることを前提とする。可変長入力、動的な演算分岐、学習途中で変わるモデル構造、専門家ルーティングによる負荷変動などでは、最初の数反復の計測が後続の実行を正確に表さない可能性がある。計画器が予測を外した場合、先読みの遅延やGPU待機が発生し得る。

第二に、GPUとSSDの直接入出力を利用できる構成が必要である。論文の実機はH100 NVL、PCIe Gen5、複数の高速NVMe SSDを備える。GPUからSSDへ直接アクセスできない場合、CPU経由のコピーが増え、評価と同じ帯域・速度は期待できない。GPUごとに複数SSDを使える物理スロットやPCIeトポロジーも制約となる。

第三に、退避は無償ではない。SSD帯域が飽和すればCPUメモリの追加帯域が必要になり、それも不足すればGPU演算が待つ。Llama3-70BのTeraio-Mixedでも理想比59.7%であり、転送待ちを完全には隠せていない。容量制約と帯域制約を同時に満たせない場合の待機が残ることは、アルゴリズム1の設計にも明記されている。

第四に、比較は単精度学習で行い、活性化再計算を無効化している。現在の大規模学習で一般的な混合精度、再計算、低精度最適化器、異なる並列戦略を組み合わせた場合の相対性能は別途評価が必要である。比較対象の最適な実装や世代が変われば、平均1.47倍という値も変わる可能性がある。

第五に、SSDの書換え寿命、故障時の回復、複数利用者によるI/O競合、GPU・SSD間のセキュリティや運用管理、電力費を含む長期的な総保有費用は主評価の対象外である。費用対効果の表は特定時点の装置購入価格に依存し、現在の価格で再計算しなければならない。さらに、本論文は学習向けであり、推論時のKVキャッシュ管理へそのまま適用した実測結果はない。

## 再監査結果

旧原稿は活動期間に基づく退避という着想と主要速度比を説明していたが、原著の帯域制約を組み込んだ候補選択、容量圧迫区間の便益計算、緊急先読み、GPUDirect Storageの実機構成、CPUメモリ併用の条件、単精度での公平比較、費用対効果の分母などを十分に詳述していなかった。今回の修復では、特性分析、アルゴリズム1、実機評価の図7～9、費用表を一次資料に照合し、最大値と平均値、理想構成とZeRO比較、購入費と速度を分けて説明した。

本研究は階層メモリ・SSD退避を用いた大規模言語モデル**学習**のシステム研究として収録する。推論のメモリ退避に転用する場合は、反復ごとのテンソル寿命と推論リクエストの動的なキャッシュ寿命が異なるため、別の予測・配置機構が必要となる。
