# Cost-Efficient LLM Training with Lifetime-Aware Tensor Offloading via GPUDirect Storage

> tensorの生存期間を基にNVMeオフロード対象とI/O時機を決め、GPUDirect StorageでLLM学習の転送待ちを抑える方式。

## 概要
TERAIOは、LLM training中のtensorを「種類」ではなく、**次に使われるまでどれだけ長く空くか**でoffloadする方式である。

weight、gradient、optimizer state、activationのどれであっても、長時間inactiveならNVMeへ逃がす候補になる。逆に、すぐ再利用するtensorはGPUに残す。

layer単位の固定offloadより細かく、tensor lifetimeとI/O帯域を見て、GDSでGPU↔NVMe転送を計算へ隠すことが主眼である。

## 手法のあらまし

### 1. `tensor lifetime`をprofileする

最初の数iterationで、各tensorについて、

- サイズ
- どのkernelで使われるか
- 次に使われるまでのinactive interval

を記録する。

ここでいうlifetimeはtensorの生成から削除までではなく、**GPU上に置いておく必要がある時間帯と、置かなくてもよい空白時間**を意味する。

### 2. `active window`

各tensorの使用時刻を並べると、GPU上に必ず存在しなければならない短い区間ができる。

TERAIOはこの区間をactive windowとして扱い、それ以外の長いinactive部分をoffload可能時間とみなす。

### 3. benefit / costでoffload候補を選ぶ

plannerは候補tensorについて、

- 解放できるGPU memory
- そのmemoryが必要になるcritical区間の長さ
- 往復I/O時間

を評価する。

概念的には、**「何GB空けられるか × どれだけ長く効くか」÷「I/O cost」** が高いtensorから選ぶ。

### 4. SSD優先、帯域飽和時はCPU DRAMへfallback

基本tierはNVMe SSDだが、SSD帯域が埋まるとCPU DRAMへ逃がす。

したがってmemory hierarchyは、

`GPU HBM → NVMe` を主経路にしつつ、必要に応じて `GPU HBM → CPU DRAM` も使う。

### 5. `GPUDirect Storage（GDS）`

GPUとNVMe間はGDSを使い、CPU stagingを避ける。

これによりCPU DRAM bandwidthを使わず、複数SSDの帯域を直接GPUへ集約する。

### 6. prefetch deadline

offloadしたtensorは、次に使うkernelの前までにGPUへ戻す必要がある。

plannerはprefetch開始時刻を逆算し、deadlineに間に合わない場合はそのtensorをoffload対象から外すか、最終的にはkernel stallを許容する。

## 評価

### まず見るところ
- **結論:** tensorの空き時間を利用してNVMeへ逃がすと、layer単位offloadよりI/Oを計算へ隠しやすい。
- **学習速度:** ZeRO系offloadより平均約1.47倍、理想HBM-onlyの約8割まで戻す条件がある。
- **容量・コスト:** 少ないHBMで大きいmodel/batchを動かし、SSD追加でGPU/HBM増設を代替する狙い。
- **I/O:** GDS＋PCIe Gen5＋複数NVMe実機。
- **注意点:** SSD本数と帯域への依存が大きく、最終task精度や長期収束は主評価外。

### 実験環境

| 項目 | 条件 |
|---|---|
| GPU | 2×H100 NVL 94GB |

| Framework | PyTorch 2.5 / TorchTitan |

### Throughput

| 指標 | 結果 |
|---|---:|
| ZeRO系offload比 | 平均1.47倍 |
| Ideal HBM-only比 | 平均80.7% |
| Cost efficiency | 1.45倍 |

### Llama 70B

| System | Ideal比 |
|---|---:|
| ZeRO-Infinity | 43.0% |
| TERAIO Mixed | 59.7% |

TERAIOは改善するが、大規模modelではNVMe bandwidthが依然ボトルネックになる。

### SSD帯域の目安

論文の解析では、GPUあたり32〜48GB/s級の双方向SSD帯域があれば、HBM-onlyにかなり近づけるとする。

そのため複数SSDの帯域集約が前提になる。

### Cost

Pure-GPU構成に対し、SSD/Mixed構成はhardware costを大幅に下げる試算を示す。ただしこれは論文時点のGPU/SSD価格と大規模training構成に依存する。

### 制約

- 2 GPU＋多数SSDという特殊構成
- GDS/PCIe topology依存
- SSD帯域が不足するとstallが露出
- 長期収束・最終task accuracyは主評価外
- consumer SSD 1台のoffload性能へ直接外挿できない
