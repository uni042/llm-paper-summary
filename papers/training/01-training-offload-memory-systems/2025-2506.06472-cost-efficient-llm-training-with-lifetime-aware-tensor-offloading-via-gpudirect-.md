# Cost-Efficient LLM Training with Lifetime-Aware Tensor Offloading via GPUDirect Storage

> テンソルごとの次回利用までの空き時間を測り、長く不要な重み・勾配・活性値をNVMe SSDへ退避し、先読みをGPU計算に重ねて固定的な層単位方式のI/O待ちを減らす学習方式。

## 概要

TERAIOは、LLM学習中のテンソルを「重みだからCPUへ」「活性値だからSSDへ」のように種類だけで決め打ちせず、**そのテンソルが次に使われるまでGPU上で不要になる時間**を見て退避先を決める方式である。

重み（weight）、勾配（gradient）、最適化状態（optimizer state）、活性値（activation）のどれであっても、長時間使われないならNVMe SSDへ逃がす候補になる。逆に、すぐ再利用するテンソルはGPUに残す。

論文の観察では、1回の学習反復（iteration）中に確保されているGPUメモリのうち、実際にその瞬間必要な「活動中テンソル」は平均1.7%程度にすぎない。つまり、多くのデータはGPUメモリを占有しているものの、かなり長い時間使われていない。

TERAIOはこの空白時間を使い、GPUとSSDの間の入出力をGPU計算と同時進行させる。単純な層単位オフロードより細かく、**テンソルごとの使用時刻とSSD帯域を基に、退避と先読みの予定表を事前に作る**ことが主眼である。

H100 NVL 2基とNVMe 8台の実機評価では、ZeRO-Offload／ZeRO-Infinity比の学習スループットが平均1.47倍、無制限GPUメモリ想定の理想スループット比が80.7%だった。

## 手法のあらまし

### 1. 最初の数回の実行からテンソルの使用時刻を記録する

最初の数反復を観測し、各テンソルについて、

- サイズ
- どのGPUカーネル（kernel）で使われるか
- いつ使われるか
- 次の使用までどれだけ時間が空くか

を記録する。

ここで論文がいう**テンソル寿命（tensor lifetime）**は、単純な「生成されてから削除されるまで」ではない。

より重要なのは、**GPU上に置いておく必要がある活動期間と、GPUから外しても問題ない非活動期間**である。

たとえば順伝播で使った後、かなり後の逆伝播まで使わないテンソルなら、その間はSSDへ退避できる。

### 2. GPU上に必ず必要な区間を「活動窓（active window）」として扱う

テンソルの使用時刻を並べると、「この時間帯だけはGPUに存在しなければならない」という区間ができる。

TERAIOはこれを**活動窓（active window）**と呼ぶ。

活動窓の外側が十分長ければ、

1. 使用後にSSDへ書き出す
2. GPUメモリを別用途へ使う
3. 次の活動窓が始まる前にSSDから先読みする

という処理が可能になる。

つまり「テンソルをSSDへ置けるか」だけでなく、**SSDへ往復する時間を確保できるか**まで見る。

### 3. 空けられるGPUメモリと入出力コストを比べて候補を選ぶ

退避すれば大きなGPUメモリを長時間空けられるテンソルほど価値が高い。一方、巨大なテンソルを短時間だけ退避しても、SSD往復に時間がかかるだけで得をしない。

計画器（planner）は概念的に、

- 何GBのGPUメモリを空けられるか
- その空きがどれだけ長く続くか
- SSDへの書き出し＋読み戻しにどれだけ時間がかかるか

を比べ、**メモリ解放効果が大きく、入出力を隠しやすいテンソルから退避する**。

### 4. 基本はSSDへ逃がし、SSD帯域が足りなければCPU DRAMも使う

主な退避先はNVMe SSDだが、SSD側の転送予定が混雑し、必要時刻までに戻せない場合はCPU DRAMも利用する。

したがって実際には、

- GPU HBM ↔ NVMe SSD
- GPU HBM ↔ CPU DRAM

という複数の経路を使う。

CPU DRAMはSSDより容量が小さい一方で高速なので、SSD帯域だけでは締め切りに間に合わないテンソルの受け皿として使える。

### 5. GPUダイレクトストレージ（GPUDirect Storage; GDS）でSSDとGPUを直接つなぐ

TERAIOはGPUとNVMe SSDの転送に**GPUダイレクトストレージ（GPUDirect Storage; GDS）**を使う。

通常のSSD入出力では、

`SSD → CPU DRAM → GPU`

のようにCPUメモリを中継することが多い。

GDSでは、

`SSD ↔ GPU`

の直接転送を使い、CPU側の中継コピーやCPUメモリ帯域の消費を減らす。

論文は複数SSDを並列に使い、その合計帯域をGPUへ集約する構成を評価している。

### 6. 「いつまでに読み戻す必要があるか」から先読み開始時刻を逆算する

SSDへ逃がしたテンソルは、次に使うGPUカーネルが始まる前までに戻っていなければならない。

この時刻を**先読み締め切り（prefetch deadline）**と考える。

たとえば読み戻しに20msかかり、次の使用まで50msあるなら、少なくとも使用20ms前には読み戻しを開始する必要がある。

TERAIOは実測したSSD帯域とテンソルサイズから転送時間を見積もり、締め切りに間に合うよう先読み開始時刻を決める。

間に合わないと判断した場合は、

- そのテンソルをそもそもSSDへ退避しない
- CPU DRAMへ置く
- やむを得なければGPU計算を待たせる

といった選択になる。

## 評価

### まず見るところ

- **結論:** テンソルが使われない時間を利用してNVMeへ退避すると、固定的な層単位オフロードよりSSD入出力をGPU計算へ隠しやすい。
- **学習速度:** ZeRO系オフロード比で平均約1.47倍。無制限GPUメモリを仮定した理想構成の平均80.7%まで処理性能を戻す。
- **容量・コスト:** 高価なHBMを増やす代わりに比較的安価なNVMe SSDを容量拡張へ使う狙い。
- **入出力:** GDS＋PCIe Gen5＋複数NVMe SSDの実機評価。
- **注意点:** SSD本数と合計帯域への依存が大きく、一般的なSSD 1台のPCへ同じ性能を期待できる結果ではない。

TERAIOでも大規模モデルではNVMe帯域が完全には隠れず、理想GPUメモリ構成との差が残る。

### SSD帯域の目安

論文の解析では、GPUあたり32〜48GB/s級の双方向SSD帯域があれば、HBM-only性能へかなり近づけるとする。

これはSSD 1台の帯域ではなく、複数SSDを並列利用した**合計入出力帯域**を想定した値である。

### コスト評価

GPU/HBMだけで全状態を保持する構成に対し、SSDやCPU DRAMを組み合わせる構成はハードウェアコストを下げられると試算する。

ただしこの結果は論文時点のGPU・SSD価格と、大規模学習サーバーの構成を前提とする。

### 制約

- 2 GPU＋多数SSDという特殊な実験構成
- GDSとPCIeトポロジ（topology）に強く依存する
- SSD帯域が不足するとGPU計算が読み戻し待ちになる
- 長期収束や最終タスク精度は主評価ではない
- 一般的なconsumer SSD 1台のオフロード性能へ直接外挿できない
