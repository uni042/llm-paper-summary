# Smart-Infinity: Fast Large Language Model Training using Near-Storage Processing on a Real System

> SSDに置いたparameterとoptimizer用の更新状態をCPU/GPUへ毎回読み戻さず、FPGA付きSmartSSDの中でAdam更新まで済ませ、PCIeを通るdata量を減らすtraining system。

## 概要
Smart-Infinityは、ZeRO-InfinityのようなSSD-offloaded trainingで、**parameterだけでなくAdamのmomentum / varianceなど、学習更新のために保持する大きな状態**を毎step SSDからCPU/GPUへ読み戻すcostを扱う。これらをまとめてoptimizer stateと呼ぶ。論文のGPT-2 8.4B分析では、optimizer state関連の通信がbaseline時間の約75.6%を占める。

そこで通常のNVMe SSDを高速化するのではなく、**FPGAを内蔵したcomputational storage device（SmartSSD）側でoptimizer updateそのものを実行**する。GPUからはgradientだけを渡し、parameterとoptimizer stateの大部分はSSD内部で読み出し・更新・書き戻す。

論文でいう **near-storage processing** は、storage上のdataをCPU/GPUまで運んでから計算するのではなく、**dataが置かれているSSDのすぐ近くにあるFPGAで計算する**ことを意味する。

したがって本研究の中心は「SSDを大容量メモリとして使う」ことではなく、**SSDに置いた状態をhostへ戻さず、その場で更新することでdata movement自体を減らす**ことにある。

## 手法のあらまし

### 1. `SmartUpdate`：optimizer stateをSSDの外へ出さない

通常のZeRO-Infinityでは、GPU memoryに収まらないparameterやoptimizer stateをCPU DRAM / NVMeへ置き、必要時に読み戻す。optimizer updateではSSD上のparameter・momentum・varianceをCPU/GPU側へ読み、更新後に再びSSDへ書き戻す必要がある。

SmartUpdateでは、この処理をSmartSSD内のFPGAへ移す。

処理の流れは概ね、

`SSD上のparameter / optimizer state → FPGAでAdam更新 → SSDへ書き戻し`

となる。hostへ送る必要があるのは主にgradientである。

### 2. Parameterを大きな連続列へまとめ、一定sizeごとに分担する

モデル構造ごとにFPGAロジックを変えないため、parameterを大きな1次元列として並べ、一定サイズのgroupへ分割する。論文の **flattened parameter subgroup** は、この「元のlayer構造をいったん無視して連続した更新単位へまとめたもの」を指す。

各SmartSSDは自分が担当するgroupだけを更新するため、CSDを増やすとoptimizer update bandwidthも並列に増やせる。

### 3. SSDとFPGAの間でhostを経由せず直接dataを動かす

parameterとoptimizer stateはSSDからFPGAのbufferへ直接送る。固定bufferを使い回しながら、次groupの読み込みと現在groupの更新を重ねる。

論文の **P2P DMA** は、CPUが一度dataを受け取ってcopyし直すのではなく、**device同士がDMAで直接dataを移す**仕組みを指す。

ここで重要なのは、**SSD→CPU→FPGAのようなhost経由を避け、SmartSSD内部でデータを動かすこと**である。

### 4. `SmartComp`：GPUからSSDへ送るgradientも圧縮する

SmartUpdateでもgradientはGPUからSmartSSDへ送る必要がある。

SmartCompはgradientの絶対値が大きい上位約1%だけをGPU側で選び、位置indexとvalueを送る。通信量は元の約2%まで下がる。

FPGA側では受け取ったindexの位置へvalueを戻し、その他を0として元sizeのgradient表現を作ってoptimizer updateへ使う。論文のscatterは、この**疎なindex/value表現を元の位置へ配置し直す処理**である。

この部分だけは**lossy圧縮**であり、SmartUpdate単体の厳密な更新とは区別する必要がある。

### 5. `SmartSSD`とは何か

本論文のSmartSSDは一般的なconsumer NVMeではない。

| 構成要素 | 役割 |
|---|---|
| NVMe flash | parameter / optimizer stateを保持 |
| FPGA | Adam等の更新を実行 |
| 内部DMA | SSDとFPGA間のデータ移動 |
| PCIe | gradientや更新済みparameterのhost通信 |

このため、GDSや通常NVMe RAIDと同じカテゴリーとして扱うと性能特性を誤る。

## 評価

### まず見るところ
- **結論:** optimizer updateをSSD内FPGAへ移すと、ZeRO-InfinityのSSD↔host転送を減らし、SSD-offloaded trainingを高速化できる。
- **学習速度:** SmartSSD台数を増やすほど伸び、代表条件で約1.5〜2倍、A100条件では最大約2.1倍。
- **品質:** SmartUpdate単体はbaselineと同精度。SmartCompは近似だが、評価taskでは大きな品質崩れを示さない。
- **I/O:** 通常NVMeではなく**FPGA付きcomputational storage**。
- **注意点:** SmartSSDの価格と専用hardware依存が大きい。

### 実験環境

| 項目 | 条件 |
|---|---|
| GPU | RTX A5000 24GB、A100 40GB、RTX A4000 16GB |
| CPU | 2×Xeon Gold 6342 |
| Storage | Samsung SmartSSD 4TB、最大10台 |
| SmartSSD FPGA | Xilinx Kintex UltraScale+ KU15P |
| Baseline | DeepSpeed ZeRO-Infinity + software RAID0 |

### GPT-2 8.4Bの高速化

| 構成 | 6 SSD | 10 SSD |
|---|---:|---:|
| SmartUpdateのみ | 1.18〜1.24倍 | 1.54〜1.60倍 |
| + transfer handler | — | 最大1.60〜1.66倍 |
| + SmartComp | — | 1.85〜1.98倍 |

SmartComp込みの最大値にはgradient近似の効果も含まれるため、SmartUpdateだけのlosslessな高速化と分けて読む必要がある。

### モデルサイズを増やした場合

| Model | 条件 | Speedup |
|---|---|---:|
| GPT-2 33B | 6 SSD | 1.37倍 |
| GPT-2 33B | 10 SSD | 1.88倍 |
| 各種model + A100 | 多CSD | 最大2.11倍 |

### FPGA側の処理能力

| 項目 | 結果 |
|---|---:|
| optimizer updater throughput | 7 GB/s超 |

FPGA計算自体より、SSD read/writeや共有PCIeが律速になりやすい設計である。

### 品質

BERT fine-tuningやGPT-2評価では、SmartUpdateはbaselineと同等の品質を維持する。SmartCompも評価範囲では比較可能な精度を保ったが、圧縮率をさらに上げれば品質とのtrade-offが生じる。

### Costと制約

| 項目 | 概要 |
|---|---|
| SmartSSD価格 | 論文時点で約$2,400 |
| 同容量通常SSD | 約$400 |
| 少数台 | cost efficiencyが悪い |
| 多数台 | PCIe共有帯域が新たな律速 |

通常のconsumer NVMe、GDS、KV cache offload、MoE expert pagingへ直接外挿できる結果ではない。
