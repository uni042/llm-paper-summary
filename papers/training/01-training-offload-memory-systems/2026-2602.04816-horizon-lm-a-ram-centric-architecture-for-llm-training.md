# Horizon-LM: A RAM-Centric Architecture for LLM Training

## 一文要約

CPU DRAMを単なるGPUメモリ不足時の退避先ではなく**パラメータと最適化状態の正本**として扱い、GPUには計算中の層だけを流し込むことでGPUメモリ使用量をモデル全体の大きさから切り離そうとする方式。ただし論文は性能計算の誤りにより撤回済み。

## 問題設定

ZeRO-3などの既存オフロード方式は、パラメータや最適化状態をCPUへ退避してGPUメモリを節約できる一方、実行の中心は依然GPU側にある。GPU上に実行可能なモデル構造や自動微分（autograd）の計算グラフを維持し、必要なパラメータをGPUへ集め直すため、GPU・CPU双方のメモリ使用量が実行時バッファや分散処理の構造にも左右される。

Horizon-LMは、追加学習（fine-tuning）やアラインメント（alignment）のような、計算量よりもモデル状態を保持するメモリ容量が制約になりやすい単一ノード学習を対象とする。

## 手法

### CPUをパラメータの正本にする

全モデルパラメータ、勾配（gradient）、Adamの最適化状態（optimizer state）をCPU DRAMへ常駐させる。GPUにはモデル全体を保持せず、各層を計算するための再利用可能な軽量テンプレートと固定容量の作業領域だけを置く。

計算する層のパラメータだけをCPUからGPUへ非同期転送し、その層の順伝播または逆伝播が終わればGPU上の領域を次の層に再利用する。このため、設計上のGPUメモリ量はモデル全体の大きさではなく、概ね最大の1層と活性値（activation）作業領域で決まる。

### 完全な自動微分グラフを保持しない

通常のPyTorch学習のようにモデル全体の自動微分グラフを長時間保持せず、区間ごとに活性値を再計算しながら明示的に勾配を伝播する。これにより、GPUだけでなくCPU側でも実行基盤由来の可変なメモリ消費を減らし、CPU DRAM使用量をモデル状態中心の予測しやすい形にする。

### 二重バッファによる転送隠蔽

2組のGPUバッファを交互に使う二重バッファリング（double buffering）を採用する。GPUが現在の層を計算している間に次の層のパラメータをCPUから先読みし、逆伝播で得た勾配も別の転送経路でCPUへ戻す。

計算、CPU→GPU転送、GPU→CPU転送を別CUDAストリームで並行させ、PCIe / NVLink系の転送待ちを可能な限りGPU計算の裏へ隠す。

## メモリ構成

この論文の中心は**CPU DRAMオフロード**であり、SSD / NVMeを主たるパラメータ階層にはしていない。

BF16パラメータ2 byte、BF16勾配2 byte、FP32 Adamの2つのモーメント8 byteとして、永続状態の理論最小CPUメモリは概ね **12 byte / parameter**。したがって100B parameterでは永続状態だけで約1.2 TBのCPU DRAMが必要になる。

つまりGPUメモリ制約を大幅に緩める代わりに、**非常に大容量のCPU DRAMと十分なCPU↔GPU転送帯域が必要**になる方式である。

## 評価条件と主要結果

撤回前原稿ではQwen2.5系などを用い、A100、GH200、H200環境で評価していた。

- 単一H200 + 1.5 TB host RAMで120B parameterまで学習可能と報告。
- 一般的な単一A100環境では、DeepSpeed ZeRO-3 + CPU offloadに対して学習throughputが最大12.2倍と報告。
- モデル規模が増えても、GPU上にモデル全体を常駐させないためGPUメモリ増加を抑え、CPUメモリ使用量も主としてパラメータ数に比例する形を狙う。

**ただし、arXiv v3の撤回コメントによれば、実験評価のtraining FLOPs式で `12HL` 項を欠落させた計算誤りがあり、報告throughput値が系統的に誤っていた。したがって12.2倍などの性能数値は有効な確定結果として引用すべきではない。** 120Bの実行可能性など、throughput式そのものとは別の主張についても、訂正版が公開されるまでは撤回論文由来の未確定な結果として扱う。

## 既存研究との差

### ZeRO-Offload / ZeRO-Infinity

既存方式はGPU中心の分散学習モデルを保ったまま、CPU DRAMやNVMeを容量拡張層として使う。Horizon-LMはCPU DRAMそのものをモデル状態の正本とし、GPUを一時的な計算装置として扱う点が異なる。

### TERAIO / SSDTrainなどのSSDオフロード

SSD系研究は、GPUまたはCPUに収まりきらないテンソルをNVMeへ退避し、I/Oを計算と重ねることが中心。Horizon-LMはSSD容量ではなく大容量DRAMを利用し、storage I/Oを避ける代わりにTB級RAMを要求する。

## 限界

- **論文自体が撤回済み**であり、性能評価には既知の計算誤りがある。訂正版または再投稿版が出るまでは性能比較の根拠に使えない。
- 100B級ではCPU DRAM自体がTB級必要で、一般的なデスクトップ環境向けではない。
- CPU→GPUへ層パラメータを継続的に流すため、転送帯域に対して計算量が小さい層・小さいbatchでは転送を隠し切れない可能性がある。
- 公開コードの対応範囲と論文が想定するアーキテクチャ範囲は分けて評価する必要がある。
- SSD / NVMeを容量階層として利用しないため、CPU DRAM容量そのものを超えるモデル状態には別の仕組みが必要。

## 一般的な実装上の含意

オフロード学習では「何をCPUへ逃がすか」だけでなく、**どのメモリ階層を状態の正本にするか**が実行基盤全体を左右する。GPUを正本として不足分だけを退避する設計から、CPUを正本として必要な計算片だけをGPUへstreamingする設計へ反転すると、GPUメモリ量をモデルサイズから切り離しやすくなる、という設計上の着眼点は性能値とは独立している。

一方で、この設計は必要帯域を消すのではなくCPU↔GPU経路へ集中させる。そのため、二重バッファ、非同期先読み、再計算の粒度、batch sizeを組み合わせ、転送時間を計算時間の中へ収められるかが性能上の核心になる。

## 引用関係

Horizon-LMはZeRO / ZeRO-Infinityを代表的なGPU中心オフロード方式として比較し、近年のSSDオフロード研究としてTERAIOなどにも言及する。系統上は、CPU DRAM / NVMeを補助階層として使う従来方式から、CPU DRAMを主記憶として再定義する方向の提案として位置付けられる。ただし撤回済みのため、後続研究との比較では研究アイデアと実証結果を分けて扱う必要がある。
