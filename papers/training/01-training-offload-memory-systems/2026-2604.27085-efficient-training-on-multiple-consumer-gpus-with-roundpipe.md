# Efficient Training on Multiple Consumer GPUs with RoundPipe

> 各GPUに特定の層（layer）を固定せず、空いたGPUへ処理段階を順番に割り当て、実測負荷に合わせた不均等分割と転送優先度制御でconsumer GPU学習の待ち時間を減らす。

## 概要

RoundPipeは、24GB級のconsumer GPUを複数枚使ってLLMをfine-tuningするとき、**パイプライン並列（pipeline parallelism）で特定のGPUだけが重い処理を担当し続けるため全体が待たされる問題**を扱う。

一般的なパイプライン並列では、

- GPU 0：layer 0〜7
- GPU 1：layer 8〜15
- GPU 2：layer 16〜23

のように、各GPUがモデルの一部分を固定的に所有する。

しかし層ごとの計算量や重みサイズは完全には均等でない。特に出力層など重い部分を担当したGPUが遅いと、他GPUは自分の処理が終わっていても次のデータを待つ。

このパイプライン上の空き時間を**パイプラインバブル（pipeline bubble）**という。

RoundPipeは「GPUごとに担当層を固定する」という前提を外し、GPU群を**特定の層を永続所有しない実行ワーカー群**として扱う。処理段階（stage）が来るたびに、スケジューラが利用可能なGPUへ割り当てる。

モデル重み、最適化状態、活性値の主な保存先はCPU DRAMで、GPUにはその時担当するstageの作業データだけを送る。SSDは中心機構ではなく、主な制約はPCIe帯域とCPUメモリ容量・帯域である。

## 手法のあらまし

### 1. 状態を固定所有しないワーカー（stateless worker）としてGPUを使う

通常のパイプライン並列では各GPUが特定stageの重みを持ち続ける。この固定対応を**重み束縛（weight binding）**と考えられる。

RoundPipeではGPUを**状態を固定所有しないワーカー（stateless worker）**として扱う。

ここでstatelessとは「GPU上にデータを一切置かない」という意味ではない。**特定のモデル層の恒久的な所有者にしない**という意味である。

あるGPUがstage Aを実行するときはCPU DRAMからそのstageの重みを受け取り、順伝播または逆伝播を実行する。処理が終われば、次は別stageを担当できる。

このため重いstageがあっても、毎回同じGPUだけがその負荷を背負う状態を避けられる。

### 2. 巡回割り当て（round-robin dispatch）でstage担当をGPU間に回す

RoundPipeはstageをGPUへ順番に割り当てる**巡回割り当て（round-robin dispatch）**を使う。

複数マイクロバッチ（microbatch）が同時にパイプライン内を流れるとき、空いたGPUへ次に実行可能なstageを回していく。

これはデータ並列の複製モデルを順番に使う方式ではない。**同じモデルの異なるstageについて、時間ごとに実行担当GPUを変える**方式である。

固定stage方式では一番遅いstageが全体周期を決めやすいが、RoundPipeは担当を循環させ、特定GPUの恒常的な負荷偏りを減らす。

### 3. 不均等stage分割（asymmetric stage splitting）：層数ではなく実際の処理時間で切る

「全32層だから8層ずつ4stage」のように層数だけで均等分割しても、各stageの処理時間は均等になるとは限らない。

RoundPipeは各層について、

- GPU計算時間
- パラメータサイズ
- 活性値サイズ
- CPU↔GPU転送時間

を測り、stage全体の所要時間が近づくよう境界を決める。

これが**不均等stage分割（asymmetric stage splitting）**である。

重い層を含むstageは層数を少なくし、軽い層のstageは多くまとめることで、パイプラインの各処理単位をできるだけ同程度の時間へそろえる。

### 4. 優先度付き転送（priority-aware transfer）：次のGPU計算を始めるデータを先に送る

CPU DRAMとGPUの間では、

- 次stageのパラメータ
- 順伝播・逆伝播で必要な活性値
- 最適化状態
- バックグラウンドの書き戻し

など複数のデータが同じPCIe帯域を奪い合う。

全部を同じ優先度で流すと、急がない最適化状態の転送がPCIeを占有し、「次のGPU計算に必要な重み」が待たされる場合がある。

このように重要度の低い処理が高い処理を塞ぐ状態を**優先度逆転（priority inversion）**という。

RoundPipeは、次の順伝播・逆伝播を開始するために必要なパラメータや活性値を高優先度で転送し、バックグラウンド転送を後回しにする。

### 5. イベント単位同期（event-based synchronization）で全GPUの一斉待ちを避ける

すべてのGPUを毎stageごとに一斉に待ち合わせる**全体バリア（global barrier）**を使うと、一部GPUの小さな遅れが全GPUへ波及する。

RoundPipeはCUDA eventなどを使い、必要な依存関係だけを細かく同期する。

つまり、

- 必要なパラメータが届いた
- 前stageの活性値が届いた
- 自分が担当するGPUが空いた

という条件がそろった処理から進む。

他stageに関係のない遅れで全GPUを止めないことが目的である。

### 6. CPU DRAMを主保存領域（backing store）として使う

モデル重み、最適化状態、活性値の大部分はCPU DRAMへ置き、GPUには現在実行するstageの**作業集合（working set）**だけを載せる。

ここで作業集合とは、「今この処理を実行するために直ちに必要なデータ一式」である。

この方式なら24GB GPUでも非常に大きなモデルを扱える一方、stageが変わるたびにパラメータをCPU→GPUへ送る必要がある。

したがってRoundPipeには、

- GPU常駐量を減らすほど扱えるモデルは大きくなる
- その代わりPCIe転送量が増える

という典型的な**容量と処理速度のトレードオフ**がある。

### 7. LoRAでは固定base modelのstreamingと相性がよい

LoRA fine-tuningでは、巨大な元モデルの大部分は固定し、小さな追加パラメータだけを学習する。

RoundPipeは固定されたbase modelの各層をCPU DRAMから順番にstreamしつつ、小さいLoRA adapterを更新する構成と相性がよい。

Qwen3-235Bをconsumer GPUサーバー上で31K sequence lengthまで扱えた結果は、この性質を強く利用している。

## 評価

### まず見るところ

- **結論:** GPUを固定stage所有者にせずワーカー群として使うことで、consumer multi-GPU学習の負荷偏りとオフロード待ちを減らせる。
- **学習処理量:** 最速の既存baselineに対して1.48〜2.16倍。
- **メモリ / context:** 8×RTX 4090環境でQwen3-235B LoRAを31K sequence lengthで実行。最大sequence lengthを次点baseline比4.7〜7.3倍へ拡張。
- **品質:** 学習計算そのものを近似する方式ではなく、stageの配置と実行順を変えるsystem最適化。
- **注意点:** 主評価は8 GPU級で、PCIe topology、NUMA、host RAM性能への依存が強い。

### Simulationの役割

パイプラインバブルやstage間の負荷差を分解するため、実機で測った層ごとの計算・転送時間をシミュレータへ入力する。

したがって論文全体がsimulation-onlyなのではなく、**主な性能結果は実機で、一部の原因分析にsimulationを使う**。

### Hardware依存性

| 要因 | 影響 |
|---|---|
| PCIe bandwidth | stage parameterのstreaming速度を左右 |
| NUMA配置 | CPU memoryから各GPUまでの転送速度差を生む |
| Host RAM bandwidth | 複数GPUへの同時streamで競合 |
| GPU間接続 | activation移動と同期costへ影響 |

ここで**NUMA（Non-Uniform Memory Access）**は、CPUメモリの場所によって各GPU・CPUコアからのアクセス速度が異なる構成を指す。

GPUを柔軟に使える代わりに、固定stage方式よりパラメータ移動が増えるため、interconnect性能は重要になる。

### 評価上の制約

- 代表評価は8 GPU構成
- SSD / direct I/Oは中心機構ではない
- 十分なhost DRAM容量と帯域が必要
- scheduler / event管理の実装複雑性が高い
- throughput / memory / context長が主評価で、最終downstream accuracyの広範比較は中心ではない
