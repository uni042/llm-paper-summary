# Efficient Training on Multiple Consumer GPUs with RoundPipe

> consumer GPU群をstateless worker poolとしてlayer stageをround-robin dispatchし、非対称分割と優先転送でpipeline bubbleとoffload待ちを減らす。

## 概要
RoundPipeは、24 GB級consumer GPUを複数枚使うLLM trainingで、固定pipeline stage ownershipによるload imbalanceとCPU offload待ちを減らすsystemである。

一般的なpipeline parallelismではGPUごとにmodelの特定layer範囲を固定所有するが、stageごとのcompute / activation量が不均衡だと最も遅いGPUが全体を止める。RoundPipeはGPUを**stateless worker pool**として扱い、layer stageをround-robinにdispatchする。

weight / optimizer state / activationの正本はhost DRAM側へ置き、各GPUには現在担当するstageのworking setだけをstreamする。SSDは中心機構ではなく、主な制約はPCIe bandwidthとhost memory capacityである。

## 手法のあらまし

RoundPipeでは `stateless worker`、`round-robin stage dispatch`、`asymmetric stage splitting`、`priority-aware transfer` が中核になる。

### 1. `Stateless Worker`：GPUへ固定model stateを所有させない

通常のpipeline parallelismではGPU 0がlayer 0〜7、GPU 1が8〜15、というようにstage ownershipが固定される。

RoundPipeでは各GPUを **stateless worker** とみなし、schedulerから割り当てられたstageのparameterをhostから受け取ってforward / backwardを実行する。

`stateless`はGPUに何も残さないという意味ではなく、**特定layerの永続的な所有者にしない**という意味である。

これにより、あるstageが重い場合でも特定GPUへ負荷が固定されない。

### 2. `Round-Robin Dispatch`：stageをworker間で循環させる

layer stageをGPUへ順番にdispatchし、複数microbatchの異なるstageを異なるGPUで進める。

固定pipelineではstage境界ごとに「次GPUが空くまで待つ」bubbleが生じるが、RoundPipeは空いたworkerへ次stageを回すことでidleを減らす。

このround-robinはdata-parallel replicaを回す方式ではなく、**model stageの実行担当を時間方向に循環させる**仕組みである。

### 3. `Asymmetric Stage Splitting`：layer数ではなく実測costでstageを切る

各layerのcompute time、parameter size、activation sizeをprofileし、stage境界を自動決定する。

単純に「各stage 8 layers」のように均等分割せず、重いlayerは少なく、軽いlayerは多く含めることでstage時間を揃える。

これが **asymmetric stage splitting** で、pipeline bubbleを減らす第一段階になる。

### 4. `Priority-Aware Transfer`：critical pathのtrafficを先に通す

host DRAMからはparameter、optimizer state、activationなど複数種類のdataがPCIeを共有する。

RoundPipeは転送を同一priorityで流さず、**次のforward / backwardを開始するために必要なparameter / activationを高priority**にする。

optimizer stateのbackground trafficがPCIeを占有してforward開始を遅らせる、といったpriority inversionを避けるのが目的である。

### 5. `Event-Based Synchronization`：global barrierを避ける

stage間の依存関係をCUDA event等で細かく表し、全GPUを毎回global barrierで揃えない。

必要なparameter / activationが届き、依存stageが完了したworkerから次へ進む。

このためpipeline timingに小さな揺らぎがあっても、他GPUまで一緒に止めにくい。

### 6. Host DRAMは`backing store`として使う

weight、optimizer state、activationの大部分はhost DRAMへ置き、GPUには現在stageのworking setだけを置く。

これにより24 GB GPUでも巨大modelを扱えるが、parameter streaming量は増える。

したがってRoundPipeはVRAMを節約するほどPCIe trafficが増える典型的なcapacity-throughput trade-offを持つ。

### 7. LoRAではbase model streamingの利点が大きい

LoRAではtrainable stateが小さいため、巨大なfrozen base model layerを順番にstreamしつつ、小さいadapterだけ更新する構成と相性がよい。

Qwen3-235Bをconsumer GPU上で31K contextまで扱える結果は、この性質を強く利用している。

## 評価

### まず見るところ
- **結論:** GPUを固定stage所有者にせずworker pool化すると、consumer multi-GPU trainingのpipeline imbalanceとoffload stallを減らせる。
- **Training throughput:** 既存最速baseline比1.48〜2.16倍。
- **Memory / context:** 24 GB RTX 4090でQwen3-235B LoRA・31K contextを実行し、最大contextを次点baseline比4.7〜7.3倍へ拡張。
- **品質:** training graphを変えずdispatch順を変えるsystem最適化で、品質は原則同等。
- **注意点:** 8 GPU級代表評価で、PCIe topology・NUMA・host RAM性能への依存が強い。

### Simulationの役割

pipeline bubbleの内訳やstage imbalanceを切り分けるため、実機で測ったlayer timing / transfer timingをsimulatorへ入力している。

したがって論文全体がsimulation-onlyではないが、**一部のpipeline分析値はsimulation**である。

### Hardware依存性

| 要因 | 影響 |
|---|---|
| PCIe bandwidth | parameter streaming速度を左右 |
| NUMA配置 | host→GPU path差を生む |
| Host RAM bandwidth | 複数GPU同時streamで競合 |
| GPU間接続 | activation / scheduling overheadへ影響 |

stateless dispatchは柔軟だが、固定stage方式よりparameter movementが増えるためinterconnect性能が重要になる。

### 評価上の制約

- 代表評価は8 GPU構成。
- SSD / direct I/Oは中心機構ではない。
- host DRAM容量とbandwidthが必要。
- scheduler / event管理の実装複雑性が高い。
- throughput / memory / context長が主評価で、最終downstream accuracyの広範比較は中心ではない。
