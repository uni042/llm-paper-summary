# FlexMoE: Scaling Large-scale Sparse Pre-trained Model Training via Dynamic Device Placement

> MoE学習中のルーティング（routing）偏りを監視し、負荷が高いエキスパート（expert）だけを必要数複製・移動して、tokenを捨てずにGPU間の待ち時間を減らすシステム。

## 概要

FlexMoEは、MoE学習で**エキスパートごとに届くtoken数が大きく偏り、その偏り方も学習中に変化する**問題を扱う。

MoEでは各tokenをゲート（gate）が少数のエキスパートへ振り分ける。同じ数のエキスパートを各GPUへ固定配置しても、人気エキスパートを持つGPUにはtokenが集中する一方、別GPUは仕事が少なくなる。

分散学習では一番遅いGPUが終わるまで他GPUも次へ進めないため、この遅いGPUを**遅延要因（straggler）**という。

既存方式には、エキスパートが受け入れるtoken数へ上限を設定し、超過分を捨てる方法もある。これは1ステップを短くできるが、学習に使えるtokenまで失う。

FlexMoEはtokenを捨てる代わりに、**負荷が高いエキスパートだけを複数GPUへ複製し、その複製間でtokenを分ける**。

64-expert GPT-MoEの観測では、上位10エキスパートだけで約75%のtokenを受ける例があり、「全エキスパートを同じ数だけ複製するより、hot expertだけ増やした方が効率的」という設計根拠になっている。

これはCPU/SSDオフロードではなく、**複数GPU上でのエキスパート配置と通信を動的に変えるMoE学習システム**である。

## 手法のあらまし

### 1. 仮想エキスパート（virtual expert; vExpert）：同じエキスパートの複製を独立配置する

1つの元エキスパートに対して、同じ重みを持つ複数の**仮想エキスパート（virtual expert; vExpert）**を作れるようにする。

vExpertは別の役割を学習した新しいエキスパートではない。**同じ計算をする複製（replica）**である。

通常のgateはこれまでどおり「元のどのexpertを使うか」を決める。その後FlexMoEが、そのexpertに対応する複数のvExpertのどれでtokenを実行するかを決める。

たとえばexpert 3へ1000 token集中し、2つのreplicaがあれば、それぞれ約500 tokenずつ処理させることができる。

### 2. Expand / Shrink / Migrateで複製数と配置を変える

負荷調整の基本操作は3つである。

| 操作 | 何をするか | 目的 |
|---|---|---|
| 複製追加（Expand） | expert replicaを追加 | hot expertのtokenを複数GPUへ分散 |
| 複製削減（Shrink） | 不要なreplicaを削除 | memoryと同期overheadを減らす |
| 配置移動（Migrate） | expertを別GPUへ移動 | 特定GPUへの負荷集中を解消 |

重要なのは平均GPU利用率をきれいに揃えることではなく、**最も遅いGPUの完了時間を縮め、全体ステップを短くすること**である。

### 3. 方策決定器（Policy Maker）が「変更する価値があるか」を予測する

expertを動かすこと自体にも、重みの転送や複製間同期というコストがある。負荷が少し偏っただけで毎回再配置すると逆に遅くなる。

FlexMoEは実際のrouting量を監視し、偏りが一定以上になったときだけ配置変更を検討する。

方策決定器（Policy Maker）は候補操作ごとに、

- expert計算時間
- tokenをexpert GPUへ送る全対全通信（All-to-All）
- replica間で勾配をそろえる全削減通信（AllReduce）
- expert重みを別GPUへ動かす時間

を見積もる。

その上で、**再配置コストを払っても一番遅いGPUの完了時刻が短くなる場合だけ変更する**。

### 4. 学習を止めずに可能な範囲で再配置する

expertの複製・移動を行うたびに全GPUを停止すると、動的配置の利点が失われる。

FlexMoEは専用CUDA streamを使い、通常の学習計算や通信と再配置を可能な範囲で重ねる。

論文の**ベストエフォート調整（best-effort adjustment）**は、「絶対に再配置を即完了させる」のではなく、学習を止めない範囲で裏側から配置変更を進める考え方である。

複製されたexpertの勾配同期についても、通信開始順を固定してdeadlockを避けるなど、動的に通信groupが変わっても安全に実行できるようにする。

### 5. 元のMoE routing自体は変えない

FlexMoEは、

- gateのTop-k
- tokenが選ぶ元expert
- model構造

を変更しない。

変えるのは、**選ばれた元expertをどのGPU上のreplicaで実行するか**だけである。

したがって、負荷分散のために別expertへtokenを迂回させる方式とは異なる。

## 評価

### まず見るところ

- **結論:** routing偏りに応じてhot expertだけを複製・移動すると、token dropなしでmulti-GPU MoE学習のstragglerを減らせる。
- **学習速度:** 目標品質までの時間はDeepSpeedより平均1.70倍、FasterMoEより平均1.30倍高速。
- **収束・品質:** token dropを避けるため、単一stepの速度だけでなくPPLやaccuracyにも利点が出る。
- **対象:** CPU/SSDオフロードではなく、GPU間expert placementとAll-to-All / AllReduce通信。
- **注意点:** routing変動が激しすぎる場合、頻繁なstate migrationが逆にoverheadになる。

### 目標品質までのtraining時間

| 比較対象 | FlexMoEの高速化 |
|---|---:|
| DeepSpeed expert parallelism | 平均1.70倍、最大2.10倍 |
| FasterMoE | 平均1.30倍、最大1.45倍 |

ここでのspeedupは推論token/sではなく、**学習で目標品質へ到達するまでの時間**である。

### 品質

| Model | 指標 | Baseline | FlexMoE |
|---|---|---:|---:|
| BERT-MoE | PPL | 3.53 / 3.31 | 3.14 / 3.07 |
| GPT-MoE | PPL | 12.20 / 10.71 | 11.72 / 10.47 |
| Swin-MoE | Top-1 | 77.316 / 77.022% | 77.754 / 77.109% |

改善の主因は、負荷均衡のためにtokenを捨てずに済むことにある。

### Cost modelと再配置

| 項目 | 結果 |
|---|---:|
| cost modelの平均予測誤差 | 3%未満 |
| Max-load metric vs Variance | 平均1.03倍、最大1.13倍良好 |

### 限界

- attentionなどnon-expert部分は最適化対象外
- optimizer update自体のoffloadはしない
- CPU DRAM / SSD / NVMe階層は扱わない
- single-GPU用途には直接効かない
- 頻繁な再配置ではstate migrationが逆に重くなる
