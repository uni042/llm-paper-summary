# FlexMoE: Scaling Large-scale Sparse Pre-trained Model Training via Dynamic Device Placement

> routing負荷に応じてexpertのGPU配置・複製数を動的に変え、token dropなしで分散MoE学習の不均衡を緩和するシステム。

## 概要
FlexMoEは、MoE学習でexpertごとのtoken流入が偏り、しかもその偏りが学習中に変化することで、特定GPUだけが遅くなる問題を扱う。固定expert parallelismでは、人気expertを持つGPUがstragglerになり、他GPUが待たされる。DeepSpeedのcapacity制限はtoken dropでstepを短くできる一方、学習信号を捨てる。FasterMoEの全GPU複製はdropを避けるが、複製粒度が粗い。

FlexMoEは、**重いexpertだけを必要な数だけ複製・移動する**。元のrouting結果は変えず、同じexpertのreplica間でtokenを分けるため、token dropなしでGPU間の仕事量を均す。64-expert GPT-MoE traceでは上位10 expertが約75%のtokenを受けるなど、実際のrouting skewが強いことを設計根拠にしている。

これはCPU/SSD offloadではなく、**multi-GPU trainingのexpert placementと通信最適化**である。

## 手法のあらまし

### 1. `vExpert`：expertの複製を最小スケジューリング単位にする

FlexMoEでは、1つの元expert（master expert）に対して複数の **virtual expert（vExpert）** を作れる。

vExpertは別の意味を持つexpertではなく、**同じ重みを使うreplica**である。gateは通常どおり元expertを選び、その後FlexMoEのrouterが、そのexpertに対応する複数vExpertへtokenを分配する。

これにより、hot expertだけを複数GPUへ広げられる。

### 2. `Expand / Shrink / Migrate`

負荷を調整する操作は3種類に整理される。

| 操作 | 何をするか | 目的 |
|---|---|---|
| Expand | expert replicaを追加 | hot expertのtokenを複数GPUへ分散 |
| Shrink | 不要になったreplicaを削除 | 同期・メモリoverheadを減らす |
| Migrate | expert配置を別GPUへ移動 | GPU間の最大負荷を下げる |

単純に平均負荷を下げるのではなく、**一番遅いGPUの完了時間を縮めること**を狙う。

### 3. `Policy Maker`：変更後のstep時間をcost modelで予測する

Schedulerは実際のtoken数とexpert配置を監視し、imbalanceが閾値を超えたときだけPolicy Makerを起動する。

Policy Makerは各候補操作について、

- expert計算時間
- tokenのAllToAll通信
- replica間のgradient AllReduce
- expert stateの移動コスト

を見積もり、**変更後の最大GPU時間が本当に短くなる操作だけ**を採用する。

### 4. `best-effort adjustment`：再配置で学習を止めない

expert再配置は専用CUDA streamで行い、可能な範囲で通常の学習通信と重ねる。

この設計を論文では **best-effort adjustment** としており、再配置そのものをcritical pathへ入れにくくしている。

また、複数replicaのgradient AllReduce順序をlogical ID順へ固定してdeadlockを避け、NCCL groupはLRUで再利用する。

### 5. 何を変えないか

FlexMoEは、

- gateのTop-k
- tokenが選ぶ元expert
- model構造

は変えない。変えるのは **「そのexpertをどのGPU上のreplicaで実行するか」** だけである。

## 評価

### まず見るところ
- **結論:** routing偏りに応じてhot expertだけを複製・移動すると、token dropなしでmulti-GPU MoE trainingのstragglerを減らせる。
- **学習速度:** 目標品質までの時間はDeepSpeedより平均約1.7倍、FasterMoEより約1.3倍高速。
- **収束・品質:** token dropを避けるため、step timeだけでなくPPLやaccuracyも改善する。
- **対象:** CPU/SSD offloadではなくGPU間placementとAllToAll/AllReduce最適化。
- **注意点:** 再配置しすぎるとstate移動・同期overheadが増える。

### 目標品質までのtraining時間

| 比較対象 | FlexMoEの高速化 |
|---|---:|
| DeepSpeed expert parallelism | 平均1.70倍、最大2.10倍 |
| FasterMoE | 平均1.30倍、最大1.45倍 |

ここでのspeedupは**推論token/sではなく、学習で目標品質へ到達するまでの時間**である。

### 品質

| Model | 指標 | Baseline | FlexMoE |
|---|---|---:|---:|
| BERT-MoE | PPL | 3.53 / 3.31 | 3.14 / 3.07 |
| GPT-MoE | PPL | 12.20 / 10.71 | 11.72 / 10.47 |
| Swin-MoE | Top-1 | 77.316 / 77.022% | 77.754 / 77.109% |

改善の主因は、負荷均衡のためにtokenを捨てずに済むことにある。

### Cost modelと再配置

| 項目 | 結果 |
|---|---:|
| cost modelの平均予測誤差 | 3%未満 |
| Max-load metric vs Variance | 平均1.03倍、最大1.13倍良好 |

### 限界

- attentionなどnon-expert部分は最適化対象外
- optimizer update自体のoffloadはしない
- CPU DRAM / SSD / NVMe階層は扱わない
- single-GPU用途には直接効かない
- 頻繁な再配置ではstate migrationが逆に重くなる
