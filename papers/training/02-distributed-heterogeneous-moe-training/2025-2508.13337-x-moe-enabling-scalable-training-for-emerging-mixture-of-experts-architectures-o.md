# X-MoE: Enabling Scalable Training for Emerging Mixture-of-Experts Architectures on HPC Platforms

> expert数とTop-kが大きい新しいMoEで、空のpadding領域を通信しないtoken配置、node間の重複送信削減、MoE部分専用のsequence分割を組み合わせて大規模HPC学習を効率化する。

## 概要

X-MoEは、DeepSeek-MoEのように**expertを細かく多数へ分け、1 tokenあたり複数expertを選ぶMoE**を大規模GPUクラスタで学習するとき、活性値メモリとGPU間通信が急増する問題を扱う。

従来のMoE実装では、各expertが受け取れる最大token数に合わせて固定サイズの領域を確保し、実際にはtokenが入っていない部分を0で埋めることがある。この**詰め物（padding）**までGPU間で送ると、expert数やTop-kが増えるほど無駄な通信とメモリが大きくなる。

さらにTop-kが大きいと、1つのtokenが同じnode内にある複数expertへ送られることがあり、node間network上では同じtokenを何度も送ることになる。

X-MoEは主に、

1. 実tokenだけを詰めて通信する
2. 同じnode宛ての重複token送信をまとめる
3. MoE blockだけsequence配置をexpert parallel向けへ変える

ことでこれらの無駄を減らす。

CPU/SSDオフロードではなく、**GPU上の活性値配置とnode内・node間通信を最適化するHPC向けMoE学習システム**である。

また、NVIDIAだけでなくAMD MI250Xを使うFrontierスーパーコンピュータ上で大規模評価した点も特徴である。

## 手法のあらまし

### 1. Padding-Free Token Packing（PFT）：実際に存在するtokenだけ詰める

固定サイズbuffer方式では、たとえばexpertごとに最大100 token分の領域を確保し、実際には20 tokenしか来なくても残り80 slotを0で埋める場合がある。

この0領域までAll-to-Allで送れば、計算に使わないデータへ通信帯域を消費する。

X-MoEの**paddingなしtoken packing（Padding-Free Token Packing; PFT）**は、

- token id
- expert id
- expertごとの実token数

を基に、routingされたtokenだけを連続したbufferへ詰める。

送信先ごとにデータ量が異なるため、固定長のAll-to-Allではなく、相手ごとに異なるサイズを送れる**可変長全対全通信（All-to-All-v）**を使う。

つまり、**「最大容量分の箱を毎回送る」のではなく、「中身が入っている分だけ送る」**方式である。

### 2. Redundancy-Bypassing Dispatch（RBD）：同じnodeへ同じtokenを何度も送らない

Top-kが6や8のように大きいと、1 tokenが複数expertへ複製される。

その複数expertが同じ遠隔node上にある場合、素朴なdispatchではnode間networkを通して同じtokenを複数回送る。

**重複回避dispatch（Redundancy-Bypassing Dispatch; RBD）**は、同じnodeへ向かう複数copyをまとめる。

1. source nodeからdestination nodeへtoken本体を1回だけ送る
2. destination node内で必要な数だけ複製する
3. node内の各expertへ配る

という流れになる。

論文でいう**pilot token**は、この「node間では代表として1回だけ送るtoken」を指す。

これにより、高価なnode間通信を、より高速なnode内通信へ置き換える。

### 3. Sequence-Sharded MoE Block（SSMB）：MoE部分だけsequence配置を変える

Transformer全体で最適なデータ配置は同じとは限らない。

Denseなattention部分ではtensor parallelやdata parallel向けの配置が効率的でも、MoE部分ではexpert parallel向けにtokenを分散した方が通信・メモリ効率がよい。

X-MoEの**sequence分割MoE block（Sequence-Sharded MoE Block; SSMB）**は、MoE blockへ入るとsequenceをexpert parallel rankへ分割し、MoE処理が終わると全収集（AllGather）で元のlayoutへ戻す。

これにより、同じtoken/activationをtensor-parallel groupごとに重複保持する必要を減らす。

つまりモデル全体の並列方式を変更するのではなく、**MoE blockの前後だけデータ配置を切り替える**。

### 4. AMD/ROCmでも使えるkernelと通信実装を用意する

X-MoEはAMD MI250Xを使うFrontierで大規模評価している。

PFTのtoken gather/scatterはTritonで実装し、AMD環境ではROCmとRCCLを使う。

ここで、

- **Triton**：GPU kernelをPython系の記述から生成するプログラミング基盤
- **RCCL**：AMD GPU向けの集合通信ライブラリ

である。

既存MoE systemの多くがNVIDIA向け最適化へ強く依存する中で、fine-grained MoEをAMD HPCでもscaleさせたこと自体が重要なsystem成果になっている。

## 評価

### まず見るところ

- **結論:** paddingとnode間重複通信を減らすことで、大expert数・大Top-kのMoEをAMD HPC上でも大規模にscaleできる。
- **規模:** DeepSeek-style MoEを545B parameters、1024 GPUまでscale。既存方式が同じhardware budgetで扱える最大modelより約10倍大きいと報告。
- **性能:** Medium 55.2BでTED比5.15倍、Tutel比1.42倍。Large MoE layer時間を62.3%、All-to-All時間を50.7%削減する条件がある。
- **品質:** token dropや量子化ではなく、layoutとcommunicationのlosslessなsystem最適化。
- **注意点:** 256 GPU超ではrackをまたぐAll-to-All混雑が新しい律速になる。

### 通信・memory削減

| 指標 | 改善 |
|---|---:|
| Large MoE layer時間 | 62.3%削減 |
| all-to-all時間 | 50.7%削減 |
| activation | 2.81 / 1.95 GB → 1.21 GB級 |

### RBD単体

冗長率54.8%の32 GPU条件では、node間通信量を52.5%削減し、dispatchを約1.55倍高速化した。

### NVIDIAでの確認

8×A100 40GBでも、10.1B・seq2048で既存方式がOOMする構成をX-MoEは実行できた。

### 制約

- 256 GPU超ではrack間network congestionが急増
- 複数expert GEMMの実行方法には別のtrade-offが残る
- 最終task accuracyよりloss/scalabilityが中心
- CPU DRAM、NVMe、GDSは対象外
