# MoE Parallel Folding: Heterogeneous Parallelism Mappings for Efficient Large-Scale MoE Model Training with Megatron Core

> 注意機構とMoEで異なるGPU並列化グループを組み、同じGPU集合を処理ごとに組み替えて、エキスパートの不要なノード間通信を減らす大規模学習方式。

## 概要

大規模Transformer学習では、1つのモデルを多数GPUへ分割するために複数種類の並列化を組み合わせる。

代表的には、

- **テンソル並列（Tensor Parallelism; TP）**：1つの大きな行列計算を複数GPUへ分割
- **データ並列（Data Parallelism; DP）**：同じモデルを複数GPU群へ複製し、異なるデータを処理
- **パイプライン並列（Pipeline Parallelism; PP）**：モデルの層をGPU群へ分割
- **文脈並列（Context Parallelism; CP）**：長いsequenceをtoken方向に分割
- **エキスパート並列（Expert Parallelism; EP）**：MoEのexpertをGPU間へ分散

がある。

問題は、**attention部分とMoE expert部分では、速い並列化の組み合わせが違う**ことである。

attentionはTPやCPで分割すると効率がよい一方、MoE部分ではexpertをEPで分散した方がよい。しかし従来は両者へ同じGPUグループ構成を押し付けることが多く、MoE token通信が必要以上にノード間へ広がる場合がある。

MoE Parallel Foldingは、**attentionを実行するときのGPUグループと、MoEを実行するときのGPUグループを別々に定義する**。

ここでいう**折り畳み（folding）**はモデルを圧縮する意味ではない。同じ物理GPU集合を、処理の種類によって別の論理的な並列グループとして見直すことを指す。

主対象はH100級GPUを数十〜1024枚使う大規模学習で、CPU/SSDオフロードではない。

実機評価では、Mixtral 8×22Bを128基のH100で49.3% MFUまで動かし、従来のMCore 5D構成の46.3%を上回った。

## 手法のあらまし

### 1. attentionとMoEで並列グループを分離する

attention側では主に、

- TP: tensor parallel
- CP: context parallel
- DP: data parallel
- PP: pipeline parallel

を組み合わせる。

MoE側では、

- **expert tensor parallelism（ETP）**：1つのexpert内部の行列を複数GPUへ分割
- **expert parallelism（EP）**：異なるexpertをGPU間へ配置
- **expert data parallelism（EDP）**：expert側のdata parallel
- PP

を別に組む。

核心は、**attentionとMoEが同じrank mappingを共有する必要はない**とした点にある。

ここでrank mappingは、「どのGPU番号同士を1つの並列グループとして扱うか」という対応表である。

### 2. MoEの全対全通信をできるだけ高速なノード内へ閉じ込める

MoEではtokenを選ばれたexpertへ送るため、GPU間の**全対全通信（All-to-All）**が発生する。

同じTP/CPグループをそのままMoEへ使うと、この通信が複数ノードへまたがりやすくなる。ノード内NVLinkよりノード間networkの方が遅いため、通信時間が増える。

FoldingではMoE側のグループを別に組み、可能な範囲でEP通信をNVLink内へ閉じ込める。

必要な場合だけETPを使い、「expertを分けるための通信」と「expert内部の行列を分ける通信」のバランスを取る。

### 3. 同じGPUを処理段階ごとに別の論理グループとして見る

物理GPUを追加するわけではない。

たとえば同じ8 GPUについて、

- attention実行時：4-way TP × 2 group
- MoE実行時：8-way EPを含む別group

のように、処理ごとに論理的な役割を切り替える。

これが「folding」の具体像である。

モデル構造に合わせてmappingを切り替えることで、attentionとMoEの両方へ同じ妥協した並列構成を使う必要がなくなる。

### 4. 柔軟token dispatcherで可変token数を扱う

MoEではexpertごとに届くtoken数が毎回変わる。

**token dispatcher**は、routing後のtokenを各expert GPUへ送って、計算後に元の順序へ戻す通信層である。

MoE Parallel Foldingの柔軟token dispatcher（Flexible Token Dispatcher）は、

- tokenを上限超過時に捨てる方式
- tokenを捨てない方式
- expertごとに異なる可変token数
- 5種類の並列化が混在する構成

を同じ実装で扱う。

つまり、並列構成を変えるたびにtoken通信部分を個別実装し直さずに済む。

### 5. 通信網構成（topology）を考慮してmappingを決める

最適なfoldingは固定ではなく、

- GPU数
- expert数
- sequence length
- ノード内NVLink帯域
- ノード間network帯域
- GPU memory budget

に依存する。

ここで**通信網構成（topology）**とは、「どのGPU同士がNVLinkで直接つながり、どの通信がノード間networkを通るか」という物理接続関係である。

したがってMoE Parallel Foldingは単一の並列recipeではなく、**model構造とhardware topologyに合わせてGPU groupの対応を組み替える方法**と考えるのが適切である。

## 評価

### まず見るところ

- **結論:** attentionとMoEでparallelism mappingを分けると、不要なcross-node通信を減らし、大規模MoE学習のGPU利用効率を改善できる。
- **利用率:** Mixtral 8×22Bで最大49.3%、Qwen2-57B-A14Bで39.0%のモデルFLOPS利用率（Model FLOPs Utilization; MFU）。
- **規模:** 最大1024 H100、sequence length 128Kまでscaleを確認。
- **品質:** rank mappingと通信方法を変えるlosslessな配置最適化。
- **注意点:** Megatron Coreと大規模NVIDIA fabricへの依存が強く、consumer GPU容量問題とは別系統。

### MFUとは

**モデルFLOPS利用率（Model FLOPs Utilization; MFU）**は、GPUの理論演算性能のうち、モデルのforward/backward計算へどれだけ有効に使えているかを見る指標である。

通信待ちやidleが増えるほどMFUは下がる。

### 代表MFU

| Model / 条件 | FSDP | FSDP+EP | MCore 5D | Folding |
|---|---:|---:|---:|---:|
| Mixtral 8×22B / 128 GPU | 4.3% | 23.4% | 46.3% | 49.3% |
| Llama3-8×70B / 256 GPU | OOM | 19.6% | 38.8% | 41.6% |
| Qwen2-57B-A14B / 64 GPU | 9.9% | 25.4% | 35.3% | 39.0% |
| Fine-grained Mixtral / 128 GPU | 2.2% | 9.0% | 17.1% | 28.8% |

fine-grained MoEではexpert数が多く1 expertあたりの処理が小さいため通信overheadの割合が増えやすく、mapping分離の効果が特に大きい。

### Strong scaling

| Model | GPU数 / 条件 | MFU推移 |
|---|---|---:|
| Llama3系 | 最大1024 GPU | 43.7 → 41.5% |
| Qwen系 | context最大128K | 38.7 → 35.9% |
| Mixtral | scale拡大 | 47.6 → 42.9% |

### FP8との組み合わせ

128 H100のMixtralでは、

| 構成 | Throughput相当 |
|---|---:|
| MCore BF16 | 458.3 TFLOPS |
| Folding BF16 | 487.7 TFLOPS |
| MCore FP8 | 575.1 TFLOPS |
| Folding FP8 | 631.7 TFLOPS |

Foldingによる通信・配置改善と、FP8による演算高速化は別の効果である。

### 制約

- H100/NVLink級fabricを前提
- rank mappingとdispatcher設定が複雑
- fine-grained expertでは依然communication overheadが大きい
- CPU RAM、SSD、NVMe、consumer GPUの容量問題は対象外
