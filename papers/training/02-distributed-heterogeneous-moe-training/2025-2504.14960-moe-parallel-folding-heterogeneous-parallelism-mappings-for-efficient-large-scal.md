# MoE Parallel Folding: Heterogeneous Parallelism Mappings for Efficient Large-Scale MoE Model Training with Megatron Core

> data・tensor・expert・pipeline parallelismを層や段階ごとにfoldし、通信量とメモリ制約へ柔軟に適応するMoE学習方式。

## 概要
MoE Parallel Foldingは、attentionとMoE expertで最適なparallelism構成が違うのに、同じGPU groupへ同じTP/EP/CP/DP設定を押し付けると不要な通信が増える問題を扱う。

ここでいう **folding** はmodel重みを圧縮する意味ではなく、**attention用parallel groupとMoE用parallel groupを、同じ物理GPU群の上へ別mappingで折り畳むこと**を指す。

主対象はH100級の大規模trainingで、CPU/SSD offloadではない。

## 手法のあらまし

### 1. attentionとMoEでparallel groupを分ける

Attention側は主に、

- TP: tensor parallel
- CP: context parallel
- DP: data parallel
- PP: pipeline parallel

を組み合わせる。

一方MoE側は、

- ETP: expert内部のtensor parallel
- EP: expert parallel
- EDP: expert側data parallel
- PP

を別に組む。

**同じrank mappingを共有しない**ことが核心である。

### 2. なぜ分けるのか

attentionはTP/CPの恩恵が大きいが、そのparallel groupをそのままMoEへ適用すると、expert dispatch/combineがcross-nodeへ広がりやすい。

Foldingでは、MoE側はEPを優先してexpert通信をNVLink内へ閉じ込め、必要な場合だけETPを使う。

### 3. `folding`の具体像

物理GPU数を増やすのではなく、**同じGPU集合を処理段階ごとに違うlogical groupとして見る**。

たとえばattentionでは4-way TPとして扱うGPU群を、MoE部分では8-way EPを含む別groupへ再解釈する。

このmapping変更で、通信経路とmemory balanceをmodel構造に合わせる。

### 4. `Flexible Token Dispatcher`

MoE部分ではexpertごとのtoken数が動的に変わる。

Flexible Token Dispatcherは、

- token-dropping / token-dropless
- dynamic token shape
- 5次元parallelism

を同じdispatcherで扱い、sequence長やcapacityが変わっても毎回dispatcher設計を作り直さない。

### 5. topology-aware mapping

最終的な構成は、

- GPU数
- expert数
- context長
- node内NVLink
- node間fabric
- memory budget

に依存する。

したがって、foldingは単一の固定parallel recipeではなく、**model構造とfabric topologyに合わせたrank mapping手法**である。

## 評価

### まず見るところ
- **結論:** attentionとMoEでparallelism mappingを分けると、不要なcross-node通信を減らし大規模MoE trainingのMFUを改善できる。
- **利用率:** 64〜1024 H100で既存5D parallelismより高いMFU。fine-grained MoEほど差が大きい。
- **品質:** rank mappingだけを変えるlossless配置最適化。
- **対象:** NVLink/cluster fabric上のdistributed training。CPU/SSD offloadではない。
- **注意点:** Megatron Coreと大規模NVIDIA fabricへの依存が強い。

### 代表MFU

| Model / 条件 | FSDP | FSDP+EP | MCore 5D | Folding |
|---|---:|---:|---:|---:|
| Mixtral 8×22B / 128 GPU | 4.3% | 23.4% | 46.3% | 49.3% |
| Llama3-8×70B / 256 GPU | OOM | 19.6% | 38.8% | 41.6% |
| Qwen2-57B-A14B / 64 GPU | 9.9% | 25.4% | 35.3% | 39.0% |
| Fine-grained Mixtral / 128 GPU | 2.2% | 9.0% | 17.1% | 28.8% |

fine-grained MoEで特に差が大きく、expert communicationを別mappingへ分離する効果が出ている。

### Strong scaling

| Model | GPU数 / 条件 | MFU推移 |
|---|---|---:|
| Llama3系 | 最大1024 GPU | 43.7 → 41.5% |
| Qwen系 | context最大128K | 38.7 → 35.9% |
| Mixtral | scale拡大 | 47.6 → 42.9% |

### FP8との組み合わせ

128 H100のMixtralでは、

| 構成 | Throughput相当 |
|---|---:|
| MCore BF16 | 458.3 TFLOPS |
| Folding BF16 | 487.7 TFLOPS |
| MCore FP8 | 575.1 TFLOPS |
| Folding FP8 | 631.7 TFLOPS |

Folding自体のmapping改善とFP8の算術高速化は別要因で、組み合わせるとさらに伸びる。

### 制約

- H100/NVLink級fabricを前提
- rank mappingとdispatcher設定が複雑
- fine-grained expertでは依然communication overheadが大きい
- CPU RAM、SSD、NVMe、consumer GPUの容量問題は対象外
