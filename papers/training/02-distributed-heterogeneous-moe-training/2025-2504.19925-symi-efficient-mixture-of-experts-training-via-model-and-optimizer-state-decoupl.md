# SYMI: Efficient Mixture-of-Experts Training via Model and Optimizer State Decoupling

> 動的に複製したいexpert重みと、巨大で移動コストの高いoptimizer stateの配置を切り離し、optimizer stateを動かさずにexpert複製数を毎iteration調整するMoE学習システム。

## 概要

SYMIは、MoE学習で人気expertへtokenが集中したとき、そのexpertを複数GPUへ複製して負荷を分散したい一方、**expertに付随する巨大な最適化状態（optimizer state）まで一緒に動かすと通信量とメモリ消費が大きくなる**問題を扱う。

Adam系最適化器では、expert重みそのものに加えて、過去の勾配を蓄積したmomentumやvarianceなど複数の状態を保持する。このoptimizer stateは重みより大きくなることがある。

従来の動的expert配置で、

`expert weight + optimizer state`

を1セットとして別GPUへ移動すると、人気度が変わるたびに大量の状態転送が必要になる。

SYMIの核心は、**expert重みとoptimizer stateを別々の場所へ置いてよい**とした点にある。

- expert weight：routing負荷に合わせてGPU上で動的に複製・再配置
- optimizer state：host側へ静的に分割配置し、基本的に動かさない

これにより、hot expertのGPU割当を毎iteration見直しても、巨大なoptimizer stateを毎回移送せずに済む。

初期arXiv版ではSwiftMoEという名称が使われていたが、現在の正式論文名・system名はSYMIで、NSDI 2026に掲載されている。

## 手法のあらまし

### 1. モデル状態と最適化状態の配置分離（model / optimizer state decoupling）

通常はexpert重みと、そのexpertを更新するoptimizer stateを同じ配置単位として扱いやすい。

SYMIはこれを分離する。

| 状態 | 配置 | 動かし方 |
|---|---|---|
| Expert weight | GPU | popularityに応じて複製・再配置 |
| Optimizer state | Host DRAM上で分割 | 基本的に固定 |

ここでいう**分離（decoupling）**は、optimizer stateを捨てることではない。「重みがGPU Aへ移ったからoptimizer stateもGPU Aへ移す」という固定対応をなくすという意味である。

更新時には、勾配をoptimizer stateが置かれているrankへ送り、そこで更新を計算する。

### 2. 前iterationの人気度から次iterationのexpert複製数を決める

MoEのrouting結果から、各expertへ何token割り当てられたかを集計する。

SYMIは前iterationのexpert人気度を、次iterationでも近い傾向が続くという予測に使う。

- hot expert：replicaを増やす
- cold expert：最低限のreplicaだけ残す

という形でGPU資源を割り当てる。

専用の学習済み予測器を使うのではなく、**routing負荷には短時間なら似た傾向が続きやすいという時間的局所性（temporal locality）**を利用する。

### 3. 更新済みweightを、もともと必要なweight通信へ載せて再配置する

optimizer stateはhost側に固定されていても、更新後のexpert weightは次iterationでGPUへ必要になる。

素朴には、

1. optimizer更新結果を元GPUへ返す
2. popularityに応じて別GPUへ再配置する

という2回の通信が必要になる。

SYMIは、この更新済みweightを次iteration用にGPUへ配る既存通信へ**相乗り（piggyback）**させる。

たとえば次iterationでexpert 3をGPU 2とGPU 5へ2 replica置くなら、更新済みweightを最初からその2 GPUへ送る。

これにより「更新後に改めて再配置する」専用通信を減らす。

### 4. 勾配をoptimizer stateの所在へ分散して送る

各expertのoptimizer stateは複数rankへ静的に分割されているため、勾配も対応するrankへ送る必要がある。

特定rankへ通信が集中すると、今度はそのrankが新しいボトルネックになる。

SYMIは同一node内の転送を優先しつつ、node間送信先を巡回（round-robin）させ、負荷を分散する。

つまりexpert重みのGPU配置とは別に、**optimizer計算側でも通信の偏りを避ける**。

### 5. 同じexpertの複製から出た勾配を二段階でまとめる

同じexpertを複数GPUへ複製すると、それぞれのreplicaから同じexpert重みに対する勾配が出る。

これらはoptimizer更新前に合算する必要がある。

SYMIは、

1. 同じGPU/node内にあるreplica勾配をまずlocalでまとめる
2. その後、必要なrank間だけ全削減通信（AllReduce）する

という二段階集約を使う。

これによりreplica数が増えるたびにnode間network trafficが比例して増えるのを抑える。

## 評価

### まず見るところ

- **結論:** expert重みの動的配置とoptimizer stateの静的配置を切り離すと、hot expertを毎iteration複製しても巨大optimizer stateを移動せずに済む。
- **収束時間:** DeepSpeedより30.5%、FlexMoEより25.9%短いtime-to-convergenceを報告。
- **収束:** token dropを減らすため、1 iterationの速度だけでなく目標lossまでに必要なiteration数も減る。
- **I/O:** optimizer stateは主にhost DRAM上へ静的分割。NVMe/GDS研究ではない。
- **注意点:** 次iterationの人気度を前iterationから推定するため、routingが突然大きく変わる場合は配置予測が外れる。

### 実験設定

| 項目 | 条件 |
|---|---|
| GPU | 16 GPU |
| Model | GPT Small / Medium / Large（125M / 350M / 760M） |
| Experts | 16 |
| Routing | Top-1 |
| Capacity factor | 1.0 |
| Baseline | DeepSpeed ZeRO-1、FlexMoE |

### 目標loss到達時間

GPT-Smallでloss 4.0へ到達する時間：

| System | 時間 |
|---|---:|
| DeepSpeed | 147.84分 |
| FlexMoE-100 | 145.42分 |
| FlexMoE-50 | 141.60分 |
| FlexMoE-10 | 138.61分 |
| SYMI | 102.68分 |

SYMIはDeepSpeed比で約30.5%、FlexMoE比で約25.9〜29.4%短縮した。

### iteration数とtoken drop

| 指標 | 改善 |
|---|---:|
| loss到達までのiteration数 | 約28.5%削減 |
| token drop | DeepSpeed比69%削減 |
| token drop | FlexMoE比43〜64%削減 |

ここでは**1 stepを速くする効果だけでなく、drop削減で収束に必要なstep自体を減らす効果**が大きい。

### 平均iteration latency

| Model | 改善 |
|---|---:|
| Small | 2.8%短縮 |
| Medium | 3.2%短縮 |
| Large | 9.3%短縮 |

1 iteration単体の改善は比較的小さいが、必要iteration数削減と合わせて目標lossまでの時間が大きく改善する。

### 通信overhead

大規模モデルを想定した解析では、baseline約0.269秒に対しSYMI約0.273秒で、追加通信overheadは約1.52%。

optimizer stateを動かさないことで、頻繁なexpert再配置を比較的小さい追加通信で実現している。

### 制約

- 実機modelは最大760M級
- 最終task accuracyよりloss到達時間が主評価
- host DRAMとPCIe帯域に依存
- routing popularityが急変するworkloadでは前iteration予測が弱い
- NVMe pagingやGDSは未評価
