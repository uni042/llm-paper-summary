# SiDA-MoE: Sparsity-Inspired Data-Aware Serving for Efficient and Scalable Large Mixture-of-Experts Models

> LSTMで各tokenのroutingを事前予測し、必要expertだけをCPU DRAMからGPUへ先読みするdata-aware MoE serving方式。

## 概要

SiDA-MoEは、Switch Transformerの大部分を占めるexpert weightをCPU DRAMへ置き、**次batchが使うexpertを小型LSTMで先に予測してGPUへ載せる**推論システムである。

大規模Switchでは全parameterのほぼ全てがexpert由来になる一方、1回のforwardで実際に使うexpertは少ない。SiDAはこのactivation sparsityを利用し、入力に応じてGPU上のexpert集合を入れ替える。

特徴的なのは、LSTM predictorが単なるprefetch hintではなく、元routerのexpert ID / scaling factorを近似する点である。そのためProMoEやExpertFlowのように「予測が外れてもnative routerの正しいexpertを必ず実行する」lossless prefetchとは異なる。

予測精度が高ければGPU memoryとtransfer待ちを大幅に減らせるが、外れれば元モデルと異なるroutingになり得る。実際、task accuracyは概ね保たれる一方、pretrained perplexityはかなり悪化する条件がある。

## 手法のあらまし

### 1. `Hash Predictor`：router経路をLSTMで先に作る

SiDAは2-layer LSTM + sparse attentionを使い、各MoE layer / tokenについて、

- expert ID
- routing scaling factor

を予測する。

予測結果はhash tableとして保存され、後続のinference threadが参照する。

### 2. `Truncated KD`：routerの上位候補だけ蒸留する

元routerのlogit全体を小型LSTMで再現するのは難しいため、top-T候補だけを蒸留するTruncated Knowledge Distillationを使う。

標準設定は `T=30` で、lossは概ね

`λ L_CE + L_TKD`

として、expert分類のcross entropyと上位logitのdistillationを組み合わせる。

短文SST2ではtop-1、MRPC / MultiRCではtop-3予測を使う。

### 3. Inference threadとHash-building threadをpipeline化

batch `X_j` のrouting hashをCPU側で構築している間に、inference threadは直前batch `X_i` を実行する。

つまり、

`predict(X_{i+1}) || infer(X_i)`

とずらすことでpredictor計算をcritical pathから外す。

batch size 1でも隣接request間pipelineを作る点が特徴である。

### 4. 予測したexpertだけGPUへresident化

各layerでhash tableを見て、次に必要と予測されたexpertがGPUに無ければCPU DRAMから転送する。

不要になったexpertはoffloadし、GPUは小さなworking setだけを維持する。

Switch-base-128 / 256のようにexpert weightが数十GBあるモデルほどこの効果が大きい。

### 5. `Lossy predictor`である点が重要

SiDAではpredictorがroutingを近似するため、予測ミスが発生するとnative routerとは異なるexpertが実行され得る。

この意味で、

- prefetchだけ予測するProMoE / ExpertFlow
- 正確な次層routingを前倒しするPre-gated MoE

とは性質が異なる。

速度とmemoryを得る代わりに、routing fidelityそのものを品質リスクとして持つ。

### 6. 長文ほどworking setが広がる

長いinputでは1 request内で触れるexpert集合が増え、GPUへ保持すべきexpertも増える。

そのため短文SST2で最もmemory削減が大きく、MultiRCのような200〜500 token入力では削減率が縮む。

## 評価

### まず見るところ
- **結論:** routingをLSTMで先読みすると大規模SwitchのGPU memoryとlatencyを大きく減らせる。
- **速度:** Switch-base-256ではSST2で最大約3.93× throughput改善。
- **メモリ:** 短文ではbase-128/256で60〜80%超のGPU memory削減。
- **品質:** task accuracy/F1は概ね高いfidelityを保つが、pretrained perplexityは明確に悪化するためlosslessとは言えない。
- **注意点:** A100 + Switch中心で、predictorのdomain shift・長文・router generalizationが主要リスク。

### 実機環境

| 項目 | 設定 |
|---|---|
| GPU | NVIDIA A100 80 GB |
| CPU | Intel Xeon Platinum 8358 |
| Batch | 1 |
| Expert backing store | CPU DRAM |
| Predictor | 2-layer LSTM + sparse attention |

### Models / tasks

| 項目 | 内容 |
|---|---|
| Models | Switch-base-8 / 64 / 128 / 256 |
| Tasks | SST2、MRPC、MultiRC |
| Baselines | Standard、DeepSpeed-MoE、Tutel |

Switch-base-256では総54.62 GB中約54.11 GB、99%超がMoE parameterであり、expert sparsityの効果が特に大きい。

### Predictor accuracy

| Model | SST2 | MRPC | MultiRC |
|---|---:|---:|---:|
| Switch-base-8 | 99.00% | 97.41% | 91.74% |
| Switch-base-128 | 98.78% | 98.65% | 90.49% |

長文MultiRCでは予測精度が低下する。

### Throughput

baseline平均比の代表値。

| Model | SST2 | MRPC | MultiRC |
|---|---:|---:|---:|
| Base-128 | 2.60× | 2.52× | 1.26× |
| Base-256 | **3.93×** | 3.83× | 1.57× |

短文ほど活性expert集合が小さく、prefetch / cacheの効果が大きい。

### GPU memory

短文SST2ではbase-128 / 256で60〜80%超の削減を報告する。

MRPCでも、

- base-128：約6.28 GB削減
- base-256：約19.84 GB削減

MultiRCでは、

- base-128：約4.52 GB
- base-256：約9.92 GB

の削減で、長文になるほどworking setが広がる。

### 品質 / fidelity

fine-tuned taskではbase-8で最大約99%、base-128で最大約96%のfidelityを報告する。

一方、pretrained perplexityは以下のように悪化する。

| Model | Original PPL | SiDA PPL |
|---|---:|---:|
| Base-8 | 6.68 | **18.49** |
| Base-64 | 4.93 | 11.84 |
| Base-128 | 4.86 | 11.73 |
| Base-256 | 4.59 | 8.11 |

この差から、`high routing prediction accuracy = native modelと同一品質` と解釈してはいけない。

### 制約

- router predictorの追加学習が必要。
- predictorはdomain / sequence lengthに依存する。
- 厳密losslessではない。
- A100サーバ + Switch系列中心。
- SSD/NVMe、KV cache、decoder-only MoE、continuous batchingは未評価。
