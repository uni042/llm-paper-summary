# LayerScope: Predictive Cross-Layer Scheduling for Efficient Multi-Batch MoE Inference on Legacy Servers

> 層別predictorとcross-layer schedulerでprefetch・on-demand transfer・CPU実行を共同最適化し、legacy GPU上のmulti-batch MoEを高速化する。

## 概要

LayerScopeは、multi-batch MoEでは**prefetchそのものがPCIeを塞いでnative missを遅らせる**ことがある、という問題を扱う。

単一request向けprefetchでは「将来expertを当てる」ことが主目的になりやすい。LayerScopeはさらに、

- どのexpertをprefetchするか
- どのexpertはCPUで直接計算するか
- on-demand loadへどれだけbandwidthを残すか
- 複数batchをどの順で処理するか

まで層横断で計画する。

中心構成は `LLaPor`、`PreSched`、`AsyncIO` の3つである。

## 手法のあらまし

### 1. `LLaPor`：Layer-Aware Predictor

各MoE layerに小型predictorを置き、そのlayer固有のrouting patternを学習する。

一つの大きなshadow modelで全層を予測するのではなく、小型predictorを分散配置することでoverheadを抑える。

予測対象は単純なtop-k完全一致だけでなく、hot expertやtoken coverageである。

### 2. Hot expert tableで初期resident集合を作る

ShareGPT等のtraceから頻出expertを抽出し、GPU cacheの初期配置に使う。

predictorが外れる前提でも、globalにhotなexpertは先に置いてmissを減らす。

### 3. `PreSched`：prefetchとnative demandを同じ計画へ入れる

PreSchedは各layerについて、

- GPUで実行
- CPUで直接実行
- 今prefetch
- native gate確定後にon-demand load

の候補を比較する。

重要なのは、prefetch trafficを無料とみなさず、PCIe bandwidth consumptionとしてcost modelへ入れる点である。

### 4. CPU executionも選択肢にする

小expertでは、weightをGPUへ送るよりCPUで直接GEMMした方が早いことがある。

そのためPreSchedはFiddlerのようにCPU計算も候補へ入れ、転送とcomputeのstragglerを減らす。

### 5. `AsyncIO`

pinned host memoryと非同期copyを使い、PyTorchの同期転送でGPU pipelineが止まるのを避ける。

cache regionを固定し、background prefetchとurgent on-demand transferを別扱いで発行する。

### 6. Multi-batchでcross-layer schedulingする

batchが増えるほど同時activated expert数が増え、prefetch queueも長くなる。

LayerScopeは現在layerだけでなく次layer以降まで見て、どのtransferを先に通すかを計画する。

この点が単純なnext-layer prefetchとの差になる。

## 評価

### まず見るところ
- **結論:** multi-batchではpredictor精度だけでなく、prefetch・native miss・CPU実行の競合をまとめて解く方が効く。
- **速度:** V100/A100双方でFate、Fiddler、Klotski、HybriMoEを上回る。
- **品質:** predictorはplacement/scheduling用でnative expert計算を維持するためlossless。
- **メモリ/I/O:** 24GB制約下でCPU DRAMとGPUを協調し、PCIe contentionを明示的に扱う。
- **注意点:** layerごとのpredictor学習・保持が必要。Mixtralのような大expertではGPU compute支配になり利得が縮む。

| Model | Improvement |
|---|---:|
| DeepSeek | +55.7% |

| Model | LayerScope throughput | vs HybriMoE | vs Fiddler |
|---|---:|---:|---:|
| DeepSeek | 41.7 t/s | +52.7% | +82.3% |

全条件の最大改善はFate / Fiddler / Klotski / HybriMoE比で約264% / 129% / 141% / 70.8%。

### Latency

Qwen3、A100、batch64では約3.74秒。

Klotski比約74.6%、Fate比約46.7% latency削減を報告する。

### Predictor

| Model | top-4 hit率 |
|---|---:|
| DeepSeek | 94% |
| Mixtral | 99% |
| Qwen | 97% |
| Moonlight | 99% |

predictor sizeは約0.5〜2.8 MB、latencyは約0.12〜0.48 ms。

ShareGPTからDPO / LLaVAへdomainを変えた場合の精度低下は平均約4.3% / 4.7%、最低でも約80%を維持。

### 制約

- layer-wise predictorのtraining / memory管理が必要。
- V100/A100 + 24GB制約を中心に評価。
- large expertではcompute時間が長くprefetch schedulingの相対効果が低下。
- runtime統合が複雑。
