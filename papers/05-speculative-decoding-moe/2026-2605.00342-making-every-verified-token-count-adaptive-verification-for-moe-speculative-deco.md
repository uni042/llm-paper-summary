# Making Every Verified Token Count: Adaptive Verification for MoE Speculative Decoding

> 各draft nodeの受理確率と実測verification costから、期待受理token／コストが最大となるtree prefixだけを動的検証する。

## 概要
EVICTは、MoE speculative decodingでdraft treeのtokenを固定数検証すると、受理されにくいnodeのために多数のexpertを起動し、verification costがacceptance gainを上回る問題を扱う。dense modelでは検証token数とcostの関係が比較的滑らかだが、MoEではnode追加により新expertが活性化されるため、costが不連続に増える。EVICTは各draft nodeのacceptance probabilityから期待受理長を推定し、実測したverification latencyとの比が最大となるancestor-closed tree prefixだけを検証する。decode stepごとにverification token数が変わり、簡単で高確率なbranchは広く、低確率またはexpert costが高いstepは小さくする。登録済みSP-MoEを引用し、prefetch中心の先行研究とは異なり、検証work自体の量を適応化する。native target verificationは選択したnodeについて厳密に行うため、samplingの正しさを維持する。SGLangとCUDA Graphへ統合した実機評価で、CPU offload／SSD offloadやKV cache offloadは対象外。expert I/Oというよりactive expert数とGPU verification computeを削減するconditional computation研究である。
## 手法のあらまし
各draft nodeにacceptance probabilityを付与し、tree上のあるprefixを選んだときに何tokenが受理されるかの期待値を計算する。nodeを選ぶにはancestorも必ず含むancestor-closed制約がある。別途、token数、tree shape、active expert数などからverification costをprofiling tableまたは軽量modelで推定し、expected accepted tokens / verification costを目的関数としてprefixを選ぶ。固定depth／固定widthのtreeと違い、stepごとのdraft confidenceとMoE costに応じて自己調整する。選択処理自体がCPU側overheadになれば利得が失われるため、候補prefix計算をSGLang execution pathへ組み込み、頻出shapeをCUDA Graphとしてcaptureする。graph replay可能な範囲にadaptive shapeを写像し、kernel launchとhost synchronizationを抑える。追加のexpert predictorを学習して先読みする方式ではなく、acceptance probabilityと計測costをresource allocation特徴量に使う。適応対象はspeculative token／verification node数であり、layer depthやexpert precisionは変えない。
## 評価
SGLangとCUDA Graphを用いたGPU実機で、Qwen3-30B-A3BなどのMoE targetを評価する。autoregressive generationに対して最大2.35倍、EAGLE-3に対して平均1.21倍のspeedupを報告する。Qwen3-30B-A3Bではverification token数を74.7%、active expert数を32.5%、verification latencyを26.6%削減した。token削減率に比べactive expert削減が小さいのは、残したnode間でもexpert集合が重なる一方、少数nodeが新expertを追加するMoE特有の非線形性を反映する。実機評価でsimulation-onlyではない。CUDA Graph融合を外すとCPUのadaptive selectionとlaunch overheadが問題となり、system integrationが手法成立の要件である。品質は選択prefixをtarget modelで正しく検証するためbaselineと整合するが、acceptance probability推定が悪いと速度だけが低下する。CPU／NVMe offload条件、PCIe bytes、energy、consumer GPUは未評価で、datacenter runtimeへの依存が強い。公式コードは一次資料から確認できない。
