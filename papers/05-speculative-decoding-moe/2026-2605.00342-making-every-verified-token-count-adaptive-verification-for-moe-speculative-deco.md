# Making Every Verified Token Count: Adaptive Verification for MoE Speculative Decoding

> 各draft nodeの受理確率と実測verification costから、期待受理token／コストが最大となるtree prefixだけを動的検証する。

## 概要
EVICTは、MoE speculative decodingで**draft treeを何nodeまでtarget modelで検証するか**を動的に決める手法である。

Dense modelではverification tokenを少し増やしても同じweightを再利用しやすいが、MoEでは1 node追加しただけで新しいexpertが活性化し、verification costが不連続に増えることがある。

そのため「acceptanceが高そうなnodeをできるだけ多く検証する」だけでは効率が悪い。EVICTは各nodeの受理確率と、実際にそのtree shapeを検証するcostを比較し、**期待accepted token / verification cost** が最も良いtree prefixだけを残す。

選んだnodeについてはtarget modelが通常通り厳密verificationするので、削るのは候補のbreadthであり、model計算自体を近似するわけではない。

## 手法のあらまし

### 1. Nodeごとのacceptance probabilityを持つ

draft treeの各nodeについて、「このtokenまでtargetにacceptされる確率」を推定する。

高確率nodeは検証する価値が高く、低確率nodeはそのためにexpertを追加起動する価値が低い。

### 2. `Ancestor-Closed Prefix`

treeの途中nodeだけを単独で選ぶことはできず、そのnodeへ至る祖先tokenも検証する必要がある。

EVICTはこの制約を満たすtree prefixだけを候補にする。

`ancestor-closed` は、**あるnodeを残すならrootからそこまでのpathも全部残す**という意味である。

### 3. Verification costを実測ベースで見る

MoEではcostがtoken数だけでは決まらない。

同じ10 tokenでも、全tokenが同じexpertへ集中する場合と、毎token別expertへ散る場合ではweight readとGEMM量が違う。

そこでEVICTはtoken数、tree shape、active expert数などからverification latencyをprofileし、cost modelへ入れる。

### 4. 目的関数は `expected accepted tokens / cost`

単純なacceptance最大化ではなく、**1単位のverification costで何token受理できそうか**を最大化する。

このためdecode stepごとにtree sizeが変わる。

- confidenceが高いstep → 広めに検証
- expert costが高いstep → treeを小さくする

### 5. CUDA Graphとの統合

adaptive treeはshapeが毎回変わるため、CPU schedulingやkernel launch overheadが増えやすい。

EVICTは頻出shapeをCUDA Graphへcaptureし、adaptive selectionをSGLang execution pathへ組み込む。

algorithmだけでなく、**可変treeのhost overheadを抑えるruntime統合**が重要になる。

## 評価

### まず見るところ
- **結論:** 受理されにくくexpert costが高いdraft枝を検証しないことで、MoE verificationを軽くできる。
- **実速度:** autoregressive比最大2.35×、EAGLE-3比平均1.21×。
- **品質:** 選択nodeはtargetで厳密verificationするため**lossless**。
- **注意点:** adaptive selection自体のCPU overheadを抑える必要がある。

### 実装

| 項目 | 内容 |
|---|---|
| Runtime | SGLang |
| Acceleration | CUDA Graph |
| Target例 | Qwen3-30B-A3BなどMoE |

### Speedup

| 比較対象 | 結果 |
|---|---:|
| Autoregressive generation | 最大 **2.35×** |
| EAGLE-3 | 平均 **1.21×** |

### Qwen3-30B-A3Bでの削減

| 指標 | 削減率 |
|---|---:|
| Verification token数 | **74.7%** |
| Active expert数 | 32.5% |
| Verification latency | 26.6% |

verification tokenを約75%減らしてもactive expertは32.5%しか減らない。

これは少数のnodeでも複数expertへ散るMoE特有のcost構造を示している。

### CUDA Graph統合の意味

adaptive tree選択だけをalgorithmとして入れると、CPU側のshape選択・kernel launch overheadが増える。

CUDA Graph統合を外すと利得が小さくなり、runtime optimizationが手法成立の一部である。

### 品質

選択したtree prefixについてtarget modelのrouter/logitsを通常通り計算するため、sampling correctnessは維持する。

### 制約

- CPU/SSD offloadのI/O削減手法ではない。
- datacenter GPU runtime前提。
- acceptance probabilityが外れると速度だけが悪化する。
- consumer GPUやenergy/tokenは未評価。
