# MoE-SpAc: Efficient MoE Inference Based on Speculative Activation Utility in Heterogeneous Edge Scenarios

> speculative decodingの検証で観測したexpert需要を先読み信号にし、utility推定・整数最適化・非同期実行でedgeのprefetchとCPU/GPU分担を制御する。

## 概要
MoE-SpAcは、speculative decodingで先に見えるfuture tokenのrouting情報を、**expert cache / prefetch / CPU-GPU配置の予測信号として再利用する**edge向けsystemである。

通常のdecodeでは1 step先のrouter情報しか得られないが、speculative verificationでは複数draft tokenについてtarget側のexpert activationをまとめて観測できる。MoE-SpAcはこの「少し先の需要」を各expertのutilityへ変換する。

そのutilityを基に、

- GPUへ常駐させるexpert
- CPUで直接計算するexpert
- 先に転送するexpert
- cacheから追い出すexpert

を一つのpolicyで決める。

つまりspeculative decodingをtoken生成高速化だけに使わず、**memory managementのlookahead sensorとして使う**のが主眼である。

## 手法のあらまし

### 1. `Speculative Utility Estimator`

speculative verification window内で、どのexpertが何回使われそうかを観測し、近い将来の需要utilityを更新する。

単純なLRUやglobal popularityと違い、**現在までの過去ではなくdraftが示す未来候補**を使う。

### 2. Utilityはcache / prefetch / evictionで共通化

cache policy、prefetch policy、eviction policyを別々のheuristicにすると互いに競合しやすい。

MoE-SpAcでは同じutilityを使って、

- utility高 → GPU resident / prefetch優先
- utility低 → eviction候補 / CPU実行候補

と判断する。

### 3. `Heterogeneous Workload Balancer`

CPUとGPUのどちらでexpertを実行するかも同時に決める。

入力は、

- VRAM容量
- CPU expert実行時間
- GPU expert実行時間
- PCIe bandwidth
- prefetch可能時間

など。

目的は片方だけを速くするのではなく、**CPU側とGPU側の完了時間を揃えてstragglerを減らすこと**。

### 4. Integer Optimization

expert配置とCPU/GPU分担を単純なgreedyで決めず、hardware制約を入れた整数最適化問題として解く。

これにより「GPUへ送るよりCPUでそのまま計算した方が速いexpert」も選べる。

### 5. `Asynchronous Execution Engine`

実際のruntimeでは、

- draft generation
- target verification
- weight transfer
- CPU expert compute
- GPU expert compute

を別queue / CUDA streamで重ねる。

utility予測だけ良くても同期実装では効果が出ないため、async engineがsystem成立の重要部分になる。

### 6. Native routingは変えない

expertを別expertへ置換する方式ではなく、**正しいnative expertをどこで・いつ実行するか**だけを変える。

したがってresource scheduling自体はlosslessである。

## 評価

### まず見るところ
- **結論:** speculative windowのfuture routingをresource managementへ使うと、cache/prefetch/CPU-GPU協調をまとめて改善できる。
- **実速度:** RTX 4090実機で既存SD / heterogeneous baselineを大幅に上回る。
- **品質:** target verificationとnative expertを維持するため**lossless scheduling**。
- **注意点:** acceptance rate、CPU/GPU比、PCIe帯域が変わるとutilityの価値も変わる。

| 比較 | 改善 |
|---|---:|
| SOTA speculative baseline比 | **+42% TPS** |
| 通常baseline群比 | 平均 **4.04×** |
| Qwen3: llama.cpp + SD / HybriMoE比 | 平均 **+52.9% TPS** |

### Latency

Qwen3条件ではlatencyを平均約45.6%削減。

### 何が効いているか

| 機構 | 役割 |
|---|---|
| Speculative utility | future expert需要を予測 |
| Cache policy | hot expertをGPUへ残す |
| CPU/GPU balancer | PCIe転送よりCPU実行が得な場合を選択 |
| Async engine | transfer / compute / verificationを重ねる |

### 品質

native target verificationとnative expert実行を保つため、cache/prefetch policy自体でmodel出力は変えない。

### 制約

- draft acceptanceが低いとfuture signalが弱くなる。
- speculative windowが短いとlookaheadが足りない。
- CPU/GPU性能比とPCIe帯域へ強く依存。
- integer optimizationとasync runtimeの実装コストがある。
- multi-request interference、SSD tier、energy/tokenは十分未評価。
