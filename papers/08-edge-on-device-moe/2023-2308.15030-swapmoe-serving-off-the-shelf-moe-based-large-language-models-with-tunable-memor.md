# SwapMoE: Serving Off-the-shelf MoE-based Large Language Models with Tunable Memory Budget

> 実expertを少数のvirtual expert枠へ動的に写像し、指定メモリ予算内で既成MoEの品質とswap遅延を調整する方式。

## 概要
SwapMoEは、全expertを保持できないconsumer／edge端末で、既成MoEモデルを再学習せずに、指定したGPU／主メモリ予算内で推論するフレームワークである。MoEは計算時にはtop-1など少数expertしか使わないが、Switch Transformerの64-expert layerは推論時14 GiBを要し、8／4 GiB級端末に収まらない。単純なon-demand swappingはPCIe転送を繰り返して6.2–8.9倍のlatencyを招き、static pruningはモデル容量とaccuracyを失う。SwapMoEは実際のexpertを小さい「Virtual Experts」スロットへ写像し、入力の局所性に合わせてスロットの中身を交換するため、GPUには小型MoE相当の重みだけを置きつつ、時間ごとに別のactual expertを参加させられる。
推論のみを扱い、学習時のexpert placement、CPUでexpertを計算するco-execution、SSDへのactivation offloadは対象外。Switch Transformer（16／32／64 experts/layer）とGPTSANを使い、要約と日本語Wikipedia language modelingを測定した。代表例ではSwitch Transformerの14.2 GiBを4.7 GiBへ67%削減し、latencyを50%下げ、ROUGE-2低下は0.041。入力ごとに重要expertが変わる性質を利用するため、単なるpruned小型モデルより元モデルの容量を保つが、予算に対するaccuracyとlatencyのtrade-offを完全には消せない。
## 手法のあらまし
まずoffline memory plannerが、layerごとのaccuracy、memory、latency性能モデルを測り、予算内で各layerのVirtual Expert数を決める。12-layer SwitchT-16の構成探索は単純全列挙だと12\^16通りになるため、genetic algorithmで構成を初期化し、遺伝・突然変異と制約違反の除去を繰り返す。layerごとのexpert重要度が異なることを利用し、性能に効くlayerへ多くのVirtual Expertスロットを割り当てる。runtimeはVirtual Expertをactual expertへ対応付け、入力tokenのrouter結果と過去の局所性を基に交換する。
GPU cacheの容量を各layerに分け、GPUにある低活性expertとRAM側の高活性expertを組にする。RAM／GPU間で重みを交換するが、毎tokenで全expertをロードする方式ではなく、スロットに載ったVirtual Expertを連続tokenで再利用する。頻度だけでなくsampleごとのexpert importance、layer-wise tolerance to absent expertsをoffline評価し、モデルの出力に効くexpertを残す。実装はHugging Face Transformers上で、batch size 1のcontinuous servingを想定する。主メモリを「全expertの正本」、GPUを「小さいactive window」とする構成であり、CPU計算で転送を避けるFiddlerや予測prefetchのSiDAとは違い、actual expertを必要に応じて置換する。
## 評価
実機はJetson Nano（最大4 GB）とJetson AGX Orinで、batch size 1。SwitchT-16／32／64はSAMSum要約、GPTSANはJapanese Wikipediaで評価し、ROUGE-2とperplexityを使った。比較はoriginal MoE、magnitudeの大きいexpertだけを固定保持するPruning、要求expertを都度読むOn-demand。SwitchT-16の例ではmemory budget 2.0 GiBに対し実測peak 1.64 GiB、latency 0.82 s、ROUGE-2 0.21（original 0.20）、3.0 GiBでは2.74 GiB／0.65 s／0.22、3.5 GiBでは3.58 GiB／0.76 s／0.23、4.0 GiBでは3.99 GiB／0.80 s／0.23。要約の代表条件では14.2→4.7 GiB、latency 50%削減、ROUGE-2低下0.041となった。
Jetson NanoでSwitchT-64を14 GiBから2.6 GBへ落とした場合、SwapMoEはPruningよりaccuracyが175%高い。SwitchT-32を4.7 GBで動かすとROUGE-2 0.232で、Pruningより8.76%高い。AGXの要約ではmemory37%、latency18%を削減しながらROUGE-2低下0.012の点もある。一方、On-demandは出力を保てるが転送latencyが高い。3.5 GiB予算で実測3.58 GiBとなるように予算違反もあり、性能モデル誤差が原因。課題はタスクが要約／日本語LM中心で、70B超を計算資源不足により未評価、GPU以外のRAM／SSD帯域を定量化していないこと。個人環境への転用性は高く、Jetsonを含む低メモリGPUで既成checkpointを使えるが、公式codeがないため再現性と新モデルへの適用コストが大きい。
