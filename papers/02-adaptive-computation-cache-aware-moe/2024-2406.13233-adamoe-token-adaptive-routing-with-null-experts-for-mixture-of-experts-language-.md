# AdaMoE: Token-Adaptive Routing with Null Experts for Mixture-of-Experts Language Models

> 計算を行わないnull expertをルーティング先に加え、容易なトークンほど実expertの実行数を減らす適応型MoE。

## 概要
AdaMoEは、通常のMoEが全トークンに固定top-kを強制する点を問題にし、トークンごとに実エキスパート数を変える軽量な方法である。追加するのは計算を行わない「null expert」で、ルータの候補数とkを増やし、nullが選ばれた分だけ実FFNの計算を省く。null expertはパラメータ・FLOPsを消費せず、オートレグレッシブ生成にもそのまま使える。負荷分散損失にはnullの平均使用量を組み込み、特定トークンが常にnullへ流れることを避ける。実装変更が小さいため、既存MoE-LLMへの追加学習（fine-tuning）や、通常のLLMにMo-LoRAとして差し込む用途を想定する。論文は、トークンの難易度差を利用して平均エキスパート負荷を下げながら精度を上げることを狙うが、MoEをゼロから事前学習していない点が明確な限界である。
null expertを追加してもルータのtop-k計算自体は増えるため、削減対象はFFNの行列演算である。モデルの非FFN部分、ルータ計算、LoRAの小さな専門家計算はFLOPs削減率へ同じ割合では寄与しない。従ってLoadとFLOPsは別指標として扱われる。null利用を平均値で制御する損失により、特定層・特定トークンだけが常時スキップすることを抑えるが、トークン難易度を明示的に教師ありで与えてはいない。既存MoEへ組み込む場合、元ゲートの確率をnullへどう拡張するかが初期学習の安定性を左右する。
ここでいう適応性は層ごとの固定top-kではなく、同じ層でもトークンごとに実計算を変える意味である。EOSのような単純トークンと内容語・推論トークンを同じ負荷で処理しないことを狙う。
## 手法のあらまし
真のエキスパートn個へm個のnull expertを加え、top-kをk個から選ぶ。nullは出力を加算せず、真のエキスパートだけがFFNを実行するため、ロード（平均実エキスパート数）をトークン単位で変えられる。ルータ確率に対するロードバランス損失は、学習初期にはnullと真のエキスパートの利用を強く均すよう設定し、後半は制約を緩めて性能を優先するアニーリングを使う。Mixtralへ適用する場合は、既存ゲートの出力次元をnull分だけ拡張し、初期確率を元の値から導いて急激な偏りを避ける。通常LLMではLlama2-7BにMo-LoRAの4実エキスパートを加える構成、MoE-LLMではMixtral-8x7BをQLoRA・4bitでfine-tuneした構成を比較した。m（null数）とk（top-k）を変えることで、平均負荷をほぼ連続的に調節できるが、nullをidentity mappingにする場合は別途ゼロFLOPs実装が必要で、論文では未検証である。
実験上の設定名m5k2やm8k3は、null数mとtop-kを表す。真の専門家が4個なら、kを増やしてもnullが上位を占めるトークンでは実行数が増えない。学習初期の強いバランス係数α1と後半の緩いα2を切り替え、ロードを制御してから性能を回復させる。Mixtralでは4bit QLoRAを使うため、AdaMoEそのものの推論性能と、量子化・LoRAの実行コストを分離する必要がある。論文が報告するFLOPsは主にFFN負荷の比較であり、実GPUのカーネル起動時間やPCIe転送を含むエンドツーエンド速度ではない点にも注意を要する。
null expertの平均使用率を負荷損失で制約するため、削減率を上げるほど精度が単調に保たれるわけではない。論文は複数のm,kを試し、実際にロードが1未満となる極端な設定も掲載している。
## 評価

### まず見るところ
- **結論:** null expertを選択肢に入れると、tokenごとに実FFN数を変え、標準設定では品質をほぼ保ったまま計算量を減らせる。
- **品質:** 標準設定では平均精度がbaselineと同等以上だが、null利用を強くしすぎると急激に崩れる。
- **計算効率:** 平均expert loadとFFN FLOPsは明確に減る。
- **実速度:** **wall-clockのend-to-end高速化は未実証**。FLOPs削減がそのままGPU latency削減になるとは限らない。
- **評価の強さ／注意点:** Mixtral側は4-bit QLoRA fine-tuningを含むため、AdaMoE自体と量子化・LoRAの影響を分けて読む必要がある。

<summary>評価条件・詳細な数値を開く</summary>

通常LLMの実験はLlama2-7B、GLUEのRTE/COLA、ScienceQA・CommonsenseQA・OpenBookQAの5データセットで、Mo-LoRA top-1/top-2をベースラインにした。Mixtral-8x7BではWinoGrande/HellaSwag/PIQA/SIQA/OQA/ARC-Cを評価し、fine-tuned baselineの平均精度84.64に対してAdaMoEは85.35、平均ロードは2.00から1.66、FLOPsは平均15.21%削減した。個別にはARC-Cがbaseline 87.46から89.15へ+1.69ポイント、WinoGrandeは80.43から81.93、HellaSwagは84.10から85.50へ改善した一方、PIQAは90.48から90.32、OQAは89.00から88.20へ小幅低下した。null 8個＋top-3（m=8,k=3）が標準構成である。SIQAのアブレーションではm=32,k=6で平均ロード1.54（baseline FLOPsの79.57%）でもbaselineを上回った。ロード制約を強くしすぎると精度が崩れ、例としてm=32,k=4はロード0.77・SIQA精度66.27、m=32,k=5は1.05・72.93である。したがって削減率と品質のトレードオフがあり、事前学習結果、nullを恒等写像にした場合、推論カーネルや転送時間の測定は未報告である。
この結果は平均値だけでなく、タスクごとの増減を伴う。WinoGrande・HellaSwag・ARC-Cでは改善したが、PIQA・OQAでは小幅な低下があり、nullを多く置けば常に品質が上がるわけではない。FLOPs削減率はFFN中心の推計で、メモリ帯域や実測レイテンシを含まないため、端末での速度改善は別途カーネル実装に依存する。
