# Not All Experts are Equal: Efficient Expert Pruning and Skipping for Mixture-of-Experts Large Language Models

> 層出力の再構成誤差で不要expertを恒久pruningし、低router weightの第二expertをtoken単位でskipする学習不要の圧縮手法。

## 概要
この論文はMixtral-8x7Bのexpert冗長性を、**静的なExpert Pruning**と**動的なExpert Skipping**の二段階で削る。

Pruningは各layerで8 expertsから6または4 expertsだけを恒久的に残し、model resident memoryそのものを減らす。Skippingは残ったmodelを実行するとき、top-2のうち2番目expertのrouter weightが十分小さいtokenでは、そのexpertをそのtokenだけ省く。

両方ともpost-trainingで大規模再学習を必要としないが、pruning集合はcalibration domainに強く依存する。特に一般C4で選んだexpert集合を数学taskへそのまま使うと品質が大きく崩れる例がある。

## 手法のあらまし

この論文では、`reconstruction-based pruning`、残存expert数`r`、dynamic skipping閾値`β`、calibration domainが重要になる。

### 1. `Reconstruction-based Expert Pruning`：frequencyではなくlayer出力を再現できる集合を残す

各MoE layer `l`について、元layer出力を `F(x)`、expert集合`C`だけ残した出力を `F'(x,C)` とする。

calibration dataに対し、

`||F'(x,C) - F(x)||_F`

が最小になるexpert集合`C`を探す。

つまり「使われる回数が少ないexpertを消す」のではなく、**そのexpertを除いてもlayer全体の出力をどれだけ再現できるか**で選ぶ。

### 2. 残存数`r`：各layerで何expert残すかを固定する

Mixtralは各layer 8 expertsなので、主設定は、

- `r=6`：2 experts削除
- `r=4`：4 experts削除

である。

残存expertだけでrouter probabilityを再正規化し、削除expertはmodel weightから除去する。

このpruningはtokenごとのruntime判断ではなく、**deployment前にmodel構造を恒久的に小さくする操作**である。

### 3. Layerごとにexpert集合を別々に選ぶ

同じexpert IDが全layerで同じ役割を持つわけではないため、各layerで独立に最適集合を探索する。

そのため「全layerのexpert 7を削る」といったglobal pruningではなく、layer 3ではexpert 2/5を削る、layer 4では1/7を削る、といった構成になる。

### 4. `Dynamic Expert Skipping`：top-2の第2expertだけtoken単位で省く

pruning後もMixtral routerは通常top-2を選ぶ。

選ばれた2 expertsのweightを `w0 >= w1` とし、第2expertの相対weight `w1 / w0` が小さいtokenでは、第2expert計算をskipする。

元は、

`z = w0 E0(x) + w1 E1(x)`

だが、skip時はほぼ第1expertだけを使う。

これはprefetch missを別expertへ置き換えるsystem手法ではなく、**model計算そのものを近似的に減らすdynamic Top-k**である。

### 5. 閾値`β`はlayerごとにcalibration dataから決める

各layerでcalibration tokenの`w1 / w0`分布を集め、その中央値を`β`として使う。

実行時に、

`w1 < β × w0`

なら第2expertをskipする。

したがって`β`は固定された普遍閾値ではなく、layer / calibration distributionごとに決まる。

### 6. Calibration domainがexpert重要度を大きく変える

一般task向けにはC4、数学task向けにはMATHを使う。

Mixtral r=6では、C4とMATHで選ばれるexpert集合が32 layer中わずか4 layerしか一致しないと報告される。

つまりこの論文の重要な示唆は、**expert重要度はmodel固有だけでなくtask distribution固有でもある**こと。

### 7. PruningとSkippingの役割は別

| 手法 | 変えるもの | 主な効果 |
|---|---|---|
| Expert pruning | Model resident expert数 | Memory削減、通信削減 |
| Dynamic skipping | Tokenごとの実行expert数 | Runtime FLOPs削減 |

両方を併用できるが、skipを追加するほどquality trade-offも増える。

## 評価

### まず見るところ
- **結論:** expertを恒久削除すると2 GPU必要だったMixtralを1 GPUへ載せられる一方、品質はcalibration domainと削減率に大きく依存する。
- **実速度:** r=6で1.20倍、r=4で1.27倍。skipping追加で最大1.33倍程度まで上積み。
- **品質:** moderateなr=6なら一般taskで数point低下だが、domain mismatchやr=4では大幅劣化する。
- **メモリ:** bf16 Mixtral 8x7BをA100 80GB×2から1枚へ縮められる。
- **注意点:** ほぼMixtral中心で、calibration選択自体がdeployment policyの一部になる。

### 一般task

ARC-c/e、BoolQ、HellaSwag、MMLU、OBQA、RTE、WinoGrandeなど8 zero-shot task。

| Model | 平均score | Baselineとの差 |
|---|---:|---:|
| Full Mixtral | 67.58 | — |
| r=6 | 64.22 | -3.36 |
| r=4 | 59.57 | -8.01 |
| Full Instruct | 69.98 | — |
| Instruct r=6 | 67.45 | -2.53 |
| Instruct r=4 | 63.88 | -6.10 |

r=6は比較的moderateだが、r=4では品質損失が明確になる。

### Memoryと実速度

| 構成 | Memory | 生成速度 |
|---|---:|---:|
| Full Mixtral | A100-80GB ×2必要 | 1.00倍 |
| r=6 | 1 GPUで実行可能 | **1.20倍** |
| r=4 | 46,879 MB | **1.27倍** |
| Wanda 2:4 | 51,214 MB | 0.91倍 |

構造的にexpert数を減らすことで、単なるweight sparsityより実GPU memory / communicationへ結びついている。

### 数学taskでのcalibration依存

GSM8K 5-shot。

| Calibration / 構成 | Score |
|---|---:|
| Full | 58.61 |
| Random r=6 | 36.39 |
| C4 r=6 | 41.02 |
| MATH r=6 | **51.25** |
| C4 r=4 | 24.87 |
| MATH r=4 | 37.07 |

**同じr=6でもcalibration data次第で10点以上差が出る**。この表が本手法の最大の注意点である。

### Dynamic skippingを追加した場合

一般task平均。

| 構成 | Score | Speedup |
|---|---:|---:|
| r=6 | 64.22 | 1.19倍 |
| r=6 + skip | 62.91 | **1.23倍** |
| r=4 | 59.57 | 1.27倍 |
| r=4 + skip | 57.91 | **1.31倍** |

Instructではr=6+skip 66.04 / 1.27倍、r=4+skip 62.33 / 1.33倍。

skippingは速度を少し上積みする代わりに、追加で1〜2点程度の品質を支払う典型的なquality–compute trade-offになる。

### 評価上の制約

- 評価modelがほぼMixtral-8x7B中心。
- calibration domainに強く依存。
- long-context / continuous batchingのsystem評価は限定的。
- dynamic skippingの速度はrouting / kernel実装にも依存する。
- pruning後のfine-tuningで回復できるが、その場合はtraining-freeではなくなる。
