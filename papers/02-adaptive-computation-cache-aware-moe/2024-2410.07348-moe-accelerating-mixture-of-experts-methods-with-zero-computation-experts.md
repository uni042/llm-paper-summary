# MoE++: Accelerating Mixture-of-Experts Methods with Zero-Computation Experts

> zero／copy／constantの計算不要expertをMoEへ混在させ、入力難度に応じて実FFN計算を減らす異種MoE。

## 概要
MoE++は、通常のFFN expertだけでなく、**ほぼ計算を必要としない3種類のexpert**をrouter候補へ最初から組み込む異種MoEである。

3種類は`zero expert`、`copy expert`、`constant expert`で、それぞれ「何も足さない」「入力をそのまま通す」「学習可能な定数を返す」という安価な経路を担当する。

AdaMoEのnull expertと似ているが、MoE++は単一のnull経路だけでなく、**異なる意味を持つ複数のzero-computation pathを学習時から機能分担させる**点が違う。

## 手法のあらまし

### 1. 3種類の`Zero-Computation Experts`

| Expert | 出力 | 狙い |
|---|---|---|
| Zero | 0相当 | そのMoE計算を実質skip |
| Copy | 入力をそのまま返す | identity / residual的な経路 |
| Constant | 学習可能な定数vector | 入力非依存の軽い補正 |

通常FFN expertと同じrouter候補に入るが、大きなFFN matrix multiplyを必要としない。

このためtokenによって「FFNを2個使う」「FFN 1個 + copy」「zeroだけ」といった異なる実計算量を学習できる。

### 2. AdaMoEとの違い

AdaMoEのnullは基本的に「計算しない枠」を作ることが中心だが、MoE++ではzero / copy / constantの**出力意味を分ける**。

特にcopy expertは情報をそのまま次へ渡せるため、単純dropより表現を壊しにくい。constant expertは入力を見ずに学習済みbias的な補正を与える。

したがって「FFNをしない」選択の中にも複数の代替表現を持たせている。

### 3. `τ`：FFN expertへ割く相対capacityを調整する

論文の`τ`は、zero-computation expertに対する**real FFN expert側のcapacity / load比率**を制御する主要parameterである。

`τ`を小さくするとzero-computation pathへ流れやすくなり計算は減るが、品質を落としやすい。大きくするとFFN利用が増えてvanilla MoEへ近づく。

標準設定はおおむね`τ=0.75`。

### 4. `Heterogeneous Capacity`：FFNとzero-computeに同じcapacityを割り当てない

FFN expertとzero / copy / constantは計算costも役割も違うため、全expertへ同じcapacityを与えるのは不自然である。

MoE++は`τ`を使ってFFN側とzero-computation側のcapacity式を分ける。

これによりcheap pathを十分使いつつ、FFN側のtoken overflow / dropが増え過ぎないよう調整する。

### 5. `Gating Residual`：前layerのrouting傾向を次layerへ渡す

各layerでrouterを完全に独立にすると、zero / FFN間の選択がlayerごとに不安定になる。

MoE++の **gating residual** は前layerのgate情報を次layerのgateへ加え、過去のrouting状態を引き継ぐ。

hidden-state residualではなく、**router decision側に残差接続を持つ**のがポイントである。

### 6. Zero-computation expertは各GPUへ複製しやすい

通常FFN expertは大きなweightを持つためexpert parallelでGPU間配置が必要だが、zero / copy / constantは極小なので全GPUへ複製できる。

そのためcheap pathを選んだtokenはexpert all-to-allやremote FFNへ送る必要が小さく、分散MoEでもcommunication削減につながる可能性がある。

### 7. 既存MoEへの後付けではない

MoE++はzero-computation pathを含んだ状態で100B〜1T token規模のtrainingを行う。

したがって既存Mixtralへruntimeだけ差し込むcache / pruning手法ではなく、**architecture + training recipeとしてのadaptive computation**である。

## 評価

### まず見るところ
- **結論:** zero / copy / constant expertを学習時から組み込むと、標準設定では品質を維持しながらexpert forwardを2割前後短縮できる。
- **実速度:** 1B / 2B / 7Bでexpert forward 21.8〜27.8%改善。攻めた`τ`ではさらに高速だが品質低下が増える。
- **品質:** 標準`τ=0.75`ではvanilla MoEと同等以上の平均score。
- **適用性:** post-hoc optimizationではなく、専用trainingが必要。
- **注意点:** 32×A100でのexpert forward中心評価で、consumer/offload環境のend-to-end latencyではない。

### 標準`τ=0.75`のexpert forward

| Model | Vanilla | MoE++ | 改善 | 平均task score |
|---|---:|---:|---:|---:|
| 1B | 610.9 ms | **500.3 ms** | **22.1%** | 45.3 → **46.1** |
| 2B | 683.4 ms | **561.0 ms** | **21.8%** | 45.9 → **47.3** |
| 7B | 1859 ms | **1455 ms** | **27.8%** | 52.3 → **53.1** |

標準設定では速度と品質を同時に改善している。

### `τ`を強く下げた場合

| Model | 設定 | Throughput改善 | 平均score |
|---|---|---:|---:|
| 1B | τ=0.10 | **111.2%** | 45.8 |
| 2B | τ=0.10 | **63.5%** | 46.3 |

標準`τ=0.75`より速いが品質は下がるため、典型的なquality–compute trade-offになる。

### Zero / Copy / Constantのablation

1B / 100B-token設定で全要素を使う構成は平均47.7。gating residualなし47.5に対し、あり47.7と小幅改善する。

constant expert数を増やし過ぎても性能が反落し、cheap pathの種類・数を増やせば単調に良くなるわけではない。

### 評価上の制約

- 既存modelへ追加するだけでは使えない。
- `τ`とcapacity設定へ品質が依存する。
- capacity overflowではtoken dropが起こる。
- 主速度指標はexpert forwardで、full serving latencyではない。
- edge / SSD / expert cache条件は直接評価しない。
