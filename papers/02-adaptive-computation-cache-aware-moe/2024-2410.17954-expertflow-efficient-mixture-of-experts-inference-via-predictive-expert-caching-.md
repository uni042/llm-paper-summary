# ExpertFlow: Efficient Mixture-of-Experts Inference via Predictive Expert Caching and Token Scheduling

> 将来routing予測・token再配置・cache枠再配分を統合し、CPU offload時のexpert miss待ちを隠すMoE推論フレームワーク。

## 概要
ExpertFlowは、CPUへoffloadしたexpertを単に予測prefetchするだけでなく、**同じexpert経路を通りそうなtokenを同じbatchへ集め、GPU cacheの枠自体もlayer間で動的に動かす**systemである。

構成は `RPP（Routing Path Predictor）`、`TS（Token Scheduler）`、`ECE（Expert Cache Engine）` の3部分。RPPが将来routingを予測し、TSがtokenをrouting pathの似た組へ並べ替え、ECEが予測需要に合わせてcacheを配分する。

予測が外れてもnative routerのexpertはon-demandで補うためlossless。主な階層はCPU DRAM ↔ GPU VRAMで、SSD offloadではない。

## 手法のあらまし

### 1. `RPP`：数layer先のexpert routing pathを予測する

Routing Path Predictorは、各tokenが将来layerでどのexpertへ送られるかを予測する軽量modelである。

単一layerの次expertだけでなく、**数layerにわたるrouting path**をまとめて出すため、prefetch開始を早められる。

RPPはnative routerを置き換えず、あくまでprefetch / schedulingのhintとして使う。

予測ミス時は正しいexpertを追加transferするため品質は変わらない。

### 2. `TS（Token Scheduler）`：routing pathが似たtokenを同じbatchへ集める

隣接する2 batch、合計`2T` tokenを対象に、予測routing pathのHamming similarityを使って二つの新batchへ再分割する。

目的は、各batch内で使うexpert集合を小さくすること。

例えば異なるexpertへばらばらに行くtokenを一つのbatchへ混ぜるより、同じexpertを使うtokenをまとめた方が、

- expert weight再利用が増える
- cache missが減る
- transfer回数が減る

という利点がある。

### 3. `Merge / Reindex`：token順序を戻す

TSはtoken順序を入れ替えるため、そのままではKV cacheや出力順序との対応が崩れる。

ExpertFlowは`Merge`と`Reindex`で、計算後のtoken / KV位置を元sequenceへ対応付け直す。

つまりTSはsemantic token orderそのものを変更するのではなく、**実行batch内の処理順を一時的に組み替えるsystem optimization**である。

### 4. `PLEC`：layer固定cacheではなく、必要layerへ枠を貸し借りする

ECE内の **PLEC（Predictive Layer-wise Expert Caching）** は、GPU expert cacheを各layerへ固定quotaで分けない。

RPPの予測需要を見て、

- 近い将来expertが多く必要なlayerへ多くの枠を割く
- 前layerの処理が終わって不要になった枠を後layerへ渡す

という形でcache capacityをlayer間で再配分する。

固定layer cacheでは「あるlayerは空いているのに別layerでmissする」という無駄が起きるため、そのidle capacityを再利用する狙いである。

### 5. 誤予測時は`priority transfer`で補正する

ECEはnative routerの実要求とRPP予測を比較し、予測外expertを検知すると、そのweightを高priorityでCPU→GPU transferする。

同時に、すでにGPUで実行中のexpert計算は止めず、transferを重ねる。

したがってRPP accuracyが低くても結果は正しく、**悪化するのは主にlatency / PCIe traffic**である。

### 6. `Dual-Batch Pipeline`：次batchのRPP / TSを現在batch計算へ隠す

RPPやtoken clusteringを逐次実行すると、そのCPU処理が新しいoverheadになる。

そこで現在batchをGPUで推論している間に、次の2 batchについてRPP / TSをCPU側で進める。

この **Dual-Batch pipeline** によりprediction / scheduling overheadをcritical pathから外す。

TSのCPU処理は10 ms未満と報告される。

### 7. Predictor単体ではなく3要素のjoint optimization

ExpertFlowの重要点は、

- RPPだけ → 先読みはできるがbatch内expert scatteringは残る
- TSだけ → expert集合は減るが未来cache準備がない
- ECEだけ → cache枠は賢く使えるが需要予測が弱い

ため、3つを一体で使うことにある。

## 評価

### まず見るところ
- **結論:** routing予測・token再編成・cache再配置を統合すると、CPU expert offloadのmiss待ちを大幅に減らせる。
- **実速度:** SwitchでSE-MoE比最大9.99倍、Mixtral/Qwen/DeepSeekでもCache-MoE比約2倍。
- **品質:** native expertへ補正するlossless構成。
- **メモリ:** Switch-128でGPU expert memory 15.26 GB→1.03 GBなど大幅削減。
- **注意点:** RPPの学習、token/KV reindex、単一A40中心の評価が必要条件。

### 実機とモデル

| 項目 | 設定 |
|---|---|

| Workloads | Alpaca、WMT16、XSUM、AIME2024 |

### Switchでのspeedup

cache=16、batch=32。

| Model | vs SE-MoE |
|---|---:|
| Switch-32 | 2.01倍 |
| Switch-64 | 3.19倍 |
| Switch-128 | **5.86倍** |

Switch-128のcacheを16→4へ縮めるとspeedupは**9.99倍**まで増える。

cacheが小さいほどbaselineのmiss penaltyが増え、predictive cachingの相対利得が大きくなる。

### 他MoEでのCache-MoE比

| Model | 最大speedup |
|---|---:|
| Mixtral-8x7B | 1.99倍 |
| Qwen1.5-MoE | **2.12倍** |
| DeepSeek-MoE | 1.94倍 |

SE-MoE / Pre-gated MoEはrouter実装の都合でこれらmodelへ対応せず、比較baselineがCache-MoE中心になる点に注意。

### Cross-domain RPP

Alpacaで学習したRPPをQwenのXSUM / WMT16へ移す。

| Task | Speedup（cache4 / batch16） |
|---|---:|
| XSUM | 2.21倍 |
| WMT16 | 2.18倍 |

predictorをtaskごとに完全再学習しなくても一定の汎化を示す。

### GPU memory

| Model | All-in-GPU | ExpertFlow |
|---|---:|---:|
| Switch-128 | 15.26 GB | **1.03 GB** |
| DeepSeek | 31.35 GB | **6.38 GB** |
| Qwen | 35.21 GB | **6.52 GB** |
| Mixtral-8x7B | OOM | **15.99 GBで完了** |

### Component-level結果

| Component | 結果 |
|---|---:|
| RPP prediction accuracy | 最大95% |
| TS追加throughput | 最大16.19%改善 |
| ECE cache hit rate | **91.96%** |
| ECE vs LRU hit-rate改善 | 最大61.15% |

headline speedupはこの3要素の合算であり、RPP accuracyだけで決まるわけではない。

### 評価上の制約

- RPP学習が必要。
- 2 batch単位のtoken / KV reindex実装が必要。
- 単一A40中心で大規模Expert Parallelは未評価。
- Mixtral等では比較baselineが限定される。
- SSD / NVMe tierは評価していない。
