# LazyLLM: Dynamic Token Pruning for Efficient Long Context LLM Inference

> 長文入力で重要トークンだけを層ごとに選び、後段で再活性化も許す動的token pruningにより推論を高速化する手法。

## 概要
LazyLLMが狙うのはモデル重みの圧縮ではなく、長い入力を読む最初のforwardの計算量である。入力全体を短い要約へ変換する方式と違い、元のtoken indexを維持しているため、後続の質問に必要な証拠を捨てたときの不可逆誤りを避けられる。これは追加パラメータを学習できない公開checkpointや、タスクごとに再訓練できないサービスで特に有用である。
（補足）本研究の可逆性は、初回に決めた固定トークン集合を使い続ける方式と異なり、生成ステップごとに必要な証拠を回復できる点にある。実際の速度は疎行列対応やキャッシュ管理に左右される。
長いプロンプトでは、最初のトークンを出すprefill（TTFT）がボトルネックになる。Llama 2 7BではLongBench上、最初のトークン生成が各decodeステップの約21倍の壁時計時間で、全生成時間の23%を占める。LazyLLMは「次トークンに全入力トークンは必要か」という問いに対し、入力を一括削除するprompt compressionではなく、各生成ステップ・各層で必要なトークンだけを計算する学習不要の動的トークンpruningを提案する。重要度は次トークンに対する各headのattention重みを平均した値で、低いトークンを層ごとに段階的に除外する。一度除外したトークンも後のステップで再選択できるため、固定圧縮より情報を回復しやすい。LongBenchの16データセット・6タスクでLlama 2/XGen 7Bを同一checkpointのまま評価し、多文書QAのTTFTを最大2.34倍（XGen 2.65倍）、精度低下1%以内という結果を示した。長文理解、要約、few-shot、合成タスク、コード補完のいずれでも、推論品質を大きく損なわず初回応答を短縮できる点が貢献である。
## 手法のあらまし
各層のattention mapを計算するためのコストも考慮し、pruningは疎なtoken選択が効く層に限定する。top-k percentileは一度の固定閾値ではなく、現在の入力長と層分布に応じて毎回変わる。Aux Cacheにより再計算を避ける代わりに、選択tokenのindexをcache間で一貫して管理する必要がある。
prefillを含む各生成ステップで、層lのattention行列から「次トークンが入力トークンiを見る確率」をhead平均し、層ごとのkパーセンタイルを閾値にする。上位トークンだけを残し、後段ほど保持率を低くするprogressive pruning（例: 前半は多く、後半は少なく）を行う。pruning位置・層数・削除率をパラメータとして速度と精度を制御できる。難所は、ある層でKVを作らなかったトークンが次のdecodeステップで再び必要になることだ。単純に最初の層から再計算すると計算が重複するため、LazyLLMは通常のKV cacheとは別にAux Cacheを置き、各層で削除されたトークンのhidden stateを保存する。後で復活したトークンは前層のAux Cacheから読み、各トークンを各層で高々一度だけ計算する。この設計により、最悪時でも標準推論より遅くならない。attentionのKVは将来トークンへの文脈として必要なため、pruneしても再利用可能な状態を保持する。実装はモデル重み・追加学習なしで既存decoderに差し込める。
## 評価
実測ではTTFTと全生成の寄与を分けて読む必要がある。要約のprompt token計算率は99.59%で全体速度1.02倍、合成タスクは63.73%で1.79倍だったため、decode比率が高いタスクほどprefill削減の効果が薄い。
NVIDIA A100で5回warm-up後に壁時計を測定。Llama 2 7Bの標準値に対し、LazyLLMは単一文書QAでTTFT 1.36倍・score 25.59（25.79）、多文書QA 2.34倍・22.31（22.43）、要約1.46倍・24.75（24.65）、few-shot 2.19倍・62.81（62.90）、合成2.89倍・4.98（4.97）、コード補完1.94倍・53.30（55.18）。XGen 7Bでは多文書QA2.65倍、合成4.77倍、コード3.47倍で、精度も概ねベースライン同等だった。prompt compressionは圧縮自体にLLMを走らせるためTTFTが0.12〜0.20倍（実質遅延）となり、random drop/static pruningは速度の割に精度を失う。全生成ではLlama 2のprompt token計算率が63.7〜99.6%、速度1.02〜1.79倍、XGenは40.5〜96.1%、1.09〜3.16倍。多文書QAの2.34倍設定は性能劣化1%以内、さらに強く削れば3倍・劣化10%以内も可能だった。限界はattention map・Aux Cache・不規則なtoken集合の管理オーバーヘッド、削り過ぎによる情報欠落、モデル・タスクごとのpruning位置/率調整である。後段pruningほど安全だが、GPUの密行列カーネルでは理論計算削減がそのまま速度にならない。
