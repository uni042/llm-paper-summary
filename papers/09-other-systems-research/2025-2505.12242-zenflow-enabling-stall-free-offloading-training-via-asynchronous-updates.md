# ZenFlow: Enabling Stall-Free Offloading Training via Asynchronous Updates

> 重要な勾配だけをGPUで即時更新し残りをCPUで非同期蓄積・更新して、LLM fine-tuningのoffload stallを抑える方式。

## 概要
ZenFlow は、GPU メモリに収まらない LLM の fine-tuning を CPU オフロードで継続しながら、CPU 更新待ちで GPU が止まる問題を、パラメータ／勾配の重要度に応じた非同期更新へ組み替えるフレームワークである。従来の ZeRO-Offload は勾配を GPU から CPU へ送り、全パラメータを CPU optimizer で更新してから更新済みパラメータを戻すため、GPU の高速な forward/backward と CPU の低速な optimizer が直列化される。Llama2-7B の例では BF16 のパラメータ14GB、勾配14GB、Adam 系 optimizer state 28GBで合計56GBとなり、単一 GPU の容量を超える。4×A100 でオフロードを有効にすると step が約0.5秒から7秒へ14倍に伸び、CPU 更新は128スレッドでも約4,600ms、PCIe 4.0×16の実効帯域約28GB/sでは片方向14GBの転送に約500msを要する。ZenFlow は top-k の重要勾配を GPU に残して直ちに更新し、残りを CPU に送って複数 step 蓄積する。従って activation は通常どおり GPU の forward/backward 用一時状態として扱われ、NVMe SSD へ常時退避する方式でも、GDS direct I/O を使う方式でもない。主対象は optimizer state、勾配、パラメータの CPU DRAM–GPU 間経路であり、GPU の演算帯域と CPU の容量を異種資源として役割分担する。Qwen2.5-0.5B/Alpaca52K では勾配上位1%が勾配ノルム二乗の88.9%を占める観測を出発点に、少量の重要チャネルだけを頻繁に更新しても学習信号を保てることを示す。さらに分散 shard 上での全勾配収集を避ける局所選択を導入し、単なる勾配圧縮ではなく、全勾配を捨てずに更新時期をずらす点が特徴である。論文はこの設計を「stall-free」な CPU–GPU パイプラインとして実装し、3.6〜5倍の end-to-end 高速化と精度維持を狙う。
## 手法のあらまし
各重み行列の入力チャネルごとに勾配ノルム二乗を集計し、全勾配を AllGather せず列ノルムの要約だけを GPU 間で交換する。Llama2-7B の q_proj（4096×4096）では、BF16勾配行列を集める代わりに4096次元・16KBのベクトルを共有し、選択の量を O(nm) から O(m) へ縮小する。この例の通信は4,000倍超減る。空間的局所性（上位1%勾配の60〜90%が上位10%チャネルに集中）と時間的局所性（上位10%チャネルを100 step追跡すると上位1%勾配の95%以上を保持）を利用して選択 index を再利用する。重要勾配は GPU の selective Adam/AdamWで in-place 更新し、非重要勾配はCPUへ送り捨てず、S=4程度の複数 stepで蓄積してからCPUで更新する。遅延側勾配エネルギー比ρ≈0.1、S=4なら、理想同期SGDに対するstaleness係数は√1.4≈1.18となる。CPUは二つの勾配bufferをdouble bufferingし、片方で当期データを受けながらもう片方で前周期のoptimizer更新を実行する。専用プロセス、I/O bucket、shared memoryでCPU処理を並列化し、GPUのforward/backwardと重ねる。GPU側 selective-optimizer のstateはlayer-wiseに一層ずつswap out/inして常駐量を抑える。Zen-autoは初期warm-upを同期更新にしてstale化を防ぎ、後半は勾配ノルムを監視して間隔を1〜2から4〜5へ広げる。top-k=10%、S=4なら、ZeRO-Offloadの毎回2M（勾配M＋更新パラメータM）に対し平均1.125Mで、PCIe trafficを理論上ほぼ半減できる。activation stateの再計算、NVMe SSD、GDS direct I/Oは扱わず、CPU DRAM–GPU HBMの経路を非同期化するのが本手法の範囲である。
## 評価

### まず見るところ
- **結論:** 重要勾配だけ毎step GPUで更新し、残りをCPUで遅延更新すると、ZeRO-OffloadのCPU optimizer待ちをほぼcritical pathから外せる。
- **学習速度:** ZeRO-Offload比平均約4.3倍、ZeRO-Infinity比平均約6.3倍と大きい。
- **品質:** **完全同期更新ではない近似**だが、標準設定ではGLUE/lossをほぼ維持。更新間隔を長くしすぎると精度低下が出る。
- **メモリ・I/O:** CPU DRAM↔GPUのgradient/parameter/optimizer経路。NVMe/GDS/activation offloadは対象外。
- **評価の強さ／注意点:** **4×A100/H100実機＋DeepSpeed実装**。高速化はCPUがoptimizer bottleneckになる条件で大きく、consumer CPUへそのまま外挿できない。

評価は実機で行い、標準は4×A100 80GB（NVLink、64コア128スレッドCPU、CPU memory 1TB、PCIe 4.0×16）、比較に4×H100 80GB（同64コア級CPU、2TB、PCIe 5.0×16）を使う。OPT-350M、Qwen2.5-0.5B/1.5B/3B、Llama2-7B/13Bを、主に GLUE（MNLI、QNLI、QQP、SST-2）で3 epoch、batch 8、AdamW、学習率1e-5、5% warm-upでfine-tuneし、別途Llama-2/Alpaca-52Kも示す。baselineはZeRO-Offload（Stage 2）、ZeRO-Infinity（Stage 3だがNVMe offload無効）、StrongHold、パイプラインを外したZenFlow*である。ZenFlowはZeRO-Offload比平均4.3倍、ZeRO-Infinity比平均6.3倍、構成別のstall分析で2.9〜5倍の速度を得た。CPU:GPU時間比は7B/13Bで12:1超から1:1以下となり、GPU stallは80〜85%以上減る。top-k=10%、S=4ではI/Oがほぼ半減し、列ノルム集約も6,000倍超の通信量削減、追加0.2秒未満/iterationだった。4 GLUE taskの精度はZeRO-Offloadと同等以上で、OPT-350Mのloss/accuracy曲線もほぼ一致する。ただし固定S=4はOPT-350Mの初期変化に粗く、S=16では3 epochで約0.02精度低下が出る。Zen-autoで調整できるが、追加GPU optimizer stateのためZenFlow*の最大対応モデルはやや小さい。CPU DRAM中心の評価で、NVMe SSD、GDS direct I/O、activation offload、低コアCPUやコンシューマGPU、広域異種ネットワークは未検証であり、最大5倍を個人環境へ外挿できない。
