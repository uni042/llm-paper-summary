# Comet: Fine-grained Computation-communication Overlapping for Mixture-of-Experts

> MoEのall-to-all通信をtile単位のGEMMと融合・重畳し、複数GPU学習／推論の通信待ちを隠すkernelランタイム。

## 概要
Cometは、分散MoEでexpert dispatch/combineのall-to-all通信がGEMMを待たせる問題を、**通信完了をtensor全体で待たず、準備できたGEMM tileから計算する**ことで隠すkernel/runtimeである。

モデル配置やexpert数は変えず、同じtensorを同じ精度で計算する。したがって量子化やpruningではなく、**GPU間通信とGEMMの実行順序を細粒度に組み替えるlossless最適化**である。

## 手法のあらまし

### 1. tensor全体ではなく`tile-level dependency`で待つ

通常はall-to-allが終わるまでGEMMを開始しない。Cometは依存関係をGEMM tile単位に分解し、必要なtoken/columnが到着したtileだけ先に実行する。

dispatch→GEMMでは主にM方向、GEMM→reduceではN方向に依存を分ける。これにより、あるexpertのtoken待ちの間に別expertの計算を進められる。

### 2. `thread-block specialization`

1つのfused kernel内でGPU thread blockへ役割を分ける。

| Blockの役割 | 処理 |
|---|---|
| communication block | tokenの送受信 |
| GEMM block | expert計算 |
| reduce block | combine/reduction |

別kernelを順番に起動するのではなく、**同じGPU上で通信担当と計算担当を同時に走らせる**のがポイントである。

### 3. `NVSHMEM`で細粒度通信する

GPU間のput/getはNVSHMEMを使う。大きなcollective完了を待つのではなく、必要なtileのdataだけをremote GPUから扱える。

### 4. `GroupGEMM`でexpertごとのtoken数の違いを吸収する

MoEではexpertごとのtoken数が揃わない。CometはCUTLASS GroupGEMMを使い、異なるGEMM shapeをまとめて処理する。

### 5. 通信blockと計算blockの比率をprofileする

通信が重いshapeとGEMMが重いshapeでは、GPU resourceの割当比率を変える必要がある。

Cometはmodel shape、token数、expert数、top-kに応じて、通信用blockと計算用blockの比率を選ぶ。したがって、完全にhardware-agnosticな固定kernelではない。

## 評価

### まず見るところ
- **結論:** all-to-allをGEMM tileと細粒度に重ねると、分散MoEの通信待ちをかなり隠せる。
- **速度:** 8×H800でend-to-end平均約1.7倍、単一layerでは最大約2倍級。
- **品質:** 実行順だけを変えるlossless system optimization。
- **対象:** NVLink/NVSHMEMを使うmulti-GPU環境。CPU/SSD offloadではない。
- **注意点:** 単一GPUにはall-to-allがないため、同じ利得は出ない。

### End-to-end

| 指標 | 結果 |
|---|---:|
| latency削減 | 約31.8〜44.4% |
| 平均speedup | 1.71倍 |
| 単一layer最大 | 1.96倍 |

### Shapeを変えた単一layer評価

| 条件 | Speedup |
|---|---:|
| token数 / expert構成変更 | 1.28〜2.37倍 |
| expert数 / top-k変更 | 1.16〜1.83倍 |
| PCIe bridgeを含む構成 | 1.19〜1.46倍 |

### 通信隠蔽率

| 実装 | 通信を隠せた割合 |
|---|---:|
| Comet | 最大86.5% |
| FasterMoE | 29.2% |
| Tutel | 68.6% |

### 追加memory

M=4096ではMixtral/Phiで約32MB、Qwenで約16MB。M=8192では概ね倍になる。追加memoryは比較的小さい。

### 制約

- NVIDIA GPU / NVSHMEM依存
- shapeが大きく変わると再profileが必要
- 異種GPUではload imbalanceを別途扱う必要がある
- CPU、NVMe、consumer VRAM不足は対象外
