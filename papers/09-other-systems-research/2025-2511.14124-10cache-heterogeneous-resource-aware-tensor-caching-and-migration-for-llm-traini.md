# 10Cache: Heterogeneous Resource-Aware Tensor Caching and Migration for LLM Training

> GPU・CPU・SSD間でtensorの再利用価値と移動コストを見積もり、LLM学習のcache配置とmigrationを動的に最適化する方式。

## 概要
10Cacheは、single-GPU LLM trainingでGPU・CPU DRAM・NVMeを単なるoffload先ではなく、**再利用時間の違う3段cache**として扱うシステムである。

parameter、gradient、optimizer state、activationを同じ規則で追い出すのではなく、次に使われる時刻とtensorの役割を見て配置を変える。

たとえば直近で使うparameterはGPUへ残し、optimizer stateはCPUへ優先し、それでも入らないcold tensorだけNVMeへspillする。

TERAIOのGDS direct pathとは違い、NVMeからGPUへ戻すときはCPU bufferを経由する。

## 手法のあらまし

### 1. `dry-run execution table`

最初に1回modelをdry-runし、各tensorについて、

- 実行順
- サイズ
- いつ使われるか
- active window

を記録する。

LLM training graphが比較的静的であることを利用し、次iteration以降のprefetch予定を事前に作る。

### 2. `active window`

各tensorについて、次に使う直前〜使用終了までのGPU必須区間をactive windowとして扱う。

この区間に近いtensorはGPUに残し、遠いtensorほどCPU/NVMeへ追い出しやすくする。

### 3. tensor種類ごとに優先tierを変える

10Cacheは単純なLRUではない。

| Tensor | 優先配置 |
|---|---|
| 直近parameter | GPU |
| optimizer state | CPU DRAM |
| cold parameter/state | NVMe |
| temporary/activation | lifetimeに応じてGPU/CPU |

つまり、再利用距離だけでなく**tensorの役割と更新場所**もplacementに使う。

### 4. size-aware buffer pool

CPU pinned bufferとGPU free-listはtensor sizeごとに前確保し、毎回malloc/freeしない。

これによりallocation overheadとfragmentationを減らす。

### 5. hookベースのscheduler

wall-clock timerで「そろそろprefetch」と判断するのではなく、実際のlayer pre/post hookで進行位置を検知する。

OS jitterやiteration時間の揺れがあっても、model execution sequenceに同期してevict/prefetchできる。

### 6. optimizer step専用prefetch

optimizer stateはforward/backwardとは別の再利用パターンを持つ。

10Cacheは現在更新中のstateをCPUに残し、次に更新するstateをNVMe→CPUへ先読みする。CPU optimizer updateとNVMe readを重ねることで待ち時間を減らす。

### 7. NVMe経路

10CacheのNVMe経路は、

`NVMe → CPU temporary buffer → GPU`

である。GPUDirect StorageでGPUへ直接読む方式ではない。

その代わりGPU/CPU cache hitを上げ、そもそもNVMeへ落とすtensor数を減らす方向で最適化する。

## 評価

### まず見るところ
- **結論:** parameter/optimizer/activationを同じoffload規則で扱わず、再利用時期に応じてGPU→CPU→NVMeへ置くとsingle-GPU trainingの待ち時間を減らせる。
- **学習速度:** ZeRO-Infinityより2倍前後、model/条件によってさらに大きい改善。
- **cache:** NVMe spillを必要最小限にし、GPU/CPU cache hitと利用率を上げる。
- **I/O:** NVMe→CPU temp→GPUの通常staging経路。GDSではない。
- **注意点:** 静的execution graphとsingle-GPUを前提にし、最終収束品質は主評価外。

### ZeRO-Infinity比

OPT/BLOOM/Falcon-7Bでは、10Cacheのparameter+memory最適化構成がZeRO-Infinity比で概ね**約2倍**のtraining時間短縮を示す。

GPT-2 5.9Bでは、

| GPU | ZeRO比speedup |
|---|---:|
| L40S | 2.60倍 |
| A100 | 2.82倍 |

### 他systemとの比較例

GPT-2 5.9BではStrongHold比でL40S 2.44倍、A100 4.17倍。

BERT/A40の特定条件では、三層cache構成がZeRO三層offloadより大幅に短いiteration timeを示す。ここは極端なbaseline差を含むため、一般的な「19倍高速」として読むより、**ZeRO側でNVMe missがほぼ毎回発生する条件をcache hitで避けた例**として読むのが適切である。

### Cache hit / NVMe spill

| 指標 | 傾向 |
|---|---|
| cache hit | modelにより大幅改善 |
| NVMe parameter数 | 約2.1〜6.7倍削減 |
| miss rate | 1%未満の条件あり |
| ZeRO miss | 約100%に近い条件あり |

### Resource utilization

OPT-13Bでは、

| System | CPU util | GPU util |
|---|---:|---:|
| ZeRO | 38% | 68% |
| 10Cache | 82% | 90% |

I/O待ちを減らし、CPU optimizerとGPU computeをより連続的に動かせている。

### Overhead

| 項目 | Epoch比 |
|---|---:|
| profile | 約1.09% |
| cache前確保 | 約3.83% |

### 制約

- static execution graph前提
- single-GPU中心
- NVMeはCPU staging経由
- MoE routingの動的変化は対象外
- 最終task accuracy/長期収束は主評価ではない
