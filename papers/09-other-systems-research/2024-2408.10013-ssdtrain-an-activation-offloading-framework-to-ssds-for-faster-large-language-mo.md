# SSDTrain: An Activation Offloading Framework to SSDs for Faster Large Language Model Training

> 学習時activationをNVMe SSDへ非同期退避・先読みし、GPUDirect StorageでGPUメモリと再計算を減らすシステム。

## 概要
SSDTrainは、LLM trainingでforward時に生成されるactivationをGPUメモリへ保持し続ける代わりに、**backwardまで使わないactivationをNVMe SSDへ一時退避する**システムである。

対象はexpert weightやKV cacheではなく、**学習時activation**。目的も「SSDを使って推論を高速化する」ことではなく、activation checkpointingによる再計算を減らしながら、GPU memoryを空けて大きなmicrobatchを使えるようにすることにある。

性能上の中心はGPUDirect Storage（GDS）で、GPUとNVMe間の転送をCPU DRAM経由にしない。論文では複数Optane SSDのRAIDを使い、I/Oをforward/backward計算の裏へ隠している。

## 手法のあらまし

### 1. activationの`lifetime`を見てoffload対象を決める

全activationを無条件にSSDへ書くわけではない。

SSDTrainは各tensorについて、

- サイズ
- forwardで生成されてからbackwardで使われるまでの生存時間
- 再利用回数

を追跡し、**長くGPUメモリを占有する割に、すぐには使わないactivation**を優先してoffloadする。

### 2. `tensor cache hook`

PyTorchのtensor保存・復元経路へhookを挿入し、framework本体を大きく改造せず、保存予定activationをSSDへ差し替える。

これによりBERT、GPT、T5のようにactivationの生存パターンが違うmodelでも同じ仕組みを使える。

### 3. deduplicationとview追跡

activationには、同じstorageを共有するviewや、実体が同じまま別tensorとして参照されるものがある。

SSDTrainはこの関係を追跡し、同じデータを何度もSSDへ書くことを避ける。これはSSD bandwidthだけでなく書込み量の削減にも効く。

### 4. 非同期writeとprefetch

forward中に、不要になったactivationをSSDへ非同期writeする。

backwardで使う直前には先読みしてGPUへ戻す。

概念的には、

`compute(layer n)` と `write/prefetch(layer n±k)`

を重ねる。I/Oが計算時間内に収まれば、step timeへの影響を小さくできる。

### 5. `GPUDirect Storage（GDS）`

GDS利用時は、GPU memoryとNVMeの間を直接転送する。

| 経路 | 特徴 |
|---|---|
| GDS | GPU ↔ NVMeを直接転送 |
| CPU offloader fallback | GPU ↔ CPU DRAM ↔ NVMe |

fallbackでも正しく動くが、論文の主な性能結果はGDS＋高速NVMe RAIDに依存する。

### 6. SSDTrainが置き換えるもの

SSDTrainはactivation checkpointingと競合するだけではなく、併用も可能である。

つまり、

- activationを保持する
- 再計算する
- SSDへ退避する

の3つを、memory budgetとI/O帯域に応じて使い分けるための選択肢を増やす研究と考えると分かりやすい。

## 評価

### まず見るところ
- **結論:** activationをNVMeへ退避してbackward前に戻すことで、**step timeをほぼ増やさずactivation memoryを大きく減らせる**。
- **メモリ:** peak activationを概ね3〜5割削減し、同じGPU容量でmicrobatchを増やせる。
- **学習速度:** 主な価値は単純なspeedupではなく、**recomputeを減らしながらthroughputを維持すること**。
- **I/O:** GDS＋複数Optane NVMe RAID実機。consumer SSD 1台へそのまま外挿できない。
- **注意点:** SSD寿命はモデル推定で、長期実測ではない。

### 実験環境

| 項目 | 条件 |
|---|---|
| GPU | 2×A100 PCIe 40GB、NVLink |

| Framework | PyTorch 2.2.2、DeepSpeed、Megatron |

### activation memory削減

| Model系 | Peak activation削減の目安 |
|---|---:|
| BERT | 約34〜47% |
| GPT | 約28〜35% |
| T5 | 約28〜35% |

論文全体では最大約47%の削減を報告する。

### 実測offload量とwrite帯域

BERT系の代表構成では以下の規模をSSDへ書く。

| Hidden size | Offload量 | PCIe write bandwidth |
|---:|---:|---:|
| 8192 | 10.37 GB | 18.0 GB/s |
| 12288 | 12.85 GB | 13.8 GB/s |
| 16384 | 10.75 GB | 8.76 GB/s |

SSDTrainが成立するには、このI/Oが十分に計算と重なる必要がある。

### Throughputの意味

step timeはactivationをGPUに保持する構成とほぼ同等に保ちつつ、より少ないpeak memoryで動作する。

同じmemory budgetに揃えたactivation recomputation方式との比較では、特定のBERT構成でSSDTrainのthroughputが高くなる。

したがって、ここで重要なのは**「SSDを追加して何倍速くなったか」より、「再計算なしに大きなbatchを維持できたか」**である。

### batch拡大による二次効果

microbatchを増やせると、

- optimizer/update overheadの償却
- pipeline parallelのbubble削減

も期待できる。BLOOMの試算では、microbatchを増やすことでPP bubbleを11.5%以上削減できる条件が示される。

### SSD寿命と制約

| 項目 | 内容 |
|---|---|
| 想定write amplification | 2.5 |
| SSD寿命 | モデル上2年以上 |
| 実長期寿命試験 | なし |

さらに、FP16＋SGDを使った評価であり、一般的なAdam＋mixed precision構成と完全に同じmemory profileではない。SSD bandwidth不足時はI/Oがcritical pathへ露出する。
