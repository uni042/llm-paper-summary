# EfficientUICoder：UI画像と出力コードの双方向トークン圧縮

## 概要

本研究は、ウェブ画面の画像を入力してHTMLとCSSを生成するUI-to-Codeの推論費用を、画像側とコード側の両方から削減する方式である。複数モダリティ大規模言語モデル（Multimodal Large Language Model、MLLM）は画像を多数の視覚トークンに変換してから言語モデルへ入力し、出力側では構造的に似たHTMLタグやCSS規則を繰り返し生成しがちである。前者は事前処理（prefill）の計算量を増やし、後者は自己回帰復号（autoregressive decoding）のステップ数を増やす。既存の画像トークン枝刈りは画面の小さなボタンや文字領域を失うことがあり、一般的な繰り返し罰則はHTMLで正当に繰り返されるタグを誤って抑制する。

EfficientUICoderは、(1)要素・配置を認識する視覚トークン圧縮（Element and Layout-aware Token Compression、ELTC）、(2)領域ごとの重要度補正（Region-aware Token Refinement、RTR）、(3)構文依存の適応的重複トークン抑制（Adaptive Duplicate Token Suppression、ADTS）の順に処理する。画面要素の領域と相互位置を保持しつつ入力を減らし、生成中のコード構造を追跡して過剰な繰り返しだけを抑える構成が新規性である。

原著v1の実験では、LLaVA-v1.6-34BとDesign2Codeを使い、無圧縮の推論全体160秒に対して82秒、事前処理1012ミリ秒に対して540ミリ秒、言語モデル部分の演算量184.1兆に対して101.5兆、生成トークン2041に対して1195を報告する。各々48.8%、46.6%、44.9%、41.4%の減少であり、「48.8倍の高速化」ではない。ここで60.36%という入力圧縮比は**残った視覚トークン数／元の数**であり、視覚トークンを60.36%削除した意味ではない。実測したGPUやベンチマークに依存する値として扱う。

## 問題設定と予備観察

対象の処理は、画像Iを視覚符号化器でパッチ表現へ変換し、投影器を通して言語モデルのトークン列に結合し、HTML/CSS文字列Cを生成する。視覚トークンが多いほど入力長nが伸び、注意演算の二乗項とフィードフォワード演算の線形項が増える。生成するコードが長いほど、次のトークンを得るために言語モデルを繰り返し起動する。したがって入力削減だけでは出力側の無駄を除去できず、出力削減だけでも最初の画像処理は軽くならない。

著者らはWebSight、Web2code、Design2Code、WebCode2Mを調べ、画像トークンとコードトークンが全トークン消費の90%超を占めると報告した。またCLIPの視覚注意を可視化し、背景など情報量が少ない領域にも注意が向く一方、画面要素の小領域が見落とされうることを確認した。これは「注意が小さいトークンを一律削除すればよい」という単純な基準がUIの構造保持には不十分であることを示す。

出力側の予備調査はLLaVA-v1.6-7B/34B、Design2CodeとWebCode2M、最大4096生成トークン、温度0、NVIDIA A800 80GB×4を用いた。重複の種類は、同一CSS宣言、同一HTML要素構造、本文文字列の繰り返しである。例えば同じCSSセレクタの宣言が増殖すると、見かけのコード長だけでなく実際の復号ステップが増える。場合によっては4096トークンの上限に達するまで繰り返し、画面後半の要素を出力できなくなる。著者らは手作業で重複事例を抽出しており、この予備調査は自動検出器の一般化性能を証明するものではない。

## 手法

### 1. ELTC：要素と配置を保持する入力選択

ELTCの入力は画面画像と視覚符号化器のトークン列である。まずUI要素検出器UIEDで文字、画像、ボタン、入力欄などの矩形領域を得る。単語ごとに細切れになった文字領域は距離しきい値で結合し、矩形の包含関係は大きい領域を採用し、部分的な重なりは外接矩形へ統合する。こうしてUIの意味単位に近い領域集合を作る。

次に、要素領域を頂点Vとし、二つの矩形境界間の最短ユークリッド距離を辺の重みとするグラフG=(V,E)を構築する。各辺の重みは w_ij = min_{p∈∂B_i,q∈∂B_j} ||p−q||₂ である。Kruskal法で総辺重みが最小の全域木を求め、画面要素間の主要な位置関係を少ない接続で表す。この木に基づいて保持する視覚領域を選ぶことで、背景の広い空白よりも、画面を構成する要素とその近傍を優先する。

この木はHTMLのDOMを直接生成するものではない。また、最小全域木を作っただけで画面のすべての視覚的意味が保存されるという数学的保証はない。検出器が小さな要素を見逃すと、後段でその要素を復元できない可能性がある。領域検出とグラフ構築の前処理費用も必要であり、画像の複雑さやUIEDの精度が実際の利得を左右する。

### 2. RTR：選択領域の過不足を視覚注意で補正

ELTCの選択集合Sにも入力欄の空白など不要なトークンが残り、非選択集合Uにも背景色や境界線など重要なトークンが残りうる。RTRは、視覚符号化器の注意行列をヘッド方向に平均したA_avgから、CLIPのCLSトークンが各画像トークンiへ向ける重み I_i = A_avg[CLS,i] を重要度の代理指標にする。

次にSの中で重要度が低い割合rのトークンを削り、Uの中で重要度が高い候補を選び直す。処理結果はELTCが保持した要素領域に限定されない修正済みの視覚トークン集合であり、言語モデルへの入力として使う。画面要素の位置関係という構造的手掛かりと、視覚符号化器が示す内容的手掛かりを両立させる意図である。

注意重みは必ずしも下流のHTML生成に対する因果的重要度ではない。視覚符号化器のCLSに依存するため、CLSを持たない視覚符号化器や異なる画像分割方式へ同じ式を無変更で適用できるとは限らない。また選択集合のサイズと交換率rの実装詳細を正しく設定しないと、重要領域の欠落や圧縮不足を招く。著者はrを感度分析しているが、すべての画面解像度に対する普遍的最適値を保証していない。

### 3. ADTS：HTML/CSS構文に基づく復号中の重複抑制

ADTSは言語モデルが出力する各トークンを順次受け取り、現在がCSSの`<style>`領域かHTMLの`<body>`領域かを状態機械で判定する。CSSではセレクタ、プロパティ、値、セレクタとプロパティの組を別々に数え、HTMLではタグ、属性、値、内容の組を追跡する。単純な文字列頻度だけでなく、構文上の単位を追う点が、同じ`div`タグが正当に多数現れる通常のUIコードと異常な複製を区別する狙いである。

復号中のロジットz_iに対して、反復回数c、減衰率λ<1、罰則を適用する後続ステップ数sを使い、原著式(9)は z̃_i = z_i·λ^c と定義する。反復が多いほど係数は小さくなり、続くs個のトークン候補を抑制する。実装ではどの構文パターンを反復と数え、どの候補ロジットに罰則をかけるかが重要である。負のロジットに正の係数を掛けると数値的には0へ近づくため、式を見ただけで**すべての候補の確率が必ず下がる**とは断定できない。原著の意図は繰り返し候補の相対選択確率を減らすことであり、正確な挙動は他候補との比較と実装に依存する。

ADTSは学習済み重みを変更するのではなく復号の選択分布を調整する。したがって追加学習を要さない一方、構文解析と反復カウンタの状態保持、毎ステップの罰則計算が増える。正常なナビゲーション要素の反復や意図的なCSS共通規則まで過剰に罰するとコードが欠落する。著者の感度実験ではs=3、λ=1/2が良好で、sを過度に増やすと過剰抑制になることを示す。

### 4. 端から端までの処理とシステム上の位置付け

一つの要求では、画像からUIED領域を抽出し、最小全域木で要素関係を構築してELTCが候補視覚トークンを選ぶ。RTRがCLIP注意に基づいて選択を補正し、その縮約系列をMLLMの言語モデルへ渡す。言語モデルの事前処理では縮約入力に対してKVキャッシュを生成する。復号ではADTSがHTML/CSS構文を逐次解析し、反復パターンに応じて次トークンのロジットを調整する。出力は短く、構造の重複が少ないHTML/CSSとなることを狙う。

この方式は重み量子化やKVキャッシュの外部退避ではない。削減対象は**入力の視覚トークン数と出力の生成トークン数**であり、モデル重みの常駐VRAMを直接小さくする設計ではない。LLaVA-v1.6-34Bのような大規模モデルを12GB級GPUへそのまま収める技術でもない。画面生成という特定の構造化出力を利用するため、一般の自由文生成へ同じADTS規則を移植することもできない。

## 評価環境と代表的な定量結果

原著v1はLLaVA-v1.6-7B/34B、Linux、NVIDIA A800 80GB×4、温度0、乱数種2026、最大4096出力トークンを使用した。Design2Codeは実在ウェブ画面484例、WebCode2Mは長さ別の集合から選んだテスト画面を使用する。比較対象は無圧縮（Vanilla）、無作為選択（Random）、FastV、Pdrop、VisionZipである。画像トークン削減方式の比較では入力トークン比を同程度に揃えている。

| Design2Code・34B・生成トークン | 2,041 | 1,195 | 41.4%減。短い出力が復号時間に寄与。 |
| Design2Code・34B・事前処理 | 1,012 ms | 540 ms | 46.6%減。画像処理を含む定義と測定系を原著に準拠。 |
| Design2Code・34B・全体推論 | 160 s | 82 s | 48.8%減。単純な処理速度比なら約1.95倍。 |
| WebCode2M・34B・言語モデルFLOPs | 195.0兆 | 111.6兆 | 42.8%減。 |

品質は単一の「正答率」ではなく、描画画像のブロック一致、文字、位置、色、CLIP類似度、およびコードのBLEUで測る。Design2Code・34Bでは、ブロック一致は無圧縮0.5516に対して0.5318と**低下**する一方、CLIP類似度は0.7343から0.7864へ改善する。BLEUは0.2914から0.2547へ低下する。したがって「すべての品質指標を完全維持した」とは言えず、特定の視覚品質指標の改善と他指標の悪化が共存する。WebCode2M・34Bでもブロック一致0.4688から0.4382、文字一致0.8207から0.7533へ低下する一方、色一致は0.5546から0.5313へ低下し、CLIPは0.7554から0.7270へ低下する。平均的な「同等品質」という著者の総括を、個別指標の完全同等と読み替えてはならない。

冗長な出力の検出数（RS）は、Design2Code・7Bで148件から64件、WebCode2M・7Bで39件から15件へ減った。34BではDesign2Codeで136件から16件、WebCode2Mで33件から2件となる。これは異常反復を減らすというADTSの直接的な効果を支えるが、出力がすべて構文的に正しいという保証ではない。人手評価ではDesign2CodeとWebCode2Mから各50画面を抽出し、5名の評価者による多数決で描画品質を比較している。大規模な人間評価ではなく、評価者間一致度や別業務への一般化には留保がある。

## 構成要素除去・パラメータ感度

原著表4はWebCode2M・7BにおけるELTC/RTR/ADTSの構成要素除去を示す。無圧縮C0のCLIP類似度0.7123、BLEU 0.1190、全体37秒に対して、全部を有効にしたC4はCLIP 0.7393、BLEU 0.1338、32秒である。ADTSを外したC3ではBLEU 0.0890、全体45秒となり、入力圧縮だけでは出力側の異常反復を抑えられないことが分かる。ただしC4のFLOPs 20.4兆に対してC1は20.1兆であり、**すべての指標でC4が最良ではない**。構成要素ごとの相互作用を考慮する必要がある。

抑制する後続トークン数sは1、3、5、10、減衰係数λは7/8、3/4、1/2、1/3を試している。sが小さすぎると反復を抑えきれず、大きすぎると正当な構文も抑える。著者が良好とした組合せはs=3、λ=1/2である。RTRの交換率rも調整対象であり、要素検出の精度や画面種類によって最適な交換割合は変わりうる。これらは著者のベンチマーク内での感度結果であり、モデルやUI言語を変えても固定値でよいという結論ではない。

## 既存手法との差

FastVは中間層の注意重みを使って視覚トークンを落とし、VisionZipは視覚符号化器の注意から優勢トークンを選び、Pdropは段階ごとに類似度を使ってトークンを削減する。いずれも画像トークンの冗長性に注目するが、HTML/CSSの構文的な重複まで扱うわけではない。EfficientUICoderは、UI要素の空間的な関係を先にモデル化し、注意に基づく補正を加え、さらに生成段階の反復を独立に制御するため、画像入力とコード出力の二つの律速へ作用する。

汎用の反復罰則と比較しても、構文解析でセレクタやタグ・属性・内容の組を数える点が異なる。一方、この専用性は対象範囲の狭さでもある。一般的な対話モデルのテキスト生成、動画の長文脈注意、KVキャッシュ管理やMoE専門家配置などを直接高速化する方式ではない。推論システム全体の新しいスケジューラやメモリ割当機構を提案したものでもない。

## 限界・負の結果・再現上の注意

第一に、品質指標の一部は無圧縮より悪化する。入力削減による細かなレイアウトや文字の欠落、ADTSによる必要な繰り返しの抑制は潜在的な失敗条件である。原著の品質「維持」は、全指標で非劣性を統計的に証明した意味ではない。第二に、画像領域検出、最小全域木、注意集約、構文解析は追加の処理を必要とする。言語モデルの演算量削減値は視覚符号化器や前処理を含む機器全体の電力削減率を直接表さない。

第三に、評価は画面画像からHTML/CSSを生成するタスクに集中する。複雑な動的JavaScript、複数ページの状態遷移、モバイルアプリ、別のマークアップ言語、ブラウザ実行環境差について同じ改善を示したものではない。第四に、34Bモデルは4枚の80GB GPUを使った環境であり、12GB GPU単体での導入可否を示す結果ではない。第五に、v1の数値は指定された乱数種と温度0、最大出力長4096という設定のもとで得られた。生成長上限やサンプリング設定を変えると、異常反復とADTSの利得が変わりうる。

第六に、原著v1の一部の記述は「圧縮率」を残存トークン比として定義している一方、文章上は削減率のようにも読める。本文の60.36%、55.86%は式R=C_compressed/C_originalに従い、残存割合として扱った。第七に、ADTSのロジット乗算式はロジットの符号に依存した解釈上の注意があり、著者の説明する単調な確率低下を一般のロジット全域へ無条件に拡張しない。第八に、2026年の著者リポジトリには追加の評価スクリプトが存在するが、本稿で照合した実験値は**2025年9月15日公開のarXiv v1**に固定しており、後続版の数値を混在させていない。
