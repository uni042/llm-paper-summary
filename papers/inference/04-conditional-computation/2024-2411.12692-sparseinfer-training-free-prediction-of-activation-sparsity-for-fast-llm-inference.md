# SparseInfer: Training-free Prediction of Activation Sparsity for Fast LLM Inference

> ReLU化FFNのzero行を入力・重みの符号bit XORだけで学習なし予測し、行単位GEMV スキップへつなぐSparseInfer。

## 概要

LLMのデコードでは、バッチが小さいと大きな重み matrixをGPU メモリから何度も読むことが律速になりやすい。FFNはTransformer 層の大きな計算・重み 通信量を占め、論文のJetson Orin上Llama2-13B profileではデコード時間の62%がMLP、38%がself-注意機構だった。

ここで**活性値 sparsity**を利用すると、入力によって「このFFN中間neuronは今回0になる」と分かった行の重みを読まず、inner product自体をスキップできる。Weight 枝刈りと違い、モデルから固定重みを削除するのではなく、リクエスト/トークンごとに実行しない行が変わるconditional computationである。

ただしLLaMA等が標準で使うSiLUは、負入力も小さな非zero値を返すため自然なexact zeroが少ない。ReLUへ置き換えて軽くfine-tuneする**ReLUfication**やProSparseは、FFN活性の約90%を0にできる。しかしzeroになるかどうかは (XW_{ゲート}) を計算してReLUへ通した後に初めて分かる。計算後にzeroだと知っても、そのゲート GEMVに必要な重み readはもう支払っている。

DEJAVU/PowerInfer系は、小型neural ネットワーク predictorを各層に持ち、zero patternをGEMV前に予測する。これなら重みをスキップできるが、predictor自体の学習、重み メモリ、FP演算が追加される。モデルを量子化し直した場合などにpredictorの再学習が必要になる点も運用コストになる。

SparseInferは「ReLUで必要なのは内積の正確な値ではなく**符号が負かどうか**だけ」という性質を使う。入力vectorと重み 行の各要素についてsign bitだけをXORし、「正の積」と「負の積」の個数を数える。負積が十分多ければinner productも負になる可能性が高いとみなし、その行を最初からスキップする。値の乗算を一度も行わず、bit operationだけでsparsity predictorを作る点が中心である。

Jetson Orin AGX 64GB、ProSparse-Llama2-7B/13Bで、predictor 遅延はPowerInferの3.66倍高速、predictor メモリは4.38倍小さい。α=1.00では密 llama.cpp比13B 1.79倍・7B 1.74倍、PowerInfer比1.27/1.30倍。early 層だけα=1.03へ保守化するとaccuracy低下を平均0.27〜0.33 pointへ抑えつつ、7Bでもllama.cpp比1.59倍を維持する。

## 問題設定

### Gate-based FFNのどこをskipできるのか

LLaMA系のゲート FFNは概念的に

[
h_1=mathrm{ReLU}(XW_{ゲート}),quad
h_2=XW_{up},quad
h_3=h_1odot h_2,quad
Y=h_3W_{down}^{T}
]

と進む。

(h_1[i]=0)なら、同じindexの (h_2[i]) は最終的に (h_1[i]) と掛けて0になる。そのため対応する (W_{up}) の行を読む必要がない。また (h_3[i]=0)なら、(W_{down}) の対応行が出力へ寄与しない。

理想的には、ゲート computation前にzero indexが分かれば (W_{ゲート})、(W_{up})、(W_{down}) のメモリ アクセスとGEMV演算をまとめて減らせる。ProSparseでは約90%の活性値 sparsityがあるため、予測が十分正しければ大きな削減余地がある。

### 予測で一番危険なのはfalse zero

本当はnonzeroになるneuronを「zero」と誤予測すると、その寄与を完全に消してモデル 出力を変える。一方、本当はzeroになる行をnonzeroと予測しても余分な計算をするだけでaccuracyは壊れない。

したがってsparsity predictorでは単純accuracyより、**zeroと判定したものが本当にzeroであるprecision**を高く保つことが重要である。SparseInferのαはこの非対称なriskを調整する。

## 手法

### 1. Inner productの符号を「各積の符号の多数」で近似する

重み 行 (W_{ゲート,i}) と入力 (X) の内積は

[
sum_j X_jW_{ij}
]

である。各項の正確な大きさを計算すれば通常GEMVと同じコストになるため意味がない。

SparseInferは、XとWの値がおおむね0中心の対称分布を持ち、各積の大きさが極端に偏らないという観察を使う。各 (X_jW_{ij}) が正か負かだけを見て、負の項数 (N_{neg}) が正の項数 (N_{pos}) より多ければ、和も負になりやすいと近似する。

ReLUは負の内積を厳密に0へするため、「和が負」と予測した行をsparse候補にできる。

これは数学的に符号を保証する判定ではなく統計的近似であり、特にearly 層では値分布が0近傍へ集中して仮定が弱くなる。そのため後述のαで保守化する。

### 2. sign bitだけをXOR + popcountする

FP16/INT8等ではsign情報を最上位bitから取れる。積の符号は2つのsignが異なると負、同じなら正なので、各要素のsign bitにXORを取れば乗算なしで正負を判定できる。

SparseInferは32個のsign bitを1つの32-bit整数へpackする。重み側はモデル 読み込み時に一度だけpackし、デコード中は再作成しない。入力 Xだけトークンごとにpackする。

CUDA カーネルではpacked 重み signとpacked XをXORし、`__popc()`で1の個数、つまり負積数を32個まとめて数える。1 warpを1 重み 行へ割り当て、行全体のnegative countをwarp reductionする。

DEJAVUの小型MLP predictorがFP16行列演算を行うのに対し、SparseInferはbitwise XORとpopulation countへ置き換えるため予測 オーバーヘッドが小さい。

### 3. αで「どれだけ確信したらskipするか」を調整する

単純条件は (N_{pos}<N_{neg}) だが、SparseInferは

[
alpha N_{pos}<N_{neg}
]

を使う。

(alpha>1)にすると、負積がかなり多い行だけzero予測するため保守的になる。スキップできる行は減るがfalse zeroも減り、qualityを守りやすい。(alpha<1)ならaggressiveになりspeedを取りやすいが誤予測riskが上がる。

実測ではlater 層はprecision 99%以上が多い一方、early 層で誤差が大きかったため、論文は最初の20 層だけα=1.01〜1.03、残りを1.0とする簡単な層-specific calibrationを使う。

neural predictorの学習ではなく数回のtest 試行で決めるパラメータなので、量子化方式を変えてもsign bitを取得できる限り再学習を必要としない。

### 4. 予測sparsityだけでなくactual sparsityも後段で追加する

sign predictorは保守的にすると、一部の本当のzeroを取り逃がす。しかしゲート GEMV (h_1) を実際に計算した後なら、どのelementがReLUで0になったかは厳密に分かる。

SparseInferは、(W_{ゲート}) では予測でスキップできた行だけを省くが、その後の (W_{up}) や (W_{down}) では「predicted sparse ∪ actual sparse」を利用する。

したがってαを大きくしてゲート 予測を安全側にしても、後段では実測zeroを回収できる。評価でもactual sparsity利用（+AS）が特にconservative αで大きく高速化倍率へ寄与する。

### 5. Sparse GEMVをrow/warp単位に合わせる

各活性値 elementが重み matrixの1 行に対応するため、SparseInferは1 warpを1 行へ割り当てる。スキップ flagが立っていればそのwarpは重みを読まず即returnする。

不規則なelement-level sparsityでは読み込み balancingやindex gatherが複雑になるが、行全体をスキップするためwork granularityがwarpと一致しやすい。SparseInferが予測精度だけでなくCUDA executionへ落とし込める理由である。

### 6. kernel fusionは補助的、主利得はweight skip

(W_{ゲート})、(W_{up})、elementwise multiplyまでを1 CUDA カーネルへ融合すると入力 Xやintermediate vectorの読み込み/storeを減らせる。

ただしJetson Orin評価ではカーネル 融合の追加高速化倍率は小さかった。入力 vectorは巨大重み/キャッシュに比べ小さく、デコードの主コストは重み 通信量だからである。

このnegative resultは、SparseInferの実利得が「一般的な融合」ではなく**sparsity 予測による大きな重み GEMV 行 スキップ**から来ていることを示す。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| ハードウェア | NVIDIA Jetson AGX Orin 64GB |
| OS / CUDA | Ubuntu 22.04、JetPack 6.0 DP、CUDA 12.2 |
| models | ProSparse-Llama2-7B / 13B |
| engine | llama.cpp拡張 |
| 比較対象 | 密 llama.cpp、PowerInfer |
| performance ワークロード | GSM8K先頭10 samples |
| quality | GSM8K、BBH |
| execution | 全重みをGPU メモリへpreload |
| 主調整パラメータ | early 層のα=1.00〜1.03 |

### Predictor自体のcost

| 項目 | PowerInfer | SparseInfer | 差 |
|---|---:|---:|---:|
| 予測 operations | 1.94×10^7 | 2.211×10^6 | 約8.8分の1 |
| operation種 | FP16 multiply中心 | 32-bit XOR/popcount | 軽量bit演算 |
| 遅延 / トークン / 層 | 約256 µs相当 | 70 µs | 3.66倍高速 |
| 13B predictor メモリ | 1480 MB | 337.5 MB | 4.38倍小さい |

SparseInferのoperation削減比ほど遅延差が大きくないのは、PowerInferのFP16演算はTensor Coreを使える一方、XORはCUDA Core側で実行されるためである。

### End-to-end speed

| モデル / α | vs llama.cpp | vs PowerInfer | 意味 |
|---|---:|---:|---|
| 13B / 1.00 | 1.79倍 | 1.27倍 | aggressive 予測で最大speed側 |
| 7B / 1.00 | 1.74倍 | 1.30倍 | 同傾向 |
| 7B / 1.03 | 1.59倍 | 1.19倍 | quality優先でも利得を維持 |

論文headlineの「PowerInferより約21% faster」は保守設定を含む代表的なシステム比較で、最大値は条件別に異なる。

### αによるquality-speed trade-off

13BのGSM8K/BBH平均は比較対象 37.76に対し、α=1.00では35.33（-2.43pt）だが、α=1.03では37.49（-0.27pt）まで回復する。

7Bは比較対象 24.61に対し、α=1.00では18.16（-6.45pt）と大きく崩れるが、α=1.03では24.28（-0.33pt）となる。early 層での誤予測を保守化することがquality維持に不可欠である。

ランダムに90% 活性値をスキップした場合はaccuracy 0%になったと報告されており、「sparsityが90%あるから任意の90%計算を落としてよい」わけではない。どのneuronがzeroになるかを予測する必要がある。

## 既存研究との差

ReLUfication / ProSparseはモデルを高sparsityにする**モデル側の前処理**であり、それだけでは実行前にzero位置が分からない。SparseInferはそのReLU-fied モデルを高速実行するランタイム predictorである。

DEJAVU/PowerInferは入力依存sparsityを学習済みneural predictorで当てる。SparseInferは重み/入力のsign bitsだけを使い、追加predictor パラメータ・学習・大量FP演算をなくす。モデル 量子化が変わってもsign bitを取り出せれば適用可能という運用上の差もある。

TEAL/CATSのようにSiLU モデルを学習なしで閾値 sparsifyする方法とは、そもそも対象が異なる。SparseInferは高いexact zeroを既に持つReLU-fied LLMを前提に、そのzeroを**計算前に安く予測する**。

## 限界

SparseInferはReLU化され十分な活性値 sparsityを持つモデルが前提である。標準SiLU LLaMAへpredictorだけ付けても約90% zeroが自然に得られるわけではない。モデル側のReLUfication/ProSparseには別途微調整 コストがある。

sign多数決は各積の**大きさ**を捨てる近似なので、少数の大きな正積が多数の小さな負積を上回るケースを誤る。early 層でprecisionが悪化する観測はこの仮定の限界を示す。

また主要評価はJetson Orin、バッチの小さいon-device デコードである。datacenter GPUの大バッチではGEMM 形状やTensor Core利用率が変わり、行-sparse GEMVの相対利得が同じとは限らない。
