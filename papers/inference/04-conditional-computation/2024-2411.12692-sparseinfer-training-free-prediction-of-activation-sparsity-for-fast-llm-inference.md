# SparseInfer: Training-free Prediction of Activation Sparsity for Fast LLM Inference

> ReLU化FFNのzero行を入力・weightの符号bit XORだけでtrainingなし予測し、行単位GEMV skipへつなぐSparseInfer。

## 概要

LLMのデコードでは、batchが小さいと大きなweight matrixをGPU memoryから何度も読むことが律速になりやすい。FFNはTransformer layerの大きな計算・weight trafficを占め、論文のJetson Orin上Llama2-13B profileではdecode時間の62%がMLP、38%がself-attentionだった。

ここで**activation sparsity**を利用すると、入力によって「このFFN中間neuronは今回0になる」と分かった行のweightを読まず、inner product自体をskipできる。Weight pruningと違い、modelから固定weightを削除するのではなく、request/tokenごとに実行しない行が変わるconditional computationである。

ただしLLaMA等が標準で使うSiLUは、負入力も小さな非zero値を返すため自然なexact zeroが少ない。ReLUへ置き換えて軽くfine-tuneする**ReLUfication**やProSparseは、FFN活性の約90%を0にできる。しかしzeroになるかどうかは (XW_{gate}) を計算してReLUへ通した後に初めて分かる。計算後にzeroだと知っても、そのgate GEMVに必要なweight readはもう支払っている。

DEJAVU/PowerInfer系は、小型neural network predictorを各layerに持ち、zero patternをGEMV前に予測する。これならweightをskipできるが、predictor自体のtraining、weight memory、FP演算が追加される。modelを量子化し直した場合などにpredictorの再trainingが必要になる点も運用コストになる。

SparseInferは「ReLUで必要なのは内積の正確な値ではなく**符号が負かどうか**だけ」という性質を使う。入力vectorとweight rowの各要素についてsign bitだけをXORし、「正の積」と「負の積」の個数を数える。負積が十分多ければinner productも負になる可能性が高いとみなし、そのrowを最初からskipする。値の乗算を一度も行わず、bit operationだけでsparsity predictorを作る点が中心である。

Jetson Orin AGX 64GB、ProSparse-Llama2-7B/13Bで、predictor latencyはPowerInferの3.66倍高速、predictor memoryは4.38倍小さい。α=1.00ではdense llama.cpp比13B 1.79倍・7B 1.74倍、PowerInfer比1.27/1.30倍。early layersだけα=1.03へ保守化するとaccuracy低下を平均0.27〜0.33 pointへ抑えつつ、7Bでもllama.cpp比1.59倍を維持する。

## 問題設定

### Gate-based FFNのどこをskipできるのか

LLaMA系のgate FFNは概念的に

[
h_1=mathrm{ReLU}(XW_{gate}),quad
h_2=XW_{up},quad
h_3=h_1odot h_2,quad
Y=h_3W_{down}^{T}
]

と進む。

(h_1[i]=0)なら、同じindexの (h_2[i]) は最終的に (h_1[i]) と掛けて0になる。そのため対応する (W_{up}) のrowを読む必要がない。また (h_3[i]=0)なら、(W_{down}) の対応rowがoutputへ寄与しない。

理想的には、gate computation前にzero indexが分かれば (W_{gate})、(W_{up})、(W_{down}) のmemory accessとGEMV演算をまとめて減らせる。ProSparseでは約90%のactivation sparsityがあるため、予測が十分正しければ大きな削減余地がある。

### 予測で一番危険なのはfalse zero

本当はnonzeroになるneuronを「zero」と誤予測すると、その寄与を完全に消してmodel outputを変える。一方、本当はzeroになる行をnonzeroと予測しても余分な計算をするだけでaccuracyは壊れない。

したがってsparsity predictorでは単純accuracyより、**zeroと判定したものが本当にzeroであるprecision**を高く保つことが重要である。SparseInferのαはこの非対称なriskを調整する。

## 手法

### 1. Inner productの符号を「各積の符号の多数」で近似する

weight row (W_{gate,i}) とinput (X) の内積は

[
sum_j X_jW_{ij}
]

である。各項の正確な大きさを計算すれば通常GEMVと同じcostになるため意味がない。

SparseInferは、XとWの値がおおむね0中心の対称分布を持ち、各積の大きさが極端に偏らないという観察を使う。各 (X_jW_{ij}) が正か負かだけを見て、負の項数 (N_{neg}) が正の項数 (N_{pos}) より多ければ、和も負になりやすいと近似する。

ReLUは負の内積を厳密に0へするため、「和が負」と予測したrowをsparse候補にできる。

これは数学的に符号を保証する判定ではなく統計的近似であり、特にearly layerでは値分布が0近傍へ集中して仮定が弱くなる。そのため後述のαで保守化する。

### 2. sign bitだけをXOR + popcountする

FP16/INT8等ではsign情報を最上位bitから取れる。積の符号は2つのsignが異なると負、同じなら正なので、各要素のsign bitにXORを取れば乗算なしで正負を判定できる。

SparseInferは32個のsign bitを1つの32-bit整数へpackする。weight側はmodel load時に一度だけpackし、decode中は再作成しない。input Xだけtokenごとにpackする。

CUDA kernelではpacked weight signとpacked XをXORし、`__popc()`で1の個数、つまり負積数を32個まとめて数える。1 warpを1 weight rowへ割り当て、row全体のnegative countをwarp reductionする。

DEJAVUの小型MLP predictorがFP16行列演算を行うのに対し、SparseInferはbitwise XORとpopulation countへ置き換えるためprediction overheadが小さい。

### 3. αで「どれだけ確信したらskipするか」を調整する

単純条件は (N_{pos}<N_{neg}) だが、SparseInferは

[
alpha N_{pos}<N_{neg}
]

を使う。

(alpha>1)にすると、負積がかなり多いrowだけzero予測するため保守的になる。skipできる行は減るがfalse zeroも減り、qualityを守りやすい。(alpha<1)ならaggressiveになりspeedを取りやすいが誤予測riskが上がる。

実測ではlater layerはprecision 99%以上が多い一方、early layerで誤差が大きかったため、論文は最初の20 layersだけα=1.01〜1.03、残りを1.0とする簡単なlayer-specific calibrationを使う。

neural predictorのtrainingではなく数回のtest runで決めるparameterなので、量子化方式を変えてもsign bitを取得できる限り再trainingを必要としない。

### 4. 予測sparsityだけでなくactual sparsityも後段で追加する

sign predictorは保守的にすると、一部の本当のzeroを取り逃がす。しかしgate GEMV (h_1) を実際に計算した後なら、どのelementがReLUで0になったかは厳密に分かる。

SparseInferは、(W_{gate}) ではpredictionでskipできたrowだけを省くが、その後の (W_{up}) や (W_{down}) では「predicted sparse ∪ actual sparse」を利用する。

したがってαを大きくしてgate predictionを安全側にしても、後段では実測zeroを回収できる。評価でもactual sparsity利用（+AS）が特にconservative αで大きくspeedupへ寄与する。

### 5. Sparse GEMVをrow/warp単位に合わせる

各activation elementがweight matrixの1 rowに対応するため、SparseInferは1 warpを1 rowへ割り当てる。skip flagが立っていればそのwarpはweightを読まず即returnする。

不規則なelement-level sparsityではload balancingやindex gatherが複雑になるが、row全体をskipするためwork granularityがwarpと一致しやすい。SparseInferがprediction精度だけでなくCUDA executionへ落とし込める理由である。

### 6. kernel fusionは補助的、主利得はweight skip

(W_{gate})、(W_{up})、elementwise multiplyまでを1 CUDA kernelへfusionするとinput Xやintermediate vectorのload/storeを減らせる。

ただしJetson Orin評価ではkernel fusionの追加speedupは小さかった。input vectorは巨大weight/cacheに比べ小さく、decodeの主costはweight trafficだからである。

このnegative resultは、SparseInferの実利得が「一般的なfusion」ではなく**sparsity predictionによる大きなweight GEMV row skip**から来ていることを示す。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| hardware | NVIDIA Jetson AGX Orin 64GB |
| OS / CUDA | Ubuntu 22.04、JetPack 6.0 DP、CUDA 12.2 |
| models | ProSparse-Llama2-7B / 13B |
| engine | llama.cpp拡張 |
| baseline | dense llama.cpp、PowerInfer |
| performance workload | GSM8K先頭10 samples |
| quality | GSM8K、BBH |
| execution | 全weightをGPU memoryへpreload |
| 主調整parameter | early layersのα=1.00〜1.03 |

### Predictor自体のcost

| 項目 | PowerInfer | SparseInfer | 差 |
|---|---:|---:|---:|
| prediction operations | 1.94×10^7 | 2.211×10^6 | 約8.8分の1 |
| operation種 | FP16 multiply中心 | 32-bit XOR/popcount | 軽量bit演算 |
| latency / token / layer | 約256 µs相当 | 70 µs | 3.66倍高速 |
| 13B predictor memory | 1480 MB | 337.5 MB | 4.38倍小さい |

SparseInferのoperation削減比ほどlatency差が大きくないのは、PowerInferのFP16演算はTensor Coreを使える一方、XORはCUDA Core側で実行されるためである。

### End-to-end speed

| model / α | vs llama.cpp | vs PowerInfer | 意味 |
|---|---:|---:|---|
| 13B / 1.00 | 1.79倍 | 1.27倍 | aggressive predictionで最大speed側 |
| 7B / 1.00 | 1.74倍 | 1.30倍 | 同傾向 |
| 7B / 1.03 | 1.59倍 | 1.19倍 | quality優先でも利得を維持 |

論文headlineの「PowerInferより約21% faster」は保守設定を含む代表的なsystem比較で、最大値は条件別に異なる。

### αによるquality-speed trade-off

13BのGSM8K/BBH平均はbaseline 37.76に対し、α=1.00では35.33（-2.43pt）だが、α=1.03では37.49（-0.27pt）まで回復する。

7Bはbaseline 24.61に対し、α=1.00では18.16（-6.45pt）と大きく崩れるが、α=1.03では24.28（-0.33pt）となる。early layerでの誤予測を保守化することがquality維持に不可欠である。

ランダムに90% activationをskipした場合はaccuracy 0%になったと報告されており、「sparsityが90%あるから任意の90%計算を落としてよい」わけではない。どのneuronがzeroになるかを予測する必要がある。

## 既存研究との差

ReLUfication / ProSparseはmodelを高sparsityにする**モデル側の前処理**であり、それだけでは実行前にzero位置が分からない。SparseInferはそのReLU-fied modelを高速実行するruntime predictorである。

DEJAVU/PowerInferは入力依存sparsityを学習済みneural predictorで当てる。SparseInferはweight/inputのsign bitsだけを使い、追加predictor parameter・training・大量FP演算をなくす。model quantizationが変わってもsign bitを取り出せれば適用可能という運用上の差もある。

TEAL/CATSのようにSiLU modelをtrainingなしでthreshold sparsifyする方法とは、そもそも対象が異なる。SparseInferは高いexact zeroを既に持つReLU-fied LLMを前提に、そのzeroを**計算前に安く予測する**。

## 限界

SparseInferはReLU化され十分なactivation sparsityを持つmodelが前提である。標準SiLU LLaMAへpredictorだけ付けても約90% zeroが自然に得られるわけではない。model側のReLUfication/ProSparseには別途fine-tuning costがある。

sign多数決は各積の**大きさ**を捨てる近似なので、少数の大きな正積が多数の小さな負積を上回るケースを誤る。early layerでprecisionが悪化する観測はこの仮定の限界を示す。

また主要評価はJetson Orin、batchの小さいon-device decodeである。datacenter GPUの大batchではGEMM shapeやTensor Core利用率が変わり、row-sparse GEMVの相対利得が同じとは限らない。
