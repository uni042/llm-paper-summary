# LazyLLM: Dynamic Token Pruning for Efficient Long Context LLM Inference

> 長文入力で重要トークンだけを層ごとに選び、後段で再活性化も許す動的token pruningにより推論を高速化する手法。

## 概要
LazyLLMは、長文入力のすべてのtokenを全層で処理する代わりに、**その時点の生成に重要そうな入力tokenだけを後段へ通す**training-freeなtoken pruning手法である。

固定prompt compressionとの違いは、一度外したtokenを永久に捨てないこと。後のdecode stepで重要度が上がれば、そのtokenを再び計算経路へ戻せる。

この「再活性化」を成立させるために、LazyLLMは通常のKV cacheとは別に `Aux Cache` を持つ。pruneされたtokenの中間hidden stateを保存しておき、必要になったとき最初から再計算せず途中層から復帰する。

主な効果は長文prefillのTTFT削減で、A100実測では多文書QAでLlama 2 7Bが2.34倍、XGen 7Bが2.65倍のTTFT改善を示す。一方、decode支配のtaskでは全生成時間への効果は小さい。

## 手法のあらまし

### 1. `Dynamic Token Pruning`：層ごとに残すtokenを変える

各層のattentionから、現在の生成tokenが入力tokenをどれだけ参照しているかを計算し、重要度の低いtokenを次の層へ送らない。

固定のprompt compressionと異なり、**同じ入力tokenでも層やdecode stepによって残る／外れるが変わる**。

### 2. `Progressive Pruning`：後段ほど強く削る

浅い層から大量にtokenを捨てると、その後の表現形成に必要な情報まで失いやすい。

そこでLazyLLMは、前半層では多くのtokenを残し、後段へ進むほど保持率を下げる `progressive pruning` を使う。

pruning位置・削除率・対象層数がquality–latencyの主な調整ノブになる。

### 3. `Aux Cache`：pruneしたtokenを後で復活できるようにする

この論文で重要な固有機構が `Aux Cache` である。

あるtokenを層lでpruneした場合、そのtokenのhidden stateを保存しておく。後のdecode stepで再び必要になったら、最初の層からやり直さず、保存済み状態から計算を再開する。

これにより各token×layerの計算を高々1回程度に抑え、再活性化のコストを小さくする。

### 4. 「tokenを削る」と「KVを捨てる」は同じではない

LazyLLMはKV cacheをSSDへ逃がす手法ではない。

pruneしたtokenでも将来必要になる可能性があるため、再利用に必要な状態を保持する。主目的は**attention/FFNへ通すtoken数の削減**であり、KV memory削減そのものが主役ではない。

### 5. attention重要度を使うため追加predictorは不要

別の小型modelや学習済みrouterを追加せず、既存attentionから重要度を得る。

その代わり、不規則なtoken集合のindex管理やattention mapの利用自体がruntime overheadになる。

## 評価

### まず見るところ
- **結論:** 長文prefillではかなり効くが、生成全体で見るとdecode比率が高いtaskほどspeedupは小さい。
- **実速度:** A100でwall-clockを測っており、理論token削減だけの結果ではない。
- **品質:** moderateなpruningなら多くのLongBench taskでほぼ維持。
- **注意点:** Aux Cacheと不規則token処理があるため、token削減率＝そのまま速度向上ではない。

### 評価環境

| 項目 | 設定 |
|---|---|
| GPU | NVIDIA A100 |
| Models | Llama 2 7B / XGen 7B |
| Benchmark | LongBench 16 datasets / 6 task groups |
| 測定 | 5回warm-up後のwall-clock |

### Llama 2 7B：TTFTと品質

| Task | TTFT speedup | LazyLLM score | Baseline score |
|---|---:|---:|---:|
| Single-doc QA | 1.36× | 25.59 | 25.79 |
| Multi-doc QA | **2.34×** | 22.31 | 22.43 |
| Summarization | 1.46× | 24.75 | 24.65 |
| Few-shot | 2.19× | 62.81 | 62.90 |
| Synthetic | **2.89×** | 4.98 | 4.97 |
| Code completion | 1.94× | 53.30 | 55.18 |

多文書QAやsynthetic taskではprefill計算を大きく削れる一方、品質差は小さい。

### XGen 7Bの代表speedup

| Task | TTFT speedup |
|---|---:|
| Multi-doc QA | 2.65× |
| Synthetic | 4.77× |
| Code completion | 3.47× |

### TTFTと全生成speedupは別物

| Model | Prompt token計算率 | 全生成speedup |
|---|---:|---:|
| Llama 2 7B | 63.7〜99.6% | 1.02〜1.79× |
| XGen 7B | 40.5〜96.1% | 1.09〜3.16× |

要約ではprompt token計算率が99.59%で全体1.02倍に留まる一方、synthetic taskでは63.73%まで減り1.79倍になる。

つまり**TTFTを2倍以上短縮しても、decodeが長ければend-to-endではほとんど変わらないことがある**。

### 強くpruneした場合

Multi-doc QAでは品質低下1%以内で約2.34倍、より強い設定なら約3倍まで伸ばせるが品質低下は10%以内まで広がる。

### 制約

- token index管理とAux Cacheが複雑。
- GPU dense kernelは不規則token集合を必ずしも効率よく処理できない。
- task/modelごとにpruning位置と率の調整が必要。
- 主効果は長文prefillであり、短promptや長decodeでは利点が縮む。
