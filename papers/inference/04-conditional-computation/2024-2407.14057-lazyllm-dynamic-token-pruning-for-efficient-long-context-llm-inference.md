# LazyLLM: Dynamic Token Pruning for Efficient Long Context LLM Inference

> 長文入力で現在の生成に重要なtokenだけを後続layerへ通し、外したtokenもhidden stateを別cacheへ保存して後で必要になれば途中layerから復帰できるようにすることで、主にprefill計算を減らす。

## 概要
LazyLLMは、長文入力のすべてのtokenを全layerで処理する代わりに、**その時点の生成に重要そうな入力tokenだけを後段へ通す**training-freeなtoken pruning手法である。

固定prompt compressionとの違いは、一度外したtokenを永久に捨てないこと。後のdecode stepで重要度が上がれば、そのtokenを再び計算経路へ戻せる。

この再活性化を成立させるために、LazyLLMは通常のKV cacheとは別に`Aux Cache`を持つ。これは**pruneしたtokenの途中layerまでのhidden stateを保存しておき、後で必要になった時に最初から計算し直さず、そのlayerから処理を再開するcache**である。

主な効果は長文prefillのTTFT削減で、A100実測では多文書QAでLlama 2 7Bが2.34倍、XGen 7Bが2.65倍のTTFT改善を示す。一方、decode支配のtaskでは全生成時間への効果は小さい。

## 手法のあらまし

### 1. Layerごと・decode stepごとに残すtokenを変える

各layerのattentionから、現在の生成tokenが入力tokenをどれだけ参照しているかを計算し、重要度の低いtokenを次のlayerへ送らない。

固定のprompt compressionと異なり、**同じ入力tokenでもlayerやdecode stepによって残る／外れるが変わる**。

### 2. 後段ほど強くtokenを減らす

浅いlayerから大量にtokenを捨てると、その後の表現形成に必要な情報まで失いやすい。

そこで前半layerでは多くのtokenを残し、後段へ進むほど保持率を下げる。

どのlayerから削り始めるか、各段階で何割残すか、何layerを対象にするかが品質とlatencyの主な調整parameterになる。

### 3. `Aux Cache`：外したtokenを後で途中から復帰させる

あるtokenをlayer `l` でpruneした場合、そのtokenのhidden stateを保存しておく。後のdecode stepで再び必要になったら、最初のlayerからやり直さず、保存済み状態から計算を再開する。

これにより「一度外したtokenを復帰できる」柔軟性を保ちつつ、同じtoken×layerの計算を何度も繰り返すことを避ける。

### 4. Tokenを計算経路から外すことと、KVをstorageへoffloadすることは別

LazyLLMはKV cacheをSSDへ逃がす手法ではない。

pruneしたtokenでも将来必要になる可能性があるため、復帰に必要な状態は保持する。主目的は**attention/FFNへ通すtoken数を減らすこと**であり、KV memory容量そのものの削減が中心ではない。

### 5. 既存attentionを重要度判定へ使うため追加predictorは不要

別の小型modelや学習済みrouterを追加せず、既存attentionからtoken重要度を得る。

その代わり、layerごとに異なるtoken集合を管理し、外したtokenを後で復帰させるindex管理自体がruntime overheadになる。

## 評価

### まず見るところ
- **結論:** 長文prefillではかなり効くが、生成全体で見るとdecode比率が高いtaskほどspeedupは小さい。
- **実速度:** A100でwall-clockを測っており、理論token削減だけの結果ではない。
- **品質:** moderateなpruningなら多くのLongBench taskでほぼ維持。
- **注意点:** Aux Cacheと不規則なtoken集合の処理があるため、token削減率＝そのまま速度向上ではない。

### 評価環境

| 項目 | 設定 |
|---|---|
| GPU | NVIDIA A100 |
| Models | Llama 2 7B / XGen 7B |
| Benchmark | LongBench 16 datasets / 6 task groups |
| 測定 | 5回warm-up後のwall-clock |

### Llama 2 7B：TTFTと品質

| Task | TTFT speedup | LazyLLM score | Baseline score |
|---|---:|---:|---:|
| Single-doc QA | 1.36× | 25.59 | 25.79 |
| Multi-doc QA | **2.34×** | 22.31 | 22.43 |
| Summarization | 1.46× | 24.75 | 24.65 |
| Few-shot | 2.19× | 62.81 | 62.90 |
| Synthetic | **2.89×** | 4.98 | 4.97 |
| Code completion | 1.94× | 53.30 | 55.18 |

多文書QAやsynthetic taskではprefill計算を大きく削れる一方、品質差は小さい。

### XGen 7Bの代表speedup

| Task | TTFT speedup |
|---|---:|
| Multi-doc QA | 2.65× |
| Synthetic | 4.77× |
| Code completion | 3.47× |

### TTFTと全生成speedupは別物

| Model | Prompt token計算率 | 全生成speedup |
|---|---:|---:|
| Llama 2 7B | 63.7〜99.6% | 1.02〜1.79× |
| XGen 7B | 40.5〜96.1% | 1.09〜3.16× |

要約ではprompt token計算率が99.59%で全体1.02倍に留まる一方、synthetic taskでは63.73%まで減り1.79倍になる。

つまり**TTFTを2倍以上短縮しても、decodeが長ければend-to-endではほとんど変わらないことがある**。

### 強くpruneした場合

Multi-doc QAでは品質低下1%以内で約2.34倍、より強い設定なら約3倍まで伸ばせるが品質低下は10%以内まで広がる。

### 制約

- layerごとに異なるtoken indexとAux Cacheを管理する必要がある。
- GPUのdense kernelは、不規則に減ったtoken集合を必ずしも効率よく処理できない。
- task/modelごとにpruning位置と率の調整が必要。
- 主効果は長文prefillであり、短promptや長decodeでは利点が縮む。
