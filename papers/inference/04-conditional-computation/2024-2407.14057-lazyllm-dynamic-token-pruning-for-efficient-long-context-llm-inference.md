# LazyLLM: 動的 トークン 枝刈り for Efficient Long Context LLM Inference

> 長文入力で現在の生成に重要なトークンだけを後続層へ通し、外したトークンもhidden stateを別キャッシュへ保存して後で必要になれば途中層から復帰できるようにすることで、主にプリフィル計算を減らす。

## 概要
LazyLLMは、長文入力のすべてのトークンを全層で処理する代わりに、**その時点の生成に重要そうな入力トークンだけを後段へ通す**training-freeなトークン 枝刈り手法である。

固定prompt compressionとの違いは、一度外したトークンを永久に捨てないこと。後のデコード stepで重要度が上がれば、そのトークンを再び計算経路へ戻せる。

この再活性化を成立させるために、LazyLLMは通常のKV キャッシュとは別に`Aux Cache`を持つ。これは**pruneしたトークンの途中層までのhidden stateを保存しておき、後で必要になった時に最初から計算し直さず、その層から処理を再開するキャッシュ**である。

主な効果は長文プリフィルのTTFT削減で、A100実測では多文書QAでLlama 2 7Bが2.34倍、XGen 7Bが2.65倍のTTFT改善を示す。一方、デコード支配のtaskでは全生成時間への効果は小さい。

したがってLazyLLMが最も有利なのは、長い入力を一度に読む時間が応答遅延の大部分を占める処理である。出力が非常に長い場合は、最初の入力処理を短縮してもその後のデコード時間が支配的になり、エンドツーエンドの改善率は小さくなる。逆に検索結果や長文書を大量に与えて短い答えを返す用途では、削減した入力トークン計算がそのまま最初の応答待ち短縮へつながりやすい。

## 手法のあらまし

### 1. 層ごと・デコード stepごとに残すトークンを変える

各層のattentionから、現在の生成トークンが入力トークンをどれだけ参照しているかを計算し、重要度の低いトークンを次の層へ送らない。

固定のprompt compressionと異なり、**同じ入力トークンでも層やデコード stepによって残る／外れるが変わる**。

### 2. 後段ほど強くトークンを減らす

浅い層から大量にトークンを捨てると、その後の表現形成に必要な情報まで失いやすい。

そこで前半層では多くのトークンを残し、後段へ進むほど保持率を下げる。

どの層から削り始めるか、各段階で何割残すか、何層を対象にするかが品質と遅延の主な調整parameterになる。

浅い層で残す割合を高くする理由は、初期表現を早く捨てると後段の重要度判定そのものが不安定になりやすいためである。後段ほど文脈表現が整理された後なので選択を強くできるが、長距離依存を必要とするタスクでは後半でも遠い入力トークンが再び重要になる。このため保持率は単なる速度つまみではなく、情報をいつまで候補として残すかを決める品質制約でもある。

### 3. `Aux Cache`：外したトークンを後で途中から復帰させる

あるトークンを層 `l` でpruneした場合、そのトークンのhidden stateを保存しておく。後のデコード stepで再び必要になったら、最初の層からやり直さず、保存済み状態から計算を再開する。

これにより「一度外したトークンを復帰できる」柔軟性を保ちつつ、同じトークン×層の計算を何度も繰り返すことを避ける。

復帰が必要になるのは、ある生成ステップでは重要度が低かった入力トークンが、後続の生成内容によって再び高いAttentionを受ける場合である。静的なプロンプト圧縮ではこのトークンは永久に失われるが、LazyLLMは途中層の隠れ状態を補助キャッシュ（Aux キャッシュ）へ残すため、必要になった層から後段計算へ再参加させられる。これにより『現在は不要』という判断を『会話全体で不要』という不可逆な判断へ変えずに済む。

### 4. トークンを計算経路から外すことと、KVをstorageへオフロードすることは別

LazyLLMはKV キャッシュをSSDへ逃がす手法ではない。

pruneしたトークンでも将来必要になる可能性があるため、復帰に必要な状態は保持する。主目的は**attention/FFNへ通すトークン数を減らすこと**であり、KV メモリ容量そのものの削減が中心ではない。

### 5. 既存attentionを重要度判定へ使うため追加predictorは不要

別の小型modelや学習済みルータを追加せず、既存attentionからトークン重要度を得る。

その代わり、層ごとに異なるトークン集合を管理し、外したトークンを後で復帰させるindex管理自体が実行時 オーバーヘッドになる。

実行時には、各層で残ったトークンを連続したテンソルへ詰め直し、AttentionとFFNを計算した後に元の系列位置との対応を維持する必要がある。保持トークン数が減っても、この収集・索引管理・補助キャッシュ参照が大きいとGPUの密な行列演算効率を失うため、削減率と実時間短縮は一致しない。特に少数トークンだけを不規則に残す強い枝刈りでは、演算量の削減より小さなカーネル起動やメモリアクセスの固定費が目立ちやすい。

以上の整理は、提案手法の動作原理と前提条件を保ったまま、一次資料の記述を要約したものである。

## 評価

### まず見るところ
- **結論:** 長文プリフィルではかなり効くが、生成全体で見るとデコード比率が高いtaskほど高速化倍率は小さい。
- **実速度:** A100でwall-clockを測っており、理論トークン削減だけの結果ではない。
- **品質:** moderateな枝刈りなら多くのLongBench taskでほぼ維持。
- **注意点:** Aux キャッシュと不規則なトークン集合の処理があるため、トークン削減率＝そのまま速度向上ではない。

### Llama 2 7B：TTFTと品質

| Task | TTFT 高速化倍率 | LazyLLM score | 比較対象 score |
|---|---:|---:|---:|
| Single-doc QA | 1.36× | 25.59 | 25.79 |
| Multi-doc QA | **2.34×** | 22.31 | 22.43 |
| Summarization | 1.46× | 24.75 | 24.65 |
| Few-shot | 2.19× | 62.81 | 62.90 |
| 合成 | **2.89×** | 4.98 | 4.97 |
| Code completion | 1.94× | 53.30 | 55.18 |

多文書QAや合成 taskではプリフィル計算を大きく削れる一方、品質差は小さい。

### XGen 7Bの代表高速化倍率

| Task | TTFT 高速化倍率 |
|---|---:|
| Multi-doc QA | 2.65× |
| 合成 | 4.77× |
| Code completion | 3.47× |

### TTFTと全生成高速化倍率は別物

| Model | Prompt トークン計算率 | 全生成高速化倍率 |
|---|---:|---:|
| Llama 2 7B | 63.7〜99.6% | 1.02〜1.79× |
| XGen 7B | 40.5〜96.1% | 1.09〜3.16× |

要約ではprompt トークン計算率が99.59%で全体1.02倍に留まる一方、合成 taskでは63.73%まで減り1.79倍になる。

つまり**TTFTを2倍以上短縮しても、デコードが長ければエンドツーエンドではほとんど変わらないことがある**。

### 強くpruneした場合

Multi-doc QAでは品質低下1%以内で約2.34倍、より強い設定なら約3倍まで伸ばせるが品質低下は10%以内まで広がる。

### 制約

- 層ごとに異なるトークン indexとAux キャッシュを管理する必要がある。
- GPUのdense カーネルは、不規則に減ったトークン集合を必ずしも効率よく処理できない。
- task/modelごとに枝刈り位置と率の調整が必要。
- 主効果は長文プリフィルであり、短promptや長デコードでは利点が縮む。
