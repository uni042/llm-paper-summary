# 適応型 層-skipping in Pre-trained LLMs

> トークンごと・層ごとに通常のattention+FFNを実行するか小型adapterだけで済ませるかを選び、skipしたトークンのKVは残すことで文脈を保ちながら計算量を減らす。

## 概要
FlexiDepthは、元LLMの重みを固定したまま、**トークンごと・層ごとにfull処理か軽いskip経路かを選ぶ**追加module型の動的 depth手法である。

この設計は、簡単なトークンの計算を軽くしながら、難しいトークンと将来参照される文脈は深く処理するという、細かな計算配分を目指している。

ただし、層を飛ばす判断は計算だけの問題ではない。現在のトークンを軽く処理しても、その隠れ状態が後続トークンの注意計算で参照されるなら、鍵と値の履歴は残しておく必要がある。FlexiDepthはこの二つを分離し、重い変換を省く一方で文脈の記憶を保つ。これにより、定型的なコピーや反復には少ない計算を割り当て、計算や推論を含む難しい箇所には元の層を使うという適応的な配分が可能になる。

固定層 枝刈りと違い、簡単なcopy トークンは浅く、計算や判断が難しいトークンは深く処理できる。各可変層には小型ルータとadapterだけを追加し、元attention/FFNは更新しない。

特徴的なのは、skipしてもhidden stateを単純に素通しせず小型adapterで補正し、さらに将来トークンがそのトークンを参照できるようK/Vは残すこと。これにより固定skipより品質をかなり守れる。

Llama-3-8Bでは平均8 層 skipでもベンチマーク平均100.7%を維持する一方、論文自身が**wall-clock 高速化倍率は未達**と報告する。トークンごとに異なる経路とadapter/ルータの追加重み accessが、減ったFLOPsを相殺するためである。

## 手法

### 1. 各可変層にfull経路と軽いskip経路を持つ

ルータが各トークンに対してgating score `g` を出す。

- `g > τ`：通常のattention + FFNを実行
- `g ≤ τ`：重いblockをskipし、小型adapterだけを通す

つまり層自体を削除するのではなく、**トークンごとに二つの経路から選ぶ**。

同じバッチ内でもトークンごとに選択が異なるため、FlexiDepthは固定した浅いsubmodelを使う方式ではない。あるトークンは前の層をskipしても次層ではfull経路へ戻れ、逆に別トークンは複数層を連続して軽量経路で通れる。この柔軟性によってcopyや定型句へ少ない計算を割き、計算・推論など不確実性の高いトークンへ深い経路を残せるが、GPU実行上はトークンごとの分岐が増えるというcostも生む。

### 2. ルータは小さいMLPを使う

ルータはhidden dimensionを `d/16` 程度へ一度縮めて戻す小型MLPを使う。

単一linearだけのルータでは品質が大きく落ちたため、トークンがfull 層を必要とするか判断するには、少し複雑な変換が必要だったと解釈できる。

### 3. Skip時も小型adapterで表現を補正する

attention/FFNを飛ばしたhidden stateをそのまま次層へ渡すと、元modelが期待する表現からずれる。

そこでskip側にも中間次元1/16程度の小型FFN adapterを置く。

adapterなしの評価で品質が大きく崩れるため、FlexiDepthでは**「層を飛ばす」より「重い層処理を安い近似変換へ置き換える」**と理解する方が正確である。

adapterはfull blockの出力を完全再現する必要はなく、skipしたトークンの表現を次の元Transformer 層が扱える分布へ近づける役割を持つ。元LLM 重みは固定されているため、後段層側をskip入力へ合わせて学習し直すことはできない。そこで軽量adapter側だけを学習し、重いattention/FFNを省いたことで生じる表現のずれを局所的に補正する。この設計により元checkpointを保ったまま動的経路を追加できる。

### 4. SkipしてもK/Vは残す

attention計算をskipするトークンでも、将来トークンがそのトークンを参照できるようK/Vは作ってキャッシュする。

つまり削るのは主にquery側attention計算やFFNで、過去トークンとしての文脈情報を消すわけではない。

これは現在トークンの計算需要と、将来トークンにとっての記憶価値を別扱いにする設計である。あるトークン自身は定型的でfull attention/FFNを必要としなくても、そのトークンが後続文脈から参照される可能性はある。K/Vまで消すと後続トークンから見えるhistoryが経路選択に依存して欠落するため、軽量経路でも将来参照用の状態だけは保存し、計算削減がcontext削除にならないようにする。

K/Vを作らない評価では品質が落ちるため、長いgenerationで重要になる。

### 5. 0/1の経路選択を学習できるようにする

推論時はfull/skipを離散的に選ぶが、そのままではルータへgradientを流しにくい。

そこで学習時だけ離散選択を滑らかに近似し、ルータを学習できるようにする。論文では`SparseMixer`を使う。

### 6. トークンごとの使用層数を可視化して分析する

論文の`DepthMap`は、各トークンが実際に何層使ったかを可視化したもの。

copy / repeatは浅く、summarize / continue / addition / multiplicationは深くなる傾向があり、単なる平均skip率だけでなく「どの種類のトークンへ計算を使ったか」を確認できる。

以上の整理は、提案手法の動作原理と前提条件を保ったまま、一次資料の記述を要約したものである。数値は論文記載の評価条件に基づく比較結果であり、モデルや入力分布、実装環境が変わる場合には同じ傾向が再現するとは限らない。

## 評価

実際の速度は、理論上の演算削減だけで決まらず、分岐をまとめて実行できるかにも依存する。
このため品質保持率と実時間を分けて確認する必要がある。
特に短い入力では分岐管理の負担が相対的に大きくなる。
また、skip率を高めるほど品質保持率との交換関係が強くなるため、用途ごとに許容する計算削減量を決める必要がある。単純に平均skip層数だけを追うのではなく、どの種類のトークンを浅く処理したかを確認することが重要である。
この見方なら、平均値の裏にある難しい入力の劣化も捉えられる。
低負荷の入力と長い推論入力では、同じskip設定でも効果が変わるため、運用時の入力分布を考慮した調整が必要になる。
この調整が品質と速度の釣り合いを決める。
実際の利用条件を反映した評価が欠かせない。
入力の長さや同時実行数が変わると、軽い経路を選ぶ割合とGPUのまとめやすさも変わるため、固定された一つの設定を全ての利用場面へ適用することは避けるべきである。

### まず見るところ
- **結論:** トークン-適応型 ルーティングで固定skipより大幅に品質を守れる。
- **品質:** Llama-3-8Bで8 層 skipしても平均ベンチマークはほぼ比較対象。
- **理論計算:** FLOPsは減る。
- **実速度:** **wall-clock 高速化倍率は未達**。
- **重要な示唆:** 動的 depthはalgorithmだけでなく、同じ経路のトークンをまとめる実行時や専用カーネルまで必要。

### 実速度が伸びない理由

- トークンごとにfull/skip経路が分かれる
- ルータとadapterの重み accessが増える
- GPU カーネルが同じ処理をする大きなバッチを作りにくい
- 実行経路の管理とメモリ trafficがFLOPs削減を相殺する

このため、**algorithm上は省計算でも現状実行時ではwall-clock改善なし**。
