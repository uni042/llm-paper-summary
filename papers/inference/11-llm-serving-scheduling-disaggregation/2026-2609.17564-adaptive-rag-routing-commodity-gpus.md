# Beyond Static RAG: An Adaptive, Tri-Metric Routing Framework for Efficient Long-Context Inference on Commodity GPUs

> 長文RAGの各要求を文書長・キーワード密度・異なり語率で未圧縮、ニューラル圧縮、BM25へ振り分け、T4のVRAM競合とOOMを抑える。

## 概要

長い検索文書をそのままLLMへ渡すと、入力処理でKVキャッシュ領域が埋まり、GPUメモリの少ない端末では要求が失敗する。そこで圧縮器を足しても、圧縮器がGPUメモリを占有し、入力を短くする前に時間を使うため、圧縮しない場合より遅くなったり別のOOMを起こしたりする。本論文は、vLLMとPyTorchの圧縮器を一台のNVIDIA T4で同時に動かす際に生じるこの「圧縮の逆説」を調べ、要求ごとに未圧縮、ニューラル圧縮、語句抽出のいずれかを選ぶ方式を示す。

Tri-Metric方式は、入力の語数、ドメイン語の密度、異なり語率をCPU上で計算し、文書の長さと構造に応じて経路を決める。短い文書は圧縮器の起動費用を避けるためそのまま送り、中程度で圧縮に向く文書だけLLMLingua-2へ回し、T4で処理の損益が逆転する長文はCPU上のBM25で抽出して4096トークン以下に切り詰める。vLLMを先に初期化してGPU領域を確保し、圧縮器が使う空きを残す配置も併用する。

LongBench multifieldqa enの未見50文書で、閾値をqasperから固定したルーターはOOMを起こさず、Combined F1 49.3±1.4%とoracle alignment 88.5±4.4%を記録した。Combined F1は、完了した文書だけでなくOOMで失敗した文書もF1=0として数える指標であり、常時BM25の44.1±1.5%を5.2ポイント上回った。この結果は単一T4、単一モデル、英語の学術QA、バッチサイズ1での評価であり、別GPUや高並列servingで同じ閾値・利得が得られることを示すものではない。

## 問題設定

RAG（Retrieval-Augmented Generation、検索拡張生成）は、検索で得た複数の文書を入力へ加えて回答を作る。入力が長いほど、LLMは最初の入力処理で多くの中間状態を作る。生成中に過去のトークンを再計算せず参照するKVキャッシュも大きくなり、GPUメモリに空きがないと入力処理がページを確保できず、サーバーは要求を完了できない。NVIDIA T4のような16 GB GPUでは、モデル重みとサーバー予約だけで使える領域が限られる。

LLMLingua-2のようなニューラル圧縮器は、入力から不要なトークンを落としてLLMの生成処理を短くする。しかし圧縮器も別のニューラルモデルであり、T4では約2.5 GBのVRAMを使う。vLLMはGPUの55%を一括予約し、実験設定では約5.5 GBの量子化重みと約3.5 GBのKVキャッシュ領域を合わせて9 GBを占める。この状態で両者を同居させると、圧縮器の処理時間と動的メモリ割り当てが、削減した生成時間や残りVRAMを上回る場合がある。

一方、圧縮器を使わなければ追加のVRAMは不要だが、長文がvLLMのKVキャッシュ用ブロックプールを使い切る。著者らは、これを一つの圧縮方式を全要求に適用することで起きる二種類の障害として分ける。未圧縮経路は長文のキャッシュ枯渇、ニューラル圧縮経路はPyTorch側のCUDAメモリ確保失敗が中心であり、単に圧縮率を上げるだけでは両方を防げない。

## 新規性

この研究の貢献は新しい圧縮モデルではなく、推論サーバーの物理的なメモリ余裕と処理時間を見て、圧縮の要否・種類を要求単位で選ぶ点にある。従来の適応型RAGは検索するか、何を検索するかをクエリの意味や難しさから決めることが多い。本方式は検索後の文書をどう圧縮して推論器へ渡すかを扱い、VRAMと前処理・生成の損益分岐を判断材料にする。

もう一つの貢献は、LLM提供器と圧縮器を同一T4へ安全に配置する初期化順序と、メモリ配分の実測である。論文はT4でvLLMの利用率を50〜80%にしたとき共存が安定し、45%では長文のKVブロック不足、85%では圧縮器側のOOMが生じたと報告する。ただし「安全」はこの実験条件での経験的な結果であり、あらゆる入力や並列度に対する形式保証ではない。

## 手法のあらまし

まず入力文書の語数を数え、短文なら圧縮器を呼ばずにLLMへ送る。一定の中間長では、文書のキーワード密度と異なり語率を調べ、構造的に崩れやすい文書を避けてからLLMLingua-2を使う。T4上でニューラル圧縮の前処理時間が生成時間の節約を超える長文帯では、CPU上のBM25で質問に関係する文を選び、入力を最大4096トークンへ制限する。

このルーティングの前提として、vLLMを先にGPUへ載せ、圧縮器が確保する静的領域と追加割り当ての余地を残す。著者らは100文書のLongBench qasperで語数の損益分岐を測り、同じ構成で二つの構造指標も調整する。得た閾値を固定し、別のLongBench分割であるmultifieldqa enへ適用して、エラー率、回答品質、処理時間と、各要求で事後的に最良経路を選ぶoracleとの一致を比較する。

## 手法

### 1. T4上でvLLMと圧縮器を共存させる

T4のメモリは16 GBで、実験のLlama-3-8B-Instruct-AWQは量子化重みに約5.5 GBを使う。vLLMのGPU利用率を55%に設定すると、サーバーの予約領域は約8.8 GBになる。論文の内訳では、これは5.5 GBの重みと約3.3〜3.5 GBのKVキャッシュ用領域に分かれ、LLMLingua-2用に約2.5 GBを割り当てても追加割り当ての余地を残せる。

初期化順序が重要である。vLLMを先に作り、GPUメモリ予約を確定してから、PyTorch上のLLMLingua-2を読み込む。逆順や同時の貪欲な予約では、二つのCUDA allocatorが残り領域を競合し、制御なしの共存実験10回すべてでdriver-level OOMになったとする。ルーター自体は学習済みの追加モデルを持たないが、ニューラル圧縮経路は圧縮器分のVRAMを必要とする。

著者らはvLLM利用率を45〜85%で振り、T4上の「Goldilocks Zone」を50〜80%とする。45%では長文用KVブロックが足りず、85%ではPyTorchへ十分な空きが残らない。80%は安定域の上端だが余裕は小さく、55%を運用点として採用する。これはT4の割当特性を測って決めた設定範囲であり、他のGPUに同じ割合を適用できるとは限らない。

### 2. Tri-Metric Routerで圧縮経路を選ぶ

ルーターは三つのCPU側指標を使う。第一の語数 `L` は入力長を表し、ニューラル圧縮の前処理時間が生成短縮分を超える領域を避ける主ゲートになる。第二のキーワード密度 `ρkey` は、文書中のドメイン用語が占める割合で、コードや数式など記号や専門語の多い入力を見分ける。第三の異なり語率（Type-Token Ratio; TTR）は、異なる語の種類数を全語数で割った値で、同じ語の繰り返しが多いかどうかを測る。

短文の境界は1500語、T4上で圧縮の損得が切り替わる長さは4332語と較正する。1500語未満では圧縮器の起動が生成時間の節約より高くつくのでRaw、つまり未圧縮のまま送る。1500〜4332語では、キーワード密度が0.05以下、かつTTRが0.45以下のときだけLLMLingua-2で目標50%へ圧縮する。

中間長でもキーワード密度またはTTRが閾値を超える場合はRawへ回す。これは数式中の演算子やコード識別子などをニューラル圧縮が落とし、回答の根拠を壊す危険を避けるための分岐である。各条件を同時に満たす必要があるため、長さだけのルーターとは異なり「圧縮が速い長さか」と「圧縮で構造を損ないやすい内容か」を分けて扱う。

4332語を超える場合はニューラル圧縮器を使わず、CPU上でBM25によりクエリ関連度の高い文を選択する。抽出後の文書は4096トークン以下に切り詰める。この経路ではGPU用圧縮モデルが不要で、出力長も制限できるため、ルーターが長文入力を扱うための安全弁になる。BM25の抽出処理はCPU上で約3ミリ秒と報告され、GPUメモリを消費しない。

### 3. 閾値を実測から較正する

語数の境界はLongBench qasperの100文書から決める。著者らは長い側21件の計測でLLMLingua-2の処理時間と、入力を50%へ圧縮した際の生成時間短縮を比較し、前者が後者と交差する長さを4332語と推定した。回帰は圧縮時間を語数の1.31乗に比例する形で近似し、当てはまりはR²=0.94と報告する。

4332語の±185語という95%区間は、21件の測定内でブートストラップした際の当てはまりの揺れを示す。別の測定標本に対する母集団区間ではなく、著者自身も真の不確実性は±500〜1000語程度かもしれないと述べる。従って4332は一般的な境界値ではなく、T4・このモデル・この圧縮器・この圧縮率に対する運転点の推定値である。

キーワード密度とTTRの閾値は決定木で調整したとされる。ただし評価手順の記述には分割数の食い違いがある。20%の検証分割20件で閾値を較正すると説明した直後に、20件を「80件の訓練分割から抽出」とし、残り80件を決定木の学習に使うと記している。どの分割でどの閾値を選んだかは本文だけでは一意に読めず、再現時には著者の実装または追加説明で確認が必要である。

### 4. 要求ごとのデータ経路

実行時には、RAGで検索した文書とクエリから三指標を計算し、決定的な条件分岐にかける。ルーターは内容を生成するモデルではなく、同じvLLMのLLMへ渡す前に、入力をそのまま通すか、LLMLingua-2で短くするか、BM25で関連文だけにするかを選ぶ。ニューラル経路で構造が崩れそうならRawへ戻し、長すぎてキャッシュ枯渇が見込まれる場合はBM25へ送る。

重要なのは、判断をGPU内の注意機構や生成中のKV状態へ挿入しないことだ。従って既存のvLLM内部へKV追い出し機構を追加せず、検索後・LLM呼び出し前にルーティングできる。反面、同じ要求の途中でKV使用量やGPU占有が変わったことを観測して再ルーティングするオンライン制御ではなく、較正した入力長と文面指標で経路を決める。

## 評価方法

実験は単一のNVIDIA T4（16 GB GDDR6、NVLinkなし）を使う。推論器はvLLM上の4-bit量子化Llama-3-8B-Instruct-AWQ、ニューラル圧縮器はXLM-RoBERTa-Largeを使うLLMLingua-2で、圧縮目標は0.5。比較対象は常時Raw、常時Neural、常時Lexical、提案ルーターの四つである。いずれもバッチサイズ1で、複数GPUや同時要求数を増やした評価はない。

qasperの100文書を短（34件）、中（45件）、長（21件）に分け、語数閾値を較正する。次にLongBench multifieldqa enの50文書へ閾値を固定して適用する。ここでのOODは同じベンチマーク内の別タスク分割であり、英語の学術QAから別分野へ移した評価ではあるが、言語・ベンチマークの外部検証ではない。

報告指標のうちCombined F1は、回答が完了した文書のF1に加え、OOMで失敗した文書を0点として含める。これにより成功した一部だけで品質を比較する偏りを抑える。Oracle alignmentは、事後に三経路を全部試して最も速くOOMしなかった方式を選ぶoracleと、ルーターの実際の選択がどれだけ一致するかを測る上限比較である。実行時にはoracleの情報は使えない。

## 結果

multifieldqa enではTri-Metric方式がOOM率0%、平均エンドツーエンド時間8.12秒、Combined F1 49.3±1.4%、oracle alignment 88.5±4.4%だった。OOMのない比較対象である常時BM25は8.47秒、44.1±1.5%であり、ルーターはCombined F1を5.2ポイント改善した。論文は10,000回の対応付きブートストラップ置換検定でp=0.014を報告し、この評価における差は統計的に有意とする。

対照的に、常時RawはOOD文書の64%でKVキャッシュ用領域を使い切り、常時Neuralは19%でPyTorch側のCUDAメモリ割り当てに失敗した。失敗を除いた文書だけのF1は生存者に偏るため、著者らはCombined F1では失敗文書を0点として計算する。提案ルーターの0%はこの50文書、T4、バッチ1で観測された値であり、あらゆる入力に対する証明済みOOM保証ではない。

qasperの較正内比較ではルーターのCombined F1が51.7±1.2%、常時BM25が47.8±1.5%で、差は3.9ポイントだった。短文帯ではRaw、中間帯ではNeural、長文帯ではLexicalを選ぶため、常時BM25のように短中入力まで強く圧縮して回答品質を下げず、常時Neuralのように長文で圧縮器メモリが枯渇する状況も避ける。OODの改善幅が較正内と異なる点は、経路選択の価値が入力分布に依存することを示す。

処理時間の内訳では中間帯のニューラル圧縮に平均1.33秒を要し、エンドツーエンド8.63秒の約15%だった。長文帯のBM25抽出は約3ミリ秒で、LLM生成が支配的なため長文を短縮できる利点が上回る。短文Rawは2.11秒、長文Lexicalは4.72秒と報告される。ただし、これはT4のバッチ1における一要求の完了時間であり、対話で2秒以下の初回応答を求める用途や高負荷servingのスループットを実証したものではない。

## 限界と位置付け

実機評価はT4、Llama-3-8B-Instruct-AWQ、LLMLingua-2、英語LongBench二分割に限られる。L4やA10Gでは較正により損益分岐が6000〜8000語へ動くという表の値は、公開仕様から置いた推定で実測結果ではない。バッチサイズ4ではKV領域が約0.9 GBまで縮み、ニューラル圧縮帯が狭まる可能性を著者ら自身が予測しているが、実験はしていない。

構造保護の二指標については標本が特に少ない。qasperで高キーワード密度または高TTRとなりRawへ送られた6件の小標本分析は統計的に有意ではない。50件のOODで二指標を外した長さだけのルーターはCombined F1が49.3%から47.8%へ下がったとされるが、著者らは二つのアブレーションを検出力不足と位置付け、効果の確証ではなく方向性を示すものと扱う。

適応の範囲にも注意が要る。Tri-Metric方式は要求到着時にCPU指標だけで経路を決め、GPU状態を常時監視してVRAM空きに合わせて閾値を変える方式ではない。閾値の較正は一度のプロファイリングに依存し、英語以外、コード主体の文書、別ベンチマーク、別LLMではキーワード集合や異なり語率の意味が変わり得る。論文はオンラインVRAM監視、他GPUへの再較正、KVキャッシュ管理との併用を今後の課題としている。

既存のKV追い出し・量子化方式は生成中のKV状態や注意機構へ手を入れるため、本論文の「LLMを呼ぶ前に選ぶ」制約とは異なる層を扱う。Tri-Metric方式はそれらを置き換えるものではなく、RAG文書の前処理方法を選んで、既存serving engineの外側からメモリ安全性と回答品質を両立しようとする。フレームワークが利用できる統計量だけで経路を決める簡潔さが利点である一方、ハードウェア・入力分布を変えるたびに計測と再較正が必要になる。
