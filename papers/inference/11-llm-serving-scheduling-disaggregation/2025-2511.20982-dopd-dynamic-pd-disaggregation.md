# DOPD: A Dynamic PD-Disaggregation Architecture for Maximizing Goodput in LLM Inference Serving

> 負荷予測と解析的な最適P/D比でプリフィル/デコード instanceを動的再構成し、8x H100実機で有効スループット最大1.5倍・SLO達成99.4%を報告。
## 書誌情報
- **著者**: Junhan Liao, Minxian Xu, Wanyi Zheng, Yan Wang, Kejiang Ye, Rajkumar Buyya, Chengzhong Xu
- **公開**: IEEE Transactions on Services Computing 2026 / arXiv:2511.20982v3
- **種別**: Journal + arXiv
- **対象**: PD disaggregation、動的 scaling、optimal P/D ratio、load prediction、length-aware スケジューラ
- **実装**: NVIDIA Dynamoを拡張し、Resource Monitor、ルーティング、NIXL Connector、PD Manager、リクエスト スケジューラを実装。etcd/NATS/Prometheus/NVMLを使用。
## 概要
DOPDはPD分離型LLM servingで、実負荷に応じた最適プリフィル/デコード instance比を解析的に求め、ARIMAによる短期負荷予測とelastic scalingで比率を動的に再構成する。mixed-length リクエストにはlength-aware batchingとultra-short リクエストの局所PD aggregationを併用する。8基H100実機とAzure/BurstGPT production トレースで、vLLM/DistServe等に対し有効スループット最大1.5倍、P90 TTFT最大67.5%低下、P90 TPOT最大22.8%低下、動的 ワークロードでSLO達成率99.4%を報告する。

DOPDは対象モデルと画像処理装置を事前計測し、入力処理時間、生成時間、メモリ容量、メモリ帯域、並列度、予測される入力長・出力長・同時要求数から、生産能力と消費能力が釣り合う入力処理・生成比を計算する。実行時には短期負荷予測を用いて次の期間の要求量と長さを見積もり、その比率へ先回りして装置数を変更する。短期的な長さ混在には要求単位のスケジューラを併用し、短い要求を長さ上限までまとめ、長い要求は待たせず処理し、極端に短い要求は生成側で入力処理も行って鍵値転送を省く。
## 問題設定
入力処理と逐次生成を別の画像処理装置群へ分ける方式では、入力処理側が生成側へ要求と鍵値状態を供給する生産者、生成側がそれを消費する消費者になる。両者の処理能力比が実際の要求分布とずれると、入力処理側が速すぎる場合は生成待ち行列が増え、生成側が速すぎる場合は生成用装置が待機する。従来の静的分離はこの比率を固定するため、入力長、出力長、同時要求数が時間変化する実運用では最適点から外れやすい。平均要求長だけを使う構成も、短い要求と長い要求が混在すると二乗的に増える注意計算量と待ち時間分散を捉えられない。既存の動的拡縮方式は負荷に応じて装置を増減できても、拡縮後に入力処理用と生成用を何台ずつ置くべきかを明示的に求めないため、過剰配備や片側飽和が残る。さらに極端に短い要求では鍵値転送時間が入力処理時間と同程度になり、常に遠隔入力処理へ送ること自体が不利になる。
## 新規性
DOPDは対象モデルと画像処理装置を事前計測し、入力処理時間、生成時間、メモリ容量、メモリ帯域、並列度、予測される入力長・出力長・同時要求数から、生産能力と消費能力が釣り合う入力処理・生成比を計算する。実行時には短期負荷予測を用いて次の期間の要求量と長さを見積もり、その比率へ先回りして装置数を変更する。短期的な長さ混在には要求単位のスケジューラを併用し、短い要求を長さ上限までまとめ、長い要求は待たせず処理し、極端に短い要求は生成側で入力処理も行って鍵値転送を省く。
## 手法
### 手法のあらまし
処理は 事前計測 監視 予測 最適比計算 装置再構成 要求振分け 鍵値転送 生成 という閉じた循環で進む。 事前計測 対象モデルと画像処理装置について 入力長ごとの初回応答時間と 生成時の系列長・同時数ごとの一出力トークン時間を測る。 監視 資源監視器が 入力処理待ち行列 鍵値使用率 装置数 初回応答時間 一出力トークン時間 平均入力長 平均出力長 要求数を継続収集する。 予測 時系列予測器が次の期間の入力長 出力長 要求数を一歩先予測する。 補正 直近の予測誤差から補正係数を作り急な分布変化への追従を速める。 計算 生成装置一台が保持できる最大同時要求数から必要な生成装置数を求める。 計算 事前計測した入力処理時間と生成時間を使い 生産速度と消費速度が釣り合う入力処理・生成比を求める。 再構成 管理器が計算結果に従い入力処理装置と生成装置を無停止で増減する。 緊急対応 待ち行列深さや鍵値使用率が閾値を超える突発負荷では定期予測を待たず直ちに増設する。 振分け 入口では生成側の接頭辞キャッシュ一致量と負荷を見て適切な生成装置を選ぶ。 入力処理 長い要求は即時に入力処理装置へ送り 短い要求は合計長上限と待ち時間上限の範囲でまとめる。 例外 極端に短い要求は生成装置上で入力処理も実行し 鍵値転送を省く。 転送 遠隔入力処理を行った要求だけ 高速装置間通信で鍵値を生成側へ移す。 生成 生成側は保持可能な同時数まで要求をまとめて逐次生成する。 再監視 得られた実測値を次の予測と比率計算へ戻し 時間変化する負荷に追従する。

### 最適な入力処理・生成比の計算
役割 入力処理側と生成側の生産消費能力を釣り合わせる。 入力 モデル容量 装置メモリ容量 メモリ帯域 並列度 入力長 出力長 同時要求数を使う。 準備 入力処理時間と生成時間を事前計測する。 計算 生成装置が保持できる最大同時要求数を求める。 計算 予測要求数から必要生成装置数を求める。 計算 入力処理時間と生成時間から生産消費比を求める。 計算 その比率から必要入力処理装置数を求める。 目的 サービス水準を満たす範囲で総画像処理装置数を最小化する。 効果 片側装置の待機を減らす。 効果 入力処理待ち行列の飽和を減らす。 差分 単純な利用率閾値ではなく拡縮後の役割別台数まで決める。

### 短期予測による先回り拡縮
役割 負荷変化が起きてから反応するのではなく次の期間に必要な装置を先に準備する。 監視 平均入力長 平均出力長 要求数を時系列として蓄積する。 予測 軽量な時系列モデルで次時点を一歩先予測する。 補正 直近の実測と予測の比から補正係数を作る。 結合 予測値を事前計測した遅延曲面へ補間する。 決定 最適比計算へ予測要求量を渡す。 実行 数百秒程度の間隔で入力処理装置と生成装置を増減する。 緊急 待ち行列や鍵値占有が閾値を超えれば周期を待たず増設する。 効果 起動に数十秒かかる大規模モデルでも負荷急増前に準備できる。 制約 稀な極端な長文や突発的な急増は予測しにくい。

### 長さを考慮する要求スケジューラ
役割 混在する要求長が固定比率を崩す短期的な不均衡を要求単位で吸収する。 判定 次期間の平均入力長予測を長短判定の基準にする。 長要求 長い入力はまとめず即座に入力処理へ送る。 短要求 短い入力は合計トークン長の上限までまとめる。 待機 待ち時間上限を設け サービス水準を悪化させるほどまとめ続けない。 選択 必要なら価値と長さの比でまとめる要求を選ぶ。 例外 極端に短い要求は生成装置上で入力処理も行う。 効果 短い要求で鍵値転送時間が支配的になる問題を避ける。 効果 長い要求と短い要求を同じ平均値で扱う資源不一致を軽減する。 計算量 待ち行列操作を中心に要求数へ線形であり実行時負担は小さい。

### 鍵値を考慮する振分けと接続
役割 要求を適切な生成装置へ送り 遠隔入力処理の鍵値を高速に移す。 監視 各生成装置の鍵値使用量と負荷を収集する。 照合 接頭辞キャッシュの一致量を装置ごとに推定する。 振分け 一致量が大きく負荷が低い生成装置を優先する。 登録 入力処理装置と生成装置の識別子と鍵値位置を共有管理する。 待ち 遠隔入力処理待ち要求を専用待ち行列へ保持する。 転送 高速装置間通信ライブラリで入力処理後の鍵値ブロックを生成装置へ送る。 効果 既存接頭辞を再利用し不要な入力処理を減らす。 効果 鍵値転送先の偏りを抑える。 連携 資源監視器と管理器へ現在の占有状況を返し次の拡縮判断へ利用する。

### 全体のデータ／制御の流れ
動的分離推論基盤を拡張し、資源監視器、接頭辞キャッシュを考慮する振分け器、鍵値転送接続器、最適比計算と装置増減を行う管理器、長さを考慮する要求スケジューラの五要素で構成する。
## 評価条件
- **ハードウェア**: 8x NVIDIA H100-SXM-80GB
- **ソフトウェア**: NVIDIA Dynamo、NIXL、Prometheus、NVML、etcd、NATS、ARIMA
- **データセット／トレース**: BurstGPT、Azure Code トレース、Azure Conversation トレース、ShareGPT
- **比較対象**: vLLM、DistServe、Dynamo、DYN-LOAD、DYN-SLA
P/D ratio計算の妥当性を固定ISL/OSLでP-instance数をsweepして確認後、同GPU budgetの静的比較と、1P(TP1)+1D(TP2)から始める動的 トレース replayを実施。
PD-disaggregated servingのP/D比最適化、mixed-length スケジューラ、動的 instance scaling。
## 主要結果
静的構成の実験では、七十億級ではなく七百億級モデルを四基相当の資源で動かす条件において、提案方式は同一場所実行の基準方式よりサービス水準付き実効処理量を最大一・五倍へ高め、一出力トークン時間の九十パーセンタイルを〇・〇九七秒から〇・〇七九秒へ短縮した。三百億モデルの分離方式比較では初回応答時間の九十パーセンタイルを七・一〇秒から二・三一秒へ下げ、実効処理量を最大二十七パーセント改善した。動的な実運用模擬負荷ではサービス水準達成率九十九・四パーセントとなり、負荷閾値方式の八十・八パーセント、サービス水準反応方式の八十七・三パーセントを上回った。

- サービス水準付き実効処理量 / 最大1.5倍 (比較対象: 同一場所実行の基準方式; 条件: Llama-3.3-70B-FP8、Azure要求分布、同等四基資源) — 入力処理と生成の比率を要求分布へ合わせ、短い要求を長さに応じてまとめることで、同じ資源量でもサービス水準を守れる同時要求数を増やせる。

- 九十パーセンタイル初回応答時間 / 7.10秒から2.31秒 (比較対象: 静的な分離推論方式; 条件: OPT-30B、一入力処理装置と一生成装置) — 長さを考慮した入力処理順序と適切な生産消費比により、入力処理待ち行列の偏りと片側飽和を減らした効果が初回応答へ表れる。

- サービス水準付き実効処理量 / 最大27%改善 (比較対象: 静的な分離推論方式; 条件: OPT-30Bの固定構成比較) — 装置数を変えない条件でも要求単位の長さ調整だけで分離推論の短期的な資源不一致を緩和できることを示す。

- サービス水準達成率 / 99.4% (比較対象: 反応型87.3%、負荷型80.8%; 条件: BurstGPTの時間変動負荷) — 負荷上昇後に反応するだけでなく次期間を予測して先に装置を増やすため、起動遅延を隠しながら急増へ追従できる。

- 九十パーセンタイル一出力トークン時間 / 0.097秒から0.079秒 (比較対象: 同一場所実行の基準方式; 条件: Llama-3.3-70B-FP8の静的比較) — 生成側の必要同時数とメモリ容量を考慮して装置を配置することで、生成待ちと資源競合を減らす。

- 短期予測処理時間 / 平均0.8秒未満 (比較対象: 数百秒単位の再構成周期; 条件: 実行時の一歩先予測) — 予測処理は装置再構成周期より十分短く、中央処理装置側の管理負担が主たる性能律速にならない。

### 負の結果・境界条件
- 極端に長い入力が突然到着すると平均長を中心とする短期予測が外れ、入力処理が一時的に支配的になって全体性能を悪化させる。
- 現在の方式は要求分布に応じて装置数を変えるが、各入力処理装置と生成装置の並列度そのものを実行中に連続的に選び直すところまでは扱わない。
- 七百億級モデルと高性能画像処理装置の組合せでは、初回応答曲面の事前計測に約九十分、一出力トークン時間の事前計測に約百五十分を要する。
- 新しい入力処理装置の起動は最大約三十秒、生成装置は実行グラフ準備のためさらに約一・五倍長くかかる。予測による先回りが外れるとこの遅延を完全には隠せない。

### 結果の読み方
分離推論の性能は鍵値転送速度だけでは決まらず、入力処理側の生産能力と生成側の消費能力が現在の要求長分布に合っているかが重要である。長期的な変動には装置数の予測駆動再構成、短期的な長さ混在には要求単位の振分けを使い分けることで、資源浪費とサービス水準違反を同時に減らせる。
## 品質への影響
モデル重み、注意計算、生成アルゴリズムは変更せず、要求振分けと装置資源管理だけを変更する。したがって生成品質を近似で落とす代わりに性能を得る方式ではない。
## 既存研究との差
DistServe/SplitWise/Mooncakeは主にphase分離とKV移送を最適化するがP/D instance数は静的。PD-Serve、Arrow、Dynamoは動的 scalingを持つが、DOPDはscale後の最適P/D比をmodel/profileから明示計算する点を差別化する。ultra-short リクエストだけをD側でプリフィルする局所aggregationもmixed-length対策として併用する。
## 限界
- ultra-long contextのrare burstは予測困難。
- TP degreeのランタイム動的選択は未対応。
- model/GPUごとの長時間pre-deployment profilingが必要。
- ARIMAは急激なburstで外れるためthreshold-based emergency scalingを併用している。
## 実装状態
Dynamo拡張として実装され、公式codeは https://github.com/liao4s/DOPD で公開。
## 研究上の位置づけ
動的 PD resource allocationとmixed-length スケジューラを統合したproduction-oriented serving framework。
