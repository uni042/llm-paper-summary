# TokenScale: Timely and Accurate Autoscaling for Disaggregated LLM Serving with Token Velocity

> プリフィル・通信・デコードを共通の「トークン速度」で観測し、突発負荷では既存デコードGPUを一時的なプリフィル処理へ転用して、新規GPU起動の遅れを埋める自動スケーリング方式。

## 概要

大規模言語モデル（LLM）の推論では、入力全体を一括処理するプリフィル（prefill）と、出力を1トークンずつ生成するデコード（decode）で資源特性が異なる。プリフィルは計算量が大きく、デコードは重みやキー・バリュー（KV）キャッシュを繰り返し読むためメモリ帯域の影響を受けやすい。このため両段階を別GPU群へ分離するプリフィル・デコード分離（prefill/decode disaggregation）が使われるが、負荷が急増すると「どちらを何台増やすか」を素早く決める必要がある。

一般的な自動スケーリング（autoscaling）はGPU使用率、待ち要求数、平均到着率などを観測する。しかし、これらは混雑が起きた後に上がる遅行指標になりやすい。さらに新しいプリフィルGPUを起動してモデルを読み込むまでには時間がかかるため、負荷の山が短い場合はGPUが準備できる前に初回トークン遅延（Time To First Token; TTFT）や出力1トークン当たり時間（Time Per Output Token; TPOT）のサービス水準目標（Service Level Objective; SLO）が破られる。

TokenScaleはこの問題に対し、各処理段階で単位時間にどれだけのトークン相当仕事量を消化できているかを表すトークン速度（Token Velocity）を先行信号として使う。さらに、普段はデコードを担当するGPUを負荷急増時だけプリフィルへ切り替える変換可能デコーダー（Convertible Decoder）を組み合わせる。これにより、新規プリフィルGPUが立ち上がるまでの過渡期を既存資源で吸収する。

A100とH100のGPUクラスタ、本番トレースを用いた評価では、DistServe、BlitzScale、AIBrixなどの比較方式が50〜88%だったSLO達成率を80〜96%へ改善し、同時に費用を4〜14%削減した。重要なのは単にGPUを多く確保した結果ではなく、負荷の位置を早く捉え、短期の突発負荷と持続負荷で異なる応答を取った点である。

## 問題設定

分離型サービングでは、プリフィルとデコードを別々に増減できる。その反面、要求数だけでは必要資源を決めにくい。入力が長ければプリフィル仕事量が大きく、出力が長ければデコード仕事量が大きい。同じ1件の要求でも、どちらのGPU群へどれだけ負荷を掛けるかが違うからである。

GPU使用率も十分な先行指標とは限らない。キューが伸びて初めてGPU使用率が張り付くなら、観測した時点でTTFT違反が始まっている可能性がある。さらにプリフィルとデコードの間ではKV状態をネットワーク転送するので、GPU以外の転送段階が詰まる場合もある。単一の要求数やGPU使用率では、どこにバックプレッシャーが発生しているかを区別しにくい。

既存方式のもう一つの問題はスケールアウトの初期化遅延である。負荷急増を検出してから新規プリフィルGPUを起動し、モデルを配置し、実行可能にするまでの時間は0ではない。短いバーストでは「増設の判断自体は正しいが、間に合わない」という状況が起こる。TokenScaleは、この検知遅れと起動待ちの両方を対象にする。

## 手法

### 1. トークン速度で段階ごとの仕事量を同じ尺度へ写す

トークン速度は、プリフィル、KV転送、デコードを単なるGPU利用率ではなく「仕事がどの速度で流れているか」として観測する。入力トークンを処理するプリフィル、状態を次段へ送る通信、出力トークンを生成するデコードを、段階横断で比較できる量へ変換することで、どこに仕事が蓄積し始めているかを早く検知する。

要求数を数えるだけでは長い入力1件と短い入力1件を同じ1件として扱うが、トークン速度は処理量へ寄せて観測する。このため、到着数がまだ少なくても入力長が急増してプリフィル負荷が高まった場合や、デコード側へ長い生成が滞留した場合を別々に扱える。

### 2. バックプレッシャーを先行してスケール判断へ使う

各段階で需要側のトークン流入速度が処理側の速度を上回れば、その差は将来のキュー増大として現れる。TokenScaleはこの傾向をバックプレッシャーの先行信号にし、GPU使用率が飽和してからではなく、飽和へ向かう段階で増設・再配置を判断する。

ここで重要なのは、プリフィルだけを独立に監視するのではなく、転送とデコードも含むことにある。プリフィルを増やしてもKV転送やデコードが詰まれば全体のSLOは改善しない。段階間で速度を比較することで、増設対象を誤るリスクを減らす。

### 3. 変換可能デコーダーで新規プリフィル起動までの穴を埋める

変換可能デコーダーは、通常はデコード用として稼働しているGPUにプリフィル処理能力も持たせ、急増時だけ一部をプリフィルへ切り替える。これにより、新しいプリフィル専用GPUの初期化が終わる前から追加プリフィル能力を出せる。

この仕組みは恒久的な容量増設ではなく、短期の緩衝層である。デコードGPUを奪いすぎればTPOTが悪化するため、プリフィル滞留だけを見て無制限に転用することはできない。TokenScaleはトークン速度を使い、プリフィル側の急増を吸収しつつ、デコード側のSLOを壊さない範囲で転用する。

### 4. 長く続く負荷は通常のスケールアウトへ引き継ぐ

バーストが短ければ変換可能デコーダーだけで吸収できるが、需要が持続する場合はプリフィルGPUの追加が必要になる。新規ワーカーの準備が終われば、一時転用したGPUをデコードへ戻す。つまり、既存GPUの転用と通常の自動スケーリングは競合する代替策ではなく、時間スケールの異なる二段階の応答になっている。

実装ではモデル読み込みを高速化するServerlessLLM系ローダーとCUDAグラフキャッシュも用い、初期化遅延を抑える。生産トレースに実プロンプト本文がない条件では、既存研究と同様の出力長予測器を模擬し、予測精度85%として評価する。この仮定は実運用での予測器精度に依存する部分である。

## 評価

### 評価条件

| 項目 | 条件 |
|---|---|
| A100クラスタ | 1ノード4× NVIDIA A100 40GB、NVLink 3.0、合計200Gbps RDMA。4ノード小規模構成と16ノード大規模構成 |
| H100クラスタ | 2ノード、各8× NVIDIA H100 80GB、NVLink、合計2880Gbps RDMA |
| 実装 | vLLM 0.9.2 + LMCache 0.3.0、PyTorch 2.7.1、CUDA 12.8 |
| 負荷 | 本番トレースを用いた突発性のある要求列 |
| 比較対象 | DistServe、BlitzScale、AIBrixなど |
| 主指標 | TTFT/TPOTのSLO達成率、GPU資源費用、スケール応答 |
| 補助条件 | 出力長予測器を85%精度として模擬 |

### 代表的な評価結果

| 評価軸 | 比較方式 | TokenScale | 改善・解釈 |
|---|---|---|---|
| SLO達成率 | 50〜88% | 80〜96% | 突発負荷でTTFT/TPOT違反を減らす |
| 費用 | DistServe・BlitzScale・AIBrix等 | 比較方式比4〜14%削減 | SLO改善を常時過剰確保だけで達成していない |
| 負荷急増への初動 | 新規プリフィル起動待ちが発生 | 稼働中デコーダーを一時プリフィル化 | 起動遅延中の性能穴を埋める |
| ボトルネック検知 | GPU使用率・要求数などの遅行指標 | 段階横断のトークン速度 | キューが顕在化する前のバックプレッシャーを使う |

SLO達成率の「50〜88%から80〜96%」は、異なるトレースや構成にまたがる範囲であり、単一条件の一つの絶対改善幅ではない。同様に費用4〜14%削減も条件依存である。数値を読む際は、SLOの定義、負荷のバースト性、GPU起動時間、モデル構成を揃える必要がある。

### 何が効いているか

トークン速度だけでは、新規GPUの初期化時間そのものは消えない。変換可能デコーダーだけでも、どの段階が詰まっているか誤認するとデコード能力を不用意に減らす。両者を組み合わせ、先行検知で一時転用を開始し、恒久増設へつなぐことが設計上の要点である。

また、H100とA100のように計算・通信能力が変わると、同じ要求列でもプリフィル・転送・デコードの相対ボトルネックは変わる。TokenScaleが絶対GPU使用率ではなく処理速度を基準にする理由もここにある。

## 既存研究との差

DistServeのような分離型サービングは、プリフィルとデコードを別資源へ置くことで干渉を減らす。AIBrixなどの管理基盤はLLMサービングの資源制御を行う。本論文が追加するのは、分離後の各段階を「何件待っているか」だけでなくトークン処理速度で結び、突発負荷に対してデコードGPUを一時的にプリフィルへ変換する過渡応答である。

したがって、TokenScaleの新規性は新しい推論カーネルやKV圧縮ではなく、分離型クラスタの制御面にある。処理段階をまたぐ観測指標と、既存資源を短時間だけ役割変更する機構を一体化している。

## 限界

- 分離型プリフィル・デコード構成を前提とする。単一GPU上の一体型推論では同じ制御問題にならない。
- 出力長予測を含む負荷推定の精度に依存し、予測誤差が大きいと必要なデコード容量を見誤る可能性がある。
- デコーダーをプリフィルへ転用すると、その間はデコード余力が減る。デコード側がすでに支配的な負荷では逆効果になり得る。
- GPU、ネットワーク、モデル読み込み時間が異なるクラスタでは、転用時間と通常スケールアウトの境界を再調整する必要がある。
- 報告されたSLO改善率と費用削減率は本番トレースを再生した評価条件に依存し、すべての価格体系・需要分布にそのまま一般化できない。
- 公開要旨からは実装コードの一般公開を確認できず、上流vLLMへ標準機能として統合済みとは言えない。
