# CacheRoute: Planned Prefix-Affinity Routing for Large-Scale LLM Serving

> キー別要求率から温存対象と安定配置を周期計画し、プレフィックス局所性と負荷均衡を両立して、60基H100の70B評価で3.5秒p99 SLO容量をPreble比2.3倍へ高めるが、親和性が効かない負荷では逆効果になる。

## 概要
CacheRouteは、LLMサービングでプレフィックスKVキャッシュを再利用するには同じキーの要求を同じ宛先へ戻す必要がある一方、単純な固定親和性は人気キーの偏りをそのまま待ち行列へ写し、p99遅延を悪化させる問題を扱う。要求ごとの即時判断ではなく、観測したキー別要求率から一定制御区間のルーティング表を周期的に作る。高頻度キーを温存対象へ優先採用し、単一宛先の能力を超えるキーだけ複数宛先へ分割し、割当仕事を最長処理時間優先（Longest Processing Time first; LPT）で負荷均衡配置する。未採用トラフィックは通常のpower-of-two choicesへ戻す。Llama-3.3-70B fp8を60基のH100で評価し、3.5秒p99 SLO下で176±11 QPS、最強比較方式Preble比2.3倍、KVヒット率93.2±0.5%を示す。一方で32Bの負の負荷では容量がFlat-LBの0.50～0.67倍まで低下するため、実運用ではシャドー再生で有効範囲を測ってから有効化する設計を提案する。

CacheRouteは新しい最適化プリミティブを主張するのではなく、既存の高頻度優先採用とLPT配置をLLMプレフィックス親和性へ組み合わせ、一定制御区間で安定した全体ルーティング計画を作る点を中核とする。各キーの要求率から必要宛先数を決め、限られた温存スロットへ高頻度キーから採用し、冷たい末尾負荷まで含めて宛先へ配置する。さらに、キャッシュ常駐を数式で保証せず、実測シャドー再生でKVヒット率・負荷偏り・p99を比較し、負の領域では通常負荷分散を維持する運用境界まで設計に含める。
## 問題設定
プレフィックスKVキャッシュは、同じ再利用可能プレフィックスを持つ後続要求が、そのKV状態をまだ保持するモデル宛先へ戻ったときだけプリフィル計算を省ける。ところが通常の負荷分散は要求を複数宛先へ散らすため、フリートを拡大すると1宛先への再訪間隔が伸び、総キャッシュ容量が増えても各プレフィックスは冷えやすくなる。逆に一貫ハッシュなどでキーを固定すると局所性は戻るが、人気キーの偏りがそのまま待ち行列偏りになり、最も混雑した宛先がフリート全体のp99を決める。PrebleやDualMapのような反応型方式も現在の負荷や再利用を見て冷たい宛先へスピルすると、その要求では温存済みKVを失う。したがって、要求ごとの局所判断だけでなく、キー別要求率の全体分布を使って、どのキーを温存し、どこへ安定配置するかを負荷制約込みで先に決める必要がある。
## 新規性
CacheRouteは新しい最適化プリミティブを主張するのではなく、既存の高頻度優先採用とLPT配置をLLMプレフィックス親和性へ組み合わせ、一定制御区間で安定した全体ルーティング計画を作る点を中核とする。各キーの要求率から必要宛先数を決め、限られた温存スロットへ高頻度キーから採用し、冷たい末尾負荷まで含めて宛先へ配置する。さらに、キャッシュ常駐を数式で保証せず、実測シャドー再生でKVヒット率・負荷偏り・p99を比較し、負の領域では通常負荷分散を維持する運用境界まで設計に含める。
## 手法
### 手法のあらまし
制御面は、各ルーティングキーbの推定要求率λ_b、独立にルーティング可能な宛先数R、1宛先の遅延急増点から較正した能力q_cap、宛先当たり温存スロットWを入力する。まず各キーに対し、1宛先へ載せる期待要求率がq_capを超えないよう、k_b=max(1, ceil(λ_b/q_cap))個の宛先を必要数として求める。次に総温存容量C=R×Wの範囲で、キーをλ_bの降順に見てΣk_bがCを超えないところまで採用する。各採用キーはλ_b/k_bの大きさを持つk_b個の配置仕事へ分割され、未採用トラフィックが各宛先へ与える期待負荷を初期値とした上で、高要求率から順に最も負荷の小さい異なる宛先へ割り当てる。これはLPT型リストスケジューリングだが、仕事分割と異宛先制約があるため古典的近似保証をそのまま主張しない。実行面では制御区間中に表を固定し、採用キーは固定T(b)内の現在最小負荷宛先へ、未採用キーはフリート全体のpower-of-two choicesへ送る。主70B分布では全キーがq_cap未満なのでk_b=1であり、主要効果は複製ではなく、高頻度キー採用・単一コピー親和性・均衡配置から生じる。計画器は要求経路外で動き、128,824キー・R=30で345 ms。新表への更新はKV再温存を伴うため、実運用では古い表の劣化と再温存費用を測定し、シャドー再生で新計画がp99または容量を改善する場合だけ有効化する。

### 要求率ベースの温存集合採用
各キーの要求率と単一宛先の能力から必要宛先数k_bを算出し、宛先当たりW個という温存スロット予算を全体でR×W個として、高要求率キーから採用する。狙いは限られたキャッシュ常駐機会を、再訪頻度が高く再利用価値を回収しやすいキーへ集中することにある。主負荷では最も人気のキーでもq_capを超えずk_b=1なので、70Bの主要結果はホットキー複製ではなく、どのキーを安定親和性へ載せるかの選別効果を測っている。未採用キーはキャッシュから排除されるわけではなく、通常のネイティブ追い出し方針と共有するため、計画は常駐保証ではなく再訪確率を高める入口配置として機能する。

### 負荷比例複製とLPT均衡配置
q_capを超えるホットキーだけはk_b>1として複数の異なる宛先へ分散し、1割当あたり期待負荷をλ_b/k_bへ抑える。採用キーの割当仕事を要求率の高い順に処理し、冷たい末尾トラフィックの期待負荷も初期値へ含めて、その時点で最も軽い宛先へ置く。合成ホエール評価では、親和性だけでKVヒット率を56%から88%へ上げても負荷偏りが3.46倍になり容量は240 QPSのままだった。複製だけでも偏り2.60倍で容量は変わらず、LPT配置まで加えて偏り1.24倍になると容量が500 QPSの測定上限へ達する。したがって局所性の獲得だけでなく、全体配置で尾部待ちを抑えることが飽和域の改善に必要になる。

### 安定制御区間と高速配送
ルーティング表は各要求で作り直さず、制御区間中は固定する。採用キーは固定された小さなT(b)の中で現在負荷が最小の宛先を選び、未採用キーはキャッシュ無視のpower-of-two choicesへ戻す。この安定性により、反応型ルータが負荷上限へ当たるたびに温存済み宛先から別の冷たい宛先へ流してしまう揺れを避ける。計画器の計算量はO(|B|log|B|+Σk_b logR)で要求経路外にあり、128,824キー・30宛先でも345 msなので、実行経路は表参照と小さな候補集合の負荷比較だけで済む。一方、率分布のドリフトで表が古くなるため、更新周期は再温存費用との交換になる。

### シャドー再生による運用ゲート
CacheRouteは計画上のスロットを物理予約せず、KVブロック移行も行わないため、表だけから実際のキャッシュ常駐を保証しない。著者は特性時間型の解析的常駐モデルも試したが、提供済みヒット率の誤差が中央値14.3ポイント、p90で44.7ポイントに達し、採用しなかった。そこで候補表の応答を利用者へ返さない短時間シャドー再生を行い、Flat-LBと同一負荷でトークン重み付きKVヒット、宛先負荷、p99、失敗率を実測する。ヒット率上昇だけでは有効化せず、p99または容量が改善した場合に限る。32Bの負・同率事例を明示し、モデル、精度、文脈長、キャッシュ割当、活性集合が変わるたび再評価する運用手順まで含めている。

### 全体のデータ／制御の流れ
周期計画器がキー別要求率から温存集合・必要宛先数・均衡配置を作り、オンラインルータは固定表内の軽い宛先へ高速配送する。未採用要求は通常負荷分散へ逃がし、計画更新はシャドー再生で性能境界を実測してから適用する。
## 評価条件
- **ハードウェア**: 主評価は60基のNVIDIA H100で、Llama-3.3-70B fp8を30個のTP2宛先として実行する。機構評価は30基のH100でLlama-3.1-8B-Instruct bf16を30単一GPU宛先として実行する。
- **ソフトウェア**: クライアント側ルーティングハーネスから各方針で直接宛先を選択し、同一のサービングスタック、要求列、ウォームアップ除外、負荷ラダー、健全性判定を使用する。ルータはモデル実行、KV容量、エンジンの追い出し方針を変更しない。
- **比較対象**: Flat-LB、Sticky consistent hashing、CHWBL、DualMap-style、Preble-style
主負荷は匿名化した運用テレメトリからキー別要求率・再訪間隔・人気度を再構成した半合成ピーク時分布で、128,824個の不透明キー、Gini係数0.756、上位4%が約47%の要求を占める。入力は平均約1.2Kトークンで、キー固有の安定文脈は約180トークン。2つ目の独立半合成分布で分布移動を検証し、Poisson、CV一致Gamma、移動ブロック再標本化でバースト感度を見る。Flat-LB、Sticky、CHWBL、DualMap風、Preble風と比較し、p99遅延が閾値以下かつ失敗率5%以下を満たす最大提供QPSをSLO容量とする。主top-K128は5組seed、top-K256確認は8組、補助評価は原則3組の対応seedを使う。
大規模実機評価と明示的な負結果を含むが、主モデルは70B fp8、機構評価は8B、負・同率領域は別32B構成で、ハードウェアはH100に限定される。半合成負荷は運用統計を保つ一方、正確なキー別時刻や要求本文は保持しない。Preble、DualMap、CHWBLは共通ハーネス上の再実装であり、原著システム全体の再現値ではない。温存枠はプレフィックス長が概ね均一と仮定し、長さが不均一な文脈向けのバイト単位採用は未実装。
## 主要結果
主70B fp8・60 H100評価でCacheRouteは3.5秒p99 SLO容量176±11 QPSを達成し、最強比較方式Prebleの76±11 QPSに対して2.3倍、Flat-LBの42±20 QPSに対して4.2倍となる。100 QPS共通点のp99は1.8秒で、5比較方式の3.8～8.5秒を下回る。提供済みKVヒット率はFlat-LBの64.1±1.3%から93.2±0.5%へ上がるが、StickyやDualMapも高ヒットでありながら尾部遅延が悪いことから、利得は親和性単独ではなく均衡配置との組合せによる。第2分布や32B負荷では同率・負の結果も観測され、適用可能性は負荷依存である。

- 70B主評価の3.5秒p99 SLO容量 / 176±11 QPS (比較対象: Preble-style 76±11 QPS / Flat-LB 42±20 QPS; 条件: Llama-3.3-70B fp8、30 TP2宛先、60 H100、top-K128、5組対応seed) — 最強比較方式比2.3倍、キャッシュ無視負荷分散比4.2倍で、安定親和性と期待負荷配置を同時に計画する効果が最も明確な条件である。

- 70B主評価の提供済みKVヒット率 / 93.2±0.5% (比較対象: Flat-LB 64.1±1.3% / Preble 72.0±0.7% / DualMap 88.7±1.9%; 条件: 主半合成分布、top-K128) — Flat-LB比29.1ポイントの再利用増加。ただしDualMapは近いヒット率でもp99が5.3秒なので、ヒット率だけでは容量改善を説明できない。

- 100 QPSでのp99遅延 / 1.8秒 (比較対象: Flat-LB 5.7秒、Sticky 8.5秒、CHWBL 3.8秒、DualMap 5.3秒、Preble 3.8秒; 条件: 70B fp8主分布、3.5秒SLO) — 高局所性だけの方式と負荷均衡寄り方式の双方より尾部を抑え、親和性と待ち行列均衡の両立を示す。

- 広い活性集合top-K256の確認 / 80 QPS (比較対象: DualMap 60 QPS; 条件: 70B fp8主分布、3.5秒p99 SLO、8組seed) — 主headlineより倍率は1.33倍へ縮み、効果量が活性集合と温存容量の関係に依存することを示す。

- 第2分布top-K256のSLO容量 / 160 QPS (比較対象: 最良比較方式100 QPS; 条件: 70B fp8、独立半合成分布、3組seed、3.5秒p99 SLO) — top-K128では複数方式が100 QPSで同率だが、活性集合が温存割当を超えると1.6倍の差が現れる。

- 合成ホエールの構成除去 / 容量240→500 QPS測定上限、負荷偏り3.46倍→1.24倍 (比較対象: 親和性のみ → 親和性+複製+LPT; 条件: 8B、top-K128、3組seed) — 親和性だけではKVヒット56%→88%でも容量は240 QPSのまま。LPTで偏りを抑えて初めて容量が測定上限へ達する。

- 32B集約Aの負領域 / Flat-LB比0.50～0.67倍 (比較対象: Flat-LB; 条件: 半合成集約A、KVヒット1.1%→11.8%) — 回収できるKV計算が小さいと、ヒット率上昇より残留負荷偏りが勝ち、親和性が容量を悪化させる。

- 再計画の温存費用 / 新表導入直後にKVヒット13.6ポイント低下 (比較対象: 既存温存状態; 条件: 6制御区間の率ベクトルをlognormal random walkで変動) — 新鮮な表への切替自体がキャッシュ再温存費用を持つため、古い表の劣化がこの費用を上回るまで配置を保つ必要がある。

### 負の結果・境界条件
- 32B集約Aでは親和性でKVヒットが1.1%から11.8%へ増えてもSLO容量はFlat-LBの0.50～0.67倍まで低下し、集約Bでは0.8%から8.5%へ増えても5秒SLO容量は同率だった。第2分布top-K128ではCacheRoute、CHWBL、DualMapが100 QPSで同率。8Bの複数条件は500 QPS測定上限へ達して右打ち切りである。解析的キャッシュ常駐モデルは実測ヒット率を中央値14.3ポイント、p90で44.7ポイント外し、運用判断には使えなかった。

### 結果の読み方
CacheRouteの本質は『キャッシュヒットを最大化するルータ』ではなく、回収可能なプリフィル計算と、そのために残る負荷偏りを一定制御区間の全体計画として交換することにある。高再利用領域では固定表が局所性を守り、LPT配置がホットスポットを抑えるため大きなSLO容量向上になるが、再利用価値が小さい領域では通常負荷分散より悪化する。したがってシャドー再生で実測境界を取る手順が方式の一部になる。
## 品質への影響
モデル実行内容や数値表現を変えず、要求の宛先だけを変えるため生成品質の近似は導入しない。影響対象はプリフィル再計算量、待ち行列、KV常駐状態、尾部遅延、失敗率である。
## 既存研究との差
Prebleは過去のプレフィックス再利用と現在負荷から要求ごとに反応し、DualMapは静的・動的候補を組み合わせるのに対し、CacheRouteはキー別要求率の全体分布から制御区間ごとの安定表を事前計画する。StickyやCHWBLの固定親和性と違い、高頻度キーの採用、過負荷キーの必要宛先数、全体LPT配置を明示的に組み合わせる。MooncakeやMemServeのようにKV状態をサーバ間移送・共有するのではなく、入口ルーティングで同じ状態を持つ宛先へ再訪させるため相補的である。
## 限界
温存集合の採用は安定プレフィックスが概ね同サイズという等スロット仮定を置き、長さが大きく異なる長文向けのバイト単位価値関数やナップサック最適化は未実装である。採用済みと未採用トラフィックは同じネイティブキャッシュを共有するため、未採用側が温存対象を追い出す可能性も残る。半合成集約は人気度や一部再訪相関を保つが正確なキー別時刻を保持せず、2種類の分布だけで全市場を代表できない。比較するPreble、DualMap、CHWBLは共通ハーネス再実装で原著実装ではなく、補助3-seed評価は信頼区間が広い。再計画では94.5%のキー配置が変わり得て再温存損失が大きいが、churn-awareな再計画器は未実装である。
## 実装状態
クライアント側ルーティングハーネスによる実機研究実装で、70B/8Bを最大60 H100で評価済み。計画器は128,824キー・30宛先で345 ms、オンライン経路は表参照と小さな候補集合の負荷比較である。2026-09-16時点で論文・arXivページ上の公式ソースコードURLは確認できない。論文はarXiv v1プレプリントで、査読採録は確認できない。
## 研究上の位置づけ
LLMサービングの状態付き入口ルーティングとプレフィックスKVキャッシュ局所性を結ぶ研究である。単一エンジン内のPagedAttention/SGLangがKV再利用を効率化するのに対し、CacheRouteは『どのエンジンへ要求を戻すか』を扱う。現在状態へ反応するオンラインルータと、KVをネットワーク越しに移送・プールする分散キャッシュの間に、率分布から安定配置を周期計画する選択肢を置き、さらに負領域を実測して有効化をゲートする運用手法まで含める。
