# Token-Budget-Aware Pool Routing for Cost-Efficient LLM Inference

> 短文・長文でvLLMプールを分離し、自己校正した総トークン予算で振り分けてGPU台数を約17〜39%削減するフリート経路制御。
## 書誌情報
- **著者**: Huamin Chen, Xunzhuo Liu, Junchen Jiang, Bowei He, Xue Liu
- **公開**: arXiv
- **種別**: Preprint
- **対象**: LLMサービング、フリート経路制御、KVキャッシュ、vLLM、コスト最適化
- **実装**: 要求ごとに定数時間で総トークン予算を推定し、短文用または長文用vLLMプールへ振り分ける軽量ルータ。評価用の自己完結型離散事象シミュレータも使用。
## 概要
実運用のLLM推論フリートで短い要求が大半なのに全インスタンスを最悪時の長いコンテキスト向けに設定する不整合を、短文用・長文用の二つのvLLMプールとオンライン自己校正型トークン予算推定で解消する。AzureとLMSYS由来トレースのLlama-3-70B/A100評価でGPUインスタンスを約17〜39%削減し、設計フリートでは先取り・拒否をゼロにしたと報告する。

論文は同一モデルのフリートを短い最大系列長で高並列性を得るshort poolと、元の長い系列長を保持するlong poolへ二分し、各要求の入力と最大出力を合わせた総トークン予算を推定してフリート横断で振り分ける。ルータ自身にモデル固有tokenizerを置かず、応答メタデータのusage.prompt_トークンからカテゴリ別bytes-トークン比を指数移動平均で学習し、過小推定の損失が大きい非対称性を分散項で保守的に補正する点が実装上の特徴である。さらに短文比率αと短文プールのスループット倍率ρから savings=α(1−1/ρ) という簡潔な事前コストモデルを導く。

代表結果として、GPUインスタンス削減はLlama-3-70B/A100、1,000 req/s、Azure/LMSYS由来トレースで全インスタンスを長文最大系列長へ設定した同一フリートに対してAzure 16.6%、LMSYS 38.5%（総括17〜39%）。短い要求を高並列設定へ集約する効果は、長い裾を持つAzureより短文集中のLMSYSで大きい。
## 問題設定
実運用のvLLMフリートでは最大コンテキスト長を64K以上の最悪要求へ合わせて各インスタンスを同一設定にすることが多いが、実トラフィックの80〜95%は短い。KVキャッシュ容量は最大系列長に強く拘束されるため、短い要求まで長文向け設定で処理すると同時実行数を4〜8倍程度失い、逆に長い要求が集中するとメモリ不足、KVキャッシュ先取り、要求拒否、長いプリフィルによる先頭待ちが発生する。既存のPagedAttentionや連続バッチ処理は単一インスタンス内部のメモリ断片化や実行効率を改善するが、フリート全体が最悪長向けに同じ設定を持つ構成不整合そのものは解消しない。また単純に短文専用プールを作るだけでは、入口で実トークン数を安全に判定するためにモデル固有トークナイザを複製する運用負担や、言語・コードごとのバイト密度差による過小推定が残る。したがって問題の本質は、GPU内スケジューリングだけでなく静的なフリート設定と要求長分布の不一致を、低コストかつ安全な経路制御で吸収することである。
## 新規性
論文は同一モデルのフリートを短い最大系列長で高並列性を得るshort poolと、元の長い系列長を保持するlong poolへ二分し、各要求の入力と最大出力を合わせた総トークン予算を推定してフリート横断で振り分ける。ルータ自身にモデル固有tokenizerを置かず、応答メタデータのusage.prompt_トークンからカテゴリ別bytes-トークン比を指数移動平均で学習し、過小推定の損失が大きい非対称性を分散項で保守的に補正する点が実装上の特徴である。さらに短文比率αと短文プールのスループット倍率ρから savings=α(1−1/ρ) という簡潔な事前コストモデルを導く。
## 手法
### 手法のあらまし
まず運用者は同じモデルを提供する二種類のvLLMプールを用意する。短文プールは例えば8K程度の小さいmax_model_lenに設定し、同じGPUメモリでより多くの系列を同時保持して高スループットを狙う。長文プールは64K等の従来設定を保持し、短文閾値を超える要求の安全な受け皿にする。要求到着時、ルータは入力文字列のバイト長をカテゴリ別の推定bytes-トークン比で割って入力トークン数を近似し、要求が指定するmax_output_トークンを加えて総トークン予算を求める。この予算がshort poolの安全閾値以下なら短文側、超えるなら長文側へ送る。実際の応答からusage.prompt_トークンが返るたびに観測bytes-トークン比を計算し、カテゴリごとの指数移動平均と分散を更新する。経路判定では平均値をそのまま使わず標準偏差分だけ保守側へずらし、CJK、英語、コードなど符号化密度の違いによる過小推定を抑える。これによりtokenizerをフリート入口へ配布せずに推定器が自己校正する。運用上はshort thresholdをトラフィックCDFと各プールの測定スループットから選び、短文比率αとスループット比ρで概算節約率を求め、重い長文の実コストを含む場合は各プールの実効処理率を用いて必要GPU数を個別計算する。ルーティングは要求ごとの定数時間処理で、各GPU内ではPagedAttention、連続バッチ、chunked プリフィル、プリフィル/デコード分離など既存機構をそのまま使う。

### 二重プールによる設定分離
同一モデルのフリートを、小さい最大系列長でKVキャッシュ当たりの同時実行数を増やす短文プールと、元の長い最大系列長で任意の要求を収容する長文プールへ分ける。短い要求を最悪長設定から切り離すことで、単一GPU内のメモリ管理を変更せずにフリート全体の容量を要求分布へ合わせる。長い要求は専用側へ隔離されるため、短文側で最大長超過による拒否やKVキャッシュ先取りが起きないよう構成できる。短文側は最大系列長を小さくすることで一系列が予約し得るKV領域を抑え、同一GPUで保持できる同時系列数を増やす一方、長文側は低い並列性を受け入れて互換性を保つ。したがって入力は同じモデルへの要求、出力も同じモデルの生成結果であり、変更点は要求を受け持つフリート設定だけである。閾値を小さくし過ぎると長文側へ要求が偏って短文側容量を活用できず、大きくし過ぎると短文側の容量安全性を損なうため、トラフィック分布と実測処理率に基づく設定が必要になる。

### 自己校正型トークン予算推定
入力バイト数をカテゴリ別bytes-トークン推定値で割り、max_output_トークンを加えた総予算で経路を決める。推定値は各応答のusage.prompt_トークンから得た実測比を指数移動平均で更新するため、ルータにモデル固有tokenizerを搭載する必要がない。さらに推定分散を使って保守側へ補正し、長い要求を誤って短文プールへ送る危険を、短い要求を長文側へ送る損失より強く抑える。初期値が不正確でも応答ごとの実測値でオンライン補正され、英語、CJK、コードなど入力種別ごとに別統計を持つことで符号化密度差を吸収する。推定値が保守的過ぎる場合は安全だが長文側への過剰経路で節約率が下がり、過小推定すると短文側の最大長を超えて拒否や再経路が必要になるため、平均だけでなく分散を使うことが安全性と利用率の調整点になる。

### フリート費用モデルと閾値選択
短文トラフィック比率αと短文設定による処理率倍率ρから、理想化したGPU節約率α(1−1/ρ)を得る。これはトラフィックCDFと事前プロファイルだけで導入前の効果を概算するための式である。重い長文が長文プールの処理率を下げる場合は、短文側と長文側それぞれの到着率を実効処理率で割って必要GPU数を算出し、単純式の過大評価を補正する。閾値感度も評価し、8K〜16K付近が両ワークロードで大部分の利益を保持することを示す。このモデルの入力は要求長CDF、短文閾値候補、各設定の測定処理率で、出力はプール別必要台数と総GPU削減見込みである。実トラフィックが長文化したり、短文設定の処理率倍率が小さいモデルでは利益が縮むため、固定式を普遍値として使わず、モデル・GPU・要求分布ごとに再プロファイルする必要がある。

### 全体のデータ／制御の流れ
フリート入口の軽量ルータだけを追加し、同一モデルを異なるmax_model_lenで構成した二つの既存vLLMプールへ要求を振り分ける。GPU内の推論エンジンや生成手順は変更しないため、既存のメモリ・バッチ・分離最適化と直交して組み合わせられる。
## 評価条件
- **ハードウェア**: 主評価はLlama-3-70BをNVIDIA A100 GPUで配信するフリートを対象とし、ケーススタディではQwen3-235B-A22BをAMD MI300Xで10,000 req/s配信する構成を投影する。
- **ソフトウェア**: vLLMの連続バッチ処理を対象とする。評価では自己完結型の離散事象シミュレータを用い、反復時間を固定作業量とactive sequence数に依存する一次モデルで近似する。
Azure LLM Inference DatasetとLMSYS-Chat-1M由来の要求長分布を使い、Llama-3-70B/A100フリートについて従来の同一長文設定と二重プール経路制御を比較する。1,000 req/sで必要GPUインスタンス数、成功率、先取り・拒否、TTFT/TPOTを評価し、P99 TTFT 2秒以下・P99 TPOT 80ms以下のサービス水準を確認する。カテゴリ別bytes-トークン推定の収束と誤経路率、short budget閾値の感度も測定する。さらに10,000 req/sのQwen3-235B-A22B/MI300Xを費用モデルで投影する。
実機フリート全体を用いた大規模オンライン実験ではなく、公開トレースと一次的な反復時間モデルを用いた離散事象評価が中心である。主な定量評価はLlama-3-70B/A100に限定され、MI300Xの大規模値はケーススタディ投影である。
## 主要結果
二重プール経路制御は1,000 req/sの評価で必要GPU数をAzure系トレースで16.6%、LMSYS系で38.5%削減し、年間費用換算で約120万〜200万ドルの節約を報告する。設計したフリートサイズでは成功率100%、先取り・拒否ゼロを達成し、P99 TTFT/TPOTの目標も維持した。自己校正推定はカテゴリ当たり約50要求で真値の3.5%以内へ収束し、誤経路率を静的比率の4.1%から1%未満へ下げる。

- GPUインスタンス削減 / Azure 16.6%、LMSYS 38.5%（総括17〜39%） (比較対象: 全インスタンスを長文最大系列長へ設定した同一フリート; 条件: Llama-3-70B/A100、1,000 req/s、Azure/LMSYS由来トレース) — 短い要求を高並列設定へ集約する効果は、長い裾を持つAzureより短文集中のLMSYSで大きい。

- 年間費用削減 / 約$1.2M〜$2.0M/年 (比較対象: 同一フリート; 条件: A100、1,000 req/sの評価規模) — インスタンス削減をクラウドGPU費用へ換算した値で、実運用単価に依存する。

- 自己校正精度 / 約50要求/カテゴリでbytes-トークン比が真値の3.5%以内、誤経路率1%未満 (比較対象: global 静的 ratioの誤経路率4.1%; 条件: カテゴリ別EMA、保守補正あり) — 言語やコードで異なる符号化密度をtokenizerなしで追従し、危険なshort-pool誤投入を抑える。

- 信頼性 / 成功率100%、先取り0、拒否0 (比較対象: 設計フリートサイズでの比較; 条件: 短文プールを予算上限以下へ制限したシミュレーション) — 長い要求を専用プールへ隔離することで短文側の容量超過を構造的に避ける。

- MI300Xケーススタディ / $15.4M/年の節約を投影 (比較対象: 同一設定フリート; 条件: Qwen3-235B-A22B、AMD MI300X、10,000 req/s) — 大規模フリートでの潜在効果を示す投影値であり主評価と同じ実測値ではない。

### 負の結果・境界条件
- GPU利用率を高めるため中央値・尾部遅延は必ずしも改善せず、AzureではP99 TTFTが約0.91秒から1.60秒へ増える例がある。ただし評価した設定ではP99 TTFT 2秒、P99 TPOT 80msの目標内に留まる。重い長文裾を持つトラフィックでは単純な閉形式費用モデルが節約を過大評価し得る。

### 結果の読み方
最大の効果は新しいGPU内スケジューラではなく、短文が大半というトラフィック構造をインスタンス設定へ反映することから生じる。コスト低下と引き換えにGPU利用率が上がり遅延余裕は縮むため、厳しい尾部遅延目標では追加余裕容量が必要になる。
## 品質への影響
同じモデル・生成設定を容量の異なるプールへ振り分けるため、モデル品質を直接変更する方式ではない。
## 既存研究との差
PagedAttention、continuous batching、chunked プリフィル、プリフィル/デコード分離などが単一GPUまたは実行段階内の効率を改善するのに対し、本手法はその外側でフリートを異なる最大系列長へ分割し、要求を適切な構成へ送る。複雑な要求単位スケジューラや異種モデルルータではなく、同一モデル・同一推論系のconfiguration-traffic mismatchを総トークン予算という一つの判定量で解く。入力長だけでなく最大出力長を加えるため、大きな出力上限を持つ短入力を誤ってshort poolへ送る問題も避ける。
## 限界
評価の中心はLlama-3-70B/A100と離散事象シミュレータで、実際の大規模vLLMフリートを用いた長期間のオンライン検証ではない。反復時間を一次モデルで近似するため、実エンジンの非線形なカーネル・通信・メモリ挙動を完全には再現しない。公開CDFから合成したトレースは長文裾を実分布より重くする可能性があり、単純な savings=α(1−1/ρ) は長文プールの実効処理率低下を無視すると節約を過大評価する。高利用率化により尾部遅延が増えるため、より厳しいSLOでは追加容量が必要になり得る。
## 実装状態
O(1)のフリート入口ルータとカテゴリ別EMA状態が主要追加要素で、vLLM内部のスケジューラ変更を要求しない。評価用にはvLLM連続バッチを模した自己完結型離散事象シミュレータを用いる。公開実装URLは今回確認できていない。
## 研究上の位置づけ
LLMサービングの費用最適化を、GPU内のKVキャッシュ管理だけでなくフリート構成とトラフィック分布の整合という層へ引き上げる研究である。長短要求の混在を二つの設定へ分離する単純な構造は、既存の高度なサービング最適化と競合せず併用でき、導入前にCDFと測定処理率から効果を見積もれる。一方、二分割で十分か、閾値や容量を時間変動へどう追従させるか、実フリートでの尾部遅延・自動拡縮との相互作用は今後の検証余地が大きい。
