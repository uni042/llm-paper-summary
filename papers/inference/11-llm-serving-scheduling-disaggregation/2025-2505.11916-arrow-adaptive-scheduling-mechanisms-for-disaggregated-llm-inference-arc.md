# Arrow — Prefill/Decode分離サービングの弾力的GPU配置

## 概要

LLMサービングでは、入力全体を処理する入力処理と、次トークンを逐次生成する逐次生成とで、計算密度、メモリ帯域要求、許容遅延が異なる。これらを別のGPU群へ分離する構成は相互干渉を減らすが、固定のGPU配分比では、長い入力が集中した時間帯には入力処理が詰まり、長い出力が増えた時間帯には逐次生成が詰まる。Arrowは各GPUインスタンスを固定役割にせず、要求の段階に応じて入力処理と逐次生成のどちらにも割り当てられるようにする。

v1の一次本文では、8基のH800上でLlama-3.1-8Bを実行し、Azure Codeトレースの持続可能要求率が同居型vLLM比5.62倍、分離型vLLM比7.78倍と報告する。ただし2025年11月に公開されたv2要旨では分離基盤比の最大値が2.55倍へ変わっている。本稿の手法・表の詳細は**取得できたv1全文に基づく**もので、v2の実験設定と直接比較できると断定しない。改訂版の数値をv1へ黙って混在させないことが重要である。

## 問題設定

入力処理は入力長が到着時に既知で、同じGPU上の待ち行列を把握すれば初回トークン遅延（初回トークン遅延）を比較的予測しやすい。一方、逐次生成の生成終了までのトークン数は要求到着時には未知であり、KVキャッシュ転送、空きメモリ、バッチの空き、反復計算時間が絡む。トークン間遅延（出力トークン間遅延）は個々の反復で変化し、完了までの平均も単調増加しない。両者を同じCPU/GPU使用率指標だけで管理すると、入力処理の待ち時間悪化を見逃したり、逐次生成の短期的な負荷変動に過敏に反応したりする。

著者らが調べたAzure Code、Azure Conversation、BurstGPT、Mooncake Conversationの実運用トレースは、入力長と出力長の分布だけでなく時間変動も異なる。Azure Codeでは低負荷の1分間の入力/出力トークン総量が25.7K/0.25Kであるのに対し、ピークでは1327.9K/16.6Kまで増え、入力側で約50倍、出力側で約65倍となる。Azure Codeの入力・出力長の相関は0.95、Azure Conversationでは0.29であり、単一の固定PD比率を異なる負荷へ使い回すことは難しい。

既存のDistServeやSplitwiseは入力処理/逐次生成分離を先行して実装したが、役割変更の際にモデル重みの再ロードや進行中要求の完了待ちが必要となる場合がある。Arrowは役割を「GPUに固定された属性」から「要求の処理段階」へ移し、モデル再ロードなしでプール所属を変更することで、役割切替の待ち時間を減らす。

## 手法

### 1. 状態を保持しないインスタンスと四つのプール

Arrowの各インスタンスは、入力処理要求と逐次生成要求のどちらも処理できる。同一の要求について、GPU Aが入力処理を終えた後、GPU BがKVキャッシュを引き取り逐次生成を続けてもよいし、Aがそのまま逐次生成を担当して転送を省略してもよい。グローバルスケジューラは要求単位で段階を分割して配置し、ローカルスケジューラはKV転送待ちと計算待ちの順序を管理する。

インスタンスプールは入力処理、逐次生成、入力処理→逐次生成移行中、逐次生成→入力処理移行中の四種類である。移行中のGPUが旧役割の要求をまだ処理している場合、処理を中断せず移行状態へ置く。旧要求が終わると新役割のプールへ入る。この表現により、GPUを停止して再起動することなく、新役割の要求を割り当て始められる。ただし「零待ち時間」とはプール所属の変更についての主張であり、旧要求の計算やKV転送の費用が消えるわけではない。

### 2. 初回トークン遅延予測と入力処理要求の配置

クラスタ起動時に、各GPUの入力処理処理時間を入力長の二次関数で近似するプロファイラを実行する。新しい要求が来ると、既存入力処理待ち行列の残り時間と新要求の推定処理時間を合算し、初回トークン遅延の遅延目標を満たせるかを判断する。まず入力処理専用プールの待ち時間が最小のGPUを探し、次に逐次生成→入力処理移行中プールを試す。どちらも遅延目標を満たせない場合、逐次生成の余裕を見て逐次生成 GPUを入力処理へ移す。

予測器の入力は到着済み要求の入力長と待ち行列であり、未来の到着率を予言するものではない。既存逐次生成処理と入力処理が混在する移行中インスタンスでは推定誤差が増えるため、通常入力処理プールを優先する。どの候補でも初回トークン遅延制約を満たせないときは、最小待ち時間の入力処理インスタンスへ戻すフォールバックがある。すべての要求で遅延目標を保証する硬い受理制御ではない。

### 3. 逐次生成要求の配置とKV転送

逐次生成側は、生成完了時刻の予測ではなく、現在走っている要求のトークン総数と直近の平均生成間隔を使う。入力処理を処理したGPUが既に逐次生成可能な状態なら同じGPUへ割り当て、KVキャッシュ転送を回避する。そうでなければ逐次生成プールで稼働トークン数の少ないGPUを選び、メモリに保持可能な最大トークン数と出力トークン間遅延閾値を満たすか確認する。移行中プールも候補とし、必要なら入力処理 GPUを逐次生成へ変更する。

各GPUの最大稼働トークン数は起動時のプロファイルから定める。KVキャッシュ容量を超えた要求を詰め込むと転送待ちが長くなり、次の生成反復までの遅延が大きくなるからである。ローカルスケジューラはKV転送が必要な要求を転送待ち行列へ置き、転送が終わってから実行待ちへ入れる。転送は先着順、計算は逐次生成を優先し、余裕に応じて入力処理をチャンク単位で混ぜる。

### 4. 役割切替と過負荷時の例外

入力処理の予測初回トークン遅延が制約を破りそうなら逐次生成→入力処理切替を試す。ただし逐次生成のインスタンスを最低限残す制約があり、逐次生成側がすでに過負荷なら切替を断念する。一方、逐次生成の生成間隔が出力トークン間遅延閾値を継続的に超える、または入力処理側が空いているときは入力処理→逐次生成へ移す。両方の段階が過負荷のときは、処理中の逐次生成要求を優先する。入力処理だけ大量に受け付けてKVを保持したまま逐次生成が進まず、メモリを圧迫する事態を避けるためである。

この非対称な規則は、初回トークン遅延が強く予測可能で一度遅延すると取り返せない一方、出力トークン間遅延は生成中の観測で調整できるという分析に基づく。ただし過負荷時には新規入力処理の遅延目標を諦める場合があり、負荷のすべての組合せで公平性や期限保証が得られるわけではない。

## 評価

### 実機と負荷条件（v1）

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA H800 80GB ×8、NVLink 400GB/s |
| CPU・RAM | Intel Xeon Platinum 8468V ×2、ホストメモリ2048GB |
| モデル | Llama-3.1-8B |
| Azure Code | 8819要求、初回トークン遅延 3秒、出力トークン間遅延 0.1秒 |
| Azure Conversation | 19366要求、初回トークン遅延 2秒、出力トークン間遅延 0.15秒 |
| BurstGPT clip | 6009要求、初回トークン遅延 0.25秒、出力トークン間遅延 0.075秒 |
| Mooncake clip | 1756要求、初回トークン遅延 30秒、出力トークン間遅延 0.1秒 |

ここでの要求率は指定初回トークン遅延/出力トークン間遅延 遅延目標を満たして処理できる持続可能な要求率であり、単一要求の推論速度ではない。比較には同居型vLLM、入力処理/逐次生成分離型vLLM、DistServeを用いる。KV転送の経路、GPU間帯域、メモリ容量が影響するため、8基のH800で得た値を単一GPUの性能倍率へ読み替えない。

| トレース（v1） | Arrow / 同居型vLLM | Arrow / 分離型vLLM | 補足 |
|---|---:|---:|---|
| Azure Code | 5.62倍 | 7.78倍 | 入力の急増を初回トークン遅延予測で検出 |
| BurstGPT | 3.60倍 | 5.04倍 | 短時間のバーストを吸収 |
| Azure Conversation | 3.76倍 | 4.06倍 | 分離型vLLMは25 req/s超でKV転送問題により試験失敗 |
| Mooncake Conversation | 3.73倍 | 4.14倍 | 長い入力で入力処理の空き資源を逐次生成へ再配置 |

これらはv1の実験表・本文に基づく。Mooncake条件ではDistServeが長文脈入力でメモリ不足となり完了できないため、同じ負荷範囲での全方式の連続的な比較曲線が存在するわけではない。ベースラインが失敗する領域を含む最大倍率だけで実用上の平均効果を判断しない。

### 構成要素除去と負荷感度

Azure Codeでは遅延目標対応の要求配置と役割切替を用いるArrowが、固定4:4配分で最小負荷配置だけを行う方式より1.67倍高い要求率を達成した。Azure Conversationでは同じ比較で1.1倍であり、入力・出力負荷が比較的釣り合うと動的役割切替の追加利得は小さい。最小負荷配置は単純なラウンドロビンより遅延目標達成率がAzure Codeで最大4.3%、Azure Conversationで最大2.4%高いと報告される。これは役割切替だけでなく、各GPUの稼働トークン数と待ち行列を見て要求を置くことにも寄与があるという証拠である。

### 改訂版の数値差をどう扱うか

2025年11月公開のv2要旨は「最先端の入力処理/逐次生成分離サービング方式に対して最大2.55倍の要求率」と述べる。v1本文の分離型vLLM比最大7.78倍とは数値が異なる。v2の全文評価表を本runでは取得できていないため、比較基準、評価負荷、設定変更のどれが差を生んだかは断定しない。v1表の値を最新版の代表値として使うことは避け、最新版の確定性能を引用する場合はv2本文の再確認が必要である。

## 限界・負の結果

役割切替が待ち時間なしという表現は、GPUのモデル重み再ロードを避ける管理上の意味であり、進行中要求を消去したりKV転送を無料化したりするものではない。移行中のGPUは旧役割と新役割の処理が競合し、初回トークン遅延予測に誤差が出る可能性がある。そのため通常プールが優先される。入力処理と逐次生成の両方が過負荷なら逐次生成を優先する設計なので、すべての要求で初回トークン遅延を満たせる保証はない。

評価は8基H800の同種クラスタとLlama-3.1-8Bを中心とする。MoEのエキスパート並列、複数ノード間のネットワーク障害、極端に低帯域なKV転送、モデル重みの入替えが必要な環境などへの適用は未検証である。さらに最新版v2でheadline性能が変更されているため、v1の最大倍率は改訂版の確定結論ではない。

## 既存研究との比較

DistServeとSplitwiseは入力処理/逐次生成分離による干渉低減を示した。Arrowは分離そのものではなく、各段階の遅延目標の予測可能性の違いを利用して役割配分をオンライン変更する。MooncakeはKVキャッシュ中心の保存・再利用を主眼とするのに対し、Arrowの主要操作はGPUプール所属と要求配置である。既存の固定PD比率の最適化と比較すると、短時間の入力バーストや長い出力への遅延追従を減らす点に独自性がある。
