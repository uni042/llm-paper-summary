# Towards High-Goodput LLM Serving with Prefill-decode Multiplexing

> MuxWiseはプリフィル（Prefill）とデコード（Decode）を別GPUへ固定分離せず、同一GPUのストリーミングマルチプロセッサ（Streaming Multiprocessor; SM）を空間分割して同時実行する。KVキャッシュは同じメモリ空間へ置いたまま計算資源だけを動的配分し、分離配信の遊休とチャンク化プリフィルのサービスレベル目標（Service Level Objective; SLO）違反を同時に減らす。

## 概要

プリフィルは大きな行列演算でGPU計算資源を使いやすく、デコードは小さい反復を繰り返しメモリ帯域の影響が強い。両者を別GPUへ分離すると相互干渉は減るが、負荷比が変わった際に一方が遊休になる。またKVキャッシュがフェーズ間で分断され、マルチターンで再計算が起きる場合がある。

逆に同一GPUでプリフィルを小チャンクへ切りデコード反復へ混ぜる方式では、デコードのトークン間時間（Time Between Tokens; TBT）を守るためチャンクを小さくするとGPUを満たしにくく、大きくするとデコードを長く止める。

MuxWiseは「メモリは共有、計算は分離」という中間点を取る。SMをプリフィル/デコードへ別々に割り当て、プリフィルを層単位で進める無気泡多重化、共有帯域競合を安全側に読む推定器、SLOから必要SM数を逆算するディスパッチャを組み合わせる。

## 手法

### 1. 同一GPU内でプリフィルとデコードを空間多重化する

GPUのSM集合を二つへ分け、両フェーズのカーネルを並行実行する。別GPUへKVを転送せず、同一プロセス/メモリ空間のKVプールを共有できるため、フェーズ分離によるメモリ断片化や再計算を避ける。

### 2. プリフィルを層単位へ細分化して気泡を抑える

長いプリフィル要求を丸ごと一つの仕事として走らせると、デコード側の反復終了や要求到着に合わせて資源を返せない。そこでプリフィルを層単位の短い仕事へし、デコード反復の境界でSM配分を再決定できるようにする。

### 3. 分割できない資源の競合を最悪時推定する

SMを分けても高帯域メモリ（High Bandwidth Memory; HBM）帯域などは共有される。MuxWiseは単独実行プロファイルと競合時の最大減速係数を持ち、同時実行時のTBT/プリフィル時間を安全側に見積もる。オンライン実測で推定値も補正する。

### 4. SLO対応ディスパッチャが「必要最小限のSM」をデコードへ与える

各反復で、現在バッチがTBT SLOを満たすのに必要なSM数を推定する。デコードへ必要量だけ確保し、残りをプリフィルへ回す。SLO余裕が大きいときはプリフィル量を増やし、厳しいときはデコードへ戻す。

## 評価

### 評価条件

| 項目 | 条件 |
|---|---|
| モデル | Llama系8B/70Bを中心とする複数規模 |
| GPU | A100を中心に、H100/H200を含む追加評価 |
| 比較 | 分離型配信、チャンク化プリフィル系、既存高スループット配信 |
| ワークロード | 入出力長、到着率、マルチターン再利用率が異なる実/合成負荷 |
| 制約 | TTFT/TBT等のSLOを満たした要求のみをgoodputとして集計 |
| 主指標 | SLO下ピークgoodput、GPU利用率、TBT、KV再利用 |

### 主な結果

| 観点 | 結果 | 解釈 |
|---|---:|---|
| SLO下ピークgoodput | 最先端基準比 平均 **2.20倍** | 同一GPUの遊休SMをフェーズ間で融通 |
| 最大改善 | **3.06倍** | 負荷比と再利用が多重化に合う条件 |
| 合成負荷の一部 | 方式間で約1.7〜9.5倍級の差が出る条件も報告 | 平均値より負荷依存性が大きい |
| マルチターン | 共有KVプールにより再利用を維持 | 分離配信で起きる再計算を避ける |
| 厳しいTBT | デコードへSMを優先 | 単純な最大利用率ではなくSLOを制約にする |

2.20倍は「1要求のモデル計算が2.20倍速い」値ではなく、SLOを満たして処理できる要求率の改善である。単体レイテンシとgoodputを混同しない必要がある。

## 既存研究との差

DistServe/Splitwise系はGPU単位でプリフィルとデコードを分ける。Sarathi-Serve/NanoFlow系は同一GPUで時間方向にチャンクを混ぜる。MuxWiseは同じGPU内で空間方向にSMを分け、両フェーズを独立に進める点が異なる。

## 限界・実装状況

SMの細粒度分割機能、CUDA実行制御、GPU世代ごとの共有資源特性へ依存する。HBM競合の上限推定もハードウェア・カーネル構成が変われば再較正が必要である。

また、プリフィル/デコード比がほぼ一定で既存分離配置が十分適合する負荷では、動的多重化の余地は小さい。
