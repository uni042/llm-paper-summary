# SGLang: Efficient Execution of Structured Language Model Programs

> 複数generation call・control flow・structured outputを含むLM programをfrontend languageで表現し、runtime側でRadixAttentionによるprefix KV reuse、cache-aware scheduling、structured decoding最適化をまとめて行うprogram-aware inference system。

## 概要

複雑なLLM applicationでは、一回のgenerationではなく、few-shot prompt、branch、parallel generation、tool use、JSONなどのstructured outputを組み合わせた複数callのprogramとして処理が進む。しかし一般的なserving APIでは各callが独立requestとして実行されるため、program内で繰り返されるprefixや分岐前のcontextを十分再利用できない。

SGLangはこの処理単位を**Language Model Program**として扱い、Pythonに埋め込んだfrontend languageと専用runtimeを組み合わせる。runtimeはprogram構造から得られるprefix reuseやparallelismを利用し、複数callを単純に逐次API実行するより効率よく処理する。

## 手法

### 1. Frontend language

`gen`、`select`などgeneration用primitiveと、`fork` / `join`などparallelism制御を提供する。通常のPython control flowと組み合わせられるため、tree search、few-shot evaluation、agent loopなどを一つのprogramとして表現できる。

interpreterはprompt stateをstreamとして管理し、依存関係を保ちながらgeneration operationを非同期にruntimeへ送る。

### 2. RadixAttention

program内・request間で共有されるtoken prefixをradix treeへ登録し、それに対応するKV cacheを保持する。新requestが来ると最長一致prefixを探し、そのKVを再利用して同じprefixのprefillを省く。

単純なexact-prefix cacheと違い、radix treeにより異なる長さの共通prefixを階層的に共有できる。memoryが不足するとLRUに基づいてcache nodeをevictする。

### 3. Cache-aware scheduling

同じprefixを共有するrequestを近いタイミングで処理し、KVがcacheから追い出される前に再利用する。これにより、単にKV cache機構を用意するだけでなく、**scheduler側もcache localityを意識する**。

### 4. Structured output decoding

JSONや選択肢制約など、出力tokenに文法制約がある場合はfinite-state machineを使う。SGLangはFSM representationとtoken mask処理を圧縮・最適化し、structured decodingのCPU overheadを下げる。

## 評価

NeurIPS 2024論文では、agent control、logical reasoning、few-shot learning、JSON decoding、RAG、multi-turn chat、multi-modal modelなど複数workloadを評価している。

既存inference systemに対して、taskによって**最大6.4×のthroughput向上**を報告する。

利得の中心はworkloadによって異なり、

- repeated / branching promptではRadixAttentionによるKV reuse
- multi-call workflowではfrontend / runtimeによるparallel execution
- constrained outputではstructured decoding最適化

がそれぞれ効く。

## 既存研究との差

### vLLM / PagedAttentionとの違い

vLLMはKV memory allocationをpage化してfragmentationを減らし、continuous batchingを大きくする。SGLangはその上位で、**どのprefix KVをrequest間で残して再利用するか**をradix treeで管理する。

PagedAttentionがmemory allocator寄りなのに対し、RadixAttentionはprefixの意味的なtoken sequence構造を利用したcache reuse機構である。

### Parrotとの違い

ParrotはSemantic Variableで複数request間のdata dependencyやprompt sharingをbackendへ見せる。SGLangはapplicationを専用LM programming languageとして記述し、**program execution runtimeそのものを提供する**。

Parrotがapplication DAG-aware schedulingを中心にするのに対し、SGLangはprefix KV cache、structured decoding、parallel generationなどexecution engine側の最適化範囲が広い。

### Pensieve / CachedAttentionとの違い

Pensieve / CachedAttentionは主にmulti-turn conversation間で過去KVを保存する。RadixAttentionはconversation sessionに限定せず、few-shot prefix、tree search branch、system prompt、multi-query workloadなど任意のtoken prefix共有を統一的に扱う。

## 限界

- 大きな効果にはrequest / program間で再利用できるprefixやmulti-call structureが必要。
- RadixAttentionはKVを保持するため、cache容量とactive request memoryの配分が競合する。
- cache-aware schedulingはlocalityを優先するため、strict fairnessや個別SLOとは別途調整が必要。
- frontend languageを最大限利用するにはapplication側をSGLangとして記述する必要がある。
- structured output高速化はgrammar complexityやtokenizerとの対応関係に影響される。

## 一般的な実装上の含意

LLM servingではrequestごとにKVを捨てるのではなく、**token prefixをkeyとするpersistent cache**として管理すると、multi-turn chat以外にもfew-shot prompt、agent tree、RAG templateなど広いworkloadでprefillを再利用できる。

また、cache機構単体よりもschedulerをcache-awareにすることが重要で、共有prefixを持つrequestを近くで実行するほどreuse opportunityを実際のspeedupへ変換しやすい。
