# SGLang: Efficient Execution of Structured Language Model Programs

> 複数のLLM callや条件分岐をruntimeが1つのprogramとして理解し、共有prefixのKV再利用・並列実行・structured output生成をまとめて効率化するinference system。

## 概要

複雑なLLM applicationでは、1回のgenerationだけでなく、few-shot prompt、複数branch、parallel generation、tool use、JSON出力などを組み合わせて複数回modelを呼ぶ。

通常のserving APIでは各callが独立requestとして見えるため、call間で同じprefixを何度もprefillしたり、本来同時に進められるcallを逐次実行したりすることがある。

SGLangはapplicationを**複数LLM callを含む1つのprogram**として記述し、runtimeがその構造を理解して実行する。これによりprefix KVの再利用、並列実行、出力形式の制約処理をまとめて最適化する。

## 手法

### 1. LLM処理をprogramとして記述する

SGLangはgeneration、候補選択、branchの複製・合流などを表す命令を提供し、通常のPythonのif / loopなどと組み合わせられる。

これによりtree search、few-shot evaluation、agent loopなどで「どのLLM callがどのcallに依存するか」をruntime側が把握できる。

### 2. 共有prefixを木構造で保存してKVを再利用する

SGLangは、これまで処理したtoken prefixを木構造で管理し、それぞれに対応するKV cacheを保持する。この仕組みを論文では **RadixAttention** と呼ぶ。

新requestが来ると、既存cacheの中から最も長く一致するprefixを探し、その部分のKVを再利用する。例えば同じsystem promptやfew-shot exampleを使うrequestでは、共通部分のprefillを省ける。

memoryが足りなくなった場合は、長く使われていないprefix KVから削除する。

### 3. KVを再利用しやすい順番でrequestを処理する

同じprefixを共有するrequestを近い時刻に処理すると、KVがmemoryから削除される前に再利用しやすい。

そのためschedulerもcacheの状態を見て、prefix共有の大きいrequestをまとめやすくする。

### 4. JSONなど出力形式の制約を効率よく処理する

JSONや固定候補など、次に生成できるtokenが制限されるtaskでは、毎tokenごとに「許可されるtoken」を計算する必要がある。

SGLangはこの制約処理を圧縮・再利用して、CPU側の判定costを減らす。

## 評価

NeurIPS 2024論文ではagent control、logical reasoning、few-shot learning、JSON decoding、RAG、multi-turn chat、multi-modal modelなどを評価している。

既存inference systemに対して、taskによって**最大6.4倍のthroughput向上**を報告する。

改善理由はworkloadによって異なり、

- repeated / branching promptではprefix KV再利用
- 複数LLM callでは並列実行
- JSONなどの出力では制約判定の高速化

が主に効く。

## 既存研究との差

### vLLMとの違い

vLLMはKV cacheを固定長blockで効率よく配置することが中心。SGLangはその上で、**どのtoken prefixのKVをrequest間で残して再利用するか**まで扱う。

### Parrotとの違い

Parrotも複数LLM callの依存関係や共有promptをserving側へ伝える。SGLangはさらに専用program表現とruntimeを持ち、prefix KV cacheやstructured output生成までexecution engine側でまとめて扱う。

### Pensieve / CachedAttentionとの違い

Pensieve / CachedAttentionは主に同じconversationのturn間でKVを再利用する。SGLangはconversationに限らず、system prompt、few-shot prompt、tree searchのbranchなど**任意の共有prefix**を対象にする。

## 限界

- 大きな効果を得るにはrequest間で共有できるprefixや複数callの構造が必要。
- prefix KVを長く残すほどactive request用のVRAMと競合する。
- prefix再利用を優先したrequest順序は、公平性や個別SLOと衝突する場合がある。
- 最大限利用するにはapplication側をSGLangのprogramとして記述する必要がある。
- structured outputの高速化効果は文法の複雑さやtokenizerに依存する。

## 一般的な実装上の含意

LLM servingではKVをrequestごとに捨てず、**token prefixをkeyにしたrequest間cache**として扱うと、multi-turn chat以外にもfew-shot、agent tree、RAG templateなどでprefillを再利用できる。

またcacheを用意するだけでなく、共有prefixを持つrequestを近いタイミングで処理するschedulerと組み合わせる方が再利用率を高めやすい。
