# SGLang: Efficient Execution of Structured Language Model Programs

> 複数のLLM呼び出しや条件分岐をランタイムが1つのプログラムとして理解し、共有接頭辞のKV再利用・並列実行・構造化出力生成をまとめて効率化する推論システム。

## 概要

複雑なLLMアプリケーションでは、1回の生成だけでなく、few-shotプロンプト、複数分岐、並列生成、ツール利用、JSON出力などを組み合わせて複数回モデルを呼ぶ。

通常のサービングAPIでは各呼び出しが独立リクエストとして見えるため、呼び出し間で同じ接頭辞を何度もプリフィルしたり、本来同時に進められる呼び出しを逐次実行したりすることがある。アプリケーション側では構造を知っていても、推論サーバ側へその情報が伝わらなければ再利用機会を失う。

SGLangはアプリケーションを**複数LLM呼び出しを含む1つのプログラム**として記述し、ランタイムがその構造を理解して実行する。これにより接頭辞KVの再利用、並列実行、出力形式の制約処理をまとめて最適化する。

中核は「プログラミング言語を追加した」ことだけではない。フロントエンドで明示した呼び出し関係を、バックエンドのKVキャッシュ・スケジューリング・構造化デコードへつなぐことで、アプリケーション構造をシステム最適化へ利用する点にある。

NeurIPS 2024の評価では、エージェント制御・論理推論・JSON・RAGなどで既存推論システム比最大6.4倍のスループット向上を報告した。

## 手法

### 1. LLM処理をプログラムとして記述し、依存関係をランタイムへ渡す

SGLangは生成、候補選択、分岐状態の複製、複数生成の並列実行などを表す命令を提供し、通常のPythonの `if` / `loop` と組み合わせられる。文字列と生成結果を「状態」に蓄積していくため、後続呼び出しがどのプロンプト履歴を継承するかを明示できる。

これにより木探索、few-shot評価、エージェントループなどで「どのLLM呼び出しがどの呼び出しに依存するか」をランタイム側が把握できる。分岐前まで同じ状態を共有する複数経路は、文字列だけでなく対応するKV状態も共有候補として扱える。

アプリケーション側が独立HTTP要求を逐次投げる場合と違い、並行可能な生成をランタイムが一度に認識できるため、GPUへまとめて投入する余地も生まれる。つまりフロントエンド表現は記述量削減だけでなく、後段最適化に必要な意味情報を供給する役割を持つ。

### 2. RadixAttentionで共有接頭辞を木構造へ保存してKVを再利用する

SGLangは、これまで処理したトークン接頭辞を基数木（radix tree）で管理し、それぞれに対応するKVキャッシュを保持する。この仕組みを論文では **RadixAttention** と呼ぶ。木の辺にはトークン列が付き、根からある節点までの経路が1つの接頭辞を表す。

新リクエストが来ると、入力トークン列と木を照合し、既存キャッシュの中から最も長く一致する接頭辞を探す。一致部分のKVは再計算せず、その直後の未計算トークンからプリフィルを再開する。例えば同じシステムプロンプトやfew-shot例を使う要求では、共通部分を何度も処理する必要がない。

分岐プログラムでは、同じ親状態から複数の子を作ると、親までの木経路を共有し、子ごとに異なる末尾だけ追加できる。会話セッション専用の固定キャッシュと違い、どの要求の組でもトークン接頭辞が一致すれば同じ構造へ統合できる。

メモリが足りなくなった場合は、参照中の経路を保護しつつ、長く使われていない葉側のKVから削除する。削除単位を木の節点／接頭辞として扱うため、ある要求で不要になったKVでも別要求が同じ接頭辞を参照している間は残せる。

### 3. 接頭辞キャッシュを再利用しやすい順番でリクエストを処理する

同じ接頭辞を共有するリクエストを近い時刻に処理すると、KVがメモリから削除される前に再利用しやすい。反対に無関係な要求を多数挟むと、共有KVが追い出されて再計算が必要になる。

そのためスケジューラもキャッシュ木の状態を見て、現在バッチと長い接頭辞を共有する要求を優先する。単純な先着順ではなく、次に処理する要求の選択が将来のキャッシュヒット率へ影響することを利用する。

この方針は計算量を減らせる一方、待ち時間だけを基準にした公平な順序とは一致しない場合がある。したがってSGLangの接頭辞指向スケジューリングは、共有プロンプトが多いワークロードほど効きやすく、厳しい個別SLOや公平性が主目的の場合には別の優先度制御との統合が必要になる。

### 4. 構造化出力では有限状態機械を圧縮し、許可トークン判定をまとめる

JSONや正規表現で指定された形式の出力では、現在までの文字列から「次に許されるトークン」を判定し、許可されない語彙をマスクする必要がある。素朴には1トークン生成するたびCPU側の有限状態機械（finite-state machine; FSM）を進め、GPUと同期する。

SGLangは、複数のトークンを連続して確定できる区間をFSM上でまとめ、状態遷移を圧縮する。ある状態から次の分岐点まで選択肢が一意なら、その区間を1トークンずつCPU判定する必要がない。これによりGPU生成とCPU制約処理の往復回数を減らす。

さらに構造化出力の制約状態を再利用できる形にし、同じ文法を多数要求で使う場合の準備コストも抑える。高速化の源泉はモデルの確率分布を近似することではなく、**生成可能集合を求める制御処理を少ない同期で実行する**ことにあるため、制約を満たす出力という意味上の正しさは維持する。

## なぜこの設計で速くなるのか

複雑なLLMプログラムでは、モデル1回のデコード速度だけを上げても、同じ接頭辞の再計算、複数呼び出しの逐次化、構造化出力のCPU同期が残る。SGLangはこれらをプログラム全体の実行グラフとして認識し、重複計算と制御待ちを別々に削る。

RadixAttentionはプリフィル計算量を減らし、プログラム表現は並行可能な呼び出しをまとめ、圧縮FSMは構造化デコードのCPU介入頻度を下げる。どの最適化が効くかはワークロードによって異なるため、論文の最大6.4倍を単一のKVキャッシュ最適化の倍率として読むのは不適切である。

一方、毎回完全に異なるプロンプトを1回だけ生成し、自由形式出力しか使わない単純ワークロードでは、接頭辞再利用や構造化出力最適化の機会は少ない。その場合は基礎となるバッチ処理・カーネル性能の差が支配的になる。

## 評価

NeurIPS 2024論文ではエージェント制御、論理推論、few-shot学習、JSONデコード、RAG、マルチターン会話、マルチモーダルモデルなどを評価している。

既存推論システムに対して、タスクによって**最大6.4倍のスループット向上**を報告する。改善理由はワークロードによって異なり、繰り返し／分岐プロンプトでは接頭辞KV再利用、複数LLM呼び出しでは並列実行、JSONなどの出力では制約判定の高速化が主に効く。

したがって評価値を見るときは、単純会話サービングと、木探索やJSON生成のような構造化プログラムを分ける必要がある。SGLangの主張は「全LLM推論を常に6.4倍高速化」ではなく、複数呼び出しの構造をランタイムへ見せた場合に失われていた再利用・並行性を回収できるというものである。

## 既存研究との差

### vLLMとの違い

vLLMはKVキャッシュを固定長ブロックで効率よく配置することが中心。SGLangはその上で、**どのトークン接頭辞のKVを要求間で残して再利用するか**まで扱う。

### Parrotとの違い

Parrotも複数LLM呼び出しの依存関係や共有プロンプトをサービング側へ伝える。SGLangはさらに専用プログラム表現とランタイムを持ち、接頭辞KVキャッシュや構造化出力生成まで実行エンジン側でまとめて扱う。

### Pensieve / CachedAttentionとの違い

Pensieve / CachedAttentionは主に同じ会話のターン間でKVを再利用する。SGLangは会話に限らず、システムプロンプト、few-shotプロンプト、木探索の分岐など**任意の共有接頭辞**を対象にする。

## 限界

- 大きな効果を得るにはリクエスト間で共有できる接頭辞や複数呼び出しの構造が必要。
- 接頭辞KVを長く残すほど実行中リクエスト用のVRAMと競合する。
- 接頭辞再利用を優先したリクエスト順序は、公平性や個別SLOと衝突する場合がある。
- 最大限利用するにはアプリケーション側をSGLangのプログラムとして記述する必要がある。
- 構造化出力の高速化効果は文法の複雑さやトークナイザに依存する。

## 一般的な実装上の含意

LLMサービングではKVをリクエストごとに捨てず、**トークン接頭辞をキーにしたリクエスト間キャッシュ**として扱うと、マルチターン会話以外にもfew-shot、エージェント木探索、RAGテンプレートなどでプリフィルを再利用できる。

またキャッシュを用意するだけでなく、共有接頭辞を持つリクエストを近いタイミングで処理するスケジューラと組み合わせる方が再利用率を高めやすい。キャッシュ配置と要求順序を別々に最適化しないことが重要になる。
