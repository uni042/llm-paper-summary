## 概要

分散LLMサービングでは、同じプロンプト接頭辞を持つ要求を同じインスタンスへ送れば、保存済みのキー・バリューキャッシュ（key-value cache; KV cache）を再利用してプリフィル（prefill）計算を省ける。しかし人気接頭辞へ要求が偏ると、そのインスタンスだけ待ち行列が伸びる。逆に最小負荷ノードへ均等に振ると、キャッシュ済み接頭辞が別ノードへ散り、再計算が増える。DualMapはこの二律背反を、単一の写像先ではなく「2つの候補」を持たせることで解く。

各要求の接頭辞を2個の独立ハッシュ関数へ入力し、常に2つの候補インスタンスを得る。同じ接頭辞は同じ候補対へ集まるためキャッシュ局所性を保ちつつ、二者択一（power of two choices）の負荷分散効果を利用できる。さらに初回トークン時間（time to first token; TTFT）のサービス水準目標（service-level objective; SLO）を超えそうな場合だけ負荷優先へ切り替え、ホットスポット時は候補対の中で要求を移し、クラスタ伸縮時は二重ハッシュリングで再写像範囲を局所化する。

## 問題設定

キャッシュ親和型のスケジューラは、共有接頭辞を持つ要求を同一ノードへ集めるためKVキャッシュ命中率は高い。しかし実トラフィックの接頭辞人気度は歪んでおり、頻繁に呼ばれるツールや共通system promptが特定ノードをホットスポット化する。論文の8インスタンス・Qwen2.5-7Bの動機実験でも、Conversation workloadでは純キャッシュ親和方式の命中率がLeast Loadedより1.21倍高い一方、負荷変動係数は悪化する。

既存のPreble、Mooncake系は1つの写像空間の中で、ある要求はキャッシュ優先、別の要求は負荷優先という切替を行う。このため一方を改善すると他方を犠牲にしやすい。DualMapは要求ごとに2候補を固定して、局所性を残したまま負荷逃がし先を常時確保する。

## 手法

### 二重写像と適応接頭辞長

global schedulerは接頭辞を2個の独立ハッシュ関数へ通し、2つの異なる推論インスタンスを候補にする。同じ接頭辞を共有する要求群は同じ候補対へ写るので、全クラスタへ散らすよりKVキャッシュが集約される。

固定長のhash keyでは、長すぎれば共有部分を越えて局所性を失い、短すぎれば異なる要求まで衝突する。そこでprefix hotness treeを持ち、スライディング窓内のトラフィック比率で接頭辞のhotnessを測る。hot prefixは木を下へ伸ばしてhash keyを長くし分散を増やし、coldになれば短く戻して再利用を高める。

### SLO-aware routing

2候補のうち、通常はキャッシュ再利用量が大きい側を選ぶ。各候補について待ち時間と再計算量からTTFTを見積もり、キャッシュ優先側の予測TTFTがSLOを超えるときだけ負荷の軽い候補へ切り替える。

負荷指標にはpending prefill token数を用いる。プリフィル時間がtoken数に概ね比例するため、GPU/NPUがSLO内で処理できるpending token数を閾値として事前に定め、キャッシュ親和から負荷優先へ切り替える。

### hotspot-aware rebalancing

既にqueueへ入った要求も、ノードが過負荷になれば第2候補へ移せる。移動候補ごとにsource/targetのqueue delayとcache reuse後のcompute timeを合算し、TTFT改善量が正になる要求を優先する。全ノード探索ではなく元の候補対だけで移動するため、負荷逃がしでキャッシュ局所性を完全には壊さない。

### 二重ハッシュリングによる伸縮

ノード追加・削除時には2本のconsistent hash ringを更新する。相対位置で候補を決めるため、クラスタ全体を再写像せず、変更ノード周辺のprefixだけが影響を受ける。これによりautoscaling時のcache cold化を抑える。

## 評価条件

| 項目 | 条件 |
|---|---|
| runtime | vLLM上のglobal scheduler |
| cluster | 各node 8×Ascend 910B4 32GB HBM または910B3 64GB HBM、1.5TB DRAM |
| workload | Conversation、Tool&Agent等の実ワークロード |
| 主SLO | TTFT 5秒 |
| 指標 | effective request capacity、goodput、P50/P90 TTFT、E2E latency、cache hit rate、load CV |
| baseline | Cache Affinity、Least Loaded、Preble、Min-TTFT/Mooncake系 |

## 主要結果

実ワークロードで、同一TTFT SLOを満たす有効要求容量を既存方式比で最大2.25倍に改善する。評価ではP90 TTFTも一貫して低下し、単純なcache hit最大化ではなく「SLOを守って処理できる要求数」が増える。

二重写像は同じprefixの要求を最大2ノードへ限定するため、要求数mが十分大きいと命中率は純Cache Affinityへ近づく。一方、2候補のうち軽い側を使えるため、1候補hashより最大負荷の偏りを抑えられる。追加候補を3個以上へ増やすと負荷分散の限界利得が小さい一方、同prefixがより多くのnodeへ散ってcache localityを損なうため、2候補を採用する。

## 既存研究との差

PrebleやMooncake/Dynamo系は単一のrouting空間でcache-awareとload-awareを切り替える。DualMapは最初からprefixごとに2つの安定候補を作り、その候補集合内でSLO routingとrebalancingを行う点が異なる。したがって負荷逃がしのたびに全クラスタから新しい行き先を選ばず、cache affinityを保持しやすい。

## 限界

TTFT予測はpending prefill tokenを中心に組み立てており、decode側のmemory exhaustionや複雑なcontentionが強い条件では推定誤差が増える。論文はこの条件を補遺で議論するが、あらゆるhardware/runtimeへ同じ閾値を移植できるわけではない。また主実機はAscendクラスタであり、CUDA GPUクラスタで同じ絶対性能になることは評価していない。
