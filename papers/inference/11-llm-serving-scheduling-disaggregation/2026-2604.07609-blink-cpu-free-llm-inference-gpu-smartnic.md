# Blink: CPU-Free LLM Inference by Delegating the Serving Stack to GPU and SmartNIC

> request処理をSmartNIC、tokenごとのbatching・scheduling・KV cache管理をGPU常駐制御へ移し、steady-state推論のcritical pathからhost CPUを外してlatency・throughputとCPU干渉耐性を改善する。

## 問題
現在のLLM servingはtensor計算をGPUで行っていても、request admission、continuous batching、KV cache block管理、CUDA dispatchなどをhost CPUがtokenごとに仲介する。この細粒度のhost-device往復は、CPUが別workloadと共存したときのcache / TLB汚染やscheduler jitterをそのままinter-token latencyへ持ち込む。

Blinkは、この問題をCPU側のmicro-optimizationではなく**control pathの配置そのもの**の問題として扱う。論文のmotivating measurementでは、H100上のLlama-3 8BをvLLMで動かしCPU干渉を加えると、throughputが7,475 tok/sから1,961 tok/sへ低下し、P99 TTFTが150 msから20,959 msへ増大する。

## 新規性
Blinkの中心は、steady-state autoregressive inferenceからhost CPUを外し、役割をSmartNICとGPUへ分解したend-to-end architectureである。

- SmartNIC：protocol parsing、request admission、network側のrequest handlingを担当。
- GPU：CUDA persistent kernelでcontinuous batching、iteration-level scheduling、Paged KV cache管理などのcontrol planeを常駐実行。
- network→GPU：一方向RDMA（one-sided RDMA）と共有ring bufferを使い、host memoryを経由せずGPU VRAMへ直接運ぶ。

単にnetwork I/OだけをSmartNICへoffloadするのではなく、autoregressive decodingでtokenごとに必要になるcontrol loopまでGPUへ移す点が主要な差である。

## 手法
GPU上のpersistent control kernelは、request queue、backpressure、fairness、進行状態をGPU-resident data structureで管理する。これにより各decode iterationのたびにCPUへ戻ってbatch membershipやKV block tableを更新する必要をなくす。

SmartNIC側はnetwork requestを処理してRDMAでGPU memoryへ入力を届ける。host CPUは初期化などsteady-state外では必要だが、論文でいう「CPU-free」はhost CPUを**推論のcritical pathから除外する**意味であり、machineからCPU自体をなくす意味ではない。

## 評価条件
実機testbedはNVIDIA H100 96 GB HBM3、2× Intel Xeon Gold 6336Y、256 GB DDR5、ConnectX-6 200 Gbps、BlueField-3 DPU（16 ARM Cortex-A78 / 32 GB）で構成される。DPU frontendとbackend serverは200 Gbps RDMAで接続する。

評価modelはLlama-3 8B、Phi-4 15B、Qwen-3 32B、Qwen-3 30B-A3B。ShareGPT v3 traceを用い、1〜32 request/sの13段階のoffered loadを各60秒測定する。比較対象はTensorRT-LLM v1.1.0、vLLM v0.13.0、SGLang v0.5.8である。

## 主要結果
- isolated環境でもpre-saturation P99 TTFTを最大8.47×、P99 TPOTを最大3.40×改善し、decode throughputを最大2.1×向上。
- CPU interference下ではbaselineが大幅劣化する一方、Blinkは概ねisolated時の性能を維持し、decode throughputで最大6.46×、request throughputで最大4.87×高い。
- energy/tokenはisolatedで最大48.6%、interference下で最大70.7%低減。
- Qwen-3 30B-A3Bのpre-saturation summaryではBlinkのP99 TTFT 1,397.5 ms、P99 TPOT 35.5 ms、saturation時throughput 4.85 req/sに対し、TensorRT-LLMは4,814.7 ms / 65.8 ms / 3.61 req/s、vLLMは8,919.2 ms / 90.9 ms / 2.91 req/s、SGLangは11,839.8 ms / 120.8 ms / 2.62 req/s。

## 限界
- 評価はH100 + BlueField-3 + 200 Gbps RDMAというdatacenter向け構成で、一般的なGPU serverへそのまま適用できるとは限らない。
- controlled comparisonではchunked prefill、prefix caching、CPU offloadingを無効化しており、Blink v1自体もこれらをまだ取り込んでいない。
- host CPUをcritical pathから外す代わりにSmartNIC/DPUとGPU persistent controlへ機能を移すため、hardware / runtime integrationの要求は高い。
- 論文v1ではBlinkをpublication後にopen-source予定としており、一次資料上で公開済み公式実装は確認できない。

## 既存研究との差
vLLM、SGLang、TensorRT-LLMなどはhost schedulingをoverlap・graph化して負担を隠す方向だが、Blinkはhost involvement自体をsteady-state loopから除く。従来のSmartNIC inference offloadが主にdata pathを対象としたのに対し、Blinkはautoregressive LLM特有のtoken-level control pathをGPU常駐化する。

## 一般的な実装への示唆
高速GPUほどhost側の短いscheduler処理やkernel dispatchが相対的に無視できなくなる。CPU処理をさらに高速化するだけでなく、control stateをGPU側へ寄せてdevice-resident schedulerを作る設計は、SmartNICを使わない構成でも検討価値がある。一方、network ingressまでCPU-freeにする効果を得るにはGPUDirect RDMA等のI/O基盤が必要になる。
