# Blink: CPU-Free LLM 推論 by Delegating the サービング Stack to GPU and SmartNIC

> Blinkは、定常状態のLLM推論でCPUが毎トークン行っていたバッチ更新・スケジューリング・KVキャッシュ管理・GPU起動をGPU常駐制御へ移し、ネットワーク要求処理をSmartNICへ移す。SmartNICとGPUはGPUメモリ上の共有リングバッファを介して直接通信し、ホストCPUを推論のクリティカルパスから外す。

## 問題
現在のLLMサービングでは、テンソル計算自体がGPU上でも、要求受付、連続バッチ処理（連続 batching）、KVキャッシュのブロック管理、CUDAグラフ起動などの制御をCPUが反復ごとに行うことが多い。自己回帰デコードではこの制御が1トークンごとに繰り返されるため、短いCPU処理でも数百トークンにわたり累積する。

CPUが他ワークロードと共存すると、CPUスケジューラの揺らぎだけでなく、最終レベルキャッシュ（LLC）や変換索引バッファ（TLB）の汚染、ページウォークの遅延が制御処理へ入る。GPU計算時間が変わらなくても、次のGPU処理をCPUが発行するまでの隙間が伸びるため、GPUが待機する。

論文の動機実験ではH100上のLlama-3 8BをvLLMで実行しCPU干渉を加えると、スループットが7,475 トークン/sから1,961 トークン/sへ低下し、P99の最初のトークンまでの時間（時間-to-先-トークン; TTFT）が150 msから20,959 msへ増えた。巨大ページ、CPU固定、キャッシュ分割なども一部の干渉は減らすが、CPUを毎トークン使う構造そのものは残る。

Blinkはこの問題をCPUコードの高速化ではなく、**定常状態の制御経路（制御 path）からホストCPUを除く配置問題**として解く。ホストCPUは起動時のモデル読み込み・CUDAグラフ準備など供給面だけを担当し、要求到着後の主要経路はSmartNICとGPUだけで進める。

## 新規性
Blinkはデータ経路だけをSmartNICへ移す方式ではない。SmartNICはHTTP/SSE処理、要求追跡、トークン化、GPUへの遠隔直接メモリアクセス（RDMA）を担当し、GPUは要求状態・連続バッチ・KVキャッシュ・推論グラフ起動を担当する。両者の唯一の共有点をGPUメモリ上のリングバッファにする。

これにより、ネットワーク→CPUメモリ→GPUという入力経路と、GPU→CPUスケジューラ→GPUというトークンごとの制御往復を両方避ける。論文でいう「CPU-free」は機械からCPUをなくす意味ではなく、**初期化後の推論クリティカルパスにホストCPUを置かない**という意味である。

## 手法

### 1. GPU常駐スケジューラが要求状態を自分で進める
GPU側では256スレッド・1スレッドブロックの永続CUDAカーネル（永続 CUDA カーネル）が終了せずに動き続ける。入力はGPUメモリ上のリングバッファで、各スロットにはプロンプト位置、トークン数、生成進捗、状態などが置かれる。スケジューラはスロットを並列走査し、新しい要求を原子的な比較交換（compare-and-swap; CAS）で確保する。

確保後は、プリフィルかデコードかに応じた事前捕捉済みCUDAグラフをGPU側から起動し、サンプリング結果がGPUメモリへ書かれるまで監視する。新しいトークンが得られたらリングバッファの進捗と出力位置を更新し、次の反復へ進む。CPUへ「このトークンが終わったので次のバッチを作ってほしい」と戻らない。

4096スロットの走査は256スレッドで分担し、論文では完全走査が約15 µsと報告される。要求数が増えても単一CPUスレッドが全要求を逐次検査する構造ではなく、GPU上の並列走査と原子操作で受付を行う。

### 2. GPUからCUDAグラフを直接起動し、120回上限を窓方式で回避する
通常のCUDAグラフはホストから起動するが、それでは毎トークンCPUを使う構造が残る。BlinkはGPUから子グラフを起動するデバイス側グラフ起動（device-side CUDA graph launch）を使い、推論グラフ自体を永続スケジューラから直接発行する。論文ではfire-and-forget起動が代表形状で約2 µsとされ、ホスト起動より短い。

ただしfire-and-forgetには、1つの親グラフ実行から未完了の起動を120回までしか発行できない制約がある。512トークンを生成するだけでも上限へ達するため、そのままでは長い生成を継続できない。Blinkは起動回数をGPUメモリで数え、120回に達したら1回だけ末尾起動（末尾 launch）で永続スケジューラ自身を新しいグラフ実行へ置き換える。

要求状態、KVキャッシュ、リングバッファ位置は永続GPUメモリにあるため、スケジューラのグラフ実行を更新しても会話状態は失われない。121反復中120回を低遅延のfire-and-forgetで処理し、上限回避用の高コスト起動をまれに挟むことで、CPUへ戻らず無制限長の生成を可能にしている。

### 3. デコード中に新着要求を走査し、1反復境界でプリフィルを挿入する
連続バッチ処理では、実行中のデコードを進めながら新しい要求も受け入れる必要がある。Blinkはデコード用CUDAグラフが非同期実行されている間に、永続スケジューラがリングバッファを走査して新規プリフィル候補を探す。走査時間をGPU計算の裏へ重ねる。

候補が見つかると、(1) 待機中プリフィルがある、(2) 完了予定分を含めてバッチ枠が空く、(3) CUDAグラフ起動窓にプリフィルと再開デコードを発行できる余裕がある、という3条件を確認する。条件を満たした場合だけ現在のデコードを1反復境界で止め、新規要求のプリフィルを実行してバッチへ併合し、その後デコードを再開する。

出力は更新されたデコードバッチであり、この一連の処理も同じ永続カーネル内部で完結する。新規要求は原則として1デコード反復以内に受け入れられるため、デコードスループットを維持しながらTTFTが無制限に伸びるのを防ぐ。評価では先着順（FCFS）を使い、スケジューリング方針自体ではなくCPU除去の効果を比較している。

### 4. GPUリングバッファをDPUとの唯一の共有状態にする
リングバッファはGPUメモリ上にあり、固定数の要求スロットと入力・生成トークン用領域からなる。各要求は `empty → prefill_pending → prefill_processing → decode_processing → decode_completed → empty` の状態機械で進み、デコード一時停止用状態も持つ。所有権更新には原子的CASとメモリフェンスを使う。

この設計ではSmartNICとGPUがCPU上の共有キューやRPCを介さず、同じGPUメモリ状態を見る。SmartNICは新しいプロンプトを書き込んで状態を「受付待ち」に変え、GPUは処理後に生成数と状態を更新する。中間コピーを挟まず、RDMAから見える更新順序をメモリフェンスで保証する。

KVキャッシュ管理もGPU常駐スケジューラ側にあり、要求状態と同じ制御ループから更新される。そのためトークン生成ごとにCPUがKVブロック表を作り直してGPUへ送る必要がない。これが「ネットワークだけCPU-free」ではなく「トークン制御までCPU-free」にする主要部分である。

### 5. SmartNICが要求受付とトークン送受信をRDMAで直接行う
BlueField DPU側はOpenAI互換HTTP/SSE前段、要求追跡、空きスロット管理、トークン読み出しを担当する。新規要求ではDPUローカルでプロンプトを準備し、一方向RDMA（one-sided RDMA）でGPUリングバッファとトークン領域へ直接書き込む。CPUメモリへ一度置いてからGPUへコピーする経路を通らない。

DPUは毎回4096スロットを遠隔走査せず、空きスロット情報をローカルキャッシュして定期的に一括更新する。生成トークンはバックグラウンド読取器がGPUリングバッファを一括ポーリングし、新着トークンを検出するとデトークン化してSSEで利用者へ返す。新規スロットを優先走査することで最初のトークン読出し遅延も抑える。

SmartNICのARMコアが新しいボトルネックにならないよう、Blinkはトークン化もキャッシュ局所性を意識した専用実装にする。論文ではBlueField-3上の実装が対象入力長でHuggingFaceトークナイザより8～19.7倍高速と報告している。したがってCPU処理をDPUへ単純移植しただけではなく、DPUの少数コア向けに前段処理も作り直している。

## なぜこの設計で速くなるのか
Blinkが減らすのはモデルの浮動小数点演算ではなく、GPU計算の間に挟まるCPU待ちとデータコピーである。同じTensorRTエンジンを使ったCPU常駐スケジューラとの比較でも、CPU経由では全体完了時間が1.16～1.70倍長くなった。これはモデル実装を変えず、制御配置だけでも差が出ることを示す。

特にGPU計算が短いモデルほど、一定量のCPU制御時間が1反復に占める割合が大きい。Qwen-3 30B-A3Bのような疎MoEでは総30Bパラメータ中約3Bだけがトークンごとに有効になりGPU反復が短いため、CPU制御除去の相対効果が大きい。一方、Qwen-3 32BのようにGPU計算自体が支配的な条件では利得が小さくなる。

## 評価条件
実機テストベッドはNVIDIA H100 96 GB HBM3、2×Intel Xeon Gold 6336Y、256 GB DDR5、ConnectX-6 200 Gbpsで、Blink前段は別マシン上のBlueField-3 DPU（16 ARM Cortex-A78、32 GB）から200 Gbps RDMAで接続する。

対象モデルはLlama-3 8B、Phi-4 15B、Qwen-3 32B、Qwen-3 30B-A3Bで、ShareGPT v3トレースを使う。1～32 リクエスト/sの13負荷点を各60秒測定し、TensorRT-LLM v1.1.0、vLLM v0.13.0、SGLang v0.5.8と比較する。公平な比較のためチャンク化プリフィル、接頭辞キャッシュ、CPUオフロードは無効化されている。

## 主要結果
隔離環境でも、Blinkは飽和前P99 TTFTを最大**8.47倍短縮**、P99の1出力トークンあたり時間（時間-per-出力-トークン; TPOT）を最大**3.40倍短縮**し、デコードスループットを最大**2.1倍**向上した。Qwen-3 30B-A3BではBlinkのP99 TTFT 1,397.5 ms、P99 TPOT 35.5 ms、飽和点4.85 req/sに対し、TensorRT-LLMは4,814.7 ms / 65.8 ms / 3.61 req/sだった。

CPU干渉下ではBlinkのTTFT・TPOT・飽和点スループットが隔離時の約0.92～1.14倍範囲に保たれる一方、CPU依存比較系は大きく劣化した。論文全体では干渉下で最大**6.46倍のデコードスループット**、最大**4.87倍の要求スループット**を報告する。

エネルギー/トークンは隔離時に最大48.6%、CPU干渉下で最大70.7%低減した。比較系と壁面電力が大きく違わない条件でスループットが高いため、1トークンあたりへ割り付けるエネルギーが下がるという結果である。

## 限界
評価はH100 + BlueField-3 + 200 Gbps RDMAというデータセンター向け構成で、一般的な単一GPUサーバーや個人PCへそのまま適用できない。ネットワーク前段までCPUを外すにはGPUDirect RDMAに相当する直接I/O基盤とSmartNIC/DPUが必要になる。

制御比較ではチャンク化プリフィル、接頭辞キャッシュ、CPUオフロードを無効化しており、Blink v1自身もこれらを統合していない。したがって最新vLLM/SGLangの全最適化を有効にした状態に対する同じ倍率を示すものではない。

GPU常駐制御はCUDAデバイス側グラフ起動、TensorRTの事前捕捉グラフ、固定GPUリングバッファなどへ依存する。動的形状や実行経路が事前グラフ化しにくい機能を追加する場合、CPU-free性を保つため別のGPU側制御が必要になる。

また「CPUを不要にする」のではなく、CPU資源をクリティカルパスから外す代わりに、約16k行のGPU側CUDA/C++と約17k行のDPU側C/C++へ制御機能を移す。実装複雑性と専用ハードウェア要求は上がる。論文v1時点では公開後にオープンソース化予定とされ、公式実装URLは確認できない。

## 既存研究との差
vLLM、SGLang、TensorRT-LLMなどは、CPUスケジューリングをGPU計算と重ねたりCUDAグラフで発行数を減らしたりして、CPUオーバーヘッドを隠す方向へ進んできた。Blinkは隠せる時間を増やすのではなく、定常デコードでCPUへ戻ること自体をなくす。

従来のSmartNIC推論研究はネットワークやデータ移動のオフロードが中心だった。Blinkは自己回帰LLM特有のトークン単位制御までGPUへ常駐させ、SmartNICをデータ・要求前段、GPUをスケジューリング・状態管理に分ける点が主要な差である。

## 一般的な実装への示唆
高速GPUほど1反復のモデル計算が短くなり、CPU側の数十µs～数百µsの処理が相対的に大きくなる。CPUコードを高速化するだけでなく、バッチ状態・KV管理・終了判定などをGPU常駐データ構造へ寄せる設計は、SmartNICを使わないサーバーでも検討価値がある。

一方、すべてをGPUへ移せばよいわけではない。ネットワークプロトコルやトークン化までGPU SMへ載せるとモデル計算と競合するため、BlinkはDPUとGPUの得意領域を分ける。CPU除去の本質は「仕事を消す」ことではなく、各制御処理をクリティカルパスへ干渉しにくい実行資源へ再配置することにある。
