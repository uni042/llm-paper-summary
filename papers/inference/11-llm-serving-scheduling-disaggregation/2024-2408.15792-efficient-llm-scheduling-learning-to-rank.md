# Efficient LLM Scheduling by Learning to Rank

## 一文要約

LLMの出力長そのものを正確に予測する代わりに、request同士の**生成長の相対順位**だけを小型予測器で学習し、その順位で短いrequestを優先することで最短ジョブ優先（Shortest Job First; SJF）/ 最短残り時間優先（Shortest Remaining Time First; SRTF）に近いscheduleを実現し、先頭待ち（Head-of-Line; HOL）blockingを減らす。

## 問題設定

OrcaやvLLMに代表される高性能LLM serving systemでは、requestの出力token数が事前には分からないため、到着順（First-Come-First-Serve; FCFS）を使うことが多い。しかし高負荷時に長いgenerationが先頭へ来ると、その後ろの短いrequestが待たされ、HOL blockingによって平均latencyが大きくなる。

古典的にはSJF / SRTFが平均latencyを下げられるが、これには各jobの長さ、LLMの場合は最終的な生成token数を事前に知る必要がある。従来のgeneration-length predictionは正確なtoken数またはlength bucketを当てようとするため、予測誤差がそのままscheduleの悪化につながりやすい。

## 手法

### 1. 正確な出力長ではなく相対順位を予測する

この研究の中心的な観察は、SJF / SRTFに必要なのは「request Aが123 token、Bが411 token」といった絶対値ではなく、**Aの方がBより短いという順序**だという点にある。

そこでpromptからgeneration lengthの順位scoreを出す小型補助modelを学習し、requestを予測された短い順へ並べる。論文ではOPT-125Mなどの小型modelを使い、ranking品質をKendallの順位相関係数（Kendall's Tau）で評価する。実測ではoracleのlength順との順位相関が高いscheduleほどend-to-end latencyも低くなる傾向を確認している。

### 2. iteration単位でrankingをscheduleへ使う

予測scoreをvLLM側のschedulerへ組み込み、実行中・待機中requestをiterationごとに順位付けしてrunning batchを構成する。これにより、全requestを一度実行して長さを観測する多段フィードバックキュー（Multi-Level Feedback Queue; MLFQ）のような方式より早い段階から短いrequestを優先できる。

実装変更は論文記載でvLLMへ約500 LoCであり、別の大規模serving architectureを作るのではなく既存runtimeへpredictive schedulingを差し込む設計になっている。

### 3. 長いrequestのstarvationを抑える

SJF系の弱点である長いrequestの飢餓（starvation）を避けるため、長時間待機したrequestのpriorityを引き上げる仕組みを併用する。したがって単純に「予測上短いrequestだけを永久に先行させる」scheduleではない。

## 評価条件

論文では主に以下の用途で評価する。

- **online chatbot serving:** ShareGPT、LMSYS-Chat-1Mなどのreal-world conversation workload
- **target LLM:** Llama-3 8B / 70Bなど
- **比較:** FCFS、MLFQ、出力長を直接分類・予測する方式など
- **offline workload:** synthetic data generation
- **主要metric:** mean / p90 latency、throughput、予測順位とoracle順位のKendall's Tau

## 主要結果

- chatbot servingでは代表結果として**p90 latencyを2.8×低減**。
- synthetic data generationでは**throughputを6.5×向上**。
- 高arrival-rate条件ではFCFSに対するmean latency改善が最大6.9×に達する評価も示される。
- exact length predictionよりも、scheduleに直接必要なrelative orderingを目的関数にした方がSJF / SRTFへ近い順序を安定して得られる。

重要なのは「length predictorの誤差を小さくする」こと自体ではなく、**最終目的であるrequest orderingへ学習目標を合わせた**点にある。

## 既存研究との差

- **Orca / vLLM:** iteration-level batchingやKV memory管理を改善するが、基本的なrequest orderはFCFSであり、出力長の差をscheduleへ積極利用しない。
- **FastServe:** 生成済みtoken数など実行中に得られる情報からpriorityを更新する。対して本研究は、実行前のpromptからrelative generation lengthを予測して早期に順序を付ける。
- **generation-length regression / classification:** 正確な長さやbucketを予測することを目的とする。本研究は絶対誤差ではなくrequest間の順位を直接学習する。
- **VTCなどfair scheduling:** client間のservice公平性を第一目的とするのに対し、本研究はjob sizeを予測して平均latency / throughputを改善する。starvation対策は持つが、client-level fairness guaranteeを主目的にはしない。

## 一般的な実装上の含意

LLM servingでは、schedulerが必要とする情報を必ずしも高精度な絶対値として予測する必要はない。たとえばgeneration length、prefill cost、KV増加量、expert I/Oなどについても、最終decisionがorderingやbucket selectionなら、**decisionに必要なrelative scoreを直接学習する方が簡単かつrobustな場合がある**。

また補助modelを使うpredictive schedulingでは、予測器の精度だけでなく、その推論costがsaved queueing timeを上回らないことが重要になる。本研究は小型modelと既存vLLMへの限定的な変更でこのtrade-offを成立させている。

## 限界

- predictorはpromptとworkload distributionからgeneration lengthの相対関係を学ぶため、domainやtarget modelが大きく変わった場合にはranking品質が低下し得る。
- 平均latencyやbatch throughputの改善が中心で、厳密なclient-level fairnessやheterogeneous SLOの保証を直接解くものではない。
- 小型predictorの追加推論costと運用・再学習costが発生する。
- generation length以外のresource差、たとえばheterogeneous model、prefix locality、P/D分離clusterのnetwork costなどは主要decision variableではない。

## 引用関係・研究系統上の位置づけ

Orca / vLLMが作ったiteration-level serving基盤に対して、FastServeなどがpriority schedulingを導入した流れの後続に位置する。本研究はそこへ**実行前のlearned job-size ordering**を加える。

同じserving系統では、QLMや後続のSLO-aware schedulerがdeadline / SLO slackを、Prebleがprefix localityを、VTC系がfairnessをschedule decisionへ取り込む。本研究は「予測したgeneration length順位」という別のsignalをschedulerへ与えるため、これらと直交的に組み合わせられる可能性がある。
