# Efficient LLM スケジューリング by Learning to Rank

## 一文要約

最終的な出力トークン数を正確に当てる代わりに、プロンプトから**どのリクエストが他より短く終わりそうかという順位だけ**を小型モデルで予測し、短そうなリクエストを先に処理して長いリクエストによるキュー待ちを減らすスケジューラ。

## 問題設定

OrcaやvLLMに代表される高性能LLM サービング システムでは、リクエストの出力トークン数が事前には分からないため、到着順で処理することが多い。しかし高負荷時に長い生成が先頭へ来ると、その後ろの短いリクエストが待たされ、平均遅延が大きくなる。

この「先頭の長い仕事が後続を塞ぐ」現象を **ヘッド-of-Line（HOL）ブロッキング** と呼ぶ。

古典的なスケジューラでは、短いジョブを先に処理するSJF（Shortest ジョブ 先）や、残り処理時間が短いジョブを先にするSRTF（Shortest Remaining 時間 先）が平均遅延を下げやすい。しかしLLMでは最終出力長を事前に知らない。

従来の生成-長さ 予測は「このリクエストは412 トークン」のような絶対値や長さ bucketを当てようとするため、多少の予測誤差がschedule順へ大きく影響する場合がある。

## 手法

### 1. 正確なトークン数ではなく「どちらが短いか」を予測する

この研究の中心的な観察は、短いリクエストを先にするスケジューラに必要なのは、必ずしも正確な出力長ではなく、**リクエスト AとBのどちらが短そうかという順序**だという点にある。

そこでプロンプトを小型モデルへ入力し、リクエストごとに「短そう / 長そう」を表す順位付け 点数を出す。この点数でリクエストを並べる。

例えば実際の長さが

- A: 123 トークン
- B: 411 トークン
- C: 250 トークン

だとしても、予測器が正確な数字を当てる必要はなく、`A < C < B` という順番を当てればスケジューラには十分役立つ。

### 2. 予測した順位を反復ごとのバッチ選択に使う

予測点数をvLLM スケジューラへ組み込み、実行中・待機中リクエストを反復ごとに順位付けしてrunning バッチを構成する。

これにより、リクエストを一度走らせてから実行時間に応じて優先度を変える方式より、**最初のトークン生成前から短そうなリクエストを優先できる**。

論文ではOPT-125Mなどの小型モデルを予測器として使い、予測順位が実際の出力長順位とどれだけ一致したかも評価する。

順位一致度にはKendall's Tauという統計指標を使うが、ここで重要なのは、**順位が実際の短い順に近いほどエンドツーエンド 遅延も低くなる**ことを確認した点である。

### 3. 長いリクエストを永久に後回しにしない

短いリクエスト優先だけを続けると、長いリクエストが新着の短リクエストに追い越され続ける可能性がある。

そこで長時間待ったリクエストは優先度を徐々に上げ、最終的には処理されるようにする。

論文でいう飢餓対策は、この**長いリクエストを永久待ちにしない優先度補正**を指す。

この補正は、理想的なShortest ジョブ 先を厳密に守ることより、長いリクエストにも時間経過とともに処理機会を与えることを優先する。新しい短リクエストが継続的に到着する高負荷状態では、順位付け 点数だけなら長リクエストが何度でも追い越され得るが、待機時間を優先度へ足すことで一定時間後には順位が上がる。その代わり平均遅延だけを最小化する理想順からは少し外れるため、性能と飢餓回避のtrade-offになる。

## 評価条件

論文では主に以下の用途で評価する。

- **オンライン chatbot サービング:** ShareGPT、LMSYS-Chat-1Mなどの実時間-world 会話 ワークロード
- **対象 LLM:** Llama-3 8B / 70Bなど
- **比較:** 到着順、実行後の情報でpriorityを変える方式、出力長を直接分類・予測する方式など
- **オフライン ワークロード:** 合成 データ 生成
- **主要指標:** mean / p90 遅延、スループット、予測順位の一致度

## 主要結果

- chatbot サービングでは代表結果として**p90 遅延を2.8×低減**。
- 合成 データ 生成では**スループットを6.5×向上**。
- 高到着-rate条件では到着順に対するmean 遅延改善が最大6.9×に達する評価も示される。
- exact 長さ 予測よりも、予定に直接必要な相対 orderingを目的関数にした方が、短いリクエストを先にする理想順へ近い予定を安定して得られる。

重要なのは「長さ 予測器の絶対誤差を小さくする」こと自体ではなく、**最終的にスケジューラが必要とする順位を直接学習した**点にある。

この利得はキューに複数リクエストが並び、どれを先に実行するか選べるときに最も大きい。到着率が低く、GPUがほぼ空いていてリクエストが来たらすぐ実行できる状態では、順位を予測しても待ち時間を短縮する余地が小さく、予測器の追加コストだけが残り得る。逆に高負荷で短いリクエストが長い生成の後ろへ多数並ぶほどヘッド-of-Line ブロッキングが大きくなり、正確なトークン数でなくても短い順を当てる価値が高くなる。

## 既存研究との差

- **Orca / vLLM:** 反復-レベル batchingやKV メモリ管理を改善するが、基本的なリクエスト orderは到着順で、出力長の差を積極利用しない。
- **FastServe:** 実行中に得られた情報から優先度を更新する。対して本研究は、実行前のプロンプトから相対 生成 長さを予測して早期に順序を付ける。
- **生成-長さ 回帰 / classification:** 正確な長さやbucketを予測することを目的とする。本研究は絶対値ではなくリクエスト間の順位を直接学習する。
- **VTCなどfair スケジューリング:** 利用者間の資源 share公平性が主目的。本研究はジョブ サイズを予測して平均遅延 / スループットを改善する。長リクエストの永久待ちは防ぐが、利用者-レベル 公平性 guaranteeは主目的ではない。

## 一般的な実装上の含意

LLM サービングでは、スケジューラが必要とする情報を必ずしも高精度な絶対値として予測する必要はない。

たとえば生成 長さ、プリフィル コスト、KV増加量、エキスパート I/Oなどについても、最終判断が「どちらを先に処理するか」なら、**絶対量ではなく相対 点数を直接学習する方が簡単で予測誤差にも強い場合がある**。

また補助モデルを使うpredictive スケジューリングでは、予測器自身の推論コストが、キュー待ち削減で得る利益を上回らないことが重要になる。本研究は小型モデルと既存vLLMへの限定的な変更でこのtrade-offを成立させている。

## 限界

- 予測器はプロンプトとワークロード 分布から生成 長さの相対関係を学ぶため、domainや対象 モデルが大きく変わると順位付け品質が低下し得る。
- 平均遅延やバッチ スループットの改善が中心で、厳密な利用者-レベル 公平性や異種 SLOの保証を直接解くものではない。
- 小型予測器の追加推論コストと運用・再学習コストが発生する。
- 生成 長さ以外の資源差、たとえば異種 モデル、プレフィックス 局所性、P/D分離クラスタのネットワーク コストなどは主要判断 variableではない。

## 引用関係・研究系統上の位置づけ

Orca / vLLMが作った反復-レベル サービング基盤に対して、FastServeなどが優先度 スケジューリングを導入した流れの後続に位置する。本研究はそこへ**実行前のlearned ジョブ-サイズ ordering**を加える。

同じサービング系統では、QLMや後続のSLO-考慮 スケジューラが締切 / SLO slackを、Prebleがプレフィックス 局所性を、VTC系が公平性を予定 判断へ取り込む。本研究は「予測した生成 長さ順位」という別のsignalをスケジューラへ与えるため、これらと組み合わせられる可能性がある。

## 補足

この研究は、要求の到着順を単純に並べ替えるのではなく、各要求が今後どれだけ計算枠を占有するかを学習し、その見積もりを順位へ反映する。短い要求を先に処理し過ぎて長い要求を永久に待たせないよう、公平性と待ち時間も同時に扱う点が重要である。実運用では、学習に使った負荷と異なる到着分布へ適用する際に、順位の偏りや飢餓が生じていないかを継続的に監視する必要がある。
