# Efficient LLM Scheduling by Learning to Rank

## 一文要約

最終的な出力token数を正確に当てる代わりに、promptから**どのrequestが他より短く終わりそうかという順位だけ**を小型modelで予測し、短そうなrequestを先に処理して長いrequestによるqueue待ちを減らすscheduler。

- **公開:** 2024-08-28

## 問題設定

OrcaやvLLMに代表される高性能LLM serving systemでは、requestの出力token数が事前には分からないため、到着順で処理することが多い。しかし高負荷時に長いgenerationが先頭へ来ると、その後ろの短いrequestが待たされ、平均latencyが大きくなる。

この「先頭の長い仕事が後続を塞ぐ」現象を **Head-of-Line（HOL）blocking** と呼ぶ。

古典的なschedulerでは、短いjobを先に処理するSJF（Shortest Job First）や、残り処理時間が短いjobを先にするSRTF（Shortest Remaining Time First）が平均latencyを下げやすい。しかしLLMでは最終output長を事前に知らない。

従来のgeneration-length predictionは「このrequestは412 token」のような絶対値やlength bucketを当てようとするため、多少の予測誤差がschedule順へ大きく影響する場合がある。

## 手法

### 1. 正確なtoken数ではなく「どちらが短いか」を予測する

この研究の中心的な観察は、短いrequestを先にするschedulerに必要なのは、必ずしも正確な出力長ではなく、**request AとBのどちらが短そうかという順序**だという点にある。

そこでpromptを小型modelへ入力し、requestごとに「短そう / 長そう」を表すranking scoreを出す。このscoreでrequestを並べる。

例えば実際の長さが

- A: 123 token
- B: 411 token
- C: 250 token

だとしても、予測器が正確な数字を当てる必要はなく、`A < C < B` という順番を当てればschedulerには十分役立つ。

### 2. 予測した順位をiterationごとのbatch選択に使う

予測scoreをvLLM schedulerへ組み込み、実行中・待機中requestをiterationごとに順位付けしてrunning batchを構成する。

これにより、requestを一度走らせてから実行時間に応じてpriorityを変える方式より、**最初のtoken生成前から短そうなrequestを優先できる**。

論文ではOPT-125Mなどの小型modelをpredictorとして使い、予測順位が実際のoutput長順位とどれだけ一致したかも評価する。

順位一致度にはKendall's Tauという統計指標を使うが、ここで重要なのは、**順位が実際の短い順に近いほどend-to-end latencyも低くなる**ことを確認した点である。

### 3. 長いrequestを永久に後回しにしない

短いrequest優先だけを続けると、長いrequestが新着の短requestに追い越され続ける可能性がある。

そこで長時間待ったrequestはpriorityを徐々に上げ、最終的には処理されるようにする。

論文でいうstarvation対策は、この**長いrequestを永久待ちにしないpriority補正**を指す。

## 評価条件

論文では主に以下の用途で評価する。

- **online chatbot serving:** ShareGPT、LMSYS-Chat-1Mなどのreal-world conversation workload
- **target LLM:** Llama-3 8B / 70Bなど
- **比較:** 到着順、実行後の情報でpriorityを変える方式、出力長を直接分類・予測する方式など
- **offline workload:** synthetic data generation
- **主要metric:** mean / p90 latency、throughput、予測順位の一致度

## 主要結果

- chatbot servingでは代表結果として**p90 latencyを2.8×低減**。
- synthetic data generationでは**throughputを6.5×向上**。
- 高arrival-rate条件では到着順に対するmean latency改善が最大6.9×に達する評価も示される。
- exact length predictionよりも、scheduleに直接必要なrelative orderingを目的関数にした方が、短いrequestを先にする理想順へ近いscheduleを安定して得られる。

重要なのは「length predictorの絶対誤差を小さくする」こと自体ではなく、**最終的にschedulerが必要とする順位を直接学習した**点にある。

## 既存研究との差

- **Orca / vLLM:** iteration-level batchingやKV memory管理を改善するが、基本的なrequest orderは到着順で、output長の差を積極利用しない。
- **FastServe:** 実行中に得られた情報からpriorityを更新する。対して本研究は、実行前のpromptからrelative generation lengthを予測して早期に順序を付ける。
- **generation-length regression / classification:** 正確な長さやbucketを予測することを目的とする。本研究は絶対値ではなくrequest間の順位を直接学習する。
- **VTCなどfair scheduling:** client間のresource share公平性が主目的。本研究はjob sizeを予測して平均latency / throughputを改善する。長requestの永久待ちは防ぐが、client-level fairness guaranteeは主目的ではない。

## 一般的な実装上の含意

LLM servingでは、schedulerが必要とする情報を必ずしも高精度な絶対値として予測する必要はない。

たとえばgeneration length、prefill cost、KV増加量、expert I/Oなどについても、最終decisionが「どちらを先に処理するか」なら、**絶対量ではなくrelative scoreを直接学習する方が簡単で予測誤差にも強い場合がある**。

また補助modelを使うpredictive schedulingでは、予測器自身の推論costが、queue待ち削減で得る利益を上回らないことが重要になる。本研究は小型modelと既存vLLMへの限定的な変更でこのtrade-offを成立させている。

## 限界

- predictorはpromptとworkload distributionからgeneration lengthの相対関係を学ぶため、domainやtarget modelが大きく変わるとranking品質が低下し得る。
- 平均latencyやbatch throughputの改善が中心で、厳密なclient-level fairnessやheterogeneous SLOの保証を直接解くものではない。
- 小型predictorの追加推論costと運用・再学習costが発生する。
- generation length以外のresource差、たとえばheterogeneous model、prefix locality、P/D分離clusterのnetwork costなどは主要decision variableではない。

## 引用関係・研究系統上の位置づけ

Orca / vLLMが作ったiteration-level serving基盤に対して、FastServeなどがpriority schedulingを導入した流れの後続に位置する。本研究はそこへ**実行前のlearned job-size ordering**を加える。

同じserving系統では、QLMや後続のSLO-aware schedulerがdeadline / SLO slackを、Prebleがprefix localityを、VTC系がfairnessをschedule decisionへ取り込む。本研究は「予測したgeneration length順位」という別のsignalをschedulerへ与えるため、これらと組み合わせられる可能性がある。
