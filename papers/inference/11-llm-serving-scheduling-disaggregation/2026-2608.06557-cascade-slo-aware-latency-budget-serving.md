# Cascade: Exploiting SLO-Aware latency budget for fair and high goodput LLM inference serving

## 書誌情報

- **Authors:** Muhammad Adnan, Rohan Mahapatra, Prashant J. Nair, Daniel Berger, Pantea Zardoshti, Rodrigo Fonseca, Esha Choukse
- **Affiliations:** The University of British Columbia, Microsoft Azure Research, NVIDIA
- **公開日:** 2026-08-06
- **arXiv:** 2608.06557v1
- **分野:** cs.DC, cs.LG
- **一次資料:** https://arxiv.org/abs/2608.06557

## 一文要約

requestごとに「SLOまであと何秒の遅延を許容できるか」を残りlatency budgetとして継続推定し、その同じbudgetでrequestの実行順とHBM / CPU DRAM / NVMe間のKV cache復元・先読み・保持・再計算をまとめて決めることで、SLOを満たす処理量と長context requestへの公平性を両立するserving system。

## 問題設定

同じservice-level objective（SLO）を持つrequestでも、prompt長、生成長、残り計算量、再利用可能なprefix KV cacheの所在は大きく異なる。FCFSは長いrequestによるhead-of-line blockingを起こしやすく、shortest-job-firstは長context requestを後回しにしやすい。一方、KV cache管理をschedulerと独立に行うと、NVMeなど深いmemory tierにcache hitがあっても、その転送時間だけでTTFT SLOを超える場合がある。

Cascadeは、queueing、GPU上の計算、preemption、KV cache転送がすべて同じ「requestが追加で耐えられる遅延」を消費すると捉え、これを **per-request latency budget** として明示的に管理する。

## 手法

### 1. requestごとの残りlatency budgetを推定する

各requestについて、入力長、予測した出力長、利用可能なprefix KV state、現在のsystem loadから残りservice timeを推定する。SLOからこの残りservice timeを引いた値を、queueingやdata movementへ追加で使えるlatency budgetとする。requestが待機・実行し、cache状態やsystem loadが変わるたびにbudgetを更新する。

budgetはdeadlineそのものではなく、残り仕事を終えるための推定時間を差し引いた余白である。そのため同じSLO期限を持つ2 requestでも、短い残作業しかないものは余裕が大きく、長い生成や深いtierからのKV復元を抱えるものは余裕が小さくなる。実行が進んだりcache hit状況が変われば残りservice timeも変わるので、固定priorityではなく継続更新する必要がある。

### 2. budgetが少ないrequestを先に実行する

schedulerはarrival orderやrequest sizeだけではなく、残りbudgetが少ないrequestを優先する。短いrequestを無条件に優遇するのではなく、「今これ以上待たせるとSLOを破りやすいrequest」を先へ進めるため、長context requestを系統的にstarvationさせにくい。

このpriorityは短いrequestを常に先にする最短仕事優先とは異なる。長contextでも早く到着してbudgetを消費し続ければ緊急度が上がり、後から来た短requestより先に選ばれる場合がある。つまり公平性はrequest長を同一視することでなく、『これ以上待たせられる余裕』を共通尺度へ変換することで実現する。

### 3. KV cacheの復元・先読み・再計算も同じbudgetで決める

再利用可能なprefix KVがHBMにない場合、CPU DRAMやNVMeなど深いtierから戻す時間と、GPUでprefixを再計算する時間を比較する。cacheを戻す方が計算を節約できても、転送が残りbudgetを使い切るならcache hitを捨てて再計算する。逆にbudgetに余裕があれば復元・prefetchを許可する。

この判断をrequest schedulingと同じbudgetへ結びつけることで、schedulerが残した余裕をKV managerが使い切る、またはKV transferのためにSLO直前のrequestを待たせる、といったsubsystem間の不整合を避ける。

### 4. preemption時にもbudgetを使う

実行中requestを退避する必要がある場合、残りbudgetが大きいrequestをvictimとして選ぶ。KV stateをDRAMへspillする時間がbudget内なら退避し、そうでなければ再計算を選び、queueへ戻した後にbudgetを再計算する。

preemption victimを選ぶ際にも同じ尺度を使うことで、schedulerとmemory managerが逆向きの判断をするのを防ぐ。例えば実行priorityが高いrequestをKV容量だけの都合で退避すると、直後にSLO違反へ近づき再度swap-inする無駄が起きる。余裕の大きいrequestから退避すれば、spillや再計算の時間を吸収できる可能性が高く、preemption自体がcritical pathへ入りにくい。

## 評価条件

- **Models:** Qwen-2.5-72B、Llama-3-70B、Llama-3-405B
- **Tensor parallelism:** 4
- **Weight precision:** NVFP4
- **KV cache precision:** FP8
- **Hardware profiling:** NVIDIA GB200 NVL72。NVLink-C2C / Multi-Node NVLink上のdata movementを実機profiling
- **Cluster-scale evaluation:** 実機profiling値を投入して拡張したVidur simulator
- **KV movement model:** LMCacheを組み込んだmulti-tier HBM / CPU DRAM / NVMe hierarchy
- **Workloads:** ChatBot、Tool&Agent、Coder、Reasoningと、それらを混合・負荷変更したproduction traces
- **Serving:** prefill / decode co-location、chunked prefill。Mixed traceの標準構成ではQwen-2.5-72B 9 instances、Llama-3-70B 6 instances、Llama-3-405B 12 instances

重要な区別として、GB200上でtransfer等をprofilingしているが、論文の大規模production-trace比較そのものは拡張Vidurによるsimulationであり、全clusterを実機でend-to-end測定した結果ではない。

## 主要結果

- production trace群の比較で、FCFSに対して **SLOを満たしたgoodputを平均2.4×** にし、**SLO violationを40%削減**したと報告している。
- Mixed workloadのQwen-2.5-72Bでは、Cascadeは7 instances（28 GPUs）でFCFSの9 instances（36 GPUs）を上回るgoodputを達成し、論文では同じloadを **22%少ないGPU** で処理できる例を示している。
- Jain's Fairness Indexをprompt長のpercentile bin間で測り、短いrequestだけを成功させてaggregate SLO attainmentを高く見せる挙動を避けることも評価対象にしている。

## 既存研究との差

- **FCFS / vLLM:** arrival orderを守る代わりに、長いrequestが後続requestのlatency budgetをqueue内で消費する。Cascadeは残りbudgetを直接priorityにする。
- **Shortest-job-first系:** 短いrequestを優先して平均latencyを下げやすいが、長context requestを継続的に後回しにしうる。Cascadeはrequest sizeではなくSLOに対する残り余裕を使う。
- **Earliest-deadline-first系:** deadlineだけでは、同じdeadlineでも残り計算量が異なるrequestの緊急度を区別しにくい。Cascadeはpredicted remaining service timeを差し引く。
- **KV cache offload / prefix-cache system:** cache容量、reuse probability、transfer costだけでKVを戻すと、NVMe hitがSLO violationを起こす場合がある。Cascadeはcache restoreをrequestの残りbudgetと結びつけ、必要ならhitを捨てて再計算する。
- **SuperInfer:** schedulingとmemory managementを協調させる点は近いが、Cascadeはrequest固有の残りlatency budgetを共通の制御量にし、HBM / DRAM / NVMeのprefix KV管理とfairnessまで統合している。

## 限界・注意点

- cluster-scaleの主要結果は、GB200 NVL72の実機profiling値を使ったVidur simulationであり、同規模clusterのend-to-end実機評価ではない。
- evaluationはGB200系の高帯域NVLink-C2C / Multi-Node NVLinkとNVMeを前提にprofilingされているため、PCIe中心の一般的なserverや異なるstorage構成ではtransferとrecomputeの損益分岐が変わる。
- 残りservice timeは出力長予測や現在loadに依存する。推定誤差へのrobustnessは重要で、実deploymentではmodel/workloadごとのcalibrationが必要になる。
- 論文はprefill / decode co-locationを主評価構成としており、P/D disaggregationへ考え方は適用可能としているものの、その構成を中心にした実証ではない。
- 2026-09-07時点でarXiv v1であり、査読付き最終採択版は確認できない。

## 実装上の含意

multi-tier KV cacheでは「cache hit率を最大化する」こと自体を目的にすると、遅いtierからのhitがSLOを壊す可能性がある。実装上は、KV object単位のreuse価値だけでなく、それを待つrequest側のlatency headroomをschedulerとcache managerで共有する設計が重要になる。また、NVMeからKVを読むかGPUでprefixを再計算するかは固定policyではなく、requestのurgency、prefix長、現在のI/O帯域、GPU loadで動的に切り替える余地が大きい。

## 引用関係

論文はvLLM、Sarathi-Serve、FastServe、DistServe、SGLang、LMCache、SuperInferなどを関連研究・baselineとして扱う。特にFastServeなどのrequest scheduling系と、LMCacheなどのmulti-tier KV reuse系を別々に最適化するのではなく、latency budgetという一つのruntime signalで接続する位置づけにある。
