# KVServe: Service-Aware KV Cache Compression for Communication-Efficient Disaggregated LLM Serving

> 分離型LLM servingでKV転送を固定圧縮せず、workload・実効bandwidth・SLO・品質制約に応じて圧縮方式を選び替え、network / storage境界のKV通信待ちを減らす。

## 問題
prefill / decode分離やKV state disaggregationでは、従来GPU内部状態だったKV cacheがnetworkやstorage境界を横切る明示的なpayloadになる。長contextではKV転送がend-to-end latencyの大部分を占める一方、既存のKV圧縮はtransform、量子化、codecなどを固定設定で使うことが多い。圧縮率が高くても圧縮・展開costが大きければ高速networkでは逆に遅くなり、workloadごとの品質耐性も異なる。

## 新規性
KVServeはKV圧縮を単一algorithmではなく、service状態に応じて選択するruntime strategyとして扱う。主な構成は、既存手法をtransform・quantizer・codecへ分解したmodular strategy pool、Bayesian optimizationで高価なoffline探索を削減するprofiling engine、実効bandwidth・SLO・品質制約を見てonlineでprofileを選ぶcontrollerである。

## 手法
### Modular Strategy Pool
KV圧縮をtransform → quantizer → codecのpipelineとして抽象化し、Delta / Hadamard / Affine等のtransform、複数量子化方式、nvCOMP codecを組み替えられるようにする。さらにretrieval headとstreaming headでbit幅を変えるMixed-Precision Head-Wise Quantization（MixHQ）を導入する。

### Bayesian Profiling Engine
組合せが約10^4規模まで増えるstrategy spaceを総当たりせず、Gaussian Processを用いたBayesian optimizationで探索する。圧縮率・品質・圧縮展開throughputの3次元Pareto候補を作り、online選択対象を絞る。論文では約1000時間相当の総当たり探索を20時間規模へ削減したと報告する。

### Service-Aware Online Controller
request単位でworkload class、実効bandwidth、latency SLO、最低品質をservice contextとして受け取る。圧縮後の通信時間とencode/decode時間を解析modelで見積もり、制約を満たすprofileからJCTを最小化する候補を選ぶ。軽量banditでoffline profileと実運用のずれを補正する。

## 評価条件
論文はKVServeをvLLMへ統合し、prefill / decode分離とKV state disaggregationの双方を評価する。複数dataset、model、GPU、network bandwidth条件を使い、固定圧縮方式や非圧縮baselineと比較する。本文ではLlama-3.1系を含むmodelとH100を用いた分離serving評価を示し、10〜50 Gbps等のnetwork条件でKV通信がJCTの16〜60%を占め得ることを確認している。

## 主要結果
- PD-separated servingでbaseline比、JCTを最大9.13倍高速化。
- KV-disaggregated servingでTTFTを最大32.8倍短縮。
- offline strategy探索を約50倍削減し、1000時間規模から20時間規模へ圧縮。
- 固定圧縮はbandwidth上昇時に圧縮・展開costが通信削減量を上回り、非圧縮より遅くなる場合がある。KVServeはservice状態を見てprofileを切り替えることでこのnegative optimizationを避ける。

これらは最大値であり、全workload・network条件で同じ倍率になるわけではない。

## 限界
- workload classが上位router等から得られることを前提にし、その分類器自体は研究対象外。
- offline profilingが必要で、model・hardware・圧縮componentが変われば候補集合を更新する必要がある。
- 品質制約はdataset / taskごとの評価metricに依存し、未知workloadへの一般化はonline補正だけでは保証されない。
- 効果はnetwork / storage bandwidthがKV movementのbottleneckになる分離構成で特に大きく、monolithic servingでは同じ利得を期待できない。
- vLLM統合実装で評価されているが、今回確認したarXiv本文から独立した公開code URLは確認できなかった。

## 既存研究との差
CacheGen、KIVI、KVQuant等が個別のKV圧縮algorithmを設計するのに対し、KVServeは複数方式をcomponentへ分解して組み合わせ、service状態に応じて選択する制御層を主な貢献とする。DistServeやMooncake等の分離型servingがKVをnode / storage間で動かすarchitectureを作るのに対し、KVServeはその移動payloadを動的に圧縮して通信critical pathを短くする。

## 一般的な実装への示唆
KV通信最適化では圧縮率だけを最大化すべきではない。`圧縮・展開時間 + 圧縮後byte数 / 実効bandwidth` を直接比較し、SLOと品質を満たす範囲で圧縮を無効化する選択肢も含めてruntimeで切り替える方が合理的である。network混雑やstorage throughputが変動するproduction servingでは、KV compressionもschedulerが扱うresource-control decisionになり得る。
