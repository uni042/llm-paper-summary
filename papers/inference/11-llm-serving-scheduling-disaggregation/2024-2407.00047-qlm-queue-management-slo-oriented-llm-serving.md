# Queue Management for SLO-Oriented Large Language Model Serving

> interactive / batch requestや複数modelを同じclusterで扱うとき、各request groupがあと何秒待てるかとmodelがどのGPUに載っているかを見て、queue順序と実行先を組み替え、latency目標を守れるrequest数を増やすsystem。

## 概要

LLM servingではinteractive requestだけでなく、締切が緩いbatch requestや複数modelのrequestが同じclusterへ到着する。単純なFIFOやmodelごとの固定queueでは、長いrequestやmodel swapが先頭に来たとき後続のlatency-sensitive requestまで待たされる。

QLMはこの問題を、GPU kernelやbatchingを直接作り替えるのではなく、**requestが実行instanceへ渡される前のqueue順序と配置を最適化する問題**として扱う。

各requestには「このlatency以内に処理したい」というSLOがある。QLMは現在までに何秒待ったか、これから実行に何秒かかりそうかを見積もり、**SLOまで余裕が少ないrequestを早めつつ、model reloadやGPU混雑も増やしすぎない順序**を作る。

## 手法

### 1. 似たrequestをgroupへまとめてschedulerの組合せ数を減らす

各requestを1件ずつ最適化すると、multi-model・大量request環境では組合せが急増する。

そこで同じmodelや近いSLOを持つrequestをRequest Groupへまとめ、schedulerはgroup単位で順序と配置を決める。group内では基本的に到着順を保つ。

### 2. 各serving instanceごとに「次に何groupを流すか」という仮想queueを持つ

QLMは各LLM serving instanceに対応するVirtual Queueを置き、そのqueue上のRequest Group順を**将来の実行予定順**として扱う。

requestが実際にGPUへ渡される前にこの順番を組み替えられるため、

- 急ぎgroupを前へ出す
- 締切に余裕があるbatch groupを後ろへ回す
- すでに目的modelが載っているinstanceへ寄せる

といった調整ができる。

### 3. 「このgroupは実行開始まであと何秒待つか」を予測する

LLMはoutput lengthが事前に確定せず、execution timeに大きなばらつきがある。そのため固定平均時間だけでqueueを並べるとSLO違反を見誤る。

QLMは各groupをqueue内のある位置へ置いた場合に、**前に並ぶgroupの処理時間を考えると何秒後に開始できそうか**を推定する。

予測には不確実性も含め、単一の決め打ち時間ではなく「この順ならSLOを守れる可能性がどの程度あるか」をschedulerへ渡す。

### 4. Queue順序を決めることで、model swapやstate移動も間接的に決める

schedulerが決めたqueue順序に応じて、下位のserving systemでは必要に応じて

- requestを別instanceへ送る
- GPU / CPU間でstateを移す
- 目的modelをGPUへloadする
- 別modelをGPUから外す

といったoperationを行う。

QLMの考え方は、これらを個別heuristicで別々に判断するのではなく、**「この順でこのinstanceへrequestを流したい」という最終queue計画を先に作り、必要operationをそこから導く**ことである。

## 評価

SoCC 2024最終版では、異種GPU・複数model・production要件を反映したreal-world serving workloadを用いて評価している。

主要結果として、既存serving方式に対して

- SLO attainment: **40〜90%改善**
- throughput: **20〜400%改善**
- device utilization: 同等以上

を報告する。

ここでSLO attainmentは、設定したlatency目標を守れたrequestの割合を指す。

特にinteractive requestだけでなく、SLOが緩いbatch requestを同じclusterへ混在させたとき、batchを単純に最後へ回すのではなく、**今どれだけ余裕があるかとmodel配置を見ながら空き時間へ差し込める**点が効く。

## 既存研究との差

### FastServe / VTCとの違い

FastServeはrunning requestをiteration boundaryで一時停止し、request priorityを制御する。VTCはclient間の公平性をtoken service量として管理する。

QLMは**request実行前のwaiting queueとmulti-model placement**を主対象にし、model swapやinstance assignmentまで含めてend-to-end SLO達成率を最適化する。

### Llumnixとの違い

Llumnixは一度実行を始めたrequestをinstance間でlive migrationし、runtimeで判明したload imbalanceを修正する。

QLMは主に実行前のqueue段階で、将来の待ち時間を見積もりrequestをどの順・どのinstanceへ入れるかを先に決める。

両者は競合というより、**QLMで事前queue / dispatchを決め、Llumnix型機構で実行開始後のplacementを修正する**ように組み合わせられる。

## 限界

- waiting-time estimatorの精度はmodel・hardware・workload profileに依存する。
- requestをgroup化するため、個々のrequest差を完全には表現しない。
- optimization-based schedulingは単純なFIFOよりcontroller overheadが大きい。
- model swapやstate swap自体のcostは下位serving systemとstorage / interconnect性能に依存する。
- SLO達成率を主目的にするため、client-level fairnessとは別の最適化軸である。

## 一般的な実装上の含意

LLM servingのSLO違反はGPU kernelだけでなく、**queueで何秒待ったか**によって大きく決まる。

特にmulti-model環境では、model localityだけを優先すると急ぎrequestが詰まり、逆にSLOだけを見るとmodel reloadが増える。

そのため、queue waiting time・残りSLO余裕・modelがすでにGPUへ載っているか・instance loadを一つのschedulerで扱い、requestをGPUへ渡す前から最適化する価値がある。
