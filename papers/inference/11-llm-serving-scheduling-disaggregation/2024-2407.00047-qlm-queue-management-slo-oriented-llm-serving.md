# Queue Management for SLO-Oriented Large Language Model Serving

> batch / interactive request、複数model、異なるlatency SLOを同じqueueで扱い、待ち時間予測を使ってrequest groupの順序とmodel instanceへの割当を組み替え、SLO達成率とGPU利用率を両立するqueue management system。

## 概要

LLM servingではinteractive requestだけでなく、締切が緩いbatch requestや複数modelのrequestが同じclusterへ到着する。単純なFIFOやmodelごとの固定queueでは、長いrequestやmodel swapが先頭に来たとき後続のlatency-sensitive requestまで待たされ、head-of-line blockingが起きる。

QLMはこの問題を、GPU kernelやbatchingを直接作り替えるのではなく、**requestが実行instanceへ渡される前のqueue順序を最適化する問題**として扱う。requestをmodel・SLOなどが似たgroupへまとめ、各groupの待ち時間を予測して、どのinstanceへどの順で流すかをglobalに決める。

## 手法

### 1. Request Group

各requestを個別に最適化すると組合せが急増するため、同じmodelや近いSLOを持つrequestをRequest Groupへまとめる。schedulerはgroup単位で順序と配置を決めるため、多model・大量requestでもoptimization overheadを抑えられる。

### 2. Virtual Queue

各LLM serving instanceに対応するVirtual Queueを置き、Request Groupの並び順を実行順序として扱う。request自体はgroup内で基本的に到着順だが、group間はSLO達成率を高めるために並べ替える。

### 3. Request Waiting Time estimator

QLMは各groupをqueue先頭へ動かした場合の待ち時間を推定する。LLMはoutput lengthが事前に確定せず、execution timeに大きなばらつきがあるため、固定の平均値だけではなく不確実性を含むwaiting-time estimateをschedulerへ渡す。

### 4. Queue orderingからserving operationを誘導

schedulerが決めたqueue順序に応じて、下位のserving systemで

- request pulling / eviction
- GPU-CPU state swapping
- load balancing
- model swapping / warm start

などを行う。つまりQLMは個々の低レベルoperationを別々にheuristic制御するのではなく、**最終的なqueue順序を決めることで必要なoperationをまとめて誘導する**。

## 評価

SoCC 2024最終版では、異種GPU・複数model・production要件を反映したreal-world serving workloadを用いて評価している。

主要結果として、既存serving方式に対して

- SLO attainment: **40〜90%改善**
- throughput: **20〜400%改善**
- device utilization: 同等以上

を報告する。

特にinteractive requestだけでなく、SLOが緩いbatch requestを同じclusterへ混在させたとき、batchを単純に後回しにするのではなく、SLO slackとmodel localityを見ながらqueueへ組み込める点が効く。

## 既存研究との差

### FastServe / VTCとの違い

FastServeはrunning requestをiteration boundaryでpreemptし、request priorityを制御する。VTCはclient間の公平性をtoken service量として管理する。

QLMは**request実行前のwaiting queueとmulti-model placement**を主対象にし、model swapやinstance assignmentまで含めてend-to-end SLO達成率を最適化する。

### Llumnixとの違い

Llumnixは一度実行を始めたrequestをinstance間でlive migrationし、runtimeで判明したload imbalanceを修正する。QLMは主にqueueing段階で将来の待ち時間を見積もり、requestをどの順・どのinstanceへ入れるかを先に決める。

両者は競合というより、**QLMでqueue / dispatchを決め、Llumnix型機構でexecution後のplacementを修正する**ような上下関係で組み合わせられる。

## 限界

- waiting-time estimatorの精度はmodel・hardware・workload profileに依存する。
- requestをgroup化するため、個々のrequest差を完全には表現しない。
- stochastic / optimization-based schedulingは単純なFIFOよりcontrol-plane overheadが大きい。
- model swapやstate swap自体のcostは下位serving systemとstorage / interconnect性能に依存する。
- SLO達成率を主目的にするため、client-level fairnessとは別の最適化軸である。

## 一般的な実装上の含意

LLM servingのSLO違反はGPU kernelだけでなく、**queueで何秒待ったか**によって大きく決まる。特にmulti-model環境では、model localityを優先しすぎるとlatency-sensitive requestが詰まり、逆にSLOだけを見るとmodel swapが増える。

そのため、queue waiting time・SLO slack・model locality・instance loadを一つのschedulerで扱い、requestをGPUへ渡す前の段階から最適化する価値がある。
