# QLM: Queue Management for SLO-Oriented Large Language Model Serving

> 対話的 / バッチ要求や複数モデルを同じクラスタで扱うとき、各要求グループがあと何秒待てるかとモデルがどのGPUに載っているかを見て、待ち行列順序と実行先を組み替え、遅延目標を守れる要求数を増やすシステム。

## 概要

LLM推論提供では対話的要求だけでなく、締切が緩いバッチ要求や複数モデルの要求が同じクラスタへ到着する。単純なFIFOやモデルごとの固定待ち行列では、長い要求やモデル交換が先頭に来たとき後続の遅延重視の要求まで待たされる。

QLMはこの問題を、GPUカーネルやバッチ処理を直接作り替えるのではなく、**要求が実行単位へ渡される前の待ち行列順序と配置を最適化する問題**として扱う。

各要求には「この遅延以内に処理したい」というSLOがある。QLMは現在までに何秒待ったか、これから実行に何秒かかりそうかを見積もり、**SLOまで余裕が少ない要求を早めつつ、モデル再読み込みやGPU混雑も増やしすぎない順序**を作る。

## 手法

### 1. 似た要求をグループへまとめてスケジューラの組合せ数を減らす

各要求を1件ずつ最適化すると、複数モデル・大量要求環境では組合せが急増する。

そこで同じモデルや近いSLOを持つ要求を要求グループへまとめ、スケジューラはグループ単位で順序と配置を決める。グループ内では基本的に到着順を保つ。

### 2. 各推論提供実行単位ごとに「次に何グループを流すか」という仮想待ち行列を持つ

QLMは各LLM推論提供実行単位に対応する仮想待ち行列を置き、その待ち行列上の要求グループ順を**将来の実行予定順**として扱う。

要求が実際にGPUへ渡される前にこの順番を組み替えられるため、

- 急ぎグループを前へ出す
- 締切に余裕があるバッチグループを後ろへ回す
- すでに目的モデルが載っている実行単位へ寄せる

といった調整ができる。

### 3. 「このグループは実行開始まであと何秒待つか」を予測する

LLMは出力長さが事前に確定せず、実行時間に大きなばらつきがある。そのため固定平均時間だけで待ち行列を並べるとSLO違反を見誤る。

QLMは各グループを待ち行列内のある位置へ置いた場合に、**前に並ぶグループの処理時間を考えると何秒後に開始できそうか**を推定する。

予測には不確実性も含め、単一の決め打ち時間ではなく「この順ならSLOを守れる可能性がどの程度あるか」をスケジューラへ渡す。

### 4. 待ち行列順序を決めることで、モデル交換や状態移動も間接的に決める

スケジューラが決めた待ち行列順序に応じて、下位の推論提供システムでは必要に応じて

- 要求を別実行単位へ送る
- GPU / CPU間で状態を移す
- 目的モデルをGPUへ読み込む
- 別モデルをGPUから外す

といった処理を行う。

QLMの考え方は、これらを個別経験則で別々に判断するのではなく、**「この順でこの実行単位へ要求を流したい」という最終待ち行列計画を先に作り、必要な処理をそこから導く**ことである。

## 評価

SoCC 2024最終版では、異種GPU・複数モデル・本番要件を反映した実運用推論提供ワークロードを用いて評価している。

主要結果として、既存推論提供方式に対して

- SLO達成: **40〜90%改善**
- スループット: **20〜400%改善**
- 装置利用率: 同等以上

を報告する。

ここでSLO達成は、設定した遅延目標を守れた要求の割合を指す。

特に対話的要求だけでなく、SLOが緩いバッチ要求を同じクラスタへ混在させたとき、バッチを単純に最後へ回すのではなく、**今どれだけ余裕があるかとモデル配置を見ながら空き時間へ差し込める**点が効く。

## 既存研究との差

### FastServe / VTCとの違い

FastServeは実行中の要求を反復境界で一時停止し、要求優先度を制御する。VTCはクライアント間の公平性をトークンサービス量として管理する。

QLMは**要求実行前の待機待ち行列と複数モデル配置**を主対象にし、モデル交換や実行単位割り当てまで含めてエンドツーエンド SLO達成率を最適化する。

### Llumnixとの違い

Llumnixは一度実行を始めた要求を実行単位間で実行中移行し、実行環境で判明した負荷の偏りを修正する。

QLMは主に実行前の待ち行列段階で、将来の待ち時間を見積もり要求をどの順・どの実行単位へ入れるかを先に決める。

両者は競合というより、**QLMで事前待ち行列 / 振り分けを決め、Llumnix型機構で実行開始後の配置を修正する**ように組み合わせられる。

## 限界

- 待機時間推定器の精度はモデル・ハードウェア・ワークロード性能測定に依存する。
- 要求をグループ化するため、個々の要求差を完全には表現しない。
- 最適化に基づくスケジューリングは単純なFIFOより制御装置オーバーヘッドが大きい。
- モデル交換や状態交換自体のコストは下位推論提供システムと記憶装置 / 接続網性能に依存する。
- SLO達成率を主目的にするため、クライアント間の公平性とは別の最適化軸である。

## 一般的な実装上の含意

LLM推論提供のSLO違反はGPUカーネルだけでなく、**待ち行列で何秒待ったか**によって大きく決まる。

特に複数モデル環境では、モデル局所性だけを優先すると急ぎ要求が詰まり、逆にSLOだけを見るとモデル再読み込みが増える。

そのため、待ち行列の待機時間・残りSLO余裕・モデルがすでにGPUへ載っているか・実行単位の負荷を一つのスケジューラで扱い、要求をGPUへ渡す前から最適化する価値がある。
