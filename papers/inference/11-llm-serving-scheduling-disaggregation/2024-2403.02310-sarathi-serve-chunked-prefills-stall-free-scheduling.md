# Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve

> 長いprefillを小さいchunkへ分割し、毎iterationで既存decodeを先に入れて残りtoken budgetへprefill chunkを詰めることで、decodeを止めずに新requestを追加しthroughputとP99 TBTを両立するserving scheduler。

## 概要

Sarathi-Serveは、continuous batchingで新しいprefillを優先すると、既存requestのdecodeが長時間止まる **generation stall** が起きる問題を扱う。

prefillは一度に長いpromptを処理するため1 iterationが長い一方、decodeはrequestごとに1 tokenだけなので短い。vLLM / Orca型のprefill-prioritizing schedulerでは、新requestをすぐbatchへ入れられてthroughputは高いが、長いprefillが進行中decodeのTBTを悪化させる。逆にdecodeを優先し続けると新requestが入れずthroughputが落ちる。

Sarathi-Serveはprefillを複数chunkへ分割し、**既存decodeを毎iteration必ず処理した上で、余った計算budgetにprefill chunkを入れる**。これによりprefillを追加してもdecodeを数秒単位で止めず、大batchのthroughputを利用できる。

## 手法

### 1. Chunked-prefills

長いpromptを、ほぼ同じ計算量になるtoken chunkへ分割して複数iterationで処理する。

full prefillをdecode batchへそのまま混ぜると1 iterationが急に長くなるが、chunk sizeを制限すればdecode側へ加わるlatencyを上限付きにできる。

chunkは小さすぎるとGEMMのarithmetic intensityが下がりfixed overheadも増えるため、単純に細かくすればよいわけではない。論文ではYi-34Bでchunk 512の場合prefill overheadが最大約25%、2048ではほぼ無視できる程度まで下がると報告する。

### 2. Stall-free scheduling

各iterationで次の順にtoken budgetを使う。

1. 進行中requestのdecode tokenをすべて入れる
2. 途中まで処理済みのprefill chunkを入れる
3. 残りbudgetがあれば新requestのprefillを入れる

新prefillは残りbudgetに収まる大きさだけ実行するため、**新requestを受け入れても既存decodeを止めない**。

Mistral-7Bの例では、full prefillをdecodeへ混ぜるとcontext 4096・batch 1でdecode-onlyの20倍以上のbatch timeになるのに対し、chunked prefillでは増加を約2倍程度へ抑えている。

### 3. Token budgetでthroughput / latencyを調整する

1 iterationで許すtoken数をtoken budgetとして設定する。

小さいbudgetはP99 TBTを抑えやすい一方、prefill chunking overheadが増える。大きいbudgetはGPU効率を高めるが、1 iterationが長くなりTBTが悪化する。

したがってSLOに応じてbudgetを選ぶことで、vLLMのmax batch sizeだけでは制御しにくいthroughput-latency trade-offを直接調整する。

### 4. Pipeline parallelismのbubbleを減らす

通常のcontinuous batchingでは、decode-only iterationと長いprefill iterationで実行時間が大きく異なり、pipeline stage間にbubbleが発生する。

Sarathi-Serveでは各iterationをtoken budget付近の比較的均一なwork量に揃えるため、pipeline parallelismでstage imbalanceを減らせる。特にcross-node tensor parallelismが高価な環境では、TPをnode内、PPをnode間に置く構成を実用化しやすい。

## 評価

### 条件

| Model | Hardware / parallelism |
|---|---|
| Mistral-7B | A100 80GB ×1 |
| Yi-34B | A100 80GB ×2、TP2 |
| LLaMA2-70B | A40 48GB ×8、TP4-PP2 |
| Falcon-180B | A100 80GB ×8、TP4-PP2、2 node間100Gbps Ethernet |

Mistral / Yi / FalconではAzure NC96ads v4を使用し、主workloadはOpenChat ShareGPT4とarXiv summarization。baselineはvLLMとOrcaで、P99 TBT SLOを満たせる最大queries/sをserving capacityとして評価する。

### Serving capacity

Sarathi-Serveは全model / workloadでbaselineを上回った。

- Mistral-7B: vLLM比 **最大2.6×**
- Yi-34B: vLLM比 **最大3.7×**
- Falcon-180Bのpipeline parallel構成: **最大5.6×級**のend-to-end serving capacity向上

OpenChat ShareGPT4のstrict SLOではYi-34BでvLLM比3.7×。P99 TBT SLOを厳しくするとvLLMはgeneration stallのためcapacityが早く頭打ちになるが、Sarathi-Serveはtoken budgetを小さくしてSLOを守りながらloadを増やせる。

### Pipeline parallelism

Falcon-180Bを2 nodeへ跨がせた場合、8-way TPではcross-node all-reduceが重く、TP4-PP2よりdecode median TBTが2倍以上大きかった。

Sarathi-Serve + TP4-PP2は、strict SLOでvLLMのTP-only構成比4.3×、vLLMのhybrid-parallel構成比3.6×のcapacityを報告する。uniformなiteration sizeでpipeline bubbleを減らす効果が大きい。

## 既存研究との差

### vLLM / Orcaとの違い

vLLM / Orcaのprefill-prioritizing schedulingはGPU memoryに余裕ができると新prefillを一括実行し、既存decodeを待たせる。

Sarathi-Serveは**decodeを先に保護して、prefill側をbudgetに合わせて分割する**ため、continuous batchingのthroughputを維持しながらtail TBTを制御できる。

### DistServe / Splitwiseとの違い

DistServeとSplitwiseはprefill / decodeを物理的に別GPU poolへ分離する。Sarathi-Serveは両phaseを同じGPUへ残し、chunkingとiteration schedulingで干渉を制御する。

したがって追加GPU poolやphase間KV transferを必要とせず、colocated servingのままthroughput-latency trade-offを改善する別解である。

### Mooncakeとの違い

MooncakeはP/D disaggregationとcluster-wide KV cacheを組み合わせる。Sarathi-Serveはsingle pool内のbatch formationが中心で、global KV reuseやremote cache routingは扱わない。

## 限界

- token budget / chunk sizeはmodel、hardware、workload、TBT SLOに依存し、固定値が常に最適ではない。論文でもdynamic budget selectionは将来課題としている。
- chunkを小さくしすぎるとprefill効率が落ち、Yi-34Bではchunk 512で最大約25%のprefill overheadがある。
- chunkを大きくしすぎるとTBTが悪化し、pipeline parallelismではiteration runtime差からbubbleも増える。
- P/Dを同じGPUへ置くため、phaseごとに異なるhardwareを割り当てたいclusterではDistServe / Splitwise型のdisaggregationが有利になり得る。
- 評価はA100 / A40世代中心で、現代的なHopper / BlackwellやMLA modelでは最適token budgetが変わる可能性がある。

## 一般的な実装上の含意

LLM servingで重要なのはbatch sizeだけでなく、**1 scheduling iterationに入れる総token量を一定範囲へ制御すること**である。

prefillを不可分requestとして扱うとprompt長がそのままdecode stallへ変わるが、chunkへ分割すればdecode latencyのbudget内でprefillをバックグラウンド的に進められる。またpipeline parallelismではiterationごとのwork量を均すこと自体がbubble削減につながる。
