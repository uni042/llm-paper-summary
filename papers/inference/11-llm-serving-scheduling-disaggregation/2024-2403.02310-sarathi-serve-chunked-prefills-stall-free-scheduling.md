# Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve

> 長いprefillを小さいchunkへ分け、毎回まず進行中requestのdecode tokenを処理し、残った総token枠へprefillを入れることで、新requestを受けながらdecodeの長時間停止を防ぐserving scheduler。

## 概要

Sarathi-Serveは、continuous batchingで新しいprefillを優先すると、**長いprompt処理の間に既存requestのdecodeが進まず、次tokenが長く返ってこない問題**を扱う。論文ではこの長時間停止をgeneration stallと呼ぶ。

prefillは一度に長いpromptを処理するため1 iterationが長い一方、decodeはrequestごとに1 tokenだけなので短い。新requestのprefillをすぐ実行すればthroughputは上がりやすいが、その間に進行中requestのtoken生成間隔が悪化する。逆にdecodeを優先し続けると、新requestのprompt処理が進まずthroughputとTTFTが悪化する。

Sarathi-Serveはprefillを複数chunkへ分割し、**既存decodeを毎iteration必ず処理した上で、残った計算枠にprefill chunkを入れる**。これによりprefillを追加してもdecodeを数秒単位で止めず、大きなbatchでGPUを使う利点も維持する。

## 手法

### 1. 長いprefillを複数回に分ける

長いpromptを、一定token数程度のchunkへ分割して複数iterationで処理する。

full prefillをdecode batchへそのまま混ぜると1 iterationが急に長くなるが、1回に入れるprefill token数を制限すれば、**新しいpromptを処理したことで既存decodeが待たされる最大時間**を抑えられる。

chunkは小さすぎると、GPUへ渡す行列演算が小さくなり固定costの割合が増えるため、prefill自体の効率が落ちる。論文ではYi-34Bでchunk 512の場合prefill overheadが最大約25%、2048ではほぼ無視できる程度まで下がると報告する。

### 2. 毎回decodeを先に入れ、余った枠へprefillを入れる

各iterationで次の順に総token枠を使う。

1. 進行中requestのdecode tokenをすべて入れる
2. 途中まで処理済みのprefill chunkを入れる
3. 残りに余裕があれば新requestのprefillを入れる

この「毎回decodeを先に確保する」方式を論文ではstall-free schedulingと呼ぶ。

新prefillは残り枠に収まる大きさだけ実行するため、**新requestを受け入れても既存decodeを完全には止めない**。

Mistral-7Bの例では、full prefillをdecodeへ混ぜるとcontext 4096・batch 1でdecode-onlyの20倍以上のbatch timeになるのに対し、chunked prefillでは増加を約2倍程度へ抑えている。

### 3. 1 iterationで処理する総token数を調整つまみにする

1 iterationで許す総token数をtoken budgetとして設定する。

- 小さいbudget: 1 iterationが短くなり、token間隔を短く保ちやすいが、prefillを細かく分けるoverheadが増える
- 大きいbudget: GPU効率は上げやすいが、1 iterationが長くなり、decode tokenが返る間隔が悪化する

したがってserviceのTBT目標に応じてbudgetを選ぶことで、throughputとtoken間latencyを直接調整する。

### 4. Multi-GPU pipelineでも各stageの待ちを減らす

pipeline parallelismではmodelを複数stageへ分け、前stageの出力を後stageへ順に流す。iterationごとの仕事量が大きく違うと、一部stageだけ仕事がなく待つ時間が増える。

Sarathi-Serveでは各iterationの総token量を近い範囲へ揃えるため、stage間の処理時間差を小さくしやすい。論文でいうpipeline bubbleは、**あるstageが他stageの処理待ちで遊んでいる時間**を指す。

特にcross-node tensor parallelismが高価な環境では、GPU内通信が多いtensor parallelismをnode内へ収め、node間はpipeline parallelismでつなぐ構成を使いやすくする。

## 評価

### 条件

| Model | Hardware / parallelism |
|---|---|
| Mistral-7B | A100 80GB ×1 |
| Yi-34B | A100 80GB ×2、TP2 |
| LLaMA2-70B | A40 48GB ×8、TP4-PP2 |
| Falcon-180B | A100 80GB ×8、TP4-PP2、2 node間100Gbps Ethernet |

Mistral / Yi / FalconではAzure NC96ads v4を使用し、主workloadはOpenChat ShareGPT4とarXiv summarization。baselineはvLLMとOrcaで、**P99 TBT目標を守りながら処理できる最大queries/s**をserving capacityとして評価する。

P99 TBTは、遅い方から1%に入るtoken間隔まで含めて見た値であり、平均だけでなく「たまに長く止まる」現象を評価する指標である。

### Serving capacity

Sarathi-Serveは全model / workloadでbaselineを上回った。

- Mistral-7B: vLLM比 **最大2.6×**
- Yi-34B: vLLM比 **最大3.7×**
- Falcon-180Bのpipeline parallel構成: **最大5.6×級**のend-to-end serving capacity向上

OpenChat ShareGPT4のstrict SLOではYi-34BでvLLM比3.7×。TBT目標を厳しくするとvLLMは長prefillによるdecode停止のためcapacityが早く頭打ちになるが、Sarathi-Serveはtoken budgetを小さくして目標を守りながらloadを増やせる。

### Pipeline parallelism

Falcon-180Bを2 nodeへ跨がせた場合、8-way TPではcross-node all-reduceが重く、TP4-PP2よりdecode median TBTが2倍以上大きかった。

Sarathi-Serve + TP4-PP2は、strict SLOでvLLMのTP-only構成比4.3×、vLLMのhybrid-parallel構成比3.6×のcapacityを報告する。各iterationの仕事量を揃え、pipeline stageの待ちを減らす効果が大きい。

## 既存研究との差

### vLLM / Orcaとの違い

vLLM / Orcaのprefill-prioritizing schedulingはGPU memoryに余裕ができると新prefillを一括実行し、既存decodeを待たせる。

Sarathi-Serveは**decodeを先に保護して、prefill側を残りtoken枠に合わせて分割する**ため、continuous batchingのthroughputを維持しながら遅いtoken間隔を制御できる。

### DistServe / Splitwiseとの違い

DistServeとSplitwiseはprefill / decodeを物理的に別GPU poolへ分離する。Sarathi-Serveは両phaseを同じGPUへ残し、chunkingとiteration schedulingで干渉を制御する。

したがって追加GPU poolやphase間KV transferを必要とせず、同じGPU poolのままthroughput-latency trade-offを改善する別解である。

### Mooncakeとの違い

MooncakeはP/D disaggregationとcluster-wide KV cacheを組み合わせる。Sarathi-Serveはsingle pool内のbatch formationが中心で、global KV reuseやremote cache routingは扱わない。

## 限界

- token budget / chunk sizeはmodel、hardware、workload、TBT SLOに依存し、固定値が常に最適ではない。
- chunkを小さくしすぎるとprefill効率が落ち、Yi-34Bではchunk 512で最大約25%のprefill overheadがある。
- chunkを大きくしすぎるとTBTが悪化し、pipeline parallelismではiteration runtime差からstageの待ち時間も増える。
- P/Dを同じGPUへ置くため、phaseごとに異なるhardwareを割り当てたいclusterではDistServe / Splitwise型のdisaggregationが有利になり得る。
- 評価はA100 / A40世代中心で、現代的なHopper / BlackwellやMLA modelでは最適token budgetが変わる可能性がある。

## 一般的な実装上の含意

LLM servingで重要なのはbatch sizeだけでなく、**1 scheduling iterationに入れる総token量を一定範囲へ制御すること**である。

prefillを不可分requestとして扱うとprompt長がそのままdecode stallへ変わるが、chunkへ分割すればdecode latencyのbudget内でprefillを少しずつ進められる。またpipeline parallelismではiterationごとのwork量を均すこと自体がstage待ち削減につながる。
