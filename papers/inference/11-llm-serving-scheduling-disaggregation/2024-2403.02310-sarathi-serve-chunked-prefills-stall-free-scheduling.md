# Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve

> 長いプリフィルを小さい分割片へ分け、毎回まず進行中要求のデコードトークンを処理し、残った総トークン枠へプリフィルを入れることで、新要求を受けながらデコードの長時間停止を防ぐ推論提供スケジューラ。

## 概要

Sarathi-Serveは、連続バッチ処理で新しいプリフィルを優先すると、**長いプロンプト処理の間に既存要求のデコードが進まず、次トークンが長く返ってこない問題**を扱う。論文ではこの長時間停止を生成停止と呼ぶ。

プリフィルは一度に長いプロンプトを処理するため1反復が長い一方、デコードは要求ごとに1トークンだけなので短い。新要求のプリフィルをすぐ実行すればスループットは上がりやすいが、その間に進行中要求のトークン生成間隔が悪化する。逆にデコードを優先し続けると、新要求のプロンプト処理が進まずスループットとTTFTが悪化する。

Sarathi-Serveはプリフィルを複数分割片へ分割し、**既存デコードを毎反復必ず処理した上で、残った計算枠にプリフィル分割片を入れる**。これによりプリフィルを追加してもデコードを数秒単位で止めず、大きなバッチでGPUを使う利点も維持する。

## 手法

### 1. 長いプリフィルを複数回に分ける

長いプロンプトを、一定トークン数程度の分割片へ分割して複数反復で処理する。

全体プリフィルをデコードバッチへそのまま混ぜると1反復が急に長くなるが、1回に入れるプリフィルトークン数を制限すれば、**新しいプロンプトを処理したことで既存デコードが待たされる最大時間**を抑えられる。

分割片は小さすぎると、GPUへ渡す行列演算が小さくなり固定コストの割合が増えるため、プリフィル自体の効率が落ちる。論文ではYi-34Bで分割片512の場合プリフィルオーバーヘッドが最大約25%、2048ではほぼ無視できる程度まで下がると報告する。

### 2. 毎回デコードを先に入れ、余った枠へプリフィルを入れる

各反復で次の順に総トークン枠を使う。

1. 進行中要求のデコードトークンをすべて入れる
2. 途中まで処理済みのプリフィル分割片を入れる
3. 残りに余裕があれば新要求のプリフィルを入れる

この「毎回デコードを先に確保する」方式を論文では停止なしスケジューリングと呼ぶ。

新プリフィルは残り枠に収まる大きさだけ実行するため、**新要求を受け入れても既存デコードを完全には止めない**。

Mistral-7Bの例では、全体プリフィルをデコードへ混ぜると文脈 4096・バッチ 1でデコードのみの20倍以上のバッチ時間になるのに対し、分割したプリフィルでは増加を約2倍程度へ抑えている。

### 3. 1反復で処理する総トークン数を調整つまみにする

1反復で許す総トークン数をトークン予算として設定する。

- 小さい予算: 1反復が短くなり、トークン間隔を短く保ちやすいが、プリフィルを細かく分けるオーバーヘッドが増える
- 大きい予算: GPU効率は上げやすいが、1反復が長くなり、デコードトークンが返る間隔が悪化する

したがってサービスのTBT目標に応じて予算を選ぶことで、スループットとトークン間遅延を直接調整する。

### 4. 複数GPUのパイプラインでも各段階の待ちを減らす

パイプライン並列化ではモデルを複数段階へ分け、前段階の出力を後段階へ順に流す。反復ごとの仕事量が大きく違うと、一部段階だけ仕事がなく待つ時間が増える。

Sarathi-Serveでは各反復の総トークン量を近い範囲へ揃えるため、段階間の処理時間差を小さくしやすい。論文でいうパイプラインの空き時間は、**ある段階が他段階の処理待ちで遊んでいる時間**を指す。

特にノード間テンソル並列化が高価な環境では、GPU内通信が多いテンソル並列化をノード内へ収め、ノード間はパイプライン並列化でつなぐ構成を使いやすくする。

## 評価

### 条件

| モデル | ハードウェア / 並列化 |
|---|---|
| Mistral-7B | A100 80GB ×1 |
| Yi-34B | A100 80GB ×2、TP2 |
| LLaMA2-70B | A40 48GB ×8、TP4-PP2 |
| Falcon-180B | A100 80GB ×8、TP4-PP2、2 node間100Gbps Ethernet |

Mistral / Yi / FalconではAzure NC96ads v4を使用し、主ワークロードはOpenChat ShareGPT4とarXiv summarization。比較対象はvLLMとOrcaで、**P99 TBT目標を守りながら処理できる最大クエリ/s**を推論提供処理能力として評価する。

P99 TBTは、遅い方から1%に入るトークン間隔まで含めて見た値であり、平均だけでなく「たまに長く止まる」現象を評価する指標である。

### 推論提供処理能力

Sarathi-Serveは全モデル / ワークロードで比較対象を上回った。

- Mistral-7B: vLLM比 **最大2.6×**
- Yi-34B: vLLM比 **最大3.7×**
- Falcon-180Bのパイプライン並列構成: **最大5.6×級**のエンドツーエンド推論提供処理能力向上

OpenChat ShareGPT4の厳格 SLOではYi-34BでvLLM比3.7×。TBT目標を厳しくするとvLLMは長プリフィルによるデコード停止のため処理能力が早く頭打ちになるが、Sarathi-Serveはトークン予算を小さくして目標を守りながら負荷を増やせる。

### パイプライン並列化

Falcon-180Bを2ノードへ跨がせた場合、8方向TPではノード間の全削減通信が重く、TP4-PP2よりデコード中央値TBTが2倍以上大きかった。

Sarathi-Serve + TP4-PP2は、厳格SLOでvLLMのTPのみ構成比4.3×、vLLMの混合並列構成比3.6×の処理能力を報告する。各反復の仕事量を揃え、パイプライン段階の待ちを減らす効果が大きい。

## 既存研究との差

### vLLM / Orcaとの違い

vLLM / Orcaのプリフィル優先スケジューリングはGPUメモリに余裕ができると新プリフィルを一括実行し、既存デコードを待たせる。

Sarathi-Serveは**デコードを先に保護して、プリフィル側を残りトークン枠に合わせて分割する**ため、連続バッチ処理のスループットを維持しながら遅いトークン間隔を制御できる。

### DistServe / Splitwiseとの違い

DistServeとSplitwiseはプリフィル／デコードを物理的に別GPUプールへ分離する。Sarathi-Serveは両処理段階を同じGPUへ残し、分割と反復スケジューリングで干渉を制御する。

したがって追加GPUプールや処理段階間KV転送を必要とせず、同じGPUプールのままスループット-遅延トレードオフを改善する別解である。

### Mooncakeとの違い

MooncakeはP/D分離とクラスタ全体KVキャッシュを組み合わせる。Sarathi-Serveは単一プール内のバッチ形成が中心で、全体KV再利用や遠隔キャッシュルーティングは扱わない。

## 限界

- トークン予算 / 分割片サイズはモデル、ハードウェア、ワークロード、TBT SLOに依存し、固定値が常に最適ではない。
- 分割片を小さくしすぎるとプリフィル効率が落ち、Yi-34Bでは分割片512で最大約25%のプリフィルオーバーヘッドがある。
- 分割片を大きくしすぎるとTBTが悪化し、パイプライン並列化では反復実行環境差から段階の待ち時間も増える。
- P/Dを同じGPUへ置くため、処理段階ごとに異なるハードウェアを割り当てたいクラスタではDistServe / Splitwise型の分離が有利になり得る。
- 評価はA100 / A40世代中心で、現代的なHopper / BlackwellやMLAモデルでは最適トークン予算が変わる可能性がある。

## 一般的な実装上の含意

LLM推論提供で重要なのはバッチサイズだけでなく、**1スケジューリング反復に入れる総トークン量を一定範囲へ制御すること**である。

プリフィルを不可分要求として扱うとプロンプト長がそのままデコード停止へ変わるが、分割片へ分割すればデコード遅延の予算内でプリフィルを少しずつ進められる。またパイプライン並列化では反復ごとの機能する量を均すこと自体が段階待ち削減につながる。

## コード

公式実装 `microsoft/sarathi-serve` が公開されている。vLLMを基盤に分割したプリフィル、停止なしスケジューラ、テンソル / パイプライン並列化、ベンチマークを実装している。
