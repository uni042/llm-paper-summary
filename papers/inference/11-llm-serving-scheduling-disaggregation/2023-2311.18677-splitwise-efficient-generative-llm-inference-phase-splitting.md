# Splitwise: Efficient Generative LLM Inference Using Phase Splitting

> compute-heavyなprompt phaseとmemory-boundなtoken generation phaseを別machine poolへ分離し、phaseごとにGPU世代・power cap・台数を変えてprovisioningすることで、cluster throughput・cost・powerを同時に改善するserving設計。

## 概要

Splitwiseは、prompt processingとtoken generationではGPUに求めるresourceが大きく違うのに、従来servingでは同じmachineで両方を処理している点を問題にする。

prompt phaseは大量tokenを並列処理するためcompute性能の高いGPUが有利だが、token generationはmemory bandwidth / capacityに支配されやすく、最新GPUの高いFLOPsや高いpower budgetを十分使わない。

そこで2 phaseを別machine poolへ分離し、**promptには高compute GPU、token generationにはより安価な旧世代GPUやpower-capped GPUを使う**ことを可能にする。requestのKV cacheはprompt machineからtoken machineへ転送する。

DistServeがSLO付きper-GPU goodputに合わせてparallelism / placementを探索するのに対し、Splitwiseは特に**hardware generation・cost・provisioned powerまで含めたcluster design**を中心に評価する。

## 問題設定

H100はA100に対して計算性能が約3.43×高い一方、HBM bandwidthは約1.64×、capacityは同じ80GBである。token generationの性能は計算性能ほど伸びないため、decode専用にH100を使うと高価なcompute resourceを余らせやすい。

また実測ではH100のpower capを700Wから350Wまで下げてもtoken generation latencyへの影響が小さい一方、prompt latencyは大きく悪化する。つまりphaseごとに適したGPU / power settingが異なる。

## 手法

### 1. Prompt / Token / Mixedの3 poolを持つ

通常requestはprompt poolでprefillし、生成されたKV cacheをtoken poolへ送ってdecodeする。

traffic分布が設計時想定からずれた場合に固定partitionが遊ばないよう、少数のmachineをmixed poolとして動的に再利用できる。queue imbalanceが大きいとprompt machine / token machineを一時的にmixed roleへ切り替える。

### 2. Phaseごとに異なるhardwareを選ぶ

評価する主なcluster variantは、

- A100 → A100
- H100 → H100
- H100 prompt → A100 token
- H100 prompt → power-capped H100 token

などである。

promptはcomputeを使い切りやすいためH100の価値が高いが、token phaseはA100やpower-capped H100でもcost / power efficiencyを高められる。

### 3. Promptとtoken machineを同時に予約する

cluster-level schedulerはrequest到着時にprompt側とtoken側の両方を決める。Shortest Queue系のroutingを用い、prompt処理中に後続token machineのcapacityを確保することでphase間handoffを安定させる。

### 4. KV transferをlayer単位でprompt計算と重ねる

prompt全体が終わってからKVを一括転送するとhandoff latencyがそのまま加算される。

Splitwiseは各layerでKVが生成されるたびにtoken machineへ転送し、後続layerのprompt計算とnetwork transferをoverlapする。高速InfiniBand backendを使い、state transferをcritical pathからできるだけ外す。

### 5. Trace-driven simulatorでcluster構成を探索する

A100 / H100上でprompt / token latency、batching、powerをprofileし、Azure production traceのinput / output length分布を使うevent-driven simulatorへ入力する。

必要なthroughputとTTFT / TBT / E2E SLOに対して、prompt / token machine数・GPU種類・power capを変え、throughput、cost、powerを最適化するcluster designを選ぶ。

## 評価

### 条件

実機characterizationではA100 / H100を使い、Llama-70BやBLOOM-176Bを評価する。cluster-level結果は実測profileとMicrosoft Azureのproduction LLM inference traceを使ったsimulationが中心である。

したがって大規模clusterの「○倍」は数十台の実clusterをすべて構築した測定ではなく、**実機profileで校正したtrace-driven simulatorの結果**として読む必要がある。

### Cost / throughput

iso-cost構成ではSplitwise-AAがH100 baselineより**1.4×高いthroughput**を、同じcostで実現した。ただしpowerは25%多く、rack spaceも多く使う。

iso-throughputでは同じthroughputを**25%低いcost**で実現できる構成を示す。

### Power budget

conversation traceのiso-power比較では、A100をphase別に使うSplitwise-AAがbaselineに対し**2.15× throughput**を同じpower / costで達成した条件がある。

論文全体ではperformance SLOを考慮した設計で、同じcostなら1.76× throughputかつ15%低いpower、または**同じcostとpowerで最大2.35× throughput**を報告する。

### Hardware specialization

token phaseはH100の700W→350W power capでもlatencyへの影響が小さい一方、prompt phaseはpower capに敏感だった。これはP/D disaggregationを単なる干渉除去だけでなく、**異種hardware / power provisioning**へ使える根拠になっている。

## 既存研究との差

### DistServeとの違い

両者ともprefillとdecodeを別GPUへ分離する。

DistServeはTTFT / TPOT SLOからphaseごとのparallelismとnetwork-aware placementを自動探索し、per-GPU goodputを中心に最適化する。Splitwiseは**A100 / H100、power cap、cost、datacenter power budget**まで含めたcluster provisioningを中心にする。

### Mooncakeとの違い

SplitwiseのKV transferは主に1 requestのprompt→token state handoffである。MooncakeはさらにKVをcluster-wide cacheとして長期間保持し、別requestのprefix reuseやreplicationまでglobal schedulingへ取り込む。

### Colocated mixed batchingとの違い

従来はpromptとtokenを同じGPUでbatchするため、長いpromptがTBTを悪化させる。Splitwiseはphaseを分けてbatching opportunityを同種workだけに集中させる一方、低loadやworkload shift時のfragmentationをmixed poolで緩和する。

## 限界

- cluster-level主要結果はtrace-driven simulationであり、数十台規模の全構成を実機で再現した結果ではない。
- A100 / H100世代のcompute対memory scalingを前提とした設計で、GB200等では最適hardware mixが変わる。
- phase間KV transferには高速backend networkが必要で、network oversubscription時の影響は大きくなる。
- heterogeneous poolはworkload変化に対してhomogeneous poolより柔軟性が低く、論文でもtrace mismatch時に最大7%程度のthroughput低下を観測している。
- model parallelismや現代的なGQA / MLAでKV sizeが変わるとhandoff costも変化する。

## 一般的な実装上の含意

P/D disaggregationの価値はphase interferenceの除去だけでなく、**hardware procurementとpower managementをphase別にできること**にある。

decodeがmemory-boundなら、最も新しく高価なGPUを全phaseへ均等配備するより、compute-heavyなprefillへ新GPUを集中し、decodeにはbandwidth / capacityあたりのcostが良いGPUを使う方がcluster全体のPerf/$を上げられる可能性がある。
