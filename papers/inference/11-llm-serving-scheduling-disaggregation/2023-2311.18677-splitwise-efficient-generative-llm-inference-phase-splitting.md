# Splitwise: Efficient Generative LLM 推論 Using Phase Splitting

> プリフィルとデコードを別の計算機群へ分け、それぞれに向くGPU世代・電力設定・台数を使い分けて、クラスタ全体のスループット・コスト・消費電力を改善するサービング設計。

## 概要

プリフィルは多数トークンをまとめて処理するためGPUの計算性能を使いやすい。一方デコードは1トークンずつ進むためメモリ帯域の影響が大きく、最新GPUの高いFLOPsを使い切れない場合がある。

Splitwiseはこの差を利用し、**プリフィルとデコードを別GPU群へ分離する**。プリフィルには計算性能の高いGPU、デコードにはより安価な旧世代GPUや消費電力を抑えたGPUを割り当てることで、同じコストや電力予算でより多くのリクエストを処理することを狙う。

ただし完全に2群へ固定すると、入力が急に長くなった場合はプリフィル群だけ、出力が長くなった場合はデコード群だけが混雑し得る。そこでSplitwiseは第3の混合群を用意し、負荷偏りが出たときに一時的に反対側の処理を引き受けさせる。

プリフィルで生成したKVキャッシュはデコード側へ転送する。この状態移動が分離方式の追加コストになるため、転送先を早めに決め、層ごとに生成済みKVを送り始めることで、プリフィル計算とネットワーク通信を重ねる。

## 問題設定

H100はA100より計算性能の伸びが大きい一方、メモリ帯域の伸びはそれほど大きくない。そのためデコードだけを見ると、高価なH100の計算性能を十分使えないことがある。

またH100の消費電力上限を下げてもデコード遅延はあまり悪化しない条件がある一方、プリフィルは大きく遅くなる。つまりプリフィルとデコードでは適したGPUや電力設定が違う。

従来の同居方式では、同じGPUが計算律速のプリフィルとメモリ律速のデコードを交互に処理するため、GPU選定・電力設定・バッチング方針を両方へ妥協して合わせる必要がある。Splitwiseは処理相を物理的に分けることで、各相へ別の最適点を使えるようにする。

## 手法

### 1. プリフィル / デコード / 混在の3種類のGPU プール

通常リクエストはプリフィル群でプロンプトを処理し、そのKVキャッシュをデコード群へ送る。クラスタ級スケジューラは到着時にプリフィル先とデコード先を同時に決め、両方の待ち行列へ予約する。

同時に転送先を決める理由は、プリフィル終了後にデコード先を探すのでは遅いからである。転送相手が事前に分かれば、プリフィルの各層がKVを生成した時点からそのGPUへ送り始められる。

トラフィックが想定からずれた時に片方だけGPUが余らないよう、一部GPUはプリフィルにもデコードにも使える混合群として動かす。混合GPUは本来の所属を保ちながら、反対種の待ち行列が長くなったときだけその処理を受け持つ。

反対側の仕事がなくなれば元の専用群へ戻るため、すべてのGPUを恒常的に混合処理へ戻すわけではない。これにより分離で得た相別最適化を維持しつつ、短期的な入力長／出力長分布のずれを吸収する。

### 2. Phaseごとにハードウェアと電力設定を選ぶ

論文では、プリフィルとデコードの両方をH100で処理する構成だけでなく、プリフィルをH100、デコードをA100にする構成や、デコード側H100の消費電力上限を下げる構成などを比較する。

狙いは、**計算性能が効くプリフィルへ高性能GPUを集中し、デコードにはメモリ性能あたりのコストが良いGPUを使う**ことにある。デコードで余る演算器へ電力を使うより、メモリ帯域を維持したまま電力上限を下げられる条件ならエネルギー効率も改善する。

ただしどのGPU世代がどちらへ適するかは固定ルールではない。モデルサイズ、量子化、GQA/MLA、バッチサイズ、新GPU世代によって計算対メモリ帯域比が変わるため、Splitwiseは実機プロファイルを基にクラスタ設計を比較する。

### 3. リクエストを待ち行列の短い機械へ割り当てる

クラスタ級スケジューラは各機械の保留トークン数やメモリ余裕を受け取り、最短待ち行列（Join the Shortest キュー; JSQ）に近い方針でプリフィル先とデコード先を選ぶ。単純なリクエスト件数ではなく、処理すべきトークン量を待ち行列の長さとして扱う。

プリフィル側が混雑して閾値を超える場合は混合群から候補を探し、それでも足りなければデコード群の一部を一時的に混合化する。逆方向も同様で、需要偏りへオンラインで応答する。

この処理で重要なのは、専用群の台数を毎リクエスト再設計するのではなく、短期偏りは混合群で吸収し、長期間偏りが続く場合だけより粗い再用途化を行う点である。頻繁な役割変更による不安定化を避けつつ、固定比率の弱点を補う。

### 4. KV転送をプリフィル計算と重ねる

プリフィル全体が終わってからKVをまとめて送ると、その転送時間がそのまま最初のデコード開始待ちになる。Splitwiseは層ごとにKVが生成された時点でデコードGPUへ送り、次層のプリフィル計算とネットワーク転送を同時に進める。

例えば層1のKVを送っている間に層2以降を計算し、最終層のプリフィルが終わるころには多くのKV転送も済ませる。これにより、分離方式の主な追加コストである「状態を別機械へ運ぶ時間」をプリフィルのクリティカルパスから外す。

ただしネットワークが遅い、KVが大きい、複数リクエストの転送が競合する条件では隠し切れない。論文の評価は高速InfiniBandを前提としており、PCIeや低速Ethernetだけの構成へ同じ転送影響をそのまま適用できない。

### 5. 実機測定からクラスタ構成を比較する

A100 / H100上でプリフィル・デコード遅延と消費電力を測定し、その値とAzureの本番トレースをシミュレーションへ入力する。候補クラスタごとにプリフィル群、デコード群、混合群の台数、GPU種類、電力設定を変え、設定した遅延SLOを満たすスループット・コスト・電力を比較する。

そのため大規模クラスタの主要結果は、**実機で測った性能を基にしたシミュレーション**であり、すべてのGPU構成を実際に組んで測った結果ではない。この区別は、2.35倍などのクラスタ級倍率を解釈する上で重要である。

## なぜこの設計で効くのか

プリフィルとデコードを同じGPUへ同居させると、演算性能を最大化したい相とメモリ帯域を重視する相へ同じハードウェア・電力設定を使う必要がある。分離すれば各相に合わせたGPUを選べるため、同じ設備費でも「余っている演算性能」に払う割合を下げられる。

さらに混合群とオンラインルーティングにより、相別分離の弱点である負荷偏りを緩和する。KV転送もプリフィルと重ねることで、分離による状態移動コストを小さくし、ハードウェア使い分けの利得を残す。

## 評価

Llama-70BやBLOOM-176Bを使ってA100 / H100の特性を測定した。

同じコストで比較した条件では、Splitwise構成がH100のみの比較対象より**1.4倍高いスループット**を示した。同じスループットなら**25%低いコスト**で済む構成も報告している。同じコストと電力を揃えた条件では、最大**2.35倍のスループット**を報告した。

またデコードではH100の電力上限を700Wから350Wへ下げても遅延への影響が小さい一方、プリフィルは大きく遅くなることを確認している。この差が相別電力設定を行う根拠になっている。

## 既存研究との差

### DistServeとの違い

両者ともプリフィルとデコードを別GPUへ分ける。DistServeはSLOを満たして処理できるリクエスト数を増やすために、各相のGPU数や並列度を決める。Splitwiseはさらに**GPU世代、コスト、消費電力**までクラスタ設計へ含める。

### Mooncakeとの違い

SplitwiseのKV転送は主に同じリクエストのプリフィル→デコード移動である。MooncakeはKVをクラスタ全体へ保存し、別リクエストでも接頭辞を再利用できるようにする。

## 限界

- クラスタ級の主要結果はシミュレーション中心。
- A100 / H100世代の性能差を前提としており、新しいGPUでは最適構成が変わる。
- 相間KV転送には高速ネットワークが必要。
- トラフィックが大きく変化すると、プリフィル／デコードの固定割合が合わなくなる。
- GQA / MLAなどでKVサイズが変わると転送コストも変わる。

## 一般的な実装上の含意

プリフィル／デコード分離の利点は、両者の干渉をなくすことだけではない。**相ごとに異なるGPUや電力設定を使える**ため、データセンターのGPU構成や電力配分そのものを効率化できる。

ただし分離だけを導入してKVを直列転送したり、負荷偏りを吸収する余剰群を用意しなかったりすると、状態移動と片側アイドルが新しいボトルネックになる。実装では相分離・転送重畳・動的な混合処理を一体として考える必要がある。
