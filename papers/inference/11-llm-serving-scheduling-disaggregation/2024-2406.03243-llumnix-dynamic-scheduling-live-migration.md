# Llumnix：実行中の要求移動でLLM提供を再スケジューリングする

## 概要

Llumnixは、複数のGPU実行単位で大規模言語モデルを提供するとき、要求を最初に振り分けて終わりにせず、**生成途中でも別の実行単位へ移動する**スケジューラである。LLMでは入力長・出力長が要求ごとに異なり、出力長とKVキャッシュの増加量を到着時に予測できない。初期配置が均等でも、時間とともに一部GPUの待ち行列やメモリだけが逼迫する。従来の到着時振り分けは、その後に判明した偏りを修正しにくい。

Llumnixは追記専用のKVキャッシュを生成処理と並行して複製し、最後の短い差分だけ要求を止めて移す。移動の仕組みを負荷分散、長い入力用の空きメモリ集約、高優先度要求の隔離、実行単位の自動伸縮に共通利用する。16台のNVIDIA A10 GPU上でLLaMA-7Bを提供する実験では、改良INFaaSスケジューラ（INFaaS++）と比べてP99の初回トークン遅延を最大約15倍、P99のデコード遅延を最大2倍改善し、同程度の末尾遅延を維持しながら最大36%の費用削減を示す。

## 問題設定：配置の良し悪しは生成中に変わる

一つのモデル実行単位では連続バッチングと動的KVメモリ割当を使う。デコードの反復ごとに新しいKVブロックが追加されるため、ある要求がどれだけメモリを使うかは生成完了まで確定しない。要求が多いと新しいブロックを確保できず、一部の要求を先取り停止して後で再計算する。元の処理を中断して再計算する費用は、単なるGPU演算の混雑よりも大きな遅延の尾を作る。

原著の動機付けでは、平均GPUメモリ利用率が約62%という中程度の負荷でも、要求の8%が先取り停止され、P99の1トークン当たり遅延は中央値の3.8倍に達した。P99要求では追加待機・KV再計算が遅延の大きな割合を占める。要求到着時にラウンドロビンで均等配置しても、長い出力を生成する要求が偏れば同じ問題が再発する。

逆に、負荷分散のため要求を広く散らすと、クラスタ全体には空きメモリがあっても各GPUの空きが小さくなり、長いプロンプトの初回処理に必要な大きなKV領域を一つの実行単位で確保できない。Llumnixが扱う断片化は、主に**複数GPU間に散らばった空き容量**であり、GPU内の物理アドレスの連続性だけを指すわけではない。負荷分散と空きメモリ集約は対立し得るが、要求を後から動かせれば状況に応じて切り替えられる。

## 手法

### 1. 追記専用KVキャッシュを利用した実行中移動

LLMのデコードでは、新しいトークンのキー・値を末尾に追加し、既存トークンのKVを通常は書き換えない。Llumnixはこの性質を使い、移動元で生成を継続しながら確定済みKVブロックを移動先へ複製する。最初の複製中にも新しいKVが生まれるため、次段階で増分を送り、最後に小さくなった未転送部分を短時間だけ停止して転送する。これにより、全KVを一括停止転送した場合の系列長に比例する停止を避ける。

転送完了後は要求の実行主体を移動先へ切り替え、移動元からはその要求を外す。論文の実測では256～8192トークンの系列長で停止時間が概ね20～30ミリ秒とほぼ一定で、移動中のデコードステップへの影響も最大約1%である。8192トークンのLLaMA-30Bを再計算して移す場合は約3.5秒を要し、移動方式の最大111倍の停止になる。これは**移動のために生成を止める時間**の比較であり、転送バイト数が系列長に無関係になるという意味ではない。

### 2. 分散した全体スケジューラと実行単位側の調整器

Llumnixはクラスタ全体の状態を見て移動先候補を決める全体スケジューラと、各実行単位で実際の要求移動を調整する局所構成要素を分離する。実装上の局所調整器はllumletと呼ばれ、実行単位のメモリ状態や要求状態を扱い、移動元・移動先の通信を進める。全体スケジューラが毎トークンの細部を直接制御するのではなく、移動元と移動先の組を決め、局所調整器が継続的に移動を実行することで中央制御の負荷を抑える。

要求が移動しても利用者への出力経路は前段の要求フロントエンドが保持する。移動元のモデル実行単位にAPI接続を固定する設計ではないため、生成結果を引き続き同じ要求として返せる。実装はvLLMを基盤にし、複数実行単位やフロントエンドをRayの分散実行主体として動かす。

### 3. 仮想使用量による複数目的の統一

Llumnixの中心的な政策表現は、実メモリ使用量と別に定義する**仮想使用量（virtual usage）**である。通常要求の仮想使用量は実際のメモリ量に等しい。待ち行列先頭の要求には、まだGPUへ載っていなくても必要メモリ量を仮想的に加える。すると、その実行単位は見かけ上混雑し、他の要求を移動して長い入力用の空きを作る方向に動く。

高優先度要求には、単なる実使用量に加えて、他要求による干渉を避けるための余裕容量を仮想的に加算する。これにより高優先度要求と同居する実行単位が混雑しているように見え、通常要求を他へ逃がせる。停止予定の実行単位には無限大の仮想使用量を持つ架空要求を置き、既存要求を別の実行単位へ移す。新規起動した実行単位には空きがあるため、反対方向の移動が進む。

### 4. 空き余裕指標と要求移動の決定

各実行単位の総メモリをM、要求ごとの仮想使用量をV_i、実行中バッチの要求数をBとすると、空き余裕の指標はF=(M−ΣV_i)/Bで表される。分母にBを置くのは、同じ空き容量でも一反復で新規KVが増える要求数によって、残り何反復を受けられるかが異なるためである。Fが負なら待ち行列や高優先度のため見かけ上過負荷となる。

新しい要求は優先度順に、空き余裕が大きい実行単位へ配置する。定期的な移動判定では、Fが小さい実行単位を移動元、大きい実行単位を移動先として組にする。移動元の局所調整器は優先度が低く系列長の短い要求を優先して移し、移動元が過負荷でなくなれば停止する。自動伸縮では平均空き余裕を一定範囲に保つよう実行単位を増減する。この共通指標が、異なる目的ごとに独立した複雑な移動規則を用意する代わりになっている。

### 5. KV転送の実装と追加費用

vLLMのKVは小さな不連続ブロックとして管理される。これを一つずつネットワークへ送ると小メッセージの費用が増えるため、LlumnixはGPUからCPUの連続バッファへまとめてコピーし、Glooの送受信機能で一括転送する。GPUとCPUの間のコピーは別のCUDA実行流を用い、デコード演算との重なりを作る。高速なGPU間通信ライブラリNCCLでは同時実行の安全性が問題となる条件を避けるため、原著実装はGlooを選んだ。

この経路はGPU→CPU→ネットワーク→CPU→GPUという転送を含み、ネットワーク帯域や移動先の空き容量が必要になる。移動の停止時間が短くても、背景通信・CPUメモリ・複製中の一時領域は無償ではない。極端な過負荷で移動先がない場合、要求を動かすだけで容量不足を解消できるわけではない。

## 評価

### 実験環境と指標

| 観点 | 条件 |
|---|---|
| 実機クラスタ | Alibaba Cloudの4仮想マシン、計16枚のNVIDIA A10 24GB |
| 各マシン | A10を4枚、128仮想CPU、752GBメモリ、PCIe 4.0 |
| マシン間接続 | 64Gbpsネットワーク |
| モデル | LLaMA-7B（1GPU/実行単位）、LLaMA-30B（4GPUテンソル並列） |
| 精度・推論基盤 | 16ビット、vLLMを全方式で共通利用 |
| ワークロード | ShareGPT、BurstGPT、入力・出力長のべき乗分布による合成要求 |
| 到着過程 | ポアソン分布、ガンマ分布。合成トレースは各1万要求 |
| 比較方式 | ラウンドロビン、改良INFaaS（INFaaS++）、機能別のLlumnix派生 |
| 主指標 | 初回トークン遅延、トークン間遅延、要求全体遅延の平均と99パーセンタイル |

初回トークン遅延は、待ち行列を含めて最初の応答を返すまでの時間である。デコード遅延は初回生成後の各トークンに要する時間を測る。P99は要求の遅い側1%の境界を示し、平均だけでは見えない長い待機・先取り停止の影響を捉える。論文は同じvLLM基盤でスケジューラを比較し、モデル実装の違いによる性能差を抑えている。

### 移動機構の単独評価

LLaMA-7Bと30Bについて、系列長256から8192までを変え、提案する実行中移動、全量停止コピー、KV再計算を比較する。提案方式は停止20～30ミリ秒程度を保つ一方、再計算方式は長系列で秒単位に増える。8192トークンの30Bでは再計算が約3.5秒で、提案方式比最大111倍の停止となる。移動中の通常デコードステップ時間への差は最大約1%、移動が進行する時間は各実行単位の全時間の約10%にとどまるという観測も示す。

この測定が示すのは、追記済みKVを生成と並行してコピーすることによって要求のサービス停止を小さくできる点である。移動の総ネットワーク量をゼロにしたわけではなく、コピーが計算より遅い構成や長文脈の別モデルで同じ停止時間になることは保証されない。

### 実運用型負荷の遅延

16個のLLaMA-7B実行単位に対するShareGPT/BurstGPTでは、ラウンドロビンに対し平均・P99の要求全体遅延をそれぞれ最大2倍・2.9倍改善した。初回トークン遅延はラウンドロビン比で平均最大26.6倍、P99最大34.4倍改善し、先取り停止による損失時間は平均84%減少した。これはランダムに近い到着時配置が、出力長の不均一さを吸収できないことを示す。

比較相手をINFaaS++へ限定すると、実負荷では平均・P99初回トークン遅延を最大2.2倍・5.5倍、P99デコード遅延を最大1.3倍改善する。さらに入力・出力長が極端に偏る合成負荷では、初回トークン遅延が平均最大7.7倍、P99最大14.8倍へ広がる。したがって「P99最大15倍」は、すべてのShareGPT/BurstGPT条件に共通する値ではなく、**長い入力が混在する合成負荷を含む評価全体の最大値**である。

### 断片化、優先度、自動伸縮

メモリ断片化の事例では、要求が待っているのに他GPUへ散在して利用できない空きメモリの割合が、INFaaS++の平均7.9%からLlumnixの0.7%へ減った。相対的に約92%減であり、実行中要求を移すことで大きな入力を受け入れる余地を作れるという機構の直接的な証拠になる。

高優先度要求の試験では、通常要求の性能を概ね維持しながら優先要求の遅延を最大1.5倍改善する。これは単に高優先度要求を待ち行列の先頭に置くだけでなく、実行中の通常要求を別のGPUへ逃がして干渉を減らす設計の効果である。自動伸縮では同程度のP99初回トークン遅延を保つ条件で、比較方式より必要な実行単位数を減らし、最大36%の費用削減を報告する。

### スケーリングと比較上の留保

論文の主要な遅延・移動時間は実機で測定している。ただし64実行単位への拡張性検討は、A10で測った性能を基にした実行モデルによる評価であり、64GPU実機を動かした結果とは区別する。要求長や到着分布を変えると、長い入力のための空き集約と通常の負荷分散の重要度が変わる。低負荷ではそもそも待ち行列が短く移動の利得が小さく、極端な高負荷では移動先の余裕が減る。

## 既存研究との差

ラウンドロビンやINFaaS++は要求到着時の配置と負荷を重視する。Llumnixは配置後のKV増加と要求長の不確実性を観測して**実行中に配置を修正**できる点が異なる。vLLMの連続バッチングやPagedAttentionは主として一実行単位内のバッチ・KV管理であり、Llumnixは複数実行単位間の要求移動を追加する。プリフィルとデコードを別資源へ分けるDistServe/Splitwiseとも、処理段階の分離でなく同種実行単位間の移動を中心にする点で異なる。

## 限界と障害時の動作

評価はA10世代、LLaMA-7B/30B、旧vLLM実装に集中する。長文脈モデル、GQA/MLAによるKVサイズの異なるモデル、GPU直結通信を使う新構成での停止時間と移動利得は別途検証が必要である。移動先のメモリ容量と転送帯域が足りない場合、仮想使用量だけでは問題を解消できない。移動の頻発は背景通信やCPUバッファ費用を増やし、ネットワーク混雑下では隠蔽できない可能性がある。

障害耐性について、全体スケジューラが故障した場合は移動を停止し、要求フロントエンドが単純な配置規則へ退避する。一方、実行単位やその局所調整器が故障した場合、その実行単位で動作中の要求は中断される。つまり実行中移動は障害発生前に状態を逃がす仕組みであり、障害時の要求状態の完全複製や無停止フェイルオーバーを保証するものではない。
