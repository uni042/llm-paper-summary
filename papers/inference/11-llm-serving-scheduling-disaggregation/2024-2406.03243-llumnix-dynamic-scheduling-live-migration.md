# Llumnix: Dynamic Scheduling for Large Language Model Serving

> requestとKV cacheを実行中のmodel instance間でlive migrationし、load imbalance・GPU memory fragmentation・priority差・auto-scalingに応じて配置を実行中に組み替えるmulti-instance LLM serving scheduler。

## 概要

一般的なmulti-instance servingではrequestを最初に1つのinstanceへdispatchした後、そのrequestは完了まで同じinstanceに固定される。しかしLLM requestはoutput lengthとKV memory消費量を事前に正確に予測できないため、dispatch時には均等でも実行中に大きなload imbalanceやmemory fragmentationが生じる。

LlumnixはこれをOSのprocess schedulingに近い問題として扱い、**実行中requestを別model instanceへ移動できるようにする**。同じmigration機構をload balancing、GPU memoryのdefragmentation、high-priority requestのisolation、auto-scaling時のinstance drainに共通利用する。

単純にKV cache全体を止めてコピーすると長contextほどstallが増えるため、LlumnixはKV cacheが過去部分を書き換えないappend-only dataであることを利用し、decodeを続けながら大部分を段階的に転送する。

## 問題設定

LLM servingではrequestごとにinput / output lengthが大きく異なり、output lengthは生成終了まで分からない。このためinstanceごとの実行時間とKV memory需要が動的に変化する。

その結果、

- あるinstanceだけが混雑してqueue / preemptionが増える
- free memoryが複数instanceへ細かく分散し、大きなpromptを受け入れられない
- latency-sensitive requestとbackground requestを十分に分離できない
- auto-scalingでinstanceを減らす際、残存requestの終了待ちが長い

といった問題が起きる。

Llumnixはone-shot dispatchだけでこれらを予測するのではなく、**状況が判明した後にrequest placementを修正する**方針を採る。

## 手法

### 1. Append-only KVを利用したlive migration

migration開始後もsource instanceはdecodeを続けながら、すでに生成済みで以後変化しないKV blockをdestinationへ送る。

最初のcopy中に新しいKVが追加されたら、その差分を次stageでコピーする。転送の方がdecode計算より速ければ未転送差分は急速に小さくなり、最後にrequestをbatchから一時停止して残った1 iteration程度のKVだけを送ってdestinationで再開する。

このため総転送量はsequence lengthに比例するが、**user-visible downtimeはほぼ最後の差分copy時間だけ**になり、sequence lengthへの依存を小さくできる。

### 2. Small KV blockをまとめて転送する

vLLMのPagedAttentionではKVが多数の小blockへ分散している。そのまま1 blockずつ送るとmessage overheadが大きい。

Llumnixはmigration時に複数blockを連続CPU bufferへまとめ、Gloo Send/Recvで一括転送する。GPU↔CPU copyは別CUDA streamで行い、decode kernelを止めないようにする。

### 3. Global scheduler + instance-local llumlet

中央schedulerがすべての細かいmigrationを同期的に管理するとscaleしにくいため、global schedulerはinstanceの状態を監視して大まかなsource / destinationを決め、各instanceの`llumlet`がrequest選択とmigration handshakeを実行する。

これによりglobal decisionとdata movementを分離し、多数instanceで継続的にreschedulingできる。

### 4. Virtual usage / freenessで異なる目的を統一する

Llumnixはrequestの実memory usageだけでなく、目的に応じて補正した**virtual usage**を定義する。

instanceの`freeness`は、おおむね「virtual usageを差し引いたfree memoryをbatch sizeで割った値」とし、値が高いinstanceほどrequestを受け入れやすいとみなす。

- load balancingでは実memory loadを反映
- high-priority requestには追加headroomを与え、混雑しにくくする
- queueがあるinstanceは仮想的により混雑しているとみなす
- termination予定instanceはrequestを外へ追い出す

といったrulesを同じmetricへ落とし込み、dispatch / migration / auto-scalingを共通化する。

### 5. Migrationをdefragmentationにも使う

cluster全体では十分free memoryがあっても、それが複数instanceへ分散していれば長いpromptを受け入れられない。

Llumnixは一部のrunning requestを別instanceへ集約して、特定instanceに大きな連続free capacityを作る。単純なload balancingだけではむしろfree memoryが均等に散らばるため、このdefragmentationは別の重要な目的になる。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Cluster | Alibaba Cloud 4 VMs / 16 GPUs |
| GPU | NVIDIA A10 24GB、各VM 4枚 |
| Interconnect | PCIe 4.0、VM間64Gbps network |
| Models | LLaMA-7B、LLaMA-30B |
| Precision | FP16 |
| Backend | vLLM |
| Workloads | ShareGPT、BurstGPT、power-law synthetic traces |
| Baselines | Round-robin、INFaaS++ |

LLaMA-7Bは1 GPU / instance、LLaMA-30Bは1 machineの4 GPUをtensor parallelismで使う。大規模scheduler scalabilityの64-instance評価だけは、A10実測profileに基づくsleep modelでGPU executionを代替する。

### Migration overhead

LLaMA-7B / 30Bでsequence lengthを256〜8Kへ伸ばしても、live migrationのdowntimeは概ね**20〜30msでほぼ一定**だった。

8K LLaMA-30BをKV再計算で移す場合は約3.5秒かかり、migration downtimeの最大111倍。migration中の通常decode stepへの性能差は最大約1%だった。

### Tail latency / fragmentation

16 LLaMA-7B instanceのreal / synthetic workloadで、INFaaS++に対して

- P99 prefill latency: 最大約15×改善
- mean prefill latency: 最大7.7×改善
- P99 decode latency: 最大2×改善

を報告する。

あるcaseではcluster memory fragmentationの平均比率を7.9%から0.7%へ下げ、約92%削減した。

### Priority / auto-scaling

high-priority requestはnormal requestの性能をほぼ保ったまま最大**1.5×低latency化**した。

さらに同程度のP99 prefill latency（約5秒）を維持するauto-scaling比較では、INFaaS++より平均instance数を減らし**約36% cost saving**を報告している。

## 既存研究との差

### One-shot load balancingとの違い

Round-robinやINFaaS型schedulerはrequest到着時にinstanceを選ぶが、その後output lengthやmemory demandが予想外に増えてもplacementを修正できない。

Llumnixは**execution途中でもrequestを動かせる**ため、dispatch後に判明したimbalanceやfragmentationを直接修正できる。

### Sarathi-Serveとの違い

Sarathi-Serveは1 instance内でprefill / decodeをchunk schedulingし、generation stallを抑える。Llumnixは複数model instance間の配置を扱い、instance内schedulerの上に追加できるcluster-level layerである。

### DistServe / Splitwiseとの違い

DistServe / Splitwiseはprefill / decode roleごとにresource poolを設計する。Llumnixはphase separationを主題とせず、**同じmodelをserveする複数instance間でrunning request自体を移動する**ことでruntime imbalanceへ対応する。

## 限界

- 主評価はA10 + LLaMA-7B / 30B + vLLMで、Hopper / Blackwellや現代的GQA / MLA modelではmigration bandwidthとKV sizeの比率が変わる。
- current implementationはGlooを使うためGPU→CPU→network→CPU→GPU copyを含み、より高速なGPU-direct networkでは設計点が変わり得る。
- migration destinationに十分なmemory headroomが必要で、cluster全体が極端に飽和している状況では移動先を作れない。
- 64-instance scalability evaluationは実GPU clusterではなく、A10 profileで校正したexecution modelを使う。
- failure時、source instance自体が失われたrunning requestはabortされるため、request stateのfault-tolerant replicationを提供する仕組みではない。

## 一般的な実装上の含意

LLM servingではrequest routingを「到着時に一度決めたら固定」と考える必要はない。KV cacheを低downtimeで移動できれば、**runtimeで判明したoutput length・memory growth・priority変化へplacementを追従させる**余地が生まれる。

特にKV cacheはappend-onlyなので、VM live migrationのようなdirty-page trackingを使わず、過去部分をdecodeと並行copyして最後の小差分だけ停止転送する設計が可能である。
