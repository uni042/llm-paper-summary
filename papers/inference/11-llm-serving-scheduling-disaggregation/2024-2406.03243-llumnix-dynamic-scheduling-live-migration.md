# Llumnix: Dynamic Scheduling for Large Language Model Serving

> 実行中要求のKVキャッシュを別モデル実行単位へ段階的に移し、GPU間の混雑差・メモリ不足・優先度変更・実行単位削減が起きた後でも要求配置を修正できる複数実行単位の推論提供スケジューラ。

## 概要

一般的な複数実行単位の推論提供では要求を最初に1つの実行単位へ振り分けした後、その要求は完了まで同じ実行単位に固定される。しかしLLM要求は出力長さとKVメモリ消費量を事前に正確に予測できないため、振り分け時には均等でも実行中に大きな負荷の偏りやメモリ不足が生じる。

Llumnixはこの問題に対し、**生成途中の要求を、過去KVを保ったまま別モデル実行単位へ移動できるようにする**。これにより、最初の配置が後から悪くなっても実行環境中に修正できる。

同じ要求移動機構を、

- 混雑GPUから空いているGPUへの負荷分散
- 大きなプロンプトを受け入れるためのメモリ集約
- 高優先度要求用の空き確保
- 自動伸縮で停止したい実行単位からの要求退避

へ共通利用する。

単純にKVキャッシュ全体を止めてコピーすると長文脈ほど停止時間が増えるため、LlumnixはKVキャッシュの過去部分がデコード中に書き換わらないことを利用し、**生成を続けながら古いKVを先に転送し、最後の小さい差分だけ要求を止めて送る**。

## 問題設定

LLM推論提供では要求ごとに入力 / 出力長さが大きく異なり、出力長さは生成終了まで分からない。このため実行単位ごとの実行時間とKVメモリ需要が動的に変化する。

その結果、

- ある実行単位だけが混雑して待ち行列 / 先取りが増える
- クラスタ全体には空きメモリがあるのに、各実行単位へ細かく分散して大きなプロンプトを入れられない
- 遅延重視の要求と背景要求を十分に分離できない
- 自動伸縮で実行単位を減らす際、残存要求の終了待ちが長い

といった問題が起きる。

Llumnixは一度きりの振り分けだけでこれらを予測するのではなく、**状況が判明した後に要求配置を修正する**方針を採る。

## 手法

### 1. 生成を続けながら過去KVを先に複製する

KVキャッシュは新しいトークン分が末尾へ追加される一方、すでに生成済みの過去KVは基本的に変化しない。

Llumnixは移行開始後も移行元実行単位でデコードを続けながら、**もう変化しない古いKVブロックを移行先へ先に送る**。

最初の複製中に新しいKVが追加されたら、その差分を次回複製する。転送の方がKV追加速度より速ければ未転送差分は徐々に小さくなる。

最後に要求を短時間だけ一時停止し、残った最新差分を送り、移行先側でデコードを再開する。

論文の実行中移行は、この**要求を最初からやり直さず、生成途中状態を別実行単位へ引き継ぐ処理**を指す。

総転送量は文脈長に比例するが、利用者に見える停止時間は最後の小差分複製だけなので、長文脈でも停止時間を小さく保ちやすい。

### 2. 小さいKVブロックをまとめて送る

vLLMのPagedAttentionではKVが多数の小ブロックへ分散している。そのまま1ブロックずつネットワーク送信するとメッセージの余分な処理が大きい。

Llumnixは移行時に複数ブロックを一時的に大きなCPUバッファへまとめて一括転送する。GPU↔CPU複製は別CUDAストリームで行い、デコードカーネルとできるだけ重ねる。

### 3. 中央スケジューラは大まかな移動先だけ決め、各実行単位が実際の移行を進める

中央スケジューラが全要求の細かい転送ステップまで同期的に管理すると拡張しにくい。

そこで全体スケジューラは実行単位の混雑・メモリ状態を見て、**どこからどこへ要求を動かすべきか**を決める。

各実行単位内の小制御装置が、実際にどの要求を選ぶか、転送開始・完了の同期処理を担当する。論文ではこの実行単位内のローカル制御装置を`llumlet`と呼ぶ。

つまり全体の判断とデータ移動を分離し、多数実行単位で継続的に再スケジューリングできる構成にする。

### 4. 異なる目的を「この実行単位にどれだけ余裕があるか」という共通スコアへ変換する

Llumnixは実際のメモリ使用量だけでなく、優先度や待ち行列状態などを加味した仮想的な使用量を作る。

例えば、

- 高優先度要求を守りたい実行単位は、実際より空きが少ないよう扱って余裕を残す
- 待ち行列が長い実行単位は、実際のメモリ以上に混雑しているとみなす
- 停止予定実行単位は、新しい要求を受けず既存要求を外へ出す方向にスコアを調整する

というようにする。

論文の仮想使用量 / 空き状況は、この**異なる運用目的を「要求を受け入れやすい実行単位かどうか」という共通スコアへ変換する**仕組みである。

### 5. 空きメモリを特定の実行単位へ集めるためにも要求を移す

クラスタ全体では十分な空きメモリがあっても、それが複数実行単位へ分散していれば長いプロンプトを受け入れられない。

Llumnixは一部の実行中の要求を別実行単位へ集約し、特定実行単位を大きく空ける。

論文でいうメモリ断片化解消は、1 GPU内の物理アドレスを並べ直すというより、**クラスタ内に散らばった空き処理能力を要求移行で特定実行単位へ集める**意味が中心である。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Cluster | Alibaba Cloud 4 VMs / 16 GPUs |
| GPU | NVIDIA A10 24GB、各VM 4枚 |
| 接続網 | PCIe 4.0、VM間64Gbpsネットワーク |
| Models | LLaMA-7B、LLaMA-30B |
| Precision | FP16 |
| Backend | vLLM |
| Workloads | ShareGPT、BurstGPT、べき乗則の合成トレース |
| Baselines | Round-robin、INFaaS++ |

LLaMA-7Bは1 GPU / 実行単位、LLaMA-30Bは1マシンの4 GPUをテンソル並列化で使う。大規模スケジューラ拡張性の64実行単位評価だけは、A10実測性能測定に基づく実行モデルでGPU実行を代替する。

### 移行オーバーヘッド

LLaMA-7B / 30Bで系列長さを256〜8Kへ伸ばしても、実行中移行の停止時間は概ね**20〜30msでほぼ一定**だった。

8K LLaMA-30BをKV再計算で移す場合は約3.5秒かかり、移行停止時間の最大111倍。移行中の通常デコードステップへの性能差は最大約1%だった。

### 末尾遅延 / メモリ集約

16 LLaMA-7B実行単位の実測 / 合成ワークロードで、INFaaS++に対して

- P99プリフィル遅延: 最大約15×改善
- 平均プリフィル遅延: 最大7.7×改善
- P99デコード遅延: 最大2×改善

を報告する。

ある事例では、各実行単位へ散らばって長プロンプトに使えない空きメモリの割合を7.9%から0.7%へ下げ、約92%削減した。

### 優先度 / 自動伸縮

高優先度要求は通常要求の性能をほぼ保ったまま最大**1.5×低遅延化**した。

さらに同程度のP99プリフィル遅延（約5秒）を維持する自動伸縮比較では、INFaaS++より平均実行単位数を減らし**約36%のコスト削減**を報告している。

## 既存研究との差

### 一度きりの負荷分散との違い

ラウンドロビンやINFaaS型スケジューラは要求到着時に実行単位を選ぶが、その後出力長さやメモリ需要が予想外に増えても配置を修正できない。

Llumnixは**実行途中でも要求を動かせる**ため、振り分け後に判明した偏りやメモリ不足を直接修正できる。

### Sarathi-Serveとの違い

Sarathi-Serveは1実行単位内でプリフィル／デコードを分割片スケジューリングし、生成停止を抑える。Llumnixは複数モデル実行単位間の配置を扱い、実行単位内スケジューラの上に追加できるクラスタ水準層である。

### DistServe / Splitwiseとの違い

DistServe / Splitwiseはプリフィル／デコードの役割ごとに資源プールを設計する。Llumnixは処理段階の分離を主題とせず、**同じモデルを提供する複数実行単位間で実行中の要求自体を移動する**ことで実行環境偏りへ対応する。

## 限界

- 主評価はA10 + LLaMA-7B / 30B + vLLMで、Hopper / Blackwellや現代的GQA / MLAモデルでは移行帯域とKVサイズの比率が変わる。
- 現在の実装はGlooを使うためGPU→CPU→ネットワーク→CPU→GPU複製を含み、より高速なGPU-直接ネットワークでは設計点が変わり得る。
- 移行先に十分なメモリ余裕が必要で、クラスタ全体が極端に飽和している状況では移動先を作れない。
- 64実行単位拡張性評価は実GPUクラスタではなく、A10性能測定で校正した実行モデルを使う。
- 障害時、移行元実行単位自体が失われた実行中の要求は中断されるため、要求状態の障害耐性付き複製を提供する仕組みではない。

## 一般的な実装上の含意

LLM推論提供では要求ルーティングを「到着時に一度決めたら固定」と考える必要はない。KVキャッシュを低停止時間で移動できれば、**実行環境で判明した出力長さ・メモリ増加・優先度変化へ配置を追従させる**余地が生まれる。

特にKVキャッシュは末尾への追記だけなので、過去部分をデコードと並行複製して最後の小差分だけ停止転送する設計が可能である。
