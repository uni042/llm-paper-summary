# Llumnix: Dynamic Scheduling for Large Language Model Serving

> 実行中requestのKV cacheを別model instanceへ段階的に移し、GPU間の混雑差・memory不足・priority変更・instance削減が起きた後でもrequest配置を修正できるmulti-instance serving scheduler。

## 概要

一般的なmulti-instance servingではrequestを最初に1つのinstanceへdispatchした後、そのrequestは完了まで同じinstanceに固定される。しかしLLM requestはoutput lengthとKV memory消費量を事前に正確に予測できないため、dispatch時には均等でも実行中に大きなload imbalanceやmemory不足が生じる。

Llumnixはこの問題に対し、**生成途中のrequestを、過去KVを保ったまま別model instanceへ移動できるようにする**。これにより、最初の配置が後から悪くなってもruntime中に修正できる。

同じrequest移動機構を、

- 混雑GPUから空いているGPUへのload balancing
- 大きなpromptを受け入れるためのmemory集約
- high-priority request用の空き確保
- auto-scalingで停止したいinstanceからのrequest退避

へ共通利用する。

単純にKV cache全体を止めてコピーすると長contextほど停止時間が増えるため、LlumnixはKV cacheの過去部分がdecode中に書き換わらないことを利用し、**生成を続けながら古いKVを先に転送し、最後の小さい差分だけrequestを止めて送る**。

## 問題設定

LLM servingではrequestごとにinput / output lengthが大きく異なり、output lengthは生成終了まで分からない。このためinstanceごとの実行時間とKV memory需要が動的に変化する。

その結果、

- あるinstanceだけが混雑してqueue / preemptionが増える
- cluster全体には空きmemoryがあるのに、各instanceへ細かく分散して大きなpromptを入れられない
- latency-sensitive requestとbackground requestを十分に分離できない
- auto-scalingでinstanceを減らす際、残存requestの終了待ちが長い

といった問題が起きる。

Llumnixはone-shot dispatchだけでこれらを予測するのではなく、**状況が判明した後にrequest placementを修正する**方針を採る。

## 手法

### 1. 生成を続けながら過去KVを先にcopyする

KV cacheは新しいtoken分が末尾へ追加される一方、すでに生成済みの過去KVは基本的に変化しない。

Llumnixはmigration開始後もsource instanceでdecodeを続けながら、**もう変化しない古いKV blockをdestinationへ先に送る**。

最初のcopy中に新しいKVが追加されたら、その差分を次回copyする。転送の方がKV追加速度より速ければ未転送差分は徐々に小さくなる。

最後にrequestを短時間だけ一時停止し、残った最新差分を送り、destination側でdecodeを再開する。

論文のlive migrationは、この**requestを最初からやり直さず、生成途中stateを別instanceへ引き継ぐ処理**を指す。

総転送量はcontext長に比例するが、user-visibleな停止時間は最後の小差分copyだけなので、長contextでもdowntimeを小さく保ちやすい。

### 2. 小さいKV blockをまとめて送る

vLLMのPagedAttentionではKVが多数の小blockへ分散している。そのまま1 blockずつnetwork送信するとmessage overheadが大きい。

Llumnixはmigration時に複数blockを一時的に大きなCPU bufferへまとめて一括転送する。GPU↔CPU copyは別CUDA streamで行い、decode kernelとできるだけ重ねる。

### 3. 中央schedulerは大まかな移動先だけ決め、各instanceが実際のmigrationを進める

中央schedulerが全requestの細かい転送stepまで同期的に管理するとscaleしにくい。

そこでglobal schedulerはinstanceの混雑・memory状態を見て、**どこからどこへrequestを動かすべきか**を決める。

各instance内の小controllerが、実際にどのrequestを選ぶか、転送開始・完了のhandshakeを担当する。論文ではこのinstance-local controllerを`llumlet`と呼ぶ。

つまりglobal decisionとdata movementを分離し、多数instanceで継続的にreschedulingできる構成にする。

### 4. 異なる目的を「このinstanceにどれだけ余裕があるか」という共通scoreへ変換する

Llumnixは実際のmemory使用量だけでなく、priorityやqueue状態などを加味した仮想的な使用量を作る。

例えば、

- high-priority requestを守りたいinstanceは、実際より空きが少ないよう扱って余裕を残す
- queueが長いinstanceは、実際のmemory以上に混雑しているとみなす
- 停止予定instanceは、新しいrequestを受けず既存requestを外へ出す方向にscoreを調整する

というようにする。

論文のvirtual usage / freenessは、この**異なる運用目的を「requestを受け入れやすいinstanceかどうか」という共通scoreへ変換する**仕組みである。

### 5. 空きmemoryを特定instanceへ集めるためにもrequestを移す

cluster全体では十分free memoryがあっても、それが複数instanceへ分散していれば長いpromptを受け入れられない。

Llumnixは一部のrunning requestを別instanceへ集約し、特定instanceを大きく空ける。

論文でいうmemory defragmentationは、1 GPU内の物理addressを並べ直すというより、**cluster内に散らばった空きcapacityをrequest migrationで特定instanceへ集める**意味が中心である。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Cluster | Alibaba Cloud 4 VMs / 16 GPUs |
| GPU | NVIDIA A10 24GB、各VM 4枚 |
| Interconnect | PCIe 4.0、VM間64Gbps network |
| Models | LLaMA-7B、LLaMA-30B |
| Precision | FP16 |
| Backend | vLLM |
| Workloads | ShareGPT、BurstGPT、power-law synthetic traces |
| Baselines | Round-robin、INFaaS++ |

LLaMA-7Bは1 GPU / instance、LLaMA-30Bは1 machineの4 GPUをtensor parallelismで使う。大規模scheduler scalabilityの64-instance評価だけは、A10実測profileに基づくexecution modelでGPU executionを代替する。

### Migration overhead

LLaMA-7B / 30Bでsequence lengthを256〜8Kへ伸ばしても、live migrationのdowntimeは概ね**20〜30msでほぼ一定**だった。

8K LLaMA-30BをKV再計算で移す場合は約3.5秒かかり、migration downtimeの最大111倍。migration中の通常decode stepへの性能差は最大約1%だった。

### Tail latency / memory集約

16 LLaMA-7B instanceのreal / synthetic workloadで、INFaaS++に対して

- P99 prefill latency: 最大約15×改善
- mean prefill latency: 最大7.7×改善
- P99 decode latency: 最大2×改善

を報告する。

あるcaseでは、各instanceへ散らばって長promptに使えないfree memoryの割合を7.9%から0.7%へ下げ、約92%削減した。

### Priority / auto-scaling

high-priority requestはnormal requestの性能をほぼ保ったまま最大**1.5×低latency化**した。

さらに同程度のP99 prefill latency（約5秒）を維持するauto-scaling比較では、INFaaS++より平均instance数を減らし**約36% cost saving**を報告している。

## 既存研究との差

### One-shot load balancingとの違い

Round-robinやINFaaS型schedulerはrequest到着時にinstanceを選ぶが、その後output lengthやmemory demandが予想外に増えてもplacementを修正できない。

Llumnixは**execution途中でもrequestを動かせる**ため、dispatch後に判明したimbalanceやmemory不足を直接修正できる。

### Sarathi-Serveとの違い

Sarathi-Serveは1 instance内でprefill / decodeをchunk schedulingし、generation stallを抑える。Llumnixは複数model instance間の配置を扱い、instance内schedulerの上に追加できるcluster-level layerである。

### DistServe / Splitwiseとの違い

DistServe / Splitwiseはprefill / decode roleごとにresource poolを設計する。Llumnixはphase separationを主題とせず、**同じmodelをserveする複数instance間でrunning request自体を移動する**ことでruntime imbalanceへ対応する。

## 限界

- 主評価はA10 + LLaMA-7B / 30B + vLLMで、Hopper / Blackwellや現代的GQA / MLA modelではmigration bandwidthとKV sizeの比率が変わる。
- current implementationはGlooを使うためGPU→CPU→network→CPU→GPU copyを含み、より高速なGPU-direct networkでは設計点が変わり得る。
- migration destinationに十分なmemory headroomが必要で、cluster全体が極端に飽和している状況では移動先を作れない。
- 64-instance scalability evaluationは実GPU clusterではなく、A10 profileで校正したexecution modelを使う。
- failure時、source instance自体が失われたrunning requestはabortされるため、request stateのfault-tolerant replicationを提供する仕組みではない。

## 一般的な実装上の含意

LLM servingではrequest routingを「到着時に一度決めたら固定」と考える必要はない。KV cacheを低downtimeで移動できれば、**runtimeで判明したoutput length・memory growth・priority変化へplacementを追従させる**余地が生まれる。

特にKV cacheはappend-onlyなので、過去部分をdecodeと並行copyして最後の小差分だけ停止転送する設計が可能である。
