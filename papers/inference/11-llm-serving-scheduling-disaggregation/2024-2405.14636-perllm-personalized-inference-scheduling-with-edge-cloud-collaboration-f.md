# PerLLM：エッジとクラウドを協調させる個別要求向けLLM推論スケジューリング

## 概要

LLMの推論要求をすべてクラウドへ送ると、集中するネットワーク転送とGPU待ち行列が遅延・エネルギーを増やす。一方、ユーザーに近いエッジ装置で小型モデルを動かせば転送を減らせるが、複雑な要求や大量の同時要求を処理する計算能力は不足しやすい。サービスごとに処理期限が異なり、帯域や空き計算資源も時間とともに変わるため、単純に「小型モデルはエッジ、大型モデルはクラウド」と固定するだけでは非効率になる。

PerLLMは、要求をエッジとクラウドのどのサーバーへ割り当てるかを、処理期限・利用可能帯域・計算能力の制約の下で決める。目的関数は送信、推論、待機の三つのエネルギー費用の重み付き合計であり、要求ごとの応答期限を満たすことを制約として扱う。組合せ多腕バンディット（combinatorial multi-armed bandit; CMAB）に定式化し、制約充足機構を組み込んだ上側信頼限界法（constraint satisfaction upper confidence bound; CS-UCB）で割当てを適応的に選ぶ。

著者はIntel Xeon Silver 4214Rのエッジ5台とNVIDIA A100 40GBのクラウド1台を用い、Yi-6B、LLaMA2-7B、LLaMA3-8B、Yi-9B、論文中でLLaMA2-33Bと呼ぶモデルを配置した。10,000要求・期限2～6秒の実験で、PerLLMはモデル別の期限達成率97～99%を報告する。比較方式に対する平均トークン処理量は2.2倍、2.1倍、1.6倍、エネルギーは50%超削減とされる。ただしモデル品質とメモリの最適化は対象外で、評価環境の一般化には制限がある。

## 問題設定

サービス集合を `G={g_1,...,g_M}`、サーバー集合を `U={u_1,...,u_N}` とする。各要求はエッジまたはクラウドの一台へ割り当てられ、送信時間と推論時間を合計した処理時間がその要求の期限以内でなければならない。サーバーごとに同時に受け入れられる計算要求量と帯域要求量に上限がある。負荷やネットワーク状況が変われば、同じモデルを実行する場合でも適切な配置先が変わる。

目的関数は `E_total = Σ_t (ω_trans E_trans,t + ω_infer E_infer,t + ω_idle E_idle,t)` を最小化することである。`E_trans` は要求・応答の通信、`E_infer` はモデル実行、`E_idle` はサーバーの待機電力に対応する。重み `ω` により各費用の相対的重要度を調整する。制約は四つあり、要求の処理時間が期限以下であること、サーバーの計算負荷が上限以下であること、送信帯域が上限以下であること、各要求を一つのサーバーにだけ割り当てることである。

この最適化は「どのサーバーが速いか」を一度測って固定する問題ではない。クラウドは高い計算能力を持つが、要求集中で通信が混雑する。エッジは近距離通信で有利でも、CPUでのモデル実行が遅い場合がある。処理期限の厳しい要求を近くで処理するか、複雑な要求をクラウドへ送るかを、現在の負荷と帯域を考慮して選ぶ必要がある。

## 手法

### 1. サービスとサーバーの組合せを多腕バンディットの行動とする

PerLLMは、各要求をどのサーバーへ割り当てるかという選択を一つの行動ベクトル `a=(a_1,...,a_M)` で表す。`a_i` は要求 `i` の処理先サーバーの番号である。すべての要求の割当てを一括して考えたものをスーパーアーム（super arm）と呼び、複数の割当て候補を試しながらエネルギーと期限達成の報酬を学習する。

環境状態は各サーバーの計算能力 `c_j` と利用可能帯域 `b_j` の組で表す。帯域が下がるとクラウドへの転送費用が上がり、エッジが混雑するとエッジの処理遅延が増える。固定の推論配置規則ではなく、報酬と状態の変化に応じて候補の優先順位を更新することで、要求の多様性と資源の変動に対応する。

ただし割当て候補の総数は要求数とサーバー数に対して組合せ的に増える。論文は候補行動の制約判定と上側信頼限界の計算を記述しているが、全候補の列挙を実用規模でどのように縮約するか、候補生成が高並列環境でどの程度の計算負担になるかは、公開情報から十分には分離できない。

### 2. 制約充足を報酬と候補選択に組み込む

著者は、処理時間・計算資源・帯域の各制約について、上限から実際の需要を引いた余裕を正規化し、その最小値を制約充足指標 `f(y)` として扱う。すべての制約を満たす場合は `f(y)≥0`、少なくとも一つを破る場合は負となる。これにより、エネルギー費用が低くても期限や資源上限を破る配置を低く評価できる。

報酬はエネルギー費用の負値に `λ f(y)` を加える形で表す。係数 `λ` は制約違反の重みを調整する。論文のアルゴリズムは制約を満たす候補を先に選別し、その中で上側信頼限界が最大の行動を選ぶと説明する。負荷変動によって以前は実行可能だった配置が実行不能になる場合も、制約の再評価を通じて別候補へ切り替える。

処理期限を単なる平均遅延の改善目標ではなく、要求単位で満たすべき条件にした点が個別サービス向け設計の中心である。ただし、物理的にどのサーバーでも期限を満たせない要求は、スケジューラの選択だけでは救えない。原著でも全要求の100%達成は示されず、実験では97～99%にとどまる。

### 3. 上側信頼限界（UCB）による探索と活用

各行動 `a` について、過去に観測した平均報酬 `R̄(a)` と選択回数 `L(a,t)` を保持し、`UCB(a,t)=R̄(a)+δ sqrt(ln(t)/L(a,t))+θP(t)` に類する値を計算する。第二項は試行回数の少ない行動へ探索の余地を与え、`δ` は探索と活用のバランスを調整する。`P(t)` は制約違反に伴う罰則を表す。制約を満たす行動の中からUCBの大きい候補を実行し、観測したエネルギー・遅延に応じて報酬推定を更新する。

著者は累積後悔（regret）の上界も議論し、制約違反の重みを含む形の評価式を示す。ただし論文の式には候補数や罰則項が含まれ、条件を固定せずに単純な「後悔が必ず対数増加する」と読むことは適切でない。実装の候補集合、資源変動、報酬の確率的仮定によって理論と実運用の関係は変わる。

一回の意思決定では候補ごとのUCB計算と制約判定が必要で、著者の計算量分析は行動数 `A` と制約検査費用 `f(A)` を使い、概ね `O(A f(A)+A)` と記述する。行動数そのものが大きい場合には、推論実行以外のスケジューリング費用が無視できない可能性がある。提案はLLMの重み、KVキャッシュ、注意計算そのものを変更する手法ではなく、配置と資源配分の最適化である。

## 評価条件

| 項目 | 一次論文の設定 |
|---|---|
| エッジ | Intel Xeon Silver 4214R CPUを使う5台 |
| クラウド | NVIDIA A100 40GBを使う1台 |
| モデル | エッジにYi-6B、LLaMA2-7B、LLaMA3-8B、Yi-9B。クラウドに論文表記のLLaMA2-33B |
| ネットワーク | エッジ100 Mbps、クラウド300 Mbps。変動条件では帯域を最大20%変動 |
| 要求数 | 10,000件の高並列推論要求 |
| 個別期限 | 各要求について2～6秒の範囲から選択 |
| 生成設定 | Hugging Face Transformers、温度0.8、top-k 200 |
| 比較 | FineInfer（クラウド専用）、AGOD（エッジ専用）、RewardlessGuidance（エッジ・クラウド協調） |
| 指標 | 期限達成率、送信＋推論の平均処理時間、トークン/秒、通信・推論・待機を含むエネルギー |

エッジがCPU、クラウドがA100という非対称構成であること、ネットワーク帯域が事前設定された値であることに注意する。帯域変動は20%の範囲で模擬したもので、実インターネットの長期的な障害や突発的な高損失状態を再現したとは限らない。また論文が用いる「LLaMA2-33B」は公式に一般的なLlama 2のモデル名称と一致しないため、正確な重み・構成・再現条件の確認が必要である。

## 評価結果

### 1. 個別要求の期限達成率

| エッジモデル | FineInfer | AGOD | RewardlessGuidance | PerLLM |
|---|---:|---:|---:|---:|
| Yi-6B | 58% | 67% | 74% | **98%** |
| LLaMA2-7B | 58% | 69% | 77% | **99%** |
| LLaMA3-8B | 58% | 66% | 74% | **98%** |
| Yi-9B | 58% | 66% | 71% | **97%** |

各要求に設定された2～6秒の期限内に、通信と推論を含む処理を終えた割合である。PerLLMは97～99%で、比較方式の58～77%より高い。ただし100%ではなく、負荷が高い要求やモデル実行時間の予測が難しい場合には違反が残る。実験は10,000件の要求で評価しているが、期限達成率を単一要求の平均応答時間短縮倍率へ読み替えることはできない。

### 2. トークン処理量と平均処理時間

| 比較対象 | PerLLMの平均スループット倍率 | 比較方式の配置 |
|---|---:|---|
| FineInfer | **2.2倍** | クラウド専用 |
| AGOD | **2.1倍** | エッジ専用 |
| RewardlessGuidance | **1.6倍** | エッジ・クラウド協調 |

論文のスループットは単位時間に処理したトークン数であり、モデル自体の1トークン当たりの演算速度とは異なる。クラウドだけでは送信待ち行列が、エッジだけでは計算能力が律速となる。PerLLMは両者を使い分けることで、待ち時間を減らしてシステム全体の処理量を改善する。著者は帯域が20%変動する場合にも平均処理時間の改善が保たれると報告するが、図から各モデルの厳密な秒数を機械的に読み取って倍率へ変換することは避ける。

### 3. エネルギー費用と内訳

PerLLMは比較方式に対して50%超のエネルギー費用削減を報告する。エネルギーの内訳は送信、推論、待機の三種類である。クラウド専用方式では要求の集中による通信と待機が増え、エッジ専用方式では計算の遅さが処理時間を増やす。PerLLMは各要求の期限と現在の資源条件に合わせて配置するため、不要な通信や待機を抑えられる。

ただし、このエネルギー比較は特定のCPU・GPU・ネットワーク構成と論文の電力モデルに依存する。異なる地域の通信経路、GPUの稼働率、CXLやNICの電力、冷却設備を含む実データセンター全体の電力を測ったものではない。トークン当たりエネルギーと要求全体のエネルギーは別指標であり、モデルの回答品質の違いを含めた効率比較でもない。

### 4. どの構成要素が効いているか

提案は期限・帯域・計算能力の制約を同時に評価するため、単純なクラウド専用やエッジ専用の方式より高い期限達成率を得る。既存のエッジ・クラウド協調方式RewardlessGuidanceに対しても1.6倍の平均処理量を報告するため、単にエッジを使ったことだけでは説明できない。ただし原著には、制約充足を外したUCBのみ、UCBを外した制約充足のみ、探索係数や罰則を変えた詳細な要因分離が十分には示されていない。改善のうちどれだけが各機構に由来するかは未確定である。

## 既存研究との差

FineInferはクラウド上の遅延バッチ処理を中心とするため、通信が律速の場面で不利になる。AGODはエッジのオフロードを扱うが、計算資源の不足に直面しやすい。RewardlessGuidanceはエッジ・クラウド協調を扱うが、個別期限と複数資源制約を同時に扱うPerLLMのような明示的な制約充足付きUCBを中心に据えていない。

PerLLMは、単なるモデル配置先の固定選択ではなく、要求ごとの期限を満たす候補だけを選び、その候補集合の中で通信・推論・待機エネルギーを低くする学習的スケジューリングを行う。LLM内部の注意機構やモデル重みを変更せずにサービス層で性能を改善するため、圧縮・量子化・KVキャッシュ最適化とは別の最適化階層に位置付けられる。

## 限界と再現上の注意

第一に、期限達成率は97～99%であり、全ての要求の厳格な保証ではない。処理時間を実行前に正確に予測できない要求や、全サーバーが混雑している場合には期限違反が残る。2～6秒の期限設定と100/300 Mbpsの帯域条件が変われば、最適配置と達成率も変わる。

第二に、論文自身がモデルの回答精度とメモリ最適化を対象外と明記している。クラウドの大型モデルとエッジの小型モデルでは、同じ入力に対する回答品質が一致する保証はない。処理時間とエネルギーだけでエッジへの割当てを評価すると、難しい要求を小型モデルへ送って品質が落ちる可能性を見落とす。品質制約を加えた比較が必要である。

第三に、実験のエッジ5台は同じCPUを用い、異なるGPU/NPUを持つ不均一なエッジ群を評価していない。ネットワーク変動も最大20%の模擬であり、実環境の突然の断線や高遅延を検証していない。通信と推論を別々に測った上での実機再現が必要である。

第四に、論文中の「LLaMA2-33B」は一般的な公式Llama 2の公開モデル名と整合しない。さらにCPUエッジ上の数十億パラメータモデルで2～6秒の期限達成率が高いことについて、入力長・出力長・量子化状態・実行プロセスなど再現に必要な条件の確認が重要である。これらを根拠なしに補って実験結果を一般化すべきではない。

第五に、組合せ多腕バンディットの行動空間は要求数とサーバー数で急増する。論文は候補行動に対する制約判定とUCB計算を示すが、超大規模な要求集合での候補削減やスケジューラ自身のCPU費用は十分に独立測定されていない。追試では割当て計算時間、要求待ち時間、TTFT、TPOT、品質、トークン当たりエネルギーを分けて測定するのが適切である。
