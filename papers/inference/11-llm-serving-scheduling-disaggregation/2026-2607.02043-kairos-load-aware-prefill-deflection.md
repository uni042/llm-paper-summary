# Towards Load-Aware Prefill Deflection for Disaggregated LLM Serving

> 分離型LLM servingでprefill queueとKV転送がTTFTを支配する時、decode nodeの余剰computeへprefillをTBT-safeな可変chunkでdeflectし、KVをdecode側で直接構築してtail TTFTを削減する。

## 問題

prefill/decode分離では、負荷が偏るとprefill nodeにqueueが生じる一方、decode nodeのcomputeには余裕が残る。通常経路ではprefill後にKV cacheをdecode nodeへ転送するため、prefill queueingとKV転送がtime-to-first-token（TTFT）のtailを押し上げる。

Kairosはこの不均衡を、既存requestのdecodeを妨げない範囲でdecode nodeへprefillを逃がすことで解消する。deflectしたrequestはdecode node上でKVを直接構築するため、別nodeからのKV転送も不要になる。

## 新規性

単にdecode側でchunked prefillを実行するのではなく、requestごとにprefill側と候補decode側のTTFTを推定し、既存decode requestのtoken-between-token（TBT）SLOを守れる**可変chunk schedule**を作ったうえでdeflection可否を決める。

後半のprefill chunkほど既存KVが大きく処理costが変わるため、固定chunk sizeではなく、現在のdecode batchとKV occupancyに応じてchunk sizeを調整する。評価では運用係数 α=1.3 を用い、decode経路の推定TTFTがprefill経路に対して許容範囲内で、かつrequest自身のTTFT SLOを満たせる場合にdeflectする。

## 手法

- dispatcherがprefill nodeとdecode nodeのloadを収集する。
- 各requestについて通常prefill経路のTTFTと、decode nodeへdeflectした場合のTTFTを推定する。
- decode nodeでは継続中requestのTBTを壊さないよう、prefillを複数chunkに分割してdecode iteration間へ挿入する。
- chunkごとのcost増加を考慮し、TBT headroomから安全なchunk sizeを逐次決める。
- deflectしたrequestのKV cacheはdecode node上で生成され、そのままdecodeへ移るためinter-node KV transferが発生しない。
- latency modelは単純な線形回帰を使い、論文の評価環境ではMAPE 10%未満。schedulerのCPU overheadはrequestあたり1 ms未満と報告する。

実装はvLLM 0.18.1へ約2,000行の変更として組み込み、node stateは100 ms間隔のheartbeatでdispatcherへ通知する。モデル・ハードウェア組ごとのprofilingは約30分としている。

## 評価条件

Azure Standard_ND96amsr_A100_v4を使用し、各nodeは8× NVIDIA A100-SXM4 80GB、AMD EPYC 7V12 64-core、約900 GiB host memoryを備える。主評価は2 prefill node + 2 decode node（2P2D）で、DeepSeek-V2-Lite（16B total / 2.4B active）とproduction-derivedなbursty traceを使用する。

SLOはP95 TTFT ≤ 4 s、P95 TBT ≤ 70 ms。比較対象は通常のprefill/decode分離とTaiChiである。

## 主要結果

- 同じjoint SLO条件でbaselineが7 RPSまでなのに対し、Kairosは9 RPSまでSLOを維持し、持続可能request rateを約28.5%高めた。
- abstractではP95 TTFTを最大81%削減したと報告する。
- decode computeをprefillへ使うためP95 TBTはおおむね5〜10 ms増えるが、評価範囲では70 ms SLO内に保たれた。
- 負荷上昇とともにdecode側headroomが減るためdeflection数も自動的に減り、6 RPSで500件超だったdeflectionが12 RPSでは265件まで低下する。

SLO attainmentの最大改善値はabstract/本文冒頭とconclusionで表記が一致しないため、ここでは共通して確認できるTTFTとsustainable request rateを主要値として扱う。

## 限界

- decode latency predictorの誤差が大きいと既存requestのTBTを侵害し得る。評価ではMAPE 10%未満でprediction起因のSLO違反は観測されなかったが、別hardware/modelへの一般化には再profilingが必要。
- node stateは100 ms heartbeatなので完全な瞬時状態ではない。同一heartbeat間に複数requestを同じdecode nodeへdeflectしすぎない制御を置く。
- prefix cacheがprefill nodeに存在するrequestをdeflectすると、そのcache localityを失う。現行TTFT estimatorはprefix-cache residencyを考慮しない。
- dispatcherは中央集約であり、非常に高いRPSではCPU bottleneckになり得る。sharding可能だがglobal load viewとのtrade-offがある。
- dispatch済みrequestを後からprefill側へ戻すmigrationは行わない。

## 既存研究との差

TaiChiなどのdisaggregated schedulerがprefill/decode間の配置やbatchingを調整するのに対し、Kairosは**decode nodeの余剰computeをprefill処理そのものへ一時的に貸す**。Sarathi系chunked prefillをSLO isolationに利用しつつ、request単位でload-awareにdeflectionし、KV転送を不要にする点が中心差分である。

## 一般的な実装への示唆

分離型servingでは各node typeの平均utilizationだけでなく、別phaseに転用できる瞬間的headroomをschedulerが資源として扱える。とくにKV転送を伴うphase境界では、「高速nodeへ送って後で状態を移す」より、最終配置先で安全に前段処理まで行う方がtail latencyを減らせる条件がある。
