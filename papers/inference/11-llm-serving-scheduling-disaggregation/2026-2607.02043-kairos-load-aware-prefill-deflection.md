# Towards Load-Aware Prefill Deflection for Disaggregated LLM Serving

> Kairosは、prefill専用GPUが混んでいるときにrequestをそこで待たせるのではなく、**decode GPUに残っている計算余力を借りてprefillまで実行する**。ただしdecode中の既存requestを遅らせすぎてはいけないため、prefillを小さなchunkへ分け、token間時間（Token-Between-Token: TBT）のSLOを守れる量だけdecode iterationの隙間へ挿入する。prefillを最終的なdecode node上で行うため、そのrequestのKV cacheをnode間転送する必要もなくなる。

## まず通常のprefill/decode分離を整理する

LLM推論は大きく2段階に分かれる。

1. **事前充填（prefill）**: 入力prompt全体を一度に処理し、各tokenのKV cacheを作る。
2. **復号（decode）**: そのKVを使いながら1 tokenずつ出力する。

大規模servingではprefill nodeとdecode nodeを分離し、requestを

`prefill node → KV cache転送 → decode node`

の順に流すことがある。

prefillとdecodeはhardware利用特性が異なるため、それぞれに最適なGPU数を割り当てられるのが利点である。

しかし実際のtrafficは一定ではない。

ある時間帯にはprefill requestが一気に到着し、prefill nodeに長いqueueができる一方、decode nodeには十分な余裕が残ることがある。

このときsystem全体ではGPU capacityが余っているのに、requestはprefill queueで待ち続ける。

## TTFTのどこに時間がかかるのか

最初のtokenまでの時間（Time To First Token: TTFT）は概ね

`queue待ち + prefill計算 + KV転送 + 最初のdecode`

で構成される。

直感的にはprefill計算そのものが大半に見えるが、論文のproduction-derived workloadでは、条件によってprefill compute自体はP95 TTFTの約2〜23%にすぎない。

残りの大きな部分を

- prefill nodeへ入るまでのqueueing
- prefill後にKV cacheをdecode nodeへ運ぶ時間

が占める。

つまりprefill kernelだけを速くしても、queueとKV transferを消せなければtail TTFTは十分改善しない。

## Kairosの発想: requestをdecode nodeへdeflectする

通常ならprefill nodeへ送るrequestについて、dispatcherが

「このrequestはdecode nodeでprefillした方が早い」

と判断した場合、そのrequestをdecode nodeへ直接送る。

この**迂回実行（deflection）**がKairosの中心である。

requestはdecode node上で

`prefill → そのままdecode`

まで完結する。

したがって2つの効果がある。

1. 混雑したprefill queueを避けられる。
2. KV cacheを最終decode node上で直接作るため、prefill node→decode nodeのKV転送が不要になる。

一方で問題も明確である。

decode nodeはすでに別requestのtokenを生成している。そのGPUで重いprefillを突然実行すると、既存userへの次tokenが遅れてTBT SLOを破る。

そのため「decode nodeに送れるか」だけではなく「どの程度のprefillならdecodeの邪魔をしないか」を制御する必要がある。

# なぜdecode GPUには計算余力が残るのか

prefillとdecodeは同じTransformerを使うが、bottleneckが異なることが多い。

### Prefill

多tokenをまとめて行列演算できるため、GPUの演算器を高効率に使いやすい。比較的**計算律速（compute-bound）**になりやすい。

### Decode

1 requestあたり1 tokenずつしか進まず、各stepで大量のmodel weightやKV cacheを読む必要がある。演算量に対してmemory trafficが大きいため、しばしば**メモリ帯域律速（memory-bandwidth-bound）**になる。

この場合、HBM bandwidthは忙しい一方、GPU演算器には未使用capacityが残る。

Kairosはこの余剰computeへprefillの小片を混ぜる。

ただしprefillもKVを読み書きするため、無制限に混ぜられるわけではない。そこでchunkingが必要になる。

# Chunked prefillとは何か

長いpromptを1回で全部prefillする代わりに、例えば8192 tokenのpromptを

`512 + 512 + 512 + ...`

のような小さな**chunk**へ分割する。

各chunkをdecode iterationの間へ差し込めば、既存decode requestを何百msも止めずに少しずつprefillを進められる。

## Chunkは小さければよいわけではない

chunkが小さいほどdecodeへの干渉は減るが、prefill完了まで多くのiterationが必要になりTTFTが増える。

chunkが大きいほどprefillは早く終わるが、1回のdecode stallが長くなりTBT SLOを破りやすい。

したがってKairosは**その時点で安全な最大chunk**を選びたい。

## なぜ後半chunkほど重くなるのか

同じ512 token chunkでもprefillの序盤と後半ではcostが違う。

attentionでは新しいtokenが、それ以前に処理済みのcontextへattentionする。

最初の512 tokenを処理するときは過去contextが短い。しかし数千token処理済みの後半chunkでは、それまでに作った大きなKV cacheを参照する必要がある。

そのためchunk indexが進むほどprefill stepが重くなる。

論文のprofilingでは、512 token以下のchunkはtested workloadでdecode stepへの追加latencyを概ね30 ms以内に抑えられた一方、1024/2048 token chunkは条件によって大きなstallを生む。2048-token chunkでは後半chunkで最大約250 ms級の追加時間になる例も示す。

だから固定chunk sizeではなく、

- decode batch size
- decode側KV occupancy
- prefillのchunk index
- current sequence lengths

に応じてchunkを小さくする必要がある。

# TBT SLOを守る安全なchunk schedule

Kairosはdecode nodeごとにlatency predictorを持つ。

predictorは現在stateと候補chunk sizeから

「このprefill chunkを次のdecode iterationへ混ぜると、そのiterationが何msになるか」

を予測する。

論文の評価環境では単純な回帰modelでも平均絶対百分率誤差（Mean Absolute Percentage Error: MAPE）10%未満を報告する。

## 可変chunk schedule

requestをdecode nodeへ送る前に、prompt全体を最後まで処理できるchunk列を仮想的に作る。

例えば

`1024 → 1024 → 512 → 512 → 256 ...`

のように、序盤は大きく、contextが増えて重くなる後半は小さくする。

各chunkについて既存decode requestのTBT SLOを超えないことを確認する。

安全なscheduleを最後まで作れなければ、そのdecode nodeへdeflectしない。

つまり「今1chunk入れられる」だけで判断せず、**request全体のprefillを安全に完走できる見込み**まで見る。

# どのnodeへ送るか

dispatcherは各requestについて少なくとも2種類のTTFTを予測する。

1. 通常どおりprefill nodeへ送った場合
2. 各decode nodeへdeflectした場合

prefill node側では現在queue待ちとprefill処理、KV転送を含める。

decode node側では安全なchunk scheduleを組み、その総prefill時間とdecode開始までの時間を見積もる。

## α=1.3 の意味

Kairosはdecode経路が単に「わずかに速そう」というだけではdeflectしない。

論文評価では運用係数 `α = 1.3` を使い、decode側予測TTFTが通常prefill側に対して十分許容でき、request自身のTTFT SLOも満たす場合にdeflectする。

この係数はaggressivenessの制御である。

- αを大きくする: より多くdecodeへ送れるが、decode interference riskが増える。
- αを小さくする: 保守的になり、prefill queueのload shedding効果は小さくなる。

# 状態取得と実装

KairosはvLLM 0.18.1へ約2,000行の変更として実装されている。

各nodeは100 ms間隔のheartbeatで

- queue state
- active batch
- KV occupancy
- その他load情報

を中央dispatcherへ送る。

model/hardware pairごとのlatency profilingは約30分、schedulerのCPU overheadはrequestあたり1 ms未満と報告する。

100 ms heartbeatは完全なinstantaneous viewではないため、同じheartbeat window中に複数requestを同じdecode nodeへ送りすぎない制御も置く。

# 主要結果

## 1. SLOを守れるrequest rateを約28.5%増加

baseline群が約7 RPSまでjoint SLOを維持したのに対し、Kairosは約9 RPSまで維持した。

したがって同一resource構成で持続可能request rateは

`7 → 9 RPS`

となり、約28.5%増える。

これはGPUを追加した結果ではなく、prefill側へ偏ったloadをdecode側の余剰capacityへ移した結果である。

## 2. P95 TTFTを最大81%削減

abstractではP95 TTFTを最大81%削減すると報告する。

効果は特にprefill queueが混雑し、decode側にまだheadroomがあるload域で大きい。

ただし論文中のSLO attainment最大改善値はabstractとconclusionで79% / 71%と表記に不一致がある。このためrepositoryでは共通して確認できるTTFT reductionとsustainable request rateを主要値として扱う。

## 3. Decode TBTは少し悪化するがSLO内

prefillをdecode GPUへ混ぜるため、既存decode requestのP95 TBTは概ね5〜10 ms程度増える。

しかし主評価では70 ms SLO内に維持される。

これはKairosが「decodeを無料で使っている」わけではないことを示す。

**TTFTを改善する代わりにdecode側の未使用slackを少し消費する**trade-offである。

## 4. Loadが高くなると自動的にdeflectionを減らす

6 RPS付近では500件超のrequestをdecode側へdeflectする一方、12 RPSでは265件程度まで減少する。

loadが高くなるほどdecode側のTBT headroomも減るため、安全なchunk scheduleを作れなくなり、自動的にprefill nodeへ戻る。

このbackoffがないstatic policyでは、load増加時にdecode SLO violationを起こしやすい。

# Static policyではなぜ駄目なのか

motivation実験では固定長のprefill chunkをdecodeへ送るstatic policyも評価する。

大きな2048-token chunkはTTFTを短くしやすいが、decodeを長時間止めるためTBT violationを発生させる。

逆に小さすぎるchunkはTBTには安全でもprefillが進まず、queue relief効果が小さい。

理想的に未来の実行時間を知るOracleではTTFT約2.6 s、SLO attainment 99.5%、TBT violation 0という結果が示され、**正しいchunk sizeをその時々で選べれば大きな余地がある**ことをmotivating gapとして使っている。

KairosはそのOracle判断をonline predictorで近似する。

# TaiChi等との違い

既存のdisaggregated schedulerは主に

- どのprefill nodeへ送るか
- どのdecode nodeへ送るか
- replica数をどうするか

を最適化する。

Kairosはphase境界そのものを一時的に崩し、**decode nodeがprefill処理まで担当する**。

しかも最終decode nodeでprefillするため、単なるload balancingだけでなくinter-node KV transferも消える。

この点が通常のrouting policyとの大きな違いである。

# 同名の別Kairosとの違い

repositoryには `Taming Request Imbalance: SLO-Aware Scheduling for Disaggregated LLM Inference`（arXiv:2605.02329）もあり、こちらもsystem名がKairosである。

両者は別研究である。

### arXiv:2605.02329

- prefill/decodeの配置は維持
- prefill queueの優先順をurgencyで変更
- decode batch membershipをTPOT slackで変更

### arXiv:2607.02043（本論文）

- prefill処理そのものをdecode nodeへdeflect
- chunked prefillでTBT isolation
- final decode node上でKVを直接作り、KV network transferを回避

system名ではなくcanonical arXiv IDで識別する必要がある。

# 限界

- 主評価はAzure A100 cluster、DeepSeek-V2-Lite、1系統のproduction-derived traceに限定される。
- predictorはmodel/hardware pairごとのprofilingを必要とし、hardwareを変えると再較正が必要。
- prediction errorが大きいと既存decode requestのTBT SLOを直接侵害する。
- node stateは100 ms heartbeatなのでstaleになる。極端に高いRPSではこの遅れが大きくなる可能性がある。
- dispatcherは中央集約型で、非常に高RPSではcontrol-plane bottleneckになり得る。
- prefix cacheがprefill node側に存在するrequestをdecodeへdeflectするとcache localityを失う。現行estimatorはprefix-cache residencyを完全には考慮しない。
- 一度decode nodeへdeflectしたrequestを途中でprefill nodeへ戻すmigrationは行わない。
- 本文記載の公式GitHub URLは2026-09-08確認時に404で、公開実装を取得できなかった。
- abstractとconclusionで最大SLO-attainment改善値に不一致があるため、一部headline値の扱いには注意が必要。

# 一般的な実装への示唆

分離型servingではresourceを

`prefill GPU capacity`

と

`decode GPU capacity`

に完全固定する必要はない。

phaseごとにbottleneckが違うなら、**あるphaseで余っているresourceを他phaseへ期限付きで貸す**設計が可能である。

特に、decodeのようにmemory bandwidth-boundでcompute unitが余りやすいphaseでは、compute-heavyなprefillを小さく混ぜる余地がある。

また、state transferを伴うphase境界では

`遠い高速resourceで処理してstateを後で移す`

より

`最終配置先で前段処理まで行いstate transfer自体を消す`

方が速い条件がある。

SSD/NVMeを含むhierarchical servingでも、compute placementとstate placementを別々に最適化するだけでなく、**stateの最終居場所で前段computeを行うことでtransferを消せないか**という観点へ拡張できる。
