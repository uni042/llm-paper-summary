# Towards 負荷-考慮 プリフィル Deflection for Disaggregated LLM サービング

> Kairosは、プリフィル専用GPUが混んでいるときにリクエストをそこで待たせるのではなく、**デコード GPUに残っている計算余力を借りてプリフィルまで実行する**。ただしデコード中の既存リクエストを遅らせすぎてはいけないため、プリフィルを小さな塊へ分け、トークン間時間（トークン-Between-トークン: TBT）のSLOを守れる量だけデコード 反復の隙間へ挿入する。プリフィルを最終的なデコード ノード上で行うため、そのリクエストのKV キャッシュをノード間転送する必要もなくなる。

## まず通常のプリフィル/デコード分離を整理する

LLM推論は大きく2段階に分かれる。

1. **事前充填（プリフィル）**: 入力プロンプト全体を一度に処理し、各トークンのKV キャッシュを作る。
2. **復号（デコード）**: そのKVを使いながら1 トークンずつ出力する。

大規模サービングではプリフィル ノードとデコード ノードを分離し、リクエストを

`事前充填 ノード → KV cache転送 → 復号 ノード`

の順に流すことがある。

プリフィルとデコードはハードウェア利用特性が異なるため、それぞれに最適なGPU数を割り当てられるのが利点である。

しかし実際のトラフィックは一定ではない。

ある時間帯にはプリフィル リクエストが一気に到着し、プリフィル ノードに長いキューができる一方、デコード ノードには十分な余裕が残ることがある。

このときシステム全体ではGPU 容量が余っているのに、リクエストはプリフィル キューで待ち続ける。

## TTFTのどこに時間がかかるのか

最初のトークンまでの時間（時間 To 先 トークン: TTFT）は概ね

`queue待ち + prefill計算 + KV転送 + 最初のdecode`

で構成される。

直感的にはプリフィル計算そのものが大半に見えるが、論文の本番-導出 ワークロードでは、条件によってプリフィル 計算自体はP95 TTFTの約2〜23%にすぎない。

残りの大きな部分を

- プリフィル ノードへ入るまでのqueueing
- プリフィル後にKV キャッシュをデコード ノードへ運ぶ時間

が占める。

つまりプリフィル カーネルだけを速くしても、キューとKV 転送を消せなければ末尾 TTFTは十分改善しない。

## Kairosの発想: リクエストをデコード ノードへdeflectする

通常ならプリフィル ノードへ送るリクエストについて、dispatcherが

「このリクエストはデコード ノードでプリフィルした方が早い」

と判断した場合、そのリクエストをデコード ノードへ直接送る。

この**迂回実行（振り分け）**がKairosの中心である。

リクエストはデコード ノード上で

`prefill → そのままdecode`

まで完結する。

したがって2つの効果がある。

1. 混雑したプリフィル キューを避けられる。
2. KV キャッシュを最終デコード ノード上で直接作るため、プリフィル ノード→デコード ノードのKV転送が不要になる。

一方で問題も明確である。

デコード ノードはすでに別リクエストのトークンを生成している。そのGPUで重いプリフィルを突然実行すると、既存利用者への次トークンが遅れてTBT SLOを破る。

そのため「デコード ノードに送れるか」だけではなく「どの程度のプリフィルならデコードの邪魔をしないか」を制御する必要がある。

# なぜデコード GPUには計算余力が残るのか

プリフィルとデコードは同じTransformerを使うが、ボトルネックが異なることが多い。

### プリフィル

多トークンをまとめて行列演算できるため、GPUの演算器を高効率に使いやすい。比較的**計算律速（計算-境界）**になりやすい。

### デコード

1 リクエストあたり1 トークンずつしか進まず、各段階で大量のモデル 重みやKV キャッシュを読む必要がある。演算量に対してメモリ トラフィックが大きいため、しばしば**メモリ帯域律速（メモリ-帯域-境界）**になる。

この場合、HBM 帯域は忙しい一方、GPU演算器には未使用容量が残る。

Kairosはこの余剰計算へプリフィルの小片を混ぜる。

ただしプリフィルもKVを読み書きするため、無制限に混ぜられるわけではない。そこでchunkingが必要になる。

# Chunked プリフィルとは何か

長いプロンプトを1回で全部プリフィルする代わりに、例えば8192 トークンのプロンプトを

`512 + 512 + 512 + ...`

のような小さな**塊**へ分割する。

各塊をデコード 反復の間へ差し込めば、既存デコード リクエストを何百msも止めずに少しずつプリフィルを進められる。

## Chunkは小さければよいわけではない

塊が小さいほどデコードへの干渉は減るが、プリフィル完了まで多くの反復が必要になりTTFTが増える。

塊が大きいほどプリフィルは早く終わるが、1回のデコード 停止が長くなりTBT SLOを破りやすい。

したがってKairosは**その時点で安全な最大塊**を選びたい。

## なぜ後半塊ほど重くなるのか

同じ512 トークン 塊でもプリフィルの序盤と後半ではコストが違う。

アテンションでは新しいトークンが、それ以前に処理済みの文脈へアテンションする。

最初の512 トークンを処理するときは過去文脈が短い。しかし数千トークン処理済みの後半塊では、それまでに作った大きなKV キャッシュを参照する必要がある。

そのため塊 indexが進むほどプリフィル 段階が重くなる。

論文のprofilingでは、512 トークン以下の塊はtested ワークロードでデコード 段階への追加遅延を概ね30 ms以内に抑えられた一方、1024/2048 トークン 塊は条件によって大きな停止を生む。2048-トークン 塊では後半塊で最大約250 ms級の追加時間になる例も示す。

だから固定塊 サイズではなく、

- デコード バッチ サイズ
- デコード側KV 占有率
- プリフィルの塊 index
- current sequence lengths

に応じて塊を小さくする必要がある。

# TBT SLOを守る安全な塊 予定

Kairosはデコード ノードごとに遅延 予測器を持つ。

予測器は現在状態と候補塊 サイズから

「このプリフィル 塊を次のデコード 反復へ混ぜると、その反復が何msになるか」

を予測する。

論文の評価環境では単純な回帰モデルでも平均絶対百分率誤差（Mean Absolute Percentage Error: MAPE）10%未満を報告する。

## 可変塊 予定

リクエストをデコード ノードへ送る前に、プロンプト全体を最後まで処理できる塊列を仮想的に作る。

例えば

`1024 → 1024 → 512 → 512 → 256 ...`

のように、序盤は大きく、文脈が増えて重くなる後半は小さくする。

各塊について既存デコード リクエストのTBT SLOを超えないことを確認する。

安全な予定を最後まで作れなければ、そのデコード ノードへ振り分けしない。

つまり「今1塊入れられる」だけで判断せず、**リクエスト全体のプリフィルを安全に完走できる見込み**まで見る。

# どのノードへ送るか

dispatcherは各リクエストについて少なくとも2種類のTTFTを予測する。

1. 通常どおりプリフィル ノードへ送った場合
2. 各デコード ノードへdeflectした場合

プリフィル ノード側では現在キュー待ちとプリフィル処理、KV転送を含める。

デコード ノード側では安全な塊 予定を組み、その総プリフィル時間とデコード開始までの時間を見積もる。

## α=1.3 の意味

Kairosはデコード経路が単に「わずかに速そう」というだけではdeflectしない。

論文評価では運用係数 `α = 1.3` を使い、デコード側予測TTFTが通常プリフィル側に対して十分許容でき、リクエスト自身のTTFT SLOも満たす場合にdeflectする。

この係数はaggressivenessの制御である。

- αを大きくする: より多くデコードへ送れるが、デコード interference riskが増える。
- αを小さくする: 保守的になり、プリフィル キューの負荷 shedding効果は小さくなる。

# 状態取得と実装

KairosはvLLM 0.18.1へ約2,000行の変更として実装されている。

各ノードは100 ms間隔のheartbeatで

- キュー 状態
- 稼働中 バッチ
- KV 占有率
- その他負荷情報

を中央dispatcherへ送る。

モデル/ハードウェア pairごとの遅延 profilingは約30分、スケジューラのCPU オーバーヘッドはリクエストあたり1 ms未満と報告する。

100 ms 生存確認は完全なinstantaneous viewではないため、同じ生存確認 窓中に複数リクエストを同じデコード ノードへ送りすぎない制御も置く。

# 主要結果

## 1. SLOを守れるリクエスト rateを約28.5%増加

比較対象群が約7 RPSまでjoint SLOを維持したのに対し、Kairosは約9 RPSまで維持した。

したがって同一資源構成で持続可能リクエスト rateは

`7 → 9 RPS`

となり、約28.5%増える。

これはGPUを追加した結果ではなく、プリフィル側へ偏った負荷をデコード側の余剰容量へ移した結果である。

## 2. P95 TTFTを最大81%削減

abstractではP95 TTFTを最大81%削減すると報告する。

効果は特にプリフィル キューが混雑し、デコード側にまだheadroomがある負荷域で大きい。

ただし論文中のSLO attainment最大改善値はabstractとconclusionで79% / 71%と表記に不一致がある。このためrepositoryでは共通して確認できるTTFT reductionとsustainable リクエスト rateを主要値として扱う。

## 3. デコード TBTは少し悪化するがSLO内

プリフィルをデコード GPUへ混ぜるため、既存デコード リクエストのP95 TBTは概ね5〜10 ms程度増える。

しかし主評価では70 ms SLO内に維持される。

これはKairosが「デコードを無料で使っている」わけではないことを示す。

**TTFTを改善する代わりにデコード側の未使用slackを少し消費する**trade-offである。

## 4. 負荷が高くなると自動的に振り分けを減らす

6 RPS付近では500件超のリクエストをデコード側へ振り分けする一方、12 RPSでは265件程度まで減少する。

負荷が高くなるほどデコード側のTBT headroomも減るため、安全な塊 予定を作れなくなり、自動的にプリフィル ノードへ戻る。

このbackoffがない静的 方策では、負荷増加時にデコード SLO violationを起こしやすい。

# 静的 方策ではなぜ駄目なのか

motivation実験では固定長のプリフィル 塊をデコードへ送る静的 方策も評価する。

大きな2048-トークン 塊はTTFTを短くしやすいが、デコードを長時間止めるためTBT violationを発生させる。

逆に小さすぎる塊はTBTには安全でもプリフィルが進まず、キュー relief効果が小さい。

理想的に未来の実行時間を知るオラクルではTTFT約2.6 s、SLO attainment 99.5%、TBT violation 0という結果が示され、**正しい塊 サイズをその時々で選べれば大きな余地がある**ことをmotivating gapとして使っている。

Kairosはそのオラクル判断をオンライン 予測器で近似する。

# TaiChi等との違い

既存のdisaggregated スケジューラは主に

- どのプリフィル ノードへ送るか
- どのデコード ノードへ送るか
- replica数をどうするか

を最適化する。

Kairosはphase境界そのものを一時的に崩し、**デコード ノードがプリフィル処理まで担当する**。

しかも最終デコード ノードでプリフィルするため、単なる負荷 均衡化だけでなくinter-ノード KV 転送も消える。

この点が通常のルーティング 方策との大きな違いである。

# 同名の別Kairosとの違い

repositoryには `Taming Request Imbalance: SLO-Aware Scheduling for Disaggregated LLM Inference`（arXiv:2605.02329）もあり、こちらもシステム名がKairosである。

両者は別研究である。

### arXiv:2605.02329

- プリフィル/デコードの配置は維持
- プリフィル キューの優先順をurgencyで変更
- デコード バッチ membershipをTPOT slackで変更

### arXiv:2607.02043（本論文）

- プリフィル処理そのものをデコード ノードへ振り分け
- chunked プリフィルでTBT isolation
- final デコード ノード上でKVを直接作り、KV ネットワーク 転送を回避

システム名ではなくcanonical arXiv IDで識別する必要がある。

# 限界

- 主評価はAzure A100 クラスタ、DeepSeek-V2-Lite、1系統の本番-導出 トレースに限定される。
- 予測器はモデル/ハードウェア pairごとのprofilingを必要とし、ハードウェアを変えると再較正が必要。
- 予測 errorが大きいと既存デコード リクエストのTBT SLOを直接侵害する。
- ノード 状態は100 ms 生存確認なのでstaleになる。極端に高いRPSではこの遅れが大きくなる可能性がある。
- 振分器は中央集約型で、非常に高RPSでは制御-プレーン ボトルネックになり得る。
- プレフィックス キャッシュがプリフィル ノード側に存在するリクエストをデコードへ振り分けするとキャッシュ 局所性を失う。現行estimatorはプレフィックス-キャッシュ residencyを完全には考慮しない。
- 一度デコード ノードへ振り分けしたリクエストを途中でプリフィル ノードへ戻すmigrationは行わない。
- 本文記載の公式GitHub URLは2026-09-08確認時に404で、公開実装を取得できなかった。
- abstractとconclusionで最大SLO-attainment改善値に不一致があるため、一部headline値の扱いには注意が必要。

# 一般的な実装への示唆

分離型サービングでは資源を

`prefill GPU capacity`

と

`decode GPU capacity`

に完全固定する必要はない。

段階ごとにボトルネックが違うなら、**ある段階で余っている資源を他段階へ期限付きで貸す**設計が可能である。

特に、デコードのようにメモリ 帯域-境界で計算 unitが余りやすい段階では、計算-heavyなプリフィルを小さく混ぜる余地がある。

また、状態 転送を伴う段階境界では

`遠い高速resourceで処理して状態を後で移す`

より

`最終配置先で前段処理まで行い状態 転送自体を消す`

方が速い条件がある。

SSD/NVMeを含む階層型 サービングでも、計算 配置と状態 配置を別々に最適化するだけでなく、**状態の最終居場所で前段計算を行うことで転送を消せないか**という観点へ拡張できる。
