# SkillZip：実行契約を保つスキル手順グラフ圧縮と推論時コンテキスト削減

## 概要

SkillZipは、大規模言語モデル（LLM）を利用するエージェントが多数のスキル文書を参照するとき、必要な手順を短く提示しながら実行上の依存関係と検証条件を残すための仕組みである。一般のプロンプト圧縮と違い、文書の語数を減らすこと自体を最適化の終点としない。各スキルの「操作を実行する前提」「使う道具と入力」「失敗した場合の処理」「結果の検証」を、互いに接続した節のグラフとして表現し、複数のスキルで繰り返す部分だけを可逆なマクロに置換する。タスク実行時には、質問に必要な部分グラフだけを展開してLLMへ渡す。

研究の中心は、スキルの再利用単位を「ファイル全体」から「入出力と検証契約を持つ手順の部分グラフ」へ変更することにある。スキル単位の検索では、例えばCSV列名の正規化を求めるだけなのに、ピボット集計やグラフ描画まで含む複数のスキル文書が選ばれ得る。単純なテキスト圧縮は余分な語を減らせるが、数式を含む表計算ファイルの検証条件を落とすなど、同じ文言の操作でも意味が異なる場合に破綻する。SkillZipは検索・圧縮・実行を同じ契約付き手順節の単位で扱うことで、不要な提示と実行条件の欠落を同時に減らす。

原著のSkillsBench、1,000スキル、MiniMax-M2.7という条件では、最も強い比較対象のSkillDAGに対して、タスク報酬27.3から33.3、最初の正解スキル検索率66.7から73.6、最終提示手順の平均トークン数3,103から1,941へ改善する。契約を保った圧縮率は3.46倍で、依存関係保存率99.2%、操作から検証器への到達率98.7%を報告する。エージェント全行程の平均所要時間も429.7秒から339.0秒へ短縮した。ただし、この速度差は検索処理だけでなく、LLM推論、道具実行、失敗からの修復を含む実験結果であり、LLM本体のトークン生成速度が高速化したことを示すものではない。

## 問題設定：なぜスキルの「文書全体」検索では不足するか

エージェントのスキルは、単なる知識検索の文書とは異なる。自然言語の手順に加えて、実行するスクリプト、入力形式、利用可能な資源、事前条件、失敗時の分岐、検証テストを含む。長期に運用するシステムではスキルが増加し、同じ下位操作が多数のスキルに繰り返し現れる。ファイル単位の検索で必要なスキルを5個選ぶと、似た導入説明や同一の前処理が5回分提示されることがあり、コンテキスト長だけでなく、どの手順を優先するかという曖昧さも増える。

従来の解決策には、意味ベクトルによるスキル検索、スキル間の依存グラフ、テキスト圧縮、検索後の実行グラフ構築がある。しかし検索はスキル単位、圧縮は文章単位、実行は手順単位という不一致が残る。たとえばCSVファイルの列名正規化と、表計算ブックの列名正規化は表面上似ているが、後者には数式保持の条件が付く場合がある。圧縮時に「表を読み、列名を正規化し、保存する」という共通部分だけ残すと、数式を壊さないための入力条件や検証器への接続が消える。

SkillZipは、処理節の境界に入出力の型、道具、前提条件、検証器を持たせる。ある処理を再利用するには、文面の類似性だけでなく、外側との接続と検証の経路が互換であることを要求する。したがって削減対象は「余分な文字」ではなく「同じ実行契約を持つ重複手順」である。これは検索品質と実行安全性を結び付ける問題設定であり、トークン削減を品質維持の代用指標としない。

## 手法：4段階で契約付きグラフを作り、圧縮し、提示する

### 1. Sec2Graph：スキルを出典付きの手順節へ分解

入力はスキルの説明文、スクリプト、テスト、参照資料などである。まず見出し、箇条書き、コード、警告、引数説明、テストを境界候補として分割し、必要に応じてLLMによる解析で節の境界と役割を補正する。役割は目的（Intent）、起動条件（Trigger）、入力（Input）、事前条件（Precondition）、操作（Operation）、資源（Resource）、失敗（Failure）、検証（Verifier）、出力（Output）の9種類。これはファイルの行番号ではなく、実行上の機能を示す分類である。

節ノードvは、役割τ、内容c、入力署名X、出力署名Y、利用資源R、前提・検証条件G、元の文書位置srcを持つ。たとえば「CSVを読み込む」は操作、「区切り文字を推定する」はその前提操作、「行数が変わらないことを確認する」は検証に分類される。節同士には、必要条件、入力の束縛、資源利用、検証、失敗修復を表す有向辺を張る。元のスキルに所属するという情報も残し、共通処理を認識しても元の出典を失わない。

同じ処理が別スキルに出現した場合、節の実体を単純に一つへ統合せず、出現ごとのノードを保持したまま、役割・入出力・資源・検証条件が互換なら共通の典型ノードへリンクする。これにより、繰り返し出現する操作を発見しながら、どのスキルのどの節だったか、どの検証器へつながっていたかを復元できる。出力は節ノードと依存辺を持つ永続的な手順グラフである。追加費用は、スキル文書の分解とLLMによる契約抽出であり、原著は大規模時のこの推論費用を局所構築時間と別に扱う。

### 2. MotifZip：同じ実行契約を持つ反復部分だけをマクロ化

入力はSec2Graphが構築した手順グラフである。MotifZipは役割署名、資源の種類、入出力の形状によって候補節を分け、互換な近傍だけから繰り返し部分グラフを探す。無制限に全ノード対を比較するわけではない。候補が複数のスキルに現れても、内部の元節が重なる、外部ポートの接続が矛盾するなどの場合は独立した再利用出現として数えない。文字列の類似度より、処理の構造と外側の接続を優先する。

圧縮候補gについて、外部入力ポートI_g、外部出力ポートO_g、契約χ_gを構築する。採用には、(a) 入出力と資源の署名が安定している、(b) 必要な依存関係がマクロ内部で閉じるか外部ポートへ明示される、(c) 状態を変更する操作から必要な検証器へ到達できる、という三条件が必要である。合格した部分グラフをマクロM_gへ置き換え、元の節と辺、出現ごとのポート対応を逆変換できるよう保持する。削減効果があっても検証条件を失う候補は拒否する。

この「可逆」は、記録された節・依存・検証器・出典を再構成できるという構造上の保証である。LLMが元の手順を正しく解釈していたか、元の検証器が十分なテストだったか、記録されなかった暗黙の副作用が存在しないかまで証明するものではない。論文自身もこの区別を明記している。実装上は、CSVを扱う二つのスキルで共通の読込マクロを作っても、数式を含むXLSXの操作を同じマクロへ誤統合しないよう、資源種別と数式検証の契約を照合する。

### 3. PathHydrate：質問から実行可能な最小コンテキストを組み立てる

入力はユーザーのタスクq、実行環境の情報p、許容トークン予算B、圧縮済みグラフである。まずタスクを目的、要求出力、必要能力、可視入力、領域、下位目標へ解析する。次に各節について、元の質問と下位目標の両方から埋め込み類似度を計算し、最大値を節候補の適合度とする。節だけで検索すると異なるスキルの節が散らばるため、スキル説明の順位とスキル内で最も適合する節の順位を相互順位融合（Reciprocal Rank Fusion）でまとめ、候補集合を絞る。

その後、タスクに必要な節をつなぐ部分グラフPを選ぶ。理想化された目的関数は ηT(P)+β|P|+γE(P)−δMatch(P,q) を最小化するもので、Tは提示トークン数、|P|は節・マクロ数、Eは後で展開する費用、Matchはタスクとの一致度である。必須条件として、要求された節の被覆、依存関係の閉包、検証器への到達、予算T(P)≤Bを課す。実行時は厳密な全探索ではなく、低費用の接続を追加しながら必要な役割を埋める。

選んだ部分グラフに操作があっても、その入力や前提、検証が欠けている場合がある。そこで操作から逆方向へ入力・前提・資源をたどり、順方向へ失敗・検証・出力をたどって補う。予算内で検証可能な部分グラフを作れなければ、元のスキル単位の最小集合へ退避する。十分な手順がそろえば、予算が余っていても不要な節を追加しない。この「必要量で止める」方針が、平均提示トークン数を予算上限より小さく保つ。

マクロは、名前のみ、契約、概要、元の節全文という四段階で展開する。たとえばCSVの列名を正規化して行数を検証するタスクなら、共通のCSV読込マクロと行数検証器だけを示し、ピボット集計や図の作成を含めない。必要な事前条件がマクロ名だけでは判断できなければ契約を示し、それでも不足すれば元の節を展開する。出力はエージェントへ提示する実行可能なコンテキストC_qと、採用した節・展開段階・費用・検証器被覆を記録する履歴である。

### 4. ReZip：スキル追加と実行失敗から圧縮辞書を更新

入力は新しいスキルまたはエージェントの実行履歴である。新しいスキルをSec2Graphで節グラフへ変換し、既存マクロと契約互換の部分は再利用する。まだ共通化できない節は残差バッファに保持し、複数のスキルで同じ契約が再び見つかり、圧縮利得が正で、契約検査を通る場合に限って新しいマクロへ昇格させる。毎回すべてのスキルを再圧縮する必要はない。

実行履歴からは、マクロの利用回数、元文書の再展開回数、検証器の失敗、後段での修復費用を集計する。危険度ρ(M)は、展開率・検証失敗率・修復費用を重み付きで合計した指標である。危険度が高くなると、まず該当タスクでのマクロの表示詳細度を上げる。それでも失敗が続けば、マクロをより狭い契約へ分割するか、元の節へ戻す。たとえば通常のCSV出力には短いマクロを維持しつつ、数式を含む表計算ブックでは数式保持の検証を明示した手順へ切り替える。

この更新は、スキル追加に伴う新しい重複の発見と、実行後の失敗に伴う圧縮の取り消しを同じ仕組みで扱う。ただし失敗の原因をマクロへ正しく帰属できなければ、必要以上に展開したり、危険な圧縮を維持したりする可能性がある。原著の失敗分析でも契約抽出と検索の誤りが主要な残存要因である。

## 評価：タスク成功、構造保存、実行費用を分離する

### 実験条件と指標

| 項目 | 条件・意味 |
|---|---|
| ベンチマーク | SkillsBenchの成果物作成87タスク、ALFWorldの140エピソード |
| 既定スキル数 | SkillsBenchで1,000個、規模感度では200～100,000個 |
| 主要モデル | MiniMax-M2.7、gpt-5.2-codex。補助のモデル横断評価では別の4モデルも使用 |
| 手順選択予算 | SkillsBenchで3,000トークン、ALFWorldで1,200トークン |
| SkillsBenchの実行器 | OpenHandsとBenchFlowのコンテナ実行環境 |
| 比較対象 | 全スキル提示、意味ベクトル検索、Graph-of-Skills、SkillDAG、単純な文章圧縮、一般的グラフ文法 |
| タスク報酬R | SkillsBenchは検証テスト合格割合、ALFWorldは目標達成エピソード割合 |
| Ret@1/Ret@5・MRR | 正解スキルが上位1件・5件にある率、最初の正解順位の逆数平均 |
| DPR・VR | 必要な依存辺の保持割合、操作から検証器への到達可能性 |
| CR・Tok | 格納する有効表現の圧縮比、最終的に提示する手順の平均トークン数 |

スキル検索で返す単位は節またはマクロなので、正解スキルとの照合時は出典ポインタで元のスキルへ戻し、重複スキルIDを最初の出現順に一意化する。これにより、スキル単位検索との比較で評価単位をそろえる。圧縮比CRはマクロ辞書を含む格納表現に対する値であり、Tokは実行時に提示したコンテキストの量である。同じ量を二度測っているわけではない。

### 主要なタスク成績と検索品質

| モデル・評価 | 比較方式 | SkillZip | 改善 |
|---|---:|---:|---:|
| MiniMax-M2.7 / SkillsBench報酬 | SkillDAG 27.3 | 33.3 | +6.0ポイント |
| MiniMax-M2.7 / ALFWorld成功率 | SkillDAG 67.1% | 79.3% | +12.2ポイント |
| MiniMax-M2.7 / SkillsBench Ret@1 | SkillDAG 66.7% | 73.6% | +6.9ポイント |
| MiniMax-M2.7 / SkillsBench Ret@5 | SkillDAG 78.2% | 92.0% | +13.8ポイント |
| gpt-5.2-codex / SkillsBench報酬 | SkillDAG 36.8 | 43.0 | +6.2ポイント |
| gpt-5.2-codex / ALFWorld成功率 | SkillDAG 93.6% | 96.4% | +2.8ポイント |

ALFWorldの+12.2ポイントはMiniMax-M2.7での値であり、すべてのモデルで12.2ポイント改善したわけではない。強い実行器では比較対象も93.6%に達しているため、改善余地が小さい。検索のRet@5向上と報酬向上は方向が一致するが、報酬は検索だけでなく、実行器が受け取った手順を正しく使えるかにも依存する。単純なベクトル検索の弱さは、共有する定型文やスキル名が近い複数パッケージを区別しにくいことと整合する。

### 圧縮と構造保存の交換条件

| 方式 | 格納圧縮比 | 平均提示トークン | DPR | VR | 修復・再展開を要する割合 | 報酬 |
|---|---:|---:|---:|---:|---:|---:|
| 元の節グラフ | 1.00倍 | 6,716 | 100.0% | 100.0% | 0.0% | 31.0 |
| 完全一致のテキスト重複排除 | 1.43倍 | 4,697 | 98.6% | 98.1% | 5.2% | 31.2 |
| 一般の文章圧縮 | 3.46倍 | 1,941 | 65.0% | 60.0% | 45.0% | 25.5 |
| 契約を見ないグラフ文法 | 2.91倍 | 2,308 | 93.4% | 90.8% | 22.7% | 29.4 |
| SkillZipの契約検査なし | 3.78倍 | 1,777 | 88.9% | 84.6% | 31.5% | 27.8 |
| 完全なSkillZip | 3.46倍 | 1,941 | 99.2% | 98.7% | 14.8% | 33.3 |

同じ3.46倍圧縮であっても、文章圧縮は依存関係の35%、検証器への経路の40%を失う。さらに45%のタスクで元の節の回復が必要になり、報酬は25.5まで下がる。対してSkillZipは99%前後の構造を保持し、回復を14.8%へ減らす。ここでの「構造保存」は抽出済み契約に対する計測であり、元の文書に書かれていない暗黙の条件まで完全に守る保証ではない。

### 構成要素除去と負の結果

| 変更 | 報酬 | Ret@1 | 平均提示トークン | DPR | VR |
|---|---:|---:|---:|---:|---:|
| 完全構成 | 33.3 | 73.6 | 1,941 | 99.2% | 98.7% |
| 節単位をやめスキル単位に戻す | 27.9 | 66.7 | 3,103 | ― | ― |
| MotifZipを外す | 31.0 | 71.8 | 2,967 | 100% | 100% |
| 依存関係の閉包を外す | 28.6 | 72.1 | 1,653 | 82.3% | 92.6% |
| 検証器制約を外す | 29.1 | 72.8 | 1,668 | 94.9% | 76.4% |
| 広域の節候補救済を外す | 30.4 | 68.2 | 1,812 | 96.5% | 96.8% |
| 適応的展開を外す | 31.5 | 73.2 | 2,587 | 99.2% | 98.7% |

節単位の表現を外すと、トークン数が59.9%増え、報酬が5.4ポイント低下する。MotifZipだけを外した場合は構造保存率が100%へ上がる一方、提示量が2,967へ増え、報酬が31.0に下がる。依存閉包や検証器の条件を外すとトークン数はさらに短くなるが、DPRまたはVRが大きく下がり、実際のタスク報酬も低下する。これは「短ければ短いほど良い」という圧縮目標の反例である。

### 推論時と全タスクの実測時間を混同しない

| 指標 | SkillDAG | SkillZip | 差の意味 |
|---|---:|---:|---|
| 局所検索・描画時間 | 41.2 ms | 27.9 ms | 質問解析LLMの時間は除外 |
| 局所検索・描画時間（Vector Skills） | 12.1 ms | 27.9 ms | SkillZipは単純なベクトル検索より遅い |
| 1タスクの平均提示手順 | 3,103 tokens | 1,941 tokens | 初回に渡す手順の量 |
| 全ターンの入力処理トークン | 2,782,696 | 1,473,532 | キャッシュ済み入力も含む |
| 全ターンの未キャッシュ入力 | 76,880 | 62,526 | 削減率は18.7% |
| 全ターンの出力トークン | 31,963 | 20,601 | 出力を短縮 |
| 道具呼出し数 | 36.9 | 28.9 | 21.7%減少 |
| 1タスクの平均総時間 | 429.7 s | 339.0 s | LLM・道具・コンテナを含み21.1%短縮 |

重要なのは、単純なベクトル検索の局所処理時間12.1msに対してSkillZipは27.9msかかるという負の結果である。グラフの閉包確認やマクロ展開には追加のCPU処理が必要である。それでもSkillDAGの41.2msより短く、エージェント全体では、余分な分岐・失敗・再実行を減らすことで時間を短縮する。したがって局所検索の高速化と全タスクの短縮は、原因も計測対象も異なる。

入力処理トークン総数の47.0%削減を、通信費や課金の47.0%削減と読み替えてはいけない。原著では入力の多くがキャッシュ経由であり、未キャッシュ分の削減率は18.7%にとどまる。実際のAPI費用はプロバイダのキャッシュ料金や入出力単価にも依存する。トークン数と実行時間は特定のベンチマークと実行器で得た値であり、同じ効果がすべての業務エージェントへ現れる保証ではない。

### 規模感度・構築費用・失敗分析

スキル数200から100,000までの規模評価では、最初の正解検索率（Ret@1）のSkillDAGに対する差が6.2ポイントから23.3ポイントへ拡大する。100,000スキル条件でSkillZipのRet@1は65.1%、局所検索・展開時間は248.3msである。契約抽出済みの約477万節ノードを入力として、グラフ構築とMotifZipの局所処理を行う時間は178秒と報告される。100スキルでは274ms、1,000スキルでは1.44秒、10,000スキルでは16.1秒。**これらの構築時間には、各スキルをLLMで解析して契約を抽出する費用が含まれない**。契約抽出を一度キャッシュする前提の測定である。

選択予算を1,000から5,000トークンへ増やす感度評価では、報酬は1,000トークンで22.4、2,000で31.5、既定3,000で33.3へ上がるが、5,000まで増やしても追加改善は0.8ポイントにとどまる。既定予算3,000でも実際の平均提示は1,941トークン、中央値1,947である。これは予算を使い切るまで文章を詰めるより、検証可能な手順がそろったところで止めることの利点を示す。

残存失敗の内訳は、検索候補の曖昧さ26%、契約抽出の誤り18%、展開不足14%、実行器の操作失敗33%、環境・道具の障害9%である。SkillZip自身の検索・契約・展開に帰属する失敗が58%残っているため、圧縮した契約の完全性が保証されたわけではない。契約の抽出精度は人手注釈に対してmacro-F1 91.6、完全一致率84.6と報告され、見落としが存在する。特に暗黙の事前条件や検証器の不足は、マクロを可逆にしても自動的には修正されない。

## 既存研究との差と実装判断

Graph-of-SkillsやSkillDAGは、主にスキル間の依存・競合・類似性を表現して検索する。SkillZipはスキル内部の節まで開き、契約互換の共通部分をマクロへ圧縮する。単純なLLMLingua系の文章圧縮は、同じ短さへできても入出力や検証のつながりを保存しない。SkillZipの新規性は、文字列の短縮とグラフ検索を別々に行うのでなく、契約付きの同じ単位で両方を処理し、実行履歴で危険なマクロを縮退させる点にある。

エージェント実装に導入する場合、必要なのはモデルの重みや注意カーネルの改変ではなく、スキルの保管・検索・プロンプト構築の中間層である。既存のMarkdown手順書を節へ分割して出典ポインタを残し、操作と検証を対応付け、タスク時には必要な節だけを提示する。実装の最初の検証では、契約抽出の正確さ、検索候補の漏れ、検証器への到達、マクロ展開頻度、タスク総時間を測るべきである。単にトークン数だけを測ると、失敗して元のスキルを再検索する後段費用を見落とす。

本研究は推論サービングのGPUメモリ、KVキャッシュ、重み量子化、投機的復号を直接最適化しない。短くなった手順はLLMの事前充填（prefill）負荷を減らし得るが、論文が示す429.7秒から339.0秒の改善は複数ターンのエージェント実行全体であり、純粋なLLMトークン/秒の測定ではない。エージェントのスキル群を多数保持するシステムで、実行条件を維持しつつ検索・コンテキストを節約したい場合に適合する。

## 限界と再現性

第一に、可逆性の保証は**抽出済みの契約**に限る。元の文書が曖昧で、モデルが前提条件や検証器を抽出し損ねた場合、その欠落した意味はマクロ展開によっても復元できない。抽出の完全一致率84.6%は、失敗が現実に起きることを示す。契約の曖昧さが高い組織固有の手順書、アクセス制御、外部APIの副作用、監査が必要な操作では、形式的な構造保存率だけを安全性保証に使わない。

第二に、最終タスク成績は、SkillsBenchの87タスクとALFWorldの140エピソード、および指定した実行器・モデル・手順予算で測定されている。長期運用の実組織のスキル更新、同時アクセス、セキュリティ権限変更、機密情報の漏えいを含む条件は、同じ実験で検証されていない。スキル100,000個の評価は検索・局所グラフ構築の規模感度であり、100,000スキルを使うエージェントがすべてのタスクを実行したという意味ではない。

第三に、契約抽出を行うLLMの事前計算費用がある。論文の178秒という大規模構築時間は抽出済み節ノードを前提とした局所処理だけの値であり、初期導入の総費用を示さない。ReZipの増分更新でも新規スキルの契約抽出は必要であり、更新頻度が高い場合はその推論費用と人手確認の費用を考慮する必要がある。

第四に、スキル単位検索より細かい節検索は、共通処理の再利用には有利だが、初期候補に正解節が入らなければ回復できない。論文の失敗内訳では検索に帰属するものが26%で最大の構造側要因である。さらに予算が狭いと必要な分岐や検証器を提示できず、元スキルへ退避する。圧縮した構造を維持することと、実際に適切な手順を見つけることは別問題である。

第五に、圧縮比・提示トークン数・全ターンの入力処理トークン・全タスク時間はそれぞれ測定単位が異なる。3.46倍の格納圧縮をそのまま3.46倍の応答高速化としない。ベクトル検索は局所的にはSkillZipより速いという反例も存在する。GPU上のLLM推論速度、ネットワーク転送量、実際のAPI課金、エネルギー消費はこの実験の主要な直接測定対象ではない。

第六に、原著の一次論文HTMLには実装の擬似コードと実験詳細があるが、著者が公開したSkillZip専用のソースコードURLを本文から特定できなかった。実装の独立再実行、第三者による契約抽出の再現性、モデル版変更後の再測定は未実施である。将来の移植時には、論文の指標に加えて、実行ログを保存して誤った圧縮が後段の道具呼出しや検証失敗を増やしていないか監査する必要がある。
