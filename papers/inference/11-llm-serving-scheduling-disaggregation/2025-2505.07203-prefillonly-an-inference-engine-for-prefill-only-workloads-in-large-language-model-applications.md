# PrefillOnly: An Inference Engine for Prefill-only Workloads in Large Language Model Applications

> LLMサービングは「長い入力の後に何十〜何百トークンも生成する」ことを暗黙に前提としている。しかし推薦・二値判定・分類では、長い履歴を読んだ後に必要なのは **Yes/Noや候補IDに相当する1トークンだけ**という場合がある。PrefillOnlyはこのワークロードを通常生成から分離し、後続デコードのためのKV保持・大バッチ・汎用スケジューリングを捨てることで、メモリ容量と待ち時間を同時に改善する。

## 概要

一般的なLLM推論は、入力列をまとめて処理する**プリフィル（prefill）**と、その後に1トークンずつ生成する**デコード（decode）**からなる。通常のサービングエンジンは出力長を事前に知らないため、プリフィルで各層が作ったキー・値キャッシュ（Key-Value cache; KVキャッシュ）を保持し続け、後続デコードで再利用する。

ところが推薦、信用確認、データラベル付けなどでは、モデルに長い情報を読ませても最終出力が1トークンだけで十分なことがある。この場合、プリフィル完了直後に要求が終わるので、**各層のKVを後のデコードへ持ち越す理由がない**。

PrefillOnlyはこの性質から三つの設計を導く。

1. 後続デコード用KVを保持しないことでGPUメモリを空ける。
2. KVを捨てても残る大きな中間活性のピークを、非注意層のチャンク化で抑える。
3. 出力長が固定なので要求完了時間を事前推定し、接頭辞キャッシュ再利用と待ち時間を考慮したスケジューリングを行う。

つまり単純な「KVキャッシュ削減手法」ではなく、**ワークロードの終了条件が既知であることをメモリ管理とオンラインスケジューリングの両方に使う推論エンジン**である。

## 背景：通常の生成向け最適化がなぜ合わないのか

### 全層KV保持が不要

通常のデコードでは、第l層で過去トークンに対応するK/Vを次の生成ステップでも使うので、全層分を残す必要がある。プリフィル専用要求は1トークンを出した時点で終了するため、第l層の処理を通過した後、その層のKVを将来参照するデコードステップが存在しない。

PrefillOnlyはこの寿命の違いを利用し、基本的には現在計算中の層に必要なKVだけを保持する。これにより入力長が伸びたときのKVメモリの線形成長を大きく抑える。

### ただしKVだけ捨ててもピークメモリは消えない

長い入力を一度に行列演算へ通すと、フィードフォワードネットワーク（Feed-Forward Network; FFN）など非注意層の中間テンソルが巨大になる。論文のLlama 3.1 8B・32,768トークンの例では、非注意層の中間活性が周期的に大きなメモリピークを作る。

したがって「KVを捨てたから任意長を処理できる」わけではない。PrefillOnlyは注意層と非注意層で実行方式を分ける。

## 手法

### 1. KVキャッシュを層単位で解放する

プリフィル中、第l層の出力が次層へ渡った後、その層のK/Vは将来のデコードに不要である。そこで全層のKVを同時にGPUへ常駐させる通常設計をやめ、寿命が終わったKVを解放する。

これにより、最大入力長（Maximum Input Length; MIL）が「全層KVを保持できる長さ」から解放される。特に単一GPU上で長い入力を扱う場合、テンソル並列やパイプライン並列でKVを複数GPUへ分散しなくても処理できる範囲が広がる。

ただし接頭辞キャッシュ（prefix caching）まで全て捨てると、同じ利用者履歴などの再利用機会を失う。そのため後述の方式では、再利用価値のある接頭辞側と不要な接尾辞側を区別して扱う。

### 2. 非注意層だけをチャンク化する「ハイブリッド・プリフィル」

注意層を小さなチャンクへ分割すると、長文注意の大きなカーネルを細切れにし、GPU効率を落としやすい。一方、線形層やFFNでは各トークン位置の演算を比較的独立に処理できる。

PrefillOnlyはこの違いを使い、

- 注意層：長い入力をまとめて処理し、効率のよい注意カーネルを維持する。
- 非注意層：入力トークンをチャンクへ分けて順に処理し、中間活性のピークを抑える。

という**ハイブリッド・プリフィル（hybrid prefilling）**を行う。

論文実装では連続する線形演算を仮想層のようにまとめ、チャンクごとに実行して出力を結合する。これにより、通常のチャンク化プリフィルのように注意まで細切れにせず、メモリだけを削る狙いがある。

### 3. 接頭辞KVは残し、接尾辞KVを捨てる

推薦では「同じユーザープロファイル + 異なる候補投稿」のように、要求間で長い接頭辞が共有されることがある。このとき全KVを即時廃棄すると接頭辞キャッシュの利点を失う。

PrefillOnlyは**接尾辞KV廃棄（suffix KV cache discarding）**を使い、再利用される接頭辞のKVは残し、要求固有の接尾辞側だけを優先して捨てる。これによりメモリ削減とキャッシュヒットの両立を狙う。

この設計は、プリフィル専用だからKVは全て無価値という単純化を避けている点が重要である。将来の**同一要求内デコード**には不要でも、将来の**別要求**では接頭辞として再利用できるからである。

### 4. 出力長固定を使ったJCT予測

通常の生成では出力長が分からないので、「この要求があと何秒で終わるか」を正確に予測しにくい。プリフィル専用要求では出力が1トークンに固定されるため、入力長、既にキャッシュ済みの接頭辞長などから要求完了時間（Job Completion Time; JCT）を比較的正確に校正できる。

PrefillOnlyは短いJCTの要求を優先することで、長大な要求がGPUを占有して短い要求を待たせる**先頭ブロッキング（head-of-line blocking）**を減らす。

### 5. JCTを継続的に再校正し、接頭辞ヒットも取り込む

ある要求を先に処理すると、その要求が作った接頭辞KVが、待ち行列内の別要求に利用可能になることがある。したがってJCTは到着時に一度計算して固定するだけでは不十分である。

PrefillOnlyはスケジューリング直前に待機要求のJCTを再計算し、現在の接頭辞キャッシュ状態を反映する。これにより、単純な最短ジョブ優先よりキャッシュヒットを活用しやすくする。

さらに「短い要求ばかり優先して長い要求が永久に待つ」飢餓を防ぐため、待ち時間をスコアへ入れる公平性項を持たせる。論文では既定の公平性パラメータを500に設定している。

## なぜ通常のバッチ拡大を主役にしないのか

デコードは重み読み出しが支配しやすいため、複数要求を同時に処理すると、一度読んだ重みを多くのトークンで共有でき、バッチ拡大がスループットを伸ばしやすい。

一方プリフィルは大きな行列積で計算器を使い切りやすい。既に計算律速なら要求をさらにバッチしても演算量はほぼ比例して増え、スループット利得が小さいのに個々の要求の待ち時間は増える。

PrefillOnlyが要求単位のJCTスケジューリングを重視するのは、このワークロード特性による。これは通常のデコード中心サービングと設計思想が逆になる部分である。

## 評価

### 評価条件

論文は二つのプリフィル専用ワークロードと複数のGPU階層を使い、平均遅延と99パーセンタイル（99th percentile; P99）遅延、毎秒問い合わせ数（queries per second; QPS）、最大入力長を測る。

| 項目 | 条件 |
|---|---|
| ワークロード1 | 投稿推薦。20利用者、利用者プロファイル約11K〜17Kトークン、各50投稿 |
| ワークロード2 | 信用判定。60利用者、履歴約40K〜60Kトークン |
| 到着過程 | ポアソン過程 |
| 負荷 | PrefillOnly飽和スループットをxとして 1/4x, 1/2x, x, 2x, 3x, 4x |
| 低価格GPU | 2× NVIDIA L4 24GB、Llama 3.1 8B |
| 中位GPU | 2× NVIDIA A100 40GB、DeepSeek-R1-Distill-Qwen-32B FP8 |
| 高位GPU | 2× NVIDIA H100 80GB、Llama 3.3 70B FP8 |
| 追加条件 | H100はPCIe構成に加えNVLink構成も評価 |
| 比較対象 | vLLM PagedAttention、チャンク化プリフィル、2-wayパイプライン並列、2-wayテンソル並列 |
| キャッシュ | 提案法・比較法とも接頭辞キャッシュを有効化 |

非並列方式では2GPUを1要求に束ねず、GPUごとに独立エンジンを動かし、同一利用者を同じGPUへ送る利用者IDルーティングを行う。

### 遅延とスループット

論文の総括では、PrefillOnlyは比較対象と同等の平均・P99遅延を保ったまま、**1.4〜4.0倍高いQPS**を処理できる。

高負荷になるほど差が広がる。通常の並列化は1要求を2GPUで処理するため低QPSでは1要求の遅延を短くできる場合があるが、要求が増えると同時に処理できる独立ジョブ数が少なくなり、待ち行列が伸びる。PrefillOnlyは単一GPUで長い要求を処理できるため、2GPUを二つの独立サービス容量として使える。

つまり「全負荷域で常に最小遅延」ではなく、**低負荷の単発遅延を一部犠牲にして、高負荷時の収容力と裾遅延を改善する**設計である。

### 最大入力長

KV廃棄と非注意層チャンク化の効果は最大入力長にも現れる。

| ハードウェア / モデル | PagedAttention | チャンク化プリフィル | パイプライン並列 | テンソル並列 | PrefillOnly |
|---|---:|---:|---:|---:|---:|
| L4 / Llama 3.1 8B | 24K | 46K | 72K | 195K | 130K |
| A100 / Qwen 32B FP8 | 11K | 17K | 38K | 77K | 87K |
| H100 / Llama 3.3 70B FP8 | 15K | 25K | 183K | 238K | 97K |

この表は「PrefillOnlyが常に最長」という結果ではない。L4ではテンソル並列の195KがPrefillOnlyの130Kを上回り、H100でも並列方式がより長い入力を扱う。一方、PrefillOnlyは**1要求を複数GPUへ分割せず**L4で130K、A100で87Kまで伸ばし、非並列のPagedAttentionや通常チャンク化に対して大幅な容量改善を得る。

特にA100ではPrefillOnly 87Kが表中最大で、40K〜60Kの信用判定ワークロードを単一GPU経路で処理できる。

### 公平性パラメータの感度

待ち時間を強く優遇するほど、長く待った要求が救済されP99は改善するが、純粋な短JCT順から離れるため平均遅延は悪化する。論文は公平性係数を変えた累積分布も示し、**平均と裾遅延の交換条件が明示的な調整項になっている**ことを確認している。

## 機構ごとの効果

PrefillOnlyの性能は一つの技巧からではなく、容量とスケジューリングの連鎖で生まれる。

- KVを層ごとに捨てる → 長文でGPU容量を節約する。
- 非注意層をチャンク化する → KVを削った後に残る活性ピークを下げる。
- 接頭辞KVだけ残す → 容量節約で再利用率を壊さない。
- JCT予測 → 出力長未知という通常サービングの不確実性を消す。
- 継続JCT校正 → 先に処理した要求が作るキャッシュを次の順序へ反映する。
- 公平性項 → 最短要求優先による飢餓を抑える。

このため、単なる「KVキャッシュを捨てるエンジン」と要約すると、後半のスケジューリング改善を見落とす。

## 既存研究との差

PagedAttentionは可変長KVの断片化を抑えるが、後続デコードに備えてKV自体は保持する。チャンク化プリフィルは長い入力を細かく処理できるが、注意層まで分割するとカーネル効率との交換条件が出る。

テンソル並列・パイプライン並列は複数GPUの容量を1要求へ集約できるため最大入力長には強い。しかしGPU間通信が増え、2GPUで1要求を処理すると高負荷時に独立して処理できる要求数が減る。

PrefillOnlyは「出力1トークン」という意味論的条件を利用することで、汎用エンジンが安全のため維持している状態を削る。したがって適用範囲は狭いが、その範囲では汎用設計より強く最適化できる。

## 限界・適用条件

最大の制約は**本当に1トークン出力で終わること**である。複数トークンを後続生成する要求に同じKV廃棄を適用すると、デコード時に再計算が必要になり逆効果になる。

また評価ワークロードは推薦と信用判定を模した二種類であり、実運用の到着分布・接頭辞再利用率・入力長分布が異なればJCT順序やキャッシュ効果も変わる。

最大入力長では並列方式がPrefillOnlyを上回る構成もあり、「並列化を不要にする」わけではない。必要文脈が単一GPU容量をさらに超える場合は、結局複数GPUを使う必要がある。

低負荷では2GPUを1要求へ使う並列方式の方が単発遅延を短くできる。したがってPrefillOnlyは、特に**高い到着率、長入力、1トークン出力、複数要求を収容したい環境**で価値が大きい。

## サーベイ上の含意

この研究が示す重要な原則は、LLMサービングで「モデルは同じでも、出力契約が違えば必要状態も違う」という点である。分類、リランキング、ガード判定、エージェント内部の二値判定などを、通常チャット生成と同じランタイム経路へ載せる必要はない。

ワークロードを出力長や状態再利用性で分類し、不要なKV寿命やデコード最適化を外すことで、モデル圧縮なしでも容量とスケジューリングを改善できる。この観点は、今後の推論基盤で「1つの汎用サーバ」から用途別実行経路へ分岐する設計を考える上で有用である。
