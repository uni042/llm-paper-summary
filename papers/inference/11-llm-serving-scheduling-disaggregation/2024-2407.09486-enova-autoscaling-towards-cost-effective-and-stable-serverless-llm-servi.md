## 概要

ENOVAは、LLMを複数GPU・複数クラスタで提供する際、サービングの設定を観測データから選び、性能悪化を検出したら再設定する**デプロイ・監視・オートスケーリング**の統合システムである。従来のLLMサービングは、`max_num_seqs`、KVキャッシュ用GPUメモリ、tensor/pipeline並列度、`max_tokens`、レプリカ数、ロードバランサの重みを人手で決めることが多い。これらはGPU種類やタスクの出力長に依存し、単にバッチ数を増やせばスループットが上がるとは限らない。処理可能な要求率が飽和した後は、過大なバッチ上限や長い出力上限が遅延だけを増やす。

ENOVAは処理完了要求数、実行中要求数、要求遅延、GPU/KVメモリ使用率などを観測し、回帰と分布推定から適切な設定を求める。質問を埋め込みでクラスタリングしてタスク別の出力token上限を選び、GPU種類別の処理能力からレプリカ数とルーティング重みを決める。運用中は半教師あり変分オートエンコーダ（VAE）でメトリクスの異常を検出し、過負荷・低負荷に応じて設定を再計算する。

A100 80GBとRTX 4090 24GBのクラスタ上でLlama2 7B/13B/70B、Mistral 7B/8×7Bを評価し、default設定の最大2倍、他の設定探索方式の1.3倍の到着率を維持した。44週間の運用メトリクスによる異常検知ではF1=0.873だった。ただし評価はpoint-adjusted F1であり、実運用事例では異常を10:22に検出してからサービスを10:29に再起動している。無停止・即時の自動スケールを保証する方式ではない。

## 問題設定と動機

### LLMサービング設定の相互作用

連続バッチでは新しい要求を実行中の要求へ合流させ、PagedAttentionで各要求のKVをブロック単位に管理する。`max_num_seqs`を増やすと同時処理可能な要求が増える一方、KVメモリが増え、1反復の計算が重くなる。GPUメモリを過剰に予約すると他サービスを載せにくくなり、少なすぎるとKV不足で要求が待機する。`max_tokens`が長すぎると、終わりのない出力や設計の悪いプロンプトがGPUを占有する。複数GPUへ要求を振るとき、単純な均等分配はA100と4090の性能差を無視する。

著者はスループットが一定の上限へ達すると、バッチ上限をさらに増やしても処理量はほぼ変わらず、待ち要求と応答遅延が急増することを観測した。したがって最大スループットだけを目的とする設定探索では、利用者が実際に感じる遅延や過負荷時の安定性を最適化できない。ENOVAはLLMの推論実行を計測し、各設定の依存関係を推定する。

### タスク別の出力長と異常検知

数学問題、プログラミング、一般対話では適切な出力長の分布が異なる。全要求へ一律の`max_tokens`を設定すると、短い応答で済むタスクにも過大な上限を与えることになる。また過負荷やメモリ不足の異常は実運用では稀で、教師あり分類に十分なラベルが集まらない。通常メトリクスだけで学習した異常検知器は、少数の異常値が混入すると検出性能が悪化し得る。

ENOVAは少量の異常ラベルを利用する半教師ありVAEと、極値理論に基づく閾値設定を使う。異常を検出したら単純にGPUを追加するだけでなく、まずバッチ上限やGPUメモリ割当などの設定を見直すことで、レプリカを増やさずに性能を回復できる場合を狙う。

## 手法

### 1. 設定推薦の対象

ENOVAは次の設定を制御する。モデルのtensor/pipeline並列度`parallel_size`、サービスに割り当てるGPUメモリ`gpu_memory`、同時処理する最大系列数`max_num_seqs`、タスク別の最大出力token数`max_tokens`、GPU種類別のレプリカ数`replicas`、各レプリカへのロードバランサ重み`weights`である。

重みメモリとKVの概算は `mem≈params×sizeof(dtype)+max_num_seqs×seq_length×token_mem+others` と書けるが、著者はモデル・GPU・タスクが多様なため、この単純式だけで設定を固定しない。実際の観測から同時実行数、完了率、メモリ使用率の関係を学習し、設定を推定する。

### 2. `max_num_seqs`の推定

単位時間当たり完了要求数`n^f`と実行中要求数`n^r`を時系列として収集する。`n^f=f(n^r)`を通常の最小二乗回帰（OLS）で近似し、t検定で両者に有意な関係が残っているか調べる。完了率が実行中要求数へ依存しているならまだ飽和前、依存が弱くなれば処理上限へ達した可能性が高いと判断する。

飽和前後の状態に応じ、完了率と要求実行時間の分布を正規分布または極値分布で近似し、カーネル密度推定（KDE）から上限要求率`n_limit`と対応する実行時間`t_limit^r`を求める。次に `max_num_seqs≈n_limit×t_limit^r` でバッチ上限を決める。これはLittleの法則に近い発想であり、負荷が飽和したときの実測処理能力と要求滞在時間を使って同時実行数を見積もる。分布推定や観測窓の選び方に依存するため、厳密な全負荷最適値の保証ではない。

### 3. GPUメモリと並列度

GPUメモリ利用率`m^u`と同時実行要求数`n^r`の関係を `m^u=g(n^r)`としてOLSで推定する。上で決めた`max_num_seqs`を代入し、必要な`gpu_memory≈g(max_num_seqs)`を求める。GPU種類のメモリ容量を見て必要な`parallel_size`を選ぶ。KVキャッシュを過小割当して要求を待たせることと、過大割当で他サービスの利用余地を奪うことの両方を避ける。

モデルの重み、KV、ランタイムの作業領域を含む実測関係を使うため、単なるパラメータ数からの見積りより負荷に適応できる。ただし実際の分散並列化ではGPU間通信や並列度変更時の再ロードが必要であり、観測したメモリ関係だけで全ネットワーク条件の性能が決まるわけではない。

### 4. タスク別`max_tokens`

各要求のテキストを`bge-large-en`で埋め込み、cosine similarityで要求グラフを構築する。グラフのmodularityを最大化するcommunity detectionで似た目的の要求をクラスタリングし、新しい要求は各クラスタ中心への類似度で割り当てる。各クラスタについて出力token長の分布をKDEで推定し、適切な`max_tokens`を決める。

これにより数学問題やコード生成などのタスク別に必要な出力長を設定できる。固定256tokenなどの一律上限では長すぎる出力を抑えられない場合がある。一方、短すぎる上限を選ぶと正しい回答を途中で切る危険があるため、実験ではGSM8K正答率とMBPP pass@1も確認する。クラスタ外の未知タスクや極端な長文生成へ一般化できるとは限らない。

### 5. レプリカ数とルーティング重み

GPU種類ごとに推定した最大処理要求率`n_limit^i`と必要メモリ、利用可能GPU台数を用い、線形計画でレプリカ数を選ぶ。GPU容量に対する必要メモリの適合度をスコア化し、配置費用を抑えつつ要求を処理できる組合せを探す。ロードバランサの重みは推定した各レプリカの処理能力に比例させ、A100と4090などの異種GPUへ均等に振り分けて片方だけを過負荷にする事態を避ける。

GPU種類が増えたときに配置先を再選択できるが、線形計画の結果はモデルの推定処理率とメモリ需要に依存する。実際の料金体系やネットワーク越し通信費用まで最適化したという意味ではない。

### 6. 半教師ありVAEによる性能異常検知

GPU利用率、GPUメモリ利用率、到着要求数、待ち要求数、完了数、同時実行数、要求遅延などを時系列で収集し、正規化してVAEへ入力する。少量の正常・異常ラベルを使って変分下界（ELBO）の再構成項とKL項を重み付けし、異常点が通常分布から離れるよう学習する。KL重みにはPI制御で更新する係数`β(k)`を使う。

推論時はVAEの事後分布と事前分布のKL divergenceを異常スコアとし、peaks-over-threshold法で閾値を自動設定する。閾値を超えた場合は、観測値と再構成値の平均差から過負荷か低負荷かを判断する。異常を検出すると設定推薦を再実行し、マルチクラスタ/ローカルクラスタのjob schedulerを通じてサービスを再配備する。

### 7. システム実装

DeployerはvLLMとTensorRT-LLMを対象とし、複数クラスタへモデルを配置する。監視はNVIDIA DCGM exporter、Prometheus exporter、OpenTelemetry collectorでハードウェア・推論・ロードバランサの情報を集め、時系列DBとストリーム処理へ送る。異常検知器と設定推薦器が必要に応じてデプロイ設定を変更する。推論カーネル自体を新規実装する研究ではなく、**既存サービングエンジンを観測・設定・再配備する制御層**を設計した研究である。

## 評価

### 実験条件

| 項目 | 原著の設定 |
|---|---|
| GPUクラスタ | A100 80GB×8、RTX 4090 24GB×8 |
| モデル | Llama2 7B/13B/70B、Mistral 7B、Mixtral 8×7B |
| タスク | GSM8K、MBPP、zero-shot/few-shot/CoTのprompt |
| 到着 | Poisson到着、15分間の高負荷trace |
| 設定推薦比較 | default、COSE（Gaussian Process Bayesian Optimization）、DDPG（強化学習） |
| 推論指標 | 出力token/GPU/秒、要求実行時間/出力token、処理可能到着率、GSM8K accuracy、MBPP pass@1 |
| 異常検知 | 44週間の実運用メトリクス、前22週学習・後22週評価、322,560点・異常251点 |
| 検知比較 | USAD、SDF-VAE、Uni-AD |
| 実運用事例 | RTX 4090上のMistral-7B、GPUメモリ割当90→95% |

COSEとDDPGは独自の配置エンジンを持たないため、比較ではENOVAのデプロイ機構を共通利用する。これにより設定選択の差を比較している。精度評価はGSM8KとMBPPで行い、長文対話や複雑なツール利用の正答率を網羅するものではない。

### サービング性能と設定推薦（Fig.4、Table III）

| 比較 | 主結果 | 解釈 |
|---|---|---|
| ENOVA vs default | 維持可能な要求到着率が最大2.0倍 | 過大なバッチ上限・出力上限や偏ったルーティングを避ける |
| ENOVA vs COSE/DDPG | 最大1.3倍の到着率 | ほぼ同じスループット上限でも遅延爆発を遅らせる |
| 5モデルのthroughput | ENOVA、COSE、DDPGで大差なし | GPU演算上限を超える処理能力を生むわけではない |
| GSM8K/MBPP精度 | defaultの最大出力上限と有意差なし | タスク別max_tokensが実験では正答を大きく切らなかった |

原著はLlama2-7BでA100の`max_num_seqs`をENOVA 144、COSE 502、DDPG 452と推薦する例を示す。COSE/DDPGは大きい同時実行数を選んでも最大throughputはほぼ同じで、過負荷時に待ち要求が増え遅延が急増する。ENOVAはより小さい同時実行上限とタスク別出力長、処理能力に応じたロードバランサ重みで遅延を抑える。要求到着率2倍という結果は**カーネル単体が2倍速くなったことではない**。

### 異常検知性能（Table IV）

| 方式 | Precision | Recall | F1 |
|---|---:|---:|---:|
| USAD | 0.767 | 0.586 | 0.664 |
| SDF-VAE | 0.683 | 0.829 | 0.749 |
| Uni-AD | 0.805 | 0.753 | 0.778 |
| ENOVA | 0.899 | 0.849 | 0.873 |

ENOVAのF1はUni-ADより0.095高い。ただし評価はpoint-adjustedで、異常区間内のどこか一点を検出すれば区間全体を正検出として扱う方式である。通常の点単位F1と同じではなく、異常が実際に起きた瞬間から何秒後に検出したかという検出遅延も別の指標となる。データは322,560点に対して異常251点と非常に不均衡であり、異常検知器の学習と閾値選択の安定性は環境依存である。

### 実運用のオートスケーリング（Fig.6）

RTX 4090 24GBでMistral-7BをGPUメモリ割当90%で提供していたところ、10:20に要求率が増え、KVC利用率が100%へ達して新規要求が待機した。ENOVAは10:22に異常を検出し、必要メモリを再推定して割当を95%へ増やした。**サービスを再起動したのは10:29**であり、検出から約7分、負荷増加から約9分を要した。再配備後はレプリカを追加せず、約1.6倍の要求を処理できた。

この事例は、設定を少し変えるだけで過負荷を緩和できることを示す一方、オートスケーリングが即時・無停止で行われたわけではないという負の運用特性も示す。ミリ秒単位の厳しいSLOであれば、検出・再起動の数分間の遅延をどう扱うかが重要になる。

### パラメータと追加検証（Fig.7–8）

`max_num_seqs`を増やすと、完了要求数/秒は最初増えるが、ある点で飽和する。一方KVキャッシュのGPUメモリ使用量は増え続けるため、飽和後の大きなバッチ上限は効率的でない。GSM8K、MBPP、ARC、MC_TESTの埋め込みをPCAで可視化すると、同種タスクはまとまり異なるタスクが分離する傾向を示した。これによりタスク別`max_tokens`設定の可能性を示すが、未知タスクや多言語・混合タスクでも同様に分離できるとは限らない。

## 既存研究との差

COSEはGaussian Process Bayesian Optimizationでサービング設定を探索し、DDPGは強化学習で設定を推薦する。これらは処理量を高める一方、モデルの推論内部でどの資源が飽和したかを直接解釈しにくい。ENOVAは完了要求率と実行中要求数、KVメモリとバッチ数の関係を観測し、LLM固有の連続バッチ・PagedAttention・出力長分布に合わせて設定を選ぶ。

一般的なクラウドautoscalerはCPU/GPU使用率や到着率の閾値でレプリカ数を増減させる。ENOVAは異常を検出しても、まずバッチ上限・GPUメモリ割当・タスク別出力上限・ルーティング重みを再設定し、**レプリカ追加なしで回復できる場合**を扱う。半教師ありVAEで稀な異常を検出し、既存vLLM/TensorRT-LLMのデプロイ層へつなぐ点が特徴となる。

## 限界と未評価事項

著者自身は、評価が特定のタスク種類とGPUデバイスに限られると述べる。異常検知はpoint-adjusted F1であり、点単位の検出品質や検出から復旧までの実時間を保証しない。実運用の再起動に約7分かかる事例があり、継続的な低遅延サービスでは停止・移行戦略が別途必要となる。

タスク別`max_tokens`は出力長分布が安定しているという仮定に依存し、未知の複雑な要求や想定外の長文生成では正答を途中で切る可能性がある。完了要求率の回帰は観測窓や到着分布に依存し、突然の負荷変化や新しいGPUで再較正が必要となる。COSE/DDPGとの比較はENOVAのデプロイ機構を共通利用する特定設定であり、他のオートスケーラ全体に対する一般的な優位を証明しない。監視、VAE、再配置、GPU追加の総コストやクラスタ障害への耐性も十分に評価されていない。

## 主要結果と研究上の位置付け

ENOVAの主要な貢献は、LLMサービングの設定を単なるGPU使用率の閾値ではなく、**連続バッチの処理上限、KVメモリ、タスク別出力長、異種GPUのルーティング**から決め、異常検知と再配備を一つの制御ループへ接続したことである。実機での要求率2倍、異常検知F1 0.873、メモリ割当変更による1.6倍の回復を報告する。一方、再起動には数分かかり、point-adjusted検知評価と未知負荷への一般化に制限がある。サービスの制御面を効率化する研究であり、LLM本体の演算量を直接減らす手法ではない。
