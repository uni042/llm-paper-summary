# Enabling Efficient Batch Serving for LMaaS via Generation Length Prediction

> 入力長・アプリ・利用者特徴から生成長を予測し、近い長さを適応バッチ化してHRRNで順序付けするMagnusにより、スループット最大234%向上・応答時間最大89.7%削減を達成する。

## 概要

LLMをサービスとして提供する言語モデル・アズ・ア・サービス（Language Model as a Service; LMaaS）では、多数の独立した要求を一つのGPUバッチへまとめることで重み読出しを共有し、処理量を高める。ただし各要求が何トークン生成するかは開始前には分からず、生成長が大きくばらつく。

論文が対象とする固定バッチ配信では、バッチ中の要求を一緒にデコードし、全要求が終わるまで次バッチへ進まない。このとき20トークンで終わる要求と500トークン生成する要求を同じバッチへ入れると、短い要求の計算自体は終わっていても、利用者は長い要求の終了まで待たされる。これが**バッチ内ストラグラ（straggler）**である。

もう一つの問題はメモリである。生成が長い要求ほど鍵・値キャッシュ（Key-Value cache; KVキャッシュ）が増える。生成長が不明なまま大きい固定バッチを組むと途中でメモリ不足（Out Of Memory; OOM）になる危険があるため、配信側は最悪ケースを見込んで小さいバッチサイズを選ばざるを得ない。実際の要求が短いとGPUメモリが余り、同時処理数を増やせたはずの容量を使えない。

Magnusはこの二つを、**生成開始前に生成長を予測する**ことで同時に扱う。著者らは多数のLMaaSアプリケーションで、生のユーザー入力長と生成長に正の相関があることを観測する。ただし同じ入力長でも、要約・翻訳・コード生成などアプリケーションが違えば出力長は変わり、同じアプリでも利用者の使い方によって分布が違う。そこで入力長だけでなくアプリケーションレベル・利用者レベルの意味特徴を予測器へ加える。

予測後は、近い生成長の要求を同じバッチへまとめて終了時刻を揃え、予測されるKVメモリ量に応じてバッチサイズを変える。さらに完成した複数バッチの実行順を最高応答比次（Highest Response Ratio Next; HRRN）で決め、短いバッチだけを優先して長いバッチが永遠に待つ飢餓を防ぐ。

IEEE ICWS 2024の実機評価では、既存の先着順（First-Come, First-Served; FCFS）・固定バッチ系の比較に対し、要求スループットを最大234%改善し、応答時間を最大89.7%短縮する。Magnusの本質はモデル演算を高速化することではなく、**出力長という将来の資源消費量を予測して、バッチ形成と待ち行列順序の両方を変えること**にある。

## 背景: 生成長が分かると二つの無駄を同時に減らせる

自己回帰LLMでは、各生成反復でバッチ中の未完了要求を1トークンずつ進める。固定バッチ方式では、ある要求が先にEOSへ到達すると、そのスロットは後続反復で仕事をしなくなる。それでも同じバッチの長い要求が終わるまで、新しい要求を入れない設計ではGPU並列度が徐々に下がる。

生成長が似た要求だけをまとめれば、バッチ内の要求がほぼ同じ時期に終了するため、この「途中から空くスロット」を減らせる。したがって長さクラスタリングは応答時間だけでなくGPU利用率にも効く。

一方、KVキャッシュは各要求の過去トークン数に比例して増える。開始時に最終生成長を予測できれば、そのバッチがピーク時に必要とするKV容量を見積もれる。短い要求群なら多数を詰め、長い要求群なら少数に抑えることで、OOMを避けながら平均バッチサイズを引き上げられる。

つまり生成長予測は「何秒かかるか」の予測だけではなく、**将来の計算反復数とメモリ使用量の両方を予測する代理変数**になる。

## 問題設定

Magnusは、到着した要求 $r_i$ について未知の生成長 $l_i$ を予測し、その推定値 $\hat l_i$ から三つを決める。

第一に、どの要求同士を同じバッチへ入れるか。第二に、その長さ群に対して何件までバッチへ入れてもGPUメモリを超えないか。第三に、複数の準備済みバッチのうちどれを次に実行するかである。

予測誤差があるため、単純に予測値を絶対視すると、長さを過小評価した要求がOOMや長いストラグラを引き起こす。そのためMagnusは予測精度そのものだけでなく、実配信でのスループット・応答時間まで通して評価する。

## 手法

### 1. 入力長を生成長の最初の説明変数にする

著者らはLMaaSの複数アプリケーションを分析し、生の入力長と生成長が正に相関するケースが多いことを示す。要約なら入力文書が長いほど出力要約もある程度長くなり、コードや対話でも入力規模が生成量の手掛かりになる。

入力長はトークナイズ時点で無料に近く取得できるため、低コストな特徴である。ただし相関の傾きは用途ごとに異なり、入力長だけでは同じ200トークンのプロンプトが「一語で答える分類」なのか「詳しく説明する質問」なのか区別できない。

そこでMagnusは入力長を土台としつつ、後述のアプリ・利用者特徴で補正する。

### 2. アプリケーション・利用者の意味特徴を加える

LMaaSではAPIの背後に複数アプリケーションがあり、それぞれプロンプトテンプレートと期待出力形式が異なる。Magnusはアプリケーションレベルの特徴を使い、同じ入力長でも用途ごとの生成長分布を分ける。

さらに利用者レベルの意味特徴を入れる。同じアプリでも「簡潔に答えてほしい利用者」と「詳細な説明を求める利用者」では生成長が偏る可能性があるためである。

入力は要求到着時に分かる情報だけで、出力は予測生成長である。将来のモデル内部状態を逐次予測するのではなく、スケジューラが必要な粗い長さ推定へ問題を限定することで、オンライン予測費用を小さくする。

### 3. 似た予測生成長を同じバッチへまとめる

予測値 $\hat l$ が近い要求を同じ長さ区間へ入れ、バッチ内の終了タイミングを揃える。これにより短い要求が長い要求を待つ時間と、生成途中で空くバッチスロットを減らす。

この機構の出力は単なる順序ではなく「長さが均質なバッチ」である。予測誤差が多少あっても、ランダムに長短を混ぜるより分散を下げられればストラグラは減る。

逆に生成長との相関が弱いアプリや分布変化後では長さ群が崩れ、利得が小さくなる。したがって予測器の再校正が運用上必要になる。

### 4. 予測されたピークKV量からバッチサイズを適応させる

固定バッチ方式は「最も長い要求が来てもOOMしないサイズ」に合わせるため保守的になる。Magnusは各バッチの予測生成長からピークKV使用量を見積もり、短い要求群ではより多く、長い要求群ではより少なく詰める。

これによりGPUの空きメモリを同時要求数へ変換する。短いバッチのサイズを増やせれば重み読出しをより多くの要求で共有でき、スループットが上がる。

予測過小時にはメモリ安全余裕が必要であり、予測器の平均誤差だけでなく上側誤差が重要になる。Magnusの配信評価は、この不確実性を含めても固定小バッチより利得が残るかを見る。

### 5. バッチ間をHRRNでスケジュールする

生成長が分かると最短処理時間優先（Shortest Job First; SJF）で短いバッチから処理したくなるが、それだけでは長い要求が新しい短い要求に追い越され続ける可能性がある。

最高応答比次（HRRN）は、おおむね「待ち時間 + 予測処理時間」を予測処理時間で割った応答比を使う。短い仕事は高い比率を得やすい一方、長く待っているバッチは待ち時間の増加によって優先度が上がる。

Magnusは長さ予測をバッチ形成だけでなくこの処理時間推定にも使い、平均応答時間を下げつつ飢餓を避ける。

「234%改善」はスループットが元の3.34倍という意味の表現であり、「234倍」ではない。同様に89.7%は応答時間の削減率である。いずれも論文の要求分布・ハードウェア・固定バッチ型配信系に依存する。

現在のvLLM等で一般的な連続バッチ処理では、完了した要求のスロットへ途中から新要求を入れられるため、固定バッチのストラグラ問題は弱まる。そのためMagnusの絶対利得を現代ランタイムへそのまま移すのではなく、「生成長予測をメモリ予約・優先度・プリフィル配置へ使う」という考え方を分離して見るべきである。

## 既存研究との差

先着順固定バッチは要求の将来長を使わないため実装が単純だが、長さのばらつきをバッチ内無駄として受け入れる。Magnusは要求到着時の特徴から将来の生成長を予測し、その予測をスケジューラの一次情報にする。

SJFのような既知のジョブ長スケジューリングは、ジョブ処理時間が既知であることを前提とする。LLMでは生成長が未知なので、Magnusはまずその推定器を作り、誤差を含む予測長でHRRNを実用化する。

後続の生成長予測型LLMサービング研究はトークン単位の連続バッチ、サービス品質目標（Service-Level Objective; SLO）、プリフィル/デコード分離などへ予測を使う。Magnusはそれらより早い段階で、生成長を「バッチ均質化・メモリ適応・公平な順序付け」の三用途へ接続した点が特徴である。

## 限界・実装状況

最大の前提は、入力長・アプリ・利用者特徴と生成長の相関が運用中も保たれることである。新アプリ追加、プロンプト形式変更、モデル更新、利用者行動変化によって分布がずれると予測誤差が増える。

過小予測は特に危険で、想定以上にKVキャッシュが伸びるとバッチメモリが不足する。実装では安全マージンや途中退避などと組み合わせる必要がある。

また論文の主要問題設定は固定バッチ型である。連続バッチ、PagedAttention、チャンク化プリフィル、プリフィル・デコード分離がある最新ランタイムではボトルネック構造が変わるため、同じ234%/89.7%を期待できない。一方、生成長予測自体はKV予約量やSLOスケジューリングの特徴として再利用できる。
