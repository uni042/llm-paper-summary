# Albireo：推論のCPU処理とsamplingを重畳・並列化してTPの非スケーラブル部分を縮小

## 概要

大規模言語モデルのTensor Parallelism（TP）は、重みとKVキャッシュを複数GPUへ分割し、1GPUで収まらないモデルを実行できる。一方、TP度を上げるとGPU間通信やCPU管理処理が増え、GPU forwardだけを並列化しても全体スループットは線形に伸びない。Albireoは、推論エンジンの各イテレーションに含まれるスケジューリング、入力準備、出力処理、samplingを、forwardと並行して実行できるようにするシステムである。

原著は、TP度を増やすことでモデル重みの複製が減り、KVキャッシュ用の総メモリ余裕が増える利点と、通信・非並列部分が増える欠点の両方を扱う。固定GPU台数で最大のスループットを得るTP度を経験的な \(t_e\) と呼ぶ。Albireoは非スケーラブル部分を削り、\(t_e\) をより大きなTP度へ移せると主張する。モデルの構造や重みを変更するのではなく、推論ランタイムの依存関係を組み替える設計である。

H100 NVLink環境の主評価では、vLLM比スループット改善がモデルサイズ別に約1.3倍（7B級）、1.5倍（13/14B級）、1.7倍（32B級）、1.9倍（70/72B級）と報告される。TPOTは22〜48%低下するが、prefill主体のTTFTはほぼ変わらない。したがって「すべての推論レイテンシが48%短縮する」と一般化するのは誤りである。

## 問題設定

### GPU forward以外の処理がAmdahlの限界を作る

一般的な自回帰推論は、各イテレーションで(1)スケジューリング、(2)入力準備、(3)GPU forward、(4)sampling、(5)出力更新・detokenizationを繰り返す。TPが主に高速化するのは(3)であり、(1)(2)(4)(5)が逐次処理のままだと、GPUの計算能力を増やしても残りの時間が律速する。原著Figure 3では、Qwen-2.5-32B、TP4、batch128のvLLMにおいて、スケジューリング約4ms、入力約4ms、forward約21ms、sampling約6ms、出力約0.5msで、forward以外が全体の約41%を占める。

ただしTPの効果は単純なAmdahl則だけで決まらない。TP度を上げると、モデル重みを分割した分だけGPU上のKVキャッシュ余裕が増え、リクエストのpreemptionやCPUへのKV swapが減る可能性がある。Qwen-2.5-32BのFP16重みを約64GBとすると、80GB GPUを2基使う場合、TP1の2インスタンスではKV用合計約32GBだが、TP2の1インスタンスでは約96GBが残るという原著の例がある。これはモデルを一つのTPインスタンスで動かすか、独立インスタンスを複数置くかという配置上の違いである。

### 固定GPU予算での最適TP度

著者らは、1インスタンスのTP度 \(t\) に対するスループットを \(T(t)\) とし、GPU総数 \(N\) なら \(N/t\) インスタンスの総スループットを比較する。TPを増やすメモリ利得が通信損失を上回る範囲では、総スループットが改善する場合がある。経験則として \(t_e=\lceil4M/C\rceil\)（モデル重みサイズ \(M\)、GPU一基容量 \(C\)）を示すが、これは原著の測定範囲で検証したヒューリスティックであり、あらゆるGPU、量子化方式、ワークロードに対する数学的な最適解ではない。

## 手法

### 1. 楽観的な1イテレーション先行スケジューリング

従来の同期的なschedulerは、前イテレーションで生成したトークンや終了判定を待ってから次を組み立てる。Albireoは、次の1イテレーションもリクエストが続くと楽観的に仮定し、先にKVブロック数と系列長を見積もってスケジュールする。prefillなら予定チャンク数、decodeなら1トークン増加を使う。各系列のexpected length、current length、new token countをイテレーションごとに区別して保持し、非同期処理中の状態混同を避ける。

この予測は終了時の1回だけ外れるため、単純なリクエストでは予測成功回数が多い。誤予測時には最大1ブロック余分に割り当てる可能性があり、後で解放する。先読みを何イテレーションも進めると新着prefillや終了条件で再スケジュールが増えるため、あえて1イテレーション先に限定する。CPU schedulingをGPU forwardへ重ねることが狙いで、未来の生成トークン内容そのものを予測する投機的復号とは異なる。

### 2. 早期feedbackによる入出力処理の分離

次イテレーションの入力は、前イテレーションのsampling結果のトークンIDを必要とする。従来はsampling後に出力更新が完了してから入力準備するため、処理が直列化される。AlbireoはsamplingでトークンIDが得られた時点でinput processorへ直接送り、未確定部分のプレースホルダを埋める。これにより、CPU上の出力処理・detokenizationを待たずに次のGPU入力を作れる。

各タスクは順序付きキューを介して連結され、出力側は終了判定と状態更新を並行して進める。原著付録では出力処理のスレッド化に加え、単一トークンと頻出トークン対のlookup表を用いた高速detokenizationを説明する。重要な実装上の費用として、頻出トークン対を10億件キャッシュする表は**モデルごとに約30GB**のメモリを要すると報告される。これはGPUのKVキャッシュ削減とは別のメモリ消費であり、CPUメモリ制約の厳しい環境では無視できない。

### 3. Sequence-parallel sampling

通常のTPでは、語彙次元に分割したlogitsを一つのdriver GPUへ集めてsamplingすることが多い。すると他のGPUがsampling中に待機し、batchが大きいとdriverのsamplingとmetadata配布が律速する。Albireoはsamplingをリクエスト系列の次元で分割し、各GPUが担当系列の次トークンを独立に選ぶ。forward後のlogitsをall-to-allで交換し、語彙次元の分割から系列次元の分割へ並べ替える。

sampling metadataのscatterはGPU forward中に重ね、最終的に集めるのは系列IDと生成token IDだけに抑える。原著は256リクエストの結果収集遅延を平均約200μsと報告する。再現性のため、固定seed下で各GPUに同じ乱数列を事前生成し、担当系列に対応する区間を消費する。この設計は乱数配布通信を減らす代わりにリクエスト当たり約128KBの追加GPUメモリを使う。collective通信の都合でbatch数がTP度で割り切れない場合はパディングして、結果からダミーを除去する。

### 4. vLLMへの組込み

Albireoのコアは約8,500行のC++プラグインで、原著はvLLMへの統合に約200行の変更を要したと述べる。GPU forwardの重みやattention構造は変更しない。CPU scheduling、入力準備、出力処理とsamplingを新しいキュー・並列機構へ置き換える。GPU演算を高速化するFlashAttention系カーネルの代替ではなく、既存のforwardが高速化するほど目立つ周辺処理を隠す技術である。

## 評価

### 実験条件

| 項目 | 一次論文の条件 |
|---|---|
| GPU環境 | H100 80GB×8 NVLink、A100 80GB×8 NVLink、A100 80GB×8 PCIe |
| CPU/RAM | Intel Xeon Platinum 8468、192論理コア、RAM 2TB |
| ベースライン | vLLM 0.11.2、SGLang 0.5.5。生産環境・resource評価は主にvLLM比較 |
| モデル | Llama-2 7B/13B、Qwen-2.5 7B/14B/32B/72B、QwQ-32B、Llama-3.1-70B。FP16 |
| TP度 | tiny 1、small 2、moderate 4、large 8を主設定とし、感度実験で変更 |
| 負荷 | Databricksのpromptを抽出。主に1GPU当たりbatch32。オンライン負荷変動も評価 |
| 指標 | tokens/s、TPOT、TTFT、GPU利用率、電力・エネルギー、tail latency |

GPU総数を固定してTP度とインスタンス数を変えるため、1インスタンスのtokens/sとノード全体のtokens/sは異なる。主なスループット改善は高負荷条件で測られ、軽負荷時の相対改善やSLO適合をすべて代表するものではない。FP16を用いるので、4bit量子化モデルや12GB GPUへの結果の外挿には注意が必要である。

### モデル規模別のスループットとGPU差

| 条件 | vLLM比の報告改善 | 備考 |
|---|---:|---|
| H100 NVLink・tiny 7B級 | 約1.3倍 | TP1でsampling並列化の利点が小さい |
| H100 NVLink・small 13/14B級 | 約1.5倍 | 非同期処理の寄与が中心 |
| H100 NVLink・moderate 32B級 | 約1.7倍 | 非同期処理と並列samplingの両方が寄与 |
| H100 NVLink・large 70/72B級 | 約1.9倍 | TP8で非並列部分の削減効果が大きい |
| A100 NVLink | 最大約1.7倍 | H100よりforward比率が高い |
| A100 PCIe | 最大約1.4倍 | GPU間通信帯域の制約が強い |

AlbireoはQwen-2.5-32Bなどのmoderateモデルで、最適なTP度を従来の2から4へ、largeモデルでは4から8へ押し上げると報告する。これはGPU台数を増やせば無制限に線形高速化するという意味ではなく、KVメモリ余裕と通信費用のバランス点を移したということ。通信が遅いA100 PCIeでは改善幅が小さいという負の条件もある。

### レイテンシと本番運用

TPOTはH100環境でvLLMより平均22〜48%低い。最大の改善はQwen-2.5-72Bで、decodeの1トークンあたり時間を短縮した。一方、TTFTはprefillの大規模GPU forwardが支配するため、vLLMとほぼ同等と著者らが明記し、詳細数値を省略している。したがって「レイテンシ48%削減」は主にTPOTのことで、TTFT改善を示す数字ではない。

本番MaaSでは、負荷が高い場合にQwQ-32Bで約1.7倍、Llama-3.1-70Bで約2倍のスループットを報告する。QwQ-32BのTPOT P99はvLLM271msからAlbireo75ms、P99.9は298msから76msとなった。ただしこれは著者らの単一サービス環境で1週間観測した結果であり、異なるモデル、利用者分布、GPUネットワークで同じtail改善が再現する保証はない。

### 非並列処理時間・利用率・電力

原著Table 1のQwen-2.5-32B、TP4では、vLLMのスケジューリング約4ms、入力約4ms、sampling約6ms、出力約0.5msに対し、Albireoはそれぞれ約5μs、40μs、1.5ms、25μsと記載する。ここでμsの値はCPU処理が消滅したのではなく、forwardとの重畳後にクリティカルパス上へ残る時間として理解すべきである。同期的なCPU管理のブロック時間は約8.5msから70μs程度へ減り、samplingは4GPU並列で約75%短縮された。合計で非スケーラブル部分を89%以上削減したと報告する。

Qwen-2.5-32BではGPU利用率が28%改善した。256同時要求の電力評価では、平均GPU電力15%減、処理時間47%減、総エネルギー54%減が報告される。電力15%減とエネルギー54%減は異なる指標であり、実行時間の短縮が総エネルギー減に寄与する。電力測定は20ms間隔のGPUサンプリングであり、CPU・ネットワーク・冷却を含む施設全体の電力量ではない。

## 既存研究との差

vLLMやSGLangはPagedAttention、連続batching、KV管理などの基盤を提供する。DistServeやSarathi-Serveはprefillとdecodeの分離・重畳、FlashInferはattentionやsamplingのGPUカーネルを最適化する。Albireoはモデルforwardの外側にあるscheduler、input/output、samplingの依存関係を崩し、TP時の非スケーラブル部分を減らす。KV圧縮、量子化、専門家オフロードのようにモデル重みやKVの内容を変える方式ではない。

実務上は、すでに複数GPUでFP16大規模モデルを配備し、decodeのCPU管理やsamplingが律速している高負荷サーバで価値が大きい。逆に単一GPU・小モデル・prefill主体の短い生成では利点が限定される。複数GPUの通信特性、CPUコア数、batch数、KVブロック長、tokenizerが性能を左右するため、推論ランタイムの置換だけで常に同じ倍率が出るとは限らない。

## 限界・負の結果

第一に、評価対象は**単一ノード内のTP**であり、マルチノードのall-reduce、TPとPPの混合、pipeline bubble、遠隔ネットワーク通信は直接扱わない。DeepSeek V3のように複数ノードへ分割が必要な巨大モデルは主評価から除外される。本文の最適TP度ヒューリスティックをマルチノードへ適用することはできない。

第二に、TTFTはほぼ改善しない。prefillのGPU forwardが支配するため、非同期schedulerとsampling並列化が主に効くのはdecodeのTPOTである。長いpromptに対して最初の応答を早くする用途と、長い出力を高速生成する用途を分けて評価する必要がある。

第三に、低TP度ではsampling並列化の利点が小さく、PCIe接続のA100ではNVLinkより改善が低い。メモリが潤沢でKV swapが発生しない軽負荷条件では、TPを増やすことのメモリ利得も小さくなり得る。1.9倍というheadlineは最大級のモデル・高負荷条件を代表する値である。

第四に、非同期処理の実装は状態管理が複雑で、終了条件の誤予測、KVブロックの過剰予約、乱数の再現性、tokenizerのスレッド安全性に対処する必要がある。特に付録の頻出token-pair lookupは約30GB/モデルのメモリを使う。GPUの省メモリだけでなく、CPUメモリや追加の管理構造も運用費用に含めるべきである。

第五に、評価はFP16、H100/A100、vLLM 0.11.2およびSGLang 0.5.5を基準とする。新しい推論エンジンや4bit量子化モデル、CPU/GPU混合オフロード、Windowsローカル環境への性能外挿は未検証である。ユーザーのワークロードでのP99、同時実行数、メモリ帯域、CPU負荷を測らずに採用判断してはならない。
