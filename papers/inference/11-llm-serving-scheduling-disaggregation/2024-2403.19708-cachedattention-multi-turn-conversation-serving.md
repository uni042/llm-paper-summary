# Cost-Efficient Large Language Model Serving for Multi-turn Conversations with CachedAttention

> multi-turn conversationの過去KVをrequest終了後もDRAM / SSDへ保存し、次turnで使うlayerのKVを少し前からGPUへ戻すことで、history全体の再prefillとstorage待ちを減らすstateful serving手法。

## 概要

multi-turn conversationでは、次turnのpromptが前turnまでのhistoryをほぼそのまま含むため、stateless servingは同じhistory tokenのKV cacheを毎回再計算する。ShareGPTを使った分析では、長い会話になるとprefill costの最大99%がこの重複計算になり得る。

CachedAttentionは、request終了時にKV cacheを捨てず、**GPU・CPU DRAM・SSDをまたぐconversation用cacheへ保存し、次turnで再利用する**。

GPU memoryだけでは全sessionを保持できないため、最近使うstateだけGPUへ置き、しばらく使わないconversationのKVはDRAMやSSDへ移す。次turnが近づいたら必要なKVをGPUへ戻す。

単に保存するだけではSSD / DRAMからの読込が新しい待ち時間になるため、**次にどのsessionを実行するかというscheduler情報を使って先読みし、GPU計算とstorage transferを重ねる**のが重要になる。

## 問題設定

multi-turn servingでKV reuseを実用化するには、以下を同時に解く必要がある。

- 全sessionのKVをGPUへ常駐させられない
- DRAM / SSDからKVを戻すとTTFTが増える
- request終了時の大量KV saveが次requestのGPU executionを邪魔する
- schedulerがsessionを実行する直前までcache placementが最適でない場合がある
- context window overflowで古いtokenを削ると、position encodingの扱いによっては保存済みKVをそのまま再利用できない

## 手法

### 1. GPU / DRAM / SSDをconversation KVの3段階の置き場として使う

各sessionの過去KVをGPU外のDRAM / SSDにも保存し、次turnでhistoryを再prefillする代わりに読み戻す。

- GPU: 近く使うactive session向けの高速tier
- DRAM: GPUより遅いが大容量の中間tier
- SSD: さらに遅いが多数sessionを保持できる大容量tier

論文のAttentionStoreは、この複数memory tierをまとめてconversation KV cacheとして扱う仕組みである。

### 2. Session全体を待たず、次layerのKVだけ先に戻す

次turn開始時に全layerのKVをGPUへ読み終わるまで待つのではなく、**現在layerをGPUで計算している間に次layerで使うKVをDRAM / SSDからGPUへ運ぶ**。

論文のlayer-wise pre-loadingはこの先読みを指す。storageからのtransferをGPU計算の裏へ隠すことで、低速tierを使ったときの追加latencyを減らす。

### 3. Request終了時のKV保存も次のGPU処理と重ねる

request終了時に全KVが保存し終わるまでGPU側処理を止めず、次のinferenceと並行してDRAM / SSDへ書き出す。

論文のasynchronous savingは、**KV saveをforegroundのcritical pathから外す**ための仕組みである。

### 4. 「次に実行するsession」をcache managerへ教える

一般的なLRUは過去のaccessだけを見てcacheを追い出すが、LLM serving schedulerは次にbatchへ入れるrequest / sessionをある程度知っている。

CachedAttentionはこの情報をcache managerへ渡し、

- 近く実行されるsessionのKVはGPUへ先に戻す
- すぐ使わないsessionはDRAM / SSDへ出す

ようにする。

つまりscheduler-aware fetching / evictionは、**未来の実行順をcache置換の手掛かりに使う**ことを意味する。

### 5. 古いtokenを削っても残りKVを再利用しやすくする

conversationがcontext上限を超えると、古いtokenを削る必要がある。RoPEなどではtoken positionがattention計算へ影響するため、実装方法によっては位置が変わると保存済みKVをそのまま使いにくい。

CachedAttentionはposition encodingの適用をKV保存形式からできるだけ切り離し、**古いprefixをtruncateした後も残ったhistory KVを再利用できるようにする**。

## 評価

USENIX ATC 2024版では、multi-turn conversation workloadで以下を報告する。

- TTFT: 最大 **87%削減**
- prompt prefilling throughput: 最大 **7.8×向上**
- end-to-end inference cost: 最大 **70%削減**

長いhistory・turn数の多いsessionほど、stateless baselineで重複prefillが増えるため効果が大きくなる。

またlayer-wise preloadとasynchronous saveにより、単純にKVをSSD / DRAMへ保存するだけの方式よりstorage access overheadを抑えられることを示す。

## 既存研究との差

### Pensieveとの違い

Pensieveもmulti-turn sessionのKVをGPU / CPUへ保持してrequest間reuseする。

CachedAttentionは同じ問題設定をさらに広げ、**SSDまで含む多段storage、schedulerの次実行情報を使った先読み、context truncation後もKVを再利用するposition処理**を明確な設計要素として持つ。

### vLLMとの違い

vLLMのPagedAttentionは主に1 request実行中のKV allocationを効率化する。CachedAttentionはrequest終了後もsession stateを保存し、次turnで再利用することが中心である。

### KV Cache Offload系との違い

single long requestのHBM不足を解消するためのKV offloadではなく、**session間のidle期間をまたいでstateを保存し、future requestの重複計算をなくす**ことが主目的なのでServing系統に分類する。

## 限界

- 利得はmulti-turn / repeated-history workloadに依存し、独立requestでは小さい。
- session catalogとhistoryが非常に大きい場合、SSD容量・帯域とcache evictionがbottleneckになる。
- slow-tier hitは再計算より速い必要があり、model・context長・storage性能によって「保存して読む方が得か、再計算した方が得か」の境界が変わる。
- scheduler-aware prefetchは将来の実行順が大きく変わると外れる可能性がある。
- positional encoding decouplingはmodel architecture依存で、すべてのposition encoding方式へ同じ形で適用できるとは限らない。

## 一般的な実装上の含意

multi-turn workloadではKV reuseの価値は単なるGPU memory optimizationではなく、**過去turnのprefill計算そのものをstorage accessへ置き換えること**にある。

このため最適なtierは常にGPUとは限らず、「再計算時間」と「DRAM / SSDからのload時間」を比較してstateを残す価値を決める必要がある。

またserving schedulerのqueue情報はcache managerにとって有用なfuture hintになるため、request schedulingとmemory hierarchyを独立に設計するより協調させた方がよい。
