# Preble: Efficient Distributed プロンプト スケジューリング for LLM サービング

> 同じプレフィックスのKVをすでに持つGPUへリクエストを送ればプリフィルを省ける一方、そのGPUだけ混むことがあるため、KV再利用で節約できる計算時間とGPUの混雑による待ち時間を比較してリクエストの送り先を決めるdistributed サービング スケジューラ。

## 概要

分散LLMサービングでは、共有プレフィックスのKVを持つGPUへ送ればプリフィルを省けるが、人気プレフィックスを一つのGPUへ固定すると待ち行列が伸びる。逆に均等分散だけを行うと、同じプレフィックスを再計算する。

PrebleはKV再利用で節約できるプリフィル時間と、候補GPUへ送った場合の待ち時間・KV転送時間を同じ尺度で比較し、再利用を優先するか負荷分散するかを要求ごとに決める。人気プレフィックスは複製してホットスポットも分散する。

Mistral-7B/Llama-3-70Bの評価では、SGLang比の平均遅延を1.5〜14.5倍、P99遅延を2〜10倍改善した。

## 問題設定

SGLangなどのプレフィックス キャッシュ化は、同じGPUへ到着したリクエスト間では共有 プレフィックスのKV キャッシュを再利用できる。しかしdistributed サービングでは通常、負荷 balanceのためリクエストを複数GPUへ分散するため、同じプレフィックスを持つリクエストが別GPUへ送られ、同じプリフィルを何度も計算する。

逆にプレフィックス 再利用だけを優先し、同じプレフィックスを常に同じGPUへ送ると、popular プレフィックスを持つリクエストが1台へ集中してキューが伸びる。

したがってクラスタ-レベル スケジューラには、**「すでにあるKVを使って何ms計算を省けるか」と「そのGPUへ送ると何ms余計に待つか」を同じ尺度で比べる仕組み**が必要になる。

論文が調べたツール 呼び出し、embodied エージェント、コード 生成、video QA、長い-document QAの5 ワークロードでは、プロンプトは生成より37〜2494倍長く、プロンプト トークンの85〜97%が他リクエストと共有されていた。こうしたワークロードではデコードよりプリフィル コストが支配的になりやすく、プレフィックス 局所性の配置への影響が大きい。

## 手法

### 1. 「KV再利用を優先するか、空いているGPUへ分散するか」を毎リクエストで選ぶ

リクエストが到着すると、スケジューラは大きく2つを比較する。

- **既存KVを使う:** 最も長い共有 プレフィックスを持つGPUへ送り、プリフィル計算を省く
- **負荷を分散する:** プレフィックス 再利用より混雑回避の方が得なら、より空いているGPUへ送る

論文では前者をexploitation、後者をexplorationと呼ぶ。

重要なのは名称ではなく、**キャッシュ 局所性と負荷 balanceを二者択一ではなく、計算時間コストで比較して決める**ことである。

### 2. GPU負荷をキュー長だけでなく「実際に必要な計算時間」で見積もる

各GPUの負荷を、単純なリクエスト数ではなく、

1. 最近そのGPUが行ったプリフィル / デコード計算
2. 新リクエストを入れるため既存KVを追い出す場合のコスト
3. 新リクエスト自身に必要な計算

を時間へ換算して合算する。

すでにキャッシュされ再利用できるプレフィックス部分は0 コストとして扱う。

これにより、「10 リクエスト待っているGPU」と「2 リクエストしかいないが全部長プロンプトのGPU」のような違いも反映できる。

### 3. 人気プレフィックスが1 GPUを詰まらせたら複製する

一度プレフィックスを特定GPUへ割り当てても、そのプレフィックスへのリクエスト rateは時間とともに変わる。

Prebleは特定GPUだけ重くなった場合、リクエストを別GPUへredirectする。さらに1 GPUでは人気プレフィックスの負荷を処理しきれない場合、そのプレフィックス KVを複数GPUへ複製し、複数インスタンスで同じプレフィックス リクエストを処理できるようにする。

つまりpopular プレフィックスのreplicationは、**キャッシュ 再利用を維持したままhotspotを横に広げる自動スケーリング**として働く。

### 4. キャッシュ hitしたリクエストとmissしたリクエストを適度に混ぜる

プレフィックス キャッシュ hitしたリクエストはプリフィル計算が大きく減るためデコード寄り、キャッシュ missしたリクエストはプリフィル寄りになる。

スケジューラは両者を同じGPUへ適度に混ぜ、1 GPUがプリフィル-heavy リクエストだけ、あるいはデコード-heavy リクエストだけに偏るのを避ける。

### 5. クラスタ全体の配置と、各GPU内の実行順を分ける

- **グローバル スケジューラ:** どのGPUへリクエストを送るかを決める
- **ローカル スケジューラ:** 各GPU内でiterationごとのバッチ / リクエスト順を決める

この2段構成により、クラスタ-レベル ルーティングの判断を各GPUの細かいトークン スケジューリングから分離する。

全体スケジューラはリクエスト到着時の比較的粗い粒度で『どのGPUへ所属させるか』を決め、ローカルスケジューラはそのGPU内でiterationごとの実際のバッチを組み直す。これにより全体制御器が全GPUのトークン単位状態を常時追わなくても、接頭部局所性と大まかな負荷を見て配置できる。一方、生成長やKV使用量が実行中に予想から外れても、各GPU側は現在のメモリ / キュー状態を見ながら短い周期で実行順を調整できる。二つの時間尺度を分けることで、クラスタ-レベル配置の制御費用を抑えつつ、実行中の変動へ局所的に追従する。

### 6. プレフィックス hitだけで同じリクエストを優先し続けない

キャッシュ-friendly リクエストだけを優先すると、プレフィックスを共有しないリクエストが長く待つ可能性がある。

そのため待機 リクエストをプレフィックス hit率に応じて複数priority クラスへ分け、それぞれへ一定の処理枠を与える。

これは厳密なclient-レベル fairness保証が主目的ではなく、**キャッシュ 再利用を増やしてもキャッシュ miss リクエストを永久に後回しにしないための安全策**である。

この安全策が必要なのは、接頭部ヒットを優先する方策が自己強化しやすいためである。あるGPUに人気接頭部が残っていると、その接頭部を持つ要求がさらに同GPUへ集まり、キャッシュ命中は高まる一方で、共有接頭部を持たない要求は相対的に処理機会を失う。待機要求を複数の優先度群へ分けて各群へ処理枠を残すことで、局所性の利得を取りつつ飢餓を防ぐ。したがってPrebleのローカル実行順は、単なる命中率最大化ではなくクラスタ配置の偏りを補正する役割も持つ。

## 評価条件

- **モデル:** Mistral-7B、Llama-3-70B
- **ハードウェア:** 4× NVIDIA A6000 クラスタ、8× NVIDIA H100 サーバー
- **ワークロード:** ツール 呼び出し、embodied エージェント、コード 生成、video QA、長い-document QA、およびAzure LLM リクエスト 到着 pattern
- **主な比較対象:** SGLang、vLLM
- **指標:** 平均 リクエスト 遅延、p99 遅延など

## 主要結果

- SGLangに対して**平均 遅延を1.5〜14.5×改善**。
- p99 遅延を**2〜10×改善**。
- vLLMとの比較でも同様に大きな改善を示す。
- 共有 プレフィックスがないワークロードでは、プレフィックス 局所性を利用できないため基本的に通常のvLLM / SGLang型サービングと同様の挙動になる。

改善幅が大きいのは、長いプロンプトの大部分がリクエスト間で共有され、プリフィル 再計算が主要コストになっているワークロードである。

## 既存研究との差

### SGLang / single-インスタンス プレフィックス キャッシュ化

SGLangはプレフィックス KVをリクエスト間再利用するが、基本的なキャッシュ 再利用はモデル インスタンス内で成立する。

Prebleはそのプレフィックス 再利用を**クラスタ-レベル リクエスト ルーティング問題**へ拡張し、「同じプレフィックスをどのGPUへ送るか」を負荷 balanceと共同最適化する。

### vLLM

vLLMのPagedAttentionはKV メモリ管理と連続 batchingを効率化する。Prebleはその上位でデータ-並列 インスタンス間のリクエスト 配置を決めるため、主題はメモリ allocationではなくdistributed スケジューリングである。

### 局所性-考慮 Fair スケジューリング / DLPM

後続のDLPM / D²LPMは、プレフィックス 局所性とclient-レベル fairnessのtrade-offを明示的なfairness 境界の中で扱う。Prebleもfairness 機構を持つが、中心課題は**プレフィックス再利用とクラスタ 負荷 balanceの両立**であり、fairnessの形式的保証が主目的ではない。

## 一般的な実装上の含意

プレフィックス キャッシュ化をmulti-GPUへ拡張するとき、キャッシュを共有storageへ移すことだけが解ではない。**リクエストを既にKVを持つインスタンスへルーティングするだけでもプリフィル再計算を大きく削減できる**。

ただしキャッシュ affinityだけを見るとhot プレフィックスが負荷 hotspotになるため、プレフィックス match 長さだけでなくキュー / recent 計算 負荷、KV 追い出し コスト、新リクエスト コストを共通の時間コストへ変換して比較する設計が有効になる。

エージェント / ツール-use / RAGのようにシステム プロンプト・ツール description・document 文脈が繰り返されるワークロードほど、このクラスタ-レベル プレフィックス-考慮 ルーティングの価値が高い。

## 限界

- 利得は共有 プレフィックス量に強く依存し、プレフィックス 共有がほぼないワークロードでは固有の高速化余地は小さい。
- プレフィックス affinityを強めるほど負荷 hotspotの危険が増えるため、到着 pattern変動に対するrebalancingが必要になる。
- 評価は主に同一モデルを複数インスタンスでserveするデータ-並列 配置を対象とし、P/D disaggregationやクラスタ-wide 遠隔 KV プールそのものを中心には扱わない。
- スケジューラはプレフィックス 再利用による計算削減を推定するコスト モデルに依存するため、ハードウェア・モデル・プロンプト 分布が変わればprofiling / コスト estimationの調整が必要になる。

## 引用関係

- **SGLang**: single-インスタンス プレフィックス KV 再利用をdistributed 配置へ拡張する直接的な基盤。
- **vLLM / PagedAttention**: Prebleが上位ルーティング 層として利用できるサービング backend。
- **Sarathi / Sarathi-Serve、Splitwise、DistServe**: プリフィルとデコードの資源特性差を扱う関連研究。
- **局所性-考慮 Fair スケジューリング (DLPM / D²LPM)**: 後続研究としてプレフィックス 局所性とfairnessをより明示的に共同最適化する。
