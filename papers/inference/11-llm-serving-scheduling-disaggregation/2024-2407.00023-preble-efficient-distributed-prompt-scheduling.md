# Preble: Efficient Distributed Prompt Scheduling for LLM Serving

## 一文要約

同じprefixのKVをすでに持つGPUへrequestを送ればprefillを省ける一方、そのGPUだけ混むことがあるため、**KV再利用で節約できる計算時間とGPUの混雑による待ち時間を比較してrequestの送り先を決める**distributed serving scheduler。

## 問題設定

SGLangなどのprefix cachingは、同じGPUへ到着したrequest間ではshared prefixのKV cacheを再利用できる。しかしdistributed servingでは通常、load balanceのためrequestを複数GPUへ分散するため、同じprefixを持つrequestが別GPUへ送られ、同じprefillを何度も計算する。

逆にprefix reuseだけを優先し、同じprefixを常に同じGPUへ送ると、popular prefixを持つrequestが1台へ集中してqueueが伸びる。

したがってcluster-level schedulerには、**「すでにあるKVを使って何ms計算を省けるか」と「そのGPUへ送ると何ms余計に待つか」を同じ尺度で比べる仕組み**が必要になる。

論文が調べたtool calling、embodied agent、code generation、video QA、long-document QAの5 workloadでは、promptはgenerationより37〜2494倍長く、prompt tokenの85〜97%が他requestと共有されていた。こうしたworkloadではdecodeよりprefill costが支配的になりやすく、prefix localityのplacementへの影響が大きい。

## 手法

### 1. 「KV再利用を優先するか、空いているGPUへ分散するか」を毎requestで選ぶ

requestが到着すると、schedulerは大きく2つを比較する。

- **既存KVを使う:** 最も長いshared prefixを持つGPUへ送り、prefill計算を省く
- **loadを分散する:** prefix reuseより混雑回避の方が得なら、より空いているGPUへ送る

論文では前者をexploitation、後者をexplorationと呼ぶ。

重要なのは名称ではなく、**cache localityとload balanceを二者択一ではなく、計算時間costで比較して決める**ことである。

### 2. GPU負荷をqueue長だけでなく「実際に必要な計算時間」で見積もる

各GPUのloadを、単純なrequest数ではなく、

1. 最近そのGPUが行ったprefill / decode計算
2. 新requestを入れるため既存KVを追い出す場合のcost
3. 新request自身に必要な計算

を時間へ換算して合算する。

すでにcacheされ再利用できるprefix部分は0 costとして扱う。

これにより、「10 request待っているGPU」と「2 requestしかいないが全部長promptのGPU」のような違いも反映できる。

### 3. 人気prefixが1 GPUを詰まらせたら複製する

一度prefixを特定GPUへ割り当てても、そのprefixへのrequest rateは時間とともに変わる。

Prebleは特定GPUだけ重くなった場合、requestを別GPUへredirectする。さらに1 GPUでは人気prefixのloadを処理しきれない場合、そのprefix KVを複数GPUへ複製し、複数instanceで同じprefix requestを処理できるようにする。

つまりpopular prefixのreplicationは、**cache reuseを維持したままhotspotを横に広げるautoscaling**として働く。

### 4. Cache hitしたrequestとmissしたrequestを適度に混ぜる

prefix cache hitしたrequestはprefill計算が大きく減るためdecode寄り、cache missしたrequestはprefill寄りになる。

schedulerは両者を同じGPUへ適度に混ぜ、1 GPUがprefill-heavy requestだけ、あるいはdecode-heavy requestだけに偏るのを避ける。

### 5. Cluster全体の配置と、各GPU内の実行順を分ける

- **Global scheduler:** どのGPUへrequestを送るかを決める
- **Local scheduler:** 各GPU内でiterationごとのbatch / request順を決める

この2段構成により、cluster-level routingの判断を各GPUの細かいtoken schedulingから分離する。

### 6. Prefix hitだけで同じrequestを優先し続けない

cache-friendly requestだけを優先すると、prefixを共有しないrequestが長く待つ可能性がある。

そのためwaiting requestをprefix hit率に応じて複数priority classへ分け、それぞれへ一定の処理枠を与える。

これは厳密なclient-level fairness保証が主目的ではなく、**cache reuseを増やしてもcache miss requestを永久に後回しにしないための安全策**である。

## 評価条件

- **Models:** Mistral-7B、Llama-3-70B
- **Hardware:** 4× NVIDIA A6000 cluster、8× NVIDIA H100 server
- **Workloads:** tool calling、embodied agent、code generation、video QA、long-document QA、およびAzure LLM request arrival pattern
- **主な比較対象:** SGLang、vLLM
- **Metrics:** average request latency、p99 latencyなど

## 主要結果

- SGLangに対して**average latencyを1.5〜14.5×改善**。
- p99 latencyを**2〜10×改善**。
- vLLMとの比較でも同様に大きな改善を示す。
- shared prefixがないworkloadでは、prefix localityを利用できないため基本的に通常のvLLM / SGLang型servingと同様の挙動になる。

改善幅が大きいのは、長いpromptの大部分がrequest間で共有され、prefill recomputationが主要costになっているworkloadである。

## 既存研究との差

### SGLang / single-instance prefix caching

SGLangはprefix KVをrequest間再利用するが、基本的なcache reuseはmodel instance内で成立する。

Prebleはそのprefix reuseを**cluster-level request routing問題**へ拡張し、「同じprefixをどのGPUへ送るか」をload balanceと共同最適化する。

### vLLM

vLLMのPagedAttentionはKV memory管理とcontinuous batchingを効率化する。Prebleはその上位でdata-parallel instance間のrequest placementを決めるため、主題はmemory allocationではなくdistributed schedulingである。

### Locality-aware Fair Scheduling / DLPM

後続のDLPM / D²LPMは、prefix localityとclient-level fairnessのtrade-offを明示的なfairness boundの中で扱う。Prebleもfairness mechanismを持つが、中心課題は**prefix再利用とcluster load balanceの両立**であり、fairnessの形式的保証が主目的ではない。

## 一般的な実装上の含意

prefix cachingをmulti-GPUへ拡張するとき、cacheを共有storageへ移すことだけが解ではない。**requestを既にKVを持つinstanceへroutingするだけでもprefill再計算を大きく削減できる**。

ただしcache affinityだけを見るとhot prefixがload hotspotになるため、prefix match lengthだけでなくqueue / recent compute load、KV eviction cost、新request costを共通の時間costへ変換して比較する設計が有効になる。

agent / tool-use / RAGのようにsystem prompt・tool description・document contextが繰り返されるworkloadほど、このcluster-level prefix-aware routingの価値が高い。

## 限界

- 利得はshared prefix量に強く依存し、prefix sharingがほぼないworkloadでは固有の高速化余地は小さい。
- prefix affinityを強めるほどload hotspotの危険が増えるため、arrival pattern変動に対するrebalancingが必要になる。
- 評価は主に同一modelを複数instanceでserveするdata-parallel placementを対象とし、P/D disaggregationやcluster-wide remote KV poolそのものを中心には扱わない。
- schedulerはprefix reuseによる計算削減を推定するcost modelに依存するため、hardware・model・prompt distributionが変わればprofiling / cost estimationの調整が必要になる。

## 引用関係

- **SGLang**: single-instance prefix KV reuseをdistributed placementへ拡張する直接的な基盤。
- **vLLM / PagedAttention**: Prebleが上位routing layerとして利用できるserving backend。
- **Sarathi / Sarathi-Serve、Splitwise、DistServe**: prefillとdecodeのresource特性差を扱う関連研究。
- **Locality-aware Fair Scheduling (DLPM / D²LPM)**: 後続研究としてprefix localityとfairnessをより明示的に共同最適化する。
