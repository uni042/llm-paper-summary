# Preble: Efficient Distributed Prompt Scheduling for LLM Serving

## 一文要約

shared prefixが長いrequestを同じGPUへ集めればKV cacheを再利用できる一方、popular prefixへrequestが集中するとload imbalanceが起きる問題に対し、**prefix再利用によるprefill削減量とGPU負荷を同じ計算時間尺度で比較してrequest placementを決めるE2 scheduler**と、global / per-GPUの階層schedulerを組み合わせ、distributed servingでprefix localityとload balanceを同時に最適化する。

## 書誌情報

- **Authors:** Vikranth Srivatsa, Zijian He, Reyna Abhyankar, Dongming Li, Yiying Zhang
- **arXiv:** 2407.00023
- **初回公開:** 2024-05-08
- **Conference:** ICLR 2025
- **Code:** https://github.com/WukLab/preble

## 問題設定

SGLangなどのprefix cachingは、同じGPUへ到着したrequest間ではshared prefixのKV cacheを再利用できる。しかしdistributed servingでは通常、load balanceのためrequestを複数GPUへ分散するため、同じprefixを持つrequestが別GPUへ送られ、同じprefillを何度も計算する。

逆にprefix localityだけを優先し、同じprefixを常に同じGPUへ送ると、popular prefixを持つrequestが1台へ集中してqueueが伸びる。したがってcluster-level schedulerには、**KV再利用による計算削減とGPU間のload balanceを同時に判断するplacement policy**が必要になる。

論文が調べたtool calling、embodied agent、code generation、video QA、long-document QAの5 workloadでは、promptはgenerationより37〜2494倍長く、prompt tokenの85〜97%が他requestと共有されていた。こうしたworkloadではdecodeよりprefill costが支配的になりやすく、prefix localityのplacementへの影響が大きい。

## 手法

### 1. E2（Exploitation + Exploration）scheduler

requestが到着すると、既存GPU上のshared prefixを利用する **exploitation** と、別GPUへrequestを分散する **exploration** を選ぶ。

- shared prefixの再計算を避けて節約できる量が、新しく計算するnon-shared部分より大きい場合はexploitationを優先する。
- exploitationでは最長prefixをcacheしているGPUへ送る。
- localityの利得が小さい場合はexplorationし、prompt-aware loadが最も小さいGPUへ送る。

prompt-aware loadは単なるqueue lengthではなく、次のcostをGPU computation timeへ換算して合算する。

1. 最近のwindow内で発生したprefill / decode計算量
2. 新requestを入れるため既存KVをevictするcost
3. 新request自身の実行cost

既にcacheされ再利用できるprefix計算は0 costとして扱うため、schedulerはcache localityをload metricそのものへ組み込める。

### 2. Popular prefixのrebalancing / replication

一度prefixを特定GPUへ割り当てても、そのprefixへのrequest rateは時間とともに変化する。Prebleはload変化を検出し、heavy GPUからlight GPUへrequestをredirectする。さらに1 GPUではpopular prefixのloadを処理しきれない場合、prefixを複数GPUへ複製してautoscaleする。

### 3. Prefill / decodeを意識したrequest mix

prefix cache hitしたrequestはprefill計算が大きく減るためdecode-heavy、cache missしたrequestはprefill-heavyとみなせる。global schedulerは両者を同じGPUへ適度に混ぜ、phaseごとのresource需要の偏りを抑える。

### 4. 階層scheduler

- **Global scheduler:** request単位のGPU placementとcluster-level load balanceを担当する。
- **Local scheduler:** 各model instanceでiteration-level schedulingを行う。

論文ではglobal schedulerが少なくとも70〜391 GPU相当の規模まで扱えることをscheduler overheadの評価で確認している。

### 5. Fairness

prefix hit率だけでwaiting requestを選ぶとcache-friendly requestが優先され続けるため、waiting requestへprefix cache hit ratioに基づくpriorityを付け、priority classごとにservice quotaを与えることでprefix reuseとfairnessを両立する。

## 評価条件

- **Models:** Mistral-7B、Llama-3-70B
- **Hardware:** 4× NVIDIA A6000 cluster、8× NVIDIA H100 server
- **Workloads:** tool calling、embodied agent、code generation、video QA、long-document QA、およびAzure LLM request arrival pattern
- **主な比較対象:** SGLang、vLLM
- **Metrics:** average request latency、p99 latencyなど

## 主要結果

- SGLangに対して**average latencyを1.5〜14.5×改善**。
- p99 latencyを**2〜10×改善**。
- vLLMとの比較でも同様に大きな改善を示す。
- shared prefixがないworkloadでは、prefix localityを利用できないため基本的に通常のvLLM / SGLang型servingと同様の挙動になる。

改善幅が大きいのは、長いpromptの大部分がrequest間で共有され、prefill recomputationが主要costになっているworkloadである。

## 既存研究との差

### SGLang / single-instance prefix caching

SGLangはRadixAttentionでprefix KVをrequest間再利用するが、基本的なcache localityはmodel instance内で成立する。Prebleはそのprefix reuseを**cluster-level request routing問題**へ拡張し、「同じprefixをどのGPUへ送るか」をload balanceと共同最適化する。

### vLLM

vLLMのPagedAttentionはKV memory管理とcontinuous batchingを効率化する。Prebleはその上位でdata-parallel instance間のrequest placementを決めるため、主題はmemory allocationではなくdistributed schedulingである。

### Locality-aware Fair Scheduling / DLPM

後続のDLPM / D²LPMは、prefix localityとclient-level fairnessのtrade-offを明示的なfairness boundの中で扱う。Prebleもfairness mechanismを持つが、中心課題はE2による**prefix locality対cluster load balance**であり、fairnessの形式的保証が主目的ではない。

## 一般的な実装上の含意

prefix cachingをmulti-GPUへ拡張するとき、cacheを共有storageへ移すことだけが解ではない。**requestを既にKVを持つinstanceへroutingするだけでもprefill再計算を大きく削減できる**が、routing policyがcache affinityだけを見るとhot prefixがload hotspotになる。

したがって実装では、prefix match lengthだけでなく、queue / recent compute load、KV eviction cost、新request costを共通の時間costへ変換して比較する設計が有効になる。またagent / tool-use / RAGのようにsystem prompt・tool description・document contextが繰り返されるworkloadほど、このcluster-level prefix-aware routingの価値が高い。

## 限界

- 利得はshared prefix量に強く依存し、prefix sharingがほぼないworkloadではE2固有の高速化余地は小さい。
- prefix affinityを強めるほどload hotspotの危険が増えるため、arrival pattern変動に対するrebalancingが必要になる。
- 評価は主に同一modelを複数instanceでserveするdata-parallel placementを対象とし、P/D disaggregationやcluster-wide remote KV poolそのものを中心には扱わない。
- schedulerはprefix reuseによる計算削減を推定するcost modelに依存するため、hardware・model・prompt distributionが変わればprofiling / cost estimationの調整が必要になる。

## 引用関係

- **SGLang**: single-instance prefix KV reuseをdistributed placementへ拡張する直接的な基盤。
- **vLLM / PagedAttention**: Prebleが上位routing layerとして利用できるserving backend。
- **Sarathi / Sarathi-Serve、Splitwise、DistServe**: prefillとdecodeのresource特性差を扱う関連研究。Prebleはcache hit / missを利用して両phase相当のworkを同一GPU上でmixする。
- **Locality-aware Fair Scheduling (DLPM / D²LPM)**: 後続研究としてprefix localityとfairnessをより明示的に共同最適化する。
