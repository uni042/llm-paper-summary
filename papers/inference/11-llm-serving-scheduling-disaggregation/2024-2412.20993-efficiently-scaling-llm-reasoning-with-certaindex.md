# Efficiently Serving LLM Reasoning Programs with Certaindex

> Certaindexで途中回答の収束度を測り、Dynasorが簡単な推論を早く止めて難問へ計算を再配分し、固定予算の推論プログラムを問い合わせ単位・配信単位で動的化する。

## 概要

推論時推論（inference-time reasoning）は、1問に対して長い思考列を作ったり、複数の解法経路を並列生成したりして精度を高める。自己整合性（self-consistency; SC）、モンテカルロ木探索（Monte Carlo Tree Search; MCTS）、REBASEのようなアルゴリズムでは、1つのユーザー問い合わせが多数のLLM要求からなる「推論プログラム」になる。しかし既存配信エンジンは個々のLLM要求を主に独立処理し、問題がすでに解けているか、残り探索がまだ有効かに関係なく固定上限まで計算しやすい。

本論文は、推論の進み具合を測るCertaindexと、それを配信へ使うDynasorを提案する。単一の長い思考列では一定間隔で途中回答を強制的に取り出す中間探索（Probe-In-The-Middle）を行い、直近の回答が連続して一致するほど確信度が高いとみなす。複数経路型では、得られた回答群の意味エントロピーを正規化し、回答が少数の意味グループへ集中するほどCertaindexを高くする。

Dynasorはこの値を、単なる早期停止だけでなく計算資源配分とスケジューリングへ使う。簡単で収束した問い合わせは早く止め、難しい問い合わせへ残り予算を回し、同じ推論プログラム内の関連LLM要求を集団スケジューリング（gang scheduling）する。評価ではバッチ処理の計算量を最大約50%削減し、オンライン配信ではSGLangやParrot系ベースラインに対して持続可能な問い合わせ率を最大3.3倍、同じサービス水準目標（service-level objective; SLO）達成率で最大4.7倍厳しい遅延目標を扱えると報告する。

## 背景: 「何トークン使うか」は問題ごとに大きく違う

推論モデルは、難問には長い探索が必要でも、簡単な問題では答えが早い段階で安定することがある。論文の分析では、AMC23で最終的な長い推論列の中央値が約2.7Kトークンである一方、途中回答の正解は中央値約830トークンで既に現れる。固定の最大長まで生成すると、その差がそのままGPU計算と待ち時間の無駄になる。

複数経路型アルゴリズムでも同様で、答えの多数決が早く固まる問題と最後まで経路が割れる問題がある。全問い合わせへ同じ枝数・探索回数を割り当てると、簡単な問題で余らせた計算を難問へ使えない。

一方、途中の確信度を測るために別の大型モデルや報酬モデルを毎回追加実行すると、その判定自体が高価になる。Certaindexは推論過程ですでに得られる回答の安定度を統計信号として使い、アルゴリズムをまたいで共通の「残り計算の価値」の代理を作る。

## 問題設定

Dynasorは、一つの推論問い合わせが複数LLM要求を動的に生成する環境を対象とする。MCTSやREBASEでは次に生じる要求グラフが中間結果に依存するため、静的な有向非巡回グラフ（directed acyclic graph; DAG）として事前固定しにくい。

目標は、精度を維持しながら (1) すでに収束した推論を早期終了する、(2) 問題難度に応じてトークン・枝・探索回数を変える、(3) 同じプログラム内の関連要求をまとめて処理して待ち時間とKVキャッシュ再利用を改善する、ことである。

## 手法

### 1. 長い思考列では途中回答の一致を測る

連鎖思考（chain-of-thought; CoT）型の推論では、一定間隔 (T) ごとに現在の思考を壊さない形で「今なら最終回答は何か」を一時的に出させる中間探索（Probe-In-The-Middle）を挿入する。プローブ応答自体は本来の思考列へ追加せず破棄し、元の推論を継続する。

直近 (N) 回の途中回答が一致していれば、回答が安定したとみなしてCertaindexを高くする。「wait」「hmm」のような迷いを示す区間は安易な終了を避けるため考慮する。したがって単に生成トークン数で止めるより、現在の推論内容の収束を見て終了できる。

### 2. 複数経路では意味エントロピーを使う

SCや探索系では複数経路から複数回答が得られる。完全一致文字列だけでなく意味的に同じ回答をグループ化し、回答群のエントロピー (H) から正規化した確信度 ((log n-H)/log n) をCertaindexとして使う。回答が1グループへ集中すると1に近づき、ばらけると低くなる。

数式問題のように答えを正規化できる場合は文字列グループ、自由文では埋め込みクラスタを使う。報酬モデルを使うMCTSやREBASEでは、平均または最大報酬も進捗信号へ取り込む。

### 3. Certaindexから問い合わせ別計算予算を変える

較正段階で、Certaindexと「ここからさらに計算した場合の精度改善」の関係を測る。実行時には高いCertaindexの簡単な問い合わせを早く止め、低い問い合わせには追加予算を与える。論文ではCertaindexと残り必要計算量の相関を複数のモデル・アルゴリズム・タスクで評価し、Pearson相関0.17〜0.75、平均0.52を報告する。

この方式は推論アルゴリズム固有の枝数や探索回数を直接置き換えるのではなく、それらの上限を問い合わせごとに動的調整する信号として働く。

### 4. プログラム内・プログラム間を分けてスケジュールする

Dynasorはクライアント側のプログラム内スケジューラと、SGLang側のプログラム間スケジューラに分かれる。前者は同じ推論プログラムに属する要求の依存関係とCertaindexを追跡し、後者は複数プログラム間でGPU実行順を決める。

関連要求を集団スケジューリングし、短い残作業を優先する短い仕事優先（shortest-job-first; SJF）も組み合わせる。メモリが逼迫したときは現在アクティブな要求を持たないプログラムのKVキャッシュ優先度を下げ、推論プログラムのまとまりを配信エンジンへ伝える。

### 代表的な評価条件

| --- | --- |
| 推論形式 | 長いCoT、自己整合性（SC）、MCTS、REBASE |
| 主なベンチマーク | MATH系、GSM8K、ASDiv、LiveCodeBench、AMC23など |
| モデル | 推論モデルおよびQwen2.5系蒸留モデルなど複数規模 |
| CoT予算 | 最大16K生成トークンを用いる設定を含む |
| プローブ間隔 | 32、64、128、256、320トークンなどを感度評価 |
| オンライン比較 | SGLang、Parrot系実装 |
| 配信指標 | SLO達成率、持続可能問い合わせ率、遅延SLO倍率、精度 |
| 計算量指標 | 生成トークン、枝数、探索反復、REBASE幅などアルゴリズム固有予算 |

### 代表的な評価結果

| 条件 | 結果 | 読み取れること |
| --- | --- | --- |
| バッチ推論・複数ワークロード | 計算量を最大約50%削減し同等精度 | 固定予算の過剰推論をCertaindexで削れる |
| REBASE / MATH | 約52.2%の計算削減 | 複数枝探索でも収束度から大きく予算を減らせる条件がある |
| SC / GSM8K | 約47.8%削減 | 多数決が早く安定する問題で枝生成を止められる |
| MCTS系 | 約9〜13%削減 | 探索構造によって削減余地は小さくなり、方式依存性がある |
| オンライン配信 | SGLang比で持続可能な問い合わせ率1.6〜3.3倍 | 単問の計算削減が同時配信能力へ反映 |
| 固定問い合わせ率 | SGLang比で1.3〜4.7倍厳しい遅延SLO | 余剰計算を減らし末尾要求の締切余地を作る |
| 同一SLO達成率 | ベースラインより0.7〜2%高い精度の条件 | 簡単な問題から回収した計算を難問へ再配分できる |
| Certaindex vs. 残り計算量 | Pearson 0.17〜0.75、平均0.52 | 完全な難度推定器ではないが動的配分に使える中程度の信号 |

この結果はすべての推論方式で50%削減できるという意味ではない。MCTSでは削減が一桁〜十数%に留まる条件があり、推論アルゴリズムの探索構造とCertaindexの使いやすさで効果が変わる。

## 既存研究との差

一般的なLLM配信エンジンは、LLM要求単位のバッチ化、接頭辞キャッシュ、KVキャッシュ管理には強いが、一つのユーザー問い合わせを構成する複数要求が「同じ推論プログラムの一部」であることや、そのプログラムがどこまで収束したかを直接扱わない。

また、入力文だけから難度を予測して事前に固定予算を決める方式と異なり、Dynasorは推論途中の回答分布を継続観測して予算を更新する。MCTS・REBASEのように実行中に要求構造が変わるアルゴリズムへも適用できる点が中心的な差である。

## 限界・実装状況

Certaindexは正答確率そのものではなく「回答の安定度」の代理である。同じ誤答へ早く収束する場合もあり、閾値を攻めすぎると早期終了が誤答を固定する。理論解析は収束仮定の下で安定度と最終分布の関係を扱うが、実運用のプローブ間隔・一致回数は較正に依存する。

また、オンライン比較のベースラインは基本的に固定予算であり、別の高度な動的難度推定器との直接比較は限定的である。Certaindexプローブ自体も追加生成を必要とするため、短い問題では判定費用の割合が増える。公式実装はDynasorとして公開されている。
