# RAGCache：検索文書の中間状態を階層化し、検索と生成を重ねる推論基盤

## 概要

RAGCacheは、検索拡張生成（Retrieval-Augmented Generation; RAG）で同じ知識文書が何度も検索されることに着目し、その文書を言語モデルが処理したときの鍵・値キャッシュ（KVキャッシュ）を複数要求で再利用する推論提供システムである。RAGでは質問文より長い検索文書をプロンプトに追加することが多い。文書が同じでも要求ごとにプロンプト全体を再処理すると、初回トークンが出るまでの計算とGPUメモリ使用量が増える。

著者らは、検索文書のアクセス頻度に偏りがあることを実測し、繰り返し使う文書列の中間状態をGPUメモリとホストメモリへ保存する。文書の順序が違うと同じ文書でも鍵・値の値が変わるため、単純な文書IDごとのキャッシュではなく、文書列の接頭辞を表す知識木を使う。保持するノードの選択には、再計算費用、頻度、容量、最近の利用を考慮した接頭辞対応の追い出し方針を導入する。

さらに、キャッシュに命中しやすい要求を優先する並べ替えと、ベクトル検索が完了する前の暫定検索結果を使って生成を先行させる動的な投機的パイプラインを組み合わせる。vLLMとFaissを統合した比較方式に対し、平均初回トークン時間を条件により1.2～4倍短縮し、処理能力を1.3～2.1倍へ改善した。SGLangとの比較でも条件により1.1～3.5倍の初回トークン時間改善を報告する。これらは特定のモデル、文書再利用率、検索条件、GPU構成での結果であり、全てのRAGで同じ倍率になるわけではない。

## 問題設定と測定による動機

RAGの基本経路は、質問を埋め込みへ変換して外部のベクトル索引から文書を検索し、その文書を質問に連結して言語モデルへ渡すというものである。検索は主にCPU側、生成はGPU側で動く。入力質問が短くても文書が数千トークンに達すれば、言語モデルは文書全体の注意機構用中間状態を計算する必要がある。従来の要求間接頭辞共有は、GPU上のメモリ容量だけでは大きな知識集合を保持しにくい。

著者らはLLaMA2-7BをA10Gで動かし、入力長を変えて推論時間を測定した。入力が4,000トークンを超えるとプロンプト処理だけで約1秒へ達する条件がある。Wikipedia由来の約30万文書では、検索文書の平均長が約3,718トークン、質問側の平均長が約348トークンであり、追加文書の処理が主要な費用となる。文書列をすでに計算してあれば、再利用によってプロンプト処理の費用を大幅に減らせる。

単純な接頭辞再利用でも、検索文書の中間状態を再計算する場合と比較して最大約11.5倍のプロンプト処理時間差がある。一方、GPU容量不足を補うためにホストメモリから鍵・値を転送する場合も、実験では完全再計算に対して最大約3.9倍短い条件があった。これらはプロンプト処理の局所的な比較であり、後述するRAG全体の初回トークン時間の倍率とは区別する。

キャッシュの価値は文書の再利用率にも依存する。MMLU、Natural Questions、HotpotQA、TriviaQAを使った検索頻度分析では、一部の文書にアクセスが集中する。例えばMMLUでは上位3%の文書が約60%の要求から参照された。全要求が毎回異なる文書を取得する場合にはキャッシュ命中がなく、保存や転送の費用だけが増える。このため、文書の人気度とキャッシュ容量を合わせた管理が必要になる。

## 手法

### 文書順序を保持する知識木

RAGCacheは検索文書のID列を接頭辞木として表す。根には共有システムプロンプトを置き、根からあるノードまでの経路が文書の並び順を表す。各ノードは対応する文書区間の鍵・値テンソルの保存位置を持つ。例えば文書D1、D2の順序で処理した場合とD2、D1の順序で処理した場合では、後続の文書の中間状態が異なる。自己注意の計算が先行トークンへ依存するため、同じ文書IDだけで状態を同一視できない。

要求が到着すると、検索結果の文書列に沿って木を根からたどり、一致する最長接頭辞を探す。途中で子ノードが見つからなければそこで照合を止め、見つかった接頭辞の鍵・値を再利用し、残りの文書だけを新しく計算する。探索費用は木の高さに比例する。vLLMの非連続なキャッシュブロック管理を利用するため、複数要求が同じ接頭辞を共有しても、各要求へ全中間状態を複製する必要はない。

保存先はGPUとホストメモリの二階層である。頻繁に利用する接頭辞は高速なGPUへ置き、使用頻度の低いものはホスト側へ移すか破棄する。ホスト側から再利用する場合には転送時間がかかるが、長い文書をGPUで再計算するより短い場合がある。階層化はGPUメモリ容量を増やす魔法ではなく、GPU容量とホスト容量、転送帯域、再計算費用の交換条件を管理する仕組みである。

### 接頭辞対応の追い出し方針

著者らは接頭辞対応Greedy-Dual-Size-Frequency（PGDSF）を設計した。基本の優先度は、最近の利用を表す論理時計に、アクセス頻度と再計算費用の積を保存容量で割った値を足す形である。優先度の低いノードから追い出す。GPUとホストの二階層で別々の論理時計を持ち、各階層の置換を管理する。

単純な最近使用順（LRU）では、大きく再計算が高価な文書と短い文書の差を十分に扱えない。頻度だけの方式でも、同じ文書がどの接頭辞の後に現れるかによって変わる再計算費用を表せない。PGDSFは、実際にその文書がキャッシュに存在しなかった要求について、未保存部分のトークン数当たり計算時間を求め、平均して費用を推定する。計算時間は、既保存トークン数と未保存トークン数を変えた事前測定から双線形補間で得る。

接頭辞木では、上位ノードを失うとその下に連なる状態の利用可能性にも影響する。したがって、文書ごとの単独の人気度ではなく、接頭辞としての再利用価値を考慮する必要がある。PGDSFは容量、頻度、最近の利用、再計算費用を一つの優先度へまとめ、二階層の限られた容量を再利用価値の高い状態へ配分する。

### キャッシュ命中を考慮した要求の並べ替え

高い要求到着率では、ある文書列をキャッシュへ載せた直後に別の文書列で上書きすると、次の要求が同じ文書を使う頃には状態が失われる。RAGCacheは要求の実行順序も調整し、キャッシュ済み接頭辞の長さを新規計算が必要な長さで割った値を優先度とする。既存状態を多く再利用でき、追加計算の少ない要求を先に処理することで、同じ状態を短時間にまとめて使う。

ただし命中率だけを最大化すると、人気の低い文書を使う要求がいつまでも待たされる。論文は要求ごとに待機窓を設定し、その窓を超えて延期しない制約を加える。これは公平性を完全に証明するものではないが、再利用効率と要求の飢餓防止を両立させる実装上の工夫である。

### 検索と生成の動的な投機的パイプライン

通常のRAGはベクトル検索の完了を待ってから生成を始める。RAGCacheは検索の途中で暫定的な上位k文書が得られることを利用し、その候補列を使って生成を先行させる。次の検索段階で候補列が変わらなければ進行中の生成を続け、変われば古い投機的生成を打ち切って新しい文書列でやり直す。最終検索結果と最新の投機的生成が一致すれば、その結果を返せる。

誤った候補で先行計算するとGPU資源を浪費するため、無条件には投機を行わない。著者らは単一要求処理の待ち行列モデルで、検索結果が変わったときに実行待ち行列が空なら投機を開始する条件を分析する。実際の連続バッチ処理では、保留中の生成要求数が所定のプロンプト処理バッチ上限より小さく、検索候補が更新された場合にだけ新しい投機を開始する。古い投機は他要求を妨げないよう現在の反復が終わってから停止する。

この上限はGPUメモリへ収まるトークン数と演算器を十分に利用できるバッチサイズの小さい方を考慮して決める。したがって低負荷では検索と生成を重ね、高負荷では余分な投機を抑える。投機的復号（speculative decoding）のように小型モデルがトークン候補を提案する方式とは異なり、ここでの投機対象は検索結果の文書列である。

### 実装と障害時の扱い

試作システムはC++とPythonの約5,000行で構成され、vLLM v0.3.0のプロンプト処理カーネルをPyTorchとTritonで拡張し、複数の注意機構形式で接頭辞再利用を扱う。ベクトル検索にはFaissを用い、IVFでは探索するクラスタを分割し、HNSWでは探索時間を区切って暫定候補を出す。最終的な検索結果の意味を変更することなく、途中の候補を推論側へ渡す。

GPU障害に備え、共有システムプロンプトなど木の上位ノードの一部をホスト側へ複製する。失敗した要求は初回反復前なら再計算し、反復後なら保存した鍵・値から再開できる場合がある。ただし全ての障害で状態を失わないという保証ではなく、復旧できる接頭辞やホスト側の保存状態に依存する。

## 評価

### 実験条件

| 観点 | 一次論文の設定 |
|---|---|
| 主要GPU | AWS g5.16xlargeのA10G 24GiB、ホストメモリ256GiB、うちキャッシュに192GiB |
| 大型モデル | H800 80GiBを2基、ホストキャッシュ384GiB |
| モデル | Mistral-7B、LLaMA2-7B、Mixtral-8×7B、LLaMA2-70B |
| 知識集合 | Wikipedia由来の約30万文書 |
| 検索 | Faiss、主にIVF 1,024クラスタ、既定の取得数top-2 |
| 課題 | MMLU、Natural Questions。追加で取得数や大型モデルの条件を評価 |
| 比較方式 | vLLM+Faiss、GPU内で接頭辞を再利用するSGLang |
| 指標 | 平均初回トークン時間、所定遅延以下で処理できる要求率、キャッシュ命中率 |
| 負荷 | 1時間の要求追跡、ポアソン到着、要求率を変更 |

Natural Questionsでは参考回答の長さ分布から出力長を標本化し、平均約6トークン、99%が32トークン以内の設定とした。MMLUは多肢選択で出力が短い。初回トークン時間が主要指標であり、生成する全トークンを長時間測った性能と混同しない。

### 全体性能と比較対象

Mistral-7BとLLaMA2-7Bを用いたMMLUおよびNatural Questionsの実験では、同じ要求率においてRAGCacheの平均初回トークン時間はvLLM比で1.2～4倍短く、SGLang比で1.1～3.5倍短かった。初回トークン時間の閾値を維持できる要求処理能力は、vLLM比で1.3～2.1倍、SGLang比で1.2～1.8倍だった。GPUだけでなくホストメモリへ文書の中間状態を保存することで、GPU内キャッシュが足りない条件でも再計算を減らせた。

同じ7Bモデルでも、LLaMA2-7Bのトークン当たりKV容量はMistral-7Bの約4倍である。したがって同じキャッシュ容量で保持できる文書数が少なく、改善倍率にも差が出る。MMLUの文書アクセスはNatural Questionsより集中しており、再利用の機会が多いため、RAGCacheの利得も大きくなる。モデル名だけでなく、鍵・値の幅と文書再利用率が性能を左右する。

取得文書数をtop-1、top-3、top-5に変えた条件でも、vLLMに対する平均初回トークン時間の改善は1.7～3.1倍、SGLangに対して1.2～2.5倍だった。ただしtop-5ではGPU容量へ収めるため文書を切り詰めており、任意の長さの五文書を無制限に扱えた結果ではない。大型モデルをH800二基で動かした条件では、低い要求率でvLLM比1.4～2.1倍の短縮が報告される。

### 構成要素の効果と負の結果

PGDSFを通常のGDSF、LRU、LFUへ置き換えた比較では、ホストキャッシュ8～128GiBの範囲でPGDSFが最も高い命中率を示した。命中率はGDSF比1.02～1.32倍、LRU比1.06～1.62倍、LFU比1.06～1.75倍であり、平均初回トークン時間も比較方針より1.05～1.29倍短い。これは追い出し方針単体の改善であり、RAGCache全体の最大4倍という結果と同じ比較ではない。

原著表2の例では、ホストキャッシュ8GiB、MMLUでPGDSFが1.38秒、GDSFが1.68秒、LRUが1.78秒、LFUが1.81秒である。128GiBではそれぞれ0.83秒、0.98秒、1.01秒、1.03秒となる。キャッシュ容量を増やすと各方式の絶対遅延が下がり、追い出し方針の差の意味も変わる。

高い要求率でキャッシュ対応の並べ替えを有効にすると、平均初回トークン時間が1.2～2.1倍短くなる条件がある。一方、投機的パイプラインは、検索結果が途中で変わる場合に余分な生成を行うため、GPUが混雑していると効果が減り得る。提案方式が負荷に応じて投機を抑えるのは、この負の結果を避けるためである。

### ハードウェア依存性

A10G上の7BモデルはGPUメモリが小さく、ホスト側へ文書KVを退避する意義が大きい。H800二基の大型モデル実験では、GPUメモリ容量やGPU間通信が変わるため、同じ文書集合でも命中率や転送費用が異なる。原著はMistral-7BのKVをトークン当たり0.125MiB、LLaMA2-7Bを0.5MiB、Mixtral-8×7Bを0.125MiB、LLaMA2-70Bを0.3125MiBとして比較している。重み容量だけでキャッシュの実効保持数を判断できないことを示す。

## 限界と適用範囲

RAGCacheの利得は同じ文書列の接頭辞が複数要求で再利用されることに依存する。検索文書が毎回異なる、または順序が頻繁に変わる場合には接頭辞命中率が下がり、ホストメモリへの保存・転送の費用が増える。検索結果の順序を勝手に入れ替えると生成品質へ影響するため、文書IDが同じというだけでは鍵・値を共有できない。知識木は順序を保つが、異なる順序の組合せが増えると保存候補の数も増える。

PGDSFは再計算時間の事前測定とアクセス頻度に依存する。文書の人気度が急変した場合や、GPUの計算能力・転送帯域が変わった場合には優先度が適切でなくなる可能性がある。ホストメモリも有限であり、保存容量を超える知識集合を全て保持できるわけではない。キャッシュ命中率の改善は、生成回答の正確さを自動的に改善するものではない。

動的投機的パイプラインは、検索途中の候補が最終結果と一致しやすく、GPUに余裕がある場合に有利である。候補が頻繁に入れ替わる場合は誤った生成を打ち切ってやり直す必要があり、高負荷ではかえって計算資源を圧迫する。論文の最適性に関する分析は単純化した待ち行列モデルに基づくものであり、一般の大規模バッチ環境に対する厳密な最適性証明ではない。

実験は主にWikipedia由来の知識集合、MMLUとNatural Questions、A10GとH800、vLLM v0.3.0を用いたものである。文書更新によるキャッシュ無効化、アクセス制御が異なる利用者間での中間状態共有、長期運用での一貫性や障害復旧、別の検索器での再現性については限定的な評価にとどまる。初回トークン時間の短縮率を全生成時間や電力費用の短縮率と同一視しない。
