# ServerlessLLM: Low-Latency Serverless Inference for Large Language Models

> request到着時にmodelをGPUへ読み込むserverless環境で、checkpointをGPU近くのSSD / DRAMへcacheし、高速loaderとmodel所在地を考慮したrequest配置、生成途中requestの移動を組み合わせてmodel起動待ちを短縮するsystem。

## 概要

serverless LLMでは多数のmodelを少数GPUで共有し、requestが来たときだけ必要なmodelをGPUへloadする運用が想定される。しかし数十GB規模のcheckpointをremote storageから毎回取得・変換すると、実際のtoken generationより**modelを使える状態にするまでの待ち時間**の方が桁違いに長くなる。

この「modelがGPUにない状態から最初のrequestを処理できるまでの起動待ち」を **cold start** と呼ぶ。

ServerlessLLMはこの問題を、単なる高速loaderではなく、**checkpointをどこに置くか・どのserverへrequestを送るか・すでに動いているrequestを別serverへどう移すか**まで含む問題として扱う。

中心となる考え方は、GPU serverに備わるlocal NVMe SSDやDRAMをmodel checkpointのcacheとして積極利用し、**どのserverがどのmodel checkpointを近くに持っているか**をschedulerが把握することにある。これがcheckpoint localityである。

local checkpointを持つserverへrequestを送ればremote downloadを避けられる一方、そのGPUが混んでいる場合もある。そのため、必要なら既存のrunning inferenceを別serverへ移してlocal checkpointを持つGPUを空ける仕組みも組み合わせる。

## 問題設定

serverless inferenceでは以下が同時に問題になる。

- model checkpointが大きく、remote object storageからのcold loadが遅い
- 一般的なloaderでは小さいreadやCPU側変換が多く、SSD・DRAM・PCIe帯域を使い切れない
- model localityだけで配置を決めると、local checkpointを持つserverへrequestが集中する
- running inferenceをkillして別serverで最初からやり直すと、長いpromptや生成途中stateの再計算が大きい
- model数がGPU数より多いため、GPUの空きだけでなくmodel startup time自体をschedulerへ入れる必要がある

## 手法

### 1. Checkpointを「高速に連続読込しやすい形」へ事前変換する

checkpointをGPUへ高速に流し込めるlayoutへ事前変換する。load時に複雑なtensor再配置や大量のsmall readを行うのではなく、storageからまとまって読み出してGPUへ送れるようにする。

つまり論文のloading-optimized formatは、**保存容量を減らす圧縮形式ではなく、起動時の読込・配置変換を減らすための保存layout**である。

### 2. SSD→DRAM→GPUを直列に待たず、複数段を同時に進める

local SSD、CPU DRAM、GPU memoryを単純な直列stageとして扱わず、SSDから次のchunkを読みながら、前のchunkをGPUへ送るpipelineを構成する。

主な工夫は以下。

- OSの通常file cacheを経由せずSSDから直接bufferへ読む
- GPUへ高速転送できるよう、OSに固定したhost memoryを使う
- 複数I/O threadでSSDへ並列readを出す
- storage→DRAMとDRAM→GPUを重ねる

論文中の `O_DIRECT` は「OS page cacheを介さずstorageから直接読む」、pinned host memoryは「OSに移動されずGPU transferへ使いやすいCPU memory」を指す。

### 3. 実行中requestは巨大なKVではなくtoken列を送って移す

running inferenceを別serverへ移す際、数GB規模になり得るKV cacheそのものをnetwork transferしない。

代わりに **prompt tokenと生成済みtoken列だけをdestinationへ送り、destination側でKV cacheを再計算する**。token列はKVよりはるかに小さいためnetwork trafficを大きく減らせる。

これが論文のtoken-based live migrationである。ここで **live migration** は、requestを最初からやり直さず、生成途中の状態を別serverへ引き継いで処理を続けることを指す。

移行中もsource側では生成を続け、destinationが過去tokenからKVを再構築して追いついた時点でrequest routingを切り替える。これによりuser-visibleな停止時間を短くする。

### 4. 「GPUが空いているか」だけでなく「modelが何秒で使えるか」で配置する

controllerはserverごとに

- checkpointがSSD / DRAM / remote storageのどこにあるか
- 既存load queue
- 各storage / transfer pathのbandwidth
- model size
- running inferenceを移した場合のcost

を使って、**そのserverでmodelが実際にrequestを処理できるまでの時間**を推定する。

単純なleast-loaded GPUではなく、modelの所在地とmigration costまで含めて最短startupになる配置を選ぶ。

## 評価

### 主な結果

OSDI 2024版では、Ray ServeやKServeなどのserverless baselineに対して、workload全体のstartup / serving latencyを **10〜200×削減**したと報告する。

checkpoint loader単体では、PyTorch / SafeTensors系loaderよりおおむね **6〜8.2×高速**。OPT-6.7Bではstartup約0.8秒に対してRay Serveは約12.1秒というcaseがある。

OPT-30Bを含む実験では、Ray Serve + cacheでも数十〜数百秒かかるmodel startup / request latencyを、ServerlessLLMは一桁〜数十秒へ抑えるcaseを示す。

またmodel数を増やした場合、local SSDへcheckpointを分散保持し、model所在地を考慮したschedulerとrequest migrationを使うことでremote storage accessの増加を抑える。

live migration評価では、KV全体を送るのではなくtoken列だけを送りdestinationで再構築するため、local checkpointを優先した配置でもuser-visible interruptionを小さくできる。

## 既存研究との差

### SpotServeとの違い

SpotServeはspot GPUが突然減る環境に対応するため、model parallel構成とrequest stateを再配置するelastic servingが主題である。

ServerlessLLMは**多数modelを必要時だけGPUへloadする環境のcold start**を主問題とし、checkpoint loading・local storage cache・startup-time schedulerを中心に据える。

### Llumnixとの違い

Llumnixは同じmodelをserveするinstance間でrunning requestのKVをlive migrationし、runtime load imbalanceを修正する。

ServerlessLLMはmodel自体がGPUへ未loadの状態を含むserverless clusterを扱い、**どのserverへmodelを起動するか**と、そのために既存inferenceをどこへ逃がすかを同時に考える。

### 一般的なmodel loaderとの違い

単にcheckpoint fileの読込だけを速くするのではなく、checkpoint format・local storage hierarchy・cluster schedulerまで含めてcold start path全体を最適化する点が異なる。

## 限界

- checkpointを事前に専用formatへ変換し、各serverのlocal storageへ配置する運用が必要になる。
- local SSD容量よりmodel catalogが大きい場合はcache evictionとremote reloadが再び支配的になる。
- token-based migrationはKV transferを避ける代わりにdestination GPUでKV再計算を行うため、非常に長いcontextではrecompute costが増える。
- 主評価は2024年時点のOPT系modelとGPU / storage環境が中心で、H100 / Blackwellや高速C2C memoryではcold-start bottleneckの比率が変わる。
- serverless workloadでのmodel switchingを主目的とするため、常時residentな少数modelだけを高throughputでserveする環境では利点が小さい。

## 一般的な実装上の含意

LLM serverless servingでは、schedulerが見るべきresourceはGPU空き容量だけではない。**model checkpointがそのserverのSSD / DRAMにすでにあるか自体が配置costの一部**になる。

またinference stateについては、巨大なderived stateをそのままcopyするより、元になる小さいstateを転送してdestinationで再構築した方が速い場合がある。ServerlessLLMではKV cacheに対してこのtrade-offを利用している。
