# ServerlessLLM: Low-Latency Serverless Inference for Large Language Models

> model checkpointをnear-GPU SSD / DRAMへ保持し、loading用format・multi-tier loader・token-based live migration・checkpoint locality-aware schedulingを組み合わせてserverless LLMのcold startを大幅に短縮する。

## 概要

serverless LLMでは多数のmodelを少数GPUで共有し、requestが来たときだけmodelをGPUへloadする運用が想定される。しかし数十GB規模のcheckpointをremote storageから毎回取得・deserializeすると、実際のtoken generationよりcold startの方が桁違いに長くなる。

ServerlessLLMはこの問題を、単なる高速loaderではなく **storage hierarchy・migration・cluster schedulingをまとめて設計する問題**として扱う。

中心となる考え方は、GPU serverに備わるlocal NVMe SSDやDRAMをmodel checkpointのcacheとして積極利用し、serverごとのcheckpoint localityをschedulerが把握することにある。local modelを優先すればremote downloadを避けられる一方、そのGPUが混んでいる場合もあるため、running inferenceを別serverへlive migrationする仕組みも組み合わせる。

## 問題設定

serverless inferenceでは以下が同時に問題になる。

- model checkpointが大きく、remote object storageからのcold loadが遅い
- PyTorch / SafeTensors型loaderではstorage・DRAM・PCIe帯域を十分並列利用できない
- model localityだけで配置を決めると、local checkpointを持つserverへrequestが集中する
- running inferenceをkillして別serverで再開すると、長いpromptや生成途中stateの再計算が大きい
- model数がGPU数より多いため、model startup time自体をscheduler objectiveへ入れる必要がある

## 手法

### 1. Loading-optimized checkpoint format

checkpointをGPUへ高速に流し込めるlayoutへ事前変換する。load時に複雑なtensor再配置や大量のsmall readを行うのではなく、storageから連続的に読み出してGPUへ送れるようにする。

### 2. Multi-tier checkpoint loading

local SSD、CPU DRAM、GPU memoryを単純な直列stageとして扱わず、各tierの帯域を並行して使うpipelineを構成する。

主な実装上の工夫は以下。

- `O_DIRECT`でpage cacheを避け、予測しやすいSSD I/Oを得る
- pinned host memoryを使って余分なcopyを減らす
- 複数I/O threadでSSD bandwidthを飽和させる
- storage→DRAM→GPU transferをpipeline化する

これによりcheckpoint loadingをCPU側のserialization overheadではなく、利用可能なstorage / PCIe bandwidthに近づける。

### 3. Token-based live migration

running inferenceを移す際、数GB規模になり得るKV cacheそのものをnetwork transferしない。

代わりに **prompt tokenと生成済みtoken列だけをdestinationへ送り、destination側でKV cacheを再計算する**。token列は数十〜数百KB程度で済むことが多いため、network transfer自体は小さい。

migrationは複数roundで進め、source側で生成を続けながらdestination側が追いつく。差分が小さくなった時点でroutingをdestinationへ切り替える。

### 4. Startup-time-aware scheduling

controllerはserverごとに

- checkpointがSSD / DRAM / remote storageのどこにあるか
- 既存load queue
- 各tierのbandwidth
- model size
- running inferenceを移した場合のmigration cost

を使って、**そのmodelが実際にserve可能になるまでの時間**を推定する。

単純なleast-loaded GPUではなく、checkpoint localityとmigration costまで含めて最短startupになる配置を選ぶ。

## 評価

### 主な結果

OSDI 2024版では、Ray ServeやKServeなどのserverless baselineに対して、workload全体のstartup / serving latencyを **10〜200×**削減したと報告する。

checkpoint loader単体では、PyTorch / SafeTensors系loaderよりおおむね **6〜8.2×高速**。OPT-6.7Bではstartup約0.8秒に対してRay Serveは約12.1秒というcaseがある。

OPT-30Bを含む実験では、Ray Serve + cacheでも数十〜数百秒かかるmodel startup / request latencyを、ServerlessLLMは一桁〜数十秒へ抑えるcaseを示す。

またmodel数を増やした場合、local SSDへcheckpointを分散保持し、locality-aware schedulerとmigrationを使うことでremote storage accessの増加を抑える。

live migration評価では、KV全体を送るのではなくtoken列だけを送りdestinationで再構築するため、checkpoint localityを優先した配置でもuser-visible interruptionを小さくできる。

## 既存研究との差

### SpotServeとの違い

SpotServeはspot GPUのpreemptionに対応するため、model parallel topologyとrequest stateを再配置するelastic servingが主題である。

ServerlessLLMは**多model serverless workloadのcold start**を主問題とし、checkpoint loading・local storage cache・startup-time schedulerを中心に据える。

### Llumnixとの違い

Llumnixは同じmodelをserveするinstance間でrunning requestのKVをlive migrationし、runtime load imbalanceを修正する。

ServerlessLLMはmodel自体がGPUへ未loadの状態を含むserverless clusterを扱い、**どのserverへmodelを起動するか**と、そのために既存inferenceをどこへ逃がすかを同時に考える。

### 一般的なmodel loaderとの違い

単にSafeTensorsを高速化するだけでなく、checkpoint format・local storage hierarchy・cluster schedulerまで含めてcold start path全体を最適化する点が異なる。

## 限界

- checkpointを事前に専用formatへ変換し、各serverのlocal storageへ配置する運用が必要になる。
- local SSD容量よりmodel catalogが大きい場合はcache evictionとremote reloadが再び支配的になる。
- token-based migrationはKV transferを避ける代わりにdestination GPUでKV再計算を行うため、非常に長いcontextではrecompute costが増える。
- 主評価は2024年時点のOPT系modelとGPU / storage環境が中心で、H100 / Blackwellや高速C2C memoryではcold-start bottleneckの比率が変わる。
- serverless workloadでのmodel switchingを主目的とするため、常時residentな少数modelだけを高throughputでserveする環境では利点が小さい。

## 一般的な実装上の含意

LLM serverless servingでは、schedulerが見るべきresourceはGPU空き容量だけではない。**model checkpointがどのstorage tierに存在するか自体がplacement costの一部**になる。

またinference stateについては、巨大なderived stateをそのままcopyするより、元になる小さいstateを転送してdestinationで再構築した方が速い場合がある。ServerlessLLMではKV cacheに対してこのtrade-offを利用している。
