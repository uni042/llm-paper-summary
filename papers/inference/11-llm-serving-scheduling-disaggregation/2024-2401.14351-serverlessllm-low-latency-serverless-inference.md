# ServerlessLLM: Low-Latency Serverless Inference for Large Language Models

> 要求到着時にモデルをGPUへ読み込むサーバーレス環境で、チェックポイントをGPU近くのSSD / DRAMへキャッシュし、高速読み込み器とモデル所在地を考慮した要求配置、生成途中要求の移動を組み合わせてモデル起動待ちを短縮するシステム。

## 概要

サーバーレス LLMでは多数のモデルを少数GPUで共有し、要求が来たときだけ必要なモデルをGPUへ読み込む運用が想定される。しかし数十GB規模のチェックポイントを遠隔記憶装置から毎回取得・変換すると、実際のトークン生成より**モデルを使える状態にするまでの待ち時間**の方が桁違いに長くなる。

この「モデルがGPUにない状態から最初の要求を処理できるまでの起動待ち」を **冷間起動** と呼ぶ。

ServerlessLLMはこの問題を、単なる高速読み込み器ではなく、**チェックポイントをどこに置くか・どのサーバーへ要求を送るか・すでに動いている要求を別サーバーへどう移すか**まで含む問題として扱う。

中心となる考え方は、GPUサーバーに備わるローカル NVMe SSDやDRAMをモデルチェックポイントのキャッシュとして積極利用し、**どのサーバーがどのモデルチェックポイントを近くに持っているか**をスケジューラが把握することにある。これがチェックポイントの局所性である。

ローカルチェックポイントを持つサーバーへ要求を送れば遠隔ダウンロードを避けられる一方、そのGPUが混んでいる場合もある。そのため、必要なら既存の実行中推論を別サーバーへ移してローカルチェックポイントを持つGPUを空ける仕組みも組み合わせる。

## 問題設定

サーバーレス推論では以下が同時に問題になる。

- モデルチェックポイントが大きく、遠隔オブジェクト記憶装置からの冷間読み込みが遅い
- 一般的な読み込み器では小さい読み出しやCPU側変換が多く、SSD・DRAM・PCIe帯域を使い切れない
- モデル局所性だけで配置を決めると、ローカルチェックポイントを持つサーバーへ要求が集中する
- 実行中推論を強制終了して別サーバーで最初からやり直すと、長いプロンプトや生成途中状態の再計算が大きい
- モデル数がGPU数より多いため、GPUの空きだけでなくモデル起動時間自体をスケジューラへ入れる必要がある

## 手法

### 1. チェックポイントを「高速に連続読込しやすい形」へ事前変換する

チェックポイントをGPUへ高速に流し込める配置形式へ事前変換する。読み込み時に複雑なテンソル再配置や大量の小さい読み出しを行うのではなく、記憶装置からまとまって読み出してGPUへ送れるようにする。

つまり論文の読み込み最適化形式は、**保存容量を減らす圧縮形式ではなく、起動時の読込・配置変換を減らすための保存配置形式**である。

### 2. SSD→DRAM→GPUを直列に待たず、複数段を同時に進める

ローカル SSD、CPU DRAM、GPUメモリを単純な直列段階として扱わず、SSDから次の分割片を読みながら、前の分割片をGPUへ送るパイプラインを構成する。

主な工夫は以下。

- OSの通常ファイルキャッシュを経由せずSSDから直接バッファへ読む
- GPUへ高速転送できるよう、OSに固定したホストメモリを使う
- 複数I/OスレッドでSSDへ並列読み出しを出す
- 記憶装置→DRAMとDRAM→GPUを重ねる

論文中の `O_DIRECT` は「OSページキャッシュを介さず記憶装置から直接読む」、固定ホストメモリは「OSに移動されずGPU転送へ使いやすいCPUメモリ」を指す。

### 3. 実行中の要求は巨大なKVではなくトークン列を送って移す

実行中推論を別サーバーへ移す際、数GB規模になり得るKVキャッシュそのものをネットワーク転送しない。

代わりに **プロンプトトークンと生成済みトークン列だけを移行先へ送り、移行先側でKVキャッシュを再計算する**。トークン列はKVよりはるかに小さいためネットワーク通信量を大きく減らせる。

これが論文のトークン方式実行中移行である。ここで **実行中移行** は、要求を最初からやり直さず、生成途中の状態を別サーバーへ引き継いで処理を続けることを指す。

移行中も出典側では生成を続け、移行先が過去トークンからKVを再構築して追いついた時点で要求ルーティングを切り替える。これにより利用者に見える停止時間を短くする。

### 4. 「GPUが空いているか」だけでなく「モデルが何秒で使えるか」で配置する

制御装置はサーバーごとに

- チェックポイントがSSD / DRAM / 遠隔記憶装置のどこにあるか
- 既存負荷待ち行列
- 各記憶装置 / 転送経路の帯域
- モデルサイズ
- 実行中推論を移した場合のコスト

を使って、**そのサーバーでモデルが実際に要求を処理できるまでの時間**を推定する。

単純な最も負荷の軽い GPUではなく、モデルの所在地と移行コストまで含めて最短起動になる配置を選ぶ。

## 評価

### 主な結果

OSDI 2024版では、Ray ServeやKServeなどのサーバーレス比較対象に対して、ワークロード全体の起動 / 推論提供遅延を **10〜200×削減**したと報告する。

チェックポイント読み込み器単体では、PyTorch / SafeTensors系読み込み器よりおおむね **6〜8.2×高速**。OPT-6.7Bでは起動約0.8秒に対してRay Serveは約12.1秒という事例がある。

OPT-30Bを含む実験では、Ray Serve + キャッシュでも数十〜数百秒かかるモデル起動 / 要求遅延を、ServerlessLLMは一桁〜数十秒へ抑える事例を示す。

またモデル数を増やした場合、ローカル SSDへチェックポイントを分散保持し、モデル所在地を考慮したスケジューラと要求移行を使うことで遠隔記憶装置アクセスの増加を抑える。

実行中移行評価では、KV全体を送るのではなくトークン列だけを送り移行先で再構築するため、ローカルチェックポイントを優先した配置でも利用者に見える中断を小さくできる。

## 既存研究との差

### SpotServeとの違い

SpotServeはspot GPUが突然減る環境に対応するため、モデル並列構成と要求状態を再配置する伸縮可能推論提供が主題である。

ServerlessLLMは**多数モデルを必要時だけGPUへ読み込む環境の冷間起動**を主問題とし、チェックポイント読み込み・ローカル記憶装置キャッシュ・起動時間スケジューラを中心に据える。

### Llumnixとの違い

Llumnixは同じモデルを提供する実行単位間で実行中の要求のKVを実行中移行し、実行環境の負荷偏りを修正する。

ServerlessLLMはモデル自体がGPUへ未読み込みの状態を含むサーバーレスクラスタを扱い、**どのサーバーへモデルを起動するか**と、そのために既存推論をどこへ逃がすかを同時に考える。

### 一般的なモデル読み込み器との違い

単にチェックポイントファイルの読込だけを速くするのではなく、チェックポイント形式・ローカル記憶装置階層・クラスタスケジューラまで含めて冷間起動経路全体を最適化する点が異なる。

## 限界

- チェックポイントを事前に専用形式へ変換し、各サーバーのローカル記憶装置へ配置する運用が必要になる。
- ローカル SSD容量よりモデル一覧が大きい場合はキャッシュ追い出しと遠隔再読み込みが再び支配的になる。
- トークン方式移行はKV転送を避ける代わりに移行先 GPUでKV再計算を行うため、非常に長い文脈では再計算するコストが増える。
- 主評価は2024年時点のOPT系モデルとGPU / 記憶装置環境が中心で、H100 / Blackwellや高速C2Cメモリでは冷間起動ボトルネックの比率が変わる。
- サーバーレスワークロードでのモデル切替を主目的とするため、常時常駐な少数モデルだけを高スループットで提供する環境では利点が小さい。

## 一般的な実装上の含意

LLMサーバーレス推論提供では、スケジューラが見るべき資源はGPU空き容量だけではない。**モデルチェックポイントがそのサーバーのSSD / DRAMにすでにあるか自体が配置コストの一部**になる。

また推論状態については、巨大な派生状態をそのまま複製するより、元になる小さい状態を転送して移行先で再構築した方が速い場合がある。ServerlessLLMではKVキャッシュに対してこのトレードオフを利用している。
