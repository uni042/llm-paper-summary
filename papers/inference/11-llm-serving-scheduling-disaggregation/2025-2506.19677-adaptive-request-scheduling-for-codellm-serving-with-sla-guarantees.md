# SABER：CodeLLM配信のSLAを守る生成速度予測型admission control

## 概要

LLM配信のcontinuous batchingは、要求の到着・終了に合わせて実行バッチを更新し、GPUを効率よく使う。しかし一度に実行する最大要求数を固定すると、短い質問と長いコード生成が混在する場面で、スループットと応答期限の最適点が変わる。並列数を増やすとGPU利用率は上がる一方、各要求のトークン生成速度が下がり、厳しいService Level Agreement（SLA）を守れなくなる場合がある。逆に並列数を低く固定すると、軽い要求が多い時間帯に処理能力を使い切れない。

**SABER**は、各要求の期限と現在実行中の要求を見ながら、新しい要求をバッチへ入れてよいかを予測するSLA-awareスケジューラである。事前の負荷試験で同時要求数Lと1要求当たりの生成速度の関係 `v_hat=f(L)` を学習し、オンラインでは新しい要求を一件追加した場合の予測速度を使う。新規要求自身が期限を守れるだけでなく、**すでに実行中の要求が新規受け入れによってSLAを破らないこと**も条件にする。期限を守る可能性がない要求は低優先キューへ移し、SLAを守れる要求へ資源を配分する。

Qwen-Coder-2.5Bと記載されたCodeLLMを単一アクセラレータ上のvLLMで提供する評価では、balanced workloadの10 requests/sで、静的最適設定のgoodput 56%に対しSABERは74%を達成した。負荷が高い場合には最大26ポイントのgoodput差を報告し、重い要求構成で完了時間/SLA比の変動係数を52.4%から33.7%へ下げた。ただしSABERは**全要求の応答を速くする方式ではない**。期限達成不能と判断した要求を後回しにするため、負荷が高いと長いコード生成・翻訳のSLA達成率が低下する条件もある。

## 問題設定

### continuous batchingの固定並列数は常に最適ではない

LLMはdecodeで1トークンずつ生成する。異なる要求は入力長・生成長・到着時刻が違うため、通常の静的バッチでは長い要求が終わるまで短い要求が待たされる。continuous batchingは毎ステップ要求を出し入れできるが、同時実行の上限を固定すると、混合ワークロードと要求到着率によって最適値が変わる。

原著の動機実験では、コード質問応答、コード生成、コード要約、コード翻訳の4種類を用意する。入力・出力長と模擬SLAはそれぞれ異なり、質問応答は平均186入力・43出力tokensで1秒、生成は463入力・387出力tokensで8秒、要約は31入力・30出力tokensで1秒、翻訳は670入力・617出力tokensで12秒とした。SLAは実運用の契約値ではなく、10 RPSで100要求を流した平均完了時間から定めた実験上の期限である。

3種類の混合負荷を作る。W1（Heavy）はコード生成40%、翻訳40%、質問応答10%、要約10%。W2（Light）は質問応答40%、要約40%、生成10%、翻訳10%。W3（Balanced）は4種類が各25%。同時実行上限10〜100を10刻み、到着率1〜10/15/20 RPSの12水準で組み合わせ、3×12×10=360条件を測定した。各条件でPoisson到着の100要求を3回流し、平均値を比較する。

goodputは `期限内に完了した要求数 / 全要求数` である。全体tokens/sが高くても、厳しい1秒SLAの質問応答が多数遅れればgoodputは下がる。逆に処理したトークン数が減っても、期限内に完了する要求が増えればSABERの目的関数では改善になる。これは「全要求の公平な遅延短縮」とは異なる最適化目標である。

### 動機実験の負荷依存性

静的な同時実行上限の代表最適値はW1で30、W2で70、W3で80と異なった。W2に適した70をW1で使うと、多くのRPS水準でgoodputが極端に悪くなる。W3では設定を30から50へ変えるだけでgoodputが最大39%低下する条件があった。同じW3でも5 RPSでは100が最適なのに、10 RPSでは80へ移る。したがって「起動時に最大並列数を一度決める」運用は、タスク比率や到着率が変化するサービスには不向きである。

## 手法

### 1. オフラインで同時実行数と生成速度の関係を測る

SABERは最初に、最大同時実行数を十分大きく設定した環境へ異なる負荷の要求を投入し、各要求が処理されたときの同時実行数L、生成token数、実行時間を収集する。1要求当たりの生成速度を `生成tokens / 実行時間` として計算し、`(L, speed)` の観測点を約1,000件作る。

これにより `v_hat=f(L)`、すなわち「現在L件を並列実行しているとき、各要求は何tokens/sで生成できるか」を推定する関数を作る。原著は複数の回帰モデルを比較し、Universal Scalability Law（USL）を採用する。USLは並列数増加による処理能力の伸びと競合・協調オーバーヘッドを近似する経験式であり、`scipy.optimize`でフィッティングする。USLの実験上の決定係数はR²=0.99で、後述の線形R²=0.91、logistic R²=0.97より良い。

SABERが予測するのは厳密な全要求の完了時刻ではなく、**並列度に応じた生成速度**である。生成長は入力によって変わり得るため、要求が持つ最大生成token数などを使って期限内完了の可否を保守的に判定する。モデル・GPU・実行エンジン・バッチ実装が変われば速度曲線も変わるため、プロファイルの再計測が必要になる。

### 2. 期限までに必要な生成速度を計算

オンラインでは要求rに、期限 `deadline_r` と想定最大生成token数 `maxTokens_r` を付与する。現在時刻tでの必要生成速度は `v_req(r,t)=maxTokens_r/(deadline_r-t)` である。例えば残り10秒で500tokens生成する必要があれば50tokens/s、待機して残り5秒になれば100tokens/sを要求する。同じ要求でも待機するほど期限達成が難しくなる。

必要速度が、単独実行でも到達できない最大生成速度を超えた要求は、すでにSLA達成不能と判定し、低優先キューへ移す。期限が厳しい要求を無制限に先送りするわけではなく、**実現可能性のなくなった要求を高優先の競合から外す**という設計である。SLAが守れなくなった要求も捨てず、高優先キューが空いたときにbest-effortで処理する。

### 3. 二段キューとhead-of-line blockingの緩和

すべての新規要求は高優先キュー（HPQ）へ入る。SLAが物理的に守れないと判定された要求は低優先キュー（LPQ）へ移る。admission controlはHPQ先頭の一定幅windowから要求をランダムに候補選択する。単純なFIFOだと、先頭の長い要求だけがバッチ投入条件を満たせず、後ろの短い要求まで止まるhead-of-line blockingが起こるためである。

ランダム選択された候補が入れられなければ、次の候補を調べる。高優先要求がある限り低優先要求は後回しになり、HPQが空いた場合にLPQからbest-effortで実行する。実装は既存vLLMの内部カーネルを変更するのではなく、外側のキューと受け入れ判定によって並列数を動的に制御する。

### 4. 新規要求だけでなく既存実行要求のSLAを守る

候補rを受け入れた後の同時実行数を `L+1` として、`v_pred=f(L+1)` を計算する。候補の必要速度 `v_req(r,t)` より `v_pred` が小さければ、候補は今入れてもSLAを守れないため受け入れない。さらに、**現在実行中のいずれかの要求の必要速度よりもv_predが低くなる**場合も、候補を受け入れない。

これにより、短い新規要求を無条件に追加して既存要求のdecode速度を落とし、既存要求のSLA違反を誘発することを避ける。条件を満たした候補だけをバッチへ追加し、実行中要求の必要速度・期限情報を更新する。Algorithm 1はこの判定を継続的に繰り返す。推定器が過度に楽観的ならSLA違反が起き、過度に悲観的なら実行できる要求まで待たせるため、速度推定の精度が結果を左右する。

## 評価

### 評価環境と比較対象

| 項目 | 条件 |
|---|---|
| モデル | Qwen-Coder-2.5Bと原著が記載するCodeLLM。具体的なcheckpoint名・量子化条件は本文記載範囲で未確定 |
| 実行環境 | 単一アクセラレータ上のvLLM。多GPU分散や複数ノードは評価外 |
| 要求 | コードQnA、生成、要約、翻訳の4種類。W1 Heavy/W2 Light/W3 Balancedの3混合 |
| 到着率 | 1〜10 RPS、15 RPS、20 RPS。Poisson到着、各条件100要求・3回反復 |
| 静的比較 | 最大同時実行数10〜100から、そのワークロードとRPSごとの**最良の静的設定**を選ぶ強い比較 |
| 指標 | goodput（SLA内完了率）、要求別完了時間CDF、完了時間/SLA比、変動係数CV |
| 予測器ablation | USL（R²=0.99）、logistic（R²=0.97）、linear（R²=0.91） |

原著の静的比較は「適当に選んだ固定設定」ではなく、各条件で事後的に最良の静的上限を選んでいる。これはSABERの動的制御を厳しく評価する比較である一方、要求長・期限の模擬値、単一GPU、100要求単位という制約がある。コード生成モデルの名称・サイズの表記は原著に従っており、同名の別checkpointへ勝手に読み替えない。

### goodputの代表結果

| 条件 | SABER | 最良静的設定 | 差と解釈 |
|---|---:|---:|---|
| W3 Balanced、10 RPS | 74% | 56% | +18パーセンテージポイント。短長混合で固定並列度が妥協を強いられる |
| W2 Light、20 RPS | 63% | 56%相当 | +7ポイント。短い要求のSLAを優先 |
| W1 Heavy、代表高負荷条件 | 36% | 28%相当 | +8ポイント。重い要求の競合を抑制 |
| 全RPS水準の平均改善 | W1 +10.2pt、W2 +1.2pt、W3 +4.3pt | 各条件の最良静的設定 | 軽負荷では差が小さく、競合増大時に改善が広がる |
| 20 RPSの高負荷 | W1 +8pt、W2 +7pt、W3 +26pt | 各条件の最良静的設定 | 最大26ポイントは飽和時のbalanced条件に関する差 |

上表の「56%相当」「28%相当」は原著が示すSABER値と差から算出した概数であり、別途報告された静的実測の独立数値ではない。論文のabstractでいう「goodput up to 26% improvement」は、本文Figure 5における20 RPSでの**26パーセンテージポイント差**と区別して読む必要がある。SLA内完了率は0〜100%の比率なので、百分率の相対改善とポイント差を混同すると評価を過大・過小に見積もる。

### 要求種別ごとのトレードオフ

原著Figure 4のCDFは、各タスクの完了時間分布とSLA閾値を比較する。W1 Heavy・5 RPSではCodeQnAが+60ポイント、CodeSummaryが+50ポイント程度改善し、少数の大きな要求が35秒超まで待つ裾を残す。W2 Light・20 RPSでは、QnAが+42.5ポイント、Summaryが+30ポイント改善する一方、**Code Generationは−30ポイント、Code Translationは−20ポイント悪化**する。W3 Balanced・10 RPSではQnA +24ポイント、Summary +16ポイント、Generation −4ポイント、Translation +28ポイントと報告する。

この結果はSABERの目的が平均遅延やすべてのタスク種別の公平性ではなく、**期限を守れる要求の総数を増やすこと**であると明確に示す。重い要求のSLA達成率を犠牲にして軽い要求を救う場合がある。サービス別の最低SLA達成率を保証したい運用では、タスク別最低保証やstarvation防止の別制約が必要になる。

### 完了時間の安定性

完了時間を各要求のSLA秒数で割った比を作り、その平均と標準偏差を到着率ごとに追う。W1では静的設定の平均比が1 RPSで0.58、20 RPSで3.0へ増え、SABERは0.60から1.75への増加に抑えた。変動係数CVは静的52.4%に対してSABER33.7%。W3でもCVは静的36.4%に対してSABER25.1%。ただしW2 Lightでは静的17.5%、SABER20.8%で、**軽負荷主体では変動係数が逆に悪化**する。論文の「最大45%変動低減」をすべての混合条件での改善と解釈してはならない。

### 速度予測器のablationと負の結果

USL予測器はR²=0.99、logisticは0.97、linearは0.91。W1 HeavyやW3 Balancedでは簡易予測器でも静的設定を上回る場合があるが、W2 Lightでは過度に保守的な判定が、まだ実行できる短い要求まで止めてしまう。全負荷水準でUSLは静的より+1.2ポイント程度の改善だが、**linearは−6.7ポイント、logisticは−5.3ポイント**で静的より悪化する。

これは「admission controlを入れれば必ず良くなる」のではなく、**速度予測の誤差と安全側の偏りがgoodputを左右する**ことを示す重要な反例である。ハードウェアやモデルを変更したとき、USLの曲線を再測定せず流用すると、同じ問題が起こり得る。

## 既存研究との差

vLLMなどのcontinuous batchingは、実行中の要求を細かく入れ替えてスループットを改善する基盤機能である。SABERはその上に「今この要求を入れると既存要求の期限を破らないか」というadmission controlを追加する。PagedAttentionやattention kernelを高速化する方式ではなく、**GPUを使う要求集合の選び方**を変える制御層である。

固定のmax concurrency設定と異なり、負荷の変化に応じて並列数を動的に調整する。SLA-awareな既存スケジューラがエンジン内部の大幅な改造を要する場合と比べ、外側の速度予測・二段キューで実装できることを重視する。要求ごとの予測出力長と残り時間を扱うため、単純な先着順や最短要求優先とも異なる。

## 限界・運用上の注意

本論文は単一アクセラレータ上のCodeLLMと模擬Poisson到着の100要求ワークロードを対象とする。実際の開発組織の長期トレース、バースト到着、複数GPU/複数ノード、マルチテナントでの公平性、複数モデルの共有メモリ競合は未検証である。SLAは測定に基づいて設定した実験値であり、外部顧客との厳密な契約保証を数学的に証明したものではない。

期限達成不能と判定された要求は低優先へ回されるため、要求が多い状態が続くと長い生成が長時間待たされ得る。W2のheavy taskでSLA達成率が下がる結果はこの設計上のトレードオフである。サービス別の公平性を守るには、低優先キューの待機上限、予約枠、最低処理比率などを追加する必要がある。

USL速度曲線は実行エンジンとモデル・GPU・量子化・入力長分布に依存する。推定に使う最大出力token数が実際の出力長から大きく外れれば、実行可能性の判定も誤る。実験の予測器ablationはその脆弱性を示す。さらにprefillが支配的な短い応答では、生成速度だけの推定がE2E遅延を十分に説明できない可能性がある。
