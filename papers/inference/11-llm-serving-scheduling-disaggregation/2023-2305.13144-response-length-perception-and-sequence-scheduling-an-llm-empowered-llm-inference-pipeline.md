# Response Length Perception and Sequence Scheduling: An LLM-Empowered LLM Inference Pipeline

> Vicuna自身を軽量な応答長予測器として使い、生成前に要求を長さ別へ並べ替える。予測外れを失敗回収・再計算で隔離し、短い要求には大きなバッチを使うことで、可変長生成に特有のバッチ内遊休を減らす。

## 概要

自己回帰生成では、一つのマイクロバッチに入った系列を並列に1トークンずつ進める。系列ごとの終了時刻が近ければGPUの各バッチスロットを最後まで使えるが、短い応答と長い応答が混ざると、短い系列がEOSへ到達した後も最長系列が終わるまでバッチ全体の処理が続く。古い固定バッチ実装では、この差がパディングや終了済み系列に対する冗長計算として現れ、バッチを大きくするほど「一つだけ長い応答」を引く確率も上がる。

この論文は、生成長を正確に知ること自体を新しいスケジューリング信号にする。まず「応答を生成する前に、そのLLM自身へ何語程度になるか答えさせる」事前知覚（Perception in Advance; PiA）を調べ、GPT-4などでは一定の予測能力があることを確認する。ただしPiAを本来の回答生成と同じプロンプト内で行うと、小型モデルでは回答内容に影響し得る。そこでVicuna-7Bを**応答長だけを数値で返す専用予測器**へ低ランク適応（Low-Rank Adaptation; LoRA）で命令調整し、予測と本生成を分離する。

予測長を得た後は、同じグループ内の要求を近い長さでまとめるだけでなく、予測外れとGPUメモリ制約へ対処する。過小予測で長い系列が短いバッチへ混ざった場合は、**失敗回収・再計算（Failure Collection and Recomputation; FCR）**で一旦打ち切って後から再実行する。短い予測のバッチでは**可変バッチサイズ（Variable Batch Size; VBS）**を大きくし、同時処理数を増やす。さらに50トークン単位の**ビニング（binning）**で小さな予測誤差へ余裕を持たせる。

Vicuna-7BをA100 80GBで評価したAlpaca 10,000要求では、固定バッチ16の1.22 samples/sに対し、命令調整した最大生成長予測と3機構を組み合わせて2.27 samples/s、86%の処理量向上を得た。真の最大長を事前に知る理想上限は2.52 samples/sで、提案法との差は0.25 samples/sである。一方、真値を知っても冗長計算率は66%から33%までしか下がらず、生成長スケジューリングだけで全ての無駄を消せるわけではない。

## 問題設定

### 可変長生成では「大きなバッチ」が常に速いとは限らない

固定長を生成する実験では、Vicuna-7B/A100上でバッチ16程度まで処理量がほぼ線形に増える。しかしEOSまで生成する通常の可変長条件では、大きなバッチほど長い外れ系列を含みやすく、短い系列の終了後に冗長な処理が残るため、ある点から処理量が低下する。

したがって問題は単純な「最大バッチを選ぶ」ことではない。各要求の**将来の出力長**を生成前に推定し、終了時刻が近いものを同じマイクロバッチへ入れられれば、平均バッチ長を短くできる。ただし生成長は確率的で、同じプロンプトでも毎回同じではない。特に過小予測は、長い応答を短い要求群へ混ぜてスケジューリング効果を壊す。

### 入力長だけでは応答長を十分に説明できない

応答長は入力トークン数だけで決まらない。「一語で答える質問」と「長い記事を書け」という要求では、似た入力長でも出力長が大きく異なる。そこで論文は、LLMが命令の意味から自分の回答規模を推測できるかを先に検証する。

PiAでは、通常の回答前に予想語数を出させる。GPT-4、ChatGPT、Claudeなどは一定の応答長知覚を示したが、小型のVicunaでは長さを先に答えさせること自体が後続生成へ影響した。これが「本生成と予測を別の推論として分離する」命令調整版へ進む理由である。

## 手法

### 1. Vicuna自身を応答長予測器へ命令調整する

学習にはAlpacaから10,000プロンプトを用いる。各プロンプトを4回生成し、その**最大応答長**を教師値にする。平均ではなく最大を選ぶのは、過小予測の方がスケジューリングへの損害が大きいためである。予測器の出力は応答本文ではなく長さを表す数値だけなので、本生成よりはるかに少ない生成トークンで済む。

学習はLoRAで3エポック行う。付録の設定ではクエリ・キー射影へLoRAを適用し、学習率は5e-5、単一A100 80GBを使う。従来のプーリング特徴＋多層パーセプトロン（Multi-Layer Perceptron; MLP）や特殊な長さトークンを追加する方法とも比較している。

Vicuna-7Bでは、予測だけをプロンプトで依頼する未調整方式の平均誤差193、±100以内の正解率59%に対し、命令調整で誤差63、±100以内81%へ改善した。プーリング＋MLPは誤差73、長さトークン微調整は84であり、Vicuna自身の意味理解を長さ推定へ使う命令調整が最も良かった。

### 2. 予測長で要求を並べ替え、50トークン単位へ丸める

一度に処理候補として集めた要求群を予測長で並べ替え、近い予測長の要求からマイクロバッチを作る。評価ではグループサイズを256とし、単一GPUのバッチサイズより十分大きい要求集合から並べ替える。

予測値は50トークン幅の区間へ入れ、実際の長さ以上となる側へ丸める。これは厳密な1トークン単位予測を要求せず、同じ区間内の誤差をスケジューリングへ影響させないための余裕である。区間化だけでも固定バッチ基準より処理量は上がるが、過小予測への対策なしでは長い外れ系列が残る。

### 3. 失敗回収・再計算で過小予測をバッチから隔離する

各バッチについて、新規生成を「そのバッチ内で最も長い予測値」までに制限する。そこへ達してもEOSが出ない要求は予測失敗とみなし、現在のバッチから回収する。回収要求はグループ内の通常処理が終わった後に再計算する。

この設計では、少数の過小予測に全ての短い要求を待たせる代わりに、外れ要求だけへ再計算コストを負わせる。最大長を教師にすると失敗回収率は15.3%だったのに対し、平均長を教師にすると29.8%まで上がり、処理量向上も86%から45%へ落ちる。したがって「平均誤差が小さい予測器」だけでなく、過小予測の尾を抑えることがシステム性能に直結する。

### 4. 可変バッチサイズで短い系列の余ったメモリを同時処理数へ変える

生成中のKVキャッシュは系列長に応じて増えるため、短い応答なら1要求当たりのGPUメモリが少ない。FCRで誤って長い系列が混ざった場合を隔離できるようになったため、短い予測群には固定バッチ16より大きなマイクロバッチを安全側で割り当てられる。

評価設定では、予測長が300以上ならバッチ16を維持し、300未満なら (256\times50/L) を基準にし、GPU利用に合わせて最も近い2の冪へ丸める。論文本文の一般式は基準バッチと基準長から「ほぼ一定の総トークン数」を保つ形でバッチを変えるという発想である。

ビニング、FCR、VBSは独立の飾りではない。ビニングが予測誤差に余裕を与え、FCRが深刻な過小予測を隔離することで、VBSが短い要求へ大きなバッチを割り当ててもメモリ超過しにくくなる。

構成要素除去実験では、ビニングなし・FCRなし・VBSなしの単純な予測長並べ替えでも1.73 samples/s（+42%）まで上がる。FCRだけを加えると1.76、さらにVBSを加えると2.22、三つ全てで2.27となる。したがって大部分の利得は「似た長さをまとめる」時点で得られるが、最終的な+86%には予測外れの隔離と短系列向け大バッチが必要である。

予測自体は各要求について入力のKVを計算し、通常2〜3トークンの数値を生成する追加推論を要する。論文はこの前処理を1〜4トークン生成相当としており、全体のスケジューリング利得で償却できると報告する。ただし低負荷でグループサイズを十分集められないサービスでは、この前処理と待ち時間の相対負担が大きくなる。

## 既存研究との差

通常の先着順（First-Come, First-Served; FCFS）や固定バッチでは、要求の終了時刻を未知のまま一緒に処理する。連続バッチ処理は終了したスロットへ新要求を差し込む別の解決策だが、本論文は**生成開始前に将来の応答長を推定して、そもそも終了時刻の近い要求を組ませる**方向を取る。

また、応答長予測を単なる補助タスクとして評価するのではなく、過小予測がシステムへ与える損害をFCRで明示的に吸収し、その安全網を前提にVBSを使う。予測精度、バッチ形成、KVメモリ量を一つの実行パイプラインへつないだ点が論文固有の貢献である。

## 限界・実装状況

第一に、応答長は本質的に確率的で、正確な事前予測は保証できない。真の最大長を既知とした場合でさえ、論文の冗長計算率は66%から33%へ下がるに留まり、可変長バッチの無駄を完全には除去できない。

第二に、方式は単一GPUのマイクロバッチより大きい要求グループを集められることを前提にする。高負荷サービスでは自然だが、低到着率では256要求を待つこと自体が待ち時間を増やす。論文もグループサイズを大きくするほど改善余地は増える一方、利得は逓減すると示している。

第三に、主評価はVicuna-7BとA100 80GB、Alpaca/Instruction-in-Wildに限られる。入力側の長文処理を対象にしておらず、近年の連続バッチ基盤やページ化KVキャッシュと組み合わせた実測もこの論文の評価範囲外である。
