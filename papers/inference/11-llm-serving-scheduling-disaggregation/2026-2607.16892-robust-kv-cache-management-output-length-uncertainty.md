# Robust KV Cache Management for LLM Serving under Output Token Length Uncertainty

> **「何token生成されるか分からないrequestへ、最初にKV cacheを何token分確保するか」を固定P90/P95の経験則ではなく、preemptionの損失と未使用HBMの損失から決め、その予約量をGPU構成・routing・prefix cacheと一緒に再最適化するcontrol-plane手法。**

## 概要

LLMのデコード（decode）では、1 token生成するたびにそのtokenのkey/valueがKV cacheへ追加される。しかしrequestを受け付けた瞬間には、回答が100 tokenで終わるか2,000 token続くかは分からない。そこでserving systemは、将来増えるKV cacheをどこまで見込んでmemoryを確保するかという判断を迫られる。

少なく予約し過ぎると、生成途中で予約枠を使い切る。論文のmodelではこの時requestをプリエンプト（preempt）して一度追い出し、それまでの処理を再計算するため、GPU computeとlatencyを二重に支払う。逆に長い回答を恐れて全requestへP99や最大長を予約すると、実際には使われないHBMが大量に残り、同じGPUへ同時に載せられるrequest数が減る。

この問題は単なるmemory allocatorの断片化問題ではない。論文が例に挙げる70B modelではKV cacheが約2.5 MB/tokenになり、2,000-token responseだけで約5 GBに達し得る。continuous batchingでは同時requestの予約量の合計がbatch capacityを決めるため、requestごとの数百tokenの過剰予約がcluster throughputへ直接響く。

productionではさらに難しい。chatは数十〜数百token、code generationは数千tokenというようにapplication classごとの長さ分布が違い、同じclassでもuser behaviorやprompt templateの変更で分布が時間とともにずれる。またGPU cluster側にもtensor parallelism（TP）やpipeline parallelism（PP）の異なるserving groupがあり、構成ごとにKV capacity・compute throughput・communication costが違う。

本研究はこの一連の判断を**control planeで共同最適化する問題**として定式化する。決めるのは次の4つである。

1. GPUをどのTP/PP構成のserving groupへ何groupずつ分けるか。
2. request classごとに何token分のKV cacheを予約するか。
3. 各classをどのserving groupへ何割routingするか。
4. class内で共通するprompt prefixをどのgroupへcacheするか。

出力長分布を過去dataそのままと信じるのではなく、Wasserstein分布ロバスト最適化（Wasserstein Distributionally Robust Optimization; Wasserstein DRO）で「観測分布から少しずれた分布」の中でも損をしにくいpolicyを求める。これにより固定P90/P95の手動tuningをやめ、cost構造とworkload変化に応じて予約量を動かす。

## 背景: これは「KV cacheをどう配置するか」より一段上の問題

PagedAttentionやvLLMは、KV cacheをpage/block単位で割り当てることでmemory fragmentationを減らす。しかしpage allocatorが効率的でも、**request Aに最初から何block分を予算として与えるべきか**という判断は別に残る。

たとえば同じGPUに2 requestを載せるとして、両方へ最大4,000 token分を予約すれば安全だが、実際の出力が各500 tokenなら7,000 token分近いcapacityを眠らせる。一方、各500 tokenだけ予約して片方が3,000 token生成したら途中でcapacity shortageに陥る。

論文はこの差を、過小予約によるプリエンプト損失（preemption cost）と過剰予約による浪費損失（waste cost）の二つで表す。

request class `i` の入力長を `L_in`、実際の出力長を `ξ`、予約した総token数を `r` とすると、実需要が予約を超えた分には

`c_p × (L_in + ξ - r)^+`

のpreemption costを課す。逆に予約が実需要を上回った分には

`c_w × (r - L_in - ξ)^+`

のwaste costを課す。ここで `(x)^+ = max(x,0)` である。

`c_p` が大きいserviceではpreemptionを強く嫌うので多めに予約すべきであり、`c_w` が大きい高負荷serviceではHBM空費を嫌うので攻めた予約が有利になる。この「どちらをどれだけ恐れるか」が最適quantileを決める。

## ニュースベンダー問題（newsvendor problem）として見ると予約quantileが導ける

この形は、需要が確定する前に商品在庫を何個仕入れるかを決める古典的なニュースベンダー問題（newsvendor problem）と同じ構造を持つ。商品を仕入れ過ぎれば売れ残りcost、少な過ぎれば機会損失が出る。ここでは商品在庫がKV reservation、品切れcostがpreemption、売れ残りcostがunused HBMに対応する。

論文の重要な理論結果は、preemption costとwaste costの比

`ρ = c_p / c_w`

から最適予約quantileが直接決まることである。出力長分布の累積分布関数を `F` とすると、予約すべきoutput bufferは

`F^-1(ρ / (ρ + 1))`

となり、総予約量は入力長を足した

`r* = L_in + F^-1(ρ / (ρ + 1))`

になる。この `q* = ρ/(ρ+1)` を臨界分位点（critical fractile）と呼ぶ。

具体例では、`ρ=9` なら `q*=0.9` なのでP90付近が合理的になる。`ρ=19` ならP95付近、`ρ=99` ならP99付近まで予約を厚くする。逆にpreemptionが比較的安いbatch workloadではより低いquantileが合理的になる。

つまりP90やP95自体が悪いのではない。**あるcost ratioでは正しいが、cost ratioが変わっても同じP90を固定することが問題**である。論文はこの関係を理論的に導出し、評価でも各fixed quantileが狭いregimeでしか最良にならないことを確認する。

## Wasserstein分布ロバスト最適化（Wasserstein DRO）は何を守るのか

臨界分位点の式だけなら、過去traceのempirical distributionからquantileを取ればよい。しかしそのままでは「今週のcode generationは先週より長い」「新しいprompt templateでtailが伸びた」といった分布変化に弱い。

そこで各request classについて、過去sampleからempirical distributionを作り、その分布から1-Wasserstein distanceで半径 `ε` 以内にある分布集合を考える。直感的には、各sampleの確率massを少し左右へ動かして作れる「あり得る近傍分布」の集合である。

optimizerはその集合の中で最も不利な出力長分布を想定してreservation costを最小化する。つまり平均やP95を一点推定して信じるのではなく、**少し長い側へ分布がずれた場合も含めてreserve policyを決める**。

有限context長とGPU memoryにより出力長supportには上限があるため、worst-case distributionではempirical sampleだけでなくsupport端へprobability massが移る可能性がある。これによりrobust reservationは単純なsample-average approximation（SAA）より保守側へずれ、`ε` が大きいほどdistribution shiftへ強く備える。

ただしrobustnessは無料ではない。大きな `ε` は余分なreservationを増やす。評価では `ε=0.5` でもcost premiumは1.3%未満、`ε=0.1〜0.2`では0.5%未満と報告されており、論文はこの範囲を未知shiftに対する実用的な設定と位置づける。

## 手法のあらまし

### 1. requestをclass化して、4つのdecisionを同じmodelへ入れる

requestはchat、QA、code generationなど同じ出力長分布を持ちやすいclassへ分ける。class `i` はarrival rate、入力長、cache可能なshared prefix長、latency SLO、未知のoutput length distributionを持つ。

GPU側には複数のparallelism候補があり、configuration `k` はTP degree、PP degree、必要GPU数、KV token capacity、compute/bandwidth特性を持つ。

optimizerが出すcontrol variableは次の通り。

- `z_k`: configuration `k` のserving groupを何group置くか。
- `r_i`: class `i` のrequestが入場時に予約するKV token数。
- `π_i,k`: class `i` のtrafficをconfiguration `k`へ送る割合。
- `δ_i,k`: class `i` のshared prefixをconfiguration `k`へ常駐cacheするか。

prefix cacheがある場合、requestごとの実効reservationからshared prefix分を引ける。ただしprefixを置くこと自体もKV memoryを使うため、すべてのprefixを全groupへ複製すればよいわけではない。

### 2. GPU memory capacityをreservationとthroughputへ結び付ける

単に「1 requestの予約量がGPU memory以下」というconstraintでは不十分である。productionでは同時に何request走るかが重要だからである。

論文はリトルの法則（Little's law）を使い、`arrival rate × service time` からconfigurationごとの平均同時request数を見積もる。その同時数にrequest classごとの実効reservationを掛け、safety factorを加えた総KV demandがconfigurationのKV capacityを超えないようにする。

これによって「予約量を10%増やすと1 requestが安全になる」だけでなく、「その結果batchへ載せられるrequest数が減りthroughputも落ちる」というcouplingがmodelへ入る。

### 3. queueing delayとSLOもroutingに含める

serving groupごとの待ち時間はM/G/1 queueのPollaczek–Khinchin式で近似し、routingしたrequestのexpected response timeを `waiting time + service time` として扱う。classごとのlatency SLOを超える分にはpenaltyを課す。

これによりoptimizerはmemoryだけでなく、「KV capacityは大きいがservice timeが長いgroup」「高速だが混雑するgroup」も比較できる。trafficをどこへ送るか、何group配置するか、reservationをどこまで増やすかが同じobjectiveで繋がる。

### 4. Wasserstein DROを有限の最適化問題へ変換する

「近傍にある無限個のdistributionすべてからworst caseを取る」問題をそのまま解くのは困難である。論文はKantorovich双対性（Kantorovich duality）を使い、各historical sampleに補助変数を置いた有限次元problemへ変換する。

ただしrouting割合とDRO側のdual variableが掛け合わさるため、最終問題は混合整数双線形計画（Mixed-Integer Bilinear Program; MIBLP）になる。global solverで毎回厳密に解くにはproduction規模で重い。

### 5. ブロック座標降下法（Block Coordinate Descent; BCD）で分割して解く

BCD-DROは変数を3 blockへ分けて交互に更新する。

第一blockではconfigurationとprefix cacheを固定し、routing `π` とreservation/DRO variableをalternating LPで更新する。第二blockでは現在のloadからprefix caching decision `δ` をclosed-form ruleで更新する。第三blockではGPU budget内で取り得る有限のconfiguration集合から `z` を選ぶ。

各block更新でobjectiveが悪化しないため、有限回で「他blockを固定したまま1 blockだけ変えても改善できない」blockwise optimumへ収束する。

これはrequest到着ごとにsolverを走らせる方式ではない。**数分ごとのcontrol-plane再最適化**でpolicyを作り、online data planeは事前計算したrouting probabilityとreservationをrequestへ適用するだけなので、online処理はO(1) per requestとされる。

## 評価

### まず見るところ

- **評価形式:** BurstGPT、Azure、ShareGPT等のproduction由来traceを使うtrace-driven simulation / optimization。実vLLM clusterでのend-to-end実測ではない。
- **主headline:** fixed-quantile reservationに対して総costを最大 **56%削減**。
- **cost regime:** `ρ=c_p/c_w` を2, 5, 10, 20, 50, 100へ変え、batchからreal-timeまでpreemption sensitivityの異なるserviceを模擬。
- **scalability:** 15 request class、12 parallelism候補、各class 2,000 historical samples、48-GPU cluster相当でBCD-DROは約 **257.7秒**。
- **robustness:** Wasserstein radius `ε=0.1〜0.2`ではrobustness premiumを0.5%未満に抑えながらshiftへ備える。

### fixed P90/P95は「常に悪い」のではなく、正しいregimeが狭い

BurstGPTのsingle-class cost比較では、`ρ=2`のbatch scenarioでDRO cost 184に対しP90 255、P95 365で、DROは28〜50%低い。`ρ=10`のuser-facing scenarioではDRO 587、P90 588、P95 617で差がほぼなく、P90が理論上のcritical fractileに近いためである。

`ρ=20`ではP95がDROと同じ931になり、こちらも理論通り。一方`ρ=100`のreal-time scenarioではDRO 1919に対しP90 4328、P95 3448で、DROが44〜56%低い。

この表の意味は「DROなら魔法のように常時大差で勝つ」ではない。**固定quantileはcost ratioが偶然一致する点ではほぼ最適だが、serviceのpreemption sensitivityがずれると急速に外れる**。DROはその切替を自動化する。

### 大規模problemでは厳密MIBLPよりBCDが必要になる

小規模な3 class × 4 configuration × 100 sampleではdirect MIBLP 0.07秒、BCD-DRO 0.17秒で、むしろ厳密solverの方が速い。5×5×200ではMIBLP 33.7秒に対しBCD-DRO 4.3秒。6×6×300になるとMIBLPは300秒timeoutだがBCD-DROは10.5秒で解ける。

さらに10×8×1000で81.2秒、15×12×2000で257.7秒。論文は後者を48-GPU clusterのproduction-scale例とし、5〜10分おきのrolling re-optimizationには収まるとする。

したがってBCD-DROはrequest-by-requestの高速schedulerではない。**workload telemetryを数分単位で集約してdeployment policyを更新するplanner**として読むのが正しい。

### distribution shiftには二種類の対策を重ねる

Wasserstein ambiguity setは、現在のhistorical windowに含まれる統計誤差や軽度のmodel mismatchへ備える。一方、長期的にdistributionそのものが動く場合はrecent telemetryでperiodic re-optimizationを行う。

論文はこの二つを補完関係として扱う。DROだけで何ヶ月ものdriftを永遠に吸収するのではなく、**短期の不確実性をrobust optimization、時間変化をrolling horizon**で処理する。

またdefault `ρ=10`の穏やかなtemporal splitではcritical fractileが約91%でP90に非常に近いため、DROとP90の差がほぼ消えるcaseも報告される。このnegative resultを明記している点は重要で、最大56%はすべてのworkloadで得られる数字ではない。

## 既存研究との差

PagedAttention/vLLMはKV blockを細粒度に管理する**data-plane mechanism**であり、capacity不足が起きた後にreactする。本研究はその上で「各classへ何token予約し、どのgroupへ送るか」を決める**control-plane policy**である。

H2OやSnapKVのようなKV eviction/compressionは保存するtoken数自体を減らす代わりにaccuracy trade-offを持ち得る。本研究はKV内容を削除せず、full-stateを保持したままreservationとplacementを変えるので直交する。必要なら両者を組み合わせられる。

output-length predictorを使う方式は「このrequestは1,240 token」と一点推定する。本研究はclass-level distributionとそのずれを扱い、prediction errorを直接Wasserstein ambiguityへ含める。個別requestのsemantic prediction精度を競う研究ではない。

DistServeやheterogeneous placement研究との違いは、parallelism/routingだけでなく**未知output lengthに由来するKV reservation decisionそのものをjoint variableへ追加**した点にある。

## 限界と適用境界

- **主評価はsimulation。** latency、preemption、queueingはmodel/replayで評価され、production vLLM clusterへ統合した実機end-to-end結果ではない。
- **preemption modelは実装依存。** 評価ではpreempted requestに2.5× service-time penaltyを置くcaseがあり、実runtimeがswap/resumeするかrecomputeするかでcostは変わる。
- **M/G/1近似を使う。** 極端なburst、correlated arrivals、複雑なcontinuous-batching kernel interactionは完全には表現しない。
- **request class化が前提。** class内のoutput distributionがある程度まとまっているほどhistorical samplesが意味を持つ。非常にheterogeneousなclassでは分割設計が必要。
- **BCDはglobal optimum保証ではない。** blockwise optimalへ収束するが、混合整数問題全体のglobal optimumを必ず返すわけではない。
- **re-optimizationは秒〜分級。** 最大例は257.7秒なので、秒以下のtraffic spikeへ直接追従するschedulerではない。
- **Wasserstein radiusの設定はoperator knob。** `ε`を大きくし過ぎれば過剰reservation、小さ過ぎればshift protection不足になる。
- **runtime固有のprefix sharingやKV transfer costは抽象化されている。** 実装時にはcache copy、NUMA、network topologyなどをcost modelへ追加する必要がある。

## 実装上の含意

実際のserving stackへ取り入れるなら、まずKV allocatorを書き換える必要はない。telemetryからrequest classごとのoutput length sample、arrival rate、shared prefix、SLOを集め、既存vLLM/DistServe等の外側でcontrol-plane optimizerをperiodicに回す構成が自然である。

最も直接的な教訓は、固定P90/P95を「安全率」として永久に使わないこと。preemptionをどれだけ高く評価するserviceかを`c_p`、HBM opportunity costを`c_w`として明示すれば、必要quantileは `ρ/(ρ+1)` から説明可能になる。

また個別output-length predictorがある場合でも競合ではない。predictor outputとprediction errorをclass-level distributionへ取り込み、その上でDRO reservationを掛ければ「一点予測 + safety margin」をより体系的に置き換えられる可能性がある。
