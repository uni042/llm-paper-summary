# MuxServe: Flexible Spatial-Temporal Multiplexing for Multiple LLM Serving

> LLM人気度を考慮した配置と事前充填・復号の動的共配置、共有KVキャッシュ管理を組み合わせ、複数LLM配信のGPU計算・メモリ利用率を同時に高める。

## 概要

単一の大規模言語モデル（LLM）を高速に提供するだけなら、そのモデル専用にGPUを割り当て、連続バッチ処理で要求を詰め込めばよい。しかし実際のエンドポイント事業者は、サイズも人気度も異なる多数のLLMを同時に提供する。モデルごとに固定GPU群を割り当てる空間分割では、不人気モデルのGPUが遊ぶ一方で人気モデル側が混雑する。逆に複数モデルを同じGPUへ置いて時間交替で動かすだけでは、巨大な重みやKVキャッシュがメモリを圧迫し、事前充填と復号の性質の違いも活かせない。

MuxServeは、この複数LLM配信を「どのモデルをどのGPU群へ共配置するか」と「共配置したモデルのどの推論段階をいつ同時実行するか」の二層問題として扱う。前者ではモデルの大きさだけでなく要求到着率、すなわち人気度を考慮してメモリを空間多重化する。後者では、入力プロンプトをまとめて処理して計算器を使いやすい事前充填（prefill）と、1トークンずつ生成してメモリ帯域律速になりやすい復号（decoding）を別ジョブとして扱い、互いの余剰資源を埋めるよう同時実行する。

実装は、配置アルゴリズム、適応バッチスケジューリング（Adaptive Batch Scheduling; ADBS）、統合資源管理器の三つを接続する。4ノード・計32基のNVIDIA A100 80GB GPUで19モデルを提供した評価では、合成負荷で空間分割・時間多重化ベースラインより最大1.8倍高いスループットを示し、要求の99%がサービス水準目標（Service Level Objective; SLO）を満たす条件では最大2.9倍多い要求を処理できた。

## 問題設定

複数LLM配信では、モデルのパラメータを保持するメモリ容量、要求ごとに増えるKVキャッシュ容量、GPUのストリーミングマルチプロセッサ（Streaming Multiprocessor; SM）計算資源が同時に制約になる。しかも要求率はモデルごとに異なる。大きいが不人気なモデルへ多数のGPUを固定すると計算資源が余り、小さいが人気なモデルへ少数GPUしか与えないと待ち行列が伸びる。

推論内部にも資源利用の偏りがある。事前充填は長い入力をまとめて行列演算するため計算資源を強く使う。一方、復号は各要求について逐次トークンを生成するので重み・KVキャッシュ転送の比重が高く、SMを使い切れない場面がある。MuxServeはこの非対称性を利用し、あるモデルの事前充填と別モデルの復号、あるいは複数モデルの復号を同じGPU群で重ねる。

既存の空間分割方式はモデル間干渉を避けやすいが、人気度変動で遊休GPUが生じる。単純な時間多重化はGPUを共有できても、モデル切替やKVキャッシュ競合があり、事前充填と復号を一つのジョブとして扱うと細粒度な共配置機会を失う。MuxServeの新規性は、配置・段階別スケジューリング・メモリ管理を同じ多重化方針へ揃える点にある。

## 手法

### 1. 人気度と計算需要を使う配置アルゴリズム

MuxServeはまず、複数GPUからなるデバイスメッシュへどのLLMを配置するかを決める。入力はモデル規模、要求率などのワークロード情報と利用可能GPUであり、各モデルについて要求量を処理できる並列構成候補を作る。単に重みサイズの大きいモデルを優先するのではなく、モデル規模と人気度を合わせた計算需要を重視する。

配置探索では、候補となるデバイスメッシュを列挙しながら、各LLMを置いたときの推定スループット利得が高い組合せを貪欲に選ぶ。これにより、不人気な大型モデルだけが大きなGPU群を占有し、人気な小型モデルが資源不足になる配置を避ける。人気モデルへ十分な計算資源を与えつつ、要求率の低いモデル同士や補完的な負荷を同じメッシュへ共配置する。

配置の出力は、モデルごとの固定GPU専有ではなく「複数モデルが共有するLLM unit」である。この単位が次段のADBSと統合資源管理器の境界になる。配置が不適切なら後段のスケジューラだけではGPU総量の偏りを解消できないため、長い時間尺度の資源割当を配置段階で処理する。

### 2. 事前充填と復号を分離する適応バッチスケジューリング

LLM unit内では、各モデルの要求を事前充填ジョブと復号ジョブへ分ける。ADBSは事前充填を優先しつつ、残ったSM資源へ復号ジョブを組み合わせる。これにより、計算集約的な事前充填と比較的メモリ集約的な復号を重ね、単独ジョブでは余る資源を別モデルが利用する。

ただし単純に空きSMへ仕事を詰めるだけでは、人気モデルがKVキャッシュを使い切ったり、不人気モデルが資源を占有したりする。ADBSは要求率に対して正規化した「トークンブロック使用量」を公平性指標として用い、モデルごとのKVキャッシュ割当量を動的に調整する。使用状況に応じてキャッシュブロックをモデル間で移し、要求量の多いモデルへ必要な容量を戻す。

評価の構成要素除去実験では、ADBSはラウンドロビンや先着順（First-Come First-Served; FCFS）より高いスループットを示す。報告された一条件ではFCFS 3.2要求/秒、ラウンドロビン4.9要求/秒、ADBS 6.6要求/秒であり、単なる順番制御ではなくKVキャッシュの公平な割当が人気モデルの詰まりを抑えることを示している。

### 3. SMを動的分割する並列実行系

ADBSが「何を同時に動かすか」を決めても、GPU上で計算資源を固定分割すると事前充填・復号の変化へ追随できない。MuxServeの並列実行系はNVIDIAのマルチプロセスサービス（Multi-Process Service; MPS）を利用し、LLM unit内のSMをジョブへ動的に割り当てる。

事前充填が到着すれば必要なSMを割り当て、残りを復号へ使う。ジョブ構成が変われば割当も変える。この時間方向の細粒度分割によって、配置アルゴリズムが作った空間方向の共配置を実際の実行時利用率へ変換する。

代償は同時実行による干渉である。合成負荷評価では人気度が均等な条件で多くの共配置機会が得られる一方、厳しいSLO条件では干渉によりSLO達成率がわずかに悪化する場合がある。したがって多重化率を上げれば常に尾部遅延も改善するわけではない。

### 4. 統合KVキャッシュ・重み・活性管理

統合資源管理器はGPUメモリをKVキャッシュ、モデル重み、活性の三領域として管理する。KVキャッシュは共配置モデルが共有する大きな領域として確保し、モデルごとに固定した巨大領域を持たせることによる断片化と未使用容量を減らす。

異なるモデルは層数や注意ヘッド数が異なるため、単純な同一形状キャッシュでは共有しにくい。MuxServeはヘッド単位キャッシュ（head-wise cache）を使い、一つのブロックにあるヘッドの複数トークン分のKVを格納する細粒度表現にする。ADBSが決めた割当量に応じてブロックをモデル間で移動できるため、人気度変化へ追随できる。

重み領域では、同じモデルの事前充填ジョブと復号ジョブが一つの重み複製を共有する。活性領域は実行中ジョブ向けに予約する。構成要素除去実験では、事前充填・復号を分ける計算管理だけでスループットが約1.7倍になり、統合メモリ管理を追加するとさらに約1.2倍のスループット改善と約3.6倍のSLO達成率改善が報告されている。

## 1要求がMuxServeを通る流れ

要求が到着すると、そのモデルは事前に配置アルゴリズムで決められたLLM unitへ送られる。入力プロンプトは事前充填ジョブになり、ADBSが他モデルの事前充填・復号との組合せとSM割当を決める。事前充填で生成されたKVは統合KVキャッシュのヘッド単位ブロックへ置かれる。

その後、要求は逐次復号へ移る。ADBSは各モデルの要求率とトークンブロック使用量を見てKV割当を調整しながら、空きSMへ複数モデルの復号ジョブを共配置する。同じモデルの事前充填と復号は重みを共有するため、別々の完全な重み複製を保持しない。

この流れにより、長い時間尺度では人気度に応じたモデル配置、短い時間尺度では段階別のSM多重化、メモリ側では共有KVキャッシュという三層が連動する。MuxServeの利得はどれか一つのカーネル高速化ではなく、複数モデル間で遊休計算・遊休メモリを融通することから生じる。

サービス水準目標（SLO）達成率は、設定した遅延目標以内に完了した要求の割合であり、高いほど利用者側の遅延保証を守れている。単純に平均スループットだけを最大化すると一部要求が長く待つ可能性があるため、MuxServeは両方を評価する。

### 人気度分布への感度

合成負荷では、べき乗分布の指数を変えてモデル人気度の偏りを調整する。人気度が比較的均等な場合、事前充填と復号、復号同士を共配置する機会が多く、GPU利用率を高められる。一方、SLO倍率が小さい厳しい遅延条件では同時実行干渉が発生し、SLO達成率がわずかに低くなる条件もある。

人気度が強く偏る場合は、人気モデルと不人気モデルを同じ資源へ置くことで、不人気モデルが保持している余剰メモリ・計算資源を人気モデルへ回しやすくなる。配置で人気度を明示的に扱う理由を裏付ける結果である。

### 構成要素の効果

ADBSの比較では、要求を単純なFCFSやラウンドロビンで処理するより、要求率に沿ってトークンブロックを配る方がKVキャッシュの公平性が高い。人気モデルがキャッシュ不足で詰まるのを防ぎながら、異なるモデルのジョブを同時実行できる。

統合資源管理器の除去実験では、計算資源管理とメモリ資源管理の双方が独立した利得を持つ。したがってMuxServeの結果を「配置アルゴリズムだけの1.8倍」と解釈するのは不正確で、配置、ADBS、SM動的分割、共有KVキャッシュが組み合わさったシステム全体の結果である。

## 既存研究との差

vLLM型の単一モデル配信は、ページ化したKVキャッシュや連続バッチ処理で一つのモデルのGPU利用率を高めるが、多数の異種モデル間でGPU群をどう共有するかは主問題ではない。MuxServeはその上位層で、モデル人気度と推論段階を使って複数モデル間の資源を多重化する。

空間分割方式はモデルごとにGPUを分離するため干渉が少ない一方、要求率が低いモデルの余剰資源を他モデルへ渡せない。時間多重化方式は同じGPUでモデルを交替できるが、事前充填と復号を一体として扱うと計算・メモリの補完性を十分利用できない。MuxServeはモデル配置を空間方向、推論段階を時間方向に分離し、両者を同じLLM unit内で接続する。

## 限界

第一に、共配置には干渉がある。複数ジョブを同時に走らせることで総スループットが増えても、厳しいSLO条件では個々の要求の遅延が悪化する場合がある。したがって高い多重化率が常に尾部遅延の改善を意味しない。

第二に、配置は要求率などのワークロード情報に依存する。人気度が急変すれば、長い時間尺度で決めた配置が現在の最適状態から外れる可能性がある。ADBSはLLM unit内の短期変動へ追随できるが、GPU群をまたぐ再配置とは別問題である。

第三に、評価環境はA100クラスタと論文当時のモデル・ランタイムを中心とする。異なるGPU世代、GPU間接続、混合専門家モデル、現在の分離型事前充填・復号基盤で同じ倍率になることは示していない。

第四に、モデル品質そのものを改善する方式ではない。重みや生成アルゴリズムを変更せず、配信資源を効率化する研究であるため、主評価はスループットとSLOであり、言語モデル精度の改善を主張していない。

## 一般的な実装上の含意

複数LLMを提供する場合、GPU割当をモデルサイズだけで決めると不人気モデルへ資源を固定しやすい。要求率とモデル計算量を組み合わせ、どのモデルが実際にどれだけ資源を消費するかを配置判断へ入れる必要がある。

また、事前充填と復号は同じTransformerを実行していても資源特性が異なる。これらを別ジョブとして扱うことで、計算律速とメモリ律速の処理を重ねられる。MuxServeは、この段階分離をGPU計算だけでなくKVキャッシュ割当と重み共有まで一貫させた点に価値がある。
