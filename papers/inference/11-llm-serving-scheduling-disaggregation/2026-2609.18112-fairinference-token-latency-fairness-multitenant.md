# Token Latency Fairness: Performance Isolation for Multi-Tenant LLM Serving

> 分離実行比δ以内のトークン遅延を保証するdeadline スケジューラとKV予約を統合し、高需要テナント下のp99 遅延 isolationを実現する。
## 書誌情報
- **著者**: Dev Bali, Soujanya Ponnapalli, Yichuan Wang, Natacha Crooks, Scott Shenker, Matei Zaharia
- **著者・所属**: University of California, Berkeley
- **公開**: arXiv preprint arXiv:2609.18112v1
- **種別**: arXivプレプリント
- **対象**: LLMサービング、マルチテナント、性能分離、トークン遅延、KVキャッシュ、deadline スケジューラ
- **実装**: SGLang v0.3.0 forkへ3–4k LOCのδ-fair スケジューラを実装し、Cの別worker threadでisolated-execution simulatorを動かす。本文では将来forkをopen-source予定としており、確認時点で公開コードURLはない。
## 概要
FairInferenceは、マルチテナントLLMサービングで長期処理量の公平性ではなく、各トークンの遅延を分離実行時から最大δだけに抑えるδ-トークン fairnessを定義・実装する。分離実行のトークン完了時刻を性能モデルとシミュレータで推定し、トークン deadlineを用いてプリフィル/デコードをスケジュールすると同時に、KV復元時間からクライアント別の非退避予約量を決める。SGLang v0.3.0上、単一A100 80GB・Llama-3 8B Instructで評価し、高需要テナント存在下でもwell-behaved clientのp99 TTFT/TBT/TTLTを大幅に保護する。

FairInferenceの論文固有の着想は、LLM配信の公平性を長期処理量ではなく、各利用者が公平割当だけを専有した仮想分離実行と比べて各生成トークンが最大δより余計に遅れないこととして定義し直した点にある。性能モデルと分離実行シミュレータで反実仮想のトークン完了時刻を作り、共有バッチの期限認識スケジューリングと、鍵値復元時間から逆算した利用者別退避禁止予約を結合する。これによりGPU計算待ちとGPUメモリ再分配遅延を同じトークン 遅延 guaranteeへ合成し、期限までの余剰資源は高需要利用者へ貸せる。

代表結果として、生成長干渉時p99初回トークン時間はδ=1秒、三適正需要+一高需要利用者で静的分割0.90秒、VTC 92.5秒、DLPM 73.7秒、標準SGLang 217秒に対して1.06秒。高需要利用者の長い生成がプリフィルを任意時間止める干渉を期限制御で抑える。
## 問題設定
複数利用者が共有するLLM配信では、高需要利用者がGPU計算時間、メモリ容量、帯域を占有すると適正需要利用者の初回・中間・最終トークンが大幅に遅れる。プリフィル優先の粗粒度GPUスケジューリングは長いプリフィルを細かく分割できず、共有鍵値キャッシュの最少使用順追い出しは適正需要利用者の再利用状態まで消して復元遅延を生む。VTC、DLPM、FairServeなどは長期サービス量を公平化するが個々のトークンが分離実行より何秒遅れるかを保証せず、要求単位の公平待ち行列も初回遅延または遅延連鎖を生む。GPUにはCPUのような細粒度資源分割がないため、計算スケジューリングだけを公平化してもキャッシュ復元遅延を抑えられず不十分である。
## 新規性
FairInferenceの論文固有の着想は、LLM配信の公平性を長期処理量ではなく、各利用者が公平割当だけを専有した仮想分離実行と比べて各生成トークンが最大δより余計に遅れないこととして定義し直した点にある。性能モデルと分離実行シミュレータで反実仮想のトークン完了時刻を作り、共有バッチの期限認識スケジューリングと、鍵値復元時間から逆算した利用者別退避禁止予約を結合する。これによりGPU計算待ちとGPUメモリ再分配遅延を同じトークン 遅延 guaranteeへ合成し、期限までの余剰資源は高需要利用者へ貸せる。
## 手法
### 手法のあらまし
端から端までの処理経路は、入力受付→分離実行時刻推定→トークン期限生成→プリフィル/デコード選択→鍵値予約・追い出し制御→GPU実行→状態更新→次期限判定→要求完了、の順で閉ループを形成する。入力として、各要求の利用者識別子、prompt トークン列と要求completion長、保留プリフィル待ち行列、実行中デコード集合、利用者ごとの公平割当と現在使用量、共有鍵値キャッシュ容量、管理者指定の最大追加遅延δを受け取る。最初に配置固有のプリフィル/デコード性能モデルを使う別スレッドの分離実行シミュレータが、各利用者が1/Nの公平割当だけを専有し他利用者から干渉されない仮想環境を再現し、各要求のプリフィル完了時刻と各デコード stepの間隔から第0、第1、…トークンの分離完了時刻を予測する。期限生成器は各分離完了時刻へδを加えて共有実行の絶対deadlineを作る。第0トークンではδを鍵値復元用δキャッシュとプリフィル スケジューラ用δプリフィルへ分解し、中間・最終トークンではデコード スケジューラ delayとして扱う。次にδ公平スケジューラが保留プリフィルと実行中デコードをdeadline順に並べ、各プリフィル候補を一件ずつ仮にバッチへ加える。性能モデルで候補追加後のプリフィル時間と、その後に必要なデコード時間を予測し、既存デコードの最も近いトークン deadlineを越える候補はその回では延期する。期限内であれば公平割当以下の利用者を優先して認め、高需要利用者は余剰GPU時間と鍵値容量がある場合だけ認める。安全なプリフィル バッチが一件以上あればGPUで実行し、その要求をデコード集合へ移す。安全なプリフィルが無ければ実行中デコード集合を一段進めて各要求から次トークンを生成する。新プリフィルのため既存デコード要求を撤回した場合は、その要求を再びプリフィル待ち行列へ戻して状態復元を明示的に扱う。これと並行してδ公平鍵値キャッシュは、利用者ごとの状態復元速度とδキャッシュから最低保持量ρ_iを計算する。prefix hitでは共有ブロックの参照数と利用者別使用量を更新し、未共有suffixだけを割り当てる。プリフィルまたはデコードでメモリ不足が起きた場合、各利用者の余剰s_i=max(u_i-ρ_i,0)を計算し、余剰が大きい利用者から被害者を選ぶ。追い出し後にu_i<ρ_iとなる利用者は候補から外すため、適正需要利用者の復元時間がδキャッシュを超える経路を抑える。GPU実行が終わるたびに生成済みトークン数、鍵値使用量、利用者使用量、分離実行シミュレーション、次トークン deadlineを更新し、同じ判定を要求完了まで繰り返す。最終出力は、高需要利用者へdeadlineまでの余剰計算・メモリを貸しながら、適正需要利用者の各トークンを推定分離完了時刻+δ以内に収める実行順序と鍵値配置である。失敗・例外経路も処理内に含む。候補プリフィルがデコード deadlineを破るなら延期し、鍵値追い出しが予約を割るなら別利用者を選び、burstによってシミュレータのdeadlineが現在より過去になった場合は現在時刻まで引き上げて飢餓を防ぐ。さらに共有デコードが公平割当へ分割した分離デコードより十分速いというheadroom条件が成立しない極端に軽い利用者には、どのスケジューラでも有限δを保証できないため、その範囲は保証対象外として明示する。

### δトークン公平性と期限生成
公平割当のGPU計算・帯域・メモリだけを専有した仮想分離実行を基準に、第kトークンの推定完了時刻へδを加えて共有実行の絶対期限を作る。初回、中間、最終をすべて同じ相対基準で縛るため、要求全体を一単位とした公平化の初回遅延と、各トークンを独立要求とした場合の遅延連鎖を避ける。初回δは鍵値復元とプリフィル スケジューラへ分け、後続はデコード スケジューラ delayとして扱う。分離時刻は性能モデルを使う別スレッドのシミュレータが更新し、burstで期限が過去なら現在時刻へ引き上げる。

### 期限認識プリフィル/デコードスケジューラ
保留プリフィルと実行中デコードをトークン期限で並べ、プリフィル候補を期限の早い順に試す。候補追加後の実行時間を性能モデルで予測し、既存デコードの次トークン期限を破る場合は延期する。期限を守れる場合も公平割当以下の利用者を優先し、高需要利用者は余剰資源と鍵値容量が残る場合だけ認める。安全なプリフィル バッチがあれば実行してデコード集合へ移し、無ければデコード集合を進める。必要な要求撤回はプリフィル待ち行列へ戻すため、高需要側の長いプリフィルによる任意時間の停止を防ぎつつバッチ効率を利用する。

### δ公平鍵値キャッシュ予約
共有鍵値キャッシュでは高需要利用者が大量の状態を挿入すると適正需要利用者の再利用状態が押し出され、次のデコード前に再計算または二次記憶からの復元が必要になる。FairInferenceは復元速度とδキャッシュから最低保持量ρ_iを逆算する。prefix共有では参照数と使用量を更新し、圧迫時はs_i=max(u_i-ρ_i,0)が最大の利用者から追い出す。追い出し後に予約未満になる利用者は候補から外し、デコード中の新規鍵値追加でも同じ制約を再適用する。これによりスケジューラがdeadlineを守ってもキャッシュ missで保証が崩れる抜け穴を塞ぐ。

### 分離実行性能モデルとheadroom制御
プリフィルとデコードのバッチ時間を総トークン数、最大系列長、要求数などの線形項と固定費で近似し、配置ごとにオフライン計測から係数を当てはめる。分離シミュレータでは公平割当条件へ変換してトークン間隔と完了時刻を推定し、共有側では候補プリフィルとデコード バッチの予測時間から次deadlineまでの余裕を計算する。実行量子をheadroom内へ制限し、スケジューラ オーバーヘッドや要求撤回費も固定費へ含める。共有バッチのデコードが公平割当へ分割した分離デコードより十分速いことが保証成立条件で、成立しない極端に軽い利用者には低δを保証できない。

### 全体のデータ／制御の流れ
SGLangのプリフィル優先配信へ利用者識別子、利用者別鍵値使用量、分離実行シミュレータ、期限計算、δ公平キャッシュを追加し、初回トークンのδをキャッシュ復元とプリフィルへ分解、後続デコード期限と合わせて一つのトークン遅延保証へ合成する。
## 評価条件
- **ハードウェア**: 単一NVIDIA A100 80GB。鍵値キャッシュ容量は全実験で約32万トークン。
- **ソフトウェア**: Llama-3 8B Instruct、SGLang v0.3.0を基盤としたFairInference実装。δ公平スケジューラは約3〜4千行で、分離実行シミュレータはC言語の別ワーカースレッドとしてPython本体へ動的結合する。比較は標準SGLang、VTC、DLPM、利用者ごとに鍵値容量を1/N固定する静的分割。
ミクロ評価では適正需要利用者と高需要利用者を組み合わせ、接頭辞再利用差と生成長差による干渉を測る。主要な尾部指標は初回トークン時間、トークン間隔、最終トークン時間の99百分位。処理量はプリフィル入力トークンとcompletionトークンを利用者種別・全体で測る。マクロ評価ではWildChatの実会話履歴から八利用者を構成し、七適正需要利用者と一高需要利用者を競合させる。δ=0、1秒、5秒を比較し、静的分割に対する利用率改善と既存公平スケジューラに対する遅延分離を確認する。
主評価は単一A100とLlama-3 8B Instruct、プリフィル優先型SGLangである。複数GPU、ハイブリッドプリフィル/デコードバッチ、最新SLO公平方式との広範比較、FairRAGを含むツール呼び出し合成保証は将来作業として残る。
## 主要結果
FairInferenceは高需要利用者が存在しても適正需要利用者のトークン尾部遅延を静的分割に近い水準へ抑え、余剰資源を高需要側へ貸すことで全体処理量を増やした。生成長干渉のミクロ評価では標準SGLangのp99初回トークン217秒、VTC 92.5秒、DLPM 73.7秒に対しδ=1秒で1.06秒。WildChatマクロ評価でも標準SGLang 512秒、VTC 171秒、DLPM 273秒に対し1.15秒だった。

- 生成長干渉時p99初回トークン時間 / 1.06秒 (比較対象: 静的分割0.90秒、VTC 92.5秒、DLPM 73.7秒、標準SGLang 217秒; 条件: δ=1秒、三適正需要+一高需要利用者) — 高需要利用者の長い生成がプリフィルを任意時間止める干渉を期限制御で抑える。

- 生成長干渉時p99最終トークン時間 / 3.87秒 (比較対象: 静的分割10.8秒、VTC 96.4秒、DLPM 76.5秒、標準SGLang 220秒; 条件: δ=1秒) — 共有実行のバッチ効率を使うため静的分割よりも最終完了が速くなる。

- WildChatマクロp99初回トークン時間 / 1.15秒 (比較対象: 静的分割0.83秒、VTC 171秒、DLPM 273秒、標準SGLang 512秒; 条件: δ=1秒、七適正需要+一高需要利用者) — 実会話由来の可変長・複数ターンでも尾部遅延分離を維持する。

- WildChatマクロ全体completion処理量 / 1475 tok/s (比較対象: 静的分割930 tok/s; 条件: δ=1秒) — 適正需要利用者を保護しながら余剰資源を高需要利用者へ利用させ、静的分割比約1.6倍。

- 接頭辞干渉時p99初回トークン時間 / 64.7 ms (比較対象: 静的分割57.8 ms、VTC 370.0 ms、DLPM 374.5 ms、標準SGLang 371.3 ms; 条件: δ=1秒、適正需要側working setが予約内) — δ公平キャッシュ予約が高需要側のランダム鍵値による追い出しを防ぐ。

### 負の結果・境界条件
- δを大きくすると予約保証が弱まり、接頭辞干渉ではδ=5秒のp99初回トークンが379.4msまで悪化する。理論保証には共有デコードが分離デコードより十分速いheadroom条件が必要で、極端に軽い利用者の非常に短い分離遅延は保証できない。分離時刻は配置固有の性能モデルに依存し、モデル誤差や負荷変化の影響を受ける。実装は進行中で、複数GPUやhybrid batchingは未評価。

### 結果の読み方
長期処理量の公平化だけではトークン単位の応答性を守れない。FairInferenceは『公平割当を専有したならいつ生成できたか』を基準に期限を作ることで、高需要利用者に余剰資源を貸しながら適正需要利用者の追加遅延だけを制限する。計算スケジューリングと鍵値容量の両方をδ予算へ組み込むことが重要である。
## 品質への影響
モデル計算や生成分布を近似せず、要求順序と鍵値保持方針だけを変更するため生成品質そのものへの近似誤差は導入しない。
## 既存研究との差
VTC、DLPM、FairServe、Equinoxは長期サービス量や仮想トークン消費を公平化するが、個々の初回・中間・最終トークンが分離実行から何秒遅れるかを保証しない。KairosやFairBatchingはSLOや期限を使うが、絶対的な最悪遅延を基準とする。FairInferenceは各利用者が公平割当資源を専有した仮想分離実行を基準に相対的な追加遅延δを保証する。またスケジューラだけでなく、復元遅延を持つ共有鍵値キャッシュへ利用者別予約を導入し、計算共有と容量共有の遅延を同じ保証へ合成する点が異なる。
## 限界
保証は共有環境のデコード処理が公平割当へ分割した分離環境に対して十分なバッチ効率を持つというheadroom仮定に依存する。極端に軽い利用者では分離デコードがこの下限より速くなり、低いδを保証できない。性能モデルはハードウェアとモデルごとに再当てはめが必要で、主評価は単一A100・Llama-3 8B・プリフィル優先SGLangに限定される。複数GPU、chunked/hybrid batching、FairRAGの合成保証、Kairos/FairBatchingとの実験比較は今後の作業。実装自体も論文でongoing projectとされ、公開forkは将来予定である。
## 実装状態
SGLang v0.3.0 fork上に約3〜4千行のδ公平スケジューラ、利用者別鍵値カウンタ、C言語の分離実行シミュレータを実装してA100で評価。論文時点ではforkの公開を将来作業としており、公式コードURLはまだ示されていない。
## 研究上の位置づけ
LLM配信の公平スケジューリングを、処理量公平性からリアルタイム系に近い遅延分離保証へ拡張する研究である。ストレージ分野のDelta Fair Sharingにある『分離実行比δ以内』という考えをトークンストリームへ移し、初回トークン・トークン間隔・最終トークンを同時に扱う。鍵値キャッシュの復元遅延まで保証対象に含めるため、fair スケジューラ、SLO スケジューラ、KV キャッシュ resource isolationの交差領域に位置する。
