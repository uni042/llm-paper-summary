# EcoServe: Designing Carbon-Aware AI Inference Systems

> 運用時炭素と製造由来炭素を同時最適化し、4Rと整数線形計画でLLM配信の総炭素をSLO維持のまま最大47%削減するEcoServe。

## 概要

LLM配信の環境負荷を電力だけで評価すると、GPU効率を高めるほどよいという結論になりやすい。EcoServeは、サーバー製造時に発生する**製造由来炭素（embodied carbon）**まで含めると最適点が変わることを示す。GPUは運用電力の大部分を占める一方、CPU、DRAM、SSD、マザーボードなどホスト側は、利用率が低くても製造由来炭素を抱えるためである。

さらに、主要クラウド事業者の2つの生成AIサービスのトレースでは、オフラインのバッチ推論が平均でサービスAの約21%、サービスBの約45%を占め、ピーク時にはそれぞれ約27%、55%へ達する。オンライン要求と違ってオフライン要求は締切に余裕があるため、GPUと一緒に搭載されながら余りやすいCPUを使える余地がある。

EcoServeはこの観測を、**Reduce（削減）、Reuse（再利用）、Rightsize（適正化）、Recycle（再循環）**の4原則へ落とし込み、モデル、ハードウェア、負荷トレースを整数線形計画（ILP）へ入力して構成を選ぶ。評価では性能最適、エネルギー最適、コスト最適の設計点と比較し、TTFT/TPOTなどの性能目標を概ね維持しながら総炭素排出を最大47%削減した。

## 問題設定

LLMサーバーにはGPUだけでなく、大容量DRAM、SSD、CPUが組み合わされる。これらはピーク時や特定機能のために過剰搭載されやすいが、製造した時点で炭素コストが発生する。したがって「1リクエスト当たりの電力」を下げても、必要以上のハードウェア台数・容量を抱えれば総炭素は最小にならない。

また、最も省電力なGPUが常に最も低炭素とは限らない。新世代GPUは同じ仕事を少ない電力で処理できる一方、新規製造に伴う炭素が増える。逆に旧世代を長く使えば製造由来炭素を償却できるが、運用電力が増える。このためGPU世代、負荷、地域の電力炭素強度、装置寿命を横断して判断する必要がある。

EcoServeは、オンライン要求の厳しいSLOと、オフライン要求の緩い締切を同一の資源プールで扱い、どの資源を減らし、どの遊休資源を再利用し、どのGPUを何台割り当て、どの部品を長く使うかを同時に考える。

## 手法

### 1. Reduce — 使われないホスト資源を最初から持たない

Reduceは、GPUに付随するDRAMやSSDを「一般的なサーバー構成だから」という理由で過剰搭載せず、対象LLMと配信機能に必要な容量へ削る。たとえばKVキャッシュの退避、接頭辞キャッシュ、モデル格納など、実際にホストメモリ／ストレージを使う用途から必要量を導く。

この削減が効くのは、CPU・DRAM・SSDなどのホスト系が製造由来炭素で大きな比率を持つためである。評価ではReduce単独でも、GPU構成によっておよそ16〜42%の炭素削減が得られる。低価格・小型GPUではもともとホスト側も小さいため利得が小さく、高性能GPUに大きなホスト構成を付ける場合ほど削減余地が大きい。

### 2. Reuse — 遊休CPUへオフライン推論を移す

Reuseは、オンライン配信のためにGPUサーバーへ既に搭載されているCPUを、オフライン推論のデコードへ再利用する。CPUを新規に増設するのではなく、既存ホストの余っている計算能力へ、締切に余裕のあるバッチ処理を割り当てる。

論文はCPUとGPUのルーフラインを比較し、低バッチのデコードは重み読出しが支配的なのでCPUでも利用価値がある一方、大規模なプリフィルや高バッチではGPUが有利になると整理する。このため全オフライン処理をCPUへ固定するのではなく、要求長や負荷に応じてCPU/GPUを選ぶ。実サービスAのトレースでは、この再利用によりオフライン用の追加インフラ容量を最大45%削減できるケースを示す。

CPU側の実行もそのままでは遅いため、Gemma 2B/27BのGGUF推論でタイル分割と並列化を調整し、llama.cpp基準に対して平均1.34倍、最大4.03倍のCPUデコード高速化を報告している。

### 3. Rightsize — プリフィル／デコードと負荷に合うGPU構成を選ぶ

Rightsizeは「最も新しいGPUを全ての仕事に使う」という構成を避ける。プリフィルとデコードでは演算密度が異なり、モデルサイズ、バッチ、系列長、TTFT/TPOTの余裕でも最適GPUは変わるため、異種GPUを含む候補から必要台数と配置を決める。

EcoServeのILPは、モデル・ハードウェアのプロファイル、要求到着率、オンライン／オフライン区分、SLOを使い、必要スループットを満たす資源量を選ぶ。Rightsize単独では、評価条件に応じておよそ15〜39%の炭素改善を示す。特に負荷変動が大きい場合や、低炭素電力地域で製造由来炭素の比率が高くなる場合に、過剰プロビジョニングを避ける効果が大きい。

### 4. Recycle — GPUとホストを同じ周期で交換しない

Recycleはサーバー全体を一体として更新せず、GPUとホスト側の寿命を非対称に扱う。GPUは世代更新で性能／電力効率が大きく変わる一方、CPU・DRAM・SSDなどは新GPUほど頻繁に交換する必要がない場合がある。

そのためEcoServeは、GPUだけを更新しながらホストを長期間再利用する選択肢を設計空間に入れる。これにより、新GPUの運用効率を得ながら、ホストを再製造する炭素を毎回支払うことを避ける。論文の例ではホスト寿命を4年から10年へ伸ばすような非対称更新も評価する。

### 5. 4RをILPで同時に選ぶ

4Rは独立の小技ではない。EcoServeの資源割当器は、GPU/CPU構成、メモリ量、モデル分割、オンライン／オフライン処理の配置をILPで組み合わせ、運用炭素と製造由来炭素の双方を目的関数へ入れる。

特にReuseとRightsizeはソフトウェア側で相互作用し、CPUへオフラインデコードを逃がした分だけGPU必要量が変わる。一方ReduceとRecycleは物理構成・ライフサイクル側から製造由来炭素を減らす。EcoServeの価値は、この二層を同じ炭素会計で比較できる点にある。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| ワークロード | 主要クラウド事業者の2つの生成AIサービスの実トレース |
| オフライン比率 | 平均約21% / 45%、ピーク約27% / 55% |
| ハードウェア例 | NVIDIA A100/H100等の異種GPU、Intel Sapphire Rapids CPU |
| CPU推論評価 | Gemma 2B / 27B、llama.cppをCPU側基準として比較 |
| 比較設計 | 性能最適、エネルギー最適、コスト最適（Melange等） |
| 制約 | オンラインTTFT/TPOT、オフライン期限、必要スループット |
| 炭素 | 運用時炭素 + GPU/CPU/DRAM/SSD等の製造由来炭素 |

### 代表的な結果

| 機構／観点 | 結果 | 読み取り |
|---|---:|---|
| EcoServe総合 | 最大47%炭素削減 | 性能・エネルギー・コスト最適点より総炭素が低い |
| Reduce | 約16〜42%削減 | ホストDRAM/SSD等の過剰搭載が製造由来炭素を押し上げていた |
| Rightsize | 約15〜39%改善 | 負荷と実行段階にGPU構成を合わせる効果 |
| CPU Reuse | 約25〜30%炭素削減 | オフライン比率があるクラスタで遊休CPUを活用 |
| オフライン容量 | 最大45%削減 | CPU再利用によりピーク時の追加GPU容量を圧縮 |
| CPUデコード最適化 | 平均1.34倍、最大4.03倍 | Reuseを現実的にするCPU実装上の改善 |
| 性能差 | 多くのEcoServe構成はPerf-optの約3%以内 | 炭素削減を大幅なSLO犠牲だけで達成していない |
| Reuse時TPOT | 約5%悪化するケース | 長文脈オフライン要求をCPUへ回す交換条件 |

制御面では、ILPの判断時間もクラスタ規模別に測っている。10〜160ノード規模の評価で、オンライン／オフライン、低負荷／高負荷を変えても、おおむね0.28〜1.32秒の範囲だった。これはリクエスト単位の高速経路ではなく、資源構成・スケジューリング判断を比較的粗い時間粒度で行う設計として読むべきである。

## 既存研究との差

vLLMやSGLangのような配信基盤、Splitwiseのようなプリフィル／デコード分離、Melangeのようなコスト最適化は、主に性能・資源効率・費用を目的に構成を選ぶ。EcoServeはそれらの設計空間に**製造由来炭素**を明示的に入れ、低電力な最新GPUへ集約することが総炭素最小とは限らない点を扱う。

また、単なる「電力が低い時間へ処理をずらす」炭素認識スケジューラではなく、サーバーのDRAM/SSD容量、CPU再利用、GPU世代、部品寿命まで設計変数に含める。運用時最適化と設備計画を一つの目的関数でつなぐところが主要な差である。

## 限界

EcoServeの結果は、ハードウェア製造時の炭素原単位、地域ごとの電力炭素強度、装置寿命、実サービスのオンライン／オフライン比率に依存する。製造由来炭素は電力のように実行時に直接計測できず、ライフサイクル評価モデルの仮定が変われば最適構成も変わる。

CPU Reuseも「CPUなら常に低炭素」という意味ではない。CPUはGPUより遅く、長時間動かす運用炭素が増えるため、既に存在する遊休CPUをオフラインSLOの範囲で利用できる場合に価値がある。オンライン比率が高い、オフライン締切が厳しい、CPUが飽和している、といった環境ではReuseの利得は縮む。
