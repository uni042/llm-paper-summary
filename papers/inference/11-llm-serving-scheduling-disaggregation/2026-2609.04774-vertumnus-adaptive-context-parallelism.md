# 適応型 文脈 並列性 for 本番 LLM サービング

> 接頭辞キャッシュ後の残計算量とワーカー混雑を測り、要求ごとの文脈並列度とクラスタのCP分割・統合を数秒単位で変えて、短文の通信費と長文の計算待ちを減らす。

## 概要

長い入力をLLMへ与えると、最初の1 トークンを生成する前のプリフィル（プリフィル）が重くなる。文脈並列（文脈 並列性; CP）は、この入力トークンとアテンション計算を複数GPUへ分割することでプリフィルを短縮する方法である。たとえばCP 次数 4なら、1 リクエストのプリフィルを4 GPUで協調して処理する。

ただし、CP 次数を大きくすれば常に得とは限らない。短い入力ではGPU間通信や同期の固定費が相対的に大きく、1 GPUで処理した方が効率的なことがある。一方、64K トークン級の長い入力では並列化できる計算量が十分大きく、論文のQwen3-30B-A3B測定ではCP=4が約2.71倍、CP=8が約3.91倍のプリフィル高速化を示す。つまり「1 リクエストを速くする」観点では大きなCP 次数が有利でも、同じGPU数で同時に走らせられる独立リクエスト数は減るため、クラスタ全体の処理能力とはトレードオフになる。

さらに本番 ワークロードでは、この最適点が固定されない。論文が解析した24時間トレースでは、32K トークン超の長リクエストは件数では約4〜8%しかないのに入力トークン量では約32〜54%を占め、リクエスト到着率は時間帯で3倍以上変動し、トークン単位のプレフィックス-キャッシュ hit率も約35〜55%の間で動く。したがって「入力長だけを見てCP=1/2/4/8を決める」静的な方式では、混雑とキャッシュ再利用の変化についていけない。

Vertumnusはこの問題を二つの時間尺度に分ける。

1. **リクエスト単位**では、いま存在するCP ワーカーのどれへ送るかを決める。
2. **クラスタ単位**では、固定GPU budgetをCP=1 ワーカー何台、CP=2 ワーカー何台、CP=4 ワーカー何台……へ配るか自体をワークロード変化に応じて組み替える。

加えて、ワーカー構成を変えるとプレフィックス キャッシュの所在も変わるため、グローバル プレフィックス-キャッシュ managerがKV キャッシュの配置・複製・回収まで同時に制御する。Vertumnusの重要点は、**並列性、キュー、プレフィックス 局所性を別々の問題として扱わず、同じサービング controllerの中で結び付けたこと**にある。

## 背景: 文脈並列（文脈 並列性; CP）は何をしているか

通常のcausal アテンションでは、後ろのトークンほど参照可能な過去トークンが増えるため、長いsequenceではアテンション計算が大きくなる。Vertumnusが前提とするCP実装では入力sequenceを複数rankへ分け、各rankを1 GPUへ対応させる。計算量が片側へ偏らないよう、sequenceを2C個のchunkに分け、前半の軽いchunkと後半の重いchunkを組にするジグザグ分割（zigzag partitioning）を用いる。

各GPUは自分のトークンからクエリ / key / 値を計算し、GPU間の全収集（AllGather）でkey/値を共有したうえで、自分が担当するクエリのアテンションを計算する。最終結果はsequence順に戻されるので、モデルの意味上は単GPUのcausal アテンションと等価であり、近似による品質低下を狙う手法ではない。

大きなCP 次数の利点は、長いプリフィル計算を複数GPUへ割れることと、1 GPUあたりのメモリ pressureを下げられること。一方で欠点は、AllGatherなどの通信と同期が増え、1 リクエストが占有するGPU台数も増えることである。したがってCP 次数は単なる「速度設定」ではなく、**リクエスト 遅延とクラスタ 容量を交換する資源 allocation**として扱う必要がある。

## プレフィックス キャッシュがあると「入力長」だけでは必要計算量が分からない

プレフィックス キャッシュは、同じシステム プロンプト、multi-turn 会話、エージェント共通プロンプトなどで既に計算済みのKV 状態を別リクエストから再利用する仕組みである。入力全体の長さを `L = P + R` とし、`P` をキャッシュ済みプレフィックス、`R` をまだ計算していない後置部とすると、新しく必要なアテンション量は概念的に

`W(R,P) = R×P + R(R+1)/2`

となる。前半は新しい後置部 クエリがキャッシュ済み プレフィックスを見る計算、後半は後置部内部のcausal アテンションである。

ここで重要なのは、同じ64K トークン リクエストでも「64K全部を新規計算」する場合と「60Kがキャッシュ hitして残り4Kだけ計算」する場合では、大きなCP 次数を割り当てる価値が全く違うことである。プレフィックス hitが大きければ、並列化して短縮できる残り計算が少なくなる一方、通信・同期の固定費は消えない。

そのためVertumnusは、リクエストの元の入力長ではなく、**ワーカーごとに実際に使えるキャッシュ済み プレフィックス長と、残った後置部長**からプリフィル時間を推定する。同じリクエストでもワーカー Aにはプレフィックスがありワーカー Bにはないため、サービス 時間予測もワーカーごとに変わる。

## 手法のあらまし

Vertumnusはプリフィル / デコード分離（プリフィル/デコード Disaggregation）を前提とし、最適化対象はプリフィル プールである。プリフィル プールには総GPU budget `G` があり、そのGPUをCP 次数の異なる永続ワーカーへ割り当てる。プリフィル終了後のリクエストとKV 状態は別に確保したデコード プールへ送られる。

### 1. キャッシュ-考慮 プリフィル-時間 モデル: 「そのワーカーであと何秒か」を予測する

Vertumnusは各モデル / ハードウェア構成について、キューのない状態で事前プロファイルを取り、CP 次数、キャッシュ済み プレフィックス長、uncached 後置部長からプリフィル サービス 時間を予測する軽量モデルをfitする。

論文のモデルは概ね次の要素へプリフィル時間を分解する。

- startupなどの固定費
- uncached トークン数に比例するがCPで完全には割れない通信・同期・データ movement
- キャッシュ済み プレフィックスを読み出して再利用する費用
- CP rankへ分散できる射影 / feed-forwardなどのトークン-ローカル計算
- `W(R,P)` で表される残りアテンション計算

最後の二つはCP 次数 `C` を増やすほど分担できるため小さくなるが、固定費や一部通信費は同じようには減らない。この構造によって、「長いけれどほぼキャッシュ hitしたリクエストではCP=8を使う意味が薄い」といった判断を予測値へ反映できる。

### 2. リクエスト-レベル スケジューリング: 待ち時間・実行時間・追加GPU時間を同時に見る

新しいリクエストが来ると、スケジューラは利用可能な各ワーカーについて次を調べる。

- そのワーカーのCP 次数
- 既に割り当て済みリクエストから推定した残りキュー ワークロード
- そのリクエストに対して再利用できる最長プレフィックス
- sequence長やメモリ条件を満たせるか
- ワーカーが稼働中か、再構成のためdrain中か

そして各候補ワーカーへ配置コストを計算する。直感的には次の3項である。

**待ち行列コスト（queueing-delay コスト）**は、前に何秒分のプリフィル仕事が残っているかを見る。キャッシュ hitが大きくても、そのワーカーだけ混雑していれば待ち時間で損をするためである。

**サービス-時間 コスト**は、前述のキャッシュ-考慮 モデルで「このワーカーのCP 次数とプレフィックス状態なら実行自体に何秒かかるか」を見る。係数を1より大きくするとキャッシュ hitによる短いサービス 時間を強く評価でき、関連リクエストを同じキャッシュ-holding ワーカーへ集めやすくなる。

**追加GPU時間コスト（additional GPU-時間 コスト）**は、大きなCP 次数が余分に占有する資源を罰する。たとえばCP=4で実行時間が少し短くなっても、4 GPUを長く占有してGPU-secondsが増えるならクラスタ全体では不利である。逆に非常に長いリクエストなら大幅な遅延短縮でこのpenaltyを上回り、大きいCP ワーカーが選ばれる。

この3項を一緒に見ることで、長さだけ、キャッシュだけ、負荷だけを見るスケジューラの弱点を避ける。キャッシュ-先ではhitを求めて混雑ワーカーへ集中し、負荷-先では空いているワーカーへ送るため長いプレフィックスを再計算し、長さ-先ではキャッシュ後に残った実仕事量を無視する。Vertumnusはこれらを一つの配置 コストへ統合する。

リクエストをワーカーへ割り当てた直後には、予測プリフィル ワークロードをそのワーカーへ予約する。これにより、同時に到着した複数リクエストが同じ古いキュー状態を見て一斉に同じワーカーへ流れるのを防ぐ。

### 3. クラスタ-レベル reconfiguration: 「どのCP ワーカーを何台置くか」自体を変える

リクエスト-レベル スケジューラは既存ワーカーの中からしか選べない。たとえばピーク時なのに大CP ワーカーばかり置いていると、1 リクエストあたりの遅延は短くても独立サービング laneが足りずキューが膨らむ。逆にoff-ピーク時にCP=1 ワーカーばかりならGPUが余っているのに長リクエストを1 GPUずつゆっくり処理することになる。

Vertumnusは事前の容量 プロファイルとhistorical ワークロードから初期ワーカー compositionを作り、その後はワークロードを監視して**隣接するワーカーのsplit / 統合**を行う。概念的には、複数GPUを使う大CP ワーカーを小さい複数ワーカーへ割るとスループット寄りになり、小ワーカーをまとめて大CP ワーカーへすると長リクエストの遅延寄りになる。

ここで再起動やモデル 重み再負荷を毎回行うと数秒〜数十秒以上の大きな停止になり得る。そこでVertumnusはGPU rankと通信groupを事前に用意し、モデル 重みをGPU上に保持したまま通信groupを切り替える。論文の実測では再構成全体が約1.1〜5.1秒、group切替そのものは1秒未満だった。

ワーカーを消す際には新規リクエストを止めてdrainさせ、実行中リクエストやキャッシュ 状態を壊さないようにする。したがってこれはiterationごとにCP 次数を変える方式ではなく、**数秒単位で永続 ワーカー populationを組み替える制御**である。

### 4. グローバル プレフィックス-キャッシュ management: ワーカー再構成でキャッシュ 局所性を捨てない

CP ワーカーをsplit / 統合すると、「以前そのプレフィックスを持っていたワーカーがなくなる」「同じプレフィックスでもCP 次数が変わりKV partitionの置き場所が変わる」という問題が出る。並列性だけ動的にしてキャッシュを放置すると、再構成後にプレフィックス hit率が下がり、せっかくの適応効果が再計算で相殺される。

Vertumnusはグローバル プレフィックス trieでクラスタ全体のプレフィックスを追跡し、どのワーカーがどのプレフィックス KVを持つかをスケジューラから見えるようにする。需要が複数ワーカーへ広がるとプレフィックスを複製し、ワーカー再構成時には必要に応じて異なるCP 次数間でもキャッシュを移し、不要な複製は回収する。

この設計により「キャッシュ hitを得るためだけに混雑ワーカーへリクエストを固定する」必要が減る。スケジューラは負荷に応じて別ワーカーを選びつつ、キャッシュ manager側が人気プレフィックスの配置を追随させられる。つまりプレフィックス 局所性はルーティングの絶対制約ではなく、動的に再配置できる資源になる。

## 評価

### まず見るところ

- **実機規模:** 8 ノード、合計64× NVIDIA H20-3e。主設定ではプリフィル プール 40 GPU、デコード プール 24 GPU。
- **モデル:** DeepSeek-V4-Flash-FP8、Qwen3-30B-A3B。
- **ワークロード:** L-Eval、Mooncake ツール-エージェント、匿名化本番 トレース。
- **最高負荷条件の主結果:** strongest 比較対象に対してmean TTFTを最大 **28.1%**、P90 TTFTを最大 **55.0%** 削減。
- **トークン-weighted TTFT SLO attainment:** 最大 **13.3 percentage point** 改善。
- **プレフィックス-キャッシュ managerの寄与:** Qwen3-30B-A3B / ツール-エージェント、60 req/s条件でmean TTFT **10.3%**、P90 TTFT **18.7%** 改善。

### 64K トークンでCP=8が速いことと、クラスタ全体でCP=8を増やすことは別問題

単体プロファイルでは64K トークン入力に対してCP=4が約2.71倍、CP=8が約3.91倍のプリフィル 高速化倍率を示す。しかし8 GPUで1 リクエストを処理するCP=8 ワーカーを増やすほど、同じ64 GPUで並列に受けられるリクエスト laneは減る。

Vertumnusのエンドツーエンド改善は「CP カーネルそのものを速くした」結果ではなく、リクエスト mixと負荷に応じてこの遅延-容量 trade-offを動かした結果と読むべきである。特に高負荷時のP90 TTFT改善がmeanより大きいことは、静的なワーカー compositionで生じるキュー偏りや長リクエスト待ちを抑えた効果が末尾側へ強く出ていることを示す。

### トークン-weighted SLOを見る理由

通常の「何リクエストがSLO内だったか」だけでは、短リクエストを大量に通せば良く見える可能性がある。論文はリクエストを入力トークン量で重み付けしたTTFT SLO attainmentも使う。これにより、件数は少ないが入力トークン量の大きい長い-文脈 リクエストを落として短リクエストだけ満たす方式を評価上有利にしにくい。

本番 トレースで長リクエストは件数4〜8%に対してトークン量32〜54%を占めたため、この指標はVertumnusが狙う異種 ワークロードに適している。

### キャッシュ manager単体でも無視できない

並列性構成を適応させても、キャッシュ 局所性を失えばプリフィル再計算が増える。Qwen3-30B-A3B / ツール-エージェントの60 req/sでキャッシュ managerを有効にするとmean TTFT 10.3%、P90 18.7%下がったという結果は、**CP再構成とプレフィックス キャッシュ管理を同じcontrollerで扱う必要性**を裏付ける。

## 既存研究との差

LoongServeやNanoCPのような動的CPは、稼働中 リクエスト、バッチ、iterationの実行中に並列性を変える方向が中心である。これは個々のリクエストを柔軟にする一方、固定GPU budgetを「CP 次数別の永続 ワーカーへ何台ずつ配るか」というクラスタ-レベル 容量 計画は直接解かない。また、一時的なrank groupだけでは将来リクエストのプレフィックス KVをどこに残すかが不安定になりやすい。

Vertumnusはここを逆方向から捉え、**永続 ワーカー compositionを動的資源として管理**する。その上でリクエスト ルーティングとプレフィックス キャッシュ replicationを組み合わせる。したがって新規性は新しいアテンション algorithmではなく、本番 サービング 制御 プレーンの設計にある。

## 限界と適用境界

- **プリフィル プール中心。** 最適化対象はP/D分離サービングのプリフィル側であり、デコード batching、デコード カーネル、TPOT最適化そのものは範囲外。デコード プールには別途十分な容量が必要。
- **事前profilingが必要。** キャッシュ-考慮 プリフィル モデルと容量 プロファイルはモデル / ハードウェア / CP実装ごとに取り直す必要がある。カーネルやネットワーク topologyが変われば係数も変わる。
- **再構成は瞬時ではない。** split / 統合は秒単位なので、millisecond級のburstへ直接追従する仕組みではない。短周期変動はリクエスト-レベル スケジューラで吸収し、持続的な変化をクラスタ controllerで扱う設計である。
- **大規模クラスタ評価。** 主評価は64 GPUで、小規模single-ノードやPCIeのみのconsumer GPU環境で同じ効果が出るとは示していない。
- **プレフィックス 転送にもコストがある。** キャッシュを複製し過ぎればメモリとネットワーク トラフィックを消費するため、人気度・再利用性と複製コストのtrade-offがある。
- **実装公開状況。** 論文はRTP-LLM上へ約8,000行を追加した実装を説明するが、監査時点で公開コード URLは一次資料から確認できない。

## 実装上の含意

長文脈 サービングでCPを導入する場合、最初から「入力長 → CP 次数」の固定tableだけを作ると、本番では三つの変動に負けやすい。1つ目は到着 rate、2つ目は長い/短い リクエスト比率、3つ目はプレフィックス hit率である。

Vertumnusから汎用化できる考え方は、**並列性の選択をサービス 時間だけで決めず、GPU-secondsというクラスタ 資源 コストも見ること**、そして**キャッシュ 局所性をルーティング制約として固定せず、キャッシュ 配置側も動かすこと**である。

特にエージェント ワークロードでは長いシステム/ツール プレフィックスが共有されやすいため、「このリクエストは64KだからCP=8」と決めるより、「このワーカーでは50Kがhitして残り14KしかないのでCP=2でよい」のようなキャッシュ-考慮な判断の方が実際の計算量を反映する。
