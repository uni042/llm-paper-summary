# Adaptive Context Parallelism for Production LLM Serving

> **Vertumnusは「長いrequestには多くのGPU」という単純な閾値ルールではなく、prefix cacheで実際に残った計算量、workerの混雑、追加GPU時間をrequestごとに比較しつつ、cluster全体のCP worker構成そのものも数秒単位でsplit / mergeする。**

## 概要

長い入力をLLMへ与えると、最初の1 tokenを生成する前のプリフィル（prefill）が重くなる。文脈並列（Context Parallelism; CP）は、この入力tokenとattention計算を複数GPUへ分割することでprefillを短縮する方法である。たとえばCP degree 4なら、1 requestのprefillを4 GPUで協調して処理する。

ただし、CP degreeを大きくすれば常に得とは限らない。短い入力ではGPU間通信や同期の固定費が相対的に大きく、1 GPUで処理した方が効率的なことがある。一方、64K token級の長い入力では並列化できる計算量が十分大きく、論文のQwen3-30B-A3B測定ではCP=4が約2.71倍、CP=8が約3.91倍のprefill高速化を示す。つまり「1 requestを速くする」観点では大きなCP degreeが有利でも、同じGPU数で同時に走らせられる独立request数は減るため、cluster全体の処理能力とはトレードオフになる。

さらにproduction workloadでは、この最適点が固定されない。論文が解析した24時間traceでは、32K token超の長requestは件数では約4〜8%しかないのに入力token量では約32〜54%を占め、request到着率は時間帯で3倍以上変動し、token単位のprefix-cache hit率も約35〜55%の間で動く。したがって「入力長だけを見てCP=1/2/4/8を決める」静的な方式では、混雑とcache再利用の変化についていけない。

Vertumnusはこの問題を二つの時間尺度に分ける。

1. **request単位**では、いま存在するCP workerのどれへ送るかを決める。
2. **cluster単位**では、固定GPU budgetをCP=1 worker何台、CP=2 worker何台、CP=4 worker何台……へ配るか自体をworkload変化に応じて組み替える。

加えて、worker構成を変えるとprefix cacheの所在も変わるため、global prefix-cache managerがKV cacheの配置・複製・回収まで同時に制御する。Vertumnusの重要点は、**parallelism、queue、prefix localityを別々の問題として扱わず、同じserving controllerの中で結び付けたこと**にある。

## 背景: 文脈並列（Context Parallelism; CP）は何をしているか

通常のcausal attentionでは、後ろのtokenほど参照可能な過去tokenが増えるため、長いsequenceではattention計算が大きくなる。Vertumnusが前提とするCP実装では入力sequenceを複数rankへ分け、各rankを1 GPUへ対応させる。計算量が片側へ偏らないよう、sequenceを2C個のchunkに分け、前半の軽いchunkと後半の重いchunkを組にするジグザグ分割（zigzag partitioning）を用いる。

各GPUは自分のtokenからquery / key / valueを計算し、GPU間の全収集（AllGather）でkey/valueを共有したうえで、自分が担当するqueryのattentionを計算する。最終結果はsequence順に戻されるので、モデルの意味上は単GPUのcausal attentionと等価であり、近似による品質低下を狙う手法ではない。

大きなCP degreeの利点は、長いprefill計算を複数GPUへ割れることと、1 GPUあたりのmemory pressureを下げられること。一方で欠点は、AllGatherなどの通信と同期が増え、1 requestが占有するGPU台数も増えることである。したがってCP degreeは単なる「速度設定」ではなく、**request latencyとcluster capacityを交換するresource allocation**として扱う必要がある。

## prefix cacheがあると「入力長」だけでは必要計算量が分からない

prefix cacheは、同じsystem prompt、multi-turn conversation、agent共通promptなどで既に計算済みのKV stateを別requestから再利用する仕組みである。入力全体の長さを `L = P + R` とし、`P` をcache済みprefix、`R` をまだ計算していないsuffixとすると、新しく必要なattention量は概念的に

`W(R,P) = R×P + R(R+1)/2`

となる。前半は新しいsuffix queryがcached prefixを見る計算、後半はsuffix内部のcausal attentionである。

ここで重要なのは、同じ64K token requestでも「64K全部を新規計算」する場合と「60Kがcache hitして残り4Kだけ計算」する場合では、大きなCP degreeを割り当てる価値が全く違うことである。prefix hitが大きければ、並列化して短縮できる残り計算が少なくなる一方、通信・同期の固定費は消えない。

そのためVertumnusは、requestの元の入力長ではなく、**workerごとに実際に使えるcached prefix長と、残ったsuffix長**からprefill時間を推定する。同じrequestでもworker Aにはprefixがありworker Bにはないため、service time予測もworkerごとに変わる。

## 手法のあらまし

Vertumnusはprefill / decode分離（Prefill/Decode Disaggregation）を前提とし、最適化対象はprefill poolである。prefill poolには総GPU budget `G` があり、そのGPUをCP degreeの異なる永続workerへ割り当てる。prefill終了後のrequestとKV stateは別に確保したdecode poolへ送られる。

### 1. cache-aware prefill-time model: 「そのworkerであと何秒か」を予測する

Vertumnusは各model / hardware構成について、queueのない状態で事前profileを取り、CP degree、cached prefix長、uncached suffix長からprefill service timeを予測する軽量modelをfitする。

論文のモデルは概ね次の要素へprefill時間を分解する。

- startupなどの固定費
- uncached token数に比例するがCPで完全には割れない通信・同期・data movement
- cached prefixを読み出して再利用する費用
- CP rankへ分散できるprojection / feed-forwardなどのtoken-local計算
- `W(R,P)` で表される残りattention計算

最後の二つはCP degree `C` を増やすほど分担できるため小さくなるが、固定費や一部通信費は同じようには減らない。この構造によって、「長いけれどほぼcache hitしたrequestではCP=8を使う意味が薄い」といった判断を予測値へ反映できる。

### 2. request-level scheduling: 待ち時間・実行時間・追加GPU時間を同時に見る

新しいrequestが来ると、schedulerは利用可能な各workerについて次を調べる。

- そのworkerのCP degree
- 既に割り当て済みrequestから推定した残りqueue workload
- そのrequestに対して再利用できる最長prefix
- sequence長やmemory条件を満たせるか
- workerが稼働中か、再構成のためdrain中か

そして各候補workerへ配置コストを計算する。直感的には次の3項である。

**待ち行列コスト（queueing-delay cost）**は、前に何秒分のprefill仕事が残っているかを見る。cache hitが大きくても、そのworkerだけ混雑していれば待ち時間で損をするためである。

**service-time cost**は、前述のcache-aware modelで「このworkerのCP degreeとprefix状態なら実行自体に何秒かかるか」を見る。係数を1より大きくするとcache hitによる短いservice timeを強く評価でき、関連requestを同じcache-holding workerへ集めやすくなる。

**追加GPU時間コスト（additional GPU-time cost）**は、大きなCP degreeが余分に占有するresourceを罰する。たとえばCP=4で実行時間が少し短くなっても、4 GPUを長く占有してGPU-secondsが増えるならcluster全体では不利である。逆に非常に長いrequestなら大幅なlatency短縮でこのpenaltyを上回り、大きいCP workerが選ばれる。

この3項を一緒に見ることで、長さだけ、cacheだけ、loadだけを見るschedulerの弱点を避ける。cache-firstではhitを求めて混雑workerへ集中し、load-firstでは空いているworkerへ送るため長いprefixを再計算し、length-firstではcache後に残った実仕事量を無視する。Vertumnusはこれらを一つのplacement costへ統合する。

requestをworkerへ割り当てた直後には、予測prefill workloadをそのworkerへ予約する。これにより、同時に到着した複数requestが同じ古いqueue状態を見て一斉に同じworkerへ流れるのを防ぐ。

### 3. cluster-level reconfiguration: 「どのCP workerを何台置くか」自体を変える

request-level schedulerは既存workerの中からしか選べない。たとえばピーク時なのに大CP workerばかり置いていると、1 requestあたりのlatencyは短くても独立serving laneが足りずqueueが膨らむ。逆にoff-peak時にCP=1 workerばかりならGPUが余っているのに長requestを1 GPUずつゆっくり処理することになる。

Vertumnusは事前のcapacity profileとhistorical workloadから初期worker compositionを作り、その後はworkloadを監視して**隣接するworkerのsplit / merge**を行う。概念的には、複数GPUを使う大CP workerを小さい複数workerへ割るとthroughput寄りになり、小workerをまとめて大CP workerへすると長requestのlatency寄りになる。

ここで再起動やmodel weight再loadを毎回行うと数秒〜数十秒以上の大きな停止になり得る。そこでVertumnusはGPU rankと通信groupを事前に用意し、model weightをGPU上に保持したまま通信groupを切り替える。論文の実測では再構成全体が約1.1〜5.1秒、group切替そのものは1秒未満だった。

workerを消す際には新規requestを止めてdrainさせ、実行中requestやcache stateを壊さないようにする。したがってこれはiterationごとにCP degreeを変える方式ではなく、**数秒単位でpersistent worker populationを組み替える制御**である。

### 4. global prefix-cache management: worker再構成でcache localityを捨てない

CP workerをsplit / mergeすると、「以前そのprefixを持っていたworkerがなくなる」「同じprefixでもCP degreeが変わりKV partitionの置き場所が変わる」という問題が出る。parallelismだけ動的にしてcacheを放置すると、再構成後にprefix hit率が下がり、せっかくの適応効果が再計算で相殺される。

Vertumnusはglobal prefix trieでcluster全体のprefixを追跡し、どのworkerがどのprefix KVを持つかをschedulerから見えるようにする。需要が複数workerへ広がるとprefixを複製し、worker再構成時には必要に応じて異なるCP degree間でもcacheを移し、不要な複製は回収する。

この設計により「cache hitを得るためだけに混雑workerへrequestを固定する」必要が減る。schedulerはloadに応じて別workerを選びつつ、cache manager側が人気prefixの配置を追随させられる。つまりprefix localityはroutingの絶対制約ではなく、動的に再配置できるresourceになる。

## 評価

### まず見るところ

- **実機規模:** 8 node、合計64× NVIDIA H20-3e。主設定ではprefill pool 40 GPU、decode pool 24 GPU。
- **モデル:** DeepSeek-V4-Flash-FP8、Qwen3-30B-A3B。
- **workload:** L-Eval、Mooncake Tool-Agent、匿名化production trace。
- **最高load条件の主結果:** strongest baselineに対してmean TTFTを最大 **28.1%**、P90 TTFTを最大 **55.0%** 削減。
- **token-weighted TTFT SLO attainment:** 最大 **13.3 percentage point** 改善。
- **prefix-cache managerの寄与:** Qwen3-30B-A3B / Tool-Agent、60 req/s条件でmean TTFT **10.3%**、P90 TTFT **18.7%** 改善。

### 64K tokenでCP=8が速いことと、cluster全体でCP=8を増やすことは別問題

単体profileでは64K token入力に対してCP=4が約2.71倍、CP=8が約3.91倍のprefill speedupを示す。しかし8 GPUで1 requestを処理するCP=8 workerを増やすほど、同じ64 GPUで並列に受けられるrequest laneは減る。

Vertumnusのend-to-end改善は「CP kernelそのものを速くした」結果ではなく、request mixとloadに応じてこのlatency-capacity trade-offを動かした結果と読むべきである。特に高load時のP90 TTFT改善がmeanより大きいことは、静的なworker compositionで生じるqueue偏りや長request待ちを抑えた効果がtail側へ強く出ていることを示す。

### token-weighted SLOを見る理由

通常の「何requestがSLO内だったか」だけでは、短requestを大量に通せば良く見える可能性がある。論文はrequestを入力token量で重み付けしたTTFT SLO attainmentも使う。これにより、件数は少ないが入力token量の大きいlong-context requestを落として短requestだけ満たす方式を評価上有利にしにくい。

production traceで長requestは件数4〜8%に対してtoken量32〜54%を占めたため、この指標はVertumnusが狙うheterogeneous workloadに適している。

### cache manager単体でも無視できない

parallelism構成を適応させても、cache localityを失えばprefill再計算が増える。Qwen3-30B-A3B / Tool-Agentの60 req/sでcache managerを有効にするとmean TTFT 10.3%、P90 18.7%下がったという結果は、**CP再構成とprefix cache管理を同じcontrollerで扱う必要性**を裏付ける。

## 既存研究との差

LoongServeやNanoCPのような動的CPは、active request、batch、iterationの実行中にparallelismを変える方向が中心である。これは個々のrequestを柔軟にする一方、固定GPU budgetを「CP degree別のpersistent workerへ何台ずつ配るか」というcluster-level capacity planningは直接解かない。また、一時的なrank groupだけでは将来requestのprefix KVをどこに残すかが不安定になりやすい。

Vertumnusはここを逆方向から捉え、**persistent worker compositionを動的resourceとして管理**する。その上でrequest routingとprefix cache replicationを組み合わせる。したがって新規性は新しいattention algorithmではなく、production serving control planeの設計にある。

## 限界と適用境界

- **prefill pool中心。** 最適化対象はP/D分離servingのprefill側であり、decode batching、decode kernel、TPOT最適化そのものは範囲外。decode poolには別途十分なcapacityが必要。
- **事前profilingが必要。** cache-aware prefill modelとcapacity profileはmodel / hardware / CP実装ごとに取り直す必要がある。kernelやnetwork topologyが変われば係数も変わる。
- **再構成は瞬時ではない。** split / mergeは秒単位なので、millisecond級のburstへ直接追従する仕組みではない。短周期変動はrequest-level schedulerで吸収し、持続的な変化をcluster controllerで扱う設計である。
- **大規模cluster評価。** 主評価は64 GPUで、小規模single-nodeやPCIeのみのconsumer GPU環境で同じ効果が出るとは示していない。
- **prefix transferにもcostがある。** cacheを複製し過ぎればmemoryとnetwork trafficを消費するため、人気度・再利用性と複製costのtrade-offがある。
- **実装公開状況。** 論文はRTP-LLM上へ約8,000行を追加した実装を説明するが、監査時点で公開code URLは一次資料から確認できない。

## 実装上の含意

長context servingでCPを導入する場合、最初から「入力長 → CP degree」の固定tableだけを作ると、productionでは三つの変動に負けやすい。1つ目はarrival rate、2つ目はlong/short request比率、3つ目はprefix hit率である。

Vertumnusから汎用化できる考え方は、**parallelismの選択をservice timeだけで決めず、GPU-secondsというcluster resource costも見ること**、そして**cache localityをrouting制約として固定せず、cache placement側も動かすこと**である。

特にagent workloadでは長いsystem/tool prefixが共有されやすいため、「このrequestは64KだからCP=8」と決めるより、「このworkerでは50Kがhitして残り14KしかないのでCP=2でよい」のようなcache-awareな判断の方が実際の計算量を反映する。
