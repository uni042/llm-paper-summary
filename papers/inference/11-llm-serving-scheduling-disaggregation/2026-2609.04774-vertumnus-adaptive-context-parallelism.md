# Adaptive Context Parallelism for Production LLM Serving

> requestごとにcontext parallelism（文脈並列）のdegreeを選び、workload変化に合わせてGPU群のCP構成をsplit / mergeしつつprefix cacheも配置・複製して、長context servingのTTFTとSLO達成率を改善する。

## 概要

Vertumnusは、長context requestではcontext parallelism（CP）がprefillを速くできる一方、短いrequestでは通信costとGPU占有が割に合わないという問題を扱う。さらにproduction workloadではrequest長、到着率、prefix再利用率が時間とともに変わるため、CP degreeを固定したworker構成では最適点が動いてしまう。

そこで二つの時間尺度で適応する。request levelでは、queue待ち・prefix cache hitを考慮したprefill予測時間・消費GPU時間を合わせたplacement costで異なるCP degreeのworkerへroutingする。cluster levelでは、持続的なworkload変化に応じてworkerをseconds-scaleでsplit / mergeし、同じGPU budgetを小CP workerと大CP workerへ動的に振り分ける。

## 手法

### Request-level scheduling

各requestについてworkerごとの残りprefill計算量とprefix cache hitを使ってservice timeを予測し、queue delayとGPU-time costも加味して送り先を選ぶ。入力長だけのthreshold routingと異なり、同じ長さでもcache localityや現在の混雑に応じてCP degreeを変えられる。

### Cluster-level reconfiguration

GPU上のmodel weightを保持したままcommunication groupを切り替え、CP workerをsplit / mergeする。process restartやweight reloadを避けるため、実測ではreconfiguration全体が約1.1〜5.1秒、group切替自体は1秒未満だった。

### Global prefix-cache management

worker構成が変わるとprefix localityを失いやすいため、global prefix trieでcache配置を追跡し、同じCP degree内だけでなく異なるdegree間でもprefix KVを複製・再配置する。これによりcache hitを維持するために混雑workerへrequestを縛り付ける必要を減らす。

## 評価

### まず見るところ
- **実機:** 64× NVIDIA H20-3e、8 node。prefill 40 GPU / decode 24 GPU。
- **Model:** DeepSeek-V4-Flash-FP8、Qwen3-30B-A3B。
- **Workload:** L-Eval、Mooncake Tool-Agent、匿名化production trace。
- **主要結果:** 最高load条件でstrongest baseline比、mean TTFTを最大28.1%、P90 TTFTを最大55.0%削減。token-weighted TTFT SLO attainmentは最大13.3 percentage point改善。
- **Prefix-cache効果:** Qwen3-30B-A3B / Tool-Agentの60 req/sではcache manager有効化によりmean TTFT 10.3%、P90 TTFT 18.7%削減。

### 既存との差

既存のdynamic parallelismはactive request / batch / iterationに対してCP構成を変えるものが中心なのに対し、Vertumnusは**clusterのpersistent worker composition自体**をworkloadに合わせて変える。また、CP degree変更とprefix cache localityを別問題にせず、cache replication / reclamationまで同じcontroller設計へ組み込む点が特徴。

## 限界

- optimization対象はP/D分離servingのprefill poolで、decode側のbatching / kernel自体は最適化しない。
- CPのoffline profilingとcapacity profileをmodel / hardware構成ごとに事前取得する必要がある。
- 評価は大規模64-GPU clusterであり、小規模single-node環境への効果は直接示していない。
- 論文本文ではRTP-LLM上に約8,000行を追加した実装を説明するが、確認時点で公開code URLは論文に提示されていない。

## 実装上の含意

長context servingでは「request単位でparallelismを選ぶ」だけでなく、request mixの変化に応じて**GPU budgetをparallelism degree間で再配分する制御面**が重要になる。prefix cacheを使う場合は、parallelism再構成とcache placementを独立に最適化するとlocalityを失うため、schedulerが両者を同時に見る設計が有効。
