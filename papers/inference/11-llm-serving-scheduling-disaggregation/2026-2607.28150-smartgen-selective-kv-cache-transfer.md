# SmartGen: Seamless Disaggregated LLM Inference with Selective KV Cache Transfer

> SmartGenの狙いは、事前充填（prefill）と復号（decode）を別nodeへ分離したときに生じる**「最初のtokenは出たのに、KVキャッシュ（KV cache）の転送が終わらず2 token目が長く出てこない」停止時間**を消すことである。通常は事前充填nodeが作ったKVを全量復号nodeへ転送するが、SmartGenはそれを3段階へ分ける。まず事前充填中に「多くのrequestで重要になりやすい位置」のKVだけを優先送信する。次に、復号時にquery依存で必要になった未転送KVは、その場でremote取得するが、復号node内のlocal KV読出しと並列化してnetwork往復を隠す。最後に、attention計算中にnetworkが空く時間を使って残りKVもbackground送信する。これにより、最初から全KV転送を待たずに復号へ移りつつ、後半では全KVがlocalに揃う。

## なぜ「2 token目までの時間」が問題になるのか

分離型LLM推論では、事前充填nodeがpromptを処理して最初のtokenを生成する。その後、生成を続ける復号nodeにはprompt全体のKVキャッシュが必要になる。

単純化すると処理順は、

`promptを事前充填 → 1 token目 → KVを別nodeへ転送 → 復号開始 → 2 token目 → 3 token目 ...`

となる。

ユーザーが見る最初の応答速度は最初のtokenまでの時間（Time To First Token: TTFT）で表せる。しかし1 token目をすぐ表示しても、その直後に巨大なKV転送が入って数秒止まれば、streaming応答としては明らかなstallになる。

そこでSmartGenは、**2 token目までの時間（Time To Second Token: TTST）**を重要指標として扱う。

論文のtestbedでは、長contextではKV転送時間が事前充填計算を大幅に上回る。Qwen3-14Bでbatched inputを増やした条件では、25 Gbps級network上で転送と事前充填の差が最大4.7×、15 Gbpsでは最大7.1×まで広がる。したがって「事前充填とKV転送を重ねれば隠せる」という従来の前提が成り立たない。

## なぜ高性能GPUほど問題が消えるとは限らないのか

KV転送量は主に、

- sequence length
- batch size
- layer数
- KV head数とhead dimension
- datatype

で決まり、network帯域が同じなら高速GPUに替えても転送時間そのものは大きく縮まらない。

むしろ事前充填側をA100など高速GPUへ替えると、事前充填計算だけが早く終わり、network転送を計算の裏に隠せる時間が短くなる。

SmartGenのprofilingでは、60K tokenの事前充填でA100がL20より最大1.9×速くなり、相対的にKV転送問題が目立つ。

つまりP/D分離では「computeを速くすればstage transitionも速くなる」とは限らない。

## 発想: 復号で本当に参照するKVは一部である

長context向けの疎アテンション（sparse attention）研究では、各queryが過去tokenすべてを同程度に使うわけではなく、重要なKVだけを選んでattentionしても精度を維持できることが知られている。

InfiniGenやHATAなどは、復号中のqueryまたはhidden stateから、そのstepで重要なKV indexを選ぶ。

ここからSmartGenは、

**「復号計算が全KVを読まないなら、stage切替時にも全KVを先に送る必要はないのではないか」**

と考える。

ただし単純な部分転送には2つ問題がある。

1. どのKVが重要かは本来、まだ存在しない未来のdecode queryを見ないと正確には分からない。
2. 先に送らなかったKVが後で必要になるたびにnetwork fetchすると、毎token・毎layerにnetwork round tripが入り、復号が遅くなる。

SmartGenの3経路は、この2問題を順番に解く。

## KVを3種類に分ける

SmartGenはKV entryを概念上、次の3種類として扱う。

### 1. 普遍的に重要なKV

request内容が変わっても、特定のlayer・sequence位置は繰り返し選ばれやすい。

これはdecode queryをまだ知らなくても、offline profilingからある程度予測できる。

このKVは**先行転送（proactive transfer）**で事前充填中に送る。

### 2. context依存で重要なKV

どのKVが重要になるかが、そのrequestや現在のdecode queryによって変わる部分である。

これは事前には完全に予測できないため、必要になった時点で**オンデマンド転送（on-demand transfer）**する。

### 3. 今のところ重要度が低いKV

当面のqueryでは使われなくても、将来必要になる可能性がある。

これらはcritical pathへ入れず、networkがidleな間に**投機的転送（speculative transfer）**する。

結果としてSmartGenはKVを永久にremoteへ置き続けるのではなく、時間とともに復号nodeへ全量を集めていく。

## 手法1: Profile-based proactive transfer

### 未来のqueryを知らずにどう重要KVを選ぶのか

通常の動的KV selectionはdecode queryが必要なので、prefill時点では使えない。

SmartGenは代わりに**位置的類似性（positional similarity）**を見る。

calibration datasetを一度decodeし、各layerの各token位置がどれだけ頻繁にKV selection algorithmから選ばれたかを記録する。

論文ではQwen3やLlama-3.1で、datasetやprompt長が変わっても「このlayerでは末尾側が頻繁に選ばれる」「このlayerでは広い範囲がほとんど選ばれない」といった相対位置の傾向があることを観測する。

これは特定requestの正確な未来selectionを当てるものではない。

**多数requestに共通して重要になりやすい領域を先に押さえる**ためのpriorである。

### layerをM個のblockに分けて重要度を記録する

各attention layerのsequence方向を固定数`M`のKV blockへ分割し、profiling中にそのblock内KVが選ばれた頻度の平均をblock重要度とする。

実装では`M=1024`を基本とする。

また最初の2 attention layerは常に重要とみなし、必ず転送対象へ入れる。

この結果、各layer・各相対位置blockに対するimportance matrixができる。

online requestでは、実際のprompt内容を深く解析せず、そのimportance matrixで上位blockから送る。

### 「重要なもの全部」ではなく、prefill中に隠せる量だけ送る

SmartGenは先行転送量を固定50%などにしない。

profilingで、

- 事前充填時間 `T_p`
- 全KV転送時間 `T_t`

を測り、事前充填計算と完全にoverlapできそうなtransfer量を計算する。

論文ではattention layer数を`L`、1 layerあたりのblock数を`M`として、上位`K_r` blockを選ぶ。

概念的には、

`K_r ∝ 全KV block数 × (prefill中に使えるtransfer時間 / full transfer時間)`

である。

最初のlayerがKVを生成するまでは転送できないため、実際には`L-1` layer分のprefill時間だけをoverlap可能時間として扱う。

この設計により、**networkが遅いほど最初に送る量を絞り、速いならfull transferへ近づける**ことができる。

network負荷が十分低い場合には、SmartGenは分析modelに基づいて全KV転送へ戻すこともできる。

### 実際の送信

prefill nodeが各layerのKVをCPU DRAMへoffloadすると、KVをblockへ分割し、そのblockがtop-`K_r`重要blockか確認する。

対象なら一方向RDMA WRITEでdecode nodeのKV cache poolへ直接pushする。

したがってdecode nodeがrequestを受け取る時点では、全KVではないが「将来使われる確率が高い部分」はすでにlocal側にある。

## 手法2: Parallel on-demand transfer

proactive transferだけでは、query依存KVをすべて当てられない。

実際、論文の例ではKVの半分を事前転送しても、decodeが必要とするKVの34%をremoteから追加取得する条件がある。

ここで単純に、

`remote KVを問い合わせる → 到着を待つ → local KVをGPUへ読む → attention`

とすれば、毎layerのcritical pathへnetwork round tripが入る。

SmartGenはlocalとremoteを2 laneに分ける。

### GPU上のKV maskで所在地を追う

decode nodeは各layerについて小さなint8のKV maskをGPU上に持つ。

各token位置は概ね、

- 0: padding
- 1: decode側にlocal存在
- 2: prefill側にremote存在

というstatusで表す。

prefill nodeがKV blockをRDMA WRITEするとき、対応するmaskも更新する。

KV本体とmask更新はRDMAのdoorbell batchingとin-order deliveryを利用し、「KVを書き終わってからlocal扱いになる」順序を保つ。

64K token・Qwen3-14Bの例でmask overheadは約2.5 MBと小さい。

### sparse attentionが選んだindexをlocal/remoteへ分割する

InfiniGenやHATAなどが「今回attentionで使うKV index」を出すと、SmartGenはGPU上でKV maskを引いて、

- local index
- remote index

へ分ける。

その後、

- local lane: decode nodeのCPU DRAMからGPUへ必要KVをload
- remote lane: remote indexをprefill nodeへ送り、必要KVをRDMAでdecode GPUへ取得

を同時に進める。

attentionは両laneが揃った時点で開始する。

network fetch自体をゼロにはしていないが、**remote待ち時間をlocal memory transferの裏へ重ねる**ことで、追加latencyを隠す。

## remote KVをわざわざ並べ替える理由

remoteで必要になるKVはsequence中の離れた位置に散らばる。

これを1 entryずつRDMAで送ると、小さなI/Oが大量に発生する。

SmartGenはattentionの性質を利用する。

選択済みKV集合について、sequence方向の並び順を変えても、KとVを同じ順序で入れ替える限りattention結果は変わらない。位置情報はすでにKV表現へ反映されているためである。

そこでlocal/remote maskでindexをsortし、remote entryがrow先頭側へ連続するよう並べ替える。

これによりprefill nodeはremote KVをまとまったchunkとして送りやすくなる。

さらにRDMA NICのscatter機能を使い、連続して受け取ったKVをdecode GPU内の複数rowへ配置する。論文ではNICのscatter-gather上限が例えば20 entryでも、I/O数を最大約20分の1へ減らせる例を挙げる。

## 手法3: Speculative transfer

parallel on-demand transferでも、remote laneがlocal laneより遅ければ一部network latencyは残る。

そして次tokenでも新しいKVが必要になれば、そのoverheadは何度も発生する。

SmartGenは最終的に**全KVをdecode nodeへbackground転送**し、この問題を時間とともに消す。

### なぜbackground転送する余裕があるのか

各Transformer layerでは、attention計算中は次に必要なKV indexがまだ確定していない。

そのためその時間、CPUとRDMA NICが一時的にidleになる。

SmartGenはこの隙間で、まだ送っていないKV blockをimportance順に転送する。

attention layer開始時にdecode nodeからprefill nodeへnetwork idleを通知し、prefill側が残存KVをRDMA WRITEする。

### foregroundと競合しない量に制限する

backgroundで送りすぎると、本当に必要なon-demand KVが出たときにnetworkを塞いで逆効果になる。

そこで1回のspeculative transferで送るblock数を、全体に対する**speculative ratio**で制限する。

論文のdefaultは10%。

- 20%: 約5 iterationで全KVが揃うが、初期tokenのTBTが最大1.4×悪化する条件がある。
- 5%: interferenceはほぼないが、全量完了に約20 iterationかかる。
- 10%: 約10 iterationで残りを送り切りつつ、foregroundへの影響を小さくするbalance。

つまりSmartGenは「重要な20%だけ永遠に使うsparse cache system」ではない。

**最初は少数KVだけで早くdecodeを開始し、その後network idle slotを使ってfull cache状態へ収束する**。

## 1 requestの時間軸

| 時点 | Prefill node | Decode node | Network |
|---|---|---|---|
| Prefill開始 | promptを計算 | 待機 | まだKVなし |
| 各layer完了 | KVをDRAMへ置き、重要block判定 | 受信pool準備 | top重要blockをRDMA WRITE |
| 1 token目生成 | 全KV正本を保持 | 重要KV subsetを保持 | full転送完了を待たずstage切替 |
| Decode初期 | remote requestへ応答 | sparse selectionで必要KVを決定 | local loadとremote fetchを並行 |
| Attention中 | background送信 | attention計算 | idle時間に残存KVを投機送信 |
| 数iteration後 | 正本保持 | ほぼ/全KVがlocalに揃う | remote on-demandが減少 |

## 評価環境

### Hardware

通常設定では、

- prefill: Alibaba Cloud `ecs.gn8is-2x.8xlarge` ×3
  - 各instance 2× NVIDIA L20 48 GB
  - 32 Gbps network
  - 各GPU 1 process、最大data parallel degree 6
- decode: `ecs.gn8is.4xlarge` ×1
  - 1× L20 48 GB
  - 25 Gbps network
- eRDMA
- node内: PCIe 4.0 ×16

を使う。

さらに15 GbpsのL20 instanceと、CloudLab上のV100S physical server・25 Gbps networkでもfactor analysisを行う。

### Models / workloads

models:

- Qwen3
- Llama-3.1
- Gemma-3
- Phi-4

workloadsはLongBenchから、

- MultiFieldQA
- GovReport
- SAMSum
- LCC

を利用する。

calibrationには評価setと分離した2WikiMultihopQAを使う。

defaultでは最大60K batched input token、output length 64 token、KV block数はlayerあたり1024、speculative ratio 10%で評価する。

### 比較対象

- **Full transfer**: prefill中に全KVをlayer-by-layerで送る通常方式
- **Partial transfer**: memory address順で先頭から転送可能量だけ送り、残りをon-demand取得する素朴な部分転送
- **HACK**: KVをint2へ量子化してnetwork量を削る方式
- **SmartGen + InfiniGen / HATA**: dynamic KV selectionをSmartGen転送engineへ接続

全方式を同じinference system上で比較し、full transfer側にもdecode local KV selectionを適用する。

## 評価指標

SmartGenは3つのlatencyを分けて見る。

### TTST — Time To Second Token

stage transitionがどれだけユーザーへstallを作るかを見る。

SmartGenの主目的はここを下げることである。

### TBT — Time Between Tokens

stage切替後のdecodeが、remote fetchやformat変換のため毎token遅くなっていないかを見る。

単にTTSTだけ速くして、その後ずっと遅ければ意味がないため重要である。

### CTL — Cumulative per-Token Latency

生成開始から各tokenまでの累積user-visible latencyを追い、初期stallと後続decodeの両方をまとめて評価する。

## 主要結果

### TTSTを最大4.3×短縮

LongBenchのGovReportなどを含む評価で、full transfer比で**TTSTを最大4.3×短縮**する。

Qwen3-14B / MultiFieldQA / batch size 6の例では、

- SmartGen: full transferより3.7×低いTTST
- HACK: 3.7×
- vanilla partial transfer: 2.9×

となる。

SmartGenとpartial transferの差は、単に「送るKV量が少ない」ためではない。SmartGenは最初に送るKVを重要度で選び、decodeで不足KVを取る際も2-lane化しているためである。

### 後続TBTはfull transferに近い

full transferではstage切替時に全KVを待つ代わり、decode開始後はKVがlocalに揃っているためTBTは理想的に小さい。

部分転送方式の難点は、この利点を失うことにある。

batch size 6条件では、vanilla partial transferはSmartGen/full transferよりTBTが約1.5×高い。毎iterationのremote fetchがcritical pathへ残るためである。

SmartGenはparallel on-demand + speculative transferによって、**full transferに近いTBTへ戻す**。

つまり結果は、

`stage切替だけpartial transferのように早い + 後半decodeはfull transferに近い`

という形を狙っている。

### networkが遅いほど価値が大きい

networkを32 Gbpsから15 Gbpsへ落とすと、full transferに対するSmartGenのTTST改善は2.5×から3.3×へ広がる。

partial transferに対するTBT改善も1.4×から1.6×へ広がる。

一方15 Gbpsでは、最初の2 layerのKVとKV-selection metadataだけでも帯域を強く使い、ideal caseよりTTSTが悪化する。論文はこのmetadata/initial-layer transfer overheadを今後の課題とする。

### profile-based selectionはrandom/sequentialよりremote fetchを減らす

profile-based proactive transferは、randomまたはmemory順の転送と比べ、on-demand ratioを最大51% / 38%削減し、最大1.3× / 1.2×のspeedupを示す条件がある。

これは「offline profileだけで未来queryを完全予測できる」という意味ではない。普遍的に重要な位置だけ先に送ることで、後からremote取得する頻度を減らす効果である。

### speculative transferで数iteration後にideal TBTへ近づく

speculative transferを追加すると、L20でTBTをさらに約1.3×、V100Sで約1.2×改善した条件がある。

残りKVがすべてdecode nodeへ到着するとremote fetchが不要になり、その後のTBTがfull-localのideal caseへ揃っていく。

## 精度について

SmartGenはKV selectionそのものを新しい近似algorithmへ置き換えるわけではない。

InfiniGenまたはHATAが「このstepで必要」と選んだKVがdecode nodeになければ、prefill nodeから取得してからattentionする。

そのため、offline profilingで選ばれなかったKVを単純にevictするproactive-only方式より精度を保ちやすい。

LongBenchではfull-cache baselineに近いaccuracyを報告する。

比較対象HACKは2-bit量子化でnetwork量を削るため効率は高いが、評価ではLongBench上のrelative accuracyが最低77%まで下がる条件がある。SmartGenの設計上の違いは、**転送を遅延/選択するが、必要と判定されたKVの値自体を粗くしない**ことである。

ただしSmartGenの最終精度は採用するsparse KV selection algorithmに依存するため、「full attentionと数学的に完全同一」という意味ではない。

## 既存研究との差

### DistServe / Splitwise / Mooncakeとの違い

これらはP/D分離とKV転送のsystem設計を扱う。

SplitwiseやDéjàVuはKV transferをprefill計算とoverlapするが、SmartGenは**networkが遅すぎてfull transferを計算時間内に隠せない領域**を対象にする。

Mooncakeは非常に高いRDMA bandwidthを利用できる環境を中心とするのに対し、SmartGenは15〜32 Gbps級のself-hosted cloud instanceを重視する。

### InfiniGen / HATAとの違い

InfiniGen/HATAは、decode計算時にどのKVを参照するかを減らすsparse attention / KV selection手法である。

SmartGenはそのselection結果を、**計算量削減だけでなくnode間network traffic schedulingへ再利用する**。

したがって両者は競合ではなく、SmartGenがselection algorithmを下位componentとして使う関係である。

### HACKとの違い

HACKは転送するKV自体を低bit化してnetwork byte数を減らす。

SmartGenは「いつ・どのKVを送るか」を変える。

- HACK: 全体をより小さくする
- SmartGen: 最初は必要そうなsubsetだけ送り、不足は取得し、idle時間で残りを埋める

という違いがある。

量子化とselective transferは原理的には併用可能だと論文は位置付ける。

## 一般的な実装への示唆

### 1. P/D分離の性能評価ではTTFTだけでは足りない

1 token目が速くても、KV handoffで2 token目が止まればstreaming UXは悪い。

stage boundaryを持つservingでは、TTSTやinter-token gapも独立に測る必要がある。

### 2. sparse computationのmetadataはnetwork schedulingにも利用できる

「どのdataが次に使われるか」を予測するmetadataは、GPU kernel内のmemory access削減だけでなく、CPU/GPU/node間transferのpriority付けにも使える。

### 3. 全dataを最初に揃えるか、永遠に部分dataだけ使うかの二択ではない

SmartGenは、

`最初は重要subset → demand fetch → idle時間でfull stateへ収束`

という時間的階層化を行う。

large state handoffがある他のdistributed inferenceでも応用可能なpatternである。

### 4. remote fetchはbytesだけでなくcritical-path位置を見る

同じnetwork転送量でも、local DRAM→GPU copyと直列に置くか並列に置くかでlatencyが変わる。

performance modelでは「何GB送るか」だけでなく「何とoverlapできるか」を扱う必要がある。

## 限界・注意点

- 主対象はnetwork帯域が15〜32 Gbps程度のself-hosted cloud deploymentであり、400〜800 Gbps級networkではfull transferの方が単純で有利になる領域が広がる。
- offline positional profilingの有効性はmodel・attention architecture・workload分布に依存する。論文はperiodic profilingやprompt-length group別matrixで追従する案を示すが、distribution shiftが極端ならon-demand ratioが増える。
- SmartGenのaccuracyはInfiniGen/HATAなど下位KV selection algorithmに依存する。full-cache attentionと完全に同一の計算を保証するものではない。
- GPU Direct RDMA（GDR）がないcloud instanceではmask管理をCPUへ移し、remote KVをいったんhost memoryへ受信してからGPUへcopyする必要があり、追加overheadが入る。
- speculative ratioを大きくしすぎるとbackground transferがforeground on-demand fetchと競合し、初期TBTを悪化させる。
- KV selection用metadata自体にもtransfer量があり、15 Gbps条件では最初の2 layerとmetadataがnetworkを飽和させる例がある。
- 評価は最大64 output tokenの設定が中心で、非常に長いgenerationではbackground full transfer完了後の挙動が支配的になる。
- decode nodeがremote KVを必要とする間はprefill node側に元KVを保持し続ける必要があり、prefill側DRAM容量とrequest lifetime管理のcostが残る。
