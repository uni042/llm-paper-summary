# P-PAS: Prefill-Pressure Adaptive Scheduling for Long-Context LLM Serving

> **P-PASは、chunked prefillのchunkを常に小さくも大きくもせず、「今decodeと競合しているか」に応じて1 iterationのtoken budgetを切り替える軽量なvLLM scheduler拡張である。**

## 概要

RAG、document analysis、agentic workflowでは、20K〜30K tokenの長いpromptを読み込ませて16〜64 token程度の短い回答だけ返すようなrequestが増える。この形では処理時間の多くをプリフィル（prefill）が占めるため、prefillをどうchunkへ分けてGPUへ投入するかがend-to-end latencyを大きく左右する。

vLLMには最大バッチtoken数（Maximum Number of Batched Tokens; MBT）というscheduler parameterがあり、1 iterationでprefillとdecodeを合わせて何tokenまで処理するかを制限する。長いpromptがMBTを超える場合は複数iterationへ分割されるため、MBTは実質的にchunked prefillのgranularityを決める。

ここには直感に反するtrade-offがある。

- **MBTを大きくする**と長promptを大chunkで処理でき、attentionやMLP kernelの実行効率が良くなることがある。低loadではこれが有利。
- **MBTを小さくする**と1回のprefillがGPUを占有する時間を短くでき、途中にactive decodeを細かく挟める。高loadではdecodeのstallを抑えやすい。

したがって「2kが常に良い」「16kが常に良い」ではなく、request到着状況とprefill/decode競合によって最適値が逆転する。この逆転を論文は**load-dependent MBT crossover**として整理する。

P-PAS（Prefill-Pressure Adaptive Scheduling）は、将来arrival rateを予測したり複雑なoptimizerを走らせたりせず、vLLM schedulerが既に知っている**同時prefill数とactive decode state**だけを見てMBTを動的変更する。評価構成では主に16kと2kを切り替え、低pressure時には16k、高pressureかつdecode競合時には2kへ落とす。

## 背景: chunked prefillとdecode interference

LLM inferenceは大きくprefillとdecodeに分かれる。

prefillではprompt全tokenを一度に処理し、各tokenのKV cacheを生成する。長contextでは大量のmatrix multiplicationとattentionが発生するためcompute-heavyである。一方decodeでは1 iterationにつき各requestから通常1 tokenずつ生成し、KV cacheを読み出す比率が高いためmemory-boundになりやすい。

continuous batchingでは、複数requestのprefillとdecodeを同じiterationへ混ぜられる。ここで30K tokenのprefillを1回で丸ごと走らせると、そのkernelが終わるまで既存decode requestは次tokenを生成できず、time per output token（TPOT）が悪化する。そこで長prefillを2Kなどのchunkへ分割し、chunk間にdecodeを挟めばtoken emissionを止めにくくできる。

しかしchunkを細かくし過ぎると、同じpromptを何回ものiterationとkernel launchへ分割することになる。attentionでは後半chunkほど過去KVを多く参照するうえ、kernel shapeも小さくなり、GPUを効率良く使えない場合がある。つまりchunkingは**interruptibilityを得る代わりにprefill efficiencyを失う**可能性がある。

## MBTは単なるmemory上限ではなくscheduler control variable

MBTは「1 iterationでschedulerが許可する総token量」の上限である。たとえばMBT=2kなら16,384-token promptは少なくとも8 chunkへ分かれる。MBT=16kならほぼ1 chunkで処理できる。

低pressure、つまりprefill requestが少なくactive decodeもほとんどない状況では、細かく分ける意味が薄い。この場合は大きなMBTで一気にprefillした方がkernel efficiencyの面で有利になりやすい。

逆に複数のlong prefillが同時到着し、すでにdecode中requestもある高pressure状況では、大MBTが1 iterationへ大量のprefill workを詰め込み、decode requestを長く待たせる。この場合はMBTを小さくしてprefillを細切れにし、decodeをiterationごとに進める方がend-to-end latencyが良くなる。

P-PASはこの「どちらが勝つかがloadで反転する」ことを利用する。

## 手法のあらまし

### 1. scheduling pressureを現在のprefill concurrencyから測る

P-PASは外部のtraffic predictorやoffline arrival distributionを必要としない。scheduler queueを直接見て、現在いくつのprefillが競合しているかをpressure signalとする。

論文で可視化された代表設定では、**prefill-pressure threshold = 2**。prefill pressureが小さい間は大きな16k MBTを使う。複数prefillが重なりpressureが閾値へ達し、さらにactive decodeが存在する場合は2kへ制限する。

active decodeを条件に含める理由は、decodeがいなければ大prefill chunkが誰かのtoken emissionを妨げないからである。単に「prefillが2本来たら常に2k」とするより、競合相手が実際にいる時だけsmall budgetへ落とす方が大chunk efficiencyを残せる。

### 2. low pressureではlarge MBTを維持する

queueが空いている、またはprefill concurrencyが低い場合、P-PASはMBT=16k級を維持する。これによってlong promptを少ないchunk数で処理し、FlashAttentionやMLPの大きなkernelを効率良く実行する。

このモードではTTFTを早くしやすく、短output workloadならrequest全体のlatencyも下がる。decode requestがほぼない状況でsmall chunkへ分割しても、interruptibilityの利益を使う相手がいないためである。

### 3. high pressure + active decodeではsmall MBTへ切り替える

複数prefillが競合し、既存decodeも走っている時はMBTを2k級へ下げる。prefillの1 iteration占有時間が短くなるので、decode tokenをより頻繁にscheduleできる。

このモードはprefill単体の実行効率を多少犠牲にするが、TPOTの悪化とqueue interferenceを抑える。P-PASのobjectiveはprefill benchmarkだけを最速にすることではなく、long-context request群の**end-to-end latencyをload変化全体で低く保つこと**である。

### 4. なぜ二値switchでも意味があるか

理論上は2k / 4k / 8k / 16kなど多数のbudgetを連続最適化できる。しかしP-PASはまず、load-dependent crossoverという主要現象を捉えるためにlarge/smallの軽量switchを採用する。

この単純さにより、per-iteration optimization costをほぼ増やさずvLLM schedulerへ組み込める。研究の主張も「この2値policyが全環境の数学的最適解」というものではなく、**static MBTよりruntime pressureに応じて変える方がrobust**という点にある。

## kernel-level解析: なぜlow pressureで16kが速くなるのか

論文はNVIDIA Nsight Systems / Nsight Computeでkernelをprofileし、単に「iteration回数が8回から1回に減るから」以上の差があることを示す。

Qwen2.5-3Bの1 decoder blockで同じ16,384 token promptを処理した場合、2k chunk×8回ではFlashAttentionの累積時間が **7.21 ms**、16k chunk×1回では **5.83 ms**。fused gate-up projectionも2k側 **7.16 ms**、16k側 **6.66 ms** だった。

complete prefillでもRTX 5090上で、Qwen2.5-0.5Bは2k **148.0 ms** → 16k **132.4 ms**（10.5%短縮）、Qwen2.5-3Bは **755.8 → 668.6 ms**（11.6%短縮）。一方Qwen2.5-7Bでは **1373 → 1365 ms**、差は0.6%しかない。

この結果は、large chunk advantageがmodel/hardwareに依存することを示す。小〜中modelでは大shapeでGPU利用率を上げる利益が出ても、大modelでは既にkernelが十分resourceを使っておりchunk拡大の余地が小さい場合がある。

したがってP-PASは「16kが本質的に高速」と主張しているわけではない。**low pressure時にlarge MBTが得になる構成がある一方、その差が弱い構成もある**という立場である。

## high pressureではなぜ2kが逆転するか

prefill単体では16kが速くても、active decodeと混在すると話が変わる。大きなprefill chunkは一つのiterationを長くし、その間decode requestの次token生成を遅らせる。

short-output workloadでも複数requestがburstすると、「最初のrequestを16kで効率良くprefillする」ことより、「既にdecode中のrequestをstallさせず、次prefillも公平に進める」方がsystem全体では重要になる。

small MBTは1回のprefill workを制限し、iteration boundaryを増やす。これによりschedulerがdecodeを挟む機会が増え、TPOTとtail latencyを抑える。つまり高pressure時の2k優位はGPU kernelそのものが速いからではなく、**preemption granularity / interference controlが良くなるから**である。

## 評価

### workloadとhardware

主に、長いpromptと短いoutputを持つbursty workloadを使う。

- prompt: おおむね20K〜30K token、代表条件25K token。
- output: 16〜64 token、代表条件32 token。
- models: Qwen2.5-0.5B / 3B / 7B、SmolLM3-3Bなど。
- GPU: RTX 5090を主評価とし、A100 SXM、H100 SXMへ拡張。
- baseline: static MBT 2k / 16k。
- adaptive policy: pressureに応じて主に16k↔2kを切り替える。

### RTX 5090: どちらのfixed MBTにも負けにくい

代表的な低/高pressure条件を跨ぐ評価で、P-PASは平均latencyをfixed MBT 2k比 **7.1〜13.9%**、fixed MBT 16k比 **9.0〜14.2%** 改善する。

重要なのは、2kだけをbaselineにして勝ったのでも16kだけをbaselineにして勝ったのでもない点である。load regimeによって勝者が入れ替わる二つのstatic設定に対し、P-PASは状況に応じて近い方を選ぶことで平均的に低latencyを維持する。

### A100でも傾向は再現するが、metricごとに常勝ではない

A100 SXM / Qwen2.5-3Bでは平均latencyが2k比 **7.8%**、16k比 **6.6%** 改善。SmolLM3-3Bでは **10.2% / 5.4%** 改善する。

P95 latencyも改善する一方、Qwen2.5-3Bの平均TTFTは2k比 +7.8%の改善でも16k比では **-5.6%**、SmolLM3-3Bでは16k比 **-11.7%** と悪化する条件がある。つまりlarge MBTはpromptを一気に処理するのでTTFTだけなら依然強い場合がある。

対して平均TPOTはQwen2.5-3Bで2k比 **8.2%**、16k比 **13.6%**、SmolLM3-3Bで **9.7% / 20.8%** 改善する。P-PASはTTFT単体の最小化より、prefillとdecode干渉を合わせたend-to-end latencyへ重心を置くpolicyである。

### H100でもcrossover自体は観測される

論文はH100 SXMでもload-dependent crossoverを確認している。ただし大chunkのkernel efficiency advantageの大きさはGPU/modelごとに異なる。このためthresholdやlarge/small budgetは「どのhardwareでも16k/2kで固定」と考えるより、deploymentごとにprofileして選ぶべきである。

## 主要結果の読み方

P-PASは新しいattention kernelを提案して10倍速くする研究ではない。改善幅は多くの条件で一桁〜十数%程度で、既存vLLM schedulerの1 parameterをruntime variableへ変えることで得ている。

価値は、static tuningでは「低load向けMBT」と「高load向けMBT」のどちらかを選ばなければならないのに対し、P-PASならdeploymentを再起動せず同じworkerが両regimeへ追従できることにある。trafficがburstyなRAG/agent servingでは、このrobustnessが平均benchmark以上に運用上有用になる。

## 既存研究との差

Sarathi-Serveなどのchunked prefillは、長prefillを分割してdecode stallを抑える基本mechanismを確立した。P-PASはchunked prefillそのものを発明するのではなく、**chunking granularityを決めるtoken budgetをstatic knobからruntime control variableへ変える**。

FlowPrefillのようにoperator-level preemptionやevent-driven schedulingへ踏み込む方式と比べると、P-PASはより小さな変更でvLLM既存schedulerへ乗せる設計である。その代わりpreemption granularityはMBT/chunk boundaryに縛られ、fine-grained interruptionの問題そのものを解くわけではない。

## 限界と適用境界

- **長context・短output中心。** 20K〜30K prompt / 16〜64 outputを主対象にしており、何千tokenもdecodeするworkloadでは最適pressure signalが変わる可能性がある。
- **二値budgetは普遍最適ではない。** 16k/2kとthreshold 2は評価上の代表設定であり、model/hardware別profilingが必要。
- **model/hardware依存性が大きい。** Qwen2.5-7Bではlarge-chunk prefill効率差が0.6%程度しかなく、low-pressureで16kへ上げる利益が小さい構成もある。
- **TTFT単体ではstatic 16kに負ける条件がある。** end-to-end latencyとTPOTの改善を優先するpolicyとして読む必要がある。
- **SLOを直接解くoptimizerではない。** requestごとのTTFT/TPOT deadlineやpriority classを明示的に扱わない。
- **network / multi-node要因は主題外。** single-engine内のGPU schedulingが中心で、P/D disaggregation間のKV transferなどは扱わない。

## 実装上の含意

serving engineの設定値には、deployment時に1回tuneして固定するより**runtime stateから切り替えた方がよいparameter**がある。MBTはその典型で、低load benchmarkだけでtuneするとproduction peakでdecode interferenceが増え、高loadだけでtuneするとoff-peak時にprefill efficiencyを捨てる。

P-PASのような軽量controllerを実装する場合、最初に見るべきなのはarrival rateの予測より、schedulerが既に持つcurrent queue stateである。現在prefillが何本重なっているか、active decodeがあるかは追加modelなしで取れ、実際のresource contentionへ直接対応している。

またlarge/small MBTの値は、Nsight等で「同じtoken数を大chunk/小chunkで処理した時のkernel時間」と「active decode混在時のTPOT」の両方を測って決めるのがよい。prefill-only throughputだけで選ぶと、productionで重要なinterferenceを見落とす。
