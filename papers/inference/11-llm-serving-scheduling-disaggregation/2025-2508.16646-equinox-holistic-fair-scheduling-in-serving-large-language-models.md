# Equinox: Holistic Fair Scheduling in Serving Large Language Models

> 利用者QoSとGPU効率を別カウンタで追い、MoPEで未知の実行コストを予測して統一公平性スコア順に要求を組むEquinox。

## 概要

LLMサービングでいう「公平性」は、単純なGPU時間の均等配分では定義しにくい。ある利用者は短い入力から長い出力を生成し、別の利用者は長い入力から短い出力を返す。プリフィルとデコードではGPUの使い方も異なるため、処理したトークン数が同じでも、利用者が感じる待ち時間やGPU利用効率は一致しない。

VTC（Virtual Token Counter）のような方式は、利用者ごとに消費したトークン量を仮想カウンタで追い、値が小さい利用者を優先する。これは「誰がどれだけサービスを受けたか」を扱いやすい反面、**出力トークン数が実行前には分からないこと、同じトークン数でも遅延・スループット・GPU利用率が大きく変わること**を十分扱えない。

Equinoxは公平性を2つに分ける。利用者側は、入力・出力トークンと待ち時間／実行時間をまとめた **User Fairness Counter（UFC）** でQoSを測る。運用者側は、スループットとGPU利用率をまとめた **Resource Fairness Counter（RFC）** で、GPUを非効率な要求へ偏らせていないかを見る。両者を重み付き和にした **Holistic Fairness（HF）** を利用者ごとに持ち、HFが最も小さい利用者から次の要求を選ぶ。

難しいのは、UFC/RFCに必要な出力長・実行遅延・GPU利用率・tokens/sが、要求を実際に走らせるまで確定しないことである。そこでEquinoxは **Mixture of Prediction Experts（MoPE）** を用い、要求を短・中・長などの特性別expertへ振り分けてこれらを事前予測する。ShareGPT/LMSYSと合成負荷の評価では、VTC比で最大1.3倍の処理量、最大60%低いTTFT、最大13%高い公平性を示し、GPU利用率は最大94%を維持した。

## 問題設定

### トークン数だけでは公平性を測れない

プリフィルは入力列をまとめて計算するため比較的計算律速になりやすく、デコードは1トークンずつ繰り返すためメモリ帯域・逐次実行の影響が強い。Equinoxはこの非対称性を背景に、出力トークンを入力トークンより重く扱う。

論文のUFCでは出力トークンを入力の4倍で数える。この4倍は価格モデルを真似ただけではなく、長いデコードがGPUを長時間占有し、利用者の待ち時間にも大きく効くという実行上の差を反映する。

さらに公平性を利用者側だけで決めると、GPUにとって効率の悪い組合せばかり優先し、全体スループットが落ちる可能性がある。逆にGPU利用率だけを追うと、処理しやすい要求ばかり選び、重い利用者が飢餓状態になる。Equinoxはこの2つを別カウンタで持つ。

### 「正しく公平にする」には未来の実行コストが必要

要求到着時に分かるのは主に入力長やプロンプト内容で、出力長は未知である。しかもトークン数と遅延・GPU利用率・スループットの関係は単純な線形ではなく、バッチ構成や長さによって非単調に変わる。

単一の出力長予測器だけでは、HFを構成する4指標のうち1つしか与えられない。そこでEquinoxは、まず出力長をより正確に予測し、その値と履歴プロファイルから遅延、GPU利用率、TPSまで対応付ける。

## 手法

### 1. User Fairness Counter — 利用者が受けたサービス量を遅延込みで数える

UFCは利用者ごとに保持され、要求をスケジュールすると更新される。概念的には、

[
UFC leftarrow UFC + omega_f
rac{Tokens_{in}+4,Tokens_{out}}
{1+delta(WaitTime+PredictTime)}
]

である。

(omega_f) は利用者優先度、(delta) は遅延補償係数で、論文実装では0.1を使う。長く待っている利用者は分母が大きくなり、同じトークン量でもUFCの増加が抑えられるため、その後の選択で優先されやすい。

ここでPredictTimeを含めることで、「すでに待った時間」だけでなく「選んだ後にどの程度GPUを占有しそうか」も公平性へ入れる。

### 2. Resource Fairness Counter — GPU側の効率をサービス量へ入れる

RFCは、推定tokens/s（TPS）とGPU利用率を使って更新する。

[
RFC leftarrow RFC + omega_f cdot TPS cdot Util_{GPU}
]

同じトークン数を処理する要求でも、低利用率でGPUを長く占有する要求と、高利用率で効率よく処理できる要求は運用者側から見たコストが異なる。RFCはこの差をカウンタへ入れる。

UFCだけを最小化するとユーザー待ち時間には敏感だが、非効率なバッチを作る可能性がある。RFCだけを最大化するとGPU効率は上がるが、不利な利用者を置き去りにする。両方を同時に持つことが「holistic」の意味である。

### 3. Holistic Fairness — 2カウンタを1つの優先度へまとめる

利用者 (f) のHFは、

[
HF_f = alpha cdot UFC_f + eta cdot RFC_f,quad alpha+eta=1
]

として計算する。Equinoxは利用者体験をより重く見るため (alpha>eta) を基本とし、HFが最小の利用者を次に優先するmax-min型の方針を取る。

単純なVTCなら累積トークンが少ない利用者を選ぶ場面でも、Equinoxは「その利用者は既に低遅延を得ている」「別利用者の方が長く待ち、相対的にサービス不足」と判断すれば順序を逆転させる。

### 4. MoPE — 出力長を1本のモデルで当てず、長さ領域ごとにexpertを分ける

MoPEは生成用MoEではなく、**サービング指標を予測するための専門家混合**である。まずrouterが入力長やプロンプト中の特徴語などから、要求を短・中・長の出力領域へ分類する。

その後、各領域専用のBERT-base回帰モデルが出力長を予測する。論文の主設定では3 expertを用い、LMSYSデータの出力長33/66/99パーセンタイルを基に、おおむね <53、53–210、>210 tokens の領域へ分ける。

単一proxy modelは長い出力で誤差が累積しやすい。MoPEは「すべての要求に1つの回帰関数」を当てる代わりに、異なる長さ分布を別expertへ持たせることで出力長予測を安定させる。

### 5. 出力長から遅延・GPU利用率・TPSを写像する

HFには出力長だけでなく、遅延、GPU利用率、TPSも必要である。Equinoxはオフラインプロファイルから「出力長と各指標の対応」を構築し、MoPEの出力長予測をこれらの実行指標へ写像する。

要求が完了した後は実測値でHFと対応表を更新する。したがってスケジューラは「予測で先に順序を決め、実測で後から補正する」閉ループとして動く。

### 6. continuous batching内で最小HFの要求を詰める

各スケジューリング周期で、要求は利用者の現在HFをキーにした優先キューへ入る。最小HFの利用者から要求を取り出し、GPUメモリとバッチ上限に収まるなら現在バッチへ追加してUFC/RFCを予測値で更新する。

実行後には実測値で再校正するため、予測誤差が永続的にカウンタへ蓄積するのを抑える。既存のcontinuous batching、chunked prefill、PagedAttention、KV-cache reuseと競合する置換方式ではなく、それらの上で「次に誰を入れるか」を決める薄いスケジューリング層である。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| 合成負荷 | A100 80GB + Llama-2-7B |
| 実トレース | 8×A100 40GB + Llama-2-70B |
| サービング基盤 | SGLang、vLLM、S-LoRA |
| 実トレース | LMSYS Chatbot Arena、ShareGPT |
| 比較 | FCFS、VTC |
| MoPE | 3 experts、LMSYSで学習、ShareGPTへ一般化評価 |
| 指標 | Service Rate、Service Difference、TTFT/E2E latency、Jain's Fairness Index、GPU utilization |

Service Rateは「利用者ごとの重み付き処理トークン量/秒」、Service Differenceは利用者間で累積サービス量がどれだけ離れたかを表す。Jain's Fairness Indexは1に近いほど各利用者への配分が均等である。

### 代表的な結果

| 条件 | 結果 | 読み取り |
|---|---:|---|
| 合成・balanced load | FCFS/VTC比 最大1.3倍 service rate | 公平制御で処理量を犠牲にせず、むしろバッチ効率を改善 |
| 同条件のresponse time | VTC比 最大60%低減 | token counterだけより待ち時間を直接考慮する効果 |
| ShareGPT + SGLang | P50/P90 TTFT 最大30%改善 | 実トレースでも先頭トークン待ちを抑制 |
| ShareGPT + SGLang | throughput 最大25%改善 | 高RPSでHOL blocking軽減が効く |
| ShareGPT + vLLM | Jain index 最大33%改善 | 基盤を変えても利用者間のばらつきを縮小 |
| 全体 | GPU利用率 最大94% | fairnessのためGPUを大きく遊ばせていない |
| headline | VTC比 fairness 最大13%改善 | 利用者・資源双方を統合した指標で改善 |

### MoPEの構成要素除去

FCFSや素のVTCは、要求ごとの実コストが異なる条件でService Differenceが大きい。VTCへMoPEを追加すると公平性は改善し、正確なコスト予測が重要であることが分かる。

一方、同じMoPEを使ってもEquinoxはVTC+MoPEをさらに上回る。つまり改善は「出力長予測が良くなったから」だけではなく、UFC/RFCを統合してスケジューリングするロジックにも由来する。Equinox+MoPEはOracle予測に近い結果を示し、MoPEの残余誤差よりもスケジューラ設計が支配的になる領域も確認されている。

## 既存研究との差

VTC系はトークン数を共通通貨にして利用者間のサービス量を揃える。Equinoxは、LLMの実行コストがトークンだけでは表現できないことを前提に、**利用者の遅延と、運用者のGPU効率を別々に数えてから統合する**。

また、多くの出力長予測研究はbatch planningや容量予測に使うが、Equinoxでは予測結果が直接fairness counterへ入り、要求優先度を変える。予測器とスケジューラが独立した補助機能ではなく、HFを計算するための一体設計になっている。

## 限界

Holistic Fairnessは価値判断を完全に消すわけではない。UFCとRFCの重み (alpha,eta)、出力トークン4倍、遅延補償係数 (delta) は、利用者体験と運用効率のどちらを重視するかで変わる。

MoPEはLMSYSから学習した長さ領域・特徴に依存し、未知のプロンプト分布で出力長予測が崩れればHFもずれる。実測完了後に補正する設計でも、バーストの先頭では予測誤差がスケジューリング判断へ影響し得る。

また「公平性」は本論文のHF定義に基づく。課金公平性、優先度付きSLA、ジョブ締切など別の公平性定義を採用する環境では、同じカウンタをそのまま使えるとは限らない。
