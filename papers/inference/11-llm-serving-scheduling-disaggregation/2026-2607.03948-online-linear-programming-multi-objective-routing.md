# Online Linear Programming for Multi-Objective Routing in LLM Serving

> **「一番空いているworkerへ送る」の代わりに、各workerの将来のbatch枠とKV cacheへ影価格（shadow price）を付け、requestを今入れる価値がそのresource costを上回るかでroutingする。目的関数の重みを変えるだけで、平均latency・TTFT・tail・throughputの優先順位を同じrouter内で切り替えられる。**

## 概要

複数のdecode workerを並べたLLM servingでは、prefillを終えたrequestをどのworkerへ送るかだけでlatencyが大きく変わる。典型的なround-robinはrequest数を均等にするが、1 requestがあと50 tokenで終わるか2,000 token続くかを考えない。最短queue優先やLeast Outstanding Requestsも現在のqueue長は見られるが、KV cacheの増加やrequestが将来何iterationもbatch slotを占有することまでは十分表せない。

LLM decodeが普通のweb request routingと違う点は、**今requestを1本追加することが未来の何十〜何千iterationにもresource reservationを作る**ことである。continuous batchingではactive requestは各iterationで1 tokenずつ進み、その間ずっとbatch slotを1つ使う。さらにKV cacheは生成tokenごとに増える。そのため「今このworkerに余裕がある」という一点だけでは、数百step後のresource pressureを判断できない。

もう一つの問題は、serving serviceごとに優先metricが違うこと。voice assistantではTTFTやtail TTFT、chatでは回答完了までのend-to-end latency（EEL）、batch APIではthroughputやQPSを重く見る。heuristic routerを目的ごとに作り分けると、policy logicが増え、latencyとthroughputのtrade-offを説明しにくい。

本研究はroutingをオンライン線形計画（Online Linear Programming; Online LP）として表し、requestをworkerへdispatchするdecisionへ明示的なrewardを与える。constraint側には各workerのbatch sizeとKV cache capacityを、**worker × future time step**ごとの有限resourceとして置く。

ただしdecode iterationごとに大きなLPを一から解くのは遅い。そこでLPの双対性（duality）を使い、各resourceに影価格（shadow price）を持たせる入札価格制御（bid-price control）へ変換する。混雑resourceのpriceは高く、余っているresourceは安くなる。requestのSLO rewardが、そのrequestが将来消費するresource priceの合計を上回る時だけdispatchする。

このdual priceは毎iteration、過去stateからウォームスタート（warm start）した射影勾配更新（projected gradient update）で追従させるため、full LP solveを避けられる。評価ではVidur simulator上の4×A100構成でrouting policyを比較し、CPU上のdecision overheadは約1〜2 ms/periodとされる。

## 背景: 「queueの本数」ではdecode workerのloadを表せない

例としてworker AとBのqueueにそれぞれ4 requestあるとする。Aのrequestが全部100 token前後、Bが全部2,000 token前後なら、request countは同じでもBははるかに長くbatch slotとKV memoryを占有する。

さらにKV memory demandは固定ではない。prefill終了時に既にprompt分のKVがあり、decode中に1 tokenずつ増える。request `j` のprefill footprintを `s_j`、開始後 `θ` token生成した時のKV使用量を簡略化すると、activeな間は概ね

`m_mem,j(θ) = s_j + θ + 1`

と増え、request完了後は0へ戻る。

したがってrequestを時刻 `τ` にworkerへ入れるdecisionは、現在のKVだけでなく、予測decode長 `ô_j` の期間にわたって次の二種類のresourceを予約する。

- **batch occupancy:** requestがactiveな各iterationで1 slot。
- **KV memory:** prompt KV + その時点までに増えたdecode KV。

本研究はこの「未来へ伸びるresource footprint」をcolumnとしてLPへ入れる。ここが単純なqueue length heuristicとの大きな違いである。

## router-side bufferingを前提にする

prefillを終えたrequestは、いったん中央router queueへ入る。routerは各decode deviceのstateを見て、**そのperiodですぐactive batchへ入れられるrequestだけをrelease**する。

このrelease-when-startable設計では、各workerのlocal queueを長くするのではなく、central router側で少し待たせる。そうすることで「workerへ投げた後に何秒もlocal queueで詰まる」状態を減らし、global stateを使って次の空きslotへrequestを割り当てられる。

routing decisionは「worker `g`へ送るか」だけでなく「今periodに開始するか」を含むadmission decisionとして扱われる。resourceが高価なら、すぐdispatchせずcentral queueへ残す選択もある。

## 手法のあらまし

### 1. 時間軸上のbatch slotとKV cacheをresource constraintへする

decode iterationを離散time period `k=1...T` とする。各worker `g`、各future period `k`、resource type `u`（batch / memory）の組を1つのconstraint coordinateとして持つ。

たとえばworker 2の100 iteration後について、

- batch slotがあと3枠ある
- KV cacheがあと20K token slotある

という二つのcapacityを別々に記録する。

request `j` を現在時刻からworker 2へ入れる候補actionは、その予測decode期間にわたり「batch slotを1ずつ」「KV memoryを `s_j+θ` ずつ」消費するcolumnになる。

これによりLPは、現在空いていても100 iteration後にmemory capacityを超えるassignmentを避けられる。request終了後はresource contributionが0になるため、その後のcapacityは再び解放される。

### 2. 複数SLOをrequestごとのrewardへ分解する

operatorは以下の重みを設定できる。

- throughputの重み `α`
- 平均end-to-end latencyの重み `β`
- 平均TTFTの重み `γ`
- QPSの重み `σ`
- tail EELの重み `ζ1`
- tail TTFTの重み `ζ2`

各candidate assignmentへ「このrequestを今開始したら、horizon内で何token処理できるか」「何step早く完了/開始できるか」といったpositive rewardを付ける。

ここで単純にlatencyをnegative penaltyにすると、horizonの終端近くでは「requestをdispatchしなければpenaltyを受けない」という不自然な解が出る。そこで論文はlatencyを、**今開始することで将来の待機stepを何step節約できるか**というpositive rewardへ書き換える。

### 3. tail latencyを即時rewardへ変換する

P99のようなtail latencyはrequest単体のmetricではなく、全request集合のquantileなので、そのままonline LPの1 action rewardにはしにくい。

本研究は、target threshold `t'` に対して「このassignmentならTTFTが `t'` 未満になるか」を0/1 indicatorにする。threshold内ならreward 1、超えるなら0とし、そのweight `ζ` を上げるほどthresholdを守るrequestを優先する。

たとえばtail TTFT重視なら `ζ2` を上げる。評価では`ζ2`を増やすほど固定TTFT thresholdを満たすrequest割合が概ね増え、operator weightがtail quantile controlとして機能することを確認している。

これは数学的に「weightを1つ設定すれば必ず厳密P99保証になる」というhard constraintではない。**tail SLOを満たすassignmentへ強いrewardを与え、empirical satisfaction rateを押し上げるsoft control**として読むべきである。

### 4. LP双対から影価格（shadow price）を得る

primal LPを毎period解く代わりに、各resource constraintへdual variable `p_i` を付ける。これが影価格（shadow price）で、「そのresource capacityをもう1 unit増やせたらobjectiveがどれだけ改善するか」、つまりscarcityの価格を表す。

workerのKV cacheが逼迫していればmemory priceが上がり、将来batch slotが埋まりそうならbatch occupancy priceが上がる。逆に余裕のあるworker/time slotのpriceは低くなる。

request `j` をworker `g`へ入れるcandidateについて、将来使うresource vectorを `a` とすると、総resource costは概念的に

`a^T p`

で計算できる。routerはrequestのSLO reward `r` と比較し、

`r - a^T p > 0`

ならそのassignmentにはscarce capacityを消費する価値があると判断する。これが入札価格制御（bid-price control）である。

この考え方は航空券やhotelのrevenue managementに近い。今の安い予約で最後の席を埋めるより、将来もっと価値の高い需要に席を残すべきかをbid priceで判断する。本研究では「席」がfuture batch slot / KV memory、「売上」がSLO-weighted serving benefitに置き換わる。

### 5. dual priceをonlineで追従させる

trafficが変わればscarce resourceも変わるので、priceは固定できない。論文はhistoryからcandidate actionをmini-batch samplingし、observed resource demandと用意したscarcity targetの差からprojected subgradientを計算する。

前periodのpriceを初期値にして少数回だけupdateし、negative priceは0へprojectionする。これをwarm-started projected mini-batch updateとして実装する。

full horizonの全constraintをdenseに計算するのではなく、candidate requestがactiveになるfuture slotだけを触る。per-step complexityは概ね `O(KGH)`、`K`がgradient update回数、`G`がworker数、`H`がeffective look-ahead horizon。workerごとのprice tensorはgradient上分離できるためparallel updateも可能とする。

実装microbenchmarkではIntel i9-13980HX CPU上でrouting computationが約**1〜2 ms/period**。A100のdecode iterationを10〜30 ms程度と想定しており、64 worker超へscaleしてもcontrol pathが主bottleneckになりにくいという見積もりを示す。ただしこれはproduction clusterのnetwork/control-plane実測ではなく、algorithm implementationのCPU overhead評価である。

## 評価

### 評価条件

- **simulator:** Vidur。
- **decode resources:** 4 parallel NVIDIA A100 GPUをsimulation。
- **real workload:** LMSYS-Chat-1Mからrequestをsample。
- **arrival:** Poisson arrival、`λ=0.4`をstable、`λ=0.5`をslight overloadとして評価。
- **prediction noise:** perfect decode-length predictionに加え、`ô_j ~ Uniform(0.8 o_j, 1.2 o_j)`、つまり真値の±20%範囲のnoiseも評価。
- **baselines:** Round Robin、Least Outstanding Requests（LOR）、Power-of-2等。
- **synthetic:** prefill/decode比の異なるworkloadでも追加検証。

注意点として、論文の表記ではsynthetic P/D比説明に本文上やや紛らわしい箇所があるため、実装上は「decode-side resource pressureが強いregimeと弱いregimeを比較する」評価として読むのが安全である。

### noisy length predictionでも平均EELを45.75%削減

真のdecode lengthに対して±20% noiseを入れた代表設定で、Round Robin比の改善率は次の通り。

- 平均EEL: **45.75%改善**
- P95 EEL: **42.49%改善**
- P99 EEL: **25.85%改善**
- throughput: **0.90%改善**
- SLO metric: **11.10%改善**

同じ表でLORは平均EEL 0.67%、P99 6.19%、Power-of-2は平均1.30%、P99 6.06%の改善にとどまる。

ここから分かるのは、この代表objective settingでは主な利益がraw throughput増ではなく、**同程度のcapacityを使いながらrequestの開始タイミングとworker配置を変えてqueueing/tailを削ったこと**である。throughputのheadlineを0.9%だけ見て「効果が小さい」と判断すると狙いを誤る。

### objective weightを変えるとPareto trade-offが動く

平均latency重視、tail重視、throughput重視のweightを変えると、routerが改善するmetricも系統的に変わる。すべてのmetricを同時に最大改善できるわけではなく、latencyを強く優先すればcapacityを空けるためthroughput側のgainが小さくなる。

これは欠点というより、論文がheuristicより明示的にしたい部分である。operatorが「なぜこのrequestを今dispatchしなかったか」を、現在のresource priceとSLO rewardの差として説明できる。

### tail weightはthreshold satisfactionへ効く

tail TTFT thresholdを固定し `ζ2` だけを増やすexperimentでは、そのthresholdを満たすrequest割合が平均的に上昇する。これによりtail objectiveをrewardへ分解するmechanismが意図通り機能することを確認している。

ただしsimulation noiseはあり、weightからP99などのquantileが解析的に一意決定されるわけではない。productionでhard SLO保証が必要ならadmission controlやconstraint-based formulationを追加する必要がある。

### decode-side congestionが弱いとoptimizationの利益も小さくなる

synthetic experimentでは、decodeが長くbatch/KV constraintsがbindingになるworkloadほどbid-price routingの差が出やすい。逆にdecodeが短く、decode workerのbatch slotとKV cacheがほとんどscarceにならないregimeでは、objective weightを変えてもperformance差は小さくなる。

これは影価格の直感と一致する。resourceが余っていればshadow priceは低く、どのworkerへ送っても大差がない。**optimizationが最も効くのは、KV/batch scarcityが実際にrouting decisionを制約する時**である。

## 既存研究との差

Round RobinやPower-of-2は軽量でrobustだが、現在/未来のKV demandを明示的なresource budgetとして扱わず、SLO trade-offもparameter weightとして表せない。

load-aware routingはqueue長やpredicted workをscore化するが、そのscoreの係数はheuristicになりやすい。本研究ではfuture batch slotとKV capacityをLP constraintとして置き、scarcityをdual priceとして導出するため、「memoryが詰まったので高価になった」というresource-level interpretationが得られる。

Prebleなどprefix-aware routingがprefix localityとloadのtrade-offを中心に扱うのに対し、この研究の主題はdecode sideのtime-coupled capacityである。prefix cache hitをreward/costへ組み込むことは理論上拡張できるが、主modelの中心ではない。

Geometry-aware schedulingのようにsingle worker内のrequest orderingを工夫する研究とも層が違う。こちらは**central routerから複数decode workerへいつreleaseするか**を決める。

## 限界と適用境界

- **主評価はVidur simulation。** production vLLM clusterへrouterを統合したend-to-end実機評価ではない。
- **decode length predictionに依存。** ±20% noiseではrobustだが、予測がsystematically biasedする場合やheavy-tailを大きく外す場合はfuture resource columnそのものが誤る。
- **finite look-ahead horizon。** future capacityを完全無限先まで追うのではなく、有限horizonで近似する。非常に長いgenerationではhorizon designが重要になる。
- **decode iteration timeを比較的安定と仮定。** P/D分離decode workerを主modelとし、prefill interferenceが大きいmixed systemではiteration-time variabilityを別途扱う必要がある。appendixでextensionは議論されるが主評価ではない。
- **tail metricはsoft reward。** `ζ`を上げることでtail satisfactionを押し上げるが、hard percentile SLOを数学的に保証するconstraintではない。
- **objective weightはoperatorが決める。** frameworkはtrade-offを透明化するが、business/applicationにとって正しい `α,β,γ,σ,ζ` を自動決定するわけではない。
- **prefix locality / network transferを主model化していない。** P/D分離のKV transfer cost、cross-node topology、cache reuseを含めるにはresource model拡張が必要。
- **routing overhead 1〜2 msはCPU microbenchmark。** 64+ workerで「bottleneckにならない」という主張はcomplexity/CPU measurementに基づき、real distributed control-planeのRPC overheadまで含む保証ではない。

## 実装上の含意

この研究から最も汎用化しやすい考え方は、routing scoreを「queue長 × 手動係数」の寄せ集めにせず、**未来resourceの機会費用（opportunity cost）として表す**ことにある。

既存runtimeへ導入するなら、最初から完全なOnline LPを実装する必要はない。各decode workerについて、

- active batch slots
- free KV blocks
- requestごとのpredicted remaining tokens

を将来数百stepぶんforecastし、memory / batchのscarcity scoreをdual-price風に更新するだけでも設計思想を取り込める。

またservice tierごとに別routerを作る代わりに、interactive tierではTTFT/tail weight、batch tierではthroughput/QPS weightを高くする構成なら、同じrouting engineを使い回せる。重要なのはweight changeによるtrade-offをoffline simulatorで校正し、hard SLOが必要な部分は別constraint/admission ruleで補うことである。
