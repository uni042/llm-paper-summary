# Online Linear Programming for Multi-Objective Routing in LLM Serving

> batch枠とKV cacheをresource budgetとして価格付けし、各requestのSLO便益がresourceのshadow priceを上回るworkerへroutingすることで、latency・TTFT・throughput・tail SLOを同じonline最適化で調整するLLM router。

## 問題設定

複数decode workerを持つLLM servingでは、到着したrequestをどのworkerへ送るかがqueueing、batch効率、KV cache pressureを左右する。Round RobinやLeast Outstanding Requestsのようなheuristicは軽い一方、どのSLOをどれだけ優先するかを明示的に表現しにくい。

本研究はroutingをonline linear programmingとして定式化し、throughput、end-to-end latency、TTFT、tail latencyなど複数目的の重みをoperatorが明示的に設定できるようにする。

## 新規性

- workerのbatch capacityとKV cacheを有限resourceとして線形制約へ入れる。
- 各resourceにdual variable由来のshadow priceを持たせ、混雑するresourceほど高価として扱う。
- requestを割り当てた際のSLO-weighted rewardとresource priceを比較するbid-price controlを使う。
- 毎requestでLPを最初から解き直さず、warm-startしたprojected first-order updateでdual priceを追跡し、millisecond級routing decisionを狙う。
- reward weightを変えるだけでlatency / throughput / tail SLOのtrade-offを同じframework内で操作できる。

## 手法

requestが到着すると、各workerへ送った場合に消費するbatch slot・KV memoryと、得られるSLO rewardを見積もる。resourceが逼迫しているworkerではshadow priceが高くなるため、単純にqueueが短いだけでは選ばれない。

routerは「そのrequestを受け入れて得る便益」が「将来requestのためにresourceを残す価値」を上回るassignmentを選ぶ。dual priceは過去の混雑状態から継続更新するため、traffic変化へonlineに追従する。

## 評価条件

Vidur simulatorへrouterを統合し、LMSYS-Chat-1M等のworkloadとdecode-length prediction errorを含む条件で、Round Robin等のstandard routing baselineと比較する。したがって主評価はsimulationであり、production clusterの実測と区別する必要がある。

## 主な結果

論文報告では複数SLO regimeでend-to-end latency、TTFT、throughput、tail performanceをbaselineより改善する。decode length予測へnoiseを加えた条件でも改善が維持され、reward weightを変えることでSLO達成方向を系統的に移動できる。

報告例では20%のlength prediction error条件でRound Robinに対し平均end-to-end latencyを45%以上削減し、P99 latencyも約25.85%改善するcaseが示される。

## 既存研究との差

Prebleやload-aware routerはprefix localityやqueue負荷など特定のcostを中心にroutingする。本研究はそれらを個別heuristicとして固定せず、**複数SLOとresource scarcityをreward / shadow priceへ明示的に埋め込む**点が中心である。

Geometry-Aware Schedulingが1 worker内のrequest orderingをKVの時空間volumeで決めるのに対し、本研究は複数decode worker間のdispatchを扱う。

## 限界

- 主評価がVidur simulationであり、network jitter、runtime overhead、実GPU上のscheduler相互作用は別途実機検証が必要。
- reward weightの選び方はservice policyに依存し、自動的に唯一の最適値が決まるわけではない。
- output lengthやresource demandの予測誤差が大きい場合、rewardとpriceの見積もり精度が落ちる。
- 線形近似で表しにくいbatching相互作用やprefix sharingをどこまで組み込めるかは今後の課題。

## 一般的な実装上の含意

LLM routerを「最も空いているworkerを選ぶ」heuristicだけで設計せず、GPU memoryやbatch slotをscarce resourceとして価格付けすると、複数SLOの優先度をoperatorが説明可能な形で調整できる。特にlatencyとthroughputのどちらを重視するかがserviceごとに異なる環境で有用な設計方向である。
