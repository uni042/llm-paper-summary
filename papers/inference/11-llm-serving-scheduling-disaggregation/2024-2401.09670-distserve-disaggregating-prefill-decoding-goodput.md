# DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving

> prefillとdecodeを別GPU群へ分け、それぞれのGPU数・model分割方法・配置場所を、最初のtokenまでの時間とその後のtoken間隔の目標に合わせて別々に決めることで、両phaseの干渉をなくすserving system。

## 概要

DistServeは、prefillとdecodeを同じGPU上でbatchingすると、**長いprefillがdecodeを遅らせる干渉**と、性質の違う2 phaseが同じGPU数・model分割方法を共有する制約が発生することに着目する。

そこでprefill instanceとdecode instanceを別GPUへ完全に分離し、それぞれに最適なGPU数・tensor / pipeline parallelismを選ぶ。さらにclusterのnetwork帯域を考慮し、prefillで生成したKV cacheをdecode側へ送るcostが大きくならないよう物理配置も決める。

評価の中心は単純なtoken/sではなく、**TTFT（最初のtokenが返るまで）とTPOT（その後1 token生成する平均時間）の両方について、設定した目標を守りながら何request/s処理できるか**である。論文では、この「SLOを守って処理できたrequest rate」をgoodputと呼ぶ。

## 問題設定

prefillはprompt全体を並列処理するため計算性能を使いやすい。一方decodeは1 tokenずつ生成し、weightやKVを読むmemory bandwidthの影響を強く受ける。両者を同じGPUで交互に処理すると、長いprefillの間にdecodeが止まり、token間隔が不安定になる。

また、同じmodelでもprefillとdecodeで最適なmodel分割方法は一致しない。prefillでは1 requestを多GPUへ分けてlatencyを短くする価値が高い場合がある一方、decodeではbatch sizeやKV容量とのtrade-offが異なる。

P/Dを分けるとKV cache transferが必要になるが、DistServeは**GPU配置をnetwork topologyへ合わせることで、そのtransferを大きなbottleneckにしない**ことを狙う。

## 手法

### 1. Prefill / decodeを独立したGPU poolへ分ける

prefill instanceはpromptを処理してKV cacheを生成し、decode instanceはそれを受け取ってcontinuous batchingへ追加する。

同じGPUで2 phaseをinterleaveしないため、prefill latencyの変動がdecode TPOTへ直接干渉しない。またprefill GPU群とdecode GPU群を別々に増減できる。

### 2. Phaseごとに「何GPUでどうmodelを分けるか」を別々に選ぶ

model、workloadのinput / output length分布、TTFT / TPOT目標、GPU memoryを入力し、使えるparallelism構成を列挙する。

実機profileから作ったsimulatorで各構成について、

- 何request/s処理できるか
- TTFT / TPOT目標を何%のrequestで守れるか
- 何GPU必要か

を見積もる。

その上でprefill / decodeそれぞれについて、**1 GPUあたりにSLOを守って処理できるrequest数が最も多い構成**を選び、traffic rateを支えられるだけinstance数を用意する。

### 3. Networkが遅い場合はKVを遠くへ送らない配置にする

cross-node networkが十分速いclusterではprefill / decode instanceを比較的自由に配置できる。

一方cross-node bandwidthが低いclusterでは、prefillとdecodeで対応するmodel stageを同じnodeへ置き、KV transferを高速なnode内NVLinkへ寄せる。

つまり「prefillとdecodeを別GPUへ分ける」ことと、「KVを無条件に別nodeへ飛ばす」ことは別であり、**networkが遅いなら物理的には近くへ置く**。

### 4. Prefillでは似た長さのrequestをまとめる

prefill側ではprompt長のばらつきが大きいと、短いrequestが長いrequestの処理完了を待つ無駄が生じる。

DistServeは近いprompt長のrequestを同じbatchへまとめ、1 batch内の処理量差を減らす。

### 5. Decode側に空きができてからKVを取りに行く

arrival burst時にprefillからKVを一斉pushすると、decode GPU memoryが溢れやすい。

そこでdecode instanceが新しいrequestを処理できる状態になった時点でKVを取りに行く。これによりprefill GPU側を一時的なKV待機場所として使い、decode側のmemory oversubscriptionを避ける。

workload分布が長期的に変わった場合はprofile統計を更新し、配置とinstance数を再計算する。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Cluster | 4 nodes / 32 GPUs |
| GPU | NVIDIA A100 SXM 80GB、各node 8GPU |
| Intra-node | NVLink |
| Cross-node | 25Gbps |
| Models | OPT-13B / 66B / 175B等 |
| Precision | FP16 |
| Workloads | ShareGPT、HumanEval、LongBench |
| Baselines | vLLM、DeepSpeed-MII |
| SLO attainment | 主評価90% |

classic MHAのOPTを使い、KV transferに厳しい条件でdisaggregationを評価している。

### SLOを守って処理できるrequest rate

様々なmodel / workload / SLOで、DistServeはbaselineに対して**最大7.4×高いrequest rate**、または同じrequest rateで**最大12.6×厳しいlatency目標**を満たした。

DeepSpeed-MII比では1.6〜7.4×高いrequest rateを報告する。LongBenchを使ったOPT-66B summarizationでは、vLLM比4.3×高いrequest rateかつ12.6×厳しいSLOを達成した条件がある。

### KV transfer overhead

OPT-175BでもKV transferは総latencyの**0.1%未満**で、95%以上のrequestが30ms未満のtransfer delayだった。

ただしこれはcross-node 25Gbpsを直接使っても常に軽かったという意味ではない。networkが遅い構成では、**prefill/decodeの対応stageを同じnodeへ置き、KVをNVLinkで送る配置を選んだ結果**である。

### Placement optimization

prefill / decodeを同じparallelismに固定せず、workloadごとに異なる構成を選ぶことで両phaseのloadを釣り合わせる。simulatorの予測は実機結果とよく一致し、最大規模のsearchも数分以内としている。

## 既存研究との差

### vLLMとの違い

vLLMはcontinuous batchingでprefillとdecodeを同一worker上へ混在させる。throughputには有利だが、長いprefillがdecode TPOTへ干渉する。

DistServeは2 phaseを物理的に分離し、**TTFTを改善するためのGPUと、decode token間隔を守るためのGPUを別々に用意する**。

### Sarathi / chunked prefillとの違い

chunked prefillは大きなprefillを小分けにしてdecode tokenと同じbatchへ載せ、同じGPU上で干渉を抑える。DistServeは共存方法を工夫するのではなく、resource pool自体を分離する。

### Mooncakeとの違い

DistServeの中心は**prefill/decodeごとのGPU配分とnetwork-aware placement**であり、KVは同じrequestをprefillからdecodeへ引き継ぐために移す。

後続のMooncakeは、KVをcluster全体へ保存し、別requestでもprefix cacheとして再利用するところまで広げる。

## 限界

- 主評価modelはOPT系列で、GQA / MQA / MLAではKV transfer量とparallelismの最適点が変わる。
- placementは観測したworkload distributionが一定期間は安定することを前提とし、急変時はreplanning lagがある。
- P/D間でKV transferが必要なため、十分なNVLink / high-speed networkがないclusterでは配置制約が強くなる。
- prefill / decode poolを別々に確保するため、非常に低loadな時間帯には片方のGPUが余る可能性がある。
- chunked-prefill等との比較は当時のsystem設計を前提としており、後年のhybrid schedulerではtrade-offが変わり得る。

## 一般的な実装上の含意

LLM servingではGPU数をmodel全体に一括配分するより、**prefillとdecodeを別serviceとしてcapacity planningする**方がSLO付きcostを下げられる場合がある。

ただしstage分離だけでは不十分で、KV sizeとnetwork topologyを含めてphysical placementを決める必要がある。またtoken/s最大化と「latency目標を守って処理できるrequest数」最大化では最適configurationが異なるため、production servingでは後者を直接optimization objectiveにする価値がある。
