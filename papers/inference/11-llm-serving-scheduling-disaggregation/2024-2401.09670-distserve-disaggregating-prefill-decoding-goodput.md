# DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving

> prefillとdecodeを別GPUへ分離し、各phaseのGPU数・model parallelism・physical placementをTTFT / TPOT SLOに合わせて別々に最適化することで、phase間干渉を除きper-GPU goodputを高めるserving system。

## 概要

DistServeは、prefillとdecodeを同じGPU上でbatchingすると、**長いprefillがdecodeを遅らせる干渉**と、性質の違う2 phaseが同じresource allocation / parallelismを共有する制約が発生することに着目する。

そこでprefill instanceとdecode instanceを別GPUへ完全に分離し、それぞれに最適なGPU数・tensor / pipeline parallelismを選ぶ。さらにclusterのcross-node bandwidthを考慮し、prefillで生成したKV cacheをdecode側へ送るcostが大きくならないphysical placementを探索する。

目標metricは単純なtoken/sではなく、**TTFTとTPOTの両方を指定割合以上のrequestで満たせる最大request rate / GPU（per-GPU goodput）**である。

## 問題設定

prefillはprompt全体を並列処理するcompute-heavyなphaseで、decodeは1 tokenずつ生成しweight / KV accessの影響を強く受ける。両者をcolocateするとprefill処理が長い間decode batchを待たせ、TPOTが悪化する。

また、同じmodelでもprefillとdecodeでgoodputを最大化するparallelismは一致しない。たとえばprefillはより多いGPUで1 requestのlatencyを縮める価値がある一方、decodeではbatch sizeやmemory容量とのtrade-offが異なる。

P/Dを分けるとKV cache transferが必要になるが、DistServeはmodern clusterのNVLink / InfiniBand帯域なら配置を適切に選べばcritical bottleneckにしなくて済むとする。

## 手法

### 1. Prefill / decodeを独立instanceへ分離する

prefill instanceはpromptを処理してKV cacheを生成し、decode instanceはそれを受け取ってcontinuous batchingへ追加する。

同じGPUで2 phaseをinterleaveしないため、prefill latencyの変動がdecode TPOTへ直接干渉しない。また各poolを独立にreplicateできる。

### 2. Phaseごとにparallelismを別々に探索する

model、workloadのinput / output length分布、TTFT / TPOT SLO、GPU memoryを入力し、feasibleなparallel configurationを列挙する。

profileから作ったsimulatorで各configurationのSLO attainmentとgoodputを推定し、prefill / decodeそれぞれについて**goodput / GPUが最も高い構成**を選ぶ。その後traffic rateを処理できる数だけinstanceをreplicateする。

### 3. Network帯域に応じてplacementを変える

cross-node networkが十分速いclusterではprefill / decode instanceを比較的自由に配置できる。

一方cross-node bandwidthが低いclusterでは、対応するpipeline stage同士を同じnodeに置き、KV transferを高速なintra-node NVLinkへ寄せる。つまりdisaggregationの利点を保ちながらnetwork topologyに合わせて配置制約を加える。

### 4. Request lengthを揃えてbatch imbalanceを抑える

prefill側ではprompt長のばらつきでbatch内の短いrequestが長いrequest待ちになりやすい。DistServeは近い処理量になるrequestをまとめてscheduleし、instance内のexecution bubbleを減らす。

### 5. KV transferはdecode側からpullする

arrival burst時にprefillからKVを一斉pushするとdecode GPU memoryが溢れやすい。そこでdecode instanceが処理可能になった時点でKVをpullし、prefill GPU memoryを一時的なqueue bufferとして使う。

workload分布が長期的に変わった場合はprofilerの統計を更新し、placementをperiodic replanningする。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Cluster | 4 nodes / 32 GPUs |
| GPU | NVIDIA A100 SXM 80GB、各node 8GPU |
| Intra-node | NVLink |
| Cross-node | 25Gbps |
| Models | OPT-13B / 66B / 175B等 |
| Precision | FP16 |
| Workloads | ShareGPT、HumanEval、LongBench |
| Baselines | vLLM、DeepSpeed-MII |
| SLO attainment | 主評価90% |

classic MHAのOPTを使い、KV transferに厳しい条件でdisaggregationを評価している。

### Goodput

様々なmodel / workload / SLOで、DistServeはbaselineに対して**最大7.4×高いrequest rate**、または同じrateで**最大12.6×厳しいSLO**を満たした。

DeepSpeed-MII比では1.6〜7.4×高いrequest rateを報告する。LongBenchを使ったOPT-66B summarizationでは、vLLM比4.3×高いrequest rateかつ12.6×厳しいSLOを達成した条件がある。

### KV transfer overhead

OPT-175BでもKV transferは総latencyの**0.1%未満**で、95%以上のrequestが30ms未満のtransfer delayだった。

これは実験clusterのcross-node bandwidthが25Gbpsしかないにもかかわらず、low-node-affinity placementで対応stageを同一nodeへ置きNVLinkを使った結果である。したがって「25GbpsでもP/D transferが常に軽い」という意味ではない。

### Placement optimization

prefill / decodeを同じparallelismに固定せず、workloadごとに異なる構成を選ぶことで両phaseのloadを釣り合わせる。placement simulatorの予測は実機結果とよく一致し、最大規模のsearchも数分以内としている。

## 既存研究との差

### vLLMとの違い

vLLMはcontinuous batchingでprefillとdecodeを同一worker上へ混在させる。throughputには有利だが、長いprefillがdecode TPOTへ干渉する。

DistServeは2 phaseを物理的に分離し、**TTFT resourceとTPOT resourceを別々にprovisioning**する。

### Sarathi / chunked prefillとの違い

chunked prefillは大きなprefillを小分けにしてdecode tokenと同じbatchへ載せ、干渉を抑える。DistServeはchunk化で共存させず、resource pool自体を分離する。

論文ではchunk数が増えると過去chunkのKVをattentionで繰り返し読むmemory accessも増える点を指摘する。

### Mooncakeとの違い

DistServeの中心は**P/D resource allocationとbandwidth-aware placement**であり、KVはphase間で1 requestのstateを移す対象である。

後続のMooncakeはP/D disaggregationに加え、異なるrequest間でも再利用するcluster-wide KV cache poolとcache-aware global schedulingを中心resourceにする。

## 限界

- 主評価modelはOPT系列で、GQA / MQA / MLAではKV transfer量とparallelismの最適点が変わる。
- placementは観測したworkload distributionが一定期間は安定することを前提とし、急変時はreplanning lagがある。
- P/D間でKV transferが必要なため、十分なNVLink / high-speed networkがないclusterではplacement制約が強くなる。
- prefill / decode poolを別々に確保するため、非常に低loadな時間帯にはresource fragmentationが生じ得る。
- chunked-prefill等との比較は当時のsystem設計を前提としており、後年のhybrid schedulerではtrade-offが変わり得る。

## 一般的な実装上の含意

LLM servingではGPU数をmodel全体に一括配分するより、**prefillとdecodeを別serviceとしてcapacity planningする**方がSLO付きcostを下げられる場合がある。

ただしstage分離だけでは不十分で、KV sizeとnetwork topologyを含めてphysical placementを決める必要がある。またtoken/s最大化とSLO付きgoodput最大化では最適configurationが異なるため、production servingでは後者を直接optimization objectiveにする価値がある。
