# DistServe：入力処理と逐次生成を分離して遅延目標下の有効処理率を高める

## 概要

大規模言語モデルの推論は、入力文を一度に処理して最初の出力を作る**事前入力処理（prefill）**と、以後のトークンを順に生成する**逐次復号（decoding）**で計算特性が異なる。前者は長い入力を行列演算として並列化でき、後者はモデル重みと鍵・値キャッシュを何度も読みながら短い計算を反復する。従来の同居型配信では、この二種類を同じ計算装置でまとめるため、長い入力処理が進行中の逐次復号を待たせる。しかも両段階が同じモデル分割構成を使わざるを得ず、入力の応答性と生成中の滑らかさを同時に保証するための装置数が増える。

DistServeは、二段階を**異なるGPU群へ分離**し、事前入力処理側と逐次復号側の装置配分、モデル並列化、要求の束ね方を独立に決める。最適化するのは総トークン処理率ではない。**初回トークン到達時間（time to first token; TTFT）**と**後続トークン平均間隔（time per output token; TPOT）**の両方が目標値を満たす要求を、GPU一台当たり毎秒何件受け付けられるかという**有効処理率（goodput）**である。二段階の分離によって発生する鍵・値キャッシュ転送は、GPU間接続の帯域を考慮した配置で抑える。

OSDI 2024の論文は、四ノード・計32台のA100 80GBを用い、OPT-13B、OPT-66B、OPT-175Bと三種のアプリケーションを評価した。90%以上の要求が両遅延目標を満たす条件で、従来方式より最大7.4倍の要求率、あるいは最大12.6倍厳しい遅延目標を達成する。ただし両最大値は異なる比較・負荷条件に由来し、すべての構成で同時に得られるものではない。

## 問題設定と既存方式の制約

### 二段階の処理資源は同じではない

入力512トークンを処理する13Bモデルの事前入力処理は、A100で計算器を高く利用できる。一方、逐次復号は一ステップに新規トークン一個を扱うため、モデル重みを高帯域メモリから読み出す費用が相対的に重くなる。逐次復号では多数要求をまとめることで重み読み出しを共有し、装置の利用率を上げやすいが、事前入力処理を同じ束へ加えると、その長い演算が後続トークンの返却を妨げる。

原著の図1では、13Bモデル、入力512・出力64トークン、A100一台という合成負荷で、同居型は90%達成率を守ると約1.6要求/秒に制約される。事前入力処理だけならGPU当たり約5.6要求/秒、逐次復号だけなら約10要求/秒を処理できる。仮に事前入力処理へ二台、逐次復号へ一台を割り当てると、全体10要求/秒、GPU当たり約3.3要求/秒となり、同居型の約2.1倍になる。この数値は動機付けの例であり、論文全体の最大7.4倍とは別の実験である。

### 並列化にも異なる好みがある

演算子内部の並列化（intra-operator parallelism）は、行列積などを複数GPUへ分割し、一回の演算時間を短縮する。短い初回応答時間が必要な事前入力処理では有利になりやすいが、GPU間通信が増える。演算子間の並列化（inter-operator parallelism）は層を複数段へ分ける方式で、個々の要求が通る段数は増える一方、同時に流せる要求数を増やしやすい。要求到着率が上がると、事前入力処理でも装置の処理時間だけでなく待ち行列が支配的になり、最適な分割方式が変わる。

従来方式では入力処理と逐次復号が同じモデル複製と並列化設定を共有するため、一方の遅延目標を満たす設定が他方には過剰であることがある。分割事前入力処理（chunked prefill）は長い入力を分けて復号と混在させるが、干渉を完全には除去しない。原著は、分割数を増やすほど以前の入力断片の鍵・値を再読込する費用が増え、細分化しすぎると行列演算効率も落ちることを問題としている。

### 有効処理率の定義

遅延目標（service-level objective; SLO）を、TTFTとTPOTの二条件として指定する。各要求について両方を満たした場合だけ達成と数え、所定の割合、主評価では90%、が達成される最大到着率を測る。この要求率を使用GPU台数で割ったものがGPU当たり有効処理率である。単に生成したトークン数を合計する指標とは違い、要求の待ち時間や長い入力の混入による尾部遅延が結果を左右する。

## 手法

### 処理段階の分離と要求の受渡し

利用者の要求は前段の事前入力処理インスタンスへ送られ、入力トークンの注意計算と最初の出力トークンを処理する。そこで各層の鍵・値キャッシュを生成し、要求識別子とともに逐次復号インスタンスへ引き継ぐ。後段は受け取った状態を既存の連続バッチへ組み込み、以後のトークンを順次生成する。二つのインスタンスは異なるGPUでモデル重みをそれぞれ保持するため、重み共有によるメモリ節約は失うが、長い事前入力処理が復号ステップを直接ブロックする状態をなくす。

事前入力処理インスタンスは、同じ入力長に近い要求をまとめ、長さが大きく異なる要求が同じ束で待ち合うのを抑える。入力長がある閾値を超えると単一要求だけでも計算器が飽和するため、その条件では無理にバッチを大きくしない。逐次復号側は一ステップの演算が小さいため、より多くの要求を集めてメモリ帯域の利用効率を高める。このように、同じモデルでも段階別にバッチ方針を変える。

### 段階ごとのGPU数とモデル分割の探索

入力はモデル規模、入力・出力長分布、要求到着率、TTFT/TPOTの目標、GPU容量と相互接続である。DistServeは候補となる演算子内・演算子間並列度とインスタンス数を列挙し、事前測定した処理時間を使う離散事象シミュレーション（discrete-event simulation）で待ち行列とSLO達成率を推定する。各段階でGPU当たり有効処理率が高い候補を選び、両段階の処理能力が釣り合うよう複製数を増やす。

重要なのは、最短の単発実行時間を持つ構成を無条件に採用しない点である。モデルを多数GPUへ細かく分ければ一要求の処理時間が短くなる場合があるが、装置台数当たりの処理率は通信や余剰資源によって下がり得る。逆に一台だけで処理する構成は装置効率が高くても、到着率が高いと待ち行列が伸びてSLOを外す。段階別の遅延制約を満たしたうえで、資源量当たりの達成要求数を最適化する。

### 帯域に応じた物理配置

分離後には、入力処理が作った鍵・値キャッシュを後段へ送らなければならない。高速なノード間ネットワークがある場合は両段階を自由に配置できるが、ノード間帯域が細い場合、キャッシュ転送が分離の利得を食い潰す。DistServeはネットワーク構成に応じて配置探索を切り替える。帯域が小さいクラスタでは、両段階で対応するモデル層を同一ノードに置き、転送をノード内の高速接続へ寄せる制約を課す。

これは「事前入力処理と逐次復号を別GPUへ分ける」ことと「別ノードへ遠距離転送する」ことを区別する設計である。各ノードに異なる段階のGPUを共存させても、同一GPU上で二段階を交互実行するわけではない。低帯域配置は探索自由度を減らすため、高帯域クラスタと同じ最適値を保証しないが、現実のネットワークで転送時間を抑える。

### 受信側主導のキャッシュ移動と実装

要求到着が急増すると、事前入力処理で完成した鍵・値をすぐ全件転送する方式では、逐次復号GPUのメモリを圧迫する。DistServeでは後段のインスタンスに空きが生じたときに受渡しを進め、後段の容量に見合った要求だけを受け付ける。これはキャッシュ移動の負荷を平準化するが、前段で完成した要求の待機が長くなるとTTFT後の処理開始が遅れるため、両段階の台数を釣り合わせる必要がある。

原著実装は、要求の受付と結果配送を行う前面部、配置・転送・実行単位を管理する調停層、GPUで計算する推論実行部からなる。GPUワーカー管理にRay、ノード間通信にNCCL、ノード内の非同期転送にCUDAのメモリコピーを利用し、連続バッチ処理、FlashAttention、PagedAttention等の既存技術を統合する。分離そのものはモデルの再学習を必要としないが、モデル重みの複製とキャッシュ転送、段階別の配置探索という運用費用を追加する。

## 評価

### 実機構成・負荷・比較対象

| 観点 | 原著の設定と読み方 |
|---|---|
| 実機クラスタ | 四ノード、計32台のNVIDIA A100 SXM 80GB。各ノード八台をNVLink接続、ノード間25Gbps。 |
| モデル | OPT-13B、OPT-66B、OPT-175B。全実験でFP16。OPTは通常の多頭注意を用い、鍵・値転送に比較的厳しい条件を作る。 |
| チャット | ShareGPT。三つのOPT規模を使用。OPT-13Bの目標はTTFT 0.25秒、TPOT 0.1秒で、大規模モデルでは緩和。 |
| コード補完 | HumanEvalの164課題から要求を構成。OPT-66Bを使用し、両遅延目標を厳しくする。 |
| 長文要約 | LongBench。OPT-66Bを使用。入力が長いためTTFTは緩く、TPOTは厳しい。OPTの位置埋込み制限により入力は最大2048トークンへ切り詰める。 |
| 到着過程 | 元データに時刻がないため、ポアソン到着を合成して要求率を変える。 |
| 比較 | 同居型のvLLM、入力分割を備えたDeepSpeed-MII。並列度は論文の設定に従う。 |
| 成功条件 | 一要求がTTFTとTPOTの双方を満たすこと。主評価は達成率90%以上。99%目標は付録で検討。 |

比較上の注意として、DeepSpeed-MIIはOPT-175Bを評価できていない。原著によれば、当時の実装では語彙数50272と演算子内並列度8の組合せがカーネルの割り切り条件を満たさず、並列度4ではGPUメモリ不足になる。したがってOPT-175BのグラフからDeepSpeed-MIIとの比較倍率を読み取ることはできない。

### 遅延制約下の主要結果

| 条件 | 比較対象 | 指標 | DistServeの結果 | 解釈 |
|---|---|---|---|---|
| ShareGPT、OPT-13B/66B/175B | vLLM | 達成率90%以上での要求率 | 2.0～4.6倍 | 同居による復号遅延の干渉を解消。 |
| ShareGPT、評価可能な規模 | DeepSpeed-MII | 同じ指標 | 1.6～7.4倍 | 分割事前入力処理でも残る干渉を削減。 |
| ShareGPT、固定要求率 | vLLM | 達成可能な遅延目標の厳しさ | 1.8～3.2倍 | 目標の倍率は要求率の倍率とは別の測定。 |
| HumanEval、OPT-66B | vLLM | 要求率 / 目標の厳しさ | 5.7倍 / 1.4倍 | 初回応答の制約が強い負荷で事前入力処理の並列化が効く。 |
| LongBench要約、OPT-66B | vLLM | 要求率 / 目標の厳しさ | 4.3倍 / 12.6倍 | 長い入力と復号の共存干渉が顕著。 |
| LongBench要約、OPT-66B | DeepSpeed-MII | 要求率 / 目標の厳しさ | 1.8倍 / 2.6倍 | 分割方式との比較でも分離に利点。 |

ここで「12.6倍厳しい目標」とは、両遅延制約を共通倍率で縮めたときに達成できる厳しさの比較である。**TTFTが12.6倍短くなったという直接測定ではない**。同様に「最大7.4倍」は、90%の達成率を保てるGPU当たり要求率の比較であって、個々のトークン生成が常に7.4倍速くなるという意味ではない。

### キャッシュ転送と通信帯域

原著図10では、最も転送量が大きいOPT-175BのShareGPT負荷でも、鍵・値キャッシュの転送時間が要求処理全体の遅延に占める割合は0.1%未満だった。さらに三つのOPTモデルについて95%超の要求は転送遅延30ミリ秒未満である。これは25Gbpsのノード間通信を自由に使っても転送が無視できるという結果ではない。対応するモデル段階を同一ノードに配置し、NVLinkを利用できるようにした**帯域制約付き配置の結果**である。

鍵・値キャッシュが小さいモデル、例えばグループ化問い合わせ注意（grouped-query attention; GQA）を使うモデルでは転送量が減る可能性がある。ただし原著の実機比較はOPT系列の通常の多頭注意であり、GQAモデルでの具体的な利得を測ったものではない。現在の異種GPUや低帯域機器に同じ0.1%を外挿してはいけない。

### シミュレータの一致と構成要素の切り分け

原著表2は、vLLMと低帯域配置版DistServeについて、要求率を変えた実機の達成率とシミュレータの予測を比較している。例えば2.0要求/秒では、vLLMの実機52.8%に対して予測51.0%、DistServeの実機99.3%に対して予測99.3%だった。各点の誤差は2パーセントポイント未満で、探索の根拠となるモデルの妥当性を裏付ける。ただしこの精度は測定したモデル・クラスタ・負荷に対するもので、未知のGPUやネットワークへ無調整で適用できる保証ではない。

図11の構成要素除去実験は、同居型vLLMでも並列化構成を探索する「vLLM++」と、分離型の低帯域配置・高帯域配置を比較する。OPT-66BのShareGPT負荷ではvLLM++が元のvLLMと同程度であり、並列化設定の探索だけでは事前入力処理と逐次復号の干渉を取り除けない。高帯域配置の分離型は低帯域配置より改善余地があるが、これは実機で高速ノード間通信を測った結果ではなく、**通信条件を変えたシミュレーション**である。分離自体の効果と、物理配置の自由度による効果を分けて読む必要がある。

### 配置探索の実行費用と規模

配置探索はGPU上の推論計算ではなく、候補並列度をCPU上で離散事象シミュレーションして選ぶ処理である。原著図12では96コアのAWS m5d.metalでGPU数を変えて探索時間を測定し、最大規模でも分単位に収まると報告する。低帯域配置はノード内の組合せ制約が増えるため、高帯域配置より探索が遅くなる場合がある。探索は再配置前に行う想定であり、各要求到着のたびに同じ計算を実行するわけではない。

### 負の結果と適用境界

二段階分離はモデル重みの複製が必要で、同居型に比べて最低限のモデル常駐容量が増える。GPU台数が少ない環境や、片方の段階しか忙しくない低負荷時間帯では、専用GPUを確保する費用が利得を上回り得る。また、入力長・出力長・到着率の分布が変化すると、事前に探索した最適なGPU比率と並列度がずれ、再配置まで待ち行列が伸びる可能性がある。

論文の中心評価はA100クラスタとOPT系列であり、近年のグループ化問い合わせ注意、混合専門家モデル、異種GPU、遠隔ストレージを伴う鍵・値再利用を包括的に評価していない。高帯域配置の一部比較はシミュレーションで、別クラスタでのエンドツーエンド実測と混同しない。性能改善は90%などの指定達成率の下で成立する条件付きの値であり、無制約の最大処理率や最悪要求の遅延保証ではない。

## 既存研究との差

**vLLM**は連続バッチ処理とページ単位の鍵・値キャッシュ管理で同居型配信の効率を高める。**DeepSpeed-MII**は長い入力処理を分割して復号と共存させ、長い一回の入力処理による停止を緩和する。DistServeは共存方式の調整ではなく、GPU群を物理的に分離して、段階別の並列度と資源量を独立に最適化する。これにより、同じ装置台数でも初回応答の目標と後続生成間隔の目標を別々に扱える。

後続のMooncakeなどは分離した二段階に加え、複数要求間の接頭部キャッシュ再利用や外部メモリ階層を重視する。DistServeの論文で測ったキャッシュ移動は、基本的に同一要求を前段から後段へ引き継ぐための転送である。別要求間のキャッシュ共有や階層ストレージを含む利得をDistServe単独の評価結果へ混ぜない。

## 限界と実装状況

原著は公開コードを提示しているが、論文当時の実装におけるGPU実行器、Ray、NCCL、CUDAの転送方式を前提にした実験である。現在の推論ランタイムに同じ配置最適化を統合する場合、KVキャッシュの所有権、段階間の障害回復、再送、接続切断時の待機要求、異種装置間のモデル並列化を改めて設計する必要がある。これらの運用機構について、原著は全条件での保証を提示していない。

なお、実験の到着時刻は実トレースではなくポアソン分布で生成されているため、急なバースト、利用者ごとの長期的な相関、要求の取り消しや優先度変更による待ち行列の挙動は十分に再現されていない。原著が示す配置探索の精度は、測定済みのモデル実行時間を入力した場合の再現性であり、需要予測の誤差まで吸収できるという意味ではない。装置故障や段階間転送の再試行に伴う回復時間も主評価指標ではない。

この研究の重要な含意は、GPU使用率や合計トークン処理率だけを最大化すると、初回応答と逐次生成の双方に遅延制約を持つ配信では資源効率を誤って評価する可能性があるという点である。利用者が実際に求める二つの遅延を満たす要求数を最適化目標とし、モデル分割、要求の束ね方、ネットワーク配置を一体として考える必要がある。
