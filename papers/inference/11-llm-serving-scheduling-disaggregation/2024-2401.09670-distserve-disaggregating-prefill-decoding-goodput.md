# DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving

> プリフィルとデコードを別GPU群へ分け、それぞれのGPU数・モデル分割方法・配置場所を、最初のトークンまでの時間とその後のトークン間隔の目標に合わせて別々に決めることで、両処理段階の干渉をなくす推論提供システム。

## 概要

DistServeは、プリフィルとデコードを同じGPU上でバッチ処理すると、**長いプリフィルがデコードを遅らせる干渉**と、性質の違う2処理段階が同じGPU数・モデル分割方法を共有する制約が発生することに着目する。

そこでプリフィル実行単位とデコード実行単位を別GPUへ完全に分離し、それぞれに最適なGPU数・テンソル / パイプライン並列化を選ぶ。さらにクラスタのネットワーク帯域を考慮し、プリフィルで生成したKVキャッシュをデコード側へ送るコストが大きくならないよう物理配置も決める。

評価の中心は単純なトークン/sではなく、**TTFT（最初のトークンが返るまで）とTPOT（その後1トークン生成する平均時間）の両方について、設定した目標を守りながら何要求/s処理できるか**である。論文では、この「SLOを守って処理できた要求割合」を有効スループットと呼ぶ。

4ノード32GPUの評価では、vLLM/DeepSpeed-MIIに対してSLOを守る要求割合を最大7.4倍、同じ要求割合で最大12.6倍厳しい遅延目標を満たした。

## 問題設定

プリフィルはプロンプト全体を並列処理するため計算性能を使いやすい。一方デコードは1トークンずつ生成し、重みやKVを読むメモリ帯域の影響を強く受ける。両者を同じGPUで交互に処理すると、長いプリフィルの間にデコードが止まり、トークン間隔が不安定になる。

また、同じモデルでもプリフィルとデコードで最適なモデル分割方法は一致しない。プリフィルでは1要求を多GPUへ分けて遅延を短くする価値が高い場合がある一方、デコードではバッチサイズやKV容量とのトレードオフが異なる。

P/Dを分けるとKVキャッシュ転送が必要になるが、DistServeは**GPU配置をネットワークトポロジーへ合わせることで、その転送を大きなボトルネックにしない**ことを狙う。

## 手法

### 1. プリフィル / デコードを独立したGPUプールへ分ける

プリフィル実行単位はプロンプトを処理してKVキャッシュを生成し、デコード実行単位はそれを受け取って連続バッチ処理へ追加する。

同じGPUで2処理段階を交互実行しないため、プリフィル遅延の変動がデコード TPOTへ直接干渉しない。またプリフィル GPU群とデコード GPU群を別々に増減できる。

### 2. 処理段階ごとに「何GPUでどうモデルを分けるか」を別々に選ぶ

モデル、ワークロードの入力 / 出力長さ分布、TTFT / TPOT目標、GPUメモリを入力し、使える並列化構成を列挙する。

実機性能測定から作ったシミュレータで各構成について、

- 何要求/s処理できるか
- TTFT / TPOT目標を何%の要求で守れるか
- 何GPU必要か

を見積もる。

その上でプリフィル／デコードそれぞれについて、**1 GPUあたりにSLOを守って処理できる要求数が最も多い構成**を選び、通信量割合を支えられるだけ実行単位数を用意する。

### 3. ネットワークが遅い場合はKVを遠くへ送らない配置にする

ノード間ネットワークが十分速いクラスタではプリフィル／デコード実行単位を比較的自由に配置できる。

一方ノード間帯域が低いクラスタでは、プリフィルとデコードで対応するモデル段階を同じノードへ置き、KV転送を高速なノード内NVLinkへ寄せる。

つまり「プリフィルとデコードを別GPUへ分ける」ことと、「KVを無条件に別ノードへ飛ばす」ことは別であり、**ネットワークが遅いなら物理的には近くへ置く**。

### 4. プリフィルでは似た長さの要求をまとめる

プリフィル側ではプロンプト長のばらつきが大きいと、短い要求が長い要求の処理完了を待つ無駄が生じる。

DistServeは近いプロンプト長の要求を同じバッチへまとめ、1バッチ内の処理量差を減らす。

### 5. デコード側に空きができてからKVを取りに行く

到着急増時にプリフィルからKVを一斉送信すると、デコード GPUメモリが溢れやすい。

そこでデコード実行単位が新しい要求を処理できる状態になった時点でKVを取りに行く。これによりプリフィル GPU側を一時的なKV待機場所として使い、デコード側のメモリ過剰割当を避ける。

ワークロード分布が長期的に変わった場合は性能測定統計を更新し、配置と実行単位数を再計算する。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| クラスタ | 4ノード / 32GPU |
| GPU | NVIDIA A100 SXM 80GB、各ノード8GPU |
| ノード内接続 | NVLink |
| ノード間接続 | 25Gbps |
| モデル | OPT-13B / 66B / 175B等 |
| 精度 | FP16 |
| ワークロード | ShareGPT、HumanEval、LongBench |
| 比較対象 | vLLM、DeepSpeed-MII |
| SLO達成率 | 主評価90% |

従来型MHAのOPTを使い、KV転送に厳しい条件で分離を評価している。

### SLOを守って処理できる要求割合

様々なモデル / ワークロード／ SLOで、DistServeは比較対象に対して**最大7.4×高い要求割合**、または同じ要求割合で**最大12.6×厳しい遅延目標**を満たした。

DeepSpeed-MII比では1.6〜7.4×高い要求割合を報告する。LongBenchを使ったOPT-66B要約では、vLLM比4.3×高い要求割合かつ12.6×厳しいSLOを達成した条件がある。

### KV転送の余分な処理

OPT-175BでもKV転送は総遅延の**0.1%未満**で、95%以上の要求が30ms未満の転送遅延だった。

ただしこれはノード間 25Gbpsを直接使っても常に軽かったという意味ではない。ネットワークが遅い構成では、**プリフィル/デコードの対応段階を同じノードへ置き、KVをNVLinkで送る配置を選んだ結果**である。

### 配置最適化

プリフィル／デコードを同じ並列化に固定せず、ワークロードごとに異なる構成を選ぶことで両処理段階の負荷を釣り合わせる。シミュレータの予測は実機結果とよく一致し、最大規模の探索も数分以内としている。

## 既存研究との差

### vLLMとの違い

vLLMは連続バッチ処理でプリフィルとデコードを同一ワーカー上へ混在させる。スループットには有利だが、長いプリフィルがデコード TPOTへ干渉する。

DistServeは2処理段階を物理的に分離し、**TTFTを改善するためのGPUと、デコードトークン間隔を守るためのGPUを別々に用意する**。

### Sarathi / 分割入力処理との違い

分割したプリフィルは大きなプリフィルを小分けにしてデコードトークンと同じバッチへ載せ、同じGPU上で干渉を抑える。DistServeは共存方法を工夫するのではなく、資源プール自体を分離する。

### Mooncakeとの違い

DistServeの中心は**プリフィル/デコードごとのGPU配分とネットワークを考慮した配置**であり、KVは同じ要求をプリフィルからデコードへ引き継ぐために移す。

後続のMooncakeは、KVをクラスタ全体へ保存し、別要求でも接頭部キャッシュとして再利用するところまで広げる。

## 限界

- 主評価モデルはOPT系列で、GQA / MQA / MLAではKV転送量と並列化の最適点が変わる。
- 配置は観測したワークロード分布が一定期間は安定することを前提とし、急変時は再計画の遅れがある。
- P/D間でKV転送が必要なため、十分なNVLink / 高速ネットワークがないクラスタでは配置制約が強くなる。
- プリフィル／デコードプールを別々に確保するため、非常に低負荷な時間帯には片方のGPUが余る可能性がある。
- 分割入力処理等との比較は当時のシステム設計を前提としており、後年の混合スケジューラではトレードオフが変わり得る。

## 一般的な実装上の含意

LLM推論提供ではGPU数をモデル全体に一括配分するより、**プリフィルとデコードを別サービスとして処理能力を計画する**方がSLO付きコストを下げられる場合がある。

ただし段階分離だけでは不十分で、KVサイズとネットワークトポロジーを含めて物理的配置を決める必要がある。またトークン/s最大化と「遅延目標を守って処理できる要求数」最大化では最適構成が異なるため、本番推論提供では後者を直接最適化目標にする価値がある。
