# AIBrix: Towards Scalable, Cost-Effective Large Language Model Inference Infrastructure

## 概要
AIBrixは、単一推論エンジン内部ではなく、クラスタ全体のLLM提供を担うクラウドネイティブ制御面を対象とする。vLLMやSGLang、TensorRT-LLMのようなエンジンがページ化KVキャッシュ、バッチング、注意計算などを最適化しても、Kubernetes側が要求のトークン長、KVキャッシュ局所性、LoRA配置、異種GPUの費用対性能を知らなければ、同じ接頭辞を別レプリカで再計算したり、QPSだけを見た自動スケールがGPU負荷を誤認したりする。

AIBrixは制御面（control plane）とデータ面（data plane）をLLM固有情報で結び、高密度LoRA管理、LLM認識ゲートウェイ、統一AI実行時（AI ランタイム）、LLM専用自動スケーラ、分散KVキャッシュ、Kubernetes+Rayの混合粒度オーケストレーション、SLO駆動の異種GPU最適化を一つの基盤へ統合する。論文の強みは各要素が「ある」という列挙だけでなく、ルーティング・スケーリング・KV共有・GPU選択について個別の性能結果を示す点にある。

## 問題設定
一般的なマイクロサービスでは要求数や同時接続数が負荷の代理になりやすいが、LLMでは入力長・出力長が要求ごとに大きく違い、プリフィルと復号でも計算特性が異なる。GPU使用率だけではKVキャッシュメモリ圧迫を捉えにくく、QPSだけでは長い要求と短い要求を同一視する。またモデルイメージが大きいため、新しいポッドの起動に2〜3分かかることもあり、従来の反応型水平ポッド自動スケーラ（Horizontal ポッド 自動スケーラ; HPA）では遅い。

さらに、同一接頭辞を含む会話やエージェント要求はプリフィルKVを再利用できるが、レプリカ間でキャッシュが共有されなければルータが別GPUへ送るたび再計算になる。GPU種類もA10、L20、V100などで価格とトークン長別性能が異なるため、「最速GPUへ全部載せる」配置も必ずしも最安ではない。

## 手法
### LLM認識ゲートウェイとルーティング
AIBrixはEnvoy ゲートウェイを拡張し、要求を単なるラウンドロビンで振り分けず、推論エンジンから収集した状態を使って宛先を選ぶ。実装済み方策にはrandom、トークン/sが低いレプリカを選ぶスループット、受理要求数が少ないleast-リクエスト、KV使用率が低いleast-kv-キャッシュ、キュー+提供遅延が小さいleast-遅延、再利用可能な接頭部 キャッシュが閾値以上のインスタンスを優先する接頭部-キャッシュ-awareがある。

この機構の入力は要求トークン、各レプリカの負荷・キャッシュ状態、出力は宛先レプリカである。適切な方策を選ぶ実験では平均遅延19.2%、P99遅延79%を削減する。つまり、同じ推論エンジンでも制御面が局所性と負荷を観測するだけでtail 遅延を抑えられる。

### 高密度LoRA管理と統一AI実行時
LoRAごとに基底モデルを別ポッドへ複製すると、長尾アダプタのために大きなモデル重みを重複保持する。AIBrixのLoRA controllerは一つのポッドへ複数LoRAを登録し、動的ロード／アンロード、LoRA認識ルーティング、Kubernetes Service/EndpointSliceを使った発見と配置を行う。出力は「どのポッドにどのアダプタを載せるか」と要求のルーティングであり、基底モデル重複を減らす。

推論エンジン固有APIを制御面へ直接埋め込まないため、各推論ポッドに軽量なAI ランタイム サイドカーを置く。サイドカーはモデル管理、負荷/unload、メトリクス、エンジン設定を共通化し、vLLM/SGLang/TensorRT-LLM間の差を吸収する。Cold Start ManagerはモデルartifactのDRAM、local storage、cloud storage所在を追跡し、最も速い経路からロードする。

### LLM専用自動スケーリング
AIBrixはKubernetesの汎用custom metrics経路を避け、自動スケーラ内でスライディング窓集計を持ち、LLM固有負荷をミリ秒単位で読む。KPA（Knative ポッド 自動スケーラ）とAIBrix ポッド 自動スケーラを利用した評価では、標準 HPA比で遅延11.5%削減、トークン スループット 11.4%増加、スケーリング振動33%削減を報告する。利得は新ポッド起動が遅いLLMで、単純な瞬時QPSではなく推論負荷の時間変化を追うことから生じる。

### 分散KVキャッシュ
単一エンジン内接頭部 キャッシュはGPU/ノード容量とエンジン境界に制約される。AIBrixはDRAMベースの分散KV poolを外部化し、複数エンジン間でKVを再利用する。高頻度KVだけを残す走査耐性（scan-resistant）追い出し、不要なデータ転送削減、非同期metadata更新、キャッシュ エンジンと推論エンジンの同居時の共有メモリ転送を組み合わせる。

入力は生成済みKVと接頭部 lookup、出力はローカル再計算を省けるKV tensorである。キャッシュが命中するほどプリフィル計算を省けるが、ネットワーク転送が再計算より高い短接頭部や低再利用負荷では利得が減る。分散poolは将来のプリフィル／復号分離（プリフィル/decode disaggregation）やリクエスト migrationの土台にもなる。

### 混合粒度マルチノード・異種GPU制御
大規模モデルのmulti-node推論では、Kubernetesはポッド/ノードのライフサイクルやrolling upgradeには強いが、細粒度分散実行には重い。Rayは逆に分散タスク実行へ強いが、クラスタ資源管理全体を担いにくい。AIBrixはKubernetesを粗粒度、Rayを細粒度に使い分けるRayClusterFleetで両者を組み合わせる。

異種GPUでは負荷 Monitorがゲートウェイ統計から代表的な入出力長分布を集め、事前profileしたGPU別性能を使う整数線形計画（integer linear programming; ILP）GPU 最適化器が、SLOを守りつつ費用を最小化するGPU組合せを選ぶ。ポッド 自動スケーラがその結果をMetricSourceとして読み、実配置を更新する。

## 評価条件
| 機構 | 条件・比較 |
|---|---|
| ルーティング | AIBrix ゲートウェイの複数方策、mean/P99 遅延 |
| 自動スケール | AIBrix/KPA系と標準 HPA、遅延・トークン スループット・oscillation |
| 分散KV | Bird-SQL、4×NVIDIA A10、vLLM 既定/chunked プリフィル/接頭部 cachingとの比較 |
| 異種GPU | A10+L20対L20-only、ShareGPT+内部Text2SQL混合負荷、SLO制約 |
| エンジン統合 | vLLM、SGLang、TensorRT-LLMをサイドカーで抽象化 |
| マルチノード | Kubernetes粗粒度+Ray細粒度オーケストレーション |

## 主要結果
分散KVキャッシュのBird-SQL評価では、vLLM 既定の総スループット 1,802.30 トークン/sに対しAIBrix distributed KV + 既定は4,133.45 トークン/s、約129%増加する。平均TTFTは3,067.07ms→825.77ms、P99 TTFTは10,060.29ms→2,132.97ms、平均ITLは189.04ms→89.78ms、P99 ITLは3,175.79ms→831.98msへ低下する。

より強いvLLM 接頭部 cachingを比較基準にしても、総スループット 3,703.26→5,615.71 トークン/s（+51.64%）、平均TTFT 999.95→349.39ms（65.06%削減）、P99 TTFT 5,744.27→1,306.05ms（77.26%削減）、平均ITL 99.50→69.95ms（29.70%削減）、P99 ITL 1,653.56→456.31ms（72.40%削減）である。したがってabstractの「スループット 50%増、遅延 70%減」は、すでに接頭部 キャッシュを持つvLLMとの比較でも概ね成立する。

chunked プリフィルとの比較でも総スループットは1,820.63→3,320.91 トークン/s（+82.40%）、平均/P99 TTFTは50.34%/50.44%削減する。キャッシュ効果が特定のvLLM設定だけに依存しないことを示す一方、効果量は比較基準機構によって大きく変わる。

ルータでは方策選択によりmean 遅延 19.2%、P99 79%削減、自動スケーリングでは標準 HPA比で遅延 11.5%削減、トークン スループット 11.4%増加、oscillation 33%削減を報告する。これらはKV実験と別の構成要素評価なので、50% スループットという一つの数値をAIBrix全体の総合speedupとして扱うべきではない。

異種GPU評価ではShareGPT+Text2SQL混合負荷をA10+L20へ割り当てると、L20-onlyより遅延が最大20%増えるが指定SLO内に留まり、費用を約10%削減する。これはGPU 最適化器が絶対最速ではなく、SLOという制約内で価格性能を選ぶ設計であることを示す。

## 既存研究との差
vLLM/SGLang/TensorRT-LLMは主に推論エンジン内部を最適化する。KServe/RayServeは一般MLモデルの配置・自動スケールを担うが、KV局所性、トークン-based負荷、LoRA、異種GPUをLLM固有状態として深く扱わない。AIBrixは両者の間に位置し、エンジン状態をクラウド制御面へ持ち上げて、ルータ、キャッシュ、自動スケーラ、アダプタ、GPU配置を協調させる点が中心である。

## 限界
論文自身が、ルーティング方策と異種GPU提供を非理想的・多様な実負荷で十分評価できておらず、一般化には追加検証が必要と明記する。異種GPU 最適化器とprofile依存autoscalingは事前のモデル/GPU性能profilingを必要とし、負荷やソフトウェア版が頻繁に変わる環境では更新費用がかかる。

分散KVキャッシュの大きな利得は接頭部重複が豊富なBird-SQL条件で測定されており、重複が少ない独立要求ではネットワーク転送とmetadata管理の固定費が相対的に大きくなる。各機構の数値は異なる実験条件から得たもので、全機能を同時有効化した一つの総合倍率ではない。運用上はKubernetes、Ray、サイドカー、分散キャッシュ、複数エンジンの整合性を保つ複雑さも追加される。
