# Hermes：確率的需要グラフでLLMアプリ全体の完了時間を短縮するサービング

## 概要

現代のLLMアプリは単一のテキスト生成要求で終わらない。文書を分割して並列要約し、生成したコードをDockerで試し、必要に応じて検索や画像モデルを呼ぶなど、複数のLLM・非LLM処理が依存関係を持つ。既存のサービングは個々のLLM要求の待ち時間を最適化することが多いが、ユーザーにとって重要なのは**アプリケーション全体が完了するまでの時間（ACT）**である。

Hermesは、機能単位ごとの入力長・出力長・並列度・次の機能への分岐確率・必要なバックエンドをProbabilistic Demand Graph（PDGraph）へ記録する。過去の実行記録と現在の進捗から残処理時間の確率分布を更新し、Gittins方策でアプリ間の実行順を決める。さらに、次に必要となるKVキャッシュ、LoRAアダプタ、Docker、画像モデル等を適切な時点で事前に読み込む。

LLaMA2-7BをA100で動かし、300アプリを30分に投入する低負荷側の条件では、vLLMに対して平均ACTを77.0%、P95 ACTを82.4%短縮する。別のLLaMA3-70B・H800×8の高負荷条件では、平均ACTの改善は58.5%、P95は62.2%となる。最大改善値をあらゆるモデル・負荷での保証と解釈してはいけない。

## 問題設定

先着順（FCFS）では長いアプリが短いアプリの前へ並ぶとhead-of-line blockingが起きる。原著の例では、小さな知識検証アプリを大きな文書統合アプリの後に処理すると平均ACTは52.8秒だが、順序を逆にすると40.3秒となる。要求単位の公平性を重視する方式も、アプリ全体の終了時刻を最小化するとは限らない。

さらにバックエンドは必要になったときだけ起動すると、モデル読み込み、LoRAアダプタ転送、KVキャッシュ復元、Docker起動などのコールドスタートがクリティカルパスに乗る。一方、全バックエンドを常時起動すればGPU/CPUメモリを浪費する。実行経路が分岐するため、次に使うバックエンドを確定的には予測できない。

Hermesが解くのは、実行前には分からない処理量を**確率分布として推定**し、実行中の観測で更新しながら、キュー順序と準備開始時刻を同時に制御する問題である。目的は単一トークンのTPOTではなく、複数要求・複数バックエンドを含むアプリ全体のACTと締切達成率である。

## 手法

### PDGraphの表現

PDGraphのノードは一つの機能単位を表す。各ノードには、backend-spec（LLMモデル、Dockerイメージ、画像モデル等）、backend-consumption（入力/出力トークン長、並列度、処理時間の履歴分布）、next-unit（次のノードへの分岐確率）を保存する。例えばコード生成では、LLMによるコード生成→Docker実行→エラー時に再生成という循環があり、ループ回数と処理量を確率的に扱う必要がある。

絶対実行時間を固定して記録するのではなく、LLMの入出力長を記録し、実行環境のtoken処理時間と組み合わせてサービス時間へ変換する。これによりA100とH800など異なるGPUへ移しても、同じアプリの構造と需要履歴を使い回しやすい。履歴は最大1000値をFIFOで保持し、ノード間の分岐頻度を推定する。

### オフライン分布とオンライン補正

まず過去の実行から各ノードの入力長、出力長、並列度を分布として学ぶ。PDGraph上をモンテカルロでランダムウォークし、分岐と各ノードの需要量をサンプリングして、アプリ全体の残処理時間の分布を得る。固定平均値だけでは、少数の非常に長い生成や条件分岐を表せないため、分布全体を保持する。

実行中は、完了した上流ノードの入力・出力長から下流の需要分布を条件付きで更新する。例えばコード生成の出力が長い場合、後続のコード検査の入力も長くなる。原著はPearson相関が0.5を超える組合せだけを使い、需要分布を10個のbucketへ分割する。現在観測したbucketと一致する履歴を選んで下流の分布を更新し、モンテカルロ予測へ戻す。これにより、同じアプリでも今回の入力の複雑さに合わせて残処理時間を変えられる。

### Gittins方策によるキュー順序

残処理時間が確定しているならshortest-remaining-processing-timeが平均ACTを下げるが、LLMアプリでは残時間は確率分布でしか分からない。HermesはGittins indexを使い、**今から一定時間実行したときに完了する可能性**を考慮して優先順位を付ける。平均残時間が短いアプリでも、短時間で完了する確率が極端に低ければ、別のアプリを先に処理する方が良い場合がある。

原著Figure 7では、ある二つのアプリの平均残時間だけを見る順序と、短時間で完了する確率を重視したGittins順序が逆転する例を示す。締切がある場合は別のHermes-DDL変種を用い、残時間と締切の余裕を考慮するLSTF型の優先付けでDeadline Satisfaction Ratio（DSR）を最大化する。

### バックエンドの先行warm

現在実行中のノードから次に遷移する候補と、その分岐確率p_sをPDGraphから得る。バックエンド準備に要する時間t_p、開始時刻t_s、現在ノードの完了時刻t_cに対し、準備が役立つ確率を`p_e = p_s * P(t_c > t_s+t_p)`と定義する。期待有効性Kを閾値とし、分岐確率が低すぎる候補は準備しない。準備する場合は期待有効性がKになるタイミングを選ぶ。

Kを小さくすると早めに準備し、次の処理開始を速くできる反面、実際には使わなかったバックエンドの起動やアイドル時間が増える。KVキャッシュやLoRAの事前GPU転送、DockerやDNNモデルの起動に同じ考え方を適用する。Kは単なる性能定数ではなく、遅延と資源浪費の交換条件を制御する運用パラメータである。

### 実装

HermesSchedulerがPDGraphから優先順位とprewarm指示を計算し、HermesLetが実際のLLM/非LLM処理を実行する。vLLM 0.4.3を低レベル推論エンジンに使い、ZeroMQ RPCで制御を交換する。著者はHermes本体を約4100行、アプリケーションベンチマークを約11300行のPythonで実装したと報告する。基盤推論カーネルを改造する方式ではなく、**アプリ全体の需要情報を使う上位スケジューラ**である。

## 評価

### 実験条件

| 項目 | 条件 |
|---|---|
| 単一GPU | A100 PCIe 40GB、AMD EPYC 7302×4、128GB DRAM、4TB SSD |
| 複数GPU | H800 80GB×8、Intel Xeon Platinum 8558×4、2TB DRAM、28TB SSD |
| LLM | LLaMA2-7B/13B、LLaMA3-70B×2（4-way tensor parallel） |
| アプリ負荷 | 10種類の代表的アプリ群、MoonCake traceの到着分布、入力はアプリ群から抽出 |
| 主要比較 | vLLM、Parrot、VTC、締切ではEDF |
| 需要モデル | 10 buckets、相関閾値0.5、prewarm K=0.5 |
| 指標 | 平均ACT、P95 ACT、DSR、KV/LoRA cache hit、Gittins policy runtime |
| 実装 | vLLM 0.4.3、ZeroMQ RPC、HermesScheduler/HermesLet |

ACTは一つのLLM要求のTTFTではなく、複数の要求・ツール呼び出しを経てアプリ全体が終わるまでの時間である。アプリの種類、到着分布、コールドスタートの頻度が違えば倍率は変わる。

### アプリ完了時間の主結果

| 条件 | 比較 | 平均ACT改善 | P95 ACT改善 |
|---|---|---:|---:|
| LLaMA2-7B / A100 / 300アプリ / 30分投入（1×負荷） | vLLM | **77.0%短縮** | **82.4%短縮** |
| 同条件 | Parrot | 76.7%短縮 | 69.0%短縮 |
| 同条件 | VTC | 66.7%短縮 | 74.1%短縮 |
| LLaMA3-70B / H800×8 / 3000アプリ / 10分投入（3×負荷） | vLLM | **58.5%短縮** | **62.2%短縮** |
| 同条件 | Parrot | 39.1%短縮 | 21.7%短縮 |
| 同条件 | VTC | 50.3%短縮 | 45.8%短縮 |

この結果は原著Figure 9/10の特定条件である。70%超というabstractのheadlineは、すべてのハードウェア・負荷での改善を意味しない。複数GPUの高負荷では改善率が下がる。各アプリの終了時間が短くなる理由は、短く終わる可能性の高いアプリを先行させ、後続バックエンドの起動待ちを隠すことにある。

### 需要予測・キャッシュ・締切の検証

| 検証 | 条件と結果 | 意味 |
|---|---|---|
| オンライン相関補正を削除 | LLaMA-7Bで平均ACT **15.3%増** | 過去平均だけでは今回の入力の難しさを反映しにくい |
| さらにGittinsも削除 | 同条件で平均ACT **47.5%増** | 分布を使う順序付けが効いている |
| Oracleとの比較 | Hermesと完全需要既知Oracleの差 **10%未満** | 試験したアプリ群では推定精度が比較的高い |
| KV cache prewarm | 500アプリ/15分、8/16/32GB cache。LRU比平均ACT **18%短縮** | キャッシュ事前転送で待ち時間を隠す |
| LoRA cache prewarm | 200種類のrank8 LoRA、1000アプリ/25分。EPWQ比cache hit **21.1%増** | アダプタの先行ロードが有効 |
| 締切達成 | 300アプリ/15分、期限倍率1.2/1.5/2.0。Hermes-DDLがEDFより高いDSR | 締切に対して需要分布を利用 |
| Gittins実行コスト | 到着率を変えた評価で **3ms未満** | 上位スケジューラの計算費用は小さい |

原著はHermes-DDLがEDFに対してDSRで「1× improvement」と表現するが、これは絶対値を示す説明として曖昧であり、DSRが2倍になったと断定しない。KV cache hitについても本文に「1.11×（0.33×）改善」とあり、EPWQ比の表現が比率か増分か不明確なので、曖昧な数値は再解釈せずACTの明示的な18%・6%短縮を優先して記録する。

### 事前warmの負の結果

Dockerや画像モデルの事前warmを早めるとアプリの待ち時間を減らせるが、分岐で実際には使われないモデルを起動する場合がある。原著Figure 14ではKを小さくするほど遅延削減が大きくなる一方、余分なCPU/GPU秒数が増える。prewarmを最大化するだけでは資源効率が悪くなり、GPUメモリが不足すれば別のアプリのキャッシュを追い出す可能性もある。

## 主要結果と既存研究との差

vLLMはLLM要求のcontinuous batchingとKV管理を行うが、アプリケーション全体の依存関係を用いて要求を並べ替えることは主目的ではない。Parrotはアプリの要求をまとめて扱うが、確率的な総需要を使わずFCFSに依存する。VTCはテナント間の公平性を重視し、短いアプリを優先して平均ACTを下げることとは目的が異なる。Hermesは**PDGraphで需要分布を推定し、アプリ単位で順序を決め、次のバックエンドを先行準備する**ことで、要求単位の最適化を超える。

## 限界・負の結果・適用条件

PDGraphは同種アプリが繰り返し実行されることを前提に履歴を収集する。初回実行や大きな分布ずれでは推定精度が低くなり、Gittins順序とprewarm判断が誤る可能性がある。アプリの分岐が複雑で履歴が薄い場合、相関閾値0.5と10bucketの設定は必ずしも適切ではない。論文の評価は特定の10種類のアプリ群とMoonCakeの到着分布に基づくため、任意の実サービスで同じ77%短縮が成立するとは限らない。

prewarmはGPU/CPUメモリと起動時間を消費するため、レイテンシだけを最大化すると余剰資源消費が増える。Gittins方策は平均ACTに焦点を当て、テナント間の公平性を明示的に保証するものではない。異なる顧客の優先度や締切に応じた公平性は別途設計が必要である。評価で用いたvLLMは0.4.3であり、新しいランタイムや分離型prefill/decodeサービングに対して同じ優位性が維持されるかは未確認。Hermes専用の公式コードURLは原著から確認できない。
