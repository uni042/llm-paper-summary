# Hermes：確率的需要を予測して複合LLMアプリの完了時間を短縮するサービング

## 概要

Hermesは、一回のLLM生成要求ではなく、複数の生成、検索、コード実行、画像処理が連鎖する**アプリケーション全体**の終了時間を最適化する。既存のvLLMの要求単位の先着順や、アプリ単位でも処理量を推定しない先着順では、短いアプリが長いアプリの後ろに並ぶ。加えて、次に必要なKVキャッシュ、LoRAアダプタ、Dockerコンテナを要求発生後に起動すると、その準備時間が全体のクリティカルパスに入る。

著者は機能単位の需要と分岐を確率的需要グラフ（Probabilistic Demand Graph、PDGraph）として保存し、オンラインで実際の入出力長を観測して需要分布を更新する。推定した分布からGittins指標でアプリの優先度を決め、次のバックエンドの事前準備を行う。LLaMA2-7B・A100・300アプリを30分に投入する条件では、vLLMに対する平均アプリ完了時間（ACT）の短縮率は77.0%、95パーセンタイルACTは82.4%だった。ただしLLaMA3-70B・H800×8・高負荷条件では平均ACTの短縮率は58.5%であり、全条件で77%改善するという意味ではない。

## 問題設定と処理対象

対象は文書統合、並列要約、知識検証、コード生成と実行、計画実行など10種類の複合アプリである。各アプリは、生成したコードをDockerで検査し失敗なら生成を繰り返す、検索結果を集めて検証する、というように複数の機能単位を持つ。実行時の入力によって生成トークン数や繰り返し回数が変わり、事前には必要なGPU時間を確定できない。原著の小さな知識検証と大きな文書統合の例では、処理順を入れ替えるだけで平均ACTが52.8秒から40.3秒へ変わった。したがって要求単位の処理速度が同じでも、アプリの待ち行列設計が完了時間を大きく左右する。

もう一つの律速は、使われるか不明なバックエンドの準備である。全てのDockerやモデル、LoRA、KVキャッシュを常駐させればメモリとアイドル計算資源が浪費される。要求到着後の準備では遅すぎる。Hermesは、どの機能が次に呼ばれるかの確率と、その到着時刻の分布を使い、必要になる前に準備を始めるかを判断する。

## 手法

### 1. 機能単位を確率的需要グラフへ記録する

PDGraphの各ノードは一つの機能単位であり、`backend-spec`（利用するモデル、コンテナ、画像処理等）、`backend-consumption`（入力・出力トークン長、並列度、処理時間）、`next-unit`（次ノードへの遷移確率）の三種類を持つ。辺には実行履歴から求めた分岐頻度を記録する。入力トークン長と出力トークン長は絶対処理時間と分けて保持し、GPU環境ごとのトークン処理速度で実行時間へ変換するため、A100とH800で需要表現を共用できる。

同じ機能でも入力ごとに処理量が異なるので、ノードの需要は単一の平均値ではなく実測値の分布で保存する。履歴は最大1,000件を先入れ先出しで保持する。PDGraph上で遷移先と各ノードの需要をサンプリングするモンテカルロ走査を繰り返し、残りのアプリ実行時間の分布を得る。平均時間のみを使う方式と異なり、少数の長い生成やループ分岐が完了時間へ与える影響を残せる。

### 2. 実行中の観測から残処理量を条件付きで更新する

オフラインで得た分布は初期予測に過ぎない。例えばコード生成が通常より長いコードを出力した場合、続くコード検査の入力も長くなる可能性が高い。Hermesは上流と下流の入力長・出力長・並列度について相関を計算し、Pearson相関係数が0.5を超える組合せを予測に使う。需要値を10個の区間へ分け、上流の観測が入った区間に対応する履歴だけを抽出して下流の条件付き分布を作り直す。

この更新は、あるアプリが実際に長い入力を受け取ったときに、過去の平均処理量のまま短い仕事と誤認することを防ぐ。下流分布の更新結果を再びモンテカルロ走査へ入れるため、分岐確率と処理量の両方を実行中に反映できる。ただし相関の薄い組合せは利用しないため、学習履歴に存在しない分岐や分布外入力への予測精度は保証されない。

### 3. Gittins指標でアプリ単位の実行優先度を決める

処理時間が既知なら残り時間が短い仕事を優先すると平均ACTを下げやすいが、Hermesでは処理時間は分布である。Gittins方策は、あるアプリを今から一定時間処理したときに完了する確率を残処理時間分布から評価し、実行優先度を更新する。平均残時間が同程度でも、短時間で完了する確率が高いアプリと、長い尾を持つアプリでは順位が変わり得る。要求単位でなく、その要求が属するアプリ全体の優先度を使う点が重要である。

期限がある場合は別変種Hermes-DDLを用いる。アプリの締切と現在時刻に対し、推定残処理時間の上限を差し引いた余裕時間を計算し、余裕の小さいアプリを先にする最小余裕時間優先（LSTF）を採用する。通常版の平均ACT最小化と、期限付き版の締切達成率最大化は異なる目的関数なので、通常版の改善率を締切性能に読み替えない。

### 4. 分岐確率と完了時刻に応じてバックエンドを事前準備する

実行中ノードから次の機能へ遷移する確率を `p_s`、現在ノードの完了時刻を `t_c`、準備開始時刻を `t_s`、準備所要時間を `t_p` とする。準備が役立つ確率を原著式(3)の `p_e = p_s × P(t_c > t_s + t_p)` で表し、期待有効性の閾値 `K` と比較する。`p_s < K` なら準備せず、それ以外は `p_e = K` を満たす開始時刻を選ぶ。これにより、実際には呼ばれない可能性が高いモデルを無条件で先行起動することを避ける。

`K` を小さくすると早めに準備するため遅延は減るが、使われないバックエンドの起動や待機によるCPU/GPU秒数が増える。対象はGPU上のKVキャッシュ・LoRAアダプタだけではなく、Dockerコンテナや画像モデルにも及ぶ。実行時にはHermesSchedulerがPDGraphから優先度と準備指示を作り、HermesLetが各処理を実行する。両者はZeroMQの遠隔手続き呼び出しで通信し、下位のLLM推論エンジンにはvLLM 0.4.3を利用する。原著の実装規模は本体約4,100行、ベンチマーク約11,300行のPythonである。

## 評価

### 実験条件と比較の単位

| 観点 | 原著の設定 |
|---|---|
| 単機 | A100 PCIe 40GB×1、AMD EPYC 7302×4、128GB DRAM、4TB SSD |
| 複数GPU | H800 80GB×8、Intel Xeon Platinum 8558×4、2TB DRAM、28TB SSD |
| モデル | LLaMA2-7B/13B、LLaMA3-70B×2（各4-way tensor parallelism） |
| 複合アプリ | 文書統合、並列要約、推論、知識検証、コード検査、コード生成、計画実行など10種類 |
| アプリ到着 | 小規模72%、中規模26%、大規模2%を混合。投入窓10/15/30分 |
| 比較 | vLLM、Parrot、VTC。期限付き評価ではEDF |
| 需要推定 | 相関係数閾値0.5、分布10区間、事前準備閾値K=0.5 |
| 指標 | 平均ACT、P95 ACT、締切達成率DSR、キャッシュヒット率、優先度計算時間 |

評価対象は**複数要求とツール処理を含むアプリの完了時間**であり、単独生成要求のTTFTやトークン毎秒とは異なる。A100単機とH800×8の結果は、モデルと同時実行数が異なるため単純なGPU性能比較でもない。

### 完了時間の主結果

| 条件 | 比較方式 | 平均ACTの短縮 | P95 ACTの短縮 |
|---|---|---:|---:|
| LLaMA2-7B / A100 / 300アプリ / 30分投入（1×） | vLLM | **77.0%** | **82.4%** |
| 同条件 | Parrot | 76.7% | 69.0% |
| 同条件 | VTC | 66.7% | 74.1% |
| LLaMA3-70B×2 / H800×8 / 3000アプリ / 10分投入（3×） | vLLM | **58.5%** | **62.2%** |
| 同条件 | Parrot | 39.1% | 21.7% |
| 同条件 | VTC | 50.3% | 45.8% |

原著図9・図10に対応する比較である。最も大きな短縮率はA100・7B・低負荷の条件で、より高い負荷と大規模モデルの条件では改善幅が小さくなる。これらの値は**ACTの相対的短縮率**であり、GPUカーネルの実行速度が同じ倍率で速くなったことを意味しない。締切付きでは300アプリを15分に投入し、元の実行時間に1.2倍、1.5倍、2倍の締切倍率を割り当てる。Hermes-DDLはEDFより高い締切達成率を示すが、原著の「1× improvement」という表現は改善率の定義が曖昧なため、数値を独断で2倍と解釈しない。

### 構成要素除去と推定精度

LLaMA-7B、300アプリを10分投入する条件では、上流と下流の相関を用いたオンライン補正を取り除くと平均ACTが15.3%増加する。さらにGittins方策も外すと増加は47.5%となる。需要を完全に知っている理想的なOracleとの差は10%未満であり、対象の10アプリ群では予測が実用的な精度に達したことを示す。ただしOracleは温度0で事前実行して真の需要を得る理想条件であり、現実の追加処理なしで同じ結果を得られるという意味ではない。

### KVキャッシュ・LoRA・非LLMバックエンド

A100上で500アプリを15分に投入し、KVキャッシュ容量を8、16、32GBと変えた試験では、HermesはLRUより平均ACTを18%、EPWQより6%短縮した。EPWQは要求が待ち行列に入ってからKVを先読みするが、Hermesはまだ到着していない下流要求の準備を始められる。原著はヒット率の改善を「1.11×（0.33×）」と表現するが、比較基準と倍率の意味が曖昧なので、明示されたACT短縮率を優先する。

LoRAではrank 8のアダプタ200種類を用意し、1,000アプリを25分に投入した。`max-loras=10`、`max-cpu-loras=20`の条件で、Hermesのキャッシュヒット率は次点のEPWQより21.1%高い。非LLM処理ではコード生成のDocker起動と計画実行の画像モデル準備を評価し、閾値Kを下げるほど待ち時間を隠せるが、使われないモデルやコンテナの事前起動による資源浪費が増える。Gittins指標の更新計算は試験した到着率の範囲で3ミリ秒未満だった。分布の区間数を増やすと計算時間はほぼ比例して増える一方、スケジューリング性能の改善は小さい。

## 既存研究との差

vLLMは連続バッチングとKV管理を中心に、到着した**LLM要求**を処理する。Parrotは同じアプリの要求をまとめるが、需要分布を利用した順序付けではない。VTCはテナント間の公平な資源配分を重視し、平均ACTの最小化とは目的が異なる。HermesはPDGraphを使って**複合アプリの残処理時間分布**を求め、Gittins方策で順序を決め、さらに次段のバックエンドを予測して先行準備する。いずれか一つだけの最適化ではなく、依存グラフの予測情報を待ち行列と事前準備へ共通利用する点が主要な差分である。

## 限界・負の結果・実装上の注意

需要予測にはアプリの繰り返し実行による履歴が必要で、初回アプリや分布外入力ではPDGraphの分布が不正確になる。10区間の離散化と相関閾値0.5は評価時の設定であり、異なるアプリ群に最適とは限らない。分岐先を外して事前準備すると、GPUメモリ、CPUメモリ、コンテナの起動時間が無駄になる。Kを小さくするほど資源浪費が増えることは原著の感度実験にも現れている。

平均ACTを優先すると、特定テナントの公平性や個別要求の尾部遅延を別途保証する必要がある。Hermes-DDLは期限を考慮するが、通常版の最適化目的とは異なる。評価で使われたvLLMは0.4.3であり、新しい分離型prefill/decode、複数モデル混在、長大なKVキャッシュ運用で同じ改善率が維持されるかは実測されていない。性能は特定のアプリ構成、入力分布、コールドスタート頻度、GPU構成に依存する。Hermes本体の公開コードURLは確認できず、論文記述だけで完全再現できるとは断定しない。
