# P/D-Serve: Serving Disaggregated Large Language Model at Scale

## 一文要約

大規模prefill / decode分離clusterで、**workloadごとにP/D groupと比率を細かく組み替え、idle prefillへのrequest再転送とblock-freeなKV device-to-device転送を組み合わせる**ことで、固定P/D構成のmismatchと大規模network転送待ちを減らすproduction serving system。

## 書誌情報

- **arXiv:** 2408.08147
- **初回公開:** 2024-08
- **実装:** Ascend + MindSpore
- **Last checked:** 2026-09-07

## 問題設定

prefillとdecodeを分離しても、prompt長・生成token数・共有prefix量がscenarioごとに違うため、固定P/D ratioでは片側がidleになりもう片側がbottleneckになる。さらに数万device規模ではscheduler情報の遅れ、KVのD2D転送、network path競合、fault recoveryが問題になる。

## 手法

- scenarioごとにP/D instanceを細粒度group化し、実測performance modelに基づいて比率を調整する。
- prefill側が混雑してrequestを拒否した場合、gatewayが別のidle prefillへon-demand forwardingし、古いqueue情報だけに依存しない。
- KV cacheを連続bufferとしてD2D転送し、受信側で必要な離散blockへscatterすることで多数の細かいtransferを減らす。
- RoCE network構成とfault recoveryも大規模cluster運用へ統合する。

## 評価条件

- **Hardware:** Ascend NPU。mirror環境は数百NPU、productionは数万NPU規模。
- **Models:** Pangu系を中心に実service由来workloadで評価。
- **Storage:** compiled model保存にSFSまたはSSD。

## 主要結果

- 8か月超、**数万NPU規模でcommercial deployment**。
- E2E throughput **60%改善**、TTFT SLO **42%改善**、D2D transfer time **46%改善**。
- aggregated LLM serving比でsystem全体のthroughput **6.7×** と報告。

## 既存研究との差

Splitwise / DistServe等がP/D分離の基本構成とresource分離を示すのに対し、P/D-Serveは数万deviceのproduction clusterで、scenario別grouping、dynamic ratio、request forwarding、KV transfer、fault handlingを一体化する点が中心。

## 一般的な実装上の含意

P/D disaggregationを大規模化すると、最適なP/D比はmodel固定値ではなくworkload mixとprefix reuseで変わる。schedulerのperiodic load reportだけでなく、拒否を利用した即時rerouteやnetwork path管理までcontrol planeへ含める必要がある。

## 限界

- 評価はAscend / MindSpore production環境に強く依存し、GPU stackへそのまま移植できるとは限らない。
- privacy上、production request内容そのものではなくfine-tune dataset由来requestを用いる部分がある。
- 結果の一部は正規化値で提示され、absolute latency / throughputの再現比較には制約がある。
