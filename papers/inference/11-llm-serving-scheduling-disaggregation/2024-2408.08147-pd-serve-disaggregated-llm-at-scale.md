# P/D-Serve: Serving Disaggregated Large Language Model at Scale

> P/D-Serveは、事前充填（prefill）と復号（decode）を別インスタンスに分ける設計を、**数万NPUの商用クラスタで運用したときに生じる制御面・ネットワーク面の問題まで含めて解く**システムである。中心は3点ある。第一に、すべての要求を巨大な共通プールへ混ぜず、似たprompt特性を持つシナリオごとに小さなP/Dグループへまとめ、事前充填側と復号側の処理能力が釣り合うよう比率を変える。第二に、事前充填ノードへ要求を予約して待たせず、忙しければ即座に拒否させてgatewayが別の空きノードへ再送する。第三に、KVキャッシュ（KV cache）を小さなページ単位で何度もRDMA転送せず、連続バッファとしてまとめて送って受信側で再びページへ戻す。論文はAscend + MindSpore上の数万NPU規模で8か月以上商用運用したと報告する。

## まず、なぜ事前充填と復号を分離するのか

LLM推論は大きく2段階に分かれる。

1. **事前充填（prefill）**: 入力prompt全体をまとめて処理し、各tokenのKVキャッシュを生成する。
2. **復号（decode）**: 生成済みKVキャッシュを使いながら、出力tokenを1個ずつ追加する。

両者はGPU/NPUの使い方がかなり違う。事前充填は大きな行列演算をまとめて行いやすく、計算量が大きい。一方、復号は1 iterationごとの処理量が小さく、KVキャッシュ読出しなどメモリ帯域の影響を強く受ける。

そのためSplitwiseやDistServeなどの分離型推論では、

`事前充填ノード → KVキャッシュ転送 → 復号ノード`

という構成を採用し、各段階に適したbatch sizeやGPU数を選ぶ。

ただし、P/D-Serveが扱うのは「分離すれば速い」という段階の次である。

**数万台規模で、異なる業務シナリオ・prompt・trafficを同時に扱うと、固定された事前充填/復号比率と単純なglobal schedulerでは崩れる**という問題を対象にしている。

## 問題1: 最適なP/D比はモデルだけでは決まらない

### prompt長と生成長の違いで詰まる場所が変わる

あるシナリオでは入力promptが非常に長く、出力は短いかもしれない。この場合は事前充填負荷が重い。

別のシナリオではpromptは短い一方、数千tokenを生成するかもしれない。この場合は復号側が長時間占有される。

したがって同じモデルでも、

- prompt長
- 出力token数
- batch size
- prefixキャッシュの命中率
- traffic量

によって必要な事前充填ノード数と復号ノード数は変わる。

固定比率で、たとえば事前充填1台:復号4台と決めると、実際には事前充填側が先に飽和して復号側が遊ぶ場合も、その逆も起きる。

P/D-Serveはこれを**P/D能力の不整合（P/D mismatch）**として扱う。

### 片側だけ増やしても全体能力は増えない

分離型pipelineの処理能力は、遅い段階で決まる。

事前充填が毎秒100 request処理できても、復号が毎秒60 request相当しか処理できなければ、system全体は60付近で頭打ちになる。

したがって事前充填だけさらに増設して毎秒200 requestにしても意味が薄い。

論文はこの釣り合いを概ね、

`n_p × b_p / T_p ≈ n_d × b_d / T_d`

で表す。

- `n_p`: 事前充填インスタンス数
- `b_p`: 事前充填batch size
- `T_p`: 事前充填にかかる時間
- `n_d`: 復号インスタンス数
- `b_d`: 復号batch size
- `T_d`: 復号側の処理時間

左右の処理能力を近づけることが目的である。

## 問題2: prefixキャッシュがあると「待ち行列の長さ」が負荷を表さない

### 同じtoken数でも処理時間が大きく違う

通常のschedulerは、各事前充填ノードから、

- 待っているtoken数
- 空きHBM
- request数

などを100 ms間隔のような周期で報告させ、次のrequestをどこへ送るか決めることがある。

しかしprefix-aware KVキャッシュがあると、これはかなり不正確になる。

たとえば8k-token promptでも、7k token分のprefix KVがすでにHBMにあれば、実際に計算する新規部分は1kしかない。逆に2k-token promptでもprefixがほとんど再利用できなければ2k近く処理する。

したがって単純な「待ちtoken数」では実際の最初のtokenまでの時間（Time To First Token: TTFT）を予測できない。

さらにstatus report自体が100 msごとなら、report直後に負荷が急変してもglobal schedulerは次の更新まで古い状態を見る。

### server-sent eventsの接続数も使いにくい

streaming応答ではサーバー送信イベント（Server-Sent Events: SSE）のconnectionがrequest処理中ずっと維持される。

しかしそのconnectionは事前充填が終わって復号へ移った後も残るため、「接続数が多い = 事前充填が忙しい」とは限らない。

つまりschedulerが外側から正確に事前充填負荷を推定しようとすると、prefix命中・batch状態・実際のphaseなど多くを追う必要がある。

P/D-Serveはここで発想を変える。

**負荷を完璧に予測してから送るのではなく、送った先が忙しければ拒否させ、空いている事前充填へ再送する。**

## 問題3: PagedAttentionのブロック配置はRDMA転送には都合が悪い

PagedAttention（ページ化アテンション）はKVキャッシュを固定サイズの小さなblockへ分け、GPU/NPU HBM上で仮想memoryのpageのように管理する。

これによりrequestごとに巨大な連続領域を予約せず、空いているblockを必要に応じて割り当てられる。

復号時のmemory効率には非常に有効だが、事前充填ノードから復号ノードへKVをRDMA転送するときには別の問題が出る。

送信側と受信側の両方がKVを離散blockとして持っている場合、素直な実装では、

`block 1を送る → 確認 → block 2を送る → 確認 → ...`

のように細かいtransferを多数発行する。

RDMAはある程度まとまった連続dataを送る方が効率が良い。小blockを何度も転送すると、data本体ではなく、

- 転送開始
- metadata交換
- completion確認
- blockごとのsoftware制御

に帯域と時間を使う。

そこでP/D-Serveは、**memory管理単位とnetwork転送単位を分離する**。

HBM内ではPagedAttention向けにblockとして扱い続ける一方、network上では可能な限り大きな連続byte列として送る。

## P/D-Serve全体構成

P/D-Serveは大きく、

1. 機械学習運用基盤（MLOps）
2. LLM serving層
3. 数万NPUとnetwork infrastructure

から構成される。

機械学習運用基盤（MLOps）はdeployment、scale、role変更、traffic control、fault recoveryを管理する。

LLM serving層は実際の事前充填/復号instance、KV転送、request処理を担当する。

infrastructureは複数region・rack・NPU・RoCE switchから成る。

論文の新規性は、新しいkernelを1個提案することよりも、**P/D分離を大規模productionへ持ち込んだときに必要になるこれらのcontrol planeとdata planeを一体として設計したこと**にある。

## 手法1: シナリオごとの細粒度P/Dグループ

### 巨大poolへ全requestを混ぜない

1つのserviceの中でも、用途によってpromptの形は違う。

例として、

- FAQは短prompt・短output
- 文書要約は長prompt・中output
- 長文生成は中prompt・長output

のような違いがある。

P/D-Serveは全要求を1つの巨大な事前充填poolと復号poolへ流すのではなく、**シナリオごとに事前充填instanceと復号instanceをまとめたP/D groupを作る**。

これには2つの利点がある。

第一に、同系統promptが同じ少数の事前充填instanceへ集まりやすくなる。HBM容量は有限なので、すべてのscenarioのprefix KVを全instanceへ複製するのは難しい。scenarioを絞れば、有用なprefix KVをHBMへ残しやすく、prefix hit率が上がる。

第二に、同じgroup内ではprompt長・生成長の分布が似るため、必要なP/D比を決めやすくなる。

### RoCE接続情報そのものをgroup構成として管理する

各NPUにはRDMA over Converged Ethernet（RoCE）のIPがあり、事前充填instanceと復号instanceの間でKVキャッシュを直接送る。

P/D-Serveは、どのNPUがどのscenarioのP/D groupに属するかというlogical mappingと、RoCE connection mappingを対応付ける。

新しいcontainerをgroupへ追加するときは、まずRoCE connectionを既存instanceとの間に作り、その後modelをloadし、health reportを確認してからroleを有効化する。

この順序にすることで、serviceを止めずにP/D構成を組み替えられる。

## 手法2: P/D比を動的に変更する

P/D-ServeはP/D比を永久固定しない。

変更のtriggerには、

- 事前profiling
- developerによる設定変更
- 平均E2E latency
- TTFTがE2E latencyに占める比率

などを使う。

直感的には、

- E2E latencyが増え、TTFT比率も増える → 事前充填側が詰まっている可能性が高い
- E2E latencyが増え、TTFT比率は下がる → 復号時間の割合が増え、復号側が詰まっている可能性が高い

と判断する。

必要ならstateless containerを追加し、RoCE接続を構築した後、事前充填または復号roleを割り当てる。全instance数を固定したまま比率だけ変える場合は、一部instanceを段階的にreleaseして反対roleへ組み替える。

このためprompt engineeringでpromptが長くなった場合や、traffic mixが変わった場合にもP/D比を追従できる。

## 手法3: 事前充填のローカル待ち行列をなくす

### なぜ「空くまでそのnodeで待つ」をやめるのか

従来はgatewayがある事前充填instanceへrequestを割り当てると、そのinstanceがbusyでもlocal queueに積み、順番が来るまで待つ。

問題は、一度local queueへ入ると、別instanceが先にidleになっても移動できないことである。

特に8k promptの後ろへ1k相当の軽いrequestが並ぶと、他の事前充填instanceが空いていても長時間待つhead-of-line blockingが起こる。

P/D-Serveはこれを避けるため、**事前充填側のlocal queueそのものを基本的に除去する**。

### accept / rejectで即時状態を返す

gatewayはまずSSE connection数などを参考に、idleでありそうな事前充填instanceへrequestを送る。

そのinstanceが実際に空いていればacceptする。busyならqueueへ積まずrejectする。

rejectされたrequestはgatewayへ戻り、候補の別事前充填instanceへ再送される。

このretryをTTFT deadline内で続ける。

結果としてrequestは、

- 特定instanceのlocal queueで待つのではなく
- gateway側で「今受け入れ可能なinstance」を探しながら待つ

ことになる。

global schedulerがprefix hit率やbatch状態から完璧なlatency予測をする必要はない。**実際のinstance自身のaccept/rejectが最も新しい負荷signalになる**。

### batchを満たすための連続forwarding

idleな事前充填instanceを見つけたら、gatewayはそのinstanceがbusyになるまで複数requestを連続forwardし、batchを作ることもできる。

つまりreject方式は単なるfailoverではなく、入力rateを事前充填groupの実処理能力へ合わせるbackpressureとして機能する。

## 手法4: Block-free D2D KVキャッシュ転送

### 送信側では連続bufferにする

事前充填中に各layerが生成するK/Vを、network送信用には連続bufferへ並べる。

layer index、prompt length、hidden size、precisionが分かれば、特定layerのoffsetとlengthを計算できる。

これにより、

- 全layerまとめて一括転送
- layer単位で計算とoverlapしながら転送

の両方を同じbuffer表現で扱える。

後者はmodel側へ転送operatorを挿入する必要があるが、KVを作ったlayerから順に送れるためlatencyを隠しやすい。

### 受信側でRecvScatterしてPagedAttention blockへ戻す

復号側ではKVキャッシュをPagedAttention blockとして管理したい。

そのためnetworkから届いた連続byte列を、そのrequestへ割り当てた離散blockへ散布する処理を**受信散布（RecvScatter）**として実装する。

つまりdata flowは、

`prefill側の連続送信用buffer → RDMA/RoCE → decode側RecvScatter → PagedAttention blocks`

となる。

重要なのは、**network transferの効率のためのlayoutと、GPU/NPU HBMを効率利用するためのlayoutを同じにしない**ことである。

### 復号側でもKV受信を非同期化する

復号instanceのHBMにも余裕は限られるので、無制限にincoming KVをqueueできない。

P/D-Serveでは復号中のrequestが1件終わってslotが空くと、そのspaceへ次のKVを非同期取得し、次iterationからbatchへ加える。

複数KV transferをoverlapさせることも可能だが、復号側に巨大な受信待ちqueueを作ると、事前充填側と同じlocal queue問題が起きる。そのためpending transfer用spaceは比較的小さく保つ。

## 手法5: 大規模networkで転送経路競合を避ける

評価環境では、NPUはnode内でHCCS接続され、rack内・rack間ではRoCE v2対応のToR/spine networkを使う。

1つのP/D requestのKV転送でも、tensor並列などにより複数NPU間のsub-transferが同時に走る。

これらが同じnetwork pathへ偏ると、multi-hopで競合し、transfer timeが数百ms単位まで大きく振れる場合がある。

そこでP/D-ServeはToR/spine間のpath diversityを使い、sub-transferの競合を避けることも運用基盤へ含める。

ここは単一nodeのRDMA microbenchmarkでは見えにくい、数千〜数万device規模特有の問題である。

## 手法6: 最小コストの自動障害復旧

数万acceleratorを常時動かせば、どこかのdevice faultは日常的に起こる。

P/D-Serveはnode上のresident processでNPU状態を監視し、故障instanceを検出したら、

1. Zookeeper上のmetadataから故障instanceを論理的に外す。
2. group内へ「今後そこへ送らない」情報を配る。
3. 新しいstateless containerを1つだけ起動する。
4. RoCE connectionを構築する。
5. 事前コンパイル済みmodelをloadする。
6. health check後に代替instanceとしてmetadataへ追加する。

という流れで置き換える。

group全体をrestartするのではなく、故障した1 instanceだけを交換するため「minimum-cost recovery」と呼んでいる。

論文は進行中requestのlive migrationまでは扱わず、failure時にはconnection cleanupやfallback応答などで終了させる。

## 評価条件

### Hardware / deployment

- 実装: Huawei Ascend + MindSpore
- ミラー環境: 数百NPU
- 商用環境: 数万NPU
- network: HCCS + RoCE v2、ToR / spine構成
- model: 主にPangu系列
- compiled model保存: SFSまたはSSD
- 商用deployment期間: 論文時点で8か月超

論文はprivacy上、request本文そのものをproduction trafficから直接開示せず、実service由来のfine-tuning datasetから構成したrequestを内容分析へ使う。一方、system metrics自体はミラー環境とproduction clusterの両方で測定している。

またfigureの値は多くが0〜1へ正規化され、absolute TTFTやtokens/sの詳細は公開されていない。

## 主要結果

### P/D比最適化: throughputを少なくとも60%改善

scenarioごとにprofilingまたはonline bottleneck detectionで最適P/D比へ調整した条件では、比較した他のP/D比より**throughputが少なくとも60%高い**と報告する。

これは単にaccelerator台数を増やした結果ではなく、同じpipeline内で事前充填と復号のどちらか一方がidleになる不整合を減らした効果である。

### On-demand forwarding: TTFT SLO成功率を最大42.3ポイント改善

local queueを持つ従来方式では、workloadを増やすとtimeoutしないrequestの割合が最悪57%まで落ちた。

事前充填queueを除去し、reject時にgatewayが別instanceへretryする方式では、さらに重いworkloadでも成功率を**少なくとも99%**へ維持した。

同一workload比較で成功率差は最大**42.3ポイント**と報告される。

abstractの「TTFT SLO 42%改善」はこの系統の結果を要約したものと理解できる。

### Block-free KV転送: 平均D2D transfer timeを46%削減

KVキャッシュを小blockごとに送る方式から、連続byte列としてまとめて送り受信側でscatterする方式へ変えることで、D2D bandwidth utilizationが改善し、平均transfer timeを**46%削減**した。

主因はdata量そのものの圧縮ではない。小blockごとに発生していたcontrol/confirmationのbubbleを減らしたためである。

### aggregated serving比6.7×の読み方

論文はP/D-Serve全体について、事前充填と復号を同じinstanceで実行する集約型LLM servingに対して**6.7× throughput**と報告する。

ただし評価節では、これは「商用の最初のdisaggregated LLM version」がすでにaggregated servingに対して達成していた全体差をbaselineとして扱っている。

したがって、**P/D-Serve論文で追加した3つの最適化だけで6.7×になった**と読むのは適切でない。

P/D-Serve固有の追加改善を見るなら、60%のP/D比改善、42.3ポイントのsuccess-rate改善、46%のD2D時間削減などを分けて見る方がよい。

## 既存研究との差

### Splitwise / DistServeとの違い

SplitwiseやDistServeは、事前充填と復号の性質が違うのでresource poolを分けるという基本設計を示した。

P/D-Serveはその上で、**数万device・複数scenario・商用trafficでは、pool自体をさらに細かく分けて動的に組み替えなければならない**とする。

つまり「PとDを分けるか」が研究質問ではなく、

- どのscenarioを同じgroupにするか
- P/D比をいつ変更するか
- connection mapをどう再構成するか
- fault時にどう1 instanceだけ交換するか

まで扱う。

### prefix cache研究との違い

CachedAttentionやMooncakeなどはKVの再利用・外部memory poolを重視する。

P/D-Serveはhost memoryへ巨大なKV poolを作ること自体が中心ではなく、**同種requestを同じ小さなprefill groupへ寄せることで、限られたHBMに置いたprefix KVの命中率を高める**。

論文はhost memory poolと直交する手法だとしている。

### scheduler研究との違い

通常のschedulerはより正確なqueue lengthやlatency predictorを作ろうとする。

P/D-Serveのprefill制御は逆に、**不正確なglobal predictionへ依存しすぎず、instanceのaccept/rejectをfeedbackとして使う**。

これは大規模distributed systemでstate observationに遅延がある場合の一般的な設計としても興味深い。

## 一般的な実装への示唆

### 1. 「最適resource比」はmodel propertyではなくworkload propertyでもある

同じmodel・同じhardwareでも、input/output length分布やprefix hit率が変わればprefill/decode balanceは変わる。

capacity planningは平均token数だけで固定せず、scenario単位に分けて追う方がよい。

### 2. staleなglobal stateを精密化するより、local rejectionをbackpressureに使える

数千nodeからglobal schedulerへ完全な瞬時状態を集めるのは難しい。

accept/rejectのような局所的なsignalを使えば、schedulerのstate freshness問題をある程度避けられる。

### 3. memory layoutとnetwork layoutは別々に最適化できる

PagedAttention blockはHBM管理には有利でも、network packet/transfer単位として有利とは限らない。

storage/memory/networkを跨ぐsystemでは、各階層に最適なrepresentationへ変換するcostと、転送効率のtrade-offを考える必要がある。

### 4. 大規模化するとfailure recoveryも推論critical pathの一部になる

数万deviceでは故障を例外として扱えない。role assignment、network connection、model loading、routing metadata更新まで自動化し、失敗instanceだけを交換できることがavailabilityへ直結する。

## 限界・注意点

- Ascend NPU、MindSpore、Huawei内のMLOps / RoCE infrastructureへ強く最適化されたproduction systemであり、CUDA / vLLM clusterへ同じ実装をそのまま移せるわけではない。
- 全figureが正規化値中心で、absolute TTFT、tokens/s、network throughput、model sizeなどの詳細な再現条件は限定的である。
- production request本文はprivacy上公開されず、content分析にはservice由来fine-tune datasetを利用するため、第三者が同一traffic分布を再現するのは難しい。
- P/D比調整は事前profilingまたはlatency signalに依存する。急激なworkload変化に対して、role再構成・model loadが瞬時に完了するわけではない。
- on-demand forwardingはglobal queue predictionを減らす一方、gateway retryとconnection管理の負担を増やす。
- block-free transferには送信側の連続bufferが必要で、そのHBM reservation costがある。fine-grained groupingとqueue抑制により確保可能とするが、別workloadではtrade-offが変わる。
- layer-by-layer転送を使う場合はmodel graphへoperatorを挿入する必要があり、完全にtransparentではない。
- 進行中requestのlive migrationは扱わず、重大fault時はcleanup/fallbackで終了する。
- 6.7×はP/D-Serve追加機構だけのincremental speedupではなく、aggregated servingからdisaggregated commercial baselineまでを含む全体差として解釈する必要がある。
