# MemServe: Conテキスト Caching for分離型 LLM Serving with Elastic Memoryプール

> プリフィルとデコードを別実行単位へ分ける推論提供で、GPU / CPU上のKVキャッシュを実行単位横断で検索・共有・転送できる共通メモリプールを作り、過去接頭部の再利用と処理段階間KV移動を同じ仕組みで扱うシステム。

## 概要

P/D分離ではプリフィルで作ったKVをデコード側へ送り、接頭部キャッシュでは要求終了後のKVを別要求から再利用する。しかしKVを一つの実行単位に閉じ込めると、処理段階間の移動とクラスタ横断の再利用を同時に扱えない。

MemServeはGPU HBMとCPU DRAM上のKVを実行単位横断の共通メモリプールとして索引化し、必要なブロックを検索・共有・転送する。ネットワーク送信時だけ小ブロックをまとめ、P/D転送の固定費と再プリフィルを減らす。

v3の8×H800評価では、ShareGPTでP/D同居比ジョブ完了時間を最大42%改善し、P/D分離へ文脈キャッシュを加えると追加で最大29%改善した。

## 問題設定

LLM推論提供では、同じ接頭部を持つ別要求間で過去のKVキャッシュを再利用する文脈キャッシュと、プリフィル／デコードを別実行単位へ分けて干渉を減らす分離推論がそれぞれ有効である。

しかし従来の推論提供エンジンはKVキャッシュを「1要求・1実行単位に閉じた中間状態」として扱う設計が多く、両者を組み合わせにくい。

プリフィル／デコードを分けると、プリフィルで作ったKVをデコード実行単位へ転送する必要がある。さらにそのKVを将来の別要求でも再利用したいなら、要求終了後も

- そのKVがクラスタ内のどこに残っているか
- GPU / CPUのどちらにあるか
- 別実行単位へどう送るか

を追跡しなければならない。

また要求ルーティングを単純な待ち行列長だけで決めると、別実行単位に存在する長いキャッシュ済み接頭部を使えず再プリフィルが発生する。

## 手法

### 1. GPU / CPU上のKVを実行単位横断の共通メモリプールとして扱う

MemServeは各推論実行単位上でMemプールを動かし、クラスタ内のGPU HBMとCPU DRAMをKVキャッシュ用の共通メモリとして扱う。

主に次の3種類の処理をまとめる。

- **メモリブロック管理:** KVブロックを確保・解放し、GPU / CPU間で移動する
- **索引管理:** プロンプトトークン列とKVの保存場所を対応付け、実行中KVだけでなく要求終了後の過去KVも検索する
- **実行単位間転送:** 別実行単位へKVを送り、送信側・受信側でモデル分割方法やネットワークが違っても転送層側で吸収する

論文の **伸縮可能メモリプール** は、固定した1実行単位のメモリではなく、**クラスタ内のGPU / CPUメモリを必要に応じてKV置き場としてまとめて使う**という意味である。

### 2. プリフィル→デコードのKV移動と、別要求の接頭部再利用を同じ仕組みにする

MemServeは通常のプリフィル/デコード同居構成だけでなく、両処理段階を別実行単位へ分ける構成でも過去KVを再利用する。

プリフィル側でキャッシュ済み接頭部を使うだけでなく、デコード側に残っているKVも将来要求の再利用対象とする。必要ならデコード実行単位からプリフィル実行単位へKVを戻す。

つまり処理段階間KV転送を、**その要求だけの一回限りの状態移動ではなく、クラスタ全体で検索・再利用できるキャッシュ管理の一部**へ広げる。

### 3. 小さいKV blockをnetwork送信時だけまとめる

PagedAttention型のKVは小さいブロックへ分かれている。そのまま1ブロックずつネットワーク APIで送ると、送信回数が増えてオーバーヘッドが大きい。

MemServeは転送時だけ複数KVブロックを大きな単位へまとめ、一度に送る。論文のブロック集約 / huge-ページ的な設計は、**論理的には小ブロック管理を保ちつつ、物理的転送だけ大きくする**工夫を指す。

小ブロック管理はPagedAttentionとの互換性や細かな解放には有利だが、ネットワーク転送では1回ごとのAPI発行・同期・メタデータ処理が固定費になる。そこで送信時だけ連続した大きな単位へ束ねることで、固定費を多数ブロックへ償却し、リンク帯域を使いやすくする。受信後は再び実行エンジンのブロック配置へ対応付けるため、メモリ管理粒度を粗くすることなく転送粒度だけを最適化できる。

### 4. 「どの実行単位に接頭部KVがあるか」を全体スケジューラが知る

スケジューラは各実行単位にどの接頭部 KVが存在するかを木構造状索引で把握する。

新しい要求が来たときは、単純に最も空いている実行単位へ送るのではなく、

- どれだけ長い接頭部を再利用できるか
- その実行単位の待ち行列がどれだけ混んでいるか
- KVを別実行単位から運ぶ必要があるか

を比較する。

論文の全体プロンプト木構造は、この**クラスタ全体の接頭部→KV所在地索引**を指す。

この索引が必要なのは、P/D分離後は『同じ要求のKVがどこにあるか』だけでなく『別要求が再利用できるKVがどこに残っているか』まで探索対象になるからである。要求到着時に各実行単位へ問い合わせていては制御遅延が増えるため、全体スケジューラが接頭部と所在地をまとめて把握し、最長一致するキャッシュ候補を先に特定する。これにより、再プリフィルで節約できる計算量と遠隔転送量を要求振り分け前に比較できる。

## 実装・評価条件

- Memプール / 全体スケジューラを新規実装。
- vLLMを改造して文脈キャッシュとP/D分離を統合。
- GPU間転送にはNCCL send/recv、DRAMが関わる転送にはsocketを使用。
- 主評価環境は **8× NVIDIA H800 80GB** の単一サーバー。
- ShareGPT、LooGLEなど、プロンプト / 生成長や接頭部共有率の異なるワークロードで評価。
- P/D同居、同居＋キャッシュ、P/D分離、P/D分離＋キャッシュを比較する。

## 主要結果

論文v3で報告される代表値は以下。

- ShareGPTではMemプールベースのP/D分離により、P/D同居構成に対してジョブ完了時間を最大 **42%改善**。
- さらにP/D分離へ文脈キャッシュを加えることで、完了時間を追加で最大 **29%改善**。
- 長プロンプト・比較的短い生成を持つLooGLEでは、P/D分離が最大 **10.8%改善**し、文脈キャッシュの追加でさらに最大 **26.9%改善**。

重要なのはキャッシュ単体やP/D分離単体の高速化より、**両者が必要とするKV状態管理を共通基盤へまとめ、同時に使えるようにした**点にある。

## 既存研究との差

- **vLLM / PagedAttention:** 要求内のKVブロック管理が中心。MemServeはそのKVを要求終了後・実行単位横断まで長寿命化し、クラスタ水準状態として扱う。
- **SGLang:** 共有接頭部を要求間で再利用する。MemServeはこの文脈キャッシュをP/D分離クラスタへ広げ、遠隔 KV転送と全体ルーティングまで扱う。
- **Pensieve / CachedAttention:** 複数ターン履歴を要求間で保存する。MemServeはセッション単位に限らず共有接頭部をクラスタ全体に検索し、P/D間でも移動・再利用できるメモリ基盤を主題にする。
- **DistServe / Splitwise:** プリフィルとデコードを分離する。MemServeは処理段階間KV転送を過去キャッシュ再利用と統合する。
- **Mooncake:** 同じくP/D分離と全体KVキャッシュを強く結び付ける後続方向。MemServeは共通分散メモリ APIとしてのMemプールを前面に出す。

## 実装上の含意

LLM推論提供を状態保持型にするほど、スケジューラだけでなくKVキャッシュの**所在・寿命・検索索引・転送**をクラスタ全体資源として扱う必要が出る。

特にP/D分離、接頭部キャッシュ、セッションキャッシュを個別機構として実装するとKV転送経路が重複しやすいため、MemServeのような共通メモリ層を挟む設計は組合せを整理しやすい。

一方、キャッシュ局所性を優先しすぎれば特定実行単位へ要求が集中するため、実運用では接頭部ヒットで節約できる計算量と待ち行列化遅延、KV転送コストを同じコストモデルで比較する必要がある。

例えば遠隔GPUに非常に長い接頭部KVが残っていれば、それをnetwork経由で取得して再利用する方がローカルで全接頭部を再プリフィルするより安い場合がある。逆に共有部分が短い、networkが混雑している、転送先の待ち行列が長い場合は、キャッシュを捨てて空いた実行単位で再計算した方が早い。分散KVキャッシュでは『ヒットするか』だけでなく、ヒットを使う実コストまで比較する必要がある。

## 限界

- 主評価は8×H800の**単一サーバー**であり、複数ノード・異種ネットワークを跨ぐ大規模クラスタでの拡張性は限定的。
- 過去KVを長く保持するほどキャッシュ処理能力と追い出し方策が重要になるが、SSDまで含む大規模階層キャッシュは主題ではない。
- 接頭部局所性を考慮したルーティングはキャッシュ再利用を増やす一方、負荷均衡とのトレードオフを持つ。
- モデル重み配置やサーバーレス冷間起動そのものは扱わない。

## 引用関係・研究系統上の位置

MemServeはvLLM、SGLang、Pensieve、Splitwise、DistServeなどを土台に、**文脈キャッシュと分離型推論を同一KVメモリ基盤で結合する**位置にある。後続のMooncakeなどと合わせると、推論提供構成が「計算実行単位中心」から「クラスタ全体 KV状態中心」へ移る流れを理解しやすい。

研究系統としては `LLM Serving / Scheduling / Disaggregation` に分類する。KVキャッシュオフロード自体ではなく、分散 KV管理を使って推論提供構成と要求ルーティングを改善することが最終目的だからである。
