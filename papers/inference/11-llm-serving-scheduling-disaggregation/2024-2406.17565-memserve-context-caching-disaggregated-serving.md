# MemServe: Context Caching for Disaggregated LLM Serving with Elastic Memory Pool

## 一文要約

prefillとdecodeを別instanceへ分けるservingで、GPU / CPU上のKV cacheをinstance横断で検索・共有・転送できる共通memory poolを作り、過去prefixの再利用とphase間KV移動を同じ仕組みで扱うsystem。

## 問題設定

LLM servingでは、同じprefixを持つ別request間で過去のKV cacheを再利用する文脈キャッシュと、prefill / decodeを別instanceへ分けて干渉を減らす分離推論がそれぞれ有効である。

しかし従来のserving engineはKV cacheを「1 request・1 instanceに閉じた中間状態」として扱う設計が多く、両者を組み合わせにくい。

prefill / decodeを分けると、prefillで作ったKVをdecode instanceへ転送する必要がある。さらにそのKVを将来の別requestでも再利用したいなら、request終了後も

- そのKVがcluster内のどこに残っているか
- GPU / CPUのどちらにあるか
- 別instanceへどう送るか

を追跡しなければならない。

またrequest routingを単純なqueue長だけで決めると、別instanceに存在する長いcached prefixを使えず再prefillが発生する。

## 手法

### 1. GPU / CPU上のKVをinstance横断の共通memory poolとして扱う

MemServeは各推論instance上でMemPoolを動かし、cluster内のGPU HBMとCPU DRAMをKV cache用の共通memoryとして扱う。

主に次の3種類の処理をまとめる。

- **memory block管理:** KV blockを確保・解放し、GPU / CPU間で移動する
- **index管理:** prompt token列とKVの保存場所を対応付け、実行中KVだけでなくrequest終了後の過去KVも検索する
- **instance間転送:** 別instanceへKVを送り、送信側・受信側でmodel分割方法やnetworkが違ってもtransfer layer側で吸収する

論文の **elastic memory pool** は、固定した1 instanceのmemoryではなく、**cluster内のGPU / CPU memoryを必要に応じてKV置き場としてまとめて使う**という意味である。

### 2. Prefill→decodeのKV移動と、別requestのprefix再利用を同じ仕組みにする

MemServeは通常のprefill/decode同居構成だけでなく、両phaseを別instanceへ分ける構成でも過去KVを再利用する。

prefill側でcached prefixを使うだけでなく、decode側に残っているKVも将来requestのreuse対象とする。必要ならdecode instanceからprefill instanceへKVを戻す。

つまりphase間KV transferを、**そのrequestだけの一回限りのstate移動ではなく、cluster全体で検索・再利用できるcache managementの一部**へ広げる。

### 3. 小さいKV blockをnetwork送信時だけまとめる

PagedAttention型のKVは小さいblockへ分かれている。そのまま1 blockずつnetwork APIで送ると、送信回数が増えてoverheadが大きい。

MemServeは転送時だけ複数KV blockを大きな単位へまとめ、一度に送る。論文のblock aggregation / huge-page的な設計は、**logicalには小block管理を保ちつつ、physical transferだけ大きくする**工夫を指す。

### 4. 「どのinstanceにprefix KVがあるか」をglobal schedulerが知る

schedulerは各instanceにどのprefix KVが存在するかをtree状indexで把握する。

new requestが来たときは、単純に最も空いているinstanceへ送るのではなく、

- どれだけ長いprefixを再利用できるか
- そのinstanceのqueueがどれだけ混んでいるか
- KVを別instanceから運ぶ必要があるか

を比較する。

論文のglobal prompt treeは、この**cluster全体のprefix→KV所在地index**を指す。

## 実装・評価条件

- MemPool / global schedulerを新規実装。
- vLLMを改造して文脈キャッシュとP/D分離を統合。
- GPU間転送にはNCCL send/recv、DRAMが関わる転送にはsocketを使用。
- 主評価環境は **8× NVIDIA H800 80GB** の単一server。
- ShareGPT、LooGLEなど、prompt / generation長やprefix共有率の異なるworkloadで評価。
- P/D同居、同居＋cache、P/D分離、P/D分離＋cacheを比較する。

## 主要結果

論文v3で報告される代表値は以下。

- ShareGPTではMemPoolベースのP/D分離により、P/D同居構成に対してjob completion timeを最大 **42%改善**。
- さらにP/D分離へ文脈キャッシュを加えることで、completion timeを追加で最大 **29%改善**。
- 長prompt・比較的短いgenerationを持つLooGLEでは、P/D分離が最大 **10.8%改善**し、文脈キャッシュの追加でさらに最大 **26.9%改善**。

重要なのはcache単体やP/D分離単体の高速化より、**両者が必要とするKV state管理を共通基盤へまとめ、同時に使えるようにした**点にある。

## 既存研究との差

- **vLLM / PagedAttention:** request内のKV block管理が中心。MemServeはそのKVをrequest終了後・instance横断まで長寿命化し、cluster-level stateとして扱う。
- **SGLang:** shared prefixをrequest間でreuseする。MemServeはこのcontext cachingをP/D分離clusterへ広げ、remote KV transferとglobal routingまで扱う。
- **Pensieve / CachedAttention:** multi-turn historyをrequest間で保存する。MemServeはsession単位に限らずshared prefixをcluster-wideに検索し、P/D間でも移動・再利用できるmemory基盤を主題にする。
- **DistServe / Splitwise:** prefillとdecodeを分離する。MemServeはphase間KV transferをhistorical cache reuseと統合する。
- **Mooncake:** 同じくP/D分離とglobal KV cacheを強く結び付ける後続方向。MemServeは共通distributed-memory APIとしてのMemPoolを前面に出す。

## 実装上の含意

LLM servingをstatefulにするほど、schedulerだけでなくKV cacheの**所在・寿命・検索index・transfer**をcluster-wide resourceとして扱う必要が出る。

特にP/D分離、prefix caching、session cacheを個別機構として実装するとKV transfer pathが重複しやすいため、MemServeのような共通memory layerを挟む設計は組合せを整理しやすい。

一方、cache localityを優先しすぎれば特定instanceへrequestが集中するため、実運用ではprefix hitで節約できる計算量とqueueing delay、KV transfer costを同じcost modelで比較する必要がある。

## 限界

- 主評価は8×H800の**単一server**であり、複数node・異種networkを跨ぐ大規模clusterでのscalabilityは限定的。
- historical KVを長く保持するほどcache capacityとeviction policyが重要になるが、SSDまで含む大規模階層cacheは主題ではない。
- prefix locality-aware routingはcache reuseを増やす一方、load balanceとのtrade-offを持つ。
- model weight placementやserverless cold startそのものは扱わない。

## 引用関係・研究系統上の位置

MemServeはvLLM、SGLang、Pensieve、Splitwise、DistServeなどを土台に、**context cachingとdisaggregated inferenceを同一KV memory基盤で結合する**位置にある。後続のMooncakeなどと合わせると、serving architectureが「compute instance中心」から「cluster-wide KV state中心」へ移る流れを理解しやすい。

研究系統としては `LLM Serving / Scheduling / Disaggregation` に分類する。KV cache offload自体ではなく、distributed KV managementを使ってserving architectureとrequest routingを改善することが最終目的だからである。
