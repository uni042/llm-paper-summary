# FlexPipe: Adapting Dynamic LLM Serving Through Inflight Pipeline Refactoring in Fragmented Serverless Clusters

> 断片化したserverless GPU上でpipeline stageを実行中に細分化・統合し、KV整合性を保ちながら負荷変動へ追随するFlexPipe。

## 概要

数十B〜数百B parameterのLLMは1 GPUへ収まらないことがあり、複数GPUへmodelを分散する。代表的な方法の1つが**Tensor Parallelism（TP）**で、1つの行列演算を複数GPUへ分ける。TPは同じlayer内で頻繁にcollective通信するため、NVLinkや高速InfiniBandのような低遅延・高帯域接続されたGPUを同時に確保できる環境で強い。

もう1つが**Pipeline Parallelism（PP）**で、layerやoperator列をstageへ分け、各stageを別GPUへ置く。前stageのactivationを次stageへ送ればよいので、TPより通信頻度を下げやすく、物理的に離れたGPUでも使いやすい。その代わりstage間に依存があるため、stage数やbatchの選び方が悪いと、あるGPUが前stageの出力を待つ**pipeline bubble / stall**が生じる。

FlexPipeが対象にするserverless clusterでは、このPPの設定を固定すること自体が問題になる。クラウドではGPUが他workloadにも割り当てられ、空きGPUが物理server間へ散らばる。論文の実cluster解析では、85%以上free memoryのGPUを1枚得られる確率が8.7%、同一serverで4枚まとめて確保できる確率は0.02%だった。実際にTP要求の78%が、隣接GPUを取れずPPへfallbackしている。さらにrequest到着間隔の変動係数（Coefficient of Variation; CV）は時間窓によって最大7倍変わり、静的pipelineでは平均GPU utilizationが約17%に留まるケースがある。

ここでpipelineの「細かさ」には逆向きの利点がある。stageを細かくすると1 stageのparameter量が減るため空いている小さなGPU断片へ載せやすく、scale-out時のmodel loadも短く、より大きな合計batchを持てる。一方stage間通信は増える。粗いpipelineは通信が少なく平常時のlatencyが低いが、burstを吸収するbufferが少なく、queueが急増しやすい。

FlexPipeはこのtrade-offを固定点で解かず、**平常時はcoarse pipeline、burst時はfine-grained pipelineへ、serviceを止めずに実行中構成を変える**。そのために、(1) 後から結合・分割しやすいoperator-level partition、(2) KV cacheを壊さないinflight refactoring、(3) 断片GPUをserver/rack/cluster topologyに沿って確保するadaptive scalingを組み合わせる。42 server・82 GPUのKubernetes clusterで、CV=1ではAlpaServe/ServerlessLLM比38.3%低いlatency、CV=4ではAlpaServe比66.1%低いlatencyを報告し、最大8.5倍のresource efficiencyを得る。

## 問題設定

### なぜpipelineを細かくするとburstに強くなるのか

OPT-66B、sequence length 4096の測定では、4 stageから32 stageへ細分化すると1 stageのparameter load時間は47.14秒から5.43秒へ短縮し、最大batchは128から1024へ増える。1 stageのcompute時間も69.94msから9.67msへ下がる。

一方、stage間communicationは6.3msから65.1msへ増える。つまり32-stage構成は常時最速ではない。平常時には通信損失が大きいが、traffic spikeで急いで追加GPUへstageを複製するときには「小さいstageを短時間でloadできる」「細かなstage間にqueueing/bufferingを分散できる」ことが効く。

論文は同じ4-stage pipelineでも、request arrivalのCVが1→4へ変わるとstall overheadが約10倍になり、CV 0.1→8ではgoodputが37%低下、平均queue長が約4倍、stall cycle ratioが22倍になると測る。逆に高CV=4では16-stageが4-stageの約1/3のlatencyになり、細分化によるcommunication overheadよりqueue congestion削減が勝つ。

したがってFlexPipeの制御対象は「GPU枚数」だけではない。**同じGPU総量でも、1 modelを何stageに割るか、各stageでどのbatchを持つか**を短時間のtraffic形状へ合わせる必要がある。

### CVとは何を表すか

CVはrequest到着間隔の標準偏差を平均で割った値で、平均QPSが同じでも「一定間隔で来る」のか「短いburstとidleが交互に来る」のかを区別する。

低CVではcoarse stageで通信回数を減らす方が得になりやすい。高CVでは瞬間queueを吸収するためfine stageへ分け、並列instanceを増やす方が得になる。FlexPipeはこのCVとqueue lengthをruntime control signalへ使う。

## 手法

### 1. Fine-Grained Model Partitioning — 将来「再結合できる」切れ目を先に作る

FlexPipeはmodelのcomputation graph (G=(V,E)) を作り、各operatorについてcompute time (t_c)、parameter size (s_p)、activation size (s_a) をprofileする。

単純に各stageのFLOPsを均等化するのではなく、computeとstage間transferのcycleを揃えつつ、将来merge/splitしやすい境界へregularizationを掛けるdynamic programmingを使う。Transformerならattention blockやMLP blockのような論理境界を保ち、同じparameter groupをcontiguous memoryへ置く。

これが重要なのは、runtime refactoringのたびにweight layoutを全面変換するとmigration costが大きくなるからである。最初のpartition時点で「後から4→8→16 stageへ分けたり戻したりできる階層」を仕込む。

micro-batch sizeが変わるとactivation transfer量も変わるため、基準batchのprofileからlog scalingでcommunication量を補正し、onlineで任意batchの候補構成を見積もる。

### 2. Granularity Adaptation — throughput / latency / CVからstage数を選ぶ

runtimeでは候補granularity (g_k=(eta_k,b_k))、すなわちstage数とbatch sizeの組を持つ。各候補についてprofile済みthroughput (T_k)、latency (L_k) を使い、現在trafficのCV (
u_t) がその候補の得意領域へどれだけ近いかを加味してscoreを計算する。

安定trafficなら通信の少ないcoarse pipelineへ寄せ、burst性が高いとfine pipelineへ移す。さらにgranularityごとのcoordination overheadを考慮して、何個のdata-parallel replicaを持つかも決める。

この判断は2〜32 stageの候補でも5ms未満で完了するとされる。つまりpipelineを作り直す判断自体を長いoffline optimizerにせず、短いtraffic変化へ追随できるcontrol loopにしている。

### 3. Inflight Refactoring — 旧pipelineを動かしたまま新pipelineへ状態を移す

実行中にstage境界を変えると、weightだけでなく既存requestのKV cacheが問題になる。あるrequestが旧GPUでprefill/decodeしていた途中にrouting先を切り替えると、新GPUにそのrequestの過去KVがなければ次tokenを正しく計算できない。

FlexPipeはtoken単位のvalidity maskで、どのKV部分が新構成へ同期済みかを追う。新しいpipelineへparameter/KVを非同期transferしている間も、旧pipelineでinferenceを継続する。必要状態が揃った段階でrouting metadataを更新し、新pipelineへ切り替える。

したがってrefactoringは「全requestを止める→全cacheをcopy→再開」ではない。旧構成をfallbackとして生かしつつselective synchronizationするため、service interruptionを抑えられる。

GPU間transferにはRDMAを優先し、RDMA非対応machineではkernel-space copyを行える`sendfile`へfallbackする。NCCL接続をrefactoringごとに新規構築すると秒単位のconnection setupが入るため、それを避ける実装になっている。

### 4. Hardware Efficiency Optimization — stable workloadは共有、bursty workloadは隔離する

断片GPUを埋めるため複数modelのstageを同じGPUへmultiplexするとutilizationは上がるが、同時burstが起きると互いに遅くなる。

FlexPipeは各stageのthroughput/memory効率へ、workload CVに応じたmultiplexing penaltyを加えてplacementを解く。penaltyはCVの二乗で強くなるため、stable workloadはGPUを共有させやすく、高CV workloadはperformance isolationを優先する。

同じmodelのstageを同じGPUへ重ねることは禁止し、pipeline parallelismそのものを壊すresource contentionを避ける。

### 5. Adaptive Pipeline Scaling — queueとCVから「どの粒度で増設するか」を決める

traffic spikeではpipeline全体を丸ごと1 replica増やすと大量GPUが必要になり、fragmented clusterでは確保待ちが長い。FlexPipeはstage単位でscaleできるようにし、queue lengthとCVが大きいほどfine-grained expansionへ寄せる。

ただし追加stageの初期化時間を含めてもSLO deadline内にqueueを処理できることをconstraintにする。つまり「空きGPUが見つかったから増やす」ではなく、**そのstageをloadしている時間も含め、増設がdeadlineへ間に合うか**を見る。

### 6. Hierarchical Resource Graph — server/rack/clusterの競合を別レベルで見る

複数modelが同時scale-outすると、GPU memoryだけでなくPCIe、rack network、persistent storage I/Oを同時に奪い合う。FlexPipeはこれをHierarchical Resource Graph（HRG）として、server levelのGPU memory/PCIe、rack levelのnetwork、cluster levelのstorage I/Oへ分けて追跡する。

recent scaling eventがあるpathを避けることで、複数のcold startが同じrack/storageへ集中するのを抑える。

さらにscale-down時にGPUからweightをevictしてもhost DRAMにはparameter copyを残し、再scale時には過去にそのmodelを載せたserverをaffinity scoreで優先する。storageから再readするcold startを、host cacheからのwarm startへ変える仕組みである。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| cluster | Kubernetes v1.23.7、42 servers、82 GPUs |
| network | 100 Gbps |
| host memory | 各server 256 GB以上 |
| workloads | Microsoft Azure Functions trace + Splitwise corpus |
| models | Whisper-9B、LLaMA2-7B、BERT-21B、OPT-66B |
| serverless baselines | ServerlessLLM、Tetris |
| pipeline / multiplexing baselines | AlpaServe、MuxServeほか |
| traffic | baseline 20 QPS、2時間、CVを1/2/4等へ変化 |
| metrics | goodput、E2E latency、queue time、stall recovery、GPU utilization、initialization latency |

Goodputは、要求されたquality/SLO条件を満たしながら処理できた有効throughputを見る指標である。単にGPU utilizationを上げるだけでSLO違反requestを増やした方式を高性能扱いしない。

### traffic variabilityとlatency

| 条件 | 主結果 | 読み取り |
|---|---:|---|
| CV=1 | AlpaServe/ServerlessLLM比38.3%低latency | stable時はcoarse側へ寄せ通信を抑える |
| CV=2 | MuxServe比46.9%低latency | communication 45→105msへ増えてもqueueを72.6%削減 |
| CV=4 | AlpaServe比66.1%、MuxServe比80.6%低latency | burst時はfine pipelineの追加通信よりqueue削減が大きい |
| CV=4 throughput | maximumの98.3%維持 | static方式はMuxServe -33.3%、ServerlessLLM -40.4% |
| always-ready GPU | peak capacityの75%→30% | peak全量を常時予約しなくてもelastic stageで吸収 |

CV=4の結果は「通信を減らしたから速い」の逆である。FlexPipeはcommunicationを45msから225msへ増やす構成も選ぶが、それ以上にqueueingを減らすためE2E latencyが下がる。狭いkernel latencyではなく、burst時のwaiting timeまで含めた最適化である。

### stall recoveryとresource efficiency

高CV=4でstall recoveryは9msで、AlpaServe 16msより44%、MuxServe 48ms / ServerlessLLM 50msより約82%短い。stallはnormal時P25 latencyの1.5倍超、recoveryは1.2倍以内へ戻った時点として測られている。

resource efficiencyでは、CV=1でFlexPipeは33% GPU utilizationでmaximum goodputを出し、AlpaServeより3倍効率的だった。CV=4ではTetrisが85% utilizationで1,543 requests/sなのに対し、FlexPipeは43% utilizationで12,000 requests/sとなり、論文の定義で8.5倍高いresource efficiencyを示す。

ここで重要なのは「GPU utilizationが高いほど良い」とは限らない点である。static pipelineでは85% utilizationの一部がcontention・stallへ費やされ、goodputへ変換されていない。

## 既存研究との差

AlpaServeのようなpipeline servingはhistorical workloadからpipeline構成をoffline最適化するが、短時間CVが変わってもstage topologyは基本固定である。ServerlessLLM/Tetrisはelastic resource provisionやmemory-efficient hostingを扱うが、modelのpipeline境界そのものをrunning requestを保ったまま組み替えることが中心ではない。

FlexPipeは**resource elasticityとpipeline architecture elasticityを同じ問題として扱う**。空きGPUへ既存pipeline replicaを増やすだけでなく、利用可能GPUの断片度と現在trafficのburstinessに合わせて、model内部のstage granularityまで変更する点が主な差である。

## 限界

refactoringは無料ではない。fine pipelineはstage間communicationを増やし、KV/parameter migrationもnetwork bandwidthを消費する。低CVのまま安定したworkloadでは頻繁なrefactoringは不要で、coarse static pipelineとの差は小さくなり得る。

host-memory parameter cacheはcold startを短くするが、その分host DRAM capacityを使う。RDMAが使えずnetworkが遅い環境ではKV migration時間が増え、traffic変動がrefactoring完了より速い場合は制御が追従しにくい。

また評価clusterは82 GPU・100 Gbps networkであり、数千GPUのmulti-region環境やNVLink island構成ではresource graphとtransfer costが変わる。最大8.5倍はCV=4のresource-efficiency比較であり、すべてのworkloadで同じ倍率になるわけではない。
