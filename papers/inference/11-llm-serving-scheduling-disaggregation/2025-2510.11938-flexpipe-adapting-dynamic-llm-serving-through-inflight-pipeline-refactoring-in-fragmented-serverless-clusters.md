# FlexPipe: Adapting Dynamic LLM Serving Through Inflight Pipeline Refactoring in Fragmented Serverless Clusters

> 断片化したserverless GPU上でパイプライン 段を実行中に細分化・統合し、KV整合性を保ちながら負荷変動へ追随するFlexPipe。

## 概要

数十B〜数百B パラメータのLLMは1 GPUへ収まらないことがあり、複数GPUへモデルを分散する。代表的な方法の1つが**Tensor Parallelism（TP）**で、1つの行列演算を複数GPUへ分ける。TPは同じ層内で頻繁に集合通信通信するため、NVLinkや高速InfiniBandのような低遅延・高帯域接続されたGPUを同時に確保できる環境で強い。

もう1つが**Pipeline Parallelism（PP）**で、層や演算子列を段へ分け、各段を別GPUへ置く。前段の活性値を次段へ送ればよいので、TPより通信頻度を下げやすく、物理的に離れたGPUでも使いやすい。その代わり段間に依存があるため、段数やバッチの選び方が悪いと、あるGPUが前段の出力を待つ**パイプライン バブル / 待ち**が生じる。

FlexPipeが対象にするserverless clusterでは、このPPの設定を固定すること自体が問題になる。クラウドではGPUが他ワークロードにも割り当てられ、空きGPUが物理server間へ散らばる。論文の実cluster解析では、85%以上free メモリのGPUを1枚得られる確率が8.7%、同一serverで4枚まとめて確保できる確率は0.02%だった。実際にTP要求の78%が、隣接GPUを取れずPPへfallbackしている。さらにリクエスト到着間隔の変動係数（Coefficient of Variation; CV）は時間窓によって最大7倍変わり、静的パイプラインでは平均GPU utilizationが約17%に留まるケースがある。

ここでパイプラインの「細かさ」には逆向きの利点がある。段を細かくすると1 段のパラメータ量が減るため空いている小さなGPU断片へ載せやすく、scale-out時のモデル 読み込みも短く、より大きな合計バッチを持てる。一方段間通信は増える。粗いパイプラインは通信が少なく平常時の遅延が低いが、burstを吸収するバッファが少なく、queueが急増しやすい。

FlexPipeはこのtrade-offを固定点で解かず、**平常時はcoarse パイプライン、burst時はfine-grained パイプラインへ、serviceを止めずに実行中構成を変える**。そのために、(1) 後から結合・分割しやすい演算子-level partition、(2) KV キャッシュを壊さないinflight refactoring、(3) 断片GPUをserver/rack/cluster topologyに沿って確保する適応型 scalingを組み合わせる。42 server・82 GPUのKubernetes clusterで、CV=1ではAlpaServe/ServerlessLLM比38.3%低い遅延、CV=4ではAlpaServe比66.1%低い遅延を報告し、最大8.5倍の資源 効率を得る。

## 問題設定

### なぜpipelineを細かくするとburstに強くなるのか

OPT-66B、系列 length 4096の測定では、4 段から32 段へ細分化すると1 段のパラメータ 読み込み時間は47.14秒から5.43秒へ短縮し、最大バッチは128から1024へ増える。1 段のcompute時間も69.94msから9.67msへ下がる。

一方、段間通信は6.3msから65.1msへ増える。つまり32-段構成は常時最速ではない。平常時には通信損失が大きいが、通信量 spikeで急いで追加GPUへ段を複製するときには「小さい段を短時間で読み込みできる」「細かな段間にqueueing/bufferingを分散できる」ことが効く。

論文は同じ4-段 パイプラインでも、リクエスト arrivalのCVが1→4へ変わると待ち オーバーヘッドが約10倍になり、CV 0.1→8では有効スループットが37%低下、平均queue長が約4倍、待ち cycle ratioが22倍になると測る。逆に高CV=4では16-段が4-段の約1/3の遅延になり、細分化による通信 オーバーヘッドよりqueue congestion削減が勝つ。

したがってFlexPipeの制御対象は「GPU枚数」だけではない。**同じGPU総量でも、1 モデルを何段に割るか、各段でどのバッチを持つか**を短時間の通信量形状へ合わせる必要がある。

### CVとは何を表すか

CVはリクエスト到着間隔の標準偏差を平均で割った値で、平均QPSが同じでも「一定間隔で来る」のか「短いburstとidleが交互に来る」のかを区別する。

低CVではcoarse 段で通信回数を減らす方が得になりやすい。高CVでは瞬間queueを吸収するためfine 段へ分け、並列instanceを増やす方が得になる。FlexPipeはこのCVとqueue lengthをランタイム 制御 signalへ使う。

## 手法

### 1. Fine-Grained Model Partitioning — 将来「再結合できる」切れ目を先に作る

FlexPipeはモデルのcomputation graph (G=(V,E)) を作り、各演算子についてcompute time (t_c)、パラメータ サイズ (s_p)、活性値 サイズ (s_a) をprofileする。

単純に各段のFLOPsを均等化するのではなく、computeと段間transferのcycleを揃えつつ、将来merge/分割しやすい境界へregularizationを掛ける動的 programmingを使う。Transformerなら注意機構 ブロックやMLP ブロックのような論理境界を保ち、同じパラメータ グループをcontiguous メモリへ置く。

これが重要なのは、ランタイム refactoringのたびに重み layoutを全面変換するとmigration コストが大きくなるからである。最初のpartition時点で「後から4→8→16 段へ分けたり戻したりできる階層」を仕込む。

micro-バッチ サイズが変わると活性値 transfer量も変わるため、基準バッチのprofileからlog scalingで通信量を補正し、onlineで任意バッチの候補構成を見積もる。

### 2. Granularity Adaptation — throughput / latency / CVからstage数を選ぶ

ランタイムでは候補granularity (g_k=(eta_k,b_k))、すなわち段数とバッチ サイズの組を持つ。各候補についてprofile済みスループット (T_k)、遅延 (L_k) を使い、現在通信量のCV (
u_t) がその候補の得意領域へどれだけ近いかを加味してスコアを計算する。

安定通信量なら通信の少ないcoarse パイプラインへ寄せ、burst性が高いとfine パイプラインへ移す。さらにgranularityごとのcoordination オーバーヘッドを考慮して、何個のdata-並列 replicaを持つかも決める。

この判断は2〜32 段の候補でも5ms未満で完了するとされる。つまりパイプラインを作り直す判断自体を長いoffline 最適化器にせず、短い通信量変化へ追随できる制御 loopにしている。

### 3. Inflight Refactoring — 旧pipelineを動かしたまま新pipelineへ状態を移す

実行中に段境界を変えると、重みだけでなく既存リクエストのKV キャッシュが問題になる。あるリクエストが旧GPUでプリフィル/デコードしていた途中にルーティング先を切り替えると、新GPUにそのリクエストの過去KVがなければ次トークンを正しく計算できない。

FlexPipeはトークン単位のvalidity maskで、どのKV部分が新構成へ同期済みかを追う。新しいパイプラインへパラメータ/KVを非同期transferしている間も、旧パイプラインでinferenceを継続する。必要状態が揃った段階でルーティング metadataを更新し、新パイプラインへ切り替える。

したがってrefactoringは「全リクエストを止める→全キャッシュをcopy→再開」ではない。旧構成をfallbackとして生かしつつselective synchronizationするため、service interruptionを抑えられる。

GPU間transferにはRDMAを優先し、RDMA非対応machineではカーネル-space copyを行える`sendfile`へfallbackする。NCCL接続をrefactoringごとに新規構築すると秒単位のconnection setupが入るため、それを避ける実装になっている。

### 4. Hardware Efficiency Optimization — stable workloadは共有、bursty workloadは隔離する

断片GPUを埋めるため複数モデルの段を同じGPUへmultiplexするとutilizationは上がるが、同時burstが起きると互いに遅くなる。

FlexPipeは各段のスループット/メモリ効率へ、ワークロード CVに応じたmultiplexing penaltyを加えて配置を解く。penaltyはCVの二乗で強くなるため、stable ワークロードはGPUを共有させやすく、高CV ワークロードはperformance isolationを優先する。

同じモデルの段を同じGPUへ重ねることは禁止し、パイプライン 並列化そのものを壊す資源 contentionを避ける。

### 5. Adaptive Pipeline Scaling — queueとCVから「どの粒度で増設するか」を決める

通信量 spikeではパイプライン全体を丸ごと1 replica増やすと大量GPUが必要になり、fragmented clusterでは確保待ちが長い。FlexPipeは段単位でscaleできるようにし、queue lengthとCVが大きいほどfine-grained expansionへ寄せる。

ただし追加段の初期化時間を含めてもSLO deadline内にqueueを処理できることをconstraintにする。つまり「空きGPUが見つかったから増やす」ではなく、**その段を読み込みしている時間も含め、増設がdeadlineへ間に合うか**を見る。

### 6. Hierarchical Resource Graph — server/rack/clusterの競合を別レベルで見る

複数モデルが同時scale-outすると、GPU メモリだけでなくPCIe、rack ネットワーク、persistent ストレージ I/Oを同時に奪い合う。FlexPipeはこれをHierarchical Resource Graph（HRG）として、server levelのGPU メモリ/PCIe、rack levelのネットワーク、cluster levelのストレージ I/Oへ分けて追跡する。

recent scaling eventがあるpathを避けることで、複数の低頻度 startが同じrack/ストレージへ集中するのを抑える。

さらにscale-down時にGPUから重みを追い出ししてもホスト DRAMにはパラメータ copyを残し、再scale時には過去にそのモデルを載せたserverをaffinity スコアで優先する。ストレージから再readする低頻度 startを、ホスト キャッシュからのwarm startへ変える仕組みである。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| cluster | Kubernetes v1.23.7、42 servers、82 GPUs |
| ネットワーク | 100 Gbps |
| ホスト メモリ | 各server 256 GB以上 |
| ワークロード | Microsoft Azure Functions トレース + Splitwise corpus |
| models | Whisper-9B、LLaMA2-7B、BERT-21B、OPT-66B |
| serverless 比較対象 | ServerlessLLM、Tetris |
| パイプライン / multiplexing 比較対象 | AlpaServe、MuxServeほか |
| 通信量 | 比較対象 20 QPS、2時間、CVを1/2/4等へ変化 |
| 指標 | 有効スループット、E2E 遅延、queue time、待ち 回復、GPU utilization、initialization 遅延 |

Goodputは、要求されたquality/SLO条件を満たしながら処理できた有効スループットを見る指標である。単にGPU utilizationを上げるだけでSLO違反リクエストを増やした方式を高性能扱いしない。

### traffic variabilityとlatency

| 条件 | 主結果 | 読み取り |
|---|---:|---|
| CV=1 | AlpaServe/ServerlessLLM比38.3%低遅延 | stable時はcoarse側へ寄せ通信を抑える |
| CV=2 | MuxServe比46.9%低遅延 | 通信 45→105msへ増えてもqueueを72.6%削減 |
| CV=4 | AlpaServe比66.1%、MuxServe比80.6%低遅延 | burst時はfine パイプラインの追加通信よりqueue削減が大きい |
| CV=4 スループット | maximumの98.3%維持 | 静的方式はMuxServe -33.3%、ServerlessLLM -40.4% |
| always-ready GPU | peak 容量の75%→30% | peak全量を常時予約しなくてもelastic 段で吸収 |

CV=4の結果は「通信を減らしたから速い」の逆である。FlexPipeは通信を45msから225msへ増やす構成も選ぶが、それ以上にqueueingを減らすためE2E 遅延が下がる。狭いカーネル 遅延ではなく、burst時のwaiting timeまで含めた最適化である。

### stall recoveryとresource efficiency

高CV=4で待ち 回復は9msで、AlpaServe 16msより44%、MuxServe 48ms / ServerlessLLM 50msより約82%短い。待ちはnormal時P25 遅延の1.5倍超、回復は1.2倍以内へ戻った時点として測られている。

資源 効率では、CV=1でFlexPipeは33% GPU utilizationでmaximum 有効スループットを出し、AlpaServeより3倍効率的だった。CV=4ではTetrisが85% utilizationで1,543 リクエスト/sなのに対し、FlexPipeは43% utilizationで12,000 リクエスト/sとなり、論文の定義で8.5倍高い資源 効率を示す。

ここで重要なのは「GPU utilizationが高いほど良い」とは限らない点である。静的 パイプラインでは85% utilizationの一部がcontention・待ちへ費やされ、有効スループットへ変換されていない。

## 既存研究との差

AlpaServeのようなパイプライン 推論提供はhistorical ワークロードからパイプライン構成をoffline最適化するが、短時間CVが変わっても段 topologyは基本固定である。ServerlessLLM/Tetrisはelastic 資源 provisionやメモリ-efficient hostingを扱うが、モデルのパイプライン境界そのものをrunning リクエストを保ったまま組み替えることが中心ではない。

FlexPipeは**資源 elasticityとパイプライン 構成 elasticityを同じ問題として扱う**。空きGPUへ既存パイプライン replicaを増やすだけでなく、利用可能GPUの断片度と現在通信量のburstinessに合わせて、モデル内部の段 granularityまで変更する点が主な差である。

## 限界

refactoringは無料ではない。fine パイプラインは段間通信を増やし、KV/パラメータ migrationもネットワーク 帯域を消費する。低CVのまま安定したワークロードでは頻繁なrefactoringは不要で、coarse 静的 パイプラインとの差は小さくなり得る。

ホスト-メモリ パラメータ キャッシュは低頻度 startを短くするが、その分ホスト DRAM 容量を使う。RDMAが使えずネットワークが遅い環境ではKV migration時間が増え、通信量変動がrefactoring完了より速い場合は制御が追従しにくい。

また評価clusterは82 GPU・100 Gbps ネットワークであり、数千GPUのmulti-region環境やNVLink island構成では資源 graphとtransfer コストが変わる。最大8.5倍はCV=4の資源-効率比較であり、すべてのワークロードで同じ倍率になるわけではない。
