# 将来KV再利用の受諾義務を推論ランタイムへ安全に対応付ける検査

## 概要

大規模言語モデルの推論基盤には、鍵・値キャッシュ（KVキャッシュ）の保持優先度、期限、CPU・ストレージへの退避、ブロックの保存・削除イベント、退避禁止、キャッシュ状態を考慮した経路選択などがある。しかし、機能が存在することと「この要求が将来このKVを再利用できるようにする」という責任をランタイムが引き受けたことは同義ではない。たとえばCPUにKVのバイト列が残っていても、再利用前にGPUへ戻せなければ将来再利用の保証は満たせない。

本研究は、将来の再利用について受諾された義務をResidentClaimとして表し、ランタイムの機能や外部アダプタがその義務を実際に満たすと判定するための条件を研究する。中心は請求識別子、受諾時点、再利用可能な状態を定義する判定条件、順序付きの状態遷移、請求単位に帰属できる結果である。根拠が不足するときには「似た機能があるから対応済み」と判断せず、近似・不適合・証拠不明に留める失敗閉鎖（fail-closed）の判定を採る。

公開されているTensorRT-LLM、SGLang/HiCache、Dynamoの機能は有用な基盤であり、一部の外部アダプタによる観測証拠も成立するが、著者が監査した証拠からはネイティブなResidentClaim適合を認定できない。一方、局所改変したvLLMのコネクタ・スケジューラ経路では、同一請求に属する復元の失敗を請求単位の拒否結果まで伝えられることを示す。これはキャッシュ退避アルゴリズムの速度改善ではなく、何を根拠に将来再利用の義務を保証と呼べるかを定める意味論・検証研究である。

## 問題設定と契約の対象

優先度を設定しても、その値が実際の退避順序を変えた証拠がなければ、将来保持を保証したことにはならない。時間制限付きの保持欄があっても、責任がいつ終了し、終了前に何が失われたかを識別できなければ、契約違反を判定できない。ブロックが保存されたというイベントも、請求が要求する先頭何トークン分のKVが再利用可能になったかを示さない場合がある。

そこで請求には、安定した請求識別子、再利用対象のKVオブジェクト、どの状態なら利用可能かを決める判定条件、容量・保持モード、受諾と終了の境界、請求に帰属する成功・失敗結果が必要となる。ブロック単位の出来事と請求単位の意味をつなぐ際、モデル、トークナイザ、トークンハッシュ、名前空間、ブロック長、要求識別子などが曖昧なら、イベントを誤った請求へ結び付ける危険がある。

論文の例では、請求Cが先頭448トークン以上の再利用可能性を要求する。受諾、必要なKVの実体化、GPUからCPUへの退避、再利用の要求、CPUからGPUへの復元という順序が意味を持つ。CPUにデータがあるだけでは不十分で、再利用の直前に正しく復元できたことが必要である。復元が失敗した場合は、同じ請求Cの失敗として記録し、必要なら活動中要求を拒否する。別請求の失敗や単なる転送カウンタでは代用できない。

## 手法

### モード別の義務束

検査器は各保持モードに必要な義務の組を定義する。最善努力（best_effort）では、請求識別子と再利用判定条件、請求単位の実体化観測が必要である。軟らかい優先度（soft_priority）では、設定値だけでなく負荷を掛けたときに優先度が保持順序へ影響したことを観測する。強い保護（hard_protected）では、受諾、保護対象の容量、退避対象候補からの除外、資源競合時の明示的な処理、阻害した請求の識別子、損失帰属、出来事の順序が必要になる。

降格可能（demotable）と期限付き（expiring）では、請求の保護責任が終了する境界が実際の損失より前に起きたことを要求する。退避可能（offloadable）では、再利用前の復元可能性に加えて、復元できなかった場合の請求単位の結果が必要である。再利用を考慮した経路選択（routed_reuse）では、どの請求のためにどの経路費用を払ったか、どのワーカーへ置いたか、その後の再利用が成功したかを同じ請求へ帰属する。

| モード | 必須の観測・制御 | 不十分な機能名だけの根拠 |
|---|---|---|
| 最善努力 | 請求の実体化条件と請求単位の観測 | ブロック保存・削除イベントだけ |
| 軟らかい優先度 | 制御した圧迫条件での保持順序への影響 | 優先度値や期間欄だけ |
| 強い保護 | 保護対象の除外、競合時処理、阻害請求の帰属 | 活動中要求の退避禁止だけ |
| 降格・期限付き | 責任終了の順序付き境界 | 優先度変更や単純な時刻計算だけ |
| 退避可能 | 再利用前の復元と同一請求の復元失敗結果 | 保存先階層、転送カウンタだけ |
| 再利用経路選択 | 請求単位の経路費用・配置・後続再利用の帰属 | KV命中率を考慮したワーカー選択だけ |

### 記述子・根拠・信頼境界

ランタイム記述子は、ネイティブ機能、外部アダプタの深さ、義務ごとの根拠、資料や実行記録への参照を持つ。検査器は、各義務について根拠が存在し、その根拠が具体的な位置や実行記録へ結び付けられ、選んだアダプタの深さでその義務を満たせるかを判定する。ある義務に根拠が一つもなければ、同じ名前の機能があっても合格へ昇格させない。

外部アダプタには深さの違いがある。イベントと外部台帳を結合する観測アダプタは、請求単位の実体化を推定できても、ランタイムのメモリ割当器へ保護対象を除外させることはできない。請求台帳、復元フック、経路選択フック、スケジューラフック、割当器フック、ランタイム内部の改変へ進むほど、実際の制御義務を満たせる余地が増える。しかし深いフックが存在するという事実だけでは十分でなく、そのフックが対象請求に対して動いた順序付き根拠が必要である。

たとえば強い保護では、スケジューラが資源競合を拒否する証拠と、割当器が保護対象を退避候補から除外する証拠の両方が必要になる。片方だけであれば、退避によって契約を破る経路が残る。検査器はこのような不十分な証拠を失敗閉鎖で扱う。

### 判定分類と偽陽性の抑止

判定は、ネイティブ機能のみで義務を満たす、適切なアダプタで義務を満たす、近似基盤はあるが義務が欠ける、不適切な対応付けなので拒否、証拠が不足して不明、の五種類である。アダプタによる合格も、観測証拠なのか制御下の優先度効果なのか、内部改変した実経路なのかを分ける。単一の「対応済み」という印は意味が広すぎる。

偽陽性の試験では、請求識別子の不一致、証拠の参照位置の欠落、時系列の逆転、復元失敗ではなく再計算で代替した場合、請求を受諾していない普通の退避、汎用的な転送カウンタなどを検査する。これらが誤って保証へ昇格しないことを確かめる。手作業で作った記述子を検査するため、検査器自体が未監査のランタイム実装を完全に証明するものではないという境界も明記される。

### 局所改変vLLMでの復元失敗経路

正の実装例は、標準vLLMではなく、コネクタとスケジューラ境界を局所改変した実行経路である。請求識別子を実際のプロセス内の退避・読み戻し処理へ通し、同じ請求のCPUからGPUへの復元を意図的に失敗させる。vLLMの無効なKV読込みを扱う経路が失敗を受け取り、請求単位の復元失敗イベントを発行し、阻害した請求識別子を付けて活動中要求の拒否へ進む。

これは単なる模擬カウンタではなく、実際の読み戻し経路とスケジューラ境界を通ることを確認する試験である。一方で、入場前の要求拒否を実装した証拠ではなく、復元失敗が発生した後の活動中要求に対する失敗閉鎖の結果である。論文はこの違いを明示し、上流の標準vLLMがResidentClaimを実装済みだとは主張しない。

## 評価条件と結果

| 評価対象 | 条件・観測 | 結果の意味 |
|---|---|---|
| 記述子と根拠の改変試験 | 16種類の偽陽性制御 | 16/16で不適切な昇格を拒否 |
| vLLM反復試験 | 実行子プロセスとイベント列 | 131/131の処理完了、131/131の有効な順序付き列 |
| vLLM観測経路 | 実体化などの観測 | 30/30の成功 |
| 同一請求の復元失敗 | スケジューラ境界での失敗・拒否 | 30/30の成功 |
| 複数請求の帰属 | 失敗対象と非対象を分離 | 3/3で対象だけ失敗・拒否、非対象は復元成功 |
| 公開TensorRT-LLM | 優先度、期間、イベント、退避 | 一部の観測・優先度アダプタ証拠、ネイティブ保証なし |
| 公開SGLang/HiCache | 階層キャッシュ、要求単位観測 | 一部の実体化観測は可能、退避義務全体の証明なし |
| Dynamo系経路選択 | KVを考慮した配置 | 請求単位の費用・後続再利用の帰属が不足 |

ここで131/131は処理とイベント列の成立件数であり、毎秒の要求処理数ではない。30/30は制御した条件での観測または同一請求の失敗結果が成立した反復件数であり、生産環境の故障率や成功率を推定する数字ではない。16/16は不正な証拠の検出試験であり、未知のすべての誤判定を排除する数学的な完全性証明ではない。

### 公開ランタイムごとの境界

TensorRT-LLMでは、保持優先度と期間の設定、KVブロックイベント、ホスト側キャッシュ、活動中の退避禁止などが確認される。外部台帳とブロック・トークンイベントを決定的に結合できる条件では、特定の最善努力請求の実体化観測が成立する。圧迫条件を変えた優先度試験では軟らかい優先度の効果も確認できる。しかし、それは将来再利用の強い保護や、失敗時の請求単位の復元結果をネイティブに実装したことを意味しない。

SGLang/HiCacheも階層的なキャッシュと観測機構を提供するが、ブロックや要求のイベントを請求台帳へ結合して初めて限定的な観測証拠になる。CPU・ストレージ階層があるだけでは、将来の請求が必要とするKVを再利用前に戻す保証や、戻せない場合の請求単位の失敗結果までは得られない。DynamoのKV認識経路選択についても、キャッシュ重複のスコアでワーカーを選べることと、受諾済み請求の費用・配置・再利用を一貫して追跡できることは異なる。

### 構成要素の証拠としての読み方

論文の重要な結果は「このランタイムは何を持つか」という単純な互換表ではなく、「このモードの義務のうち、どれが、どの信頼境界で、どの根拠により満たされたか」を分離した判定表である。アダプタの深さを増しただけで合格になるわけではない。根拠のない義務は失敗閉鎖で残し、既存機能の有用性と将来契約への適合性を混同しないことが、負例群の存在理由である。

## 既存研究との差

KVの圧縮、退避、階層キャッシュ、命中率に基づく経路選択の研究は、容量や速度、再利用率を改善する。一方、本論文はそれらの機構が将来再利用の受諾義務を満たすかを検査する。保持優先度や退避APIを新しく発明する研究ではなく、既存のAPIから導ける保証と導けない保証を区別する意味論の研究である。

また、単なる契約仕様の提案に留まらず、記述子と根拠を検査する実行可能な照合器、偽陽性の負例、公開ランタイムの境界調査、局所改変vLLMの実経路という四つを結び付けている。とくに復元失敗を「請求に属する順序付きの結果」へ変換する点が、一般的なキャッシュ命中・不命中の観測と異なる。

## 限界

第一に、検査器は手作業で作成した記述子とアンカー付き根拠を入力とする。監査対象外の実行経路、未知の競合状態、イベント欠落をすべて排除するものではない。アダプタ自身が誤った請求識別子を発行したり、出来事を取りこぼしたりする場合、根拠の信頼性が崩れる。失敗閉鎖の方針は曖昧な場合に合格を与えないという保守的な規則であり、ランタイムの形式検証を自動で完成させるわけではない。

第二に、公開ランタイムの分類は監査時点の特定バージョン・根拠の範囲に限定される。新しい版で契約に必要なフックが追加されれば再評価が必要である。ネイティブ適合なしという結果を「これらのランタイムにはKV再利用機能がない」という意味へ読み替えてはならない。

第三に、局所改変vLLMの正例は、復元失敗と活動中要求の拒否が同一請求に帰属することを示すが、上流標準vLLMでの完成済み実装ではない。生産環境の負荷、スループット、初回トークン時間、通常の復元遅延、障害耐性の優位性も測定していない。将来KV再利用契約を製品環境で導入するには、監査範囲を広げた実装・運用検証が必要である。
