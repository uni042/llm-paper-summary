# gpu-let：GPUの空間分割を使う複数モデル推論の応答時間制約付きスケジューリング

## 概要

本論文は、オンラインの複数モデル推論において、応答時間のサービス水準目標（service-level objective; SLO）を守りながらGPUの演算器を無駄なく使うためのスケジューリングを扱う。推論要求は到着を待って初めてバッチを形成できるため、学習と違って常に巨大なバッチを用意できるとは限らない。短い応答時間を優先すると小さなバッチを実行することになり、物理GPU全体を占有しても演算器の一部が使われない。複数モデルを時間順に切り替えるだけでは、この遊休部分を他モデルへ同時に渡せない。

著者らはNVIDIAの複数プロセスサービス（Multi-Process Service; MPS）による演算資源の空間分割を利用し、GPUの一定割合を割り当てた仮想GPU「gpu-let」を抽象化する。モデルごとに要求到着率、バッチサイズ、区画の演算資源割合、実行時間の関係を事前計測し、同居時の干渉を推定したうえで、要求を複数gpu-letへ配置する。需要が変化すれば区画を組み直す。提案の干渉考慮版「gpulet+int」は、同一4 GPU実機で既存の時間共有方式SBPに対し、5種類の複数モデル推論シナリオにおける最大処理量を平均102.6%改善した。

**適用範囲に重要な制約がある。** 実験モデルはLeNet、GoogLeNet、ResNet50、SSD-MobileNet、VGG-16という画像系ネットワークであり、LLMの自己回帰生成、KVキャッシュ容量、初回トークン遅延を測定した研究ではない。GPU資源分割・干渉予測・SLO制御という基盤設計はLLM配信にも検討価値があるが、報告された倍率をLLMへ直接転用してはならない。

## 問題設定：バッチを増やすと遅延が増え、増やさないとGPUが余る

既存の複数モデル推論システムNexusは、モデルの要求到着率と応答時間制約から、各GPUへモデルを詰め込む変形箱詰め方式「squishy bin packing（SBP）」を使う。複数モデルのバッチを時間的に順番に処理するため、一度にGPUへ割り当てるのは原則として一つのモデルのバッチである。モデル別の実行時間と要求の蓄積時間を足してSLOに収めるよう、バッチ形成の周期（duty cycle）を調整する。

この方式は、大きなバッチならGPUの並列演算器を効率よく使えるが、小さなバッチには過大な演算資源を与える。原著図3ではGoogLeNet、ResNet50、SSD-MobileNet、VGG-16について、バッチサイズを1から32、区画割合を20%から100%へ変えて実行時間を計測する。バッチが小さいと区画を増やしても遅延がほとんど下がらない平坦領域があり、GPUの残り部分を別モデルへ渡せる余地があることが分かる。

著者らはGPU分割の効果を1,023種類の要求到着率の組合せでも検討した。モデル5種類それぞれに4通りの到着率を与え、全ゼロの1通りを除いた4の5乗マイナス1の組合せである。空間分割は時間共有のみのSBPが処理不能と判定する組合せを大きく減らす。ただし、この事前観察だけでは同時実行時のメモリ帯域競合や実運用時の再分割費用を考慮していないため、分割しただけでSLOが保証されるわけではない。

同じGPUで二つのモデルを同時に実行すると、GPUの演算器割合を別々に設定してもL2キャッシュや外部DRAM帯域などを奪い合う。原著の事前実験では、モデルとバッチと分割比率の組合せで作った250組について、同居による遅延増分を測定し、90%の組合せで干渉増分は18%未満だったが、残りの長い裾では無視できない遅延増加が生じた。したがって資源分割と同居干渉の予測を一体で扱う必要がある。

## 手法

### 1. gpu-let抽象：MPSの演算資源割合を独立した推論実行先として管理

gpu-letは物理GPUの一定割合の計算資源を持つ仮想実行単位である。入力は物理GPUの空き計算資源、モデルの推論要求、各モデルの応答時間目標であり、区画を割り当てると、その区画に対応する実行器プロセスがモデルのバッチを処理する。物理GPUを複数のgpu-letに分ければ、二つのモデルのカーネルを同時に実行できる。これはモデルを高速化する新しいCUDAカーネルではなく、既存カーネルが占有するGPUの計算資源を管理する仕組みである。

実装はNVIDIA MPS制御デーモンの稼働スレッド割合（active thread percentage）を使って区画の演算能力を制限する。原著のRTX 2080 TiはTuring世代であり、Ampere以降のメモリ帯域分離機能を実験に利用したわけではない。したがって「計算資源を分けたからメモリ帯域も完全に独立」という仮定は置けず、後述の干渉モデルが必要になる。

### 2. 事前性能測定：バッチ数と区画割合から実行遅延を引く

スケジューラはモデルごとに、バッチサイズ$b$と区画割合$p$に対する推論実行時間$L(b,p)$を事前測定して保持する。各モデルの到着率$rate_m$は指数移動平均で追跡し、SLOを満たすバッチ形成と実行の組合せを選ぶ。区画を増やしたときに実行時間が急減する領域と、増やしてもほとんど速くならない領域を分け、性能曲線の曲率が大きい「ひざ」に相当する割合を効率のよい区画$p_{eff}$とする。

さらに現在の到着率をSLO違反なく処理するために必要な最小区画$p_{req}$を求め、原著の擬似コードでは$p_{ideal}=\min(p_{eff},p_{req})$を選ぶ。必要量が効率のよい割合より大きい場合は、一つの区画を無理に肥大化させず、未処理到着率を次の反復で別区画へ割り当てる。これは、単一モデルへGPUを100%与えるより、効率のよい区画を複数用意した方が総処理量を上げられるという観察に基づく。

### 3. 弾性区画割当て：要求到着率順の貪欲配置と時間共有の併用

弾性区画割当て（ElasticPartitioning）は、一定のスケジューリング周期ごとにモデルを要求到着率の降順へ並べる。各モデルについて未割当ての要求率が残る限り、最適区画割合を計算し、空きgpu-letを小さい順に探索する。適切な区画が物理GPUの100%領域しかなければ、必要な区画と残りの区画に分割し、後続モデルへ残余を回す。このときバッチの実行時間に干渉予測分を足してもSLOを満たすか検査する。

すでに配置済みのモデルと時間共有できる場合は、区画を統合して既存実行器へ相乗りさせる選択肢も調べる。空間分割一辺倒ではなく、同じ区画を時間共有する方がよい場合には時間共有へ戻せることが重要である。全GPUの分割比率、モデル配置、バッチ数を完全探索すると、原著は探索空間の規模を$O(P^N NPM^2)$と整理する。ここで$P$は分割戦略数、$N$はGPU数、$M$はモデル数であり、実運用では貪欲な増分割当てに置き換えている。大域最適解の保証はない。

### 4. 同居干渉の予測：L2キャッシュ利用率とDRAM帯域を線形結合

分割された二つの区画が同時に動くとき、片方の遅延はもう片方のL2キャッシュ利用とDRAM帯域消費の影響を受ける。原著はNVIDIA Nsight Computeで単独実行時の両モデルのL2利用率とDRAM帯域消費を測り、二モデルの4つの説明変数と定数項を線形結合する干渉係数を学習する。係数は$c_1$から$c_5$までであり、同居時の遅延増加を予測して区画割当てのSLO判定へ反映する。

原著は1,250組の同居条件から2,500件の推論実行データを作り、1,750件で回帰係数を学習、750件で検証した。予測誤差が10.26%以下に収まるのは90%の条件、13.98%以下に収まるのは95%の条件である。この予測は完全ではないが、干渉を無視して危険な配置を採用するより、SLO違反の可能性が高い要求率を処理不能と判定する保守的な判断に使える。

### 5. 実行系と再構成：フロントエンド、バックエンド、20秒周期

C++約12,100行のフロントエンドスケジューラはモデル別に到着要求を貯め、必要バッチ数に達するか周期が満了すると、Unixドメインソケットでバックエンド推論実行器へバッチを送る。バックエンドはPyTorchでモデルを実行し、結果をスケジューラへ返す。モデルとGPU区画の割当ては負荷の変化に応じて再計算され、必要なら別のMPS区画を用意する。

実装の再編成周期は20秒である。GPU区画を作り直すにはプロセス起動、PyTorchカーネル準備、モデルロード、ウォームアップが必要で、実測で約10〜15秒を要したため、背景で再構成して稼働中の処理をなるべく妨げない。区画変更が瞬時に完了する仕組みではなく、需要変動がこの再構成時間より速いと予測誤差とSLO違反が残り得る。

## 評価

### 実験条件

| 項目 | 原著の条件 |
|---|---|
| 計算機 | Xeon E5-2630 v4（20コア）、ホストDRAM 192GB |
| GPU | NVIDIA RTX 2080 Ti 11GB ×4、各4,352 CUDAコア、616GB/s公称メモリ帯域 |
| 実行環境 | Ubuntu 16.04.6、CUDA 10.2、ドライバ440.64、PyTorch 1.2 |
| 要求発生器 | 別サーバから40Gbpsネットワーク経由で到着、モデルごとにポアソン到着を模擬 |
| モデル | GoogLeNet、LeNet、ResNet50、SSD-MobileNet、VGG-16。いずれも画像認識・物体検出系 |
| モデル別SLO | GoogLeNet 44ms、LeNet 5ms、ResNet50 95ms、SSD-MobileNet 136ms、VGG-16 130ms |
| 複数モデル応用 | game（LeNet×6とResNet50）、traffic（SSD→GoogLeNet/VGG-16） |
| 比較対象 | Nexus由来SBP、事前測定値を与えたguided self-tuning、干渉なしgpulet、干渉ありgpulet+int |
| 主な指標 | SLO違反を生じず処理可能な最大要求率、SLO違反率、処理可能シナリオ数、理想スケジューラとの比 |

SLOはモデルごとの単独実行遅延の約2倍として設定され、表の値は画像推論要求に対するもの。要求到着は実測のインターネットサービスログではなく、合成した到着率とポアソン過程に基づく。比較対象のguided self-tuningには事前測定値と最適区画を与えており、通常のオンライン探索だけを行う実装より有利な条件で比較している。

### 代表結果と読み方

| 条件・指標 | 比較対象 | 提案方式 | 原著の結果 | 解釈 |
|---|---|---|---|---|

最初の「102.6%増」は速度倍率102.6倍ではない。基準を1としたとき約2.026倍である。gpulet（干渉なし）が平均106.0%増と見かけ上さらに高いのは、同居干渉を無視して処理可能と誤判定した要求率を含むためで、原著図13ではequalとshort-skewにおいて1%を超えるSLO違反が発生する。干渉を考慮したgpulet+intは、その要求率を不適格とするか配置を変えることで違反を抑える。処理量だけで最良方式を選ぶとSLO保証の目的を見失う。

最大処理量の実験では、5つのケース（equal、long-only、short-skew、game、traffic）を用いる。equalは5モデル各50 req/s、long-onlyはResNet50、SSD、VGG-16各100 req/s、short-skewはLeNet、GoogLeNet、ResNet50各100 req/sとSSD、VGG-16各50 req/sから開始して到着率を増加させる。アプリケーション構成が違うため、改善率は一つのCNNのカーネル単体の高速化ではなく、モデル混在負荷全体の処理能力を表す。

需要変動への追随評価では、モデルごとに異なる到着率変化を与えると、必要なgpu-letの総割合が増減に追随した。20秒ごとの再編成と干渉予測を使っても、予測が外れた瞬間にSLO違反は発生する。原著本文は1,800秒の観測区間と記す一方、図14の説明文は1,200秒と記しており、観測時間の表記が一致しない。したがって本稿はそのどちらかを無条件に確定せず、SLO違反率0.14%という本文の結果を記載する。

### 構成要素除去と最適解との差

干渉予測の有無を比較したgpuletとgpulet+intの差が、主要な構成要素除去実験に相当する。予測を追加すると最大処理量の平均増加率は106.0%から102.6%へ3.4ポイント低下する一方、危険な配置を抑制する。これはモデルの予測誤差が実サービスのSLO違反へつながる点を示す。線形予測器自体の誤差分布も図9で別途測定されており、システム全体の結果と内部モデルの精度を混同していない。

さらに全探索の理想スケジューラと比較すると、処理可能と判定できた1,023条件のうち18条件を取りこぼす。最大処理可能要求率は理想解の平均92.3%であり、特にtrafficでは87.7%へ低下する。貪欲なbest-fitが短時間で実用的な配置を得る代わりに、複数モデルの配置相互作用を完全には最適化できないことが分かる。

## 既存研究との違い

NexusのSBPは、モデル別のSLOを守るためのバッチ周期とモデルのGPU配置を決めるが、GPUを空間的に分割しない。GSLICEはGPUの空間分割を活用するが、原著が比較する実装では異種モデルを時間共有する柔軟性がない。gpu-letは、同じ物理GPUを小さな計算区画に分ける空間共有、区画内の時間共有、モデルごとのSLOを同時に扱い、さらに同居干渉を推定する点で異なる。

GPU分割そのものはMPSが既に備える機能である。論文の新規性はハードウェアの新機能ではなく、区画割合をモデルのバッチ・到着率・SLOへ対応付け、干渉を考慮して複数GPUへ配置し直すシステム設計にある。単純にMPSを有効化するだけで平均102.6%増になると解釈してはならない。

## 限界・LLM推論への適用判断

最大の限界は評価対象がCNNを中心とする画像推論であることだ。自己回帰LLMでは事前処理（prefill）と逐次生成（decode）でGPU計算とメモリ帯域の比率が異なり、KVキャッシュが文脈長と同時要求数に応じて成長する。したがって画像モデルの固定入力に対するバッチ・区画曲線を、そのままLLMのTTFT（初回トークン遅延）やTPOT（トークン間遅延）の制約へ適用できない。LLMへ移植するなら、少なくとも事前処理と生成を分けた$L(b,p)$の測定、KVメモリ上限、メモリ帯域の競合、長文脈と短文脈の混合要求を含む再評価が必要である。

またMPSの計算資源割合はGPUメモリ容量を自動的に分離しない。異なるモデルの重みを同時に置くには、合計のVRAM使用量が物理GPUの容量を超えないことが前提になる。再分割には実測10〜15秒を要するため、短い突発的な需要変動に対する即応策とはならない。線形干渉モデルも、L2とDRAM帯域の二つの資源利用指標だけで全ての実行干渉を正確に説明するものではない。

原著の比較はRTX 2080 Ti×4という単一サーバ構成に限定される。最新GPUのMIG区画、複数ノード間通信、モデルロードが非常に重い巨大LLM、GPUごとの異種性能差、障害復旧、エネルギー消費を包括的に評価したものではない。コード公開を将来行うとの記載はあるが、一次資料中に確認できる公式配布先URLはない。これらは未評価または未確認の事項として残す。
