# SLO-Aware GPU DVFS for Energy-Efficient LLM Inference Serving

> RPSとGPU周波数からp95/p99遅延を予測し、25生成反復ごとにSLOを満たす最低周波数へDVFSする方式。GPT-J-6B＋A100/A30の実機配信で、最大周波数運用比22.8〜45.5%のエネルギー削減を示す。

## 概要

GPUによる大規模言語モデル（Large Language Model; LLM）配信では、最高周波数で実行すれば遅延を短くしやすいが、サービス水準目標（Service-Level Objective; SLO）より十分速い時間帯にも余分な電力を使う。逆に周波数を一律に下げると、負荷が高い時間帯にp95/p99の尾部遅延がSLOを越える。

この問題がLLMで難しいのは、自己回帰生成中にも実行負荷が変わるためである。流入要求が増減すると動的バッチ処理（inflight batching）の実効バッチサイズが変わり、1生成反復の実行時間も変わる。同じGPU周波数でも、要求毎秒（Requests Per Second; RPS）が低いときには大きな遅延余裕がある一方、高負荷時には最高周波数でも余裕がほとんどない。

本論文は、GPUの動的電圧・周波数制御（Dynamic Voltage and Frequency Scaling; DVFS）をこの余裕へ追従させる。まずオフラインで一部の「GPU周波数×RPS」を計測し、p95またはp99のエンドツーエンド尾部遅延を3次多項式で近似する。オンラインでは約25生成反復ごとにRPSを再計測し、予測上SLOを満たす候補のうち最も低い周波数を選ぶ。安全な候補がなければ最高周波数へ戻る。

NVIDIA Triton Inference ServerとTensorRT-LLM上でGPT-J-6Bを配信し、A100 SXM 40GBとA30 24GBを使った実機評価では、既定の最大周波数運用に対して22.8〜45.5%のエネルギー削減を報告する。利得は低〜中負荷、緩いSLO、p95制約で大きく、高負荷では周波数を下げる余地がなくなる。

## 問題設定

### 最大周波数は「SLOより速い」時間をエネルギーとして浪費する

配信系の目的は最短遅延そのものではなく、指定されたSLOを守りながら要求を処理することである。たとえばp99エンドツーエンド遅延が7秒以下というSLOなら、最大周波数で5秒まで縮めても、その2秒分の余裕は利用者側の追加価値にならない場合がある。

GPUは周波数を下げると演算性能が落ちる一方、電力・エネルギーを削減できる。したがって遅延余裕が大きいときだけ周波数を下げ、余裕が縮んだら戻すのが自然である。

### 固定電力制御では動的バッチの負荷変化を扱いにくい

LLM配信では、要求が到着・完了するたびに動的バッチ内の系列数が変わる。特に自己回帰デコードは多数の短い生成反復を繰り返すため、1件の要求を処理している最中でも負荷状態が変わり得る。

固定周波数や静的な電力上限は、この変化に追従できない。低負荷へ合わせれば高負荷でSLOを破り、高負荷へ合わせれば低負荷時にエネルギーを浪費する。本論文はRPSを負荷の軽量な代理変数として使い、反復中に周波数を更新する。

## 手法全体

処理はオフライン較正とオンライン制御に分かれる。

1. 対象GPUについて複数のRPSとGPU周波数を選び、尾部遅延を計測する。
2. RPS増加・周波数低下で遅延が悪化する単調性を利用し、明らかにSLOを満たせない領域の計測を省く。
3. 収集した点から、GPU周波数とRPSを入力、p95/p99エンドツーエンド遅延を出力とする3次多項式モデルを学習する。
4. 配信時には一定反復ごとに最近のRPSを観測し、移動窓で平滑化する。
5. 候補GPU周波数ごとの尾部遅延をモデルで予測する。
6. SLO以下と予測される周波数のうち最低値を選び、NVIDIA管理コマンド（nvidia-smi）で周波数を変更する。
7. どの候補もSLOを満たさない場合は最大周波数へ戻す。

## 手法

### 1. 疎なオフライン計測で周波数–負荷–尾部遅延面を作る

Ampere GPUには多数の周波数段階があり、全周波数×全RPSを総当たりで測ると較正コストが大きい。論文は、同じRPSなら周波数が高いほど遅延は悪化しにくく、同じ周波数ならRPSが高いほど尾部遅延が悪化するという単調性を使う。

ある点でSLOを満たせないことが分かれば、より低周波数・高RPS側の多くを計測対象から外せる。こうして較正データ量を削った後、残る点で予測モデルを作る。

### 2. 3次多項式でp95/p99エンドツーエンド遅延を予測する

入力はGPU周波数とRPS、出力は対象SLOに対応するp95またはp99尾部遅延である。著者らは線形・2次・3次の近似を比較し、負荷と周波数の非線形な関係を十分表せる3次多項式を採用する。

A100では全プロファイルデータの12.5%程度でも平均絶対誤差（Mean Absolute Error; MAE）を0.2秒未満へ抑えられた。A30では同程度の精度により多くの点が必要で、少なくとも約35%を使うとMAE 0.3秒未満になる。

予測器は性能最大化ではなく、SLO境界をまたがない最低周波数を判断するための安全余裕推定器として使われる。そのため誤差が大きい装置では較正点を増やす必要がある。

### 3. 約25生成反復ごとにRPSを更新する

実行時は約25 LLM反復、時間にしておおむね1秒ごとにRPSを計測する。短期変動で周波数を振動させないよう移動窓で平滑化し、大きな負荷スパイクが起きた場合は古い履歴を引きずらないよう窓をリセットする。

更新周期を無限に細かくできない理由の一つは、GPU周波数変更をNVIDIA管理コマンド経由で行うオーバーヘッドである。1トークンごとにDVFSするのではなく、生成反復を数十回まとめて制御する。

### 4. SLOを満たす最低周波数を選び、危険時は最大周波数へ戻す

現在のRPSに対して候補周波数を予測モデルへ入力し、p95またはp99尾部遅延がSLO以下になる候補を列挙する。その中で最も低い周波数を選ぶ。

予測上どの周波数でもSLOを満たせない高負荷状態では、節電より遅延を優先して最大周波数へ戻る。したがって制御器は「常に周波数を下げる」のではなく、余裕がある区間だけエネルギーを回収する。

## 評価

### 代表的な評価条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA A100 SXM 40GB、NVIDIA A30 24GB |
| モデル | GPT-J-6B |
| 配信基盤 | NVIDIA Triton Inference Server + TensorRT-LLM |
| バッチ | 動的バッチ処理（inflight batching） |
| 負荷生成 | MLPerf Inference Server方式のPoisson到着＋Alibaba本番トレースをGPU能力へ縮尺 |
| 出力長 | 各要求128新規トークン |
| 入力長 | 可変 |
| 尾部指標 | p95 / p99エンドツーエンド遅延 |
| 厳しいSLO | A100 7秒、A30 8.4秒 |
| 緩いSLO | 10秒 |
| 基準方式 | Triton既定最大周波数（DEF） |
| 追加比較 | 全較正点を使う参照表方式（Lookup Table; LUT） |
| 主指標 | 総エネルギー、尾部遅延、予測誤差 |

### 代表的な結果

| 条件・観察 | 結果 | 何を示すか |
|---|---|---|
| 全GPU/SLO設定 | 最大周波数比22.8〜45.5%のエネルギー削減 | SLO余裕をDVFSへ変換できる |
| 緩い10秒SLO | 厳しいSLOより節電幅が大きい | 許容遅延が大きいほど低周波数区間を増やせる |
| p95制約 | p99より節電幅が大きい傾向 | 尾部の厳しさが周波数選択を制約する |
| A100予測器 | 較正点約12.5%でMAE < 0.2秒 | 全周波数総当たりは不要 |
| A30予測器 | 約35%以上でMAE < 0.3秒 | GPUごとに必要較正量が異なる |
| 高RPS区間 | 周波数低下余地がほぼ消える | 利得は負荷依存で、常時同率ではない |
| 学習モデル対LUT | 細粒度15 MHz刻みを選べるため条件によりLUTを上回る | 補間モデルが未計測周波数も利用できる |

A100のトレースではRPSが5を超えるような高負荷区間でほぼ最大周波数が必要になり、節電幅が縮む。逆に低〜中負荷では周波数を下げ、尾部遅延をSLO境界へ近づけることでエネルギーを削減する。

この結果は「周波数を下げれば常に効率が上がる」という主張ではない。遅延余裕がある区間だけ周波数を下げることが重要で、負荷が高い場合は通常運用と同じ最大周波数へ収束する。

## 既存研究との差

静的なGPU電力上限や固定DVFSは、負荷が変わるLLM配信で一つの設定を使い続ける。一部の従来DNN配信研究はバッチサイズと周波数を共同調整するが、自己回帰LLMの反復中に要求が出入りする動的バッチでは状態変化がより細かい。

本論文はモデル内部の重み、量子化、KVキャッシュ、スケジューラを変更せず、外部から観測できるRPSとGPU周波数だけで尾部SLOを予測して制御する。既存Triton/TensorRT-LLMへ比較的薄い制御層として加えられる点が特徴である。

一方、後続研究で見られる出力長予測やKVキャッシュ状態、インスタンス数の共同最適化までは扱わない。この論文の制御変数はGPU周波数、主要負荷信号はRPSである。

## 限界・実装状況

評価モデルはGPT-J-6B一種類、GPUはAmpere世代のA100/A30に限られる。モデル規模、量子化、GPU世代、メモリ帯域律速の強さが変われば周波数感度も変わるため、予測モデルは再較正が必要になる。

SLOは128トークン生成全体のエンドツーエンド尾部遅延で評価しており、初回トークン遅延（Time To First Token; TTFT）と1出力トークン当たり時間（Time Per Output Token; TPOT）を個別SLOとして最適化していない。対話型サービスでTTFTとTPOTを別々に保証する場合は拡張が必要である。

RPSは軽量な負荷指標だが、同じRPSでも入力長、出力長、モデル、KVキャッシュ占有量で実コストは変わる。本評価では出力長を128トークンへ固定しているため、出力長分布が広い本番負荷ではRPSだけの予測精度が低下し得る。

また周波数変更は管理コマンドを介するため無償ではなく、制御周期を約1秒まで粗くしている。急激な負荷変化への追従性と周波数切替オーバーヘッドには交換条件がある。

## 一般的な実装上の含意

LLM配信の省エネルギー化では、平均利用率だけでなくSLOまでの遅延余裕（slack）を資源として扱える。余裕があるときだけクロックを下げる方が、常時電力上限を設定するより尾部遅延を管理しやすい。

ただし予測器はGPU・モデル・負荷分布に依存する。実装する場合は、SLO境界付近で予測誤差を吸収する余裕、負荷急増時の最大周波数フォールバック、周波数切替自体のオーバーヘッドを一緒に測る必要がある。
