# Taming Request Imbalance: SLO-Aware Scheduling for Disaggregated LLM Inference

> 長短requestが混在するprefill/decode分離型servingで、prefill完了予測とSLO残余時間からurgentなrequestを先に処理し、decodeではTPOT SLOまでのslack内に短いrequestを選択的に詰めることで、head-of-line blockingとstraggler待ちを減らす。

## 概要

prefillとdecodeを別GPU群へ分離するservingでは、request lengthのlong-tail分布が2種類の非効率を生む。prefill側では長いrequestが先頭に来ると後続の短いrequestが待たされ、time-to-first-token（TTFT）SLOを落とす。decode側では長短requestを同じcontinuous batchへ入れると、1 stepの時間が最も長いrequestに引っ張られ、短いrequestが毎step待つ。

本研究のKairosは、prefillとdecodeそれぞれに軽量なSLO-aware schedulingを入れる。prefillでは各requestの完了時刻をonline throughputから予測し、TTFT SLOまでの残り時間をrequest長で正規化したurgencyで優先順位を決める。decodeではrequestごとのTPOT SLOまでのslackと、batch size・sequence lengthごとのstep time lookup tableを使い、SLOを破らない範囲で短いrequestだけを先に進める。

## 手法

### 1. Prefill完了時刻を予測し、SLOに近いrequestを優先する

prefill schedulerはqueue中の各requestについて、remaining prefill tokensを現在のprefill throughputで割って完了時刻を推定する。prefix-cache hit等で実際に必要なtoken数が変わるため、この推定は各scheduling stepで更新する。

各requestについて、予測完了時刻がTTFT SLOまでにどれだけ余裕を残すかを計算し、その値をrequest lengthで正規化したurgency scoreを作る。短いrequestは同程度の残余時間なら優先される一方、長いrequestもdeadlineへ近づけばurgencyが上がるため、単純なshortest-job-firstのようなstarvationを避ける設計になっている。

### 2. DecodeではTPOT SLOまでのslackを使ってbatchを動的に分ける

各active requestについて、これまでの経過時間、生成済みtoken数、TPOT SLO、現在のsequence lengthから、次tokenまでに残っているslackを計算する。schedulerは全request中の最小slackを安全予算として使う。

batch sizeとsequence lengthから1 decode step時間を引くlookup table（LUT）を持ち、短いrequestをsequence length順に検討する。そのrequestを加えてもstep timeが最小slack以下で、かつthroughputが改善する場合だけbatchへ入れる。条件を満たさないrequestはそのstepでは遅延させ、slackがない場合は通常どおり全requestをdecodeする。

LUTはmodel-hardware構成ごとにoffline profilingし、runtimeでも実測step timeで更新する。したがってhardware variabilityや他processの干渉でstep timeが変わっても、固定profiling値だけに依存しない。

## 評価

### 結論

同一4-prefill GPU + 4-decode GPU構成でDistServeと比較し、SLO attainmentとdecode throughputの両方を改善している。特にQPS 3.0付近でhead-of-line blockingとdecode stragglerの影響が大きくなり、end-to-end SLO attainment差が最大になる。

### 評価環境

| 項目 | 設定 |
|---|---|
| Hardware | 8× NVIDIA H200 SXM、192 Intel Xeon Platinum 8558 cores、2 TB RAM、NVLink/NVSwitch |
| 配置 | 4 GPU prefill + 4 GPU decode、各TP4 |
| Model | MiniMax-M2.5 |
| Dataset | 実運用LLM service由来の1000-request online trace、long-tail sequence length |
| Baseline | DistServe、同じ4P+4D / TP4構成 |
| SLO | TTFT 8 s、TPOT 50 ms |

### 主な結果

- QPS 3.0でend-to-end SLO attainmentはKairos 89.6%、DistServe 55.8%で、33.8 percentage point高い。
- 同じQPS 3.0でTTFT SLO attainmentは100%対76.1%で、23.9 point改善する。
- TPOT SLO attainmentはQPS 3.0で89.6%対62.5%となり、27.1 point改善する。
- QPS 2.0でmedian decode throughputは28.1 tok/s対23.6 tok/sで19.3%改善し、QPS 2.0〜4.8では13〜19%程度高い。
- motivation測定ではMiniMax-M2.5で8K-token requestのdecode stepが約11.0 ms、128K-tokenでは約40.3 msとなり、同batch化時に短いrequestが約29.3 ms/step待つ例を示している。

これらはkernel単体ではなく、実機のdisaggregated serving prototype上でのrequest-level指標である。一方、比較対象は主にDistServeであり、複数schedulerとの広範な比較ではない。

## 既存研究との差

同名の別研究 `arXiv:2607.02043` のKairosは、decode nodeの余剰computeへprefillそのものをdeflectし、inter-node KV transferも避ける方式である。本論文 `arXiv:2605.02329` のKairosは別研究で、prefill/decodeの配置自体は維持しながら、prefill queueの優先順位とdecode batch compositionをSLO slackに基づいて変える。

DistServeのFCFS prefill + continuous batchingを直接のbaselineとし、output length predictionやrequest preemptionを使わず、prefill time predictionと実測decode step LUTだけでadaptする点が中心差分である。

## 限界・実装状況

- 主評価は単一server、8× H200、MiniMax-M2.5、1種類のproduction traceに限定される。別model、別interconnect、multi-node構成で同じ改善幅になるかは未確認。
- TTFT 8 s / TPOT 50 msという固定SLOで評価しており、より厳しい/緩いSLOでslack-guided batchingの有効範囲は変わる。
- decode LUTはmodel-hardware構成ごとのprofilingを必要とする。runtime更新は行うが、急激な性能変動時には推定誤差が残り得る。
- prefill completion predictionは平均throughputを用いるため、複雑なinterferenceや急激なqueue状態変化を完全には表現しない。
- 一次資料から公式code repositoryは確認できなかった。
- 同じ「Kairos」という名称の別研究が同repoに存在するため、system名ではなくcanonical arXiv IDで識別する必要がある。

## 一般的な実装上の含意

SLOが平均latencyより緩い場合、その差分は単なる余裕ではなくschedulerが利用できるresource budgetとして扱える。特にdecodeでは「全active requestを毎step必ず一緒に進める」必要はなく、token delivery deadlineを守る範囲でstepごとのbatch membershipを変えることで、長いsequenceが短いsequenceへ与える同期待ちを減らせる。
