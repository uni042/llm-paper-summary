# Taming リクエスト Imbalance: SLO-考慮 スケジューリング for Disaggregated LLM 推論

> この論文の狙いは、長いリクエストを単純に後回しにすることではない。**各リクエストがサービス水準目標（サービス レベル 目的: SLO）を破るまでにどれだけ時間の余裕を持っているか**をスケジューラが使い、余裕のないリクエストを先に進めつつ、余裕のあるリクエストは短時間だけ待たせる。これによりプリフィル側の先頭待ちとデコード側の長文リクエストによる同期待ちを減らす。

## まず何が問題なのか

大規模LLM サービングでは、入力プロンプト全体を処理する**事前充填（プリフィル）**と、出力トークンを1個ずつ生成する**復号（デコード）**を別GPU群へ分けることがある。これを**プリフィル-デコード分離（プリフィル-デコード disaggregation）**という。

プリフィルとデコードは性能特性がかなり違うため、別GPUへ分けるとそれぞれを独立にscaleできる。しかしリクエスト長が大きくばらつくと、今度は各phaseのスケジューラで別種類の非効率が現れる。

この論文が扱うのは次の2つである。

1. プリフィル側の**先頭ブロッキング（ヘッド-of-line ブロッキング）**
2. デコード側の**straggler interference**

## SLO、TTFT、TPOTとは何か

論文では平均遅延だけでなく、利用者-facingなdeadlineを重視する。

### 最初のトークンまでの時間（時間 To 先 トークン: TTFT）

リクエスト送信から最初の出力トークンが届くまでの時間である。

主に

`queue待ち + prefill + KV transfer + 最初のdecode`

で決まる。

### トークン間時間（時間 Per 出力 トークン: TPOT）

最初のトークン以降、次のトークンが届くまでの平均的な間隔である。

例えばTPOT SLOが50 msなら、システムは概ね50 ms以内ごとに次トークンを利用者へ渡せればよい。

ここで重要なのは、GPUが10 msでトークンを作れるなら残り40 msは**余裕時間（slack）**としてスケジューラが利用できることだ。

この論文はそのslackを「他リクエストを少し進めるための安全予算」として使う。

# 1. プリフィル側: なぜFCFSでヘッド-of-line ブロッキングが起こるのか

一般的な先着順（先-Come, 先-Served: FCFS）キューを考える。

例えばプリフィル キューが

1. 128K トークンの長いリクエスト A
2. 2K トークンの短いリクエスト B
3. 1K トークンの短いリクエスト C

の順だったとする。

Aのプリフィルに長時間かかると、BとCは自分自身ならすぐ処理できるにもかかわらずAの後ろで待つ。

これがヘッド-of-line ブロッキングである。

短いリクエストを常に先にする**最短ジョブ優先（Shortest ジョブ 先: SJF）**なら平均遅延は下がるが、今度は長いリクエストが新しい短リクエストに抜かれ続け、飢餓（starvation）する危険がある。

したがって必要なのは

- 短リクエストの速さを活かす
- ただしdeadlineへ近い長リクエストは確実に救う

という優先順位である。

## プリフィル スケジューリングの考え方

スケジューラはキュー中の各リクエストについて、現在のプリフィル スループットと残りトークン量から**予測完了時刻**を計算する。

プレフィックス キャッシュ hit等により実際に処理すべきトークン数が変わるため、この見積りはスケジューリング 段階ごとに更新する。

次に

`TTFT SLOまで残っている時間`

を計算する。

この余裕が少ないリクエストほどurgentである。

ただし余裕時間だけを見ると、大きなリクエストが常に不利になる。そこで論文はdeadlineまでの余裕をリクエスト長で正規化した**緊急度（urgency）**を使う。

直感的には

- 同じdeadline余裕なら、すぐ終わる短リクエストを先に片付ける
- 長リクエストでもdeadlineが迫るにつれてurgencyが上がり、最終的には先に処理される

という動きになる。

そのためSJFよりstarvationを抑えつつ、FCFSより短リクエストを救いやすい。

この優先順位は、短い入力を常に優先して長い入力を放置する規則ではない。各リクエストの残り時間、見積もった処理時間、期限までの余裕を同じ尺度で更新するため、短いリクエストの回転を保ちながら、期限が迫った長いリクエストの順位も自然に上がる。入力長の偏りが大きい場合でも、プリフィル側で待ち行列が詰まり続けることを避けるための判断材料になる。デコード側でも同じ考え方を使い、各段階で余裕を再計算して、今進めるべき要求と一時的に待たせられる要求を区別する。これにより、長い要求を無条件に排除せず、短い要求の処理機会だけを必要な範囲で増やせる。

# 2. デコード側: なぜ長いsequenceが短いsequenceを遅らせるのか

デコードでは複数リクエストを1つの**連続バッチ（連続 バッチ）**としてGPUへ流す。

1 iterationで各リクエストが1 トークンずつ進むのが基本である。

しかしアテンションは各リクエストの過去KV キャッシュを読むため、sequence 長さが長いほど1 段階の処理が重くなる。

論文のMiniMax-M2.5測定では、

- 8K-トークン リクエスト: デコード 段階 約11.0 ms
- 128K-トークン リクエスト: 約40.3 ms

である。

この2つを同じバッチへ入れると、短いリクエスト側の計算が先に終わってもGPU バッチ全体は長いリクエスト側の処理終了を待つ。

したがって8K リクエストは本来約11 msで進められるのに、約40 ms周期に引っ張られ、1 段階あたり約29 ms待つことになる。

この最も遅いリクエストを**straggler**と呼ぶ。

## 「全稼働中 リクエストを毎段階進める」必要はない

通常の連続 batchingでは稼働中 リクエストを毎iteration一緒に進めることが多い。

しかしTPOT SLOが50 msなら、8K リクエストが前回トークンを11 msで作った後、次トークンを必ず11 ms後に生成する必要はない。

利用者へ50 ms以内に次トークンを渡せればSLOは守れる。

そこで論文は一部リクエストを1 段階だけ休ませ、短いsequence同士を先に進める。

これがデコード側の中心アイデアである。

## Slackとは何か

各リクエストについて、

- 最初のトークンが出てから何ms経ったか
- ここまで何トークン生成したか
- TPOT SLOが何msか
- 次のデコード 段階に何msかかりそうか

を使い、次トークンのdeadlineまで何ms余っているかを計算する。

これが**余裕時間（slack）**である。

例えばTPOT SLOが50 msで、あるリクエストが前回トークンから10 msしか経っていなければ、単純にはまだ40 ms近い余裕がある。

一方、すでに45 ms経っているリクエストにはほとんど余裕がない。

スケジューラは稼働中 リクエスト中で最も小さいslackを安全予算として使う。

# 3. Slack-guided 適応型 batching

## 段階 1: デコード 段階時間を予測する

モデル/ハードウェア構成ごとに

`batch size × sequence length → 1 decode stepの時間`

を表す**参照表（Lookup Table: LUT）**をオフライン profilingで作る。

各構成を100回程度測定して初期値を作り、本番実行後は実測値の履歴平均でLUTを更新する。

したがって完全な静的プロファイルではなく、ランタイムの性能変動にもある程度追従する。

## 段階 2: 短いリクエストから候補へ入れる

稼働中 リクエストをsequence 長さの短い順に並べる。

これは短いリクエストをまとめると1 段階が速くなりやすく、多くのトークンを短時間に進められるからである。

## 段階 3: SLO slackを使って安全性を確認する

候補リクエストをバッチへ追加した場合の段階 時間をLUTで予測する。

その時間が全リクエストの最小slack以内であり、さらにスループットが改善する場合だけ、その短い-リクエスト バッチを実行する。

条件を満たさないリクエストはそのiterationでは進めず、次回へ回す。

slackがほぼ残っていないリクエストがあれば、通常どおり全リクエストをデコードしてdeadline violationを避ける。

## なぜこれでTPOTを破らないのか

重要なのは「GPUがトークンをいつ作るか」と「利用者へトークンをいつ渡すか」は完全には同じではないことだ。

生成がSLOより速いときはトークンを少しバッファできる。

たとえば50 msごとにトークンを届ける必要があるリクエストを10〜20 ms周期で生成できているなら、一時的に別リクエストを先に進めてもバッファされたトークンでdelivery cadenceを保てる。

この余剰をスケジューラが使うことで、平均スループットとTPOT SLOを両立させる。

# 4. プリフィルとデコードの2つを組み合わせる

このシステムは論文中でKairosと呼ばれる。

ただし同repositoryには別研究 `arXiv:2607.02043` もKairosという名前を使っているため、混同してはいけない。

この `arXiv:2605.02329` のKairosは

- プリフィルのキュー順をurgencyで変える
- デコードのバッチ membershipをslackで段階ごとに変える

システムである。

プリフィルをデコード ノードへ移動する研究ではない。

## 評価条件

| 項目 | 設定 |
|---|---|
| ハードウェア | 8× NVIDIA H200 SXM、192 Intel Xeon Platinum 8558 cores、2 TB RAM、NVLink/NVSwitch |
| 配置 | 4 GPU プリフィル + 4 GPU デコード、各TP4 |
| モデル | MiniMax-M2.5 |
| Dataset | 実運用LLM サービス由来の1000-リクエスト トレース、長い-末尾 sequence 長さ |
| 比較対象 | DistServe、同じ4P+4D / TP4構成 |
| TTFT SLO | 8 s |
| TPOT SLO | 50 ms |

## 主要結果

### エンドツーエンド SLO attainment

QPS 3.0で、TTFTとTPOTの両方を満たすリクエスト割合は

- Kairos: 89.6%
- DistServe: 55.8%

となり、**33.8 percentage point**高い。

これは単に平均遅延が少し速くなったというより、「利用者-facingな両deadlineを同時に満たすリクエスト数」が大きく増えたという結果である。

### TTFT

QPS 3.0では

- Kairos: 100%
- DistServe: 76.1%

で、TTFT SLO attainmentは23.9 point改善する。

主にプリフィル キューで長リクエストに短リクエストが巻き込まれるヘッド-of-line ブロッキングを減らした効果である。

### TPOT

同じQPS 3.0では

- Kairos: 89.6%
- DistServe: 62.5%

で、27.1 point改善する。

長sequenceを含むバッチへ短sequenceを毎段階固定で入れず、slackがある間は短い-リクエスト mini-バッチを先に処理する効果である。

### デコード スループット

QPS 2.0でmedian デコード スループットは

- Kairos: 28.1 tok/s
- DistServe: 23.6 tok/s

となり約19.3%改善する。

QPS 2.0〜4.8の範囲でも概ね13〜19%高い。

これはSLOを守るために処理量を犠牲にしたシステムではなく、むしろstraggler同期を減らすことでスループットも改善できたことを示す。

## なぜ効果がQPSで変わるのか

低負荷ならキューが短く、プリフィル HOL ブロッキングもデコード バッチ interferenceも少ないため比較対象との差は小さい。

QPSが上がると

- プリフィル キューに長い リクエストが溜まる
- デコード 稼働中 集合が大きくなる
- 長い/短い sequenceを同時に持つ確率が上がる

ためKairosの余地が大きくなる。

さらに負荷が極端に高くなり全リクエストのslackがほぼ消えると、デコード スケジューラが一部リクエストを待たせる余裕も減る。そのため改善幅は無限には伸びない。

## DistServeとの差

DistServeはプリフィル/デコードを分離し、各phaseへ専用資源を割り当てることでinterferenceを抑える代表的システムである。

この論文はそのphase separation自体は維持する。

違いは、各phase内部で

- プリフィル: FCFSではなくdeadline-考慮 priority
- デコード: 稼働中 集合を毎段階固定せずslack-考慮に分割

する点にある。

つまり**資源 配置を変える研究ではなく、同じ配置の上でリクエスト orderingとバッチ compositionを変える研究**である。

## 別のKairosとの違い

同名の `Towards Load-Aware Prefill Deflection for Disaggregated LLM Serving`（arXiv:2607.02043）は、デコード ノードの余剰計算へプリフィルそのものを移す。

一方、本論文では

- プリフィル リクエストはプリフィル GPUで処理
- デコード リクエストはデコード GPUで処理

という境界を崩さない。

したがってシステム名だけでなくcanonical arXiv IDで識別する必要がある。

## 限界

- 主評価は単一サーバー、8× H200、MiniMax-M2.5、1種類の本番 トレースに限定される。
- 比較対象は主にDistServeで、最新スケジューラを多数並べた広範比較ではない。
- TTFT 8 s / TPOT 50 msという固定SLOであり、SLOが極端に厳しい場合は利用できるslackが減る。
- デコード LUTはモデル/ハードウェアごとのprofilingが必要である。
- ランタイム更新は過去実測の平均なので、急激な性能 変更には遅れて追従する可能性がある。
- プリフィル 完了 予測は平均スループットを使うため、複雑なGPU interferenceや急激なキュー変化を完全には予測しない。
- official コード repositoryは一次資料確認範囲では特定できていない。
- スケジューラはモデル出力を変えないが、リクエストを1 iteration休ませるため、slack推定が外れるとTPOT violationへ直結する。

## 一般的な実装上の示唆

SLOは単なる合否判定値ではなく、スケジューラが利用できる**時間budget**として扱える。

特にstreaming デコードでは、GPUが利用者-facing SLOより速くトークンを生成しているなら、その余裕を

- 短い リクエストの先行処理
- プリフィル work
- background メモリ movement

などへ一時的に振り替えられる可能性がある。

また、連続 batchingは「全稼働中 リクエストを常に一緒に進める」必要はない。リクエストごとのdeadlineを管理できれば、iterationごとにバッチ membershipを変える方が長い-末尾 sequence 長さに強くなる。
