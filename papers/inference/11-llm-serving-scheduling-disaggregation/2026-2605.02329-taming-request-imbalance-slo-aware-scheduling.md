# Taming Request Imbalance: SLO-Aware Scheduling for Disaggregated LLM Inference

> この論文の狙いは、長いrequestを単純に後回しにすることではない。**各requestがサービス水準目標（Service Level Objective: SLO）を破るまでにどれだけ時間の余裕を持っているか**をschedulerが使い、余裕のないrequestを先に進めつつ、余裕のあるrequestは短時間だけ待たせる。これによりprefill側の先頭待ちとdecode側の長文requestによる同期待ちを減らす。

## まず何が問題なのか

大規模LLM servingでは、入力prompt全体を処理する**事前充填（prefill）**と、出力tokenを1個ずつ生成する**復号（decode）**を別GPU群へ分けることがある。これを**prefill-decode分離（prefill-decode disaggregation）**という。

prefillとdecodeは性能特性がかなり違うため、別GPUへ分けるとそれぞれを独立にscaleできる。しかしrequest長が大きくばらつくと、今度は各phaseのschedulerで別種類の非効率が現れる。

この論文が扱うのは次の2つである。

1. prefill側の**先頭ブロッキング（head-of-line blocking）**
2. decode側の**straggler interference**

## SLO、TTFT、TPOTとは何か

論文では平均latencyだけでなく、user-facingなdeadlineを重視する。

### 最初のtokenまでの時間（Time To First Token: TTFT）

request送信から最初の出力tokenが届くまでの時間である。

主に

`queue待ち + prefill + KV transfer + 最初のdecode`

で決まる。

### token間時間（Time Per Output Token: TPOT）

最初のtoken以降、次のtokenが届くまでの平均的な間隔である。

例えばTPOT SLOが50 msなら、systemは概ね50 ms以内ごとに次tokenをuserへ渡せればよい。

ここで重要なのは、GPUが10 msでtokenを作れるなら残り40 msは**余裕時間（slack）**としてschedulerが利用できることだ。

この論文はそのslackを「他requestを少し進めるための安全予算」として使う。

# 1. Prefill側: なぜFCFSでhead-of-line blockingが起こるのか

一般的な先着順（First-Come, First-Served: FCFS）queueを考える。

例えばprefill queueが

1. 128K tokenの長いrequest A
2. 2K tokenの短いrequest B
3. 1K tokenの短いrequest C

の順だったとする。

Aのprefillに長時間かかると、BとCは自分自身ならすぐ処理できるにもかかわらずAの後ろで待つ。

これがhead-of-line blockingである。

短いrequestを常に先にする**最短ジョブ優先（Shortest Job First: SJF）**なら平均latencyは下がるが、今度は長いrequestが新しい短requestに抜かれ続け、飢餓（starvation）する危険がある。

したがって必要なのは

- 短requestの速さを活かす
- ただしdeadlineへ近い長requestは確実に救う

という優先順位である。

## Prefill schedulingの考え方

schedulerはqueue中の各requestについて、現在のprefill throughputと残りtoken量から**予測完了時刻**を計算する。

prefix cache hit等により実際に処理すべきtoken数が変わるため、この見積りはscheduling stepごとに更新する。

次に

`TTFT SLOまで残っている時間`

を計算する。

この余裕が少ないrequestほどurgentである。

ただし余裕時間だけを見ると、大きなrequestが常に不利になる。そこで論文はdeadlineまでの余裕をrequest長で正規化した**緊急度（urgency）**を使う。

直感的には

- 同じdeadline余裕なら、すぐ終わる短requestを先に片付ける
- 長requestでもdeadlineが迫るにつれてurgencyが上がり、最終的には先に処理される

という動きになる。

そのためSJFよりstarvationを抑えつつ、FCFSより短requestを救いやすい。

# 2. Decode側: なぜ長いsequenceが短いsequenceを遅らせるのか

decodeでは複数requestを1つの**連続バッチ（continuous batch）**としてGPUへ流す。

1 iterationで各requestが1 tokenずつ進むのが基本である。

しかしattentionは各requestの過去KV cacheを読むため、sequence lengthが長いほど1 stepの処理が重くなる。

論文のMiniMax-M2.5測定では、

- 8K-token request: decode step 約11.0 ms
- 128K-token request: 約40.3 ms

である。

この2つを同じbatchへ入れると、短いrequest側の計算が先に終わってもGPU batch全体は長いrequest側の処理終了を待つ。

したがって8K requestは本来約11 msで進められるのに、約40 ms周期に引っ張られ、1 stepあたり約29 ms待つことになる。

この最も遅いrequestを**straggler**と呼ぶ。

## 「全active requestを毎step進める」必要はない

通常のcontinuous batchingではactive requestを毎iteration一緒に進めることが多い。

しかしTPOT SLOが50 msなら、8K requestが前回tokenを11 msで作った後、次tokenを必ず11 ms後に生成する必要はない。

userへ50 ms以内に次tokenを渡せればSLOは守れる。

そこで論文は一部requestを1 stepだけ休ませ、短いsequence同士を先に進める。

これがdecode側の中心アイデアである。

## Slackとは何か

各requestについて、

- 最初のtokenが出てから何ms経ったか
- ここまで何token生成したか
- TPOT SLOが何msか
- 次のdecode stepに何msかかりそうか

を使い、次tokenのdeadlineまで何ms余っているかを計算する。

これが**余裕時間（slack）**である。

例えばTPOT SLOが50 msで、あるrequestが前回tokenから10 msしか経っていなければ、単純にはまだ40 ms近い余裕がある。

一方、すでに45 ms経っているrequestにはほとんど余裕がない。

schedulerはactive request中で最も小さいslackを安全予算として使う。

# 3. Slack-guided adaptive batching

## Step 1: decode step時間を予測する

model/hardware構成ごとに

`batch size × sequence length → 1 decode stepの時間`

を表す**参照表（Lookup Table: LUT）**をoffline profilingで作る。

各configurationを100回程度測定して初期値を作り、本番実行後は実測値の履歴平均でLUTを更新する。

したがって完全な静的profileではなく、runtimeの性能変動にもある程度追従する。

## Step 2: 短いrequestから候補へ入れる

active requestをsequence lengthの短い順に並べる。

これは短いrequestをまとめると1 stepが速くなりやすく、多くのtokenを短時間に進められるからである。

## Step 3: SLO slackを使って安全性を確認する

候補requestをbatchへ追加した場合のstep timeをLUTで予測する。

その時間が全requestの最小slack以内であり、さらにthroughputが改善する場合だけ、そのshort-request batchを実行する。

条件を満たさないrequestはそのiterationでは進めず、次回へ回す。

slackがほぼ残っていないrequestがあれば、通常どおり全requestをdecodeしてdeadline violationを避ける。

## なぜこれでTPOTを破らないのか

重要なのは「GPUがtokenをいつ作るか」と「userへtokenをいつ渡すか」は完全には同じではないことだ。

生成がSLOより速いときはtokenを少しbufferできる。

たとえば50 msごとにtokenを届ける必要があるrequestを10〜20 ms周期で生成できているなら、一時的に別requestを先に進めてもbufferされたtokenでdelivery cadenceを保てる。

この余剰をschedulerが使うことで、平均throughputとTPOT SLOを両立させる。

# 4. Prefillとdecodeの2つを組み合わせる

このsystemは論文中でKairosと呼ばれる。

ただし同repositoryには別研究 `arXiv:2607.02043` もKairosという名前を使っているため、混同してはいけない。

この `arXiv:2605.02329` のKairosは

- prefillのqueue順をurgencyで変える
- decodeのbatch membershipをslackでstepごとに変える

systemである。

prefillをdecode nodeへ移動する研究ではない。

## 評価条件

| 項目 | 設定 |
|---|---|
| Hardware | 8× NVIDIA H200 SXM、192 Intel Xeon Platinum 8558 cores、2 TB RAM、NVLink/NVSwitch |
| 配置 | 4 GPU prefill + 4 GPU decode、各TP4 |
| Model | MiniMax-M2.5 |
| Dataset | 実運用LLM service由来の1000-request trace、long-tail sequence length |
| Baseline | DistServe、同じ4P+4D / TP4構成 |
| TTFT SLO | 8 s |
| TPOT SLO | 50 ms |

## 主要結果

### End-to-end SLO attainment

QPS 3.0で、TTFTとTPOTの両方を満たすrequest割合は

- Kairos: 89.6%
- DistServe: 55.8%

となり、**33.8 percentage point**高い。

これは単に平均latencyが少し速くなったというより、「user-facingな両deadlineを同時に満たすrequest数」が大きく増えたという結果である。

### TTFT

QPS 3.0では

- Kairos: 100%
- DistServe: 76.1%

で、TTFT SLO attainmentは23.9 point改善する。

主にprefill queueで長requestに短requestが巻き込まれるhead-of-line blockingを減らした効果である。

### TPOT

同じQPS 3.0では

- Kairos: 89.6%
- DistServe: 62.5%

で、27.1 point改善する。

長sequenceを含むbatchへ短sequenceを毎step固定で入れず、slackがある間はshort-request mini-batchを先に処理する効果である。

### Decode throughput

QPS 2.0でmedian decode throughputは

- Kairos: 28.1 tok/s
- DistServe: 23.6 tok/s

となり約19.3%改善する。

QPS 2.0〜4.8の範囲でも概ね13〜19%高い。

これはSLOを守るために処理量を犠牲にしたsystemではなく、むしろstraggler同期を減らすことでthroughputも改善できたことを示す。

## なぜ効果がQPSで変わるのか

低負荷ならqueueが短く、prefill HOL blockingもdecode batch interferenceも少ないためbaselineとの差は小さい。

QPSが上がると

- prefill queueにlong requestが溜まる
- decode active setが大きくなる
- long/short sequenceを同時に持つ確率が上がる

ためKairosの余地が大きくなる。

さらにloadが極端に高くなり全requestのslackがほぼ消えると、decode schedulerが一部requestを待たせる余裕も減る。そのため改善幅は無限には伸びない。

## DistServeとの差

DistServeはprefill/decodeを分離し、各phaseへ専用resourceを割り当てることでinterferenceを抑える代表的systemである。

この論文はそのphase separation自体は維持する。

違いは、各phase内部で

- prefill: FCFSではなくdeadline-aware priority
- decode: active setを毎step固定せずslack-awareに分割

する点にある。

つまり**resource placementを変える研究ではなく、同じ配置の上でrequest orderingとbatch compositionを変える研究**である。

## 別のKairosとの違い

同名の `Towards Load-Aware Prefill Deflection for Disaggregated LLM Serving`（arXiv:2607.02043）は、decode nodeの余剰computeへprefillそのものを移す。

一方、本論文では

- prefill requestはprefill GPUで処理
- decode requestはdecode GPUで処理

という境界を崩さない。

したがってsystem名だけでなくcanonical arXiv IDで識別する必要がある。

## 限界

- 主評価は単一server、8× H200、MiniMax-M2.5、1種類のproduction traceに限定される。
- 比較対象は主にDistServeで、最新schedulerを多数並べた広範比較ではない。
- TTFT 8 s / TPOT 50 msという固定SLOであり、SLOが極端に厳しい場合は利用できるslackが減る。
- decode LUTはmodel/hardwareごとのprofilingが必要である。
- runtime更新は過去実測の平均なので、急激なperformance changeには遅れて追従する可能性がある。
- prefill completion predictionは平均throughputを使うため、複雑なGPU interferenceや急激なqueue変化を完全には予測しない。
- official code repositoryは一次資料確認範囲では特定できていない。
- schedulerはmodel出力を変えないが、requestを1 iteration休ませるため、slack推定が外れるとTPOT violationへ直結する。

## 一般的な実装上の示唆

SLOは単なる合否判定値ではなく、schedulerが利用できる**時間budget**として扱える。

特にstreaming decodeでは、GPUがuser-facing SLOより速くtokenを生成しているなら、その余裕を

- short requestの先行処理
- prefill work
- background memory movement

などへ一時的に振り替えられる可能性がある。

また、continuous batchingは「全active requestを常に一緒に進める」必要はない。requestごとのdeadlineを管理できれば、iterationごとにbatch membershipを変える方がlong-tail sequence lengthに強くなる。
