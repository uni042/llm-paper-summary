# FLARE: Fine-Grained Length-Aware Routing for Resource-Efficient Heterogeneous LLM Serving

> 出力長からクエリごとの遅延と費用を推定し、精度閾値を満たす候補から資源目的を最小化するモデルを選ぶことで、精度を保ったまま遅延と費用を大幅に削る多モデルルータ。

## 概要

モデルプールが多様化し、能力も価格も異なる大規模言語モデルが並ぶ環境では、クエリごとにどのモデルへ送るかを決めるルーティングが実質の性能を左右する。ところが既存のルータは、正解率を上げること自体を目的に学習されるか、遅延と費用をデータセット単位の粗い近似でしか扱わない。本論文の FLARE（Fine-Grained Length-Aware Routing for Resource-Efficient Heterogeneous LLM Serving）は、この資源感覚の粗さを直す。二つの実測の観察が土台である。第一に、精度の閾値を満たす候補同士では、正解率のばらつきより遅延と費用のばらつきの方がはるかに大きい。つまり「正解できるモデルの中から安くて速いものを選ぶ」余地が大きい。第二に、出力長は遅延と強く相関する（DeepSeek-R1-671B ではピアソン相関0.9605、線形近似の決定係数0.9225）。API の課金が生成トークン数に比例するため、費用とも強く結び付く。

そこで FLARE は、クエリごとに各候補モデルについて正解確率、出力長、遅延、費用の四つを推定する。精度と長さは XGBoost の予測器が担い、遅延はモデルごとの線形回帰で長さから換算し、費用は入出力単価と長さから計算する。そのうえで、予測正解確率が閾値 τ 以上の候補集合に絞り、遅延と費用の重み付き和を最小化するモデルを選ぶ。重みの配分で、精度優先（FLARE-Acc）、効率優先（FLARE-Efficient）、均衡（FLARE-Balance）の三つの動作モードを切り替えられる。新しいモデルがプールへ加わった場合は、約200リクエスト分の初期トレースで遅延回帰と予測器を立ち上げるコールドスタート手順が用意されている。

**代表結果:** 分布内の5データセットで、FLARE-Acc は「精度が最も高い候補を常に選ぶ」方式と同等の精度を保ちながら遅延を最大59パーセント、費用を最大69パーセント削減した。FLARE-Efficient は先行ルータ（RouterBench、TensorOpera）に対して遅延26〜68パーセント、費用44〜75パーセントの削減を、精度の犠牲5〜20パーセントで達成した。分布外の CommonsenseQA と MATH でも三モードとも先行方式よりパレート前線に近い選択（IGD が最小）を示した。ルータ自体の追加負荷は1クエリあたり18.12ミリ秒で、最速モデルの平均遅延1,500ミリ秒に対して無視できる水準である。

## 問題設定

ルーティングの問題は、クエリ x とモデル m の組ごとに、正解したかどうか、出力長、エンドツーエンド遅延、金額コストが決まる点にある。精度だけを見れば大きいモデルが有利だが、遅延と費用は桁違いに開く。本論文の予備調査（観察1）では、MMLU で精度の閾値を満たした候補集合の中では、精度のばらつきより効率指標のばらつきの方が大幅に大きいことが示された。裏を返せば、精度を落とさずに効率だけを改善する選択の余地が、候補集合の中に大量に眠っている。

既存ルータがこの余地を使えない理由は二つある。第一に、TensorOpera のような品質駆動型ルータは正解しそうかどうかだけを学習し、クエリごとの遅延と費用を目的に入れていない。第二に、RouterBench のような費用配慮型でも、データセットごとに固定した小さなモデル集合をオフラインの精度・費用前線から選ぶだけで、クエリごとの費用変動や遅延を扱わないため、難しいクエリへの過小配分や、易しいクエリへの過剰配分が起きる。

もう一つの困難は、遅延と費用をクエリ単位で推定すること自体である。遅延は実行時の競合やシステム側の揺らぎにも左右される。しかし観察2が示すように、自己回帰生成では出力トークン数にほぼ比例してデコード時間が伸びるため、出力長という一つの信号が遅延の分散の大半を説明する。費用はさらに直接的で、多くの API が入力・出力トークン単価で課金する。本論文はこの比例関係を、ルーティングの決定に使える精度で推定する問題として扱う。

## 手法のあらまし

FLARE はオフラインのプロファイリング段階とオンラインの配信段階に分かれる。オフラインでは、訓練クエリをプール内の全モデルへ実際に流し、正解・出力長・遅延・費用を収集する。クエリ側の特徴（意味埋め込み、プロンプト長、データセット種別、全モデルの正解率から作る難易度）とモデル側の記述子（パラメータ数、公開年、知識カバレッジ、配信形態）を結合した特徴ベクトルを作り、正解確率を予測する分類器と出力長を予測する回帰器を XGBoost で学習する。遅延はモデルごとに「遅延＝傾き×出力長＋切片」の線形回帰で結び、費用は単価と長さから決める。オンラインでは、到着したクエリを埋め込み、近傍のプロファイル済みクエリから種別と難易度を推し、各候補の四指標を推定して、精度閾値で候補を絞り、動作モードに応じた目的関数で1モデルを選ぶ。

## 手法

### 1. 問題の定式化 — 精度適格集合とクエリごとのパレート前線

各クエリ x とモデル m について、正解 A、生成語数 L、遅延 T、費用 C を考える。精度閾値 τ に対して、正解確率が τ 以上と予測されるモデルの集合を精度適格集合と定義する。この集合の中で、遅延と費用の両方で劣らず少なくとも一方で優れるモデルは支配関係にあり、支配されないモデルの集合がそのクエリにおける（遅延、費用）空間のパレート前線になる。実運用では前線全体ではなく一つの動作点が要るため、FLARE は重み付き目的 α×T＋β×C（必要に応じて精度の重み ω を追加）を適格集合の上で最小化するモデルを選ぶ。選んだモデルが理想の前線にどれだけ近いかは、逆世代距離（Inverted Generational Distance; IGD）で測る。τ が精度の下限を、α と β が遅延と費用のどちらを重く見るかを決めるため、この定式化だけで利用場面ごとの方針を表せる。

### 2. オフラインのプロファイリングと特徴構築

この機構が観測するのは、全モデルへ訓練クエリを流して得た実測の四指標である。クエリ側では、all-MiniLM-L6-v2 による384次元の意味埋め込みに、プロンプト長とデータセット種別を加える。難易度は、全モデル中の正解率（cross-LLM correctness rate）として計算し、三段階に分ける。これは「多くのモデルが解けるクエリは易しい」という、モデル集合そのものを物差しにする定義である。モデル側では、パラメータ規模、公開年、大まかな知識カバレッジ、配信形態を記述子として持つ。両者を結合した特徴ベクトル ϕ(x, m) が、後段の二つの予測器への共通入力になる。保持する状態は、プロファイル済みのクエリ群とその実測値であり、これはオンライン段階で未知データセットの属性を推す近傍参照にも使われる。追加費用は、全モデル×訓練クエリの実推論という初期投資であり、プールやデータが大きく変われば再プロファイルが要る。

### 3. 精度予測器と長さ予測器 — XGBoost による二つの学習器

精度予測器は、特徴ベクトルから「そのモデルがそのクエリに正解する確率」を出す二値分類器である。予測確率が τ 以上なら正解見込みありとして扱う。長さ予測器は、同じ特徴ベクトルから出力長を回帰する。どちらも XGBoost で学習され、表形式の混合特徴に対して強いこと、埋め込みだけに頼る BERT 型の予測器より誤差が小さいことが比較で示された。実測では、長さ予測は平均絶対誤差101.2、決定係数0.6122（BERT＋MLP は誤差107.5、決定係数0.5649）、精度予測は正解率0.8609、F1 値0.8856、AUC 0.9351（BERT＋MLP は0.8511、0.8356、0.9254、単純な近傍法は大きく劣る）。減るボトルネックは、候補ごとに実推論しなければ分からなかった正解見込みと生成量を、推論なしで見積もれることである。失敗条件は予測誤差そのもので、特に長さ予測の誤差は遅延推定へ直結する。ただし頑健性の検証では、長さ信号にノイズを混ぜて決定係数を0まで落としても性能は崖状には崩れず、精度の閾値フィルタが独立に働くため方式全体は保たれることが示されている。

### 4. 長さからの遅延・費用モデルと、新規モデルのコールドスタート

遅延は、モデルごとに実測の遅延を実出力長へ最小二乗回帰した直線で推定する。傾きと切片はモデルごとに大きく異なり（傾きはトークンあたり0.6〜8.3ミリ秒相当、決定係数は0.71〜0.97）、配信ハードウェアやモデル規模の差をこの二つの数値が吸収する。予測した長さから推定した遅延の決定係数は全体で0.616であり、長さ予測の精度がそのまま遅延推定の上限を決める構造になっている。費用は、入力長と予測出力長にモデルごとの入出力単価を掛けて求める。

新規モデルへの対応は、この線形回帰の立ち上げを軽くする工夫である。新モデル投入時は、初期の少数の遅延・長さトレースから傾きと切片を暫定推定し、配信しながら回帰を更新する。精度・長さの予測器も、25リクエスト単位のバッチで増分更新する。leave-one-model-out の検証では、多くのモデルで約200リクエスト（8ステップ）後に予測器がプール内水準へ近づき、最終的な差はおおむね10パーセント以内に収まった。再学習は CPU 上の XGBoost 更新で、GPU 推論と重ねて実行できるため、立ち上げが配信の表側を止めることはない。

### 5. オンラインのルーティング — 特徴推定、精度フィルタ、三つの動作モード

到着したクエリはまず埋め込まれ、プロファイル済みクエリから k 近傍を引く。未知のデータセットでは、近傍のメタデータと正解統計を集約して、データセット種別（近傍分類の精度0.9689）と難易度（マクロ F1 0.6849）を推す。次に精度フィルタで、予測正解確率が τ 以上の候補だけを残し、小さいモデルに適格なものがあればそれを優先し、大モデルは小モデルの適格者がいない場合に限る。候補が一つも残らなければ τ を緩め、目的値が最小のモデルへ落とす。

残った候補からの最終選択は動作モードで変わる。FLARE-Acc は精度フィルタを厳しくしたうえで予測正解確率が最大のモデルを選ぶ。FLARE-Efficient は τ=0.50 の下限だけを課し、α=0.55、β=0.45 で遅延と費用の重み付き和を最小化する。FLARE-Balance は誤り確率の推定を ω=0.35 の重みで目的へ加え（α=0.40、β=0.25）、効率と精度を同時に見る。重みは検証集合で IGD を最小化するよう調整され、前線に近い動作点が得られるようになっている。誤判定時の挙動として、精度予測が外れて難しいクエリを小モデルへ送ると正解率は落ちるが、フィルタの閾値と小モデル優先の順序により、大きなモデルへの全面依存には戻らない設計である。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 精度予測器 | クエリとモデルの結合特徴 | 正解確率を推定し閾値 τ で候補を絞る | 解けないモデルへの無駄な送客 | 予測が外れると難しいクエリを落とす |
| 長さ予測器 | 同上 | 出力長を回帰で推定する | 遅延・費用の事前見積もり | 誤差が遅延推定へそのまま伝わる |
| 遅延・費用モデル | モデルごとの実測トレース | 遅延は線形回帰、費用は単価と長さの積で換算 | クエリ単位の資源見積もり | ハードウェアが変われば再回帰が要る |
| コールドスタート | 新規モデルの初期トレース | 約200リクエストで回帰と予測器を立ち上げ増分更新する | プール拡張の初期費用 | 立ち上げ直後は推定が粗い |
| 動作モード選択 | 推定した四指標 | 精度優先・効率優先・均衡の目的関数で1モデルを選ぶ | 場面ごとの精度と効率の配分 | 三つのプリセットのみで細かな調整は利用者ができない |

## 評価

結論は、クエリごとの遅延と費用を明示的に推定して目的へ入れることで、精度をほぼ保ったまま資源消費を大きく削れる、というものである。評価は分布内の5データセット（ARC-Easy、GSM8K、MBPP、MMLU、MuSR、各8対1対1に分割）と、分布外の2データセット（CommonsenseQA、MATH、テストのみ各2,000件）で行われた。モデルプールは10モデルで、大モデル段（API の DeepSeek-R1-671B、Gemma3-27B）、有力な小モデル段（Apple M4 上の Qwen2.5-7B-Instruct、Mathstral-7B、Llama3-8B、Phi-4）、低費用な小モデル段（RTX 3060 上の Qwen2.5-3B-Instruct、Llama3.2-3B、DeepSeek-R1-1.5B、Phi-4-mini）という、ハードウェア差を残した三段構成である。費用は OpenRouter や提供元の単価表から長さベースで計算した。

主要な読み方は三つある。第一に、FLARE-Acc と「精度最大の候補を選ぶ」方式の比較では、精度がほぼ同等（MMLU で0.885対0.862、GSM8K で0.960対0.950）にもかかわらず、遅延と費用が半分以下になる場面が多い（MMLU で遅延17.80秒から7.93秒、費用は約3分の1）。これは観察1の通り、正解できる候補の中に資源面で大きな分散があるためである。第二に、FLARE-Efficient の削減幅は精度の犠牲と引き換えであり、データセットによって精度が5〜20パーセント下がる。効率優先が許される場面向けの設定として読むべきである。第三に、分布外でも FLARE-Balance の IGD が最小（CommonsenseQA 0.062、MATH 0.061）で、近傍による属性推定が効いている一方、RouterBench は MATH で精度が0.490まで落ち、固定した小集合の硬さが分布のずれに弱いことが対照的に表れた。

除去実験では、パレート選択を外すと遅延と費用の配分が崩れ、精度閾値フィルタを外すと FLARE-Acc の遅延と費用が増え FLARE-Efficient の精度が大きく落ち、クエリごとの長さをモデルの平均長へ置き換えると精度は保たれるが遅延と費用が悪化した。つまり、精度の関門と、個体ごとの長さ信号の両方が必要である。感度分析では、閾値 τ には適した中間域があり（低すぎると品質管理が効かず、高すぎると候補が枯れて最低スコアへの落下が増える）、遅延と費用の重み α と β は変えても効率指標の変化が±5パーセント程度と小さい一方、精度の重み ω を大きくすると費用と遅延が急に伸びることが示された。

## 既存研究との差

先行するルーティング研究は、精度を目的に学習する予測型（Hybrid-LLM、RouteLLM、TensorOpera など）と、閾値で格上げするカスケード型（FrugalGPT など）に大別されるが、いずれもクエリごとの遅延と費用を第一級の目的として扱わない。RouterBench は費用を意識するものの、データセット単位の固定集合という粗さが残る。一方、出力長予測の系譜（S3 の長さ予測によるパッキング、応答長知覚によるスケジューリング、µ-Serve の長さ分類と電力・遅延の協調最適化）は、単一モデルの配信内部の最適化に長さを使ってきた。本論文の新しい点は、長さ予測を異種モデルプールのルーティングへ持ち込み、精度閾値で関門を作ったうえで遅延と費用の多目的最適化として振り分けを定式化したこと、そして新規モデルへのコールドスタートまで含めて運用の形にしたことである。

## 限界・実装状況

著者らが挙げる限界は四点ある。第一に、長さと遅延の推定は実行時の競合やシステム側の揺らぎなどルータの外の要因に左右され、予測精度にはまだ伸びしろがある。今後の方向として、KV キャッシュの動態や早期停止のような配信機構側の信号を取り込む案が示されている。第二に、精度は二値でモデル化されており、応答内容に基づく細かな品質は扱っていない。第三に、評価は比較的短いクエリの標準ベンチマーク中心で、実トラフィックの多様さは未検証である。第四に、動作モードは三つのプリセットに限られ、利用者が重みを直接調整して費用・性能の曲面を細かく走査することはできない。実装状況として、予測器は CPU 上で動く XGBoost で実行時負荷は小さく、新規モデルの再学習も推論と並行できる。コードの公開先は論文中に明記されていない。

## 一般的な実装上の含意

多モデル配信で費用と遅延を管理したい場合、ルータの学習目標に精度だけでなく、クエリ単位の資源見積もりを入れることが効く。その見積もりの担い手として出力長は安くて強い信号であり、モデルごとに「長さ→遅延」の直線を引くだけで、ハードウェア差を含む遅延の近似が得られる。また、精度の関門（閾値フィルタ）を資源最適化と分離しておくと、長さ予測が崩れても品質の下限は守られるという、失敗の局所化の利点がある。プールへモデルを足す運用では、約200リクエスト規模のウォームアップで予測器を立ち上げられるかどうかが、拡張の実用性を決める点も示されている。
