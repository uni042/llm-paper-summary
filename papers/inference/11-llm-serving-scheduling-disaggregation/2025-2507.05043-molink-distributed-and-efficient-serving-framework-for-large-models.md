# MoLink：家庭用GPUを狭帯域・異種環境で連結する分散LLMサービング

## 概要

MoLinkは、専用の高速相互接続を持たないGPUを複数台集め、大きな言語モデルをパイプライン並列で提供するシステムである。狙いはGPUの演算性能そのものを上げることではなく、ネットワーク待ちで各段のGPUが停止する時間を短くし、OS・GPU性能・接続形態が異なる端末を一つの推論サービスとして扱うことである。マスターがノード選択とモデル層分割を決め、ワーカーがvLLM実行エンジンと通信処理を担当する。通信遅延に合わせてマイクロバッチ数を動的に増やし、プリフィルの大きな中間活性を分割して、デコードの小さな中間活性を優先送信する。

原著v2（2025年10月16日更新）のTable 2では、RTX 4090を1枚ずつ積んだ2サーバー、Llama-2-7B、Azure Conversation由来の要求トレースで比較した。100 Mbps・往復遅延10 ms・毎秒1要求のとき、MoLinkは196.142 token/sで、Petals 45.343、vLLM 135.86を上回る。最も差の大きい条件ではPetals比でスループットが458%増える。ただし高速ネットワーク下ではvLLMとの差が小さく、全ての遅延指標で常勝するわけではない。原著の収益率は実際のサービス売上ではなく、仮定したAPI単価・GPU購入価格またはレンタル料・電力単価を使った試算である。

## 問題設定と既存方式の限界

大規模モデルを小容量のコンシューマーGPUで動かすには、モデル層を複数ノードへ割り当てるパイプライン並列が自然な選択肢となる。しかし通常のパイプライン並列は、前段が計算した隠れ状態を次段へ送ってから次の段が処理する。高速なデータセンター内相互接続を前提にしたマイクロバッチ数では、インターネットや100 Mbps Ethernetの転送待ちを隠せない。ある段のGPUが計算を終えても次のマイクロバッチが届かず、パイプラインに空白（バブル）が生じる。

もう一つの問題はプリフィルとデコードの通信競合である。長い入力のプリフィルは一度に多数トークンの中間活性を送るのに対し、デコードでは通常1ステップにつき少量を送る。単純なFIFO転送では、長いプリフィルの送信中に、短いデコード結果が同じ回線上で待たされる。原著Figure 5は、Llama-30B、100 Mbps、入力1,000トークン、バッチ4を例に、この競合でデコード転送が遅れる様子を示す。計算の並列化だけでは、ネットワークの優先制御不足は解消しない。

加えてWindowsデスクトップ、Linuxサーバー、受信ポートが制限されたコンテナ型GPUレンタル環境を同じKubernetesノードとして扱うことは難しい。MoLinkは管理面と推論面を分け、各OSに合う接続・監視・起動方式を用意する。これはモデル品質の改良ではなく、異種GPU資源の運用と実効スループットの問題である。

## 手法

### 1. マスター制御面と異種ノード統合

利用者は`DeployLLMService`でモデル名、必要GPU、推論パラメータを指定する。マスターのタスクスケジューラは、要求を満たすノードを選び、単一ノード内でテンソル並列が可能ならそれを優先する。ノードをまたぐパイプライン並列が必要なら、遅延と帯域が良い組合せを選ぶ。GPU性能が同じ場合は層を均等に分け、異なる場合は起動時の計算プロファイルに基づいて速いノードへ多くの層を割り当てる。パイプライン先頭ノードにはAPI処理と制御が集中するため、CPU能力と接続状態も選択条件に含める。

LinuxワーカーではKubernetesの制御面とKubeletを使い、GPUメトリクスはNode Exporter、DCGM、Prometheusなどで集める。WindowsワーカーではWSL2上のUbuntu 22.04に推論エンジンを置き、WSL Node ManagerとMoLink Daemonが起動・終了・メトリクス収集を受け持つ。外部コンテナ型VMは受信接続が禁止される場合があるため、DaemonがSSHトンネルのポート転送を用意する。このように管理面を分岐させつつ、推論時のデータ面は共通のgRPC転送に寄せる。

### 2. パイプラインとvLLMの接続

先頭ワーカーのAPIサーバーは要求を受け、前処理後に要求キューへ入れる。プロファイラはバッチサイズ・系列長ごとのGPU計算時間と、後続ノードへの通信時間を測る。マイクロバッチ制御器はこれらを入力として分割数と各分割のトークン量を決め、vLLMの継続バッチ処理に基づくスケジューラへ渡す。モデル層の演算結果である中間活性は通信プロセスがgRPCで送信する。

後続ワーカーは受信した中間活性をバッファへ置き、復元処理を経てバッチキューに投入する。各段で同じvLLM系の実行エンジンが担当層を処理する。重要なのは、KVキャッシュを他ノードへ毎回丸ごと複製する方式ではなく、モデル層間の活性をパイプラインに沿って送る構造である。分割の粒度を細かくすれば転送待ちを隠しやすいが、バッチ数を増やすほど実行・通信の管理費用も増えるため、無制限に細分化するわけではない。

### 3. 動的マイクロバッチ数による通信待ち隠蔽

通常の設定でマイクロバッチ数をパイプライン段数と同じにすると、ネットワーク待ちの長い段では次の活性が届くまでGPUが空く。MoLinkは起動時にGPU演算時間を計測し、実行中にネットワーク遅延・利用可能帯域を更新する。先頭の制御器が各反復でマイクロバッチ数`N`を1から増やし、増分による計算費用を残存するパイプラインの空白時間に重ねられる範囲を探す。トークン数や最大バッチサイズの制約も併用する。

原著Figure 4の例では、従来2分割で空いていた段に3番目のマイクロバッチを投入することで、先行マイクロバッチの転送をその計算と重ねる。帯域が変化すれば適切な`N`も変わるため、固定の分割数よりも狭帯域で効く。追加分割がパイプラインの空白を埋められない場合、増やすだけではスループットが伸びず、スケジューリング・転送のオーバーヘッドが残る。

### 4. プリフィル活性の分割送信とデコード優先

プリフィル結果の活性は多数の入力トークンに対応するため、単一の巨大な送信として扱うとデコードの1トークン分の活性を待たせる。MoLinkはプリフィルの活性を固定サイズのチャンクに分けて送信し、通信待ちキューをプリフィル用とデコード用に分ける。通信プロセスは新たにデコード送信が到着すれば、次の送信機会にそれを優先する。大きなプリフィル送信を小単位に区切ることで、送信中の長時間の占有を避ける。

このチャンク化はSarathiのような「プリフィルのGPU計算を分割してデコードと混ぜる」方法とは異なる。MoLinkが直接分割するのは**計算済みプリフィルの中間活性のネットワーク転送**である。したがって通信が律速である状況では効果を期待できるが、GPU演算そのものが律速の場合に同じ利得を保証するものではない。固定チャンク長の調整・キュー管理には実装上の費用があり、原著ではあらゆるネットワーク条件で最適なチャンク長を保証していない。

## 評価

### 評価環境と指標

| 項目 | 原著の条件 |
|---|---|
| 主要比較 | Petals、vLLM（Rayを用いた分散提供）、MoLink |
| モデル | Llama-2-7B（FP16）、別途Llama-2-70B-AWQ（4bit） |
| 主要GPU | 2台のサーバーに各RTX 4090 1枚。収益比較では4台のRTX 4090と単体H20/A100も使用 |
| ネットワーク | 100 Mbps、1 Gbps、10 Gbps、遅延10 msの設定 |
| 要求 | Azure Conversationトレースを基に到着率を変更。入力256トークン超、出力512トークン超は除外 |
| 指標 | スループット（生成token/s）、初回トークン時間TTFT、出力トークン当たり時間TPOT、仮定単価に基づく費用利益率 |

TTFTは待ち行列とプリフィルを含む初回出力までの時間、TPOTはその後のトークン間隔を測る。スループットの増加とTTFT/TPOTの短縮は別の目標であり、同じ設定で必ず同時に改善するとは限らない。原著Table 2はLlama-2-7Bの実験、Table 4は4bitの70Bと異なるGPU構成による経済性の比較なので、両者を単一の速度実験として扱わない。

### 主要性能：Table 2の絶対値

| 1 Gbps・10 ms／0.5 req/s | throughput token/s | 26.444 | 91.65 | 111.162 | vLLM比約21.3%増 |
| 1 Gbps・10 ms／0.5 req/s | TTFT 秒 | 0.204 | 0.177 | 0.181 | vLLMより0.004秒遅い |

原著が示す「最大458%のスループット増加」は、10 Gbps・10 ms・毎秒0.5要求でPetalsの21.332からMoLinkの119.11 token/sとなる比較（増分97.778/21.332 ≈ 458%）に対応する。**Petalsに対する最大値であり、vLLMに対して458%改善したという意味ではない**。また原著の「最大44%対vLLM」は100 Mbps・毎秒1要求の196.142対135.86と整合する。高速回線ではパイプライン通信待ちが減り、MoLink固有の分割・優先送信の利点が相対的に縮小する。

### 費用利益率：Table 3・4と前提

原著の費用利益率は`(Profit - Cost)/Cost`で、売上を生成token/sと仮定したAPI単価から計算する。ローカル購入ではGPU価格を5年で按分し、消費電力と電力単価を加える。Table 3のRTX 4090価格は12,999元、消費電力450 W、電力0.538元/kWh、Llama-2-7B API単価は100万出力トークン当たり0.25米ドルと仮定する。したがって原著の利益率は価格変動・実利用率・回線費用等に強く依存し、商用運用での利益を直接測定した数値ではない。

| Table 3：2×RTX 4090・1 req/s | Petals | vLLM | MoLink |
|---|---:|---:|---:|
| 100 Mbps・10 ms | -61.8% | 14.3% | 65.1% |
| 1 Gbps・10 ms | -60.4% | 38.0% | 75.0% |
| 10 Gbps・10 ms | -64.8% | 81.3% | 86.5% |

Table 4ではLlama-2-70B-AWQ 4bitを、H20 96GB単体（S1）、A100 80GB単体（S2）、4台のRTX 4090 24GBを使う分散構成（S3）で比較する。毎秒5要求ではS1=264.97、S2=606.48、S3=737.74 token/s、TTFTは26.457、1.469、0.53秒である。毎秒8要求ではS3の909.16 token/sが最高だが、TTFTは14.483秒に悪化する。S3の費用利益率696%という値は、原著が置いたレンタル価格・トークン価格に基づくものであり、TTFT悪化を相殺する品質保証ではない。

### 負の結果と未評価の範囲

原著Table 2では1 Gbps・0.5 req/sのTTFTとTPOTがvLLMよりわずかに悪い。10 Gbps・1 req/sのスループット差は約2.9%であり、狭帯域の最大倍率を高速ネットワークへ一般化できない。Table 4では高負荷で分散4090構成のTTFTが14秒以上に増える。特に原著の主要比較はLlama-2系と限定されたトレース・帯域・到着率であり、MoE、長文脈、多様なGPU間の障害回復、WANでのパケット損失、異なる同時接続分布を網羅する保証はない。

原著のTable 2とTable 3は10 Gbps・0.5 req/sのMoLinkスループットについて119.11と105.687という異なる値を掲載している。後者は経済性計算表の値であり、ここでは勝手に訂正せず、比較表ごとの数値として区別する。性能の結論はTable 2、費用の結論はTable 3の記載に限定した。著者の収益試算の外部妥当性や実運用価格は原著の直接実測ではない。

## 既存研究との差と実務上の位置付け

Petalsはインターネット上の異種GPUによる分散推論を扱うが、MoLinkはvLLMの継続バッチ処理と通信待ちに応じた分割数調整を統合する。一般的なvLLM分散提供との違いは、弱い回線とWindows/コンテナ環境を運用上の前提に置き、通信の分割・優先制御とGPU層配置を一体化する点である。DistServe/Splitwiseはプリフィルとデコードを別GPU群に分ける構成、Sarathiはプリフィル計算のチャンク化を主眼とするため、MoLinkの「パイプライン層間のプリフィル活性送信を分割する」機構と区別する必要がある。

Windows対応といってもWindowsネイティブのvLLM実行ではなく、**WSL2 Ubuntu 22.04内でLinux向け推論エンジンを起動**する方式である。複数の家庭用GPUを持つ環境には運用上参考になるが、単一GPUでのCPUオフロードや1台のRTX 4070 Superに対する直接的な高速化の根拠ではない。GPU台数、ネットワーク帯域、モデル層配置、利用者要求分布が変われば利得も変わる。
