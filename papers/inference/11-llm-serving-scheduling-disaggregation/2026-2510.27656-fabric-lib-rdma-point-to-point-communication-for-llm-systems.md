# fabric-lib: RDMA Point-to-Point Communication for LLM Systems

> ConnectX-7とAWS EFAを共通の順序非依存RDMA点対点APIで扱い、KV転送・MoE配送・重み更新を複数NICへ透過分散してLLM基盤のNIC依存を減らす。

## 概要

大規模LLM基盤では、通信が従来のテンソル並列のような固定集合通信だけでは済まなくなっている。プリフィルとデコードを別ノードへ置く分離推論ではKVキャッシュを任意のデコードノードへ送る必要があり、混合専門家モデル（Mixture of Experts; MoE）ではトークンを選択された専門家へ低遅延で配送する。さらに非同期強化学習では学習クラスタから推論クラスタへ巨大な重みを更新する。これらは相手や転送量が動的で、点対点通信の柔軟性が重要になる。

fabric-libは、NVIDIA ConnectX-7とAWS Elastic Fabric Adapter（EFA）の異なるRDMA機構を、共通の片方向書込みと完了通知へ抽象化する。ネットワークが書込み順序を保証することを前提にせず、即値付き書込みと受信側カウンタで完了を検出する。GPUに複数NICが付く構成では自動的に転送を分割する。単純なマイクロベンチマークだけでなく、KV転送、1兆パラメータ級の重み更新、MoE配送の3用途で検証し、ConnectX-7とEFAの双方で400Gbps級の帯域を示した。

## 問題設定

NCCLなどの集合通信は、参加GPU集合と通信パターンが比較的固定されたテンソル並列やデータ並列に強い。一方、分離推論では要求ごとにプリフィル側とデコード側の組合せが変わり、MoEでは各トークンのルーティング結果で送信先が変わる。固定グループの初期化や一様なバッファを前提にすると、弾力的なLLMサービングへ組み込みにくい。

さらに、NICのプログラミングモデルがベンダーごとに異なる。ConnectX向けのGPU主導通信を前提にした実装はEFAへそのまま移せず、逆も同様である。fabric-libは、性能を大きく落とさずにこのハードウェア差を隠し、LLMランタイムが「どのNICか」ではなく「どのGPUメモリ領域を相手へ送るか」を指定できる層を狙う。

## 手法のあらまし

各GPUには転送エンジンを対応させ、CPU側の専用スレッドをNUMA近傍のコアへ固定する。エンジン内部では、GPUに接続された複数NICをドメイングループとして束ね、個別NICのキューや完了処理はドメインが担当する。大きな連続領域だけでなく、ページ化KVのような非連続領域をまとめて送れる。

主要な片方向操作は、遠隔メモリへ書いた後に即値を通知するWriteImmである。EFAとConnectXの一部動作ではパケットや完了順序を暗黙に仮定できないため、受信側はImmCounterを増やし、必要数の到着で転送完了を判断する。これにより、順序保証の差を上位LLMランタイムへ漏らさない。

GPU計算と通信を重ねる用途では、統合仮想メモリ（Unified Virtual Memory; UVM）上の完了位置をCPUスレッドがGDRCopyで監視する。プリフィルがあるTransformer層のKVを作り終えた時点で、その層だけをすぐデコードノードへ送り始められるため、全層のプリフィル完了を待つ必要がない。

## 手法

### 1. TransferEngineと複数NIC集約

転送エンジンはGPU単位で動作し、登録済みGPU/ホストメモリを遠隔側へ公開する。GPUに複数の100Gbps級NICが接続される場合、ドメイングループが書込みをNICへ分割し、上位層からは単一の広帯域経路として見せる。

この設計の効果は、LLMランタイム側がNIC数や種類に合わせてKVページを手動分割しなくてよいことにある。一方でCPUプロキシスレッドを使うため、CPU配置やNUMA局所性が悪いと低遅延通信の利得を失う。著者らはスレッド固定とロックなしキューでこの費用を抑える。

### 2. 順序非依存のWriteImmとImmCounter

大量データは片方向WRITEで遠隔GPUメモリへ直接送る。送信側は完了を示す即値も発行し、受信側のImmCounterがその到着数を数える。重要なのは「最後に送った通知が最後に届く」ことを仮定しない点である。

これにより、NICごとの順序特性を抽象化しつつ、上位側はカウンタが所定値へ達した時点で対象バッファを安全に使える。ページ化KVでは複数ページを複数NICへ並列配送できるため、分離推論の転送単位と合う。

### 3. UVM Watcherによる計算・通信重畳

プリフィル計算が全層終了してからKVを一括送ると、ネットワーク時間が初回トークン時間（Time To First Token; TTFT）へそのまま加算される。fabric-libはGPUカーネルが更新するUVM位置をCPUから監視し、層のKVが準備できた瞬間にネットワーク転送を開始する。

128K系列の評価では層ごとのKV転送が約1.6msで、プリフィル計算と重ねることで通信をクリティカルパスから外す。Qwen3-235Bの例では分離構成のTTFTが17,056ms、標準構成が16,735msで、分離に必要なネットワーク追加費用を小さく抑えた。

### 4. MoE配送と重み更新への再利用

MoEでは専門家並列のdispatch/combineを同じ点対点プリミティブで実装する。EFAでは従来のConnectX専用GPU主導方式が使えないためCPUプロキシが重要になる。DeepSeek-V3の評価で、EFA上のデコード処理量は既存実装より3〜6倍となり、ConnectX-7でもDeepEPと同等以上の条件がある。

非同期学習の重み更新では、ホスト→GPUコピー、重みのunshard/量子化、RDMA転送をパイプライン化する。Kimi-K2-1T相当の重みを256学習GPUから128推論GPUへ送る例で総時間1.233秒、RDMAがクリティカルパスへ残す部分は42msと報告される。これは推論専用機構ではないが、同じ通信抽象が異なるLLMシステム段階で再利用できる証拠になっている。

## 既存研究との差

DeepEPのようなMoE専用通信は非常に高速だが、GPU主導RDMAなど特定NIC機能への依存が強い。fabric-libは最高性能の単一用途カーネルではなく、ConnectXとEFAを同じ上位APIで扱い、KV転送・MoE・重み更新へ共通利用できる点を主眼に置く。

またNCCLの集合通信を置き換えるのではなく、固定集合通信では表現しにくい動的点対点通信を補完する。したがってテンソル並列のall-reduceまでfabric-libへ移す設計ではない。

## 限界・実装状況

低遅延を維持するにはCPUプロキシのコア固定、NUMA配置、メモリ登録が重要で、CPU資源が逼迫する環境では結果が変わり得る。400Gbps飽和には連続WRITEで16MiB級、ページWRITEで32〜64KiB級のメッセージが必要とされ、小さい転送では帯域を使い切れない。

評価はConnectX-7とEFAを中心としており、すべてのRDMA NICで同等の性能を保証するものではない。分離推論のTTFT差も128K等の特定構成での値で、ネットワーク混雑を含む任意のクラスタへ一般化する際は再測定が必要である。

## 一般的な実装上の含意

LLM通信では「最高帯域」だけでなく、動的相手選択、非連続ページ、複数NIC、順序保証の違いを上位ランタイムから隠せるかが重要になる。また、KV転送は一括コピーより層単位の生成完了へ連動させ、計算と通信を重ねる方がTTFTへの影響を小さくできる。
