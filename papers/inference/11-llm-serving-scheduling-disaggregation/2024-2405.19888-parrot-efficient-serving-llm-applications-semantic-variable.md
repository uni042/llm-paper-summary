# Parrot: Efficient Serving of LLM-based Applications with Semantic Variable

> 複数LLM callから成るapplicationのprompt構造・依存関係・共有prefixをSemantic Variableでbackendへ伝え、request DAG全体を見ながら並列化・batching・prefix reuse・schedulingを共同最適化するapplication-aware serving system。

## 概要

従来のLLM serving APIでは各requestが独立した`prompt -> output`としてbackendへ届く。そのため、実際には同じapplicationの中で前後関係があるrequestや、同じ長いsystem promptを共有するrequestでも、serving側にはその関係が見えない。

Parrotはrequest内のinput / output部分を**Semantic Variable**として明示し、それらを複数request間で接続する。これによりbackendはapplication全体をdataflow graphとして把握でき、単一requestだけを最適化するのではなく、**application end-to-end latency / throughputを目標にrequest群をまとめて最適化する**。

## 手法

### 1. Semantic Variable

prompt中のinput / output variableへ意味付きの識別子を付ける。あるrequestのoutput Semantic Variableを別requestのinputへ接続すると、backendはその依存関係を直接知ることができる。

これにより、clientが一つずつ結果を受け取って次requestを発行しなくても、backend側でdependent requestを準備・実行できる。

### 2. Application DAGの復元

Semantic Variableの接続からrequest dependency DAGを作り、どのrequestが並列実行可能か、どのrequestがcritical path上にあるかを判断する。

例えばmap-reduce型applicationでは、複数map requestはthroughput重視で大きくbatchし、最後のreduce requestはend-to-end latencyを縮めるため早く処理する、といった**requestごとのperformance objective推定**が可能になる。

### 3. Shared-prefix detectionとcontext-aware scheduling

複数requestが共通prompt prefixを持つ場合、そのprefixを別々にprefillせず共有する。Parrotはprompt構造とSemantic Variableを使うため、固定system promptだけでなくapplication実行中に生成されたcontextの共通部分も見つけられる。

schedulerは共有contextをすでに持つengineへrequestを寄せ、prefix KVを再利用する。さらに共通prefixを持つrequest向けにattention処理も最適化する。

### 4. ServeCoreと複数Engine

中央のServeCoreがapplication-level DAGとrequest schedulingを管理し、複数のLLM Engineへrequestを割り当てる。各Engineは独立したmodel serving backendとして動作し、Parrotの上位schedulerからcontext-awareなFill / Gen requestを受け取る。

## 評価

OSDI 2024ではdocument processing、共有system promptを持つapplication、multi-agent programmingなど複数の実用的workflowを評価している。

主要結果として、既存のrequest-level serving方式に対し

- application end-to-end speedup: **最大11.7×**
- request throughput: **最大12×**

を報告する。

特に改善が大きいのは、複数request間で大量のprompt / contextを共有するapplicationや、DAG内で並列実行できるrequestが多いケースである。

## 既存研究との差

### vLLM / PagedAttentionとの違い

vLLMは一つのrequest内部および明示的に共有できるKV blockを効率よく管理するが、application内の複数LLM callがどう関係しているかは基本的に知らない。

Parrotは**requestの上にあるapplication dataflowをserving systemへ見せる**ことで、request dependencyとshared prefixを同時に利用する。

### QLMとの違い

QLMはmulti-model queueでrequestのSLOとwaiting timeを見て実行順序を最適化する。ParrotはrequestのSLOだけでなく、**そのrequestがapplication DAGのどこにあり、他requestとどのprompt / dataを共有するか**まで扱う。

### Pensieve / CachedAttentionとの違い

Pensieve / CachedAttentionはmulti-turn conversationの過去KVをturn間で保存するstateful servingである。Parrotはconversationに限定せず、任意のmulti-request applicationやmulti-agent workflowのdata dependencyとshared contextを対象にする。

## 限界

- application側がSemantic Variableを使ってprompt構造とdata dependencyを明示する必要があり、完全にtransparentなbackend最適化ではない。
- 改善幅はrequest間の依存関係・並列性・shared prefix量に強く依存する。
- application DAGを中央ServeCoreで管理するため、大規模multi-tenant環境ではcontrol-plane scalabilityが課題になる。
- custom API / programming modelを導入するため、既存OpenAI互換APIだけを使うapplicationには変更が必要。
- production model servingの全機能を網羅したruntimeではなく、公開実装はresearch prototypeである。

## 一般的な実装上の含意

LLM applicationが複数callで構成される場合、request-level schedulerだけでは**本来並列に実行できるcall、critical path、shared prefix**を見落とす。

そのため、serving APIに少量のapplication-level metadataを加えるだけでも、backendがdataflow analysisを行い、batching・placement・KV reuseを別々ではなく共同で最適化できる。agent workflowが増えるほど重要になる設計点である。
