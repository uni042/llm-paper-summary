# Parrot: Efficient Serving of LLM-based Applications with Semantic Variable

> 複数LLM呼び出しから成るアプリケーションについて、どの呼び出しの出力を次の呼び出しが使うか、どのプロンプト部分を共有するかをバックエンドへ伝え、アプリケーション全体を見て並列実行・バッチ処理・接頭部 KV再利用を調整する推論提供システム。

## 概要

従来のLLM推論提供APIでは各要求が独立した`プロンプト -> 出力`としてバックエンドへ届く。そのため、実際には同じアプリケーションの中で前後関係がある要求や、同じ長いシステムプロンプトを共有する要求でも、推論提供側にはその関係が見えない。

Parrotはプロンプト中の「ここは別呼び出しから受け取った値」「この出力は後続呼び出しで使う」といった部分へ識別子を付け、複数要求間のつながりをバックエンドへ伝える。この識別子を論文では **意味変数** と呼ぶ。

これによりバックエンドは、単一要求ではなく**アプリケーション全体の処理順・並列に実行できる呼び出し・共有できるプロンプト部分**を把握できる。結果として、要求ごとに個別最適化するのではなく、アプリケーションエンドツーエンド遅延 / スループットを目標に要求群をまとめて最適化する。

## 手法

### 1. プロンプトの入出力部分に「どの値か」を示す名前を付ける

プロンプト中の入力 / 出力変数へ意味付きの識別子を付ける。ある要求の出力を別要求の入力へ接続すると、バックエンドはその依存関係を直接知ることができる。

例えば、

`呼び出しAの出力 → 呼び出しBとCの入力`

という関係が分かれば、A終了後にB/Cを並列実行できる。クライアントがAの結果を受け取ってからB/Cを1件ずつ発行する必要がない。

### 2. 複数の呼び出しの依存関係を有向グラフとして復元する

意味変数の接続から、どの要求がどの要求を待つかを表す依存グラフを作る。

論文の **DAG（Directed Acyclic Graph）** は、処理の依存関係を「Aが終わったらB/Cへ進む」のような矢印で表したものを指す。

このグラフを見ることで、

- 今すぐ並列に走らせられる要求
- アプリケーション完了時間を左右する重要な要求
- スループット重視でバッチを大きくしてよい要求

を区別できる。

例えばマップ・リデュース型アプリケーションでは、複数対応付け要求は大きくバッチして効率を上げ、最後の削減要求はアプリケーション完了を遅らせないよう優先する、といった判断ができる。

### 3. 要求間で同じプロンプト接頭部を再利用する

複数要求が共通プロンプト接頭部を持つ場合、その接頭部を別々にプリフィルせずKVを共有する。

Parrotはプロンプト構造と意味変数を知っているため、固定システムプロンプトだけでなく、**アプリケーション実行中に前段呼び出しから生成された同じ文脈を複数後続呼び出しが共有する場合**も見つけられる。

スケジューラはその共有KVをすでに持つエンジンへ要求を寄せ、再プリフィルを減らす。

ただし共有KVを持つエンジンへ常に寄せれば、そのエンジンだけ待ち行列が伸びる可能性がある。そのため共有接頭部の再利用価値は、アプリケーション依存関係や実行単位の混雑と一緒に判断する必要がある。Parrotの利点はキャッシュ機構単体ではなく、データフロー情報を同じ制御器が持つことで『再計算を省く配置』と『アプリケーションを早く進める配置』を同じ判断に含められる点にある。

### 4. 中央制御器がアプリケーション全体を見て複数LLMエンジンへ振り分ける

中央のServeCoreがアプリケーション単位の依存グラフと要求スケジューリングを管理し、複数のLLMエンジンへ要求を割り当てる。

各エンジンは通常のモデル推論提供バックエンドとして動作するが、ServeCoreから

- どの要求を先に処理するか
- どの文脈を再利用できるか
- どの要求を同じエンジンへ寄せるか

という情報を受け取る。

この情報があると、個々の要求だけを見た最短処理順と、アプリケーション全体の最短完了順が異なる場合を扱える。例えば後続の多数要求を解放する前段要求は、その要求単体の生成長が多少長くても早く完了させる価値が高い。一方、互いに独立な枝は同時に実行できる。Parrotは依存グラフからこの違いを把握し、重要な依存経路を詰まらせないことと、独立枝をまとめて高効率に実行することを両立させる。

## 評価

OSDI 2024では文書処理、共有システムプロンプトを持つアプリケーション、複数エージェントプログラミングなど複数の実用的処理手順を評価している。

主要結果として、既存の要求単位推論提供方式に対し

- アプリケーションエンドツーエンド高速化倍率: **最大11.7×**
- 要求スループット: **最大12×**

を報告する。

特に改善が大きいのは、複数要求間で大量のプロンプト / 文脈を共有するアプリケーションや、依存グラフ内で並列実行できる要求が多いケースである。

## 既存研究との差

### vLLM / PagedAttentionとの違い

vLLMはKVキャッシュを効率よく配置・共有する仕組みを提供するが、アプリケーション内の複数LLM呼び出しがどう関係しているかは基本的に知らない。

Parrotは**要求の上にあるアプリケーションデータフローを推論提供システムへ見せる**ことで、要求依存関係と共有接頭部を同時に利用する。

### QLMとの違い

QLMは複数モデル待ち行列で要求のSLOと待機時間を見て実行順序を最適化する。Parrotは要求のSLOだけでなく、**その要求がアプリケーションのどこにあり、他要求とどのプロンプト / データを共有するか**まで扱う。

### Pensieve / CachedAttentionとの違い

Pensieve / CachedAttentionは複数ターン会話の過去KVをターン間で保存する状態保持型推論提供である。Parrotは会話に限定せず、任意の複数要求アプリケーションや複数エージェント処理手順のデータ依存関係と共有文脈を対象にする。

## 限界

- アプリケーション側が意味変数を使ってプロンプト構造とデータ依存関係を明示する必要があり、完全に透過的なバックエンド最適化ではない。
- 改善幅は要求間の依存関係・並列性・共有接頭部量に強く依存する。
- アプリケーショングラフを中央ServeCoreで管理するため、大規模複数利用者環境では制御装置自体の拡張性が課題になる。
- 独自API / プログラミングモデルを導入するため、既存OpenAI互換APIだけを使うアプリケーションには変更が必要。
- 本番モデル推論提供の全機能を網羅した実行環境ではなく、公開実装は研究試作である。

## 一般的な実装上の含意

LLMアプリケーションが複数呼び出しで構成される場合、要求単位スケジューラだけでは**本来並列に実行できる呼び出し、アプリケーション完了時間を左右する呼び出し、共有接頭部**を見落とす。

そのため、推論提供APIに少量のアプリケーション単位メタデータを加えるだけでも、バックエンドが依存関係を見てバッチ処理・配置・KV再利用を共同で最適化できる。エージェント処理手順が増えるほど重要になる設計点である。
