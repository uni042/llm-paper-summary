# Parrot: Efficient Serving of LLM-based Applications with Semantic Variable

> 複数LLM callから成るapplicationについて、どのcallの出力を次のcallが使うか、どのprompt部分を共有するかをbackendへ伝え、application全体を見て並列実行・batching・prefix KV再利用を調整するserving system。

## 概要

従来のLLM serving APIでは各requestが独立した`prompt -> output`としてbackendへ届く。そのため、実際には同じapplicationの中で前後関係があるrequestや、同じ長いsystem promptを共有するrequestでも、serving側にはその関係が見えない。

Parrotはprompt中の「ここは別callから受け取った値」「この出力は後続callで使う」といった部分へ識別子を付け、複数request間のつながりをbackendへ伝える。この識別子を論文では **Semantic Variable** と呼ぶ。

これによりbackendは、単一requestではなく**application全体の処理順・並列に実行できるcall・共有できるprompt部分**を把握できる。結果として、requestごとに個別最適化するのではなく、application end-to-end latency / throughputを目標にrequest群をまとめて最適化する。

## 手法

### 1. Promptの入出力部分に「どの値か」を示す名前を付ける

prompt中のinput / output variableへ意味付きの識別子を付ける。あるrequestのoutputを別requestのinputへ接続すると、backendはその依存関係を直接知ることができる。

例えば、

`call Aの出力 → call BとCの入力`

という関係が分かれば、A終了後にB/Cを並列実行できる。clientがAの結果を受け取ってからB/Cを1件ずつ発行する必要がない。

### 2. 複数callの依存関係を有向グラフとして復元する

Semantic Variableの接続から、どのrequestがどのrequestを待つかを表す依存graphを作る。

論文の **DAG（Directed Acyclic Graph）** は、処理の依存関係を「Aが終わったらB/Cへ進む」のような矢印で表したものを指す。

このgraphを見ることで、

- 今すぐ並列に走らせられるrequest
- application完了時間を左右する重要なrequest
- throughput重視でbatchを大きくしてよいrequest

を区別できる。

例えばmap-reduce型applicationでは、複数map requestは大きくbatchして効率を上げ、最後のreduce requestはapplication completionを遅らせないよう優先する、といった判断ができる。

### 3. Request間で同じprompt prefixを再利用する

複数requestが共通prompt prefixを持つ場合、そのprefixを別々にprefillせずKVを共有する。

Parrotはprompt構造とSemantic Variableを知っているため、固定system promptだけでなく、**application実行中に前段callから生成された同じcontextを複数後続callが共有する場合**も見つけられる。

schedulerはその共有KVをすでに持つengineへrequestを寄せ、再prefillを減らす。

### 4. 中央controllerがapplication全体を見て複数LLM engineへ振り分ける

中央のServeCoreがapplication-levelの依存graphとrequest schedulingを管理し、複数のLLM Engineへrequestを割り当てる。

各Engineは通常のmodel serving backendとして動作するが、ServeCoreから

- どのrequestを先に処理するか
- どのcontextを再利用できるか
- どのrequestを同じengineへ寄せるか

という情報を受け取る。

## 評価

OSDI 2024ではdocument processing、共有system promptを持つapplication、multi-agent programmingなど複数の実用的workflowを評価している。

主要結果として、既存のrequest-level serving方式に対し

- application end-to-end speedup: **最大11.7×**
- request throughput: **最大12×**

を報告する。

特に改善が大きいのは、複数request間で大量のprompt / contextを共有するapplicationや、依存graph内で並列実行できるrequestが多いケースである。

## 既存研究との差

### vLLM / PagedAttentionとの違い

vLLMはKV cacheを効率よく配置・共有する仕組みを提供するが、application内の複数LLM callがどう関係しているかは基本的に知らない。

Parrotは**requestの上にあるapplication dataflowをserving systemへ見せる**ことで、request dependencyとshared prefixを同時に利用する。

### QLMとの違い

QLMはmulti-model queueでrequestのSLOとwaiting timeを見て実行順序を最適化する。ParrotはrequestのSLOだけでなく、**そのrequestがapplicationのどこにあり、他requestとどのprompt / dataを共有するか**まで扱う。

### Pensieve / CachedAttentionとの違い

Pensieve / CachedAttentionはmulti-turn conversationの過去KVをturn間で保存するstateful servingである。Parrotはconversationに限定せず、任意のmulti-request applicationやmulti-agent workflowのdata dependencyとshared contextを対象にする。

## 限界

- application側がSemantic Variableを使ってprompt構造とdata dependencyを明示する必要があり、完全にtransparentなbackend最適化ではない。
- 改善幅はrequest間の依存関係・並列性・shared prefix量に強く依存する。
- application graphを中央ServeCoreで管理するため、大規模multi-tenant環境ではcontroller自体のscalabilityが課題になる。
- custom API / programming modelを導入するため、既存OpenAI互換APIだけを使うapplicationには変更が必要。
- production model servingの全機能を網羅したruntimeではなく、公開実装はresearch prototypeである。

## 一般的な実装上の含意

LLM applicationが複数callで構成される場合、request-level schedulerだけでは**本来並列に実行できるcall、application完了時間を左右するcall、shared prefix**を見落とす。

そのため、serving APIに少量のapplication-level metadataを加えるだけでも、backendが依存関係を見てbatching・placement・KV reuseを共同で最適化できる。agent workflowが増えるほど重要になる設計点である。
