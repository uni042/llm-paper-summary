# Parrot: Efficient Serving of LLM-based Applications with Semantic Variable

> 複数の言語モデル呼出しから成るアプリケーションの入力・出力の関係を、意味変数という抽象化で推論提供側へ公開する。これにより要求間の依存関係、同一接頭部の再利用、アプリケーション全体の完了時間を考慮した要求配置を可能にする。単一要求の速度ではなく、複数要求を組み合わせた作業の完了時間を最適化する研究である。

## 概要

Parrotは、複数の大規模言語モデル呼出しを組み合わせるアプリケーションのための推論提供システムである。従来の一般的な補完APIでは、一つの要求が完成したプロンプトとして送られ、推論サーバーはその要求がどのアプリケーションに属し、どの先行要求の出力を使い、どの後続要求へ結果を渡すかを知らない。サーバーは個々の要求の待ち時間や処理率を最適化できても、複数要求から成る処理全体の完了時間を直接最適化しにくい。

Parrotは、プロンプトの中に意味変数（Semantic Variable）を残したまま要求を登録する。意味変数はプロンプトの入力部分または出力部分を表し、ある要求の出力変数を別要求の入力変数へ接続することで、複数要求のデータフローを推論提供側が把握できる。これにより、クライアントへ一度結果を返して次の要求を発行し直す通信を減らし、依存関係を守りながら並列化し、共通のプロンプト接頭部の計算結果を再利用する。

OSDI 2024正式論文は、文書の連鎖要約、マップ・リデュース要約、共有プロンプトを使う多数利用者、複数エージェントのプログラミングなどを評価する。例えば一つの長文を分割して順次要約する処理では、基準のvLLMを用いた提供方式に対して完了時間が最大1.38倍短縮され、HuggingFace実装との比較では最大1.88倍となる条件を報告する。多数の要求が混在する条件ではさらに改善が大きくなる。個別の最大改善倍率をすべてのアプリケーションへ一般化してはならない。

## 問題設定

### 要求ごとに独立したAPIでは見えない情報

複数の文章断片を要約して最後にまとめるアプリケーションでは、断片ごとの要約は並列に実行できるが、最後の統合要約は前段のすべての結果を待つ必要がある。プログラム生成エージェントでは、設計書を作った後に複数のファイルを並列生成し、生成したコードを受け取って試験コードを作るなど、さらに複雑な依存関係が生じる。従来の要求単位のAPIでは、こうした構造がクライアントの制御コード内に閉じており、推論提供側には個々の文字列要求しか届かない。

論文の図3は、複数段の呼出しをクライアントと推論サーバーの間で往復させると、ネットワーク往復と待ち行列への再投入が繰り返されることを示す。実運用で観測した連鎖型の要求では、モデル外部の費用が平均で30〜50%、悪い条件では70%超に達する。先行要求の結果をサーバー内で後続要求へ直接渡せれば、クライアントとの不要な往復を減らせる。これはモデルの行列演算を高速化する施策とは異なる。

### 要求単位の目標と作業全体の目標の違い

一つの要求の遅延を最小化することと、アプリケーション全体を最短で終わらせることは同じではない。多数の独立した断片を要約する段階では、大きなバッチを使って処理率を上げる方が作業全体を早く進められる。一方、最後の統合要約では、その一件が終わるまでアプリケーションが完了しないので、個別要求の遅延を優先した方がよい。論文の図4では、この切替によってマップ・リデュース要約の全体完了時間を2.4倍改善する例が示される。

要求をすべて同じ遅延目標で扱うと、前段の多数要求に対して小さなバッチを選び、GPUの処理率を下げる可能性がある。逆にすべてを処理率重視にすると、最後の一件が大きなバッチの待ち行列へ入り、完了が遅れる。Parrotはアプリケーションの依存関係と完了目標を知ることで、段階に応じて適切な方針を変える。

### 共通プロンプトを繰り返す無駄

同じアプリケーションを多数の利用者が使う場合、役割指示や例示などの長い接頭部が共通する。複数エージェントの作業でも、過去の会話や共有した指示が各要求へ繰り返し埋め込まれる。論文表1では、文書分析は一作業あたり2〜40回の要求、チャット検索は2〜10回、MetaGPTは14回、AutoGenは17回という例を示す。繰返し段落の割合は文書分析3%、チャット検索94%、MetaGPT72%、AutoGen99%と大きく異なる。

共通接頭部の鍵値キャッシュを再利用するには、同じ内容を持つ要求を、対応するキャッシュが存在するエンジンへ割り当てる必要がある。要求単位で文字列を完全に展開してから送ると、共通構造の検出に追加の比較費用がかかる。Parrotはプロンプトの固定部分と意味変数の関係を事前に知るため、どの接頭部が共有され得るかを推論提供側が早期に把握できる。

## 手法

### 1. 意味関数と意味変数

Parrotでは、言語モデルへ与えるプロンプトのひな型を意味関数（Semantic Function）として扱う。ひな型の入力欄と出力欄は意味変数として残される。例えば「課題からプログラムを書く」関数の出力であるコードを、「課題とコードから試験を書く」関数の入力へ接続する。推論提供側には、完成した文字列だけでなく、どの変数がどの要求によって生成され、どの要求で消費されるかが伝わる。

通常のひな型処理では、クライアント側で変数を文字列へ置換してから要求を送るため、推論提供側には変数の同一性が見えない。Parrotはこの置換をできるだけ遅らせ、変数を独立した構造として保持する。意味変数は、値をまだ生成していない段階でも後続要求へ接続できるため、先行要求の完了を待たずに処理手順全体を登録できる。

意味関数は必ずしも一つの巨大な処理ではない。短い指示、固定例、先行出力、ユーザー入力などを組み合わせて一つのプロンプトを作る。意味変数は、その中でどの部分が共有可能で、どの部分がまだ未確定かを示す。これが要求間の依存分析と接頭部再利用の共通の基盤になる。

### 2. 要求間のデータフロー分析

Parrot Managerは意味変数の生成者と消費者を調べ、要求間の依存関係を有向非巡回グラフとして復元する。先行要求の出力が二つの後続要求に使われる場合、先行要求の完了後には後続の二件を並列に実行できる。後続要求が別の先行要求も必要とする場合は、必要な入力が揃うまで待つ。依存グラフを知ることで、要求を単純な到着順で処理するより、アプリケーションの進行を意識した実行順を選べる。

分析の結果は、ある意味変数の生成者を返す操作、消費者を返す操作、接頭部の共有を検出する操作、性能目標を得る操作などに利用される。論文の図8はこれらの情報を扱う内部操作の例を示す。データフロー分析はモデル内部の注意重みを解析するものではなく、アプリケーションが定義したプロンプト変数の接続を解析する。

### 3. 要求をまたぐ通信の削減

従来は先行要求の出力をクライアントが受け取り、次の要求のプロンプトへ埋め込み、再びサーバーへ送る。この往復は、後続要求が先行出力をそのまま使う場合でも必要だった。Parrotは意味変数の接続を保持し、先行要求が生成した値を推論提供側で後続要求の入力へ渡す。クライアントとサーバー間の余分な通信を減らし、後続要求を新しい独立要求として待ち行列へ入れ直す費用も削減できる。

この機構は、すべての要求を同じGPUで処理しなければならないという意味ではない。要求の依存関係と実行場所を管理する中央制御器が、必要な変数を適切なエンジンへ渡す。依存する要求を同じ場所へ配置すれば通信を減らせる一方、その場所が混雑すれば待ち時間が増えるため、配置と混雑の両方を考慮する必要がある。

### 4. 接頭部の共有と文脈の再利用

同じ固定指示や例示を含む複数要求は、先頭部分のトークン列を共有する。Parrotは意味関数の固定部分を識別できるため、同じ接頭部を何度も計算せず、鍵値キャッシュを持つエンジンへ後続要求を割り当てられる。複数エージェントで共通の会話履歴を使う場合も、履歴が同じ意味変数から生成されたことを利用して共有を見つける。

ただし、キャッシュの再利用価値だけで配置を決めると、同じエンジンへ要求が集中して待ち行列が長くなる可能性がある。Parrotは接頭部の再利用とアプリケーション全体の完了時間を同時に考え、必要なら別のエンジンで再計算する選択肢も残す。重要なのは、キャッシュの存在と要求の依存関係を同じ制御器が知っていることである。

### 5. アプリケーションの性能目標を反映した実行順

複数要求のアプリケーションでは、独立して処理できる段階と、最後の一件が作業完了を決める段階がある。Parrotは、各意味変数をどの要求が消費するかを追跡することで、処理手順全体の進行にとって重要な要求を把握する。多数の独立した前段要求では大きなバッチを使い、最後の統合要求では個別遅延を優先するなど、処理段階に応じて方針を変える。

この判断は、単に短い要求を優先するものでも、常に先に来た要求を優先するものでもない。例えば前段の一件が終わらなければ多数の後続要求を開始できない場合、その一件を早く完了させる価値は高い。反対に互いに独立した枝では、まとめて高い処理率で実行しても依存関係を壊さない。データフローを持つことが、要求単位の待ち時間とアプリケーション単位の完了時間の違いを扱う基盤になる。

### 6. 推論エンジンとの接続

Parrotの推論エンジンは、入力トークンを処理して文脈の鍵値キャッシュを構築する操作、既存文脈から出力を生成する操作、不要になった文脈を解放する操作を分けて提供する。正式論文の第7節は、文脈識別子と親文脈識別子を用いて文脈の生成や分岐を管理することを説明する。入力部分と生成部分を別の操作に分けることで、意味変数の固定部分と動的な出力部分を効率よく扱える。

生成は終了文字、最大長、終端トークンなどの条件で止まり、複数要求は反復ごとの継続的なバッチ処理で実行される。入力部分を一度処理した後に複数の生成を分岐させる場合、親文脈を共有することで接頭部の再計算を避けられる。文脈の寿命を中央制御器が把握できれば、不要になった鍵値キャッシュを解放し、次の要求へメモリを渡せる。

## 評価

### 実験環境と比較対象

正式論文の単一GPU実験は24コアのAMD EPYC 7V13と80GBのA100を用い、複数GPU実験は64コアのAMD EPYCと48GBのA6000を四基用いる。いずれもCUDA 12.1とcuDNN 8.9.2で動作させる。各推論エンジンではLLaMA 7Bまたは13Bを使用する。基準方式は、LangChain等のアプリケーションから通常の補完APIを呼び出し、FastChatを通してHuggingFaceまたはvLLMの推論エンジンへ送る構成である。

| 項目 | 実験条件 |
|---|---|
| 単一GPU | A100 80GB、AMD EPYC 7V13 24コア |
| 複数GPU | A6000 48GBを四基、AMD EPYC 64コア |
| 実行環境 | CUDA 12.1、cuDNN 8.9.2 |
| 言語モデル | LLaMA 7B、LLaMA 13B |
| 文書分析 | 学術論文の長文を連鎖要約またはマップ・リデュース要約 |
| 共有プロンプト | 複数利用者の共通指示・例示を含む要求 |
| 複数エージェント | 設計、プログラム生成、レビュー、修正を伴う処理手順 |
| 混合負荷 | 複数アプリケーションとチャット要求の混在 |
| 比較 | FastChat経由のHuggingFaceまたはvLLM |

実験ではネットワーク費用を模擬するため、要求に200〜300ミリ秒の遅延を付加する条件も用いる。文書要約では長さ20,000トークン超の文書から十件を選び、複数の断片へ分けて処理する。出力長や断片長を変え、全体の完了時間を比較する。したがって改善率はモデルの演算速度だけではなく、クライアントとの通信、待ち行列、キャッシュ再利用、実行順の効果を含む。

### 要求間通信を減らす連鎖要約

連鎖要約では、前段の要約結果を次の要求へ渡すため、通常のAPIでは毎回クライアントとの往復が発生する。Parrotは先行結果をサーバー側で後続要求へ渡し、この費用を減らす。論文の図11では、出力長を変えた条件でvLLMを基準に最大1.38倍、HuggingFaceを基準に最大1.88倍の完了時間改善を示す。断片長を変えた条件でも、vLLM比でおおむね1.19〜1.21倍の改善が続く。

ただし、出力長が長くなると、生成トークンそのものに費やす時間が大きくなるため、通信削減の相対的な効果は小さくなる。断片長を大きくすれば呼出し回数が減り、同じく通信の削減余地が変わる。したがって「常に同じ倍率で高速化」とは言えず、要求数、出力長、ネットワーク往復時間に依存する。

### 混雑時と複数アプリケーション

図12では、背景要求の到着率を変えたとき、Parrotの連鎖要約が基準のvLLM構成より短時間で終わることを示す。背景負荷が大きい条件では最大2.38倍の改善が示され、独立した要約アプリケーションの数を増やす条件でも約1.38〜1.68倍の改善が報告される。図13は複数の連鎖要約アプリケーションのそれぞれについて、基準方式よりParrotが早く完了したことを示す。

この改善には、後続要求を新しい独立要求として待ち行列へ入れ直さない効果が含まれる。通常の要求単位の提供方式では、先行要求が終わった直後に別の利用者の要求が先に並ぶ可能性がある。Parrotは依存関係を把握し、後続要求を適切に継続させられるため、アプリケーション全体の待ち時間を減らせる。

### 共有接頭部の規模と効果

論文表1のアプリケーション別統計では、チャット検索の繰返し段落割合が94%、AutoGenでは99%と高い一方、長文分析では3%にとどまる。共有接頭部を活用する最適化は、すべての処理で同程度に効くわけではない。共通指示や会話履歴が繰り返されるアプリケーションでは再計算削減が大きいが、各要求の入力がほぼ異なる場合には依存関係に基づく通信・スケジューリングの方が重要になる。

接頭部再利用では、同じ接頭部のキャッシュを持つエンジンへ要求を寄せることで、入力処理を省ける。ただし多数の要求が同じエンジンへ集中すると、そのエンジンの待ち行列が長くなる。共有量と混雑を同時に考えることが必要であり、キャッシュ再利用だけを最大化する方針が必ずしも全体完了時間の最小化にならない。

### マップ・リデュース要約の実行順

図4では、断片を並列に要約する段階で処理率を重視し、最後に統合する段階では遅延を重視する方針を比較する。要求単位の遅延を一律に最小化するより、アプリケーション全体の完了時間を2.4倍改善する例が示される。これは各要求を常に最短で処理することが、全体の最短時間につながるとは限らないことを具体的に示す。

### 結果の適用範囲

論文は複数のアプリケーションを組み合わせた評価で大きな改善を示すが、その効果は要求間の依存、共有接頭部、通信遅延、混雑度によって変わる。モデルの行列演算自体を一律に何倍高速化した研究ではない。比較したモデルはLLaMA 7Bと13Bであり、異なる規模のモデルや別のGPU構成で同じ改善率が出るとは限らない。改善率を論じる際には、どの処理手順とどの基準方式を使ったかを明記する必要がある。

## 既存研究との差

vLLMやPagedAttentionは、推論エンジン内部の鍵値キャッシュ管理や継続的なバッチ処理を効率化する。Parrotはその上の層で、複数要求がどのアプリケーションに属し、どの入力・出力を共有するかを扱う。エンジン単体の効率化と、アプリケーション全体の実行順最適化は別の問題であり、両者は組み合わせて利用できる。

一般的なエージェントの処理手順では、依存関係をアプリケーション側の制御コードが知っていても、推論サーバーへは完成した文字列だけが送られる。Parrotは意味変数を残すことで、サーバー側にもデータフローを見せる。これにより、要求間の直接通信、並列化、共有接頭部の再利用、段階別のバッチ方針を一つの制御器で判断できる。

## 限界と未検証事項

第一に、アプリケーションが意味変数を用いてプロンプトの構造と入出力の関係を記述する必要がある。既存の完成文字列だけを送るAPIに対して完全に透過的な改善ではない。意味変数を適切に付けないアプリケーションでは、推論提供側が依存関係を把握できず、効果が小さくなる。

第二に、要求間の共有が少ない場合には、接頭部再利用の効果が限られる。表1では長文分析の繰返し割合が3%であり、AutoGenの99%と大きく異なる。通信削減や実行順の最適化は残るが、すべてのアプリケーションで同じ種類の最適化が支配的になるわけではない。

第三に、中央制御器が依存グラフ、要求配置、文脈の寿命を管理するため、利用者やアプリケーションが増えた場合の制御費用を考える必要がある。モデル実行を複数のエンジンへ分散できても、管理側の処理が無制限に拡張することを意味しない。論文の実験範囲を超える大規模な複数地域サービスでの性能を推測しない。

第四に、実験のネットワーク費用には200〜300ミリ秒の遅延を模擬した条件が含まれる。実際の配置が同一データセンター内で往復が小さい場合、通信削減による相対的な改善は縮む可能性がある。逆に広域ネットワークでは効果が大きくなることもあるが、論文にない条件の倍率を作ってはいけない。

第五に、評価モデルはLLaMA 7Bと13Bを中心とし、現代の数百億〜数千億パラメータの混合専門家モデルを直接評価していない。長文脈や多段エージェントへの設計上の示唆はあるが、任意のモデルで同じ性能倍率を保証するものではない。論文はアプリケーションを考慮した要求提供の研究であり、モデルの出力品質を改善する新しい学習方式ではない。

第六に、接頭部キャッシュの再利用を優先すると、同じエンジンへの要求集中が起こり得る。共有する文脈があることと、そのエンジンへ割り当てることが最善であることは異なる。Parrotは共有の利益と待ち行列の費用を併せて扱うが、最適な判断は実行時の負荷とメモリ容量に依存する。

第七に、アプリケーションの依存関係を把握しても、実行できる計算そのものの総量が必ず減るわけではない。連鎖型処理では通信往復と待ち行列の費用を減らし、共有接頭部がある場合は入力処理を省ける。一方、全要求が独立で共有部分がない場合には、データフローを公開する利益は限定される。処理率と完了時間の両方を測定する必要がある。
