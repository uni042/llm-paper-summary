# xGR：生成式推薦のビーム探索に合わせた低遅延推論基盤

## 概要

生成式推薦（Generative Recommendation; GR）は、利用者が過去に閲覧・購入した商品の履歴をトークン列として入力し、次に推薦すべき商品の識別子を自己回帰的に生成する。通常の対話型LLMとは異なり、入力は数百〜数千トークンと長い一方、出力は商品を表す数個のトークンに限られる。しかも候補商品の網羅性を確保するため、ビーム幅128〜512程度の大規模なビーム探索（beam search）を各復号段階で行う。xGRは、この負荷を一般の文章生成向けサービングに載せた場合に生じる共通KVキャッシュの反復読込み、ビーム分岐時のブロック複製、候補ソート、ホスト・デバイス同期を一体的に解消する推論基盤である。

著者は注意演算子xAttention、探索アルゴリズムxBeam、実行管理xScheduleの三つをxLLM上に統合する。xAttentionは全ビームが共有する長い接頭辞と、各ビームで異なる少数の生成トークンのKVを分離する。xBeamは存在しない商品を生成しないための制約マスクと、不要な候補比較を止める早期終了を実装する。xScheduleはホストでの準備とアクセラレータでの実行を重ね、短い復号工程で無視できなくなる起動費用を抑える。

原著PDFの第3版（2026年6月27日、v3）では、Ascendクラスタで99パーセンタイル遅延（P99）が200ミリ秒以下となる要求率について、xLLM比でQwen3は**少なくとも2.89倍**、OneRecは**少なくとも8.05倍**と記す。Qwen3-4B、入力1,000トークン、ビーム幅512では、xLLMのピークメモリ46.3GBに対してxGRは10.6GBだった。旧版の要旨等に見られる3.49倍と最新版の2.89倍は混同せず、本稿では確認したv3本文の数値を採用する。

## 問題設定：短い出力でも復号が重い理由

推薦商品を一つの識別子として直接予測するのではなく、商品IDを複数の意味トークンの組合せとして表す方式では、生成したトークン列が実在商品に対応するかを判定する必要がある。原著の例では商品IDを3トークンで表し、各段階でビーム幅BWと上位候補数Kを128〜512程度に設定する。例えば512×512なら約26万件の候補スコアが発生する。通常のLLMの1系列・1トークン生成と比べ、生成ステップ数は少なくても候補選別の仕事量が非常に大きい。

全ビームは同じ利用者履歴を接頭辞として持つ。それにもかかわらず、一般的なページ化注意（PagedAttention）をそのまま使うと、各ビームの注意計算で同じ接頭辞KVを繰り返し読み込む。ビーム分岐時には新しい系列を作るが、接頭辞の末尾がページ境界に一致しなければ、ページの物理複製も必要になる。ここで不足するのは単純な演算能力だけでなく、KVの帯域、複製先メモリ、ブロック管理の効率である。

さらに推薦サービスでは応答の最悪側を抑える必要があり、原著はP99遅延200ミリ秒をサービス水準目標（Service Level Objective; SLO）として扱う。比較的小型の推薦モデルでは、GPU/NPU上の行列積が速くなるほどCPU側の準備、カーネル起動、マスク転送、バッチ間同期の比率が高まる。xGRはこの三層の律速を、注意・探索・実行管理を別々に調整するだけでなく、データの受渡しまで含めて設計する。

## 手法

### 1. xAttention：共有KVと非共有KVの分離

事前充填（prefill）で得られる利用者履歴のKVを「共有キャッシュ」に一度だけ格納する。一方、ビーム探索によって新たに生まれたトークンのKVは「非共有キャッシュ」に格納する。生成する商品IDのトークン数NDが事前に分かっているため、非共有領域はビーム数に比例する小さな固定上限を持つ。原著の記述では選択候補数KとNDの積に対応するトークン単位の領域を確保する。共有履歴をビームごとに複製する必要はない。

非共有領域はページ境界に合わせずトークン粒度で管理する。ビームの親子関係が変化しても、生成済みトークンの位置を直接参照し、更新順序を制御して上書き前に必要な値が失われないようにする。これによりページ単位のコピーと内部断片化を減らす。利得はビーム幅と履歴長が大きいほど増えるが、親子関係の索引管理は追加で必要であり、任意の可変長出力を対象とした一般のKV管理と同じではない。

### 2. xAttention：注意計算の三段階化とコア配分

注意のスコア計算を共有履歴に対する部分と非共有の生成トークンに対する部分に分け、それぞれを独立した計算群で実行する。最後に両部分の正規化統計をオンラインSoftmax（Online Softmax）で合成する。単純に二つのSoftmax結果を平均するのではなく、部分ごとの最大値・指数和を調整して全体の正規化と整合させる設計である。これにより共有履歴の読み込みをビーム間で再利用しつつ、ビーム固有の短い計算を並列化できる。

各段階をアクセラレータのコア群（Core Group; CG）へ割り当て、行列演算とSoftmaxを同じ群内でパイプライン化する。合成段階は前段の出力を待つ必要があるため、ワークスペース上のフラグを用いた軽量同期を行う。共有段階に計算資源を偏らせすぎると非共有KVの更新が詰まり、逆も起きる。著者は共有・非共有のトークン長とCGの割当三つ組を入力にした決定木回帰器で、分配候補の実行性能を予測して選ぶ。固定的なBWやヘッド次元は配備時に決まるため、予測器の入力を過度に増やさない。

この設計は行列積・ベクトル演算・明示管理可能な高速メモリという抽象に依存する。AscendではCube/Vector系の演算器、NVIDIAではTensor Core/CUDA Coreへ対応付けるが、同じ実装バイナリが両者で動くわけではない。Hopper世代GPUでは連続配置されたKVをテンソルメモリアクセラレータ（Tensor Memory Accelerator; TMA）で非同期転送するという固有最適化を用いる。

### 3. xBeam：無効な商品IDの排除

トークンの組合せの多くは実際の商品に対応しない。原著の図5では、制約なしに生成した300件中、無効商品が平均131件に達した。xBeamは事前構築した有効商品語彙から、次に許可するトークンを表すマスクを作り、モデルのロジットへ加算する。無効トークンには負の無限大を与えるため、Softmax後の選択確率は0となる。これは生成後に無効商品を捨てる方式と違い、探索候補の段階で無駄を減らす。

ただし全商品と全段階の密なマスクを事前保存するとメモリが膨らむ。最初の復号段階では候補が多いため密形式をモデルロード時に生成し、後半の段階では候補が少ないので疎形式で変更箇所だけを更新する。マスク生成はホストでの前処理とデバイス内の適用を分け、後述のスケジューリングで重畳する。商品集合が頻繁に変わる場合のマスク更新費用や整合性は、静的な有効商品集合を前提とする評価からは一般化できない。

### 4. xBeam：早期ソート終了と領域再利用

ビーム探索は全候補の完全ソートではなく、上位K候補だけを見つければよい。各ビーム内の候補は累積対数確率の降順に並ぶので、xBeamは全体の上位K候補を保持する最小ヒープを使う。あるビームの候補スコアがヒープ内の最小値を下回った時点で、その後ろの候補も採用されないと分かるため、当該ビームの走査を打ち切る。スコアの順序が保証されていることがこの枝刈りの前提であり、任意順序の候補列にそのまま適用できるわけではない。

またビーム幅と候補数が固定される性質を利用し、ビームが更新されるたびに新しいデータ構造を作らず、旧ビームが占有していたメモリ領域を次の候補へ再利用する。探索の前後でヒープ、候補配列、KV参照をつなぎ直すため、割当・解放とデータ移動の回数を抑える。ソート費用の削減とKV容量削減は別機構だが、どちらもビーム幅が大きい条件で効く。

### 5. xSchedule：三層の実行重畳

最上位のスケジューラが要求の資源確保と埋め込み情報の準備を担当し、エンジンが事前充填とビーム探索・復号の実行順序を管理し、ワーカーが各段階の演算を実行する。エンジンは同一要求のビーム探索と復号を完全に分離できないため、依存関係を保ったまま別要求・別バッチ間の仕事を重ねる。ホストでの次バッチの準備、フィルタマスクの生成、デバイスでの前バッチの行列計算を同時進行させる。

一連のカーネルとメモリ転送を静的な実行グラフとしてまとめ、CPUがカーネルを逐次発行する費用を減らす。要求の入力長は数十から数千トークンまで変動するため、単純な要求数ではなくトークン予算でバッチを組む。待機時間がSLOの割当上限に達したらバッチを送り、スループットだけを優先して待ち続けない。小型モデルでは一つのバッチだけでは演算器が空くため、複数ストリームで別バッチを並行実行する。ここでの利得はデバイスの計算量だけでなく、ホスト準備と転送を隠蔽できるかに依存する。

## 評価条件と主要結果

### 1. 評価環境

| 観点 | 原著v3の条件 |
|---|---|
| ハードウェア | Ascendクラスタ64ノード、各ノード16基の64GB NPU、HCCS接続。別評価でNVIDIA H800 80GB×8を8ノード、NVLink接続 |
| 実装 | xLLM基盤。Ascend C/CUDA/C++約17k行、Python約4k行。GPU側はHopper TMAを利用 |
| モデル | Qwen3 0.6B・1.7B・4B、OneRec 0.1B・0.7B・3B |
| 入力 | 公開Amazon Reviewと実サービス由来のJD Trace。入力長・要求到着率を変化 |
| 探索 | ビーム幅BW=128/256/512、各ビームの上位候補数KはBWに等しく設定 |
| 比較 | xLLM、vLLM（Ascend移植版）。vLLMはOneRec未対応のためOneRec比較から除外 |
| サービス指標 | 平均遅延、P99遅延、毎秒要求数（RPS）。P99≤200msを主要SLOとする |
| 内部評価 | Qwen3-4Bのピークメモリ、注意カーネル遅延・演算処理量・メモリパイプライン占有率、OneRec-0.1Bの機構除去試験 |

「64ノード×16基」は実験クラスタの構成であり、個々のグラフが常に1024基すべてを使用したことを意味しない。図ごとの測定単位は別である。とくにメモリ評価は単一NPUでRPS=4の条件と明記されている。H800の評価はGPU移植性の確認であり、Ascend上の全数値をH800へ転用しない。

### 2. サービング全体の遅延と処理量

| 比較と条件 | 原著結果 | 解釈 |
|---|---|---|
| Ascend、Qwen3各規模、P99≤200ms | xLLM比で持続可能なRPSが少なくとも2.89倍 | 速度ではなく同じ遅延制約下の処理能力。図13と本文9.2節 |
| Ascend、OneRec各規模、P99≤200ms | xLLM比で持続可能なRPSが少なくとも8.05倍 | vLLMはOneRec未対応。図14と本文9.2節 |
| ビーム幅128→512 | 比較基盤は遅延が急増、xGRは増加が比較的緩やか | 幅を増やしたときの挙動。絶対RPSは図の条件に依存 |
| H800 GPUクラスタ、Qwen3 | xGRがxLLM/vLLMより低遅延・高い持続可能処理量 | 図18の定性的傾向。Ascendの倍率を移植した値ではない |
| 実運用に関する著者記述 | 6か月超の配備、数億利用者、ピーク数万RPSでP99≤200ms | 論文の自己申告。独立した外部監査結果ではない |

vLLM-Ascendは大きなビーム幅で十分最適化されていないと著者自身が述べ、後続のAscend評価では主にxLLMを比較対象にしている。したがって「すべての最適化済みLLMサービング基盤に対して同じ倍率」という意味ではない。推薦専用モデル・商品語彙・短い固定出力という条件が大きく効く。

### 3. KVメモリ使用量

| Qwen3-4B、単一Ascend NPU、RPS=4 | xLLM | xGR | 変化 |
|---|---:|---:|---|
| 入力1,000トークン、BW=512 | 46.3GB | 10.6GB | 約77.1%削減、約4.37分の1 |
| 入力3,000トークン、BW=256 | 約30GB | 12.0GB | 約60%削減 |

前者はビーム数を増やす図15(a)、後者は入力長を増やす図15(b)であり、同じ負荷の前後比較として合算しない。xGRでも入力長が長くなると共有KVそのものは増えるため、「文脈長に関係なく完全な定数メモリ」とは主張しない。主な節約は、ビーム間で共有できる履歴を物理的に一つに保つ点にある。

### 4. 注意カーネルと実行管理の内部評価

| 指標・条件 | 比較結果 | 対応する機構 |
|---|---|---|
| Ascend、図16のカーネル遅延 | PagedAttentionに対して最大約6.6倍の短縮 | 接頭辞の共有と段階化した注意演算 |
| 同、カーネル演算処理量 | 最大約7倍 | 演算器の稼働改善 |
| 同、メモリパイプライン占有率 | PagedAttention平均93.4%、xAttention約52% | KV反復読込みの削減。単独ではGPU全体の稼働率ではない |
| OneRec-0.1B、Amazon Review、図17 | グラフ発行と複数ストリームの有効化でP99遅延が低下 | ホスト・デバイス重畳と起動費用削減 |
| 同、商品妥当性フィルタ | フィルタ追加による遅延は小さいと著者報告 | マスクを探索カーネル内で適用 |

カーネルの6.6倍をエンドツーエンドの6.6倍と書き換えてはいけない。図17の曲線は複数の要素を順に加えた構成要素除去試験であり、個々の最適化が独立に同じ倍率を出す証拠ではない。メモリパイプラインの占有率が52%へ下がったことも、使用帯域が減ったという内部指標であり、総演算利用率を単独で確定するものではない。

## 既存方式との差と再現上の制約

一般的なvLLMは多様な文章生成モデル・可変長出力の同時処理を主眼とし、ページ化KVキャッシュで断片化を抑える。xGRは推薦という特定の負荷ではページの柔軟性よりも、長い接頭辞の共有と固定長のビーム固有領域が有利になることを利用する。xLLMは本研究の実装基盤であり、xGRはその上で注意・探索・スケジューリングを共同最適化する。FlashAttentionからはタイル化とオンラインSoftmaxの考え方を取り入れるが、単なる同カーネルの置換ではなく、ビーム間のデータ配置そのものを変える。

評価は推論システムの遅延・容量・処理量に集中しており、推薦品質の独立した網羅的比較、商品カタログの頻繁な更新時のマスク再構築費用、異なる出力長・ビーム幅・GPU世代への一般化は限定的である。原著は推薦品質を維持することを意図して有効商品を制約し、同じモデルを実行しているが、推薦精度があらゆる本番条件で等価だと外挿することはできない。実運用の規模も著者申告に依存する。

また、推薦専用のビーム探索で優れる設計が、自由形式の対話生成やMoEの長い回答に直結するわけではない。一般的な推論基盤へ応用する場合は、複数系列の共通接頭辞の再利用、KVのトークン粒度管理、カーネル発行のグラフ化を独立に移植し、対象負荷の入力長・出力長・同時要求数で測り直す必要がある。xLLMの公開リポジトリは存在するが、論文の実験版xGRがすべて同一条件で公開・再現可能かは今回の一次資料から確定できない。
