# PrefillShare: A Shared Prefill Module for KV Reuse in Multi-LLM Disaggregated Serving

> 複数LLMが同じ文脈を別々にプリフィルする重複を、凍結共有プリフィル＋KV条件付き追加学習でモデル横断共有し、エージェント処理の尾遅延とKVメモリを削減する。
## 書誌情報
- **著者**: Sunghyeon Woo, Hoseung Kim, Sunghwan Shim, Minjung Jo, Hyunjoon Jeong, Jeongtae Lee, Joonghoon Kim, Sungjae Lee, Baeseong Park, Se Jung Kwon, Dongsoo Lee
- **著者・所属**: NAVER Cloud
- **公開**: arXiv preprint arXiv:2602.12029
- **種別**: Preprint
- **対象**: 複数LLMサービング、共有プリフィル、KVキャッシュ再利用、分離サービング、エージェント推論
- **実装**: vLLMの分離サービング基盤上に、利用者単位ルーティング、共有プリフィルプール、複数タスク固有デコードワーカーを備えるプロキシ型試作系を実装して評価している。公開コードURLは一次資料で確認できなかった。
## 概要
PrefillShareは、複数の専門LLMが同じ長い文脈を繰り返し読むエージェント型処理で、モデルごとに同じプリフィル計算とKVキャッシュを作り直す無駄を除く。凍結した共通基盤モデルを共有プリフィル専用にし、そのKVキャッシュを各タスク固有デコーダへ渡す。単純共有では精度が崩れるため、事前計算した共有KVを条件として専門デコーダだけを追加学習する。実行時は利用者単位の接頭辞局所性を保つルーティングで、増分トークンだけを再プリフィルし、複数モデル間で共通文脈の計算とメモリを一度に集約する。

PrefillShareは、推論モデル全体を各専門モデルごとに複製する前提を崩し、凍結した共通基盤モデルをプリフィル専用モジュールとして一度だけ実行し、そのKV状態を複数のタスク固有デコーダへ再利用する。単純に共有KVを注入すると表現分布の不一致で精度が崩れるため、専門デコーダ側だけを共有KV条件下で追加学習する点が核心である。これにより同一モデル内の接頭辞再利用ではなく、異なる追加学習済みモデル間で100%の共有接頭辞KVを使えるようにする。さらにサービングでは利用者を同じプリフィルワーカーへ固定し、会話が伸びた分だけ増分計算することで、学習上の共有可能性を実行時の高いキャッシュ命中率へ結び付ける。

代表結果として、ReActのP95エンドツーエンド遅延は4モデルのReAct型エージェント処理、到着率を変化でモデルごとに独立した分離プリフィル・デコード経路に対して最大3.9倍短縮。モデル切替ごとの共通文脈再計算をなくし、接頭辞KVを一組に集約することで負荷上昇時のプリフィル待ちを抑える。
## 問題設定
複数の専門LLMを順番に呼ぶエージェント型処理では、各モデルが会話履歴や長いシステム指示など、ほぼ同じ入力文脈を個別にプリフィルする。モデルAのKVキャッシュはモデルBの重みで計算したKVとは一致しないため、通常の接頭辞キャッシュはモデル境界を越えて使えない。このためN個の専門モデルを持つと、共通文脈のプリフィル計算とKVメモリもほぼN重に複製される。分離サービングでプリフィルGPUとデコードGPUを分けても、このモデル間重複自体は消えない。エージェントのターン数や同時セッション数が増えると、プリフィル処理の競合とKV容量不足が尾遅延を押し上げるため、異なる専門モデルが同一文脈を共有できる仕組みが必要になる。
## 新規性
PrefillShareは、推論モデル全体を各専門モデルごとに複製する前提を崩し、凍結した共通基盤モデルをプリフィル専用モジュールとして一度だけ実行し、そのKV状態を複数のタスク固有デコーダへ再利用する。単純に共有KVを注入すると表現分布の不一致で精度が崩れるため、専門デコーダ側だけを共有KV条件下で追加学習する点が核心である。これにより同一モデル内の接頭辞再利用ではなく、異なる追加学習済みモデル間で100%の共有接頭辞KVを使えるようにする。さらにサービングでは利用者を同じプリフィルワーカーへ固定し、会話が伸びた分だけ増分計算することで、学習上の共有可能性を実行時の高いキャッシュ命中率へ結び付ける。
## 手法
### 手法のあらまし
学習前に、共通基盤モデルを共有プリフィルモジュールとして凍結する。各訓練例の入力文脈をこのモジュールへ通してKV状態を事前計算し、そのKVは勾配を流さず固定する。その後、各タスク固有デコーダは通常の次トークン予測損失を使うが、自己の前段層で入力文脈を再計算する代わりに、共有モジュールが生成したKVを条件として学習する。教師強制で正解系列を与えながら、デコーダの重みだけを更新することで、共有基盤のKV表現と専門デコーダの内部表現のずれを吸収する。推論ではクライアント前段のプロキシが利用者識別子を一定のプリフィルワーカーへ写像する。最初の専門モデル呼び出しでは、そのワーカーが共通基盤モデルで文脈全体をプリフィルし、生成したKVを対象のデコードワーカーへ転送する。次の専門モデルへ処理が移っても、同じ利用者は同じプリフィルワーカーへ戻るため、既存の共有接頭辞KVに命中し、新たに追加されたモデル出力や会話トークンだけをプリフィルする。更新後のKVを次の専門デコーダへ渡し、この処理をモデル切替と複数ターンにまたがって繰り返す。共通接頭辞長をL、各モデル固有部分をU_iとすると、独立方式は各モデルがLを持つため概ねN×Lに比例してKVを複製するが、PrefillShareでは共通Lを一組だけ保持し、モデル固有部分だけを追加する。その結果、プリフィル計算量とキャッシュ容量の両方をモデル数に対して償却できる。

### 共有プリフィルとKV条件付き追加学習
共通基盤モデルをプリフィル専用として凍結し、訓練データの文脈からKV状態を先に作って固定する。各専門デコーダは、その共有KVを入力条件として次トークン予測を学習し、共有プリフィル側には勾配を戻さない。単純なKV流用では、専門モデルの追加学習によって変化した注意表現と基盤モデルのKV表現が一致せず、共有割合を増やすほど精度が急落する。そこで専門デコーダ自身を共有KVの分布へ適応させることで、推論時に接頭辞部分をすべて共有してもタスク精度を維持する。各タスクで必要なのはデコーダ側の追加学習だけなので、共通プリフィルモジュールを一つ固定したまま複数の専門モデルを増やせる。

### 接頭辞局所性を保つ増分プリフィルルーティング
実行時のプロキシは利用者識別子とプリフィルワーカーの対応表を維持し、同じセッションを常に同じ共有プリフィルワーカーへ戻す。最初の呼び出しでは文脈全体を計算するが、専門モデルAの応答が会話へ追加されて専門モデルBを呼ぶときは、既存の接頭辞KVを再利用して新しく増えたトークンだけを計算する。そのKVをモデルBのデコードワーカーへ転送し、次のターンでも同じ規則を繰り返す。モデル切替のたびに文脈全体を別のプリフィルGPUで再計算する方式と異なり、長い共有履歴ほど命中の価値が高くなる。局所性を保てないと共有KVが存在するワーカーへ到達せず再計算が発生するため、利用者固定ルーティングが学習上可能になったモデル横断共有を実際の性能改善へ変換する重要な条件になる。

### 分離サービング上の共有KVメモリ構造
試作系はクライアント向けプロキシ、共有プリフィルプール、複数のタスク固有デコードワーカーからなる。プリフィル側には凍結基盤モデルだけを置き、デコード側にはモデルA、B、C、Dのような異なる追加学習済みモデルを置く。独立方式では各モデルが共通接頭辞Lと固有部分U_iをそれぞれ保持するためKV量は概ねN×Lとともに増えるが、共有方式ではLを一度だけ持ち、各モデル固有の追加部分だけを保持すればよい。これにより同じGPU総数でも接頭辞KVの重複が減り、より多くのセッションをGPUメモリ内に残せる。ただしデコード側の各セッション固有KVまで共有されるわけではないため、極端な同時実行数ではデコードGPUのKV容量が再び上限になり、CPUへの一時退避と再読込みが発生する。

### 全体のデータ／制御の流れ
4モデルのエージェント処理を例にすると、比較系は各専門モデルに独立したプリフィル・デコード経路を持ち、合計8 GPUを4組へ分ける。PrefillShareも同じ4プリフィルGPU＋4デコードGPUの総予算を使うが、プリフィルGPU群は単一の凍結基盤モデルを共有し、デコードGPU群だけが異なる専門モデルを持つ。プロキシが利用者局所性を維持し、共有KVを必要なデコードワーカーへ転送する。高同時実行時にデコード側GPUメモリが足りない場合、基盤のvLLMは一部KVをCPUへ退避して後でGPUへ戻すため、その段階ではCPU-GPU転送が新たなボトルネックになる。
## 評価条件
- **ハードウェア**: 追加学習は単一ノードの8基A100-SXM4-80GBで実施する。サービング評価は同じ総GPU予算として4基をプリフィル側、4基をデコード側へ割り当て、LLaMA3.1-8Bを主対象にする。付録では同一の処理構成をQwen3-14Bへ置き換えて再評価している。
- **ソフトウェア**: 追加学習にはLMFlowを使い、MetaMathQA-40K、EvolInstruct-Code-80K、xLAM-function-calling-60Kを用いる。サービング試作はvLLMの分離サービング基盤を拡張し、利用者固定ルーティング、共有プリフィルプール、複数の専門デコードワーカー、KV転送をプロキシで統括する。
学習品質はLLaMA3.1-8BとQwen3-8Bを中心に、数学、コード生成、関数呼出しの複数指標で通常の完全追加学習と比較する。学習はバッチ1、勾配蓄積16、最大系列長1024、1エポック、AdamWで実施する。サービングでは4エージェントが順次呼ばれ、長い共有文脈が増えていくReActとReflexionの処理を用いる。各モデル呼出しの入力・出力長は既存測定に基づいて固定し、セッション到着率や最大同時セッション数を変化させ、P95エンドツーエンド遅延、スループット、最初のトークンまでの時間、接頭辞キャッシュ命中率を測る。
主なサービング実験は単一A100ノード内の分離サービングであり、複数ノード間ネットワークをまたぐKV転送や生産環境の長さ分布変動は直接評価していない。対象は同じ共有基盤モデルから派生した専門デコーダで、任意の異種アーキテクチャ間共有ではない。比較は同じ8 GPU総予算で行うため計算資源条件は揃っているが、専門デコーダを事前にKV条件付き追加学習できることが前提になる。
## 主要結果
PrefillShareは、共有文脈が長くモデル切替が多いエージェント処理ほど効果が大きい。ReActではP95遅延を最大3.9倍短縮しスループットを最大3.6倍、ReflexionではP95遅延を最大4.5倍短縮しスループットを最大3.9倍へ改善した。低負荷では比較系との差が小さいが、同時セッションが増えると独立モデル群は接頭辞KVの重複でGPU容量を圧迫して命中率が下がる一方、共有方式は高い命中率を維持する。ただしデコード側の固有KVは残るため、極端な同時実行数では再びメモリ圧力が性能を制限する。

- ReActのP95エンドツーエンド遅延 / 最大3.9倍短縮 (比較対象: モデルごとに独立した分離プリフィル・デコード経路; 条件: 4モデルのReAct型エージェント処理、到着率を変化) — モデル切替ごとの共通文脈再計算をなくし、接頭辞KVを一組に集約することで負荷上昇時のプリフィル待ちを抑える。

- ReActのスループット / 最大3.6倍 (比較対象: 独立分離サービング; 条件: 同じ8 GPU総予算) — 共有プリフィル計算と高い接頭辞命中率により、同じGPU数で処理可能なセッション数を増やす。

- ReflexionのP95エンドツーエンド遅延 / 最大4.5倍短縮 (比較対象: 独立分離サービング; 条件: 複数ターンで文脈が増えるReflexion型処理) — 長い履歴を繰り返し利用するため、共有接頭辞を増分更新する利点がReActより大きくなる。

- Reflexionのスループット / 最大3.9倍 (比較対象: 独立分離サービング; 条件: 同じ8 GPU総予算) — 重複プリフィルと重複KVメモリを減らすことで、高負荷時の有効処理能力を大きく保つ。

- 接頭辞キャッシュ命中率 / 約89%を広い同時実行範囲で維持 (比較対象: 比較系は約60%で頂点となった後、約40同時セッション以降低下; 条件: ReAct、4セッション/秒、最大同時セッション数を変化) — 共有接頭辞をモデルごとに複製しないため、GPUメモリ圧力が増えても共通文脈を保持しやすい。

- LLaMA3.1-8B GSM8K精度 / 71.4 (比較対象: 通常完全追加学習 71.3; 条件: KV条件付き追加学習後) — 共有KVへ専門デコーダを適応させることで、100%の共有接頭辞を使っても数学タスクの精度をほぼ維持する。

- Qwen3-8B HumanEval精度 / 86.6 (比較対象: 通常完全追加学習 83.5; 条件: KV条件付き追加学習後) — 共有KV条件が必ず精度を落とすわけではなく、コード生成では比較値を上回る例もある。ただし全タスクで一貫した向上を主張する結果ではない。

### 負の結果・境界条件
- 共有KVを専門モデルへそのまま注入するだけでは、共有率が高いほど表現不一致が拡大して精度が崩れるため、KV条件付き追加学習が必要である。サービングでも低負荷時は重複計算が待ち時間を支配しないため改善幅が小さい。また約110同時セッション付近から、共有側の命中率が高いままでもスループットが飽和または低下する。これはデコード側のセッション固有KVがGPU容量を超え、vLLMがCPUへ一部を退避してGPUへ再読込みする転送費が増えるためである。Qwen3-14Bでは高到着率で最初のトークンまでの時間が増える領域もあり、共有プリフィル側の利用率上昇が初期応答を遅くすることがある。

### 結果の読み方
性能改善の因果は、モデル横断で共有可能な接頭辞を一組へ集約し、同じ利用者を同じプリフィルワーカーへ戻して増分計算だけにすることにある。これによりプリフィルGPUの再計算と共通KVの複製が同時に減り、同時実行数が増えても接頭辞をGPU内に残しやすくなる。一方、生成中のモデル固有KVやデコード計算は共有されないため、負荷がさらに上がるとボトルネックはデコード側へ移動する。したがってPrefillShareは全推論状態を共有する方式ではなく、複数モデル処理で最も重複しやすい共通文脈部分を切り出して償却する方式である。
## 品質への影響
KV条件付き追加学習後は、LLaMA3.1-8BとQwen3-8Bの数学、コード生成、関数呼出しで通常の完全追加学習と概ね同等の精度を示す。例えばLLaMA3.1-8BのGSM8Kは71.3から71.4、BFCL Simple Pythonは90.0から90.7、Qwen3-8BのGSM8Kは85.8から84.8である。手法はKVを近似圧縮するのではなく、専門デコーダを凍結共有KVに合わせて訓練するため、品質差は表現整合化の学習結果として評価する必要がある。
## 既存研究との差
通常の接頭辞キャッシュは同一モデルが同一接頭辞を再利用する。KVFlowなども主に同じモデル内の接頭辞局所性を改善する。DroidSpeakやKVCommは異なるモデル間のKV再利用・通信を扱うが、PrefillShareは推論経路を共有プリフィルとタスク固有デコードへ明示的に分解し、専門デコーダを共有KV条件下で学習して100%の接頭辞共有を成立させる。ICaRusのように共通部を共有する既存発想に対しては、共通プリフィルを生成ループから切り離し、デコード時に共通モジュールを繰り返し実行しない点が異なる。システム側では利用者固定ルーティングと増分プリフィルを組み合わせ、学習上の互換性だけでなく高負荷時のキャッシュ命中率まで対象にする。
## 限界
任意の既存専門モデル同士へ後付けでKVを共有できる方式ではなく、各専門デコーダを同じ凍結共有プリフィルのKV分布へ適応させる追加学習が必要である。そのためモデル提供者が重みを更新できないAPI型モデルや、基盤アーキテクチャが異なるモデル群へ直接適用することは難しい。主要サービング評価は単一A100ノード内で、入力・出力トークン長も既存統計に基づいて固定しており、複数ノード間ネットワーク、予測不能な長さ分布、モデルの頻繁な入替えは十分に評価していない。また共通接頭辞だけを共有するため、同時セッションが増えてデコード側固有KVが膨らむとCPU退避と再読込みが発生し、共有プリフィルの利点だけでは性能低下を防げない。
## 実装状態
論文はvLLMの分離サービング基盤上にプロキシ型の試作系を実装している。プロキシは利用者からプリフィルワーカーへの対応表を管理し、プリフィルプールには単一の凍結共有基盤モデル、デコードプールには複数の専門モデルを配置する。KV転送、増分更新、接頭辞局所性管理、高同時実行時のvLLMによるCPU一時退避まで実機で評価している。一方、一次資料中に著者公式の公開コードURLは確認できず、再現用実装が一般公開されているとは判断しなかった。
## 研究上の位置づけ
複数モデル・複数エージェントのサービングで、同一文脈をモデルごとに処理する計算とKVメモリの重複を、モデル設計と実行基盤の両側から除く研究である。単一モデル内のKV圧縮や階層退避ではなく、モデル境界そのものを越えて共通文脈を共有するため、エージェント型ワークロードが増えるほど重要になる。メモリ階層の観点では、GPUからCPUへKVを逃がす前に重複する共通KVを論理的に一組へ畳み込む方式と位置付けられ、KVキャッシュ容量管理や分離サービング、モデル配置と補完関係にある。
