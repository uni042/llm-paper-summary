# Pallas: A Proactive KV Cache Migration Framework for LLM Inference in AI-RAN

> **Pallasは、handover後にKV cacheを救出するのではなく、handover前の予測時間を使って「古い大部分はtargetで再計算、これから増える部分だけsourceからstream」し、切替時点にほぼ最新の推論状態を揃える。**

## 概要

AI無線アクセス網（AI-RAN）では、基地局（gNB）近傍のGPUでLLMを実行すると、mobile userから遠いdatacenterへ毎token通信するよりnetwork latencyを短くできる。しかし、ユーザーが移動して接続先基地局を切り替えるhandoverが起きると、**ユーザーはtarget gNBへ移ったのに、その会話のKV cacheはsource gNBに残る**という状態になる。

autoregressive decodeを途中から再開するには、これまでのtokenに対応するKV cacheが必要である。KV cacheはcontext長に比例して大きくなり、sourceでdecodeを続けている間にも毎token増える。論文の例ではQwen3-32BのKV cacheは約256 KiB/tokenで、4,000 token時点で約1 GiB。300 Mbpsのinter-gNB linkで1 GiBをそのまま送るだけなら約28秒かかる。これをhandover後に開始すると、edge inferenceとしては致命的な停止時間になる。

既存の選択肢は大きく二つある。

- **source-side retention / Detour:** source GPUでそのまま生成を続け、tokenだけ新しい基地局経由でユーザーへ転送する。生成は止まらないが、以後すべてのtokenが遠回りするためトークン間遅延（Inter-Token Latency; ITL）が恒常的に増える。
- **target-side recovery:** handover後にKVをtargetへ全copy、全contextをprefill再計算、あるいは両者を組み合わせる。handover後はlocal servingへ戻れるが、状態準備が終わるまでサービス中断時間（Service Interruption Time; SIT）が発生する。

Pallasの発想は、mobility systemがhandover先とおおよそのhandover時刻を事前予測できるなら、**その予告時間をKV cache migrationへ使えばよい**というもの。source側は通常通りdecodeとtoken配信を続けながら、target側で同じ推論状態を並行して作る。handover時点では残作業だけをSITとして支払えばよく、準備済み部分はユーザーから見えない時間へ隠せる。

## 背景: なぜ「全部copy」でも「全部再計算」でも重いのか

KV cache migrationには、networkとGPU computeの二種類のresourceがある。

**Full-Copy**はsourceにあるKV tensorをそのままtargetへ送るためGPU再計算は不要だが、contextが長いほどnetwork payloadが直線的に増える。論文のQwen3-32B / 300 Mbps測定では、1K tokenで約7.17秒だったSITが4K tokenでは約29.07秒まで増える。

**Recomputation**はKVではなくtoken IDsだけを送り、target GPUでprompt + generated historyをprefillし直す。network payloadは非常に小さくなる一方、長contextのprefill計算をhandover後に丸ごと実行するため停止時間が残る。1K→4K tokenで約581 ms→2,103 msへ伸びる条件が報告される。

**ctHO**はprefixを再計算しsuffixを転送するhybridだが、準備開始がhandover後なので、その処理は依然SITへ直接乗る。

この観察からPallasは「copyとrecomputeのどちらを選ぶか」だけではなく、**いつ開始してどこまでhandover前へ隠すか**を主要制御変数にする。

## 手法のあらまし

Pallasはhandover予測を受けると、予測handover時刻から逆算して準備開始時刻を決める。この開始からhandoverまでの時間を先読み窓（prefetching window）と呼ぶ。

準備開始時点で、現在のtoken sequenceを二つに分ける。

1. **安定履歴prefix（stable historical prefix）**: 開始時点までに既に確定しているtoken列。以後内容が変わらない。
2. **発展suffix（evolving suffix）**: 準備開始後、sourceでdecodeを続けることで新しく増えていくtoken列。

この「過去は固定、未来だけ増える」という性質を使って、二つを別の方法でtargetへ作る。

### 1. stable prefixはKVを送らず、token IDからtargetで再計算する

準備trigger時点でsourceはstable prefixのtoken IDsをtargetへ送る。token IDsはKV tensorより桁違いに小さいためnetwork負荷は軽い。target GPUはこれを通常のprefillとして実行し、自分のGPU上に同じprefix KVを再構築する。

たとえば1 GiBのKVを300 Mbpsで送ると何十秒もかかる一方、数千個のtoken IDはほぼ無視できる大きさである。targetにprefill compute余力があるなら、networkをGPU computeへ置換した方が速い。

### 2. evolving suffixはsourceからKV blockを逐次streamする

prefix再計算中もsourceはactive ownerとしてdecodeを続け、ユーザーへtokenを返し続ける。この間に生成された新tokenはprefix再計算には含まれていないため、そのKV stateを別途targetへ追従させる必要がある。

PallasはvLLMのPagedAttention block単位で完成したsuffix KV blockを取り出し、asynchronous gRPCでtargetへstreamする。prototypeではblock size 16 tokenを用いる。targetは到着したsuffix blockをbufferし、prefix再構築と並行して蓄積する。

ここで「suffixも再計算すればよい」としないのは、sourceで生成が進み続けるためtarget側がmoving targetを追いかけることになるからである。逆に「prefixも全部stream」すると巨大な歴史payloadがnetwork bottleneckになる。したがって、**固定済みの大部分をcomputeで再生し、増分だけnetworkで追う**のがPallasの核心である。

### 3. handover時はfinal deltaだけ同期してtargetをactivateする

実際のhandoverが来ると、sourceは最終sequence positionを記録し、まだstreamされていない最後のtoken/KV blockをtargetへ送ってdecodeを停止する。

targetは、(a) 自分でprefillしたprefix KV、(b) 事前stream済みsuffix KV、(c) 最終deltaを、vLLMの新しいrequestとblock tableへ対応付ける。computed-token stateも更新し、全contextをもう一度prefillすることなくdecodeを再開する。

handover前に準備がすべて間に合えば、handover後のSITはこのfinalizationだけになる。間に合わなかった場合は、残っているprefix prefillやsuffix transfer分だけがSITに露出する。

## 先読み窓（prefetching window）は早ければ早いほど良いわけではない

準備開始を非常に早めればhandoverまでの余裕は増え、SITは小さくしやすい。しかし早く始めるほど二つの無駄が増える。

第一に、target GPUをhandoverよりかなり前から使うため、他requestを処理できたresourceを占有する。第二に、準備開始後にsourceで生成されるevolving suffixが長くなり、その分KV streamingが増える。さらにhandover先予測が外れれば、準備した状態全体が無駄になる。

逆に開始が遅過ぎればtarget prefix prefillやsuffix transferがhandoverまでに終わらず、未完了部分がSITへ残る。

論文のQwen3-14B、3,000-token context、300 Mbpsの例では、windowを0から約1秒へ増やすとSITが約1.1秒から約0.25秒へ大きく下がるが、4秒まで早めると約2.4秒のearly-preparation exposureが発生する。つまり明確なtrade-offがある。

## online scheduler: runtime telemetryからwindowを選ぶ

PallasのScheduler Engineは以下を継続的に観測する。

- 現在context長
- sourceのdecode throughput
- targetのprefill throughput
- inter-gNB goodput
- target GPUで準備可能か
- 予測handover先
- 予測handoverまでの残り時間

throughputやgoodputは指数移動平均（Exponentially Weighted Moving Average; EWMA）で平滑化し、候補prefetch windowをbounded grid上で評価する。costは概念的に、**handover後に残るSIT**と**早過ぎる準備によるresource exposure**の加重和である。prototypeの評価では重み `α=0.8` を用いる。

300 Mbps / Qwen3-14B / 3,000 tokenの例ではschedulerが1.64秒のwindowを選び、SIT 227.57 ms、early-preparation exposure 0.017 sとなった。単純に最大windowを選ぶのではなく、現在のprefill速度とlink速度から「必要なだけ先に始める」点が重要である。

## mobility predictionが外れた場合

proactive migrationには予測ミスが避けられない。Pallasはtarget predictionが変更された場合、epochを更新して古いmigrationをcancelし、準備済みstateを解放して新targetへreplanする。

実handover先が準備先と異なった場合は、prepared stateを使えないためpost-handover recoveryへfallbackする。したがってPallasはprediction errorで正しさを失うわけではないが、準備compute / bandwidthを無駄にし、最悪時にはreactive baseline相当のSITへ戻る。

windowに上限を設けることで、誤予測時に何秒分もtarget resourceを浪費し続けるのを抑える。評価ではcell size 50〜150 m条件でincorrect target predictionが37.3%から11.2%へ変化し、平均wasted preparationも1.46→0.58秒へ変化しており、mobility prediction品質が実用性へ直接効く。

## 評価

### 実装とhardware

- **runtime:** vLLM 0.8.5ベース。
- **server:** 2 physical servers、各NVIDIA RTX A6000 1台。
- **network:** 1 Gbps Ethernetを用い、inter-gNB goodputを100 / 300 / 500 Mbpsへ制御。
- **KV管理:** PagedAttention 16-token block、PyTorch/BytesIO serialization、asynchronous gRPC transfer。
- **models:** Meta-Llama-3-8B、Qwen3-14B、Qwen3-32B-Instruct-AWQ。
- **追加network:** SNOB-5Gのtime-varying goodput traceも使用。

### single handover: SITを数十秒級から数百msへ隠す

固定goodput条件で、PallasはFull-Copy比 **70.13〜89.68倍**、Recomputation比 **2.35〜7.28倍**、ctHO比 **2.28〜6.76倍** の平均SIT短縮を報告する。

特に100 Mbps / Qwen3-32Bでも平均SITは321 ms。巨大KVをhandover後に100 Mbpsで送れば長時間停止する条件でも、大部分をhandover前へ隠せたためである。

論文abstractにある「2.28〜89.68倍」はtarget-side recovery方式全体をまとめた範囲であり、baselineによって改善倍率が大きく異なる。Full-Copyが最もnetwork-boundなので倍率が大きく、既にhybridなctHOに対しては2.28〜6.76倍程度となる。

### serving localityを戻すのでDetourよりITLも低い

source-side DetourはSITをほぼ避ける一方、handover後も遠いsourceからtokenを転送し続ける。Pallasはtargetへstateを移してlocal decodeへ戻るため、平均ITLをDetour比 **16.0〜50.0%**削減し、固定goodput条件では概ね28〜48 msを維持した。

source forwardingでhop数が増える測定ではQwen3-32BのP90/P99 ITLが126.68/263.54 msまで上がる例もあり、100 ms級token-latency objectiveを超える。Pallasは「handover時の一度きりの移行cost」を前倒しして、「以後ずっと支払うnetwork detour」を避ける設計といえる。

### repeated mobility trace

nuScenes trajectory replayを用いた反復handoverでは、3 modelで平均SIT **153.8〜323.8 ms**、P99 SIT **216.3〜488.1 ms**、平均ITL **25.1〜66.7 ms** を報告する。single handoverだけでなく、移動し続けるuserでmigrationを繰り返しても数百ms級へ収められることを示す。

### ablation: recomputationとincremental streamingの両方が必要

300 Mbps / Qwen3-14B条件ではPallasのSIT 235 msに対し、prefix recomputationを使わないvariantは12,486 ms、incremental streamingを使わないvariantは655 ms。Pallasはそれぞれに対して約97.93%、33.3%のSIT削減となる。

これは「token ID + target prefill」で巨大history transferを避けることが最大の効果を持ち、その上でevolving suffixを逐次streamしてhandover直前のdeltaを小さくすることも追加で効く、という設計意図を支持する。

## 既存研究との差

datacenter内のKV live migrationでは、network topologyが比較的安定し、migration先もscheduler自身が選べることが多い。AI-RANではuser mobilityがmigrationを強制し、inter-gNB帯域はdatacenter fabricより細く変動し、target predictionも外れ得る。

Pallasはこの環境差を利用し、**mobility predictionをstate preparation deadlineへ変換**する。ctHOのようなprefix-recompute + suffix-transferの分割自体だけでなく、それをhandover前にsource inferenceとoverlapさせ、windowをonline制御する点が中心である。

## 限界と適用境界

- **sourceとtargetで同一model/state表現を再現できる必要がある。** model version、quantization、KV layoutが異なるheterogeneous edge間migrationは直接扱わない。
- **mobility predictionに依存。** targetや時刻が外れるほどprepared workが無駄になり、fallback recoveryも増える。
- **target GPU余力が必要。** proactive prefix prefillはhandover前にtarget computeを使うため、targetが常時飽和していると準備そのものがqueueへ入る。
- **network contention。** multi-user handoverが重なるとsuffix streamingが競合する。論文はmulti-user評価を行うが、joint resource allocation最適化は範囲外。
- **prototype規模は2 server。** RAN全体で多数gNBと多数userを同時制御するcontrol-plane scalabilityは今後の課題。
- **KV cacheを小さくする手法ではない。** pruning / quantization / compressionとは直交し、Pallasは「大きいstateをどう移すか」を解く。
- **公開code未確認。** 監査時点では論文に詳細prototype実装は記載されるが公式repositoryを確認できない。

## 実装上の含意

Pallasの考え方はAI-RAN以外にも使える。増え続けるstateをlive migrationする場合、snapshot全体をcopyするより、**immutableな大部分をdestinationでreconstructし、snapshot後のdeltaだけstreamする**方がnetworkを節約できる。database replicationやVM migrationに近い発想をLLM KVへ適用したものと見られる。

またmigration start timeは「早いほど安全」ではなく、destination compute、network bandwidth、prediction confidenceを含むresource allocation問題である。実装時にはSITだけ最小化すると無駄なprefetchを大量発生させるため、Pallasのようにearly-preparation exposureもobjectiveへ入れる必要がある。
