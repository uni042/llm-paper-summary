# CrossPool: Efficient Multi-LLM Serving for Cold MoE Models through KV-Cache and Weight Disaggregation

> **CrossPoolは、複数の低頻度MoEモデルで「常に大きいFFN weight」と「時々だけ大きくなるKV cache」を同じHBMへ押し込むのをやめ、weight用GPUとKV用GPUへ分けることで、modelごとの余ったKV容量を1つの共有poolとして使えるようにする。**

## 概要

LLM servingでは、人気modelだけでなく、多数のmodelをAPI catalogへ常時載せておく必要がある。しかし実際のtrafficは大きく偏り、論文がOpenRouterのtoken消費分布を整理した例では、およそ90%のmodelが低頻度な「cold model」側に位置する。こうしたmodelはrequestがほとんど来ていない時間でも、すぐ応答できるようmodel weightをGPUへ置いておく必要がある。 citeturn877467view0

特に疎な専門家混合（Mixture-of-Experts; MoE）モデルでは、この固定weightが大きい。CrossPoolが扱うQwen3-30B-A3Bでは29.0B parameter、DeepSeek-V2-Liteでは14.9B parameterがFFN側にあり、いずれもattention側を含む主要weightの約95%をFFNが占める。つまりMoEでは「常に置いておく巨大weight」と「active requestがある時だけ増えるKV cache」が、同じHBMを奪い合う構造になりやすい。 citeturn877467view0

KV cacheはweightと性質が逆である。request開始時にはprompt分が作られ、decodeが進むほど増え、requestが終われば解放される。cold modelでは各modelが同時にpeakへ達する確率が低いため、model A/B/Cそれぞれに「最悪の場合のKV容量」を固定予約するより、**複数modelの実際の同時KV需要を足した共有pool**へまとめた方が少ないHBMで同じburstへ耐えやすい。

ところが既存のmulti-model servingで単にGPU memoryをelasticに共有するだけでは、weightもKVも同じGPU poolに残る。さらに最近のマルチクエリアテンション（Multi-Query Attention; MQA）や多頭潜在注意（Multi-head Latent Attention; MLA）のようにKV head数が少ないattentionでは、低concurrency時にdata-parallel replicaのうちrequestを担当する1 replicaのKV memoryしか1 requestから見えないことがある。4 GPUを持っていても、配置次第では1 requestが利用できるKV容量が全体の1/2や1/4に限られる。これが長contextの収容能力をさらに下げる。 citeturn877467view0

CrossPoolはこの問題を、単なるallocator改善ではなく**memory objectの寿命に合わせたGPU pool分離**で解く。

- **KV pool**にはattention、非FFN module、共有KV cacheを置く。
- **weight pool**には複数MoE modelのFFN weightを集約する。
- layerごとに両pool間を往復するのは巨大なKV tensorではなくhidden stateだけにする。

KVをattentionの近くに残すので、長contextになるほど膨らむKVを毎token network越しに読む必要はない。一方、FFN weightをKV GPUから追い出すことで、KV poolのHBMをmodel横断で大きく確保できる。

ただし、この分離だけでは毎layerのhidden-state transferと細かいGPU制御が新たなbottleneckになる。そこでCrossPoolは、共有KV容量を事前計画するKV planner、CUDA仮想メモリ管理（CUDA Virtual Memory Management; CUDA VMM）によるonline virtualizer、2 batchを交差させるlayer-wise pipeline、GPU常駐の永続kernel（persistent kernel）を組み合わせる。 citeturn877467view0turn178761view0

## 背景: なぜ「KVを共有するだけ」では足りないのか

### 固定weightと動的KVは、同じHBMに置くと相性が悪い

model weightはmodelをloadした時点からほぼ一定量を占める。一方KV cacheはtraffic、prompt長、output長、同時request数によって大きく変化する。

仮に3つのcold modelがあり、それぞれ最大20 GBのKVを必要とし得るとしても、同時に3 modelすべてが20 GBを必要とするとは限らない。それぞれへ20 GBずつ固定予約すると合計60 GB必要だが、実trafficではaggregate demandのP99が30 GB程度かもしれない。共有poolならこの統計的多重化（statistical multiplexing）を利用できる。

しかしweightとKVを同じGPU群へ混載すると、その共有KV poolの上限そのものがweight配置に縛られる。MoE weightは数十〜百GB級なので、elastic allocatorを導入しても「空いているHBMがそもそも少ない」という問題は残る。

CrossPoolはそこで、FFN weightを別GPUへ移し、KV専用側のHBMを物理的に空ける。

### KV head数が少ないmodelでは、総HBMが1 requestから見えない

4 GPUでattentionを実行する例を考える。

通常の多頭注意（Multi-Head Attention; MHA）やKV head数が十分多いグループ化クエリ注意（Grouped-Query Attention; GQA）では、tensor parallelismでKV headを4 GPUへ分散できる。1 requestが4 GPUすべてを使うため、4台分のKV capacityをまとめて利用できる。

一方、KV headが2個しかないGQAなら、実装は2-GPU tensor-parallel replicaを2組作る構成になり得る。cold trafficでrequestが1本しかなければ、そのrequestが利用するのは1 replicaだけなので、全4 GPUのKV capacityの約1/2しか見えない。MQAやMLAのようにdata parallelismを使い4 replicaへ分ければ、1 requestから見えるのは1 GPU、つまり約1/4になる。 citeturn877467view0

高concurrencyなら複数replicaへrequestを散らして総capacityを使えるが、cold modelは同時requestが少ない。したがって**throughput向けのdata parallel配置が、single long-context requestの最大context capacityを逆に狭める**というalgorithm-system mismatchが起きる。

CrossPoolはattention/KV側をFFN weight配置から独立させることで、この制約を緩める。

## 手法のあらまし

### 1. FFN weight poolとKV poolをGPU単位で分ける

1 transformer layerのdecodeを大まかに見ると、attentionとFFNが交互に現れる。CrossPoolではattentionとlayer normalizationなどの非FFN moduleをKV poolで実行する。attentionは過去tokenのKV cacheへ毎stepアクセスするため、KVをlocal HBMへ残すのが重要だからである。

attentionが出したhidden stateだけをweight poolへ送り、そこでMoE FFNを実行する。FFN出力を再びKV poolへ返し、次layerのattentionへ進む。この往復を全layerで繰り返す。

なぜKVそのものをweight poolへ持っていかないのか。KV trafficはcontext長に比例して増え、decodeのたびに過去KV全体へアクセスする。一方hidden state transfer量は、その時のbatch token数とhidden dimensionで決まり、過去contextが64Kから128Kになっても同じ1 decode stepのtransfer量が倍になるわけではない。したがってpool境界にはhidden stateを置いた方が長contextへscaleしやすい。 citeturn877467view0

MoEではこの分離のmemory利得も大きい。論文のparameter内訳ではFFN shareがDeepSeek-V2-Lite 95.0%、Qwen3-30B-A3B 95.0%、GLM-4.7-Flash 94.5%。一方dense modelのLlama-30Bは66.0%、Qwen3-32Bは76.8%であり、同じ設計でもMoEの方が「KV側から追い出せるweight」が多い。 citeturn877467view0

### 2. KV planner: 各modelの最大値を足さず、「ランダムな時点のaggregate KV」を見積もる

共有poolを作っても、小さ過ぎればburstでOOMし、大き過ぎればweight側GPUを減らしてしまう。そこでoffline KV plannerが必要になる。

plannerはmodelごとに次の情報を受け取る。

- prompt token数のsample
- output token数のsample
- decode service time
- request arrival rate
- 1 tokenあたりKV byte数
- KV page size
- P95/P99などのprovisioning target

request `i` が到着してからの経過時間を `u`、prompt長を `O_p,i`、最終output長を `O_d,i`、KV poolへ滞在するdecode時間を `T_i` とする。論文はrequestがactiveな間、KV token数を

`Q_i(u) = O_p,i + O_d,i × u/T_i`

のように線形増加すると近似し、request終了後は0とする。modelごとのactive KV bytesは、その時点で生きている全requestについてこれを足し、model固有の1-token KV bytes `κ(M)` を掛ける。最後に全modelを足して

`K_pool(t) = Σ_M K_M(t)`

を作る。 citeturn877467view0

重要なのは、**requestごとの最終KV peakを全部足していない**こと。random observation timeで実際に同時activeなKV量を再現し、trace-driven Monte Carloでaggregate demandのP95/P99を取る。prompt長・output長・service timeの相関もsample単位で保つため、「prompt P99 × output P99 × concurrency P99」のような過剰なworst-case積み上げを避けられる。

plannerは最終的に、共有KV poolのpage budgetと各modelのparallelism planを出す。

### 3. KV virtualizer: modelごとの仮想領域を作り、物理pageだけ共有する

online runtimeでは、各modelから見えるKV address spaceと、実際に消費するphysical HBM pageを分離する。

CrossPoolはCUDA VMMを使い、modelごとに大きな仮想KV領域をreserveする。requestがKVを必要とした時だけshared poolからphysical pageを割り当て、そのvirtual addressへmapする。attention kernel側には通常のpaged KV cacheとして見えるため、modelごとに巨大なcontiguous physical memoryを先取りする必要がない。 citeturn877467view0

複数DP rankから選べるmodelでは、新batchを最もfree KV pageが多いrankへ送る。active decodeのpageはrequest完了まで保持し、pool budgetを使い切った場合は、既存requestを途中で追い出すのではなく新規requestをqueueまたはrejectする。

この設計はKV compression/offloadとは違う。KV内容を削ったりCPUへ退避したりするのではなく、**GPU上のKV capacityをmodel横断でどこへ割り当てるか**をvirtualizeしている。

### 4. layer-wise pipeline: 2つのbatchをずらしてattention GPUとFFN GPUを同時利用する

pool分離の素朴な実装では、1 batchについて

`attention → transfer → FFN → transfer → 次layer attention`

を直列に実行する。この間、attention中はweight poolがidle、FFN中はKV poolがidleになり、GPU利用率が低い。

CrossPoolは2つのin-flight batchを持ち、異なるstageを重ねる。batch B1がKV poolでlayer `l` のattentionを実行している間、batch B2はweight poolで別layerのFFNを実行する。stage終了後のhidden-state transferも非同期に発行する。 citeturn877467view0

B1とB2は同じmodelである必要はなく、layer数も違ってよい。それぞれmodel ID、現在layer、completion stateを独立に持つため、一方が先に全layerを終えたらtokenをpublishして新batchへ差し替え、もう一方は自分のlayer cursorから続行する。

このため複数model間で「全員がlayer 10を終えるまで待つ」といったglobal barrierを設けず、heterogeneous cold modelsを混ぜられる。

### 5. persistent kernelと制御降ろし（control lowering）: layerごとのhost往復を避ける

layer-wise pipelineをCPU schedulerから細かく制御すると、各layerで

- kernel launch
- graph選択
- transfer開始
- completion確認
- 次batch選択

をhostが行うことになり、cold modelの小batchではCPU-GPU control overheadが相対的に大きくなる。

CrossPoolはwarmup時にattention subgraphとFFN subgraphを別々にCUDA Graphとしてcaptureし、そのhandleをGPU常駐persistent kernelへ渡す。persistent kernelはserving開始時から走り続け、GPU上のper-model queueをpollし、ready batchを選び、対応graphをdispatchし、pool境界ならNVSHMEM transferを起動し、completionを待ってbatch stateを更新する。 citeturn877467view0

host側はadmission、KV physical page mapping、failure handlingなどの低頻度処理だけを担当する。つまり高頻度なlayer state machineをGPU側へ「降ろす」ことで、disaggregationで増えたcontrol eventを隠す。

## 実装

prototypeはSGLang v0.5.10上に実装される。KV poolではSGLang既存のrequest scheduler、tokenizer、sampling、attention kernelを維持し、FFN layerだけproxy layerへ置換する。proxyはlocal attention後のhidden stateをweight poolへ送り、remote FFN outputを受け取って次layerへ進む。weight pool側ではSGLangのFusedMoE kernelを使う。 citeturn877467view0

pool間transportはNVSHMEMで実装し、同一server内NVLinkを使用する。KV virtualizerはCUDA VMMでphysical pageをmap/unmapする。現在の最適化pathではbatch size 1〜4をwarmup時にcaptureしており、cold-model decodeの小batchを主対象にしている。prefillは別のtemporal-multiplexing engineで処理し、CrossPoolの主評価はdecode側である。 citeturn877467view0turn178761view0

## 評価

### まず見るところ

- **実機:** 5× NVIDIA A100 40GB、NVLink接続のsingle server。
- **models:** Qwen3-30B-A3B、GLM-4.7-Flash、DeepSeek-V2-Liteの3 MoE。3 modelのweight合計は約154 GB HBM。
- **配置:** CrossPoolはGPU0をKV pool、GPU1〜4を3 model共通のFFN weight poolにする。
- **workload:** ShareGPTでdecode TBT、LongAlignでlong-context capacity。
- **baseline:** Static Partition、Chimera/kvcached。
- **主headline:** 0.8 RPS/modelでkvcached比P99 TBTをQwen3 **7.6×**、DeepSeek **10.4×**、GLM **7.3×**短縮。 citeturn178761view0

### long-context結果は「直接測定した全点throughput」ではない

LongAlign評価ではcontext length binごとにrequestをsampleし、各方式のGPU placementとKV budgetから、OOM/fatal failureに達する前の最大aggregate RPSを**推定**している。図のすべての点がend-to-end serving benchmarkで直接測ったthroughputという意味ではない。 citeturn178761view0

Static Partitionやkvcachedはcontextが長くなると、modelごとまたはDP replicaごとのKV capacityを使い切ってverticalなcapacity cliffへ達する。CrossPoolは同じ5 GPU budgetで1つの大きなKV poolを見せられるため、plotされたsupported long-context rangeのより先までpositive max RPSを維持する。

この結果が示すのは「CrossPoolのattention kernelがlong contextで速い」ことではなく、**1 requestが利用できるKV HBMの上限を大きくしたため、従来配置ではOOMになるcontextを収容できる**というcapacity improvementである。

### Static Partitionより常にlatencyが低いわけではない

ShareGPTの0.2〜1.0 RPS/model sweepでは、Static Partitionが最も低latencyを出す。各modelをisolated placementへ固定しているため、multi-model contentionやpool境界transferがないからである。 citeturn178761view0

CrossPoolが狙うのはStatic Partitionを純粋latencyで上回ることではない。Static Partitionはその代わり各modelのKV capacityが固定され、long-context poolingができない。CrossPoolは**長context収容能力を増やしつつ、elastic multi-model baselineよりtail latencyを安定させる中間点**を狙う。

kvcached比では、0.8 RPS/modelでP99 TBTがQwen3 7.6×、DeepSeek 10.4×、GLM 7.3×改善。1.0 RPSまで負荷を上げると改善幅は2.1×、5.0×、2.2×へ縮む。kvcachedでは複数modelが同じresourceへ非協調に重なり、SM・memory bandwidth・KV pressureがtailへ出やすいのに対し、CrossPoolはKV budgetとFFN execution poolを明示的に分けてresource usageを予測しやすくしている。 citeturn178761view0

### pipelineだけよりpersistent kernelとの組合せが重要

0.5 RPS/modelの3-model ShareGPT ablationでは、unoptimized disaggregated baselineが **55.42 token/s**。

- persistent kernel/control loweringだけ: **77.86 token/s（1.41×）**
- layer-wise pipelineだけ: **60.83 token/s（1.10×）**
- 両方: **111.40 token/s（2.01×）**

となる。 citeturn178761view0

単に2 batchをpipelineにしただけでは1.10×に留まり、host側の細かいcontrol overheadがまだ残る。逆にpersistent kernelだけでも1.41×改善するが、pool片側がidleになる時間は残る。両方を組み合わせることで、「GPUを同時に働かせる」と「その切替を安くする」の二つが噛み合い、2.01×になる。

この2.01×はCrossPool全体が既存systemより2.01×速いという意味ではなく、**CrossPool内部のunoptimized disaggregated executionに対するablation**である。

## 既存研究との差

MuxServe、Weaver、Chimera/kvcachedなども複数LLMのGPU共有やelastic memory allocationを扱う。しかし多くはweightとKVを同じGPU memory pool内で共存させるため、cold modelの巨大weightがKV capacityを圧迫する構造は残る。

CrossPoolはここを、**安定してmodelに結び付くFFN weightと、trafficに結び付くtransient KVを別物理poolへ置く**ことで分離する。

attention-MoE disaggregation自体はMegaScale-InferやStep-3などにもあるが、主目的はMoE compute scalingやheterogeneous multi-node throughputである。CrossPoolは同じattention/FFN分離を、**複数cold modelの共有KV capacityを最大化するため**に使う点が異なる。論文も典型配置を1〜2 nodeの低latency interconnectと位置付ける。 citeturn178761view0

またMooncake、LMCache、CacheGen、InfiniGenのようなKV offload/compression/streamingとも直交する。CrossPoolはKVをCPU/SSDへ逃がすのではなく、primary decode pathをGPU上に保ちながらmodel間でGPU KV memoryを共有する。

## 限界と適用境界

- **複数のcold MoEが主対象。** 単一hot modelではweight/KVを分けるstatistical poolingの利得が小さく、pool間通信だけが増える可能性がある。 citeturn178761view0
- **MoEほど有利。** FFN weight比が約95%の評価modelでは分離効果が大きいが、dense modelではKV poolから移せるweight割合が小さい。
- **低latency interconnect前提。** prototypeは同一server内NVLink + NVSHMEM。PCIeだけ、Ethernet/RDMA越しのmulti-nodeで同じTBTが出るとは示していない。 citeturn877467view0turn178761view0
- **hidden-state communicationは完全には隠れない。** attention→FFN、FFN→attentionのtransfer自体はcritical pathに残る。論文も4-stage finer pipelineをfuture workとして挙げる。 citeturn178761view0
- **heterogeneous model間のstage imbalance。** attention/FFN時間が大きく違うmodelを組み合わせると、短いstageが長いmodelを待ちpipeline efficiencyが落ちる。似たcompute profileのcold modelを同じpoolへまとめるplacementが必要。 citeturn178761view0
- **optimized batch sizeは1〜4。** cold decode向けのsmall batchを中心にgraph captureしており、高concurrency大batchでの最適化pathは別検証が必要。
- **prefillは主題外。** prefillは別engineで処理し、CrossPoolの主評価はdecode memory colocation、TBT、output throughputである。 citeturn178761view0
- **LongAlignのmax RPS図はcapacity estimationを含む。** すべてのcontext binの点を直接実機throughput測定と解釈しない方がよい。
- **共有poolのP95/P99 provisioningにはoverflow riskが残る。** plannerのquantileを超えるburstでは新requestをqueue/rejectするため、worst-case無停止を保証する構成ではない。

## 実装上の含意

CrossPoolの最も一般化しやすい教訓は、multi-model servingでmemoryを「model単位」だけでpartitionしないことにある。weight、KV cache、activationは寿命と変動性が違うため、**固定量とburst量を別poolへ分け、burst量だけをfleet横断で統計的に多重化する**とcapacityを節約できる。

ただし分離した瞬間にnetwork boundaryが生まれるため、何を境界越しに動かすかが重要になる。CrossPoolは「context長に比例して膨らむKVを動かさず、1 stepのhidden stateだけ動かす」という選択をしている。この原則はCPU/GPU/SSD階層やmulti-node disaggregationでも使える。

またshared memory plannerは、各dimensionのP99を独立に掛け合わせるより、実traceのprompt/output/service-time相関を保ったrandom-time aggregate demandを直接sampleする方が過剰provisioningを避けやすい。productionではこのplannerをtraffic telemetryから定期更新し、overflow時のqueue/reject policyまで一緒に設計する必要がある。
