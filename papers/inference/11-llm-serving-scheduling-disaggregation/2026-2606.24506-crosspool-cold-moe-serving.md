# CrossPool: Efficient Multi-LLM Serving for Cold MoE Models through KV-Cache and Weight Disaggregation

> **CrossPoolは、複数の低頻度MoEモデルで「常に大きいFFN weight」と「時々だけ大きくなるKV cache」を同じHBMへ押し込むのをやめ、weight用GPUとKV用GPUへ分けることで、modelごとの余ったKV容量を1つの共有poolとして使えるようにする。**

## 概要

LLM servingでは、人気modelだけでなく多数のmodelをAPI catalogへ常時載せておく必要がある。しかしtrafficは大きく偏り、論文が整理したOpenRouterのtoken消費分布では、modelの大半が低頻度な「cold model」側に位置する。こうしたmodelはrequestがほとんど来ていない時間でも、即時応答のためmodel weightをGPUへ置いておく必要がある。

特に疎な専門家混合（Mixture-of-Experts; MoE）モデルでは固定weightが大きい。CrossPoolが扱うQwen3-30B-A3BやDeepSeek-V2-Liteなどでは、parameterの大部分をFFN側が占める。一方KV cacheはrequest開始時に作られ、decodeが進むほど増え、request終了時に解放される。つまり同じHBMの中で、**ほぼ固定で巨大なweight**と、**trafficに応じて大きく変動するKV**が競合する。

cold modelでは各modelが同時にpeak KV需要へ達する確率は低い。model A/B/Cへそれぞれworst-case KV容量を固定予約するより、複数modelの実際の同時KV需要を1つの共有poolへまとめる方が、同じ総HBMから大きなburstを吸収しやすい。

ただし、既存のelastic multi-model servingでallocatorだけ共有しても、weightとKVが同じGPU poolに残る限り「空きHBMそのものがweightで少ない」という問題は消えない。そこでCrossPoolは、memory objectの寿命に合わせてGPUを二種類のpoolへ物理分離する。

- **KV pool**: attention、非FFN module、共有KV cacheを置く。
- **weight pool**: 複数MoE modelのFFN weightを集約する。

layer境界で両pool間を往復するのは巨大なKV tensorではなくhidden stateだけである。KVはcontext長に比例して増えるが、1 decode stepのhidden state量は過去context長そのものには比例しないため、長contextほどこの境界選択が重要になる。

## なぜKV head数の少ないmodelでは問題が深刻になるのか

4 GPUでattentionを実行する例を考える。KV head数が十分多い多頭注意（Multi-Head Attention; MHA）やグループ化クエリ注意（Grouped-Query Attention; GQA）では、tensor parallelismでKV headを複数GPUへ分散しやすい。1 requestが複数GPUをまたいで実行されるため、複数GPU分のKV capacityをまとめて利用できる。

一方、KV head数が少ないGQA、マルチクエリアテンション（Multi-Query Attention; MQA）、多頭潜在注意（Multi-head Latent Attention; MLA）では、data-parallel replicaを複数作る構成になりやすい。cold trafficでrequestが1本しか来ていなければ、そのrequestは1 replicaしか使わない。このため4 GPUのHBMがあっても、1 requestから見えるKV capacityは1/2や1/4に限られ得る。

高concurrencyなら複数replicaへrequestを散らして総HBMを使えるが、cold modelではその前提が成立しにくい。CrossPoolはattention/KV側をFFN weight配置から切り離し、低concurrencyでも大きな共有KV poolを見せることで、この「総HBMは余っているのに1 long-context requestがOOMする」状況を緩和する。

## 手法のあらまし

### 1. FFN weight poolとKV poolを分離する

transformer layerのdecodeは概ねattentionとFFNからなる。CrossPoolではattentionとlayer normalizationなどの非FFN部分をKV poolで実行し、attention後のhidden stateをweight poolへ送ってMoE FFNを計算する。FFN出力はKV poolへ戻され、次layerのattentionへ進む。

この設計では過去context全体のKVはattention GPUのlocal HBMに残る。pool境界を越えるhidden stateはbatch token数とhidden dimensionに依存するが、64K contextから128K contextになったからといって1 decode stepのtransfer量が2倍になるわけではない。

MoEではFFN parameter比率が高いため、この分離でKV pool側から追い出せるweight量が大きい。論文のmodelではFFN shareがおよそ95%に達するものがあり、dense modelよりCrossPoolのmemory分離効果が大きくなりやすい。

### 2. KV plannerは「各modelのpeakの総和」を予約しない

共有KV poolが小さ過ぎればburstでOOMし、大き過ぎればweight poolに割けるGPUを減らす。そこでoffline KV plannerがtraffic traceから必要容量を推定する。

request `i` のprompt長を `O_p,i`、output長を `O_d,i`、decode service timeを `T_i`、到着後の経過時間を `u` とする。論文はactive requestのKV token数を概ね

`Q_i(u) = O_p,i + O_d,i × u/T_i`

と近似し、request終了後は0とする。modelごとのactive KVを足し、さらに全modelについて

`K_pool(t) = Σ_M K_M(t)`

を作る。

重要なのは、requestごとの最終peak KVを単純加算しないこと。random observation timeで実際に同時activeになっているKV量をtrace-driven Monte Carloでsampleし、aggregate demandのP95/P99を取る。prompt長・output長・service timeの相関もsample単位で保つため、「prompt P99 × output P99 × concurrency P99」のような過剰provisioningを避けられる。

plannerは最終的に、共有KV poolのpage budgetと各modelのparallelism planを出す。

### 3. CUDA VMMでmodelごとの仮想KV領域と物理HBMを分離する

online runtimeではCUDA仮想メモリ管理（CUDA Virtual Memory Management; CUDA VMM）を使う。各modelには大きなvirtual KV address spaceをreserveするが、physical HBM pageはrequestが必要とした時だけshared poolから割り当てる。

このためmodelごとに巨大なcontiguous physical memoryを先取りする必要がない。複数data-parallel rankから選べる場合、新batchはfree KV pageが最も多いrankへ送る。active requestのpageは完了まで保持し、pool budgetを使い切った場合は既存requestを途中でevictするのではなく、新規requestをqueueまたはrejectする。

CrossPoolはKV compressionやCPU/SSD offloadとは異なる。KV内容を削ったり低bit化したりせず、GPU上のKV capacityをmodel横断でどこへ割り当てるかをvirtualizeする方式である。

### 4. layer-wise pipelineでKV GPUとFFN GPUのidleを減らす

素朴な分離では1 batchについて

`attention → hidden-state transfer → FFN → transfer → 次layer attention`

を直列実行する。この場合、attention中はweight poolがidle、FFN中はKV poolがidleになる。

CrossPoolは2つのin-flight batchをずらして処理する。batch B1がKV poolでattentionを実行している間、batch B2はweight poolでFFNを実行する。両batchは同じmodelである必要はなく、layer数が違っていてもよい。それぞれmodel ID、現在layer、completion stateを独立に持つため、全modelが同じlayer番号へ揃うglobal barrierを必要としない。

### 5. 永続kernel（persistent kernel）で細かい制御をGPUへ移す

layer-wise pipelineではstage切替が細かくなる。CPUが毎layerでkernel launch、graph選択、transfer開始、completion確認、次batch選択を行うと、小batchのcold servingではcontrol overheadが無視できない。

CrossPoolはwarmup時にattention subgraphとFFN subgraphをCUDA Graphとしてcaptureし、そのhandleをGPU常駐の永続kernel（persistent kernel）へ渡す。persistent kernelはper-model queueをpollし、ready batchを選び、対応graphをdispatchし、必要ならNVSHMEM transferを開始し、completionを待ってbatch stateを更新する。

host側はadmission、KV physical page mapping、failure handlingなど低頻度処理へ集中する。つまり高頻度のlayer state machineをGPU側へ降ろすことで、disaggregationが生む制御回数の増加を抑える。

## 実装

prototypeはSGLang v0.5.10上に構築される。KV poolでは既存のrequest scheduler、tokenizer、sampling、attention kernelを維持し、FFN layerをremote execution用proxyへ置換する。weight pool側ではSGLangのFusedMoE kernelを使用する。

pool間transportはNVSHMEM、interconnectは同一server内NVLink。KV virtualizerはCUDA VMMでpageをmap/unmapする。optimized pathではbatch size 1〜4をwarmup時にcaptureしており、cold-model decodeの小batchが主対象である。prefillは別engineで処理し、CrossPoolの主評価はdecode側に集中する。

## 評価

### 評価条件

主評価は1 server、5× NVIDIA A100 40GB、NVLink接続。CrossPoolはGPU0をKV pool、GPU1〜4をFFN weight poolとして使う。Qwen3-30B-A3B、GLM-4.7-Flash、DeepSeek-V2-Liteの3 MoEを同時提供し、3 modelのweight合計は約154 GB HBM。ShareGPTでdecodeのトークン間時間（Time Between Tokens; TBT）、LongAlignでlong-context capacityを評価する。

比較対象はmodelごとにresourceを固定するStatic Partitionと、elastic multi-model servingのChimera/kvcached。

### kvcachedに対するP99 TBTは大きく改善する

0.8 RPS/modelでは、kvcachedに対するP99 TBT短縮がQwen3で約 **7.6×**、DeepSeekで **10.4×**、GLMで **7.3×**。ただし1.0 RPS/modelまで負荷を上げると改善幅は約2.1×、5.0×、2.2×へ縮む。

kvcachedでは複数modelの実行が同じresourceへ非協調に重なり、SM、memory bandwidth、KV pressureの競合がtailへ出やすい。CrossPoolはKV budgetとFFN execution poolを明示的に分離することで、この干渉を制御しやすくする。

### Static Partitionより純粋latencyで常に速いわけではない

ShareGPTの0.2〜1.0 RPS/model sweepではStatic Partitionが最も低latencyを出す条件がある。各modelをisolated placementへ固定しているため、pool境界transferやmulti-model contentionがないからである。

したがってCrossPoolの価値は「固定分割よりすべてのlatency metricで速い」ことではない。Static PartitionではmodelごとのKV capacityが固定され、long-context burstへ柔軟にHBMを貸し借りできない。CrossPoolは**long-context収容能力を増やしつつ、elastic baselineのtail latencyを抑える**trade-offを狙う。

### LongAlignのmax RPSはcapacity estimationを含む

LongAlignではcontext length binごとにrequestをsampleし、各方式のGPU placementとKV budgetからOOMに達する前の最大aggregate RPSを推定する。このため図の全点を「実際にそのRPSでend-to-end servingした直接測定値」と解釈してはいけない。

ここで示している中心的な改善はattention kernelの計算速度ではなく、**1 requestから利用できるKV HBM上限を大きくして、従来配置ではOOMになる長contextを収容できること**である。

### pipelineとpersistent kernelは両方必要

0.5 RPS/modelの3-model ShareGPT ablationでは、unoptimized disaggregated baselineが **55.42 token/s**。persistent kernel/control loweringだけで **77.86 token/s（1.41×）**、layer-wise pipelineだけで **60.83 token/s（1.10×）**、両方で **111.40 token/s（2.01×）**になる。

pipelineだけではCPU-GPU制御overheadが残り、persistent kernelだけでは片側poolのidle時間が残る。両者を組み合わせて初めて「両poolを同時に働かせる」と「stage切替を安くする」が両立する。

この2.01×はCrossPool全体が既存systemより2.01×速いという意味ではなく、CrossPool内部のunoptimized disaggregated implementationに対するablationである。

## 既存研究との差

MuxServe、Weaver、Chimera/kvcachedなども複数LLMのGPU共有やelastic memory allocationを扱うが、weightとKVを同じGPU memory pool内で共存させる方式では、cold modelの巨大weightがKV capacityを圧迫する構造が残る。

CrossPoolは、**modelに固定的なFFN weightと、trafficに追従するtransient KVを別物理poolへ置く**。attention-MoE disaggregation自体は既存研究にもあるが、CrossPoolではそれを複数cold modelの共有KV capacity最大化へ使う。

Mooncake、LMCache、CacheGenなどのKV offload/streamingとも目的が異なる。CrossPoolはKVをCPU/SSDへ逃がさず、primary decode pathをGPU上に保ちながらmodel間でGPU KV memoryを共有する。

## 限界と適用境界

- **coldな複数MoEが主対象。** 単一hot modelではstatistical poolingの利得が小さく、pool間通信だけが増える可能性がある。
- **MoEほど有利。** dense modelではKV poolから追い出せるFFN weight割合が小さく、memory分離効果が弱い。
- **低latency interconnect前提。** prototypeは同一server内NVLink + NVSHMEM。PCIeのみ、Ethernet/RDMA越しmulti-nodeで同じTBTになるとは示していない。
- **hidden-state communicationは消えない。** attention→FFN、FFN→attentionの転送はcritical pathに残り、model間のstage imbalanceもpipeline efficiencyを下げ得る。
- **optimized batch sizeは1〜4。** 高concurrency大batchで同じ実装効率になるかは別途検証が必要。
- **prefillは主題外。** 主評価はdecode memory colocation、TBT、output throughput。
- **P95/P99 provisioningにはoverflow riskが残る。** plannerのquantileを超えるburstでは新requestをqueue/rejectする。

## 実装上の含意

CrossPoolから一般化しやすい原則は、multi-model servingでmemoryをmodel単位だけでpartitionしないことである。weight、KV cache、activationは寿命と需要変動が異なるため、**固定量とburst量を別poolへ分け、burst量だけをfleet横断で統計的に多重化する**設計が有効になり得る。

また分離した瞬間にnetwork boundaryが生まれるため、何を境界越しに動かすかが重要である。CrossPoolは「context長に比例して膨らむKVを動かさず、1 stepのhidden stateだけを動かす」という選択をしている。この考え方はGPU間だけでなくCPU/GPU/SSD階層の設計にも応用できる。
