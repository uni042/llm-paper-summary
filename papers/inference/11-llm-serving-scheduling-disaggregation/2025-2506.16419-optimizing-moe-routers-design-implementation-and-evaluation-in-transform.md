# Optimizing MoE Routers：6方式のルーティング特性とQwen1.5-MoEへの組込み

## 概要

Mixture-of-Experts（MoE）はTransformerのフィードフォワード層（FFN）を複数のエキスパートに置き換え、トークンごとに少数のエキスパートだけを実行する構造である。総パラメータ数を増やしても、各トークンが使うパラメータを抑えられる。ただし選択器であるrouterが偏ったエキスパートにトークンを集中させると、一部の計算資源だけが混雑し、他の資源が遊ぶ。逆に多様なエキスパートを使わせようとしてrouterを複雑化すると、選択器自体の演算量とメモリ負荷が増える。

本稿は新しい分散MoEサービング基盤を提案するのではなく、**routerの設計選択がパラメータ数、トークン処理遅延、選択分布の集中度、既存モデルへの組込み難度にどう効くか**を実装比較する研究である。比較対象はLinear、Attention、MLP、Hybrid、MLP-Hadamard、Hashの6種類。BERT-baseの学習済み隠れ状態を使う評価と、Qwen1.5-MoEのrouterを差し替えてLoRA微調整する実験を組み合わせる。

主な数値は、ランダム初期化入力に対する表IIでLinearが0.07ms、Attentionが0.29ms、MLPが0.23ms、Hybridが0.58ms、MLP-Hadamardが0.88ms、Hashが85.0msである。**Hashが理論的に軽量なのに実測で極端に遅い**という反例があり、単純な計算量だけではPython実装を含む実測遅延を説明できない。MLP-Hadamardはエントロピー1.1003と集中したエキスパート選択を示すが、集中は負荷分散の改善やタスク正答率向上と同義ではない。

## 問題設定：routerのコストと負荷偏り

### MoEの計算経路

通常のTransformer FFNは入力隠れ状態`x`に対して同じパラメータを適用する。MoEでは`E`個のエキスパート`F_e`を用意し、routerが各トークンに対する選択確率`p(e|x)`を求める。上位`k`個を選び、その出力を選択重みで加算する。モデルのパラメータ容量はエキスパート数に比例して増えるが、実行時には原則`k`個だけを使うため、密な全エキスパート実行より演算を抑えられる。

ただし選択が偏ると、複数GPUへ分散したエキスパートの通信量と待ち時間が不均等になる。単一GPUでもエキスパートごとのトークン数がばらつくとバッチ化効率が落ちる。routerのスコア分布が鋭いほど、同じエキスパートへトークンが集中する可能性があるが、実際の負荷分散にはトークン分布、Top-k、capacity、エキスパート配置も関与する。

この論文の測定は主にrouterモジュールの比較であり、GPU間all-to-allや複数同時要求を含む大規模サービングのend-to-end速度測定ではない。したがって、routerの単体遅延をそのままクラスタ全体のthroughputへ換算してはならない。

### 線形routerだけでは何が不足するか

一般的な線形routerは`softmax(Wx+b)`で各エキスパートのスコアを計算する。重み行列`W`の大きさはおおむね`E×H`であり、隠れ次元`H`に対して単純で高速である。しかしトークン特徴とエキスパート適性の関係が非線形なら、一段の線形変換だけでは表現しにくい。MLPやAttentionを使えば表現力を上げられるが、追加の射影や中間テンソル、softmaxが必要となる。

もう一つの選択肢は学習パラメータを持たないHashルーティングである。計算上は簡単でも、固定割当は入力分布の変化に適応しにくい。著者の実装では、Hashの実測遅延が他方式より桁違いに長く、理論上の軽さが実装の軽さを保証しないという結果になった。

## 手法

### 共通インターフェースとデータフロー

研究では各routerが`compute_router_probabilities`を実装する共通基底クラスを設ける。入力は形状`[B,S,H]`の隠れ状態、出力は`[B,S,E]`のエキスパート確率である。MoE層は確率上位`k`個のインデックスと重みを取り出し、選択した重みを合計1へ再正規化して各エキスパート出力を重み付き合成する。こうすることでrouterの内部実装を交換しても、MoE層の外部入出力形状を変えずに済む。

さらに選択数の偏りを測るため、エキスパート`e`へ送ったトークンの割合`f_e`と、routerが割り当てた平均確率`g_e`を求め、`α_aux E Σ_e f_e g_e`型の補助負荷分散損失を計算する。`f_e`は実際の割当、`g_e`は選択前の平均的な好みを表す。論文には平方項を含む別表現も併記されているため、実装再現時はどちらを実際のコードで使ったかを確認する必要がある。特にTop-kが複数なら`f_e`の定義上の総和が1でない場合があり、比較するエントロピーの定義と正規化も合わせる必要がある。

### Linear Router：単一射影

Linearは`p=softmax(Wx+b)`だけで選択確率を計算する。パラメータは隠れ次元とエキスパート数の積にほぼ比例し、行列積とsoftmaxだけなので実装が単純である。選択後は共通MoE層がTop-kと加重和を行う。追加の中間隠れ層を持たないため、同じ入力形状ではrouter自身の遅延が小さくなりやすい。一方、エキスパートへの適性が非線形な場合はスコア表現力が制約される。

### Attention Router：トークンと学習可能なエキスパートキー

Attentionは入力トークンを`W_q x`でクエリ空間へ写像し、各エキスパートに対応する学習可能なキーと内積を取る。スコアは`q K^T / (sqrt(d_k) τ)`で、温度`τ`が確率分布の鋭さを調整する。トークンとエキスパートを共通の特徴空間で照合する設計であり、単なる線形routerとはパラメータの分解と正規化方法が異なる。実装ではクエリ・キーをL2正規化し、適用可能なら高速注意カーネルを使い、そうでなければ通常のscaled dot-productに戻す。

エキスパートキーを学習するため、Qwen1.5-MoEの既存ゲートを単に置換するだけでは重み形状が一致しない。著者は`replace_qwen_routers()`でMoE層の`gate`と`experts`を再帰的に探索し、隠れ次元・エキスパート数・Top-kを読み取って新しいrouterを生成する。必要なら共有ゲートも置換する。LoRAの対象には従来の`q_proj/k_proj/v_proj/o_proj`に加え、新しいrouterの`query_proj`を含める。追加の射影と中間表現は、表現力の代償としてメモリと遅延を増やす。

### MLP Router：非線形な特徴変換

MLPは`h=σ(W1x+b1)`を計算してから`p=softmax(W2h+b2)`へ渡す。中間層の活性化により線形分離できないトークン特徴の組合せを扱えるが、2つの射影と活性化の演算が必要になる。隠れ層の大きさが増えるとrouterパラメータ数と中間テンソルも増える。原著では学習済みBERT埋め込みを使うとrouter出力の分布がランダム入力時と大きく変化し、入力の意味的構造に敏感であることを示している。ただし、分布が変化したことだけで最終タスクの精度が改善したとは言えない。

### Hybrid Router：線形とAttentionの組合せ

Hybridは線形スコアとAttentionスコアを併用し、固定または学習可能な重みで結合する。単純な特徴とエキスパートキー照合の両方を利用できる反面、双方の計算と統合処理が必要である。原著のランダム入力評価では6方式中Hashを除くと最も遅い側に入り、複雑なrouterが自動的に高速化をもたらすわけではないことを示す。混合の重みが入力分布や学習条件に依存するため、単純な足し算が常に精度改善になるわけでもない。

### MLP-Hadamard Router：要素積による特徴の強調

新規提案のMLP-Hadamardは、MLPで変換した特徴`h_mlp`と元入力`x`（必要なら射影した`x_p`）の**要素ごとの積**`h_hadamard=h_mlp⊙x_p`を取る。続く線形層がエキスパート確率へ変換する。要素積によって、元の特徴が大きい次元を強調し、対応しない次元を抑えるような相互作用を表現できる。単なる入力連結や線形スコアの足し算とは異なる。

著者は当初、パラメータなしのHadamard行列による決定的ルーティングを試したが、**全トークンが1エキスパートへ集中する失敗**が起きた。そこでHadamard行列を直交性を保つ構造的な正則化要素へ役割変更し、Top-k制約を加えた。修正版は2エキスパートへ集中する分布を示す。これは狙った疎化だが、全体の負荷均衡が改善した証拠ではない。固定的な集中が続けば、逆にホットスポットを作り得る。

### Hash Router：固定写像の実装依存性

Hashは入力トークン表現をハッシュ値へ変換し、`hash(x) mod E`で1つのエキスパートを決める。確率は選択先だけ1のone-hotで、学習パラメータは0である。一般に計算式だけ見れば軽量だが、原著の実装はトークンごとの処理やPython側の変換などにより極端に遅い可能性がある。実際の測定値は85.0msで、線形routerの0.07msから大幅に悪化する。原著はこの差を完全に要素分解していないため、Hash一般の速度劣位を主張する材料にはならない。

### ランダム入力での遅延・選択分布：表II

| Router | Token latency（ms） | Entropy | Mean top-k probability |
|---|---:|---:|---:|
| Linear | 0.07 | 1.9513 | 0.2129 |
| Attention | 0.29 | 2.0793 | 0.1273 |
| MLP | 0.23 | 2.0769 | 0.1361 |
| Hybrid | 0.58 | 2.0476 | 0.1686 |
| MLP-Hadamard | 0.88 | 1.1003 | 0.4152 |
| Hash | 85.0 | 0.0000 | 0.5000 |

この表のLatencyは**routerを含む実験系でのトークン処理遅延**であり、Qwen全モデルの1トークン生成時間やTTFTと同一ではない。LinearはAttentionの約4.1分の1、MLPの約3.3分の1の遅延で、表現力の高い設計ほど追加コストを払う傾向が見える。HybridはLinearの約8.3倍、MLP-Hadamardは約12.6倍である。一方、Hashは約1,214倍遅く、**パラメータ数0なら速い**という直感に反する。

Entropyはエキスパート選択の分布の広がりを測る量で、値が大きいほど広く分散する。8エキスパートなら一様分布の自然対数エントロピーは`ln 8 ≈ 2.0794`である。Attentionの2.0793とMLPの2.0769はほぼ一様に近く、MLP-Hadamardの1.1003は強く集中する。Hashの0は完全な決定的選択を表すが、全トークンが一つのエキスパートへ集中したか、トークンごとに異なる先へ一意に割り当てられたかは、この表の値だけで判別できない。

学習済みBERTの隠れ状態では、ランダム入力と異なるスコア分布が生じる。たとえばLinearのEntropyは1.9513から2.0680へ上がる。MLPの出力標準偏差0.06820はLinearの0.03083より大きく、活性化のスケールが変わる。これは実データ由来の隠れ状態に対するrouterの応答が異なることを示すが、**エキスパートの実際の処理負荷や最終的な正答率が良くなった証拠ではない**。付録のSelf-Supervisedは主要6方式とは別の探索的設計であり、主要比較表に混ぜない。

### Qwenのrouter差替えとLoRA学習

Qwen1.5-MoEは総14.3B、各トークンで約2.7Bを活性化し、60エキスパートからTop-4を選ぶ構造として紹介される。著者は既存ゲートをLinearまたはAttentionに差し替え、Tiny Shakespeare 100行で50ステップの微調整を実施した。Linear置換の学習損失は10ステップ付近で1.9086、20ステップで0.1569、30ステップで0.0027、50ステップで0.0006まで低下する。Attention置換は10ステップで9.645、20ステップで6.0565、30ステップで3.5086、40ステップで1.7095、50ステップで0.7318となる。

Linearの急速な損失低下は、著者自身が小規模データの暗記・過学習を疑っている。Attentionの損失がより高いことを「一般化が良い」「考え方が深い」と結論づける根拠はない。独立したテストセットの正答率・PPLや、同一計算予算での一般化比較がないため、ここから実運用の精度優位を確定できない。**この実験が示す中心成果は、量子化やLoRAの制約があるQwenへカスタムrouterを組み込んで学習を走らせられたこと**である。

### 負の結果と実装上の失敗

初期Hadamardルータは全トークンを一つのエキスパートへ送ってしまい、負荷偏りを生じた。Top-k制約と構造正則化へ変更した後に2エキスパートへの選択を実現したが、これが多GPUサービングの最適負荷分散を意味するわけではない。

Hashは理論上の軽さに反して85msと最遅だった。著者は具体的なPythonプロファイルやGPUカーネルの内訳を公開していないため、Hash方式一般が遅いと一般化しない。

QwenのGPTQ形式では重みがパックされた形で保存され、通常の`weight.data`を前提とする次元取得やLoRAチェックポイントのロードでunexpected keys、形状不一致が起きた。著者は量子化レイヤと通常レイヤの両方から入出力次元を推定する処理を追加し、routerの新規パラメータを明示的に生成して対応した。大きなバッチではA100でもメモリ圧迫が起き、FlashAttention非対応環境で遅延が増えたため、データの部分サンプリングを行った。**サンプルを減らして成立した動作確認を、量子化MoEの大規模実運用評価と読み替えない**ことが重要である。

## 既存研究との差

Switch TransformerやMixtralの標準的な線形Top-kルーティングは、単純で高速な選択器を使い、学習時の負荷分散補助損失で集中を抑える。Hash Layersは固定的なルーティングを使う。本稿は新しいMoE学習アルゴリズムそのものを提示するよりも、**これらの選択器を同一のMoEレイヤインターフェースへ入れ替え、速度・エントロピー・表現力を並べて比較**する点に重心がある。

MLP-Hadamardは入力特徴と変換特徴の要素積を加え、元のHadamard方式で生じた一エキスパート集中を修正する。Attention Routerはエキスパートごとに学習可能なキーを用意し、クエリとの照合をrouterの計算として使う。いずれも線形routerより多くの演算を使うため、表現力と実行コストの交換条件を直接見ることができる。

ただし原著の比較は標準化された大規模MoEサービングベンチマークではなく、既存方式に対する総生成時間・スループット・分散通信の改善倍率を示していない。推論インフラの実装選定では、ルータ単体の遅延よりも、トークン分布とexpert配置、通信、バッチ化、負荷均衡まで測る必要がある。

## 限界・再現性・実装状況

**評価の小規模性。** 主なrouter表はBERT由来特徴とランダム特徴の比較で、実運用Qwenの大規模トークン生成評価ではない。Qwen微調整はTiny Shakespeareの100行に限定され、50ステップの学習損失だけではモデル品質や推論性能を評価できない。表IIのバッチ条件の記述と本文の遅延定義にも不一致がある。

**性能の移植性。** Colab上のA100 40GB単一GPUで得たrouter遅延は、vLLMやSGLangなどの最適化された推論サーバーで同じになるとは限らない。実装言語・Pythonループ・attention kernelの有無・トークン数・expert数が異なれば順位が変わり得る。特にHashの85msは実装に起因する可能性が高く、Hash一般の計算複雑性を示す値ではない。

**品質評価の欠落。** Router entropyは分布の広がりを示す指標であり、正答率、PPL、推論時のバッチ効率、負荷均衡、専門家の質を直接測らない。MLP-Hadamardの低エントロピーを優れたモデル品質の証明として使わない。AttentionのLoRA損失がLinearより高いことから一般化が良いと推測することもできない。

**量子化モデルとの互換性。** Qwen1.5-MoE-A2.7BのGPTQ Int4 checkpointと16bit学習の記述が併存する。どの実験がどの重み表現で測られたかを完全に一対一対応づける表はない。元の量子化レイヤを入れ替える際にはパック済み重みのshape、LoRAのtarget modules、既存checkpointのkey名に注意する必要がある。

**コード公開。** 本文はGitHubからコードをcloneしたと説明するが、確認できる本文には公式リポジトリの安定URLが明記されていない。`code`は未確認として`null`にし、第三者コードを公式と推定しない。研究成果は原著PDFの手法・表I/II/IV・学習曲線を根拠として記録した。
