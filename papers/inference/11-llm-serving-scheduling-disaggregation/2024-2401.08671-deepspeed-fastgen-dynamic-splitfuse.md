# DeepSpeed-FastGen: High-throughput Text Generation for LLMs via MII and DeepSpeed-Inference

> 長いpromptを複数iterationへ分割し、短いprompt・prefill chunk・decode tokenを一定のtoken budgetへ組み合わせるDynamic SplitFuseにより、generation stallを抑えつつGPUを高throughput領域で動かすLLM serving system。

## 概要

DeepSpeed-FastGenは、continuous batchingを使うLLM servingで**長いpromptのprefillが進行中requestのdecodeを止め、token間latencyとtail latencyを悪化させる問題**を扱う。

vLLM型のschedulerではprompt processingとgenerationを別forwardとして扱うため、長いprefillを入れるとdecodeが待たされる。一方Orca型ではprompt全体をrunning batchへ混ぜられるが、長promptが1 iterationのwork量を急増させる。どちらもprompt長のばらつきがforward時間のばらつきへ直結しやすい。

DeepSpeed-FastGenは **Dynamic SplitFuse** を導入し、長いpromptは小さいchunkへ分割し、短いpromptは必要なら分割・結合して、decode tokenと合わせた各forwardの総token数をtarget付近へ揃える。これにより長prefillによるgeneration stallを避けながら、GPUをthroughputが飽和する領域で継続的に動かす。

systemとしてはDeepSpeed-MIIをserving frontend、DeepSpeed-Inferenceをbackendとし、blocked KV cache、continuous batching、高性能CUDA kernelとDynamic SplitFuseを統合する。

## 問題設定

LLM servingには大きくprefillとdecodeがある。prefillは多数tokenを一度に処理できるため計算効率は高いが、promptが長いほど単一forwardが長時間になる。decodeは各sequenceにつき通常1 tokenずつ進むため、interactive servingでは短い間隔で繰り返し実行したい。

長prefillを一括で優先すると、その間は既存sequenceのdecodeが進まずgeneration latencyが跳ねる。逆にdecodeだけを優先すると新requestのprefillが進まず、throughputやTTFTが悪化する。

論文はbatch内のsequence数よりも、**1 forwardで処理する総token数がforward latencyを強く決める**という観察から、schedulerの主要制御量をtoken数へ置く。

## 手法

### 1. Forward sizeをtoken数で制御する

実測では、forward latencyはsequence batch sizeより総forward token数との関係が強い。またtoken数が少ない領域ではweight readなどのmemory costが支配的で、token数を増やすほどthroughputが上がり、十分大きくなるとcompute-boundな飽和領域へ入る。

さらにtoken-throughput曲線が概ねconcaveであるため、一定量のworkを極端に大小の異なるforwardへ分けるより、複数forwardへ均等に配る方が総throughputを高めやすい。この観察をDynamic SplitFuseのtoken budget設計に使う。

### 2. 長いpromptを分割する

長promptを一度のprefillで処理せず、小さいchunkへ分けて複数iterationに跨って処理する。最終chunkを処理するまではgenerationへ移らない。

これにより1件の長promptが巨大なforwardを作って既存decodeを長時間止めることを避ける。

### 3. 短いpromptとdecodeを融合する

各iterationにtarget token budgetを設け、decode tokenに加えてshort promptやprompt chunkを組み合わせる。短promptでもbudgetを正確に埋めるため必要なら途中で分割する。

結果としてforward sizeを比較的一定に保ち、低token数でGPU utilizationが低いiterationと、長prefillで極端に遅いiterationの双方を減らす。

### 4. Blocked KV cacheとcontinuous batching

DeepSpeed-FastGenはDynamic SplitFuse単独ではなく、固定size blockで非連続にKVを保持するblocked KV cacheとcontinuous batchingを組み合わせる。requestのjoin / leaveを細粒度で扱いつつ、KV fragmentationを抑えてconcurrencyを確保する。

## 評価

### 条件

主要評価はLlama-2 7B / 13B / 70Bを用い、NVIDIA A100、H100、A6000でDeepSpeed-FastGenとvLLMを比較する。70Bでは4×A100-80GBのtensor parallel構成などを使用する。

throughput-latency curveに加え、interactive workload向けにprompt処理速度とgeneration速度のSLAを満たしたrequestだけを数える **effective throughput** を評価する。512 request、1〜32 concurrent clientsを用いる実験も行う。

### 主要結果

論文全体ではvLLMに対して以下を報告する。

- effective throughput: **最大2.3×**
- average latency: **最大2×低減**
- token-level tail latency: **最大3.7×低減**

特に長promptを含むworkloadで、prompt processingによるgeneration stallを抑えることでtail latencyとthroughputの両方を改善する。

Dynamic SplitFuseは各forwardのwork量をtarget付近へ揃えるため、平均性能だけでなくgeneration tokenが返る間隔のvarianceを小さくすることを狙っている。

## 既存研究との差

### Orcaとの違い

Orcaはiteration-level schedulingによりrequestをforward単位でjoin / leaveできるようにしたcontinuous batchingの基礎研究だが、prompt全体をrunning batchへ入れると長promptがiteration timeを大きくできる。

DeepSpeed-FastGenはiteration-level batchingの上で、**sequence数ではなく総token数をbudgetとしてpromptを分割・融合する**。

### vLLMとの違い

vLLMはPagedAttentionによるKV memory効率化とcontinuous batchingが中心である。DeepSpeed-FastGenもblocked KV cacheを使うが、主な新規性はprompt processingとgenerationをDynamic SplitFuseで同一token budgetへ組成し、long-prefill stallを減らす点にある。

### Sarathi / Sarathi-Serveとの関係

論文自身がSarathiのchunked prefillを類似手法として挙げる。両者とも長prefillを分割してdecodeと混ぜる点は近い。

DeepSpeed-FastGenはforward throughput曲線から**均一なtarget token countを作るために長promptをsplitし短promptをfuseする**設計を前面に出す。一方Sarathi-Serveはdecodeを毎iteration先に保護し、残ったtoken budgetへprefillを詰めるstall-free schedulingと、P99 TBT SLO・pipeline parallelismへの効果をより体系的に扱う。

したがって両研究は、2023〜2024年に独立に発展した「chunked prefill + decode混載」の近接枝として読むのが適切である。

## 限界

- 論文の主要比較対象は当時のvLLMであり、後発のSarathi-Serve、DistServe、SGLang等との同一条件比較はない。
- target token budgetはmodel・GPU・workloadに依存する。throughput飽和点がhardwareやkernelで変われば最適値も変わる。
- prefill / decodeを同じresource poolで処理するため、phaseごとにGPUを独立provisionしたい環境ではDistServe型のP/D disaggregationが別の選択肢になる。
- 評価modelはLlama-2中心で、MLAや極端なlong-context modelなど現代的architectureで同じforward-token則がどこまで成立するかは別途検証が必要。
- arXiv v1のpreprintであり、会議最終版に基づく追加評価は確認できない。

## 一般的な実装上の含意

continuous batchingでは「何sequence入っているか」だけでなく、**各iterationが実際に処理する総token量を安定させる**ことが重要である。

長prefillを不可分な仕事として扱わずchunk化すると、interactive decodeを止める最大時間を制御しやすくなる。同時にshort promptやdecodeだけでforwardが小さすぎる場合は、別のprefill workを融合してGPUを高効率領域へ押し上げられる。

この考え方は後のchunked prefill schedulerにも共通し、現代のserving runtimeでprefill chunk size / token budgetが主要なscheduling knobになった流れを理解する基礎になる。
