# DeepSpeed-FastGen: High-throughput Text Generation for LLMs via MII and DeepSpeed-Inference

> 長いプロンプトを小さく分割し、短いプロンプト・プリフィル 分割片・デコード トークンを毎回ほぼ同じ総トークン数になるよう混ぜることで、長いプリフィルがデコードを止める時間を抑えつつGPUを効率よく使うLLM 提供処理 システム。

## 概要

DeepSpeed-FastGenは、連続バッチ処理を使うLLM 提供処理で**長いプロンプトのプリフィルが進行中リクエストのデコードを止め、トークン間遅延と末尾 遅延を悪化させる問題**を扱う。

vLLM型のスケジューラではプロンプト 処理と生成を別順伝播として扱うため、長いプリフィルを入れるとデコードが待たされる。一方Orca型ではプロンプト全体を実行中の バッチへ混ぜられるが、長プロンプトが1 反復の処理量を急増させる。どちらもプロンプト長のばらつきが順伝播時間のばらつきへ直結しやすい。

DeepSpeed-FastGenは **動的分割融合** を導入する。これは、**長いプロンプトを小分けにし、短いプロンプトやデコード トークンと組み合わせて、各順伝播で処理する総トークン数をほぼ一定に保つ仕組み**である。

長いプロンプトは複数反復へ分割し、逆に短いプロンプトやデコードだけではGPUに渡す仕事が少なすぎる場合は複数リクエストを同じ順伝播へ混ぜる。これにより長プリフィルによる生成 停止を避けながら、GPUへ毎回ある程度まとまった仕事を与える。

システムとしてはDeepSpeed-MIIを提供処理 フロントエンド、DeepSpeed-Inferenceをバックエンドとし、ブロック単位のKVキャッシュ管理、連続バッチ処理、高性能CUDA カーネルと動的分割融合を統合する。

## 問題設定

LLM 提供処理には大きくプリフィルとデコードがある。プリフィルは多数トークンを一度に処理できるためGPUを効率よく使いやすいが、プロンプトが長いほど単一順伝播が長時間になる。デコードは各系列につき通常1 トークンずつ進むため、対話型 提供処理では短い間隔で繰り返し実行したい。

長プリフィルを一括で優先すると、その間は既存系列のデコードが進まず生成 遅延が跳ねる。逆にデコードだけを優先すると新リクエストのプリフィルが進まず、スループットやTTFTが悪化する。

論文はバッチ内の系列数よりも、**1 順伝播で処理する総トークン数が順伝播 遅延を強く決める**という観察から、スケジューラの主要制御量をトークン数へ置く。

## 手法

### 1. 1回のforwardで処理する総token数を揃える

実測では、順伝播 遅延は系列数より総順伝播 トークン数との関係が強い。トークン数が少なすぎると、モデル 重みを読む時間など固定コストの割合が大きく、GPUを十分使えない。トークン数を増やすとGPU利用効率が上がり、やがて追加トークンを増やしてもスループットが大きく伸びない飽和領域へ入る。

したがって、同じ総処理量を「極端に小さい順伝播」と「極端に大きい順伝播」へばらけさせるより、**毎回ある程度似た大きさの順伝播へ分ける方が安定して速い**。動的分割融合はこの性質を使う。

### 2. 長いpromptを分割する

長プロンプトを一度のプリフィルで処理せず、小さい分割片へ分けて複数反復に跨って処理する。最終分割片を処理するまでは生成へ移らない。

これにより1件の長プロンプトが巨大な順伝播を作って既存デコードを長時間止めることを避ける。

### 3. 短いpromptとdecodeを同じforwardへ混ぜる

各反復に「このくらいの総トークン数を処理したい」という目標を設け、デコード トークンに加えて短い プロンプトやプロンプト 分割片を組み合わせる。短プロンプトでも目標を大きく超える場合は途中で分割する。

結果として、仕事量が少なすぎてGPUが余る反復と、長プリフィルで極端に遅い反復の双方を減らす。

### 4. KV cacheも固定長blockで必要分だけ持つ

DeepSpeed-FastGenは動的分割融合単独ではなく、KVキャッシュを固定大きさ ブロックへ分け、リクエストの増減に応じて必要ブロックだけ確保する方式と連続バッチ処理を組み合わせる。

これにより長さの異なるリクエストが出入りしても、未使用メモリや細切れの空き領域を減らし、同時に処理できるリクエスト数を確保する。

## 評価

### 条件

主要評価はLlama-2 7B / 13B / 70Bを用い、NVIDIA A100、H100、A6000でDeepSpeed-FastGenとvLLMを比較する。70Bでは4×A100-80GBのtensor 並列の構成などを使用する。

スループットと遅延の関係に加え、対話型 ワークロード向けに、**設定したプロンプト処理速度と生成速度の目標を両方満たしたリクエストだけを数えるスループット**も評価する。論文ではこれを実効的 スループットと呼ぶ。

### 主要結果

論文全体ではvLLMに対して以下を報告する。

- 実効的 スループット: **最大2.3×**
- 平均 遅延: **最大2×低減**
- トークン単位 末尾 遅延: **最大3.7×低減**

特に長プロンプトを含むワークロードで、プロンプト 処理による生成 停止を抑えることで末尾 遅延とスループットの両方を改善する。

動的分割融合は各順伝播の処理量を目標付近へ揃えるため、平均性能だけでなく**遅いトークンが極端に遅れる状況**を減らすことも狙っている。

## 既存研究との差

### Orcaとの違い

Orcaは反復-level スケジューリングによりリクエストを順伝播単位で参加 / 離脱できるようにした連続バッチ処理の基礎研究だが、プロンプト全体を実行中の バッチへ入れると長プロンプトが反復 時間を大きくできる。

DeepSpeed-FastGenはその上で、**系列数ではなく総トークン数を予算としてプロンプトを分割・融合する**。

### vLLMとの違い

vLLMはPagedAttentionによるKV メモリ効率化と連続バッチ処理が中心である。DeepSpeed-FastGenもブロック単位のKVキャッシュ管理を使うが、主な新規性はプロンプト 処理と生成を同じトークン 予算へ組み込み、長いプリフィル 停止を減らす点にある。

### Sarathi / Sarathi-Serveとの関係

両者とも長プリフィルを分割してデコードと混ぜる点は近い。

DeepSpeed-FastGenは**各順伝播の総トークン数をできるだけ均一にする**設計を前面に出す。一方Sarathi-Serveはデコードを毎反復先に保護し、残ったトークン 予算へプリフィルを詰めることで、デコードの停止を避けることをより明確に扱う。

## 限界

- 論文の主要比較対象は当時のvLLMであり、後発のSarathi-Serve、DistServe、SGLang等との同一条件比較はない。
- 目標 トークン 予算はモデル・GPU・ワークロードに依存する。GPUやカーネルが変われば最適値も変わる。
- プリフィル / デコードを同じ資源 プールで処理するため、段階ごとにGPUを独立して増減したい環境ではDistServe型の分離方式が別の選択肢になる。
- 評価モデルはLlama-2中心で、MLAや極端な長文脈 モデルなど現代的構成で同じ性質がどこまで成立するかは別途検証が必要。
- arXiv v1のpreprintであり、会議最終版に基づく追加評価は確認できない。

## 一般的な実装上の含意

連続バッチ処理では「何系列入っているか」だけでなく、**各反復が実際に処理する総トークン量を安定させる**ことが重要である。

長プリフィルを不可分な仕事として扱わず分割片化すると、対話型 デコードを止める最大時間を制御しやすくなる。同時に短い プロンプトやデコードだけで順伝播が小さすぎる場合は、別のプリフィル 処理量を融合してGPUへ十分な仕事を与えられる。

この考え方は後の分割型 プリフィル スケジューラにも共通し、現代の提供処理 実行系でプリフィル 分割片 大きさ / トークン 予算が主要なスケジューリング 調整つまみになった流れを理解する基礎になる。
