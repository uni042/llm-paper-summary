# DeepSpeed-FastGen: High-throughput Text Generation for LLMs via MII and DeepSpeed-Inference

> 長いpromptを小さく分割し、短いprompt・prefill chunk・decode tokenを毎回ほぼ同じ総token数になるよう混ぜることで、長いprefillがdecodeを止める時間を抑えつつGPUを効率よく使うLLM serving system。

## 概要

DeepSpeed-FastGenは、continuous batchingを使うLLM servingで**長いpromptのprefillが進行中requestのdecodeを止め、token間latencyとtail latencyを悪化させる問題**を扱う。

vLLM型のschedulerではprompt processingとgenerationを別forwardとして扱うため、長いprefillを入れるとdecodeが待たされる。一方Orca型ではprompt全体をrunning batchへ混ぜられるが、長promptが1 iterationのwork量を急増させる。どちらもprompt長のばらつきがforward時間のばらつきへ直結しやすい。

DeepSpeed-FastGenは **Dynamic SplitFuse** を導入する。これは、**長いpromptを小分けにし、短いpromptやdecode tokenと組み合わせて、各forwardで処理する総token数をほぼ一定に保つ仕組み**である。

長いpromptは複数iterationへ分割し、逆に短いpromptやdecodeだけではGPUに渡す仕事が少なすぎる場合は複数requestを同じforwardへ混ぜる。これにより長prefillによるgeneration stallを避けながら、GPUへ毎回ある程度まとまった仕事を与える。

systemとしてはDeepSpeed-MIIをserving frontend、DeepSpeed-Inferenceをbackendとし、block単位のKV cache管理、continuous batching、高性能CUDA kernelとDynamic SplitFuseを統合する。

## 問題設定

LLM servingには大きくprefillとdecodeがある。prefillは多数tokenを一度に処理できるためGPUを効率よく使いやすいが、promptが長いほど単一forwardが長時間になる。decodeは各sequenceにつき通常1 tokenずつ進むため、interactive servingでは短い間隔で繰り返し実行したい。

長prefillを一括で優先すると、その間は既存sequenceのdecodeが進まずgeneration latencyが跳ねる。逆にdecodeだけを優先すると新requestのprefillが進まず、throughputやTTFTが悪化する。

論文はbatch内のsequence数よりも、**1 forwardで処理する総token数がforward latencyを強く決める**という観察から、schedulerの主要制御量をtoken数へ置く。

## 手法

### 1. 1回のforwardで処理する総token数を揃える

実測では、forward latencyはsequence数より総forward token数との関係が強い。token数が少なすぎると、model weightを読む時間など固定costの割合が大きく、GPUを十分使えない。token数を増やすとGPU利用効率が上がり、やがて追加tokenを増やしてもthroughputが大きく伸びない飽和領域へ入る。

したがって、同じ総workを「極端に小さいforward」と「極端に大きいforward」へばらけさせるより、**毎回ある程度似た大きさのforwardへ分ける方が安定して速い**。Dynamic SplitFuseはこの性質を使う。

### 2. 長いpromptを分割する

長promptを一度のprefillで処理せず、小さいchunkへ分けて複数iterationに跨って処理する。最終chunkを処理するまではgenerationへ移らない。

これにより1件の長promptが巨大なforwardを作って既存decodeを長時間止めることを避ける。

### 3. 短いpromptとdecodeを同じforwardへ混ぜる

各iterationに「このくらいの総token数を処理したい」というtargetを設け、decode tokenに加えてshort promptやprompt chunkを組み合わせる。短promptでもtargetを大きく超える場合は途中で分割する。

結果として、仕事量が少なすぎてGPUが余るiterationと、長prefillで極端に遅いiterationの双方を減らす。

### 4. KV cacheも固定長blockで必要分だけ持つ

DeepSpeed-FastGenはDynamic SplitFuse単独ではなく、KV cacheを固定size blockへ分け、requestの増減に応じて必要blockだけ確保する方式とcontinuous batchingを組み合わせる。

これにより長さの異なるrequestが出入りしても、未使用memoryや細切れの空き領域を減らし、同時に処理できるrequest数を確保する。

## 評価

### 条件

主要評価はLlama-2 7B / 13B / 70Bを用い、NVIDIA A100、H100、A6000でDeepSpeed-FastGenとvLLMを比較する。70Bでは4×A100-80GBのtensor parallel構成などを使用する。

throughputとlatencyの関係に加え、interactive workload向けに、**設定したprompt処理速度とgeneration速度の目標を両方満たしたrequestだけを数えるthroughput**も評価する。論文ではこれをeffective throughputと呼ぶ。

### 主要結果

論文全体ではvLLMに対して以下を報告する。

- effective throughput: **最大2.3×**
- average latency: **最大2×低減**
- token-level tail latency: **最大3.7×低減**

特に長promptを含むworkloadで、prompt processingによるgeneration stallを抑えることでtail latencyとthroughputの両方を改善する。

Dynamic SplitFuseは各forwardのwork量をtarget付近へ揃えるため、平均性能だけでなく**遅いtokenが極端に遅れる状況**を減らすことも狙っている。

## 既存研究との差

### Orcaとの違い

Orcaはiteration-level schedulingによりrequestをforward単位でjoin / leaveできるようにしたcontinuous batchingの基礎研究だが、prompt全体をrunning batchへ入れると長promptがiteration timeを大きくできる。

DeepSpeed-FastGenはその上で、**sequence数ではなく総token数をbudgetとしてpromptを分割・融合する**。

### vLLMとの違い

vLLMはPagedAttentionによるKV memory効率化とcontinuous batchingが中心である。DeepSpeed-FastGenもblock単位のKV cache管理を使うが、主な新規性はprompt processingとgenerationを同じtoken budgetへ組み込み、long-prefill stallを減らす点にある。

### Sarathi / Sarathi-Serveとの関係

両者とも長prefillを分割してdecodeと混ぜる点は近い。

DeepSpeed-FastGenは**各forwardの総token数をできるだけ均一にする**設計を前面に出す。一方Sarathi-Serveはdecodeを毎iteration先に保護し、残ったtoken budgetへprefillを詰めることで、decodeの停止を避けることをより明確に扱う。

## 限界

- 論文の主要比較対象は当時のvLLMであり、後発のSarathi-Serve、DistServe、SGLang等との同一条件比較はない。
- target token budgetはmodel・GPU・workloadに依存する。GPUやkernelが変われば最適値も変わる。
- prefill / decodeを同じresource poolで処理するため、phaseごとにGPUを独立して増減したい環境ではDistServe型の分離方式が別の選択肢になる。
- 評価modelはLlama-2中心で、MLAや極端なlong-context modelなど現代的architectureで同じ性質がどこまで成立するかは別途検証が必要。
- arXiv v1のpreprintであり、会議最終版に基づく追加評価は確認できない。

## 一般的な実装上の含意

continuous batchingでは「何sequence入っているか」だけでなく、**各iterationが実際に処理する総token量を安定させる**ことが重要である。

長prefillを不可分な仕事として扱わずchunk化すると、interactive decodeを止める最大時間を制御しやすくなる。同時にshort promptやdecodeだけでforwardが小さすぎる場合は、別のprefill workを融合してGPUへ十分な仕事を与えられる。

この考え方は後のchunked prefill schedulerにも共通し、現代のserving runtimeでprefill chunk size / token budgetが主要なscheduling knobになった流れを理解する基礎になる。
