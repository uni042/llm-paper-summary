# Andes: Defining and Enhancing Quality-of-Experience in LLM-Based Text Streaming Services

## 一文要約

LLMのstreaming responseを単純な生成速度ではなく、**最初のtokenが早く届き、その後もユーザーが読む速度に間に合うようtokenが途切れず届くか**で評価し、十分先まで生成済みのrequestを一時停止して、今すぐGPU時間が必要なrequestへ回すserving system。

## 問題設定

LLM servingではthroughput、TTFT、TPOTなどserver側のmetricがよく使われる。しかしstreaming textを人間が読む・聞く用途では、GPUがユーザーの消費速度よりはるかに速くtokenを生成しても、**すでに画面側へ十分な未読tokenが溜まっているなら、そのrequestをさらに先まで生成しても今の体感品質はほとんど上がらない**。

一方、新しいrequestが最初のtokenを待っていたり、表示済みtokenをユーザーが読み切りそうなのに次tokenがまだ生成されていなかったりすると、体感品質は大きく悪化する。

Andesはこの差を、各tokenがユーザーへ届き消費されるend-to-end timelineとして扱う。目標は全requestを単純に最速完了させることではなく、**ユーザーが必要とする時刻までに必要量のtokenを供給し、まだ不要な先行生成へGPUを使い過ぎないこと**である。

## 手法

### 1. 「ユーザーが必要な時刻までにtokenが届いたか」で品質を測る

各responseについて、

- 最初のtokenは十分早く届く
- その後は想定するreading / listening speed以上でtokenが供給される

という理想timelineを置き、実際のtoken deliveryがそこからどれだけ遅れたかを評価する。

論文ではこのuser-visibleな品質を **QoE（Quality of Experience）** と呼ぶ。単なるaverage TPOTとは違い、「序盤だけ長く待たされた」「途中でtoken表示が途切れた」といった体感差を区別できる。

### 2. 1 token生成の区切りでrequestを入れ替える

schedulerはrequestを一度batchへ入れたら完了まで固定するのではなく、token generationの区切りで実行requestを切り替えられる。

各requestについて、

- 今GPU時間を追加するとどれだけQoEが改善するか
- そのrequestがどれだけGPU memory / computeを使うか
- client側に未読tokenがどれだけ残っているか

を見て優先順位を決める。

すでにユーザーが消費できる量より十分先までtokenを生成済みのrequestは一時的に優先度を下げ、そのGPU時間を**最初のtoken待ちや、まもなく表示tokenが尽きるrequest**へ回す。

論文ではこの選択をknapsack型最適化として表すが、直感的には**限られたGPU枠を「今処理すると体感改善が大きいrequest」から埋める問題**である。

### 3. Request切替そのもののcostも考える

実行中requestを止めて別requestへ切り替える **preemption** は無料ではない。KV cacheやmemory配置の扱いなど追加costがあるため、理論上QoEが少し上がるだけで頻繁に切り替えると逆効果になる。

AndesはQoE改善量だけでなく切替costも考え、**切り替える価値がある場合だけrequestを入れ替える**。

### 4. Client側に少しtokenをbufferしてserver側の揺れを隠す

serverが先に生成したtokenをclient側でbufferし、想定する消費速度に合わせて表示する。

これによりnetwork jitterやserver schedulingの細かな揺れをそのままuser-visibleなstreamへ出さずに済む。またserver側は「このrequestにはしばらく表示できるtokenが残っている」と分かるため、その間GPUを別requestへ貸せる。

## 評価条件

論文はLLM text streaming workloadについて、vLLM等の既存serving方式と比較し、高負荷・bursty trafficを含む条件でQoEとresource efficiencyを評価する。ShareGPT等のconversation workload / traceを利用し、単純なthroughputだけでなくuser-side delivery timelineを評価対象にする。

## 主要結果

最新arXiv v2のabstractでは、同じGPU resourceで既存のstate-of-the-art serving systemに対し**平均QoEを最大4.7×改善**し、同じ高QoEを維持する条件では**GPU resourceを最大61%削減**したと報告している。

重要なのは、改善源が単なるkernel高速化ではない点である。人間がまだ消費できないtokenを過剰に先行生成するcomputeを抑え、その余力をTTFT待ちやstream starvationの危険が高いrequestへ振り替えることで、同じhardwareでもuser-visibleなservice qualityを上げる。

ここでstream starvationは、**ユーザー側の未読tokenが尽き、次tokenを待って表示が止まる状態**を指す。

## 既存研究との差

- **Orca / vLLM:** continuous batchingやKV memory efficiencyでGPU throughputを高めるのが中心。Andesはその上で「誰の次tokenを今生成するとuser experienceが最も改善するか」をschedulerの目的にする。
- **FastServe:** token / iteration boundaryでrequestを一時停止できる点は近いが、主眼はjob latency / queue待ち。Andesはresponse completionの速さではなく、streamを人間が消費するtimelineからpriorityを決める。
- **Sarathi-Serve:** chunked prefillでdecode stallとthroughput-latency tradeoffを改善するのに対し、Andesはuser consumption speedまで含むQoEを直接最適化する。
- **VTC / fairness系:** client間service量の公平性を目的にするのに対し、Andesは各requestの現在のbuffer余裕と「今処理したときのQoE改善量」に基づいてresourceを再配分する。

## 一般的な実装上の含意

interactive LLMでは「GPUが生成できる速度」と「ユーザーがtokenを必要とする速度」は同じではない。したがってschedulerが**client buffer残量や、次tokenが必要になる時刻**を把握できるなら、先行生成を意図的に遅らせてもQoEを落とさずcapacityを別requestへ貸せる。

これはchatだけでなく、speech synthesis、translation、agent UIなどoutputを逐次消費するapplicationにも一般化しやすい。一方、machine-to-machine agentのように生成tokenを即座に次のcomputeへ使うworkloadでは、人間のreading rateを前提にした余裕は小さくなり、同じ利得は期待できない。

## 限界

- QoEは想定するuser consumption rateに依存する。実際のreading / listening speedはuser・language・taskで異なる。
- client-side pacingが有効なのは、先行生成tokenをすぐ表示しなくても問題ないinteractive streaming用途が中心。
- preemptionにはKV state / memory managementのoverheadがあり、頻繁に切り替えれば必ずよいわけではない。
- outputを人間ではなく別model / toolが即時消費するagent workloadでは、QoE定義をそのまま適用しにくい。
