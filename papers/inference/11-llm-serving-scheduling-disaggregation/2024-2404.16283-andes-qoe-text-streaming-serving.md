# Andes: Defining and Enhancing Quality-of-Experience in LLM-Based Text Streaming Services

## 一文要約

LLMのstreaming responseをserver側のthroughputだけで評価せず、**最初のtokenが早く届き、その後はユーザーが消費できる速度で途切れず届くこと**をQoEとして定式化し、token単位のpreemptive schedulingとclient-side pacingで、burst時にも限られたGPUをQoE改善効果の高いrequestへ優先配分するserving system。

## 書誌情報

- Authors: Jiachen Liu, Jae-Won Chung, Zhiyu Wu, Fan Lai, Myungjin Lee, Mosharaf Chowdhury
- arXiv: 2404.16283
- Initial release: 2024-04-25
- Latest arXiv version used here: v2
- Category: LLM Serving / Scheduling / Disaggregation

## 問題設定

LLM servingではthroughput、TTFT、TPOTなどserver側のaggregate metricがよく使われる。しかしstreaming textを人間が読む・聞く用途では、GPUがユーザーの消費速度よりはるかに速くtokenを生成しても、その先行生成分はその時点の体感品質を改善しない。一方、burstで新しいrequestのTTFTが伸びたり、表示tokenが途中で枯れたりすると体感品質は大きく悪化する。

Andesはこのずれを、各tokenがユーザーへ届き消費されるend-to-end timelineとして扱う。目標は単純に全requestを最速完了させることではなく、**ユーザーが必要とする時刻までに必要量のtokenを供給し、余分な先行生成へGPUを使い過ぎないこと**である。

## 手法

### 1. Text streaming向けQoE

各responseについて、最初のtokenが十分早く届き、その後のtokenが想定するreading / consumption rateに沿って利用可能になる理想timelineを置く。実際のtoken deliveryがそこからどれだけ遅れるかを使い、interaction全体のQoEを評価する。

これにより、同じcompletion timeや平均TPOTでも「序盤で待たされる」「途中でtoken供給が止まる」といった体感差を区別できる。

### 2. Token-level preemptive scheduler

schedulerはrequestを一度batchへ入れたら完了まで固定するのではなく、token generationの途中で実行requestを切り替える。各requestについて、短い将来windowで追加GPU serviceを与えた場合のQoE gainとresource demandを評価し、限られたGPU capacityへどのrequestを載せるかを決める。

すでにユーザーが消費できる量より十分先までtokenを生成済みのrequestは一時的に優先度を下げ、そのGPU時間をTTFT待ちやtoken不足が近いrequestへ回す。選択問題はresource constraint付きのknapsack型として扱い、実行時に使えるheuristicで近似する。

### 3. Preemption overheadの考慮

requestの入れ替えはKV cache / memory状態の扱いなどoverheadを伴うため、理論上のQoE gainだけで頻繁にpreemptすると逆効果になり得る。Andesはresource usageと切替costを考慮してscheduleをrefineし、QoE改善とpreemption overheadを両立させる。

### 4. Client-side token pacer

serverが先に生成したtokenをclient側でbufferし、想定する消費速度に合わせて表示する。network jitterやserver schedulingの細かな揺れをuser-visibleなstreamへ直接出さず、server側ではbufferの余裕を利用して別requestへcomputeを回せる。

## 評価条件

論文はLLM text streaming workloadについて、vLLM等の既存serving方式と比較し、高負荷・bursty trafficを含む条件でQoEとresource efficiencyを評価する。ShareGPT等のconversation workload / traceを利用し、単純なthroughputだけでなくuser-side delivery timelineを評価対象にする。

## 主要結果

最新arXiv v2のabstractでは、同じGPU resourceで既存のstate-of-the-art serving systemに対し**平均QoEを最大4.7×改善**し、同じ高QoEを維持する条件では**GPU resourceを最大61%削減**したと報告している。

重要なのは、改善源が単なるkernel高速化ではない点である。人間がまだ消費できないtokenを過剰に先行生成するcomputeを抑え、その余力をTTFT待ちやstream starvationの危険が高いrequestへ振り替えることで、同じhardwareでもuser-visibleなservice qualityを上げる。

## 既存研究との差

- **Orca / vLLM:** continuous batchingやKV memory efficiencyでGPU throughputを高めるのが中心。Andesはその上で「誰の次tokenを今生成するとuser experienceが最も改善するか」をschedulerの目的関数にする。
- **FastServe:** token / iteration boundaryでpreemptionできる点は近いが、主眼はjob latency / HOL blocking。Andesはresponse completionの速さではなく、streamを人間が消費するtimelineからpriorityを決める。
- **Sarathi-Serve:** chunked prefillでdecode stallとthroughput-latency tradeoffを改善するのに対し、Andesはuser consumption speedまで含むQoEを直接最適化する。
- **VTC / fairness系:** client間service量の公平性を目的にするのに対し、Andesは各requestの現在のbuffer余裕と将来のQoE gainに基づいてresourceを再配分する。

## 一般的な実装上の含意

interactive LLMでは「GPUが生成できる速度」と「ユーザーがtokenを必要とする速度」は同じではない。したがってschedulerがTTFT / TPOT / completion latencyだけでなく、**client buffer残量や消費deadlineに相当する状態**を持てるなら、先行生成を意図的に遅らせてもQoEを落とさずcapacityを別requestへ貸せる。

これはchatだけでなく、speech synthesis、translation、agent UIなどoutputを逐次消費するapplicationにも一般化しやすい。一方、machine-to-machine agentのように生成tokenを即座に次のcomputeへ使うworkloadでは、人間のreading rateを前提にしたslackは小さくなり、同じ利得は期待できない。

## 限界

- QoEは想定するuser consumption rateに依存する。実際のreading / listening speedはuser・language・taskで異なる。
- client-side pacingが有効なのは、先行生成tokenをすぐ表示しなくても問題ないinteractive streaming用途が中心。
- preemptionにはKV state / memory managementのoverheadがあり、scheduler policyだけを理想化して頻繁に切り替えることはできない。
- outputを人間ではなく別model / toolが即時消費するagent workloadでは、QoE定義をそのまま適用しにくい。
