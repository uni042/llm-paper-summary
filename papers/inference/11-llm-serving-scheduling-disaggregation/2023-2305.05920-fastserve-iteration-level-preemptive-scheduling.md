# FastServe: Iteration-Level Preemptive Scheduling for Large Language Model Inference

> output tokenを1つ生成する区切りでrequestを一時停止・再開できるようにし、短いrequestを優先しながらKV cacheをCPUへ退避・先読みして待ち時間を減らすLLM serving scheduler。

## 概要

OrcaやvLLMのcontinuous batchingでは、新しいrequestを途中からbatchへ入れられる。しかし一度実行を始めたrequestを基本的に最後まで続けると、長いrequestがGPU枠とKV memoryを長く占有し、後から来た短いrequestが待たされる。

FastServeはこの問題に対して、**output tokenを1つ生成するたびにrequestを一時停止できるscheduler**を導入する。短そうなrequestを先に進め、長いrequestは一時的に後回しにすることで、queueでの待ち時間を減らす。

ただし一時停止したrequestのKV cacheをすべてGPUに残すとVRAMが足りなくなる。そこでFastServeは、すぐには再開しないrequestのKVをCPU DRAMへ移し、再開時刻を予測して必要になる前にGPUへ戻す。

## 問題設定

continuous batchingを使っても、実行中requestを完了まで止めない方式では、outputが長いrequestが後続requestを待たせる。

特に負荷が高い環境では、model計算そのものより**queueで待つ時間**がlatencyの大きな割合を占める。そのためkernelを速くするだけでは改善しきれない。

一方、requestを頻繁に一時停止するとKV cacheが増える。KVをGPUへ残せばVRAMを圧迫し、捨てれば再計算が必要になるため、schedulerとKV memory管理を一緒に設計する必要がある。

## 手法

### 1. 1 tokenごとにrequestを一時停止できる

FastServeはdecodeで1 tokenを生成した直後を切り替え地点にする。Transformerの途中で止めるのではないため、複雑な内部状態を保存する必要がない。

毎回schedulerが、

- 今のrequestを続ける
- より優先度の高いrequestへ切り替える

のどちらかを選ぶ。

### 2. 短いrequestを優先しつつ、長いrequestも放置しない

FastServeはOSで使われる複数段階のpriority queueをLLM向けに調整している。論文では **skip-join Multi-Level Feedback Queue（MLFQ）** と呼ぶ。

- prompt lengthから最初のtoken生成costを推定し、最初から適切なpriority queueへ入れる。
- 実行時間が長いrequestは低いpriorityへ送る。
- starvation防止機構で長時間待ったrequestを永久に後回しにしない。

output lengthそのものは事前に分からなくても、既知のinput lengthを使ってclassic MLFQより無駄なdemotionを減らす。

### 3. 一時停止中のKVをCPUへ移す

すぐ再開しないrequestのKV cacheはhost memoryへ退避する。

再開が決まってから戻すのではなく、queue状態から次に必要になるKVを事前uploadし、GPU計算とasynchronous transferを重ねてswap待ちを隠す。

### 4. 大型modelでは分散実行も統合

tensor parallelismとpipeline parallelismを使うlarge modelでは、KV cache managerも複数GPUへ分散し、pipeline内で複数batchを同時進行させてbubbleを減らす。

## 評価

NSDI 2026最終版の公式ページでは、vLLMと比較して**同じlatency条件でthroughputを最大6.1倍改善**したと報告している（USENIX NSDI 2026公式abstract）。

評価は実機で行われ、主なtestbedはAWS EC2 p4d.24xlarge 2台、合計16枚のNVIDIA A100 40GB GPU。ShareGPT / Alpaca由来workloadを用いる。

### 版による評価値の注意

arXiv上のprepublication版は、average latency SLOで最大31.4倍、tail latency SLOで最大17.9倍など、NSDI 2026公式ページより大きなheadline値を記載している。これらは**別versionの数値**なので、本ページの代表結果には混在させず、最終採択版として公開されているUSENIX側の6.1倍を優先する。

## 既存研究との差

### Orca / vLLMとの違い

OrcaとvLLMはtoken生成ごとにbatchを組み替えられるが、FastServeはそのiteration boundaryを**request自体のpreemption point**として使い、priority schedulerで実行順を変える。

### Sarathi-Serveとの違い

Sarathi-Serveは長いprefillを小分けにしてdecodeとの干渉を抑えることが中心。FastServeはdecode中requestを含めたjob全体の優先順位とpreemptionを扱う。

### Llumnixとの違い

FastServeはserving instance内でrequestの実行順とKV placementを変える。Llumnixは実行中requestを別instanceへmigrationし、GPU間load imbalanceを調整する。

## 限界

- model/hardwareごとのiteration costに依存するため、GPU・kernel stackが変わればprofileを取り直す必要がある。
- request長がほぼ均一ならshort-job優先の利点は小さい。
- KV swapはhost DRAM容量とPCIe bandwidthを使うため、host側が混雑すると効果が下がる。
- priority schedulerはlatencyを改善する一方、長いjobへのfairness / tail latency対策が必要。
- arXiv prepublicationとNSDI 2026 finalではheadline評価値が変わっているため、versionを跨いで数値を比較・合成しないことが重要。

## 一般的な実装上の含意

LLM servingではoutput lengthを正確に予測できなくても、input lengthや既に消費したGPU timeを使ってFCFSより細かいpreemptive schedulingを作れる。

ただしpreemptionを導入するとstarted-but-not-finished requestのKV stateが増える。したがって**schedulerだけでなく、KVのGPU/host placementとprefetchを同時設計する**必要がある。

## コード

公式実装 `LLMServe/FastServe` が公開され、preemptive scheduling、continuous batching、proactive memory swapping、PagedAttention、tensor / pipeline parallelismとartifact evaluation手順を含む。

## 引用関係

- Orca / vLLMのiteration-level schedulingを基礎に、job-level preemptionとpriority schedulingを追加する。
- KV swappingをschedulerへ統合するため、KV offload系研究とも接点がある。
- 後続のmigration/disaggregation系とは、queueing delayとresource stateをjointly扱う方向で関連する。
