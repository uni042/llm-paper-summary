# FastServe: Iteration-Level Preemptive Scheduling for Large Language Model Inference

> output tokenごとのpreemptionと入力長を使ったpriority設定で長いrequestによるhead-of-line blockingを避け、preemptされたrequestのKV cacheはCPUへ先回りswapしてGPU memory圧迫を抑えるLLM serving scheduler。

## 概要

FastServeは、continuous batching / iteration-level schedulingを使っていても、FCFSで一度batchへ入ったrequestを完了まで走らせると、長いrequestが短いrequestを待たせる**head-of-line blocking**が残ることを問題にする。

requestのoutput lengthは事前には分からない一方、input lengthは既知で、prefill時間や各decode iterationの実行時間はhardware / modelごとに比較的予測しやすい。FastServeはこの情報を使い、**各output token生成後にrequestをpreemptできるpriority scheduler**を導入する。

ただしpreemptionを増やすと、実行待ちrequestのKV cacheまでGPUに保持する必要が生じる。そこで低priority requestのKVをCPU DRAMへ退避し、次に使う時刻を予測して必要になる前にGPUへ戻すproactive swappingを組み合わせる。

初期preprintは `Fast Distributed Inference Serving for Large Language Models` という題名だったが、NSDI 2026最終版では現在の題名に変更され、評価も更新されている。本ページでは最終版の数値を優先する。

## 問題設定

OrcaやvLLMはiteration単位でbatchへrequestを追加・削除できるため、従来の固定batchよりLLM servingに適している。しかしFCFSでrunning requestをrun-to-completionにすると、output lengthが長いrequestがGPU slotやKV memoryを長時間占有し、後着の短いrequestのqueueing delayが大きくなる。

論文のShareGPT / Alpaca workloadでは、負荷が高い条件でend-to-end latencyの大部分をqueueing delayが占める。つまりkernel自体を高速化するだけではtail latencyを十分下げられない。

一方で単純なpreemptionは、preemptしたrequestのKVをGPUに残すとVRAMを圧迫し、捨てると再計算costが大きい。この**schedulerとKV memory managementを一体で扱う必要がある**のがFastServeの問題設定である。

## 手法

### 1. Output tokenごとのpreemption

FastServeは各decode iteration、つまり1 token生成の境界をpreemption pointとして使う。

batch内のrequestが1 tokenを生成したあと、同じrequestを続行するか、よりpriorityの高いrequestへslotを譲るかをschedulerが決める。Transformerの1 iteration途中を止めないため、operator stateを複雑に保存する必要がない。

### 2. Skip-join MLFQ

classicなMulti-Level Feedback Queue（MLFQ）は新規jobを最上位queueへ入れ、長く走るjobを順に低priorityへ落とす。しかしLLMでは長いpromptのprefillだけで最初のquantumを使い切りやすく、単純MLFQでは不要なdemotionが増える。

FastServeはmodel / hardwareのprofileから新規requestのprefill時間を見積もり、その時間を収められる**最も高いpriority queueへ直接入れる**。それより上のqueueをskipするため `skip-join` と呼ぶ。

output lengthは未知なので、実行を続けてquantumを使い切ったrequestは通常のMLFQと同様に低priorityへ移す。長いrequestが永久に後回しにならないよう、一定時間待ったrequestを最上位へ戻すstarvation preventionも入れる。

### 3. Proactive KV cache swapping

preempted requestが増えるとKV cache総量が大きくなる。FastServeはinactiveなrequestのKVをCPU DRAMへoffloadし、GPUには近いうちに実行するrequestのKVを優先して置く。

単純なreactive swapでは、requestを再開すると決まってからKVをGPUへ戻すためPCIe transferがcritical pathに入る。FastServeは各requestの**次回schedule予想時刻**を見積もり、必要になる前にswap-inを開始する。逆に次回実行が遠いrequestからswap-outする。

これによりKV transferを別requestのGPU計算と重ねる。

### 4. 分散実行

FastServeのruntimeはcontinuous batchingに加え、tensor parallelismとstreaming pipeline parallelismを実装する。大きいmodelでもscheduler自体はrequest-level priorityを維持し、各stageがiteration単位で協調して実行する。

公式実装はPython frontendとC++のSwiftTransformerを組み合わせ、custom attention kernel / paged attentionも利用する。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Cluster | AWS EC2 p4d.24xlarge ×2 |
| GPU | NVIDIA A100 40GB、各node 8枚 |
| Host memory | 各node 1152GB |
| Interconnect | node内NVLink、CPU-GPU PCIe 4.0 x16 |
| Models | OPT-13B / 66B / 175B、Llama3-8B |
| Precision | FP16 |
| Workloads | ShareGPT、Alpaca、synthetic |
| Baselines | FasterTransformer 5.3、vLLM 0.6.1、FastServe-FCFS |

OPT-13Bは1 GPU、OPT-66Bは4 GPU、OPT-175Bは16 GPUで評価し、Llama3-8BではGQAでも効果が残るかを確認する。

### 主要結果

同じlatency SLOを満たすthroughputで、FastServeはvLLMに対して**2.1〜6.1倍**の改善をShareGPTで報告する。AlpacaでもvLLM比**2.75〜3.5倍**だった。

P95 tail latencyのSLOで見ても、vLLMに対して最大**8.1倍**のthroughput改善を報告しており、短いrequestを優先することで平均だけを良くして長いrequestを極端に悪化させる設計ではない。

GQAを使うLlama3-8Bでも、vLLM比でShareGPT **2.1倍**、Alpaca **3.0倍**のthroughput改善を示す。

### Scheduler / swappingのablation

skip-join MLFQはFCFS、naive MLFQ、固定priorityに対して、条件によりそれぞれ最大**8.9倍、1.87倍、13.9倍**低いnormalized latencyを示す。

proactive KV swappingは、KVを捨てて再計算する方式より最大**2.7倍**、必要になってからswapするreactive方式より**1.7倍**高速だった。FastServeではswap時間がend-to-end latencyの5%未満に抑えられている。

## 既存研究との差

### Orca / vLLMとの違い

Orcaはiteration-level scheduling、vLLMはそこへPagedAttentionを加えるが、基本的にはFCFSでrunning requestを完了まで継続する。

FastServeはiteration-level schedulingを**preemption pointとして利用**し、request priorityを動的に変えてhead-of-line blocking自体を減らす。

### Sarathi-Serveとの違い

Sarathi-Serveは長いprefillをchunkへ分け、decodeをstallさせないことに重点を置く。FastServeは長いoutputも含むrequest全体のqueueing delayを対象にし、decode途中でもrequestをpreemptする。

### Llumnixとの違い

FastServeは1つのserving replica内でどのrequestを次に実行するかを最適化する。Llumnixはさらに上位でrunning requestを別replicaへlive migrationし、instance間のload imbalanceを修正する。

## 限界

- schedulerはmodel / hardwareごとのiteration latency profileを使うため、hardware構成やkernelが変わればprofile更新が必要になる。
- preemptionの利得はrequest length分布が不均一なworkloadほど大きく、長さが均一でqueueing delayが小さい場合は改善余地も小さい。
- proactive swapはhost DRAM容量とhost-device bandwidthを使うため、PCIe競合やCPU memory pressureが強い環境では利得が減り得る。
- end-to-end評価の中心はA100とOPT系列で、Llama3-8BのGQA評価はあるものの、Hopper / BlackwellやMLA系modelは未評価。
- priority / starvation parameterはSLOに合わせた調整が必要で、すべてのservice policyを自動で導出するsystemではない。

## 一般的な実装上の含意

LLM servingではoutput lengthが未知でも、**「全部分からないからFCFS」まで後退する必要はない**。input lengthとiteration profileだけでも、長いrequestがqueueを塞ぐ可能性をかなり避けられる。

またpreemptive schedulingを導入するなら、schedulerだけでなくKV residencyまで一緒に設計する必要がある。preemptionで増えたpending stateをCPU memoryへ逃がし、そのtransferを次回schedule予測で先回りさせることで、priority schedulingとmemory capacityを両立できる。
