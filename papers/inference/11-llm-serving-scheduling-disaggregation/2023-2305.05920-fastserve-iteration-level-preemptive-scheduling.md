# FastServe: Iteration-Level Preemptive Scheduling for Large Language Model Inference

> 出力トークンを1つ生成する区切りで要求（request）を一時停止・再開できるようにし、短い要求を優先しながらKVキャッシュ（KV cache）をCPUへ退避・先読みして待ち時間を減らすLLMサービングスケジューラ（serving scheduler）。

## 概要

OrcaやvLLMの連続バッチ処理（continuous batching）では、新しい要求を途中からバッチへ入れられる。しかし一度実行を始めた要求を基本的に最後まで続けると、長い要求がGPU枠とKVメモリを長く占有し、後から来た短い要求が待たされる。

FastServeはこの問題に対して、**出力トークンを1つ生成するたびに要求を一時停止できるスケジューラ**を導入する。短そうな要求を先に進め、長い要求は一時的に後回しにすることで、待ち行列（queue）での待ち時間を減らす。

ただし一時停止した要求のKVキャッシュをすべてGPUに残すとVRAMが足りなくなる。そこでFastServeは、すぐには再開しない要求のKVをCPU DRAMへ移し、再開時刻を見越して必要になる前にGPUへ戻す。

## 問題設定

連続バッチ処理を使っても、実行中要求を完了まで止めない方式では、出力が長い要求が後続要求を待たせる。

特に負荷が高い環境では、モデル計算そのものより**待ち行列で待つ時間**が遅延（latency）の大きな割合を占める。そのためカーネル（kernel）を速くするだけでは改善しきれない。

一方、要求を頻繁に一時停止するとKVキャッシュが増える。KVをGPUへ残せばVRAMを圧迫し、捨てれば再計算が必要になるため、スケジューラとKVメモリ管理を一緒に設計する必要がある。

## 手法

### 1. 1トークン境界を安全なプリエンプション点にする

FastServeはデコード（decode）で1トークンを生成した直後を切り替え地点にする。Transformer層の途中で停止するのではなく、1反復が完了して新しいトークンと対応するKV状態が確定した時点で止めるため、中間カーネル状態や部分的な演算結果を退避する必要がない。

各反復の終了時、スケジューラは待機中要求と実行中要求の優先度を比較し、現在の要求を次の反復へ進めるか、より優先度の高い要求へGPU枠を譲るかを決める。出力長を事前に知らなくても、すでに消費した実行時間を観測しながら長い要求を段階的に低優先度へ送れる。

切り替えの出力は「次の反復で実行する要求集合」であり、要求本体の生成状態はKVキャッシュと生成済みトークン列に残る。したがってプリエンプション後もプロンプト処理からやり直さず、KVを利用可能にできれば次のトークンから再開できる。細粒度プリエンプションを成立させる鍵は、計算状態ではなくKV状態を効率よく保持・移動することにある。

### 2. Skip-join MLFQで短い要求を先にしつつ長い要求の飢餓を防ぐ

FastServeはOSで使われる多段階フィードバック待ち行列（Multi-Level Feedback Queue; MLFQ）をLLM向けに調整する。通常のMLFQは新規ジョブを最上位へ入れ、一定時間使ったら徐々に下位へ落とすが、LLMでは入力長から初回処理コストの一部を推定できる。

そこでFastServeは入力長から開始時の実行時間を概算し、新規要求を最上位へ一律投入せず、予想コストに対応した途中の待ち行列へ直接参加させる。論文の「skip-join」は、要求が最初から通る必要のない高優先度待ち行列を飛ばすことを意味する。これにより長いプロンプトが短い要求と同じ最上位枠を何度も消費して降格される無駄を減らす。

実行時間が増えた要求はより低い優先度へ移るため、短い要求は早く完了しやすい。一方、低優先度要求が永久に実行されない飢餓（starvation）を避けるため、一定時間待った要求の優先度を回復させる。目的は最短要求を完全に知ることではなく、既知の入力長と実測済み実行時間だけで、先着順より短い要求へGPU時間を寄せることである。

### 3. 一時停止中のKVをCPUへ退避し、再開前に先読みする

すぐ再開しない要求のKVキャッシュはホストメモリへ退避する。GPUに残すKV量を抑えることで、プリエンプションによって「開始済みだが未完了」の要求が増えても、VRAMを使い切りにくくする。

重要なのは、再開が決まってから同期的にKVを戻すのではないことである。FastServeは待ち行列の順位と各要求の残り時間枠から、近く再開しそうな要求を先に選び、現在のGPU計算とCPU→GPU転送を非同期に重ねる。再開時点までに必要なKVが戻れば、プリエンプションによる待ち時間をほぼ計算の裏へ隠せる。

予測より早く要求が昇格した場合やPCIeが混雑した場合は、KV転送完了を待つ必要があり、プリエンプションの利得が小さくなる。したがってFastServeの遅延改善は優先度制御だけでなく、「次に誰が走るか」というスケジューラ情報をKV先読みへ渡すことによって成立する。

### 4. 分散モデルではKV管理とプリエンプションを全並列ワーカーで揃える

単一GPUに収まらない大規模モデルでは、テンソル並列（tensor parallelism）やパイプライン並列（pipeline parallelism）を使う。1つの要求のKVは複数GPU・複数パイプライン段へ分散しているため、あるワーカーだけで要求を停止・再開しても正しい状態にならない。FastServeは要求IDとスケジューリング決定を分散ワーカー間で共有し、同じ反復境界で対象要求の進行を切り替える。

KVキャッシュ管理器もワーカーごとに対応するKV断片を追跡し、プリエンプト対象の断片を各GPUからホストへ退避する。再開前には必要な断片をそれぞれのGPUへ先読みし、全段で状態が揃った時点で次の反復へ戻す。つまり単一の巨大KVを1か所へコピーするのではなく、モデル並列で分割された状態をスケジューリング単位と同期して移す。

パイプライン並列では複数のバッチを異なる段で同時進行させ、1つのバッチが段間を移る間に別バッチを処理して空き時間（pipeline bubble）を減らす。FastServeのプリエンプションはこのパイプラインを無視して即時停止するのではなく、反復境界で次の実行集合を更新するため、分散実行を保ちながら要求単位の優先順位を変更できる。

## なぜこの設計で遅延を減らせるのか

先着順で長い要求がGPUを占有すると、後から来た短い要求の処理時間が短くても待ち時間が長くなる。FastServeはトークン境界で長い要求を一時停止し、短い要求を途中へ挿入するため、平均・末尾遅延（tail latency）を支配する先頭ブロッキング（head-of-line blocking）を減らせる。

ただし開始済み要求を増やすだけではKV容量が新しい制約になる。KVのホスト退避と先読みを一体化することで、VRAMを解放しながらプリエンプションの再開コストを抑える。したがって高速化の因果関係は「細粒度スケジューリング → 開始済み要求増加 → KV退避が必要 → 次回実行順を利用した先読みで転送を隠す」という一続きの設計である。

## 評価

NSDI 2026最終版の公式ページでは、vLLMと比較して**同じ遅延条件でスループットを最大6.1倍改善**したと報告している。

評価は実機で行われ、主なテストベッドはAWS EC2 p4d.24xlarge 2台、合計16枚のNVIDIA A100 40GB GPU。ShareGPT / Alpaca由来のワークロードを用いる。

### 版による評価値の注意

arXiv上の公開前版は、平均遅延SLOで最大31.4倍、末尾遅延SLOで最大17.9倍など、NSDI 2026公式ページより大きな見出し値を記載している。これらは**別版の数値**なので、本ページの代表結果には混在させず、最終採択版として公開されているUSENIX側の6.1倍を優先する。

## 既存研究との差

### Orca / vLLMとの違い

OrcaとvLLMはトークン生成ごとにバッチを組み替えられるが、FastServeはその反復境界を**要求自体のプリエンプション点**として使い、優先度スケジューラで実行順を変える。

### Sarathi-Serveとの違い

Sarathi-Serveは長いプリフィルを小分けにしてデコードとの干渉を抑えることが中心。FastServeはデコード中要求を含めたジョブ全体の優先順位とプリエンプションを扱う。

### Llumnixとの違い

FastServeはサービングインスタンス内で要求の実行順とKV配置を変える。Llumnixは実行中要求を別インスタンスへ移行し、GPU間負荷不均衡を調整する。

## 限界

- モデル／ハードウェアごとの反復コストに依存するため、GPU・カーネルスタックが変わればプロファイルを取り直す必要がある。
- 要求長がほぼ均一なら短いジョブ優先の利点は小さい。
- KV交換はホストDRAM容量とPCIe帯域を使うため、ホスト側が混雑すると効果が下がる。
- 優先度スケジューラは遅延を改善する一方、長いジョブへの公平性（fairness）／末尾遅延対策が必要。
- arXiv公開前版とNSDI 2026最終版では見出し評価値が変わっているため、版を跨いで数値を比較・合成しないことが重要。

## 一般的な実装上の含意

LLMサービングでは出力長を正確に予測できなくても、入力長や既に消費したGPU時間を使って先着順より細かいプリエンプティブスケジューリング（preemptive scheduling）を作れる。

ただしプリエンプションを導入すると開始済み未完了要求のKV状態が増える。したがって**スケジューラだけでなく、KVのGPU／ホスト配置と先読みを同時設計する**必要がある。
