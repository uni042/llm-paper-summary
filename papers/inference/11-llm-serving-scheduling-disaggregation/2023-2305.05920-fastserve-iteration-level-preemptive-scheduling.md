# FastServe: Iteration-Level Preemptive Scheduling for Large Language Model Inference

> output tokenを1つ生成する区切りでrequestを一時停止・再開できるようにし、短いrequestを優先しながらKV cacheをCPUへ退避・先読みして待ち時間を減らすLLM serving scheduler。

## 概要

OrcaやvLLMのcontinuous batchingでは、新しいrequestを途中からbatchへ入れられる。しかし一度実行を始めたrequestを基本的に最後まで続けると、長いrequestがGPU枠とKV memoryを長く占有し、後から来た短いrequestが待たされる。

FastServeはこの問題に対して、**output tokenを1つ生成するたびにrequestを一時停止できるscheduler**を導入する。短そうなrequestを先に進め、長いrequestは一時的に後回しにすることで、queueでの待ち時間を減らす。

ただし一時停止したrequestのKV cacheをすべてGPUに残すとVRAMが足りなくなる。そこでFastServeは、すぐには再開しないrequestのKVをCPU DRAMへ移し、再開時刻を予測して必要になる前にGPUへ戻す。

## 問題設定

continuous batchingを使っても、実行中requestを完了まで止めない方式では、outputが長いrequestが後続requestを待たせる。

特に負荷が高い環境では、model計算そのものより**queueで待つ時間**がlatencyの大きな割合を占める。そのためkernelを速くするだけでは改善しきれない。

一方、requestを頻繁に一時停止するとKV cacheが増える。KVをGPUへ残せばVRAMを圧迫し、捨てれば再計算が必要になるため、schedulerとKV memory管理を一緒に設計する必要がある。

## 手法

### 1. 1 tokenごとにrequestを一時停止できる

FastServeはdecodeで1 tokenを生成した直後を切り替え地点にする。Transformerの途中で止めるのではないため、複雑な内部状態を保存する必要がない。

毎回schedulerが、

- 今のrequestを続ける
- より優先度の高いrequestへ切り替える

のどちらかを選ぶ。

### 2. 短いrequestを優先しつつ、長いrequestも放置しない

FastServeはOSで使われる複数段階のpriority queueをLLM向けに調整している。論文では **skip-join MLFQ** と呼ぶが、仕組みは次のように理解できる。

- promptが短く、prefillが軽いrequestは高い優先度から始める
- 長く実行し続けたrequestは徐々に優先度を下げる
- 長時間待ったrequestは優先度を上げ直し、永久に後回しにならないようにする

prefill時間はinput lengthから比較的予測しやすいため、新規requestを最初から適切なpriorityへ入れる。

### 3. 一時停止中のKVをCPUへ移す

すぐに再開しないrequestのKV cacheはCPU DRAMへ退避する。

重要なのは、再開が決まってからGPUへ戻すのではなく、**次に実行されそうな時刻を予測して先に転送を始める**ことにある。これによりPCIe転送を別requestのGPU計算と重ね、再開時の待ち時間を短くする。

## 評価

主な環境はA100 40GBを最大16枚使うAWS cluster。OPT-13B / 66B / 175BとLlama3-8BをFP16で評価し、ShareGPT、Alpacaなどを使った。

同じlatency SLOを満たせるthroughputでは、ShareGPTでvLLM比**2.1〜6.1倍**、Alpacaで**2.75〜3.5倍**を報告している。

P95 latencyのSLOを使った条件でも、vLLM比で最大**8.1倍**のthroughput改善を報告した。

CPUへ退避したKVを必要になる前にGPUへ戻す方式は、必要になってから転送する方式より最大**1.7倍**高速で、KVを捨てて再計算する方式より最大**2.7倍**高速だった。

## 既存研究との差

### Orca / vLLMとの違い

OrcaとvLLMはtoken生成ごとにbatchを組み替えられるが、基本的には現在実行中のrequestを継続する。

FastServeはその区切りを**requestの一時停止地点**として使い、短いrequestを先に進められるようにした。

### Sarathi-Serveとの違い

Sarathi-Serveは長いprefillを小分けにしてdecodeを止めないことが中心。FastServeはdecode中のrequestも含め、request全体の優先順位を変える。

### Llumnixとの違い

FastServeは1つのserving instance内で実行順を変える。Llumnixは実行中requestそのものを別instanceへ移し、GPU間の負荷差を直す。

## 限界

- modelとhardwareごとの実行時間profileを使うため、kernelやGPUが変わると再計測が必要。
- request長がほぼ均一なworkloadでは、短いrequestを優先する利点が小さくなる。
- CPU DRAMとPCIe帯域を使うため、host memoryやPCIeが混雑している環境では効果が下がる。
- 主評価はA100とOPT系列で、Hopper / BlackwellやMLA系modelは未評価。
- priority設定はserviceのSLOに合わせた調整が必要。

## 一般的な実装上の含意

LLM servingではoutput長が事前に分からなくても、すべてを到着順で処理する必要はない。input lengthや過去の実行時間profileだけでも、短いrequestをある程度優先できる。

また、requestを一時停止するschedulerを作るなら、KV cacheをどこへ置くかも同時に設計する必要がある。**優先順位制御とKVのCPU退避・先読みを組み合わせる**ことで、latency改善とVRAM節約を両立できる。
