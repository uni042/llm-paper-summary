# VoltanaLLM: Feedback-Driven Frequency Control and State-Space Routing for Energy-Efficient LLM Serving

> P/D分離配信で周波数制御・遅延予測・状態空間ルーティングを連動し、SLOを保ちながら最大36.3%省エネするVoltanaLLM。

## 概要

LLMサービングでは、1つの要求を**プリフィル（prefill）**と**デコード（decode）**に分けて考える。プリフィルは入力プロンプトをまとめて処理するため大きな行列積を効率よく実行しやすく、計算量に支配されやすい。一方デコードは1トークンずつ生成し、そのたびにモデル重みとKVキャッシュへアクセスするため、低バッチではメモリ帯域律速になりやすい。

近年のP/D分離サービングは、この2段階を別GPU群へ置いて干渉を減らす。ただし、それぞれのGPUを常に最大クロックで動かすと、必要以上の電力を消費する。GPU周波数を下げれば電力は減るが、プリフィルではTTFT（最初のトークンまでの時間）、デコードではITL（隣接出力トークン間隔）が悪化し、SLO違反につながる。

VoltanaLLMは、P/D分離によって段階ごとに独立したGPUがあることを逆に利用する。**EcoFreq**が各反復で「SLOを満たせる最低周波数」を選び、**EcoPred**が現在のバッチ・KV量・候補周波数からTTFT/ITLを予測し、**EcoRoute**がデコード要求の配置先を選ぶ。特に、バッチサイズがGPUのGEMMタイル境界を跨ぐと、1リクエスト増えただけで余分なタイルが立ち上がり遅延・電力が不連続に悪化する。この「frequency cliff」を、ルーティング時のwhat-if分析で避けるのが特徴である。

SGLang上でMinistral-3B、LLaMA-3.1-8B、Qwen3-32Bを用い、2 prefill + 2 decodeインスタンスで評価した結果、最大周波数固定のSGLangに近いSLO達成率を維持しながら、E2Eエネルギーを最大36.3%削減した。

## 問題設定

### なぜ「低周波ほど省エネ」ではないのか

GPUの消費電力は周波数を下げると減るが、処理時間は伸びる。エネルギーは電力×時間なので、クロックを下げ過ぎると長時間動作する静的電力が支配的になり、かえって総エネルギーが増える。

VoltanaLLMのA100プロファイルでは、プリフィル・デコードの双方でエネルギー対周波数がU字型となり、1005 MHz付近が省エネルギーのsweet spotだった。1005 MHzより低い領域では、遅くなる割に電力が十分下がらず、エネルギーと遅延の両方が悪化する。

さらにP/Dで応答特性が異なる。計算律速に近いプリフィルは周波数上昇でTTFTが比較的大きく改善する一方、低バッチ・メモリ律速のデコードでは1005→1410 MHzに上げてもITL改善は約20%に留まり、エネルギーは約50%増える例がある。したがって両段階へ同じクロック方針を適用するのは非効率である。

### バッチサイズ1件の差が「周波数の崖」を作る

GPUのGEMMは固定サイズのタイルに分けて実行される。バッチがタイル境界ぴったりなら各タイルを埋めやすいが、例えば256→257要求へ増えると、257番目のためだけに新しいタイルが必要になる場合がある。新しいタイルの有効データが少なくても、GPUはそのタイルを実行するため、ITLが段階的に跳ね上がる。

SLOを守るEcoFreqは、この遅延増加を補うため周波数を一段上げる。そのため、ルータが単純に均等配分すると複数インスタンスが同時に境界を越え、エネルギーが急増する。VoltanaLLMはこのハードウェア粒度までルーティング判断へ入れる。

## 手法

### 1. EcoFreq — 各反復でSLOを満たす最低周波数を選ぶ

EcoFreqはprefill/decode各インスタンスで反復ごとに動く周波数制御器である。入力は、待ち行列、現在のバッチ情報、候補周波数集合、EcoPredが返す推論時間予測である。

まず待ち要求がある場合は最大周波数を選び、滞留を優先して解消する。待ち行列がなければ、プリフィルではTTFT SLOから既に待った時間を引き、残り時間を実行予算とする。デコードではITL SLOそのものを実行予算として使う。

その後、低い周波数から順にEcoPredへ問い合わせ、予測実行時間が予算以内になる最小周波数を採用する。どの周波数でもSLOへ届かない場合だけ最大周波数へフォールバックする。つまり「クロックをできるだけ下げる」のではなく、**その瞬間のSLO余裕を電力削減へ変換する**制御である。

### 2. EcoPred — 負荷状態と周波数からTTFT/ITLを予測する

EcoFreqとEcoRouteは、まだ実行していない候補状態の遅延を知る必要がある。EcoPredはそのための軽量予測器で、XGBoostを用いる。

プリフィルは主に候補周波数とバッチ内トークン数 (N_{tok}) から実行時間を予測する。デコードは、同時実行要求数 (N_{req})、KVキャッシュ内トークン数 (N_{kv})、周波数 (f) を入力にし、タイル境界による階段状の遅延変化を含めて学習する。

初期モデルは広い状態空間を均等にプロファイルしたデータから学習する。ただし本番トラフィックは入力長・出力長・到着率が偏るため、実行中に新しい実測データを収集し、一定数ごとにバックグラウンドで再学習して分布ずれを補正する。1回の予測は0.5 ms未満で、周波数制御・ルーティングの高速経路へ入れられる。

### 3. EcoRoute — デコード状態空間を仮想遷移させる

各decodeインスタンスは、((N_{req},N_{kv})) の2次元状態にいると考えられる。その状態へEcoFreqを適用すると、必要周波数 (f) も決まるため、状態空間は「低周波で済む領域」と「高周波へ上げないとSLOを守れない領域」に分かれる。

EcoRouteは新しい要求が来るたびに、その要求を各decodeインスタンスへ仮に置いた場合の状態をEcoPred/EcoFreqで計算する。単純round-robinではなく、どの配置がfrequency cliffを跨ぐかを先に見る。

例えば2インスタンス・520要求・境界256の例では、260/260に均等化すると両方が境界を越え高周波へ移る。一方240/280と非対称に置けば、一方を低周波領域へ残せる。もう一方のITLは少し増えてもSLO内なら、全体エネルギーは低くなる。

### 4. 高周波領域への「不要な遷移」を避ける

EcoRouteは候補配置後の周波数集合 (mathcal{F}') を現在の (mathcal{F}) と比較する。一部インスタンスだけが高周波へ上がり、周波数差が許容しきい値 (Delta) 内なら、周波数を上げずに済むインスタンスのうち最も低周波のものを選ぶ。

それ以外では、仮配置後の必要周波数が最も低いインスタンスを優先し、同率ならround-robinする。EcoPredへの複数候補照会はバッチ化され、EcoRoute全体の追加遅延は1 ms未満とされる。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| 構成 | 2 prefill + 2 decode（2P2D） |
| モデル | Ministral-3B、LLaMA-3.1-8B、Qwen3-32B |
| Qwen3-32B | 各インスタンス2-way tensor parallel |
| GPU周波数候補 | 1005 / 1410 MHz |
| ルータしきい値 | (Delta=500) |
| SLO | Ministral 200/20 ms、LLaMA 600/60 ms、Qwen3 1200/120 ms（TTFT/ITL） |
| 基盤 | SGLang |
| 比較 | SGLang-1005、SGLang-1410 + round-robin |
| 指標 | TTFT SLO達成率、ITL SLO達成率、E2Eエネルギー |

### 代表的な結果

| 条件 | 結果 | 読み取り |
|---|---:|---|
| 最大エネルギー削減 | 36.3% | 最大周波数1410 MHz固定より低エネルギー |
| 最大値の条件 | Qwen3-32B + ShareGPT、20 RPS | 低〜中負荷で低周波時間を長く取れる |
| SLO達成率 | SGLang-1410と同等水準 | 省エネを大幅な遅延違反で得ていない |
| ITL | 条件によって1410 MHz固定より改善 | EcoRouteが複数インスタンス同時のfrequency cliff越えを避ける |
| SGLang-1005 | 省エネだがSLO達成率が低い | 静的sweet spotだけでは負荷変動へ対応できない |

評価のポイントは、1005 MHzが平均的にはエネルギーsweet spotでも、それを固定すれば高負荷時にSLOを破ることにある。逆に1410 MHz固定は安全だが、低負荷で余分な電力を使う。EcoFreqが時間方向に運転点を変え、EcoRouteが空間方向に要求配置を変えることで両者の間を埋める。

## 既存研究との差

既存のDVFS型LLMサービングは、GPU周波数や電力上限を負荷へ合わせるが、P/D分離でprefillとdecodeを独立制御し、さらに要求ルーティングまで同じ制御問題として扱うものは限られる。

VoltanaLLMのもう一つの差は、GPUのタイル粒度によって起こる不連続な性能境界をサーバー側ルーティングへ持ち込んだ点である。単純な「最も空いているGPU」ではなく、**1件追加した後に必要周波数がどの領域へ移るか**を予測して配置する。

## 限界

VoltanaLLMはP/D分離型サービングを前提とする。結合型のchunked prefillではprefill/decodeトークンが同じカーネルに混ざり、論文が観測したデコードの階段状境界が弱くなる可能性がある。

EcoPredはオンライン適応するとはいえ、GPU世代、カーネル実装、モデル、テンソル並列度が変われば性能曲面を再学習する必要がある。評価で使った1005/1410 MHzや (Delta=500) も普遍定数ではない。

また最大36.3%は特定のQwen3-32B・ShareGPT・20 RPS条件の値であり、高負荷になるほどSLO維持のため高周波へいる時間が増え、節電余地は小さくなる。
