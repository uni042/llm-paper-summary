# Observation, Not Prediction: Conversation-Level Disaggregated Scheduling for Agentic Serving

> agentの各turnを個別予測して配置せず、conversation全体を初回の重いprefillと長いmemory-bound tailの2段階として扱い、観測可能なinput長とKV占有量だけで配置してKV転送と誤予測を減らす。

## 問題
agentic workloadはLLM推論とtool callを多数のturnにわたって繰り返す。従来のmulti-turn servingがturn単位で「prefillをremote workerへ送るか、decoder側でlocal実行するか」を決めると、まだ観測できないdecode長、tool挙動、KV成長量を予測しなければならない。

論文は、この予測困難性をworkload固有ではなく**scheduling unitの選び方**が生む問題と捉える。userが待っているのは各tool-call turnのTTFTではなく、conversationが初めてuser-visibleな成果を返す時点であるため、time-to-first-effective-token（TTFET）というconversation-level指標も導入する。

## 新規性
ConServeはturnではなくconversationを配置単位にする。agentic conversationを、(1) 長いtask promptを処理するcompute-boundなturn-1 prefill、(2) KVが蓄積した状態で短いappend-prefillとdecodeを繰り返すmemory-bound tail、の2 phaseとして扱う。

これにより必要な判断材料は初回input token数とdecoderのKV-cache occupancyという直接観測可能な量になる。未来のdecode長やtool挙動を学習modelで予測しない。

## 手法
- 初回prefillを高throughput prefillerへ送る。
- 生成したKV cacheをdecoderへ**1回だけ**転送する。
- first-turn decode以降のappend-prefill / decodeをconversation終了まで同じdecoderへ固定する。
- decoderのKV occupancyが高い場合は、新しいconversationを別decoderへrouteし、配置済みconversationを途中migrationしない。
- heterogeneous clusterではcompute-bound initial prefillを高性能GPU、memory-bound tailを十分なmemory bandwidth / capacityを持つ低power tierへ対応付ける。

## 評価条件
agentic traceはSWE-bench系workloadを使い、profiling / serving評価はQwen3-0.6Bをbf16でNVIDIA A40上に実装する。heterogeneous評価ではGPUをTDPの2/3へpower capし、compute能力が低いtierを模擬する。論文自身も結果がmodel / hardware固有である点を明記する。

## 主要結果
per-turn prediction baselineに対し、ConServeはp95 TTFETを51.08%削減し、last-turn TBTとSLOを維持しながらenergy efficiencyを7.51%改善する。conversation-levelの2 phaseをheterogeneous GPU tierへ割り当てると、homogeneous構成からさらに22.75%のenergy efficiency改善を報告する。

## 限界
- 主評価modelはQwen3-0.6B、hardwareはA40であり、大型modelや現行acceleratorでの絶対値・最適配置は変わり得る。
- 「初回prefillが大きく、その後のappendが小さい」というagentic workload構造に依存する。後続turnでも大規模context追加が頻発するagentでは2 phase仮定が弱くなる可能性がある。
- decoderへconversationを固定するため、長conversationが偏った場合はoverprovisioningと新規conversation routingで吸収する設計で、既存conversationのmigrationによる再均衡は行わない。

## 既存研究との差
AMPD / PPDのようなper-turn routingは各turnでlocal / remote prefillを選び、将来costの予測またはlookupを必要とする。ConServeはconversation単位へ抽象度を上げることでdecision自体をほぼ一度にし、予測器ではなく観測可能stateを使う。

## 一般的な実装への示唆
agent workloadではrequest単位の最適化を積み上げてもuser-visible latencyと一致しない場合がある。schedulerの予測器を高度化する前に、状態を保持する単位をconversation / sessionへ拡大すると、未来予測を不要にできる可能性がある。またKVを何度も往復させるより、一度だけ適切なmemory-bound workerへ移してpinする設計が有効なworkloadがある。
