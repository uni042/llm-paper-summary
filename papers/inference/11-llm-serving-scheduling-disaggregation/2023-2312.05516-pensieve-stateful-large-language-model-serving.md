# Stateful Large Language Model Serving with Pensieve

> multi-turn conversationの過去KV cacheをrequest終了後もGPU / CPUへ残し、次のturnで同じhistoryを再びprefillする計算を避けるstateful LLM serving system。

## 概要

通常のLLM APIでは各requestを独立に扱うため、multi-turn conversationでも毎回history全体をpromptとして送り直す。この方式ではturnが進むほど、**以前すでに処理したhistoryを何度もprefillする無駄**が増える。

Pensieveはconversationごとに過去KV cacheを保存し、次turnでは新しく追加されたuser messageだけをprefillする。過去historyのKVはそのまま再利用する。

多数conversationのKVをすべてGPUへ置くのは難しいため、よく使うKVはGPU、しばらく使われていないKVはCPU DRAMへ置く。必要になった時はCPUからGPUへ戻す。

## 問題設定

multi-turn conversationではhistoryがturnごとに長くなる。毎回history全体をprefillし直すと、conversationが長くなるほど重複計算が増える。

論文ではLlama2-13B、history 2048 token、batch 32の条件で、historyの再prefill時間が200 decode stepより約4倍長くなる例を示す。

一方でKVをrequest間に保存すると、

- 多数userのKVをGPUへ全部置けない
- CPUへ移したKVを戻すPCIe転送が必要
- KVを入れ替えるとGPU memory上で連続しなくなる
- follow-up requestでは複数の新tokenをまとめてprefillする必要がある

という問題が生じる。

## 手法

### 1. ConversationごとにKVを残す

過去turnで作ったKV cacheをconversation IDと結び付けて保存する。次turnでは新しく追加されたtokenだけをmodelへ通し、attentionでは保存済みKVを参照する。

これにより過去historyに対するQKV projectionやMLP計算を毎回繰り返さなくてよい。

### 2. GPUとCPUを2段階のKV置き場として使う

最近使ったconversationのKVはGPUへ置き、GPU memoryが不足してきたらしばらく使われていないKVをCPU DRAMへ移す。

CPUからKVを戻す時はlayerごとに転送し、前のlayerをGPUで計算しながら次のdataを運ぶことでPCIe待ちを隠す。

### 3. GPUが完全に埋まる前にKVを退避する

GPU memoryが本当に足りなくなってからKVを追い出すと、新requestがその場で待たされる。

Pensieveは空きmemoryが少なくなった段階で、inactive conversationのKVを先にCPUへ移しておく。

### 4. 捨てた時の再計算量も考えてKVを残す

CPU memoryにも限界があるため、最終的には一部KVを完全に捨てる必要がある。

単純に「最後に使ってから時間が長いKV」だけを捨てるのではなく、**そのKVを失った場合に次回どれだけhistoryを再計算することになるか**も考えて、残す優先度を決める。

### 5. GPU上で散らばったKVをそのままattentionへ使う

KVをGPU / CPU間で入れ替えると、GPUへ戻したKVがmemory上で連続しない場合がある。

Pensieveは、複数の新しいinput tokenから、GPU上に分散して置かれた過去KVへ直接attentionできるkernelを用意し、一度大きな連続bufferへコピーする処理を避ける。

## 評価

Llama 2系modelとShareGPT / UltraChat系multi-turn workloadを使い、vLLMとTensorRT-LLMを比較対象とした。

最終版ではvLLM / TensorRT-LLMに対して**1.14〜3.0倍のthroughput**を報告している。

長いconversationや同じhistoryを再利用する機会が多いほど効果が大きくなる。

構成要素ごとの評価では、GPU上のKV再利用だけでも改善があり、CPUへの退避、再計算量を考えた保存優先度、転送と計算の同時実行を加えることでさらにthroughputが上がる。

## 既存研究との差

### vLLMとの違い

vLLMは主に**1 requestの実行中**にKV memoryを効率よく管理する。Pensieveはrequestが終わった後もconversation KVを残し、**次requestで再利用する**。

### KV offload研究との違い

一般的なKV offloadは、実行中のlong-context requestのKVをCPU / storageへ移してVRAM不足を解消する。

PensieveではCPU退避は手段であり、主目的は**multi-turn conversationで過去historyを再計算しないこと**にある。

### Mooncakeとの違い

Mooncakeはcluster全体でKVを共有する大規模serving architecture。Pensieveはconversation単位でrequest間KVを保持することが中心である。

## 限界

- 毎回独立したpromptでは過去KVを再利用できず、効果が小さい。
- 非常に大きなhistoryをCPUとGPUの間で頻繁に移すとPCIe転送が支配的になる。
- conversation stateを長期間保存するほどCPU memory容量が必要。
- 過去historyを途中で編集すると、その位置以降のKVは再計算が必要。
- 主評価はA100世代とLlama 2系で、KV sizeが小さいGQA / MLA modelでは利得が変わる。
- 2026-09-07時点で著者公式code repositoryは確認できない。

## 一般的な実装上の含意

chat / agent workloadではKV cacheを「request終了時に必ず捨てる一時data」と考える必要はない。conversation IDと結び付けてrequest間に保持すれば、同じhistoryのprefillを大きく削減できる。

またKVを残す優先順位は、最近使ったかどうかだけでなく、**失った時にどれだけ再計算が必要か**まで考える方が合理的である。
