# Stateful Large Language Model Serving with Pensieve

## 概要

Pensieveは、会話型の大規模言語モデルを複数往復にわたって提供するとき、前回までの履歴を毎回最初から入力処理する重複計算を減らす状態保持型の推論提供システムである。通常の要求単位の処理では、回答生成が終わるとその要求の鍵値キャッシュを解放する。次のユーザー発話が届くと、過去の発話と回答をすべて再度プロンプトに含め、同じ履歴をプリフィルし直す。Pensieveは会話識別子と結び付けた鍵値キャッシュを要求終了後もGPUまたはCPUに残し、次の往復では追加された入力だけを処理する。

ただし多数の会話の鍵値をGPUに置き続けることはできない。PensieveはGPUとCPU主記憶の二層キャッシュを使い、会話が非活動だった時間と、鍵値を捨てた場合の再計算費用を考慮して保持先を決める。GPU容量が尽きる前に退避し、CPUからの回復では層ごとの転送と計算を重ねる。さらに、過去鍵値がGPU上で連続していなくても、新しい複数入力トークンから直接注意を計算できる専用カーネルを実装する。

EuroSys 2025の論文は、OPT-13B、Llama 2-13Bなどの単一GPUモデルで、vLLM・TensorRT-LLM比1.14～1.70倍、OPT-66B・Llama 2-70Bなど4GPUモデルで1.64～3.0倍の処理量を報告する。これは複数往復会話で履歴が再利用される条件の結果であり、独立した単発要求の全てで同じ改善が得られるわけではない。

## 問題設定と動機

通常のプリフィルは入力列全体の鍵値を作り、出力生成では過去鍵値をキャッシュして新しいトークンの注意を計算する。複数往復会話では次の発話を処理するときにも以前の会話履歴が必要だが、要求ごとにキャッシュを破棄すると、すでに計算した履歴の鍵値をもう一度生成する。往復が進み履歴が長くなるほど、追加された短い発話より履歴の再処理が支配的になる。

原著は13B規模のモデルで、16ビットの鍵値を各層に保存すると1トークン当たり約0.78MBが必要になる例を示す。例えば40層・隠れ次元5120では、鍵と値の二つに2バイトずつを掛けるため、1トークン当たり約819,200バイトとなる。会話履歴が数千トークンなら一会話でも数GB規模になり、多数会話の全履歴をGPUだけで保持することは難しい。

一方、CPUへすべて退避すれば次の往復でGPUへ戻す転送費が生じる。容量が足りず一部を完全に破棄した場合は、その部分を再計算する必要がある。さらに戻した鍵値はGPU上の非連続領域に置かれるため、連続した過去列を前提にした従来のプリフィル用注意カーネルをそのまま使えない。Pensieveは「何を保存するか」「いつ移すか」「欠けた履歴をどう再計算するか」「新しい入力と分散した過去鍵値をどう同時に処理するか」を一つのシステムで解決する。

## 手法

### 1. 会話単位の鍵値状態を要求間で保持

Pensieveの基本単位は会話であり、同じ会話に属する複数の要求を関連付ける。前回の回答が完了しても履歴の鍵値を直ちに捨てず、次の要求で利用する。新規要求には、追加されたユーザー発話のトークンと、必要ならキャッシュから失われた履歴の再計算対象が含まれる。過去の鍵値が残っていれば、その部分について質問・鍵・値の投影やフィードフォワード計算を繰り返さない。

この仕組みは文字列の履歴を保存するだけでは実現できない。各層の鍵値を会話のトークン位置と対応させ、以前の要求で生成された回答も次の履歴へ含める必要がある。履歴の一部が変更された場合、変更箇所以降の鍵値を無条件に再利用することはできない。著者らは会話履歴が順次追加される通常の対話を主な対象としている。

### 2. GPU・CPU二層の細粒度キャッシュ

GPU側は最近使った会話の鍵値を保持し、CPU主記憶側はGPUに置けない非活動会話の鍵値を保持する。退避の粒度は会話全体ではなく、複数トークンをまとめた小さなチャンクである。原著では32トークンのチャンクが良い設定だった。これにより会話の一部はGPU、一部はCPU、一部は破棄済みという状態を許容し、容量を細かく調整できる。

退避の優先順位には二つの要素を使う。最後に会話が活動してからの時間Tと、そのチャンクを再計算する費用Cost(s,l)である。sはチャンク長、lはその位置までの文脈長で、保持価値を `V=Cost(s,l)/T` と定義する。Vが小さいものから退避するため、長く使われていない会話のチャンクや、失っても安く再計算できるチャンクを優先的に外す。

重要なのは同じ32トークンでも、会話の先頭にあるチャンクと後方にあるチャンクでは再計算費が異なる点である。後方のトークンはより長い先行文脈へ注意するため、注意演算が高価になる。著者らは再計算費を注意演算の費用とそれ以外の演算費へ分け、文脈長を2の累乗ごとに実機計測し、その間を補間して推定する。単なる最終利用時刻だけでなく、失った場合の計算負担を保持価値へ入れることが特徴となる。

### 3. GPUが満杯になる前の先行退避

GPUの鍵値スロットが完全に埋まってから退避を始めると、新しい要求が到着した瞬間に転送待ちが発生する。PensieveはGPU空きスロットが一定閾値より少なくなった段階、例えば25%未満となった時点で、非活動会話の低価値チャンクをCPUへ先行退避する。要求が来てから慌てて全量を移すのではなく、空き時間に退避しておく設計である。

次の往復でCPUにある鍵値が必要になったときには、層単位の転送と計算を重ねて回復する。前の層の計算中に後続層の鍵値をGPUへ運ぶことでPCIe待ちを隠す。CPU側に残っている履歴の再利用と、GPU上に残っている履歴の即時利用を組み合わせるため、退避が発生しても全履歴の再プリフィルより安い可能性がある。

### 4. 破棄済み履歴の再計算と非連続配置

CPU側も容量制限があるため、一部の鍵値は完全に破棄される。再利用できる部分が履歴の途中にある場合、要求の入力は「先頭の破棄済み部分」「CPUから回復する部分」「GPUに残る部分」「今回追加された部分」に分かれる。先頭の破棄済み部分と末尾の新規入力は計算が必要だが、その間の鍵値は再利用できる。このような非連続な配置を、従来の連続プリフィル用注意へ単純に渡すことはできない。

Pensieveは、過去の鍵値がGPU上の非連続領域に散らばっていても、複数の新しい質問トークンから直接注意を計算するカーネルを実装する。vLLMのPagedAttentionは非連続な鍵値を扱えるが、原著が対象とした実装では生成段階の1要求1入力トークンに限定されていた。Pensieveは質問側を複数トークンへ一般化し、プリフィルと生成を同じ注意処理へ載せる。

### 5. プリフィルと生成を統合したスケジューラ

通常の推論提供ではプリフィルと生成を別々のカーネル呼び出しとして実行することが多い。Pensieveの統合スケジューラは、ある要求が新しい入力を複数トークン処理する段階でも、別の要求が1トークンずつ生成する段階でも、同じバッチに入れられる。生成ステップが終わるたびに完了した要求を外し、待機列から新しい要求を追加する。待機列からの選択には先着順を用いる。

統合バッチを可能にするのが、非連続鍵値へ複数質問トークンから注意できるカーネルである。これにより短いプリフィルと生成を別々に小さなカーネルとして動かす非効率を避ける。単にキャッシュを保存するだけではなく、回復した状態を実際に効率よく利用するための実行基盤も変更している。

## 評価

### モデル・比較対象と測定範囲

| 項目 | 条件 |
|---|---|
| 小規模側 | OPT-13B、Llama 2-13B。主に単一GPUの提供処理 |
| 大規模側 | OPT-66B、Llama 2-70B。4GPUの提供処理 |
| ワークロード | ShareGPT・UltraChatなどの複数往復会話履歴に基づく要求 |
| 比較対象 | vLLM、TensorRT-LLM。原著当時の要求間状態を保存しない構成 |
| 主指標 | 提供処理量、応答遅延、キャッシュ・カーネル・スケジューラの寄与 |
| 保存階層 | GPUの鍵値領域とCPU主記憶。チャンク単位の退避・回復 |
| 比較の前提 | 同一会話の履歴が繰り返し使われる複数往復の要求分布 |

原著の要旨と導入の結果では、単一GPUのOPT-13B・Llama 2-13Bに対して、比較対象比1.14～1.70倍の処理量を報告する。4GPUのOPT-66B・Llama 2-70Bでは1.64～3.0倍となる。最大3.0倍は全モデル・全要求分布に一律の値ではなく、大規模な複数往復会話の評価条件での最大値である。原著は中程度の提供負荷で遅延も大きく改善すると述べるが、具体的な各条件の数値は図表の該当条件と合わせて読む必要がある。

### 再プリフィル削減の効果

履歴を毎回再処理する基準では、会話が長くなるほど新規入力に対する重複計算の割合が増える。原著の図3は、履歴長を増やしたときのプリフィル費用と200ステップの生成費用を比較している。会話が進んで履歴が長くなると、履歴の再計算が生成そのものより大きな費用になることが示される。Pensieveはこの重複を減らすため、履歴が短く再利用も少ない条件より、長く継続する会話で利得が大きい。

ここで改善はモデルの計算精度を近似した結果ではない。元の履歴に対応する鍵値が残っていれば再利用するため、再計算すべきトークンが減る。キャッシュが失われた部分は再計算するので、保存済みの鍵値を誤って別の履歴へ使うことがないよう会話とトークン位置の整合性が重要となる。

### キャッシュ退避方針の寄与

単純なGPU内保持だけでは、同時に利用する会話数が増えるとGPU容量が不足する。CPUへの退避を組み合わせればより多くの会話履歴を保存できるが、復帰時のPCIe転送が増える。先行退避と層ごとの転送重畳は、必要になってからの待機を減らす。再計算費用に基づく保持価値は、同じ保存容量で将来の再プリフィルをどれだけ減らせるかを改善する。

特に後方の履歴ほど再計算が高価という性質を利用するため、会話全体を一括で捨てる方式や、最終利用時刻だけで選ぶ方式と異なる。CPU容量がさらに不足した場合にも、最初に捨てるのは再計算が安いチャンクとなる。この評価の目的はキャッシュ命中率だけを最大化することではなく、次の要求で発生する総計算量と転送時間を減らすことである。

### 注意カーネルと統合バッチの効果

原著のシステムでは、複数新規トークンと非連続鍵値に対応する注意カーネルを導入している。これがなければ、回復した鍵値を一度連続領域へ詰め直すか、新しい入力を1トークンずつ逐次処理する必要があり、プリフィルの並列性を失う。統合バッチでは、生成中の要求と新規入力の要求を同じ反復で実行でき、短いカーネル呼び出しが増えることを避けられる。したがって処理量の改善は、キャッシュ保持、退避、回復、注意カーネル、スケジューラを組み合わせたシステム全体の結果である。

### 何と比較していないか

論文の基準は当時のvLLM・TensorRT-LLMの状態非保持構成である。現在のプレフィックス共有キャッシュや、会話履歴を外部の共有キャッシュへ置く後続システムに対する優位性を、この結果だけから導くことはできない。また、単発要求で再利用可能な履歴がない場合、保存・追跡・退避の費用だけが増える可能性もある。改善倍率を現在の全ての推論基盤へ直接移すのは不適切である。

## 既存研究との差

vLLMのPagedAttentionは、主として実行中の要求の鍵値を非連続なGPU領域へ効率よく配置し、生成段階で参照する仕組みである。Pensieveはその発想を要求間へ拡張し、完了した会話の鍵値を保存し、次の要求で再利用する。さらに複数トークンのプリフィルを非連続鍵値へ適用できるカーネルを実装するため、単にPagedAttentionのキャッシュを長持ちさせるだけではない。

通常の鍵値オフロードは、一つの長い要求の実行中にGPU容量を補うためCPUや他の記憶階層を使う。PensieveのCPU側キャッシュは、複数往復にまたがって再利用される履歴を保存するために使われる。後続の分散キャッシュ方式はクラスタ全体で共有する方向へ進むが、Pensieveの焦点は会話識別子に紐づいた再プリフィル削減と、GPU・CPU二層での局所的な保持管理である。

## 限界と再監査判断

第一に、同じ会話の履歴が繰り返し使われなければ効果は小さい。独立した一問一答の要求では保存済み鍵値の再利用機会がなく、管理費用だけが生じ得る。履歴が途中で編集された場合も、その位置以降の鍵値を無条件に再利用できず、再計算が必要となる。

第二に、GPUとCPUの容量・転送帯域が制約となる。多数の会話が同時に再開するとCPUからGPUへの回復が競合し、先行退避だけでは転送待ちを消せない。CPU主記憶の容量が不足すると、保持価値の低いチャンクを破棄して後で再計算する必要がある。再計算費用の推定はモデルとハードウェアの実測に依存するため、異なるGPUや注意構造へそのまま適用できる保証はない。

第三に、原著のモデルはOPT・Llama 2系の13B～70Bが中心で、グループ化質問注意や多頭潜在注意など鍵値容量の小さい新しい構造では保存価値と転送費の比率が変わる。長い会話の状態保持は会話識別子、保持期限、権限分離といった運用上の要件も伴うが、原著の性能倍率はこれらの全運用費を包括した評価ではない。

第四に、論文が示す1.14～3.0倍は複数往復会話の処理量の改善であり、単一トークンの演算が3倍速くなるという意味ではない。再プリフィル削減、CPU回復、非連続注意、統合バッチの寄与を含むシステム全体の比較として解釈する必要がある。

以上より、一次資料の状態保持、32トークン単位の保持価値式、GPU・CPU退避、非連続な複数トークン注意、統合バッチ、モデル規模別の処理量改善を照合した。元原稿で短かった手法と評価の説明を、具体的な保存判断と比較条件に沿って補強し、再監査合格と判定する。
