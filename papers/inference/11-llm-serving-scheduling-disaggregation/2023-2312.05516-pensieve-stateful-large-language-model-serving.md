# Stateful Large Language Model Serving with Pensieve

> multi-turn conversationの過去historyから作ったKV cacheをrequest間で保持し、GPU / CPUの2-tier cacheとnon-contiguous KV対応attentionで再prefillを避けるstateful LLM serving system。

## 概要

通常のLLM serving APIはrequestごとにstatelessで、multi-turn conversationでも毎回conversation history全体をpromptへ付け直す。そのためturnが増えるほど、**前turnまでに一度処理したhistoryを再びprefillする計算**が増える。

Pensieveはconversationをrequest間でstatefulに扱い、過去historyのKV cacheを次turnへ持ち越す。新しいuser messageだけprefillし、以前のhistoryはcache hitならそのままattentionへ使う。

ただし多数conversationのKVをGPUに常駐させることはできないため、GPU VRAMをfast tier、CPU DRAMをcapacity tierとするmulti-tier cacheを構成する。またswapやevictionでKVがGPU上に非連続配置されても、複数の新しいinput tokenから直接attentionできるkernelを用意する。

## 問題設定

multi-turn servingではconversation historyがturnごとに伸びる。stateless servingではturn nのrequestが、turn 1〜n-1で処理済みのtokenも含めて再度prefillする。

長いconversationではこの重複計算が支配的になる。論文では、history 2048 token・batch 32のLlama2-13Bで、history再prefill時間が200 decode stepより約4倍長くなる例を示す。

一方、stateを保存すると別の問題が生じる。

- 多数userのhistory KVをGPUへ全部置けない
- inactive conversationのstateをCPUへ退避するとPCIe transferが増える
- eviction / recovery後のKVはGPU上で非連続になる
- follow-up requestは複数input tokenを一度にprefillするため、single-token decode向けPagedAttentionだけでは足りない

## 手法

### 1. Conversation単位のKV state reuse

各conversationについて、過去turnで生成済みのKV cacheを保持する。次turnでは新規user inputだけをmodelへ通し、そのqueryからcached history KVへattentionする。

これによりhistory lengthが増えても、同じtokenに対するQKV projectionやMLP計算を毎turn繰り返す必要がなくなる。

### 2. GPU / CPU multi-tier KV cache

active / recent conversationのKVはGPUに置き、GPU memory pressureが高まるとcoldなKV chunkをCPU pinned memoryへswap-outする。

follow-up requestが来たconversationのstateがCPUにある場合はGPUへrecoverする。swapはlayer単位にpipeline化し、あるlayerのKVを転送しながら前layerを計算してPCIe latencyを隠す。

### 3. Ahead-of-time eviction

GPUが完全に埋まってからevictionするとnew request admissionやCPU→GPU recoveryがstallする。

Pensieveはfree GPU cacheが減ってきた時点でinactive stateを先回りしてCPUへ出し、次のrequestに必要なheadroomを作る。

### 4. Recompute costを考慮したeviction

CPU cacheも有限で、最終的には一部stateを完全evictして次回再計算する必要がある。

Pensieveは単純LRUだけでなく、**そのchunkを失ったときに後でどれだけhistoryを再計算する必要があるか**も考慮してretention priorityを決める。再計算costが高いstateを優先して残す。

### 5. Multi-token attention over non-contiguous KV

vLLMのPagedAttentionは非連続KV blockを扱えるが、主にdecodeのsingle query tokenを想定する。

Pensieveはこれを拡張し、follow-up requestの複数new tokenを一度にprefillしながら、GPU上に散らばったcached KVへ直接attentionできるkernelを実装する。別途contiguous bufferへgatherしてからattentionする必要をなくす。

## 評価

### 条件

論文はLlama 2系model、ShareGPT / UltraChat系multi-turn workloadを使い、vLLMとTensorRT-LLMをstateless baselineとして比較する。

主な評価軸はthroughput、latency、GPU / CPU cache hit、recomputed token数、user think timeへの感度である。

### 主な結果

最終版ではPensieveはvLLM / TensorRT-LLMに対して **1.14〜3.0×のthroughput**を報告する。

ShareGPT系の一部設定ではvLLM比約1.5〜2×級、長いconversationやstate reuseが増える条件では最大3×まで差が広がる。

初期版評価ではvLLM比1.51〜1.95×、latency 60〜75%削減という結果も報告されており、最終版ではworkload / system構成を広げて最大3×まで評価が拡張されている。

ablationでは、GPU上のKV reuseだけでも大きな改善があり、CPU tier、cost-aware eviction、transfer overlapを順に加えることでさらにthroughputが向上する。

またuser think timeを長くした場合でも、CPU tierにconversation stateを保持できればstate reuseの効果が残ることを示す。

## 既存研究との差

### vLLM / PagedAttentionとの違い

vLLMは**1つのrequest内部**でKV memoryをpage-like blockとして効率化するが、request終了後のconversation stateを次requestへ継続利用することは主目的ではない。

PensieveはPagedAttentionの発想をrequest境界の外まで広げ、conversation stateを長期間cacheする。

### KV Cache Offload系との違い

一般的なKV offloadは1つのlong-running requestのKVをCPU / storageへ逃がしてHBM不足を解消する。

Pensieveの主目的は**multi-turn request間の重複prefillをなくすこと**であり、CPU tierはそのstateful servingを多数conversationへscaleさせるための手段である。このため分類はServing系統とする。

### Mooncakeとの違い

Mooncakeはcluster-wide KV cache poolを作り、prefill / decode disaggregationとprefix reuseを大規模clusterで最適化する。

Pensieveはsingle serving system内のconversation state persistenceが中心で、multi-turn chatの同一history再利用に焦点を当てる。

## 限界

- state reuseの利得はmulti-turn / repeated-prefix workloadに依存し、毎回独立promptではほぼ得られない。
- CPU offload hitではPCIe transferが必要なため、非常に大きなhistoryを頻繁にswapするとtransferが支配的になり得る。
- conversation stateを長時間保持するほどCPU memory容量とcache eviction policyが重要になる。
- userが過去historyを編集した場合やprefixが一致しない場合、該当位置以降は再計算が必要になる。
- 主評価はA100世代とLlama 2系で、GQA / MLAによってKV footprintが小さくなったmodelではcapacity bottleneckの比率が変化する。
- 2026-09-06時点で、論文著者による公式実装repositoryは確認できなかった。

## 一般的な実装上の含意

chat / agent workloadではKV cacheを「requestが終われば捨てる一時memory」と考える必要はない。session / conversation IDと結びつけて**request間cache**として扱えば、repeated prefix computationを大きく削減できる。

またstateful servingでは、cache容量だけでなく「再計算した方が安いstate」と「transferしてでも残すべきstate」を区別する必要がある。KV cache管理は単純なLRUよりrecompute costを含めた方が合理的になる。
