# Stateful Large Language Model Serving with Pensieve

> 複数往復会話の過去KVキャッシュをリクエスト終了後もGPU / CPUへ残し、次の往復で同じ履歴を再びプリフィルする計算を避ける状態保持型LLM提供処理システム。

## 概要

通常のLLM APIでは各リクエストを独立に扱うため、複数往復会話でも毎回履歴全体をプロンプトとして送り直す。この方式では往復が進むほど、**以前すでに処理した履歴を何度もプリフィルする無駄**が増える。

Pensieveは会話ごとに過去KVキャッシュを保存し、次の往復では新しく追加されたユーザーメッセージだけをプリフィルする。過去履歴のKVはそのまま再利用する。つまり、会話ごとに履歴へ対応するKVを持ち回るため、新しい発話に対応する部分だけを追加計算すればよい。

多数会話のKVをすべてGPUへ置くのは難しいため、よく使うKVはGPU、しばらく使われていないKVはCPU DRAMへ置く。必要になった時はCPUからGPUへ戻す。

## 問題設定

複数往復会話では履歴が往復ごとに長くなる。毎回履歴全体をプリフィルし直すと、会話が長くなるほど重複計算が増える。このため、GPU容量不足への対応と履歴再計算の削減を同時に実現する必要がある。GPUへ残し続ければ同時に扱える会話数が減り、すぐ捨てれば次の往復で削減できたはずの計算をやり直すことになる。

論文ではLlama2-13B、履歴 2048 トークン、バッチ 32の条件で、履歴の再プリフィル時間が200 デコード ステップより約4倍長くなる例を示す。

一方でKVをリクエスト間に保存すると、

- 多数ユーザーのKVをGPUへ全部置けない
- CPUへ移したKVを戻すPCIe転送が必要
- KVを入れ替えるとGPU メモリ上で連続しなくなる
- 続きの リクエストでは複数の新トークンをまとめてプリフィルする必要がある

という問題が生じる。

## 手法

### 1. ConversationごとにKVを残す

過去の往復で作ったKVキャッシュを会話IDと結び付けて保存する。次の往復では新しく追加されたトークンだけをモデルへ通し、注意機構では保存済みKVを参照する。

これにより過去履歴に対するQKV 射影やMLP計算を毎回繰り返さなくてよい。

### 2. GPUとCPUを2段階のKV置き場として使う

最近使った会話のKVはGPUへ置き、GPU メモリが不足してきたらしばらく使われていないKVをCPU DRAMへ移す。

CPUからKVを戻す時は層ごとに転送し、前の層をGPUで計算しながら次のデータを運ぶことでPCIe待ちを隠す。

### 3. GPUが完全に埋まる前にKVを退避する

GPU メモリが本当に足りなくなってからKVを追い出すと、新リクエストがその場で待たされる。

Pensieveは空きメモリが少なくなった段階で、非活動 会話のKVを先にCPUへ移しておく。

### 4. 捨てた時の再計算量も考えてKVを残す

CPU メモリにも限界があるため、最終的には一部KVを完全に捨てる必要がある。

単純に「最後に使ってから時間が長いKV」だけを捨てるのではなく、**そのKVを失った場合に次回どれだけ履歴を再計算することになるか**も考えて、残す優先度を決める。この判断は、単なる最終利用時刻による追い出しではなく、失った場合に発生する再計算量を含めた保存価値の評価である。したがって、長い履歴を持つ会話のKVは、最近使われていなくても残す意味が大きい場合がある。

### 5. GPU上で散らばったKVをそのまま注意機構へ使う

KVをGPU / CPU間で入れ替えると、GPUへ戻したKVがメモリ上で連続しない場合がある。

Pensieveは、複数の新しい入力 トークンから、GPU上に分散して置かれた過去KVへ直接注意機構を適用できるカーネルを用意し、一度大きな連続バッファへコピーする処理を避ける。

## 評価

Llama 2系モデルとShareGPT / UltraChat系複数往復 ワークロードを使い、vLLMとTensorRT-LLMを比較対象とした。

最終版ではvLLM / TensorRT-LLMに対して**1.14〜3.0倍のスループット**を報告している。

長い会話や同じ履歴を再利用する機会が多いほど効果が大きくなる。

構成要素ごとの評価では、GPU上のKV再利用だけでも改善があり、CPUへの退避、再計算量を考えた保存優先度、転送と計算の同時実行を加えることでさらにスループットが上がる。

## 既存研究との差

### vLLMとの違い

vLLMは主に**1 リクエストの実行中**にKV メモリを効率よく管理する。Pensieveはリクエストが終わった後も会話 KVを残し、**次リクエストで再利用する**。

### KV offload研究との違い

一般的なKV オフロードは、実行中の長文脈 リクエストのKVをCPU / 保存領域へ移してVRAM不足を解消する。

PensieveではCPU退避は手段であり、主目的は**複数往復 会話で過去履歴を再計算しないこと**にある。

### Mooncakeとの違い

Mooncakeはクラスタ全体でKVを共有する大規模提供処理 構成。Pensieveは会話単位でリクエスト間KVを保持することが中心である。

## 限界

- 毎回独立したプロンプトでは過去KVを再利用できず、効果が小さい。
- 非常に大きな履歴をCPUとGPUの間で頻繁に移すとPCIe転送が支配的になる。
- 会話 状態を長期間保存するほどCPU メモリ容量が必要。
- 過去履歴を途中で編集すると、その位置以降のKVは再計算が必要。
- 主評価はA100世代とLlama 2系で、KV 大きさが小さいGQA / MLA モデルでは利得が変わる。
- 2026-09-07時点で著者公式コード リポジトリは確認できない。

## 一般的な実装上の含意

対話 / エージェント ワークロードではKVキャッシュを「リクエスト終了時に必ず捨てる一時データ」と考える必要はない。会話 IDと結び付けてリクエスト間に保持すれば、同じ履歴のプリフィルを大きく削減できる。

またKVを残す優先順位は、最近使ったかどうかだけでなく、**失った時にどれだけ再計算が必要か**まで考える方が合理的である。
この考え方は、会話の長さと再利用される可能性を保存判断へ組み込むことを意味する。短い履歴なら捨てても再計算の負担は小さいが、長い履歴を捨てると次の往復で大きな入力処理が発生する。したがって、空き容量が限られる場合でも、将来の計算削減量が大きいKVを優先して残すことが重要になる。
このように、保存領域の管理と推論の計算量削減を一つの判断として扱うことが、状態保持型の提供処理を成立させる。
