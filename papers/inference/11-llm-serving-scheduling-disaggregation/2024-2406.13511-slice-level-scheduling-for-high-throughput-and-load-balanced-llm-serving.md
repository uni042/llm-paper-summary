# Slice-Level Scheduling for High-Throughput and Load-Balanced LLM Serving

## 概要

SCLS（スライス単位スケジューリング）は、LLMの応答長が要求到着時に分からないことから生じる二つの資源浪費を解消するサービング手法である。第一に、系列単位の静的バッチでは、短い応答が終了しても長い応答と同じバッチの計算を続け、無効トークンと入力の埋め草を処理する。第二に、反復単位の連続バッチでは完了要求を速やかに除外できても、将来のKVキャッシュ増加が未知なので、メモリ不足を避けるため並列要求数を保守的に制限する。複数GPUへ単純に順番割当てすると、偶然長い応答が集中した装置だけ終了が遅れる。

SCLSは最大生成長を小さい固定長の区間に分け、一区間だけを処理するバッチを作る。各区間の最大追加トークン数が既知なので、入力長・バッチサイズ・区間長から実行時間とKVキャッシュの必要量を推定できる。時間推定値を用いた動的計画法で要求をまとめ、長時間のバッチから空き負荷の小さいLLMインスタンスへ配分する。区間を終えてまだ生成が続く要求は、最新の生成済み文脈を持つ要求として待機列へ戻す。

著者らはAnt GroupのCodeFuse実運用要求記録を用い、8台のNVIDIA A100 80GBでLLaMA2-13Bを動かした。Hugging Face Transformersを用いる静的バッチの系列単位方式に対し要求処理率を232.3～315.8%増加させ、DeepSpeed-Inference上の反復単位方式に対しても61.6～171.0%増加させた。ただし、同じ実装条件での比較に限定され、現在のvLLMとの直接対照実験は行っていない。さらに長い生成を複数区間へ分けると、その都度入力の事前処理を再実行する追加費用がある。論文はこれを長い生成が少ない実要求分布と適切な区間長で償却する設計を採る。

## 問題設定と観測

自己回帰生成では、要求の入力長は受付時に分かるが、終了記号が現れるまでの出力長は事前に確定しない。通常の静的バッチは最大入力長へ短い入力を埋め、最大出力長まで同期反復するため、短い要求の終了後も無効な生成を行う。バッチ全体を一つの仕事として扱う系列単位方式では、短い要求を利用者へ返す時刻も最長要求に引きずられる。生成上限を全体で1024トークンとするなら、実際には100トークンで終わる要求にも最大長の容量余裕を考慮してバッチを小さくしがちである。

反復単位方式は各トークン生成の境界で要求を入れ替え、上記の無効トークンを抑える。しかし、長い要求が多く残った場合にKVキャッシュが膨張することを予測できないため、Deepspeed-FastGenなどの比較方式は同時実行要求数を制限する。論文はLLaMA2-13BをA100 80GB×8で動かし、到着率20件/秒の条件で、SCLSのほうが大きなバッチを形成し、埋め草・無効生成が少なく、インスタンス終了時刻のばらつきも小さいことを示す。

方式設計のもう一つの根拠は実要求の長さ分布である。著者らはShareGPTの40万件とCodeFuseの1か月分の要求記録を分析し、大部分の生成長が512トークン未満であることを確認した。したがって最大生成長を例えば2048から128トークンずつに区切っても、多くの要求は少数の区間で完了する。この偏りがなければ、区間ごとの再実行費用は大きくなり、同じ利得を保証できない。

## 手法

### 1. 区間分割と要求の再投入

受付時の要求には入力文と最大生成トークン数が付いている。SCLSは最大長全体ではなく、次の区間長Sだけをバッチの生成上限にする。静的バッチ内でS回の生成に達したら、その時点で終了記号を出した要求を返し、未完了の要求を新しい入力文脈とともに待機列へ戻す。次回は新着要求と混ぜてバッチを作り直す。これにより長い要求は一区間を越えてGPU資源を独占せず、区間ごとに負荷の再配置が可能となる。

この論文のSCLS実装は静的バッチを強化する方式であり、連続バッチそのものへスライスを直接組み込んだ完成実装ではない。論文は連続バッチとの統合を将来課題として挙げる。区間の境界で以前のKVキャッシュをそのまま維持して処理を再開するとは限らず、実験実装では文脈の事前入力計算を再実行する。従って、区間長Sを小さくすれば予約の不確実性は減るが、事前入力の再計算回数と入力埋め草が増える。

### 2. 実測に基づく処理時間推定器

一つのバッチについて、要求数N、最大入力長Li、区間長Sを用いる。総処理時間は事前入力処理時間 `T_prefill(N,Li)` と、文脈長が増える各生成反復の時間 `τ_decode(l,N)` の和で近似する。論文は事前入力処理を `p1*N*Li + p2*N + p3*Li + p4`、各反復を `d1*N*l + d2*N + d3*l + d4` の形で近似し、実際の推論エンジンの測定値から係数を適合させる。区間長が固定されているため、到着時に未知の最終生成長を予測する必要はない。

推定器の入力はモデル・推論エンジンごとの事前測定値、バッチ要求数、最大入力長、区間長であり、出力は各バッチの推定処理秒数である。実測との比較では事前入力時間の平均推定誤差がHugging Faceで約0.16秒、DeepSpeedで0.04秒未満、128反復を含む総処理時間の平均誤差がそれぞれ約2.3秒と0.4秒未満だった。これらは対象モデル・環境の測定値であり、任意の新しいGPUやカーネルへ係数をそのまま移植できることを意味しない。

### 3. KV容量の安全判定

KVキャッシュの1トークン当たり必要量をΔ、バッチの最大入力長をLi、区間長をSとすると、静的バッチのKV容量上限は `M_KV=(Li+S)*N*Δ` で表せる。利用可能な容量はGPU物理容量からモデル重みと推論エンジン固有の占有量を差し引いた値である。これにより `M_KV <= M_available` を満たす要求集合だけを同時実行する。区間長Sが最大生成長より小さいため、同じGPU容量でも大きいNを安全に採用できる。

ただし理論式だけでは実装依存の断片化や管理領域を説明できない。Hugging Faceでは使用可能容量へ安全係数ζ=0.9を掛ける。DeepSpeed-Inferenceでは単一係数でも容量不足の判定を安定させられなかったため、区間長を含む全トークン長 `Li+S` に応じて最大バッチ数を事前測定する。論文の実験設定では、全長512以下なら最大28、512超1024以下なら最大22、1024超なら最大12という段階的な判定規則を使う。ここは「完全な数学的保証」ではなく、対象エンジンを測定して作った安全制約である。

### 4. 動的計画法によるバッチ分割

同じバッチに入力長10の要求15件と入力長1024の要求1件を混ぜると、短い15件まで1024へ埋める必要があり、入力計算が浪費される。一方、全要求を個別実行するとGPUの並列性を活用できない。SCLSの適応バッチ化は入力長の昇順に要求を並べ、先頭i件を処理する最小推定時間T[i]を計算する。最後のバッチがj番目からi番目までを含むとき、候補値は `T[j-1]+T_serve(i-j+1,Li,S)` である。容量安全判定に通るjだけを調べ、最小値を与える分割位置P[i]を記録する。

入力長の昇順に並べているため、最後のバッチの最大入力長はi番目の長さとなり、各候補の時間推定へそのまま渡せる。動的計画法の出力は、埋め草を抑えながら十分大きなバッチを作る分割列である。実際の生成長を予測するのではなく、区間内の最大生成回数と入力長を使って計算費用を比較する。要求集合が巨大になると分割探索の計算費用も増えるため、後述の受付間隔と組み合わせて実行する。

### 5. 複数GPUへの最大・最小負荷割当て

適応バッチ化が作った各バッチには、前段で推定した処理時間が付く。SCLSは処理時間が長いバッチから順に取り出し、現在の待ち行列の推定処理時間合計が最小のインスタンスへ渡す。渡した後はそのインスタンスの負荷値に推定時間を加算し、バッチ完了時には当該推定時間を差し引く。これは生成長が偶然偏っても、次の区間で新たに負荷配分をやり直せる仕組みである。

割当てはインスタンス間の推論実行そのものを分割するわけではない。各ワーカーは受信待ち行列からバッチを取り、Hugging FaceまたはDeepSpeed-Inferenceで処理する。SCLSはワーカー間の割当てを調整するゲートウェイであり、分散テンソル並列やGPU間のKVキャッシュ移送を主要機構として評価したものではない。完了時刻の標準偏差を測り、順番割当てより終了時刻がそろうことを負荷分散の証拠としている。

### 6. 受付間隔の適応

SCLSは一定間隔Tで待機列から要求を取り出し、上記のバッチ形成と割当てを実行する。軽負荷では要求を長く待たせず、高負荷ではある程度まとめて大きいバッチを作りたい。このため `T=max(λ*min_w T_load(w), Γ)` とし、ワーカーの最小推定負荷に比例させつつ最低受付間隔Γを確保する。実験ではλ=0.5、ΓはHugging Faceで6秒、DeepSpeedで3秒とした。

ここでTは利用者の生成トークン間隔ではなく、ゲートウェイが要求をまとめて取り出す周期である。予測誤差があってもワーカーが空になりすぎないようλを1未満にし、極端に短い周期で小バッチばかり作らないようΓを置く。負荷の急変や誤推定があると最適な間隔からずれるため、周期と係数は実環境の要求到着率へ合わせる必要がある。

### 構成要素除去と予測誤差

論文は系列単位方式へ機構を順に足す比較を行った。区間分割だけの方式では短い要求を早く返せるが、入力の埋め草は十分減らない。入力長をそろえる簡易バッチ化を加えると埋め草が減り、容量上限に基づく完全な適応バッチ化で同時要求数が増える。最小負荷インスタンスへの割当てで終了時刻の偏りが縮まり、受付間隔の適応で高負荷時にさらに大きいバッチを作れる。これらは「区間化だけで最大性能が出た」という解釈を否定する構成要素別の結果である。

処理時間推定器の誤差も評価されている。Hugging Faceの事前入力時間の平均誤差は約0.16秒、DeepSpeedでは0.04秒未満であり、128反復の総時間ではそれぞれ約2.3秒と0.4秒未満だった。予測した負荷を割当てに使うため、この誤差が大きい別のエンジンへ同じ係数を転用すれば、最小負荷への割当てが誤る可能性がある。論文はインスタンス完了時刻の標準偏差がSCLSで最小となることを報告するが、全到着率の具体的な標準偏差値を本文の表としては提示していない。

### 区間長の感度と悪化条件

区間長を短くしすぎると、同じ要求を何度も待機列へ戻して事前入力処理を再実行し、埋め草の処理も繰り返す。区間長を大きくしすぎると、最大KV予約量が増えて安全バッチが小さくなり、短い要求は終了後も無効な生成と待機に巻き込まれる。論文は区間長に対して性能が一度上がってから下がる傾向を示し、128を標準値としつつ、要求分布に合わせた探索が必要だと論じる。

実際に生成長512超が60%という長い応答中心の人工分布では、区間長128から256への変更で平均応答時間が15.7%短くなった。これは通常分布の最適値をすべての条件へ固定するべきでないことを示す。大半の通常要求は3スライス未満で完了し、区間途中でバッチ全員が終了する割合は1%未満と報告されるが、生成長分布が変わればこれらの前提も変わる。

## 既存研究との差

系列単位スケジューリングは固定した要求群を全生成区間で保持するため、短い応答の返却が遅れる。反復単位スケジューリングは各トークン境界で要求を入れ替えるが、長期のKV容量を予測できず並列数を制限することがある。SCLSはこの間に**固定長の複数トークン区間**を設け、将来の全生成長を予測せず、次の区間だけの時間・容量を見積もる。したがって単純な生成長予測器やトークン反復ごとの完全な動的入替えとは異なる。

OrcaやDeepSpeed-FastGenが主に連続バッチを活用するのに対し、論文のSCLSは静的バッチを前提に、区間分割と入力長別の動的計画法を組み合わせる。低水準の注意カーネルを新規開発する研究ではなく、既存のHugging FaceおよびDeepSpeed推論器の上で動く要求受付・割当て層である。論文はvLLMを直接比較対象にしていない。静的バッチと連続バッチでは利用できるカーネル最適化が異なり、スケジューリング単体の公平な比較が難しいと著者らは説明する。

## 限界・実装上の注意

第一に、スライス境界で未完了要求の事前入力処理を再計算するため、生成が長い要求では同じ文脈を何度も処理する。短い生成が多い実運用記録では償却できても、長い回答ばかりの業務では区間長を調整しなければ利得が縮む。再計算を避けるKV状態の完全な持越しは本稿の実装成果として主張されていない。

第二に、メモリ安全判定はエンジンごとの占有量・断片化に依存する。Hugging Faceの安全係数0.9やDeepSpeedの最大バッチ数28/22/12はA100 80GB上の対象モデルに合わせた値であり、別モデルや量子化・ページ化KV管理では再測定が必要である。安全上限を誤れば容量不足の危険が残る。

第三に、実験はLLaMA2-13Bと8基のA100を中心とする。モデル混在、異種GPU、CPU・SSDオフロード、極端な長文脈、推論品質とエネルギー消費の定量比較を網羅していない。負荷分散はバッチの推定処理時間を基準にしたワーカー割当てであり、異種GPUの通信帯域やKV移送を最適化したと読み替えるべきではない。

第四に、論文はサービス水準目標の違反率やトークン間遅延の分布を主指標としていない。要求処理率と平均・95パーセンタイル応答時間の改善は示すが、利用者ごとに厳密な最初のトークン時間を保証する設計ではない。さらに静的バッチ中心の評価なので、現行のvLLMやSGLangの連続バッチへ直接組み込んだ場合の性能は未検証である。
