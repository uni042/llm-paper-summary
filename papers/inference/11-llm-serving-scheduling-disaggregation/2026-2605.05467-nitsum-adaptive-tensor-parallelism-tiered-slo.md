# Nitsum: Serving Tiered LLM Requests with Adaptive Tensor Parallelism

> 多階層SLOの負荷変動に応じてテンソル並列度、プリフィル/デコードGPU配分、要求スケジューリングを同時に切り替え、重み再読込不要化と高速KV移行で再構成をミリ秒級に抑えるLLMサービング方式。

- **種別**: プレプリント

- **実装**: SGLang上にグローバル/ローカルスケジューラ、TP切替用GPUカーネル、KV移行機構を実装し、約1.2万行を変更・追加したと論文は記載する。原稿はNitsumを近日公開するとしているが、2026-09-13時点の検索では著者によるNitsum公式コード公開先を確認できなかった。
## 概要
Nitsumは、厳しい応答遅延を要求する対話処理と、遅延を許容できる背景処理が同じGPU群を共有する多階層SLO環境で、固定したテンソル並列度では負荷変動に追従できない問題を扱う。テンソル並列度、プリフィルとデコードへのGPU配分、要求配置とバッチ形成を約1秒周期で共同変更し、SLOを満たす要求数である有効スループットを最大化する。頻繁な並列度変更を可能にするため、各GPUにモデル重みを1コピーだけ保持して実行時に必要なシャードを選び、候補となる並列度ごとの実行プロセスを事前起動する。さらに断片化したKVキャッシュをGPU上で連続バッファへ集約し、二重バッファでメモリコピーとGPU間転送を重ねる。A100/H100実機、AzureとServeGenの実ワークロード由来トレースで、既存方式よりSLO準拠有効スループットを最大5.3倍にし、低負荷から高負荷まで動的な実行構成変更の価値を示す。

Nitsumの中心的な新規性は、テンソル並列度を配備時の固定値ではなく、SLO達成率を改善する実行時制御変数として扱い、プリフィル/デコードのGPU台数と要求スケジューリングまで一体で決める点にある。そのために、各GPUへモデル重みを1コピーだけ常駐させたまま並列度ごとのシャードをカーネル側で選ぶ重み再利用、候補並列度ごとの実行プロセス事前起動、断片KVを集約して二重バッファで転送する高速移行を組み合わせ、再構成をミリ秒級へ縮める。この低コスト切替を前提に、約1秒周期で到着率とSLOから各階層の資源構成を再計算できる。

代表結果として、SLO準拠有効スループットはA100/H100、Azure/ServeGenトレース、8B/14Bを含む多階層SLO評価でLlumnix、Chiron、Split、SGLang系に対して既存方式比で最大5.3倍。負荷と階層構成に応じてTPとGPU配分を変え、要求のサービス時間と待ち時間の両方を調整できるため、高負荷で固定構成が飽和した後もSLOを満たす要求を残せる。
## 問題設定
同じGPU予算で、応答性を重視する対話要求と、遅延を許容できる背景要求を同時に処理すると、各階層が要求する初回トークン時間（TTFT）と出力トークン当たり時間（TPOT）が異なるため、単純な共有や固定分割では資源を使い切れない。従来のSLO対応サービングは、待ち行列、バッチ、要求移行、自動スケーリングなど「いつ・どのGPUで要求を実行するか」を主に変えるが、モデルを何基のGPUへ分割して実行するかというテンソル並列度はほぼ固定する。しかしテンソル並列度はプリフィルの計算時間だけでなく、低バッチ時には重み行列のキャッシュ効率とGPU間通信の釣り合いを通じてデコード効率も変える。実トレースでは最適な並列度とプリフィル/デコード配分が秒単位で変わり、固定構成は動的な理想構成より総有効スループットが23〜29%低い。一方、素朴に並列度を変更すると重み再読込、カーネル再初期化、KVキャッシュ再配置に秒〜数十秒かかり、負荷変動へ追従する前に再構成時間が利益を打ち消す。
## 新規性
Nitsumの中心的な新規性は、テンソル並列度を配備時の固定値ではなく、SLO達成率を改善する実行時制御変数として扱い、プリフィル/デコードのGPU台数と要求スケジューリングまで一体で決める点にある。そのために、各GPUへモデル重みを1コピーだけ常駐させたまま並列度ごとのシャードをカーネル側で選ぶ重み再利用、候補並列度ごとの実行プロセス事前起動、断片KVを集約して二重バッファで転送する高速移行を組み合わせ、再構成をミリ秒級へ縮める。この低コスト切替を前提に、約1秒周期で到着率とSLOから各階層の資源構成を再計算できる。
## 手法
### 手法のあらまし
サービス開始前に、モデルについてテンソル並列度、バッチサイズ、系列長ごとのプリフィル時間とデコード性能を測定する。実行中はグローバルスケジューラが最近の要求到着率、プロンプト長・出力長の分布、各階層のTTFT/TPOT目標を観測し、既定では1秒ごとに新しい構成を選ぶ。各候補について、ある階層がSLOを満たしながら処理できる要求数をプリフィル側とデコード側の処理能力から見積もり、GPU 1基当たりのSLO準拠有効スループットを計算する。需要に対して十分処理できていない階層の重みを上げる貪欲割当てにより、特定階層だけが資源を独占しないようGPUを順次配る。選ばれた構成では、階層ごとにプリフィル/デコードGPU群とテンソル並列度が変わる。

並列度を変更する際、通常のように別形状の重みをホストやストレージから読み直さない。各GPUは完全なモデル重みを1コピーだけ保持し、カスタムGPUカーネルが現在のテンソル並列度に対応する範囲を参照する。CUDA Graphや`torch.compile`などの初期化を要求時に行わないよう、候補となる並列度ごとのプロセスも事前に起動・準備し、選ばれたプロセスだけを活動状態にする。これにより重みの複数コピーを保持するよりメモリを節約しつつ、再初期化の秒単位停止を避ける。

既存要求が持つKVキャッシュは並列度変更時にGPU間で再分配する必要がある。ページ化注意機構ではKVが小さな非連続領域へ分散するため、多数の小さな`cudaMemcpyAsync`を発行すると転送効率が悪い。Nitsumはカスタムカーネルで必要なKV領域を連続バッファへ集約し、二つのバッファを交互に使ってGPU内集約とNVLink等のGPU間転送を重ねる。移行が十分短くなるため、複雑な生移行ではなく短時間停止して移す方式を選べる。

要求処理ではグローバル待ち行列を基本的に先着順で見ながら、背景階層は受入れ可能GPUへラウンドロビンし、それ以外は現在の階層用GPUが残すSLO準拠処理帯域から要求が間に合うかを判定する。間に合う要求は最も負荷の低いプリフィルGPUへ置き、間に合わない要求も最善努力として処理する。各GPUのローカルスケジューラはSLO達成可能要求を優先して反復バッチへ入れ、残容量へ最善努力要求を追加する。これにより構成変更と要求順序が別々に最適化されて互いを打ち消すのを避ける。

### 再読込不要のテンソル並列切替
各GPUにモデル重みの完全コピーを一つだけ保持し、テンソル並列度ごとに別の重みファイルや複数コピーを置かない。実行カーネルが現在の並列度に必要な重み範囲を選ぶため、並列度変更時のホスト・ストレージからの再読込を消す。さらに候補となるTP=1/2/4/8などの実行プロセスをあらかじめ立ち上げ、CUDA Graphやコンパイル済みカーネルを準備して休止させる。構成変更時は該当プロセスを有効化するだけなので、通常なら10秒〜1分以上かかり得る初期化を要求経路から外せる。ただし完全重みを各GPUへ置くため、メモリ容量に余裕がないモデルでは適用範囲が狭くなる。

### 集約・パイプライン化KVキャッシュ移行
テンソル並列度が変わると、要求ごとのKVヘッドを新しいGPU集合へ分配し直す。ページ化されたKVは物理的に断片化しているため、そのまま多数の小転送を発行すると制御オーバーヘッドと帯域利用率の低下が大きい。NitsumはGPUカーネルで対象ページを連続バッファへ集め、移行管理側が要求識別子、KVヘッド、文脈長などのメタデータを交換して送受信範囲を決める。二重バッファにより、一方をGPU内で集約している間に他方をGPU間転送し、メモリコピーと通信を重ねる。0.5〜5GBのKV移行で素朴な非同期コピーが0.88〜9.25秒かかったのに対し3.6〜24.8msへ短縮し、短時間停止方式でも頻繁な切替が可能になる。

### 有効スループット指向の資源再構成と要求スケジューリング
グローバルスケジューラはオフライン測定値と直近負荷から、階層ごとのプリフィルGPU数、デコードGPU数、それぞれのテンソル並列度を候補として評価する。単純な総スループットではなく、TTFTとTPOTを両方満たせる要求数をGPU数で割った効率を使い、さらに需要に対して処理不足な階層の重みを増やして貪欲にGPUを割り当てる。要求到着後は現在の残存SLO準拠帯域から達成可能性を判定し、達成可能要求を優先して最も空いているGPUと反復バッチへ配置する。負荷推定が外れた場合でも要求自体は最善努力経路へ残るが、予測が大きく外れたり制御周期が長すぎたりすると最適構成への追従が遅れる。

### 全体のデータ／制御の流れ
同一モデルを提供する均質GPUクラスタを、階層ごとのプリフィル群とデコード群へ動的に分ける。単一のグローバルスケジューラが約1秒周期で負荷統計と性能プロファイルから資源構成を計画し、各GPUのローカルスケジューラがSLO達成可能性を考慮して反復バッチを作る。並列度変更時は事前準備済み実行プロセスへ切り替え、移行管理器がKVを再配置する。制御系は要求のクリティカル経路から分離され、128 GPU・4要求群でも再構成計画は平均2.49msと報告される。
## 評価条件
- **ハードウェア**: RunPodクラウド上で、1ノード8基NVLink接続のNVIDIA A100 80GBまたはH100 80GBを使用する。A100ノードは128 vCPUと2TBシステムメモリ、H100ノードは224 vCPUと2TBシステムメモリ。主要エンドツーエンド評価は4または8 GPU、拡張性は4〜64 GPU、制御系は最大128 GPU相当で測定する。
- **ソフトウェア**: SGLangを基盤とし、グローバルスケジューラ、ローカルスケジューラ、GPUカーネル、KV移行を合わせて約1.2万行変更・追加する。Llama 3.1 8B、Llama 3.1 70B、DeepSeek-R1-Distill-Qwen-14Bを16ビット精度で使用する。
- **データセット／トレース**: Azure production LLM serving chat トレース、Azure production LLM serving coding トレース、ServeGen conversation ワークロード、ServeGen code-generation ワークロード
- **比較対象**: Llumnix、Chiron、階層ごとにGPUを固定分割し各階層で最良静的TPを使うSplit、プリフィル・デコード分離を追加したSGLang、標準SGLang
Azure本番LLMトレースからチャットとコード処理の代表10分区間を選び、Alibaba Cloud Model Studioに合わせたServeGenから会話とコード生成の各10分トレースを使う。Azureチャットは平均プロンプト1155、出力211トークン、0.5要求/秒、Azureコードは2048/28トークン、2.3要求/秒。ServeGen会話は871/86トークン、10.66要求/秒、コードは912/148トークン、11.94要求/秒である。公開された本番SLO値がないため、モデルが収まる最小TPで単一要求を流した平均TTFT/TPOTを厳格階層、バッチ128の平均値を緩和階層の基準として設定する。要求到着率を変え、TTFTとTPOTを両方満たした要求/秒を有効スループットとして比較する。
主要結果はA100/H100実機で測定され、シミュレーション中心ではない。ワークロードはAzure実トレースとServeGenの本番較正トレースを使う一方、SLO閾値自体は公開本番値ではなくマイクロベンチマークから構成した合成値である。モデルは8B・14B・70B、精度は16ビット、クラスタは主に4〜8 GPUで、異種GPU混在クラスタや複数モデル同時配置は対象外である。
## 主要結果
Nitsumは負荷が高く階層ごとの最適テンソル並列度が頻繁に変わる条件ほど効果が大きく、全評価設定で比較対象以上のSLO準拠有効スループットを示し、最大5.3倍を報告する。アブレーションでは要求スケジューラだけでも14B・8 H100・70要求/秒で28.0要求/秒まで伸びるが、素朴な動的TP切替を加えると再構成コストで0まで崩壊し、高速切替を含む完全系で33.3要求/秒へ達する。つまり利益は「動的TPを選ぶ」だけでは得られず、KV移行と重み切替をミリ秒級にしたことが成立条件である。

- SLO準拠有効スループット / 既存方式比で最大5.3倍 (比較対象: Llumnix、Chiron、Split、SGLang系; 条件: A100/H100、Azure/ServeGenトレース、8B/14Bを含む多階層SLO評価) — 負荷と階層構成に応じてTPとGPU配分を変え、要求のサービス時間と待ち時間の両方を調整できるため、高負荷で固定構成が飽和した後もSLOを満たす要求を残せる。

- KVキャッシュ移行時間 / 0.5〜5GBで3.6〜24.8ms、素朴な非同期コピー比245〜376倍高速 (比較対象: 断片ページをcudaMemcpyAsyncで転送; 条件: TP変更時のKV再配置マイクロベンチマーク) — 断片を連続バッファへ集約し、GPU内コピーとGPU間転送を二重バッファで重ねることで、多数の小転送の固定費を削減する。

- アブレーション有効スループット / 13.2→16.7→17.2→28.0→33.3要求/秒、素朴な動的切替は0要求/秒 (比較対象: 標準SGLangから機構を段階追加; 条件: DeepSeek-R1-Distill-Qwen-14B、8 H100、70要求/秒) — SLO認識スケジューリングが大きく効き、さらに高速TP切替を組み合わせると追加利益が出る。一方、遅い切替は動的並列化の利益を完全に相殺する。

- クラスタ拡張性 / 4〜64 GPUでほぼ線形に増加、同等性能に比較対象は1.5〜4倍のGPUが必要 (比較対象: 比較対象サービング方式; 条件: 全体SLO達成率80%以上を維持できる最大要求/秒で比較) — 制御器が小さなTP候補集合だけを探索し、要求経路から分離されているため、クラスタ規模を増やしても計画処理が主ボトルネックになりにくい。

- グローバル制御系性能 / 50,000要求を3.1秒で振り分け16.1K要求/秒、128 GPU・4要求群の再構成計画2.49ms平均 (比較対象: 単独の制御系測定; 条件: 128モデル複製を想定したスケーラビリティ評価) — 約1秒の制御周期に対して計画時間は十分短く、制御処理そのものがデータ経路を塞がない。

### 負の結果・境界条件
- 低負荷ではGPU余力が大きいため各方式の差が小さい。SLOを非常に緩くすると各階層の最適構成が低TPへ収束し、動的切替の利得は縮小する。14B・8 H100・70要求/秒のアブレーションでは、プリフィル/デコード分離だけのSGLangと、遅い重み/KV切替を使う動的TPはいずれも有効スループット0まで崩壊した。高負荷ではNitsumでもp90はSLO内に保つ一方、p99はSLO違反を始める。制御周期も短すぎると再構成オーバーヘッド、長すぎると負荷追従遅れが生じ、0.5〜1秒付近が最良で全体変動は約6%だった。

### 結果の読み方
Nitsumの効果は、階層化されたSLOが異なる実行構成を好み、かつ負荷が時間変動する場合に生まれる。厳格なTTFTには高TPによるプリフィル短縮が有利で、低バッチのデコードでも重みキャッシュ効率により高TPが有利になり得る。一方、高バッチや緩いSLOではGPU間通信の追加コストが効き、低TPが総スループットに有利になる。この最適点の移動を1秒程度で追跡し、その切替コストを数十ms以下へ抑えることが、固定構成との差につながる。
## 品質への影響
モデル計算の近似やKV圧縮を導入しておらず、同じ重みとKV内容を別のテンソル並列配置で実行するため、生成品質を犠牲にして速度を得る方式ではない。評価指標は出力品質ではなくTTFT/TPOTのSLO達成であり、最善努力へ回された要求は遅延目標を外す可能性があるが、意味的な出力品質低下は本方式の設計要因ではない。
## 既存研究との差
Llumnixは要求をGPUインスタンス間で移して負荷をならすが、モデルの実行並列度自体は固定する。QLMはグローバル待ち行列、追い出し、ウォームスタートなどで待ち行列競合を抑える。Chironは背圧と自動スケーリングでバッチやインスタンス数を変え、SCOOTは推論エンジンの外部パラメータを調整する。これらに対しNitsumは、要求の置き場所だけでなく、テンソル並列度を変更して1要求のプリフィル時間とデコード効率そのものを動かす。さらにプリフィル/デコードGPU配分と要求達成可能性判定を同じ制御ループへ入れる点が特徴である。
## 限界
各GPUへモデル重みの完全コピーを置く設計は切替を速くする代わりにメモリ容量を消費する。論文自身も追加メモリ負担を制約として挙げ、メモリが厳しいモデルやクラスタでは利用可能なTP候補が狭まる。性能判断は直近の到着率と要求長分布、事前測定プロファイルに依存するため、急激で予測不能な変化では最適構成への追従が遅れる。対象は均質GPUクラスタで単一モデルを複数SLO階層へ提供する設定であり、異種GPU、複数モデル同居、広域ネットワークは未評価である。本番のTTFT/TPOT SLO値が公開されていないため閾値はマイクロベンチマーク由来であり、実事業者の契約SLOで同じ倍率が出るとは限らない。高負荷p99ではNitsumもSLO違反を起こす。安定負荷では固定TPで十分な場合がある。

## 研究上の位置づけ
多階層SLO対応のLLMサービングと動的並列化の交差点に位置する。従来のサービング研究では要求スケジューリング、KV移行、クラスタ分割、自動スケーリングが主な制御面だったが、本研究はテンソル並列度を秒単位で変えられる実行構成資源として追加する。特に、低バッチ時には高TPがGPU内キャッシュ効率の改善によりGPU間通信コストを上回る場合があるという観測を、実際のSLO制御へ接続した点が重要である。将来のサービング基盤では、要求の優先順位だけでなく、並列度・段階分離・メモリ配置を一体で動かす制御器の比較基準になる。
