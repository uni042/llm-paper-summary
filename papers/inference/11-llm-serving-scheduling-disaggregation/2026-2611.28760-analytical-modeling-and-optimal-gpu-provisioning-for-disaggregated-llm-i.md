# Analytical Modeling and Optimal GPU Provisioning for Disaggregated LLM Inference

> 分離推論のプリフィル・デコード間GPU配分を、タイル単位の解析的容量モデルと釣り合いの閉形式、整数探索でプロファイルなしに求め、H100で容量誤差3.5%・ステップ時間誤差約9%を達成し全配分の実測6条件全てで最適配分を選んだプロビジョニング手法。

## 概要

分離サービングは、入力を一括処理するプリフィルと、トークンを逐次生成するデコードを別々のGPUプールへ置く構成である。各フェーズに最適化できる反面、プール間のGPU配分を誤ると、速い側のプールが遅い側を待って全体のスループットが遅い側で決まる。問題は最適な配分比が固定ではないことで、入力が長いほどプリフィルの仕事は増え、出力が長いほどデコードの仕事が増えるため、最適比は入力長で3.3倍から4.9倍動き、出力長では8.0倍から13.2倍動く。著者らの試算では、1つの比を全ワークロードへ使い回すと最悪条件で41%から43%のスループットを失う。

この配分を決める従来の方法は、候補構成を実機で測るプロファイル型か、ピーク性能と帯域だけから見積もるルーフライン型だった。前者は構成のたびに測定が要り、後者は誤差が大きい。本論文の OSplit は第3の道として、演算ごとの時間をハードウェアの構造から解析的に推定する容量モデルを作る。行列積はタイルと波の単位で、注意はキーブロック更新同士の重なりまで、集合通信は段階単位でモデル化し、L2キャッシュのヒットや最終波の partial な空き、小さいカーネルの固定費まで入れる。この容量から両フェーズのリクエストあたり費用を出し、スループットが釣り合う配分比を閉形式で求め、整数台数と並列度の制約の下で最適構成を探索する。代表結果として、H100 で容量予測の誤差は平均3.5%、プリフィル時間9.0%、デコード時間9.4%にとどまり（ルーフラインは57%と40%）、8GPUの全配分を実測した6条件全てで実測最適の配分を選んだ。

## 問題設定

ここで余っているのは、配分を誤ったときに速い側のプールに生じる待ち時間であり、足りないのは測定なしで信用できる容量の見積もりである。プリフィルは多数の行を一度に処理するためテンソルコアの処理能力が効きやすく、デコードは行数が少なく重み読みと固定費が支配的になりやすいという対照があるため、単純な演算量と帯域の比では両フェーズを同じ物差しで測れない。ルーフラインの誤差がプリフィルで大きくなるのは、注意でピーク性能を仮定し波の埋まり具合を無視するためで、デコードで大きくなるのは小さいカーネルの固定費やホスト側のステップ費用を演算量と帯域だけでは表せないためである。さらに配分の決定には絶対値の正確さとは別の性質が要る。両フェーズに同じ方向の誤差が乗るなら配分比は動かないが、フェーズ間で誤差の向きが違うと比がずれ、その損失は比の大小で非対称になる。本論文はこの「配分決定に必要な精度」の構造まで含めて問題を定式化している点が、単なる性能予測の論文と違う。

## 手法のあらまし

入力はモデル、GPU、分離対象のフレームワーク（vLLM）、ワークロード（バッチ、最大系列長、平均の入力長と出力長）である。まず容量モデルが、候補となる並列度ごとに、メモリから決まる最大バッチと、演算時間モデルから決まる反復時間を計算する。反復時間は層ごとの正規化、注意、全結合の時間の合計で、各演算の時間はテンソルコア、L2、HBM、相互接続のうち律速する資源で決まる。次にプリフィル側は「1リクエストに要するGPU秒」、デコード側は「出力トークン1個に要するGPU秒」へ換算し、両プールの処理能力が一致する配分比と、そのときのGPUあたりスループットを閉形式で得る。最後に、並列度の候補全てについて整数台数の配分を評価し、実際に置ける構成の中で最良のものを選ぶ。出力は vLLM の並列度やトークン予算などの設定値へ写像される。

## 手法

### 1. タイル単位の演算時間モデル — 容量を構造から推定する

この機構が観測するのはモデルとGPUの仕様およびGPU種別ごとに一度だけ測る定数（到達帯域やステップあたりのホスト費用など）であり、保持する状態は演算ごとの律速資源の内訳である。行列積については、タイルの大きさと分割Kの候補を列挙し、各候補でブロック数、波の数、最終波の空き、L2ヒットの確率（スタック距離モデル）まで入れて時間を計算し、最も速い構成の時間を採用する。注意については、デコードではキャッシュの分割数と部分結果の統合費用を、プリフィルではキーブロック更新同士の重なりを「1回目の更新の費用」と「2回目以降の追加費用」の形で表す。MoEについては、最も忙しいGPUの負荷の偏りと、デコードで活性化するエキスパート数まで入れる。集合通信は段階ごとの最遅転送に固定遅延を加えて表す。効く理由は、ルーフラインが落としていた「波の端数、キャッシュの効き、固定費」という、実際の律速要因を式へ戻した点にある。追加費用はGPU種別ごとの定数測定で、運用やモデルごとの再測定は不要とされる。失敗条件は、カーネルの実装が想定と違う場合で、フレームワークの版が変わってカーネル選択が変わればモデルの前提もずれる。

### 2. 釣り合い配分の閉形式 — 費用の比が最適比を決める

容量モデルが出力するプリフィルの費用 P（1リクエストのGPU秒）とデコードの費用 D（出力トークン1個のGPU秒）から、平均出力長を掛けた総費用の比が最適なGPU配分比になる。全体のスループットは遅い側のプールで決まるため、両プールの処理能力が一致する点が最適であり、GPUあたりスループットは総費用の逆数として得られる。この形により、プリフィル側の並列度は P を最小化するもの、デコード側は D を最小化するものと独立に選べる。感度の解析もこの形から導かれ、配分比を最適から外したときの損失は方向で非対称で、最適比が1未満の場合はプリフィル側を少なく配る誤りのほうが高くつく。また予測誤差については、両フェーズに共通する誤差は比を動かさず、フェーズ間で異なる誤差だけが配分をずらすことが式で示される。これは「絶対誤差が1割あっても配分は正しく選べる場合がある」ことの理論的な裏づけであり、後述の評価結果の読み方を決める性質である。

### 3. 整数配分と並列度の探索 — 置ける構成の中で最適を選ぶ

閉形式の最適は連続値だが、実際のプールは並列度の倍数台でしか構成できない。この機構は、プリフィルとデコードの並列度候補（注意ヘッドの割り切り条件、メモリへ収まる条件、デコードではトークン間時間の制約を満たす条件を通ったもの）全ての組について、連続最適の近傍にある整数配分だけを評価し、最もスループットの高い組を返す。連続最適の前後の候補だけを見ればよいのは、配分を一方向へ動かすとスループットが単調に下がる構造があるためで、全数探索を避けられる。結果として1配分の探索は CPU 1コアで0.39秒から0.82秒で終わる。出力は vLLM の設定へ直接写像され、プリフィルとデコードのインスタンス間は NIXL コネクタで KVキャッシュを NVLink 経由で渡す構成が想定され、その転送時間は計算時間の約1%で次プリフィルと重なるとされる。失敗条件は、候補の前提（割り切り条件やメモリ条件）を満たす構成が存在しない大きなモデルで、例えば405B級は1ノード内では配分自体が測れないことが評価でも明記されている。

### 4. データと制御の流れ

運用者の流れは、モデルとGPUとワークロードを与えると、容量モデルが候補ごとの費用表を作り、閉形式が連続最適を与え、整数探索が置ける最良構成を返し、その構成が vLLM の引数へ写像されて2つのプールが起動する、という一方向の手順である。実行時の適応やフィードバックはなく、ワークロードが変われば再計算して再配分する前提の設計である。再計算自体が秒単位で終わるため、条件が変わるたびに回す使い方が可能だと著者らは位置づける。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 演算時間モデル | モデル仕様とGPU定数 | タイル・波・キャッシュ・固定費から反復時間を推定 | 容量見積もりの誤差 | カーネル実装の変化に弱い |
| 釣り合いの閉形式 | 両フェーズのGPU秒 | 処理能力が一致する配分比を導出 | 配分の決定 | 連続値の最適であり整数化が別途要る |
| 整数探索 | 並列度候補と台数 | 近傍の整数配分を評価し最良構成を返す | 実配置への落とし込み | 候補が存在しない規模では使えない |

## 評価

### まず見るところ

- **結論:** 解析モデルは、配分決定に十分な精度をプロファイルなしで達成し、実測した全条件で最適配分を選んだ。絶対精度はGB300側でやや落ちるが、配分の結論は保たれている。
- **速度・効率:** 本手法自体の費用は CPU 1コアで1配分0.39秒から0.82秒、全探索の試算でも8コア112秒であり、実機プロファイルの反復に比べれば無視できる水準である。
- **品質:** 生成品質には関与しない。評価対象は予測誤差と配分選択の正しさである。
- **メモリ・入出力:** KV容量の予測誤差は H100 で平均3.5%、GB300 で5.0%。容量そのものの削減手法ではない。
- **評価の強さ／注意点:** 予測誤差の測定点は多い（H100でステップ時間100件、GB300で336件）が、配分そのものの検証は H100 の8GPUノード、2モデル、3ワークロードの6条件に限られ、GB300 の NVL72 での配分の実測検証はない。

この評価で最初に見るべきなのは、予測誤差の非対称な意味である。H100 では容量の誤差が平均3.5%（モデル別0.9%から6.7%）、プリフィル時間の誤差が9.0%、デコード時間の誤差が9.4%だった。ルーフラインは同じ条件でプリフィル57.2%、デコード39.7%の誤差であり、特にデコードでは小さいカーネルの固定費とホスト費用を落とすことが誤差の主因だと本文は分析している。プリフィルでは入力長を1Kから32Kへ変えても Llama-8B の相対誤差が-6.3%から-8.0%の範囲に収まっており、誤差の向きが条件によらずそろう傾向が見える。手法の感度解析が示すとおり、配分を動かすのはフェーズ間で異なる誤差だけなので、この「そろった誤差」は配分の正しさにとって相対的に無害である。逆にGB300ではプリフィル19.9%、デコード16.8%と誤差が広がり、モデル別ではプリフィルで最大26%の例もある。新しいハードウェアでは定数とカーネル前提の較正が追いついていない可能性を示す数値であり、絶対値の予測として使う場合の留保になる。

配分の検証は、8GPUノードをプリフィル台数1から7まで全て振って実測した6条件（Llama-8B と Qwen3-30B、各3ワークロード）で行われ、OSplit は6条件全てで実測最適の台数を選んだ。スループット曲線そのものの予測誤差の中央値は8.4%から27.0%で、長い入力の W3 条件では25.0%と27.0%と大きく、比較対象の AIConfigurator のほうが近い条件もある（19.5%と20.9%）。W2 では逆に OSplit が8.4%から13.1%、AIConfigurator が14.1%から30.0%だった。重要なのは、曲線の絶対誤差が2割超でも台数の選択は外れていない点で、台数は1台単位でしか変わらず、比の誤差が隣の配分と同点になる境界を越えなければ結論が保たれるという本文の説明と整合する。ただし裏を返せば、この検証は「台数の粒度が粗い8台構成」での結果であり、NVL72 のような大規模ドメインで比の解像度が細かくなった場合に同じ頑健さが保たれるかは未評価である。GB300 側の配分はモデルの予測として提示されるだけで、実測の全配分比較は行われていない。

第7節の応用分析は、配分を固定することの損失を定量化している。最適比は入力長に対して3.3倍から4.9倍、出力長に対して8.0倍から13.2倍動き、単一の比を全条件へ使うと最悪条件で全モデル共通に41%から43%のスループットを失う。デコード時間に占める注意の割合も入力長で大きく動き、Llama-8B では66%から90%、70Bでは33%から65%、405Bでは7%から17%と、モデル規模で様相が違う。大きなモデルでは重み読みが支配的でバッチ拡大による償却が効き、小さいモデルでは文脈が伸びるほど KV 読みが支配的になる。この分析は配分ツールとしての主張を超えて、「分離構成の配分はワークロードの申告なしには決められない」という運用上の含意を持つ。未評価の軸としては、到着過程が変動する動的負荷での再配分の効果、遅延制約を入れた場合の配分の実測、電力や費用を目的関数に入れた場合の結果があり、トークン間時間の制約はモデル内にはあるが配分検証の主結果には含まれていない。

## 既存研究との差

分離サービング自体は DistServe、Splitwise、Mooncake などが確立し、その後の研究は配分比の動的調整や強化学習によるスケーリングへ進んだ。性能予測では Vidur がプロファイルとシミュレーションを組み合わせ、AIConfigurator が測定データベースで構成を最適化する。本論文の差は、データベースも運用ごとのプロファイルも持たず、演算の構造から容量を解析的に出し、配分の最適を閉形式と整数探索で直接解く点と、誤差が配分へ効く条件（フェーズ間で異なる誤差だけが効くこと、損失の非対称性）までを理論側で明示した点にある。

## 限界・実装状況

- ハードウェア依存条件: 予測はGPU種別ごとの定数測定とカーネル実装の前提に依存する。GB300では誤差がプリフィル19.9%、デコード16.8%まで広がっており、新しいハードウェアやフレームワークの版では較正の追随が要る。
- モデル／ワークロード依存条件: 配分の実測検証は2モデル6条件に限られ、405B級は1ノードでは配分自体が構成できない。合成プロンプトでの測定であり、実トラフィックでの検証は未評価である。
- 実装状況: 解析モデルは Python 実装で vLLM の設定へ写像されるが、コード公開のURLは本文に示されていない。実行時の動的再配分は扱わない。
- 前提の限界: ワークロードの平均入力長・出力長が既知であることを前提とし、分布が時間で大きく変わる場合の追随方法は本論文の範囲外である。

## 一般的な実装上の含意

配分や構成の決定に予測モデルを使う場合、絶対精度そのものより「決定を動かす方向の誤差がどれだけか」を見るべきである。両選択肢に共通する誤差は決定を変えず、粒度の粗い決定（台数など）は誤差への頑健さを持つ。逆に、最適値が入力条件で数倍動く量を固定値で運用すると、予測以前の問題として大きな損失が出る。まず「決める量が条件でどれだけ動くか」を測ることが、最適化の前に要る作業である。
