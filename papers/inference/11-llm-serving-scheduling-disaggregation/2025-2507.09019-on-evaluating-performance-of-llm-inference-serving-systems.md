# On Evaluating Performance of LLM Inference Serving Systems

## 概要

本論文は、大規模言語モデル（LLM）の推論配信システムにおける性能評価の落とし穴を体系化した方法論研究である。新しいカーネルやスケジューラで処理速度を上げる研究ではなく、**既存研究が報告する高速化をどの条件なら公平に比較できるか**を論じる。特に、入力処理と逐次生成の資源特性の違い、入力・出力長の大きなばらつき、対話利用での生成停滞への敏感さが、従来の平均処理時間だけの評価を危険にすると指摘する。

著者らは評価上の悪習（anti-pattern）を三群・八項目に分ける。第一群は比較実装の公平性であり、アルゴリズム以外の実装差と、比較対象の調整不足を問題にする。第二群は実験条件であり、古いモデル、現実的でない要求負荷、許容できない絶対遅延を扱う。第三群は指標設計であり、目的に合わない指標、分布を隠す単一の要約統計、初期待ちや生成停滞を見えなくする正規化を取り上げる。さらに投機的復号（speculative decoding）を事例に、平均トークン時間が改善しても、トークン間隔の長い尾や初回トークン遅延が悪化し得ることを示す。

本論文の重要性は、単に「複数の指標を報告するべきだ」と主張する点ではない。どの指標がどの利用者体験に対応し、どの分母で正規化すると何が消えるのかを、具体的な負荷・比較方式・数値で説明する点にある。LLM推論の論文サーベイで異なる高速化倍率を横比較する際、再現性と適用範囲を監査するための共通基準として利用できる。

## 問題設定：LLM配信特有の評価の難しさ

### 二段階処理と要求待ち

LLM推論は、要求の到着から実行開始までの待ち、入力トークンを並列に処理する入力処理（prefill）、出力トークンを一つずつ生成する逐次生成（decode）に分かれる。入力処理は比較的大きな行列積を使うため演算性能が支配的になりやすい。一方、逐次生成は小さいバッチで重みやKVキャッシュを繰り返し読み、メモリ帯域や他要求との干渉が支配的になりやすい。このため、同じGPU上でも入力が長い要求と出力が長い要求では、使う資源と遅延の構造が違う。

要求が到着してから最初のトークンを返すまでの時間は、スケジューリング待ちと入力処理の合計で決まる。出力が始まってからは、各トークン間の待ち時間が対話の滑らかさを左右する。単に要求全体の平均時間を短くしても、最初の応答が遅い、あるいは途中で何秒も止まる方式は対話用途では好ましくない。反対に、非対話の一括要約では全完了時間や一定遅延制約内の処理容量を重視することがある。したがって、用途を指定せず「推論が何倍速い」と述べても意味が確定しない。

### 実運用負荷の異質性

論文表1は公開された実運用の要求記録（trace）を比較する。Azure Code 2024の入力長中央値は1928、出力長中央値は8、Azure Conversation 2024は入力928、出力41、Mooncakeの記録は入力6345、出力30である。Mooncakeの入力長99パーセンタイルは61616と極端に長い。平均だけでなく中央値、四分位範囲、99パーセンタイルが大きく違うため、短いチャットだけで最適化した方式が長文要約やコード補完で同じ効果を出す保証はない。

モデル側の変化も重要である。多問い合わせ注意（MHA）からグループ化問い合わせ注意（GQA）へ変わるとKVキャッシュの必要容量が減り、古いMHAを対象にしたメモリ最適化の効果が小さくなることがある。混合専門家（MoE）モデルでは重みのアクセスパターンや通信負荷も変わる。ある方式が古い密モデルで優位でも、現在のモデル系統へそのまま当てはめるのは危険である。

## 手法

### 指標の定義と使い分け

| 指標 | 定義 | 見たいもの | 単独利用の問題 |
|---|---|---|---|
| 初回トークン遅延（TTFT） | 要求到着から最初の出力まで。待ち時間と入力処理を含む | 対話開始の応答性 | 逐次生成中の停滞は見えない |
| 最終トークン遅延（TTLT） | 要求到着から全出力完了まで | 完成物が必要な作業の所要時間 | 途中の滑らかさを示さない |
| トークン間隔（TBT） | 連続する出力トークンの到着間隔 | 読み進める際の流暢さ | 中央値だけでは長い停滞を隠す |
| 出力トークン当たり時間（TPOT） | 逐次生成にかかった時間を出力数で割る | 平均的な逐次生成費用 | バーストと停止が平均化される |
| 正規化遅延 | 要求全体の遅延を出力トークン数で割る | 長さの異なる要求の比較補助 | 固定の初期待ちを出力数で薄める |
| 容量（capacity） | 指定した遅延目標を守りながら処理できる最大要求率 | サービスとしての持続可能な負荷 | 遅延目標を明示しないと値が変わる |

ここで、TPOTと正規化遅延は同じではない。TPOTは主に逐次生成段階の時間を出力数で割るのに対し、正規化遅延は待ち時間と入力処理を含む要求全体を出力数で割る。論文を比較する際には、分母のトークン数に初回出力を含むか、測定時間に待ちを含むか、出力長を実測か固定長で扱うかも確認する必要がある。

### 評価上の八つの悪習

### 1. 実装差をアルゴリズムの貢献と混同する

新方式と比較対象が別の実装基盤で動いていると、CPUのスケジューリング負荷、通信プロトコル、GPUカーネル、メモリ管理などの差が、方式固有の改善として計上されてしまう。原著はCPU側の負荷が遅延の50%以上を占める例を挙げる。たとえ同じモデルとGPUを使っても、比較対象のカーネルが古ければ「新方式が速い」のではなく「新しい実装の方が洗練されている」だけかもしれない。

具体例としてNanoFlowの細粒度バッチ化は総合スループット1.91倍を報告したが、構成要素除去実験では中核アルゴリズム単体の寄与が16%で、残りの多くはシステム実装の最適化に由来したと整理する。この区別を示すことが、方式の一般化可能性を判断するうえで重要である。評価時には同じコード基盤へ新機構だけを移植した比較や、段階的に最適化を加える実験が望ましい。

### 2. 比較対象の設定値を十分に調整しない

LLM配信には、バッチサイズ、入力処理の分割幅、入力処理用と生成用の資源配分、スケジューリング方針など多数の設定値がある。新方式を綿密に調整し、比較対象を既定値のまま使えば、比較対象が不当に不利になる。分離型の入力処理・逐次生成配信では、両段階へのGPU割当比率が性能を大きく変える。分割入力処理（chunked prefill）でも分割幅が遅延と処理容量の交換条件を左右する。

原著はDistServeやLoongServeの一部比較で、比較対象側の重要な分割幅の調整が十分報告されていない点を問題視する。一方、OrcaがFasterTransformerのバッチサイズを複数試した例を比較的良い実践として挙げる。サーベイでは、双方に同程度の探索予算を与えたか、最適化対象が同じ指標か、ハードウェア制約が等しいかを監査する必要がある。

### 3. 古い・不適切なモデルで評価する

モデル構造はメモリ最適化の効果を大きく左右する。MHAを使う古いモデルだけでKVキャッシュ削減を測ると、GQAを採用する現行モデルよりキャッシュ削減余地が大きく、実運用の改善幅を過大評価し得る。原著はDuoAttentionがMHAとGQAの両方を評価し、KV削減効果が2.55倍対1.67倍に縮む条件を示した例を、モデル構造の差を明らかにする良い実践として挙げる。

MoEでも活性化する専門家数と総重み数、通信量の関係が密モデルと異なる。量子化やオフロードの比較で、モデル系列、注意形式、重み精度、活性パラメータ数を明示しなければ、方式がどの資源制約を解決したのか判別できない。

### 4. 実運用を代表しない要求負荷を使う

ShareGPTなど単一の短文対話集合だけを使う、入力長を固定する、出力長の分布を無視する、合成要求だけで測ると、現実の長文・短文混在、複数ターン、急な要求到着、出力長の偏りを再現できない。論文はVidurの知見を引用し、ある負荷に最適化した構成が別の負荷では最大2倍ほど性能で劣る場合があると説明する。

実験では少なくとも、短入力短出力、長入力短出力、短入力長出力、長入力長出力を区別し、到着率、入力長と出力長の分布、要求同士の相関を記録するべきである。長い入力の処理が生成中の要求へ割り込むと、平均トークン速度が同じでも生成停滞が増える可能性がある。単一負荷での最高倍率は、その負荷に限定した結果として扱う。

### 5. 実用的な絶対遅延制約を無視する

相対的な高速化率が高くても、初回トークンに数十秒や数分かかる条件では対話用途として成立しない。原著は長文入力を扱うLoongServeの正規化指標を例に、入力長が極端に長い条件では、正規化した値から復元される絶対TTFTが数千秒以上になることを問題視する。分母を入力トークン数にした指標だけを見ても、実際の利用者の待ち時間を把握できない。

容量比較では「TTFTが何秒以内、TBTが何ミリ秒以内」というサービス水準目標（SLO）を指定し、その条件を守れる最大要求率を示す必要がある。遅延制約を緩めれば処理容量を増やせるのは当然なので、制約の違う二方式の最大スループットをそのまま比べてはならない。

### 6. 目的に合わない、定義の不透明な指標を選ぶ

一つの数字に要求全体をまとめた「平均遅延」や「トークン当たり時間」が、実際の一人の利用者が経験する時間と一致するとは限らない。原著はdLoRAで使われた、全要求の遅延合計を全出力トークン数で割る集計を例示する。この量は要求ごとの初期待ち、長さ、分布を混ぜてしまい、個別要求の待ち時間や末尾の悪化を隠す。

指標の定義式、測定開始時点、終了時点、集計単位を明記することが最低条件である。コード補完では完成までのTTLT、対話ではTTFTとTBT、一括処理では制約付き容量など、対象用途から指標を選ぶ。論文が「latency」とだけ書く場合は、どの遅延か不明なまま数値を比較しない。

### 7. 中央値や99パーセンタイルだけを報告する

中央値だけでは、少数の要求が長く待つ現象が見えない。反対に99パーセンタイルだけでも、90パーセンタイル付近の悪化を見逃す。原著はvLLMとSarathi-Serveの比較で、Sarathi-ServeのP99が良くてもP90付近では悪い条件を示し、P50・P90・P99を含む分布全体を見る必要性を論じる。

特に投機的復号では、複数トークンが一度に受理されると、連続するトークンの一部がほぼ同時に出力される。そのためTBT中央値が非常に小さくても、候補が外れて再検証が必要な場面で長い停滞が発生する。分布の片側だけを要約すると、実際の対話の滑らかさと逆の評価になり得る。

### 8. 正規化によって初期待ちや停滞を隠す

正規化遅延 `(待ち＋入力処理＋生成時間)/出力トークン数` は、出力が長いほど固定の待ち時間が薄まる。例えば二つの要求がどちらも10秒待ち、生成速度が20ミリ秒/トークンであっても、10トークンの要求は約1.02秒/トークン、1000トークンの要求は約0.03秒/トークンになる。両方の利用者は同じ10秒の初期待ちを経験したのに、正規化後の数字は大きく異なる。

原著のvLLMとSarathi-Serveの事例では、vLLMの要求の60%以上に25秒超のスケジューリング待ちが生じた条件があり、その差が正規化遅延の図では見えにくいと指摘する。TPOTも平均化のため、滑らかに一定間隔で出す方式と、まとめて出した後に長く停止する方式を同じ値にし得る。正規化指標は有用だが、絶対TTFTとトークン到着間隔の分布を併記して初めて解釈できる。

## 評価

### 事例研究：投機的復号を平均速度だけで評価すると何が起こるか

投機的復号は、軽いドラフトモデルが複数トークンを提案し、元モデルがまとめて検証する。成功すれば複数トークンが短時間に出力され、失敗すれば候補生成と検証の費用を払ったのに少数しか受理されない。出力間隔が均一でないため、通常の自回帰生成に適した平均指標だけでは利用者体験を捉えにくい。

原著図3の条件は、Llama 3 70B、H100 GPU 4基、ShareGPT系の負荷、到着率0.25要求/秒である。投機的復号では、受理バーストのため約75%のトークン間隔がほぼゼロとなる。一方で失敗時の長い間隔もあるため、TBTの分布は二峰性を帯びる。TBT中央値だけを見ると「ほとんど待たずに生成できる」と誤解しやすい。

TPOT中央値は自回帰方式より約1.3倍良い値を示す一方、99パーセンタイルのTPOTは約1.16倍悪いと報告する。さらにドラフトモデル側の入力処理が必要なため、初回トークン遅延（TTFT）が悪化する。したがって「平均トークン速度の改善」「最初の応答」「途中で止まらないこと」は同時に改善するとは限らない。

| 観測軸 | 投機的復号の事例で見えたこと | 誤った結論につながる指標 |
|---|---|---|
| TBT分布 | 約75%の間隔がほぼゼロ、残りに長い停止 | TBT中央値のみ |
| TPOT中央値 | 約1.3倍の改善 | 中央値だけなら一律に速いと誤認 |
| TPOTのP99 | 約1.16倍の悪化 | 平均だけでは末尾悪化を見落とす |
| TTFT | ドラフト側の入力処理費用で悪化 | 逐次生成の指標だけでは初期応答を見落とす |
| 期限遵守型の流暢度 | 生成停止の頻度を可視化できる | 単純なトークン/秒では停滞が見えない |

この事例は「投機的復号は利用すべきでない」という結論ではない。長い出力ではドラフトの初期費用を多数の生成トークンに分散でき、平均処理速度の改善が重要になる。逆に短い対話応答ではTTFTの増分が目立ち、長い停滞を嫌う音声対話では期限遵守型の流暢度が重要になる。方式の優劣は、対象用途と要求長の分布、受理率、SLOを指定して初めて決まる。

### 論文比較に使う監査チェックリスト

| 監査観点 | 確認すべき記録 | 不十分な場合の扱い |
|---|---|---|
| 比較基盤 | 両方式のカーネル、CPU負荷、通信、同じ実装基盤か | アルゴリズム単体の改善と断定しない |
| 比較対象の調整 | バッチ、分割幅、GPU配分、最適化の探索範囲 | 不公平な比較の可能性を明記 |
| モデル | 系列、規模、注意形式、MoE構成、KV容量 | 異なるモデルへの一般化を保留 |
| 要求負荷 | 入力・出力長分布、到着率、複数ターン、実運用記録か | 合成負荷・単一負荷に限定した結論とする |
| 絶対遅延 | TTFT、TTLT、TBT、待ち時間の内訳 | 正規化倍率だけで実用性を判定しない |
| 制約付き容量 | SLOを守る最大要求率と違反率 | 最大スループットのみでは容量比較不可 |
| 分布 | P50、P90、P99、可能なら累積分布 | 中央値またはP99のみの結論に留保 |
| 生成の滑らかさ | 各トークン到着時刻、停滞時間、期限遵守率 | 平均TPOTから体感速度を推測しない |
| 寄与分離 | 中核アルゴリズムと実装最適化の除去実験 | 全改善を新方式の貢献としない |
| 再現性 | ソース、測定条件、モデル版、乱数、サンプル数 | 未報告部分を明示し再現不能と区別 |

サーベイ原稿では、各研究の「最大何倍」を一覧へ並べる際、比較対象と測定指標を同じセルに記録することが重要である。例えば「通常自回帰比2.4倍の周期模擬スループット」と「別投機的復号比1.8倍の同一メモリ予算内トークン数」は別指標であり、同じ性能ランキングに統合してはいけない。

## 限界

### 研究としての貢献と限界

本論文の主な貢献は、個々の配信研究が報告する数字を疑うための具体的な監査観点を提示したことである。比較対象の調整不足、モデル構造の古さ、現実的でない負荷、分布を隠す正規化という問題を、LLM推論の二段階性と関連付けて整理する。さらに、投機的復号の平均速度と生成停滞の食い違いを、実際のモデル・GPU・負荷条件を明示して説明する。特に研究サーベイの品質監査に直結する内容である。

一方、原著の表2は既存論文における評価項目の有無を著者らが分類したものであり、各方式の性能を同じ実装環境で再測定した統一ベンチマークではない。表のチェック記号は評価方法の網羅性についての判断であり、その方式のアルゴリズムが優れているかどうかの評価ではない。論文自体が新しいスケジューラを実装して速度を上げたわけでもないため、通常の「高速化率」を本研究の成果として付けるのは不適切である。

また、適切なSLOは用途と製品要件に依存する。会話、音声、コード補完、バッチ要約に共通の絶対的な遅延上限を、この論文が一つ定めたわけではない。投機的復号の事例もLlama 3 70Bと4基H100の特定負荷であり、単一GPUの小型モデルや異なるドラフト受理率へ同じ比率を適用できない。チェックリストは比較を厳密にする道具だが、未測定の条件における速度を推定するモデルではない。
