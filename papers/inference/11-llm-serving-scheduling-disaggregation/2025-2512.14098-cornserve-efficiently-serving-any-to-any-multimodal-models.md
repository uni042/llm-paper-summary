# Cornserve: Efficiently Serving Any-to-Any Multimodal Models

> Cornserveが解くのは「大きなモデルを何GPUに置くか」だけではない。Any-to-Anyモデルでは、**要求の入力・出力モダリティごとに通る計算グラフが違い、同じモデル内部でも構成要素ごとにGPUの増やし方への反応が違う**。Cornserveはこの異質性を明示的な計算グラフとワークロード経路率として扱い、単体配置・分離配置・テンソル並列・複製数を一緒に決める。

## 概要

従来のテキストLLM配信では、一つの要求は概ね同じモデル経路を通る。入力長や出力長に差はあっても、主な構成要素はプリフィルとデコードを行う同じTransformerである。

Any-to-Anyマルチモーダルモデルでは事情が異なる。例えばテキスト・画像・動画・音声を受け取り、テキストまたは音声を返すモデルでは、入力モダリティ用エンコーダ、思考用LLM、音声トークン用LLM、音声生成器など複数の異質な構成要素が並ぶ。テキスト出力だけの要求は音声生成器を通らず、画像付き要求だけが視覚エンコーダを通るなど、要求種別ごとに経路が分岐する。

さらに、各構成要素のスケーリング特性も違う。大きいLLMはテンソル並列で複数GPUへ広げる価値がある一方、小さいエンコーダを単独GPUへ分離するとGPUを余らせることがある。拡散Transformerは反復計算が支配的で、自己回帰LLMとは最適な複製数が異なる。

Cornserveはモデル開発者に計算グラフをタスクとして記述させ、計画器がモデル・ワークロード双方を測って配置計画を作る。計画には「分離するか」「どの構成要素を同居させるか」「テンソル並列度はいくつか」「複製を何個作るか」が含まれる。実行ランタイムはその計画に従い、要求ごとに必要な構成要素だけを通す。

## 背景と問題設定

### 単体配置では一つの遅い構成要素が全体を止める

全構成要素を一つの大きなプロセス/ワーカーとして配置すると、ある時点で実行中の構成要素以外はGPU資源を有効利用できない。例えば音声生成が長時間GPUを占有している間、思考LLMや別要求の前処理が待たされる。

また、LLMのキー・値キャッシュ（KV cache）と大きいマルチモーダルエンコーダを同居させると、エンコーダがメモリを消費してLLMが保持できるKV量を減らす。結果としてバッチが縮小したり、要求の待ち行列やプリエンプションが増える。

### 「全部分離」も最適ではない

逆に、各構成要素へ専用GPUを与えればよいわけでもない。小型エンコーダは処理時間が短く、専用GPUへ置くと大半の時間が遊休になる。そのGPUをLLMから取り上げたためにLLMのKV容量が減れば、むしろ全体スループットが落ちる。

Cornserveの重要な設計判断は、分離配信（disaggregated serving）を目的ではなく**候補の一つ**として扱う点にある。実際の評価では、Qwen2.5-VL 32Bのように単体配置が最良のモデルに対し、計画器は無理に分離せず既存最良構成へ一致する。

### 要求経路の割合まで含めないと複製数を決められない

同じモデルでも、音声出力要求が多いワークロードでは音声生成器が律速になる。テキスト出力中心なら音声生成器へ多数GPUを割く意味はない。

したがって配置はモデル構造だけから決められない。各要求種別がどの経路を何%通るか、その構成要素が一要求をどれだけ処理できるかを組み合わせて、各経路の流量を支えられる配置を作る必要がある。

## 手法

### 1. モデルをタスク計算グラフとして表現する

Cornserveでは、マルチモーダルエンコーダ、自己回帰LLM、拡散Transformer（Diffusion Transformer; DiT）、音声生成器などを独立したタスクとして記述し、テンソル依存関係を辺としてつなぐ。

この抽象化により、特定モデル名へハードコードせず、「画像がある要求だけ視覚エンコーダを通る」「音声出力ならTalkerと音声生成器へ進む」といった条件分岐を同じグラフで表せる。

分離配置の単位もこのタスク境界になる。計画器は二つのタスクを同居させる案と別GPU群へ分ける案の両方を候補にできる。

### 2. 各構成要素のスケーリング特性を測る

同じGPU数を追加しても、構成要素によって処理能力の伸び方は違う。Cornserveは構成要素ごとに、テンソル並列度、複製数、入力特性などに対する実効処理量を測り、計画の性能モデルを作る。

ここで重要なのは、単に「一番速い単体構成」を選ばないことである。ある構成要素を高速化しても、後段が遅ければ待ち行列が移るだけで全体スループットは上がらない。グラフ全体の経路流量を満たすよう資源を配る。

### 3. 計画器が分離・同居・並列度・複製数を共同探索する

計画器は利用可能GPU数とワークロード分布を受け取り、各タスクをどのGPUセルへ置くかを探索する。候補には単体配置も含むため、分離オーバーヘッドが得にならない場合は分離しない。

代表例としてQwen3-Omniを8GPUで配信する場合、計画器はThinker LLMをテンソル並列2で1複製、Talker LLMを5複製、音声生成器を1構成とする分離案を選ぶ。16GPUへ増やすと、Thinkerをテンソル並列2で3複製、Talkerと音声生成器を同居させた10複製へ変える。

GPUを2倍にしただけで同じ構成を2倍コピーするのではなく、**どこが次の律速になるかに応じて構成比そのものを変える**のがポイントである。この例では16GPU化でスループットが2.68倍となり、単純な線形複製より大きい改善が出る条件を示す。

### 4. 要求静的ルーティングで実行時制御を軽くする

計画段階で、各要求経路をどの複製へどの割合で送るかまで決める。実行時に毎回全ワーカーの待ち行列を問い合わせて最小キューを探すのではなく、計画済みの比率に従う要求静的ルーティング（request-static routing）を用いる。

これは計画器がワークロード経路率を既に考慮しているから成立する。制御面で頻繁な状態収集をせず、計画どおりの流量を各構成要素へ与えられる。

### 5. 構成要素間は生成側から消費側へ直接テンソルを渡す

分離したタスク間で中間テンソルを中央コーディネータ経由にすると、CPUコピーや余分なネットワーク転送が増える。Cornserveの分散ランタイムはデータ依存関係を追跡し、生成した構成要素から次の消費構成要素へ直接テンソルを送る。

後続の公開実装では記録・再生型（record-and-replay）実行を用い、制御処理とデータ面を分離する。Kubernetes上で複数GPUノードへ展開しつつ、要求ごとの分岐した計算経路を実行できる。

## 一要求の流れ

要求が到着すると、入力モダリティと希望出力から通るタスク列が決まる。例えば画像・音声付き入力からテキストを返す要求なら、必要な入力エンコーダとThinker LLMを通るが、音声出力生成器は通らない。

ルータは計画済みの割合に従って各タスクの複製を選ぶ。前段タスクが出力した中間テンソルは直接後段タスクへ送られ、不要な構成要素は起動しない。各複製は自身の構成要素に適したバッチ方式で処理できるため、例えば分離した自己回帰生成器で連続バッチ処理を使いやすくなる。

ワークロード分布や利用GPU数が変わった場合は、同じ配置を固定使用するのではなく計画器を再実行し、分離境界と複製比率を変える。

## 評価

### 代表的な評価条件

| 項目 | 条件 |
|---|---|
| クラスタ | 同一拠点2ノード |
| GPU | 各ノードNVIDIA A100-80GB ×8、計16GPU |
| ノード内接続 | NVLink |
| ノード間接続 | RDMA、少なくとも400Gbps |
| 主指標 | 要求スループット、P50/P90/P95/P99遅延 |
| 定常計測 | 原則2,000要求以上を投入し、立上り/終了を除く定常区間で算出 |
| 対象モデル | Qwen3-Omni、Qwen2.5-Omni、Qwen2.5-VL 32B、InternVL3 38B、Qwen-Image等 |
| 比較 | 各モデルの単体配置や既存最良サービング構成 |
| ワークロード | テキスト・画像・動画・音声の組合せ、実トレース/合成負荷をモデルに応じて使用 |

### 代表的な評価結果

| 対象 | 条件 | 結果 | 機構との対応 |
|---|---|---|---|
| 全体 | 複数Any-to-Anyモデル | 既存方式比で最大3.81倍のスループット | 構成要素別の分離・複製・並列度最適化 |
| Qwen2.5-Omni | 16GPU | P50 3.24倍、P95 5.3倍、P99 5.79倍短縮 | 構成要素干渉と待ち行列を分離で削減 |
| Qwen2.5-Omni | 画像+テキスト→音声 | P99最大9.47倍短縮 | 音声生成器を分離し、長い生成が他経路を塞ぐのを防ぐ |
| Qwen3-Omni | 8→16GPU | GPU 2倍でスループット2.68倍 | GPU増加に合わせてThinker/Talker/音声生成器の構成比も変更 |
| Qwen3-Omni | 一部長文脈ワークロード | 単体1GPU配置はOOM、Cornserveは分離で実行可能 | 構成要素メモリ分離で配置可能性自体を改善 |
| Qwen2.5-VL 32B | 各評価負荷 | 単体配置が最良、Cornserveはその構成に一致 | 分離が常に得ではないことを計画器が判定 |
| InternVL3 38B | 画像負荷の偏った条件 | 分離構成で1.26倍スループット、遅延曲線も改善 | 大型エンコーダとLLMのKV容量競合を解消 |
| Qwen-Image | 16GPU | 計画器は単体配置を選択 | LLMとDiTの計算量差が大き過ぎ、有限GPUで分離均衡を作れない |

### Qwen2.5-Omniでは裾遅延改善が中央値より大きい

16GPUのQwen2.5-Omniでは、単体配置はある構成要素が長く動くと別経路の要求まで止める。分離すると各構成要素が独立に進めるため、特に待ち行列の影響を強く受けるP95/P99が改善する。

例えばテキスト・画像・動画を入力し音声を出す要求では、単体配置のP99が340.5秒に対しCornserveは44.3秒まで下がる。テキスト・画像から音声を出す経路では最大9.47倍のP99短縮が観測され、要求種類によって律速が大きく違うことが分かる。

### 分離しない判断も評価上重要

Qwen2.5-VL 32Bの視覚エンコーダは比較的小さく、専用GPUへ切り出すとエンコーダ側が遊ぶ一方、LLMが使えるGPUとKV容量が減る。画像が多い場合も、エンコーダ出力トークンが増えることでLLMプリフィル計算も増え、エンコーダだけが単独律速になるとは限らない。

Qwen-Imageでも、テキスト埋め込み側LLMと20B DiTの計算量差が大きく、16GPUという予算内では分離した二段の処理能力を均衡させにくい。このため計画器は単体配置を選ぶ。

この二例は、Cornserveの価値が「常に分離すること」ではなく、**分離の得失をモデル・ワークロード・GPU予算ごとに判断すること**にあると示す。

## 既存研究との差

テキストLLMのプリフィル/デコード分離は、同じモデル内の二フェーズを異なるGPU群へ分ける。Cornserveはそれより一般化し、エンコーダ、複数LLM、DiT、音声生成器など任意のタスクグラフを分離候補にする。

特定のマルチモーダルモデル向けシステムは、そのモデル固有の段階構成へ最適化できる一方、新しいAny-to-Anyモデルごとに配信器を作り直す必要がある。Cornserveはタスク抽象化と計画器を介し、同じランタイムで複数の入出力モダリティ構成を扱う。

また、単純な負荷分散器と違い、実行時キュー長だけで配置を決めない。オフライン/計画段階で経路率と各構成要素の処理能力を使い、実行時は軽い静的ルーティングへ落とす。

## 限界・実装状況

第一に、最適配置はワークロード分布に依存する。音声出力率、画像解像度、入力長、出力長が変われば律速構成要素も変わるため、古い計画を固定すると不均衡が再発する。

第二に、分離にはネットワーク転送が追加される。評価環境はノード間400Gbps以上のRDMAであり、低速Ethernetや遠隔ノードでは中間テンソル転送費が相対的に大きくなる。

第三に、GPU数が少ないと各構成要素の処理能力を均衡させる整数配置が作れない場合がある。Qwen-Imageの例のように、理論上分離可能でも単体配置の方が良い。

第四に、計画器は測定した構成要素性能と想定経路率を使う。モデル更新、カーネル変更、入力分布変化で性能モデルがずれれば再プロファイル・再計画が必要である。

第五に、最大3.81倍/5.79倍は全モデル共通の固定倍率ではない。Qwen2.5-VLのように改善がほぼなく単体最良に一致する場合もあり、Cornserveは「悪い分離を避ける」能力を含めて評価すべきである。

## サーベイ上の含意

Cornserveは異種モデル配信を、単一の巨大モデル配置問題ではなく**経路付きの複数サービス段階の容量計画問題**として扱う。要求がどの段階を通るかと、各段階が何要求/秒を処理できるかを結びつけることで、GPU割当を構成要素単位へ細分化する。

今後、音声・画像・動画生成を含むエージェント系モデルが一つのサービス内で複数推論器を呼ぶ場合にも、この考え方は適用しやすい。一方で、構成要素間転送と再計画頻度が新しいオーバーヘッドになるため、分離可能性と分離有利性は区別して判断する必要がある。
