# Cornserve: Efficiently Serving Any-to-Any Multimodal Models

> Cornserveは、テキスト・画像・動画・音声を入力にも出力にも持つAny-to-Anyマルチモーダルモデルで、要求種別ごとに異なる計算経路と構成要素ごとのスケーリング特性を明示し、モノリシック配置・分離配置・混合配置を自動探索する配信システムである。エンコーダ、大規模言語モデル（Large Language Model; LLM）、拡散Transformer（Diffusion Transformer; DiT）などを独立に配置・拡縮でき、2ノード×各8基A100-80GB・400 Gbps以上のRDMA環境を含む評価で、既存方式に対し最大3.81倍のスループットと最大5.79倍の裾遅延改善を報告する。

## 概要

通常のLLM配信では、多くの要求が「プリフィル→自己回帰デコード」という共通経路を通る。Any-to-Anyモデルでは、画像＋テキストからテキストを返す要求、音声からテキスト＋音声を返す要求、画像を生成する要求などで、実際に通過するモデル構成要素そのものが異なる。

さらに、各構成要素はGPU追加に対する伸び方も違う。画像・音声エンコーダ、自己回帰LLM、DiT生成器を同じGPU集合へ固定すると、ある要求混合では一部の構成要素が遊休し、別の要求混合では一つの生成器だけが混雑する。反対に何でも分離すれば、中間テンソル転送と分散制御の費用が増える。

Cornserveはこの問題を「どの構成要素を分離するか」「何レプリカ用意するか」「各要求種別をどの経路へ流すか」という共同計画として扱う。モデル開発者は計算グラフを記述し、計画器がワークロードとプロファイルから配置を選ぶ。実行時は記録・再生（record-and-replay）型の分散ランタイムと構成要素間の直接テンソル転送で、その計画を低オーバーヘッドに実行する。

## 問題設定

Any-to-Any配信では三種類の異質性が同時に現れる。

1. **要求種別の異質性**：入力・出力モダリティによって必要処理が異なる。
2. **計算経路の異質性**：同じモデルでも要求ごとに実行グラフ上の経路が変わる。
3. **スケーリングの異質性**：エンコーダ、LLM、生成器はGPU数に対するスループット曲線が異なる。

モノリシック配置は構成要素間通信を最小化できる一方、全要求が同じGPU集合を共有するため、部分的な過負荷と遊休を解消しにくい。完全分離は独立拡縮しやすいが、ネットワーク転送とキューイングを増やす。したがって最適な分離粒度は、モデル構造だけでなく要求混合にも依存する。

## 手法

### 1. タスク抽象化で計算グラフと要求経路を明示する

入力は、マルチモーダルエンコーダ、LLM、生成器などをノード、テンソル依存関係を辺として表した計算グラフである。要求種別ごとに、どのノードを通過するかを記述する。

出力は計画器が解析可能な実行グラフであり、InternVL系の「画像エンコーダ→LLM」とQwen Omni系の「複数入力エンコーダ→思考用LLM→音声生成」のような違いを同じ抽象化で扱える。

### 2. 各デプロイ候補をプロファイルし、セルとしてまとめる

各構成要素についてGPU数、並列方式、要求種別を変えたときの処理能力を事前測定する。ここで重要なのは、単純にパラメータ数比例でGPUを配るのではなく、実測したスケーリング曲線を使うことである。

計画器は実際に配置可能な構成を「セル」として扱い、モノリシック、エンコーダ分離、生成器分離など複数候補を比較する。細粒度な任意GPU割当を直接探索するより、実装可能な候補へ空間を制限できる。

### 3. レプリカ数と要求経路を共同最適化する

計画器への入力は、要求種別ごとの到着率、実行グラフ、各セルの処理能力である。各要求率をどの経路へ何割流すかと、各セルを何レプリカ用意するかを同時に決める。

ある構成要素だけがボトルネックならそこだけ増やし、共有した方が効率的な部分は同居させる。Cornserveの方針は「常に分離」ではなく、要求混合に応じて分離と共有を選ぶことである。

### 4. 記録・再生型ランタイムで分散グラフを低オーバーヘッド実行する

分散した構成要素を毎要求Python制御で組み直すと、GPU計算が速いほど制御面が律速になる。Cornserveは依存関係を記録して再生し、同じ形の要求を軽量に繰り返し実行する。

中間テンソルは中央制御器へ戻さず、生産側から消費側へ直接送る。これにより分離で増えるデータ移動を必要最小限にする。

### 5. 到着時に経路を選び、実行途中の判断を減らす

計画器が求めた要求種別別の経路確率に従い、要求到着時点で実行経路を選択する。その後は選択済み経路上の構成要素へ処理を流す。

実行中の細かい再ルーティングを避けられる一方、要求混合が大きく変われば計画自体の更新が必要になる。

## 評価

### 評価条件

| 項目 | 条件 |
|---|---|
| テストベッド | 同一拠点2ノード |
| GPU | 各ノード8×NVIDIA A100 80GB、ノード内NVLink |
| ノード間 | 400 Gbps以上のRDMA |
| 主指標 | request throughput（requests/s） |
| 定常測定 | 原則2,000要求以上を投入 |
| 遅延 | P50/P90/P99、CDF、tail latency |
| 代表モデル | InternVL 3 38B、Qwen Omni系列など |
| 比較 | モノリシック/固定分離を含む既存配置 |
| 後続実装 | Kubernetes上の分散システム、約23K行のPython |

### 主な結果

| 観点 | Cornserve | 読み方 |
|---|---:|---|
| 最大スループット改善 | 3.81倍 | 要求経路と構成要素負荷に合わせた配置の最大値 |
| 最大裾遅延改善 | 5.79倍 | ボトルネック構成要素の混雑緩和による最大値 |
| InternVL 3 38B例 | 同じ8×A100-80GBでも配置方式で処理量が変化 | 総GPU数より分離粒度が重要 |
| 測定方式 | 長い定常区間を使用 | 起動直後だけの瞬間性能ではない |

3.81倍/5.79倍はすべてのワークロードに共通する倍率ではない。モノリシックが有利な要求混合もあり、Cornserveの中心的価値は「モデルごとに固定した最適配置」ではなく、モデル構造と負荷から適切な配置を選ぶことにある。

## 既存研究との差

LLMのプリフィル/デコード分離は、同じモデル内の二段階を対象とする。Cornserveは、要求ごとに実行する構成要素そのものが変わるマルチモーダル計算グラフを一般化し、任意のエンコーダ・LLM・生成器を分離候補として扱う。

モデルごとの専用サーバーを人手で構成する方式との差は、プロファイルと要求混合から配置、レプリカ数、経路分割を自動計画する点にある。

## 限界・実装状況

- プロファイルしていないGPU・並列方式・モデルへ移ると再測定が必要。
- 構成要素分離は中間テンソル通信を増やすため、ネットワークが遅い環境ではモノリシックが有利になり得る。
- 要求分布が急変すると、計画時の負荷と現在負荷がずれる。
- 最大3.81倍/5.79倍は特定モデル・要求混合の最大値であり、一般倍率ではない。
- Cornserve本体はオープンソースだが、2026年8月時点では自動計画器の完全な研究再現コードは本体リポジトリと同じ成熟度ではないため、論文結果の再現には公開状況を別途確認する必要がある。

## 一般的な実装上の含意

複合マルチモーダルモデルでは「モデル1個＝サーバー1個」という資源単位を固定しない方がよい。要求別に実際に通る構成要素を計測し、独立に伸縮させる価値がある部分だけを分離する。

一方、細分化そのものは目的ではない。中間テンソル転送、キューイング、制御費用を含むエンドツーエンドのgoodputで分離粒度を決めるべきである。
