# Hierarchical Autoscaling for Large Language Model Serving with Chiron

## 一文要約

interactive requestのlatency目標を守りながら余ったGPU capacityをbatch requestへ使うため、**各GPUで同時処理するrequest数を素早く増減する制御**と、**cluster全体のGPU instance数を遅い周期で増減する制御**を分けたLLM autoscaler。

## 問題設定

LLM servingでは、user-facingなinteractive requestは秒単位の厳しいTTFT / inter-token latency目標を持つ一方、background処理などのbatch requestは分〜時間単位まで待てる。

この2種類を同じclusterで処理すると、単純なqueue長やGPU utilizationだけを見たautoscalingには二つの無駄が生じる。

1. **各GPUの中:** 同時に処理するrequest数を増やすとthroughputは上がるが、各requestのtoken間隔は悪化しやすい。固定の小batchではbatch workload時にGPUを使い切れない。
2. **cluster全体:** batch requestがqueueへ入っただけですぐGPUを増やすと、interactive burst用に確保していた余裕をbatch処理へ一時利用できるのに、不要なscale-up / scale-downが起きる。

さらにLLMはmodel loadに15秒〜1分程度かかり得るため、通常のweb serviceのようにtraffic burstを見てから即座にinstanceを追加しても間に合わない場合がある。

## 手法

Chironはresource調整を、**すぐ変えられるlocal control**と**反応が遅いglobal control**の二段階へ分ける。

二段階に分ける理由は、操作ごとの反応時間が大きく違うからである。1 GPU内の同時処理数は次のbatchから変えられる一方、新しいGPU instanceはmodel loadや初期化を伴うため即座には増やせない。短いtraffic変動をinstance増減だけで追うと、追加GPUが使える頃にはburstが終わっている可能性がある。そこでlocal controlを高速な一次応答、global controlを持続的なcapacity不足へ対処する二次応答として使い分ける。

### 1. Local control: 1 GPUで同時に何request処理するかを動的に変える

各serving instanceではbatch sizeを調整つまみとして扱う。

- batch sizeを増やす → 同時処理requestが増えthroughputは上がりやすい
- batch sizeを増やしすぎる → interactive requestのlatencyが悪化しやすい

Chironはruntime中にlatency目標違反とthroughputを観測し、

- latencyが悪化したらbatch sizeを下げる
- SLOに余裕がありGPUが余っていればbatch sizeを上げる

ようにする。

論文でいう **local backpressure** は、「これ以上requestを詰めるとlatencyが悪くなる」というruntime feedbackをbatch sizeへ返す仕組みである。

### 2. Global control: 今あるGPUだけでdeadlineに間に合わなくなる前にinstanceを増やす

cluster levelでは、queueが増えたという理由だけでscale-outしない。

interactive request用に一定のspare capacityを残し、deadlineに余裕のあるbatch requestはまずその余りへ流す。

batch requestについて、

- すでに何秒待ったか
- deadlineまであと何秒あるか
- 現在のGPU capacityならいつ処理開始できるか

を見積もる。

**このままではdeadlineに間に合わないと判断した時点で初めてGPU instanceを追加する**。

論文のglobal backpressureは、この「queueの長さ」ではなく**SLOまでの残り余裕からresource不足を判断するfeedback**を指す。

### 3. Batch requestはinteractive burst用の余剰capacityへ opportunisticに入れる

interactive trafficはburstへ備えて少しresourceを余らせる必要がある。しかしその余りを常時idleにするとcost効率が悪い。

Chironはdeadlineの緩いbatch requestをqueueへ保持し、interactive requestが少ない間だけそのspare capacityへ入れる。

interactive loadが増えればlocal batch sizeを縮めたりbatch requestを後回しにしたりして、user-facing latencyを守る。

### 4. Scale-up / scale-downを短時間で繰り返さない

trafficが境界付近で揺れると、GPUを追加した直後に削減し、またすぐ追加するような振動が起こり得る。

Chironは似たdeadlineのrequestをgroup化し、resource増減の判断に余裕を持たせる。

論文でいう **hysteresis** は、scale-upとscale-downの判断境界を少しずらし、短期的なtraffic変動でinstance数が往復し続けないようにする仕組みである。

## 評価条件

- backend: **vLLM**
- hardware: **NVIDIA A100 GPU cluster**
- models: 本文ではLlama 8B / Llama 70Bを含む構成を評価
- workload: **ShareGPT**を用い、production requirementから導いたinteractive / batch workloadを構成
- burstinessを変化させたsynthetic workloadと、production clusterで観測したarrival patternも分析
- 比較対象にはLlumnix等の既存LLM serving / autoscaling方式を含む

## 主要結果

論文が報告する代表値は以下。

- **SLO attainment:** arrival rateに応じて既存方式より最大 **90%向上**。
- **request throughput:** 最大 **300%向上**。
- **GPU efficiency / resource saving:** throughput向上により必要GPUを最大 **70%削減**。
- local / globalの両制御がSLO attainmentとthroughput改善へ寄与し、異なるSLO値・bursty arrivalに対するrobustnessも確認している。

## 既存研究との差

### vs. Llumnix

Llumnixはrunning request / KV stateをinstance間migrationしてload imbalanceやfragmentationを修正する。一方Chironは、**request配置より上位のresource量**を主題とし、batch sizeとinstance countをSLO-awareに変える。

### vs. QLM

QLMは既存resource上でqueue順序・instance assignmentを最適化し、request waiting timeを推定する。Chironはそのwaiting-time estimationをglobal autoscalingへ利用し、**必要resource量そのものを増減する**。

### vs. Andes

Andesはtoken streaming時のuser-perceived QoEを改善するtoken-level schedulingが中心。Chironはbatch sizeとinstance数を操作するautoscaling layerであり、より長いcontrol timescaleを扱う。

### vs. ServerlessLLM

ServerlessLLMはmodel checkpoint localityと高速loading / migrationでcold start自体を短くする。Chironはmodel startup latencyが依然大きいことを前提に、**burst後にGPUを増やすだけでは間に合わないので、普段のspare capacityをbatch requestへ貸す**。

## 実装上の含意

- LLM autoscalingではrequest countやGPU utilizationだけでなく、**TTFT / ITL SLOまであと何秒余裕があるかとrequest class**をcontrol signalへ入れる価値が高い。
- 「GPU台数」だけをautoscaling knobにするとmodel startupが遅すぎるため、**batch sizeのような即時変更できるlocal knobとinstance countの遅いglobal knobを階層化**すると制御しやすい。
- interactive workloadのburst対策で生じるreserved capacityは完全なidle resourceではなく、deadlineの緩いbatch workloadをqueueingして吸収させる余地がある。
- P/D disaggregationやspeculative decoding、prefix cachingなどconfiguration spaceが増えるほどoffline profilingだけで最適batchを固定する方法は維持しにくく、runtime feedback型のresource controlが重要になる。

## 限界

- 公開版はarXiv v1で、本文上はpreliminary / under-review workとして提示されている。
- 評価は主にA100 clusterとvLLM backendであり、異種GPUやP/D disaggregated clusterで同じcontrol policyがそのまま最適とは限らない。
- reactive controlなので、model startupより速い急激なtraffic spikeを完全に先読みする仕組みではない。burst耐性には一定のover-provisioned spare capacityを前提とする。
- request class / SLOをoperatorが把握できる環境を想定しており、deadlineやworkload classが不明瞭なpublic endpointでは追加の推定が必要になる。
