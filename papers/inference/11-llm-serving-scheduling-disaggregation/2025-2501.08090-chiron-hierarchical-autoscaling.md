# 階層型 自動スケーリング for Large Language モデル サービング with Chiron

## 一文要約

対話型 リクエストの遅延目標を守りながら余ったGPU 容量をバッチ リクエストへ使うため、**各GPUで同時処理するリクエスト数を素早く増減する制御**と、**クラスタ全体のGPU インスタンス数を遅い周期で増減する制御**を分けたLLM 自動スケーラ。

## 問題設定

LLM サービングでは、利用者-facingな対話型 リクエストは秒単位の厳しいTTFT / inter-トークン 遅延目標を持つ一方、background処理などのバッチ リクエストは分〜時間単位まで待てる。

この2種類を同じクラスタで処理すると、単純なキュー長やGPU 利用率だけを見た自動スケーリングには二つの無駄が生じる。

1. **各GPUの中:** 同時に処理するリクエスト数を増やすとスループットは上がるが、各リクエストのトークン間隔は悪化しやすい。固定の小バッチではバッチ ワークロード時にGPUを使い切れない。
2. **クラスタ全体:** バッチ リクエストがキューへ入っただけですぐGPUを増やすと、対話型 burst用に確保していた余裕をバッチ処理へ一時利用できるのに、不要な規模拡大 / 規模縮小が起きる。

さらにLLMはモデル 負荷に15秒〜1分程度かかり得るため、通常のweb サービスのようにトラフィック burstを見てから即座にインスタンスを追加しても間に合わない場合がある。

## 手法

Chironは資源調整を、**すぐ変えられるローカル 制御**と**反応が遅いグローバル 制御**の二段階へ分ける。

二段階に分ける理由は、操作ごとの反応時間が大きく違うからである。1 GPU内の同時処理数は次のバッチから変えられる一方、新しいGPU インスタンスはモデル 負荷や初期化を伴うため即座には増やせない。短いトラフィック変動をインスタンス増減だけで追うと、追加GPUが使える頃にはburstが終わっている可能性がある。そこでローカル 制御を高速な一次応答、グローバル 制御を持続的な容量不足へ対処する二次応答として使い分ける。

### 1. ローカル 制御: 1 GPUで同時に何リクエスト処理するかを動的に変える

各サービング インスタンスではバッチ サイズを調整つまみとして扱う。

- バッチ サイズを増やす → 同時処理リクエストが増えスループットは上がりやすい
- バッチ サイズを増やしすぎる → 対話型 リクエストの遅延が悪化しやすい

Chironはランタイム中に遅延目標違反とスループットを観測し、

- 遅延が悪化したらバッチ サイズを下げる
- SLOに余裕がありGPUが余っていればバッチ サイズを上げる

ようにする。

論文でいう **ローカル 逆圧** は、「これ以上リクエストを詰めると遅延が悪くなる」というランタイム フィードバックをバッチ サイズへ返す仕組みである。

### 2. グローバル 制御: 今あるGPUだけで締切に間に合わなくなる前にインスタンスを増やす

クラスタ レベルでは、キューが増えたという理由だけで拡縮-outしない。

対話型 リクエスト用に一定の余剰 容量を残し、締切に余裕のあるバッチ リクエストはまずその余りへ流す。

バッチ リクエストについて、

- すでに何秒待ったか
- 締切まであと何秒あるか
- 現在のGPU 容量ならいつ処理開始できるか

を見積もる。

**このままでは締切に間に合わないと判断した時点で初めてGPU インスタンスを追加する**。

論文のグローバル 逆圧は、この「キューの長さ」ではなく**SLOまでの残り余裕から資源不足を判断するフィードバック**を指す。

### 3. バッチ リクエストは対話型 突発負荷用の余剰容量へ opportunisticに入れる

対話型 トラフィックは突発負荷へ備えて少し資源を余らせる必要がある。しかしその余りを常時アイドルにするとコスト効率が悪い。

Chironは締切の緩いバッチ リクエストをキューへ保持し、対話型 リクエストが少ない間だけその余剰 容量へ入れる。

対話型 負荷が増えればローカル バッチ サイズを縮めたりバッチ リクエストを後回しにしたりして、利用者-facing 遅延を守る。

### 4. 規模拡大 / 規模縮小を短時間で繰り返さない

トラフィックが境界付近で揺れると、GPUを追加した直後に削減し、またすぐ追加するような振動が起こり得る。

Chironは似た締切のリクエストをgroup化し、資源増減の判断に余裕を持たせる。

論文でいう **hysteresis** は、規模拡大と規模縮小の判断境界を少しずらし、短期的なトラフィック変動でインスタンス数が往復し続けないようにする仕組みである。

この二層構成では、短い変動を各GPU内の同時処理数で吸収し、長く続く不足だけをクラスタ全体の台数変更へ伝える。したがって台数変更の準備時間を待つ間も、既存GPUの余力を利用して対話型処理の遅延目標を守りやすい。逆に、余力が尽きて期限に間に合わない見込みになった時点では、キュー長を待たずに上位の制御が容量追加を判断できる。この判断を分離しておくことで、対話型とバッチ型の要求を同じ待ち時間の尺度で扱わず、それぞれの期限に応じて資源を融通できる。

## 評価条件

- backend: **vLLM**
- ハードウェア: **NVIDIA A100 GPU クラスタ**
- モデル: 本文ではLlama 8B / Llama 70Bを含む構成を評価
- ワークロード: **ShareGPT**を用い、本番 requirementから導いた対話型 / バッチ ワークロードを構成
- burstinessを変化させた合成 ワークロードと、本番 クラスタで観測した到着 patternも分析
- 比較対象にはLlumnix等の既存LLM サービング / 自動スケーリング方式を含む

## 主要結果

論文が報告する代表値は以下。

- **SLO attainment:** 到着 rateに応じて既存方式より最大 **90%向上**。
- **リクエスト スループット:** 最大 **300%向上**。
- **GPU efficiency / 資源 saving:** スループット向上により必要GPUを最大 **70%削減**。
- ローカル / グローバルの両制御がSLO attainmentとスループット改善へ寄与し、異なるSLO値・bursty 到着に対するrobustnessも確認している。

## 既存研究との差

### vs. Llumnix

Llumnixはrunning リクエスト / KV 状態をインスタンス間移行して負荷 imbalanceやfragmentationを修正する。一方Chironは、**リクエスト配置より上位の資源量**を主題とし、バッチ サイズとインスタンス 件数をSLO-考慮に変える。

### vs. QLM

QLMは既存資源上でキュー順序・インスタンス assignmentを最適化し、リクエスト 待機 時間を推定する。Chironはその待機-時間 estimationをグローバル 自動スケーリングへ利用し、**必要資源量そのものを増減する**。

### vs. Andes

Andesはトークン streaming時の利用者-perceived QoEを改善するトークン単位 スケジューリングが中心。Chironはバッチ サイズとインスタンス数を操作する自動スケーリング 層であり、より長い制御 timescaleを扱う。

### vs. ServerlessLLM

ServerlessLLMはモデル checkpoint 局所性と高速loading / 移行でcold 開始自体を短くする。Chironはモデル 起動 遅延が依然大きいことを前提に、**突発負荷後にGPUを増やすだけでは間に合わないので、普段の余剰 容量をバッチ リクエストへ貸す**。

## 実装上の含意

- LLM 自動スケーリングではリクエスト 件数やGPU 利用率だけでなく、**TTFT / ITL SLOまであと何秒余裕があるかとリクエスト クラス**を制御 signalへ入れる価値が高い。
- 「GPU台数」だけを自動スケーリング 調整つまみにするとモデル 起動が遅すぎるため、**バッチ サイズのような即時変更できるローカル 調整つまみとインスタンス 件数の遅いグローバル 調整つまみを階層化**すると制御しやすい。
- 対話型 ワークロードの突発負荷対策で生じるreserved 容量は完全なアイドル 資源ではなく、締切の緩いバッチ ワークロードをqueueingして吸収させる余地がある。
- P/D disaggregationや投機的 デコード、プレフィックス キャッシュ化など構成 spaceが増えるほどオフライン profilingだけで最適バッチを固定する方法は維持しにくく、ランタイム フィードバック型の資源 制御が重要になる。

## 限界

- 公開版はarXiv v1で、本文上はpreliminary / 査読中 workとして提示されている。
- 評価は主にA100 クラスタとvLLM backendであり、異種GPUやP/D disaggregated クラスタで同じ制御 方策がそのまま最適とは限らない。
- reactive 制御なので、モデル 起動より速い急激なトラフィック spikeを完全に先読みする仕組みではない。突発負荷耐性には一定のover-provisioned 余剰 容量を前提とする。
- リクエスト クラス / SLOをoperatorが把握できる環境を想定しており、締切やワークロード クラスが不明瞭なpublic endpointでは追加の推定が必要になる。

## 引用関係

- **直接利用:** QLMのリクエスト 待機-時間 estimationをグローバル 自動スケーリング判断に利用する。
- **比較・背景:** Llumnix、vLLM / PagedAttention、Orca、Andes、ServerlessLLMなどをLLM サービング / スケジューリング / 資源 managementの先行研究として位置づける。
- **研究上の位置:** QLMがキュー、Llumnixがランタイム 配置 / 移行を制御するのに対し、Chironはローカル バッチ サイズとグローバル インスタンス 件数を階層制御するため、サービング系統の**SLO-考慮 自動スケーリング**の枝に位置づけられる。

## 補足

Chironの階層構成は、要求の増減を一つの大きな制御器で処理するのではなく、短い時間の反応と長い時間の資源準備を分ける考え方である。短時間の突発負荷には既存の余剰枠を使い、継続的な増加には上位の制御器が複製数や装置数を調整する。評価値は特定の負荷履歴とGPU構成で得られた結果なので、実環境では起動時間、移行時間、締切違反を含む監視値を使って段階ごとの判断を校正する必要がある。
