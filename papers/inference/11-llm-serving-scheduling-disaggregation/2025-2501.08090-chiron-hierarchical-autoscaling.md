# Hierarchical Autoscaling for Large Language Model Serving with Chiron

## 一文要約

interactive requestとbatch requestで異なるSLOを考慮し、**instance内のbatch sizeとcluster全体のinstance数を二階層のbackpressureで別々に調整**することで、LLM servingのSLO attainmentとGPU利用効率を同時に高めるautoscaler。

## 問題設定

LLM servingでは、user-facingなinteractive requestは秒単位の厳しいTTFT / inter-token latency SLOを持つ一方、background処理などのbatch requestは分〜時間単位まで待てる。この2種類を同じclusterで処理すると、単純なqueue長やGPU utilizationだけを見たautoscalingには二つの無駄が生じる。

1. **instance内:** batch sizeを大きくするとthroughputは上がるが、attention時間やKV preemptionが増えてinteractive requestのinter-token latencyを悪化させる。逆に固定の小さいmax batch sizeではbatch workload時にGPUを使い切れない。
2. **cluster全体:** batch requestがqueueへ入っただけで即座にinstanceを増やすと、本来はinteractive workload用に確保されたspare capacityへbatch requestをmultiplexできるのに、不要なscale-up / scale-downが起きる。

さらにLLMはmodel loadに15秒〜1分程度かかり得るため、通常のweb serviceのようにburstを見てから即座にinstanceを追加することも難しい。

## 手法

Chironは既存LLM serving backendへ追加できる**hierarchical autoscaler**で、localとglobalの二段階でbackpressureを計算する。

### 1. Local autoscaling: batch sizeをSLOに合わせて調整

各serving instanceでは、batch sizeそのものをlocal resource knobとして扱う。

- batch sizeを増やすと同時処理requestが増えてthroughputは上がる。
- 一方でlatencyが悪化し、interactive requestのSLO violationやpreemptionが増える。
- Chironはoffline profilingで固定値を決めるのではなく、latencyとthroughputを組み合わせたlocal backpressureをruntimeで観測する。
- SLO violation / throughput degradationが見えればbatch sizeを縮小し、SLOに余裕があれば拡大する。

これにより、interactive requestには小さめのbatchを保ちながら、batch workloadが多い時間帯には余剰GPU capacityをより大きなbatchで利用する。

### 2. Global autoscaling: instance数をSLO slack込みで調整

cluster levelでは、queueが増えたという理由だけでscale-outしない。

- interactive requestはすぐ処理する必要があるため、burst対策として一定のspare capacityが必要。
- deadlineに余裕のあるbatch requestはqueueに保持し、そのspare capacityへopportunistically multiplexする。
- QLM由来のrequest waiting-time estimationを利用し、batch requestがSLO deadlineへ近づいてspare capacityだけでは間に合わなくなる場合にscale-outする。
- 類似deadlineのrequestをgroup化して処理し、短時間のscale-up / scale-down反復（hysteresis）を抑える。

つまりChironは、**localでは「1 GPUへ何request詰めるか」、globalでは「GPU instanceを何台持つか」**を別々の時間・resource scaleで制御する。

## 評価条件

- backend: **vLLM**
- hardware: **NVIDIA A100 GPU cluster**
- models: 本文ではLlama 8B / Llama 70Bを含む構成を評価
- workload: **ShareGPT**を用い、production requirementから導いたinteractive / batch workloadを構成
- burstinessを変化させたsynthetic workloadと、production clusterで観測したarrival patternも分析
- 比較対象にはLlumnix等の既存LLM serving / autoscaling方式を含む

## 主要結果

論文が報告する代表値は以下。

- **SLO attainment:** arrival rateに応じて既存方式より最大 **90%向上**。
- **request throughput:** 最大 **300%向上**。
- **GPU efficiency / resource saving:** throughput向上により必要GPUを最大 **70%削減**。
- local / global backpressureの両方がSLO attainmentとthroughput改善へ寄与し、異なるSLO値・bursty arrivalに対するrobustnessも確認している。

## 既存研究との差

### vs. Llumnix

Llumnixはrunning request / KV stateをinstance間migrationしてload imbalanceやfragmentationを修正する。一方Chironは、**request placement後のmigrationより上位のresource provisioning**を主題とし、batch sizeとinstance countをSLO-awareに変える。

### vs. QLM

QLMは既存resource上でqueue順序・instance assignmentを最適化し、request waiting timeを推定する。Chironはそのwaiting-time estimationをglobal autoscalingへ利用し、**必要resource量そのものを増減する**。

### vs. Andes

Andesはtoken streaming時のuser-perceived QoEを改善するtoken-level schedulingが中心。Chironはbatch sizeとinstance数を操作するautoscaling layerであり、より長いcontrol timescaleを扱う。

### vs. ServerlessLLM

ServerlessLLMはmodel checkpoint localityと高速loading / migrationでcold start自体を短くする。Chironはmodel startup latencyが依然大きいことを前提に、**burst後にscale-outするだけでは間に合わないためspare capacityをbatch requestへ有効利用する**。

## 実装上の含意

- LLM autoscalingではrequest countやGPU utilizationだけでなく、**TTFT / ITL SLO slackとrequest class**をcontrol signalへ入れる価値が高い。
- 「GPU台数」だけをautoscaling knobにするとmodel startupが遅すぎるため、**batch sizeのような即時変更できるlocal knobとinstance countの遅いglobal knobを階層化**すると制御しやすい。
- interactive workloadのburst対策で生じるreserved capacityは完全なidle resourceではなく、deadlineの緩いbatch workloadをqueueingして吸収させる余地がある。
- P/D disaggregationやspeculative decoding、prefix cachingなどconfiguration spaceが増えるほどoffline profilingだけで最適batchを固定する方法は維持しにくく、runtime feedback型のresource controlが重要になる。

## 限界

- 公開版はarXiv v1で、本文上はpreliminary / under-review workとして提示されている。
- 評価は主にA100 clusterとvLLM backendであり、異種GPUやP/D disaggregated clusterで同じcontrol policyがそのまま最適とは限らない。
- reactive controlなので、model startupより速い急激なtraffic spikeを完全に先読みする仕組みではない。burst耐性には一定のover-provisioned spare capacityを前提とする。
- request class / SLOをoperatorが把握できる環境を想定しており、deadlineやworkload classが不明瞭なpublic endpointでは追加の推定が必要になる。
