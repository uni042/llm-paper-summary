# OUTLETS: Output-Length Prediction from Speculative Decoding Backbones

> **OUTLETSは、speculative decoding用のdraft modelを「先のtokenを当てる装置」だけでなく「この生成があと何token続きそうかを読む装置」としても使い、予測した残長でdecodeのqueue順序とworker割当を改善する。**

## 概要

LLM servingでは、同じようなpromptを受けても出力長が数十tokenで終わるrequestもあれば、数千token続くrequestもある。しかもこの分布は裾が長い（heavy-tailed）ため、単純な先着順で処理すると短いrequestが非常に長いrequestの後ろへ入り、長時間待たされることがある。これが先頭job待ち（Head-of-Line blocking; HOL blocking）で、平均latencyよりもP99のようなtail latencyを悪化させる主要因になる。

出力長を事前に予測できれば、短く終わるrequestを先に実行する最短job優先（Shortest-Job-First; SJF）や、「残仕事量が最も少ないdecode instanceへ送る」という負荷分散（Load Balancing; LB）が可能になる。しかし従来法には二つの典型的な問題がある。

1. **外部proxy modelを使う方式**は、長さを予測するためだけにBERTや小型LLMなどを別途走らせる必要があり、予測そのものがlatencyとcompute costを増やす。
2. **target LLM内部のhidden stateへ浅いprobeを付ける方式**は軽いが、そのhidden stateは基本的に「次の1 token」を予測するために学習されており、何百token先の終了時点を読むには情報の加工が不足しやすい。

OUTLETSの着眼点は、speculative decoding（投機的復号）に使うdraft decoderが既に「未来のsequence trajectoryを先読みする」よう訓練されていることである。特にEAGLE-3系ではtarget LLMの複数layerのfeatureを融合し、軽量Transformer decoderで先のtokenをdraftする。このdraft stateは単なる現在状態ではなく、未来方向へ展開された表現なので、生成終了までの距離も含みやすいと考えられる。

そこでOUTLETSは、draft decoderを新たに別目的で置き換えるのではなく、**同じdraft representationから token draft用head と output-length回帰head の二つを出す**。speculative decodingを既に採用しているruntimeなら、重いbackbone計算は共有でき、追加部分は小さな回帰headだけで済む。

## 背景: なぜ出力長予測がservingに効くのか

### decodeは「いつ終わるか」が分からないjob scheduling

prefillは入力token数が最初から分かるため、おおよその仕事量を見積もりやすい。対してdecodeはautoregressiveに1 tokenずつ生成し、EOSなどの停止条件に達するまで長さが確定しない。そのためschedulerから見ると、各requestは「残り実行時間が未知のjob」である。

たとえばdecode worker Aに残り100 tokenのrequestが3本、worker Bに残り1500 tokenのrequestが3本あるとする。request件数だけなら両者のloadは同じ3本だが、実際の仕事量は大きく違う。round-robin（RR）で新requestを均等配布しても、長requestが偶然集まったworkerだけqueueが膨らむ。

同様にworker内部で先着順（First-Come-First-Served; FCFS）にすると、数十tokenで終わるrequestが数千tokenrequestの後ろへ入り、ユーザーから見れば「すぐ終わるはずの処理なのに何十秒も待つ」状態になる。出力長予測は、この二種類の不均衡を同時に改善するsignalになる。

### static predictionとdynamic prediction

論文は残り長を `r_t = L - t` と定義する。`L` が最終的な生成token数、`t` が現在までに生成済みのtoken数である。

**静的予測（static prediction）**はdecode開始前、つまり `t=0` で最終出力長 `L` を予測する。requestをどのdecode instanceへ送るか、queueのどこへ入れるかはdecode前に決める必要があるため、system-level schedulingで直接使うのはこちらである。

**動的予測（dynamic prediction）**はdecode途中で、その時点からあと何token残るかを更新する。生成された内容が増えるほど「そろそろ結論へ向かっている」「まだ途中である」というtrajectory情報が見えるため、原理的には精度を改善できる。OUTLETSではdynamic predictionも評価するが、現行system実装はonline migrationや途中での再routingまでは行わず、serving policyはstatic predictionを使う。

この区別は重要である。論文が「decodeが進むほど予測精度が上がる」と示しても、その改善をend-to-end schedulingへ完全に利用しているわけではない。

## 手法のあらまし

OUTLETSの構成は大きく、(1) target LLMの複数layer featureを融合する部分、(2) trajectoryを処理するdraft decoder、(3) draft token headとlength regression headの二出力からなる。

### 1. multi-level feature fusion: 1 layerだけでなく複数の深さを見る

EAGLE-3の考え方を踏襲し、frozen target LLMの複数layerからhidden stateを取り出す。論文では概ね浅いlayer、中間layer、上位layerに対応する `2`, `floor(N/2)`, `N-2` の3箇所を選び、それらをconcatして全結合層（Fully Connected layer; FC）でdraft embedding次元へ射影する。

この理由は、最上位layerだけでは次token予測へ特化し過ぎる可能性があるためである。浅い層には語彙・局所的特徴、中間層には構文的pattern、深い層には高水準なsemantic contextが含まれやすい。生成が「あとどのくらい続くか」は、直後のtokenだけでなく、回答構造や話題の進行度にも依存するため、複数depthを合わせた方が長期signalを取りやすい。

融合featureはそのrequestの文脈を表すanchorになり、次のdraft decoderへ入力される。

### 2. draft decoder: static hidden stateを未来trajectoryへ変換する

中核は軽量Transformerのdraft decoderである。これはtarget LLMのhidden stateをそのまま回帰へ入れる単純MLPと違い、speculative decodingで先のtokenをdraftするためにsequenceをroll forwardする。

OUTLETSはこの部分を「trajectory-aware forecasting module」と解釈する。生成終了は未来のcontinuationがどこでEOSへ到達するかという性質なので、未来tokenを予測するために変換されたdraft stateは、単なるcurrent-state probeより残長予測に適しているという仮説である。

実装ではEAGLE-3標準attentionの代わりにゲート付きattention（Gated Attention）を使い、長距離のtermination signalを保ちやすくする。論文のablationでは標準的なLlama attentionより長さ予測精度が改善したと報告する。

### 3. dual-head: 同じstateからdraft tokenと残り長を出す

共有draft state `h_t^draft` から二つのheadを出す。

**Draft Model Head** は通常のspeculative decodingと同じで、vocabulary分布を出して次のcandidate tokenを提案する。これはEAGLE-3本来の役割である。

**Length Regression Head** は同じdraft stateから残り生成token数を予測する。出力長はheavy-tailで、数十〜数千tokenを線形値のまま回帰すると長requestの誤差がlossを支配しやすい。そのためOUTLETSは `log(1 + length)` のlog-spaceへ変換して回帰し、推論時にtoken長へ戻す。

head自体はhidden dimensionを段階的に縮めるMLPである。代表的なhidden size 2,048の構成では、speculative backboneが約72.3M parameter、length prediction MLPは約2.6M parameterと報告される。すでにspeculative decodingを使っている場合、OUTLETS固有の追加modelは後者が中心になる。

### 4. joint training: draft能力と長さ予測を同じbackboneへ学習させる

OUTLETSはdrafting objectiveとlength-regression objectiveを同じbackboneで学習する。ここで懸念になるのは、「長さ予測を追加するとdraft tokenの精度が落ち、speculative decoding本来のacceptance rateを損なうのではないか」という点である。

論文はSD-ONLYとのablationで、このauxiliary length objectiveを加えてもspeculative acceptanceを実質的に悪化させないことを確認している。

逆に長さ予測だけへ専用化したLP-ONLYと比較すると、static predictionではOUTLETSが概ね同等以上である一方、dynamic predictionではLP-ONLYがやや有利になる。staticでは1 requestにつき教師labelが1個しかなくdata-sparseなので、drafting objectiveがrepresentationをregularizeする利点がある。一方dynamicでは各decode stepが教師signalになるため、専用modelが回帰へ特化しやすい、という解釈である。

## schedulerへの使い方

論文のsystem evaluationでは、OUTLETSの**static output-length prediction**を二箇所へ使う。

### instance-level load balancing（LB）

各decode instanceについて、running / queued requestの「予測残長」を足してestimated remaining workloadを計算する。新requestはこの推定仕事量が最も小さいinstanceへ送る。

単純round-robinがrequest「本数」しか均等化しないのに対し、LBはtoken-levelの仕事量を均等化しようとする。長requestが偏ったworkerへさらにrequestを送り続けることを防ぐのが目的である。

### local shortest-job-first（SJF）

各decode queueの中では、予測出力長が短いrequestを優先する。これによって短requestが長requestの後ろで何十秒も待つHOL blockingを減らす。

SJFには「長いjobが永遠に後回しになるstarvation」の懸念がある。しかし評価ではlong requestのP99もbaselineより悪化せず、むしろわずかに改善した。少なくとも評価workloadでは、queue fragmentationとworker imbalanceを減らした利益が優先順位penaltyを上回った。

## 評価

### 予測器の実験条件

- **dataset:** ShareGPT、Alpaca、LMSYS-Chat-1M。
- **label生成:** 同じpromptに対して各target model自身でresponseを再生成し、そのmodel固有の実出力長をlabelにする。
- **filter:** 生成が2,048 tokenを超えるsampleは除外。
- **split:** train:test = 4:1。
- **training環境:** 4 NVIDIA GPU、合計141 GB HBM、2×56-core CPUのcloud node。DeepSpeedを使用。
- **metric:** 静的/動的とも平均絶対誤差（Mean Absolute Error; MAE）。dynamicでは各decode stepのremaining-length errorをrequest内で平均する。

### prediction accuracy: proxy modelより一貫して低いMAE

static predictionでは、OUTLETSは論文が比較したBERT、OPTなどのproxy-based predictorやinstruction-based baselineより一貫して低いMAEを示す。これは「speculative draft stateにfuture trajectory signalがある」という中心仮説を支持する。

dynamic predictionでは、ShareGPTの例でMAEが生成初期の **80.6** から後半には **67.6** まで低下する。つまり生成が進むにつれdraft stateが実際のtrajectoryを追跡し、残り長を更新できている。

ただし前述の通り、現行serving policyはこのdynamic更新をroutingへ使わない。これはrepresentationとして有用であることの検証であり、online reschedulingの実装結果ではない。

### standalone costと「すでにSDを使う場合」のcostを分けて読む

代表構成ではdraft backboneが1 decode stepあたり約 **1.7 ms**、length headが約 **0.7 ms** の追加costとされる。この数字から「OUTLETSのcostは0.7 msだけ」と一般化するのは誤りである。

**すでにEAGLE-3系speculative decodingを動かしているsystemなら**、1.7 msのbackbone計算は元から必要なのでlength prediction固有の増分は主に0.7 msのheadになる。対して長さ予測のためだけにOUTLETS backboneを新設するなら、backbone costも含める必要がある。論文の「計算共有」の価値はここにある。

## system-level評価

### 構成

vLLMベースのprefill / decode分離systemを使い、**1 prefill instance + 3 decode instances**で評価する。ShareGPT test setからprompt長50 token以下の1,914 requestを選び、prefill側の差を小さくしてdecode schedulingの効果を分離している。

主比較は次の3方式。

- **RR + FCFS:** 通常のround-robin dispatch + 到着順処理。baseline。
- **RR + SJF:** worker割当はround-robinのまま、worker内だけOUTLETS予測でSJF。
- **LB + SJF:** OUTLETS予測をinstance-level load balancingとlocal SJFの両方へ使う。

飽和条件は100 QPS。ここではschedulerの寄与を切り分けるため、全構成でspeculative acceleration自体は無効化している。つまりこのsystem結果は「EAGLE speculative decodingでtoken生成が速くなった分」を混ぜず、**長さ予測をschedulerへ与えた効果**を見ている。

### 主結果: short requestのP99が59.8秒 → 39.0秒

100 QPSの飽和条件で、RR+FCFS baselineは17,840.4 tokens/s、平均latency 51.6 s。output 800 token未満のshort requestのP99は **59.8 s** だった。

RR+SJFにするとshort P99は **38.0 s** まで低下する。この段階ではworker割当はround-robinのままなので、tail改善の大部分が**queue内SJFによるHOL blocking緩和**から来ていることが分かる。

LB+SJFではshort P99 **39.0 s**、medium request（800〜1299 token）のP99 **60.1 s**、long request（1300 token以上）は **100.1 s**。baselineの59.8 / 74.6 / 103.0 sと比べ、shortは **34.8%削減**、mediumも改善し、longも悪化していない。

throughputはbaseline **17,840.4 tokens/s** → LB+SJF **18,434.7 tokens/s** で約 **3.3%向上**。RR+SJFの18,108.2 tokens/sよりさらに高いため、instance-level LBはtail latencyよりもcluster-wide load balance / throughput側へ追加寄与している、と論文は分析する。

要するに、**SJFが「誰を先に処理するか」を改善し、LBが「どのworkerへ置くか」を改善する**。34.8%というheadlineはOUTLETS predictor単体のMAE改善ではなく、この予測を使ったscheduling結果である。

### predictorを固定比較した実験

論文はさらに、policyをRR+SJFまたはLB+SJFへ固定し、length predictorだけをNo predictor / PIA / BERT / OPT / MLP / OUTLETS / Oracleで差し替えるcontrolled testを5回ずつ行う。

LB+SJFではstatic MAEが概ね PIA **1014.71**、BERT **309.44**、OPT **306.40**、MLP **267.98**、OUTLETS **221.92**、Oracle 0。OUTLETSはnon-oracleの中で最も低いMAEだった。

同じLB+SJF条件でOUTLETSは平均latency **68.71 s**、medium P99 **104.12 s**、long P99 **154.55 s** と、non-oracle群の中で全体として最も強いlatency profileを示す。Oracleとの差が残っていることから、長さ予測精度をさらに上げればscheduler側にもまだ改善余地がある。

このcontrolled testはbatch invariant modeを有効にしており、絶対throughputは主saturation tableと直接比較すべきではない。目的は同一policy内でpredictor品質だけを比較することにある。

## ablationから分かること

### joint trainingはdraftingを壊していない

SD-ONLYとの比較では、length regression objectiveを追加してもspeculative acceptanceに実質的な低下は見られない。したがって「scheduler signalを得る代わりにspeculative decoding本来の価値を失う」という明確なtrade-offは評価範囲では確認されていない。

### draft decoderを抜くと最も悪化する

multi-level feature fusion、input embedding、Training-Time Test（TTT）、draft decoderなどを外すablationでは、**draft decoderを除去した時のMAE悪化が最大**である。これは「target LLMのhidden stateを複数layerから集めただけ」では不十分で、そこから未来trajectoryへ変換するdraft decoderが長さsignal形成の主要部分であることを示す。

### regressionの方がbucket classificationより良い

長さをいくつかの区間へ分類する方式より、log-spaceのdirect regressionの方が一貫して良い結果だった。schedulerが必要なのは単なる「short / medium / long」のlabelだけでなく、各workerの残仕事量を足し合わせるための連続的なcost estimateなので、回帰値はsystem側でも扱いやすい。

## 既存研究との差

OUTLETSの中心は新しいSJF algorithmではない。SJFもload balancingも既知のscheduling primitiveである。新規性は、**既にspeculative decodingが未来予測のために計算しているrepresentationを、schedulerが必要とするoutput-length signalへ再利用すること**にある。

外部proxy model方式に比べれば追加model実行を避けやすく、target hidden stateへ単純MLPを付ける方式に比べればdraft decoderのtrajectory modelingを利用できる。またspeculative decoding研究が通常「何candidate token受理されたか」「1 token何ms速くなったか」を見るのに対し、この論文は中間表現をcluster resource managementへ渡す用途を示している。

## 限界と適用境界

- **system評価で使うのはstatic prediction。** dynamic predictionの精度改善は示すが、decode途中の再routing、migration、priority更新へは利用していない。
- **speculative decoding未導入systemではbackboneが追加costになる。** 「軽量headだけ」という利点は既存SD backboneを共有できる場合に最も強い。
- **評価labelは2,048 output token以下。** 何万tokenも続くagentic trajectoryや超長reasoningで同じ精度が維持されるかは未検証。
- **sampling条件依存。** temperature、stop sequence、tool callなどにより同じpromptでも出力長分布は変わる。実運用ではmodel / decoding policy変更時の再学習またはcalibrationが必要になり得る。
- **SJFには一般にstarvation riskがある。** 評価ではlong requestは悪化しなかったが、常にshort requestが流入し続ける別workloadでも保証されるわけではない。
- **主system評価は1 prefill + 3 decode instance。** より大規模な数十〜数百decode replicaでのrouting scalabilityはこの評価から直接は分からない。
- **予測誤差は消えない。** Oracleとの差が残るため、より厳しいSLO環境ではuncertainty-aware schedulingと組み合わせる余地がある。

## 実装上の含意

この論文から一般化できる重要な設計原則は、**推論高速化のために既に計算している中間表現を、control plane用のsignalとして再利用する**ことである。LLM servingではschedulerのためだけに別modelを置くと、そのmodelのlatency、GPU memory、version管理、calibrationが新たな運用costになる。

EAGLE-3型speculative decodingを既に採用しているなら、draft stateをlength headへ渡し、まずはadmission時のload balancingとSJFだけに使うのが実装上もっとも単純である。その後dynamic predictionを利用して、decode途中のworker migrationやpriority再調整まで行えれば、OUTLETSが示した「生成が進むほど残長推定が良くなる」性質をさらに活かせる可能性がある。

一方、speculative decodingを使っていないruntimeにOUTLETSだけを入れる場合は、BERT/MLPなどのより小さいpredictorと、72.3M級draft backboneの追加costを含めて比較すべきである。どの方式が得かは、予測精度そのものではなく、**予測cost + scheduling改善によるsaved latency / throughput**で判断する必要がある。
