# Optimizing LLM Inference: Fluid-Guided Online Scheduling with Memory Constraints

> 生成に伴って増えるKV cacheを内生的メモリ制約として流体近似し、均衡batch構成から導くWAIT/Nested WAITの閾値制御でeviction cascadeを抑え、特に高負荷域の安定性とlatencyを改善する。

## 問題

LLM servingではprefill後もdecode tokenが増えるたびにKV cacheが成長する。batchを大きくすると固定overheadを共有できthroughputは上がる一方、resident KV cacheも増え、GPU memoryを超えると進行中requestのevictionとrecomputationが発生する。さらに出力長が未知なら、admission時点で最終memory量を正確に見積もれない。

論文はこの状況を、確率的arrival・多段service・共有memory制約を持つonline schedulingとして定式化する。重要なのは、memory容量が理論上足りていてもFCFS等のnaive policyではresident requestの構成が均衡から外れ、eviction cascadeによって実効throughputとlatencyが悪化し得る点である。

## 新規性

中心は、KV cacheの内生的成長を含むstochastic servingをfluid modelで近似し、arrivalとcompletionが釣り合う**fluid equilibrium**、それを支える必要memory量 M*、stability regionを導いたうえで、その均衡構成をstochastic system側で追跡するthreshold policyを設計したことにある。

出力長既知ではWAIT（Waiting for Accumulated Inference Threshold）、未知ではNested WAITを用いる。後者はoutput-length predictionを前提にせずdecode stageをnested segmentへ分け、生き残ったrequestだけを後段へ進めることで長短requestを実行中に分類する。

## 手法

各promptはprefill stage 0と複数decode stageを持ち、type jのresident promptがdecode stage sにあるとKV memoryは入力長 l_j と進捗 s に応じて増える。1 iterationの時間は固定overhead d0とbatch全体のcached-token量に比例する項 d1 の和で近似する。このため、大batchはd0を償却するが、将来のmemory pressureも増やす。

fluid modelから、各type・stageにどの程度のrequestが存在すべきかというreference compositionを得る。WAITは対応thresholdに余裕がある場合だけpromptをprefill/decodeへ進め、resident populationをこの構成へ戻す方向にadmissionする。既知出力長ではtype別の進行を直接制御できる。

Nested WAITは未知出力長を複数のdecode segmentへ分解し、短いrequestは早いsegmentで完了してmemoryを解放し、残ったrequestだけを次のsegmentへ送る。さらにmoderate-scaleのsafety bufferを設け、未知長によるoverflow/evictionを吸収する。論文の漸近解析では、所定のmemory条件とheavy-traffic scalingの下で両方式がfluid benchmarkへ近づく。

## 評価条件

主評価はVidur simulatorをLlama-2-7B・single NVIDIA A100向けに設定し、synthetic workloadとreal-world workloadを用いる。比較対象はvLLM系のmemory-reactive FCFS schedulingとSarathi系chunked-prefill scheduling。本文ではA100 80GB上のbatch timingを測定し、cached-token総量に対するlinear iteration-time近似を検証している。Appendix H.2ではreal-GPU end-to-end validation、H.4ではprefill-decode disaggregated deploymentへの適用も補足する。

## 主要結果

WAITとNested WAITは、tested baselineに比べて経験的に安定して処理できるarrival-rate領域を広げ、特にcapacity近傍およびoverload時のmean end-to-end latencyを低減する。低負荷では方式間の差は小さいが、負荷が上がるとbaselineはlatencyが急増しcompletion rateが早く飽和する一方、threshold方式はresident workloadをfluid equilibriumに近づけてeviction cascadeを抑える。

論文の主張は単一の最大speedup値よりも、memory growthを事前に制御することでoffered loadに近いcompletionを維持できるstable operating rangeの拡大にある。Nested WAITは出力長予測なしでもsegment boundaryでの分類とsafety bufferにより同じ原理を実現する。

## 限界

- 主理論はPoisson arrival、type化されたprompt、linear multi-stage iteration-time modelなど明示的な仮定に依存する。実際のprefill attentionやhardware saturationでは非線形性が強くなるため、service-time curveの再較正が必要。
- 主評価はVidur simulationで、real A100検証は補足的。異なるmodel、GPU、multi-GPU topology、production schedulerでの一般化は追加検証が必要。
- WAITの既知長版は正確なoutput lengthを前提とする。Nested WAITはこの依存を除く代わりにsegment設計と追加memory bufferを必要とする。
- 論文はeviction mechanism自体の高速化ではなく、recomputationを前提にevictionを起こしにくくするschedulerを扱う。CPU/SSD swapを積極利用するsystemではtrade-offが変わり得る。
- thresholdはreference workload compositionに基づくため、急激な非定常arrivalでは追従・再推定の設計が重要になる。

## 既存研究との差

vLLMやSarathiが主としてmemory management、continuous batching、chunked prefill等のsystem mechanismを提供するのに対し、本研究は**KV cacheが成長するqueueing systemのstabilityそのもの**をモデル化し、fluid equilibriumからadmission thresholdを導く。output length predictorでrequest順序を決める方式とも異なり、Nested WAITは未知長を実行途中のsegment通過で扱う。

## 一般的な実装への示唆

memory overflow後のeviction/recomputeを高速化するだけでなく、resident requestの「件数」ではなくdecode進捗を含む**構成**を制御することが重要である。KV cache容量に余裕が見えても、将来のgrowthを含めた均衡構成から外れればcascadeが起こり得るため、admission controlは現在memoryだけでなくstage distributionを状態として持つ価値がある。
