# Optimizing LLM Inference: Fluid-Guided Online Scheduling with Memory Constraints

> この論文の中心は「GPU memoryが足りなくなってからrequestを追い出す」のではなく、**数十〜数百token先までdecodeするとKV cacheがどのように増えるかを見越して、GPU内に残すrequestの構成そのものを調整する**ことである。大量のrequestを連続量として近似する流体モデル（fluid model）から理想的なbatch構成を求め、実際の確率的request到着をWAIT / Nested WAITというthreshold制御でその状態へ近づける。

## まず何が問題なのか

LLM servingではrequestを複数まとめてGPUへ流す**バッチ処理（batching）**を大きくすると、kernel launchや同期などの固定costを多数requestで共有できるためthroughputが上がる。

しかしLLMには普通のfixed-size jobと違う問題がある。requestのmemory使用量が実行中に増える。

### PrefillとdecodeでKVはどう増えるか

requestが来ると、まず入力prompt全体を処理する**事前充填（prefill）**が行われる。ここで入力token分のKV cacheが作られる。

その後の**復号（decode）**では1 iterationごとに1 tokenずつ出力する。新しいtokenを生成するたびに、そのtokenのKey/ValueもKV cacheへ追加される。

例えば入力512 token、出力1000 tokenのrequestなら、prefill直後のKVは512 token分だが、decode終了近くでは約1512 token分まで成長する。

つまりschedulerがrequestをGPUへ入れた瞬間のmemoryだけ見て「まだ空いている」と判断しても、そのrequest群が後から一斉に長くdecodeするとmemory overflowが起こり得る。

## Overflowすると何が悪いのか

GPUのKV cache容量を超えた場合、一般には

- CPU/SSDへ退避する
- KVを捨てて後で再計算する

などが必要になる。

この論文は特に、KVを捨ててprefillからやり直す**再計算（recomputation）**を想定する。

一度overflowすると、あるrequestをevictしてmemoryを空けても、そのrequestを再計算した時に再びKVが戻ってくる。さらに別requestがoverflowし、またevictされると、

`overflow → eviction → recomputation → 再びmemory圧迫 → 次のeviction`

という**eviction cascade**が起きる。

GPU自体は忙しく動いているのに、完了requestへつながらない再計算が増えるため、実効throughputが崩れる。

## なぜ「空きmemoryがある間はrequestを入れる」では駄目なのか

重要なのはGPU内requestの総数だけではない。

同じ100 requestでも、

- ほとんどがprefill直後
- 多くがdecode後半

では将来のKV量が全く違う。

decode後半のrequestはすでに大きなKVを持ち、さらに長時間residentする。長いrequestばかり溜まると、その時点ではmemory内に収まっていても、次の数iterationでoverflowしやすい。

したがってschedulerが見るべきstateは

`resident request数`

だけではなく

`prefillに何件、decode 1〜20 token段階に何件、decode 21〜50 token段階に何件……`

という**進捗ごとの構成（composition）**になる。

## 流体モデル（fluid model）とは何か

queueing theoryで使うfluid modelは、大量の個別requestを1件ずつ追う代わりに、requestの流れを水のような連続量として近似する方法である。

実systemではrequestがばらばらの時刻に到着し、出力長も揺れる。しかし十分長い時間・高いloadで見ると、

- 1秒あたり何request入るか
- 各stageへどれだけ流れるか
- 1秒あたり何request完了するか

を連続的なflowとして扱える。

この近似systemで「流入量と流出量が釣り合い、各prefill/decode stageのrequest数が一定になる状態」が**流体平衡（fluid equilibrium）**である。

### なぜこの平衡が役に立つのか

平衡状態が分かれば、例えば

- prefill直後のrequestは平均何件いるべきか
- decode前半には何件いるべきか
- decode後半のlong requestは何件までならよいか

という理想的なresident populationが分かる。

さらに、その構成を維持するのに必要なKV memory量 `M*` も計算できる。

`M* <= GPU capacity C`

なら、少なくともfluid approximation上はarrival rateを処理し続けられる可能性がある。これが論文のいう**安定領域（stability region）**である。

ただし、ここが重要で、`M* <= C` だからFCFSでも安定するわけではない。

確率的な実systemではrequest到着が偏り、FCFS等では一時的にlong requestが大量にresidentして平衡構成から外れる。その結果、理論上はcapacity内でもeviction cascadeを起こせる。

WAITはこのずれを抑えるためのonline制御である。

## WAIT: output lengthが分かっている場合

WAITは **Waiting for Accumulated Inference Threshold** の略である。

名前の通り、各stageで「処理するのに十分なrequestが溜まるまで待つ」thresholdを持つ。

### 直感

1件来るたび即座にGPUへ入れると、その場ではlatencyが低く見える。しかし小batchばかりになりfixed overheadを共有できず、しかもstage populationが理想構成から崩れやすい。

逆にrequestを溜めすぎるとmemory pressureが高くなる。

fluid equilibriumから「このstageにはおよそn件ずつ流すとarrival/completion/memory growthが釣り合う」というreference量を求め、WAITはそのthresholdに沿ってrequestを進める。

### 実際の動き

output lengthが既知なら、requestを長さclassへ分けられる。

schedulerは各type・decode stageについてthresholdを持ち、

- thresholdに十分なworkがある
- 次へ進めてもmemory構成がreferenceから大きく外れない

場合にだけbatchへ入れる。

不足していれば少し待つ。

「GPUを常に仕事で埋めるwork-conserving scheduling」と違い、**今すぐ処理できても将来のmemory imbalanceを避けるため意図的に待たせる**のが特徴である。

この待ちによりbatching効率も上げつつ、decode後半へrequestが流れすぎることを防ぐ。

## Nested WAIT: output lengthが分からない場合

現実のLLMでは、requestを受けた時点で何token出力するか普通は分からない。

WAITをそのまま使うには「これは20 tokenで終わるrequest」「これは500 token続くrequest」と事前分類する必要があり、実用上強い仮定になる。

Nested WAITはこれを**実際にdecodeを進めながら分類する**。

### Decodeをsegmentへ分ける

例えばoutput長を

- Segment 1: token 1〜20
- Segment 2: token 21〜50
- Segment 3: token 51〜100

のように区切る。

すべてのrequestはSegment 1へ入る。20 tokenまでに終わったrequestはそこでsystemを出てKVを解放する。

20 tokenを超えてまだ続くrequestだけがSegment 2の候補になる。

つまり20 token生成した時点で初めて

「このrequestは短文ではなく、少なくとも20 tokenを超えるlonger requestだった」

と情報が得られる。

Nested WAITはこの**survivor**だけを後段segmentへ送る。

### なぜNestedなのか

後段へ行くほどrequest数は自然に減る。

Segment 1には全requestが来るが、Segment 2には20 tokenを超えたものだけ、Segment 3には50 tokenを超えたものだけが来る。

各segmentに別thresholdを置くことで、long responseだけがdecode後半へ大量蓄積するのを防ぐ。

requestの最終output lengthを予測するのではなく、**実際に生き残ったかどうかをboundaryで観測して段階的に分類する**のがポイントである。

## Safety bufferは何のためか

output length未知では、次のsegmentへ何件surviveするかは確率的である。

平均では30%しか残らないとしても、あるbatchでは偶然50%残るかもしれない。

その揺れを吸収するためNested WAITは追加の**安全余裕（safety buffer）**をmemoryへ確保する。

理論解析では、このbuffer込みでthroughput、latency、eviction avoidanceの保証を導く。

## Iteration time model

論文はGPUの1 iteration時間を、大まかに

`固定overhead + batch内のKV量に比例するcost`

で近似する。

直感的には、decodeでは各requestが過去KVを読むので、batch内で抱えているcached token総量が大きいほど1 stepが重くなる。一方でfixed overheadはbatchを大きくするとrequestあたりで償却できる。

このためschedulerは

- batchを大きくしてGPU効率を上げたい
- resident KVは増やしすぎたくない

というtrade-offを解くことになる。

WAITはfluid equilibriumから、この2つが釣り合うbatch/stage構成を導く。

## 評価条件

主評価は離散事象LLM serving simulatorのVidurを使用する。

- Model: Llama-2-7B
- GPU: NVIDIA A100 80GB相当
- 主比較: vLLM、Sarathi
- synthetic workloadとlmsys-chat-1m由来workload
- AppendixでA100実機timingとend-to-end validationも実施

論文の狙いは最大speedup 1点ではなく、arrival rateを上げたとき**どこまでlatencyが発散せず処理を続けられるか**を見ることにある。

## 主要結果

### Single-type synthetic workload

prompt 512 token、decode 20 tokenの単一typeでは、

- vLLM: およそ19 req/s付近から不安定化
- Sarathi: およそ22 req/s付近
- WAIT: およそ23 req/s付近までlatencyを制御

という順になった。

低負荷では差は小さいが、23 req/s付近ではWAITとSarathiのmean latency差が70%以上まで拡大する。

これはrequest typeを賢く分類した効果ではない。単一typeなので、**threshold admissionだけで平衡構成へ近づける効果**を示している。

### Two-type workload

70%がdecode 20 token、30%がdecode 50 tokenという条件では、

- vLLM: stable boundary ≈18 req/s
- Sarathi: ≈21 req/s
- Nested WAIT: ≈22 req/s

となる。

ここでは30%のlong requestがdecode後半に溜まることが主なmemory pressureになる。Nested WAITは後段segment populationを制限し、short requestがlong requestの蓄積に巻き込まれるのを防ぐ。

### Long-decode workload

prompt 512 / decode 1000 tokenではrequest 1件が長時間KVを保持するため差がより分かりやすい。

arrival rate 4.0 req/sで

- WAIT: mean latency 26.4 s、eviction restart 0%
- Sarathi: 30.2 s、restart 2.88%

となった。

4.5 req/sではWAIT 32.3 s、Sarathi 41.7 s、vLLM 53.8 sと報告される。

### lmsys-chat-1m

実conversation distributionでは、filter後のdecode lengthは平均147.3 token、median 116 tokenで、約31%は50 token以下、約14%は300 token超となる。

Nested WAITは最終出力長を予測せず、decode進捗segmentごとにsurvivor数を制御する。高負荷へ近づくほどbaselineよりlatency増加が緩やかになり、fluid modelが予測する安定境界へ実systemを近づける傾向を示す。

## この論文の「性能改善」をどう読むか

この研究は「常に20%速いscheduler」というタイプではない。

低負荷ではvLLM/Sarathiとの差は小さい。GPU memoryに余裕がありevictionが起きないなら、わざわざ待つメリットも小さいからである。

効果が出るのは

- arrival rateがcapacityへ近い
- long outputが混ざる
- KV cacheがmemory限界へ近い
- eviction/recomputeが起き始める

領域である。

つまり主張は**peak throughputを少し上げることより、overload直前でsystemが崩れる境界を後ろへずらすこと**にある。

## 既存手法との差

vLLMはpaged KV managementやcontinuous batchingによりmemoryを効率利用するが、基本的には現在stateへ反応するsystemである。

Sarathiはchunked prefill等でbatch interferenceを抑える。

本研究はそれらと違い、

`将来のKV growthを含むqueueing system全体の定常構成`

を先に理論モデル化し、そのreference compositionへonline schedulerを寄せる。

また、output length predictorを使ってrequestごとの最終長を直接当てる方式とも異なる。Nested WAITは「20 token時点でまだ終わっていない」という実行中に判明した情報だけでlong requestを段階分類する。

## 限界

- 主理論はPoisson arrival、type化request、linear iteration-time approximation等の仮定に依存する。
- 主評価はVidur simulationであり、A100実機評価は補足的である。
- model/hardwareが変わればiteration-time modelやthresholdを再較正する必要がある。
- Nested WAITはoutput length predictionを不要にする代わり、decode segment設計とsafety bufferを必要とする。
- workload distributionからthresholdを作るため、急激にrequest mixが変化するproduction環境では再推定が必要になる。
- 本研究はCPU/SSD swap自体を高速化する研究ではなく、recomputation前提でoverflowを起こしにくくする研究である。高速swap tierがある場合は最適trade-offが変わる。
- 意図的にrequestを待たせるため、低負荷で極端にTTFTを最小化したい用途ではthreshold設定が重要になる。

## 一般的な実装への示唆

LLM schedulerでmemory pressureを見るとき、単純な

`現在のfree VRAM`

だけでは不足する。

必要なのは

`現在のKV量 + resident requestがdecodeを続けた時のstage distribution`

である。

特にlong-tail outputでは、後半stageへ進む少数requestが長時間大量KVを保持する。現在memoryが空いているからといって新規requestを大量admitすると、数十iteration後にcascadeが発生し得る。

したがって、KV eviction / offload policyだけでなく**admission controlをmemory hierarchyの一部として設計する**価値がある。
