# InstantInfer：通信有限オートマトンでLLMコールドスタートの依存関係を組み替える

## 概要

LLM推論のコールドスタートは、GPU上に対象モデルがまだ存在しない状態から、プロセス起動、モデル重みの読み込み、KVキャッシュ・CUDA実行環境の準備を経て、最初の要求を処理できる状態にするまでの経路である。複数モデルをオンデマンドで起動するサーバーレス環境では、通常の推論速度が速くても、起動だけで数十秒から数分かかると初トークン遅延（TTFT）を支配する。原著の例では10B未満で約50秒、70B級で約160秒、400B超で約300秒を要し、コールドスタートを含むTTFTの99.6〜99.9%が起動に費やされる。

InstantInferは、モデルの演算を近似したり量子化したりするのではなく、**起動プログラムの実行依存関係とI/O粒度**を改善する。vLLMの従来実装では、frontend、core、GPU workerを順に初期化し、モデル重みを個々のtensor単位で読み込む。この実装は理解しやすいが、互いに独立な準備まで直列に待たせ、小さなI/Oを多数発行してストレージ帯域を使い切れない。

著者はCommunicating Finite Automata（CFA、通信有限オートマトン）で構成要素の進行状態を表し、必要な前提だけを待つ並列化と、重みを大きなチャンクに統合するI/Oを設計する。さらに旧モデルが稼働中に新モデルのGPU非依存準備を進め、切替停止時間を短縮する。H20環境ではServerlessLLM比の単発コールドスタートTTFTが2.7〜2.9倍、通常のvLLM/SGLang比では3.2〜7.2倍高速化した。ただし**最大7.2倍は定常生成tokens/sの改善ではない**。

## 問題設定：直列起動とI/O粒度の不一致

コールドスタートは大きくProcess Init、Model Init、Optimizeの三段階に分かれる。Process InitではPythonパッケージのimport、CUDAコンテキスト、IPC、プロセスツリーを作る。Model Initでは重みをストレージからホストへ、さらにGPUへ移す。OptimizeではKV領域、CUDA Graph capture、演算子の準備などを行う。原著のQwen3-30B-A3B例ではvLLMの各段階が26/58/23秒、SGLangが27/58/56秒であり、単に重み読込だけ速くしても全体の起動遅延は残る。

第一の問題は、親プロセスが完全にReadyになるまで子プロセスの独立な初期化を待たせることだ。子が親からの設定を必要とする時点だけ待てばよいのに、プログラムの呼出し順が粗いバリアを作っている。第二の問題はtensor単位のI/Oである。重みテンソルは形状と分割によりサイズがばらばらで、SSDやネットワークストレージの望ましい連続転送サイズと一致しない。複数GPUへのtensor-parallel分割はさらに断片化を招く。

従来のServerlessLLMはモデルロード用の形式変換・キャッシュなどを利用し、既存エンジンの起動を短縮する。InstantInferは起動処理そのものを状態遷移へ分解して、独立処理の並列化とI/O統合を同じ原理で扱う点が異なる。特定のGPU演算子を高速化する技術ではない。

## 手法：CFAで依存関係を記述する

### 1. 単調状態と状態依存DAG

各物理・論理コンポーネントc（プロセス、重みチャンク、tensor、モデル）を有限オートマトンとし、状態S(c)は有限の順序集合に沿って単調・不可逆に進む。コンポーネント間の依存は「ciが状態siに到達したら、cjは状態sjから次へ遷移してよい」という組で表す。全遷移と依存が有向非巡回グラフ（DAG）になる場合、独立な遷移は並行実行できる。

原著Theorem 1はDAG CFAの停止性、Theorem 2は各コンポーネント内部の状態遷移順序が従来のChain CFAと同じなら、両者の終状態が一致することを示す。**無条件の並列化安全性を証明したわけではない**。正しい依存を宣言し、内部状態遷移を保持し、DAG条件を満たすことが前提である。共有データの依存を漏らせば、この形式化だけでバグが消えるわけではない。

### 2. 開発者向けチャネルと同期

開発者は既存コードの節目に`channel.set_state(component,state)`を挿入し、完了した状態を公開する。別の処理は`channel.wait_state(component,state)`で必要な前提を待つ。チャネルは関連するコンポーネントの状態を管理する独立した名前空間で、異種の全状態を一つの巨大な表へ入れることを避ける。バックグラウンドのデーモンが状態公開と待機者の解除を処理するため、開発者は元の逐次コードの大部分を維持しつつ、依存関係を明示的に表現できる。

CFAのもう一つの用途は、互いに独立な小さなオートマトンの遷移を一つの大きな遷移へまとめることである。これにより、論理的なtensor操作を維持したまま、物理的なI/Oをストレージに適したチャンク単位へ変えられる。並列化とI/O統合は別の小技ではなく、状態遷移の分解・統合という共通の抽象化で説明される。

### 3. プロセスツリーの並列materialization

従来のfrontend→core→workerという順次起動では、子のローカルな環境準備まで親の完了を待つ。InstantInferでは各プロセスの状態をStart、Constructed、Readyなどに分け、子は親のReady前でも独立にConstructedまで進める。親の情報が必要な遷移の直前でだけ待つ。GPU workerが複数あると、逐次初期化で足し算されていた準備時間を重ねられる。依存の粒度を細かくするだけであり、親が提供する実データの準備完了前に子が利用することは許さない。

### 4. チャンク単位のtensor materialization

重みファイルを一定サイズのチャンクへ分割し、各チャンクにInDisk、InMem、InGPU、Destroyedという状態を与える。各tensorはAlloc、Loadedの状態を持ち、どのチャンクに属するデータが必要かを事前に対応付ける。チャンクをストレージ→ホスト→GPUへパイプライン転送し、必要なチャンクがGPUへ届いた時点でtensorの最終領域へコピーして組み立てる。すべての関連tensorがLoadedになった後に一時チャンクを解放するため、未使用のデータを早く消してしまわない。

複数GPUではチャンクをrankごとのsegmentに分割し、各GPUが自分のsegmentを並列読込した後、NCCL AllGatherで完全なチャンクを各GPUへ構築する。これは各GPUが同じデータを個別にストレージから重複読込するより、ストレージとGPU間ネットワークの複数経路を利用できる場合に有利である。ただしAllGatherの通信費用が追加され、GPU間接続が遅い環境では利得が小さくなり得る。

### 5. モデル切替時の稼働停止を短縮

旧モデルM1はActive→GMemFreed→Destroyed、新モデルM2はStart→EnvReady→Activeの状態を持つ。新モデルはGPU非依存のプロセス・環境準備を旧モデルがまだサービス中に実施する。GPUメモリの競合を避けるため、M1がGMemFreedに到達した後にだけM2がEnvReadyからGPU依存の準備へ進む。著者は過去の初期化時間・解放時間の予測を用い、旧モデルの停止開始を新モデルの準備完了へ近づけるようにスケジュールする。旧モデルを早く止めすぎて無駄な待機を作ることも、新モデルがGPUを必要とするのに旧モデルが占有し続けることも減らす狙いである。

## 評価条件

原著Section 6.1による。H20テストベッドはNVIDIA H20 141GB×8、NVLink、50GB/sのGPFSストレージ、L40は48GB×8、PCIe、20GB/sストレージで、いずれもホストメモリ2TB、Xeon Platinum 8468（192論理コア）。比較エンジンはvLLM 0.13.0、SGLang 0.5.9、ServerlessLLM 0.8.0。torch compileキャッシュを全方式で有効化する。単発コールドスタートではモデルを原則としてストレージから読み、メモリキャッシュ前提の別実験とは区別する。

H20ではQwen3-30B-A3B（TP1）、Llama-3.1-70B（TP2）、Qwen3-235B-A22B（TP4/EP4）、DeepSeek-R1（TP8/EP8）を評価。L40ではLlama-3.1-8B（TP1）、Qwen3-30B-A3B（TP2/EP2）、Qwen3-32B（TP4）、Llama-3.1-70B（TP8）を用いる。ShareGPT由来の最大32Kトークンの要求を用い、TTFTにはエンジン起動、待ち行列、prefillを含める。モデル起動を含まない定常のtokens/sとは異なる。

複数インスタンスを同時起動するQwen3-30B-A3Bのメモリキャッシュ実験では、1インスタンス時の改善は比較対象比2.6〜4.3倍、8インスタンス時は1.6〜2.3倍に縮小する。プロセス起動、Python import、CUDAコンテキスト初期化が競合し、インスタンス数に対して理想的な線形スケーリングにはならない。したがって「モデルが増えるほど常に7.2倍」という解釈は誤りである。

アブレーションではtensor materializationの高速化が起動時間に対して2.4〜3.7倍の最大の寄与を持ち、そこへprocess-tree materializationを追加すると最適化済み構成に対してさらに1.2〜1.5倍の改善を示す。モデル切替の重なりは切替時の停止時間に寄与するが、単純な単発起動と同じ指標ではない。原著はモデルロード単体で最大32.3倍という値も報告するが、**この値はコールドスタートTTFTや生成速度の倍率ではない**。

定常稼働への影響を調べるため、要求を10秒間隔で送る実験では、コールドスタート中の初期要求は遅いものの、起動完了後はresident vLLMと要求遅延が収束する。これは起動の高速化が定常処理を大きく悪化させない証拠であり、定常推論そのものが高速化したという証拠ではない。

## 実装状況・限界・負の結果

著者はvLLMのPython初期化コードを約3000行変更し、チャンクI/O用のC++拡張を約2700行追加した。GDS/cuFile、libaio、tmpfs/cudaMemcpyAsyncに対応する。プログラムを全面的に作り直す必要はないという利点がある一方、**数千行規模の改修はゼロコストの設定変更ではない**。正しい依存状態の設計、チャネルの管理、エラー時の再試行、ストレージ環境ごとの調整は実装上の負担となる。

性能はストレージ帯域、NVLink/PCIe構成、モデルのtensor分割、GPU数、既存エンジンのバージョンに強く依存する。十分にメモリキャッシュされたモデル、常時起動する少数モデル、Optimize段階が主律速の環境では改善率が縮む可能性がある。論文は主にコールドスタート時のTTFTとモデル切替を扱い、長時間のcontinuous batchingの生成速度や総GPU費用の削減を直接保証しない。原著はOptimize段階の高速化は直交する課題と明記しており、CUDA Graphやコンパイルの最適化をCFAの効果と混同してはいけない。

CFAの終状態同等性の定理は、各コンポーネント内部の遷移順序と依存DAGの妥当性を仮定する。性能上の理由で依存を省略した実装のデータ競合を自動で検出する仕組みではない。また実機はH20/L40と指定されたネットワークストレージの二種類であり、単一GPUのローカルSSDや異なるOS・コンテナ・GPU共有形態へ数値を直接外挿できない。
