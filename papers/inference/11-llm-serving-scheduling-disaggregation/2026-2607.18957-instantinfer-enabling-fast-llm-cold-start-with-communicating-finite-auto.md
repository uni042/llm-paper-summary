# InstantInfer：通信有限オートマトンでLLMコールドスタートの依存関係を組み替える

## 概要

LLM推論のコールドスタートは、計算装置上に対象モデルがまだ存在しない状態から、プロセス起動、モデル重みの読み込み、KVキャッシュ・CUDA実行環境の準備を経て、最初の要求を処理できる状態にするまでの経路である。複数モデルをオンデマンドで起動するサーバーレス環境では、通常の推論速度が速くても、起動だけで数十秒から数分かかると初トークン遅延（TTFT）を支配する。原著の例では10B未満で約50秒、70B級で約160秒、400B超で約300秒を要し、コールドスタートを含む初トークン遅延の99.6〜99.9%が起動に費やされる。

InstantInferは、モデルの演算を近似したり量子化したりするのではなく、**起動プログラムの実行依存関係とI/O粒度**を改善する。vLLMの従来実装では、フロントエンド、core、GPUワーカーを順に初期化し、モデル重みを個々のテンソル単位で読み込む。この実装は理解しやすいが、互いに独立な準備まで直列に待たせ、小さなI/Oを多数発行してストレージ帯域を使い切れない。

著者はCommunicating Finite Automata（CFA、通信有限オートマトン）で構成要素の進行状態を表し、必要な前提だけを待つ並列化と、重みを大きなチャンクに統合するI/Oを設計する。さらに旧モデルが稼働中に新モデルの計算装置非依存準備を進め、切替停止時間を短縮する。H20環境ではServerlessLLM比の単発コールドスタート初トークン遅延が2.7〜2.9倍、通常のvLLM/SGLang比では3.2〜7.2倍高速化した。ただし**最大7.2倍は定常生成tokens/sの改善ではない**。

## 問題設定：直列起動とI/O粒度の不一致

コールドスタートは大きくプロセス初期化、モデル初期化、最適化段階の三段階に分かれる。プロセス初期化ではPythonパッケージのimport、CUDAコンテキスト、IPC、プロセスツリーを作る。モデル初期化では重みをストレージからホストへ、さらに計算装置へ移す。最適化段階ではKV領域、CUDA Graph capture、演算子の準備などを行う。原著のQwen3-30B-A3B例ではvLLMの各段階が26/58/23秒、SGLangが27/58/56秒であり、単に重み読込だけ速くしても全体の起動遅延は残る。

第一の問題は、親プロセスが完全にReadyになるまで子プロセスの独立な初期化を待たせることだ。子が親からの設定を必要とする時点だけ待てばよいのに、プログラムの呼出し順が粗いバリアを作っている。第二の問題はテンソル単位のI/Oである。重みテンソルは形状と分割によりサイズがばらばらで、SSDやネットワークストレージの望ましい連続転送サイズと一致しない。複数計算装置へのテンソル-parallel分割はさらに断片化を招く。

従来のServerlessLLMはモデルロード用の形式変換・キャッシュなどを利用し、既存エンジンの起動を短縮する。InstantInferは起動処理そのものを状態遷移へ分解して、独立処理の並列化とI/O統合を同じ原理で扱う点が異なる。特定の計算装置演算子を高速化する技術ではない。

## 手法：CFAで依存関係を記述する

### 1. 単調状態と状態依存有向非巡回グラフ

各物理・論理コンポーネントc（プロセス、重みチャンク、テンソル、モデル）を有限オートマトンとし、状態S(c)は有限の順序集合に沿って単調・不可逆に進む。コンポーネント間の依存は「ciが状態siに到達したら、cjは状態sjから次へ遷移してよい」という組で表す。全遷移と依存が有向非巡回グラフ（DAG）になる場合、独立な遷移は並行実行できる。

原著定理 1は有向非巡回グラフ CFAの停止性、定理 2は各コンポーネント内部の状態遷移順序が従来のChain CFAと同じなら、両者の終状態が一致することを示す。**無条件の並列化安全性を証明したわけではない**。正しい依存を宣言し、内部状態遷移を保持し、有向非巡回グラフ条件を満たすことが前提である。共有データの依存を漏らせば、この形式化だけでバグが消えるわけではない。

### 2. 開発者向けチャネルと同期

開発者は既存コードの節目に`channel.set_state(component, state)`を挿入し、完了した状態を公開する。別の処理は`channel.wait_state(component, state)`で必要な前提を待つ。チャネルは関連するコンポーネントの状態を管理する独立した名前空間で、異種の全状態を一つの巨大な表へ入れることを避ける。バックグラウンドのデーモンが状態公開と待機者の解除を処理するため、開発者は元の逐次コードの大部分を維持しつつ、依存関係を明示的に表現できる。

CFAのもう一つの用途は、互いに独立な小さなオートマトンの遷移を一つの大きな遷移へまとめることである。これにより、論理的なテンソル操作を維持したまま、物理的なI/Oをストレージに適したチャンク単位へ変えられる。並列化とI/O統合は別の小技ではなく、状態遷移の分解・統合という共通の抽象化で説明される。

### 3. プロセスツリーの並列実体化

従来のフロントエンド→中核プロセス→GPUワーカーという順次起動では、子のローカルな環境準備まで親の完了を待つ。InstantInferでは各プロセスの状態をStart、Constructed、Readyなどに分け、子は親のReady前でも独立にConstructedまで進める。親の情報が必要な遷移の直前でだけ待つ。GPUワーカーが複数あると、逐次初期化で足し算されていた準備時間を重ねられる。依存の粒度を細かくするだけであり、親が提供する実データの準備完了前に子が利用することは許さない。

### 4. チャンク単位のテンソル 実体化

重みファイルを一定サイズのチャンクへ分割し、各チャンクにInDisk、InMem、InGPU、Destroyedという状態を与える。各テンソルはAlloc、Loadedの状態を持ち、どのチャンクに属するデータが必要かを事前に対応付ける。チャンクをストレージ→ホスト→計算装置へパイプライン転送し、必要なチャンクが計算装置へ届いた時点でテンソルの最終領域へコピーして組み立てる。すべての関連テンソルがLoadedになった後に一時チャンクを解放するため、未使用のデータを早く消してしまわない。

複数計算装置ではチャンクをrankごとのsegmentに分割し、各計算装置が自分のsegmentを並列読込した後、NCCL AllGatherで完全なチャンクを各計算装置へ構築する。これは各計算装置が同じデータを個別にストレージから重複読込するより、ストレージと計算装置間ネットワークの複数経路を利用できる場合に有利である。ただしAllGatherの通信費用が追加され、計算装置間接続が遅い環境では利得が小さくなり得る。

### 5. モデル切替時の稼働停止を短縮

旧モデルM1はActive→GMemFreed→Destroyed、新モデルM2はStart→EnvReady→Activeの状態を持つ。新モデルは計算装置非依存のプロセス・環境準備を旧モデルがまだサービス中に実施する。計算装置メモリの競合を避けるため、M1がGMemFreedに到達した後にだけM2がEnvReadyから計算装置依存の準備へ進む。著者は過去の初期化時間・解放時間の予測を用い、旧モデルの停止開始を新モデルの準備完了へ近づけるようにスケジュールする。旧モデルを早く止めすぎて無駄な待機を作ることも、新モデルが計算装置を必要とするのに旧モデルが占有し続けることも減らす狙いである。


### 状態遷移の依存性と安全性の監査

原著第3節では、各構成要素を有限個の状態を単調に進むオートマトンとして扱う。ある構成要素の状態が前提となる別の構成要素の遷移だけを依存辺で結び、全体が閉路を持たない有向グラフになることを要求する。前提を満たした遷移は、もとの逐次プログラムで先に現れた別処理の完了を待たずに進められる。通信チャネルの状態公開操作は待機中の処理を起こし、待機操作は必要状態が既に公開されていれば直ちに通過する。これによって初期化コードの処理順を無制限に入れ替えるのではなく、必要な依存だけを残して並列性を得る。

定理1はこの依存グラフの終端到達を、定理2は構成要素内部の状態遷移順序を元の逐次版と同一に保った場合の最終状態の一致を述べる。これは任意のプログラムを自動的に並列化しても安全という保証ではない。実装者が依存関係を漏らせば、共有資源の競合や読み出し前の使用が起き得る。著者はプロセス生成、テンソル読込、モデル切替という個別の改修でデータ安全性を論じている。証明の前提と実装の前提を分けて読む必要がある。

重みの読込では、モデル上の論理単位である小さなテンソルをそのまま大量の入出力要求にすると、記憶装置の効率的な転送単位と一致しない。著者は互いに独立な読込を大きな連続チャンクへまとめ、記憶装置から主記憶、主記憶から計算装置への転送を重ねる。これは圧縮率の向上ではなく、細粒度要求の発行費用と帯域未使用時間を減らす工夫である。重みのレイアウトや並列分割が変わると適切なチャンク境界も変わり得るため、単一の最適値を全環境へ適用できない。

## 評価条件

原著節 6.1による。H20テストベッドはNVIDIA H20 141GB×8、NVLink、50GB/sのGPFSストレージ、L40は48GB×8、PCIe、20GB/sストレージで、いずれもホストメモリ2TB、Xeon Platinum 8468（192論理コア）。比較エンジンはvLLM 0.13.0、SGLang 0.5.9、ServerlessLLM 0.8.0。torch compileキャッシュを全方式で有効化する。単発コールドスタートではモデルを原則としてストレージから読み、メモリキャッシュ前提の別実験とは区別する。

H20ではQwen3-30B-A3B（TP1）、Llama-3.1-70B（TP2）、Qwen3-235B-A22B（TP4/EP4）、DeepSeek-R1（TP8/EP8）を評価。L40ではLlama-3.1-8B（TP1）、Qwen3-30B-A3B（TP2/EP2）、Qwen3-32B（TP4）、Llama-3.1-70B（TP8）を用いる。ShareGPT由来の最大32Kトークンの要求を用い、初トークン遅延にはエンジン起動、待ち行列、入力処理を含める。モデル起動を含まない定常のtokens/sとは異なる。

定常稼働への影響を調べるため、要求を10秒間隔で送る実験では、コールドスタート中の初期要求は遅いものの、起動完了後はresident vLLMと要求遅延が収束する。これは起動の高速化が定常処理を大きく悪化させない証拠であり、定常推論そのものが高速化したという証拠ではない。


### 単発要求と突発到着の違い

原著第6.2節の単発要求実験は、要求ごとに新しい推論エンジンを起動して初トークンまでの時間分布を測る。高速なH20計算装置を8基と毎秒50ギガバイトの共有記憶装置を使う条件では、コールドスタート専用のServerlessLLMに対して2.7〜2.9倍、通常のvLLMとSGLangに対して3.2〜7.2倍となる。帯域が毎秒20ギガバイトの共有記憶装置とL40計算装置8基の条件では、それぞれ1.8〜2.6倍、2.1〜3.7倍である。異なる構成で倍率が変わるため、最大値だけで汎用性能を判断しない。

32要求が同時に到着する突発負荷では、ServerlessLLM比1.8〜2.5倍、通常エンジン比2.6〜4.9倍に相対利得が縮む。起動時間を短縮しても、要求の待ち行列と入力処理が初トークン遅延の一部を占めるためである。原著の付録では16要求と64要求の結果も示され、同時到着数が増えるほど起動以外の時間の比率が高まる。ここで測られたのはコールドスタートを含む要求遅延であり、定常的に稼働するサービスの生成速度ではない。

原著の図8では、初回要求をきっかけに起動したエンジンと、あらかじめ常駐させたエンジンに同じ要求列を投入している。起動中の要求は遅いが、初期化と待機列の解消後には遅延が常駐版へ近づく。この結果は、改修が定常的な要求処理を大きく損なわないことを支持するが、定常処理が高速化したことまでは示さない。

## 実装状況・限界・負の結果

著者はvLLMのPython初期化コードを約3000行変更し、チャンクI/O用のC++拡張を約2700行追加した。GDS/cuFile、libaio、tmpfs/cudaMemcpyAsyncに対応する。プログラムを全面的に作り直す必要はないという利点がある一方、**数千行規模の改修はゼロコストの設定変更ではない**。正しい依存状態の設計、チャネルの管理、エラー時の再試行、ストレージ環境ごとの調整は実装上の負担となる。

性能はストレージ帯域、NVLink/PCIe構成、モデルのテンソル分割、計算装置数、既存エンジンのバージョンに強く依存する。十分にメモリキャッシュされたモデル、常時起動する少数モデル、最適化段階段階が主律速の環境では改善率が縮む可能性がある。論文は主にコールドスタート時の初トークン遅延とモデル切替を扱い、長時間のcontinuous batchingの生成速度や総計算装置費用の削減を直接保証しない。原著は最適化段階段階の高速化は直交する課題と明記しており、CUDA Graphやコンパイルの最適化をCFAの効果と混同してはいけない。

CFAの終状態同等性の定理は、各コンポーネント内部の遷移順序と依存有向非巡回グラフの妥当性を仮定する。性能上の理由で依存を省略した実装のデータ競合を自動で検出する仕組みではない。また実機はH20/L40と指定されたネットワークストレージの二種類であり、単一計算装置のローカルSSDや異なるOS・コンテナ・計算装置共有形態へ数値を直接外挿できない。



再監査では、起動の高速化を「モデルが同じ計算をより少ない演算で実行する」と読み替えないようにした。通信有限オートマトンが扱うのは起動時の依存順序であり、通常の注意演算や専門家層の演算量は変更しない。モデル重みを常時主記憶に置ける場合、起動の発生頻度が低い場合、最適化段階のコンパイルや計算グラフ記録が支配的な場合には、総運用費用に対する改善は小さくなる。著者は最適化段階の高速化を別の研究と組み合わせ得ると説明するが、その組合せの性能値を本研究単独の実測結果として扱ってはならない。
