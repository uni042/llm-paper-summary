# Intelligent Router for LLM Workloads: Improving Performance Through Workload-Aware Load Balancing

> **要点**: この研究は、vLLMのような各GPU内スケジューラを改良するのではなく、その一段手前の「どのLLMインスタンスへ要求を送るか」を最適化する。入力長だけでなく予測出力長、各インスタンスのプリフィル/デコード構成、異なる長さの要求を同時実行したときの干渉を状態として使い、ヒューリスティックで誘導した強化学習（reinforcement learning; RL）ルータが待ち行列とプリエンプションを減らす。

## 概要

複数GPUで同じLLMを提供するサービスでは、到着要求をどのモデルインスタンスへ送るかという**クラスタ側ルーティング**と、各GPU内でどの要求を次のイテレーションへ入れるかという**インスタンス内スケジューリング**が別々に存在する。後者だけを高度化しても、前者が長いプリフィルや長いデコードを同じGPUへ偏らせれば、そのGPUの待ち行列は詰まり、他GPUが空いていても全体遅延は悪化する。

さらにLLM要求は、入力を一括処理するプリフィルと、1トークンずつ生成するデコードで資源特性が違う。入力長だけを見て配置しても出力が長い要求を予測できず、単純なラウンドロビンや最短キューでは「いま何件いるか」は分かっても「その組合せが次の数秒でどんな干渉を起こすか」を表せない。

本論文は、①出力長予測器、②異なるプリフィル/デコード長を同時実行したときの混在ペナルティモデル、③その知識を初期方策へ埋め込んだヒューリスティック誘導RLルータを組み合わせる。Llama-2-7Bを4台のV100上のvLLMで配信する主評価では、2,000要求×20エピソードでラウンドロビン比11.43%の平均エンドツーエンド遅延削減を示す。A100 + Llama-3.1-8Bでも約10.8%改善し、Cloud Provider Xの実負荷では7.8%の改善を報告する。

## 背景と問題設定

### プリフィルとデコードを同じ「1要求」と数えると負荷を誤る

プリフィルは入力トークンを並列に処理するため計算量が入力長へ強く依存し、長いプロンプトが入るとそのイテレーションが長くなる。一方デコードは各要求が1トークンずつ進み、KVキャッシュ容量やバッチ内要求数、残り生成長が継続時間を左右する。

したがって、同じ「キューに5件」でも、5件が短いQAなのか、長文要約+長生成なのかで将来負荷は大きく違う。ルータが件数だけを均等化すると、見かけ上は公平でも処理時間は偏る。

### インスタンス内スケジューラでは、悪い配置を後から完全には直せない

一度あるGPUへ要求を送ると、KVキャッシュなどの状態を持つため、途中で別GPUへ移すのは高コストである。vLLMの先着順（First-Come-First-Served; FCFS）やプリフィルチャンク化を使っても、そのGPUへ長い要求が集中した事実自体は消えない。

論文の位置付けは、カーネルやインスタンス内方策の代替ではなく、**それらが働く前の要求配置を改善する層**である。そのため同じモデル、GPU、インスタンス内スケジューラの条件で「ルータだけ変えたとき」のエンドツーエンド効果を測る。

## 手法

### 1. 入力から出力長を予測する

要求到着時点では入力トークン数は分かるが、生成トークン数は未知である。しかしデコードが何イテレーション続くかを知らなければ、将来のバッチ占有時間を見積もれない。

そこで軽量な応答長予測器を学習し、プロンプト特徴から出力長を推定する。ルータ状態には既知の入力長と予測出力長を入れ、各インスタンスで現在実行中/待機中の要求がどれだけプリフィル・デコード負荷を持つかを表現する。

予測が完全でなくても、長短の相対関係が分かれば単純キュー長より良い配置が可能になる。一方、分布が変わって予測器が外れるとルーティング判断も悪化するため、本方式の重要な依存点でもある。

### 2. ワークロード混在による干渉を実測してモデル化する

長いプリフィルと多数のデコードを同時に処理すると、初回トークン時間（Time To First Token; TTFT）とトークン間時間（Time Between Tokens; TBT）の双方へ影響する。論文は入力長・出力長の異なる要求を組み合わせた実測から、この混在効果を定式化する。

ルータは単に「残りトークン総数が少ないGPU」を選ぶのではなく、新規要求をそのインスタンスへ加えた場合の混在ペナルティを見る。これにより、同じ総仕事量でも相性の悪い組合せを避ける。

### 3. ヒューリスティックをRLの学習初期へガイドとして入れる

状態は各インスタンスの負荷と新規要求特徴、行動は配置先インスタンス、報酬はエンドツーエンド遅延を小さくする方向で構成する。純粋なRLだけでも学習できるが、巨大な状態空間で初期探索が非効率になる。

そこで前節の混在ペナルティをヒューリスティックとして使い、学習初期はその知識を強く反映し、エピソードが進むにつれてガイド係数を指数的に弱める。初期は「既知の悪い混載を避ける」方針から始め、後半はRLがより複雑な配置規則を学ぶ設計である。

論文は、単純にペナルティを報酬へ足すワークロード認識RLと、方策探索自体を誘導するワークロード誘導RLを比較し、後者が最も大きい改善を示す。

### 4. ルータ側で少し待ち、より良い配置機会を作る

到着した瞬間に必ずどこかへ送ると、直後に別インスタンスが空くことを利用できない。提案ルータは短時間ルータ側で待たせる選択肢を持ち、全体待ち時間が減るなら即時割当を避ける。

主評価ではルータ待ち時間が平均2.05秒発生するが、その代わりGPU内の長いキューやプリエンプションが減り、エンドツーエンドでは改善する。つまり「ルータ待ち時間ゼロ」を目的にせず、ユーザが受ける総遅延を最小化する。

## 評価

### 代表的な評価条件

| 項目 | 主評価 |
|---|---|
| モデル | Llama-2-7B-HF |
| GPU | NVIDIA V100 ×4 |
| 推論基盤 | vLLM、既定FCFSのiteration-level scheduler |
| 到着率 | 平均20要求/秒 |
| RL行動間隔 | 0.02秒 |
| 1エピソード | 2,000要求 |
| 反復 | 20エピソード |
| 主指標 | エンドツーエンド遅延、TTFT、TBT、スループット |
| 比較 | Round Robin、基本RL、workload-aware RL、workload-guided RL |
| 追加検証 | A100 + Llama-3.1-8B、chunked prefill、Cloud Provider X実トレース |

### 主評価の結果

| ルータ | Round Robin比の平均遅延改善 | 解釈 |
|---|---:|---|
| 基本RL | **4.35%**（約7.53秒） | 状態を学習するだけでも均等割当より改善 |
| workload-aware RL | **7.79%**（約13.50秒） | 混在ペナルティを報酬へ追加すると改善拡大 |
| workload-guided RL | **11.43%**（約19.18秒） | ヒューリスティックで探索を誘導する構成が最良 |

別の集計表では、同条件でRound Robinの平均E2E遅延248.41秒に対し、workload-guided RLは221.80秒（10.71%減）、chunked prefillを有効にすると220.93秒（11.06%減）と報告される。論文中の11.43%は20エピソードの改善量集計、表の10.71%は平均値から算出される条件であり、数値の集計方法を区別して読む必要がある。

A100 + Llama-3.1-8Bへモデル・ハードウェアを変え、到着率80要求/秒に再プロファイル/再学習した条件でもRound Robin比約10.81%の改善を維持する。実クラウド負荷では約7.8%のエンドツーエンド遅延削減を報告している。

## 既存研究との差

Join-Shortest-QueueやRound Robinは現在の件数/割当回数を使うが、各要求のプリフィル長、将来デコード長、異種要求を同時実行したときの干渉を直接表さない。本方式は出力長予測と混在モデルを状態へ持ち込み、LLM固有の二相実行をルーティング判断へ入れる。

インスタンス内スケジューラ最適化とは競合せず、chunked prefillやprompt cachingなどが入った構成でも、その組合せを再プロファイルしてルータを学習し直せる。論文はこの性質から、特定のインスタンス内スケジューラが持つ性能上限を評価するベンチマーク枠組みとしても利用できると述べる。

## 限界・実装状況

強化学習方策はモデル、GPU、インスタンス内スケジューラ、入力/出力長分布へ依存する。A100 + Llama-3.1へ移す際にも到着率に合わせてプロファイルと学習をやり直しており、ゼロ設定で別クラスタへ移植できる方式ではない。

出力長予測が外れると将来デコード負荷の見積もりが崩れる。また実トレースの傾向が変われば、学習時の混在ペナルティも古くなる。オンラインで頻繁に再学習する場合は、その運用コストと方策安定性を別途考える必要がある。

主評価は同一モデルの複数**均質インスタンス**間ルーティングであり、GPU世代やモデルが混在する異種クラスタの価格性能最適化を直接扱う研究ではない。さらに平均E2E遅延改善が主目的で、厳密なSLO保証を行うスケジューラとは目的関数が異なる。
