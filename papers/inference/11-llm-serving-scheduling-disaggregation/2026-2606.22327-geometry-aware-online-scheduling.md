# Geometry-Aware Online Scheduling for LLM Serving: From Theoretical Bound to System Practice

> **SVFはrequestを「何token残っているか」だけでなく、「その間にどれだけKV memoryを占有し続けるか」まで面積として数え、小さいmemory-time volumeから実行することで、memory-boundなLLM servingのhead-of-line blockingを減らす。**

## 概要

LLM servingで短いrequestを先に処理する最短ジョブ優先（Shortest Job First; SJF）は直感的に強い。出力が50 tokenで終わるrequestを2,000-token requestより先に入れれば、短requestが長時間待つ先頭job待ち（Head-of-Line blocking; HOL blocking）を減らせるからである。

しかしLLM decodeには、通常のCPU job schedulingと大きく違う性質がある。requestは実行時間だけでなく、**生成するたびに増えるKV cacheというmemory resourceを同時に占有する**。promptが8,000 tokenあるrequestは、decode開始直後から8,000-token分近いKVを持ち、token生成ごとに8,001、8,002……と増えていく。一方promptが100 tokenなら、同じoutput長でも占有するmemoryははるかに小さい。

したがってoutput長だけが同じ2 requestでも、GPU memory pressureへの寄与は違う。SJFはどちらも同じ長さのjobとして扱うが、memory-constrained servingでは「大量のKVを長時間握り続けるrequest」を早く入れると、後続requestをadmitできる空きKV capacityが減る。

本研究は、このrequestを1次元の「時間」ではなく、**memory × timeの2次元形状**として捉える。Smallest Volume First（SVF）は、prompt長 `s_i` と予測output長 `o_i` から、decode中にKV cacheが描く台形状の面積をvolumeとして計算し、その小さいrequestから優先する。 citeturn177128view0

さらに、高精度なoutput-length regressionそのものがcostになる場合に備え、1-bit SVFを提案する。こちらはrequestを「短い / 長い」の2 classに分類するだけで、それぞれへ代表output長を割り当ててproxy volumeを作る。論文はBERT-base regressionを使うSVFと、BERT-tiny binary classifierを使う1-bit SVFの両方をvLLMへ組み込み、8×A100実機で評価する。 citeturn715976view0

理論面では、burst arrival下のSVFについて、offline optimumに対する最悪競争比（competitive ratio）を

`1 + 2/(1-α)`

と証明する。`α` は最大requestがGPU memoryの何割を占めるかで、高concurrencyな `α→0` ではboundが3へ近づく。既存解析の48というconstant boundより大幅にtightである。ただし**3倍という数字は実測speedupではなく、omniscient optimumから最悪どこまで離れ得るかという理論上限**である。 citeturn177128view0

## 背景: SJFが見落とす「KVを保持する時間」

request `i` のprompt長を `s_i`、decodeで生成するoutput token数を `o_i` とする。

decodeの最初のstepではKV footprintはおよそ `s_i + 1`、次は `s_i + 2`、最後は `s_i + o_i` になる。requestが完了するまでのKV占有量を全decode stepで足すと、

`v_i = s_i × o_i + (o_i^2 + o_i)/2`

となる。論文はこれをrequestの**volume**と呼ぶ。 citeturn177128view0

第一項 `s_i × o_i` は「最初から持っているprompt KVを、output生成中ずっと保持するcost」。第二項は「decodeに伴って新しく増えるKVを、その後のstepでも保持するcost」である。

### 同じoutput長でもpromptが長ければvolumeは大きい

例としてどちらも100 token生成するrequestを考える。

- A: prompt 100 token → `v ≈ 100×100 + 100×101/2 = 15,050`
- B: prompt 10,000 token → `v ≈ 10,000×100 + 5,050 = 1,005,050`

SJFはA/Bを「100-token job」として同順位にするが、Bは約67倍のmemory-time volumeを持つ。Bを先にactive batchへ入れると、decode中ずっと大きなprompt KVが居座るため、他requestのadmissionを妨げやすい。

逆にSVFはAを先に完了させ、使ったKVを早く解放する。これは単に短jobを先にするのではなく、**GPU memoryを早く循環させ、continuous batchingへ次requestを入れられる状態を作る**ことを狙う。

## 手法のあらまし

### 1. SVF: output長を予測し、volume順にwaiting queueへ並べる

request到着時にoutput length predictor `P` が予測output長を返す。実運用では複数pending requestをbatchでpredictし、scheduler critical pathを塞がないようにする。

prompt長 `s_i` はrequest到着時に既知なので、予測output長 `ô_i` から

`v̂_i = s_i × ô_i + (ô_i^2 + ô_i)/2`

を計算する。waiting queue `Q_wait` はこの予測volumeの小さい順にpriority queueへ入れる。

execution側はdecode stepが進んでactive requestが完了するたび、空いたKV capacityへ `Q_wait` の先頭からrequestを詰める。次のrequestがmemory capacityへ収まる限りadmitし、これ以上入らなければ現在のbatchを進める。 citeturn177128view0

つまりSVFはrequestを途中でpreemptして並べ替える方式ではない。論文の理論modelも**非プリエンプティブ（non-preemptive）**を前提とし、実行開始したrequestは完了までactive batchへ残る。工夫するのは「空きができた時、waiting queueから誰を次にadmitするか」である。

これはpreemptionに伴うKV eviction / reload / recomputation costを避け、既存vLLM continuous batchingのadmission policyだけを差し替えやすくするためである。 citeturn177128view0

### 2. volumeは「memory × time」の積分として解釈できる

SVFの優先度は単なる経験的scoreではない。時間軸を横、KV footprintを縦にとると、requestのdecode中のmemory曲線は右上がりになる。その下の面積がvolumeである。

GPU memory capacityを `M` とすると、時間 `t` までにsystemが消化できる総volumeにはおおまかに `t×M` という上限がある。これは「幅t、高さMの長方形に、requestのmemory-time形状を詰める」packing問題と見なせる。

LP緩和すると、限られた `t×M` のcapacityの中でできるだけ多くのrequestを早く完了させるには、volumeが小さいitemから先に詰める構造が現れる。論文はこれをSVFの理論的根拠としている。 citeturn177128view0

### 3. 1-bit SVF: output長を正確に当てず、short/longだけ予測する

full SVFはoutput token数の回帰予測を必要とする。予測modelが重い、またはlength regression自体が難しい場合の軽量版が1-bit SVFである。

binary classifierは各requestを

- `m=0`: short
- `m=1`: long

のどちらかへ分類する。classごとに代表output長 `O_m` を1つ持ち、

`v̂_i = s_i × O_m + (O_m^2 + O_m)/2`

でproxy volumeを計算する。 citeturn177128view0

ここで重要なのは、1 bitでもprompt長 `s_i` は正確に分かっていること。したがって同じ「long」classに入ったrequestでも、prompt 100とprompt 20Kではproxy volumeが大きく違い、memory pressureの差は残る。

論文の実機実装ではBERT-tiny classifierを使う。full SVFはBERT-base regressionを使うため、1-bit版は予測器をかなり軽くできる。 citeturn715976view0

### 4. 理論用の1-bit thresholdと実装上のclassifierを混同しない

burst-arrival worst-case theoremでは、最大model lengthを `T` とした数学上の設定として、classification threshold `θ=√T`、short proxy `O_0=T^(1/4)`、long proxy `O_1=T^(3/4)` を使い、競争比を `O(T)` に抑えられることを証明する。 citeturn177128view0

これは**production実装で必ずこの3値を使うべきというtuning recipeではない**。理論上「1 bitしかfuture情報がなくても、burst sizeが無限に増えた時に無制限悪化しない」というworst-case guaranteeを作るための構成である。

Poisson arrivalの理論ではまた別に、short/long classの条件付き期待output長をproxyとして使う。実機評価ではdatasetから学習したBERT-tiny classifierを用いる。したがってtheoremの定数、stochastic model、practical predictorは分けて読む必要がある。

## 理論保証は何を意味するか

### SVFのburst-arrival bound

全requestが同時到着するadversarial burstを考え、request `i` の最大瞬間memory `p_i=s_i+o_i` がGPU capacity `M` の `α` 倍以下、つまり

`p_i ≤ αM`

とする。

`α` はtuning parameterではなく、最大requestがGPUをどれだけ占めるworkloadかを表す。`α=1/2`なら最低2 request、`α=1/10`なら最低10 requestを同時収容できる程度のconcurrency headroomがある。

論文はSVFの総end-to-end latencyについて

`CR ≤ 1 + 2/(1-α)`

を示す。 citeturn177128view0

- `α=1/2` → CR ≤ **5.00**
- `α=1/4` → **3.67**
- `α=1/10` → **3.22**
- `α=1/100` → **3.02**
- `α→0` → **3**

高concurrencyではprior workのconstant 48から3近傍へtightenする。 citeturn177128view0

ただしcompetitive ratio 3とは「SVFがbaselineより3倍高速」という意味ではない。**どれだけ悪意あるburstでも、未来を全部知るoffline optimal scheduleの総latencyの3倍程度以内へ抑えられる**というworst-case upper boundである。実際のbenchmark gainは後述の実測値を見る必要がある。

### なぜvolume orderがproofにも効くのか

request `j` がwaitingしているのにadmitできない時、active batchのmemoryが十分埋まっているはずである。もしactive requestの最大memory合計が `(1-α)M` 以下なら、最大でも `αM` のrequest `j` を追加できるためである。

したがって「jが1 step待たされた」という事実そのものが、systemがその間ある程度大きなmemory massを処理していたcertificateになる。

さらにSVFではjより先にactiveなrequestはj以下のvolumeを持つ。このwaiting timeを先行requestのvolumeへchargeし、offline optimumのlower boundと同じvolume-prefix sumへ対応させることで、従来のlength bucket / time-window proofよりslackの少ないboundを得る。 citeturn177128view0

### Poisson arrivalでもsteady-state boundを与える

continuous trafficについてはarrivalをPoisson process、output lengthを離散幾何分布（Geometric distribution）として解析し、system utilization `ρ<1` の条件でSVFと1-bit SVFの期待競争比に上限を与える。

これは実際のLMSYSやLongBenchが厳密に幾何分布であることを証明するものではなく、**memory-time geometryがburstだけでなくstochastic steady stateでも解析可能**であることを示すmodeling resultと読むべきである。論文自身もこれらをexact observed speedupではなくtheoretical limitとして位置付ける。 citeturn177128view0

## 評価

### 実験条件

- **node:** 8× NVIDIA A100 80GB。
- **runtime:** vLLM continuous batching。
- **models:** Meta-Llama-3.1-8B-Instructは1 GPU、Llama-3.1-70B-Instructは8 GPU tensor parallelism。
- **precision:** FP16/BF16。
- **context window:** 65,536 token。
- **maximum generation:** 4,096 token/request。
- **workload:** LMSYS-ChatとLongBench、それぞれserving評価へ2,000 request。predictor training dataとは非重複。
- **arrival:** 全requestがt=0のburstと、QPS {2, 8, 16, 32, 64, 128} のPoisson arrival。
- **predictor:** SVF/SJFの回帰にBERT-base、1-bit SVFにBERT-tiny。
- **baselines:** FCFS、SJF、Oracle SJF、Oracle SVF。 citeturn715976view0

### 評価metricは「request latency」そのものではなくper-token latency

論文の表でAvg/P95 Latencyと呼んでいる値は、各requestのend-to-end latencyを**実際のoutput token数で割ったper-token latency（s/token）**である。output長が大きく違うLMSYSとLongBenchを比較する際、長いresponseが単純に大きなE2E値を持つbiasを減らすためである。 citeturn715976view0

したがって、たとえばLongBenchの70.0169 s/tokenを「TTFT 70秒」と読んではいけない。request completion timeでもTTFTでもなく、E2E latency / output tokensという論文固有metricである。

### burst: SVFは4条件すべてで平均latency最小

burst-arrival tableのnon-oracle結果は以下の通り。数値は `平均 / P95 per-token latency / throughput`。

**Llama-3.1-8B / LMSYS**
- FCFS: `2.4592 / 10.2364 / 3338.1 tok/s`
- SJF: `1.0087 / 4.8632 / 3229.9`
- 1-bit SVF: `1.5614 / 6.2247 / 3361.8`
- SVF: **`0.8901 / 3.7570 / 3239.4`**

**Llama-3.1-8B / LongBench**
- FCFS: `125.8883 / 393.1413 / 23.9`
- SJF: `106.1588 / 300.2542 / 25.9`
- 1-bit SVF: `72.5786 / 249.2350 / 28.7`
- SVF: **`70.0169 / 215.1756 / 28.2`**

**Llama-3.1-70B / LMSYS**
- FCFS: `3.0666 / 14.0373 / 2467.9`
- SJF: `1.8275 / 11.4283 / 2444.3`
- 1-bit SVF: `1.9850 / 6.8657 / 2492.1`
- SVF: **`1.6090 / 9.0097 / 2360.6`**

**Llama-3.1-70B / LongBench**
- FCFS: `226.2472 / 721.3823 / 10.9`
- SJF: `173.9461 / 442.1720 / 11.9`
- 1-bit SVF: `141.4835 / 524.7749 / 12.4`
- SVF: **`140.4193 / 420.2404 / 12.5`**

SVFは4条件すべてで平均latencyが最小。P95も多くの条件で強い。一方throughputは常にSVFが最大ではなく、8B/LMSYSでは1-bit SVF、70B/LMSYSでも1-bit SVFが上回る。 citeturn715976view0

この結果は「volume metricがすべてのmetricで一律勝つ」のではなく、**memory-constrainedなlatency objectiveで特に強い**ことを示す。

### LongBenchで1-bit SVFがSJFを上回る理由

LMSYSのようなinteractive workloadでは、output長の細かい順序が効きやすく、binary predictionしかない1-bit SVFはSJFより平均latencyが少し悪い場合がある。

しかしLongBenchではpromptが長くKV footprintの差が大きいため、SJFがoutput timeだけを正確に近似してもmemory pressureを無視する弱点が大きくなる。1-bit SVFはoutput長情報が粗くてもprompt長を含めたvolumeを使うため、SJFより平均latencyを改善する。論文はこの結果を「prediction precisionよりmetric dimensionalityが重要になるmemory-intensive regime」の例としている。 citeturn715976view0

### tail latencyで長requestを必ずstarveするわけではない

SJF系greedy schedulingには「long jobがshort jobに抜かれ続ける」というstarvation懸念がある。SVFもsmall volume firstなので同様に見える。

論文の解釈では、small-volume requestを早く終わらせることでKV memoryが早く解放され、その空きへ大requestをadmitできるため、global HOL blockingを減らせる。実測P95でもSVFは概ねFCFS/SJFより改善する。 citeturn715976view0

ただしこれは有限workloadでの実験結果であり、任意のarrival processで個々のlong requestに厳密なstarvation-free deadlineを保証するmechanismではない。公平性hard guaranteeが必要ならaging/priority capとの組合せが必要になる。

### Oracle結果はdeployable policyとそのまま比較できない

Oracle SJF/SVFはground-truth output lengthをpriorityに使うだけでなく、各requestのmaximum generation length自体もground truthへ設定する。通常runtimeが安全のため確保する余分なgeneration budgetがなくなるため、resource consumption条件も実用policyと変わる。 citeturn715976view0

このため論文はOracleのthroughputを報告していない。Oracleは「futureを完全に知り、allocationも実需要へぴったり合わせた理想下限」であって、SVFと公平なdeployable baselineではない。

### predictor overheadは小さいが、比率の分母も大きい

200 concurrent requestをまとめてpredictした測定では、BERT-base regressionのpredictor timeはLMSYS **1.1394秒**、LongBench **1.8283秒**。E2E全体に対する比率は最大 **0.06%**。BERT-tiny classifierは0.1043/0.7905秒で、比率は **0.01%以下**。 citeturn715976view0

これはhigh-concurrencyでbatched predictor inferenceを行ったamortized値である。single requestを毎回独立BERT inferenceするcostを0.06%と保証するものではない。特にlow-load serviceではpredictor batchingが効かず、相対overheadが変わり得る。

## 既存研究との差

FCFSはarrival orderだけ、SJFは主にoutput length/timeだけを見る。SVFは**prompt KVを保持する時間 + decodeで増えるKV**を積分したmemory-time costで並べる。

output-length prediction研究との関係では、predictor自体を新しく高精度化することが主題ではない。同じBERT-base predictorをSJFとSVFに与えてpriority metricだけ変え、「未来長を予測できてもtimeだけを見るmetricではmemory pressureを捉えきれない」と比較する。

Robust KV Cache Managementのようなcontrol-plane研究はclassごとのreservation量、GPU configuration、routingを数分単位で共同最適化する。SVFはもっとlocalな層で、**1 workerのwaiting queueから次に誰をactive batchへadmitするか**をonlineで決める。両者は競合せず、上位plannerがKV budgetを決め、その中でSVFがrequest orderingを行う構成が可能である。

Fluid-guided schedulingもmemory constraintを扱うが、fluid equilibriumやWAIT policyから安定性/queueingを制御する方向。SVFは各requestの2D geometric volumeを明示的なgreedy priorityへする点が異なる。

## 限界と適用境界

- **output-length情報が必要。** full SVFは回帰予測、1-bit SVFでもshort/long classifierが必要。predictor errorでvolume順序を誤るとgainが縮む。
- **従来型full KV growthを前提。** volume式はprompt KVを保持し、decode tokenごとにKVが線形増加するmodel。prefix sharing、KV pruning/compression、CPU/SSD offload、sliding-window attentionでは実memory-time footprintが変わるため式を拡張する必要がある。
- **非プリエンプティブadmission。** active requestの途中priority変更やKV swapは扱わない。すでにlong requestをadmitした後のoverloadを救うmechanismではない。
- **single-worker schedulingが中心。** 70Bは8 GPU TPだが、論理的には1 serving worker。複数replica/複数node間のload balancingはfuture work。 citeturn715976view0
- **理論modelは1 token=1 time unit、標準化memory unit。** model size、batch size、kernel efficiencyでtoken step時間が変わる実GPUの非線形性は抽象化している。
- **Poisson/幾何分布の理論はmodel assumption。** production arrival/outputがその分布に厳密一致する保証はない。
- **per-token latency中心。** user-facing TTFT、raw E2E completion time、TPOTを個別SLOとして最適化した結果ではない。
- **公平性のhard constraintなし。** 実験上P95は改善するが、long requestの最大待ち時間を保証するaging ruleはない。
- **predictor overheadはbatched測定。** low-concurrency時の個別predict costは別途profileすべき。

## 実装上の含意

既存vLLM schedulerへ取り入れる場合、最も簡単なのはrequest metadataへ `predicted_output_tokens` と `predicted_volume` を追加し、waiting queueをvolumeのmin-heapへする方法である。active batchへ空きKV blockができた時、volumeが小さいrequestからmemoryへ収まるだけadmitする。

すでにoutput-length predictorをSJFのために持っているsystemなら、新しいML modelを追加せずpriority式だけ

`output_length`

から

`prompt_length × output_length + output_length(output_length+1)/2`

へ変えられる。特にRAGやlong-context agentのようにprompt長のvarianceが大きいworkloadでは、この変更の価値が大きくなりやすい。

高精度predictorを置きたくない場合は、short/long classification + class代表長でもprompt長によるmemory差を残せる。まず1-bit版でA/B testし、memory-intensive workloadでSJFより差が出る場合だけfull regressionへ進むのが実装costとの釣り合いを取りやすい。

一方、prefix cacheやKV offloadを併用するsystemではraw prompt lengthをそのまま `s_i` に使うと誤る。実際にGPU HBMへresidentになるprefix/suffix量を使って**effective volume**を作る方がSVFの考え方に忠実である。
