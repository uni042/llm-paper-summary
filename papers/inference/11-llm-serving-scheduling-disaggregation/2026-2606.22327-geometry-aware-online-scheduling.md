# Geometry-考慮 オンライン スケジューリング for LLM サービング: From Theoretical 境界 to システム Practice

> **SVFはリクエストを「何トークン残っているか」だけでなく、「その間にどれだけKV メモリを占有し続けるか」まで面積として数え、小さいメモリ-時間 体積から実行することで、メモリ-境界なLLM サービングのヘッド-of-line ブロッキングを減らす。**

## 概要

LLM サービングで短いリクエストを先に処理する最短ジョブ優先（Shortest ジョブ 先; SJF）は強力な基本方針である。出力が50 トークンで終わるリクエストを2,000-トークン リクエストより先に処理すれば、短リクエストが長時間待つ先頭ジョブ待ち（ヘッド-of-Line ブロッキング; HOL ブロッキング）を減らせる。

しかしLLM デコードでは、通常のCPU ジョブ スケジューリングと違ってリクエストが実行時間だけでなくGPU メモリも継続的に占有する。プロンプトが8,000 トークンあるリクエストはデコード開始直後から約8,000-トークン分のKV キャッシュを持ち、1 トークン生成するたびに8,001、8,002……と増える。一方プロンプトが100 トークンなら、同じ出力長でもメモリ 占有量は小さい。

したがって出力長が同じ2 リクエストでも、GPU メモリ pressureへの寄与は大きく異なる。SJFは両方を同じ長さのジョブとして扱うが、メモリ-制約付き サービングでは大量のKVを長時間保持するリクエストを先にadmitすると、後続リクエストを連続 バッチへ入れられる空きKV 容量が減る。

本研究はリクエストを1次元の「時間」ではなく、**メモリ × 時間の2次元形状**として捉える。Smallest 体積 先（SVF）は、プロンプト長と予測出力長からデコード完了までに占有するKV メモリの積分値を体積として計算し、その小さいリクエストから優先する。

さらに、高精度出力-長さ 回帰を置きたくない場合に備え、1-bit SVFを提案する。こちらはリクエストを短い/長いの2 クラスに分類するだけで、それぞれに代表出力長を割り当てて代理 体積を作る。論文は全量 SVFにBERT-基準 回帰、1-bit SVFにBERT-小型 binary classifierを使い、vLLMへ組み込んで8×A100実機で評価する。

理論面では、burst 到着下のSVFについてオフライン optimumに対する最悪競争比（競合 ratio）を

`1 + 2/(1-α)`

と証明する。`α` は最大リクエストがGPU メモリの何割を占めるかで、高concurrencyな `α→0` では境界が3へ近づく。ここで3は実測高速化倍率ではなく、未来を完全に知るオフライン optimal scheduleに対してworst 事例で何倍以内に収まるかという理論上限である。

## 背景: SJFが見落とす「KVを保持する時間」

リクエスト `i` のプロンプト長を `s_i`、デコードで生成する出力 トークン数を `o_i` とする。

デコードの最初の段階ではKV 占有量はおよそ `s_i + 1`、次は `s_i + 2`、最後は `s_i + o_i` になる。リクエストが完了するまでのKV占有量を全デコード 段階で足すと、

`v_i = s_i × o_i + (o_i^2 + o_i)/2`

となる。論文はこれをリクエストの**体積**と呼ぶ。

第一項 `s_i × o_i` は「最初から持っているプロンプト KVを出力生成中ずっと保持するコスト」。第二項は「デコードで新しく増えたKVを、その後の段階でも保持するコスト」である。

### 同じ出力長でもプロンプトが長ければ体積は大きい

どちらも100 トークン生成するとする。

- A: プロンプト 100 トークン → `v ≈ 15,050`
- B: プロンプト 10,000 トークン → `v ≈ 1,005,050`

SJFでは両方とも100-トークン ジョブなので同程度の優先度になる。しかしBはAの約67倍のメモリ-時間 体積を持つ。Bを先に稼働中 バッチへ入れると、大きなプロンプト KVがデコード完了まで居座り、他リクエストのadmissionを妨げやすい。

SVFはAのようなsmall-体積 リクエストを先に完了させ、KVを早く解放する。これは単に短ジョブを先にするのではなく、**GPU メモリを早く循環させ、次リクエストを入れられる状態を作る**ことを狙う。

## 手法のあらまし

### 1. SVF: 予測出力長から体積を計算する

リクエスト到着時に出力 長さ 予測器 `P` が予測出力長を返す。プロンプト長 `s_i` はリクエスト到着時に既知なので、予測出力長 `ô_i` から

`v̂_i = s_i × ô_i + (ô_i^2 + ô_i)/2`

を計算する。

待機 キューは予測体積の小さい順にpriority キューへ入れる。デコード 段階が進んで稼働中 リクエストが完了しKV 容量が空くと、キュー先頭から「現在のメモリへ収まるリクエスト」をadmitする。

SVFは稼働中 リクエストを途中でpreemptして順序を変える方式ではない。実行開始したリクエストは完了まで稼働中 バッチに残る**非プリエンプティブ（非プリエンプティブ）**方式であり、工夫するのは「空きができた時、待機 キューから誰を次に入れるか」である。

この設計ならKV 追い出し/reload/再計算を新たに導入せず、vLLM 連続 batchingのadmission orderだけを変更できる。

### 2. 体積はメモリ-時間積分として解釈できる

時間軸を横、KV 占有量を縦にすると、リクエストのデコード中のメモリ曲線は右上がりになる。その下の面積が体積である。

GPU メモリ 容量を `M` とすると、時間 `t` までにシステムが処理できる総体積には概ね `t×M` の上限がある。これは「幅t、高さMの長方形へリクエストのメモリ-時間形状を詰める」packing問題として見られる。

この幾何学的解釈から、限られた容量内で多くのリクエストを早く完了させるにはsmall-体積 itemを優先する構造が現れる。SVFは経験的scoreというより、LLM リクエストの時空間占有を直接priorityへしたものといえる。

### 3. 1-bit SVF: 出力長を正確に当てなくてもよい

全量 SVFは出力 トークン数の回帰値が必要である。しかし予測 モデルが重い場合や長さ予測精度が低い場合、短い/長いのbinary classificationだけに落とした1-bit SVFを使える。

クラス `m` ごとに代表出力長 `O_m` を持ち、

`v̂_i = s_i × O_m + (O_m^2 + O_m)/2`

で代理 体積を作る。

重要なのは、1 bitしか未来情報がなくてもプロンプト長 `s_i` は正確に分かっていること。同じ長い クラスに入ったリクエストでもプロンプト 100とプロンプト 20Kでは体積が大きく違い、メモリ pressureの差をpriorityへ残せる。

実機実装では全量 SVFにBERT-基準 回帰、1-bit版にBERT-小型 classifierを使う。

### 4. 理論用1-bit 閾値と実装classifierは別物

burst-到着 worst-事例 theoremでは、最大モデル 長さを `T` としてclassification 閾値 `θ=√T`、短い 代理 `O_0=T^(1/4)`、長い 代理 `O_1=T^(3/4)` を使い、1 bitしか未来情報がない場合でもworst-事例 ratioを制御できることを示す。

これは本番で必ずこの閾値を使うべきというtuning recipeではない。理論上の競合 ratioを構成するための設定である。

Poisson 到着の理論では短い/長い クラスの条件付き期待出力長を代理に使い、実機評価では学習したBERT-小型 classifierを使う。theorem、stochastic モデル、practical 予測器は分けて読む必要がある。

## 理論保証

### SVFのburst-到着 競合 ratio

全リクエストが同時到着するburstを考え、リクエスト `i` の最大瞬間メモリ `p_i=s_i+o_i` がGPU 容量 `M` の `α` 倍以下、つまり

`p_i ≤ αM`

とする。

`α` はtuning parameterではなく、最大リクエストがGPU メモリをどれだけ占めるワークロードかを表す。`α=1/2`なら最低2 リクエスト、`α=1/10`なら最低10 リクエストを同時収容できる程度のheadroomがある。

論文はSVFの総エンドツーエンド 遅延について

`CR ≤ 1 + 2/(1-α)`

を示す。

- `α=1/2` → CR ≤ **5.00**
- `α=1/4` → **3.67**
- `α=1/10` → **3.22**
- `α=1/100` → **3.02**
- `α→0` → **3**

既存解析のconstant 48より大幅にtightである。ただし、これはSVFが比較対象より3倍速いという意味ではなく、任意のadversarial burstに対してオフライン optimumの総遅延の何倍以内かを示すworst-事例 upper 境界である。

### なぜ体積 orderがproofに効くのか

リクエスト `j` が待機していてメモリへadmitできない時、稼働中 バッチのメモリはかなり埋まっている必要がある。もし稼働中 リクエスト群が `(1-α)M` 以下しか使っていなければ、最大でも `αM` のリクエスト `j` を追加できるからである。

つまり「jが1 段階待たされた」という事実を、その間システムが処理したメモリ-時間 体積へchargeできる。さらにSVFではjより先に実行されるリクエストはj以下の体積を持つため、この待機 時間を体積-プレフィックス sumへ対応させ、オフライン optimumのlower 境界と比較できる。

連続 トラフィックについてはPoisson 到着と幾何分布（Geometric 分布）の出力 長さを仮定し、steady-状態での期待競合 ratioも解析する。これはLMSYSやLongBenchが厳密にその分布という意味ではなく、メモリ-時間 geometryをstochastic モデルでも解析できることを示す理論結果である。

## 評価

### 実験条件

- **ノード:** 8× NVIDIA A100 80GB。
- **ランタイム:** vLLM 連続 batching。
- **モデル:** Meta-Llama-3.1-8B-Instructは1 GPU、Llama-3.1-70B-Instructは8 GPU tensor 並列性。
- **文脈 窓:** 65,536 トークン。
- **maximum 生成:** 4,096 トークン/リクエスト。
- **ワークロード:** LMSYS-ChatとLongBench、それぞれ2,000 リクエスト。
- **到着:** 全リクエストがt=0のburstと、QPS {2, 8, 16, 32, 64, 128} のPoisson 到着。
- **予測器:** SVF/SJFにBERT-基準 回帰、1-bit SVFにBERT-小型。
- **比較対象:** FCFS、SJF、オラクル SJF、オラクル SVF。

### 「Avg/P95 遅延」は生 リクエスト 遅延ではない

論文の表でAvg/P95 遅延と呼ぶ値は、各リクエストのエンドツーエンド 遅延を**実際の出力 トークン数で割ったトークンごと 遅延（s/トークン）**である。LongBenchのように長いresponseが多いワークロードで、出力長そのものによるE2E差を小さくするための指標である。

したがってLongBenchで70 s/トークンと書かれていても、TTFT 70秒を意味しない。リクエスト 完了 時間そのものでもない。

### burst 到着の主結果

**Llama-3.1-8B / LMSYS**
- FCFS: `2.4592 / 10.2364 / 3338.1 tok/s`
- SJF: `1.0087 / 4.8632 / 3229.9`
- 1-bit SVF: `1.5614 / 6.2247 / 3361.8`
- SVF: **`0.8901 / 3.7570 / 3239.4`**

**Llama-3.1-8B / LongBench**
- FCFS: `125.8883 / 393.1413 / 23.9`
- SJF: `106.1588 / 300.2542 / 25.9`
- 1-bit SVF: `72.5786 / 249.2350 / 28.7`
- SVF: **`70.0169 / 215.1756 / 28.2`**

**Llama-3.1-70B / LMSYS**
- FCFS: `3.0666 / 14.0373 / 2467.9`
- SJF: `1.8275 / 11.4283 / 2444.3`
- 1-bit SVF: `1.9850 / 6.8657 / 2492.1`
- SVF: **`1.6090 / 9.0097 / 2360.6`**

**Llama-3.1-70B / LongBench**
- FCFS: `226.2472 / 721.3823 / 10.9`
- SJF: `173.9461 / 442.1720 / 11.9`
- 1-bit SVF: `141.4835 / 524.7749 / 12.4`
- SVF: **`140.4193 / 420.2404 / 12.5`**

各行は `平均per-token latency / P95 per-token latency / throughput`。

SVFは4条件すべてで平均遅延が最小。一方スループットは常にSVFが最大ではなく、8B/LMSYSや70B/LMSYSでは1-bit SVFの方が高い。この結果は、SVFが生 スループットを最大化するスケジューラというより、メモリ-制約付き 遅延を狙う方策であることを示す。

### LongBenchでは1-bitでもSJFを上回る

LMSYSのような対話型 ワークロードでは、出力長の細かな順序が効くため1-bit SVFはSJFより平均遅延が少し悪い場合がある。

しかしLongBenchではプロンプトが長くKV 占有量差が大きい。SJFが出力 時間をよく予測してもメモリ pressureを無視する弱点が大きくなり、出力長情報が粗い1-bit SVFでもプロンプト長を含めた体積を使うことでSJFを上回る。

これは「予測 精度を上げること」だけでなく、**スケジューラが見るdimensionを時間から時間×メモリへ増やすこと**にも価値があることを示す。

### オラクル 比較対象はdeployable 方策と条件が違う

オラクル SJF/SVFはground-truth 出力 長さをpriorityへ使うだけでなく、リクエストごとのmaximum 生成 長さもground truthへ設定する。通常ランタイムが安全のため余分に確保する生成 budgetが消えるため、資源 consumption条件そのものが実用方策と変わる。

そのためオラクルは「将来を完全に知る理想下限」として読むべきで、SVFとの公平なdeployable 比較対象ではない。論文もオラクル スループットを通常方式と同じ意味では報告しない。

### 予測器 オーバーヘッド

200 concurrent リクエストをまとめて予測した測定では、BERT-基準 回帰がLMSYS **1.1394秒**、LongBench **1.8283秒**で、E2E全体に対する比率は最大 **0.06%**。BERT-小型 classifierは **0.1043秒 / 0.7905秒**で、比率は **0.01%以下**。

ただしこれはhigh-concurrencyでbatched 予測器 推論を行ったamortized値である。low-負荷時に1 リクエストずつBERTを動かした場合も0.06%以下になるという保証ではない。

## 既存研究との差

FCFSは到着 orderだけ、SJFは主に出力 長さ/時間だけを見る。SVFは**プロンプト KVを保持する時間 + デコードで増えるKV**を積分したメモリ-時間 コストで並べる。

出力-長さ 予測研究との関係では、予測器自体を高精度化することが主題ではない。同じBERT-基準 予測器をSJFとSVFへ与えてpriority 指標だけを変えることで、「未来長が分かっても時間だけを見るとメモリ pressureを捉えきれない」と示す。

頑健 KV キャッシュ Managementのような制御-プレーン研究はクラスごとの予約量、GPU 構成、ルーティングを数分単位で共同最適化する。SVFはよりローカルな層で、**1 ワーカーの待機 キューから次に誰を稼働中 バッチへadmitするか**をオンラインで決める。両者は併用可能である。

## 限界と適用境界

- **出力-長さ情報が必要。** 全量 SVFは回帰予測、1-bit SVFでも短い/長い classifierが必要。
- **従来型全量 KV growthを前提。** プレフィックス 共有、KV 枝刈り/compression、CPU/SSD オフロード、sliding-窓 アテンションでは実メモリ-時間 占有量が変わるため、生 プロンプト長ではなくeffective 常駐 KV量を使う必要がある。
- **非プリエンプティブ。** 稼働中 リクエストの途中priority変更やKV swapは扱わない。
- **single logical ワーカー スケジューリングが中心。** 70Bは8 GPU TPだが、複数replica/複数ノード間のルーティングは別問題。
- **理論モデルは抽象化されている。** 1 トークン=1 時間 unitや標準化メモリ unitを置き、実GPUのバッチ/カーネル非線形性を完全には表さない。
- **トークンごと 遅延中心。** TTFT、生 E2E 完了 時間、TPOTを個別SLOとして直接最適化した結果ではない。
- **公平性厳格 guaranteeなし。** finite ワークロードでは末尾も改善するが、長い リクエストの最大待ち時間を保証するaging ruleはない。
- **予測器 オーバーヘッドはbatched測定。** low-concurrency時は別途プロファイルが必要。

## 実装上の含意

既存vLLM スケジューラへ取り入れる最小変更は、リクエスト metadataへ `predicted_output_tokens` と `predicted_volume` を追加し、待機 キューを体積のmin-heapへすること。稼働中 バッチへ空きKV blockができた時、小体積からメモリへ収まるだけadmitする。

すでにSJF用出力-長さ 予測器を持っているシステムなら、新しいML モデルを追加せずpriority式だけ

`output_length`

から

`prompt_length × output_length + output_length(output_length+1)/2`

へ変えられる。RAGや長い-文脈 エージェントのようにプロンプト長のvarianceが大きいワークロードほど、この変更が効きやすい。

プレフィックス キャッシュやKV オフロードを併用する場合は生 プロンプト 長さをそのまま `s_i` に使わず、実際にGPU HBMへ常駐になるプレフィックス/後置部量を使って**effective 体積**を作る方がSVFの考え方に沿う。
