# Geometry-Aware Online Scheduling for LLM Serving: From Theoretical Bound to System Practice

> **SVFはrequestを「何token残っているか」だけでなく、「その間にどれだけKV memoryを占有し続けるか」まで面積として数え、小さいmemory-time volumeから実行することで、memory-boundなLLM servingのhead-of-line blockingを減らす。**

## 概要

LLM servingで短いrequestを先に処理する最短ジョブ優先（Shortest Job First; SJF）は強力な基本方針である。出力が50 tokenで終わるrequestを2,000-token requestより先に処理すれば、短requestが長時間待つ先頭job待ち（Head-of-Line blocking; HOL blocking）を減らせる。

しかしLLM decodeでは、通常のCPU job schedulingと違ってrequestが実行時間だけでなくGPU memoryも継続的に占有する。promptが8,000 tokenあるrequestはdecode開始直後から約8,000-token分のKV cacheを持ち、1 token生成するたびに8,001、8,002……と増える。一方promptが100 tokenなら、同じoutput長でもmemory footprintは小さい。

したがってoutput長が同じ2 requestでも、GPU memory pressureへの寄与は大きく異なる。SJFは両方を同じ長さのjobとして扱うが、memory-constrained servingでは大量のKVを長時間保持するrequestを先にadmitすると、後続requestをcontinuous batchへ入れられる空きKV capacityが減る。

本研究はrequestを1次元の「時間」ではなく、**memory × timeの2次元形状**として捉える。Smallest Volume First（SVF）は、prompt長と予測output長からdecode完了までに占有するKV memoryの積分値をvolumeとして計算し、その小さいrequestから優先する。

さらに、高精度output-length regressionを置きたくない場合に備え、1-bit SVFを提案する。こちらはrequestをshort/longの2 classに分類するだけで、それぞれに代表output長を割り当ててproxy volumeを作る。論文はfull SVFにBERT-base regression、1-bit SVFにBERT-tiny binary classifierを使い、vLLMへ組み込んで8×A100実機で評価する。

理論面では、burst arrival下のSVFについてoffline optimumに対する最悪競争比（competitive ratio）を

`1 + 2/(1-α)`

と証明する。`α` は最大requestがGPU memoryの何割を占めるかで、高concurrencyな `α→0` ではboundが3へ近づく。ここで3は実測speedupではなく、未来を完全に知るoffline optimal scheduleに対してworst caseで何倍以内に収まるかという理論上限である。

## 背景: SJFが見落とす「KVを保持する時間」

request `i` のprompt長を `s_i`、decodeで生成するoutput token数を `o_i` とする。

decodeの最初のstepではKV footprintはおよそ `s_i + 1`、次は `s_i + 2`、最後は `s_i + o_i` になる。requestが完了するまでのKV占有量を全decode stepで足すと、

`v_i = s_i × o_i + (o_i^2 + o_i)/2`

となる。論文はこれをrequestの**volume**と呼ぶ。

第一項 `s_i × o_i` は「最初から持っているprompt KVをoutput生成中ずっと保持するcost」。第二項は「decodeで新しく増えたKVを、その後のstepでも保持するcost」である。

### 同じoutput長でもpromptが長ければvolumeは大きい

どちらも100 token生成するとする。

- A: prompt 100 token → `v ≈ 15,050`
- B: prompt 10,000 token → `v ≈ 1,005,050`

SJFでは両方とも100-token jobなので同程度の優先度になる。しかしBはAの約67倍のmemory-time volumeを持つ。Bを先にactive batchへ入れると、大きなprompt KVがdecode完了まで居座り、他requestのadmissionを妨げやすい。

SVFはAのようなsmall-volume requestを先に完了させ、KVを早く解放する。これは単に短jobを先にするのではなく、**GPU memoryを早く循環させ、次requestを入れられる状態を作る**ことを狙う。

## 手法のあらまし

### 1. SVF: 予測output長からvolumeを計算する

request到着時にoutput length predictor `P` が予測output長を返す。prompt長 `s_i` はrequest到着時に既知なので、予測output長 `ô_i` から

`v̂_i = s_i × ô_i + (ô_i^2 + ô_i)/2`

を計算する。

waiting queueは予測volumeの小さい順にpriority queueへ入れる。decode stepが進んでactive requestが完了しKV capacityが空くと、queue先頭から「現在のmemoryへ収まるrequest」をadmitする。

SVFはactive requestを途中でpreemptして順序を変える方式ではない。実行開始したrequestは完了までactive batchに残る**非プリエンプティブ（non-preemptive）**方式であり、工夫するのは「空きができた時、waiting queueから誰を次に入れるか」である。

この設計ならKV eviction/reload/recomputationを新たに導入せず、vLLM continuous batchingのadmission orderだけを変更できる。

### 2. volumeはmemory-time積分として解釈できる

時間軸を横、KV footprintを縦にすると、requestのdecode中のmemory曲線は右上がりになる。その下の面積がvolumeである。

GPU memory capacityを `M` とすると、時間 `t` までにsystemが処理できる総volumeには概ね `t×M` の上限がある。これは「幅t、高さMの長方形へrequestのmemory-time形状を詰める」packing問題として見られる。

この幾何学的解釈から、限られたcapacity内で多くのrequestを早く完了させるにはsmall-volume itemを優先する構造が現れる。SVFは経験的scoreというより、LLM requestの時空間占有を直接priorityへしたものといえる。

### 3. 1-bit SVF: output長を正確に当てなくてもよい

full SVFはoutput token数の回帰値が必要である。しかしprediction modelが重い場合や長さ予測精度が低い場合、short/longのbinary classificationだけに落とした1-bit SVFを使える。

class `m` ごとに代表output長 `O_m` を持ち、

`v̂_i = s_i × O_m + (O_m^2 + O_m)/2`

でproxy volumeを作る。

重要なのは、1 bitしか未来情報がなくてもprompt長 `s_i` は正確に分かっていること。同じlong classに入ったrequestでもprompt 100とprompt 20Kではvolumeが大きく違い、memory pressureの差をpriorityへ残せる。

実機実装ではfull SVFにBERT-base regression、1-bit版にBERT-tiny classifierを使う。

### 4. 理論用1-bit thresholdと実装classifierは別物

burst-arrival worst-case theoremでは、最大model lengthを `T` としてclassification threshold `θ=√T`、short proxy `O_0=T^(1/4)`、long proxy `O_1=T^(3/4)` を使い、1 bitしか未来情報がない場合でもworst-case ratioを制御できることを示す。

これはproductionで必ずこのthresholdを使うべきというtuning recipeではない。理論上のcompetitive ratioを構成するための設定である。

Poisson arrivalの理論ではshort/long classの条件付き期待output長をproxyに使い、実機評価では学習したBERT-tiny classifierを使う。theorem、stochastic model、practical predictorは分けて読む必要がある。

## 理論保証

### SVFのburst-arrival competitive ratio

全requestが同時到着するburstを考え、request `i` の最大瞬間memory `p_i=s_i+o_i` がGPU capacity `M` の `α` 倍以下、つまり

`p_i ≤ αM`

とする。

`α` はtuning parameterではなく、最大requestがGPU memoryをどれだけ占めるworkloadかを表す。`α=1/2`なら最低2 request、`α=1/10`なら最低10 requestを同時収容できる程度のheadroomがある。

論文はSVFの総end-to-end latencyについて

`CR ≤ 1 + 2/(1-α)`

を示す。

- `α=1/2` → CR ≤ **5.00**
- `α=1/4` → **3.67**
- `α=1/10` → **3.22**
- `α=1/100` → **3.02**
- `α→0` → **3**

既存解析のconstant 48より大幅にtightである。ただし、これはSVFがbaselineより3倍速いという意味ではなく、任意のadversarial burstに対してoffline optimumの総latencyの何倍以内かを示すworst-case upper boundである。

### なぜvolume orderがproofに効くのか

request `j` がwaitingしていてmemoryへadmitできない時、active batchのmemoryはかなり埋まっている必要がある。もしactive request群が `(1-α)M` 以下しか使っていなければ、最大でも `αM` のrequest `j` を追加できるからである。

つまり「jが1 step待たされた」という事実を、その間systemが処理したmemory-time volumeへchargeできる。さらにSVFではjより先に実行されるrequestはj以下のvolumeを持つため、このwaiting timeをvolume-prefix sumへ対応させ、offline optimumのlower boundと比較できる。

continuous trafficについてはPoisson arrivalと幾何分布（Geometric distribution）のoutput lengthを仮定し、steady-stateでの期待competitive ratioも解析する。これはLMSYSやLongBenchが厳密にその分布という意味ではなく、memory-time geometryをstochastic modelでも解析できることを示す理論結果である。

## 評価

### 実験条件

- **node:** 8× NVIDIA A100 80GB。
- **runtime:** vLLM continuous batching。
- **models:** Meta-Llama-3.1-8B-Instructは1 GPU、Llama-3.1-70B-Instructは8 GPU tensor parallelism。
- **context window:** 65,536 token。
- **maximum generation:** 4,096 token/request。
- **workload:** LMSYS-ChatとLongBench、それぞれ2,000 request。
- **arrival:** 全requestがt=0のburstと、QPS {2, 8, 16, 32, 64, 128} のPoisson arrival。
- **predictor:** SVF/SJFにBERT-base regression、1-bit SVFにBERT-tiny。
- **baselines:** FCFS、SJF、Oracle SJF、Oracle SVF。

### 「Avg/P95 Latency」はraw request latencyではない

論文の表でAvg/P95 Latencyと呼ぶ値は、各requestのend-to-end latencyを**実際のoutput token数で割ったper-token latency（s/token）**である。LongBenchのように長いresponseが多いworkloadで、output長そのものによるE2E差を小さくするための指標である。

したがってLongBenchで70 s/tokenと書かれていても、TTFT 70秒を意味しない。request completion timeそのものでもない。

### burst arrivalの主結果

**Llama-3.1-8B / LMSYS**
- FCFS: `2.4592 / 10.2364 / 3338.1 tok/s`
- SJF: `1.0087 / 4.8632 / 3229.9`
- 1-bit SVF: `1.5614 / 6.2247 / 3361.8`
- SVF: **`0.8901 / 3.7570 / 3239.4`**

**Llama-3.1-8B / LongBench**
- FCFS: `125.8883 / 393.1413 / 23.9`
- SJF: `106.1588 / 300.2542 / 25.9`
- 1-bit SVF: `72.5786 / 249.2350 / 28.7`
- SVF: **`70.0169 / 215.1756 / 28.2`**

**Llama-3.1-70B / LMSYS**
- FCFS: `3.0666 / 14.0373 / 2467.9`
- SJF: `1.8275 / 11.4283 / 2444.3`
- 1-bit SVF: `1.9850 / 6.8657 / 2492.1`
- SVF: **`1.6090 / 9.0097 / 2360.6`**

**Llama-3.1-70B / LongBench**
- FCFS: `226.2472 / 721.3823 / 10.9`
- SJF: `173.9461 / 442.1720 / 11.9`
- 1-bit SVF: `141.4835 / 524.7749 / 12.4`
- SVF: **`140.4193 / 420.2404 / 12.5`**

各行は `平均per-token latency / P95 per-token latency / throughput`。

SVFは4条件すべてで平均latencyが最小。一方throughputは常にSVFが最大ではなく、8B/LMSYSや70B/LMSYSでは1-bit SVFの方が高い。この結果は、SVFがraw throughputを最大化するschedulerというより、memory-constrained latencyを狙うpolicyであることを示す。

### LongBenchでは1-bitでもSJFを上回る

LMSYSのようなinteractive workloadでは、output長の細かな順序が効くため1-bit SVFはSJFより平均latencyが少し悪い場合がある。

しかしLongBenchではpromptが長くKV footprint差が大きい。SJFがoutput timeをよく予測してもmemory pressureを無視する弱点が大きくなり、output長情報が粗い1-bit SVFでもprompt長を含めたvolumeを使うことでSJFを上回る。

これは「prediction precisionを上げること」だけでなく、**schedulerが見るdimensionをtimeからtime×memoryへ増やすこと**にも価値があることを示す。

### Oracle baselineはdeployable policyと条件が違う

Oracle SJF/SVFはground-truth output lengthをpriorityへ使うだけでなく、requestごとのmaximum generation lengthもground truthへ設定する。通常runtimeが安全のため余分に確保するgeneration budgetが消えるため、resource consumption条件そのものが実用policyと変わる。

そのためOracleは「futureを完全に知る理想下限」として読むべきで、SVFとの公平なdeployable baselineではない。論文もOracle throughputを通常方式と同じ意味では報告しない。

### predictor overhead

200 concurrent requestをまとめて予測した測定では、BERT-base regressionがLMSYS **1.1394秒**、LongBench **1.8283秒**で、E2E全体に対する比率は最大 **0.06%**。BERT-tiny classifierは **0.1043秒 / 0.7905秒**で、比率は **0.01%以下**。

ただしこれはhigh-concurrencyでbatched predictor inferenceを行ったamortized値である。low-load時に1 requestずつBERTを動かした場合も0.06%以下になるという保証ではない。

## 既存研究との差

FCFSはarrival orderだけ、SJFは主にoutput length/timeだけを見る。SVFは**prompt KVを保持する時間 + decodeで増えるKV**を積分したmemory-time costで並べる。

output-length prediction研究との関係では、predictor自体を高精度化することが主題ではない。同じBERT-base predictorをSJFとSVFへ与えてpriority metricだけを変えることで、「未来長が分かってもtimeだけを見るとmemory pressureを捉えきれない」と示す。

Robust KV Cache Managementのようなcontrol-plane研究はclassごとのreservation量、GPU configuration、routingを数分単位で共同最適化する。SVFはよりlocalな層で、**1 workerのwaiting queueから次に誰をactive batchへadmitするか**をonlineで決める。両者は併用可能である。

## 限界と適用境界

- **output-length情報が必要。** full SVFは回帰予測、1-bit SVFでもshort/long classifierが必要。
- **従来型full KV growthを前提。** prefix sharing、KV pruning/compression、CPU/SSD offload、sliding-window attentionでは実memory-time footprintが変わるため、raw prompt長ではなくeffective resident KV量を使う必要がある。
- **非プリエンプティブ。** active requestの途中priority変更やKV swapは扱わない。
- **single logical worker schedulingが中心。** 70Bは8 GPU TPだが、複数replica/複数node間のroutingは別問題。
- **理論modelは抽象化されている。** 1 token=1 time unitや標準化memory unitを置き、実GPUのbatch/kernel非線形性を完全には表さない。
- **per-token latency中心。** TTFT、raw E2E completion time、TPOTを個別SLOとして直接最適化した結果ではない。
- **公平性hard guaranteeなし。** finite workloadではtailも改善するが、long requestの最大待ち時間を保証するaging ruleはない。
- **predictor overheadはbatched測定。** low-concurrency時は別途profileが必要。

## 実装上の含意

既存vLLM schedulerへ取り入れる最小変更は、request metadataへ `predicted_output_tokens` と `predicted_volume` を追加し、waiting queueをvolumeのmin-heapへすること。active batchへ空きKV blockができた時、小volumeからmemoryへ収まるだけadmitする。

すでにSJF用output-length predictorを持っているsystemなら、新しいML modelを追加せずpriority式だけ

`output_length`

から

`prompt_length × output_length + output_length(output_length+1)/2`

へ変えられる。RAGやlong-context agentのようにprompt長のvarianceが大きいworkloadほど、この変更が効きやすい。

prefix cacheやKV offloadを併用する場合はraw prompt lengthをそのまま `s_i` に使わず、実際にGPU HBMへresidentになるprefix/suffix量を使って**effective volume**を作る方がSVFの考え方に沿う。
