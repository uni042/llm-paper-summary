# Geometry-Aware Online Scheduling for LLM Serving: From Theoretical Bound to System Practice

> requestの実行時間だけでなく、生成中に時間とともに増えるKV cacheの占有量を含む「時空間volume」で優先順位を決め、memory pressure下の平均・tail latencyを下げるLLM serving scheduler。

## 問題設定

Shortest Job First（SJF）のような従来schedulerは、requestを主に「あとどれくらい時間がかかるか」で並べる。しかしLLM decodeでは生成tokenが増えるほどKV cacheも増え、requestは時間だけでなくGPU memoryも継続的に占有する。長さだけが近い2 requestでも、prompt長や既存KV量によってmemory pressureへの寄与が異なる。

この論文はLLM requestを、実行時間とKV cache footprintが作る2次元の幾何学的な占有領域として捉え、単なる残り時間ではなく**memoryをどれだけ長く占有するか**までschedulerへ入れる。

## 新規性

- Smallest Volume First（SVF）として、requestの残り処理とKV footprintから定義したvolumeを優先度に使う。
- exact output lengthが分かる場合だけでなく、予測長や短い/長いの1-bit情報しかない場合も扱う。
- 1-bit SVFでは小型predictorから得る粗い長さ分類だけでscheduler overheadを抑える。
- 理論上のcompetitive ratioを従来解析より大きく改善し、memory-constrained LLM scheduling固有の保証を与える。
- vLLMへplug-in schedulerとして実装し、理論だけでなくserving stack上でも評価する。

## 手法

### SVF
requestごとに、現在から完了までにKV cacheが時間方向へ占有する量を近似し、その小さいrequestを先に進める。SJFが「横幅＝時間」だけを見るのに対し、SVFは「時間 × memory」の面積に相当する量を見る。

これにより、短くても巨大なKVを抱えるrequestや、長くてもmemory footprintが小さいrequestを区別でき、GPU memory不足によるadmission待ちやpreemptionを減らしやすい。

### 1-bit SVF
output lengthを高精度に回帰する代わりに、requestを短い/長いの2群へ分類する。情報量を1 bitまで削っても、KV pressureを無視するFCFS/SJFより良い優先順位を作れることを狙う。

## 評価条件

Llama-3.1系modelと公開workloadを用い、vLLMへschedulerを組み込んだ評価と、論文・公開artifactのschedule simulationを行う。比較対象にはFCFSやSJF系heuristicが含まれる。

## 主な結果

- SVFは平均latencyとtail latencyの双方で従来heuristicを継続的に改善する。
- memory-intensiveな条件では、output lengthを知るSJFよりも、KV footprintを含むSVFが有利になるcaseを示す。
- 1-bit SVFも1 bitの長さ情報だけで競争力のあるthroughput / latencyを維持する。
- 理論面ではknown output length条件のworst-case competitive ratioを大幅にtightenしている。

## 既存研究との差

SJFやoutput-length prediction系研究は主にrequestの終了までの時間を推定して短いjobを先にする。SVFは**生成中に増え続けるKV cache占有量をschedulerのcostへ明示的に入れる**点が中心的な差である。

Robust KV Cache Managementのような研究がKV予約・routing・GPU構成を共同最適化するのに対し、本研究はonline request orderingそのものを幾何学的に定式化する。

## 限界

- output lengthまたはその粗い分類を事前に推定する必要がある。
- memory footprint modelが実runtimeのprefix sharing、KV compression、offload等とずれると優先順位の精度が落ちる。
- 公開artifactはschedule simulationも含み、すべての結果をproduction clusterそのものの測定とみなすべきではない。
- 理論保証と実環境のnetwork / multi-node overheadは別問題である。

## 一般的な実装上の含意

LLM schedulerではrequest長だけでなく、**そのrequestが完了までにどれだけのKV memoryをどれだけ長く保持するか**を見ると、memory-constrainedな高負荷時の優先順位を改善できる。output length predictorも絶対値を高精度に当てる必要はなく、粗い分類でもschedulerに価値を与えられる可能性がある。
