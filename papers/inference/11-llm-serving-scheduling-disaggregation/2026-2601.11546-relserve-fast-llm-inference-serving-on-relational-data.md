# RelServe：表形式LLM問い合わせの進捗とキャッシュを考慮する低遅延スケジューラ

## 概要

RelServeは、表の各行へ同じテンプレートのLLM処理を適用する問い合わせ（relQuery）を、オンラインで低遅延に実行するための推論基盤である。例えば表計算ソフトの多数の行へ感情分類や短い要約を一度に適用すると、1人の利用者の操作が多数のLLM要求へ展開される。利用者が待つのは個々の行の初回トークンではなく、**その問い合わせに含まれる全行の処理が完了するまでの時間**である。

従来の先着順では長い問い合わせが短い問い合わせを待たせる。静的な短い仕事優先方式は開始前の待ち時間を減らせても、処理が進んだ後の残作業や共有接頭辞キャッシュの利用状況を反映しない。また、事前入力を常に優先すると、最後の数行の復号が遅れ、問い合わせ全体の完了が長引く。RelServeは、残作業に応じて優先度を毎反復で更新するDPUと、事前入力・復号のどちらを先に実行すべきかを総遅延の見積もりで選ぶABAを組み合わせる。

原著は4基のA100 40GB GPUを持つサーバーで、OPT-13B、Qwen2.5-32B、Llama2-70B、4データセット、5種類の問い合わせテンプレートを評価する。各条件の最大負荷では、平均問い合わせ遅延がvLLM比2.3～3.1倍、静的優先度付きvLLM比1.4～2.2倍短いと報告する。これは**複数行をまとめた問い合わせの完了時間**であり、一般的なチャットの1トークン当たり生成速度が3.1倍になるという意味ではない。

## 問題設定：待機・中心処理・末尾処理の三つの遅延

relQuery Rは、表Tの各行s_iへ同じタスクテンプレートζを埋め込んだ要求集合 `{ζ[s_i]}` である。たとえば映画レビューと作品説明を含む表の各行に「このレビューから評価を1～5で予測」と指示する。問い合わせRの処理は、各行の事前入力を行うバッチと、その後のトークン生成を行う復号バッチの列に分解される。最後の行の要求が終了するまでRは完了しない。

原著はこの完了時間を三つに分ける。待機時間はRの到着から最初の事前入力バッチが始まるまで、中心処理時間は最初の事前入力からRの最後の事前入力が終わるまで、末尾処理時間は最後の事前入力からRの最後の復号が終わるまでである。個々の要求の初回トークン時間だけを見ると、最後の数行の復号が他の問い合わせの事前入力に割り込まれている問題を見落とす。

動機付けのOPT-13B・Amazonデータの分析では、先に走っているrelQueryの残り処理量は新しいrelQueryが到着した時点で平均34%になっていた。また共有接頭辞キャッシュの平均命中率は38%で、入力トークン数をそのまま処理時間に換算すると、実際に計算すべきトークンを過大評価する。さらに中心処理と末尾処理の時間比は54対46であるのに、末尾処理のトークン数は全体の8%しかない。これは末尾の計算そのものより、事前入力を優先し続けることによる待ちが支配的になり得ることを示す。

## 手法

### 全体処理：問い合わせ単位の状態を毎反復で更新

RelServeはvLLMを拡張し、各要求にどのrelQueryへ属するかを示すrel_idと優先度を付ける。問い合わせが到着すると各行の要求を待機キューへ置く。1反復ごとに、動的優先度更新器（Dynamic Priority Updater; DPU）が待機・実行中の問い合わせの残り時間を見積もり、優先度を更新する。次に適応型バッチ配置器（Adaptive Batch Arranger; ABA）が候補の事前入力バッチと復号バッチを比較し、平均完了遅延が小さくなる方を選ぶ。

選んだバッチをGPUで実行すると、事前入力済み要求は実行キューへ移り、終了トークンに達した復号要求は削除される。全行が終了した問い合わせを利用者へ返す。DPUとABAは次反復で更新されたキューとKVキャッシュ状態を再び使うため、開始時に固定した順序に縛られない。追加のスケジューリング計算は必要だが、論文はその費用を削減する近似も設ける。

### 1. DPU：残作業の時間を問い合わせ優先度へ変換

DPUの中核は優先度推定モデル（Priority Estimation Model; PEM）である。未完了の問い合わせR_tについて、既に完了した行を除き、現在の接頭辞キャッシュで計算不要になったトークンを考慮する。次に、事前入力の最大バッチトークン数、復号の最大要求数、GPU上で保持可能なトークン容量を守りながら、残る要求を事前入力バッチ列Pと復号バッチ列Dへ分解する。

PEMは、各バッチのトークン数・要求数を入力する線形実行時間予測器 `L_prefill` と `L_decode` を使い、`PEM(R_t)=Σ_{p∈P}L_prefill(p)+Σ_{d∈D}L_decode(d)` として残り所要時間を求める。この値が小さい問い合わせを先に処理する。個々の要求の優先度も所属する問い合わせの値を共有するため、1行だけを短く処理しても、同じ問い合わせの残り多数行が遅れれば完了時間は改善しないという特性に対応できる。

静的な優先度は入力長と予想出力長を一度だけ足し合わせるため、実行が進んでも値が変わらない。DPUは実行中の行が終わるたびに残り仕事を減らし、接頭辞キャッシュが新たに作られたときは再利用できる部分を減算する。これにより、ほぼ完了した問い合わせが新しい長い問い合わせに追い越される状況を抑える。ただし、予測器の線形近似が大きく外れる場合には優先順位を誤る。

### 2. DPUの計算費用を抑える二つの近似

正確な未キャッシュトークン数を毎反復で求めるには、待機中の多数の要求を巨大な接頭辞キャッシュへ照合する必要がある。DPUは同じrelQueryの行が同じテンプレートとデータ源を共有する点を利用し、一部の行だけを無作為抽出してキャッシュ未命中率を推定する。抽出集合R_sに対して `miss_ratio=Σuncached(r)/Σtokens(r)` を計算し、他の行は `estimated_uncached(r)=tokens(r)×miss_ratio` と近似する。

この近似は、同じ問い合わせ内でキャッシュ命中率がある程度似ている場合に有効である。行ごとの接頭辞が大きく異なる場合やキャッシュの状態が急変した場合には推定誤差が増える。原著はサンプル数を調整可能なパラメータとし、すべての行の接頭辞を厳密照合する費用を避ける。

もう一つの近似は、問い合わせの全要求が待機キューに留まり、実行進捗が変わっていない場合に、前回の優先度を再利用することである。実行中の別の問い合わせによってキャッシュが変化する可能性はあるが、別テンプレート・別データ源なら待機中問い合わせへの影響は小さいという仮定を置く。再利用が可能なときはPEMを毎回走らせず、スケジューラ自身が推論を妨げることを防ぐ。

### 3. ABA：事前入力と復号の遅延差を比較する

事前入力を先に行うと、新しい問い合わせの待機時間が減り、既に走っている問い合わせと後続の復号をまとめて実行できるためGPUの利用効率が上がる。一方、復号を先に行うと現在の問い合わせを早く完了できるが、新しい問い合わせが待つ。どちらがよいかは、待機中・実行中の問い合わせ数、候補バッチの処理時間、出力長に依存する。常に事前入力優先、常に復号優先のどちらも全条件で最適ではない。

ABAはその反復で実行可能な候補事前入力バッチp_candと復号バッチd_candを作り、事前入力を先にする場合の全問い合わせ完了遅延の差Δを推定する。実行中の問い合わせに対しては、p_candの実行で復号が止まる時間と、後続復号バッチへ要求が追加されることで増える時間を足す。待機中の問い合わせに対しては、事前入力が早く終わり後続復号を共通化できることで減る時間を見積もる。

原著の式(15)～(17)は、実行中問い合わせ数、p_candの予測実行時間、追加要求数、出力長の重なり、復号の線形予測器の傾き・切片を使って `Δ=Δ_running+Δ_waiting` を計算する。Δ<0なら事前入力を先に、そうでなければ復号を先にする。この判断は各反復で更新されるので、現在の負荷と残り処理量に応じて切り替わる。

ABAの予測は「候補バッチの選択が全問い合わせの総遅延をどれだけ変えるか」という近似であり、未来の全到着要求を見通した厳密最適化ではない。出力長の見積もりが外れたり、GPUの実行時間が線形予測から大きく外れたりすると、選んだ順序が最良でなくなる可能性がある。それでも事前入力・復号の一律な優先順位より柔軟に処理できる。

### 4. 長い問い合わせの飢餓防止

残り仕事が短い問い合わせを常に優先すると、行数が多い問い合わせが後回しになり続ける。RelServeは問い合わせの待ち時間を元の行数で割った単位待ち時間を公平性指標として使い、しきい値を超えた問い合わせを救済する。行数が多い問い合わせと少ない問い合わせを、単純な絶対待機時間だけで比較しないための規則である。

しきい値を厳しくすると最大待ち時間は改善し得るが、平均完了遅延が悪化する交換条件がある。過負荷で多くの問い合わせが飢餓防止に引っ掛かる場合は、スケジューラの工夫だけでは不足し、GPU容量そのものを増やす必要がある。原著はこの限界を明記する。

## 評価

### 装置・モデル・データセット

実装はvLLMのスケジューラを置き換える形で、A100 40GBを4基搭載しNVLinkで接続したサーバーを用いる。OPT-13Bは1基、Qwen2.5-32Bは2基、Llama2-70Bは4基を使用し、すべてFP16で評価する。データはAmazon商品、Rotten映画レビュー、Beerレビュー、PDMX音楽メタデータの4種類で、各データセットの先頭1万行を利用する。フィルタ、分類、数値評価、要約、自由記述質問の5種類のテンプレートを作り、最大出力長を5～100トークンへ設定する。

各評価設定では100個のrelQueryを無作為に作り、1問い合わせあたり1～100行の要求を含める。合計で約5,000個のLLM要求を持つ負荷を、到着率を変えたポアソン過程で流す。各設定は3回実行して平均値を報告する。比較対象は標準vLLM、分割事前入力のSarathi、静的優先度付きvLLM-SPである。vLLM-SPは同じコード基盤でDPUとABAを無効にした比較方式なので、スケジューリング部分の追加利得を見やすい。

| 指標・条件 | 結果 | 注意点 |
|---|---|---|
| 最大負荷条件、vLLM比 | 平均relQuery遅延2.3～3.1倍短縮 | 比較するのは問い合わせ全行の完了時間 |
| 最大負荷条件、静的優先度付きvLLM-SP比 | 1.4～2.2倍短縮 | DPU/ABAの追加利得 |
| Llama2-70B、4データセット平均 | vLLM比2.8倍、vLLM-SP比1.9倍 | 大規模モデルほど待ち行列の影響が大きい |
| Amazon/Rotten/Beer/PDMX、vLLM比 | 2.5/2.6/2.8/2.6倍 | 3モデル平均の報告 |
| Amazon/Rotten/Beer/PDMX、vLLM-SP比 | 1.6/1.8/1.5/1.6倍 | データセットごとに利得が異なる |
| DPU+ABAのスケジューラ費用 | 全体完了時間の1%未満 | OPT・Beerの測定例 |

### どの機構が効いたか

図10の構成要素除去では、常に事前入力を先にする方式と、常に復号を先にする方式を比較する。PDMXとLlamaの組合せでは長い復号が残りやすく、復号優先が事前入力優先より有利な場合がある。一方、OPTとAmazonのように出力が短い条件では、事前入力を先にして復号をまとめる方が有利になる。ABAは両候補の総遅延差を予測するため、負荷・モデル・出力長に応じて選択を変えられる。

図11では、静的優先度付きvLLM-SPと比べ、RelServeの待機時間は近い一方、中心処理時間と末尾処理時間が短い。これは待機段階だけの優先順位では不十分で、DPUによる残り仕事の更新とABAによる復号の割り込み制御が必要であるという仮説と整合する。表6ではDPUとABAの累積計算時間を示し、OPT・Beerの各到着率条件で両者の合計が完了時間の1%未満だったと報告する。ただし他のモデル・GPUでの費用上限ではない。

図12では飢餓防止しきい値を小さくすると最大遅延が下がる代わりに平均遅延が上がることを示す。したがってRelServeは、平均完了時間の最小化と極端に遅い問い合わせの救済を同時に無償で達成するものではない。低負荷では問い合わせ間の競合が少ないため、標準vLLMとの差も小さくなる。

### 分離型推論との比較上の制約

原著は4基のA100を用い、事前入力と復号を別GPUへ分ける構成も一部比較する。Amazon・1 relQuery/秒の条件で、4基をまとめるvLLMが18.64秒、1基事前入力＋3基復号が35.91秒、2＋2が55.57秒、3＋1が141.01秒と報告する。この比較では分離型のGPU割当が負荷と合わず、稼働率が低くなる可能性がある。これを根拠に一般の分離型推論が常に不利と結論付けることはできない。RelServeの主評価は同居型の推論に限定している。

## 限界・再現性・適用判断

本研究の主要な前提は、複数の行が一つの問い合わせを構成し、利用者は全行の完了を待つという点である。通常のチャットサービスでは要求が独立しており、1人の利用者の100行分の処理を同時に完了させる必要はない。従って、relQuery単位の短い仕事優先と動的優先度を一般の対話推論へそのまま移しても同じ倍率になるとは限らない。

接頭辞キャッシュの命中率が同じ問い合わせ内で類似するという近似は、テンプレートと行データの共通性が弱い場合に外れる。PEMは出力長を上限として扱うため、実際の終了トークンが早い場合や生成長の分散が大きい場合には推定を更新する必要がある。ABAの時間予測は線形近似であり、GPUメモリ逼迫、極端なバッチサイズ、モデル構造差のある環境で精度が低下する可能性がある。

評価は単一サーバー4基のA100で、要求到着は合成ポアソン過程、データセットは4種類、各設定100問い合わせである。大規模分散クラスタでの全体ルーティング、障害、長時間運用時の負荷変動、異なるユーザー優先度のSLOは直接評価していない。モデルの出力品質は変更しない設計だが、バッチ順序や浮動小数点演算の非決定性を含めた厳密な出力一致率の測定が中心ではない。

## 既存研究との違い

vLLMはページ化されたKV管理と反復バッチ処理を提供するが、通常は要求到着順に処理する。Sarathiは事前入力を分割して復号と混ぜ、GPUの稼働効率を改善する。静的な短い仕事優先は待機時間を減らすが、完了済み行と接頭辞キャッシュの変化を反映しない。RelServeは、問い合わせ全体の残作業を毎反復で推定し、事前入力・復号の順序を全問い合わせの予測完了時間で切り替える点で異なる。

表計算・データベースのオンラインAI関数のように、同じテンプレートを多数行へ適用する環境では、DPUのキャッシュ未命中率のサンプリングとABAの総遅延比較が参考になる。通常のLLM推論基盤へ導入する際には、問い合わせのグループ化単位、出力長予測、キャッシュ共有度、平均と最大の遅延の交換条件を再評価する必要がある。
