# Strata: Hierarchical Context Caching for Long Context Language Model Serving

## 概要
長文脈サービングでは、再利用可能な接頭辞のKVキャッシュをGPU高帯域メモリ（High-Bandwidth Memory; HBM）だけに置き続けることが難しい。Strataが示す例ではLlama-8BのKVを40 GBのHBMへ置く場合、約30万トークンで容量を使い切る。このためCPU DRAMやSSDへKVを退避する階層キャッシュが必要になるが、再利用時には大量のKVをGPUへ戻さなければならない。既存のページ化注意（PagedAttention）は計算時のメモリ断片化を抑える一方、1〜32トークン程度の小ページを非連続に配置するため、階層間転送では小さなDMA要求が多数発生する。

Strataはこの問題を「容量」だけでなく「転送粒度とスケジューリング」の問題として扱う。GPU支援I/Oで小ページを高並列に運び、GPU側の計算向け配置とCPU/ストレージ側の転送向け配置を分離する。さらにキャッシュ認識スケジューラがPCIe等の帯域を計算資源と同様に明示的に扱い、KVロードを隠せる量のプリフィル計算を同じバッチへ組み込む。SGLang上の実装は長文脈ベンチマークでvLLM+LMCacheに対する初回トークン時間（Time To First Token; TTFT）を最大5倍、TensorRT-LLM比で最大3.75倍改善した。

## 問題設定
従来の階層KVキャッシュでは、GPUへ戻すKVを`cudaMemcpyAsync`等でページごとに転送する。高帯域リンクを飽和させるには通常メガバイト級の転送サイズが有利だが、LLMサービングはキャッシュ命中率とメモリ利用率のため小ページを好む。論文の測定では8192トークン分のKVをページサイズ32でCPUからGPUへ戻した場合、PCIe 5.0の理論帯域の約22%しか利用できず、Grace-Hopperのようなより高速なNVLink環境では利用率が約5%まで落ちる。

単純にページを大きくすると転送効率は上がるが、接頭辞一致の粒度が粗くなる。Mistral-24BとShareGPTを使った測定ではページサイズを最大1024へ増やすと、平均TTFTが最大2倍、P90 TTFTが最大2.9倍へ悪化した。したがって「大ページでI/Oを速くする」だけではキャッシュ再利用率を犠牲にする。

もう一つの問題は、既存スケジューラがKVロードをプリフィル計算で隠せると仮定している点である。長い再利用文脈に対して新規入力が短い要求では、ロード時間が計算時間を超える。SGLangベースのプロファイルではKV転送待ちがプリフィル時間の74%に達し、スループットが最大4分の1まで落ちる例がある。StrataはCPU-GPU帯域を第一級のスケジューリング資源として扱う。

## 手法

### GPU支援I/O
Strataのキャッシュ制御器（Cache Controller）は、小ページごとにCPUからDMA要求を発行する代わりにCUDAカーネルを起動する。多数のGPUスレッドがCPUの登録済み固定メモリまたはGPUメモリから小さな断片をレジスタへ読み、宛先へストリームする。転送単位は128バイト程度まで細かくできるため、キャッシュページを大きくせずに高い並列度を確保できる。

GPUをI/Oへ使うと計算カーネルとの競合が起きるため、Strataは少数の大きなCUDAブロックへI/O処理を閉じ込める。H200での測定では1024スレッドのブロックを2個使う設定で約50 GB/sを達成し、同時実行するプリフィルへの性能影響を5%未満、デコードへの影響を10%未満に抑えた。CPU→GPUロードには2ブロック、非クリティカルなGPU→CPU退避には1ブロックを既定値とする。

### メモリ階層ごとの配置分離
計算カーネルは層ごとにKVへアクセスするためGPUでは層優先配置が都合よいが、CPUやSSDとの転送では同一ページのデータを連続させた方が大きなI/Oを作りやすい。StrataはGPU支援I/Oカーネル内で軽量なレイアウト変換を行い、GPUと下位階層で同一の物理配置を強制しない。これにより計算側のページ粒度を維持しつつ、下位階層では転送効率を優先できる。

SSD等からの復帰では、待ち行列に要求が入った時点でキャッシュ命中を検出するとCPUメモリへ先読みし、キュー待ち時間とストレージI/Oを重ねる。実際に要求がディスパッチされた時点では利用可能になった範囲を使い、未完了の先読みは停止するため、遅いストレージをクリティカルパスへ無条件に持ち込まない。

### キャッシュ認識スケジューリング
Strata SchedulerはSGLangのRadixTreeを拡張したHiRadixTreeを参照し、各ページがどの階層に存在するかを追跡する。待ち要求ごとに新規プリフィル計算量とロードすべきKV量を見積もり、プリフィル計算時間でI/Oを隠せるようバッチを組む。ロードが計算を上回る場合には、PCIeを使うKVロードとHBM帯域中心のデコードを重ね、GPUの遊休時間を別作業で埋める。

同じ接頭辞への複数要求が最初のキャッシュミス解決中に到着する「遅延ヒット（delay hit）」も扱う。非同期スケジューラでは次バッチを先に構築するため、同じ接頭辞を重複プリフィルしやすい。HiRadixTree上の状態を使って進行中ロード・生成を認識し、長文脈ほど高価になる重複計算を避ける。

## 評価
|項目|条件|
|---|---|
|実装基盤|SGLang|
|GPU例|H200、Grace-Hopperを含む複数環境|
|モデル例|Qwen2.5-14B、Mistral-24B、Llama系|
|ワークロード|LooGLE、ShareGPT等の長文脈/一般サービング|
|比較|vLLM+LMCache、TensorRT-LLM、SGLang系階層キャッシュ|
|主指標|TTFT、スループット、I/O帯域利用率、短文脈への干渉|

|結果|値|意味|
|---|---:|---|
|vLLM+LMCache比TTFT|最大5倍改善|階層キャッシュ復帰のI/O律速を削減|
|TensorRT-LLM比|最大3.75倍高速|高度に最適化された基準に対しても長文脈で優位|
|GPU支援I/O|約50 GB/s|2 CUDAブロックでも高帯域を確保|
|既存小ページ転送|PCIe 5.0理論値の約22%|断片I/Oが実効帯域を制限|
|大ページ化の副作用|P90 TTFT最大2.9倍悪化|単純なページ拡大ではキャッシュ命中を損なう|

主要結果は長文脈でキャッシュロード量が大きい条件に集中する。短文脈では階層I/Oの利得が小さいため、Strataは余計な処理を増やさず既存高性能系と同等性能を維持することを設計目標にしている。

## 既存研究との差
LMCacheやCachedAttentionなどはCPU/SSDへKVを退避し、層ごとの計算とロードを重ねる。Strataは「計算が十分長ければロードを隠せる」という前提を外し、リンク帯域自体をスケジューラの制約へ入れる。またPagedAttentionの小ページを維持したままGPUスレッドでI/Oを集約するため、転送効率のためにページ粒度を粗くする必要がない。

## 限界
効果が最大になるのは、再利用する長いKVが下位階層にあり、ロード時間がプリフィル計算と同程度以上になるワークロードである。GPU支援I/OはSM・レジスタ等を消費するため、ブロック割当を増やしすぎると計算と競合する。ストレージ先読みもキュー待ち時間が短い場合は十分隠せない。論文は本番導入を報告するが、全モデル・全相互接続・全要求分布で同じ倍率を保証するものではない。
