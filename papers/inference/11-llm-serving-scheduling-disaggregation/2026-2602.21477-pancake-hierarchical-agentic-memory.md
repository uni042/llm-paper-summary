# Pancake: Hierarchical Memory System for Multi-Agent LLM Serving

> 動的なエージェント記憶向けに多段インデックスキャッシュ、複数エージェント協調インデックス、CPU-GPU協調を統合し、既存メモリ基盤比で端から端まで平均4.29倍超の性能向上を示す。

- **実装**: Python APIとしてsearch/insert/update/deleteと複数メモリ scopeを実装し、既存Faiss IVFインデックスを読み込める。検索、更新、キャッシュ、GPU処理を独立スレッド化し、隣接操作のbatching、共有クラスタのlock、非同期GPU転送・挿入バッファを備える。論文本文およびarXivページからPancake本体の公開コードURLは確認できない。
## 概要
LLMエージェントの外部メモリは、記憶規模の拡大、検索と細粒度更新の高頻度な交互実行、複数エージェントによる共有・局所メモリの併存により、近似最近傍探索（ANN）が推論全体の主要ボトルネックになり得る。Pancakeは、単一エージェント向けの多段インデックスキャッシュ、複数エージェントの粗粒度インデックスをつなぐハイブリッドグラフとエージェント別アクセスプロファイル、CPU-GPU協調キャッシュを統合した階層型エージェントメモリ基盤である。8M件のMS MARCO知識ベースと複数の実エージェントデータセットを使ったCPU-GPUサーバ評価で、既存メモリライブラリに対し単一エージェントの端から端までの性能を1.12〜26.18倍、平均4.29倍超改善し、メモリ処理時間を平均3.2%まで抑える。

Pancakeはエージェント固有の時間的・意味的局所性を索引の保守方針そのものへ組み込み、単一エージェント、複数エージェント、CPU-GPUの三階層を一体設計する。単一エージェントではアクセス系列を有限状態機械（FSM）で継続的に学習し、関連クラスタを多段キャッシュへ昇格させる。複数エージェントでは各粗粒度索引を接続点で結んだハイブリッドグラフにより、一度のグラフ探索で対象範囲を横断する。共有クラスタにはエージェント別アクセスプロファイルを保持し、同じ物理データでも利用者ごとの検索傾向を反映する。GPU側は索引全体を固定常駐させず、参照頻度の高いクラスタだけをキャッシュし、更新用バッファと非同期転送で頻繁な挿入を吸収する。

代表結果として、単一agent エンドツーエンド スループットは複数model・dataset・4 access patternsでA-Mem / MemGPT / LlamaIndex / LangMemに対して1.12×〜26.18×、平均4.29×超。外部メモリ処理が大きい条件ほど索引最適化がLLM serving全体へ直結する。
## 問題設定
LLMエージェントは外部メモリから関連情報を検索し、生成途中の結果や履歴を継続的に挿入・更新する。既存のエージェントメモリ実装は機能性を優先し、大規模化するとメモリ処理が推論時間の82%以上を占め得る。一方、一般的なベクトルデータベースは静的索引または周期的・一括的な更新を想定するため、検索と小規模更新が細かく交互に発生するエージェント負荷では、新規ベクトルが高次元空間の複数クラスタへ散らばり、検索量と再現率が悪化する。複数エージェントでは個別索引を順番にたどる粗粒度探索コスト、共有メモリで異なるアクセス傾向が混ざる問題も加わる。さらにGPUはLLM推論と容量を奪い合うため、近似最近傍探索（ANN）索引全体をGPUへ常駐させる前提も現実的ではない。したがって、動的更新、複数エージェント共有、検索局所性、CPU-GPU容量差を同時に扱う外部メモリ基盤が必要になる。
## 新規性
Pancakeはエージェント固有の時間的・意味的局所性を索引の保守方針そのものへ組み込み、単一エージェント、複数エージェント、CPU-GPUの三階層を一体設計する。単一エージェントではアクセス系列を有限状態機械（FSM）で継続的に学習し、関連クラスタを多段キャッシュへ昇格させる。複数エージェントでは各粗粒度索引を接続点で結んだハイブリッドグラフにより、一度のグラフ探索で対象範囲を横断する。共有クラスタにはエージェント別アクセスプロファイルを保持し、同じ物理データでも利用者ごとの検索傾向を反映する。GPU側は索引全体を固定常駐させず、参照頻度の高いクラスタだけをキャッシュし、更新用バッファと非同期転送で頻繁な挿入を吸収する。
## 手法
### 手法のあらまし
基底索引にはIVF系のクラスタ構造を利用するが、Pancakeは静的なクラスタ配置をそのまま使うのではなく、検索・挿入・更新履歴からエージェントごとの局所性を継続的に学習して探索順序と配置を変える。単一エージェント経路では、有限状態機械が直前に利用したメモリ領域と次に参照されたクラスタの遷移を記録し、繰り返し共起するクラスタや最近頻繁に利用されたクラスタを上位の多段キャッシュへ昇格する。問い合わせ時はこの上位層から優先して探索し、十分な候補が集まれば下位クラスタの走査を省略することで検索量を減らす。複数エージェント経路では、各エージェントまたは共有範囲ごとに持つ粗粒度索引を独立に全走査せず、代表点を接続点として結んだハイブリッドグラフを構成し、一度のグラフ探索で関連する索引群へ絞り込む。共有領域では同じベクトルを重複保存せず、クラスタ単位にエージェント別アクセスプロファイルを付与し、利用者ごとの頻度や選好に応じて細粒度探索順を変える。CPU-GPU階層ではCPU側を大容量の正本索引とし、GPU側には参照頻度が高いクラスタだけを容量制限付きで配置する。挿入や更新はまずCPU側バッファへ受理し、GPU反映やクラスタ分割を非同期化することで、オンライン更新が検索やLLM生成のクリティカルパスを長時間停止させないようにする。最終的には、局所性学習による探索削減、複数エージェント間の粗粒度探索共有、GPUホットクラスタ加速を同じ外部メモリ層で連携させ、動的な読み書きが続く長寿命エージェントでも検索再現率と処理性能を両立する。

### 単一エージェント多段インデックスキャッシュ
高頻度の小規模挿入では、意味的に近い新規ベクトルが複数の既存IVFクラスタへ散在し、固定索引のままでは問い合わせごとの走査クラスタ数が増える。Pancakeは検索と更新の履歴を有限状態機械で表し、あるメモリ領域を参照した後に次にどのクラスタへ移るかという遷移頻度を継続的に学習する。繰り返し共起するクラスタや最近利用されたクラスタは上位のキャッシュ層へ昇格し、問い合わせでは上位層から順に探索する。十分な近傍候補が早い段階で得られれば下位層の走査を打ち切れるため、再現率を維持しながら検索量を減らせる。固定IVFや一定件数到達時だけクラスタ分割する方式と異なり、アクセスパターンの変化を待たずに探索順へ反映できるため、長時間運用で負荷分布が変わる場合にも適応しやすい。更新で新しい遷移が現れた場合は状態を追加・統合し、索引再構築を毎回行わずに局所性モデルだけを漸進的に更新する。

### 複数エージェント協調インデックス
エージェントごとに独立した粗粒度索引を持つだけでは、エージェント数の増加にほぼ比例して上位探索コストが増える。Pancakeは各索引の代表点を接続点としてハイブリッドグラフで結び、一度のグラフ探索から関連するエージェント領域や共有範囲へ到達できるようにする。共有メモリは物理ベクトルを一度だけ保持しつつ、クラスタごとにエージェント別アクセスプロファイルを持たせる。同じ共有データでも、あるエージェントでは頻出、別のエージェントでは低頻度という差を細粒度探索の優先順位へ反映できる。完全共有、部分共有、局所領域といった複数のメモリ範囲を同一の検索・挿入・更新・削除インターフェースから扱い、共有による容量削減と個別局所性の保持を両立する。

### CPU-GPU協調インデックス管理
LLM推論がGPUメモリを大きく消費するため、ANN索引全体をGPUへ常駐させる設計ではモデルのKVキャッシュや活性値と競合する。PancakeはCPU側を大容量の正本階層、GPU側を参照頻度の高いクラスタだけを置く高速キャッシュ階層として分離する。検索履歴から高頻度クラスタを選んでGPUへ配置し、キャッシュ命中時は類似度計算をGPUで処理する一方、低頻度クラスタや容量超過分はCPU側から検索する。挿入や更新はCPU側の挿入バッファへ即時受理し、GPUへの反映、クラスタ分割、置換を非同期ワーカーへ渡すため、細かな更新ごとにGPU検索を停止させない。GPU容量を5〜15GB程度へ制限しても多くの負荷で効果が飽和することを示し、索引全常駐ではなくホット部分だけで加速を得る。LLM推論が利用できる残余容量に応じてキャッシュ量を調整できるため、外部メモリ処理と生成処理を同じGPU上で共存させやすい。

### 非同期実行と既存フレームワーク統合
検索、挿入、更新、削除をPythonインターフェースとして公開し、既存Faiss IVF索引の読み込みにも対応する。検索ワーカー、更新ワーカー、キャッシュ管理、GPU処理を分離し、隣接する小さな操作は内部でまとめて処理する。共有クラスタはロックで保護し、更新と検索が同時に走る場合の整合性を維持する。メモリ操作をLLM呼び出しと非同期に進められるため、MemGPT型の処理フローやLangChain、LlamaIndexなど既存のエージェント基盤を全面的に置き換える必要がなく、外部メモリのバックエンドとして差し替えられる。

### 全体のデータ／制御の流れ
CPU側が大容量ベクトル索引、アクセス状態、ハイブリッドグラフ、更新制御を保持し、GPU側はLLM推論に残された容量の範囲で高頻度クラスタをキャッシュする階層構成である。検索要求はメモリ範囲とエージェント識別子を使ってハイブリッドグラフ上で粗粒度候補を絞り、多段キャッシュとエージェント別プロファイルから細粒度走査順を決める。更新はCPU側へ即時受理して索引状態と有限状態機械・プロファイルを更新し、必要なGPU反映を非同期化する。これにより大容量、動的更新、複数エージェント共有、GPU容量制約を単一のメモリ提供層で扱う。
## 評価条件
- **ハードウェア**: AMD EPYC 9534 64-core CPU、NVIDIA H100 80GB GPU ×8
- **ソフトウェア**: Pancake Python interface、Faiss IVF-compatible index、vLLM for Llama models、GPT-5 API for remote model 条件
- **モデル**: Llama3.1-8B、Llama3.1-70B、GPT-5 API
- **データセット／トレース**: AgentGym、GSM8K、PRM800K、UltraChat、UltraFeedback、APIGenをエージェント負荷として使用。静的知識ベースはMS MARCO 8M passagesをE5（1024次元）で埋め込み。
- **比較対象**: A-Mem、MemGPT、LlamaIndex、LangMem/LangChain、Quake、SpFresh、DiskANN、Pancake-IVF-静的、Pancake-IVF-Split
- **正確性・品質**: ANN検索の品質は再現率と遅延のトレードオフで検証する。検索のみの条件では素のIVFが再現率0.9超を得るため最大128クラスタを走査する必要があり、検索と更新が混在する条件では挿入ベクトルの散在によって再現率がさらに低下する。Pancakeが高い再現率を維持しながら走査クラスタ数と検索遅延を削減できるかを比較し、単なる高速化で検索品質を犠牲にしていないことを確認する。
- **単一エージェントの端から端までの評価**: 複数のエージェントデータセット、Llama3.1-8B/70BとGPT-5 API、局所・共有メモリ条件で既存のエージェントメモリ基盤とスループット・メモリ処理時間を比較する。
- **複数エージェント混合・スケーリング**: 異なるデータセットを組み合わせた2エージェント混合負荷と、最大20同時エージェントまでの条件で、既存メモリ基盤の干渉とPancakeのスループット低下を測る。
- **ベクトルDB単体性能**: 実エージェント負荷から生成されたメモリ操作ベクトルを入力し、バッチサイズ8でSpFresh、DiskANN、Quake、IVF派生方式と問い合わせスループットを比較する。
- **再現率と動的更新**: 検索のみと検索・挿入混在条件で走査クラスタ数、遅延、再現率を比較し、固定IVF、分割型保守、多段キャッシュ、GPU協調の差を評価する。
- **機構別寄与とGPUキャッシュ**: 多段キャッシュ、ハイブリッドグラフ、エージェント別プロファイルの寄与を分離し、GPUキャッシュ容量を0〜30GB程度で変化させてCPU版からの高速化倍率、ウォームアップ、クラスタ分割時の遅延急増を測定する。
機能的なエージェントメモリ基盤とのエンドツーエンド比較と、動的ANN索引との単体比較を分けて評価する。前者ではLLM生成を含むスループット、メモリ操作時間比率、複数エージェント間干渉を測り、後者では問い合わせスループット、再現率、走査量を測る。さらに索引保守、エージェント間協調、GPUキャッシュを個別に無効化・置換する機構別評価により、各機構の寄与と動的負荷への収束速度を検証する。
評価は単一種類のCPU-GPUサーバ構成を中心とし、初期知識ベースはMS MARCO 8M passagesである。最大20エージェントまでの評価であり、数百〜数千エージェント規模、分散ノードを跨ぐ索引、障害回復、永続ストレージ入出力の詳細は対象外である。GPT-5条件は遠隔APIを利用するため、ネットワークおよびAPI側の変動もエンドツーエンド値へ含まれ得る。
## 主要結果
Pancakeは既存のagent メモリ libraryに対し、単一agentの端から端までのスループットを1.12〜26.18倍改善し、平均高速化倍率は4.29倍超となる。メモリ operation単体は6.81倍超高速で、全実行時間に占めるメモリ operationは平均3.2%（最大17.9%未満）まで低下する。2-agent混合では既存比較対象が29.9〜55.9%低下するのに対しPancakeは9.8%以下、20 agentsまででも低下は10.2%未満に抑える。multi-level キャッシュは長時間負荷で最大2.23倍、hybrid graphはcoarse search costを20倍超削減し、GPU キャッシュはCPU版比最大1.92倍を示す。

- 単一agent エンドツーエンド スループット / 1.12×〜26.18×、平均4.29×超 (比較対象: A-Mem / MemGPT / LlamaIndex / LangMem; 条件: 複数model・dataset・4 access patterns) — 外部メモリ処理が大きい条件ほど索引最適化がLLM serving全体へ直結する。

- メモリ operation 高速化倍率 / 6.81×超 (比較対象: 既存agent メモリ implementations; 条件: 検索・挿入を含むメモリ path) — LLM計算ではなくANN メモリ 層自体を高速化した効果を分離して確認できる。

- メモリ operation時間比 / 平均3.2%、17.9%未満 (比較対象: 既存方式では規模増加時82%以上になり得る; 条件: エンドツーエンド ワークロード) — 外部メモリが主要ボトルネックになる状態を大きく緩和する。

- 2-agent mixed ワークロード degradation / 9.8%以下 (比較対象: 既存比較対象は29.9%〜55.9%低下; 条件: 異なるdatasetを混合) — hybrid graphとagent profileがcross-agent interferenceを抑える。

- 20-agent scaling degradation / 10.2%未満 (比較対象: single-agent 条件; 条件: 最大20 concurrent agents) — 評価範囲ではagent数増加に対してほぼ線形にscalingする。

- multi-level index キャッシュ / 最大2.23× 遅延 reduction (比較対象: IVF 静的/split maintenance; 条件: long-serving 動的 ワークロード) — 閾値splitの収束待ちより早くagent localityへ適応する。

- coarse index search cost / 20×超削減 (比較対象: agentごとの独立coarse index; 条件: multi-agent index management) — hybrid graphによりagent数に比例する上位索引走査を避ける。

- vector similarity computation / hybrid graphで最大11.6%削減、agent profileでさらに平均21.8%削減 (比較対象: independently constructed indexes; 条件: multi-agent shared メモリ) — 上位ルーティングだけでなくfine-grained scan順にもagent-specific localityが効く。

- GPU キャッシュ 高速化倍率 / CPU版比最大1.92× (比較対象: Pancake CPU; 条件: GPU キャッシュ、5〜15GB付近で多くのワークロードがplateau) — 索引全常駐なしでもhot clusterだけでGPU accelerationを引き出せる。

### 負の結果・境界条件
- **GPU効果はワークロード依存**: 会話型datasetではquery-relevant clusterが広く分散するため、十分な高速化倍率へ到達するのにより大きなGPU キャッシュが必要で、5〜15GBでplateauするという傾向もワークロードごとに異なる。
- **streaming insertで一時spike**: GPU版でも挿入がcluster splitを引き起こす瞬間には追加計算により遅延 spikeが発生する。多くのcluster operationをGPUで行うことで影響は小さくなるが、完全には消えない。
- **IVFのrecall劣化**: 素のIVFはsearch-onlyでもrecall 0.9超のため最大128 cluster scanが必要で、search-update混在では挿入vectorの散在によりさらにrecallが悪化する。Pancakeの利点はこの動的劣化を局所性キャッシュで補う点にある。
- **大規模分散agentは未検証**: 最大20 agents、単一CPU-GPU nodeの範囲では良好にscaleするが、より大きなagent populationやnode間で共有するメモリ indexの通信・整合性は評価していない。

### 結果の読み方
Pancakeの本質はエージェント外部メモリを一般的なvector DBとして扱わず、検索と更新の順序、agent identity、共有scope、GPU残容量というserving ランタイム固有の情報をindex maintenanceへ取り込む点にある。特に、頻繁なsmall updateが一般DBのバッチ-oriented rebalancingと相性が悪いことを示し、動的メモリでは『検索アルゴリズム』だけでなく『誰がいつどのclusterへアクセスするか』を階層キャッシュとhybrid graphへ反映する必要がある。KV キャッシュとは別系統の外部メモリ hierarchyだが、CPU大容量層とGPU高速層をhotnessで往復させるという点でLLM servingの階層メモリ研究と接続する。
## 品質への影響
モデルの生成品質を直接変更しないシステム最適化だが、外部メモリ retrievalのrecallはagent出力へ影響し得る。そのためPancakeは単なる遅延短縮ではなくrecall-遅延 trade-offを測定し、動的更新下で高recallを保ちながらscan量を減らす。評価はretrieval recall中心で、最終的なtask accuracyへの影響を網羅的に評価したものではない。
## 既存研究との差
- **MemGPT/A-Mem等との差**: 既存agent メモリはメモリ semanticsや管理機能を提供することを主眼に置くのに対し、PancakeはANN indexの動的保守とhardware hierarchyをserving ボトルネックとして最適化するbackend systems研究である。既存workflowを置き換えるより、そのメモリ backendとして統合する。
- **SpFresh/Quake等との差**: 動的vector DBもonline updateを扱うが、主にtraditional databaseのperiodic/バッチ-oriented updateを前提とする。PancakeはLLM agentで検索とsmall updateが各generation step近辺にinterleaveすること、agentごとに局所性が異なることを索引構成へ明示的に利用する。
- **一般GPU vector searchとの差**: 索引全体をGPUへ置く方式や静的index キャッシュではなく、LLM inferenceとVRAMを共有する前提でhot clusterだけをキャッシュし、insert バッファとasync transferで更新可能性を維持する。GPUを高速な一段階として使うhierarchical designである。
- **KV キャッシュ階層化との差**: 保存対象はtransformer内部のKV stateではなく、agentが長期的に参照・更新する外部embedding メモリである。ただしCPU大容量層とGPU高速層の間でhotnessに基づき配置するため、LLM servingにおける階層メモリ 配置というsystems上の共通問題を持つ。
## 限界
- **単一ノード・限定agent数**: 実験はEPYC + H100×8の1ノードが中心で、multi-agent scalabilityも最大20 agentsまでである。分散メモリ service、node間network、partition/replication、failure recoveryを含む大規模deploymentへ結果をそのまま一般化できない。
- **GPU-rich環境への依存**: 評価機はH100 80GBを8枚備えるため、GPU キャッシュへ5〜15GB程度を割り当てられる。GPU容量が厳しい環境や推論modelがほぼ全VRAMを占有する条件ではGPU tierの効果が縮小する可能性がある。
- **永続性・運用機能の評価不足**: 論文は検索・更新・キャッシュ管理の性能を主題とし、クラッシュ整合性、耐久ログ、backup、multi-tenant isolation、access controlなどproduction vector storeの運用要件を中心には評価していない。
- **task品質は間接評価**: retrieval recallは測定するが、メモリ indexの変更が最終agent task successや生成品質へ与える影響を全datasetで詳細に比較してはいない。高recall維持は示すものの、エンドツーエンド qualityの保証とは別である。
- **公開実装の確認不可**: Python interfaceとprototype implementationの詳細は記述されているが、arXivページと本文からPancake本体の公開repository URLは確認できず、第三者による再現性は公開コードがあるシステムより制約される。

## 研究上の位置づけ
LLM推論システムの中では、agentic servingにより新たに生じる外部メモリ I/O・ANN計算をfirst-class resourceとして扱う研究である。KV キャッシュ、モデルオフロード、RAG retrievalが主に一回の推論要求内のstateや静的 corpusを扱うのに対し、Pancakeは複数agentが長期間にわたり同じメモリ baseへ細粒度にread/writeする状態を対象とする。SSD/NVMeを直接最適化する論文ではないが、将来メモリ corpusがDRAMを超える場合にはCPU/GPU tierの下へstorage tierを追加する自然な接続点があり、agent メモリの階層配置・プリフェッチ・update スケジューラを考える基盤になる。
