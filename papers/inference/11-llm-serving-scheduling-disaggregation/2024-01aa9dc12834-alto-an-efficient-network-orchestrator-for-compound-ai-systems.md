# ALTO：複合AIパイプラインの部分出力を逐次配送するネットワーク実行基盤

## 概要

ALTO（Automatic Language Token Orchestrator）は、言語モデルの生成結果を複数の検索・再順位付け・追加生成段へ渡す**複合AIシステムの実行基盤**である。一般的な段階実行では、ある言語モデルがすべての主張や検索文を生成し終えるまで、次の段が開始できない。ALTOは、主張を一つ抽出した時点、検索文を一つ生成した時点、さらには検索文のトークンを一つ生成した時点で後段へ送る。これにより、同一要求に属する上流生成と下流検索を重ね、後段が遊休する時間を減らす。

ただし、途中のトークンを任意の後段インスタンスへ送ればよいわけではない。BM25が検索文中の複数トークンの関連度を合計する場合、同じ検索文のトークンを一貫したインスタンスへ送らなければ正しく集約できない。ALTOはこの**集約制約を持つ部分出力の配送**を扱い、独立した部分出力には並列処理を許す。論文の実機評価では、応答遅延4秒を目標とする条件で、非逐次転送の比較方式より最大3倍の要求到着負荷を処理し、低負荷での99パーセンタイル遅延を1.8分の1にした。

重要な区別として、原著が定量的に評価したのは**中間結果の逐次転送の有無**である。論文が議論するプロンプト内容を考慮した分散スケジューリングは未実装の将来設計であり、3倍の改善をその機能の成果として説明してはならない。

## 問題設定と処理例

論文は事実確認を行う6段の処理を例にする。第1段で質問への回答を生成し、第2段で回答中の検証可能な主張を抽出する。第3段では主張ごとに複数の検索文を生成する。第4段のBM25検索と第5段のColBERT検索文符号化を経て、第6段でColBERTが検索候補を再順位付けする。第3段から第4・第5段への分岐があり、後段で検索結果を組み合わせる必要がある。原著の実験では、元のFacToolにある最終的な主張の真偽判定段は省略し、検索結果までを対象にしている。

全出力待機方式では、第2段がすべての主張を抽出し終えるまで第3段は動けず、第3段がすべての検索文を生成し終えるまで検索段が待つ。逐次転送方式では、第2段の最初の主張が出た時点で第3段が動き、最初の検索文が出た時点でBM25とColBERT側の仕事を開始できる。この重畳は単なるモデルのトークン生成高速化とは異なり、**複数のモデル呼び出しと検索処理を含む要求全体の待ち時間**を削る。

難点は、生成モデルが要求ごとに異なる数の主張・検索文・トークンを出力することである。処理段ごとに集約の粒度も異なる。主張単位で独立してよい段と、検索文内の全トークンを合算する段とでは、許される負荷分散の自由度が異なる。集約制約を無視すると結果が誤り、全段を一律に要求単位へ固定すると遊休インスタンスが生じる。

## 手法：中間結果を流す仕組み

### 1. 部分出力と非同期キュー

ALTOでは開発者が処理段、入力キュー、出力キュー、データ形式を定義する。段間のデータはProtocol Buffersで型を指定し、言語モデルが新しい出力を生成するたびに次段へ書き込める。集中実行基盤がキューを通じて段間配送を仲介するため、上流段は下流段の処理完了を待たずに次の部分出力を生成できる。入力と出力の間で非同期実行することで、生成・検索・再順位付けが重なる。

原著の試作キューは、上流から集中実行基盤への出力用と、集中実行基盤から下流への入力用という二つの信頼性のあるUNIXドメインソケットを組み合わせる。集中実行基盤は転送途中のProtocol Buffersを復号せず、アプリケーション側で復号する。したがって中央部はデータ本体を解釈するのではなく、付与された識別情報と制約から配送先を選ぶ。論文はネットワークソケットへの拡張可能性に言及するが、評価した実装の通信路と、多ノード実機で検証済みの構成を混同してはならない。

### 2. 集約制約付き配送（aggregation-aware routing）

開発者はデータのヘッダに、全体要求の識別子、主張の識別子、検索文の識別子などを付与する。論文の例では、検索トークンをBM25へ送るとき、`constraints=[obj_id, claim_id, query_id]` のような階層的識別子を使う。同じ検索文に属するトークンを合計するには、同じ集約制約を持つ部分出力を同一BM25インスタンスへ送る必要がある。一方、互いに独立した検索文は別インスタンスへ送ってよい。

実装した単純なスケジューラは、集約制約があればその識別子をハッシュ化し、配送先インスタンス数で剰余を取って宛先を決める。集約制約がない場合は巡回順（round robin）で次の宛先を選ぶ。これにより、同じ集約単位のデータは宛先が一貫し、独立データは複数インスタンスへ分散する。集約演算には検索文の関連度合計だけでなく、上位k件選択、件数計測、フィルタ処理なども考えられるが、汎用集約演算子の自動提供は将来課題である。

この方式は集約の正しさと並列性を両立させる一方、ハッシュによる静的割当では、ある検索文だけが大量のトークンを生む場合にその宛先が過負荷になる。論文の図4は、片方のインスタンスが5個、もう片方が3個の部分出力を担当したとき、後者が先に遊休する例を示す。集約制約は処理の正しさのために必要だが、負荷分散に自由度の上限を設ける。

### 3. 集中実行基盤と段の起動

集中実行基盤は二つの設定ファイルを受け取る。一つは各段の計算資源要求と入出力キュー、もう一つは段ごとの実行インスタンス数である。基盤は要求ごとの大域識別子を付け、集約制約を解釈して次の宛先を決める。実装は約7,000行のRustで、処理段はPythonで記述する。Python側は非同期入出力の`asyncio`を利用し、モデル実行器は逐次生成結果を非同期で返せれば接続できる。論文はvLLMとSGLang Runtimeの連携実装を明記している。

集中型の制御は実装を単純化するが、全ての部分出力の配送が中央経路を通るため、規模拡大時の集中部の処理能力、障害時の回復、ネットワーク越しの転送遅延を別途評価する必要がある。原著の9ページ版はこれらの大規模分散試験を報告していない。

### 4. 分散プロンプト認識スケジューリングは提案段階

原著の表1は、生成段によって部分出力数、平均長、実行時間が大きく異なることを示す。例えば主張抽出は要求あたり平均3.3件の主張を生み、検索文生成は主張あたり平均2.5件の検索文を生む。検索文生成はさらにトークン単位の細かな出力を持つ。したがって単純な要求数均等化では、段ごとの実際の計算量を均等化できない。

論文は将来の方策として、プロンプト種類ごとの出力量・処理時間・待ち行列遅延を測り、同じ接頭部を共有する要求を可能なら同じ言語モデルインスタンスへ送る「プロンプト局所性」と、異なるプロンプト間の負荷均等化を同時に扱う構想を提示する。ただし§4の試作スケジューラはプロンプト内容を使っていない。局所性を考慮する分散割当の最適化問題も、実装と定量評価を将来へ残している。

### 既存方式との相違

従来の単一言語モデル実行器は、注意機構の鍵・値キャッシュ共有、連続バッチ処理、生成トークンの逐次送信などを最適化する。ALTOはモデル内の注意計算を置換するのではなく、**複数モデルと検索処理をまたぐ部分出力の配送経路**を扱う。既存のモデル実行器が生成したトークンを、後続の主張抽出や検索段が待機せず消費できる点が差である。

一般のマイクロサービス基盤やストリーム処理基盤は非同期メッセージ送信や集約演算を提供する。しかし、生成モデルの出力が「要求→主張→検索文→トークン」という階層で増殖する場合、どの階層で同じインスタンスへ集める必要があるかを簡潔に表現しにくい。ALTOの制約ヘッダはこの階層を開発者が指定する仕組みである。現行試作は開発者による手動タグ付けを要求するため、既存基盤の全ての集約処理を自動で置換できるわけではない。

## 限界

**集約制約と負荷均等化の競合。** 同じ検索文のトークンを一つのBM25インスタンスへ固定すると、出力数の多い検索文を引いたインスタンスが長く動き、別インスタンスが遊休し得る。図4はこの構造的な負荷偏りを示す。単純なハッシュ配送で集約の正しさを守るだけでは、最適な負荷分散を保証しない。

**スケジューラの未実装部分。** 原著の試作にはプロンプト内容に応じた分散配置最適化が入っていない。プロンプトの実行時間・出力量・待ち行列を観測し、同じ接頭部を同じ実行器へ集める機構は設計案にとどまる。3倍の改善を「プロンプト局所性最適化」の実証値として使うことはできない。

**実装の集中性と通信範囲。** 中央実行基盤とUNIXドメインソケットを使う試作を単一HGXノードで評価している。ネットワークソケットを使う真の複数ノード構成、障害時の配送継続、集約状態の再配置、中央基盤の処理能力上限はこの論文の主要実測範囲外である。モデル数やパイプライン段数を増やしたときに同じ改善が続くとは結論できない。

**対象処理と品質。** 実験はSQuAD質問から主張を抽出し検索証拠を取得する6段処理で、FacToolの最終的な主張判定段を省いている。評価は要求処理量と遅延が中心で、検索結果の正答率・回答品質・生成モデルの精度が逐次転送でどう変わるかを独立に定量比較したものではない。集約制約を守ることは正しい処理経路の必要条件だが、モデルの意味的正確性を保証するわけではない。
