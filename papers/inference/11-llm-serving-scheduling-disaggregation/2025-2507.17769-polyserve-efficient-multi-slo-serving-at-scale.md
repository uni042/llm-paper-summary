# PolyServe: Efficient Multi-SLO Serving at Scale

> PolyServeは、すべての対話要求を同じ低遅延クラスとして扱わず、出力1トークン当たり時間（Time Per Output Token; TPOT）のサービス品質目標（Service Level Objective; SLO）ごとに要求を階層化する。各階層を専用サーバ群へ割り当てつつ、SLOを満たせる範囲で要求を高負荷サーバへ寄せることで、空きサーバと飽和サーバが混在する状態を避け、自動拡縮しやすい負荷勾配を意図的に作る。

## 概要

従来の配信制御では、要求を「遅延重視（latency-sensitive）」と「ベストエフォート（best-effort）」の二種類に分ける設計が多い。しかし実際のLLMサービスでは、同じ遅延重視でもアプリケーションごとに許容TPOTが異なる。20 ms/tokenを要求する対話と100 ms/tokenを許容する処理を同じクラスに入れると、前者に合わせて全体を過剰配備するか、後者に寄せて前者のSLOを破る。

さらにLLMの連続バッチ処理では、同じバッチ内の要求がほぼ同じデコード周期で進む。異なるTPOT目標を同居させると、厳しい要求に合わせた資源配分が緩い要求にも適用され、余剰容量が生じる。逆にSLO階層ごとに完全分離すると、負荷の偏りによってあるプールは飽和し、別プールは遊休になる。

PolyServeはこの問題を、SLO階層ごとの**ビン分け → サーバ群割当 → SLO達成可能性を見た高負荷側への集約 → 必要時の階層間共有**として解く。さらに、要求待ち時間を使った優先度調整、プリフィルの動的チャンク化、次チャンクの所要時間予測を組み合わせ、平均goodputだけでなく裾遅延を壊さないよう制御する。

## 背景と問題設定

### 二値の優先度では「厳しいSLO同士」の違いを扱えない

低遅延要求とベストエフォート要求だけなら、混雑時にベストエフォートを中断して低遅延要求を守れる。しかし複数の低遅延SLOがある場合、緩いSLOの要求も無期限には止められない。つまり「優先度の低い要求を犠牲にすればよい」という設計が使えず、各階層の裾遅延を同時に管理する必要がある。

### 自動拡縮も総要求率だけでは足りない

クラスタ全体の要求率が同じでも、厳しいTPOT階層が急増した場合と緩い階層が増えた場合では必要なインスタンス数が異なる。したがって総リクエスト毎秒だけを見る自動拡縮（autoscaling）では、階層ごとの需要変化を捉えられない。

PolyServeは、スケジューラがSLO階層ごとの負荷を意図的に偏らせることで、「どのサーバ群が次に増減すべきか」を明瞭にする。これは単なる要求振り分けだけでなく、自動拡縮へつながる配備状態を作る設計である。

## 手法

### 1. TPOT SLOで要求を複数ビンへ分ける

到着要求を要求TPOTに応じたビンへ分類し、各ビンにサーバ群を対応付ける。これにより、同じデコード周期で進む要求同士が近い遅延要件を持つようになり、厳しいSLOへ合わせた過剰資源配分を減らす。

### 2. 「最も空いている」ではなく「最も混んでいてもSLOを守れる」サーバへ送る

一般的な負荷分散は最小負荷サーバへ要求を広げる。しかし全サーバを中程度に埋めると、どのサーバも停止・縮退できず、自動拡縮に不利になる。

PolyServeはプロファイルから各サーバのSLO達成可能性を予測し、**SLOを満たせる候補の中で最も高負荷のサーバ**を選ぶ。これにより一部サーバを高利用率へ集約し、別サーバを低負荷にして、負荷勾配を作る。低負荷側を縮退しやすく、高負荷側は増設判断を出しやすい。

### 3. 緩いSLOを厳しいSLO用インスタンスへ一時的に共有する

SLO階層ごとの完全分離では、緩い階層のサーバが飽和していても、厳しい階層のサーバに余裕があれば資源が余る。PolyServeは、厳しいSLOの安全余裕を壊さない範囲で緩い要求をそのプールへ流す。

この共有は無制限ではなく、プロファイル済みの処理能力と現在の負荷から、既存要求のSLOを満たせるかを確認して決める。したがって利用率向上とSLO隔離の中間を取る。

### 4. 待ち時間・チャンク化プリフィルで裾遅延を制御する

プリフィルが長い要求をそのまま実行すると、後続デコードのTPOTを押し上げる。一方、チャンクを細かくし過ぎるとGPU効率が落ちる。PolyServeは要求待ち時間をスケジューリング判断へ入れ、プリフィルチャンク長を動的に調整する。

さらに、現在チャンクを実行しながら次チャンクの所要時間を継続的に予測し、将来のSLO違反を早めに避ける。ここでの目的は平均遅延の最小化ではなく、複数SLO階層で一定の達成率を維持したまま処理要求数を増やすことである。

## 評価

### 代表的な評価条件

| 項目 | 条件 |
|---|---|
| クラスタ規模 | goodput評価では20 serving instances |
| 到着過程 | Poisson過程 |
| 負荷 | 各トレースで理想スループットの20%〜120%まで変化 |
| トレース | Mooncake conversation / synthetic / tool-agent、LMSYS、ShareGPT、Splitwise系など |
| 配備形態 | プリフィル・デコード分離（PD）と同居（CO）の双方 |
| 比較 | Random、Minimal-load系、固定chunked schedulerなど |
| 主指標 | TPOT階層別SLO達成率、全体SLO達成率、goodput、最適goodput比 |

### 代表的な評価結果

| 条件・指標 | 結果 | 読み取れること |
|---|---:|---|
| プリフィル・デコード分離版PolyServe | 90% SLO達成点で最良基準より平均 **1.23倍** goodput | 多SLOを分離しつつ空き資源も共有する効果 |
| 同居版PolyServe | 同条件で平均 **1.18倍** goodput | GPU同居環境でもスケジューリング効果が残る |
| 理想解との比較 | 最大 **92.5%** の最適goodput | ヒューリスティック制御が理想上限へ比較的近い |
| SLO階層別 | 高負荷でも各TPOT階層の達成率を比較的均等に維持 | 緩い階層だけを犠牲にして総達成率を作る方式ではない |
| 負荷上昇 | 20%→120%の範囲で評価 | 軽負荷だけでなく飽和付近の挙動を確認 |

1.23倍は単一モデルのトークン生成カーネルが1.23倍速くなる値ではない。**SLOを満たして完了できる要求量（goodput）**の改善であり、ルーティング・待ち行列・チャンク化・サーバ占有率を含むクラスタ全体の効果である。

## 既存研究との差

従来の低遅延/ベストエフォート方式は、優先度が二段階であるため「どちらも遅延制約を持つが厳しさが異なる」要求群を表現しにくい。単純な最小負荷ルーティングは要求を均等に散らすため、個々のサーバは安全でも自動拡縮の余地を消しやすい。

PolyServeはSLOを複数階層へ離散化し、サーバ群も対応する階層へ分けた上で、あえて負荷勾配を作る。さらに階層間共有を安全余裕付きで許すことで、完全分離と完全混載の中間を取る点が特徴である。

## 限界・実装状況

SLO達成可能性は事前プロファイルと現在負荷の見積りに依存する。モデル、GPU、カーネル、要求長分布が変わればプロファイルの更新が必要であり、急激な分布変化では安全余裕が不足する可能性がある。

また、SLOをビンへ離散化するため、非常に多くの細かな契約階層を持つサービスではビン数・サーバ分割・共有規則の設計が複雑になる。20インスタンス規模の評価で傾向は示されるが、数百〜数千インスタンスでの制御プレーン負荷や障害時再配置は別途検証が必要である。
