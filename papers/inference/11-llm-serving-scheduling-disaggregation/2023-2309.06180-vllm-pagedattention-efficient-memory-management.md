# Efficient Memory Management for Large Language Model Serving with PagedAttention

> KV cacheを固定長のblockへ分割して非連続なGPU memoryへpageのように配置し、必要な分だけ割り当て・複数sequence間で共有することで、fragmentationと過剰予約をほぼなくしてcontinuous batchingのbatch sizeを拡大するvLLM serving system。

## 概要

vLLMは、LLM servingではGPU computeだけでなく**KV cacheのmemory allocationがbatch sizeを制約する**ことに着目した研究である。

従来systemは各requestに最大sequence lengthを想定した連続領域を予約するため、実際には使われない領域が大量に生じる。またrequestごとに予約sizeが異なることでexternal fragmentationも起きる。論文のprofileでは、既存方式でKV cache memoryのうち実際のtoken stateに使われている割合が約20〜38%に留まる条件があった。

vLLMはOSのvirtual memoryになぞらえ、KV cacheを固定token数の**logical block**へ分割し、それぞれを任意の**physical block**へmapするPagedAttentionを導入する。physical blockは連続している必要がなく、token生成に合わせて必要な分だけ追加割当する。

さらにparallel sampling、beam search、共通prefixなどでは複数sequenceが同じphysical KV blockを共有し、変更が必要な時だけcopy-on-writeする。これによりmemory節約を直接より大きなcontinuous batchへ変換する。

## 問題設定

model weightはserving中ほぼ固定だが、KV cacheはrequestごとに生成token数に応じて伸び、終了すると消える。しかも最終sequence lengthは事前には分からない。

連続領域を事前予約する方式では、

- 実際のoutputが最大長より短いことによるinternal fragmentation
- request sizeの違いによるexternal fragmentation
- parallel sampling / beam searchで同一prompt KVを重複保存するcost

が発生する。

これによりGPUにcompute余力があってもbatchへ追加requestを載せられず、Orcaのようなiteration-level schedulingが持つcontinuous batchingの利点をmemory側が制限する。

vLLMは**KVの論理的なsequence順序とphysical GPU memoryの連続性を切り離す**ことでこの問題を解く。

## 手法

### 1. PagedAttention

各sequenceのKV cacheを固定token数のlogical blockへ分ける。logical block tableは、各logical blockがどのphysical GPU blockに置かれているかを保持する。

attention kernelはblock tableを辿って必要なK/Vを読むため、physical block同士が連続memoryに並ぶ必要がない。

新tokenで現在blockが満杯になった時だけ新しいphysical blockを割り当てるため、request最大長分を先に予約する必要がない。固定size blockなのでexternal fragmentationも基本的に発生しない。

### 2. Block-level memory manager

schedulerはfree physical block poolを管理し、sequenceへon-demandにblockを割り当てる。

memory pressureが高い場合はrequestをpreemptし、KV blockをCPU memoryへswapするか、後から再計算する。PagedAttentionとschedulerを一体設計することで、requestの追加・停止・再開をblock単位で扱える。

### 3. Copy-on-writeによるKV共有

parallel samplingでは複数output candidateが同じpromptから分岐する。vLLMはpromptに対応するphysical blockをcandidate間で共有し、reference countを持たせる。

共有blockへ新しいtokenを書き込む必要が出た時だけ新しいphysical blockを作り、必要部分をcopyする。beam searchでも同様にcandidate間で共通するprefix blockを共有できる。

これにより同じpromptや途中sequenceを候補ごとに丸ごと複製する必要がない。

### 4. Shared prefix

異なるrequest同士でもsystem promptやfew-shot exampleなど共通prefixがあれば、logical blockを同じphysical blockへmapできる。

これは単なるbeam search内共有ではなく、requestを跨いだKV reuseを可能にする設計で、後のprefix caching / distributed KV cache systemにつながる。

### 5. Distributed serving

vLLMはMegatron-LM型tensor parallelismを使ったmulti-GPU servingにも対応し、各workerが対応するKV block partitionを管理する。

PagedAttentionのblock allocationはdistributed構成でも同じlogical abstractionを維持する。

## 評価

### 条件

| Model | GPU構成 | Total GPU memory |
|---|---|---:|
| OPT-13B | 1× A100 40GB | 40GB |
| OPT-66B | 4× A100 40GB | 160GB |
| OPT-175B | 8× A100 80GB | 640GB |

追加でLLaMA-13Bをshared-prefix workloadに使用する。Google Cloud A2 instance上で評価し、workloadはShareGPTとAlpacaの実textからinput / output lengthを取り、arrival timeをPoisson processで生成する。

baselineはFasterTransformerと、OrcaをKV reservation方式別に再実装した`Orca (Max) / (Pow2) / (Oracle)`である。Orca公式実装は公開されていなかったため、論文著者による再実装比較である点に注意が必要。

### 主要結果

論文全体では同程度のlatencyで既存system比**2〜4倍のthroughput**を報告している。

ShareGPT single-sequence generationでは、vLLMはoutput lengthを事前に知る理想化されたOrca (Oracle)に対しても**1.7〜2.7倍**高いrequest rateを維持した。最大長を予約するOrca (Max)に対しては**2.7〜8倍**だった。

OPT-13B / ShareGPTでは平均同時batch request数がOrca (Oracle)の約13.6に対しvLLMは約30.4で、memory efficiencyがそのままbatch capacityへ反映されている。

### 複数sequence生成

parallel samplingではKV block共有によるmemory savingがAlpacaで約6.1〜9.8%、ShareGPTで約16.2〜30.5%。beam searchではAlpacaで約37.6〜55.2%、ShareGPTで約44.3〜66.3%だった。

OPT-13B + Alpacaでは、Orca (Oracle)に対する性能差がbasic samplingの1.3倍からbeam width 6で2.3倍まで広がった。

### Shared prefix

LLaMA-13Bのtranslation workloadで、80-tokenの1-shot prefix共有ではOrca (Oracle)比**1.67倍**、341-tokenの5-shot prefixでは**3.58倍**のthroughputを報告している。

## 既存研究との差

### Orcaとの違い

Orcaはiteration-level schedulingによってrequest setを毎token変えられるようにしたが、KV cache memory allocation自体のfragmentationやreservation wasteは残る。

vLLMはOrca型continuous batchingを前提に、**KV cacheをpaged memoryとして管理することで、batchへ実際に載せられるrequest数を増やす**。つまりscheduler flexibilityをmemory manager側から解放する研究である。

### FastServeとの違い

FastServeはrequest priorityとpreemptionを中心にhead-of-line blockingを減らし、KV swapを補助機構として使う。vLLMはpriority schedulingより**KV block allocation / sharing**が主題である。

### KV compression / evictionとの違い

PagedAttentionはKVの内容を削除・近似・量子化しない。必要なKVをlosslessに保持したままphysical placementとsharingを改善するため、品質とのtrade-offを持たないmemory management手法である。

## 限界

- PagedAttention kernelは非連続blockを参照するため、単純なcontiguous attention kernelよりaddress mapping overheadがある。
- block sizeが大きすぎると最後のblock内fragmentationが増え、sharing機会も減る。小さすぎるとmetadata / kernel overheadが増えるため調整が必要。
- 評価の中心はOPTとLLaMA世代で、GQA / MLA / paged-KV専用kernelが一般化した後のarchitectureとはcost balanceが異なる。
- Orca比較は著者による再実装であり、公式Orca runtimeとの直接比較ではない。
- PagedAttention自体はrequest routing、P/D disaggregation、cluster-level load balancingを解決しない。

## 一般的な実装上の含意

vLLMの核心は、LLM servingのKV cacheを通常tensorのような**連続配列として扱う必要はない**と示した点である。

logical sequenceとphysical memoryをpage tableで分離すれば、unknown output length、preemption、beam branching、prefix sharingのすべてを同じblock abstractionで扱える。これは単なるattention kernel最適化ではなく、scheduler・memory manager・decoding algorithmの共通基盤になる。

また「memory efficiencyが少し上がる」こと自体より、その空いたmemoryで**より多くのrequestをcontinuous batchへ入れられる**ことがthroughput向上の主因であり、servingではmemory optimizationをbatching policyまで含めて評価する必要がある。
