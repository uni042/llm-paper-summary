# Efficient Memory Management for Large Language Model Serving with PagedAttention

> KV cacheを固定長blockへ分け、必要になった分だけGPU memoryを割り当てて複数sequence間でも共有し、未使用領域を減らして同時に処理できるrequest数を増やすvLLM serving system。

## 概要

vLLMは、LLM servingではGPUの計算能力だけでなく**KV cacheの置き方がbatch sizeを制限する**ことに注目した研究である。

従来方式では、requestごとに最大sequence lengthを想定した大きな連続領域を先に確保することが多かった。実際のoutputが短ければ、その大部分は使われない。また長さの違うrequestが出入りすると、空き領域が細かく分かれて使いにくくなる。

vLLMはKV cacheを固定token数のblockへ分け、各blockをGPU memory上の好きな場所へ置ける **PagedAttention** を導入した。名前はOSのmemory pageから来ているが、重要なのは**requestのKVを1つの連続領域に置く必要をなくした**点である。

新しいtokenが増えた時だけblockを追加するため、最大長分を先に確保する必要がない。また同じprefixを持つ複数sequenceでは、共通部分のKV blockを共有できる。

## 問題設定

KV cacheはrequestごとに生成token数に合わせて増え、request終了時に消える。output長は事前には分からない。

そのため大きな連続領域を先に予約すると、

- 最後まで使われないmemoryが増える
- 空きmemoryが細切れになって使いにくくなる
- beam searchや複数候補生成で同じprompt KVを重複保存する

という問題が起きる。

GPUに計算余力があってもKV用memoryが足りなければ、新しいrequestをcontinuous batchへ追加できない。

## 手法

### 1. KV cacheを固定長blockへ分ける

各sequenceのKVを固定token数のblockへ分割する。request側から見たblock順序と、実際にGPU memory上のどこへ置くかは分離する。

attention kernelは対応表を使って必要なK/V blockを読むため、物理的に連続している必要がない。

現在のblockが一杯になった時だけ次のblockを割り当てるので、まだ使わない将来分のmemoryを予約しなくてよい。

### 2. 空きblockを共通poolとして管理する

schedulerは空いているKV blockをまとめて管理し、必要なrequestへその都度割り当てる。

memoryが足りなくなった場合はrequestを一時停止し、KVをCPUへ移すか、後で再計算することもできる。

### 3. 同じprefixのKVを共有する

parallel samplingやbeam searchでは、複数candidateが同じpromptから分岐する。vLLMは分岐前のKV blockをcandidate間で共有し、内容を書き換える必要が出た時だけ新しいblockを作る。

これは一般にcopy-on-writeと呼ばれる方法だが、ここでは**同じKVを最初から複製せず、違いが生じた部分だけ別memoryにする仕組み**と考えればよい。

異なるrequestでもsystem promptやfew-shot exampleなど同じprefixがあれば、同じKV blockを再利用できる。

## 評価

主な評価はA100上のOPT-13B / 66B / 175Bで行い、ShareGPTとAlpaca由来のrequest長を使った。

論文全体では、同程度のlatencyで既存system比**2〜4倍のthroughput**を報告している。

ShareGPTでは、output長を事前に知っている理想化されたOrca実装に対しても**1.7〜2.7倍**高いrequest rateを維持した。

OPT-13B / ShareGPTでは平均同時request数がOrca側の約13.6に対してvLLMは約30.4となり、memory節約がそのままbatch拡大につながっている。

beam searchでは共通KVの共有効果が大きく、条件によってKV memoryを約44〜66%削減した。

## 既存研究との差

### Orcaとの違い

Orcaはtoken生成ごとにbatchを組み替えられるようにしたが、KV memory自体の無駄は大きく残る。

vLLMは**KV memoryを必要量だけ確保する仕組み**を加え、Orca型のcontinuous batchingで実際に載せられるrequest数を増やした。

### FastServeとの違い

FastServeはrequestの優先順位と一時停止が中心。vLLMはKV cacheの割当と共有が中心で、どのrequestを先に処理するか自体は主題ではない。

### KV compressionとの違い

PagedAttentionはKVの内容を削除・近似・量子化しない。保持する情報はそのままで、**memoryの配置方法だけを効率化する**。

## 限界

- 非連続blockを読むため、単純な連続memoryよりaddress lookupの処理が増える。
- block sizeが大きすぎると最後のblockに未使用領域が増え、小さすぎると管理costが増える。
- 評価modelはOPT / LLaMA世代が中心で、現在のGQA / MLAでは最適なblock設計が変わる可能性がある。
- request routingやprefill / decode分離、cluster全体のload balancingは直接扱わない。

## 一般的な実装上の含意

vLLMの核心は、KV cacheを**1つの連続tensorとして置く必要はない**と示したことにある。

固定長blockで必要分だけ割り当てると、unknown output length、requestの一時停止、beam search、prefix共有を同じ仕組みで扱える。

servingではmemoryを少し節約すること自体より、**空いたVRAMへさらにrequestを入れてbatchを大きくできること**がthroughput向上につながる。
