# PipeRAG：検索・生成の並列化と性能モデルによる検索品質の制御

## 概要

検索拡張生成（Retrieval-Augmented Generation、RAG）では、生成開始前に一度だけ外部情報を検索する方式に加え、生成文が伸びる途中でも検索を繰り返す方式がある。後者は、文章の話題が変化しても最新の文脈に近い資料を取り込める一方、検索が完了するまで言語モデルが次の生成へ進めない。大規模な文書データベースでは検索待ちが無視できず、検索回数を増やすほど推論装置と検索装置が交互に遊休する。PipeRAGは、この逐次依存そのものを緩めるアルゴリズムとシステムの協調設計である。

中心となる三つの機構は、少し古い生成文脈から次区間の検索を前倒しする**検索・生成のパイプライン並列化**、RETROの固定64トークンに縛られない**可変検索間隔**、そして次の生成区間の計算時間に収まる範囲で近似最近傍探索の深さを最大化する**性能モデル駆動検索**である。単に検索器のアルゴリズムを速くするのではなく、検索の開始時刻・取得知識を使う位置・検索器に割り当てる時間予算を一体化する。

原著の評価は582MパラメータのRETRO、最大30億個のトークン区間からなるC4由来データベース、Wikipedia・RealNews・C4を対象とする。1024トークン生成の端から端の遅延では、同等以上の困惑度を維持しながらRETRO比最大2.6倍の短縮を示す。同じ遅延なら困惑度を最大0.93ポイント改善する条件もある。一方、非検索モデルと比較すると検索結果を統合する交差注意などの費用は残り、遅延が完全に一致するわけではない。

## 問題設定と設計上の観測

### 逐次RETROでは二つの装置が交互に待つ

RETROは入力と生成済み系列を一定長の区間に分割し、直前の区間を検索窓として関連トークン区間をデータベースから取り出す。検索で得た区間はエンコーダで処理され、デコーダは区間単位の交差注意を介してその情報を参照する。基準方式は64トークンを一単位とし、次の生成区間を開始する前に必要な検索結果を確定する。検索器がCPU中心の別サーバーで動作し、生成器がGPUで動く場合、検索中はGPUが待ち、GPU生成中は検索器が次の問い合わせを受け取れない。

検索を一度しか実行しない方式ではこの待機は少ないが、長い文章で話題が変わると初回の取得結果が古くなる。検索間隔を短くすれば文脈の鮮度は改善しやすいが、逐次実行では待機回数も増える。PipeRAGが解く問題は、検索精度と検索回数の交換条件だけではなく、**検索・生成の実行依存をどう配置するか**というシステム問題である。

### 生成時間と検索時間はそれぞれ変動する

デコーダの注意計算では生成済み系列が伸びるほど過去のキー・値を参照する仕事が増えるため、次の一定トークン数を生成する時間は系列位置によって変わる。一方、近似最近傍検索（Approximate Nearest Neighbor Search、ANN）では、索引の探索範囲を広げるほど真の近傍を発見しやすいが、比較対象ベクトル数が増えて時間がかかる。索引の転送、検索サーバーの負荷、ネットワーク往復時間も遅延を左右する。両装置の所要時間が同程度なら並列化で隠せる待ちが多いが、片方だけ極端に遅いと重畳だけでは十分でない。

## 手法

### 1. 古い検索窓を用いた先行検索

通常のRETROでは、次の区間を生成する直前に直前の64トークンを問い合わせにする。PipeRAGは検索窓をsトークン前へずらし、生成器が現在の区間を処理している間に次の区間向けの検索を始める。原著は本来の窓Qに対して古い窓Q̂を用い、検索結果を`Shift(Ret(Q̂), s)`として補正する。補正は検索結果の先頭側の古い位置を除外し、生成区間と参照位置の対応を合わせるためのもので、検索器が未来の生成トークンを知っているという意味ではない。

この設計では、次区間で使う資料は少し古い文脈から取得されるため、文脈が急変した場合に本来の最新検索と異なる結果を返す可能性がある。したがって先行検索は完全に同一の検索結果を得る最適化ではなく、**検索窓の鮮度と待機時間を交換する**アルゴリズム変更である。初回の検索だけは前の生成区間が存在しないため通常の検索を行い、以降の区間から重畳を利用する。

### 2. 可変検索間隔と交差注意の整合性

RETROではデータベースの区間長、検索窓長、検索間隔が64トークンで揃っている。PipeRAGはデータベース区間長と問い合わせ窓長を64のまま保ちつつ、生成中の検索間隔m′を8、16、32、64などに変えられるよう交差注意の参照領域を修正する。例えばm′=32なら、64トークンの検索窓を32トークンずつずらして問い合わせる。短い間隔では最新文脈とのずれが小さくなり、取得情報をより頻繁に統合できる。

交差注意の修正は重要である。検索結果を受け取るデコーダ位置と、検索窓を作った過去位置の対応を誤ると、モデルがまだ生成していない情報を参照したり、別の区間の資料を使ったりする。PipeRAGはエンコーダからデコーダ、デコーダからエンコーダへの注意領域を可変間隔に合わせて変更する。これは外部検索だけのプラグインではなく、RETRO型モデルの注意構造に依存する改変である。

検索間隔m′は一つの生成要求の途中で毎トークン変えるのではなく、原著では生成過程ごとに設定する。検索を短い間隔で繰り返すと、検索器が忙しくなって次の区間までに完了できない場合もある。そのため間隔の柔軟化は、後述する性能モデルによる探索量制御と組み合わせて初めて待機を抑えやすい。

### 3. 推論側の実測性能モデル

次の区間の生成時間を、検索結果のエンコード時間とデコーダ生成時間の和`T_C = T_Enc + T_Dec`として見積もる。デコーダの所要時間は既に生成したトークン数と区間長に依存し、検索結果のエンコード費用は取得する近傍数や各近傍のトークン数に依存する。原著は複数の系列長でGPU推論を計測して性能表を作り、生成状態から次区間の計算時間を予測する。これは大規模な学習済み予測モデルを必須とするわけではなく、実機のプロファイリングを用いたモデルでよい。

推論モデルが与えるのは、検索器が次の結果を届けるまでに利用できる時間予算である。検索器がこの予算より速く終われば、GPU側の生成に隠れて検索待ちが表面化しない。逆に予算を超えれば次区間の開始時に待機が発生する。予算は系列長や実装によって変わるため、検索範囲を固定するだけでは常に最適にならない。

### 4. 検索側の性能モデルとnprobeの決定

原著の検索器はFaissの倒立ファイル索引と積量子化を組み合わせたIVF-PQを使う。データベースのベクトルを複数のクラスタリストへ割り当て、問い合わせ時には近いと推定した一部のリストを調べる。`nprobe`は実際に探索するリスト数であり、大きくすると検索品質が上がる傾向があるが、メモリ読出しと距離計算も増える。

検索時間は、ネットワーク往復、問い合わせのベクトル化、索引探索、候補ベクトルの走査に分解する。原著は`nprobe`と検索時間の関係を実機で計測し、近似的な線形回帰で表す。検索器は次区間の推論時間`T_C`を受け取り、`T_Ret(nprobe) ≤ T_C`を満たす最大の`nprobe`を選ぶ。こうして単に検索を最速にするのでなく、**生成時間に隠せる限界まで検索品質へ時間を配分**する。

検索器側が探索量を選ぶ理由もシステム的である。検索サーバーは複数の生成器から同時に問い合わせを受ける可能性があり、現在の検索負荷は生成器からは分からない。検索器が自身の負荷と性能を観測して調整する方が、各生成器が独立に検索間隔を変えるより柔軟である。ただし原著の実測では特定の検索サーバー構成を用いており、多テナント負荷への追随を網羅的に保証するものではない。

### 5. 実装と一要求の処理順

開始時には最初の検索窓で通常検索を実行する。その結果を使ってGPUが次のトークン区間を生成し始めると、検索器は既に確定した少し古い窓から次区間向け検索を先行する。検索器は推論時間の見積もりから探索範囲を決め、結果を生成器へ送る。生成器は古い検索窓に合わせた注意領域で結果を統合し、次の区間を生成する。この流れを繰り返す。

原著のGPU推論にはONNX Runtimeを使い、元のPyTorch版RETROからKV状態のキャッシュなども加えた。検索器はCPU上のFaissで、二装置間はgRPCで通信する。従って2.6倍という値は、同一論文内のRETRO基準に対するシステム構成・検索制御の比較であり、ONNXとPyTorchの速度差をそのままPipeRAG固有の効果として二重計上してはならない。公開された公式実装には推論クライアント、検索サーバー、性能モデル、困惑度評価と作図の各コードがある。

## 評価結果

### 1. 同じ品質を満たす端から端遅延

図6の遅延と困惑度のパレート曲線では、PipeRAGはRETROより良好な領域を形成する。RETROの`nprobe`を大きくして品質を改善しようとすると検索時間が増え、そのまま生成遅延へ加算される。PipeRAGでは検索時間の多くを生成と重ねるため、同じ困惑度を達成する際に最大2.6倍の遅延短縮が得られた。逆に同じ遅延を許す場合には、より短い検索間隔と広い探索範囲を使い、困惑度を最大0.93ポイント下げられる。

ここで2.6倍は「トークン生成器単体の行列積が2.6倍速くなった」ことを意味しない。検索・生成・ネットワーク・交差注意を含む端から端の比較である。さらに最大値は特定の検索条件の結果であり、すべての検索間隔・データセットで同じ速度倍率ではない。

### 2. 性能モデル駆動検索と検索なし・RETROの比較（原著表1）

|データ|検索なし：時間/PPL|RETRO：時間/PPL|PipeRAG性能モデル駆動：時間/PPL|
|---|---|---|---|
|Wikipedia|9.35秒 / 16.74|14.59秒 / 13.49|10.34秒 / 13.47|
|RealNews|9.35秒 / 17.37|12.36秒 / 14.94|10.58秒 / 14.87|
|C4|9.35秒 / 24.18|11.13秒 / 19.48|10.58秒 / 19.36|

Wikipediaでは検索なしの9.35秒に対してPipeRAGは10.34秒で、遅延増は約10.6%である。一方、PPLは16.74から13.47へ3.27低下する。RealNewsでは遅延が9.35秒から10.58秒（約13.2%増）となる代わりにPPLが17.37から14.87へ2.50改善する。C4でも同じ10.58秒でPPLが24.18から19.36へ4.82改善する。RETROの同じデータの時間はそれぞれ14.59、12.36、11.13秒で、PipeRAGは品質を保ちながら待機を減らす。

検索なしの9.35秒とPipeRAGの10秒台には差が残る。原著は主に検索結果をモデルへ統合する交差注意などの追加演算を理由として挙げる。つまり検索を完全に無料化したわけではない。またWikipediaのRETRO PPL13.49とPipeRAG13.47の差は0.02と小さく、速度差に比べて品質差が小さい条件もある。改善量を常に大きな品質向上と表現するのは不適切である。

### 3. 短い検索間隔による品質改善とRetro+の対照

図5では検索範囲を広げるほど一般にPPLが下がり、32トークン以下の検索間隔でPipeRAGがRETROより良好な品質を示す。短い間隔は生成文脈の変化に早く追随できる反面、検索回数が増える。そこで原著は、PipeRAGと同じ可変検索間隔用の注意機構を持つが検索と生成を逐次実行するRetro+を比較した。図8ではRetro+が同程度のPPLを得ても、同じPPLのPipeRAGの方が生成遅延を短縮する。

この対照により、品質改善の一部は注意構造と検索間隔の変更、速度改善の主要部分は検索と生成の重畳という役割を分離できる。単に「検索間隔を短くしたから高速化した」という説明ではない。短い間隔を逐次方式へ追加するだけなら検索待ちが増え、むしろ遅くなる可能性がある。

### 4. データベース規模と検索範囲の感度

図4はデータベース規模を変え、検索なし、初回のみ検索、RETRO、PipeRAGを比較する。全データセットで検索なしのPPLが最も悪く、初回のみ検索は定期検索より悪い。データベースを大きくすると、より適切な近傍が得られてPPLが下がる傾向がある。ただしデータベース規模が増えると検索のメモリ使用量・走査費用も増えるため、性能モデルと索引の構成を更新する必要がある。

`nprobe`を大きくすると探索範囲が増え、検索結果の品質は改善しやすいが、推論の時間予算を超えると待機が再び現れる。PipeRAGは現在のGPU生成時間を使って最大探索量を選ぶため、単純な固定探索幅より効率的なパレート曲線を得る。ここで評価しているのは近似検索の品質を言語モデルPPLで測った結果であり、検索器単体の再現率が何ポイント改善したかと混同してはならない。

### 5. ハードウェアが変わった場合の負の感度

図7と付録Cは、推論装置だけ、または検索装置だけを4倍・16倍速くした仮想条件をモデル化する。どちらか一方だけが桁違いに速くなると、PipeRAGとRETROの差は縮小する。並列化で節約できるのは重なっている時間であり、二処理の所要時間が近いほどその割合が大きいからである。逆に片方が極端に遅いと、速い方の仕事をすべて隠しても遅い方が律速となる。

この評価は新しい16倍高速ハードウェアを実際に用意した測定ではなく、原著の性能モデルによる将来構成の推定である。現代の高性能GPU、専用ベクトル検索アクセラレータ、共有GPU上の検索器などにそのまま数値を当てはめられない。検索装置と生成装置の実測時間を再プロファイルすることが前提になる。

## 既存研究との差

RETROは定期検索した結果を区間交差注意で生成へ統合するが、検索と生成が逐次依存する。PipeRAGは検索窓を前へずらして次区間の検索を先行させ、待ち時間を重ねる。これは初回のみ検索する一般的なRAGと異なり、生成中の話題変化へ追随する機構を残したまま待機を減らす点に価値がある。

kNN-LMのようなトークンごとの検索方式は検索間隔が1であり、検索対象も言語モデルの内部状態に近い。PipeRAGはRETROのトークン区間検索と交差注意を前提にするため、任意の外部API型RAGに変更なしで適用できるわけではない。Chameleonなどの検索アクセラレータ研究は検索器側の演算・転送を高速化するのに対し、PipeRAGは検索器が別装置にある状況で二つの仕事の時間的な重畳を最適化する。両者は相補的だが、原著は複合した速度改善を実証していない。

## 限界・負の結果

先行検索には、現在の生成区間より古い検索窓を使うという本質的な近似がある。生成中に話題が突然変わる場合、最新文脈で検索した場合と異なる資料を取得し、PPLや生成内容が悪化する可能性がある。短い検索間隔は古さを減らすが、検索器の負荷と通信回数を増やす。従ってすべての生成分布で品質非劣化を保証する方式ではない。

パイプライン化の利得は検索と推論の時間比に依存する。片方だけ16倍高速になる将来ハードウェアの推定では相対的な改善幅が縮む。性能モデルは実機での事前測定に基づき、GPUの混雑、検索器の同時問い合わせ、ネットワーク遅延の変動が大きい場合は予測が外れ得る。検索を先行しても結果が遅れれば待機は残る。

主要評価は582M RETRO、FP32、A100 40GB、CPU検索サーバー、英語文書のPPLであり、現在の7B～70B級デコーダ専用LLM、MoE、長文対話、多数ユーザーの本番サービングで同じ2.6倍が得られるとは示されていない。主な品質指標は困惑度であり、事実性、回答の根拠、検索文書の引用精度を人手評価したものではない。遅延は1024トークン生成の5回測定中央値で、P95/P99の要求遅延や大規模負荷でのサービス水準目標（SLO）は主要結果に含まれない。

検索なしの9.35秒に対して性能モデル駆動PipeRAGは10.34～10.58秒であり、検索結果の統合演算を完全には隠せない。Retro+との対照では可変検索間隔だけで同じ品質を得ても、逐次実行の待ちが残る。従って本論文の成果は「検索を無料にした」「検索器単体を2.6倍高速化した」ことではなく、検索品質へ割り当てる時間と生成の並列性を協調させた点にある。
