# Fairness in Serving Large Language Models

> clientごとに入力・出力tokenへ重み付けしたservice量を追跡し、最もserviceの少ないclientを優先するVirtual Token Counterで、continuous batchingを止めずに公平性を保証するLLM serving scheduler。

## 概要

LLM servingではrequest数だけを公平にしても、短いchatと長いdocument requestでは実際に消費する計算量が大きく異なる。またoutput lengthは実行前に確定しないため、通常のjob-size-aware schedulerをそのまま適用しにくい。

既存serviceでよく使われるrequests-per-minute型のrate limitは、client間の独占を抑えられる一方、systemに空きがあっても上限以上をserveしないためwork-conservingではない。

本論文はLLM servingにおける「service量」を入力tokenと出力tokenの重み付きcostとして定義し、各clientが受けた累積serviceをvirtual counterとして追跡する **Virtual Token Counter（VTC）** を提案する。

## 問題設定

公平性の対象はrequest単位ではなくclient単位である。同じclientは複数requestを持てるため、schedulerは「queue内で最も古いrequest」ではなく、各clientがこれまでどれだけ計算資源を受け取ったかを考慮する必要がある。

さらにLLM servingには次の制約がある。

- input lengthは到着時に分かるがoutput lengthは生成終了まで分からない
- continuous batchingではrunning requestとnew requestが同じiterationへ混在する
- KV cache容量の制約により、単純に全clientを同時実行できない
- 公平性のためにGPUを意図的にidleにするとthroughputが大きく落ちる

したがって、未来のrequest長を正確に予測せず、実際に消費したserviceを逐次accountingする必要がある。

## 手法

### 1. Tokenベースのservice cost

requestのservice量を、入力token数と生成済みoutput token数の重み付き和として扱う。prefillとdecodeのcost差を反映できるよう入力・出力tokenには別weightを設定できる。

より一般には、単純な線形token数に限らず、profilingした実行cost関数へ置き換えられるよう定式化している。

### 2. ClientごとのVirtual Token Counter

各clientにcounterを持たせ、requestがserviceを受けるたびにそのcostをcounterへ加える。

新しいrequestをbatchへ入れる際は、**現在counterが最も小さいclientを優先する**。これにより大量requestを送るclientでも、他clientより大きく先行してserviceを受け続けることを防ぐ。

### 3. Returning clientのcounter補正

しばらくrequestを送っていなかったclientのcounterを古い小さい値のまま残すと、復帰直後に大量の優先serviceを受けてしまう。

VTCはactive client群のcounter水準に合わせて復帰clientのcounterを補正し、過去のidle時間をcreditとして蓄積しないようにする。

### 4. Work-conserving scheduling

VTCは公平性を守るために空きGPU slotを意図的に捨てない。serve可能なrequestがある限りbatchを埋めるため、固定RPM制限のようなcapacity浪費を避ける。

論文では、同時にbackloggedな2 client間のservice差に対して **2×のtight upper bound** を証明している。

### 5. Weighted fairness

clientごとに異なるweightを与える拡張も示す。例えばweight 1:2:3:4を設定すれば、長時間では各clientが概ねその比率でserviceを受けるよう制御できる。

## 評価

### 条件

主な実機評価では以下を使用する。

| 項目 | 条件 |
|---|---|
| Model | Llama-2-7B |
| GPU | NVIDIA A10G 24GB |
| KV cache pool | 10,000 tokens |
| Backend | S-LoRA / LightLLM系serving engine |
| Workload | synthetic workloads、LMSYS Chatbot Arena trace |
| Baselines | FCFS、Round-Robin系、request-rate-limit系など |

### 主な結果

synthetic workloadでは、VTCだけが論文で定義した複数のfairness条件を一貫して満たし、他baselineはいずれかのcaseでclient間service差が大きくなることを示す。

実traceでも、単純FCFSとほぼ同程度のGPU利用・throughputを維持しながら、client間の累積service差を大幅に抑える。

論文の実験設定を再現した報告では、Llama-2-7B / A10Gのchat traceでVTCは約779 token/s、FCFSは約777 token/sとthroughputをほぼ維持しつつ、平均service differenceを433から252へ縮小している。一方、厳しい5-RPM制限ではthroughputが約340 token/sまで落ちる。

付録ではweight 1:2:3:4のweighted VTCが、4 clientへの累積serviceをほぼ設定比率どおりに分配できることも確認している。

## 既存研究との差

### FCFSとの違い

FCFSは到着順を守るだけで、client単位のresource consumptionを考慮しない。大量requestを送るclientや長いrequestが他clientを長時間待たせる可能性がある。

VTCはclientごとの累積serviceを基準にするため、request頻度やrequest sizeが異なる場合でもclient間のresource shareを制御できる。

### FastServeとの違い

FastServeはrequest単位のpriority / preemptionでaverage・tail latencyを下げることが主目的で、公平性の定義そのものを与える研究ではない。

VTCはclient単位のservice accountingと理論boundを主題とし、continuous batching engineの上にfairness policyとして追加できる。

### Orca / vLLMとの違い

OrcaやvLLMはbatchingとKV memory efficiencyを改善して総throughputを高める。VTCはそのようなengine上で「誰を次にbatchへ入れるか」を決めるpolicy layerであり、complementaryな関係にある。

## 限界

- token数をresource costのproxyにするため、長contextによるmemory bandwidth増加やmodel / hardware差を完全には表せない。
- prefix cache hitなどで実際に計算しなかったinput tokenも単純token costでは同じserviceとして数えてしまう。
- 主評価はLlama-2-7B / A10Gで、現代的なGQA / MLA modelや大規模multi-node servingではcost functionの再調整が必要になる。
- fairnessを改善しても個別requestのdeadlineやSLO達成を直接保証するわけではない。
- client identityをどう定義するか、複数accountやtenant hierarchyをどう扱うかは運用側のpolicyに依存する。

## 一般的な実装上の含意

LLM servingのfairnessは「1 request = 1 unit」と考えるより、**実際に消費した推論workをclient単位で逐次課金するscheduler**として設計した方が自然である。

output長の予測が難しくても、生成したtoken分だけcounterへ後払いで加算すればよいため、future length predictorなしでも公平制御が可能になる。

またVTC自体はbatching / kernel / memory managerを置き換えず、admission順序を変えるpolicyなので、vLLMのような既存continuous-batching runtimeへ比較的小さく追加できる。
