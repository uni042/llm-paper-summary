# Fairness in Serving Large Language Models

> clientごとの累積input / output token処理量を重み付きで追跡し、service量が少ないclientを優先してGPUを遊ばせず公平性を保つ。

## 問題
request数だけのrate limitでは、短いchatと長いdocument requestの計算量差を扱えず、空きcapacityがあっても上限によってGPUを遊ばせることがある。output lengthは実行前に不明で、continuous batchingではrunning requestと新規requestが同時に処理されるため、既存のjob-size-aware fair schedulerをそのまま適用しにくい。

## 手法
Virtual Token Counter（VTC）はrequestではなくclientごとにservice counterを持つ。input tokenと生成済みoutput tokenを重み付きcostとして逐次加算し、新しいrequestをbatchへ入れる際にcounterが小さいclientを優先する。output長を事前予測せず、実際に生成した分だけ後払いでaccountingできる。

inactiveだったclientが古い小さなcounterを保持して復帰時に過剰な優先権を得ないよう、active client群のcounter水準へ補正する。また処理可能なrequestがある限りGPU slotを空けないwork-conserving性を保つ。論文はbackloggedな2 client間のservice差にtightな2倍上界を示す。client weightを変えて異なるresource shareを与える拡張も扱う。

## 評価条件
主な実機評価はLlama-2-7B、NVIDIA A10G 24GB、10,000-token KV cache pool、S-LoRA / LightLLM系serving engineを使用し、synthetic workloadとLMSYS Chatbot Arena traceでFCFS、Round-Robin系、rate-limit系などと比較する。

## 主要結果
synthetic workloadではVTCが論文のfairness条件を一貫して満たし、実traceでもFCFSと近いGPU利用・throughputを維持しながらclient間service差を抑える。chat traceではVTC約779 token/s、FCFS約777 token/sとthroughputをほぼ維持し、平均service differenceを433から252へ縮小する一方、厳しい5-RPM制限ではthroughputが約340 token/sまで低下する。weighted設定では1:2:3:4のresource shareも追従する。

## 既存研究との差
FastServeなどがrequest latency最小化を主目的とするのに対し、VTCはclient単位のservice accountingと公平性保証を主題にする。OrcaやvLLMのcontinuous batching / KV memory managementを置き換えるのではなく、その上でadmission順序を決めるpolicy layerとして補完的に使える。

## 限界
- token数はresource costの代理であり、長contextのmemory bandwidth、model / hardware差、prefix cache hitなどを完全には表さない。
- 主評価はLlama-2-7B / A10Gで、現代的なGQA / MLA modelや大規模multi-node servingではcost functionの再調整が必要。
- fairness自体は個別requestのdeadlineやSLO達成を直接保証しない。
- client identityやtenant hierarchyの定義は運用policyに依存する。

## 実装状況
公式の再現用artifact `Ying1123/VTC-artifact` が公開され、S-LoRA / LightLLM系serving engine上にVTCと比較schedulerが実装されている。
