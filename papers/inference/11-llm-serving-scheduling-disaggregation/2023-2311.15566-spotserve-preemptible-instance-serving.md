# SpotServe: Serving Generative Large Language Models on Preemptible Instances

> 安価だが突然利用できなくなるspot GPUの増減に合わせてmodelの分割方法を組み替え、既存weightとKV cacheをできるだけ再利用してLLM servingを継続するsystem。

## 概要

cloudのspot / preemptible instanceは通常instanceより安いが、provider側の都合で途中回収される可能性がある。小さいmodelならrequestを別GPUへ送り直せばよいが、大規模LLMでは1 modelを複数GPUへ分割しているため、1台消えるだけで全体の配置を見直す必要がある。

SpotServeは、利用可能なGPU数が変わるたびに、**data parallelism / tensor parallelism / pipeline parallelismの組み方を変える**。その際、すでに各GPUにあるweightやKV cacheをなるべく使い回し、storageから全modelを読み直す時間を減らす。

さらにspot instanceが停止する前に短い予告時間がある場合、その時間で実行中requestのKVを別GPUへ移し、promptからやり直さず途中tokenからgenerationを再開する。

## 問題設定

spot GPUをLLM servingへ使うと、主に3つの問題がある。

1. **GPU数が変わるとmodelの分割方法も変える必要がある**
   - GPUが減れば今のtensor / pipeline構成が成立しなくなることがある。
   - GPUが増えても、古い構成のままでは追加GPUを使い切れない。

2. **modelを読み直す時間が長い**
   - 大規模weightをstorageから全GPUへ再配置すると、数十秒〜数分の停止につながる。

3. **実行中requestの進捗を失いたくない**
   - preemptionのたびにpromptからprefillし直すと、長context requestほど無駄が大きい。

## 手法

### 1. GPU数と負荷に合わせてmodelの分割を変える

controllerは現在使えるGPU数とrequest量を見て、data / tensor / pipeline parallelismの組合せとbatch sizeを選ぶ。

workloadが軽い時はlatencyを優先し、requestが増えた時はthroughputを高められる構成へ切り替える。

### 2. すでにあるweightをなるべく残す

新しい配置を作る時、すべてのGPUへweightを最初から読み直すのではなく、**旧配置と新配置で同じweightを持てるGPUを優先して対応付ける**。

論文ではこの対応付けを数理的に解き、移動するweight量を最小化する。重要なのはalgorithm名ではなく、**既存GPU上のdataを捨てずに再利用する配置を探す**点である。

### 3. model計算とdata移動を重ねる

modelを再配置する時も一斉停止しない。pipelineの後段など、まだ現在の計算で使わない部分から先に移し、GPU計算とweight / KV転送をできるだけ同時に進める。

### 4. 実行中requestを途中から再開する

spot instanceが停止する前の予告時間を使ってKV cacheを残るGPUへ移す。

新しいmodel配置が準備できたら、そのKVからdecodeを続けるため、prompt全体を再計算する必要がない。

## 評価

AWSのT4 GPUを最大48枚使い、OPT-6.7B、GPT-20B、LLaMA-30Bを評価した。実際のspot availability traceを再現して、GPUが増減する環境を作っている。

既存方式と比べてP99 latencyを最大**2.4〜9.1倍改善**したと報告する。

GPT-20Bでは、on-demand instanceだけを使う構成より**最大54%のcost削減**を報告し、その条件でaverage latency増加を18%未満に抑えた。

## 既存研究との差

### 通常のautoscalingとの違い

通常はreplica数を増減するだけだが、SpotServeでは1 modelが複数GPUへ分割されているため、**model内部の分割方法まで作り直す**。

### 単純なrequest reroutingとの違い

requestを別GPUへ最初から送り直すのではなく、weightとKVを再利用して途中から処理を続ける。

### Llumnixとの違い

Llumnixは基本的にmodel instanceの形を保ったままrequestを別instanceへ移す。SpotServeは**使えるGPU数そのものが変わることを前提に、model parallel構成まで変更する**。

## 限界

- 主評価はT4 clusterで、A100 / H100 / Blackwellではdata移動costの比率が変わる。
- spot価格と回収頻度はcloud / region / 時期に依存する。
- 停止前の予告時間がない突然の故障には、同じ方法でKVを退避できない。
- GPUの増減が頻繁すぎるとmodel再配置そのものが負荷になる。
- 各parallel構成の性能見積もりが必要。

## 一般的な実装上の含意

大規模LLMでは、GPU数の増減を単にreplica数だけで扱えない。modelを複数GPUへ分けている場合は、**GPU数に合わせてmodelの分割方法まで変える必要がある**。

また再配置を速くするには、現在各GPUがすでに持っているweightやKVを考慮し、移動量が少ない配置を選ぶことが重要になる。
