# SpotServe: Serving Generative Large Language Models on Preemptible Instances

> spot GPUの増減に合わせてdata / tensor / pipeline parallelismを動的に組み替え、既存weight・KVを最大限再利用するmigrationとtoken単位のstate recoveryで、安いpreemptible instance上のLLM servingを継続するsystem。

## 概要

SpotServeは、通常instanceより安価だがcloud providerから突然回収される**preemptible / spot GPU instance**だけでも大規模LLMをserveできるようにする研究である。

小規模DNNならinstanceが消えた時にrequestを別GPUへrerouteすればよいが、LLMは1 requestを複数GPUへmodel-parallelに分割するため、1台のpreemptionがpipeline全体へ影響する。また利用可能GPU数が変わるたびにmodelを一からreloadすると、巨大weightの読み込みだけで長時間停止する。

SpotServeは、利用可能GPU数とrequest loadに合わせて**data / tensor / pipeline parallelismの組合せをruntimeで変更**する。その際、旧配置と新配置の間でどのinstanceをどこへ再利用すればweightやKVの移動量が最小になるかを最適化し、さらにcloudのgrace period中に生成済みKVを別instanceへ移して、token単位で途中からgenerationを再開する。

つまり単なるspot VMのauto-scalingではなく、**model parallelism、parameter placement、KV state、request recoveryを一体でelastic化**するsystemである。

## 問題設定

spot instanceは通常instanceより大幅に安い一方、availabilityは時間とともに変化する。大規模LLM servingではこの変化が3つの問題を生む。

1. **Parallel configurationが固定できない**
   - ある時点で最適なtensor / pipeline / data parallel構成が、GPU台数減少後には実行不能になる。
   - GPUが増えた時も、古い構成のままでは追加resourceをthroughputへ変換できない。

2. **Reparallelization時のmodel migrationが重い**
   - 新しい構成へ切り替えるたびに全weightをstorageからloadすると停止時間が大きい。
   - 論文では120B modelをAWS上でpersistent storageからloadすると2分超かかる例を示す。

3. **実行中requestの進捗を失いたくない**
   - preemptionでpipelineを捨て、別pipelineでpromptから再計算すると長context / 長outputほど無駄が大きい。

SpotServeはこの3つを、dynamic reparallelization・migration planning・stateful inference recoveryで解く。

## 手法

### 1. Dynamic reparallelization

controllerは現在のspot GPU availabilityとrequest arrival rateに対して、

- data parallel degree
- pipeline parallel degree
- tensor parallel degree
- batch size

の候補を評価し、throughput・latency・利用可能GPU数の制約を満たす構成を選ぶ。

単にGPU数が変わるたび固定ruleで再分割するのではなく、workloadが軽い時はlatency寄り、requestが積み上がる時はthroughputを確保できるparallel configurationへ切り替える。

### 2. Device mappingをgraph matchingとして最適化

parallel configurationを変えると、各GPUが保持すべきmodel shardも変わる。ただし旧GPUには新構成でも再利用できるweight shardが残っている場合がある。

SpotServeは旧instanceと新しいlogical device placementの対応付けを**bipartite graph matching**として表現し、Kuhn–Munkres algorithmで移動costが最小になるmappingを求める。

これによりすべてをstorageからloadし直すのではなく、すでに各GPUが持っているweight / stateを可能な限りそのまま使う。

### 3. Migration orderをpipeline executionと重ねる

新配置へ必要なweight / contextを動かす時も、一斉停止してからmigrationするのではない。

pipeline stageには実行順序があるため、まだ現在のrequest計算で使っていないstageから先にmigrationし、**model computationとstate transferをoverlap**させる。

### 4. Stateful inference recovery

AWS spot instanceなどは強制終了前に短いgrace periodを与える。SpotServeはこの時間を使い、request全体が終わるのを待つのではなく**生成済みtokenまでのKV cacheをcommit**する。

preemption対象GPU上のKVは、残るinstanceへjust-in-timeに移す。新parallel configurationが立ち上がった後は、そのKVからgenerationを続行できるため、promptからのfull recomputationを避ける。

request-level checkpointではなくtoken-level progressを利用する点がLLM特有の設計である。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Cloud | AWS |
| Instance | g4dn.12xlarge |
| GPU | 4× NVIDIA T4 / instance |
| Cluster | 最大12 instance、48 GPU |
| Network | 50Gbps TCP/IP |
| Models | OPT-6.7B、GPT-20B、LLaMA-30B |
| Availability | 実AWS g4dn spot availability traceを収集してreplay |
| Workload | stable / bursty synthetic + Microsoft公開MAF trace |

real 12-hour spot availability traceから異なる変動傾向を持つ20分区間を抽出し、同じavailability変化を実clusterでreplayする。

stable workloadのdefault arrival rateはOPT-6.7Bで1.5 req/s、GPT-20Bで0.35 req/s、LLaMA-30Bで0.2 req/s。bursty workloadではGamma arrival processも使用する。

### 主要結果

既存の`Reparallelization`型baselineと、preemptされたpipelineを捨てて別pipelineへrequestを送る`Rerouting`型baselineに対して、SpotServeは**P99 tail latencyを最大2.4〜9.1倍改善**したと報告する。

LLaMA-30Bのstable workloadでは、P99 latencyでReparallelization比約1.34〜2.43倍、Rerouting比約2.14〜9.13倍の改善を示した。

fluctuating MAF workloadでも、P99 tail latencyをReparallelization比最大2.94倍、Rerouting比最大1.73倍改善している。

### Monetary cost

GPT-20Bの比較では、on-demandだけを使う構成と比べて**最大54%のmonetary cost削減**を報告した。その条件ではaverage latency増加を18%未満に抑えている。

spot価格とon-demand価格の差が大きいcloud / instance typeほどcost advantageは大きくなる。

### Ablation

parallelization controller、migration planner、state recoveryを順に外すとtail latencyが悪化する。migration plannerは単にtransferを速くするだけでなく、GPT-20Bをserveできるminimum GPU数を16から12へ下げ、選べるparallel configurationの範囲も広げた。

## 既存研究との差

### 固定parallel servingとの違い

通常のdistributed servingはGPU topologyとparallel configurationを長時間固定する。SpotServeは**resource availability自体が変化することを前提**に、model parallel structureをruntimeで作り替える。

### 単純reroutingとの違い

小規模DNN向けspot servingではpreemptされたrequestを別instanceへ送り直せるが、LLMではmodel shardとKV stateが複数GPUへ分散している。

SpotServeはpipelineごと捨てず、weightとKVを再利用しながらreparallelizeして、途中tokenからrequestを再開する。

### Llumnixとの違い

Llumnixは固定されたmodel instance群の間でrunning request / KVをlive migrationし、load imbalanceやfragmentationを修正する。

SpotServeはさらに下の**model parallel topology自体をGPU availabilityに応じて変更**する。request migrationよりresource elasticityとcost optimizationが主題である。

### Splitwise / DistServeとの違い

Splitwise / DistServeはprefillとdecodeに異なるresource poolを割り当てるが、基本的にはresource pool自体が存在し続ける前提で設計する。SpotServeはinstanceが突然消える環境でmodel placementを再構成する。

## 限界

- 主評価はT4 clusterとOPT / GPT / LLaMA初期世代で、A100/H100/Blackwellや高速NVLink fabricではmigration cost balanceが変わる。
- spot availabilityとprice advantageはcloud / region / 時期に依存するため、54% cost reductionが一般に保証されるわけではない。
- preemption前のgrace periodを利用するため、予告なしで即時消失するfailureには同じstateful recoveryを適用できない。
- model shard再配置はnetwork / storage bandwidthを消費し、頻繁すぎるpreemptionではmigration自体がserving capacityを圧迫する。
- parallel configuration探索には各model / hardware構成のperformance estimateが必要。
- 実験clusterは最大12 g4dn instanceで、より大規模なproduction clusterではcontroller / migration coordination overheadが変わり得る。

## 一般的な実装上の含意

elastic LLM servingでは、GPU数の増減を単に**replica countの増減**として扱うだけでは足りない。modelが複数GPUに跨る場合、resource变化に合わせてtensor / pipeline / data parallelismそのものを再設計する必要がある。

またreconfigurationを速くするには、移動data量だけでなく**現在どのGPUがどのweight / KVをすでに持っているか**を入力にしてmappingを決める方がよい。これはspot instanceに限らず、heterogeneous clusterやautoscalingにも一般化できる。

さらにautoregressive generationではtokenごとにprogressをcommitできるため、traditional request-level checkpointより細かいstate recoveryが可能である。
