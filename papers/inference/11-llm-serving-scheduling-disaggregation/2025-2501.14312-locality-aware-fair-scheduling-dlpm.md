# Locality-aware Fair Scheduling in LLM Serving

## 一文要約

clientごとのGPU利用量を公平に保ちつつ、**公平性が大きく崩れない範囲だけ実行順を入れ替えて、同じprefixを持つrequestを続けて処理しKV再利用を増やす**scheduler。複数GPUではさらにprefix localityとGPU間load balanceも同時に調整する。

## 問題設定

LLM servingでは、複数clientが同じGPUを共有するときに一部clientがresourceを独占しないようfairnessを保証したい。一方、同一・類似prefixを持つrequestを続けて処理すると、prefix KV cacheを共有してprefill計算とKV memoryを節約できる。

既存のVTCはclientごとの累積service量を追跡して公平に処理するが、prefix localityを見ないため、同じprefixを持つrequestをばらしてcache reuseを失いやすい。

逆にSGLangのLongest Prefix Match（LPM）のように「今のcacheと最も長いprefixを共有するrequest」を常に選ぶと、同じprefixを大量投入するclientがschedulerを占有し、他clientが長く待つ可能性がある。

分散servingではさらに、同じprefixを同じGPUへ寄せるほどcache reuseは増える一方、popular prefixが1 GPUへ集中してload imbalanceが悪化する。

したがって、

1. client間の公平性
2. prefix KV再利用
3. 複数GPU間のload balance

を同時に扱う必要がある。

## 手法

### 1. DLPM: 公平性の「許容ずれ」の範囲でprefixが近いrequestを選ぶ

VTC型fair schedulerでは、本来次に処理すべきclientは「これまで受けたservice量が少ないclient」で決まる。

DLPMはこの順序を完全固定せず、**client間のservice差が一定範囲以内なら、prefix KVを再利用しやすいrequestを先に選んでもよい**とする。

例えばclient Aが少しだけ多くGPUを使っていても、公平性の許容範囲を超えていなければ、現在cacheと長いprefixを共有するAの次requestを続けて処理できる。

これによりKV reuseを増やしつつ、特定clientが無制限に先行するのを防ぐ。

### 2. `deficit`は「公平な配分からどれだけ先行 / 遅延しているか」

論文のDeficit Longest Prefix Match（DLPM）でいう **deficit** は、各clientが理想的な公平配分に対して、どれだけserviceを受け過ぎ / 受け不足かを表す値である。

schedulerはこの差が設定範囲を超えないようにしながら、その中でLongest Prefix Matchを使う。

### 3. `quantum`で公平性とprefix reuseの強さを調整する

論文の **quantum** は、「公平な順序からどこまでずれてよいか」という許容量である。

- quantum小 → 実行順をあまり入れ替えられず、VTCに近い強いfairness
- quantum大 → prefixが近いrequestをまとめやすく、LPMに近い高cache reuse

となる。

つまりquantumは**公平性をどこまで緩めてcache localityへ振るかを直接調整するつまみ**である。

論文は、この許容範囲を設けてもclient間のservice差や待ち時間が無制限に広がらないことを理論的に示す。

### 4. D²LPM: 複数GPUではglobal routingにも同じ考えを使う

複数workerでは、各GPU内のrequest順序だけでなく、requestをどのGPUへ送るかも決める必要がある。

D²LPMはglobal dispatcher側にもdeficitを持たせ、

- client fairnessが大きく崩れない
- 既存prefix KVを持つGPUへできるだけ寄せる
- 特定GPUだけ混み過ぎない

ようにrequestを配置する。

同一prefixを1 GPUへ固定すればcache reuseは最大化できるがhotspotになる。round-robinで均等分配すればloadは揃うが、各GPUで同じprefixを再計算する。D²LPMはその中間を選ぶ。

## 評価と主要結果

論文はsingle-workerとdistributed servingの双方でVTC、LPMおよび既存のlocality-aware distributed schedulingと比較している。

主要な報告値は以下。

- DLPM / D²LPMはfairness boundを維持しながら、VTC比で**最大2.87× throughput**。
- locality-awareな既存distributed serving手法との比較では、client単位latencyを**最大7.18×削減**。
- quantumを変えることで、VTCに近いfairnessからLPMに近いthroughputまで連続的なtrade-offを作れる。

主な成果は単なる平均throughput向上ではなく、**prefix reuseのためにrequest順序を変えても、client間のresource shareが無制限に偏らない範囲を明示した**点にある。

## 既存研究との差

### Fairness in Serving Large Language Models / VTC

VTCは入力・出力tokenに基づく累積serviceをclientごとに数え、公平に処理する。ただしrequest間のprefix関係を考慮しない。

DLPMはVTCのfairness accountingを引き継ぎつつ、**一定範囲だけdispatch順を緩めてprefix reuseを取り込む**follow-upと位置づけられる。

### SGLang / LPM

SGLangのprefix-aware schedulingはKV reuseを増やせるが、client isolationを目的としていない。

DLPMはLPMをfairness constraintの内側で使うことで、locality-only schedulerによる長期的なclient starvationを防ぐ。

### Preble

Prebleはdistributed servingでprefix reuseとGPU load balanceを共同最適化する。D²LPMはさらに**client間fairnessを制約として追加**し、3者のtrade-offを扱う。

## 実装上の含意

prefix cachingを持つserving engineでは、cache eviction policyだけでなく**request ordering自体をfairness accountingと共同設計する価値がある**。

agent、Tree-of-Thought、MCTS、multi-turn conversationなど、同一clientが長い共通prefixを繰り返すworkloadでは、厳密にclientを交互実行するとprefix reuseを壊しやすい。

逆にlocalityだけを最大化すると、長い共通prefixを大量に持つclientが有利になる。そのためmulti-tenant servingでは、prefix hit率を単独で最大化するより、**clientごとの累積service差へ上限を置いた上でlocalityを最大化する**方が安全である。

## 限界

- fairnessとlocalityのtrade-offはquantum設定に依存し、workloadに対して適切な値を選ぶ必要がある。
- prefix sharingが少ないworkloadではlocality-aware schedulingの利益自体が小さい。
- fairnessは主としてresource service量に対する保証であり、application-level job completion timeやagent workflow全体のcritical pathを直接最適化するものではない。
- arXiv v1時点の研究であり、確認時点では会議最終版への更新は確認できていない。
