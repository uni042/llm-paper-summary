# Niyama: Breaking the Silos of LLM Inference Serving

> 対話・コード補完・要約などを「対話型」「バッチ型」の別GPU群へ固定せず、要求ごとの細かなサービス品質（Quality of Service; QoS）期限を同じGPUプールで扱う配信系。Niyamaはデコード要求の締切余裕を見ながらプリフィルの分割サイズを動的に変え、期限優先と残り仕事量優先を混ぜ、過負荷時には少数要求だけを低優先度へ降格する。固定QoSではサイロ型より最大32%高い配信容量を示す。

## 概要

LLM配信ではコード補完のように数百ミリ秒級の反応を要求する用途と、要約のようにより長い遅延を許容できる用途が同居する。従来はこれらを「対話型」と「バッチ型」の別GPUクラスタへ分けることが多いが、時間帯で要求比率が変わると片方のGPUが遊休し、もう片方だけが過負荷になる。

Niyamaはこのサイロをやめ、各要求に具体的な遅延目標を持たせて共有GPU上で共スケジューリングする。単に期限の早い要求を先に処理するだけではなく、プリフィルを何トークンずつ実行するか、デコードをどれだけ優先するか、過負荷時にどの要求を保護するかまで一体で制御する。

中心となる三機構は、デコードの締切余裕から安全なプリフィルチャンクを決める動的チャンク化、最早締切優先（Earliest Deadline First; EDF）と最短残りプリフィル優先（Shortest Remaining Prefill First; SRPF）の間を負荷に応じて調整するハイブリッド優先度、そして既にSLO違反がほぼ避けられない要求を低優先度キューへ移す選択的降格である。

Llama-3-8BやQwen系をA100上で、Azure由来コード・対話トレースとShareGPTを用いて評価し、同じQoSを満たすために必要なGPU数をサイロ型より13〜32%削減する。共有クラスタの最大配信容量では最大32%改善し、極端な突発負荷では従来方式の連鎖的な締切違反を約1桁減らす。

## 問題設定

サイロ型配備では、各QoSクラスのピークへ別々にGPUを確保する必要がある。対話要求が少ない時間でも対話用GPUをバッチ処理へ即座に融通できず、逆方向も同じである。負荷比率が変わるたびにクラスタ単位で再配置するのは、要求単位の共スケジューリングより粗く遅い。

共有GPUへ単純に要求を混ぜるだけでも問題は解けない。プリフィルは大量トークンを並列計算できるので大きなチャンクほどスループットが高いが、長いプリフィルを一度に実行すると、その間にデコード中要求の次トークンが待たされ、トークン間遅延（Time Per Output Token; TPOT）のSLOを破る。

逆にプリフィルチャンクを常に小さく固定すればデコードへ頻繁に制御を返せるが、カーネル起動や小バッチ化でGPU効率が落ちる。したがって「現在のデコード要求があとどれだけ待てるか」を計算し、その余裕をプリフィルへ貸す必要がある。

また過負荷では全要求を守ること自体が不可能になる。先着順（FCFS）は全員を均等に遅らせ、EDFは既に間に合わない要求を救おうとして後続の多数要求まで巻き込む場合がある。Niyamaはこの状況で少数の違反を意図的に隔離し、残りの要求を保護する。

## 手法

### 1. 細粒度QoSを要求ごとに持つ

各アプリケーションは、粗いinteractive/batchラベルではなく、最初のトークンまでの時間（Time To First Token; TTFT）やトークン間遅延など具体的な期限を指定する。スケジューラは要求の到着時刻、残りプリフィル量、生成中のデコード期限と合わせて現在の余裕を計算する。

これにより「バッチ要求だから常に後回し」ではなく、同じアプリ種類でも期限が厳しい要求と余裕のある要求を区別できる。共有クラスタで余ったQoS余裕を別クラスの仕事へ使えることがサイロ解消の前提になる。

### 2. 動的チャンク化でデコード締切までの空きをプリフィルへ使う

Sarathi-Serve型のチャンクプリフィルでは、長い入力を複数回に分け、デコードと同じ反復へ混ぜられる。固定チャンクでは安全側の小さなサイズを選ぶ必要があるが、実際には同時実行中のデコード要求数や残り締切により使える時間は毎回異なる。

NiyamaはLLM推論時間が入力トークン数などから比較的予測しやすい性質を利用する。論文ではVidurのシミュレーションプロファイルから学習した軽量なランダムフォレストで、候補チャンクを実行した場合の時間を見積もる。

現在のデコード要求が次の期限へ達する前に終えられる範囲でチャンクを大きくする。負荷が低いときは大きなプリフィルをまとめてGPU効率を上げ、締切が近いデコードが多いときは小さく切って割込み性を高める。

### 3. ハイブリッド優先度で期限と残り仕事量を両立する

EDFは期限保護に強い一方、長いプリフィル要求が前に来るとGPUを長く占有する。SRPFは残りプリフィルが短い要求を先に終わらせてスループットを上げやすいが、期限の厳しい長要求を飢餓させる可能性がある。

Niyamaは両者の順位をパラメータαで混ぜたハイブリッド優先度を使う。低負荷では期限を守るEDF寄りの挙動を取り、高負荷ではSRPF成分を強め、短い仕事を流してキュー滞留を抑える。

入力は各要求の締切と残りプリフィル量、出力は次の反復で実行する要求順序である。動的チャンク化と接続することで、「誰を先にするか」と「その要求をどこまで進めるか」を別々ではなく同じ反復で制御する。

### 4. 選択的降格で過負荷の連鎖を止める

負荷が物理容量を超えると、全要求のSLOを守るスケジュールは存在しない。このとき既に大幅な違反が見込まれる要求を高優先度のまま残すと、その一件を救うためのGPU時間で多数の後続要求も違反する。

Niyamaは一部の要求を低優先度の降格キューへ早めに移す。通常キューはまだSLOを守れる要求に集中し、降格要求は余裕ができたとき処理する。報告では約5%程度の要求を意図的に降格することで、極端な負荷時の違反拡大を抑える。

これは要求を破棄する方式ではなく優先度を落とす方式である。ただし降格された要求のQoSは犠牲になるため、「全員を少し悪化」ではなく「少数を大きく遅らせて多数を守る」というサービス方針を許容できることが前提になる。

## 評価

### 主な評価条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA A100 80GBを中心とする実機評価 |
| モデル | Llama-3-8B（単一A100）、Qwen系7B（2 GPUテンソル並列）等 |
| ワークロード | Azure-Code、Azure-Conv、ShareGPT |
| QoS | 複数の遅延ティアを同じ要求流へ混在 |
| 基盤 | Sarathi-Serve系チャンクプリフィル |
| 比較 | サイロ型配備、Sarathi-FCFS、Sarathi-EDF等 |
| 主要指標 | 固定QoSで必要なGPU数、goodput、SLO違反率、負荷耐性 |

### 代表結果

| 条件 | 比較対象 | Niyama | 読み取れること |
|---|---|---:|---|
| 固定交通量・同一QoS | サイロ型 | 必要A100を13〜32%削減 | QoSクラス間の遊休GPUを共有できる |
| 最大配信容量 | サイロ型 | 最大32%増 | 粗いクラスタ分割より一つの共有スケジューラが高密度 |
| 共有クラスタgoodput | Sarathi-FCFS | 1.5〜2.4倍 | QoSを無視した到着順より有効仕事を多く完了 |
| 共有クラスタgoodput | Sarathi-EDF | 20〜40%増 | 期限だけでなく残り仕事量とチャンクを考慮する効果 |
| 違反なしで耐えられる負荷 | Sarathi-EDF | 最大30%増 | 動的チャンクとハイブリッド優先度で余裕を回収 |
| 極端な突発負荷 | 従来戦略 | SLO違反を約1桁削減 | 選択的降格が連鎖的なdeadline missを隔離 |

容量向上と過負荷時の違反削減は異なる評価場面で得られた結果である。32%の値を「すべてのトレースで一律32%速い」と解釈してはいけない。Figure 1のサイロ比較でもAzure-CodeとAzure-Convで改善幅は約12〜32%と変動する。

## 既存研究との差

Sarathi-Serveはプリフィルを分割してデコードとの干渉を抑える基盤を提供するが、NiyamaはチャンクサイズをQoS余裕に応じて動かし、異種QoSを同じGPUへ共配置する。固定チャンクの効率と期限保護の交換条件をオンライン制御へ変える点が追加される。

EDFのような期限スケジューリングだけでも、SRPFのようなスループット志向だけでも全負荷域をうまく扱えないという観察から、両者を連続的に混ぜる。さらに処理能力を超えた領域ではスケジューリングだけで全要求を救おうとせず、選択的降格という明示的な過負荷モードを持つ。

## 限界・実装状況

動的チャンク化は実行時間予測の精度に依存し、GPU・モデル・入力分布が変わればプロファイルの再取得が必要になる。論文の主評価はA100系と限られたモデル・トレースであり、H100等の異なるカーネル比率で同じ改善幅になるとは限らない。

選択的降格は過負荷時に少数要求のQoSを意図的に犠牲にするため、要求間の公平性や契約上の優先クラスをどう扱うかは配備ポリシーと結び付く。すべての要求を同一に保護する必要があるサービスでは使いにくい。
