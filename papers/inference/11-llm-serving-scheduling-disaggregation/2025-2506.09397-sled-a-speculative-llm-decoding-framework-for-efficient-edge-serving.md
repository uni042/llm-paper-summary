# SLED：異種エッジ端末の草稿生成と共有サーバー検証による分散投機的復号

## 概要

SLEDは、各エッジ端末に置いた小型言語モデルで草稿トークンを生成し、近傍の共有エッジサーバーに置いた大型目標モデルが複数端末の草稿をまとめて検証する分散推論基盤である。通常の投機的復号（speculative decoding）は、小型モデルが複数候補を提案し、大型モデルが一回の前向き計算で受理・棄却を判定する。SLEDの焦点は、この二段階を単一GPU内で完結させず、計算能力とメモリ容量が異なる多数の端末と一台の共有サーバーへ分離することにある。

端末は各自の計算資源に合う草稿モデルを選び、サーバーは一つの大きな目標モデルを共有する。端末側は草稿の信頼度で検証を依頼するタイミングを調節し、サーバーは複数要求をバッチ化してGPUの利用率を高める。Raspberry Pi 4B/5、NVIDIA Jetson Orin NanoとA100 4基を使う評価では、中央集約型の大型モデル単独サービングと比べてシステム容量約2.6〜2.9倍、システム全体の検証済みトークン生成率が最大約2.2倍と報告される。数値は端末の草稿生成速度と到着過程を組み合わせたシステム評価を含み、任意のネットワーク・端末構成で保証される速度ではない。

重要な制約は通信障害時の振る舞いである。正常な検証が行われる間は元の目標モデルの出力分布を保つ投機的復号を使えるが、SLEDは連続した検証失敗後に**未検証のローカル草稿を利用者へ返す退避動作**を持つ。原著のGSM8K評価では通信損失が増えると品質が小型モデルの水準へ近づく。したがって「SLEDは常に品質劣化ゼロ」とは解釈できない。

## 問題設定：端末側だけでも中央サーバーだけでも非効率

高性能な大型言語モデルを端末へ完全配置すると、重み・活性値・鍵値キャッシュの容量や計算量が、Raspberry Piなどの低電力機器では過大になる。強い量子化や枝刈りはメモリ負担を減らせるが、精度を失う可能性がある。逆に全生成をサーバーへ委ねる方式では、端末側の計算資源が遊休になり、大型GPUがすべての逐次生成を処理するため高い利用料金と同時要求数の制約が生じる。

モデル層を複数端末へ分割する方式も、端末間の帯域や遅延が不均一なときには同期が難しい。SLEDは層単位の分割ではなく、トークン生成の**草稿段階と検証段階**を分ける。小型モデルで安価にできる処理は端末に残し、大型モデルにしかできない出力品質の確定だけをサーバーに集中させることで、サーバーGPUの時間を多数の要求で共有する。

この設計では、端末からサーバーへ渡すのは主にプロンプト・草稿トークンであり、巨大な中間活性値を逐次転送する層分割方式とは通信内容が異なる。ただしネットワーク往復は残り、検証要求の頻度、草稿の受理率、同時端末数、バッチ待機時間の調整が重要になる。

## 手法：端末の動的草稿とサーバーの一括検証

### 1. 端末ごとに小型草稿モデルを配置する

各端末は利用者の入力をトークン化し、端末の処理能力に合わせた小型モデルで複数の次トークンを提案する。例えば計算能力が小さいRaspberry Piと、GPUを備えるJetsonでは同じ草稿モデルを強制せず、異なるモデルを選択できる。サーバーには高精度な目標モデルを一つ配置し、全端末の検証要求を集約する。

この構成の重要な互換条件は**端末の草稿モデルとサーバーの目標モデルが同じトークン化器を共有すること**である。トークンIDの意味が異なれば、端末の提案した列をそのまま目標モデルの条件付き分布で検証できない。モデル規模の違いは許容されるが、任意の別語彙モデルを無変換で混在できるという意味ではない。

### 2. 元モデルの分布を保つ受理・修正

端末の草稿モデルが提案したトークン $\tilde x$ について、目標モデルの条件付き確率を $p_{\mathrm{target}}$、草稿モデルの条件付き確率を $p_{\mathrm{draft}}$ とすると、原著は標準的な投機的サンプリングの受理確率を

$$\alpha=\min\left(1,\frac{p_{\mathrm{target}}(\tilde x\mid x_{1:n})}{p_{\mathrm{draft}}(\tilde x\mid x_{1:n})}\right)$$

と記す。棄却したときは二つの分布の差に基づく補正分布から再サンプリングする。この受理・補正を正しく実施した場合、草稿モデルの品質が低くても最終的な出力分布は目標モデルに一致する。草稿モデルの役割は正解の確定ではなく、目標モデルが一度に検証できる候補を安価に供給することにある。

サーバーは棄却位置と修正トークンを端末へ返し、端末は確定した接頭辞を基準に次の草稿を作る。単に小型モデルの出力を大型モデルが採点するだけではなく、棄却後の補正まで含むことが分布保存の条件である。

### 3. 草稿信頼度に基づく動的な検証依頼

端末で生成した各草稿トークンには、小型モデルの出力ロジットから得られる信頼度 $c_i$ がある。著者は草稿信頼度と大型モデルによる受理率に相関があることを観測し、経験的に設定する閾値 $c_{\mathrm{th}}$ と比較する。$c_i\ge c_{\mathrm{th}}$ の間は端末が次の草稿トークンを生成し、$c_i<c_{\mathrm{th}}$ になった時点でサーバーへ検証を依頼する。固定長で頻繁に検証するより、見込みの高い連続列を長く提案し、無駄なネットワーク往復を減らす狙いがある。

閾値は理論上の普遍定数ではなく、草稿モデルと負荷条件に合わせて決める経験的な値である。信頼度が高くても目標モデルが受理するとは限らず、草稿が長すぎれば検証費用が増える。著者は後述の実験で、草稿長を伸ばすと端末あたりの生成速度とサーバーが支えられる端末数が逆方向に動くことを確認した。

### 4. 非同期草稿生成、タイムアウト、退避動作

検証要求を送った端末は、サーバーの返答を待つ間にも小型モデルで後続の草稿を生成できる。先に送った草稿がすべて受理された場合、その間に用意した続きを次の検証待ち列へつなげられるため、通信待ち時間を端末計算で隠蔽できる。通信が遅延した場合はタイマーに従い、草稿を再度まとめて検証する。

ただし通信が連続して失敗した場合、SLEDは応答性を優先して未検証のローカル草稿を利用者へ出す。これは分布保存型の投機的復号とは**別の縮退モード**であり、元の大型モデルと同じ品質を保証しない。ネットワーク断でも何らかの回答を返せることと、大型モデルによる検証済み回答を返せることを混同してはならない。

### 5. サーバー側の静的バッチ化

サーバーは端末から届く検証要求を待ち行列に蓄積し、一定数に達したらバッチ計画器がまとめる。現在の試作では**静的バッチ化**を使い、要求ごとに長さの異なるトークン列をパディングして一つの検証バッチへ変換する。大型モデルは同じ重みを共有し、GPUの並列処理で複数端末の候補を検証する。これにより個々の端末が大型モデルを保持する必要がなくなる。

静的バッチには待ち時間とパディングによる計算浪費が残る。入力長・草稿長が大きく異なる要求を集めると、短い要求も長い要求に合わせる必要がある。著者はより高度な鍵値キャッシュ管理や資源認識型検証制御を将来課題として挙げており、これらがすでに完成した最適化として実装されているわけではない。

## 評価条件と比較対象

論文は研究構想を含む短報（position paper）であり、実測した端末の草稿生成速度を使ったシステム負荷のモデル化と、実機の試作測定を組み合わせる。端末にはRaspberry Pi 4B、Raspberry Pi 5、Jetson Orin Nano、検証サーバーにはNVIDIA A100を4基使用する。Llama系列の1B・3Bを草稿側、11B・70Bを目標側に用いる条件を扱い、最大128Kの文脈長に対応する構成を記す。端末からの検証要求の到着間隔はポアソン過程に対応する指数分布としてモデル化し、各端末の要求率には実機の草稿速度を用いる。

比較は、サーバーの大型モデルがすべてのトークンを逐次生成する中央集約型、端末だけで小型モデルを実行する端末単独型、端末草稿と共有サーバー検証を組み合わせるSLEDの三方式である。評価指標は、システム全体の検証済みトークン生成率（Whole System Token Generation Rate、WSTGR）、目標応答速度を維持しながら支えられる端末数、端末あたりの生成率、1,000トークン当たりの費用、通信損失時の生成率と品質である。これらは異なる指標であり、「スループット2.2倍」と「容量2.8倍」は同じ測定ではない。

## 主要結果

### システム容量：同じ応答速度で何台を支えられるか

原著表1では、同じ目標応答速度を保てる最大端末数の比較が示される。

| 端末種類 | SLEDの容量 | 中央集約型の容量 | 容量比 |
|---|---:|---:|---:|
| Raspberry Pi 4B（llama.cpp） | 18.30 | 7.05 | 2.60倍 |
| Raspberry Pi 5（llama.cpp） | 5.24 | 1.83 | 2.86倍 |
| NVIDIA Jetson | 19.53 | 7.06 | 2.77倍 |

端末数が小数なのは物理的に端末を小数台配置する意味ではなく、システムモデルから求めた平均的な収容能力の指標である。三条件とも2.6〜2.9倍程度の容量改善があるが、端末性能によって絶対的な収容数は大きく異なる。

### システム全体の生成率と草稿長の交換関係

端末側にLlama 3Bを置いたRaspberry Pi 5からの要求負荷を使い、11Bまたは70Bの目標モデルをサーバーで検証する比較では、同じ目標モデル・端末数の中央集約型よりSLEDの全体生成率が高い。著者は最大約2.2倍の改善を主要結果として示す。GPUバッチを大きくすると固定起動費用が償却され、検証側の並列性が増すことが主な理由である。

一方、Raspberry Pi 5でLlama 1Bを使い草稿長を変える試験では、草稿を長くすると端末あたりの出力速度は下がるが、サーバーが支えられる端末数は増える傾向がある。長い草稿は一回の検証要求で多くの候補を送るため通信回数を減らすが、端末側の草稿生成とサーバーの検証が長引く。したがって端末の応答性を最大化する設定と、システムの総収容能力を最大化する設定は一致しない。

### 費用・スループットの同時比較

費用モデルは端末の購入価格を3年間・平均稼働率70%で償却し、電力料金を加えて1,000トークン当たりの費用へ換算する。Raspberry Pi 5は購入価格80米ドル、平均電力8W、電気料金0.083米ドル/kWhという仮定を使う。16・8・4ビット量子化と端末数1、2、4、8、16を比較し、費用と生成率のパレート前線を調べる。

原著は、同じ収容数・量子化条件の一例でSLEDが137トークン/秒、中央集約型比3.5倍の生成率で、費用は中央集約型の29%だったと記す。また4ビット・16端末のSLEDでは137トークン/秒、1,000トークン当たり0.13米ドルとなり、最良の端末単独構成より65%高い生成率を示した。これは**特定構成の費用モデル上の比較**であり、すべての条件で一律3.5倍や0.13米ドルになるという意味ではない。

### 通信損失と品質：無損失性の成立範囲

通信耐性の試作では、Raspberry Pi 5上のLlama-3.2-1B-Instructが草稿を生成し、A100側のLlama-3.1-70B-Instructが検証する。検証応答のパケット損失率を0〜100%で変えると、5〜10%程度以下の損失では端末生成率の悪化は通常2〜3%未満だった。検証応答が一切届かない場合でも、端末は小型モデルへ退避して少なくとも5.24トークン/秒の生成を継続した。

しかしGSM8Kの品質は、損失率10%未満では大型目標モデルに近い一方、10%から100%へ増えるにつれて小型草稿モデルの水準へ低下した。これは「通信断でも応答を継続する」という可用性と「目標モデルの出力分布を保存する」という品質保証が両立しない場合を実測した重要な負の結果である。分布保存が成立するのは、正しい受理・補正をサーバーで実行できたトークンに限られる。

## 構成要素の意味と制約

SLEDの主な利益は、端末に計算を分散して共有GPUの逐次生成負担を減らすこと、サーバー側のバッチ化で検証処理を集約すること、信頼度で検証頻度を調節することの組合せで生じる。端末側の草稿が遅い場合は、サーバーGPUが遊休になっても端末がボトルネックになり得る。反対に草稿が速くても、通信遅延やサーバー待ち行列が大きいと端末応答が遅くなる。静的バッチ化は実装が簡単だが、待機時間と長さ揃えの余剰計算を増やし得る。

原著の主要な容量値は実機性能を入力にした負荷モデルと測定の組合せであり、異種端末が多数ある任意の現場でそのまま再現されたわけではない。ネットワーク遅延の分布、端末ごとの要求混合、複数利用者の隔離、端末側とサーバー側の鍵値キャッシュ整合、草稿モデルの更新、トークン化器の互換性など、運用時に解くべき条件が残る。論文自体も、鍵値キャッシュ最適化、動的資源配分、マルチモーダル対応を今後の課題として挙げる。

小型端末での推論にllama.cppを利用した表があることは、SLED全体が既存のllama.cppだけで動くという意味ではない。実際の導入には、端末から草稿と確率情報を送る通信処理、サーバーでの目標モデル検証、受理・補正結果の返送、タイムアウトと縮退制御、異種要求のバッチ計画を追加実装する必要がある。特に通信断時に小型モデルの出力を許容するかどうかは、用途の品質要件で決めるべき設計選択である。

## 関連研究との比較

端末へ量子化済みの小型モデルだけを置く方式は、ネットワークなしで動作できるが、回答品質は端末モデルの能力に制限される。中央サーバーだけで大型モデルを動かす方式は品質を確保しやすいが、すべての生成をサーバーで行うためGPU費用が大きい。モデルを層単位に分割する方式は中間活性値を送る必要があり、端末の異種性と通信の変動に影響される。SLEDは端末が草稿生成、共有サーバーが一括検証という役割分担により、これらとは異なる交換関係を作る。

通常の単一ホスト投機的復号との差は、モデル間の草稿・検証という計算分担をネットワーク越しに行い、端末ごとに異なる草稿モデルを許し、サーバーの検証要求を複数端末から集める点である。新しい投機的サンプリングの確率式そのものではなく、分散配置、信頼度に基づく検証タイミング、非同期処理と退避、共有バッチ化を合わせたシステム構成が貢献である。
