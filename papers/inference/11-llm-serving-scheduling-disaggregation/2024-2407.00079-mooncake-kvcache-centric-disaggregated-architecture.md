# Mooncake: A KVCache-centric Disaggregated Architecture for LLM Serving

## 概要

Mooncakeは、大規模言語モデル（Large Language Model、LLM）の推論サービスで、GPUの計算能力とメモリを同時に効率よく使うための分散サービング基盤である。入力をまとめて処理する事前入力処理（Prefill）と、一度に1トークンずつ生成する復号（Decoding）を異なるノード群へ分けるだけでなく、鍵・値キャッシュ（Key-Value Cache、KVキャッシュ）をクラスタ全体で再利用可能な共有資源にする。これにより、同じ接頭辞を持つ別の要求が既存KVを読み込んで重複計算を省ける。余剰のCPUメモリ、DRAM、SSD、ネットワーク帯域を使って共有KVプールを構成する点が、GPU内だけの接頭辞キャッシュと異なる。

中心にあるのは、KVの所在と移動費用を知る全体スケジューラ（Global Scheduler）であるConductorである。単に負荷が低いGPUへ要求を送るのではなく、要求と既存キャッシュの接頭辞一致長、転送時間、事前入力の待ち時間、復号側の残容量を予測し、最初のトークンまでの時間（Time to First Token、TTFT）とトークン間隔（Time Between Tokens、TBT）のサービス水準目標（Service Level Objective、SLO）を守れる組合せを選ぶ。ホットなKVブロックは複数ノードに複製して転送集中を避け、過負荷時には完成できない要求をできるだけ早く拒否して無駄な計算を減らす。

この研究には複数の版がある。2024年の技術報告とその改訂版では、LLaMA2-70B相当の模擬モデルと要求トレースによる比較で、長文の合成負荷におけるSLO適合処理量を最大525%増、実トレース再生で約75%多い要求を処理したと記載する。**2025年11月のACM Transactions on Storage掲載拡張版**は、より大きな実運用と拡張評価を報告し、実トレースに基づく有効要求容量が比較対象比59～498%増、実運用のA800/H800クラスタで115%/107%多い要求を処理したと記載する。これらは測定条件と版が異なるので、一つの表の同条件比較として扱わない。

## 背景・問題設定

事前入力処理は入力列全体の注意計算とKVの生成を行うため、長文では計算量が大きくなる。一方、復号は各要求につき一度に1トークンしか進められず、既存KVの読み出しとモデル重みのメモリ帯域が支配的になりやすい。両者を同じGPUで交互に処理すると、長い事前入力が復号の連続バッチを妨げ、TBTが悪化する。反対に事前入力と復号を分ければ各ノード群を異なる並列構成で最適化できるが、事前入力で生成したKVを復号ノードへ転送する通信費用が生じる。

既存の局所KVキャッシュは、同じGPU・同じプロセスに到着した要求間でしか接頭辞を再利用できないことが多い。クラスタ全体では空いているCPUメモリが存在しても、KVが特定の推論インスタンスに閉じているため、別ノードへ要求を送ると再計算が必要になる。逆にキャッシュが存在するノードへすべての要求を送れば、そのノードが過負荷になり待ち時間が増える。KVの再利用と負荷分散を独立に決めるのは不十分である。

さらに実際の商用サービスでは要求到着率が供給能力を超える。すべての要求を一旦受け付けてから処理しようとすると、事前入力を終えた後に復号スロットが不足して拒否される場合がある。完了しない要求に使ったGPU時間は有効処理量（Goodput）に寄与しない。Mooncakeは、**SLOを満たして最後まで完了した要求**の処理容量を最大化することを目標に、KVの配置・転送・負荷・拒否を一体の問題として扱う。

## 手法

### 1. 事前入力・復号・共有KVプールの分離

クラスタを事前入力ノード群、復号ノード群、分散KVプールに分ける。事前入力側は入力長や必要な並列度に応じて要求を処理し、生成したKVを共有メモリへ書き出す。復号側は受け取ったKVを用いて連続バッチ処理（Continuous Batching）を行い、生成時のTBTを安定させる。共有KVプールはCPUのDRAMやSSDなどの階層にまたがり、必要なブロックをネットワーク経由でGPUへ転送する。ブロックは自身と先行ブロックの内容から作る接頭辞ハッシュで識別し、同じ接頭辞を持つ要求で共有できる。

Mooncake Storeは共有KVの保存と転送を担当する。拡張版では、複数のRDMAネットワークインターフェースを利用するための転送エンジン、ゼロコピー（Zero-Copy）転送、ネットワークのトポロジを考慮した経路選択、接続先のプール化なども設計対象である。大容量キャッシュを確保するだけでなく、**転送時間が再計算時間より短い場合に限って再利用する**ことが実用上重要になる。LLaMA3-70B相当の拡張版の解析では、8,192トークンの共有接頭辞を再利用する際の必要帯域をA800で約6GB/s、H800で約19GB/sと試算する。ただしこれは理論上の損益分岐条件で、転送の重なりが不完全な実装では必要帯域がさらに増える。

要求の典型的な処理順序は、まずConductorが再利用可能なKVの位置を調べ、事前入力と復号のノードを選ぶ。事前入力ノードは遠隔KVを読み込み、未計算部分を増分的に処理する。新たなKVは層ごとに非同期転送され、復号ノード側のCPUメモリへ先回りして置かれる。すべての必要KVが届いた後、復号ノードの局所スケジューラが最新負荷を再確認して連続バッチへ入れる。最初の割当と復号開始時点の負荷が変わり得るため、局所側での再確認も必要である。

### 2. 長文入力の分割パイプラインと層単位転送

長文入力を複数ノードへ分散する際、テンソル並列（Tensor Parallelism）をノード間に広げると層ごとの集合通信が増える。系列並列（Sequence Parallelism）でも層ごとの通信が必要になり、KV転送用ネットワーク帯域と競合する。Mooncakeは入力を塊に分ける分割パイプライン並列（Chunked Pipeline Parallelism、CPP）を導入し、別の事前入力ノードが異なる塊をパイプライン処理する。ノード間通信を主として段境界に限定することで、長文入力のTTFTを減らしつつ、通信競合を抑える。

層単位の事前入力処理（Layer-wise Prefill）では、次層で必要なキャッシュを事前に非同期読み込みし、現層の注意計算が終わると生成済みKVの非同期保存を始める。GPUが計算している間にCPU側への転送を重ねるので、事前入力のGPUメモリにKVを長時間保持する必要が小さくなる。単にKVをCPUへ退避する方式と異なり、転送を事前入力の計算に重ねられるかが重要である。論文は1要求のKVがGPUへ収まることを前提に、事前入力ノードのスケジューリングではGPU上の長期KV常駐量よりもDRAMとキャッシュ配置を重視できると説明する。

### 3. ConductorのKV認識スケジューリング

各要求の入力トークンを一定サイズのブロックへ分け、直前ブロックのハッシュを含めた接頭辞ハッシュを作る。各事前入力インスタンスが保持するブロックと照合し、再利用できる最長接頭辞を推定する。Conductorはその一致長から省略できる事前入力計算量を求め、待ち行列時間、必要な遠隔KV転送時間、未計算トークン数から、候補ノードごとのTTFTを予測する。最長の一致があるノードを機械的に選ぶのではなく、転送して別ノードで処理した方が早い場合はそちらを選ぶ。

復号ノードはTBTとGPUメモリ容量の制約で選ぶ。候補となる事前入力・復号の組合せがSLOを満たせなければ、Conductorは要求を拒否する。論文のアルゴリズムでは、キャッシュ再利用長と負荷の差が閾値を超える場合に、ホットブロックを別のノードへ複製する。頻出するシステムプロンプトのようなキャッシュは、単一ノードだけにあるとそのノードへの転送が集中する。頻度を正確に予測することは難しいため、実際の転送要求と負荷から自動的にホットスポットを緩和する経験則を採用している。

このスケジューラの目的は単一要求の最短計算時間だけではない。再利用率を高めても、遠隔転送が混雑すればTTFTを破る。バッチ数を増やして演算利用率を高めても、復号のTBTを破る。局所キャッシュだけを見た割当でも、全体のキャッシュ分布を考慮した割当でも、通信・待ち行列・復号容量のどれかを無視すれば効果が逆転する。Mooncakeはこれらを同時に評価する点で、単なる接頭辞キャッシュ機構と異なる。

### 4. 過負荷時の早期拒否と予測

事前入力が終わってから復号容量不足で要求を拒否すると、事前入力で消費した計算が無駄になる。そこでMooncakeは要求到着時に事前入力と復号の両方の負荷を調べ、後段が受け入れられないと見込まれる要求を早期に拒否する。ただし現在の復号負荷だけで判定すると、事前入力を通過して復号へ到着するまでの遅れにより、事前入力と復号の負荷が逆位相で増減する現象が生じる。

この揺れを抑えるため、予測に基づく早期拒否（Prediction-based Early Rejection）を使う。要求ごとの生成長を正確に予測する方式は高コスト・不正確になりやすい。技術報告では、各要求の復号時間を代表値で近似し、一定時間後の復号側の要求数と平均TBTを予測するシステム水準の方式を採用している。新たな事前入力完了分を加え、完了予定分を引いた将来負荷を使って受け入れを判断する。これは生成内容の品質を改善する手法ではなく、GPU時間を完成可能な要求へ割り当てる運用アルゴリズムである。

### 5. 拡張版での実装上の寄与

ACM Transactions on Storageの拡張版では、Mooncake Storeの大規模運用、複数RDMA NICを活用する転送、動的な事前入力・復号ノードの切替、要求分布の変化に応じたキャッシュ方針、故障耐性、vLLM/SGLangとの統合を追加の設計要素として扱う。GPUの空き計算時間だけでなく、CPUメモリ、SSD、ネットワーク帯域、転送接続の管理までを含む運用基盤として構築されている。著者らは共有KVプールをペタバイト級へ拡張し、日次1000億トークン超を扱う実運用で使われていると報告するが、これは論文著者による運用規模の報告であり、公開トレースから独立に再現した数値ではない。

## 評価結果：定量比較

### 技術報告の公開・合成・実トレース実験

技術報告の公開データセット評価では、4インスタンスの一体型vLLMと、3事前入力+1復号または2事前入力+2復号のMooncakeを比較した。ArXiv Summarization（平均入力8,088、出力229トークン、キャッシュ再利用ほぼ0%）では、3P+1DがSLO内処理量を20%改善した。L-Eval（平均入力19,019、出力72、キャッシュ比率80%超）では40%改善した。一方2P+2DはTBTが短い条件でもTTFTが悪化し、**事前入力・復号ノード比率の選択を誤ると効果が低下する**という負の結果がある。

合成長文負荷では入力16k、32k、64k、128k、出力512トークン、キャッシュ比率50%を設定し、同じ4インスタンス構成で比較した。長文の事前入力が一体型vLLMの復号を妨げるため、vLLMはTBTを守るべく一度に1要求しか処理できない場合があった。分離したMooncakeはTBTを守りながらバッチ処理でき、条件によりSLO内処理量を50～525%増やした。525%はこの合成負荷の最大値であり、全トレースや実運用の代表値ではない。

実トレース再生では10事前入力+10復号と20一体型vLLMを比較し、TTFTの上限30秒、TBTの上限0.1秒/トークンを設定した。両方式ともTTFTのSLOをほぼ100%の要求で満たしたが、TBTのSLO達成率はMooncakeがほぼ100%、vLLMが57%だった。この条件でMooncakeは約75%多い要求をSLO内で処理できた。つまり差の主因はTTFTだけではなく、長文の事前入力による復号の干渉を抑えたことにある。

技術報告で公開した1時間の要求トレースは約23,608件で、入力平均8,590、出力平均182トークン、512トークン単位の接頭辞ブロックハッシュを含む。キャッシュ容量1,000ブロックではLRU命中率0.34、10,000では0.46、50,000では0.55となり、100,000や無限容量でもこのサンプルでは0.55だった。要求の偏りにより、一部ブロックが何度も使われる一方、半数超は再利用されない。キャッシュ容量を増やすだけでなくホットブロックを分散する理由となる。ただしこの1時間のサンプルだけから全運用での最適容量を断定できない。

過負荷評価では8事前入力+8復号で約23,000要求を2倍速再生し、従来の拒否方式は4,183件、早期拒否は3,771件、将来負荷予測付き早期拒否は3,589件を拒否した。予測付き方式は従来比594件少ない拒否となる。拒否数の減少は無条件の受け入れを意味せず、処理できる見込みのある要求を選び、無駄な事前入力を減らした結果として解釈すべきである。

### ACM Transactions on Storage 2025拡張版

拡張版の要旨と導入・評価概要では、実会話トレースに基づく**有効要求容量が比較方式比59～498%増**と報告される。論文の図1は16台の8×A800ノードでTBTのSLO閾値を変えた比較を示し、閾値によって改善幅が変わる。拡張版は実運用について、従来システムに対しA800クラスタで115%、H800クラスタで107%多い要求を扱うと記す。ここで「115%多い」は2.15倍、「107%多い」は2.07倍の要求容量に相当するが、公開の実運用トレースを第三者が独立再現した値ではない。

拡張版は分散共有キャッシュと局所キャッシュの比較で、キャッシュ命中率が最大2.36倍、事前入力計算時間が最大48%減ると報告する。転送エンジンは比較した既存実装より約2.4倍および4.6倍高速と報告するが、これは個別の転送比較であり、**全推論処理が4.6倍高速になる意味ではない**。容量改善・キャッシュ命中・転送エンジンの速度は異なる測定軸として分ける必要がある。

拡張版の解析では、LLaMA3-70B相当、8×A800、共通接頭辞8,192トークンの例で、KVの再利用が再計算より得になる転送帯域の損益分岐を約6GB/sと見積もる。H800相当では約19GB/sとする。これらは計算速度・転送帯域・キャッシュ長から求める理論条件であり、現実のネットワーク競合や転送重複の不完全さにより必要帯域は増える。帯域を確保できない環境では共有KVを増やすだけではTTFTを改善できない。

## 関連研究と独自性

SplitwiseとDistServeも事前入力と復号の分離を扱うが、MooncakeはKVを単なる要求間の中間データではなく、クラスタ横断で保存・複製・移動する第一級資源として扱う。vLLMのページ化注意（PagedAttention）と局所接頭辞再利用、SGLangの基数木注意（RadixAttention）もKVの再利用を改善するが、Mooncakeは分散したCPUメモリ・SSDまで含む保存階層とグローバルな転送判断を組み合わせる。AttentionStoreなどの階層KV管理と設計思想を共有する一方、Mooncakeは要求割当とSLOを含む全体制御まで扱う。

KVの低ビット量子化や重要トークン選択はキャッシュ1ブロックの容量を減らす技術であり、Mooncakeのような分散配置・通信・負荷分散とは補完関係にある。KIVIなどでKVを小さくできれば、共有キャッシュの容量と転送量を改善する可能性はある。ただし圧縮・逆量子化費用と転送費用を同時に含めた測定なしに、両方式の速度向上率を掛け算して予測することはできない。

## 限界：適用範囲と再現性

第一に、改善幅は接頭辞の再利用率、入力長、到着分布、ネットワーク帯域、GPU構成、SLOに強く依存する。公開要約データセットはキャッシュ再利用がほぼ0%のものから80%超のものまで幅があり、同じ構成でも改善率が異なる。実トレースのキャッシュ再利用可能率は最大55%程度という分析もあり、別のサービスの高い接頭辞再利用率をそのまま適用できない。

第二に、事前入力と復号の資源比率を誤るとTTFTが悪化する。技術報告の2P+2D構成は3P+1Dに比べてTTFTが不利だった。クラスタ負荷が時間とともに変化する場合、固定のノード比率が常に最適とは限らず、拡張版で動的なP/D切替が扱われる理由となる。通信の待ち時間や転送エンジンの実装が弱い場合、遠隔キャッシュを利用する利益が消える。

第三に、過負荷時の予測は不確実である。生成長を個別要求ごとに正確に知ることは難しく、システム水準の近似は平均的な将来負荷を予測する。到着率が急変したり長い出力が集中したりすると、誤った拒否や後段での拒否が残る。早期拒否の件数が少ないことだけでは、利用者間の公平性や優先度を保証しない。

第四に、公開の再現可能な実験は、実ユーザーの本文を使わず、要求時刻・入出力長・接頭辞ハッシュを匿名化したトレースと模擬モデルを使う。実運用でのA800/H800の要求容量改善や日次1000億トークン超という規模は著者らの運用報告であり、公開資料だけで第三者が同一条件を完全再現できるわけではない。初期の技術報告のLLaMA2-70B相当と拡張版のLLaMA3-70B相当を混ぜて評価すべきではない。

第五に、単一GPU・Windows・家庭内LANでの導入にそのまま適用する方式ではない。論文の利益は多数のGPUノード、余剰CPUメモリ、複数RDMA NIC、共通接頭辞の再利用に基づく。Windows 11と12GB級GPUでのCPU退避、PCIe帯域、NVMeキャッシュの実効速度は論文で測っていない。分散サービスの設計原則としては有用だが、個人PCで同等の容量改善率・スループットを期待する根拠にはならない。
