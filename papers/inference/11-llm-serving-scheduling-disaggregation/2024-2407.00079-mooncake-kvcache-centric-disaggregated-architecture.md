# Mooncake: Trading More Storage for Less Computation — A KVCache-centric Architecture for Serving LLM Chatbot

> prefill / decode clusterを分離し、GPU cluster内のDRAM・SSD・RDMAをglobal KV cacheとして束ね、cache reuseとinstance loadを同時に見たschedulerでSLOを守りながらrequest capacityを高める大規模LLM serving system。

## 概要

Mooncakeは、Kimiの実運用を背景に設計された**KVCache-centricなdisaggregated serving architecture**である。

prefillとdecodeでは計算特性とSLOが異なるため、Mooncakeは両者を別node poolへ分離する。さらに各GPU nodeで余りやすいCPU、DRAM、SSD、RDMA NICをまとめ、nodeを跨いで再利用できるdistributed KV cache pool（Mooncake Store）を構成する。

新しいrequestが来ると、global schedulerのConductorは「どのprefill instanceに最長prefixがあるか」だけでなく、queue待ち・KV transfer時間・prefill時間・decode loadを合わせて、TTFT / TBT SLOを満たすprefill / decode pairを選ぶ。

単なるKV offloadではなく、**KV cacheをcluster-level schedulingの中心resourceとして扱う**点が主題である。

## 問題設定

長context servingではprefillが重く、同時に過去requestのprefix KVを再利用できれば大きな計算を省ける。しかしlocal HBM / DRAMだけのprefix cacheでは容量が小さく、同じprefixを持つrequestが別nodeへ送られるとcacheを再利用できない。

一方、global cacheを作ってもremote KV transferが遅ければ、prefillを再計算した方が速い。MooncakeはLLaMA3-70B相当の分析から、十分なnetwork bandwidthがあればremote KVを取得する方が有利になる領域を示し、A800構成では100Gbps級のlinkでも実用的になり得るとする。

またprefillとdecodeを同じworkerで実行すると、長いprefillがdecode batchへ割り込み、TBTを悪化させる。この干渉を避けることもP/D disaggregationの狙いである。

## 手法

### 1. Prefill poolとdecode poolを分離する

requestごとにConductorがprefill instanceとdecode instanceを選ぶ。

prefill側はprefix cache reuseとTTFTを重視し、decode側はVRAMに収まるKV量とTBTを考慮しつつbatchを大きくしてthroughputを高める。prefill完了後にまとめてKVを送るのではなく、layer / chunk単位で生成したKVをdecode nodeへstreamingすることでtransferをprefill計算と重ねる。

### 2. CPU DRAM・SSDをdistributed KV cache poolとして使う

Mooncake StoreはKVをpaged blockとしてDRAM / SSDへ保持し、prefix hashで重複を識別する。同じblockを複数nodeへreplicateでき、hot blockは複製してfetch congestionを減らす。

local cacheに閉じずcluster全体からprefixを探せるため、request routingの自由度を保ちながらcache hit率を上げられる。

### 3. Multi-NIC RDMA Transfer Engine

KV transferはDRAM↔DRAMだけでなくVRAMも扱い、条件が合えばGPUDirect RDMAを使う。

各serverのNUMA / PCIe / NIC topologyを事前に表へまとめ、source / destination memoryに近いNIC pathを選ぶ。またdataをsliceへ分けて複数NICへ振り分け、endpoint poolingとfailure時のalternative path selectionも行う。

### 4. Cache-aware global scheduling

prefill instance選択では、

- 利用できるprefix長
- remote cache transfer時間
- instanceのqueue待ち
- 残りprefillの推定計算時間

を比較し、最小TTFTになるworkerを選ぶ。

最長prefixを持つworkerが混雑している場合、別workerへKVを転送して処理する方が速いかを判定する。この転送自体がhot prefixのreplicaを増やすため、将来のload balancingにもつながる。

### 5. SLOを満たせないrequestを早めにrejectする

GPUを短時間で増設できないoverload時には、予測TTFTまたはTBTがSLOを超えるrequestを受け続けると、既存requestまで遅くなる。Mooncakeはschedulerの推定値からSLO達成が難しいrequestを早期rejectし、SLO内で完了するeffective throughputを最大化する。

## 評価

### 条件

再現可能な評価では、LLaMA3-70B相当のdummy modelと実workload traceを使い、主に16台の8×A800 nodeでMooncake、vLLM、vLLM Prefix Caching、vLLM Chunked Prefillを比較する。実際のKimi deploymentではA800 / H800 clusterを使用する。

workloadはconversation、tool / agent、長contextを含むsynthetic / public dataset由来traceなどを評価する。

### Effective request capacity

conversation workloadではSLO設定に応じてbaseline比**59〜498%**のeffective request capacity向上を報告している。

Tool / Agent workloadでは200ms TBT thresholdでvLLM Prefix Caching比42%改善、synthetic workloadではvLLM比40%改善した条件がある。

実運用のhistorical statisticsでは、以前のvLLM系systemと比べてKimiが処理できるrequest数をA800 clusterで**115%**、H800 clusterで**107%**増やしたとしている。

### Global KV cache

global Mooncake Storeはlocal cache構成よりcache hit rateを最大**2.36×**高め、prefill GPU timeを最大48%削減した。

これはKV容量を増やすだけでなく、異なるnodeへあるcacheをremote reuseできる効果を含む。

### Transfer Engine

40GB KV transferでは、

- 4×200Gbps NIC: 87GB/s
- 8×400Gbps NIC: 190GB/s

を測定し、TCP比でそれぞれ約2.4× / 4.6×高速だった。

帯域感度評価では100Gbpsを下回るとTTFTが急増し、remote cache reuseの利点が崩れやすくなる。

## 既存研究との差

### Local prefix cachingとの違い

vLLM型のlocal prefix cacheでは、cache hitを得るためrequest routingが特定workerへ偏りやすい。MooncakeはKV自体をworker間で移動・複製できるため、**cache localityとcompute load balancingを分離**できる。

### DistServe / Splitwiseとの違い

P/D disaggregation自体は先行研究にもあるが、Mooncakeはそれに**cluster-wide distributed KV cache**を組み込み、prefix reuse・KV transfer・prefill/decode schedulingを一つのglobal schedulerで扱う。

### Sarathi-Serveとの違い

Sarathi-Serveはprefillを小さいchunkへ分割しdecodeと同じGPU上でinterleaveして干渉を抑える。Mooncakeはprefillとdecodeを物理的に別poolへ分け、高速KV transferでstage間を接続する。

## 限界

- 十分なRDMA network帯域が前提で、100Gbpsを大きく下回る環境ではremote KV reuseの利得が急減する。
- global cache metadata、replica、network path、prefill/decode loadを同時管理するためruntimeが複雑になる。
- 最大498%は特定SLO / workload条件でのeffective request capacityであり、token/sの一律なspeedupではない。
- 実運用の115% / 107%増加はMoonshot AIのhistorical deployment比較で、完全に同一条件の公開baseline experimentではない。
- fixed P/D ratioを基本とし、大きなtraffic変化時だけ役割変更するため、短時間で大きく変動するworkloadでは追加のelastic controlが必要になる。

## 一般的な実装上の含意

大規模servingではKV cacheは単なるGPU memory allocationではなく、**再計算costを保存・network transferへ交換できるcluster-wide resource**として扱える。

その場合、schedulerはcache hit率だけを最大化せず、remote transfer、queue、prefill compute、decode SLOを同じcost modelで比較する必要がある。またP/D disaggregationを実用化するには、stageを分離するだけでなくKV transferをprefill計算とstreaming overlapすることが重要になる。

## コード・実装状況
