# Mooncake: Trading More Storage for Less Computation — A KVCache-centric Architecture for Serving LLM Chatbot

> プリフィルとデコードを別GPU群へ分け、クラスタ内のCPU DRAM・SSDへ過去KVを保存して別ノードからも再利用できるようにし、KV取得時間・待ち行列待ち・残りプリフィル計算を比較してリクエストの実行先を決める大規模な推論提供システム。

## 概要

Mooncakeは、Kimiの実運用を背景に設計された大規模LLM推論提供基盤である。

中心的な発想は、KV キャッシュを「そのリクエストが動いているGPUにだけ属する一時データ」とせず、**クラスタ内で保存・検索・移動・再利用できる共有資源として扱う**ことにある。

プリフィルとデコードでは計算特性と遅延目標が異なるため、Mooncakeは両者を別ノード群へ分離する。さらに各GPUノードのCPU DRAMやSSDを使い、リクエスト終了後もプレフィックスKVを大量に保持する。

新しいリクエストが来ると全体スケジューラは、単純に「最長プレフィックスを持つGPU」へ送るのではなく、

- 既存KVをネットワークで取ってくる時間
- そのワーカーの待ち行列待ち
- キャッシュで省けなかった残りのプリフィル計算
- デコード側の混雑とメモリ

を合わせて、TTFT / TBT目標を満たしやすいプリフィル／デコードの組を選ぶ。

## 問題設定

長文脈推論提供ではプリフィルが重く、過去リクエストと同じプレフィックスKVを再利用できれば大きな計算を省ける。しかし局所HBM／DRAMだけのプレフィックスキャッシュでは容量が小さく、同じプレフィックスを持つリクエストが別ノードへ送られるとキャッシュを再利用できない。

一方、クラスタ全体のキャッシュを作っても遠隔KV転送が遅ければ、保存済みKVをネットワークで取るよりプリフィルを再計算した方が速い。

したがってMooncakeは、**キャッシュヒットかミスかだけでなく「遠隔KV取得と再計算のどちらが速いか」までスケジューラで比較する**。

またプリフィルとデコードを同じワーカーで実行すると、長いプリフィルがデコードバッチへ割り込みTBTを悪化させる。この干渉を避けるため両段階を物理的に分離する。

## 手法

### 1. Prefill poolとdecode poolを分離する

リクエストごとにスケジューラがプリフィルインスタンスとデコードインスタンスを選ぶ。

プリフィル側はプレフィックス再利用とTTFTを重視し、デコード側はVRAMに収まるKV量とTBTを考慮しつつバッチを大きくしてスループットを高める。

プリフィルが全層終わってからKVをまとめて送るのではなく、層／チャンク単位でKVが生成されるたびデコードノードへ送り、**プリフィル計算とKV転送を同時に進める**。

### 2. CPU DRAM・SSDをcluster-wide KV cacheとして使う

Mooncake StoreはKVをブロック単位でDRAM／SSDへ保持し、プロンプトプレフィックスのハッシュから同じKVを検索する。

同じKVブロックを複数ノードへ複製することもできる。よく使われる頻出プレフィックスを複数場所へ置けば、1ノードへ取得リクエストが集中するのを防げる。

局所キャッシュに閉じずクラスタ全体からプレフィックスを探せるため、リクエストルーティングの自由度を保ちながらキャッシュヒット率を上げられる。

### 3. 複数NICを使い、KVを高速にnode間転送する

MooncakeはRDMAを使い、CPUを経由するコピーやソフトウェアオーバーヘッドを抑えながらメモリ間でデータを送る。

**RDMA（遠隔直接メモリアクセス）** は、遠隔マシンのメモリへネットワークアダプタから直接読み出し／書き込みし、CPU介在を減らす通信方式である。

1 サーバに複数NICがある場合はKVを複数分割片へ分け、複数リンクで並行転送する。またGPU メモリを直接送れる条件ではGPUDirect RDMAを利用する。

論文の転送エンジンは、サーバ内のGPU／CPU／NICの接続関係を見て、**どのNIC経路を使えば最も高い帯域を得られるかを選ぶデータ転送層**である。

### 4. Cache reuseとqueue待ちを同じ時間尺度で比較する

プリフィル インスタンス選択では、

- 利用できるプレフィックス長
- 遠隔キャッシュ転送時間
- インスタンスの待ち行列待ち
- キャッシュにない残りプリフィルの計算時間

を合計し、最もTTFTが小さくなりそうなワーカーを選ぶ。

最長プレフィックスを持つワーカーが混雑している場合は、そのKVを空いているワーカーへ転送して処理する方が速いこともある。

この転送でKV複製が増えるため、頻出プレフィックスは自然に複数ノードへ広がり、将来の負荷分散にも役立つ。

### 5. どう見積もってもSLOを守れないrequestは早めにrejectする

GPUを短時間で増やせない過負荷時に、遅延目標を大幅に超えるリクエストを無制限に受け入れると、既存リクエストまで待ち行列が伸びてSLO違反になる。

Mooncakeは予測TTFT / TBTから、**今受け入れても目標を守れそうにないリクエストを早めに拒否し、すでに受け入れたリクエストの品質を守る**。

## 評価

### 条件

再現可能な評価では、LLaMA3-70B相当の模擬モデルと実ワークロードトレースを使い、主に16台の8×A800ノードでMooncake、vLLM、vLLMプレフィックスキャッシュ化、vLLM分割プリフィルを比較する。実際のKimi展開ではA800／H800クラスタを使用する。

ワークロードは会話、ツール／エージェント、長文脈を含む合成／公開データセット由来トレースなどを評価する。

### SLOを守って処理できるrequest capacity

会話ワークロードではSLO設定に応じて比較対象比**59〜498%**の実効リクエスト容量向上を報告している。

ここで実効リクエスト容量は、単純なトークン/sではなく、**設定した遅延目標を守りながら受け付けられるリクエスト割合**を指す。

ツール／エージェントワークロードでは200ms TBTしきい値でvLLMプレフィックスキャッシュ化比42%改善、合成ワークロードではvLLM比40%改善した条件がある。

実運用の過去の統計では、以前のvLLM系システムと比べてKimiが処理できるリクエスト数をA800クラスタで**115%**、H800クラスタで**107%**増やしたとしている。

### Global KV cache

全体のMooncake Storeは局所キャッシュ構成よりキャッシュヒット割合を最大**2.36×**高め、プリフィルGPU時間を最大48%削減した。

これはKV容量を増やすだけでなく、異なるノードに保存されたキャッシュをネットワーク経由で再利用できる効果を含む。

### Transfer Engine

40GB KV 転送では、

- 4×200Gbps NIC: 87GB/s
- 8×400Gbps NIC: 190GB/s

を測定し、TCP比でそれぞれ約2.4× / 4.6×高速だった。

帯域感度評価では100Gbpsを下回るとTTFTが急増し、遠隔キャッシュ再利用の利点が崩れやすくなる。

## 既存研究との差

### Local prefix cachingとの違い

vLLM型の局所プレフィックスキャッシュでは、キャッシュヒットを得るためリクエストルーティングが特定ワーカーへ偏りやすい。

MooncakeはKV自体をワーカー間で移動・複製できるため、**「キャッシュがある場所」と「計算する場所」を必ずしも同じにしなくてよい**。これによりキャッシュ局所性と計算負荷の分散を分離できる。

### DistServe / Splitwiseとの違い

P/D分離自体は先行研究にもあるが、Mooncakeはそれに**クラスタ全体の分散KVキャッシュ**を組み込み、プレフィックス再利用・KV転送・プリフィル／デコードスケジューリングを一つの全体スケジューラで扱う。

### Sarathi-Serveとの違い

Sarathi-Serveはプリフィルを小さいチャンクへ分割しデコードと同じGPU上で交互に処理して干渉を抑える。Mooncakeはプリフィルとデコードを物理的に別プールへ分け、高速KV 転送で両段階を接続する。

## 限界

- 十分なRDMAネットワーク帯域が前提で、100Gbpsを大きく下回る環境では遠隔KV再利用の利得が急減する。
- 全体キャッシュメタデータ、複製、ネットワーク経路、プリフィル／デコード負荷を同時管理するため実行時環境が複雑になる。
- 最大498%は特定SLO / ワークロード条件での実効 リクエスト 容量であり、トークン/sの一律な高速化倍率ではない。
- 実運用の115%／107%増加はMoonshot AIの過去の展開比較で、完全に同一条件の公開比較対象実験ではない。
- 固定P/D比率を基本とし、大きな通信量変化時だけ役割変更するため、短時間で大きく変動するワークロードでは追加の弾性制御が必要になる。

## 一般的な実装上の含意

大規模推論提供ではKVキャッシュは単なるGPUメモリ割り当てではなく、**再計算コストを保存容量とネットワーク転送へ交換できるクラスタ全体の資源**として扱える。

その場合、スケジューラはキャッシュ ヒット率だけを最大化せず、遠隔 転送、待ち行列、プリフィル 計算、デコード SLOを同じ時間尺度で比較する必要がある。またP/D 分離を実用化するには、段階を分離するだけでなくKV 転送をプリフィル計算とストリーミング 重複することが重要になる。
