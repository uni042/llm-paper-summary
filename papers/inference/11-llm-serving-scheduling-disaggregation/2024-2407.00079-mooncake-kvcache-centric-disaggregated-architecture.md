# Mooncake: Trading More Storage for Less Computation — A KVCache-centric Architecture for Serving LLM Chatbot

> prefillとdecodeを別GPU群へ分け、cluster内のCPU DRAM・SSDへ過去KVを保存して別nodeからも再利用できるようにし、KV取得時間・queue待ち・残りprefill計算を比較してrequestの実行先を決める大規模serving system。

## 概要

Mooncakeは、Kimiの実運用を背景に設計された大規模LLM serving architectureである。

中心的な発想は、KV cacheを「そのrequestが動いているGPUにだけ属する一時data」とせず、**cluster内で保存・検索・移動・再利用できる共有resourceとして扱う**ことにある。

prefillとdecodeでは計算特性とlatency目標が異なるため、Mooncakeは両者を別node poolへ分離する。さらに各GPU nodeのCPU DRAMやSSDを使い、request終了後もprefix KVを大量に保持する。

新しいrequestが来るとglobal schedulerは、単純に「最長prefixを持つGPU」へ送るのではなく、

- 既存KVをnetworkで取ってくる時間
- そのworkerのqueue待ち
- cacheで省けなかった残りprefill計算
- decode側の混雑とmemory

を合わせて、TTFT / TBT目標を満たしやすいprefill / decode pairを選ぶ。

## 問題設定

長context servingではprefillが重く、過去requestと同じprefix KVを再利用できれば大きな計算を省ける。しかしlocal HBM / DRAMだけのprefix cacheでは容量が小さく、同じprefixを持つrequestが別nodeへ送られるとcacheを再利用できない。

一方、cluster-wide cacheを作ってもremote KV transferが遅ければ、保存済みKVをnetworkで取るよりprefillを再計算した方が速い。

したがってMooncakeは、**cache hitかmissかだけでなく「remote KV取得と再計算のどちらが速いか」までschedulerで比較する**。

またprefillとdecodeを同じworkerで実行すると、長いprefillがdecode batchへ割り込みTBTを悪化させる。この干渉を避けるため両phaseを物理的に分離する。

## 手法

### 1. Prefill poolとdecode poolを分離する

requestごとにschedulerがprefill instanceとdecode instanceを選ぶ。

prefill側はprefix reuseとTTFTを重視し、decode側はVRAMに収まるKV量とTBTを考慮しつつbatchを大きくしてthroughputを高める。

prefillが全layer終わってからKVをまとめて送るのではなく、layer / chunk単位でKVが生成されるたびdecode nodeへ送り、**prefill計算とKV transferを同時に進める**。

### 2. CPU DRAM・SSDをcluster-wide KV cacheとして使う

Mooncake StoreはKVをblock単位でDRAM / SSDへ保持し、prompt prefixのhashから同じKVを検索する。

同じKV blockを複数nodeへ複製することもできる。よく使われるhot prefixを複数場所へ置けば、1 nodeへfetch requestが集中するのを防げる。

local cacheに閉じずcluster全体からprefixを探せるため、request routingの自由度を保ちながらcache hit率を上げられる。

### 3. 複数NICを使い、KVを高速にnode間転送する

MooncakeはRDMAを使い、CPUを経由するcopyやsoftware overheadを抑えながらmemory間でdataを送る。

**RDMA（Remote Direct Memory Access）** は、remote machineのmemoryへnetwork adapterから直接read/writeし、CPU介在を減らす通信方式である。

1 serverに複数NICがある場合はKVを複数sliceへ分け、複数linkで並行転送する。またGPU memoryを直接送れる条件ではGPUDirect RDMAを利用する。

論文のTransfer Engineは、server内のGPU / CPU / NICの接続関係を見て、**どのNIC pathを使えば最も高い帯域を得られるかを選ぶdata-transfer layer**である。

### 4. Cache reuseとqueue待ちを同じ時間尺度で比較する

prefill instance選択では、

- 利用できるprefix長
- remote cache transfer時間
- instanceのqueue待ち
- cacheにない残りprefillの計算時間

を合計し、最もTTFTが小さくなりそうなworkerを選ぶ。

最長prefixを持つworkerが混雑している場合は、そのKVを空いているworkerへ転送して処理する方が速いこともある。

この転送でKV replicaが増えるため、popular prefixは自然に複数nodeへ広がり、将来のload balancingにも役立つ。

### 5. どう見積もってもSLOを守れないrequestは早めにrejectする

GPUを短時間で増やせないoverload時に、latency目標を大幅に超えるrequestを無制限に受け入れると、既存requestまでqueueが伸びてSLO違反になる。

Mooncakeは予測TTFT / TBTから、**今受け入れても目標を守れそうにないrequestを早めにrejectし、すでに受け入れたrequestの品質を守る**。

## 評価

### 条件

再現可能な評価では、LLaMA3-70B相当のdummy modelと実workload traceを使い、主に16台の8×A800 nodeでMooncake、vLLM、vLLM Prefix Caching、vLLM Chunked Prefillを比較する。実際のKimi deploymentではA800 / H800 clusterを使用する。

workloadはconversation、tool / agent、長contextを含むsynthetic / public dataset由来traceなどを評価する。

### SLOを守って処理できるrequest capacity

conversation workloadではSLO設定に応じてbaseline比**59〜498%**のeffective request capacity向上を報告している。

ここでeffective request capacityは、単純なtoken/sではなく、**設定したlatency目標を守りながら受け付けられるrequest rate**を指す。

Tool / Agent workloadでは200ms TBT thresholdでvLLM Prefix Caching比42%改善、synthetic workloadではvLLM比40%改善した条件がある。

実運用のhistorical statisticsでは、以前のvLLM系systemと比べてKimiが処理できるrequest数をA800 clusterで**115%**、H800 clusterで**107%**増やしたとしている。

### Global KV cache

global Mooncake Storeはlocal cache構成よりcache hit rateを最大**2.36×**高め、prefill GPU timeを最大48%削減した。

これはKV容量を増やすだけでなく、異なるnodeに保存されたcacheをnetwork経由で再利用できる効果を含む。

### Transfer Engine

40GB KV transferでは、

- 4×200Gbps NIC: 87GB/s
- 8×400Gbps NIC: 190GB/s

を測定し、TCP比でそれぞれ約2.4× / 4.6×高速だった。

帯域感度評価では100Gbpsを下回るとTTFTが急増し、remote cache reuseの利点が崩れやすくなる。

## 既存研究との差

### Local prefix cachingとの違い

vLLM型のlocal prefix cacheでは、cache hitを得るためrequest routingが特定workerへ偏りやすい。

MooncakeはKV自体をworker間で移動・複製できるため、**「cacheがある場所」と「computeする場所」を必ずしも同じにしなくてよい**。これによりcache localityとcompute load balancingを分離できる。

### DistServe / Splitwiseとの違い

P/D disaggregation自体は先行研究にもあるが、Mooncakeはそれに**cluster-wide distributed KV cache**を組み込み、prefix reuse・KV transfer・prefill/decode schedulingを一つのglobal schedulerで扱う。

### Sarathi-Serveとの違い

Sarathi-Serveはprefillを小さいchunkへ分割しdecodeと同じGPU上で交互に処理して干渉を抑える。Mooncakeはprefillとdecodeを物理的に別poolへ分け、高速KV transferで両phaseを接続する。

## 限界

- 十分なRDMA network帯域が前提で、100Gbpsを大きく下回る環境ではremote KV reuseの利得が急減する。
- global cache metadata、replica、network path、prefill/decode loadを同時管理するためruntimeが複雑になる。
- 最大498%は特定SLO / workload条件でのeffective request capacityであり、token/sの一律なspeedupではない。
- 実運用の115% / 107%増加はMoonshot AIのhistorical deployment比較で、完全に同一条件の公開baseline experimentではない。
- fixed P/D ratioを基本とし、大きなtraffic変化時だけ役割変更するため、短時間で大きく変動するworkloadでは追加のelastic controlが必要になる。

## 一般的な実装上の含意

大規模servingではKV cacheは単なるGPU memory allocationではなく、**再計算costを保存容量とnetwork transferへ交換できるcluster-wide resource**として扱える。

その場合、schedulerはcache hit率だけを最大化せず、remote transfer、queue、prefill compute、decode SLOを同じ時間尺度で比較する必要がある。またP/D disaggregationを実用化するには、stageを分離するだけでなくKV transferをprefill計算とstreaming overlapすることが重要になる。
