# Mico：出力トークン長予測とバッチ補充によるマルチクラウドLLM推論スケジューリング

## 概要

LLMの生成要求は、入力の長さだけでなく生成するトークン数によって処理時間が大きく変わる。要求数だけを均等に複数クラウドへ振り分けても、長い応答が特定クラウドへ集中すると他のクラウドが先に空き、システム全体の完了時刻とスループットが悪化する。また固定バッチの一部がEOSに達しても、残りの要求が生成を続ける間は空きスロットを十分利用できず、KVキャッシュを保持する負担も残る。

Micoはこの問題を2段階で扱う。第1段階では軽量DistilBERTが応答長の範囲を予測し、クラウド間で処理予定トークン数が偏らないように要求を配る。第2段階では推論エンジンの各生成反復の間に完了した要求を取り除き、別の要求を同じバッチスロットへ挿入する。挿入時のattention maskとKVキャッシュを調整して、既存要求の生成結果を変えずに処理を継続する。

GPT-2/GPT-Neoを使ったA6000の評価では、3クラウド・200要求・バッチ3の条件で累積KVキャッシュ長が44.89%減少し、要求処理スループットが1.79倍になった。条件を変えた表1では最大2.22倍の改善を報告する。ただし実験はクラウドのGPU性能とネットワーク条件を均一に置いており、実際の複数事業者クラウドのネットワーク遅延、費用、異種GPU配置を同時に評価した結果ではない。

## 問題設定と従来法との差

従来のround-robinやhashによる要求分散は、要求数が等しくても出力長が異なれば各クラウドの計算負荷を均等化できない。バッチ単位の推論では最長の応答が終了するまで短い応答のスロットが遊び、既にEOSを生成した位置が次の反復でも処理対象に残ることがある。Orcaなどの反復単位スケジューリングはこの問題を扱うが、著者は既存方式のattention処理の複製が追加パラメータやメモリを増やし、バッチサイズに比例して費用が増える点を問題視する。

Micoはクラウド間とクラウド内の両方を同時に最適化する。クラウド間では**出力長予測**を利用し、クラウド内では**反復単位のスロット補充**を行う。これらは異なる問題に作用するため、一方だけを導入した場合の効果と両方を組み合わせた効果をアブレーションで比較する。目的は要求処理スループットとKVメモリ利用効率であり、SLA違反率やP99応答遅延の厳密な最小化を直接解いたアルゴリズムではない。

## 手法

### 応答長の10区間分類器

自己回帰LLMの生成反復回数は、概ね出力トークン数に対応する。しかし同じ質問でもtemperatureやtop-k/top-pによって生成長が変わるため、厳密なトークン数の回帰よりも長さ区間への分類を採用する。Micoは約6600万パラメータのDistilBERTを基盤とし、出力長を10個のbucketへ分ける。各学習例の出力トークン長を測り、最大出力長を10分割した区間番号を教師ラベルにする。

DistilBERTをAdamW、学習率5×10⁻⁵、batch32、3epochで微調整する。Alpaca約52,000件とMath-Word-Problems約200,000件を利用し、分類結果の区間中央を推定生成長としてクラウド間スケジューラへ渡す。正確な長さが不要な理由は、要求数が多い場合に各クラウドの総負荷を近づけるには大まかな長短の識別だけでも役立つためである。モデルや利用者の質問分布が変われば予測器を再学習する必要があり、予測器自体の4.5ms程度の遅延も新たに生じる。

### クラウド間のクエリ配分

各要求の予測出力長区間の中央値を求め、同じ区間の要求をグループ化する。長い応答のグループから順に各クラウドへ配り、クラウドごとの処理予定トークン総数Mkが均等になるようにする。グループ内の要求数がクラウド数で割り切れない場合は次グループから借りるなどして偏りを緩和する。著者はアルゴリズムの計算量をO(n)と説明する。

入力プロンプト自体の長さもKVキャッシュ容量に影響するため、出力長だけでなく処理予定トークン数を考慮する。予測が外れて特定クラウドへ長い要求が偏った場合、空いたクラウドへ未処理要求を移すバックオフを提案するが、移動交渉とネットワーク状態を考慮した実装は詳細に評価していない。実際のクラウド間ネットワーク遅延やGPU性能の違いを組み込む最適化は将来課題とされる。

### バッチ内の反復単位スケジューラ

処理中バッチの要求cがEOSに達したとき、次の要求nをそのスロットへ入れる。既存要求a,bは次の1トークンだけを入力するのに対し、新要求nは初回prefillなので入力全体を渡す必要がある。Micoはトークン行列をパディングで揃え、attention maskでは既存要求の新しい1トークンだけを有効、新要求の入力トークン全体を有効とする。完了要求cに対応する旧KVの参照を無効化し、旧KV位置へ−∞を置いて新要求のattentionへ影響させない。

新要求が入る反復の後は、全スロットで共通して不要になったattention maskとKVのprefixを解放する。原著図5・6ではattention maskが0の最長prefixを見つけ、その区間に対応するKVを同時に解放する。これによりスロットの再利用で旧要求のKVを誤って参照することを避ける。完了していない要求のKVは変更しないため、生成結果の論理的一貫性を維持すると著者は説明する。

ただし挿入時のパディングは新たな計算を増やすため、長い新要求をすぐ挿入すると逆効果になる場合がある。著者は短い要求を優先して挿入する方法、prefillを先に別処理してからdecodeバッチへ加える方法を提案する。またバッチが大きいとKVがHBMを圧迫するため、空きメモリに応じた動的バッチサイズ変更やCPUメモリへの退避を拡張案として述べる。これら拡張の全てが評価済みのMicoの主結果に含まれるわけではない。

## 評価条件

| 項目 | 条件 |
|---|---|
| 基盤モデル | GPT-2（最大1,024トークン）、GPT-Neo（最大2,048トークン） |
| GPU | 各推論ノードにNVIDIA RTX A6000 |
| クラウド数 | 2、3、6、9ノード |
| バッチサイズ | 2〜10、主な可視化では3 |
| 要求数 | 200、500、800、1,000 |
| 要求分布 | Alpaca検証データからランダム抽出、実際の生産トレースは未使用 |
| 比較 | 要求数均等配分、反復単位処理のみ、予測長配分のみ、両者を統合したMico |
| 主要指標 | 累積KV長（メモリ資源利用の代理指標）、要求完了時刻、システム処理スループット |
| 予測器 | DistilBERT 66M、10区間分類、Alpaca/Math-Word-Problemsで微調整 |

ネットワークとクラウド間GPU性能差は均一として実験から除外する。したがってマルチクラウドの配置費用、転送料金、地理的遅延、SLAの差を測った結果ではない。KVメモリ資源については**累積KVのseq length**を代理指標として使っており、実測HBMピーク容量が同じ割合で減ると断定しない。

## 評価結果

### 3クラウド・200要求・バッチ3

| 指標 | Micoの結果 | 比較の意味 |
|---|---|---|
| 累積KV長削減・Cloud1 | 41.54% | 要求数ベース配分＋固定バッチとの比較 |
| 累積KV長削減・Cloud2 | 39.45% | 同上 |
| 累積KV長削減・Cloud3 | 50.68% | 同上 |
| 累積KV長削減・システム全体 | 44.89% | 3クラウド合計の累積KV長 |
| 要求処理スループット・Cloud1 | 1.79倍 | 各クラウドの要求完了速度 |
| 要求処理スループット・Cloud2 | 1.78倍 | 同上 |
| 要求処理スループット・Cloud3 | 1.75倍 | 同上 |
| 要求処理スループット・全体 | 1.79倍 | システムの完了要求数/時間 |

KVの長さは時間に沿って増減し、固定バッチでは完了した要求のスロットが新しい要求で補充されないため、鋸歯状の波形が現れる。Micoは早く終了したスロットを補充して継続的に処理するため、ピークのKV長は近くても同じ要求群を早く処理し、**時間積分したKV長**を削減する。累積KV長44.89%減をGPUのピークVRAM44.89%減と読み替えるのは誤りである。

### バッチサイズ・クラウド数の感度

バッチサイズ2〜10、要求200〜1,000を変えた図11では、全体スループット改善は1.69〜2.17倍だった。クラウド数2/3/6/9、要求800でバッチサイズ2〜10を変えた表1では1.67〜2.22倍を報告する。最大2.22倍は2クラウド・バッチ9の条件であり、すべての構成で2.22倍ではない。

| クラウド数 | batch2 | batch3 | batch5 | batch8 | batch9 | batch10 |
|---|---:|---:|---:|---:|---:|---:|
| 2 | 1.67 | 1.88 | 2.05 | 2.10 | 2.22 | 2.17 |
| 3 | 1.70 | 1.91 | 2.04 | 2.10 | 2.16 | 2.16 |
| 6 | 1.79 | 1.94 | 2.04 | 2.10 | 2.09 | 2.02 |
| 9 | 1.77 | 1.89 | 2.08 | 2.07 | 2.11 | 2.14 |

クラウド数を増やしても速度比は単調には上昇しない。ランダム抽出による応答長分布の違いと、バッチサイズによる並列度・スロット補充機会の違いが影響する。図11と表1は要求数やクラウド数が異なるため、最大値だけを比較して統一的な増分を主張できない。

### アブレーションと予測器の精度

予測器の10区間分類精度はAlpacaで85.37%、Math-Word-Problemsで80.69%、1要求の予測時間は平均約4.5ms。別データセット約200例を使って追加微調整すると、新しい検証セットで82.5%となり、元データの精度は約0.9ポイント下がった。分布変化に適応できる一方、既存ドメインの精度低下がある。分類が外れる場合も隣接区間に入る例が多く、スケジューリングには必ずしも厳密な出力長予測を必要としない。

クラウド間の予測長ベース配分だけ、またはクラウド内の反復単位スロット補充だけでも処理スループットは改善するが、両者の統合が最良である。反復単位処理の新要求挿入に要する時間は1ms未満で、単一の生成反復約70msと比較すると小さい。ただしGPUカーネルや実装によってこの比率は変わり、あらゆるモデルで挿入費用が無視できるわけではない。

別モデルGPT-Neoで3クラウド、バッチサイズと要求数を変えて10回試行すると、Micoのスループット改善は1.22〜1.75倍だった。GPT-2での最大2.22倍より小さい条件があるため、モデルを変えても同じ速度比が再現されるとはいえない。

## 限界と運用上の含意

Micoの最大の制約は、クラウド間ネットワーク差・異種GPU性能・実際の負荷トレースを評価に含めていない点である。実際には長いプロンプトのprefill、ネットワーク転送、KVのCPUオフロード、スケジューラの中央集約による待ち時間、価格差、リクエストの優先度が影響する。出力長予測が大きく外れた場合のバックオフも詳細な実測比較はなく、別クラウドへの再割当が常に得になる保証はない。

評価モデルはGPT-2とGPT-Neoであり、近年のGQA、MoE、大規模モデル、連続バッチングを実装したvLLM/SGLangなどの最新サービング系へそのまま速度比を外挿できない。固定バッチとEOS処理を前提としたベースラインは、現代の連続バッチングより不利な場合がある。したがって実装価値は、既存エンジンがすでに持つスロット補充機能との重複を確認して判断する必要がある。

精度面では、既存要求のKVを維持してマスクを調整するため生成内容の一貫性を保つ設計だが、実装の−∞マスク、数値精度、パディング位置、モデルごとのKV形状に注意が必要である。実務上はクラウド間配分に予測トークン数を使う着想が汎用的であり、クラウド内補充の部分は現在のサービングエンジンのcontinuous batchingとの比較で評価すべきである。総スループットに加え、TTFT、TPOT、P95/P99完了時間、GPU実使用メモリ、予測器のオーバーヘッドを同じ負荷で測る必要がある。
