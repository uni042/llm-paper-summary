# Mico：生成長予測と反復単位バッチ補充を組み合わせたマルチクラウドLLM推論

## 概要

LLMサービングの処理量は、同時に受け付ける要求数だけでは決まらない。自己回帰生成では、応答が長い要求ほどデコード反復回数が多く、要求の終了時点もばらばらになる。クラウド間で要求を均等に割り当てても、生成長が偏れば処理終了までの時間に差が生じる。さらにクラウド内部で固定バッチを維持すると、短い応答が先に終了しても長い応答が終わるまで計算資源の一部が空いたままになる。Micoはこの二つの粒度の非効率を一体として扱う。軽量な予測器で応答長の区間を推定し、クラウド間でトークン処理量を均す。クラウド内部では、生成反復ごとに終了した要求のスロットを空け、待機中の新しい要求をバッチへ補充する。

著者らはGPT-2とGPT-NeoをNVIDIA A6000上で動かし、2〜9クラウドの均質構成を模した実験を実施した。3クラウド・200要求・バッチサイズ3の代表条件では、要求数ベースの固定バッチ方式と比べて累積KVキャッシュ長が44.89%減り、システム全体の要求処理スループットが1.79倍となる。別のクラウド数・バッチサイズを含むTable 1では最大2.22倍である。これらはクラウド間ネットワーク遅延やGPU異種性を固定した条件であり、実運用の全てのマルチクラウド環境に対する保証ではない。

## 問題設定と既存方式の不足

### 出力長が未知の要求をどう配るか

Webサービスの一般的なラウンドロビン方式は、要求数の均等化を優先する。しかしLLMでは同じ要求1件でも生成するトークン数が数十から数百に変わる。生成反復はデコード中の計算時間とKVキャッシュ占有を増やすため、要求数が等しいだけでは負荷は等しくならない。入力長も初期KV容量に影響し、長い入出力が同じノードに偏ればGPUメモリ不足を起こし得る。出力長を正確に事前確定することはできないが、短い応答と長い応答を大まかに分類できれば、クラウドごとの総トークン処理量を近づけられるというのがMicoの発想である。

### 固定バッチが長い要求に引きずられる

通常の自己回帰デコードでは各反復で1トークンを出し、各系列の過去キー・値をキャッシュする。長さの異なる複数系列をまとめると、先にEOSへ達した系列が残っている間も、他の系列は生成を続ける。完成した系列の結果を返すだけではバッチの並列度が落ちる。空いた場所へ新しい系列を挿入するには、系列ごとのトークン列、attention mask、KVの長さが変わることに対応しなければならない。単純なテンソル連結や注意層の複製には余計なメモリと計算が必要である。

先行研究のOrcaは反復単位スケジューリングの重要な基盤だが、著者らは既存の方式が単一推論エンジン内部の処理に焦点を当て、クラウド間での生成長による負荷差を直接解消しない点を課題としている。Micoは、クラウド間の割当を担当するQと、クラウド内の反復単位処理を担当するIを組み合わせる。両者は異なるボトルネックに効くため、片方だけを採用した場合の改善と統合した場合の改善を別々に評価している。

## 手法

### 1. DistilBERTによる応答長の区間予測

予測器の基盤は約6,600万パラメータのDistilBERTである。ユーザー要求の入力文を受け取り、対象LLMが返す応答のトークン長を、最大出力長を10等分した区間のいずれかに分類する。出力長の厳密な回帰値ではなく区間ラベルを選ぶのは、temperature、top-k、top-pなどのサンプリング条件で生成長が変動し、厳密なトークン数を当てることが困難だからである。区間中央の値を推定長として使えば、割当のための大まかな負荷指標になる。

学習にはAlpaca約52,000件とMath-Word-Problems約200,000件を使用する。クロスエントロピー損失、AdamW、初期学習率5×10^-5、バッチ32、3エポックで微調整する。実験ではAlpacaで85.37%、Math-Word-Problemsで80.69%の区間分類精度を報告する。新しいデータセットから約200件を使った追加微調整では、新データ検証82.5%となる一方、元データの精度が約0.9ポイント低下した。これは分布変化に対応できる可能性と、旧分布に対する忘却・劣化の両方を示す。予測の平均時間は約4.5ms/要求であり、無視できるゼロコストのオラクルではない。

誤分類の多くが隣接区間に収まると著者らは述べる。負荷配分では数トークンの誤差より、短い要求と長い要求を大まかに識別できることが重要になる。ただし分類器の学習時に使った生成モデル、応答形式、温度、入力分布が実運用と違えば予測がずれる。予測器の出力を確定値として扱わず、実際の処理量を見ながら更新する運用が必要となる。

### 2. クラウド間のトークン負荷配分

スケジューラは各要求の予測区間の中央値を推定応答長とする。要求を推定長ごとにグループ化し、長いグループから順にクラウドへ分配する。各クラウドに割り当てた推定トークン総量を維持し、できるだけ均衡するように要求を置く。グループ内の件数がクラウド数で割り切れない場合には、次のグループから要求を借りる柔軟な割当も行う。入力長と応答長の双方がKV占有に関係するため、単純な応答件数だけの均等化よりメモリ逼迫の危険を抑えやすい。

この設計は複雑な最適化問題を厳密に解くものではない。区間予測自体が粗いため、実行時間の厳密な予測に多くの計算を費やすより、負荷の大きな偏りを減らすことを狙う。原著ではネットワーク状況、地域、SLA、クラウドごとのGPU性能を割当の主要変数に含めない。現実の異種クラウドでは同じ推定トークン数でも実行時間が違うため、トークン量の均等化が完了時間の均等化と一致するとは限らない。

### 3. クラウド内部の反復単位バッチ補充

各クラウドの推論エンジンは、毎回の生成反復が終わるたびにEOSを出した要求を確認する。終了要求の結果を直ちに返し、不要になったKVキャッシュを解放する。待機中の要求があれば空いたバッチ位置へ新規入力を挿入し、次の反復から既存の未完了系列と並行処理する。既存系列のKVを維持しながら、新規系列に必要な初期トークン・KV・attention maskを組み合わせ、系列間の注意を混同しないようにする。原著の図5とアルゴリズムは、トークンベクトル、mask、KVの三者を同期して更新する流れを示す。

既存要求の注意はその要求の過去トークンだけに作用しなければならない。新しい要求を挿入する際にmaskを誤ると、別要求の情報を参照したり、既存要求の文脈が変わったりする。そのためMicoは単に空きスロットへ新しいテキストを代入するのではなく、KVとmaskの整合を維持する。挿入にかかる時間は著者の測定で1ms未満であり、約70msの通常生成反復に比べれば小さいとされる。ただしこの差は対象GPU、モデルサイズ、バッチ条件に依存する。実運用でKVのコピー、メモリ断片化、メモリ管理の競合が増える場合も同じ値になるとは限らない。

### 4. 動的バッチサイズとメモリ圧迫への対応

大きなバッチはGPUを効率よく使う反面、生成が進むにつれKVの占有が増え、メモリ不足の危険が高まる。原著は出力長予測に基づき、推定されるKV量が資源上限を超えない範囲でバッチに要求を加える考え方も説明する。反復途中で資源が逼迫すれば、一部の系列のトークン・mask・KVをRAMへ退避し、逆に余裕が生じたら新規要求を補充できるとする。ただしこの節は設計上の可能性の説明を含み、全ての退避・復帰条件について実機性能を網羅的に測定したものではない。バッチサイズの選び方と退避の転送費用は別途評価が必要である。

## 評価

### 定量結果と条件

### 評価条件・比較対象

原著§4では、生成モデルにGPT-2（最大系列長1,024）とGPT-Neo（最大系列長2,048）を使う。各推論ノードにNVIDIA A6000を割り当て、2、3、6、9クラウド相当の構成を評価する。要求は主にAlpacaの検証データからランダムに抽出する。予測器の訓練には前述のAlpacaとMath-Word-Problemsを使い、要求数、バッチサイズ、クラウド数を変える。比較は要求数均等配分＋固定バッチを基本線とし、出力長に基づく割当だけ、反復単位補充だけ、両方の統合という構成を比較する。原著のPDF抽出では上付きバーの記号が崩れやすいため、本稿ではQを長さ予測配分、Iを反復単位補充と呼び、ベースラインとの機能差で識別する。

ネットワーク性能とノード処理能力は意図的に同一条件とし、クラウド間の通信差を測らない。原著自身が、実運用トレースがないためランダム抽出で負荷分布をなるべく均衡させたと述べている。手動で不均衡な生成長分布を作った非正式な実験も記述されるが、数値が統一された公開トレースでの追試結果ではない。大規模な異種GPU群にそのまま外挿することは避けるべきである。

### 3クラウド・200要求・バッチ3の代表条件

Figure 7〜10では、3クラウド・200要求・バッチ3での推論を比較する。個別クラウドの累積KV長はそれぞれ41.54%、39.45%、50.68%減少した。個別クラウドの要求処理スループットはそれぞれ1.79倍、1.78倍、1.75倍となった。システム全体では累積KV長44.89%削減、要求処理スループット1.79倍と報告する。重要なのは「累積KV長」という指標であり、GPUのピークメモリ使用量が44.89%減ったことを意味しない。Figure 7の説明ではピークKV長は両方式で近い一方、Micoの方が早く処理を終えると述べる。したがって総KV占有量の時間積分に近い指標の改善と、最大VRAM使用量の改善は区別する必要がある。

バッチの完了を待たずに要求ごとに結果を返すことは比較側でも許されている。そのうえでMicoは空いたスロットに次の要求を補充できるため、バッチ処理中の遊休が減り、要求全体の完了時間が短縮する。Figure 9は完了要求数の累積分布を示し、固定バッチの階段状の完了と、Micoの継続的な処理進行の違いを表している。ここから、1.79倍の改善は単なる応答返却タイミングの違いだけではないと読める。

### 構成要素別の効果とモデル差

Figure 12は出力長予測に基づくクラウド間配分だけの効果、Figure 13は反復単位補充だけの効果を比較する。どちらも単独でスループットを改善するが、両方を組み合わせたMicoの改善がより大きい。クラウド間配分の改善は要求数や長さの偏りに依存し、バッチ補充の改善は同時実行系列の生成長のばらつきに依存する。単独の改善を単純に乗算した値が統合効果になるわけではない。著者らはランダムな要求選択の影響を抑えるため、関連するアブレーションで10回の独立実験の平均を使用した。

GPT-Neoを使ったFigure 14では、3クラウド、各種バッチサイズと要求数に対し、固定バッチ比較で1.22〜1.75倍のスループット改善を報告する。GPT-2のTable 1で見られる最大2.22倍をGPT-Neoにも当てはめることはできない。モデルによってデコードの演算密度、KV占有、バッチの並列効率が違い、改善幅が変わるためである。

## 限界

### 負の結果と適用範囲

第一に、原著は複数クラウドを想定するが、実験でクラウド間のネットワーク遅延とノードの処理能力差を意図的に除いている。実際にはクラウドごとにGPU型番、メモリ帯域、転送帯域、価格、可用性、地域レイテンシが異なる。生成トークン数が同じでも処理時間が等しいとは限らないため、推定トークン量の均等配分だけで最適化できるとは言えない。著者自身も結論でネットワーク状態と異種ノード性能を将来課題として挙げている。

第二に、予測器の分類精度は完全ではなく、Alpacaで85.37%、Math-Word-Problemsで80.69%にとどまる。新データに合わせると旧データで約0.9ポイントの低下が生じる。生成モデル、サンプリング温度、利用者分布、出力形式が変われば予測誤差が大きくなる可能性がある。予測誤差がどの程度スループットやP99レイテンシを悪化させるかについて、全ての現実的な分布変化を網羅した感度分析は示されない。

第三に、44.89%というメモリ改善は累積KVキャッシュ長の削減であって、GPU総VRAMピークの44.89%削減ではない。モデル重み、アクティベーション、一時バッファ、ランタイム予約領域は別に存在する。Figure 7ではピークKV長が両方式で同程度の条件もある。したがって、同じGPUへモデルや要求を何倍も詰め込めるという結論は導けない。

第四に、主要実験はGPT-2とGPT-Neoという比較的小型の旧世代モデルで行われた。現行の大規模MoE、GQA/MQA、paged attention、continuous batching、prefix caching、分離prefill/decode、量子化KVなどを統合した商用エンジンとの全面比較ではない。既にcontinuous batchingが実装されているサーバーにMicoの反復単位補充を追加した場合、固定バッチ基準の大きな改善が再現するとは限らない。競合する高度なスケジューラに対する追加利得は別途測る必要がある。

第五に、論文はスループットとKV占有を中心に測定しており、SLO違反率、P99 TTFT、P99 TPOT、クラウド間転送量、電力、GPUコスト、障害復旧時の挙動を統一した形で報告していない。バッチ補充は全体の完了件数を増やしても、長い要求の待ち時間や公平性を悪化させる可能性がある。実運用での優先度、タイムアウト、キャンセル、KV退避の公平性はこの評価からは判断できない。

第六に、反復途中での要求挿入はmaskとKVの厳密な管理を要する。実験での挿入時間1ms未満は特定実装の値であり、メモリ断片化、動的割当、複数GPU間のKV同期を含む環境での上限ではない。特に長文脈モデルでのKV再配置やCPU退避を行う場合には、転送費用が補充効果を相殺する条件があり得る。本文にあるRAM退避とバッチサイズの動的調整は設計案の性格が強く、全条件での性能保証ではない。

## 位置づけ・再監査判断

Micoの貢献は新しい注意カーネルや量子化方式ではなく、推論要求の処理量を二つの粒度で捉え直すことにある。予測した応答長をクラウド間の負荷配分へ用いる点と、終了した系列の資源を反復途中で次の系列へ渡す点を統合する。固定バッチの遊休が大きく、ノードの計算能力が比較的均質なサービスでは合理的な改善策となる。一方、既に高度な連続バッチを使う現代的なサービング環境では、主にクラウド間の生成長予測と実負荷の追跡が差分として残る。改善倍率は原著のベースライン条件に限定して読むべきである。

今回の意味品質再監査では著者公開の17ページの一次PDFについて、§3の予測・配分・補充の機構、§4の評価条件、Figure 7〜14、Table 1、§6の将来課題を照合した。主要な数値は一次PDFの該当箇所から確認し、特に累積KV長とピークVRAM、代表条件の1.79倍と最大2.22倍、GPT-2とGPT-Neoの条件差を明確に分離した。既存論文と同一canonical identity・同一target pathを維持し、GitHub原稿の固定blob SHAと全bytes SHA-256をキュー値に合わせた再監査差し替え候補として保存する。新規論文として二重登録してはならない。
