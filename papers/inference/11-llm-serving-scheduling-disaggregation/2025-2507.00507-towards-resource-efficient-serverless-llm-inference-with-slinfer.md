# SLINFER：異種CPU・GPUの共有でサーバーレスLLM推論の収容力を高める

## 概要

SLINFERは、個別モデルへの要求が少なく断続的に発生する私設大規模言語モデル（LLM）サービスを対象に、CPUとGPUの両方を推論実行先として扱い、同一ノードで複数モデルを弾力的に共有するシステムである。従来のサーバーレスLLM基盤は要求に応じてモデルを起動できても、各インスタンスへGPUを排他的に割り当てがちで、モデルが多数あるほどGPUを確保できず待ち行列が長くなる。論文の事前調査では、ServerlessLLMで各インスタンスへGPU全体を割り当てたときの平均GPUメモリ利用率が23%にとどまる条件が示される。SLINFERはこの未使用資源を他のLLMへ渡す。

重要なのは単なるモデル多重配置ではない。トークンごとに推論の実行時間が変わり、入力処理（prefill）が生成処理（decode）を遅延させるうえ、要求が増減すると鍵・値キャッシュ（KV cache）の必要容量も変化する。SLINFERは、①各要求の応答期限までの余裕（headroom）を使ったトークン単位の計算配分、②仮想実行検査（shadow validation）による新要求受入れ判定、③余裕容量を持つKVキャッシュの伸縮とメモリ操作の安全な順序付け、④小さく分裂したモデルインスタンスを統合する先行的退避と後追い集約を組み合わせる。

4台の32コアIntel Xeon 6462C CPUノードと4基のNVIDIA A100-80GB GPUノードで、3B・7B・13BモデルとAzure由来の要求分布を評価した。128モデルを扱う条件で、SLO達成要求数はGPU専用ServerlessLLM比86～154%、CPUも利用するServerlessLLM比47～62%、CPU/GPUを静的に半分ずつ共有する派生版比18～70%増えた。これは「全ての応答が同じ比率で高速化した」意味ではなく、期限内に処理できた要求の件数の比較である。小規模モデルが多いほど効果が大きく、大規模モデルが優勢になると共有利得は縮む。

## 問題設定：低頻度の多モデル負荷でGPU排他が非効率になる理由

サーバーレス推論は多数の異なるモデルを必要時に起動し、非稼働時には資源を回収する。モデルの呼出しが疎である場合、単一モデルを高速に処理する能力より、多数のモデルの重みを必要なときだけ配置し、期限を守って処理する収容力が重要になる。論文はHugging Faceのダウンロード統計とLMSYSの呼出し分布を動機として挙げ、8B以下の小規模モデルが多数を占める状況を重視する。GPU専用方式では空きGPUがないと待つ一方、すでに動いているGPUインスタンスは演算器とメモリを使い切っていないことがある。

新しいCPUは高度な行列演算拡張を持つ。SLINFERはIntel AMXのような行列演算支援を備えるCPUを独立した推論ノードとして利用し、CPUでは期限を守れないモデル・長い入力・厳しい期限に対してGPUへ戻す。CPUをGPUのKV転送補助に限定せず、軽いモデルの要求をCPUだけで完結させることが特徴である。ただしCPUならどのLLMでも同等に動くわけではない。CPU世代・モデル規模・文脈長ごとの処理時間を事前測定し、要求ごとの適合性を検査する。

一つのインスタンス内で複数要求を連続バッチ化すると演算効率が上がるが、CPUやGPUの共有資源が先に他モデルへ割り当てられていると、同じモデルの新要求を別インスタンスへ分散せざるを得ない。すると重みの複製と小バッチ化が同時に起きる。計算・メモリ・インスタンス統合を別々に最適化しても、片方の制約が他方の利益を相殺する。この相互作用を解くことが研究の中心である。

## 手法

### 1. 要求受付からトークン生成までの全体制御

要求到着時、SLINFERは同じモデルの既存インスタンスへ追加できるかを調べる。まずCPU側の候補を優先するが、対象CPUが行列演算支援を持たない、あるいはその要求の初回トークン時間（TTFT）・出力トークン間隔（TPOT）を守れない場合はGPU側を選ぶ。各候補へ要求を追加した場合の計算時間とKV容量を仮想的に検査し、既存要求を含めて期限を守れると予測できた場合だけ受け入れる。

既存インスタンスへ追加できない場合、同じノードの他モデルの小さなインスタンスを退避して既存インスタンスを拡張できないか試みる。それでも難しければ別ノードへ新インスタンスを起動する。新要求の入力処理はそのインスタンスで行い、生成段階では既存バッチに加わる。要求終了時にはKV領域を必要に応じて縮小し、一定の待機時間を超えた空インスタンスを回収する。モデル重みのロードはServerlessLLMの既存機構を流用している。

### 2. 期限余裕（headroom）を使うトークン単位のスケジューリング

SLINFERは同じノード上で複数のモデルインスタンスを並行に実行させるのではなく、インスタンス単位の推論反復を一回ずつ順番に割り当てる。各反復は新規入力のプレフィルまたは生成一トークン分のデコードに相当する。どのインスタンスを次に動かすかを、要求の残り猶予時間で決める。開始時刻を $ST$、現在時刻を $CT$、既生成トークン数を $O$ とすると、論文の式(1)は次の通りである。

$$\mathrm{headroom}=ST+\mathrm{TTFT}_{SLO}+O\,\mathrm{TPOT}_{SLO}-CT$$

値が小さい要求ほど次の出力を遅らせられず、負になると期限違反である。各インスタンスが処理する要求の緊急度を比較し、最も余裕のない要求を持つインスタンスへ次の反復を渡す。単に到着順や均等な時間片で回す方式と異なり、プレフィルで一度長く計算した後に既存デコードが詰まる状況を考慮する。処理を終えると生成トークン数と現在時刻を更新し、全候補の優先度を再計算する。

### 3. 実行時間の近似モデルと仮想実行検査

期限余裕だけでは、候補インスタンスへ新しい要求を追加した結果どれだけ計算が遅くなるか分からない。そこでプレフィルは入力トークン長に対する一次補間、デコードはバッチ数と平均トークン長の二次元線形補間で反復時間を推定する。デコードの注意計算はキャッシュ長、フィードフォワード計算はバッチ規模に依存するため、両方を説明変数にする。ハードウェアとモデルの組合せごとに事前測定した点から補間する。

新要求を受け入れる際は、実際のインスタンスへ投入する前に、仮想的に追加した状態で将来の反復順序を模擬する。新要求のプレフィルが遅れて初回応答期限を破る場合、既存要求がプレフィルに押されてトークン間隔を破る場合、新要求の参加後に各インスタンスのデコード反復が重くなり全体の期限を破る場合を区別する。負荷の変動と生成長の増加を見込んで各反復の予測時間に10%の安全余裕を加え、違反が予測されれば別インスタンスを試す。これはSLOを数学的に保証する証明ではなく、測定モデルに基づく予測的な受入れ制御である。

### 4. KVキャッシュ必要容量の推定

一つのモデルインスタンスのメモリは重みと要求ごとのKVキャッシュからなる。最終出力長は到着時に分からないため、現在までの生成長だけを合計すると必要量を過小評価する。論文の式(2)は、各トークンのKV消費量を $C$、要求数を $R$、要求 $r$ の入力長を $I_r$、既生成長を $O_r$、過去の平均出力長を $\bar O$、下限トークン数を $L_{min}$ として、

$$M_{require}=C\max\left(\sum_{r=1}^{R}\left[I_r+\max(O_r,\bar O)\right],L_{min}\right)$$

を用いる。要求が短くても一定の下限を確保し、既生成長が平均より長ければその実長を採用する。平均値を用いるため極端に長い生成では過小評価が残り得る。そこで次のウォーターマーク制御と再配置の救済策が必要になる。

### 5. ウォーターマークによる先行拡張・遅延縮小

論文が使用するページ化KV領域では、容量変更に伴ってブロックを再確保し、既存のKV内容をコピーする費用が発生する。32GBから16GBへの縮小には約0.3秒、32GBから64GBへの拡張には約1.9秒を要した評価例がある。要求ごとに必要量ぴったりへ変更すると、拡張と縮小が短時間で繰り返され、応答遅延を増やす。

SLINFERは必要容量 $M_{require}$ に余裕率 $w$ を掛け、推奨容量 $M_{recommend}=M_{require}(1+w)$ を定める。到着した要求を収容するには現在容量が不足するとき、必要量だけでなく推奨量まで先行拡張する。要求終了後はすぐ縮小せず、推奨容量にさらに余裕率を考慮しても現在容量より小さいときに縮小する。実験の標準設定は $w=25\%$ である。容量利用率はやや下がるが、繰返し再配置による時間損失を抑える。

### 6. 楽観的な予約と悲観的な実行判定の分離

複数モデルが同じノードでKV領域を伸縮させると、あるインスタンスの縮小が完了する前に別のインスタンスの拡張が始まり、一時的に物理メモリが不足する危険がある。SLINFERは要求を受付ける段階では縮小予定分を先に予算から差し引く楽観的な容量管理を使い、メモリ操作を発行する。一方、操作を実際に走らせる際は、縮小がまだ終わっていなければ旧容量を占有中と数える悲観的な使用量を使う。

縮小操作は先に実行し、拡張操作が物理容量を超えるおそれがあれば予約ステーションに待機させる。縮小完了通知が来たときに待機中の拡張を再評価して実行する。この二重管理により、要求を必要以上に拒否せず、非同期の解放完了を待たない早すぎる拡張によるメモリ不足も防ぐ。推奨容量まで確保できない場合には最低必要容量までの拡張を試し、それも無理なら期限余裕の大きい要求を退避・再スケジュールする。

### 7. インスタンス断片化の先行・後追い統合

同じモデルの要求が増えたとき、既存インスタンスを大きくする方がバッチ化に有利だが、周囲の別モデルが資源を占有していると新しい小インスタンスを作りがちになる。SLINFERの先行的統合は、拡張したいインスタンスより小さいバッチを持つ隣接インスタンスだけを退避候補にし、最小バッチから検討する。退避先でも期限を守れるか仮想実行検査を通す。これにより、大きなバッチを崩して新たな断片化を作ることを抑える。

それでも分裂した同一モデルの複数インスタンスが残る場合、後追い統合では新規要求を大きなバッチのインスタンスへ優先的に入れる。小さい方へ新しい仕事を入れないことで、既存要求が終了した後にそのインスタンスを回収しやすくする。両者は「すぐに移せるときは先行統合、すでに分裂したものは自然終了を促す」という役割分担であり、GPUを静的に半分ずつ割り当てる方式とは異なる。

## 評価

### 実験設定と比較の読み方

| 項目 | 論文の設定 |
|---|---|
| 計算資源 | 32コアIntel Xeon 6462C CPUノード4台、NVIDIA A100-80GB GPUノード4台 |
| 主要モデル | Llama-3.2-3B、Llama-2-7B、Llama-2-13B、いずれも16ビット |
| 推論エンジン | vLLM 0.5.2（GPU）、OpenVINO 2024.6.0（CPU） |
| 入出力長 | Azure LLM Conversationデータセットから標本化 |
| 呼出し分布 | Azure Serverless Traceの最初の30分を使用し、32/64/128関数へモデルを対応付け |
| SLO | TTFTは入力長 $L$ に応じ $\min(\max(0.5,L/512),8)$ 秒、TPOTは0.25秒 |
| 主な指標 | 期限内要求数、期限達成率、GPU使用台数、初回トークン時間、バッチ規模 |
| 比較 | sllm=GPU専用ServerlessLLM、sllm+c=CPU対応追加、sllm+c+s=CPU/GPUを静的に分割共有 |

冷却状態からのモデルロードが生じる要求については、ロード時間に相当する猶予をTTFTへ追加する。したがって厳密に全要求を同一の固定TTFTで評価した数値と比較できない。いずれの比較系も同じエンジンを使用し、SLINFERだけ高速な推論カーネルを用いた比較ではない。

| CPUノードを追加する感度評価 | GPUノード1台の収容力にCPU約3～4台が必要 | CPUは代替になっても単純にGPUと等価ではない |
| モデル混在のGPU利用解析 | sllmより平均バッチサイズ74%増加 | インスタンス統合によるバッチ化効果 |

少数モデルの条件ではGPU専用のsllmが中央値TTFTで勝つ場合がある。SLINFERはCPUを優先するため、低負荷での単一要求最速化を狙うシステムではない。高負荷ではSLO期限を超えると見込まれた要求が事前に破棄されるため、TTFTの累積分布が100%へ達しないこともある。これは性能改善の読み方を左右する重要な条件である。

### プレフィルとデコードを分離した場合の負の結果

| 64モデルの条件 | 同一インスタンスで両段階実行 | 段階別インスタンス分離 |
|---|---:|---:|
| SLINFERの平均GPU使用数 | 2.5 | 2.9 |
| SLINFERのSLO達成率 | 99% | 98% |
| 静的共有sllm+c+sの平均GPU使用数 | 3.6 | 3.9 |
| 静的共有sllm+c+sのSLO達成率 | 93% | 70% |

この評価ではノード間通信帯域を100Gbpsとした。小規模モデルの低頻度呼出しでは、プレフィル専用インスタンスが平均93%の時間を起動・待機に費やす。分離アーキテクチャが一般に無効という意味ではなく、低頻度・多モデルのこの条件では段階別インスタンスの常駐費用が利益を上回った、という負の結果である。128モデルではSLINFERのSLO達成率が同居86%、分離69%となり、負荷の増加とともに不利が顕著になる。

### 感度分析と境界条件

ウォーターマークを0%にするとKV領域の伸縮操作がインスタンス寿命の11.3%を占めたのに対し、25%では約1.4%となり、容量予測不足による要求移動率は0～0.3%に収まった。余裕率を大きくし続けても追加の利益は小さく、空きメモリを使うだけなので論文は低めの25%を推奨する。

長い入力を含むLongBenchでは、CPUの初回トークン時間が期限を守れずGPUへ切り替える。論文の環境ではCPUが8秒のTTFT期限で扱える入力は約8.4kトークンまでで、32k入力は不適合である。比較の静的共有方式はLongBenchで63.4%の期限違反を生じた。別のBurstGPT呼出し分布を64モデルへ配分した評価では、毎秒4要求の条件で静的共有の期限違反7.7%に対しSLINFERは1.0%であった。負荷や生成長が変わっても同一の絶対効果が保証されるわけではない。

## 既存方式との相違と実装上の意味

ServerlessLLMは高速ロードを実現するが、要求のたびにGPUを占有するという配分方式が多モデルの密度を制約する。静的な複数モデル共有はGPUの未使用部分を埋められる一方、プレフィルとデコードの変動、KVキャッシュ増減、モデル別の期限差を反映しにくい。SLINFERは既存ローダを利用したまま、トークン単位の時間予算、KV容量の二重追跡、断片化の統合を同じ制御面で扱う。

CPUを使うこと自体は、GPUから重みやKVを退避するPowerInfer・NEO型の補助処理とも異なる。SLINFERのCPUノードは小規模モデルを単独で推論し、GPUが必要な要求だけをGPUへ送る。さらにプレフィル・デコードの分離は高負荷の単一モデルに有利な場合があるが、この論文の低頻度多モデル設定ではむしろ非効率という条件依存性を示した。

## 限界・未評価事項

最も大きい制約は対象負荷である。小～中規模モデルの多数同時配備と低頻度呼出しに最適化されており、巨大モデルや長入力でCPUが期限を守れない場合は排他的GPU配分へ退避する。実験のCPUはAMXを備える比較的新しい世代であり、古いCPU、異なるGPU、複数のメモリ容量、ネットワーク条件に同じ比率を外挿できない。16ビットモデル中心の評価で、量子化によるさらなる収容力改善は別条件として述べられるが、全てのモデルで一律に実証されたわけではない。

計算時間は補間モデル、出力長は過去平均に依存する。極端な入力・生成長や未経験の負荷では予測誤差が増え、仮想実行検査は期限の形式的保証にならない。メモリ不足時には要求の退避・再スケジュールが発生し得る。実装評価は特定のエンジンとAzure由来の模擬された多モデル呼出し分布であり、任意の実サービスにおける費用削減率、エネルギー削減率、ハードウェア世代間の再現性までは測定していない。
