# Cauchy: A Cost-Efficient LLM Serving System through Adaptive Heterogeneous Deployment

## 概要

大規模言語モデルのオンライン推論は、入力文をまとめて処理する入力一括処理（prefill）と、生成トークンを逐次追加する復号（decode）に分かれる。前者は行列積が多く演算性能に依存しやすい一方、後者はモデル重みと鍵値キャッシュ（Key-Value cache; KVキャッシュ）の読み出しが支配的になり、メモリ帯域に依存しやすい。同じGPUが両段階で最も費用効率のよい選択になるとは限らない。さらに文書要約、チャット、長文生成では入力長と出力長が大きく異なり、最適なGPU構成も変わる。

Cauchyは、計算能力とメモリ帯域が異なるGPUを、prefillとdecodeへ適切に割り当てる大規模言語モデル配信基盤である。基本単位はGPU Comboと呼ばれる組合せで、例えば「prefill用H800を2基、decode用H20を4基」のように、両段階へGPUの種類と台数を指定する。要求分布、モデル構造、GPU性能、価格を使って組合せの処理トークン数/米ドルを推定し、必要な有効処理量を満たす配置を整数線形計画で選ぶ。

配置だけでなく、要求を組合せ間で配る上位スケジューラ、組合せ内で空きGPUを活用する下位スケジューラ、負荷変動に応じて組合せを増減する自動伸縮機構を統合する。異種GPU間でKVを転送する費用を抑えるため、層ごとのKVを複数経路で並列転送し、計算と通信を重ねる。これにより、単純にGPUの種類を混ぜるだけでなく、**prefillとdecodeの役割・配分・運用中の負荷変化**を一体で扱う。

24基の異種GPUを使ったLlama-3.1-8Bの評価では、異種GPU配置を扱う既存方式Mélangeと比較して、費用当たり処理トークン数を16.4〜38.3%改善し、平均要求遅延を21.2〜59.1%短縮する。効果は使用GPUの単価、入力と出力の比、要求到着率、サービス品質目標に依存し、任意のGPU群で同じ改善率が保証されるわけではない。

## 問題設定

prefillでは入力長`R_in`に対する注意計算とフィードフォワード層の行列演算が大きく、演算性能当たりの価格が重要になる。decodeでは生成長`R_out`に沿ってモデル重みと増大するKVを繰り返し読み出すため、メモリ帯域当たりの価格が重要になる。論文のGPU仕様表では、H800-SXMは計算性能が高くprefill向き、H20-NVLは帯域当たりの費用が低くdecode向きと位置付けられる。

従来のGPU割当では、一つのGPU上で両段階を処理する集約方式、またはprefillとdecodeを分離しても同種GPUへ割り当てる方式が多い。分離すれば計算・帯域特性に合わせた配置ができる反面、prefillで生成したKVをdecode側へ転送する必要がある。入力が非常に長い文書要約ではこの転送費用が大きく、集約方式の方が適する場合もある。短い入力から長い出力を生成する場合はdecodeの比率が高く、分離配置が有利になりやすい。

異種GPUの選択は単に「高性能GPUをprefillへ、安いGPUをdecodeへ」と決めるだけでは済まない。GPUの在庫、要求量、出力長、遅延目標、KV転送費用、組合せ内の処理能力が絡み合うためである。さらに要求到着率は時間で変動し、平均負荷だけを見た固定配置ではピーク時に品質目標を破り、閑散時にはGPUを過剰確保する。

Cauchyの目的は、初回トークンまでの遅延や生成トークン間隔を満たす有効処理量（goodput）を制約として、費用当たり処理トークン数（Tokens/USD）を高めることにある。単なるピークスループットではなく、**遅延のサービス水準を満たして完了した要求量**を考慮する。

## 手法

### GPU Comboと処理段階別費用モデル

GPU Comboはprefillとdecodeへ割り当てるGPUの種類・台数の組である。例えば`<2×H800,4×H20>`はH800を2基でprefill、H20を4基でdecodeへ割り当てる。論文は異種構成だけでなく、集約実行に適した同種GPUの組合せも候補に含める。同じGPU対でもprefillとdecodeの役割を逆にすると費用効率が異なるため、候補の向きまで区別する。

prefillの処理時間は、モデル層数、隠れ幅、MLP幅、入力長から見積もった浮動小数点演算数を、割当GPUの演算性能で割って近似する。論文の係数では注意の二次項が`C1=4lh`、線形項が`C2=8lh²+6lhi`であり、入力長に対する演算量を`B(C1 R_in²+C2 R_in)`とする。ここで`B`はバッチ数、`l`は層数、`h`は隠れ幅、`i`は中間幅である。

decodeはモデル重みの読み出し量`C3`と1トークン当たりKV量`C4`を用い、出力トークンが増えるにつれて必要なメモリ読み出し量が増えると近似する。モデル重みの大きさ、KVヘッド数、精度、入力長、生成長、バッチ数、GPUメモリ帯域を用いてdecodeのトークン毎秒を推定する。prefillとdecodeの性能を組み合わせ、各GPUの時間単価で割ることで、候補Comboの費用当たり処理トークン数を計算する。

このモデルはハードウェアの理論性能だけで最終決定しない。候補の有効処理量は実際のプロファイル測定を使い、遅延目標の下でどれだけの要求を処理できるかを把握する。推定費用効率と測定済みgoodputを併用する点が、単純なTFLOPS/価格順の選択と異なる。

### Combo候補の絞り込みと配置最適化

候補選定では、入力・出力長とモデル構造からprefillとdecodeの重要度を見積もり、利用可能なGPU組合せの費用効率を計算する。向きの違う組合せで一方が明らかに劣る場合は除外し、費用効率とgoodputの良い候補を残す。論文の3種類のGPUを使う構成では、候補組合せは最大12種類程度になり、prefill:decodeの台数比は1:1から2:6まで検討する。

配置段階では、各モデル・負荷に割り当てるCombo数を整数変数とし、必要なgoodputを満たすこと、各GPU種別の総使用台数が在庫を超えないことを制約にする。目的関数は、費用の最小化と費用効率の最大化を合わせた指標である。最も費用効率の良いComboが必ずしも最安で必要量を満たすとは限らないため、過剰な処理能力を買わずに済む組合せを選ぶ。解法にはPythonの整数線形計画ライブラリPuLPを使い、実験の候補規模では通常20〜50ミリ秒で解が得られる。

例えば残りgoodputが0.80要求/秒のとき、費用効率は少し低くても0.82要求/秒を1.09ドル/時で処理できるA800構成を、1.23要求/秒を1.50ドル/時で処理できるH20構成より選ぶ例が示される。単純な最大費用効率の追求では余剰容量を高く買うことがあるため、必要処理量に見合う最小の組合せを選ぶ。

### 組合せ間の有効処理量重み付き配分

配置した複数Comboへ要求を振り分ける上位スケジューラは、有効処理量重み付きラウンドロビン（goodput-weighted round robin）を用いる。各Comboのgoodputを全Comboのgoodput合計で割り、処理能力に比例して要求を配分する。単純な順番配分では低速Comboへ過剰な要求が流れ、待ち行列が伸びる。残りトークン数だけで重み付けしても、GPUの種類による性能差やSLOの達成能力を正確に反映できない。

この配分は、異種Comboが混在するクラスタで特に重要である。高性能Comboには多くの要求を、低速Comboにはその能力に見合う要求を渡すことで、遅いComboが全体のボトルネックになることを避ける。Comboの追加・削除時には重みを更新し、配置変化へ追従する。

### 組合せ内の機会利用スケジューリング

下位スケジューラは、prefill担当とdecode担当のGPUの空き状態を監視し、固定のprefill→decode経路に縛られずに要求を処理する。例えばdecode GPUが空いているときには、そのGPU上でprefillからdecodeまでの集約実行を行い、prefill GPUが空いているときも状況に応じて全段階を処理する。これにより、片方の段階のGPUが待っているのにもう片方だけが混雑する状況を減らす。

実装では残りトークン数や待ち行列を軽量な監視で収集し、要求の処理先を柔軟に変更する。処理経路の変更はメタデータで制御し、不要なKV移動や高価なプロセス切替を避ける。連続バッチ処理（continuous batching）と共存するよう設計されているため、組合せ内での空きGPUの活用が有効処理量の改善につながる。

### Combo単位の自動伸縮

負荷の変化には、Comboを単位として追加・削除する。要求到着率（Queries Per Second; QPS）を移動窓で監視し、基本設定では2分間の平均負荷が現在の処理能力から20%以上ずれた場合に反応する。増加時には不足分を埋める費用効率の良いComboを追加し、減少時には余剰処理能力に近いComboを一定の猶予を置いて削除する。短い負荷の揺らぎへ過敏に反応しないよう、削除前に30秒の猶予を置く。

さらに約30分間の安定した負荷が続く場合は、クラスタ全体の最適配置を再計算して現在の配置と照合する。短期の反応的な伸縮と長期の配置最適化を分けることで、突発負荷に対応しつつ、時間が経つにつれて費用効率の悪い配置が固定されるのを防ぐ。

### KVキャッシュ転送の並列化

prefillとdecodeを異なるGPUへ分離すると、prefill側で生成したKVをdecode側へ移す必要がある。CauchyはKVを層単位に分けて専用の複数経路から先行送信し、計算と通信を重ねる。受信側ではCPUメモリへ一時的にKVを受け、必要な段階でGPUへ移す。GlooのTCP転送を使い、層単位の送信を重ねることで単一の一括転送による待ち時間を減らす。

この最適化は異種GPU配置の利得を通信費用が打ち消さないために必要である。ただしCPUバッファや転送経路を追加するため、GPUだけでなくCPUメモリ、ネットワーク帯域、転送制御の費用も考慮する必要がある。

## 主要結果

### 既存の異種GPU配置との比較

Mélangeは異なる種類のGPUを割り当てるが、prefillとdecodeを同じGPUで処理する集約構成を中心に静的配置を選ぶ。Cauchyからprefill/decode分離を取り除いたCauchy*は、Mélangeに対して費用効率を7.8〜17.1%改善する。分離可能な異種GPU Comboを使う完全版では改善率が16.4〜38.3%となり、単なる動的割当以上に、処理段階の違いを使ったGPU選択が有効であることを示す。

同じ比較で、Cauchyは平均の要求全体遅延を21.2〜59.1%短縮し、初回トークンまでの時間（Time To First Token; TTFT）を28.5〜95.1%、トークン間隔（Time Between Tokens; TBT）を18.9〜61.5%短縮する。これらは評価した三種類の負荷における範囲であり、38.3%と59.1%が同じ負荷で同時に得られたと断定するべきではない。

### 配置最適化と階層スケジューラの効果

Combo配置の目的関数を比較すると、費用効率だけを最大化する方式（MCE-LP）より、費用と費用効率を併せて考える提案方式（CO-LP）が高い費用効率を示す。DailyMailではMCE-LP比で46.9%改善し、最小費用だけを追う方式（MC-LP）に対しても28.9%の費用優位がある。これは処理能力を過剰に買わず、必要なgoodputを満たす組合せを選ぶ効果である。

Combo間の要求配分では、有効処理量重み付きラウンドロビンが単純ラウンドロビンより低遅延となる。LongWriterで平均遅延を25.4%短縮し、DailyMail・LongWriterではトークン数重み付き方式に対しても3〜6%改善する。GPUの処理能力が異なるため、残りトークン数だけでは要求を適切に配分できないことを示す。

Combo内の機会利用スケジューラは、prefill1基・decode1基の構成で通常のラウンドロビンよりTokens/USDを8.7%改善し、goodputを8.4%高め、平均E2E遅延を8.5%短縮する。prefill1基・decode2基の構成でも費用効率が6.9%、goodputが8.3%改善する。decode担当GPUが増えると改善幅は条件によって小さくなるが、空きGPUで処理を肩代わりする効果は残る。

### 負荷変動とKV転送

自動伸縮を無効にした静的配置に比べ、Combo単位の伸縮を有効にすると90パーセンタイル要求遅延がDailyMailで25.57秒から21.88秒、ShareGPTで11.16秒から10.68秒、LongWriterで36.77秒から32.83秒へ改善する。これは平均負荷に合わせた固定配置ではピーク時に処理能力が不足し、要求が滞留することを示す。

KV転送では、2048トークンの入力に対する転送遅延が通常の一括転送625ミリ秒から、層別並列転送85ミリ秒へ短縮し、7.4倍の改善となる。256〜2048トークンの範囲でも3.4〜5.5倍の改善が報告され、転送並列度8付近で最も良い条件がある。16経路まで増やすと制御スレッドの負担が増え、利得は頭打ちになる。これらは**KV転送処理の遅延**であり、全推論の7.4倍高速化を意味しない。

## 既存研究との差

MélangeはGPUの種類を選ぶことでクラスタ全体の費用を削減するが、prefillとdecodeの資源特性を独立した配置単位として最適化しない。Cauchyは、GPUの演算性能・メモリ帯域・価格と要求の入出力長を組み合わせ、prefill/decodeの異種ペアを配置の基本単位とする点で異なる。

DistServeなどのprefill/decode分離方式は両段階を分けて遅延と有効処理量を改善するが、同種GPUを使う構成ではGPUごとの費用効率の違いを活用し切れない。Cauchyは段階別のGPU種類・台数を同時に選び、必要なgoodputとGPU在庫を制約とした配置最適化を行う。

さらに、配置計画だけで終わらず、Combo間・Combo内の二段階スケジューラ、自動伸縮、KV転送の並列化まで一体化する。配置が最適でも要求の振り分けが偏ればGPUが遊ぶため、運用中のスケジューリングを含めて評価している点が特徴である。

## 限界・運用上の注意

評価モデルはLlama-3.1-8Bで、GPUはH800、H20、A800の3種類に限られる。論文の価格表は2025年6月時点の仕様・時間単価を前提としており、地域やクラウド契約が異なれば最適な組合せは変わる。GPUの種類が多い場合、候補数と事前プロファイル費用も増える。

prefillとdecodeを分離するとKV転送とネットワークが新たな律速要因になる。論文は層別並列転送で費用を下げるが、ネットワーク帯域が小さい環境、非常に長い入力、複数ノード間の混雑が激しい環境では、集約配置の方が有利な場合がある。Cauchy自身も集約GPU Comboを候補に含めるのはこのためである。

推定モデルはprefillを演算律速、decodeを帯域律速と近似する。実際にはバッチサイズ、量子化、注意実装、KVキャッシュ配置、カーネル効率、ネットワーク負荷などで律速が変わるため、理論的な費用効率だけでは正確な配置を選べない。論文はgoodputの事前プロファイルを併用するが、新しいモデルやGPUの導入時には再測定が必要になる。

自動伸縮は新しいComboを立ち上げる時間、GPU在庫、短期的な要求変動に依存する。2分間の窓と20%閾値は実験設定であり、急激なトラフィックの立上がりに対して即時に十分なGPUを確保できるとは限らない。静的配置に対する遅延改善も、論文の到着率とGPU資源を前提とする。

最後に、Cauchyはクラスタ規模の配置・スケジューリング方式であり、単一GPU上の推論カーネルを直接高速化する研究ではない。Windows上の単一コンシューマGPUへそのまま適用できる方式ではなく、複数の異種GPUを保有し、モデル配信のSLOと運用費用を最適化したい環境で主に価値がある。
