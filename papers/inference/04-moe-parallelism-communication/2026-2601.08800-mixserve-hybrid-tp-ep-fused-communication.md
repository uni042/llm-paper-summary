# MixServe: An Automatic Distributed Serving System for MoE Models with Hybrid Parallelism Based on Fused Communication Algorithm

> モデル形状と階層ネットワーク帯域からTP・DP・EP・PP構成を自動選択し、ノード内の全削減通信とノード間の全対全通信を融合・重畳して、MoE配信のTTFTを最大3.80倍、スループットを最大50.3%改善する。

## 概要
MixServeは、分散MoE推論でノード内帯域とノード間帯域が大きく異なるにもかかわらず、テンソル並列と専門家並列を経験則で固定すると通信効率を落とす問題を扱う。オフライン段階でモデル形状、計算性能、ノード内・ノード間の帯域とネットワーク構成を入力し、テンソル並列・データ並列・専門家並列・パイプライン並列の候補ごとに計算時間、通信時間、待ち時間、メモリ制約を見積もって構成を自動選択する。選ばれた混合TP-EP構成では、全削減通信（All-Reduce）を削減散布（Reduce-Scatter）と全収集（All-Gather）へ分解し、専門家間の全対全通信（All-to-All）と非同期に融合してノード内通信とノード間通信を重ねる。DeepSeek-R1とQwen3-235B-A22BをH20 GPU群とAscend 910B NPU群で評価し、比較方式に対してTTFTを1.08〜3.80倍、ITLを1.03〜1.66倍高速化し、総トークンスループットを5.2〜50.3%改善した。

MixServeは、モデルの層構成・専門家数・活性専門家数・バッチ・系列長と、計算性能・ノード内／ノード間帯域・トポロジを一つの費用モデルへ入れ、TP・DP・EP・PPの候補を自動評価する。そのうえでMoEブロックの通信を、ノード内TPのReduce-Scatter／All-Gatherとノード間EPのDispatch／Combineへ分解し、同じhidden state断片に対する通信を非同期に重ねる融合AR-A2Aを導入する。単なる並列度探索ではなく、選択した階層並列構成専用の通信アルゴリズムまで共同設計する点が中心的な新規性である。
## 問題設定
大規模MoEは総パラメータが巨大なため複数GPU/NPU・複数ノードへ分散する必要があるが、ノード内高速リンクとノード間ネットワークの帯域差が大きく、単一の並列方式を全通信域へ適用すると性能を失う。テンソル並列はAll-Reduceを頻繁に行うためノード間へ広げると帯域不足で急激に悪化し、専門家並列はAll-to-Allを使うため多ノードへ広げやすい一方、並列度が高いと専門家ごとの負荷不均衡とトークン通信量が問題になる。Attention側のデータ並列とMoE側の専門家並列の比率もネットワーク・メモリ・要求率によって最適値が変わるため、経験則だけでは構成を一意に決められない。
## 新規性
MixServeは、モデルの層構成・専門家数・活性専門家数・バッチ・系列長と、計算性能・ノード内／ノード間帯域・トポロジを一つの費用モデルへ入れ、TP・DP・EP・PPの候補を自動評価する。そのうえでMoEブロックの通信を、ノード内TPのReduce-Scatter／All-Gatherとノード間EPのDispatch／Combineへ分解し、同じhidden state断片に対する通信を非同期に重ねる融合AR-A2Aを導入する。単なる並列度探索ではなく、選択した階層並列構成専用の通信アルゴリズムまで共同設計する点が中心的な新規性である。
## 手法
### 手法のあらまし
MixServeはオフライン分析とオンライン配信の二段階で動く。オフラインではモデル形状といくつかのバッチ・系列長でのプロファイル値を取得し、GPU/NPUの計算性能、ノード内リンク、ノード間リンク、ノード数、各ノードのデバイス数を読み込む。並列戦略はAttentionとMoEを別々にTP・DP・EPへ分割し、必要に応じてDecoder層をPPへ分ける文法として列挙する。各候補について、All-ReduceをReduce-ScatterとAll-Gatherに分けた通信量、専門家All-to-Allの通信量、計算量、PPの点対点通信、要求率に基づくM/M/1近似の待ち時間を計算する。さらにAttention重み、MoE専門家重み、KVキャッシュがデバイスメモリへ収まる制約を課し、TTFT・ITL・スループットの推定値から目的に合う構成を選ぶ。オンラインでは選択結果に合わせて重みを分割・読み込み、Attention側のノード内TP／ノード間DPとMoE側のノード内TP／ノード間EPを構築する。MoEへ入るDispatchでは、各ノード内でhidden dimensionをTP shardへ分けた後、同じTP rank間だけをノード間Pairwise通信し、受信した断片ごとにノード内All-Gatherを重ねる。MoEから戻るCombineでは、ノード間Pairwise通信とノード内Reduce-Scatterを非同期に進め、top-k重み付き結果を集約した後にAll-Gatherで完全hidden stateを復元する。この構成により、低速なノード間通信のデータ量をTP shard分だけ減らしつつ、その時間を高速なノード内通信と重ねる。DPとEPの並列度が一致しない場合も、DPが大きい側では専門家重みを複製し、EPが大きい側では重複hidden stateを削除して通信群を調整する。

### 階層ネットワーク対応の自動並列分析器
TP・DP・EP・PPの候補を、モデルの演算量・専門家数・活性専門家数とハードウェアの計算性能・帯域・メモリ制約から評価する。通信についてはTPのAll-ReduceをReduce-ScatterとAll-Gatherに、EPのAll-to-AllをDispatchとCombineに分けてデータ量と通信回数をモデル化する。さらに要求率と1トークン当たり処理時間からM/M/1近似の待ち時間を導入し、プリフィルでは入力長、デコードでは系列長1としてTTFTとITLを見積もる。これにより、単純な通信量最小化ではなく、メモリ制約とオンライン待ちを含む構成選択を行う。

### ノード内TP・ノード間EPの混合分割
各ノード内では高帯域リンクを使うTPを採用し、ノード間では専門家を分けるEPを採用する。Attentionはノード内TPとノード間DP、MoEはノード内TPとノード間EPとして分けることで、ノードを跨ぐAll-Reduceを避ける。MoEのhidden stateはTP shardされた状態でノード間へ送るため、純粋なEPより一回当たり通信量をノード内TP並列度ぶん縮小できる。DPとEPの並列度が異なるケースも候補として扱い、重み複製とhidden state重複削除のトレードオフを費用モデルで選択する。

### 融合Reduce-Scatter／Combine通信
MoE出力側では、各ノード間で同じTP rank同士がPairwise方式でhidden state断片を非同期交換するのと並行して、到着済み断片に対してノード内Reduce-Scatterとtop-k重み付けを進める。全ノード分の断片を処理した後だけノード内All-Gatherを行い、完全なhidden stateへ戻す。ノード間Combine通信とノード内Reduce-Scatterを同時進行させるため、逐次実行時の通信時間和ではなく長い側へ近づける。代わりに各rankには出力相当の一時領域が必要で、総空間量はバッチ・系列長・hidden次元・ノード内デバイス数に比例する。

### 融合All-Gather／Dispatch通信
MoE入力側では、各rankが担当するhidden次元断片について専門家ルーティングを行い、同じTP rankの別ノードへ必要断片だけを非同期送信する。受信した専門家別断片はノード内All-Gatherで復元するが、最初と最後の通信を除いてノード間Dispatchとノード内All-Gatherを互いに重ねる。ノード内のローカル断片は送受信不要なので通信回数を削減し、追加一時領域は定数規模とする。この方式により、専門家並列のノード間通信量削減とTP側の高速ノード内帯域利用を同時に達成する。

### 全体のデータ／制御の流れ
オフライン分析器が最適な並列度を出し、オンラインの重みローダ／分割器がその構成に合わせてAttention・MoE重みを配置する。配信時のメモリ管理と要求スケジューリングはvLLM系の仕組みを利用し、混合通信群をモデルのforward経路へ注入する。H20環境ではTutel、Ascend 910B環境ではvLLMを基盤とし、同一設計をGPUとNPUの異なる階層ネットワークへ適用する。
## 評価条件
- **ハードウェア**: 2台のサーバーに各8枚のNVIDIA H20 96GBを搭載した16 GPU環境と、4台のAtlas 800T A2に各8個のAscend 910B 64GBを搭載した32 NPU環境を用いる。H20はノード内NVLink 4.0最大900GB/s、ノード間InfiniBand 400Gbps。910Bはノード内HCCS最大480Gbps、ノード間RoCE最大200Gbps。
- **ソフトウェア**: H20クラスタではTutel、Ascend 910BクラスタではvLLMを基盤にMixServeを実装する。比較ではvLLMのTP+PP、DP+EP構成と、H20でTutelのTP+EP構成を用い、TP並列度4・8など複数の分割を比較する。
- **比較対象**: vLLM TP+PP、vLLM DP+EP、Tutel TP+EP、TP並列度4/8の複数構成、融合通信の同期版
DeepSeek-R1 671B（256 routed エキスパート＋1 shared エキスパート、1トークン当たり37B活性）とQwen3-235B-A22B（128 エキスパート、22B活性）をShareGPT-V3で評価する。要求率を2・4・8 req/s、最大バッチ16、最大系列長4096に設定し、TTFT、ITL、総トークンスループットを測定する。主要結果は10回実行の平均で、誤差棒は標準偏差。並列戦略のDP/EP比を3通りに変える試験と、融合AR-A2Aを同期実行／非同期重畳する試験で構成要素を分解する。
2種類の特定クラスタと2種類の大規模MoEに限定した実機評価であり、他のGPU世代、Ethernetのみのネットワーク、専門家偏りが極端な独自ワークロード、障害時の再構成は測らない。分析器の待ち時間はM/M/1近似を使うため、実際の要求到着やサービス時間が指数分布から外れる場合の予測精度は別途検証が必要である。
## 主要結果
MixServeはDeepSeek-R1とQwen3-235B-A22Bの両方、H20 GPUとAscend 910B NPUの両環境で比較構成より低い応答遅延と高いスループットを示した。TTFTは1.08〜3.80倍、ITLは1.03〜1.66倍高速化し、総トークンスループットは5.2〜50.3%向上する。特にノード間帯域が相対的に遅いAscend環境では純粋なTP+PPとの差が大きく、H20環境では通信改善幅は小さめでもスループット向上が大きい。DPとEPの最適比はハードウェアで変わり、分析器が固定経験則ではなくネットワーク構成に応じて選び直す必要性も確認される。

- TTFT高速化 / 1.08〜3.80倍 (比較対象: vLLM/Tutelの各並列構成; 条件: DeepSeek-R1/Qwen3、H20・Ascend 910B、2/4/8 req/s) — プリフィルは通信量が大きく、ノード内TPとノード間EPを融合して重ねる効果が最も強く現れる。

- Ascend 910B上のDeepSeek-R1 TTFT / vLLM TP+PP比2.67倍、vLLM DP+EP比1.70倍 (比較対象: vLLM; 条件: 4ノード×8 Ascend 910B) — 低速なノード間RoCEへAll-Reduceを広げる構成を避け、階層帯域を意識した混合並列が大きく効く。

- Ascend 910B上のQwen3 TTFT / vLLM TP+PP比3.80倍、DP+EP比1.32〜1.93倍 (比較対象: vLLM; 条件: Qwen3-235B-A22B、32 NPU) — モデル形状と専門家構成が異なっても自動選択と融合通信の利得が維持される。

- ITL高速化 / 1.03〜1.66倍 (比較対象: vLLM/Tutel; 条件: 全評価構成) — デコードはプリフィルより通信量が小さいためTTFTほど大きくないが、全条件で改善方向を維持する。

- Ascend 910B上のITL / DeepSeek-R1 227.33ms→160.06ms、Qwen3 134.27ms→81.1ms (比較対象: vLLM TP+PP; 条件: Ascend 910Bクラスタ) — それぞれ1.42倍と1.66倍の高速化で、融合通信がデコード段階にも効く。

- 総トークンスループット / 5.2〜50.3%向上 (比較対象: 既存並列構成; 条件: 全評価構成) — 遅延削減だけでなく、通信待ちが短くなることで同じクラスタが処理できるトークン数も増える。

- H20上のDeepSeek-R1スループット / 362.78→545.23 トークン/s（+50.3%） (比較対象: vLLM TP+PP; 条件: 2ノード×8 H20) — 高帯域NVLink環境でもノード間通信との重畳が大きな処理量改善につながる。

- H20上のQwen3スループット / 435.82→625.45 トークン/s（+43.5%） (比較対象: vLLM TP+PP; 条件: 2ノード×8 H20) — 別MoE構成でも同様に大きなスループット利得を得る。

- DP/EP構成依存性 / AscendではDP=EPが良好、H20ではDP<EPが最良例 (比較対象: 複数DP/EP比; 条件: Qwen3例: Ascend 383.14ms・150.08 トークン/s、H20最小TTFT 228.99ms) — 単一の並列比を全クラスタへ固定せず、帯域階層に合わせて自動選択する設計を支持する。

### 負の結果・境界条件
- H20ではTTFT高速化が1.08〜1.23倍、ITLが1.03〜1.16倍に留まり、Ascend環境ほど劇的ではない。これはノード内NVLinkが高速で既存構成も比較的効率的なためである。融合RS-Combineは出力相当の一時領域を各rankに追加し、時間短縮とメモリを交換する。自動分析器の待ち時間モデルはM/M/1近似で、重い裾を持つ要求やバースト到着の精度は示されない。また公式コード公開が確認できず、比較実装の細部を第三者が完全再現する障壁がある。

### 結果の読み方
結果は『EPを増やせば常に良い』という単純則を否定し、モデル・デバイス数・ノード内外帯域によってDP/EP/TPの最適点が変わることを示す。MixServeは低速なノード間リンクへ送るhidden stateをノード内TPで先にshardし、その通信と高速なノード内集約を重ねるため、帯域階層の差が大きいほど効果が出やすい。一方、もともと通信が小さいデコードや高帯域環境では利得も縮小する。
## 品質への影響
モデル計算や専門家選択結果を近似しないため、性能最適化による意図的な推論品質低下はない。評価はシステム指標に集中し、精度ベンチマークを別途改善する手法ではない。
## 既存研究との差
DeepSpeed-MoEやTutelなどがEP通信カーネルや分散MoE実装を最適化するのに対し、MixServeはAttentionとMoEを含む並列構成全体をハードウェア帯域から自動選択し、その構成専用にARとA2Aを融合する。SmartMoEは訓練時の動的並列選択を扱うが、MixServeはオンライン推論のTTFT・ITL・待ち時間とKVメモリ制約を目的へ組み込む。MegaScale-Inferのような分離配信とも排他的ではなく、論文自身も要求スケジューリングやプリフィル/デコード分離と併用可能と位置付ける。
## 限界
評価はH20 16 GPUとAscend 910B 32 NPUの2環境、DeepSeek-R1とQwen3-235B-A22Bの2モデルに限られる。待ち時間推定にM/M/1を用いるため、バースト到着や重い裾を持つサービス時間での選択精度は未検証である。融合Reduce-Scatter／Combineは通信を重ねる代わりに追加一時バッファを必要とする。専門家負荷そのものを予測・移動する仕組みではないため、極端なルーティング偏りには別の負荷分散が必要になる。著者公式コード公開先も一次資料から確認できず、再現性は実装記述に依存する。
## 実装状態
Ascend 910BではvLLM、NVIDIA H20ではTutelを基盤に実機実装しており、重み分割、混合通信群、融合RS-Combine／AG-Dispatchを評価している。一次資料にはアルゴリズム疑似コードと理論式があるが、2026-09-14時点で著者公式コードURLは確認できない。arXivコメントはICDCS 2026へ投稿済みとするが、採択済みとは確認できない。
## 研究上の位置づけ
MoE推論の通信最適化系統で、専門家キャッシュやオフロードよりも上位の分散配置・集合通信層を扱う。重要なのはノード内とノード間を同一帯域として扱わず、ノード内TPでhidden stateを細分化してからノード間EPへ流すことである。CPU/SSD専門家オフロードを組み合わせる場合も、GPU/NPU間通信だけでなくストレージ入出力帯域を費用モデルへ追加する発展が考えられる。
