# HGCA: Hybrid GPU-CPU Attention for Long Context LLM Inference

> 長文LLM推論でKVキャッシュがGPUメモリを超えると、CPUへ退避したKVを注意計算のたびにPCIe経由でGPUへ戻す方式は転送待ちがボトルネックになる。HGCAは最近のKVをGPUに残して密な注意計算を行い、古いKVはCPUメモリ上でヘッド単位に重要項目だけを選んで疎な注意計算を実行する。CPUとGPUの部分結果はlog-sum-exp統合で合成し、生KV全体ではなく小さな部分出力だけをPCIe転送する。A6000とXeonの実機で、より長い文脈・大きなバッチをGPUメモリ不足なしで処理し、既存のKV退避・疎注意方式より高い拡張性を示す。
## 書誌情報
- **著者**: Weishu Deng, Yujie Yang, Peiran Du, Lingfeng Xiang, Zhen Lin, Cheng-Zhong Xu, Song Jiang, Hui Lu, Jia Rao
- **公開**: arXiv:2507.03153v1, 2025-07-03
- **種別**: arXivプレプリント
- **対象**: KVキャッシュオフロード、CPU・GPU共同注意計算、長文脈推論、疎な注意計算、階層メモリ
- **実装**: 約1.5K行のPythonコードとしてPyTorch 2.4 + CUDA 12.4上に実装し、FlexGenとHugging Face Transformersへ統合して評価する。公開リポジトリURLは一次資料では確認できない。
## 問題設定
GPUメモリ上のKVキャッシュ容量は文脈長とバッチ数に比例して増え、重みが収まるモデルでも長時間生成ではKVが先にHBMを使い切る。従来のCPU退避は容量を増やせるが、注意計算時に生のKVをPCIe経由でGPUへ戻すため、デコードのようなメモリ帯域律速処理では転送が計算を直列化する。別の疎注意方式はGPUへ戻すKVを減らせるが、層全体で一律のTop-kを選ぶとヘッドごとの注意分布の差を無視し、重要KVを捨てて精度を落とす。HGCAはCPUを単なる保管場所ではなく注意計算の実行資源として使い、生KV転送を避けながら容量と精度を両立させる。
## 新規性
最近のKVと古いKVを別資源へ固定的に分けるだけでなく、GPU側は最近窓へ完全注意、CPU側は過去KVへヘッドごとの適応的疎注意を同時実行し、それぞれの部分出力と正規化統計だけをlog-sum-expで統合する。CPU側で複雑な選択処理を行うため、ヘッドごとに尖り方が違う注意分布へ個別の閾値を適用できる。さらにGPUのKV領域を事前確保した循環バッファにして古いブロックを非同期にCPUへ送るため、動的割当断片化も避ける。
## 手法
### 手法のあらまし
各注意層についてGPUには固定容量の連続KV領域を事前確保し、直近トークンのKVを循環的に保持する。容量を超えた古いKVブロックと、そのKVが過去に受けた注意重みの移動平均を専用CUDAストリームでCPUへ非同期退避する。CPU側では各ヘッドを独立に扱い、注意重みの移動平均がヘッド固有の閾値を超えるKVだけを文脈キャッシュへ残して疎な注意対象にする。閾値係数βを大きくするとCPU計算を減らせる一方、重要KVを落とす危険が増える。新しいプロンプトや文脈変化時には保持済みKVを再評価し、以前落としたKVも必要なら復帰させる。推論時にはGPUが直近窓へ通常の密注意を実行するのと並行して、CPUの複数スレッドがヘッドごとに古い文脈の選択KVへ疎注意を行う。双方は注意出力だけでなくlog-sum-exp正規化値も生成する。CPU側結果は固定形状のピン留めバッファへ書き、FlashInfer由来のmerge_stateを拡張したゼロコピー統合でGPU側結果と結合する。PCIeを流れるのは古いKV全体ではなく部分出力と正規化値なので、KVが大きくなるほど従来の再読込方式との差が広がる。 この構成により、GPU容量、CPU計算量、PCIe通信量を別々の資源として使い分ける。

### 局所性を利用したGPU・CPU KV配置
各GPUに注意層ごとの連続KVバッファを事前確保し、最近生成されたKVを高帯域GPUメモリへ保持する。容量超過時は最古ブロックを注意重み移動平均とともにCPUへ非同期退避する。直近KVは空間局所性が高く次のトークンで重要になりやすいため完全注意へ残し、遠いKVはCPU側の大容量メモリへ移す。事前確保によりトークン生成のたびに動的割当する必要がなく、長文脈でのメモリ断片化も抑える。CPU側に退避したKV自体は削除せず、疎注意用に選ばれなかった項目も後で再評価できる。 また、層ごとに固定領域を持つため、ある層の長大KVが別層の管理領域を侵食せず、退避判定とオフセット管理を単純化できる。

### ヘッド単位の適応的疎化
注意分布はヘッドによって極端に異なり、あるヘッドでは上位10%のKVが注意質量99%を占める一方、別ヘッドでは同じ99%を得るため約80%が必要になる。そこで層全体の固定Top-kではなく、各ヘッド内の注意重み移動平均に対して閾値βを適用し、重要KVだけをCPU側注意対象へ選ぶ。尖ったヘッドは少数、平坦なヘッドは多く残せるため、同じCPU計算量で重要文脈を保ちやすい。β=1付近ではヘッドにより1%未満から30%程度まで保持率が変わる。 この設計は各ヘッドで必要な保持率が違うという観測を直接利用し、同じ疎化率を全ヘッドへ強制する方式より無駄なCPU計算と重要情報の欠落を同時に減らす。

### CPU・GPU並行ハイブリッド注意
GPUは最近KVへの密注意、CPUは退避済み古いKVへの疎注意を同時に実行する。CPU側は複数コアへヘッドを分配し、選択済みKVをヘッドごとに連続配置して不規則アクセスを減らす。CPUの演算能力はGPUより低いが、デコード注意はメモリ帯域律速であり、古いKVの対象を疎化すればGPUの進行を遅らせず計算へ参加できる。従来はCPUメモリを倉庫として使い、生KVをGPUへ戻していたのに対し、この方式はCPU側で計算まで完了させる。 CPUとGPUの処理時間が近ければ双方を重ね合わせられ、CPUを単なる待避メモリとして扱う場合に発生するGPUのKV転送待ちを隠せる。

### log-sum-expによる小容量結果統合
GPU側とCPU側は独立したKV部分集合に対する注意出力とlog-sum-exp正規化統計を生成する。CPUからGPUへ送るのは巨大なK/V行列ではなく、ヘッドごとの固定形状出力と正規化値だけである。ピン留め共有バッファとゼロコピー転送を使い、FlashInferの状態統合処理を拡張して両部分を数学的に再正規化する。この統合自体は部分集合間のsoftmax正規化を正しく戻すため、近似誤差の主因はCPU側でどの過去KVを疎化するかに限定される。 したがって通信量は文脈長に比例する生KV量ではなく、ヘッド数と隠れ次元に対応する小さな統合用状態へ縮約される。

### 全体のデータ／制御の流れ
初期化時にモデル層をGPUへ割り当て、各注意層のGPU KV領域を固定容量で予約する。生成が進むと最新KVをGPUへ追加し、古いブロックを非同期にCPUへ移す。CPUの専用スレッドは退避KVをヘッド別に疎化して文脈キャッシュを更新する。各デコードではGPU密注意とCPU疎注意を並列起動し、CPU側の小さな結果だけをGPU側へ渡してlog-sum-exp統合する。層末で必要な同期だけを行い、退避・疎化処理は可能な限り推論のクリティカルパス外へ置く。
## 評価条件
- **ハードウェア**: デュアルソケットIntel Xeon Gold 6430（各32コア）、DDR5 512GB、NVIDIA RTX A6000 48GB×8。GPUはPCIe 4.0接続で、各GPUの片方向帯域上限は32GB/s。
- **ソフトウェア**: 約1.5K行のPython、PyTorch 2.4+cu124。GPU側はCUDAストリーム、CPU側はthreading.Threadとtorch.fork、統合にはFlashInferのmerge_stateを拡張して使用。FlexGenとHugging Face Transformersへ統合して比較する。
- **データセット／トレース**: WikiText
- **比較対象**: FlexGen、H2O、InfiniGen、Hugging Face Transformers完全注意
単一注意層の微小評価ではGPUに残るKV数、CPUへ退避したKV数、バッチ数を変え、CPU側計算を使わず生KVをGPUへ戻す方式との速度差を測る。エンドツーエンドではFlexGen、H2O、InfiniGen、Hugging Faceと比較し、128トークン生成・1920トークンプリフィル、4096トークン生成、16384トークン連続生成などを評価する。HGCAではFlexGen比較時にGPU KV比5%、H2O/InfiniGenは20% KV疎化設定。品質は完全注意のHugging Faceを基準にパープレキシティを比較する。
実機評価だが、A6000とXeonを中心とする単一サーバでの検証であり、CXLメモリ、NVLink-C2C、モバイルSoCなど別のCPU・GPU接続では比率が変わる。CPU疎注意のマルチスレッド負荷偏りにより16384トークン付近でTBTの外れ値が発生する。
## 主要結果
HGCAの主要な利点は、KVをCPUへ置いた後に再びGPUへ転送するのではなくCPU上で疎注意まで処理することで、長文脈ほど支配的になるPCIe転送を小さな部分出力転送へ置き換える点にある。単一層ではCPU側KV量とバッチが増えるほどハイブリッド注意の利得が大きく、エンドツーエンドでもFlexGenとH2Oを全バッチ条件で上回る。GPT-NeoX-12BではHugging Faceが2枚のA6000でも2048生成トークンまでしか保持できない条件に対し、HGCAは1枚GPUとCPU共同注意で4096トークンまで処理する。16384トークン連続生成でも末尾で3〜4トークン毎秒を維持する。

- 長文脈生成の拡張性 / 16384トークン生成、末尾3〜4 トークン/s (比較対象: GPUメモリ内KVのみの推論; 条件: GPT-NeoX-12B、バッチ1、GPU上4096 KV、β=1) — GPU上の固定窓を超えた古いKVをCPU側で処理するため、GPU容量を超えても生成を継続できる。

- 必要GPU枚数 / 1 GPUで4096トークン生成を完了 (比較対象: Hugging Faceは2 A6000でも2048トークンまで; 条件: GPT-NeoX-12B、バッチ15) — KV容量をCPUへ逃がしながらCPU側で注意計算することで、GPUを追加せず長い出力へ拡張できる。

- GPU KV常駐割合 / 5% (比較対象: InfiniGen/H2OはCPU KVを必要時にGPUへ読み込む比較設定; 条件: FlexGen上のOPT-13B/30B/66B、128生成・1920プリフィル) — 大部分のKVをCPU側へ置いたまま計算しつつ、FlexGenとH2Oを全バッチ条件で上回った。

- パープレキシティ例 / OPT-6.7B基準19.12に対し19.02（GPU比0.25, β=0.75） (比較対象: 完全注意19.12; 条件: WikiText、文脈長2048) — 疎化しても一部条件では完全注意とほぼ同等のパープレキシティを保つ。

- パープレキシティ悪化例 / OPT-30B基準16.78に対し19.97（GPU比0.25, β=0.25） (比較対象: 完全注意16.78; 条件: WikiText、文脈長2048) — GPU保持量と疎化閾値の組合せによっては品質が明確に悪化し、無損失ではない。

### 負の結果・境界条件
- CPU疎注意は常にGPU注意より速いわけではなく、CPU側KVが少ない短文脈や小バッチでは並列化の利点が小さい。16384トークン連続生成ではCPUスレッドのスケジューリングと負荷偏りによりTBTの大きなばらつきと外れ値が観測される。パープレキシティも設定依存で、OPT-30Bの一部条件やLLaMA-2-13Bの一部条件では完全注意より悪化する。

### 結果の読み方
CPUの行列演算性能はGPUより低いが、長文デコード注意は演算よりメモリ帯域とKV転送が支配しやすい。そのためCPUへ置いた古いKVを十分に疎化できれば、PCIe越しに生KVを往復させるよりCPUで直接計算する方が速くなる。利得はCPU側KV量とバッチが増えるほど大きく、長文脈・大バッチで顕著になる。
## 品質への影響
CPU側は選択的な疎注意なので厳密な無損失ではない。ヘッドごとの適応閾値により多くの設定で完全注意に近いパープレキシティを示すが、モデル・GPU KV割合・βによって悪化もあり、品質とCPU計算量の交換が必要である。
## 既存研究との差
一般的なKVオフロードはCPUを容量拡張として使い、注意計算時に必要KVをGPUへ戻すためPCIe帯域を消費する。HGCAはCPU側KVをCPU上で直接処理し、GPUには小さな部分注意出力だけを返す。H2OのようなGPU中心疎注意は層単位Top-kでKVを削減するのに対し、HGCAはCPUの分岐処理能力を利用してヘッドごとに保持率を変える。後発のHybridGenがCXL階層メモリ、注意ロジット並列、動的負荷配分まで広げるのに対し、HGCAはその前段としてPCIe接続CPU・GPU上の局所性利用と部分結果融合を具体化している。
## 限界
単一サーバ上のXeon Gold 6430とA6000を中心にした評価であり、CPUメモリ帯域とPCIe帯域の比率が違う環境では最適なGPU KV割合とCPU疎化率が変わる。CPU側注意はスレッド単位の負荷偏りに弱く、長文脈実験でTBT外れ値が実測されている。疎注意は品質完全不変ではなく、βとGPU保持割合をモデルごとに調整する必要がある。実装はPyTorch中心で、専用CPUカーネルやNUMA配置の徹底最適化余地が残る。公開コードURLも一次資料では確認できない。
## 実装状態
PyTorch 2.4+CUDA 12.4上に約1.5K行で実装され、FlexGenおよびHugging Face Transformersへの統合評価がある。GPU KV管理はCUDAストリーム、CPU管理はPythonスレッド、CPU注意はtorch.fork、部分結果統合はFlashInferのmerge_state拡張を利用する。研究コードの公開リポジトリは一次資料で確認できない。
## 研究上の位置づけ
本研究はKVキャッシュの階層化を「保存場所の選択」だけでなく「保存場所でそのまま計算する」という異種計算問題へ拡張する。SSD活用研究へ直接SSDを導入してはいないが、遅い階層のデータを高速階層へ全量搬送せず、その階層に近い計算資源で縮約してから小さい結果だけを上位へ返す原則は、CXLメモリや計算ストレージへつながる。サーベイ上ではKVオフロード、CPU・GPU協調注意、後発HybridGenやCXL-NDP系の橋渡しとして有用である。
