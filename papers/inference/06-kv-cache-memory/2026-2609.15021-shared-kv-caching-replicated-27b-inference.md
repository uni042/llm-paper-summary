# Shared KV Caching for Replicated 27B Inference: Correctness Failures and Performance Boundaries

> 共有KVキャッシュのページ表現・CUDAストリーム順序・全容量ピン留めを段階検証し、レプリカ移動時だけ大きな長文プリフィル再利用効果が得られる境界を実測する。
## 書誌情報
- **著者**: Frank Li
- **著者・所属**: UNSW Sydney
- **公開**: arXiv
- **種別**: Preprint
- **対象**: KVキャッシュ共有、LMCache、vLLM、CUDAストリーム順序、レプリカ間再利用
- **実装**: vLLM 0.28.0、LMCache 0.5.4、PyTorch 2.13.0+cu129。既存LMCacheパッチとmixed allocator経路を利用し、追加の診断・ベンチマークを実施。
## 概要
2つの27B vLLMレプリカが256 GiBのLMCache共有ホストメモリを使う構成で、共有KV再利用の正しさと性能境界を実機検証する工学事例。パック済みページ表現の不整合と、非既定CUDAストリーム依存を欠く生ポインタコピー経路を切り分け、バイト単位試験、実アロケータ試験、全容量ピン留め、サービス回帰を段階的に確認する。修復後、別GPUへ移動した128k入力の初回トークン時間は31.715秒から0.605秒、256kでは92.047秒から0.790秒へ低下する一方、同じGPUへ固定した会話では共有層の利得がほぼない。

本研究は新しいキャッシュアルゴリズムより、実際のvLLM・LMCache構成で共有状態再利用を安全に導入する検証方法と性能境界を明らかにする。論理ブロックが複数のパック済みページから成る表現不整合と、非既定CUDAストリーム上の生ポインタコピーが依存関係を欠く順序障害を別問題として切り分ける。固定バッファの遅延注入バイト試験、実アロケータ・ヘルパ試験、256 GiB全容量ピン留め、サービス回帰を積み上げた後、同GPU再利用と別GPU共有再利用を同じ実験で比較する。

代表結果として、別レプリカ再利用TTFTは完全共有可能な整列接頭辞、4 paired chains per sizeで共有層OFFで受信GPUがローカル冷状態に対して128k: 31.715秒→0.605秒、256k: 92.047秒→0.790秒。長い接頭辞を受信GPUで再計算せず、共有RAMから状態を回復することでプリフィル支配時間をほぼ除去する。
## 問題設定
複数の完全なLLMレプリカで長文・複数ターン要求を処理すると、同じGPUへ戻る要求はローカル接頭辞キャッシュを使えるが、負荷分散、障害回復、容量制約などで別GPUへ移ると、受信レプリカにはその長い接頭辞状態がなく、数万〜数十万トークンを再びプリフィルしなければならない。共有ホストメモリへKV状態を置く方式はこの再計算を避けられる候補だが、実装上は単純な全注意KVだけでなく再帰状態を含むハイブリッドモデルのページ表現、GPUからホストへの非同期コピー順序、巨大なピン留め確保を同時に正しく扱う必要がある。キャッシュヒット数やHTTP 200はデータが存在したことしか示さず、転送されたバイト列が生成側の最新状態と一致する証明にはならないため、壊れた状態を高ヒット率のまま再利用して誤答する危険がある。また共有層の性能を冷状態との比較だけで評価すると、会話を元のGPUへ固定してローカル接頭辞を使う現実的な代替策を無視して共有キャッシュの利得を過大評価する。したがって必要なのは、共有状態転送の表現・順序・メモリ経路をバイトレベルからサービスレベルまで検証した上で、冷計算、同GPUローカル再利用、別GPU共有再利用を分離し、共有層が本当に必要になる局所性喪失条件と追加オーバーヘッドを測ることである。
## 新規性
本研究は新しいキャッシュアルゴリズムより、実際のvLLM・LMCache構成で共有状態再利用を安全に導入する検証方法と性能境界を明らかにする。論理ブロックが複数のパック済みページから成る表現不整合と、非既定CUDAストリーム上の生ポインタコピーが依存関係を欠く順序障害を別問題として切り分ける。固定バッファの遅延注入バイト試験、実アロケータ・ヘルパ試験、256 GiB全容量ピン留め、サービス回帰を積み上げた後、同GPU再利用と別GPU共有再利用を同じ実験で比較する。
## 手法
### 手法のあらまし
構成は一台のホスト上に完全な27B vLLMレプリカを2つ置き、それぞれがGPU 0とGPU 1でプリフィルとデコードの両方を実行する。両レプリカは256 GiBのLMCache共有ホストメモリへ接続し、各GPU自身の接頭辞キャッシュも維持する。対象モデルは全注意層だけでなくGated DeltaNet状態を持つため、共有可能な接頭辞は注意KVページと対応する再帰状態スナップショットを共通境界で回復できる必要がある。最初の障害では論理注意ブロックが複数の32トークンページへパックされる表現を旧経路が正しく扱えず、既存のパック済みサブページ対応パッチを採用する。表現修復後も別GPU再利用で誤答が残るため、同一入力を冷状態、同GPU再利用、別GPU再利用、受信GPU冷状態で比較して共有転送へ原因を絞る。次にLMCacheのCUDA拡張がない場合に選ばれる生ポインタ経路を調べると、現在の非既定CUDAストリームを指定せずコピーしており、先行するgather/scatterとの依存が欠ける。そこで1 MiBなどの固定バッファへ遅延書込みを入れ、古い値がコピーされることをバイト単位で再現する。同じバッファのまま先行ストリーム待機、現在ストリーム上の非同期コピー、同一ストリームのテンソルコピーへ変えると全試験が通ることを確認する。実運用ではlazy allocatorを無効化して既存mixed allocatorのテンソルコピー経路を選び、順序依存を復元する。さらに256 GiB要求がPyTorchの丸めで過大確保されページ可能メモリへ退避する問題を避けるため、大容量ピン留めの丸め閾値を設定し、全容量が実際にピン留めされることを確認する。最後にOFF–ON–ON–OFFの独立再起動4ブロックで共有層なし・ありを比較し、冷計算、同GPU再利用、別GPU再利用、複数ターン固定配置・交互配置を測る。これにより転送の正しさを確立した後で、共有キャッシュが局所性喪失時にどれだけ再プリフィルを置換するかを分離して評価する。

### 共有ハイブリッド状態の表現整合性
対象27Bモデルは48層のGated DeltaNetと16層の全注意を持ち、共有対象は単純な注意KVだけではない。LMCacheは互換な転送配置の層をカーネルグループへまとめ、共有窓条件でオブジェクトグループへ束ねる。評価構成では1,568トークンの論理ブロックが49個の32トークンページにまたがる。初期経路はランク5注意テンソルを認識しても対象のランク4パック表現を欠き、HTTP成功とヒット数が出ても誤ったバイト列を復元した。既存パッチで論理ブロック全体のビューと配置制約を明示し、注意接頭辞と再帰状態スナップショットが共通境界でそろう場合だけ完全な共有接頭辞として扱う。

### CUDAストリーム順序の診断と修復
表現修復後の誤答を、同一入力の冷計算と局所再利用が正しい一方、共有再利用だけ異なるという対照実験で転送経路へ絞り込む。生ポインタfallbackは現在の非既定CUDAストリームを渡さずコピーするため、先行する生成側処理とコピー、コピーと消費側処理の依存が保証されない。遅延注入した4 KiB、1 MiB、16 MiBの両方向試験では生経路が遅延あり120/120失敗、遅延なし120/120成功し、ストリーム待機・現在ストリーム非同期コピー・同一ストリームテンソルコピーの3対照は720/720成功した。実アロケータ試験でもlazy経路10/10失敗、mixed経路20/20成功となり、既存mixed allocatorを選ぶことで現在ストリーム上の順序を復元する。

### 全容量ピン留めと局所性別性能評価
小容量mixed allocator試験が通っても256 GiBサービス要求では、アライメント分を加えた確保量がPyTorchの2冪丸めで512 GiBへ膨らみ、ページ可能メモリへ退避し得る。大容量確保の丸め閾値を設定し、274,877,911,040バイトが約39秒で実際にピン留めされ、サービスも約42秒で警告なく初期化することを確認する。その最終構成だけを性能評価へ使い、共有層OFFとONを独立再起動した4ブロックで比較する。各チェーンは冷計算、同GPU再利用、別GPU再利用、受信GPUでの再利用を含み、複数ターンでは固定配置と交互配置を分けるため、共有RAMの効果を単なるローカル接頭辞キャッシュの効果と混同しない。

### 全体のデータ／制御の流れ
共有RAMはゲートウェイではなく推論ホスト上のLMCacheサービスで、各レプリカは完全なモデルとローカルGPU接頭辞キャッシュを保持する。プリフィル・デコード分離構成ではない。正しさ検証は表現、コピー順序、実アロケータ、全容量ピン留め、サービス応答の層に分け、性能は局所性条件ごとに測る。
## 評価条件
- **ハードウェア**: 推論ホストにNVIDIA RTX PRO 6000 Blackwell Server Edition 2基を評価レプリカとして使用し、各GPUは約97,887 MiB。CPUはAMD EPYC 9455 48コアを2基、共有ホストRAMは256 GiB。
- **ソフトウェア**: vLLM 0.28.0、LMCache 0.5.4、PyTorch 2.13.0+cu129。Qwen3.8-27B-NVFP4系チェックポイント、FP8 KV、HND配置、接頭辞キャッシュ有効。共有層は1,568トークンチャンク、LRU。
OFF–ON–ON–OFFの4独立再起動ブロックで共有LMCacheなし・ありを二組の対として比較し、各ブロック192測定要求、合計768要求を収集する。8k、32k、128k、256k入力のチェーンで冷計算、同GPU再利用、別GPU再利用、受信側再利用を測る。6ターン会話は32k/128k初期文脈で固定GPUと交互GPUを比較する。別に512/2048トークン強制生成と4/8並行セッションを測る。正しさは遅延注入バイト試験、実アロケータ、サービス回帰、正確値応答で段階検証する。
一つのモデル構成、一台のホスト、二つの独立ブロック対に限定され、信頼区間や有意差主張は行わない。共有プール飽和、持続的開ループ容量、ホスト間共有、実ゲートウェイの負荷駆動移動は未評価。ホストは完全専有ではなく、別GPU活動がある区間も存在する。
## 主要結果
共有キャッシュの最大効果はレプリカ移動でローカル接頭辞が失われる場合に現れる。別GPU再利用の中央値は128k入力で31.715秒から0.605秒、256kで92.047秒から0.790秒へ低下する。6ターン交互配置では32k初期文脈で16.708秒から10.821秒、128kで73.220秒から40.553秒となり、平均対変化は約-35.26%と-44.61%。一方固定配置では同じGPUのローカル接頭辞が既に使えるため、32kで+0.36%、128kで+0.34%と利得がない。デコード速度変化も-0.82%〜+0.16%に留まり、共有層は主に再プリフィル回避へ効く。

- 別レプリカ再利用TTFT / 128k: 31.715秒→0.605秒、256k: 92.047秒→0.790秒 (比較対象: 共有層OFFで受信GPUがローカル冷状態; 条件: 完全共有可能な整列接頭辞、4 paired chains per size) — 長い接頭辞を受信GPUで再計算せず、共有RAMから状態を回復することでプリフィル支配時間をほぼ除去する。

- 6ターン交互配置会話 / 32kで-35.26%、128kで-44.61%の平均対壁時計時間変化 (比較対象: 共有層OFF; 条件: レプリカをターンごとに交互利用) — 毎ターン局所性が失われる状況では共有状態が繰返し再プリフィルを防ぎ、セッション全体でも大きな効果を保つ。

- コピー順序検証 / 遅延付き生経路120/120失敗、3種の順序復元対照720/720成功 (比較対象: 現在CUDAストリーム依存を欠く生ポインタfallback; 条件: 4 KiB、1 MiB、16 MiB、双方向、固定バッファ) — 誤答が浮動小数点差や標本化ではなく、非既定ストリームとコピー間の欠落依存で再現可能なバイト破損に由来することを強く支持する。

### 負の結果・境界条件
- 固定レプリカ配置では共有層ONの6ターン時間が32kで+0.36%、128kで+0.34%とわずかに悪化し、同GPUローカルキャッシュが維持できるなら共有層の性能利得はほぼない。長出力のデコード速度差は-0.82%〜+0.16%で、共有RAMはデコード演算そのものを高速化しない。256 GiB超の飽和やホスト間共有は未検証。

### 結果の読み方
共有KVの価値はキャッシュ容量そのものより要求配置の局所性に依存する。固定配置が可能ならGPUローカル接頭辞が最速であり、共有RAMは負荷分散・障害・移動で別GPUへ切り替えるときの保険として大きな価値を持つ。また性能測定以前に転送バイトの正しさを検証しないと、ヒット数だけ高い壊れたキャッシュを高速化として誤認し得る。
## 品質への影響
正しさを保つ状態再利用が前提であり近似的KV圧縮ではない。修復後は正確値応答を多数確認するが、強制長生成は意味品質を評価せず、後半会話の一部は期待値を履歴に含むため遠距離接頭辞回復の独立検証にはならない。
## 既存研究との差
LMCacheやMarconiのような共有・ハイブリッドKVキャッシュ機構そのものを新規提案するのではなく、既存共有層を27Bハイブリッドモデルへ適用した際の正しさ障害と局所性境界を実証する。ヒット率やHTTP成功を正しさ指標にせず、パック済みページ表現、CUDAストリーム順序、実アロケータ、全容量ピン留め、サービス応答を別層で検証する点が特徴。性能面では共有再利用だけでなく同GPUローカル再利用を強い比較対象として残す。
## 限界
一台のホスト、2 GPUレプリカ、1モデル構成、2独立ブロック対という工学事例であり、大規模分散環境の統計的性能保証ではない。256 GiB共有プールの飽和、ホスト間共有、持続的高負荷、実ゲートウェイの親和性制御や負荷移動は未評価。コピー試験は単一バイトオブジェクトを対象とし、すべての登録カーネルグループのバイト等価性を直接検証したわけではない。元の障害要求の完全なCUDA転送トレースもない。
## 実装状態
vLLM 0.28.0とLMCache 0.5.4の実運用相当構成で、既存パック済みサブページパッチ、既存mixed allocator、PyTorchピン留め確保設定を組み合わせる。論文は利用したLMCache、PyTorch、モデルの具体的コミット・リビジョンを記録する。
## 研究上の位置づけ
分散KVキャッシュ研究に対する実装検証・性能境界のケーススタディであり、共有キャッシュの設計だけでなく、非同期GPU転送の順序契約と要求配置の局所性が実際の効果を左右することを示す。共有RAMを常時ローカルGPUキャッシュの代替にするのではなく、親和性を基本にしつつレプリカ移動時の再利用層として組み合わせる設計を支持する。
