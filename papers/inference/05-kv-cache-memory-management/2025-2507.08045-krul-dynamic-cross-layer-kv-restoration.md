# Krul: Efficient State Restoration for Multi-turn Conversations with Dynamic Cross-layer KV Sharing

> 対話ごとの注意類似度から層間の鍵・値共有を動的選択し、注意類似度計算を中央処理装置と画像処理装置へ分担、圧縮後の再計算とロードを層間パイプラインで重畳してマルチターン状態復元を高速・省容量化する。

- **実装**: Python、PyTorch、Hugging Face Transformersを基盤に実装。複数の非同期実行流、中央処理装置での注意類似度計算、画像処理装置での逐次類似度計算、装置間キャッシュ先読み、復元キャッシュ結合を使用する。本文の成果物URLは仮置き表記で、一次資料から有効な公開コードURLは確認できない。
## 概要
Krulは休眠したマルチターン対話を再開するとき、履歴全体の鍵・値キャッシュを再計算または全量ロードするコストを削減する推論システムである。既存の層間共有は後段の隣接層など固定した圧縮組合せを全対話へ適用するため、対話ごとに異なる注意パターンを無視して生成品質を落とし得る。Krulは将来入力に敏感な層を圧縮対象から事前除外し、残る入力非依存層について対話ごとの注意類似度から共有層ペアを動的選択する。注意類似度計算は入力処理段階の大きな注意重みを中央処理装置へ非同期退避して計算し、逐次生成段階では最新トークン分だけ画像処理装置で逐次計算する。復元時は圧縮によって層ごとに不均衡になった再計算量とロード量をピラミッド状に配分し、複数の非同期実行流で重畳する。4基のA100 80GB、128GB主記憶、PCIe第4世代環境でLLaMA-7B/30B、Qwen1.5-7B、Qwen2-72Bを評価し、平均精度損失1%未満を維持しながら既存方式比で最初のトークンまでの時間を1.28〜2.68倍高速化し、完全保存比で平均2.35倍のキャッシュ容量削減を報告する。

Krulは層間キャッシュ共有を固定配置ではなく会話ごとの注意類似度に基づく動的戦略へ変え、将来入力に敏感な層を事前に圧縮対象から除外する。さらに入力処理と逐次生成の注意重み特性の非対称性を利用して、入力処理側の大きな注意重みは中央処理装置へ非同期退避して類似度を計算し、逐次生成側は最新トークン分だけ画像処理装置上で計算する。復元時には圧縮写像から生じる層別の再計算量減少・ロード量増加を利用し、両処理をピラミッド状に重畳する待ち時間の少ない復元スケジューラを構成する。

代表結果として、TTFT vs SOTAは4 models / LongBench-style restorationでstate-restoration 比較対象に対して平均1.28×〜2.68× 高速化倍率。動的 compressionとrecompute-load overlapを組み合わせることで品質を維持しつつ復元を高速化。
## 問題設定
マルチターン対話では休眠中の会話キャッシュを画像処理装置から退避する必要があり、再開時に履歴を全入力処理して鍵・値を再計算すると履歴長に比例して最初のトークンまでの時間が増える。全キャッシュを中央処理装置へ保存して再ロードすれば計算は省けるが、Qwen1.5-7Bでは2000トークンの1ターンだけで平均約1GBとなり、多数対話で主記憶を圧迫し、溢れれば補助記憶からのロードも必要になる。層間で似た注意パターンを利用する固定圧縮は保存量を減らせるが、注意類似度は対話内容ごとに変わり、将来のユーザー入力が参照する重要情報を固定共有が壊す場合がある。さらに対話ごとの共有層を選ぶには巨大な注意重みの保存と類似度計算が必要で、4000トークン・7Bモデルでは単純保持が約30GBの画像処理装置メモリを要求する。圧縮後は層ごとのロード量と再計算量も不均衡になるため、固定比率の再計算・ロードパイプラインには待ち時間が生じる。
## 新規性
Krulは層間キャッシュ共有を固定配置ではなく会話ごとの注意類似度に基づく動的戦略へ変え、将来入力に敏感な層を事前に圧縮対象から除外する。さらに入力処理と逐次生成の注意重み特性の非対称性を利用して、入力処理側の大きな注意重みは中央処理装置へ非同期退避して類似度を計算し、逐次生成側は最新トークン分だけ画像処理装置上で計算する。復元時には圧縮写像から生じる層別の再計算量減少・ロード量増加を利用し、両処理をピラミッド状に重畳する待ち時間の少ない復元スケジューラを構成する。
## 手法
### 手法のあらまし
各対話の生成中、Krulはまず注意パターンを観測して入力依存性の高い層を識別する。系列の先頭10%と末尾10%への平均注意量が閾値を満たさない層を入力依存層として圧縮対象から外し、将来入力により注目先が変わりやすい層の鍵・値を保持する。残る入力非依存層では各層・注意頭の注意重みを一次元化し、層ペア間のユークリッド距離を計算して類似度順に並べ、同じ層を重複利用しない制約の下で指定圧縮率まで共有層ペアを選ぶ。類似度推定のメモリ負荷を抑えるため、入力処理で生成される大きな注意重みは非同期実行流で中央処理装置へ送り、逐次生成では最新トークンの注意だけを画像処理装置に残して毎トークン距離を加算し、最後に両者を統合する。対話終了時には選択した写像に従って鍵・値を層間共有して中央処理装置へ退避する。次のターンが到着すると、保存されていない前段の鍵・値は隠れ状態から再計算し、共有済み後段の鍵・値は中央処理装置から画像処理装置へロードする。スケジューラは層が深くなるほど再計算量を減らしロード量を増やすよう仕事を配置し、複数の非同期実行流と入出力スレッドで両処理を同時進行させる。必要な隠れ状態は前段で計算済みのより長い状態から切り出せるため依存関係を保ち、最後に再計算分とロード分を結合して通常の逐次生成へ接続する。これにより対話履歴の入力から圧縮戦略選択、休眠時保存、再開時復元、次トークン生成までが一つの閉じた処理経路になる。

### 事前圧縮戦略選択器
将来の利用者入力そのものは未知なので、現在の質問だけで重要トークンを捨てるのではなく、注意パターンが入力変化へ敏感かどうかを層単位で先に分類する。系列先頭10%と末尾10%への平均注意量から入力依存層を検出して共有対象外とし、比較的入力に頑健な層だけを候補にする。その候補間で注意重みのユークリッド距離を計算し、類似度の高い層ペアから、同一層を複数ペアに使わない制約と圧縮率を満たすまで貪欲に選択する。後半隣接層を固定共有する方式と異なり、各対話が異なる層写像を持つため、将来ターンで必要になる文脈を壊す確率を下げながら保存量を削減する。

### トークン単位の異種注意類似度推定器
入力処理の注意重みは全入力トークン間を含むため大きく、画像処理装置に保存し続けると容量を圧迫するが、一度にまとまって生成されるので中央処理装置へ非同期転送して類似度を計算できる。一方、逐次生成の注意重みは1トークン分ずつ小さいが、ShareGPT分析では出力が入力より平均6.56倍長く頻繁に発生するため、最新トークン分だけ画像処理装置で逐次計算し直ちに破棄する。入力処理側の中央処理装置計算と逐次生成側の画像処理装置計算を生成本体と重畳し、最後に距離統計を合算することで、全注意履歴を高価な装置メモリへ保持せず対話固有の層類似度を得る。

### 層間動的キャッシュ共有
入力依存性が低い層のうち注意分布が近い層ペアでは、一方の鍵・値を他方と共有し、休眠対話で保存するキャッシュ量を削減する。共有写像は対話ごとに異なり、共有対象にならなかった層の鍵・値と復元に必要な隠れ状態を保持する。再開時には、共有によって保存されていない鍵・値を全量ロードするのではなく、浅い層で必要部分を再計算しながら、深い層では保存済みの共有キャッシュを並行してロードする。共有層を選ぶ際は同じ層を複数ペアへ割り当てないため、どの層の値をどの層が再利用するかが一意になり、復元時の依存関係を明確にできる。圧縮率を上げれば保存量とロード量は減る一方、再計算量や品質リスクが増えるため、単なる圧縮率最大化ではなく、入力依存層の除外と類似度順位によって品質との交換条件を制御する。結果としてこの構成要素は、保存形式を変えるだけでなく、後段スケジューラが扱う再計算仕事とロード仕事の量を決める設計変数として働く。

### 待ち時間を抑える復元スケジューラ
圧縮写像により、浅い層ほど再計算対象の隠れ状態が長く計算量が大きい一方、深い層ほど共有済みキャッシュの再利用が増えてロード量が大きくなるというピラミッド型の仕事分布が生じる。Krulはこの構造を利用し、浅い層で画像処理装置が再計算している間に、後段で必要になる鍵・値を中央処理装置から別の非同期実行流で先読みする。層が進むにつれて再計算対象の系列長を短くし、その空いた計算時間にロード仕事を増やすことで、計算流と入出力流のどちらか一方だけが先に終わって待つ区間を減らす。必要な隠れ状態は前段で既に計算されたより長い状態から切り出せるという単調な依存関係を使うため、順序を組み替えても復元の正しさを維持できる。最後に再計算で生成した鍵・値とロードした鍵・値を結合し、完全な履歴状態として次のトークン生成へ渡す。固定比率の部分再計算方式と違い、圧縮写像が変われば層別仕事量も変わることを明示的に反映するため、対話ごとに異なる圧縮戦略でも計算資源と転送帯域を同時に使いやすい。

### 全体のデータ／制御の流れ
生成時には注意統計を中央処理装置と画像処理装置へ分担して蓄積し、ターン終了時に対話固有の層写像を確定して圧縮キャッシュを主記憶へ保存する。再開要求では写像から必要な再計算量とロード量を層ごとに導出し、非同期実行流と入出力スレッドで復元を重畳する。復元後は両経路で得た鍵・値を結合し通常の入力処理・逐次生成機構へ戻す。保存段階の圧縮判断と復元段階の仕事配置が同じ層写像を共有するため、保存量を減らした結果としてどこに再計算が発生するかを実行時に推測し直す必要がない。
## 評価条件
- **ハードウェア**: 4×NVIDIA A100 80GB、128GB ホスト DRAM、10TB SSD、PCIe Gen4
- **ソフトウェア**: PyTorch、Hugging Face Transformers、CUDA ストリーム
- **モデル**: LLaMA-7B、LLaMA-30B、Qwen1.5-7B、Qwen2-72B (8-bit model 量子化)
- **データセット／トレース**: LongBench、ShareGPT
- **比較対象**: Full KV recompute、Full KV load / AttentionStore-style、Partial KV recompute、H2O KV 追い出し、MiniCache fixed KV compression
- **正確性・品質**: LongBenchで生成品質を比較し、Krulは平均accuracy lossを1%未満に抑える。Qwen1.5-7Bの詳細表では14 task平均26.70で、非圧縮比較対象 26.94、MiniCache 25.82、固定化したKrul戦略25.72に対し動的選択が最も比較対象へ近い。
- **LongBench accuracy**: context末尾128 トークンを新user inputとして分離し、それ以前をhistorical conversationとしてKV圧縮して品質を評価する。
- **TTFT comparison**: 4 modelでfull recompute、full load、partial recompute、KV 追い出し、fixed KV compressionと比較する。
- **prompt length sensitivity**: LLaMA-7Bでhistorical prompt lengthを500〜4000 トークンへ変えTTFTとKV storageの伸びを比較する。
- **スループット**: ShareGPT ワークロードを使いプリフィル スループットを測定し、複数リクエストのcontinuous バッチを有効化する。
- **similarity オーバーヘッド**: CPUでのプリフィル attention similarity計算、GPU デコード、GPU デコード+similarityの遅延をsequence lengthごとに比較する。
同一testbed上で状態復元方式を切り替え、TTFT、プリフィル スループット、KV storage、LongBench accuracyを測定する。復元方式の差を明確にするためfull recompute/load、固定圧縮、partial recompute/load パイプライン、sparse 追い出しを比較し、Krulの動的 層 sharingとスケジューラの組合せを評価する。
A100 PCIe serverでの実機評価。CPU DRAMを休眠KVの主要退避先とする構成で、分散KV store、NVMe主体の復元、CXL、異種GPU、production トレースでの大規模multi-tenant運用は直接評価していない。
## 主要結果
KrulはLongBenchで平均accuracy lossを1%未満に保ちながら、既存state-restoration方式に対して平均TTFTを1.28〜2.68倍高速化する。full recompute比ではLLaMA-7B/30B/Qwen1.5-7Bで平均2.65倍、Qwen2-72Bで6.62倍、full KV load比2.35倍、fixed KV compression比1.76倍、partial KV recompute比1.5倍のTTFT 高速化倍率を報告する。プリフィル スループットもfull recompute/load/fixed compression/partial recompute比でそれぞれ平均2.5倍、1.9倍、1.41倍、1.29倍。休眠時KV storageはfull KV比平均2.35倍、fixed compression比1.75倍削減する。

- TTFT vs SOTA / 平均1.28×〜2.68× 高速化倍率 (比較対象: state-restoration 比較対象; 条件: 4 models / LongBench-style restoration) — 動的 compressionとrecompute-load overlapを組み合わせることで品質を維持しつつ復元を高速化。

- TTFT vs full recompute / LLaMA-7B/30B/Qwen1.5-7B平均2.65×、Qwen2-72B 6.62× (比較対象: Full KV recompute; 条件: A100 testbed) — 履歴プリフィルの大部分をKV load/shared KVで回避する。

- TTFT vs load/compression/パイプライン / full KV load比2.35×、fixed KV compression比1.76×、partial KV recompute比1.5× (比較対象: Full load / MiniCache-style fixed compression / partial recompute; 条件: overall evaluation) — 圧縮量だけでなく層-aware パイプライン再配置が復元bubbleを削減する。

- プリフィル スループット / full recompute 2.5×、full load 1.9×、fixed compression 1.41×、partial recompute 1.29× (比較対象: 各方式; 条件: ShareGPT ワークロード) — recomputeとloadの並列復元がprompt処理能力を高める。

- KV storage / full KV比2.35×、fixed KV compression比1.75× reduction (比較対象: Full KV / fixed compression; 条件: inactive conversations) — 一部KVを再計算へ回し、I-R層ではcross-層 sharingするため保存量が減る。

- LongBench average accuracy / 比較対象 26.94、MiniCache 25.82、Krul(Fix) 25.72、Krul 26.70 (比較対象: uncompressed / fixed compression; 条件: Qwen1.5-7B, 14 tasks) — conversation-specific 動的 strategyが固定共有より比較対象品質へ近い。

- Recompute/load ratio example / 2:3でfull recompute比2×、full load比1.35× 高速化倍率 (比較対象: full recompute / full load; 条件: LLaMA-7B ratio analysis) — computeとloadの長さを近づけるとoverlap効率が最大化する。

### 負の結果・境界条件
- 固定化したKrul共有範囲はLongBench平均25.72でMiniCache 25.82よりわずかに低く、層 rangeを広げるだけでは品質改善にならない。動的conversation-specific選択が必要である。またQwen2-72BはMQAかつ8-bit量子化を使うため他modelと条件が完全同一ではない。CPU similarity計算はデコードへ重畳できる条件では隠れるが、CPUが遅い環境やデコードが短いワークロードではオーバーヘッドが表面化し得る。

### 結果の読み方
Krulの利得は、保存量を減らす圧縮と復元時間を減らすスケジューラを別々に最適化せず、圧縮mapが生む層別load/recompute量をスケジューラへ直接渡す点にある。conversation-specific attention similarityで品質を守りながら共有KVを増やし、減ったloadをrecomputeとのoverlap余地へ変換するため、storageとTTFTを同時に改善できる。
## 品質への影響
動的KrulはLongBench平均26.70対比較対象 26.94で平均accuracy loss 1%未満。固定圧縮やKV 追い出しより品質維持を優先する設計で、性能改善をトークン 追い出しによる大きなaccuracy lossへ転嫁しない。
## 既存研究との差
- **Full KV loadとの差**: 全KVを保存・ロードせず、conversation-specific cross-層 sharingと一部recomputeで保存量とload量を減らす。
- **Pensieve/Cake等との差**: 固定したsuffix recompute/load比ではなく、圧縮層 mapに応じて層ごとのrecomputeとloadを動的配置しbubbleを抑える。
- **MiniCacheとの差**: 後半隣接層を固定共有せず、input-sensitive 層を除外したI-R層全体からconversationごとに高類似pairを選ぶため、同じ圧縮式でも品質低下を抑える。
- **H2O等sparse attentionとの差**: 現在queryだけでトークン KVを追い出しせず、future inputを考慮できないトークン 追い出しの品質riskを避け、層間共有で情報を保持する。
## 限界
- **単一server testbed**: 4×A100 80GB、128GB DRAM、PCIe Gen4の単一serverで評価しており、remote KV store、RDMA、CXL、複数nodeやheterogeneous GPUでのrestorationは未評価。
- **将来入力の間接推定**: future user input自体は観測できないため、現在までのattention patternからinput-sensitive 層を除外する。会話分布が大きく変化すると判定が外れ、重要contextを共有KVで十分保持できない可能性がある。
- **CPU/DRAM前提**: inactive KVをCPU DRAMへ置きCPUでプリフィル similarityを非同期計算できることを前提とする。CPU計算資源やPCIe帯域が不足するとoverlapが崩れ、SSD主体の大規模KV階層では追加設計が必要。
