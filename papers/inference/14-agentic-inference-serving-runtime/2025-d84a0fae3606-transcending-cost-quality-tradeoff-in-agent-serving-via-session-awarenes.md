# AgServe：セッション認識型LLMエージェント推論基盤

## 概要

AgServeは、大規模言語モデル（LLM）を繰り返し呼び出すエージェントの実行に合わせ、KVキャッシュの再利用、使用モデルの段階的な昇格、GPU資源の割当を連携させるサービング基盤である。一般的なチャット向け推論サーバーは各要求を比較的独立に扱うが、エージェントは一つのタスクで短い応答と外部ツールの呼出しを繰り返し、同じセッションの次要求が比較的予測可能な間隔で到着する。対話履歴が長くなると、先頭の共通指示と末尾の新しい観測を残して途中の履歴を削る場合もある。従来の単純な接頭辞一致キャッシュや最近使用順の退避では、この特徴を活かしにくい。

AgServeはセッション認識サーバー（SAS）、品質監視クライアント（SGC）、資源スケジューラ（RS）を組み合わせる。SASは次要求の到着予測でKVキャッシュの退避を決め、途中切り詰め後の位置埋め込みをキャッシュ内で補正する。SGCは開始時の難度判定と実行中の応答品質監視により、必要に応じてより大きなモデルへ切り替える。RSはモデルごとの需要と供給を監視し、GPU割当を再配置する。

NeurIPS 2025の実機評価では、AWエージェントでGPT-4oと近い品質を**16.5%の費用**で達成し、同一費用の費用・品質曲線に対して**1.8倍の品質**を報告する。複数エージェントを同時実行する負荷では、拡張したLlumnix++に対して費用を64%削減し、品質指標を1.6倍にした。これらは特定のAgentBench派生タスク、モデル選択肢、費用モデルでの結果であり、一般のあらゆるエージェントでの保証ではない。

## 問題設定：エージェント負荷は短い生成と重い事前計算の反復

論文はエージェントの要求列を、共通接頭辞（SP）、タスク固有の定型部分（TST）、伸長する対話履歴（IH）に分解する。各ラウンドの出力は比較的短く、ツール実行後の観測が次ラウンドの入力へ追加される。したがって、生成そのものより、過去の長い文脈を繰り返し読み直す事前計算（prefill）が負荷になりやすい。通常の接頭辞キャッシュは履歴が途中で切り詰められると、以前と同じ後半トークンでも位置が変わるため、再利用が難しくなる。

また、セッションの序盤では小さなモデルでも十分な応答を返せるが、後半では文脈とタスク難度が増して大きなモデルが必要になることがある。最初から高価なモデルだけを使うと序盤の費用が無駄になる。一方、要求単位で小型・大型モデルを頻繁に切り替えると、KVキャッシュの移動・再構築や推論状態の不連続が問題となる。さらに、多くのセッションが後半に移ると大型モデルへの要求が増え、固定したGPU配分では資源が不足または遊休化する。

AgServeは「次に同じセッションからいつ要求が来るか」「途中切り詰め後にKVをどう使うか」「どの時点でモデルの能力が不足したか」「どのモデルへGPUを配るか」を連携して扱う。単一要求の待ち時間だけではなく、セッション全体の完了品質、費用、遅延を評価する点が一般的な推論スケジューリングと異なる。

## 手法

### SAS：セッションIDとKVキャッシュの対応を保持

セッション認識サーバー（SAS）は、vLLMに由来するページ単位の注意管理（PagedAttention）を使い、セッションIDから現在の系列とキャッシュブロックを引く対応表SISTを保持する。新しい要求が来ると、その要求が属するセッションのキャッシュを特定し、保持できている部分を再利用する。セッションの途中履歴が切り詰められている場合には、後述の位置補正を行ったうえで既存のキー・値キャッシュを利用する。これにより、単純な接頭辞一致だけでは見失う再利用機会を保持する。

SISTが追加するのはセッションID、系列とブロックの対応であり、モデルの推論重みそのものを変える仕組みではない。セッションが終了したときのキャッシュ解放や、メモリ不足時の退避判断と結び付く。エージェントの次要求が十分早く到着するなら、直前のKVを残すことが再事前計算の回避につながる。逆に長時間使われないセッションを保持し続けると、他セッションのキャッシュを追い出してしまう。

### 原位置でのRoPE位置補正

エージェントが履歴の中央を切り詰めると、保持された末尾トークンの新しい位置p'は元の位置pから変化する。回転位置埋め込み（RoPE）を用いたキーキャッシュは元の位置の位相を含むため、そのまま再利用すると位置関係が不正になる。AgServeは位置差δp=p'−pに対応する回転を、保持済みキーに原位置で適用する。具体的にはキーの偶数・奇数次元の組に対しcos(δpθ)とsin(δpθ)を使う二次元回転を施し、新しい位置のキーへ変換する。

原著はこの操作をバッチ化したCUDAカーネルで実装し、RoPEモジュールの三角関数キャッシュを再利用する。元のキーと再利用用の別キーを二重保持する方式に比べ、同じキャッシュ領域を更新できることが利点である。ただし補正は位置依存部分の整合を回復する操作であり、削除した履歴の意味内容を復元するものではない。切り詰めによってタスクの必要情報を失えば品質が低下し得るため、キャッシュ再利用の正確さとタスク品質は別に確認する必要がある。

### ECE：次要求の到着時刻に基づく退避

通常の最近使用順（LRU）では、最近使われていないキャッシュを退避する。しかしエージェントではツール呼出し後の待機時間とラウンドの進行から、次の要求が比較的早く来るセッションを予測できる。ECEは到着予測時刻（ETA）を用いて、次に必要となるキャッシュを優先して保持する。全セッションのキャッシュが同じサイズなら、次要求が最も遅いものから退避することが有効であり、論文はその条件での最適性を議論する。

実際にはセッションごとにKVの長さが異なるため、単に到着が遅い順に退避するだけでは必要メモリを確保できない。論文は、各セッションのキャッシュ長l_i、再事前計算のトークン当たり費用P、並列復号時間D_k、到着順序を使って、候補集合を退避したときの将来遅延の費用を動的計画法で評価する。すべての将来を完全に予知するのではなく、到着予測に基づく近似的な意思決定である。予測が外れる場合、退避済みセッションの再事前計算が発生するため、到着予測の精度とキャッシュ長の偏りが効率を左右する。

SASは長い文脈のCPU退避を採用せず、GPU内のキャッシュ再利用と退避を中心に設計する。これはCPU転送が長文脈で高価になり、同じバッチの他系列を妨げ得るためである。セッションの到着時刻が予測しやすいという前提が崩れる場合には、ECEの利得も縮む。

### SGC：セッション単位のモデル選択と品質監視

品質監視クライアント（SGC）は、開始時にQ-Judgeでタスクと初期観測から難度を0・1・2の三段階へ分類し、十分な能力を持つ最も安価なモデルでセッションを始める。過剰に大きなモデルを選ぶ誤りは費用を回収できないため、Q-Judgeの学習損失は過大選択に重い罰則を与える。原著はChatbot-Arena由来のデータを用いて判定器を学習し、単純な交差エントロピー分類やRouteLLMと比較する。

セッション中はR-Judgeが一定頻度で応答品質を監視する。判定にはモデル規模、推論文や応答、タスク、直近の行動・観測を入力し、長い全履歴をそのまま読み込まずに判定費用を抑える。品質不足が検出されると、まず再試行し、それでも不十分なら大きなモデルへ昇格する。サービス失敗の場合は別のモデルへ一般的な移行を行い、対応するエージェントでは以前のチェックポイントへ復帰して履歴を短くすることもできる。

R-Judgeの閾値θは品質と費用の交換関係を制御する。厳格すぎれば大型モデルへの移行が頻発し、緩すぎれば品質不足を見逃す。原著はθ=0で常にGPT-4oを使う状態に、θ=1で品質監視を行わないCascadeに近づくと説明する。品質判定の誤りがあるため、昇格は必ずしも最適ではない。判定器自体の誤検出率と追加の推論費用を測る必要がある。

### RS：モデル需要とKV供給量に基づくGPU再配置

資源スケジューラ（RS）は、モデルごとの呼出し頻度を需要として集計し、現在のモデルインスタンスがKVキャッシュへ収容できるトークン数を供給量として扱う。需要／供給比が高いモデルを増やし、低いモデルを減らす。単一ノードへ収まる調整可能なモデルは、GPU数を最小必要数の整数倍で配分し、モデルごとにインスタンスを統合する。初期化費用が高く複数ノードにまたがる固定モデルは手動管理としている。

RSは需要が少し変化するたびに重みを載せ替えるのではなく、需給の不均衡が大きい場合にだけ再配置する。これは再配置の重みロード費用を抑えるためである。品質監視によりセッションが大型モデルへ昇格すると需要分布が変わるため、SGCとRSの連携が必要になる。一方、再配置に必要なモデル起動時間が長い場合や、特定モデルが急増するバースト負荷では追従遅延が生じ得る。

## 評価

### 実験環境と指標

| 項目 | 原著の設定 |
|---|---|
| 実装 | Python、vLLMベースのSAS、位置補正用CUDAカーネル、Q-Judge/R-Judge、動的RS |
| 実機A | 2ノード、各4枚のNVIDIA A6000（48GB） |
| 実機B | 2ノード、各8枚のNVIDIA A800（80GB）、PCIe接続 |
| エージェント | AgentBenchを基にしたAW、CG、KG、M2Wの4種類 |
| モデル | Llama系列の8B/70BとGPT-4oを選択肢に使用（本文評価節） |
| 比較 | vLLM+、単純なCascade、RouteLLM、品質モジュールを加えたLlumnix++ |
| 主要指標 | セッション終端間遅延、品質得点、GPU資源と外部APIを含む費用 |
| 品質得点 | 100点満点。正常進行25%、タスク処理50%、少ないラウンドでの完了25% |
| 負荷 | 複数エージェントの起動分布を一様、バースト、Poisson、Gammaで合成 |

終端間遅延の集計では、無効な行動などでタスク完了前に停止したセッションを除外している。このため、遅延だけで品質を評価せず、完了品質と費用を併記する必要がある。複数エージェントの起動時刻は合成分布に基づき、全ラウンドを含む実際の企業エージェントログではない。比較する品質の尺度はAgentBenchに基づく独自の100点満点指標であり、一般的な数学問題の正解率とは異なる。

### セッション単位の費用と品質（原著図8）

A6000の実機でLlama-8B、Llama-70BとGPT-4oを組み合わせ、資源再配置を無効にしてモデル選択部分を比較した。AgServeはAWエージェントでGPT-4oと近い品質を費用16.5%で実現し、同じ費用の従来の費用・品質曲線に対して1.8倍の品質を得た。単純Cascadeは4エージェントのうち1つでしか費用・品質曲線を明確に超えず、RouteLLMは4つすべてで曲線より下になった。これは、開始時の難度だけでなく実行中の品質低下を監視してモデルを昇格することの効果を示す。

ただし「GPT-4oの16.5%」は特定エージェントの費用比較であり、すべてのモデル呼出しをGPT-4oの16.5%の価格で提供できるという意味ではない。費用はGPUノード利用時間とAPI料金を含む実験上のモデルであり、実際の契約料金やクラウドの割引率によって変わる。

### 複数エージェント・キャッシュ・動的割当（原著図9〜14、表2）

| 評価対象 | 比較条件 | AgServeの結果 | 解釈 |
|---|---|---|---|
| 複数エージェント費用 | A800実機、Llumnix++ | 64%削減 | セッション管理・品質選択・割当を統合した効果 |
| 複数エージェント品質 | 同上 | 1.6倍 | 品質を犠牲にした単純なコスト削減ではない |
| キャッシュ命中率 | AW、バッチ8、ECE対LRU | 2.86倍 | 到着予測を使う退避の効果 |
| キャッシュ命中率 | AW、バッチ7/6/5 | 2.80/2.14/1.73倍 | バッチ条件により利得が変化 |
| セッションキャッシュ処理 | AW、vLLMとの比較 | 最大2倍の高速化 | 原位置補正と再利用の寄与 |
| 動的割当の平均終端間遅延 | A800、AgServe | 119.38秒 | 固定配分FS1は125.43秒、FS2は242.35秒 |
| 動的割当の90パーセンタイル | 同上 | 177.05秒 | FS1は206.86秒、FS2は295.86秒 |

キャッシュの2.86倍はバッチ8の命中率比であり、全処理が2.86倍高速化する意味ではない。動的割当の表2では平均遅延119.38秒と固定配分FS1の125.43秒の差は比較的小さい一方、90パーセンタイルは177.05秒対206.86秒と改善が大きい。FS2（大型モデルだけの固定配分）に対しては平均遅延がほぼ半分となるが、モデル構成が異なるため、GPUスケジューラ単体の効果と断定しない。RSの個別寄与は原著の比較設定を確認する必要がある。

### 品質判定器の精度と失敗条件

原著の表1ではQ-Judgeの難度分類正解率が70.4%、RouteLLMが57.9%、単純な交差エントロピー分類が62.4%である。Q-Judgeは大型モデルを過剰に選ぶ誤りを抑えるよう学習されている。R-Judgeは満足できない応答の再現率95.2%を報告するが、閾値を動かすと誤検出率と見逃し率が大きく変わる。表3の例では、ある閾値設定で偽陽性率28.09%、偽陰性率17.60%、別設定では偽陽性率47.93%、偽陰性率0.91%となる。品質監視を強めれば費用が増え、緩めれば低品質の行動が残る。

SGCの判定費用は通常の対話では小さいとされるが、長い文脈の判定やモデル移行では追加処理が発生する。特にR-Judgeが誤って品質不足と判定すると、不要な再試行や大型モデルへの昇格によって費用が増える。逆に品質不足を見逃すと、エージェントの無効な行動やルール違反を防げない。これらはシステムの性能を決める実質的な制約であり、単なる分類器精度だけでなくセッション全体の品質と費用で評価する必要がある。

## 既存研究との差

vLLMやSGLangはページ単位のKV管理や接頭辞キャッシュを提供するが、エージェントのセッションIDと次要求時刻を前提にした退避を直接扱わない。CachedAttentionは対話履歴のKV再利用を工夫するが、途中切り詰めに対応するための別形式のキャッシュが追加メモリを必要とする。AgServeはRoPE位置を原位置で補正することで、セッションの途中切り詰め後にも保持したKVを再利用しやすくする。

RouteLLMは要求単位のモデル選択が中心で、エージェントが長期セッションの後半で難しくなることを十分に考慮しない。AgServeは開始時Q-Judgeと継続R-Judgeを分け、昇格の必要性を継続監視する。Llumnixのような資源配置方式と比べても、キャッシュ・モデル品質・GPU需要の変化を同じセッションの状態として結び付ける点が異なる。これは単なる推論カーネル高速化ではなく、エージェントのプログラム的な呼出し構造を利用したサービング設計である。

## 限界・実装状況

ECEはセッションの次要求到着がある程度予測可能であることを前提とし、外部ツールの遅延が大きく変動する場合や長時間停止するセッションでは予測誤差が生じる。R-Judgeの品質判定は完全ではなく、閾値の設定により費用と見逃しが変わる。論文のテストベッドは2ノードで、セッションを初回に選んだインスタンスへ固定しており、進行中セッションの移動による負荷均衡は将来課題としている。大規模クラスタの評価は付録のシミュレーションであり、60ノードの実機で同じ利得を実測したわけではない。

実装は著者の公開コードにあり、SASはvLLMを基礎にし、RoPE位置補正のCUDAカーネルを追加している。ただし本原稿は著者の測定を一次論文から整理したもので、コードの再実行や別GPUでの再現性検証は行っていない。各数値の比較対象を、キャッシュ命中率・セッション遅延・費用・品質で混同しないことが重要である。
