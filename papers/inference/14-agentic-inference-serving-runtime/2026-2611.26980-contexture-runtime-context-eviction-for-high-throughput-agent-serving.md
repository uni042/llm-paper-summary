# Contexture: Runtime Context Eviction for High-Throughput Agent Serving

> エージェント履歴のトークンをツール操作の置き換え関係でたどって削除候補を特定し、共有KVキャッシュの圧力と残留を見て確定する実行時エビクションで、サービス品質目標下のスループットを最良比較対象比20から73パーセント高めるエージェント提供手法。

## 概要

HermesやOpenClaw、CodexのようなLLMエージェントは、ファイルの確認やコマンド実行を繰り返しながら、増え続ける実行履歴を毎回のリクエストで送り直す。提供側は再計算を避けるため履歴のKVキャッシュをGPUの高帯域メモリに保持するが、同時セッションが有限の共有容量を取り合い、容量そのものがスループットを律速する。論文の観測では、H200のKVプールを半分にするとピークスループットが約40パーセント落ちる。既存の文脈削減はエージェント側の局所的な視点しか持たず共有メモリの圧力を知らず、逆に実行時のKV管理はツール実行の意味を知らない。Contextureはこの2つの情報をつなぐ。トークンを生んだツール操作へたどることで、後続操作に置き換えられた古い出力と関連ターンを削除候補として特定し、確定の判断は共有KVの状態へ委ねる。

**代表結果:** 2モデル、2ハーネス、2ベンチマークの8構成で、サービス品質目標（SLO）を満たすスループットは、削除なし、ハーネス側の圧縮、AgentDiet、Continuumのうち最良のものより20から73パーセント高かった。実エージェント実験では精度が無負荷の削除なし条件より平均1.4ポイント上がり、最悪でも3.7ポイントの低下にとどまった。

## 問題設定

エージェント提供の費用構造は通常の対話提供と違う。履歴はセッション中に単調に増え、しかも各リクエストは履歴全体をプレフィックスとして再送するため、KVキャッシュの需要はセッション数と履歴長の積で膨らむ。容量が尽きると新規セッションを受けられず、再計算のためのプリフィルがデコードと干渉して遅延も悪化する。既存対策は両極端に寄っている。ハーネス側の圧縮や履歴編集は、どの部分が古いかは分かっても、今その削除が共有キャッシュの再利用をどれだけ壊すかを知らない。逆に実行時のKV管理は圧力や残留は見えても、どのトークンが意味的に不要かを知らない。さらに削除には副作用がある。キャッシュ済みの後続部分まで無効化されると次のリクエストで再プリフィルが必要になり、削除で得た容量以上の計算を並行デコードへ押しつける場合がある。問題は「何を消せるか」だけでなく「今消すことが得か」を同時に解くことである。

## 手法のあらまし

Contextureはハーネスが保持する完全な会話履歴と、モデルが実際に見る実行文脈を分離する。ハーネス側の論理は変えず、モデルの実行も変えない。その間に立ち、まず各トークンを生んだツール操作を記録し、後続の操作が先行する出力と関連ターンを置き換えたことを検出して削除候補にする。候補は設定可能な猶予期間だけ保持され、エージェントが関連作業を終える余地を残す。各リクエストでは、候補と共有KVの圧力、キャッシュ済みプレフィックスの残留を突き合わせる。最も早い削除点より後ろにキャッシュ済みKVが残っていない場合は即座に確定し、残っている場合はメモリ圧力が高まるまで遅らせる。再プリフィルの量には上限を設け、確定が並行デコードを圧迫しないようにする。追加のモデル呼出しも学習も使わない。

## 手法

### 1. 置き換え関係の追跡 — 意味的に不要な部分を特定する

この機構が観測するのはツール実行の履歴であり、各トークンがどのツール操作から生まれたかを保持する。後の操作が前の出力を置き換えた、例えば同じファイルを新しい内容で読み直した、同じ対象を再実行して結果が更新された、といった関係が検出されると、古い出力とそれに紐づくターンが削除候補になる。記録された最終履歴では、この候補が全体の64パーセントを占めた。効く理由は、削除の根拠がトークンの古さや注意スコアのような代理指標ではなく、意味的な置き換えという直接の証拠にある点である。追加費用は操作単位の来歴の保持であり、モデル推論は増えない。境界として、置き換えが明示されない暗黙の依存、例えば古い出力を読んで下した判断が後段に効いている場合は候補化されず、保守的に残る。

### 2. 猶予期間 — 候補をすぐ消さない選択の段階

候補になった部分は即座には消えず、設定可能な猶予期間の間は利用可能なまま残る。これは、置き換えた直後の操作が失敗して古い出力へ戻る場合や、関連する一連の作業がまだ続いている場合への保険である。猶予を過ぎた候補だけが確定判断の対象になる。感度評価では猶予の長さがスループットと安全性の交換を動かすことが示され、短すぎると再参照のたびに再計算が起き、長すぎると容量の解放が遅れて圧力緩和に間に合わない。この段階が減らすボトルネックは誤った早期削除による再計算であり、消費する資源は候補分のKV保持である。

### 3. 全体状態に基づく確定時期 — 圧力ゲートとキャッシュ配慮の確定方針

確定の判断は実行時の全体状態で行う。最も早い削除点より後ろにキャッシュ済みKVが何も残っていない場合、その部分は次のリクエストでも再計算が要るため、削除しても失う再利用はなく即座に確定する。これを冷えた確定として扱う。逆に後続のキャッシュが生きている場合、削除はその再利用を捨てることになるため、共有メモリの圧力が高まって容量解放の価値が損失を上回るまで確定を遅らせる。さらに1回の確定で生じる再プリフィルの量に上限を設け、確定が一斉に起きてプリフィルがデコードを押しのける事態を防ぐ。論文の切り分けでは、選択だけでもピークスループットは上がり、冷えた確定がプリフィルと初回トークン遅延を減らし、圧力ゲートがさらにピークを引き上げた。失敗条件は圧力の読み違いであり、急な負荷増では解放が遅れる可能性があるが、上限付きの再プリフィルにより悪化は緩やかになる。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 置き換え追跡 | ツール操作とトークンの来歴 | 置き換えられた出力と関連ターンを候補化 | 意味的に不要なKVの滞留 | 明示されない依存は残す |
| 猶予期間 | 候補の経過時間 | 一定期間は候補を保持 | 早期削除による再計算 | 容量解放の遅れ |
| 圧力ゲート | 共有KV圧力と残留 | 得な時期だけ確定し再プリフィルに上限 | キャッシュ再利用の喪失と干渉 | 急な負荷増への追随遅れ |

## 評価

結論は、エージェント提供では文脈削減の成否は削除対象の選び方ではなく、共有キャッシュの状態と結び付けた確定判断で決まる、というものである。評価はvLLM上に実装し、H100とH200で、2モデル、2ハーネス、2ベンチマークの8構成を比べた。SLO下のスループットは最良の比較対象より20から73パーセント高く、その比較対象のSLOスループットにおける利用者側の90パーセンタイルの遅延悪化は30から78パーセント小さかった。観測マスキングとの比較では8構成中5構成で7から63パーセント上回り、残り3構成はQwenの混合専門家構成でマスキングが上だったが、マスキングは全構成で精度が3から28ポイント落ちたのに対し、Contextureの実エージェント精度は平均で1.4ポイント改善し最悪でも3.7ポイントの低下だった。削除の副作用の対照も明確で、圧縮は90パーセンタイルの遅延悪化が削除なしの1.4から2.5倍、AgentDietは2倍以上になったのに対し、Contextureは削除なしの10パーセント以内に収めた。エネルギーでは完了セッションあたりのGPUエネルギーが最大11パーセント減り、LMCache単独との比較でもH100でSLO下スループットが23パーセント高かった。読み方として、容量を空けること自体は他の方式もできるが、キャッシュ再利用を捨てる損と再プリフィルの干渉を制御できるかどうかが、遅延と精度を守りながら容量利得を回収できるかを分けている。感度評価では、猶予の長さ、圧力の閾値、再プリフィルの上限のいずれも、極端な設定では利得が痩せるものの、中間の広い範囲では結果が大きく崩れないことが示され、調整値への過度な依存ではないことも確認されている。除去比較では選択、冷えた確定、圧力ゲートの順に利得が積み上がり、どの段階が何を改善するかの対応も取れている。

## 既存研究との差

ハーネス側の圧縮やAgentDietのような履歴編集は、削除対象の選択をエージェント側の局所情報だけで決め、共有キャッシュの圧力や残留を知らない。観測マスキングは古い観測を一律に隠すため精度の代償が大きい。逆にLMCacheのような実行時KV管理はキャッシュの状態は扱うがツール実行の意味を持たない。Contextureの差は、意味的な候補特定と実行時状態による確定判断を分離し、両者を突き合わせた点にある。削除を履歴編集の問題ではなく、共有資源のスケジューリング問題として扱う立場である。

## 限界・実装状況

限界は、置き換え関係がツール操作の来歴として観測できる環境に依存すること、猶予期間や圧力の閾値、再プリフィル上限といった調整値がワークロードごとに感度を持つこと、評価が2ハーネスと2ベンチマークの範囲に限られることである。観測マスキングに劣る構成が混合専門家モデルに偏る理由は論文内でも完全には解明されていない。実装はvLLM上の研究実装であり、追加のモデル呼出しや学習は不要だが、ハーネス側から来歴を受け取る連携が前提になる。公式コードの公開先は一次資料で確認できなかった。

## 一般的な実装上の含意

キャッシュから何かを消す判断は、消す対象の古さではなく、消した後に失われる再利用と発生する再計算を、共有資源の現在の圧力と比べて決めるべきである。意味的に不要である証拠と、今消すことが得である証拠は別の情報源から来るため、候補の特定と確定の判断を分離する設計は、エージェント提供以外のキャッシュ管理にも転用できる。再計算量に上限を設けることは、最適化の副作用が他の利用者へ転嫁されることを防ぐ実務的な歯止めになる。もう一つの含意は観測可能性である。どの部分がいつ、どの圧力を理由に消えたかを記録できなければ、精度が落ちたときに原因を削除判断へさかのぼれない。来歴と確定理由を一緒に残すことは、性能の改善と障害時の切り分けを両立させるための前提であり、共有資源を扱う実行時最適化では測定と同じくらい重要である。
