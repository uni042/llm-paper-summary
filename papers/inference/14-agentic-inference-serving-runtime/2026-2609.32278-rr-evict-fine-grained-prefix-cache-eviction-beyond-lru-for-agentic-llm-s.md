# RR-Evict: Fine-Grained Prefix Cache Eviction beyond LRU for Agentic LLM Serving

## 概要

RR-Evictは、長い対話履歴を保持する複数の大規模言語モデル（LLM）エージェントを同時に処理する際、接頭辞キャッシュの削除が一部のエージェントに集中し、初回トークン遅延の外れ値を生む問題を解決する。エージェントはモデル呼び出しの間にツール実行やユーザー応答待ちを挟むため、過去の履歴を再利用する時刻が不規則になる。通常の最近最少使用方式（Least Recently Used、LRU）では、同じエージェントのキャッシュ木に属するノードの最近使用時刻がほぼ同時に更新され、削除対象が特定のエージェントに偏る。

RR-Evictは休止中のエージェントを巡回し、各エージェントの履歴末尾から小片を一つずつ削除する。キャッシュの接頭辞整合性を維持しながら、少数の履歴を丸ごと消す代わりに多数の履歴を部分的に保持する。SGLangでの実装をNVIDIA H100上で評価した結果、従来のLRUと比べ、会話エージェントの99パーセンタイル初回トークン遅延（P99 TTFT）を最大75.4%、未キャッシュ入力トークン数の99パーセンタイルを最大65.7%削減した。これは最良の評価条件における尾部遅延改善であり、平均生成速度が75.4%改善したという意味ではない。

## 問題設定

LLM推論の事前入力処理では、入力トークンに対する注意機構の鍵・値（KV）を計算する。過去と同じ接頭辞が入力された場合、そのKVを保存しておけば再計算を省略できる。エージェントが第1ターンから第Nターンへ進む際、通常は既存の会話履歴に新しいツール結果や指示を追加するため、長い接頭辞が繰り返し現れる。接頭辞キャッシュは、この反復処理の計算量と初回トークンまでの待ち時間を抑える。

ところが、エージェントの同時実行数が増えると、各履歴に対応するキャッシュの合計量がGPUメモリを超える。配信基盤は実行中の要求が使っているノードを保護しながら、休止中の履歴から容量を回収しなければならない。SGLangは接頭辞を基数木（radix tree）として管理し、削除可能な葉から削除を進める。共有システム指示は複数エージェントが再利用できる一方、長い対話履歴の大半はエージェント固有である。

LRUが適切に働くには、ノード間の最終使用時刻に意味のある差が必要になる。しかしエージェントの新しい要求は残存する履歴全体を接頭辞照合するため、その経路のノードを一斉に更新する。論文はこれを「最近性の同期（recency synchronization）」と呼ぶ。あるエージェントが最も長く休止していると、その葉を削除した直後に新しく葉になった親もほぼ同じ古い使用時刻を持つ。結果として同じエージェントのノードが連続して選ばれ、履歴のほとんどを失う場合がある。

キャッシュ命中率の全体平均だけではこの問題を見落とす。大半の要求は再利用できても、履歴を全消去された少数のエージェントが復帰すると長い事前入力処理を強いられ、P99の初回トークン遅延を押し上げる。RR-Evictは平均命中率の最大化よりも、削除の負担を複数の休止履歴へ配分して極端な再計算を抑えることを主目的とする。

## 手法

### 1. 休止エージェントの抽出と巡回待ち行列

RR-Evictは基数木の接頭辞照合、活動中ノードの保護、葉から親へ遡る削除という基本規則を変更しない。メモリを一定量回収する必要が生じると、まず活動中要求が参照していない削除可能な履歴をエージェント単位にまとめる。従来のLRUが葉ノードの最終アクセス時刻を基準に優先度付き待ち行列を構成するのに対し、RR-Evictは休止中のエージェント軌跡を一つずつ巡回する待ち行列を作る。

待ち行列の先頭から一つの軌跡を取り出し、その末尾の小片を削除する。まだ削除可能な末尾が残っていれば、その軌跡を待ち行列の末尾へ戻す。必要なメモリ量を回収するまでこれを繰り返す。選択単位がエージェント軌跡であるため、一つの履歴の古いノードだけを連続して削除しにくくなる。アルゴリズムの入力は休止軌跡集合と必要回収量であり、出力は回収されたキャッシュ容量と、残存する各軌跡の接頭辞である。

### 2. 末尾小片の選択と木構造の整合性

一度に削除する末尾小片（tail chunk）は、基数木の葉ノード全体であっても、その葉の末尾部分であってもよい。葉の一部を削除した場合、残りの葉が次の削除候補になる。葉全体を消した場合は親ノードが新しい葉となるが、親が活動中の要求や共有接頭辞によって保護されていれば削除しない。こうして常に有効な連続接頭辞を保持する。

この「末尾から削る」という条件は重要である。履歴の中間部分を消して末尾だけ残しても、通常の接頭辞照合では後半のKVをそのまま再利用できない。末尾だけを削れば、復帰したエージェントは残った接頭辞を利用し、失われた末尾と新しく追加したトークンだけを再計算できる。論文の評価では削除小片の大きさを1,024トークン相当に設定している。

### 3. 活動状態の再確認と完了通知

待ち行列を構成した後にエージェントが再開する可能性がある。RR-Evictは小片を削除する直前に対象軌跡がまだ休止中かを確認し、活動中であれば飛ばす。これにより、削除処理と新しいモデル呼び出しの競合を避ける。未来の要求到着時刻やツール実行時間の予測は必要ない。

終了済みエージェントのキャッシュを保持し続けることも無駄である。アプリケーションがエージェントの完了を通知できる場合、共有されない履歴を直ちに解放する。論文の評価では、RR-Evictと比較対象の「完了通知付きLRU」の両方へ同じ完了通知を渡している。そのため両方式の差は、完了通知の有無ではなく、まだ生存する休止エージェントのキャッシュをどのように削除するかに起因する。

完了通知を得られない場合には、最終アクセス時刻に基づく段階分け（recency tiering）を組み合わせる拡張も説明される。古い段階から順に処理し、同じ段階内では巡回削除する設計である。ただし、この段階別方式は論文の実験では評価されていない。実測の改善率をその拡張にそのまま適用することはできない。

### 4. 理論モデルと有効なメモリ領域

論文は、エージェント間に履歴共有がなく、各履歴の大きさが等しい単純化モデルを使って、削除の分散が尾部遅延へ与える影響を説明する。生存エージェント数を `n`、活動中の割合を `a`、休止中の割合を `s=1-a`、完全な履歴一つ分を1単位としたキャッシュ容量を `m` とする。活動中の履歴は約 `na`、休止中の履歴は約 `ns` となる。

`m ≥ n` ならすべての履歴を保持できるため削除は不要である。反対に `m ≤ na` なら活動中の要求だけで容量を使い切り、休止履歴を保存する余地がほぼない。RR-Evictの主な利点が生じるのは **`na < m < n`** の中間領域である。このとき活動中の履歴を保護した後に、休止履歴へ `m-na` 単位の容量を分配できる。

理想的な巡回削除では各休止履歴の保持割合は `h=(m-na)/(ns)`、再計算割合は `q=1-h=(n-m)/(ns)` になる。一方、削除が集中するLRUでは、割合 `q` の復帰エージェントが履歴を完全に失い、残りの割合 `1-q` は全履歴を保持すると近似できる。両方式の平均再計算割合はともに `q` であるが、分布が異なる。巡回方式は再計算を各エージェントへ薄く配分するため、完全な履歴欠損による極端な初回トークン遅延を抑えやすい。

この理論モデルは平均要求待ち時間や実機のP99をそのまま予測するものではない。新規入力トークン、待ち行列、同時実行中の要求の突発増加、エージェント間の共有接頭辞、削除粒度を無視している。また、LRUで完全欠損となる割合 `q` が極めて小さいと、固定された分位点では巡回方式が必ずしも有利とはならない。したがって論文は巡回方式の優位をあらゆるメモリ容量へ一般化していない。

## 評価

### 実験環境と比較の公平性

著者はRR-EvictをSGLangに実装し、NVIDIA H100 GPUをNVLinkで接続した環境で、会話エージェントとコード修正エージェントの両方を評価した。会話負荷はローカルのτ²-bench銀行業務222軌跡であり、Qwen3-Coder-30B-A3B-InstructをBF16・テンソル並列2で動作させる。コード修正負荷はSWE-benchとQwen3-8Bを使い、事前入力処理ワーカー1台と逐次生成ワーカー3台の分離配信（1P3D）で評価する。コード修正では接頭辞キャッシュを事前入力処理側に置く。

| 評価項目 | 会話エージェント | コード修正エージェント |
|---|---|---|
| ワークロード | τ²-benchの銀行業務222軌跡 | SWE-bench |
| モデル | Qwen3-Coder-30B-A3B-Instruct | Qwen3-8B |
| 配信構成 | BF16、テンソル並列2 | 事前入力処理1・逐次生成3ワーカー（1P3D） |
| GPU | NVIDIA H100、NVLink接続 | NVIDIA H100、NVLink接続 |
| 比較対象 | LRU、完了通知付きLRU | LRU、完了通知付きLRU |
| 提案方式の削除粒度 | 1,024トークン相当 | 1,024トークン相当 |
| 主要指標 | P99初回トークン遅延、P99未キャッシュ入力数 | 同左 |

各方式の比較においては、一度ベンチマークを実行して入力文脈、出力長、要求順序、ターン間の待ち時間を記録し、その軌跡を再生する。これにより、方式ごとにエージェントの判断が変わって負荷が変動することを抑えている。同時実行数は、システムに受け入れるエージェント数を変えることで調整する。ツール実行やユーザー応答待ちの間も、エージェントは受け入れ済みとして数えられ、休止履歴がGPUメモリを占有し続ける。

初回トークン遅延（TTFT）は要求が到着してから最初の出力トークンが得られるまでの時間で、事前入力処理と待ち行列の影響を含む。未キャッシュ入力トークン数は、要求の入力長から再利用できた接頭辞の長さを引いた値であり、新しい入力だけでなく、削除によって失った過去の履歴も含む。両指標を併用することで、キャッシュ削除による再計算量と利用者に見える遅延を対応付けられる。

### 主要な定量結果

| ワークロード | 比較対象 | P99初回トークン遅延の最大削減 | P99未キャッシュ入力数の最大削減 |
|---|---|---:|---:|
| 会話エージェント | 通常LRU | 75.4% | 65.7% |
| 会話エージェント | 完了通知付きLRU | 46.9% | 30.6% |
| コード修正、1P3D | 通常LRU | 60.7% | 60.8% |
| コード修正、1P3D | 完了通知付きLRU | 60.5% | 56.2% |

会話エージェントでは、評価した同時実行数の全条件でRR-Evictが両比較方式より良好な尾部指標を示した。ただし表の削減率は各比較における最大値であり、全同時実行数の平均値ではない。完了通知付きLRUとの比較でも最大46.9%のP99遅延削減が残ることから、終了済みエージェントの早期解放だけでは説明できない改善がある。

コード修正負荷では、エージェントのツール待ちが会話負荷より短く、休止状態を利用する余地が少ない。それでも事前入力処理と逐次生成を分離すると、生成処理中にも事前入力処理側で接頭辞が休止状態となる。この構成ではRR-Evictが通常LRU比で最大60.7%、完了通知付きLRU比で最大60.5%のP99遅延を削減した。これらの結果は分離配信構成に固有のものであり、単一GPUの全構成へ一般化してはならない。

### 同時実行数、メモリ圧迫と尾部の関係

会話負荷の同時実行数80の軌跡では、活動中要求のKV需要はキャッシュ容量内に収まる一方、活動中と休止中の需要の合計は容量を超える時間帯が継続していた。これは理論節の `na < m < n` に対応する状況であり、休止履歴の一部を残すための容量がある。RR-Evictはこの余地を複数の履歴へ配分することで、完全な履歴欠損を減らす。

同じ同時実行数80での未キャッシュトークン数と初回トークン遅延の分布は、極端に長い事前入力処理の頻度が減ることを示す。初回トークン遅延の改善が未キャッシュトークン数の改善より大きい場合、長い事前入力処理が後続要求を待たせる先頭詰まりを緩和した可能性があると著者は説明する。ただしこれは実測した各分布の解釈であり、両指標の改善率が常に一致するという主張ではない。

低い同時実行数では完了通知だけでも十分に容量を解放できるため、巡回方式の追加利得は小さくなる。反対に最も高い同時実行数では、活動中のKV需要が増えて休止履歴に割ける容量が減るため、利得が再び狭まる。RR-Evictでも長いキャッシュ欠損が完全に消えるわけではなく、活動中要求が突発的に増えると再計算の外れ値が残る。論文はこの負の条件も示している。

### 結果の解釈と未評価事項

P99削減率は最悪1%付近の遅延を改善した指標であり、全要求の平均遅延や総生成トークン数の改善率を直接示すものではない。会話負荷とコード修正負荷ではモデル規模、タスク、配信構成が異なるため、表の数値を単一のハードウェア条件で横並びに比較することにも注意が必要である。図の正規化された結果から読み取れるのは、同じ負荷点の比較方式に対する相対的な改善である。

原著は最近性段階別の拡張について定量評価していない。多数のエージェント間で長い接頭辞が共有される場合、外部KV階層と組み合わせた場合、異なるGPU世代やモデル系列、非常に短いセッションだけの負荷で同じ削減率が成立するかも、本論文の実験だけでは断定できない。平均命中率、総処理量、電力、運用時の予測外負荷に対する改善は、P99の報告値と混同しない。

## 既存研究との差

従来のLRUは各キャッシュノードの最近使用時刻を基準に削除順を決める。共有システム指示と要求固有の短い接尾辞が混在する通常の推論では、この基準はよく機能する。一方、長期エージェントでは同じ履歴の多数のノードが同時に参照されるため、最近使用時刻がノード間の有用性を区別しにくくなる。RR-Evictは最近性の予測精度を高めるのではなく、履歴の削除負担を分散させることを選ぶ。

エージェントの将来の実行順序を予測して保持対象を選ぶ方式や、CPUからの事前取得を組み合わせる方式とも異なる。RR-Evictが必要とするのは現在の活動状態とキャッシュ木の情報であり、次にどのエージェントが呼び出されるかを推定しない。実装では接頭辞キャッシュ木とKV計算の仕組みを維持できるため、モデルの再学習やKVの近似量子化を必要としない。改善は削除順序と粒度の変更から得られる。

## 限界と負の結果

第一に、活動中要求のKVだけでメモリが満杯になる条件では、休止履歴へ配分する容量がなく、巡回方式だけでは容量不足を解決できない。第二に、完了通知を得られない場合は既に終了したエージェントのキャッシュを保持し続けるおそれがあり、著者が提案する最近性段階別の拡張は未評価である。第三に、同じ量のKVを削除しても各エージェントの接頭辞が少しずつ短くなるため、全体の平均再計算量が常に減るわけではない。理論モデルでは平均再計算量がLRUと等しい場合でも尾部が改善する。

第四に、評価は記録済みの要求軌跡を再生する方式であり、応答時間の変化がエージェントの将来の行動を変える閉ループ負荷を全面的に再現したものではない。第五に、最大75.4%という改善率は特定の会話負荷と同時実行数の条件に依存し、通常のLLMサービング全般で保証されるものではない。第六に、接頭辞を大規模に共有する負荷、外部キャッシュ階層、異なるKV管理単位へ適用した際の効果は追加評価が必要である。
