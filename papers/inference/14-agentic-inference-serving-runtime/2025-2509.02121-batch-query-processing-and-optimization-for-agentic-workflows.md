# Batch Query Processing and Optimization for Agentic Workflows

> Haloは「LLM呼出しを1件ずつ速くする」のではなく、同時に走るエージェントワークフロー全体を実行計画として扱う。最新版v2では、同一ツール要求の統合とCPU-GPU協調を加え、強いエージェント基盤に対してバッチ推論最大3.6倍、オンライン処理量最大2.58倍を報告する。

## 書誌情報

Junyi Shen、Noppanat Wadlom、Yao Luによる論文で、arXiv:2509.02121として2025年9月2日に初版が投稿され、2026年1月19日にv2へ改訂された。本ページは最新版v2を基準にする。初版v1で報告された「最大18.6倍・4.7倍」と、v2の「最大3.6倍・2.6倍」は評価系とシステム設計が更新されているため混同しない。

## 概要

一般の推論サーバは一つ一つのLLM要求について、連続バッチ処理（continuous batching）やキー・値キャッシュ（Key-Value cache; KVキャッシュ）を最適化する。一方、エージェント処理では1ユーザー要求が複数のLLM、SQL、検索、HTTP、ローカル関数へ分岐し、同じ型のワークフローが数百〜数千件並ぶ。同じモデル、共通プロンプト、同一SQL、同じ検索結果を再利用できても、各要求を独立に処理するとその構造は推論エンジンから見えない。

Haloは各ワークフローを依存関係付き有向非巡回グラフ（Directed Acyclic Graph; DAG）へ変換し、GPU上のLLMノードとCPU/I/O上のツールノードを同じ計画対象にする。各演算の過去プロファイル、モデル常駐状態、KVキャッシュ、CPU負荷、依存関係を使い、エポック単位の動的計画法（Dynamic Programming; DP）で実行順序・GPU配置・バッチ形成を同時に選ぶ。実行時には、同じツール呼出しを一度へ統合し、結果を複数の論理ノードへ配るほか、CPU処理とGPU推論を重ね、空き時間には依存関係を壊さない範囲で別の準備済みノードを先に実行する。

v2の主評価は3基のNVIDIA H200 NVLを備えたサーバで、Qwen3 14B/32BとGPT-OSS 20B、PostgreSQLを組み合わせた6種のエージェントDAGを用いる。1024問い合わせのバッチでは、単純なvLLM逐次実行に対してW1で71時間超→676秒と400倍超になるが、これはバッチしない極端な比較である。より強いワークフロー基盤との比較では、単純〜中程度のW1〜W4で1.03〜2.6倍、重複I/Oが多いW5/W6で2.4〜3.6倍となる。オンラインではLangGraphに対して最大2.58倍、OpWiseに対して1.53〜1.74倍の処理量改善を報告する。

## 背景：エージェントDAGでは「推論」だけでなくCPUツール待ちがGPUを空転させる

通常のLLM配信では、プリフィル（prefill）とデコード（decode）の要求をまとめ、同じモデルをGPUに常駐させ、KVキャッシュを再利用することで効率を上げる。ところがエージェント型ワークフローでは、LLMの出力を受けてSQLを実行し、その結果を次のLLMへ渡し、さらにHTTP検索へ進む、といった異種資源間の依存が生じる。GPU側だけを最適化しても、直前のCPUツールが終わらなければGPUは次のノードを実行できない。

逆に、DAG実行器だけではLLM固有の状態を扱えない。一般的なデータ処理基盤は演算ノードを黒箱として見なすため、同じモデルを連続して実行して重み再ロードを避ける、共通接頭辞のKVを再利用する、といった判断ができない。Haloは「ワークフロー構造」「CPU/GPUの異種性」「GPU上のモデル/KV状態」の3点を同時に見えるようにしたことが中心である。

## 問題設定

入力は、同じテンプレートを共有しつつパラメータや取得データが異なる多数のエージェントワークフローである。各DAGにはGPUで実行するLLMノードと、SQL・HTTP・関数などCPU/I/O主体のツールノードがあり、先行ノードの完了なしには後続を実行できない。

目的は論理計画そのものを書き換えて回答を近似することではなく、同じ意味の処理を保ったまま物理実行を速くすることにある。したがってHaloは、依存関係を守りながら、どのノードをいつ、どのGPU/CPU実行器で、どの要求とまとめて処理するかを最適化する。性能はモデル切替、プリフィル/デコード長、KV再利用、CPUツール待ち、通信量によって変わるため、固定した「最短ノード優先」のような規則では不十分になる。

## 手法

### 1. パーサがLLMとツールを明示的なDAGノードへ分離する

Haloの入力は宣言的なワークフロー仕様である。パーサはこれを型付き中間表現GraphSpecへ変換し、プロンプト内やエージェント実装内に埋もれていたデータベース問い合わせ、API、ローカル関数を独立ノードとして取り出す。この依存分離によって、CPU側の処理もLLMノードと同じように「いつ実行するか」をスケジューラが判断できる。

出力は、ノード種別、依存辺、モデルやツールの設定を含むDAGである。この表現がない場合、推論エンジンからは「次のLLM要求がなぜまだ来ないのか」が見えず、CPUツール側からも「どの処理を先に終えればGPUが動けるか」が分からない。

### 2. プロファイラがモデル・KV・CPUツールの実行費用を見積もる

各ノードの費用は同一ではない。HaloはSQLについてデータベースの実行計画、黒箱APIやユーザー関数について実測移動平均、LLMについてモデル・GPU構成別に較正したプリフィル/デコード処理量曲線を使う。GPUについては、目的モデルがすでに常駐しているか、共通接頭辞のKVが残っているかで追加費用を変える。

この費用モデルの入力は「実行候補ノード」と「現在のワーカー状態」で、出力はその配置を選んだときの予測時間である。モデル切替やKVミスを固定費として無視しないため、同じモデルを使うノードを続けて置く、同じ系譜の要求を同じGPUへ寄せる、といった判断を数値化できる。

### 3. エポック単位の動的計画法で実行順序・配置・バッチを共同最適化する

スケジューラは、すべての準備可能ノードを一度に巨大な整数計画へ入れるのではなく、エポックごとに現在状態から次の実行集合を決める。メモ化した動的計画法は、完了済みノード集合とハードウェア状態を状態として、候補バッチとGPU割当てを試し、費用モデルで評価して状態遷移を進める。

ここで得たいのは局所的に最速の1ノードではなく、後段まで含めた総完了時間の短縮である。例えば少し待って同じモデルの複数要求をまとめた方が重み再ロードを避けられる場合や、CPU側の重い前処理を先に開放した方が将来のGPU空転を防げる場合を扱える。W1では混合整数線形計画（Mixed-Integer Linear Programming; MILP）のオラクル322.17秒に対しHaloは323.64秒で、計画時間は1.44時間から2.24秒へ短縮した。

### 4. 同一ツール要求を統合し、結果をファンアウトする

CPU/I/O側では、演算種別と正規化した引数から要求署名を作り、同一署名の保留中要求を一つの物理実行へ統合する。例えば多数のエージェントが同じSQLテンプレートと同じ引数を発行した場合、データベースへ一度だけ問い合わせ、結果を複数の論理ノードへ配る。準備済みSQLもエポック内で再利用する。

これは単なる「同時実行」の逆で、重複処理そのものを消す最適化である。特に高ファンアウト型DAGでは効果が大きく、W6でこの要求統合を無効にするとエンドツーエンド遅延が154%増え、約2.54倍遅くなった。したがってv2では、初版のKV共有だけでなくCPU/I/O重複排除が主要な改善源になっている。

### 5. CPU-GPUパイプラインと機会的実行で空き時間を埋める

実行時コーディネータは、次のLLMノードを開放するCPUタスクを優先し、ツールごとの同時実行数には上限とバックプレッシャーを設ける。GPU側は計画されたモデル常駐・KV再利用を尊重しつつ、厳密な全ワーカー同期は行わない。1ノードが終われば依存条件を満たした後続をすぐ進める波面型実行（wavefront execution）を採る。

外部APIなどのばらつきで本来の高優先ノードが止まった場合は、依存関係を満たし、近い将来必要なモデルを追い出さない範囲で別の準備済みノードを機会的に実行する。W6ではこの機構を除くと56%遅くなり、CPU負荷ガイダンスを除くと18%悪化した。計画の良さだけでなく、実測時間の揺らぎへランタイムで追従する必要があることを示している。

バッチサイズを大きくすれば常に良いわけではない。プロセッサ内バッチを増やす初期段階では固定費を償却できるが、大き過ぎると一段の処理完了を待つ時間が延び、後段へデータが流れず先頭待ち（head-of-line blocking）が発生する。Haloはこの折れ曲がり点付近を狙う。

## 既存研究との差

vLLMやSGLangは個々のLLM要求内部のバッチ・KV管理に強いが、SQLやHTTPを含む上位DAGの依存関係を見ない。LangGraphやAgentScopeは逆にエージェントの制御フローを見られるが、GPU上のモデル常駐、KV状態、推論バッチへ直接介入しない。Haloはこの二層を同じ費用モデルとスケジューラへ接続する。

ParrotやAyo/Teolaのような意味・データフロー認識型基盤に対しては、Haloの主眼は単一要求の論理変換ではなく、多数DAGをまとめた物理実行最適化にある。またv2は、初版よりCPUツールを明示的に扱い、要求統合とCPU-GPUパイプラインを中心へ広げているため、旧版の「GPUワーカー配置とKV共有だけのシステム」と理解すると不足する。

## 限界・実装状況

評価ワークロードはIMDb、FineWiki、TPC-Hに基づくものの、DAGそのものは実運用構造を模した合成ワークロードである。実際のエージェントでは外部APIの遅延分布、失敗、再試行、非決定的ツール、副作用を伴う書込みがあり、同一署名の要求を安全に一つへまとめられない場合がある。

またHaloは固定された論理DAGを前提に物理配置を最適化する。自由度の高い自律エージェントのように、次のツールや分岐が実行中に大きく変わる場合は、計画の再構築頻度と最適化費用が増える。モデル数についても主評価は比較基盤の静的配備制約に合わせ各ワークロード最大3種類へ制限しており、より多数の異種モデルを同時利用したときの実運用挙動は追加評価が必要である。

強い速度倍率を読む際には比較対象を区別する必要がある。400倍超は要求間バッチをしないvLLM逐次実行に対する値で、Halo自体の優位性を示す代表値としては、強いワークフロー基盤に対する最大3.6倍やオンライン最大2.58倍の方が適切である。
