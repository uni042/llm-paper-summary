# Scepsy: Serving Agentic Workflows Using Aggregate LLM Pipelines

> LLMごとの安定した相対負荷を集約パイプライン化し、GPU分数・テンソル並列・複製数・配置を共同探索して任意の複数LLMエージェント処理を効率化する。
## 書誌情報
- **著者**: Marcel Wagenländer, Otto White, Britannio Jarrett, Pedro Silvestre, Yanda Tao, Guo Li, Huanzhou Zhu, Llúis Vilanova, Peter Pietzuch
- **著者・所属**: Imperial College London; Independent Researcher
- **公開**: arXiv
- **種別**: プレプリント
- **対象**: エージェントサービング、複数LLM、GPU割り当て、テンソル並列、GPU共有
- **実装**: 約25K行のPythonプロトタイプ。Kubernetes、変更したdevice plugin、NVIDIA MPSを用い、vLLMやSGLang等の実行エンジンを対象とする。
## 概要
Scepsyは、分岐・反復・ファンアウトを含む複数LLMエージェント処理を、個々の制御フローを予測せずGPU群へ割り当てるサービングシステムである。各LLMがワークフロー全体の実行時間に占める相対比率が要求間で安定するという観測から、低水準のLLM呼び出しトレースと並列度別プロファイルを集約LLMパイプライン（Aggregate LLM パイプライン）へ変換する。この軽量予測器を使い、GPU分数、テンソル並列度、複製数を共同探索し、最後にNVLink等の接続構造と断片化を考慮して配置する。16 GPU評価では既存方式に対し最大2.4倍のピークスループットまたは最大27倍低い平均遅延を報告する。

Scepsyの中心的観測は、要求ごとの絶対実行時間は大きく揺れても、各LLMがワークフロー全体のLLM実行時間に占める相対比率は最大4倍ほど安定するという点である。そこで動的制御フローを完全予測せず、LLM呼び出し回数、要求内並列度、並列構成別の処理量・遅延プロファイルを集約LLMパイプラインへ圧縮する。これを資源割り当ての高速予測器として、各LLMのGPU分数、テンソル並列度、複製数を共同探索し、複数LLM間で変化するボトルネックをワークフロー単位で均衡させる。さらに分数GPUを実機へ置く際、テンソル並列を高速相互接続内へ閉じ込め、断片化を抑える階層配置まで統合する。

代表結果として、最大ピークスループット改善は同一GPU予算、現実的エージェントワークロードで個別LLM最適化またはユーザー指定割り当てに対して最大2.4×。LLM間の相対需要を共同最適化し、ボトルネックへ複製・並列資源を再配分する効果。
## 問題設定
エージェント型ワークフローは異なるLLM、ツール、データベースを組み合わせ、入力に応じて分岐・反復・再帰・ファンアウトする。生成長も変動するため、同じ処理でも実行時間とLLM呼び出し回数が大きく変わる。論文のビーム探索では生成LLM呼び出しが要求ごとに24〜844回、エンドツーエンド遅延が9〜264秒に広がる。さらに複数LLMはGPU数を上回りやすく、複製を増やすとスループットは上がる一方でテンソル並列へ使えるGPUが減り遅延が悪化する。既存のエージェントサービングは特定プログラミングモデルや単一LLMを仮定し、一般的な複数LLMサービングは各モデルを独立最適化するため、ワークフロー全体のボトルネック移動を扱いにくい。
## 新規性
Scepsyの中心的観測は、要求ごとの絶対実行時間は大きく揺れても、各LLMがワークフロー全体のLLM実行時間に占める相対比率は最大4倍ほど安定するという点である。そこで動的制御フローを完全予測せず、LLM呼び出し回数、要求内並列度、並列構成別の処理量・遅延プロファイルを集約LLMパイプラインへ圧縮する。これを資源割り当ての高速予測器として、各LLMのGPU分数、テンソル並列度、複製数を共同探索し、複数LLM間で変化するボトルネックをワークフロー単位で均衡させる。さらに分数GPUを実機へ置く際、テンソル並列を高速相互接続内へ閉じ込め、断片化を抑える階層配置まで統合する。
## 手法
### 手法のあらまし
まず任意のエージェントフレームワークのLLM API前段へHTTPプロキシを置き、代表要求から各LLM呼び出し、開始終了時刻、直列・並列関係を収集する。ここではアプリ内部のグラフ表現を解析せず、実際に発生したLLM API呼び出しだけを観測する。次にLLMごとに平均呼び出し回数nと平均要求内並列度pを算出し、同じトレースのLLM要求を到着率とテンソル並列度を変えて再生して、飽和までのスループット・遅延曲線を測る。この再生では実トレースの入力長、出力長、接頭辞キャッシュ特性を保持する。得られたLLM別曲線をワークフロー単位へ換算し、呼び出し回数と並列度で遅延寄与を補正した集約LLMパイプラインを構成する。全体スループットは最も能力の低いLLM段、全体遅延は各段の補正済み遅延寄与から予測する。スケジューラはこの予測器を繰り返し評価し、まず目標到着率を満たす処理能力を複製で確保し、残資源を遅延短縮に有効なテンソル並列へ配る。GPUを細かな分数として扱い、LLMの相対遅延比、必要メモリ、高速相互接続の上限を使って探索候補を枝刈りし、分数割り当て、実GPUへの詰め込み、テンソル並列度と複製数の解決を順に行う。複数ワークフロー時はさらにワークフロー間へ資源を配る階層を加え、一方を飢餓させない候補を選ぶ。最後に大きなテンソル並列配置から先にノードへ置き、高速接続領域を守りながら小さな分数を密に詰め、Kubernetes配置を生成する。変更したdevice pluginが階層配置を実現し、NVIDIA MPSが同一GPU上の複数LLMへ計算資源を分割する。これにより実行時の動的分岐を逐一予測せず、観測→集約→候補探索→物理配置という一連の流れでワークフロー全体の処理量と遅延を共同最適化する。

### 集約LLMパイプライン
低水準APIトレースから各LLMの平均呼び出し回数nと要求内並列度pを取り、LLMごとの実測スループット・遅延プロファイルをワークフロー単位へ変換する。プロファイル作成では実トレースを到着率ごとに再生し、テンソル並列度も1、2、4など複数条件で測るため、入力・出力長や接頭辞キャッシュの実際の偏りを保持する。各段の遅延は平均呼び出し回数と並列度で補正し、ワークフロー全体の処理能力は最も遅い段が決めるとみなす。絶対実行時間より相対LLM需要が安定する性質を使うため、分岐・ループ・ファンアウトを静的グラフとして解析せずに多数の資源割り当て候補を高速比較できる。

### GPU分数・並列度・複製数の共同探索
GPUを整数台だけでなく細かな分数資源として扱い、各LLMへモデル重みとKVキャッシュを保持できる必要最小分数をまず保証する。そこから相対遅延が大きいLLMほど多くの資源を得る順序制約、連続したGPU分数への割り当て、テンソル並列を高速相互接続範囲内に制限する条件で候補を枝刈りする。分数を実GPU数へ写した後、テンソル並列度×複製数が利用GPUを無駄なく使う組合せを列挙する。複製数を増やすとボトルネック段の処理能力が増え、テンソル並列を増やすと臨界段の単要求遅延が下がるため、集約パイプラインで目標到着率を満たすかを確認しながら両者を共同選択する。

### 接続構造対応の分数配置
論理的に選んだGPU分数を実クラスタへ置く際、単純な空き容量だけでなくテンソル並列通信と将来の断片化を考慮する。まず多くのGPUをまたぐテンソル並列インスタンスを優先して、NVLink等の高速接続領域内へまとまるようノードへ配置する。次に小さな分数を同一GPUへ密に詰め、空きが細切れになって後続の大きな配置が不可能になることを避ける。配置結果はKubernetes deploymentへ変換し、変更device pluginが階層的なGPU割り当てを提示し、NVIDIA MPSが同一GPU上の複数LLMへ計算資源を分離する。これにより探索器が選んだ分数資源とテンソル並列条件を物理トポロジ上で崩さず実行できる。

### 全体のデータ／制御の流れ
ScepsyはエージェントアプリとLLM実行エンジンの間にあるオーケストレーション層であり、特定のLangGraph等の内部表現を要求しない。トレース・再生プロファイル・集約予測・資源探索・物理配置を分離することで、vLLMやSGLangなど既存エンジンの推論最適化をそのまま利用しつつ、複数LLM間の資源配分だけをワークフロー全体で最適化する。
## 評価条件
- **ハードウェア**: 最大16 GPUのクラスタで評価し、4 GPU・8 GPU構成でも比較する。論文はGPU間高速接続をテンソル並列配置制約として扱い、複数ノード・複数GPU分数の配置を評価する。
- **ソフトウェア**: 約25K行のPython実装。Kubernetes上のオーケストレーション、変更device plugin、NVIDIA MPSによる空間共有を使用する。LLM実行エンジンとしてvLLM等を利用し、Aegaeon比較とAyo比較を実施する。
RAG+reranker、ビーム探索、両者の複合という3種の現実的エージェントワークロードを用いる。代表実行をHTTPプロキシでトレースし、LLMごとに到着率とテンソル並列度を掃引してプロファイルを作る。評価では到着率を変えたスループット・平均遅延曲線、4/8 GPUでのAegaeon・Ayo比較、複数ワークフロー同時実行、集約パイプライン予測精度、探索時間とGPU分数粒度の拡張性を測る。
動的な複数LLMエージェント処理のクラスタ資源割り当てが対象で、単一LLMカーネルやKV管理そのものは既存実行エンジンへ委ねる。相対LLM需要が安定し、ツール実行時間がLLMに比べ小さいワークロードを主対象とする。異なるLLM間の同時ファンアウトや二峰性負荷、長時間ツールは議論で制約として明示される。
## 主要結果
Scepsyは個別LLMを独立配置する方式やユーザー指定配置に対し、同一GPU予算で最大2.4倍のピークスループット、同一スループットで最大27倍低い平均ワークフロー遅延を報告する。Aegaeon比較ではビーム探索で4 GPU時7.3倍、8 GPU時6.8倍のスループット、遅延は14.1倍・12.9倍改善した。RAGではスループット2.5倍・2.9倍、遅延3.4倍・4.5倍改善した。

- 最大ピークスループット改善 / 最大2.4× (比較対象: 個別LLM最適化またはユーザー指定割り当て; 条件: 同一GPU予算、現実的エージェントワークロード) — LLM間の相対需要を共同最適化し、ボトルネックへ複製・並列資源を再配分する効果。

- 最大平均遅延改善 / 最大27×低減 (比較対象: 既存複数LLM/ワークフロー配置; 条件: 同一目標スループット) — 余剰GPUを重要LLMのテンソル並列へ回し、ワークフロー全体の臨界経路を短縮する。

- Aegaeon対ビーム探索 / 4 GPU 7.3×、8 GPU 6.8×高スループット; 遅延14.1×、12.9×改善 (比較対象: Aegaeonの複数配置構成; 条件: ビーム探索) — 固定的なモデル単位多重化よりワークフロー需要に沿う配置が有利。

- Aegaeon対RAG / 4 GPU 2.5×、8 GPU 2.9×高スループット; 遅延3.4×、4.5×改善 (比較対象: Aegaeon; 条件: RAG+reranker) — 異種LLMの負荷比を考慮することでRAG系でも改善する。

- Ayo対スループット / ビーム探索3.2×/8.2×、RAG 2.1×/2.4× (比較対象: Ayo; 条件: 4 GPU / 8 GPU) — 要求単位スケジューリングだけでなくGPU割り当て自体を到着率へ適応させる効果を示す。

### 負の結果・境界条件
- 低到着率の遅延重視領域ではAyoの要求バッチ化等が一部点でScepsyをわずかに上回る。異なるLLM同士が同時にファンアウトする場合、現在の集約パイプラインは直列段として近似するため遅延を誤モデル化する。LLMが複数役割・複数ワークフローで再利用され二峰性負荷になる場合も単一集約分布では配置が最適でなくなる。長時間ツール処理は現在無視されるため、それが支配的なワークフローでは予測誤差が増える。

### 結果の読み方
動的エージェント処理のすべての分岐を予測する必要はなく、定常状態のLLM別需要比だけでも資源配分には十分な情報を持つことを示す。これにより複雑なワークフロー解析を避けつつ、複製・テンソル並列・空間共有を同じ目的関数で選べる。
## 品質への影響
モデルやエージェントアルゴリズムを変更しないため出力品質への近似は導入しない。性能改善は資源割り当てと配置によるもので、品質は元ワークフローに依存する。
## 既存研究との差
ParrotやAyoはワークフロー構造を使って要求実行を最適化するが、専用表現や単一LLM前提があり、GPU資源割り当て自体は中心ではない。AutellixやJITServeは動的要求を予測・優先度制御するが、複数異種LLMの共同資源配分を扱わない。AlpaServe、MuxServe、Aegaeon等は複数LLMを多重化できる一方、各LLMを独立サービスとして最適化し、エージェント内依存を資源配分へ反映しない。Scepsyは低水準トレースからワークフローの相対需要を抽出し、GPU分数・テンソル並列・複製数を同時に選ぶ点が異なる。
## 限界
集約LLMパイプラインは異なるLLM間の同時ファンアウトを直列として扱うため、LLM間並列が強いワークフローでは臨界経路を正確に表せない。単一LLMが異なる役割や複数ワークフローで二峰性の負荷分布を持つ場合、一つの集約分布では最適でない割り当てを選び得る。長時間の外部ツール処理も現在のパイプラインから除外され、LLM以外が遅延支配的なら予測が外れる。配置探索時間はLLM数やGPU数とともに増え、論文の拡張性図では5 LLMで数十秒級、GPU数増加でも大きくなる。評価規模は最大16 GPUで、より大規模クラスタの探索・配置コストは未検証である。
## 実装状態
約25K行のPythonプロトタイプとして実装。Kubernetes上で変更device pluginとNVIDIA MPSを用い、任意のエージェントフレームワークとvLLM/SGLang系実行エンジンを想定する。論文記載のコードURLは匿名査読用 `https://github.com/anon/Scepsy` で、arXiv v1時点ではpost-acceptance公開予定との記載である。
## 研究上の位置づけ
エージェント推論基盤のうち、要求の時間スケジューリングではなく『どのLLMへ何割のGPU、何複製、何テンソル並列を与えるか』というクラスタ資源計画を扱う。動的制御フローを静的解析せず、定常的な相対需要へ圧縮する発想により、フレームワーク非依存性とワークフロー認識を両立する。GPU空間共有、テンソル並列、データ並列、接続構造対応配置を一つのオーケストレーション問題へ統合する研究である。
