# LLM Agents Are Latent Context Managers: Eliciting Self-Managed Context via State Proprioception

> エージェントに自分の文脈の状態を示すダッシュボードと、原文を失わない保管・復旧の道具を与える学習不要の層で、長期課題の成功率をLOCA-Benchで22.7から50.7パーセントへ引き上げた。

## 概要

表計算の記入、データベースの修正、コードの修正のように、道具を使いながら何十手順も進むエージェントでは、文脈そのものが作業記憶になる。道具の出力、古い観測、失敗した試み、利用者の制約、ファイルの場所などが積み上がり、文脈は窓の上限へ向けて膨らんでいく。溢れた分をどう扱うかが長期課題の成否を決めるが、既存の扱いには二つの型しかなかった。第1は実行系が規則で古い観測を隠したり切り捨てたりする型で、大きさや古さの統計は実行系の内部にだけあり、エージェントはどの証拠が後に要るかを知る立場にない。第2は圧縮方針を学習する型で、要約や削除で証拠そのものが失われ、学習した環境へ結び付く。どちらの型でも、エージェントはブロックの内容は読めても、その大きさ、新しさ、既に保管したかどうか、残り予算といった、保持か保管かを決めるための状態を見られていない。

本論文はこの欠落を、自分の体の状態を感じ取れない状態になぞらえて自己受容感覚（proprioception）の欠如と呼び、見方を変える。有能なモデルは、メモの取り方や資料の整理といった跡を事前学習で既に身に付けており、足りないのは方針ではなく界面である、という引き出し（elicitation）の立場である。提案するVISTA（Visible Internal State for Tool Agents）は、作業記憶を型付きで番地を持つブロックとして表し、ブロックごとのトークン使用量、新しさ、保管の段階、残り予算を示すダッシュボードを毎ターン提示し、大きなブロックを原文の完全な写しのまま外部へ保管して、必要なときに通常のファイル読みで正確に戻せるようにする。学習は不要で、基盤モデルを選ばない。論文はさらに理論として、復旧可能性と十分に情報のある状態提示の両方が必要であることを示している。

**代表結果:** 百万トークン級の軌跡を扱うLOCA-Benchで、VISTAはGemini-3-Flashの成功率を、素のReActの22.7パーセント、製品エージェントのClaude Codeの42.7パーセントに対して50.7パーセント（75課題中38課題）へ上げ、軌跡のトークン量もClaude Codeの6.72Mに対して2.86Mと少なかった。深い調査型のBrowseComp-Plusでは最強の比較対象52.0パーセントに対して58.0パーセント、短い軌跡のGAIAでは73.3パーセントとClaude Codeの73.9パーセントに並んだ。課題あたりの費用でも0.93ドルと最も安かった。

## 問題設定

資源の観点では、文脈窓は有限の作業領域であり、エージェントの判断はその配分問題である。残すべき証拠は後になってから判明することが多く、判断の時点では将来の需要が見えない。ここで不可逆な要約や削除は、将来必要になるかもしれない正確な識別子や数値を、その時点で静かに捨てることになる。逆に全部を残せば窓が溢れ、実行系による強制的な切り捨てが起きる。もう一つの問題は観測可能性である。内容の文章だけからは、ブロックのトークン数が推定できないことが論文の診断で示されている。4つの基盤モデルにダッシュボードなしで自分の文脈の総量を推定させると、相対誤差の中央値は0.43から0.84に達し、真値とほぼ無相関だった。大きさが分からなければ、大きな冗長ブロックを外して小さな決定的証拠を残すという当然の判断すらできない。つまりボトルネックは、方針の学習不足である前に、判断材料の提示不足である。本論文はこの診断を土台に、可視化、無損失の保管、通常の道具としての復旧という3点セットで応え、可視化なしでは復旧があっても無駄な保管と復旧が増えることを理論と除去実験の両方で裏付ける。

## 手法のあらまし

処理は3段のループである。第1段で、メッセージと道具の出力が到着するたびに、履歴を安定した識別子を持つブロックの列へ書き換える。各ブロックは、プロンプト内に原文で見える状態か、短い取っ手と要約だけを残して原文を外部へ保管した状態のどちらかに置かれる。第2段で、道具の結果が登録されるたびにダッシュボードを作り直し、ブロックごとのトークン見積もり、新しさ、種類、保管の段階、状態、残り予算をエージェントへ提示する。第3段で、エージェントは通常の環境道具と並んで、保管と削除の文脈道具を選べる。保管した原文の復旧は専用道具ではなく、保管先の場所を通常のファイルや端末で読むことで行う。候補の描画が予算を超える場合は、通常の道具を止めて文脈道具だけを使える超過モードへ切り替わり、エージェント自身が何を外すかを選ぶ。実行系は予算の上限だけを強制し、中身の選択はエージェントへ残す。

## 手法

### 1. 文脈ストリーム — 履歴を番地のあるブロックの作業集合へ変える

この機構が観測するのは、到着するメッセージと道具の出力である。保持する状態は二層であり、表側はプロンプト内に原文で見えるブロックと、保管先への取っ手と要約だけが見えるブロック、裏側は外部に置かれた原文の完全な写しである。行う動作は番地付けと出し入れであり、新しい観測は結果が予算内に収まる場合だけ受け入れ、収まらない大きな結果は復旧可能な仮置きへ替えるか、 短い通知とともに受け入れを拒んで、文脈を整理してから再実行できるようにする。道具の結果とそれを呼んだ側の対応は保たれ、親の呼び出し自体が保管された場合は孤立した応答にならない形で描かれる。減るボトルネックは、追記専用の履歴が無制限に伸びることと、切り捨てによる証拠の喪失であり、作業集合は予算内に収まり、しかも外した証拠は失われない。追加費用は取っ手と要約とダッシュボードが占めるトークンであり、これは第4の分析で実測されている。失敗条件は、元の道具の応答自体が途中で切れていた場合であり、保管は見たままを正確に保存するだけで、欠けた情報の再取得はエージェントの再問い合わせに委ねられる。削除は保管とは別の明示的な動作であり、選んだ内容を恒久的に消す。

### 2. ダッシュボード — 判断材料である実行状態を毎ターン提示する

この機構が観測するのは、実行系が予算判定に使うのと同じトークン見積もりと、各ブロックの登録状態である。保持する状態は持たず、道具の結果が登録されるたびに台帳を作り直して提示する。提示する内容は、ブロックの識別子、トークン見積もり、新しさ、種類、保管の段階と状態、残り予算であり、課題の隠れた証拠を足すものではなく、実行系とエージェント自身の過去の動作が生んだ状態だけである。行う動作は可視化そのものであり、これによってエージェントは「どのブロックが大きくて古く、どれが小さくて決定的か」を見て保管対象を選べる。減るボトルネックは判断材料の欠如であり、診断ではダッシュボードを与えることで総量推定の誤差が全モデルで0になり、ブロック単位の誤差も0から0.02へ下がった。追加費用はダッシュボード自体のトークンで、測定では登録ブロック数が約62の付近で約340トークンを頂点として、その後は軌跡が伸びても増えず、可視の作業集合の伸びも直線より緩やかだった。失敗条件は、モデルが台帳を読み違えたり、後で要る証拠を保管したりする場合であり、可視化は正しい判断を保証しない。能力の低いモデルでは引き出せる力自体が小さいことも限界として述べられている。

### 3. 保管と復旧の道具 — 原文を失わずに作業集合から外す

この機構が観測するのは、エージェントが選んだブロックの集合と、付け替え用の短い要約である。保持する状態は、外部の保管場所にある原文の写しと、表側に残る場所・段階・大きさ・照合情報を含む取っ手である。行う動作は保管と復旧であり、保管は選んだブロック群を外部へ移して取っ手へ置き換え、復旧は取っ手を頼りに通常のファイル読みで原文を正確に戻す。範囲を指定して一部だけ戻すこともでき、大きな写しを全部読み直さずに済む。保管は階層的であり、複数のブロックを束ねた保管を、圧迫が強まればさらに大きな束として保管し直せる。要約は案内の役割に留まり、証拠の唯一の表現にはならない点が、要約型の圧縮との決定的な違いである。減るボトルネックは不可逆性であり、後の需要が判明したときに証拠を正確に戻せるため、外す判断の危険 が下がる。追加費用は復旧の読み込みトークンと、保管と復旧の手順数である。失敗条件は復旧の遅れと過剰な出し入れであり、理論の節では、状態情報が乏しい管理者は要らないブロックまで保管して復旧義務を増やすことが示され、実測でもダッシュボードなしの変種は保管255回に対して復旧57回と、選別のない出し入れに陥った。完全な形では保管69回、復旧105回と対照的である。

### 4. 超過モードと予算の強制 — 溢れたときは中身の選択をエージェントへ残す

この機構が観測するのは、候補の描画の大きさと予算の残りである。保持する状態は現在の作業空間の写しであり、描画が予算を超えると、通常の環境道具と回答を無効化し、文脈道具だけを使える状態へ切り替える。行う動作は強制と委任の分離であり、上限の遵守は実行系が保証するが、どのブロックを外すかはダッシュボードを見たエージェントが決める。新しい道具結果がどうしても収まらない場合は、黙って切り捨てず、受け入れを拒んで通知する。減るボトルネックは、実行系の規則による一律の切り捨てであり、証拠の価値を知る側が選択できる。追加費用は、超過の間は課題の進行が止まることである。失敗条件は、エージェントが整理に失敗して超過から抜けられない場合であり、その場合は課題自体が進まない。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 文脈ストリーム | メッセージと道具の出力 | 番地のあるブロック化し、見える状態と保管状態へ振り分ける | 履歴の無制限な伸長と証拠喪失 | 取っ手と要約のトークンが増える |
| ダッシュボード | 実行系のトークン見積もりと登録状態 | 毎ターン台帳を作り直して提示する | 判断材料の欠如 | モデルが読み違えれば効果が出ない |
| 保管と復旧 | 選択したブロックと要約 | 原文を外部へ移し、通常の読みで正確に戻す | 不可逆な圧縮の危険 | 復旧の読み込みと手順数が増える |
| 超過モード | 描画の大きさと残り予算 | 通常道具を止め文脈道具だけを許可する | 規則による一律の切り捨て | 整理の間は課題が止まる |

なお論文には、同じ界面の上で強化学習により保管と復旧の使い方を適応させる枝も用意されている。作業空間と台帳と無損失の契約は変えず、軌跡単位の報酬に、文脈圧迫への罰則、無効な文脈道具への罰則、無意味な保管と復旧の往復への罰則だけを加えて方針を磨く。報酬に保管回数や削減量そのものは入れず、過剰な保管で稼ぐ抜け道を塞いでいる。

## 評価

結論は三点である。第1に、完全なVISTAは3つの規模の異なるベンチマークで、欠けた要素を持つ方式群を一貫して上回るか並び、特に長い軌跡で差が開く。第2に、除去実験で、ダッシュボード、保管、復旧、エージェントによる選択のどれを外しても成績が落ち、文言の変種では落ちないことから、効果は界面の能力そのものに由来する。第3に、同じ未学習の層が4つの基盤モデルすべてで改善し、オフラインの軌跡記憶の課題へも転移する。評価は実測のエージェント実行であり、ベンチマークごとに採点規則を固定して比較している。

### 感度・スケーリング・ストレス条件

文脈の伸びに対する圧力走査では、圧迫が強いほど利得が大きい。BrowseComp-Plusの窓の走査では、小さすぎる窓ではダッシュボードの費用が重く、大きすぎる窓では素の方式でも証拠が残るため、利得は中間の窓で最大になった。難しい課題ほど文脈道具の使用が増えることも学習版の分析で示され、易しい課題へ一律に管理をかける方式ではないことが分かる。

## 既存研究との差

文脈をエージェントのために管理する系譜は、古い観測の隠蔽、ページング、決定的な切り捨てなど、実行系が代わりに決める方式であり、状態の統計は実行系の内部に閉じていた。長期記憶の系譜は保存と検索の基盤を提供するが、現在のプロンプト内のブロックの地図をエージェントへは渡さない。エージェント自身が管理する系譜は、圧縮や折り畳みの道具を学習方針とともに提供するが、対象は要約や節目といった粗い単位であり、どのブロックが大きいかという状態は示されず、表現は不可逆だった。本論文は、問題を方針ではなく観測可能性として切り分け、ブロック単位の状態提示と無損失の保管・復旧を一つの界面にまとめた点が異なる。学習による文脈管理とは対立せず、同じ界面の上で方針を学習する枝も示している。

## 限界・実装状況

論文自身が挙げる限界は複数ある。第1に、ダッシュボードは正しい利用を保証せず、モデルが読み違えたり、後で要る証拠を保管したり、復旧が遅れたりする失敗は残る。第2に、潜在的な文脈管理の力が小さいモデルでは引き出せるものが少なく、評価した4基盤でもGLM-5とDeepSeek-V4-Proの利得が最も小さかった。第3に、敵対的入力や汚染された証拠、生成型の誘発条件は未検証である。第4に、多くの結果は課題ごとに1本の軌跡に基づいており、繰り返し測定によるばらつきの評価は今後の課題である。実装状況としては、学習不要の層として記述され、強化学習の適応手順も示されているが、公式実装の公開先は論文中に示されていない。本まとめはarXiv第5版（2026-07-31）に基づく。

## 一般的な実装上の含意

推論基盤とエージェント実行系に共通する含意は、文脈の状態をモデルの推測に任せず、実行系が持つ正確な台帳をそのまま見せるべきだという点である。トークン数、残り予算、キャッシュや保管の状態は、実行系にとっては既知の事実であり、提示の費用も軌跡の長さに対して控えめに抑えられる。また、文脈を外す操作は不可逆な要約ではなく、原文を正確に戻せる保管として設計すると、判断の誤りの被害が大幅に下がる。スケジューラや文脈予算の運用でも、固定規則で一律に切り捨てるより、上限の強制だけを実行系が担い、中身の選択を文脈の意味を知る側へ委ねる分担が有効である。さらに、文脈の編集は前方キャッシュの再利用を壊して費用を押し上げ得るため、トークン総量だけでなくキャッシュ込みの費用で評価すべきである。
