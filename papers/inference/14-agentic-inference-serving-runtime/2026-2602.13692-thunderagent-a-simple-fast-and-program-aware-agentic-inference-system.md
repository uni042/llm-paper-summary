# ThunderAgent: A Simple, Fast and Program-Aware Agentic Inference System

> エージェントの推論・ツール実行を独立要求ではなく永続プログラムとして追跡し、KVキャッシュの一時停止・復帰、GPU間移動、ツール環境の先行準備と回収を協調させ、配信スループットを最大3.58倍改善する。

## 概要

エージェント型大規模言語モデルは、モデル推論だけを連続実行するのではなく、推論と外部ツール実行を何度も往復する。従来の推論エンジンは各モデル呼出しを独立要求として扱い、ツール基盤もコンテナやAPI環境を別に管理する。この分離により、ツール待ち中のKVキャッシュがメモリ圧迫時に追い出され、ツール終了後に長い会話履歴を再プリフィルする、GPUノード間でKV容量が偏る、終了済みツール環境がディスクやポートを占有し続けるという三つの無駄が生じる。

ThunderAgentは、複数ターンの推論とツール呼出しを一つの「エージェントプログラム」として追跡する。プログラム識別子、文脈長、必要ツール、配置ノード、推論中かツール実行中かという段階、実行・一時停止・終了状態を共通メタデータにする。スケジューラはこの情報から、どのKVを保持し、どのプログラムを一時停止し、どのGPUへ復帰させるかを決める。ツール管理器も同じ寿命情報を使い、環境を推論と重ねて準備し、終了時に確実に回収する。

GLM-4.6 355BやQwen3 235Bを8×H100上で動かすコーディングエージェントなどの実機評価では、vLLMに対する配信スループットが1.48〜3.58倍、Continuumに対して1.17〜3.31倍となった。分散強化学習（Reinforcement Learning; RL）のロールアウトでは1.79〜3.92倍を報告する。予測しやすいツール時間の負荷ではKVヒット率をほぼ100%へ保ち、ツール資源の寿命管理ではディスク使用量を最大4.2倍削減する。単一要求のトークン生成を高速化するのではなく、長寿命ワークフロー全体の状態管理で持続スループットを上げる研究である。

## 問題設定

エージェントの履歴はターンごとに前の履歴を接頭辞として伸びるため、本来は前ターンのKVをほぼ完全に再利用できる。しかし要求単位の推論基盤は、ツール呼出し中のプログラムを「現在推論していない要求」としか見ない。高並行度でメモリが足りなくなると、そのKVを他要求のために追い出し、ツール完了後に履歴全体を再計算する。論文の測定ではこのスラッシングによりエンドツーエンド遅延が非スラッシング時の最大7.14倍になった。

複数GPUノードでも、KV局所性だけを優先して同じワークフローを同じノードへ固定すると、長さと寿命が不均一なエージェント間でメモリ使用量が偏る。OpenHandsのロールアウトを2台の8×H100ノードで90分観測した例では、ノード間メモリ差が37分以上20%を超え、最大51%に達した。空きノードがあっても、KV局所性を守るため混雑ノードへ要求が集中する。

さらにツール環境はGPU外の状態を持つ。コーディングエージェントならDockerイメージ、依存パッケージ、リポジトリ、ネットワークポートなどが必要で、準備には長い入出力時間がかかる。推論基盤がツール寿命を知らなければ、必要になってから環境を作るため待ち時間が増え、終了した環境をいつ消すべきかも分からない。ThunderAgentはGPUのKVと外部ツール状態を同じプログラム寿命へ結び付けることを問題の中心に置く。

## 手法

ThunderAgentは既存のvLLM等を置き換える新しいモデル実行器ではなく、その上にプログラム単位の制御層を置く。各ワークフローを、識別子、現在文脈長、ツール集合、配置先、実行段階、状態の組として保持する。推論中は「Reasoning」、外部ツールを待つ間は「Acting」と区別し、実行中、一時停止、終了を追跡する。既存推論エンジンとはOpenAI互換の要求境界で接続できるため、モデルカーネルを大きく変更しない。

### 1. プログラム単位の費用モデル

スケジューラはメモリ量だけでなく、そのメモリが何秒占有されるかを含む空間時間積（Space-Time Product; STP）で無駄を整理する。総費用を、実際に役立つデコードと新規プリフィル、追い出した履歴を戻す再計算、ノード偏りで使えない空き容量、ツール待ち中にKVを保持する遊休キャッシュへ分解する。最適化対象は後ろ三つの非生産的費用である。

この分解により「ツール待ちKVは常に保持すべき」という単純方針を避ける。短いツール呼出しなら保持して再計算を避ける方がよいが、長時間戻らないならGPUを占有し続ける方が損になる。ThunderAgentはプログラムの段階と経過時間を見て、保持費用と再計算費用のどちらが大きいかを近似する。

### 2. 周期的スラッシング検出と一時停止・復帰

各GPUバックエンドのKV容量に対し、実行中プログラムの文脈長合計を周期的に確認する。文脈はデコード中にも伸びるため、新規要求到着時だけではなく一定間隔で再評価する。容量を超えそうなら、一部プログラムを一時停止してKVを解放する。逆に空きができれば待ち行列からプログラムを復帰させる。高水位と低水位を用いたヒステリシスで、停止と復帰が細かく振動するのを防ぐ。

ツール実行中のプログラムには時間減衰を掛ける。ツール待ちが長くなるほど、そのKVを「今すぐ守るべき容量」として数える重みを小さくし、メモリ圧迫時に追い出しやすくする。論文はツール時間が無記憶性を持つ場合、指数減衰が整合的であることを示す。予測が外れてすぐツールが戻れば再プリフィル費用が発生するが、固定の有効期限を当てる方式より、経過時間と実メモリ圧力の双方を使って判断できる。

### 3. 最短文脈優先の追い出しと大域待ち行列

追い出す対象は文脈長が短いプログラムを優先する。再プリフィルでは履歴が伸びるほど注意計算と保持時間が増え、空間時間積としての再計算費用が文脈長の二乗に比例するというモデルを使う。必要な容量を空けるとき、短い文脈を先に一時停止すれば、同じ解放量に対する将来の再計算損失を抑えられる。

一時停止したプログラムは元ノードへ固定せず、全データ並列バックエンドが共有する大域待ち行列へ戻す。復帰時には空き容量のあるノードを選べるため、KV局所性を絶対視して一部ノードだけが満杯になる状態を避ける。移動時はKVをそのまま転送するのではなく、必要なら再プリフィルで復元するため、局所性損失とノード平準化の交換になる。長文脈ほど再計算が高価なので、追い出し選択と組み合わせて損失を抑える。

### 4. ツール環境の先行準備と寿命回収

プログラム状態には必要なツール環境の集合も含まれる。ThunderAgentは待ち行列とプログラム進行を見て、将来必要になるDocker環境等をモデル推論と非同期に準備する。従来はモデルがツール呼出しを決めてから環境作成を始めるため、その入出力待ちがそのままエンドツーエンド遅延になる。先行準備では環境作成時間をGPU推論と重ね、見える待ち時間を減らす。

終了時にはプログラムの終了フックをツール管理へ伝え、参照されなくなったサンドボックス、ディスク、ポートを回収する。これにより長時間運用で資源が累積するのを防ぐ。予測したツールを使わなければ準備費用が無駄になる可能性はあるが、プログラム寿命に基づく回収でリークを残さない。GPU側のKV管理とツール側の環境管理を同じ識別子で結ぶことが、要求単位システムとの本質的な差である。

### 5. 一つのエージェントが進む流れ

新しいエージェントを受けるとプログラム識別子を作り、推論要求をReasoning状態としてGPUへ配置する。モデルがツール呼出しを出すとActingへ遷移し、KVはすぐ捨てず再利用候補として残す。同時に必要なツール環境を準備・実行する。周期監視でGPUが逼迫した場合、ツール待ち時間と文脈長を考慮して一時停止対象を選び、KVを解放する。

ツールが戻ると、KVが残っていればそのまま次ターンを増分プリフィルし、追い出されていれば履歴を再プリフィルして復元する。元ノードが混雑していれば別ノードへ復帰できる。これを終了まで繰り返し、最後にツール環境を回収する。したがって失敗時の挙動は「状態を失う」のではなく、KV局所性を失った場合に再計算へ戻る設計であり、性能劣化として吸収される。

## 評価

配信評価ではOpenHandsとmini-SWEAgentをSWE-Bench Liteへ、ToolOrchestraをHLEへ、OpenHandsをScienceAgentBenchへ適用する。大規模モデルはGLM-4.6 355BとQwen3 235BをFP8・テンソル並列8で8×H100ノードに配置し、ToolOrchestraではQwen3-8B FP16をRTX 5090で動かす。推論GPUクラスタとDocker用CPUクラスタは分離する。比較対象は要求単位のvLLMと、ツール時間を予測してKVをHBMへ固定するContinuumである。

高並行度、例えば96並列プログラムでは、ThunderAgentはvLLMに対して1.48〜3.58倍、Continuumに対して1.17〜3.31倍のスループットを得る。予測可能なツール時間の負荷ではKVヒット率がほぼ100%に保たれる一方、Continuumはメモリ不足で固定KVも追い出され、90%以上から約60%へ低下する。ThunderAgentは並行数がGPU容量を超えても実行数を制御するため、比較対象のような急激なスループット崩壊を避ける。

RLロールアウトは同じモデル・ワークフローを2台の8×H100ノードで評価し、vLLMとSGLang Gatewayを組み合わせた分散基準に対して1.79〜3.92倍の改善を示す。ロールアウトはRL全体の壁時計時間の70%以上を占め得るため、ここでの持続スループット改善はデータ生成の陳腐化を減らす意味もある。追加評価では最大64 H100までワーカー複製数に対してほぼ線形に伸び、KVオフロードとの併用も検証している。

ツール側ではOpenHandsのように1サンドボックス10GB超を使う負荷で、終了フックによる回収がディスク累積を防ぐ。論文は最大4.2倍のディスク使用量削減を報告する。これはGPUカーネル高速化ではなく、不要になった環境を確実に破棄する運用上の容量削減である。したがってGPUスループット倍率と同じ種類の数値として混同すべきではない。

## 既存研究との差

vLLMやSGLangは高性能なモデル推論エンジンだが、基本のスケジューリング単位は要求である。Autellixはエージェントをプログラムとして扱うがGPU実行時間を中心に管理し、ThunderAgentが重視するツール段階とKV寿命、外部環境の寿命を同じ制御面で扱わない。Continuumはツール時間を予測した有効期限でKVを固定するが、予測不能なツール時間やGPU容量超過時には固定が崩れ、スラッシングが残る。

ThunderAgentは、ツール待ちを単なるアイドルではなく将来KVを再利用するプログラム段階として明示し、時間減衰と実メモリ圧力で保持価値を変える。また、元ノードへの固定を外して大域待ち行列から再配置するため、KV局所性とノード平準化を同時に扱う。さらにDocker等の寿命までプログラム識別子へ結び付ける点が、GPUだけを最適化する既存エージェント配信方式との差である。

## 限界・実装状況

利得は、長い履歴を再利用し、推論とツール呼出しを反復するワークロードで大きい。単発チャットやツールを使わない要求ではプログラム単位管理の余地が小さい。また、ツール時間が長く不規則な場合はKVを保持するか追い出すかの交換が避けられず、時間減衰の設定によって再計算量が変わる。大域移動も、KV局所性を捨てて再プリフィルする場合があるため無料ではない。

実装は公開され、既存推論エンジンとOpenAI互換境界で統合する。論文はSkyRLやNVIDIA Dynamoへの採用も報告する。ただし評価の中心は特定のコーディング・ルーティング・科学エージェントとGPU構成であり、人間待ちが支配する対話や別種の長時間外部処理では、スループット改善の割合が異なる可能性がある。
