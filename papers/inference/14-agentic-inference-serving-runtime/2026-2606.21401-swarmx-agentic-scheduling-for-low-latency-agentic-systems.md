# SwarmX：エージェントの呼び出し構造を予測する分布認識スケジューリング

## 概要

エージェント型のLLMアプリケーションでは、一つの要求が単一モデルの生成で終わらず、計画、検索、コード編集、テスト、要約、外部ツール実行などを繰り返す。各段階で呼び出すモデルが異なり、次に何を実行するかも前段の出力によって決まる。そのため、要求を受けた時点では必要なGPU時間、CPU時間、後続モデルのレプリカ数が確定していない。単純なラウンドロビンや平均実行時間に基づく割当では、長い要求が特定のキューに集中し、遅延の裾が悪化しやすい。

SwarmXは、プロンプトの意味、対象モデル、装置、実行時状態を組み合わせ、要求の推論時間と後続モデル呼び出し数の確率分布を予測するスケジューラである。要求をどのレプリカへ送るかを決めるルータと、どのモデルのレプリカを何個用意するかを決めるスケーラが、同じ予測基盤を利用する。平均値だけでなく分位点を保持することで、P95やP99のような遅い要求を重視した判断を行う。

128基のH20 GPUを用いた試験環境では、Deep Researchの全体P95遅延をRay比61.5%削減した。実運用ではP99遅延を44〜52%削減し、同じサービス水準を満たす最大スループットを約2倍にした条件も報告する。ただし結果は著者らのクラスタと実運用トレースに依存し、独立した公開クラスタでの再現性や、予測器を別のモデル系列へ移す費用には留保がある。

## 問題設定：推論時間と呼び出し構造がプロンプトで変わる

通常のLLMサービングでも入力長、出力長、バッチサイズ、KVキャッシュ容量によって実行時間が変わる。エージェント型ではこれに加えて、どのツールを呼ぶか、次にどのモデルへ処理を渡すか、何回やり直すかがプロンプトの意味に依存する。著者の観測では、意味が似た要求でも生成トークン数が194、886、1569と大きく異なる例がある。最初のモデル呼び出しの長さだけでなく、後続の呼び出しグラフも変化する。

ルータは各レプリカのキューがいつ空くかを予測して要求を配置する必要がある。スケーラは、まだ実行されていない後続モデルの需要を予測してレプリカを準備しなければならない。平均実行時間だけで判断すると、短い要求が多いキューと少数の長い要求が残るキューを区別できない。さらに、単一の長い要求が処理を占有すると、低QPSでも待ち時間の裾が悪化する。

既存のRayやKubernetesの単純な割当、平均時間に基づくMurakkab、単一エージェント中心の方式では、プロンプト意味に依存する二種類の変動を同時に扱いにくい。SwarmXは、各モデル呼び出しを独立に最適化するだけでなく、アプリケーション全体の遅延を見てルータとスケーラを協調させる。

## 手法

### 小型意味モデルと軽量予測器

SwarmXは要求の意味を理解するために、対象モデルと似た構造を持つ小型の言語モデルを使う。対象モデルをそのまま実行して予測すると費用が大きいため、層数や幅を縮めた同型の小型モデルから意味特徴を抽出する。これに装置の種類、演算能力、稼働率、同時実行数、実行エンジンの設定、対象モデルの構成などを加え、軽量な多層パーセプトロンで予測する。

ルータ向けには、要求が特定のレプリカで何秒かかるかの分布を出す。スケーラ向けには、後続でどのモデルが何回呼ばれるかの分布を出す。著者は対象のQwen3-8Bに対して約3500万パラメータの意味モデルを選び、モデルの規模を増やしても予測誤差があまり改善しない領域で費用と精度の折衷を取る。装置や実行時状態は小型MLPで処理するため、予測の費用を推論本体より十分小さくできる。

予測器は運用トレースから学習する。意味モデルは出力長や応答構造を予測し、ルータ用MLPは遅延分位点を、スケーラ用MLPは後続呼び出し数の分位点を学習する。分位点回帰にはピンボール損失を用い、平均だけでなく遅い要求の分布を保つ。単に予測モデルを導入するのではなく、予測対象をルータとスケーラの判断に合わせて分ける点が重要である。

### 分布を保持したルーティング

ルータは各レプリカのキューに対して、すでに割り当てた仕事の終了時間分布を分位点スケッチとして保持する。新しい要求が来ると、その要求を各候補レプリカへ割り当てた場合の遅延分布を予測し、候補キューの分布へ合成する。全キューの状態から遅延の裾に関する費用を評価し、良い候補へ要求を送る。

平均値だけを足すと、実行時間が極端に長い要求の影響を見落とす。SwarmXは分布の形を保持したまま候補を評価し、P99の悪化を避けるように選択する。スケーラも同じ考え方で、将来の呼び出し数の分布を使ってモデル別レプリカ数を決める。レプリカ数の小さな変化で頻繁に再配置しないよう、変更の閾値も設ける。

この方式では予測誤差がそのままスケジューリング判断に影響するため、予測器の監視が必要になる。SwarmXは実際の遅延と予測分位点のずれを監視し、一定期間の誤差が閾値を越えたときに軽量MLPを再学習する。対象モデルそのものが変わった場合は意味モデルの更新も必要になる。予測器が利用できない場合は既存のスケジューラへフォールバックし、予測基盤が単一障害点にならないようにする。

### 既存基盤との統合

SwarmXは既存のクラスタ管理基盤を全面的に置き換えるのではなく、Rayなどのスケジューラにプラグインとして組み込む。ルータとスケーラを軽量なスケジューラエージェントとして扱い、観測できる状態、予測器、実行可能な配置操作を共通の枠組みで管理する。これにより、推論モデル、動画生成モデル、CPU上のツール呼び出しなどを一つのアプリケーション内で協調制御できる。

## 評価設定と実測結果

| 項目 | 原著の条件 |
|---|---|
| 制御された試験環境 | NVIDIA H20を128基、vLLM 0.16.0、Rayプラグイン |
| 実運用GPU | H20を320基、L20を560基の異種クラスタ |
| 実運用CPU | 百万コア以上のCPUクラスタを含む |
| ワークロード | Deep Research、Text-to-Video、OpenClaw、Coding Agent、Video OCRなど |
| 比較 | Ray、Murakkab、Power-of-Two Choices、既存本番スケジューラ |
| 指標 | P50、P95、P99の全体遅延、SLO内の最大スループット |

### ルータとスケーラの単独評価

ルータだけを変更し、レプリカ数を固定した場合、Text-to-VideoのP95遅延はRay比18.0%削減、Deep Researchでは28.3%削減となる。Deep Researchではプロンプトによって推論時間が大きく変わるため、意味を考慮した予測の効果が大きい。スケーラだけを変更した場合も、Text-to-Videoで7.8〜13.7%、Deep Researchで約50%の遅延削減が報告される。

### 全体遅延と実運用

| 条件 | 主な結果 |
|---|---|
| Text-to-Video、Ray比 | P50を32.1%、P95を34.9%削減 |
| Deep Research、Ray比 | P50を53.7%、P95を61.5%削減 |
| OpenClaw、二モデル構成、Ray比 | P95を32.4%削減 |
| Coding Agent、二モデル構成、Ray比 | P95を14.9%削減 |
| Video OCR、本番CPUサービス | P50を59.6%、P99を48.38%削減 |
| 異種GPU上の意味解析 | 同じSLOで最大約2倍のスループット |
| Video Transcode、本番CPUサービス | P99を44〜52%削減 |

原著§5.3〜5.4。ルータとスケーラを同時に使うと、Deep ResearchのP95遅延を61.5%削減する。ただしオープンエンドなCoding Agentでは改善が比較的小さく、単一モデル構成のP95ではMurakkabとほぼ同等になる条件もある。最大値だけを一般化すると、ワークロードごとの違いを見落とす。

### 予測費用

Wan2.1-T2V-1.3B向けの予測器は約6.6万パラメータ、261KB、予測時間1ミリ秒未満。Qwen3-8B向けは約3500万パラメータ、約100MB、CPUで約30ミリ秒、GPUで約4ミリ秒と報告する。対象モデルの実行時間は秒から分単位であるため、これらの条件では予測費用は比較的小さい。ただし短い生成要求や非常に高いQPSでは、予測の費用とキュー更新の費用が無視できるとは限らない。

## 負の結果と限界

本研究の大規模な実運用結果は著者らの内部サービスに基づく。モデルの配置、運用トレース、既存スケジューラの設定が公開の再現実験と完全に一致するとは限らず、別組織のクラスタで同じP99改善率を得られる保証はない。また、予測器の訓練には過去の要求ログが必要で、モデル変更や新しいワークロードへの移行時には予測精度の低下を監視し、再学習する必要がある。

著者は短い推論要求ではなく、秒から分単位のエージェント処理を主な対象とする。単一モデルで短い応答を大量に返すサービスでは、意味モデルによる予測費用が相対的に大きくなり、単純な負荷分散が十分に有効な場合もある。さらに、予測が不正確な場合に最悪遅延が必ず改善するという理論保証はない。分布認識の利点は、予測分布が実際の要求の変動をある程度捉えていることに依存する。

また、スケジューラが改善するのは要求の配置と資源割当であり、LLM内部の演算や注意カーネルそのものを高速化するわけではない。実運用ではGPUを増減する費用、モデルの起動時間、CPUツールの待ち時間などを含めたアプリケーション全体の評価が必要である。高いスループットと低いP99遅延を同時に達成するには、サービス水準と負荷条件を揃えて比較しなければならない。

## 既存研究との差と適用先

従来のLLMサービング最適化は、一つのモデルのバッチ処理、KVキャッシュ、プリフィルとデコードの分離などに注目することが多い。SwarmXはそれらを置き換えるのではなく、複数のモデルとツールをまたぐ要求全体の遅延を対象とする。プロンプト意味に依存する実行時間と、次に呼ぶモデルの分布を予測し、ルータとスケーラを同時に動かす点が特徴である。

複数モデルを使うコードエージェント、調査エージェント、動画生成パイプラインのように、要求ごとに呼び出し構造が変わる用途では有用である。一方、モデル呼び出しの構造が固定で短い要求が多い用途では、予測器の追加費用を正当化できるか検証が必要である。採用時には、予測器を含めた総費用、実際のP95/P99、SLO達成率、モデル切替時の適応時間を同じ条件で比較する。
