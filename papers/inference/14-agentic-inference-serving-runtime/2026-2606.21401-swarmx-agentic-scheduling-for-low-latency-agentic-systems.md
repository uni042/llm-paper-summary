# SwarmX：推論時間の分布予測とモデル呼出し需要予測を結合したエージェント・スケジューリング

## 概要

複数のLLMや画像生成モデル、ツール実行を連結するエージェント処理では、同じモデルへの要求でもプロンプト内容によって生成長、思考量、後続モデル呼出し数が大きく変わる。従来のクラスタ管理では、GPUの現在負荷や平均処理時間から次の要求を割り当て、一定の利用率や待ち行列長に応じてレプリカを増減することが多い。しかし平均時間が同じでも「短い要求が多数」と「極端に長い要求が少数」では待ち行列の上位分位点が異なる。モデル呼出しが連鎖するワークフローでは、一段の待ち時間の見誤りが下流の処理を遅らせる。

SwarmXは、入力プロンプトの意味、対象モデル、GPU・CPUの種類と状態、推論ランタイムの設定を入力として、要求時間と将来のモデル呼出し需要を**一点推定ではなく分布**として予測する。ルータは各候補待ち行列へ新しい要求を置いた場合のtail遅延を比較し、スケーラは後続呼出しの予測分布をもとにモデル別のレプリカ数を調整する。両者は独立に動作するが、レプリカ増減を通知して候補集合を更新するため、リクエスト単位の割当と時間窓単位の容量計画が整合する。

128基のNVIDIA H20を使うテストベッドでは、Deep ResearchのエンドツーエンドP95遅延をRay Core比61.5%削減した。Text-to-Videoでは同34.9%削減。これらは**P95の相対削減率**であり、モデルの生成トークン速度が61.5%上昇したという意味ではない。本番環境でも動画変換サービスのP99遅延44〜52%削減を報告するが、社内運用トレースと専用の配備構成に基づく結果であり、公開コードによる第三者再現とは区別する。

## 問題設定と既存方式との差

### なぜ平均処理時間では足りないか

LLMの要求遅延は、入力長だけでなく出力長、モデルの推論経路、混雑、バッチ編成に依存する。論文のFigure 2では意味の近い三つのプロンプトでも出力トークン数が194、886、1569と大きく異なる例を示す。固定長の画像処理と異なり、Deep Researchのようなワークフローは検索や再計画の回数もプロンプトごとに変わる。ルータが平均値だけを見れば、長い処理が積み重なる待ち行列へさらに要求を送り、P95/P99を悪化させる。

Murakkabのようなエージェント向け既存スケジューラは複数モデルを考慮するが、予測を平均的な代表値へ集約する。Ray Coreのround-robinは処理時間分布を明示的に使わない。Power-of-Two Choicesは候補二つの負荷を比べるが、プロンプトの意味や将来の呼出し構造を十分には表さない。SwarmXの新規性は、単に学習器をスケジューラへ追加する点ではなく、**分布を保持したまま待ち行列へ合成し、その分布を評価関数へ渡す**点と、同じ予測基盤をルータとスケーラの両方に使う点にある。

### 目的関数と制御の粒度

ルータは新規要求の割当先を決めるため、各キューの完了時刻分布を比較する。スケーラは時間窓におけるモデル別の到着需要とレプリカ能力を比較し、過剰配備とSLO違反の両方を避ける。前者は要求ごと、後者は時間窓ごとの判断であり、最適化する量も異なる。両者を一つの中央最適化器で毎要求ごとに解くと制御通信と計算が律速になり得るため、SwarmXは小さな状態変化通知を介した分散協調を採用する。

## 手法

### 1. 意味モデルとMLPを分離した予測器

予測器は二段階からなる。まず対象LLMに構造を近づけた小型の意味モデルがプロンプトから特徴量を抽出する。次に多層パーセプトロン（MLP）が意味特徴と対象モデル情報、GPU/CPUの種類・演算能力、実行時の利用率・同時要求数・最大バッチサイズなどを結合し、推論時間または将来需要の分位点を出力する。対象モデルそのものを毎回もう一度実行して予測する方式ではないため、長い生成要求に対して予測費用を小さく抑えられる。

ルータ用の予測器は「この要求をこの実行環境へ置くと何秒かかるか」を見積もる。スケーラ用の予測器は「このプロンプトからどのモデル呼出しが何件発生し、いつ負荷が増えるか」を推定する。後者は上流ルータが抽出した意味表現を再利用し、重い意味モデルをスケーラ側で繰り返し動かさず、軽量MLPだけで更新する。これによりモデルごとのレプリカ需要を先読みする一方、スケーラの制御ループが予測器のGPU時間を過度に消費しないようにする。

### 2. 分位点スケッチを使った候補評価

分布全体の確率密度を保持すると状態量が大きくなるため、SwarmXは複数の分位点からなる小型スケッチを使う。分位点は「要求の何%がこの時間以内に終わるか」を表し、P95は95%の要求が下回る時間である。平均値だけでは見えない長い尾を保持できる。Algorithm 1では各候補キューに対して新要求の時間分布を予測し、その候補キューの既存スケッチと合成した状態を作る。さらに全キューを含む状態のtailコストを計算し、最も低い候補へ要求を送る。

重要なのは「新要求の予測時間が最短のGPUを選ぶ」だけではないことである。既存キューに長時間要求が残っていれば、新要求自身が短くても待ち時間は長い。逆にGPUが一時的に忙しくても、既存要求の残り時間が短ければ早く処理できる場合がある。SwarmXは候補行動が**全体のtail分布へ与える増分**を評価する。スケーラも同じ考え方を需要スケッチへ適用し、レプリカ追加・削除の候補を比較する。論文は分布合成を用いるが、すべての将来呼出しを完全に知るわけではなく、予測誤差と負荷変動を伴う。

### 3. ルータとスケーラの協調、制御境界

スケーラがレプリカを増減したら、そのモデルを扱うルータへ新しい候補レプリカ集合を通知する。ルータは最新のキューと利用可能レプリカを用いて次の要求を割り当てる。制御面は、状態参照とDispatch・Deploy・Drainのような限定された操作を公開し、予測器が任意のクラスタ操作を実行しないようにする。既存Ray等のクラスタ管理を置き換えるのではなく、プラグインとして配備可能な構成にする。

学習データは実際のアプリケーション実行ログから作る。各記録にプロンプト文脈、対象モデル、ハードウェア・ランタイム状態、スケジューリング行動、実測結果を含め、予測器を学習する。Algorithm 2は観測遅延と予測分位点の差に基づくpinball lossをスライディング窓へ蓄積し、誤差が閾値を超えた場合にMLPを非同期再学習する。通常は意味モデルを固定し、環境・負荷の変化を小型MLPで追う。予測器が使えないときは元のスケジューラへフォールバックするが、その間の最適化利得は保証されない。

## 評価

### 環境・比較・指標

| 項目 | 一次論文での条件 |
|---|---|
| テストベッド | NVIDIA H20 GPU 128基、Ray上のスケジューラプラグイン |
| 本番GPU群 | H20 320基とL20 560基の異種GPU群 |
| 本番CPU群 | 動画OCR・変換などを含む100万コア超の規模 |
| 推論ランタイム | vLLM 0.16.0を使用したモデルサービング |
| Deep Research | DR Bench 20,000サンプル、計画/要約Qwen3-32B、検索Qwen3-8B系 |
| Text-to-Video | OpenVid-1Mから2,000サンプル、Qwen3-8BとWan2.1-T2V-1.3B |
| OpenClaw / Coding Agent | MCP Atlas、SWE-bench Pro由来のエージェント・トレース |
| 本番トレース | 約1,100万件の実運用記録 |
| 比較対象 | Ray Core、Murakkab、Power-of-Two、Random、静的レプリカ、既存本番スケジューラ |
| 指標 | 完全ワークフローのP50/P95、実運用P99、同一SLO下の持続処理量、予測費用 |

P50は中央値、P95/P99は上位5%/1%の遅い要求が始まる境界を表す。平均値が改善してもP99が悪化すればSLO違反が増えるため、これらを区別して記録する。比較は実機のスケジューラ性能であり、LLM単体の演算カーネルの性能ではない。

### 実測結果と構成要素除去

| 対象・条件 | 比較 | 指標 | SwarmXの結果 |
|---|---|---|---|
| Text-to-Video、ルータのみ | Ray Core | P50 / P95 | 11.0% / 18.0%削減 |
| Deep Research、ルータのみ | Ray Core | P50 / P95 | 29.0% / 28.3%削減 |
| Text-to-Video、スケーラのみ | 静的レプリカ数 | 遅延 | 7.8〜13.7%削減 |
| Deep Research、スケーラのみ | 静的レプリカ数 | 遅延分位点 | 約50%削減 |
| Text-to-Video、統合 | Ray Core | P50 / P95 | 32.1% / 34.9%削減 |
| Deep Research、統合 | Ray Core | P50 / P95 | 53.7% / 61.5%削減 |
| Text-to-Video、統合vsルータのみ | SwarmX Static | P95 | さらに20.7%削減 |
| Deep Research、統合vsルータのみ | SwarmX Static | P95 | さらに43.8%削減 |
| OpenClaw | Ray Core | P95 | 16.2%削減 |
| OpenClaw | Murakkab | P95 | 5.8%削減 |
| Video OCR、本番CPU | 既存本番スケジューラ | P50 / P99 | 59.6% / 48.38%削減 |
| Video Transcode、本番CPU | 既存本番スケジューラ | P99 | 44〜52%削減 |

ルータのみの比較では、Text-to-VideoのMurakkabはRayよりP50が18.0%、P95が23.1%悪化する。平均値中心の予測が多峰性の実行時間分布を捉えられない場合、学習器を追加しただけでは改善しないという**負の結果**である。統合方式が単体ルータよりさらに改善するのは、割当先だけでなく、後続段の需要に合わせてレプリカを増やせるためである。Deep Researchの方が利得が大きいのは、検索・再計画などによる呼出し数と生成時間の両方が変動するためである。

### 予測費用とドリフトへの頑健性

Qwen3-8B向けには約3,500万パラメータの予測器を使い、CPUで約30ms、GPUで約4ms、メモリ100MB未満と報告する。対象モデルの推論は秒〜分の単位なので、制御に追加する数ms〜数十msが相対的に小さいという評価である。ただし短いリクエストや極端な高QPS環境では予測費用が無視できるとは限らず、論文の配備条件を超える一般化は避ける。

80GPUのDeep Research実験でGPU利用可能資源を総計71%減らす強い環境変化を注入すると、再学習しない古い予測器ではP90遅延が40秒を超える。一方、誤差検知に基づいてMLPを再学習するとP90を20秒未満に保ち、検知から再学習完了まで100秒以内だった。これは分布予測の誤りが実際にスケジューリングを悪化させること、オンライン適応が必要なことを示す。長期的な季節変動や未知のモデル系列への転移まで証明した結果ではない。

## 限界・負の結果・実装状況

第一に、主要な本番結果は内部サービス・内部トレース・独自クラスタで得られている。動画変換やOCRの負荷分布、GPU優先度設定、CPUコア数が一般の公開クラスタと異なる可能性があり、同じ相対改善率が再現するとは限らない。論文本文では実運用データを報告しているが、第三者が同じ条件で検証できる完全な公開トレースや実装の存在は確認できない。論文の結論ではコードを今後公開する予定と述べており、公開済みと記述しない。

第二に、予測器の学習ログ収集、意味モデルの配備、分布スケッチの保持、モデルごとのMLP再学習、ドリフト監視に運用費用がかかる。予測器の精度が落ちたときは、再学習の間に誤割当が増える可能性がある。元スケジューラへのフォールバックは可用性を保つための仕組みであって、性能保証ではない。予測器の出力が誤っても分位点スケッチが必ず正しいとは限らず、観測された分布外の長時間要求には弱い。

第三に、スケーラは将来のモデル呼出し構造を推定するが、ツール失敗や人間介入など、プロンプトだけでは決まらない分岐は完全には予測できない。OpenClawやCoding Agentでは構造化パイプラインより改善が小さくなる場合がある。論文はCoding AgentについてOpenClawほどの大きな利得を示さず、負荷が均質な場合には複雑な分布予測の追加価値が縮むことを示唆する。

第四に、実測は特定のvLLM・Ray構成であり、別ランタイム、異種GPUの割合、ネットワーク帯域、バッチ形成、短文脈・超高QPS条件では性能と制御費用が変わる。レプリカを増やす判断が常にコスト最適とは限らない。論文のP95削減率をエネルギー削減率、単一GPUのトークン毎秒改善率、あるいは全ワークロードでのSLO保証と混同してはいけない。

## 既存研究との差

ParrotやPieなどはLLMワークフローの構造や変数を利用した最適化に重点を置く。Murakkabは複数モデルのリソース調整を扱うが、平均処理時間に近い点予測へ依存する。SwarmXはプロンプト意味・モデル・デバイス・ランタイムを入力にする予測器と、分位点スケッチを使うtailコスト評価を統合し、要求単位のルータと時間窓単位のスケーラを同じ制御基盤へ載せる。モデル自体を高速化する研究ではなく、異種計算資源にまたがる待ち時間と需要の予測誤差を小さくし、SLOを改善するシステム研究である。
