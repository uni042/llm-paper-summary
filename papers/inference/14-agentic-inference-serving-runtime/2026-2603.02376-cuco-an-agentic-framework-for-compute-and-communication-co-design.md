# CUCo：LLMエージェントでGPU計算とGPU間通信を協調設計する

## 概要

**CUCo（Compute–Communication Co-design）**は、大規模言語モデルの分散推論・学習で重要なGPU計算とGPU間通信を、言語モデルのエージェントが**通信を含むCUDAカーネルの形で共同最適化**する研究である。既存の分散処理では、行列積や注意計算を高速化する担当と、NCCL通信を高速化する担当が分離されやすい。しかし実際の層全体の遅延は「計算＋通信」だけではなく、両者をどこまで重ねられるか、CPUから通信を起動する間にGPUが待つか、転送完了をどの粒度で確認するかに大きく依存する。

CUCoは、通信方式・同期方式・転送位置などを8つの設計軸として形式化し、まず**正しさ優先の高速経路（fast-path）**でCPU起動型プログラムをGPU起動型通信へ安全に変換する。続いて**性能探索の低速経路（slow-path）**で、コンパイル・数値照合・実機ベンチマークを通した候補だけを残し、進化的な探索で転送と計算の重なり方を改善する。LLMにCUDAコードを無制約で書かせるのではなく、既知の正しい通信操作と明示的な設計空間を渡して、探索の範囲を限定するのが中心的な工夫である。

2サーバー、合計8基のNVIDIA A100 80GBを使う評価では、注意計算の文脈並列、MoEのdispatch/combine、KVキャッシュの受け渡し、行列積＋AllGatherの4負荷を対象とし、CPU起動のNCCL基準構成より**最大1.57倍**の高速化を報告する。別途、DeepSeek-V3のMoE層をDeepEPの標準的な逐次実行と比較し、自己宛てトークンの計算を通信と重ねる二ストリーム構成によって**12〜14%程度の層遅延短縮**を示す。後者はDeepEPのあらゆる最適な使用法に対する勝利ではなく、比較した呼び出し側のスケジュールに対する結果である。

## 背景：速い通信プリミティブだけでは層全体は速くならない

GPU間通信の典型的な実装では、CPUが計算カーネルを起動し、その終了後にNCCLの集団通信を起動する。これを繰り返すと、計算中にネットワークを遊ばせ、転送中に演算器を遊ばせる。CUDAストリームで非同期実行を組み合わせても、通信開始や完了通知が別のカーネルとしてスケジュールされる場合、計算カーネルが全SMを占有すると通知側が実行できない。原著は、注意計算中に通信側の通知カーネルが走れず、通信と計算が逐次化する優先度逆転を具体例として示す。

GPU起動通信（device-initiated communication）は、GPUのスレッドからネットワーク転送や対向GPUメモリへの書き込みを直接指示できる。NCCLのデバイスAPIでは、ネットワーク向けのGPU-Initiated Networking（GIN）と、NVLinkで対向GPUのメモリを直接ロード・ストアするLoad/Store Accessible（LSA）などが使える。GPU内のタイル単位で「このタイルが届いたら直ちに計算する」といった細粒度パイプラインが可能になる。

ただし、その自由度が新しい問題を生む。どのスレッド・ワープ・CTAが通信を発行するか、転送完了をバリアで待つかシグナルで待つか、書き込みの可視性をどの順序で保証するか、転送を計算カーネル内へ融合するか、別ストリームで並走させるかは相互依存する。選択を誤ると性能低下だけでなくデッドロックや誤った結果が生じる。さらにNVLink、RoCE、InfiniBandなどの接続構成が違えば、正しい選択でも最速とは限らない。

DeepEP、FLUX、TokenWeaveなどは熟練者がこの問題を解いた代表例だが、用途とハードウェアに合わせて手作業で最適化している。CUCoは通信プリミティブそのものを発明するのではなく、**それらを呼び出す計算・通信スケジュールを自動で設計する層**に焦点を当てる。実際、DeepEPの通信自体がCUCoより速い場合でも、通信を計算の陰に隠せれば層全体の時間は短くなる。

## 手法

### 8軸の設計空間：コード生成前に意思決定を明示する

CUCoは設計空間を C = B × M × P × S × I × G × O × K と表現する。Bは通信バックエンド、Mは完了確認、Pは通信の配置、Sは同期の範囲、Iは発行主体の粒度、Gは転送単位、Oはメモリ順序、Kは通信コンテキスト数を表す。エージェントはまず各軸を選んだ**最適化指示（optimization directive）**を出し、その指示に沿うCUDAコードを生成する。

| 軸 | 主な選択肢 | 速度・正しさへの影響 |
|---|---|---|
| B：通信バックエンド | GIN／LSA／Hybrid | RoCE等のネットワーク通信かNVLinkの対向メモリ参照かを選ぶ。接続構成を無視すると成立しない |
| M：完了確認 | Barrier／Signal／SignalShadow／Counter | バリアは安全で単純だが全体待ちを増やす。シグナルやカウンタは細粒度重畳が可能な一方、競合・順序制約が増える |
| P：転送配置 | Deferred／Tile-fused／Tile-pipelined／Stream-split | 計算の前後に通信を置くか、タイル単位で融合するか、別ストリームで重ねるかを決める |
| S：同期範囲 | Local／World／Rail／Hierarchical | 全GPUで待つか近接グループだけで待つかを選び、必要以上の全体同期を減らす |
| I：通信発行主体 | Thread／Warp／WarpSpan／Tile／CTA | 細粒度化と発行オーバーヘッド、並列計算資源の占有を調整する |
| G：転送粒度 | Per-peer／Per-tile／Per-chunk | 宛先別、タイル別、チャンク別の転送を選び、パディングとパイプラインを調整する |
| O：メモリ順序 | Relaxed／Acquire／Release／AcqRel | データ書き込みが相手へ見える順序を保証し、誤読・競合を防ぐ |
| K：コンテキスト数 | 1／2／N | 同時に進行する通信コンテキストの数を選ぶ |

たとえば同じMoE層でも、GPU間のネットワーク越しではGINによる宛先別転送が必要であり、同一ノードのNVLinkならLSAと別ストリームの組み合わせが適する場合がある。正解は単に「通信を非同期化する」ことではなく、計算中にどのデータが必要になるか、どのGPUが待つかを含めて決まる。

著者らはDeepEPのNVLink経路、InfiniBand経路、FLUXの設計をこの8軸へ意味的に対応付けている。ただし既存実装は独自の通信手段を使うことがあり、**NCCLデバイスAPIと完全に同一のコード**を使うという意味ではない。8軸は既存方式を比較する共通の抽象化である。

### 正しさ優先のfast-path：動く基準実装を先に確保する

### 1. 既存CUDAコードから依存関係を抽出

入力は、CPUが通信を起動する既存のホスト駆動型プログラムである。静的解析器が計算と通信の依存関係を調べ、どの計算結果が転送の入力になり、どの転送結果が次の計算で必要かを特定する。ここを曖昧な自然言語だけで推定すると、転送開始が早すぎる、完了を待たずに読み込むなどの誤りを生みやすい。

### 2. 通信環境の構築と呼び出し置換を分離

まず対称メモリ割当、通信ウィンドウ登録、GPU側コミュニケータの初期化などの**通信基盤**を用意する。次にCPUから呼んでいた集団通信をGPU側の命令へ置き換える。GINならput／waitSignal系、LSAなら対向メモリ書き込みとバリアなどを使う。二段階の生成と判定に分けることで、コンパイルエラーの原因が環境設定か通信意味論かを切り分けられる。

この段階では最高速を狙わず、CTA単位の発行、保守的なバリア、広い同期範囲、release順序などを選ぶ。これらは性能上の最終解ではないが、通信の意味を満たす最初の実行可能候補を作りやすい。LLM判定器のフィードバックとコンパイル・実行照合を使い、誤った候補を修正する。

### 3. 変更可能領域だけを後段へ渡す

動作を確認したプログラムには、進化探索で編集してよい領域を示すマーカーを付ける。初期化処理、正しさを測るテスト、評価ハーネスなどは固定し、通信の配置や同期、チャンク分割などを編集対象にする。こうすることで探索中の候補がベンチマークを改変して見かけの高速化を作る危険や、初期化コードを壊して無駄な試行を繰り返す危険を減らす。

fast-pathの役割は**安全な種（seed）を作ること**であり、この段階だけで最速化が完了するわけではない。原著の構成要素除去実験では、この段階を省くと初期5世代の候補がコンパイル失敗やデッドロックとなり、限られた探索予算の25%が浪費された。

### 性能探索のslow-path：実測で通信の隠し方を見つける

slow-pathは、設計空間Cを制約として、LLMによる変更提案と進化的な探索を組み合わせる。複数の独立した候補集団（island）を維持し、良い候補を残しながら異なる構成を試す。一定の間隔で候補を交換し、単一の最適化方向へ早く収束しすぎることを防ぐ。

変更提案には、全体の設計を変える**全面書き直し**、細かなパラメータを直す**差分パッチ**、複数の優秀候補の要素を組み合わせる**交差生成**の三種類がある。初期は探索（explore）を重視し、後半は改善（exploit）を重視する。たとえば初期に「タイル融合」と「二ストリーム分割」の両方を試し、後半は勝ち筋となった方式の同期範囲やメモリ順序を細かく調整する。

各候補は、(1)コンパイル、(2)mpirunによる数値一致確認、(3)CUDAイベントによる実機遅延測定の三段階を通る。前段で失敗した候補は後段の高価なベンチマークを実行しない。候補データベースにはコード、計測値、失敗の診断、コード埋め込みによる類似度などを保持する。次の提案時には、親候補の履歴だけでなく、類似した失敗例や複数世代にわたる改善傾向を提示する。

この仕組みは「LLMに最適化案を一回聞く」方式とは異なる。**実行可能性と性能の両方を実機で判定**し、失敗の理由を次の探索へ反映する。特に通信コードは、実行して初めて分かるデッドロックやタイミング依存の問題があるため、静的なコードの見た目だけで評価できない。

## 評価

### 評価環境と負荷の設計

| 項目 | 原著の条件 |
|---|---|
| GPU | 2サーバー、各4基のNVIDIA A100 80GB（合計8基）。負荷ごとに2基または4基を使用 |
| CPU・RAM | 各サーバーに16コアIntel Xeonを2基、メモリ256GiB |
| 接続 | 同一ノード内はNVLink、ノード間はRoCE |
| OS・ライブラリ | Ubuntu 22.04.4、Linux 5.15、CUDA 13.1、NCCL 2.28.9 |
| エージェント | Claude Sonnet 4.5。LLMのAPI利用費用とGPUを動かす計算資源の費用は別 |
| 測定 | CUDAイベントを用い、安定した5回の測定の中央値を採用 |
| 基準 | CPU起動のNCCL通信と既存CUDA計算を組み合わせたホスト駆動型。既存の一般的なストリーム重畳を含む |
| 比較対象 | 4負荷ではホスト駆動型NCCL、別途MoE層ではDeepEPの標準的な逐次実行を比較 |

4負荷は、長文のRing Attention、DeepSeek-V3型MoEのdispatch/combine、プリフィルとデコードを分離した際のKVキャッシュ転送、GEMMとAllGatherである。これらは通信パターンが異なるように選ばれている。Ring AttentionはKVブロックをGPU間で回しながら注意計算し、MoEは専門家への可変トークン配送、KV転送は一方向の中間状態引き渡し、GEMM＋AllGatherは計算直後の集団通信を表す。

ただし評価は著者らが構成した4つの代表負荷であり、vLLMやSGLang全体を組み込んだ実運用ベンチマークではない。したがって、ここでの速度改善は**該当する演算・通信パイプラインの端から端までの遅延**であり、サービス全体のトークン処理量やp99応答時間が同じ割合で改善することを意味しない。

### 主要な性能結果

| 負荷・条件 | CUCoが見つけた設計 | 定量結果と比較範囲 |
|---|---|---|
| 4種の複数GPU負荷全体 | 通信・計算の重畳、GPU起動通信、同期粒度の変更 | CPU起動NCCL基準に対し遅延5.3〜36.2%短縮。最大1.57倍の高速化。全負荷で一律1.57倍ではない |
| Ring Attention、4GPU NVLink、SEQ=4096、HD=32 | 通信専用CTAと計算CTAを分けた持続カーネル、タイルごとの準備完了をカウンタで監視 | 1230.7→1091.7 ms、11.3%短縮。細粒度パイプラインで通信と計算の空白を削減 |
| MoE、2GPU同一ノードNVLink、DeepEP比較 | 自己宛てトークンのGEMMを先行し、遠隔dispatchを高優先度ストリームで重ねる | Rank 0の表では8.42→7.38 ms、12.4%短縮。1〜16層の連続実行でも約12〜14%の層当たり改善 |
| MoE、2GPUノード間RoCE | GINによる可変サイズの宛先別配送と自己計算の重畳 | ルーティング偏り2:1〜5:1で検証。逐次通信・計算やパディングの待ちを改善。DeepEP比較とは接続条件が異なる |
| KVキャッシュ転送、2GPU NVLink | KのGEMM→K転送→VのGEMM→V転送をGPU側から連鎖起動 | CPUが各送信を起動する際の計算・送信間の空白を減らす。個別図の値を全システムのTTFTと混同しない |
| GEMM＋AllGather、4GPU | GEMM完了直後にGPUから集団通信を開始、接続に応じLSA／GINを選択 | ノード内とノード間の双方で比較。計算後のアイドル時間を削減する |

### Ring Attentionのプロファイルが示すこと

Ring Attentionでは、GPUごとにクエリの一部を保持し、KVブロックを順に受け取りながら注意計算する。CPUが転送と注意カーネルを交互に起動する方式では、通信ラウンド間に計算が止まりやすい。CUCoは通信担当CTAを一つ確保し、計算担当CTAと同じ持続カーネル内で、到着したタイルから処理する。後続タイルの転送と、到着済みタイルの演算を重ねられる。

SEQ=4096、HD=32の例では、タイル単位のパイプライン化が63.7ms、通信ラウンド中の計算ストリーム空白の削減が37.7ms、ホスト側の代理処理削減が37.6msの節約要因として示され、合計で約139msの短縮になる。これは単にNCCL通信帯域が高くなったという説明ではなく、**通信待ちとGPU実行のスケジューリングを変えた結果**である。特定のSEQ・HDでのプロファイルなので、長文長や注意頭次元が変われば最適なCTA数やタイル分割も変わる。

### DeepEPとの比較で重要な「通信単体は遅くても全体は速い」

MoE層のDeepEP比較では、標準的な逐次構成が、量子化→dispatch→専門家GEMM→combineを順番に実行する。CUCoは、自己GPUの専門家へ送るトークンはネットワークを待たずに計算できることに着目する。6144トークンのRank 0の内訳では、GEMMを3072トークンずつの自己宛て部分と遠隔部分へ分割し、自己部分を計算している間に遠隔dispatchを別ストリームで開始する。遠隔部分のGEMMはdispatch完了をCUDAイベントで確認してから実行する。

原著の内訳では、DeepEPのdispatch単体は0.47ms、CUCoのdispatchは約1.0msで、**通信だけを比較すればCUCoのほうが遅い**。しかし自己宛てGEMMの約3.04msの裏にdispatchを隠せるため、通信が層全体のクリティカルパスから外れる。合計では8.42msから7.38msへ短縮する。通信プリミティブの最小時間だけで設計を決めるのが不適切であることを、実測で示している。

ただしDeepEPは非同期APIや専用通信ストリームを提供しており、適切な上位スケジューリングを人手で書けば同様の重畳を実現しうる。著者らも、比較したのはDeepEPの**標準的な逐次呼び出し構成**であり、DeepEPのプリミティブを使った理論上の最適な上位実装すべてではないと明記する。したがって本結果は「CUCoの自動探索が専門ライブラリより常に高速」という証明ではなく、「専門ライブラリが提供する部品の組み方を自動最適化できる」証拠である。

### 構成要素除去実験：なぜ二段階と集団探索が必要か

### fast-pathを省くと初期探索が壊れる

ノード間RoCEのMoE負荷で、fast-path＋slow-pathと、slow-pathのみを比較した。前者ではfast-pathが2回のLLM反復で正しいGINカーネルを作り、slow-pathが3世代以内に評価スコア83.95へ到達した。後者では初期5世代がコンパイル失敗やデッドロックとなり、探索予算の25%を浪費する。最終スコアも81.81にとどまり、前者より約2.5%低い。ここでのスコアは論文の内部評価であり、ミリ秒の遅延値ではない。

この比較から、LLMがNCCLデバイスAPIの細部を学習済みであると期待し、最初から高速なコードを書かせる方法は効率が悪いことが分かる。安全な基準プログラムを最初に固定し、編集可能な領域を限定してから性能探索する方が、同じ試行回数を性能改善へ使える。

### 探索と改善を分ける意味

同じMoE負荷で18世代を使い、初期40%を多様な構成の探索に振り向ける二段階方式と、最初から細部の改善だけを行う方式を比較した。二段階方式は3世代で83.86、最終的に83.95に達した。一方、改善のみの方式は9世代ほどスコアが揺れ、10世代目まで76を超えず、最終80.36であった。最終スコアは約4.3%低い。通信を融合するか別ストリームに分けるかといった**構造的に異なる選択肢**を序盤に試さないと、局所最適に陥りやすい。

### 単純な反復プロンプトとの比較

一つのコードをLLMに繰り返し改善させる方式は、20世代で144msから142.3msへ約1.1%改善しただけだった。CUCoの集団・履歴・交差生成を使う方式は3世代で118.1msに達し、同じ出発点から約17%の改善を示す。単純な「修正してください」を繰り返すのではなく、**複数の候補系列を維持し、失敗例と成功例の構造を比較する**ことが重要である。

### 自動最適化の費用と再現性

著者らは、fast-pathに2〜3反復、slow-pathに10〜20世代を用い、負荷ごとの探索に**0.8〜1.8時間**を費やしたと報告する。エージェントのLLM API料金は**4.98〜10.96米ドル／負荷**である。要旨では「10ドル未満」と概括しているが、本文§4の実測範囲には10.96ドルが含まれるため、厳密にすべての負荷が10ドル未満だったとは言えない。さらにこの金額はLLM API利用料金であり、複数A100を稼働させる時間・電力・インフラ費用を含む総最適化費用ではない。

コードベースは約18,000行のPythonとされ、原著は匿名化したコード公開先を示す。実行にはCUDA 13.1、NCCL 2.28.9のデバイス起動API、NVLinkやRoCEを含む通信環境が必要である。評価用エージェントにはClaude Sonnet 4.5を使用しているため、他のLLMに置き換えた場合の候補生成能力やAPI費用が同じになる保証はない。

再現の際には、基準実装をCPU起動NCCLのどの構成にするか、CUDAストリームの重畳をどこまで許すか、コンパイルと正しさ検査を同じ基準で行うかが重要になる。DeepEP比較では、通信プリミティブを同じものに固定した上で上位スケジューリングを変えた場合の結果と、別の通信実装へ切り替えた場合の結果を混同してはならない。

## 限界

**通信がクリティカルパスにない負荷には効きにくい。** 行列積がほぼ全時間を占め、NVLinkでの通信がごく短い場合、重畳の余地がない。すでに専門家が最適な融合スケジュールを書いた負荷でも改善幅は小さい。CUCoは通信と計算の待ち時間が大きい領域を対象とする。

**ハードウェア依存性が強い。** A100、NVLink、RoCE、CUDA 13.1、NCCL 2.28.9の結果を、RTX 4070 Superなどの単一GPUや、NCCLデバイスAPIの条件が異なる環境へそのまま移植できない。特に単一GPUではGPU間通信がないため、本研究の主たる高速化機構は働かない。

**専門ライブラリの最適構成との網羅比較ではない。** DeepEP以外の専門実装は、著者らのハードウェア上で導入・測定できなかったため、全面比較していない。DeepEP自体も標準逐次構成が基準であり、利用者が独自に高度な非同期重畳を組んだ場合の差は別問題である。

**生成コードの正しさは検査条件に依存する。** コンパイル成功と数値一致だけでは、あらゆる形状・通信タイミング・GPU構成でのデッドロック不在を形式的に保証できない。実運用ではテスト形状、ルーティングの偏り、ストリーム優先度、メモリ順序、複数GPUの故障などを追加検証する必要がある。

**探索費用はゼロではない。** 1負荷あたり0.8〜1.8時間の実機探索と数ドルから十数ドルのAPI料金が必要になる。負荷形状が頻繁に変わるサービスでは、最適化結果の再利用率や、再探索の費用対効果を考える必要がある。論文は固定した4負荷での評価であり、動的なオンライン自動チューニングを常時走らせた場合の運用費用は測っていない。

**測定値はカーネルパイプラインの遅延である。** 実運用のモデルロード、リクエスト待ち行列、前処理、ネットワーク入出力、バッチング、長文メモリ管理などを含むTTFT・TBT・p99の改善率を直接示していない。特定演算の36.2%短縮を、LLMサービス全体の36.2%短縮として報告するのは誤りである。

**原著内の条件表記には読み分けが必要である。** MoEのノード間RoCE評価では4096トークン／rankなどを用いる一方、DeepEP比較の内訳表ではRank 0の6144トークンが示される。評価構成と表の内訳を確認せず、両者を同一の測定値として結合してはならない。

## 実装への示唆

この研究の一般化可能な点は、LLMにすべてのコードを自由生成させるのではなく、**ドメイン専門家が定義した設計空間と検証可能な変換手順の上で探索させる**ことにある。通信の意味論を固定したまま、同期の範囲、タイル粒度、ストリーム構成などを変えられるようにすれば、実機測定に基づいて性能を改善できる。逆に、基準の正しさを確認する前に自由な最適化を始めると、通信のデッドロックやコンパイル失敗で探索予算を浪費する。

MoEの推論基盤では、自己宛てトークンの専門家計算と遠隔dispatchの並走が特に分かりやすい。これはDeepEPのような高性能通信プリミティブを置き換える必要がなく、上位スケジューラの依存関係を組み替えるだけでも効果が出る場合があることを示す。KVキャッシュのプリフィル・デコード分離では、KとVの生成完了を待ってからCPUが転送を起動する代わりに、GPU側で生成と転送を細かく連鎖させる設計が有効な場合がある。

評価では、通信単体の時間ではなく**計算と通信を含むクリティカルパスの長さ**を測るべきである。また、探索の性能だけでなく、候補が正しく動く割合、失敗に費やす世代数、実機測定費用、異なるGPUトポロジーへ移したときの再探索量も測定対象にすることが重要である。CUCoの最大1.57倍は、こうした設計を特定の4負荷とA100環境で検証した結果であり、すべてのLLM推論に保証される定数倍率ではない。
