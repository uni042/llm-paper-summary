# LatentMem：役割別の潜在記憶を学習してマルチエージェントの入力負荷を抑える

## 概要

複数のLLMエージェントが分担して質問応答、コード作成、計画立案を進めるとき、過去の実行軌跡を再利用することは有効である。しかし全エージェントへ同じ履歴や要約を渡すと、役割に無関係な情報が増え、似た指示を共有することで同じ誤りを繰り返す危険がある。反対に、エージェントごとに人手で別の記憶スキーマを設計すると、役割数とタスクの増加に合わせて管理が複雑になる。LatentMemはこの二つの問題を、**経験を保存する場所と、現在の役割向けに記憶を生成する場所を分離**して扱う。

システムは過去の複数エージェント実行軌跡を保存する経験バンク（experience bank）と、検索した軌跡と現在のエージェントの役割説明を受け取り、固定長の潜在記憶を生成するメモリ合成器（memory composer）からなる。生成した記憶は文章としてプロンプトへ追加するのではなく、基盤LLMの入力埋込みと同じ次元を持つ短いベクトル列として結合する。記憶の長さを固定するため、長い履歴をそのままプロンプトに載せる方式より入力トークン相当の費用を制御しやすい。

さらに、潜在記憶方策最適化（Latent Memory Policy Optimization; LMPO）を用い、最終課題の成否からメモリ合成器のパラメータを改善する。基盤エージェントのLLM重みは固定し、学習可能な記憶生成器を介して役割に適した情報を渡す点が中核である。Qwen3-4Bを使ったAutoGenでは6課題の平均スコアが記憶なし53.61から62.75、MacNetでは50.73から60.02に改善した。これらは同一実験内の比較であり、別のエージェント基盤やGPUで同じ改善が得られる保証ではない。

## 問題設定と既存方式との差

従来の記憶には、過去の会話を全文保存する方式、履歴を要約して検索する方式、抽象化したスキルを蓄積する方式、役割ごとに手作業で記憶を割り当てる方式がある。全文保存は忠実だが長い。要約は短いが何を残すかに依存する。手順やスキルの記憶は汎用性がある一方、現在の役割に必要な情報が違っても同じ内容を返す場合がある。複数エージェントの協調では、計画担当、実装担当、検証担当がそれぞれ違う観点から同じ過去の経験を読む必要がある。

LatentMemは経験バンクに人手で抽象化した教訓を直接書き込むのではなく、実行軌跡を比較的素朴な形式で保存する。実行時に検索された軌跡を、各エージェントの役割説明とともに学習済み合成器へ渡す。このため同じ履歴から、計画担当には全体戦略、実装担当には具体的な制約、検証担当には失敗条件というように、異なる潜在記憶を作る余地がある。ただしその潜在ベクトルを人が直接読んで意味を確認できるわけではない。

問題は、エージェント集合 `A={a1,...,aN}`、処理順を定める実行グラフ `G`、記憶モジュール `M` を持つシステムとして定式化される。各エージェントは役割説明 `γk` と生成方策 `πθk` を持ち、タスクqに対する実行軌跡τの最終報酬 `R(τ)` の期待値を最大化する記憶モジュールを求める。ここで最適化対象は単なる検索精度ではなく、**記憶を使った最終課題の達成度**である。履歴の再現性が高くても回答の正しさに寄与しなければ、良い記憶とは評価されない。

## 手法

### 1. 経験バンク：生の実行軌跡を蓄積して検索する

経験バンク `B` は、過去のエージェントの動作を `τ={(αj,pj,oj)}` の形で保存する。`αj` はその段階で活動したエージェント、`pj` は入力、`oj` は出力である。ここで保存するのは単一のユーザー発話だけではなく、複数エージェントの協調過程を含む軌跡である。履歴から人手で「成功の法則」を抽出して保存するのではなく、まず実行事実を保持し、再利用時に合成器へ意味づけを委ねる。

新しい問い合わせqが来ると、問い合わせと各軌跡を埋込みモデル `v(·)` でベクトル化し、余弦類似度の上位K件を選ぶ。式では `Tq=topK(sim(v(q),v(τi)))` と書ける。著者実装は `all-MiniLM-L6-v2` を検索用埋込み器とし、主要設定でK=1を使う。これは検索時に大量の軌跡を合成器へ渡さない設定であり、必ず1件だけで十分だという一般的な結論ではない。

実行が終わると新しい軌跡をバンクへ追加し、次回の検索対象とする。経験バンクへの追加は推論時にも行えるが、メモリ合成器のパラメータをその都度オンライン強化学習することとは別である。論文の「継続的な改善」は、少なくとも経験集合が更新されることを含む。検索品質が落ちるほどバンクが肥大化した場合の削除、重複排除、信頼度管理、プライバシー保護は別途設計が必要になる。

### 2. メモリ合成器：役割条件付きの固定長潜在トークン

メモリ合成器 `C=σφ` は、検索された軌跡集合 `Tq` と現在の役割説明 `γ` から、潜在記憶 `m=σφ(γ,Tq)` を生成する。出力形状は `L'×D` で、Dは基盤LLMの隠れ次元、L'は固定の記憶長である。主要実験は `L'=8` とする。たとえ検索した軌跡が長くても、基盤モデルへ注入する記憶は8個の潜在トークンであり、元の長文全体を追加プロンプトとして処理するわけではない。

現在の入力の埋込みを `h` とすると、合成器の出力を `concat(h,m)` の形で入力列へ結合する。エージェントを呼び出す外側の協調フレームワークには、役割説明と通常のタスクを与えるインターフェースを保ちつつ、モデル入力に潜在記憶を挿入する。著者が「フレームワークの改変不要」と述べるのは、この上位のエージェント制御構造を変更しなくてよいという意味である。**一般的な文字列プロンプト専用の外部APIへ8個の浮動小数点ベクトルをそのまま渡せることは意味しない**。モデルの埋込み層にアクセスする実装が必要である。

役割を合成器の条件に入れることで、同じ経験から異なる記憶を生成できる。役割説明を除外すればエージェント間の記憶が似通いやすく、実装担当と検証担当の区別が弱まる。記憶を自然言語で可読にしない設計は入力長を抑える一方、何を記憶したかの説明可能性と監査を難しくする。実装では検索元軌跡のID、役割、合成器版を外部ログへ残す必要がある。

### 3. LMPO：最終課題の報酬を記憶合成器へ伝える

潜在記憶は基盤LLMの入力へ連続値として入るため、基盤モデルを凍結しても、生成確率が記憶ベクトルに依存する。その依存関係を通じて、メモリ合成器のパラメータφへ勾配を伝えられる。論文のLMPOは、同一課題から複数の実行軌跡をサンプリングし、グループ内の相対的な成否から優位度を作るGRPO系の最適化である。

グループG本の軌跡に対して、軌跡iの報酬を `Ri`、平均を `μG`、標準偏差を `σG` とすれば、優位度は `Ai=(Ri-μG)/(σG+ε)` となる。成功した軌跡だけを絶対値で褒めるのではなく、同じ課題で試した軌跡同士の相対差を利用する。さらに各軌跡の各エージェント・各トークンの生成確率比を用い、旧方策から大きく外れすぎないようクリップした目的関数でφを更新する。基盤LLMのθは固定され、学習されるのは合成器側のパラメータである。

軌跡長が大きく異なる場合、軌跡ごとの損失を単純平均すると、長い協調過程に現れる重要な局所判断へ適切に学習信号が届かない可能性がある。LMPOはグループ全体の生成トークン数で正規化したトークン単位の代理目的を採用する。ただし最終報酬がどの潜在記憶成分に因果的に対応したかを直接証明するものではない。報酬評価器の偏りや失敗した軌跡からの誤学習は依然残る。

### 4. 実行時の処理順と追加費用

実行時は、(1)新しい課題を受け取る、(2)経験バンクから類似軌跡を検索する、(3)役割ごとに合成器が8個の潜在トークンを生成する、(4)各エージェントの入力埋込みへ記憶を追加して推論する、(5)完成した協調軌跡をバンクへ追加する、という順序になる。検索、合成器の順伝播、入力の連結、履歴保存は追加の処理である。記憶が短いからといってシステム全体の実行時間が必ず短くなるわけではなく、削減できた長いテキスト履歴の処理費用と、追加した記憶生成費用の差を測る必要がある。

訓練時にはさらに、複数の軌跡生成、報酬計算、勾配伝播が必要である。原著は合成器を軽量Transformerとし、基盤モデルのパラメータから初期化してLoRAで学習する。したがって推論時のモデル本体は凍結されるが、合成器を別のモデル系列へ移植するには、隠れ次元と入力埋込みの分布、役割説明の表現を再確認する必要がある。

## 評価

### 実験環境・比較対象

原著は6つの課題を、TriviaQA・PopQAの知識質問応答、KodCode・BigCodeBenchのコード、StrategyQAの推論、PDDLの記号計画に分ける。複数エージェントの枠組みにはAutoGen、MacNet、CAMEL、DyLANを使う。AutoGenとMacNetを訓練時に見た枠組み、CAMELとDyLANを未見の枠組みとして区別し、課題についても4つの学習対象と2つの未学習対象を分ける。基盤モデルはQwen3-4B-Instruct-2507とLlama-3.1-8B-Instructを評価する。

比較対象には記憶なし、ChatDev、MetaGPT、Generative、Voyager、G-Memory、JoyAgent、OAgentsなどを含む。これらは単純な「同じ記憶を8トークンへ縮めたもの」ではなく、保存・検索・要約の設計が異なる。性能差は潜在トークンだけでなく、役割条件付け、学習方法、検索の設計を含む方式全体の差として解釈する必要がある。

主要設定は検索上位K=1、潜在記憶長L'=8、検索埋込みモデルall-MiniLM-L6-v2である。基盤LLMと合成器の役割、学習データと未学習データ、実行フレームワークの区別を固定せずに結果を横断比較すると、汎化性能を過大評価する危険がある。

### 6課題での主結果

Qwen3-4B-Instruct-2507を用いた表1では、AutoGenの6課題平均が記憶なし53.61からLatentMem 62.75へ**9.14ポイント**上がる。MacNetは50.73から60.02へ**9.29ポイント**上がる。これは相対9.14%という意味ではなく、百分率尺度のスコア差である。AutoGenのTriviaQAは60.31→76.51で16.20ポイント、MacNetのPopQAは24.89→44.14で19.25ポイント改善する。

| 枠組み・課題 | 記憶なし | LatentMem | 差 |
|---|---:|---:|---:|
| AutoGen / 6課題平均 | 53.61 | 62.75 | +9.14ポイント |
| MacNet / 6課題平均 | 50.73 | 60.02 | +9.29ポイント |
| AutoGen / TriviaQA | 60.31 | 76.51 | +16.20ポイント |
| AutoGen / KodCode | 68.40 | 76.80 | +8.40ポイント |
| AutoGen / PDDL（未学習） | 16.39 | 23.49 | +7.10ポイント |
| MacNet / PopQA | 24.89 | 44.14 | +19.25ポイント |
| MacNet / PDDL（未学習） | 20.73 | 25.13 | +4.40ポイント |

未見のCAMELでも6課題平均は53.22から60.72へ7.50ポイント改善する。別枠組みへ移した場合に役割条件付き記憶が機能する証拠だが、全く異なる基盤モデルや任意のエージェント数へ外挿できるわけではない。著者はLlama-3.1-8BのMacNet/KodCodeで48.50から65.50への改善も報告する。これは別モデル条件の値なので、Qwen3-4Bの表1へ混ぜて平均しない。

### 費用、トークン数、推論時間

図3は各記憶方式の性能向上と時間・トークン費用の関係を示す。著者は従来の記憶方式と比べてトークン数を約半分にし、推論時間をおよそ3分の2にできる条件があると説明する。具体例としてDyLAN/TriviaQAでは、OAgentsに対して推論時間を2.16倍短縮しながら記憶なしより11.68ポイント高いスコアを示す。AutoGen/KodCodeでは記憶なしより0.01Mトークン少ない条件で8.40ポイント改善したと報告する。

ただし図3の値は特定の複数エージェント設定と比較方式に依存する。**入力トークン数の減少と、GPUでの全体生成速度の増加は別の指標**である。潜在記憶の生成に必要な合成器の計算や、検索用埋込み計算、メモリ保存のI/Oを含むかを確認しないと、実運用でのエンドツーエンド遅延は分からない。特に短い課題や履歴が少ない初期状態では、合成器の追加処理が相対的に重くなる可能性がある。

### 構成要素除去と汎化

著者は役割情報を合成器へ渡さない条件を比較し、KodCodeでAutoGenは2.30ポイント、MacNetは6.45ポイント悪化したと報告する。役割が複雑な協調枠組みほど、同じ潜在記憶を全員へ渡す方式が不利になる可能性を示す。経験バンクの実行時更新を止めると、MacNet/KodCodeは3.60ポイント、PDDLは7.63ポイント悪化する。過去の履歴を新しく追加する仕組みと、役割別に記憶を作る仕組みの両方が結果に寄与している。

これは合成器の潜在記憶だけが改善を生んだという単一要因の証明ではない。検索バンク、役割条件、LMPO学習、入力への潜在注入が組み合わさった方式である。論文はMARTIとの比較で同等の学習計算予算を用いた条件も設けるが、比較対象のエージェント方策の更新範囲は異なるため、すべての訓練方式に対する普遍的優位を示すものではない。

## 限界

第一に、**潜在記憶は人が読めない**。検索された軌跡と役割説明は記録できても、合成器が8個のベクトルへ何を保存したかを直接監査するのは難しい。誤った履歴、個人情報、攻撃的な入力がバンクに入った場合、どの情報が後続の推論へ作用したかを追跡する仕組みが別途必要になる。論文の実験は公開ベンチマークの制御環境であり、実ユーザーの長期記憶やアクセス権限を扱う製品環境の安全性を検証していない。

第二に、**経験バンクの品質と検索器に依存する**。主要設定K=1では、最上位の軌跡が不適切だと合成器へ渡す情報が偏る。軌跡を追加するだけでは、重複、陳腐化、誤情報、異なるユーザーのデータ混線は自動解消されない。長期運用では検索の適合率、バンク容量、履歴の有効期限、出典と権限を管理する必要がある。

第三に、**基盤LLMの内部埋込みへアクセスする必要がある**。上位のAutoGen等の協調フローを変えずに済むとしても、文字列だけを受け付ける閉鎖的なAPIで同じ注入ができるとは限らない。合成器の出力次元Dはモデルに依存し、別のモデルへ移すときは次元・層・トークナイザー・正規化を合わせる必要がある。モデル重みを更新した場合、既存の合成器と記憶表現の互換性を再確認するべきである。

第四に、**学習と推論の費用を分ける必要がある**。LMPOは複数の協調軌跡を生成して報酬を評価し、凍結したLLMを通して合成器へ勾配を伝える。基盤LLM自体を再学習しなくても、メモリ合成器の最適化は無料ではない。論文のトークン削減や応答時間の改善を、合成器の学習費用まで含む総所有コストの削減と同一視できない。

第五に、**課題と枠組みの範囲が限られる**。6課題、4種類の協調枠組み、2つの基盤モデルでの評価は有用だが、何百ものエージェントが長期間稼働する運用、モデルが頻繁に更新される環境、外部ツールによる破壊的操作、敵対的な履歴注入に対する検証ではない。未学習課題と未見フレームワークでの改善は、無制限の領域外汎化を保証しない。

第六に、**役割別の記憶生成とエージェント間の通信は別問題**である。本方式は履歴から各エージェントへ潜在記憶を提供するが、任意の二つの異種LLMが内部状態を直接相互送信するプロトコルを一般的に解決するわけではない。通信のトポロジー、キャッシュ共有、セッション分離、モデル間の隠れ状態整合は別途設計が必要である。

## 既存方式との差と実装上の判断

LatentMemの価値は、過去の軌跡を保存するだけでなく、**同じ経験を現在の役割に応じて固定長の潜在表現へ変換し、その生成器を最終タスクの報酬で学習する**点にある。AgeMemのように記憶の追加・更新・検索をツール呼出し方策へ組み込む方式とは異なり、記憶そのものの提示形式を連続ベクトルに変える。ReasoningBankのように成功・失敗から自然言語の戦略を抽出する方式とも異なり、可読性を犠牲にして固定長の入力を重視する。

推論エンジンへ移植するなら、まず埋込み層に任意の潜在トークンを追加できるか、モデルごとに次元を合わせられるか、追加トークンを含むKVキャッシュの位置管理が正しいかを確認する。次に、同じ検索軌跡から役割別に生成した記憶と、役割を無視して生成した記憶を比較し、タスク品質、トークン数、TTFT、全体遅延、GPUメモリ、検索・合成器費用を測る。最後に、誤った軌跡や機密情報を混入させた場合の影響と、記憶を無効化するフォールバックを検証する。

ローカルGPUでは、合成器の順伝播と基盤LLMの推論が同じVRAMを奪い合う可能性がある。8個の潜在トークン自体は小さくても、検索モデル、合成器、バンク、最適化器の実装に必要なメモリを加算するべきである。論文の改善率を別のGPUや量子化モデルへ直接転記しない。これらの確認は本稿から導く実装上の検討事項であり、原著があらゆる環境で実証した内容ではない。
