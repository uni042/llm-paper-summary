# SparseRead：LLMエージェントが外部資料を読み過ぎないための段階的読解層

## 概要

長い作業を実行する大規模言語モデル（LLM）エージェントは、文書、PDF、表、コード一式などの外部資料を繰り返し読む。多くの読解道具はファイル全体を一度に返すため、エージェントが一行の証拠を探しているだけでも大量の無関係なトークンが文脈へ入る。これにより入力処理の計算費用と遅延が増えるだけでなく、重要な根拠が埋もれて道具選択や停止判断を誤る場合がある。

SparseReadは、外部資料の内容がモデルの文脈へ入る**前**に、必要な根拠だけを段階的に取得する学習不要の読解層である。資料の短いプレビュー、構造化した読解意図、どの領域を調べて何を得たかを保持する根拠状態、資料種類に応じた読解器、疎な読解を使うか全文読解へ戻すかを決める読解判定器（Read Gate）を組み合わせる。モデル重みの変更や別の要約モデルの推論を必須としない。

原著は6モデル・5種類の作業場面で最大92.9%のトークン削減と最大89.0%の実行時間削減を報告する。ただし**最大値であり全設定の平均ではない**。30のモデル・場面の組合せのうち26組は品質維持または改善、4組は小幅な品質低下である。全文を読むべき表計算や小さいファイルへ無理に適用すると、逆にトークン量が大きく増える例も確認しており、読解判定器はこの負の条件を避けるための主要機構である。

## 問題設定：外部資料の過剰読解

原著はエージェントの軌跡の60〜80%を外部観測が占めるという先行研究を背景に、高い疎性を持つ作業では投入された読解内容のうち意思決定に役立つ情報が6〜15%程度にとどまる場合があると報告する。比較実行では、全文読解のエージェントがSparseReadより最大17.3倍のトークンを使っても、作業品質が向上しない例がある。問題は単なる長文脈の処理速度ではなく、不要な証拠を一度投入すると、次の推論呼出しで再び処理され、誤った推論経路にも影響することである。

通常の文脈圧縮は、読んだ後の観測を短くする。これは後続の呼出しを軽くできても、最初に全文を取り込んだ費用を取り消せない。また、短い要約だけを返しても、どこを確認したか、未調査領域は何かが分からなければ、エージェントは圧縮結果を信用できず、同じ資料を繰り返し読み直す。原著はこの状態を「圧縮への不信（compression distrust）」と呼び、根拠の範囲が分からない条件で要求回数が1.7〜6.2倍、トークン量が2.1〜12.5倍となる例を示す。

したがって単なる抜粋器では不十分である。読解した領域、得られた根拠、未解決の問い、停止してよい条件をモデルへ明示し、必要なら全文読解へ戻る手順が要る。SparseReadは資料へのアクセスそのものを制御対象とし、エージェントの読み取りを一回の大きい操作から、根拠の不足を確認しながら進める一連の小さい操作へ変える。

## 手法

### 1. 資料プレビューと読解意図

外部資料の読解要求を受けると、まず資料の見出し、ページ、ファイル一覧、表の列などを上限付きでプレビューする。エージェントは現在の目的とプレビューから、何を知りたいかを構造化した読解意図（Read Intent）として作る。例えば大きな監査用フォルダから「特定のAPI変更が失敗する条件」を探すなら、全ファイルを投入するのではなく、関係するファイルや関数の候補、調査すべき証拠の種類を意図として記述する。

読解意図は別モデルが予測するのではなく、既存エージェントが通常の読解行動の一部として作る。プレビューは、どこに情報がありそうかという地図を与えるが、証拠そのものの完全性を保証しない。以後の部分読解で根拠が不足すれば、意図を狭めたり調査領域を広げたりする。初回の意図に含まれる未解決事項は後の更新でも保持されるため、都合のよい証拠だけを見て勝手に終了しにくい。

### 2. 状態を持つ読解手順と五つの操作

原著のAlgorithm 1は、資料o、エージェント状態z、通常読解の経路Nを入力し、最大K回の読解ラウンドを実行する。読解の進捗はモデルにも見える根拠状態（Evidence State）Eとして保持する。Eは取得済みの根拠、出典位置、調査済み領域、未解決要求、取得状況を管理する。これにより「検索した範囲には証拠がなかった」と「まだ調べていないため不明」を区別できる。

エージェントに公開する操作は五種類である。scoutは情報空間を概観し、focusは狭い根拠位置を探し、collectは複数の根拠を集め、refineは残る疑問を絞り込み、verifyは得た主張を再確認する。読解器が異なってもこの操作語彙は共通であり、エージェントが資料種類ごとに大量の道具名を覚える必要はない。

各ラウンドでエージェントが操作を選ぶと、読解器のルータが資料種類と操作に合う実装を選び、出典位置を付けた結果を返す。Eを更新し、現在の読解意図に対して必要な根拠がそろえば終了する。適切な読解器がない、結果が利用不能、状態が進展しない、K回の予算を使い切った場合は、通常読解へ戻す。これは無限に細切れ検索を繰り返すことを防ぐための制御である。

### 3. 読解器の差替えと資料種類の分離

読解制御部と、実際の資料から根拠を取得する読解器（Reader Backend）を分離する。文章・PDF読解器は見出しやページ番号を索引として短い範囲を取り出す。表読解器は列構造、標本行、必要な行・列の投影、計算可能な表断片を返す。複数ファイルの読解器はまず目録を作り、候補ファイルを選んでから必要部分を開く。読解器ごとに対応する資料型と操作、推定費用を登録する。

読解器のルータは対応可否で候補を絞り、読解意図に最も具体的に合う実装を優先する。専門領域向けの読解器を後から追加しても、エージェントに見せる五つの操作や根拠状態の形式は変えない。原著は外部の学習済み圧縮器を読解器として組み込む可能性も述べるが、既存の別方式を統合した場合の性能まで実測したわけではない。評価した読解器は追加の学習済みモデルを呼ばず、読解時の予測不能な計算費用を抑えている。

### 4. 読解判定器：疎な読解が不利な要求を除外

読解判定器（Read Gate）は、プレビューpと意図hを受け、疎な読解へ強制的に入るか、通常読解を使うか、両方を許す助言モードにするかを一度決める。資料全体を処理しないと意味がない集計や、適切な読解器のない資料では通常読解を選ぶ。残る要求について、避けられる文脈投入量s、読解手順の追加費用c、重要情報の取りこぼし危険rを正規化し、b=w_s s−w_c c−w_r rという線形余裕値を計算する。

余裕値が上側閾値以上なら疎な読解を強制、下側閾値以下なら通常読解、その間ならエージェントに選択を許す。重みと閾値は開発用の作業負荷で品質低下の許容範囲を守りながらトークン削減を最大化するよう選ぶ。追加の学習モデルで判定するのではなく、観測可能な資料規模・意図の範囲・読解器費用から決めるため、判定自体の推論費用が小さい。

この判定は万能ではない。原著§3.2では、全体を読む必要がある対照課題へ疎な読解を強制すると、トークン量がそれぞれ309.2%、210.5%増える条件を示す。短いファイルを何度も分割して読むと、プレビューや根拠確認の往復が全文読解より高くつくためである。助言モードと通常読解への復帰は、こうした逆効果を避ける安全側の設計である。

### 5. エージェントへの統合と文脈キャッシュ

共有実行基盤はプレビュー、根拠状態、判定器、読解器の実装を持ち、エージェントごとには薄い接続部だけを追加する。NanoBotには道具を直接登録し、OpenCodeとOpenClawではプラグインまたは接続部から`sro_preview`と`sro_read`を公開する。既存のモデルやエージェント方針を再学習しなくても、読み取りの入口を置き換えられることが利点である。

原著は、読み取り境界より前の会話と道具呼出しの接頭辞を変えず、その後に追加する観測だけを短くする設計を説明する。接頭辞完全一致によるキャッシュがある場合、境界より前のKVキャッシュ再利用は維持できる一方、追加する入力の事前処理量が減る。これはモデル内部のKVを量子化・削除する手法ではなく、モデルへ送る外部資料のトークン数そのものを抑える方式である。

## 評価

### 課題、モデル、比較対象

原著はQwenClawBench、Claw-Eval、PinchBench、LooGLEから125課題を抽出し、長文書の質問応答、PDF読解、多数ファイルの監査・診断、構造化データ処理、全文処理向け対照課題を含める。材料化学の科学研究課題も追加する。NanoBotの主評価はClaude Opus 5、Qwen3.6-Plus、DeepSeek-V4-Flash、DeepSeek-V4-Pro、GLM-5.1、Kimi-K2.5の六つのモデルで行う。比較方式は全文読解、補助モデルによるACON圧縮、最近の観測10件だけを残す位置依存の観測マスクである。

評価指標は全作業のトークン削減率、作業品質の得点差、壁時計時間の削減率である。補助モデルを使う比較方式では、その呼出し費用も含む。したがってこれはモデル単体のトークン/秒やGPUカーネル処理量の測定ではなく、資料読解を含むエージェント作業全体の比較である。原著は3回の実行を平均した値を報告する。

### 六モデル・五場面の結果

図7の30組のモデル・場面では、全組合せでトークン量と壁時計時間が減少し、最大削減率はそれぞれ92.9%、89.0%である。作業品質は26組で維持または改善したが、4組では小幅に低下する。疎な読解が適した四場面の24組では、トークン削減15.7〜92.9%、時間削減28.3〜89.0%、品質非低下は22組であった。最強モデルとして評価したOpus 5でも、疎な読解向け場面でトークン59.6〜89.0%、時間51.3〜78.1%の削減を示した。高性能モデルなら外部資料の過剰投入が問題にならないという仮説を否定する結果である。

材料化学の科学研究課題では、六モデルすべてでトークン量が82.7〜89.1%、時間が28.3〜63.0%減少した。ただし全体の最大値を各場面へ適用してはいけない。必要な証拠が散らばっている課題や、全体を計算する課題では、追加の部分読解が利益を相殺する。

### 既存圧縮方式との直接比較

ACONと観測マスクとの直接比較は、二場面・三モデルの計六条件で行われる。SparseReadは全条件で最少のトークン量と作業時間を示し、トークン63.4〜86.3%、時間44.7〜72.3%の削減を記録した。時間削減を完了時間の逆比で表すと約1.8〜3.6倍の高速化となる。ACONは六条件中四条件で全文読解よりトークン・時間の両方が増え、Qwen3.6-Plusの複数ファイル診断では得点が0.80低下する例もある。観測マスクは単に新しい観測を残すだけで、必要な証拠の所在に対応しないため、DeepSeek-V4-Proの二条件で全文読解より費用が増えた。

### 判定器の選択性と負の結果

原著図9ではDeepSeek-V4-Pro上の対照課題を用い、疎な読解が有効な要求と全文読解が適する要求の分離を確認する。読解判定器が介入した38組ではトークン費用が減り、39組では品質維持または改善と報告する。明確な利益のある14組の中央値削減は79.6%であった。ただし対照課題で疎な読解を強制した場合は、前述の通りトークン量が2〜3倍以上増える。判定器を使わない常時疎読解は、本手法の完成形と同等ではない。

## 従来方式との差異

注意計算の疎化やKVキャッシュ圧縮は、すでにモデルへ投入したトークンを安く処理する方式である。観測マスクは投入後の古い観測を隠し、補助モデルによる圧縮は読み取った文章を短くする。SparseReadは、そもそも全文を投入せず、根拠位置と未解決事項を持つ状態付きの読解操作を通じて必要な部分だけを取得する。対象とする最適化位置が、モデル内部や履歴整理ではなく**外部資料の取得境界**にある。

根拠状態を持たない単純な抜粋では、エージェントが短い回答を信用できず繰り返し読んでしまう。SparseReadの停止・検証・復帰の規則は、トークン削減と同時に「根拠を確かめた」という判断を支える機構である。反面、全文を必要とする作業では通常読解を残すことが不可欠であり、常に部分読解だけで十分という主張ではない。

## 限界・適用できない条件

第一に、表の全行を集計する、全文を厳密に走査する、小さなファイルを丸ごと読むといった低疎性の作業では、細切れの読解手順が費用を増やす。強制適用時のトークン量+309.2%と+210.5%は明確な負の結果である。第二に、部分読解の根拠が不足していてもエージェントが誤って完了と判断すれば、重要な情報を見落とす。根拠状態と検証操作はこの危険を抑えるが、完全な情報網羅を数学的に保証するものではない。

第三に、判定器の重みと閾値は開発用負荷で調整するため、資料種類や業務が変われば疎性・危険度の見積もりがずれる可能性がある。第四に、30組のうち4組、三基盤比較15組のうち3組で小さい品質低下があり、「全条件で品質が必ず不変」という主張は成り立たない。第五に、3回実行のエージェント評価は確率的な揺らぎを含み、得点差が小さい場合の有意性を別途確認する必要がある。

第六に、測定した削減率はエージェントの道具呼出しと入力処理を含む作業全体の値であり、LLMの生成カーネルが92.9%高速化したことを示さない。第七に、追加の読解器を増やせる設計であっても、未実装の専門資料へ同じ結果を外挿できない。第八に、通常読解へ復帰するときには、それまでの部分読解費用に全文読解の費用が加わるため、判定器が失敗した場合は総費用が増え得る。
