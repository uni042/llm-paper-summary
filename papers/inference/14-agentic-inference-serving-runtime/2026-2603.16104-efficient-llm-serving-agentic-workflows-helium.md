# Efficient LLM Serving for Agentic Workflows: A Data Systems Perspective

> Heliumはエージェント型処理を問い合わせ計画として最適化し、モデル呼出しの重複・KV再計算・キャッシュ追い出しをワークフロー横断で減らす。H100 NVL 2基で、複合的なTrading処理においてKVFlow比最大1.34倍の高速化を報告する。

## 概要

複雑なエージェントは、一つの課題を解くために複数のモデル呼出しを連ね、並列の調査、複数エージェントの討論、段階的な要約を組み合わせる。こうした処理では、異なる呼出しが同じ指示文、文脈、途中結果を繰り返し扱う。通常の推論器は各呼出しの連続バッチ処理や接頭辞キャッシュを効率化するが、ワークフロー全体の依存関係や、後続呼出しで再利用できる状態までは把握しない。そのため、必要な演算を重ねて行ったり、共有接頭辞のキャッシュを別の処理で追い出したりする。

本論文は、エージェント処理をデータベースの問い合わせ処理に似た計画問題として扱うHeliumを提案する。入力ごとの処理を有向非巡回グラフ（Directed Acyclic Graph; DAG）へ展開し、大規模言語モデル（Large Language Model; LLM）呼出しを第一級の演算子として表す。論理計画の整理、演算子出力のキャッシュ、静的プロンプト接頭辞の先行計算、複数GPUワーカーへの割当を連携させ、同じバッチに含まれる複数のエージェント処理をまとめて実行する。

中心となる構造は、プロンプトの接頭辞と演算子間の依存関係を一体で保持するテンプレート化基数木（Templated Radix Tree; TRT）である。TRTをもとに、Heliumは先行する演算子の完了を守りながら、共通のプロンプト接頭辞を続けて処理する順序を決める。評価では、複数の定型ワークフローと金融分析の複合ワークフローを使い、Qwen3-8B／14BをH100 NVL 2基で測定した。TradingではKVFlow比で最大1.34倍、基礎ワークフロー群ではKVFlow比で最大1.56倍の高速化を報告する。小規模化した7設定で整数線形計画法の最適スケジュールと比べた際は、提案方式の平均最適性ギャップは0.9%、最大3.6%だった。

## 問題設定

既存の推論器は、モデル呼出しを単位として要求を受け取り、連続バッチ処理やページ単位のKVキャッシュ管理で計算機利用率を高める。一方で、エージェントの処理を組み立てる一般的な実行基盤は、モデル呼出しを不透明な関数として扱うことが多い。前者は上位の処理グラフを知らず、後者はモデル実行状態やキャッシュ利用量を見通せない。この境界をまたいで最適化する仕組みが不足している。

エージェント型のバッチでは、複数の入力に同一のタスク文脈やエージェント指示が現れ、同じ入力や中間出力を使う演算子が複数の枝に存在する。さらに、後段の処理は前段の出力を待つ一方、独立した別の枝は並列に実行できる。要求到着後に観測した接頭辞だけで順序を決める方式では、将来の共通性が見えず、実行順序によっては必要なKV状態が追い出される。反対に演算子単位で全入力を処理すると、バッチ並列性は得られても、別演算子間の共通接頭辞を交互に利用することでキャッシュが入れ替わりやすい。

本研究は、エージェントの制御フローを事前に表せるバッチ型処理を対象にする。各入力は共通のワークフローテンプレートを通り、主な演算はモデル呼出しかローカルデータ処理である。評価はオンプレミスの複数GPUで行い、ワークフロー内では同じ基盤モデルを使う。動的な条件分岐や反復で実行時に処理枝が増減する場合、また外部APIの遅延が大きく不確かな場合は、想定の中心から外れる。

## 手法

### ワークフローのグラフ化と論理計画の書き換え

HeliumのDSLでは、モデル呼出し、データ取得、文字列整形などを演算子として記述する。遅延データフロー方式により、DSLの記述時には実処理を走らせず、各演算子とデータ受け渡しを記録した記号的グラフを作る。実行バッチをコンパイル時にグラフへ結び付けた後、計画の書き換えとスケジューリングを行う。この構成により、処理手順を保ったまま、複数入力にまたがる構造を分析できる。

最初に、使われない枝や恒等演算を除去する。次に共通部分式除去（Common Subexpression Elimination; CSE）を適用し、同じ入力に依存する同型部分グラフを一度だけ実行する形へ統合する。論文のMapReduce型ワークフローでは、複数の専門エージェントが同じ文脈を使うため、共有文脈の準備演算をまとめられる。この段階で計画の重複をなくすことは、演算回数を減らすだけでなく、同じプロンプト接頭辞を検出して再利用するための手掛かりにもなる。

さらに、確定的な演算子の入力から出力を引ける大域プロンプトキャッシュを調べる。演算子の種類と、定数またはキャッシュから解決済みの入力値を基に署名を作り、既存結果に一致すれば演算子を軽量なCacheFetchへ置き換える。出力を再利用できるのは、通常のデータ処理や貪欲サンプリングのLLM呼出しなど、同じ入力で同じ出力が期待できる演算子に限る。キャッシュの追い出しには最長未使用方式を用いる。確率的サンプリングの出力を無条件で使い回す設計ではない。

### 接頭辞と依存関係を統合したTRT

KVキャッシュは、過去に処理したトークン列に対する注意状態を保持し、同じ接頭辞の再プリフィルを省く。TRTは、プロンプト中の固定トークン列と、前段演算子の出力が入る動的な箇所を、基数木の枝として表現する。その葉にはLLM演算子を置き、葉同士を結ぶ依存辺によって、どの演算子が他の出力を待つかも表す。つまり、接頭辞一致を探す木構造と、実行可能性を示す依存グラフを一つの表現にまとめる。

単純に最長の共有接頭辞を持つ要求を先に実行するだけでは、依存関係を壊したり、後で必要となるキャッシュを追い出したりする。論文の例では、先行するエージェントの出力を使う二つの後続呼出しが固定のシステムプロンプトを共有する。依存のない別要求を間に挟むと、共有プロンプトのKV状態が失われ、二度目の後続呼出しで再計算が必要になり得る。TRTは共有と依存を同時に見て、必要な順序を事前に計画する。

固定接頭辞については、次のバッチの実行前にvLLMへ特別な要求を送り、KV状態をあらかじめ計算してGPUメモリへ保持する。HeliumはvLLMを改変し、こうして作った状態を優先してピン留めする。容量が足りない場合のブロック単位の追い出しはvLLMの仕組みに任せ、追い出された接頭辞は次のバッチで再計算する。これにより、受信後に偶然ヒットすることを期待する受動的キャッシュだけでなく、既知のワークフロー構造から有用な共有状態を先に用意できる。

### 依存とキャッシュ局所性を考慮したスケジューリング

スケジューラーは、最適化後の演算子グラフと、別の入力集合で事前に測った各演算子の平均出力トークン数を受け取る。プリフィル時に新たに処理するトークン数は、直前の呼出しとの共通接頭辞によって変わるため、TRT上の共通祖先からの経路を使って見積もる。生成側は出力トークン数に応じたコスト、依存側は前段の完了とバッチ処理上の待ちを反映する遅延として扱い、全呼出しの完了時点を短くする順序を選ぶ。

全要求の厳密な最適化は、入力バッチが大きくなると探索が重くなり、実行時の出力長や連続バッチの挙動も読めない。Heliumは個々の入力要求を列挙して固定順序を作るのではなく、ワークフロー構造を単位にした貪欲な再帰方式を使う。依存の深い枝と早く実行可能な枝を優先するクリティカルパスの考え方を用いて木を深さ優先にたどり、GPUごとに共有接頭辞を持つ演算子をまとめる入れ子の順序を組み立てる。

計画は厳密な実行時刻表ではなく、実行時に多少の順序変更を許す柔らかな予定としてワーカーへ渡される。ある演算子が依存出力を待っている間は、無関係な別枝を動かし、GPUの空きを減らす。共有接頭辞が同じ演算子は同じワーカーで連続処理し、KVの再利用とバッチ形成を両立させる。各ワーカーは準備できた呼出しをまとめて推論器へ送り、依存を守りながらGPUを埋める。

### 実装とプロファイル

試作実装はPythonのDSL、グラフ最適化器、TRT構築器、実行計画生成器、ワーカー群から構成される。各ワーカーは個別のvLLMプロセスを持ち、プロセス間通信のキューで計画と要求を受け渡す。先行計算したKV状態を維持するためvLLMを改変している。スケジューリングに必要な出力長などの統計は、別入力で事前に測定する。論文はこの一回限りのプロファイル費用は、後続ワークフローで償却できるとしている。

## 評価条件と代表結果

評価機はAMD EPYC 9554 64コア、94GB NVIDIA H100 NVLを2基搭載する。Qwen3-8BとQwen3-14Bを用い、各推論器をGPUごとに一つ配置した。HeliumはvLLM v0.16.0、KVFlowは論文のSGLang実装を使い、その他の比較対象には共通の推論サーバーを接続した。全モデル呼出しは貪欲サンプリングで実行する。指標は計画準備から実行までを含むバッチ全体の壁時計時間であり、Heliumについても最適化・スケジューリング時間を含めている。

基礎ワークフローは、複数専門家の出力をまとめるMapReduce、複数エージェントが複数回やり取りする討論、回答と批評を繰り返す振り返り、反復処理、並列処理の5種である。MMLU、TAT-QA、Amazonのレビューを使い、専門家数、討論回数、レビュー断片数などを変える。Heliumはこれらの設定で既存比較対象を上回り、KVFlowより最大1.56倍、Parrotより最大2.21倍高速だった。どの設定でも同じ倍率が得られるわけではなく、論文の最大値は特定のワークフローと入力条件で観測された上限である。

複合評価のTradingワークフローは、株価・企業情報・ニュース・SNSを調べる分析段階、複数の研究役が議論する段階、8系統の投資判断をリスク管理役とファンドマネージャーがまとめる段階からなる。合計19エージェント、88個のLLM演算子を持つ。100銘柄を2日分収集し、1日目をキャッシュの準備、2日目を評価に使う。Qwen3-8Bと14Bでバッチサイズを変えた結果、HeliumはKVFlow比最大1.34倍、LangGraph比最大1.49倍、AgentScope比最大1.46倍、Parrot比最大2.51倍の高速化を報告した。単純な要求単位のvLLM逐次実行と比べた最大差は39.50倍だが、これは複合ワークフローを何もまとめずに処理する基準との差であり、同系統の強いサービング基盤との比較値とは分けて読む必要がある。

Tradingでバッチサイズ16、Qwen3-8Bを使った構成要素除去実験では、完全なHeliumの処理時間は130.14秒だった。共通部分式除去を含む計画整理を外すと160.53秒（23.35%増）、キャッシュ考慮型スケジューリングを外すと153.12秒（17.66%増）、出力プロンプトキャッシュを外すと147.79秒（13.56%増）、先行KVキャッシュを外すと134.76秒（3.55%増）になった。結果からは、先行KV計算だけが主因というより、重複枝の除去とキャッシュを意識した順序制御が大きく寄与し、複数要素を組み合わせて効果が出ると読める。

スケジューリングだけを比較するため、先行KV計算と出力キャッシュを無効にした実験では、Heliumの遅延は149.76秒、キャッシュヒット率は56.5%だった。オンラインで要求を並べ替えるLSPFは188.93秒、37.9%であり、この条件でHeliumは1.26倍速く、ヒット率は32.9%高い。依存グラフの縮小設定7種について整数線形計画法（Mixed Integer Linear Programming; MILP）の解と比べると、Heliumの平均最適性ギャップは0.9%、最大3.6%だった。ただしこれは小規模化した設定での比較で、大規模な任意ワークフローに対する最適性保証ではない。

感度分析では、Tradingのバッチサイズを8から80、判断枝を4から16、討論回数を2から5へ増やし、モデルをLlama-3.1-8B、Qwen3-8B／14B／32Bへ替えても、HeliumはLangGraphに対する優位を保った。共有接頭辞が多くプリフィルが支配的な合成設定では、討論ワークフローで最大2.07倍の差があった。反対に生成側が支配的、または接頭辞が異なる設定でも優位は残ったが、キャッシュ共有から得る利得の大きさは負荷構成によって変化する。

スケジューリング構造のメモリ量は、16枝の設定でHeliumのTRTと付随情報が552 KiB、SGLangのRadixCacheメタデータが14.8 MiBだった。Tradingのバッチサイズ16では、計画最適化・スケジュール生成・TRT構築の合計時間は230ミリ秒未満と報告され、LLM実行時間に比べて小さい。別のトレースでは、HeliumはLangGraphより平均バッチ当たり要求数が1.18倍、中央値の要求遅延を28.3秒から20.5秒、95パーセンタイルを51.7秒から37.2秒へ減らした。これらは実装された評価機と比較設定における観測値であり、すべてのモデル・GPU構成の保証ではない。

## 既存研究との位置付け

KVFlowはエージェントのステップ関係を使い、KVの追い出しと先読みを改善する。Heliumは同じキャッシュ課題に加え、計画の書き換えや決定的な演算子出力の再利用、バッチ全体の順序付けも扱う。SGLangの基数木は入力済み要求の接頭辞を管理するのに対し、HeliumのTRTはまだ実行されていないワークフロー構造と動的な出力位置、演算子の依存もモデル化する。したがって主な差はキャッシュ機構単体ではなく、計画器と実行器の情報をつないで、要求が到着する前にワークフロー全体の共有を使う点にある。

## 適用範囲と限界

評価は貪欲サンプリング、同一基盤モデル、ローカルのデータ操作、複数GPUという範囲に限られる。異なる基盤モデルを演算子ごとに選択する場合、遠隔サービスの待ち時間・制限、ネットワーク越しのツール処理は評価されていない。オンライン要求の構成が事前に不明な環境では、静的な接頭辞を先に温めたり、全体の依存グラフを見て計画したりする利点が小さくなる可能性がある。

DAG表現は条件分岐や反復など、直前のLLM出力で後続の枝数や経路が決まる制御フローを自然には表現できない。外部API呼出しも現状は最善努力で扱い、遅延のばらつきを費用モデルに十分組み込んでいない。将来方向として条件付きループなどの制御フロー表現と確率的な費用モデルが挙げられる。このため、動的なツール主体エージェントを含む一般運用基盤として、そのまま置き換えられるという評価ではない。

また、公式実装は公開されているが、論文の評価は特定の試作環境で行われている。比較には各基盤の標準機能を使った条件と、同一推論器に接続した実装上の調整が混在するため、特定の倍率を一般的なフレームワーク間の固定差とみなすべきではない。最大39.50倍は逐次実行の素朴なvLLM基準に対する値であり、KVFlowとの最大1.34倍と同じ比較強度ではない。加えて、最適性ギャップの小ささは7つの縮小設定と単一ワーカーのMILP比較に基づく。

## まとめ

Heliumは、エージェント処理を個々のLLM要求へ分解して実行する方式の外側に、計画と推論をつなぐサービング層を置く。共通部分グラフの統合と演算子出力キャッシュで不要な実行を減らし、TRTでプロンプト接頭辞と依存関係を表して、先行KV計算と順序制御に使う。複合Trading評価や構成要素除去実験は、効果がキャッシュ単体ではなくグラフ整理とキャッシュ局所性を考慮した順序付けにも強く依存することを示した。評価前にバッチ構造を把握できる分析型エージェントや高い接頭辞共有がある負荷に適する一方、動的制御フロー、確率的出力、遠隔ツールを含む場合は、別途適用可能性を検証する必要がある。
