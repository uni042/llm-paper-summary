# FlowMesh: A Service Fabric for Composable LLM Workflows

> LLMワークフローをDAG演算子へ分解し、完全一致の重複排除・実行互換バッチ化・異種GPU配置・無状態ワーカーを一体化して、金銭コスト1.8〜3.8倍、エネルギー1.3〜2.0倍の改善を示す。

## 概要

LLMの運用は、単一モデルへの1回の推論だけでなく、教師あり微調整（Supervised Fine-Tuning; SFT）、選好学習、報酬モデル推論、評価、エージェントの道具利用などを連結した多段ワークフローへ広がっている。ところがKubernetesやRayのような汎用基盤から見ると、こうした処理は大きなジョブやコンテナとして見えることが多い。同じ基盤モデル・同じ入力・同じ前処理を別利用者が繰り返していても、ワークフロー内部の意味を横断して共有しにくく、GPUの重複計算と過剰確保が生じる。

FlowMeshはこの抽象化を変え、各ワークフローを細粒度演算子からなる有向非巡回グラフ（Directed Acyclic Graph; DAG）として保持する。完全に同じ演算子はタスクハッシュで1回だけ実行し、入力だけが異なる互換処理は実行署名でまとめて連続バッチ処理する。制御面は処理量、GPUの時間単価、すでに重みやキャッシュが載っているかというデータ局所性を同じ効用関数で評価し、バッチと実行ワーカーを同時に決める。実行面は内容アドレス可能ストア（Content-Addressable Store; CAS）を永続状態の中心に置き、ワーカー自体を無状態にするため、負荷に応じた増減とプリエンプション後の再実行を同じ仕組みで扱える。

評価ではLlama-3.1-8B、Llama-3.2-3B、Llama-3.2-1Bを使い、推論・SFT・直接選好最適化（Direct Preference Optimization; DPO）・近接方策最適化（Proximal Policy Optimization; PPO）を含むワークフローを実行した。6台の異種GPU構成では、基準方式に対して金銭コストを1.8〜3.8倍、エネルギー消費を1.3〜2.0倍改善し、コスト遅延積とエネルギー遅延積は2〜10倍改善した。一方、静的に高性能GPUを優先する方式が生スループットではわずかに上回る条件もあり、FlowMeshの強みは最高スループットそのものではなく、共有・異種資源・伸縮性を含む費用効率にある。

## 問題設定

### ワークフローを「大きな1ジョブ」と見ることが問題になる理由

後学習やエージェント処理は、データ準備、モデル推論、評価、更新など依存関係を持つ複数段階で構成される。例えば複数チームが同じ基盤モデルから異なる実験を始めると、初期のSFTや報酬モデル推論が完全に同じになる場合がある。しかしジョブ単位で隔離して実行すると、その共通部分を各ジョブが別々に計算する。

さらに、ワークフロー内の各段階は必要資源が異なる。軽い推論、GPUメモリを大きく使う学習、データ処理を同じGPUクラスへ固定すると、高価なGPUが軽作業に使われたり、逆に必要メモリを満たさず再試行になったりする。要求到着も一定ではないため、ピークに合わせた静的確保はアイドル時間を生み、少なめの確保は待ち行列を増やす。

FlowMeshは、これらを別々の問題として解くのではなく、DAG中の「実行可能になった演算子」をクラスタ全体から見える共通プールへ出し、共有可能性・バッチ互換性・実行場所・ワーカー数を同じ制御面で扱う。

## 手法

### 1. 二つのハッシュで「同一処理」と「一緒に実行できる処理」を分ける

各演算子には、モデルの識別子、正規化したハイパーパラメータ、上流入力の内容ハッシュを含むタスク同一性
`H_task = hash(H_model, canonical(P), H_in,1...n)`
を与える。異なる利用者のDAGで `H_task` が一致すれば、入力まで含めて同じ処理であるため、FlowMeshは計算を最大1回だけ実行する。すでに結果がCASに存在すれば実行自体を省き、その同一成果物を各DAGの下流へ配る。

一方、入力が違えば結果は同じではないので重複排除はできない。それでも同じモデル・同じ設定・同じ資源クラスなら同じ推論器でまとめて処理できる。そこでFlowMeshは入力ハッシュを除いた実行署名
`H_exec = hash(H_model, canonical(P), resource_class)`
も持つ。同じ `H_exec` の演算子は、利用者やDAGが異なっていても1つのマイクロバッチへ統合できる。この二段階を分けることで、「同一結果を再利用すること」と「異なる入力を同じGPU実行に束ねること」を混同せず、各DAGの系譜も保てる。

### 2. 制御面はバッチとGPUを一つの効用関数で同時に選ぶ

通常の構成では、先にバッチを作り、その後で空いているGPUを探すなど、バッチ形成と配置が別々に決まることがある。FlowMeshは実行可能な `H_exec` ごとの集合から候補バッチ (B) を作り、ワーカー (j) との組を評価する。

論文の効用関数は
`U(j,B) = w_t T_eff(j,B) - w_c C(j) + w_l G_loc(j,B)`
である。`T_eff` はそのGPUで予測される実効処理量、`C` はワーカーの正規化コスト率、`G_loc` は必要なモデル重み・アダプタ・トークナイザ・キャッシュがすでにそのワーカーにあることによる局所性利得を表す。さらにVRAM、メモリ帯域、GPU世代、利用者の配置制約などを満たす組だけを実行可能候補とする。

この設計により、対話的処理ではコスト重みを下げて速いGPUを選び、期限の緩い大量ロールアウトでは安いGPUを選ぶ、といった方針を同じ機構で表せる。重要なのは「最速GPUを常に選ぶ」のではなく、現在のバッチと、既に温まっている実行器の状態まで含めて配置する点である。

### 3. 連続バッチ処理で「温まった実行レーン」へ要求を追加する

一度割り当てたバッチを閉じてから次のジョブを待つのではなく、各ワーカーは実行署名ごとの受入キューを持つ。制御面は互換演算子が到着するたび、実行中の長寿命実行器へ追加投入する。ワーカー内部ではvLLMなどの実行系が連続バッチ処理を行う。

これにより、同じモデル重みを何度も読み込み直す必要が減り、複数利用者の小さな要求でもGPU占有率を上げられる。演算完了後は、入力ごとの成果物をCASへ別の内容ハッシュで保存し、対応する元DAGの辺だけを解放する。そのため、バッチ化しても「どの結果がどのワークフローに属するか」は失われない。

### 4. CASと無状態ワーカーで伸縮と障害復旧を同じ経路にする

モデルチェックポイント、アダプタ、入力、報酬値、評価結果などの耐久状態はS3互換CASへ置く。ワーカーは入力をハッシュ参照で受け取り、ローカルに無ければCASから取得し、結果を新しい内容ハッシュとしてCASへ返す。ワーカー側へ唯一の状態を残さないため、増設・停止・置換が容易になる。

障害時は実行中演算子をREADYへ戻し、別ワーカーで同じ入力ハッシュから再実行する。もし統合実行の別経路で結果がすでにCASへ入っていれば再計算も省ける。遅いワーカーへの対策として投機的複製を走らせる場合も、最初に成功した結果だけをCASへ公開し、後着結果を内容同一性で破棄する。

### 5. KubernetesとVast.aiで同じ論理構造を保つ

集中管理クラスタでは、制御面をKubernetesのコントローラとスケジューラ拡張として実装し、待ち行列長を指標に水平Pod自動拡張（Horizontal Pod Autoscaler; HPA）を動かす。CASは共有永続ボリュームまたはオブジェクトストアを使う。

分散GPU市場のVast.aiでは、同じワーカーコンテナを使いつつ、制御面が市場価格と信頼性を取得してインスタンスを借りる。ローカルディスクが一時的なのでCASは外部S3互換ストアへ置く。したがってKubernetesとVast.aiで資源獲得手段は違っても、DAG、ハッシュ、受入キュー、CASという上位設計は共通である。

## 評価

### 評価条件

| 項目 | 条件 |
|---|---|
| ワークフロー | エージェント推論、SFT、DPO、PPO |
| データ | GSM8K、MMLU、TruthfulQA |
| モデル | Llama-3.1-8B、Llama-3.2-3B、Llama-3.2-1B |
| Group A | 5種類のエージェント推論DAG、200ワークフローを抽出 |
| Group B | Group AにSFT/PPO/DPO等の後学習段階を追加 |
| 実行系 | 推論はvLLM、強化学習系はHugging Face TRL |
| バッチ | Group A: 24、Group B: 12 |
| コスト・電力評価 | 6 GPUワーカー。H100 NVL 94GB、RTX 4090 48GB、RTX 4090 24GBを同数構成 |
| 負荷 | Group Aから抽出、到着率を6→0.6要求/分へ指数的に低下 |
| 比較 | MF（モノリシック+First-Fit）、DS（分解+静的配置）、DR（分解+Round-Robin） |
| 大規模性評価 | 最大48ノード、各ノードH100 80GB、同時投入64 |
| 実装環境 | ローカルクラスタ、Kubernetes、Vast.ai |

コスト遅延積（Cost–Delay Product; CDP）とエネルギー遅延積（Energy–Delay Product; EDP）は、単に安い・省電力な方式が極端に遅くなることを避けるため、1タスク当たり費用またはエネルギーと平均時間を掛けた指標であり、低いほど良い。

### 主要結果

| 観点 | 条件・比較 | 結果 | 読み取れること |
|---|---|---|---|
| 金銭コスト | 6台異種GPU、各基準方式比 | 1.8〜3.8倍改善 | 高価なGPUへ固定せず、小型GPUも使う配置が費用を下げる |
| エネルギー | 同上 | 1.3〜2.0倍改善 | 異種GPU利用と不要ワーカー停止が電力面にも効く |
| CDP / EDP | 同一負荷 | 2〜10倍改善 | 安さだけでなく遅延を含めても改善が残る |
| 生スループット | DSとの比較 | DSがわずかに高い条件あり | FlowMeshは最大スループットより費用・電力との均衡を選ぶ |
| 演算子統合の除去 | 24並行エージェント処理 | 遅延1.36倍、コスト1.25倍へ悪化 | 共通処理の統合とバッチ化が独立に効いている |
| 伸縮資源の除去 | 同条件 | 遅延1.21倍、コスト1.78倍へ悪化 | アイドルGPUを抱えないことが特にコストへ効く |
| 多目的スケジューリングの除去 | Round-Robin相当 | 遅延1.33倍、コスト1.24倍へ悪化 | 異種GPUを無作為に使わず用途と局所性を合わせる価値を示す |
| ワーカー障害 | H100を2分後に停止 | 平均遅延+13.3%、検出30.0秒、完遂 | CASと再投入で障害を越えられるが、無コストではない |
| 資源指定誤り | GPUメモリ要求を過小申告 | 平均遅延+5.1%、検出8.6秒、完遂 | 実行失敗後に十分な資源のワーカーへ再配置できる |
| 8→48ワーカー | Kubernetes、Group A | 17→32 task/min | 6倍のGPU追加に対し約1.9倍で、スケールは明確にサブリニア |
| 8→48ワーカー | Kubernetes、Group B | 13→26 task/min | 後学習を含む複雑DAGでも増えるが線形ではない |
| 待ち時間 | Group A、8→48ワーカー | 約400秒→150秒 | 台数増加の主効果は個別処理より待ち行列短縮 |
| Vast.ai伸縮 | 動的負荷 | 生成・停止に30〜60秒の遅れ | 市場API経由の伸縮は即時ではなく、厳しいSLOでは制約になる |

### 評価から見える境界

FlowMeshの利得は、複数ワークフローに共通演算やバッチ互換演算が存在するほど大きい。演算子統合を無効にすると遅延・コストが悪化した結果は、この設計意図と対応している。一方、各DAGが完全に異なり共有機会が少ない場合には、この部分の利得は小さくなる。

大規模性評価も重要な負の結果を含む。8から48ワーカーへ6倍に増やしてもGroup Aの処理量は17から32 task/minであり、線形には伸びない。論文自身もKubernetesのオーバーヘッドが無視できないと述べている。またVast.aiでは資源追加・解放に30〜60秒の遅れがあり、短いバーストへ即応する用途では伸縮制御だけで待ち時間を消せるわけではない。

## 既存研究との差

vLLMやSGLangはモデル単位の推論サーバ内部で、KVキャッシュ管理やバッチ処理を改善する。一方FlowMeshが見る単位は、その上位にある「複数利用者の複数DAG」である。推論器自体を置き換えるのではなく、vLLMをワーカー内部に使いながら、どのワークフローのどの演算子を同じ実行器へ流すかを決める。

RayやDaskは動的タスクグラフを扱えるが、論文が狙うのはLLMワークフロー固有のモデル常駐、異種GPU、実行互換性、系譜を利用した横断共有である。JellyBeanのように演算子へ分解して異種資源へ置く方式に対しても、FlowMeshは静的役割分担ではなく、複数DAGを横断した完全一致重複排除、連続バッチ化、動的ワーカープールを同時に扱う点が異なる。

## 限界・実装状況

論文は2025年10月のarXivプレプリントで、本文自身が予備研究・査読中と記載している。評価はローカルクラスタ、最大48台のKubernetesクラスタ、Vast.aiで行われており、複数環境で実装を示しているが、巨大な本番マルチテナント基盤での長期運用実績を示すものではない。

共有利得はワークロード間の重複度に依存する。完全一致再利用は `H_task` が一致する必要があり、意味的に似ていても入力や設定が異なれば同じ結果としては再利用しない。これは誤共有を防ぐ一方、共有可能性の上限にもなる。

CASへ耐久状態を寄せる設計は復旧を単純化するが、重みや中間成果物の取得コストが消えるわけではない。局所性項でその転送を避けようとする設計なので、オブジェクトストア帯域や地域間ネットワークが弱い環境では配置判断の重要性が増す。

スケールアウトはサブリニアで、KubernetesのオーバーヘッドとVast.aiの30〜60秒の確保遅延が測定されている。したがって、数秒単位の厳しいサービス品質目標（Service-Level Objective; SLO）へ外部GPU市場の伸縮をそのまま使えるとは評価されていない。
