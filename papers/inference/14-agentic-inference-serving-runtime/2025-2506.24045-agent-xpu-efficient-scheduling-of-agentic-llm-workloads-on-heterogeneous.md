# Agent.xpu：異種統合チップ上で反応型と背景型の言語モデル処理を協調させる

## 概要

Agent.xpuは、個人端末で複数の言語モデル利用エージェントを同時に動かす際、中央処理装置、統合画像処理装置、ニューラル処理装置を協調させる推論実行基盤である。個人用エージェントには、ユーザーの入力にすぐ応答する**反応型**と、通知の監視や文書整理を継続する**背景型**がある。これらは単発の推論要求ではなく、入力処理、逐次生成、外部ツール待ち、再開を繰り返す長寿命の処理系列である。従来の端末推論エンジンは単発実行や固定的な演算配置を前提とするため、背景型の処理がアクセラレータを占有すると反応型の待ち時間が伸びる。

Agent.xpuは、演算子ごとの装置適性を測った異種実行グラフ、入力処理と逐次生成の段階別配置、共有主記憶の帯域競合を考慮した同時実行、反応型を優先する細粒度の割込み、余裕時間に背景型を実行する相乗り処理を組み合わせる。Intel Core Ultraの実機でLlama系列の3B・8Bモデルを使い、背景型だけの負荷では統合画像処理装置単独比で最大2.4倍、静的なニューラル処理装置・統合画像処理装置の直列実行比で最大4.9倍の処理能力を報告した。反応型と背景型の混合負荷では、統合画像処理装置単独比で反応型遅延を**91～97%短縮**しつつ、背景型処理能力を**0.3～58%改善**した。原著の比較条件を明記し、最大値をすべての装置に共通する性能と誤解しないようにする。

## 問題設定

端末内の統合チップは、CPU、統合GPU、NPUなどの計算資源を備える。NPUは事前に形状が決まった密な演算を効率よく処理しやすいが、可変長系列や動的なバッチ、複雑な制御には制約がある。一方、統合GPUは柔軟だが、画面描画との競合や電力効率の問題がある。さらに両者は主記憶を共有するため、単純に同時実行させると帯域が飽和し、メモリ読出しの多い演算が互いを遅くする。この非対称な競合は、独立した専用メモリを持つ複数のデータセンターGPUとは異なる。

言語モデルの入力処理段階では、多数の入力トークンをまとめて処理するため、行列積の演算密度が高い。逐次生成段階では、毎回一トークンを出すため、重み読出しとメモリ帯域の負担が大きくなりやすい。同じモデルでも段階によってNPUと統合GPUの有利不利が変わる。原著の計測では、入力処理はバッチを増やしても計算資源を既に使い切っているため追加利得が小さく、逐次生成はバッチ化で処理能力が伸びるものの、一つの要求の遅延は他要求の長さとバッチ規模に影響される。

反応型フローはユーザーの待ち時間が重要で、背景型フローは期限内に一定量の仕事を進めることが重要である。背景型を優先せずに長時間走らせると反応型の遅延が増える。一方、反応型だけを常に最優先すると背景型が飢餓状態になる。したがって単純な先着順や固定的な優先度だけでは、応答性と総処理能力を両立しにくい。Agent.xpuは演算子の配置、段階別の資源配分、要求の優先度を同時に調整する。

## 手法

### 異種実行グラフによる演算子適性の記録

最初に、モデルを構成する演算子をNPUと統合GPUで実行したときの時間、対応可能な形状、メモリ負荷などをオフラインで測定する。この情報を異種実行グラフ（HEG）に記録し、演算子をどちらの装置へ置くと効率的かを推定できるようにする。実行グラフには、静的な配置候補だけでなく、実行時に束縛を変更できる演算単位と予測費用を持たせる。これにより、モデル全体を一定比率で分割するのではなく、入力長、生成段階、他のフローの負荷に応じて実行装置を選び直せる。

NPUは対応する行列演算に高い効率を示すが、形状変更や実行グラフの準備には費用がある。統合GPUは短い処理や動的な演算に柔軟に対応できる。異種実行グラフは、どの演算をどちらに置くかを毎回ゼロから探索する費用を避けつつ、変化する負荷へ対応するための中間表現である。ただしオフライン測定は装置依存なので、別のチップやドライバへ移す際には再計測が必要になる。

### 入力処理と逐次生成の段階別配置

Agent.xpuは、入力処理と逐次生成を同じ装置配分で固定しない。入力処理は大きな行列演算をNPUへ割り当てやすく、逐次生成は統合GPU上で継続的なバッチ処理を行う方が適する場合がある。そこで、入力処理の一部をNPUへ移しつつ、逐次生成は統合GPUを中心に実行する。要求が段階を切り替えるたびに、実行グラフの束縛と待ち行列の優先度を更新する。

主記憶の帯域競合も配置判断に含める。二つの装置が同時に大きな重みを読み込むと、計算資源が空いていても主記憶帯域が律速になる。したがって「常にNPUと統合GPUを同時に動かす」ことは最適ではない。計算律速の入力処理と帯域律速の逐次生成を組み合わせる、あるいは同時実行のタイミングをずらすことで、競合を抑えながら処理を重ねる。原著の装置計測に基づく段階弾性が、単純な静的テンソル分割との差である。

### 反応型の細粒度割込み

反応型の要求が新しく到着したとき、背景型が大きな演算やバッチを終えるまで待たせると、ユーザーの体感遅延が大きくなる。Agent.xpuは演算子・カーネルの小さな単位で背景型の実行を中断し、反応型を先に処理する。統合チップの共有メモリ空間を利用して、装置間の状態コピーをできるだけ避けながら切り替える。割込みは要求単位だけでなく、入力処理と逐次生成の双方に適用される。

ただし背景型の進行を完全に止めてしまうと、反応型要求が続く環境で背景型が飢餓状態になる。そこで反応型の遅延目標までに残る余裕を推定し、その範囲へ背景型の演算を相乗りさせる。反応型の応答を遅らせない程度の余裕がある場合には、統合GPUのバッチへ背景型を追加する。背景型の入力長や残り生成長を考慮し、長い背景要求が反応型の期限を圧迫しないようにする。

### 背景型の相乗りと可変バッチ

背景型フローは処理能力を重視するため、複数の要求をまとめて逐次生成する利点が大きい。しかしバッチを無制限に増やすと、反応型の一要求が待つ時間も増える。Agent.xpuは反応型を無条件に優先して受け入れ、背景型についてはバッチ容量や反応型の有無、各要求の長さを見て追加する。原著の擬似コードでは、反応型要求を優先して次の生成バッチを組み立て、残りの余地へ背景型を加える。

この仕組みは、反応型の遅延を短くするために背景型を常に停止するのではなく、負荷が低い瞬間に背景型を進める。予測される余裕時間が小さいときは背景型を抑え、余裕が大きいときは同時処理を増やす。効果は要求の到着率や入力長、生成長の分布に依存し、背景型の処理能力がどの程度改善するかは負荷構成によって変わる。

### 実装の構成

原著は、要求の優先度を受け取る前面の接口を約2300行のPythonで実装し、背後の推論実行部を約6000行のC++で実装したと説明する。実装はIntel Core Ultra向けのOpenVINO 2025.2の低水準APIを利用し、NPUと統合GPUの非同期起動・完了待ちを制御する。入力処理と逐次生成のイベントループを別に持ち、スレッド安全な待ち行列を通じて連携する。演算内部の分割と要求間の並列性を別々に制御するため、単一の静的な演算グラフだけでは扱いにくいフロー間の優先度を表現できる。

## 評価条件

| 観点 | 原著の条件 |
|---|---|
| 実機 | ASUS NUC 14 Pro+、Intel Core Ultra 5 125H、主記憶64GB DDR5 |
| 基盤 | Ubuntu 24.04、Intel Arc統合GPU、Intel AI Boost NPU |
| モデル | Llama-3.2-3B-Instruct、Llama-3.1-8B-Instruct |
| 数値形式 | 重み8ビット・活性16ビットの量子化。比較方式も同じ精度 |
| 背景型負荷 | ProactiveBench、SAMSum、CNN/DailyMail |
| 反応型負荷 | LMSys-chat-1M、MTRAG、関数呼出しベンチマーク |
| 到着モデル | 元データに時刻がないため、毎分1～30要求のポアソン到着を合成 |
| 評価期間 | 条件ごとに15分の要求列を作成 |
| 比較方式 | Llama.cppのCPU実行、OpenVINOの統合GPU実行、静的なNPU・統合GPU直列実行 |
| 指標 | 正規化された要求遅延、反応型の90パーセンタイル遅延、統合GPU利用率、トークン当たり消費エネルギー |

比較方式の精度をそろえることで、量子化の強さが異なるために速度が変わるという交絡を減らしている。反応型の90パーセンタイル遅延は、平均だけでは見えないユーザー待ちの長い側を評価するための指標である。一方、正規化遅延は入力と出力のトークン数を考慮した尺度であり、単純な要求件数や最高トークン毎秒と同一ではない。

## 評価結果

### 背景型だけの負荷

背景型だけの要求列では、Agent.xpuはOpenVINOの統合GPU専用配信より**1.2～2.4倍**の処理能力を達成し、静的なNPU・統合GPU直列実行に対しては**1.4～4.9倍**と報告する。SAMSumのように比較的短い入力と出力を持つ課題では、Llama-3Bで統合GPU専用比2.0～2.4倍となる。ProactiveBenchやCNN/DailyMailでは、同じ正規化遅延目標に対して処理可能な要求数が約20%増える条件がある。8Bモデルでは計算負担が大きいため、異種装置へ分散する利点が強く現れる。

Llama.cppのCPU実行は逐次生成では有利な場面があるが、長い入力処理に弱い。静的なNPU・統合GPU直列実行は、両装置の演算を重ねにくい。OpenVINOの統合GPU実行は連続バッチで処理能力を伸ばすが、NPUを同時に利用できない。Agent.xpuは同じ低水準演算カーネルを利用しながら、段階別の異種配置と同時実行によって差を生む。これはカーネル単体の演算速度が劇的に変わった結果ではない。

### 反応型と背景型の混合負荷

反応型と背景型の両方を流した場合、原著は統合GPU専用の比較方式に対して、反応型の要求遅延を**91～97%短縮**し、同時に背景型の処理能力を**0.3～58%改善**したと報告する。反応型の優先度を高くするだけなら背景型の進行が止まる可能性があるが、Agent.xpuでは細粒度の割込みと余裕時間の相乗りを組み合わせるため、両方の指標で改善を狙える。

原著図11は反応型の毎分到着率を変えながら背景型の到着率を増やした場合を比較する。反応型要求が多くなるほど背景型へ使える余裕が減るため、改善幅は一定ではない。反応型遅延の大きな改善と背景型処理能力の小さな改善が同時に起こる条件もあり、最大値だけで全負荷を代表させるべきではない。反応型の遅延目標を優先する設計なので、背景型だけの最高処理能力と混合負荷での処理能力を同じ条件として扱わない。

### エネルギーと画面描画への影響

原著は統合GPU専用配信との比較で、トークン当たりのエネルギー消費を約26.8%減らす結果を報告する。また静的なNPU・統合GPU方式との比較を含む条件で、統合GPUの利用率を約32.5%低下させる。これはNPUへ適した演算を移すことで、統合GPUを常時占有せずに済むためである。統合GPUは画面描画にも使われるので、利用率を抑えることは描画への干渉を減らす点でも意味がある。ただしエネルギーと利用率の改善は比較相手が同一とは限らず、同じ百分率を一つの万能な削減効果として並べてはいけない。

### 感度と比較の解釈

入力処理と逐次生成は演算の性質が異なる。入力処理では単一要求でも高い演算密度が得られ、バッチを増やしても追加利得が小さい。一方、逐次生成では複数要求をまとめるとメモリ読出しを共有しやすいが、一つの反応型要求の待ち時間が増えやすい。Agent.xpuはこの違いを利用して段階ごとに配置とバッチ化を変える。単にNPUと統合GPUを同時に起動する方式では、共有主記憶の帯域競合で遅くなる場合があるため、演算子の種類と帯域使用量を考慮する必要がある。

評価はIntel Core Ultra 5 125Hの一種類の実機を中心とし、量子化された3B・8Bモデルと合成到着列を用いる。より新しい端末、別ベンダーのNPU、独立したGPUメモリを持つ構成では、演算子適性と共有帯域の競合が変わる。原著の改善率は、この実機と評価条件に基づく結果である。

## 既存方式との差

データセンター向けの配信基盤は、主として同種GPU群の連続バッチ、鍵・値キャッシュ、要求の優先度を最適化する。端末向けの異種実行は、モデルの層やテンソルをNPUと統合GPUへ静的に分けることが多い。Agent.xpuは、モデル内の演算子適性、入力処理と逐次生成の段階差、共有主記憶の帯域競合、ユーザーの待ち時間と背景仕事の進行を同じ実行時制御で扱う。これにより、背景型が存在するから反応型が遅くなるという単純な二者択一を緩和する。

また、演算の種類に応じて装置を選び直すため、モデルの重みを追加学習する必要はない。効果は実行時の配置とスケジューリングによって得られ、量子化や疎注意と組み合わせられる。ただし個々の演算子の性能予測が誤ると、適切でない配置を選んでしまう可能性がある。

## 限界

第一に、装置適性の事前測定が必要であり、別のチップやドライバへそのまま移植できるとは限らない。第二に、NPUと統合GPUが共有主記憶を使うという構成に最適化しているため、独立メモリを持つデータセンターGPU群では前提が異なる。第三に、反応型要求が極端に多いと背景型の相乗り余地が小さくなり、背景型の処理能力が制約される。第四に、予測した余裕時間や演算費が外れると、背景型を挿入したことで反応型の遅延が増える可能性がある。第五に、評価では元データに時刻がないため合成した到着列を用いており、現実のすべての個人エージェント利用履歴を再現しているわけではない。

第六に、実機評価は主としてLlama系列3B・8BとIntelの統合チップである。大きな混合専門家モデル、別のNPU、異なる量子化形式、外部ツール待ちが極端に長い処理系列での性能は別途検証が必要である。反応型遅延を91～97%短縮した結果は強いが、端末のあらゆる負荷で常に同じ短縮率を保証するものではない。
