# Optimizing Agentic Language Model Inference via Speculative Tool Calls

> ツール呼出しを「LLMが確定してから実行する」直列経路から外し、小型モデルが次の呼出しを先読みして外部処理を本体生成と重ねる。クライアント側だけでも6〜21%の時間短縮を報告し、ツールが短い条件では推論エンジン統合がさらに2〜3%を削る。

## 書誌情報

Daniel Nichols、Prajwal Singhania、Charles Jekel、Abhinav Bhatele、Harshitha Menonによる2025年12月17日投稿のプレプリントで、arXiv識別子は2512.15834である。対象はツール利用エージェントのエンドツーエンド推論で、通常の投機的デコード（speculative decoding）が「次トークン」を先読みするのに対し、本論文は「次のツール名・引数とその実行」を先読みする。

## 概要

ツール利用エージェントでは、本体モデルが思考・生成を進め、ツール呼出しを出力し、外部APIやコード実行が終わるまで停止し、結果をプロンプトへ追加して再び推論する。この直列化では、ツール実行が1〜3秒かかればGPU側の生成と重ならず、その時間がほぼそのまま応答時間へ加算される。さらに一般的なクライアント実装ではツール待ちの間に要求を推論エンジンから外すため、復帰時に接頭辞を再処理したりKVキャッシュを再構築したりする費用も生じる。

提案は二段階である。クライアント側投機では、小型の投機モデルが本体モデルより早く「次に呼ぶツールと引数」を予測し、そのツールを非同期に開始する。本体モデルが同じ呼出しへ到達すれば既に進んでいる、または完了した結果を使い、外れれば投機結果を捨てて通常経路へ戻る。最終的なツール選択は本体モデルが決めるため、読み取り系ツールなら回答意味を変えずに待ち時間だけを隠せる。

エンジン統合方式ではさらに、投機ツール呼出しをドラフトトークン列として本体モデルで検証し、要求をアクティブな推論バッチとKVキャッシュに残す。「ツールキャッシュ（tool cache）」APIへ先行実行結果を登録し、呼出しが確定した時点で一致する結果を直接継続生成へ接続する。これによりツール待ちだけでなく、要求を退避・再投入する境界費用も減らす。

Berkeley関数呼出しリーダーボード（Berkeley Function Calling Leaderboard; BFCL）由来のタスクと制御したツール遅延で、クライアント側投機はエンドツーエンド時間を6〜21%短縮した。エンジン統合はツールが0〜1秒程度で本体生成中に完了する条件でさらに2〜3%を削減する。一方、ツール自体が長い条件では、追加のエンジン統合利得はほぼ消える。つまり本手法の価値は「投機モデルの精度」だけでなく、本体生成時間とツール遅延の重なり方で決まる。

## 背景：通常の投機的デコードでは外部ツールの待ち時間は消せない

通常の投機的デコードは、小型ドラフトモデルが複数トークンを先に生成し、大型ターゲットモデルがまとめて検証する。受理されたトークン分だけ大型モデルの逐次デコード回数を減らせるが、ツール呼出しが確定した後に外部サービスを待つ時間は別問題として残る。

エージェントでは、例えば本体モデルが「天気APIを東京で呼ぶ」というJSONを最後まで生成した後でAPIを開始する。ツール結果を得るまで次の生成へ進めないので、生成時間を短くしても外部待ちが支配的なら全体速度はあまり上がらない。本論文は、ツール呼出しそのものを投機対象にして「本体が呼出しを確定する時間」と「外部ツールが動く時間」を重ねる。

理想化すると、本体がツール呼出しへ到達するまでの生成時間をG、ツール実行時間をTとしたとき、直列実行は概ねG+Tを要する。完全に正しい投機を直ちに開始できれば必要時間は概ねmax(G,T)となり、GとTが同程度のとき理論上の利得が最大になり、上限は約2倍になる。どちらか一方が極端に長ければ、短い側を隠しても改善率は小さくなる。

## 問題設定

入力は、会話履歴と利用可能なツール仕様を受け取り、途中で一つ以上の外部ツールを呼ぶエージェント推論である。最終出力は従来と同じ本体モデルの判断に従わせながら、ツール待ちと推論エンジン境界のオーバーヘッドを減らしたい。

投機には追加費用もある。小型モデルを別GPUまたはAPIで動かす費用、誤ったツールを先に実行する費用、複数候補を投機する場合のAPI呼出し数増加が発生する。したがって「命中率を最大化する」だけでなく、投機モデルの速度・価格、ツール遅延、本体生成時間、副作用安全性を同時に考える必要がある。

## 手法

### 1. クライアント側投機：小型モデルの予測と本体推論を並行する

クライアントは本体モデルへの要求とほぼ同時に、小型モデルへ次のツール呼出し候補を生成させる。投機モデルがツール名と正規化可能な引数を返したら、そのツールを非同期で開始する。本体モデルの出力を待って、実際の呼出しと投機結果が一致すれば先行結果を利用する。

一致しなければ、投機結果は破棄して本体モデルが指定した本来のツールを実行する。したがって読み取り専用ツールであれば、誤投機は主に追加計算・追加API費用として現れ、回答品質を直接変えない。複数候補を同時投機すれば命中率を上げられるが、ツール実行数と投機モデル費用も増える。

### 2. 複数投機で命中率と費用を交換する

評価ではxLAM-2の1B、3B、8Bを投機モデルとして使い、1回のターンで1/3/5/7/9候補を生成する。8Bモデルはツール呼出し精度が約80%で、大きいモデルほど単発命中率は高い。一方、小さい1Bでも候補数を増やすと命中率を大きく押し上げられ、1候補から9候補に増やすとヒット率は約60%相対改善した。

ただし候補数を増やす利得は無償ではない。外部ツールが有料APIなら誤候補分の課金が増え、副作用のあるツールならそもそも並列投機できない。投機数は「追加呼出しの限界費用」と「ツール待ちを隠せる確率」の交換として決める必要がある。

### 3. エンジン統合：投機呼出しをドラフトとして検証し、系列を常駐させる

エンジン統合版はカスタムvLLMへツールキャッシュAPIを追加する。クライアント側で投機ツールを実行したら、要求IDと正規化したツール呼出しをキーとして結果をサーバ側へ登録する。推論中にツール呼出し開始を検出すると、投機モデルの予測した呼出し文字列をドラフトトークンとして注入し、通常の投機的サンプリングと同様に本体モデルで検証する。

予測が正しければ、ツール呼出しを一文字ずつ最後までデコードする必要を減らせる。さらに一致するツール結果がキャッシュへ既に届いていれば、系列を推論エンジンから退避せず、現在のKVキャッシュへ結果を接続して次の生成へ進める。予測が外れたり結果が未着なら通常経路へフォールバックする。

この構造の重要点は、ツール実行そのものより短い境界処理も削ることである。通常実装では「ツール呼出しを出力→バッチから削除→クライアントでツール実行→長くなった履歴を再投入→接頭辞を再プリフィル」という経路になりやすい。常駐方式はこの再投入・再プリフィルを避ける。

### 4. どの遅延領域で効くか

クライアント側投機は、ツールが遅いほど隠せる絶対時間が増える一方、本体生成より長過ぎる部分は結局待つ。エンジン統合の追加効果は逆に、ツールが本体推論中に完了する短遅延領域で目立つ。論文では0〜1秒程度のツールで追加2〜3%が見られ、ツールが長くなるとクライアント側投機が支配して差が消える。

したがって「投機的ツール呼出し」と「エンジン統合」は同じ効果を二重に足しているわけではない。前者は主として外部待ちの重畳、後者はツール呼出しトークンのデコードとKV/再プリフィル境界の削減を狙う。

## 既存研究との差

通常の投機的デコードは、同じ出力分布を保ちながら将来トークンを小型モデルで先読みする。本論文は予測対象をエージェントのツール呼出しへ広げ、予測が当たったとき外部世界の処理まで前倒しする。ボトルネックがGPUデコードではなく外部I/Oに移ったエージェント型推論に合わせた拡張とみなせる。

またクライアント実装だけで終わらず、推論エンジンにツールキャッシュという明示的な境界を追加し、ツール待ち中も系列とKVを管理対象に残す点がシステム上の差である。これは「ツール呼出しをアプリケーション層の完全な中断」として扱う一般的なエージェント基盤に対し、推論サーバ自身がツール状態を認識する設計である。

## 限界・実装状況

第一の制約は副作用である。検索、読み取りAPI、純粋関数は誤投機を捨てやすいが、送金、メール送信、データ更新のような操作を誤って先行実行すると取り消せない。実運用では投機可能ツールを副作用なしの操作へ限定するか、準備と確定を分離できるトランザクション設計が必要になる。

第二に、利得はツール遅延と本体生成時間の比へ強く依存する。ツールが極端に短ければ投機オーバーヘッドの割合が増え、極端に長ければ隠せない残余待ち時間が支配する。投機モデルが遅い、または精度が低い場合も先行開始が間に合わず効果が縮む。

第三に、評価のツール遅延は主にキャッシュ済み代表出力へ人工的な遅延を付けて制御している。少数の実ツール確認で傾向が変わらなかったと報告するものの、現実のAPIでは遅延の裾、エラー、レート制限、課金、副作用が同時に発生する。さらにエンジン統合評価はvLLM側のバッチ投機オーバーヘッドのため並行度1中心であり、大規模多重化サーバでの追加利得は未確定である。
