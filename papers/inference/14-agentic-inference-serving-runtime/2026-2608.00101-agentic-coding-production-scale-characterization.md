# Agentic Coding in the Wild: Characterizing GitHub Copilot Traces at Production Scale

> 1350万GitHub Copilotセッションを解析し、直列的なLLM↔ツール連鎖、入力偏重、KVキャッシュの境界崩壊、長いターン間遊休を定量化してエージェント向け資源管理の設計根拠を示す。
## 書誌情報
- **著者**: Banruo Liu, Haoran Qiu, Íñigo Goiri, Rodrigo Fonseca, Ricardo Bianchini, Esha Choukse
- **著者・所属**: University of Illinois Urbana-Champaign; Microsoft Azure Research; Microsoft Azure
- **公開**: arXiv
- **種別**: プレプリント
- **対象**: エージェント推論、実運用ワークロード、KVキャッシュ、資源回収、コーディングエージェント
- **実装**: 匿名化クライアント側テレメトリを再構成・集計する解析基盤と、ターン境界の遊休時間を予測するLightGBM量子回帰器12本の約2MBアンサンブルを実装。衛生化したトレースは将来公開予定と記載され、論文時点で公開データURLは未提示。
## 概要
GitHub Copilotの実運用テレメトリを用い、コーディングエージェントが従来の独立・短時間・状態なしのLLM要求とは異なる負荷を作ることを定量化した研究である。2026年6月の1週間から320万ユーザー、1350万セッション、7.605億LLM呼出し、7.747億ツール呼出しを解析し、LLMとツールがほぼ1対1で直列連鎖すること、呼出しの87%がエージェント起点であること、入力が中央値68Kトークンに対し出力247トークンと極端に入力偏重であることを示す。ターン内ではKVキャッシュ再利用が高い一方、ターン境界・モデル切替・文脈圧縮で再利用率が崩れる。さらにターン境界の長い遊休時間を予測する軽量モデルを作り、総遊休時間の86〜90%を捕捉できることから、エージェント向け基盤ではセッション単位のキャッシュ・コンテナ資源管理が必要だと論じる。

本研究の新規性は、GitHub Copilotのコーディングエージェントについて、2026年6月の1週間にわたる匿名化実運用テレメトリをセッション・利用者ターン・個別ステップの三階層へ再構成し、1350万セッション規模でエージェント負荷を体系的に測定した点にある。単なる利用量集計ではなく、LLM↔ツールの連鎖、並列度、ワークフロー類型、入力／出力トークン非対称性、KVキャッシュのターン境界・モデル切替・文脈圧縮による劣化、利用者類型別の再プリフィル費用、コンテナとKVキャッシュの遊休時間まで結び付ける。さらに観測結果からターン境界を資源回収信号として使う軽量遊休時間予測器を構築し、測定を具体的な配信設計へ接続する。
## 問題設定
vLLMやSGLangに代表されるLLM配信基盤は、短時間で独立した要求を単位にスケジューリング、連続バッチ化、KVキャッシュ管理を行う。一方、コーディングエージェントは一つの利用者入力から複数のLLM呼出しとファイル読出し、編集、ビルド、端末実行などのツール処理を自律的に連鎖させ、数分から数時間にわたり状態を持つ。既存のエージェント配信研究はこの構造を利用したキャッシュ保持やワークフロー認識スケジューリングを提案しているが、多くはSWE-bench等の合成・小規模負荷で評価されており、実運用で呼出し深さ、キャッシュ再利用、ツール待ち、失敗再試行、利用者差がどの程度あるか不明だった。そのため最適化の前提自体が本番負荷と一致しているかを検証する大規模測定が必要である。
## 新規性
本研究の新規性は、GitHub Copilotのコーディングエージェントについて、2026年6月の1週間にわたる匿名化実運用テレメトリをセッション・利用者ターン・個別ステップの三階層へ再構成し、1350万セッション規模でエージェント負荷を体系的に測定した点にある。単なる利用量集計ではなく、LLM↔ツールの連鎖、並列度、ワークフロー類型、入力／出力トークン非対称性、KVキャッシュのターン境界・モデル切替・文脈圧縮による劣化、利用者類型別の再プリフィル費用、コンテナとKVキャッシュの遊休時間まで結び付ける。さらに観測結果からターン境界を資源回収信号として使う軽量遊休時間予測器を構築し、測定を具体的な配信設計へ接続する。
## 手法
### 手法のあらまし
入力データはVisual StudioとVS Code上のGitHub Copilotコーディングエージェントから得た匿名化テレメトリで、各LLM呼出しとツール呼出しの時刻、所要時間、入力・出力トークン数、モデル名、ツール名、成功／失敗状態を含む。プロンプト本文、モデル出力、ソースコード、ツール引数、利用者識別可能情報は収集しない。匿名化された利用者・セッション等の識別子を用いて関連イベントを結合し、セッションを全タスク期間、ターンを一つの利用者入力から最終応答までの自律連鎖、ステップを一回のLLMまたはツール呼出しとして再構成する。次に各階層で呼出し数、期間、トークン量、同時実行度、ツール構成、失敗率を集計し、ターンをツール構成・LLM深さ・トークン量・実行特性から六つのワークフロー類型へ分類する。LLM側ではプロンプト中のキャッシュ済みトークン比率を追跡し、ターン内位置、ターン境界、モデル切替、文脈圧縮の前後でKVキャッシュ再利用率がどう変わるかを測る。利用者単位では行動を五類型へ分け、キャッシュミス時に必要な再プリフィル量やコンテナ状態量の違いを比較する。さらに連続するツール呼出し間をコンテナ遊休、連続するLLM呼出し間をKVキャッシュ遊休と定義し、ターン内とターン間で分布を分離する。ターン間の長い遊休が資源回収機会になるため、各ターンの所要時間・呼出し数・失敗率、セッション内位置・過去遊休時間、曜日等を特徴量にLightGBM量子回帰器を学習し、遊休時間の生存曲線を推定する。資源管理側は任意の時点で一定時間以上遊休が続く確率を参照し、KVキャッシュのDRAM／ディスク退避、保持優先度、ツールコンテナ休止の判断へ使える。最終出力は単一の性能値ではなく、エージェント負荷の構造的統計と、どの境界でどの資源を保持・回収すべきかという設計指針である。

### 三階層の実運用トレース再構成
匿名化されたイベントをセッション、利用者ターン、ステップへ再構成する。セッションはコーディング作業全体、ターンは一つの利用者入力からエージェントが制御を返すまで、ステップはLLM呼出しまたはツール呼出しである。この階層化により、単純な要求数では見えない自律連鎖の深さと状態継続を測れる。各ターンは必ず利用者起点LLM呼出しで始まり、その後はエージェント起点のLLM／ツール処理が続くため、呼出し起点を区別して自律度を算出できる。さらに壁時計時間の重なりからLLM並列度を測り、ツール構成・LLM深さ・トークン量・失敗を使って六つのワークフロー類型を抽出する。これにより、失敗再試行を含む深いループが少数でも計算量を大きく増幅することを、通常の読み取り中心ターンやLLM単独ターンと分離して評価する。

### セッション構造に沿ったKVキャッシュ寿命解析
各LLM呼出しのプロンプトトークンとキャッシュ済みトークンを使い、同一ターン内で共有接頭辞が蓄積される過程と、構造イベントで再利用が崩れる過程を分けて測る。ターン内では前の推論・ツール結果が次のプロンプトへ追加されるため接頭辞再利用率が高くなる一方、利用者入力を待つターン境界では時間経過による追い出しが起こる。さらに別モデルへ切り替わるとモデル間でKV状態を共有できず、文脈圧縮では古い履歴を要約・削除して接頭辞自体を書き換えるため、ほぼコールドスタートになる。研究はこれらを別イベントとして前後比較し、平均再利用率だけでは隠れるキャッシュ寿命を明らかにする。利用者類型ごとの再プリフィル量も測ることで、同じ追い出し一回でも深いループ利用者とチャット中心利用者では費用が約50倍異なることを資源管理へ接続する。

### ターン境界を使う遊休時間予測と資源回収
エージェントはLLM推論中にツール用コンテナが遊び、ツール実行中や利用者待ち中にはKVキャッシュが遊ぶため、二種類の遊休時間を別々に定義する。測定するとターン内の遊休は秒単位で短く、ターン間は分単位以上へ跳ねるため、ターン境界を資源回収判断点とする。境界ごとにターンの所要時間、LLM／ツール数、トークン量、失敗率、セッション内ターン番号、過去の平均遊休、直前遊休、曜日などを特徴量化し、12個のLightGBM量子回帰器から遊休時間の生存曲線を構成する。単一点予測ではなく一定時間を超えて遊休が続く確率を返すため、運用側はKVキャッシュ退避やコンテナ休止の費用に合わせて閾値を変更できる。時間経過後も条件付き生存確率を閉形式で更新でき、モデル再実行を必要としない。

### 全体のデータ／制御の流れ
本論文は新しい配信エンジンそのものではなく、実運用観測から配信基盤の設計単位を『個別要求』から『状態を持つセッション／ワークフロー』へ変える根拠を構築する。測定、キャッシュ寿命解析、利用者類型化、遊休予測を連結し、ターン内では状態を積極保持し、ターン境界では予測と利用者特性に応じてKVキャッシュやコンテナを退避・休止する階層的な運用像を導く。
## 評価条件
- **ハードウェア**: 本研究は配信サーバのGPU性能測定ではなくクライアント側実運用テレメトリの解析であり、推論基盤のGPU型、GPU利用率、キュー長、バッチサイズ、メモリ圧力は取得しない。遊休予測器のみ16-vCPU AMD EPYC 7763単一ノードで学習し、約2MBの12モデル構成を用いる。
- **ソフトウェア**: GitHub CopilotコーディングエージェントのVisual Studio／VS Codeテレメトリを解析する。観測期間は2026年6月第1週で、27以上のLLMモデルと45以上のツールを含む。遊休時間予測にはLightGBM量子回帰器を使い、12分位点それぞれ400木の勾配ブースティングモデルを学習する。
匿名化テレメトリは1350万セッション、9510万ターン、320万ユーザー、7.605億LLM呼出し、7.747億ツール呼出し、449億ではなく44.9兆のプロンプトトークン、393億完了トークンを含む。集計指標以外は機密保護のため標本化された部分集合を解析し、地域は米国内の最大3時間帯に限定される。プロンプト本文、応答本文、ソースコード、ツール引数、個人識別情報は収集しない。遊休予測器は1週間から15万セッションを学習、翌週5万セッションを評価に使い、60秒超遊休の識別ROC-AUC、時間経過ごとの正解率・F1、捕捉した総遊休時間割合で評価する。
GitHub Copilotという単一の本番コーディングエージェント、米国地域、2026年前半の挙動に基づく。クライアント側観測なのでGPU側の実負荷や配信キューを直接説明できず、内容を収集しないためタスク成功品質との相関も測れない。著者らは主要特性が2026年1〜6月で安定していたとするが、モデル・ツール・自律戦略の急速な更新により将来分布が変わる可能性がある。
## 主要結果
実運用コーディングエージェントは、中央値1セッション15 LLM呼出し・13ツール呼出しで、呼出しの87%がエージェント自身から発生する。各LLM呼出しは中央値68K入力に対し247出力と極端に入力偏重で、ターン内では接頭辞キャッシュが高効率だが、利用者入力を挟むターン境界、モデル切替、文脈圧縮で再利用が大きく崩れる。深い失敗ループは全ターンの9.1%ながら36 LLM呼出し・34ツール群という高負荷を生み、利用者類型間の一回のキャッシュミス再プリフィル費用は23K対1.1Mトークンで約50倍違う。ターン境界ではKVキャッシュ遊休中央値172秒、コンテナ243秒とターン内より二桁以上長く、軽量予測器は総遊休時間の86〜90%を捕捉する。

- エージェント起点LLM呼出し率 / 87% (比較対象: 利用者起点13%; 条件: GitHub Copilot実運用トレース) — 配信負荷の大半は利用者要求そのものではなく、一つのターン内で自律的に連鎖する後続呼出しから生じる。

- 入力／出力トークン中央値 / 68K prompt / 247 completion、275:1超 (比較対象: 従来チャットのより均衡した要求; 条件: LLM呼出し単位) — 生成よりプリフィルとKVキャッシュ再利用が支配的な最適化対象になる。

- KVキャッシュ再利用 / ターン内平均約90%、ターン境界55%、モデル切替後平均8% (比較対象: 同一ターン内継続; 条件: 接頭辞キャッシュ済みトークン比率) — キャッシュ寿命は要求単位ではなくセッション構造とモデル経路に支配される。

- 文脈圧縮影響 / 7.8%のセッションが44.2%の総トークンを占め、圧縮後キャッシュヒット率中央値66.1%低下 (比較対象: 圧縮前の高再利用状態; 条件: 文脈圧縮イベント) — 少数の最重量セッションで圧縮が長いプリフィルとキャッシュ再構築を同時に発生させる。

- ターン間遊休中央値 / コンテナ243秒、KVキャッシュ172秒 (比較対象: ターン内5.8秒、1.2秒; 条件: 連続ツール／LLM呼出し間隔) — ターン境界は退避・休止費用を償却できる自然な資源回収点になる。

- 遊休予測 / 60秒超識別ROC-AUC 0.73、総遊休時間捕捉86〜90% (比較対象: 直前遊休だけのヒューリスティックROC-AUC 0.58; 条件: 15万セッション学習、翌週5万セッション評価) — 正確な終了時刻を当てなくても、回収価値の高い長い遊休を高い割合で識別できる。

### 負の結果・境界条件
- 遊休予測の点ごとの正解率とF1は経過時間が長くなるほど低下し、30秒時点の約80〜88%から30分時点では25〜43%まで落ちる。クライアント側テレメトリのみなのでGPU利用率・キュー・バッチ・メモリ圧力を直接観測できず、提案する資源管理方針のエンドツーエンド節約量を実配信基盤で実証してはいない。プロンプト／応答内容がないため資源節約とタスク品質の関係も評価できない。

### 結果の読み方
重要なのは平均要求サイズではなく、セッション内の位置とイベントで資源価値が急変することである。ターン内では次のLLM呼出しが近くKVキャッシュ保持価値が高いが、ターン境界では分単位の遊休が生じる。さらに深いループ利用者はキャッシュミス費用が桁違いに大きいため、固定TTLや全利用者一律のLRUだけでは費用を最小化しにくい。
## 品質への影響
測定研究でありモデル出力品質を変更する手法ではない。ただし内容を収集しない設計上、成功率やコード品質と資源消費の相関を検証できず、資源回収を積極化した際の品質・利用者体験への影響は今後の課題である。
## 既存研究との差
vLLMやSGLangなど従来配信基盤は独立要求を基本単位とするのに対し、本研究は本番トレースからセッション・ターン・ステップというワークフロー単位が必要だと示す。CacheTTL、SAGA、Sutradhara、Pythiaなどのエージェント向け配信研究はキャッシュ保持やワークフロー認識スケジューリングを提案するが、多くはSWE-bench等の合成負荷で評価される。本研究は新しい配信機構を競うのではなく、それらの設計仮定を1350万実運用セッションで検証・定量化する測定研究である。TraceLab等の既存コーディングエージェント解析より利用者・セッション規模が大幅に大きく、利用者類型とKVキャッシュ寿命、ツール待ち、文脈圧縮を一つの資源管理像へ結び付ける。
## 限界
第一に、プライバシーと機密保護のためプロンプト、応答、ソースコード、ツール引数を収集せず、タスク成功やコード品質と資源消費を関連付けられない。第二にクライアント側テレメトリなので、GPU利用率、配信キュー長、連続バッチ状態、KVキャッシュの実メモリ圧力などサーバ側指標を直接観測できず、クライアント遅延から推測する部分が残る。第三にGitHub Copilot、米国地域、2026年6月中心の負荷であり、Claude CodeやCodex、他地域、別の自律戦略へ数値をそのまま一般化できない。エージェント製品は急速に変化するため、著者らが2026年1〜6月で傾向の安定を確認していても長期追跡が必要である。
## 実装状態
arXiv:2608.00101v1として2026-07-30公開のプレプリント。GitHub Copilotの内部匿名化テレメトリ解析を基盤とし、遊休予測器はLightGBMで具体的に実装・評価されている。論文は衛生化したトレースを将来公開予定と述べるが、確認時点では公開データセットURLや再現コードURLは本文に提示されていない。
## 研究上の位置づけ
エージェント配信システムの設計に必要な負荷モデルを提供する基礎測定研究である。特に、KVキャッシュを単なる要求内デコード状態ではなくセッション寿命を持つ資源として扱うこと、GPU推論とCPU／入出力ツール処理が交互に現れること、ターン境界が退避判断点になること、利用者類型でキャッシュミス費用が約50倍違うことを定量化した点が重要である。今後の階層KVキャッシュ、分離型キャッシュ、セッション認識スケジューラ、サンドボックス休止、文脈圧縮制御を評価する際の実運用分布として価値が高い。
