# AVO：コードエージェントを進化的探索の変異演算子にするGPUカーネル自動最適化

## 書誌・概要

本論文は2026年3月25日公開の12ページのプレプリントであり、進化的探索における大規模言語モデル（LLM）の役割を、候補コードを一度生成する部品から、過去の候補を読み、性能測定を行い、失敗を修正して再評価する長期実行エージェントへ拡張する。主な実証対象はNVIDIA Blackwell世代のB200上で実行する注意計算のGPUカーネルであり、推論基盤・学習基盤の共通ボトルネックとなる注意演算の実装最適化として位置づけられる。

古典的な進化探索では、親の選択、変異・交叉、評価、集団の更新を外側の枠組みが固定規則で実行する。LLMを導入しても、多くの方式では親から一度だけ候補を生成する役割に限られる。複雑なGPUカーネルの最適化では、実装を生成するだけでなく、CUDAやPTXの仕様書を調べ、コンパイル結果と数値正当性を検査し、プロファイラから待ち時間を特定し、何度も修正する工程が重要になる。AVO（Agentic Variation Operators）は、この一連の工程を変異演算子そのものとして扱う。

著者らは内部開発の汎用コードエージェントを使用し、NVIDIA B200でマルチヘッド注意（MHA）の順伝播カーネルを7日間自律改善した。40の成功版を保存し、途中では500を超える候補最適化方向を試したと報告する。最終版は、因果注意でcuDNN比最大3.5%、FlashAttention-4比最大10.5%の処理量改善を示す。さらにグループ化問い合わせ注意（GQA）へ約30分で適応させ、因果GQAでcuDNN比最大7.0%、FA4比最大9.3%を報告した。ただし全GPUや全形状での優位性ではなく、評価したB200・BF16・前処理順伝播の条件に限定される。

## 問題設定：固定された生成器と長期的な試行錯誤の差

従来のLLM支援進化探索は、蓄積された候補群P_tから親を選ぶSampleと、親から新候補を作るGenerateを組み合わせたVary(P_t)=Generate(Sample(P_t))という構造を持つ。LLMが生成を担当しても、いつ過去の実装を比較するか、いつ文書を読むか、何回デバッグするか、どの性能指標を優先するかは外部の固定的な手順に依存する。LLMの一回の応答で候補を生成するだけでは、すでに高度に最適化されたCUDAカーネルの数%の性能差を見つけるには不十分である。

注意演算はQK^Tを計算し、行ごとにソフトマックスを適用してVを掛ける。素朴な実装は系列長Nに対してN×Nのスコア行列をメモリへ実体化するが、FlashAttention系の実装はタイル処理とオンラインソフトマックスでこれを避ける。Blackwellでは行列積、ソフトマックス、累積値補正、データロードなどを異なるワープ群へ割り当て、並列に実行する。ここで性能をさらに上げるには、命令の依存関係、同期の重さ、レジスタ不足、局所メモリへの退避、演算と通信の重畳を同時に調整する必要がある。

AVOの目的は、手作りの変異規則で探索空間を固定することなく、正当性を維持したままGPUカーネルの測定処理量を継続的に改善することである。研究はエージェントの能力そのものを抽象的に測るのではなく、実際のGPU上で得られたカーネルの数値正当性とTFLOPSを評価指標にする。したがって論文の主張は、一般的なプログラミングベンチマークの成功率ではなく、特定の高性能GPUカーネルで人間が最適化した既存実装へ迫り、一部で上回ったという実証である。

## 手法

### 1. 変異演算子を自律エージェントへ置換する

AVOは従来のVaryをAgent(P_t,K,f)へ置き換える。P_tはこれまでに確定したコード実装とその評価スコアの履歴、KはCUDAプログラミング資料、PTX命令仕様、Blackwellアーキテクチャ資料、FlashAttention-4の既存コードなどの知識基盤、fは正当性検査と実行処理量を返す評価関数である。単なるコード生成モデルへのプロンプトではなく、ファイル操作、シェル、コンパイル、ベンチマーク、文書参照、過去の実装比較を利用できるエージェントを変異操作として定義する。

対象となる候補x_iはCUDAと必要に応じたインラインPTXを含む注意カーネル実装である。f(x_i)は単一のスカラーだけではなく、系列長、バッチサイズ、因果マスクの有無など各テスト設定に対応するスコアベクトルである。数値正当性に失敗した候補は、処理量が高くてもスコア0として扱う。誤ったカーネルが高速だからといって進化の成功版に入ることを防ぐ設計である。

一回の変異ステップの内部で、エージェントは過去の成功版を比較し、どの形状で性能が落ちるかを調べ、仕様書から使用可能な命令・同期規則を確認する。その後にコードを修正し、コンパイルして正当性と処理量を測定する。失敗した場合は原因を分析して別の修正を試す。これを一回のステップ内で複数回繰り返せることが、生成器だけを置く方式との主要な違いである。エージェントの探索過程は非決定的でも、成功版の受入条件は正当性とベンチマークの改善で明確にする。

### 2. 単一系列の成功版を保存する

本論文が実際に評価したのは、複数集団を持つ一般的な進化アルゴリズムではなく、単一の成功系列を長期に改善する設定である。初期コードx_0から始め、正当性検査に合格し、最良の確定版以上のベンチマーク得点を出した実装だけを次の確定版x_1、x_2、…として保存する。確定版はGitコミットと評価スコアで履歴化し、後のエージェントが過去の工夫を再利用できる。失敗した中間試行はエージェントの内部探索履歴には残るが、成功版の系列へは入れない。

この仕組みには二つの効果がある。第一に、実験のたびに過去の成功実装へ戻れるため、性能を悪化させる変更があっても最良状態を失わない。第二に、エージェントが前の改善で何を変更したかを文脈として持ち、初期段階の大きな構造変更から後半の微細な同期・レジスタ調整へ探索の重点を移せる。逆に言えば、成功版だけを並べたグラフは全探索回数を表さず、試行の計算費用を過小に見せる可能性がある。

### 3. 停滞時の監督機構

数日にわたる自律探索では、現在の仮説が尽きて改善が止まる、あるいは失敗する編集を繰り返す問題がある。AVOは停滞や不生産な循環を検出すると、監督エージェントが過去の探索軌跡を見直して別の最適化方向を提案する仕組みを持つ。主エージェントが実装・測定・修正を継続し、監督は必要な場合に方向転換を促す。監督の具体的な発火規則やエージェント内部モデルの詳細は、公開本文だけでは完全には再現できないため、再現性の評価ではその点を留保する。

7日間の実験では40の成功版を確定し、その背後で500を超える候補方向を内部探索したと報告する。成功版の数と全候補試行数は区別する必要がある。論文が示す40版は「40回しか生成していない」という意味ではなく、正当性・性能条件を満たした確定状態の系列である。また、単一系列以外の集団・島モデル・多目的アーカイブへ一般化できると著者らは述べるが、その拡張はこの論文の実験では未検証である。

### 4. Blackwell注意カーネルでの実装対象

Blackwell世代の注意カーネルでは、QK行列積で注意スコアを作る行列積ワープ群、オンラインソフトマックスを計算するワープ群、累積出力の再尺度化を担う補正ワープ群、Tensor Memory Acceleratorを使うデータ転送ワープ群などが役割分担する。FlashAttention-4の二重Qタイル方式では、複数の処理段階を並行させるが、行列積の完了待ちや同期バリアが性能を制限する。AVOはこの内部構造を仕様書・コード・プロファイラで把握し、既存カーネルを段階的に改善する。

対象は注意の前処理（prefill）の順伝播であり、デコード時のKVキャッシュ管理、長い逐次生成の応答間隔、学習の逆伝播を直接高速化したという評価ではない。マルチヘッド注意（MHA）での7日間の最適化を主実験とし、得られたコードをグループ化問い合わせ注意（GQA）へ短時間で移植する実験を追加する。GQAは問い合わせヘッド数よりKVヘッド数が少ないため、メモリアクセスや演算形状が異なる。移植実験は改善の転用可能性を示すが、任意のモデル構造への普遍性を保証しない。

## 評価

### 測定環境と比較の公平性

原著4章の測定環境はNVIDIA B200、CUDA 13.1、PyTorch 2.10.0である。比較対象はNVIDIAのcuDNN 9.19.1と、公開実装のFlashAttention-4（論文が明記するコミット71bf77c）である。全方式に同じベンチマーク形状を適用し、FlashAttention-4の公式ベンチマークスクリプトと同じウォームアップ・繰返し設定を使い、10回の実験で平均と標準偏差を求める。評価値は注意カーネルの浮動小数点演算処理量（TFLOPS）であり、モデル全体の要求処理量やユーザー向け応答時間ではない。

| 項目 | 原著の条件 |
|---|---|
| GPU | NVIDIA B200（Blackwell） |
| ソフトウェア | CUDA 13.1、PyTorch 2.10.0 |
| 精度 | BF16 |
| 対象 | 注意の前処理順伝播 |
| ヘッド次元 | 128 |
| 系列長 | 4096、8192、16384、32768 |
| バッチサイズ | 8、4、2、1（合計32768トークン） |
| MHA | 16ヘッド、因果・非因果 |
| GQA | 問い合わせ32ヘッド、KV4または8ヘッド（群サイズ8または4） |
| 比較対象 | cuDNN 9.19.1、FlashAttention-4 |
| 測定 | 同じベンチマーク条件、10回の繰返し |

合計トークン数を固定して系列長とバッチサイズを反比例させるのは、演算形状の違いを比較するためである。ただし系列長が長いほどバッチが小さくなるため、系列長だけを独立に変えた測定とは異なる。性能差を読む際には形状をセットで記載すべきである。

### MHAの処理量と負の結果

原著図3では、因果MHAの全評価形状でAVOが両比較方式を上回り、cuDNN比で+0.4〜+3.5%、FlashAttention-4比で+5.0〜+10.5%と報告する。系列長4K・バッチ8から32K・バッチ1までを対象とする。図5の40版を通じた因果MHAの幾何平均TFLOPSは、cuDNNが1488、FA4が1426、AVO最終版が1520である。従って最大10.5%は全形状の平均改善率ではなく、特定形状での最大値である。平均はこの3値から別に判断する必要がある。

非因果MHAでは効果が小さい。系列長16Kを超える長い形状でcuDNN比+1.8〜+2.4%の改善がある一方、短い系列長では両比較方式との差が測定ノイズの範囲に入ると論文は明記する。図6の幾何平均はcuDNN 1611、FA4 1620、AVO最終版1630 TFLOPSであり、因果MHAほどの大幅な差はない。したがって「すべての注意演算で10%高速」という要約は誤りである。因果マスクの有無、形状、比較方式によって効果は変わる。

### GQAへの30分の移植

MHAで進化させたカーネルをGQAへ対応させるようエージェントに指示すると、著者らは人間による個別のコード変更なしに約30分でGQA対応版が得られたと報告する。原著図4では問い合わせヘッド32、KVヘッド4（群サイズ8）と8（群サイズ4）の二構成で、因果・非因果を評価する。因果GQAの最大改善はcuDNN比+7.0%、FA4比+9.3%、非因果GQAはcuDNN比最大+6.0%、FA4比最大+4.5%である。

この実験が示すのは、MHAで得られたワープ間同期やパイプライン構造の工夫が、異なる注意ヘッド配置へ比較的短時間で移植できたことである。一方、7日間のMHA探索と30分のGQA移植を同じコストで比較してはならない。後者はすでに成熟したMHAカーネルを初期資産として利用している。GQAの全組合せに対して別途7日間のゼロからの探索を行った実験ではない。

### 進化軌跡と探索コスト

7日間の実行で成功版40件を保存し、内部では500を超える候補最適化方向を試した。図5・図6では性能が毎回一定幅ずつ増えるのではなく、構造的な改善が見つかった版で段差状に伸び、その後しばらく停滞する。著者らが主要な転換点として挙げるのは、v8のQK/PV処理の交互化と因果マスク、v13のソフトマックス処理再構成、v20の分岐なし累積値再尺度化、v30の補正処理と行列積の重畳、v33のワープ群間レジスタ再配分である。

初期のv1〜v20は大きな構造改善で伸び、後半のv21〜v40は同期、スケジューリング、資源配分などの微細な改善を積み重ねる傾向がある。これは長期の自律探索が既存の単発コード生成と異なる理由を示す。ただし7日間のエージェント実行に必要なGPU時間、推論トークン数、API費用、電力、人間が同条件で開発した場合の比較実験は原著からは定量的に確定できない。500を超える内部試行の失敗率や各試行費用も全件公開されていない。

### 構成要素の除去実験：何が速くなったか

原著表1は最終版と直前版を比較する局所的な除去実験であり、以下の改善を報告する。数値は各測定形状の幾何平均TFLOPSの増分であり、各改善を単純に足した値が最終版の全改善率になるわけではない。

| 最適化内容 | 版の比較 | 非因果MHA | 因果MHA |
|---|---|---:|---:|
| 分岐なしの累積値再尺度化と軽いフェンス | v19→v20 | +8.1% | +1.6% |
| 補正処理と行列積のパイプライン重畳 | v29→v30 | +1.1% | +0.4% |
| ワープ群間のレジスタ再配分 | v32→v33 | +2.1% | 約0% |

第一の分岐なし再尺度化では、オンラインソフトマックスの行最大値が更新されたとき、累積出力を再尺度化する必要がある。旧版は再尺度化が必要かを条件分岐で確認していたが、分岐の同期が毎回の鍵ブロック処理で費用になっていた。新方式は倍率を常に計算し、不要なら1を選んで掛ける。不要な乗算を許す代わりに分岐・ワープ同期を減らし、さらに軽量なメモリフェンスを使えるようにした。非因果では鍵ブロックの多くがマスクされず、この経路を広く使えるため+8.1%の利得が大きい。因果ではマスクされた部分に元の分岐を残すため+1.6%にとどまる。

第二のパイプライン重畳では、二重Qタイルを処理する際、補正ワープが二つのPV行列積の完了を待っていた依存関係を変更する。第一のPV行列積が終わった時点でその出力補正を開始し、第二の行列積と重ねる。補正ワープの待ち時間を減らすことで非因果+1.1%、因果+0.4%を得た。改善が小さいのは既存のFlashAttention-4自体が高度に重畳されたパイプラインを持つためであり、全体の実行時間がこの一箇所だけで決まるわけではない。

第三のレジスタ再配分では、元の実装がソフトマックス担当ワープへ192、補正担当へ80、残りの担当へ48レジスタを配っていたのに対し、AVOは184/88/56へ変更した。補正担当はローカルメモリへのレジスタ退避が生じていた一方、ソフトマックス担当には余裕があった。レジスタを移すことで補正ワープの退避を減らし、非因果で+2.1%を得たが、因果ではほぼ効果がなかった。単に全ワープのレジスタを増やすのではなく、限られたSM資源を性能上の律速箇所へ再配分した点が重要である。

## 既存研究との差

FunSearchやAlphaEvolveのようなLLM支援進化探索では、LLMが候補生成を担い、親選択・評価・集団管理などは外部のアルゴリズムが制御する。AVOはその一回の生成を、文書探索、コード編集、実行、プロファイリング、失敗修復を内包する自律ループに置き換える。固定した変異率や手作りのコード変更規則だけでは見つけにくい、複数のハードウェア制約をまたぐ改良を発見できる点を強調する。

また、AVOはFlashAttention-4やcuDNNそのものに対する新しい数学的注意アルゴリズムの提案ではない。注意の演算結果を維持しながら、既存のオンラインソフトマックスやワープ特殊化をより効率的に実装する探索手法である。従って注意の計算量の漸近次数を変えたという主張ではなく、同じB200での実測TFLOPSを改善したという工学的成果として読むべきである。自律エージェントの汎用性についても、今回実証されたのは注意カーネルであり、あらゆるGPU演算に同じ改善幅が得られることを示してはいない。

## 限界・負の結果・適用条件

第一に、性能評価はNVIDIA B200とCUDA 13.1に限定される。Blackwellのワープ群・レジスタ・同期命令を前提とする改善は、RTX 4070 Superなどの別世代GPUやAMD GPUへそのまま移せない。対象はBF16の注意前処理順伝播であり、デコード時の小バッチ処理、KVキャッシュ移動、モデル全体の応答遅延、学習の逆伝播などは直接評価していない。TFLOPSの改善をユーザー体感の生成速度へ等置しない。

第二に、非因果MHAの短い系列長では既存方式との差が測定ノイズの範囲にあり、最終版が常に明確な性能優位を持つわけではない。レジスタ再配分は因果MHAで約0%、補正・行列積の重畳も因果では+0.4%にとどまる。論文の最大改善率は条件ごとの最大値であり、全形状平均やモデル全体の改善率ではない。

第三に、7日間の探索と500超の試行方向は相応の開発計算資源を要する。確定した40版だけでは探索費用を測れず、全失敗試行の回数・GPU時間・モデル推論費用を再現できない。論文の汎用エージェントは内部開発とされ、具体的なモデル構成や探索ログの完全公開も確認できない。既存実装を上回ったという測定は有用だが、誰でも同じ予算で再現できることを意味しない。

第四に、実際に実証したのは単一系列の進化であり、複数集団・島モデル・アーカイブを使う一般的な進化探索へAVOを組み込む案は将来の拡張である。監督エージェントの介入が何回必要だったか、介入がなければ性能がどこで止まったかを厳密に切り分けた除去実験も示されていない。従ってエージェント化の各構成要素の独立寄与をすべて数値化した研究ではない。

第五に、最適化されたカーネルの数値正当性はベンチマークの参照実装に照らして判定される。評価外の形状、データ型、マスク方式、GPU環境でも正当性と速度を保証するものではない。高速化と引き換えに複雑な同期規則やメモリフェンスを変更するため、製品導入では対象GPU・カーネル設定ごとの回帰試験が不可欠である。

## まとめとサーベイ上の意義

AVOは、LLMを単なる候補生成器として使うのではなく、ハードウェア資料、実装履歴、正当性検査、プロファイラへアクセスする長期実行の変異演算子として使う。7日間の自律探索で注意カーネルを40の成功版へ改良し、B200の因果MHAではcuDNNやFlashAttention-4を上回った。具体的な改善は分岐・同期削減、補正処理の重畳、レジスタの再配分という実装上のボトルネック対策である。サーベイでは、LLM推論・学習カーネルの自動生成と最適化を担う研究として収録し、対象GPU・評価形状・最大改善率と平均改善率の違い・探索費用の未公開部分を明記するのが適切である。
