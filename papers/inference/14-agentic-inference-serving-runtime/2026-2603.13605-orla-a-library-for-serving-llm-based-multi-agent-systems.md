# Orla：複数LLMエージェントの処理段階を横断して推論基盤を制御するライブラリ

## 概要

Orlaは、大規模言語モデル（Large Language Model, LLM）を使う複数エージェントの処理を、個別の推論要求ではなく、依存関係を持つ段階的な仕事の集合として実行・管理するライブラリである。エージェント型アプリケーションでは、問い合わせ分類、資料検索、外部ツール呼出し、検証、回答生成などが順番または並列に進む。従来のvLLMやSGLangは一つのモデル推論要求を高速に処理することに長けているが、次の段階がどのモデルを使うか、先行段階のKV状態を残すべきか、複数段階をどう優先するかというワークフロー全体の情報を持たない。

Orlaは、処理段階を有向非巡回グラフ（Directed Acyclic Graph, DAG）で記述し、段階割当器、ワークフロー調停器、メモリ管理器を推論基盤の上に置く。段階ごとに軽量・重量モデルや異なる実行基盤を選び、依存関係を守って準備済み段階を並列実行し、次段階で再利用できるKVキャッシュを残す。バックエンドとの接続はOpenAI互換のHTTP APIで統一するため、SGLang、vLLM、Ollamaや模擬推論器を差し替えやすい。

著者はSWE-bench Lite由来の仕事とDAG-MATH-Formatted-CoTの段階的推論を用いて評価する。分類段階をQwen3-4B、重い段階をQwen3-8Bへ割り当てた異種構成は、単一Qwen3-8Bの比較対象に対し壁時計時間38%、平均完了時間60%、推定推論費用35%を削減した。段階間のKV保持も初回トークン時間（Time to First Token, TTFT）の分布を改善する。ただし、38%、60%、35%は異なる測定量であり、すべての仕事で応答速度が60%改善するという意味ではない。

## 問題設定と既存方式との差

複数段階を持つエージェントは、単一の推論要求と違って処理段階間の依存関係と情報の再利用を持つ。問い合わせ分類は小型モデルで足りる場合があるが、規則文書の解釈や最終回答には大きなモデルが必要になる。同時に、ある段階が別段階の完了を待つ間に、独立した段階を実行できる場合もある。これらの情報は、通常のモデル配信器に送られる一つずつのHTTP要求からは復元しにくい。

アプリケーション側のLangGraphやAutoGenは、エージェントの役割、ツール連携、対話の進行を記述する。一方、vLLMやSGLangはモデルの計算、連続バッチ処理、KVキャッシュのページ管理を行う。Orlaが担当するのはその間であり、どの段階をどのモデル・配信器へ送るか、要求をどの順序で投入するか、どのKVを段階間で残すかを制御する。モデルの注意演算や量子化アルゴリズムを変更する方式ではない。

近い研究ThunderAgentは、エージェント処理の状態を踏まえたGPUメモリと要求順序の調整を扱うが、論文の比較では単一モデルの推論プログラムを主に対象とする。Orlaは異種モデル・異種配信器を使うDAGを扱い、段階ごとに異なる割当と優先度を許す。したがって、Orlaは既存配信器を置き換えるのではなく、その上の制御層として併用できる。

## 手法

### 1. 段階・ワークフロー・バックエンドの抽象化

Orlaの段階（stage）は、モデル推論、必要に応じた外部ツール呼出し、ツール結果を使った追加推論からなる一単位である。段階には、利用するモデル、実行先、推論パラメータ、任意のツールを指定する。ワークフローは段階を頂点、先行関係を辺とするDAGで表し、上流段階が終わるまで下流段階を実行可能にしない。複数の上流段階がある場合には、その結果を受け取って入力文脈を構築する。

バックエンドは、実際に推論を処理するエンドポイントである。SGLangとOllamaのように実装やハードウェアが異なっても、Orlaは統一されたHTTPインターフェースを介して接続する。これにより、ワークフロー定義を維持したまま実行先のURLやモデル割当を変えられる。アプリケーションから見ると一つの仕事だが、実際には複数のモデル配信器へ段階的に分割して送ることができる。

### 2. 段階割当器（Stage Mapper）

段階割当器は、段階の計算負荷、必要なモデル能力、利用可能な実行基盤を見て、モデルとバックエンドを選ぶ。明示的な割当では、開発者が段階ごとにモデルを固定し、Orlaがバックエンドの存在や推論パラメータの適合性を検証する。動的な割当では、独自の分類器や方策を差し込める。論文のOneBitStageMapperは軽量なLLM呼出しで仕事を「簡単」「複雑」に分け、小型または大型モデルへ送る例である。

問い合わせ対応の例では、最初の分類段階をQwen3-4Bへ割り当て、規則確認、担当部署への振分け、返信作成などはQwen3-8Bへ割り当てる。小型モデルが適切な段階だけを受け持てば、大型モデルの実行時間と課金対象トークンを減らせる。ただし、分類が誤ると必要な能力を持たないモデルへ仕事を送る危険がある。Orla自体がすべての段階で回答品質を保証するわけではなく、モデル割当の品質検証は別途必要である。

### 3. ワークフロー調停器（Workflow Orchestrator）

調停器はDAGの依存関係を管理し、上流が完了した段階を実行可能待ち行列へ入れる。実行先バックエンドごとに待ち行列を持ち、その中を段階識別子ごとの副待ち行列へ分ける。段階スケジューラはどの段階の待ち行列を先に処理するかを決める。標準の先着順（First Come First Served, FCFS）では先頭要求の到着が早い段階を優先するが、優先度に基づく方策にも切り替えられる。

この二層構造の利点は、同じバックエンドを使う複数段階の仕事を、依存関係と優先度を守りながら制御できることである。例えば分類が終わった後、担当部署の調査と社内規則の照会が互いに独立なら、両方を実行可能にする。両段階が同じ重量モデルを使う場合でも、待ち行列の優先順位を管理し、結果が揃った時点で最終返信へ進める。

### 4. 文脈・KVキャッシュの段階間保持

通常の推論APIは要求が終わると、その要求のKVキャッシュを次の独立要求へ自動的には引き継がない。しかしエージェントの段階は、先行段階の入力文脈をほぼそのまま利用することがある。Orlaのメモリ管理器は、段階の依存関係、予測される再利用、バックエンドの切替、ワークフロー完了などの情報から、KVを残すか回収するかを判断する。

同じバックエンドで文脈の変化が小さい段階へ移るなら、前置文の計算結果を再利用して入力処理費用を抑える。一方、別モデル・別バックエンドへ切り替えるときは、重みや位置表現が互換とは限らないため、KVをそのまま移してよいとはしない。ワークフローが終了すれば、残ったキャッシュを回収する。したがって、段階間キャッシュ保持は「どんなモデル間でもKVを交換する」技術ではなく、同じ実行基盤で再利用可能な状態の寿命をワークフロー全体で管理する技術である。

### 5. 実装・模擬バックエンドとデモ

論文はOrlaを公開ライブラリとして説明し、SGLangやvLLMのGPU実行器と、OllamaのCPU実行器を差し替え可能にする。GPUデモではQwen3-4BとQwen3-8Bを使い、CPUだけのノートPC向けデモではQwen3-0.6BとQwen3-1.7Bを用いる。設定の変更によって同じ問い合わせ対応DAGを実行する。これは小型モデルの能力が大型モデルと同じという主張ではなく、制御層が異なる配信器に依存しないことの動作確認である。

また、入力処理と復号の遅延をパラメータで模擬するバックエンドも用意する。模擬環境は、GPU実機の性能をそのまま再現するためではなく、段階スケジューラの方策差や依存関係の影響を再現性よく比較するために利用できる。実機測定と模擬測定を混ぜて単一の高速化倍率にまとめないことが重要である。

## 評価

### 評価データ・モデル・比較条件

| 評価軸 | 論文記載の条件 | 注意点 |
|---|---|---|
| 仕事の集合1 | SWE-bench Lite由来2,294要求 | 原著は金パッチで変更されたファイルを基準版から読み、修正差分生成を要求 |
| 仕事の集合2 | DAG-MATH-Formatted-CoT由来2,894要求のうち先頭5問 | 段階間キャッシュ管理の小規模試験。全2,894問を実行した意味ではない |
| モデル割当 | 分類をQwen3-4B、重い段階をQwen3-8B | 単一Qwen3-8B構成との比較 |
| バックエンド | vLLM/SGLang、Ollama、模擬バックエンド | デモ経路と性能測定経路を区別 |
| キャッシュ比較 | 段階ごとに消去する方式対、ワークフロー単位で保持する方式 | TTFTの累積分布で比較 |
| 主な測定量 | 壁時計時間、平均完了時間、推定推論費用、TTFT | 総処理時間と一要求当たり時間は別の指標 |

SWE-bench Liteの評価は、元のバグ修正ベンチマークの問題をそのままエージェントの最終正解率として報告するものではない。論文は変更対象ファイルを既知の金パッチから抽出し、基準コミット時点のファイルを読ませて統一差分を生成する仕事へ変換している。評価では、ワークフローの各段階にどのモデルを割り当てるかを変え、実行時間と推定費用を比較する。論文の本文要約からGPU機種・総メモリ・通信帯域・要求到着率の全条件は確定できないため、ここでは不明な環境値を推測で補わない。

### 異種モデル割当の効果

| 指標 | 比較対象 | Orlaの構成 | 論文報告の改善 | 解釈 |
|---|---|---|---|---|
| 壁時計時間 | 全段階Qwen3-8B | 軽量段階Qwen3-4B、重量段階Qwen3-8B | 38%短縮 | 仕事群全体を終えるまでの経過時間 |
| 平均完了時間 | 同上 | 同上 | 60%短縮 | 個別仕事の平均完了時間 |
| 推定推論費用 | 同上 | 同上 | 35%削減 | モデルごとの課金単価・トークン量を踏まえた推定値 |

ここでの壁時計時間は複数の仕事をまとめて処理する総経過時間であり、平均完了時間は一つの仕事が完了するまでの時間を平均したものなので、改善率が異なることは矛盾しない。また、推論費用35%削減はハードウェアの電力35%削減やGPUメモリ35%削減ではない。安い小型モデルへ一部の段階を移すことによる料金モデル上の推定である。各段階の品質が完全に同じであることを示す独立した大規模評価は、この報告値だけからは読み取れない。

### 段階間KV保持の効果

DAG-MATH-Formatted-CoTから選んだ5問を多段階ワークフローとして実行し、各段階の終了ごとにKVを消す方式と、Orlaが次段階の再利用可能性に応じてKVを保持する方式を比較する。論文の図3はTTFTの累積分布関数（Cumulative Distribution Function, CDF）を示し、保持方式の分布が短時間側へ改善したと報告する。TTFTは最初のトークンが返るまでの時間であり、短いほど利用者が応答開始を早く観測できる。

この結果が示すのは、同じモデル・同じバックエンドで前置文が共有される場合、段階ごとに入力処理をやり直すよりも状態保持が有効になり得ることである。ただし、対象は2,894要求全体ではなく選択した5問である。論文の本文要約では分布の全百分位値を数表として確認できないため、中央値やp99を推測で作成しない。保持するKVが増えると他の仕事のためのメモリを圧迫する可能性があり、保持と回収の方策が重要になる。

### システム設計の評価境界

Orlaの貢献は個々のGPUカーネルを速くすることではなく、処理段階のモデル割当、スケジューリング、状態の再利用を統一的に制御することにある。したがって、異種モデル割当で得た38%・60%の改善と、段階間キャッシュ保持で得たTTFT改善は別実験の成果であり、単純に掛け合わせた総合高速化倍率は論文から導けない。複数モデルの品質、ツール実行の失敗率、キャッシュ競合、要求到着分布が変われば結果も変わり得る。

## 限界・適用条件

第一に、異種モデルへの割当は品質と費用の交換条件を持つ。分類器が難しい仕事を小型モデルへ送れば回答品質が低下し得るし、割当のための追加推論自体にも費用がかかる。第二に、KV保持は同じモデル・同じ文脈を再利用する段階で有効であり、異なるモデル間のKVを無条件に移送する方式ではない。第三に、長時間稼働する多数ワークフローでキャッシュを保持しすぎれば、GPUメモリ不足や追出し競合を生じ得る。

第四に、SWE-bench Liteから生成した差分要求と、DAG-MATHの少数の段階的問題は、現実の多数エージェントが同時にツールを呼び出す複雑な運用負荷を完全には代表しない。ツールのネットワーク遅延、失敗・再試行、セキュリティ境界、外部APIの料金変動、複数GPU間の実際のKV転送費用を含む一般化には追加評価が必要である。第五に、公開実装の論文記載URLは確認できたが、確認時にはリポジトリのリダイレクトにより現行READMEを取得できなかったため、最新の依存関係や公開コードの完全性までは保証しない。

この方式が有用なのは、複数のLLMや実行基盤を組み合わせ、段階ごとの処理能力と費用を変えたいエージェント配信基盤である。単一モデルを一回だけ呼ぶ用途や、すべての段階が完全に独立して文脈を共有しない用途では、追加制御層の利得は小さい可能性がある。Orlaの数値を適用する際は、モデル割当方策、課題難易度、同時要求数、前置文共有率、メモリ上限を明示して再評価する必要がある。
