# Hexgen-Flow: Optimizing LLM Inference Request Scheduling for Agentic Text-to-SQL

> 依存するText-to-SQLのLLM呼び出しを、異種GPUへの大域負荷分散と残り期限に基づく局所優先度制御で協調し、問い合わせ全体のSLOを守る。

## 概要

エージェント型Text-to-SQLは、スキーマ対応付け、SQL候補生成、自己修正、評価を順に実行し、一つのユーザー問い合わせから多数のLLM推論要求を生む。BIRDベースの三トレースでは1問い合わせあたり平均19.4〜21.1回のLLM呼び出しが発生する。各段の遅れは後段を開始できなくし、GPU世代が混在すると同じ要求でも処理時間が異なるため、vLLMの先着順と単純なラウンドロビン配置では問い合わせ全体のサービス品質目標（Service-Level
Objective; SLO）を扱いにくい。

Hexgen-Flowは中央の大域調停器と各モデルインスタンスの局所優先度待ち行列を組み合わせる。大域側は入力長・予測出力長から各GPUでの計算時間を見積もり、現在の待ち時間と合わせて配置先を決める。局所側は問い合わせ全体の残り期限を残り各段へ計算量比例で配り、待機時間と予測計算時間から緊急度を算出して、連続バッチの境界で順序を更新する。Llama3.1-70Bを用いた異種GPU評価では、vLLM比でP95末尾遅延を19.2〜56.2%削減し、スループットを49.1〜81.0%改善した。

## 問題設定

一般的なLLMサーバーは各要求をほぼ独立とみなす。ところがText-to-SQLでは、前段のSQL候補が完成しなければ自己修正へ進めず、自己修正の反復回数も入力ごとに変わる。早い段階で予算を使い過ぎると後段の評価が期限切れになり、逆に早い段を過度に優先すると他ユーザーを待たせる。

さらにA100、L40、A6000のような異種GPUでは、同じ入力・出力長でも実行時間が異なる。単純なラウンドロビンは重い要求を遅いGPUへ送る可能性があり、最速GPUだけを選ぶとその待ち行列が膨らむ。Hexgen-Flowは「配置先」と「配置後の実行順」を別階層で解く。

## 手法

### 依存関係を明示する大域調停器

問い合わせを複数段のワークフローとして保持し、前提段が完了した要求だけを実行可能にする。SQL候補生成のように並列化できる要求は同時に複数インスタンスへ送る。各段が完了するたびに問い合わせ全体の経過時間を更新し、残り期限を後続段へ伝播させる。

実行中要求を別GPUへ移すとKVキャッシュやバッチ状態の転送が高価なため、Hexgen-Flowは原則として新規到着時の配置を最適化し、実行中移動はしない。失敗・タイムアウト時は同じ配置規則で別インスタンスへ再発行する。

### 計算時間と待ち時間を結合する配置スコア

入力長と予測出力長から、各モデルインスタンスmでのプリフィル時間とデコード時間を推定し、予測計算時間を作る。待ち時間はそのインスタンスの待ち行列にある要求の予測計算時間の和で近似する。

配置スコアは、待ち行列が短いほど高くなる項と計算時間が短いほど高くなる項を、係数αで調整する。α=1なら実行速度を優先し、α=0なら待ち行列の空き具合を優先する。固定の最速GPU選択と単純負荷分散の中間を、負荷に応じて動かせる。

### 残り期限を段ごとへ配るSLO予算

問い合わせ全体の残り時間を、今後の各LLM呼び出しの平均予測計算時間に比例して分配する。重い後段には多くの時間を割り当て、前段で遅延が発生した場合は次段の予算を再計算する。自己修正のような反復は設定上限と観測済み進捗から残作業量を見積もる。

この再計算が、単純な最小余裕時間優先（Least Laxity First;
LLF）との差になる。問い合わせ全体の余裕だけでなく、どの段がどれだけ計算を必要とするかを毎段反映する。

### 緊急度に基づく局所待ち行列

局所インスタンスでは、予測計算時間から「残りSLO余裕」を引いた値を緊急度Uとして使う。待機時間が伸びるほど余裕が減ってUが上がるため、長く待つ要求は自然に優先度が上がり、飢餓を防ぐ。

優先度は連続バッチの新しいバッチを組む境界で再評価する。モデル内部のトークン生成順を変更するのではなく、次にバッチへ入れる要求を選び直すため、vLLMの実行エンジンを活用しつつ上位スケジューリングを差し替える構成になる。

### シミュレーションによるα調整

負荷分布とGPU混成比が変わると最適αも変わる。Hexgen-Flowは観測トレースを使う軽量シミュレータで候補αを試し、実環境で全候補を探索する費用を避ける。これにより急なトラフィック変動時にも、計算速度重視と待ち行列分散重視の比率を更新する。

## 既存研究との差

vLLMは先着順、VTCはユーザー間公平性、QLMはSLOグループの待ち時間、LLFはジョブ全体の余裕時間を主に見る。Hexgen-Flowは依存段の進捗を持ち、異種GPUへの配置と局所期限優先を二階層で結ぶ。Ray
ServeはDAG自体を表現できるが、段をまたぐ期限圧力とLLM固有の計算量を配置判断へ組み込まない。

## 限界・実装状況

主評価はText-to-SQLという特定のエージェントDAGであり、ツール待ちがLLM推論より支配的なワークフローでは同じ効果を期待できない。出力長予測と性能プロファイルの誤差は配置判断へ影響するが、後段SLO予算の再計算で一部を吸収する。実行中要求を積極的に移動しないため、配置後にGPU負荷が急変した場合の修正力には限界がある。
