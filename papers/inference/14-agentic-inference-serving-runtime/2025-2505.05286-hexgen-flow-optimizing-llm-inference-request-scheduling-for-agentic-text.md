# HEXGEN-FLOW: Optimizing LLM Inference Request Scheduling for Agentic Text-to-SQL

## 概要

本研究は、一つの利用者問い合わせが約20回の大規模言語モデル（LLM）呼び出しを誘発するエージェント型Text-to-SQL処理に対し、問い合わせ全体の応答期限を守る推論スケジューラを設計する。自然言語からSQLを生成するエージェントは、スキーマ対応付け、複数SQL候補の生成、実行エラーの自己修正、最終候補の評価を順に行う。各段には前後の依存関係があり、前段が遅れると後段の残り時間が減る。さらにGPUの種類が混在すると、同じ入力長・出力長でも処理速度が変わるため、単純なラウンドロビン配置と先着順処理では、問い合わせ全体のサービス品質目標（SLO）を満たしにくい。

提案するHEXGEN-FLOWは、依存関係を追跡する大域調停器と、各モデルインスタンスの緊急度優先待ち行列からなる二層スケジューラである。大域側は要求の予測計算時間と配置先の待ち時間を同時に考慮し、局所側は問い合わせ全体の残り期限を未完了の段へ配分し直す。Llama3.1-70BとBIRD由来の三つのトレースを使う比較では、vLLM基準でP95末尾遅延を19.2〜56.2%削減し、完了問い合わせ数/秒を49.1〜81.0%改善する。これは同じSQL生成ワークフローの実行順と配置を最適化した結果であり、モデル自体のSQL正答率を上げる学習手法ではない。

## 問題設定

典型的なText-to-SQLエージェントは、最初に自然言語とデータベースの表・列を対応付ける。次に複数のSQL候補を並列に生成し、実際のデータベース実行結果に基づいて最大10回程度の修正を行う。最後に候補SQLを自然言語の検証項目で評価して最終回答を選ぶ。候補生成は並列化できても、自己修正は候補が揃わなければ開始できない。SQL実行そのものはLLM推論より短いため、LLM呼び出しの待機と生成が全体遅延を支配する。

同じ利用者問い合わせから発生する複数の推論要求は、個別の到着順よりも全体の残り期限に応じて優先度を決める必要がある。さらにA100、A6000、L40の混成クラスタでは、重い候補生成を遅いGPUへ割り当てると全体が詰まる。逆に最速GPUだけを選ぶと、その待ち行列が膨らむ。全体の期限、段間の依存関係、GPUごとの処理速度、局所キューの混雑を同時に扱うことが課題である。

## 手法

### 大域調停器による依存関係管理

各利用者問い合わせを有向非巡回グラフ（DAG）で表し、スキーマ対応付けが完了した後に候補生成を発行し、必要な候補が揃ってから自己修正・評価へ進む。実行可能な候補生成要求は複数のモデルインスタンスへ並列に送る。各段の完了時に経過時間と残りの段数を更新し、期限に遅れが生じた場合は後続の予算を締める。これにより、単なる独立LLM要求の集合ではなく、一つの端点SLOを持つ作業として制御できる。

調停器は各GPUでの実行時間を経験的な性能プロファイルから推定する。要求の入力トークン数と予測出力トークン数を使い、プリフィルとデコードの時間を別々に見積もって合算する。出力長は事前には不確実なので、推定誤差がスケジューリングに影響する。モデルインスタンスの待ち時間は、その待ち行列に積まれた要求の予測計算時間の和から近似する。要求が配置された後はKVキャッシュやバッチ状態の転送が高価なため、原則として実行中要求をGPU間で移動しない。失敗時には標準的なタイムアウト・再試行を利用して別インスタンスへ割り当て直す。

### 計算速度と待ち行列を統合する配置スコア

要求qをモデルインスタンスmへ送る際のスコアは、**Score(q,m)=(1−α)・β/t_queue(q,m)−α・t_comp(q,m)** と定義する。t_compはそのGPUでの予測計算時間、t_queueは待ち行列から推定した待機時間であり、αは0〜1の調整係数である。βは両項の尺度を揃えるための導入時較正定数で、参照計算時間と参照待機時間の積から決める。スコアが最大となるインスタンスを選ぶ。

α=1なら予測実行時間の短いGPUを優先し、α=0なら空いている待ち行列を優先する。両者の中間では、重い段をA100へ送りながら、軽い段をL40などへ分散できる。固定ラウンドロビンと異なり、要求の計算量と配置先の負荷を両方見ている。調整係数は負荷とGPU混成によって最適値が変わるため、固定し続けるのではなく後述の模擬実行で更新する。

### 問い合わせ全体の残り期限を各要求へ配分

問い合わせiの端点SLOをT_i、これまでの経過時間をτ_elapsedとすると、残り時間はT_i−τ_elapsedとなる。次の要求jへ配る時間予算は、残り時間に、jの平均予測計算時間を残り全要求の平均予測計算時間合計で割った比率を掛ける。すなわち **budget(i,j)=(T_i−τ_elapsed)・t̄_comp(i,j)/Σ_{k≥j}t̄_comp(i,k)** である。重い段には長めの予算を与え、先行段が遅れれば後段の予算が自動的に減る。

局所キューの緊急度は **U(i,j)=t_comp(i,j)−(budget(i,j)−τ_queue(i,j))** とする。予測計算時間に対して残りの許容待機時間が短いほどUが大きくなり、優先度が上がる。待機時間が伸びてもUが上がるため、先着順のように緊急要求を一律に後回しにせず、長時間待機の飢餓も抑える。再順位付けは連続バッチの境界で行う。これは既存の生成中トークンの意味を変更するものではなく、次の処理枠にどの要求を入れるかの決定である。

一般的な最小余裕時間優先（LLF）も端点期限を参照するが、HEXGEN-FLOWは段ごとの予測計算量に比例した予算を進捗に応じて再計算する点が異なる。優先度は利用者ごとではなく、同じ問い合わせの段間で伝播する遅延も反映する。

### 模擬実行によるαの自動調整

大域配置のαは、直近の到着要求を模したCPU上の軽量シミュレータで調整する。候補αを0.0から1.0まで0.1刻みで試し、95%の問い合わせが完了する時間を最小化する値を選ぶ。実サービスに全候補を流して試すのではなく、性能プロファイルと観測トレースを用いるため調整の影響を抑えられる。実験では100秒の監視窓に対し調整時間は1.9〜3.1秒で、性能悪化を検知した窓だけで調整が発火した。最適αはトレースとGPU構成で異なるため、常に最速GPU重視、あるいは常に待ち行列重視が最善とは限らない。

## 評価

### 実験条件と指標

| 観点 | 一次論文v3で確認した条件 |
|---|---|
| 主モデルと処理 | Llama3.1-70B、CHESS型のText-to-SQLエージェント、vLLMの連続バッチ |
| データ | BIRD開発セット由来の金融・Formula1データベース。三つのトレースで難易度は単純14%、中程度72%、困難14% |
| 呼び出し数 | 1問い合わせ当たり平均19.4、20.7、21.1回（Trace 1〜3）。自己修正は最大10反復 |
| GPU配置 | Hetero-1：A100とA6000、Hetero-2：A100・A6000・L40、Homo：A100のみ |
| 到着負荷 | 0.5/1.0問い合わせ毎秒、30 QPSの高負荷、5→20→5 QPSの変動負荷 |
| 比較対象 | vLLM先着順＋ラウンドロビン、VTC、QLM、LLF、Ray Serve |
| 指標 | 95%の問い合わせが期限内に収まる最小SLO倍率、P95末尾遅延、完了問い合わせ数/秒 |
| 追加評価 | MAC-SQL＋Qwen3-30B＋Spider、混合負荷、異なるSLOを持つ2利用者 |

SLO倍率は、専有環境で測った各問い合わせの基準実行時間へ何倍の余裕を与えるかを表す。例えばSLO倍率3.5とは、実測遅延3.5秒という意味ではない。図4のP95改善と図5の処理量改善は異なる指標であり、同じ倍率を相互に読み替えない。論文の実装説明には各インスタンスのGPU数とテンソル並列度に整合しない記述があるため、厳密なGPU枚数の再現は公式実装の確認が必要である。

### 主要な比較結果

| 比較対象 | P95末尾遅延の削減範囲 | 完了問い合わせ処理量の改善範囲 |
|---|---:|---:|
| vLLM | 19.2〜56.2% | 49.1〜81.0% |
| VTC | 19.2〜53.8% | 10.3〜39.8% |
| QLM | 14.0〜39.6% | 17.5〜36.6% |
| LLF | 12.4〜39.6% | 6.7〜59.8% |
| Ray Serve | 8.6〜23.8% | 30.4〜38.2% |

この範囲は論文第5.2節の各トレース・構成における比較であり、全条件で同じ割合だけ速くなる保証ではない。例えばTrace 1・Hetero-1・到着率0.5 QPSでは、95%達成に必要なSLO倍率がvLLMの5.4からHEXGEN-FLOWの3.5へ下がる。Trace 2・Hetero-2・0.5 QPSではVTCの7.9から5.2、Trace 3・Hetero-2・1.0 QPSではQLMの7.8から6.1へ下がる。v3要旨のP95 1.42〜1.56倍、処理量1.49〜1.81倍という総括値と、比較対象ごとの百分率範囲を混同しない。

同種A100クラスタでも、vLLMに対するP95改善は最大32.6%に達する。したがって改善要因は異種GPUへの適切な配置だけでなく、段間の残り期限を反映した局所優先度にもある。30 QPSの高負荷や5→20→5 QPSの変動負荷では、全比較対象に対してP95を5.2〜23.3%削減する。MAC-SQLとQwen3-30Bを使う別のワークフローではP95を34.0〜38.3%削減し、BIRD/CHESS専用の効果だけではないことを補足する。ただし評価対象はいずれもLLM推論が支配的なエージェント処理である。

### 構成要素除去、配置分布、調整費用

大域の負荷均衡配置（WB）と局所優先キュー（PQ）を切り離した構成要素除去では、WB+PQはRR+PQに比べてP95を10.5〜34.8%削減し、WB+FCFSに比べて最大48%削減した。Trace 3・Hetero-2・0.5 QPSで、RR配置では重い第2段の18.1%しかA100二台へ送られなかったのに対し、WB配置では57.5%がA100へ送られ、L40へ送る比率は9.6%から3.1%へ下がった。反対に軽い第1段ではL40の担当比率が26.8%から32.3%へ増えた。重い処理と軽い処理をGPU能力に合わせて分けることが、単なる公平な配分との違いである。

局所キューの実例では、先着順なら到着22.4秒の要求1を処理するが、緊急度に基づく方式では到着64.4秒の要求6（緊急度26.9）を選ぶ。先に来た要求を無条件に優先しないことで、全体期限が迫った問い合わせの違反を防ぐ。αの最適値はTrace 1のHetero-1で0.1、Hetero-2で0.3と異なり、Trace 3のHetero-2では0.4が良い。監視窓100秒の模擬調整は1.9〜3.1秒、20〜30 QPSの負荷試験では監視窓300秒に対し3.9〜6.6秒を要する。調整費用はゼロではないが、毎回全候補を本番GPUで実行する方式より小さい。

異なるSLOを持つ2利用者の試験ではP95を27.9〜35.7%削減し、Jain公平性指数0.98を報告する。ただし指数は対象の三トレースで計算された値であり、任意の多利用者構成で公平性が保証されるわけではない。

## 既存研究との差

vLLMの基本先着順は各要求を独立に扱い、VTCは利用者間の消費トークン量の公平性、QLMは待機時間とSLO、LLFは問い合わせ全体の余裕を主に参照する。Ray ServeはDAGを表現できるが、LLMの段ごとの推論費用と残り端点期限を同時に反映した配置・優先度の連携を持たない。HEXGEN-FLOWは依存DAGの進捗を大域調停器が把握し、異種GPUへの割当てと局所キューの優先度を二階層で連動させる点に特徴がある。

## 限界・実装状況

第一に、主評価はText-to-SQLのCHESS型ワークフローであり、外部APIや人間の承認待ちが支配的なエージェント処理へ同じ改善率を外挿できない。第二に、入力長からの出力長予測やGPU性能プロファイルに誤差があると、配置先と期限予算の推定が外れる。第三に、実行中要求を積極的にGPU間移動しないため、配置後に負荷が急変した場合の修正には限界がある。第四に、調整器はCPU時間と観測窓を消費し、急激な変動へ無遅延で追従するわけではない。

第五に、主な実験は特定の70Bモデルと混成GPU構成であり、単一消費者向けGPUやCPUオフロードを前提にした効果は測っていない。第六に、SQLの正答率を改善する手法ではなく、同じワークフローの実行順を変えるため、元モデルが誤ったSQLを生成する問題は残る。第七に、本文には各モデルインスタンス4GPUという記述とテンソル並列度8という記述が併存しているため、GPU割当てを再現する際は公式コードと実験設定を追加確認する必要がある。実装は著者の公式GitHubで公開されている。
