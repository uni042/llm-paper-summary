# Sherlock: Reliable and Efficient Agentic Workflow Execution

> 反実仮想故障注入で脆弱節点へだけ検証器を置き、検証中に後続処理を投機実行して必要時だけ巻き戻すSherlock。平均精度+18.3%、検証費用-26.0%、検証完了時間最大-48.7%。

## 概要

複数のLLM呼び出し、検索、ツール利用、推論をグラフとしてつなぐエージェント型ワークフローでは、上流節点の小さな誤りが後段へ伝播し、最終出力で大きな失敗になる。一方、全節点へ自己改善、討論、LLM判定器などの検証器を挿入すると、追加LLM呼び出しがクリティカルパスへ入り、単一検証器でも条件によって無検証比で最大28.9倍の遅延、53.2倍の費用増を生む。

Sherlockは「どこを検証するか」「どの検証器を使うか」「検証待ちをどう隠すか」を分離する。まずオフラインで各節点へ反実仮想の誤りを注入し、その誤りが最終結果へどれだけ伝播するかを測って脆弱節点を特定する。次に、節点の種類と検証器ごとの改善量・費用から、予算内で適切な検証器を動的選択する。

実行時には検証器の返答を待たず、元出力を仮採用して下流節点を開始する。検証後の修正版が元出力と実質的に同じなら投機結果をそのまま使い、意味のある変更なら最後に確認済みの状態へ巻き戻して再実行する。これにより検証を品質向上へ使いながら、その待ち時間の一部を下流計算で隠す。

CoTCollection、OMEGA、LiveCodeBenchで、無検証ワークフローより平均18.3%精度を改善した。AFlow等との比較では検証費用を26.0%削減し、投機実行は検証完了までの時間（Time to End Verification; (T_{vrf})）をLiveCodeBenchで平均48.7%短縮する。

## 問題設定

### すべての節点が同じ危険度ではない

ワークフロー節点は、位置、入力の集約数、担当タスクによって失敗時の影響が異なる。ある中間節点が多少変わっても後段で吸収される一方、初期の計画や最終統合の誤りは複数枝へ波及しやすい。

Sherlockは「その節点自身のエラー率」だけでなく、そこで誤りが起きた場合に最終出力が壊れるかという反実仮想影響を測る。これにより、単純な深さ順や等間隔配置ではなく、限られた検証予算を最終品質へ効く節点へ割り当てる。

### 検証器ごとに得意領域と費用が違う

LLM判定器（LLM-as-a-Judge）、討論（Debate）、高度な自己改善などは、同じ節点でも精度改善量・トークン消費・待ち時間が異なる。強い70Bモデルを常に使えば品質は上げやすいが、費用目標を満たさない。

そのためSherlockは、節点を「検証する／しない」だけでなく、どの検証器を使うかまで実行時に選択する。目的は最大精度の検証器を固定することではなく、ワークフロー全体の費用制約下で期待品質改善を最大化することである。

## 手法

### 1. 反実仮想故障注入で節点脆弱度を測る

ドメイン導入時にワークフローを通常実行して基準出力を得る。その後、対象節点 (n) の出力へ故障モデルから生成した誤った候補 (o'_n) を注入し、その状態から後続グラフを再実行する。

元の最終結果と故障注入後の結果を比較すれば、「節点nの誤りが最終出力まで生き残る確率」を推定できる。論文は100を超えるワークフローグラフ、15Kを超える実行トレースを使って構造・位置と誤り伝播を分析し、この脆弱度推定器を構築する。

この分析により、単にローカル失敗率が高い節点ではなく、**誤った時の下流影響が大きい節点**を検証対象として優先できる。

### 2. 予算内で検証器を配置する

オンラインではワークフローの費用サービス水準目標（Service Level Objective; SLO）を受け、脆弱度が高い節点から検証候補を選ぶ。均等配置やランダム配置と異なり、節点ごとの最終品質寄与を使って限られた検証回数を配る。

予算を増やせば検証節点を増やせるが、全節点検証へ自動的に移行するわけではない。費用と信頼性の操作点をユーザー側が変えられる設計である。

### 3. 学習済み選択器が節点ごとに検証器を変える

Sherlockは各検証器について、タスク種類や節点特性に対する精度改善と費用を事前分析する。実行時の選択器は、与えられた節点に対し最も費用対効果の高い検証器を選ぶ。

評価実装では、主実行器にLlama-3.1-8B-Instruct、LLM判定器／討論の副実行器にQwen2.5-7B-Instruct、高度な改善器にLlama-3.3-70B-Instruct、判定モデルにSelene-1-Mini-Llama-3.1-8Bを使う。検証器の計算量が大きく異なるため、選択自体が費用最適化の主要要素になる。

### 4. 検証と下流実行を投機的に重ねる

節点出力が生成されると、その出力を検証器へ送るのと同時に、未検証出力を使って下流節点も開始する。検証が成功すれば下流の投機結果を確定し、検証が修正を返した場合は差分を調べる。

これにより従来の「実行 → 検証待ち → 次節点」という直列クリティカルパスを、「検証」と「後続実行」の並行区間へ変える。特に検証器が大型LLMの場合、その数秒の待ち時間を下流LLM・ツール処理で覆える。

### 5. 修正が実質同一ならロールバックしない

検証器は、内容上は同じでも文体だけ修正することがある。そのたびに下流を捨てると投機実行の利点が失われる。Sherlockは元出力と修正版の類似度を軽量指標で比較し、意味のある差が小さい場合は投機結果を維持する。

指示追従・ツール利用ではROUGE-Lがground-truth同値判定と比較的よく相関し、Spearman相関が約0.55、AUCが約0.85だった。ROUGE-L等は0.05秒未満で計算できるのに対し、追加LLM判定は平均2〜3秒規模なので、ロールバック判定自体を軽量に保てる。

一方、コードと数学ではこれらの文字列類似指標がほぼランダム（AUC約0.5）まで崩れるため、Sherlockは保守的に完全ロールバックする。このドメイン別フォールバックが、投機結果を誤って再利用しないための境界条件である。

## 評価

### 代表的な評価条件

| 項目 | 条件 |
| --- | --- |
| GPU | 8× NVIDIA A100 80 GB |
| 実行基盤 | vLLM |
| 主実行器 | Llama-3.1-8B-Instruct / 2 GPUs |
| 高価な改善器 | Llama-3.3-70B-Instruct / 4 GPUs |
| 判定・討論用 | Qwen2.5-7B-Instruct / 1 GPU |
| Judge | Selene-1-Mini-Llama-3.1-8B / 1 GPU |
| ベンチマーク | CoTCollection、OMEGA compositional subset、LiveCodeBench |
| 比較 | 無検証、均等/ランダム配置、表引き式選択、AFlow、非投機実行 |
| 指標 | accuracy/pass@1、正規化検証費用、(T_{exec})、(T_{vrf}) |

### 品質・費用

| 指標 | 結果 | 比較対象 | 読み取り |
| --- | ---: | --- | --- |
| 最終精度 | 平均 +18.3% | 無検証ワークフロー | 脆弱節点への選択的検証で誤り伝播を抑える |
| 検証費用 | -26.0% | Monte Carlo探索ベース方式 | 節点と検証器を同時に選ぶことで不要な高価検証を減らす |
| 単一検証器の最悪追加費用 | 最大53.2倍 | 無検証 | 全節点検証が現実的でない動機 |
| 単一検証器の最悪追加遅延 | 最大28.9倍 | 無検証 | 投機実行で隠すべき対象が大きい |

18.3%は「投機実行による精度改善」ではなく、検証器配置・選択による無検証比の平均品質改善である。投機実行は同じ検証を待つ時間を短くする性能機構として分けて評価される。

### 投機実行の遅延削減

| ベンチマーク | (T_{exec}) 平均削減 | (T_{vrf}) 平均削減 |
| --- | ---: | ---: |
| CoTCollection | 51.4% | 21.9% |
| OMEGA | 53.4% | 30.6% |
| LiveCodeBench | 62.9% | 48.7% |

(T_{exec}) はワークフロー実行自体が終了する高速経路、(T_{vrf}) は最終検証済み出力が確定するまでの低速経路である。headlineの48.7%はLiveCodeBenchにおける(T_{vrf})平均削減で、全ベンチマーク平均や(T_{exec})最大値ではない。

LiveCodeBenchでは(T_{exec})が平均62.9%短くなる一方、最終検証を待つ(T_{vrf})は48.7%短縮に留まる。これは投機で実行待ちは多く隠せても、最終的な検証器そのものの処理時間は完全には消せないことを示す。

## 既存研究との差

自己改善やLLM判定器を各節点へ挿す方式は信頼性を上げるが、どこを検証すべきかをワークフロー全体の誤り伝播から判断しない。Sherlockは反実仮想故障注入で「その節点が壊れると最終結果がどれだけ壊れるか」を直接測り、配置問題へ使う。

AFlowのようなワークフロー探索方式に対しては、グラフ自体を最適化することより、既存グラフをどう安全・低遅延に実行するかへ焦点を置く。また投機実行は通常のCPU命令投機と同じく、正しい可能性が高い未検証結果で先に進み、失敗時にだけ巻き戻すが、LLM出力では「修正版と元が意味的に同じ」ケースが多いため類似度ベースの選択的ロールバックを追加している。

## 限界・実装状況

脆弱度モデルは導入時の故障注入と実行トレースに依存するため、ワークフロー構造やモデル、ツール、入力分布が大きく変われば再プロファイルが必要になる。検証器自体も完全ではなく、Sherlockは「検証結果が常に正しい」と保証する仕組みではない。

選択的ロールバックに使うROUGE-L等は自然言語では有効だが、コード・数学では意味同値性を判定できず完全ロールバックへ戻る。この条件では投機的に行った下流計算が無駄になりやすく、LiveCodeBench等の実測利得は失敗率・検証修正率・下流計算長に依存する。

また本研究は8×A100上の研究評価であり、API課金型モデルやネットワーク越しのツール呼び出しでは費用・遅延構成が変わる。平均18.3%精度改善、26.0%費用削減、48.7%遅延削減はそれぞれ異なる比較軸の値であり、単一の同一条件倍率としてまとめてはいけない。
