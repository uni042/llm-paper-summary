# Shared Disk KV Cache Management for Efficient Multi-Instance Inference in RAG-Powered LLMs

> RAG文書のKVキャッシュをNVMe SSDへ永続化して複数LLMインスタンスで共有し、待ち行列時間にCPU等で先行生成することで重複プリフィルを削減する。
## 書誌情報
- **著者**: Hyungwoo Lee, Kihyun Kim, Jinwoo Kim, Jungmin So, Myung-Hoon Cha, Hong-Yeon Kim, James J. Kim, Youngjae Kim
- **著者・所属**: Sogang University; ETRI; Soteria Inc.
- **公開**: arXiv:2504.11765v1
- **種別**: arXivプレプリント
- **対象**: RAG、KVキャッシュ、NVMe SSD、複数インスタンス推論、プリフィル最適化
- **実装**: FaissベクトルDB、CPUメモリキャッシュ、NVMe上KV格納、複数推論インスタンス用共有KV管理器と先行KV生成器を実装。公開コードURLは論文本文で確認できない。
## 概要
RAGでは検索文書をプロンプトへ追加するためプリフィル計算が増え、最初のトークンまでの時間が長くなる。RAG-DCacheは文書のKVキャッシュを事前計算してNVMe SSD上のベクトルDBへ永続化し、再検索時には文書本文を再計算せずKVを読み込む。Shared RAG-DCacheはこれを複数LLMインスタンスで共有し、混雑時の待ち行列にある要求について空きGPUまたはCPUが検索とKV生成を先行実行する。2基のRTX 2080 SUPERとRyzen 9 3900XT、Samsung 970 EVO NVMeで、CPUをKV生成へ割り当て両GPUを推論へ残す構成が最良となり、top-k=1/2でスループット16.8%/25.2%向上、平均遅延36.8%/29.8%削減を示した。

RAG-DCacheは文書チャンクのKVを事前計算し、埋め込み・文書ID・本文と同じベクトルDBの項目へ対応付けてNVMe SSDへ半永続保存する。Shared RAG-DCacheはこれを中央共有KV管理器へ拡張し、複数LLMインスタンスが同じディスク上のKVを再利用できるようにする。さらに中央要求待ち行列を監視し、一定時間以上待っている質問についてKV生成器が本来の推論順番より前に埋め込み検索とtop-k文書のKV生成を始める。生成場所は空きGPUだけでなくCPUも選べるため、混雑時に発生する待ち時間と推論GPU以外の遊休計算資源を前処理へ変換できる。初期の文書別KVではtop-k>1時に文書間注意を失う問題も実測し、Shared版では検索された文書集合をまとめてプリフィルして組合せ単位のKVとして保存することで品質低下を避ける。

代表結果として、単一インスタンス平均スループットはOPT 1.3B/2.7B/6.7B平均で通常RAGに対して17.53→20.07 QPS。NVMe読込み費用より文書プリフィル再計算の削減が大きい。
## 問題設定
検索拡張生成（Retrieval-Augmented Generation; RAG）は外部文書をプロンプトへ追加して知識を補うが、その文書トークンまで毎要求でプリフィルするため、入力が長いほど最初のトークンまでの時間が増えGPU計算を占有する。同じ文書が多数の質問から繰り返し検索されても通常RAGは毎回同じKVを再計算する。RAGCacheはGPU/CPUメモリへ中間KVを置いて高速化するが、モデル大型化と長文書化に対して主記憶容量が制約になる。TurboRAGはディスクへ事前計算KVを保存するが、実サービスで複数のLLMインスタンスが並行稼働する場合に、あるインスタンスの計算結果を他へ共有したり、混雑による待ち時間中に次要求のKVを準備する仕組みを主眼にしていない。著者らのHotpotQA、SQuAD、TriviaQA分析では50%の質問が参照する文書は全体の22.9%、3.1%、31.4%に集中しており、この局所性を大容量SSDで利用できる余地がある。
## 新規性
RAG-DCacheは文書チャンクのKVを事前計算し、埋め込み・文書ID・本文と同じベクトルDBの項目へ対応付けてNVMe SSDへ半永続保存する。Shared RAG-DCacheはこれを中央共有KV管理器へ拡張し、複数LLMインスタンスが同じディスク上のKVを再利用できるようにする。さらに中央要求待ち行列を監視し、一定時間以上待っている質問についてKV生成器が本来の推論順番より前に埋め込み検索とtop-k文書のKV生成を始める。生成場所は空きGPUだけでなくCPUも選べるため、混雑時に発生する待ち時間と推論GPU以外の遊休計算資源を前処理へ変換できる。初期の文書別KVではtop-k>1時に文書間注意を失う問題も実測し、Shared版では検索された文書集合をまとめてプリフィルして組合せ単位のKVとして保存することで品質低下を避ける。
## 手法
### 手法のあらまし
まず文書コーパスをチャンク化し、all-MiniLM-L6-v2等で埋め込みを作ってFaissへ登録する。同時に対象LLMで各文書または文書集合をプリフィルし、その鍵・値テンソルをNVMe SSDへ保存する。KV管理器はSSDの上にCPU RAMキャッシュを持ち、要求時にはメモリ、SSDの順で検索する。質問が到着するとRAG処理器が埋め込み検索でtop-k文書IDを取得し、対応KVを管理器から受け取る。推論インスタンスは文書本文を再び対象LLMへ通す代わりに保存済みKVを過去状態として注入し、質問トークンだけを追加プリフィルしてデコードする。Shared版では複数インスタンスの前段に中央待ち行列とKV生成器を置く。待ち時間が閾値を超えた質問は、割当先インスタンスが空く前に検索を済ませ、必要KVが未登録なら空きGPUまたはCPUで生成して共有SSDへ追加する。既存KVなら生成を省き、要求が実際にインスタンスへ渡る時点では共有管理器から取得するだけにする。これにより一つのインスタンスが生成した計算結果を全インスタンスが使え、待ち時間とプリフィル準備を重ねられる。文書単位KVを単純連結するとtop-k>1で文書間注意が欠けるため、最終設計では取得文書IDの組合せをキーに文書集合をまとめて計算したKVを保存する。

### ディスク常駐KVキャッシュ
文書チャンクを対象LLMへ一度プリフィルして得たKVテンソルを、埋め込み・文書ID・本文と対応付けてNVMe SSDへ保存する。次に同じ文書が検索された要求では、文書トークンをGPUで再計算せず保存KVを過去状態として読み込むため、プリフィルの重複計算をSSD読出しへ置き換えられる。KV管理器は16GBなどのCPU RAMキャッシュも持ち、頻出または最近使った項目はSSDを再読せず返す。SSDはGPU/CPUメモリより大容量なので多くの文書を保持できる一方、OPT 6.7BとSQuADではKV付きDBが16GBまで増え、保存容量とヒット率のトレードオフが生じる。

### 共有KV管理器
各LLMインスタンスが独立したKVキャッシュを持つのではなく、中央のShared KV キャッシュ Managerがディスク上の一つのKV名前空間を管理する。背景KV生成器や任意の推論インスタンスが新しいKVを作ると中央管理器へ登録され、別インスタンスが同じ文書集合を必要とした時にも再計算せず利用できる。管理器はCPU RAMの追い出し付きキャッシュをSSDの前段に置き、同時期に複数インスタンスから参照される頻出KVのディスクI/Oも減らす。これにより計算結果の共有範囲を単一要求や単一GPUからサービス全体へ広げるが、複数ホスト時のネットワーク転送費は本評価では測定されていない。

### 待ち行列先行生成
高負荷時には質問がLLMインスタンスの空きを待つため、その待ち時間を無駄にしない。KV キャッシュ Generatorは中央待ち行列を監視し、待機時間が設定閾値を超えた質問を見つけると、質問埋め込み、ベクトル検索、top-k文書決定を先に実行する。必要KVが未登録なら空いているGPUまたはCPUで文書集合をプリフィルし、結果を共有SSDへ保存する。質問が実際に推論インスタンスへ割り当てられる頃には文書KVが準備済みとなり、推論GPUは質問部分とデコードへ集中できる。評価ではGPU 1基を生成専用にするよりCPUへ生成を任せてGPU 2基を推論へ残す方が良く、資源配分が重要である。

### top-k集合KV
初期RAG-DCacheは文書ごとに独立してKVを作り、複数文書検索時にそれらを組み合わせていた。しかしtop-kが1を超えると文書同士の注意計算が存在しないため、F1と完全一致を組み合わせた精度指標が通常RAGより低下した。そこでShared版では、ある質問から取得されたtop-k文書をまとめて対象LLMへ入力し、文書間注意を含んだKVを一括生成する。保存時には文書IDの組合せをキーとして管理し、同じ組合せを後続要求が使う場合に再利用する。これにより品質を保てる一方、top-kや文書組合せの種類が増えるほどキャッシュ項目数が膨らみ、単一文書KVより再利用機会が細分化される可能性がある。

### 全体のデータ／制御の流れ
中央要求待ち行列、KV キャッシュ Generator、Shared KV キャッシュ Manager、各インスタンスのPrompt Generator、FaissベクトルDB、NVMe SSD、CPU RAMキャッシュ、複数LLM推論インスタンスから構成される。
## 評価条件
- **ハードウェア**: 単一ホスト。AMD Ryzen 9 3900XT 12コア、NVIDIA RTX 2080 SUPER 8GB×2、RAM 64GB、Samsung 970 EVO NVMe SSD 500GB（読出し3.4GB/s、書込み2.4GB/s）。
- **ソフトウェア**: Faiss IndexFlatIP、all-MiniLM-L6-v2埋め込み。単一インスタンスはfacebook/opt-1.3b/2.7b/6.7b、複数インスタンスはLlama-3.2-1B。
SQuAD v1.1を使用。単一インスタンスでは2,000要求、16GB CPUメモリキャッシュを設定し、通常RAGとRAG-DCacheのTTFT、プリフィル時間、KV読込み時間、QPSをモデル・バッチ別に比較する。複数インスタンスでは1,000要求を40 req/sで流し、top-k=1/2、メモリキャッシュ無効で共有ディスク効果を分離する。構成AはGPU 1基をKV生成、残り1基を推論、構成BはCPUをKV生成、GPU 2基を推論へ使う。データセットをランダム順で複数回処理しディスクKV蓄積によるヒット率変化も観測する。
単一ホスト2GPU/1CPUのRAGサービスとSQuAD中心の評価。Shared版はデコード長の変動を避けるためプリフィル段階に測定を限定し、複数ホスト間のネットワーク共有性能や大規模モデルでのShared版挙動は直接測っていない。
## 主要結果
単一インスタンスRAG-DCacheはOPT 1.3B/2.7B/6.7Bで平均QPSを17.53から20.07へ上げ、TTFTを概ね10〜20%短縮した。複数インスタンスではCPUにKV生成を任せGPU 2基を推論へ残す構成が最良で、top-k=1は23.96→27.98 QPS、75.75→47.92秒、top-k=2は14.34→17.96 QPS、208.22→146.17秒となった。GPU 1基をKV生成専用にすると推論GPUがボトルネックになり、top-k=2では基準より悪化する場合もあった。

- 単一インスタンス平均スループット / 17.53→20.07 QPS (比較対象: 通常RAG; 条件: OPT 1.3B/2.7B/6.7B平均) — NVMe読込み費用より文書プリフィル再計算の削減が大きい。

- 単一インスタンスTTFT / 概ね10〜20%削減 (比較対象: 通常RAG; 条件: SQuAD、複数モデル・バッチ) — モデルとバッチが大きいほど削減するGPU計算量が増え効果が大きい。

- Shared構成B top-k=1 / 23.96→27.98 QPS、75.75→47.92秒 (比較対象: 共有KVなし2GPU推論; 条件: CPU KV生成、GPU×2推論、40 req/s) — CPUの空き計算を待ち時間中のKV準備へ使い、GPU推論並列度を維持する構成が有効。

- Shared構成B top-k=2 / 14.34→17.96 QPS、208.22→146.17秒 (比較対象: 共有KVなし2GPU推論; 条件: CPU KV生成、GPU×2推論) — 文書数増加で絶対負荷は上がるが共有KVにより性能低下を緩和する。

- ストレージ費用 / SQuADで通常Faiss DB 0.5MBに対しKV付きはOPT 1.3B 5.9GB、2.7B 9.9GB、6.7B 16GB、Llama 1B 1GB (比較対象: 通常ベクトルDB; 条件: 全対象KV保持) — 計算削減と引き換えに数GB〜十数GBの永続容量を消費し、局所性に応じた保持選択が必要。

### 負の結果・境界条件
- 初期RAG-DCacheでtop-k>1の文書KVを独立生成すると文書間注意を欠き、通常RAGより精度が低下したため、Shared版ではtop-k文書集合をまとめてKV化する設計へ変更した。GPU 1基をKV生成専用にする構成Aはtop-k=2で残り1基の推論GPUが詰まり、キャッシュのオーバーヘッドが利得を相殺して基準と同等または悪化する試行がある。

### 結果の読み方
SSD容量を使ってプリフィル計算を時間方向に移し、さらに複数インスタンス間で共有することで、同じRAG文書への反復計算を永続的なデータ再利用へ変換する。性能はSSD帯域だけでなく、KV生成へどの計算資源を割り当てるかと待ち行列の混雑度に強く依存する。
## 品質への影響
top-k=1では精度同等。top-k>1は文書単位KVの単純連結では精度低下するため、文書集合を同時処理してKVを生成する必要がある。
## 既存研究との差
RAGCacheのGPU/CPU多段キャッシュに対してSSDを大容量の永続層として前面に出し、TurboRAGの事前計算KVに対して複数LLMインスタンス間の共有と待ち行列時間を使った動的先行生成を追加する。一般的なKVオフロードが単一要求のメモリ不足を解くのに対し、本方式はRAG文書という要求横断で再利用可能な接頭辞をSSD上の共有資産にする。
## 限界
Shared版評価はLlama-3.2-1BとSQuAD、単一ホスト2GPUに限られ、複数ホストで中央KV管理器を共有した際のネットワーク帯域・整合性・障害耐性は未評価。KVはモデル固有でモデル更新時に再生成が必要となり、全SQuAD文書を保持するだけでもOPT 6.7Bで16GBと容量費用が増える。低負荷では待ち行列が短く先行生成機会が少ない。top-k文書の組合せをまとめてKV化すると精度は保ちやすいが、組合せ数が増えて再利用率と保存効率が低下し得る。

## 研究上の位置づけ
SSD/NVMe活用系統で、低速階層を容量拡張だけでなく計算結果の永続共有層として利用する例。特にRAGの文書局所性と待ち行列というワークロード特性を使い、KV生成時刻を前倒しして複数インスタンスへ再利用する。今後はKV圧縮、SSD上の選択的保持、GPUDirect Storage、分散共有キャッシュ、予測型プリフェッチと組み合わせる余地がある。
