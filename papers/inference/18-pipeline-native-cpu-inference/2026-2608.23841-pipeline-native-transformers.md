# Pipeline-Native Transformers: Co-Designing Model Architecture and CPU Inference for Bandwidth-Efficient Autoregressive Decode

## 概要

CPUで1トークンずつ自己回帰デコードする場合、演算能力より主記憶からの重み読み込みが律速しやすい。毎トークン、実際に使う重みを読み込むため、実行順と配置はメモリ帯域を左右する。本論文は、汎用Transformerを実行するランタイムだけを最適化する従来の分離設計を見直し、層間依存関係を変更したモデル構造とCPU推論ランタイムを一緒に設計する独立研究報告である。

提案するcflowは、Q4重みをL2キャッシュに収まるタイルへ並べ、計算で使う順番にストリーミングするCPU向け推論系である。別途、標準Transformerでは逐次処理が必要となる層間依存グラフを書き換え、複数層の重みを縦方向に読む段階実行を可能にするpipeline-native構造を5種類設計・学習した。5構造のうちarch2_4_combinedはクリティカルパス重み転送量を9.00から4.50 MB/tokenに減らし、最良品質の構造から困惑度0.24以内だった。さらに30.9BのMoEを32-vCPU Ice Lakeで動かし、5.94 token/sを報告する。

## 問題設定

標準的なCPUデコードでは、1層の注意機構とFFNを完了してから次層へ進む。次層は前層の残差出力に依存するため、複数層の重みをまとめて先読みしても、計算順とメモリ読み込み順を自由に組み替えられない。重みデータがメインメモリからL2へ運ばれる際のアクセス順がハードウェアプリフェッチャの効き方にも影響するため、汎用形式のままカーネルだけを最適化するだけでは限界がある。

MoEでは、各トークンで選択されるのは全専門家の一部だけなのに、素朴な実装がすべての専門家重みを読み込み、未選択分を捨てる場合がある。CPUの帯域律速環境では、これは実際に使う重み量を大きく上回る転送につながる。著者は、モデル依存グラフ、重みファイル配置、推論スケジューラ、専門家I/Oを一体として扱う。

## 手法

### タイル型ストリーミングランタイム

cflowは重みを128×256要素のQ4タイルに並べ替える。タイルは約18 KBでL2キャッシュに収まるよう設計され、行単位の連続配置ではなく、計算スレッドが消費する順にメモリから取り出される。一般的な単一トークンデコード用の層ごと形式（.cflow）と、層をまたいで段階実行するためのstage-major形式（.vflow）を用意する。QKV射影やgate-up射影を融合し、AVX2によるQ4内積カーネルを組み込む。

MoEの場合、ルータが選んだtop-k専門家だけのタイルをランダムアクセスで読み出す。ファイル形式に依存した実行スケジュールと組み合わせるため、重み配置だけ、またはカーネルだけを単独で変更するより、モデルの依存関係に沿ったデータ移動を目指す。

### 層間依存の書き換え

標準pre-norm Transformerでは次層の注意入力が前層の完全な残差出力に依存し、注意出力の後には同じ層のFFNも実行される。そのため、単一トークンの系列では層間の重み読込順を自由に重ねにくい。報告は、dense_delayとexpert_delayという依存緩和パラメータを定義し、FFN出力や専門家出力の合流を後続段階へ遅らせて、stage-major実行が数学的に成立する構造を検討する。

5つの候補は、注意ストリームとFFNストリームを分離して定期的に同期する構造、dense FFN入力を遅らせる構造、明示的なpipeline registerを持つ構造、ルーティングをdense変換前に行って専門家出力を遅延合流する構造、重み共有した反復ブロック構造である。帯域削減に有利な設計と困惑度に有利な設計は同じではなく、依存緩和の程度が帯域・品質・パラメータ効率の交換条件を作る。

### 遅延認識スケジューラとI/O重ね合わせ

ランタイムは各モデルのdense_delayとexpert_delayを読み、必要な過去の残差をリングバッファに保持する。層の実行時には遅延した残差と、所定の層で合流すべき専門家出力を取り出して計算する。実行系はRustで実装され、arch2_4_combinedとarch4_async_expertsについてPyTorch参照トレースと照合され、出力ノルムの相対誤差0.006%以内かつ検査位置のargmax一致を報告する。

expert_delayは、ルーティングを行う層で選択済み専門家のタイルをストレージから非同期取得し、計算を続けた後、遅延先の層で専門家出力を合流させることでI/O重ね合わせにも利用する。これにより転送と計算を時間的に重ねられる。ただし、I/Oが全体を律速する条件で明示的プリフェッチが常に役立つとは限らず、実測では設計上の主張の一つが否定され、別の主張は結論不能となった。

### 学習と評価の範囲

5つのpipeline-native構造はTinyStoriesで10,000ステップ学習され、勾配発散や学習崩壊なく収束した。これは学習高速化方式の提案ではなく、推論時の依存グラフと帯域を評価するため、変更した構造が学習可能であることを確かめる実験である。訓練したモデルは8.34B規模の密構造などで帯域・困惑度を比較し、さらに30.9B pipeline-native MoEを実CPU上で動かす。

## 評価条件と主要結果

報告はTinyStoriesで学習した5種類の構造に対し、テスト困惑度とクリティカルパス重み帯域を比較する。tile layoutによるキャッシュ読み込みミスは、測定したdense-down射影でrow-major配置の7.29分の1となった。arch2_4_combinedは遅延なし構成の9.00 MB/tokenに対して4.50 MB/tokenを達成し、クリティカルパス上の重み帯域を2倍削減した。テスト困惑度は6.50で、最良品質のarch4の6.26から0.24差である。つまり全構造が両目的を達成するのではなく、同報告の測定ではこの構成だけが明確な帯域削減を示した。

エンドツーエンド比較では、32-vCPU Intel Ice Lake上で30.9B pipeline-native MoEをcflowで動かし、5.94 token/sを得た。比較として同一CPU上でllama.cppはパラメータ数が近い密モデルに4.75 token/s、vLLM CPU backendは1.65 token/sだった。ただしモデル構造が同一でないため、これはランタイム単独の同条件比較ではなく、モデルと実行系を合わせた比較である。報告自身もモデルを揃えた対照実験が今後必要とする。

ディスク常駐専門家を使うI/O実験では、expert_delayによる非同期重ね合わせが最大1.68倍の実測利得を得た。一方、明示的プリフェッチは測定した規模で利益を示さず、stage-majorディスク配置の効果はSSDキャッシュ状態と分離できず結論不能だった。負の結果を含め、I/O律速のままでは先読み利得が現れない条件を提示している。

## 既存研究との差

CPU向け量子化ランタイムは通常、既存モデルの重み形式や演算カーネルを効率化する。ハードウェア意識型モデル設計も幅・深さなどのマクロ構造を選ぶことはあるが、層間依存グラフそのものは維持する。本研究は、モデル側の依存関係を変えて縦方向のstage-major重みストリーミングを可能にし、cflow側がその順序を実行する協調設計を主張する。GPUのバッチ推論や一般的な演算最適化とは異なり、主対象はCPUでの単一トークンデコードである。

## 限界

30.9B MoEの比較はpipeline-nativeモデルと既存ランタイムの密モデルを比べており、同一モデルを異なるランタイムで実行する統制比較ではない。帯域削減も主に著者が定義したモデル形状と測定環境で示された結果で、別の規模・CPU・実運用負荷へそのまま一般化できない。実測結果の一つは未確定で、明示的プリフェッチは測定条件で利益がなかった。

実装の全性能はx86-64 AVX2/FMA経路に依存する。報告時点ではARM NEONやApple Silicon向け最適化は未実装で、スカラー経路はあるものの同等の速度向上は主張されない。新しい依存グラフを持つモデルを学習・配布する必要もあるため、既存Transformerをそのまま実行できる汎用エンジンではない。著者はコード、ベンチマーク、参照トレースを公開し、モデル構造とランタイムの双方を再現可能な研究成果として位置づける。
