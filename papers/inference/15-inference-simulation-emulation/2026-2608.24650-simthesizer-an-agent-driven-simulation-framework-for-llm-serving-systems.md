# Simthesizer：推論提供システムの動的な構造を表すシミュレータと自動拡張

## 概要

大規模言語モデル（LLM）の推論提供では、連続的なバッチ形成、入力処理と生成の分離、KVキャッシュの退避、投機的復号、専門家混合（MoE）、複数回のモデル呼出しを含むエージェント処理など、複雑な機構が急速に増えている。実機で全ての構成を試すのは費用が高く、専用ハードウェアが未発売の場合はそもそも実測できない。シミュレータは設計空間の探索に必要だが、既存の固定的な処理経路へ新機構を追加するたび、大規模な修正が必要になる。

Simthesizerは、計算や通信のイベントだけでなく、要求の振分け、バッチの構成、キャッシュ管理といった**制御判断そのもの**を、実行時に拡張できる有向非巡回グラフ（DAG）へ統一する。さらにSynthesizer agentが自然言語の機能要求を仕様へ落とし、既存の構成要素に対応付け、必要な部分だけ実装し、実機の測定結果や文献の証拠と照合する。実機のLLMを高速化する直接的な推論アルゴリズムではなく、推論提供システムの研究・設計探索を速く正確にするための基盤である。

同一のコーディングエージェントと検証手順を使い、FP8のKV量子化、投機的復号、Mamba混合モデルへの対応を追加した比較では、Simthesizer上の拡張の平均処理率誤差が実機比2.51%、従来シミュレータ上の拡張が6.03%だった。模擬実行時間もLLMServingSim2.0比で最大284.96倍、Vidur比で最大23.19倍短かった。ただし後者は**シミュレーション計算の高速化**であり、モデルの実際のトークン生成速度を同倍率で高めた結果ではない。

## 背景と問題設定

従来の推論提供シミュレータは、モデル実行、要求の到着、バッチ処理、通信などを予め定めた一つの処理経路へ組み込むことが多い。これは一回の入力処理と生成を繰り返す構成では扱いやすいが、エージェントの複数呼出し、外部ツールの待機、動的な経路分岐、入力処理と生成を別ノードへ割り当てる構成、投機的復号の検証ループなどでは、処理経路自体が要求ごとに変わる。既存の処理経路を前提に新しい機構を追加すると、実装が複数箇所へ広がり、既存機構の意味や性能モデルを壊す危険がある。

さらにコーディングエージェントに既存リポジトリを自由に編集させても、シミュレーションの正確性は保証されない。生成コードが構文的に正しく、機能試験に通っても、例えば投機的復号で検証トークン数を誤って数えると、処理率を大きく過大評価する。そこでSimthesizerは、**変更箇所を局所化する抽象化**と、**実機・参照資料に基づく意味検証**をセットで設計する。

## 手法

### 1. 制御判断を含む統一的な動的グラフ

Simthesizerの実行層は、計算ノード、通信ノード、論理ノードの三種類を一つの有向非巡回グラフで表す。計算ノードは指定デバイスで実行するモデル演算、通信ノードはデバイス間のデータ転送、論理ノードは要求到着、経路選択、バッチ形成、状態更新などの制御判断を表す。辺は先行関係であり、全ての前提ノードが終わったときだけ後続ノードを実行可能にする。

計算ノードはスケジュール済みの演算とデバイスが決まれば遅延を確定できるものとして扱い、内部のカーネル詳細は計算費用モデルへ委ねる。通信ノードは他の通信との競合によって完了時刻が変わるため、リンクの帯域状況が変化したときに予定完了イベントを無効化して再登録する。論理ノードは制御状態を更新し、新しいノードや依存関係を実行時に追加できる。これにより、実行層そのものへ投機的復号や分離推論などの専用分岐を埋め込まなくて済む。

イベント駆動の実行器は、依存関係が解決したノードを時刻順の待ち行列に入れ、最も早いイベントから処理する。状態変更でグラフが増えた場合も同じ実行器で処理する。新機構の違いは、どの論理ノードがどの計算・通信ノードを作るか、という局所的なグラフ操作に表れる。

### 2. 動的グラフの操作と制御層

機構を実装するための操作として、論理ノードの追加、計算ノードの追加、通信ノードの追加、依存辺の追加、既存の出辺の切離しなどを提供する。例えば入力処理と生成を別のGPUへ分ける場合、元の入力処理→生成の辺を外し、その間にKV転送ノードを挿入して、転送が完了するまで生成を待たせる。実行層を変更せずに処理経路を表現できる。

制御層は要求の経路選択、システム全体の調整、バッチスケジューリング、モデル実行、モデル記述、計算・通信の時間見積りなどを役割別の構成要素へ分ける。例えばバッチスケジューラは要求を受け取って次のバッチを返す共通インターフェースを持ち、その内部ではチャンク化された入力処理、メモリ予算による受入れ、接頭辞キャッシュなどを自由に実装できる。構成要素の状態はその内部に閉じ込め、他の制御層へ詳細を漏らさない。

既存の構成要素が揃っている場合は構造化設定の組合せだけで推論提供方式を構成できる。未対応の政策が必要な場合は、その政策の構成要素だけを実装し、グラフ実行器や他の構成要素を再利用する。標準の構成には単一・複数インスタンス、入力処理と生成の分離、KV転送、専門家並列、モデル並列、MoEのモデル記述などが含まれる。

### 3. 計算・通信費用モデルの差替え

計算ノードの遅延は、既定では事前に測定したGPU演算の費用表から推定する。層ごとの特性に応じて、トークン数、KVの長さ、問い合わせと文脈の相互作用数、活性化した専門家数などを索引として補間する。全層を同じ総トークン数だけで見積もると、注意層やMoE層の費用を誤るため、層ごとの意味に合わせた索引を使う。

通信側はデバイスとリンクの接続グラフ上で転送経路を求め、共有するリンクの帯域を転送間で分配する。新しい転送が始まると既存転送の完了予測が変わるので、イベントを再計算する。必要なら、より詳細な計算・ネットワークシミュレータへ差し替えられるが、既定の軽量モデルは全体の設計探索を速く行うことを優先する。したがって未計測のカーネルやハードウェアを正確に予測できる保証はなく、費用表の校正範囲が重要となる。

### 4. Synthesizer agentの段階的な機能実装

機能要求を受けたエージェントは、まず要求の意味を明確にする仕様設計段階、次にその意味を既存構成要素へ対応付ける段階、最後に不足部分を実装する段階を経る。成果物として、シミュレータ向けの仕様書、実装先の対応表、検証報告を残す。要求に曖昧な点がある場合、計算・通信・状態遷移に影響する部分を明示的に解決してから実装する。エージェントが自由に新しい実行経路を作るのではなく、既存の構成要素インターフェースとグラフ操作を使うよう制約する。

例えば投機的復号では、ドラフトモデルが作った候補トークンのうち、対象モデルが一度に何個を検証するか、何個を正式に採用するか、KVキャッシュへどの接頭辞まで確定させるかを分けて定義する。候補数と正式採用数を混同すると、対象モデルの計算量や次の要求状態を誤る。Simthesizerでは検証幅をモデル実行側へ、採用済みの進行をスケジューラ管理状態へ割り当て、共通のグラフ実行経路を再利用する。

### 5. 証拠に基づく正確性検証

実機の測定結果がある場合は、同じ要求列、モデル、ハードウェア、設定で実行し、処理率だけでなく、待ち行列長、バッチ構成、資源利用率などの内部の時系列も比較する。ずれが生じたときは、スケジューリング、計算量、通信、依存関係のどの意味付けが原因かを特定し、仕様と実装を修正する。実機がない場合は、論文や参照実装などの技術的根拠を用いて検証するが、この場合は実機との一致を証明できないため、未確認の仮定を検証報告へ残す。

論文の投機的復号の実例では、最初の候補が対象モデルの検証幅を最後の層にしか反映せず、他の層では少ないトークン数で計算したため、実機処理率を13.4%過大評価した。計算の意味付けを修正すると、次の候補の差は6.7%となり、集約処理率では4.7%の過小評価になった。この実例は「コードが動いた」ことと「推論提供を正しく模擬した」ことの違いを具体的に示す。

## 評価

### 実機・比較方式・ワークロード

実機との比較にはNVIDIA RTX Pro 6000 Blackwellを2枚、Intel Xeon Gold 6326、vLLM 0.19.1を用いた。エージェント的な要求にはSWE-bench系とtau-bench系から50～100件を採り、通常の対話にはShareGPTから400件を用いた。エージェント的な要求では、実機からモデル出力とツール呼出しの経路を収集し、ツールの所要時間を予め測ってシミュレーションへ再生した。これは同じ要求経路で性能を比較するための方法であり、ツールの意味的な振舞いまで予測したことにはならない。

比較シミュレータはLLMServingSim2.0とVidur。追加する機構はFP8 KVキャッシュ量子化、EAGLE3型投機的復号、Mambaを含む混合モデルの3種類である。最初の二つにはQwen3 32B、混合モデルにはNemotron-3-Nano 30B-A3Bを用いた。各シミュレータへ同じエージェント、同じ要求、同じ参照資料、同じ費用表、同じ検証枠組みを与え、複数の独立試行の平均を報告した。エージェントは主にCodexを使い、別のエージェントへの転移も調べた。

### 複雑な要求列への追従

通常の密なモデルでは計算が比較的決定的で、模擬処理率は実機の傾向をよく追った。MoEでは、どの専門家が選ばれるか、専門家間でどのように同期するかを統計的に見積もるため、要求ごとの実際の経路とずれが大きくなった。論文は初回トークン遅延（TTFT）、トークン当たりの生成時間（TPOT）、トークン間遅延（ITL）も比較しており、ネットワーク競合やカーネル起動の裾の長い遅延が影響するTTFT・ITLの誤差はTPOTより大きい。処理率の平均誤差だけで全ての遅延分布が正確だと解釈してはならない。

### 新機構の自動追加後の正確性

3種類の機構追加では、同じエージェントと検証枠組みを使ったSimthesizer上の拡張が、実機の平均処理率に対して2.51%の誤差だった。比較シミュレータ上に同じ機構を追加した場合は平均6.03%の誤差となった。KV量子化は主として容量と量子化費用の追跡で済むため各方式とも誤差が小さかったが、投機的復号やMamba混合モデルでは実行経路、モデル構造、スケジューリングが相互に影響し、構成要素の境界が明確なSimthesizerが有利だった。

ただしこの比較は、特定の機構3件、指定したエージェントと費用表、vLLMの実機構成に対する結果である。未知の推論器や別のハードウェアでも2.51%以内に収まる保証はない。また「2.51%」は処理率誤差の平均であり、単一の要求の遅延誤差ではない。

### エージェント用の制約と検証の効果

投機的復号の追加実験で、仕様の解決と自己検証を促す枠組みを取り除くと、処理率・遅延の模擬誤差は1.65～3.69倍へ増えた。機能の意味を十分に解決しないまま実装へ進み、計算・通信・状態遷移の重要な細部を落としやすくなるためである。逆に、構造化された仕様と検証を経ると、誤りを特定して修正しやすい。これはエージェントのモデル性能だけでなく、対象ソフトウェアの抽象化と検証設計が自動実装の品質に影響することを示す。

### シミュレーション実行時間

同じShareGPT要求列と追加機構で模擬実行時間を比較すると、SimthesizerはLLMServingSim2.0より平均164.9倍、最大284.96倍速く、Vidurより平均6.65倍、最大23.19倍速かった。比較側は新機構のために固定的な処理経路へ追加処理を組み込む必要があるのに対し、Simthesizerは共通のイベント実行器を保ったまま局所的な構成要素を差し替えられる。Mamba混合モデルでは層構成が不均一なため、同一層の費用を繰り返し使える密なモデルより模擬時間が長くなる。

**この倍率はシミュレータの実行速度**である。実機のモデルが164.9倍速くなる、LLMの生成遅延が284.96分の1になる、といった解釈は誤りである。シミュレーションの高速化と実機追従性は別の軸として評価する必要がある。

### コーディングエージェントを替えた場合

投機的復号の実装をCodexとClaude Codeで行った比較では、処理率、TTFT、TPOT、ITLの平均誤差がそれぞれ4.1%、4.9%だった。どちらも実機の時間変化を概ね追っており、特定のエージェント専用の命令やツールだけに依存する枠組みではないことを示す。ただし比較は限定されたモデル・機構・要求列であり、任意のコーディングエージェントで同等の結果になるとまでは示していない。

## 既存研究との差と限界

Simthesizerの特徴は、従来の「計算と通信を表すグラフ」の外側に置かれがちな**制御判断もグラフの一部にした**ことにある。要求の経路選択やバッチ形成、状態遷移が実行時に次の計算・通信を決めるため、推論提供の新機構を共通の抽象化へ表現できる。さらに、エージェントにリポジトリ全体の自由編集を許すのではなく、仕様設計・実装対応表・検証報告を残して変更を局所化する。これにより自動実装後の意味的な誤りを発見しやすくする。

限界は、模擬計算費用が事前のGPUプロファイルや統計的なMoE経路推定に依存することである。未測定のハードウェア、未知の通信混雑、カーネル起動の裾遅延、専門家の要求依存性は精度を損ない得る。実機がない場合の参照資料による検証は、実機との一致の証明ではない。エージェントが正しい構造でコードを作れても、モデル化対象の物理的な費用が誤っていれば予測は外れる。

評価対象の機構は3種類、実機は特定のvLLM構成であり、分散した大規模クラスタ、複数の異種ネットワーク、極端な混雑や障害を網羅したものではない。実機処理率の平均誤差が小さくても、個々の要求の裾遅延が同程度に正確とは限らない。模擬実行速度の倍率も比較シミュレータの実装と追加機構に依存する。したがって本研究は、**新しい推論提供機構を迅速に比較するためのシミュレーション研究**として収録し、実機LLMの直接高速化と混同しない。
