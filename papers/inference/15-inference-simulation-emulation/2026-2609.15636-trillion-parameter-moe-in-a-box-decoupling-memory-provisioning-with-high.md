# Trillion-Parameter MoE in a Box: Decoupling Memory Provisioning with High-Bandwidth Flash

## 概要
低並列で兆パラメータ級MoEを1ノードに常駐させる装置では、重みだけでTB級容量が必要になる。HBMだけで容量を満たすと、容量と同時に非常に高い帯域まで購入することになり、低並列の実行時状態には過剰な場合がある。本論文は高帯域フラッシュ（High-Bandwidth Flash; HBF）へ重みを移し、DRAMをKV等の実行時状態専用にしたとき、各階層に本当に必要な容量と帯域を分離して測る。

対象はDSV4-Pro 1.6T/active 49BとKimi-K3 2.8T/active 104B。量子化重みはそれぞれ865GB、1.56TBだが、1Mトークン・batch 1の永続状態は4.66GBと28.99GBである。著者は固定450 TFLOP/s FP8計算器、DRAM状態層、512GB・内部1.6TB/sのHBF複数個からなる装置をモデル化し、LLMServingSim 2.0で3種類の複数ターンagentic traceを流す。

性能地形には、状態DRAM帯域とHBF→ホスト転送帯域にほぼ独立した二つの「膝」が現れる。256GB状態容量の下で基準完了時間+10%以内を満たす帯域/容量比はDSV4-Proで4.0 s^-1、Kimi-K3で1.4 s^-1であり、HBM3eの33.3 s^-1より8〜24倍低い。6個のHBFでは各384GB/s、合計2.30TB/sだけホストへ露出しても10%境界内に入り、4 HBFの全帯域露出6.14TB/s基準より62.5%低い。

## 問題設定
HBFでTB級重みを常駐できても、内部帯域をすべてホストへ出すには広いパッケージI/Oが必要になる。また重みをHBFへ移した後もHBMと同じ帯域/容量比でDRAM状態層を設計すると、KV等の状態量に対して帯域を過剰供給する可能性がある。

論文は二つの問いへ分解する。第一に、重みをHBFへ移した後、状態専用DRAMは容量1GBあたり何GB/s必要か。第二に、HBF個数を増やして内部並列帯域が増えるとき、ホスト側リンクも容量比例で増やす必要があるか、である。二つを独立に掃引し、完了時間が急に悪化し始める性能の膝を探す。

## 手法
### 重みと状態の資源分離
DSV4-Proは61層、384 routed experts、Top-6、Kimi-K3は93層、896 experts、Top-16を持つ。重み容量は865GB/1.56TBなのに対し、1Mトークン状態は4.66GB/28.99GBであり、並列度8でも総常駐量の95.9%/87.1%を重みが占める。これを根拠に重み容量をHBF、動的状態をDRAMへ割り当てる。

Kimi-K3の吸収型潜在注意ではbatch 8・1Mトークン時に層あたり約9.7GBの潜在KVを読むが、投機検証の実効トークンを1から6へ増やしても状態交通量は0.1%未満しか変わらず、演算強度は182.3から1092.9 FLOP/Bへ上がる。状態側は重み配送ほど帯域律速にならないことを示す。

### HBF内部帯域とホスト露出の分離
各HBFを512GB、内部読出し1.6TB/s、16 NAND dies、dieあたり96 planes、4KB page、読出し4usとしてモデル化する。内部帯域のうちホストへ露出する `B_ext` を96GB/s単位で1〜16量子まで掃引し、露出率 `eta_exp=B_ext/B_int` を変える。

HBF個数は1,2,4,6,8,10,12を探索する。個数を増やすと容量だけでなくNAND内部並列性も増えるため、同じホスト総帯域でも少数HBFへ太いリンクを付ける構成と性能が一致しない。必要に応じて各HBFにFP8近傍計算器を置く構成も設計空間に含める。

### 状態層とエンドツーエンドtrace
状態層候補はHBM3e 36GB/1.2TB/s、SOCAMM2 128GB/153.6GB/s、LPCAMM2 64GB/136.5GB/sを基本点とし、個数を変える。帯域/容量比はそれぞれ33.3、1.20、2.13 s^-1である。

評価trace A/B/Cは32/29/52ターン、入力文脈18K〜261K、キャッシュ命中率94.1〜96.6%で、prefillとdecode比率が異なる。各traceを8セッションへ複製し、平均100msの指数到着間隔、8,192トークン超のchunked prefill、実効6トークン・受理長4.27の投機検証を用いる。ルータ負荷はSPEED-Bench実測traceに合わせたPólya-urnで生成する。

## 評価
### 評価条件
|項目|内容|
|---|---|
|方式|LLMServingSim 2.0による設計空間シミュレーション|
|モデル|DSV4-Pro 1.6T/49B active、Kimi-K3 2.8T/104B active|
|計算器|450 TFLOP/s FP8、M次元partition 16|
|HBF|512GB/package、内部1.6TB/s、1〜12 packages|
|状態層|HBM3e、SOCAMM2、LPCAMM2|
|trace|3種のmulti-turn agentic trace、各8 sessions|
|文脈|18K〜261K、cache hit 94.1〜96.6%|
|基準|HBM3e×2 + HBF×4 full exposure、near-HBF compute off|
|目標|基準完了時間の1.10倍以内|

### 主要結果
|条件|指標|結果|読み取り|
|---|---|---|---|
|256GB状態容量|必要帯域/容量比|DSV4-Pro 4.0 s^-1、Kimi-K3 1.4 s^-1|HBM3e 33.3 s^-1は大幅な過剰帯域|
|DSV4-Pro|状態帯域の膝|約0.6〜1.2TB/s|1.2TB/s超では追加帯域の効果が小さい|
|Kimi-K3|状態帯域の膝|約0.4〜0.6TB/s|attention構成差でDSV4-Proより低帯域|
|HBF×6、各4 link quanta|ホスト露出|384GB/s/package、計2.30TB/s|6.14TB/s全露出基準より62.5%低いが1.10倍以内|
|LPCAMM2×8|状態層|512GB、1.09TB/s|DSV4-Proの10%境界を満たす|
|Trace C、同じ6.14TB/s host aggregate|HBF×4×16 quanta vs HBF×8×8|前者約1.05〜1.10倍、後者約0.90倍|HBF個数が内部並列性も増やす|

状態帯域とHBFホスト帯域を二次元に振るとL字型の等性能線になり、一方を極端に不足させた構成は他方を増やしても救えない。逆に両方が膝を越えると追加帯域の利得は小さい。このほぼ直交した性質が、資源を個別にプロビジョニングできる根拠である。

Trace AからCへ純decode比率が約11%→28%→50%へ増えると、重み配送が支配的になりHBFリンクの膝は右へ移る。したがって必要帯域は文脈長だけでは決まらず、prefill/decode構成とキャッシュ命中も含む実ワークロード依存である。

## 既存研究との差
従来のHBF研究はHBFデバイス特性、HBM/HBF間配置、直接データパスなどを主に扱う。本論文は「HBFを使えば容量が増える」こと自体より、重みをHBFへ移した後に状態DRAMとホストリンクをどこまで縮められるかを、兆パラメータMoEのエンドツーエンドtraceで定量化する。

また一般的な大規模データセンタサービングのようにprefill/decodeを別資源へ分離せず、低並列1〜8でcold prefill、cache-hit incremental prefill、投機検証、decodeを固定資源の一装置へ同居させる点が評価対象の特徴である。

## 限界
結果は実機HBF装置の測定ではなく、固定450 TFLOP/s計算器とLLMServingSim 2.0による設計空間モデルである。最終的なパッケージ実現性はdie配置、配線長、信号品質、電力供給に依存し、論文もそれらを別問題として残している。

性能の膝はモデルとtraceに依存する。DSV4-ProとKimi-K3だけでも必要状態帯域が4.0対1.4 s^-1と異なり、decode比率の増加でHBFリンク要求も変わる。したがって「256GB・特定帯域」が全MoEに共通する設計値ではない。

低並列の単一ノード装置を意図しており、高並列continuous batchingやprefill/decode分離クラスタへ数値を直接移すことはできない。近傍計算を含むモデル化も、実装コストや熱設計まで実証したものではない。
