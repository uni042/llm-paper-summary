# HYDRA：混合LLM向け異種チップレットの構成と実行方針を共同設計する

## 概要

HYDRAは、注意機構（Attention）と状態空間モデル（State Space Model、SSM）を混在させた大規模言語モデルの推論サービスに向けて、複数種類の計算・メモリチップレットをどう組み合わせ、配置し、実行時に使い分けるかを探索する設計空間探索（Design Space Exploration、DSE）基盤である。対象は単一GPU上のカーネル最適化ではなく、2.5次元パッケージ上でのチップレット構成、チップ間ネットワーク（Network-on-Interposer、NoI）、高帯域幅メモリ（HBM）配置、要求バッチ制御、実行タスク割当の共同最適化である。

原著は、静的な構成・実行方式と比較して、提案する配置・弾力的割当・動的バッチを組み合わせたとき、12種類のモデル・データ組合せで平均スループット1.55倍、初回トークン遅延（Time To First Token、TTFT）43.7%削減、最大スループット改善2.3倍を報告する。さらにマルコフ連鎖に基づく近似推定器は、数日から8日以上かかる設計空間探索を4〜15分に縮め、全探索で得られる最大スループットの平均93%を回収する。ここでの結果は**論文内のイベント駆動シミュレータによる推定**であり、製造済みの24チップレット・パッケージやGPUクラスタでの直接測定値ではない（原著第VI節、表V）。

論文の主要な発見は、異なる演算器を並べるだけでは効率が決まらず、事前入力処理（prefill）と逐次復号（decode）の時間的な負荷比、HBMまでの通信距離、同時要求数をまとめて設計する必要があることだ。注意機構は文脈長に応じてKVキャッシュ転送量が増える一方、Mamba系は比較的小さい再帰状態を維持するため、同じ設計の最適なメモリ容量と通信帯域は異なる。

## 問題設定と既存研究との差

純粋なTransformerでは、長い入力の事前処理は行列演算が中心となり、逐次復号では過去トークンの鍵・値（KV）キャッシュ参照が支配的になりやすい。Mambaの状態空間ブロックでは、長さに比例するKVキャッシュの代わりに再帰状態を保持するが、ゲート・活性化などの要素ごとの演算が多く、行列積用の演算器だけでは十分に使い切れない。Nemotron-Hのような混合モデルはこの二つの性質を同じ要求の中に含む。

既存のチップレット設計空間探索には、同種の演算器を主に扱うGemini、端末向けのCascade、Transformerの微細構成を対象とするWSC-LLMなどがある。原著表Iによると、HYDRAは最大24チップレットを対象に、混合モデル・マクロ構成・要求到着による実行時変動を同時に表現する点で区別される。従来の静的モデルは、どの演算器に何を割り当てるかが設計時に固定され、入力長・生成長・到着時刻の変化による待ち行列とチップ間通信競合を十分に表現できない。

探索変数は演算器の種類と個数、HBMの個数と担当ブロック、演算器の物理配置、チップ間リンク帯域、最大バッチ数、実行時のタスク割当である。帯域を増やすには物理配線や入出力回路の面積が必要となり、同じダイ面積制約では計算器やSRAMに使える面積が減る。このため、単純に「リンク帯域は大きいほどよい」とはならない。スループットとTTFTも相反し、復号へ演算器を多く割くと定常生成は速くなるが、新規要求の初回出力を待たせることがある。

## 手法：入力から構成候補と実行計画まで

### 1. モデル・要求・ハードウェアの統一記述

入力として、Transformerの注意ブロックとMambaブロックの数、各ブロックの重み・実行状態容量、要求の入力・出力長分布、チップレット種類ごとの計算特性、HBM容量と帯域、パッケージ面積、チップ間ネットワークの構成を受け取る。モデルの演算を全結合層・注意・状態空間演算などのタスク集合に展開し、演算器ごとの処理時間表を用意する。タスクの処理時間には局所メモリアクセスの費用を含め、別のチップレットにあるメモリとの通信時間は別に推定する。

計算チップレットは、注意機構の事前処理用A_p、注意機構の復号用A_d、Mambaの事前処理用M_p、Mambaの復号用M_dという四分類で扱う。さらにHBM3チップレットを組み合わせる。事前処理向けは計算資源とSRAMを概ね均等に配置し、復号向けはメモリ側の面積を相対的に厚くする。これにより、同じ演算種類でも段階ごとに異なる最適資源比を探索できる。

出力は単一の最速構成ではなく、スループットとTTFTの両方で他候補に支配されないパレート前線の構成群である。原著はその中から、平均以上のスループットを持つ候補のうちスループット/TTFTを最大化する均衡構成B*と、スループット最大のM_Tを選び、以降の配置・スケジューラ評価に用いる。

### 2. HBM容量の分割と通信局所性を考慮した配置

配置は二段階で求める。最初にHBMチップレットをインターポーザ外周に配置し、Mambaブロック用と注意ブロック用に分割する。Mamba側の同時要求上限は、概念的に `r_M=floor((N_M*C_HBM-L_M*W_M)/S_M)` の非負値として求める。N_Mは割当HBM数、C_HBMは1基の容量、L_MはMambaブロック数、W_Mはブロックの重み容量、S_Mは1要求の再帰状態容量である。注意側もKVキャッシュを使って同様に求め、両者の小さい方 `min(r_M,r_A)` を最大にするメモリ分割を選ぶ。片方のメモリだけを過剰に増やしても全体同時処理数が伸びないことを、分割目的に反映している。

次に、計算チップレットを主なメモリ群の近くへ配置する。通信費用は、転送量と格子上のマンハッタン距離を掛けたものとして近似し、遠いHBMへ大きなデータを何度も送る配置を不利にする。Mamba計算群と注意計算群の候補位置が競合した場合は、大きな群から順に好ましい位置を割り当てる。この段階の出力は、メモリ容量制約を満たし、計算・通信の双方の負荷を抑える物理配置である。

距離近似は通信混雑そのものを解く厳密なネットワークシミュレーションではない。最初の候補選別を軽くするための指標であり、実行時のリンク競合やホットスポットは後段のイベント駆動シミュレーションで確認する。近くに配置しただけでは復号による恒常的な通信集中を完全に解消できない点も原著図11で示される。

### 3. 動的要求バッチとメモリ圧迫時の先取り停止

新規要求は要求プールに入り、現在のバッチ上限とトークン予算の両方を満たした場合に実行中バッチへ参加する。トークン予算は、現在のバッチ規模と要求ごとのトークン費用の中央値を使って概算する。長い入力や長い生成の要求が混在する状況でも、固定バッチが最長要求の終了を待つ無駄を減らす狙いである。要求の入退場ごとに実行中バッチを更新するため、一般的な連続バッチ処理に近いが、異種演算器とチップ間通信の予算も考慮する。

各要求のKVキャッシュまたはMamba再帰状態は仮想メモリブロックで管理し、物理HBMを必要に応じて確保する。要求を追加・延長するとHBM容量を超える場合は、生成済みトークンが最も少ない要求を先取り停止し、そのメモリを回収してプールへ戻す。すでに長く実行した要求を優先して完了させる方針であり、停止対象の進捗や再開費用によって公平性・待ち時間の偏りが生じ得る。論文はこの方針をメモリ逼迫時の実行制御として使っている。

### 4. 弾力的タスク割当

タスクkを演算器cで実行する費用は、演算器固有の処理時間 `t_comp(k,c)` と通信時間 `t_comm(k,c)` の和で近似する。通信時間は `d_Man(c,m_k)*V_k/B_NoI` と置き、データ量V_k、メモリまでのホップ数、チップ間帯域を考慮する。初期配置では、各チップレットへ割り当てられたタスク費用の合計の最大値を小さくすることで、最も遅い段階を抑える。

実行時には要求の到着や復号長の変動により、初期割当が不均衡になる。弾力的スケジューラは各演算器の待ち行列を観測し、負荷の軽い互換チップレットへ一部タスクを移す。単純な仕事奪取（work stealing）と異なり、メモリまでの距離と元の配置を尊重する。負荷差が小さいなら近くの演算器を使い続け、大きいときだけ通信費用と釣り合う範囲で移動する。この設計が、局所性を失う過剰な移動と、固定割当による遊休の両方を抑える。

### 5. マルコフ近似による探索の高速化

すべての候補について要求到着から通信競合まで細かく模擬すると、探索だけで数日を要する。HYDRAは、演算器N個のうちs個が事前処理に割り当てられ、残りN-s個が復号に割り当てられる状態を連続時間マルコフ連鎖（Continuous-Time Markov Chain、CTMC）の状態として扱う。個々のタスク順序を追わず、どの段階へどの程度の資源が割かれたかという粗い状態に圧縮する。

各状態sにおける事前処理能力G_p(s)と復号能力G_d(s)は、事前処理・復号に特化したチップレットが本来の仕事を行う場合と、他方へ応援する場合の速度を合算する。状態sの滞在割合π_sは流体待ち行列近似で求め、期待スループットを `T_p = Σ_s π_s G_d(s)` とする。TTFTも同じ状態推移から近似する。事前処理に資源を回せばTTFTが下がりやすく、復号に回せば定常生成が伸びやすいという競合を、構成候補ごとに短時間で評価できる。

近似器の出力は「製品の最終性能を証明する数値」ではなく、詳細なイベント駆動シミュレーションへ送る候補の順位付けである。タスク単位の通信衝突、突発的な待ち行列、仮想メモリ操作などは抽象化されるため、近似で選んだ候補は詳細シミュレーションで再検証する必要がある。

## 評価条件と主要結果

### 評価環境と比較軸

原著第VI節では、混合モデルNemotron-H-4B、TransformerのみのLLaMA3-7B、MambaのみのMamba-2.8Bを用い、ArXiv-4K、Bilingual Web Books、LongWriter-6K、LMSYS-Chat-1Mの四つの入力・出力長特性を組み合わせる。24チップレットの2次元メッシュ、HBM3数2〜16、リンク帯域256/384/512/640 GB/s、最大バッチ数2/4/8/16/32/64、インターポーザ面積2700〜3000平方ミリメートルを探索する。各候補は100秒の要求時間をイベント駆動で模擬する。

演算器の性能はMARCAとTSTCの既報の微細構成・カーネル特性、メモリはRamulator、SRAMはCACTI、非線形演算器はFlexSFUを使ってモデル化する。異なる設計の面積と性能は22nmプロセスに正規化して比較する。実験計算機はAMD Ryzen Threadripper 7985WXであり、これは**シミュレーション実行側のCPU**であって、評価対象チップレットを実製造したという意味ではない。

| 弾力的割当 | 静的割当、Nemotron-H | TP/TTFT比1.40〜2.04倍、最大スループット1.17〜1.73倍 | 負荷変動への適応、図12 |

配置単体の効果を詳しく見ると、ラウンドロビン配置に対して、Nemotron-Hの四データ集合で通信考慮配置がTP/TTFT比を平均1.29倍、最大スループットを1.22倍改善する。無作為配置との比較ではTP/TTFT比が1.04〜1.80倍、スループットが1.07〜1.22倍となる。図11のチップ間リンク使用率は、メモリ近接配置が長距離通信を減らす一方、復号に伴う残存ホットスポットがあることを示す。これは通信局所性の利得を裏付けるが、すべての負荷で初回遅延が同時に改善する保証ではない。

弾力的割当は、静的配置に対してNemotron-HでTP/TTFT比1.40〜2.04倍、最大スループット1.17〜1.73倍を示す。先着順の割当と比べても1.04〜1.30倍改善する。仕事奪取方式と比較した八つの条件では六つで優位、残るBilingual Web Booksの二条件でも4%以内の差にとどまる。つまり、通信局所性を保つことが、単に空いている演算器へ仕事を移すことと異なる価値を持つ。

探索高速化は、LLaMA3-7BとMamba2-2.8Bでは全探索がそれぞれ2日8時間、3日1時間を要するのに対し、HYDRAは各4分で済む。Nemotron-H-4Bでは全探索8日8時間に対し15分である。屋根線近似も同じ4〜15分程度で済むが、見つけた最大スループットは全探索比平均74%にとどまり、HYDRAの93%を下回る。論文は設計候補の削減倍率を2520〜8520倍とも報告するが、これはシミュレーション対象候補数の削減であり、LLM生成そのものがその倍率で速くなるわけではない。

### 混合モデルへの汎化と負の結果

原著表IVはJamba-tiny、Zamba2-7B、Nemotron-H-4Bの三種類について、特定モデルだけに最適化した設計が他モデルへどの程度転用できるかを検証する。Jamba特化構成の均衡指標はJambaで1.00だが、Zambaでは0.42、Nemotron-Hでは0.31まで落ちる。三モデルを同時に対象とした設計では、Jamba0.96、Zamba0.91、Nemotron-H0.86となり、最悪条件の劣化を14%に抑える。特化設計の最高値を少し譲っても、モデル更新に耐える構成を得られることが分かる。

ただし、どのモデルへも同時に完全最適な構成が存在するわけではない。最大スループット目的では、三モデル向け共通設計の正規化値はJamba0.99、Zamba0.96、Nemotron-H0.84であり、Nemotron-H特化に比べ16%劣る。多用途サーバ向けの汎用性と、単一モデル専用機のピーク性能は明確に交換条件となる。原著第VI-C節は、均衡指標とスループット指標で転用性が異なる点も示している。

## 限界・実装上の留意点

第一に、性能値は実製造チップレットを稼働させた測定ではなく、既報カーネルの特性、メモリモデル、イベント駆動シミュレーションを組み合わせた推定である。実パッケージの熱制約、電力供給、物理配線、故障率、ホスト側の要求転送などが、モデル化した範囲を超えて性能へ影響する可能性がある。原著の結論も電力・熱・信頼性を今後の研究課題として挙げており、エネルギー効率改善や消費電力削減の定量値は本研究の実測成果として主張していない。

第二に、近似器は事前処理と復号へ割く演算器数という粗い状態に依存する。実際の演算依存関係やネットワーク競合を完全には表現しないため、個別の候補で推定誤差がある。Nemotron-HとLongWriterの組合せでは、静的スケジューリング条件の均衡構成でスループット8%、最大スループット構成で約12%の推定差がある。したがって、マルコフ近似だけを最終採用判定にせず、詳細シミュレーションを後段に残す構成が重要である。

第三に、対象は最大24チップレット・特定の四データ集合・選んだモデルと演算器の組合せである。PCIe越しのGPUクラスタや一般的なRTX 4070 Superの単体推論に、そのまま平均1.55倍の利得が得られるとは言えない。一般の推論基盤へ移植する場合は、GPU間通信やHBM配置ではなく、モデルごとの事前処理/復号負荷とKV・再帰状態の資源配分を共同最適化する考え方が参考になる。

## 関連系統と位置づけ

vLLMの連続バッチやPagedAttention、DistServe・Splitwiseの事前処理/復号分離は実GPUサービングを直接扱う。一方、HYDRAはそれらの動的要求管理の考え方を、混合モデルに特化した異種チップレットの物理構成探索まで拡張する。Mamba専用のMARCAやTransformer専用のTSTCと比べても、個別演算器の回路改善ではなく、演算器の個数・配置・メモリ・リンク・実行方針を横断することが新規性である。

実務的には、混合アーキテクチャのモデルを固定した専用推論機の設計、複数モデルに対応する汎用推論アクセラレータの設計、設計時の候補削減と実行時スケジューラを接続する研究の参照先として有用である。導入判断では、表Vの探索時間と図9〜12の推論性能を混同せず、実測の有無を明記するべきである。
