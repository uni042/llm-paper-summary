# Demystifying AI Platform Design for Distributed Inference of Next-Generation LLM models

> operator-level rooflineとcollective通信modelでLLM構造・serving最適化・分散方式からcompute/memory/network要件を逆算するGenZ。

## 概要

LLM用hardwareの議論では「もっとTFLOPSが必要」「HBM帯域が重要」「networkが律速」といった説明がされるが、どの資源を増やすべきかは推論の段階とmodel構造で変わる。例えばprefillはinput tokenをまとめて行列演算できるためcompute-boundになりやすい。一方decodeは1 stepで追加するtoken数が少なく、巨大weightやKV cacheを読みながら小さい行列演算を繰り返すためmemory-bandwidth-boundになりやすい。

さらにGQAはKV cacheを小さくし、MoEは1 token当たりのactive FLOPsを減らす代わりに総weight容量やexpert通信を増やす。Mambaはattentionとは異なるstateを持つ。Chunked prefillはcompute-heavyなprefill tokenをdecode batchへ混ぜ、speculative decodingはdraft modelを追加する代わりにtarget model 1回当たりの確定tokenを増やす。つまり「同じ70B LLM」でもalgorithmとserving policyを変えると、必要なcompute/memory/networkの比率が変わる。

この設計空間を全部real GPUでbenchmarkするのは高価で、まだ存在しない次世代acceleratorはそもそも測れない。GenZは、モデル・workload・parallelism・hardware specificationを入力にし、operator単位で「computeに何秒かかるか」「memoryから読むのに何秒かかるか」「collective通信に何秒かかるか」を解析的に積み上げる軽量performance modelである。1 forwardの解析は一般的な8-core CPUで約30msとされ、数千構成をdesign-space explorationする用途を狙う。

GenZはLLaMA、OPT、GPT系だけでなくDense/GQA/MoE/Mamba、さらにsliding-window attention、speculative decoding、weight sparsity、KV pruning、mixed precisionなどをparameterとして表現する。実hardwareとの検証ではprefill runtimeのgeomean error 2.73%、decode 1.85%、chunked prefill 1.43%、SN40L/MI300X/Gaudi2を横断したLLaMA3-8Bで5.82%を報告する。

重要なのは「未来hardwareの性能を一点予言する」ことではない。GenZはSLOを入力に、**そのworkloadでは何TFLOPS、何GBのmemory、何TB/sのmemory bandwidth、何GB/sのnetwork、どのlink latencyが必要になるか**を切り分け、どの資源を増やしてももう速くならない境界を探すための解析器である。

## 問題設定

### Hardware requirementはmodel parameter数だけでは決まらない

同じmodelでも、質問応答とRAGではprompt lengthが異なり、code generationではoutput lengthが長くなる。batch sizeが増えればKV cacheも増える。beam searchなら複数sequence分のdecode stateが必要になる。

Memory capacityは大まかに **model weight + KV cache** で決まる。KV cacheはbatch、input length、output length、KV head数、layer数へ比例するため、小型dense modelではweightに対してKVが大きな割合を占めることがある。一方巨大MoEでは総model容量は非常に大きくても1 iterationで読むactive expert weightの比率は小さい。

論文の例ではlargest KV cache / active weightsの比率がLLaMA2-7Bで82%、GPT-4 1.8T相当では2.8%と大きく異なる。したがって「長文脈だから必ずKVが支配的」という単純化もmodel scaleによって外れる。

### Prefillとdecodeは欲しいhardwareが逆になる

Prefillでは多tokenを一度に処理するためGEMMのarithmetic intensityが高く、compute FLOPSを増やすと速くなりやすい。DecodeではweightやKVを毎step読み直す割合が大きく、FLOPSを増やしてもmemory bandwidthが変わらなければ速くならない。

分散通信でも差がある。Tensor ParallelismのAllReduce messageはprefillでは数百MBになることがありbandwidthが重要だが、decodeでは128KB未満のような小messageが多く、network bandwidthよりlink latencyが支配しやすい。

したがって「次世代NPUはFLOPSとnetwork bandwidthを何倍にすべきか」は、prefill/decode/chunkingを分けないと答えられない。

## GenZのモデル化

### 1. Model Characterizer — modelをoperator列へ展開する

GenZはTransformer layerをGEMM、attention score、softmax、KV read/writeなどのoperatorへ分解し、各operatorの計算量 (C_{op}) とmemory access量 (M_{op}) をshapeから計算する。

Dense、GQA、MoE、Mambaではoperator構成やtensor shapeが異なるため、それぞれを明示的にmodel化する。量子化なら1 element当たりbyte数、KV pruningなら保持token数、speculative decodingならdraft/targetの実行回数とacceptance probabilityを変更する。

ここで「optimizationをspeedup係数として後付け」するのではなく、**optimizationによって変わったtensor量・演算量を再びhardware modelへ流す**ため、bottleneckがcompute→memoryへ移る場合も表現できる。

### 2. Operator Roofline — compute時間とmemory時間の遅い方を取る

Roofline modelは、あるoperatorが「演算器の速度」で止まるのか「dataをmemoryから持ってくる速度」で止まるのかを切り分ける簡易性能モデルである。

GenZでは各operator時間を概念的に

[
T_{op}=maxleft(
rac{C_{op}}{FLOPScdot Eff_C},
rac{M_{op}}{BW_{mem}cdot Eff_{mem}}

ight)
]

とする。Peak FLOPSやpeak HBM bandwidthをそのまま使わず、real kernelで得たefficiency factorを掛けるのがポイントである。

例えばPeak 1000 TFLOPSでも、対象shapeのGEMMが実効55%しか出なければ (Eff_C=0.55) として扱う。memory側も同様に実効bandwidthを補正する。この少数のprofile情報によってideal rooflineよりreal systemへ近づける。

### 3. Fast memory / offload memoryを別に表す

各NPUにはHBM/DDRのようなfast memoryと、PCIe/CXL越しCPU memoryやSSD/Flashのようなslow/offload memoryを持たせられる。

それぞれcapacity、bandwidth、efficiencyを別parameterとして扱うため、「model weightがHBMへ収まらないので一部offloadする」といった構成も単なる容量判定ではなくtransfer time込みで比較できる。

### 4. Platform Characterizer — parallelismから必要collectiveを生成する

分散推論ではData Parallelism（DP）、Tensor Parallelism（TP）、Pipeline Parallelism（PP）、Expert Parallelism（EP）、Sequence Parallelism（SP）を指定できる。

GenZはparallelismごとに必要なcollective patternを生成する。TPならAllReduce / AllGather / ReduceScatter、EPならAll-to-AllやAllReduce、PPならSend/Recvなどである。

Network側は複数dimensionを持つinterconnectとして、link bandwidth、link latency、efficiencyを指定する。collective runtimeはASTRA-simのtopology-aware algorithmへ渡して推定する。これにより「8 GPUだから通信X ms」という定数ではなく、scale-up fabricとscale-out networkの違いを設計変数にできる。

### 5. Serving workloadをprefill / decode / chunkingへ変換する

入力長 (	au_p)、出力長 (	au_d)、batch、beam size、chunk sizeなどから各stageのoperator shapeを生成する。

Chunked prefillではdecode requestとprefill chunkを同じforwardへ入れるため、「compute-bound prefillとmemory-bound decodeを混ぜてGPU utilizationを上げる」という効果をtensor shapeレベルで反映する。

Speculative decodingではdraft token数Nとacceptance probability (gamma) から、1 target passで期待何token確定するかを求める。同時にdraft model自体のweight/KV memoryとruntimeも追加するため、acceptanceが低い場合に「speculative decodingの方が遅い」領域も出せる。

## 実機検証

### 代表的な検証条件

| 検証 | Hardware / model | 結果 |
|---|---|---:|
| Prefill / Decode | V100/A100/H100等、LLaMA2-7B/13B、OPT-175B | geomean error 2.73% / 1.85% |
| Chunked prefill | 2×A100、LLaMA2-7B、batch 1–32、input 512–2048、chunk 256/768 | 1.43% |
| 異種accelerator | 8×SambaNova SN40L、1×AMD MI300X、1×Intel Gaudi2、LLaMA3-8B | 5.82% |
| Interconnect | 2/4/8×H100 HGX、NCCL AllReduce | decode 3.89%、prefill 2.7% |

H100 HGXのnetwork validationではNVLink実効効率を約75%、1 GPU当たりeffective bandwidthを約350 GB/sとしている。

Prefillとdecodeのcollective errorを別に見るのは、message sizeの性質が違うからである。DecodeのAllReduceは約50–128KB規模でlink latencyの影響が強く、prefillは数百MBでbandwidthが支配する。

## GenZで分かったこと

### 1. Chunked prefillはmodel architectureによって効き方が違う

GPT-3型dense modelとLLaMA3.1-405B GQAをGB200-like NPU、TP=4で比較すると、decode batchが増えた際のKV cache負担が大きく異なる。

Dense modelではKV cacheが大きくなり、chunk内にdecode batchを多く入れるとattention/KV memory bandwidthがbottleneckになる。一方GQAはKV head数を減らしているため、405Bという大きいmodelでもKV占有率の伸びが緩く、より大きなbatchを載せられる。

「parameter数が大きいmodelほどbatchを載せられない」とは限らず、KV architectureがplatform requirementを大きく変える例である。

### 2. Speculative decodingはNを増やせば常に速くなるわけではない

GenZはdraft token数Nとacceptance (gamma) を変えて、LLaMA3.1-70B + 8B draft、Gemma2-27B + 2B draftを分析する。

Nを16へ増やすとdraft modelを長く回すcostが増え、(gamma=0.7,N=16) では通常decodeより遅くなる。N=4でも(gammaapprox0.5) ではほぼbaselineと同等に留まる。

さらにdraft modelのweightとKVがmemoryを追加で消費する。32K input/output・batch 4の例では総追加memoryが約25–28%になる。アルゴリズム上のtarget call削減だけでhardware要件を見ないと、memory capacity側で失敗することを示す。

### 3. SLOからcompute / memory / bandwidthを逆算できる

GenZはTTFTをprefill側、TPOT（Time Per Output Token）をdecode側のSLOとして、必要platform資源を逆算する。

固定modelならprefill compute requirementは概ね

[
TFLOPS_{req}propto rac{Bcdot	au_p}{TTFT}
]

となり、promptが長いRAGではcompute requirementが増える。論文ではQA→RAG QAでprefill側必要TFLOPSが全model平均5.41倍へ増える。

Decodeのmemory bandwidthは概ね

[
BW_{req}propto
rac{ActiveModel+KVCache}{TPOT}
]

で、巨大modelではweight readが支配するため、GPT-4相当ではcontextを10倍にしたRAGでもmemory-bandwidth requirement増加が8%に留まる例がある。

このように「long contextなら必ずmemory bandwidth 10倍」ではなく、active model weightとの比で決まる。

## 次世代hardwareのcase study

GenZは仮想5T parameter Dense-GQA modelを32 NPU platformで動かし、TFLOPS、HBM bandwidth、interconnect bandwidth、link latencyを1つずつ増減してsensitivityを見る。

| 増やすhardware特性 | Prefill | Decode | Chunked prefill |
|---|---|---|---|
| Compute TFLOPS | 長contextで大きく効く | ほぼ効かない | large chunk / 少decodeで効く |
| Memory BW | compute-boundなのでほぼ効かない | ほぼ比例して効く | decodeが多い時に効く |
| Network BW | 大message prefillで効く | 小messageなので効きにくい | large chunkで効きやすい |
| Network latency改善 | short-context prefillで一部効く | 大きく効く | small chunkで効きやすい |

この表が論文のhardware-design messageをよく表す。FLOPS・HBM・networkを一律に同率増強するのではなく、対象serving regimeでbottleneckになっているresourceだけを増やすべきである。

論文はさらにGPU型multi-chip、wafer-scale、SRAM-centric chip cluster、Transformer-specific ASICを同じGenZ parameterへ落とし、current 8B/70B/405Bから5T/10T modelまでthroughputとenergy効率を比較する。これは特定vendorを一律順位付けする目的ではなく、architectureのcompute/memory/network balanceがworkloadごとにどこで有利になるかを見るdesign studyである。

## 既存研究との差

Ideal rooflineだけならoperatorのcompute-vs-memory balanceは見られるが、model architecture、serving optimization、distributed collectiveを横断したplatform analysisは難しい。ASTRA-simなどはnetwork-centricなdistributed training simulationに強いが、LLM inference固有のprefill/decodeやGQA/MoE/Mamba、KV cache、speculative decodingをそのまま高水準入力にはしない。

GenZはcycle-accurate simulatorほど細かいhardware内部を再現する代わりに、**LLMの構造とserving policyを変更しても30ms級で次のdesign pointを評価できる解析速度**を重視する。ハードウェア設計の初期段階や大きなparameter sweepに適した位置付けである。

## 限界

GenZの予測精度はefficiency factorに依存する。新しいGPUや未知kernelでreal utilization profileがない場合、peak FLOPS/BWだけを入れれば実測とずれる可能性がある。

Operator時間はroofline型のmax(compute,memory)を基本とし、kernel fusion、cache hierarchy、fine-grained overlap、runtime scheduler、queueing、OS noiseなど実装固有の効果を全てcycle-levelで再現するものではない。

Communicationも論文評価ではnon-overlapを基本仮定としており、compute-communication overlapが強い最新kernelでは実run timeとの差が変わり得る。未来5T/10T platform studyはこのanalytical model上のdesign-space analysisであり、実在hardware上の性能実証とは区別する必要がある。
