# Demystifying AI Platform Design for Distributed Inference of Next-Generation LLM models

> 演算子-level ルーフラインと集合通信通信モデルでLLM構造・推論提供最適化・分散方式からcompute/メモリ/ネットワーク要件を逆算するGenZ。

## 概要

LLM用ハードウェアの議論では「もっとTFLOPSが必要」「HBM帯域が重要」「ネットワークが律速」といった説明がされるが、どの資源を増やすべきかは推論の段階とモデル構造で変わる。例えばプリフィルは入力 トークンをまとめて行列演算できるため計算律速になりやすい。一方デコードは1 stepで追加するトークン数が少なく、巨大重みやKV キャッシュを読みながら小さい行列演算を繰り返すためメモリ-帯域-boundになりやすい。

さらにGQAはKV キャッシュを小さくし、MoEは1 トークン当たりの活性 FLOPsを減らす代わりに総重み容量や専門家通信を増やす。Mambaは注意機構とは異なる状態を持つ。Chunked プリフィルはcompute-heavyなプリフィル トークンをデコード バッチへ混ぜ、投機的復号は下書きモデルを追加する代わりに対象モデル 1回当たりの確定トークンを増やす。つまり「同じ70B LLM」でもalgorithmと推論提供 policyを変えると、必要なcompute/メモリ/ネットワークの比率が変わる。

この設計空間を全部real GPUでベンチマークするのは高価で、まだ存在しない次世代acceleratorはそもそも測れない。GenZは、モデル・ワークロード・並列化・ハードウェア specificationを入力にし、演算子単位で「computeに何秒かかるか」「メモリから読むのに何秒かかるか」「集合通信通信に何秒かかるか」を解析的に積み上げる軽量performance モデルである。1 順伝播の解析は一般的な8-core CPUで約30msとされ、数千構成をdesign-space explorationする用途を狙う。

GenZはLLaMA、OPT、GPT系だけでなくDense/GQA/MoE/Mamba、さらにsliding-window 注意機構、投機的復号、重み sparsity、KV 枝刈り、mixed precisionなどをパラメータとして表現する。実ハードウェアとの検証ではプリフィル ランタイムのgeomean error 2.73%、デコード 1.85%、chunked プリフィル 1.43%、SN40L/MI300X/Gaudi2を横断したLLaMA3-8Bで5.82%を報告する。

重要なのは「未来ハードウェアの性能を一点予言する」ことではない。GenZはSLOを入力に、**そのワークロードでは何TFLOPS、何GBのメモリ、何TB/sのメモリ 帯域、何GB/sのネットワーク、どのリンク 遅延が必要になるか**を切り分け、どの資源を増やしてももう速くならない境界を探すための解析器である。

## 問題設定

### Hardware requirementはmodel parameter数だけでは決まらない

同じモデルでも、質問応答とRAGではプロンプト lengthが異なり、コード generationでは出力 lengthが長くなる。バッチ サイズが増えればKV キャッシュも増える。beam searchなら複数系列分のデコード 状態が必要になる。

Memory capacityは大まかに **モデル 重み + KV キャッシュ** で決まる。KV キャッシュはバッチ、入力 length、出力 length、KV ヘッド数、層数へ比例するため、小型密 モデルでは重みに対してKVが大きな割合を占めることがある。一方巨大MoEでは総モデル容量は非常に大きくても1 iterationで読む活性 専門家 重みの比率は小さい。

論文の例ではlargest KV キャッシュ / 活性 重みの比率がLLaMA2-7Bで82%、GPT-4 1.8T相当では2.8%と大きく異なる。したがって「長文脈だから必ずKVが支配的」という単純化もモデル scaleによって外れる。

### Prefillとdecodeは欲しいhardwareが逆になる

Prefillでは多トークンを一度に処理するためGEMMのarithmetic intensityが高く、compute FLOPSを増やすと速くなりやすい。Decodeでは重みやKVを毎step読み直す割合が大きく、FLOPSを増やしてもメモリ 帯域が変わらなければ速くならない。

分散通信でも差がある。Tensor ParallelismのAllReduce メッセージはプリフィルでは数百MBになることがあり帯域が重要だが、デコードでは128KB未満のような小メッセージが多く、ネットワーク 帯域よりリンク 遅延が支配しやすい。

したがって「次世代NPUはFLOPSとネットワーク 帯域を何倍にすべきか」は、プリフィル/デコード/chunkingを分けないと答えられない。

## GenZのモデル化

### 1. Model Characterizer — modelをoperator列へ展開する

GenZはTransformer 層をGEMM、注意機構 score、softmax、KV read/writeなどの演算子へ分解し、各演算子の計算量 (C_{op}) とメモリ access量 (M_{op}) を形状から計算する。

Dense、GQA、MoE、Mambaでは演算子構成やテンソル 形状が異なるため、それぞれを明示的にモデル化する。量子化なら1 element当たりbyte数、KV 枝刈りなら保持トークン数、投機的復号ならドラフト/対象の実行回数と受理率 probabilityを変更する。

ここで「optimizationを高速化倍率係数として後付け」するのではなく、**optimizationによって変わったテンソル量・演算量を再びハードウェア モデルへ流す**ため、ボトルネックがcompute→メモリへ移る場合も表現できる。

### 2. Operator Roofline — compute時間とmemory時間の遅い方を取る

Roofline モデルは、ある演算子が「演算器の速度」で止まるのか「dataをメモリから持ってくる速度」で止まるのかを切り分ける簡易性能モデルである。

GenZでは各演算子時間を概念的に

[
T_{op}=maxleft(
rac{C_{op}}{FLOPScdot Eff_C},
rac{M_{op}}{BW_{mem}cdot Eff_{mem}}

ight)
]

とする。Peak FLOPSやpeak HBM 帯域をそのまま使わず、real カーネルで得た効率 factorを掛けるのがポイントである。

例えばPeak 1000 TFLOPSでも、対象形状のGEMMが実効55%しか出なければ (Eff_C=0.55) として扱う。メモリ側も同様に実効帯域を補正する。この少数のprofile情報によってideal ルーフラインよりreal システムへ近づける。

### 3. Fast memory / offload memoryを別に表す

各NPUにはHBM/DDRのようなfast メモリと、PCIe/CXL越しCPU メモリやSSD/Flashのようなslow/オフロード メモリを持たせられる。

それぞれcapacity、帯域、効率を別パラメータとして扱うため、「モデル 重みがHBMへ収まらないので一部オフロードする」といった構成も単なる容量判定ではなくtransfer time込みで比較できる。

### 4. Platform Characterizer — parallelismから必要collectiveを生成する

分散推論ではData Parallelism（DP）、Tensor Parallelism（TP）、Pipeline Parallelism（PP）、Expert Parallelism（EP）、Sequence Parallelism（SP）を指定できる。

GenZは並列化ごとに必要な集合通信 patternを生成する。TPならAllReduce / AllGather / ReduceScatter、EPならAll-to-AllやAllReduce、PPならSend/Recvなどである。

Network側は複数dimensionを持つinterconnectとして、リンク 帯域、リンク 遅延、効率を指定する。集合通信 ランタイムはASTRA-simのtopology-aware algorithmへ渡して推定する。これにより「8 GPUだから通信X ms」という定数ではなく、scale-up fabricとscale-out ネットワークの違いを設計変数にできる。

### 5. Serving workloadをprefill / decode / chunkingへ変換する

入力長 (	au_p)、出力長 (	au_d)、バッチ、beam サイズ、chunk サイズなどから各段の演算子 形状を生成する。

Chunked プリフィルではデコード リクエストとプリフィル chunkを同じ順伝播へ入れるため、「計算律速 プリフィルとメモリ律速 デコードを混ぜてGPU utilizationを上げる」という効果をテンソル 形状レベルで反映する。

Speculative 復号ではドラフト トークン数Nと受理率 probability (gamma) から、1 対象 passで期待何トークン確定するかを求める。同時に下書きモデル自体の重み/KV メモリとランタイムも追加するため、受理率が低い場合に「投機的復号の方が遅い」領域も出せる。

## 実機検証

### 代表的な検証条件

| 検証 | Hardware / モデル | 結果 |
|---|---|---:|
| Prefill / Decode | V100/A100/H100等、LLaMA2-7B/13B、OPT-175B | geomean error 2.73% / 1.85% |
| Chunked プリフィル | 2×A100、LLaMA2-7B、バッチ 1–32、入力 512–2048、chunk 256/768 | 1.43% |
| 異種accelerator | 8×SambaNova SN40L、1×AMD MI300X、1×Intel Gaudi2、LLaMA3-8B | 5.82% |
| Interconnect | 2/4/8×H100 HGX、NCCL AllReduce | デコード 3.89%、プリフィル 2.7% |

H100 HGXのネットワーク validationではNVLink実効効率を約75%、1 GPU当たりeffective 帯域を約350 GB/sとしている。

Prefillとデコードの集合通信 errorを別に見るのは、メッセージ サイズの性質が違うからである。DecodeのAllReduceは約50–128KB規模でリンク 遅延の影響が強く、プリフィルは数百MBで帯域が支配する。

## GenZで分かったこと

### 1. Chunked prefillはmodel architectureによって効き方が違う

GPT-3型密 モデルとLLaMA3.1-405B GQAをGB200-like NPU、TP=4で比較すると、デコード バッチが増えた際のKV キャッシュ負担が大きく異なる。

Dense モデルではKV キャッシュが大きくなり、chunk内にデコード バッチを多く入れると注意機構/KV メモリ 帯域がボトルネックになる。一方GQAはKV ヘッド数を減らしているため、405Bという大きいモデルでもKV占有率の伸びが緩く、より大きなバッチを載せられる。

「パラメータ数が大きいモデルほどバッチを載せられない」とは限らず、KV 構成が基盤 要件を大きく変える例である。

### 2. Speculative decodingはNを増やせば常に速くなるわけではない

GenZはドラフト トークン数Nと受理率 (gamma) を変えて、LLaMA3.1-70B + 8B ドラフト、Gemma2-27B + 2B ドラフトを分析する。

Nを16へ増やすと下書きモデルを長く回すコストが増え、(gamma=0.7,N=16) では通常デコードより遅くなる。N=4でも(gammaapprox0.5) ではほぼ比較対象と同等に留まる。

さらに下書きモデルの重みとKVがメモリを追加で消費する。32K 入力/出力・バッチ 4の例では総追加メモリが約25–28%になる。アルゴリズム上の対象 call削減だけでハードウェア要件を見ないと、メモリ capacity側で失敗することを示す。

### 3. SLOからcompute / memory / bandwidthを逆算できる

GenZはTTFTをプリフィル側、TPOT（Time Per Output Token）をデコード側のSLOとして、必要基盤資源を逆算する。

固定モデルならプリフィル compute 要件は概ね

[
TFLOPS_{req}propto rac{Bcdot	au_p}{TTFT}
]

となり、プロンプトが長いRAGではcompute 要件が増える。論文ではQA→RAG QAでプリフィル側必要TFLOPSが全モデル平均5.41倍へ増える。

Decodeのメモリ 帯域は概ね

[
BW_{req}propto
rac{ActiveModel+KVCache}{TPOT}
]

で、巨大モデルでは重み readが支配するため、GPT-4相当ではcontextを10倍にしたRAGでもメモリ-帯域 要件増加が8%に留まる例がある。

このように「long contextなら必ずメモリ 帯域 10倍」ではなく、活性 モデル 重みとの比で決まる。

## 次世代hardwareのcase study

GenZは仮想5T パラメータ Dense-GQA モデルを32 NPU 基盤で動かし、TFLOPS、HBM 帯域、interconnect 帯域、リンク 遅延を1つずつ増減してsensitivityを見る。

| 増やすハードウェア特性 | Prefill | Decode | Chunked プリフィル |
|---|---|---|---|
| Compute TFLOPS | 長contextで大きく効く | ほぼ効かない | large chunk / 少デコードで効く |
| Memory BW | 計算律速なのでほぼ効かない | ほぼ比例して効く | デコードが多い時に効く |
| Network BW | 大メッセージ プリフィルで効く | 小メッセージなので効きにくい | large chunkで効きやすい |
| Network 遅延改善 | short-context プリフィルで一部効く | 大きく効く | small chunkで効きやすい |

この表が論文のハードウェア-design メッセージをよく表す。FLOPS・HBM・ネットワークを一律に同率増強するのではなく、対象推論提供 regimeでボトルネックになっている資源だけを増やすべきである。

論文はさらにGPU型multi-chip、wafer-scale、SRAM-centric chip cluster、Transformer-specific ASICを同じGenZ パラメータへ落とし、current 8B/70B/405Bから5T/10T モデルまでスループットとenergy効率を比較する。これは特定vendorを一律順位付けする目的ではなく、構成のcompute/メモリ/ネットワーク balanceがワークロードごとにどこで有利になるかを見るdesign studyである。

## 既存研究との差

Ideal ルーフラインだけなら演算子のcompute-vs-メモリ balanceは見られるが、モデル 構成、推論提供 optimization、distributed 集合通信を横断した基盤 analysisは難しい。ASTRA-simなどはネットワーク-centricなdistributed 学習 シミュレーションに強いが、LLM inference固有のプリフィル/デコードやGQA/MoE/Mamba、KV キャッシュ、投機的復号をそのまま高水準入力にはしない。

GenZはcycle-accurate simulatorほど細かいハードウェア内部を再現する代わりに、**LLMの構造と推論提供 policyを変更しても30ms級で次のdesign pointを評価できる解析速度**を重視する。ハードウェア設計の初期段階や大きなパラメータ sweepに適した位置付けである。

## 限界

GenZの予測精度は効率 factorに依存する。新しいGPUや未知カーネルでreal utilization profileがない場合、peak FLOPS/BWだけを入れれば実測とずれる可能性がある。

Operator時間はルーフライン型のmax(compute,メモリ)を基本とし、カーネル 融合、キャッシュ hierarchy、fine-grained 重畳、ランタイム スケジューラ、queueing、OS noiseなど実装固有の効果を全てcycle-levelで再現するものではない。

Communicationも論文評価ではnon-重畳を基本仮定としており、compute-通信 重畳が強い最新カーネルでは実run timeとの差が変わり得る。未来5T/10T 基盤 studyはこのanalytical モデル上のdesign-space analysisであり、実在ハードウェア上の性能実証とは区別する必要がある。
