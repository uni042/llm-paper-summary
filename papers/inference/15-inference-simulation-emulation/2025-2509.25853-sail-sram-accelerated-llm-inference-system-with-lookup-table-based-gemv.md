# SAIL: SRAM-Accelerated LLM Inference System with Lookup-Table-based GEMV

## 概要

SAIL（SRAM-Accelerated Inference of LLMs）は、量子化されたLLMをCPUベースのサーバで効率的に推論するため、CPUのLast-Level Cache（LLC）の各sliceの近傍に演算可能なSRAM（C-SRAM）を追加し、低ビット重みの行列ベクトル積（GEMV）をLook-Up Table（LUT）で処理するハードウェア・ソフトウェア共同設計である。量子化のbit幅が2〜8bitなどで変化しても、専用のbit幅固定演算器を多数設けずに対応することを狙う。

主な構成要素は、(1) キャッシュ近傍のLUT-GEMV、(2) 複数利用者の処理をtensor単位にまとめるスケジューリング、(3) キャッシュを二分してDRAMからのロードと演算を重ねるping-pongパイプライン、(4) 入力パターンの再利用を見つけるPattern-Aware LUT、(5) C-SRAM内部の並列型変換である。これらによりモデル重みのデータ移動と低ビット演算の無駄を削減する。

著者はARM Neoverse-N1系CPUに提案機構を加えた**修正gem5シミュレータ**で評価し、CPU baseline比最大10.7倍の速度、GCP料金を用いた推定で最大19.9倍のtokens per dollarを報告する。**SAIL搭載の実チップを製造して実測した結果ではない**。比較対象のAMX CPUやNVIDIA V100/A100には実機ベンチマークが含まれ、SAILの推定結果との測定基盤が異なる。GPUに対するコスト優位もハードウェアの見積りとクラウド価格の仮定に依存する。

## 問題設定：低ビット量子化とCPUメモリ階層

LLMのprefillは比較的大きな行列積をまとめて処理できるが、1トークンずつ生成するdecodeは、モデル重みとKVを繰り返し読むためメモリ帯域に制約されやすい。CPUは広く利用できるが、2〜4bitの低ビット重みを直接扱うSIMD演算器の対応が限られ、packing/unpacking、dequantization、型変換が追加コストとなる。GPUは高帯域メモリと大規模並列演算器を備える一方、コストやメモリ容量の制約がある。

既存のProcessing-in-Memory（PIM）は演算をデータ近傍へ移すことで帯域の壁を回避しようとする。しかしDRAM側PIMはCPUの浮動小数点演算との連携が重く、cache内部PIMは所定の位置へデータを集める転送が高コストとなり得る。Near-cache方式はCPUとの連携が容易だが、cache外部帯域が制約となる。SAILはLLC sliceに近接したC-SRAMへ高帯域にアクセスし、低ビットGEMVをLUTで実行することで、これらのトレードオフを改善する。

LUT方式では、少数の重みの組合せ和を予めテーブル化し、入力activationのbitパターンに応じてテーブルを参照する。`NBW`個の基底重みを使うと`2^NBW`個の表エントリが必要になる。NBWが大きいと演算回数は減る一方、テーブル容量と構築コストが指数的に増える。SAILはこのNBW、bit幅、バッチサイズの三者を同時に調整する。

## 手法：ハードウェア構成

### 1. LLC slice近傍のC-SRAM

提案は32MBの共有L3キャッシュを32 sliceに分けたARM系CPUを基準とし、各sliceの近くに演算可能なC-SRAM配列を追加する。C-SRAMは通常のSRAM保存機能に加え、複数wordlineの同時活性化とsense amplifierを使うbitline演算を行う。transpose unitは水平配置と垂直配置のデータを変換し、reconfigurable control unitが量子化精度に応じた演算を制御する。

C-SRAMの演算結果はCPUのvector engineへ渡され、必要なdequantizationや残差演算などの浮動小数点処理を担当する。つまりCPUを完全に置き換えるのではなく、**低ビットGEMVをC-SRAMへ寄せ、残りを既存CPUへ分担する**。非LLM用途ではC-SRAMを追加のLLC容量として使う設計も想定される。専用の新命令`lutmm_1k`を加えるが、実際の商用CPUのISAに搭載されているわけではない。

### 2. LUT-GEMVの計算手順

NBW=3なら3個の基底重みに対して8個の部分和をLUTへ用意する。入力activationの各bit面を調べ、そのbitパターンに対応する重み和を引き、bit位置に応じてshift-and-addする。これにより、低ビット乗算を直接繰り返すより効率的に計算できる。SAILはC-SRAM内でテーブルを構築し、複数トークン・利用者の入力で再利用する。

オフラインでLUTを全部保存すれば構築コストは減るが、モデル容量が増える。原著はQ4・NBW=4で最大3.75倍のモデルサイズになる例を示し、オンラインLUT構築を採用する。オンライン構築のオーバーヘッドは設定によりend-to-end cyclesの3〜12%と報告される。低bitだから常に高速とは限らず、NBWとbatch sizeを同時に調整しなければ逆効果になる。

### 3. Tensor-level schedulingとping-pong buffer

通常のリクエスト単位処理では、各ユーザーの全層を順に処理するため、巨大なモデル重みをcacheへ何度も読み直す可能性がある。SAILは**layer/tensor単位で複数ユーザーの計算をまとめる**。ある層の重みをDRAMからLLCへロードしたら、その重みを使う複数リクエストのGEMVを処理してから次層へ進む。これにより重みロードを複数ユーザーで共有する。

LLC sliceを二つの領域に分け、一方へ次のtensorをロードしながら他方をC-SRAMが読み、演算する。次の段階で役割を交換するping-pong bufferを形成する。著者はbatch=8でパイプラインが良好になる例を示すが、LUT構築・量子化bit幅まで含めた最適batchは一意ではない。計算が転送より短いメモリ律速条件では、演算と転送を重ねても転送時間を完全には消せない。

### 4. Pattern-Aware LUT再利用

入力activationのbitパターンが繰り返されることに着目し、Data Feeding Module（DFM）へ32-entryの全連想Pattern Reuse Tableを追加する。テーブルにはパターンhashと直前のLUT結果を保存し、hit時はC-SRAMのLUTアクセスを省略する。著者は入力パターンの約17%に再利用性があると観測し、この機構で計算cycleを13.8%減らしたと報告する。

PRT自体のハードウェアコストはFreePDK-45nmで評価され、8 DFM合計で0.01mm²未満、2mW未満と推定される。ただしこれはPRT部分の面積・電力であり、C-SRAMやcache制御を含むシステム全体の消費電力を示す値ではない。

### 5. In-memory型変換

量子化GEMVの出力を浮動小数点へ戻す処理はCPU vector engineの負担となる。SAILはSRAMの並列論理演算を使い、符号付き整数からIEEE-754単精度浮動小数点への変換を実行するアルゴリズムを提案する。原著のAlgorithm 1は入力整数幅`n<=25`に制限し、先頭1の位置、指数、仮数をbit演算で構築する。

この型変換は一般の浮動小数点演算すべてをC-SRAMで代替するものではない。原著はNaNやsubnormal等の例外ケースをサポートしないと明記している。LLM推論の通常範囲では有効でも、完全なIEEE-754演算器と同等の機能を保証しない。dequantization後の一部処理はCPU側に残る。

### KVキャッシュとの互換性

原著§III-Bでは、量子化済みKVと非量子化KVの両方を扱う設計を説明する。新トークンのKey/Valueを生成すると、必要に応じてCPU側vector engineでdequantizationやre-quantizationを行ってキャッシュへ保存する。QとK_cacheの積では、キャッシュの転置行列をC-SRAM配列へcolumn方向に分割し、LUT-GEMVを使う。

著者はKV関連の動的行列積がend-to-end遅延の約5%とプロファイルしていると述べるが、これは対象構成の内部測定であり、すべての長文脈・batch sizeで5%という保証ではない。長いコンテキストではKVが支配的になる場合がある。論文はKVパスの性能内訳をcamera-ready版へ追加予定と記しており、プレプリントv1では独立した詳細表が十分ではない。

### Tokens per dollarの解釈

論文は`TPD = (tokens/s × 30 days) / (monthly GCP on-demand price)`と定義し、最大19.9倍のCPU baseline比cost efficiency、V100比最大7.04倍を報告する。価格表では5-core CPU/32GBが月292.31ドル、16-core CPU/32GBが665.45ドル、1×V100付き構成が1,861.5ドル、4×V100が7,446.0ドルである。

この指標はクラウドの想定月額価格と生成throughputから計算した**経済モデル**であり、実際にSAIL搭載CPUが販売されているわけではない。新規C-SRAMの製造・検証コスト、実運用の稼働率、電力料金、ホストメモリ構成、ハードウェア価格、量産歩留まりなどを独立に実測した総所有コストではない。価格やクラウドGPUの世代が変われば倍率も変わる。

### ハードウェアコストと実装の現実性

論文§V-Iでは1 threadが2個の256×512bit C-SRAMを使い、32KB/thread、16 threadで512KBの追加C-SRAMが必要とする。32MB LLCに対して容量比は約1.6%である。Table Vの総面積オーバーヘッドは約2%とされ、DFM、adder tree、pattern reuse logicの寄与を含む。これは追加のC-SRAMだけでなくCPU/cacheの改造を必要とする提案であり、既存CPUへソフトウェアをインストールするだけで実現できるわけではない。

新命令の追加、cache address hasherの変更、C-SRAMのbitline演算、転送制御、tensor単位スケジューラ、データ配置の調整が必要となる。ソフトウェア側ではllama.cpp等の既存実装を参照しているが、SAILをそのまま現行のWindows 11 PCで有効化できるパッチではない。CPU製品への搭載にはシリコン設計とISA・コンパイラ・ランタイムの統合が必要である。

### アブレーション・設計空間

NBWが増えるとLUT容量は`2^NBW`で増え、テーブルの構築や読出しが重くなる。batchが小さいと構築コストを償却できず、batchが大きいと複数入力でテーブルを再利用できる。原著はbatch 24、Q2でNBW=4が3.00M cyclesに対し、NBW=2では11.45M cyclesになる例を挙げ、低bit化だけでは性能が決まらないことを示す。同じbatch=24・NBW=4ではQ4が4.87M cyclesであり、bit幅も演算時間に影響する。

Pattern-Aware LUTは約17%の入力パターン再利用を見つけ、計算cycleを13.8%減らした。これは全推論処理の13.8%の短縮と必ずしも一致しない。C-SRAMによる型変換はCPU vector engineの負担を減らすが、例外ケースの非対応や浮動小数点処理の一部残存がある。性能の主要因は、低bit演算単体の高速化だけでなく、DRAMからLLCへの重みロードを複数ユーザーで共有するスケジューリングとping-pongの組合せである。

## 既存研究との比較

T-MACなどソフトウェアLUT-GEMVは汎用CPUの命令で低bit演算を高速化するが、SAILはcache近傍の専用C-SRAMでLUTを構築・参照する点が異なる。DRAM-PIMは外部メモリで演算するが、CPUとの浮動小数点連携やデータ移動が重い場合がある。Neural Cacheのようなin-cache計算は既存cache配列を演算に用いるが、SAILはcache sliceに隣接するC-SRAMとping-pong bufferによって転送を隠す構成をとる。

AMXやGPUは既存の高性能行列演算器を利用できるが、2〜4bit重みの柔軟な演算や小batchのメモリ律速に課題がある。SAILは低bit演算と帯域の両方に専用の最適化を加える一方、ハードウェアの製造コスト・普及性・互換性の点では汎用ソフトウェア最適化と直接比較できない。量子化方式の品質そのものを改善する研究ではなく、**既に量子化されたモデルを実行するハードウェア**の研究である。

## 限界・批判的検証

**最重要の限界はシミュレーションであること。** SAILのTPSと面積・電力の一部はgem5および回路推定に依存する。GPU/AMX実機と同じ計測器でSAIL実機を測ったものではない。メモリタイミング、配線、電力、熱、NoC競合、キャッシュの実際の製造制約がモデル化と異なる可能性がある。

**モデルの世代と対象が限定される。** Llama-2 7B/13B、Q2〜Q8の評価が中心であり、最新のMoEやMLA、長文脈GQA、量子化KVとの複雑な組合せで同じ効果が出るとは限らない。LLMの出力品質、量子化誤差、生成内容の一致を測る研究ではなく、主に計算性能を評価している。

**GPU比較には容量効果が混ざる。** 4K contextではGPUのKVがbatchを制約するためSAILの相対順位が改善するが、512-token contextではGPUが優勢な例がある。A100 13B Q8/4KはSAILより高速。したがって「GPUを不要にする10.7倍」という解釈は誤りである。最大10.7倍はARM CPU baseline比であり、GPU比ではない。

**cost efficiencyは価格モデル依存。** 19.9倍や7.04倍はクラウド料金と推定throughputから導いた値で、商用製品としての採算性を保証しない。量産コスト、開発費、電力、稼働率、クラウド価格を変えると結果が変わる。

**batch・精度・LUTの相互作用。** 少数リクエストではLUT構築コストが相対的に高く、十分なbatchが集まらなければthroughputを稼げない。単一ユーザーの対話でのTTFTや1token latencyと、複数ユーザーをまとめたtokens/sは異なる。tensor単位スケジューリングによるリクエスト間の公平性・tail latencyは独立検証が必要である。

**実装の移植性。** 新ISA命令とcache改造を伴うため、現行のx86/ARM CPUやRTX 4070 SuperでソフトウェアだけによりSAILの効果を得ることはできない。ローカルLLM環境への示唆は、重み再利用・低bit演算・メモリ移動削減という設計原理にあり、即導入できる最適化パッチではない。
