# Improving the End-to-End Efficiency of Offline Inference for Multi-LLM Applications Based on Sampling and Simulation

## 概要
SamuLLMは、複数のLLMから構成されるオフライン推論アプリケーションを単一ノード複数GPUで実行するとき、「どのモデルを同時に走らせるか」と「各モデルへデータ並列（data parallelism; DP）とテンソル並列（tensor parallelism; TP）を何度ずつ割り当てるか」を共同最適化するframeworkである。各requestの到着は実行前に分かるが、自己回帰生成の出力長は未知なので、候補planの完了時刻を単純な平均token数だけで比較するとdecode中にbatchが縮む挙動を再現できない。

SamuLLMは、事前に多数requestから得た出力長の経験累積分布（empirical cumulative distribution function; eCDF）から仮想出力長をsampleし、vLLMのrequest schedulingをiteration単位でsimulationする。各iterationのmodel computation、input preparation、output samplingをprofile済み線形modelで推定し、それらを積み上げて「このmodelをこのDP/TP構成で残りrequestへ走らせた場合の時間」を得る。

このcost modelを使い、model依存をcomputation graphとして表したapplicationを複数のexecution stageへ分割する。各stageでは複数modelを同時実行でき、modelが一つ完了した時点をstage境界として残りGPUを再割当する。計画時の予測と実行時の完了順がずれた場合は、全探索をやり直さずruntime情報から次stageを補正する。3種類のapplicationとmixed applicationで、計画時間を含むend-to-end completion timeを比較し、heuristic baselineに対して1.0〜2.4倍の高速化を報告する。

## 問題設定
一つのmodelだけを最大GPU数へ載せれば必ず速くなるわけではない。例えば一次論文のprofileではChatGLM3-6Bが1000 requestを1枚のA100で48秒、8枚で32秒であり、GPU数を8倍にしてもthroughputは線形には増えない。modelごとにこのscaling curveが違うため、「全modelを順番に8 GPUで実行する」「可能な限り同時実行してGPUを均等分割する」といった固定規則は非効率になり得る。

さらに同じmodel・同じ並列構成でも、decodeが進んで短いrequestが終了するとactive sequence数が減り、GPU利用率が変わる。長文書をchunkごとに処理するapplicationでは、短いdocumentが先に終わり、後半では一部modelのrequest数だけが大きく減る。この時間変化を無視して「request当たり平均時間」だけを使うと、stage間のGPU割当順位を誤る。

最適化問題は、各stageで実行するmodel集合と各modelのplan (P=(dp,tp)) を決め、依存関係とGPU容量を守りながらapplication全体の完了時刻を最小化することである。bin packingを特殊ケースとして含むためNP困難で、全stage列挙は現実的でない。

## 手法

### 1. 出力長のsampling
著者らはNo Robotsから10,000 requestをsampleし、modelごとの出力長eCDFを作る。通常の自由生成では、出力長分布はinput lengthやinstruction categoryが変わっても比較的似ており、個々のrequestを別modelで高価に予測しなくても、集合全体の分布を再現すればmodel完了時間の推定には十分という観察を使う。

ただし「回答だけ返せ」のように出力形式を強く制約するinstructionやmax output lengthの変更では分布が変わる。その場合は同じeCDFを無条件に使わず、該当workloadの経験分布を別途用意する必要がある。

### 2. iteration-level simulation
sampleした各requestの出力長と、vLLMなどengineのFirst-Come First-Serve（FCFS）規則から、そのiterationでprefill/decodeへ参加しているsequence集合をsimulationする。これにより短い生成が終了してactive batchが徐々に縮む過程を再現する。

各iterationのlatencyは三成分に分ける。model computationはrequest数 (B)、系列長、hidden size、layer数、TP degreeから推定したFLOPsとの線形関係でmodel化する。input preparationは (B) とpadding後の総長、output token samplingは (B) と非padding総長を説明変数とする。さらにmodel loadingとTP communication environment初期化の時間もplan別のprofile tableから加える。

Vicuna-13B-v1.5で1000 SharedGPT requestを処理した例では、loadingを除くsimulation推定98秒に対し実測92秒で誤差6.5%。loadingまで入れると推定128秒、実測127秒となり、stage planningに使える精度を示す。

### 3. computation graphとexecution stage
multi-LLM applicationをnode=LLM、edge=data dependencyのcomputation graphとして表す。self-loopを持つ反復処理は展開してDAGとして扱える。あるmodelは上流modelが完了済み、または同じstage内でpipeline状に進行可能なときだけ起動できる。

一つのexecution stageではmodel集合と各 (P=(dp,tp)) を固定し、最初にいずれか一modelが完了した時刻でstageを終了する。この境界なら完了modelが返したGPUをすぐ次stageへ再配置でき、他model終了までidleにしない。

### 4. per-GPU marginal gainによる貪欲探索
各stageで、候補modelへGPUを追加してplanを変えたときのthroughput増加をGPU一枚当たりで比較し、最も増分が大きいmodel/planへ順にresourceを割り当てる。model loadingやpreemption costもcost modelへ含める。

均等分割ではなく「追加GPUの限界利得」が高いmodelへ多く割り当てられるため、TP scalingが良いmodelと悪いmodelを同時に扱える。総当たりではないのでglobal optimum保証はないが、NP-hard探索を現実的なplanning timeへ落とす。

### 5. planningとrunningの二段階
planning phaseはsampled output lengthsで全stage列を作る。running phaseでは実際のmodel完了順を監視し、予測した順番と異なれば、その時点のunfinished requestsに合わせてstage構成を補正する。初期simulationを完全に当てることを要求せず、実観測で誤差を吸収する設計である。

## 評価
一次論文は単一ノード複数GPU環境で、複数modelを独立に使うensemble型、依存を持つmulti-model pipeline/summary型など3 applicationと、それらを混在させたmixed applicationを評価する。baselineは全GPUでmodelを順番に実行する方式や、実行可能modelへGPUを均等に分けるheuristicを含む。

全workloadを通したSamuLLMのend-to-end speedupは比較方式に対して1.0〜2.4倍で、planning/search時間もこの値に含まれる。したがって高速化は「cost model計算を無視したoffline oracle」の値ではない。

model preemptionとstage間再配置を禁止するとthroughputは1.0〜1.4倍低下する。これは一modelが先に終わった後、そのGPUを残りmodelへ再割当できることが主要な利得源の一つであることを示す。

cost modelの個別検証では前述のVicuna-13B 1000-request例で総時間127秒を128秒と推定する一方、全requestの正確な個別出力長を事前予測する必要はない。eCDF samplingでactive-request曲線の形を再現し、iteration latencyを積み上げることでstage順位決定に必要な精度を得ている。

## 既存研究との差
単一LLM serving schedulerは同じmodel内でrequest ordering、continuous batching、KV cacheを最適化する。SamuLLMはmodel自体が複数あり、GPU memoryの都合で全modelを同時常駐できず、modelごとにDP/TP scalingも異なるapplication-level schedulingを対象にする。

また出力長predictorをrequestごとに追加実行する方式と異なり、個別長の正確さではなく集合全体の分布をsampleしてsimulationへ使う。これにより長さ予測用LLMの追加推論を避けつつ、平均長だけでは表現できないdecode batch shrinkageを扱う。

## 限界
評価対象は単一node multi-GPUで、model execution planはDPとTPが中心である。pipeline parallelism、CPU/NVMe offload、multi-node network topologyを含む場合はplan空間とcost modelを拡張する必要がある。

eCDFはworkload distributionが安定していることを前提とし、出力形式を強く制約するpromptや最大生成長が変われば再収集が必要である。runtime補正は予測誤差を緩和するが、model loading・preemption自体に費用があるため、頻繁な誤予測が無料になるわけではない。

貪欲探索はglobal optimumを保証せず、online request arrivalやtail-latency SLOも主対象ではない。したがってSamuLLMの1.0〜2.4倍は、request集合が事前に分かるoffline multi-LLM applicationに対する結果として解釈すべきである。
