# ScaleSim: Serving Large-Scale Multi-Agent Simulation with Invocation Distance-Based Memory Management

## 概要

LLMを使うマルチエージェントシミュレーションでは、各エージェントが推論している時間より、環境内で行動を実行してLLMを使わない時間が長いことがある。それでもLoRAアダプタ、接頭辞キャッシュ、専用モデル、検索状態などのエージェント固有メモリを全員分GPUへ常駐させると、エージェント数の増加に伴って容量を超える。

一般的なSGLang等はアプリケーションの将来実行順を知らず、要求が来てから必要状態をCPUからGPUへロードし、LRU等で過去の利用履歴に基づき退避する。ScaleSimはこの反応的管理を、次回LLM呼出しまでの相対距離を表す「呼出し距離（invocation distance）」で先読みする方式へ変える。

SGLang上の実装をAgentSociety、Generative Agents、情報拡散の3種で評価し、SGLang比最大1.74倍の高速化を報告する。高並行条件では初回トークン時間（time to first token; TTFT）をHiCache比48〜68%短縮し、Qwen2.5 7B/32Bと1〜8 H100でも利得を維持する。

## 問題設定

エージェントは「LLMで次行動を決める段階」と「決めた行動を環境で実行する段階」を交互に進む。後者ではLLMを使わないため、同時にLLMを要求するエージェントは総数よりかなり少ない。この実行疎性はGPU状態を入れ替える余地を作る。

しかしLRUは「最近使われなかった」ことしか見ない。たとえば長い行動に入ったAgent 1と、数秒後にLLMへ戻るAgent 2がともに非活動なら、LRUがAgent 2を先に追い出す可能性がある。Agent 2が戻ると大きなLoRAや接頭辞キャッシュを再ロードし、その間GPU推論が待つ。

ScaleSimはメモリ不足そのものではなく、フロントエンドが知っている将来の呼出し順序がバックエンドへ伝わらない「意味の断絶」を主要問題とする。

## 手法

### 呼出し距離という統一抽象

各エージェントについて、現在から次のLLM呼出しまでの厳密な秒数ではなく、他エージェントと比較できる相対距離Dをアプリケーションがバックエンドへ通知する。Dが小さいほど近く再利用される状態として扱う。

独立シミュレーションでは現在行動の残り時間をDにできる。相互作用型では、現在行動の残り時間 D_action と他エージェントとの予想相互作用までの D_interaction の小さい方、すなわち D=min(D_action,D_interaction) を使う。情報拡散のように活性化経路が決まる場合は、情報源からのhop数を相対距離として使う。

この抽象により、バックエンドはアプリケーション固有の意味を理解せず、「どの状態が先に必要か」だけを共通形式で比較できる。

### 距離誘導型の先読み

CPUへ退避されているエージェントのDが閾値より小さくなったら、ScaleSimはGPU内の非活動エージェントと距離を比較する。空き容量があるか、よりDの大きい非活動状態を置換できるなら、必要状態をLLM要求到着前にCPUからGPUへ転送する。

PCIe転送はGPU上のLLM計算そのものとは別経路なので、別エージェントの推論や対象エージェントの行動シミュレーションと重ねられる。要求到着時の同期ロードを消すことが、TTFTと全体実行時間を短縮する直接要因である。

### 将来再利用を考慮した退避

GPU容量が不足すると、LRUの代わりにDが大きいエージェント状態を優先して退避する。最近使ったかではなく、次に必要になるまでの距離を基準にするため、近く再利用する状態の往復転送を減らす。

アクティブなエージェントはD=0として保護される。先読み候補も、現在residentな非活動状態より近く必要になる場合だけ入れ替えるため、無制限な先読みで有用状態を追い出さない。

### 異種エージェント状態の統一管理

ScaleSimはLoRA、接頭辞KV、専用モデル等を個別のハードコード対象にせず、エージェント固有メモリの登録・ロード・退避を行う拡張可能なインターフェースとして管理する。同じ呼出し距離を複数種類の状態へ適用し、次のLLM呼出しに必要な一式をまとめて準備する。

## 評価条件

|項目|内容|
|---|---|
|実装|SGLang上のScaleSim|
|ワークロード|AgentSociety、Generative Agents、情報拡散|
|モデル|Qwen2.5 7B / 32B|
|GPU|H100、1/2/4/8 GPU構成|
|規模|AgentSocietyで25〜1000 agents、拡張性評価は500 agents等|
|比較|SGLang、SGLang + HiCache|
|指標|シミュレーション実行時間、TTFT、I/O時間、高並行時の速度|

## 主要結果

|条件|結果|比較|読み取れること|
|---|---:|---|---|
|情報拡散|最大1.74倍高速化|SGLang|構造化された活性化順序でcold startを強く削減|
|Generative Agents|最大1.31倍高速化|SGLang|移動距離から相互作用時刻を予測して先読み可能|
|高並行条件TTFT|48〜68%短縮|HiCache|同期ロード・KV再計算の待ちを削減|
|AgentSociety 25〜1000 agents|全規模で実行時間低下|SGLang/HiCache|agent数増加でもI/O削減効果を維持|
|Qwen2.5 7B/32B、1〜8 H100|全構成でSGLangより高速|SGLang|単一GPU専用の最適化ではない|

## 感度と内部挙動

AgentSocietyでは行動時間を変えて同時活動密度を調整し、250/500エージェントで評価する。GPUには約125エージェント分しか同時常駐できない条件でも、非常に疎な場合だけでなく広い活動密度でSGLangより高速だった。

実行時間内訳ではLoad、Prefill、Decode、Otherを分離し、ScaleSimの主改善がhost-to-GPUロード時間削減から来ることを確認する。したがってモデル計算そのものを高速化する方式ではなく、将来再利用情報によるI/O隠蔽が機構と結果の対応になる。

## 既存研究との差

HiCache等はKVを階層メモリへ置くが、アプリケーションから将来呼出し順を受け取らない。InferCeptは外部tool実行時間を利用して中断要求のKVを管理するが、相互作用や行動によって次回呼出しが変わる多数エージェントを一般化していない。

ScaleSimはシミュレーション側が持つ意味情報を「呼出し距離」だけへ縮約し、独立行動、相互作用、グラフ伝播という異なるアプリケーションを同じメモリ管理器へ接続する。

## 限界

利得は次回呼出し順をある程度予測できることに依存する。距離推定が大きく外れると、先読みした状態が使われる前に再退避され、余計なPCIe転送を生む。論文は距離が厳密時刻でなくても相対順序が有用とするが、完全に予測不能なagent workloadは主対象ではない。

また評価対象はマルチエージェントシミュレーションで、一般的な独立チャット要求へそのまま適用するものではない。最大1.74倍は情報拡散の特定条件であり、Generative Agentsでは最大1.31倍と利得幅が異なる。
