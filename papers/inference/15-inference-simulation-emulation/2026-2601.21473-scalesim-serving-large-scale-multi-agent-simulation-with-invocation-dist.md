# ScaleSim：次回呼出し距離に基づくマルチエージェント推論メモリ管理

## 概要

ScaleSimは、多数の大規模言語モデル利用エージェントを同時に動かすシミュレーションにおいて、GPUメモリ上のエージェント固有状態を、**次にどのエージェントが言語モデルを呼び出すか**というアプリケーション側の予測に基づいて管理する配信システムである。各エージェントには専用の低ランク適応重み、接頭辞の鍵・値キャッシュ、場合によっては専用モデルや検索用状態がある。全員分をGPUへ保持することはできない一方、実際に言語モデルへ要求を出しているエージェントは一部にすぎない。ScaleSimはこの時間的な疎性を利用し、次回呼出しが近い状態を先読みし、遠い状態を優先的に退避する。

中心概念は「呼出し距離（invocation distance）」である。これは必ずしも正確な秒数ではなく、次回の言語モデル呼出しが他エージェントより近いか遠いかを比較できる相対尺度である。独立行動、エージェント間相互作用、情報拡散の三種類のシミュレーションで、この尺度をそれぞれ別の情報から算出する。配信基盤には共通の距離更新インターフェースだけを渡すため、配信側がシミュレーションの全意味を理解する必要はない。SGLang上の実装を三つの代表的なワークロードで評価し、通常のSGLang比で最大**1.74倍**の実行高速化を報告する。高並行時の最初のトークンまでの時間は、階層キャッシュを備えたHiCacheとの比較でも**48～68%短縮**した。ただし改善幅はシミュレーションの活性化予測可能性と、GPUに保持できるエージェント状態数に依存する。

## 問題設定

マルチエージェントシミュレーションの各エージェントは、言語モデルを呼び出して行動を決める段階と、その行動を環境内で実行する段階を交互に繰り返す。後者では言語モデルを使わないため、総エージェント数が大きくても、同時にGPU推論を必要とする数は相対的に小さい。しかし各エージェントの個別接頭辞キャッシュや適応重みを保持し続けると、GPU容量を圧迫する。容量を超えると、要求が来た時点でCPUから必要状態を転送するため、GPU演算の準備待ちが発生する。

従来の配信基盤は個々の推論要求を独立に扱う。最近使われなかった状態を追い出す方式では、あるエージェントが長い行動段階に入ったのか、それとも間もなく言語モデルへ戻るのかを区別できない。原著の図4では、GPUに二人分の状態しか置けない三エージェントの例で、近く再利用するエージェント2を追い出し、当面使わないエージェント1を残してしまう。エージェント2が復帰すると状態を再読込みする必要がある。この無駄は単なるキャッシュ容量不足ではなく、アプリケーションの実行予定が配信基盤へ伝わっていないことに由来する。

また、接頭辞の鍵・値キャッシュはCPUへ退避して復元できる場合と、退避時に捨てて再計算しなければならない場合がある。近く使う状態を誤って追い出すと、PCIe転送だけでなく、再度の入力処理が発生する。ScaleSimはこの違いを意識し、どの状態が近く必要になるかを優先順位の基準にする。

## 手法

### 呼出し距離をアプリケーション別に定義する

ScaleSimの呼出し距離 `D` は、現在のエージェント状態から次の言語モデル要求までの相対的な近さを表す。厳密な時刻予測は必須ではなく、複数エージェントの緊急度を比較できればよい。アプリケーションは各エージェントの距離を `UpdateAgentDistance(agentID, D)` によって配信側へ伝える。これにより、配信側は行動内容や相互作用規則を実装し直さずにメモリ配置を判断できる。

独立シミュレーションでは、エージェントが現在の行動を終えるまでの残り時間を距離とする。たとえば一定時間移動した後に次の行動計画を生成する場合、その行動の終了時点が次の言語モデル呼出しとなる。行動中は推論を使わないため、その残り時間を先読みの猶予として利用できる。行動時間が厳密に定まらない場合でも、アプリケーションの規則や推定器で相対順序を与えられれば機能する。

相互作用を伴うシミュレーションでは、予定した行動が終了する前に他エージェントと遭遇し、会話や再計画が必要になる場合がある。そこで、行動終了までの距離 `Daction` と、相互作用が起こりそうな時点までの距離 `Dinteraction` の小さい方を採り、`D=min(Daction,Dinteraction)` とする。空間移動を扱う場合には、他エージェントとの物理距離と移動速度から相互作用までの時間を概算する。単に現在の行動終了だけを見積もると、途中で割り込む会話の要求を見落とすため、この二つを比較する設計になっている。

情報拡散型のシミュレーションでは、情報源からネットワーク上の辺を何本たどるかというホップ数を距離とする。ここでは実時間の秒数ではなく、伝播の順序が重要になる。たとえば幅優先に情報が広がる場合、情報源に近い頂点ほど先に活性化されやすい。独立行動、相互作用、グラフ伝播という三種類の異なる時間尺度を、配信基盤から見れば同じ「次回利用の相対順位」として扱えることが、この抽象の利点である。

### 距離に基づく先読み

CPU側に退避されているエージェントの距離が所定の閾値より小さくなると、ScaleSimはGPUに存在する非活動エージェントの距離と比較する。GPUに空きがあるか、GPU上にもっと遠い非活動エージェントがいる場合に限り、近く使うエージェントの状態を先読みする。原著の図6では、GPU上の非活動エージェント8と5の距離が2と3、CPU側のエージェント7の距離が1なので、エージェント7を先読みする。一方、距離3の別候補は優先順位上の利得がないため先読みしない。

この転送は、対象エージェントがまだ環境内で行動している間に開始できる。要求が届いてから状態を読み込む従来方式と異なり、転送を環境側の処理時間と重ねられるため、要求到着時の待ち時間を短縮できる。ただし、PCIe帯域やGPUメモリが無限にあるわけではなく、同時に多数の状態を先読みすれば転送競合が起きる。距離の閾値と置換候補の比較を併用するのは、先読み自体がキャッシュを乱すのを防ぐためでもある。

### 将来再利用を意識した退避

GPU容量が不足した場合、ScaleSimは最後に使われた時刻だけでなく、次回呼出しまでの距離が大きい状態を優先して退避する。言語モデルを現在使っているエージェントの距離は0として扱い、実行中の状態を先読みのために追い出さない。非活動エージェントの間では、近く再利用する状態を残し、当面不要な状態を先に移す。この判断は、状態をCPUへ保存して後で戻す場合にも、接頭辞キャッシュを破棄して後で再計算する場合にも意味を持つ。

原著の図7では、エージェント2がすぐに推論へ戻るならその状態を残し、長く行動中のエージェント1を退避する。通常の最近使用順では逆の選択になる可能性がある。これにより、同じGPU容量でもCPUからの再転送や接頭辞再計算を減らせる。距離が誤っていた場合には利得が減るため、距離更新をアプリケーションから継続的に受け取ることが重要である。

### 異種メモリの共通管理と予測誤差への対応

ScaleSimは、エージェント固有の状態を単一の種類に限定しない。低ランク適応重みの読込み、接頭辞キャッシュの復元などを共通のメモリ管理インターフェースへ接続し、エージェント単位の距離を使って必要状態を扱う。原著の実装ではSGLang 0.5.2を基盤とし、代表例として低ランク適応重みと接頭辞キャッシュの二つのモジュールを実装する。検索用索引や専用モデルへの拡張可能性は示すが、すべての種類を同じ詳細度で実機評価したわけではない。

予測より早く要求が到着した場合には、転送待ち行列の優先順位を更新する必要がある。付録Aの図15では、距離2の低優先度ロード中に距離0の緊急ロードが到着すると、前者を中断して待ち行列へ戻し、緊急側を先に処理する。メモリモジュールが中断信号を確認できるインターフェースを持つため、先読みが外れた場合でも緊急要求を後回しにし続けない。この割込み機構は距離予測が完全でない実環境に必要な安全弁である。

## 評価条件

| 観点 | 原著の設定 |
|---|---|
| 実装 | SGLang 0.5.2を拡張。低ランク適応重みと接頭辞キャッシュを管理 |
| 主モデル | Qwen2.5-7B-Instruct。拡張性試験ではQwen2.5-32Bも使用 |
| GPU | 主実験はH100 80GBを1基、PCIe第5世代64GB/秒。複数GPUは最大8基を高速相互接続 |
| ワークロード | 独立行動のAgentSociety、相互作用するGenerative Agents、構造化された情報拡散 |
| 比較対象 | 通常のSGLang、階層キャッシュ機構HiCacheを有効にしたSGLang |
| GPU常駐上限 | 代表的な端点比較では総エージェントの25%、最大125エージェント分 |
| 活動率 | 代表的な端点比較では約20%のエージェントが同時に活動 |
| 指標 | シミュレーション全体の実行時間、段階ごとの実行時間、初回トークン遅延、ロード時間 |

評価上の重要な条件として、各エージェントに個別の論理識別子を与え、低ランク適応重みと接頭辞キャッシュを持たせている。ただし、多数の異種エージェントを模擬する際には同じ適応重みを共有し、論理識別子で別々の状態として扱う。これはエージェント数の増加による管理負荷を調べる工夫であり、すべてのエージェントが完全に異なる重みを持つ現実の負荷をそのまま再現したという意味ではない。

通常のSGLangではGPUの接頭辞キャッシュが追い出されると再利用時に再計算が必要となる。HiCacheはCPUへの階層退避と復元を使うが、両比較方式ともエージェントの将来呼出し距離を知らず、要求到着後に反応的なロードを行う。この比較は「階層キャッシュの有無」だけでなく、「将来呼出しの意味情報を使うか」を分けて解釈する必要がある。

## 評価結果

### シミュレーション全体の実行時間

| ワークロード | 通常SGLangに対する最大高速化 | 主な理由 |
|---|---:|---|
| AgentSociety | 1.73倍 | 独立した行動時間から次回要求を見積もり、接頭辞状態を事前準備 |
| Generative Agents | 1.31倍 | 移動距離と遭遇可能性を反映し、会話前に必要状態を配置 |
| 情報拡散 | 1.74倍 | グラフ上の活性化順序を使い、下流エージェントの初回ロードを回避 |

原著図8は、三種類のアプリケーションとエージェント数の違いによって改善幅が変わることを示す。最大1.74倍は情報拡散の特定条件であり、すべてのアプリケーションで同じ倍率が得られるという主張ではない。AgentSocietyでは最大1.73倍、相互作用を伴うGenerative Agentsでは最大1.31倍である。相互作用の発生時刻は行動終了時刻より不確かなので、構造化された情報拡散ほど先読みの効果が一定にならないことと整合する。

図9ではAgentSocietyのエージェント数を25から1000へ増やし、一段階当たりの実行時間を比較する。すべての方式で規模に応じて時間は増えるが、ScaleSimはSGLangおよびHiCacheより低い実行時間を維持する。これはモデル演算そのものの高速化ではなく、必要状態を要求前に用意してロード待ちを短縮した効果として説明される。

### 初回トークン遅延と同時実行密度

初回トークン遅延は、エージェントが言語モデルへ要求を出してから最初の生成トークンを受け取るまでの時間である。GPU状態が退避されていると、その復元や接頭辞再計算がこの待ち時間へ加算される。図10ではエージェント数が増えるとどの方式でも初回トークン遅延は増えるが、ScaleSimは高並行条件でHiCache比**48～68%短縮**する。比較対象が通常SGLangではなくHiCacheである点を明記する必要がある。

図11では、250または500エージェントのシミュレーションで行動時間を変え、同時活動密度を操作する。GPUに保持できる状態が最大約125エージェント分という制約の下でも、極端に活動が疎な条件だけでなく、広い活動密度で通常SGLangを上回った。活動率が上がると先読みの猶予が短くなるため、改善が無条件に増えるわけではない。予測可能な非活動期間が十分にあることが先読みの鍵となる。

### モデル規模とGPU数の感度

図12では500エージェントを使い、Qwen2.5の7Bを1～2基、32Bを4～8基のH100で実行して比較する。ScaleSimは複数の構成で通常SGLangより高い性能を示すが、すべてのGPU数で最大1.74倍に達するわけではない。GPU間の通信やモデル配置が変わると、状態転送と推論の重ね合わせの程度も変わる。実験は高帯域のH100とPCIe第5世代を主とするため、古いGPUや遅いCPU-GPU接続への直接的な保証ではない。

## 既存研究との差

HiCacheは接頭辞の鍵・値を階層メモリへ置くが、将来のエージェント活性化順序を受け取らない。S-LoRAなどは複数の適応重みを効率よく配信するが、エージェントの行動段階まで考慮しない。InferCeptは外部ツール実行時間から次回推論を予測するものの、エージェント間相互作用で予定が変わるシミュレーションや、グラフ上の情報伝播を共通形式で扱うものではない。AI Metropolisは特定の生成エージェント設定で要求順序を調整するが、環境内行動が後の推論に影響しないという仮定が一般のシミュレーションには適用できない。

ScaleSimはアプリケーションが知る将来の呼出し順序を、距離という小さな情報へ変換して配信側へ渡す。既存の階層キャッシュや適応重み管理を置き換えるというより、それらの状態を**いつ読み込み、いつ追い出すか**の意思決定に新しい信号を与える方式である。

## 限界と負の条件

第一に、呼出し距離の順位を推定できることが前提であり、完全に予測不能な外部要求には適用しにくい。第二に、予測が外れて不要な状態を先読みすると、帯域消費と有用なキャッシュの退避が発生し得る。第三に、距離を更新するためのアプリケーション側の実装が必要で、既存の汎用配信基盤へ無変更で適用できるわけではない。第四に、同時活動エージェントがGPU常駐上限に近づくと、先読みと実推論の間に利用できる余裕が減る。第五に、評価した異種メモリの具体的な実装は適応重みと接頭辞キャッシュであり、任意の検索索引や専用モデルが同等に高速化するかは未検証である。

第六に、主な実験はシミュレーション型のワークロードとQwen2.5・H100構成に集中する。エージェントの活性化規則が異なる現実の対話サービス、予測が頻繁に反転する用途、転送が演算と重ねられない環境では効果が縮む可能性がある。原著の付録Aは緊急ロードによる待ち行列の割込みを設計しているが、これは予測誤差をゼロにするのではなく、誤差発生時の優先度逆転を緩和するための機構である。
