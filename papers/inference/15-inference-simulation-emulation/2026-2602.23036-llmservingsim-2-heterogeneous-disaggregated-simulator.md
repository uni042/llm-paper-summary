# LLMServingSim 2.0: A Unified Simulator for Heterogeneous and Disaggregated LLM Serving Infrastructure

> 異種GPU/TPU/PIMと分離サービング・多階層鍵値メモリ・MoE・電力を要求駆動ループで統合模擬するLLMサービングシミュレータ。
## 書誌情報
- **著者**: Jaehong Cho, Hyunmin Choi, Guseul Heo, Jongse Park
- **著者・所属**: School of Computing, KAIST, Daejeon, South Korea
- **公開**: IEEE ISPASS 2026 / arXiv
- **種別**: 国際会議論文
- **対象**: 推論シミュレーション、異種アクセラレータ、分離サービング、多階層メモリ、MoE、電力モデル
- **実装**: 著者公式casys-kaist/LLMServingSimで公開。ASTRA-simとChakraを異種計算・演算子駆動推論向けに拡張し、PyTorch/HuggingFace演算子プロファイラ、Serving Engine、Model Serving Group、System Simulatorを統合。
## 概要
LLMServingSim 2.0は、異種アクセラレータ、多階層メモリ、事前充填・復号分離、MoE、接頭辞キャッシュ、計算・メモリ退避を単一の実行時ループで扱うLLMサービング用システムシミュレータである。演算子プロファイルと要求駆動の実行グラフを結び、スケジューリング、データ移動、通信競合、電力を相互作用込みで再現する。実機検証では主要性能・メモリ・電力指標を平均誤差約0.95%で再現し、複雑な構成でも概ね10分規模のシミュレーション時間を維持する。

LLMServingSim 2.0は、要求ルータ、モデルサービンググループ、システムシミュレータを一つの実行時ループへ統合し、ソフトウェアの意思決定とハードウェア状態を同じ時間軸で更新する。各演算子の遅延・電力は実機または外部ハードウェアシミュレータから一度プロファイルし、その結果を要求駆動の有向非巡回実行グラフへ付与する。鍵値キャッシュの多階層配置、接頭辞共有、専門家ルーティング、計算・メモリ退避、事前充填・復号分離、通信と電力までを共通抽象化で扱える。

代表結果として、実機集約性能誤差はRTX A6000 / H100で実vLLMに対して0.99% / 1.54%。処理量と遅延を実行全体で高精度に再現。
## 問題設定
現代のLLMサービングは同種GPUだけで完結せず、世代の異なるGPU、TPU/NPU、PIM/PNM、CXL接続メモリなどを組み合わせ、さらに事前充填と復号、MoE専門家、鍵値キャッシュ、モデル重みを別資源へ分離する。性能は個々の演算器速度だけでなく、要求到着に応じた一括処理変化、経路選択、配置、鍵値の昇格・退避、専門家転送、ネットワーク競合が時間的に相互作用して決まる。既存のハードウェア中心シミュレータは静的な演算・通信には詳しいが要求駆動のサービング状態を扱いにくく、VidurやAPEXなどのシステム中心方式は異種資源や多階層メモリ、分離構成の対応が限定的である。そのため新しいアクセラレータやメモリを、実際のサービング方策と組み合わせて設計段階で比較する統一基盤が不足していた。
## 新規性
LLMServingSim 2.0は、要求ルータ、モデルサービンググループ、システムシミュレータを一つの実行時ループへ統合し、ソフトウェアの意思決定とハードウェア状態を同じ時間軸で更新する。各演算子の遅延・電力は実機または外部ハードウェアシミュレータから一度プロファイルし、その結果を要求駆動の有向非巡回実行グラフへ付与する。鍵値キャッシュの多階層配置、接頭辞共有、専門家ルーティング、計算・メモリ退避、事前充填・復号分離、通信と電力までを共通抽象化で扱える。
## 手法
### 手法のあらまし
入力は作業負荷構成、クラスタ構成、ハードウェア性能プロファイルの三種である。初期化時にExecution PlannerがモデルごとにModel Serving Groupを作り、異種デバイスプール、並列化、鍵値管理、退避、接頭辞キャッシュ、電力方策を設定する。要求到着後、リクエスト ルーティングが適切なグループへ送り、バッチ スケジューラがメモリ容量、鍵値占有、最大一括数、接頭辞常駐・退避費を見て実行集合を形成する。Operation Mapperは各演算子をGPU、PIM、その他資源へ割り当て、MoEなら語ごとの専門家経路と専門家退避を反映する。Operation スケジューラは依存関係、テンソル・パイプライン・データ・専門家並列、必要な通信、鍵値・重み移動を有向非巡回グラフへ展開する。System Simulatorは改造ASTRA-sim/Chakraを用いてグラフを実行し、ネットワーク競合、同期、多階層メモリ帯域、CXL共有、PIM操作を時間軸上で模擬する。完了した時間とメモリ状態は次の要求処理へ戻り、全要求が終わるまで反復する。演算子プロファイルは単一デバイス・単一復号ブロックで取得でき、Llama 3.1-70B/H100でも一回約2.1時間で、その後の多数の構成探索に再利用できる。電力はアクセラレータ、CPU、DRAM、相互接続、NIC、ストレージ、その他の7成分に分け、アクセラレータは活動・待機・休止の三状態、メモリとリンクは転送量比例で積算する。

### モデルサービンググループ
一つのLLMインスタンスを表す論理実行単位で、異種デバイスプール、要求待ち行列、一括処理器、メモリモデル、電力モデル、演算子配置器、実行順序器を保持する。要求は事前充填から復号まで同じグループ内で状態を蓄積し、待ち時間、初回語時間、語間時間、終端間遅延を追跡する。一括処理器は単に最大件数まで詰めるのではなく、各デバイスのメモリ容量、現在の鍵値占有、接頭辞キャッシュの常駐状態と退避費を照会し、実行可能な集合だけを次段へ送る。演算子配置器はテンソル・パイプライン・データ並列だけでなく、GPUとPIMの混在時の注意演算退避や、MoE専門家の配置・一時退避を演算子単位で決める。専門家ルータは無作為、巡回、負荷比例、利用者定義方策を切り替えられ、語ごとの経路が通信と専門家読込へ変換される。このため個別の新サービング手法ごとに専用シミュレータを作るのではなく、同じグループ抽象化の方策を交換して比較できる。

### 多階層メモリと分離実行
鍵値キャッシュをデバイスHBM、ホストDRAM、CXL共有メモリ、ストレージへ配置し、各階層の容量、帯域、共有範囲、読込・書込費を明示する。要求の一括処理を作る際に鍵値退避と昇格を判断し、必要な転送を実行グラフへ自動挿入するため、容量不足だけでなく転送が通信やメモリ帯域と競合する時間も反映される。事前充填・復号分離では同一モデルに複数の事前充填グループと復号グループを作り、任意のM:N比で対応付ける。事前充填側が生成した鍵値は層単位の転送操作として復号側へ渡され、ネットワーク構成に従って遅延が計算される。接頭辞キャッシュも各デバイス固有、同一ノードCPU共有、クラスタ全体CXL共有を表現でき、命中による演算削減と遠隔取得費、複数インスタンス間共有の利益を同じ状態機械で比較できる。

### 演算子プロファイル駆動モデル
PyTorch/HuggingFaceを用いる演算子プロファイラがモデル・デバイス組ごとの遅延と電力を測定し、シミュレーション時は実行グラフの各節点へその特性を付与する。モデル全体をあらゆる一括数・系列長で繰り返し測るのではなく、単一復号ブロックを中心に演算子特性を収集するため、Llama 3.1-70BをH100で測る場合でも一回約2.1時間でプロファイルを作れる。取得済みプロファイルは要求到着率、並列構成、メモリ階層などを変えた多数のシミュレーションへ再利用できる。実機GPUだけでなくTPU向けプロファイラも実装され、TPU-v6e-1実機との検証を行っている。さらにPIMのように対象実機を持たない将来アクセラレータは、外部ハードウェアシミュレータが生成した同じ演算子形式の性能表を入力できるので、Serving Engine側の意味論を変更せず設計探索へ追加できる。

### 要求駆動システムシミュレータ
改造したASTRA-simとChakra上で、各モデルサービンググループが生成する演算子有向非巡回グラフをクラスタ規模で実行する。各節点には実行デバイス、演算遅延、メモリ量、通信量、電力情報を付け、辺にはデータ依存と実行順序を持たせる。元のASTRA-sim/Chakraが主に反復的な学習通信を想定するのに対し、異種計算資源、推論固有の専門家並列、要求ごとに変化する演算グラフを扱えるよう拡張している。実行中には同期、ネットワーク競合、デバイス間通信、メモリ帯域競合、鍵値移動、共有メモリへのアクセスを同じ時間軸で処理する。グラフ完了後に変化した時刻、メモリ常駐、待ち行列、電力状態が次の一括処理・経路・配置判断へ戻るため、静的な構成表や平均演算時間の加算では捉えにくい待ち行列増幅、突発負荷、段階遷移、共有キャッシュ競合を再現できる。

### 全体のデータ／制御の流れ
静的な演算時間表を足し合わせるのではなく、ソフトウェア方策が現在状態から実行グラフを作り、そのグラフをハードウェア側が実行し、変化した時間・メモリ・電力状態を次の方策判断へ戻す閉ループが中心設計である。この境界を保ったままデバイスプロファイルと方策を交換できるため、既存GPUからTPU、PIM、CXLまで同じサービング意味論で比較できる。
## 評価条件
- **ハードウェア**: 実機検証は(1) RTX A6000×4とIntel Xeon Gold 6326、(2) H100-SXM-80GB×8、(3) Google Cloud TPU-v6e-1。A6000は40GB・936GB/s・PCIe 4.0×16、H100は80GB・3.35TB/s・NVLink、TPUは32GB・1.6TB/s・800GB/s相互接続として設定。PIM事例は256チャネル、各1GB HBM2、2000MT/s。
- **ソフトウェア**: 実サービングはvLLM。CPU共有接頭辞キャッシュ検証ではLMCacheを併用。シミュレータは改造ASTRA-sim/Chakra、PyTorch/HuggingFace演算子プロファイラ、公開LLMServingSim 2.0実装を使用。
密モデルLlama 3.1-8B/70BとMoEのPhi-mini MoE、Mixtral 8×7Bを使用。通常評価はShareGPTから300要求を抽出し、毎秒10要求のPoisson到着を生成。実機との時系列処理量、TTFT、TPOT、総合遅延、メモリ使用量、接頭辞命中率、電力・エネルギーを比較。比較シミュレータはVidur、APEX、TokenSim、初代LLMServingSim。複雑な分離・MoE構成では各比較方式が実行可能な範囲だけ比較する。
同種GPUの単一インスタンスだけでなく、複数インスタンス、接頭辞共有、事前充填・復号分離、MoE、TPU、仮想PIMを含む。プロファイルに基づくシステムレベル精度を狙い、個々のGPUマイクロアーキテクチャを命令単位で模擬する方式ではない。
## 主要結果
LLMServingSim 2.0は、RTX A6000とH100の実サービングに対して時系列処理量の平均誤差5.14%と3.29%、実行全体の処理量・遅延集約では0.99%と1.54%の平均誤差を示した。メモリ・接頭辞キャッシュでは単一インスタンス0.93%、CPU共有の複数インスタンス0.41%、エネルギーは1.34%の誤差で実機挙動を再現した。TPUでも時系列処理量3.95%、集約指標0.3%未満であり、GPU以外へ同じプロファイル方式を拡張できることを示す。複雑な分離・MoE構成を含む比較では主要指標の平均誤差1.81%で、既存シミュレータが未対応または大きな誤差となる設計空間を扱える。実務上は、実クラスタを構築する前に異種資源・メモリ階層・サービング方策の相互作用を分単位のシミュレーションで比較できる点が主要成果である。

- 実機集約性能誤差 / 0.99% / 1.54% (比較対象: 実vLLM; 条件: RTX A6000 / H100) — 処理量と遅延を実行全体で高精度に再現。

- 時系列処理量誤差 / 5.14% / 3.29% (比較対象: 実vLLM; 条件: RTX A6000 / H100) — 動的一括処理や段階遷移を含む時間変動も追従。

- エネルギー誤差 / 1.34% (比較対象: 実RTX A6000サーバ; 条件: テンソル並列1・2、パルス負荷) — 三状態GPUと七成分電力モデルが実測消費を再現。

- メモリ・接頭辞挙動誤差 / 0.93% / 0.41% (比較対象: 実システム; 条件: 単一インスタンス / CPU共有複数インスタンス) — 階層キャッシュの成長と共有命中率を再現。

- TPU集約性能誤差 / 0.3%未満 (比較対象: 実TPU-v6e-1 vLLM; 条件: Llama 3.1-8B単一インスタンス) — 非GPUアクセラレータへプロファイル方式を移植可能。

- GPU+PIM復号処理量 / 1.43倍 (比較対象: GPUのみ; 条件: Llama 3.1-8B、プリフィル後デコード期間) — PIMがメモリ律速復号を加速する設計探索例。

- GPU+PIMエネルギー / J/トークン 14.8%削減 (比較対象: GPUのみ; 条件: PIM事例) — 性能だけでなく電力を同時比較できる。

### 負の結果・境界条件
- 詳細な実行時・メモリ挙動を扱うためVidurやTokenSimなど軽量GPU中心シミュレータよりシミュレーション時間は長い。PIMのsub-バッチ interleavingは小一括数ではGPUの実効一括数を下げ、GPUのみと同程度の性能なのに追加PIM分だけエネルギーが増えた。SBIが有効なのは256以上の非常に大きな一括数が持続する区間だった。

### 結果の読み方
演算子単体の精度だけではなく、要求・キャッシュ・通信の状態を閉ループで更新することが、分離サービングや異種資源でのシステム性能再現に重要である。PIM事例のように単体ハードウェアが高速でもサービング方策との組合せ次第で逆効果になるケースを事前に発見できる。
## 品質への影響
生成品質の評価手法ではない。シミュレータの忠実度を実機の性能・メモリ・電力指標との誤差で検証している。
## 既存研究との差
初代LLMServingSimは単一インスタンスの実行統計中心で、複数インスタンス、MoE、分散鍵値配置、PD分離に非対応。Vidur/APEXは演算子プロファイルと構成探索に強いが、多階層メモリ、異種配置、接頭辞共有などの相互作用が限定的。TokenSimは動的要求と注意状態再利用を扱うがメモリ抽象化が簡略で、帯域競合や鍵値移動の忠実度が不足する。2.0は異種デバイスプール、演算子配置、詳細メモリ移動、専門家経路、分離グループ、電力を同じ実行グラフと時間軸へ統合する。
## 限界
演算子プロファイル駆動なので、未計測の新ハードウェアでは外部シミュレータまたは実機プロファイルの品質に精度が依存する。ASTRA-sim/Chakraを拡張した詳細な要求駆動模擬は軽量シミュレータより実行時間が長く、非常に大きな探索空間では費用が増える。TPU実機検証は当時のvLLM-TPUが安定対応する単一インスタンス密モデルに限定され、TPU上のPD分離や接頭辞キャッシュは仮想探索に留まる。PIM事例も実機ではなくプロファイルによる将来ハードウェアケーススタディである。
## 実装状態
ISPASS 2026採択版。著者公式GitHubでシミュレータとartifactを公開し、arXiv v2にはartifact appendix、導入・実験手順・設定変更方法を収録。演算子プロファイラはGPUだけでなくTPUへ拡張済みで、外部性能モデルから将来PIMも取り込める。
## 研究上の位置づけ
推論基盤研究の評価インフラ系統に位置し、単一の新スケジューラではなく、スケジューラ、鍵値階層、オフロード、MoE、PD分離、異種アクセラレータを共通の実行時意味論で比較する土台を提供する。特にSSD/CXL/遠隔メモリ、PIM、異種GPUなど、実機構築費が高い設計をサービング方策と共同探索する研究に直接利用できる。
