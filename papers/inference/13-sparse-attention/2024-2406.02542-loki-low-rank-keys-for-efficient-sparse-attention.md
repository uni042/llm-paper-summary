# Loki: Low-Rank Keys for Efficient Sparse Attention

> キーの低ランク性を使い、低次元スコアで候補KVを選んでから全次元注意を計算し、品質を保ちながら注意計算を最大約45%短縮する疎注意法。

## 概要

長文脈LLMのデコードでは、各生成ステップで過去全トークンのキーと値をKVキャッシュから読み、現在のクエリとの注意を計算する。系列が長くなるほど演算だけでなくGPU DRAMからKVを読むデータ移動が支配的になる。疎注意は参照トークンを減らせるが、重要トークンを選ぶために全次元の注意スコアを先に計算すると、その選択自体が高価になる。

Lokiは、Llama2/3、Mistral、Mixtralなどの注意キーがヘッド次元全体を均等に使わず、低次元部分空間へ集中する観察を利用する。オフライン較正で主成分分析（Principal Component Analysis; PCA）の射影基底をヘッドごとに求め、実行時には少数主成分だけで全KVを順位付けする。上位トークンだけを選んだ後は全次元へ戻って正確な注意を計算する。

代表設定 `kf=0.25, df=0.25` は、全KVの25%を最終注意へ使い、候補選択にはキー次元の25%だけを使う。理論上の注意計算高速化は約2.6倍で、4モデルのWikiText-2 パープレキシティ悪化は完全注意から0.1以内だった。A100実機ではLlama2-13B相当、プロンプト3072・生成512で、KVキャッシュ追記を除く注意計算を約45%短縮した。

一方、LokiはKV容量そのものを減らさない。さらにHugging Face TransformersではKVキャッシュ追記が層時間の80%以上を占め、注意だけを速くしてもエンドツーエンド利得が隠れる。論文はこの負の結果まで示している。

## 問題設定

通常の自己注意では、現在クエリと長さSの過去キーの内積を全トークンについて計算する。ヘッド次元Dに対し、クエリ・キー積と注意重み・値積は概ねO(DS)で、デコードでは毎ステップ長いKVを読み直す。長文脈ほどGPUメモリ帯域が律速になりやすい。

トークン追い出し型はKV容量も減らせるが、削除トークンを後のクエリで参照できない。動的な上位k選択なら全KVを残せるが、正確な順位付けのため全次元 `qK^T` を計算すれば元の注意に近い費用がかかる。Lokiは「最終注意」ではなく「候補選択」の次元を削る。

## 手法のあらまし

較正時に各層・各ヘッドのキーを収集してPCA基底Pを作る。生成時には新しいクエリとキーをPで回転し、回転後キーをKVへ保存する。候補選択では先頭d主成分だけを使って全Sトークンの近似スコアを計算し、上位k索引を得る。次に、その索引のキーだけ全D次元で正確な注意スコアを再計算し、対応する値との積から出力を作る。

### 1. PCA射影 — キーの低ランク性を候補選択へ使う

入力は較正データで収集したキーである。ヘッドごとにPCAを行い、分散の大きい順に直交基底を保持する。全D次元なら直交変換なので内積は保存されるが、候補選択では先頭d次元だけを読む。

Llama2-7Bでは代表設定で、低次元スコアと正確なスコアが選ぶ上位k集合のJaccard類似度が約0.9だった。これが低次元順位付けで品質を保てる直接的な内部根拠である。

回転位置埋め込み（Rotary Position Embedding; RoPE）との関係はモデル依存である。Llama3-8BではRoPE適用後キーのPCAを使うとパープレキシティが完全注意約5.57から11.45へ悪化した条件があるが、RoPE適用前の基底ではこの崩壊を避けられた。位置情報が較正データ固有の分布を基底へ混ぜる可能性がある。

### 2. 低次元スコア — 全KVを安く順位付けする

回転後クエリと全キーの先頭d次元だけで近似スコアを作り、上位kトークンを選ぶ。`df=d/D` を小さくすると全KV走査時の読み出しと積和演算が減る一方、順位付け精度は落ち得る。`kf=k/S` を大きくすると品質を保ちやすいが、後段で読む全次元KVが増える。

したがってdfは「選択器の情報量」、kfは「最終注意の疎度」を独立に制御する。代表設定では両方0.25とし、理論速度式は系列長が十分長いと約 `1/(df/2+kf)` になる。

### 3. 選択トークンだけ全次元で正確に計算する

上位k索引に対応するキーと値だけを読み、クエリとの全D次元内積を再計算してsoftmaxと値積を行う。低次元表現を最終注意へ直接使わないことが重要である。

付録のPCAAttnは低次元キーをそのまま保存して最終注意まで計算し、KV容量も減らそうとしたが失敗した。Llama2-7Bではdf=0.5でパープレキシティ 38.40、df=0.25で243.26、Mistral-7Bでは396.90と933.60まで悪化した。低ランク性は「順位付けに十分」でも「最終注意に必要な情報を捨ててよい」ことを意味しない。

### 4. Tritonカーネル — 疎な読み出しを実測速度へ変える

標準PyTorchで部分テンソルを索引すると一時的な密コピーが作られ、削減した演算をメモリ転送が相殺する。LokiはTritonで行列積を実装し、必要な次元と選択トークンをKVから直接レジスタへ読む。

既存SparQカーネルより並列化方向を増やし、逐次生成で自然に生じる2の累乗でないKV長も扱う。バッチ1・KV長4096・25%トークン利用のクエリ・キー積ではSparQより約2.8倍高速だった。小バッチでは系列方向の並列性を使えることが効く。

### 5. 一生成ステップの流れ

新トークンからクエリ・キー・値を作り、クエリとキーをPCA基底へ回転する。回転後キーと値をKVへ追記し、全キーの先頭d次元だけを読んで上位k索引を選ぶ。その索引の全次元キーと値だけを読み、正確な注意を計算する。

全トークンについて読むキー次元と、全次元で読むトークン数の両方を減らすが、KVキャッシュ追記とKV容量は元の注意とほぼ同じで、PCA射影と上位k選択が追加費用になる。

理論2.6倍は注意演算量の見積もりであり、生成全体の高速化ではない。実測では上位k選択自体が小さい行列積と同程度の費用になり、Hugging FaceではKVキャッシュ追記がさらに支配する。この区別が論文の重要なシステム上の結果である。

PCA基底をWikiText-103、C4、BookCorpusのいずれから作っても品質は概ね一貫した。一方、層ごとにdfを変える可変方策は固定dfに対する明確な改善を得られなかった。低ランク性の層差を単純な次元割当へ変換するだけでは足りない。

## 既存研究との差

H2OはKVを恒久追い出しして容量を減らすが、Lokiは全KVを保持して現在クエリに必要な部分だけ毎ステップ読む。したがって容量削減と帯域削減は直交し、H2O等で残ったKVへLokiを重ねる余地がある。

Exact-TopKは選択品質の上限に近いが、順位付けのため全次元注意を計算するので高速化にならない。LokiはPCA低次元スコアでこの選択を近似する。SparQに対しては、アルゴリズムだけでなく索引付き行列積のカーネル並列化と任意KV長対応も改善している。

## 限界・実装状況

第一にKV容量を減らさない。容量不足には量子化、追い出し、CPU退避など別機構が必要である。第二に上位k選択が新しいボトルネックとなり、理論演算削減がそのまま実時間へ出ない。第三にFlashAttention等の高効率注意カーネルとの本格統合は今後の課題である。

第四に汎用ランタイムではKVキャッシュ追記が80%以上を占めたため、注意カーネル単独最適化の効果がユーザー遅延へ変換されにくい。第五に、PCAAttnの大幅な品質崩壊が示すように、キーの低ランク性をKV容量圧縮へ直接読み替えることはできない。

## 一般的な実装上の含意

長文脈推論ではKV容量とKV読み出し帯域を別資源として扱う必要がある。容量が足りても毎トークン全KVを読むことが遅い場合は動的選択が効くが、容量不足には別の圧縮が必要になる。

近似は最終出力へ直接入れるより、候補選択だけに使い最後を正確計算へ戻す方が品質を保ちやすい場合がある。また理論FLOPsだけでなく、索引、top-k、KVキャッシュ追記、一時テンソル生成まで測らなければ実際の高速化は判断できない。
