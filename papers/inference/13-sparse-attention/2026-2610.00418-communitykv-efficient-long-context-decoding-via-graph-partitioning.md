# CommunityKV：注意グラフのコミュニティ分割による長文脈KV検索

## 概要

CommunityKVは、長文脈の自己回帰生成で過去トークンの鍵・値キャッシュ（key-value cache; KV cache）を毎回すべて読み込む代わりに、**入力文脈中で意味的にまとまったトークン群だけを検索して正確な注意計算を行う**学習不要の疎注意方式である。入力処理（prefill）中にすでに計算される `QKᵀ` の注意スコアからトークン間の疎グラフを作り、Leidenコミュニティ検出で分割する。生成時には新しいクエリと各コミュニティの重心を比較し、関連する群のトークンだけをKVから取り出す。

KVを永久削除する圧縮方式と異なり、**元のKVは保持したまま、生成ステップごとの読込対象を変える**。新しく生成したトークンは既存の群へ局所的に割り当てるため、毎ステップの再クラスタリングを避ける。Qwen3系列とLlama-3.1を使うLongBench v2、BABILong、RULERで評価し、H200での端から端生成速度はクエリヘッド別グラフで1.08〜1.25倍、クエリグループへ集約したグラフで1.39〜1.71倍となった。

ただしこの高速化は追加のグラフ・重心メモリを必要とする。ヘッド別グラフでは密注意よりピークメモリが17〜29%増え、グループ集約で0.5〜8.5%増に抑えられる。**疎注意はKVの保存容量自体を削減するとは限らない**という区別が重要である。

## 問題設定と着眼点

長い文脈ではKVキャッシュのサイズがトークン数に比例して増える。全域注意を毎生成ステップで行うと、過去の鍵・値を広く読み込むため、メモリ帯域と注意演算が負担となる。Questのような連続ブロック単位の検索は速いが、1つの高得点トークンが含まれるだけで無関係な隣接トークンも取得しやすい。鍵ベクトルをk-meansでクラスタリングするMultipole型は意味的な集団を作れるが、初期クラスタリングが重く、生成中に新トークンを追加する際の更新費用が問題になる。

CommunityKVは、注意行列が単に重みを持つだけでなく、トークン間の関連を表すグラフとして利用できる点に着目する。強く参照する関係と、同じクエリから共に参照される関係を組み合わせ、単語の隣接順序ではなく**実際の注意の結び付き**に基づいて群を作る。新トークンの割当を局所化できれば、検索に使う索引を長い生成中も維持できる。

## 手法

### 1. 入力処理の注意スコアから疎グラフを作る

長さnの入力の注意スコア行列を `α ∈ [0,1]^(n×n)` とする。各クエリiについて、過去の鍵のうち注意重みが高い上位κ個の位置集合 `K_i` を選ぶ。論文の既定値は `κ=8` である。先頭の注意シンク（attention sinks）10トークンは高得点になりやすいが意味的なまとまりを表さないため、top-κの候補から除外し、生成時には別枠で常時取得する。

直接注意グラフは、クエリiが強く参照した鍵jに `w^(1)_ij = α_ij 1(j∈K_i)` という重み付き有向辺を張る。共注意（co-attention）グラフは、同じクエリmが上位κで共に選んだ鍵iと鍵jを結び、`w^(2)_ij = Σ_m α_mi α_mj 1({i,j}⊆K_m)` とする。直接注意は「iがjを見る」関係、共注意は「iとjが同じ問いに関係する」関係を表す。

両者を `w = (λ/2)(w^(1)+(w^(1))ᵀ) + (1−λ)w^(2)` として対称化・混合する。既定値 `λ=0.5` は直接と共注意の両方を使う設定である。各クエリの直接辺はκ本、共注意の辺は高々κ²本なので、κを定数とみなすと辺数は `O(nκ(1+κ)) = O(n)` に抑えられる。元の密な注意行列を別途フルサイズで保持するのではなく、**通常の入力処理中のQK計算に上位κの選択を融合する**ことが重要である。

### 2. Leiden法で意味的コミュニティへ分割

構築した対称重み付きグラフをLeidenコミュニティ検出へ渡す。Leidenは局所移動、精緻化、集約を繰り返し、グラフのモジュラリティを高める。モジュラリティは、同じ群に属するトークン間の実際の辺の重みが、次数から期待される値よりどれだけ強いかを測る。解像度パラメータγは群の大きさを制御し、γが大きいほど細かな群を作りやすい。

論文は反復回数を `floor(log10 n)` に制限し、辺数がO(n)のグラフに対して初期分割の計算量を `O(n log n)` と見積もる。各群の鍵ベクトル重心を計算する追加処理は `O(nd)` で、全体は `O(n log n + nd)` となる。k-meansで多数の重心へ全トークンを繰り返し割り当てる方式とは異なり、注意の関係を事前に持つ疎グラフ上のスカラー重みを利用する。

### 3. 生成時にコミュニティ重心で候補を選ぶ

生成ステップiでは、現在のクエリ `q_i` とコミュニティごとの重心を比較し、得点の高い群から検索候補集合 `R_i` を作る。群に属するトークン位置を取得し、先頭シンク集合Sと現在位置iを加えて `S∪R_i∪{i}` を注意計算の対象とする。総取得トークン数は4,096などの予算で制限する。群全体を検索単位にするため、離れた位置にあるが共通の文脈で使われるトークンを一緒に取得できる。

論文はグラフの群数が経験的におおむね `O(√n)` で増えると報告し、各重心との照合費用を `O(√n d)` と見積もる。これは全n個の鍵を毎回走査する `O(nd)` より小さい。ただし√n則はモジュラリティの解像度とデータ分布に依存し、**あらゆる入力で厳密な最悪時計算量を保証するものではない**。群の大きさが極端に偏れば、トークン予算に収まる候補集合の作り方にも影響する。

### 4. 新トークンの辺と所属を局所更新

生成した新トークンiを索引へ入れる際、過去の全nトークンとの注意を再計算しない。既に検索した `R_i` と現在位置だけを使い、近似注意重み `α̃_ij` と上位κの鍵を求める。この上位鍵に対して直接注意辺を追加し、同じ上位鍵集合内のペアには共注意辺の増分を加える。更新する辺は高々κ(κ+1)本程度である。

新トークンの所属は、既存の隣接コミュニティに入る場合と、新しい単独コミュニティを作る場合のモジュラリティ利得を比較して決める。過去トークンの所属は固定したまま、新トークンの所属と該当コミュニティ重心だけを更新する。κを定数とすれば重心の更新費用は `O(d)` で、系列長nに依存しない。これが**検索は準線形、更新は系列長に依存しない**という論文の中心的な組合せである。

一方、近似上位鍵は検索済み候補の中からしか選べない。重要な鍵が別コミュニティにあって検索から漏れれば、その鍵との辺も索引に追加されない。局所更新を続けるとグラフ分割が劣化する可能性がある。論文は4,096トークンの継続生成での安定性を検証し、さらに定期的なLeiden再分割による修復も提案する。

### 5. GPU実装の入力処理・分割パイプライン

入力処理のFlashAttention型QKタイル演算にtop-κ選択を融合する。GPUスレッドが各行の少数候補を保持し、タイルごとに比較挿入して上位鍵を更新する。全タイルを処理した後、ワープ間で候補を統合して注意スコアを正規化する。計算量の次数は元の入力処理のQK行列積と同じであり、追加の密行列積を別に実行するわけではない。原著の測定ではこの選択処理が入力処理時間へ6〜8%を追加する。

Leiden分割は層の順伝播と重ねる。層Lの注意スコアが得られた時点でグラフを非同期ワーカーへ送り、次の層の順伝播と並行して分割する。最後の層だけは後続計算で隠せないため、Qwen3系列で約0.37〜0.45秒の分割待ちが露出する。したがって短い生成では前処理費用が支配的になり得るが、長い生成では毎ステップのKV読込削減で償却できる。

## 評価結果

### 検索精度：削除型GraphKVとの違い

| Qwen3-8B / LongBench v2 | 検索予算4,096 | 8,192 | 16,384 | 32,768 |
|---|---:|---:|---:|---:|
| GraphKV（永久削除） | 3.4% | 10.5% | 18.5% | 22.5% |
| CommunityKV（動的検索） | **31.1%** | 31.2% | 31.4% | 31.4% |

密注意の正解率は31.4%である。CommunityKVは4,096トークンの検索で31.1%に達する一方、GraphKVは32,768トークンの保持予算でも22.5%に留まる。これは両者のグラフの使い方が違うためである。GraphKVは削除した過去情報を後から復元できないが、CommunityKVは全KVを保存し、必要なときだけ該当群を取り出せる。**4,096という値は検索するトークン数であり、全KVを4,096トークンへ圧縮して保持するという意味ではない**。

LongBench v2の4,096トークン予算では、Qwen3-4Bが密注意27.4%・CommunityKV27.4%、Qwen3-8Bが31.4%・31.1%、Qwen3-14Bが32.0%・32.0%だった。Questは同じ予算でそれぞれ14.1%、24.7%、30.6%である。ただし小予算128〜256ではMultipoleがCommunityKVより高い場合もあり、全予算帯で常に最高という結果ではない。

BABILongの64k文脈・4,096トークン予算では、Qwen3-8BのQA1〜QA5平均は密注意48.6%、CommunityKV45.4%、SnapKV49.2%であり、**CommunityKVはSnapKVに負けている**。Llama-3.1-8Bでは密注意42.4%、CommunityKV42.2%、SnapKV42.0%で、こちらはCommunityKVがわずかに上回った。長距離の複数事実検索では、モデルと課題によって最良方式が変わる。

測定はH200、バッチ1、出力32,768トークンで、入力処理と全生成処理を含む。クエリヘッド別グラフは速度比1.08〜1.25倍だが、グラフ・重心の補助記憶量がKV本体の52〜82%に相当し、密注意に対するピークメモリ増分は17〜29%だった。クエリグループでグラフを共有すると、補助記憶量はKVの約12〜15%、ピークメモリ増分は0.5〜8.5%となり、速度も1.39〜1.71倍へ改善した。精度はヘッド別32.0%に対してグループ集約31.8%と近い。

ここでのグループ集約は、グループ化クエリ注意（grouped-query attention; GQA）でKVを共有するクエリヘッド群ごとに索引を共用することを指す。層全体で一つのグラフへ集約すると、後述のように精度が大幅に悪化する。**索引の共有単位が速度・メモリ・品質を同時に左右する**ことが実測されている。

### 構成要素除去と悪化条件

| Qwen3-14B / LongBench v2 / 4,096トークン | 精度 | 解釈 |
|---|---:|---|
| κ=2 | 30.3% | 辺が少なく群が断片化 |
| **κ=8** | **32.0%** | 既定の疎密バランス |
| κ=32 | 27.8% | 辺を増やし過ぎて群の境界が曖昧になる |
| λ=0（共注意のみ） | 28.8% | 直接注意の情報が不足 |
| **λ=0.5** | **32.0%** | 両関係を混合 |
| λ=1（直接注意のみ） | 28.5% | 共注意の関係が不足 |
| ヘッド別グラフ | 32.0% | 品質基準 |
| クエリグループ共有 | 31.8% | メモリ削減と品質維持の両立 |
| 層単位共有 | 21.5% | 共有し過ぎると検索精度が崩れる |
| シンクをグラフから除外 | 32.0% | 既定 |
| シンクをグラフに含める | 31.3% | 無関係な群をつなぐハブになり得る |

Leidenを単純な連結成分分割や、上位鍵の一近傍をたどる方法へ置き換えた比較でも、CommunityKVが予算128〜4,096の全条件で上回った。したがって性能は単にQKスコアからグラフを作ったことだけでなく、**グラフをモジュラリティで分割して検索単位を作る処理**にも依存する。重心を追加で取得する予算を設ける試験では、重心なしの32.0%に対して重心256個の設定は28.6%へ低下し、圧縮された広さより原トークンを深く検索する方が有利だった。

## 長期生成での索引の劣化と再分割

局所更新は過去トークンの所属を変えないため、生成が続くと新しい話題に合わないコミュニティ構造が残り得る。原著は4,096トークン生成で注意質量の保持率が85%を上回ることを確認したが、これは任意長で劣化しないという保証ではない。16,384トークンの固定継続文脈では、512ステップごとにLeidenを再実行すると、最後の512トークンでの密注意top-1一致率が68.05%から82.81%へ改善した。

定期的な全体再分割には追加遅延が発生する。原著は約√nステップごとに再分割する場合の償却計算量を `O(√n log n)` と見積もるが、長い実配信でどの頻度が最適かはGPU負荷と分割の劣化速度に依存する。新トークンの辺は検索済み候補にしか張れないため、検索漏れが更新にも伝播するという近似誤差の循環がある。

## 既存研究との差

GraphKVは注意グラフを用いて冗長なKVを永久削除するのに対し、CommunityKVは**全KVを保存したまま動的に読み込む**。Questは連続したトークン区間を検索単位にするが、CommunityKVは離れた位置のトークンも同じ群にできる。Multipoleは鍵ベクトルのクラスタリングで群を作るが、初期のk-means費用と生成時の更新が重い。CommunityKVは入力処理中のQKスコアを再利用し、グラフの局所更新だけで生成を継続する。

学習型のDeepSeek Sparse Attentionなどと違い、疎性のためにモデルの重みを追加学習しない。ただし学習不要だから計算費用がゼロになるわけではない。入力処理のtop-κ選択に6〜8%の時間が加わり、Leiden分割と索引保存にも費用がかかる。生成が十分長いほどKV読込削減の便益を償却しやすい。

## 限界と適用判断

原著の端から端速度評価はH200、バッチ1、非常に長い出力32,768トークンで行われている。短い回答、同時要求数の多いサービング、PCIe/CPUメモリへのオフロード併用、別GPUで同じ1.71倍を保証しない。追加ピークメモリがヘッド別で最大約29%に達するため、容量が厳しいGPUではむしろ実行可能バッチ数を減らす可能性がある。グループ集約が有利なのは、KVヘッド共有構造と索引の共有単位が整合する場合である。

Leidenの分割品質はトークン間の注意グラフが意味的な集団を持つという仮定に依存する。孤立した単一事実の検索や、異なる群を横断する推論では群単位の検索が余分なトークンを含むこともある。新トークンの局所更新は近似検索で取り逃した鍵を復元できず、長期生成では再分割が必要になる可能性がある。論文の「O(d)更新」は新トークンの索引への追加部分の計算量であり、クエリ重心検索 `O(√n d)` や選択トークンへの注意演算を含む総生成ステップが定数時間になるという意味ではない。
