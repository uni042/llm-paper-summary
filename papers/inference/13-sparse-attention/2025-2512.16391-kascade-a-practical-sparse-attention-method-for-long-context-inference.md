# Kascade: A Practical Sparse Attention Method for Long-Context LLM Inference

> 長文脈の注意を10%だけ計算すれば理論上は大きく速くなるが、「どの10%を残すか」を毎層正確に探す処理が高い。Kascadeは、**高い注意重みを持つキー集合が近接層でかなり似る**という性質を利用し、少数のアンカー層だけでTop-k探索をやり直す。残りの層ではそのインデックスを再利用するため、疎化の選択費用を層間で償却できる。さらに、ヘッド間で重要キーが同じとは限らないため、GQAを含むヘッド対応を学習不要のマッピングとして扱う。

## 概要

長文脈Transformerでは、プリフィルの注意計算は系列長 (N) に対して概ね (O(N^2))、デコードでは新しい1クエリが過去 (N) 個のKVを読むため1トークン当たり (O(N)) になる。MLP側は系列長に対して線形またはデコード1ステップで定数的なので、文脈が長くなるほど注意が占める割合が増える。

注意重みのsoftmax後分布は多くの場合疎で、出力へ大きく寄与するキーは一部だけである。そこでTop-kキーだけへ注意すれば計算量とKV読み出しを減らせる。しかし動的Top-k方式には逆説がある。**正しいTop-kを知るために全キーとのスコアを計算すると、疎化前と同じ仕事をほぼ一度してしまう**。

Kascadeはこの探索費用を「層方向に再利用」する。いくつかの層をアンカー層（anchor layer）にして正確なTop-kを求め、その間の再利用層（reuse layer）は直前のアンカーで得たキー集合だけを見る。どの層をアンカーにするかは固定間隔ではなく、開発集合上で層間Top-k類似度を測り、限られたアンカー数で類似度を最大にする動的計画法で決める。

## 背景：なぜ既存の疎注意だけでは不十分か

### 固定窓は速いが、遠距離依存を内容に応じて残せない

StreamingLLMのような固定窓は選択費用が小さく、GPU実装もしやすい。しかし「直近だから残す／古いから捨てる」という規則は、RAGの文書内にある離れた根拠や、推論途中で参照し直す古い中間結果を内容に応じて保持できない。

### 動的Top-kは精度に強いが、探索自体が重い

Questなどはクエリに合わせて重要なKVページを選ぶため、固定窓より柔軟である。一方、重要度計算・ページ統計・Top-k選択が追加される。特にプリフィルは多数クエリが同時に存在するので、トークン単位の細かなTop-kはGPUタイル実行と相性が悪い。

### 近接層では「重要な場所」が似る

Kascadeの観測は、softmax後に大きな注意重みを持つキーの集合が隣接層で高い重なりを持つことにある。論文では、ある層のTop-k集合が次の複数層のTop-kを高率で包含する例を示す。

この性質が成立するなら、「各層で重要キーを探す」必要はない。数層ごとにだけ探索し、その間はインデックスを使い回せる。

## 手法

### 1. アンカー層では正確なTop-kを求める

アンカー層では、全キーに対する注意スコアを計算し、softmax後の注意重みから重要なキーを選ぶ。Kascadeがpost-softmax値を使うのは、単純な生のQKスコアより「最終的に出力へどれだけ寄与するか」に近い尺度になるためである。

ただしsoftmax後Top-kを得るには正規化分母が必要で、アンカー層は再利用層より高価になる。実装は複数パスになる。

デコードでは概ね、
1. 全QKスコアと行和を計算・保持、
2. softmaxしてタイル単位へプール、
3. プール値に対してTop-kタイルを選ぶ、
4. 選んだキーだけで最終注意を計算する、

という流れになる。

プリフィルでは全注意行列をHBMへ書くと巨大なので、第一パスでは主に行和を保持し、第二パスでQKを再計算してpost-softmax値を得る。そのため**プリフィルのアンカー層は再計算費が大きい**。これがデコードよりプリフィル高速化率が小さい主因の一つである。

### 2. 再利用層ではTop-k探索を省く

アンカー層の後に続く再利用層は、アンカーが選んだキー/タイルだけに注意を計算する。Top-k=10%なら、理想的な再利用層では読むKVと注意演算を約1/10へ近づけられる。

論文のH100測定では、再利用層カーネル単体は全注意の約10%程度の時間まで下がる長文条件がある。しかしモデル全体では5層程度のアンカー層が残るため、最終高速化は10倍ではなく4倍前後になる。

### 3. アンカー層を動的計画法で選ぶ

単純に「4層ごとにアンカー」とすると、層間類似性が急に変わる境界をまたいでTop-kを再利用し、精度を落とす可能性がある。

Kascadeは開発集合上で、アンカー候補層aのTop-kを後続層bへ流用したときの類似度行列 (S[a,b]) を作る。平均だけでなく、プロンプト内で悪いトークンを拾う保守的な集約を使い、所定のアンカー数で総類似度が高くなる区切りを動的計画法で選ぶ。

論文設定ではMuSiQueの1000要求を開発集合に使用する。代表例は次の通りである。

| モデル | 総層数 | アンカー層 |
|---|---:|---|
| Llama-3.1-8B-Instruct | 32 | [0, 2, 8, 13, 14] |
| Qwen3-8B | 36 | [0, 2, 7, 14, 23] |
| DeepSeek-R1-Distill-Llama-8B | 32 | Llama-3.1と同じ集合 |

したがってKascadeは学習不要だが、**新モデルへ完全に無調整で投入する方式ではない**。小規模な開発集合で層間類似度を測り、アンカー配置を事前決定する工程がある。

### 4. タイル単位Top-kでGPU実装へ合わせる

FlashAttention系カーネルはQ/Kをタイル単位で処理する。各トークンが全く別のTop-kキーを選ぶと、不規則なgatherが増えてGPU効率が下がる。

Kascadeはクエリタイル内の複数トークンでキー選択を共有できるよう、注意重みをキー側タイル単位へプールしてTop-kを選ぶ。論文・公式実装の高速カーネルではtile size 32を前提にする。

この設計により、理論的な「10%のキーだけ見る」を、まとまったメモリアクセスとタイル演算へ変換する。

### 5. ヘッドを無視してTop-kを共有しない

グループ化クエリ注意（Grouped-Query Attention; GQA）では複数のquery headがKV headを共有するが、各query headが注目する位置は同一とは限らない。また隣接層でも「似た役割のヘッド番号」が単純に一致するとは限らない。

Kascadeはアンカー層と再利用層のヘッド間類似度を使い、再利用側ヘッドを最も適したアンカー側ヘッドへ対応付ける。全ヘッドで一つのTop-k集合を共有する変種も評価されているが、AIME-24では標準Kascadeより精度が落ちる。

この結果は、疎注意で**層方向の再利用はできても、ヘッド方向まで無条件に共有すると情報を潰す**ことを示す。

## 一要求の処理

長文プロンプトのプリフィルでは、まず第0アンカー層で密注意を計算し、Top-kタイルを得る。続く再利用層はそのタイルだけを参照する。次のアンカー層へ到達したら全キーを再度評価し、Top-k集合を更新する。この処理を層末尾まで繰り返す。

デコードでも同じアンカー/再利用構造を使う。各生成トークンについてアンカー層は現在クエリに対するTop-kを更新し、再利用層はその集合を使う。文脈長が増えるほど、密なアンカー層の費用は増えるが、再利用層で省けるKV読み出しも増えるため利得が大きくなる。

### LongBench：プリフィルも疎化した上でどこまで残るか

LongBenchはプリフィル比率が高い。Quest、OmniKV、LessIsMoreはこの比較ではプリフィルを密注意のままにするため、デコードだけ疎化する方式とKascadeの得点は単純には同じ仕事量ではない。

| モデル | 方式 | LongBench平均 |
|---|---|---:|
| Llama-3.1-8B-Instruct | 密注意 | 45.92 |
|  | StreamingLLM | 33.42 |
|  | LessIsMore（decode-only） | 45.52 |
|  | OmniKV（decode-only） | 45.75 |
|  | Quest（decode-only） | 44.39 |
|  | **Kascade** | **45.02** |
| Qwen3-8B | 密注意 | 46.35 |
|  | StreamingLLM | 34.57 |
|  | LessIsMore（decode-only） | 43.77 |
|  | Quest（decode-only） | 43.95 |
|  | **Kascade** | **44.57** |

Llamaでは密注意との差0.90点、Qwenでは1.78点である。Kascadeはプリフィルまで10% Top-kへ疎化しているため、decode-only法と近い平均値でも計算削減範囲が広い。

### AIME-24：長い思考過程で疎化が崩れないか

AIME-24は30問の数学推論で、各設定を8回サンプリングして平均Pass@1を報告する。

| 方式 | DeepSeek-R1-Distill-Llama-8B | 平均生成長 | Qwen3-8B | 平均生成長 |
|---|---:|---:|---:|---:|
| 密注意 | 50.42 | 11.3K | 73.75 | 14.4K |
| StreamingLLM | 0.00 | 7.5K | 0.00 | 6.9K |
| LessIsMore | 36.25 | 14.8K | 60.83 | 17.9K |
| OmniKV | 39.58 | 12.5K | — | — |
| Quest | 7.50 | 22.9K | 25.33 | 28.8K |
| **Kascade** | **47.92** | **14.6K** | **70.42** | **15.9K** |
| Kascade・全ヘッド共有 | 41.25 | 14.0K | 65.83 | 17.9K |

10% Top-kでは密注意との差がDeepSeekで2.50点、Qwenで3.33点に収まる。一方、生成長はDeepSeekで約29%、Qwenで約10%長くなっており、**Pass@1が近いから生成挙動も同一というわけではない**。

また全ヘッド共有は標準Kascadeより6.67点/4.59点落ちる。ヘッド再マッピングが単なる実装詳細ではなく品質維持に効くことが分かる。

Top-kを20%へ増やすとDeepSeekのAIME精度は密注意へさらに近づき、生成長も短くなる。したがってkは速度だけでなく、推論経路の安定性を調整する主要ノブである。

### H100注意カーネル性能

10% Top-kの代表値は次の通りである。

| フェーズ | 文脈長 | FlashAttention-3 | Kascade | 高速化 |
|---|---:|---:|---:|---:|
| デコード | 8K | 約0.70 ms | 約0.24 ms | 約2.9倍 |
| デコード | 131K | 約11.68 ms | 約2.83 ms | 約4.1倍 |
| デコード | 512K | 約21.85 ms | 約5.33 ms | 約4.1倍 |
| プリフィル | 8K | 約0.76 ms | 約0.62 ms | 約1.2倍 |
| プリフィル | 131K | 約215.76 ms | 約98.55 ms | 約2.2倍 |
| プリフィル | 262K | 約864.02 ms | 約408.30 ms | 約2.1倍 |

短めの8KではアンカーTop-k選択の固定費が大きく、特にプリフィルは1.2倍程度に留まる。長文化すると密注意の仕事量が増える一方、再利用層は10%だけ読むので差が開く。

### どの処理が残るか

再利用層だけならほぼTop-k比率に沿って高速化できる。しかしアンカー層では、
- 全QK計算、
- softmax正規化、
- タイルプール、
- Top-k、
- 選択後の注意、

が必要である。プリフィルではQKの再計算まである。このため**アンカー層の割合が性能上限を決める**。

32層中5層をアンカーにするLlama設定より、36層中5層のQwen設定の方がアンカー比率は低く、同じTop-kなら理論上再利用の恩恵を受けやすい。

## 既存研究との差

StreamingLLMは固定窓 + attention sinkで選択費用をほぼなくす代わりに、内容依存の遠距離情報を落とす。AIME-24で0%になった結果は、長い推論で固定窓が破綻し得る例である。

Questはクエリ依存Top-kを行うが、Kascadeは**選択結果そのものを層間共有する**ことでTop-k探索費を減らす。OmniKVやLessIsMoreも層選択やKV削減を使うが、論文比較ではプリフィルを密のままにする。

Kascadeの特徴は、アルゴリズム上の疎化率だけでなく、タイル選択・ヘッド対応・アンカー層の多パス処理まで実カーネルに合わせて設計し、プリフィルとデコードの双方を高速化した点にある。

## 限界・実装状況

第一に、KVキャッシュの**保存容量そのものは基本的に減らさない**。Kascadeは各層の注意で読むキー/値を減らす方式であり、将来のクエリに備えてKV全体は保持する。KV容量が主問題なら量子化・eviction・offloadを別途組み合わせる必要がある。

第二に、アンカー層配置とヘッドマッピングを開発集合から作る必要がある。MuSiQueで選んだ配置が分布外ワークロードでも最適とは限らない。

第三に、10% Top-kでも密注意との差はゼロではない。AIMEでは生成長が増え、20%へ上げると精度と生成長が改善するため、速度/品質の交換条件が残る。

第四に、公式の高速経路は2026-09-28時点でHopper系、FP16、tile size 32などに制約があり、vLLM統合も実験的ブランチである。A100、L40S、Blackwell、別のページサイズで同じ倍率になるとは限らない。

第五に、性能値は注意カーネル中心であり、LLM要求全体のエンドツーエンド倍率ではない。MLP、通信、サンプリング、ランタイムスケジューリングを含めると、モデル全体の高速化は注意が占める割合に制限される。

## サーベイ上の含意

Kascadeは、疎注意のボトルネックが「何個残すか」だけでなく**重要トークンを見つける費用**にあることを明確に示す。動的選択を毎層繰り返す代わりに、モデル内部の時間的/層間局所性を使って制御決定をキャッシュする設計と捉えられる。

この考え方は注意以外にも一般化できる。専門家混合（Mixture of Experts; MoE）のexpert選択、KV圧縮率、オフロード先など、近接層・近接トークンで最適決定が安定するなら、重い最適化をアンカー時点だけ実行し中間で再利用できる可能性がある。ただし、再利用期間を伸ばし過ぎたときの品質劣化を測る必要がある。
