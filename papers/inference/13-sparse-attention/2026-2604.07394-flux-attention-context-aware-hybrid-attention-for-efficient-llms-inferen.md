## 概要

Flux Attentionは、長文LLMの各Transformer層で**完全注意（Full Attention; FA）を維持するか、疎注意（Sparse Attention; SA）へ切り替えるか**を、入力promptの文脈に応じて学習した軽量ルータで決める方式である。既存のhybrid attentionは全入力に固定のFA/SA層比率を適用したり、head単位で細かく選んだりする。前者は検索中心の質問と全体要約のように必要な文脈参照が異なるタスクへ適応しにくく、後者はGPU上でheadごとの演算量が不均衡になり、同期の遅いheadに全体が引きずられる。

Flux Attentionは層全体をFAかSAのどちらかへ切り替えるため、同じ層内のheadが同じ演算パターンとなり、GPU実装が比較的単純になる。ルータはprefillで1回だけ実行し、その層別選択をdecode中に使い回す。SA層では完全な履歴KVを保持しないため、attention計算だけでなく永続KVメモリも減る。

Llama-3.1-8B-Instructの256K文脈・モデル疎化率約50%という条件では、PruLongのRULER 30.00に対しFlux 59.39、decode遅延36.14に対し24.58ms/token、永続KVメモリ28.79に対し17.47GiBを報告する。dense FA2はRULER 72.34なので、Fluxは**PruLongより精度を守るがdense精度を完全には維持しない**。また原著のprefill最大2.8倍は別のFA-TA backend構成であり、この約50%疎化の表にあるprefill 1.77倍とは区別する。

## 問題設定

### 固定疎化率とhead単位のGPU負荷不均衡

長文ではFAの計算量とKV読み出しが大きくなるが、すべてのタスクが同じ程度に長距離依存を必要とするわけではない。特定箇所の検索や複数文書からの情報抽出は一部の重要位置を保持すべきであり、長い文書の全体要約やコード補完では別のattentionパターンが有効になり得る。静的な層・head割当では、これらの差を同じ設定で扱う。

head単位でFA/SAを混ぜると、GPUの同一層内でheadごとに異なるKV読出し・演算量が発生する。最も遅いheadへの同期待ちや非連続メモリアクセスにより、理論的な疎化率に比例した実行時間短縮が得られない。Fluxはルータの選択単位を**層全体**へ粗くすることで、このGPU実行上の問題を回避する。

### 精度・遅延・KV容量の三者交換

FA層は過去の完全KVを保持し、長距離検索を守る。一方SA層は疎attention kernelに必要なKVだけを残す。ルータの選択により、品質、prefill時間、decode時間、永続KV容量が変わる。単なる疎化率の最大化ではなく、同じ疎化率でどの層をFAとして残すかが重要になる。

## 手法

### 1. Prefix/Suffix poolingとLayer Router

各層の入力queryテンソルから、promptの先頭と末尾にあるtoken群の特徴をpoolingしてシーケンス記述子を作る。これをMLP Context Encoderへ渡し、別のMLP Router HeadがFAとSAの2つのlogitを出す（原著第3.1節）。先頭に指示が置かれ、末尾に質問が置かれる長文promptを想定し、全文の追加エンコードを避ける軽量な特徴抽出である。

このpoolingはheuristicであり、文脈中央に重要な指示が散在する場合は十分な情報を得られない可能性がある。ルータが全promptを理解したと解釈してはいけない。

### 2. 学習時のsoft routing

FA/SAの二値選択はそのままでは微分できないため、学習時はGumbel-Softmaxの温度`τ`でsoft weight `r_soft`を作る（式4）。各層の出力を`r_soft·FA(Q,K,V)+(1−r_soft)·SA(Q,K~,V~)`と混合してcross-entropyで学習する（式5）。温度は学習とともに下げ、推論時の二値化との差を減らす。

基盤LLMの重みは凍結し、ルータだけを更新する。FAに全層を割り当てれば言語損失が小さくなりやすいため、SA層割合が目標から外れる量`L_diff`に対するLagrangian型の線形・二乗罰則を加える（式6）。タスクごとに異なる疎化目標と乗数を学習する。原著は検索重視のタスクに0.45、文脈全体を扱うタスクに1.0の目標を設定したと記載するが、実際に採用される疎化率はルータが選んだ結果`Ω_MSR`として別途計測される。

### 3. 推論時のhard routingとdecode再利用

推論ではprefill中に各層のFA/SA logitのargmaxから二値決定を1回作り、decode中はその選択をキャッシュして使う。`Ω_MSR=(1/L)Σ_l(1−r_hard^(l))`はSAを選んだ層の実現割合である。tokenごとにルータを再実行しないため、制御費用が小さく、各層の演算パターンが安定する。複数ターンの対話では新しいturnのprefill時にルートを再評価するので、全会話を通じて固定するわけではない。

FA層は完全KVを保持し、SA層は選択したsparse kernelが必要とする最小限のKVだけを保持する。SA backendにはStreaming Sparse Attention（SSA）、XAttention（XA）、Triangle Attention（TA）を実験し、ルータの層選択と実際の疎attention演算子を分離している。原著の実装はBlock-Sparse-Attentionのblock64、chunk16384、sink128などを用いる（付録F）。

### 4. 学習データと費用

Qwen3-4B/8BとLlama-3.1-8B-Instructをbackboneに使い、ChatQA2-Long-SFT、MuSiQue、CoLT-132K、GovReport、XSumを組み合わせて、検索中心・全体文脈処理の両方を含む約0.74B token、長さ1K～64Kの学習集合を作る。ルータ学習は8台A800で1 run約12時間。付録FではBF16、global batch48、300 training steps、AdamW、warmup0.2等を記載する。

訓練元コーパスと下流ベンチマークの間に完全なサンプル非重複が保証されるわけではなく、著者らは付録F.2でその制約を明示する。結果は学習データのタスク分布とルータの汎化に依存する。

### 最大prefill・decode速度の解釈

原著図3では、FA-TA（FA層とTriangle Attention疎層）構成の256K prefillでdense比最大2.8倍のend-to-end短縮を報告する。これは上のFA-SSA・約50%疎化比較表の1.77倍と別のbackend/設定である。decodeでは図3の単独kernel測定で約2.0倍へ近づくと説明するが、付録表16のFA-SSA・256Kでは2.22倍となっている。両者は対象backend・疎化率・測定系列が異なるため、数値の不一致を一つの固定条件の矛盾とみなさない。

### 品質と学習のばらつき

LongBench-EではQwen3-4Bのdense平均48.45に対しFA-SSA Flux平均48.72という小さな改善があるが、すべてのモデル・タスクでdenseを上回るわけではない。Llama-3.1-8B-InstructのRULER 128Kではdense 80.12、FA-SSA sparse-decode Flux 62.94で17.18ポイント低下する。Elastic Attentionとの付録比較ではLlamaのRULER平均がElastic 72.85、Flux 76.75、dense 83.47となり、Fluxは競合より改善してもdense未満である。

付録G.4ではLlamaの2回のルータ学習seedにおけるLongBench-E平均が52.19と52.27で、差0.08ポイントと報告する。ルータの訓練seedによる揺らぎが小さいという根拠にはなるが、異なるデータ分布・バックボーンでの汎化保証ではない。

## 既存研究との差

DuoAttentionやPruLongはhead単位でFA/SAを割り当てる。Fluxはlayer単位でFA/SAを選び、同一層内の実行パターンを均一化することで、理論的な疎化率を実GPUのdecode高速化へ変換しやすくする。さらにルータがpromptの内容を読んで層配分を変えるため、全入力で固定した層構成より検索中心・文脈全体処理の双方に適応できる。

Elastic Attentionのようなhead単位の動的選択は細粒度で表現力が高いが、実行時の負荷不均衡が問題になる。Fluxは細粒度を捨てて実装しやすさを取る設計であり、head単位の方法がアルゴリズム的に常に劣ると主張するものではない。SA backend自体はSSA/XAttention/TAなどに差し替えられるが、論文が実測した組合せ以外での速度改善を保証しない。

## 限界と実務上の判断

1. **層単位の粗さ:** 一部のheadだけが長距離情報を必要とするタスクでは、層全体をFAに残すかSAにする二値選択が非最適になり得る。
2. **prefix/suffix heuristic:** prompt中央に重要な指示が分散している場合、先頭・末尾poolingではタスク意図を捉えきれない可能性がある。
3. **denseとの差:** 256K RULERはdense 72.34、Flux 59.39。PruLong比で良くても完全な品質維持ではない。
4. **backend依存:** 最大2.8倍prefillはFA-TA設定、約50%疎化の表はFA-SSA設定。任意の疎attention演算子で同じ高速化は保証されない。
5. **GPU条件:** 単一A800 80GBと8×H20の実験。異なるGPU・batch・文脈長・サービングエンジンでの再現性は未確認。
6. **学習データ:** 約0.74B tokenの混合学習であり、公開ベンチマークとの完全な非重複を保証していない。タスク分布の違いでルーティングが変わり得る。
7. **router費用:** 原著は平均0.20ms/層と報告する。decodeでは再利用するが、prefillの追加費用はゼロではない。
8. **コード:** 原著に[公式GitHub](https://github.com/qqtang-code/FluxAttention)が明記される。利用時には対応backboneとbackendの実装条件を別途確認する必要がある。
