# FlashPrefill: Instantaneous Pattern Discovery and Thresholding for Ultra-Fast Long-Context Prefilling

## 概要
FlashPrefillは、長文脈大規模言語モデル（LLM）のプリフィル（プリフィル）で支配的になる二次複雑度の自己注意を、入力ごとに発見したブロック-疎 注意へ置換する手法である。既存の動的疎注意では「重要ブロックを探す処理」自体が高価で、4K〜16K程度では密 FlashAttentionより遅くなることがある。FlashPrefillは、注意スコアの完全計算・ソート・prefix sumを避け、少数のクエリ probeとプール済み キーからvertical / slash / ブロック-疎の混合パターンを一度に見つける。

もう一つの中心機構は最大値ベース動的閾値（max-based 動的 閾値処理）である。上位k件のように各クエリへ固定数ブロックを残すのではなく、そのクエリ ブロックで得た最大proxy スコアに比例する閾値を作り、長いlow-スコア tailを1 passで削る。入力によって必要ブロック数が変わるため、固定疎性より適応型でありながらソートやcumulative sumを要しない。Qwen3-30B-A3B-Instruct-2507の演算子 ベンチマークでは4Kで1.71倍、256Kで27.78倍、vLLM エンドツーエンドの初回トークン生成時間（TTFT）で最大7.22倍を報告する。

## 問題設定
プリフィルでは文脈中の全クエリが過去キーへ注意するため、系列長 `L` に対し注意計算・メモリ トラフィックが `O(L²)` で増える。長文脈モデルではFFNやMoE部分を高速化しても、プリフィル 注意がwall-clockを支配し得る。

疎注意は有効だが、動的手法には探索オーバーヘッドがある。全スコアを計算してから上位k件をソートすれば既に密 注意に近い仕事をしてしまう。上位確率質量のためにスコアをソートし累積和を取ればさらに重い。固定ブロック パターンなら探索不要だが、実際の注意はsink、局所 diagonal、vertical retrieval、散在ブロックなどがヘッド・層・入力ごとに変わるため、固定パターンでは品質か疎性を犠牲にしやすい。

FlashPrefillの設計目標は、**パターン discoveryそのものを密 注意より十分安くすること**、かつ4Kのような比較的短い文脈でも探索費を償却できることである。

## 手法
### 1. block単位のproxy score
キー 系列をブロックへ分け、各キー ブロックを平均プーリングして代表ベクトルを作る。クエリ側も全クエリを使うのではなく、系列全体へ均等に配置したクエリ probeを使う。各probeとプール済み キー ブロックのdot productからブロック重要度のproxyを得る。

単純なmean キーに対する指数スコアは、ブロック内の各キー スコアの指数和に対する幾何平均に対応し、ブロック内分散が極端でない限り重要ブロックのrankを概ね保持できる、というのが近似の根拠である。これによりトークン-トークン全組合せを計算せず、注意の大域構造を粗いブロック resolutionで観測する。

### 2. 瞬時pattern discovery
長文脈注意には、同じキー列が多数クエリから参照されるvertical パターン、causal diagonalに沿うslash/局所 パターン、離れた局所領域に集中するブロック パターンが混在する。FlashPrefillはこれらを別々のdetectorで探索するのでなく、均等クエリ probe × プール済み-キー スコアを共通の観測として使い、重要ブロック coordinateをまとめて抽出する。

ただし、全クエリ ブロックと全キー ブロックのproxy 行列を大域 メモリへ書けば `O(L²/B)` の中間テンソルが生じ、探索自身がメモリ ボトルネックになる。そこで実装は2次元のfused reductionを使う。クエリ tileとキー ブロックのスコアをSRAM上で計算し、クエリ軸でmax reduction、指数変換、sum reductionを同一カーネル内に融合する。大域 maxを使って数値規模を合わせながら、必要なブロック-level scalarだけを出力する。巨大なスコア 行列をDRAMへmaterializeしないことが短文脈でも速い理由の一つである。

### 3. 最大値ベース動的閾値
各クエリ ブロック `I` についてブロック proxy スコア `S_{I,J}` を得た後、
`threshold_I = α · max_J S_{I,J}`
を計算し、閾値未満のキー ブロックを落とす。上位k件なら何個残すかを先に決める必要があり、上位確率質量ならソートとcumulative sumが必要だが、max-based 閾値は最大値reduceと比較だけで済む。

強い注意 最大が少数しかないクエリでは残存ブロックが少なくなり、スコアが広く分散したクエリでは多く残る。このため実際の疎性はクエリ/層/入力ごとに変動する。係数 `α` は速度と忠実度の主要hyperparameterで、高くするとより aggressiveに削れるが重要な中程度スコアも落としやすい。

### 4. index-driven sparse attention kernel
パターン discoveryで得たブロック indexを、後段のTriton 疎 注意カーネルへ直接渡す。論理的には全キー ブロックをloopしてマスクでskipする実装も可能だが、それではindex計算とbranchを全ブロック分払う。FlashPrefillは選択済み ブロック coordinateへ物理的にjumpし、保持ブロックだけQK^T、softmax、PVを計算する。

したがって総時間は「パターン discovery + 閾値 + 疎 注意」で決まり、文脈が長く疎性が高いほど密 `O(L²)` との差が拡大する。主対象はプロンプト プリフィルで、デコード時の1-クエリ対長-KV 注意を同じ方法で高速化するものではない。

## 評価条件
演算子 ベンチマークの中心モデルはQwen3-30B-A3B-Instruct-2507で、文脈 長さ 4K〜256Kを掃引する。比較はFlashAttention 密、FlexAttention系、XAttention、FlashMoBA等の長文脈疎注意。PyTorch 2.9/Triton系環境で実装し、同一GPU上で注意カーネル 遅延を測る。

品質はNeedle-in-a-Haystack、RULER、InfiniteBenchを使い、Llama-3.1系、Qwen2.5系、Qwen3系で完全 注意との精度差を調べる。さらにvLLMへ統合し、注意カーネル単体ではなくリクエストのTTFTがどこまで短縮されるかを測る。

## 主要結果
### operator速度
Qwen3-30B-A3B-Instruct-2507ではFlashAttentionに対し、4K 1.71倍、8K 2.79倍、16K 4.48倍、32K 6.94倍、64K 11.45倍、128K 18.67倍、256K 27.78倍と文脈長にほぼ単調に高速化倍率が伸びる。4Kでも1を超える点が、パターン discovery固定費を抑えた設計の主張に対応する。

代表的な絶対 遅延でも、32Kで密約97.2msに対しFlashPrefill約14.0ms、256Kでは約6044.1msに対し約217.6ms。長文脈では密 注意の二次増大を疎 ブロック数へ置き換えた効果が支配的になる。

固定疎性で疎 カーネル自体を比較すると、60%残存条件で4Kは既存1.27ms対0.72ms、512Kは14990.36ms対11256.11ms。6%残存では4K 0.43ms対0.14ms、512K 1513.66ms対1109.44msで、パターン discoveryだけでなくindex-driven カーネル側にも利得がある。

### end-to-end
vLLMへ統合したTTFTでは最大7.22倍を報告する。演算子の27.78倍より低いのは、実サービスではembedding、MoE/FFN、normalization、ランタイム scheduling等の非注意 コストが残るためである。したがってheadlineの27.78倍を「LLM全体のプリフィルが27.78倍」と読むのは誤りである。

### 品質
Needle-in-a-Haystackでは完全 注意とほぼ同じretrieval挙動を示す。RULER平均ではLlama-3.1系で完全 89.12に対しFlashPrefill 90.15と同等圏で、128Kも74.25対75.31。単純な固定ブロック 枝刈りと比べ、入力-適応型 discoveryが重要情報を残せていることを示す。

ただしInfiniteBenchは完全無損失ではない。Llama-3.1系の平均は完全 48.39に対しFlashPrefill 46.32、Qwen3系は37.83対36.23へ下がる一方、Qwen2.5系は23.87対24.93と上がる。データセット/モデル依存の揺れがあり、「全タスクで無損失」とは言えない。

## 既存研究との差
固定ウィンドウや固定ブロック-疎方式はパターン探索が不要だが、入力-dependentな長距離 retrievalを捨てやすい。XAttention等の動的 疎 注意は重要ブロックを探せるが、スコア aggregation・ソート・選択のオーバーヘッドが短〜中文脈で大きい。FlashPrefillはプール済み ブロック proxy、fused 2D reduction、max 閾値を一つの高速パイプラインへまとめ、探索コストを削ること自体を主貢献にする。

上位k件方式とも異なり、各クエリへ固定ブロック数を割り当てずスコア分布に応じて疎性が変わる。そのため「簡単なクエリは強く削り、必要なクエリは広く残す」という適応型 予算 allocationになる。

## 限界
FlashPrefillは近似疎 注意であり、削除したブロックの寄与は復元されない。InfiniteBenchの一部モデルで平均スコアが下がるように、注意が広く分散するタスクや、中程度のスコアを持つ多数のキーが協調して効くタスクでは品質 lossが生じ得る。

閾値係数 `α` は速度・疎性・品質のtrade-offを決めるため、モデル/ヘッド/タスクの注意 sharpnessが変われば最適値も変わり得る。4Kでも高速とはいえ、密 カーネルが非常に小さいバッチ/shapeや異なるGPUで同じ倍率になる保証はない。

また主対象はプリフィルであり、自己回帰デコードのKV キャッシュ 帯域を27.78倍削減する方式ではない。vLLM エンドツーエンド最大7.22倍が示す通り、システム全体では注意以外のコストが残る。Triton 疎 カーネル・ハードウェア アーキテクチャへの依存もあり、他バックエンドで同じ絶対 性能が得られるとは限らない。
