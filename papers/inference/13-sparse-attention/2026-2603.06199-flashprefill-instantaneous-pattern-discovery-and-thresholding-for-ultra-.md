# FlashPrefill: Instantaneous Pattern Discovery and Thresholding for Ultra-Fast Long-Context Prefilling

## 概要
FlashPrefillは、長文脈大規模言語モデル（LLM）のプリフィル（prefill）で支配的になる二次複雑度の自己注意を、入力ごとに発見したblock-sparse attentionへ置換する手法である。既存の動的疎注意では「重要blockを探す処理」自体が高価で、4K〜16K程度ではdense FlashAttentionより遅くなることがある。FlashPrefillは、注意scoreの完全計算・sort・prefix sumを避け、少数のquery probeとpooled keyからvertical / slash / block-sparseの混合patternを一度に見つける。

もう一つの中心機構は最大値ベース動的閾値（max-based dynamic thresholding）である。top-kのように各queryへ固定数blockを残すのではなく、そのquery blockで得た最大proxy scoreに比例する閾値を作り、長いlow-score tailを1 passで削る。入力によって必要block数が変わるため、固定sparsityよりadaptiveでありながらsortやcumulative sumを要しない。Qwen3-30B-A3B-Instruct-2507のoperator benchmarkでは4Kで1.71倍、256Kで27.78倍、vLLM end-to-endのtime-to-first-token（TTFT）で最大7.22倍を報告する。

## 問題設定
prefillではcontext中の全queryが過去keyへattentionするため、系列長 `L` に対しattention計算・memory trafficが `O(L²)` で増える。長文脈modelではFFNやMoE部分を高速化しても、prefill attentionがwall-clockを支配し得る。

疎注意は有効だが、動的手法には探索overheadがある。全scoreを計算してからtop-kをsortすれば既にdense attentionに近い仕事をしてしまう。top-pのためにscoreをsortし累積和を取ればさらに重い。固定block patternなら探索不要だが、実際のattentionはsink、local diagonal、vertical retrieval、散在blockなどがhead・layer・inputごとに変わるため、固定patternでは品質かsparsityを犠牲にしやすい。

FlashPrefillの設計目標は、**pattern discoveryそのものをdense attentionより十分安くすること**、かつ4Kのような比較的短いcontextでも探索費を償却できることである。

## 手法
### 1. block単位のproxy score
key sequenceをblockへ分け、各key blockを平均poolingして代表vectorを作る。query側も全queryを使うのではなく、sequence全体へ均等に配置したquery probeを使う。各probeとpooled key blockのdot productからblock重要度のproxyを得る。

単純なmean keyに対する指数scoreは、block内の各key scoreの指数和に対する幾何平均に対応し、block内分散が極端でない限り重要blockのrankを概ね保持できる、というのが近似の根拠である。これによりtoken-token全組合せを計算せず、attentionの大域構造を粗いblock resolutionで観測する。

### 2. 瞬時pattern discovery
長文脈attentionには、同じkey列が多数queryから参照されるvertical pattern、causal diagonalに沿うslash/local pattern、離れた局所領域に集中するblock patternが混在する。FlashPrefillはこれらを別々のdetectorで探索するのでなく、均等query probe × pooled-key scoreを共通の観測として使い、重要block coordinateをまとめて抽出する。

ただし、全query blockと全key blockのproxy matrixをglobal memoryへ書けば `O(L²/B)` の中間tensorが生じ、探索自身がmemory bottleneckになる。そこで実装は2次元のfused reductionを使う。query tileとkey blockのscoreをSRAM上で計算し、query軸でmax reduction、指数変換、sum reductionを同一kernel内に融合する。global maxを使って数値scaleを合わせながら、必要なblock-level scalarだけを出力する。巨大なscore matrixをDRAMへmaterializeしないことが短文脈でも速い理由の一つである。

### 3. 最大値ベース動的閾値
各query block `I` についてblock proxy score `S_{I,J}` を得た後、
`threshold_I = α · max_J S_{I,J}`
を計算し、閾値未満のkey blockを落とす。top-kなら何個残すかを先に決める必要があり、top-pならsortとcumulative sumが必要だが、max-based thresholdは最大値reduceと比較だけで済む。

強いattention peakが少数しかないqueryでは残存blockが少なくなり、scoreが広く分散したqueryでは多く残る。このため実際のsparsityはquery/layer/inputごとに変動する。係数 `α` は速度と忠実度の主要hyperparameterで、高くするとより aggressiveに削れるが重要な中程度scoreも落としやすい。

### 4. index-driven sparse attention kernel
pattern discoveryで得たblock indexを、後段のTriton sparse attention kernelへ直接渡す。論理的には全key blockをloopしてmaskでskipする実装も可能だが、それではindex計算とbranchを全block分払う。FlashPrefillはselected block coordinateへ物理的にjumpし、保持blockだけQK^T、softmax、PVを計算する。

したがって総時間は「pattern discovery + threshold + sparse attention」で決まり、contextが長くsparsityが高いほどdense `O(L²)` との差が拡大する。主対象はprompt prefillで、decode時の1-query対long-KV attentionを同じ方法で高速化するものではない。

## 評価条件
operator benchmarkの中心modelはQwen3-30B-A3B-Instruct-2507で、context length 4K〜256Kをsweepする。比較はFlashAttention dense、FlexAttention系、XAttention、FlashMoBA等の長文脈疎attention。PyTorch 2.9/Triton系environmentで実装し、同一GPU上でattention kernel latencyを測る。

品質はNeedle-in-a-Haystack、RULER、InfiniteBenchを使い、Llama-3.1系、Qwen2.5系、Qwen3系でfull attentionとの精度差を調べる。さらにvLLMへ統合し、attention kernel単体ではなくrequestのTTFTがどこまで短縮されるかを測る。

## 主要結果
### operator速度
Qwen3-30B-A3B-Instruct-2507ではFlashAttentionに対し、4K 1.71倍、8K 2.79倍、16K 4.48倍、32K 6.94倍、64K 11.45倍、128K 18.67倍、256K 27.78倍とcontext長にほぼ単調にspeedupが伸びる。4Kでも1を超える点が、pattern discovery固定費を抑えた設計の主張に対応する。

代表的なabsolute latencyでも、32Kでdense約97.2msに対しFlashPrefill約14.0ms、256Kでは約6044.1msに対し約217.6ms。長文脈ではdense attentionの二次増大をsparse block数へ置き換えた効果が支配的になる。

固定sparsityでsparse kernel自体を比較すると、60%残存条件で4Kは既存1.27ms対0.72ms、512Kは14990.36ms対11256.11ms。6%残存では4K 0.43ms対0.14ms、512K 1513.66ms対1109.44msで、pattern discoveryだけでなくindex-driven kernel側にも利得がある。

### end-to-end
vLLMへ統合したTTFTでは最大7.22倍を報告する。operatorの27.78倍より低いのは、実serviceではembedding、MoE/FFN、normalization、runtime scheduling等の非attention costが残るためである。したがってheadlineの27.78倍を「LLM全体のprefillが27.78倍」と読むのは誤りである。

### 品質
Needle-in-a-Haystackではfull attentionとほぼ同じretrieval挙動を示す。RULER平均ではLlama-3.1系でfull 89.12に対しFlashPrefill 90.15と同等圏で、128Kも74.25対75.31。単純な固定block pruningと比べ、input-adaptive discoveryが重要情報を残せていることを示す。

ただしInfiniteBenchは完全無損失ではない。Llama-3.1系の平均はfull 48.39に対しFlashPrefill 46.32、Qwen3系は37.83対36.23へ下がる一方、Qwen2.5系は23.87対24.93と上がる。dataset/model依存の揺れがあり、「全taskでlossless」とは言えない。

## 既存研究との差
固定windowや固定block-sparse方式はpattern探索が不要だが、input-dependentなlong-range retrievalを捨てやすい。XAttention等のdynamic sparse attentionは重要blockを探せるが、score aggregation・sorting・selectionのoverheadが短〜中contextで大きい。FlashPrefillはpooled block proxy、fused 2D reduction、max thresholdを一つの高速pipelineへまとめ、探索costを削ること自体を主貢献にする。

top-k方式とも異なり、各queryへ固定block数を割り当てずscore分布に応じてsparsityが変わる。そのため「簡単なqueryは強く削り、必要なqueryは広く残す」というadaptive budget allocationになる。

## 限界
FlashPrefillは近似sparse attentionであり、削除したblockの寄与は復元されない。InfiniteBenchの一部modelで平均scoreが下がるように、attentionが広く分散するtaskや、中程度のscoreを持つ多数のkeyが協調して効くtaskではquality lossが生じ得る。

閾値係数 `α` は速度・sparsity・品質のtrade-offを決めるため、model/head/taskのattention sharpnessが変われば最適値も変わり得る。4Kでも高速とはいえ、dense kernelが非常に小さいbatch/shapeや異なるGPUで同じ倍率になる保証はない。

また主対象はprefillであり、自己回帰decodeのKV cache bandwidthを27.78倍削減する方式ではない。vLLM end-to-end最大7.22倍が示す通り、system全体ではattention以外のcostが残る。Triton sparse kernel・hardware architectureへの依存もあり、他backendで同じabsolute performanceが得られるとは限らない。
