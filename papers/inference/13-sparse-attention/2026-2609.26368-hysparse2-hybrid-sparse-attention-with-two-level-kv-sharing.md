# HySparse2：二段階KV共有で長文脈エージェント推論を省計算化する混合疎注意

## 概要

エージェント型LLMでは、モデルが短いツール呼び出しを生成した後に、検索結果、実行ログ、文書などの長い観測が返る。対話を重ねると新規入力のprefillが繰り返され、履歴全体を保持するKVキャッシュも増える。この負荷は、長い入力を一度だけ読んで長い回答を生成する通常のチャットとは異なる。必要なのは単なる注意計算の削減だけでなく、長いツール観測を再処理する層数の削減、層間KV重複の解消、遠い過去の根拠を拾う精度の維持である。

HySparse2は、先行HySparseの「全注意層が後続の疎注意層へKVと選択索引を供給する」設計を拡張し、YOCO型のself-decoderとcross-decoderの間にもKVを橋渡しする。さらに疎注意の選択粒度を64トークン単位のブロックから個々のトークンへ細分化し、直近128トークンを必ず選択に入れる。これによりcross-decoderの局所注意専用の独立した状態を持たずに済み、prefill時にはself-decoder側だけを走らせて必要なKVを生成できる。これはモデル全体の演算をゼロにするのではなく、**入力トークンのKVを作るためにcross-decoderを逐次実行する依存関係を断つ**ことが要点である。

80B-A3B MoEを同一データ量で学習した比較では、長文脈検索の改善と、1Mトークンでのprefill FLOPs・KV容量の削減が示される。一方、モデルの構造がGQAからMQAへ変わり、各注意方式のヘッド次元も異なるため、結果を「同一モデルへ後付けした純粋なカーネル最適化」と解釈してはならない。論文は学習済みアーキテクチャの比較であり、FLOPs削減をそのまま実機速度倍率と呼ぶこともできない。

## 問題設定と比較対象

元のHySparseは、全注意（FA）層が正確な注意スコアで候補を選び、そのKVと選択結果を後続の疎注意（SA）層が再利用する。補助索引器の別途学習を避けられる一方、prefillでは全層を通す必要があり、疎注意側の64トークンブロック選択は、エージェントの長い履歴から散在する少数の根拠を拾う際に予算を浪費する。また、疎注意層の局所文脈を別のSWA分岐で計算すると、cross-decoder側に専用KVを作る依存が残る。

比較対象のHybrid SWAは、全注意層と滑動窓注意（SWA）層を混ぜる方式で、局所窓の計算は軽いが、窓外の履歴から重要情報を抽出する仕組みが弱い。YOCOは一度作ったKVを後段で共有するself-decoder/cross-decoder構造を示した先行例である。HySparse2はYOCOの二段構造を採用しつつ、cross-decoderの全注意層にだけ外側のKV Bridgingを置き、内側ではHySparse由来のKV Reuseを維持する。異なる役割の二種類の共有を組み合わせた点が特徴である。

論文の主な評価対象は、総パラメータ80B・各トークンの活性パラメータ約3BのMoEである。3方式は49層、隠れ次元2,048、学習データとスケジュールを揃えている。ただし注意構成は同一ではない。Hybrid SWAは全注意層9・Q/KVヘッド64/4、HySparseは全注意層5・64/4、HySparse2は全注意層5・64/1で、HySparse2はMQAを用いる。ヘッド次元も前二者がQK/V=192/128、HySparse2が256/256となる。したがって精度差は二段共有だけでなく、学習された注意設計全体の差として評価する必要がある。

## 手法

### 1. Full-Attention-Only KV Bridging：外側の共有

モデルをself-decoderとcross-decoderに分割する。self-decoderは全注意とSWAの混合で、cross-decoderは全注意と疎注意の混合である。対応するself側全注意層の入力隠れ状態を、cross側全注意層のK/V投影の入力として再利用する。cross側のクエリQは、そのcross層自身の隠れ状態から投影するため、cross側が生成中に自分の状態に応じて問い合わせる能力は残る。

式で書けば、self側の全注意層iの入力をH_self,i、対応するcross側全注意層jの入力をH_cross,jとすると、K_cross,j = ProjK_j(H_self,i)、V_cross,j = ProjV_j(H_self,i)、Q_cross,j = ProjQ_j(H_cross,j)である。K/Vの投影行列はcross層ごとに別であり、全cross層が同じKV値を丸ごと使うわけではない。共有されるのはK/Vを生成するためのself側隠れ状態である。self側の一つの全注意層が複数のcross側全注意層へ供給する配置も可能で、両半分の全注意層比率を一致させる必要はない。

prefill時にはself-decoderを通して必要な隠れ状態を生成し、cross側のK/V投影だけを実施すれば、後でdecodeするためのcross側全注意KVを構築できる。cross-decoder本体の各層を新しい入力トークンについて実行する必要がない。decodeではcross側のQと共有済みKVを使って通常の注意を行う。prefill–decode分離構成ではprefillノードにself側と投影器だけを置けるため、論文の49層構成では先頭25層を配備するという設計になる。ただしK/Vの投影計算、KVの転送、decodeノードでの残りの層の実行は消えない。

### 2. KV Reuse：ブロック内の共有と索引の供給

各hybrid block内では、全注意層が全履歴に対する正確な注意スコアを計算し、後続疎注意層が読むトークン位置を選ぶ。疎注意層はその全注意層のKVキャッシュと選択索引を再利用し、独自の全履歴KVを保持しない。全注意層を「索引器」としても使うため、別の学習済み索引モデルや補助蒸留損失を導入する必要がない。これは索引を全く計算しないという意味ではなく、少数の全注意層の高価な演算を検索索引の品質にも利用する設計である。

HySparse2は従来の64トークン単位ブロック選択をトークン単位top-k選択へ置き換える。例えば長いツールログの途中に散在する複数の重要トークンを拾うとき、ブロック選択では重要トークン一つのために周辺63トークンも読み込む。トークン単位なら1,024個のグローバル選択予算をより直接的に根拠位置へ配分できる。論文の構成では1,024グローバルトークンに加え、直近128トークンを必ず選択する。

### 3. 局所SWA分岐の撤去と直近窓の強制包含

従来HySparseは疎注意のグローバル選択に加え、独立した128トークンSWA分岐をゲート融合していた。しかしcross側の独立SWAは、cross側の隠れ状態から局所KVを作る必要がある。後段のSWAに必要な状態を得るには前段のcross層を一部再実行し、その必要区間が層を遡るほど伸びる。単純に直近128トークンだけをcross側で計算すれば済むとは限らず、prefillをself側で完全に早期終了する妨げとなる。

HySparse2では別SWA分岐を除去し、疎注意の選択集合へ直近128トークンを強制追加する。局所と大域の両方を全注意層から共有された同一KVで読むので、cross側の局所KV生成依存が消える。これは精度上の無償な置換ではない。局所注意の独立パラメータと融合の表現力を失うため、後述のablationでは算数・複数ラウンド検索で悪化が確認される。論文はこの不利を受け入れ、prefillの層数とキャッシュ量を削減する設計を選んでいる。

### 4. 学習・推論の実装上の位置づけ

self側SWAには部分RoPE（回転次元64、基数10,000）を用い、全注意と疎注意にはNoPEを用いる。疎注意層とSWA層にはsigmoid出力ゲートと学習可能なattention-sink biasを持たせる。全注意層を少数残す理由は、グローバル情報を拾う索引器としてだけでなく、モデルの品質維持にも役立つためである。将来、全注意層を軽量索引器に置換する案は示されるが、論文で実証済みの成果ではない。

事前学習ではself/cross境界の隠れ状態を使う単一のMulti-Token Prediction（MTP）層を導入して収束を補助する。post-training後により大きなDFlash型drafterへ置換し、投機的デコードを非同期化する構想はあるが、そのdrafterの学習と非同期検証は将来課題であり、今回の定量的高速化実測ではない。prefill FLOPsを減らしたことと、投機的デコードによる実際のtoken/s改善を同一の成果として数えない。

## 評価条件と主要結果

### 評価環境と比較の公平性

| 項目 | 論文で確認できる条件 |
|---|---|
| 主モデル | 49層・80B-A3B MoE、隠れ次元2,048。全注意層はHybrid SWA 9、HySparse 5、HySparse2 5 |
| 注意構成 | Hybrid SWA/HySparseはGQA 64/4ヘッド、HySparse2はMQA 64/1ヘッド。ヘッド次元も異なる |
| 事前学習 | 約500Bトークン、32k文脈。Muon optimizer、WSD、peak LR 1e-3 |
| 軽い追加学習 | 約100Bトークン、256k文脈へ延長。agenticデータを追加、peak LR 5e-5 |
| 疎注意予算 | HySparse2はグローバル1,024トークン＋直近128トークン。HySparseは64トークンブロック選択と独立128トークンSWA |
| 一般能力評価 | MMLU、BBH、MATH、GSM8K、DROP、HumanEval+、MBPP+等 |
| 長文脈評価 | RULER、NoLiMa、MRCR-v2、RULER-v2、GraphWalks、AgentPPL（内部1,000軌跡）、LongPPL（349例） |
| 資源分析 | 1k～1Mトークンのprefill FLOPsとFP8 KV容量。実機TTFT/TPOTやGPU構成別token/sは主要表で提示なし |

主要な公平性は同じ学習データとスケジュールで各アーキテクチャを一から比較した点にある。ただし、同一の重みへ異なるattention kernelだけを差し替えたablationではない。特にMQA採用はKV容量削減に直接寄与するため、2.69GBと6.72GBの差をすべてKV Bridgingの効果へ帰属させない。

### 事前学習後の能力：長文脈で強く、一般能力では混在

| 指標（高いほど良い、PPLは低いほど良い） | Hybrid SWA | HySparse | HySparse2 |
|---|---:|---:|---:|
| MMLU | 61.48 | 64.48 | 63.92 |
| BBH | 60.14 | 61.93 | **64.29** |
| MMLU-Pro | 36.12 | 35.74 | **37.56** |
| MATH | **36.18** | 36.14 | 34.32 |
| DROP | 60.90 | **63.78** | 58.99 |
| GSM8K | **64.44** | 64.14 | 61.94 |
| HumanEval+ | **35.98** | 34.76 | 34.15 |
| RULER | 88.71 | 84.89 | **90.77** |
| NoLiMa | 30.13 | 40.27 | **49.76** |
| Repo Code PPL（低いほど良い） | 1.1578 | 1.1588 | **1.1570** |

表は原著Table 2からの抜粋であり、追加学習後の表と混同しない。HySparse2はHySparse比でRULERが5.88点、NoLiMaが9.49点高い。NoLiMaは文字列一致だけに頼らない長文脈検索であり、トークン単位の選択が重要箇所を拾う能力と整合する。一方でDROPは63.78から58.99、GSM8Kは64.14から61.94、MATHは36.14から34.32へ低下しており、「全能力が改善」という結論は成り立たない。Repo Code PPLの改善は1.1588から1.1570と小さい。これらの値は、推論速度ではなくモデル品質の指標である。

### 追加学習後の長文脈エージェント性能

約100Bトークンの追加学習後、原著Figure 3ではMRCR-v2、RULER-v2、AgentPPL、LongPPLを長さ別に評価する。HySparse2は比較した長さ範囲で両基準より良好で、HySparse比のMRCR-v2平均は**+11.30ポイント**、RULER-v2平均は**+19.81ポイント**。Hybrid SWA比ではそれぞれ+6.44、+18.65ポイントである。256kでのRULER-v2はHySparse2が58.45、HySparseが32.61、Hybrid SWAが35.74で、差が長文脈端で縮まっていないことを示す。

AgentPPLとLongPPLもHySparse2が比較対象より低いが、両指標の長さ依存性は逆である。AgentPPLは対話履歴が長いほど難しくなり、LongPPLは長い履歴に必要情報が含まれるほど対象トークンの予測が容易になる場合がある。したがって「文脈が長いほどPPLは必ず悪化する」と一般化できない。AgentPPLは著者らの内部1,000軌跡、LongPPLは349例であり、公開ベンチマークだけで独立に再現された数字ではない。

### Prefill演算量・KV容量：理論分析と実機性能の区別

| 1Mトークン、80B-A3B、FP8 KV | Hybrid SWA | HySparse | HySparse2 |
|---|---:|---:|---:|
| KVキャッシュ容量 | 12.09GB | 6.72GB | **2.69GB** |
| HySparse2比のprefill FLOPs | 5.02倍 | 2.92倍 | 1.00倍 |

原著Figure 4の資源分析による。HySparse2のKV容量はHySparse比約40.0%、Hybrid SWA比約22.2%に相当する。FLOPsはHySparse比で2.92分の1、Hybrid SWA比で5.02分の1だが、これは理論的演算量の比較であり、GPUでprefillが2.92倍または5.02倍高速になることを実測した値ではない。カーネル効率、通信、KV投影・転送、バッチサイズ、ネットワーク帯域、prefill/decodeの分離方式が実時間へ影響する。

論文の49層構成ではprefillノードがself側25層と投影器だけを保持すればよいという設計上の利点がある。ただし全パラメータ80BのモデルをGPUにどう分散したか、PCIe/NVLink帯域、GPU枚数、実TTFT・P99、実行時ピークメモリなどを同じ条件で測った表は示されない。配備設計の有望さと実運用上の確証は分けて評価すべきである。

| token vs block | GraphWalks | 34.92 vs 29.38 | +5.54点（論文本文は丸めにより5.55点と記載） |
| token vs block | BBH | 60.70 vs 61.93 | トークン単位の方が1.23点低い |
| Forced SWA vs Gated SWA | RULER-v2 | 55.98 vs 53.66 | 強制局所窓が+2.32点 |
| Forced SWA vs Gated SWA | GSM8K | 59.44 vs 64.52 | 強制局所窓が5.08点低い |
| Forced SWA vs Gated SWA | MRCR-v2 | 22.67 vs 27.66 | 強制局所窓が4.99点低い |
| Bridging有無 | 290B-A8B、1.8T事前学習、RULER | 96.01 vs 96.32 | Bridgingありで0.31点低い |
| Bridging有無 | 290B-A8B、DROP | 68.17 vs 71.37 | Bridgingありで3.20点低い |
| Bridging有無 | 290B-A8B、LongPPL | 3.4202 vs 3.6053 | Bridgingありで低下（改善） |
| Bridging vs KV Mirror | 80B-A3B、事前学習後RULER | 87.65 vs 81.28 | 全注意層だけを橋渡しする構成が優位 |

Ablationの条件は主表と異なる場合がある。token/block比較はグローバル1,024と別の128局所窓を揃えた条件で、局所窓の除去効果と混ぜない。局所窓比較はGated SWA、No SWA、Forced SWAの3条件であり、No SWAではRULER-v2 54.62、MRCR-v2 20.73、LongPPL 7.1307となる。Forced SWAは別SWAを消す利点がある一方、算数やMRCR-v2でGated SWAに劣る。これが設計の明確な負の結果である。

さらに290B-A8BのKV Bridging有無比較は、約1.8Tトークンで別途学習した大きなモデルを使う。MMLUは72.68から72.80、TriviaQAは73.32から74.10へ改善する一方、BBHは70.65から69.57、GSM8Kは77.63から76.65、DROPは71.37から68.17へ低下する。RULERは96.32対96.01でほぼ同程度、LongPPLは3.6053対3.4202で改善する。これを「完全に品質劣化なし」と呼ばず、タスク別のトレードオフとして扱う。

## 既存研究との差

YOCOはself-decoderが一度構築したKVをcross-decoderで共有するが、HySparse2は全注意層だけを橋渡し対象とし、疎注意層はその全注意KVを再利用する二段構造へ拡張する。単純に全層のKVを共有するのではなく、どの層の隠れ状態を投影してどのKVを作るかを制限することが重要である。KV Mirrorのように初期層と末尾層を逆順に結ぶ方式よりRULERが高かった理由として、著者らは全注意層の隠れ状態が全履歴からの勾配を受けており、局所SWA層よりグローバル情報を保持しやすいと推測する。これは論文の説明仮説であって、別の表現解析で因果的に証明された事実ではない。

HySparseとの違いは、prefillの早期終了と、トークン単位の根拠検索である。HySparseはブロック選択でも事前学習の通常ベンチマークで十分だったが、長い複数ターンの検索では選択粒度がボトルネックとなる。HySparse2は局所窓を疎注意の選択集合へ統合してcross側の別KV依存を断ち、二段階共有の効用をprefill全体へ拡張した。GQAをMQAへ変える点も容量に寄与するが、これは精度とカーネル実装の両方へ影響する設計変更である。

KVキャッシュ量子化（KIVIなど）は値の精度を減らす別軸の圧縮であり、HySparse2の主要な貢献は精度ではなく層・トークン・ヘッドの構造的共有にある。精度量子化との併用は概念的には可能だが、併用実装の速度・品質は今回の原著で実証されていない。投機的デコードも将来構想であり、prefillのFLOPs低減と別に測る必要がある。

## 限界と実運用上の判断

最大の限界は、主張の中核にある「prefill演算量削減」がFLOPsと理論KV容量で示され、同じモデル・GPU・要求トレースでのTTFT、TPOT、トークン毎秒、P99遅延、電力、ネットワーク転送を測るエンドツーエンドのサービング評価ではないことである。prefill–decode分離時にKVを投影・転送する費用や、短い入力での固定費が利得をどの程度削るかは定量的に未確認である。モデルの実配備や通信負荷がボトルネックになる条件で、理論的なFLOPs倍率がそのまま実時間倍率になる保証はない。

一般能力の一部は悪化する。HySparse2の事前学習後DROP、GSM8K、MATH、HumanEval+はHySparseより低く、強制局所窓のablationではGSM8KとMRCR-v2がGated SWAより明確に悪化する。290B-A8BのKV Bridging比較でもDROPは3.20点低い。これらを長文脈の利得で相殺できるかは用途次第であり、コード生成や算数が重要なサービスへ無条件で適用すべきではない。

学習は500Bトークン＋追加100Bトークンの80B-A3B MoEが中心で、全注意層を少数残す構成、MQA、特定の局所窓・top-k、学習時のRoPE/NoPE設計に依存する。既存の任意の学習済みモデルにプラグインとして差し込めることは示されていない。長文脈のAgentPPLは内部データを使い、256kまでの品質評価と1Mでの資源分析は別条件である。1Mでの精度が256kの水準を保つと断言してはならない。モデル重み・実装コードの公式公開先も一次資料から確認できず、第三者による完全再現性には制約がある。

実装判断としては、長いツール観測のprefill頻度が高く、複数ターンで離れた根拠を正確に拾うことを重視する新規MoE設計の参考になる。特に層間KV共有、トークン単位選択、局所窓の強制包含の3点を独立に評価する価値がある。一方、既存モデルの実行速度をすぐ改善する手法として導入するには、同じ学習済みモデルでの比較、GPU上の実測TTFT/TPOT、KV転送量、長さ別の精度・メモリ、SWA削除による一般能力悪化を別途確認する必要がある。
