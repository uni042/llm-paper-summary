# From Logical to Computational Sparsity: Structure-Aware Block-Sparse Attention for Long Code Completion

## 一文解説

SabreCoderはプログラムの構文単位と依存・類似関係から注意対象を選び、Tritonのブロック疎カーネルで不要な行列演算を実際に飛ばすことで、長文コード補完の初回トークン遅延を低減する。

## 概要

長いコードを補完する言語モデルでは、入力コードを一度に処理する事前計算（prefill）の注意演算が入力長の二乗に応じて増える。コード特有の関数・識別子・import文を考慮しない疎注意は重要な依存を失って補完精度が落ちやすい。一方、コード構造を利用する既存のLongCoderやSparseCoderは論理的には参照位置を減らせても、GPUが効率よく飛ばせる連続した計算ブロックへ整列しないため、実測の初回トークン時間が密注意より悪化する場合がある。

SabreCoderは、まず構文解析器tree-sitterでコードを関数・クラス・import文などのチャンクに分割し、構文木から参照関係を抽出する。次に同一チャンク内、明示的依存、埋め込み類似、グローバル参照という四つの規則を合成して注意マスクを作る。最後にトークン単位のマスクをGPUのタイル単位へ丸め、Tritonで不要タイルの読み込みと行列積を省く。単一ファイルだけでなく、検索拡張生成（RAG）によって取り込んだ別ファイルのコード断片を独立チャンクとして扱う。

著者らはNVIDIA RTX 3090（24GB）、半精度（FP16）でDeepSeek-Coder-1.3Bを主対象に評価した。LCCのPythonでは密注意の初回トークン時間1,686.72 msを931.19 msへ短縮し、完全一致率は36.43%で一致した。CrossCodeEvalのPythonでは1,788.46 msから804.21 msへ短縮し、完全一致率は17.00%から17.25%となった。ただし構文解析等の前処理に200 ms程度を要し、モデル規模の実測は最大3Bである。ここでの高速化はコード補完・対象GPU・実験条件に対する結果であり、任意の一般会話や7B超のモデルへ直ちに外挿できない。

## 問題設定と既存方式の限界

通常の因果注意では、位置ごとに過去のトークンへ注意重みを計算する。長いソースコードを読み込む際、クエリとキーの行列積が増えるため、補完候補を一文字も表示する前の待ち時間が長くなる。単に直近数千トークンだけを残す窓方式は、ファイル冒頭のimport宣言や遠くに定義された関数を参照できない。これは自然言語の近傍依存と異なり、ソースコードの呼び出し・継承・識別子参照が離れた位置を結び付けるためである。

LongCoderは局所窓・グローバルトークン・橋渡しトークンを使い、SparseCoderは識別子に基づく疎性を導入する。しかし、トークン位置が散在するマスクを実装するだけでは、GPUの行列演算器がまとまった行列タイルを処理することを避けられない。演算後に不要要素をマスクするだけなら、理論上の非零要素数が減っても演算は残る。加えてコード解析の費用が乗るため、実測ではLongCoderがLCC Pythonで1,841.45 msと、密注意Tritonの1,686.72 msより遅い。

SabreCoderが狙うのは、コードの意味を保存するための「論理的疎性」と、GPUが実際にスキップできる「計算的疎性」を一致させることだ。実装では、マスクが粗いブロックへ丸められるほど重要でない要素まで計算するため、精度・疎性・メモリアクセスの三者に交換条件が生じる。

## 手法

### 1. 構文チャンク化と依存グラフ

入力は長さnのコードトークン列Xである。単一ファイル補完ではtree-sitterによる抽象構文木（AST）から、関数定義、クラス定義、import文などを連続トークン範囲として切り出し、チャンク集合C={c1,...,cm}を得る。単なる固定長分割と違い、同じ関数の本体が同じチャンクに入るため、局所注意を残すことが意味的に自然になる。

各チャンクを頂点とする有向依存グラフG=(V,E)を作る。関数呼び出し、クラス継承、変数参照、importの関係を構文木から抽出し、ciがcjに依存すれば辺(ci,cj)を立てる。出力は「どのチャンクがどの定義を必要とするか」という疎な接続関係であり、次段の注意マスクの一部になる。ただし構文解析は無料ではなく、コード変更時の再解析や、構文解析器が対応しない言語への拡張が課題となる。

リポジトリ横断補完では、BM25検索で得た関連コード断片をそれぞれ独立したチャンクとする。検索断片はすでに意味的にまとまっていると仮定し、内部を細分化しない。入力の直前コードだけは通常どおり構文分割するため、チャンク集合は検索断片k個と直前コード由来m'個の合計m=k+m'個となる。検索断片内のまとまりを壊すと、後述の構成要素除去実験で完全一致率が大きく低下する。

### 2. 四種類の注意マスクの合成

第一のチャンク内注意（intra-chunk attention）は、同じ関数・クラス等に属するトークン対を許可する。論文ではMintra[i,j]=1を同一チャンクのときに設定する。これは関数本体内の局所的な変数利用や文脈を保つが、これだけでは別関数への呼び出しを追えない。

第二の明示依存注意（dependency-based attention）は、依存グラフの辺(cp,cq)に沿って、cp内のトークンからcq内のトークンへの参照を許可する。これにより離れた場所の関数定義や親クラスを選択的に読める。ただし静的解析で表現されない意味的関連や、検索断片と直前コードの曖昧な対応は捕捉しきれない。

第三の類似注意（similarity-based attention）は、チャンクごとにモデルのトークン埋め込みを平均してeiを作り、チャンク間の余弦類似度を計算する。各チャンクから上位α%の類似チャンクへ注意を許可する。埋め込みはモデルの既存埋め込み表から直接取り出し、追加のモデル順伝播を必要としない。明示的な呼び出し辺がない別ファイルの検索断片と現在のコードを結ぶのが主な役割である。一方、チャンク間類似度の計算・上位選択は前処理費用になり、関連の弱い断片を誤選択すれば注意対象が不足する。

第四のグローバル注意（global attention）はimport文や関数シグネチャなどを特別トークン集合Sに入れ、全位置との相互参照を許可する。関数全体をグローバル化するのではなくシグネチャ部分に絞ることで、重要な入口情報を保ちつつ密注意に戻り過ぎることを防ぐ。四つのマスクは和集合Mchunk=Mintra∪Mdep∪Msim∪Mglobalとして統合し、実行時にモデル固有の因果マスクMmodelとの積集合Meffを取る。これにより未来トークンを参照しないという自己回帰モデルの制約を維持する。

### 3. トークン疎性からブロック疎カーネルへ

チャンク単位の許可位置は不規則なので、そのままGPUへ渡しても効率的な行列積の単位にならない。SabreCoderは注意行列をB×Bのタイルへ分割し、あるタイル内に許可要素が一つでもあれば、そのタイルを活性とする。数式ではMblock[p,q]を対応領域のMchunkの最大値で定義する。この写像は必要なチャンク間関係を落とさない一方、同じタイル内の本来不要な要素も計算対象になる。したがってBを大きくし過ぎると疎性の利点が失われる。

生成したブロックマスクをTritonの専用注意カーネルへ渡し、非活性のキー・値タイルは読み込まず、対応する行列積も実行しない。これは行列積を終えてからトークン単位の値を0にする方式と異なる。FlashAttention型のタイル計算を基礎にしつつ、どのタイルを読み込むかをコード構造に由来するブロックマスクで制御する。論文の主張する計算量は、平均チャンク長L、平均依存数kについて概ねO(knL)で、kL≪nの条件では密注意のO(n²)より小さくなる。ただしこれは構造が十分疎であることを前提とした近似であり、チャンク間接続が密になれば利得は縮む。

### 4. 処理の連結とコスト

一つの要求では、(1)ソースコードと検索断片を受け取り、(2)構文チャンクと依存グラフを作り、(3)埋め込み類似・グローバル規則を合わせ、(4)因果制約を適用してブロックマスクへ写像し、(5)Tritonのブロック疎注意で事前計算を行い、(6)補完トークンを生成する。ここでの主な追加費用は構文解析とマスク作成であり、カーネル側で削減する注意演算と相殺される可能性がある。コードベースが変わらない複数回の補完では依存グラフをキャッシュできるが、論文はキャッシュ再利用の効果を実運用トレースで定量実証していない。

### 構成要素除去：どの設計が効いたか

CrossCodeEval Pythonにおける構成要素除去（Table 3）は、速度だけでなく補完品質を保つ条件を示す。

| 除去した要素 | TTFT (ms) | EM (%) | 完全版との差 |
| --- | ---: | ---: | --- |
| 完全版 | 804.21 | 17.25 | 基準 |
| 類似チャンク接続 | 679.28 | 6.25 | 速いがEMが11.00ポイント低下 |
| グローバル可視性 | 858.60 | 11.75 | EMが5.50ポイント低下 |
| 同一チャンク内注意 | 792.09 | 13.75 | EMが3.50ポイント低下 |
| 明示依存辺 | 812.76 | 15.75 | EMが1.50ポイント低下 |
| ブロック写像 | 1065.55 | 7.75 | TTFTが32.5%増、EMが9.50ポイント低下 |
| 検索断片を独立チャンク扱いしない | 719.80 | 9.50 | EMが7.75ポイント低下 |

類似接続を削除すると計算は減るが、別ファイル間の暗黙の関連を失って完全一致率が大きく崩れる。逆にブロック写像を外すと、論理的にマスクしたトークンがあってもGPUの計算タイルを十分に省けず、速度と精度の両方が悪化する。検索断片を再分割した場合にもEMが17.25%から9.50%へ低下するため、検索結果の意味的まとまりを残す判断が実験で支持される。ただし、各要素除去の速度と品質の相互作用を単純な独立寄与として足し合わせることはできない。

### 系列長・モデル規模・前処理・ブロックサイズ

系列長2k～14kの感度実験では、密注意TritonのTTFTが急増する一方、SabreCoderは緩やかな増加を示した。14kでLCC約45%、CrossCodeEval約55%の速度改善が報告される。ただしこれはモデルのすべての入力長で同じ倍率という意味ではない。LCCデータセットには32kまでの入力例があるが、系列長感度図の実測範囲は14kまでである。

モデルを変えた6k入力予算の比較（Table 4）では、Qwen2.5-Coder-0.5BでLCCのTTFTが151.35→125.23 ms、CrossCodeEvalが193.37→144.25 msとなった。Qwen2.5-Coder-3BではLCCが759.69→613.03 ms、CrossCodeEvalが989.86→726.21 msである。StarCoder2-3BではLCCが768.33→576.93 ms、CrossCodeEvalが1034.45→689.06 msとなった。ここでは0.5B～3Bの異なるモデルで改善を確認したが、7B以上の実測はない。

前処理（Table 5）では、LCCの依存抽出等に216.6 ms、CrossCodeEvalに200.0 msを要し、それぞれ報告された疎注意の事前計算時間940.5 msと791.2 msの23.0%、25.3%に相当する。前処理費用を無視して「モデル呼び出し全体が常に半分」と解釈してはいけない。とくにコードベースの初回要求ではこの費用が顕在化する。依存グラフの再利用・増分解析は将来の運用改善策として論じられるが、表の測定値はその改善がすでに実装された場合の数値ではない。

RTX 3090上のDeepSeek-Coder-1.3B/LCCで、ブロックサイズBを16、32、64、128と変えた比較（Table 6）ではTTFTが順に1338.5、1213.9、940.5、2354.9 msとなり、64×64が最良だった。小さすぎるタイルはアクセス頻度が増え、大きすぎるタイルは少数の許可トークンを含むだけで大きな領域が活性化され、疎性が消える。128×128では64×64の約2.50倍の遅延であり、ブロック化自体が常に改善を保証するわけではない。

## 既存研究との差

Sliding WindowやStreamingLLMは規則的な疎注意で高速だが、関数呼び出し・import・検索断片との意味的なつながりを十分に表現できず、長文コード補完の完全一致率を落とす。LongCoderやSparseCoderはコード構造を取り込むが、トークン単位の不規則な参照がGPUの行列演算タイルと噛み合わず、論理上の削減を実測速度へ転換しにくい。SabreCoderは構文由来の四種類の関係を一度チャンクマスクへ統合し、必要な関係を保持したままブロック疎実行へ落とす点が違う。

また、検索拡張生成を使うリポジトリ横断補完では、検索断片を独立チャンクとして保存し、明示的依存辺では届かない断片を埋め込み類似で接続する。この設計は、単一ファイルの構文木だけに依存する方式より広い入力に対応する。一方、類似度選択とグローバル可視性は追加の前処理・計算を生むため、単純な固定窓方式より最短時間で劣る条件があることも実測から分かる。

## 限界と未評価事項

著者自身が挙げる第一の制約は前処理費用である。依存抽出の200～216.6 msは疎注意事前計算の約23～25%に相当し、初回の単発補完では無視できない。キャッシュによる償却は見込めるが、コード変更頻度・複数利用者の共有・キャッシュ失効を含む実運用評価は本文の主実験では示されない。

第二に構文解析器の対応範囲がPython、Java、C#へ限られる。構文解析が難しい言語、動的に生成されるコード、構文木に現れない実行時依存では、チャンク分割や依存辺の品質が下がる可能性がある。第三に、GPUメモリ24GBの制約から評価モデルは最大3Bで、7B以上や多数同時要求を持つ本番サービングで同等の改善が出るとはまだ実証されていない。

第四にハードウェアのメモリ帯域やキャッシュ階層により最適タイルサイズは変わる。64×64がRTX 3090で最良という結果を、H100や別のアクセラレータへそのまま当てはめられない。さらにブロックの粒度が粗くなると、非零のトークンが一つあるだけでタイル全体が活性化され、計算削減が失われる。最後に、注意演算の削減は初回トークン遅延の改善を意味するが、連続バッチ処理のスループット、復号段階の1トークン当たり遅延、エネルギー、精度を含む幅広い運用条件はこの論文だけでは確定できない。
