# Post-Training Sparse Attention with Double Sparsity

> 重要トークン選択自体を重要チャネルだけで近似し、選ばれた完全KVだけを読む二重疎性で、長文脈デコードのKV帯域とGPU容量を同時に削る。

## 概要

長文脈デコードでは、1トークン生成するたびに過去全トークンのKey/Value（KV）を読み出すため、注意演算は計算量だけでなくメモリ帯域に支配される。既存の動的疎注意は重要トークンだけを計算対象にできても、その重要度を求めるために全Keyを一度読むなら帯域削減が限定される。

Double Sparsityは「重要トークンを選ぶためのスコア計算」まで疎化する。層ごとに注意スコアへ強く寄与する特徴チャネルを事前校正し、そのチャネルだけを抜き出した小さなラベルキャッシュ（label cache）で全トークンを粗く順位付けする。上位トークンが決まった後だけ元の完全K/Vを読み、正確な注意を計算する。1/16のトークン率と1/16のチャネル率を同時に使っても各種品質評価の低下を小さく保ち、A10G/A100で注意演算最大14.1倍、エンドツーエンド最大1.9倍を報告する。

## 問題設定

トークン疎化だけなら、最終的に注意するK/V量は減る。しかし各クエリに対して「どの過去トークンが重要か」を全Keyとの内積で求めると、候補選択段階で結局全KeyをHBMから読む。長い系列ではこの選択用メモリアクセスが疎注意の利得を食い潰す。

一方、クエリとKeyの内積は全特徴次元が同じ強さで寄与するわけではなく、少数チャネルの積がスコアを強く左右する。しかも著者らは重要チャネルの位置が入力ごとに大きく変わらず、オフライン校正で安定して推定できることを観測する。チャネル比が0.25を超えると、オンラインで求めた重要チャネルとの重なりが約0.95に達する。

## 手法のあらまし

各層について校正データから重要チャネル集合 `C` を決める。推論用KVを作るとき、完全Keyに加えて `C` の成分だけを連続配置した `K_label` を保持する。デコード時はクエリも `C` の成分だけ取り出し、`Q_label × K_label` で全トークンの近似スコアを安価に求める。そこから上位kトークンを選び、選択トークンの完全Keyで正確なsoftmaxスコアを再計算し、対応Valueだけを加重和する。

### オフライン重要チャネル校正

注意スコアを特徴次元ごとの積 `Q_i*K_i` の和と見なし、少量の検証データ上で寄与が大きい次元を層別に抽出する。推論時に毎回重要チャネルを探索しないため、選択器自体の計算と不規則アクセスを避けられる。モデル重みは変更せず、学習後に校正だけを追加する。

この校正が外れると近似順位が悪化し、必要なトークンがtop-kから漏れる。したがってチャネル率を下げるほどラベルキャッシュは小さくなる一方、候補順位の精度と下流品質にリスクが出る。

### ラベルキャッシュと二段階注意

重要チャネルを元Keyのストライド位置から都度読むと非連続アクセスになり、GPU帯域を使い切れない。そこで重要チャネル値だけを別の連続バッファへ保存する。クエリ側も同じチャネルを抜き出し、ラベルキャッシュ全体との小次元内積で近似スコアを作る。

近似スコアから `argtopk` でk個のトークン位置を得た後、その位置の完全K/Vだけを読み、通常の注意スコアと出力を計算する。チャネル疎性は「候補探索の帯域」を、トークン疎性は「最終注意の帯域と計算」を削るため、二つの疎性が別の費用へ効く。

### Double Sparsity-Offload

GPU容量をさらに減らす版では完全KVをCPU側へ置き、GPUにはラベルキャッシュと実際に使うKVだけを持つ。隣接層では重要トークン集合が似るという観測を使い、前層の選択結果から次層で必要になりそうなK/Vを非同期にCPU→GPU転送する。

通信と計算が完全に重ならない場合は転送待ちが残る。論文自身も非同期化による通信隠蔽の改善を今後の課題として挙げており、Offload版の利得はPCIe転送をどれだけ先読みで隠せるかに依存する。

## 評価

| 項目 | 代表設定 |
|---|---|
| モデル | Llama-2-7B/70B、Mixtral-8x7B、Vicuna-7B-16K |
| 品質 | WikiText-2 perplexity、KV retrieval、長文脈ベンチマーク |
| GPU | NVIDIA A10G、A100-SXM |
| 実装 | PyTorchで近似選択、Tritonでtop-k注意、gpt-fastへ統合 |
| 精度 | 重み・活性ともFP16 |
| 負荷 | バッチ4〜32、系列長1K〜16K；Offloadは64K〜256K |
| 比較 | PyTorch scaled_dot_product_attention、gpt-fast、FlexGen Offload |

| 条件 | 結果 | 意味 |
|---|---|---|
| 1/16 token + 1/16 channel | 品質低下は小さい | 二段階選択が極端な帯域削減でも重要KVを保持 |
| 注意演算 | 最大14.1倍高速 | ラベルキャッシュとtop-kでKV読み出しを削減 |
| A10G | 全条件5倍以上、半数超で9倍以上 | 帯域律速が強いGPUで効果大 |
| A100 | ほぼ全条件4倍以上、最大約10倍 | 高速GPUでも帯域削減が有効 |
| E2E Llama-2-7B | 全条件1.3倍以上、最大約1.9倍 | 注意以外の層計算が残るためカーネル倍率より小さい |
| Offload、同じ1/16 KV予算 | FlexGen比4〜8倍、64K〜256Kで約16倍 | 全KV転送せず選択KVだけ先読みする効果 |

## 既存研究との差

H2OやScissorhandsは重要トークンを残すが、退去したKVを後から参照できない。QuestやSparQは全KVを保持して動的に候補を選ぶが、候補選択のためのメタデータやKeyアクセスが必要になる。Double Sparsityはトークン選択をチャネル疎性でさらに安くし、全KVを保持する無退去型でも帯域を削る。

Offload版ではFlexGenのように大きなKV集合を毎回移すのではなく、次層で必要と予測したトークンだけを転送する。KV容量削減と注意演算削減を同じ重要度選択機構へ接続した点が特徴である。

## 限界・実装状況

重要チャネルはオフライン校正に依存し、モデルや分布が大きく変われば再校正が必要になる。top-k選択自体は近似なので完全注意と数学的に同一ではない。Offload版はCPU-GPU通信を完全には隠せず、帯域や非同期実装により利得が変わる。エンドツーエンド倍率が注意カーネル倍率より小さいことからも、短文脈や注意以外が支配的な負荷では改善余地が縮む。
