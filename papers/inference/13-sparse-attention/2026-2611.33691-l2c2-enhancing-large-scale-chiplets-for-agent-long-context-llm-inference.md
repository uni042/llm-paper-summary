# L2C2: Enhancing Large-scale Chiplets for Agent Long-Context LLM Inference with Sparse and Distributed Attention

> チップレット上の分散スパース注意を、部分プリフィルのSplit-Comm注意と長さ適応の双モード、デコードのトークン交互割当てと動的キャッシュ分散で最適化するL2C2を提案し、シミュレーションで部分プリフィル1.45倍、デコード1.53倍の高速化を示した。

## 概要

エージェント用途では、多ターンにわたって文脈が積み上がる長文脈推論が要る。計算を減らすには、読むキー・バリュー（KV）を絞るスパース注意が、規模を広げるにはチップレット技術が有望だが、両者を組み合わせると文脈を複数チップへ分ける文脈並列が必要になり、分散したスパース注意という新しい問題が生じる。部分プリフィル、つまり長いキャッシュへ短い新規入力を足す段階では、従来のリング注意が入力を時間ステップへ分けるため、同じKVブロックが複数ステップで繰り返し読まれる。デコードでは、スパース注意が選ぶKVに偏りがあることと、計算量均衡のためのトークン割当てが重なり、特定のチップへメモリアクセスが集中する。

本論文のL2C2は、この2段階へ別々の機構で対処するシステム最適化である。部分プリフィルでは、クエリを選ばれたKVブロックのあるランクへ先に送り、同じブロックを選んだクエリをまとめて計算するSplit-Comm注意を提案し、チップレットの高帯域な相互接続で通信とメモリアクセスを交換する。入力が長い場合は不利になるため、入力長に応じてリング注意と切り替える双モードにする。デコードでは、トークンをランクへ交互に割り当てる静的分散と、熱いKVブロックだけを注意計算の空き時間へ隠して移す動的分散を組み合わせる。代表結果として、シミュレーションで、キャッシュ長512K、入力512トークンの部分プリフィルで1.45倍、デコードで合計1.53倍の高速化を、大規模チップレット構成で達成した。

## 問題設定

長文脈ではKVキャッシュの容量が巨大になり、1チップのメモリへ収まらないため、文脈方向へ分割する文脈並列が要る。頭方向へ分ける並列ではKVが細切れになり、ランダムな読み出しの効率が落ちることが論文の前提分析で示される。一方でスパース注意は、読むKVを絞ることで計算量あたりのメモリアクセスの比重を高めるため、分散実行では通信よりメモリアクセスの重複と偏りが支配的になる。部分プリフィルでは、新規入力の平均長がエージェント用途で429トークン程度と短いのに、数百Kのキャッシュへ注意を向けるため、通信量は小さくメモリ読み出しが重いという非対称がある。リング注意は通信を計算と重ねて隠す設計だが、その代わりにクエリを時間ステップへ分け、同じKVを繰り返し読む。デコードでは、スパース注意の選択が文の先頭と近傍へ集中する山形のパターンを持ち、先頭と末尾を同じランクへ置く従来の割当てでは、最も選ばれやすいKVが1ランクへ集まってしまう。つまり問題は、段階ごとに異なる形で現れるメモリアクセスの無駄であり、通信の最適化だけでは解けない。本論文はこの切り分けに立ち、プリフィルでは重複読みを、デコードでは偏りを、それぞれ対象にする。

## 手法のあらまし

全体は、前段の文脈並列の採用を前提に、部分プリフィルとデコードの2つの最適化からなる。部分プリフィルでは、まず新規入力の長さとキャッシュ長から、クエリ転送とKV転送のどちらが通信量で有利かを見積もる。そのうえで、入力が閾値より短ければSplit-Comm注意を使い、クエリを選ばれたKVのあるランクへ送ってまとめて計算し、部分結果を集約する。長ければ従来のリング注意を使う。デコードでは、プリフィルの段階でトークンをブロック単位にランクへ交互に割り当て、各ランクのKVが選択確率の総量で均等になるようにする。実行中は、アクセス頻度の高いブロックを軽量な集計で追跡し、過負荷なチップレットから低負荷なチップレットへ、注意計算の合間に少量ずつ移して偏りの変化へ追随する。スパース注意の選択そのものは既存の方式を前提とし、本論文はその分散実行の方法だけを変える。

## 手法

### 1. Split-Comm注意 — クエリをKVのある場所へ送って重複読みを消す

この機構が観測するのは、各クエリがスパース注意で選んだKVブロックの集合であり、保持する状態はブロックごとの担当ランクである。処理は通信と計算を分ける。まずクエリを、選んだKVブロックを保持するランクへ送る。最悪の場合は全ランクへの集約通信になる。次に各ランクは、手元のKVブロックを選んだ全クエリについてまとめて注意を計算する。最後にクエリごとの部分結果を集約通信で戻す。効く理由は、同じKVブロックを複数クエリが選ぶ場合に、そのブロックの読み出しが1回で済むことにある。リング注意のように時間ステップごとにクエリが巡回する方式では、同じブロックがステップの数だけ読み直される。追加費用は、通信を計算と重ねて隠せないことであり、通信の遅延がそのまま表に出る。そのため本機構が勝つのは、チップレットの相互接続が高帯域で通信遅延がメモリ読み出しより小さい条件に限られ、通信量自体はリング注意と同程度に保たれる設計である。失敗条件は入力が長い場合で、クエリ側が大きくなるとタイル分割が必要になり、重複読みの削減が消えて通信の分だけ不利になる。

### 2. 長さ適応の双モード — 入力長でリング注意と切り替える

Split-Commの有利不利は入力長とキャッシュ長で決まるため、この機構は両方式の遅延を見積もる式から閾値を決め、入力が閾値未満ならSplit-Comm、以上ならリング注意を選ぶ。見積もりでは、通信遅延、メモリアクセス量と帯域、リング注意で通信と処理が重なる効果を入れる。閾値はモデルとハードウェアが固定ならオフラインの実測で決められ、論文の実験ではチップレット構成で入力4000程度までSplit-Commの有利が保たれる。エージェント用途の平均入力長が数百トークンであることを考えると、実用範囲の大半はSplit-Comm側に入るというのが著者らの読みである。追加費用は方式の二重実装と閾値の事前測定であり、失敗条件は、見積もりの前提と実際の運転条件がずれて、切り替え境界の近くで不利な方式を選び続けることである。短いキャッシュと長い入力の組合せでは、Split-Commが35%の効率低下を示した条件も報告されており、双モードなしでは採用できない方式であることが結果からも分かる。

### 3. インターリーブ型トークン割当て — 選択確率の総量をランク間で均す

デコードの偏りの根本原因は、割当てと選択パターンの重なりにある。スパース注意では各トークンが読むKVブロックの数は位置によらず一定であるため、計算量はトークンの位置で変わらない。したがって計算量均衡のために先頭と末尾を同じランクへ置く必要はなく、割当てを変えてもプリフィルの計算均衡は保てる。この機構は、KVブロックの単位でトークンをランクへ交互に割り当て、各ランクが文全体に分散したKVを持つようにする。その結果、先頭と近傍へ集中する選択パターンでも、各ランクの被選択量が均等に近づく。保持する状態は割当ての規則だけであり、実行時の追加費用はほぼない。効き方の限界も明確で、静的な割当てでは実行中に選択の焦点が移ることへ追随できず、論文の測定でも理想的な均衡と比べて21.8%の改善余地が残る。割当てはブロック長64の単位で行われるため、ブロック内の偏りはこの機構では均せない。

### 4. アジャイルキャッシュバランシング — 熱いブロックだけを隠して移す

静的割当てで残る偏りへは、動的な再配置で対処する。この機構が観測するのは各KVブロックのアクセス頻度であり、ブロック総数よりはるかに少ないエントリ数の表で、頻度の高いブロックを軽量な近似集計で追跡する。過負荷と判定したチップレットは、スパース注意で既に読み出したブロックの中から熱いものを少量だけ選び、低負荷な隣接チップレットへ送る。受け側はオンチップにバッファし、自らの注意計算が早く終わる空き時間にメモリへ書き込むため、移行の遅延は注意計算の背後に隠れる。往復で冷たいブロックを返すことはせず、移す量を最小限にすることで占有量の偏りを無視できる範囲に抑える。毎ステップ少量ずつ移せるため、固定間隔でまとめて移す方式と違い、選択の焦点の変化へ即座に追随できる。失敗条件は、移行量が増えて隠せる時間枠を超える場合と、頻度集計が追いつかない速さで焦点が移る場合であり、相互接続の遅延が大きい構成では隠せる枠が狭くなることが、GPU構成での利得の小ささにも表れている。

## 評価

### まず見るところ

- **結論:** 文脈並列の採用自体が大きな前提であり、そのうえで部分プリフィルとデコードの両方に、条件を限定すれば効く最適化が示される。利得はチップレット構成で最も大きく、GPU構成でも方向は保たれる。
- **速度・効率:** 全てシミュレーションによる遅延とスループットの評価で、実機測定ではない。モデル品質の評価はなく、スパース注意の近似による品質は前提の方式に委ねられる。
- **品質:** 本論文の機構は計算の配置と順序を変えるもので、注意の結果自体は変えない設計である。したがって品質への影響は、スパース注意の選択方式側の問題として切り分けられる。
- **評価の強さ／注意点:** 対象モデルは1種、キャッシュ長は512Kを中心とする設定で、ワークロードはトレースに基づくスパース選択である。実エージェントのトラフィックや複数リクエストの混在は未評価である。

前提の確認から読む必要がある。文脈並列と頭方向並列の比較では、マルチチップ構成で頭方向並列の読み出し遅延が文脈並列の最大7倍に達し、並列度を上げても改善が止まる条件がある。デコードのスループットでも、並列度8で頭方向並列は文脈並列の35.7%しか出ない。つまり本論文の最適化以前に、KVを細切れにしない文脈並列の採用が大きな決定であり、L2C2の各機構はその上での追加利得として読むべきである。

部分プリフィルでは、Split-CommによるKVアクセスの削減が入力256で最大5.49倍と大きく、実用域の入力512ではエンドツーエンドで1.45倍の高速化になる。入力が増えるほど削減は縮み、閾値を超えると通信の分だけ逆転するため、双モードの切り替えが利得の条件になっている。ハードウェア別の違いも明確で、GPUの基本構成では有利な範囲が入力1000程度までと狭く、高速化も入力128で1.33倍にとどまる一方、広帯域の次世代GPU構成ではチップレットに近い範囲まで有利が保たれる。短いキャッシュと長い入力の組合せでは35%の効率低下という明確な悪化条件も報告されており、方式の適用範囲は相互接続の帯域と遅延で決まることが分かる。

デコードでは、インターリーブ割当てでアクセス量の分散が2.775から0.48へ下がり、高速化はチップレットで1.34倍、GPU構成でも1.32倍と、静的対策だけで大きな効果がある。動的分散を加えると、固定間隔の移行方式を全て上回り、並列度8ではさらに17.7%改善して理想的な均衡に近づく。2つを合わせた高速化はチップレットで1.53倍、GPU基本構成で1.32倍、次世代GPU構成で1.36倍であり、動的分散の追加利得は相互接続の遅延が小さい構成ほど大きい。感度として効くのは文脈並列の並列度であり、並列度が上がるほど各チップの保持ブロックが減って偏りの影響が直接出るため、分散の利得は広がる。逆に並列度が小さい条件では、1チップあたりの保持ブロックが多い分だけ偏りが平均化され、静的割当てだけでも不足が目立ちにくい。つまり本方式の機構は、規模を広げるほど必要性が増す種類の最適化であり、小規模構成での再現実験だけで利得を判断すると過小評価になる点にも注意が要る。未評価事項として、実機での検証、複数リクエストやバッチの混在、プリフィルとデコードが同時進行するサービング条件、スパース選択方式を変えた場合の頑健性、閾値のオンライン調整が残る。アブレーションにあたる分解は、静的割当てと動的分散の段階的な追加と比較、固定間隔移行との比較で示されており、各機構の寄与は分離されている。

## 既存研究との差

分散注意の代表であるリング注意は、通信を計算と重ねて隠すことを主眼に、クエリを巡回させる設計である。本論文の差は、スパース注意と長文脈の条件では支配的な費用が通信ではなくメモリアクセスの重複と偏りに移ることを示し、対処の対象をそちらへ変えたことにある。Split-Commは通信を隠すことをあえて捨て、帯域の豊富なチップレット相互接続を使って重複読みと交換する。デコード側でも、計算量均衡のための割当てがスパース注意では不要であることを見抜き、割当ての目的を選択確率の均衡へ置き換えた点が、従来の負荷分散との違いである。文脈並列そのものの有効性を示した先行研究に対しては、その内部の段階別最適化を加えた位置づけになる。

## 限界・実装状況

- ハードウェア依存条件: 利得はチップレットの広帯域・低遅延な相互接続に強く依存し、相互接続が弱い構成では適用範囲と利得が縮む。評価はシミュレーションのみで実機検証がない。
- モデル／ワークロード依存条件: 対象モデルは1種で、スパース注意の選択パターンが異なる方式やモデルでは、偏りの形と分散の効果が変わり得る。エージェント用途の平均入力長という前提に、部分プリフィルの利得は依存する。
- 実装状況: シミュレータ上の評価段階であり、公式コードの公開は本文に示されていない。実サービング基盤への統合や、複数リクエスト環境での挙動は未確認である。
- 近似の品質リスク: 本機構自体は注意の結果を変えないが、前提とするスパース注意の近似品質は本論文の評価範囲外であり、方式全体の品質は選択方式と併せて判断する必要がある。

## 一般的な実装上の含意

分散実行の最適化では、通信量だけでなく、同じデータを何度読むかと、読み出しがどこへ集中かを分けて測ることが重要である。計算を削る近似、ここではスパース注意を入れると、費用の支配項が通信からメモリへ移ることがあり、従来の最適化の前提が崩れる。もう1つは、負荷分散を静的な割当てと動的な再配置の2層に分け、根本原因は割当てで、時間変化は少量の移行で追うという分け方である。移行を隠せる時間枠がある実行形態では、少量を頻繁に移すほうが、まとめて移すより追随性と費用の両方で有利になり得る。
