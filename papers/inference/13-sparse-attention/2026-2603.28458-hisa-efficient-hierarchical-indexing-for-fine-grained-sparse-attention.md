## 概要

HISA（Hierarchical Indexed Sparse Attention）は、DeepSeek-V3.2系のDeepSeek Sparse Attention（DSA）で、疎な注意計算そのものではなく**上位トークンを探すindexer**が長文脈で律速になる問題を対象にする。DSAでは各queryがprefix中の全token keyを軽量indexerで採点し、top-kだけをSparse MLAへ渡すため、注意本体はおおむね `O(Lk)` まで疎化できる。一方、indexerは各queryごとに長さ `L` のprefix全体を走査するので、layer全体では `O(L²)` が残る。128K〜1M token級では、この「疎化対象を探す計算」が無視できなくなる。

HISAはこの検索経路だけを、block粗選別→token精査の二段階へ置換する。最終出力は従来DSAと同じ「queryごとのtop-k token index」なので、下流のSparse MLA、KV cache形式、学習済みmodel本体を変えずに差し替えられる。狙いはblock-sparse attentionへ変更することではなく、blockを**検索用の粗いindex**としてだけ使い、最終的な注意対象はtoken粒度のまま維持することにある。

## 問題設定

DSAのindexerは、各query headのindexing queryと各過去tokenのindexing keyの内積を計算し、headごとのgateを掛けてReLU後に集約したscoreからtop-k tokenを選ぶ。この方式はquery依存の細粒度選択ができる反面、候補が常にprefix全体なので、context lengthが伸びるほどindexerの演算量とHBMアクセス量が増える。

単純なblock-sparse方式なら候補数を大幅に減らせるが、選んだblock内の全tokenを残すため、同じtoken budgetでも重要度の低いtokenへ計算を使う。また、重要tokenが複数blockへ散らばるとblock単位の選別誤差が品質へ直結する。HISAは「粗いblock検索で大半を落とすが、最後は元indexerでtoken単位に再ランキングする」という二段構成で、この速度と選択精度の交換条件を緩和する。

## 手法

### 1. block代表の構築

prefixを連続するblock size `B` の区間へ分け、各blockのindexing keyを平均poolingして代表keyを作る。代表keyはcoarse search専用であり、元のtoken-level indexing keyやSparse MLAが読むKV stateは変更しない。したがって、HISAを導入してもcheckpointやKV cache layoutを作り直す必要はない。代表keyはKV cacheと同時に増分更新できるため、長文脈でも全blockを毎回再構築する必要はない。

### 2. Stage 1: block-level coarse filtering

query側は元DSAのindexing queryとgateをそのまま使い、個々のtokenではなくblock代表だけをscoreする。全 `M=ceil(L/B)` blockから上位 `m` blockを選び、そのunionをcandidate token集合とする。因果maskを守り、現在queryより未来のblockは候補に入れない。論文実装ではattention sinkを含む先頭blockと局所文脈を含む末尾blockを常に候補へ含め、長文脈で重要になりやすいglobal/local情報をcoarse stageで誤って落としにくくしている。

### 3. Stage 2: token-level refinement

残った最大 `mB` tokenに対して、元DSAと同一のtoken scoreを計算し、そこから最終top-kを選ぶ。最終出力形式がDSAと同一なので、Sparse MLA側は無変更でよい。候補数は `mB >= k` を満たす必要があり、prefixが短く `L <= mB` の場合はcoarse filterが実質的に全blockを通すため、HISAは自然に元DSAへ近づく。

query当たりのindexing costは `O(L)` から `O(L/B + mB)`、layer全体では `O(L²)` から `O(L²/B + LmB)` へ下がる。一方、`m` を減らしすぎると重要blockを粗選別で落とす危険が増え、`B` を大きくしすぎると代表keyがblock内部の細かな重要度差を表しにくくなる。

### 4. GPU kernel

著者らはTileLangでcoarse stageとrefinement stageを別kernelとして実装する。第1段は少数のpooled keyだけを読み、第2段は選ばれたcandidate block内のtokenへだけ元indexer相当の計算を行う。固定candidate budgetを使う場合、第2段の入力長を一定化できるため、context lengthが増えてもrefinement kernelのcostをほぼ一定に保ちやすい。

## 評価条件

速度評価ではNVIDIA A100上で、query length 1024、最終top-k=2048、block size `B=128` を用い、元DSA indexerとHISAをTileLang kernelで比較する。64K contextでは元DSA indexerがSparse MLA本体より大きなcostになっており、indexer単体の高速化を測る。HISAは4:1のcoarse compressionと、8K固定candidate budgetの二設定を評価する。

品質評価ではDeepSeek-V3.2およびGLM-5へ追加学習なしでHISAを差し込み、Needle-in-a-HaystackとLongBenchを使う。LongBenchではDSA、HISA、block-only sparseの最終attention budgetをすべて2048 tokenへ揃える。HISAは64 block×128 token=8192 tokenを第1段で残し、そこから第2段で2048 tokenへ精査する。

## 主要結果

64K contextのindexer kernelでは、4:1のcoarse compressionで元DSAに対して約2.16倍、8K固定candidate budgetでは最大約3.75倍のspeedupを示す。元DSAでは64K時にindexerが約5.6 ms、Sparse MLA本体が約1.6 msであり、長文脈ではindexerが本当に支配的になるという問題設定と整合する。ここでの値は**indexer kernel単体**であり、end-to-end serving throughputの同倍率改善を意味しない。

LongBenchではDeepSeek-V3.2の平均scoreがDSA 51.05、HISA 50.78、block-only 49.54、GLM-5ではDSA 46.01、HISA 46.32、block-only 42.67だった。HISAは元DSAへかなり近い一方、block-only方式より一貫して高く、粗いblock選択の後にtoken-level refinementを残す意味が確認できる。

Needle-in-a-HaystackではHISAが元DSAに近いretrieval heatmapを維持し、block-only方式より中間位置のneedleで安定する。これは、重要情報が含まれるblockをcoarse stageで拾った後、block内部でtoken単位に再選別する構造が効いていることを示す。

## 既存研究との差

MInference、FlexPrefill、NSA、MoBAなどのblock-oriented sparse attentionは、blockを最終attention粒度として使う。HISAではblockは検索空間を縮めるための一時的なindexであり、最終attention対象はDSAと同じtoken-level top-kである。また、IndexCacheのように別layerのindexを再利用する方式とも異なり、同一layer内で検索をcoarse-to-fine化する。

## 限界

HISAはcoarse stageで落としたblock内のtokenを第2段で復活できない。したがって、`m` や `B` を攻めすぎるとselection fidelityと下流品質が落ちる。短contextではprefix全体を走査しても安いため、pooled key管理と二段kernel呼び出しの固定費が相対的に大きく、長contextほどの利得は得にくい。

また、主要速度結果はindexer kernel単体であり、end-to-end latency、throughput、KV cache管理、batchingを含めたserving全体の改善量は別途検証が必要である。評価modelも主にDSA型indexerを持つDeepSeek-V3.2/GLM-5で、他のsparse attention設計へ同じblock poolingがそのまま最適とは限らない。
