# AsyncTLS: Efficient Generative LLM Inference with Asynchronous Two-level Sparse Attention

## 概要

長文脈生成では過去の鍵・値（KV）を毎トークン参照するため、文脈が伸びると注意演算とキャッシュ容量が同時に負担になる。必要な過去トークンだけを読む疎注意（sparse attention）は計算を減らすが、重要トークンを毎回全体から探す索引処理が重い。反対に、連続したトークンをブロック単位で選ぶ方式はGPUの連続アクセスに向く一方、必要のない位置も大量に読み、同じトークン予算で品質を損ないやすい。

AsyncTLSはまずブロック単位で候補を絞り、その内部だけをトークン単位で再選別する二段索引を導入する。さらに、CPU側へ退避したKVキャッシュを生成時に必要な分だけ戻す際、隣接する生成段階の重要ブロック集合が似ていることを利用する。前の段階で選んだブロックから今回の細選択を進める間に、今回の粗選択で次段階のKVを先読みする。Qwen3とGLM-4.7-Flashの長文脈評価では、全注意に近い品質を保ち、注意演算子単体で最大10.0倍、96K文脈でオフロードを含む要求処理率は最大4.70倍の改善を報告した。演算子倍率とシステム倍率は異なる測定である。

## 問題設定

通常の注意では、長さ $n$ の過去KVに対して生成時の問い合わせが全ての鍵を参照する。生成1段階では過去長に比例する参照が必要になり、長い系列全体では注意計算が二次的に増える。過去KV自体も長さに比例して増えるため、GPUの高帯域メモリだけに保持できない場合はCPU主記憶へ退避する必要がある。転送を同期的に待つと、注意計算を削った利益がPCIe待ちへ置き換わる。

Quest型のブロック選択はブロック内の鍵を集約した索引で候補を減らせるが、ブロック内の無関係トークンをそのまま含める。Double-Sparsity型のトークン選択は精密だが、全過去位置を対象に近似スコアを計算して上位を探す費用が大きい。AsyncTLSが解くのは、最終的に少数のトークンしか読まないのに、そのトークンを探すための索引が長文脈全体を走査する矛盾である。さらに、選択したトークンのKVをCPUから戻す通信まで、同じ生成段階の待ち時間に入れないことが必要になる。

## 手法

### 1. 粗いブロック選択と行列積向け索引

過去KVを長さ $B$ のブロックへ分け、各ブロックの鍵ベクトルについて特徴次元ごとの最大値・最小値を保持する。現在の問い合わせベクトルの正成分と負成分をそれぞれ分離し、ブロックの最大・最小値との積を足して重要度を近似する。元のQuest式を正負分離した行列積に書き換えることで、共有KVを使う多頭潜在注意（MLA）でもTensor Coreを利用しやすくする。問い合わせが強く反応しそうな上位 $k_b$ ブロックを選び、その合計 $k_bB$ トークンを次の候補とする。

ブロック最大値・最小値はブロック内の真の最大注意スコアそのものではなく、問い合わせとの関連を素早く見積もるための代理表現である。粗い段階で重要なブロックを落とすと、次の精選択はその内部を見られない。このため、粗選択の上位数とブロック幅は索引費用と取りこぼしの交換条件になる。論文の代表設定ではブロック幅64、上位128ブロックを残し、細選択の探索対象を8,192トークンに制限する。

### 2. トークン単位の細選択

残したブロックの内部ではDouble-Sparsity型の方法を使う。事前の較正用データで、問い合わせと鍵の各特徴次元の最大絶対値を使って重要度を見積もり、重要な特徴次元集合 $\mathcal C$ を選ぶ。問い合わせと鍵をその特徴次元だけへ射影し、鍵側の索引は4ビット整数量子化で小さくする。全次元の内積を各候補へ実行する代わりに、この圧縮索引で近似注意スコアを計算する。

複数の問い合わせ頭が同じ鍵・値を共有するグループ化クエリ注意（GQA）では、グループ内の頭の近似スコアを集約して候補を選ぶ。上位 $k_t$ トークンの位置集合 $\mathcal S_t$ を得た後、最終的な注意演算だけは元の全次元の鍵・値を使って実行する。したがって、近似は「どの位置を読むか」の索引に用い、選ばれた位置の値の演算自体は全次元で行う。索引量子化と最終注意の精度を混同してはいけない。

GQAでは索引用の特徴次元を32、MLAでは128に設定している。MLAは圧縮潜在表現をキャッシュし、共有されたKVを使うため、粗選択の行列積化の利点が大きくなる。一方、重要な特徴次元が較正データと実運用で変わると、近似スコアによる候補選択の誤りが増える。細選択の候補数を小さくするほど演算量は減るが、正答に必要な遠隔トークンを失う危険が高まる。

### 3. 一段遅れの非同期KV先読み

疎注意の計算だけではCPU上のKVをGPUへ戻す転送時間は消えない。AsyncTLSは生成段階 $t$ で、直前の粗選択集合 $\mathcal M_{t-1}$ を使って細選択集合 $\mathcal S_t$ を求め、注意演算を実行する。その計算と同時に、現在の問い合わせから新しい粗選択集合 $\mathcal M_t$ を求め、次段階で必要になりそうなブロックを非同期に先読みする。粗選択が1段階遅れて細選択へ渡る点が、同じ段階内で両方を順番に実行する通常の二段索引と異なる。

この遅延が成立する前提は、隣接段階で重要なブロック集合が大きく変化しないことである。現在の注意計算と後続の全結合層の演算を実行している間に、次段階用のCPU→GPU転送を進められれば、転送時間を生成の待ち経路から隠せる。反対に、参照する文書位置が急に切り替わる生成では、前段階の選択が外れ、必要KVの転送待ちや選択品質の低下が生じ得る。論文はこの時間局所性を設計根拠とするが、全ての文脈で成立する保証はない。

### 4. 差分転送とGPU常駐集合

GPU側に常駐しているブロック集合を $\mathcal C_t$ とすると、今回新たに選んだ $\mathcal M_t$ のうち、$\mathcal C_t$ にないものだけを転送対象 $\mathcal T_t=\mathcal M_t\setminus\mathcal C_t$ とする。毎段階で上位128ブロックを全て送り直すのではなく、選択集合が変化した差分だけを送る。転送量は概ね $k_bBd$ に比例する全量転送から、差分ブロック数 $|\mathcal T_t|Bd$ に比例する量へ下がる。

細選択はGPUへ到着したブロックの中からトークンを絞り、最終注意ではその位置の全次元KVを参照する。粗選択、差分先読み、細選択、最終注意という処理が段階をまたいで流れるため、メモリ配置だけでなく計算と転送の時系列を合わせる必要がある。GPUメモリに全KVを置く方式より容量を節約できるが、GPU常駐集合の管理と索引保持、非同期転送の制御が追加費用になる。

### 5. 計算量と残る費用

生成1段階の主要費用は、全ブロックの粗いスコア計算 $O((n/B)d)$、残したブロック内の細選択 $O(k_bB|\mathcal C|)$、最終注意 $O(k_td)$ に分けられる。全トークンに細索引をかける方式より探索空間を縮められるが、粗い索引は全ブロックを見続けるため費用が完全に一定にはならない。オフロードではさらに差分ブロック転送が加わる。最終的な利得はブロック幅、索引次元、残すトークン数、時間局所性、CPU–GPU帯域に依存する。

## 評価

### 評価条件

一次論文はQwen3-8B、Qwen3-14B、GLM-4.7-Flashで、グループ化クエリ注意と多頭潜在注意の両方を検証する。精度には長文脈理解のLongBench、文脈内検索・複合検索を含むRULERを使用する。速度では全注意、ブロック単位の比較方式、トークン単位の比較方式と比較する。カーネル単体はTileLang実装でバッチ1～8、文脈32K～128Kを変え、システム測定は32K～96Kの長文脈を扱う。

| 項目 | 条件 |
|---|---|
| モデル | Qwen3-8B、Qwen3-14B、GLM-4.7-Flash |
| 粗選択 | 64トークン/ブロック、128ブロック、最大8,192候補トークン |
| 細索引 | GQAは32次元、MLAは128次元、鍵索引はINT4 |
| 細選択トークン予算 | 512、1,024、2,048を比較 |
| 精度評価 | RULER、LongBench、全注意・Quest・トークン細選択方式との比較 |
| 演算子評価 | バッチ1～8、文脈32K～128K、TileLangカーネル |
| システム評価 | Qwen3-8BとGLM-4.7-Flash、32K～96K、オフロード有無を区別 |

### 精度と負の結果

LongBenchの平均値はQwen3-8Bで全注意50.14に対しAsyncTLS49.90、Qwen3-14Bで52.16に対し51.80、GLM-4.7-Flashで50.83に対し50.58である。全注意に近いという総括には、このように具体的な小幅差がある。ブロック方式の平均はそれぞれ47.49、49.33、46.75であり、二段選択が粗いブロック選択より有利な条件を示す。

RULERではQwen3-8Bの平均が全注意90.45、AsyncTLS90.54、ブロック方式38.92である。Qwen3-14Bは全注意86.24、AsyncTLS87.21、ブロック方式37.89となる。ただしGLM-4.7-FlashのRULERでは全注意85.73に対しAsyncTLS81.50で、完全に無損失とはいえない。GLMでは一部タスクを評価設定上の異常のため除外しており、モデル間の平均値を同一条件の単純比較とみなすべきではない。こうした差を残すことで、疎化しても常に品質が等しいという誤読を避ける。

### カーネル・全体性能とオフロード

| 条件 | 比較対象 | 結果 | 意味 |
|---|---|---|---|
| GQAの注意カーネル | 全注意 | 1.7～6.2倍 | 二段索引を含む注意演算子の高速化 |
| GQAの注意カーネル | トークン細選択方式 | 1.2～4.0倍 | 全候補を細索引する費用を削減 |
| MLAの注意カーネル | 全注意 | 3.3～10.0倍 | 共有KV構造で行列積化の利点が大きい |
| MLAの注意カーネル | トークン細選択方式 | 1.9～4.0倍 | 精密選択の索引費用を縮小 |
| オフロードなしのモデル推論 | 全注意 | Qwen3-8Bで2.3倍、GLM-4.7-Flashで2.7倍 | 注意以外の演算も含む全体遅延の比較 |
| 96K・オフロードあり | 全注意 | Qwen3-8Bで1.84倍、GLM-4.7-Flashで4.70倍 | バッチ形成とKV転送を含む処理率の比較 |

オフロードありの処理率比較では、AsyncTLSはバッチ6を扱える一方、全注意はメモリ制約によりバッチ1となる。このため最大4.70倍は「同じバッチで注意カーネルだけが4.70倍速い」という値ではない。GPUへ常駐させるKVを減らしたことによる同時要求数の増加も含む、システム全体の利得である。GPU容量に余裕がある短い文脈や、CPU転送が重い構成で同じ倍率が出るとは限らない。

## 限界と適用範囲

細選択の候補は粗選択で残したブロックに限られるため、粗選択で重要位置を落とすと後段で回復できない。圧縮索引の特徴次元と量子化は較正分布に依存し、選択品質と索引容量の交換条件がある。一段遅れの先読みは重要ブロックの時間局所性を仮定するため、注意先が急に変わる生成では誤予測による待ち時間や品質差が増え得る。

性能は長文脈のQwen3とGLM-4.7-Flash、評価された疎化予算とGPU環境に基づく。極端に短い入力、異なるモデル構造、長時間の多数要求が競合する実サービス、CPU主記憶容量やPCIe帯域が厳しい環境への一般化は論文の表だけでは判断できない。GPU上に残す索引・選択状態の管理費用も存在し、すべてのメモリが減るわけではない。公式の公開実装URLは一次論文の確認範囲では特定できず、既存推論基盤へそのまま組み込めるという主張は避ける。

## 既存研究との差

ブロック選択方式Questはブロックの関連度を素早く見積もるが、ブロック内の不要位置を残す。Double-Sparsityはトークンを精密に選べる一方、長文脈全体を索引する費用が大きい。AsyncTLSは粗選択で候補を削った後に細選択を行うことで、同じトークン予算で精度と索引費用を両立させる。さらにFlexGenやInfiniGenなどの階層メモリ方式と異なり、トークン細選択に必要なブロックを前段階の粗選択から予測し、差分だけを非同期に転送する点が固有の設計である。
