# Janus：エージェントの疎KVをSSDから先読みするサービング基盤

## 概要

Janusは、ツール呼出しを繰り返すエージェントの長い会話履歴をSSDに保持し、疎Attentionで必要なKVだけをGPUへ戻すときのI/O待ちを減らすシステムである。エージェントの各ラウンドでは過去の履歴を再計算せず、新しく追加されたツール結果や指示だけをappend prefillで処理する。疎Attentionは必要な過去KVを選ぶが、その選択結果はモデルの中間計算が進まないと分からない。SSDの読込を選択後に開始するとGPUが待たされ、計算量を削減したはずの疎AttentionでもTTFTが長くなる。

Janusはモデル自身の選択インデクサを、通常より早い層の中間表現へ適用してKV需要を予測する。予測したKVをSSDから非同期に読み、GPUの残りの計算と重ねる。実際のインデクサが後で選んだKVに予測漏れがあれば補正読込するため、推測の誤りをそのままAttention結果の誤りにしない。さらに連続したSSD読込を結合し、散在したGPUページをCPUで連続書込へ整形し、読込中の背景書込を抑える。

原著はDeepSeek-V4-Flash、DeepSeek-V4-Pro、GLM-5.2の三モデルと三種類のエージェントトレースで評価し、isolated append prefillのTTFTがTutti比最大1.57倍・平均1.22倍、LMCache比最大3.69倍・平均1.85倍短縮されたと報告する。これらは特定のSSD、GPU、モデル、履歴長、DRAM制限での実測であり、全環境で同じ倍率になるわけではない。

## 問題設定

エージェントの履歴は長く、新しい入力の長さは履歴に比べて短いことが多い。原著の三トレースでは平均履歴長が77K、119K、125Kトークン、追加入力は1.1K、1.4K、4.8K、生成出力は237、365、357トークンである。各ラウンドの入力をappend prefillするときに過去KVを再利用できれば、履歴全体の再計算を避けられる。GPU HBMは多セッションの履歴を全保持できないため、CPU DRAMやSSDへ退避する必要がある。

密Attentionなら全履歴KVが必要と分かっているので、前もって読込を開始しやすい。しかし疎Attentionは現在のクエリに対してインデクサが上位の過去トークンを選ぶまで、どのKVが必要か確定しない。インデクサの出力を待ってからSSD読込を始めると、そのI/Oが推論のクリティカルパスに乗る。反対に全履歴KVを先読みするとSSD帯域とHBMを浪費する。Janusはこの「正確な選択は遅いが、予測読込は早く始めたい」という矛盾を扱う。

SSD特有の問題もある。疎選択は離れたKVページを読むため、小さいランダムI/Oが多数発生する。PagedAttentionによるGPU上のKVページも書込時には散在しており、そのままSSDへ書くと連続I/Oにならない。さらにSSDで読込と書込が同時に走ると内部資源が競合し、読込帯域が大きく低下する。原著の観測では読込と書込の干渉によって読込帯域が約60%悪化する条件がある。エージェントではラウンドをまたぐ履歴の読込量が書込量より大きいため、読込優先の制御が有効になり得る。

## 手法

### 1. 早い中間表現で同じ選択器を先行実行する

通常の疎Attentionでは、ある層の入力隠れ状態と過去のインデクサキーを使って上位k個のKVを選ぶ。Janusは同じモデルのインデクサを早い中間表現へ適用し、後で必要になる選択集合を予測する。別途学習した予測器を追加するのではなく、既存の選択機構を再利用するためtraining-freeと位置付けられる。ただし予測用のインデクサ実行自体には計算費用がある。

予測したKVのSSD読込を早く開始し、その間にモデルは次の層を計算する。正確な選択集合が確定した時点で、先読み済みのKVを使い、予測から漏れたものだけ補正読込する。余分に先読みしたKVはI/O帯域を消費するが、結果に混ぜてAttentionを変えるわけではない。漏れを補うため出力一致を保てる。性能上は予測の再現率が高く、先読みが計算に十分隠れ、補正読込が少ないほど有利になる。

### 2. GPU間の履歴分割による予測の高速化

早期予測を行っても、予測器の計算が長ければSSD読込開始が遅くなる。Janusは過去履歴のインデクサキーを参加GPUへ分割し、各GPUが担当部分の選択を並列に推定する。局所的な候補を統合して予測集合を作ることで、インデクサの追加実行を主計算のクリティカルパスへ大きく乗せない。モデルによって疎Attention層が密Attentionと交互に配置される場合や、複数層で選択結果を共有する場合があり、先行予測の精度と先読み可能な時間が異なる。全モデルで同じ層間予測精度を仮定してはいない。

### 3. 散在I/Oの結合とCPU側の書込整形

予測したKVの位置が近接していれば、SSDへの複数の小さな読込要求を連続範囲としてまとめる。疎Attentionが選んだ位置を無条件に全履歴へ拡張するのではなく、隣接している範囲をbest-effortで結合し、ランダムI/Oの回数を減らす。書込時にはGPU HBMに散在するKVページをCPU側で連続バッファへ整形し、SSDへ順次書く。GPUのSMを使ったパッキングと異なり、モデル計算と書込整形の資源競合を抑える狙いがある。

読込と書込が同時に発生する際には、背景書込の帯域を制限するphase-aware write cappingを行う。エージェントのappend prefillでは読込がTTFTに直結するため、書込完了を少し遅らせても読込帯域を守る方が全体に有利な条件がある。ただし書込が多いワークロードでは遅延やバックログが生じる可能性があり、常に同じ制限が最適とは限らない。

### 4. GPU主導SSDアクセスと正確性

原著はGPU-initiated NVMe I/Oの仕組みを利用し、GPUからSSDへの要求を直接発行してCPU側の個別I/O起動費用を減らす。GPU HBMとSSD間のDMA、NVMeの送信・完了キュー、非同期の読込完了待ちを用いる。CPUは主にセットアップと書込整形などに関わる。重要なのは、予測は先読みを開始するためだけに使い、Attentionへ渡すKVの正確な集合は本来のインデクサが決めることである。したがって予測漏れは遅延要因になるが、出力を変える必要はない。

## 評価

### 実験条件と比較対象

評価モデルはDeepSeek-V4-Flash、DeepSeek-V4-Pro、GLM-5.2で、原著の記載ではそれぞれ284B、1.6T、753Bパラメータ規模である。モデル重みとKVはFP8、DeepSeek-V4のインデクサキーはFP4とする。トレース1・2はSWE-Bench-ProとTerminal-Benchから生成し、トレース3は産業パートナーの非公開トレースである。比較はGPU主導SSDアクセスのTutti、GPU-CPU-SSD階層管理のLMCache、予測を省いて正確な選択後にKVを読むJanusbaseで行う。すべてvLLMをバックエンドにし、SSD中心の条件を作るためCPU DRAM容量を16GBへ制限する。結果は五回の試行平均である。

| 指標と比較対象 | Janusの改善倍率 | 何を比較したか |
|---|---:|---|
| isolated append prefill TTFT、Tutti比 | 最大1.57倍、平均1.22倍 | SSD中心・GPU主導の全履歴読込方式 |
| isolated append prefill TTFT、LMCache比 | 最大3.69倍、平均1.85倍 | CPU起動I/Oを含む階層管理方式 |
| isolated append prefill TTFT、Janusbase比 | 最大1.71倍、平均1.27倍 | 先読み予測を省いた疎KV読込 |
| サービングP95 TTFT、Tutti比 | 1.05〜1.51倍 | 待ち行列も含むオンライン到着 |
| サービングP95 TTFT、LMCache比 | 1.31〜3.04倍 | 同上 |
| サービングP95 TTFT、Janusbase比 | 1.01〜1.68倍 | 同上 |
| サービングTPOT | 比較方式間の差は概ね3%以内 | デコード自体の高速化が主目的ではない |

### 先読みとI/O最適化の寄与

原著の時間内訳では、先読みなしのJanusbaseではSSD読込がappend prefillのクリティカルパスへ大きく露出する。Janusは先読みした読込をGPU計算へ重ねるため、図12で明示されるKV読込時間は主に予測漏れの補正読込になる。著者はクリティカルパスに残るSSD I/Oをappend prefill時間の6.5%未満へ抑えたと報告する。先読みのためのインデクサ計算もゼロではないが、GPU間の分割で費用を小さくする。

ただし先読みなしでも疎KVだけを読むJanusbaseは、全履歴を読むTuttiより常に速いわけではない。疎KVの選択後に読込を始めると、I/O量は少なくても待ち時間がGPU計算を止めるからである。この負の結果は、SSD中心の疎Attentionで重要なのが単なる読込バイト数ではなく、読込をいつ開始できるかであることを示す。

### サービング時の負の条件

オンライン到着を模した評価では要求到着率0.005のポアソン過程を用い、P95 TTFTとP95 TPOTを測る。isolated要求より速度倍率の幅が狭くなるのは、キュー待ちが追加されるためである。P95 TTFTのJanusbase比は1.01倍まで縮む条件もあり、すべての条件で大幅な改善が得られるわけではない。デコード処理そのものは変更しないため、TPOTの差は概ね3%以内である。TuttiではGPU上のKVパッキングがモデル計算と競合し、一部条件でTPOTが悪化することも報告される。

## 既存研究との差

LMCacheはCPU DRAMを含む階層的なKV管理を提供し、TuttiはSSDを主たる保持先にしてGPU主導I/Oを行う。これらは全履歴KVをまとめて戻す場合があり、疎Attentionが実際に使う部分だけを早く読めるとは限らない。Janusbaseは疎選択後に必要な部分だけ読むが、SSD待ちがクリティカルパスに乗る。Janusはモデル自身の選択器を早く実行する予測、予測漏れの補正、SSDの読込・書込整形を一体化する。近傍のデコードステップの選択類似性を使う既存の先読み研究と異なり、エージェントのappend prefillを主対象にする点が特徴である。

## 限界・負の結果・再現性

先行予測の再現率が低いモデルでは補正読込が増え、性能が低下する。SSDとGPUの間のI/O能力、GPU間の分割方法、インデクサの配置、履歴長と新規入力長の比により先読み可能な時間が変わる。DRAMを16GBに制限したSSD中心の評価は、豊富なDRAMを持つ一般的なサーバと条件が異なる。三トレースのうち一つは非公開であり、完全に同一のワークロードを第三者が再現することは難しい。

性能の主要指標はTTFTで、デコードのTPOTは大きく変わらない。全モデルの出力品質を変えないという主張は、予測漏れを正確なインデクサ選択に基づいて必ず補正する実装に依存する。SSDの背景書込を制限する方式は読込が支配的なエージェント負荷に適しているが、書込が多いサービスへ無条件に一般化できない。原著の速度倍率は比較対象ごとに分母が異なるため、最大3.69倍をTutti比や全サービスのスループット改善と誤読しない。今回独立の実機再現は行っていない。
