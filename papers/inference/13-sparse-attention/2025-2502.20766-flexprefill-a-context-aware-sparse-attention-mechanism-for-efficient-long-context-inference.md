# FlexPrefill: A Context-Aware Sparse Attention Mechanism for Efficient Long-Sequence Inference

> **要点**: FlexPrefillは、長文プリフィルの注意計算を一律の疎パターンへ置き換えるのではなく、入力と注意ヘッドごとに「クエリごとに見る場所が違う多様型」か「多くのクエリが似た場所を見る構造型」かを判定し、その型に合う索引だけを累積注意量の閾値まで選ぶ。これにより、必要なヘッドには多く、簡単なヘッドには少ない計算予算を割り当てる。

## 概要

長いプロンプトを処理するプリフィルでは、通常の自己注意は各クエリが過去の全キーを見るため、系列長 (L) に対して注意計算が概ね (O(L^2)) に増える。固定窓や固定ブロック疎注意なら計算量は減らせるが、重要な位置が入力ごと・ヘッドごとに変わる場合、同じ疎パターンを全てへ適用すると必要な長距離依存まで削ってしまう。

FlexPrefillはこの問題を「どの疎パターンを使うか」と「どこまで計算するか」の二段階に分ける。まず末尾側の代表クエリ集合を使って注意分布を粗く観測し、Jensen–Shannon距離（Jensen–Shannon divergence; JSD）から、クエリごとの注意先が大きく変わる**多様型（Diverse pattern）**と、縦方向・斜め方向など比較的規則的な**構造型（Structured pattern）**を切り替える。次に、その型に合わせてキー索引を順位付けし、累積注意量が閾値 (gamma) を超えるまでブロックを採用する。

このため疎率は固定値ではなく、入力・層・ヘッドごとに変わる。難しいヘッドでは多くのブロックを残し、注意が少数箇所へ集中するヘッドでは大幅に削る。Meta-Llama-3.1-8B-Instruct、GLM-4-9B-Chat、Yi-9B-200K、Qwen2-7B-InstructでRULERとInfiniteBenchを評価し、完全注意に近い品質を維持しながら、注意カーネル単体では512K文脈で最大9.6倍の加速を報告する。

## 背景と問題設定

### 固定疎注意は「どの入力にも同じ重要位置がある」と仮定しやすい

StreamingLLMのような固定窓・attention sink型の方式は軽量だが、遠距離の検索対象が入力によって変わる課題では必要情報を窓外へ落としやすい。MInferenceのように疎パターンを利用する方式も、限られた観測からパターンを決めるため、ヘッドごとの実際の注意分布と合わない場合がある。

FlexPrefillが観測したのは、同じモデルでも注意ヘッドには性質の違いがあることだ。あるヘッドでは異なるクエリが別々のキーへ注意し、別のヘッドでは多数のクエリが似たキー集合へ集中する。前者を単一の構造パターンで近似すると重要な関連を落とし、後者に毎クエリ固有の探索を行うと余分な計算が増える。

### 速度だけでなく「必要な注意質量を残す」ことが目的

疎注意では「何%のブロックを削るか」を固定すると、易しい入力には過剰計算、難しい入力には過剰削減になる。FlexPrefillは計算率そのものではなく、選択した位置が元の注意分布の累積質量をどれだけ覆うかを制御する。したがって (gamma) は速度と品質を直接つなぐ主要パラメータになる。

## 手法

### 1. 代表クエリで注意分布を安価に推定する

各ヘッドについて全クエリ×全キーの密な注意行列を先に計算してしまうと、疎化の意味がない。そこでFlexPrefillは末尾の1ブロック分など少数の代表クエリ (hat{Q}) と全キー (K) の注意だけを計算し、どのキー領域に質量が集まるかを推定する。

この前処理は系列長に対して線形に近い追加費用で、後段の二乗計算を省くための索引情報を作る。論文の実装ではブロックサイズ128を用い、Tritonで疎注意カーネルを実装する。

### 2. JSDで多様型と構造型を切り替える

代表クエリごとの注意分布が互いに似ているかをJSDで測る。JSDが大きく、クエリごとに注意先が変わるヘッドでは、各クエリの特徴を残せる多様型の探索を使う。一方、JSDが小さく共通構造が強いヘッドでは、より安価な構造化パターンを使う。

入力は代表注意分布、処理はJSDによる型判定、出力は「このヘッドをどの索引探索へ送るか」というルーティング結果である。固定のヘッド分類ではなく、同じヘッドでも入力によって経路を切り替えられる点が重要になる。

### 3. 累積注意量でヘッドごとの計算予算を決める

選んだパターン上で候補ブロックを注意スコア順に並べ、累積注意量が (gamma) を超える最小集合を採用する。たとえば注意がごく少数のブロックへ集中していれば少ない計算で終了し、広く分散していればより多くのブロックを残す。

これにより「各ヘッドを常に90%疎化」といった固定予算を避けられる。論文のアブレーションでは、(gamma) が低いと一部ヘッドの選択量が不足するため最小予算が有効だが、十分高い (gamma) では最小予算を増やしても必ずしも品質は上がらない。最大予算の上限もモデルによって影響が異なる。

### 4. 選択索引だけをTriton疎注意カーネルで計算する

最終的な出力は選択済みクエリ・キーブロックの集合である。実際の注意値はその集合に対してのみ計算し、値ベクトル (V) を集約する。モデル重みを再学習する方式ではなく、プリフィル時の注意計算経路を差し替えるため、元モデルの表現能力をできるだけ維持しながら計算量を減らす。

重要なのは、本方式が主に**プリフィル注意**を狙うことだ。生成後半のデコードで増え続けるKVキャッシュを圧縮する方式ではなく、長い入力を最初に読み込む二乗計算を削る。

## 評価

### 代表的な評価条件

| 項目 | 条件 |
|---|---|
| モデル | Meta-Llama-3.1-8B-Instruct、GLM-4-9B-Chat、Yi-9B-200K、Qwen2-7B-Instruct |
| 長文ベンチマーク | RULER、InfiniteBench |
| RULER文脈長 | 4K、8K、16K、32K、64K、128K |
| 比較 | 完全注意、StreamingLLM、MInference。追加評価でLM-Infinite、InfLLM、MoA、HIP |
| 実機 | NVIDIA A100 80GB ×1 |
| 実装 | PyTorch + FlashAttention系基盤、Triton、ブロックサイズ128 |
| 主制御 | パターン切替閾値 (	au)、累積注意閾値 (gamma)、最小/最大計算予算 |
| 主指標 | 長文課題スコア、注意関数レイテンシ、文脈長に対する加速率 |

### 代表的な結果

| 条件 | FlexPrefill | 比較対象 | 読み取り |
|---|---:|---:|---|
| LLaMA / RULER平均 | **89.18** | 完全注意 88.70、MInference 85.42 | 疎化しても平均品質を維持 |
| GLM / RULER平均 | **89.34** | 完全注意 89.06、MInference 89.18 | 完全注意とほぼ同等 |
| LLaMA 128K 注意時間 | **185.75 ms** ((gamma=0.9)) | 完全注意 658.83 ms | 約3.5倍の注意カーネル短縮 |
| Qwen 128K 注意時間 | **133.19 ms** ((gamma=0.85)) | 完全注意 569.86 ms | 約4.3倍の注意カーネル短縮 |
| 長文スケーリング | 512Kで最大 **9.6倍** | FlashAttention | 文脈が長いほど疎化の利得が拡大 |
| 代表クエリ位置アブレーション | pattern判定はmiddleでもほぼ維持、索引選択をmiddleへ変えるとLLaMA平均 **38.18** | 通常のlast/lastは89.18 | 末尾代表クエリは索引探索で重要 |

この表の「9.6倍」は注意計算の加速率であり、要求全体の初回トークン時間（Time To First Token; TTFT）やデコードまで含むエンドツーエンド倍率と同一ではない。導入時は前処理・JSD計算・索引探索を含む全体時間を別に測る必要がある。

## 既存研究との差

StreamingLLMのような固定パターンは非常に軽い一方、入力依存の遠距離関係を拾いにくい。MInferenceは疎パターンを利用するが、FlexPrefillはさらに**入力とヘッド単位でパターン種別と計算予算の両方を変える**。つまり「どこを見るか」だけでなく「どれだけ見るか」も動的である。

完全な動的探索を全クエリへ適用する方式に対しては、代表クエリと構造型経路を使って選択オーバーヘッドを抑える。精度優先なら (gamma) を高くし、速度優先なら低くするという明示的な交換条件も持つ。

## 限界・実装状況

FlexPrefillは近似的に注意位置を削るため、選択器が重要ブロックを外せば品質は落ちる。特に累積質量方式は、弱い注意が広く分布するヘッドでは多くのブロックを残して速度利得が縮む一方、(gamma) を下げ過ぎると必要情報を落とす。

実験は主に7B〜9B級モデルとA100で行われており、より大きいモデル、異なる注意機構、別GPU世代で同じ閾値が最適とは限らない。またプリフィル高速化が中心で、デコードKV容量そのものは削減しない。

公式実装はByteDanceから公開されている。ただし疎ブロック選択と専用Tritonカーネルを必要とするため、既存推論基盤へ導入する際はFlashAttentionだけを置き換えるより大きい統合作業が必要になる。
