# GPU演算別回帰と分散学習タイムラインを組み合わせるLLM学習時間予測

## 概要

大規模言語モデルの学習を数十～数百GPUへ分散すると、計算量だけでなく、GPU世代、GEMMの形状、通信集合演算、パイプラインの気泡、データ並列の勾配同期などによって1回の更新に必要な時間が変わる。本論文は、こうした複雑さをブラックボックスの「モデルサイズから学習時間を推定する式」だけで扱うのではなく、**演算・通信プリミティブの実測回帰器と、実行依存関係を反映した時間軸モデルを組み合わせる**ことで、実際の学習反復時間を予測する手法を提案する。

PerlmutterのNVIDIA A100-SXM4とTACC VistaのNVIDIA GH200で、GPT-20B、LLaMA-13B、Llemma-7Bを用い、最大128 GPUまで検証した。論文の代表結果は、予測した学習反復時間と実測の比較における平均絶対誤差がPerlmutterで4.98%、Vistaで9.38%というもの。これは**学習自体を4.98%高速化した結果ではない**。予測器はCPU上で動作し、事前のハードウェア演算プロファイルを使って構成案を比較できることが主な価値である。

重要な負の結果として、Vistaの1 GPU/ノード構成ではネットワーク競合による実測反復時間のばらつきが大きく、通信演算単体の予測誤差は50%前後に達する例もある。全体誤差が小さいのは、計算時間が支配的な構成では通信誤差が総時間に与える影響が比較的小さく、モデル並列all-reduceなど主要通信については別に精度を確保しているためである。予測精度の良さを「すべての通信演算を精密にモデル化できた」と読み替えてはならない。

## 問題設定と従来方式との差

学習時間の見積りには大きく三種類の難しさがある。第一に、A100とGH200では演算器、メモリ階層、Tensor Core、ライブラリの自動チューニングが異なり、同じ行列演算でも形状によって性能が階段状に変わる。FLOPsだけから理想スループットで割る解析モデルでは、その切替えやメモリ律速を捉えにくい。第二に、Attentionの行列積、FFN、正規化、Softmax、埋め込みでは計算律速と帯域律速の比率が異なる。単一の回帰式へ混ぜると誤差が増えやすい。第三に、DP（データ並列）、MP（モデル・テンソル並列）、PP（パイプライン並列）の組合せでは、演算と通信が直列ではなく重なり、同じ演算時間の総和でも実行時間が変わる。

従来のend-to-endサンプリング型予測は、対象の巨大モデルを実機で短時間学習して速度を測る。精度を上げるには多くの構成をサンプリングする必要があり、GPU資源が貴重な環境では予測のための実験自体が高価になる。論文では20Bモデルを128 A100で60秒サンプリングするだけで2ノード時間を使う例を挙げる。本方式はモデル全体を繰り返し学習する代わりに、再利用可能な演算形状・通信量の測定を集めて予測器を作る。ただし、**一度も対象ハードウェアを使わずに正確な予測ができるゼロショット方式ではない**。演算ごとの実機プロファイルは前提である。

## 手法

### 1. Transformerを演算・通信プリミティブへ分解する

入力は学習するモデルの構造（層数、隠れ次元、系列長、ヘッド数、語彙数）、バッチとマイクロバッチ、DP/MP/PPの分割度、GPUノード構成である。GPT-NeoXを対象に、埋め込み、AttentionのQKV投影、QK^T、Softmax、値との積、FFN、正規化、損失、optimizerを区別する。通信はMPのall-reduce、DPのall-reduce/all-gather、PPのpoint-to-pointへ分ける。単なる演算名だけでなく、実行時間に影響する入力形状や通信規模を回帰器の特徴量として持たせる。

例えばQKV投影では入力を[batch×sequence, hidden]、出力を[batch×sequence, 3×hidden/MP]のように表現する。AttentionのQK^Tはバッチ、ヘッド数、系列長、ヘッド次元に依存し、FlashAttentionは別の融合演算として特徴量を与える。通信のall-reduceでは転送要素数、ノード数、ノード当たりGPU数を特徴量とし、NVLinkによるノード内集約とInfiniBand等のノード間通信を区別できるようにする。これにより、GPU数だけを入力とする単純な回帰より、どの演算が遅いかを分析しやすくなる。

### 2. 演算別マイクロベンチマークを収集する

対象GPUでPyTorch profilerとCUDA eventを使い、演算・通信を独立実行して時間を記録する。論文は10回のウォームアップと追加10回の反復を説明し、異常値の影響を減らすため中央値に基づくサンプル選択を行う。演算時間は関連するGPUカーネルの最早開始と最遅終了の差から推定する。こうして得た教師データには演算形状、分割度、ノード構成を付ける。

モデル並列度は1～16の2倍刻み、系列長は1,024～5,120の512刻み、隠れ次元は2,048～約8,129の範囲をサンプリングする。通信についてもMP/DPのall-reduce、DPのall-gather、PPのP2Pで要素数と参加プロセス数を変える。全構成を網羅するわけではないので、性能が非線形に変化しやすい範囲を重点的に取る。ライブラリがカーネルを切り替える閾値やネットワークトポロジーが変わる場所では、補間・外挿の信頼性に注意が必要である。

### 3. 演算種別ごとに回帰器を学習する

演算別の教師データにRandomForestとXGBoostを適用し、80%学習・20%検証で演算ごとに予測器とハイパーパラメータを選ぶ。選定後は全データで最終回帰器を学習する。行列積の形状、正規化の帯域律速、通信の参加GPU数という異質な関係を単一の理論式に押し込まず、**演算種別に適した非線形回帰**で表す。出力は個々の演算の予測実行時間であり、まだ学習全体の時間ではない。

この段階での利点は、例えば新しい隠れ次元やマイクロバッチを検討するとき、すでに集めた近傍の形状から各演算時間を推定できることだ。一方、回帰器が知らないGPUアーキテクチャ、通信ライブラリ版、強いネットワーク混雑、未サンプリングの融合カーネルでは誤差が増える。論文はフレームワーク固有のカーネル融合と独立ベンチマークのずれを調整・検証する必要性も認めている。

### 4. 3D並列の時間軸へ統合する

予測した演算時間を単純合算すると、PPの1F1B実行でforward/backwardが重なること、DP勾配同期の一部が他ステージのbackwardに隠れることを誤る。著者は各パイプラインステージの最大forward時間と最大backward時間、マイクロバッチ数、ステージ数、最初のステージの勾配同期、最大optimizer更新時間を使う時間軸式を組み立てる。

論文の式(7)を要約すると、1更新の予測時間は `(microbatches - 1 + pipeline_stages) × (max_stage_forward + max_stage_backward) + first_stage_gradient_sync + max_update` である。PPの送信側へP2P費用を割り当て、最初以外の勾配同期や一部の更新処理は重なりで隠れるとする。`max_update`にはoptimizerとDP all-gatherの費用を含める。埋め込みと出力層は通常のTransformer層と費用が違うため、最初・中間・最後のステージへの層割当を別に計算する。

語彙数はモデル並列度に合わせて128×MPの倍数へ切り上げる。モデルが実際に使用するテンソル形状と推定器の入力形状を合わせるためであり、理論上の元語彙数をそのまま用いると埋め込み・出力層の演算量を取り違える。こうした実装依存の調整は、単純なFLOPsモデルとの差を生む。

## 評価

### 環境・モデル・測定対象

| 項目 | Perlmutter | TACC Vista |
|---|---|---|
| GPU | NVIDIA A100-SXM4、40 GB HBM2 | NVIDIA GH200、96 GB HBM3 |
| CPU/メモリ | AMD EPYC 7763、256 GB DDR4 | NVIDIA Grace、120 GB LPDDR5 |
| ノード内GPU数 | 4 | 1 |
| ノード内接続 | NVLink 3.0 | NVLink-C2C |
| ノード間接続 | Slingshot-10 | NDR InfiniBand 400 Gb/s |
| 最大規模 | 32ノード、128 GPU | 128ノード、128 GPU |

モデルはGPT-20B（隠れ次元6144、44層、系列長2048）、LLaMA-13B（5120、40層、2048）、Llemma-7B（4096、32層、4096）。精度はFP16、micro-batchは4、optimizerはFusedAdam、ZeRO stage 1。更新当たりの反復数はLlemmaで8、他2モデルで16である。GPT-20BとLLaMA-13BではFlashAttentionを使用せず、Llemma-7Bで使用する。評価は学習1バッチ／1パラメータ更新に要する**実測時間と予測時間の一致度**であり、推論のTTFTやTPS、学習精度を改善する実験ではない。

### 代表的な実測時間と安定性

| モデル、PP-MP-DP | Perlmutter最小 / 平均（秒） | Vista最小 / 平均（秒） | 注意点 |
|---|---:|---:|---|
| GPT-20B、4-4-8 | 17.35 / 17.43 | 7.13 / 8.62 | Vistaは平均が最小より20.98%長い |
| GPT-20B、4-8-4 | 42.53 / 42.80 | 7.48 / 12.75 | Vistaは平均が最小より70.38%長い |
| GPT-20B、8-4-4 | 9.23 / 9.27 | 6.39 / 13.30 | Vistaは平均が最小より108.30%長い |
| LLaMA-13B、4-8-2 | 48.37 / 48.76 | 6.76 / 7.54 | Vistaは平均が最小より11.57%長い |
| Llemma-7B、4-2-2 | 9.57 / 9.59 | 5.04 / 5.30 | Vistaは平均が最小より5.21%長い |

Perlmutterでは最小と平均の差が概ね1%未満で安定するが、Vistaではモデル並列all-reduceがノード間通信を必要とし、ばらつきが大きい。著者はこのため、予測の正解値に平均実行時間ではなく**観測された最短バッチ時間**を採用する。この選択はGPU本来の潜在性能を予測するには合理的だが、運用時の平均ジョブ完了時間やSLOを保証するものではない。例えばVistaのGPT-20B 8-4-4は最短6.39秒に対して平均13.30秒なので、最短時間を予測できても混雑下の平均時間は大きく異なる。

### 全体予測誤差と成分別誤差

| モデル、PP-MP-DP | Perlmutter全体誤差 | Vista全体誤差 | 解釈 |
|---|---:|---:|---|
| GPT-20B、4-4-8 | −8.82% | −9.15% | 両環境で実測最短より短く見積もる |
| GPT-20B、4-8-4 | +3.94% | −15.16% | Vistaで最大級の過小予測 |
| GPT-20B、8-4-4 | −5.87% | −8.41% | PPの構成差で誤差が変化 |
| LLaMA-13B、4-8-2 | −4.95% | −9.02% | 13Bでも通信構成依存 |
| Llemma-7B、4-2-2 | +1.30% | −5.18% | 小型モデルでは比較的良い |
| 5構成の平均絶対誤差 | 4.98% | 9.38% | モデル全体の学習反復時間の予測誤差 |

成分別にはforward/backwardの誤差が大規模GPTで10～15%程度になる例がある。DP all-reduceの誤差はVistaで−49.69%、DP all-gatherは−52.47%という例もあるが、著者はそれらが総時間に占める比率が小さい構成では全体誤差が限定されると説明する。逆にVistaやMP=8のようにモデル並列all-reduceが支配的な場合は、その通信予測精度が重要になる。論文はMP all-reduceの誤差を多くの構成で5%未満、最大10.67%と報告している。

注意点として、論文の表IXの誤差符号は「予測値−実測値」を基準としているため、負の値は**過小予測**を表す。本文の「GH200で保守的な上限見積り」という表現は、表に並ぶ負の誤差と整合しにくい。少なくともこの表の条件では予測器が実測最短を下回る例が多く、**設備予算の過小見積りリスクを防ぐ保証**とは解釈できない。

### 比較対象・感度・未報告事項

本論文の評価は演算別回帰器とタイムライン統合の妥当性を実測と照合するもので、全体学習を短時間サンプリングする既存予測器との同一GPU予算での詳細な直接比較や、異なるGPU世代へのゼロショット転移の定量評価は主要表にはない。GPU構成の違い、PP/MP/DPの割当、モデル規模、通信トポロジーに対する予測誤差は示すが、回帰器の学習に必要な総GPU時間や、モデル選択を誤った場合の最悪コストは十分に定量化されていない。最大128GPUの実機検証は有用だが、数千GPUの学習を実際に予測した証明ではない。

## 既存方式との違い・適用判断

解析モデルだけではGPUライブラリの非線形な実装最適化やネットワーク通信を正確に捉えにくく、巨大モデル全体をサンプリングする方式はGPU資源を多く消費する。提案方式は**一度集めた演算別測定を構成案の横断比較へ再利用**できることが強みである。回帰器をCPUで評価するため、候補構成の試行錯誤自体に大量のGPUを占有しない。DP/MP/PPの選択やモデル層構成の変更による実行時間の方向性を事前に把握する用途に向く。

ただし、GPUの新世代、カーネルの融合方針、通信ネットワーク、NCCLのアルゴリズムが変われば再プロファイルが必要になりうる。推論サーバーのKVキャッシュ、decode、continuous batchingはこの論文のモデル化対象外である。推論フレームワークにそのまま導入できる性能予測器ではなく、**分散学習の配置・容量計画用**の研究として位置づけるべきである。

## 限界・負の結果

第一に、教師データは対象GPU上の実測演算から収集するため、未知ハードウェアへ追加測定なしで転用できる保証はない。第二に、通信負荷が不安定なVistaでは実測の平均と最小の差が108.30%に達し、最短値を予測する目的と実運用の平均完了時間予測は別問題になる。第三に、DP all-reduce/all-gatherなど個別通信の予測誤差は大きい条件があり、通信律速の別ワークロードへ外挿すると全体誤差も増える可能性がある。第四に、表IXにはVistaで−15.16%の過小予測があり、容量計画の安全側保証とはいえない。第五に、検証モデルは7B/13B/20Bと最大128GPUであり、より大きなMoE、長文脈、混合精度、障害・再試行、クラスタ混雑の一般化は未実証である。

また、モデル構成・ライブラリ版が違うと演算融合の粒度が変わる。個別演算のマイクロベンチマークが実アプリケーションの実行パスと一致しなければ、回帰器の精度が高くても全体予測がずれる。予測精度を評価する際は対象フレームワークの演算グラフと実際の通信重畳の仕方を再確認する必要がある。
