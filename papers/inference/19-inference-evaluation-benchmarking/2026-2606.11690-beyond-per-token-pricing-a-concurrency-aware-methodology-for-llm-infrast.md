# 推論費用は要求率で変わる：同時実行を考慮したLLMサービング費用の実測

## 概要

LLMを自前のGPUで提供する費用を見積もる際、GPUの時間単価を公開ベンチマークの最大トークン処理能力で割り、APIのトークン単価と比較することが多い。しかし、この計算はGPUが常に十分な要求を受け取り、ベンチマークに近い処理能力を発揮していると仮定する。実際には要求の到着率が低いと、GPUは少数の要求しか同時処理できず、単位時間当たりの出力トークンが減る。GPUを借りている時間の費用は残るため、出力100万トークン当たりの実効費用は大きく上昇する。

本研究はこの差を、要求到着率を明示した費用測定問題として定式化する。ハードウェア、モデル構造、量子化精度、要求到着率、遅延目標を分け、同じGPUでも負荷によって費用がどの程度変わるかを実機で測る。H100 NVLの主実験では、3種類のモデルと2種類の精度の計6構成を7段階の要求率で測定し、同じ構成内で17.5～36.3倍の出力トークン単価差を観測した。モデルと構成をまたぐ最小値と最大値は0.21～15.25米ドル/出力100万トークンである。これらの倍率は**同一モデル・同一GPUの到着率変更**と、**異なるモデルを含む全体の価格範囲**を区別して読む必要がある。

論文は費用を計算するだけでなく、稼働中のvLLMサーバーのPrometheusメトリクスから、実際に生成された出力トークン数とGPU費用を用いて実効単価を表示する`vllm-cost-meter`を公開する。これにより「8Bモデルは1トークン当たりいくらか」という固定値ではなく、「このGPU・モデル・量子化・要求率・遅延制約の下でいくらか」という運用点ごとの費用曲線を扱えるようにする。

## 問題設定と背景

### 理論最大処理能力を実効処理能力と混同する問題

従来型の費用試算は、GPUの時間単価を理論的またはベンチマーク上の最大トークン処理能力で割る。だがGPUを1時間確保しても、その1時間に要求がほとんど来なければ、出力トークンの総数は最大値に達しない。LLMの復号は少数同時要求時に重み読み出しや通信の固定費が相対的に大きくなるため、要求を増やしてバッチを埋めると処理効率が改善する場合がある。逆に要求を増やし過ぎれば待ち行列が生じ、初回トークン遅延や応答完了時間の上位百分位が悪化する。

著者が調べた公開費用計算器の多くは、利用率を固定値として仮定するか、利用者に任意の利用率を入力させる。入力ができても、要求到着率から実際の同時実行数と処理能力がどう変わるかを測定しない点が問題である。したがって本研究は、推論カーネルを高速化する新しいアルゴリズムではなく、既存の推論エンジンが達成する処理能力を運用負荷に結び付けて費用を推定する方法を扱う。

### 到着率と同時実行数は別の変数

単位時間に到着する要求数を `λ`（要求/秒）、要求が系内に滞在する平均時間を `W`、系内で処理中の平均要求数を `N` とすると、安定した系ではリトルの法則（Little's Law）により `N≈λW` が成り立つ。GPUが実際に一度に処理する要求数は、到着率だけでなく応答時間とスケジューラーの挙動にも依存する。著者は実験の操作変数を到着率 `λ` とし、同時実行数は観測される結果として扱う。「同時実行を考慮する」とは、固定のバッチ数を入力することではなく、到着する仕事量に応じて生じる実効バッチと処理能力を測ることである。

## 手法

### 1. 運用点ごとの実効単価を定義する

著者は実効費用を `C_eff=f(H,M,Q,λ;L)` と書く。`H` はGPU型式・台数・接続、`M` は密モデルか混合専門家（MoE）かを含むモデル構造、`Q` はFP16やFP8などの量子化精度、`λ` は要求到着率、`L` は遅延のサービス水準目標（SLO）である。原著の主走査では `H,M,Q,λ` を変え、`L` を能動的に走査してはいない。遅延は測定結果として得て、後から所定の遅延上限を満たす運用点を選別する。これは5変数すべての最適化を実測したこととは異なる。

GPUの時間単価を `P_GPU`（米ドル/時間）、実測した出力処理能力を `Θ_achieved`（出力トークン/秒）とすると、出力100万トークン当たりの実効費用は `C_eff=P_GPU×10^6/(3600×Θ_achieved)` である。最大処理能力 `Θ_max` を使った従来推定値は `C_naive=P_GPU×10^6/(3600×Θ_max)` となる。達成率 `U=Θ_achieved/Θ_max` を定義すれば、`C_eff/C_naive=1/U` である。最大能力の10%しか使っていないなら、最大能力で割った試算は実効費用を10分の1に過小評価する。

ここでいう利用率 `U` は処理能力の達成率であり、`nvidia-smi`が報告するカーネル稼働時間の割合ではない。単一要求の復号カーネルが常に実行されていても、出力トークン数が少なければ経済的な利用率は低い。原著は両者を混同しないよう明記している。

### 2. 密モデルとMoEの負荷曲線を別々に測る

密モデルは毎トークンで同じ重み集合を活性化する一方、MoEは選択された専門家の一部だけを使う。したがってモデルの総パラメータ数だけでは、GPUが処理すべき重み量や同時要求数への応答を予測できない。実験ではLlama 3.1 8B Instruct（総8B・活性8B）、Qwen3-30B-A3B Instruct（総30B・活性3B）、Mixtral 8x7B Instruct（総46.7B・活性12.9B）を使い、FP16とFP8を比較する。Qwenは総パラメータがLlamaより大きいが、活性パラメータは小さいという構造差を利用している。

この構成の比較は、MoE一般の法則を証明するものではない。著者自身が、異なる専門家比率や大きな密モデルでの追加検証が必要と述べる。GPU世代によってFP8演算器の有無も異なるため、量子化の効果を全ハードウェアへ移してはならない。

### 3. 実測データと稼働中のサーバーを接続する

主実験はvLLMの連続バッチ処理を使い、入力512トークン・出力256トークンの固定長要求をPoisson到着で投入する。各条件で100件の暖機要求を捨て、500件の要求を測定する。接頭辞キャッシュは無効にし、共通接頭辞の再利用が低負荷時の純粋な効果を覆い隠さないようにする。出力処理能力、初回トークン遅延（TTFT）の中央値・90・99百分位、応答全体の遅延、GPUメモリ占有を記録する。要求内容は再現性のための合成トークンであり、実際の対話サービスの入力分布を直接代表しない。

`vllm-cost-meter`は稼働中のvLLMのPrometheus `/metrics` を定期的に読み、出力トークン/秒と設定されたGPU単価からその時点の実効費用を計算する。既存のベンチマークで得た曲線を参照することも、運用中のサーバーを計測することもできる。ただし分単位の極端に低い出力数を使って費用を割ると、非常に大きな瞬間単価が出る。瞬間値は月次請求額そのものではなく、観測窓内の費用按分である。

## 評価条件

| 項目 | 主実験の設定 |
|---|---|
| GPU | H100 NVL 96GB×2、NVLink接続、Azureノード |
| GPU単価 | ノード13.96米ドル/時、単一GPU使用時6.98米ドル/時で按分 |
| 推論エンジン | vLLM 0.19.0、PyTorch 2.10.0+cu128、CUDA 12.8 |
| 密モデル | Llama 3.1 8B Instruct、TP=1 |
| 疎MoE | Qwen3-30B-A3B Instruct、TP=1 |
| MoE | Mixtral 8x7B Instruct、TP=2 |
| 精度 | FP16、FP8 |
| 走査 | 6構成×7要求率＝42回（H100の見出し値） |
| 要求 | 入力512、出力256トークン、Poisson到着 |
| 測定 | 100件暖機後、500件/構成 |
| 除外した最適化 | 接頭辞キャッシュ、投機的復号を無効化 |
| 追加実験 | H100上のSGLang比較42回、A100 PCIeで56回 |

単一GPU構成の6.98米ドル/時は、同じノードのもう一方のGPUが別の利用者により独立して使われていると仮定した按分値である。ノード全体を専有して片方しか使わない運用では、単一GPU構成の費用を倍にする必要がある。これは費用試算の結論に直接関係する重要な前提である。

H100実験の測定環境はLinuxとCUDA 12.8であり、Windows 11やRTX 4070 Superにおける直接測定ではない。追加のA100はPCIe接続で、NVLink接続のH100とは通信条件が異なる。TensorRT-LLMは評価対象外である。SGLangは補助実験として存在するが、見出しの費用倍率はvLLMの主走査から計算される。

## 評価結果

### 到着率による費用差と処理能力

同一H100上で要求到着率を変えると、同じモデル・同じ精度・同じGPU割当でも実効費用が17.5～36.3倍変動した。低負荷の1要求/秒ではMixtral FP16が15.25米ドル/出力100万トークンとなるが、25要求/秒では約0.87米ドルまで下がる。ここでの17.5倍は同一Mixtral構成の負荷差であり、別モデル間の差ではない。Qwen3-30B-A3B FP8の1要求/秒での最大過小評価倍率は36.3倍だった。

| H100でのモデル・精度 | 最大出力処理能力 | 飽和時の出力100万トークン費用 |
|---|---:|---:|
| Llama 3.1 8B FP16 | 6,238トークン/秒 | 0.311米ドル |
| Llama 3.1 8B FP8 | 8,155トークン/秒 | 0.238米ドル |
| Qwen3-30B-A3B FP16 | 5,319トークン/秒 | 0.364米ドル |
| Qwen3-30B-A3B FP8 | 9,271トークン/秒 | 0.209米ドル |
| Mixtral 8x7B FP16 | 4,454トークン/秒 | 0.871米ドル |
| Mixtral 8x7B FP8 | 7,524トークン/秒 | 0.515米ドル |

FP8化による最大処理能力の増分は、Llama 3.1 8Bが31%、Qwen3-30B-A3Bが74%、Mixtralが69%だった。著者はこの三例でMoEの改善率が密モデルの改善率の約2.2～2.4倍と指摘する。ただしこれは3モデルの改善**百分率**の比であり、MoEが密モデルより絶対性能で2.4倍速いという意味ではない。またQwenのFP8飽和単価0.209米ドルはLlama FP8の0.238米ドルより安いが、モデルの品質や総パラメータ数だけから一般化できる結果ではない。

### 遅延目標を満たす運用点は飽和時と異なる

最大出力処理能力が得られる負荷は、必ずしも利用者が許容する応答遅延を満たさない。論文は初回トークン遅延の99百分位300ms以下、トークン間遅延の99百分位50ms以下という一つの条件を後処理で適用し、測定済み7段階の中から条件を満たす最大要求率を選んでいる。

| モデル・精度 | 遅延条件を満たす最大要求率 | 条件付き費用/100万出力トークン | 飽和時費用 | 条件による上乗せ |
|---|---:|---:|---:|---:|
| Llama 8B FP16 | 25要求/秒 | 0.368米ドル | 0.311米ドル | 1.18倍 |
| Llama 8B FP8 | 25要求/秒 | 0.337米ドル | 0.238米ドル | 1.42倍 |
| Qwen3-A3B FP16 | 25要求/秒 | 0.411米ドル | 0.364米ドル | 1.13倍 |
| Qwen3-A3B FP8 | 50要求/秒 | 0.263米ドル | 0.209米ドル | 1.26倍 |
| Mixtral FP16 | 10要求/秒 | 1.666米ドル | 0.871米ドル | 1.91倍 |
| Mixtral FP8 | 25要求/秒 | 0.732米ドル | 0.515米ドル | 1.42倍 |

例えばLlama FP16の飽和単価0.311米ドルは、初回トークン遅延99百分位が7.4秒に達する高負荷条件で得られる。対話型サービスの例示条件を満たす最安単価は0.368米ドルである。上乗せ幅1.13～1.91倍は、この一つの遅延条件と離散的な7段階の要求率に対する結果である。論文が遅延制約の連続的な最適化を完了したという意味ではない。

### A100と別エンジンでの再検証

A100 80GB PCIeの56回の測定でも、要求率が低いと高く、負荷が増えると単価が低下する曲線を確認した。ただし同一構成内の倍率は7.0～11.4倍で、H100の17.5～36.3倍より小さい。これは低負荷時の費用問題がH100だけの現象ではない一方、倍率の絶対値はGPUとエンジンに依存することを示す。SGLangでのLlama 3.1 8B FP16の同様の倍率は12.0倍で、vLLMの24.4倍と異なる。両者の最大処理能力の差によって、遊休から飽和までの比率も変わる。

実測データの全体はH100 vLLM 42回、H100 SGLang 42回、A100 56回の合計140回である。見出しの42回だけを全実験件数として記録してはならない。さらに入力・出力長、接頭辞キャッシュ、到着間隔のばらつきに対する感度実験も行われている。実際の共有接頭辞を持つサービスではキャッシュが有効になり、費用曲線が変わる可能性がある。

### APIとの損益分岐と計測窓の注意

著者は自前推論の実効単価と商用APIの公開**出力トークン単価**を比較する。Mixtral FP16は1要求/秒で15.25米ドル/100万出力トークンとなり、比較対象の一部のAPI単価より高い。一方5要求/秒では3.16米ドルまで下がる。したがって自前推論が常にAPIより安いとは言えない。ただしAPIの入力トークン単価、接頭辞キャッシュ割引、バッチ割引、企業契約価格を比較線に反映していないため、同じ品質のモデル同士を総費用で厳密に比較したものではない。モデル品質も異なるため、単価だけで代替可能性を判断してはならない。

稼働中のvLLMを使った6段階の負荷変化では、分単位の費用按分が非常に大きく変動した。著者は最大653倍という瞬間比も記録するが、ほぼ出力のない分を分母にした比率であり、月次費用倍率として使えないと明記する。運用判断では瞬間値、時間加重平均、月次の総GPU費用と総出力トークン数を分けて管理すべきである。

## 既存研究との差

従来の費用計算器はモデル、GPU、最大処理能力から一つの単価を出す。VidurやMélangeのような推論システム研究は、GPU割当や並列度を最適化して処理能力と費用の交換条件を探る。GuideLLMなどのベンチマークは要求率を走査し、遅延と処理能力を出す。本研究は、これらの測定を運用者の**実際の要求率における出力単価**へ変換する点が中心である。特に、最大能力の試算値からの過小評価倍率を`1/U`として明示し、モデル構造と量子化の違いを同一GPUで測定し、稼働中のvLLMから費用曲線を出す道具を提供する。

これは新しいサービングスケジューラーや量子化アルゴリズムではない。既存のvLLMやSGLangの性能改善が最大処理能力を押し上げても、低負荷時の費用を計算する際には実効処理能力を使う必要がある。論文の方法は、GPU調達、レプリカ数、共有GPUの採用、クラウドAPIと自前推論の選択、遅延目標の設定といった意思決定の基礎になる。

## 限界と適用条件

第一に、主走査は固定長の合成要求で、入力512・出力256トークン、Poisson到着、接頭辞キャッシュと投機的復号の無効化を前提とする。実際の対話では入力長・出力長の分布、共有接頭辞、バースト、キャッシュヒット率が異なる。低負荷費用が高くなる方向性は重要だが、17.5～36.3倍をあらゆる本番サービスの予測値にしてはならない。

第二に、遅延SLOは主実験の独立した走査変数ではない。TTFTやトークン間遅延を測った後で、一つの閾値を満たす点を選んでいる。実際には要求の急増、99.9百分位の遅延、スケールアウト、障害時の余裕、複数モデルの共存などを考慮する必要がある。最大処理能力で割った単価は、厳しいSLOを守るサービスの下限単価より楽観的になる。

第三に、GPU時間単価はAzureの公開価格に基づく。単一GPU構成は2GPUノードの片方を別の利用者が使うと仮定して半額按分しているため、専有ノードで片方を遊ばせると費用が倍になる。予約・スポット・自社保有の減価償却・人件費・電力費用では絶対単価が変わる。APIとの比較も出力トークン価格に限定され、入力料金・割引・品質差を完全には調整していない。

第四に、モデルは密8B、超疎30B-A3B、疎Mixtralの三種類である。活性パラメータ数が飽和時の費用を説明するという傾向や、FP8がMoEで大きく効くという傾向は興味深いが、三モデルだけから一般的なスケーリング則を導くことはできない。FP8専用演算器を持たないGPUでは量子化の効果が逆転する場合があり、A100との比較が示すように接続方式も重要である。

第五に、実測した経済的利用率とGPUの稼働表示を混同しないこと。`nvidia-smi`の利用率が高くても、バッチが埋まらず出力処理能力が低い場合がある。費用の評価では、同じ観測窓でのGPU時間単価、実際の出力トークン数、到着率、遅延分布を組にして記録する必要がある。
