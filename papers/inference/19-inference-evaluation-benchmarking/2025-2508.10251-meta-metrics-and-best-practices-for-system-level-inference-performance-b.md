# FMwork：LLM推論ベンチマークの測定条件を選ぶためのメタ指標と実験設計

## 概要

LLM推論性能を比較するとき、モデル名やGPU名だけを固定しても評価条件は一意にならない。入力トークン長、出力トークン長、同時実行数、重み精度、テンソル並列数、推論エンジン、スケジューラ設定を変えると、初回トークン遅延（TTFT）、トークン間遅延（ITL）、総スループット（THP）は異なる。すべての組合せを実機で測ることは費用が大きい。一方、少数の都合のよい設定だけを測ると、実運用で必要な同時実行数の範囲や飽和点を見落とす。

SalariaらのFMworkは、**LLM推論そのものを高速化する方式ではなく、推論性能を測定する実験計画を高速・低費用にする枠組み**である。入力・出力・バッチ数からなる多次元空間を代表点で実測し、未測定点を補間した場合の誤差と、実験に費やした時間・資源を比較する「メタ指標」を定義する。測定条件選択、GPU当たり性能と費用の評価、合成入力・合成モデルによる制御実験を一つの流れとして扱う。

代表結果として、NVIDIA H100単体、Llama 3.1 8B、BF16、vLLM 0.7.2の測定では、全入力長・全バッチ数を1024出力トークンで測ると32,270秒かかった。バッチ数を1、2、4、8、16、32、64、128の8点へ絞り、出力を128トークンにすると1,301秒で済み、未測定点のITLを補間した平均相対差は4.5%だった。原著の費用対忠実度指標は約24倍となる。**この24倍は実験スイープの省力化であり、LLMの生成速度が24倍になるという主張ではない。**

## 問題設定：推論性能の測定空間と観測対象

### 測定変数と目的関数を分離する

一つの実験条件は、ハードウェア（GPU種別・台数・メモリ）、モデル（密モデルかMoEか、パラメータ規模）、バックエンド（vLLM、TensorRT-LLM、PyTorch等）、精度（重み・活性・KVキャッシュ）、並列化方式（テンソル・パイプライン・エキスパート並列）、負荷（入力長I、出力長O、バッチ数B）で指定される。FMworkはこれらを「事前に制御する入力」「実行するバックエンド」「測定された出力」の三群へ分ける。評価者は一度にすべてを変えるのではなく、対象のモデル・実装・GPUを固定してからI、O、Bの代表点を設計する。

TTFTは要求開始から最初のトークンまでの時間で、長い入力のprefill費用を強く反映する。ITLは連続する出力トークン間の平均時間で、逐次decodeの応答感に関係する。THPは対象の計測時間に生成した総トークン数を割った処理率であり、原著ではTTFTを除く生成時間を用いている。TTFTを含むエンドツーエンドTPSと混同してはならない。さらに費用や電力当たり性能を計算する際には、必要GPU台数と単価も変数になる。

Bを大きくすると一度の重み読み出しで多くの系列を処理でき、総THPは上がり得る。しかし一要求のITLは悪化し、飽和後はBを増やしてもTHPが伸びない。長いIはprefillとKV容量を増やし、長いOはdecodeを長時間占有する。よって、単一の「最速設定」を測っても、チャット用途の50ms/token制約下での最適な構成と、大量バッチ処理の最大THP構成は一致しない。

### 全探索を基準にすると何が問題になるか

I、O、Bがそれぞれ多数の値を取るだけで測定点は積集合として増える。論文は極端な概算として、1測定20秒、100万台の計算装置を使っても全探索が5年以上かかる規模の探索空間を例示する。この例は実際に100万台で測定した結果ではなく、網羅探索が非現実的であることを示す思考実験である。

逆に、バッチ数を1と最大値だけ測ると、性能の飽和点や遅延制約を満たす中間領域を捉えられない。単純に測定点を減らすだけでなく、**どれだけ減らしたら元の性能曲面をどの程度再現できるか**を定量化することが論文の中心課題である。

## 手法

### 1. 測定集合G・Mと補間集合Pを分ける

対象の入力長集合I、出力長集合O、バッチ数集合Bの直積から、十分に密に実測した基準集合Gを作る。Gは比較のためのground truthであり、全ての現実的なGPU・モデル構成の真の全空間ではない。次にGの部分集合Mだけを実際に測定する実験計画を定義する。測定していない条件はMの隣接点から線形補間などで推定し、推定値を含む集合Pを得る。

たとえばB=2と4を測ってB=3を測らなかった場合、同じI・OのTTFTとITLをB=2、4の値から補間する。補間を行う際に必要なのはBの端点と十分な中間代表点であり、原著は最小と最大のBを常に保持した上で、2の累乗のような規則的な選択を比較する。2の累乗は唯一の最適点集合ではなく、再現性と扱いやすさを重視した候補の一つである。

ここでMは「測った条件」、Pは「測定値と補間値を合わせた予測」、Gは「比較のために密に測った条件」である。Gに対するPの誤差が小さければ、Mだけの実験で広いB範囲を近似できたことになる。**少数点の精度が良いという評価は、Gと同じハードウェア・モデル・実装条件における補間忠実度であり、別GPUへの外挿精度を保証しない。**

### 2. 時間・費用のメタ指標を定義する

実験(i,o,b)の測定時間をt(i,o,b)、単位時間当たり装置費用をC_unitとすると、全測定の費用を `C = C_unit × Σ_i Σ_o Σ_b t(i,o,b)` と定義する。GPUの台数を増やして並列測定すれば壁時計時間は短縮できるが、GPU時間の総和に基づく費用が同じ割合で下がるわけではない。費用指標と終了までの経過時間を区別しておく必要がある。

忠実度は、Gに含まれる各条件の実測性能f_Gと、Pの推定性能f_Pの差から評価する。原著は正規化差 `δ = (|f_G|-|f_P|)/|f_G+f_P|` を示し、平均・中央値・パーセンタイル・二乗平均平方根誤差などで全体の誤差Δをまとめる。本文中の「accuracy」はモデルの回答正答率ではなく、**性能曲面を推定する際の一致度**を指す。誤差指標の符号・集約方法を確認せず、通常の相対誤差と機械的に同一視しない。

費用対忠実度の簡易効率指標は `E(G,P)=(1-Δ(G,P))/(C_P/C_G)` である。C_PはMを測るための費用、C_GはGを密に測る費用に対応する。少ない費用でΔが小さければEは大きくなる。ただしEは絶対的なベンチマーク品質保証ではない。平均誤差が小さくても、特定のBにおけるtail latencyやOOM境界の予測が外れる可能性がある。

### 3. 代表的なバッチ数・出力長を選ぶ

実験ではB=1から128までの整数をすべて測るGを作り、測定点数を26、8、2などへ減らしたMと比較する。端点B=1、128は常に含め、8点の場合は2の累乗を選ぶ。O=1はTTFT測定に用い、ITLについてはO=16、128、1024の条件を比較する。Iは128から2倍刻みで増やした複数条件を使用する。

Oを短くすれば一回の実験時間は減るが、短すぎるとウォームアップや初期トークンの影響が大きくなり、長い生成での定常ITLを正確に反映しなくなる。原著のH100実験では、O=128と8点のB選択でITLの平均差が数%に収まり、O=1024を毎回生成する必要はないという結論になった。ただし、長いdecodeで生じるKV成長・温度・動的スケジューリングの変化を、128トークンが常に代表できるとは示していない。

### 4. GPU台数を性能・遅延・価格で選び直す

FMworkは測定点削減だけでなく、測定したTHPをGPU台数で割る `THP/device` と、時間単価から算出する100万生成トークン当たりの費用も出す。TPを2、4、8に変えた場合、総THPが最大の構成と、GPU当たりTHPが最大の構成は異なる。実運用の同時実行数とITL上限を与えて、採用できる候補を絞ってから費用を比較する。

この費用計算では、同じGPUの時間単価を仮定し、総THPに対する必要GPU数を掛けて比較する。TP=8の方が常に一台当たり効率的とは限らない。モデル重みを載せられないTP=1はそもそも選択肢から外す。GPU数の決定は性能測定の結果であって、モデルの演算カーネルを新しく実装する機構ではない。

### 5. 合成入力と合成モデルを使って要因を切り分ける

実際の要求トレースを用意できない場合、FMworkは合成入力のモダリティ、入力長分布、バッチ内の不均質性、時間相関、prefill/decodeの演算パターンを設定できる。テキストでは独立な乱数列や時間相関を持つ系列を生成し、画像を含む条件では解像度やテキストとの組合せを調整する。実データに似せた平均長だけでなく、負荷分布の形を制御する設計である。

合成モデル生成器ではTransformerの層数・隠れ次元・中間次元・ヘッド数を変え、たとえば隠れ次元を64の倍数とし、中間次元を隠れ次元の4倍とするなどの形状制約を置く。実モデルの幾何学的形状を再現したモデルと実モデルの速度を比較し、さらに層数・隠れ次元を独立に変えてスループットの飽和点を調べる。これにより実モデルの公開重みを大量に準備しなくても、**形状が性能へ与える影響**を系統的に測定できる。ただし合成モデルは実モデルの活性分布や注意パターン、品質を再現するものではない。

## 評価条件と定量結果

### 評価A：Llama 3.1 8Bにおける測定点削減

| 項目 | 原著の設定 |
|---|---|
| モデル | Llama 3.1 8B、BF16 |
| ハードウェア | NVIDIA H100 1台、テンソル並列1 |
| 推論エンジン | vLLM 0.7.2、eager mode、scheduler step 1 |
| 入力長 | 128から2倍刻みの複数条件 |
| 出力長 | TTFT測定用1、ITL用16/128/1024 |
| 基準バッチ | B=1～128の全整数 |
| 縮約バッチ | B=1,2,4,8,16,32,64,128（8点） |
| 推定 | 未測定BのTTFT/ITLを隣接点から線形補間 |

| 測定範囲 | 全B・O=1024 | 8点B・O=1024 | 8点B・O=128 |
|---|---:|---:|---:|
| 入力長1024の実験時間 | 2,499秒 | 111秒 | 19秒 |
| 全入力長の実験時間 | 32,270秒 | 3,483秒 | 1,301秒 |
| 全入力長の平均ITL推定差 | 基準 | 3.4% | 4.5% |
| 全入力長の費用対忠実度E | 基準1 | 約9倍 | 約24倍 |

入力長1024だけの条件では、8点B・O=128のITL差は3.4%、TTFT差は0.6%と報告される。2,499秒に対して19秒は約131.5倍の実験時間削減だが、全入力長へ広げると32,270秒に対する1,301秒で約24.8倍となる。原著の効率指標は推定差4.5%を加味して約24倍である。**一つの入力長だけの約130倍と、全入力長の約24倍を同じ条件の結果として扱わない。**

8点BでO=1024からO=128へ短縮した場合、全入力長の時間は3,483秒から1,301秒となり約2.7倍短い。原著の「96.6% accuracy」は、O=1024の8点BにおけるITL平均差3.4%の補数として読むのが適切で、モデルの回答精度96.6%という意味ではない。O=128の全入力長の平均差は4.5%であり、96.6%と混同しない。

### 評価B：Llama 3.3 70Bのテンソル並列数と費用

別実験ではLlama 3.3 70B、16-bit、H100 80GB、vLLM 0.8.4（engine v0、scheduler step 8）、入力長1024、B=1～512を用い、TP=2/4/8を比較する。70Bの重みだけで約140GB必要なため、TP=1はH100 80GBに載らない。TP=8は総THPでは高いが、GPU当たりTHPではB≤96でTP=2、B=128/192でTP=4、それより大きいBでTP=8が優位と記載される。

| 判断条件 | 原著の観測 |
|---|---|
| 総THP最大化 | 対象Bの範囲ではTP=8が高い |
| B≤96のGPU当たりTHP | TP=2が高い |
| B=128/192のGPU当たりTHP | TP=4が高い |
| より大きなBのGPU当たりTHP | TP=8が高い |
| ITL上限50ms/token、TP=4、入力1024 | 最大約192同時系列が条件内 |
| 100万トークン当たり費用 | H100 1台当たり5.50米ドル/時の仮定で算出 |

「TP=4で192ユーザー」は、論文の静的同時実行数・入力長1024・ITL閾値という限定条件に基づく。到着率、リクエスト長分布、キュー待ち時間、P99、TTFTのサービス水準を同時に保証した数字ではない。$5.50/時は計算用の仮定であり、地域や契約による現在のGPUクラウド料金ではない。

### 評価C：合成入力・合成モデルの妥当性

合成入力と実入力のスループット差は、入力長1024～16384、B=1～128の試験で幾何平均2.37%、最大差でもB=96・入力8192の条件で7.01%未満と報告される。この結果は測定対象の合成入力が実入力の計算時間をよく近似した証拠であるが、あらゆる実トレースやマルチモーダル負荷へ一般化できるとは限らない。

合成BERT-base/large形状モデルと実BERTのスループット差は、入力512・B=1～1024の2倍刻みで幾何平均10%だった。層数12で隠れ次元128と1024を比べると、B=1024では小さいモデルが約9倍速いが、B=4では差が約8%にとどまる。隠れ次元1024の合成モデルはB=64～128付近でTHPが飽和し、それ以上のBで悪化する条件がある。**合成モデルの形状比較はBERT型encoderの結果であり、Llamaのdecode速度にそのまま適用しない。**

## 既存研究との差と実装上の意義

MLPerf Inferenceは固定された負荷とルールに従う標準化比較を重視する。LLM-Inference-Benchは複数アクセラレータとモデルの測定範囲を広げる。Vidurは実機測定をシミュレーションへ置き換えて大規模な設定を予測する。一方FMworkの中心は、**どの設定を実機で測るべきか、その削減費用と補間誤差をどう評価するか**という実験設計である。新しい注意カーネルやKVキャッシュ管理、LLMの学習手法を提案する論文ではない。

実務では、推論エンジンを更新した際、モデル・GPU・精度を固定し、I/O長とBの代表点を短時間で測り、THPの飽和域やITLの許容域を推定する用途に向く。比較結果を長期保存するなら、vLLMのバージョン、eager/graph、scheduler step、生成長、TTFTを含むかどうか、ウォームアップ、GPU単価などをメタデータとして残す必要がある。論文自身がvLLM 0.7.2と0.8.4を異なる実験で用いているため、両実験の数字を直接比較して「バージョン差の性能」と解釈してはならない。

FMworkはH100を中心とする測定計画の実証であり、RTX 4070 SuperやCPUオフロード、llama.cppの低ビットモデルで同じ8点B・O=128が最適になるという証拠ではない。特にVRAMが小さい環境では、Bを増やした際のOOMやKVキャッシュ容量境界が非連続に現れる。線形補間でOOM点を埋めると誤った推定になるため、メモリ制約を別のハードゲートとして測る必要がある。

## 限界・負の結果・未検証事項

第一に、代表点の補間は性能曲面が比較的滑らかであることを暗黙に利用する。バッチ数によるカーネル切替、CUDA graphの有無、ページング、量子化カーネルの閾値、OOM境界、ネットワーク通信の発生などで性能が急変すると、端点と2の累乗だけでは局所的な悪化を捉えにくい。論文はH100と特定vLLM版での精度を示すが、他のGPU・ドライバ・エンジンへ誤差保証を与えない。

第二に、メタ指標の平均誤差は、実サービスのP99遅延、tail TTFT、キュー待ち、到着率、要求中断、負荷バーストを必ずしも代表しない。原著の50ms/tokenという基準は一つの運用仮定であり、これを守るだけでユーザー体感の応答速度を保証できるわけではない。SLO違反率や公平性を最適化するには別の指標と到着トレースが必要である。

第三に、合成入力の幾何平均差2.37%は特定の系列長とバッチ分布での結果である。実際のRAGでのprefix再利用、キャッシュ命中率、MoEのexpert偏り、入力モダリティごとの前処理、モデル間共有GPUなどは異なる費用構造を持つ。合成モデルのBERT実験も、生成系LLMの全層を模擬したものではない。

第四に、実験時間削減と本番運用費用削減は別である。ベンチマークを24倍効率化しても、実サービスのトークン単価や消費電力が24分の1になるわけではない。さらに全探索G自体が限定された基準集合であるため、Gに近いPを作れても未観測のモデル・ハードウェア条件まで精度が担保されるわけではない。

第五に、本文の誤差定義は絶対値と分母の形に注意が必要で、集約統計や条件によって一般的な絶対百分率誤差と異なる。論文の「accuracy 96.6%」と、8点B・O=128での4.5%平均差を一つの数値へ混ぜない。FMworkを追試する際は、原著のFigure 2、Equation 2、出力長・入力長の集計単位を固定して比較する。
