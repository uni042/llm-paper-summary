## 概要
GPUカーネル最適化では「同じ出力を返すコードを書ける」だけでは不十分で、参照実装より実測で速くなければ意味がない。KernelBenchは、大規模言語モデル（large language モデル; LLM）へPyTorchの参照 `Model`、初期化関数、具体的な入力形状・dtypeを渡し、CUDA・Triton・CUTLASS・PTXなどを使った置換 `ModelNew` を生成させる。生成物は自動でコンパイル・正当性検証・時間測定されるため、一般的なコード ベンチマークより「GPU固有の性能工学」を直接評価する。

250課題は、単一基本演算中心のレベル 1=100、3〜6演算の連鎖・融合を含むレベル 2=100、実際のモデル構造を含むレベル 3=50に分かれる。論文の中心指標 `fast_p` は、**機能的に正しく、かつPyTorch 比較基準より少なくとも (p) 倍速いカーネルを得た課題の割合**である。主結果は、2025年時点のfrontier モデルでも一発生成でPyTorch 逐次実行を上回れる課題は少数である一方、実行エラーやプロファイラ結果を反復的に返すと一部条件で成功率を大きく伸ばせる、という二点である。

## 問題設定
PyTorch 逐次実行や`torch.compile`は、演算ごとに成熟したCUDA libraryやコンパイラ最適化を利用する。LLMがこれを上回るには、演算融合、tile 形状、shared メモリ、vectorization、Tensor Core、メモリ coalescingなどを入力形状とGPUに合わせて選ぶ必要がある。単にPythonコードをCUDAへ移すだけでは、コンパイルは通っても遅いことが多い。

さらにカーネル性能はハードウェア依存である。同じ生成カーネルでもL40SとA10Gで相対順位が変わり得るため、「正しいカーネルを生成できる能力」と「特定GPU上で比較基準を上回る能力」を分けて測る必要がある。KernelBenchは正当性と速度を同じ自動評価loopで測ることで、この区別を明示する。

## 手法
### 課題形式と自動正当性検証
各課題はPyTorch `Model` と `get_inputs()`、必要なら `get_init_inputs()` を持つ。LLMは同一interfaceの `ModelNew` を返し、その内部で任意のcustom GPU カーネルを使える。評価器は生成コードをbuildし、5個のランダム入力で参照モデルと出力形状・数値を比較する。コンパイル error、ランタイム error、メモリ violation、出力不一致は不正解として扱う。

正当なカーネルだけを反復実行し、wall-clock 遅延を測る。したがって「高速だが間違ったカーネル」は `fast_p` に一切寄与しない。レベル 1は個別演算、レベル 2は複数演算を融合できる短い計算graph、レベル 3はより大きなモデル ブロックなので、段階が上がるほど融合機会は増えるが正当性維持も難しくなる。

### fast_p
参照実装の実行時間を (t_{基礎})、生成カーネルを (t_{gen}) とし、高速化倍率 (s=t_{基礎}/t_{gen}) とする。ある閾値 (p) に対し、正しくかつ (s>p) を満たす課題比率を `fast_p` と定義する。`fast_0` は速度を問わない機能正答率に近く、`fast_1` は「PyTorch 比較基準より速い正答」の割合、(p>1) はさらに強い高速化要求になる。

この指標により、LLMが「動くが遅いコード」を大量に生成する場合を正答率だけで過大評価しない。Figure 3では (p) を上げると全モデルの成功率が急速に下がり、正しさと高性能の両方を満たす難しさが見える。

### 一発生成とhardware依存性
標準評価はNVIDIA L40S上のgreedy 一回生成生成で、簡単なカーネル例を一つin-contextで与える。GPT-4o、OpenAI o1、DeepSeek V3/R1、Claude 3.5 Sonnet、Llama 3.1 70B/405Bを同一課題集合で比較する。

同じ生成カーネルを別GPUでも測り、ハードウェア間の一般化も調べる。レベル 2のDeepSeek R1は `fast_1` がL40Sで36%、A10Gで47%となり、同一コードでもGPUのメモリ hierarchyや演算特性で相対性能が変わる。したがってベンチマーク scoreはtarget ハードウェアを明記して読む必要がある。

### 反復改善
一回生成だけでなく、前回生成物 (G)、実行結果・コンパイラ/ランタイム フィードバック (E)、プロファイラ情報 (P) を次反復へ返す最大10回の反復を評価する。条件は (G) のみ、(G+E)、(G+E+P) を分け、単なる「前回コードを見せる」効果と、実際の失敗・性能観測を与える効果を分離する。

また高温度で独立サンプルを多数引く反復 samplingも比較する。これはフィードバックなしで探索量だけ増やした場合の上限を測るためで、反復エージェントが本当に測定情報を使えているかを比較できる。

## 評価条件
| 観点 | 条件 |
|---|---|
| 課題 | 250件: レベル 1=100、レベル 2=100、レベル 3=50 |
| レベル 1 | 単一基本演算・単純な演算子 |
| レベル 2 | 3〜6演算のsequence、fusion余地あり |
| レベル 3 | 実際のモデル architecture/ブロック |
| 主GPU | NVIDIA L40S |
| ハードウェア比較 | NVIDIA A10G等 |
| 比較基準 | PyTorch 逐次実行、`torch.compile` |
| モデル | GPT-4o、OpenAI o1、DeepSeek V3/R1、Claude 3.5 Sonnet、Llama 3.1 70B/405B |
| 正当性 | 5個のランダム入力で参照出力と比較 |
| 一発生成 | greedy、簡単な例を1個提示 |
| 反復 | 最大10 反復、(G)、(G+E)、(G+E+P) |
| 探索量評価 | 反復 sampling、最大100 サンプル |
| 主指標 | `fast_p`、特に `fast_1` |

## 主要結果
L40S上でPyTorch 逐次実行を比較基準にした一発生成の `fast_1` は、GPT-4oがレベル 1/2/3で4%/5%/0%、OpenAI o1が10%/24%/12%、DeepSeek V3が6%/4%/8%、DeepSeek R1が12%/36%/2%、Claude 3.5 Sonnetが10%/7%/2%、Llama 3.1-70Bが3%/0%/0%、405Bが3%/0%/2%である。レベルごとに最強モデルが異なり、全体としてPyTorch 逐次実行を上回れる課題は少ない。

`torch.compile`を比較基準にすると順位も難度も変わる。例えばo1は28%/19%/4%、DeepSeek R1は38%/37%/2%であり、「逐次実行より速い」と「コンパイラ最適化済み実装より速い」は同じ能力ではない。論文の高速化倍率分布では (p=1) 時に多くのモデル/レベルで15%未満しかPyTorchを上回らず、正当性だけ満たすカーネルの多くが性能では負けている。

失敗分析では、推論モデルのo1/R1は不正解率が概ね55%未満なのに対し、他モデルは70%超の条件が多い。差の大きな要因はコンパイラ/ランタイム 失敗の減少で、機能的な出力不一致は推論モデルでも依然多い。つまりreasoningは「実行可能なカーネルを書く」能力を改善するが、完全な意味正当性と高速性を自動的には解決しない。

反復改善ではDeepSeek R1のレベル 2が一回生成 `fast_1=36%` から、10 反復の (G+E+P) で72%へ上がる。レベル 1は12%→43%、レベル 3は2%→18%。R1はレベル 1/2で10 反復内に90%以上の課題で少なくとも一度は機能的に正しいカーネルを作れるが、その全てが比較基準より速いわけではない。

構成要素比較では、レベル 2のR1は (G) のみ44%、(G+E) 62%、(G+E+P) 72%で、実行フィードバックとプロファイラが段階的に寄与する。一方DeepSeek V3のレベル 2は一回生成 4%、反復@10 14%、(G+E+P) 6%で、フィードバックを与えれば常に改善するわけではない。モデル自体がprofiling情報を適切に使える能力が必要である。

100回の独立サンプルではDeepSeek V3 レベル 2の `fast_1` が4%→37%まで上がるが、レベル 1のconvolution系34課題は100 サンプルでも一度も解けない。探索量を増やすだけでは越えられないsystematicな知識・最適化欠損が残るという負の結果である。

ハードウェア依存も大きい。DeepSeek R1 レベル 2は同じ一発生成でもL40S 36%に対しA10G 47%となる。したがって「モデルが良いカーネルを書いた」という評価は、対象GPU・input 形状との組を含む。

## 既存研究との差
従来のLLM コード ベンチマークは主にunit 評価の通過や一般プログラムの実行効率を見る。KernelBenchはGPU カーネルへ対象を限定し、PyTorch参照と同じ形状/dtypeで、**正当性と実測性能を同時に**要求する。さらに実行/プロファイラを反復フィードバックとして返すため、単発コード 生成だけでなく自動カーネル engineer型エージェントの改善loopも評価できる。

## 限界
正当性は5個のランダム入力による自動比較なので、未テストcorner caseまで形式的に保証するものではない。逆に数値許容差や乱数条件によっては、実運用で十分なカーネルが失敗判定される可能性もある。ベンチマーク scoreはこの評価 harnessの定義に依存する。

性能はGPU型、driver/コンパイラ、PyTorch/CUDA版、input 形状へ強く依存する。同じカーネルがL40SとA10Gで異なる相対性能を示すため、一つの `fast_1` を別ハードウェアへ直接一般化できない。レベル 1/2/3の250課題は有用なサンプルだが、LLM推論で使う全カーネルや将来のハードウェア 基本演算を網羅するわけではない。

またKernelBenchは「LLMがカーネルを書けるか」のベンチマークであり、生成カーネルをLLM serving全体へ組み込んだTTFT/TPOTやcontinuous batchingのエンドツーエンド改善を測る研究ではない。反復フィードバックは成功率を上げる一方、最大10回のコンパイル・execute・profileを要するため、探索時間そのものは増える。offline カーネル engineeringでは有効でも、ランタイムで毎要求行う方式ではない。
