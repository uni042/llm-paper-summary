# LLMCBench: Benchmarking Large Language Model Compression for Efficient Deployment

> 圧縮性能から信頼性までの6軸で疎化と量子化の代表7手法を統一測定し、量子化が性能保持で優れること、重みのみ量子化が汎化で安定すること、疎化は学習が軽いが配布基盤の対応が未熟なことを明らかにした。

## 概要

大規模言語モデルは賢い反面、計算と保存の負担が大きく、そのままでは実運用に出しにくい。重みを間引く疎化と、数値のビット数を下げる量子化を中心に圧縮手法が多数提案されているが、困ったことに手法ごとに評価の土台モデル、データセット、指標がばらばらで、横並びの比較ができない。同じモデルの困惑度（次トークン予測の外しにくさ）ですら論文によって5.68と12.62のように大きく違い、土台の揃っていない比較になっている。さらに効率の評価は計算量やパラメータ数といった理論値が中心で、実際にどれだけ速くなるか、どれだけメモリが減るか、圧縮する過程自体にどれだけ費用が掛かるか、そして圧縮後のモデルが敵対入力や誤情報に対してどれだけ信頼できるかは、ほとんど測られていなかった。

本論文のエルエルエムシーベンチは、実際のモデル生産の要件から逆算して6つの評価軸（トラック）を設計したベンチマークである。圧縮性能、汎化能力、学習消費、推論消費、ハードウェア加速、信頼性の6軸で、疎化の代表3手法と量子化の代表4手法を、11データセット、18アーキテクチャ、3つの配布基盤で同じ条件で測る。各軸の指標は、圧縮前に対する比を二乗平均でまとめた総合指標に統一され、100が圧縮前と同等を意味する形にそろえられている。

代表的な発見は3つある。第1に、圧縮性能の総合指標は量子化が95を超えるのに対し疎化は90未満が多く、性能保持では量子化が優れる。第2に、汎化では重みのみを量子化する手法が安定して高い一方、重みと活性の両方を量子化する手法はモデルによって困惑度が数千から数万へ爆発し、総合指標が0.82まで落ちる。第3に、実測の加速では4ビット量子化が最も速く、構造化疎化と8ビット量子化が同程度で、2対4疎化は対応ライブラリが1つしかない。本論文は新しい圧縮手法ではなく、実測中心のベンチマーク研究である。

## 問題設定

比較が成立しない原因は、評価条件の自由度が高すぎることにある。土台モデルが違えば素の性能が違い、データセットが違えば得意不得意が違い、指標が理論値だけでは実装の出来不出来が見えない。例えば疎化でゼロにした重みは、専用の実装がなければ保存も計算も減らず、理論上の演算量削減が実測の速度やメモリに結び付かない。逆に量子化は、ビット数を下げれば保存量は確実に減るが、配布ライブラリがその形式に対応しているかで実測速度が大きく変わる。つまり圧縮の良し悪しは、数学的な削減量だけでなく、学習過程の費用、推論時の実メモリ、配布基盤の対応、圧縮後の信頼性まで含めた生産全体で決まる。本論文はこの全体を6軸に分解し、各軸で「圧縮前と比べてどうか」を同じ物差しで測れるようにした。読者は、自分の場面で重い軸を優先して手法を選べるようになる。

## 手法のあらまし

進め方は、まず対象手法を固定することから始まる。疎化からは非構造化と2対4疎化を担うワンダとスパースジーピーティー、構造化疎化のエルエルエムプルーナーの3手法、量子化からは重みのみ量子化のジーピーティーキューとエーダブリューキュー、重みと活性の量子化のスムースクアントとオムニクアントの4手法を選ぶ。いずれも公開コードがあり広く使われている手法である。次に、6軸ごとに使うモデルとデータセットを決め、圧縮条件を統一する。疎化率は50パーセント、量子化は原則8ビットとし、汎化の軸では差が出やすいよう4ビット条件も使う。各軸では圧縮前モデルと圧縮後モデルを同じデータで測り、比を二乗平均した総合指標を計算する。最後に、軸ごとの結果を並べて、どの手法がどの生産条件に向くかを分析する。

## 手法

### 1. 6つの評価軸 — 生産要件を測定可能な単位へ分解する

この機構が観測するのは、圧縮手法の振る舞いを生産の観点で切り分けた6つの側面である。保持する状態は、各軸の定義と、使うモデルとデータセットの対応表である。動作は次のとおりである。圧縮性能の軸では知識能力と推論能力に分けて精度を測る。汎化能力の軸ではモデル系列と規模を広く変えて困惑度を測る。学習消費の軸では圧縮に要する時間と最大メモリを測る。推論消費の軸では推論時のメモリ、モデルサイズ、演算量を測る。ハードウェア加速の軸では配布ライブラリ3種で生成速度を実測する。信頼性の軸では敵対入力への頑健さと、誤情報下での真実性を測る。減るボトルネックは、手法選択の判断材料の欠落であり、特に学習消費と信頼性は従来ほぼ未測定だった。追加で消費する資源は大規模な実測そのもので、18アーキテクチャに及ぶ測定が要る。失敗時の挙動として、軸の切り方が生産要件とずれれば結論もずれるため、本論文は要件起点の設計であることを明示し、将来の軸追加を前提にしている。

### 2. 総合指標 — 比の二乗平均で軸内の結果を1つにまとめる

この機構が観測するのは、各データセットと各モデルでの圧縮前と圧縮後の測定値の比である。保持する状態は軸ごとの集計式であり、全軸で同じ形、すなわち比の二乗の平均の平方根を使う。動作は、精度の軸では圧縮後の精度を圧縮前の精度で割り、消費の軸では速い方が大きくなるよう向きをそろえて割り、データセットとモデルについて平均してから100倍して読みやすくすることである。二乗平均を使う理由は、外れ値に引っ張られ過ぎず、大きな悪化を見逃さないためである。減るボトルネックは、多数の生数値を並べただけでは手法の優劣を読み取れない問題であり、軸ごとに1つの物差しができることで、例えば汎化指標0.82という数字だけで壊滅的な手法を即座に見分けられる。追加費用は集計の単純さと引き換えの情報の圧縮であり、どのデータセットで崩れたかは元の表へ戻る必要がある。失敗時の挙動として、平均化は最悪条件を薄めるため、本論文は総合指標と生の表を併記して、最悪の爆発も表から追える形にしている。

### 3. 測定条件の統一 — 圧縮率とビット数と土台をそろえる

この機構が観測するのは、各手法の原論文がばらばらに選んでいた土台モデル、圧縮の強さ、ハイパーパラメータである。保持する状態は統一条件であり、疎化は疎化率50パーセント、量子化は重みのみが8ビット、重みと活性も8ビットを原則とし、汎化の軸だけは差を際立たせるため重みのみ4ビット、重みと活性は4ビット同士の条件を使う。動作は、全手法を同じエー800上で、各手法の公開コードと原設定のまま実行し、同じデータで圧縮前と比較することである。減るボトルネックは、土台の素性能の差や条件の有利不利が手法の差に混ざる問題である。追加費用として、条件統一のために各手法の最も得意な設定とは違う条件で測る場合があり、手法の最大性能ではなく公平な条件下の性能を測る割り切りが入る。失敗時の挙動として、公開コード自体に実量子化の配布対応がない手法では推論消費が不利に出ることがあり、論文はその旨を注記して、別ライブラリでの配布可能性にも触れている。

### 4. 実測中心の加速評価 — ライブラリ対応まで含めて測る

この機構が観測するのは、圧縮形式ごとに、配布ライブラリが実際に高速化できるかどうかである。保持する状態は、圧縮形式とライブラリの対応表と、毎秒トークン数で測った生成速度である。動作は、構造化疎化、2対4疎化、非構造化疎化、8ビット量子化、4ビット量子化の形式ごとに、テンソルアールティーエルエルエム、ブイエルエルエム、エムエルシーエルエルエムの3基盤で同じモデルを動かして速度を測ることである。減るボトルネックは、理論上の演算量削減と実測速度の乖離であり、2対4疎化は1基盤でしか加速せず、非構造化疎化はほぼ加速しないことが実測で初めて明確になる。追加費用は基盤ごとの実装と測定の手間である。失敗時の挙動として、ライブラリの対応状況は時期で変わるため、この軸の結論は測定時点のものであり、対応が進めば順位が入れ替わり得る。論文の議論でも、疎化は基盤整備が進めば評価が変わり得る将来課題として扱われている。

## 評価

### まず見るところ

- **結論:** 現時点の基盤とハードウェアでは、性能保持と実測加速の両面で量子化、特に重みのみ量子化が無難であり、疎化は学習の軽さが強みだが配布対応が追い付いていない。
- **速度・効率:** 理論指標と実測を意図的に分けて測っており、両者の乖離自体が主要な結果である。
- **品質:** 圧縮は全て近似であり、精度保持は軸1と軸2と軸6で多面的に測られている。知識能力と推論能力で疎化と量子化の得意が分かれる点が重要である。
- **メモリ・入出力:** 推論メモリとモデルサイズは絶対値で示され、構造化疎化だけが疎化の中で実際にメモリを減らせることが分かる。

### 感度・スケーリング・ストレス条件

モデル規模と系列を変えた汎化軸が感度評価に相当し、規模が大きいほど圧縮への耐性が上がる傾向と、特定系列での全手法的な崩壊が確認されている。信頼性軸は敵対入力というストレス条件の評価であり、圧縮性能の順位と信頼性の順位は一致せず、性能が良い手法が信頼できるとは限らないことが示されている。

## 既存研究との差

従来の圧縮論文は、自手法の評価を自ら選んだ土台とデータで報告し、他手法との比較は条件の違う数字の引用になりがちだった。本論文は手法提案ではなく測定の枠組みの提案であり、全手法を同一の土台、同一の圧縮条件、同一のハードウェアで再実行して比べ直した点が根本的な差である。また、従来ほぼ扱われなかった学習消費と信頼性を正式な評価軸へ加え、加速を理論値ではなく配布ライブラリでの実測にしたことで、生産判断に必要な情報の欠落を埋めた。疎化と量子化という2大分類を、性能、汎化、消費、加速、信頼性の全軸で横断した比較も初めての試みと位置付けられている。

## 限界・実装状況

- 対象範囲の限界として、代表7手法のみであり、鍵値キャッシュ圧縮や蒸留の本格評価は含まれていない。データセットも符号生成や数学を含まない。
- 時期依存の限界として、ハードウェア加速の結論は測定時点のライブラリ対応に強く依存し、基盤の進化で順位が変わり得る。
- 条件の割り切りとして、公平さのために統一した圧縮条件は各手法の最適条件とは限らず、手法の上限性能を測るものではない。
- 実装状況として、ベンチマーク一式のコードは公式に公開され、パイトーチ上で再実行できる。上流の圧縮ライブラリへ統合される性質のものではない。
- 近似の品質リスクとして、本論文自体は圧縮を行わないが、対象手法はいずれも近似であり、特に活性量子化はモデルにより壊滅的な精度低下を起こし得ることが実測で示されている。

## 一般的な実装上の含意

圧縮や最適化の手法選定では、理論上の削減量ではなく、配布先の基盤がその形式を実際に高速化できるかを先に確認すべきである。対応がない形式は、演算量が減っても速度もメモリも減らない。また、平均指標だけで判断せず、最悪のモデルや最悪のデータセットでの崩壊を必ず確認することが重要であり、特に活性側を触る最適化はモデルごとの外れ値の性質で成否が分かれる。さらに、最適化過程自体の費用と、最適化後の信頼性を、性能と並ぶ正式な選定基準として最初から組み込むと、実運用での手戻りを減らせる。
