# Don't Do RAG: When Cache-Augmented Generation is All You Need for Knowledge Tasks

## 概要
キャッシュ拡張生成（Cache-Augmented Generation; CAG）は、知識集合が限定的かつ長文脈modelのcontext windowへ収まる用途で、質問時のretrievalを丸ごと省く設計である。外部文書群をofflineで一度modelへprefixとして通し、そのKey-Value（KV）cacheをdiskまたはmemoryへ保存する。onlineでは質問tokenだけを既存cacheへ続けて処理するため、RAGのretriever latency、誤ったdocument selection、retrieverとgeneratorを統合するsystem complexityを避ける。

この方式は「modelのparameterへ知識を書き込む」ものではない。文書tokenから計算された各attention layerのK/V状態を再利用するprefix cachingであり、知識内容そのものはcontextとして残る。従って適用条件は、知識集合全体がcontext windowに収まり、更新頻度が十分低く、全知識を各queryで参照させることが合理的な場合である。

## 問題設定
RAGは大規模・動的なcorpusからqueryごとに少数の関連passageを選ぶため、context windowを節約できる。一方、企業内FAQ、小規模なinternal documentation、call center knowledgeなど、知識集合自体が長文脈へ収まる場合にもretrievalを毎回行うと、retrieval latencyとtop-k selection errorが残る。さらにretriever、index、chunking、ranking、generatorを個別に保守する必要がある。

長文脈LLMでは「全候補文書をそのままcontextへ入れる」選択肢が生まれたが、各queryで毎回同じ長いprefixをprefillすると計算が重い。CAGはこの重複prefillをKV cacheへ移し、**retrievalをしないこと**と**長い共通知識prefixを再計算しないこと**を同時に狙う。

## 手法
### 1. External Knowledge Preloading
対象applicationで必要な文書集合 `D={d1,d2,...}` を前処理し、modelのextended context windowへ収まる形で連結する。LLM `M` に一度Dを入力し、
`C_KV = KV-Encode(D)`
として各layerのK/V状態を計算する。このcacheはdiskまたはmemoryへ保存し、Dの処理costをquery数に関係なくofflineで一度だけ支払う。

### 2. Inference
query `q` が来たら保存済み `C_KV` をloadし、modelは
`r = M(D ⊕ q) = M(q | C_KV)`
として回答を生成する。online pathにはinformation retrieval modelが存在せず、全document prefixも再prefillしない。これによりretrieval omissionやranking mistakeを原理的に除き、knowledge prefixのprefillをquery間で償却する。

ただし、全knowledge tokenへattentionできるため「必ず必要情報を使える」ことと、「非常に長いcontextから正しく情報を見つけ出せる」ことは別である。contextが長くなるほどmodel自体のlong-context retrieval能力が支配的になる。

### 3. Cache Reset
query tokenはappend-onlyにKV cacheへ追加されるため、そのまま次queryへ使うと前queryの状態が混ざる。CAGはquery終了後、追加したquery/response由来のcache tailをtruncateし、offlineで作ったknowledge prefixのcache長へ戻す。knowledge cache全体をdiskから再load・再computeせず、同じbase stateから次queryを開始できる。

### RAGとの計算上の交換条件
RAGはonlineでretrieval costを払う代わりに、LLMへ渡すcontextをtop-k passageへ絞る。CAGはretrieval costを0にする代わり、全knowledge分のKV cacheを保持し、query generation時にもその長いK/Vへattentionする。従ってknowledge sizeが増えるとCAGのcache memoryとattention costは増え、RAGではretrieval後の短いcontextが有利になり得る。この境界が「Don’t Do RAG」という題名の実質的な適用条件である。

## 評価条件
全方式のgeneratorにはLlama 3.1 8Bを使用し、Tesla V100 32GB ×8で実験する。datasetはsingle-passage QAのSQuAD 1.0とmulti-hop QAのHotPotQA。回答品質はground-truthとのBERTScoreで測る。

knowledge sizeをsmall/medium/largeの3段階へ分ける。HotPotQAは16/32/64 documents、約21k/43k/85k tokensで、QA pairsは1,392/1,056/1,344。SQuADは3/4/7 documents、約21k/32k/50k tokens、各500 QA pairsである。CAGは各集合を丸ごとpreloadする。

baselineはLlamaIndex上のBM25 sparse RAGとOpenAI Indexesを用いたdense RAGで、それぞれtop-1/3/5/10 passageをgeneratorへ渡す。latency評価ではHotPotQAについてretrieval timeとgeneration timeを分け、さらに毎queryで全reference textを通常prefillするin-context learning（ICL）とも比較する。

## 主要結果
### 回答品質
HotPotQA smallではCAGのBERTScore 0.7951に対し、最良のsparse RAGはtop-5の0.7676、dense RAGはtop-3の0.7582。mediumでもCAG 0.7821がsparse 0.7633、dense 0.7432を上回る。largeではCAG 0.7407となり、sparse top-5の0.7535を下回る。つまりknowledgeが長くなるとCAGの優位が縮まり、HotPotQA largeでは明確な負の結果がある。

SQuADではsmall CAG 0.7695、medium 0.7383、large 0.7734。最良RAGはsmallでsparse top-3 0.7616、mediumでdense top-10 0.7310、largeでsparse top-5 0.7658であり、3 sizeすべてCAGがわずかに上回る。論文が「多くの条件で最高」と表現するのはこの結果に基づくが、差の大きさはdataset・knowledge sizeに依存する。

著者ら自身、size増加でgapが狭まることをlong-context LLMの性能劣化と関連付ける。またsparse RAGがdense RAGをしばしば上回るため、このbenchmarkがsemantic retrievalを必要とするほど難しくない可能性も指摘している。従って「retrievalなしが普遍的にRAGより高精度」という結論ではない。

### 応答時間
HotPotQA smallではCAG generation 0.8512s。sparse RAG top-3はretrieval 0.0008s + generation 0.7406sで合計ではCAGより速く、dense RAG top-3は0.4849+1.0093sでCAGより遅い。mediumではCAG 1.4078s、sparse top-3は約0.7156s、dense top-3は約1.3706sで、CAGはdense top-3にも僅かに遅い。largeではCAG 2.2631s、sparse top-3約0.6675s、dense top-3約1.3454sで、retrievalを消しても全knowledgeへのattention costによりRAGより遅い条件がある。

一方、全reference textを毎回prefillする通常ICLはsmall 9.3197s、medium 26.3717s、large 92.0824sで、CAGは0.8512/1.4078/2.2631s。knowledge prefixをKV cacheとして再利用する効果はknowledge sizeが増えるほど大きい。したがって本論文の強いlatency結果は「RAG全般より常に速い」より、**同じ全contextを毎回prefillする方式を大幅に高速化し、dense retrievalのoverheadも避けられる**という点にある。

## 既存研究との差
通常RAGはqueryに応じて知識を選び、TurboRAG等のcache利用方式はretrieved chunkのprefillを高速化する。CAGはquery-dependent retrieval自体を除き、applicationの全knowledgeを1個のshared prefix cacheとして扱う。long-context model単独利用との違いは、その長いcontextをqueryごとに再computeせずoffline KVへ変換している点である。

## 限界
最大の制約は、全関連文書がcontext windowとKV-cache memoryへ収まる必要があること。論文自身もlarge datasetには実用的でないと明記する。知識更新時にはbase KV cacheを再生成する必要があり、高頻度更新、userごとに可視documentが異なるaccess control、queryごとに巨大corpusのごく一部だけ必要な用途ではRAGの選択性が重要になる。

評価もLlama 3.1 8B、SQuAD/HotPotQA、最大85k-token knowledgeに限定され、long-context能力やcache memory costをmodel間で比較していない。BERTScore中心で、人手評価やfactualityの詳細分析もない。latency表はCAGのretrieval timeが0である一方、長いcacheへattentionするgeneration costを含むため、sparse RAGがCAGより速い条件も存在する。

したがって適切な結論は「RAGを一般に廃止する」ではなく、**小さく安定したknowledge baseで、retrieval errorを避けたい多数query workloadなら、offline prefix KV cacheによるretrieval-free構成が有力**というものになる。
