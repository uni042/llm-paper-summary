# LIMINAL: Exploring The Frontiers of LLM Decode Performance

> LIMINALは、自己回帰デコードの上限を、モデル側の演算・重み・キー・バリュー（Key-Value; KV）キャッシュ需要と、加速器側の演算性能・メモリ容量・帯域・集合通信性能へ分解する解析性能モデルである。8基H100を含む既存ハードウェア測定に対して平均絶対パーセント誤差7.6%で性能を再現し、HBM3からHBM4、先進3次元積層DRAMまでを仮想的に置換して律速の移動を追う。分析では5,000〜10,000ユーザートークン/秒級へ近づくと帯域だけの増強では逓減し、10,000トークン/秒を大きく超えるにはモデル・文脈・デコード方式側の変化も必要になると結論づける。

## 概要

LLMデコードの性能予測は、単純な「GPUのFLOPSが何倍になったか」では決まらない。自己回帰生成は1トークンごとに重みを読み、過去KVを参照し、テンソル並列などを使う場合はGPU間で集合通信を行う。演算器が高速化しても高帯域メモリ（High Bandwidth Memory; HBM）の帯域が足りなければメモリ律速になり、帯域を増やしても集合通信の遅延が残れば通信律速へ移る。モデルや同時ユーザー数を増やせば、今度はメモリ「帯域」より「容量」が先に尽きる。

LIMINALはこの相互作用を解析式で扱う。入力としてモデル構造、精度、バッチ/ユーザー数、系列長などのアプリケーション条件と、加速器数、演算性能、メモリ容量・帯域、チップ間リンクと集合通信の特性を与える。各オペレーターについて必要な演算量、メモリ転送量、装置間通信量を見積もり、それぞれの下限時間からトークン生成速度を予測する。

目的は特定GPUのベンチマークを置き換えることではなく、「演算2倍」「HBM帯域2倍」「容量4倍」「集合通信改善」のどれが将来LLMデコードへ効くかを同じモデルで比較することにある。実機で検証した後、現行HBM3、近未来HBM4、さらに高帯域・大容量を狙う3次元積層DRAMまでパラメータを振り、どこで次のボトルネックへ移るかを探索する。

## 問題設定

デコードでは各生成ステップが前ステップに依存するため、単一系列内の時間方向を自由に並列化できない。バッチや多数ユーザーをまとめれば行列演算の利用率は上がるが、その分だけ各ユーザーのKVキャッシュが増え、HBM容量を消費する。大モデルをテンソル並列化すると重み容量は分散できる一方、層ごとにGPU間集合通信が必要になる。

したがって性能上限は少なくとも「演算」「重み/KVを載せる容量」「それらを毎ステップ読む帯域」「複数加速器を同期する集合通信」の連立制約になる。ある一つだけを無限に改善しても、別の制約へ律速が移るため速度は飽和する。

既存の屋根線モデル（roofline model）は演算強度とメモリ帯域の関係を見るには有用だが、LLMデコードではモデル並列の集合通信、KV容量、ユーザー並列性まで同時に扱う必要がある。LIMINALはハードウェアとアプリケーションの両側を抽象化し、将来技術をまだ存在しないGPU製品として固定せず、能力値として差し替えられる形にする。

## 手法

### 1. アプリケーション側を演算・重み・KV需要へ展開する

入力はモデルの層数、隠れ次元、注意構造、パラメータ精度、文脈長、同時ユーザー数などである。LIMINALは各Transformer演算について浮動小数点演算量、重み読み出し、活性値/KVアクセスを見積もる。

自己回帰デコードでは同じ重みを各トークン生成で繰り返し使うため、小さいバッチでは重み読み出しが支配しやすい。バッチを増やすと重みは多数要求で再利用され演算利用率が上がるが、ユーザーごとのKVは増える。このため「バッチを増やせば常に速い」わけではなく、容量制約との交差点が存在する。

### 2. ハードウェアを演算・容量・帯域・通信で抽象化する

加速器側はピーク演算性能、メモリ容量、メモリ帯域、装置数、チップ間通信性能などで表す。特定のCUDAカーネル実装を直接シミュレーションするのではなく、各演算が必要とする資源量とハードウェア上限から下限時間を求める。

これにより「H100を次世代品に交換」のような製品名単位だけでなく、帯域だけをHBM4相当に増やす、容量だけを増やす、集合通信遅延だけを改善するといった反実仮想を比較できる。ボトルネックが移れば、追加投資の限界効用も変わる。

### 3. 分散実行の集合通信を独立した律速として入れる

テンソル並列では複数GPUが局所行列積を行った後、全削減（all-reduce）などの集合通信で結果を統合する。演算器やHBMが十分速くなるほど、この同期時間は隠しにくくなる。LIMINALは演算・メモリ時間だけでなく、装置数とリンク性能に応じた通信時間をデコード時間へ加える。

ここが将来予測で重要である。HBM帯域を大きく増やした設計では、以前は目立たなかった集合通信が次の支配項になる。したがって「次世代メモリで帯域を何倍にすれば何倍速くなる」と単独で外挿するのを避けられる。

### 4. 技術ノブを一つずつ振り、律速遷移を調べる

検証済みモデルを使い、HBM3、HBM4、先進3次元積層DRAM相当へ容量・帯域を拡張し、演算性能や集合通信も変化させる。出力はユーザートークン/秒と、各条件でどの資源が下限を決めているかである。

分析からは、メモリ帯域だけを増やす段階では速度が伸びるものの、一定点以降は容量・集合通信・逐次性など別制約が支配する。このため10,000トークン/秒を大幅に超える領域では、ハードウェアの比例改善だけでなくモデル/文脈削減、より高いデコード並列性などアルゴリズム側の共同設計が必要になる。

## 評価

### 評価条件

| 項目 | 内容 |
|---|---|
| 評価対象 | 自己回帰LLMデコード。プリフィル性能そのものを主対象にしない |
| 検証 | 既存加速器上での実測LLM性能と解析予測を比較 |
| 代表実機 | 8×NVIDIA H100サーバーを含む現行ハードウェア測定 |
| 予測入力 | モデル/系列/ユーザー条件と、演算性能・HBM容量/帯域・装置間通信 |
| 将来メモリ | 現行HBM3、HBM4、先進3次元積層DRAMを含む設計空間 |
| 主指標 | ユーザートークン/秒、実測に対する予測誤差、律速資源 |
| 目的 | 特定製品の順位付けではなく、能力値を変えたときの上限とボトルネック遷移の分析 |

### 主な結果

| 観点 | 結果 | 意味 |
|---|---|---|
| モデル精度 | 既存実機に対する平均絶対パーセント誤差7.6% | 設計空間探索に使える程度に実測傾向を再現 |
| 実測分散 | 8×H100等の測定で性能変動の90%以上を説明と報告 | 単一のFLOPS指標より複数資源モデルが必要 |
| 高帯域メモリ | HBM3→HBM4→3次元積層DRAMで帯域律速を押し上げられる | ただし速度向上はやがて別律速へ移る |
| 将来上限 | 3D-DRAMと改善された集合通信でも5,000〜10,000ユーザートークン/秒級で逓減 | 帯域だけを増やしても無限には伸びない |
| 10,000超 | 大幅な継続向上にはアルゴリズム変化も必要 | モデル/文脈削減やデコード並列性の改善が共同設計対象 |

### 5つの「避けられない課題」の読み方

論文は5つの非交渉的課題（non-negotiable challenges）としてハードウェア側の制約を整理し、その中心を演算、メモリ容量、メモリ帯域、集合通信に置く。数え上げ自体より重要なのは、一つの資源を改善すると次の資源が律速へ現れるという連鎖である。

たとえば小バッチでは重みストリーミングの帯域が支配しやすいが、多数ユーザーを同時処理するとKV容量が膨らむ。大モデルを複数GPUへ分散すれば容量は確保できるが、今度は集合通信が増える。将来予測ではこの「律速の移動」を見る必要がある。

### 評価上の制約

LIMINALは解析モデルであり、特定ランタイムのスケジューラ、カーネル融合、キャッシュ階層、OSノイズをサイクル精度で再現するシミュレータではない。7.6%は評価した実機・モデル範囲での平均誤差であり、未検証の将来アクセラレータでも同じ誤差になる保証ではない。

また「10,000トークン/秒」は単一ユーザーの逐次生成速度と混同してはいけない。論文は同時ユーザーを含むシステムスループットの設計空間を議論しており、レイテンシ、ユーザー数、モデル規模を揃えず他ベンチマークのtok/sと直接比較できない。

## 既存研究との差

従来の実測ベンチマークは、具体的GPUと具体的モデルの組合せについて高い信頼性を持つ一方、「HBM帯域だけ2倍ならどうなるか」「容量だけ増やしたら何が次の壁か」という未実在設計を直接測れない。LIMINALはそこを解析モデルで補う。

単純な屋根線分析との差は、メモリ帯域と演算だけでなく、KV容量・ユーザー並列性・複数GPU集合通信までLLMデコードの同じ性能式へ入れる点にある。したがって将来ハードウェアの評価では、ピークFLOPSや帯域の単独ランキングではなく、モデル側要求との交点を出力できる。

## 限界・実装状況

- 主対象は自己回帰デコードであり、長大なプリフィルや投機デコード、拡散型言語モデルなど別実行様式には追加モデル化が必要。
- 将来HBM4・3D-DRAMの結果は仮定した能力値に依存し、製品実装の電力・歩留まり・パッケージ制約をすべて含むものではない。
- 平均絶対誤差7.6%は検証集合の値であり、未知のアーキテクチャへ同じ精度を保証しない。
- 解析上の上限へ近づくには、実際のカーネルやランタイムも各資源を高効率で使う必要がある。
- 10,000ユーザートークン/秒超の議論は、モデル規模・ユーザー数・品質条件を固定せず一般的な単一数値目標として使えない。

## 一般的な実装上の含意

LLM推論ハードウェアを選ぶとき、FLOPS、HBM容量、HBM帯域、GPU間通信を個別スペックとしてではなく、対象モデルと同時実行数に対する連立制約として見るべきである。特に量子化で重み容量と帯域を減らした場合、次にKV容量や通信が律速へ出る可能性がある。

同様に、ハードウェアロードマップの改善率をそのままtok/sへ掛けない。現在の支配項を一つ減らした後の「次の壁」をモデル化する方が、将来投資やアルゴリズム共同設計の優先順位を決めやすい。
