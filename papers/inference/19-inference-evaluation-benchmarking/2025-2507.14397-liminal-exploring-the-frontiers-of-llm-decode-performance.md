# LIMINAL: Exploring The Frontiers of LLM Decode Performance

> 「次世代GPUならLLMは何トークン/秒まで速くなるか」を、現在のソフトウェア実装に依存したベンチマークから切り離して考えるための解析モデル。LIMINALはLLMの各演算子を**演算量・読み書きバイト数・同期回数**へ落とし、ハードウェア側の演算性能、メモリ容量・帯域、集合通信遅延を組み合わせてデコードの上限を推定する。結論は単純な「帯域を増やせばよい」ではなく、帯域を上げるほど次に同期が露出し、容量不足はそもそも配置可能な並列構成を制限するため、四要素を均衡させる必要があるというものだ。

## 概要

自己回帰デコードでは、1ステップごとに次の1トークンしか確定できない。このため巨大な行列演算を一度にまとめやすいプリフィルと違い、モデル重みを何度も読み出し、KVキャッシュへアクセスし、テンソル並列（tensor parallelism）で分割した装置間では層ごとに集合通信を繰り返す。

一般的な性能議論では「デコードはメモリ帯域律速」と説明されることが多い。しかしモデルが数百B級になり、文脈が長く、さらに低遅延を求めて64〜128台規模へ強スケーリングすると、単にHBM帯域を増やしても別の律速が前面に出る。LIMINALはこれを、特定のCUDAカーネルやフレームワークではなく、第一原理に近い資源モデルで分析する。

論文の重要な読み方は、LIMINALが「現状のGPU性能を精密に再現するシミュレータ」ではない点である。むしろソフトウェア上の一時的な非効率を取り除いた**到達可能な性能境界**を見積もり、次のボトルネックが何かを調べる道具である。

## 背景：デコード速度を一つの指標だけで説明できない理由

### 1. メモリ容量

モデル重みとKVキャッシュが装置に載らなければ、その装置だけでは推論できない。たとえばLlama 3 405Bでは、64K文脈のKVキャッシュだけで1利用者あたり約15.75GBとなり、32利用者なら約504GBになる。重みも含めると、モデルを載せるだけでも少なくとも約385GB、32利用者・64K文脈では合計約881GBが必要になると論文は示す。

この容量制約は「大容量メモリが欲しい」というだけでなく、必要チップ数を増やし、その結果として通信回数と同期距離も増やす。したがって容量問題は通信問題の入口でもある。

### 2. メモリ帯域

デコードの小バッチでは、行列演算が計算器を飽和させる前に重み読み出しが支配しやすい。高帯域メモリ3e（High Bandwidth Memory 3e; HBM3e）級のシステムでは、Llama 3 405Bの1利用者トークン速度が概ね750トークン/秒付近で頭打ちになるという分析を示す。

帯域を4倍にすると理想的には4倍速くなりそうだが、実際には通信・同期が露出するため利得は約3倍程度へ縮み、128K文脈ではおおむね1,500〜2,800トークン/秒の範囲になる。

### 3. 演算性能

バッチを増やす、MoEの活性専門家が多い、注意計算が長文脈で増える、といった条件では演算側も無視できない。LIMINALは「常にメモリ律速」と固定せず、各演算子で演算時間とメモリ時間を比較する。

### 4. 同期・集合通信

帯域が十分大きくなると、テンソル並列の全削減（all-reduce）などが次の壁になる。64〜128チップで極低遅延に強スケーリングするには、サブマイクロ秒級の同期が重要になる。高帯域の3次元積層DRAMを用意しても、同期が数マイクロ秒かかれば帯域増分を使い切れない。

## LIMINALの性能モデル

### 演算子を「演算・バイト・依存関係」へ分解する

LIMINALはTransformerの各演算子について、必要浮動小数点演算数（floating-point operations; FLOPs）、メモリから読む／書くバイト数、前後の依存関係、並列化で必要になる通信を求める。

モデル固有の名称ではなく、これらの基本量へ還元することで、Llama系の密モデル、グループ化クエリ注意（Grouped-Query Attention; GQA）、DeepSeek-V3の多頭潜在注意（Multi-head Latent Attention; MLA）や専門家混合（Mixture of Experts; MoE）を同じ枠組みで比較できる。

### 1バッチの時間

中核となる近似は、

**バッチ時間 ≈ max(演算時間, メモリ転送時間) + 露出同期時間**

という形である。

演算とメモリアクセスはある程度重ねられるので、完全に足し合わせるのではなく大きい側が本体時間を決める。一方、依存関係のため隠せない集合通信や同期は露出遅延として追加される。

このモデルにより、あるハードウェアで「帯域を2倍にしたらどこまで速くなるか」「チップ数を増やしたら通信で逆に止まるか」「メモリ容量の大きいDRAM系と、高帯域だが低密度なSRAM系のどちらがシステム全体で得か」を探索できる。

### 利用者速度とシステム効率を分ける

論文は、単一利用者から見たトークン速度だけでなく、システム全体のトークン/秒、電力あたりトークン/秒も区別する。

極端なSRAM型構成は1利用者の速度を高くできても、容量密度が低いため多数チップが必要になり、電力・コスト効率でDRAM型へ負ける場合がある。逆にバッチを大きくすると重み読み出しを利用者間で共有でき、1利用者速度を少し犠牲にしてシステム効率を大きく伸ばせる。

## 評価

LIMINALの評価は「提案カーネルが何倍速いか」ではなく、**解析モデルが既存システムをどの程度説明できるか**と、**仮想ハードウェアの設計空間で律速がどう移るか**が中心である。

### 代表的な評価・解析条件

| 項目 | 内容 |
|---|---|
| 主対象 | 自己回帰デコード |
| モデル例 | Llama 3 70B、Llama 3 405B、DeepSeek-V3級 |
| モデル機構 | GQA、MLA、MoEを含む |
| ハードウェア軸 | 演算性能、メモリ容量、メモリ帯域、チップ数、集合通信遅延 |
| メモリ技術 | HBM3/HBM3e級、HBM4、3次元積層DRAM、SRAM型仮想構成 |
| 並列化 | 主にテンソル並列を含む強スケーリング |
| 主指標 | 1利用者トークン/秒、システムトークン/秒、電力効率、容量要件 |
| 検証 | 実ハードウェア測定および高忠実度の装置固有モデルとの比較 |

### 解析モデルの妥当性

論文は既存ハードウェアと比較した全体評価で**平均絶対誤差7.6%**を報告する。一方、個別演算子では理想化の影響が大きい例も明示している。Llama 3 405Bの1×16384×16384の行列ベクトル積では、LIMINALの理想化予測が146µsなのに対し、実H100では736µsだった。著者らはカーネル起動、プリフェッチ不足、L2キャッシュミスなど、モデルが意図的に捨てたソフトウェア／マイクロアーキテクチャ上の非効率が原因と分析する。

この負の例は重要で、LIMINALの値を「今日そのまま得られる速度」と読むべきではない。むしろ**その差が改善可能な実装余地なのか、物理資源の上限なのかを切り分ける**ためのモデルである。

### 代表的な結果

| 観点 | 代表値・傾向 | 解釈 |
|---|---:|---|
| モデル精度 | 平均絶対誤差 7.6% | 第一原理モデルとして既存システムを概ね追従 |
| Llama 3 405B、64K、1利用者 | KV約15.75GB | 長文だけでも容量制約が大きい |
| Llama 3 405B、64K、32利用者 | 重み+KVで約881GB | 容量のため多チップ化が避けにくい |
| HBM3e級 | 約750利用者トークン/秒付近 | 帯域が主律速 |
| 約4倍の帯域 | 約1,500〜2,800利用者トークン/秒級 | 帯域増加は同期で線形には効かない |
| 高帯域・多数チップ | 同期遅延に強く依存 | サブµs級集合通信が重要 |
| さらに先 | 1万トークン/秒級より上で壁 | ハードウェアだけでなくアルゴリズム変更が必要 |

## 「五つの動かせない条件」の意味

論文は将来LLMハードウェアについて、概ね次の論点を避けられないと整理する。

**容量**は重みとKVを載せるための最低条件であり、これを満たせなければチップ数が強制的に増える。**帯域**は小バッチデコードの重み・KV読み出し速度を決める。**同期**は帯域が高速化した後に前面へ出る。**システム効率**は最大速度とトークン/ワット・トークン/ドルが一致しないことを示す。最後に、これらを十分改善しても**逐次デコードというアルゴリズム構造**自体が上限を作る。

そのため、将来1万トークン/秒を大幅に超える目標では、投機的デコード（speculative decoding）のように1回の同期で複数トークンを進める方法、より強い圧縮、同期回数の少ないモデル構造など、アルゴリズム側の変更が必要になるというのが論文の大きな結論である。

## 既存研究との差

実機ベンチマークは現実の性能を測れる一方、あるGPUが遅い理由が帯域不足なのか、カーネル実装なのか、通信ライブラリなのかを分離しにくい。LIMINALは逆に実装詳細を意図的に落とし、物理資源から「速くできたとしてもここで止まる」という境界を見る。

GPU性能予測やサイクル精密シミュレータとも目的が異なる。特定GPUの命令・キャッシュ挙動を再現するのではなく、モデル×ハードウェアの広い組み合わせを素早く走査し、設計の感度と律速遷移を見る。

## 限界

LIMINALはサイクル精密モデルではない。カーネル起動、実メモリアクセスの局所性、キャッシュヒット率、プリフェッチ、ランタイムスケジューリングなどは第一近似では抽象化される。そのため、短い演算やソフトウェア効率が支配する条件では実測との差が大きくなり得る。

また将来技術の帯域・容量・通信遅延は仮定であり、パッケージング、歩留まり、電力、実装可能なネットワークトポロジーが変われば結果も変わる。

さらに主対象は自己回帰デコードであり、プリフィル、分離サービング、要求待ち行列、連続バッチ処理などサービス全体の挙動をそのまま予測するものではない。

## サーベイ上の含意

この論文は、推論最適化を評価するとき「FLOPsを何%減らしたか」だけでは不十分な理由を定量的に示す。量子化で重みを縮めれば容量と帯域は改善するが、通信同期は残る。SSDオフロードで容量を増やせても、PCIe/NVMe帯域がデコードの読み出し経路へ入れば帯域上限が急激に下がる。MoEで活性重みを減らしても、専門家通信と同期が増えれば別の壁へ移る。

したがって新手法を比較するときは、**容量→帯域→演算→同期のどこを動かし、その結果として次に何が律速になるか**まで記述するのが有用である。
