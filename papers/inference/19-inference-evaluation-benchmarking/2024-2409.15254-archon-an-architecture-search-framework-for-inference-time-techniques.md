# Archon: An Architecture Search Framework for Inference-Time Techniques

> 生成・融合・順位付け・批判・検証などの推論時技法の部品とモデルの組み合わせをベイズ最適化で自動探索し、課題と計算予算に合わせた推論アーキテクチャを組むことで、フロンティアモデルを平均15.1パーセント上回りながら推論呼び出しを20パーセント減らした構成探索フレームワーク。

## 概要

推論時技法とは、学習ではなく推論に追加の計算を使うことで大規模言語モデルの出力を良くする工夫の総称である。同じモデルを複数回サンプリングして多数決を取る、複数モデルの回答を融合する、候補を順位付けして上位だけを残す、といった技法はそれぞれ効く場面がある。しかし、どの技法がどの課題とモデルに効くかは一様ではなく、技法同士の相互作用もあるため、組み合わせの空間は巨大になる。従来の代表的な推論システムは人が固定の構成を設計しており、計算予算の使い方にも無駄が残っていた。

本論文のArchonは、推論時技法を部品（生成器、融合器、順位付け器、批判器、検証器、単体テスト生成・評価器）としてモジュール化し、利用可能なモデルの集合と推論呼び出しの予算が与えられた下で、ベイズ最適化により構成を自動探索するフレームワークである。まず技法ごとの効き方と相互作用を指示追従・推論・コーディングの課題群で体系的に測り、単一の技法が全課題を支配しないこと、生成のアンサンブルに批判・検証・融合を重ねると候補の最良値を超える最終回答が得られることを示した。そのうえで探索した最良構成は、o1、GPT-4o、Claude 3.5 Sonnetといったフロンティアモデルを平均15.1パーセント上回り、既存の推論時アーキテクチャより推論呼び出しを20.0パーセント、入力トークンを15.1パーセント、出力トークンを13.5パーセント少なく使った。オープンソースモデルだけの構成でもフロンティアモデルを平均11.2パーセント上回った。

## 問題設定

推論時計算の配分問題は、資源のトレードオフとして表れる。予算である推論呼び出し回数は有限で、サンプリング回数を増やせば多様性は上がるが、融合や検証に回す分が減る。モデルを増やせば視点は増えるが、弱いモデルを混ぜると候補の質が下がり得る。課題によっても最適解が違い、数学やコーディングではサンプリングと検証が効き、指示追従や推論では順位付けと融合が効く。つまり余っているのは「単発の生成では使われない追加計算の余地」で、足りないのは「どの技法へどれだけ配分すべきかという知識」である。人手設計は数通りの構成しか試せず、しかも課題が変わるたびにやり直しになる。本論文の着眼点は、この配分問題をニューラルアーキテクチャ探索と同様の最適化問題として定式化し、ベイズ最適化で効率よく探索することにある。

## 手法のあらまし

入力は対象ベンチマーク、推論呼び出しの予算、利用可能なモデルの集合、利用可能な推論時技法の集合である。Archonの構成は、生成器の層（どのモデルを何回サンプリングするか）、その後に続く順位付け・批判・検証の層、融合器の層といった段階的なパイプラインとして表される。探索アルゴリズムはベイズ最適化で候補構成を提案し、対象ベンチマークで実際に評価し、結果を代理モデルへ戻して次の候補を決める、という循環を回す。出力は対象課題向けに最適化された構成であり、課題横断の汎用構成を探索することもできる。探索に先立ち、論文は各部品の単独効果と組み合わせ効果を広く測っており、その知見が探索空間の設計（どの部品を、どの順序で、何層まで許すか）に使われている。

## 手法

### 1. 推論時技法の部品群 — 生成、融合、順位付け、批判、検証

各部品は入力と出力が定義された言語モデルへの呼び出しである。生成器は指示を受けて候補回答を出す部品で、複数モデルを並列に呼ぶアンサンブルと、同一モデルの複数回サンプリングの両方を担い、モデル数・サンプル数・温度が調整可能である。論文の分析では追加サンプリングは特にコーディングで効き、モデルアンサンブルも性能が単調に伸びる傾向が確認された。融合器は指示と候補集合を受けて、より良い1つ以上の回答へ統合する部品で、全ベンチマークで平均8.9パーセントの改善をもたらし、複数層重ねる効果も課題によっては大きかった（指示追従では3〜4層で勝率が10〜15ポイント伸びる一方、MixEvalでは1〜2ポイントにとどまる）。順位付け器は候補を品質順に並べて上位K件へ絞る部品で、指示追従と推論で特に効き、MT-BenchとArena-Hard-Autoでは無作為選択より10.8パーセント良く、オラクル選択から2.7パーセント以内に収まった。批判器は各候補の長所と短所を列挙して後段の改善材料を出し、70B級10モデルのアンサンブルと融合の構成に加えると平均11.5ポイントの改善があった。検証器は候補の推論過程が妥当かを2段階で判定し、単体テスト生成・評価器はコーディング課題でテストを作って候補を実行検証する。これらの部品は、それぞれが追加の推論呼び出しを消費し、誤った順位付けや検証は良い候補を落とす危険を持つため、組み合わせの良し悪しは実測でしか決まらない。

### 2. 構成の表現とベイズ最適化による探索

探索の対象は、どのモデルを生成器に使うか、各モデルを何回サンプリングするか、順位付けで何件残すか、批判・検証を挟むか、融合器を何層重ねるか、といった離散的な設計判断の組み合わせである。素朴に全探索すると組み合わせが爆発するため、Archonはベイズ最適化を使う。過去に評価した構成とその成績から代理モデルが有望な領域を予測し、まだ試していない有望な構成を次に評価する。これにより、限られた評価予算の中で精度と最大トークン予算のパレートフロンティアを押し上げる構成が見つかる。探索は課題ごとに特化した構成と、複数課題に共通する汎用構成の両方に対応する。追加費用は探索自体の推論呼び出しであり、見つけた構成を使う推論の費用とは別にかかる。失敗条件は、探索に使ったベンチマークと実際の利用課題の分布がずれる場合で、特化構成ほどその危険が大きい。論文が汎用構成も評価しているのはこのためである。

### 3. 技法の効き方と相互作用の分析 — 探索空間の根拠

Archonの探索空間は場当たりではなく、先行する分析に基づく。論文はオープンソースと閉鎖ソースのモデルを使い、技法ごとの効き方を課題カテゴリ別に測った。その結果、単一の技法が全課題を支配することはなく、サンプリングは数学とコーディングに、融合と順位付けは指示追従と推論に効くという棲み分けが見えた。相互作用については、生成アンサンブルへ批判・検証・融合を組み合わせると、融合しない候補群のオラクル最良値を最終回答が上回る場合があることが示された。つまり部品の効果は単純な足し算ではなく、候補の多様性を品質へ変換する後段の部品があるかどうかで変わる。この分析があるため、探索は「サンプリング回数だけを増やす」ような一次元的な調整に陥らず、層の構成そのものを変える探索になっている。

### 4. データと制御の流れ

推論時の1件の処理では、生成器の層が複数モデル・複数サンプルで候補集合を作り、順位付け器が上位へ絞り、批判器と検証器が候補の弱点と妥当性を付け、融合器がそれらを材料に最終回答を合成する、という流れを、探索で決まった層構成のとおりにたどる。探索時の流れはこれを外側から包み、構成の提案、実評価、代理モデルの更新を繰り返す二重のループになっている。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 生成器 | 指示 | 複数モデル・複数サンプリングで候補集合を作る | 候補の多様性と上限品質 | 呼び出し予算を最も消費する |
| 融合器 | 指示と候補集合 | 候補を統合してより良い回答を合成 | 最終品質（平均8.9パーセント改善） | 層を重ねると費用が増え効果は課題依存 |
| 順位付け・批判・検証 | 候補集合 | 上位への絞り込み、弱点の列挙、妥当性の判定 | 候補選択の精度 | 誤判定で良い候補を落とす危険 |
| ベイズ最適化 | 構成と実評価の成績 | 代理モデルで有望な構成を提案し評価を繰り返す | 探索の評価予算 | 探索自体に推論費用がかかる |

## 評価

### まず見るところ

- **結論:** 自動探索した構成は、人手設計の既存システムとフロンティアモデルの単体利用の両方を上回り、しかも推論呼び出しは少なく済んだ。推論時計算は「増やす」より「配分する」ことが重要だという結果である。
- **速度・効率:** 本論文の効率は遅延ではなく予算効率で、同じ品質をより少ない呼び出しとトークンで得る形で測られている。カーネルやサービングの高速化とは別種の効率である。
- **品質:** 融合や批判は出力を書き換えるため無損失ではない。品質の物差しは各ベンチマークの精度や勝率であり、構成はその物差しに最適化されている。
- **評価の強さ／注意点:** 6ベンチマークと多様なモデルで一貫した傾向を示す一方、探索と評価に同じベンチマークを使うため、未知の課題への転移は汎用構成の結果で判断する必要がある。

## 既存研究との差

Mixture-of-AgentsやLLM-Blenderは複数モデルの生成と融合という枠組みを示したが、構成は人手で固定されていた。DSPyは単一モデルのプロンプトを最適化し、ADASやAFlowは単一モデル系のワークフローを自動設計するが、複数モデルと複数技法をまたぐ構成は扱わない。本論文が追加したのは、技法の効き方と相互作用の体系的な実測を土台に、モデル選択・サンプリング回数・絞り込み・検証・融合層数までを含む構成全体をベイズ最適化の対象にした点である。推論時計算の使い方を「設計者の経験」から「探索可能な設計空間」へ変えたことが固有の貢献である。

## 限界・実装状況

- ハードウェア依存条件: 特定ハードウェアの最適化ではなく、APIを含む実モデルの呼び出しが前提である。実時間の遅延はモデル提供側の状況に左右される。
- モデル／ワークロード依存条件: 構成は対象ベンチマークへ最適化されており、課題分布が変われば最適構成も変わる。探索には相応の推論費用が先行して必要である。
- 実装状況: オープンソースのフレームワークとして提示され、新しい技法やモデルを部品として追加できる設計である。本原稿では公式コードのURLを特定できなかったためcodeはnullとした。
- 近似の品質リスク: 融合と批判は生成内容を書き換えるため、検証をすり抜けた誤りが最終回答へ混入し得る。検証器と単体テストはコーディング等の一部課題でしか決定的に働かない。

## 一般的な実装上の含意

推論時計算を使うシステムでは、モデル選びと同じ水準で「追加計算の配分」が品質を決める。サンプリング、順位付け、検証、融合のどれに予算を割くべきかは課題カテゴリで系統的に違うため、代表課題での実測なしに構成を決め打ちしないことが重要になる。他の推論基盤でも、部品を差し替え可能な形でモジュール化し、構成を自動探索できるようにしておけば、新しいモデルや技法が現れたときに全体を作り直さずに最適構成を更新できる。逆に、探索に使った評価と実運用の課題分布のずれは、そのまま構成の陳腐化として現れるため、探索は一度きりではなく運用の中で繰り返す前提で設計すべきである。
