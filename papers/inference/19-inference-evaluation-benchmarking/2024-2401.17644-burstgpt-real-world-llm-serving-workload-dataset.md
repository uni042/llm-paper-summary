# BurstGPT: A Real-world Workload Dataset to Optimize LLM Serving Systems

> BurstGPTはAzure OpenAI GPTの10.31 million要求・213日分の実トレースを公開し、到着の集中、会話間隔、応答長、失敗を含む現実的な評価負荷を提供する。

## 概要

大規模言語モデル（LLM）のサービング基盤は、要求をどの順番で処理するか、キー・バリュー（KV）キャッシュをどう保持するか、プリフィルとデコードをどう分けるかによって性能が変わる。ところが、新しい方式の評価では、要求が一定間隔で到着し、入力長や応答長も安定している合成負荷が使われることが多い。実サービスの要求は短時間に集中したり、会話の続きを含んだり、モデルや機能によって入力・出力長が大きく違ったりする。負荷が単純すぎると、特定条件に合わせた最適化が実運用でも効くように見え、導入後に待ち時間や失敗率が悪化するおそれがある。

BurstGPTは、この評価上のずれを減らすため、地域別Azure OpenAI GPTサービスから得られた10.31 million要求、213日分のトレースをまとめたデータセットである。論文は単に平均到着率や平均トークン長を示すのではなく、要求の集中、会話の連続性、モデル応答長、サービスの失敗を含む負荷の特徴を記述する。これにより、研究者は要求到着を再生し、負荷変動を保った状態でサービング方式を比較できる。

## データと分析の構成

データセットは、実際のサービスで観測された要求の時刻と処理特性をもとに構成される。論文は利用者、モデル、サービスの三つの側面から負荷を捉える。利用者側では、要求がどれほど集中して到着するかと、会話内で要求が何回続き、どの程度の間隔を空けるかを見る。モデル側では、入力と応答のトークン長を調べ、自己回帰生成で応答長がサービス時間へ与える影響を扱う。システム側では、会話サービスとAPIで観測された失敗を含め、処理要求が多い時間帯とサービス可用性の関係を分析する。

第一の特徴は、到着の集中度がサービスやモデル種別ごとに異なることである。平均要求数だけでは、短い時間窓に要求が何件重なって届くかは分からない。到着に山と谷があると、平均負荷に合わせた固定資源構成でもピーク時には待ち行列が伸びる。BurstGPTは、実測した時間系列を使ってこの集中性を保持するため、定常到着モデルでは見えにくい瞬間的な混雑を再現できる。負荷を平均化してから再生すると、この特性が失われるため、評価では元の到着時刻を保つことが重要となる。

第二の特徴は、要求が独立した一回限りの呼出しだけではない点である。会話サービスでは、前の応答を受けて次の要求が来る。会話内の呼出し数や間隔が分かれば、KV状態をいつまで保持するか、再入場までどれくらい待つかを評価する材料になる。同じ会話の要求をばらばらの独立要求として扱うと、文脈再利用やセッション状態を考慮する最適化を正しく比較できない。BurstGPTは会話パターンを負荷の一部として分析し、単一要求単位のベンチマークでは捉えられない再利用機会と待ち時間を示す。

第三の特徴は、応答長が一定ではなく、要求やモデルによって分布が異なることである。デコードはトークンを順番に生成するため、出力が長い要求はGPUを長く占有し、同じバッチにいる要求の完了時刻にも影響する。入力長だけを揃えた評価では、出力長の偏りに由来する待ちやスループット変化を見落としうる。論文は応答長の統計的な関係を分析し、サービング方式の評価に現実的な生成量が必要であることを示している。

第四の特徴は、失敗や利用可能性を含めたことである。サービスの負荷が高いと、単に遅くなるだけでなく、要求失敗や応答の欠落が起きる場合がある。正常に完了した要求だけで性能を測ると、負荷の強い時間帯を除外してしまい、実際の信頼性を過大評価することになる。BurstGPTは会話とAPIサービスにおける失敗を分析対象に含め、要求の需要とサービスの制約を同じ実測トレースの中で考える。

## 示された知見と使い方

著者らのデモ評価は、負荷の頻繁な変動を含めることで、効率、安定性、信頼性の低下が現れることを示す。また、KVキャッシュ管理、要求スケジューリング、プリフィル・デコード分離といった最適化は、一つの負荷に合わせただけでは別の現実的負荷へ一般化しない場合があると指摘する。つまり本論文の主要な結果は、特定サービング方式の勝敗というより、負荷仮定が異なると評価結論自体が変わりうるという測定上の発見にある。

利用時には、トレースの到着時刻や要求長を保ったまま再生し、比較する方式に同一の要求集合を与える。要求数や平均到着率だけを一致させても、短時間集中や会話間隔が異なれば同条件とは言えない。性能評価では、スループットと平均遅延に加え、遅延の裾、失敗、混雑時の回復を確認する必要がある。長い応答の比率や会話間隔を変えた感度分析を行えば、どの特性が方式の優劣を変えるのかを分けて考えられる。

## 限界と適用範囲

このデータセットは特定時期のAzure OpenAI GPTサービスから採取されたもので、他社サービス、社内専用モデル、別地域の利用者構成をそのまま代表するわけではない。サービス構成や利用者の行動は変化するため、BurstGPTを現在の本番負荷の完全な代替とみなすのではなく、現実的な変動を含む公開ベンチマークの一つとして使うべきである。論文で観測されたモデルやサービス区分の特徴を、すべてのLLMへ一般化することもできない。

公開トレースは元サービスの内部実装、GPU配置、スケジューラ状態をすべて記録するわけではない。要求が到着した時刻やトークン長から、遅延の原因を単一のシステム要因へ割り当てることには限界がある。また、個人情報保護のため元の会話内容と結び付く詳細な本文を公開するものではないので、プロンプト意味内容によるモデル動作差を再現する資料ではない。したがって、サービングの到着・長さ・会話構造を評価する用途に適するが、意味品質や内容依存の推論コスト評価を置き換えるものではない。

## まとめ

BurstGPTは、Azure OpenAI GPTサービスの10.31 million要求、213日分を収録し、到着の集中、会話の反復、応答長、失敗という実サービス負荷の特徴を提供する。著者らは、現実的な変動を含めるとサービング最適化の効率や安定性が崩れ、KV管理やスケジューリングなどの一般化が保証されないことを示す。この研究の価値は、単一の新しいサーバー設計ではなく、評価負荷を現実に近づけ、方式の頑健性を測り直すための公開データ基盤にある。
