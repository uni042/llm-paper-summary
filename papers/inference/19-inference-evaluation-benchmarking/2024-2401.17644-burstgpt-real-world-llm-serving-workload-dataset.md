# BurstGPT: A Real-world Workload Dataset to Optimize LLM Serving Systems

> Azure OpenAI GPTサービスの1031万件・213日分の実トレースと再生基盤BurstGPT-Perfを公開し、平均RPSだけを揃えた合成負荷では見えないバースト、会話間隔、応答長、失敗がサービング評価の結論を変えることを示す。

## 概要

大規模言語モデル（LLM）のサービング研究では、スループットや遅延を比較するために要求列が必要になる。ところが、一定の要求毎秒数（Requests Per Second; RPS）や単純な確率分布から作った合成負荷では、実サービスにある「短時間の集中」「会話の再入場」「入力と応答の長さの偏り」「混雑時の失敗」が薄まる。同じ平均RPSでも、要求が均等に来るか短時間へ集中するかで、待ち行列、KVキャッシュ容量、バッチ構成、失敗率は大きく変わる。

BurstGPTは、地域別Azure OpenAI GPTサービスから取得した1031万件、213日分のトレースを公開し、LLMサービング固有の実負荷を評価へ持ち込む研究である。v5では3,000人超の利用者を持つ地域サービスから、要求開始時刻、入力・応答トークン長、API/会話サービス種別、ChatGPT/GPT-4/GPT-4Vのモデル種別、失敗要求を記録する。内訳としてAPIはChatGPT 869万件、GPT-4 95万件、会話サービスはChatGPT 30万件、GPT-4 16万件を含む。

論文はデータセットだけでなく、トレースを対象システム規模へ拡大・縮小して再生するBurstGPT-Perfも提供する。要求到着をガンマ分布、要求長をZipf分布としてモデル化する経路と、元トレースの時刻をRPSに合わせて伸縮する経路を用意し、平均値だけでなく瞬間的な遅延・スループット・失敗率・揺らぎを測る。

デモ評価では、同じ平均RPSへ揃えた非LLMクラウド負荷MAF2よりBurstGPTの方がバースト性が強く、vLLM上の資源占有とKV圧力が増える。また、会話負荷で有利なスケジューリングがAPI負荷では同じ優位性を示さない。つまり本論文の主要結果は「特定のランタイムが最速」という順位ではなく、現実的な負荷形状を変えると最適化の評価結論自体が変わるという点にある。

## 問題設定

LLMサービングの負荷は、通常の軽量クラウド関数と同じ尺度では捉えにくい。論文例では、Microsoft Azure Functions系負荷MAFの平均RPSが1.64である一方、BurstGPTのChatGPT会話サービスは0.019 RPS、APIサービスは0.21 RPSと低い。しかし、RPSが低いから負荷が穏やかとは限らず、LLM側は短時間の集中度が高い。さらに1要求当たりの計算量が入力長・出力長に強く依存する。

プリフィル計算は入力系列長の増加に対して重くなり、デコードでは出力トークン数だけ反復処理が続く。同じ100件でも、短い入力・短い出力が分散して来る場合と、長い入力・長い出力が一斉に来る場合ではGPU滞在時間とKVキャッシュ占有が違う。そのため「平均要求数だけを一致させる」比較では、スケジューラやKV管理の頑健性を誤って評価しうる。

会話サービスでは同一セッションが時間を空けて戻るため、KVをいつまで保持するかも重要になる。BurstGPTでは35%超の会話が1要求で終了する一方、中央値は2要求、75%は4要求以下であり、要求数が多い会話ほど長い間隔を複数含む傾向がある。これは「全会話のKVを長く保持する」ことも「毎回すぐ捨てる」ことも一律には最適でないことを示す。

さらに失敗要求を捨てて成功例だけを評価すると、混雑時に最も重要な信頼性低下を見落とす。BurstGPTではChatGPT会話サービスの平均失敗率が5%を超えると報告され、短時間のバースト変化がメモリ圧力と失敗率の急増へつながる例を示す。

## データセットとベンチマーク

### 1. 利用者側: 長期周期と短期バーストを分けて記録する

会話サービスは平日・営業時間に増える周期性を持つ一方、APIサービスは自動処理を含むと考えられる不規則な集中が目立つ。短期バーストは20分ごとにガンマ分布でモデル化し、形状パラメータと率/尺度パラメータの変化を追う。単一の固定分布ではなく、時間帯によって分布自体が変わる点が重要である。

BurstGPT-Perfでは、元トレースの時刻を倍率で伸縮するRPSスケーリングと、ガンマ分布のパラメータから新しい到着列を作るモデル化スケーリングを用意する。後者では対象GPUのKV使用率が30〜40%程度になる初期到着率へ合わせ、その後に元トレースの変動を再現できる。

### 2. 会話側: 要求回数と再入場間隔を残す

同一会話内の要求回数と間隔を分析することで、KVキャッシュを保持すべき時間の分布を評価へ持ち込める。長い会話ほど長い待ち時間区間も増えるため、単純な「直近アクセス順」だけで状態を管理した場合に、将来再利用される会話を早く追い出す可能性がある。

この情報はKVオフロード、接頭辞キャッシュ、状態復元方式を比較するときに重要である。独立した単発要求へ分解してしまうと、再利用可能な状態が存在するという実サービスの条件を失う。

### 3. モデル側: 入力長だけでなく応答長分布も扱う

BurstGPTは入力と応答のトークン数を記録する。ChatGPTの入力長分布と、ShareGPT由来のプロンプトを与えたLlama-2-13B-chatを比較すると、入力側が似ていても応答長分布は異なる。LLMサービングではモデル自体が出力長を決めるため、合成負荷側で固定出力長を与えるとデコード占有時間を歪める可能性がある。

BurstGPT-Perfでは要求長をZipf分布に合わせてプロンプトプールからサンプリングし、応答長はモデル自身に生成させる。これにより、入力到着とモデル生成特性を別々に固定し過ぎない。

### 4. システム側: 成功率・遅延揺らぎまで測る

ベンチマークは平均トークン遅延と平均スループットだけでなく、瞬間値、トークン遅延の標準偏差、失敗率を記録する。これにより、平均性能が同じでもピーク時に失敗が集中する方式や、遅延が大きく揺れる方式を区別できる。

ワークロード生成器はプロンプトサンプラー、プロンプトプール、同時実行生成器、非同期HTTPクライアントから構成され、指定長の要求を実際の時系列として推論サーバーへ送る。単なるオフライン統計ではなく、サービング系を駆動する再生基盤まで含む。

## 評価

### 評価条件

| 項目 | 条件 |
|---|---|
| トレース | 1031万件、213日、3,000人超の地域Azure OpenAI GPT利用 |
| 記録項目 | 開始時刻、入力/応答トークン長、API/会話種別、モデル種別、失敗 |
| 実機評価 | NVIDIA A800 / A6000 GPUサーバー |
| モデル | Llama-2-13B-chat、感度実験ではLlama-2-7B-chatも使用 |
| ランタイム | vLLM |
| プロンプトプール | ShareGPT等 |
| 主指標 | 平均・瞬間の失敗率、トークン遅延、遅延揺らぎ、スループット |
| スケジューラ比較 | FCFS、短要求優先（SRF）、長要求優先（LRF） |
| 負荷比較 | BurstGPT、MAF2、会話/API別トレース、ガンマ/Zipfパラメータ感度 |

### 代表的な結果

| 条件 | 指標・結果 | 何が確認できるか |
|---|---|---|
| BurstGPT vs MAF2、同じ0.326 RPS、6126秒 | BurstGPTの方が平均遅延・スループットとも高く、KV使用と失敗が強く変動 | 平均RPSを合わせてもバースト形状が違えば資源圧力は同じにならない |
| 会話 vs API負荷 | 会話で得られたスケジューラの優位性がAPIでは維持されない | スケジューリング最適化は実負荷種別を越えて一般化しない場合がある |
| バースト性パラメータ感度 | 小さな分布変化で要求失敗が急増する条件を確認 | 平均遅延だけでは信頼性劣化を見逃す |
| 会話統計 | 35%超が1要求で終了、中央値2、75%が4要求以下 | KV保持・退避の寿命設計には会話再入場分布が必要 |
| ChatGPT会話サービス | 平均失敗率が5%超 | 実負荷評価では成功要求だけでなく失敗を含める必要がある |
| 負荷予測 | 10分粒度は1分粒度よりNMSEが58%低い | 細粒度な予測ほど難しく、スケール制御の反応速度と予測精度にトレードオフがある |
| PD分離プロトタイプ | 6:00にP:D比を2:6から6:2へ変更してgoodput改善 | 固定プリフィル/デコード比では時間変動へ追従できない |

「スループットが高い」だけを良い結果と解釈してはいけない。BurstGPT対MAF2では負荷そのものが重くなり、GPUが多く仕事をしている結果としてスループットが高く見える。同時に遅延・KV圧力・失敗も増えるため、効率、安定性、信頼性を一緒に読む必要がある。

また、論文のスケジューラ比較は特定方式の普遍的な順位付けを目的としていない。会話負荷とAPI負荷で順位が変わること自体が、評価負荷の選択が結論に影響する証拠として使われている。

## 既存研究との差

従来のLLMサービング研究は、独自の合成到着列、ShareGPTのような会話データ、あるいはAzure Functionsのような非LLMクラウドトレースを用いることが多かった。これらは入力本文や要求長を提供できても、LLM固有の短期バースト、モデル応答長、会話再入場、失敗を同じ時系列で含まない。

BurstGPTは「より大きなベンチマーク」ではなく、負荷の多次元性を保つ点が差である。さらにBurstGPT-Perfを付け、対象システム規模へRPSや分布を調整しながら時系列特性を残すことで、データセットをそのままサービング評価へ接続している。

## 限界

- 収集元は一つの地域Azure OpenAI GPTサービスであり、全世界のOpenAI利用、他社API、社内LLMを代表するものではない。
- v5は213日へ拡張されているが、利用パターンは時代・料金・モデル・アプリケーションの変化で変わる。現在の本番負荷そのものとして扱うべきではない。
- プライバシー独立のメタデータを中心に公開しており、元の意味内容は再現しない。内容依存の推論難度や推論品質評価には使えない。
- トレースは内部GPU配置や全てのサーバー状態を記録しないため、観測された失敗の原因を単一資源へ厳密に同定する資料ではない。
- スケーリングで平均RPSを対象環境へ合わせても、モデル・ハードウェアが変われば同じガンマ/Zipfパラメータが同じ利用率を生むとは限らない。
- デモ評価はA800/A6000、Llama-2系、vLLMを中心とする。最新ランタイムや異なるモデルでの絶対性能は再測定が必要である。
