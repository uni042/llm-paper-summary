# MoE++: Accelerating Mixture-of-エキスパート Methods with Zero-Computation エキスパート

> 通常のFFN エキスパートに加えて、何も出力しない・入力をそのまま返す・学習済み定数を返す軽量エキスパートをルーティング候補へ入れ、トークンに応じて実際のFFN計算数を減らすMoE。

## 概要
MoE++は、通常のFFN エキスパートだけでなく、**大きな行列計算をほとんど必要としない3種類のエキスパート**をルータ候補へ最初から組み込む異種MoEである。

3種類は`zero expert`、`copy expert`、`constant expert`で、それぞれ「何も足さない」「入力をそのまま通す」「学習可能な定数を返す」という安価な経路を担当する。

AdaMoEのnull エキスパートと似ているが、MoE++は単一の「計算しない経路」だけでなく、**計算を省く時にも複数の代替出力を持たせ、学習中に役割分担させる**点が違う。

## 手法のあらまし

### 1. 3種類の`Zero-Computation Experts`

| エキスパート | 出力 | 狙い |
|---|---|---|
| Zero | 0相当 | そのMoE計算を実質skip |
| Copy | 入力をそのまま返す | FFNを通さず情報を次へ渡す |
| Constant | 学習可能な定数vector | 入力に依存しない軽い補正 |

通常FFN エキスパートと同じルータ候補に入るが、大きなFFN matrix multiplyを必要としない。

このためトークンによって「FFNを2個使う」「FFN 1個 + copy」「zeroだけ」といった異なる実計算量を学習できる。

### 2. AdaMoEとの違い

AdaMoEのnullは基本的に「計算しない枠」を作ることが中心だが、MoE++ではzero / copy / constantの**出力意味を分ける**。

特にcopy エキスパートは情報をそのまま次へ渡せるため、単純に出力を0にするより表現を壊しにくい。constant エキスパートは入力を見ずに学習済みの一定vectorを足す。

したがって「FFNをしない」選択の中にも複数の代替表現を持たせている。

### 3. `τ`：通常FFNへ回すトークン量を調整する

論文の`τ`は、計算不要エキスパートに対して**通常FFN エキスパートへどれくらいトークンを流せるようにするか**を調整する主要parameterである。

`τ`を小さくすると計算不要エキスパートへ流れやすくなり計算は減るが、品質を落としやすい。大きくすると通常FFNの利用が増えてvanilla MoEへ近づく。

標準設定はおおむね`τ=0.75`。

### 4. 通常FFNと軽量エキスパートで受け入れ可能なトークン数を分ける

通常FFN エキスパートとzero / copy / constantは計算costも役割も違うため、全エキスパートへ同じトークン上限を与えるのは不自然である。

MoE++は`τ`を使ってFFN側と計算不要側で、受け入れられるトークン数の上限を別々に決める。

これにより軽量な経路を十分使いつつ、FFN側へトークンが集中し過ぎて一部トークンを処理できなくなることを抑える。

### 5. `Gating Residual`：前層のルーティング傾向を次層へ渡す

各層でルータを完全に独立にすると、計算不要エキスパートとFFN エキスパートのどちらを選ぶかが層ごとに不安定になる。

MoE++の **gating residual** は前層のルータ出力を次層のルータ判断へ加え、過去のルーティング傾向を引き継ぐ仕組みである。

hidden stateを足す通常のresidual connectionではなく、**ルータの判断情報そのものを次層へ渡す**のがポイントである。

### 6. 計算不要エキスパートは各GPUへ複製しやすい

通常FFN エキスパートは大きな重みを持つためエキスパート parallelでGPU間配置が必要だが、zero / copy / constantは極小なので全GPUへ複製しやすい。

そのため軽量エキスパートを選んだトークンは、別GPUへトークンを送ってremote FFNを実行する通信を減らせる可能性がある。

軽量エキスパートは巨大なFFN重みを持たないため、エキスパート並列で通常FFNのようにGPUごとへ分散配置する必要が小さい。各GPUへ複製しておけば、その経路を選んだトークンはローカルでzero / copy / constant処理を完了でき、全対全通信（all-to-all communication）へ参加するトークン数も減らせる。したがってMoE++の利得はFFN FLOPs削減だけではなく、分散MoEで通信と特定FFNへの負荷集中を減らせる点にもある。ただし実際のエンドツーエンド利得は、軽量経路を選ぶ割合と通常FFN側の通信パターンに依存する。

### 7. 既存MoEへの後付けではない

MoE++は計算不要エキスパートを含んだ状態で100B〜1T トークン規模のtrainingを行う。

したがって既存Mixtralへ実行時だけ差し込むキャッシュ / 枝刈り手法ではなく、**architectureとtraining方法を一緒に変える適応型 computation**である。

この学習が必要なのは、zero / copy / constantのどれを選べば表現を壊さずFFN計算を省けるかが、トークンと層によって異なるためである。zeroはMoE出力を加えない、copyは入力情報をそのまま残す、constantは入力に依存しない補正を加えるので、三者は同じ『計算しない経路』でも機能が違う。学習時から通常FFNと同じルータ候補へ置くことで、単純なトークンには軽量経路、変換が必要なトークンには通常FFNを割り当てる役割分担をモデル側に形成させる。推論時だけ通常FFNを軽量経路へ置き換える方式では、この役割分担を学んでいないため同じ品質は期待できない。

## 評価

### まず見るところ
- **結論:** zero / copy / constant エキスパートを学習時から組み込むと、標準設定では品質を維持しながらエキスパート forwardを2割前後短縮できる。
- **実速度:** 1B / 2B / 7Bでエキスパート forward 21.8〜27.8%改善。通常FFNへ回すトークン量をさらに減らす設定ではもっと速いが品質低下が増える。
- **品質:** 標準`τ=0.75`ではvanilla MoEと同等以上の平均score。
- **適用性:** 既存modelへ後付けする方式ではなく、専用trainingが必要。
- **注意点:** 32×A100でのエキスパート forward中心評価で、consumer/オフロード環境のエンドツーエンド 遅延ではない。

| Model | Vanilla | MoE++ | 改善 | 平均task score |
|---|---:|---:|---:|---:|
| 1B | 610.9 ms | **500.3 ms** | **22.1%** | 45.3 → **46.1** |

| 7B | 1859 ms | **1455 ms** | **27.8%** | 52.3 → **53.1** |

標準設定では速度と品質を同時に改善している。

### `τ`を強く下げた場合

| Model | 設定 | スループット改善 | 平均score |
|---|---|---:|---:|
| 1B | τ=0.10 | **111.2%** | 45.8 |
| 2B | τ=0.10 | **63.5%** | 46.3 |

標準`τ=0.75`より速いが品質は下がるため、速度と品質のtrade-offになる。

### Zero / Copy / Constantの要素別評価

1B / 100B-トークン設定で全要素を使う構成は平均47.7。gating residualなし47.5に対し、あり47.7と小幅改善する。

constant エキスパート数を増やし過ぎても性能が反落し、軽量エキスパートの種類・数を増やせば単調に良くなるわけではない。

### 評価上の制約

- 既存modelへ追加するだけでは使えない。
- `τ`と各エキスパートへ許すトークン数の設定へ品質が依存する。
- 一部エキスパートへトークンが集中し過ぎると処理しきれないトークンが出る。
- 主速度指標はエキスパート forwardで、full serving 遅延ではない。
- edge / SSD / エキスパート キャッシュ条件は直接評価しない。
