# Dynamic Expert Sharing: Decoupling Memory from Parallelism in Mixture-of-Experts Diffusion LLMs

> 並列dLLMのトークン群で専門家コア集合を共有し、MoEのユニーク重み転送を約55%削減しつつ相対精度99.5%を維持、MoE層遅延を最大38%短縮する。

- **著者・所属**: Imperial College London; Samsung AI Center, Cambridge
- **公開**: arXiv:2602.00879v1

## 概要
拡散大規模言語モデル（diffusion Large Language Model; dLLM）の並列復号では、複数トークンが同時に独立ルーティングされるため、混合専門家（Mixture-of-Experts; MoE）のユニーク専門家数がブロック長とともに増える「エキスパート explosion」が起き、HBMからオンチップメモリへの重み転送が律速になる。動的 エキスパート Sharing（DES）は、トークン単位の枝刈りではなく並列ブロック全体で共有する専門家コア集合を動的に選び、その集合内で各トークンを再ルーティングする。DES-Seqとルータ重みを集約するDES-Voteを提案し、LLaDA2.0-Mini 16BとLLaDA-MoE-7BをB200上で評価した。DES-VoteはLLaDA2.0-Miniで平均相対精度99.5%を維持しながら平均ユニーク専門家数を84から38へ約55%削減し、MoE層遅延を最大38.0%、総GPUカーネル時間を8.2〜14.3%短縮する。

DESは最適化対象を各トークンの局所的な専門家削減から、並列ブロック全体のユニーク専門家集合へ移す。共有コア集合を先に決め、その内部だけで各トークンのTop-Kを取り直すことで、並列トークン数Nから重みフェッチ上限を切り離す。DES-Voteは各トークンの局所Top-K外をマスクしたルータ重みをシーケンス全体で合算し、総サリエンシー上位M_core専門家を共有集合にする。
## 問題設定
dLLMは複数のマスクトークンを同時に処理して自己回帰復号の逐次メモリ律速を緩和するが、MoEを組み合わせると各並列トークンが独立にTop-K専門家を選ぶため、1ブロックで必要になるユニーク専門家の和集合が急増する。論文のモデルではMoE層遅延を、専門家重みのフェッチ費用bとトークン計算費用aを用いて、b×ユニーク専門家数+a×N×Kと表す。現代GPUでは重みフェッチ側が支配的になりやすく、既存のエキスパート skippingでトークン当たり計算を減らしても、他トークンが同じ専門家を使えばその重みは結局ロードされる。したがって並列度を上げるほどHBM-to-SRAM転送が増え、MoE FFNが再び推論律速になる。
## 新規性
DESは最適化対象を各トークンの局所的な専門家削減から、並列ブロック全体のユニーク専門家集合へ移す。共有コア集合を先に決め、その内部だけで各トークンのTop-Kを取り直すことで、並列トークン数Nから重みフェッチ上限を切り離す。DES-Voteは各トークンの局所Top-K外をマスクしたルータ重みをシーケンス全体で合算し、総サリエンシー上位M_core専門家を共有集合にする。
## 手法
### 手法のあらまし
処理は各MoE層ごとに、通常ルータが並列ブロックNトークンそれぞれについて全M専門家のスコアを計算するところから始まる。通常方式なら各トークンが独立に上位Kを選び、その和集合の全重みをHBMから読み込むが、DESは専門家計算へ入る前にシーケンスレベルの合意段階を挿入する。DES-Seqでは各トークンの局所上位k（k<K）を取り、それらの和集合を共有コア集合Cとする。DES-Voteでは各トークンについて元の局所Top-K外のルータ重みをゼロにしてノイズを除き、残った重みを専門家ごとに全Nトークンで加算する。その総サリエンシーの上位M_coreだけをCに残すため、コア集合サイズを直接制御できる。

Cが決まると各トークンは全M専門家ではなくCだけを候補として元のK個を改めて選び、選択したゲート重みをモデル所定の活性化関数で再正規化する。その後K専門家を実行して出力を加重和し、通常のMoE層と同じ形のトークン出力を後段へ渡す。この二段階化により、計算項N×Kは維持しつつ、重みフェッチ項のユニーク専門家数を全トークンの独立選択の和集合から|C|へ置き換える。共有済み専門家を複数トークンが再利用するので、同じ重みを一度オンチップへ持ち込んだ後の追加計算は比較的安い。さらにDES-Voteの選択処理そのものが律速にならないよう、softmax、局所Top-K、マスク、重み集約など12演算相当を第1融合GPUカーネルへまとめ、レジスタ計算とatomic更新で専門家サリエンシーを作る。第2カーネルがランキング閾値から最終マスクを確定し、そのマスクを制約付き局所ルーティングへ渡す。

### 共有コア集合制約
各MoE層で並列ブロックの全トークンが利用可能な専門家集合Cを専門家実行前に共有する。通常は各トークンの独立Top-Kの和集合がブロック長Nとともに膨らみ、どれか1トークンが使う専門家は重みロードが必要になる。DESでは候補をCへ制限するためユニーク専門家数を|C|以下へ明示的に抑えられる。重要なのは各トークンの活性数K自体を減らさない点で、各トークンはC内からK個を選び直し、ルータ重みを再正規化して通常と同数の専門家出力を合成する。

同じCの専門家は並列トークン間で再利用されるため、重みフェッチ回数を増やさず計算を使って精度を回復できる。論文の同一ユニーク集合サイズの比較でも、トークン当たりKを8から4へ減らすと精度が下がり、共有集合内での再活性化が有効であることを示す。したがってDESの中心は計算を極端に疎化することではなく、メモリ転送の対象集合だけを共有によって小さくする点にある。

### DES-Seq
DES-Seqは共有集合を作る最も単純な方法で、各トークンの通常ルータ順位から上位k専門家だけを一旦選び、その集合を全Nトークンについて和集合する。kは元の活性数Kより小さくし、各トークンが特に重要とみなした候補だけをCへ持ち込むことで、独立Top-Kの完全な和集合より専門家数を減らす。Cの作成後は各トークンがC内から元のK個を選び直すので、最初のkは最終的なトークン当たり計算数ではなく、共有候補集合を形成するための局所予算である。

一方、トークンごとに同じkを割り当てるため、あるトークンの2位専門家が別トークンの3位専門家よりはるかに重要でも区別できない。また和集合方式なのでCの大きさを直接固定できず、重複の少ないブロックでは集合が膨らむ。この弱点がDES-Vote導入の動機になっており、実験でも同程度の専門家フットプリントではDES-Voteの方が高い相対精度を示す。

### DES-Vote
DES-Voteは局所順位だけでなくルータ重みの大きさを使って、シーケンス全体で専門家を投票選択する。まず各トークンの元のTop-Kに入らない専門家の重みをマスクし、低確率専門家が多数積み上がって投票を汚すのを防ぐ。次に残った重みを専門家ごとにNトークンで加算し、総サリエンシーV_iを得る。その上位M_core専門家をCに採用するため、共有集合サイズを予算係数betaで直接決められる。

重み付き投票なので、一部トークンで極めて重要な専門家は、他トークンの低順位候補より強く残りやすい。Figure 4ではこの選択がDES-Seqより元のTop-K専門家の再現率を高め、再構成損失を下げる。主表でも同等以下のユニーク専門家数でDES-Seqより平均相対精度が0.6〜2.3ポイント高く、シーケンス全体の重要度を集約する利点が確認される。

### 融合コア集合選択カーネル
DES-Voteを素朴なPyTorch演算列で実装すると、softmax、Top-K、マスク、reduction、最終選択など多数の小カーネルを順次起動し、中間テンソルをHBMへ書き戻すため、専門家重み転送を減らしても選択処理が新たなオーバーヘッドになり得る。著者はこの経路を専用GPU実装へ融合し、第1カーネルでトークン単位softmaxとTop-Kフィルタ、重み付き専門家集約をまとめる。中間値をレジスタ中心に保持し、atomic操作でグローバルな専門家サリエンシーへ加算する。

第2カーネルは得られた集約値をランキング閾値と比較して最終専門家マスクを生成し、そのマスクを後続の制約付きルーティングへ渡す。これにより12カーネル相当を2つへ削減し、論文のB200測定ではコア集合選択をPyTorch基準より6倍高速化する。選択処理の固定費を抑えることで、専門家重み転送の削減をMoE層最大38.0%の遅延短縮へ結び付ける。

### 全体のデータ／制御の流れ
DESは専門家重み自体を圧縮・枝刈りするのではなく、各並列ステップで実際にHBMからオンチップへ持ち込むユニーク専門家集合を制御する。特にメモリ帯域律速のB200実測でMoE層遅延がユニーク専門家数とほぼ線形に増える観測を利用する。

共有集合内では各トークンのKを維持できるため、同じ総ユニーク専門家数でもK=8からK=4へ減らすと精度が落ちるというアブレーションに対し、共有済み専門家を再利用して計算を増やすことは追加重み転送をほぼ増やさず精度回復に使える。結果としてDESは並列度を上げた際のメモリトラフィック増加を抑え、ブロックサイズを主に生成品質と並列効率の観点から選びやすくする。

## 主要結果
LLaDA2.0-Mini 16BではVanillaの平均ユニーク専門家数84・MoE単層メモリ0.98GBに対し、DES-Vote beta=0.15は38・0.45GBまで削減しながら平均相対精度99.5%を維持する。より厳しいbeta=0.10では25専門家・0.29GBで96.4%。LLaDA-MoE-7BではVanilla 59専門家・0.35GBに対しDES-Vote beta=0.6が38・0.22GBで97.6%、beta=0.4が25・0.15GBで96.0%。B200実測ではMoE層遅延を最大38.0%/31.9%削減し、総GPUカーネル時間を8.2〜14.3%改善する。

- LLaDA2.0-Mini平均相対精度 / 99.5% (比較対象: Vanilla 100%; 条件: DES-Vote beta=0.15, block length 32) — 平均ユニーク専門家数を84から38へ約55%減らしてもほぼ精度を維持。

- LLaDA2.0-Mini MoE単層メモリ / 0.45 GB (比較対象: Vanilla 0.98 GB; 条件: DES-Vote beta=0.15) — ユニーク活性専門家パラメータのメモリ量を約54%削減。

- LLaDA-MoE-7B平均相対精度 / 97.6% (比較対象: Vanilla 100%; 条件: DES-Vote beta=0.6) — 平均ユニーク専門家数59から38、メモリ0.35GBから0.22GBへ削減。

- MoE層遅延削減 / 最大38.0%（LLaDA2.0-Mini）、31.9%（LLaDA-MoE-7B） (比較対象: Vanilla; 条件: single NVIDIA B200) — 共有コア集合によるHBM重み転送削減が実カーネル時間へ反映。

- 総GPUカーネル時間改善 / 8.2–14.3% (比較対象: Vanilla; 条件: single NVIDIA B200) — attention等の非MoE固定費を含めてもエンドツーエンド GPU カーネル timeが改善。

- コア集合選択高速化 / 6x (比較対象: PyTorch selection implementation; 条件: custom fused カーネル) — 12演算相当を2カーネルへ融合しDES自体の選択オーバーヘッドを抑制。

### 負の結果・境界条件
- **既存エキスパート skippingの大幅精度低下**: LLaDA2.0-MiniではNAEEとMC-MoEの平均相対精度が約46.6〜46.7%まで低下し、並列トークンへAR向け局所枝刈りを適用するだけでは不十分。
- **過小コア集合では精度低下**: DES-VoteでもLLaDA2.0-Mini beta=0.10は96.4%、LLaDA-MoE-7B beta=0.4は96.0%となり、メモリ削減を強めるほど品質とのトレードオフが残る。
- **トークン当たり専門家数の削減は不利**: 同じユニーク専門家集合サイズでも各トークンの活性数を8から4へ減らすと全ベンチマークで精度が低下し、共有済み専門家の再利用計算は維持した方がよい。

### 結果の読み方
結果はMoE並列復号のボトルネックが単なるFLOPsではなくユニーク専門家重みのフェッチであるというモデルを支持する。DES-Voteは局所Top-Kを保ちながら共有集合を小さくするため、追加の重みロードなしに各トークンが複数専門家を再利用でき、単純なTop-K削減より精度を保つ。
## 品質への影響
Vanillaと完全同一ではなく近似ルーティングであり、コア集合予算を縮めるほど精度低下が増える。ただし主設定ではLLaDA2.0-Miniで99.5%の平均相対精度を維持し、専門家フットプリントと遅延を大幅に削減する。
## 既存研究との差
- **エキスパート skippingとの差**: NAEEやMC-MoEは各トークンの低重要度専門家計算を減らすが、他の並列トークンがその専門家を使えば重みロードは残る。DESはブロック全体のユニーク専門家集合を直接小さくする。
- **offline 枝刈り/mergingとの差**: モデル重みを恒久的に削るのではなく、入力ブロックごとにコア集合を動的選択するため、異なるシーケンスで必要な専門家へ切り替えられる。
- **OEA型AR バッチ sharingとの差**: 既存のバッチ-level sharingを独立リクエストのARバッチへ適用するのに対し、DESは意味的に結び付いたdLLM並列トークンをsequence-level consensusとして扱い、重み付き投票で共有集合を選ぶ。
## 限界
- **単一GPU・限定モデル評価**: 実測は単一NVIDIA B200と2つのMoE dLLMに集中し、マルチGPUのエキスパート parallel通信やCPU/SSD専門家オフロードを直接評価していない。
- **dLLM並列復号への依存**: 共有の根拠は同一文脈から同時生成されるトークンの専門家需要が重なる点にあり、独立リクエストを混ぜる通常のAR batchingへ同じ効果がそのまま成立するとは限らない。
- **近似ルーティングによる品質トレードオフ**: コア集合を小さくし過ぎると平均相対精度は96%前後まで低下する。用途ごとにbetaまたはkを調整する必要がある。
- **公開実装URLが本文で確認できない**: 融合GPUカーネルを含む実装は評価されるが、本文から著者公式コードリポジトリURLを確認できず、再現性は公開コード付き研究より弱い。
## 実装状態
dInfer + Fast-dLLM環境でDES-Seq/DES-Voteを実装し、DES-Vote向けに12処理を2カーネルへ融合したGPU実装を評価している。本文記載の公式公開コードURLは確認できない。
## 研究上の位置づけ
適応型 エキスパート Computation / Compression系統では、専門家を削除・量子化・オフロードするのではなく、同時生成トークン間の専門家再利用を増やして実行時のユニーク重み転送量を減らす方式に位置付く。MoE-Lightning等のCPUオフロードやエキスパート キャッシュと組み合わせる場合、1ステップで要求されるユニーク専門家集合自体を縮めるため、PCIe/HBM転送要求を上流で減らす補完策になり得る。ただし論文はオフロード併用を実測していない。
