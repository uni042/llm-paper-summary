# XMoE: Sparse Models with Fine-grained and Adaptive Expert Selection

## 概要

XMoEは、混合専門家モデル（Mixture-of-Experts、MoE）の計算を、**専門家を細かく分割すること**と**トークンごとに選ぶ専門家数を変えること**で適応的に配分する手法である。通常の上位k個選択（Top-k）では、ルータの出力が一つの専門家に集中しているトークンでも、複数専門家へ分散しているトークンでも同じ数の専門家を実行する。XMoEはルータ確率を大きい順に累積し、所定の閾値へ達したところで選択を止める。計算を必要とするトークンに多く、不要なトークンに少なく配分する狙いである。

ただし、専門家を小さくして計算量を減らすことと、実際のGPU上の推論時間を短くすることは同じではない。論文の図8では、**小専門家ほど行列積やルーティングの固定費が増え、演算量を減らしても壁時計時間が悪化する条件**を報告する。XMoEの主たる実証は、同程度の演算量で困惑度や翻訳品質が改善すること、および品質を大きく損なわずにMoE層の演算量を削減できることであり、あらゆるGPUで同じ倍率の実測高速化が得られるという主張ではない。

言語モデルの約323Mパラメータ設定では、64専門家・中間次元384のXMoEがOpenWebText困惑度19.46、WikiText-103困惑度19.97を達成した。同じ専門家構成の固定Top-kはそれぞれ19.79、20.10である。密モデルを小専門家へ分割した実験では、WikiText-103の困惑度が密モデル22.24に対しXMoEで21.97となる条件があり、MoE層の演算量を元の25%まで減らしても改善を維持した。一方、OpenWebTextでは密モデル22.61に対しXMoE23.07となるため、全条件で品質が改善するわけではない。

## 問題設定

標準的なMoEの専門家は、フィードフォワードネットワーク（FFN）を一つの単位として選ぶ。選択した専門家の内部では、多くの中間ニューロンがゼロや小さい活性値を出すことがある。実際に有用な成分が一部しかなくても、専門家全体の行列積を実行するため、専門家単位の疎性だけでは内部の不要な計算を避けられない。

論文の図1は、ReLUやGELUを使うFFNで、専門家数が増えるにつれて正の活性値の割合が小さくなる傾向を示す。著者らは、必要な情報を担う中間成分が複数の専門家に分散していると考え、FFNをより小さな専門家へ分割することを提案した。小専門家を必要な数だけ選べば、大専門家を一つ丸ごと計算するより、トークンごとの必要な部分を細かく指定できる。

従来の固定Top-kでは、トークンの複雑さやルータ確率分布にかかわらず同じ数の専門家を選ぶ。確信度が高いトークンには余分な計算が生じ、分布が広いトークンには専門家数が足りない可能性がある。XMoEはルータの確率質量を使い、必要な専門家数を入力依存で決める。ただしこれは、既存の大規模MoEへ学習なしで追加する単純な推論スイッチではない。小専門家とルータを含む構成で学習することが主な評価条件である。

## 手法

### 1. FFNの細分化

通常のFFNは `W2 σ(W1 x)` と書ける。活性化関数σが要素ごとに作用するため、中間次元を複数の区間へ分割し、対応する `W1_i` と `W2_i` からなる小FFNの出力を合計して元のFFNを表せる。論文の式(4)がこの分解を示す。XMoEはこの考え方を使い、一つの大きな専門家の代わりに多数の小さな専門家を学習する。

専門家が小さくなると、一つを選ぶときに計算する中間次元が減る。例えば中間次元3072の専門家8個と、中間次元384の専門家64個は、専門家の総中間次元という観点では対応するが、後者は一トークンが必要な部分を細かく選べる。もっとも、専門家を増やすとルータが扱う候補数も増え、選択・整列・実行管理の費用が増えるため、細分化は無条件に有利ではない。

### 2. 累積確率の閾値ルータ

入力トークンの中間表現hから、学習可能な重み行列Wで各専門家の得点を計算し、ソフトマックスで確率 `p_i` に変換する。通常のTop-kは確率値にかかわらず固定k個を選ぶ。XMoEは確率を降順に並べ、累積和が閾値t以上になる**最小の専門家数m**を選ぶ。論文の式(5)がこの規則を定義する。

例えば確率が `[0.92, 0.03, 0.03, 0.02]` ならt=0.90では一専門家で足りる。一方 `[0.39, 0.30, 0.16, 0.15]` なら同じ閾値へ達するには四専門家が必要となる。これはトークンごとに演算量が変わることを意味する。t=0なら実質的にTop-1、t=1なら全専門家を選ぶ。tは品質と計算量の交換条件を調整する直接の制御変数となる。

選ばれた専門家の出力は、ルータ確率を重みとして合計する。閾値が低いと、確率の小さい専門家の寄与を省くことで演算量を減らせるが、その専門家が必要な情報を持っていた場合は品質が悪化し得る。したがって「ルータが確信している」という言葉は学習済み確率の分布形を表すもので、個々のトークンが客観的に簡単か難しいかを直接計測したものではない。

### 3. 専門家容量と優先順位

一つの専門家へ多くのトークンが集中すると、専門家容量を超えたトークンが破棄される。論文は、バッチのトークン数T、専門家数N、容量係数γから専門家の受け入れ容量を `T/N×γ` と定義する。γを大きくするとトークン破棄は減るが、ゼロ埋めの処理が増える。小専門家を使うXMoEでは、専門家一つの演算費用が小さいことを利用し、同程度の計算予算を維持しながらγを調整できる。

複数のトークンが同じ専門家を選んだときは、優先順位を付けて処理する。論文の規則では、その専門家がトークンにとって何番目の候補かとルータ確率を用い、優先度を概ね `p-i` の形で設定する。これにより、容量が不足した際に、その専門家をより高く評価したトークンを優先して残す。単に確率の閾値を設けるだけでなく、容量制約のもとでどのトークンを処理するかまで定義する点が重要である。

### 4. 補助損失と学習

専門家へのトークン割当が偏りすぎると、一部の専門家が十分に学習されず、実行時の容量超過も増える。XMoEは負荷分散の補助損失を加えるが、制約するのは主として各トークンの第一候補専門家への割当である。第二候補以降の選択数まで均一化すると、累積確率による適応配分の自由度が失われるためである。

論文の言語モデルは12層のデコーダ型Transformerを用い、Megatron-LMを基盤としてOpenWebTextとWikiText-103で学習する。翻訳モデルは12層エンコーダ・6層デコーダでfairseqを基盤とする。既定の閾値tは0.90である。比較では小専門家にした構成の容量係数γを調整し、同程度のMoE層演算量で品質を比べる。

### 5. 密モデルからの疎計算

XMoEは、密モデルのFFNを小専門家へ分割し、学習中はt=1、γ=Nとして全専門家を実行する設定も評価する。このときルータは各部分の有用性を学び、推論時にtとγを下げることで一部専門家だけを計算する。したがって「学習済み密モデルの重みを任意に分割するだけで同じ品質が保たれる」という方式ではなく、分割構成での学習を前提とする。

この実験は、学習時には密に使ったパラメータの一部を推論時に省ける可能性を示す。ただし専門家数を極端に増やすと、ルータの整列費用や小さい行列積の実行効率が問題となる。著者らも、専門家の中間次元を1まで縮める構成は現行実装で実現できなかったと限界節に記す。

## 評価条件

| 項目 | 論文での条件 |
|---|---|
| GPU | NVIDIA A100を4基備えた単一ノード |
| 言語モデル | 12層デコーダ型Transformer、約323M/556Mパラメータの比較 |
| 言語モデルのデータ | OpenWebText、WikiText-103 |
| 翻訳モデル | 12層エンコーダ・6層デコーダ |
| 翻訳データ | WMT23の5言語→英語 |
| 比較方式 | 密Transformer、Switch Transformer、Hash Layer、BASE Layer、固定Top-k、XMoE |
| ルータ | 閾値t=0.90を既定とし、感度評価で変化 |
| 品質 | 言語モデルの困惑度、翻訳のBLEUとChrF |
| 効率 | MoE層の演算量、実際のバッチ処理時間 |
| 公平性 | 小専門家の容量係数γを調整し、同程度の演算予算で比較 |

困惑度は低いほど良く、BLEU・ChrFは高いほど翻訳品質が良い。演算量の削減率はMoE層内の値であり、注意層を含むモデル全体の演算量や壁時計時間の削減率とは区別する。実際のGPU上の推論時間は、専門家数に応じて発生するルータと小行列積の固定費にも左右される。

## 主要結果

### 1. 言語モデルでの同等演算量比較（表1）

| 約323M設定の方式 | 専門家数×中間次元 | OpenWebText困惑度 | WikiText-103困惑度 |
|---|---|---:|---:|
| Switch Transformer | 8×3072 | 20.11 | 20.60 |
| 固定Top-k | 16×1536 | 19.81 | 20.24 |
| 固定Top-k | 64×384 | 19.79 | 20.10 |
| XMoE | 16×1536 | 19.57 | 20.16 |
| XMoE | 32×768 | 19.49 | 20.00 |
| XMoE | 64×384 | 19.46 | 19.97 |

同程度のMoE層演算量で比較すると、XMoEの小専門家構成が固定Top-kより良い困惑度を示す。例えば64×384のXMoEはOpenWebTextで19.46、固定Top-kで19.79となり、0.33ポイント低い。Switch Transformerの20.11との差は0.65ポイントである。これは「小専門家と可変選択を組み合わせると、同じ計算予算をより有効に使える」という主張の直接的な根拠となる。

ただし約556M設定では、専門家の細分化を進めるほど常に品質が改善するわけではない。OpenWebTextではXMoE 32×1024が18.68、64×512が18.72であり、さらに細かくするとわずかに悪化する。したがって小専門家の粒度はデータとモデル規模に依存し、単純に数を増やし続ければよいわけではない。

### 2. 演算量削減と困惑度（図4・表2）

XMoEの小専門家構成は、MoE層の演算量を減らしても困惑度が比較的安定する。図4では64×384のXMoEが、WikiText-103でSwitch Transformerの8×3072より少ない演算量でも良い困惑度を示す。これは一トークンごとの計算資源を細かく選ぶ効果を示すが、演算量が少ないことだけで実時間の短縮を保証するものではない。

密モデルから分割した実験の表2では、元の密モデルがOpenWebText 22.61、WikiText-103 22.24であるのに対し、8×384のXMoEは演算量を元の25%へ減らした条件でOpenWebText 23.07、WikiText-103 21.97となった。**WikiText-103では品質を維持・改善した一方、OpenWebTextでは0.46ポイント悪化**した。演算量75%削減という値を「全データで無損失」と表現してはならない。

### 3. 機械翻訳（表3）

WMT23の5言語から英語への翻訳では、平均BLEUと平均ChrFが、Switch Transformerで27.6/52.7、固定Top-kの64×1024で28.2/53.4、XMoEの64×1024で28.7/53.8だった。XMoEの128×512でも平均BLEUは28.7、ChrFは53.7であり、専門家をさらに細かくしても平均品質はほぼ頭打ちとなる。

個別言語でも一様に改善するわけではない。例えばヘブライ語→英語ではXMoE 64×1024のBLEUが36.1、128×512が35.5であり、より細かい構成が悪い。論文は品質改善の大きさが言語と評価指標に依存することを認める。平均値だけで全言語に対する単調な改善を主張しない。

### 4. 閾値・専門家数の感度（図5・図7）

図5では学習が進むと、閾値を満たすために必要な専門家数が減る傾向が見られる。著者らは、学習の進行によって少数の有用な専門家へ確率が集中し、適応ルータが不要な専門家計算を省きやすくなると解釈する。図7では閾値tを上げるほど概ね困惑度が改善するが、t=0.90がt=1.0よりわずかに良い条件もある。選択専門家数と品質は必ずしも単調な関係ではない。

t=1.0では全専門家を選び、t=0.0では実質的にTop-1となる。閾値を低くすれば演算量を減らせる一方、トークンによっては必要な専門家を省く可能性がある。学習時の閾値と推論時の閾値を別々に変えた図7は、学習構成と実行時設定の組合せで品質が変わることを示す。

### 5. 実時間の負の結果（図8）

図8は、MoE層の演算量と一バッチの壁時計時間を直接比較する。演算量を減らすと全体として時間は短くなる傾向があるが、同じ演算量なら小専門家の構成ほど**むしろ実行時間が長い**条件が報告されている。理由として著者らは、細かい疎計算がGPU/TPU上で十分効率的に実行されないこと、専門家候補数が増えて並べ替えや順位付けの費用が増えることを挙げる。

したがって「MoE層FLOPsを75%減らした」ことを「エンドツーエンド推論遅延を75%短縮した」と読み替えてはならない。実運用では、専門家へトークンを集約するカーネル、ルータの整列、専門家ごとの小行列積の効率まで含めて測定する必要がある。これはXMoEを大規模推論基盤へ組み込む際の重要な制約である。

## 既存研究との差

Switch Transformerは通常一トークンを一専門家へ割り当て、固定Top-kは指定数の専門家を毎回選ぶ。XMoEは小専門家と累積確率閾値を組み合わせるため、同じトークンでもルータの確率分布に応じて選択数が変わる。専門家を小さくするだけの構成と、ルータを適応型にする構成の両方が品質と計算効率へ寄与する点が特徴である。

また、既存モデルの専門家重みをCPUへ退避する研究や、専門家を低ビット量子化する研究とは目的が異なる。XMoEは主にモデル構造とルーティングを学習して演算量を適応配分する。GPUメモリ不足を直接解消するオフロード方式ではなく、同じ演算予算での品質や同じ品質での演算量を改善する方向の研究である。

## 限界と適用範囲

第一に、評価対象は最大556Mパラメータであり、数十億～数千億パラメータの実運用MoEに対する同じ品質・速度改善を実測したものではない。論文の限界節でも大規模モデルでの追加検証が必要とされる。言語モデルと機械翻訳以外のタスクに対する一般性も未確認である。

第二に、細分化を進めると小行列積やルータの並べ替え費用が増える。図8の実時間評価は、FLOPs削減が壁時計時間の削減と一致しない負の結果を示す。演算量削減を推論基盤の性能改善へ結び付けるには、GPUカーネルやトークン振り分け処理を合わせて最適化する必要がある。

第三に、累積確率閾値tと容量係数γの設定は品質と計算量を左右する。tを低くしすぎると必要な専門家を省くことがあり、γを小さくしすぎると専門家容量超過によるトークン破棄が増える。閾値を推論時に調整できても、すべてのモデルで品質が維持されるわけではない。

第四に、密モデルからの疎計算は、分割した構成で学習してから推論時に選択数を減らす実験であり、任意の既存チェックポイントへ学習なしで適用できる手法ではない。著者らは専門家中間次元を1にする極端な細分化を現行実装で実現できなかったと明記している。

第五に、表2のOpenWebTextでは密モデルより困惑度が悪化する。表3でも言語によって細分化の利得が変わる。XMoEの主張は特定条件での品質・演算量の良好な交換条件であり、無損失の普遍的高速化ではない。
