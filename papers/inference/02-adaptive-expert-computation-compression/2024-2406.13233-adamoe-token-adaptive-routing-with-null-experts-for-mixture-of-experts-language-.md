# AdaMoE: Token-Adaptive Routing with Null Experts for Mixture-of-Experts Language Models

> 計算を行わないnull expertをrouting候補へ加え、簡単なtokenではnullを多く選ばせることで、実際にFFN計算するexpert数をtokenごとに変えるMoE。

## 概要
AdaMoEは固定Top-kを直接可変長routerへ作り直す代わりに、**計算をしないnull expertを通常expertと同じrouting候補へ混ぜる**ことで、tokenごとの実FFN数を変える。

router自体はTop-kを選び続けるが、選択枠の一部がnullなら、その分だけreal expert計算が消える。したがって既存MoEのTop-k処理を大きく変えずにdynamic expert countを実現できる。

null利用率を制御する補助lossと、trainingが進むにつれてその制約を徐々に緩める仕組みを入れ、計算削減を強くし過ぎて全tokenがnullへ逃げることを防ぐ。既存Mixtralへ適用する場合はQLoRA fine-tuningを行うため、完全なpost-hoc inference最適化ではない。

## 手法のあらまし

### 1. `Null Expert`：Top-k枠を使うがFFN計算はしない

通常expertはFFNを実行して出力を返すが、null expertはparameterを持たず、実質的に出力寄与を持たない計算ゼロ経路として扱う。

例えばTop-k=3でも、選ばれた3候補が

`real, null, null`

なら実際のFFNは1個だけ実行される。

これによりrouter interfaceは固定Top-kのまま、**実expert数だけtokenごとに0〜kの範囲で変化**させられる。

### 2. `m5k2` / `m8k3`：null数mとrouter Top-kを表す

論文中の設定名は、

- `m` = 追加するnull expert数
- `k` = routerが選ぶ総候補数

を表す。

`m`を増やすほどrouterがnullを選ぶ自由度が増え、`k`を増やすほどreal expertを複数残す余地も増える。

その組合せで平均real expert実行数を細かく調整する。

### 3. `Load`：選択候補数ではなく実行したreal expert数

AdaMoEでいうloadはTop-kそのものではなく、**token当たり平均で何個のreal expertを実行したか**を指す。

nullが選ばれるほどloadは下がる。

そのためTop-k=3でも平均loadが1.66などになり得る。

### 4. Null利用の偏りを抑える補助loss

通常MoEのload-balancing lossをそのまま使うと、nullとreal expertを同じように均等化しようとして望む計算削減率を作りにくい。

AdaMoEはnull利用量を含む専用の補助lossを使い、training初期は強く分布を整え、後半で制約を緩める。

目的は「ほぼすべてのtokenがnullへ流れる状態」や「一部real expertだけへ集中する状態」を避けること。

### 5. 既存Mixtralへ追加する時はgate出力次元を拡張する

Mixtralへ適用する場合、元gateの8 real expertsにnull候補を追加し、gateが出すscore数を増やす。

初期化時に元router probabilityを大きく壊さないようnull側scoreを設定し、その後QLoRAでfine-tuneする。

つまり**推論時にnullを後付けするだけではなく、routerがnullの使い所を学習する必要がある**。

### 6. Mo-LoRA構成では通常LLMにも適用する

Dense Llama2-7BではMo-LoRA形式で複数LoRA expertを持たせ、そこへnull expertを加える。

この場合も「real expert = LoRA branch」「null = branch計算なし」としてtoken-adaptive loadを作る。

### 7. FLOPs削減とwall-clockは別

nullが選ばれても、

- router計算
- tokenをexpertへ振り分けて戻す処理
- non-FFN部分

は残る。

さらにtokenごとにreal expert数が違うとGPU batch形状が不均一になるため、FFN FLOPsが15%減ってもwall-clockが15%速くなるとは限らない。

論文は主にload / FLOPsを報告し、optimized inference kernelでのend-to-end speedupは示していない。

## 評価

### まず見るところ
- **結論:** null expertをrouter候補へ入れると、既存Top-k構造を保ちながらtokenごとのreal expert数を変えられる。
- **品質:** 標準設定ではbaselineと同等以上だが、null利用を強め過ぎると急激に崩れる。
- **計算量:** Mixtral標準設定で平均load 2.00→1.66、FFN FLOPs約15.2%削減。
- **実速度:** **end-to-end wall-clock高速化は未実証**。
- **注意点:** Mixtral評価は4-bit QLoRA fine-tuningを含み、AdaMoE単独のruntime効果と分離して読む必要がある。

### Mixtral-8x7Bの主設定

WinoGrande、HellaSwag、PIQA、SIQA、OpenBookQA、ARC-Cを評価。

| 構成 | 平均精度 | 平均real expert load | FLOPs削減 |
|---|---:|---:|---:|
| Fine-tuned baseline | 84.64 | 2.00 | — |
| AdaMoE m=8,k=3 | **85.35** | **1.66** | **15.21%** |

標準設定では計算を減らしながら平均精度が僅かに上がる。

### Task別の変化

| Task | Baseline | AdaMoE |
|---|---:|---:|
| WinoGrande | 80.43 | 81.93 |
| HellaSwag | 84.10 | 85.50 |
| PIQA | 90.48 | 90.32 |
| OpenBookQA | 89.00 | 88.20 |
| ARC-C | 87.46 | **89.15** |

全taskで改善するわけではなく、PIQA / OQAでは小幅低下する。

### Null利用を強くした場合

SIQAの要素別評価。

| 設定 | 平均load | 精度 |
|---|---:|---:|
| m=32,k=6 | 1.54 | baseline以上を維持 |
| m=32,k=5 | 1.05 | 72.93 |
| m=32,k=4 | **0.77** | **66.27** |

loadを1未満まで落とせてもqualityが急落するため、null数を増やせば一方的に良くなるわけではない。

### 通常LLM側

Llama2-7B + Mo-LoRAでRTE、CoLA、ScienceQA、CommonsenseQA、OpenBookQAを評価し、fixed Top-1 / Top-2 Mo-LoRAと比較する。

主張は同じで、tokenごとのreal branch数を変えることで同じ平均computeをより有効に配分する。

### 評価上の制約

- optimized wall-clock inferenceを報告していない。
- Mixtral側は4-bit QLoRAの影響を含む。
- nullを入力そのまま通過へ変えた派生は未検証。
- full pretrainingからの大規模検証はない。
- tokenごとに異なるexpert数を効率よく処理するkernelが別途必要。
