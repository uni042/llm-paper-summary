# AdaMoE: トークン-適応型 ルーティング with Null エキスパート for Mixture-of-エキスパート Language Models

> 計算を行わないnull エキスパートをルーティング候補へ加え、簡単なトークンではnullを多く選ばせることで、実際にFFN計算するエキスパート数をトークンごとに変えるMoE。

## 概要
AdaMoEは固定Top-kを直接可変長ルータへ作り直す代わりに、**計算をしないnull エキスパートを通常エキスパートと同じルーティング候補へ混ぜる**ことで、トークンごとの実FFN数を変える。

ルータ自体はTop-kを選び続けるが、選択枠の一部がnullなら、その分だけreal エキスパート計算が消える。したがって既存MoEのTop-k処理を大きく変えずに動的 エキスパート countを実現できる。

null利用率を制御する補助損失と、学習が進むにつれてその制約を徐々に緩める仕組みを入れ、計算削減を強くし過ぎて全トークンがnullへ逃げることを防ぐ。既存Mixtralへ適用する場合はQLoRA微調整を行うため、完全な事後推論最適化ではない。

## 手法のあらまし

### 1. `Null Expert`：Top-k枠を使うがFFN計算はしない

通常エキスパートはFFNを実行して出力を返すが、null エキスパートはparameterを持たず、実質的に出力寄与を持たない計算ゼロ経路として扱う。

例えばTop-k=3でも、選ばれた3候補が

`real, null, null`

なら実際のFFNは1個だけ実行される。

これによりルータ interfaceは固定Top-kのまま、**実エキスパート数だけトークンごとに0〜kの範囲で変化**させられる。

### 2. `m5k2` / `m8k3`：null数mとルータ Top-kを表す

論文中の設定名は、

- `m` = 追加するnull エキスパート数
- `k` = ルータが選ぶ総候補数

を表す。

`m`を増やすほどルータがnullを選ぶ自由度が増え、`k`を増やすほどreal エキスパートを複数残す余地も増える。

その組合せで平均real エキスパート実行数を細かく調整する。

### 3. `Load`：選択候補数ではなく実行したreal エキスパート数

AdaMoEでいうloadはTop-kそのものではなく、**トークン当たり平均で何個のreal エキスパートを実行したか**を指す。

nullが選ばれるほどloadは下がる。

そのためTop-k=3でも平均loadが1.66などになり得る。

この仕組みでは、選択枠の形式を変えずに実際の演算量だけを調整できる。難しい入力には通常エキスパートを多く割り当て、簡単な入力にはnullを割り当てるため、全トークンへ一律の削減率を適用するよりも、限られた計算予算を内容に応じて使い分けられる。ただし、nullを増やし過ぎると必要な表現まで失われるため、品質を確認しながら利用率を決める必要がある。

### 4. Null利用の偏りを抑える補助loss

通常MoEの負荷分散損失をそのまま使うと、nullと実エキスパートを同じように均等化しようとして望む計算削減率を作りにくい。

AdaMoEはnull利用量を含む専用の補助損失を使い、学習初期は強く分布を整え、後半で制約を緩める。

目的は「ほぼすべてのトークンがnullへ流れる状態」や「一部real エキスパートだけへ集中する状態」を避けること。

### 5. 既存Mixtralへ追加する時はgate出力次元を拡張する

Mixtralへ適用する場合、元ゲートの8実エキスパートにnull候補を追加し、ゲートが出すスコア数を増やす。

初期化時に元ルータ確率を大きく壊さないようnull側スコアを設定し、その後QLoRAで微調整する。

つまり**推論時にnullを後付けするだけではなく、ルータがnullの使い所を学習する必要がある**。

### 6. Mo-LoRA構成では通常LLMにも適用する

Dense Llama2-7BではMo-LoRA形式で複数LoRA エキスパートを持たせ、そこへnull エキスパートを加える。

この場合も「実エキスパート = LoRA分岐」「null = 分岐計算なし」としてトークン適応型の負荷を作る。

### 7. FLOPs削減とwall-clockは別

nullが選ばれても、

- ルータ計算
- トークンをエキスパートへ振り分けて戻す処理
- non-FFN部分

は残る。

さらにトークンごとにreal エキスパート数が違うとGPU バッチ形状が不均一になるため、FFN FLOPsが15%減ってもwall-clockが15%速くなるとは限らない。

論文は主に負荷／FLOPsを報告し、最適化済み推論カーネルでのエンドツーエンド高速化倍率は示していない。

可変計算量になる理由は、通常エキスパートの上位順位を直接打ち切るのではなく、ルータ自身に『この選択枠は計算しなくてよい』というnullエキスパートを選ばせる点にある。簡単なトークンでは複数のnullがTop-kへ入り、難しいトークンでは通常エキスパートが多く残るので、同じTop-kインターフェースのまま実FFN数だけが変わる。補助損失は平均null利用量を制御するが、個々のトークンに同じnull数を強制しないため、このばらつきが残る。逆に補助損失が強すぎれば全トークンの構成が似通い、弱すぎればnullへ過度に集中し得るため、計算予算と品質の両方を学習時に調整する必要がある。

またnullエキスパートを選ぶとFFN計算は消えるが、ルータ判定そのものやトークンの振り分け管理まで完全に消えるわけではない。したがって実機での高速化は、削減したFFN演算量がランタイムの分岐・通信・小バッチ化の固定費を十分上回る条件で大きくなる。

## 評価

### まず見るところ
- **結論:** null エキスパートをルータ候補へ入れると、既存Top-k構造を保ちながらトークンごとのreal エキスパート数を変えられる。
- **品質:** 標準設定では比較対象と同等以上だが、null利用を強め過ぎると急激に崩れる。
- **計算量:** Mixtral標準設定で平均load 2.00→1.66、FFN FLOPs約15.2%削減。
- **実速度:** **エンドツーエンド wall-clock高速化は未実証**。
- **注意点:** Mixtral評価は4-bit QLoRA fine-tuningを含み、AdaMoE単独の実行時効果と分離して読む必要がある。

### Mixtral-8x7Bの主設定

WinoGrande、HellaSwag、PIQA、SIQA、OpenBookQA、ARC-Cを評価。

| 構成 | 平均精度 | 平均real エキスパート load | FLOPs削減 |
|---|---:|---:|---:|
| Fine-tuned 比較対象 | 84.64 | 2.00 | — |
| AdaMoE m=8,k=3 | **85.35** | **1.66** | **15.21%** |

標準設定では計算を減らしながら平均精度が僅かに上がる。

### Task別の変化

| Task | 比較対象 | AdaMoE |
|---|---:|---:|
| WinoGrande | 80.43 | 81.93 |
| HellaSwag | 84.10 | 85.50 |
| PIQA | 90.48 | 90.32 |
| OpenBookQA | 89.00 | 88.20 |
| ARC-C | 87.46 | **89.15** |

全taskで改善するわけではなく、PIQA / OQAでは小幅低下する。

### Null利用を強くした場合

SIQAの要素別評価。

| 設定 | 平均load | 精度 |
|---|---:|---:|
| m=32,k=6 | 1.54 | 比較対象以上を維持 |
| m=32,k=5 | 1.05 | 72.93 |
| m=32,k=4 | **0.77** | **66.27** |

負荷を1未満まで落とせても品質が急落するため、null数を増やせば一方的に良くなるわけではない。

### 通常LLM側

Llama2-7B + Mo-LoRAでRTE、CoLA、ScienceQA、CommonsenseQA、OpenBookQAを評価し、固定Top-1／Top-2 Mo-LoRAと比較する。

主張は同じで、トークンごとの実分岐数を変えることで同じ平均計算量をより有効に配分する。

### 評価上の制約

- optimized wall-clock inferenceを報告していない。
- Mixtral側は4-bit QLoRAの影響を含む。
- nullを入力そのまま通過へ変えた派生は未検証。
- full pretrainingからの大規模検証はない。
- トークンごとに異なるエキスパート数を効率よく処理するカーネルが別途必要。
