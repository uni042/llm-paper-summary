# ExpertFlow: Efficient Mixture-of-Experts Inference via Predictive Expert Caching and Token Scheduling

> 数layer先で使うexpertを予測し、同じexpertを使いそうなtokenをまとめ、GPU cache容量も需要に応じてlayer間で動かすことで、CPUからexpertを読む待ち時間を減らすMoE推論system。

## 概要
ExpertFlowは、CPUへoffloadしたexpertを単に先読みするだけでなく、**同じexpert経路を通りそうなtokenを同じbatchへ集め、GPU上のexpert cache容量もlayerごとの将来需要に合わせて動かす**systemである。

構成は3部分ある。

- `RPP（Routing Path Predictor）`: 各tokenが数layer先までどのexpertを使いそうか予測する軽量model
- `TS（Token Scheduler）`: 同じexpertを使いそうなtokenを同じbatchへ集める
- `ECE（Expert Cache Engine）`: 予測需要に合わせてGPU上のexpert cache容量をlayer間で配り直す

予測が外れてもnative routerが要求した正しいexpertをCPUから追加で読み込むため、出力結果は元modelと同じ。主なmemory階層はCPU DRAM ↔ GPU VRAMで、SSD offloadではない。

## 手法のあらまし

### 1. `RPP`：数layer先のexpert routingを予測する

Routing Path Predictorは、各tokenが将来layerでどのexpertへ送られるかを予測する軽量modelである。

単一layerの次expertだけでなく、**数layerにわたるrouting sequence**をまとめて出すため、expert転送を早く開始できる。

RPPはnative routerを置き換えず、先読みと実行順調整のhintとして使う。予測ミス時は正しいexpertを追加transferするため品質は変わらない。

したがって予測器の誤りは、モデル出力の誤りではなく資源利用の誤りとして現れる。外れたエキスパートを先に載せればGPUメモリとPCIe帯域を一時的に浪費し、必要なエキスパートを見落とせば正規ルータ判定後の追加転送を待つ。一方で正しいエキスパート計算へフォールバックするため、予測精度が低い条件でも推論結果そのものを近似する必要はない。これは予測ルーティングをそのまま実経路に使う方式と異なり、予測器を速度最適化の補助情報として安全に使える理由である。

### 2. `TS（Token Scheduler）`：同じexpertを使うtokenを同じbatchへ集める

隣接する2 batch、合計`2T` tokenを対象に、予測したexpert sequenceが似ているtoken同士をまとめ、二つの新しいbatchへ再分割する。

目的は、各batch内で必要になるexpert種類を減らすこと。

同じexpertを使うtokenをまとめると、

- 一度読み込んだexpert weightをより多くのtokenで再利用できる
- GPU cacheにないexpertを読む回数が減る
- CPU→GPU転送回数が減る

という利点がある。

### 3. Token順序を元sequenceへ戻す

TSは実行時だけtoken順序を入れ替えるため、そのままではKV cacheや出力位置との対応が崩れる。

そこで計算後にtokenとKVの位置を元sequenceへ対応付け直す。

つまりsemanticなtoken順序を変更するのではなく、**GPUで処理する順番だけを一時的に組み替える**。

### 4. `PLEC`：layer固定cacheではなく、必要なlayerへ容量を貸し借りする

ECE内の`PLEC（Predictive Layer-wise Expert Caching）`は、GPU上のexpert cacheを各layerへ固定量ずつ割り当てない。

RPPの予測需要を見て、

- 近い将来expertを多く使うlayerへ多くのcache容量を割く
- 前layerの処理が終わって不要になった容量を後layerへ回す

という形でcache容量を再配分する。

固定配分では「あるlayerには空きがあるのに、別layerでは必要expertが入らずCPU読み込みが発生する」ことがあるため、その無駄を減らす。

### 5. 予測外expertを優先して転送する

ECEはnative routerの実要求とRPP予測を比較し、予測していなかったexpertが必要になった場合、そのweightを優先してCPU→GPU転送する。

同時に、すでにGPUで実行できるexpert計算は止めずに進める。

したがって予測精度が低くても結果は正しく、悪化するのは主にlatencyとPCIe転送量である。

### 6. 次batchの予測・並べ替えを現在batchのGPU計算中に行う

RPPやtoken groupingを逐次実行すると、そのCPU処理が新しい待ち時間になる。

そこで現在batchをGPUで推論している間に、次の2 batchについてRPPとTSをCPU側で進める。

この**2-batch pipeline**により、prediction / scheduling処理をGPUが待つ主要経路から外す。TSのCPU処理は10 ms未満と報告される。

### 7. 3要素を組み合わせる理由

- RPPだけ → 先読みはできるが、1 batch内で必要expertがばらける
- TSだけ → 1 batch内のexpert種類は減るが、事前にcacheを準備できない
- ECEだけ → cache容量は賢く使えるが、将来需要の予測が弱い

ため、3つを一体で使うことが重要になる。

三要素は同じ転送待ちを別の段階から減らす。RPPは『何が必要になるか』を早めに知らせ、TSは『同じ重みを使うトークンをいつ一緒に処理するか』を変え、ECEは『限られたGPUメモリをどの層のエキスパートへ使うか』を変える。RPPが正しくても各バッチの経路がばらばらなら多数の重みを同時に保持する必要があり、TSだけで経路を揃えても必要重みを直前までCPUに置いたままでは待ち時間が残る。ECEも予測なしでは将来どの層へ容量を貸すべきか判断しにくい。このため三者を直列の独立最適化ではなく、同じ将来ルーティング情報を共有する一つの制御系として扱うことが性能向上の中心になる。

## 評価

### まず見るところ
- **結論:** routing予測・tokenの実行順調整・cache容量再配分を組み合わせると、CPU expert offloadの読み込み待ちを大幅に減らせる。
- **実速度:** SwitchでSE-MoE比最大9.99倍、Mixtral/Qwen/DeepSeekでもCache-MoE比約2倍。
- **品質:** 予測を外してもnative expertへ戻るためlossless。
- **メモリ:** Switch-128でGPU expert memory 15.26 GB→1.03 GBなど大幅削減。
- **注意点:** RPPの学習、token/KV位置の戻し処理、単一A40中心の評価が必要条件。
