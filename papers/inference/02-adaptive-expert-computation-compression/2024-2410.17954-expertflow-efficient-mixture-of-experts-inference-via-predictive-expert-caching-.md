# エキスパートFlow: Efficient Mixture-of-エキスパート Inference via Predictive エキスパート キャッシュ化 and トークン スケジューリング

> ExpertFlowは数層先の専門家利用を予測し、同じ経路のトークンをまとめ、層ごとのGPUキャッシュ容量も再配分してCPUからの重み転送待ちを隠す。

## 概要
エキスパートFlowは、CPUへオフロードしたエキスパートを単に先読みするだけでなく、**同じエキスパート経路を通りそうなトークンを同じバッチへ集め、GPU上のエキスパート キャッシュ容量も層ごとの将来需要に合わせて動かす**systemである。

構成は3部分ある。

- `RPP（Routing Path Predictor）`: 各トークンが数層先までどのエキスパートを使いそうか予測する軽量model
- `TS（Token Scheduler）`: 同じエキスパートを使いそうなトークンを同じバッチへ集める
- `ECE（Expert Cache Engine）`: 予測需要に合わせてGPU上のエキスパート キャッシュ容量を層間で配り直す

予測が外れてもnative ルータが要求した正しいエキスパートをCPUから追加で読み込むため、出力結果は元modelと同じ。主なメモリ階層はCPU DRAM ↔ GPU VRAMで、SSD オフロードではない。

NVIDIA A40 48GB実機のSwitch-128をcache 16・batch 32で測ると、SE-MoE比5.86倍、cacheを4へ縮めると9.99倍のend-to-end高速化となった。RPPの予測精度95%やTSの16.19%向上、ECEのcache hit率91.96%（LRU比最大61.15%向上）は構成要素の指標であり、全体の速度倍率とは区別する。


ExpertFlowは、予測した経路へトークンをまとめ、層別キャッシュも再配分して転送を隠す。RPPの専門家予測精度は最大95%、TS追加時のスループット改善は最大16.19%、ECEのキャッシュ命中率は91.96%でLRU比最大61.15%向上した。

## 手法のあらまし

### 1. `RPP`：数層先のエキスパート ルーティングを予測する

ルーティング Path Predictorは、各トークンが将来層でどのエキスパートへ送られるかを予測する軽量modelである。

単一層の次エキスパートだけでなく、**数層にわたるルーティング sequence**をまとめて出すため、エキスパート転送を早く開始できる。

RPPはnative ルータを置き換えず、先読みと実行順調整のhintとして使う。予測ミス時は正しいエキスパートを追加transferするため品質は変わらない。

したがって予測器の誤りは、モデル出力の誤りではなく資源利用の誤りとして現れる。外れたエキスパートを先に載せればGPUメモリとPCIe帯域を一時的に浪費し、必要なエキスパートを見落とせば正規ルータ判定後の追加転送を待つ。一方で正しいエキスパート計算へフォールバックするため、予測精度が低い条件でも推論結果そのものを近似する必要はない。これは予測ルーティングをそのまま実経路に使う方式と異なり、予測器を速度最適化の補助情報として安全に使える理由である。

### 2. `TS（Token Scheduler）`：同じエキスパートを使うトークンを同じバッチへ集める

隣接する2 バッチ、合計`2T` トークンを対象に、予測したエキスパート sequenceが似ているトークン同士をまとめ、二つの新しいバッチへ再分割する。

目的は、各バッチ内で必要になるエキスパート種類を減らすこと。

同じエキスパートを使うトークンをまとめると、

- 一度読み込んだエキスパート 重みをより多くのトークンで再利用できる
- GPU キャッシュにないエキスパートを読む回数が減る
- CPU→GPU転送回数が減る

という利点がある。

### 3. トークン順序を元sequenceへ戻す

TSは実行時だけトークン順序を入れ替えるため、そのままではKV キャッシュや出力位置との対応が崩れる。

そこで計算後にトークンとKVの位置を元sequenceへ対応付け直す。

つまりsemanticなトークン順序を変更するのではなく、**GPUで処理する順番だけを一時的に組み替える**。

### 4. `PLEC`：層固定キャッシュではなく、必要な層へ容量を貸し借りする

ECE内の`PLEC（Predictive Layer-wise Expert Caching）`は、GPU上のエキスパート キャッシュを各層へ固定量ずつ割り当てない。

RPPの予測需要を見て、

- 近い将来エキスパートを多く使う層へ多くのキャッシュ容量を割く
- 前層の処理が終わって不要になった容量を後層へ回す

という形でキャッシュ容量を再配分する。

固定配分では「ある層には空きがあるのに、別層では必要エキスパートが入らずCPU読み込みが発生する」ことがあるため、その無駄を減らす。

### 5. 予測外エキスパートを優先して転送する

ECEはnative ルータの実要求とRPP予測を比較し、予測していなかったエキスパートが必要になった場合、その重みを優先してCPU→GPU転送する。

同時に、すでにGPUで実行できるエキスパート計算は止めずに進める。

したがって予測精度が低くても結果は正しく、悪化するのは主に遅延とPCIe転送量である。

### 6. 次バッチの予測・並べ替えを現在バッチのGPU計算中に行う

RPPやトークン groupingを逐次実行すると、そのCPU処理が新しい待ち時間になる。

そこで現在バッチをGPUで推論している間に、次の2 バッチについてRPPとTSをCPU側で進める。

この**2-バッチ パイプライン**により、prediction / スケジューリング処理をGPUが待つ主要経路から外す。TSのCPU処理は10 ms未満と報告される。

### 7. 3要素を組み合わせる理由

- RPPだけ → 先読みはできるが、1 バッチ内で必要エキスパートがばらける
- TSだけ → 1 バッチ内のエキスパート種類は減るが、事前にキャッシュを準備できない
- ECEだけ → キャッシュ容量は賢く使えるが、将来需要の予測が弱い

ため、3つを一体で使うことが重要になる。

三要素は同じ転送待ちを別の段階から減らす。RPPは『何が必要になるか』を早めに知らせ、TSは『同じ重みを使うトークンをいつ一緒に処理するか』を変え、ECEは『限られたGPUメモリをどの層のエキスパートへ使うか』を変える。RPPが正しくても各バッチの経路がばらばらなら多数の重みを同時に保持する必要があり、TSだけで経路を揃えても必要重みを直前までCPUに置いたままでは待ち時間が残る。ECEも予測なしでは将来どの層へ容量を貸すべきか判断しにくい。このため三者を直列の独立最適化ではなく、同じ将来ルーティング情報を共有する一つの制御系として扱うことが性能向上の中心になる。

予測距離を長くすると転送を始める猶予は増えるが、誤予測による不要なキャッシュ占有とPCIe転送も増えやすい。したがって予測器は単純に最長距離を選ぶのではなく、転送を隠せる時間と予測精度の両方が有利になる範囲で使う必要がある。

以上の整理は、提案手法の動作原理と前提条件を保ったまま、一次資料の記述を要約したものである。

## 評価

### まず見るところ
- **結論:** ルーティング予測・トークンの実行順調整・キャッシュ容量再配分を組み合わせると、CPU エキスパート オフロードの読み込み待ちを大幅に減らせる。
- **実速度:** SwitchでSE-MoE比最大9.99倍、Mixtral/Qwen/DeepSeekでもキャッシュ-MoE比約2倍。
- **品質:** 予測を外してもnative エキスパートへ戻るため無損失。
- **メモリ:** Switch-128でGPU エキスパート メモリ 15.26 GB→1.03 GBなど大幅削減。
- **注意点:** RPPの学習、トークン/KV位置の戻し処理、単一A40中心の評価が必要条件。
