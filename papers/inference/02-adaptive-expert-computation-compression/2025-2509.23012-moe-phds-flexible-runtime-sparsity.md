# MoE-PHDS: One MoE checkpoint for flexible runtime sparsity

> 複数top-kを混ぜたSFTと低kアンカーにより、一つのMoEチェックポイントを複数の実行時疎性へ対応させ、SLA・エネルギー要求に応じてkを直接切り替える。

## 概要
MoE-PHDS（Post Hoc Declared Sparsity）は、固定top-kで事前学習されたMoEを軽量な教師あり微調整で複数の実行時kへ対応させ、一つのチェックポイントから予測可能な精度・計算トレードオフを提供する。微調整中に複数kを一様サンプリングし、必要に応じて終盤を低kへ徐々に固定するカリキュラム・アンカーを使う。OLMoE、Qwen1.5-MoE、内部1B級モデルで、kを20〜30%下げても概ね1〜2%以内の相対QA低下に抑え、別々のk専用チェックポイントよりクロスk回答一致率を7〜22%改善する。

PHDSは新しい専門家構造やトークン別ルータを導入せず、既存MoEのSFT段階で複数のグローバルkを混ぜるだけで、学習後にkを宣言して切り替えられる一つのチェックポイントを作る。さらに複数k混合だけでは極端に疎な点で高k共活性パターンの干渉が残るため、学習終盤を低kへ徐々に寄せるカリキュラム・アンカーを加える。実行時の制御面はk一つだけで、SLA、ユーザー階層、負荷、電力制約に応じてグローバル計算量を予測可能に変えられる。

代表結果として、OLMoE ランタイム sparsity shiftはOLMoE-1B-7B-0125でk=8に対してk=8→6で相対QA低下1.2%、WikiText perplexity増6.4%。事前学習MoE自体が20〜30%程度のk削減へ頑健。
## 問題設定
一般的な疎MoEは事前学習時のtop-kを配備時にも固定し、異なる精度・遅延・エネルギー目標を満たすにはkごとに別モデルを学習・保守する運用になりやすい。これは保存・評価・更新・ドリフト管理を複数化する。一方、トークン適応ルーティングは固定グローバル予算の使い方を変えられるが、入力依存で実行量が変動し、サービスレベル合意や電力制限に対する単純で予測可能なノブにはなりにくい。論文は公開MoEが想定よりk変更に頑健で、OLMoEは8→6で相対QA低下1.2%、WikiText perplexity増6.4%、Qwen1.5-MoEは4→3で精度低下0.43%、perplexity増1.2%に留まることを出発点とする。
## 新規性
PHDSは新しい専門家構造やトークン別ルータを導入せず、既存MoEのSFT段階で複数のグローバルkを混ぜるだけで、学習後にkを宣言して切り替えられる一つのチェックポイントを作る。さらに複数k混合だけでは極端に疎な点で高k共活性パターンの干渉が残るため、学習終盤を低kへ徐々に寄せるカリキュラム・アンカーを加える。実行時の制御面はk一つだけで、SLA、ユーザー階層、負荷、電力制約に応じてグローバル計算量を予測可能に変えられる。
## 手法
### 手法のあらまし
入力は固定k_preで事前学習済みのMoEチェックポイントと、配備時に使いたいkの集合K_trainである。第1段階のmulti-k SFTでは各forward passごとにK_trainからk_trainを一様サンプリングし、その回の全MoE層へ同じグローバルkを適用して通常の言語モデリング損失で更新する。ルータはまずk_preまでの確率を計算し、今回のtop-k_trainに残る専門家は元確率、k_pre内だが今回落とす専門家は小さいε、その他は0とするソフトマスクを使う。正規化型ルータではマスク後に再正規化する。εを完全0にしないため落とされた経路にも微小な勾配が残り、配備実装では配列形状を変えず複数kを扱える。LayerNormやload-balancing lossなどk依存統計はkごとに保存・切替する。第2段階のcurriculum anchoringではmulti-k学習を十分行った後、学習分布を低いアンカーkへ徐々に寄せる。これにより高kで同時活性化される専門家パターンの干渉を弱め、k_pre/2付近など疎な点の安定性を上げる。学習後には複数候補チェックポイントから、既定k_preでの検証性能または対象k範囲平均で一つだけ選ぶ。配備時は同じ重みをロードしたまま、要求・SLA・電力状況に応じてk_evを宣言し、通常のtop-kルータがその数だけ専門家を活性化する。別チェックポイント交換、アーキテクチャ変更、トークン別ポリシーは不要で、k_evはk_pre以下に制限する。

### multi-k教師あり微調整
SFTの各forward passで候補集合K_trainから一つのkを一様サンプリングし、その回のMoEをその疎性で実行する。例えばk_pre=8なら4〜8を混ぜる。単一kだけで微調整するNaive方式と異なり、同じパラメータが複数の専門家活性数で損失を下げるよう更新されるため、学習後に見たことのあるk間を一つのチェックポイントで横断できる。モデル構造は変えず、通常の言語モデリングSFTを利用する。補助損失や正規化統計にk依存状態がある場合はkごとに保持し、あるkの統計が別kへ混入することを避ける。公開モデルでは元から頑健性が高いが、調整不足の内部モデルではこの混合学習がクロスk性能を安定させる。

### ソフトtop-kマスク
元ルータは事前学習時k_preまでの専門家確率を計算する。今回のk_train上位に残る専門家はその確率を保持し、k_pre内だが今回落とす専門家にはε=1e-6を与え、それ以外は0とする。正規化top-k softmaxの場合は残った値を再正規化する。完全な0ではなく微小値を置くことで落とされた経路にも勾配流を残し、学習中に特定kだけへ不可逆に崩れることを避ける。またJAX等でkごとに配列形状を変える必要がなく、同じ静的形状のまま疎性だけを変えられる。付録のε=1e-1〜1e-8アブレーションでは1e-4未満で大差がなく、1e-6を採用する。

### カリキュラム・アンカー
multi-k混合学習だけでは高kで同時に活性化される専門家パターンが低k時の役割分担を妨げ、非常に疎な設定で性能が落ちることがある。そこで初期のmulti-k学習後、学習分布を目標とする低いk_trainへ徐々に寄せて終盤をアンカーする。内部CommonSense170Kでは約1万step、1epochの93.9%付近からカリキュラムを開始した例を報告する。これにより複数kへの汎化を保ちながら低kで必要な専門家・注意機構の役割を安定化する。アンカーは必須ではなく、公開OLMoE/Qwenではアンカーなしmulti-kも強いが、未調整モデルや広いk範囲では追加の安定性を与える。

### k依存状態管理
モデル重み本体は一つに共有するが、LayerNormパラメータやload-balancing lossなど疎性レベルによって最適状態が変わる補助成分はkごとに保存・有効化する。これによりmulti-k SFTで同じforward graphを繰り返し使いつつ、ある疎性の統計や負荷均衡信号が別の疎性を不必要に歪めることを防ぐ。内部モデルではload-balancing値0.01、公開OLMoE/Qwen実験では0.0など設定を明示する。PHDSの主目的は複数完全モデルを保持することではなく、支配的な専門家・注意・埋め込み等の重みを一つへ統合したまま、必要最小限のk依存補助状態だけ切り替えることである。

### 単一チェックポイント選択
multi-kとアンカー学習の途中で複数候補が得られるため、配備用には一つだけ選択する。論文の既定ではモデル・タスク不整合による初期性能低下を避ける5000step burn-in後、事前学習時の既定k_preで最も良い複数選択QA性能を持つチェックポイントを選ぶ。運用目的によっては対象k範囲の平均性能で選ぶこともできる。重要なのはkごとに別々の最良チェックポイントを配備するのではなく、選んだ一つを全k_evで再利用する点である。これによりモデル交換によるキャッシュ・メモリ・運用複雑性を避け、同じモデルの回答傾向を疎性変更間で保ちやすくする。

### 実行時グローバル疎性制御
配備後、運用者は同じチェックポイントに対してk_evを宣言する。k_evは事前学習で専門家が経験した上限k_pre以下とし、各MoE層のtop-k活性数を一括で変える。トークン難易度に応じて毎回kを変える方式ではないため、要求単位の計算量・FLOPs・遅延・電力が予測しやすい。SLAの厳しい要求は高k、負荷ピークや電力制約時は低kといったサービス制御へ直接接続できる。論文の経験則では20〜30%程度のk削減は多くの評価で小さな品質低下に留まるが、k_pre/2未満では劣化が急になるためbest-effort領域として扱う。

### 全体のデータ／制御の流れ
学習側はmulti-k SFT→低kアンカー→単一チェックポイント選択、配備側は同一チェックポイントへ実行時k_evを渡すだけの二段構成。グローバルkなので同一要求内の全トークン・層の予算が予測しやすく、運用制御面を単純化する。
## 評価条件
- **ハードウェア**: 2×A100 40GB、8×A100 40GB
- **データセット／トレース**: CommonSense170K、Tülu-3 SFT mixture、Internal Data Mixture、ARC-C/E、BoolQ、HellaSwag、PIQA、SciQ、WinoGrande、SocialIQA、OpenBookQA、TriviaQA-fixed、WikiText
- **比較対象**: well-specified Oracle k_pre、Naive single-low-k SFT、pretrained checkpoint ランタイム mis-specification、PHDS multi-k without curriculum、PHDS multi-k with curriculum
1B〜14.3B総パラメータの等サイズrouted エキスパート MoEが対象。生成中心のcoding/summarization、大規模MoE、異種専門家サイズは未評価。k_evはk_pre以下。
## 主要結果
公開OLMoE/QwenはSFT方式に関係なく中程度のk低下へかなり頑健で、PHDSの最大価値は調整不足モデルで複数kを一つのチェックポイントへ安定統合する点にある。内部CommonSense170KではPHDSが対応Oracle付近の精度を保ちつつ、別々のOracleチェックポイントを切替える場合よりcross-k回答一致率を7〜22%高めた。運用上は複数k専用モデルを1個へ統合でき、図2の内部例では学習量を50%削減した。

- OLMoE ランタイム sparsity shift / k=8→6で相対QA低下1.2%、WikiText perplexity増6.4% (比較対象: k=8; 条件: OLMoE-1B-7B-0125) — 事前学習MoE自体が20〜30%程度のk削減へ頑健。

- Qwen ランタイム sparsity shift / k=4→3で精度低下0.43%、perplexity増1.2% (比較対象: k=4; 条件: Qwen1.5-MoE-A2.7B) — 単一チェックポイントのグローバルkを下げても小さな品質差に留まる。

- cross-k回答一致率 / Oracle別チェックポイント比+7〜22% (比較対象: 異なるk用のwell-specified Oracle checkpoint; 条件: 内部モデルk=(2,4),(4,6)) — 同じPHDS重みをkだけ変える方がユーザー向け出力の一貫性を保ちやすい。

- 内部k_pre=4 accuracy / PHDS [2,3,4]→3: k=2/3/4で0.7085/0.7140/0.72388 (比較対象: Oracle4: 0.66113/0.70663/0.72013; 条件: CommonSense170K平均) — 低k mis-specificationでOracle4より大幅に頑健。

- 内部k_pre=6 accuracy / PHDS [4,5]→4: k=4/5/6で0.72063/0.73200/0.74025 (比較対象: Oracle6: 0.72200/0.73163/0.73388; 条件: CommonSense170K平均) — 対応範囲でOracleと同等以上の点を持つ。

- 学習運用コスト / 内部図示例で50%削減 (比較対象: kごとに別チェックポイントを学習; 条件: 一つのPHDS checkpointで複数kを提供) — 複数モデル学習・保守を単一SFTへ統合できる。

### 負の結果・境界条件
- k_evをk_pre/2未満へ下げると性能劣化が顕著になり、安全範囲ではない。
- 公開OLMoE/Qwenは元から頑健で、PHDSがNaive/Oracleを常に大幅に上回るわけではない。
- kをk_preより増やしても、より密なkで事前学習したOracleの性能は回復できない。
- 評価は1B〜14.3Bで、より大規模MoEへのスケーラビリティは未確認。
- coding・summarizationなど生成中心課題を省いており、回答スタイル変化と能力変化を完全には分離していない。

### 結果の読み方
PHDSは専門家を新しく作るのではなく、同じパラメータを複数の欠落パターンへSFT中に繰り返し曝露することで、k変更を分布外障害から既知の実行条件へ変える。低kアンカーは最も疎な条件で必要な注意・専門家役割へ終盤の更新を集中し、単一チェックポイントの広い動作領域を作る。
## 品質への影響
実務的にはkを20〜30%下げる範囲で多くのモデル・課題が1〜2%程度以内の相対QA低下に留まるが、範囲はモデル依存である。PHDSは特に複数k間の安定性と回答一貫性を改善する。
## 既存研究との差
動的 MoE、AdaMoE、DynaMoE等はトークン難易度から活性専門家数を変え、同じ要求内でも計算量が揺れる。PHDSは要求単位で一つのkを明示するのでFLOPs・遅延・電力を予測しやすい。Flextron等のmany-in-one LLMは層・幅の可変構造やルータを扱うが、PHDSは既存MoE構造を変えずtop-kだけを制御する。kごとに別Oracleを学習する現行運用と比べ、同一重みのためcross-k出力一致も高い。
## 限界
- 1B〜14.3Bモデル中心で巨大MoEへの拡張は未確認。
- 等サイズrouted エキスパートだけを扱い、partial ルーティングや異種専門家サイズは未評価。
- k_pre/2未満では品質が急落し、任意に広い疎性範囲を保証しない。
- coding・summarization等の生成中心課題を省く。
- 安全なk削減幅はモデル・タスク依存で、サービス側で品質検証が必要。
## 実装状態
既存MoEのtop-kルータへsoft maskとk別補助状態を加える軽量SFT方式。OLMoE/Qwen対応差分と設定JSONは機関承認後公開予定とされ、本文時点で確定リポジトリURLはない。
## 研究上の位置づけ
MoEの疎性を学習時固定ハイパーパラメータから配備時サービスプリミティブへ変える研究で、SLA・負荷・電力に応じた要求単位のモデル弾力性を簡単な制御面で提供する。
