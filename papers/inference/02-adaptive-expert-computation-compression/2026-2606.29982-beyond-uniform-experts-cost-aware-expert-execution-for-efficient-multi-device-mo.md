# Beyond Uniform エキスパート: Cost-Aware エキスパート Execution for Efficient Multi-Device MoE Inference

> ルータ上の寄与が小さい一方で転送・実行に時間がかかり、特に全体処理を遅らせているdevice上のエキスパートを省き、その寄与を実行済みエキスパートへ振り分けてmulti-device MoEを高速化する。

## 概要
Cost-Aware エキスパート実行（CAEE）は、元Top-k内のエキスパートをすべて同じ価値として扱わず、**ルータ上の寄与と実際のハードウェア費用を同時に見て、一部エキスパートを実行しない**近似手法である。

multi-deviceでは各deviceの処理時間が揃わず、最も遅いdeviceが層全体の完了時刻を決める。CAEEは平均的に計算量を減らすのではなく、**その時点で全体を待たせている遅いdeviceの処理を優先して減らす**。

## 手法のあらまし

### 1. `benefit` と `cost` を分けて考える

元Top-kの中でもルータスコアには差がある。一方、GPUキャッシュにないエキスパートはルータスコアが小さくても同じ大きさの重み転送を発生させる。

そこでCAEEは、概念的に

`expertのrouting寄与 / そのexpertを実行するsystem cost`

が小さいエキスパートを省く候補にする。

寄与と費用の比を使うことで、ルータスコアだけを見る動的Top-kとは異なる選択になる。例えばスコア0.08のエキスパートがGPU常駐なら追加費用は小さく実行した方がよい一方、スコア0.10でも別デバイスへの転送と同期を発生させ、そのデバイスが臨界経路なら省く価値が高い場合がある。CAEEは意味的寄与とハードウェア遅延を別軸で測り、同じTop-k集合の中からシステム上の限界費用が大きいエキスパートを探す。

### 2. costには実行時間だけでなく重みの置き場所と転送も入る

エキスパート costはGEMM時間だけではない。

- すでにdevice上にあるか
- GPU キャッシュに無く、CPU等からtransferが必要か
- どのdeviceで実行されるか
- そのdeviceが現在層全体を待たせているか

を含める。

そのため同じエキスパートでも、キャッシュ hit時とmiss時で省く価値が変わる。

### 3. 最も遅いdeviceを優先して軽くする

複数デバイスMoEではデバイスごとの完了時刻に差が出る。速いデバイスのエキスパートを削っても、別デバイスが遅ければ全体遅延は変わらない。

CAEEは平均時間ではなく、**層全体の完了時刻を決めている最遅deviceの処理時間**を短くするエキスパートを優先して省く。

論文ではこの考え方を`straggler-aware`と呼ぶ。ここでstragglerは「他デバイスより遅く、全体を待たせているデバイス」を意味する。

完了時間を短くするには、最遅デバイス以外の仕事を減らしても意味がない。例えばデバイスAが8 ms、Bが12 msで終わる層でAから2 ms削っても層完了は12 msのままであるが、B側の寄与が小さいエキスパートを2 ms分省けば10 msへ短縮できる。CAEEはこの臨界経路性を費用へ入れ、同じ総FLOPs削減でもエンドツーエンド遅延へ反映される場所を優先する。

### 4. 省いたルータ 重みを実行済みエキスパートへ再配分する

省いたエキスパートのルータ 重みは単に捨てず、すでに実行予定のエキスパートや低cost エキスパートへ再正規化する。

重要なのは、この補正のために新しいエキスパートを追加loadしないこと。**I/Oを減らすために別のキャッシュ missを起こしては意味がない**からである。

### 5. training-freeだが近似推論

追加予測器や再学習は不要。ただし元Top-kの一部を実際に省くため、無損失なプリフェッチ／キャッシュ最適化ではない。

training-freeである代わりに、補正は元ルータ scoreと実行済みエキスパートの範囲で行う。省いたエキスパートの重みを新しいエキスパートへ振り直す際、追加loadを必要とする候補は選ばないためI/O削減を相殺しない。これは精度回復の自由度を制限するが、実行時 遅延を確実に減らすための制約である。品質低下を1%未満へ抑えたという結果は、この限定的なrenormalizationとthreshold設定の範囲での実測であり、完全同値ではない。

以上の整理は、提案手法の動作原理と前提条件を保ったまま、一次資料の記述を要約したものである。

## 評価

### まず見るところ
- **結論:** ルータ scoreだけでなく、その時点でエキスパートを実行・転送するcostを見ると、寄与が小さく全体を待たせているエキスパートを優先して省ける。
- **速度:** DeepSeek-R1 671Bのmulti-device実機で遅延を8〜18%削減。
- **品質:** **近似あり**。推奨設定ではaccuracy低下を1%未満に抑える。
- **I/O:** オフロード条件ではGPUにないエキスパートのtransfer削減がTPOT改善へ効く。
- **注意点:** 事前に測ったhardware costへ依存し、帯域やワークロードが大きく変化するとcost推定がずれる可能性がある。

### オフロード条件

バッチ 16ではthresholdによりTPOTを4.36〜23.24%、TTFTを最大6.03%削減した。

推奨threshold 0.8では、全バッチ sizeでTPOTを13.90〜17.09%削減し、MMLU低下0.86%、GSM8K低下0.66%だった。

この結果は、エキスパート数を減らした割合だけでは性能を説明できないことも示す。通信と同期が集中するデバイスを対象にすれば、同じ削減量でも全体の待ち時間に効きやすい。逆に余裕のあるデバイスだけを削っても、臨界経路が変わらず高速化は限定される。

この点が一律削減との違いであり、全体の完了時刻を見て削減箇所を選ぶ明確な理由である。

評価ではこの視点を重視する。

### on-device execution

| バッチ | TPOT 比較対象 | CAEE | 改善 |
|---:|---:|---:|---:|
| 64 | 59.29 ms | 51.66 ms | 12.87% |
| 128 | 68.78 ms | 59.42 ms | 13.62% |

特定層／デバイスでは転送回数を9から3へ減らす例もあり、最も遅いデバイス側のI/O削減が実際の遅延改善へつながっている。

### trade-off

thresholdを強くすると速度は上がるが、native エキスパートを多く省くため品質リスクも増える。したがって本手法は、**速度をどこまで優先するかをthresholdで調整できる近似実行時**と読むのが適切である。
