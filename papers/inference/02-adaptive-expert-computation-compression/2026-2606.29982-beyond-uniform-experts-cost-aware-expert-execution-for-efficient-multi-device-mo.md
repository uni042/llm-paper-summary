# Beyond Uniform Experts: Cost-Aware Expert Execution for Efficient Multi-Device MoE Inference

> router寄与が小さく転送・実行コストが高いexpertをstraggler-awareに省き、既存active expertへ寄与を再配分して多デバイスMoEを高速化する。

## 概要
Cost-Aware Expert Execution（CAEE）は、native Top-k内のexpertをすべて同じ価値として扱わず、**router上の寄与と実際のhardware costを同時に見て、一部expertを実行しない**近似手法である。multi-deviceでは平均costではなく最も遅いdeviceがend-to-end latencyを決めるため、stragglerを狙って削減する。

## 手法のあらまし

### 1. `benefit` と `cost` を分けて考える

native Top-kの中でもrouter scoreには差がある。一方、cache missしたexpertはrouter scoreが小さくても同じ大きさのweight transferを発生させる。

そこでCAEEは、概念的に

`expertのrouting寄与 / そのexpertを実行するsystem cost`

が小さいexpertを候補にする。

### 2. costには実行だけでなくresidencyとtransferも入る

expert costはGEMM時間だけではない。

- すでにdevice上にresidentか
- cache missでtransferが必要か
- どのdeviceで実行されるか
- そのdeviceが現在のcritical pathか

を含める。

そのため同じexpertでも、cache hit時とmiss時でprune候補としての優先度が変わる。

### 3. `straggler-aware`

multi-device MoEではdeviceごとの完了時刻に差が出る。速いdeviceのexpertを削っても、別deviceが遅ければ全体latencyは変わらない。

CAEEは平均時間ではなく、**layer全体の完了を決める最遅deviceのmakespan**を短くするexpertを優先して削る。

### 4. 省いたrouting massを既存active expertへ再配分する

pruneしたexpertのrouter weightは捨てず、すでに実行予定のexpertや低cost expertへ再正規化する。

重要なのは、このcompensationのために新しいexpertを追加loadしないこと。**I/Oを減らすために別のcache missを起こしては意味がない**からである。

### 5. training-freeだが近似推論

追加predictorや再学習は不要。ただしnative Top-kの一部を実際に省くため、losslessなprefetch/cache最適化ではない。

## 評価

### まず見るところ
- **結論:** router scoreだけでなく、今そのexpertを実行・転送するcostを見ると、寄与の小さい高cost expertを省いてstragglerを減らせる。
- **速度:** DeepSeek-R1 671Bのmulti-device実機でlatencyを8〜18%削減。
- **品質:** **近似あり**。推奨設定ではaccuracy低下を1%未満に抑える。
- **I/O:** offload条件ではcache miss transfer削減がTPOT改善へ効く。
- **注意点:** offline profileに依存し、bandwidthやworkloadが大きく変化するとcost modelがずれる可能性がある。

### offloading条件

batch 16ではthresholdによりTPOTを4.36〜23.24%、TTFTを最大6.03%削減した。

推奨threshold 0.8では、全batch sizeでTPOTを13.90〜17.09%削減し、MMLU低下0.86%、GSM8K低下0.66%だった。

### on-device execution

| Batch | TPOT baseline | CAEE | 改善 |
|---:|---:|---:|---:|
| 64 | 59.29 ms | 51.66 ms | 12.87% |
| 128 | 68.78 ms | 59.42 ms | 13.62% |

特定layer/deviceではtransfer countを9から3へ減らす例もあり、straggler側のI/O削減が実際のlatency改善へつながっている。

### trade-off

thresholdを強くすると速度は上がるが、native expertを多く省くため品質リスクも増える。したがって本手法は **quality–latency Paretoを調整するruntime** と読むのが適切である。
