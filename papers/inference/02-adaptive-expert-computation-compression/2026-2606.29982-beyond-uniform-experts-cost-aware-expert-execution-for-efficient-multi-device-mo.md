# Beyond Uniform Experts: Cost-Aware Expert Execution for Efficient Multi-Device MoE Inference

> router上の寄与が小さい一方で転送・実行に時間がかかり、特に全体処理を遅らせているdevice上のexpertを省き、その寄与を実行済みexpertへ振り分けてmulti-device MoEを高速化する。

## 概要
Cost-Aware Expert Execution（CAEE）は、native Top-k内のexpertをすべて同じ価値として扱わず、**router上の寄与と実際のhardware costを同時に見て、一部expertを実行しない**近似手法である。

multi-deviceでは各deviceの処理時間が揃わず、最も遅いdeviceがlayer全体の完了時刻を決める。CAEEは平均的に計算量を減らすのではなく、**その時点で全体を待たせている遅いdeviceの処理を優先して減らす**。

## 手法のあらまし

### 1. `benefit` と `cost` を分けて考える

native Top-kの中でもrouter scoreには差がある。一方、GPU cacheにないexpertはrouter scoreが小さくても同じ大きさのweight transferを発生させる。

そこでCAEEは、概念的に

`expertのrouting寄与 / そのexpertを実行するsystem cost`

が小さいexpertを省く候補にする。

benefit/cost比を使うことで、router scoreだけを見るdynamic Top-kとは異なる選択になる。例えばscore 0.08のexpertがGPU residentなら追加costは小さく実行した方がよい一方、score 0.10でも別deviceへのtransferと同期を発生させ、そのdeviceがcritical pathなら省く価値が高い場合がある。CAEEはsemantic contributionとhardware latencyを別軸で測り、同じTop-k集合の中からsystem上の限界費用が大きいexpertを探す。

### 2. costには実行時間だけでなくweightの置き場所と転送も入る

expert costはGEMM時間だけではない。

- すでにdevice上にあるか
- GPU cacheに無く、CPU等からtransferが必要か
- どのdeviceで実行されるか
- そのdeviceが現在layer全体を待たせているか

を含める。

そのため同じexpertでも、cache hit時とmiss時で省く価値が変わる。

### 3. 最も遅いdeviceを優先して軽くする

multi-device MoEではdeviceごとの完了時刻に差が出る。速いdeviceのexpertを削っても、別deviceが遅ければ全体latencyは変わらない。

CAEEは平均時間ではなく、**layer全体の完了時刻を決めている最遅deviceの処理時間**を短くするexpertを優先して省く。

論文ではこの考え方を`straggler-aware`と呼ぶ。ここでstragglerは「他deviceより遅く、全体を待たせているdevice」を意味する。

makespanを短くするには、最遅device以外の仕事を減らしても意味がない。例えばdevice Aが8 ms、Bが12 msで終わるlayerでAから2 ms削ってもlayer完了は12 msのままであるが、B側のlow-benefit expertを2 ms分省けば10 msへ短縮できる。CAEEはこのcritical-path性をcostへ入れ、同じ総FLOPs削減でもend-to-end latencyへ反映される場所を優先する。

### 4. 省いたrouter weightを実行済みexpertへ再配分する

省いたexpertのrouter weightは単に捨てず、すでに実行予定のexpertや低cost expertへ再正規化する。

重要なのは、この補正のために新しいexpertを追加loadしないこと。**I/Oを減らすために別のcache missを起こしては意味がない**からである。

### 5. training-freeだが近似推論

追加predictorや再学習は不要。ただしnative Top-kの一部を実際に省くため、losslessなprefetch/cache最適化ではない。

training-freeである代わりに、補正は元router scoreと実行済みexpertの範囲で行う。省いたexpertのweightを新しいexpertへ振り直す際、追加loadを必要とする候補は選ばないためI/O削減を相殺しない。これは精度回復の自由度を制限するが、runtime latencyを確実に減らすための制約である。品質低下を1%未満へ抑えたという結果は、この限定的なrenormalizationとthreshold設定の範囲での実測であり、完全同値ではない。

## 評価

### まず見るところ
- **結論:** router scoreだけでなく、その時点でexpertを実行・転送するcostを見ると、寄与が小さく全体を待たせているexpertを優先して省ける。
- **速度:** DeepSeek-R1 671Bのmulti-device実機でlatencyを8〜18%削減。
- **品質:** **近似あり**。推奨設定ではaccuracy低下を1%未満に抑える。
- **I/O:** offload条件ではGPUにないexpertのtransfer削減がTPOT改善へ効く。
- **注意点:** 事前に測ったhardware costへ依存し、bandwidthやworkloadが大きく変化するとcost推定がずれる可能性がある。

### offloading条件

batch 16ではthresholdによりTPOTを4.36〜23.24%、TTFTを最大6.03%削減した。

推奨threshold 0.8では、全batch sizeでTPOTを13.90〜17.09%削減し、MMLU低下0.86%、GSM8K低下0.66%だった。

### on-device execution

| Batch | TPOT baseline | CAEE | 改善 |
|---:|---:|---:|---:|
| 64 | 59.29 ms | 51.66 ms | 12.87% |
| 128 | 68.78 ms | 59.42 ms | 13.62% |

特定layer/deviceではtransfer countを9から3へ減らす例もあり、最も遅いdevice側のI/O削減が実際のlatency改善へつながっている。

### trade-off

thresholdを強くすると速度は上がるが、native expertを多く省くため品質リスクも増える。したがって本手法は、**速度をどこまで優先するかをthresholdで調整できる近似runtime**と読むのが適切である。
