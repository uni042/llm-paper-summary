# Merge, Then Compress: Demystify Efficient SMoE with Hints from Its Routing Policy

> MC-SMoEは、**MoEのrouterがすでに持っている『どのexpertがよく使われ、どのexpertが似た入力を受けているか』という情報を、expert圧縮にも使う**研究である。まず似たexpertを代表expertへ統合し、その後で統合済みweightをさらにlow-rank + sparseに圧縮する。

## 概要

疎活性化Mixture-of-Experts（Sparse Mixture-of-Experts: SMoE）は、1 tokenあたり実際に使うexpertを少数に限定するため、全parameter数を増やしてもFLOPsの増加を抑えられる。一方で、**使わないexpertのweightもmemory上には存在する**ため、推論時のmodel sizeは依然として大きい。

さらに、routerを学習すると複数expertが似た入力を担当するようになり、機能的に冗長なexpertが生まれることがある。つまり「parameterはたくさんあるが、実際には似た仕事をしているexpertが複数いる」という状態である。

この論文は、その冗長性を利用してexpert数を減らす。ただし単純にweightを平均するだけではうまくいかない。

理由は大きく2つある。

1. **expertごとに中間ニューロンの並びが違う。** 同じ機能を表すFFNでも、hidden neuron 1と2を入れ替えて学習できるため、対応しない列同士を平均すると機能が壊れる。
2. **重要expertと低利用expertを同じ重みで平均すると、重要expertの機能が薄まる。**

そこでM-SMoEは、まずexpertのニューロン順序を揃え、routerの利用統計から代表となるexpertを選び、似たexpertをそこへまとめる。MC-SMoEはさらに、merge後のweightが低次元化しやすいという観察を使い、low-rank成分とsmall sparse residualへ分解して圧縮する。

## 問題設定

### MoEは計算量を減らしても、memory量までは減らさない

たとえばSwitch Transformerでは、各tokenが32 expertのうち1つだけを使うとしても、32 expert分のweightは保存しておく必要がある。

したがってMoEは「1 tokenあたりのFLOPs」を抑えるには有効でも、GPU memoryやmodel storageという観点では依然として重い。

特にresource-constrained environmentでは、使われる頻度の低いexpertまで全部保持するのは効率が悪い。

### 低利用expertを単純削除すると品質を失う

expert pruningなら、利用頻度の低いexpertを消せる。しかし利用頻度が低くても、特定のtask / inputだけで重要なexpertかもしれない。

MC-SMoEは「不要expertを捨てる」のではなく、**そのexpertが持つ情報を似た代表expertへ吸収してから消す**方針を取る。

### weightの見た目だけでは『同じ役割』か判断しにくい

2つのexpert weightが数値的に近いからといって、同じ入力を担当しているとは限らない。逆に、weightが直接は似て見えなくてもrouterがほぼ同じtokenを送っているなら、機能は近い可能性がある。

そこでこの論文は、**routerをexpert機能の観測装置として使う**。

router logitの変化を多数inputで観察し、似たinputへ似たrouting scoreを出すexpert同士を近いものとして扱う。

## 手法のあらまし

MC-SMoEは大きく2段階に分かれる。

### 段階A: M-SMoE — expertを減らす

1. calibration dataを元modelへ通し、各expertの利用頻度とrouter logitを記録する。
2. expert間で中間ニューロンの順序を整列する。
3. 利用頻度の高いexpertを代表expert（dominant expert）として残す。
4. それ以外のexpertを、router挙動が最も近いrepresentativeへ割り当てる。
5. 同じgroupのexpertを利用頻度で重み付け平均する。

### 段階B: MC-SMoE — merge済みexpertをさらに圧縮する

6. merge後weightのrank structureを調べる。
7. weightを「low-rankで表せる大部分」と「low-rank近似から外れる残差」に分ける。
8. 残差のうち重要度の低いcolumnをstructured pruningする。
9. 元modelをteacherとしてdistillation fine-tuningし、品質を回復する。

つまり、**expert数を減らす → 残ったexpertの1個あたりsizeも減らす**という2段構成である。

## 手法

### 1. expertのニューロン順序を整列する

各expertは通常2-layer FFNで、概略的には

`input → W_in → activation → W_out → output`

という構造を持つ。

この中間hidden neuronは、同じ順序で `W_in` のrowと `W_out` のcolumnを入れ替えればnetwork機能を変えずに並べ替えられる。

たとえばexpert Aで「neuron 1」がexpert Bでは「neuron 17」に相当している場合、weightをそのまま平均すると異なる機能同士を混ぜてしまう。

M-SMoEは重み照合（weight matching）を使い、**対応するニューロンが同じ位置へ来るようexpertをpermutationしてからmergeする**。

ここは通常のweight averagingとの大きな違いである。

### 2. routing frequencyから『残すexpert』を選ぶ

calibration dataをmodelへ通すと、各expertが何回選ばれたかを数えられる。

M-SMoEでは、この利用頻度をexpert重要度のproxyとして使う。頻繁に選ばれるexpertはdominant expertとして残し、低頻度expertはmerge候補にする。

ただしlayerごとにroutingの偏り方は違う。

- あるlayerでは2〜3 expertにtrafficが集中している
- 別layerでは多くのexpertが比較的均等に使われている

という差があるため、全layerに同じexpert削減率を強制しない。

頻度をlayer内でnormalizeし、model全体でdominant expertを選ぶことで、trafficが均等なlayerには多めのexpertを残し、冗長性の高いlayerは強くmergeする。

### 3. router logitからexpert同士の機能類似度を測る

各input tokenに対してrouterはexpertごとのscoreを出す。

expert `i` と `j` が、多数inputに対してほぼ同じscore変化を示すなら、「同じ種類のinputに反応するexpert」とみなせる。

論文では、calibration token群に対するexpertごとのrouter logit vectorを作り、そのcosine similarityをexpert間距離として使う。

非dominant expertは、**router logit similarityが最も高いdominant expertのgroupへ入れる**。

ここで重要なのは、weight similarityではなく**routing behavior similarity**でgroupingしている点である。

### 4. 利用頻度で重み付けしてmergeする

group内expertを単純平均すると、ほとんど使われないexpertが高頻度expertと同じ強さで最終weightへ影響する。

そこでM-SMoEは

`merged expert = Σ(利用頻度 × expert weight) / Σ利用頻度`

というfrequency-weighted averageを使う。

これによりdominant expertの機能を強く残しつつ、低頻度expertの情報を少量ずつ吸収できる。

直感的には、「main expertを中心に、似たrare expertの差分を少しずつ混ぜる」処理である。

### 5. mergeするとweightがlow-rank化しやすい

論文はmerge前後のweight行列についてstable rankを調べ、merge後に多くのlayerでeffective dimensionalityが下がることを観察している。

stable rankは、単純に非zero singular value数を数えるのではなく、singular value energyがどれだけ少数方向へ集中しているかを見る指標である。

mergeによって似たexpertの共通成分が強まり、ばらばらだった細かいdirectionが平均化されるため、weightがよりlow-rank近似しやすくなるという解釈である。

### 6. `W ≈ UV + S` に分ける

MC-SMoEではmerge後weight `W` を、

- **low-rank成分 `UV`**: weightの主要構造を少数rankで表す
- **残差 `S`**: low-rankだけでは表せない情報

へ分ける。

`U` と `V` のrank `r` を元dimensionよりかなり小さくすれば、dense full matrixを保存するよりparameter数を減らせる。

ただし全部をlow-rankへ押し込むと精度が落ちるため、残りを `S` として保持する。

### 7. 残差はcolumn単位でstructured pruningする

残差 `S` の全要素を保持すれば圧縮効果が弱い。

そこで各weightについて、

`|weight × loss gradient|`

をimportanceとして使い、そのcolumn内で合計する。

importanceの低いcolumnから削ることで、残差を**構造化疎行列（structured sparse matrix）**へ変える。

この形ならunstructured sparsityよりhardware accelerationしやすい可能性があるが、実際のGPU kernelがそのstructureへ最適化されているかは別問題である。

### 8. 最後にdistillationする

M-SMoE / MC-SMoEは完全なtraining-free圧縮ではない。

expert groupingとmatrix decompositionの後、元SMoE modelをteacherとしてknowledge distillationを行い、出力分布を合わせるfine-tuningをする。

したがって「checkpointを変換しただけで即同等品質」という手法ではなく、**圧縮structureを作った後に再調整するpost-training compression**として読むべきである。

## 評価

### まず見るところ

この論文では、memory / parameter / FLOPsは大きく減る一方、**最も強く圧縮したMC-SMoEが必ずしもwall-clock latencyで速いわけではない**。

この点が重要である。

圧縮率だけを見るとMC-SMoEは非常に強いが、low-rank + sparse residualを既存GPU kernelで効率的に処理できないと、dense modelより遅くなることがある。

### 条件

- Switch-Base-32
- fairseq-MoE-15B
- 8 downstream benchmarks
- memory / parameter / FLOPs / task quality / 実GPU latencyを評価

Switch-Base-32では、32 expertを持つ各MoE layerを対象にrouting statisticsを収集してmergeする。

### memory / parameter削減

論文はM-SMoEで最大約60%、MC-SMoEで最大約80%のmemory reductionを報告している。

Switch-Base-32の代表設定では、

- Full: 約2.0B parameters
- M-SMoE: 733M
- MC-SMoE: 381M

まで削減する。

MC-SMoEはexpert mergeだけでなく、merge後expertのlow-rank + sparse compressionを追加するためM-SMoEよりさらに小さい。

FLOPsについても最大約20%削減する。

### 品質

8 taskで評価し、強い圧縮でも元SMoEに近い性能を維持する。M-SMoEでは条件によって元modelより少し改善する場合もあり、冗長expertの統合がregularizationのように働く可能性を示している。

ただしこれは全MoE・全taskで品質不変を保証するものではなく、distillationを含む評価結果である。

### wall-clock latencyは逆転する場合がある

代表的な実GPU測定では、

| 構成 | GPU memory | latency |
|---|---:|---:|
| Full SMoE | 約3895 MB | 約114.3 ms |
| M-SMoE | 約1456 MB | 約106.2 ms |
| MC-SMoE | 約715 MB | 約189.0 ms |

となる。

M-SMoEはexpert数自体を減らすためmemoryもlatencyも改善する。一方MC-SMoEはmemoryをさらに半分程度まで下げるが、**low-rank + sparse residualの演算が既存hardware / kernelへうまくmappingされず、latencyはむしろ悪化**している。

したがってこの論文の「80% memory reduction」「20% FLOPs reduction」を、そのまま「20%以上高速化」と読むべきではない。

## 既存研究との差

### expert pruningとの違い

expert pruningは利用頻度の低いexpertを削除する。

M-SMoEは削除前に、そのexpertをrouter behaviorが似たdominant expertへmergeするため、低頻度expertが持つtask-specific informationを一部残そうとする。

### 一般的なmodel mergingとの違い

通常のmodel soup / weight averagingは、同一initializationからfine-tuneしたmodel同士など、parameter alignmentが比較的揃っている場合を想定することが多い。

SMoE expertは別々のoptimization trajectoryを辿るため、neuron permutationが一致していない。M-SMoEは**permutation alignmentを明示的に行ってからmergeする**。

### 後続のmodern MoE圧縮との関係

後続研究ではMixtral / Qwen / DeepSeekのようなdecoder-only MoEを対象に、

- expert pruning
- expert merging
- shared low-rank basis
- quantization
- routing-aware compression

が多数研究される。

MC-SMoEはその早い段階で、**routing traceをexpert redundancyのsignalとして使う**という方向を明確に示した研究と位置づけられる。

## 限界

- **distillation fine-tuningが必要**で、完全training-freeではない。
- Switch-Base / fairseq-MoE中心で、現在の大規模decoder-only MoEとはarchitecture・routing regimeが異なる。
- routing statisticsはcalibration dataに依存し、deployment trafficが変わればexpert similarity / frequencyも変わり得る。
- low-rank + sparse residualはparameter/FLOPsを減らしても、optimized kernelがなければwall-clock speedupにつながらない。
- expert mergeはlossyであり、元modelと数学的に同値ではない。
- memory削減とcompute削減のどちらを優先するかで適切なcompression ratioが変わる。

## 一般的な実装上の含意

MC-SMoEから得られる重要な示唆は、MoE routerが**dispatchのためだけのcomponentではない**という点である。

router traceには、

- どのexpertが実trafficで重要か
- どのexpert同士が似たinputを担当するか
- layerごとに冗長性がどれくらい違うか

という情報が含まれる。

これはexpert cache、prefetch、placement、quantization、pruningにも使える。

一方、最終的なsystem性能ではparameter数や理論FLOPsだけでなく、**圧縮後matrix structureをGPU kernelが高速に処理できるか**まで確認する必要がある。MC-SMoEのlatency逆転は、この点を非常に分かりやすく示す例である。
