# Merge, Then Compress: Demystify Efficient SMoE with Hints from Its Routing Policy

> MC-SMoEはルータ履歴で似た専門家を代表へ統合し、統合重みを低ランク成分と疎な残差へ圧縮して、専門家数とメモリ使用量を減らす。

## 概要

疎活性化Mixture-of-専門家（Sparse Mixture-of-専門家: SMoE）は、1 トークンあたり実際に使う専門家を少数に限定するため、全パラメータ数を増やしてもFLOPsの増加を抑えられる。一方で、**使わない専門家の重みもメモリ上には存在する**ため、推論時のモデル サイズは依然として大きい。

さらに、ルータを学習すると複数専門家が似た入力を担当するようになり、機能的に冗長な専門家が生まれることがある。つまり「パラメータはたくさんあるが、実際には似た仕事をしている専門家が複数いる」という状態である。

この論文は、その冗長性を利用して専門家数を減らす。ただし単純に重みを平均するだけではうまくいかない。

理由は大きく2つある。

1. **専門家ごとに中間ニューロンの並びが違う。** 同じ機能を表すFFNでも、隠れ neuron 1と2を入れ替えて学習できるため、対応しない列同士を平均すると機能が壊れる。
2. **重要専門家と低利用専門家を同じ重みで平均すると、重要専門家の機能が薄まる。**

そこでM-SMoEは、まず専門家のニューロン順序を揃え、ルータの利用統計から代表となる専門家を選び、似た専門家をそこへまとめる。MC-SMoEはさらに、merge後の重みが低次元化しやすいという観察を使い、低ランク成分と小さい 疎 残差へ分解して圧縮する。


実機GPUのSwitch-Base-32／fairseq-MoE-15B・8下流タスクでFull SMoEを基準に、M-SMoEはメモリ最大約60%削減（代表3895→1456MB、遅延114.3→106.2ms）、MC-SMoEは最大約80%削減（715MB）だが遅延189.0msへ悪化した。

## 問題設定

### MoEは計算量を減らしても、memory量までは減らさない

たとえばSwitch Transformerでは、各トークンが32 専門家のうち1つだけを使うとしても、32 専門家分の重みは保存しておく必要がある。

したがってMoEは「1 トークンあたりのFLOPs」を抑えるには有効でも、GPU メモリやモデル storageという観点では依然として重い。

特にresource-constrained environmentでは、使われる頻度の低い専門家まで全部保持するのは効率が悪い。

### 低利用expertを単純削除すると品質を失う

専門家 枝刈りなら、利用頻度の低い専門家を消せる。しかし利用頻度が低くても、特定のタスク / 入力だけで重要な専門家かもしれない。

MC-SMoEは「不要専門家を捨てる」のではなく、**その専門家が持つ情報を似た代表専門家へ吸収してから消す**方針を取る。

### weightの見た目だけでは『同じ役割』か判断しにくい

2つの専門家 重みが数値的に近いからといって、同じ入力を担当しているとは限らない。逆に、重みが直接は似て見えなくてもルータがほぼ同じトークンを送っているなら、機能は近い可能性がある。

そこでこの論文は、**ルータを専門家機能の観測装置として使う**。

ルータ logitの変化を多数入力で観察し、似た入力へ似たルーティング スコアを出す専門家同士を近いものとして扱う。

## 手法

MC-SMoEは大きく2段階に分かれる。

#### 段階A: M-SMoE — expertを減らす

1. 較正 データを元モデルへ通し、各専門家の利用頻度とルータ logitを記録する。
2. 専門家間で中間ニューロンの順序を整列する。
3. 利用頻度の高い専門家を代表専門家（支配的 専門家）として残す。
4. それ以外の専門家を、ルータ挙動が最も近いrepresentativeへ割り当てる。
5. 同じグループの専門家を利用頻度で重み付け平均する。

#### 段階B: MC-SMoE — merge済みexpertをさらに圧縮する

6. merge後重みのランク 構造を調べる。
7. 重みを「低ランクで表せる大部分」と「低ランク近似から外れる残差」に分ける。
8. 残差のうち重要度の低い列をstructured 枝刈りする。
9. 元モデルをteacherとして蒸留 微調整し、品質を回復する。

つまり、**専門家数を減らす → 残った専門家の1個あたりサイズも減らす**という2段構成である。

## 手法

### 1. expertのニューロン順序を整列する

各専門家は通常2-層 FFNで、概略的には

`input → W_in → activation → W_out → output`

という構造を持つ。

この中間隠れ neuronは、同じ順序で `W_in` の行と `W_out` の列を入れ替えればネットワーク機能を変えずに並べ替えられる。

たとえば専門家 Aで「neuron 1」が専門家 Bでは「neuron 17」に相当している場合、重みをそのまま平均すると異なる機能同士を混ぜてしまう。

M-SMoEは重み照合（重み matching）を使い、**対応するニューロンが同じ位置へ来るよう専門家をpermutationしてからmergeする**。

ここは通常の重み averagingとの大きな違いである。

### 2. routing frequencyから『残すexpert』を選ぶ

較正 データをモデルへ通すと、各専門家が何回選ばれたかを数えられる。

M-SMoEでは、この利用頻度を専門家重要度のproxyとして使う。頻繁に選ばれる専門家は支配的 専門家として残し、低頻度専門家はmerge候補にする。

ただし層ごとにルーティングの偏り方は違う。

- ある層では2〜3 専門家に通信量が集中している
- 別層では多くの専門家が比較的均等に使われている

という差があるため、全層に同じ専門家削減率を強制しない。

頻度を層内でnormalizeし、モデル全体で支配的 専門家を選ぶことで、通信量が均等な層には多めの専門家を残し、冗長性の高い層は強くmergeする。

### 3. router logitからexpert同士の機能類似度を測る

各入力 トークンに対してルータは専門家ごとのスコアを出す。

専門家 `i` と `j` が、多数入力に対してほぼ同じスコア変化を示すなら、「同じ種類の入力に反応する専門家」とみなせる。

論文では、較正 トークン群に対する専門家ごとのルータ logit vectorを作り、そのcosine 類似度を専門家間距離として使う。

非支配的 専門家は、**ルータ logit 類似度が最も高い支配的 専門家のグループへ入れる**。

ここで重要なのは、重み 類似度ではなく**ルーティング behavior 類似度**でgroupingしている点である。

### 4. 利用頻度で重み付けしてmergeする

グループ内専門家を単純平均すると、ほとんど使われない専門家が高頻度専門家と同じ強さで最終重みへ影響する。

そこでM-SMoEは

`merged expert = Σ(利用頻度 × expert weight) / Σ利用頻度`

という頻度-weighted 平均を使う。

これにより支配的 専門家の機能を強く残しつつ、低頻度専門家の情報を少量ずつ吸収できる。

直感的には、「main 専門家を中心に、似たrare 専門家の差分を少しずつ混ぜる」処理である。

### 5. mergeするとweightがlow-rank化しやすい

論文はmerge前後の重み行列についてstable ランクを調べ、merge後に多くの層で実効 dimensionalityが下がることを観察している。

stable ランクは、単純に非zero singular 値数を数えるのではなく、singular 値 energyがどれだけ少数方向へ集中しているかを見る指標である。

mergeによって似た専門家の共通成分が強まり、ばらばらだった細かいdirectionが平均化されるため、重みがより低ランク近似しやすくなるという解釈である。

### 6. `W ≈ UV + S` に分ける

MC-SMoEではmerge後重み `W` を、

- **低ランク成分 `UV`**: 重みの主要構造を少数ランクで表す
- **残差 `S`**: 低ランクだけでは表せない情報

へ分ける。

`U` と `V` のランク `r` を元dimensionよりかなり小さくすれば、密 full 行列を保存するよりパラメータ数を減らせる。

ただし全部を低ランクへ押し込むと精度が落ちるため、残りを `S` として保持する。

### 7. 残差はcolumn単位でstructured pruningする

残差 `S` の全要素を保持すれば圧縮効果が弱い。

そこで各重みについて、

`|weight × loss gradient|`

をimportanceとして使い、その列内で合計する。

importanceの低い列から削ることで、残差を**構造化疎行列（structured 疎 行列）**へ変える。

この形ならunstructured sparsityよりハードウェア accelerationしやすい可能性があるが、実際のGPU カーネルがその構造へ最適化されているかは別問題である。

### 8. 最後にdistillationする

M-SMoE / MC-SMoEは完全な学習-free圧縮ではない。

専門家 groupingと行列 decompositionの後、元SMoE モデルをteacherとしてknowledge 蒸留を行い、出力分布を合わせる微調整をする。

したがって「checkpointを変換しただけで即同等品質」という手法ではなく、**圧縮構造を作った後に再調整するpost-学習 圧縮**として読むべきである。

## 評価

### まず見るところ

この論文では、メモリ / パラメータ / FLOPsは大きく減る一方、**最も強く圧縮したMC-SMoEが必ずしもwall-clock 遅延で速いわけではない**。

この点が重要である。

圧縮率だけを見るとMC-SMoEは非常に強いが、低ランク + 疎 残差を既存GPU カーネルで効率的に処理できないと、密 モデルより遅くなることがある。

### 条件

- Switch-Base-32
- fairseq-MoE-15B
- 8 downstream ベンチマーク
- メモリ / パラメータ / FLOPs / タスク 品質 / 実GPU 遅延を評価

Switch-Base-32では、32 専門家を持つ各MoE 層を対象にルーティング statisticsを収集してmergeする。

### memory / parameter削減

論文はM-SMoEで最大約60%、MC-SMoEで最大約80%のメモリ 削減を報告している。

Switch-Base-32の代表設定では、

- Full: 約2.0B パラメータ
- M-SMoE: 733M
- MC-SMoE: 381M

まで削減する。

MC-SMoEは専門家 mergeだけでなく、merge後専門家の低ランク + 疎 圧縮を追加するためM-SMoEよりさらに小さい。

FLOPsについても最大約20%削減する。

### 品質

8 タスクで評価し、強い圧縮でも元SMoEに近い性能を維持する。M-SMoEでは条件によって元モデルより少し改善する場合もあり、冗長専門家の統合がregularizationのように働く可能性を示している。

ただしこれは全MoE・全タスクで品質不変を保証するものではなく、蒸留を含む評価結果である。

### wall-clock latencyは逆転する場合がある

代表的な実GPU測定では、

| 構成 | GPU メモリ | 遅延 |
|---|---:|---:|
| Full SMoE | 約3895 MB | 約114.3 ms |
| M-SMoE | 約1456 MB | 約106.2 ms |
| MC-SMoE | 約715 MB | 約189.0 ms |

となる。

M-SMoEは専門家数自体を減らすためメモリも遅延も改善する。一方MC-SMoEはメモリをさらに半分程度まで下げるが、**低ランク + 疎 残差の演算が既存ハードウェア / カーネルへうまくmappingされず、遅延はむしろ悪化**している。

したがってこの論文の「80% メモリ 削減」「20% FLOPs 削減」を、そのまま「20%以上高速化」と読むべきではない。

## 既存研究との差

### expert pruningとの違い

専門家 枝刈りは利用頻度の低い専門家を削除する。

M-SMoEは削除前に、その専門家をルータ behaviorが似た支配的 専門家へmergeするため、低頻度専門家が持つタスク-特定 informationを一部残そうとする。

### 一般的なmodel mergingとの違い

通常のモデル soup / 重み averagingは、同一initializationからfine-tuneしたモデル同士など、パラメータ alignmentが比較的揃っている場合を想定することが多い。

SMoE 専門家は別々のoptimization trajectoryを辿るため、neuron permutationが一致していない。M-SMoEは**permutation alignmentを明示的に行ってからmergeする**。

### 後続のmodern MoE圧縮との関係

後続研究ではMixtral / Qwen / DeepSeekのようなdecoder-のみ MoEを対象に、

- 専門家 枝刈り
- 専門家 merging
- shared 低ランク basis
- 量子化
- ルーティング-aware 圧縮

が多数研究される。

MC-SMoEはその早い段階で、**ルーティング トレースを専門家 redundancyのsignalとして使う**という方向を明確に示した研究と位置づけられる。

## 限界

- **蒸留 微調整が必要**で、完全学習-freeではない。
- Switch-Base / fairseq-MoE中心で、現在の大規模decoder-のみ MoEとはarchitecture・ルーティング regimeが異なる。
- ルーティング statisticsは較正 データに依存し、deployment 通信量が変われば専門家 類似度 / 頻度も変わり得る。
- 低ランク + 疎 残差はパラメータ/FLOPsを減らしても、optimized カーネルがなければwall-clock 高速化倍率につながらない。
- 専門家 mergeはlossyであり、元モデルと数学的に同値ではない。
- メモリ削減と計算削減のどちらを優先するかで適切な圧縮 ratioが変わる。

## 一般的な実装上の含意

MC-SMoEから得られる重要な示唆は、MoE ルータが**dispatchのためだけの構成要素ではない**という点である。

ルータ トレースには、

- どの専門家が実通信量で重要か
- どの専門家同士が似た入力を担当するか
- 層ごとに冗長性がどれくらい違うか

という情報が含まれる。

これは専門家 キャッシュ、プリフェッチ、配置、量子化、枝刈りにも使える。

一方、最終的なシステム性能ではパラメータ数や理論FLOPsだけでなく、**圧縮後行列 構造をGPU カーネルが高速に処理できるか**まで確認する必要がある。MC-SMoEの遅延逆転は、この点を非常に分かりやすく示す例である。
