# DSpark: Confidence-Scheduled Speculative Decoding with Semi-Autoregressive Generation

> 並列ドラフトの後半受理率低下を軽量な逐次ヘッドで抑え、較正した接頭辞生存確率と実機処理能力から検証長を負荷適応で配分し、実トラフィックで同等処理能力時のユーザー当たり生成速度を57〜85%改善する。

- **実装**: DeepSeek-AIは学習・評価基盤DeepSpecとDSparkのチェックポイントを公開している。論文ではDeepSeek-V4-Flash/Proの生産エンジンへ組み込み、非同期の動的上位K選択と変長検証用カーネルを実運用したことを報告する。
## 概要
DSparkは、投機的復号で長い候補列を並列生成すると後半ほど受理率が落ち、高並列サービングでは棄却される候補まで対象モデルで検証してバッチ容量を消費するという二つの問題を同時に扱う。深い並列ドラフト本体に軽量な逐次ヘッドを付け、ブロック内のトークン依存を回復して後半の受理率低下を抑える。さらに各位置の接頭辞生存確率を信頼度ヘッドで推定・較正し、実機で事前計測したバッチ規模別処理能力と現在負荷を使って要求ごとの検証長を動的に配分する。Qwen3系列ではEagle3に対する平均受理長を26.7〜30.9%、DFlashに対して16.3〜18.4%改善した。DeepSeek-V4の実ユーザートラフィックでは、同等の総処理能力においてユーザー当たり生成速度をV4-Flashで60〜85%、V4-Proで57〜78%高めた。一方、低受理率の難しい要求でも最初の並列ドラフト生成費用は必ず発生する点が残る。

DSparkの新規性は、並列ドラフトの計算上の利点を維持したまま局所的な逐次依存だけを戻す半自己回帰構造と、各候補位置が実際に受理接頭辞として残る確率を推定し、それを実機のバッチ規模別処理能力へ結び付ける検証スケジューラを一体化した点にある。候補を長く生成できること自体を目的にせず、負荷が軽いときだけ余剰計算を有望な候補へ振り、混雑時は検証長を縮める。さらに生産系では2ステップ前の信頼度だけで次回容量を予測する非同期化によりGPU待ちを避けつつ、当該ステップの候補順位は最新信頼度で決め、分布保存の因果条件を崩さない。

代表結果として、Qwen3系列の平均受理長改善はQwen3-4B / 8B / 14B、提案長7、9ベンチマークのマクロ平均でEagle3に対してEagle3比 +30.9% / +26.7% / +30.0%。深い並列本体と軽量逐次依存の組合せが、浅い自己回帰ドラフトより長い受理接頭辞を作れる。
## 問題設定
投機的復号では軽量なドラフト器が複数トークンを提案し、大きな対象モデルがまとめて検証することで対象モデルの順次実行回数を減らす。しかし完全並列のドラフト器は各位置を互いに独立に予測するため、最初の位置では深い並列モデルの表現力を生かせても、後半では先行トークンが選んだ意味経路を条件にできず、複数のもっともらしい継続が混ざって受理率が急減する。さらに高並列サービングでは、長い候補列を全て対象モデルへ渡すと棄却確率の高い後半トークンも検証バッチを占有し、他要求へ使える計算容量を奪う。固定の検証長や固定閾値は、コードと会話のような要求種別による受理率差、ならびに軽負荷と飽和負荷で変わる検証の機会費用を同時に扱えない。
## 新規性
DSparkの新規性は、並列ドラフトの計算上の利点を維持したまま局所的な逐次依存だけを戻す半自己回帰構造と、各候補位置が実際に受理接頭辞として残る確率を推定し、それを実機のバッチ規模別処理能力へ結び付ける検証スケジューラを一体化した点にある。候補を長く生成できること自体を目的にせず、負荷が軽いときだけ余剰計算を有望な候補へ振り、混雑時は検証長を縮める。さらに生産系では2ステップ前の信頼度だけで次回容量を予測する非同期化によりGPU待ちを避けつつ、当該ステップの候補順位は最新信頼度で決め、分布保存の因果条件を崩さない。
## 手法
### 手法のあらまし
処理はドラフト生成、受理確率推定、検証予算配分、対象モデル検証の四段階で進む。まず対象モデルの文脈表現を受けた深い並列バックボーンがブロック全位置の基礎ロジットと隠れ状態を一度に生成する。次に軽量な逐次ヘッドが、実際にサンプルされた直前トークンの情報を位置順に取り込み、各位置のロジットを補正する。標準設定のマルコフヘッドでは語彙遷移を低ランク分解し、重い変換器層を再実行せずにブロック内依存を加える。並行して信頼度ヘッドは、各位置のドラフト分布と対象分布の全変動距離から導く受理確率を教師として学習し、後処理の逐次温度尺度化によって接頭辞生存確率の過信を補正する。実行時には要求ごとの各候補位置について、そこまで連続して受理される確率を累積値として得る。エンジン起動時に一度だけ計測した検証バッチ規模と毎秒処理ステップ数の表を参照し、有望度の高い接頭辞延長を全要求から貪欲に選び、期待受理トークン数と毎秒ステップ数の積が最大になる検証予算を決める。理論版では目的値が下がった時点で探索を止めて未来候補への依存を防ぐ。生産版ではGPUパイプラインを停止させないため2ステップ前の信頼度から次回の総容量だけを予測し、現在ステップでは最新の累積信頼度で上位候補を選ぶ。最後に対象モデルが選択された可変長接頭辞を一括検証し、標準の拒否サンプリングで受理する。変長要求は物理カーネル上で全トークンを平坦化し、系列境界と依存関係をマーカーテンソルで表現するため、パディングによる無駄を避ける。

### 半自己回帰ドラフト器
深い並列バックボーンは全候補位置の基礎表現を一度の並列計算で作り、その後段だけに軽量な逐次ヘッドを置く。標準のマルコフヘッドは直前にサンプルされたトークンから次位置への補正を低ランクの語彙遷移として計算し、完全な自己回帰ドラフト器のように重い変換器層を位置数だけ繰り返さない。これにより第1位置では深い並列モデルの表現力を保持し、後続位置では実際に選ばれた接頭辞へ条件付けして複数経路の混合を抑える。RNNヘッドも評価されるが、長い提案での追加利得が小さく実装が複雑になるため既定ではマルコフ方式を使う。提案長を4から16へ伸ばしても、バッチ128の1ラウンド遅延増加はDFlash比0.2〜1.3%に収まり、後半の受理長改善へ計算費を集中できる。

### 信頼度推定と較正
各候補位置について、ドラフト分布と対象分布の全変動距離から理論的な1ステップ受理確率を作り、それを信頼度ヘッドの教師信号にする。接頭辞検証では位置単独の確率ではなく、先頭からその位置まで連続して生き残る確率が検証価値を決めるため、推定値を累積して利用する。未較正のヘッドは識別性能が高くても過信する傾向があり、実測ではROC-AUCが0.81〜0.90でも期待較正誤差が3〜8%残る。逐次温度尺度化を適用すると平均誤差を約1%まで下げ、要求間で候補価値を比較できる確率へ整える。固定閾値試験では会話の全体受理率が45.7%から95.7%へ上がり、低価値な後半候補を識別できることを確認している。

### 実機負荷対応の接頭辞スケジューラ
エンジン初期化時に検証バッチ規模ごとの毎秒ステップ数を計測し、軽量な費用表として保持する。実行時には全要求の接頭辞延長候補を累積生存確率の高い順に並べ、候補を一つ追加するたびに期待受理トークン数と実機処理能力の積を更新して、全体の期待トークン処理量が最大になる検証長を要求ごとに決める。理論版は目的値が悪化した時点で停止し、まだ観測していない未来トークンに選択が依存することを防ぐ。実運用版では2ステップ前の信頼度から総容量だけを非同期予測し、現在の候補順位には最新信頼度を使うため、連続GPU実行を止めずに因果性を保つ。軽負荷では1要求あたり約4〜6トークンまで検証を広げ、飽和時には自動的に縮小してバッチ競合を抑える。

### 全体のデータ／制御の流れ
学習時は対象モデルを凍結し、共有埋め込み層と言語モデルヘッドも固定したまま、ドラフト本体・逐次ヘッド・信頼度ヘッドだけを更新する。生産時はDeepSeek-V4の継続実行スケジューラと疎注意カーネルへ統合し、論理的な可変長接頭辞を物理的には平坦なトークン列として処理する。静的な複数トークン予測と異なり、要求内容と現在負荷に応じて対象モデルへ送る検証量だけを変える。
## 評価条件
- **ハードウェア**: オフラインではQwen3-4B、8B、14BとGemma4-12Bを対象にし、1ラウンド遅延はバッチサイズ128、文脈長512/1024/2048/4096トークンの平均で測る。生産評価はDeepSeek-V4-FlashとV4-Proのプレビュー系エンジンへDSpark-5を配備し、実ユーザートラフィックのテレメトリを用いる。GPU型番は本文で開示されていない。
- **ソフトウェア**: 公開のDeepSpec学習・評価基盤とDSparkチェックポイントが提供される。生産系は内部基盤HAI-LLM、連続CUDAグラフ実行、ゼロオーバーヘッドスケジューリング、変長検証向け疎注意カーネルを利用する。
- **比較対象**: Eagle3、DFlash、MTP-1
オフラインではEagle3、DFlash、DSparkを同一フレームワーク・同一データで再学習し、提案長7をそろえて数学、コード、日常会話の9ベンチマークで1ラウンド当たり受理長を比較する。Open-PerfectBlendの130万プロンプトから対象モデル応答を再生成し、各ドラフト器を10エポック学習する。信頼度ヘッドは静的閾値走査と信頼度較正で識別・較正性能を確認する。生産評価ではMTP-1を従来基準として、実トラフィック上のユーザー当たり生成速度と総出力処理量の前線を比較し、複数のサービス水準アンカーで処理量を測る。
オフライン評価はドラフト品質を分離するため信頼度スケジューラを無効化している一方、生産評価は実トラフィックと実エンジンを使う。生産結果はDeepSeek-V4の特定プレビュー構成に基づき、GPU型番、要求分布の完全な公開、他社推論基盤での再現結果は示されないため、数値の外部一般化には制約がある。
## 主要結果
オフラインでは半自己回帰化によって並列ドラフトの後半受理率低下を抑え、Qwen3-4B/8B/14BでEagle3に対する平均受理長を30.9%、26.7%、30.0%、DFlashに対して16.3%、18.4%、18.3%改善した。提案長を7から15へ伸ばすほどDFlashとの差が広がり、長い候補列で逐次依存を戻す効果が大きい。生産系ではMTP-1と比べ、同等の総処理能力でユーザー当たり生成速度をV4-Flashで60〜85%、V4-Proで57〜78%高めた。中程度のサービス水準では総処理量も約51〜52%増え、混雑時には検証長を縮めることで静的な長い候補検証の性能崖を回避した。

- Qwen3系列の平均受理長改善 / Eagle3比 +30.9% / +26.7% / +30.0% (比較対象: Eagle3; 条件: Qwen3-4B / 8B / 14B、提案長7、9ベンチマークのマクロ平均) — 深い並列本体と軽量逐次依存の組合せが、浅い自己回帰ドラフトより長い受理接頭辞を作れる。

- 並列ドラフトに対する平均受理長改善 / DFlash比 +16.3% / +18.4% / +18.3% (比較対象: DFlash; 条件: Qwen3-4B / 8B / 14B、同一フレームワーク・同一データ) — 後半位置へ実際の先行トークン依存を入れることが、完全並列方式の接尾辞劣化を抑える。

- 長い提案での改善 / 提案長15で数学 +30%、コード +26%、会話 +22% (比較対象: DFlash; 条件: Qwen3-4B、5層ドラフト、提案長15) — 候補列が長いほど独立予測の弱点が累積するため、半自己回帰化の相対利得が増える。

- 逐次ヘッドの遅延増分 / +0.2%〜+1.3% (比較対象: DFlash; 条件: バッチ128、文脈長512〜4096の平均、提案長4から16) — 対象モデル検証が主要費用となる高バッチ条件では、軽量逐次補正の追加費用は小さい。

- 信頼度較正 / 期待較正誤差を3〜8%から平均約1%へ低減 (比較対象: 未較正信頼度ヘッド; 条件: 逐次温度尺度化を適用) — 接頭辞生存確率を要求間で比較し、検証予算配分へ使うための確率精度が向上する。

- 生産系のユーザー当たり生成速度 / V4-Flash +60〜85%、V4-Pro +57〜78% (比較対象: MTP-1; 条件: DeepSeek-V4実トラフィック、同等の総処理能力で比較) — 静的な1トークン予測より長い候補を使いつつ、負荷に応じて検証量を絞ることで対話性を高められる。

- 中程度サービス水準の総処理量 / V4-Flash +51%、V4-Pro +52% (比較対象: MTP-1; 条件: 80 tok/s/user と 35 tok/s/user の各アンカー) — 極端な性能境界ではない実用域でも、負荷適応検証が総処理量を押し上げる。

### 負の結果・境界条件
- RNNヘッドはマルコフヘッドより長い候補でわずかな追加利得を示すが、実装複雑性と配備特性を考えると既定方式には採用されない。またDSparkは検証対象を賢く減らせても、各要求で最初に最大長の並列ドラフトブロックを生成する固定費は残る。受理率が本質的に低い難問ではこの前払い計算を回収できず、ドラフト器自体の難易度適応早期終了が将来課題である。厳しいサービス水準で報告される+661%や+406%の総処理量差は、基準MTP-1が低並列の性能境界へ入るため倍率が膨らむと著者自身が注意している。

### 結果の読み方
DSparkの主要な利得は、長い候補を常に検証することではなく、並列生成で安価に候補を用意したうえで、どこまで検証する価値があるかを要求内容と現在負荷の両方から決めることにある。軽負荷では余剰計算を利用して長く検証し、混雑時は棄却確率の高い後半を切るため、単一要求の受理長と全体バッチ効率を同じ制御面で扱える。
## 品質への影響
拒否サンプリングによって対象モデル分布を保つ損失なし方式であり、品質向上を目的とする近似復号ではない。理論スケジューラは未来トークンへ依存しない停止規則を使い、生産版も過去ステップの容量予測のみを使うことで現在トークンの選択バイアスを避ける。
## 既存研究との差
DFlashのような完全並列ドラフトは全位置を一度に作る代わりにブロック内依存を持たず、Eagle3のような自己回帰ドラフトは依存を持つ代わりに提案長に比例してドラフト遅延が増える。DSparkは重い本体を並列のままにして軽い出力補正だけ逐次化する。また固定長・固定閾値の投機的復号と異なり、候補の受理見込みと実機の現在容量を同じ目的関数で扱い、要求ごとの検証長を変える。
## 限界
第一に、並列バックボーンで最大長の候補ブロックを先に生成する固定費があり、低受理率要求では検証前に無駄が発生する。第二に、生産評価はDeepSeek-V4-Flash/Proの特定プレビュー環境と非公開トラフィックに依存し、GPU型番や全エンジン設定が開示されていないため外部環境で同じ前線が得られる保証はない。第三に、ハードウェア処理能力表と2ステップ前予測を使う制御は対象エンジンの容量曲線へ適合させる必要があり、異なるカーネルや連続バッチ方式では再プロファイルが必要である。
## 実装状態
DeepSpecのコードとDSparkチェックポイントが公開されている。論文はDeepSeek-V4の生産系へ実際に配備し、MTP-1を置き換えたと報告しているため、単なるシミュレーションではない。ただし生産用HAI-LLM、ゼロオーバーヘッドスケジューラ、変長検証カーネルの全実装は公開リポジトリだけでは再現できない。
## 研究上の位置づけ
投機的復号系統のうち、ドラフト器設計とサービング負荷制御を横断する研究に位置する。受理長を増やすアルゴリズム研究と、同時要求数に応じて検証予算を配るシステム研究を一つの経路へ統合しており、高並列推論でのバッチ容量を第一級資源として扱う点が重要である。
