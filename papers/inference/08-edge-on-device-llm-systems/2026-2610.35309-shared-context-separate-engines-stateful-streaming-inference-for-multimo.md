# Shared Context, Separate Engines: Stateful Streaming Inference for Multimodal LLMs on Edge SoCs

> 履歴を版付き文脈として公開し、エンジン間でKV状態とプリフィル済み分枝を受け渡せるようにして、取り込みと回答を別エンジンで同時に行い、状態の場所と待ちから配置を決めることで、エッジSoCの複数エンジンを遊ばせないストリーミング推論方式。

## 概要

動画ストリームを見ながら質問に答えるマルチモーダルLLMは、エッジ機器の上で二つの仕事を同時に抱える。新しいフレームをモデルの履歴へ取り込む仕事と、溜まった履歴について質問へ答える仕事である。エッジSoCにはCPU、GPU、NPUがあるのに、llama.cppやMLXのような単一エンジン実行では一つのエンジンが両方を担い、取り込みと回答が互いを待たせ、残りのエンジンは遊ぶ。GPU単独のMLXではM4 MaxのGPU使用率が85から99パーセントに達する一方で、ニューラルエンジンは idle のままである。別のエンジンに回答を引き継がせようにも、履歴は構築したランタイムの中に、そのランタイム固有の形式のKV状態として閉じ込められており、引き継ぎには状態のインポートか再構築が要って、忙しいエンジンを待つより高くつくことがある。

本論文のCrossInferは、論理的な履歴とエンジン固有のKV状態を分けることでこの閉じ込めを解く。履歴は観測が取り込まれるごとに版として公開され、各クエリは「聞かれた時点の版」へ結びつく。版が固定されるため、一つのエンジンが次の版を作り続けながら、別のエンジンが古い版から回答できる。さらに、クエリのプリフィルまで終えた状態を別エンジンへ渡してデコードだけを任せるフェーズ単位の状態継続と、CPUとGPUが別々のクエリへ同時に答える並行実行を備える。配置はSDEP（状態駆動の実行計画）が決め、各エンジンが保持する状態と待ち行列から完了時間を予測する。

**代表結果:** M4 Maxの実ストリーム（32フレーム、毎秒1フレーム、回答128トークン）では、SDEPが95パーセンタイルの応答開始時間（最初のトークンまでの時間）をGPU単独実行の3.56秒から0.86秒へ76パーセント減らし、全クエリが1秒以内に最初のトークンを受けた。状態を持つストリーミング実行は、同じエンジン群を逐次に回す方式の最大2.48倍のスループットを出し、滞留がある条件ではGPU単独よりリクエストスループットが最大35パーセント高い。RK3588の2ストリーム同時実行では単一エンジンより19.6パーセント、状態共有なしの両エンジン並行より27.2パーセント高いスループットだった。実機測定に基づく研究で、出力は逐次実行とトークン単位で一致する。

## 問題設定

問題は三つの資源の不整合として理解できる。第一に実行容量である。取り込みは視覚符号化と文脈のプリフィルからなり、回答はクエリのプリフィルとデコードからなる。段階ごとに得意なエンジンが違い、バッチ1のデコードはM4 MaxではGPUが最速だがRK3588ではCPUが最速で、RK3588では32トークンの生成に568から903ミリ秒かかるのに対し、NPUでの画像符号化は70ミリ秒で済む。単一エンジンに寄せると、段階ごとの得意不得意も、空き容量も使えない。

第二に状態の可搬性である。共有メモリを持つSoCでも、ランタイムごとにバッファとKVキャッシュのレイアウトが違うため、あるエンジンの状態を別のエンジンがそのまま読むことはできない。再利用の仕組みはあっても状態はバックエンド固有であり、空いたエンジンが履歴を引き継ぐには、互換性のあるKV状態をインポートするか、視覚埋め込みとテキストから再構築するしかなく、その費用が待ち時間を上回れば引き継ぎは割に合わない。クエリ全体を1エンジンに割り当てる方式では、デコードが得意なエンジンにも自分のクエリのプリフィルをやらせることになる。

第三に干渉である。CPUとGPUを同時に動かすと共有メモリ帯域を取り合う。RK3588では同時実行でCPUデコードが26パーセント、GPUデコードが11パーセント遅くなり、QCS6490ではCPUとGPUの同時実行でGPUが13.3GB毎秒を保つ一方、CPUの読み取り帯域が15.5GB毎秒から2.4GB毎秒へ落ちる。M4 Maxでは第2の言語エンジンを足すと、ワークロードによってスループットが最大29パーセント上がる場合と45パーセント下がる場合がある。つまり「両方動かせば速い」ではなく、状態の所在地、段階の費用、干渉込みで配置を決める必要がある。本論文の着眼点は、履歴を版として固定して受け渡し可能にし、その上で完了時間の予測で配置を選ぶことにある。

## 手法のあらまし

ストリームは観測を時刻順に供給し、各観測について視覚符号化が埋め込みを作り、文脈取り込みがそれを履歴へ加える。取り込みが完了した履歴は文脈の版として公開され、クエリは既定では到着前に届いた最新の観測に対応する版へ結びつく。その観測がまだ取り込み中なら、版が公開されるまで待つ。クエリのプリフィルは版を根とする私的な回答分枝の上で行われ、デコードはその分枝を伸ばす。新しい観測は取り込み側の根を伸ばして次の版を作るため、回答中の分枝の接頭辞やトークン位置は変わらない。実行の担い手は言語レーンと呼ばれる、エンジンに固定されたランタイムのワーカーで、クエリは対応する受け渡し境界で別のレーンへ移れる。モードは二つある。一つは、あるレーンが新しい観測を取り込みながら別のレーンが公開済みの版から答える状態持ちストリーミング生成で、もう一つはCPUとGPUのレーンが別々のクエリへ同時に答える並行シーケンス生成である。視覚符号化はNPUが担い、両モードで言語実行と重なる。SDEPは取り込み、クエリのプリフィル、デコードのそれぞれについて、状態の所在地と段階費用と待ち行列から完了時間を予測して配置を決める。

## 手法

### 1. 版付き文脈と回答分枝 — 履歴を固定して、取り込みと回答を切り離す

この機構が観測するのは観測の到着と取り込みの完了である。保持する状態は、版として公開された履歴と、版を根として各クエリが持つ私的な回答分枝であり、分枝を参照する回答や受け渡しが残っている間は状態を保持する。行う動作は、取り込みが終わった履歴を版として公開し、クエリをその版へ結びつけ、プリフィルとデコードは分枝の上だけで進めることである。新しい版の公開は、実行中の回答が結びついた接頭辞もトークン位置も変えない。減るボトルネックは、共有履歴を回答の間ロックすることと、回答ごとに履歴全体を複製することの両方で、取り込みは回答を待たずに進み、回答は取り込みに割り込まれない。追加で消費する資源は、版と分枝の管理と、参照が残る間の状態の保持である。失敗条件は、応答を入力へ戻す使い方で、その場合は回答を後の版へ加えてから依存するクエリを走らせる必要がある。また、ハイブリッドモデルでは分枝が注意のKV接頭辞を共有しても回帰状態は接頭辞へ切り戻せないため、各回答は結びついた接頭辞を完了まで保持する。正しさの基準は明確で、各回答は、結びついた履歴を順に取り込んで同じエンジンでデコードした逐次実行と一致しなければならない。

### 2. エンジン間の状態継続 — 履歴とプリフィル済み分枝を受け渡す

この機構が扱うのは、レーンが必要な履歴をどう用意するかである。用意の経路は3通りある。再利用は、レーンが既に持つ状態を分枝として分ける方法で、接頭辞、トークン位置、モデル設定、表現形式が一致する場合に使える。インポートは、互換性のあるKV状態と位置のメタデータを別のバックエンドから移す方法で、費用は履歴の大きさとともに増える。再構築は、保持してある視覚埋め込みとテキストをプリフィルし直す方法で、視覚符号化はやり直さないため、どの言語エンジンでも履歴を続けられる。受け渡しの境界は2種類ある。文脈の受け渡しは公開済み履歴のKV状態と位置を渡し、受け手がクエリのプリフィルから行う。フェーズ単位の状態継続は、クエリのプリフィルまで終えた分枝を渡し、受け手は生成から直接始められる。M4 MaxではMetal側が分枝のKV状態、位置、プリフィル最後のロジットをCPUへ送り、CPUが最初のトークンをサンプリングしてデコードを続け、その間にMetalは取り込みへ戻る。減るボトルネックは二つある。プリフィルが速いエンジンにプリフィルを寄せることで、プリフィルが遅い受け手は自分の時間をデコードに使え、履歴の再計算も避けられる。RK3588ではGPUの文脈をインポートすることで、接頭辞を再計算する場合の1482ミリ秒に対して319ミリ秒と、最初のトークンまでの時間が4.6倍短くなった。追加費用は状態の転送そのもので、視覚トークンは記述子を共有するバッファ管理を介して渡し、コピーを避ける。M4 Maxではこの記述子の受け渡しが直列化とコピーをする方式に対して転送の往復を12.1分の1にした。失敗条件は表現形式の不一致で、その場合は再構築へ落ちる。またフェーズ単位の継続は、文脈の受け渡しより元のエンジンから移す仕事が少ない代わりに、受け手が早く回答を終えて次のクエリを受けられる利点と引き換えになる。

### 3. SDEP — 状態の所在地と待ち行列から完了時間を予測して配置する

SDEP（状態駆動の実行計画）が観測するのは、各レーンが保持する状態、実行中と待ち行列の仕事量、段階ごとの処理時間である。保持する状態は、同時実行時の処理時間の移動平均で、NPUの視覚処理を含む干渉を織り込む。行う動作は、クエリごとに単一レーンでの完了時間を見積もることで、待ち時間、そのレーンで最も安い経路で結びついた文脈を用意する時間、プリフィルと生成の時間の合計として計算し、最も早く終わると予測した経路を選ぶ。分割経路ではプリフィル、状態転送、受け手の空きの依存関係まで見積もりに入れる。忙しいレーンでも、再利用の利得や処理時間の優位が待ち行列の遅れを上回れば選ばれる。取り込み側については、次の版の用意と観測されたクエリ処理の負荷から見込まれる負荷が小さいエンジンへ置く。ライブストリームではさらに、取り込みレーンの見込み時間がクエリ到着間隔の予算を超える場合に、適格なクエリを空いた第2レーンへ寄せて、取り込みレーンが回答に使う量を調整する。この調整では、受け渡しで取り込みレーンに返ってくる時間から書き出し費用を引いた分を数える。減るボトルネックは、状態を持たない空きエンジンを選んで再構築を払う誤配置と、状態を持つ忙しいエンジンへ詰め込む誤配置の両方である。RK3588の9通りの履歴と滞留の組み合わせでは、SDEPは毎回速いほうのエンジンを選んだ。追加費用は段階費用の計測と予測計算で、判断はバックエンドへの投入と完了の境界で行う。失敗条件は費用の予測ずれで、同時実行の干渉がプラットフォームごとに大きく違うため、移動平均による追随が前提になる。

### 4. バックエンド実現 — プラットフォームごとに使える継続経路が違う

配置の選択肢はバックエンドの対応で決まる。M4 Maxでは視覚符号化をニューラルエンジンかGPUが行い、言語はggmlのCPUとMetalの2バックエンドが両方向の状態継続に対応し、KV表現を共有するためレイアウト変換が要らない。CPU側は版の正確な接頭辞長で分枝を分け、Metal側は取り込みの根と回答分枝を分けて持つ。RK3588とQCS6490では視覚符号化をNPUが行い、言語レーンはCPUとGPUで、GPUからCPUへの状態継続により、GPUが履歴を伸ばしながらCPUが結びついた版から答えられる。MNNがGPUの状態を書き出してCPUレーンへ取り込む。RK3588では取り込みエンジン自体も実行時にSDEPが選ぶため、どちらのレーンも後続クエリのための文脈を構築できる。減るボトルネックは、プラットフォーム固有の制約を計画側へ正直に渡すことで、使えない経路を前提にした配置を避けられる点にある。追加費用はバックエンドごとの統合実装であり、論文は付録にニューラルエンジン向けバックエンドとコンパイルの詳細を持つ。失敗条件は、表現が共有できないバックエンドの組で、その場合はインポートが使えず再構築の費用で判断することになる。

## 評価

### まず見るところ

- **結論:** 状態を受け渡せるようにすることが利得の源泉で、状態共有なしに両エンジンを並行させる方式より27.2パーセント高いスループットが出た。単にエンジンを増やすのではなく、履歴を移動可能にしたことが効いている。
- **速度・効率:** M4 Maxの実ストリームで95パーセンタイルの応答開始時間が3.56秒から0.86秒へ下がり、単一リクエストでも最初のトークンまで227ミリ秒とMLXの244ミリ秒、llama.cppの255ミリ秒を下回った。単一リクエストのエネルギーもllama.cppより23.6パーセント少ない。
- **品質:** 実行場所を変えるだけなので品質の交換はなく、全プラットフォームで出力トークンと最初のステップのロジットが逐次実行と一致した。状態継続を使った96件の回答もすべて一致している。
- **メモリ・入出力:** 版と分枝の保持が追加のメモリを使うが、FastVLMの評価ではGPU単独よりピーク常駐メモリが10パーセント少ない設定もあった。帯域の奪い合いが利得を消す条件は第5.5節で切り分けられている。
- **評価の強さ／注意点:** 3プラットフォームの実機測定で、外部の比較対象、単一レーンの対照、機構ごとのアブレーション、出力一致の確認まで揃っている。一方で、モデルはエッジ向けの規模が中心で、利得の符号がプラットフォームとワークロードで逆転する条件も結果に含まれている。

数値の読み方では、2.48倍という最大値は「同じエンジン群を逐次に回し、文脈再利用もない」比較対象に対するもので、日常的な比較対象であるGPU単独と文脈再利用ありに対しては、応答開始時間の76パーセント減やスループットの9.3から35パーセント増として読むべきである。機構ごとの寄与は段階的に積み増す形で測られており、完了時間による振り分け、到着率に応じた容量調整、フェーズ単位の状態継続が順に応答開始時間を下げていく。

### 感度・スケーリング・ストレス条件

第2レーンの効果はプリフィルとデコードの相対費用で決まり、プラットフォームで傾向が逆転する。M4 Maxでは9設定中6設定で改善し、短いプリフィルと中程度の生成では最大29.3パーセント増えたが、プリフィル1024トークンと出力8トークンでは44.8パーセント悪化した。RK3588ではプリフィルが長いほど利得が増え、生成が長いほど帯域の競合で利得が縮む。同時実行数の掃引ではRK3588で最大52.0パーセントのスループット増があった。視覚と重なりの効果は回答が短いほど大きく、Qwen3.5系では回答32トークンで最大72.4パーセント、128トークンで23.9パーセントだった。サーバー級GPUやデータセンター規模での評価は未評価である。

### 立ち上がり・内部挙動

段階費用は実行前に補間と再生で予測でき、64トークン実行のセッション時間の予測は実測の1.3パーセント以内だった。SDEPの内部挙動として、RK3588の9通りの履歴と滞留の条件すべてで速いほうの固定方針と同じ選択をしたことが示されている。履歴が長い8フレーム条件では、短い滞留の下でCPUの再利用を待つことが完了時間を72.7パーセント短くし、長い滞留では逆に空いたGPUを使うことが31.6パーセント短くするなど、条件で最適が入れ替わる様子も記録されている。

- エッジSoCの3プラットフォームに限られ、サーバー級の推論基盤での挙動は未評価である。
- 利得の符号がワークロードとプラットフォームで逆転する条件があり、常に速くなる方式ではない。
- モデルはエッジ向け規模が中心で、27B級が最大である。
- 段階費用の移動平均による干渉の追随が前提で、急な負荷変動時の判断の質は未評価である。

## 既存研究との差

異種プロセッサ推論の先行研究は、モデルのモジュールをプロセッサへ配置したり、符号化、プリフィル、デコードの段階へ資源を割り当て直したりするが、ストリームの言語状態をエンジン間で続けることは扱わなかった。文脈再利用の先行研究は履歴の再計算を省くが、状態はバックエンド固有のままである。プリフィルとデコードの分離は主にクラウドの別マシン間で行われてきた。本論文の差は、履歴を版と分枝という論理単位で管理し、KV状態とプリフィル済み分枝をSoC内の異種エンジン間で受け渡せるようにした点と、配置判断が状態の所在地を完了時間の予測の形で直接使う点にある。動画のKV再利用で解析と質問応答を分ける方式に対しても、版管理によって「どの時点の履歴へ答えているか」を保ったまま実行場所を変えられる点が違う。

## 限界・実装状況

- ハードウェア依存条件が強く、段階費用と干渉の大きさはプラットフォームごとに違い、利得が出る条件もSoCごとに異なる。新しいSoCでは費用の計測から始める必要がある。
- ワークロード依存条件として、プリフィルが長く生成が短い条件では第2レーンが逆効果になる場合があり、SDEPの予測が外れると単一エンジンより遅くなりうる。
- ハイブリッドモデルでは回帰状態を接頭辞へ切り戻せないため、分枝の保持の仕方に制約がある。
- 実装は3プラットフォーム向けに作り込まれており、公式コードは公開されているが、上流ランタイムへ統合された汎用機能ではなく研究実装である。
- 品質面のリスクは低く、出力一致が確認されている一方、数値表現が異なるバックエンド間での受け渡しでは一致の前提が崩れうる点は、論文の範囲では限定的にしか確認されていない。

## 一般的な実装上の含意

第一に、状態を持つ推論では、状態を「どのエンジンのどの形式で存在するか」ではなく「どの版の履歴か」という論理単位で管理すると、実行場所の自由度が大きく上がる。第二に、配置判断の入力はエンジンの空き状況だけでなく、状態の所在地と用意の費用を含めるべきで、空いているが状態を持たないエンジンは、忙しいが状態を持つエンジンより遅いことがある。第三に、異種エンジンの同時実行は帯域の奪い合いで逆効果になりうるため、干渉込みの実測費用で判断し、利得の符号が条件で変わることを前提に設計すべきである。第四に、プリフィルとデコードの分離は、状態を受け渡す境界を用意すればマシン間だけでなくSoC内のエンジン間でも成立する。
