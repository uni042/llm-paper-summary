# Transition-Aware Backend Dispatch for Edge LLM Inference

## 概要

エッジ端末で変換器を動かすとき、モデル全体をCPUかGPUの一方へ固定する方法は管理しやすい反面、演算の形状ごとに実行性能が変わる点を拾えない。逆に各演算を個別に最速の実行先へ送ると、GPUとCPUの間、またはPyTorchとONNXの実行基盤の間を行き来し、同期やデータ変換の費用が積み上がる。著者らは、対象演算の形状情報だけでなく、直前に選んだバックエンドも使い、演算が速くなる利得より切替費用が大きい場合は実行先を維持する選択方式を調べる。

評価では、7つのモデル実行から抽出した線形層、MLP活性化、RMSNorm、LayerNormの9,584演算を278種類の厳密な形状・文脈グループへまとめる。Jetson Orin NanoでPyTorch CPU、PyTorch CUDA、ONNX CPUの演算費用と切替費用を計測し、モデル由来の並び順で費用を再生する。最良の静的バックエンドに比べた平均改善は遅延17.4%、エネルギー14.4%、エネルギー遅延積（EDP）28.5%だった。ただし、これは統合実行基盤上の全モデル実行で得た改善率ではない。

## 問題設定

同じ変換器でも、行列積、MLP活性化、正規化処理では計算量とメモリアクセスの比が異なり、入力系列長・隠れ次元・データ型などの形状によってもCPU、GPU、実行基盤ごとの得意不得意が変わる。そのため全演算を一つの場所へ固定すると、少なくとも一部の形状でより速い選択肢があっても使えない。

演算ごとの独立選択は形状差を利用できるが、ある演算の直後に別デバイスや別の実行基盤へ切り替える必要が出る。切替には同期、データ移動、テンソル形式変換、実行文脈の切替が伴い得る。個々の演算で節約した時間・電力がこれらを下回れば、局所最適の積み重ねがトレース全体では損になる。本研究の問いは、演算の局所費用だけでなく直前の選択先との遷移費用も織り込むと、エッジ推論の順序付き処理を改善できるかである。

## 手法のあらまし

著者らは7モデルをJetson上で実行し、モデル由来の演算順序と形状情報を記録する。対象は線形層、MLP活性化、RMSNorm、LayerNormに限り、同じ演算種類・フェーズ・テンソル形状・データ型・出力サイズをもつ項目をまとめる。278個の形状グループそれぞれを三つのバックエンドで個別に測り、演算費用と切替費用の表を作る。次に、演算の特徴だけを使う演算局所選択器と、直前のバックエンド状態も特徴に加える遷移考慮選択器を学習する。最後に元の順番を保ったまま選択器を各演算へ適用し、予測先に対応する計測費用と切替費用を累積する。対象外演算は選択器に入れず、静的な実行先を維持する。

## 手法

### 形状別計測と費用表

トレースはQwen2.5-0.5B、Qwen3-0.6B、TinyLlama-1.1B、SmolLM2-135M、SmolLM2-360M、OLMo2-1B、ModernBERT-baseから採取した。入力はバッチ1・FP32で、長さ16、32、64、128の「hello」反復トークン列を使用する。因果言語モデルのデコード部分は、KVキャッシュを使って連続生成する完全なループではなく、長さ1の前向き計算を一度行ったトレースである。したがって、この測定は入力形状と演算順序を制御するためのもので、文章生成品質を比較していない。

対象演算は9,584個あり、演算種類・フェーズ・テンソル次元・データ型・出力サイズが一致するものをまとめると278形状グループとなる。各グループをPyTorch eager CPU、PyTorch eager CUDA、ONNX CPUで独立に計測し、合計834の形状・バックエンド行を得る。レイテンシと稼働電力を測り、同じ反復回数で測ったアイドル電力を引いて演算の電力分を推定する。電力と遅延からエネルギー、エネルギーと遅延からEDPを算出する。全保持行はPyTorch CPU出力を参照にしたFP32許容誤差検査を通過したと報告される。

### 直前の実行先を使う選択

演算局所選択器は現在の演算特徴から、遅延・エネルギー・EDPそれぞれを最小化するバックエンドを予測する。遷移考慮選択器はこれに前の対象演算で選択したバックエンドを加え、候補先ごとの費用を「演算そのものの費用＋前の実行先から候補先への有向切替費用」として扱う。同じバックエンドを続ける場合は切替費用をゼロとし、別の実行先なら元の実行先から候補先へ切り替えたときの実測値を使う。遅延と電力量を合わせたEDP用の費用も作り、各形状を直前の3種類×候補の3種類へ展開した2,502行の候補表を構成する。

Extra Trees、ランダムフォレスト、クラス重み付きロジスティック回帰、ヒストグラム勾配ブースティングを比較し、形状ID単位のGroupKFoldで同じ形状由来の行が訓練と検証に分かれないようにする。報告対象の遷移考慮モデルにはHistGBMを選び、乱数seedは42とする。これは次の一演算に対して現在の形状と直前状態から貪欲に決める選択であり、未来のトレース全体を見て最適なバックエンド列を解くものではない。

### 順序を保つ費用再生

評価では実行済みモデルのトレース順序を保ち、選択先に対応する測定済み演算コストと方向付きの遷移ペナルティを引いて合計する。対象外演算は全方式で同じ静的割当てのままである。したがって、実際に単一モデルを複数のバックエンドへまたがって動かし、モデル出力まで通したランタイム統合評価ではない。選択器、接続済みモデル実行によるフレームワーク負荷、統合ディスパッチャのオーバーヘッドも再生値には含まれない。

再生時にはバックエンド、デバイス、実行基盤の切替数も別々に記録する。演算局所選択と遷移考慮選択との差をこれらの回数で見ることで、遷移状態を加えた方式が時間・電力量の和だけでなく切替の頻度にもどう影響したかを示す。切替回数の分類と費用再生はいずれも、ベンチマークで対象とした三つのバックエンドと七つのモデル由来トレースに限定される。

## 評価

### 実験条件

| 項目 | 設定 |
|---|---|
| 装置・電力設定 | NVIDIA Jetson Orin Nano、25 Wモード、強制クロックなし |
| ソフトウェア | JetPack 6.2 / L4T R36.4.3、CUDA 12.6、PyTorch 2.8.0、ONNX Runtime 1.23.2、Python 3.10.12 |
| モデル | Qwen2.5-0.5B、Qwen3-0.6B、TinyLlama-1.1B、SmolLM2-135M/360M、OLMo2-1B、ModernBERT-base |
| 入力 | 合成「hello」反復入力、バッチ1、FP32、プリフィル長16/32/64/128。デコードは因果モデルごとに長さ1の前向き計算 |
| 対象 | Linear、MLP活性化、RMSNorm、LayerNormの9,584演算、278形状、3バックエンド |
| 計測 | 3回ウォームアップ後に公称500回。短い演算は適応反復し、保持行は10〜27,077回、中央値778回。VDD_INをtegrastatsで50 ms間隔サンプリング |
| 正確性 | PyTorch CPU出力を参照しFP32許容誤差を確認。生成品質や言語タスク精度は対象外 |

### 比較方式

| 方式 | 実行先の選び方 |
|---|---|
| 静的割当て | トレース全体で単一バックエンドを使い、切替を避ける |
| 演算局所 | 現在の対象演算特徴ごとに最小コスト先を独立選択する |
| 遷移考慮 | 現在特徴と直前のバックエンドを見て、演算コストと次の切替コストの和を最小化する |

### 主な結果

| 指標 | 最良静的割当て（平均／トレース） | 遷移考慮（平均／トレース） | 改善率 |
|---|---:|---:|---:|
| 遅延 | 4,782.0 ms | 4,012.4 ms | 17.4% |
| エネルギー | 39.10 J | 34.07 J | 14.4% |
| EDP | ― | ― | 28.5% |

改善率は各モデルのトレースごとに最良静的方式と比べてから平均したため、演算数の多いトレースが平均を支配しない。EDPは累積エネルギー×累積遅延で算出する。最大の個別結果はSmolLM2-135Mで、静的割当てに比べ遅延37.1%、エネルギー32.0%、EDP57.3%を改善した。一方ModernBERT-baseとOLMo2-1BのEDP改善はそれぞれ14.2%、14.1%で、トレース形状分布によって効果は大きく異なる。

### 選択器の予測誤差

Table Iの精度は演算局所の遅延・エネルギー・EDPで0.8741/0.8705/0.8597、遷移考慮では0.8921/0.8897/0.9005だった。regret（最良候補との差分コスト）は各方式・目的で0.0052〜0.4094%の範囲に収まる。ただし、二方式は決定文脈の件数やラベルとなるコストが異なるため、精度値を同じ母集団の直接的な優劣として比較しない。

### 遷移考慮の追加効果とモデル外し評価

演算局所選択から遷移考慮へ変えると、静的割当て比の平均遅延改善は16.8%から17.4%、エネルギー改善は13.7%から14.4%、EDP改善は27.4%から28.5%へ増えた。より目立つ変化は切替回数であり、演算局所選択と比べバックエンド切替を目的別に14.0〜14.9%減らし、デバイス切替を最大19.7%、実行基盤切替を最大17.6%減らした。従って静的方式を上回る主な理由は形状別の演算選択で、直前状態を考慮する追加の役割は小さな費用利得と切替の抑制にある。

モデルを一つずつ訓練から外す評価では、遅延とEDPは7モデル中6モデル、エネルギーは7モデルすべてで静的方式を上回る。平均改善率は遅延12.51%、エネルギー12.96%、EDP23.68%。ただしエンコーダ型ModernBERT-baseを未見モデルとした場合は、エネルギーこそ2.61%改善するが、遅延は15.49%、EDPは6.10%悪化する。著者らは形状分布が訓練時の主なデコーダ型トレースと異なることを理由として挙げる。

## 既存研究との差

現行リポジトリのエッジ系統には、FreeToken（[arXiv:2608.16157](https://github.com/uni042/llm-paper-summary/blob/main/papers/inference/08-edge-on-device-llm-systems/2026-2608.16157-freetoken-efficient-edge-native-moe-serving-with-bandwidth-adaptive-execution.md)）のようにGPU/CPU処理分担・専門家/KV配置・PCIe帯域を動的に調整するMoEサービングや、ATSInfer（[arXiv:2607.10183](https://github.com/uni042/llm-paper-summary/blob/main/papers/inference/08-edge-on-device-llm-systems/2026-2607.10183-atsinfer-automated-tensor-scheduling-hybrid-cpu-gpu.md)）のようにテンソル常駐と転送を組み合わせるCPU/GPU推論がある。これらはモデルやテンソルの配置・搬送、計算の重ね合わせを主に扱う。本論文はその隣に位置する演算グラフ実行層の問題として、線形・活性化・正規化ごとに既存バックエンドを選び、遷移の向きと前状態を費用に加える点が異なる。さらに、TVMやAnsorなどのコンパイラ・スケジュール探索が新規スケジュールやカーネルを生成・選択するのと異なり、ここでは既存のPyTorch/ONNX eagerバックエンドから選ぶ。位置づけとしては、既存エッジLLM方式を置き換える圧縮やサービングスケジューラではなく、異種CPU/GPU実行における選択粒度と切替モデルを具体化する実証である。

## 限界・実装状況

- 提案の主結果は、実測した個別演算と切替の費用をトレース順に合算する再生結果であり、切替込みのモデル全体を統合ランタイムで実行した比較ではない。統合ディスパッチャやフレームワーク間の変換・運用オーバーヘッドは含まれない。
- 対象はJetson Orin Nano上のFP32、3バックエンド、4演算種、7モデルに限る。別装置・別クロック・量子化や融合カーネルでの費用順位はこの結果からは判断できない。
- 合成反復入力による演算形状・順序の採取が中心で、言語タスクの生成品質・実ユーザー負荷、複数同時要求への影響は評価していない。デコードトレースもKVキャッシュを伴う生成ループ全体ではない。
- 遷移考慮方式は一つ先の状態のみを使う因果的な貪欲選択で、将来演算列を使った大域最適化ではない。モデル外し評価でもModernBERTの遅延・EDPは悪化しており、異なる形状分布への一般化が課題として残る。
- 論文は統合実行基盤、注意計算・KVキャッシュ演算、量子化演算、融合カーネル、ONNX CUDA/TensorRTを今後の拡張として挙げる。
- 論文は匿名化された公開実装を案内するが、この調査では公開物の実行・再現は行っていない。

## 一般的な実装上の含意

エッジ推論で演算単位の異種実行を導入する際は、各演算の単体ベンチマークだけでバックエンドを選ばず、デバイス間転送・同期・フレームワーク変換を方向付きの遷移費用として分けて測る必要がある。特に演算局所選択と遷移考慮選択を別の比較群にすれば、改善が形状別実行先選択から来るのか、切替抑制から来るのかを区別できる。ただし本論文の費用再生から、本番ランタイムの純便益が同じになるとは結論できない。
