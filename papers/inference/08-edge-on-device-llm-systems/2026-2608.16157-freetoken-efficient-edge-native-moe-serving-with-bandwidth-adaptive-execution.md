# FreeToken：帯域に応じたCPU・GPU協調実行で端末上の巨大MoEを配信する仕組み

## 概要

FreeTokenは、混合専門家モデル（Mixture of Experts、MoE）の全専門家重みがGPUメモリに収まらない場合に、GPU・CPU・主記憶・PCIeを一つの推論基盤として使うローカル配信システムである。MoEでは一つのトークンが少数の専門家だけを使うため、実際の計算量は総パラメータ数より小さい。しかし専門家全体の重みは大きく、必要な専門家を毎回GPUへ移すと転送待ちが増える。単純にCPUへ専門家計算を任せても、一般的な端末の主記憶帯域が限界になる。

FreeTokenは事前処理と逐次生成で異なる戦略を採る。事前処理では多数トークンがほぼ全専門家を通るので、層全体の重みを二重バッファで先読みしてGPU計算と転送を重ねる。逐次生成では専門家の呼出しに時間的局所性があるため、全層で共有する最近使用順キャッシュを使い、GPUにない専門家だけをPCIe転送とCPUでの直接実行に分配する。さらに、対話履歴が編集される位置に再帰状態のチェックポイントを残し、不要な事前処理のやり直しを減らす。GPUメモリの専門家キャッシュとKVキャッシュの割当も実行中に変更できる。

論文は6台の装置と実際の数学・コード修正・ツール利用・メール/予定表操作を含む4種類のエージェント負荷で評価した。RTX 5090ではQwen3.6-35B-A3Bが77～83トークン/秒、DeepSeek-V4-Flashが22～25トークン/秒で、各条件の最良比較方式に対して1.5～2.3倍の生成処理能力を示した。8GBのRTX 4060ノートPCでは35B級のNVFP4モデルを39.3トークン/秒で実行し、RTX PRO 6000一基では753B級GLM-5.2を14.9トークン/秒で実行した。ただし、重み形式、CPU主記憶容量、PCIe帯域、対応するCUDA環境が揃った実験結果であり、任意の端末で同じ速度が出る保証ではない。

## 問題設定

長い入力を事前処理すると、各トークンが異なる専門家を選ぶため、ある層で実際に必要となる専門家の和集合はほぼ全体へ広がる。したがって、逐次生成時に一部専門家だけを使うというMoEの疎性は、事前処理時の重み転送量を十分には減らさない。論文のDeepSeek-V4-FlashのFP4構成では約140GBの専門家重みを転送する必要があり、RTX 5090のPCIe 5.0 x16なら約2秒、PCIe 4.0 x16級なら約5秒、ノートPCのx8接続なら10秒以上かかる条件がある。

一方、逐次生成では隣り合うトークンが似た専門家を呼ぶ傾向がある。固定配置方式はその変化へ追従できず、GPUにない専門家をCPUで実行するか、PCIeで移すかの二択を固定しがちである。CPU主記憶帯域はPCIeと同じ主記憶を共有するため、転送とCPU計算を同時に実行する場合、両方へ無制限に帯域を割り当てられない。FreeTokenは、装置上で実測した帯域を使い、専門家のキャッシュ未命中を二つの実行経路へ分配する。

エージェント利用ではツール呼出しや履歴圧縮で文脈が編集され、長い接頭部を繰り返し事前処理する問題もある。特に再帰型・混合注意型モデルでは、標準のKVキャッシュだけでなく再帰状態の復元位置が必要となる。さらに、端末のGPUメモリはブラウザや他アプリケーションと共有されるため、開始時に決めた専門家とKVの固定分割が長い対話で適切とは限らない。

## 手法

### 1. 全専門家の主記憶保持と事前処理の二重バッファ

FreeTokenは全専門家重みをCPU主記憶に置き、GPUメモリには必要な専門家の一部を保持する。モデルの専門家以外の重みはGPUに残す。事前処理では、次の層で必要な専門家がほぼ全体に及ぶため、個別専門家を予測して少しずつ読むのではなく、層単位で全専門家をストリーム転送する。二つの層バッファを交互に使い、GPUが層 `l` の専門家を計算している間に、転送専用ストリームで層 `l+1` の重みをもう一方へ読み込む。

二つの完全な層を置く空き領域がなければ、過剰にGPUメモリを確保せず、必要時に専門家を読み込む方式へ戻る。事前処理と逐次生成のキャッシュは同じGPUスロット群を使うため、事前処理で読み込んだ専門家の一部は生成開始時のキャッシュにも残る。事前処理を高速化するための二重バッファと、逐次生成時の最近使用順キャッシュを別々に固定確保しない点が重要である。

### 2. 意味的な区切りに再帰状態のチェックポイントを残す

標準の全注意層のKVは接頭部木を使って再利用する。一方、再帰型の層では過去を一つの状態へ畳み込むため、履歴の途中が変更されると変更後の状態を再利用できない。FreeTokenは、思考区間、ツール呼出し、ツール出力、会話ターンの境界にチェックポイントを置き、編集後も残る最も深い境界から再帰状態を復元する。変更された後半だけを再計算すればよい。

この方法は、エージェントの履歴編集が意味的なブロック境界に沿うという仮定に依存する。任意の位置で文脈を変更する用途では、保存したチェックポイントが生き残らない場合がある。チェックポイントはメモリを使うので、少数の状態を最近使用順に再利用する。

### 3. 全層共通の専門家キャッシュ

逐次生成では、各層の専門家番号と層番号の組を一つの論理識別子として扱う。GPU上の専門家キャッシュは層ごとに固定容量を割り当てず、全層をまたいだ最近使用順（LRU）で管理する。ルータが選んだ専門家がGPUにあればそのまま計算し、なければキャッシュ未命中として扱う。専門家を転送したときは将来の再利用に備えてキャッシュへ登録し、最も長く使われていない専門家を追い出す。

固定配置では、負荷が変化しても事前に選んだ専門家だけがGPUに残る。共有LRUなら実際のトークン系列の呼出し履歴に追従でき、層ごとの未使用枠も減らせる。ただし、キャッシュ未命中を完全になくせるわけではないため、残る未命中を次の帯域適応方式で処理する。

### 4. 実測帯域から専門家の転送数を決める

ある層でGPUキャッシュにない専門家が `m` 個あったとする。PCIeでGPUへ転送して計算する専門家を `q` 個、CPU主記憶上で直接計算する専門家を `m−q` 個に分ける。GPU転送の実測帯域を `B_P`、CPU側の専門家演算で得られる実効主記憶帯域を `B_H` とすると、PCIe転送が主記憶から消費した後にCPU計算へ残る帯域は概ね `max(B_H−B_P,0)` となる。

転送側とCPU側の終了時刻を揃えると、論文の式(4)は `q* ≈ m B_P / B_H` となる。実装では整数へ丸め、キャッシュを温め続けるため最低一つは転送する。例えばCPU主記憶帯域に対してPCIeが遅いノートPCでは、CPU側で直接計算する未命中専門家を増やす。反対にPCIeと主記憶帯域が近ければ、ほぼすべてをGPUへ転送する。両方の処理は並行して行い、CPUとGPUの部分出力を合成する。モデルの専門家選択や重みを近似的に変更する方式ではない。

### 5. CUDAグラフと可変メモリ割当

ルータの出力によって専門家番号と未命中数が毎ステップ変わっても、ホスト側で毎回Pythonの分岐を作り直すとGPUの実行効率が落ちる。FreeTokenは、GPU上のキャッシュ参照、重複専門家の除去、退避候補の選択、物理スロットへの変換を装置側で処理し、固定の作業領域とCPUタスク記述子を使ってCUDAグラフの再実行に対応する。

GPUメモリは、非専門家重みなどを確保した残りをKVページと専門家スロットへ分ける。利用可能なメモリが変化した場合、スケジューラの安全な区切りで専門家キャッシュを再構築し、CPU側の全専門家プールを読み直さずに割当を変更する。起動時には独自の専門家重み配置形式（FTW）を使って主記憶へ直接読み込み、空の巨大領域を先に固定して初期化する無駄を避ける。GPUの初期キャッシュが空でも通常の未命中処理で起動できる。

## 評価

### 装置と負荷の条件

| 条件 | 主な設定 | 注意点 |
|---|---|---|
| GPU | RTX 3090、4090、5090、5090デスクトップ、4060ノート、RTX PRO 6000 | 計6構成、後者は96GB GPU |
| ノートPC | RTX 4060 8GB、PCIe 4.0 x8、主記憶32GiB | 主記憶帯域47.5GB/秒、PCIe転送11.8GB/秒を実測 |
| RTX 5090サーバー | 32GB、PCIe 5.0 x16 | CPUスレッド数を制限して端末相当の帯域へ合わせた |
| モデル | Qwen3.6-35B-A3B、DeepSeek-V4-Flash、GLM-5.2 | 35Bは主にBF16、ノートはNVFP4、他はMXFP4/NVFP4 |
| 負荷 | AIME、OpenCode+SWE、Claude Code+SWE、OpenClawメール/予定表 | ツール呼出しと長い対話を含む |
| 比較 | llama.cpp、Ollama、KTransformers、MoE-Infinity | 未対応モデル・負荷は実行不可として扱う |
| 指標 | 生成トークン/秒、最初のトークンまでの時間（TTFT）、未命中率 | モデル品質の独立比較ではない |

### 生成処理能力と待ち時間

RTX 5090ではQwen3.6-35B-A3Bの生成速度が77～83トークン/秒、DeepSeek-V4-Flashが22～25トークン/秒だった。最良比較方式に対して前者は1.8～2.3倍、後者は1.5～1.9倍である。エージェント負荷でも単発の数学問題に比べて速度低下が12%以内に留まり、長い文脈やツール利用での性能の安定性を示した。一方、KTransformersはDeepSeek-V4-Flashのコード修正負荷で単発時より31%遅くなった。

最初のトークンまでの時間については、複数ターンの6条件中5条件でFreeTokenが最も短い平均値だった。すべての評価条件で最悪ターンは44秒未満だったが、比較方式は少なくとも一条件で150秒を超え、llama.cppは最大232秒、Ollamaは179秒、KTransformersは946秒に達した。こうした長い待機はエージェント側のタイムアウトへ直結する。ただし、評価では比較方式も最後まで測れるようにOpenClawの通常の120秒監視を無効化している。

### 各機構の効果

事前処理の二重バッファを有効にすると、RTX 5090で8192トークンの処理塊は1.19～1.22秒となり、約64.4GBの専門家プールをPCIeで一回流す時間に近づいた。二重バッファを無効にすると、事前処理能力は4K入力で19%、8Kで25%、16Kで26%低下した。これは重み転送と計算を重ねることの効果を直接測った比較である。

同じキャッシュ容量で専門家の未命中率を比較すると、RTX 5090上でQwen3.6はFreeTokenの共有LRUが16%、KTransformersの固定的配置が41%、llama.cppが62%だった。DeepSeek-V4-Flashではそれぞれ39%、59%、89%だった。単にCPUとGPUへ分配するだけでなく、専門家の局所性を追うキャッシュが転送要求を減らすことを示す。

### 装置を変えた場合

五つの一般向け装置では、最良比較方式に対する生成速度比はRTX 3090と4090で各1.3倍、5090サーバーで1.9倍、5090デスクトップで2.1倍、4060ノートで1.8倍だった。4060ノートはNVFP4形式の35Bモデルを39.3トークン/秒で処理した。5090のサーバーとデスクトップで同じGPUを使うと、FreeTokenの速度低下は約4%である一方、llama.cppは主記憶チャネル減少の影響を大きく受けた。

RTX PRO 6000 96GB一基では753B級GLM-5.2を14.9トークン/秒で処理し、同条件のllama.cppの7.3トークン/秒に対して約2倍だった。これらは装置と量子化形式が異なる個別の実測であり、RTX 4060で753Bを同速度で動かせるという意味ではない。また、35BモデルのノートPC結果とBF16のデスクトップ結果は精度形式が異なるため、単純なGPU性能比較には使えない。

## 既存研究との差

従来の専門家キャッシュ・先読み研究は、どの専門家をGPUへ残すか、次に必要な専門家をどれほど正確に予測するかを改善してきた。しかし未命中が残ればPCIe転送かCPU計算が必要となる。FreeTokenは未命中そのものを共有LRUで減らすだけでなく、避けられない未命中を実測帯域の比率でCPUとGPUへ同時配分する。さらに、事前処理の層単位二重バッファ、エージェント履歴編集後の再帰状態復元、実行中のGPUメモリ再配分を一つのランタイムへ統合した点が特徴である。

近似的に専門家を省略・置換する方式と異なり、論文の専門家実行はルータが選んだ重みをそのまま評価し、CPUとGPUの部分結果を合成する。ただし、BF16・MXFP4・NVFP4などモデルの保存形式自体による量子化誤差は別問題であり、異なる精度形式の間で品質が完全一致することを示したわけではない。

## 限界

第一に、主な詳細評価は特定の三モデルとNVIDIAの単一GPU構成であり、複数GPU、AMDや統合GPU、異なるCPU命令セットに同じ効率が移るかは未確定である。実測帯域から求める配分比率は装置固有であり、カタログ上のPCIe帯域だけで設定すべきではない。CPU主記憶に全専門家プールを置くため、巨大モデルにはGPUメモリとは別に非常に大きい主記憶容量が必要になる。

第二に、実験はエージェントの特定の履歴編集方式を使っており、意味的な区切りを残さない編集では再帰状態のチェックポイントが使えない可能性がある。共有LRUもルーティングに時間的局所性が乏しい負荷では未命中が増える。主記憶を他アプリケーションが強く消費する環境や高同時接続数での待ち行列の振る舞いは、今回の主要評価だけでは確定できない。

第三に、モデル重みの量子化形式やCPU側の実装に依存し、すべてのMoEモデルを同じ速度で実行できるわけではない。主要な評価は生成速度と応答開始時間であり、量子化が数学・コード修正・ツール利用の正答率に与える影響を独立に測定した比較ではない。原著の最大高速化値を、別モデルや別形式の品質と速度の両方へ無条件に適用してはいけない。
