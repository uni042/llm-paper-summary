# FreeToken: Efficient Edge-Native MoE Serving with Bandwidth-Adaptive Execution

> 個人PCのGPU・CPU・RAM・PCIeをまとめて見て、expert cache容量、CPU/GPUで処理するexpert量、KVとのVRAM配分をhardware帯域に合わせて変えるMoE runtime。

## 概要
FreeTokenは、local MoE inferenceを「GPUに載らない分をCPUへ逃がす」だけでなく、**GPU compute、CPU memory bandwidth、PCIe、expert cache、KV cacheを一つのruntimeで共同管理する**システムである。8GB laptop GPUからworkstationまで同じ設計を使い、hardwareごとにCPU/GPU分担を変える。

## 手法のあらまし

### 1. Runtime向けのweight配置へ変換する

FreeTokenはlocal loadingとCPU/GPU kernelの両方で扱いやすい独自weight layoutを使う。

論文中の `FTW weight format` は、**CPU側で連続して読みやすく、GPUへ転送しやすく、量子化kernelでも余計な並べ替えを減らせるようweightの保存順を変えた形式**である。

### 2. Prefillでは2層分のbufferを交互に使ってweight転送を隠す

prefillではlayer weightを順番にstreamしながら計算する。

二つのbufferを用意し、

`layer nを計算中 → layer n+1のweightを転送`

と重ねる。

論文では `full-layer double buffering` と呼ぶが、要点は**現在layer用bufferを計算に使っている間に、もう一方へ次layerを読み込む**ことである。

全expertをGPUに常駐させず、layer単位でweightをstreamすることでVRAMを節約する。

### 3. Decodeでは全layer共通のexpert cacheを使う

多くのoffload runtimeはlayerごとにexpert cache容量を固定する。FreeTokenは全layerをまたいだ一つのLRU cacheとして管理する。

これにより、あるlayerでcache枠が余っているのに別layerで不足するという固定partitionの無駄を減らす。

論文の `global LRU expert cache` のglobalは、**expert cacheの容量をlayerごとに分割しない**ことを意味する。

### 4. CPUとGPUの処理量をmemory帯域・PCIe速度に合わせて変える

runtimeは事前・実行時に測った

- CPU memory bandwidth
- GPU throughput
- PCIe bandwidth

から、expert tokenをCPUとGPUへ分配する。

GPUへ送れば必ず速いとは限らず、PCIeが遅い場合はCPUで直接expertを計算した方が早いことがある。

FreeTokenは、**CPU側とGPU側の処理ができるだけ同じ頃に終わるようexpert量を分け、遅い側だけを待つ時間を減らす**。

### 5. Expert cacheとKV cacheでVRAMを固定分割しない

長いcontextではKV cacheが増え、短いrequestではexpert cacheへより多くVRAMを使える。

FreeTokenはこの二つの予算を固定せず、request数やcontext長に応じて動的に再配分する。

ここで重要なのは、KV cacheをSSDへoffloadするのではなく、**KVとexpert weightが同じVRAMを取り合う問題をruntime allocationで解く**点である。

### 6. Tool call後に同じ長いprefixを再計算しないため状態を保存する

agentic workloadではtool callを挟んで同じprefixへ戻ることがある。

FreeTokenの `semantic anchor checkpoint` は、tool callなど意味的な区切りでKV/stateを保存し、次turnで同じprefixから再開できるようにする仕組みである。

狙いは**tool call後に長いprefixを毎回prefillし直すコストを減らすこと**にある。

### 7. Native routingは変えない

expert pruningやsubstitutionはせず、native routerが選んだexpertをCPU/GPUのどちらで、どのcacheから実行するかだけを変える。

したがってqualityを近似する手法ではなく、system-level optimizationである。

## 評価

### まず見るところ
- **結論:** CPU・GPU・RAM・PCIeとexpert/KV cacheを一体管理すると、consumer hardwareでも非常に大きなMoEをlocal servingできる。
- **速度:** RTX 4060 laptop〜RTX 5090まで実機で既存runtimeを上回る。
- **容量:** 35B級を8GB laptop GPU、さらに数百B級をdesktop/workstationへ拡張。
- **品質:** native expert計算を維持するためlossless system optimization。
- **注意点:** 性能はCPU RAM帯域、PCIe、quantized kernel、cache hitに強く依存する。通常NVMeをcritical expert tierとして使う研究ではない。

### laptop条件

8GB RTX 4060 laptopでも35B級MoEで39.3 tokens/sを報告する。

ここでは「全weightをGPUへ置いた最速条件」ではなく、CPU RAMとGPUを併用しながらinteractive throughputを維持している点が重要である。

### cache設計

全layer共通LRUは同容量条件でKTransformers / llama.cppより低いexpert miss rateを示す。固定layer quotaをなくした効果がdecode throughputへつながる。

### capacity

論文は35B級をlaptop、284B級をgaming desktop、753B級をworkstationでserve可能と報告する。

ただしmodelごとの速度差は大きく、CPU bandwidth、PCIe topology、quantized kernel効率、expert cache hit率へ依存するため、代表speedupを全modelへ一般化すべきではない。

### 評価上の限界

SSD読出し量、HBF/CXL、学術benchmark qualityの詳細な速度との交換関係は中心評価ではない。またtool call地点で状態を保存する仕組みの利得はmulti-turn agent workloadで特に大きく、通常のsingle-turn generationでは効果が限定される。
