# FreeToken: Efficient Edge-Native MoE Serving with Bandwidth-Adaptive Execution

> GPU・CPU・RAM・PCIeを統合資源として扱い、global expert cache、帯域適応CPU/GPU実行、KV再利用を一体化した個人PC向けMoE runtime。

## 概要
FreeTokenは、local MoE inferenceを「GPUに載らない分をCPUへ逃がす」だけでなく、**GPU compute、CPU memory bandwidth、PCIe、expert cache、KV cacheを一つのruntimeで共同管理する**システムである。8GB laptop GPUからworkstationまで同じ設計を使い、hardwareごとにCPU/GPU分担を変える。

## 手法のあらまし

### 1. `FTW weight format`

FreeTokenはlocal loadingとCPU/GPU kernelの両方で扱いやすい独自weight layoutを使う。論文中のFTWは、このruntime向けにweight配置を変換した形式である。

狙いは、CPU側での連続read、GPU transfer、quantized kernelのいずれでも余計なrepackを減らすことにある。

### 2. prefillは`full-layer double buffering`

prefillではlayer weightを順番にstreamしながら計算する。

二つのbufferを用意し、

`layer nを計算中 → layer n+1のweightを転送`

と重ねる。全expertをGPUに常駐させるのではなく、layer単位のweight streamingで容量を稼ぐ。

### 3. decodeは`global LRU expert cache`

多くのoffload runtimeはlayerごとにexpert cache容量を固定する。FreeTokenは全layerをまたいだ一つのglobal LRUとして管理する。

これにより、あるlayerで使われないcache quotaが余っているのに、別layerで不足するという固定partitionの無駄を減らす。

`global` の意味は、**expert cacheの置換対象をlayer境界で分けない**ことにある。

### 4. `bandwidth-adaptive CPU/GPU co-execution`

runtimeは事前・実行時に測った

- CPU memory bandwidth
- GPU throughput
- PCIe bandwidth

から、expert tokenをCPUとGPUへ分配する。

GPUへ送れば必ず速いとは限らず、PCIeが遅い場合はCPUで直接expertを計算した方が早いことがある。FreeTokenはCPU/GPUの完了時間が近づくように配分し、片方だけがstragglerになるのを避ける。

### 5. expert cacheとKV cacheでVRAMを固定分割しない

長いcontextではKV cacheが増え、短いrequestではexpert cacheへより多くVRAMを使える。

FreeTokenはこの二つの予算を固定せず、request数やcontext長に応じて動的に再配分する。

ここで重要なのは、KV cacheをSSDへoffloadするのではなく、**KVとexpert weightが同じVRAMを取り合う問題をruntime allocationで解く**点である。

### 6. `semantic anchor checkpoint`

agentic workloadではtool callを挟んで同じprefixへ戻ることがある。semantic anchor checkpointは、その区切りでKV/stateを保存し、後続turnで再利用する機構である。

狙いはtool call後に長いprefixを毎回prefillし直すコストを減らすことにある。

### 7. native routingは変えない

expert pruningやsubstitutionはせず、native routerが選んだexpertをCPU/GPUのどちらで、どのcacheから実行するかだけを変える。したがってqualityを近似する手法ではなく、system-level optimizationである。

## 評価

### まず見るところ
- **結論:** CPU・GPU・RAM・PCIeとexpert/KV cacheを一体管理すると、consumer hardwareでも非常に大きなMoEをlocal servingできる。
- **速度:** RTX 4060 laptop〜RTX 5090まで実機で既存runtimeを上回る。
- **容量:** 35B級を8GB laptop GPU、さらに数百B級をdesktop/workstationへ拡張。
- **品質:** native expert計算を維持するためlossless system optimization。
- **注意点:** 性能はCPU RAM帯域、PCIe、quantized kernel、cache hitに強く依存する。通常NVMeをcritical expert tierとして使う研究ではない。

|---|---:|
| Qwen系 | 77〜83 tokens/s |
| DeepSeek系 | 22〜25 tokens/s |
| 既存baseline比 | 1.5〜2.3倍 |

### laptop条件

8GB RTX 4060 laptopでも35B級MoEで39.3 tokens/sを報告する。

ここでは「全weightをGPUへ置いた最速条件」ではなく、CPU RAMとGPUを併用しながらinteractive throughputを維持している点が重要である。

### cache設計

global LRUは同容量条件でKTransformers / llama.cppより低いexpert miss rateを示す。固定layer quotaをなくした効果がdecode throughputへつながる。

### capacity

論文は35B級をlaptop、284B級をgaming desktop、753B級をworkstationでserve可能と報告する。

ただしmodelごとの速度差は大きく、CPU bandwidth、PCIe topology、quantized kernel効率、expert cache hit率へ依存するため、代表speedupを全modelへ一般化すべきではない。

### 評価上の限界

SSD読出し量、HBF/CXL、学術benchmark qualityの詳細Paretoは中心評価ではない。またsemantic anchorの利得はtool-useを含むmulti-turn workloadで特に大きく、通常のsingle-turn generationでは効果が限定される。
