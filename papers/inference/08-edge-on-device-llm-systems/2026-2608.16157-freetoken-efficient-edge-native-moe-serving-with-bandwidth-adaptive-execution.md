# FreeToken: Efficient Edge-Native MoE Serving with Bandwidth-Adaptive Execution

> FreeTokenはGPU・CPU・RAM・PCIe帯域を実測し、専門家キャッシュ容量、CPU/GPU分担、KVへのVRAM配分を動的に変えて、MoE転送待ちを抑えるランタイム。

## 概要
FreeTokenは、ローカルなMoE推論を「GPUに載らない分をCPUへ逃がす」だけでなく、**GPU計算、CPU メモリ 帯域、PCIe、エキスパート キャッシュ、KV キャッシュを一つの実行ランタイムで一体的に共同管理する**システムである。8GB laptop GPUからworkstationまで同じ設計を使い、ハードウェアごとにCPU/GPU分担と実行場所を負荷に応じて細かく変える。つまり、端末の計算資源と記憶資源を個別に固定せず、実測した転送速度に合わせてその都度組み合わせる。

この調整は、単に保存場所を変えるだけでなく、重みを読む順序、計算を始める時点、キャッシュへ残す量をまとめて決める。端末ごとの違いを同じ設定で無理に吸収せず、実行時の計測結果を次の配置判断へ反映できる点が中心的な設計上の特徴である。

実機評価では、8GB RTX 4060 laptopで35B級MoEを39.3トークン/秒、RTX 5090では既存比較対象比1.5〜2.3倍で処理し、ネイティブ専門家計算の品質を維持した。

## 手法のあらまし

### 1. Runtime向けのweight配置へ変換する

FreeTokenはローカル loadingとCPU/GPU カーネルの両方で扱いやすい独自重み 配置を使う。

論文中の `FTW weight format` は、**CPU側で連続して読みやすく、GPUへ転送しやすく、量子化カーネルでも余計な並べ替えを減らせるよう重みの保存順を変えた形式**である。

### 2. Prefillでは2層分のbufferを交互に使ってweight転送を隠す

プリフィルでは層 重みを順番にストリームしながら計算する。

二つのバッファを用意し、

`layer nを計算中 → layer n+1のweightを転送`

と重ねる。

論文では `full-layer double buffering` と呼ぶが、要点は**現在層用バッファを計算に使っている間に、もう一方へ次層を読み込む**ことである。

全エキスパートをGPUに常駐させず、層単位で重みをストリームすることでVRAMを節約する。

### 3. Decodeでは全layer共通のexpert cacheを使う

多くのオフロード ランタイムは層ごとにエキスパート キャッシュ容量を固定する。FreeTokenは全層をまたいだ一つのLRU キャッシュとして管理する。

これにより、ある層でキャッシュ枠が余っているのに別層で不足するという固定partitionの無駄を減らす。

論文の `global LRU expert cache` の全体は、**エキスパート キャッシュの容量を層ごとに分割しない**ことを意味する。

### 4. CPUとGPUの処理量をmemory帯域・PCIe速度に合わせて変える

ランタイムは事前・実行時に測った

- CPU メモリ 帯域
- GPU スループット
- PCIe 帯域

から、エキスパート トークンをCPUとGPUへ分配する。

GPUへ送れば必ず速いとは限らず、PCIeが遅い場合はCPUで直接エキスパートを計算した方が早いことがある。

FreeTokenは、**CPU側とGPU側の処理ができるだけ同じ頃に終わるようエキスパート量を分け、遅い側だけを待つ時間を減らす**。

### 5. Expert cacheとKV cacheでVRAMを固定分割しない

長い文脈ではKV キャッシュが増え、短いリクエストではエキスパート キャッシュへより多くVRAMを使える。

FreeTokenはこの二つの予算を固定せず、リクエスト数や文脈長に応じて動的に再配分する。

ここで重要なのは、KV キャッシュをSSDへオフロードするのではなく、**KVとエキスパート 重みが同じVRAMを取り合う問題をランタイム allocationで解く**点である。

### 6. Tool call後に同じ長いprefixを再計算しないため状態を保存する

agentic ワークロードではtool callを挟んで同じprefixへ戻ることがある。

FreeTokenの `semantic anchor checkpoint` は、tool callなど意味的な区切りでKV/stateを保存し、次turnで同じprefixから再開できるようにする仕組みである。

狙いは**tool call後に長いprefixを毎回プリフィルし直すコストを減らすこと**にある。

### 7. Native routingは変えない

エキスパート 枝刈りやsubstitutionはせず、ネイティブ ルータが選んだエキスパートをCPU/GPUのどちらで、どのキャッシュから実行するかだけを変える。

したがってqualityを近似する手法ではなく、システム-水準 最適化である。

## 評価

### まず見るところ
- **結論:** CPU・GPU・RAM・PCIeとエキスパート/KV キャッシュを一体管理すると、consumer ハードウェアでも非常に大きなMoEをローカル 提供できる。
- **速度:** RTX 4060 laptop〜RTX 5090まで実機で既存ランタイムを上回る。
- **容量:** 35B級を8GB laptop GPU、さらに数百B級をdesktop/workstationへ拡張。
- **品質:** ネイティブ エキスパート計算を維持するため無損失 システム 最適化。
- **注意点:** 性能はCPU RAM帯域、PCIe、量子化済み カーネル、キャッシュ hitに強く依存する。通常NVMeを重要 エキスパート 階層として使う研究ではない。

### laptop条件

8GB RTX 4060 laptopでも35B級MoEで39.3 トークン/sを報告する。

ここでは「全重みをGPUへ置いた最速条件」ではなく、CPU RAMとGPUを併用しながら対話型 スループットを維持している点が重要である。

### cache設計

全層共通LRUは同容量条件でKTransformers / llama.cppより低いエキスパート miss rateを示す。固定層 quotaをなくした効果がデコード スループットへつながる。

### capacity

論文は35B級をlaptop、284B級をgaming desktop、753B級をworkstationでserve可能と報告する。

ただしモデルごとの速度差は大きく、CPU 帯域、PCIe topology、量子化済み カーネル効率、エキスパート キャッシュ hit率へ依存するため、代表高速化倍率を全モデルへ一般化すべきではない。

### 評価上の限界

SSD読出し量、HBF/CXL、学術ベンチマーク qualityの詳細な速度との交換関係は中心評価ではない。またtool call地点で状態を保存する仕組みの利得はmulti-turn agent ワークロードで特に大きく、通常のsingle-turn generationでは効果が限定される。
