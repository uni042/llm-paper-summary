# ShadowNPU: System and Algorithm Co-design for NPU-Centric On-Device LLM Inference

> NPUで重要トークン位置だけを近似推定し、高精度疎注意をCPU/GPUへ限定してパイプライン化することで、モバイルLLMの注意フォールバックを削減する。

## 概要

モバイルNPUは整数行列演算のスループットと電力効率に優れるが、実際の端末内LLMでは注意演算がCPU/GPUへ戻されることが多い。理由はQ/K/Vが入力ごとに変動する活性値で、外れ値が多く、静的グラフとテンソル単位量子化を前提とするNPUでは高精度化しにくいからである。論文の測定では、注意をそのままNPUへ載せると4モデル×3タスク平均で18ポイントの精度低下が生じる。

shadowAttnは注意計算を二段に分ける。NPUはQKの絶対値を正確に求めるのではなく「どの位置が大きいか」をINT8で推定する。その位置索引だけをCPU/GPUへ渡し、選ばれた少数トークンについて高精度のQKV演算を行う。重要位置の再現率は20〜80%の各疎率で概ね99%以上であり、NPUの量子化誤差を最終注意値ではなく候補選択へ閉じ込める。

さらに、静的グラフの量子化スケールを複数バケットとして事前生成し、ヘッドごとの重要度から疎率を変え、NPU推定→top-k→CPU/GPU疎注意をヘッド単位で重ねる。Xiaomi 14では完全CPU/GPU注意に対し注意カーネル最大6.9倍・平均3.5倍、入力が支配的な実タスクでは端から端最大4.5倍・平均2.9倍高速化した。4モデル×3タスク平均精度は完全注意36.8に対し36.4である。

## 問題設定

llm.npuやHeteroLLMのような端末向け基盤は、全結合演算をNPUへ載せても注意をCPUへ残す。Q/K/Vは重みと違ってリクエストごとに値域が変わり、テンソル全体で一つの固定スケールを使うと外れ値へ範囲を合わせるため通常値の量子化分解能が不足する。PhoneLM-0.5BではNPU完全注意にするとArxivSumで14.7ポイント、DroidCallで7ポイント低下する例が示される。

一方、注意重みは強く偏っており、Qwen2の測定では大部分が小さい。ならばNPUの低精度計算は「重要位置を当てる」用途に限定し、絶対値が必要な最終積和だけCPU/GPUへ残せる。ただし通常の動的疎注意をCPU/GPUだけで行うと、全位置の重要度推定とtop-k自体が新たな費用になり、20%程度の疎化では速度利得が小さい。

NPUへ推定を移すだけでも不十分である。NPUは入力shapeと量子化scaleが固定された静的計算グラフを最適化するため、変動するQ/Kを一つのグラフへ押し込むと精度が落ちる。またNPU推定、top-k、CPU/GPU疎注意には依存関係があり、ヘッドごとの疎率も異なるため、単純な逐次実行では異種プロセッサの待ち時間が残る。

## 手法

### NPUを「順位推定器」として使う二段注意

shadowAttnでは各ヘッドについて、まずNPUが低精度QKを計算して重要位置候補を得る。ここで必要なのは注意スコアの正確な絶対値ではなく順位なので、量子化誤差に対する許容度が高い。選ばれた位置索引だけをCPU/GPUへ送り、そこに対応するQ/K/Vを高精度で計算する。

この分割により、CPU/GPUは全系列ではなく疎な候補だけを処理する。NPU推定の再現率はWikiText-2の128サンプルで、PhoneLM/Qwen2の0.5B/1.5Bモデルに対し20〜80%の各設定で99.03〜99.95%と高い。一方、候補から重要位置が漏れれば最終高精度計算では取り戻せないため、疎率を下げ過ぎると品質が急落する。

### ヘッド別疎率

全ヘッドへ同じtop-k比率を与えるのではなく、較正データ上でヘッドを除去したときの損失増分を重要度として測り、重要ヘッドには多く、重要度の低いヘッドには少ない計算予算を与える。層・ヘッドで感度が大きく違うという測定を、計算配分へ直接使う。

既定の全体疎率は20%である。感度実験では20%が精度を保てる膝点で、30〜50%へ増やすと削減計算が減って遅くなり、20%よりさらに小さくすると精度低下が目立つ。したがって疎率は単なる速度ノブではなく、端末モデルの品質制約を決めるパラメータである。

### 静的NPUグラフのスケール・バケット化

NPUの静的グラフでは量子化scaleを実行前に固定する必要がある。shadowAttnは較正データからQ/Kのscale組をクラスタ化し、複数の計算グラフを事前生成する。実行時は入力Q/Kのscaleと各バケット代表値の平均二乗誤差を計算し、最も近いバケットのグラフを選ぶ。

既定では9バケット、step size 0.5を使う。5→9バケットでは精度が改善するが、それ以上は利得が飽和する。またstep sizeを桁違いにすると精度が大きく悪化する。つまりバケット化は静的NPUを動的活性値へ適応させる近似であり、グラフ数を増やせば無限に良くなるわけではない。

### ヘッド単位NPU–CPU/GPUパイプライン

各ヘッドにはNPU推定、top-k、疎QKVの3段がある。NPU推定とCPU/GPU疎QKVは別プロセッサ上の計算律速処理、top-kは比較的メモリ律速なので、依存しない別ヘッドの段を同時実行できる。shadowAttnはこれを三段パイプライン化する。

さらに同じscaleバケットに属する複数ヘッドを一つのNPU起動へ融合する。MI14の例では1ヘッド2 msに対し、2ヘッド融合3 ms、4ヘッド融合4 msであり、NPUの高スループットを使いやすくなる。ヘッドごとの疎率で後段時間が違うため実行順も並べ替え、パイプラインの空きを減らす。論文はこの計画問題をNP困難とし、実装側で探索・最適化する。

### プリフィル中心の統合

shadowAttnを第三者フレームワークのプリフィル注意へ差し替え、デコードは完全CPU/GPU注意のままにする。論文の対象モバイル負荷は入力3840/4096/1792に対し出力50/10/10と入力側が支配的で、ここへNPU中心の疎注意を当てる。

したがって本方式はデコードのKV帯域問題を直接解く方式ではない。長い出力が主体のチャット生成では、論文が高速化したプリフィルの割合が小さくなり、端から端の倍率も縮むと考えるべきである。

## 既存研究との差

CPU/GPU動的疎注意は候補選択までCPU/GPUで行うため、疎化しても推定費用が残る。shadowAttnは候補推定をNPUへ移し、しかも絶対値精度ではなく順位だけを要求することでINT8静的グラフを使いやすくする。

NPU完全注意はCPU/GPUをほぼ使わないが、活性値量子化の誤差で品質を失う。shadowAttnは「NPUだけで最終注意を計算する」のではなく、NPUを粗い検索器、CPU/GPUを高精度な疎計算器として役割分担する点が異なる。さらにscale bucketとヘッド別パイプラインを入れ、NPUの静的グラフ制約と異種実行の待ちを同時に扱う。

## 限界

評価は主に0.5B/1.5BのモバイルLLMと2種類のSnapdragon端末であり、大型モデルやApple/MediaTek等の異なるNPUへ同じ結果を外挿できない。実際、V73のRedmiではV75のMI14より高速化率が低い。

端から端評価は入力が長く出力が短いプリフィル主体の負荷である。デコードは完全CPU/GPU注意を使うため、長い生成を続けるワークロードではshadowAttnの寄与率が下がる。

品質も完全一致ではない。平均値は36.8対36.4と近いが、個別にはQwen2-1.5BのDroidCallが48.0→44.5、Octopusが61.2→56.1へ下がる。疎率やscale bucketを外すとさらに悪化するため、端末・モデルごとの較正が必要である。
