# MemExplorer: Navigating the Heterogeneous Memory Design Space for Agentic Inference NPUs

> SRAM/HBM/LPDDR/GDDR/HBFを統一モデル化し、プリフィル/デコードNPUとメモリ階層を共同探索して、基準NPU比でプリフィル最大2.3倍・デコード最大1.93倍の電力効率を得る。

## 概要

エージェント型LLMは通常の一問一答より長い状態を持つ。ツール呼び出し結果、ブラウザや画面状態、過去の行動、複数エージェント間の会話を文脈へ積み上げるため、プリフィルで一度に読むトークン数が増え、デコードでは長大な鍵・値キャッシュ（Key-Value cache; KVキャッシュ）を何度も参照する。さらに同時に多数のエージェントを走らせれば、容量と帯域の両方が急速に増える。

この負荷へ単一の「高速メモリを多く積む」設計だけで対応するのは難しい。オンチップ静的RAM（Static Random-Access Memory; SRAM）は非常に高速だが容量当たり面積が大きい。高帯域メモリ（High Bandwidth Memory; HBM）は高帯域だが電力・コストが高い。低消費電力DDR（Low-Power Double Data Rate; LPDDR）は大容量・低電力に向くが帯域が低い。GDDRは別の帯域・電力点を持ち、高帯域フラッシュ（High-Bandwidth Flash; HBF）のような新技術は非常に大きな容量を狙える代わりにアクセス特性が異なる。

しかもプリフィルとデコードでは必要なメモリが異なる。プリフィルは多数トークンをまとめた大きな行列積を持ち、演算器へ十分なデータを供給する帯域と計算性能の均衡が重要になる。デコードは1トークンずつ進むため重みやKVの読出し比率が高く、容量を増やして大きなバッチを載せることが演算器利用率へ効く。したがって一つのNPUと一つのメモリ構成を両段階へ強制すると、どちらかで電力または性能を無駄にする。

MemExplorerはこの設計問題を自動探索する**メモリシステム合成器（memory system synthesizer）**である。SRAM、HBM、LPDDR、GDDR、HBFを同じ抽象化で扱い、オンチップ・オフチップのどこに何を置くかだけでなく、NPUの行列演算器規模、量子化精度、データフロー、プリフィル装置とデコード装置の役割分担まで共同で探索する。

論文はLlama-3.3-70B等のモデルとBFCL・OSWorld由来のエージェント負荷を用い、同一電力予算のプリフィルでは基準NPU比最大2.3倍、H100比3.23倍のエネルギー効率を報告する。デコードでは同等性能を達成する条件で、基準NPU比最大1.93倍、H100比2.72倍の電力効率を示す。ここで主張されているのは一つの万能メモリではなく、**ワークロード段階と電力制約に応じて異種メモリを組み合わせること自体が設計変数になる**という点である。

## 背景: 容量と帯域を別々に買う必要がある理由

LLMアクセラレータのメモリ設計では、容量、帯域、アクセスエネルギーを一つの軸で同時に最大化できない。HBMを増やせば帯域は高いが、スタック数とI/O電力も増える。LPDDRへ容量を逃がせば多数の重みやKVを保持しやすいが、全データを毎トークン高帯域で読む用途には向かない。SRAMは最も近いが、巨大モデルの重みや全KVを置く容量はない。

このため「頻繁に再利用する小さなデータはSRAM」「帯域が必要な主要データはHBM」「大容量だがアクセス頻度の低い状態はLPDDR/HBF」といった階層化が考えられる。しかし実際にどのデータをどの技術へ置くのがよいかは、モデル形状、バッチ、文脈長、量子化、演算器の規模によって変わる。

エージェント負荷ではこの変化が大きい。長いツール履歴はKV容量を増やし、複数同時エージェントはバッチを増やす。一方、ツール実行の合間にはモデル呼び出しが途切れる場合もある。固定された短文チャットの平均値だけでNPUを設計すると、実際のエージェント実行で容量不足または帯域過剰が起きる。

## 問題設定

MemExplorerが解くのは「候補メモリの中から一番速いものを選ぶ」単純問題ではない。オンチップSRAM量、オフチップメモリの技術とチャネル数、重み・活性・KVの配置、演算精度、行列エンジン寸法、データフローを組み合わせると設計空間は巨大になる。

さらにプリフィル専用NPUとデコード専用NPUを分離する異種システムでは、同じ総電力予算を二装置へどう分配するかも決める必要がある。プリフィル装置だけを極端に高速化してもデコードが追いつかなければエージェント全体の処理量は伸びない。

そこで目的を単一の最大スループットではなく、電力と性能のPareto前線として扱う。同じ電力ならどの構成が最も高い処理量を持つか、同じ処理量ならどの構成が最も低電力かを探索する。

## 手法

### 1. 異なるメモリ技術を共通インターフェースへ抽象化する

各メモリ技術について、利用可能容量、読出し/書込み帯域、アクセス遅延、読書きエネルギー、インターフェース電力などを共通パラメータへ変換する。これによりSRAMとHBMのように実装形態が大きく異なる候補も、同じNPUデータフローの下で比較できる。

この抽象化の入力はメモリ技術パラメータとモデルテンソルの大きさ・アクセス頻度であり、出力は各階層で必要になる時間と電力の推定である。単純な容量適合だけでなく、どのテンソルをどこから何回読むかを通してエネルギーへ結び付ける。

HBFのような新しい候補も同じ枠へ入れられることが重要で、将来メモリを加えるたびNPUシミュレータ全体を書き直さず設計比較を行える。

### 2. プリフィルとデコードを別の装置設計として扱う

プリフィル装置では大きな行列積を処理するため、行列エンジンの規模と高帯域メモリの供給能力を合わせる。計算器を増やしてもメモリから入力を供給できなければ演算器が遊ぶため、演算ピークだけを最大にしない。

デコード装置では、重みとKVを毎反復読む容量・帯域が支配的になる。大容量のLPDDRやHBFを組み合わせるとより多くの要求を同時保持でき、バッチを大きくして重みアクセスを償却できる。そのため単体アクセス速度がHBMより低くても、システム全体の電力効率が高くなる設計点が現れる。

二装置を別々に最適化した後、エージェントワークロードのプリフィル量とデコード量に合わせて性能を釣り合わせる。これが一枚の汎用NPUを両段階へ使う基準との差になる。

### 3. NPUの演算器規模・データフロー・量子化も同時探索する

メモリだけ固定して比較すると、ある構成が遅い理由が「メモリが弱い」のか「演算器が過大/過小」なのか区別できない。MemExplorerは行列エンジン寸法を設計変数に入れ、メモリ帯域へ見合う計算能力を選ぶ。

さらに重み固定（weight-stationary）などのデータフロー、データ型・量子化精度も候補にする。低ビット化で重み/KVが小さくなれば必要帯域と容量も変わるため、同じメモリ構成の最適演算器規模も変化する。

入力はモデル、ワークロード、電力予算、候補技術集合であり、出力は「このプリフィルNPUにはこの演算器とメモリ階層、このデコードNPUには別構成」という具体的な設計点になる。

### 4. 多目的ベイズ最適化で巨大な設計空間を絞る

全構成を総当たりすると組合せが多過ぎるため、多目的ベイズ最適化（Multi-Objective Bayesian Optimization; MOBO）を用いる。少数の初期設計を評価し、その結果から代理モデル（surrogate model）を作り、性能・電力Pareto前線を改善しそうな次候補を優先して評価する。

この方法の目的は、シミュレーション回数を減らしながら有望な異種構成を見つけることである。探索中にメモリ技術だけでなく演算器・データフローも一緒に動くため、「HBMが良い」という単一変数の結論ではなく、相互作用を含む設計を得られる。

### 5. エージェント実負荷の文脈長・段階比率へ合わせる

評価では単一の固定系列長だけでなく、BFCLやOSWorldのようなエージェントタスクから得られる入力・出力特性を設計へ反映する。長い観測やツール出力が増えるほどプリフィル量、KV容量、デコード読出しが変わるためである。

このワークロード依存性があるため、MemExplorerの出力は「全LLM向け最適NPU」ではなく、対象エージェント負荷・モデル・電力予算に対する設計候補として読む必要がある。

## 評価

### 代表的な評価条件

| 項目 | 条件 |
| --- | --- |
| 対象 | エージェント型LLMのプリフィル・デコード |
| モデル例 | Llama-3.3-70B等 |
| ワークロード例 | BFCL、OSWorld |
| メモリ候補 | オンチップSRAM、HBM、LPDDR、GDDR、高帯域フラッシュ（HBF） |
| NPU設計変数 | 行列エンジン規模、メモリ階層、データ配置、データフロー、量子化 |
| 探索 | 多目的ベイズ最適化（MOBO） |
| 比較対象 | 基準NPU、NVIDIA H100 |
| 主指標 | 同電力でのエネルギー効率/性能、同性能での電力効率 |
| 実装形態 | 解析・シミュレーションによる設計空間探索。実製造チップの測定ではない |

### 代表的な評価結果

| 条件 | 比較対象 | MemExplorer設計 | 改善・差 | 読み取れること |
| --- | --- | --- | --- | --- |
| プリフィル、同一電力予算 | 基準NPU | 探索された異種メモリNPU | 最大2.3倍のエネルギー効率 | 計算器と帯域の共同調整が効く |
| プリフィル、同一電力予算 | H100 | 探索されたNPU | 最大3.23倍 | 汎用GPUよりワークロード特化設計に大きな余地 |
| デコード、同等性能 | 基準NPU | 探索された異種メモリNPU | 最大1.93倍の電力効率 | 大容量メモリとバッチ増加が低電力化へ効く |
| デコード、同等性能 | H100 | 探索されたNPU | 最大2.72倍 | デコードでは演算ピークより容量・読出し設計が重要 |
| メモリ階層の探索 | 単一高速メモリ | SRAM + 複数オフチップ技術 | Pareto前線を改善 | 容量と帯域を異なる技術へ分担する価値を確認 |

プリフィルの2.3倍/3.23倍とデコードの1.93倍/2.72倍は評価条件が異なる。前者は同じ電力予算でどれだけ効率よく処理できるか、後者は同等性能を満たすときにどれだけ電力を下げられるかであり、一つの共通倍率として比較してはいけない。

また「H100比」は実装済みMemExplorerチップをH100実機とベンチマークした結果ではなく、対象モデル・ワークロードを同じ解析基盤で比較したアーキテクチャ設計評価である。

## 既存研究との差

従来のNPU設計空間探索は、HBMなど一種類のオフチップメモリを前提に演算器寸法やデータフローを探すことが多い。MemExplorerはメモリ技術そのものを選択変数にし、容量・帯域・電力が異なる複数技術を階層として組み合わせる。

プリフィル・デコード分離（prefill-decode disaggregation）研究は既存GPU群を役割別に分けることが中心だが、MemExplorerはハードウェア設計段階から各フェーズ専用NPUの演算器とメモリを別に作る。したがって「どのGPUを何台割り当てるか」より下のアーキテクチャ層を扱う。

単一のHBM容量を増やす方式に対しては、大容量低電力メモリを一部に導入してバッチを増やし、必要なホットデータだけ高速階層へ置くという異種化を探索できる点が差になる。

## 限界・実装状況

主結果は解析・シミュレーションに基づくため、物理チップの配線、メモリコントローラ競合、熱、製造コスト、実ソフトウェアランタイムのオーバーヘッドが全て実証されているわけではない。特にHBFのような新興技術は製品化時の実パラメータが変わり得る。

設計結果はワークロード分布に依存する。BFCL/OSWorldより短い会話、異なるエージェントループ、拡散言語モデル、MoE、KV圧縮を使う場合、容量・帯域比率が変化して別のPareto点が選ばれる可能性が高い。

量子化やKV圧縮を後から追加するとメモリ律速そのものが変わるため、MemExplorerが選んだメモリ階層をそのまま使うのではなく再探索する必要がある。逆にこれは、アルゴリズム変更を設計変数へ追加して共同探索できることも意味する。
