# Efficient Mixture-of-Experts LLM Inference with Apple Silicon NPUs

> NPUMoEは、Apple NPUで動的な専門家選択を固定容量のグループと共有計算グラフへ変換し、頻出群を常駐させて小粒度実行とCPU同期を減らす方式。
## 概要

Apple NPUは動的な専門家選択と小さな計算・CPU同期を苦手とする。NPUMoEは専門家を固定容量のグループへ分け、同じ形状を共有グラフで実行し、頻出群を常駐させて小粒度起動と同期を減らす。Apple M2 Max/M2 Ultra実機のPhi-3.5-MoE系評価では、比較対象に対するプリフィル遅延を1.32〜5.55倍、エネルギー効率を1.81〜7.37倍改善し、枝刈りによる精度低下を1.1%未満に抑えた。

## 問題設定
MoEは各トークンをルータが少数の専門家へ振り分けるため、層ごと・専門家ごとの入力トークン数が毎回変化する。GPUは可変形状や小さなカーネルを比較的柔軟に処理できるが、Appleのニューラル処理装置（Neural Processing Unit; NPU）は事前にコンパイルした静的形状の計算グラフを高効率に実行する設計で、動的な上位K選択、散布・収集、専門家ごとに異なる入力長をそのまま載せにくい。素朴に専門家ごとに小さなNPUグラフを起動するとキュー投入とCPU–NPU同期が直列化し、論文の測定では同期・制御が実行時間の60%以上を占める条件がある。さらに長文プリフィルは全体遅延の約80%、CPUサイクルの約70%を占めるため、重みが統合メモリに収まっていても計算実行方式の不一致だけでNPUの性能とエネルギー効率を引き出せない。
## 新規性
NPUMoEは、すべての専門家重みがAppleの統合メモリに収まる状況で、ストレージからの重み入替ではなくNPUの静的グラフ制約そのものを最適化対象にする。専門家の入力容量を少数の固定段階へ量子化して可変形状を静的化し、同じ容量の複数専門家を一つの計算グラフへ束ねて起動回数を減らし、利用頻度の高いグループだけをNPUに置く。容量を超えたトークンは重要度に基づいて枝刈りし、パディング・起動費・品質低下の交換条件を制御する。MoEの動的性を完全にNPUへ持ち込むのではなく、静的グラフへ写像できる少数の実行形へ変換する点が中心的な発想である。
## 手法
### 手法のあらまし
まずモデル変換時に、注意機構などの密な演算と専門家の全結合ネットワークをNPU向け計算グラフへ変換し、ルーティングの上位K選択、マスク生成、専門家への散布、結果の統合など入力依存の制御はCPU側へ残す。こうしてNPUには形状が確定した行列演算を集中させ、CPUは実行時の不規則な制御だけを担当する。長い入力は一定長のチャンクへ分割し、静的入力形状のグラフを繰り返し利用できるようにする。

次にオフラインの校正データから、各層でどの専門家へ何個のトークンが到着しやすいかを測る。すべての専門家へ最大容量を割り当てると大量のゼロ埋め計算が発生するため、32、64、128トークンのような少数の容量段階を用意し、人気の高い専門家には大きい容量、利用の少ない専門家には小さい容量を割り当てる。実際の入力が割当容量より少ない場合はパディングし、多い場合は容量内へ収める必要がある。超過時には注意機構出力のL2ノルムを重要度として利用し、重要度の低いトークンから枝刈りして固定形状へ変換する。ここが性能のために計算を近似する箇所であり、評価では枝刈り量と精度低下を別に測定する。

さらに、同じ容量段階に属する複数専門家を個別の小さな計算グラフとして順番に呼ぶ代わりに、専門家の重みと入力をまとめた一つの静的グラフへ束ねる。NPUへの投入・同期回数を減らし、より大きな行列演算としてハードウェアを埋めやすくする。一方でグループを大きくしすぎると計算グラフ自体が巨大化し、M2 Ultraでは約1.2GBを超えるグラフがCPUへフォールバックする境界が観測される。そのため容量段階とグループ数を組み合わせて、NPUに載る範囲で起動費とパディングを抑える。

最後に専門家の利用頻度をオフラインで集計し、高頻度の専門家グループはNPU向けグラフとして常駐させる。低頻度・小規模なグループはCPUやGPU側へ回すことで、たまにしか使わないグラフまでNPUへ投入する同期費を避ける。Apple SiliconはCPU・GPU・NPUが統合メモリを共有するため、本方式は重みをSSDから都度読み込むのではなく、同じ重みがメモリにある状態でどの計算機構に実行させるかを変える。プリフィルでは多数トークンをまとめられるためNPU起動費を償却しやすいが、1トークンずつ進むデコードでは同じ利点が小さくなる。

### 静的な専門家容量段階
オフライン校正で層ごとの専門家人気度と到着トークン数の分布を測り、専門家ごとに32、64、128など少数の固定容量から一つを割り当てる。実行時の可変長入力をこの固定枠へ詰めることで、NPUが要求する静的形状の計算グラフを再利用できる。全専門家へ最悪時容量を与える方式よりゼロ埋め計算を減らせる一方、容量不足時には超過トークンを処理できない。そこで注意機構出力のL2ノルムを重要度として、寄与の小さいトークンから枝刈りする。入力分布が校正時から変わると超過率やパディング率が増え、計算量または品質のどちらかが悪化するため、容量段階は性能だけでなく分布変化への余裕も持たせる必要がある。

### 同容量専門家のグループ実行
同じ容量を持つ専門家を一つずつNPUへ投入すると、各専門家の全結合計算が短くてもCPUからのグラフ起動、キュー投入、同期が専門家数だけ繰り返される。NPUMoEは複数専門家の入力と重みを一つの大きな静的計算グラフへまとめ、1回の起動で並列に処理する。容量64の実験ではトークン当たり遅延が非グループ化の0.23ミリ秒から4専門家で0.19、8専門家で0.18ミリ秒まで下がる。ただしグループを大きくするとグラフサイズとパディングが増え、一定サイズを超えるとNPU実行自体が成立せずCPUへフォールバックするため、最大グループ化が常に最適ではない。

### 利用頻度に基づく計算グラフ配置
校正ワークロードで得た専門家人気度を用い、頻繁に使われる専門家グループのコンパイル済み計算グラフをNPU側へ優先配置する。利用頻度の低い専門家や小さ過ぎてNPU起動費を償却できないグループはCPUまたはGPUで処理し、CPU–NPU間の制御・同期を減らす。Apple Siliconの統合メモリでは重みそのものを別階層へコピーせず同じ物理メモリから各計算機構が参照できるため、ここでの「配置」は主に実行先とコンパイル済みグラフの常駐を意味する。専門家人気度が入力領域で変わると静的な人気順位が外れるため、論文は未見入力での上位専門家重なりも測定し、分布変化が配置判断の限界になることを示す。

### CPU制御とNPU計算の分割・チャンク化プリフィル
上位K選択、専門家IDの整理、散布・収集、可変マスクのような入力依存処理はCPUへ残し、注意機構と専門家全結合計算のような規則的な演算だけをNPUへ渡す。長いプロンプトは256、512、1024トークンなどの固定チャンクへ分け、同じ静的グラフを繰り返し呼べるようにする。この分割によりCore MLが動的形状のためCPUへ戻す範囲を狭められるが、チャンクが小さ過ぎると起動・同期回数が増え、大き過ぎると専門家容量超過とパディングが増える。したがってチャンク長、専門家容量、グループ数は独立ではなく、NPUで効率よく処理できる計算粒度を共同で決める。

### 全体のデータ／制御の流れ
実行時はCPUが入力チャンクを受け、注意計算後の活性値からルータの上位K専門家を決める。各専門家へのトークン集合を、その専門家に割り当てられた固定容量へ変換し、必要なら重要度の低い超過トークンを枝刈りする。同じ容量段階の高頻度専門家はまとめたNPUグラフへ送り、低頻度グループはCPU/GPUへ回す。NPUの出力をCPU側で元のトークン順へ統合して次層へ渡す。この流れをプリフィルの各チャンク・各MoE層で繰り返す。性能は、専門家分布が校正時と似ていてグループがNPUのグラフサイズ制約に収まり、1回のプリフィルで十分なトークン数をまとめられるほど高い。デコードや分布変化では小粒度実行と容量外れが増え、利得が縮む。
## 評価条件
- **ハードウェア**: Apple M2 Max: 64GB統合メモリ、12コアCPU、16コアApple Neural Engine、Apple M2 Ultra: 192GB統合メモリ、24コアCPU、32コアApple Neural Engine
- **ソフトウェア**: Apple Core ML、Swift実装、ANEMLLによるモデル変換
- **モデル**: Phi-3.5-MoE-Instruct: 約42.6B、16専門家、上位2選択、Phi-tiny-MoE-Instruct: 約3.8B、Qwen3-30B-A3B: 48層、128専門家
- **データセット／トレース**: HellaSwag、BoolQ、RULER系長文タスク
- **比較対象**: Core ML CPU実行、Core MLの素朴な既定スケジューリング、ANEMLLの密モデル向けNPU実行
- **正確性・品質**: 容量超過トークンを重要度で枝刈りするため厳密な等価実行ではない。したがって高速化と品質を別々に評価し、精度低下が1.1%未満、RULER系課題で96.0%を保つことを確認している。
- **専門家容量とグループ数**: 固定専門家容量32/64/128、専門家グループ数4/8などを比較し、NPU起動費、パディング、グラフサイズの交換条件を測る。
- **長文プリフィル**: 入力長1024および4096を中心に、チャンク長256/512/1024を変えてプリフィル遅延、エネルギー、CPUサイクルを比較する。
- **品質評価**: 容量超過トークンを枝刈りした状態でHellaSwag、BoolQ、RULER系課題を評価し、元モデルとの差を測る。
- **専門家人気度の汎化**: 校正時と未見入力・別データセットで上位専門家集合の重なりを測り、静的容量・配置が分布変化へどこまで耐えるか確認する。
同一チェックポイントとトークナイザを用い、主要演算をFP16で比較する。モデル規模、入力長、専門家容量、グループ数を変え、プリフィル遅延、トークン当たりエネルギー、CPUサイクル、精度を実機で測る。構成要素評価ではグループ化、容量段階、配置を段階的に追加し、GPUとの比較では速度だけでなく消費電力とエネルギーも分離する。
全モデル重みがAppleの統合メモリに収まる構成を対象とし、SSDやUFSから専門家重みを都度読み込む容量不足問題は扱わない。主な最適化対象は長文プリフィルで、トークン単位のデコードではNPU起動・同期を償却しにくく利得が小さい。Apple Core MLとApple Neural Engine固有のグラフ制約を前提とするため、他社NPUへの一般化には再設計が必要である。
## 主要結果
NPUMoEは、MoEの可変専門家入力を静的NPUグラフへ変換し、専門家をまとめて起動することで、特に長文プリフィルのCPU同期と小粒度実行を削減する。Phi-3.5-MoE系では比較対象に対してプリフィル遅延を1.32〜5.55倍改善し、エネルギー効率を1.81〜7.37倍高める。Qwen3-30B-A3Bでも1.19〜3.86倍の高速化を示す。一方、NPUはGPUより絶対速度で遅い条件があるため、狙いは最高スループットよりも電力・エネルギー効率とCPU負荷の削減であり、固定容量のために10〜20%のトークンを枝刈りする近似も含む。

- Phi-3.5-MoE系プリフィル遅延 / 比較対象比1.32〜5.55倍高速化 (比較対象: Core ML CPU、Core ML素朴実行、ANEMLL NPU実行; 条件: M2 Max/M2 Ultra、複数入力長・容量設定) — 専門家ごとの小さなNPU呼出しをまとめ、CPU同期とパディングの双方を削減することで長文入力ほど差が広がる。

- Phi-3.5-MoE系エネルギー効率 / 比較対象比1.81〜7.37倍改善 (比較対象: 同上; 条件: 実機プリフィル) — NPUの低消費電力演算を大きな静的グラフとして使い切ることで、CPU中心実行や非効率なNPU起動よりトークン当たりエネルギーを下げる。

- Qwen3-30B-A3Bプリフィル速度 / 比較対象比1.19〜3.86倍高速化 (比較対象: Core ML/ANEMLL系比較対象; 条件: 128専門家を持つQwen3-MoE、Apple Silicon) — 専門家数が多いモデルでも容量段階とグループ化によりNPU起動数を抑えられる。

- エンドツーエンド遅延 / Core ML素朴実行比最大3.86倍、CPU比1.26倍、ANEMLL比1.19倍高速化 (比較対象: 各既存実行経路; 条件: 主要MoEモデルの実機評価) — 専門家全結合部分だけでなく、ルーティングや注意機構を含む全体でも利得が残る。

- CPUサイクル削減 / CPU比2.64〜3.75倍、素朴実行比3.17〜4.67倍、ANEMLL比2.01〜2.99倍削減 (比較対象: 各比較対象; 条件: エンドツーエンド評価) — 専門家計算をNPUへ大きな粒度で移すことでCPUが制御と散布・収集に集中できる。

- 品質影響 / 精度低下1.1%未満、RULER系課題96.0%維持 (比較対象: 枝刈りなし元モデル; 条件: 容量超過時に約10〜20%のトークンを重要度で枝刈り) — 近似計算ではあるが、低重要度トークンを選んで落とすことで測定上の品質低下を小さく抑える。

- 専門家グループ化遅延 / 容量64で0.23→0.19→0.18ミリ秒/トークン (比較対象: 非グループ化→4専門家→8専門家; 条件: 同容量専門家を単一NPUグラフへ統合) — 専門家数だけ繰り返していた起動・同期の固定費を償却できる。

- 全最適化の構成要素効果 / 基準実装比2.89倍高速化、容量段階＋グループ化のみより1.09倍高速化 (比較対象: 構成要素を段階追加した実装; 条件: プリフィル構成要素評価) — 容量段階とグループ化が主要因で、人気度を使った配置が追加利得を与える。

### 負の結果・境界条件
- **GPUは絶対速度で優位**: 比較GPUは条件によりNPU方式より1.26〜5.4倍高速い。一方でエネルギーは1.87〜4.48倍、電力は5.65〜9.41倍大きく、NPUMoEは最高速度より省電力オンデバイス実行を狙う設計である。
- **固定形状パディングの残存費**: 平均で計算トークンの35.35%がパディングとなり、CPUサイクルを1.25〜1.36倍、実行時間を27〜29%増やす。容量段階を粗くし過ぎると静的グラフ化の利点をゼロ埋め計算が食い潰す。
- **注意機構は遅くなる条件がある**: 専門家部分をNPUへ最適化しても注意機構側の遅延が約27.6%増える条件があり、全体性能は専門家全結合だけでは決まらない。
- **デコードへの効果は限定的**: 1トークン単位のデコードでは専門家グループを大きく埋めにくく、NPU起動とCPU同期を十分償却できないため、論文の中心的な利得は長文プリフィルに集中する。
- **専門家人気度は分布変化でずれる**: 未見入力で上位専門家の重なりは高い条件もあるが、別データセット間のPhiMoEではプリフィルの上位集合重なりが65.2%まで下がる。静的配置を長期間固定すると低頻度と判断した専門家が実際には頻繁に使われる可能性がある。

### 結果の読み方
NPUMoEが効く中心理由は、NPUへ演算を移すこと自体ではなく、MoEの動的・小粒度な専門家計算をNPUが得意な少数の大きな静的グラフへ変換したことにある。専門家容量段階は形状を固定し、グループ化は起動・同期を償却し、人気度配置は低効率なグラフ呼出しを減らす。この三つが長文プリフィルでは多数トークンに対してまとめて働く。一方、容量段階はパディングと枝刈りを生み、デコードでは計算粒度が小さく、GPUは絶対速度で依然優位なため、用途は省電力なオンデバイス長文入力処理へ最も適合する。
## 品質への影響
厳密な無損失方式ではない。固定専門家容量を超えた入力のうち活性値重要度が低いトークンを枝刈りするため、元MoEとは計算が変わる。論文は約10〜20%のトークンを落とす設定で精度低下1.1%未満、RULER系長文課題96.0%を報告する。したがって速度・エネルギー改善の一部は小さな品質交換を含むと解釈すべきである。
## 既存研究との差
- EStreamはスマートフォンNPUでMoEを実行する点は近いが、全専門家重みをDRAMへ置けないことを前提にUFSストレージから必要な専門家を固定作業領域へ読み込み、読出しとNPU計算を重ねる。NPUMoEは全重みがApple統合メモリに収まる前提で、主問題を動的ルーティングと静的計算グラフの不一致、起動・同期費へ置く。
- FreeTokenはGPU・CPU・RAM・PCIe帯域を測り、専門家キャッシュ容量とCPU/GPUの処理分担を動的に変える。NPUMoEはAppleのNPUとCore MLの静的グラフ制約を対象にし、専門家入力を固定容量へ変換してグループ計算するため、資源選択より実行形状の変換が中心である。
- D²MoEはSSDからの専門家重み転送と低ビット実行をルーティング・スケジューリングで調整する。NPUMoEはSSD読出しを行わずFP16重みを統合メモリに保持し、容量超過トークンの枝刈りとNPUグラフ常駐で計算側を最適化する。
- PowerInfer-2はCPU・NPU・フラッシュを含むスマートフォン全体の異種実行を扱うが、NPUMoEはMoE固有の専門家負荷偏り、散布・収集、可変専門家入力をApple NPUの静的形状へ写像することに焦点を絞る。
## 限界
- 専門家容量超過時にトークンを枝刈りする近似方式であり、品質低下は測定上1.1%未満でも厳密な無損失推論ではない。
- すべての専門家重みが統合メモリに収まることを前提にし、SSD/UFSやCPU DRAM階層から専門家を都度読み戻す容量不足問題は解かない。
- 主要利得は長文プリフィルで、デコードは小粒度かつメモリ律速になりやすく、NPU起動・同期費を十分に償却できない。
- 専門家容量とNPU配置はオフラインの人気度に依存する。データ分布が変わるとパディング、容量超過、CPU/GPUへの低温専門家実行が増える可能性がある。
- 計算グラフを大きくし過ぎるとNPUの実装上限を超え、約1.2GBを越える条件ではM2 Ultra上でもCPUへフォールバックするため、専門家を無制限にグループ化できない。
- Apple Core MLとApple Neural Engine固有の変換・実行制約に依存し、Android系NPUや独立メモリ型アクセラレータでは同じ設計点が成立する保証はない。
- 論文はコードを公開予定としているが、確認時点で一次資料に専用公開リポジトリURLがなく、完全な再現性は今後の公開に依存する。
## 実装状態
ANEMLLを使ったモデル変換、Apple Core ML、Swiftにより、CPU側の動的ルーティングとNPU側の静的専門家グラフを統合した実機試作系を構築している。M2 MaxとM2 Ultraで複数MoEモデルを評価済み。論文はコードベースを公開予定としているが、2026-09-10確認時点で専用公開URLは一次資料から確認できなかった。
## 研究上の位置づけ
エッジ・オンデバイスLLMシステム系統のうち、メモリ容量不足ではなく「MoEの動的性を静的グラフ型NPUへどう落とすか」を中心課題とする研究に位置付ける。既存repoではEStreamがストレージからNPUへの専門家ストリーミング、FreeTokenやD²MoEがCPU/GPU/SSD間の専門家配置と帯域適応を扱うため、NPUMoEはそれらと重複せず、全重み常駐時のNPU実行効率という空白を埋める。将来的にはEStream型の階層ストレージ管理とNPUMoE型の静的グラフ変換を組み合わせ、重みが常駐できない場合にも専門家の読出しとグループNPU実行を共同最適化する方向へ拡張できる。
