# TierKV：端末のKVキャッシュを予測に基づいて三階層配置する

## 概要

大規模言語モデルの自己回帰推論では、過去トークンの鍵・値（Key-Value、KV）を各層に保存する。KVキャッシュは系列長にほぼ比例して増え、復号の各ステップで再び参照される。長い文書を入力する検索拡張生成、長い推論過程、画像や音声を含む入力では、モデルの重みだけでなくKVが端末のDRAM容量を圧迫する。サーバーGPUと異なりスマートフォンはOSや他アプリとDRAMを共有し、メモリ上限を超えるとプロセスが強制終了される場合がある。

TierKVは、キャッシュを正確なFP16形式の階層0、低ランク圧縮したDRAM内の階層1、フラッシュへ退避した階層2に分ける。従来の圧縮だけ、トークン削除だけ、退避だけの方式と異なり、各階層の境界と層別の圧縮ランクを一体の最適化問題として解く。最初の入力処理（prefill）が既に生成した隠れ状態を用いて将来の生成長を予測し、復号開始前にキャッシュ計画を決めるため、メモリ不足が発生してから場当たり的に退避する方式の遅れを減らす。

原著はテキスト、画像、音声の8モデルをAdreno 750、Adreno 740、Mali-G715の3モバイルSoCで評価した。RAMに常駐するKVキャッシュを12.5〜34%削減し、同じメモリ予算で最大文脈長を最大2.6倍へ延長する。一方で圧縮されたKVの再構成費用があるため、復号速度は通常のFP16方式より低下する例が多い。事前入力の最大17.6倍高速化はMNN-LLMとの比較であり、llama.cpp比の最大値は約1.6倍である。評価の長所と負の結果を分けて扱う必要がある。

## 問題設定

### 長文脈で増大するKVメモリ

層数 `N_layers`、KVヘッド数 `N_kv`、ヘッド次元 `d_h`、系列長 `L` のFP16キャッシュ容量は、鍵と値の2種類と1要素2バイトを考慮して `2 × N_layers × N_kv × d_h × L × 2 bytes` となる。系列長が倍になればKV容量も倍になる。原著の例ではLlama-3.2-3Bの32KトークンでKVだけで約1.8GB、Llama-3.2-1Bの131Kトークンでは4GBを超える。モデルが小さくても長文脈ならKVが重みを上回り得る。

OnePlus 12の12GB端末では、カーネル、Androidサービス、ハードウェア予約、最低空き領域を除くと安定して利用できるアプリ予算は約6.8GBである。モデル重みと演算バッファがこの容量を使うため、KVの急増はアプリの終了を招く。OSが常に滑らかにスワップしてくれるとは限らず、瞬間的なピークも問題になる。

### 既存の圧縮・削除・退避の問題

低ランク圧縮はKV行列の冗長性を使って記憶量を減らせるが、復号時に全ランクへ復元すると追加の行列積が発生する。原著はOnePlus 12で従来型の再構成が平均30%の演算追加になると述べる。MLA型の潜在注意へ後から変換する方式も、系列長に応じた追加の行列ベクトル積が端末GPUでは律速になり得る。論文の表2ではLlama-3.2-1Bの900トークンで通常FP16が19.3 tokens/sなのに対し、MHA2MLAは4.8 tokens/sまで低下する。

トークン削除方式は削除した情報を後で取り戻せない。フラッシュ退避方式は情報を残せるが、端末の転送帯域が限られ、毎トークン多数のKVを戻すとI/O待ちが増える。原著の例ではLlama-3.2-3Bの9.6Kトークンを退避すると、復号ステップ当たり約189msの追加遅延が生じる。したがって圧縮・削除・退避を単独で選ぶより、品質が敏感なトークンを正確に残し、残りを圧縮と退避に分ける必要がある。

## 手法

### 1. 三階層KVキャッシュ

TierKVは系列長方向に二つの境界 `n` と `m` を設ける。階層0（Tier-0、Exact）は区間 `[0,n]` のKVを正確なFP16で保持する。階層1（Tier-1、Compressed）は区間 `(n,m]` のKVを特異値分解（Singular Value Decomposition、SVD）による低ランク形式でDRAMに置く。階層2（Tier-2、Offloaded）は区間 `(m,L]` のKVをフラッシュへ置く。すべてのトークンの情報への参照経路を残すため、不可逆なトークン削除とは異なる。

層別の圧縮ランク `R_l` は、各層の特異値分布をオフラインで較正した候補群から選ぶ。毎要求で巨大なSVD探索をやり直すのではなく、事前較正したランク形状を使って境界と圧縮水準を決定する。階層2はフルランクのままフラッシュへ置き、退避先でも圧縮して再構成費を増やすことは避ける。階層0は注意の初期位置など圧縮に敏感なトークンを保護する役割を持つ。

### 2. 圧縮に敏感な位置の保護

論文の表4はLlama-3.1-8B-Instructを用い、正確に保持するトークン割合と低ランクの割合を変えた場合のMMLU、ARC Challenge、GSM8Kを比較する。MMLUのFP16基準0.6807に対し、正確保持0%、ランク50%では0.6268だが、正確保持40%、ランク50%では0.6809となる。初期位置を一定割合保護すると品質を回復できる例である。

ただしGSM8Kは圧縮に非常に敏感で、正確保持20%、ランク25%で0.0258、ランク12.5%で0.0076と大幅に悪化する。正確保持80%でもランク12.5%では0.0106であり、MMLUの傾向をそのまま数学推論へ一般化できない。原著は圧縮率だけでなくタスクの精度制約を最適化に含める必要を強調する。この負の結果は「多少の精度低下で済む」という一括表現では隠れてしまう重要な条件である。

### 3. 事前入力状態からの生成長予測

TierKVは入力処理で既に計算した隠れ状態を利用して、将来の生成長とKV需要を予測する。追加の大型予測モデルを呼び出すのではなく、隠れ状態のエントロピーや過去要求との類似性を利用して予測する。これにより、質問の内容やモダリティに応じてキャッシュの配分を復号開始前に決められる。

予測は完全ではないため、長さが外れれば実際の必要KV量と計画がずれる。原著はLongWriter-6kやLM-SYSなど異なる負荷で予測器の頑健性を調べる。予測に基づく計画は反応型の削除・退避で生じる循環依存を避けるが、未来の生成長を確実に知る方式ではない。

### 4. 予測型多階層最適化

予測型多階層キャッシュ最適化（Predictive Multi-Tier Cache Optimization、PMCO）は、予測長 `L`、境界 `n,m`、層別ランク形状 `{R_l}` を用い、メモリ上限 `M_limit` と注意の忠実度制約を満たしながら復号遅延を最小化する。遅延には正確なKVの注意演算、低ランクKVの復元と注意、フラッシュ読込の費用を含める。重要なのはI/Oと演算の重なりを考慮する点であり、単純に各費用を足しただけでは最適な配置を選べない。

低ランク階層を広げればDRAMを減らせるが、再構成計算が増える。退避階層を広げればDRAMをさらに減らせるが、フラッシュとGPU間転送が増える。正確な階層を広げれば品質は維持しやすいがメモリが足りなくなる。PMCOはこの三者を同時に扱い、事前較正したランク候補と境界の閉形式の解法を使って実行時の設定費用を抑える。固定の圧縮率を全質問に適用する方式より、質問ごとの資源予算を使いやすい。

### 5. 融合注意演算と潜在空間の値集約

低ランクKVをそのまま全次元へ復元してから注意を計算すると、メモリ節約が復元費用で相殺される。TierKVは鍵（K）と値（V）で異なる経路を使う。値側では低ランクの潜在表現のまま注意重みを集約し、最後に低次元から元の次元へ戻す。原著は値側の費用を `O(L·R·D)` から `O(L·R + R·D)` に近づけると説明する。長い系列に対する値の全次元復元を避けるのが利点である。

鍵側は回転位置埋め込み（RoPE）の適用のため高精度の扱いが必要になるが、射影、回転、注意スコア計算を一つの融合カーネルへまとめる。これにより中間テンソルのメモリ往復を削減する。原著の図6では単純なSVD復元型の行列ベクトル演算に比べ、融合カーネルが平均2.3倍速いと報告する。この倍率はカーネルの比較であり、全体の復号速度が2.3倍になるという意味ではない。

### 6. フラッシュI/Oと計算の重畳

階層2のKVを参照する場合、フラッシュからRAMへ読み、さらにGPUへ渡す必要がある。TierKVは低ランクKVの再構成計算が走っている間に、退避KVを先読みしてI/O待ちを隠そうとする。原著はLlama-3.2-1Bの2Kトークン条件で先読み命中率94.4%を報告するが、モバイルGPUのホストからデバイスへの転送帯域は約1.66GB/sであり、転送自体が残る律速になる。

このためI/Oを完全に隠せるとは限らない。原著は813トークンの退避で約1.6MBのGPUメモリを節約できる一方、ホストからデバイスへの転送で合計約16msの追加時間が生じる例を示す。退避が大きすぎれば復号が遅くなるので、PMCOはフラッシュへ置く範囲を容量・遅延の交換条件として選ぶ。

### 7. 実装と端末別調整

実装はllama.cppを基盤とし、C/C++、OpenCL、Pythonで約1万行を追加した。融合カーネルのタイル幅、SIMD幅、ループ展開、局所キャッシュ利用などを端末別に調整する。Adreno 740と750では最適な展開幅やメモリアクセス形状が異なるため、モデルとGPUに応じて1〜4回のウォームアップで候補カーネルを測り、誤差検証後に最速構成を選ぶ。特定GPUだけに固定したカーネルではなく、複数SoCへの移植性を考慮している。

## 評価条件

| 項目 | 原著の設定 | 注意点 |
|---|---|---|
| モバイルGPU | Adreno 750、Adreno 740、Mali-G715 | 3種類のSoCを使用 |
| モデル | Llama-3.2 1B/3B、Qwen2.5-3B、TinyLlama-1.1B、Qwen2-VLM-2B、Ultravox-1B、SmolVLM2-1.7B、Gemma4 E2B | テキスト・画像・音声の8モデル |
| 比較方式 | llama.cpp、MNN-LLM、MLC-LLM | 一部比較方式は一部モデルのみ対応 |
| 容量条件 | 安定利用可能なRAM約6.8GBの端末例 | 重み・バッファも予算内に含める |
| 精度指標 | MMLU、ARC Challenge、GSM8K、MMMU-val、LibriSpeech-clean | 圧縮の影響を検証 |
| 性能指標 | 事前入力速度、復号速度、要求全体遅延、KVメモリ、最大文脈長 | 前処理と復号を区別 |
| モデル重み | FP16比較を基本とし、Q8との併用も評価 | KV圧縮と重み量子化は別軸 |

MLC-LLMは比較対象の一部モデル・精度にしか対応しないため、平均倍率を全8モデルで一律に比較したと誤解してはならない。最大文脈長もモデルの学習時の文脈上限を超えられるかどうかとは別であり、メモリが許しても学習済みの位置長制限がある場合は制約が残る。

## 主要結果

### 容量と文脈長

原著の表7では、RAM常駐KVの節約率はモデルによって12.5〜34%、平均約25%である。Llama-3.2-1Bで29%、Llama-3.2-3Bで26%、Qwen2.5-3Bで20%、Qwen2-VLM-2Bで28%、Ultravox-1Bで34%、TinyLlama-1.1Bで22%、SmolVLM2-1.7Bで30%、Gemma4 E2Bで12.5%となる。最大文脈長は同じ予算で最大2.6倍へ延長できたと報告するが、全モデルで同じ倍率ではない。

### 事前入力速度と比較対象

表7の事前入力速度はLlama-3.2-1Bでllama.cpp182.6 tokens/s、TierKV275.1、TinyLlamaで174.6から272.8、Qwen2.5-3Bで45.2から69.4となる。テキストモデルではllama.cpp比およそ1.2〜1.6倍であり、平均は1.34倍である。一方、MNN-LLM比の平均は5.43倍、最大は17.6倍である。MLC-LLM比の183倍は対応するLlama-3.2-1Bの限定条件で、比較対象の実装制約を強く反映する。異なる比較方式の最大倍率を混ぜて「一般に17.6倍高速」とするのは不正確である。

### 復号速度の負の結果

TierKVは低ランクKVの再構成があるため、復号速度はllama.cppより遅い。Llama-3.2-1Bは6.0から4.3 tokens/s、Llama-3.2-3Bは2.4から1.9、SmolVLM2-1.7Bは4.6から1.9へ低下する。8モデルでの平均復号速度比はllama.cppの0.71倍であり、長文脈容量の改善と復号速度の低下が交換条件になっている。原著は事前入力の改善が復号の悪化を上回るため、要求全体では平均1.10倍の速度改善と述べるが、出力が長い要求では復号の遅さが支配的になり得る。

### 再構成・先読みの寄与

融合SVDカーネルは単純な復元方式比平均2.3倍速く、先読みスケジューラは94.4%の命中率を達成したと報告する。ただしこれは特定カーネルとI/O条件の測定であり、全システムの復号性能と同じ指標ではない。ホストからGPUへの転送が隠せない条件では、退避領域を大きくするほど追加遅延が増える。メモリ削減率と復号速度を同時に示す必要がある。

### 圧縮品質の条件依存

表4のMMLUでは正確保持40%、ランク25%でも0.6782とFP16基準0.6807に近い一方、GSM8Kでは正確保持80%、ランク25%でも0.0667とFP16基準0.7809から大きく悪化する。この結果はタスクによって圧縮耐性が極端に違うことを示す。したがって実装がメモリを減らせても、すべての数学推論や長い推論連鎖で「軽微な品質劣化」と言い切ることはできない。PMCOの精度制約が正しく較正されていることが重要である。

## 既存研究との差

固定ランクのSVD圧縮方式は、要求の長さや精度感度にかかわらず同じランクを使う場合がある。TierKVは事前入力の情報から要求ごとに階層境界とランクを選ぶ。トークン削除方式はメモリを減らせるが過去情報を不可逆に失うのに対し、TierKVはフラッシュ上に残す。フラッシュ退避だけの方式は毎ステップの読込遅延が大きいのに対し、圧縮DRAM階層を中間に置いて退避量を制限する。

MLA型の潜在注意は学習済みモデルの内部表現を変えるか、後付け変換で計算費が増える場合がある。TierKVは既存モデルの重みを変えず、KVキャッシュの配置と低ランク再構成経路を変更する。値の潜在空間集約と鍵の融合注意カーネルにより、全ランク再構成のメモリ往復を避ける点が実装上の特徴である。重み量子化とKV圧縮は独立して併用できるが、同じ量子化率を使った比較が必要である。

## 限界・適用条件

第一に、復号速度の低下が明確に存在する。平均0.71倍という復号速度比は、生成するトークン数が多い会話や長い思考連鎖では重要な負担になる。事前入力の高速化が要求全体の時間を改善するかは、入力長と出力長の比率に依存する。容量だけでなくトークン間遅延も評価すべきである。

第二に、圧縮の品質影響はタスク依存である。特にGSM8Kのような計算推論では強い圧縮が深刻な正答率低下を起こす例があり、精度制約の較正が不適切だと品質が保てない。原著の評価モデル以外に同じ閾値を使うことは危険である。

第三に、将来生成長の予測は確率的である。予測が外れると階層境界の計画が過不足を起こす可能性がある。メモリ上限が急に下がる、他アプリが増える、極端に長い回答が生成されるといった状況での頑健性は別途評価が必要になる。

第四に、フラッシュ退避はI/O待ちを完全に隠せない。モバイルGPUのホスト・デバイス転送帯域が狭いと、先読みが成功してもGPU転送が残る。フラッシュ容量を使えることと、復号が高速であることは別である。端末のフラッシュ性能やOSのI/O制御も影響する。

第五に、評価はAdrenoとMaliの3種類のモバイルSoCが中心である。WindowsのRTX GPU、NVMe SSD、CUDAカーネル、サーバー上の複数要求を対象とした結果ではない。llama.cppの通常版へそのまま追加するだけで同じ効果が得られるとは限らず、OpenCL融合カーネルと端末別調整を要する。

第六に、論文のEuroSys 2027書誌は2026年時点では開催前の先行公開情報であり、開催済みの会議論文として扱わない。また論文は複数要求のKV接頭辞再利用との統合を未解決課題として挙げる。接頭辞共有と低ランク階層を組み合わせるには、ランク形状と射影行列の互換性が必要になる。
