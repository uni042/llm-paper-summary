# BlockFFN: Towards End-Side Acceleration-Friendly Mixture-of-Experts with Chunk-Level Activation Sparsity

> **要点**: BlockFFNは、混合専門家（Mixture-of-Experts; MoE）の「1トークン当たりは疎でも、複数トークンをまとめるとほぼ全専門家が必要になる」という弱点を狙う。ReLU+RMSNormルータで各トークンの専門家数を可変にし、連続トークンが同じ専門家集合を再利用するよう学習して、投機的デコード（speculative decoding）で複数トークンを同時処理しても高い疎性が残る構造を作る。

## 概要

通常のMoEは、各トークンをTop-k個の専門家だけへ送ることで1トークン当たりの浮動小数点演算を減らす。しかし端末側推論では、重みを外部メモリから読む費用や、小さい演算を多数起動する費用が支配的になりやすい。さらに投機的デコードのように複数候補トークンを一括検証すると、各トークンが別々の専門家を選ぶため、その**和集合**は大きくなり、結局ほとんどの専門家重みを触ることになる。

BlockFFNはこの問題を、トークン単位疎性（Token-Level Sparsity; TLS）だけでなく、複数連続トークンの専門家和集合に対する**チャンク単位疎性（Chunk-Level Sparsity; CLS）**として明示する。モデル構造ではTop-kの離散選択をやめ、線形ルータ→ReLU→RMSNormでゼロ/非ゼロを連続的に学習できるようにする。学習では隣接トークンの活性パターンを揃える損失と、チャンク内で専門家が一度でも活性化する確率を抑える損失を追加する。

結果として80%超のTLSと、8トークンチャンクで70%超のCLSを両立する。NVIDIA Jetson Orin NX 16GB上の専用カーネルでは、疎FFNだけの1トークン処理よりも、EAGLE-2の投機木をまとめて処理する32トークン相当の設定が最も速く、密な自己回帰基準に対して最大3.67倍のデコード高速化を報告する。

## 背景と問題設定

### TLSが高くても、複数トークンをまとめると疎ではなくなる

専門家数を (N_e)、あるトークンが活性化する専門家数を (a_t) とすると、TLSは各トークンで未使用の専門家割合を表す。たとえば80% TLSなら平均して20%程度の専門家だけを使う。

しかしGPUカーネルや投機的デコードでは複数トークンをまとめて処理する。このとき必要なのは各トークンの専門家数の平均ではなく、チャンク内で一度でも選ばれた専門家の和集合である。各トークンが別の20%を選べば、8トークン後には和集合がほぼ全専門家へ広がり、重み読み込み・カーネル起動を削れない。

BlockFFNはCLSを「1 − チャンク内で活性化された専門家和集合 / 全専門家数」と定義し、実機でまとめて省ける重み量に近い指標として扱う。

### 固定Top-kは計算需要の違いを表しにくい

通常のTop-kルータは、簡単なトークンにも難しいトークンにも同じk個を強制する。また離散的な上位k選択は勾配を直接通しにくく、負荷均衡など補助損失を別途設計しやすい。

BlockFFNは、トークンによって活性専門家数自体を変えられるようにし、意味が単純な数字・文字では少なく、複雑な意味を持つトークンでは多くの専門家を使う方向を狙う。

## 手法

### 1. ReLU + RMSNormで可変数の専門家を選ぶ

入力表現 (x) をルータ線形層へ通し、各専門家のスコアを得る。Top-kで順位切断する代わりにReLUを使い、負のスコアを0、正のスコアを活性として残す。このため「何個選ぶか」は固定kではなく入力に応じて変わる。

ReLUだけで活性値そのものへ疎性圧力をかけると、ルータ出力の大きさが縮み、専門家出力の混合比まで不安定になる。そこでReLU後にRMSNormを置き、**どの専門家を0にするかというパターン**と**活性値の尺度**を分離する。これがReMoE系の単純ReLUルーティングに対する主要な構造差である。

### 2. 活性局所性損失で隣接トークンの専門家集合を揃える

連続トークンが似た専門家を使えば、チャンクで必要な重み和集合が小さくなる。BlockFFNは隣接トークンの軟らかい活性パターン間に二値交差エントロピー（Binary Cross Entropy; BCE）型の**活性局所性損失**を加え、選択パターンを近づける。

入力は隣接する2トークンのルータ事前活性、処理はシグモイドを通した活性確率の整合、出力は「次トークンも前トークンに近い専門家を使いやすい」ルータである。論文の分析では隣接トークン間の活性専門家再利用率が平均85%超に達する。

### 3. チャンク疎化損失で「一度でも使う専門家」を直接減らす

局所性だけでは、少しずつ専門家集合がずれて長いチャンクで和集合が広がる可能性がある。そこで各専門家について、長さ (L) のチャンク内で少なくとも1回活性化する確率を計算し、その平均を抑える**チャンク疎化損失**を追加する。

これはTLSを間接的に改善する損失ではなく、実際のCLS定義に近い量を直接最適化する。言語モデル損失、活性局所性損失、チャンク疎化損失を組み合わせ、疎性と品質を共同学習する。

### 4. 投機的デコードでは専門家和集合だけを一括計算する

EAGLE-2などのドラフト木では、一度の検証で複数候補トークンがターゲットモデルへ入る。BlockFFNのカーネルは、まずその候補群で必要な専門家の和集合を求め、その専門家だけについて複数トークン分のFFNをまとめて計算する。

高CLSなら和集合が小さいため、重みロードを減らしつつ大きめの行列演算へまとめられる。各トークンを別々の疎カーネルで処理するより、GPUのテンソルコアを使いやすい。計算後に活性マスクを適用し、各トークンに不要な専門家出力は除く。

## 評価

### 代表的な評価条件

| 項目 | 条件 |
|---|---|
| 比較アーキテクチャ | Vanilla Top-k MoE、DeepSeekMoE、GRIN、ReMoEなど |
| 疎性指標 | TLS、チャンク長を変えたCLS、隣接トークン専門家再利用率 |
| 品質指標 | 検証パープレキシティ、下流タスク |
| デコード比較 | 密な自己回帰（AR）、純粋な投機的デコードEAGLE-2、疎FFNのみ、疎性+投機的デコード |
| 実機 | NVIDIA Jetson Orin NX 16GB |
| 実装 | CUTLASSベースの専用疎FFNカーネル、テンソルコア利用 |
| 代表チャンク | 8トークンCLS、投機木をまとめる32-token設定 |

### 主な結果

| 観点 | 結果 | 意味 |
|---|---:|---|
| トークン単位疎性 | **80%超 TLS** | 単一トークンでは大部分の専門家を省ける |
| 8トークンチャンク疎性 | **70%超 CLS** | 複数トークンでも専門家和集合が広がりにくい |
| 隣接トークン再利用 | 平均 **85%超** | 重み局所性が高く端末側の転送削減に有利 |
| EAGLE-2のみ | 約 **1.74倍** | 投機だけではFFN重み処理が残る |
| 疎性中心の1-token設定 | 約 **3.14倍** | TLSを直接実機速度へ変換 |
| 疎性 + 投機的デコード | 最大 **3.67倍** | CLSにより複数候補をまとめても疎性を保持 |

論文は、1-token設定と32-token設定のFFN速度が、それぞれのTLS/候補和集合疎性から予想される理論上限に近づくことも確認している。つまり「疎性の数字は高いがGPUでは速くならない」というギャップを、専用カーネルとチャンク局所性でかなり埋めている。

## 既存研究との差

従来MoEは主に「1トークンで何個の専門家を使うか」を中心に設計する。BlockFFNは、投機的デコードやバッチ化で実際に複数トークンを処理する状況では**専門家の和集合**がハードウェアコストを決めると捉え、CLSを学習目標へ入れる。

ReMoEのReLUルータに対してはRMSNormで活性パターンと尺度を分離し、さらにCLS向け損失を加える。投機的デコード研究に対しては、ドラフト木の候補数を増やしてもターゲット側FFNが疎なままになるようモデル構造そのものを共設計する点が異なる。

## 限界・実装状況

高いCLSは学習時から誘導するため、既存の密モデルやMoEへ推論時だけ差し込める最適化ではない。モデルの事前学習または継続学習と専用カーネルが必要で、既存チェックポイントを無変更で高速化する用途には向かない。

速度評価の中心はJetson Orin NX 16GBであり、データセンターGPUでは重み帯域・演算密度の比率が異なる。同じ3.67倍をそのまま期待できず、特に大きいバッチでは密GEMMの効率が上がるため疎化の相対利得が変わる。

またCLSを高め過ぎると、隣接トークンが本来異なる専門家を必要とする場面で表現力を制限する可能性がある。論文は品質との両立を示すが、より長いチャンクや分布外入力でどこまで活性局所性を維持できるかは追加検証が必要である。

公式コードとチェックポイントはTHUNLPから公開され、学習、ベースライン、推論カーネルが分離して提供されている。
