# SwapMoE: Serving Off-the-shelf MoE-based Large Language Models with Tunable Memory Budget

> GPUには少数のexpert用slotだけを置き、RAM上の実expert重みを必要に応じてslotへ入れ替えることで、指定したmemory budget内で既存MoEを動かす近似方式。

## 概要
SwapMoEは、全expertをGPUへ置けない端末で、**少数のexpert用スロットだけをGPUへ用意し、中身をactual expert間で入れ替える**方式である。再学習なしで既成MoEを使える代わりに、常にnative expertが全て利用可能とは限らないため近似推論になる。

## 手法のあらまし

### 1. `Virtual Expert`は新しいexpertではなくGPU上の空き枠

SwapMoEでいうVirtual Expertは、新しいexpertを学習するわけではない。

GPU上に置く固定数の **expert slot** を指し、そのslotへactual expert weightを差し替えて使う。

例えば64 expertあるlayerでも、GPUには8 slotだけ置き、現在の入力で重要な8 expertをそこへ割り当てる、といった使い方になる。

### 2. 事前にlayerごとのslot数を決める

全layerへ同じslot数を与えるのではなく、layerごとの

- expert欠落に対する品質感度
- memory cost
- swap latency

を測り、限られたmemory budgetをどこへ配るか決める。

構成候補が非常に多いため、論文ではgenetic algorithmを使って探索する。ここでのgenetic algorithmは、**各layerへ何slot配るかの多数の組み合わせを試し、品質とlatencyの良い配置を残していく探索法**である。

### 3. 実行中にactual expertをslotへ入れ替える

routerが選ぶexpertと最近の利用傾向を見て、GPUにある低頻度expertとRAM側の高頻度expertをswapする。

毎tokenで必要expertを全てon-demand loadするのではなく、**一度slotへ載せたexpertを複数tokenで再利用する**ことでtransfer回数を減らす。

### 4. static pruningとの違い

static pruningは削除したexpertを二度と使えない。SwapMoEはGPUに常駐していないだけで、RAMには元expertを保持しており、必要に応じて後からslotへ入れ替えられる。

このため小さい固定pruned modelより元モデルの容量を活かせる一方、現在slotにないexpertは即座に使えないため、memory budgetを絞るほどquality trade-offが増える。

## 評価

### まず見るところ
- **結論:** 少数のexpert slotを入れ替えることで、4GB級Jetsonでも既成MoEを再学習なしで動かせる。
- **メモリ:** GPU resident expertを大幅に減らせる。
- **速度:** 毎回on-demand loadするよりswapを局所化でき、latencyを削減する。
- **品質:** **近似あり**。slot数が少ないほどnative expert不在の影響が増える。
- **注意点:** Jetson実機だが、taskは要約・日本語LM中心でmodern 70B級MoEやSSD階層は未評価。

### 実機

| 端末 | 主な条件 |
|---|---|
| Jetson Nano | 最大4GB級memory |
| Jetson AGX Orin | edge GPU / shared-memory系 |

SwitchT-16/32/64はSAMSum要約、GPTSANはJapanese Wikipedia language modelingで評価した。

### 代表的なmemory削減

| 条件 | 元 | SwapMoE | 結果 |
|---|---:|---:|---|
| Switch Transformer | 14.2 GiB | 4.7 GiB | memory 67%削減 |
| 同条件 | — | — | latency 50%削減、ROUGE-2低下0.041 |

### SwitchT-16のmemory budget別結果

| 予算 | 実測peak | latency | ROUGE-2 |
|---:|---:|---:|---:|
| 2.0 GiB | 1.64 GiB | 0.82 s | 0.21 |
| 3.0 GiB | 2.74 GiB | 0.65 s | 0.22 |
| 3.5 GiB | 3.58 GiB | 0.76 s | 0.23 |
| 4.0 GiB | 3.99 GiB | 0.80 s | 0.23 |

memoryを増やせば常にlatencyが単調に下がるわけではなく、swap patternやplanner誤差にも左右される。

### pruningとの比較

Jetson NanoでSwitchT-64を約14GiBから2.6GBへ落とした条件では、SwapMoEはstatic pruningより大きく品質を維持した。SwitchT-32を4.7GBで動かす条件でもROUGE-2 0.232で、pruningより高かった。

一方On-demand方式はnative expertを読み込めるため品質は守りやすいが、毎回のweight transferでlatencyが大きい。
