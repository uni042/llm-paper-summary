# MELTing point：モバイル言語モデル推論の速度・電力・熱・品質の横断測定

## 概要

大規模言語モデルをスマートフォンや小型計算機で動かす際、単にトークン生成速度が高ければ実用的とは限らない。モデル読込み中の操作不能、端末の発熱、連続実行での動作周波数低下、バッテリー消費、量子化による回答品質の劣化も重要である。MELTing pointは、こうした端末側の制約を統一的に測定するため、Android、iOS、NVIDIA Jetsonを自動制御する測定基盤MELTを構築し、複数の言語モデルと推論実装を比較した研究である。

MELTはモデルの取得・変換・量子化から、端末への配備、対話の自動実行、推論イベントの記録、電力・熱・メモリ追跡、品質評価までを一連の処理として扱う。異なる推論基盤が使うモデル形式やハードウェアAPIを吸収し、単純なベンチマークだけでなく端末を実際に操作したときの応答性も評価する。

主な知見は、端末の自己回帰生成がしばしば**メモリ帯域律速**であり、ビット数を下げれば必ず高速になるわけではないこと、モデルが動作しても電力・熱・応答性の面で長時間利用が難しいこと、そして量子化による品質低下が小型モデルで無視できないことである。原著の評価条件では4ビットモデルの生成スループットが3ビットモデルより平均24.77%高かった。2024年時点のハードウェアと推論実装の結果であり、現行製品の普遍的な優劣を示すものではない。

## 問題設定

### 動くだけでは配備可能とは言えない

端末メモリへモデル重みが収まるかどうかは最初の制約だが、実際の対話では入力処理、生成、アプリ画面描画、バッテリー、熱管理が競合する。GPUが画面描画にも使われる端末では、推論中にUIが重くなり、メモリ不足ではアプリが強制終了する。モデル読込み中の数秒間に端末が無反応になることもあり、生成速度だけの測定ではこうした問題を見逃す。

また、自己回帰生成では1トークンごとにモデル重みへ繰り返しアクセスするため、演算器の理論的な演算性能より、DRAMからオンチップメモリへの転送が支配的になりやすい。端末の温度上昇で動作周波数が下がれば、短時間のピーク性能と連続実行性能も一致しない。MELTはこれらをモデル・推論基盤・端末ごとに追跡し、ボトルネックの原因を分解する。

### 量子化の品質・速度・容量は別の軸

低ビット量子化は重み容量と転送量を減らすが、非対応演算形式では復元演算（dequantization）が増え、3ビットより4ビットの方が速くなることもある。低ビット化による容量削減が、演算効率や下流の回答品質を自動的に改善するわけではない。原著は複数のモデルと量子化方式でこの非単調性を検証し、端末のメモリ不足による実行失敗も含めて評価する。

## 手法・測定基盤

### 1. Raspberry Piを中心とする端末群の自動制御

MELTはRaspberry Pi 4を制御ノードとし、スマートフォン群（PhoneLab）とJetson群（JetsonLab）へ実験を配布する。制御ノードはモデルと対話データの転送、実行条件の適用、アプリの起動・操作、イベント記録、結果収集、実験間の休止を自動化する。これにより、同じ対話系列を端末や推論基盤を変えて繰り返し実行できる。

AndroidではAndroid Debug Bridge（ADB）を利用し、Wi-Fi経由で入力やアプリ操作を送る。iOSではBluetoothの仮想ヒューマンインタフェース装置（Human Interface Device; HID）としてキーボード・マウス操作を模倣する。JetsonではSSH経由でCLI実行を制御する。モデルの実行開始・終了時刻、生成の各段階、メモリ、温度、消費電力を記録し、後から時系列で照合できるようにする。

### 2. 電力測定の再現性確保

スマートフォンはMonsoon電力計へ接続し、端末のバッテリーを取り外して電源端子から給電することで、充電動作の影響を避ける。最大5kHzで電力を測り、USB給電線は切替ハブで切り離す。Wi-FiとBluetoothの待機電力は測定値から補正する。画面輝度は25%、ダークモードを使用し、OSやアプリの自動更新、適応充電などの変動要因を抑える。

Jetsonではシステムファイルシステムの電力・温度センサを約100Hzで監視し、CPU、GPU、DRAMなどの構成要素の状態を追う。Jetsonの電力モードとファン設定も制御し、電力制限とメモリ周波数が推論へ与える影響を比較する。測定器と端末の時計は同期し、推論イベントと電力の山を対応付ける。

### 3. モデル変換と実行基盤の抽象化

モデルは公開重みから取得し、推論基盤に応じてGGUFやコンパイル済み形式へ変換する。必要に応じて量子化し、端末へ配備する。対象にはllama.cpp、MLC-LLM、iOS向けLLMFarmなどが含まれる。異なる実装が同じモデル名を使っていても、量子化方式やGPUカーネル、モデルのコンパイル条件が異なるため、同一の実行条件を可能な範囲で揃える必要がある。

品質評価ではLM-Evaluation Harnessと推論基盤への接続層を用い、複数選択問題の正答率や生成課題の指標を測る。量子化誤差の分析では、指示微調整や人間フィードバックによる強化学習の影響を分離するため、主に事前学習モデルを評価する。したがって、対話アプリとしての使いやすさと、量子化そのものによるモデル品質の変化は別の測定系である。

### 4. 推論段階を分けた測定

入力文を処理する事前計算（prefill）と、トークンを逐次出力する復号（decode）を分けて計測する。前者は比較的大きな行列演算をまとめて行えるが、後者は小バッチでモデル重みを繰り返し読むため、メモリ帯域の影響が強い。端末全体の応答時間に加え、演算子ごとのカーネル時間、モデル読込み時間、連続対話中の電力・温度変化を追跡する。

原著の低水準分析では、Llama-7Bの3ビット版をAndroidのMLC-LLMで実行し、量子化復元と行列積を融合した演算が事前計算時間の97%、復号時間の95.7%を占めた。ここでの割合はプロファイラで観測した特定の演算子構成に対するもので、あらゆる推論実装の全体時間を示すものではない。

## 評価・主要結果

### 4ビットが3ビットより速い条件

原著の端末・実装の組合せでは、4ビット量子化モデルの生成スループットが3ビット版より**平均24.77%高い**。ビット数が少ない方が重みは小さくなるが、復元演算の実装、キャッシュ整列、カーネルの最適化度合いが性能を左右する。4ビットへ上げるとメモリ使用量が増え、RAMの小さい端末ではメモリ不足で実行できない場合もあるため、速度だけでなく動作可否を合わせて評価する必要がある。

同様に、MLC-LLMはllama.cppに対してGPU生成で平均約4%高いスループットを示し、CPU版llama.cppとの比較では平均約28%高い。ただし対象モデルや端末で逆転例があり、最大3.53倍という局所的な条件も存在する。MLC-LLMはプラットフォームごとのコンパイルが必要で、モデルの持ち運びやすさとの交換条件がある。**推論基盤の一般的な順位ではなく、同時点の端末・モデル・実装条件の比較**として扱う。

### 端末間のばらつきと消費電力

MLCのGPU実行では、iPhoneのMetal経路はAndroidのOpenCL経路に対して平均78.93%高い生成スループットを示した。これも端末SoCやカーネル実装、量子化形式が完全に揃ったハードウェア比較ではない。CPUでのllama.cpp実行でもiPhoneが速い条件がある一方、電力効率では必ずしも優位ではない。処理量とエネルギー効率を別々に読む必要がある。

Zephyr-3Bの4ビット版を使った対話時の電力波形では、iPhone 14 Proの平均化された電力が最大13.8W、瞬間最大18W超に達した一方、Galaxy S23は瞬間最大14W、持続8.5W未満だった。電力の山は入力処理や生成、モデル読込みの時刻と対応する。モデル読込みは平均2.41±0.09秒かかり、その間に端末が無反応になることがあった。ピーク電力の比較だけでバッテリー持続時間を判断できず、生成速度、処理時間、待機時電力を積算する必要がある。

### 継続実行での性能劣化と発熱

iPhone 14 ProでZephyr-3Bの4ビット版を50プロンプト連続実行した実験では、開始直後から生成性能の低下が観測され、平均的には20番目と32番目のプロンプト付近で挙動の変化があった。著者らは動作電圧・周波数制御（DVFS）や省電力モードへの移行を原因候補として挙げるが、遷移時点は実験間で変動する。Jetson AGXの50Wモードでは、より滑らかな持続スループットが得られた。

端末表面温度は、iPhone 14 Proでの対話後に47.9°Cに達する条件があった。これはユーザーが触れる端末として快適性を損なう水準であり、推論速度だけでは評価できない。モデルがメモリに収まっていても、画面描画の競合、発熱、電力制限で実用性が下がる。連続利用の品質は、短いベンチマーク一回の結果から推定できない。

### 量子化と回答品質

低ビット化は重み容量を減らすが、品質の悪化が特に3ビット以下で目立つ。原著の定性的評価では、3B以下の一部モデルが3ビットで同じプロンプトを反復したり、幻覚を多く出したりして、実用困難になった。7B以上のモデルではAWQやGPTQがやや良い条件もあるが、モデルサイズが増える交換条件があり、全データセットで一つの量子化方式が優位になるわけではない。

量子化品質の測定はHellaSwag、Winogrande、ARC、TruthfulQAなどを用い、選択問題は尤度に基づく正解率、生成課題はBLEURTを使う。これらの値は事前学習モデルの評価であり、指示微調整済みの対話品質へ直接等置できない。量子化方式の評価では、**モデルの大きさ・量子化ビット数・手法・実装・データセット**の相互作用を考える必要がある。

### エッジへのオフロードと電力モード

Jetson Orin NanoとAGXを端末近傍の計算資源とみなし、Wi-Fi 6でプロンプトを送る設定を検討する。Jetsonでは電力モードを変え、CUDA上のllama.cppで生成スループットとエネルギーを測定した。Zephyr-7Bの4ビット版では、端末側の対応条件に比べ、Jetsonの事前計算が平均3.3倍、生成が1.78倍のスループットを示す例がある。これらは実験の電力モード・モデル・端末構成に依存する。

興味深いことに、低電力モードが常にトークン当たりの省エネルギーを意味するわけではない。メモリ周波数が下がると重み読込み待ちが長くなり、演算器が停止している時間が増える。より高い電力枠でメモリ転送を速く終えた方が、結果としてトークン当たりエネルギーが小さくなる場合がある。これはピーク消費電力と処理完了までの総エネルギーを区別すべき理由である。

## 既存研究との差

既存のモデル単体ベンチマークは、固定入力に対するトークン生成速度やメモリ量を測ることが多い。MELTは端末の電力・温度・応答性を時系列で測り、OSやアプリの操作を含む実行経路を自動化する点が特徴である。AndroidとiOSの操作手段が異なる問題を制御ノード側で吸収し、推論実装と端末の組合せを横断的に比較できる。

また、量子化の精度と実行速度を同じ研究で測定し、低ビット化の利得が単純な単調関係ではないことを示す。メモリ帯域律速という構造的な問題を演算子プロファイルと電力・メモリの時系列で裏付けており、モデルをさらに圧縮すべきか、カーネルやメモリ階層を改善すべきかの設計判断に役立つ。

## 限界・負の結果

第一に、対象は2024年時点の1B〜13B級モデルと端末・推論実装である。最新のllama.cpp、MLC、Android NPU、iOS GPU、より新しいモデルや量子化形式では結果が変わり得る。平均24.77%や78.93%の差を、2026年の製品の性能差として扱うべきではない。

第二に、端末の画面描画、通信、バッテリー状態、周囲温度、OSの省電力制御は実利用で変動する。原著は測定条件を揃えているが、すべての同時実行アプリや屋外利用を再現したわけではない。連続実行の温度上昇や周波数低下も端末固有であり、単一の熱しきい値を一般化できない。

第三に、量子化の品質評価は主に事前学習モデルであり、指示微調整済みモデルの全対話品質を測ったものではない。3ビットが実用困難という例はモデル・実装・課題に依存し、3ビット方式全般が必ず使えないと結論するのは過剰である。

第四に、オフロード評価ではWi-Fi 6の高速接続を仮定し、ネットワーク往復遅延や同時利用者の競合を十分に評価したわけではない。端末内推論とエッジ実行を比較するには、通信費用、プライバシー、エッジ装置の待機電力まで含めた系全体の評価が必要である。

第五に、論文自身が指摘する通り、世界全体での環境負荷や多数端末へ分散した推論の総エネルギーは評価対象外である。端末一台の電力効率が高くても、装置製造や待機電力まで含む環境負荷の最小化を示すものではない。
