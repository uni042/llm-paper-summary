# FlexServe: A Fast and Secure LLM Serving System for Mobile Devices with Flexible Resource Isolation

> TrustZoneのアクセス権と資源管理権を分離してページ単位セキュアメモリと切替可能NPUを実現し、LLM向けキャッシュ・回収・先読みでセキュア端末内推論の起動遅延を大幅に削減する。
## 書誌情報
- **著者**: Yinpeng Wu, Yitong Chen, Lixiang Wang, Jinyu Gu, Zhichao Hua, Yubin Xia
- **著者・所属**: Institute of Parallel and Distributed Systems, Shanghai Jiao Tong University
- **公開**: arXiv:2603.09046v3
- **種別**: プレプリント
- **対象**: 端末内LLM、ARM TrustZone、TEE、NPU隔離、セキュアメモリ、KVキャッシュ、メモリ管理、マルチモデルエージェント
- **実装**: NanoPC-T6上に試作実装。Flex-Monitor約4.5K LoC、C/C++の信頼アプリケーション（Trusted Application）としてFlexServe Framework約8.3K LoCを実装し、Llama3/Qwen3系列をサポートする。論文本文からFlexServe本体の公開リポジトリURLは確認できない。
## 概要
端末内大規模言語モデル（LLM）をARM TrustZoneのセキュア世界（secure world）で保護すると、GB級の連続セキュアメモリ確保、通常世界（normal world）と分断された資源管理、NPUの固定隔離が大きな起動遅延と通常アプリへの資源圧迫を生む。FlexServeはアクセス権と管理権を分離し、通常OSから内容は読めないままページ単位で割当・回収できるFlex-Memと、必要時だけセキュア世界へ切り替えるFlex-NPUを構築する。さらに層単位のセキュア推論パイプライン、モデル重み/KVの動的キャッシュ、二段階非同期回収、ワークフロー認識先読みを組み合わせる。NanoPC-T6実機で単一モデルの先頭トークン遅延を素朴なTrustZone構成比平均10.05倍、最適化TrustZone構成比平均2.44倍高速化し、通常アプリ性能を非推論時の97.2%に維持する。

中核は『資源へアクセスできる主体』と『資源を割当・回収できる主体』を分離する回収可能資源隔離（Recallable Resource Isolation）である。第2段階ページテーブル（Stage-2 Page Table; S2PT）とシステムメモリ管理ユニット（System メモリ Management Unit; SMMU）を使い、通常世界OSにはFlex-Mem/Flex-NPUの内容へのアクセスを許さない一方、OSが既存のメモリ圧力検知・割当機構を使ってセキュア資源の量を管理できるようにする。これをLLM側の再利用確率、回収コスト、モデル/KVキャッシュの意味情報と組み合わせ、TEEに大きな固定資源を永久予約する方式と、毎回全資源を破棄する方式の二者択一を避ける。

代表結果として、8GBセキュアメモリ割当はFlex-Memと連続セキュアメモリ確保の比較でCMA 6440.67msに対して568.58ms、11.33倍高速。通常ページを権限切替でセキュア化するため、断片化環境で高価な物理ページ圧縮を避けられる。
## 問題設定
端末内大規模言語モデル（LLM）の重みと利用者データをカーネル権限の攻撃者から守るため、推論をARM TrustZoneのセキュア世界へ移すと、従来の固定的なセキュア資源隔離がLLMの大容量・動的ワークロードに合わない。TrustZoneはセキュアメモリを少数の物理連続領域として扱うため、断片化した16GB端末で8GBを連続メモリアロケータ（CMA）から確保すると6.44秒かかる一方、通常のmmapは0.56秒で済む。NPUのドライバ状態も簡単には切り替えられず、CPUだけでセキュア推論するとLlama3.1 8Bの128トークンプリフィルが約30.06秒になり、通常世界NPUの約1.94秒から大幅に悪化する。さらにセキュア世界がモデル重みやKVを固定保持すれば通常アプリのメモリを圧迫し、毎回解放すればモデルロードと再計算で先頭トークン遅延が伸びる。
## 新規性
中核は『資源へアクセスできる主体』と『資源を割当・回収できる主体』を分離する回収可能資源隔離（Recallable Resource Isolation）である。第2段階ページテーブル（Stage-2 Page Table; S2PT）とシステムメモリ管理ユニット（System メモリ Management Unit; SMMU）を使い、通常世界OSにはFlex-Mem/Flex-NPUの内容へのアクセスを許さない一方、OSが既存のメモリ圧力検知・割当機構を使ってセキュア資源の量を管理できるようにする。これをLLM側の再利用確率、回収コスト、モデル/KVキャッシュの意味情報と組み合わせ、TEEに大きな固定資源を永久予約する方式と、毎回全資源を破棄する方式の二者択一を避ける。
## 手法
### 手法のあらまし
実行開始時、通常世界OSは既存のページアロケータで必要量の通常ページを確保し、Flex-Monitorへ保護切替を要求する。Flex-Monitorは対象ページを通常世界のS2PTとデバイス側SMMUから外し、セキュア世界だけがアクセスできるFlex-Memへ変換するため、物理的な巨大連続領域を事前予約する必要がない。NPUを使うときはMMIO領域とドライバ状態を通常世界から外し、保護されたNPUドライバ用サンドボックスのS2PTへ移し、NPUのDMA到達先をFlex-Memへ限定する。セキュア世界のFlexServe Frameworkはモデル実行を、メモリ割当、暗号化モデルのSSD読込、復号、NPU前向き計算へ分解し、層iの計算中に層i+1の割当・読込・復号を進めるパイプラインを構成する。モデル重みと履歴KVはFlex-Mem内へ動的にキャッシュし、最近の呼出し率、頻度、履歴プロンプト長からモデルごとのキャッシュ予算と保持対象を決める。マルチモデルのエージェントワークフローが過去の呼出しパターンに一致すると、現在モデルのデコード中に次モデルの重みと関連KVをSSDから先読みする。通常アプリのメモリ圧力が上がると、OSは返却が必要なFlex-Mem量だけをセキュア側へ通知し、FlexServeは具体的にどのページを捨てるかをLLMの意味と回収費用から選ぶ。モデル重みはSSDに元データがあるためゼロ化だけで返せるが、更新されたKVは暗号化してSSDへ書き戻す必要があるので、モデル重みページを先に返しKVを後段へ回す二段階回収を行う。さらにページをOSへ返却可能と通知した後に暗号化、ゼロ化、マッピング復元を進めることで、通常世界の待ち時間から高価な処理を外す。NPU利用終了時はMMIO/ドライバマッピングを通常世界へ戻し、保護不要期間はモニタを凍結して整合性ハッシュを保持する。次のセキュア要求ではハッシュ検証後に保護を再有効化する。このように、通常OSの大域的資源管理能力を残したまま、ページ/NPUの内容アクセスだけをTEE境界で遮断し、その上でモデルロード、KV再利用、先読み、回収をLLM向けに最適化する。

### 回収可能セキュアメモリ（Flex-Mem）
巨大な連続セキュア領域を起動時に固定予約せず、通常OSが既存アロケータで確保した任意の物理ページをS2PTとSMMUの権限切替によってセキュア世界専用へ変換する。通常OSはページ内容を読めないが、どれだけのページを割り当てるか、メモリ圧力時にどれだけ返却させるかという管理権は維持する。回収要求時にはFlexServeが具体的なモデル/KVページを選び、OSへ返却可能になったことを早期通知した後で、必要なKVの暗号化書戻し、ページゼロ化、S2PT/SMMU復元を非同期に進める。これにより物理メモリ断片化に伴うCMA圧縮を避け、8GB確保を6440.67msから568.58msへ、128MBのクリティカル回収待ちを74.69msから2.89msへ短縮する。

### 回収可能セキュアNPU（Flex-NPU）
NPUを常時セキュア領域へ固定するのではなく、セキュア推論の間だけNPUのMMIO領域を通常世界S2PTから外し、保護NPUドライバを専用サンドボックスS2PTへマッピングする。NPUのSMMUはFlex-MemだけをDMA到達可能にするため、侵害された通常OSがNPUを代理にして秘密データを通常メモリへコピーする経路を遮断する。推論終了後はMMIOとドライバ状態を通常世界へ戻し、通常アプリからNPUを再利用できる。切替は0.21msで、SMMU設定やタスク発行の追加費用も小さいため、CPUのみのセキュア推論を避けながら、必要な期間だけNPUを排他的に保護する。

### セキュア推論パイプラインと動的キャッシュ
モデルのプリフィルを、Flex-Mem割当、暗号化されたモデル層のSSD読込、復号、NPU計算へ分解し、異なる資源を使う段階を層単位で重ねる。SSDモデルロードが残る律速になるため、モデル重みと履歴KVをFlex-Mem内へ動的に保持する。最近の呼出し率、頻度、履歴プロンプト長からモデルごとのキャッシュ予算を決め、再利用価値の高いKVとモデル前方部分を優先する。複数モデルを順に呼ぶエージェントワークフローでは過去の遷移パターンを利用し、現在モデルのデコード中に次モデル重みと必要KVをSSDから先読みして、次段のコールドロードをクリティカルパスから外す。単一モデルだけでなくマルチモデルの連鎖的な起動遅延を減らす点が重要である。

### LLM認識型の協調メモリ回収
通常世界OSとセキュア側ランタイムが秘密内容を共有せず役割を分担する。OSは全端末のメモリ圧力から『何MB返すか』を決め、FlexServeはモデル重み、KV、再利用履歴、書戻し費用から『どのページを返すか』を決める。SSDに原本があるモデル重みページはゼロ化だけで返せるため先に選び、更新状態であるKVページは暗号化・SSD書戻しが必要なので後段に回す。さらに低負荷時に休止KVを事前にSSDへ退避しておけば、将来の緊急回収時にはゼロ化だけで済む。この二段階・非同期方式により、通常アプリが必要とするメモリを早く返しながら、将来再利用される可能性が高いセキュアLLMキャッシュを可能な限り保持する。

### 全体のデータ／制御の流れ
Flex-MonitorがEL2/EL3でページ/NPUのアクセス制御とオンデマンド保護を担当し、セキュア世界の信頼アプリケーションがLLM推論、モデル/KVキャッシュ、先読み、回収対象選択を担当する。通常OSのページアロケータ、メモリ圧力検知、NPU資源管理を全面置換せず、S2PT/SMMUを境界として内容アクセスだけを隔離する。
## 評価条件
- **ハードウェア**: NanoPC-T6 development board、8-core ARM CPU、16GB DRAM、6 TOPS NPU、2.65GB/s SSD
- **ソフトウェア**: Linux カーネル 6.1.57、OP-TEE 4.5.0、Flex-Monitor、C/C++ FlexServe Trusted Application、community reverse-engineered NPU ランタイム
- **モデル**: Llama3.2 3B、Llama3.1 8B、Qwen3 0.6B、Qwen3 1.7B、Qwen3 8B
- **データセット／トレース**: input length 64/128/256/512 合成 リクエスト sweep、UltraChat、OpenAssistant、Dolly Dataset、Alpaca Data、10 mobile agent workflows
- **比較対象**: NW-Base: normal world + パイプライン + NPU、Strawman: TrustZone + CMA secure メモリ + CPU、Strawman-OPT: TrustZone + CMA + パイプライン + secure NPU
- **正確性・品質**: 脅威モデルはカーネル権限の攻撃者を想定し、モデル重みとセキュアクライアント経由の入力・出力の機密性と完全性をS2PT、SMMU、セキュアブート、応答証明で保護する。通常世界クライアント自体の入出力、サイドチャネル、物理攻撃、サービス拒否は範囲外である。性能最適化は同じモデルの実行経路を変えるもので、追加の近似推論を導入しない。
- **資源隔離マイクロベンチマーク**: 8GBセキュアメモリの割当・回収、128MB緊急回収、NPU SMMU設定、NPUタスク発行、Flex-NPU切替、S2PT起動時保護とハッシュ検証など、セキュア資源の遷移に伴う基本費用を個別に測定する。
- **単一モデルのコールドスタート**: モデル/KVキャッシュを無効化し、Llama/Qwen各モデルをINT8で実行する。入力長64〜512トークンと背景メモリ負荷0〜10GBを変化させ、先頭トークン遅延、デコード処理率、断片化による影響をNW-Base、Strawman、Strawman-OPT、FlexServeで比較する。
- **マルチモデルとエージェントワークフロー**: 4GBのセキュアキャッシュ予算で複数モデルへ実データセット由来要求を振り分け、モデル/KV動的キャッシュとワークフロー認識先読みの効果を測る。さらに10種類のモバイルエージェントワークフローで複数モデルを連続呼出しし、応答遅延を比較する。
- **通常世界アプリへの影響**: SQLite、SPEC CPU 2017、sysbench、pgbench、memtier、アプリ起動を使い、Flex-Memの動的拡縮、仮想化、協調回収が通常アプリの性能と利用可能メモリへ与える影響を評価する。
同一NanoPC-T6上で、保護なしの性能上限であるNW-Base、固定的な連続セキュアメモリとCPU推論を使う素朴構成、パイプラインとセキュアNPUを加えた最適化構成、FlexServeを段階的に比較する。マイクロベンチマークでページ/NPU隔離機構の費用を分離した後、単一モデルのコールドスタート、メモリ圧力、複数モデル、エージェントワークフロー、通常アプリ共存へ評価を広げる。さらにFlex-NPU、Flex-Mem、パイプライン、キャッシュ、非同期回収、インライン暗号想定を除去・追加する分析で、改善の寄与を切り分ける。
評価の中心はNanoPC-T6一機種であり、商用Android SoCごとに異なるTrustZone、SMMU、NPUドライバへ数値をそのまま一般化できない。ベンダーNPUランタイムが非公開のためコミュニティ実装を使う。また試験機はインラインストレージ暗号化・復号を備えず、その高速化効果はエミュレーションで推定される。
## 主要結果
FlexServeは、セキュア推論の計算そのものよりも、GB級メモリとNPUをセキュア世界へ出し入れする資源管理費を削減することで大きな効果を得る。Flex-Memは8GBのセキュアメモリ割当を6440.67msから568.58msへ11.33倍、回収を503.64msから157.69msへ3.19倍高速化し、二段階非同期回収は128MBのクリティカル待ちを74.69msから2.89msへ縮める。Flex-NPUのsecure/normal切替は0.21msである。単一モデルのコールドスタートではCPUのみの素朴TrustZone構成比で平均7.15倍・最大14.44倍、パイプラインとセキュアNPUを既に使うStrawman-OPT比でも平均1.85倍・最大2.42倍の先頭トークン遅延改善を示す。論文の全条件集約では平均10.05倍/2.44倍を報告する。複数モデルとエージェントワークフローでは動的キャッシュと先読みの効果が加わり、通常アプリ性能も非推論時の97.2%を維持する。

- 8GBセキュアメモリ割当 / 568.58ms、11.33倍高速 (比較対象: CMA 6440.67ms; 条件: Flex-Memと連続セキュアメモリ確保の比較) — 通常ページを権限切替でセキュア化するため、断片化環境で高価な物理ページ圧縮を避けられる。

- 8GBセキュアメモリ回収 / 157.69ms、3.19倍高速 (比較対象: CMA 503.64ms; 条件: Flex-Mem reclaim) — ページ単位の回収と非同期後処理により通常世界へ資源を早く返せる。

- 128MBクリティカル回収待ち / 2.89ms (比較対象: 二段階・非同期回収なし74.69ms; 条件: two-stage asynchronous reclamation) — モデル重みを先に返し、KVの暗号化書戻しを後段へ移すことで、高価な状態整理を通常アプリの待ち時間から外す。

- Flex-NPU切替 / 0.21ms (比較対象: 固定セキュアNPUまたはCPU-only推論; 条件: secure/normal mode transition) — 必要な期間だけNPUをセキュア側へ貸し出せるため、固定予約による通常アプリへの資源損失を抑える。

- 単一モデル先頭トークン遅延 / 平均7.15倍、最大14.44倍高速 (比較対象: CPU-only Strawman; 条件: キャッシュなし、複数モデル・入力長) — NPU利用と細粒度セキュアメモリ割当を組み合わせることで素朴なTrustZone実行の主要律速を除去する。

- 単一モデル先頭トークン遅延 / 平均1.85倍、最大2.42倍高速 (比較対象: Strawman-OPT; 条件: 両方式ともパイプラインとsecure NPUを利用) — 計算器の高速化だけでは残るメモリ確保・ロード・資源競合の費用をFlexServeがさらに削減する。

- 背景メモリ圧力下の先頭トークン遅延 / 平均1.87倍、最大3.05倍高速 (比較対象: Strawman-OPT; 条件: background メモリ load 0〜10GB) — 通常メモリが断片化するほどCMAを使わないFlex-Memの効果が大きくなる。

- マルチモデル先頭トークン遅延 / Strawman比平均8.84倍、Strawman-OPT比最大2.53倍高速 (比較対象: 二つのTrustZone構成; 条件: 4GBキャッシュ、複数モデル群) — モデル/KVの動的キャッシュとワークフロー先読みがモデル切替のロード遅延を削減する。

- エージェントワークフロー応答遅延 / 最大24.30倍/4.05倍、平均14.15倍/2.94倍高速 (比較対象: Strawman / Strawman-OPT; 条件: 10 mobile agent workflows) — 複数モデルを連鎖的に呼ぶ処理では、次モデル重みとKVの先読みがコールドスタートを繰り返し回避する。

- 通常世界アプリ性能 / 非推論比較対象の97.2% (比較対象: LLM推論なし; 条件: 協調メモリ管理下の通常アプリ群) — セキュアLLMキャッシュを固定占有せず必要量をOSへ返すため、通常アプリとの共存性を高く保てる。

- FlexServeと非保護NW-Baseのデコード処理率差 / 0.57〜6.29%低下、平均3.01% (比較対象: normal-world NPU inference; 条件: 重み常駐、NPU/パイプライン使用) — 定常デコード時のセキュリティ隔離そのものの処理率費用は比較的小さい。

### 負の結果・境界条件
- NanoPC-T6にはインラインストレージ暗号化・復号ハードウェアがないため、論文が示す平均16.06%の追加先頭トークン遅延削減は実機測定ではなくエミュレーションである。通常世界のクライアントアプリが要求を送る場合、侵害されたカーネルはそのクライアントの入力・出力を観測または改変でき、端から端の保護にはセキュア世界クライアントが必要になる。サイドチャネル、物理攻撃、サービス拒否も範囲外である。またデコードが長いワークフローではコールドスタート最適化が全処理に占める割合が小さくなり、最大値ほど大きな全体高速化は得られない。

### 結果の読み方
結果は、端末内セキュアLLMの主な性能問題が暗号処理やTEE境界そのものだけでなく、固定セキュア領域と通常OSの間で資源を融通できない管理方式にあることを示す。モデル重みやKVのようなGB級状態は再利用価値が高い一方、通常アプリも同じDRAM/NPUを必要とするため、固定予約と毎回破棄のどちらも非効率である。FlexServeはアクセス権だけを厳しく隔離し、量の決定を通常OS、具体的なページ選択をLLMランタイムへ分担することで、セキュリティ境界を維持したまま既存OSの資源圧力制御を利用する。
## 品質への影響
FlexServeは推論品質を近似して速度を得る方式ではなく、同一モデルのセキュア実行経路と資源管理を改善する。評価モデルはNPUに合わせてINT8量子化されるが、Flex-Mem、Flex-NPU、キャッシュ、回収、先読み自体は生成品質を追加で変化させない。
## 既存研究との差
既存のTrustZone向けLLM推論研究がモデルをセキュア世界で実行することやセキュア計算そのものを中心に扱うのに対し、FlexServeはGB級DRAMとNPUを通常/セキュアワークロード間で動的に貸し借りするOS・実行時系の問題を主対象にする。固定セキュアパーティションとは異なり、通常OSが確保した任意ページをS2PT/SMMUで保護へ切り替え、内容アクセスを禁止したままOSに割当・回収量の決定を残す。一般的な端末内LLMサービングが量子化、モデルロード、NPUスケジューリングを最適化するのに対し、本方式は侵害されたカーネルを脅威モデルに含め、モデル/KVキャッシュ、SSD書戻し、先読み、メモリ回収をセキュリティ境界の切替と一体で設計する。
## 限界
評価はNanoPC-T6一機種と6 TOPS NPUを中心としており、商用モバイルSoCごとに異なるTrustZone、SMMU、NPUドライバ、メモリ帯域へ性能値をそのまま一般化できない。ベンダーNPUランタイムが非公開のためコミュニティのリバースエンジニアリング実装を使っており、商用ドライバ最適化を完全には反映しない。試験機にインラインストレージ暗号がなく、その効果はエミュレーションである。脅威モデルはカーネル侵害を含むが、通常世界クライアントの入出力、サイドチャネル、物理攻撃、サービス拒否は範囲外である。モデル/KVキャッシュを保持するほど起動遅延は改善する一方、通常アプリへ返せるメモリは減るため、動的キャッシュ方針にはワークロード依存の交換条件が残る。
## 実装状態
NanoPC-T6上に実機試作がある。Flex-Monitorは約4.5K LoC、FlexServe FrameworkはC/C++の信頼アプリケーションとして約8.3K LoCで、Llama3/Qwen3系列、Flex-Mem、Flex-NPU、層単位パイプライン、モデル/KVキャッシュ、協調回収を実装する。2026-09-14時点で論文本文からFlexServe本体の著者公式公開リポジトリURLは確認できない。
## 研究上の位置づけ
端末内LLM実行基盤のうち、信頼実行環境（Trusted Execution Environment; TEE）のセキュリティとメモリ/NPUオーケストレーションを同時に扱うOS・実行時系研究である。階層メモリの観点では、モデル重みとKVをDRAMとSSDの間で動かす際に、単なる容量・I/O最適化だけでなく、どのセキュリティ領域がページを管理し、いつアクセス権を切り替えるかが先頭トークン遅延と通常アプリ性能を左右することを示す。LLM認識型回収とワークフロー認識先読みは、複数モデルを同じNPUとDRAM上へ安全に多重化する将来の端末内エージェント実行基盤へ直接つながる。
