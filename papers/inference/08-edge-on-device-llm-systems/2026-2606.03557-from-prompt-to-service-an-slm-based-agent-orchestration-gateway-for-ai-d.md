# From Prompt to Service：小規模言語モデルによるエージェントサービス振り分け

## 概要

生成AIを使う対話型の仮想空間では、一つのユーザー入力が会話、翻訳、知識検索、専門的な解説、3D素材生成など異なる処理を要求しうる。すべての機能を仮想空間のクライアントへ直接組み込むと、サービスを追加するたびに接続先・認証・要求形式・応答形式を更新しなければならない。大きな言語モデル一つですべての入力を処理する設計は、簡単なサービス振り分けにも大きな推論費用と遅延を要する。

本論文は、小規模言語モデル（Small Language Model: SLM）をエッジ端末で動かし、自然言語入力を異なるバックエンドへ振り分けるエージェント統合ゲートウェイ（Agent Orchestration Gateway）を設計する。サービス一覧から動的に作る指示文で意図を分類し、返却された構造化された経路指定を検証してから対象サービスを呼び出す。ゲートウェイは単一のREST窓口を提供し、クライアントをバックエンドの配置や種類から切り離す。

著者はキプロスの文化財を題材にしたInterwovenXR仮想博物館で実装し、Jetson Orin NX 8GBを用いて複数の小型モデルを比較した。単独の未調整Qwen2.5-0.5Bはルーティング正答率24.8%だったが、タスク特化の教師あり調整を施すと83.0%になり、平均ルーティング遅延は329.3ミリ秒から392.0ミリ秒へ増えた。さらに、0.5Bルータと1.5B会話モデルを同一端末へ配置すると、100件の会話要求で平均端末間応答時間1454.18ミリ秒を報告した。**これらは特定の5分類・仮想博物館の評価値であり、汎用モデル選択の正答率や高負荷時の保証値ではない。**

## 問題設定

従来の仮想空間アプリケーションは、対話モデル、翻訳サービス、検索基盤、画像・3D生成基盤をそれぞれ直接呼び出すことがある。この構成では、サービスを置き換えるとクライアント側も変更が必要となり、エッジとクラウドをまたぐ計算資源の移動に追従しにくい。単一の大きなLLMをサービス選択と会話生成の両方に用いると、サービス選択だけで済む要求にも大きな推論モデルを毎回起動することになる。入力に応じて処理先を変えること自体は従来から可能だが、著者が重視するのは**小型のモデルによる意味的な意図認識、サービスレジストリによる検証、異種バックエンドの共通呼び出し、実エッジ端末上の応答性能**を一つの構成として評価することである。

対象は仮想博物館内の来訪者と案内役エージェントの対話である。来訪者は同じ会話窓から挨拶、翻訳、教会の歴史、モザイクの専門的解釈、3D素材生成などを要求する。表面上似た「文化財の説明」と「特定のモザイクの専門解説」を正しく区別する必要がある。これは単純なキーワード判定では難しいが、ルータの推論が遅すぎると対話体験が悪化する。

## 手法

### 1. 単一窓口とサービスレジストリ

実装はPythonのFastAPIを用いるゲートウェイで、仮想空間クライアントは自然言語の質問をJSONとして一つのREST窓口へ送信する。ゲートウェイはサービスレジストリから、現在有効なサービスの名前、種類、説明、接続先を取得する。その情報から意図分類器へ与える経路選択用の指示文を生成する。分類器は選択経路、意図ラベル、信頼度、整形した問い合わせを含む構造化JSONを返す。ゲートウェイは、経路が実際に登録・有効化されているかを検証し、正しい場合にだけ対応するサービスを呼び出す。無効な経路の場合には代替経路を使うか、ユーザーへ確認を求める設計である。

バックエンドにはOpenAI互換の会話サービス、通常のHTTPサービス、JSON入出力サービス、検索拡張生成（Retrieval-Augmented Generation: RAG）、3D生成などを想定する。返却された結果はゲートウェイ側で共通のJSON構造へ正規化される。クライアントは内部のモデル名や配置先を知る必要がなく、サービス追加・移転をゲートウェイ側の設定で吸収できる。

論文の試験環境はInterwovenXRの仮想博物館で、Jetson Orin NX 8GB上に意図分類機能を置き、文化財知識検索、専門モデル、3D生成などのサービスを接続する。ルータの仕事は文章全体の生成ではなく、入力の意味を5分類へ落とすことに限定される。**処理先の振り分けが正しくても、呼び出された専門モデルの回答品質が正しいとは限らない**ため、ルータ精度とサービス出力品質を分離して評価する必要がある。

### 2. 五つの経路と構造化出力

著者が評価する経路は、(1) 挨拶や一般的な案内を処理する会話、(2) 翻訳などの言語適応、(3) 教会のモザイクを専門的に解釈する専門家、(4) 教会の歴史や建築に関する知識検索、(5) 3Dモデル生成である。意図分類器は、これらの経路を返すだけでなく、ゲートウェイが処理できるJSONを安定して出力しなければならない。誤った経路だけでなく、構文不正・未知の経路を返すことも運用上の失敗として計測する。

五分類のうち専門家経路と知識検索経路は、どちらも同じ文化財についての質問を含み、意味的に近い。たとえば「教会の歴史」は知識検索、「モザイクの保存状態と意義」は専門家という区別が必要になる。著者はこの曖昧さを意図的に含む評価入力を作成した。したがって、単にモデルがJSONを返せるかだけでなく、似たサービス間を分けられるかが重要になる。

### 3. 小型ルータの教師あり調整

ルータ候補にはQwen2.5-1.5B、SmolLM2-1.7B、およびそれぞれの小型版Qwen2.5-0.5B、SmolLM2-360Mなどを用いる。モデルは4ビット量子化（Q4）を基本とする。小型版の未調整モデルはJSON形式やサービス意味の理解が不安定だったため、著者は5分類それぞれ1000件、合計5000件の教師ありルーティング例を用いて微調整した。各学習例はシステム指示、ユーザー入力、正解のJSON経路指定を含む。

学習は4ビット量子化低ランク適応（QLoRA）を用い、WindowsのRTX 4060搭載機で行った。論文に記載された条件は、デバイス当たりバッチ1、勾配蓄積8、3エポック、計1689最適化ステップである。SmolLM2-360M-FTの検証損失は0.0775、Qwen2.5-0.5B-FTは0.0724で、平均トークン正解率はそれぞれ0.9740と0.9745だった。ただし、このトークン正解率は経路選択の正答率とは別の学習時指標であり、運用上のルーティング精度を表さない。

### 4. ルータと会話モデルの二層配置

本論文の二層構成では、最初の意図判定を微調整済みの10億パラメータ未満のモデルが担当する。会話経路が選ばれた場合に限り、別の1.5Bまたは1.7B級モデルがローカルで回答を生成する。その他の経路では登録された専門サービスへ要求を転送する。両モデルはJetson Orin NX上のllama.cppサーバで同時に動作し、モデル読込み時約5GB、推論中最大約7.4GBのRAM使用量が報告された。

二層化の意図は、最初のサービス選択に高価な会話生成モデルを使わず、意味分類のための小型モデルで高速に経路を決めることにある。会話が必要な場合は別の大きめの小型モデルを起動するため、会話品質を担保しつつ振り分けを短時間で済ませられる。もっとも、ルータが誤ると適切なサービスに到達できない。最も小さいルータが最も良いとは限らず、正答率と遅延を同時に評価する必要がある。

## 評価

### 評価方法と環境

評価は二段階で行われた。第1段階は500件（五分類各100件）の入力を使い、ルータのみの経路正答率、無効出力率、平均遅延を測定する。下流の検索や3D生成は呼び出さないため、ここでの遅延はエンドツーエンドの応答時間ではない。第2段階は会話経路に属する100件の入力を仮想空間から送信し、クライアント→ゲートウェイ→ルータ→ローカル会話モデル→クライアントの実経過時間を測定する。評価端末はJetson Orin NX 8GB、会話生成はllama.cppで実行した。

ルータ候補の性能が低い理由が、そもそも五分類の区別不能性にあるのか、モデル容量不足にあるのかを分けるため、Qwen2.5-14Bを参照モデルとして使う。参照モデルは500件中489件を正しく分類し、正答率97.80%、無効出力0%、平均ルーティング遅延5684.1ミリ秒であった。これは分類体系の区別可能性を確かめる参照点であり、Jetson上のルータ候補として評価したわけではない。

### 第1段階：経路選択の正答率と遅延

以下は原著Table Iから転記した主要値である。平均遅延は**ルータのみ**の値であり、下流サービスの処理時間は含まない。

| モデル | 正答件数/500 | 正答率 | 平均ルーティング遅延 | 無効出力率 |
|---|---:|---:|---:|---:|
| Qwen2.5-0.5B | 124 | 24.80% | 329.3 ms | 0.00% |
| Qwen2.5-0.5B-FT | 415 | 83.00% | 392.0 ms | 3.20% |
| Qwen2.5-1.5B | 473 | 94.60% | 1776.9 ms | 0.00% |
| SmolLM2-360M | 84 | 16.80% | 533.5 ms | 9.00% |
| SmolLM2-360M-FT | 246 | 49.20% | 560.3 ms | 22.60% |
| SmolLM2-1.7B | 427 | 85.40% | 1314.9 ms | 0.80% |
| Qwen2.5-14B（参照） | 489 | 97.80% | 5684.1 ms | 0.00% |

Qwen2.5-0.5Bの教師あり調整による改善は24.8%から83.0%への**+58.2パーセントポイント**である。「58.2%の相対改善」と解釈してはいけない。ルーティング遅延は329.3→392.0ミリ秒（+62.7ミリ秒、約19.0%増）となるが、1.5Bモデルの1776.9ミリ秒より短い。微調整済み0.5Bモデルの全体正答率は高くなった一方、モザイク専門家経路の正答率は49.0%にとどまる。全体平均83%という値だけで、意味的に近い専門サービスを安定して選択できると判断してはならない。

SmolLM2-360Mも調整により16.8%→49.2%へ改善したが、無効出力が22.6%と高く、知識検索経路の正答率は0%である。より小さく速いモデルを使えば運用上も優位になるという単純な結論は成立しない。Qwen2.5-1.5Bは94.6%と高精度で無効出力がなかったが、平均遅延1776.9ミリ秒とルーティングだけで時間を消費した。したがって、著者は正答率と遅延の交換条件を考慮し、0.5B-FTを二層構成の有力なルータと位置付ける。

### 第2段階：二層構成の会話応答時間

原著Table IIは100件の会話入力について、ルータと会話モデルを同じ端末で実行したときの応答時間を示す。

| ルータ | 会話モデル | 平均 | 中央値 | P95 | P99 |
|---|---|---:|---:|---:|---:|
| Qwen2.5-0.5B-FT | Qwen2.5-1.5B | 1454.18 ms | 1415.93 ms | 1995.68 ms | 2640.59 ms |
| Qwen2.5-0.5B-FT | SmolLM2-1.7B | 1518.63 ms | 1358.18 ms | 2174.89 ms | 2644.32 ms |
| SmolLM2-360M-FT | Qwen2.5-1.5B | 1306.06 ms | 1247.34 ms | 2116.62 ms | 2312.07 ms |
| SmolLM2-360M-FT | SmolLM2-1.7B | 1339.26 ms | 1265.26 ms | 2071.19 ms | 2646.67 ms |

全4構成の平均は1.6秒未満、中央値は1.5秒未満だった。著者は対話型利用における2秒程度の目安と比較して、エッジ配置の実用可能性を主張する。ただし**平均が2秒未満でもP95やP99は2秒を超える**。例えばQwen2.5-0.5B-FTとQwen2.5-1.5Bの組合せはP95が約1.996秒、P99は約2.641秒であり、尾部遅延が無視できない。

SmolLM2-360M-FTを使う組合せの方が平均応答時間は短いが、第1段階のルーティング正答率が49.2%しかなく、22.6%が無効出力だった。したがって最短の平均応答時間だけを根拠に選ぶと、誤ったサービスへ転送する危険が増す。著者は、正答率83.0%のQwen2.5-0.5B-FTとQwen2.5-1.5Bの組合せを、精度と遅延の均衡がよい構成として評価した。

### 結果の解釈で注意すべき点

第1段階の500件は著者が作成した単一仮想博物館向けの制御された入力であり、未知のドメインにおける一般化性能を測る外部ベンチマークではない。第2段階は会話経路100件のみであり、遠隔RAG、翻訳、3D生成などを含むすべてのサービス経路の端末間遅延を測ったわけではない。モデルの出力文そのものの品質を人間が評価した試験でもない。ネットワーク混雑、複数ユーザーの同時要求、長い文脈、障害時の代替経路などを網羅した実運用試験も報告されていない。

## 既存研究との差

一般的な意図分類器は入力をラベルへ割り当てることを主目的とする。これに対して本論文は、登録済みサービスの情報を動的にルータの指示文へ反映し、JSON経路の妥当性を検証し、異種バックエンドの呼び出し結果を共通形式でクライアントへ返す**運用時の統合基盤**を実装する。すべてを一つのLLMに担当させる構成と比べ、分類専用の小型モデルと生成専用の別モデルを同じエッジ端末に置く二層化を実証した点が実装上の貢献である。

他方、GPU上の注意演算やKVキャッシュを最適化する推論カーネルの研究ではない。推論基盤サーベイにおいては、**小型モデルによるサービス選択・異種モデルのルーティング・エッジでの実行分担**に分類するのが適切である。評価した速度はリクエストのルーティングと会話の端末間時間であり、言語モデルのトークン生成速度の改善ではない。

## 限界・実装状況

著者が明記する制約は、単一博物館・500件の制御された経路選択入力・単一エッジ端末・制御されたネットワーク環境に評価が限られること、専門家や利用者による応答品質の評価がないこと、ルータの調整が特定の5分類に依存するためサービス定義変更時に再調整が必要になることである。実験では同時要求が多い状況での尾部遅延や、未知の入力に対する安全な代替経路の品質を十分に検証していない。

特に、Qwen2.5-0.5B-FTの83.0%はサービス選択を誤る入力が85/500件残ることを意味する。3.2%の無効出力を検出できるとしても、**構文上有効だが意味的に誤った経路**はレジストリ検証だけでは防げない。信頼度閾値、確認質問、複数モデルによる再判定などは今後の設計課題となる。また、公開コードの再現可能な配布先は一次資料から確認できなかったため、論文の記述だけで実装手順が完全に再現できるとは判断しない。
