# MawForge: Memory-Bounded Expert Materialization for Local Mixture-of-Experts Inference

> MawForgeは、ローカルMoEを「full modelがRAMへ入るか」で判定するのではなく、**共通weightだけを常駐させ、routingされたexpertだけdiskから上限付きcacheへ実体化（materialize）する**方式である。最も重要な結果は、expert cacheを大きくすれば速くなるとは限らないことで、unified-memory machineではhit率向上よりmemory pressure悪化の方が大きくなり得る。

## 概要

疎な混合エキスパート（Mixture-of-Experts; MoE）modelは、総parameter数が非常に大きくても1 tokenが使うexpertは一部だけである。

例えば35B total parameterのMoEでも、1 tokenで実際に計算するactive parameterは3B程度という構成がある。

このため「計算量だけ見れば小型modelに近いのでconsumer machineでも動かせそう」に見える。

しかし一般的なlocal runtimeでは、推論開始時にfull GGUF modelをmmap / loadし、

- 全model weight
- KV cache
- runtime buffer
- Metal / GPU allocation
- filesystem cache
- macOS / display / 他process

が同じunified memoryを奪い合う。

つまり**sparse computationが自動的にsparse residencyになるわけではない**。

1 tokenが2 expertしか使わなくても、64 expert全部をmemoryへ常駐させれば容量問題はdense modelとあまり変わらない。

MawForgeはここを変える。

full modelをdisk上のdurable storageとして扱い、

- attention / embedding / normなど全tokenが使う**共通tensor**は常駐
- MoE expert weightはlayer × expert単位へ分離してdisk保持
- routerが実際に要求したexpertだけをbounded cacheへload

する。

狙いは「cache hit率を最大化して最速にする」ことではない。

**指定したmemory budgetを絶対条件にし、その範囲内でどのexpert-cache容量が最も速いか測れるexecution substrateを作る**ことが目的である。

## 問題設定

### 1. Unified memoryではGPU cacheだけを考えられない

discrete GPUではGPU VRAMとCPU RAMを別容量として考えやすい。

Apple SiliconではCPUとGPUが同じ物理memory poolを共有する。

そのためexpert cacheを2GB増やすと、単に「GPU cacheが2GB増えた」のではなく、

- OS headroom
- KV cache
- process heap
- Metal allocation
- file cache

へ使える余裕も2GB近く減る。

memory pressureが高くなると、

- memory compression
- paging / swap
- file cache eviction
- effective bandwidth低下

などが起き、expert missを減らした以上にsystem全体が遅くなることがある。

MawForgeはこのため、**expert cache hit率をobjectiveにしない**。

### 2. Context lengthがexpert cacheの余白を食う

KV cacheはcontext lengthに応じて増える。

同じmodel・同じexpert cacheでも、4K contextでは安全だった構成が32Kではbudgetを超える可能性がある。

したがってcache sizingは、

`model weightだけ` ではなく

`resident common + expert cache + KV cache + runtime headroom`

として扱う必要がある。

### 3. Quantizationも単なるmodel-size決定ではない

Q8とQ4ではdisk size / resident expert sizeが変わる。

expert 1個をcacheへ置くcostが変われば、同じcache percentageでも絶対byte数とmemory pressureが変わる。

そのため最適cache比率も変わる。

MawForgeの評価では、同じQwen3.6 35B A3B familyでもQ8とQ4でcache optimumが異なる。

## 手法のあらまし

MawForgeの実行は大きく、

1. **split pack作成**
2. **static planning**
3. **bounded serving**
4. **route-aware measurement**

に分かれる。

### 1. Full GGUFをcommon tensorとexpert payloadへ分離する

通常GGUFではmodel tensorが1つの大きなfile体系にまとまっている。

MawForgeはこれを、

- 常に必要な共通tensor
- `layer L / expert E`に対応するexpert tensor

へ分離した**split pack**へ変換する。

これによりruntimeはfull GGUFをmemoryへmapする必要がなく、必要expertのpayloadだけdiskから読める。

### 2. Memory budgetから実行可能性をload前に判定する

ユーザーは例えば18GiBというserving budgetを指定する。

static plannerは少なくとも、

- `C`: resident common tensor bytes
- `E(p)`: cache比率`p`で確保するexpert-cache bytes
- `K(n)`: context長`n`に必要なKV-cache bytes

を見積もる。

下限は概念的に、

`L(p,n) = C + E(p) + K(n)`

である。

この時点ですでにbudgetを超える構成は、**試してswap地獄へ入る前に拒否する**。

これはbenchmark上も重要で、「起動して遅かった」と「そもそもbudget制約下で不可能」を分離できる。

### 3. Routerが要求したexpertだけをexecution cacheへmaterializeする

推論中、MoE routerがexpert IDを選ぶ。

そのexpertがexecution cacheにあればそのまま使う。

無ければsplit packから対応expert payloadをdisk / file pathから読み、cache slotへmaterializeする。

つまりlogical modelには全expertが存在するが、物理memoryには**現在のworking setだけ**を置く。

static expert pruningとは異なり、cacheにないexpertも必要になれば後から正しくloadできる。

### 4. Cache容量をhard boundする

expert cacheは「空いているmemoryを全部使う」方式ではない。

plannerが許可した上限内だけslotを用意する。

cache missが増えてもbudgetは超えない。

このためMawForgeは、speed-maximizing cacheというより**bounded execution cache**として位置付けられる。

## Cacheを増やすと何が起こるか

直感的にはcacheを増やすほど、

- hit rate↑
- disk materialization↓
- latency↓

になりそうに見える。

MawForgeの実測では最初の2つは概ね成立するが、3つ目が成立しない。

理由はunified memory pressureである。

cache resident footprintが増えすぎると、OS / Metal / file subsystemを含むmachine全体が悪いmemory operating regimeへ入る。

そのため最終latencyは概念的に、

`expert materialization時間 + compute時間 + memory-pressure penalty`

で決まり、最後の項が急増するとhit率改善を打ち消す。

## 評価

### まず見るところ

- **Machine:** MacBook Pro M5 Pro、24GB unified memory。
- **Serving budget:** 18GiB。
- **Matrix:** 3 model profile × 5 cache setting × 2 context × 4 prompt class × 5 repetition = 600 rows。
- **Static planning:** 30 unique構成中27 feasible、3 rejected。
- **Execution:** feasible 540 generation rowは全て96-token completionを返し、memory guard 0回。
- **最重要結果:** cache hit率最大点 ≠ throughput最大点。
- **Qwen Q8:** 4K/32Kとも15% cacheが全prompt classでbest。
- **Gemma Q8:** feasible範囲では35%がbest。35→65%でhit率は上がるのにdecodeが約13.86→1.30 tok/sへ崩れる。

### Qwen Q8

Qwen Q8では4K / 32K、全4 prompt classで**最小の15% cacheが最速**だった。

例えば32K codeで45% cacheはhit率89.90%、materialized I/O 33.00GiBまで改善する一方、decodeは1.56 tok/s。15% cacheでは約12.12 tok/sを出す。

つまり同modelではcacheを増やしてroute localityをより多く保持するより、resident footprintを小さくしてsystem pressureを避ける方が圧倒的に有利だった。

### Qwen Q4

Q4ではoptimumがprompt/contextで変わる。

4Kでは、

- long-form: 15%
- code: 25%
- reasoning: 25%
- summarization: 35%平均が高いが25%が安定

32Kでは35%が広いdefaultになり、reasoningは25%がbest。

同じmodel topologyでもquantizationによってexpert byte数が変わると、optimal cache pointが変わる。

### 32K context

Gemma Q8のKV cacheは、4Kで約0.859GiB、32Kでは約6.875GiB。

そのため50/65% expert cacheが32Kではstatic rejectionになる。

ただしbest feasible pointは4Kと同じ35%だった。

contextが伸びたから「必ずexpert cacheを小さくすべき」と単純化できず、model topology・quantization・route localityとの相互作用を見る必要がある。

## Speculative decoding addendum

論文はGemma Q8でmulti-token prediction系のspeculationも小規模に試している。

25% expert cache、horizon 4、acceptance threshold 0.5のfocused runでは、7 draft token中4 token、57.1%をacceptした。

dense modelだけを見ると「半分以上acceptなら速くなりそう」に見える。

しかし結果は、

- non-speculative exploratory baseline: **9.52 tok/s**
- speculative: **8.31 tok/s**

と遅くなった。

さらにmaterialized expert bytesは、

- 48.06 GiB
- → 116.66 GiB

へ増えた。

理由として重要なのが**route churn**である。

speculative verificationでは複数future tokenを同時にtargetへ通すため、単一token decodeより多種類のexpertへroutingされ得る。

受理tokenで節約したtarget stepより、追加expert materializationの方が高ければ速度は下がる。

このaddendumは600-row main matrixほど強いfactorial evaluationではないが、**MoE speculative decodingではacceptance rateだけを性能指標にできない**ことを示す診断結果として重要である。

## Direct full-GGUF loadとの比較

Gemma Q8、32K contextで通常のfull-GGUF Metal loadもguard付きで試している。

system-used memoryが99.19%へ達し、98% safety guardを超えたためroute output前に停止した。

これは「llama.cppでは絶対動かない」という主張ではない。

示しているのは、**この24GB machine、このmodel/context、このdirect full-residency pathでは安全な運用が困難だった**という狭いfeasibility resultである。

MawForgeは同じmachineで、static plannerがfeasibleと判定したGemma Q8 32K cellを18GiB target内で完走させた。

## 既存研究との差

### MoE-Infinity / ProMoE等との違い

多くのexpert-offload研究は、cache hit率、prefetch accuracy、transfer overlapを改善して速度を上げる。

MawForgeはそれらより前段の、**local machineがmemory pressureで壊れないbounded operating envelope**を主題にする。

cache hit率が上がってもthroughputが下がる実測を中心に据える点が特徴的である。

### FluxMoEとの違い

FluxMoEはdatacenter GPU servingでexpert residencyを動的に減らし、その分をKV cacheへ配る。

MawForgeもexpert residencyとKV capacityを同じbudget問題として見るが、full modelのbacking tierをdiskへ置き、Apple Silicon unified memory上で「明示的budgetを超えないlocal execution」を優先する。

### Static pruningとの違い

expertを削除してmodelを小さくするのではない。

全expertはdiskに残り、routerが要求すればloadできるため、main non-speculative pathはnative routingを維持する。

## 限界

- 主評価は単一MacBook Pro M5 Pro 24GBで、server GPU / Linux / discrete VRAMへそのまま一般化できない。
- 96-token completion固定なので、数千tokenの長期generation中にcache working setがどう変化するかは主matrixから分からない。
- 600 rowsといってもmodel profileは3種類であり、MoE architecture全般を網羅しない。
- Disk / filesystem / macOS cache behaviorに性能が依存する。
- cache percentageはmodelごとに同じ絶対byte量ではないため、割合だけで他modelへ移植できない。
- direct full-GGUF baselineはfeasibility addendumであり、公平な同条件throughput baselineではない。
- speculative decoding結果はfocused addendumで、main factorial studyほど網羅的ではない。
- cache hit率・materialized bytesだけでoptimal pointを予測できず、machineごとのmeasurementが必要。

## 一般的な実装上の含意

MawForgeの価値は「diskからexpertを読む」という機構そのものより、**memory budgetをfirst-class constraintにしたこと**にある。

local MoE runtimeでは、

1. full modelが入るかではなく常駐必須tensorが何byteか
2. context長からKV reserveをいくら取るか
3. OS / runtimeへどれだけheadroomを残すか
4. 残りをexpert cacheへ何byte渡すか
5. hit率ではなくend-to-end latencyがどこで最小になるか

を順に決める方が安全である。

特にunified memoryでは「空きRAMをcacheで埋める」は危険なpolicyになり得る。

またMoEでspeculative decodingを導入する場合、accepted token数だけでなく、

- unique expert数
- materialized expert bytes
- cache churn
- verification中のroute diversity

も同時に測る必要がある。
