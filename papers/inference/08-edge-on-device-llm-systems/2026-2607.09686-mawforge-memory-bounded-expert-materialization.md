# MawForge: Memory-Bounded Expert Materialization for Local Mixture-of-Experts Inference

> MawForgeは、ローカルMoEを「完全な モデルがRAMへ入るか」で判定するのではなく、**共通重みだけを常駐させ、ルーティングされたエキスパートだけディスクから上限付きキャッシュへ実体化（実体化）する**方式である。最も重要な結果は、エキスパート キャッシュを大きくすれば速くなるとは限らないことで、共有-メモリ マシンではヒット率向上よりメモリ 圧力悪化の方が大きくなり得る。

## 概要

疎な混合エキスパート（Mixture-of-エキスパート; MoE）モデルは、総パラメータ数が非常に大きくても1 トークンが使うエキスパートは一部だけである。

例えば35B 総 パラメータのMoEでも、1 トークンで実際に計算する実行対象 パラメータは3B程度という構成がある。

このため「計算量だけ見れば小型モデルに近いので個人向け マシンでも動かせそう」に見える。

しかし一般的なローカル ランタイムでは、推論開始時に完全な GGUF モデルをmmap / 読み込みし、

- 全モデル 重み
- KV キャッシュ
- ランタイム バッファ
- Metal / GPU allocation
- ファイルシステム キャッシュ
- macOS / display / 他プロセス

が同じ共有 メモリを奪い合う。

つまり**疎 計算が自動的に疎 常駐になるわけではない**。

1 トークンが2 エキスパートしか使わなくても、64 エキスパート全部をメモリへ常駐させれば容量問題は密 モデルとあまり変わらない。

MawForgeはここを変える。

完全な モデルをディスク上の永続 保存として扱い、

- 注意機構 / embedding / normなど全トークンが使う**共通テンソル**は常駐
- MoE エキスパート 重みは層 × エキスパート単位へ分離してディスク保持
- ルータが実際に要求したエキスパートだけを上限付き キャッシュへ読み込み

する。

狙いは「キャッシュ ヒット率を最大化して最速にする」ことではない。

**指定したメモリ 予算を絶対条件にし、その範囲内でどのエキスパート-キャッシュ容量が最も速いか測れる実行 基盤を作る**ことが目的である。

## 問題設定

### 1. Unified memoryではGPU cacheだけを考えられない

独立 GPUではGPU VRAMとCPU RAMを別容量として考えやすい。

Apple SiliconではCPUとGPUが同じ物理メモリ 共有領域を共有する。

そのためエキスパート キャッシュを2GB増やすと、単に「GPU キャッシュが2GB増えた」のではなく、

- OS 余裕
- KV キャッシュ
- プロセス heap
- Metal allocation
- ファイル キャッシュ

へ使える余裕も2GB近く減る。

メモリ 圧力が高くなると、

- メモリ 圧縮
- ページング / スワップ
- ファイル キャッシュ 追い出し
- 実効 帯域低下

などが起き、エキスパート 未検出を減らした以上にシステム全体が遅くなることがある。

MawForgeはこのため、**エキスパート キャッシュ ヒット率を目的にしない**。

### 2. Context lengthがexpert cacheの余白を食う

KV キャッシュは文脈 lengthに応じて増える。

同じモデル・同じエキスパート キャッシュでも、4K 文脈では安全だった構成が32Kでは予算を超える可能性がある。

したがってキャッシュ sizingは、

`model weightだけ` ではなく

`resident common + expert cache + KV cache + runtime headroom`

として扱う必要がある。

### 3. Quantizationも単なるmodel-size決定ではない

Q8とQ4ではディスク 大きさ / 常駐 エキスパート 大きさが変わる。

エキスパート 1個をキャッシュへ置く費用が変われば、同じキャッシュ 割合でも絶対バイト数とメモリ 圧力が変わる。

そのため最適キャッシュ比率も変わる。

MawForgeの評価では、同じQwen3.6 35B A3B 系列でもQ8とQ4でキャッシュ 最適点が異なる。

## 手法のあらまし

MawForgeの実行は大きく、

1. **分割 パック作成**
2. **静的 計画**
3. **上限付き 提供**
4. **経路-aware 測定**

に分かれる。

### 1. Full GGUFをcommon tensorとexpert payloadへ分離する

通常GGUFではモデル テンソルが1つの大きなファイル体系にまとまっている。

MawForgeはこれを、

- 常に必要な共通テンソル
- `layer L / expert E`に対応するエキスパート テンソル

へ分離した**分割 パック**へ変換する。

これによりランタイムは完全な GGUFをメモリへmapする必要がなく、必要エキスパートのデータだけディスクから読める。

### 2. Memory budgetから実行可能性をload前に判定する

ユーザーは例えば18GiBという提供 予算を指定する。

静的 plannerは少なくとも、

- `C`: 常駐 共通 テンソル バイト
- `E(p)`: キャッシュ比率`p`で確保するエキスパート-キャッシュ バイト
- `K(n)`: 文脈長`n`に必要なKV-キャッシュ バイト

を見積もる。

下限は概念的に、

`L(p,n) = C + E(p) + K(n)`

である。

この時点ですでに予算を超える構成は、**試してスワップ地獄へ入る前に拒否する**。

これはベンチマーク上も重要で、「起動して遅かった」と「そもそも予算制約下で不可能」を分離できる。

### 3. Routerが要求したexpertだけをexecution cacheへmaterializeする

推論中、MoE ルータがエキスパート IDを選ぶ。

そのエキスパートが実行 キャッシュにあればそのまま使う。

無ければ分割 パックから対応エキスパート データをディスク / ファイル pathから読み、キャッシュ slotへ実体化する。

つまり論理 モデルには全エキスパートが存在するが、物理メモリには**現在の作業 集合だけ**を置く。

静的 エキスパート 枝刈りとは異なり、キャッシュにないエキスパートも必要になれば後から正しく読み込みできる。

### 4. Cache容量をhard boundする

エキスパート キャッシュは「空いているメモリを全部使う」方式ではない。

plannerが許可した上限内だけslotを用意する。

キャッシュ 未検出が増えても予算は超えない。

このためMawForgeは、速度-最大化 キャッシュというより**上限付き 実行 キャッシュ**として位置付けられる。

## Cacheを増やすと何が起こるか

直感的にはキャッシュを増やすほど、

- ヒット 率↑
- ディスク materialization↓
- 遅延↓

になりそうに見える。

MawForgeの実測では最初の2つは概ね成立するが、3つ目が成立しない。

理由は共有 メモリ 圧力である。

キャッシュ 常駐 footprintが増えすぎると、OS / Metal / ファイル subsystemを含むマシン全体が悪いメモリ operating regimeへ入る。

そのため最終遅延は概念的に、

`expert materialization時間 + compute時間 + memory-pressure penalty`

で決まり、最後の項が急増するとヒット率改善を打ち消す。

## 評価

### まず見るところ

- **マシン:** MacBook Pro M5 Pro、24GB 共有 メモリ。
- **提供 予算:** 18GiB。
- **Matrix:** 3 モデル profile × 5 キャッシュ setting × 2 文脈 × 4 入力 分類 × 5 repetition = 600 行。
- **静的 計画:** 30 固有構成中27 実行可能、3 拒否。
- **実行:** 実行可能 540 生成 行は全て96-トークン completionを返し、メモリ 保護条件 0回。
- **最重要結果:** キャッシュ ヒット率最大点 ≠ スループット最大点。
- **Qwen Q8:** 4K/32Kとも15% キャッシュが全入力 分類でbest。
- **Gemma Q8:** 実行可能範囲では35%がbest。35→65%でヒット率は上がるのにデコードが約13.86→1.30 tok/sへ崩れる。

32Kで次の3 条件は読み込み前にrejectされた。

| モデル | キャッシュ | 静的 minimum |

18GiB 予算を超えるため、これらを「遅いベンチマーク 結果」として実行しない。

### Gemma Q8: hit率とthroughputが逆転する代表例

4K 文脈平均。

| キャッシュ | デコード | TTFT | ヒット 率 | 実体化された I/O |
|---|---:|---:|---:|---:|
| 15% | 8.51 tok/s | 25.9s | 61.46% | 165.88 GiB |
| 25% | 8.62 tok/s | 24.9s | 78.83% | 91.30 GiB |
| **35%** | **13.86 tok/s** | **17.4s** | 86.73% | 56.88 GiB |
| 50% | 2.35 tok/s | 91.6s | 92.85% | 29.95 GiB |
| 65% | 1.30 tok/s | 116.0s | **95.03%** | **20.13 GiB** |

65%は最もキャッシュ ヒット率が高く、実体化された エキスパート バイトも最少である。

それでもスループットは35%時の約1/10まで落ちる。

これは「ディスク I/Oさえ減らせば速い」というモデルが共有-メモリ環境では成立しないことを示す。

### Qwen Q8

Qwen Q8では4K / 32K、全4 入力 分類で**最小の15% キャッシュが最速**だった。

例えば32K codeで45% キャッシュはヒット率89.90%、実体化された I/O 33.00GiBまで改善する一方、デコードは1.56 tok/s。15% キャッシュでは約12.12 tok/sを出す。

つまり同モデルではキャッシュを増やして経路 localityをより多く保持するより、常駐 footprintを小さくしてシステム 圧力を避ける方が圧倒的に有利だった。

### Qwen Q4

Q4では最適点が入力/文脈で変わる。

4Kでは、

- long-form: 15%
- code: 25%
- reasoning: 25%
- summarization: 35%平均が高いが25%が安定

32Kでは35%が広いdefaultになり、reasoningは25%がbest。

同じモデル 構造でも量子化によってエキスパート バイト数が変わると、最適 キャッシュ pointが変わる。

### 32K context

Gemma Q8のKV キャッシュは、4Kで約0.859GiB、32Kでは約6.875GiB。

そのため50/65% エキスパート キャッシュが32Kでは静的 rejectionになる。

ただしbest 実行可能 pointは4Kと同じ35%だった。

文脈が伸びたから「必ずエキスパート キャッシュを小さくすべき」と単純化できず、モデル 構造・量子化・経路 localityとの相互作用を見る必要がある。

## Speculative decoding addendum

論文はGemma Q8でmulti-トークン 予測系のspeculationも小規模に試している。

25% エキスパート キャッシュ、horizon 4、受理 threshold 0.5の限定的 実行では、7 下書き トークン中4 トークン、57.1%をacceptした。

密 モデルだけを見ると「半分以上acceptなら速くなりそう」に見える。

しかし結果は、

- non-投機 探索的 比較対象: **9.52 tok/s**
- 投機: **8.31 tok/s**

と遅くなった。

さらに実体化された エキスパート バイトは、

- 48.06 GiB
- → 116.66 GiB

へ増えた。

理由として重要なのが**経路 churn**である。

投機 検証では複数将来 トークンを同時に対象へ通すため、単一トークン デコードより多種類のエキスパートへルーティングされ得る。

受理トークンで節約した対象 stepより、追加エキスパート materializationの方が高ければ速度は下がる。

この補足は600-行 主な matrixほど強い要因比較 evaluationではないが、**MoE 投機 デコードでは受理 率だけを性能指標にできない**ことを示す診断結果として重要である。

## Direct full-GGUF loadとの比較

Gemma Q8、32K 文脈で通常の完全な-GGUF Metal 読み込みも保護条件付きで試している。

システム-使用 メモリが99.19%へ達し、98% 安全 保護条件を超えたため経路 output前に停止した。

これは「llama.cppでは絶対動かない」という主張ではない。

示しているのは、**この24GB マシン、このモデル/文脈、この直接 完全な-常駐 pathでは安全な運用が困難だった**という狭いfeasibility 結果である。

MawForgeは同じマシンで、静的 plannerが実行可能と判定したGemma Q8 32K 条件を18GiB 対象内で完走させた。

## 既存研究との差

### MoE-Infinity / ProMoE等との違い

多くのエキスパート-オフロード研究は、キャッシュ ヒット率、プリフェッチ 精度、転送 重ね合わせを改善して速度を上げる。

MawForgeはそれらより前段の、**ローカル マシンがメモリ 圧力で壊れない上限付き operating envelope**を主題にする。

キャッシュ ヒット率が上がってもスループットが下がる実測を中心に据える点が特徴的である。

### FluxMoEとの違い

FluxMoEはdatacenter GPU 提供でエキスパート 常駐を動的に減らし、その分をKV キャッシュへ配る。

MawForgeもエキスパート 常駐とKV capacityを同じ予算問題として見るが、完全な モデルのbacking tierをディスクへ置き、Apple Silicon 共有 メモリ上で「明示的予算を超えないローカル 実行」を優先する。

### Static pruningとの違い

エキスパートを削除してモデルを小さくするのではない。

全エキスパートはディスクに残り、ルータが要求すれば読み込みできるため、主な non-投機 pathはnative ルーティングを維持する。

## 限界

- 主評価は単一MacBook Pro M5 Pro 24GBで、server GPU / Linux / 独立 VRAMへそのまま一般化できない。
- 96-トークン completion固定なので、数千トークンの長期生成中にキャッシュ 作業 集合がどう変化するかは主matrixから分からない。
- 600 行といってもモデル profileは3種類であり、MoE アーキテクチャ全般を網羅しない。
- ディスク / ファイルシステム / macOS キャッシュ behaviorに性能が依存する。
- キャッシュ 割合はモデルごとに同じ絶対バイト量ではないため、割合だけで他モデルへ移植できない。
- 直接 完全な-GGUF 比較対象はfeasibility 補足であり、公平な同条件スループット 比較対象ではない。
- 投機 デコード結果は限定的 補足で、主な 要因比較 研究ほど網羅的ではない。
- キャッシュ ヒット率・実体化された バイトだけで最適 pointを予測できず、マシンごとの測定が必要。

## 一般的な実装上の含意

MawForgeの価値は「ディスクからエキスパートを読む」という機構そのものより、**メモリ 予算を最初-分類 constraintにしたこと**にある。

ローカル MoE ランタイムでは、

1. 完全な モデルが入るかではなく常駐必須テンソルが何バイトか
2. 文脈長からKV reserveをいくら取るか
3. OS / ランタイムへどれだけ余裕を残すか
4. 残りをエキスパート キャッシュへ何バイト渡すか
5. ヒット率ではなくエンドツーエンド 遅延がどこで最小になるか

を順に決める方が安全である。

特に共有 メモリでは「空きRAMをキャッシュで埋める」は危険なpolicyになり得る。

またMoEで投機 デコードを導入する場合、受理 トークン数だけでなく、

- 固有 エキスパート数
- 実体化された エキスパート バイト
- キャッシュ churn
- 検証中の経路 多様性

も同時に測る必要がある。
