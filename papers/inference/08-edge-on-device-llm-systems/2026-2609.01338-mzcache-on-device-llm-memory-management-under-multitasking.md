# mzCache: On-Device LLM Memory Management under Multitasking

## 書誌情報

- **著者**: Hongseung Yu, Minsung Kim, Jongseok Park, Kyunghan Lee
- **公開**: arXiv:2609.01338v1, 2026-09-01
- **採択**: MobiCom 2026（その 32nd Annual International Conference 上 Mobile Computing および Networking）
- **DOI**: 10.1145/3795866.3844495
- **分類**: Inference / Edge・On-端末 LLM システム
- **実装**: llama.cppを基盤に約6k行のC/C++、GPU 注意機構 カーネルはOpenCL約0.6k行

## 一文要約

スマートフォンで他アプリがRAMを要求したとき、LLMの重みとKV キャッシュを必要量だけ細かく退避し、KVは圧縮RAMとFlash 保存へ分散、重みは後ろの層から退避して前の層から推論を再開することで、メモリを空けながら復帰時のTime-へ-最初-トークン（最初のトークンが出るまでの時間）を短縮するシステム。

## 問題設定

オンデバイス LLMは会話履歴をKV キャッシュとして保持すると、小型モデルでも重みと合わせて5〜7 GB程度のRAMを占有し得る。スマートフォンではcamera、game、video等の別アプリが同じRAMを使うため、バックグラウンドのLLMはOSによるページングやプロセス終了の対象になる。

一般的なOS ページングでは、重みはFlash 保存から再読込され、KV キャッシュはzRAM等へスワップされる。しかしKV キャッシュは一般用途のLZ4 / Zstdでは圧縮しにくく、論文の8k-トークン評価ではspace savingが0.2〜9.3%に留まる。さらに復帰時は必要ページを使うたびに保存から読むため、プリフィルがページ 欠落待ちで止まる。Galaxy S25+の完全な 追い出しでは、全て-内-メモリに比べTTFTがFlash スワップで18〜20倍、zRAMでも5〜6倍に悪化した。

一方、GPU ドライバ等でページ-lockしたメモリはOSがページングできず、メモリ 圧力時に他アプリへRAMを譲れない。このため、単に「LLM メモリを固定する」方法でもmobile マルチタスクとは両立しにくい。

## 手法

### 1. Fine-grained shared bufferによる弾力的なmemory解放

通常のLLM ランタイムのように重み / KVを大きな連続バッファとして固定せず、層 重みとKV キャッシュを細かい共有 バッファへ分割する。外部から「何GB空ける必要があるか」が与えられると、必要量だけバッファを解放できる。

mobile SoCの共有 メモリを使い、CPUとGPUが同じ物理 メモリを共有する。これにより、CPUが保存 読む・割当・KV 展開を行っている間も、復帰済みのバッファをGPUが直接使え、CPU→GPUへの追加コピーを避けられる。

### 2. Hybrid Swap: KVを圧縮RAMとFlashの2経路へ分散

静的な重みはFlashへ戻せる一方、動的に生成されたKV キャッシュは保存だけへ置くと復帰I/Oが重い。mzCacheはKV キャッシュの一部を8-ビット 量子化等で圧縮してRAM内へ保持し、残りをFlash 保存へ置く。

単純にKVをRAM、重みをFlashへ固定するのではなく、端末ごとに事前測定したKV 展開 スループットとFlash 連続読み出し スループットから、復帰時に両方の経路が同時に仕事を終えられるようKVの配置量を決める。重み 再読み込みが増える場合には、その時間と並行して展開できるだけの圧縮された KVをRAM側へ残す。

実装ではKV 塊を256 トークン単位とし、UFS 4.0の順次 読むが十分な帯域へ達する約512 KB以上のI/O粒度を確保する。

### 3. Backward-out / Forward-in: 後ろから捨て、前から戻す

Transformerは層 1から順番に実行するため、先頭層を退避すると、その層が復帰するまでGPUはプリフィルを始められない。

そこでmzCacheはメモリを空ける際、最後の層側から重みとKVを退避する。復帰時は逆に、推論で次に必要になる前側から順に戻す。先頭側がメモリに残っていればGPUはすぐプリフィルを開始でき、その間にCPUが後続層を保存 / 圧縮された RAMから復帰する。

この順序により、**復帰処理そのものを消すのではなく、CPUによる復帰をGPUのforward計算の背後へ隠す**。

### 4. 非連続KV chunkを直接読むattention kernel

細分化されたKVを毎回1つの連続バッファへ詰め直すとコピー 費用が増えるため、GPU 注意機構 カーネルは共有 バッファ上の非連続KV 塊をpointer array経由で直接ストリーミングする。online softmaxを使い、塊を統合せず1 passで注意機構を計算する。

このカーネル変更がないと、fine-grained 追い出しで得た弾力性を推論再開時の再packing 費用が打ち消してしまう。退避と復元の結果として物理配置がばらばらでも、そのまま注意機構へ渡せれば『必要量だけ戻す』方針を維持できる。つまりメモリ 管理器が作る非連続配置を計算 カーネル側も受け入れることで、部分的 復元とゼロコピー 共有 メモリの利点をエンドツーエンドで残している。

## 評価条件

- **実機**: Galaxy S25+（12 GB LPDDR5X、Adreno 830、UFS 4.0）、OnePlus 12（12 GB LPDDR5X、Adreno 750、UFS 4.0）
- **モデル**: Qwen3-0.6B、EXAONE-4.0-1.2B
- **文脈**: 8k / 16k / 32k トークン
- **入力**: 既存文脈に対する8-トークンの短いfollow-up 問い合わせ
- **比較**: OS ページング、保存-裏付けられた 部分的 オフロード等
- **実装**: Android アプリとして実機マルチタスク環境でも検証

## 主要結果

- 保存-裏付けられた 部分的 オフロードに対して **TTFTを2.1〜5.5倍短縮**。
- 完全な 追い出し時、通常のOS ページングでは全て-内-メモリ比でTTFTがFlash スワップ **18〜20倍**、zRAM **5〜6倍**へ悪化する一方、mzCacheは復帰と計算を重ねてこの停止時間を大幅に削減する。
- mobile向け小型モデルでも長文脈ではKVだけで数GBに達する。論文例ではLlama 3.2 1Bの128k 文脈でKV約4 GB、Qwen3-1.7Bの32k 文脈でKV約3.5 GB。
- Galaxy S25+ではUFS 4.0 順次 読む約4.2 GB/sに対してLPDDR5X ピーク 帯域約84.8 GB/sであり、保存・CPU 展開・GPU 計算を並行させる余地がある。

## 既存研究との差

従来のオンデバイス LLM研究は、CPU / GPU / NPUへの計算配置、重み オフロード、疎 実行等により「モデルを端末 メモリへ収めて高速に実行する」ことを主に扱ってきた。mzCacheは、LLMが一度動いた後に**他アプリがメモリを要求してLLM メモリが部分的に追い出されるmobile固有のマルチタスク状態**を主問題にする。

server向けのKV オフロード / hierarchical キャッシュとも異なり、独立 GPUのHBMとCPU DRAMという独立した高速階層を前提にできない。mobile SoCの共有 メモリ上で、圧縮RAMとFlashを復帰経路として組み合わせる点が中心となる。

## 限界

- 評価モデルはQwen3-0.6BとEXAONE-4.0-1.2Bで、巨大モデルや大規模MoEは対象外。
- 主評価GPUはQualcomm Adreno系で、注意機構 カーネルもそのFP16実行特性に合わせている。
- メモリ release量は外部から与えられる設計で、どのアプリへどれだけRAMを譲るべきかというOS全体のメモリ 圧力 予測自体は扱わない。
- 圧縮された KVをRAMへ残すため、極端なメモリ 圧力で全データをFlashへ出す状態では2経路の並列性を維持できない。
- KV 圧縮には既存方式を利用しており、圧縮 algorithmそのものが主貢献ではない。

## 一般的な実装含意

オンデバイス LLMでは「平常時に何GBで動くか」だけでなく、バックグラウンドへ回った後のメモリ 回収と再開遅延をランタイム設計に含める必要がある。特に共有-メモリ 端末では、CPUとGPUの間でデータをコピーするのではなく同じバッファを共有し、CPUが保存 / 展開を担当しながらGPUが復帰済み層を実行する構成が有効になり得る。

また、オフロードの順序は単なるLRUではなくモデルの実行順序を考慮すべきである。先に使う層を残し、後で使う層を先に退避することで、同じ保存 I/O量でもTTFTを短くできる。
