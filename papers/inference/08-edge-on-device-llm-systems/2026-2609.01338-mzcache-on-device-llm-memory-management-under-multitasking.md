# mzCache: On-Device LLM Memory Management under Multitasking

## 書誌情報

- **著者**: Hongseung Yu, Minsung Kim, Jongseok Park, Kyunghan Lee
- **公開**: arXiv:2609.01338v1, 2026-09-01
- **採択**: MobiCom 2026（The 32nd Annual International Conference on Mobile Computing and Networking）
- **DOI**: 10.1145/3795866.3844495
- **分類**: Inference / Edge・On-device LLM Systems
- **実装**: llama.cppを基盤に約6k行のC/C++、GPU attention kernelはOpenCL約0.6k行

## 一文要約

スマートフォンで他アプリがRAMを要求したとき、LLMのweightとKV cacheを必要量だけ細かく退避し、KVは圧縮RAMとFlash storageへ分散、weightは後ろのlayerから退避して前のlayerから推論を再開することで、memoryを空けながら復帰時のTime-to-First-Token（最初のtokenが出るまでの時間）を短縮するsystem。

## 問題設定

on-device LLMは会話履歴をKV cacheとして保持すると、小型modelでもweightと合わせて5〜7 GB程度のRAMを占有し得る。スマートフォンではcamera、game、video等の別applicationが同じRAMを使うため、backgroundのLLMはOSによるpagingやprocess終了の対象になる。

一般的なOS pagingでは、weightはFlash storageから再読込され、KV cacheはzRAM等へswapされる。しかしKV cacheは一般用途のLZ4 / Zstdでは圧縮しにくく、論文の8k-token評価ではspace savingが0.2〜9.3%に留まる。さらに復帰時は必要pageを使うたびにstorageから読むため、prefillがpage fault待ちで止まる。Galaxy S25+のfull evictionでは、all-in-memoryに比べTTFTがFlash swapで18〜20倍、zRAMでも5〜6倍に悪化した。

一方、GPU driver等でpage-lockしたmemoryはOSがpagingできず、memory pressure時に他applicationへRAMを譲れない。このため、単に「LLM memoryを固定する」方法でもmobile multitaskingとは両立しにくい。

## 手法

### 1. Fine-grained shared bufferによる弾力的なmemory解放

通常のLLM runtimeのようにweight / KVを大きな連続bufferとして固定せず、layer weightとKV cacheを細かいshared bufferへ分割する。外部から「何GB空ける必要があるか」が与えられると、必要量だけbufferを解放できる。

mobile SoCのunified memoryを使い、CPUとGPUが同じphysical memoryを共有する。これにより、CPUがstorage read・allocation・KV decompressionを行っている間も、復帰済みのbufferをGPUが直接使え、CPU→GPUへの追加copyを避けられる。

### 2. Hybrid Swap: KVを圧縮RAMとFlashの2経路へ分散

静的なweightはFlashへ戻せる一方、動的に生成されたKV cacheはstorageだけへ置くと復帰I/Oが重い。mzCacheはKV cacheの一部を8-bit quantization等で圧縮してRAM内へ保持し、残りをFlash storageへ置く。

単純にKVをRAM、weightをFlashへ固定するのではなく、deviceごとに事前測定したKV decompression throughputとFlash sequential-read throughputから、復帰時に両方の経路が同時に仕事を終えられるようKVの配置量を決める。weight reloadが増える場合には、その時間と並行して展開できるだけのcompressed KVをRAM側へ残す。

実装ではKV chunkを256 token単位とし、UFS 4.0のsequential readが十分なbandwidthへ達する約512 KB以上のI/O粒度を確保する。

### 3. Backward-out / Forward-in: 後ろから捨て、前から戻す

Transformerはlayer 1から順番に実行するため、先頭layerを退避すると、そのlayerが復帰するまでGPUはprefillを始められない。

そこでmzCacheはmemoryを空ける際、最後のlayer側からweightとKVを退避する。復帰時は逆に、推論で次に必要になる前側から順に戻す。先頭側がmemoryに残っていればGPUはすぐprefillを開始でき、その間にCPUが後続layerをstorage / compressed RAMから復帰する。

この順序により、**復帰処理そのものを消すのではなく、CPUによる復帰をGPUのforward計算の背後へ隠す**。

### 4. 非連続KV chunkを直接読むattention kernel

細分化されたKVを毎回1つの連続bufferへ詰め直すとcopy costが増えるため、GPU attention kernelはshared buffer上の非連続KV chunkをpointer array経由で直接streamingする。online softmaxを使い、chunkを統合せず1 passでattentionを計算する。

## 評価条件

- **実機**: Galaxy S25+（12 GB LPDDR5X、Adreno 830、UFS 4.0）、OnePlus 12（12 GB LPDDR5X、Adreno 750、UFS 4.0）
- **model**: Qwen3-0.6B、EXAONE-4.0-1.2B
- **context**: 8k / 16k / 32k tokens
- **入力**: 既存contextに対する8-tokenの短いfollow-up query
- **比較**: OS paging、storage-backed partial offload等
- **実装**: Android applicationとして実機multitasking環境でも検証

## 主要結果

- storage-backed partial offloadに対して **TTFTを2.1〜5.5倍短縮**。
- full eviction時、通常のOS pagingではall-in-memory比でTTFTがFlash swap **18〜20倍**、zRAM **5〜6倍**へ悪化する一方、mzCacheは復帰と計算を重ねてこの停止時間を大幅に削減する。
- mobile向け小型modelでも長contextではKVだけで数GBに達する。論文例ではLlama 3.2 1Bの128k contextでKV約4 GB、Qwen3-1.7Bの32k contextでKV約3.5 GB。
- Galaxy S25+ではUFS 4.0 sequential read約4.2 GB/sに対してLPDDR5X peak bandwidth約84.8 GB/sであり、storage・CPU decompression・GPU computationを並行させる余地がある。

## 既存研究との差

従来のon-device LLM研究は、CPU / GPU / NPUへの計算配置、weight offload、sparse execution等により「modelをdevice memoryへ収めて高速に実行する」ことを主に扱ってきた。mzCacheは、LLMが一度動いた後に**他applicationがmemoryを要求してLLM memoryが部分的に追い出されるmobile固有のmultitasking状態**を主問題にする。

server向けのKV offload / hierarchical cacheとも異なり、discrete GPUのHBMとCPU DRAMという独立した高速tierを前提にできない。mobile SoCのunified memory上で、圧縮RAMとFlashを復帰経路として組み合わせる点が中心となる。

## 限界

- 評価modelはQwen3-0.6BとEXAONE-4.0-1.2Bで、巨大modelや大規模MoEは対象外。
- 主評価GPUはQualcomm Adreno系で、attention kernelもそのFP16実行特性に合わせている。
- memory release量は外部から与えられる設計で、どのapplicationへどれだけRAMを譲るべきかというOS全体のmemory pressure prediction自体は扱わない。
- compressed KVをRAMへ残すため、極端なmemory pressureで全dataをFlashへ出す状態では2経路の並列性を維持できない。
- KV compressionには既存方式を利用しており、compression algorithmそのものが主貢献ではない。

## 一般的な実装含意

on-device LLMでは「平常時に何GBで動くか」だけでなく、backgroundへ回った後のmemory reclaimと再開latencyをruntime設計に含める必要がある。特にunified-memory deviceでは、CPUとGPUの間でdataをcopyするのではなく同じbufferを共有し、CPUがstorage / decompressionを担当しながらGPUが復帰済みlayerを実行する構成が有効になり得る。

また、offloadの順序は単なるLRUではなくmodelの実行順序を考慮すべきである。先に使うlayerを残し、後で使うlayerを先に退避することで、同じstorage I/O量でもTTFTを短くできる。
