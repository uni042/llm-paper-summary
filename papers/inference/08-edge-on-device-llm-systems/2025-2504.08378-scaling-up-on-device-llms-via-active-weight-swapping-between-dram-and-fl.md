# ActiveFlow：端末推論で使う重みだけをDRAMへ先読みする

## 概要

スマートフォン上で大規模言語モデルを動かす際、モデルの全重みをDRAMに置けないことが最大の制約になる。ストレージに重みを置き必要時に読み込めばモデル規模は増やせるが、自己回帰復号では各トークン生成で多数の層を順番に実行するため、フラッシュからの重み読込が毎回の待ち時間となる。一般的なニューラルネットワーク向けの層単位入替えは、演算時間で次層の読込を隠す余地があるが、メモリ帯域律速のLLM復号ではそのままでは十分に隠せない。

ActiveFlowは、文脈に応じて重要度の高い重みチャネルだけを演算・読込対象にする「活性重み（active weights）」を利用する。さらに現在の層の活性化ベクトルから数層先の活性重みを予測して先読みし、複数層の重みをフラッシュ上で近接配置する。先読みで外れた重みは実際の活性化が判明してから追加読込する。頻繁に使われるチャネルをDRAMに保持し、メモリ予算に応じてキャッシュと先読み領域を調整する。疎性による出力のずれは、密な元モデルの分布へ近づける自己蒸留で補償する。

原著はOnePlus 12、Pixel 6、Infinix ZERO 30でCPUベースのllama.cpp改造版を実装し、同じモデル品質・速度条件でLLaMA 7BのDRAMを最大40%削減したと報告する。Pixel 6では4ビット量子化したMixtral-8x7Bを2.9GBの重みメモリ費用、毎秒1.8トークンで動作させた。ただしこれは端末・モデル・疎性率が固定された実験であり、どのモデルでも元の密な計算と完全に同じ回答を維持できるという意味ではない。

## 問題設定と技術的背景

スマートフォンのDRAM容量は端末製造時に固定され、OSや同時起動アプリも占有する。LLMが必要とするメモリは重み、KVキャッシュ、作業バッファからなり、特に重みが大きいとアプリが起動できないか、OSのメモリ圧迫により終了する。モデルをフラッシュに置き、必要な層の重みをDRAMへ入れ替える方法は容量を節約するが、毎トークン各層の読込を繰り返すとフラッシュI/Oが支配的になる。原著は端末上のDRAM帯域とフラッシュ帯域におよそ5倍の差があると説明し、フラッシュ転送量を減らす必要を示している。

一方、Transformerの線形変換では入力活性化の大きさがチャネルごとに異なる。寄与の小さいチャネルを省いても出力の変化が小さい場合があり、入力文脈に依存する疎性（contextual sparsity）が生じる。原著のLlama-2-70Bでの上限分析では、トークンを同じに保つのに必要な活性重みは多くのトークンで全体の5%未満、最大でも15%と報告される。ただしこれは重要度を後から計算した理想的な上限分析であり、実行前に正確な活性重みを予測できる証明ではない。

ReLU活性化を用いる既存方式では出力が厳密にゼロになるチャネルを利用できるが、現代のLLMはSiLU等を使い、ReLU固有のゼロを前提にできない。別の方式では予測器を追加して活性チャネルを予測するが、予測器自身のメモリや学習費用が発生する。ActiveFlowは活性化の大きさに基づく上位Kチャネル選択を採用し、ReLUへモデルを改造しなくても使えるようにする。活性化が確定してから重みを読めば遅いので、層間の活性化の相関を利用して先読みを可能にする点が独自の設計である。

## 手法

### 活性チャネルの決定

線形層の入力ベクトルに対し、活性化絶対値の大きい成分を優先する上位K選択（Top-K）で必要な重みチャネルを選ぶ。入力成分が小さいと、その成分に掛ける重みの出力への寄与も小さくなりやすい。従って演算対象を減らせるが、全重みを使う密な演算の近似である。各層の入力が実際に確定すれば正確な上位K集合を計算できるものの、その時点からフラッシュを読み始めると復号の逐次依存によりI/Oを隠せない。

### 層をまたぐ活性重みの先読み

残差接続を持つTransformerでは、前層の入力が次層へ大きく残るため、近接層の活性化ベクトルの分布が似る。原著のLLaMA-2-7Bでは第3層以降の注意Q/K/VとFFNのgate/upで入力の類似度が95%を超え、上位K集合の一致精度は層間で80%超と報告される。この相関を利用し、現在層の入力活性化から次の複数層で使うと予想されるチャネルを選ぶ。

先読み対象を数層単位の群にまとめ、現在の群を計算している間に次群の活性重みを非同期に読み込む。次群の実入力が得られたら、先読み集合と実際の上位K集合を比較し、欠けているチャネルだけを要求時読込する。先読みが的中すれば計算とI/Oが重なり、外れれば追加I/Oと待ち時間が生じる。活性化の類似性が弱い層や入力では的中率が下がるため、先読みの効果は一定ではない。

### フラッシュ配置と転送粒度

フラッシュは小さな断片を多数読むと帯域を活用しにくい。原著のUFS 2.2/3.1/4.0測定では転送塊を64KBより大きくすることが高い帯域を得る目安になる一方、活性重みのチャネル単位は約4KB程度になり得る。単純なチャネル別読込では転送要求が細かく分かれ、GB/s級のフラッシュが実効的にMB/s級へ落ちる可能性がある。

ActiveFlowは重みの格納順を層群単位に再編成し、先読みする複数層のチャネルを連続した大きいI/Oへまとめる。GGUF内の重みテンソルを再配置し、量子化重みと尺度因子を対応して取り出せるよう転置処理も行う。したがって通常のGGUFをそのまま読み込むだけで同じ効果が得られるわけではなく、格納形式と実行器の協調が必要である。

### 文脈別の頻出重みキャッシュ

復号中は同じ会話文脈で活性化しやすい重みチャネルが繰り返し現れる。原著はWikiText-2上で、特定文脈内のチャネル選択確率が0.7を超える例がある一方、データセット全体の頻度とは異なることを観測した。そこで層ごとにチャネルの使用頻度カウンタを保持し、キャッシュにない新規チャネルの頻度が、既存キャッシュ内で最も低頻度のチャネルを上回れば入れ替える。

このキャッシュは単に直近に使った重みを保持するのではなく、同一文脈で繰り返し必要になるチャネルを優先する。原著の図12の例では、最初のトークンで4チャネル中1件しかキャッシュにない命中率25%から、次のトークンでは4件中3件が命中する75%へ改善する。これは仕組みを説明する例であり、すべての実負荷で命中率が75%になるという意味ではない。

### DRAM予算に応じた群・キャッシュ配分

DRAM予算を、現在計算に使う重みと先読み群、頻出重みキャッシュ、KVキャッシュに分ける。原著の式(8)では `M = M_cl + M_cache + M_kv` と表し、固定KV容量を前提として、前二者を調整する。メモリが少ないほど疎性率を上げて読み込む重みを減らす必要があるが、疎性を強くしすぎると品質が低下する。著者はまず予算に収まる疎性率を決め、次に群に含む層数を増やしながら、先読み時間が現在の計算時間で隠せるか、追加の改善が十分かを調べる貪欲探索を採用する。

フラッシュ読込時間のモデルには先読みの大きな転送と、予測漏れによる小さな要求時転送を別々に含める。先読みが多すぎるとメモリを圧迫し、キャッシュを削って再読込を増やす。キャッシュが大きすぎると先読みの並列度を確保できない。可用DRAMが変化した場合にはキャッシュ領域を調整し、計算とフラッシュ読込の重なりを維持しようとする。予算配分は復号速度とモデル品質の交換条件であり、容量だけを最小化するものではない。

### 疎性に対応した自己蒸留

上位K疎性は密な元モデルの演算を近似するため、特に高疎性では確率分布や回答品質が変わる。ActiveFlowは密な元モデルを教師、疎性を適用したモデルを生徒とする自己蒸留（self-distillation）を行い、教師の出力分布へ近づくよう重みを調整する。損失は出力分布のカルバック・ライブラー発散を含み、疎性マスクを通る勾配には直通推定（straight-through estimator）を利用する。

原著はBitDistillerに疎性モジュールを追加し、C4の部分集合で各エポック約5万標本・100億トークン、2エポック、学習率1e-6、4ビット量子化を用いる。A100 80GBを4基使い、1モデルの蒸留に約10時間かかったと報告する。推論時に疎性率を変更してもモデルを毎回蒸留し直さず使える設計で、学習時と推論時の疎性率が±15%違ってもPPL誤差1%以内という表3の結果がある。ただし追加学習が不要な方式ではなく、端末への導入前に相応のGPU学習資源を要する。

### CPU上の非同期実装

実装はllama.cppのCPU側を改造し、演算を大きいCPUコア、フラッシュ読込を小さいコアへ分担する。Linuxの非同期I/O機構 `io_uring` で重みの読込を要求し、別スレッドがバッファへ配置する。原著は重みの格納形式、量子化尺度、キャッシュ置換、計算スレッドとの同期までを実装している。従って単純なメモリマップやOSページキャッシュ任せの方式とは異なり、LLMの層構造と活性化予測を利用してアプリケーション側がI/Oを制御する。

## 主要結果

原著の導入と第7節では、同じモデル品質と速度の条件でLLaMA 7BのDRAM使用量をllama.cpp比最大40%削減したと述べる。この数値はメモリ・品質・速度を同時に考えた特定の比較点であり、全モデル・全端末の平均削減率ではない。同じ疎性率でTEALと比較した場合にはDRAM使用量を最大2分の1にできると報告し、先読みとキャッシュによる容量の効率化を示している。

Pixel 6では元の非ReLUのMixtral-8x7Bを4ビット量子化した構成を、重み用DRAM約2.9GB、毎秒1.8トークンで動作させた。Mixtralは総パラメータ数が大きい混合専門家モデルであるため、全重みをDRAMへ常駐させず必要部分だけ読み込む設計の効果が分かりやすい。ただし毎秒1.8トークンは高速なデスクトップGPU推論と同等という意味ではなく、低メモリの端末で大きなモデルを動かせたという容量上の結果である。

原著の図1は、LLaMA-3-8BのPPLと重みメモリ費用の関係で、ActiveFlowが比較対象の量子化、枝刈り、疎性方式に対してパレート前線を構成する点を示す。これは、ある品質水準でメモリを削減する、または同じメモリ予算で品質を維持するという交換条件の比較であり、単独の最大速度値ではない。

第2節の上限分析は、Llama-2-70Bの大半のトークンが5%未満の重みで同じ次トークンを生成できると示す。しかし実装時の上位K選択には予測誤差があり、同じトークンを常に再現できるわけではない。第5節の自己蒸留はその近似誤差を低減する機構で、疎性率が学習時から変化してもPPL悪化を抑えるという表3の感度結果を持つ。上限分析、実装の実測性能、自己蒸留による品質改善は別の実験であり、混同してはいけない。

先読みについては層間活性化の上位K一致率80%超が設計根拠となる。残りの予測漏れは要求時I/Oを引き起こすため、フラッシュのランダムアクセスが遅い端末では性能に影響する。大きい転送塊を作る重み配置、群数の選択、頻出重みキャッシュがこの漏れを補う。キャッシュ命中率の例と実機の総復号速度は別の指標であり、命中率の改善がそのまま生成速度の同率改善を意味しない。

## 既存研究との差

llama.cppの通常CPU実装は重みの演算・読込を行うが、ActiveFlowは文脈依存の活性チャネルを選び、層群をまたぐ先読みと頻出重みキャッシュを統合する。ReLUによるゼロ活性を前提にしたPowerInfer系とは異なり、SiLUなどを用いる元のLLM構造を保持する。TEALは活性化の大きさに基づく疎性を利用するが、ActiveFlowはその活性重みをフラッシュから効率的に読み込むための事前予測・格納配置・I/O重畳を追加する。

従来の層単位DRAM・フラッシュ入替えは演算と読込を重ねられるモデルに適するが、復号の重み帯域律速では十分でない。ActiveFlowは層単位ではなく活性チャネル単位で読込量を減らし、さらに複数層の転送をまとめてフラッシュの大きいI/Oを使う。量子化だけで容量を削減する方式や、静的な重み枝刈りとは異なり、文脈ごとに選ばれる重み集合が変化することを利用する。

## 限界・適用条件

第一に、活性重みの先読みは層間活性化の相関が高いことを前提とする。入力分布やモデル構造によって相関が低いと予測漏れが増え、要求時の小さいI/Oが復号を妨げる。群を大きくしすぎると先読みメモリが増えるため、DRAM予算とフラッシュ帯域の両方で調整が必要である。

第二に、上位K疎性は密なモデルの近似であり、品質劣化がゼロとは限らない。自己蒸留で補償するが、蒸留にはA100複数基による追加学習が必要である。公開済みの任意モデルを何も学習せず同じ品質で疎性化できるという主張ではない。疎性率を極端に高めれば精度・PPLの悪化が残る可能性がある。

第三に、原著の実装と実測はAndroid系端末のCPUバックエンドとUFSストレージを対象とする。GPUやNPUを中心にした推論、WindowsのファイルI/O、NVMe SSD、PCIe GPUとの転送、サーバー上の高並列処理へ同じ効果が一般化するとは示されていない。CPUコアへのI/Oスレッド割当てやLinux `io_uring` は別環境への移植を必要とする。

第四に、重みをフラッシュに置くことでDRAMを減らしても、フラッシュの読み込み回数、消費電力、端末の熱制約、書込寿命とは別の問題が残る。原著は復号速度と端末電力を測定するが、長期利用の発熱・電池劣化・多アプリ競合まで包括的に保証するものではない。また評価のKVキャッシュは固定容量として扱うため、長文脈化によるKV容量の急増は別途対処が必要である。

第五に、論文の最大40%削減やMixtral実行例は特定のモデル・量子化・端末・疎性率の条件であり、平均的なユーザー環境で常に達成する値ではない。とりわけローカルPCのRTX GPUに対して直接同じ性能改善を見込むべきではなく、対象ハードウェアのDRAM/VRAM帯域、SSD帯域、重み配置と負荷条件を改めて測る必要がある。
