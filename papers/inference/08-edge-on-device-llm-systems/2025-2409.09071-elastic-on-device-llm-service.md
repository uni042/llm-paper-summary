# Elastic On-Device LLM Service — ElastiLM

## 概要

端末内で一つの大規模言語モデルを複数アプリから共用する場合、画面操作エージェント、チャット、バックグラウンド要約は、それぞれ異なる遅延目標を要求する。最初のトークンまでの時間（TTFT）は入力の長さとモデルの規模の両方に影響されるが、後続トークン間隔（TPOT）は通常、重みの読出しに左右されるためモデル規模の影響が強い。したがって同じ計算削減率でも、プロンプトを短縮するか、モデル幅を縮小するかで品質と遅延の交換条件が変わる。

ElastiLMは、この二つの調整軸を同じ要求制御に統合する。注意ヘッドと多層パーセプトロン（MLP）のニューロンを重要度順に物理配置し、一つの重み集合から連続した先頭領域を切り出して部分モデルを構成する。さらに二頭の小型言語モデルが、要求のTTFT・TPOT目標を満たすように、残す入力トークンと部分モデルの幅を決定する。品質回復用の低ランク適応（LoRA）も部分モデルごとに付加する。

著者らは市販スマートフォン3機種、3B〜8Bの5モデル、6種類の応用を模した合成要求列で、7方式に対する絶対正解率の改善6.60〜14.83ポイント、平均10.45ポイントを報告した。これは生成速度が10.45%増えたという意味ではなく、指定された遅延制約を守った要求の**正答率の絶対差**である。モデル切替は平均0.31秒で、論文の端末実験では平均TTFTの1%未満に収まる。端末の並行要求や実機GPU・NPUによるエンドツーエンド実行は検証範囲外である。

## 問題設定：モデルだけを小さくしてもサービスは弾力化しない

同一のLLMを各アプリが利用するとき、サービス水準目標（SLO）は要求ごとに異なる。論文ではSLOを元のモデルに対する初回トークン時間の比率と出力トークン間隔の比率の組として表す。たとえば `<40%,70%>` なら、元のモデルのTTFTの40%以下、TPOTの70%以下が目標である。比率が小さいほど厳しい要求になる。単一の固定モデルは緩い要求で過剰に計算し、厳しい要求では応答が間に合わない。一方、要求に合わせた複数の別モデルを端末へ常駐させるとメモリを使い尽くす。

枝刈りで同じ元モデルから大小の部分モデルを作っても、実行時に必要な重みがメモリ内で飛び飛びに配置されると問題が残る。密な行列演算の高速カーネルを使うには部分モデルの行列を連続配置へ並べ直す必要があり、その移動が要求のTTFTへ直接加算される。著者のRedmi K60 Champion実験では、従来の構造的枝刈り方式で20%から30%へモデルを切り替えるだけで8.2秒を要した。4096×4096の問い合わせ射影行列の再配置にも最悪139ミリ秒かかる。

もう一つの難点は、モデル側と入力側のどちらを削るかによって答えの品質が異なることだ。論文のARC_E例では、同じ遅延制約を満たす二つの圧縮配分でも片方しか正解しない。Octopusの関数選択課題では、無作為な配分は理想的な配分より上位5件の関数選択正解率が15.2ポイント低かった。従ってモデル幅をSLOから一意に逆算するだけでも、プロンプトを一律の割合で切り詰めるだけでも十分ではない。

## 手法：オフライン準備から要求処理まで

### 置換整合な計算単位の重要度計測

Transformerの中間表現には、順序を変えても隣接する行列の対応する軸を同時に入れ替えれば最終出力が変わらない単位がある。たとえば二つの線形変換 `xW1W2` では、`W1` のある列と `W2` の同じ番号の行を一組として並べ替えれば、途中の要素順だけが変わり、積の結果は維持される。ElastiLMはこの性質を、注意機構のヘッド単位とMLPのニューロン単位へ適用する。注意ヘッドでは問い合わせ・鍵・値の射影列と出力射影行を整合させ、MLPでは上向き射影列と下向き射影行を同時に動かす。回転位置埋め込みやグループ化問い合わせ注意など、論文で挙げる一般的なTransformer変種にも適用できる。

どの単位を先に残すべきかは、較正用コーパスの次トークン予測損失 `L` を用いて決める。単位 `i` をゼロ化したときの損失差 `|L-L(W_i=0)|` を重要度とし、実装では一次の近似 `|∂L/∂W_i · W_i|` を使う。既定の較正データはBookCorpusの部分集合である。この勾配に基づく指標は単なる重み絶対値と異なり、実際の予測損失に対する寄与を推定する。ただし一次近似であり、複数単位を同時に削ったときの非線形相互作用まで厳密に保証するものではない。

### 一度限りの並べ替えと連続した部分モデル

重要度を求めたら、各注意ブロックとMLPブロックの内部で単位を重要な順に並べ替える。この並べ替えはクラウド上で一度だけ実施する。実行時には重み配列の先頭から所定の境界までを読み出すだけで、20%から100%まで既定10%刻みの部分モデルを選択できる。各層の密行列を保持できるため、飛び飛びの要素を集める疎カーネルや要求ごとの重みコピーを必要としない。モデル幅を変える操作は重み領域の終端ポインタの変更と、後述の適応行列の付け替えになる。

すべての層を一様に削るわけではない。層を外したときの損失増加を調べると、約20%の層が特に重要な「アンカー層」に相当する。これらは縮小せず、残りの層で削減率を調整する。論文は32層のうち26層を非アンカー層とする例を示し、モデル全体を50%相当にするため非アンカー層で37.5%の単位を保持する。このため「モデル50%」は全層を半分ずつ切るという意味ではない。アンカー層を保持することが、極端に小さな部分モデルの品質を支える。

### 部分モデルごとの低ランク回復と切替

枝刈りだけでは正答率が落ちるため、各部分モデルの問い合わせ・鍵・値・出力射影およびMLPの重みに低ランク適応行列を付ける。既定の階数は8で、元の重みを固定したまま、Alpaca-cleanedの約5,000万トークンを使って次トークン予測損失を最小化する。追加の適応重みは元モデル重みの約0.1〜0.5%相当で、全ての部分モデルを保持しても追加メモリは5%未満と報告される。端末では以前の適応行列を外し、終端ポインタを移動し、新しい適応行列を付ける。4096×4096の問い合わせ射影行列を拡張する例では約2ミリ秒で、従来の重み移動約140ミリ秒と区別される。

### 二頭小型言語モデルによる入力と幅の同時選択

プロンプトをどれだけ削るか、モデルをどこまで縮めるかを選ぶのは、MobileBERTを基盤にした約4,000万パラメータの小型言語モデル（TLM）である。SLOを専用の埋め込みトークンとして入力し、二つの出力頭を使う。採点頭（score-head）は各入力トークンを保持・削除の二値で採点する。決定頭（decision-head）は、モデルの幅とプロンプト残存率をそれぞれ多クラス分類として選ぶ。既定では下位24層中12層を共有し、各頭の専用部分の学習と推論の負担を抑える。

採点頭はMeetingBank由来の約5,000万トークンに対し、GPT-4が付けた保持・削除ラベルで訓練する。決定頭の訓練では、MMLU-Proの質問と正解、候補となる部分モデル・圧縮率、端末で事前計測した遅延表を組み合わせる。要求とSLOに対して実行可能な配分を列挙し、正解できる中で最も軽い配分を教師ラベルにする。全配分で正解できなければ既定の選択を用いる。この自己生成ラベル付けには実際の部分モデルを繰り返し評価するオフライン費用がある。

要求処理では、TLMが決定した残存率に合わせて採点頭の保持確率上位のトークンを残し、決定された幅の部分モデルへ入力する。端末の一度限りの遅延プロファイルを使って制約を判定し、決定頭の予測が制約を満たさないときは実行時検査で、制約を厳格に満たす代替配分へ切り替える。TLMの実行自体は、元モデルのTTFTの5%以内と著者らは報告するが、ゼロ費用ではない。採点頭の出力、配分の選択、モデル切替の全てが要求の実行経路に含まれる。

### 実装経路と追加コスト

クラウド側はPyTorchとHugging Face Transformersを用い、8基のNVIDIA A40で重要度計測、部分モデル回復、二頭モデル学習を実行する。端末側はC++推論基盤mllmを改造し、密な線形演算をポインタ付きのElasticLinearに置き換える。低ランク行列積と加算にはARM NEONを使う。アプリは独立した推論サービスを呼び出し、要求の入力とSLOを渡す。したがって高速な切替の前提は、対応する行列の配置、部分モデルの適応行列、端末固有の遅延表を事前に用意できることである。

| 3端末での600要求合成列、α=0・±0.25 | 7比較方式に対する絶対正解率差 | +6.60〜+14.83ポイント、平均+10.45ポイント | 各要求のSLOを満たす条件での回答品質差であり、速度倍率ではない |
| LLaMA-7B、Redmi K60 Champion、α=0 | 部分モデルの切替時間 | 0.31秒、平均TTFTの1%未満 | 重み再配置をなくしてもLoRA切替などの実費用は残る |
| 同条件、PFS/LaCoを全サイズ常駐とした理想構成 | 常駐メモリ | ElastiLMと通常サービスは15〜17GB程度、理想PFSは29.3GB、理想LaCoは76.3GB | 複数の専用モデルを全て端末に載せる案は3機種のRAMを超える |
| 同条件、従来のPFSスワップ／LLMPruner | 要求ごとのモデル切替遅延 | 最大8.3秒／6.2秒、ElastiLMは0.31秒 | 重み移動と再配置の削減が要求単位の利得につながる |
| 単独データセット、Mi 14でのSLOを利用しクラウド評価 | 比較方式に対する正答率差 | 最大+40ポイント、PFSより高いSLO条件は77.8% | 切替費用を除いた別評価であり実機要求列の+10.45と同一視しない |
| 指定の品質低下2ポイント以内 | 元モデルに対するTTFT/TPOT | TTFT最大5倍、TPOT最大2倍の高速化 | 品質損失を許容した条件付きの性能・品質交換 |

モデル側だけの枝刈りでは、緩い制約に余裕があっても入力側を調整しないため品質を最大化できない。入力側だけの圧縮では、初回処理の費用を削れても出力段階の重み読出しを十分には削れない。ElastiLMが両方を選択することで、特に厳しいTTFTとTPOTを組み合わせた要求で優位が生じる。反対に元モデルへ近い緩いSLOでは、削る余地が小さく、比較方式との品質差は縮む。これは論文の単独データセット評価で明記されている。

### 構成要素除去、準備費用、量子化

| 追加実験 | 具体的な観測 | 因果関係・留保 |
|---|---|---|
| LLaMA-7BをMi 14向けに準備 | 合計68.3 GPU時間、うち部分モデル回復40.4時間、決定頭ラベル生成・学習26.3時間 | オフラインで一度払う費用。比較する他の枝刈り方式より21.7〜68.2 GPU時間多い |
| 並べ替えを無効化 | 正解率が10ポイント超低下 | 重要な置換整合単位を先頭に集める効果が大きい |
| 採点頭を無効化 | 正解率が約5ポイント低下 | 入力トークンの内容依存選別も寄与する |
| 回復用データを10倍／20倍 | 正解率改善は+0.2／+0.4ポイント | 学習データ増加の限界利得が小さい |
| TLM規模と共有層 | 約40M、共有12層が良好 | より大きいTLMは予測品質の利得を実行費用が相殺 |
| 圧縮段階の刻み幅 | 10%から5%へ細分化してもほぼ変化なし | 段階数の増加が常に品質向上につながるわけではない |
| 重みのみ量子化 | 8ビットはほぼ無損失、4ビットは絶対正解率約3ポイント低下 | 量子化との併用は可能だが極端な低ビット化には品質代償 |
| 入力の冗長性を先に約15%削減 | なお比較方式を上回る | 最初から短い入力でも、二軸の配分選択に利得が残る |

オフライン準備の68.3 GPU時間は、スマートフォンが毎回負担する時間でも、モデルを一つ学習するための事前学習全費用でもない。モデル回復と、正解を得る配分を探索する自己生成ラベル作成が大半を占める。モデルと端末の組合せが変われば遅延表の再計測や部分モデルの回復が必要になる可能性があり、準備済みモデルを無制限に他の端末へ移せるとは示していない。

### エネルギーと端末アクセラレータの追加分析

論文はTTFT・TPOT以外に、要求全体の推論時間と消費エネルギーを制約にしたMi 14上の追加分析も行い、比較方式より良い傾向を報告する。ただし主たる実機エンドツーエンド評価はCPU上であり、GPU/NPUについては実機上の完全なサービスを動かした測定ではない。端末の演算・メモリ負荷を別途プロファイルした遅延へ写像する「仮定的な」評価であり、動的形状、グラフ構築、SDK制約などが解消された後の実性能を保証するものではない。

## 既存方式との差と適用条件

PFSは複数の既製モデルを使い分けるが、全モデル常駐ならメモリ費用が大きく、入替なら初回トークン時間を圧迫する。LLMPrunerは元モデルから枝刈りした部分モデルを使えるが、密行列を実行しやすい連続領域へ並べ直す必要がある。層単位のLEやShortGPT、LaCo、AttnDropは切替粒度が粗く、全層の内部にある重要度の差を十分利用しない。LLMLingua2と文脈依存疎化の組合せは入力の圧縮に重点を置くが、疎計算が端末の密行列カーネルで効率良く実行されるとは限らない。

ElastiLMの差は、注意ヘッドとMLPニューロンを一度だけ整列し、連続した部分行列を同じ密カーネルで扱える点と、入力トークン削除・モデル幅・遅延目標を一つの二頭モデルで同時決定する点にある。どちらか一方だけでは、モデル切替の重み移動か、要求内容に依存する圧縮配分の誤りが残る。これらを合わせて、単一モデルを多用途サービスとして運用するという課題に対応する。

## 限界と負の結果

第一に、要求列は6種類のアプリと600要求から合成したもので、実際の利用者が同時に複数アプリを使う競合トレースではない。著者らも基本的には単一ユーザーによる逐次要求を想定し、並行要求には別の上位スケジューラやバッチ処理が必要になり得ると述べる。従って混雑時の待ち行列やバッチ形成による品質・遅延変化は本論文の主結果からは推定できない。

第二に、端末GPU・NPUについての追加図は演算・メモリ負荷から遅延を見積もった仮定的な分析であり、完全なサービスの実機評価ではない。動的形状やグラフ構築の制約を受ける端末SDKへそのまま移植できる保証はない。主結果のCPU向けC++実装と混同してはならない。

第三に、重要度は較正コーパスの勾配に基づく一次近似であり、未知の専門タスクや極端な入力分布へ移ると、残すべき単位やトークンが変わる可能性がある。決定頭の教師ラベルもMMLU-Proと事前計測した端末遅延表に依存する。予測が制約に違反するときは保守的な代替配分へ退避するが、その退避が品質最適であることは保証されない。小型モデルの推論は元モデルTTFTの5%以内という実測上の費用を持つ。

第四に、圧縮後の品質回復には部分モデルごとのLoRAが必要であり、オフラインで68.3 GPU時間の準備を行っている。4ビット量子化では約3ポイントの絶対正解率低下が報告される。非常に緩いSLOでは従来の枝刈り方式との差も縮み、全ての要求・精度・ハードウェア条件で同じ利得が得られるわけではない。論文が示した正解率差や切替時間は、特定の端末、モデル群、合成要求分布に結びついた結果として読む必要がある。
