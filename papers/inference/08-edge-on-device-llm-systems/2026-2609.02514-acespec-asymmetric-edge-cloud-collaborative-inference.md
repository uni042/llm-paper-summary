# AceSpec: An Asymmetric Edge-Cloud Collaborative Framework for Communication-Efficient LLM Inference

> **AceSpecは、edge-cloud speculative decodingでdraftが外れた時に「cloudの返事を待つ→edgeで最初からdraftし直す→また送る」というWAN rollbackを避けるため、cloud待ち時間中にedge側で複数の外れ方を先回り計算してcacheしておく。**

## 概要

edge deviceだけで大きなLLMを動かすのはmemory/compute的に難しい。一方、cloudだけで推論するとnetwork latencyが増える。

そこで使えるのが**edge-cloud speculative decoding**である。

基本形は次の通り。

1. edge側の小型言語model（Small Language Model; SLM）が数tokenをdraftする。
2. draft token列だけをcloudへ送る。
3. cloud側の大きなtarget LLMがまとめてverificationする。
4. targetがacceptしたtokenを確定する。

split inferenceのように巨大なhidden tensorを毎layer WANへ送る必要がなく、token index中心の通信で済むためedge-cloud協調に向いている。

しかしWANでは**round-trip time（RTT）**が大きい。しかもdraft modelとtarget modelは完全には一致しないので、draft rejectionが必ず起こる。

single-chain pipelineでは、rejectionが起きるとedge側の先読み状態が無効になり、

`cloudからrejection結果を受け取る → 正しいtokenでedge stateを戻す → draftを作り直す → 再送する`

というrollbackが必要になる。

このrollbackには再計算だけでなくWAN往復が入り、pipelineが大きくbubbleする。

AceSpecの中心発想は、**cloudの返事を待っている時間にedge GPU/NPUが空いているなら、そのcomputeを使って「もしここでrejectされたら次は何が起こるか」を複数branch先回りして計算しておく**ことである。

rejectが実際に起きても、正しいbranchがcacheにあれば、そのstateへpointerを切り替えるだけで次roundへ進める。

## vanilla edge-cloud speculative decodingの問題

### stop-and-waitではWAN RTTを毎round払う

draft長を`γ`とすると、単純な同期方式の1 roundは概ね

`edge draft時間 + WAN RTT + cloud verify時間`

になる。

edgeがdraftを作り終えた後はcloud responseを待つだけなので、edge computeがidleになる。

そこで既存研究はdraftとcloud verificationを非同期化し、次draftをcloud待ち時間とoverlapする。

### 非同期single chainはrejectに弱い

全draftがacceptされるなら、edgeはずっと先へ走れる。

しかし1 tokenでもtargetと不一致になれば、そのtoken以降を前提にedgeが作ったstateは無効になる。

single-chainしか用意していない場合、reject後の正しいtokenから再draftしなければならない。

論文はこの追加penaltyを概念的に

`rejection probability × (WAN RTT + re-draft time)`

として整理する。

acceptance rateが下がるほどこのpenaltyが支配的になり、非同期pipelineの利得が消えて同期方式へ近づく。

## 手法のあらまし

### 1. main chainだけcloudへ送る

edge SLMは通常通り長さ`γ`のdraft main chainを作る。

ただしAceSpecは、edgeで後から作る全branchをcloudへ送らない。

WAN uplinkへ送るのは基本的に

- main-chain token indices
- verificationに必要な最小限のmetadata

だけである。

これが**非対称通信（asymmetric communication）**のuplink側である。

branch tree全体をuploadすると、tree speculationの計算並列性は得られてもWAN bandwidthを使い切ってしまうためである。

### 2. cloud待ち時間を「branch作成時間」に変える

main chainを送った後、cloudはtarget LLMでverifyし、WANを通ってresponseを返す。

この間edgeは待機しない。

main chainの各位置について、

> 「このtokenがrejectされ、別candidate tokenが採用されたら、その先はどう続くか」

というalternative branchを作る。

例えばmain chainが

`A → B → C → D`

なら、Bがrejectされた場合の

`A → X → ...`

やCがrejectされた場合の

`A → B → Y → ...`

といったstateを先に計算する。

### 3. branchはedge SLMの確率分布から選ぶ

cloud targetの正確な分布はresponseが返るまで分からない。

そこでedgeは自分のSLM distributionをproxyとして使う。

各potential rejection depthで、main-chain token以外の上位candidateを取り、branchを展開する。

ここで各depthへ同じbranch数を割り当てるとは限らない。

rejectionが起きやすい位置へ多くのbranch budgetを与える方がcache hit率を上げられるため、後述のoptimizationでfan-out shapeを変える。

### 4. Tree Attentionで複数branchを一括計算する

branchを1本ずつautoregressiveに計算すると、branch数Nに比例してedge compute timeが増え、cloud待ち時間へ収まらない。

AceSpecは複数branchを1 sequenceへpackし、**木構造attention mask（Tree Attention Mask）**を使って1 parallel forwardへまとめる。

maskは大きく3領域に分かれる。

- **shared prefix**: すべてのbranchが既にverifiedな過去contextを参照できる。
- **main-path prefix**: branchが分岐する位置までのmain chainだけ参照する。
- **branch suffix**: 各branchは自分のancestorだけを見る。

これによりbranch同士が未来情報を混ぜず、複数branch stateをGPU並列性で同時に作れる。

論文でいう`O(1)`は、このようなparallel constructionや後述lookupの観点でbranch数に対するsequential loopをcritical pathから外すという意味であり、**推論全体が絶対的な定数時間になるという意味ではない**。

### 5. branchのKV/stateをprobabilistic cacheへ保存する

作成したbranchごとに、そこから推論を続けられるstateをedge memoryへ保持する。

概念的には

`(reject position, resampled token) → precomputed branch state`

というlookup tableになる。

このcacheを論文は**確率的state cache（probabilistic state cache）**として扱う。

「確率的」というのはstate自体が曖昧だからではなく、どのreject outcomeが来るか分からないので、確率の高いoutcomeを限られたmemory/compute budget内で先回りcacheするという意味である。

### 6. cloudはreject位置とtarget distributionを返す

cloud targetはmain chainをverifyする。

acceptできなくなった位置では、cloud側で最終sampleまで完結させて長いstateを返すのではなく、

- rejection position
- target probability distributionの必要部分

をedgeへ返す。

full vocabulary distributionは巨大なので、downlinkではsparse/compact representationにする。

uplinkはtoken index中心、downlinkは必要なtarget distribution中心という**非対称protocol**で、双方向とも通信量を抑える。

### 7. edge側でlocal resamplingする

edgeはcloudから受け取ったtarget distributionを使い、speculative samplingで必要なresamplingをlocalに行う。

ここで正しいtoken `X` が決まったとする。

edge cacheに

`(reject position, X)`

に対応するbranchがあれば、そのbranch stateへ切り替える。

cache lookup自体はkey lookupなので`O(1)`に近い。

これが論文のいう**定数時間state recovery（O(1) state recovery）**である。

ただし重要な注意がある。

> `O(1)`なのはcache hitした後のstate selectionであり、branchを事前に作るcomputeもWAN responseも無くなるわけではない。

### 8. cache missなら従来通りrollbackする

正しいresampled tokenのbranchを事前に作れていなければ、AceSpecでもrollbackが必要になる。

その場合はinvalid KVを戻し、正しいtokenからsequential re-draftする。

したがってAceSpecの目的はrollbackを数学的に完全排除することではなく、**有限compute budgetでcache-hit probabilityを最大化し、高価なWAN rollbackの発生頻度を下げる**ことである。

## treeを大きくすればよいわけではない

branchを大量に作ればcache hit率は上がる。

しかしedge computeとmemoryには限界があり、cloudのresponseが返るまでにtree constructionを終えられなければ次pipeline roundを遅らせる。

AceSpecはここを二段階optimizationで決める。

### Network-Aware Budgeting

まず現在の

- WAN RTT
- cloud verification時間
- edge compute throughput

から、cloud turnaround window内に隠せるbranch compute量の上限を求める。

WANが遅ければedgeに長い空き時間があるので多くbranchを作れる。WANが速ければbranch construction budgetを小さくする。

つまり、**network latencyを単なる損失ではなくspeculative computeを行う時間budgetとして利用する**。

### Task-Aware Shape Allocation

次に、その総branch budgetをどのdepthへ配るか決める。

main chainの早い位置でrejectされると、それ以降のdraftが全部無効になるためpenaltyが大きい。一方、各depthでalternative tokenの確率分布も異なる。

そこでLagrange multiplierを使ったoptimizationで、branch fan-outを一律ではなくnon-uniformに配分する。

要するに、

> 「外れやすく、外れた時の損失が大きい場所へbranchを多く置く」

というresource allocationを数理的に行う。

## なぜnucleus sampling対応が重要なのか

edge-cloud systemでは通信を減らすためgreedy decodingだけを扱う研究もある。

greedyならtargetが選ぶtokenは1つなのでprotocolは単純になる。

しかし一般chat generationではtemperatureやtop-pを使ったstochastic samplingが必要になる。

nucleus samplingではdraft modelとtarget modelのdistribution差からreject/resampleが増えやすく、target distributionの情報も必要になる。

AceSpecはsparse downlink distributionとlocal resamplingを使い、**stochastic samplingを維持したままWAN rollbackを抑える**ことを狙う。

## 評価

### hardware / network

実験はedge側にNVIDIA AGX Orin、cloud側にA100-class GPU環境を使い、WAN bandwidthとlatencyを制御して行う。

比較対象は同期speculative decodingや既存edge-cloud pipeline方式。

### 最大3.52× throughput

headlineではbaselineに対し最大**3.52× throughput speedup**を報告する。

この改善はtarget modelを3.52倍高速化したものではない。

主因は、

- WAN待ちとedge branch constructionをoverlap
- reject後のsequential redraftをcache hitで回避
- full treeをWAN送信しない

ことで、communication bubbleを減らしたことにある。

### 50 Kbpsでもnear-peak performance

論文はWAN bandwidthを極端に**50 Kbps**まで絞った条件でも、peakに近いinference performanceを維持したと報告する。

ここで「50 KbpsでもLLMの全dataを高速転送できる」という意味ではない。

AceSpecはそもそもWANへ巨大activationやfull treeを流さず、main-chain indexとsparse distributionに通信内容を縮小している。そのためthroughputがraw bandwidthへ強く依存しにくくなる。

## 既存研究との差

### split inferenceとの違い

split inferenceはlayer途中のhidden activationをedge-cloud間で送る。tensorは大きく、WAN bandwidthが細いとcommunication wallが出る。

AceSpecはtoken-level speculative decodingなのでWAN payloadを小さくする。

### vanilla speculative decodingとの違い

通常のspeculative decodingはtargetとdraftが同じserver内にあり、高速interconnectを前提とする。rejection後のstate synchronization costが小さい。

AceSpecはWAN RTTを主problemとして扱う。

### asynchronous single-chain方式との違い

PicoSpec等はedgeを先へ走らせWAN latencyを隠すが、single chainがrejectされると先読み全体が無効になる。

AceSpecは**複数reject outcomeをedgeだけでbranch cacheする**ため、target resultに応じてlocal stateを切り替えられる。

### naive tree speculationとの違い

branch tree全体をcloudへ送ればWAN payloadが増える。

AceSpecはtreeをedge recovery専用cacheとして使い、cloudへはmain chainしか送らない。

## 限界と適用境界

- **edge側に余剰computeが必要。** edge SLMがすでに飽和している場合、branch生成を無料でoverlapできない。
- **state cache memoryが必要。** branch数を増やすほどKV/state footprintも増える。
- **cache missは残る。** 予測していないreject outcomeではrollback/re-draftが必要。
- **draft distributionをproxyにする。** targetとdraftの分布差が大きいと、間違ったbranchへbudgetを使う可能性がある。
- **WAN条件で最適budgetが変わる。** RTT/bandwidthが急変する環境ではre-optimizationが必要。
- **50 Kbps headlineはprotocol payloadが小さい条件の結果。** 任意のlarge side-channel dataも50 Kbpsで問題ないという意味ではない。
- **`O(1)`はlocal lookup。** branch construction、cloud verify、network responseまで定数時間になるわけではない。
- **edge/cloud両方でspeculative protocol実装が必要。** 単純なOpenAI-style remote APIだけではstate/distribution exchangeが難しい。

## 実装上の含意

AceSpecの一般化しやすい考え方は、distributed speculative executionでfailure recoveryを**失敗後に計算するのではなく、network待ち時間中に先回り計算する**ことである。

特にWAN環境ではRTTを完全に消すことはできない。ならばその待ち時間をlocal compute windowとして使い、rollback可能性が高いstateをcacheする方がよい。

またtree speculationをdistributed systemへ持ち込む時、tree全体をnetwork越しに送る必要はない。**compute用treeとcommunication pathを非対称にする**ことで、local redundancyをWAN bandwidthへ漏らさない設計が重要になる。
