# AceSpec: An Asymmetric Edge-Cloud Collaborative Framework for Communication-Efficient LLM Inference

> AceSpecは端末–クラウド投機的復号で棄却分岐をWAN待ち中に先回り生成して状態キャッシュへ保存し、棄却後の再下書きと往復通信を減らす方式。

## 概要

端末側 端末だけで大きなLLMを動かすのはメモリ/計算的に難しい。一方、クラウドだけで推論するとネットワーク 遅延が増える。

そこで使えるのが**端末側-クラウド 投機 デコード**である。

基本形は次の通り。

1. 端末側側の小型言語モデル（小さい Language モデル; SLM）が数トークンを下書きする。
2. 下書き トークン列だけをクラウドへ送る。
3. クラウド側の大きな対象 LLMがまとめて検証する。
4. 対象が受理したトークンを確定する。

分割 推論のように巨大な隠れた テンソルを毎層 WANへ送る必要がなく、トークン 索引中心の通信で済むため端末側-クラウド協調に向いている。

しかしWANでは**往復 時間（RTT）**が大きい。しかも下書き モデルと対象 モデルは完全には一致しないので、下書き 棄却が必ず起こる。

単一連鎖 パイプラインでは、棄却が起きると端末側側の先読み状態が無効になり、

`cloudからrejection結果を受け取る → 正しいtokenでedge stateを戻す → draftを作り直す → 再送する`

という巻き戻しが必要になる。

この巻き戻しには再計算だけでなくWAN往復が入り、パイプラインが大きく空白する。

AceSpecの中心発想は、**クラウドの返事を待っている時間に端末側 GPU/NPUが空いているなら、その計算を使って「もしここで棄却されたら次は何が起こるか」を複数分岐先回りして計算しておく**ことである。

棄却が実際に起きても、正しい分岐がキャッシュにあれば、その状態へpointerを切り替えるだけで次往復へ進める。

AGX Orin端末とA100級クラウドでWAN条件を制御した評価では、同期投機的復号に対して最大3.52倍のスループットを示し、50 Kbpsでもピーク近くの性能を維持した。

## vanilla edge-cloud speculative decodingの問題

### stop-and-waitではWAN RTTを毎round払う

下書き長を`γ`とすると、単純な同期方式の1 往復は概ね

`edge draft時間 + WAN RTT + cloud verify時間`

になる。

端末側が下書きを作り終えた後はクラウド 応答を待つだけなので、端末側 計算がアイドルになる。

そこで既存研究は下書きとクラウド 検証を非同期化し、次下書きをクラウド待ち時間と重ね合わせする。

### 非同期single chainはrejectに弱い

全下書きが受理されるなら、端末側はずっと先へ走れる。

しかし1 トークンでも対象と不一致になれば、そのトークン以降を前提に端末側が作った状態は無効になる。

単一連鎖しか用意していない場合、棄却後の正しいトークンから再下書きしなければならない。

論文はこの追加penaltyを概念的に

`rejection probability × (WAN RTT + re-draft time)`

として整理する。

受理 率が下がるほどこのpenaltyが支配的になり、非同期パイプラインの利得が消えて同期方式へ近づく。

## 手法のあらまし

### 1. main chainだけcloudへ送る

端末側 SLMは通常通り長さ`γ`の下書き 主な 連鎖を作る。

ただしAceSpecは、端末側で後から作る全分岐をクラウドへ送らない。

WAN 上りへ送るのは基本的に

- 主な-連鎖 トークン indices
- 検証に必要な最小限のメタデータ

だけである。

これが**非対称通信（非対称 通信）**の上り側である。

分岐 木構造全体をuploadすると、木構造 投機の計算並列性は得られてもWAN 帯域を使い切ってしまうためである。

### 2. cloud待ち時間を「branch作成時間」に変える

主な 連鎖を送った後、クラウドは対象 LLMで検証し、WANを通って応答を返す。

この間端末側は待機しない。

主な 連鎖の各位置について、

> 「このトークンが棄却され、別候補 トークンが採用されたら、その先はどう続くか」

という代替 分岐を作る。

例えば主な 連鎖が

`A → B → C → D`

なら、Bが棄却された場合の

`A → X → ...`

やCが棄却された場合の

`A → B → Y → ...`

といった状態を先に計算する。

### 3. branchはedge SLMの確率分布から選ぶ

クラウド 対象の正確な分布は応答が返るまで分からない。

そこで端末側は自分のSLM 分布を代理として使う。

各potential 棄却 深さで、主な-連鎖 トークン以外の上位候補を取り、分岐を展開する。

ここで各深さへ同じ分岐数を割り当てるとは限らない。

棄却が起きやすい位置へ多くの分岐 予算を与える方がキャッシュ ヒット率を上げられるため、後述の最適化で分岐 形状を変える。

### 4. Tree Attentionで複数branchを一括計算する

分岐を1本ずつautoregressiveに計算すると、分岐数Nに比例して端末側 計算 時間が増え、クラウド待ち時間へ収まらない。

AceSpecは複数分岐を1 sequenceへパックし、**木構造注意機構 マスク（Tree 注意機構 Mask）**を使って1 並列 forwardへまとめる。

マスクは大きく3領域に分かれる。

- **共有 接頭部**: すべての分岐が既にverifiedな過去文脈を参照できる。
- **主な-経路 接頭部**: 分岐が分岐する位置までの主な 連鎖だけ参照する。
- **分岐 suffix**: 各分岐は自分のancestorだけを見る。

これにより分岐同士が未来情報を混ぜず、複数分岐 状態をGPU並列性で同時に作れる。

論文でいう`O(1)`は、このような並列 構築や後述検索の観点で分岐数に対する順次 loopをcritical 経路から外すという意味であり、**推論全体が絶対的な定数時間になるという意味ではない**。

### 5. branchのKV/stateをprobabilistic cacheへ保存する

作成した分岐ごとに、そこから推論を続けられる状態を端末側 メモリへ保持する。

概念的には

`(reject position, resampled token) → precomputed branch state`

という検索 表になる。

このキャッシュを論文は**確率的状態 キャッシュ（確率的 状態 キャッシュ）**として扱う。

「確率的」というのは状態自体が曖昧だからではなく、どの棄却 結果が来るか分からないので、確率の高い結果を限られたメモリ/計算 予算内で先回りキャッシュするという意味である。

### 6. cloudはreject位置とtarget distributionを返す

クラウド 対象は主な 連鎖を検証する。

受理できなくなった位置では、クラウド側で最終sampleまで完結させて長い状態を返すのではなく、

- 棄却 position
- 対象 確率 分布の必要部分

を端末側へ返す。

完全な vocabulary 分布は巨大なので、下りでは疎/簡潔 表現にする。

上りはトークン 索引中心、下りは必要な対象 分布中心という**非対称プロトコル**で、双方向とも通信量を抑える。

### 7. edge側でlocal resamplingする

端末側はクラウドから受け取った対象 分布を使い、投機 サンプリングで必要な再標本化をローカルに行う。

ここで正しいトークン `X` が決まったとする。

端末側 キャッシュに

`(reject position, X)`

に対応する分岐があれば、その分岐 状態へ切り替える。

キャッシュ 検索自体は鍵 検索なので`O(1)`に近い。

これが論文のいう**定数時間状態 recovery（O(1) 状態 recovery）**である。

ただし重要な注意がある。

> `O(1)`なのはキャッシュ ヒットした後の状態 選択であり、分岐を事前に作る計算もWAN 応答も無くなるわけではない。

### 8. cache missなら従来通りrollbackする

正しいresampled トークンの分岐を事前に作れていなければ、AceSpecでも巻き戻しが必要になる。

その場合はinvalid KVを戻し、正しいトークンから順次 re-下書きする。

したがってAceSpecの目的は巻き戻しを数学的に完全排除することではなく、**有限計算 予算でキャッシュ-ヒット 確率を最大化し、高価なWAN 巻き戻しの発生頻度を下げる**ことである。

## treeを大きくすればよいわけではない

分岐を大量に作ればキャッシュ ヒット率は上がる。

しかし端末側 計算とメモリには限界があり、クラウドの応答が返るまでに木構造 構築を終えられなければ次パイプライン 往復を遅らせる。

AceSpecはここを二段階最適化で決める。

### Network-Aware Budgeting

まず現在の

- WAN RTT
- クラウド 検証時間
- 端末側 計算 スループット

から、クラウド turnaround 窓内に隠せる分岐 計算量の上限を求める。

WANが遅ければ端末側に長い空き時間があるので多く分岐を作れる。WANが速ければ分岐 構築 予算を小さくする。

つまり、**ネットワーク 遅延を単なる損失ではなく投機 計算を行う時間予算として利用する**。

### Task-Aware Shape Allocation

次に、その総分岐 予算をどの深さへ配るか決める。

主な 連鎖の早い位置で棄却されると、それ以降の下書きが全部無効になるためpenaltyが大きい。一方、各深さで代替 トークンの確率分布も異なる。

そこでLagrange multiplierを使った最適化で、分岐 分岐を一律ではなくnon-uniformに配分する。

要するに、

> 「外れやすく、外れた時の損失が大きい場所へ分岐を多く置く」

という資源 割当を数理的に行う。

## なぜnucleus sampling対応が重要なのか

端末側-クラウド システムでは通信を減らすためgreedy デコードだけを扱う研究もある。

greedyなら対象が選ぶトークンは1つなのでプロトコルは単純になる。

しかし一般対話 生成ではtemperatureやtop-pを使ったstochastic サンプリングが必要になる。

nucleus サンプリングでは下書き モデルと対象 モデルの分布差から棄却/resampleが増えやすく、対象 分布の情報も必要になる。

AceSpecは疎 下り 分布とローカル 再標本化を使い、**stochastic サンプリングを維持したままWAN 巻き戻しを抑える**ことを狙う。

## 評価

### hardware / network

実験は端末側側にNVIDIA AGX Orin、クラウド側にA100-分類 GPU環境を使い、WAN 帯域と遅延を制御して行う。

比較対象は同期投機 デコードや既存端末側-クラウド パイプライン方式。

### 最大3.52× throughput

見出し結果では比較対象に対し最大**3.52× スループット 高速化倍率**を報告する。

この改善は対象 モデルを3.52倍高速化したものではない。

主因は、

- WAN待ちと端末側 分岐 構築を重ね合わせ
- 棄却後の順次 redraftをキャッシュ ヒットで回避
- 完全な 木構造をWAN送信しない

ことで、通信 空白を減らしたことにある。

### 50 Kbpsでもnear-peak performance

論文はWAN 帯域を極端に**50 Kbps**まで絞った条件でも、ピークに近い推論 性能を維持したと報告する。

ここで「50 KbpsでもLLMの全データを高速転送できる」という意味ではない。

AceSpecはそもそもWANへ巨大活性値や完全な 木構造を流さず、主な-連鎖 索引と疎 分布に通信内容を縮小している。そのためスループットがraw 帯域へ強く依存しにくくなる。

## 既存研究との差

### split inferenceとの違い

分割 推論は層途中の隠れた 活性値を端末側-クラウド間で送る。テンソルは大きく、WAN 帯域が細いと通信 wallが出る。

AceSpecはトークン単位 投機 デコードなのでWAN データを小さくする。

### vanilla speculative decodingとの違い

通常の投機 デコードは対象と下書きが同じserver内にあり、高速interconnectを前提とする。棄却後の状態 synchronization 費用が小さい。

AceSpecはWAN RTTを主problemとして扱う。

### asynchronous single-chain方式との違い

PicoSpec等は端末側を先へ走らせWAN 遅延を隠すが、単一 連鎖が棄却されると先読み全体が無効になる。

AceSpecは**複数棄却 結果を端末側だけで分岐 キャッシュする**ため、対象 結果に応じてローカル 状態を切り替えられる。

### naive tree speculationとの違い

分岐 木構造全体をクラウドへ送ればWAN データが増える。

AceSpecは木構造を端末側 recovery専用キャッシュとして使い、クラウドへは主な 連鎖しか送らない。

## 限界と適用境界

- **端末側側に余剰計算が必要。** 端末側 SLMがすでに飽和している場合、分岐生成を無料で重ね合わせできない。
- **状態 キャッシュ メモリが必要。** 分岐数を増やすほどKV/状態 footprintも増える。
- **キャッシュ 未検出は残る。** 予測していない棄却 結果では巻き戻し/re-下書きが必要。
- **下書き 分布を代理にする。** 対象と下書きの分布差が大きいと、間違った分岐へ予算を使う可能性がある。
- **WAN条件で最適予算が変わる。** RTT/帯域が急変する環境ではre-最適化が必要。
- **50 Kbps 見出し結果はプロトコル データが小さい条件の結果。** 任意の大きい side-channel データも50 Kbpsで問題ないという意味ではない。
- **`O(1)`はローカル 検索。** 分岐 構築、クラウド 検証、ネットワーク 応答まで定数時間になるわけではない。
- **端末側/クラウド両方で投機 プロトコル実装が必要。** 単純なOpenAI-style 遠隔 APIだけでは状態/分布 exchangeが難しい。

## 実装上の含意

AceSpecの一般化しやすい考え方は、分散 投機 実行でfailure recoveryを**失敗後に計算するのではなく、ネットワーク待ち時間中に先回り計算する**ことである。

特にWAN環境ではRTTを完全に消すことはできない。ならばその待ち時間をローカル 計算 窓として使い、巻き戻し可能性が高い状態をキャッシュする方がよい。

また木構造 投機を分散 システムへ持ち込む時、木構造全体をネットワーク越しに送る必要はない。**計算用木構造と通信 経路を非対称にする**ことで、ローカル redundancyをWAN 帯域へ漏らさない設計が重要になる。
