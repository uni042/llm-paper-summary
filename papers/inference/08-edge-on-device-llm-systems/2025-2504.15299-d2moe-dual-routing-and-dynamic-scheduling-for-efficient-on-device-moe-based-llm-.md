# D²MoE: Dual Routing and Dynamic Scheduling for Efficient On-Device MoE-based LLM Serving

> native routerが選んだexpertごとにINT2/3/4のどれで実行するかを追加routerで決め、deviceごとのSSD読込・GPU計算時間に合わせてweight転送と計算を重ねるedge向け方式。

## 概要
D²MoEは、expertを「使う/使わない」だけでなく、**そのexpertを何bitで読み込むか**までtokenごとに選び、SSD/CPU→GPU転送と計算をdevice条件に合わせて組み立てるedge向けruntimeである。

native MoE routerがexpert IDを決め、その後のbit-width routerが必要精度を選ぶ二段階構成なので、論文名の `Dual Routing` は**expert選択とprecision選択を別々のrouterで行う**ことを指す。

## 手法のあらまし

### 1. INT2 / INT3 / INT4を完全な別copyとして保存しない

D²MoEの `Matryoshka Weight Quantization (MWQ)` は、INT2、INT3、INT4を三つの完全なweight copyとして持たない。

低bit表現を土台にして追加bitを差分として保存し、

`INT2 + 追加情報 = INT3`

`INT3 + 追加情報 = INT4`

のように復元する。

論文ではこの入れ子構造を `nested residual` と呼ぶ。狙いは、**複数precisionを切り替えられる状態を保ちながら保存量とSSD I/Oを三重化しないこと**である。

例えばINT4版を完全copyとして別保存すると、INT2で十分なtokenでもINT4全体を読み込むか、precisionごとに重複weightを持つ必要がある。MWQではまず共通する低bit部分だけを読み、必要なtokenでだけ追加bitを足してINT3/4へ拡張できる。そのためprecisionを上げるcostも『別expert全体を読み直す』のではなく追加residual分のI/Oとして表現でき、bit-width routerの動的判断をstorage側で実現しやすい。

### 2. `bit-width router`：選ばれたexpertを何bitで実行するか決める

native MoE routerが「どのexpertを使うか」を決めるのに対し、bit-width routerは **そのexpertをINT2 / INT3 / INT4のどれで実行するか** を決める。

入力tokenの状態とexpert重要度から、品質への影響が大きい場合は高bit、影響が小さい場合は低bitを選ぶ。

このrouterはC4で追加学習するため、完全training-freeではない。

### 3. DeviceごとにSSD読込時間と計算時間を実測する

### 3. DeviceごとにSSD読込時間と計算時間を実測する

この実測は単なるbenchmark表作成ではなく、後段のruntime schedulerが使うcost modelになる。各precisionについてload時間とcompute時間が分かれば、現在expertの計算が終わるまでに次expertのどのbitまで先読みできるかを見積もれる。余分な高bit residualを読んで品質を上げてもpipelineを止めない条件と、低bitへ落とさないとI/O bubbleが生じる条件をdeviceごとに区別できる。

各bit幅について、

- そのexpert weightをSSD / host側から準備する時間
- そのbit幅でGPU計算する時間

を事前に測る。

RTX 3060のようなPCIe＋SSD構成と、Jetsonの共有memory構成では最適なprecisionや転送量が違うため、**同じpolicyを全deviceへ固定しない**。

profiling結果は、どのexpert-bitを先にloadすればGPU計算とI/Oの終了時刻を近づけられるかを決める材料になる。SSD読出しが遅いdeviceでは低bit化でtransfer byteを減らす価値が高く、計算が相対的に遅いdeviceでは追加bitを読み込んでもそのI/Oを現在のGEMM裏へ隠せる場合がある。つまりprecisionは品質だけでなく、その端末のI/O時間とcompute時間の比率を変えるschedule変数でもある。

### 4. よく使うexpertの重要bitから優先して保持・転送する

利用頻度が高いexpertについて、まず低bit版を確保し、memoryや帯域に余裕があれば追加bitを読み込んで高精度化する。

論文ではこの優先順位を `Hottest-Expert-Bit-First (HEBF)` と呼ぶ。

memoryに余裕があるならhot expertを高bitで保持し、厳しいときは低bit版だけを残すため、**expert単位ではなくbit単位でmemory budgetを配れる**。

この粒度なら『expert Aを残すか捨てるか』の二択より柔軟である。頻出expertはINT2のbaseを常駐させ、追加bitだけ必要に応じて保持すれば、最低限のhit率を確保しながら空きmemoryを品質改善へ使える。逆に低頻度expertへ高bit residualを常駐させると、ほとんど使わないbyteが貴重なedge memoryを占有するため、HEBFは利用頻度とprecisionの両方をcache価値へ反映する。

### 5. SSD I/OとGPU計算を重ねる

現在のexpertをGPUで計算している間に、次に必要なweightをSSD/CPU側から読み込む。

低bit化は単なるVRAM削減ではなく、**SSD→GPUで運ぶbyte数を減らして、weight読込を現在の計算時間内へ隠しやすくする手段**としても働く。

## 評価

### まず見るところ
- **結論:** expertごとにINT2/3/4を選び、device帯域に合わせてI/O/計算をscheduleすると、低VRAM laptopでもMoEを実用速度で動かせる。
- **品質:** 近似量子化だが、標準設定では高bit baselineにかなり近い。
- **実速度:** RTX 3060 / Jetson実機で既存edge offloadよりthroughput改善。
- **I/O:** **Samsung 970 EVO SSDからのweight readを含む実機評価**。
- **注意点:** bit-width routerの学習、device profiling、低bit weightを計算用に戻す処理のoverheadが必要。

### 実機構成

| 環境 | 主な構成 |
|---|---|
| Laptop | RTX 3060 6GB + i7-11800H + RAM 32GB |
| SSD | Samsung 970 EVO、read約3.5GB/s |
| Edge | Jetson AGX Orin 64GB |

モデルはLLaMA-MoE-3.5BとMixtral 8x7Bを使用する。

### 品質

| モデル | 高精度baseline | D²MoE |
|---|---:|---:|
| LLaMA-MoE PPL | 14.55 | 14.58 |
| Mixtral PPL | 4.04 | 4.09 |
| Mixtral PIQA | 82.4 | 82.29 |

標準設定では量子化による品質低下は小さい。

### RTX 3060でのthroughput

| 比較対象 | D²MoEの改善 |
|---|---:|
| EdgeMoE / LLaMA-MoE系 | 1.14〜1.39倍 |
| MoQE-DynaIO | 1.42〜3.37倍 |

memory使用量も既存方式比33〜53%削減した。

### memory制約が厳しい場合

Hold-in-Memory-AWQは2500MBで94.3 token/s。一方D²MoEは1600MBで89.14 token/sを維持する。

さらに他方式がmemory不足で動かせないMixtral条件でも38.07 token/sを報告する。ここでは最高速度より、**より小さいmemory budgetでモデルを成立させること**が重要である。

### runtime overhead

| 項目 | overhead |
|---|---:|
| bit-width router compute | 0.22〜0.28% |
| router memory | 0.12〜0.53% |
| router latency | 1.04〜1.67% |

一方MWQの低bit weightを計算用に戻す処理はより重く、Mixtralではrequest数によって計算overheadが約16〜21%になる。したがって低bit化でI/Oを減らしても、この処理が遅いと利得を食う。
