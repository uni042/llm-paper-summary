# D²MoE: Dual Routing and Dynamic Scheduling for Efficient On-Device MoE-based LLM Serving

> ネイティブ ルータが選んだエキスパートごとにINT2/3/4のどれで実行するかを追加ルータで決め、端末ごとのSSD読込・GPU計算時間に合わせて重み転送と計算を重ねるedge向け方式。

## 概要
D²MoEは、エキスパートを「使う/使わない」だけでなく、**そのエキスパートを何ビットで読み込むか**までトークンごとに選び、SSD/CPU→GPU転送と計算を端末条件に合わせて組み立てるedge向けランタイムである。

ネイティブ MoE ルータがエキスパート IDを決め、その後のビット-width ルータが必要精度を選ぶ二段階構成なので、論文名の `Dual Routing` は**エキスパート選択と精度選択を別々のルータで行う**ことを指す。

この分離により、同じモデルでも端末の記憶容量や読み出し速度が違えば、必要なビット幅と配置を個別に選べる。精度を保つべきエキスパートと転送を軽くできるエキスパートを区別し、限られた資源の中で計算と読み出しの待ち時間を同時に抑える設計である。

## 手法のあらまし

### 1. INT2 / INT3 / INT4を完全な別copyとして保存しない

D²MoEの `Matryoshka Weight Quantization (MWQ)` は、INT2、INT3、INT4を三つの完全な重み コピーとして持たない。

低ビット表現を土台にして追加ビットを差分として保存し、

`INT2 + 追加情報 = INT3`

`INT3 + 追加情報 = INT4`

のように復元する。

論文ではこの入れ子構造を `nested residual` と呼ぶ。狙いは、**複数精度を切り替えられる状態を保ちながら保存量とSSD I/Oを三重化しないこと**である。

例えばINT4版を完全コピーとして別保存すると、INT2で十分なトークンでもINT4全体を読み込むか、精度ごとに重複重みを持つ必要がある。MWQではまず共通する低ビット部分だけを読み、必要なトークンでだけ追加ビットを足してINT3/4へ拡張できる。そのため精度を上げる費用も『別エキスパート全体を読み直す』のではなく追加residual分のI/Oとして表現でき、ビット-width ルータの動的判断を保存領域側で実現しやすい。

### 2. `bit-width router`：選ばれたexpertを何bitで実行するか決める

ネイティブ MoE ルータが「どのエキスパートを使うか」を決めるのに対し、ビット-width ルータは **そのエキスパートをINT2 / INT3 / INT4のどれで実行するか** を決める。

入力トークンの状態とエキスパート重要度から、品質への影響が大きい場合は高ビット、影響が小さい場合は低ビットを選ぶ。

このルータはC4で追加学習するため、完全training-freeではない。

### 3. DeviceごとにSSD読込時間と計算時間を実測する

この実測は単なるベンチマーク表作成ではなく、後段のランタイム スケジューラが使う費用 モデルになる。各精度について読み込み時間と計算時間が分かれば、現在エキスパートの計算が終わるまでに次エキスパートのどのビットまで先読みできるかを見積もれる。余分な高ビット residualを読んで品質を上げてもパイプラインを止めない条件と、低ビットへ落とさないとI/O bubbleが生じる条件を端末ごとに区別できる。

各ビット幅について、

- そのエキスパート 重みをSSD / ホスト側から準備する時間
- そのビット幅でGPU計算する時間

を事前に測る。

RTX 3060のようなPCIe＋SSD構成と、Jetsonの共有メモリ構成では最適な精度や転送量が違うため、**同じ方針を全端末へ固定しない**。

プロファイリング結果は、どのエキスパート-ビットを先に読み込みすればGPU計算とI/Oの終了時刻を近づけられるかを決める材料になる。SSD読出しが遅い端末では低ビット化で転送 byteを減らす価値が高く、計算が相対的に遅い端末では追加ビットを読み込んでもそのI/Oを現在のGEMM裏へ隠せる場合がある。つまり精度は品質だけでなく、その端末のI/O時間と計算時間の比率を変える予定変数でもある。

### 4. よく使うexpertの重要bitから優先して保持・転送する

利用頻度が高いエキスパートについて、まず低ビット版を確保し、メモリや帯域に余裕があれば追加ビットを読み込んで高精度化する。

論文ではこの優先順位を `Hottest-Expert-Bit-First (HEBF)` と呼ぶ。

メモリに余裕があるなら高頻度 エキスパートを高ビットで保持し、厳しいときは低ビット版だけを残すため、**エキスパート単位ではなくビット単位でメモリ budgetを配れる**。

この粒度なら『エキスパート Aを残すか捨てるか』の二択より柔軟である。頻出エキスパートはINT2のbaseを常駐させ、追加ビットだけ必要に応じて保持すれば、最低限のhit率を確保しながら空きメモリを品質改善へ使える。逆に低頻度エキスパートへ高ビット residualを常駐させると、ほとんど使わないbyteが貴重なedge メモリを占有するため、HEBFは利用頻度と精度の両方をキャッシュ価値へ反映する。

### 5. SSD I/OとGPU計算を重ねる

現在のエキスパートをGPUで計算している間に、次に必要な重みをSSD/CPU側から読み込む。

低ビット化は単なるVRAM削減ではなく、**SSD→GPUで運ぶbyte数を減らして、重み読込を現在の計算時間内へ隠しやすくする手段**としても働く。

## 評価

### まず見るところ
- **結論:** エキスパートごとにINT2/3/4を選び、端末帯域に合わせてI/O/計算を予定すると、低VRAM laptopでもMoEを実用速度で動かせる。
- **品質:** 近似量子化だが、標準設定では高ビット 比較対象にかなり近い。
- **実速度:** RTX 3060 / Jetson実機で既存edge オフロードよりスループット改善。
- **I/O:** **Samsung 970 EVO SSDからの重み readを含む実機評価**。
- **注意点:** ビット-width ルータの学習、端末 プロファイリング、低ビット 重みを計算用に戻す処理のオーバーヘッドが必要。

### 実機構成

| 環境 | 主な構成 |
|---|---|
| Laptop | RTX 3060 6GB + i7-11800H + RAM 32GB |
| SSD | Samsung 970 EVO、read約3.5GB/s |
| Edge | Jetson AGX Orin 64GB |

モデルはLLaMA-MoE-3.5BとMixtral 8x7Bを使用する。

### 品質

| モデル | 高精度比較対象 | D²MoE |
|---|---:|---:|
| LLaMA-MoE PPL | 14.55 | 14.58 |
| Mixtral PPL | 4.04 | 4.09 |
| Mixtral PIQA | 82.4 | 82.29 |

標準設定では量子化による品質低下は小さい。

### RTX 3060でのthroughput

| 比較対象 | D²MoEの改善 |
|---|---:|
| EdgeMoE / LLaMA-MoE系 | 1.14〜1.39倍 |
| MoQE-DynaIO | 1.42〜3.37倍 |

メモリ使用量も既存方式比33〜53%削減した。

### memory制約が厳しい場合

Hold-in-メモリ-AWQは2500MBで94.3 トークン/s。一方D²MoEは1600MBで89.14 トークン/sを維持する。

さらに他方式がメモリ不足で動かせないMixtral条件でも38.07 トークン/sを報告する。ここでは最高速度より、**より小さいメモリ budgetでモデルを成立させること**が重要である。

### runtime overhead

| 項目 | オーバーヘッド |
|---|---:|
| ビット-width ルータ 計算 | 0.22〜0.28% |
| ルータ メモリ | 0.12〜0.53% |
| ルータ 遅延 | 1.04〜1.67% |

一方MWQの低ビット 重みを計算用に戻す処理はより重く、Mixtralではリクエスト数によって計算オーバーヘッドが約16〜21%になる。したがって低ビット化でI/Oを減らしても、この処理が遅いと利得を食う。
