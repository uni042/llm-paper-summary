# Cache-Resident LLM Inference in GB-Scale Last-Level Caches

> GB級のCPU last-level cacheへmodel weightを常駐させ、weight計算とattention/KV stateを別socketへ分離し、core-localな配置と細粒度同期でDRAM往復とoperator barrierを減らすCPU LLM inference system。

## 問題設定

CPUでLLMをdecodeすると、GEMVなどの計算そのものよりmodel weightやKV cacheをmemory hierarchy上で動かすcostが支配的になりやすい。近年のserver CPUでは3D-stacked cache等によりsocketあたりGB級のlast-level cache（LLC）が可能になり、model weightの一部をDRAMではなくon-chip cacheへ常駐させられる余地がある。

しかし単純にpipeline parallelismを深くして各stageのweightをcacheへ収めるだけでは、同時に流すtoken/request数が増えてKV cache footprintも膨らみ、weightとKVが同じcacheを奪い合う。またweightがcache-residentになって1 operatorが短くなると、従来runtimeのoperator単位global barrierやthread scheduling overheadが相対的に大きくなる。

本論文はこの2つを、**weightとKV/attentionのresource分離**と、**cache topologyに合わせた実行・同期**で解く。

## 新規性

- weight-centric operatorとattention/KV stateを別socketへ置く weight–attention（WA）separationにより、増え続けるKV cacheがweight-resident LLCをpolluteするのを防ぐ。
- socket内ではphysical coreをtensor-parallel resource domainとして扱い、weight shardを近いLLC sliceへfirst-touch配置し、activationはL1へ複製して高頻度reuseをL1に閉じ込める。
- operator boundaryの一括barrierではなく、実際のdata dependencyに沿ったsub-operator coordinationと階層同期を使い、cache line bouncingを抑える。
- cache-resident kernelが短くなった後に顕在化するgeneric runtime overheadを避けるため、per-socket static thread poolを使う。

## 手法

### 1. WeightとAttention/KVをsocketで分ける

linear projectionやFFNなど大きなweightを読むoperatorをweight socketに、KV cacheを保持してattentionを計算する処理をattention socketに置く。これにより、contextやbatchが増えてKV footprintが膨らんでも、同じLLC上のresident weightを追い出しにくくする。

この分離は常に得ではなく、追加socketとcoordination costを使う。したがってcache pressureが小さい3B・small batchでは利益が小さく、大きいmodelやlong contextで効果が増える。

### 2. LLCをlarge-data streaming layer、L1をactivation reuse layerとして使う

INT8 QKV projection weightのような大きいdataはLLCからcoreへ1回ずつstreamし、KB級のactivation vectorは各coreのL1へ複製してreuseする。96 coreへweight output channelを分けることで、各coreが担当するweight shardを近接LLC sliceへ収める。

weight warmup時のfirst-touchでhome cache bankを決め、threadを固定coreへpinすることで、毎token同じcoreが同じweight shardへ近い経路でアクセスする。

### 3. Static thread poolと階層同期

OpenMPのdynamic schedulingやglobal barrierは、operatorが数百µs級まで短くなると無視できない。そこでsocketごとに固定thread poolを作り、thread migrationを禁止する。

同期も全coreが1個のcounterを更新するのではなく、CCD内でlocal counterへ集約し、その代表だけが次段へ進むtree型にする。これによりcross-CCDのcache-line ownership transferを抑える。

### 4. Pipeline node間はRDMAでembeddingだけを送る

rack node間ではInfiniBand RDMAを使い、固定pipeline topologyとpre-registered bufferでkernel network stackやconnection setupを避ける。weight自体をnode間で毎token移すのではなく、stage間の小さいactivationを送る。

## 評価条件

- 4 rack-node CPU cluster
- CPU: AMD EPYC 9684X、各node 2 socket
- 各socket: 96 core、aggregate LLC 1152MB
- memory: 各node 1.5TB DDR5
- network: NVIDIA ConnectX-7、RDMA
- quantization: weight・KV cacheともINT8
- model: Llama-3.2-3B、Llama-2-7B、Qwen3-8B。Llama-2-70Bはmodel-based extrapolationにも利用
- baseline: 同じhardware・checkpoint・quantizationのllama.cpp
- context: 1024〜4096
- batch: 1〜32

`evaluation_type: mixed` としたのは、3B / 7Bは実machineでend-to-end測定している一方、より大きいmodelを含む広いgridの最大値はvalidated analytical modelによるextrapolationだからである。

## 主要結果

### 実測end-to-end

context length 4096で、llama.cppに対してTPOTを **2.04〜11.51倍**高速化した（Table 2、§6.1）。

- Llama-3.2-3B: batch 1で11.51×、batch 32で2.83×
- Llama-2-7B: batch 1で10.43×、batch 32で2.04×

batchが増えるとbaseline側でもweight loadingをamortizeできるため、相対speedupは縮む。

### model-based extrapolation

実測から検証したanalytical modelを大きいmodel・context・batchへ展開した結果では、最大 **13.9× TPOT**、**12.5× throughput** speedupを報告する（Fig. 8、§6.3）。これは実測最大値ではなくextrapolationなので区別する必要がある。

### component ablation

- specialized static thread pool: geomean 1.05〜1.16×、small batchで最大1.56×（Fig. 10、§6.4）。
- WA separation: context 4096で3Bはgeomean 1.00×、7Bは1.13×、70B extrapolated caseは1.16×。cache pressureが高いほど有効で、常に速くなる機構ではない（Fig. 9、§6.5）。
- 4 pipeline nodeのRDMA通信は3B decodeで約50µs、end-to-end latencyの約0.5%と報告する（§4.4）。

## 既存研究との差

### FlexGenなどのoffloadとの違い

FlexGenはGPU・CPU DRAM・NVMeを跨いでweight / activation / KVを配置し、capacity不足を外部memoryで補う。本論文は逆に、GB級LLCを**DRAMより内側の高速tier**として積極利用し、weightをon-chipに留めることが中心である。

### CPU-GPU heterogeneous inferenceとの違い

HeteGenやTwinPilotsのようにCPUとGPUへoperatorを分担するのではなく、CPU clusterだけでcache topologyをresource hierarchyとして使う。主な最適化対象はPCIe転送ではなくLLC/DRAM trafficと同期overheadである。

### Prefill/decode disaggregationとの違い

DistServe等はprefillとdecodeを別GPU poolへ分ける。本論文のWA separationはdecode内部でweight-centric operatorとattention/KV stateを別socketへ分けるので、phase分離とは粒度が異なる。

## 限界

- 実機end-to-end評価はLlama-3.2-3BとLlama-2-7Bまでで、大型modelのheadline最大値はanalytical modelによる外挿。
- current prototypeはdecode TPOTを中心に最適化し、prefillの詳細最適化はfuture work。
- GB級LLCを持つEPYC platformに強く依存し、通常の小容量LLC CPUへそのまま一般化できない。
- WA separationはsocket budgetを増やすため、latencyを改善してもper-socket throughput efficiencyは下がり得る。
- continuous batching、online KV reclamation、MoE routingは今後の課題としている。
- 2026-09-08の一次資料確認では公式code repositoryを確認できなかった。

## 一般的な実装上の含意

memory hierarchyに新しい高速tierが増えたとき、単に「そこへweightを置く」だけでは不十分である。weightをresidentにすると次にKV cache interferenceやruntime barrierがcritical pathへ出てくるため、**data placement・operator分離・thread affinity・synchronizationを同じcache topologyに合わせる**必要がある。

特に大容量LLCや将来のon-chip SRAMを使うsystemでは、weightと成長するstateを同じcapacity poolへ混在させないresource isolationが重要になる。
