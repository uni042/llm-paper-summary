# GB級最終段キャッシュに重みを常駐させるCPU推論基盤

## 概要

この研究は、GPUではなく大容量の最終段キャッシュ（last-level cache; LLC）を備えたサーバCPUを使い、言語モデルの逐次生成を高速化する実行方式を提案する。モデル重みを毎トークンDRAMから読み直すのではなく、複数ソケットのGB級LLCへ分割して常駐させる。ただし重みをキャッシュへ収めるだけでは十分でない。要求ごとに増える鍵・値キャッシュ（KVキャッシュ）が同じLLCを使うと重みを追い出し、キャッシュ常駐の利益が失われる。さらに計算が速くなるほど、演算子ごとの全体同期や一般的なスレッド管理の費用が無視できなくなる。

提案は二つの柱からなる。第一は**重み・注意分離（Weight–Attention Separation; WA分離）**であり、重みを読む射影・前向きネットワークを担当するソケットと、要求ごとのKV状態を持つ注意計算ソケットを分ける。第二は**演算子内部の依存関係に沿う非同期処理（sub-operator asynchronicity）**であり、全ての注意頭が終わるまで一括して待つのではなく、各頭の出力が準備できた時点で依存先の計算を進める。これを固定スレッドプール、キャッシュ局所配置、階層的な同期で支える。

著者はAMD EPYC 9684Xを使う複数CPUノードの試作を実装し、同じ計算資源を割り当てたllama.cppと比較する。Llama-3.2-3BとLlama-2-7Bの実機エンドツーエンド評価では、出力トークン当たり時間（time per output token; TPOT）が2.04～11.51倍短くなった。一方、最大13.9倍という別の値は、実測で検証した解析モデルを大きなモデルや負荷条件へ適用した**外挿結果**である。実測値とモデル予測値を分けて読む必要がある。

## 問題設定：重み常駐を阻む二つの壁

Transformerの逐次生成では、各トークンについて全層の線形射影、注意、前向きネットワークを実行する。線形射影と前向きネットワークは静的な重みを繰り返し読むが、単一トークンの行列・ベクトル積は演算量に対する読み込みバイト数が大きい。大きなバッチで重みを再利用すれば効率が改善するものの、低遅延のオンライン配信では無制限にバッチを増やせない。したがって重みをDRAMより高帯域のLLCに保持できれば、同じ演算でもメモリ待ちを減らせる。

近年の3次元積層キャッシュを持つサーバCPUでは、ソケット当たり1GB前後のLLCを利用できる。ただしLLCは重み専用ではない。注意計算に必要なKVキャッシュは要求ごとに異なり、文脈長と同時要求数に比例して増える。通常のパイプライン並列では、重みを各段へ小分けするため段数を増やすが、パイプラインを埋めるため同時進行中の要求も増える。結果として、各段で保持するKVの総量が減らず、重みをキャッシュから追い出す可能性がある。

原著はこの現象をKVキャッシュ圧力の逆説として定式化する。全層数を`L`、パイプライン段数を`p`、バッチを`B`、文脈長を`S`とすると、段当たりの層数は`L/p`になるが、パイプラインを埋めるための同時要求数は少なくとも`p`に比例する。段当たりKV容量は概念的に`(L/p)×p×B×S=L×B×S`となり、`p`を増やしても減らない。重みだけは段数に応じて小さくなるため、重みとKVを同じLLCへ置く方式では、段数を増やしてもキャッシュ常駐を保証できない。

もう一つの壁は同期である。重みがLLCに収まって行列・ベクトル積が短くなると、従来の演算子単位の全体バリアやスレッドスケジューラの費用が相対的に増える。各注意頭は独立に計算できる部分が多いのに、全ての頭の計算が完了するまで次の演算子を始めない方式では、速く終わったコアが待機する。キャッシュ常駐の効果を引き出すには、メモリ配置と同期粒度の両方を変える必要がある。

## 手法

### 重み中心演算子と注意・KV状態を別ソケットへ分離

QKV射影と前向きネットワーク（FFN）は、モデルの固定重みを繰り返し参照する。これらを**重みノード**に置き、KVキャッシュを必要とする注意演算を**注意ノード**に置く。重みノードではKVを保持しないため、文脈が長くなっても重み用LLCがKVによって追い出されにくい。注意ノードは要求ごとのKV状態を管理し、対応する問い合わせを受けて注意計算を実行する。

各生成系列は特定の注意ノードへ対応付けられ、KV状態の所有者が明確になる。重みノードの射影結果を対応する注意ノードへ送り、注意結果を後続の重み演算へ渡す。文脈が長くなりKV容量が足りなくなれば、注意ノードを増やして対応できる。重み用パイプラインの段数を深くせずにKV容量を増やせる点が、単純な層分割と異なる。

ただしソケットを分ければ、射影結果などの活性値を追加で転送する必要がある。KVが小さい場合は同じソケットへ置いた方が資源効率が良い可能性がある。原著はWA分離を必須ではなく選択可能な設計とし、KV圧力が高い条件では重み常駐を守る利点が大きくなる一方、低負荷では専用ソケットを増やす費用が利益を上回る可能性を認める。

### キャッシュ階層に合わせた行列・ベクトル積

各ソケット内では物理コアごとに出力チャネルを分割し、担当する重み片を繰り返し読む。大きな重み行列をL1やL2へ全て収めるのではなく、LLCを重みの供給層として使い、KB級の活性値ベクトルは各コアのL1に複製する。原著の例では4096×4096のINT8射影行列が3個で約48MBとなるが、96コアへ分ければ1コア当たり約512KBの重み片になり、近いLLCスライスから効率よく読める。

重み片をどのLLCバンクへ置くかも重要である。初期化時に各コアが自分の重み片へ最初にアクセスすることで、近いキャッシュバンクに配置されやすくする。以後も同じスレッドを同じ物理コアへ固定し、毎トークン同じ重み片を担当させる。スレッドがコア間を移動すると、重みのホームバンクが遠くなったりキャッシュ行の所有権が移動したりして遅延が増えるため、固定配置を重視する。

注意側では、KVブロックを小さな区画に分けて読み込み、注意スコアと値の集約を大きな中間行列として実体化せずに計算する。問い合わせベクトルは私有キャッシュに置き、KVブロックはLLCから順次供給する。重み中心演算子と注意演算子では参照するデータの再利用特性が違うため、両者に同じキャッシュ配置規則を適用しない。

### 注意頭ごとの準備完了通知と階層同期

通常の演算子中心の実行では、テンソル並列で分割された全コアが一つの演算子を終えるまで、後続演算子を開始しない。しかし注意頭ごとの計算は独立しているため、ある頭の出力が準備できた時点で、その頭に依存する後続処理を進められる。提案方式は頭ごとの準備完了信号を使い、不要な全体バリアを省く。

一方、前向きネットワークの入力には頭の出力をまとめた埋め込みが必要になるため、全ての同期を消せるわけではない。部分結果を何度もLLCへ書き戻して完全非同期化すると、逆にメモリ転送が増える。そこで著者は、コア間の結果を木構造で段階的に集約する。まず同じキャッシュ複合領域（CCD）内で同期し、その代表だけがソケット全体の同期へ参加する。全コアが一つの原子変数を奪い合う方式より、キャッシュ行の所有権移動を抑えられる。

この設計は同期を完全に禁止するのではなく、真のデータ依存がある位置に限って同期し、同時に余計なLLCへの書き戻しを避ける。短い演算子ほどバリア費用の割合が大きくなるため、重みをLLCに常駐させた後の性能を決める重要な要素となる。

### 固定スレッドプールと分散パイプライン

著者は一般的なOpenMPの動的スケジューリングに代えて、ソケットごとに固定スレッドプールを作る。各スレッドを物理コアへ恒久的に固定し、担当する重み片と処理順を決めておく。毎トークンの処理では一般的なタスクキューを組み直さず、軽い状態遷移で次の演算を進める。これにより短い演算のたびに発生するタスク投入やロック競合を抑える。

クラスタのノード間では、層を分けるパイプライン並列を使い、段階間ではモデル重みではなく活性値を送る。InfiniBandの遠隔直接メモリアクセス（RDMA）を利用し、固定された接続と事前登録バッファで通信設定の費用を抑える。各ノード内では二つのCPUソケットを重み側と注意側へ割り当てる。大きな重みをノード間で毎トークン移動しないことと、KV状態を注意側へ固定することが、通信量とキャッシュ局所性の両方に効く。

## 評価

### 実機構成と比較条件

| 観点 | 原著の条件 |
|---|---|
| CPU | AMD EPYC 9684X、1ソケット96コア、LLC約1.1GB |
| ノード | 2ソケットCPUノードを複数接続したクラスタ |
| 通信 | InfiniBand RDMA、事前登録バッファ |
| 実機モデル | Llama-3.2-3B、Llama-2-7B |
| 大規模モデル | Llama-2-70B等は検証済み解析モデルによる外挿に含まれる |
| 比較 | 同等の計算資源を割り当てたllama.cpp |
| 主な精度形式 | 重み・KVともINT8を用いる構成 |
| 文脈・バッチ | 文脈長1024～4096、バッチ1～32などを評価 |
| 指標 | 出力トークン当たり時間（TPOT）、処理能力、構成要素の寄与 |

実機の値と解析モデルの外挿値を区別することが重要である。モデルサイズが大きくなるほど重みをLLCへ分割配置する段数が増え、KV圧力と同期の両方が変化するため、3B/7Bでの実測を70Bでの実測として扱うことはできない。

### 出力トークン当たり時間の実測

| 実機モデル | バッチ | llama.cppに対するTPOT短縮倍率 | 解釈 |
|---|---:|---:|---|
| Llama-3.2-3B | 1 | 11.51倍 | 小バッチで重み読み込み・同期の削減が大きく効く |
| Llama-3.2-3B | 32 | 2.83倍 | バッチ化で比較対象の重み再利用も改善する |
| Llama-2-7B | 1 | 10.43倍 | より大きなモデルでもキャッシュ常駐が有効 |
| Llama-2-7B | 32 | 2.04倍 | 高バッチでは相対利得が小さくなる |

これらは原著の実機エンドツーエンド評価で、文脈長4096を含む設定の結果である。小バッチで倍率が高いのは、llama.cpp側ではトークンごとに重みを読み込む費用が相対的に大きい一方、提案方式では重みがLLCに常駐しているためである。バッチを増やすと比較対象も重みを複数要求で再利用できるようになり、提案方式との相対差は縮む。最大11.51倍を全バッチ・全モデルの代表値として使わない。

### 解析モデルによる外挿と構成要素除去

| 評価対象 | 結果 | 注意点 |
|---|---|---|
| 検証済み解析モデルによる大規模条件 | TPOT最大13.9倍 | 実機で13.9倍を測ったわけではない |
| 同じ解析モデルによる処理能力 | 最大12.5倍 | モデル・文脈・バッチの広い組合せを予測 |
| 固定スレッドプール | 小バッチで最大1.56倍、幾何平均1.05～1.16倍 | 同期・タスク管理費用を削減 |
| 重み・注意分離、3B | 文脈4096で幾何平均約1.00倍 | KV圧力が小さい場合は利益がない |
| 重み・注意分離、7B | 文脈4096で幾何平均約1.13倍 | KV圧力が増えると効果が出る |
| 重み・注意分離、70B外挿 | 幾何平均約1.16倍 | 実測ではなく解析モデルの条件 |
| ノード間RDMA通信の例 | 3Bデコードで約50マイクロ秒、端点遅延の約0.5% | 固定構成での通信費用の観測 |

WA分離の効果が3Bで約1.00倍にとどまることは重要な負の結果である。重みとKVが同じLLCに収まる場合、分離によって追加ソケットや転送費用を払っても利益がない。一方、モデルが大きく文脈が長くなるとKVが重みを追い出すため、分離が効きやすくなる。したがってWA分離は常時有効な最適化ではなく、キャッシュ圧力と利用可能なソケット数によって選ぶべき機構である。

固定スレッドプールの利益もバッチに依存する。演算子が短い小バッチでは一般的なタスク管理の固定費が目立つため効果が大きいが、計算量が増えると固定費の比率が下がる。著者はこの構成要素除去を通じて、キャッシュ常駐が達成された後に初めて顕在化する同期・スケジューリングの費用を実測している。

## 既存方式との差

GPU・CPU間オフロードを扱う方式は、GPUの容量不足をCPU DRAMやSSDで補い、転送の重なりや配置を最適化する。本研究は逆に、CPU内部のLLCという**DRAMより内側の高速階層**へ重みを常駐させる。GPUとCPUの間で重みを動かす方式ではなく、複数CPUのキャッシュと計算資源を固定配置する方式である。

プリフィルとデコードを別のGPU群へ配置する分離配信とも粒度が違う。本研究のWA分離は、一つのデコード処理の内部で静的重み演算子と動的KV注意演算子を分ける。これによりKV容量を重み用パイプラインの段数から切り離す。一般的なテンソル並列の演算子単位バリアを、注意頭などの真の依存関係に沿った準備完了通知へ置き換える点も特徴である。

## 限界と負の結果

この方式は、ソケット当たりGB級のLLCを持つ特定のCPUと、複数ソケット・ノードを利用できる環境を前提とする。通常の小容量LLCを持つデスクトップCPUでは重みを同じように常駐させられず、11.51倍の実測値を再現できるとは限らない。重みを分割配置するために複数のCPU資源が必要であり、1ソケット当たりの処理能力や電力費用で比較すると別の交換条件が生じる。

実機でのエンドツーエンド測定は3B/7Bモデルを中心とし、13.9倍という最大値は解析モデルの外挿である。70B規模での実際の通信・キャッシュ干渉・故障時の復旧まで実証したものではない。文脈長も主に4096までで、数万～数十万トークンのKV状態、オンラインでの継続バッチ処理、複雑な要求到着、MoEの専門家ルーティングに対する評価は限られる。

WA分離は追加の注意ソケットを必要とし、KV圧力が低い3Bでは幾何平均約1.00倍と利点がほとんどない。細粒度同期も完全な非同期ではなく、前向きネットワークに必要な埋め込みの集約には同期が残る。スレッド固定やキャッシュバンク局所配置は特定のCPUトポロジに合わせた調整が必要で、汎用ランタイムへそのまま移植できるとは限らない。公式コードの公開先も一次資料では確認できず、再現には試作実装の詳細が必要となる。
