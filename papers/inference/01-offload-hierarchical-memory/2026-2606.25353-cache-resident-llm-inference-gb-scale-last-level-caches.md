# Cache-Resident LLM Inference in GB-Scale Last-Level Caches

> GB級のCPU last-レベルキャッシュへモデル重みを常駐させ、重み計算と注意機構/KV状態を別ソケットへ分離し、コア局所な配置と細粒度同期でDRAM往復と演算子バリアを減らすCPU LLM inferenceシステム。

## 問題設定

CPUでLLMをデコードすると、GEMVなどの計算そのものよりモデル重みやKVキャッシュをメモリ階層上で動かすコストが支配的になりやすい。近年のserver CPUでは3D-stackedキャッシュ等によりソケットあたりGB級のlast-レベルキャッシュ（LLC）が可能になり、モデル重みの一部をDRAMではなくon-chipキャッシュへ常駐させられる余地がある。

しかし単純にパイプライン並列性を深くして各段階の重みをキャッシュへ収めるだけでは、同時に流すトークン/リクエスト数が増えてKVキャッシュ使用量も膨らみ、重みとKVが同じキャッシュを奪い合う。また重みがキャッシュ-常駐になって1演算子が短くなると、従来ランタイムの演算子単位全体バリアやスレッドスケジューリングオーバーヘッドが相対的に大きくなる。

本論文はこの2つを、**重みとKV/注意機構の資源分離**と、**キャッシュトポロジに合わせた実行・同期**で解く。

## 新規性

- 重み-中心演算子と注意機構/KV状態を別ソケットへ置く重み–注意機構（WA）分離により、増え続けるKVキャッシュが重み-常駐 LLCをpolluteするのを防ぐ。
- ソケット内では物理コアをテンソル並列資源領域として扱い、重み分割片を近いLLCスライスへ初回アクセス配置し、活性値はL1へ複製して高頻度再利用をL1に閉じ込める。
- 演算子 boundaryの一括バリアではなく、実際のデータ依存関係に沿ったsub-演算子調整と階層同期を使い、キャッシュ行 bouncingを抑える。
- キャッシュ-常駐カーネルが短くなった後に顕在化する一般的ランタイムオーバーヘッドを避けるため、ソケットごと静的スレッドプールを使う。

## 手法

### 1. WeightとAttention/KVをsocketで分ける

線形射影やFFNなど大きな重みを読む演算子を重みソケットに、KVキャッシュを保持して注意機構を計算する処理を注意機構ソケットに置く。これにより、文脈やバッチが増えてKV使用量が膨らんでも、同じLLC上の常駐重みを追い出しにくくする。

この分離は常に得ではなく、追加ソケットと調整コストを使う。したがってキャッシュ圧力が小さい3B・小さいバッチでは利益が小さく、大きいモデルやlong文脈で効果が増える。

### 2. LLCをlarge-data streaming layer、L1をactivation reuse layerとして使う

INT8 QKV射影重みのような大きいデータはLLCからコアへ1回ずつストリームし、KB級の活性値ベクトルは各コアのL1へ複製して再利用する。96コアへ重み出力チャネルを分けることで、各コアが担当する重み分割片を近接LLCスライスへ収める。

重みウォームアップ時の初回アクセスでホームキャッシュバンクを決め、スレッドを固定コアへ固定することで、毎トークン同じコアが同じ重み分割片へ近い経路でアクセスする。

### 3. Static thread poolと階層同期

OpenMPの動的スケジューリングや全体バリアは、演算子が数百µs級まで短くなると無視できない。そこでソケットごとに固定スレッドプールを作り、スレッド移行を禁止する。

同期も全コアが1個のカウンタを更新するのではなく、CCD内でローカルカウンタへ集約し、その代表だけが次段へ進む木型にする。これにより横断-CCDのキャッシュ-行所有権転送を抑える。

### 4. Pipeline node間はRDMAでembeddingだけを送る

ラックノード間ではInfiniBand RDMAを使い、固定パイプライントポロジと事前登録済みバッファでカーネルネットワーク積層や接続設定を避ける。重み自体をノード間で毎トークン移すのではなく、段階間の小さい活性値を送る。

この通信設計が成立するのは、重み分割片を各段階のLLCへ固定常駐させるからである。トークンごとに移動するデータを大きなパラメータではなくembedding/活性値へ限定すれば、ノード間パイプラインを深くしてもネットワークバイトはモデルサイズへ比例しない。事前登録済みバッファと固定peerを使うことでRDMA設定も頻出経路から外し、キャッシュ-常駐演算子を短くした後にネットワーク制御オーバーヘッドが相対的に目立つのを防ぐ。

## 評価条件

- 4ラック-ノード CPUクラスタ
- CPU: AMD EPYC 9684X、各ノード 2ソケット
- 各ソケット: 96コア、集約 LLC 1152MB
- メモリ: 各ノード 1.5TB DDR5
- ネットワーク: NVIDIA ConnectX-7、RDMA
- 量子化: 重み・KVキャッシュともINT8
- モデル: Llama-3.2-3B、Llama-2-7B、Qwen3-8B。Llama-2-70Bはモデルベース外挿にも利用
- 比較対象: 同じハードウェア・checkpoint・量子化のllama.cpp
- 文脈: 1024〜4096
- バッチ: 1〜32

`evaluation_type: mixed` としたのは、3B / 7Bは実計算機でエンドツーエンド測定している一方、より大きいモデルを含む広い格子の最大値は検証済み解析的モデルによる外挿だからである。

## 主要結果

### 実測end-to-end

文脈長さ 4096で、llama.cppに対してTPOTを **2.04〜11.51倍**高速化した（Table 2、§6.1）。

- Llama-3.2-3B: バッチ 1で11.51×、バッチ 32で2.83×
- Llama-2-7B: バッチ 1で10.43×、バッチ 32で2.04×

バッチが増えると比較対象側でも重み読み込みを償却できるため、相対高速化倍率は縮む。

### model-based extrapolation

実測から検証した解析的モデルを大きいモデル・文脈・バッチへ展開した結果では、最大 **13.9× TPOT**、**12.5× スループット** 高速化倍率を報告する（Fig. 8、§6.3）。これは実測最大値ではなく外挿なので区別する必要がある。

### component ablation

- specialized静的スレッドプール: geomean 1.05〜1.16×、小さいバッチで最大1.56×（Fig. 10、§6.4）。
- WA分離: 文脈 4096で3Bはgeomean 1.00×、7Bは1.13×、70B extrapolated caseは1.16×。キャッシュ圧力が高いほど有効で、常に速くなる機構ではない（Fig. 9、§6.5）。
- 4パイプラインノードのRDMA通信は3Bデコードで約50µs、エンドツーエンド遅延の約0.5%と報告する（§4.4）。

## 既存研究との差

### FlexGenなどのoffloadとの違い

FlexGenはGPU・CPU DRAM・NVMeを跨いで重み / 活性値 / KVを配置し、capacity不足を外部メモリで補う。本論文は逆に、GB級LLCを**DRAMより内側の高速階層**として積極利用し、重みをon-chipに留めることが中心である。

### CPU-GPU heterogeneous inferenceとの違い

HeteGenやTwinPilotsのようにCPUとGPUへ演算子を分担するのではなく、CPUクラスタだけでキャッシュトポロジを資源階層として使う。主な最適化対象はPCIe転送ではなくLLC/DRAM通信量と同期オーバーヘッドである。

### Prefill/decode disaggregationとの違い

DistServe等はプリフィルとデコードを別GPUプールへ分ける。本論文のWA分離はデコード内部で重み-中心演算子と注意機構/KV状態を別ソケットへ分けるので、phase分離とは粒度が異なる。

## 限界

- 実機エンドツーエンド評価はLlama-3.2-3BとLlama-2-7Bまでで、大型モデルのheadline最大値は解析的モデルによる外挿。
- current試作はデコード TPOTを中心に最適化し、プリフィルの詳細最適化は将来 work。
- GB級LLCを持つEPYC platformに強く依存し、通常の小容量LLC CPUへそのまま一般化できない。
- WA分離はソケット予算を増やすため、遅延を改善してもソケットごとスループット efficiencyは下がり得る。
- 連続バッチ処理、online KV reclamation、MoEルーティングは今後の課題としている。
- 2026-09-08の一次資料確認では公式code repositoryを確認できなかった。

## 一般的な実装上の含意

メモリ階層に新しい高速階層が増えたとき、単に「そこへ重みを置く」だけでは不十分である。重みを常駐にすると次にKVキャッシュ interferenceやランタイムバリアが重要経路へ出てくるため、**データ配置・演算子分離・スレッド affinity・synchronizationを同じキャッシュトポロジに合わせる**必要がある。

特に大容量LLCや将来のon-chip SRAMを使うシステムでは、重みと成長する状態を同じcapacityプールへ混在させない資源 isolationが重要になる。

- FlexGen等のメモリ階層 / オフロード系と、キャッシュ-常駐実行という内側階層の利用で関係する。
