# Harvest: Opportunistic Peer-to-Peer GPU Caching for LLM Inference

> HarvestはNVLink接続された別GPUの空きHBMを一時キャッシュに使い、MoE重みやKVをホストDRAMから再取得する遅延を減らす。正本はCPUや再計算に残し、キャッシュ喪失にも耐える。

## 概要

Harvestは、GPUメモリ不足時のオフロードを「計算中GPUのHBMかホスト DRAMか」の二択にせず、**NVLinkで接続された別GPUの余っているHBMを中間の一時キャッシュとして使う**研究である。

対象はKVキャッシュだけではない。論文では、

- MoEのオフロードエキスパート重み
- デコード時のKVキャッシュ ブロック

の2種類へ同じ仕組みを適用する。

別GPUの空きHBMは、そのGPU自身のワークロードが増えれば急に使えなくなる可能性がある。そのためHarvestは、そこにしか存在しないデータを置かない。重みならCPU DRAMに正式コピーを残し、KVならCPU コピーを使うか必要に応じて再計算できるようにする。つまり**別GPUのキャッシュを失っても推論結果が壊れない一時的な高速置き場**として使う。

この点で、どのGPU同士でメモリを融通するかを事前に決めるAquaより動的で、KVだけでなく複数種類の推論 状態を扱える一般的なメモリ管理を目指している。


実機評価では、別GPUのHBMからの再取得がホストDRAM比でKimi-K2は5.42〜5.68倍、Mistral-Large-3は3〜5.65倍高速で、MoEの50%エキスパート退避ではデコードスループットを48〜110%以上改善した。

## 問題設定

大規模LLMではモデル重みとKVキャッシュの両方がHBMを圧迫する。一方、本番 クラスタでは全GPUが常にメモリを使い切っているとは限らない。

論文が参照するAlibaba クラスタトレースでは、約68%の機械 スナップショットが利用可能GPUメモリの20%以下、約87%が50%以下の消費だった。つまりクラスタ内には、時間帯やGPUによって一時的に使われていないHBMがかなり存在する。

ホスト DRAMには容量があるがPCIeが遅く、オフロードエキスパートやKVキャッシュを必要時に戻す遅延がトークン生成の待ち時間へ直接加わる。2×H100環境の転送測定では、エキスパート相当大きさのデータを別GPUからNVLinkでコピーすると、CPU→GPU 転送より約7.5〜9.5倍高速だった。

Harvestは、この**余っているHBMと高速GPU間リンク**を一時キャッシュとして利用する。

## 手法

### 1. Local HBM / 別GPU HBM / Host DRAMの3段階でdataを置く

Harvestではメモリを主に、

1. 計算中GPUのローカル HBM
2. NVLink接続された別GPUのHBM
3. ホスト DRAM

の3段階として扱う。

ローカル HBMから追い出したデータを別GPU HBMへ置ければ、次回必要になった時はPCIeではなくGPU間コピーで戻す。別GPUに空きがなければ従来どおりホスト DRAMを使う。

この3階層化の要点は、ピア HBMを新しい永続保存先として扱うのではなく、ホストより速くローカルへ戻せる追い出し対象キャッシュとして挟むことである。ローカル HBMに保持できないエキスパートやKVでも、近隣GPUに空きがある間だけ複製しておけば次回ミスの復旧経路をPCIeからNVLinkへ変えられる。ピア側の空きがなくなった場合は階層を1段飛ばしてホストへ戻るため、ピアキャッシュの有無で正しさが変わらない。

### 2. 別GPUのcacheはいつ失ってもよい前提にする

`harvest_alloc` で別GPUのHBMを要求すると、ランタイムが空き容量のあるGPUを選び、利用場所を返す。

ただし、そのGPU自身のワークロードがメモリを必要とした場合、貸していた領域は回収される可能性がある。アプリケーションは回収通知を受けたら、「そのデータはもう別GPUにはない」と管理表を更新し、CPU コピーまたは再計算へ戻る。

Harvestは、別GPU上のデータを後からCPUへ書き戻して正式版にするような複雑な同期管理を行わない。**別GPUのキャッシュは読出し高速化専用で、正しさに必要なデータは別の場所へ残す**ことで仕組みを単純にしている。

### 3. Dataの種類ごとに復旧方法を変える

- **重み / エキスパート:** 再構築が高価なのでCPU DRAMに正式コピーを維持する。
- **KV / 中間 状態:** CPU コピーを残す、または必要なら再計算できる。

重要なのは、**別GPUキャッシュは性能改善のためだけに使い、それを失っても推論を継続できるようにする**ことにある。

重みとKVで復旧方法を分けるのは再生成コストが違うためである。エキスパート重みは元パラメータから毎回再構築するよりホスト DRAMの正式コピーを残す方が安い。一方KVはリクエスト 状態から再計算可能な場合があり、ホスト コピーを必ず二重保持するか再計算へ戻すかをランタイムが選べる。どちらの場合もピア HBM上のコピーを唯一の正本にしないため、貸出GPUが突然メモリを取り戻してもモデル 状態を失わず、性能だけがホスト/recompute経路へ戻る。

### 4. MoE-Lightningへ別GPUのexpert cacheを追加する

MoE評価ではMoE-Lightningの既存パイプラインを拡張する。ルーティングやマイクロバッチ処理は変えず、オフロードエキスパートの取得先だけを

`host DRAM または別GPU HBM → local HBM`

から選べるようにする。

各エキスパートについてローカル / 別GPU / ホストのどこにあるかを表で管理し、別GPU コピーが利用可能ならNVLinkから取得する。貸していた領域が回収された場合はホストへ戻る。

### 5. vLLMへ別GPUのKV cache置き場を追加する

KVキャッシュではvLLMのKV managerを拡張し、各KV ブロックがローカル HBM / 別GPU HBM / ホスト DRAMのどこにあるかを追跡する。

ローカル HBMに必要ブロックがない時、別GPUにあればGPU間コピーで非同期に戻す。別GPUの領域が回収された場合は、その情報を無効化してホスト コピーまたは再計算へ戻る。

### 6. どのGPUの空きmemoryを使うかは変更可能

prototypeでは、要求大きさに近い空き領域を選んでメモリの細切れを減らす単純な方法を使う。ただし将来的には、

- NVLinkで近いGPUを優先する
- 特定tenantだけが空きメモリを独占しないようにする
- 相手GPUのメモリ帯域使用量を見る
- 領域を頻繁に貸したり回収したりしない場所を選ぶ

といった基準へ差し替えられるようにしている。

GPUをハードウェア機能で分割してキャッシュ領域を隔離する案も議論しているが、分割間でGPU同士の直接コピーが使えない構成もあるため必須条件にはしていない。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Machine | Microsoft Azure NC80adis H100 v5 |
| GPU | NVIDIA H100 ×2 |
| Host RAM | 640GB |
| CPU-GPU | PCIe 5.0 |
| GPU-GPU | 12 NVLink links |
| MoE 比較対象 | MoE-Lightning / CGOPipe |
| MoE モデル | Mixtral-8x7B、Qwen2-MoE、Phi-3.5-MoE、Phi-tiny-MoE |
| KV モデル | DeepSeek-V3、Mistral-Large-3、Kimi-K2 |

### MoE expert offload

50%のエキスパートをオフロードする条件で、別GPUのHBMキャッシュを使うとCPUオフロード版CGOPipeに対しデコードスループットが**48%〜110%以上**改善した。

Qwen2-MoEではオフロード率を0→100%へ上げてもHarvestは約975トークン/sをほぼ維持した一方、CPUオフロードでは約810トークン/sへ低下した。Mixtralでも別GPU版は約740トークン/sを維持し、ホスト版はfullオフロードで600トークン/s未満まで落ちた。

エキスパート 転送単体ではホスト経由より最大ほぼ**10倍**低遅延だった。

### KV cache offload

DeepSeek-V3、Mistral-Large-3、Kimi-K2のKV 大きさを模したデータ 転送で、CPU→GPUと別GPU→GPUを比較している。

Kimi-K2では別GPUからの再読込がホスト 再読込より約**5.42〜5.68倍**高速、Mistral-Large-3では約3〜5.65倍高速だった。

KVについては主に転送時間の測定で、MoEのような完全なエンドツーエンド 提供スループット評価は限定的である点に注意が必要。

## 既存研究との差

### Aquaとの違い

Aquaも別GPUのHBMを利用するが、どのproducer / consumerを組み合わせるかを事前にプロファイルして配置を決め、主にGPUメモリ不足時のKV退避を高速化する。

Harvestは**事前の組み合わせ決定を必須にせず、ランタイムでその時空いている別GPU HBMを一時キャッシュとして借りる**。さらにKVだけでなくMoEエキスパート重みにも同じAPIを使う。

### MoE-Lightningとの違い

MoE-Lightningはエキスパートをホスト DRAMへオフロードし、CPU-GPU-I/OパイプラインでPCIe遅延を他の計算と重ねる。Harvestはそのパイプラインを保ったまま、キャッシュ ミス時にホストではなく別GPU HBMから取得できるようにして**転送自体を高速化する**。

### KVPRとの違い

KVPRは遅いPCIe 転送の一部をGPUでのKV再計算へ置換する。Harvestは再計算ではなく、より高速な別GPU HBM コピーへ置換する。

### DirectKVとの違い

DirectKVはCPU上のKVをローカル HBMへコピーせず、GPUカーネルがCPUメモリを直接読む。Harvestは別GPU HBM上のデータを**ローカル HBMへコピーしてから使うキャッシュ システム**である。

## 限界

- 実機評価は2×H100の単一NVLink システムのみで、多数GPUをswitchで接続した大規模環境での帯域競合は未評価。
- 別GPUに空きHBMがなければ通常のホストオフロードへ戻るため、利得はクラスタ内のGPUメモリ利用状況に依存する。
- テンソル parallelism等がNVLinkを大量利用する環境での帯域 competitionは評価していない。
- KVキャッシュ側は転送遅延中心で、エンドツーエンド 提供 performanceの評価はMoE側より薄い。
- 利用できるメモリ領域が実行中に変わるため、メモリ addressが固定されることを前提にしたCUDA Graph等の最適化を使いにくくなる場合がある。
- GPU間の距離や帯域競合まで考えた配置は今後の課題。
- 2026-09-07時点で著者公式code repositoryは確認できなかった。

## 一般的な実装上の含意

Harvestの重要な点は、別GPUメモリを「別モデルを固定配置する場所」ではなく、**いつ失ってもCPU コピーや再計算から戻せる一時キャッシュ**として扱うことである。

正しさに必要な正式データと高速キャッシュを分離すれば、クラスタ内で一時的に余っているメモリを安全に性能改善へ使える。これはKVキャッシュ、エキスパート重み、prefixキャッシュなど再取得・再構築可能な状態へ広く応用できる。

また今後GPU間接続がrack規模へ広がるほど、**計算中GPUのHBM、近くのGPU HBM、遠いGPU HBM、ホスト DRAM、CXLメモリを速度順に使い分ける**ようなランタイムが重要になる。
