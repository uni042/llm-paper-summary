# Harvest: Opportunistic Peer-to-Peer GPU Caching for LLM Inference

> NVLinkで接続された別GPUの空きHBMを、失ってもCPU copyや再計算から復旧できる一時cacheとして使い、MoE expert weightやKV cacheをhost DRAMから戻すより高速に再取得するoffload framework。

## 概要

Harvestは、GPU memory不足時のoffloadを「計算中GPUのHBMかhost DRAMか」の二択にせず、**NVLinkで接続された別GPUの余っているHBMを中間の一時cacheとして使う**研究である。

対象はKV cacheだけではない。論文では、

- MoEのoffloaded expert weight
- decode時のKV cache block

の2種類へ同じ仕組みを適用する。

別GPUの空きHBMは、そのGPU自身のworkloadが増えれば急に使えなくなる可能性がある。そのためHarvestは、そこにしか存在しないdataを置かない。weightならCPU DRAMに正式copyを残し、KVならCPU copyを使うか必要に応じて再計算できるようにする。つまり**別GPUのcacheを失っても推論結果が壊れない一時的な高速置き場**として使う。

この点で、どのGPU同士でmemoryを融通するかを事前に決めるAquaより動的で、KVだけでなく複数種類のinference stateを扱える一般的なmemory管理を目指している。

## 問題設定

大規模LLMではmodel weightとKV cacheの両方がHBMを圧迫する。一方、production clusterでは全GPUが常にmemoryを使い切っているとは限らない。

論文が参照するAlibaba cluster traceでは、約68%のmachine snapshotが利用可能GPU memoryの20%以下、約87%が50%以下の消費だった。つまりcluster内には、時間帯やGPUによって一時的に使われていないHBMがかなり存在する。

host DRAMには容量があるがPCIeが遅く、offloaded expertやKV cacheを必要時に戻すlatencyがtoken生成の待ち時間へ直接加わる。2×H100環境のtransfer測定では、expert相当sizeのdataを別GPUからNVLinkでcopyすると、CPU→GPU transferより約7.5〜9.5倍高速だった。

Harvestは、この**余っているHBMと高速GPU間link**を一時cacheとして利用する。

## 手法

### 1. Local HBM / 別GPU HBM / Host DRAMの3段階でdataを置く

Harvestではmemoryを主に、

1. 計算中GPUのlocal HBM
2. NVLink接続された別GPUのHBM
3. host DRAM

の3段階として扱う。

local HBMから追い出したdataを別GPU HBMへ置ければ、次回必要になった時はPCIeではなくGPU間copyで戻す。別GPUに空きがなければ従来どおりhost DRAMを使う。

この3階層化の要点は、peer HBMを新しい永続保存先として扱うのではなく、hostより速くlocalへ戻せるvictim cacheとして挟むことである。local HBMに保持できないexpertやKVでも、近隣GPUに空きがある間だけ複製しておけば次回missの復旧経路をPCIeからNVLinkへ変えられる。peer側の空きがなくなった場合は階層を1段飛ばしてhostへ戻るため、peer cacheの有無で正しさが変わらない。

### 2. 別GPUのcacheはいつ失ってもよい前提にする

`harvest_alloc` で別GPUのHBMを要求すると、runtimeが空き容量のあるGPUを選び、利用場所を返す。

ただし、そのGPU自身のworkloadがmemoryを必要とした場合、貸していた領域は回収される可能性がある。applicationは回収通知を受けたら、「そのdataはもう別GPUにはない」と管理表を更新し、CPU copyまたは再計算へ戻る。

Harvestは、別GPU上のdataを後からCPUへ書き戻して正式版にするような複雑な同期管理を行わない。**別GPUのcacheは読出し高速化専用で、正しさに必要なdataは別の場所へ残す**ことで仕組みを単純にしている。

### 3. Dataの種類ごとに復旧方法を変える

- **weight / expert:** 再構築が高価なのでCPU DRAMに正式copyを維持する。
- **KV / intermediate state:** CPU copyを残す、または必要なら再計算できる。

重要なのは、**別GPU cacheは性能改善のためだけに使い、それを失っても推論を継続できるようにする**ことにある。

weightとKVで復旧方法を分けるのは再生成costが違うためである。expert weightは元parameterから毎回再構築するよりhost DRAMの正式copyを残す方が安い。一方KVはrequest stateから再計算可能な場合があり、host copyを必ず二重保持するか再計算へ戻すかをruntimeが選べる。どちらの場合もpeer HBM上のcopyを唯一の正本にしないため、貸出GPUが突然memoryを取り戻してもmodel stateを失わず、性能だけがhost/recompute経路へ戻る。

### 4. MoE-Lightningへ別GPUのexpert cacheを追加する

MoE評価ではMoE-Lightningの既存pipelineを拡張する。routingやmicro-batch処理は変えず、offloaded expertの取得先だけを

`host DRAM または別GPU HBM → local HBM`

から選べるようにする。

各expertについてlocal / 別GPU / hostのどこにあるかを表で管理し、別GPU copyが利用可能ならNVLinkから取得する。貸していた領域が回収された場合はhostへ戻る。

### 5. vLLMへ別GPUのKV cache置き場を追加する

KV cacheではvLLMのKV managerを拡張し、各KV blockがlocal HBM / 別GPU HBM / host DRAMのどこにあるかを追跡する。

local HBMに必要blockがない時、別GPUにあればGPU間copyで非同期に戻す。別GPUの領域が回収された場合は、その情報を無効化してhost copyまたは再計算へ戻る。

### 6. どのGPUの空きmemoryを使うかは変更可能

prototypeでは、要求sizeに近い空き領域を選んでmemoryの細切れを減らす単純な方法を使う。ただし将来的には、

- NVLinkで近いGPUを優先する
- 特定tenantだけが空きmemoryを独占しないようにする
- 相手GPUのmemory bandwidth使用量を見る
- 領域を頻繁に貸したり回収したりしない場所を選ぶ

といった基準へ差し替えられるようにしている。

GPUをhardware機能で分割してcache領域を隔離する案も議論しているが、分割間でGPU同士の直接copyが使えない構成もあるため必須条件にはしていない。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Machine | Microsoft Azure NC80adis H100 v5 |
| GPU | NVIDIA H100 ×2 |
| Host RAM | 640GB |
| CPU-GPU | PCIe 5.0 |
| GPU-GPU | 12 NVLink links |
| MoE baseline | MoE-Lightning / CGOPipe |
| MoE model | Mixtral-8x7B、Qwen2-MoE、Phi-3.5-MoE、Phi-tiny-MoE |
| KV model | DeepSeek-V3、Mistral-Large-3、Kimi-K2 |

### MoE expert offload

50%のexpertをoffloadする条件で、別GPUのHBM cacheを使うとCPU offload版CGOPipeに対しdecode throughputが**48%〜110%以上**改善した。

Qwen2-MoEではoffload率を0→100%へ上げてもHarvestは約975 token/sをほぼ維持した一方、CPU offloadでは約810 token/sへ低下した。Mixtralでも別GPU版は約740 token/sを維持し、host版はfull offloadで600 token/s未満まで落ちた。

expert transfer単体ではhost経由より最大ほぼ**10倍**低latencyだった。

### KV cache offload

DeepSeek-V3、Mistral-Large-3、Kimi-K2のKV sizeを模したdata transferで、CPU→GPUと別GPU→GPUを比較している。

Kimi-K2では別GPUからのreloadがhost reloadより約**5.42〜5.68倍**高速、Mistral-Large-3では約3〜5.65倍高速だった。

KVについては主にtransfer時間の測定で、MoEのような完全なend-to-end serving throughput評価は限定的である点に注意が必要。

## 既存研究との差

### Aquaとの違い

Aquaも別GPUのHBMを利用するが、どのproducer / consumerを組み合わせるかを事前にprofileして配置を決め、主にGPU memory不足時のKV退避を高速化する。

Harvestは**事前の組み合わせ決定を必須にせず、runtimeでその時空いている別GPU HBMを一時cacheとして借りる**。さらにKVだけでなくMoE expert weightにも同じAPIを使う。

### MoE-Lightningとの違い

MoE-Lightningはexpertをhost DRAMへoffloadし、CPU-GPU-I/O pipelineでPCIe latencyを他の計算と重ねる。Harvestはそのpipelineを保ったまま、cache miss時にhostではなく別GPU HBMから取得できるようにして**転送自体を高速化する**。

### KVPRとの違い

KVPRは遅いPCIe transferの一部をGPUでのKV再計算へ置換する。Harvestは再計算ではなく、より高速な別GPU HBM copyへ置換する。

### DirectKVとの違い

DirectKVはCPU上のKVをlocal HBMへcopyせず、GPU kernelがCPU memoryを直接読む。Harvestは別GPU HBM上のdataを**local HBMへcopyしてから使うcache system**である。

## 限界

- 実機評価は2×H100の単一NVLink systemのみで、多数GPUをswitchで接続した大規模環境での帯域競合は未評価。
- 別GPUに空きHBMがなければ通常のhost offloadへ戻るため、利得はcluster内のGPU memory利用状況に依存する。
- tensor parallelism等がNVLinkを大量利用する環境でのbandwidth competitionは評価していない。
- KV cache側はtransfer latency中心で、end-to-end serving performanceの評価はMoE側より薄い。
- 利用できるmemory領域が実行中に変わるため、memory addressが固定されることを前提にしたCUDA Graph等の最適化を使いにくくなる場合がある。
- GPU間の距離や帯域競合まで考えた配置は今後の課題。
- 2026-09-07時点で著者公式code repositoryは確認できなかった。

## 一般的な実装上の含意

Harvestの重要な点は、別GPU memoryを「別modelを固定配置する場所」ではなく、**いつ失ってもCPU copyや再計算から戻せる一時cache**として扱うことである。

正しさに必要な正式dataと高速cacheを分離すれば、cluster内で一時的に余っているmemoryを安全に性能改善へ使える。これはKV cache、expert weight、prefix cacheなど再取得・再構築可能なstateへ広く応用できる。

また今後GPU間接続がrack規模へ広がるほど、**計算中GPUのHBM、近くのGPU HBM、遠いGPU HBM、host DRAM、CXL memoryを速度順に使い分ける**ようなruntimeが重要になる。
