# Harvest: Opportunistic Peer-to-Peer GPU Caching for LLM Inference

> 余っているpeer GPUのHBMを一時的なcache tierとして使い、MoE expert weightやKV cacheのmissをhost DRAMではなくNVLink経由で処理し、peer memoryが回収されてもCPU fallbackや再構築で正しさを保つ汎用inference offload framework。

## 概要

Harvestは、GPU memory不足時のoffloadを「local HBMかhost DRAMか」の二択にせず、**NVLinkで接続された別GPUの余剰HBMを中間cache tierとして挿入する**研究である。

対象はKV cacheだけではない。論文では、

- MoEのoffloaded expert weight
- decode時のKV cache block

の2種類へ同じmemory harvesting abstractionを適用する。

peer HBMは常に利用できる保証がないため、Harvestはそこをauthoritative storageにはしない。weightならhost DRAMに正式copyを残し、KVなら必要に応じてhost copyへfallbackするか再構築する。つまり**peer HBMが突然revokeされても正しさが壊れないbest-effort cache**として設計する。

この点で、model placementまで事前調整するAquaよりopportunisticで、特定のdata typeに閉じない一般的な階層memory runtimeを目指している。

## 問題設定

大規模LLMではmodel weightとKV cacheの両方がHBMを圧迫する。一方、production clusterでは全GPUが常にmemory-fullとは限らない。

論文が参照するAlibaba cluster traceでは、約68%のmachine snapshotが利用可能GPU memoryの20%以下、約87%が50%以下の消費だった。近年のinference cluster traceでもmemory utilizationには大きなばらつきがあるとしている。

host DRAMには容量があるがPCIeが遅く、offloaded expertやKV cacheを必要時に戻すlatencyがcritical pathへ出る。2×H100環境のmicrobenchmarkでは、expert相当sizeのtransferでNVLink peer copyはCPU→GPU transferより約7.5〜9.5倍高速だった。

Harvestは、この**spare HBM + fast P2P interconnect**を一時cacheとして利用する。

## 手法

### 1. Local HBM / Peer HBM / Host DRAMの3 tierとして扱う

Harvestではmemoryを主に、

1. compute GPUのlocal HBM
2. NVLink接続されたpeer GPUのHBM
3. host DRAM

の3段階として扱う。

local HBMから追い出したobjectをpeer HBMへ置ければ、次回miss時はPCIeではなくCUDA P2P copyで回収する。peer capacityがなければ従来どおりhost DRAMを使う。

### 2. Peer HBMをephemeral cacheに限定する

`harvest_alloc` でpeer HBMを要求すると、runtimeが空き容量のあるGPUを選び、device pointerとplacement metadataを返す。

ただしpeer GPU自身のworkloadがmemoryを必要とした場合、そのallocationはrevokeされる可能性がある。そのためapplicationはcallbackを登録し、revoke時にplacement mapを無効化してhost copyまたは再計算へfallbackする。

Harvest自身はdirty stateやwrite-back coherenceを管理しない。この簡素化によって、peer HBMを不安定なresourceとして使える。

### 3. Objectごとにdurabilityをapplication側で決める

- **weight / expert:** 再構築が高価なのでhost DRAMをauthoritative copyとして維持する。
- **KV / intermediate state:** 再計算可能、または状況により捨てても再生成できるため、peer cacheを失ってもcorrectnessを保てる。

この「remote cacheはperformance optimizationであってcorrectness dependencyではない」という分離が設計の核になっている。

### 4. MoE-Lightningへpeer expert cacheを追加する

MoE評価ではMoE-LightningのCGOPipeを拡張する。routingやmicro-batch pipelineは変えず、offloaded expertのfetch先だけを

`host DRAM → peer GPU HBM → local HBM`

へ変更する。

各expertについてlocal / peer / hostのどこにあるかresidency mapを持ち、peer copyが利用可能ならNVLinkからfetchし、revoke時はhostへfallbackする。

### 5. vLLMへpeer KV cache tierを追加する

KV cacheではvLLMのKV managerへKVOffloadManagerを追加し、logical KV blockのresidencyをlocal HBM / peer HBM / host DRAMで追跡する。

local miss時にpeer HBMへblockがあればCUDA peer-to-peer copyで非同期reloadする。peer allocationが回収された場合はmappingを無効化してhostまたはrecomputationへfallbackする。

### 6. Allocation policyは差し替え可能にする

prototypeではfragmentationを抑えるbest-fitを使うが、APIとしては

- topology-aware placement
- tenant fairness
- peer GPUのmemory-bandwidth負荷
- allocation churnの少なさ

などを考慮するpolicyへ差し替えられる。

MIGによるcache領域の隔離も議論しているが、環境によってMIG間P2Pが制限されるためfunctional requirementではない。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Machine | Microsoft Azure NC80adis H100 v5 |
| GPU | NVIDIA H100 ×2 |
| Host RAM | 640GB |
| CPU-GPU | PCIe 5.0 |
| GPU-GPU | 12 NVLink links |
| MoE baseline | MoE-Lightning / CGOPipe |
| MoE model | Mixtral-8x7B、Qwen2-MoE、Phi-3.5-MoE、Phi-tiny-MoE |
| KV model | DeepSeek-V3、Mistral-Large-3、Kimi-K2 |

### MoE expert offload

50%のexpertをoffloadする条件で、peer GPU cacheへ置き換えるとCPU offload版CGOPipeに対しdecode throughputが**48%〜110%以上**改善した。

Qwen2-MoEではoffload率を0→100%へ上げてもHarvestは約975 token/sをほぼ維持した一方、CPU offloadでは約810 token/sへ低下した。Mixtralでもpeer GPU版は約740 token/sを維持し、host版はfull offloadで600 token/s未満まで落ちた。

expert transfer単体ではhost経由より最大ほぼ**10倍**低latencyだった。

### KV cache offload

DeepSeek-V3、Mistral-Large-3、Kimi-K2のKV footprintを模したtransferで、CPU→GPUとpeer GPU→GPUを比較している。

Kimi-K2ではpeer GPU reloadがhost reloadより約**5.42〜5.68倍**高速、Mistral-Large-3では約3〜5.65倍高速だった。

KVについては主にtransfer microbenchmarkで、MoEのような完全なend-to-end serving throughput評価は限定的である点に注意が必要。

## 既存研究との差

### Aquaとの違い

Aquaもpeer GPU HBMを利用するが、producer / consumerをprofileしてcluster placementを行い、主にpreemptive LLM inferenceのpagingを高速化する。

Harvestは**事前matchingを必須にせず、runtimeで空いたpeer HBMをbest-effort cacheとしてharvestする**。さらにKVだけでなくMoE expert weightにも同じAPIを使うため、より汎用memory-tier abstractionに寄っている。

### MoE-Lightningとの違い

MoE-Lightningはexpertをhost DRAMへoffloadし、CPU-GPU-I/O pipelineでPCIe latencyを隠す。Harvestはそのpipelineを保ったまま、cache miss sourceをpeer HBMへ変えて**転送自体を高速化する**。

### KVPRとの違い

KVPRは遅いPCIe transferの一部をGPU recomputationへ置換する。Harvestはrecomputeではなく、より高速なpeer HBM copyへ置換する。

### DirectKVとの違い

DirectKVはCPU-resident KVをGPU kernelが直接読むzero-copy方式。Harvestはremote HBM上のobjectを**local HBMへ明示的にcopyしてから使うcache system**であり、kernel側のremote dereferenceを要求しない。

## 限界

- 実機評価は2×H100の単一NVLink systemのみで、NVSwitchを含む大規模fabricでのcontentionは未評価。
- peer GPUにspare HBMがなければ通常のhost offloadへ戻るため、利得はworkload mixに依存する。
- tensor parallelism等がNVLinkを大量利用する環境でのbandwidth competitionは評価していない。
- KV cache側はtransfer latency中心で、end-to-end serving performanceの評価はMoE側より薄い。
- dynamic allocationによりCUDA Graphなど固定memory layoutを前提とするoptimizationを使いにくくなる場合がある。
- topology-aware / contention-aware placementは今後の課題。
- 2026-09-06時点で著者公式code repositoryは確認できなかった。

## 一般的な実装上の含意

Harvestの重要な点は、peer GPU memoryを「別modelを置くための固定resource」ではなく、**失っても正しさに影響しないvolatile cache tier**として扱うことである。

model stateのauthoritative copyとfast cacheを分離すれば、cluster内の一時的なmemory slackを安全に性能へ変換できる。これはKV cache、expert weight、prefix cacheなど再取得・再構築可能なstateへ広く応用できる。

また、今後GPU間topologyがrack規模へ広がるほど、local HBM / near peer HBM / far peer HBM / host DRAM / CXL memoryのようなNUMA的な階層をruntimeが扱う必要が出てくる。
