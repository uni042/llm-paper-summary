# MoE-Infinity: Efficient MoE Inference on Personal Machines with Sparsity-Aware Expert Cache

> MoE-Infinityはルーティング履歴から次に再利用される専門家を予測し、GPUキャッシュへ先読みして個人PCのMoEオフロード転送待ちを減らす。

## 概要
MoE-Infinityは、個人PCで典型的なバッチ=1・単一ユーザーのデコードでは、**同じリクエストの中で使われるエキスパートの組み合わせに偏りが続きやすい**ことを利用するMoE inference systemである。

エキスパート重みの正本は主にホスト DRAMへ置き、GPUにはdense重み、attention、KVキャッシュと一部のよく使われるエキスパートだけを置く。単純に「最後に使った時刻」だけを見るキャッシュではなく、現在リクエストのルーティング履歴から「この先どのエキスパートが再利用されそうか」を予測してプリフェッチ / 追い出しを行う。

公開実装はSSDを含む階層にも対応するが、論文の主な実機結果は**CPU DRAM ↔ GPU VRAM**のエキスパートオフロードとして読む方が正確である。KVキャッシュはGPUへ残すため、長文ではエキスパートキャッシュとは別にKV容量がボトルネックになる。

主要評価では、既存方式比でper-token latencyを3.1〜16.7倍改善し、Mixtralオフロード比でも約1.4倍、1 GPUで近い遅延を示した。

## 手法のあらまし

MoE-Infinityの独自性は、単純なエキスパート frequencyではなく、**リクエストごとのルーティング pattern全体を行列として記録し、似た過去リクエストから未来のエキスパート利用を予測する**点にある。

論文中では `iEAM`、`rEAM`、`EAMC`、`pEAM` という似た名前が出てくるため、役割を分けて見ると理解しやすい。

### 1. `iEAM`：1 iteration分のexpert利用を記録する

**iEAM（iteration-levelエキスパート活性値 Matrix）** は、ある生成iterationで各層・各エキスパートへ何トークン流れたかを表す行列である。

ざっくり言えば、

`行 = MoE layer`、`列 = expert`、`値 = そのiterationで何token選ばれたか`

というルーティング履歴になっている。

単なる「エキスパート 3がよく使われる」という1次元frequencyではなく、**どの層でどのエキスパートが使われたか**を残すため、リクエストのルーティング patternをより細かく表せる。

### 2. `rEAM`：request全体のrouting傾向を累積する

生成が進むたびにiEAMを足し合わせ、リクエスト単位で累積したものが **rEAM（リクエスト-level EAM）** である。

rEAMは「このリクエストでは、全体としてどの層のどのエキスパートが使われやすいか」を表す特徴表のような役割を持つ。

MoE-Infinityは、同じtaskや似たプロンプトではrEAMも似やすいと仮定する。

### 3. `EAMC`：過去requestのrouting patternを蓄積する

過去リクエストのrEAMをそのまま無制限に保存すると検索costが増えるため、論文では履歴集合を **EAMC（エキスパート活性値 Matrixキャッシュ / Collection）** として管理する。

過去のrEAMをK-meansで似たもの同士にまとめることで、Switch系を除く多くのmodelでは1000系列をおよそ10〜30個程度の代表groupへ圧縮できると報告している。

ここでK-meansを使う目的はエキスパートをまとめることではなく、**似たリクエストルーティング patternをまとめて、保存・検索する履歴数を減らすこと**である。

### 4. 過去の似たrequestから未来routingを予測する

現在リクエストのiEAMを1列の数値列に並べ、EAMC中の過去patternと形が近いものを探す。論文ではこの近さをcosine距離で測る。

近い複数のrEAMを合成すると、「このリクエストが今後どのエキスパートを使いそうか」という予測分布を作れる。

さらにMoE-Infinityは、**現在位置に近い層ほど予測を重く扱う補正**を入れる。論文ではこれを `layer-proximity` 係数と呼ぶ。

これは、

- すぐ次の層の予測は重要
- かなり先の層予測は不確実

として、現在位置から遠い層ほど予測重みを弱める仕組みである。

この最終的な予測行列が **pEAM（predicted EAM）** で、プリフェッチとキャッシュから追い出すエキスパートの判断に使われる。

### 5. 将来再利用されそうなexpertを優先してGPUへ残す

通常のLRUは「最後にいつ使ったか」でキャッシュから外すエキスパートを決める。MoE-InfinityはpEAMから得た**将来再利用確率**も見る。

キャッシュが満杯の場合、

- 近いうちに再利用されそうか
- どの層に属するか
- 過去にどの程度キャッシュ hitしているか

などを組み合わせ、将来価値が低いエキスパートから追い出す。

特に初期層はルーティング predictionがまだ安定しにくいため、キャッシュ優先度を高める設計も入っている。

### 6. Prefetchが外れても本来のexpertを必ず使う

pEAMはあくまでプリフェッチ用であり、nativeルータを置き換えない。

予測が外れた場合は、実際にルータが選んだエキスパートをホストからその場で読み込んで計算する。

したがって、

- hit / 正しいプリフェッチ → 遅延削減
- miss / 誤プリフェッチ → 同期fetchが発生して遅くなる

という関係で、**予測誤差は品質ではなくI/Oコストへ出る**。

### 7. この方式が効きやすいrequest分布

MoE-Infinityはリクエストごとのルーティング傾向がしばらく続くことを前提にするため、同じ種類のtaskや似たプロンプトを繰り返す環境では履歴が効きやすい。

一方、毎回まったく異なるリクエストが来るmulti-tenant servingでは、EAMCの代表patternが現在リクエストをうまく説明できず、利得が小さくなる可能性がある。

つまり全リクエスト共通の単純な人気順キャッシュより適応的だが、**過去のルーティング履歴が未来リクエストの傾向をある程度代表すること**は必要になる。

## 評価

### まず見るところ
- **結論:** リクエスト単位のルーティング patternを使ってエキスパートキャッシュ / プリフェッチすると、単純オフロードよりTPOTを大きく減らせる。
- **実速度:** 1 GPUでも、modelによっては4〜8 GPUで全重みを載せる構成へ近い遅延を示す。
- **品質:** nativeルータと同じエキスパートを必ず実行するため無損失。
- **メモリ・I/O:** エキスパートは主にCPU DRAM、GPUにはよく使うエキスパートとKVを保持。論文の主結果をSSD実測と解釈しない方がよい。
- **注意点:** バッチ=1・類似リクエストのルーティング傾向が続くほど有利。long contextではGPUに残したKVキャッシュが別ボトルネックになる。

| Benchmark | task数 |
|---|---:|

主な比較対象はvLLM、Ollama / llama.cpp、DeepSpeed-Inference、Mixtral-オフロード、BrainStorm。

### 代表的なTPOT

プロンプト 512、デコード 32の条件。

| Model | MoE-Infinityの平均TPOT |
|---|---:|
| DeepSeek | 155 ms |
| Switch | 155 ms |
| NLLB | 531 ms |
| Mixtral worst case | 836 ms |

NLLBは全重みをGPUへ置く構成なら8 GPU、Switchは4 GPUを要する条件に対し、MoE-Infinityは1 GPUで近い遅延を示す。

### 既存方式に対する改善

| 比較 | 結果 |
|---|---:|
| Mixtral offloading baseline | 約1.4倍改善 |
| 論文abstractの全model総括 | 既存方式比3.1〜16.7倍のper-token latency改善 |

3.1〜16.7倍という値はmodel・比較対象をまとめた範囲であり、すべてのmodelで一律16倍になるという意味ではない。

### Long-context時の影響

LongBenchでcontext lengthを `2^12〜2^17` まで伸ばしている。

| 指標 | 結果 |
|---|---:|
| MoE-Infinityの追加latency | 最大137 ms |

長くなるほどKVキャッシュがGPUメモリを圧迫し、エキスパートキャッシュへ使える余裕が減る。

一方vLLM側でKVもオフロードすると、KV transferとエキスパート fetchが帯域を競合するため、別の形で遅延が増える。

### 履歴が十分たまるまでの期間

| 項目 | 結果 |
|---|---:|
| 同一taskで安定するまで | 約50 request |
| worst-case overhead | 約5% |

EAMCに十分なルーティング patternが集まるまでは、予測精度が安定しにくい期間がある。

### 予測patternの圧縮

| 元のrequest数 | 代表group数 |
|---:|---:|
| 1000系列 | 約10〜30 group（Switch等を除く） |

これはエキスパート数を減らしているのではなく、**リクエストルーティング履歴の保存・検索量を減らしている**。

### 評価上の制約

- 1 GPU / low-バッチ中心。
- 同種リクエストでルーティング傾向が似ることを利用するため、リクエスト分布の変化に依存する。
- KVキャッシュはGPU常駐で、極端なlong contextではGPUメモリを強く圧迫する。
- 公開OSS版と論文評価版には実装差があるとREADMEに明記されている。
- SSD対応は公開実装側にあるが、論文主結果を物理SSDストリーミングベンチマークとして扱わない方がよい。
