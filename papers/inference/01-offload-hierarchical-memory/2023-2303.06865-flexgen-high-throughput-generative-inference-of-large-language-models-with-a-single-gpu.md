# FlexGen: High-Throughput Generative Inference of Large Language Models with a Single GPU

> GPU・CPU DRAM・NVMe SSDを一つのmemory hierarchyとして扱い、weight・activation・KV cacheの配置と計算順を探索して、単一commodity GPUで巨大LLMのbatch throughputを引き上げるoffload system。

## 概要

FlexGenは、**GPU memoryにモデル全体が載らない環境でも、interactive latencyをある程度犠牲にして大量requestの総throughputを高める**ことを狙ったLLM inference systemである。

単にweightをCPUやSSDへ置くのではなく、生成処理全体を

- どの順番でbatch / token / layerを処理するか
- weightをGPU / CPU / SSDのどこへ置くか
- activationをどこへ置くか
- KV cacheをどこへ置くか
- KV cacheがCPU側にある場合にattentionをGPUへ持ってくるか、CPUで直接計算するか

という一つの最適化問題として扱う。

特に重要なのは、通常の「1 batchをtokenごとに最後まで処理する」実行順を崩し、**同じlayer weightを複数batchで使い回すblock schedule**へ変えた点である。これにより、GPUへ一度読み込んだweightを大きなeffective batchへ再利用でき、CPU / SSDからのweight I/Oを多数requestへ償却できる。

このためFlexGenは、chatbotのような低latency servingよりも、benchmark、information extraction、data processingなど、**多少1 requestが遅くても大量のpromptをまとめて処理したいoffline / throughput-oriented workload**に向いている。

## 問題設定

GPU memory不足をoffloadで解決する場合、容量だけを見ればweightをCPUやSSDへ移せばよい。しかし自己回帰生成ではlayerとtokenを何度も巡回するため、素朴なoffloadでは同じweightを繰り返しPCIeやSSD経由で読み直すことになり、I/Oが支配的になる。

さらに大batchではKV cache自体も巨大になる。論文のOPT-175Bの例では、batch=512、prompt length=512、output length=32の場合、FP16 weightが約325 GBなのに対しKV cacheは約1.2 TBとなり、**weight以上にKV cacheがmemory bottleneckになり得る**。

したがってFlexGenの問題は単なる「weightをどこへ置くか」ではなく、**weight・activation・KV cacheを3階層memoryへどう分散し、どの実行順ならI/Oを最小化できるか**である。

## 手法のあらまし

### 1. LLM generationを「計算順を選べるgraph」として扱う

FlexGenは、

- 縦方向: Transformer layer
- 横方向: 生成token
- 奥行き方向: 複数batch

からなる計算graphとしてgenerative inferenceを見る。

各計算にはweight、activation、KV cacheが必要で、前のtoken / layerとの依存関係とGPU・CPU・SSDの容量制約を守りながら全計算を終える必要がある。

ここで重要なのは、依存関係を守る限り**計算順は一意ではない**という点である。FlexGenはこの自由度をI/O削減に使う。

### 2. Row-by-rowではなく、weightを使い回すblock schedule

従来のoffload runtimeは概ね、1つのbatchについてlayerを順番に進み、そのtokenを処理したら次tokenへ進む。

これは単一requestを早く終わらせるには自然だが、隣り合う計算が別layerなので、GPUに載らないweightを毎回読み直す必要がある。

FlexGenは逆に、**同じlayerを複数GPU batchへ連続適用してweightを使い回す**方向へ計算順を寄せる。

完全にlayer単位で全datasetを処理するとactivationとKV cacheがCPU / SSDを埋め尽くすため、実際には一定数batchをまとめたblockごとに進む `zig-zag block schedule` を採用する。

この名称だけ見ると特殊だが、要点は単純で、

> 一度GPUへ載せたlayer weightを、可能な限り多くのbatchへ使ってから次layerへ進む

というscheduleである。

論文では、実装したこのscheduleのI/O量が理論上の最適scheduleに対して高々2倍以内になることも示している。よりI/O効率の高いdiagonal scheduleも理論上提示しているが、実装複雑性から本体runtimeでは採用していない。

### 3. Weight I/O、KV / activation I/O、GPU計算を同時進行させる

各batchの計算中に、

- 次layerのweightを読み込む
- 前batchのactivation / KV cacheを書き出す
- 次batchのactivation / KV cacheを読み込む
- 現在batchをGPUで計算する

という処理を並行させる。

つまり転送を「計算の前後に行う待ち時間」にせず、可能なものを現在のGPU計算の裏で進める。

この重畳を成立させるため、block内に複数のGPU batchを持たせる。`GPU batch size × block内のGPU batch数` がeffective batch sizeとなる。

### 4. Weight・activation・KV cacheを別々にGPU / CPU / SSDへ配置する

FlexGenでは3種類のtensorを同じ配置規則にしない。

- **weight**: layer単位でGPU / CPU / SSDへ配置
- **activation**: tensor内部を割合でGPU / CPU / SSDへ配置可能
- **KV cache**: tensor内部を割合でGPU / CPU / SSDへ配置可能

例えば「weightはほぼCPU、KV cacheはCPU中心、activationはGPUとCPU」のように、workloadとhardware bandwidthに合わせて別々のplacementを選べる。

ここが「modelの何layerかをCPUへ逃がす」だけの単純offloadより広い設計空間になっている。

### 5. KV cacheをCPUへ置いた場合は、attentionもCPUで計算することがある

KV cacheがCPUにある場合、それを毎token GPUへ送り返してattentionを計算するとPCIe転送が大きい。

FlexGenはこの場合、**KV cacheを動かす代わりに小さいquery / activation側をCPUへ送り、attention scoreをCPU上で計算する**選択肢を持つ。

論文の解析では、KV cache transfer量はactivation transfer量のおよそsequence length倍になるため、長いsequenceではCPU計算自体が遅くても、データを動かさない方が全体では速くなる場合がある。

これは「高速deviceで全部計算する」のではなく、**計算速度よりdata movement costを優先して実行場所を決める**という設計である。

### 6. Hardware profileからoffload policyを探索する

FlexGenはGPU / CPU / diskの

- memory容量
- CPU↔GPU bandwidth
- disk↔CPU bandwidth
- GPU compute性能
- CPU compute性能

をprofileし、prefill / decodeそれぞれについて「転送と計算を重畳した時に最も遅い経路が1 layerの時間になる」と近似するcost modelを作る。

探索する主な変数は、

- GPU batch size
- block size
- weightのGPU / CPU / SSD比率
- activationのGPU / CPU / SSD比率
- KV cacheのGPU / CPU / SSD比率

である。

GPU batch sizeとblock size候補をいくつか列挙した後、残る9個のplacement比率を**線形計画法で高速に探索**する。

ただし論文自身が、memory fragmentationなどを完全にはmodel化できず、探索結果がOOMになる場合や、手動調整でさらに良いpolicyが得られる場合があると認めている。したがって完全なautotunerというより、**大きな設計空間から良い初期policyを見つける仕組み**として見る方が正確である。

### 7. Multi-GPUではpipeline parallelismを組み合わせる

複数GPUがある場合はlayerをGPU間で分割し、各GPU内では同じoffload scheduleを使う。

FlexGenはlatency低減よりthroughputを重視するため、tensor parallelismより通信量の少ないpipeline parallelismを選ぶ。

### 8. 4-bit化は「低bit演算」よりI/O削減が目的

FlexGenはweightとKV cacheをgroup-wise asymmetric quantizationで4-bit保存する。

重要なのは、4-bitのままmatrix multiplicationすることが主目的ではなく、**memory footprintとCPU / SSD↔GPUの転送byteを減らす**ための圧縮だという点である。

実際の計算前にはFP16へ戻す。group sizeは64で、weightはoutput channel方向、KV cacheはhidden dimension方向にgroup化する。

このdequantization overheadはCPUでは重いため、4-bit compressionを使う場合は前述のCPU attention delegationを無効化している。

### 9. Sparse attentionは補助的な実験

さらにattention score上位10%のtokenに対応するV cacheだけを読む簡易sparse attentionも試している。

これはFlexGenの中核ではなく、「KV cache I/Oをさらに減らすapproximationをplug-inできる」ことを示す予備実験に近い。

## 評価

### 実験環境

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA T4 16 GB |
| CPU memory | 208 GB |
| SSD | 1.5 TB NVMe |
| SSD read | 約2 GB/s |
| SSD write | 約1 GB/s |
| Model | OPT-6.7B / 30B / 175B |
| Prompt length | 512 / 1024 |
| Output | 32 tokens |
| 主baseline | DeepSpeed ZeRO-Inference / Hugging Face Accelerate |
| 分散比較 | Petals |

throughput benchmarkでは全systemにdummy weightを使い、accuracy評価ではreal weightを使う。promptは同じ長さへpaddingしたsynthetic workloadである。

### 単一T4でのgeneration throughput

代表値は以下。

| Prompt | Model | Accelerate | DeepSpeed | FlexGen | FlexGen 4-bit |
|---|---:|---:|---:|---:|---:|
| 512 | OPT-30B | 0.62 | 0.60 | 7.32 | 8.70 |
| 512 | OPT-175B | 0.01 | 0.01 | 0.69 | 1.12 |
| 1024 | OPT-30B | 0.31 | 0.29 | 3.50 | 3.98 |
| 1024 | OPT-175B | 0.01 | OOM | 0.35 | 0.42 |

単位はgenerated token/s。

OPT-175B / prompt 512では、compressionなしでもbaselineの約69倍、4-bit版では約112倍の数値になる。論文本文ではlatency constraintを揃えた比較として40倍、より大きなlatencyとcompressionを許した最大throughput比較として約100倍と説明している。

ここで重要なのはkernel単体が100倍速いわけではなく、**baselineがmemory制約でbatch sizeを1〜2程度までしか増やせない一方、FlexGenは大きなeffective batchを作ってweight I/Oを多数requestへ償却できる**ことが差の主要因である。

### 4 GPUへのscale

prompt 512では、OPT-175Bのgeneration throughputが

- FlexGen 1 GPU: 0.69 token/s
- FlexGen 4 GPU: 2.33 token/s
- DeepSpeed 4 GPU: 0.05 token/s

となる。

6.7Bではdecode部分だけを見るとFlexGenは1 GPU 38.28 token/sから4 GPU 764.65 token/sへ大きく伸びている。これはGPUが増えてmemory pressureが下がり、より大きいbatchへ切り替えられるため、単純な4倍を超えて伸びる領域があるためである。

### Ablation

OPT-175B / prompt 512でのthroughputは、

| 構成 | token/s |
|---|---:|
| 全最適化 | 0.69 |
| policy searchなし | 0.27 |
| I/O overlapなし | 0.59 |
| CPU computeなし | 0.62 |
| SSDを使わない | OOM |
| DeepSpeed相当policyをFlexGen runtimeで実行 | 0.01 |

となっている。

この結果から、FlexGenの効果は単一の工夫ではなく、**大batchを可能にするplacement policyが中心で、そこへI/O overlapとCPU delegationが積み重なる**構造だと分かる。

### 4-bitによる品質変化

OPT-175Bでは、

| 構成 | LAMBADA accuracy | WikiText perplexity |
|---|---:|---:|
| FP16 | 0.758 | 10.82 |
| 4-bit weight + KV | 0.756 | 10.94 |
| 4-bit + sparse V cache | 0.756 | 10.94 |

と報告している。

一方、3-bit compressionは品質を維持できなかったとしている。

## この論文の重要な読み方

FlexGenを「SSDからLLM weightを読むruntime」とだけ捉えると狭すぎる。

本質は、**GPU・CPU・SSDという異なるmemory / compute resourceを、LLM generationの計算順まで含めてjoint optimizationしたこと**にある。

また、現在のinteractive servingから見ると非常に長いlatencyを許す設定だが、これは欠点というより研究対象そのものが異なる。FlexGenは「1 requestを速く返す」より「安価なhardwareで大量promptを何時間かけて処理した時の総token/s」を最大化している。

## 限界

### 1. Online / interactive serving向けではない

最大throughputを出すにはlarge batch / blockを使うため、個々のrequest latencyは非常に大きくなる。論文でもlatency-insensitive workloadを明確な対象としている。

後続のNEOやAPEXなどがonline workloadを扱うのは、この点を埋める方向と考えられる。

### 2. 評価modelがOPT系に限定される

6.7B〜175Bまでscaleは広いが、architectureはOPTのみ。現代のGQA、MoE、より長いcontext、FlashAttention系kernelを使うmodelではresource balanceが変わる。

### 3. Workloadがかなり整っている

主throughput評価は固定prompt length、固定32-token output、padding済みsynthetic datasetで、request lengthが動的に変わるmodern servingとは異なる。

### 4. Policy searchは完全自動ではない

cost modelはmemory fragmentationなどを完全には表現できず、探索policyがOOMすることがある。著者自身もmanual tuningでより良いpolicyが得られる場合が多いと述べている。

### 5. SSD性能は現代基準では低い

主評価のSSD readは約2 GB/sである。現在の高速NVMe、GPUDirect Storage、CXL、computational storageではbottleneck構造が変わり得る。

逆に、この差がInstInferなど後続研究の余地になっている。

### 6. 4-bitはcompute quantizationではない

weight / KVを4-bitで保持するが、計算前にFP16へ戻すため、低bit GEMMの高速化とは別物である。主目的はmemory / I/O削減。

### 7. Sparse attentionは予備的

Top-10% V cacheだけを読む実験はあるが、現代のKV pruning / eviction研究ほど詳細なtoken retention policyやlong-context benchmarkは行っていない。

## 既存研究との差

### vs DeepSpeed ZeRO-Inference / Hugging Face Accelerate

これらは主にlayerを順番に処理するoffload strategyを使い、weightを繰り返し移動する。FlexGenは計算順そのものをblock化し、weight reuseを大きくする。

さらにweightだけでなくactivation / KV cacheのplacementとCPU computeまで同じpolicy searchに入れる。

### vs Petals

Petalsは複数machineへmodelを分散し、network越しにactivationを流す。FlexGenは1 machine内のGPU / CPU / diskを集約する。

したがってFlexGenはlocal I/O bandwidth、Petalsはnetwork bandwidth / latencyが主要制約となる。

### vs 後続のCPU / storage offload

HeteGen、FastDecode、NEO、InstInfer、HybridGenなどの後続研究は、FlexGenが示した「GPU外memory / computeを使う」設計を、

- low-latency化
- dynamic workload対応
- CPU-GPU同時計算
- KV cacheだけの選択的offload
- computational storage
- CXLを含むtiered memory

などへ発展させている。

FlexGenはこれらの直接baselineとして繰り返し参照される基礎systemに位置する。

## 引用関係から見つかった次の調査候補

この論文の参考文献と後続引用を辿ると、現在のカタログ未収録候補として特に次が重要。

- **DeepSpeed-Inference** — FlexGenが直接比較する先行offload baseline。
- **HeteGen (2024)** — CPU / GPUを並列計算資源としてより積極的に使う。
- **FastDecode (2024)** — KV-heavyなattentionをCPU側へ分離したheterogeneous pipeline。
- **InstInfer (2024)** — KV cacheとdecode attentionをcomputational storageへ移す。
- **NEO (2024/MLSys 2025)** — online serving向けにCPU offloadを動的scheduleする。
- **APEX (2025/2026 revision)** — CPU / GPU executionを非同期に重ねるonline inference。
- **HybridGen (2026)** — CXL-expanded memoryを使いCPU / GPUでattentionを共同実行する。

これらはこのページでは深入りせず、以後1本ずつ独立して精読する。
