# FlexGen: High-Throughput Generative Inference of Large Language Models with a Single GPU

> GPU・CPU DRAM・NVMe SSDを一つのmemory hierarchyとして扱い、weight・activation・KV cacheの配置と計算順を探索して、単一commodity GPUで巨大LLMのbatch throughputを引き上げるoffload system。

## 概要

FlexGenは、**GPU memoryにモデル全体が載らない環境でも、interactive latencyをある程度犠牲にして大量requestの総throughputを高める**ことを狙ったLLM inference systemである。

単にweightをCPUやSSDへ置くのではなく、生成処理全体を

- どの順番でbatch / token / layerを処理するか
- weightをGPU / CPU / SSDのどこへ置くか
- activationをどこへ置くか
- KV cacheをどこへ置くか
- KV cacheがCPU側にある場合にattentionをGPUへ持ってくるか、CPUで直接計算するか

まで含めて最適化する。

FlexGenの中心は**block schedule**である。通常のtoken-by-token実行では、layer weightを何度もGPUへ読み込む必要がある。FlexGenは複数batchの同じlayer処理をまとめ、1回読み込んだweightを複数batchへ使い回すことでI/Oをamortizeする。

## 問題設定

巨大LLMを単一GPUで推論するとき、GPU memoryへ載らないweightをCPU DRAMやSSDへ逃がす必要がある。しかしnaive offloadではPCIeやSSD I/OがGPU計算より遅く、GPUがdata待ちになる。

FlexGenはinteractive servingではなく**throughput-oriented generation**を主眼に置き、latencyを許容してbatchを大きくすることでI/Oを隠す。

## 手法

### 1. Tensor placement

weight、activation、KV cacheごとにGPU / CPU / SSDへ置く割合を決める。placement searchはhardware bandwidth、memory容量、計算量からcost modelを作り、実行可能な配置の中からthroughputが高いものを選ぶ。

### 2. Block schedule

layerごとに複数batchをまとめて処理し、weight transferをbatch間で共有する。これによりSSD→CPU→GPUのweight I/O回数を減らす。

### 3. I/O overlap

CPU↔GPU transfer、SSD↔CPU transfer、GPU computeをpipeline化して重ねる。offload systemでは単純な転送量だけでなく、**転送をcomputeの裏へ隠せるか**が重要になる。

### 4. 4-bit weight / KV compression

必要に応じてweightやKV cacheを4-bitへ圧縮し、memory footprintとI/O量を減らす。

## 評価条件

OPT-30B、OPT-175Bなどを単一NVIDIA T4 / A100系GPUとCPU DRAM、NVMe SSDを組み合わせた環境で評価する。比較対象はDeepSpeed ZeRO-Inferenceなど。

FlexGenはinteractive latencyを最小化するsystemではないため、評価の中心は**throughput（tokens/s）**である。

## 主要結果

論文では、OPT-175Bを単一16GB GPUで実行し、DeepSpeed ZeRO-Inferenceと比較して高いgeneration throughputを報告している。特に大きなbatchを許容できるoffline workloadで優位になる。

代表的には、OPT-175BでFlexGenはZeRO-Inferenceより最大約19×高いthroughputを示す条件がある。ただしこれはlatencyとのtrade-offを含み、interactive requestへそのまま適用できる数字ではない。

## 限界

- 大batchを使ってI/Oをamortizeするため、interactive latency用途には不向き。
- SSD bandwidthが低い環境ではI/O bottleneckが強い。
- modern attention kernelやcontinuous batchingを前提とした現在のserving stackとは設計世代が異なる。
- MoE expert単位のrouting-aware cacheではなくdense modelを含む一般的なtensor offloadが中心。

## 既存研究との差

ZeRO-Inference等がweight offloadを中心に扱うのに対し、FlexGenは**weight・activation・KV cacheの配置と実行scheduleを同時に探索する**。さらにbatchをlayer方向へ組み替えるblock scheduleでweight reuseを増やす点が大きな特徴である。

後のMoE offload研究では、ここからさらにexpert sparsityやrouting localityを利用して「全weightではなく必要expertだけを動かす」方向へ発展する。

## 一般的な実装上の含意

SSD offloadで重要なのは単に「SSDからweightを読む」ことではなく、

1. 1回のreadを何回のcomputeへ使い回せるか
2. SSD→CPU、CPU→GPUをどれだけ並列化できるか
3. KV cacheやactivationとweightのmemory budgetをどう分けるか

である。

これは現在のMoE expert offloadでも基本的に同じで、expert cache hit率だけでなく**I/O reuseとpipeline overlap**が性能を決める。
