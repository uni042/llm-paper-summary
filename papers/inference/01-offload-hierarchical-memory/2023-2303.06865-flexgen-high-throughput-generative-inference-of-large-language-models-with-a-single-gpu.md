# FlexGen: High-Throughput Generative Inference of Large Language Models with a Single GPU

> FlexGenは巨大LLMの重み・中間活性・KVキャッシュをGPU・CPU・SSDへ分け、計算順序とバッチでI/Oを使い回して単一GPUの生成スループットを高める。

## 概要

FlexGenが対象にするのは、chatのように1 リクエストの応答をすぐ返す用途ではなく、ベンチマーク、情報抽出、文書処理のような**多少待ってもよい代わりに、多数のリクエストをできるだけ安く処理したい生成処理**である。論文ではこれをスループット-指向 generative inferenceと呼ぶ。

単一16GB GPUで175B級モデルを扱う場合、重みだけでもGPUへ収まらない。そこでCPU DRAMやNVMe SSDを使うのは自然だが、単純に「必要な層をSSDから読み、計算し、次へ進む」とすると、GPUはほとんどの時間をI/O待ちに使ってしまう。

FlexGenの発想は、**遅延を許容できるなら、一度読み込んだデータをできるだけ多くのリクエストへ使い回せばよい**というものだ。そのために生成処理をバッチ・トークン・層の3軸で並べ替え、同じ層の重みを多数リクエストへ使い回す。

さらにFlexGenは、次の3種類のテンソルを別々に扱う。

- **重み (重み)**: 全リクエストで共有できるが非常に大きい。
- **中間活性 (活性値)**: リクエストごとに異なるが、1時点で必要な量は比較的小さい。
- **KV キャッシュ**: リクエストごとに異なり、生成が進むほど増え続ける。

この3種類は「容量」「再利用性」「毎トークンでの読み方」が異なるため、全部を同じオフロード 方針で扱うと無駄が出る。FlexGenはGPU・CPU・SSDへの配置比率を個別に決め、さらにKV キャッシュがCPUにある場合は注意 スコア計算自体をCPUへ寄せる選択肢も持つ。

## 問題設定

### 単純なweight offloadだけではbatchを大きくできない

巨大モデルで最初に問題になるのは重み容量だが、生成ではKV キャッシュも無視できない。バッチ サイズを増やすとリクエスト数に比例してKV キャッシュが増えるため、重みだけをCPUへ追い出しても、今度はGPU上のKV キャッシュがバッチ サイズの上限になる。

既存のオフロード システムでは、学習で使われた層-by-層の実行順をほぼそのまま推論へ流用することが多かった。この場合、巨大な重みを何度もCPUやSSDから読み直すうえ、KV キャッシュをGPUへ保持するためバッチも大きくしにくい。

FlexGenは、**GPU メモリを「何を常駐させるか」ではなく、「どれだけ大きなバッチを成立させ、そのバッチで何回I/Oを再利用できるか」から逆算する**。

### 遅いSSDでも、1回のreadを多数リクエストへ使えばthroughputは上げられる

主評価環境ではGPUがNVIDIA T4 16GB、CPU DRAMが208GB、NVMe SSDが1.5TBで、SSD 読出し帯域は約2GB/sである。GPUの演算能力に比べるとSSDは非常に遅い。

しかし、例えば1 層分の重みをSSDから一度読み込んだあと、その重みで1 リクエストだけでなく数十〜数百リクエストを処理できれば、1 リクエストあたりの重み I/O コストは大きく下がる。

そのためFlexGenでは、**大バッチを成立させるためにKV キャッシュまでCPUやSSDへ逃がし、その代わり重み 読出しを多数リクエストで償却する**という、対話的 提供とは逆方向のtrade-offを積極的に使う。

## 手法

FlexGenの実行は、概念的には次の順序で理解すると分かりやすい。

1. GPU・CPU DRAM・SSDの容量と帯域を測る。
2. 重み・中間活性・KV キャッシュを各階層へ何割置くか候補を作る。
3. 1回のGPU バッチ サイズと、それを何個まとめて1 ブロックとして処理するかを決める。
4. 同じ層をブロック内の多数バッチへまとめて実行し、重みの再読込回数を減らす。
5. 次層の重み読込、次バッチのキャッシュ/活性値 読込、前バッチの保存するをGPU計算と重ねる。
6. 必要ならKV キャッシュがCPUにあるリクエストでは注意 スコア計算をCPUへ委譲する。
7. 容量やI/Oがさらに厳しい場合は、重みとKV キャッシュを4-bitへ圧縮する。

つまりFlexGenは単一のオフロード技法ではなく、**配置・計算順・計算場所・圧縮を一つのコスト モデルで選ぶシステム**である。

## 手法

### 1. 3階層memoryへtensor種別ごとの配置比率を決める

FlexGenはGPU、CPU DRAM、ディスクを3段階のメモリ 階層として扱う。

各テンソル種別について、例えば重みなら

- GPUに何%置くか
- CPUに何%置くか
- SSDに何%置くか

を決める。同様に中間活性とKV キャッシュにも別の配置比率を持つ。

重要なのは、**「ある層はGPU、別層はSSD」と固定するだけではない**点である。実行実行計画と組み合わせ、必要な時点だけGPUへ持ち込み、計算後に下位階層へ戻すことを前提に配置を決める。

重みは層単位、中間活性とKV キャッシュはテンソル単位の粒度で移動する。この粒度は、細かすぎる転送によるランタイム オーバーヘッドと、粗すぎる配置による柔軟性低下の折衷として選ばれている。

### 2. block scheduleで重みを多数リクエストへ使い回す

通常の生成を素直に書くと、各リクエストについてトークン 1の全層、トークン 2の全層、という順に進めたくなる。しかしオフロード環境では、この順序だと同じ層の重みを何度も読み込む。

FlexGenは処理を大きな**ブロック**にまとめる。ブロックの中では、ある層の重みをGPUへ読み込んだら、複数GPU バッチの同じ層処理を連続して実行してから次層へ進む。

直感的には、

`重みAを読む → リクエスト群全部にAを使う → 重みBを読む → リクエスト群全部にBを使う`

という順序である。

この実装済み実行計画は論文で**ジグザグブロック 実行計画 (zig-zag ブロック 実行計画)** と呼ばれる。I/O量の観点では理論最適そのものではないが、論文はそのI/O complexityが最適解の2倍以内であることを示している。

よりI/O効率のよい**対角ブロック 実行計画 (diagonal ブロック 実行計画)** も理論的に示されるが、KV キャッシュを非連続メモリ上で動的に管理する実装が複雑なため、本体システムではzig-zag方式を採用している。

### 3. GPU batchとblock sizeを分ける

FlexGenでは「GPUへ一度に入れるバッチ」と「同じ重み 読込で処理する全リクエスト数」を分ける。

GPU メモリへ一度に載るリクエスト数が小さくても、例えばGPU バッチを何回も繰り返して一つのブロックを構成すれば、同じ層 重みをCPU/SSDから1回読み込んだまま、多数リクエストへ再利用できる。

この構造により、GPU メモリが小さくても**実効バッチ サイズ**を大きくできる。OPT-175Bの評価で比較対象より大きなバッチを成立させられる主因がここにある。

### 4. I/Oとcomputeをpipelineで重ねる

ブロック 実行計画だけでは、データを読む時間そのものは残る。そこでFlexGenは複数のCUDA ストリームやCPU threadを使い、

- 次層の重み 読込
- 次バッチの活性値 / KV 読込
- 前バッチの活性値 / KV 保存する
- 現在バッチのGPU 計算

を可能な範囲で並行させる。

ここで重要なのは、I/O時間をゼロにするのではなく、**critical pathから外せるI/OをGPU計算の裏へ隠す**ことである。

SSD→CPUとCPU→GPUも別経路なので、パイプラインが十分埋まれば複数階層の転送を同時に進められる。

### 5. KVがCPUにある場合はattentionをCPUへ寄せられる

デコード 注意では、現在トークンのqueryは小さい一方、過去全トークンのK/Vは長文脈になるほど大きい。

KV キャッシュをCPUに保存している場合、それを毎トークン GPUへ全部戻して注意 スコアを計算するとPCIe 通信量が大きい。そこでFlexGenは、場合によっては**注意 スコア計算そのものをCPUで実行する**。

この場合、GPUからCPUへ送るのは現在トークンの比較的小さい活性値で済み、巨大なKV全体をGPUへ移す必要がない。

後のFastDecodeやNEOが「KVのあるCPUへ注意 計算を寄せる」設計を本格化するが、その基本的な計算委譲の考え方はFlexGenにもすでに含まれている。

### 6. 線形計画法でplacementを探索する

候補を人手で選ぶのではなく、FlexGenはハードウェア profileからコスト モデルを作る。

固定したGPU バッチ サイズとブロック サイズについて、

- GPU / CPU / SSDのメモリ 容量を超えない
- 各データ pathのI/O時間を見積もる
- GPU 計算時間を見積もる
- 1 ブロックの総実行時間を最小化する

という問題を解く。

配置については主要変数が9個程度の**線形計画問題 (線形 programming problem)** に整理されるため、探索自体は高速である。

つまり「CPU メモリが多いmachineではKVをCPUへ多めに置く」「SSDが遅いmachineでは重みをできるだけCPUへ寄せる」といった判断を、同じ枠組みからハードウェア別に出せる。

### 7. 4-bit圧縮でI/Oそのものも減らす

FlexGenは重みと注意用KV キャッシュを4-bitへ圧縮する選択肢も持つ。

目的は単にVRAMを節約することではなく、**CPU/SSDから運ぶbyte数を減らすこと**である。オフロード システムではテンソルが下位メモリにある時間が長いため、圧縮によるI/O削減の価値が大きい。

論文では細粒度のグループ-wise 量子化を使い、retrainingや較正なしでOPT-175Bまで4-bit化し、小さい精度低下に抑えている。一方3-bitでは品質維持が難しかったと報告している。

この圧縮構成は `FlexGen (c)` として非圧縮版と分けて評価されている。

## 評価

### まず見るところ

FlexGenのheadline 高速化倍率は、**1 リクエストの遅延改善ではなく、非常に長い遅延を許容してバッチを大きくしたときの最大 スループット改善**である。

したがって「OPT-175Bを16GB GPUで100倍高速化した」と読むのは不正確で、正しくは「既存オフロード システムがメモリ制約でバッチ 1〜2しか使えない条件で、FlexGenはCPU/SSDも使って桁違いに大きい実効 バッチを成立させ、総生成スループットを上げた」である。

### Hardware

主評価環境は次の通り。

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA T4 16GB ×1 |
| CPU | Intel Xeon 2.00GHz |
| CPU DRAM | 208GB |
| SSD | 1.5TB NVMe |
| SSD 読出し | 約2GB/s |
| SSD write | 約1GB/s |
| Model | OPT-6.7B / 30B / 175B |
| 比較対象 | Hugging Face Accelerate、DeepSpeed ZeRO-Inference、Petalsほか |

追加評価ではRTX 3090 24GB + 125GB CPU メモリ + 1TB SSDも使っている。興味深いのは、GPUが3090の方が強くても、175B級オフロードではCPU メモリが少ないためT4構成より不利になる場合がある点である。**オフロード システムではGPU性能だけでなくホスト メモリ容量がスループットを左右する**。

### OPT-175B: memory制約をbatch拡大へ変える

入力 512 トークン、出力 32 トークンの代表条件で、DeepSpeed ZeRO-Inferenceはバッチ サイズ 1〜2程度に制限される。

同じ約5000秒の遅延 budgetでは、FlexGenは実効 バッチ 64を使い、DeepSpeedより40倍超のスループットを達成した。

さらに遅延を約12000秒まで許容すると、非圧縮FlexGenは実効 バッチ 256まで拡大し、比較対象比**最大69倍**のスループットを報告する。

4-bit圧縮版では重みをCPU DRAMへ収めてディスク オフロード自体を避けられる構成が成立し、実効 バッチ 144、約4000秒の遅延で**最大100倍**のスループット frontierを示す。

### 「1 token/s」の意味

論文abstractでは、OPT-175Bを単一16GB GPUで初めてgeneration スループット 1 トークン/s級まで持っていったことを強調している。

これは1 userが毎秒1 トークン受け取る対話的 streaming性能とは違う。多数リクエストをまとめて処理した**aggregate generation スループット**である。

この distinction はFlexGenを現在のonline 提供 システムと比較するときに特に重要である。

### I/O breakdown

OPT-175Bの実行時間内訳では、デコードでKV キャッシュ 読出しが非常に大きな割合を占める条件がある。Appendixの例ではデコード合計11315秒のうちキャッシュ 読出しが7046秒で、重み 読出し 3047秒より大きい。

つまり巨大モデルのオフロードでは「重みさえSSDから効率よく読めばよい」わけではなく、**長くなるKV キャッシュをどう配置・再利用するかが後半の主要ボトルネックになる**。

## 既存研究との差

### DeepSpeed ZeRO-Inferenceとの違い

ZeRO-Inferenceは学習由来の重み オフロードを中心に、必要層をGPUへ持ち込んで実行する。

FlexGenは推論専用に、重みだけでなく活性値とKV キャッシュまで配置 探索へ含め、さらにブロック 実行計画で一回の重み 読込を多数リクエストへ再利用する。

### Hugging Face Accelerateとの違い

Accelerateもモデルをdevice間へ分割できるが、スループット-指向にバッチ・テンソル 配置・実行順を共同最適化するシステムではない。175B級ではメモリ制約から小バッチに留まりやすい。

### 後続のKV / MoE offloadとの関係

FlexGenは密 モデル全体を対象にした汎用テンソル オフロードである。

後の研究では、

- FastDecode / NEO: KVと注意をCPU側へ寄せる
- KVPR / CAPTURE: KV 転送を部分再計算へ置換する
- MoE-Infinity等: 全重みではなく選択専門家だけを移動する

というように、FlexGenが扱った大きなdesign spaceの各部分を、モデル sparsityやonline 提供へ特化して細分化していく。

## 限界

- **遅延-sensitive 提供向けではない。** スループットのために数千〜1万秒規模のブロック 遅延を許容する評価がある。
- 大バッチで重み I/Oを償却する設計なので、リクエスト数が少ないと利点が小さい。
- SSD帯域、CPU DRAM容量、PCIe帯域への依存が強い。
- 4-bit圧縮版はfull precisionと数学的に同値ではない。
- 主モデルはOPT系列で、現在一般的なGQA、MoE、continuous batching、PagedAttention世代の提供 stackより古い設計である。
- 理論的により良いdiagonal ブロック 実行計画は、KV メモリ管理の実装難から本体ランタイムには採用されていない。
- variable-length リクエストはpaddingで揃えるため、現在のragged batchingより無駄が出やすい。

## 一般的な実装上の含意

FlexGenから現在でも有効な教訓は、オフロード性能を**単一の帯域値だけで判断しない**ことである。

SSDが2GB/sしかなくても、一回の重み 読出しを100 リクエストへ再利用できれば、リクエストあたりのI/O コストは大きく下がる。一方でKV キャッシュはリクエスト間共有できないため、バッチを増やすほど別のI/O ボトルネックとして成長する。

したがって階層メモリ型LLM推論では、少なくとも次を同時に見る必要がある。

1. **容量:** どのテンソルをどの階層へ置けばバッチを成立させられるか。
2. **再利用:** 1回のI/Oを何回の計算へ使い回せるか。
3. **重畳:** I/Oを他の計算 / I/Oの裏へどれだけ隠せるか。
4. **再計算との交換:** 古いテンソルを運ぶより作り直す方が安くないか。
5. **計算場所:** データを計算へ運ぶより、計算をデータ側へ寄せる方がよくないか。

後続のMoE 専門家 オフロードやKV オフロードの多くは、この5点のどれかをより細かい単位で最適化したものと見ることができる。

## 実装状況

公式実装は `FMInference/FlexGen` として公開されている。研究prototypeとしてOPT系列のオフロード、圧縮、パイプライン parallelismを実装する。
