# FlexGen: High-Throughput Generative Inference of Large Language Models with a Single GPU

> FlexGenは、巨大LLMを単一GPUで動かすときに「GPUへ載らない重みをCPUやSSDへ逃がす」だけでなく、**重み・中間活性・KV cacheの保存先と、計算順序そのものを一緒に設計する**ことで、遅いI/Oを大きなbatchへ分散し、offline throughputを上げるsystemである。

## 概要

FlexGenが対象にするのは、chatのように1 requestの応答をすぐ返す用途ではなく、benchmark、情報抽出、document処理のような**多少待ってもよい代わりに、多数のrequestをできるだけ安く処理したい生成処理**である。論文ではこれをthroughput-oriented generative inferenceと呼ぶ。

単一16GB GPUで175B級modelを扱う場合、重みだけでもGPUへ収まらない。そこでCPU DRAMやNVMe SSDを使うのは自然だが、単純に「必要なlayerをSSDから読み、計算し、次へ進む」とすると、GPUはほとんどの時間をI/O待ちに使ってしまう。

FlexGenの発想は、**latencyを許容できるなら、一度読み込んだdataをできるだけ多くのrequestへ使い回せばよい**というものだ。そのために生成処理をbatch・token・layerの3軸で並べ替え、同じlayerの重みを多数requestへ使い回す。

さらにFlexGenは、次の3種類のtensorを別々に扱う。

- **重み (weights)**: 全requestで共有できるが非常に大きい。
- **中間活性 (activations)**: requestごとに異なるが、1時点で必要な量は比較的小さい。
- **KV cache**: requestごとに異なり、生成が進むほど増え続ける。

この3種類は「容量」「再利用性」「毎tokenでの読み方」が異なるため、全部を同じoffload policyで扱うと無駄が出る。FlexGenはGPU・CPU・SSDへの配置比率を個別に決め、さらにKV cacheがCPUにある場合はattention score計算自体をCPUへ寄せる選択肢も持つ。

## 問題設定

### 単純なweight offloadだけではbatchを大きくできない

巨大modelで最初に問題になるのは重み容量だが、生成ではKV cacheも無視できない。batch sizeを増やすとrequest数に比例してKV cacheが増えるため、重みだけをCPUへ追い出しても、今度はGPU上のKV cacheがbatch sizeの上限になる。

既存のoffload systemでは、trainingで使われたlayer-by-layerの実行順をほぼそのまま推論へ流用することが多かった。この場合、巨大な重みを何度もCPUやSSDから読み直すうえ、KV cacheをGPUへ保持するためbatchも大きくしにくい。

FlexGenは、**GPU memoryを「何を常駐させるか」ではなく、「どれだけ大きなbatchを成立させ、そのbatchで何回I/Oを再利用できるか」から逆算する**。

### 遅いSSDでも、1回のreadを多数requestへ使えばthroughputは上げられる

主評価環境ではGPUがNVIDIA T4 16GB、CPU DRAMが208GB、NVMe SSDが1.5TBで、SSD read帯域は約2GB/sである。GPUの演算能力に比べるとSSDは非常に遅い。

しかし、例えば1 layer分の重みをSSDから一度読み込んだあと、その重みで1 requestだけでなく数十〜数百requestを処理できれば、1 requestあたりのweight I/O costは大きく下がる。

そのためFlexGenでは、**大batchを成立させるためにKV cacheまでCPUやSSDへ逃がし、その代わりweight readを多数requestで償却する**という、interactive servingとは逆方向のtrade-offを積極的に使う。

## 手法のあらまし

FlexGenの実行は、概念的には次の順序で理解すると分かりやすい。

1. GPU・CPU DRAM・SSDの容量と帯域を測る。
2. 重み・中間活性・KV cacheを各階層へ何割置くか候補を作る。
3. 1回のGPU batch sizeと、それを何個まとめて1 blockとして処理するかを決める。
4. 同じlayerをblock内の多数batchへまとめて実行し、重みの再読込回数を減らす。
5. 次layerの重みload、次batchのcache/activation load、前batchのstoreをGPU計算と重ねる。
6. 必要ならKV cacheがCPUにあるrequestではattention score計算をCPUへ委譲する。
7. 容量やI/Oがさらに厳しい場合は、重みとKV cacheを4-bitへ圧縮する。

つまりFlexGenは単一のoffload技法ではなく、**配置・計算順・計算場所・圧縮を一つのcost modelで選ぶsystem**である。

## 手法

### 1. 3階層memoryへtensor種別ごとの配置比率を決める

FlexGenはGPU、CPU DRAM、diskを3段階のmemory hierarchyとして扱う。

各tensor種別について、例えば重みなら

- GPUに何%置くか
- CPUに何%置くか
- SSDに何%置くか

を決める。同様に中間活性とKV cacheにも別の配置比率を持つ。

重要なのは、**「あるlayerはGPU、別layerはSSD」と固定するだけではない**点である。実行scheduleと組み合わせ、必要な時点だけGPUへ持ち込み、計算後に下位階層へ戻すことを前提にplacementを決める。

重みはlayer単位、中間活性とKV cacheはtensor単位の粒度で移動する。この粒度は、細かすぎるtransferによるruntime overheadと、粗すぎる配置による柔軟性低下の折衷として選ばれている。

### 2. block scheduleで重みを多数requestへ使い回す

通常の生成を素直に書くと、各requestについてtoken 1の全layer、token 2の全layer、という順に進めたくなる。しかしoffload環境では、この順序だと同じlayerの重みを何度も読み込む。

FlexGenは処理を大きな**block**にまとめる。blockの中では、あるlayerの重みをGPUへ読み込んだら、複数GPU batchの同じlayer処理を連続して実行してから次layerへ進む。

直感的には、

`重みAを読む → request群全部にAを使う → 重みBを読む → request群全部にBを使う`

という順序である。

この実装済みscheduleは論文で**ジグザグblock schedule (zig-zag block schedule)** と呼ばれる。I/O量の観点では理論最適そのものではないが、論文はそのI/O complexityが最適解の2倍以内であることを示している。

よりI/O効率のよい**対角block schedule (diagonal block schedule)** も理論的に示されるが、KV cacheを非連続memory上で動的に管理する実装が複雑なため、本体systemではzig-zag方式を採用している。

### 3. GPU batchとblock sizeを分ける

FlexGenでは「GPUへ一度に入れるbatch」と「同じweight loadで処理する全request数」を分ける。

GPU memoryへ一度に載るrequest数が小さくても、例えばGPU batchを何回も繰り返して一つのblockを構成すれば、同じlayer weightをCPU/SSDから1回読み込んだまま、多数requestへ再利用できる。

この構造により、GPU memoryが小さくても**実効batch size**を大きくできる。OPT-175Bの評価でbaselineより大きなbatchを成立させられる主因がここにある。

### 4. I/Oとcomputeをpipelineで重ねる

block scheduleだけでは、dataを読む時間そのものは残る。そこでFlexGenは複数のCUDA streamやCPU threadを使い、

- 次layerのweight load
- 次batchのactivation / KV load
- 前batchのactivation / KV store
- 現在batchのGPU compute

を可能な範囲で並行させる。

ここで重要なのは、I/O時間をゼロにするのではなく、**critical pathから外せるI/OをGPU計算の裏へ隠す**ことである。

SSD→CPUとCPU→GPUも別経路なので、pipelineが十分埋まれば複数階層の転送を同時に進められる。

### 5. KVがCPUにある場合はattentionをCPUへ寄せられる

decode attentionでは、現在tokenのqueryは小さい一方、過去全tokenのK/Vは長contextになるほど大きい。

KV cacheをCPUに保存している場合、それを毎token GPUへ全部戻してattention scoreを計算するとPCIe trafficが大きい。そこでFlexGenは、場合によっては**attention score計算そのものをCPUで実行する**。

この場合、GPUからCPUへ送るのは現在tokenの比較的小さいactivationで済み、巨大なKV全体をGPUへ移す必要がない。

後のFastDecodeやNEOが「KVのあるCPUへattention computeを寄せる」設計を本格化するが、その基本的な計算委譲の考え方はFlexGenにもすでに含まれている。

### 6. 線形計画法でplacementを探索する

候補を人手で選ぶのではなく、FlexGenはhardware profileからcost modelを作る。

固定したGPU batch sizeとblock sizeについて、

- GPU / CPU / SSDのmemory capacityを超えない
- 各data pathのI/O時間を見積もる
- GPU compute時間を見積もる
- 1 blockの総実行時間を最小化する

という問題を解く。

placementについては主要変数が9個程度の**線形計画問題 (linear programming problem)** に整理されるため、探索自体は高速である。

つまり「CPU memoryが多いmachineではKVをCPUへ多めに置く」「SSDが遅いmachineでは重みをできるだけCPUへ寄せる」といった判断を、同じframeworkからhardware別に出せる。

### 7. 4-bit圧縮でI/Oそのものも減らす

FlexGenは重みとattention用KV cacheを4-bitへ圧縮するoptionも持つ。

目的は単にVRAMを節約することではなく、**CPU/SSDから運ぶbyte数を減らすこと**である。offload systemではtensorが下位memoryにある時間が長いため、圧縮によるI/O削減の価値が大きい。

論文では細粒度のgroup-wise quantizationを使い、retrainingやcalibrationなしでOPT-175Bまで4-bit化し、小さい精度低下に抑えている。一方3-bitでは品質維持が難しかったと報告している。

この圧縮構成は `FlexGen (c)` として非圧縮版と分けて評価されている。

## 評価

### まず見るところ

FlexGenのheadline speedupは、**1 requestのlatency改善ではなく、非常に長いlatencyを許容してbatchを大きくしたときのmaximum throughput改善**である。

したがって「OPT-175Bを16GB GPUで100倍高速化した」と読むのは不正確で、正しくは「既存offload systemがmemory制約でbatch 1〜2しか使えない条件で、FlexGenはCPU/SSDも使って桁違いに大きいeffective batchを成立させ、総生成throughputを上げた」である。

### Hardware

主評価環境は次の通り。

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA T4 16GB ×1 |
| CPU | Intel Xeon 2.00GHz |
| CPU DRAM | 208GB |
| SSD | 1.5TB NVMe |
| SSD read | 約2GB/s |
| SSD write | 約1GB/s |
| Model | OPT-6.7B / 30B / 175B |
| Baseline | Hugging Face Accelerate、DeepSpeed ZeRO-Inference、Petalsほか |

追加評価ではRTX 3090 24GB + 125GB CPU memory + 1TB SSDも使っている。興味深いのは、GPUが3090の方が強くても、175B級offloadではCPU memoryが少ないためT4構成より不利になる場合がある点である。**offload systemではGPU性能だけでなくhost memory容量がthroughputを左右する**。

### OPT-175B: memory制約をbatch拡大へ変える

input 512 token、output 32 tokenの代表条件で、DeepSpeed ZeRO-Inferenceはbatch size 1〜2程度に制限される。

同じ約5000秒のlatency budgetでは、FlexGenはeffective batch 64を使い、DeepSpeedより40倍超のthroughputを達成した。

さらにlatencyを約12000秒まで許容すると、非圧縮FlexGenはeffective batch 256まで拡大し、baseline比**最大69倍**のthroughputを報告する。

4-bit圧縮版では重みをCPU DRAMへ収めてdisk offload自体を避けられる構成が成立し、effective batch 144、約4000秒のlatencyで**最大100倍**のthroughput frontierを示す。

### 「1 token/s」の意味

論文abstractでは、OPT-175Bを単一16GB GPUで初めてgeneration throughput 1 token/s級まで持っていったことを強調している。

これは1 userが毎秒1 token受け取るinteractive streaming性能とは違う。多数requestをまとめて処理した**aggregate generation throughput**である。

この distinction はFlexGenを現在のonline serving systemと比較するときに特に重要である。

### I/O breakdown

OPT-175Bの実行時間内訳では、decodeでKV cache readが非常に大きな割合を占める条件がある。Appendixの例ではdecode合計11315秒のうちcache readが7046秒で、weight read 3047秒より大きい。

つまり巨大modelのoffloadでは「重みさえSSDから効率よく読めばよい」わけではなく、**長くなるKV cacheをどう配置・再利用するかが後半の主要bottleneckになる**。

## 既存研究との差

### DeepSpeed ZeRO-Inferenceとの違い

ZeRO-Inferenceはtraining由来のweight offloadを中心に、必要layerをGPUへ持ち込んで実行する。

FlexGenは推論専用に、重みだけでなくactivationとKV cacheまでplacement searchへ含め、さらにblock scheduleで一回のweight loadを多数requestへ再利用する。

### Hugging Face Accelerateとの違い

Accelerateもmodelをdevice間へ分割できるが、throughput-orientedにbatch・tensor placement・実行順を共同最適化するsystemではない。175B級ではmemory制約から小batchに留まりやすい。

### 後続のKV / MoE offloadとの関係

FlexGenはdense model全体を対象にした汎用tensor offloadである。

後の研究では、

- FastDecode / NEO: KVとattentionをCPU側へ寄せる
- KVPR / CAPTURE: KV transferを部分再計算へ置換する
- MoE-Infinity等: 全weightではなく選択expertだけを移動する

というように、FlexGenが扱った大きなdesign spaceの各部分を、model sparsityやonline servingへ特化して細分化していく。

## 限界

- **latency-sensitive serving向けではない。** throughputのために数千〜1万秒規模のblock latencyを許容する評価がある。
- 大batchでweight I/Oを償却する設計なので、request数が少ないと利点が小さい。
- SSD帯域、CPU DRAM容量、PCIe帯域への依存が強い。
- 4-bit圧縮版はfull precisionと数学的に同値ではない。
- 主modelはOPT系列で、現在一般的なGQA、MoE、continuous batching、PagedAttention世代のserving stackより古い設計である。
- 理論的により良いdiagonal block scheduleは、KV memory管理の実装難から本体runtimeには採用されていない。
- variable-length requestはpaddingで揃えるため、現在のragged batchingより無駄が出やすい。

## 一般的な実装上の含意

FlexGenから現在でも有効な教訓は、offload性能を**単一の帯域値だけで判断しない**ことである。

SSDが2GB/sしかなくても、一回のweight readを100 requestへ再利用できれば、requestあたりのI/O costは大きく下がる。一方でKV cacheはrequest間共有できないため、batchを増やすほど別のI/O bottleneckとして成長する。

したがって階層memory型LLM推論では、少なくとも次を同時に見る必要がある。

1. **容量:** どのtensorをどの階層へ置けばbatchを成立させられるか。
2. **再利用:** 1回のI/Oを何回のcomputeへ使い回せるか。
3. **重畳:** I/Oを他のcompute / I/Oの裏へどれだけ隠せるか。
4. **再計算との交換:** 古いtensorを運ぶより作り直す方が安くないか。
5. **計算場所:** dataをcomputeへ運ぶより、computeをdata側へ寄せる方がよくないか。

後続のMoE expert offloadやKV offloadの多くは、この5点のどれかをより細かい単位で最適化したものと見ることができる。
