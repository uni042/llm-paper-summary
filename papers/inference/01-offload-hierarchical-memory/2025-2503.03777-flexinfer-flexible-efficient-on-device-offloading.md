# FlexInfer: Breaking Memory Constraint via Flexible and Efficient Offloading for On-Device LLM Inference

> 重み読出しを計算と非同期化し、各層へ固定メモリを均等配分し、容量に応じて保持テンソルを切り替えることで、端末向けCPU推論をmmap比最大12.5倍高速化する。

## 概要
FlexInferは、端末内メモリに収まらない大規模言語モデルをCPU中心のローカル環境で動かすと、重みをストレージから都度読み込む入出力が推論を支配する問題を扱う。計算と重み読出しを別スレッドで重ねる非同期先読み、利用可能メモリを各層へ均等に割り当てて読出し量を平準化するメモリ固定、残り容量に応じて注意機構または全結合ネットワークのテンソルを選択保持する方式を組み合わせる。llama.cppを828行のC/C++で拡張し、4ビット量子化したLlama 2とCodeLlamaをCPU上で評価した結果、mmap方式に対して最大12.5倍のスループットを報告する。モデル自体を剪定・蒸留せず、利用者が指定したメモリ上限へ実行時の配置を適応させる点が特徴である。

中心的な発想は、利用可能メモリを単なる大きなキャッシュとして使うのではなく、各層で残る入出力量ができるだけ均一になるよう配り、さらにテンソルの大きさと読出し効率を見て保持対象を切り替える点にある。非同期先読みで計算と読出しを重ねても、ある層だけ大きなテンソルをストレージから読むとその層が律速になるため、メモリ固定を全層へ均等化する。また空き容量が少ないときは小さな注意機構テンソルを優先して多数の読出しを消し、容量が増えると大きな全結合ネットワークのテンソルを保持して転送量そのものを減らす。この二段階の判断により、同じメモリ量でも入出力と計算の重なりを維持しやすくする。
## 問題設定
端末内で大規模言語モデルを動かす場合、モデル重みが物理メモリに収まらないとストレージ上の重みを層ごとに読みながら計算する必要がある。llama.cppのmmap方式はオペレーティングシステムのページフォールトに依存して必要ページを同期的に取り込むため、計算スレッドが入出力完了を待ち、生成速度がストレージ帯域に強く制約される。一方、量子化・剪定・蒸留はモデル自体を小さくできるが、品質変化を伴い得るうえ、利用者ごとに異なる空きメモリ量へ柔軟に合わせにくい。単純な先読みだけでも、余ったメモリの使い方が層ごとに偏ると入出力量が不均一になり、ある層では計算より読出しが長くなって待ちが再発する。FlexInferはモデル内容を変えず、ストレージ読出し、計算、メモリ保持の三者を協調させてこの待ち時間を隠す。
## 新規性
中心的な発想は、利用可能メモリを単なる大きなキャッシュとして使うのではなく、各層で残る入出力量ができるだけ均一になるよう配り、さらにテンソルの大きさと読出し効率を見て保持対象を切り替える点にある。非同期先読みで計算と読出しを重ねても、ある層だけ大きなテンソルをストレージから読むとその層が律速になるため、メモリ固定を全層へ均等化する。また空き容量が少ないときは小さな注意機構テンソルを優先して多数の読出しを消し、容量が増えると大きな全結合ネットワークのテンソルを保持して転送量そのものを減らす。この二段階の判断により、同じメモリ量でも入出力と計算の重なりを維持しやすくする。
## 手法
### 手法のあらまし
実行時には、計算用スレッドとは別に複数の入出力スレッドを用意し、現在計算している層より数層先の重みテンソルを直接入出力でストレージから読み込む。既定の先読み窓は3層で、窓内のテンソルが用意できた層から計算スレッドが処理し、使用後の一時重みは解放する。これにより、ある層をCPUで計算している時間を次層の重み読出しに使う。次に、利用者が指定したメモリ上限から先読みバッファに必要な容量を差し引き、残りを恒久的な重み保持へ割り当てる。ここで先頭の層から丸ごと固定すると後半層だけ大きな入出力が残るため、FlexInferは各層へ同程度の保持量を配り、層ごとの残存読出し時間を平準化する。最後に、各層内でどのテンソルを保持するかを空き容量に応じて変える。小容量では比較的小さい注意機構の重みを優先し、多数の小さな読出しと断片化を減らす。容量が増えると全結合ネットワークの大きな重みを層横断で少しずつ保持し、ストレージから読む総バイト数を減らす。グループ化クエリ注意では特に小さいキー・値射影を優先できる。これらの配置を推論開始前に決め、その後の各トークン生成では同じ層順序を繰り返すため、先読み順序を安定して予測できる。

### 非同期先読み
計算スレッドが現在層を処理している間に、独立した複数の入出力スレッドが後続層のテンソルを先回りして読み込む。テンソル単位で作業を分け、直接入出力を用いてページキャッシュを経由する余分なコピーやページフォールト依存を避ける。既定では3層分の窓を持ち、窓を広げれば入出力をより早く開始できる一方、その分だけ一時バッファのメモリ消費が増える。各テンソルは計算で一度使った後に解放され、次トークンでは再び同じ順序で読み込むため、デコードの規則的な層走査を利用して計算時間の背後へストレージ待ちを隠す。

### 均衡メモリ固定
余剰メモリがある場合に、先頭層を丸ごと固定する単純方式では、固定済み層の入出力はゼロでも後続層には大きな読出しが残り、後半で計算が停止する。FlexInferは固定できる重み量を全デコード層へ分散し、各層でストレージから残って読む量をほぼ均等にする。狙いは総読出し量だけでなく、各層の読出し時間をその層の計算時間以下へ近づけることである。層ごとの入出力が平準化されると、非同期先読みが安定して計算の後ろに隠れ、追加メモリを増やしたときの性能改善も段階的に得やすくなる。この配分は、同じ固定容量でも長い入出力を持つ単一層がパイプライン全体を止める尾部遅延を避ける役割を持つ。したがって、保持量の最大化ではなく層ごとの残存読出し時間の均一化を目標にする点が、単純な前方層優先固定との本質的な差である。

### 柔軟テンソル保持
Transformer層では注意機構と全結合ネットワークでテンソル寸法が異なり、同じメモリ量でも何を残すかで入出力効率が変わる。空き容量が小さい範囲では小さい注意機構テンソルを優先し、限られた容量で多くの読出し要求を消す。容量が大きくなると、大きな全結合ネットワーク重みを各層にまたがって保持し、総転送量を大きく削る。中間領域では大きな重みを層横断で段階的に増やしてから残りを小テンソルで埋める。グループ化クエリ注意ではキー・値射影が特に小さいため優先保持の効果が高く、モデル構造に合わせて固定対象を変える。

### 全体のデータ／制御の流れ
FlexInferはllama.cppのCPU推論経路を拡張し、利用可能メモリ量と入出力スレッド数を実行時引数として受け取る。埋め込みなど常駐させる部分を除き、デコード層の重みを固定領域と先読み領域へ分ける。固定領域は全層へ均等に配り、先読み領域は循環バッファとして後続層のテンソルを受け取る。計算側は必要テンソルの準備完了を同期点として待つが、通常は前層の計算中に読出しが済むため待機を隠せる。ストレージが遅すぎる、CPU計算が速すぎる、または先読み窓を確保できないほどメモリが小さい場合は入出力が再び表面化し、性能はストレージ帯域へ近づく。
## 評価条件
- **ハードウェア**: Ubuntuを動かすAMD Ryzen Threadripper PRO 7995WX搭載サーバ、主記憶512GB。cgroupで利用可能メモリ、tasksetでCPUコア数を制限し、資源制約端末を模擬する。論文は端末に強力なGPUがない状況を主対象としてCPU推論を評価する。
- **ソフトウェア**: llama.cppを828行のC/C++で拡張したFlexInfer試作。ストレージ読出しには直接入出力を使い、計算スレッドと複数の入出力スレッドを分離する。先読み窓の既定値は3層。
- **データセット／トレース**: 自己回帰デコードのスループット評価
- **比較対象**: llama.cpp mmap、同期読出し、先読みのみ、均衡メモリ固定を除いた構成、注意機構優先保持、全結合ネットワーク優先保持
モデルごとに利用可能メモリ量を変化させ、トークン生成スループットを測る。mmapとの比較に加え、同期読出し、非同期先読み、均衡メモリ固定、柔軟テンソル保持を段階的に有効化した除去実験で各機構の寄与を測定する。保持戦略については注意機構テンソルを先に残す方式と全結合ネットワーク重みを先に残す方式を比較し、同じメモリ制約でどのテンソル構成が入出力待ちを減らすかを評価する。
実機測定ではあるが、スマートフォンや組み込み端末そのものではなく、高性能CPUサーバをcgroupとtasksetで制限して端末条件を模擬している。GPU/NPU経路、モバイルストレージ固有の帯域・熱制約、異なるモデル系列への一般化は直接評価していない。対象モデルは4ビット量子化されたLlama 2とCodeLlamaであり、規則的なTransformer層構造と反復デコードを前提とする。
## 主要結果
FlexInferは、モデル全体がメモリに収まらない条件でllama.cppのmmap方式より一貫して高い生成スループットを示し、Llama 2 7Bでは条件により5.2〜12.5倍、13Bでは5.0〜11.8倍、CodeLlama 34Bでは4.2〜10.6倍、Llama 2 70Bでは5.0〜11.0倍の高速化を報告する。除去実験では、同期読出しだけでも低メモリ条件のmmapより2.6〜3倍速くなり、入出力経路自体が大きな律速であることを確認する。さらに非同期先読み、層間で均等化したメモリ固定、容量依存のテンソル保持を加えるほど、計算とストレージ読出しの重なりが増え、追加メモリを性能へ変換しやすくなる。

- 生成スループット高速化 / 最大12.5倍 (比較対象: llama.cpp mmap; 条件: 4ビットLlama 2 7B、利用可能メモリを制限したCPU推論) — ページフォールトに依存する同期的なmmap読出しを、明示的な直接入出力と計算・読出しの重畳へ置き換える効果が最も大きい条件では一桁以上の高速化になる。

- 非同期先読みの追加改善 / 34.8〜59.4%改善、メモリ増加時は最大69.9〜118.8%改善 (比較対象: 同期読出し構成; 条件: 各モデルの資源制約設定で先読みを追加) — 計算中に後続層の重み読出しを進められるため、CPU計算時間で入出力待ちを隠せる。空きメモリが増えると先読みと固定領域を確保しやすくなり利得が拡大する。

- 均衡メモリ固定の改善 / 最小メモリ条件で9.2〜11.1%、余裕のある条件で56.8〜83.3%改善 (比較対象: 層間で不均衡なメモリ固定; 条件: 同量の重みを保持しつつ固定位置だけを変更) — 総保持量が同じでも、固定領域を全層へ分散して各層の残存読出しを平準化すると、局所的な長い入出力が計算を止める事態を減らせる。

- 柔軟テンソル保持の改善 / 7Bで注意機構優先比最大21.9%、全結合ネットワーク優先比最大12.0%；13Bでそれぞれ最大7.8%、14.6% (比較対象: 単一種類を常に優先する保持戦略; 条件: Llama 2 7B/13Bで利用可能メモリ量を変化) — 小容量では小テンソルを多数残す方が有利だが、容量が増えると大きな全結合ネットワーク重みを保持して総転送量を減らす方が有利になり、固定戦略では両領域を同時に最適化できない。

### 負の結果・境界条件
- 入出力が計算時間内に隠れないほどストレージが遅い場合や、先読みバッファを十分確保できない極端な低メモリ条件では性能は依然として入出力帯域に制約される。34B/70Bではグループ化クエリ注意によりテンソル構成が偏り、柔軟保持と注意機構優先の差が小さくなるため、論文は7B/13Bほど明確な保持戦略差を示していない。また実機スマートフォンではなく制限したサーバCPU上の評価であるため、モバイルストレージや熱制約下の絶対性能は未確認である。

### 結果の読み方
改善幅がメモリ量とモデル構造で変わるのは、FlexInferが単に読出し回数を減らすのではなく、各層の計算時間に対して残存入出力時間をどれだけ隠せるかを最適化するためである。最低限のメモリでは非同期化そのものが主な利得となり、余裕が出ると固定重みを層間で均等化する効果が増える。さらに保持可能量が大きくなると、大きなテンソルを残して総転送バイトを減らす方が有利になる。したがって、利用可能メモリの増加を段階的に待ち時間削減へ変換する設計が、固定的なmmapや一律保持方式との差を生む。
## 品質への影響
評価対象は同一の4ビット量子化モデルであり、FlexInferは重み値や生成アルゴリズムを変更しない。したがってFlexInferによる追加の近似誤差や精度低下はなく、性能差は重み配置と入出力スケジュールに由来する。元の4ビット量子化による品質影響はFlexInfer固有の効果ではない。
## 既存研究との差
FlexGenはGPU・CPU・SSD間で重み、活性値、KVキャッシュを配置し、バッチ推論向けにオフロード計画を最適化するのに対し、FlexInferはGPUを前提にしない端末側CPU推論で、ストレージからの重み読出しを計算へ重ねることに焦点を置く。llama.cppのmmap方式とは、オペレーティングシステム任せのページフォールトではなく、明示的な複数スレッド直接入出力と先読み窓を使う点が異なる。LLM in a FlashやPowerInferのような方式は疎性や選択的重み読出しを利用するが、FlexInferは全モデル重みを保持したまま配置と転送だけを変える。vLLMのPagedAttentionは主にサーバ推論のKVキャッシュ管理を扱うため、モデル重みそのものが端末メモリに収まらない問題とは対象資源が異なる。
## 限界
評価は高性能CPUサーバ上でcgroupとtasksetを用いて資源制約端末を模擬しており、スマートフォン、組み込みSoC、NPU、モバイル向けGPUでの実測ではない。対象はLlama 2とCodeLlamaの4ビット量子化モデルで、層構造が規則的かつデコード時の重みアクセス順が予測可能であることを利用するため、動的な専門家選択を伴う混合専門家モデルなどでは同じ先読み規則がそのまま成立しない可能性がある。性能はストレージ帯域、直接入出力の特性、CPU計算速度に依存し、入出力が計算より大幅に遅い条件では先読みだけで完全には隠せない。一次資料から著者公式コード公開先は確認できず、再現性の追加確認が必要である。
## 実装状態
論文はllama.cppへ828行のC/C++変更を加えた試作実装を用いて実測している。利用可能メモリ量と入出力スレッド数を指定でき、先読み窓は既定3層、ストレージ読出しには直接入出力を用いる。2026-09-14時点でarXiv一次資料には公式リポジトリURLが示されておらず、外部検索で著者公式実装を確定できなかったため、コード公開状況は未確認として扱う。
## 研究上の位置づけ
端末内LLM推論のメモリ不足に対し、モデル圧縮ではなく階層メモリと入出力スケジューリングで解く系統に位置する。特に、追加メモリを単純なキャッシュ容量として扱わず、層ごとの残存入出力量を均等化することで非同期先読みの隠蔽率を高める点は、SSD・CPU・GPU階層オフロードにも応用可能な設計原理である。一方で評価環境はCPUサーバによる端末模擬であり、実モバイルSoCの共有メモリ、NPU、熱・電力制約まで含む共同設計ではない。このため、端末実機系の後続研究と比較する際は、FlexInferを『モデル重みオフロードのソフトウェア基準』として扱い、ハードウェア固有最適化とは分離して比較するのが適切である。
