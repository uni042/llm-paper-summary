# Taming Latency-Memory Trade-Off in MoE-Based LLM Serving via Fine-Grained Expert Offloading

> 生成反復ごとのルーティング履歴とプロンプトの類似性から近い過去リクエストを探し、次に使われそうなエキスパートだけを先読み・GPUキャッシュへ保持して、小さいVRAMでもエキスパート転送待ちを減らす無損失オフロード方式。

## 概要
fMoE（改訂版では **FineMoE**）は、エキスパート重み本体をCPU DRAMへ置き、GPU側の小さなエキスパートキャッシュを**反復単位のルーティング履歴とプロンプトの意味的類似性**で制御するMoE 提供 システムである。

題名の`fine-grained`はエキスパート重みを細かいブロックへ分割する意味ではなく、**リクエスト全体の平均ではなく、生成反復ごとのルーティング変化を追う**という時間粒度の細かさを指す。

MoE-Infinityがリクエスト-水準のルーティング パターンを使うのに対し、FineMoEは反復単位の`Expert Map`を保存することで、次の数層で必要なエキスパートをより狭く予測する。予測はプリフェッチにのみ使い、ネイティブルータが選んだエキスパートは最終的に必ず実行するため無損失である。

## 手法のあらまし

FineMoEでは、反復ごとのルーティング情報を保存する `Expert Map`、ルーティング履歴の近さ、プロンプト内容の近さ、何層先を読むか、何個のエキスパートまで先読みするか、という5つの要素が中心になる。

### 1. `Expert Map`：iterationごとのrouting分布を保存する

各生成反復について、各MoE層のゲート確率分布をまとめたものが **エキスパート 対応表** である。

単に「エキスパート 5が何回選ばれたか」を数えるのではなく、

- どの層で
- どのエキスパートに
- どれくらいのゲート 確率が付いたか

を保持する。

リクエスト全体へ集約せず反復ごとに残すため、生成途中でルーティング傾向が変わっても追いやすい。

### 2. Routingの動き方が似た過去iterationを探す

論文ではこの比較を **軌跡 類似度** と呼ぶ。現在のエキスパート 対応表と過去のエキスパート 対応表を比べ、**層を進む中でエキスパート選択が似た履歴**を探す。

MoE-Infinityのリクエスト-水準 EAMより時間粒度が細かいため、例えば同じリクエストの前半と後半でエキスパート分布が変わっても、現在の局所パターンに近い履歴を使える。

この細粒度化によって、**次に使われるエキスパート候補のばらつきを小さくし、無駄プリフェッチを減らす**のが狙いである。

### 3. Prompt内容の近さも補助信号にする

ルーティング履歴だけでなく、プロンプト 埋め込みの近さも検索に使う。論文ではこれを **意味 類似度** と呼ぶ。

同じルーティング パターンでもプロンプトの意味が大きく違えば将来のエキスパート利用が分岐する可能性があるため、ルーティング履歴と意味情報を組み合わせて候補を絞る。

重要なのは、意味 埋め込みがルータを置き換えるわけではなく、**どの過去エキスパート 対応表を参照するかを決める補助特徴**だという点である。

### 4. 何expertまでprefetchするかを累積確率で決める

検索したエキスパート 対応表から各層のエキスパート 確率を得た後、上位エキスパートを順に足し、累積確率が設定値 `δ` に達するまでをプリフェッチ対象にする。

`δ`を大きくすると、

- ネイティブエキスパートを事前に含める確率は上がる
- その代わり余分なエキスパート 転送が増える

というトレードオフになる。

したがって`δ`は、**キャッシュ ヒット率とPCIe 通信量のどちらを優先するかを調整する設定値**である。

### 5. 何layer先から読み始めるかを調整する

`prefetch distance d` は、現在層から何層先のエキスパートを先読みするかを表す。

遠くから始めれば転送を隠す時間は増えるが、ルーティング予測が外れやすくなる。近すぎれば予測は当たりやすいが重み 到着が間に合わない。

FineMoEは反復単位 mapによって将来予測の候補を絞り、比較的遠い層を先読みしてもヒット率を保つことを狙う。

### 6. Cacheから外すexpertは将来予測と過去利用を両方見る

GPUキャッシュが満杯の場合、将来の予測確率と過去の訪問頻度を組み合わせ、価値が低いエキスパートから外す。

単純LRUより、**近い将来の再利用見込み**を含めてキャッシュ 空間を配分する。

ミスが発生した場合はプリフェッチを一時的に抑え、本当に必要なエキスパートのオンデマンド 読み込みを優先する。これにより誤プリフェッチがネイティブ 読み込みを邪魔し続けることを避ける。

### 7. 履歴検索を推論の待ち時間にしない

エキスパート 対応表の保存、類似履歴の検索、GPUキャッシュ管理を別構成要素 / スレッドとして動かし、C++ / CUDA 課題 poolで推論と並列化する。

つまりFineMoEは予測algorithmだけでなく、**過去履歴を探す処理自体をGPU計算の待ち時間にしないランタイム設計**まで含む。

## 評価

### まず見るところ
- **結論:** 反復単位ルーティング履歴とプロンプト類似性を使うと、小さいGPUエキスパートキャッシュでも既存オフロード方式よりTTFT / TPOTを減らせる。
- **実速度:** 改訂版ではDeepSpeed比TTFT 74%、TPOT 46%削減など、複数比較対象を上回る。
- **品質:** ネイティブエキスパートへ必ずfallbackする無損失構成。
- **メモリ・I/O:** エキスパート重みはCPU DRAM、GPUは小さなエキスパートキャッシュ。SSD / KVオフロードは未評価。
- **注意点:** ルーティング履歴・プロンプト分布の類似性と、ハードウェアに合った`δ` / `d`へ依存する。

### 実機環境

| 項目 | 設定 |
|---|---|
| GPU | RTX 3090 24 GB ×6 |
| GPU間 | NVLink |
| CPU | Threadripper PRO 3955WX 32-core |
| Host memory | 480 GB |
| PCIe | Gen4、約32 GB/s |

モデルはMixtral-8x7B、Qwen1.5-MoE、Phi-3.5-MoE。

### Workload

| Dataset | Prompt長 | 生成長 |
|---|---:|---:|
| LMSYS-Chat-1M | 平均37 | 約127 |
| ShareGPT | 平均43 | 約122 |

70%をエキスパート 対応表構築、30%をtestへ使う。

### 主なbaseline

| Baseline | 予測 / cache粒度 |
|---|---|
| DeepSpeed-Inference | エキスパートを予測せず必要時に読み込み |
| Mixtral-Offloading | 数層先を固定的に先読み + LRU |
| ProMoE | predictor型先読み（再実装） |
| MoE-Infinity | 要求-水準 ルーティング履歴 |

FineMoEの主な比較点は、MoE-Infinityより**反復単位へ時間粒度を細かくしたこと**である。

### 改訂版のTTFT削減

| 比較対象 | TTFT削減 |
|---|---:|
| DeepSpeed | **74%** |
| Mixtral-Offloading | **67%** |
| ProMoE | **56%** |
| MoE-Infinity | **53%** |

### 改訂版のTPOT削減

| 比較対象 | TPOT削減 |
|---|---:|
| DeepSpeed | **46%** |
| Mixtral-Offloading | **38%** |
| ProMoE | **27%** |
| MoE-Infinity | **22%** |

初期版abstractでは推論遅延 47%削減、エキスパート ヒット 率 36%改善、改訂版ではヒット 率 39%改善と報告される。版によって集計値が異なるため混同しない方がよい。

### GPU expert cacheを小さくした場合

キャッシュ容量を6〜96 GBへ変化させる。6 GBという厳しい条件でもTPOTは次の通り改善する。

| 比較対象 | 6 GB cacheでのTPOT削減 |
|---|---:|
| DeepSpeed | 36% |
| Mixtral-Offloading | 25% |
| ProMoE | 16% |
| MoE-Infinity | 29% |

この結果が「遅延-メモリ トレードオフ」という題名に対応しており、**大きなGPUキャッシュを確保できなくてもルーティング予測でミスを抑える**ことが主張の中心である。

### Expert Map Storeの容量

| 対応表数 | CPU memory |
|---:|---:|
| 32K entries | 200 MB未満 |
| 通常利用 | 約1K entriesで十分と報告 |

ルーティング履歴を保存するコストはエキスパート重み本体に比べ小さい。

### Online serving

Azureトレースから256リクエスト、平均2.91 req/sを再生している。対応表 Storeが空で過去履歴がない状態から始めても比較対象より優位を維持したと報告する。

### 別GPUでの傾向

A100 80 GB / HBM2e 2 TB/sでは6×RTX 3090環境より比較対象との差が縮む。

GPUメモリ帯域やGPUへ常駐できるエキスパート数が増えるほどオフロード自体のpenaltyが小さくなり、FineMoEの相対利得も小さくなるためである。

### 評価上の制約

- CPU DRAMへエキスパート正本を置けることが前提。
- SSD / HBF / CXLは評価していない。
- エキスパート 対応表が過去リクエスト分布を代表する必要がある。
- `δ`とプリフェッチ distance `d`はGPU / PCIe条件で再調整が必要。
- ProMoE比較は著者再実装。
- arXiv v1と改訂版でヒット-率等の数字が更新されている。
