# Taming Latency-Memory Trade-Off in MoE-Based LLM Serving via Fine-Grained Expert Offloading

> 生成iterationごとのrouting履歴とpromptの類似性から近い過去requestを探し、次に使われそうなexpertだけを先読み・GPU cacheへ保持して、小さいVRAMでもexpert転送待ちを減らすlossless offload方式。

## 概要
fMoE（改訂版では **FineMoE**）は、expert weight本体をCPU DRAMへ置き、GPU側の小さなexpert cacheを**iteration単位のrouting履歴とpromptの意味的類似性**で制御するMoE serving systemである。

題名の`fine-grained`はexpert weightを細かいblockへ分割する意味ではなく、**request全体の平均ではなく、生成iterationごとのrouting変化を追う**という時間粒度の細かさを指す。

MoE-Infinityがrequest-levelのrouting patternを使うのに対し、FineMoEはiteration-levelの`Expert Map`を保存することで、次の数layerで必要なexpertをより狭く予測する。予測はprefetchにのみ使い、native routerが選んだexpertは最終的に必ず実行するためlosslessである。

## 手法のあらまし

FineMoEでは、iterationごとのrouting情報を保存する `Expert Map`、routing履歴の近さ、prompt内容の近さ、何layer先を読むか、何個のexpertまで先読みするか、という5つの要素が中心になる。

### 1. `Expert Map`：iterationごとのrouting分布を保存する

各生成iterationについて、各MoE layerのgate確率分布をまとめたものが **Expert Map** である。

単に「expert 5が何回選ばれたか」を数えるのではなく、

- どのlayerで
- どのexpertに
- どれくらいのgate probabilityが付いたか

を保持する。

request全体へ集約せずiterationごとに残すため、生成途中でrouting傾向が変わっても追いやすい。

### 2. Routingの動き方が似た過去iterationを探す

論文ではこの比較を **trajectory similarity** と呼ぶ。現在のExpert Mapと過去のExpert Mapを比べ、**layerを進む中でexpert選択が似た履歴**を探す。

MoE-Infinityのrequest-level EAMより時間粒度が細かいため、例えば同じrequestの前半と後半でexpert分布が変わっても、現在の局所patternに近い履歴を使える。

この細粒度化によって、**次に使われるexpert候補のばらつきを小さくし、無駄prefetchを減らす**のが狙いである。

### 3. Prompt内容の近さも補助信号にする

routing履歴だけでなく、prompt embeddingの近さも検索に使う。論文ではこれを **semantic similarity** と呼ぶ。

同じrouting patternでもpromptの意味が大きく違えば将来のexpert利用が分岐する可能性があるため、routing履歴と意味情報を組み合わせて候補を絞る。

重要なのは、semantic embeddingがrouterを置き換えるわけではなく、**どの過去Expert Mapを参照するかを決める補助特徴**だという点である。

### 4. 何expertまでprefetchするかを累積確率で決める

検索したExpert Mapから各layerのexpert probabilityを得た後、上位expertを順に足し、累積確率が設定値 `δ` に達するまでをprefetch対象にする。

`δ`を大きくすると、

- native expertを事前に含める確率は上がる
- その代わり余分なexpert transferが増える

というtrade-offになる。

したがって`δ`は、**cache hit率とPCIe trafficのどちらを優先するかを調整する設定値**である。

### 5. 何layer先から読み始めるかを調整する

`prefetch distance d` は、現在layerから何layer先のexpertを先読みするかを表す。

遠くから始めればtransferを隠す時間は増えるが、routing予測が外れやすくなる。近すぎれば予測は当たりやすいがweight arrivalが間に合わない。

FineMoEはiteration-level mapによって将来予測の候補を絞り、比較的遠いlayerを先読みしてもhit率を保つことを狙う。

### 6. Cacheから外すexpertは将来予測と過去利用を両方見る

GPU cacheが満杯の場合、将来の予測確率と過去の訪問頻度を組み合わせ、価値が低いexpertから外す。

単純LRUより、**近い将来の再利用見込み**を含めてcache spaceを配分する。

missが発生した場合はprefetchを一時的に抑え、本当に必要なexpertのon-demand loadを優先する。これにより誤prefetchがnative loadを邪魔し続けることを避ける。

### 7. 履歴検索を推論の待ち時間にしない

Expert Mapの保存、類似履歴の検索、GPU cache管理を別component / threadとして動かし、C++ / CUDA task poolで推論と並列化する。

つまりFineMoEは予測algorithmだけでなく、**過去履歴を探す処理自体をGPU計算の待ち時間にしないruntime設計**まで含む。

## 評価

### まず見るところ
- **結論:** iteration-level routing履歴とprompt類似性を使うと、小さいGPU expert cacheでも既存offload方式よりTTFT / TPOTを減らせる。
- **実速度:** 改訂版ではDeepSpeed比TTFT 74%、TPOT 46%削減など、複数baselineを上回る。
- **品質:** native expertへ必ずfallbackするlossless構成。
- **メモリ・I/O:** expert weightはCPU DRAM、GPUは小さなexpert cache。SSD / KV offloadは未評価。
- **注意点:** routing履歴・prompt分布の類似性と、hardwareに合った`δ` / `d`へ依存する。

### Workload

| Dataset | Prompt長 | 生成長 |
|---|---:|---:|
| LMSYS-Chat-1M | 平均37 | 約127 |
| ShareGPT | 平均43 | 約122 |

### 主なbaseline

| Baseline | 予測 / cache粒度 |
|---|---|
| DeepSpeed-Inference | expertを予測せず必要時にload |
| Mixtral-Offloading | 数layer先を固定的に先読み + LRU |
| ProMoE | predictor型prefetch（再実装） |
| MoE-Infinity | request-level routing履歴 |

FineMoEの主な比較点は、MoE-Infinityより**iteration-levelへ時間粒度を細かくしたこと**である。

### 改訂版のTTFT削減

| 比較対象 | TTFT削減 |
|---|---:|
| DeepSpeed | **74%** |
| Mixtral-Offloading | **67%** |
| ProMoE | **56%** |
| MoE-Infinity | **53%** |

### 改訂版のTPOT削減

| 比較対象 | TPOT削減 |
|---|---:|
| DeepSpeed | **46%** |
| Mixtral-Offloading | **38%** |
| ProMoE | **27%** |
| MoE-Infinity | **22%** |

初期版abstractでは推論latency 47%削減、expert hit rate 36%改善、改訂版ではhit rate 39%改善と報告される。版によって集計値が異なるため混同しない方がよい。

### GPU expert cacheを小さくした場合

cache容量を6〜96 GBへ変化させる。6 GBという厳しい条件でもTPOTは次の通り改善する。

| 比較対象 | 6 GB cacheでのTPOT削減 |
|---|---:|
| DeepSpeed | 36% |
| Mixtral-Offloading | 25% |
| ProMoE | 16% |
| MoE-Infinity | 29% |

この結果が「latency-memory trade-off」という題名に対応しており、**大きなGPU cacheを確保できなくてもrouting予測でmissを抑える**ことが主張の中心である。

### Expert Map Storeの容量

| Map数 | CPU memory |
|---:|---:|
| 32K entries | 200 MB未満 |
| 通常利用 | 約1K entriesで十分と報告 |

routing履歴を保存するcostはexpert weight本体に比べ小さい。

### Online serving

Azure traceから256 request、平均2.91 req/sを再生している。Map Storeが空で過去履歴がない状態から始めてもbaselineより優位を維持したと報告する。

### 別GPUでの傾向

A100 80 GB / HBM2e 2 TB/sでは6×RTX 3090環境よりbaselineとの差が縮む。

GPU memory bandwidthやGPUへ常駐できるexpert数が増えるほどoffload自体のpenaltyが小さくなり、FineMoEの相対利得も小さくなるためである。

### 評価上の制約

- CPU DRAMへexpert正本を置けることが前提。
- SSD / HBF / CXLは評価していない。
- Expert Mapが過去request分布を代表する必要がある。
- `δ`とprefetch distance `d`はGPU / PCIe条件で再調整が必要。
- ProMoE比較は著者再実装。
- arXiv v1と改訂版でhit-rate等の数字が更新されている。
