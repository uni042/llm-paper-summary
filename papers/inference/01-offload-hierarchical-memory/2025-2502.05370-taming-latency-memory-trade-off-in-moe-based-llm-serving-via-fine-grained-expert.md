# FineMoE：反復ごとの専門家選択を予測する細粒度オフロード

## 概要

混合専門家モデル（Mixture-of-Experts; MoE）は、各トークンが一部の専門家だけを使うため計算量を抑えられる。しかし専門家全体の重みは大きく、GPUメモリへすべてを常駐させるのは難しい。CPUメモリへ専門家を退避するとGPU容量の不足は補えるが、必要な専門家をその都度PCIeで転送するため、推論の遅延が増える。先読みを使えば一部の転送をGPU計算と重ねられるものの、ルータが次に選ぶ専門家を正確に予測できなければ、使わない重みを転送したり、必要な重みを同期読み込みしたりする。

FineMoEは、生成反復ごとのルータ確率分布を記録したエキスパート対応表（Expert Map）を用いて、現在の要求と似た過去のルーティング軌跡を検索する。さらに入力プロンプトの意味的類似性を使い、将来選ばれやすい専門家を推定してGPUキャッシュへ先読みする。GPUに保持する専門家を細かく制御することで、限られたメモリでも専門家のキャッシュヒット率を高め、CPUからのオンデマンド転送を減らす。

本研究でいう「細粒度」は、専門家重みを小さなブロックに分割するという意味ではない。従来の要求全体の専門家使用頻度ではなく、**生成の各反復ごとのルーティング分布**を追跡するという時間粒度の細かさである。これにより、同じ要求でも生成の前半と後半で専門家選択が変化することを扱える。先読み予測が外れた場合でも元のルータが選んだ専門家を読み込んで実行するため、専門家を別のものに置換する近似方式とは異なる。

EuroSys 2026掲載版の要旨は、六GPU実機で推論遅延を最大47%削減し、専門家ヒット率を39%改善したと報告する。既存原稿にあるDeepSpeed比の初回トークン遅延74%削減、出力トークン当たり遅延46%削減などは、特定の比較対象と評価条件での数値であり、全比較対象に一律の改善率が得られるという意味ではない。モデル、GPUキャッシュ容量、先読み距離、入力分布によって効果は変化する。

## 問題設定

### 要求全体へ集約すると失われる情報

従来の専門家キャッシュ方式は、ある要求がどの専門家を多く使ったかを集計し、次の要求の先読みに利用することがある。しかしMoEルータの選択は生成トークンと層に依存し、同じ要求でも反復が進むと変化する。要求全体の使用頻度へ集約すると、どの反復でどの専門家が選ばれたかが失われ、直近の状態に基づく予測が難しくなる。

原著図3は、Mixtral-8x7B、Qwen1.5-MoE、Phi-3.5-MoEを用い、反復単位の専門家分布と要求単位へ集約した分布を比較する。反復単位では選択の偏りが見えるが、反復を重ねて集約すると分布のエントロピーが増え、予測が難しくなる。著者らはこの現象を、要求全体の集約だけでは専門家先読みを十分に誘導できない根拠とする。

### 負荷分散による専門家人気度の平準化

現代のMoEでは負荷分散損失により、トークンが一部の専門家へ極端に集中しないよう学習することが多い。そのため、単純に「最も人気のある専門家を常駐させる」という方針だけでは高いヒット率を得られない場合がある。原著表1ではMixtral-8x7Bの有効パラメータ約12.9Bに対して総数46.7B、Qwen1.5-MoEでは2.7B対14.3B、Phi-3.5-MoEでは6.6B対42Bであり、活性化されないパラメータの割合が大きい。

GPUへ全専門家を常駐させれば転送遅延は減るがメモリ費用が増える。逆にCPUへ多く退避すればメモリは節約できるが同期転送が増える。FineMoEは、先読み対象を必要な専門家へ絞ることで、この遅延とメモリ容量の交換条件を改善しようとする。圧縮や専門家の削除ではなく、元の専門家を必要な時刻までにGPUへ届けることが目標である。

### 先読み距離の難しさ

専門家を何層先から読み始めるかも重要である。遠くから先読みすると転送を隠す時間が増える一方、遠い層のルーティングを予測するのは難しい。近い層なら予測しやすいが、転送が完了する前にその層の計算へ到達してしまう。先読み距離が同じでも、モデルの層数、専門家数、GPU計算時間、PCIe帯域によって最適値は変わる。

原著図4は複数モデルで、粗い要求単位の予測と細かい反復単位の予測を先読み距離ごとに比較する。FineMoEの動機は、反復単位の履歴と意味的な手掛かりを使うことで、遠い先読みでも必要な専門家を含む確率を高めることである。単に先読みを早く開始するだけでは、無駄な重み転送が増えて逆効果になり得る。

## 手法

### 1. 反復ごとのエキスパート対応表を記録する

FineMoEは各生成反復について、各MoE層のゲートが出力する専門家選択確率を記録する。これをエキスパート対応表と呼ぶ。単に専門家が何回使われたかを数えるのではなく、どの層で、どの専門家へ、どれほどの確率が割り当てられたかを保持する。要求全体へ集約せず反復ごとに残すことで、生成が進むにつれて変化する専門家の選択傾向を追跡できる。

対応表の保存にはCPUメモリを使う。専門家重み本体と比較すると履歴の容量は小さく、原著の評価では32K件の対応表を保存しても200MB未満であると報告する。通常の評価では約1K件でも十分な条件があった。ただし履歴数を増やせば必ず予測が改善するわけではなく、古い分布の履歴を大量に保存すると現在の要求と似た情報を選ぶことが重要になる。

### 2. 層方向のルーティング軌跡を比較する

現在の反復で観測されたルータ分布を、過去の対応表に保存された分布と比較する。論文では、複数層を進む中で専門家選択がどのように変化するかをルーティング軌跡と呼ぶ。過去の軌跡が現在と近ければ、その先の層で使われる専門家も似ている可能性がある。FineMoEはこの軌跡類似度を用い、次の層で参照する履歴を絞り込む。

要求全体の専門家使用頻度だけを使う方式では、前半と後半で選択が変わった場合に情報が混ざる。反復単位の対応表なら、現在の状態に近い履歴だけを選べる。これは専門家の選択をルータに代わって決める操作ではなく、必要な重みをいつGPUへ持ち込むかを決める予測である。最終的な専門家選択は元のルータが行う。

### 3. プロンプトの意味的類似性を補助情報にする

ルータの軌跡が似ていても、入力プロンプトの内容が大きく異なれば将来の専門家選択が分岐する可能性がある。FineMoEはプロンプトから得た意味埋め込みも利用し、内容の近い過去要求を優先して検索する。軌跡類似度と意味的類似度を組み合わせることで、単純な使用頻度の集計より、現在の要求に合う過去の専門家分布を見つけようとする。

意味埋め込みはルータの計算を置き換えるものではない。入力が何を求めているかという特徴を使い、どの過去履歴を先読みの根拠にするかを選ぶ補助信号である。したがって、プロンプトの意味が似ていてもモデル内部のルーティングが必ず一致するわけではない。意味的類似性と実際の専門家選択との関係は、モデルと入力分布によって変わる。

### 4. 累積確率から先読み専門家数を決める

検索した過去の対応表から、将来の層で専門家が選ばれる確率分布を得る。専門家を確率の高い順に並べ、累積確率が設定値δに達するまでを先読み対象にする。δを大きくすると本来必要な専門家を含めやすくなるが、使われない専門家も転送するため、PCIe帯域とGPUキャッシュを消費する。δを小さくすると転送は節約できるが、予測が外れて同期読み込みが増える。

この調整は、モデルごとの専門家数やGPUメモリ容量に依存する。専門家数が多いモデルでは、同じ累積確率を得るために必要な候補数が変わる可能性がある。FineMoEは固定個数の専門家を全層で先読みするより、予測分布に合わせて対象を選ぶことを重視する。確率分布が不正確な場合には先読みの効率も下がるため、対応表検索の品質が重要になる。

### 5. 先読み距離を調整する

先読み距離dは、現在の層から何層先で使う専門家の重みを転送し始めるかを示す。距離が短いと予測精度は高くても転送を隠せず、距離が長いと転送時間を確保できるが誤予測が増える。FineMoEは反復単位の細かい履歴を使って予測の不確実性を下げ、必要な専門家を早めにGPUへ配置することを狙う。

この距離は固定の普遍値ではない。GPUの演算速度が速いほど層間の時間が短く、同じ距離でも転送を隠しにくい場合がある。PCIe帯域が高ければ短い距離で足りる可能性もある。原著は複数の距離で専門家ヒット率を比較しており、先読み距離と予測粒度を一体で評価する必要がある。

### 6. 将来の利用見込みを加味したキャッシュ追い出し

GPUキャッシュが満杯の場合、FineMoEは過去の使用頻度だけでなく、検索した対応表から得られる将来の専門家利用確率も使い、残すべき重みを選ぶ。単純な最近使用順の追い出しでは、少し前に使ったが直近では必要ない専門家が残り、次に必要な専門家が追い出されることがある。将来の利用見込みを考慮することで、同期転送を減らす。

先読みが外れて本来必要な専門家がGPUにない場合には、先読み処理よりその専門家のオンデマンド読み込みを優先する。これにより、誤った先読みがPCIe帯域を使い続け、必要な重みの転送を妨げる事態を抑える。元のルータが選んだ専門家を必ず実行するため、予測失敗時には遅延が発生してもモデルの計算内容を近似しない。

### 7. 履歴検索とGPU計算を並行させる

細かい履歴を記録して検索するだけでは、検索そのものが推論の待ち時間になり得る。FineMoEは対応表の保存、類似履歴の検索、キャッシュ管理を分離し、推論と並行して処理する。C++やCUDAの実装を用いて、専門家の転送や履歴検索をできるだけGPU計算と重ねる。予測の精度だけでなく、予測を実行するランタイムの追加費用も抑える設計である。

この非同期化は、履歴検索が完全に無料になることを意味しない。CPUメモリ、CPU演算時間、転送管理の費用は残る。過去履歴が非常に多い場合や入力分布が頻繁に変化する場合、検索費用と予測利得の交換を再評価する必要がある。論文の性能改善は、予測アルゴリズムとシステム実装を合わせた結果である。

## 評価

### 実験環境と評価対象

| 項目 | 原著の評価設定 |
|---|---|
| GPU | NVIDIA RTX 3090 24GB ×6、NVLink接続 |
| CPU | Threadripper PRO 3955WX、32コア |
| ホストメモリ | 480GB |
| PCIe | Gen4、約32GB/秒の条件 |
| モデル | Mixtral-8x7B、Qwen1.5-MoE、Phi-3.5-MoE |
| 入力集合 | LMSYS-Chat-1M、ShareGPT |
| 履歴の分割 | 約70%を対応表構築、30%を評価 |
| 主な指標 | 初回トークン遅延、出力トークン当たり遅延、専門家ヒット率、GPUキャッシュ容量 |

原著はHuggingFace Transformersを基盤に実装し、六GPUの実機で比較する。LMSYS-Chat-1Mは平均プロンプト長約37トークン、生成長約127トークン、ShareGPTは平均プロンプト長約43、生成長約122という評価条件が既存原稿に記録されている。短いプロンプトと比較的長い生成を持つ会話型ワークロードが中心であり、極端な長文脈や特殊なコード生成に同じ性能が出るとは限らない。

### 比較方式

DeepSpeed-Inferenceは必要な専門家をオンデマンドで読み込む基準となる。Mixtral-Offloadingは先読みと最近使用順のキャッシュを組み合わせる。ProMoEは専門家の予測器を用いる先読み方式で、論文では比較用に再実装されている。MoE-Infinityは要求単位の専門家活性化履歴を利用する。FineMoEはこれらと比べ、反復単位の確率分布とプロンプト意味情報を併用する点が異なる。

比較対象が異なると初回トークン遅延と出力トークン当たり遅延の改善率も変わる。単一の「47%」だけではどの基準に対して何を改善したかが分からないため、以下では指標と比較対象を分けて記載する。ProMoEは著者再実装なので、公式実装と同一条件の性能であることを無条件には保証できない。

### 初回トークン遅延と出力トークン当たり遅延

| 比較対象 | 初回トークン遅延の削減 | 出力トークン当たり遅延の削減 |
|---|---:|---:|
| DeepSpeed | 74% | 46% |
| Mixtral-Offloading | 67% | 38% |
| ProMoE | 56% | 27% |
| MoE-Infinity | 53% | 22% |

既存原稿の改訂版比較では、上記のように複数基準に対する改善が示される。初回トークン遅延は入力受信から最初の出力トークンまでの時間であり、出力トークン当たり遅延はデコード中の一トークン生成にかかる時間を示す。前者はプリフィルや初期化、後者は繰り返しの専門家転送待ちの影響を受ける。これらを合算した「推論遅延」とは区別する。

EuroSys 2026版の要旨にある最大47%の推論遅延削減と専門家ヒット率39%改善は、上表の特定比較の値と同じ集計ではない。原著の版や評価指標によって数値が変わるため、47%と74%を同じ基準に対する矛盾した測定と決めつけない。比較対象、指標、集計対象を確認する必要がある。

### GPUキャッシュ容量を減らした場合

原著はGPU側の専門家キャッシュ容量を約6GBから96GBまで変化させ、メモリ制約が強い場合の性能を調べる。既存原稿では6GBの条件で、DeepSpeed比36%、Mixtral-Offloading比25%、ProMoE比16%、MoE-Infinity比29%の出力トークン当たり遅延削減を報告している。小さなキャッシュでも、反復単位の先読みが同期転送を減らすことで一定の利得を維持するという結果である。

ただし、6GBの専門家キャッシュという値はモデル全体を6GBのGPUメモリに収めたという意味ではない。非専門家部分、活性値、KVキャッシュ、実行時作業領域など別のメモリが必要になる。GPUメモリ全体の最小要件と専門家キャッシュだけの容量を混同しないことが重要である。

### 対応表の容量と履歴が少ない場合

対応表32K件でもCPUメモリ使用量は200MB未満であり、専門家重み本体に比べると小さい。通常の評価では約1K件の履歴で十分な条件があったと報告する。これはルータ確率分布の履歴が、巨大な重みを追加保存することなく先読みの手掛かりになることを示す。ただし履歴の質が低い場合には、数だけ増やしても適切な候補を検索できるとは限らない。

オンライン到着を模した追加評価では、Azureトレースから256要求を再生し、平均到着率約2.91要求/秒とする。対応表が空の状態から始めても比較対象に対する優位性が維持されたと報告するが、これは特定のトレースと要求数での結果であり、長期間にわたる分布変化や極端な同時要求数への保証ではない。履歴の蓄積と利用の効果は、配備時の入力分布に依存する。

### 別GPU・異なる帯域条件

原著の追加評価ではA100 80GBのようにGPUメモリ容量や帯域が大きい環境では、RTX 3090環境より比較方式との差が縮む。GPUへ常駐できる専門家が増え、転送待ちが減るほど、FineMoEが先読みで解消できる残余の遅延が小さくなるためである。したがって、GPUが高速になればFineMoEの相対改善率も必ず大きくなるという関係ではない。

これはメモリ階層の最適化一般に共通する注意点である。専門家転送が支配的な環境では予測とキャッシュ管理の効果が大きいが、GPU計算や別の通信が支配的になると同じ先読みをしても全体の遅延改善は限定される。GPUメモリ容量、PCIe帯域、専門家の選択分布を合わせて評価する必要がある。

## 既存研究との差

MoE-Infinityなどの要求単位の履歴を利用する方式では、要求全体の専門家使用頻度へ集約することで生成反復ごとの違いが失われる。FineMoEは各反復のルータ確率分布を保存し、現在の軌跡と近い過去の反復を検索する。さらにプロンプトの意味的類似性を補助情報として利用し、同じような入力で将来選ばれやすい専門家を推定する。これにより先読み対象を細かく絞り、GPUキャッシュの限られた容量を有効に使う。

FiddlerのようにCPU側で専門家計算を直接行う方式とは異なり、FineMoEは本来の専門家重みを必要な時刻までにGPUへ届けることを重視する。専門家を別の専門家へ置換するBuddyMoEとも異なり、予測が外れた場合には同期読み込みして本来の専門家を実行する。圧縮・削除・代替計算による品質低下を主な交換条件とせず、先読みとキャッシュ管理の効率を改善する無損失系のオフロード方式である。

## 限界

FineMoEは過去のルーティング軌跡とプロンプトの意味的類似性を使うため、配備後の入力分布が変化すると予測精度が低下する可能性がある。モデル更新によってルータの選択分布が変わった場合も、古い対応表が適切とは限らない。過去履歴が少ない起動直後や、未知の分野の入力が続く場合には、同期転送が増えて性能が下がり得る。

予測が外れた場合でも元の専門家を読み込んで実行するため、計算結果を意図的に近似しない一方、同期転送の遅延は残る。累積確率のしきい値δを大きくするとヒット率が上がる可能性があるが、余分な先読みがPCIe帯域とGPUキャッシュを消費する。先読み距離dを長くしても誤予測が増える場合がある。したがってδとdはモデル・GPU・PCIe・ワークロードごとに調整する必要がある。

主な実機評価はRTX 3090を六基持つシステムで、CPUメモリに専門家重みを保持できることが前提である。SSD、NVMe、CXLなど別の低速階層から重みを読み込む場合の費用は直接評価していない。また、KVキャッシュのCPU退避を中心に最適化する方式でもなく、専門家キャッシュの6GBという値はGPUメモリ全体の必要量ではない。

履歴検索と意味埋め込みの処理にはCPUメモリ・演算時間・非同期管理の費用がある。論文はこれらを推論と重ねる実装を提案するが、履歴の量や検索負荷が極端に増えた場合の費用を無条件に無視できるわけではない。ProMoEとの比較には著者再実装が含まれ、他の方式の最新実装と完全に同じ最適化条件であることは保証できない。

EuroSys 2026版の要旨にある遅延47%削減とヒット率39%改善は、特定の実機・モデル・入力集合に対する結果であり、すべての比較対象に対する同じ倍率ではない。初回トークン遅延と出力トークン当たり遅延は異なる指標で、DeepSpeed比74%と46%を同じ数値として扱うこともできない。モデルやGPUが変わると相対利得が縮小する例もあるため、性能は実機の条件付きで解釈すべきである。
