# eLLM: Elastic Memory Management Framework for Efficient LLM Serving

> LLMサービングで活性値とKVキャッシュを別々の固定メモリ領域として管理すると、片方が空いていても他方へ融通できずGPUメモリが遊ぶ問題に対し、仮想テンソル抽象で両者を同じ物理プールへ載せ、GPU内で領域を動的に貸し借りし、さらにCPUメモリを弾性的な退避先として使う推論基盤。初回トークン時間と出力トークン間隔のSLO違反を監視してCPUバッファ量を調整し、長文脈時の待ち行列とバッチ容量を両立する。A100実機でvLLM等と比較し、最大2.32倍のデコードスループット、128K入力で3倍のバッチ規模を報告する。

- **種別**: 査読付き国際会議論文
- **対象**: LLM推論基盤、GPUメモリ仮想化、KVキャッシュ管理、弾性メモリ、CPU退避、SLO制御

## 問題設定
LLM推論では重みは固定だが、活性値とKVキャッシュは入力長、出力長、実行段階によって必要量が大きく変わる。vLLMのページ化注意機構は伸長するKVをページ単位で管理して断片化を減らす一方、活性値はPyTorch側の通常テンソル領域、KVは専用領域に分離される。最大文脈長へ合わせて活性値領域を予約すると、実際の短い入力やデコード中にはその領域の大半が遊ぶが、KV領域が不足しても借りられない。論文ではMTP-30Bの最大文脈を2Kから200Kへ伸ばすと活性値予約がGPUメモリの0.3%から30.8%へ増え、実ワークロードでは90%以上のプリフィルバッチが最大文脈の30%未満しか使わないと示す。デコード時の活性値利用は約1%であり、この空きが長時間続く。固定チャンクのプリフィルは活性値ピークを減らせるが過去KVの再読込を増やし、プリフィル・デコード分離は重み複製、GPU間利用率の偏り、KV転送を追加するため、根本的な領域分離は残る。
## 新規性
eLLMは活性値とKVを同じ管理方式に無理に押し込むのではなく、用途別の仮想テンソルを同じ物理GPUメモリプールへ対応付ける。KVは長寿命で規則的に伸びるため大きな仮想領域を先に確保し、実ページだけ必要時に割り当てる。活性値は短寿命・高頻度なので可変仮想区間を使う。この共通物理プール上で、KV不足時には使われていない活性値用物理チャンクを回収してKVへ貸す膨張、逆方向へ戻す収縮を行う。GPU内だけで足りない場合は、プリフィルで生成した直後のKVをCPUへ先行退避し、デコード開始前に戻す。さらにCPUバッファを増やすと初回トークン時間は改善するが出力トークン間隔が悪化するため、両SLOの違反回数から論理バッファ容量を動的に増減する。仮想化、GPU内融通、CPU退避、SLO制御を一つのメモリ抽象へ統合した点が新規性である。
## 手法
### 手法のあらまし
要求が到着すると、まず活性値とKVの双方をeTensorという仮想テンソルとして扱う。KV用eTensorは各要求の最大文脈長に相当する連続した仮想アドレスを予約するが、物理GPUチャンクはKVが実際に生成された分だけ対応付ける。活性値用eTensorは短寿命なので必要な大きさの仮想区間を都度使う。両者の物理チャンクは同じGPUメモリ資源から供給されるため、論理上は別用途のままでも空き物理容量を融通できる。KV割当時にKV側のチャンクが足りなければ、活性値側へ膨張要求を出す。活性値側は現在使われていないeTensorを軽量なガベージ収集で探し、その物理対応付けを外し、所有権をKV側へ移す。そのチャンクを対象KVの仮想アドレスへ対応付ければ、通常なら待ち行列に入る要求をすぐプリフィルできる。活性値が再び必要になった場合は逆の収縮を遅延実行し、不要な往復を避ける。GPU内融通だけで負荷を吸収できない場合、スケジューラはプリフィルで生成されたKVの一部をCPU DRAMへ退避する。新規KVはプリフィル直後からデコード開始まで即時参照されないため、この時間を転送に使う。Transformerの層ごとにプリフィル計算とKV転送を重ね、転送量は文脈長に対して線形である一方、長文脈プリフィルの注意計算は二次的に増えるため、条件によって転送を計算へ隠せる。デコードへ移ると活性値の必要量が小さくなるのでGPU内領域をKVへ戻し、CPU上のKVも必要な要求からGPUへ復帰させて大きなデコードバッチを作る。ただしCPUバッファを大きくするとプリフィル要求を多く先行処理できる反面、復帰転送や大きなデコードバッチでTPOTが悪化し得る。そこで物理CPUバッファの上に論理的な使用上限を置き、直近5反復でTTFTまたはTPOTがSLOを3回超えたかを監視する。TPOT違反なら論理バッファを縮めてプリフィル先行を抑え、TTFT違反なら拡大して待ち行列を減らす。既定の調整係数は2である。仮想アドレス対応付け自体の費用は、デコードの次トークン用領域を先に対応付けする投機的事前割当と、一つの物理チャンクを一時的に複数仮想アドレスへ対応付けできるGPU仮想メモリ機構を使った非同期解除で隠す。この循環により、入力処理と逐次生成の段階変化に合わせてGPU内の活性値/KV比率とCPU退避量を連続的に変える。

### 用途別eTensorと統一物理プール
KVキャッシュと活性値を同じ形のテンソルとして扱うのではなく、それぞれの寿命とアクセス特性に適した仮想表現を持たせる。KV用eTensorは最大文脈長ぶんの連続仮想アドレスを先に予約し、実際にトークンが増えたときだけ物理チャンクを対応付けるので、インデックス計算を単純に保ったまま物理容量の先取りを避けられる。解放後の対応付け済み区間は再利用候補として保持し、要求サイズ以上で最小の区間を選ぶ最適適合方式を使う。活性値用eTensorは短寿命・高頻度の割当へ合わせて可変区間を使い、PyTorch由来の最適適合・併合方式を維持する。論理管理は別でも物理チャンクの供給元を統一するため、従来の『活性値側は空いているのにKV側が満杯』という内部断片化を解消できる。

### GPU内メモリ膨張・収縮
KV側で新しい物理チャンクが必要になり手元の空きが不足すると、活性値プールへ容量借用を要求する。活性値側は全領域を整理する重い処理ではなく、現在の計算から参照されていないeTensorを探す軽量な回収を行い、その仮想対応付けを解除する。回収した物理チャンクの所有権だけをKVプールへ移し、必要なKV用仮想区間へ再対応付けするため、テンソル内容を別バッファへコピーする必要はない。逆に大きなプリフィルで活性値容量が必要になれば収縮でKV側から物理チャンクを戻す。収縮は即時ではなく遅延させ、短時間に用途が往復するときの対応付け費用を避ける。これにより推論段階ごとに大きく変わる活性値とKVの割合へ同じGPU内で追随する。

### CPUを使う弾性KVバッファ
GPU内部の貸し借りだけで要求を収容できない場合、プリフィル中に生成されたKVをCPU DRAMへ積極的に退避する。生成直後のKVは対応する要求がデコードへ選ばれるまで参照されないため、各Transformer層の計算中に別層のKV転送を重ねる。KV転送量は入力長に比例するが、長文脈プリフィルの注意計算量は入力長の二乗に近く増えるため、Llama3-8BとA100の実測では退避費用を完全に隠せる領域がある。GPU上のKV占有を一時的に減らすことで、待っているプリフィル要求を早く受け入れ、後でデコード時に必要KVを戻して大きなバッチを形成する。ただしPCIe帯域で転送を隠せない条件では性能低下が生じるため、CPU退避を無制限には使わない。

### SLO連動の論理バッファ制御
CPU側の物理バッファ容量を固定したまま、そのうちスケジューラが利用してよい論理容量だけを変える。CPU退避を増やすとプリフィル要求の入場待ちが減りTTFTは改善しやすいが、デコードへ戻すKVや同時実行要求が増えてTPOTを悪化させる可能性がある。eLLMは直近5回のスケジューリング反復を観測し、TTFTまたはTPOTが設定SLOを3回超えると調整イベントを発生させる。TPOT違反時は論理CPUバッファを縮小し、TTFT違反時は拡大する。既定では調整係数2で段階的に変えるため、ワークロードの入力長や到着率が変化しても単一の固定バッファ設定に縛られない。物理データを縮小時に直ちに追い出す必要はなく、使用上限だけを変えるので制御自体は軽量である。

### 全体のデータ／制御の流れ
eLLMはvLLM 0.5.5上に約4,000行のC++とPythonで実装される。KV eTensor用にはC++ライブラリを追加し、従来のKVテンソルを置き換え、最小割当粒度をページからGPU物理メモリチャンクへ変更する。活性値側はPyTorchのキャッシュアロケータを改変し、通常のcudaMalloc系割当の代わりにGPU仮想メモリ管理APIを用いる。仮想対応付け費用を隠すため、自己回帰デコードでは各系列が次トークンを生成すると仮定して次の物理領域を非同期で先行対応付けし、追加メモリを50MB未満に抑える。解除時は一つの物理チャンクを新しい仮想区間へ先に対応付けてから旧区間を非同期解除し、計算と重ねる。スケジューラはプリフィルとデコードで活性値需要が異なることを利用し、プリフィルではCPU退避、デコードではGPU復帰を優先しつつ、SLO違反から論理バッファ容量を更新する。
## 評価条件
- **ハードウェア**: NVIDIA A100 80GBを8枚搭載しNVLinkで接続したサーバ。CPUはIntel Xeon Platinum 8369B、ホストメモリ1TB。単一GPU、2 GPU、および複数GPU条件で評価する。
- **ソフトウェア**: PyTorch 2.4.0、CUDA Driver 12.4、vLLM 0.5.5を使用。比較対象はvLLM、512トークン単位のチャンク化プリフィルを有効にしたvLLM、プリフィル・デコード分離型のDistServe。
- **データセット／トレース**: ShareGPT、固定長合成系列
- **比較対象**: vLLM、vLLM+チャンク化プリフィル、DistServe
オンライン評価では初回トークン時間（TTFT）、出力トークン間隔（TPOT）、出力スループット、SLO達成率を測る。SLOは競合のない条件で得たTTFTとTPOTの25倍に設定し、90%以上の要求がSLOを満たす最大到着率を有効スループットとして導出する。オフライン評価では総スループット、デコードスループット、最大バッチ規模を測る。GPU内弾性だけ、GPU-CPU弾性だけ、両者統合の機構分解も実施する。
実機GPUサーバでの評価で、一般的なTransformerのLlama3、ハイブリッドMamba-MoEのJamba、MHAのOPTという異なる構造を含む。一方、GPU世代はA100に限定され、GPU-CPU接続条件も一つのサーバ構成である。CPU退避の利得はPCIe帯域とプリフィル計算量の比に依存するため、より高速なGPUや異なる接続では境界が変わり得る。
## 主要結果
eLLMは固定された活性値領域をKVへ転用することで、特に長文脈や活性値/KV比が大きいモデルで同時実行バッチを拡大する。単一A100のオンライン評価では待ち行列を強く減らし、初回トークン時間をvLLM比で最大295倍、チャンク化プリフィル比で最大140倍短縮する。CPU退避を増やすとTPOTはvLLMより高くなる条件があるものの、両SLOを合わせた有効スループットは最大2.5倍となる。オフライン128K入力では総スループット1.82倍、デコードスループット2.32倍を達成し、仮想メモリ管理操作の時間比率は1〜5%、CPUスケジューリングは1%未満に抑える。

- 初回トークン時間の短縮 / 最大295倍高速、チャンク化プリフィル版vLLM比では最大140倍高速 (比較対象: vLLMおよびvLLM+チャンク化プリフィル; 条件: Llama3-8B-262K、A100 80GB 1枚、オンライン2K-2KおよびShareGPT系負荷) — 活性値の遊休領域をKVへ貸し、必要ならCPU退避で新規プリフィルの入場条件を緩めることで、高負荷時の待ち行列時間を大幅に削減する。

- SLOを満たす有効スループット / 最大2.5倍、チャンク化プリフィル版vLLM比2.26倍 (比較対象: vLLMおよびvLLM+チャンク化プリフィル; 条件: 単一A100オンライン評価、90%の要求がTTFT/TPOT SLOを満たす最大到着率) — CPU退避によるTPOT悪化を含めても、TTFTとの総合的なサービス品質ではより高い要求率を処理できる。

- オフライン総スループット / 最大1.82倍 (比較対象: vLLM; 条件: 長文脈条件を含むJamba-Mini 2 GPUまたはLlama3-8B単一GPU評価、最大値は128K-4K条件を含む) — デコード中にほぼ使われない活性値予約をKVへ転用し、静的分割では収容できない大きなバッチを実行できるため総処理量が増える。

- デコードスループット / 最大2.32倍 (比較対象: vLLM; 条件: 128K入力・4K出力のオフライン条件) — 長いKVを多数保持する条件ほど固定活性値予約による容量損失が効くため、統一物理プールの利得が大きい。

- 最大バッチ規模 / 128K入力で最大3倍 (比較対象: 既存の固定領域型サービング基盤; 条件: 長文脈オフライン推論) — GPU内の遊休活性値領域とCPUバッファをKV容量へ変換し、メモリ制約で決まる同時系列数を拡大する。

- 管理オーバーヘッド / CPUスケジューリング1%未満、仮想メモリ管理操作1〜5% (比較対象: eLLM総実行時間; 条件: オンラインサービング評価) — 対応付けの再利用、投機的事前対応付け、非同期解除により、仮想化の追加費用は得られる容量・スループット改善より小さい。

### 負の結果・境界条件
- GPU内弾性とGPU-CPU弾性を同時に使う構成は、GPU内弾性だけより出力スループットが低くなる条件がある。原因はデコード段階でPCIe転送を完全には計算へ隠せないためである。また単一GPU評価では、eLLMとチャンク化プリフィル版vLLMはデコード用KV容量を増やして大きなバッチを作るため、vLLMよりTPOTが高くなる。逆にGPU内弾性だけでは高負荷時のプリフィル待ちを防げず、有効スループットが下がる。したがってCPU退避は常に多いほど良いわけではなく、TTFTとTPOTのSLOを見ながら量を調整する必要がある。

### 結果の読み方
最大の利得は、固定予約と実利用量の差が大きいほど増える。長文脈対応モデルは最大入力に合わせて活性値領域を大きく予約するが、実要求やデコードではその大半を使わないため、物理チャンクをKVへ転用する余地が大きい。Jambaのように活性値/KV比が高い構造でも同じ傾向が強い。一方、CPUを追加容量として使う利得はGPU演算時間とPCIe転送時間の重なりに依存する。SLO連動バッファ制御はこの境界を負荷に応じて追従し、TTFTだけを最小化してTPOTを悪化させる固定設定を避ける。
## 品質への影響
メモリ内容を量子化・近似・枝刈りせず、仮想アドレスと物理チャンクの対応関係やCPU/GPU配置だけを変更するため、アルゴリズム上の生成品質低下は導入しない。性能上の主な代償は追加の仮想メモリ管理費用とCPU-GPU転送であり、後者はTPOTや出力スループットを悪化させる条件が実測されている。
## 既存研究との差
vLLMのページ化注意機構はKVキャッシュ内部の断片化を減らすが、活性値とKVの物理領域は分離したままである。vAttentionは連続仮想アドレスを用いてKVのトークン方向の断片化を改善するが、eLLMが主対象とする活性値領域との相互融通までは行わない。チャンク化プリフィルは活性値ピークをスケジューリング側から抑える一方、過去KVの再読込を増やす。DistServe等のプリフィル・デコード分離は段階ごとにGPUを専用化するが、重み複製、利用率偏り、KV転送が必要になる。eLLMは同一GPU内の物理チャンクを用途間で貸し借りするため、これらとは異なるメモリ管理層の解決策であり、分離サービングとも原理上は併用できる。
## 限界
評価GPUはA100世代と単一サーバ構成に限られ、GPU-CPU転送をプリフィル計算へ隠せる範囲はPCIe帯域、GPU演算性能、モデル構造によって変化する。実際にデコード段階では転送を隠し切れず、GPU内弾性のみより統合構成の出力スループットが下がる条件がある。SLO連動バッファ制御も直近5反復で3回違反という固定窓と既定調整係数2を使うため、急激な負荷変動や異なるSLO形状で最適とは限らない。vLLM 0.5.5とPyTorchアロケータへ深く統合した実装なので、ランタイム更新や別推論基盤への移植では仮想メモリ管理部分の再実装が必要になる。
## 実装状態
vLLM 0.5.5上に約4,000行のC++/Pythonで実装され、KV eTensor用C++ライブラリとPyTorchキャッシュアロケータ改変を含む。GPU仮想メモリ管理APIを実際に使い、A100実機でオンライン・オフライン評価しているため、シミュレーションのみの提案ではない。論文本文には公開コードURLの明示は見当たらず、再現性は実装記述と論文評価に依存する。
## 研究上の位置づけ
LLM推論の階層メモリ研究の中では、単純にKVをCPUへ逃がす方式より一段下の『GPU内部で用途別に分断された予約領域そのものを弾性化する』研究として位置付けられる。KVキャッシュ容量不足を解く前に、活性値用として固定確保されたが実際には使われていないGPU容量を回収するため、オフロード量とPCIe通信を減らせる可能性がある。その上で不足分だけCPUを拡張バッファとして使い、SLOから退避量を制御する。SSDやCXLを次の階層として追加する研究では、このeTensor型の統一物理プールと論理容量制御をGPU-CPU-SSDへ拡張し、各階層への退避を単なる容量不足ではなくTTFT/TPOTと通信費の境界で決める設計へ発展させられる。
