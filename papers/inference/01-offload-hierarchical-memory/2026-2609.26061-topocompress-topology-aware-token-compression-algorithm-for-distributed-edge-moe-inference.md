# TopoCompress: Topology Aware Token Compression Algorithm for Distributed Edge MoE Inference

> 意味的重要度と現在の専門家配置による通信費用を同時に見てトークンを圧縮し、圧縮後トラフィックに合わせてMoE専門家配置とGPU/CPU常駐を再最適化する分散エッジ推論方式。
## 書誌情報
- **著者**: Ning Li, Xinyu Wang, Xin Yuan, Wenchao Xu, Athanasios V. Vasilakos, Song Guo, Haijun Zhang
- **公開**: arXiv preprint
- **種別**: preprint
- **対象**: 分散MoE推論、トークン圧縮、専門家配置、階層メモリ、エッジ推論
- **実装**: 論文ではPyTorch実装とトレース駆動シミュレータによる評価を記載する。arXivページおよび本文で公式コード公開URLは確認できなかった。
## 概要
分散エッジ環境の混合専門家モデル（Mixture-of-Experts; MoE）では、トークンごとに選択される専門家が異なるサーバーへ分散するため、専門家配置だけを最適化してもサーバー間通信が残る。本研究は、意味的重要度が低い一方で現在の配置トポロジーでは転送費用が高いトークンを優先的に圧縮し、その圧縮後トラフィックを使って専門家の配置・複製・GPU/CPU常駐を再最適化する双方向の二時間尺度方式を提案する。10台の異種エッジサーバーを用いるトレース駆動シミュレーションでは、Mixtral-8x7BでDanceMoE比29.8%の通信量削減などを示すが、実機分散クラスタではなくシミュレーション評価である。

TopoCompressの中心的な新規性は、トークンの意味的重要度と現在の専門家配置が生むルーティング費用を同時に評価して圧縮対象を選び、その圧縮後トラフィックを次の専門家配置へ戻す双方向結合にある。

トークン単位の高速判断と配置期間単位の低速判断を二時間尺度の交互最適化として分離し、圧縮、専門家配置・冗長複製、GPU/CPU常駐、複数専門家への協調ルーティングを同じ目的関数の下で連携させる。

代表結果として、サーバー間通信量はMixtral-8x7B、既定シミュレーション条件でDanceMoEに対して1.18 GB / 1,000 トークン。DanceMoEより29.8%少なく、MoE-Infinityより41.9%、EdgeShardより73.5%少ない。高費用・低価値トークンを転送前に除去する効果を示す。
## 問題設定
分散エッジ環境で混合専門家モデル（Mixture-of-Experts; MoE）を動かすと、各トークンが選ぶ上位k個の専門家が複数サーバーへ散在し、帯域の狭い通常インターネット回線を跨ぐ転送が推論遅延を支配しうる。従来の専門家配置・キャッシュ・オフロード方式は圧縮前の生トークントラフィックを前提に配置を最適化する一方、既存のトークン圧縮は意味的重要度や注意重みだけを見て配置トポロジー由来の通信費用を考慮しない。

この分離最適化では、安価なローカルトークンを落とす一方で高価な遠隔トークンを残したり、圧縮後には使われない専門家複製へGPUメモリを割き続けたりするため、通信量・品質・配置資源の同時最適化ができない。
## 新規性
TopoCompressの中心的な新規性は、トークンの意味的重要度と現在の専門家配置が生むルーティング費用を同時に評価して圧縮対象を選び、その圧縮後トラフィックを次の専門家配置へ戻す双方向結合にある。

トークン単位の高速判断と配置期間単位の低速判断を二時間尺度の交互最適化として分離し、圧縮、専門家配置・冗長複製、GPU/CPU常駐、複数専門家への協調ルーティングを同じ目的関数の下で連携させる。
## 手法
### 手法のあらまし
入力要求が入口サーバーへ到着すると、各MoE層のゲートがトークンごとに上位k専門家を選ぶ。TopoCompressはその選択結果、各専門家複製の配置場所、現在のトークン位置、サーバー間帯域と遅延から遠隔実行費用を計算し、トークンの意味的重要度と組み合わせた二次元スコアを作る。品質劣化予算に余裕があり、意味的重要度が低い一方で転送費用が高いトークンだけを枝刈りまたは類似トークン統合で圧縮し、高価値トークンは残す。

圧縮後に残ったトークンについては、選択された専門家を個別に最短配置へ送るのではなく、品質制約とサーバー安定性制約を満たす複製候補を列挙し、上位k専門家の集合としてファンアウトとファンインの最大費用を抑える組合せを選ぶ。候補が小さいときは厳密探索、大きいときは幅Wのビーム探索と1交換局所探索を用いる。利用可能な近似候補がなくても、最低1個保持する完全精度専門家複製へフォールバックして推論を継続する。

オンライン実行中には、圧縮後に実際に各専門家へ到達したトラフィックを蓄積する。配置期間の境界で低速オフラインループがこの統計を読み、選択頻度とCPUからGPUへの転送費用からGPU常駐優先度を更新し、残存する高費用トラフィックを最も削減できるサーバーへ専門家複製を追加する。その後にGPU/CPU常駐を再最適化し、新しい配置からルーティング費用グラフを再計算する。次の期間ではこの新しい費用グラフが再びトークン圧縮判断へ入力されるため、配置→圧縮→圧縮後需要→再配置という閉ループになる。各ブロック更新は共通の正規化目的関数を悪化させない場合だけ採用され、非凸問題に対して座標ごとの停留点へ収束させる。

### トポロジー認識型オンライン圧縮・協調ルーティング
高速オンライン側は、各層でゲートが選んだ上位k専門家と、その専門家の複製位置、現在のトークン位置、サーバー間帯域・遅延からルーティング費用を求め、さらにトークンの意味的重要度を組み合わせて二次元スコアを作る。単に重要度の低いトークンを削るのではなく、意味的には削除可能で、かつ現在の配置では遠隔転送費用が大きいトークンを優先する。圧縮操作は枝刈りだけでなく類似トークン統合も候補とし、較正で定めたトークン単位の品質劣化予算を超える操作は採用しない。

圧縮後に残った専門家活性は個別に最短経路へ送るのではなく、上位k専門家を集合として扱い、品質制約とサーバー安定性制約を満たす複製候補からファンアウト・ファンインの最大通信費用を小さくする組合せを選ぶ。候補数が小さい場合は厳密探索、大きい場合は幅Wのビーム探索と1交換局所探索で計算量を抑える。近似候補が不適切または利用不能な場合は最低1個保持される完全精度専門家複製へフォールバックする。

### 圧縮後トラフィック認識型オフライン配置
低速オフライン側は、圧縮前のゲート選択頻度ではなく、高速オンライン処理を通過して実際に専門家へ到達した圧縮後トラフィックを配置期間ごとに集計する。この統計を用いて、各専門家をどのサーバーへ置くか、追加複製をどこへ作るか、各複製をGPUまたはCPUメモリのどちらへ常駐させるかを更新する。GPU常駐の優先度は専門家が選択される確率とCPUからGPUへ移す際の転送遅延を組み合わせる。

冗長複製については、候補位置へ複製したときの経路短縮による通信節約と、圧縮後にも残る高費用トラフィックをどれだけ減らせるかを評価して配置する。追加後には常駐割当も再計算するため、複製だけ増やしてGPU容量を浪費することを避ける。圧縮で消えるアクセスを前提に複製やGPU常駐を決めないことが従来配置との重要な差である。

### 二時間尺度の閉ループ最適化
全体は、トークンごとに動く高速オンラインループと、複数要求を集約した配置期間ごとに動く低速オフラインループを交互に実行する二時間尺度方式として定式化される。オンライン側では配置・常駐状態を固定したまま各トークンの圧縮判断と専門家集合ルーティングを改善し、オフライン側では圧縮後トラフィックを固定して専門家の複製位置とGPU/CPU常駐を改善する。

配置を変えると次の期間のトポロジー費用が変わり、それによって圧縮対象も変化する一方、圧縮対象が変われば次の配置期間で観測される専門家需要も変わる。各更新は同じ正規化目的関数を悪化させない場合だけ受理される。問題自体は非凸なので大域最適性は保証せず、論文はブロック座標の停留点への収束を主張する。評価では4〜5エポック付近で安定し、第1エポック比で最終目的値が21.3%低下する。

### 全体のデータ／制御の流れ
地理的に分散した異種エッジサーバー群へMoE専門家を複製配置し、各複製をGPUまたはCPUメモリへ常駐させる。ユーザーの入口サーバーから始まるトークンは層ごとに居場所を変え、事前計算したルーティング費用グラフを参照して圧縮と専門家集合ルーティングを行う。

オンライン処理が圧縮後トラフィック統計を蓄積し、次の配置期間でオフライン配置器がその統計を使って常駐・複製を更新する。完全精度の専門家複製を最低1個保持する不変条件と品質予算により緊急フォールバック経路も確保する。
## 評価条件
- **ハードウェア**: 10台の異種エッジサーバーを模擬し、計算性能18〜120 TFLOPS、GPUメモリ12〜48 GB、CPUメモリ96〜512 GB、サーバー間帯域0.8〜10 Gbps、伝搬・待ち行列遅延0.3〜22 msを設定する。専用高速網ではなく通常インターネット相当の地理分散リンクを想定する。
- **ソフトウェア**: TopoCompressはPyTorchで実装され、トレース駆動の地理分散エッジシミュレータ上で評価される。公式コード公開URLは本文およびarXivページでは確認できない。
Switch-Base-8E、Qwen-MoE-A2.7B、Mixtral-8x7Bの3モデルを用い、WikiText-103のパープレキシティ、SQuADのF1、GSM8Kの正解率で品質を測る。保持した較正集合で専門家配置、GPU/CPU常駐、ルーティング費用グラフ、層別圧縮閾値、圧縮後トラフィックを計算し、基盤モデル自体は固定する。既定では品質劣化予算2%、ビーム幅8、冗長配置メモリ予算比2.0、交互最適化5エポック、要求到着率40件/秒。比較対象はDanceMoE、MoE-Infinity、EdgeShard、SnapKV、H2Oで、通信量、平均/P99遅延、遠隔実行率、圧縮率、スループット、品質を比較する。さらにトポロジー認識スコア、GPU/CPU常駐最適化、トラフィック認識複製、低速オフラインループを個別に除くアブレーションを行う。
評価は実際の地理分散GPUクラスタでの実測ではなく、異種資源・帯域・遅延を与えたトレース駆動シミュレーションである。したがって、通信削減と品質制約のアルゴリズム上の傾向は比較できるが、実ネットワークの輻輳変動、GPUカーネル効率、実際のCPU-GPU転送競合、制御面オーバーヘッドを含む壁時計性能への一般化には追加の実機検証が必要である。
## 主要結果
Mixtral-8x7Bの既定条件では、TopoCompressは通信量、平均遅延、P99遅延、遠隔実行率、スループットのすべてで主要比較対象を改善し、品質低下を既定2%予算内に抑える。特に通信量は1,000トークン当たり1.18 GBとなりDanceMoE比29.8%減、平均遅延149 ms、スループット1,540 トークン/sを達成する。効果は単なる意味ベース圧縮ではなく、トポロジー認識スコアと圧縮後トラフィックを配置へ戻す低速ループの双方に依存する。一方で結果はシミュレーション由来であり、品質は完全無損失ではない。

- サーバー間通信量 / 1.18 GB / 1,000 トークン (比較対象: DanceMoE; 条件: Mixtral-8x7B、既定シミュレーション条件) — DanceMoEより29.8%少なく、MoE-Infinityより41.9%、EdgeShardより73.5%少ない。高費用・低価値トークンを転送前に除去する効果を示す。

- 平均推論遅延 / 149 ms (比較対象: DanceMoE; 条件: Mixtral-8x7B、既定シミュレーション条件) — DanceMoEより27.0%、EdgeShardより58.6%低い。帯域制約下でファンアウト・ファンイン転送を減らした効果と解釈される。

- P99推論遅延 / 279 ms (比較対象: DanceMoE; 条件: Mixtral-8x7B、既定シミュレーション条件) — DanceMoEより35.7%、EdgeShardより61.8%低く、集合ルーティングと高費用トークン圧縮が尾部の多段遠隔経路を抑える。

- スループット / 1,540 トークン/s (比較対象: EdgeShard; 条件: Mixtral-8x7B、既定シミュレーション条件) — EdgeShardの2.18倍で、通信量削減が処理能力へ反映される。

- 品質保持 / 全3モデルで98.8%以上 (比較対象: 完全中央集約モデル; 条件: 品質劣化予算2%を既定値としてWikiText-103、SQuAD、GSM8Kを評価) — 通信削減は近似圧縮を伴うが、WikiText-103はパープレキシティ+0.34、SQuAD F1は-0.7、GSM8K正解率は-1.0に抑えられる。

- 交互最適化による目的値改善 / 初回エポック比21.3%低下 (比較対象: 第1エポック; 条件: 5エポックの二時間尺度交互最適化) — 4〜5エポックで安定し、最初の3エポックで通信量24.6%、CPUオフロード率19.0%が低下する。圧縮後トラフィックを配置へ戻す逆方向結合の寄与を示す。

### 負の結果・境界条件
- 品質は無損失ではなく、中央集約モデルに対してWikiText-103パープレキシティ+0.34、SQuAD F1 -0.7、GSM8K正解率-1.0の低下がある。品質予算を0.5%から3%へ緩めるほど通信量は減るが品質低下も増える。また全体最適化問題は非凸であり、交互最適化は大域最適ではなく座標ごとの停留点への収束のみを主張する。実機ではなくシミュレーションなので、実装オーバーヘッド込みの壁時計速度向上は未実証である。

### 結果の読み方
利得が大きい理由は、専門家配置だけを改善する方式と、意味だけでトークンを削る方式を直列に置くのではなく、現在の配置で本当に高価なトークンを選んで圧縮し、その結果として変化したトラフィックへ次の配置を適応させるためである。アブレーションではトポロジー認識スコアを外すと通信量が1.18から1.74 GB/1,000 トークンへ悪化し、低速オフラインループを外しても1.52 GBへ悪化する。したがって通信削減は圧縮側と配置側の双方向結合に依存する。
## 品質への影響
近似方式。既定2%品質予算で品質低下を明示的に許容する代わりに通信量と遅延を削減する。高価値トークンを保護する品質ガードと完全精度専門家複製への緊急フォールバックを備え、測定された品質低下は設定予算を下回るが、完全な無損失性は主張しない。
## 既存研究との差
MoE-InfinityやPre-gated MoEのような単一ノード内のGPU/CPU階層で専門家をキャッシュ・先読みする系統に対し、TopoCompressは通常インターネットで結ばれた複数エッジサーバー間のトポロジー費用を明示的に扱う。DanceMoEのような専門家配置方式とは、圧縮前トラフィックではなく圧縮後トラフィックを配置・複製へフィードバックする点が異なる。SnapKVやH2Oなどのトークン圧縮とは、意味的重要度だけでなく現在の専門家配置に由来する遠隔通信費用を圧縮判断へ入れる点が異なる。したがって本研究は、専門家配置・階層メモリ常駐・通信ルーティング・トークン圧縮を横断して結合する位置づけにある。
## 限界
最大の制約は、10台の異種エッジサーバーを模したトレース駆動シミュレーションであり、実際の地理分散GPUクラスタ上の壁時計評価ではない点である。実ネットワークの突発輻輳、GPUカーネル実行、CPU-GPU転送競合、制御面処理を含む実装費用は十分に検証されていない。また圧縮は近似的で品質低下を許容し、非凸な全体問題に対して大域最適性を保証しない。較正集合で得る統計や閾値に依存するため、分布変化が大きい運用環境での再較正頻度も実運用上の論点になる。
## 実装状態
論文はPyTorch実装を用いたと記載するが、arXiv本文と論文ページで公式コード公開URLは確認できなかった。評価環境もトレース駆動シミュレータであり、再現可能な実機デプロイメント一式の公開は確認できない。
## 研究上の位置づけ
リポジトリの重点である混合専門家モデル（MoE）の専門家配置・キャッシュと、GPU/CPUを跨ぐ階層メモリ、さらに分散推論通信の3系統を直接つなぐ研究である。特に、専門家をどこへ置くかという従来の配置問題に対して、そもそも遠隔専門家へ送るトークン量をトポロジー依存で変えるという追加自由度を導入し、圧縮後需要を次の配置へ戻す点が重要である。現時点では実機システム論文というより、配置と圧縮を共同最適化するアルゴリズム設計・シミュレーション検証として扱うのが適切で、将来の実機エッジMoEやSSD/CPUを含む多階層配置へ拡張する際の設計原理として価値がある。
