# Who Should Own the Expert Cache? Kernel-Managed Tiering for Trillion-Parameter MoE Inference

> この論文が問うのは「LRUとLFUのどちらが良いか」より一段上の問題である。**巨大MoEのexpert cacheを誰が所有すべきか**、すなわちLLM runtimeがexpert単位の専用cacheを自前実装するべきか、それともLinux kernelがすでに持つpage cacheをDRAM tierとして利用すべきかを実機で比較する。1.45TBのexpert poolが480GB Grace DRAMにも収まらないproduction-scale条件で、kernelのrecency policyが意外なほど強く、静的hot-expert表よりdomain shiftに頑健だったことを示す。

## まず「expert poolがDRAMにも収まらない」と何が起きるのか

Mixture-of-Experts（MoE）では各layerに多数のexpert networkがあり、1 tokenはrouterが選んだ一部expertだけを通る。

計算量は疎だが、modelを正しく実行するには**全expert weightをどこかには保持**しなければならない。

小〜中規模MoEなら

- hot expert: GPU HBM
- cold expert: CPU DRAM

という2階層でも成立する。

しかしtrillion-parameter級ではexpert pool自体が数百GB〜TB級になり、CPU DRAMにも全て収まらない。

本論文のproduction modelでは

- 92 routed layers
- 1 layerあたり896 experts
- top-k = 16
- expert総数: 82,432
- int4 expert pool: 約1.45 TB
- attention/router等のdense spine: さらに約114 GB

となる。

1 accepted tokenあたり平均約1,585 expert read、約27.8 GBのexpert dataを1.45TB poolから参照する。

480GB Grace DRAMだけでは全expertを置けないため、残りはNVMe-backed fileに存在し、**DRAMそのものがNVMe expert storeのcache**になる。

## 従来設計: runtimeがexpert cacheを自分で持つ

MoE-Infinityなどのoffload systemでは、runtime側で

- expert activation frequency
- recency
- router prediction
- pinning
- prefetch

を管理し、「このexpertをDRAM/GPUに残す」と明示的に決めることが多い。

典型的にはuser spaceで大きなpinned memory arenaを確保し、expert単位でcache replacementを行う。

この設計には直感的な利点がある。

routerはmodel固有情報を知っているので、OSより賢くexpert需要を予測できそうだからである。

しかしLinuxには元々、fileを一度読んだpageを空きDRAMへ残し、memory pressureが来たら古いpageをevictする**ページキャッシュ（page cache）**がある。

expert weightをfile-backed mappingとして読めば、kernel自身が

`NVMe → DRAM page cache → accelerator`

というcache hierarchyを作れる。

論文の問いは、

**本当に専用expert cacheをもう一度user spaceで作る必要があるのか？**

である。

# この研究で重要な前提: page-cache hitをGPUが高速に読めること

通常のframeworkでfile-backed weightを扱うと

`file → CPU buffer → framework tensor → GPU`

のような余分なcopyが入り、page cacheのpolicy以前にdata pathが遅くなる。

本研究はcompanion studyのzero-copy file-backed execution contractを使い、GPUがpage-cache-resident host pageを直接高速に読む。

評価nodeで実測した主な帯域は

- HBM weight read: 約2938 GB/s
- file-backed host pageをGPUからread: 約327 GB/s
- framework-owned hostAlloc: 約330 GB/s
- ordinary malloc: 約23 GB/s
- NVMe: 約27.0 GB/s
- overlapしたcopy-then-compute streaming: 約346 GB/s

である。

つまり**page cacheにhitしたexpertなら、専用pinned arenaとほぼ同じhost-memory帯域でGPUへ供給できる**data pathを先に確立している。

この条件で初めて「evictionをkernelに任せるかuser spaceにするか」をfairに比較できる。

# Page cacheに任せるとはどういうことか

expertは個別file/pageとしてNVMe上に存在する。

runtimeがexpertを読むと、必要pageがDRAMにない場合はNVMeから読み込まれ、Linux page cacheへ入る。

次に同じexpert pageを読むとDRAMから供給される。

memory pressureが高まるとkernelのreclaim mechanismが古いpageを追い出す。

つまりruntime側で

- expert hit table
- explicit LRU list
- manual eviction copy

を持たなくても、file I/Oそのものがcache admissionになり、kernelがrecencyに基づいて容量内へ収める。

ここでの中心policyはLinuxのLRU系recency、特に評価環境ではMGLRUを含むreclaim pathである。

# Router localityを3つのmodelで調べる

kernel recencyが有効かどうかは、expert reuseが最近の履歴に現れるかに依存する。

論文は

- Qwen3-30B-A3B: 128 experts/layer
- DeepSeek-V3: 256 experts/layer
- production trillion-scale model: 896 experts/layer

のrouter traceを、systems prose、code、math、travel/chatの4 domainで調べる。

## 観測1: expert数が増えるほど「固定hot set」は弱くなる

Qwen3-30Bでは上位expertへの集中が比較的強い。

しかし896-expert production modelでは、各layerのtop-8 expertsが受け持つselectionはわずか13〜16%程度である。

大量expertへ需要が広がるため、少数hot expertを永久pinするだけではcoverageが足りない。

## 観測2: layerによって需要分布が大きく違う

production modelではtop-8 shareが

- 最も平坦なlayer: 約3.9%
- 最も集中したlayer: 約18.0%

と4.6倍違う。

固定で「各layerに同じ数のcache slot」を割り当てる設計も非効率になりやすい。

global page cacheなら、実際に最近多く読まれたlayerへ自然にDRAM pageが多く残る。

## 観測3: recency reuseは強い

production modelではexpert selectionの

- 32〜36%が直前1 token以内で再利用
- 57〜59%が8 token以内
- 80〜82%が64 token以内

に再出現する。

固定frequency rankingより、**直近で使ったexpertを残すrecency**がかなり有効なworkloadである。

## 観測4: domainが変わるとstatic hot setは変わる

domain間でtop-expert setのJaccard overlapは小さい。

production modelでも最大0.188程度しか重ならない条件がある。

code workloadで学習したhot-expert表をmathへ持っていくと、人気expertがずれる。

一方LRUは過去数十tokenの実accessから自動的に新domainへ追従する。

# Frequency oracleとLRUの比較

論文はstatic-frequency baselineに**評価traceそのものを事前に見せる**というかなり有利なoracle条件を与える。

それでもhost-tier相当のcache budgetではLRUが強い。

## 極小cacheではfrequencyが勝つ

cacheがtop-k routing fan-outと同程度しかない場合、LRUは次reuse前にexpertを追い出してthrashする。

production scaleの `B=8` 相当では

- LRU hit: 0.5%
- LFU: 12.7%
- static frequency: 9.8%

となる。

つまり「kernel LRUが常に最良」という論文ではない。

## Host DRAM級capacityではrecencyが逆転する

`B>=32`、production scaleで約52GB以上に相当する領域ではLRUがstatic frequencyへ追いつき、その後優勢になる。

production scaleの代表点ではLRUはBelady offline optimumの約70%をcaptueし、static frequencyは約3分の1程度になる。

さらにdomain shiftではstatic tableのhit率が21〜45%まで落ちる一方、LRUは70〜71%程度を維持する。

この結果が「eviction ownershipをkernelへ戻してよいのでは」という主張の核である。

# Equal-memory比較が重要な理由

user-space pinned cacheとpage cacheを比べるとき、片方だけ実質的に多くDRAMを使っていたら意味がない。

論文はcgroup memory wallを使い、

- pinned arenaのlocked memory
- page-cache resident file pages

を**同じmemory budget**へchargeして比較する。

256GB条件ではcacheから供給できた需要量は

- kernel page-cache/LRU: 75.3%
- same-domain static-frequency oracle: 74.6%

とほぼ同じである。

## それでもpinned arenaは少し速い

同じdata量がhitしていても、`pread`を通るpage-cache hit pathにはkernel/file-system処理costがある。

oracle-pinned arenaはpage cacheより1.09〜1.11×速い。

block-device counterでは実際にNVMeから読んだbyte量がほぼ同じなので、この差はcache policyではなく**mechanism overhead**である。

つまり結論は

- hit selectionではkernel LRUで十分強い
- user-space pinned arenaには約10%のmechanism advantageが残る

という二段構造になる。

# Memory-pressure benchmarkの罠: balloon + MGLRU

この論文のもう1つ重要な貢献は、cache algorithmそのものではなく**memory容量をどう人工制限するか**で結果が変わることを示した点である。

研究ではしばしば、使えるDRAMを減らすために大きなanonymous memoryを `mlock` して「balloon」として占有する。

しかしMGLRUと高いmlock率を組み合わせると、低capacityでreclaim behaviorが不自然になり、同じexpert pageを余計に読み直すre-read amplificationが発生する。

production nodeでは

- 64GB cache相当、約81% memory locked: amplification発生
- 約93GB、74% locked: 発生しない

というkneeを観測する。

一方、

- cgroup-v2 `MemoryMax`
- boot時の物理 `mem=` 制限

では同じ低capacity amplificationが現れない。

balloonだけを使ったbenchmarkでは、低capacity時のdevice trafficを約**2倍過大評価**し得る。

これは他のNVMe/offload研究にも重要で、memory-pressure benchmarkの作り方自体が結論を歪める可能性を示す。

# Router predictionはなぜほとんど効かなかったのか

model-specific cacheでは「次layerで使うexpertをrouterから予測してprefetchすればよい」と考えやすい。

本研究では実router predictorのlookahead recallは64.7%だった。

この予測を2つの方法で使う。

## 1. Kernel readahead advice

`fadvise`等で「このfile pageを近いうち使う」とkernelへ知らせる。

結果はmedian timeでわずか**0.3%改善**。

## 2. Synchronous prefetch

予測expertをblocking readで先に読む。

こちらは測定可能な改善がなかった。

さらにperfect one-layer adviceでも、kernel advisory interfaceで約5.0%改善に留まり、blocking readでは利益が出ない。

なぜならprediction accuracyだけでなく、**いつ・どの非同期mechanismでdataを配送するか**が重要だからである。

予測が当たってもcritical path上で同期readすれば、単に待ち時間を前へ移すだけになる。

この結果から論文は、model knowledgeをeviction replacementへ大量投入するより

- admission
- nonblocking advice

に限定する方が費用対効果が高い可能性を示す。

# Capacityをperformance knobとして扱える

native 1.45TB replayではDRAM cache capacityを変えると

- iteration time
- block-device traffic

が滑らかで再現性の高いmonotonic curveを描く。

run-to-run spreadは概ね4%以内。

つまりtrillion-scale MoEでも

`DRAMを何GB与えると、どれだけNVMe miss/latencyが増えるか`

をcapacity curveとしてmodel化しやすい。

これはcluster capacity planningで重要で、cache hit率を複雑なblack boxにせず、DRAM budgetそのものをsizing knobとして扱える。

# Production engineでのend-to-end結果

trace replayだけでなくproduction CUDA engineへpage-cache admissionを有効化し、balanced A/B pairを9組実行する。

結果はsteady decodeで**1.09〜1.10× speedup**。

出力token列はpair間で一致した。

つまりspeedupはexpert削除や近似routingによるものではなく、同じexpert computationを実行したままDRAM reuseを増やした効果である。

headlineとしては10%程度と大きくないが、専用cache managerを追加せずkernel default mechanismを利用して得た改善という点が設計上重要である。

# なぜGH200でこの設計が成立しやすいのか

GH200はGrace CPU memoryとGPUの間を高帯域coherent linkで接続する。

評価ではfile-backed host pageをGPUから約327GB/sで読める。

これはdiscrete PCIe GPUのhost readより大幅に高い。

そのためpage-cache hitしたexpertを「CPUにあるから遅すぎる」とは限らない。

一方、普通のPCIe GPUではhost bandwidthが数十GB/s程度になるため、

- HBM hot set
- explicit double buffering
- compression
- predictive streaming

の価値がより高くなる。

論文自身も結論をGH200 topologyから全GPUへ無条件に一般化していない。

# MoE-Infinity等との違い

MoE-Infinityのようなsystemはmodel-aware expert cacheをuser spaceで構築し、expert activation localityやprefetchを積極的に使う。

本論文は逆方向から

**「OS page cacheという既存cacheをbaselineにしたとき、専用policyは本当に必要か」**

を検証する。

違いを整理すると、

### Model-aware user-space cache

- expert単位metadataをruntimeが持つ
- explicit pin/evict
- frequency/router情報を直接policyへ使える
- data structure/control overheadが増える

### Kernel-managed page cache

- file page単位でOSがresident setを管理
- recency/reclaimをkernelへ任せる
- domain shiftへ自動適応
- model固有情報はadvice/admissionとして補助的に使う

という設計思想の差である。

# 限界

1. **GH200依存性**: Grace↔GPUの高速coherent host readが大きな前提で、PCIe discrete GPUでは同じmechanism advantageにならない。
2. **page-cache mechanism overheadは残る**: equal-memoryでpinned arenaが1.09〜1.11×速く、kernel pathが無料ではない。
3. **tiny cacheではLRUがthrash**: fan-outと同程度の極小budgetではLFU/static frequencyが有利。
4. **prediction実装依存**: router lookahead自体の価値が0.3%しかないというより、64.7% recallとfadvise/blocking-readというdelivery semanticsでの結果である。
5. **decode中心**: prefill traceを除外し、production decode localityを主に測っている。
6. **production modelの詳細非公開部分**: full architecture/workloadを完全公開できるopen-model benchmarkではない。
7. **NVMe media detailの一般性**: 3.9TB local NVMeとGH200 nodeでの結果であり、SSD firmware/RAID/topologyが変わればcapacity curveは変わる。
8. **kernel version/reclaim policy依存**: MGLRU等Linux memory-management behaviorがsystem resultへ直接影響する。

# 一般的な実装上の示唆

この論文から得られる最も重要な実務上の教訓は、NVMe/DRAM階層を作るときに**cache policyを実装する前にOS page cache baselineを測るべき**という点である。

特にfile-backed weightをzero-copyでacceleratorから読めるsystemなら、

- page cacheのrecency
- cgroupでのcapacity wall
- kernel readahead advice

だけでかなり強いbaselineになる可能性がある。

またbenchmarkでは、memory容量制限方法を少なくとも2種類でcross-checkする価値がある。

`mlock balloon`だけでdeep-pressure trafficが急増した場合、それがalgorithmic cache missなのかkernel reclaim artifactなのかを分離しなければならない。

SSD活用研究の観点では、model-aware predictionをどのexpertを残すかへ使うより、

`どのpageをcacheへadmitするか / いつasynchronous read adviceを出すか`

へ使う方が、kernelの既存recency policyと役割分担しやすい可能性がある。
