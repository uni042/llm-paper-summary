# Who Should Own the Expert Cache? Kernel-Managed Tiering for Trillion-Parameter MoE Inference

> MoE expert poolがDRAMにも収まらない領域で、専用expert cacheをuser spaceに作る代わりにOS page cacheをDRAM tierとして使えるかを、1.45 TB expert poolとGH200で検証する研究。

## 問題設定
巨大MoEではGPU HBMだけでなくhost DRAMにも全expertが収まらず、NVMe等から必要expertを読む階層が必要になる。従来systemはexpert単位のfrequency table、pinning、専用eviction policyをuser spaceで管理しがちだが、OSには既にfile pageをDRAMへcacheする仕組みがある。

## 手法
production modelを含む3種類のrouter traceを使い、OS page cacheのrecency policyと静的frequency oracleを同一memory budgetで比較する。さらにcapacity制御方法としてballoon型mlock、cgroup memory wall、物理memory制限を分け、memory pressureの測定方法そのものが結果へ与える影響も調べる。

router lookaheadはcache evictionを置き換えるのではなく、kernel readaheadへのadviceとして評価する。

## 評価条件
production trillion-parameter MoEの1.45 TB expert poolを、480 GB Grace DRAMと3.9 TB NVMeを持つNVIDIA GH200 node上でnative replayする。別のGH200でもcross-validationし、production CUDA engineでend-to-end decodeも確認する。

## 主要結果
同一memory wallでは、kernel recencyがstatic-frequency oracleとほぼ同程度の需要をDRAMから供給する。一方、pread経路ではoracle-pinned arenaに1.09〜1.11×のmechanism advantageが残るが、domain shiftではstatic hot setが劣化する。

router lookaheadは実測recall 64.7%ではkernel readahead adviceとしてmedian timeを0.3%しか改善せず、perfect one-layer adviceでも5.0%だった。production engineではpage-cache admissionを有効化するとsteady decodeが**1.09〜1.10×高速化**し、token列は一致した（Table 3 / §9）。

また、balloon + MGLRU条件だけでは低capacity時のdevice trafficを約2×過大に見せ得ることを示し、offload研究のmemory-pressure評価方法にも注意を促している（§5）。

## 限界
中心評価はGH200のcoherent-memory topologyに強く依存する。discrete PCIe GPUではhost read bandwidthが低く、HBM working setや明示的streamingが依然必要になる。router trace replayとproduction engine評価の役割も分けて解釈する必要がある。

## 既存研究との差
MoE-Infinity等はmodel-awareなexpert cache / prefetch policyをuser spaceで構築する。本研究はeviction ownership自体をOSへ戻し、model knowledgeはadmissionとadviceに使う方が堅牢ではないかを検証する。

## 一般的な実装上の含意
SSD/NVMe offloadではcache algorithmだけでなく、**OS page cacheを無効化するか利用するか、memory capacityをどう制限してbenchmarkするか**が結果を大きく左右する。特に統合・coherent memory機ではkernel-managed DRAM tierをbaselineとして比較する価値が高い。

## 引用関係
