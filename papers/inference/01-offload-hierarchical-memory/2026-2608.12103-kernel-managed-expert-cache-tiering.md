# Who Should Own the Expert Cache? Kernel-Managed Tiering for Trillion-Parameter MoE Inference

> この論文が問うのは「LRUとLFUのどちらが良いか」より一段上の問題である。**巨大MoEのエキスパートキャッシュを誰が所有すべきか**、すなわちLLMランタイムがエキスパート単位の専用キャッシュを自前実装するべきか、それともLinuxカーネルがすでに持つページキャッシュをDRAM階層として利用すべきかを実機で比較する。1.45TBのエキスパートプールが480GB Grace DRAMにも収まらない実運用規模条件で、カーネルの最近性方針が意外なほど強く、静的頻出-エキスパート表より領域移動に頑健だったことを示す。

## まず「expert poolがDRAMにも収まらない」と何が起きるのか

Mixture-of-Experts（MoE）では各層に多数のエキスパートネットワークがあり、1トークンはルータが選んだ一部エキスパートだけを通る。

計算量は疎だが、モデルを正しく実行するには**全エキスパート重みをどこかには保持**しなければならない。

小〜中規模MoEなら

- 頻出エキスパート: GPU HBM
- 低頻度エキスパート: CPU DRAM

という2階層でも成立する。

しかしtrillion-パラメータ級ではエキスパートプール自体が数百GB〜TB級になり、CPU DRAMにも全て収まらない。

本論文の実運用モデルでは

- 92ルーティング済み層
- 1層あたり896エキスパート
- 上位k = 16
- エキスパート総数: 82,432
- int4エキスパートプール: 約1.45 TB
- 注意機構/ルータ等の密 spine: さらに約114 GB

となる。

1 acceptedトークンあたり平均約1,585エキスパート読み出し、約27.8 GBのエキスパートデータを1.45TBプールから参照する。

480GB Grace DRAMだけでは全エキスパートを置けないため、残りはNVMe-backedファイルに存在し、**DRAMそのものがNVMeエキスパート格納のキャッシュ**になる。

## 従来設計: runtimeがexpert cacheを自分で持つ

MoE-Infinityなどのオフロードシステムでは、ランタイム側で

- エキスパート活性値頻度
- 最近性
- ルータ予測
- 固定
- プリフェッチ

を管理し、「このエキスパートをDRAM/GPUに残す」と明示的に決めることが多い。

典型的にはuser領域で大きな固定済みメモリ arenaを確保し、エキスパート単位でキャッシュ置換を行う。

この設計には直感的な利点がある。

ルータはモデル固有情報を知っているので、OSより賢くエキスパート需要を予測できそうだからである。

しかしLinuxには元々、ファイルを一度読んだページを空きDRAMへ残し、メモリ圧力が来たら古いページを追い出しする**ページキャッシュ（ページキャッシュ）**がある。

エキスパート重みをファイル裏付け対応付けとして読めば、カーネル自身が

`NVMe → DRAM page cache → accelerator`

というキャッシュ階層を作れる。

論文の問いは、

**本当に専用エキスパートキャッシュをもう一度user領域で作る必要があるのか？**

である。

# この研究で重要な前提: page-cache hitをGPUが高速に読めること

通常のフレームワークでファイル裏付け重みを扱うと

`file → CPU buffer → framework tensor → GPU`

のような余分なコピーが入り、ページキャッシュの方針以前にデータ経路が遅くなる。

本研究はcompanion studyのゼロコピー ファイル裏付け実行 contractを使い、GPUがページ-キャッシュ-常駐ホストページを直接高速に読む。

評価ノードで実測した主な帯域は

- HBM重み読み出し: 約2938 GB/s
- ファイル裏付けホストページをGPUから読み出し: 約327 GB/s
- フレームワーク-owned hostAlloc: 約330 GB/s
- 通常の malloc: 約23 GB/s
- NVMe: 約27.0 GB/s
- 重複実行したコピー後計算ストリーミング: 約346 GB/s

である。

つまり**ページキャッシュにヒットしたエキスパートなら、専用固定済み arenaとほぼ同じホスト-メモリ帯域でGPUへ供給できる**データ経路を先に確立している。

この条件で初めて「追い出しをカーネルに任せるかuser領域にするか」をfairに比較できる。

# Page cacheに任せるとはどういうことか

エキスパートは個別ファイル/ページとしてNVMe上に存在する。

ランタイムがエキスパートを読むと、必要ページがDRAMにない場合はNVMeから読み込まれ、Linuxページキャッシュへ入る。

次に同じエキスパートページを読むとDRAMから供給される。

メモリ圧力が高まるとカーネルのreclaim仕組みが古いページを追い出す。

つまりランタイム側で

- エキスパートヒット表
- 明示的 LRU list
- manual追い出しコピー

を持たなくても、ファイル I/Oそのものがキャッシュ受け入れになり、カーネルが最近性に基づいて容量内へ収める。

ここでの中心方針はLinuxのLRU系最近性、特に評価環境ではMGLRUを含むreclaim経路である。

# Router localityを3つのmodelで調べる

カーネル最近性が有効かどうかは、エキスパート再利用が最近の履歴に現れるかに依存する。

論文は

- Qwen3-30B-A3B: 128エキスパート/層
- DeepSeek-V3: 256エキスパート/層
- 実運用兆パラメータ規模モデル: 896エキスパート/層

のルータトレースを、systems prose、code、math、travel/chatの4領域で調べる。

## 観測1: expert数が増えるほど「固定hot set」は弱くなる

Qwen3-30Bでは上位エキスパートへの集中が比較的強い。

しかし896-エキスパート実運用モデルでは、各層の上位-8エキスパートが受け持つ選択はわずか13〜16%程度である。

大量エキスパートへ需要が広がるため、少数頻出エキスパートを永久固定するだけではcoverageが足りない。

## 観測2: layerによって需要分布が大きく違う

実運用モデルでは上位-8 shareが

- 最も平坦な層: 約3.9%
- 最も集中した層: 約18.0%

と4.6倍違う。

固定で「各層に同じ数のキャッシュ slot」を割り当てる設計も非効率になりやすい。

全体ページキャッシュなら、実際に最近多く読まれた層へ自然にDRAMページが多く残る。

## 観測3: recency reuseは強い

実運用モデルではエキスパート選択の

- 32〜36%が直前1トークン以内で再利用
- 57〜59%が8トークン以内
- 80〜82%が64トークン以内

に再出現する。

固定頻度 rankingより、**直近で使ったエキスパートを残す最近性**がかなり有効なワークロードである。

## 観測4: domainが変わるとstatic hot setは変わる

領域間で上位-エキスパート集合のJaccard重複実行は小さい。

実運用モデルでも最大0.188程度しか重ならない条件がある。

codeワークロードで学習した頻出-エキスパート表をmathへ持っていくと、人気エキスパートがずれる。

一方LRUは過去数十トークンの実アクセスから自動的に新領域へ追従する。

# Frequency oracleとLRUの比較

論文は静的-頻度比較対象に**評価トレースそのものを事前に見せる**というかなり有利な理想化基準条件を与える。

それでもホスト-階層相当のキャッシュ予算ではLRUが強い。

## 極小cacheではfrequencyが勝つ

キャッシュが上位kルーティング分岐と同程度しかない場合、LRUは次再利用前にエキスパートを追い出してスラッシングする。

実運用規模の `B=8` 相当では

- LRUヒット: 0.5%
- LFU: 12.7%
- 静的頻度: 9.8%

となる。

つまり「カーネル LRUが常に最良」という論文ではない。

## Host DRAM級capacityではrecencyが逆転する

`B>=32`、実運用規模で約52GB以上に相当する領域ではLRUが静的頻度へ追いつき、その後優勢になる。

実運用規模の代表点ではLRUはBelady offline optimumの約70%をcaptueし、静的頻度は約3分の1程度になる。

さらに領域移動では静的表のヒット率が21〜45%まで落ちる一方、LRUは70〜71%程度を維持する。

この結果が「追い出し所有権をカーネルへ戻してよいのでは」という主張の核である。

# Equal-memory比較が重要な理由

ユーザー空間固定済みキャッシュとページキャッシュを比べるとき、片方だけ実質的に多くDRAMを使っていたら意味がない。

論文はcgroupメモリ経過を使い、

- 固定済み arenaの固定済みメモリ
- ページ-キャッシュ常駐ファイル pages

を**同じメモリ予算**へchargeして比較する。

256GB条件ではキャッシュから供給できた需要量は

- カーネルページ-キャッシュ/LRU: 75.3%
- same-領域静的-頻度理想化基準: 74.6%

とほぼ同じである。

## それでもpinned arenaは少し速い

同じデータ量がヒットしていても、`pread`を通るページ-キャッシュヒット経路にはカーネル/ファイル-システム処理コストがある。

理想化基準-固定済み arenaはページキャッシュより1.09〜1.11×速い。

ブロックデバイスカウンタでは実際にNVMeから読んだバイト量がほぼ同じなので、この差はキャッシュ方針ではなく**仕組みオーバーヘッド**である。

つまり結論は

- ヒット選択ではカーネル LRUで十分強い
- ユーザー空間固定済み arenaには約10%の仕組み利点が残る

という二段構造になる。

# Memory-pressure benchmarkの罠: balloon + MGLRU

この論文のもう1つ重要な貢献は、キャッシュ algorithmそのものではなく**メモリ容量をどう人工制限するか**で結果が変わることを示した点である。

研究ではしばしば、使えるDRAMを減らすために大きなanonymousメモリを `mlock` して「膨張」として占有する。

しかしMGLRUと高いmlock率を組み合わせると、低capacityでreclaim挙動が不自然になり、同じエキスパートページを余計に読み直すre-読み出し amplificationが発生する。

実運用ノードでは

- 64GBキャッシュ相当、約81% メモリ固定済み: amplification発生
- 約93GB、74% 固定済み: 発生しない

というkneeを観測する。

一方、

- cgroup-v2 `MemoryMax`
- boot時の物理 `mem=` 制限

では同じ低capacity amplificationが現れない。

膨張だけを使ったベンチマークでは、低capacity時の装置通信量を約**2倍過大評価**し得る。

これは他のNVMe/オフロード研究にも重要で、メモリ-圧力ベンチマークの作り方自体が結論を歪める可能性を示す。

# Router predictionはなぜほとんど効かなかったのか

モデル-specificキャッシュでは「次層で使うエキスパートをルータから予測してプリフェッチすればよい」と考えやすい。

本研究では実ルータ予測器の先読み再現率は64.7%だった。

この予測を2つの方法で使う。

## 1. Kernel readahead advice

`fadvise`等で「このファイルページを近いうち使う」とカーネルへ知らせる。

結果はmedian時間でわずか**0.3%改善**。

## 2. Synchronous prefetch

予測エキスパートを待機読み出しで先に読む。

こちらは測定可能な改善がなかった。

さらにperfect one-層助言でも、カーネル advisory interfaceで約5.0%改善に留まり、待機読み出しでは利益が出ない。

なぜなら予測 accuracyだけでなく、**いつ・どの非同期仕組みでデータを配送するか**が重要だからである。

予測が当たっても重要経路上で同期読み出しすれば、単に待ち時間を前へ移すだけになる。

この結果から論文は、モデル knowledgeを追い出し置換へ大量投入するより

- 受け入れ
- nonblocking助言

に限定する方が費用対効果が高い可能性を示す。

# Capacityをperformance knobとして扱える

native 1.45TB再生ではDRAMキャッシュ capacityを変えると

- iteration時間
- ブロックデバイス通信量

が滑らかで再現性の高いmonotonic曲線を描く。

run-to-run spreadは概ね4%以内。

つまり兆パラメータ規模 MoEでも

`DRAMを何GB与えると、どれだけNVMe miss/latencyが増えるか`

をcapacity曲線としてモデル化しやすい。

これはクラスタ capacity planningで重要で、キャッシュヒット率を複雑なblack boxにせず、DRAM予算そのものをsizing knobとして扱える。

# Production engineでのend-to-end結果

トレース再生だけでなく実運用 CUDAエンジンへページ-キャッシュ受け入れを有効化し、balanced A/B対を9組実行する。

結果はsteadyデコードで**1.09〜1.10× 高速化倍率**。

出力トークン列は対間で一致した。

つまり高速化倍率はエキスパート削除や近似ルーティングによるものではなく、同じエキスパート計算を実行したままDRAM再利用を増やした効果である。

headlineとしては10%程度と大きくないが、専用キャッシュ managerを追加せずカーネル default仕組みを利用して得た改善という点が設計上重要である。

# なぜGH200でこの設計が成立しやすいのか

GH200はGrace CPUメモリとGPUの間を高帯域整合的 linkで接続する。

評価ではファイル裏付けホストページをGPUから約327GB/sで読める。

これは離散 PCIe GPUのホスト読み出しより大幅に高い。

そのためページ-キャッシュヒットしたエキスパートを「CPUにあるから遅すぎる」とは限らない。

一方、普通のPCIe GPUではホスト帯域が数十GB/s程度になるため、

- HBM頻出集合
- 明示的 double buffering
- compression
- predictiveストリーミング

の価値がより高くなる。

論文自身も結論をGH200トポロジから全GPUへ無条件に一般化していない。

# MoE-Infinity等との違い

MoE-Infinityのようなシステムはモデル認識型エキスパートキャッシュをuser領域で構築し、エキスパート活性値局所性やプリフェッチを積極的に使う。

本論文は逆方向から

**「OSページキャッシュという既存キャッシュを比較対象にしたとき、専用方針は本当に必要か」**

を検証する。

違いを整理すると、

### Model-aware user-space cache

- エキスパート単位metadataをランタイムが持つ
- 明示的固定/追い出し
- 頻度/ルータ情報を直接方針へ使える
- データ structure/制御オーバーヘッドが増える

### Kernel-managed page cache

- ファイルページ単位でOSが常駐集合を管理
- 最近性/reclaimをカーネルへ任せる
- 領域移動へ自動適応
- モデル固有情報は助言/受け入れとして補助的に使う

という設計思想の差である。

# 限界

1. **GH200依存性**: Grace↔GPUの高速整合的ホスト読み出しが大きな前提で、PCIe離散 GPUでは同じ仕組み利点にならない。
2. **ページ-キャッシュ仕組みオーバーヘッドは残る**: equal-メモリで固定済み arenaが1.09〜1.11×速く、カーネル経路が無料ではない。
3. **tinyキャッシュではLRUがスラッシング**: 分岐と同程度の極小予算ではLFU/静的頻度が有利。
4. **予測実装依存**: ルータ先読み自体の価値が0.3%しかないというより、64.7% 再現率とfadvise/待機-読み出しというdelivery意味論での結果である。
5. **デコード中心**: プリフィルトレースを除外し、実運用デコード局所性を主に測っている。
6. **実運用モデルの詳細非公開部分**: full architecture/ワークロードを完全公開できるopen-モデルベンチマークではない。
7. **NVMe media detailの一般性**: 3.9TBローカル NVMeとGH200ノードでの結果であり、SSD firmware/RAID/トポロジが変わればcapacity曲線は変わる。
8. **カーネル version/reclaim方針依存**: MGLRU等Linuxメモリ-management挙動がシステム resultへ直接影響する。

# 一般的な実装上の示唆

この論文から得られる最も重要な実務上の教訓は、NVMe/DRAM階層を作るときに**キャッシュ方針を実装する前にOSページキャッシュ比較対象を測るべき**という点である。

特にファイル裏付け重みをゼロコピーでacceleratorから読めるシステムなら、

- ページキャッシュの最近性
- cgroupでのcapacity経過
- カーネル readahead助言

だけでかなり強い比較対象になる可能性がある。

またベンチマークでは、メモリ容量制限方法を少なくとも2種類で横断-checkする価値がある。

`mlock balloon`だけでdeep-圧力通信量が急増した場合、それがalgorithmicキャッシュ missなのかカーネル reclaim artifactなのかを分離しなければならない。

SSD活用研究の観点では、モデル認識型予測をどのエキスパートを残すかへ使うより、

`どのpageをcacheへadmitするか / いつasynchronous read adviceを出すか`

へ使う方が、カーネルの既存最近性方針と役割分担しやすい可能性がある。
