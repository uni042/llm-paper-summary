# LLM in a flash：DRAM容量を超える言語モデルをフラッシュから選択的に実行する

## 概要

LLM in a flashは、モデル重み全体を端末の主記憶（DRAM）へ保持できない場合に、フラッシュストレージを重みの大容量置き場として利用し、トークン生成ごとに必要な重みだけを読み込む推論方式である。通常のオフロードではGPUメモリに収まらない重みをCPUのDRAMへ置くことが多いが、本論文は**システム全体のDRAMにもモデルが収まらない**状況を扱う。特にパーソナル機器ではフラッシュ容量がDRAMより大きくても、ランダム読出しの待ち時間と転送帯域が大きな制約になる。

著者らは、活性化が疎なフィードフォワード網（Feed-Forward Network; FFN）に着目し、必要な中間ニューロンの重みだけを読み出す。軽量な活性予測器が次に必要になるFFNニューロンを推定し、最近使ったニューロンの重みをDRAMへ短期間保持する窓方式（windowing）で再読出しを減らす。さらに同一ニューロンに対応する上向き・下向き投影重みをフラッシュ上で連続配置する行列束ね（row-column bundling）により、小さいランダムI/Oを大きい読出しへまとめる。重みを入れ替える際のDRAM再確保・再配置費用も抑える。

ACL 2024正式掲載論文は、モデルサイズの約半分しかDRAMへ割り当てられない条件を中心に、OPT 6.7B、Falcon 7B、Llama 2 7B、Persimmon 8B、Phi-2 2.7BをCPU・Metal・GPU実装で評価する。例えばOPT 6.7Bの1トークン当たり総遅延は、単純な重み再読出し方式のCPU 3182 msから669 ms、Metal M2 2270 msから305 ms、GPU 2218 msから84 msへ短縮した。重要なのはGPUの演算が26倍速くなったわけではなく、**もともと支配的だったフラッシュ読出し時間を大幅に減らした結果**という点である。

## 問題設定とハードウェア上の制約

数十億パラメータのモデルを半精度で保存すると、重みだけでも数GBから十数GB以上を必要とする。DRAM容量がこれを下回る機器で、モデルを全てフラッシュに置いて毎トークン読み直すと、計算そのものよりI/O待ちが長くなる。単純に転送量をモデルサイズとSSDの公称帯域で割るだけでは、実際の時間を予測できない。小さいランダム読出しでは、要求発行から最初のバイトが届くまでの固定待ち時間が相対的に大きく、要求回数が増えると帯域を使い切れないためである。

論文の図2は、MacBook M1 Maxの1TBフラッシュで1GiBの連続読出しが6GiB/sを超える一方、少量のランダム読出しでは転送単位と並列要求数によって実効帯域が大きく変化することを示す。著者らは32KiB以上のランダム読出しを複数スレッドで並列化する設計が有効と述べる。必要なバイトだけを細かく読む方式が必ずしも最速ではなく、多少余分なデータを読んでも連続した大きい塊にまとめる方が速い場合がある。

もう一つの制約は、FFNの活性がモデル構造に依存する点である。ReLUなどで中間ニューロンの大半がゼロになる場合は、活性ニューロンに対応する重みだけを転送できる。論文はOPT 6.7BのFFNで約97%、ReLU化したFalcon 7Bで約95%の疎性を挙げる。Llama 2もFATReLUへ変更し追加学習することで約90%の疎性を得る条件を扱う。したがって、任意の密なモデルに追加処理なしで同じI/O削減率が得られるわけではない。

## 手法

### 1. 注意重みを常駐させ、FFNだけを必要に応じて読む

基本方針は、トークン生成で繰り返し必要になる埋め込みと注意機構の重みをDRAMへ常駐させ、活性が疎なFFN部分を選択的に読み込むことである。論文では注意重みがモデル全体のおよそ3分の1を占める構成を想定する。これを保持するため、利用可能DRAMがモデルの半分程度という条件でも、FFNへ割ける空間は限定される。そこでFFNの全重みを一括常駐させず、各層・各トークンで実際に必要な部分集合をフラッシュから供給する。

FFNの上向き投影は入力を大きい中間次元へ写像し、活性関数を通した後、下向き投影で元の隠れ次元へ戻す。中間ニューロンがゼロなら、そのニューロンに対応する下向き投影の寄与もゼロになる。ただし、活性がゼロかどうかを知るために上向き投影の全重みを読み込んでいてはI/O削減が成立しない。この循環を避けるため、著者らは軽量な活性予測器を先に実行する。

### 2. 低ランク活性予測器による事前選択

各層の注意出力を入力とする低ランクの予測器を学習し、FFNの中間ニューロンが活性化するかどうかを予測する。論文の図3では小さい低ランク行列とシグモイド判定を用い、予測した活性集合に対応する上向き・下向き投影の重みだけを読み込む。予測器は出力トークンを直接生成する別の言語モデルではなく、**どの重みをストレージから取得するかを決める補助器**である。最終的なFFN計算には元のモデルの重みを使用する。

論文はC4の訓練データから10,000サンプルを使い、各予測器を2エポック学習したと記す。予測器1件の学習にはA100 GPUで約4時間を要した。したがって推論時の転送削減は無償ではなく、モデルや層に応じた事前学習費用がある。予測が外れて必要なニューロンを見落とせば元のFFN出力を完全には再現できないため、「重みは元のままだから品質は数学的に完全一致」と言い切れない。

論文表1のゼロショット評価では、OPT 6.7BのArc Easyが予測器なし66.1、予測器あり66.2、Arc Challengeが30.6対30.6、HellaSwagが50.3対49.8である。小さいが負の差もあり、品質影響が厳密にゼロという証明ではなく、評価した範囲では小さいという結果として読むべきである。

### 3. 直近トークンの活性重みを保持する窓方式

活性予測器が選んだニューロンの重みを毎回破棄すると、同じニューロンが連続するトークンで使われてもフラッシュを再読出しする。窓方式は直近 `k` トークンで活性化したニューロン集合をDRAMに保持し、次トークンでは窓内にまだない新規ニューロンの重みだけを読む。著者らは直近 `k` トークンで使った集合の大きさを `s_agg(k)` とし、新たなトークンを加えたときの増分 `s_agg(k+1)−s_agg(k)` が追加I/Oを決めると説明する。

窓を大きくすれば再利用率が上がり、読み出す重みは減る。しかしDRAMの占有量が増え、常駐できるモデルの大きさに影響する。図4はFalcon 7Bの第10層で、窓長が伸びると新規に必要なニューロンの割合が小さくなることを示す。著者らは端末の容量予算内で可能な限り大きい窓を選ぶ方針を述べるが、これは全モデル・全負荷で同じ窓長が最適であることを意味しない。

### 4. 行列束ねで小ランダム読出しを大きい連続読出しへ変える

FFNの同一中間ニューロンを使うには、上向き投影の対応する列と下向き投影の対応する行が必要になる。一般的な行列保存形式では、これらが離れた場所にあるため小さい読出しを多数発行しやすい。行列束ねは、同一ニューロンに対応する上向き投影の列と下向き投影の行をフラッシュ上で隣接させ、まとめて一度に読めるようにする。重み要素のバイト数を `b`、隠れ次元を `d_model` とすると、片側だけの `d_model×b` に対し、束ねた塊は `2d_model×b` となる。

この配置は読出し要求の固定費を償却し、フラッシュの連続転送性能を利用する。一方、論文は同時活性の相関が高いニューロン同士を束ねる別案も検討し、**最も共起するニューロンとの束ねはかえって高頻度ニューロンを何度も読み込ませた**という負の結果を報告する。共起度だけで物理配置を決めれば必ずI/Oが減るわけではない。この失敗は、局所的な共起頻度と実際の転送要求数を区別すべきことを示す。

### 5. DRAM領域の事前確保と詰め替え

転送量を減らしても、各トークンで必要な行列を再確保し、既存重みをコピーして詰め直していればメモリ管理時間が新たな支配項になる。論文は各層で必要な最大行数に合わせてDRAM領域を事前確保し、ニューロンの元の識別子と格納位置を対応付けるポインタ配列、現在の使用行数、最近の活性状態を管理する。

不要になったニューロンの行は末尾側の有効行で置き換え、残りを連続領域に詰める。新規ニューロンの重みは有効領域の末尾に追加する。こうすれば毎回行列全体を再確保・再コピーせずに済む。上向き投影と下向き投影の対応する部分を同一の格納行にまとめるため、FFNの計算時には必要な前半・後半を取り出して使用できる。論文の図6は削除・詰め替え・追加の3段階を図示する。

### 6. どこで速度が決まるか

トークン当たり遅延は、フラッシュ読出し、DRAM管理、実際の行列演算の合計である。活性予測器はI/Oを減らすが、予測自体の計算と誤予測リスクが加わる。窓方式は重み再利用を増やすがDRAMを使う。行列束ねは読出し効率を上げるが、転送する塊が大きくなる。事前確保は管理費用を減らすが、ピーク必要量の見積もりが必要になる。著者らはこれらを別々に設計した上で、実機評価で三つの時間成分を分解している。

### 品質と予測器の誤差

低ランク活性予測器を追加したOPT 6.7Bのゼロショット評価では、Arc Easyが66.1→66.2、Arc Challengeが30.6→30.6、HellaSwagが50.3→49.8となる。HellaSwagは0.5ポイント低下しており、すべての指標が不変ではない。したがって「モデルの元重みを使うので完全に無損失」という一般化は避ける。疎性を増やすためにReLUやFATReLUへ変更・追加学習したモデルでは、その変更自体が元の密なモデルとの差を生み得る点も分けて考える必要がある。

### 容量と窓長の交換条件

論文図7では、DRAMへ保持するモデル重みの割合を増やすと、フラッシュから読み込む重みが減って遅延が短くなる。窓長を増やせば直近で使ったニューロンの再利用が増えるが、キャッシュに保持する重みも増える。モデルサイズの約50%という評価条件は圧縮率ではなく、**実行時にDRAMへ置く重みの容量制約**である。フラッシュにはモデル全体の重みが残る。Phi-2では疎性が低いためDRAM割当を65%へ変更しており、全モデルが同一の50%予算で評価されたわけではない。

### 長い生成・熱・エネルギーの負の結果

著者らは通常の256トークン程度の生成に加え、OPT 6.7Bで1000トークン生成したときのフラッシュ遅延も調べた。図8では生成が進んでも平均フラッシュ読出し遅延が継続的に増加する現象は見られず、序盤はキャッシュが空のため遅延が高いと説明する。ただし、この結果だけで長時間連続負荷、端末の発熱、SSD寿命など全ての運用条件を保証するものではない。

特に重要な負の結果として、論文5.3節は、疎なフラッシュ方式が同程度の密なモデルより瞬間電力を低くできても、トークン生成時間が長いため**総消費エネルギーはむしろ高かった**と報告する。詳細な電力波形の定量評価は将来課題とされる。メモリ不足環境で推論を成立させること、単純なフラッシュ再読出し方式より高速化すること、DRAMに全重みを保持できる密な方式よりエネルギー効率が高いことは、別々の主張である。

## 既存研究との差

量子化や枝刈りはモデルの保存サイズや計算量を減らすが、LLM in a flashの主目的は、モデルがDRAMに入り切らない場合に**フラッシュからどの重みを何回・どの粒度で読むか**を最適化することである。FlexGenなどの階層オフロードはGPUとCPUのDRAMを使うが、全重みがDRAMにも入らない端末ではフラッシュの帯域が強い制約となる。SparseGPUは活性疎性に基づく選択的重みロードを扱うが、主にRAMからのロードを前提とする。本論文はフラッシュの小ランダム読出しの固定費、ニューロンごとの物理配置、短期的な再利用、DRAM詰め替えを同時に扱う。

MoE専門家キャッシュとは異なり、主に通常のTransformerのFFN中間ニューロンを単位として扱う。KVキャッシュの圧縮方式でもない。重みの読み出し最適化は、GPUカーネル高速化や投機的復号と理論上は組み合わせられるが、複数方式を重ねた場合の性能はそれぞれの測定条件を区別する必要がある。

## 限界・実装状況

第一の制約は活性疎性への依存である。FFN中間ニューロンが高い割合でゼロにならないモデルでは、読み出す重みが増え、窓方式や束ねの利得が小さくなる。疎性を得るためのReLU化やFATReLU化には追加学習やモデル変更が必要になる場合がある。活性予測器も層ごとの学習費用があり、誤予測が出力品質へ影響し得る。論文表1のHellaSwagの小幅低下は、元の重みを使うことと厳密な分布一致が同義でないことを示す。

第二に、評価は単一系列のトークン生成を中心とする。大規模な同時要求、連続バッチ処理、複数モデルの同時常駐、長大なプリフィルなどのサーバ負荷を直接評価したものではない。DRAMが十分ある機器では、フラッシュからの動的読出しより全重み常駐の方が通常は有利である。表3の20倍超という数値は、毎トークン全重みを再読出しする極端に不利な基準方式との比較であり、DRAM常駐推論に対する高速化を示すものではない。

第三に、フラッシュI/Oは端末のSSD性能、要求粒度、並列度、OSキャッシュ、熱制御に依存する。MacBook M1 Maxで測った連続読出し帯域を他の端末の小ランダム読出しへ直接代入できない。さらに予測器とキャッシュの管理にもDRAM・計算費用がある。論文の実装はHugging Face Transformers/PyTorchに基づく評価用の構成であり、すべての商用端末や推論エンジンで同じ性能が得られると実証したわけではない。

第四に、電力の評価では瞬間電力が低くても総消費エネルギーが高くなる負の結果が報告されている。モデルを動作可能にする容量面の利点と、電池持続時間やエネルギー効率の改善を混同してはならない。著者が詳細な電力解析を将来課題としていることも明記しておく。公式実装の公開コードURLは一次論文から確認できず、再監査は正式掲載PDFの方法・表1/3・図2/4/7/8・負の結果を確認したもので、追試や新たなベンチマークは行っていない。
