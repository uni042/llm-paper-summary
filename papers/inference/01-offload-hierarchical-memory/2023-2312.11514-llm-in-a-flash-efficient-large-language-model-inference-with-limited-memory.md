# LLM in a Flash: Efficient Large Language Model Inference with Limited Memory

> LLM in a Flashは直近で使ったFFN重みをDRAMに残し、ニューロン単位でFlash上の重みをまとめて必要部分だけ読み出して大規模モデルを限られたメモリで生成する。

## 概要
LLM in a Flashは、DRAMにモデル全体を保持できない端末で、モデル重みをフラッシュストレージへ置き、各トークンで必要なFFN部分だけをDRAMへ読み込む重みストリーミング方式である。MoE専用ではなく、OPT 6.7BとReLU化して疎化したFalcon 7Bを対象に、FFN活性値疎性をそのままI/O疎性へ変換する。

著者らの観測ではOPTのFFNは約97%、疎化済み Falconは約95%が非活性で、各トークンが実際に使うニューロンは少ない。そこで「全FFN重みを毎トークン読む」のではなく、活性化すると予想されたニューロンの重みだけをフラッシュから読む。

評価はApple M1 MaxとLinux + RTX 4090で行われ、モデルサイズのほぼ半分程度しか計算用メモリへ割り当てられない条件でも推論を成立させる。これはCPU DRAMへのオフロードではなく、通常のフラッシュ / SSDを直接大容量の重み置き場として使う研究であり、KVキャッシュやMoEエキスパートキャッシュは主対象ではない。

## 手法のあらまし

この論文の核心は、フラッシュオフロードで効くのが単純な「読出しバイト数」だけではなく、**読み出し回数・読み出し粒度・再利用**だと整理した点にある。主な仕組みは、直近トークンで使った重みを短期間残す `windowing`、同じニューロンに必要な重みをストレージ上でまとめる `row-column bundling`、必要重みを事前に絞る活性予測器の3つである。

### 1. `Windowing`：直近tokenで使ったFFN weightを短期間だけ残す

論文の **windowing** は、直近 `k` トークンで活性化したニューロンの重みをDRAMへ残す短期キャッシュである。

各トークンで活性化ニューロン集合を完全に入れ替えると、同じニューロンが連続して使われても毎回フラッシュ読み出しが発生する。そこで直近数トークンの利用集合を保持し、次トークンでは

`今回必要な集合 - すでにwindow内にある集合`

だけを新しく読む。

この方式が有効なのは、LLMのFFN活性値に**短期的な再利用性**があるためである。論文ではウィンドウ sizeを大きくするとhitは増える一方、DRAM使用量も増えるため、C4などで適切な`k`を選ぶ。

### 2. `Row-Column Bundling`：同じニューロンに対応するweightを連続配置する

フラッシュストレージでは、小さなランダム読み出しを大量に発行すると、読み出しリクエストを出してから最初のデータが返るまでの待ち時間の影響が大きくなる。

FFNの同じ中間ニューロンを計算するには、up-projection側の対応するrowと、down-projection側の対応するcolumnが必要になる。通常配置のままだと、この二つが離れた位置にあり、別々の読み出しになりやすい。

**row-column bundling** は、この対応するrow / columnをストレージ上で近くへ並べ、**一つの大きめの連続読み出しで両方を取れるようにするlayout変更**である。

多少使わないバイトまで読んでも、

- 小読み出しを何回も発行する
- 少し大きな読み出しを1回発行する

なら後者の方が速い場合がある、というフラッシュ固有の性質を利用している。

つまりこの手法は「バイトを最小化」するのではなく、**I/Oリクエスト数と転送量のトレードオフを最適化**している。

### 3. Activity Predictor：実際に読むニューロンを先に予測する

FFNの出力がReLUで疎になるモデルでは、attention出力から「次のFFNでどのニューロンが非ゼロになるか」を軽量予測器で推定できる。

この予測器はFFNの出力を代替するものではなく、**どの重みをフラッシュから先に持ってくるかを決めるためだけ**に使う。

したがって、最終計算には元モデルの重みを使う。予測器自体の役割はI/O削減であり、別の小型モデルでトークンを生成する推測的デコードとは異なる。

論文ではwindowingとactivity predictionを組み合わせることで、各問い合わせでフラッシュから読むFFN重みを約2%程度まで絞れる条件を示している。

### 4. Read開始時の固定待ち時間を意識したcost model

この研究ではストレージ帯域だけでなく、読み出しリクエストを出してから最初のデータが返るまでの **first-バイト遅延** もcost modelへ入れている。

そのため、

- 読み出しバイト数を減らす
- 読み出しを連続化する
- 読み出しリクエスト数を減らす

を別々に考える。

SSD/NVMeオフロードでは「帯域が3 GB/sだから300 MBを0.1秒で読める」といった単純計算だけでは小読み出しの実時間を説明できない、という点が重要である。

### 5. Memory管理のoverheadも抑える

必要重みをトークンごとにmalloc/freeしていると、I/Oを減らしてもメモリ領域の確保・解放処理が新しいボトルネックになる。

そこでDRAM領域をあらかじめ確保し、必要重みをその領域へ上書きして使う。評価ではフラッシュ読み出しだけでなくメモリ管理時間も個別に測っており、アルゴリズム上のI/O削減がランタイム上どこまで残るかを確認している。

macOSでは `F_NOCACHE`、LinuxではDirect I/Oを使い、OSのfileキャッシュを経由せずストレージから直接読むようにして、OSキャッシュによる見かけの高速化を避けている点も評価上重要である。

## 評価

### まず見るところ
- **結論:** FFN疎性を利用してフラッシュから必要重みだけを読むと、モデル全体がDRAMに入らなくてもトークン生成を成立させられる。
- **速度・効率:** 単純に全重みを再読込する方式に対し、論文全体ではCPUで4〜5倍、GPUで20〜25倍の高速化を報告する。
- **品質:** I/O最適化自体は元重みをそのまま使うため無損失。ただしFalcon評価はReLU化・疎化したmodelを前提とする。
- **評価の強さ／注意点:** **M1 MaxとRTX 4090の実機評価**。一方でバッチ=1中心で、連続バッチ処理や長いプリフィル、推測的デコードは未評価。

### 評価環境

| 環境 | 主な構成 | Weight精度 | Storage |
|---|---|---|---|
| Apple M1 Max | CPU / unified memory | 32-bit | 1 TB SSD |
| Linux + RTX 4090 | RTX 4090 24 GB | BF16 / 16-bit系 | SSD |

モデルはOPT 6.7Bと疎化済み Falcon 7Bを中心に評価している。

### 全体として報告される高速化

| 実行側 | 単純な全weight再読込に対する高速化 |
|---|---:|
| CPU | 約4〜5倍 |
| GPU | 約20〜25倍 |

この大きな倍率はGPU計算自体が20倍速くなったという意味ではなく、**比較対象側でフラッシュ I/O待ちが非常に大きい条件から、そのI/Oを大幅に削った結果**である。

### Falcon 7B / M1 Maxの代表例

ウィンドウ size 4の条件では、1トークンあたりのおおよその時間内訳は次の通り。

| 項目 | 時間 |
|---|---:|
| Flash load | 約161 ms |
| Memory management | 約90 ms |
| 合計 | 約250 ms |
| 単純baseline | 約2330 ms |

この代表条件では合計遅延が約9〜10倍改善している。

ここから分かるのは、フラッシュ読み出しを減らした後でも**メモリ領域の確保・再利用処理が無視できない割合を占める**ことである。低レベルランタイム最適化の余地が残っている。

### RTX 4090側の代表値

| 項目 | 時間 |
|---|---:|
| Flash load | 約40.5 ms |
| Memory management | 約40 ms |
| Baseline I/O | 2000 ms超 |

GPU計算が速いほど、重みがDRAMにない場合はストレージ I/Oの比率がさらに大きくなる。そのためGPU側で相対高速化倍率が大きく見える。

### Memory予算

論文は、利用可能DRAMが**モデルサイズのおおむね半分程度**でも全modelを実行できる構成を示している。

これはmodelを半分に圧縮したという意味ではなく、**残りをフラッシュに保持し、必要部分を入れ替えながら実行する**という意味である。

### 比較対象と読み方

| 比較対象 | 位置付け |
|---|---|
| 全weight再読込 | 最も単純なflash streaming baseline |
| FlexGen | 既存の階層memory/offload方式 |
| 理論最低I/O | modelの一部だけを読む理想的下限 |

主な評価指標は1トークンあたり遅延で、フラッシュ load・メモリ管理・計算の内訳も分けている。

### 評価上の制約

- 単一系列 / バッチ=1中心。
- プロンプト処理や大規模プリフィルの詳細評価は限定的。
- 連続バッチ処理は未評価。
- 推測的デコードとの組み合わせは未評価。
- 電力・発熱は主評価に含まれない。
- PyTorchベースの概念実証で、専用ストレージ/ランタイムカーネルによる最終性能ではない。
- M1 MaxではOSバッファキャッシュを無効化しており、通常利用時と遅延が変わる可能性がある。
- Falconの結果は疎化済み / ReLU系modelの活性値疎性に依存する。

したがって、**「一般dense LLMなら必ず20倍速くなる」研究ではなく、活性値疎性があり、DRAMより大きいmodelをフラッシュから読み出しながら動かすときのI/O設計**として読むのが適切である。
