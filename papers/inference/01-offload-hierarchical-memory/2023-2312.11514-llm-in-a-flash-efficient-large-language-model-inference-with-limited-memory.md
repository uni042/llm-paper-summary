# LLM in a Flash: Efficient Large Language Model Inference with Limited Memory

> Flashから必要な重み行列部分だけを読み、windowingとrow-column bundlingで端末上LLMのI/OとDRAM使用量を減らす手法。

## 概要
LLM in a Flashは、DRAMにモデル全体を保持できない端末で、モデル重みをflash storageへ置き、各tokenで必要なFFN部分だけをDRAMへ読み込むweight streaming方式である。MoE専用ではなく、OPT 6.7BとReLU化して疎化したFalcon 7Bを対象に、FFN activation sparsityをそのままI/O sparsityへ変換する。

著者らの観測ではOPTのFFNは約97%、sparsified Falconは約95%が非活性で、各tokenが実際に使うニューロンは少ない。そこで「全FFN weightを毎token読む」のではなく、activeになると予想されたニューロンのweightだけをflashから読む。

評価はApple M1 MaxとLinux + RTX 4090で行われ、モデルサイズのほぼ半分程度しか計算用memoryへ割り当てられない条件でも推論を成立させる。これはCPU DRAMへのoffloadではなく、通常のflash / SSDを直接capacity tierとして使う研究であり、KV cacheやMoE expert cacheは主対象ではない。

## 手法のあらまし

この論文の核心は、flash offloadで効くのが単純な「読出しbyte数」だけではなく、**read回数・read粒度・再利用**だと整理した点にある。主な仕組みは `windowing`、`row-column bundling`、activity predictor の3つである。

### 1. `Windowing`：直近tokenで使ったFFN weightを短期間だけ残す

論文の **windowing** は、直近 `k` tokenで活性化したニューロンのweightをDRAMへ残す短期cacheである。

各tokenでactive neuron集合を完全に入れ替えると、同じニューロンが連続して使われても毎回flash readが発生する。そこで直近数tokenの利用集合を保持し、次tokenでは

`今回必要な集合 - すでにwindow内にある集合`

だけを新しく読む。

この方式が有効なのは、LLMのFFN activationに**短期的な再利用性**があるためである。論文ではwindow sizeを大きくするとhitは増える一方、DRAM使用量も増えるため、C4などで適切な`k`を選ぶ。

### 2. `Row-Column Bundling`：同じニューロンに対応するweightを連続配置する

flash storageでは、小さなrandom readを大量に発行するとfirst-byte latencyの影響が大きくなる。

FFNの同じ中間ニューロンを計算するには、up-projection側の対応するrowと、down-projection側の対応するcolumnが必要になる。通常配置のままだと、この二つが離れた位置にあり、別々のreadになりやすい。

**row-column bundling** は、この対応するrow / columnをstorage上で近くへ並べ、**一つの大きめの連続readで両方を取れるようにするlayout変更**である。

多少使わないbyteまで読んでも、

- 小readを何回も発行する
- 少し大きなreadを1回発行する

なら後者の方が速い場合がある、というflash固有の性質を利用している。

つまりこの手法は「byteを最小化」するのではなく、**I/O request数と転送量のトレードオフを最適化**している。

### 3. Activity Predictor：実際に読むニューロンを先に予測する

FFNの出力がReLUで疎になるモデルでは、attention出力から「次のFFNでどのニューロンが非ゼロになるか」を軽量predictorで推定できる。

このpredictorはFFNの出力を代替するものではなく、**どのweightをflashから先に持ってくるかを決めるためだけ**に使う。

したがって、最終計算には元モデルのweightを使う。predictor自体の役割はI/O削減であり、別の小型モデルでtokenを生成するspeculative decodingとは異なる。

論文ではwindowingとactivity predictionを組み合わせることで、各問い合わせでflashから読むFFN weightを約2%程度まで絞れる条件を示している。

### 4. `First-byte latency` を意識したcost model

この研究ではstorage bandwidthだけでなく、read requestを出してから最初のdataが返るまでの **first-byte latency** をcost modelへ入れている。

そのため、

- read byte数を減らす
- readを連続化する
- read request数を減らす

を別々に考える。

SSD/NVMe offloadでは「帯域が3 GB/sだから300 MBを0.1秒で読める」といった単純計算だけでは小readの実時間を説明できない、という点が重要である。

### 5. Memory管理のoverheadも抑える

必要weightをtokenごとにmalloc/freeしていると、I/Oを減らしてもmemory managementが新しいbottleneckになる。

そこでDRAM領域をあらかじめ確保し、必要weightをその領域へ上書きして使う。評価ではflash readだけでなくmemory management時間も個別に測っており、アルゴリズム上のI/O削減がruntime上どこまで残るかを確認している。

macOSでは `F_NOCACHE`、LinuxではDirect I/Oを使い、OSのpage cacheによる見かけの高速化を避けている点も評価上重要である。

## 評価

### まず見るところ
- **結論:** FFN sparsityを利用してflashから必要weightだけを読むと、モデル全体がDRAMに入らなくてもtoken生成を成立させられる。
- **速度・効率:** 単純に全weightを再読込する方式に対し、論文全体ではCPUで4〜5倍、GPUで20〜25倍の高速化を報告する。
- **品質:** I/O最適化自体は元weightをそのまま使うためlossless。ただしFalcon評価はReLU化・疎化したmodelを前提とする。
- **評価の強さ／注意点:** **M1 MaxとRTX 4090の実機評価**。一方でbatch=1中心で、continuous batchingや長いprefill、speculative decodingは未評価。

### 評価環境

| 環境 | 主な構成 | Weight精度 | Storage |
|---|---|---|---|
| Apple M1 Max | CPU / unified memory | 32-bit | 1 TB SSD |
| Linux + RTX 4090 | RTX 4090 24 GB | BF16 / 16-bit系 | SSD |

モデルはOPT 6.7Bとsparsified Falcon 7Bを中心に評価している。

### 全体として報告される高速化

| 実行側 | 単純な全weight再読込に対する高速化 |
|---|---:|
| CPU | 約4〜5倍 |
| GPU | 約20〜25倍 |

この大きな倍率はGPU compute自体が20倍速くなったという意味ではなく、**baseline側でflash I/O待ちが非常に大きい条件から、そのI/Oを大幅に削った結果**である。

### Falcon 7B / M1 Maxの代表例

window size 4の条件では、1 tokenあたりのおおよその時間内訳は次の通り。

| 項目 | 時間 |
|---|---:|
| Flash load | 約161 ms |
| Memory management | 約90 ms |
| 合計 | 約250 ms |
| 単純baseline | 約2330 ms |

この代表条件では合計latencyが約9〜10倍改善している。

ここから分かるのは、flash readを減らした後でも**memory managementが無視できない割合を占める**ことである。低レベルruntime最適化の余地が残っている。

### RTX 4090側の代表値

| 項目 | 時間 |
|---|---:|
| Flash load | 約40.5 ms |
| Memory management | 約40 ms |
| Baseline I/O | 2000 ms超 |

GPU computeが速いほど、weightがDRAMにない場合はstorage I/Oの比率がさらに大きくなる。そのためGPU側で相対speedupが大きく見える。

### Memory予算

論文は、利用可能DRAMが**モデルサイズのおおむね半分程度**でも全modelを実行できる構成を示している。

これはmodelを半分に圧縮したという意味ではなく、**残りをflashに保持し、必要部分を入れ替えながら実行する**という意味である。

### 比較対象と読み方

| 比較対象 | 位置付け |
|---|---|
| 全weight再読込 | 最も単純なflash streaming baseline |
| FlexGen | 既存の階層memory/offload方式 |
| 理論最低I/O | modelの一部だけを読む理想的下限 |

主な評価指標はper-token latencyで、flash load・memory管理・計算の内訳も分けている。

### 評価上の制約

- 単一sequence / batch=1中心。
- prompt処理や大規模prefillの詳細評価は限定的。
- continuous batchingは未評価。
- speculative decodingとの組み合わせは未評価。
- 電力・発熱は主評価に含まれない。
- PyTorchベースのproof-of-conceptで、専用storage/runtime kernelによる最終性能ではない。
- M1 MaxではOS buffer cacheを無効化しており、通常利用時とlatencyが変わる可能性がある。
- Falconの結果はsparsified / ReLU系modelのactivation sparsityに依存する。

したがって、**「一般dense LLMなら必ず20倍速くなる」研究ではなく、activation sparsityがあり、DRAMより大きいmodelをflash tierから動かすときのI/O設計**として読むのが適切である。
