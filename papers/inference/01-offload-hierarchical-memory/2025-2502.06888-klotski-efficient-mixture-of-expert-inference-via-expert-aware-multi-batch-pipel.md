# Klotski: Efficient Mixture-of-Expert Inference via Expert-Aware Multi-Batch Pipeline

> 複数batchで共通して使われるexpertを先にGPUで計算し、その計算中にまだGPUにないexpertをCPU RAM / SSDから読み込むことで、巨大MoEのI/O待ちを隠す単一GPU向け推論system。

## 概要
Klotskiは、GPU VRAMにexpert weightが収まらないMoEで、**複数batchを同時に流してGPU計算時間を長くし、その間にCPU RAM / SSDから次expertを読む**ことでGPUがI/Oを待つ時間を減らす推論engineである。

Dense LLMならbatchを増やすほどweight再利用が効きやすいが、MoEではbatchを増やすと選ばれるexpertの種類も増え、単純なmulti-batch化だけではI/O量も増える。Klotskiはこの問題に対し、複数batchで共通して多く使われるexpertを先にGPUで計算し、その計算時間を**まだGPUにないexpertの先読み時間**として使う。

RTX 3090環境では実際のSSD（約1 GB/s read）まで含めて評価しており、CPU DRAMだけのoffloadより階層が深い。

## 手法のあらまし

Klotskiの主要な仕組みは、複数batchをまとめて扱うこと、SSD→CPU→GPUの二段先読み、よく使われそうなexpertの予測、expertの実行順変更である。

### 1. 複数batchを一つの実行単位として扱う

Klotskiはbatchを単純に大きくするのではなく、複数のbatchをまとめた **batch group** をpipeline単位として扱う。

batch group内のbatch数を`n`とすると、`n`を増やすほどGPU計算時間が長くなり、その裏でweight I/Oを隠しやすくなる。

一方で、

- 選ばれるexpert数が増えて読むweightも増える
- KV cacheが増える
- VRAM使用量が増える

ため、`n`は大きければよいわけではない。

実行前の測定結果を使うplannerは各layerのcompute時間とI/O時間を見て、**GPUがI/Oを待つ時間をほぼ隠せる最小の`n`**を選ぶ。

### 2. CPU RAMが十分な場合：1段先のweightをprefetchする

CPU RAMへmodel全体を保持できる場合は、GPUがlayer `i`を計算している間にlayer `i+1`で必要になるtensorをCPU→GPUへprefetchする。

これは、片方のbufferを計算に使っている間にもう片方へ次dataを用意する方式に近い。ただしMoEでは全expertを読むのではなく、後述のexpert利用予測を使って優先順位を付ける。

### 3. CPU RAMも足りない場合：SSD→RAM→GPUを二段階で先読みする

CPU RAMには固定で`L` layer分程度のweightを保持し、同時に二つのprefetchを走らせる。論文ではこれを **two-level prefetch** と呼ぶ。

- GPU側：CPU RAMから近い将来のlayerを読む
- CPU側：SSDからさらに先のlayerをRAMへ読む

イメージとしては、GPUが`i+1`用weightをRAMから受け取っている間に、CPUがSSDから`i+L`用weightを先回りして読む。

これによりGPUが低速SSDを直接待つことを避け、**SSD → CPU RAM → GPU VRAM** の二段pipelineを形成する。

### 4. 複数batchで多く使われそうなexpertだけ先に読む

multi-batchでは選ばれるexpert数が増えるため、全候補をprefetchすると帯域を使い切ってしまう。

そこでKlotskiは事前にexpert同士の利用関係を集計し、直前layerのrouting履歴から現在layerで多く使われそうなexpertを予測する。

論文の主設定ではpath length `l=1`、つまり**直前layerのexpert選択だけ**を主な予測信号に使う。

複数batchのrouting傾向を集約し、「batch group全体で多く使われそうなexpert」を先に読むことで、少数tokenしか使わないexpertのI/Oを後回しにする。

### 5. GPUにすでにあるexpertから先に計算する

通常のrouting順どおりに計算するのではなく、Klotskiは**GPUにすでにあるexpertを先に計算**する。

その計算中に、まだGPUにないexpertをCPU / SSDからtransferする。

つまり実行順を、

`routing順` ではなく `I/Oを隠しやすい順`

へ並べ替える。

expert outputは最終的に元のtoken位置へ戻すため、計算順変更自体はmodel qualityを変えない。

### 6. WeightとKVの転送を別々に進める

実装では少なくとも次の4本のCUDA streamを用途別に使う。

| Stream | 役割 |
|---|---|
| Weight prefetch | 次weightをCPU→GPUへ読む |
| Expert transfer | gate確定後の必要expertを補う |
| KV prefetch | 次micro/batch用KVを用意 |
| KV save | 計算済みKVを保存 |

weightとKVを同じcopy queueに詰めず、依存しないI/Oを同時進行させる。

### 7. 量子化とsparse attentionは別の追加最適化

Klotskiは4-bit HQQでweight transfer量を減らす構成や、StreamingLLM型のsparse attentionでmulti-batch時のKV cacheを抑える構成も評価する。

ただしこれらはpipelineそのものとは別の最適化である。

- HQQ → weightを低bit化して転送byte数を減らす
- sparse attention → 保持するKV容量を減らす
- Klotski pipeline → I/O待ちをGPU計算と同時進行させる

と役割を分けて読む必要がある。

## 評価

### まず見るところ
- **結論:** multi-batchで共通して使われるexpertの計算をI/O待ちを隠す時間として使うと、CPU RAMだけでなく実SSDまで含むoffloadでも巨大MoEを単一GPUで動かせる。
- **実速度:** Mixtral-8x22BをRTX 3090で1.3 tokens/s超、H800で約53 tokens/sまで引き上げる構成要素比較を示す。
- **品質:** pipeline/cache/prefetch自体はlossless。4-bit量子化やsparse attentionを有効化した場合は別のquality trade-offがある。
- **メモリ・I/O:** **RTX 3090環境では実SSD 1 GB/sを使用**し、SSD→RAM→GPUの二段prefetchを評価。
- **注意点:** batch groupを増やすとKV cacheが膨らむため、I/Oを隠せる時間とVRAM消費のtrade-offが強い。

### 実機環境

| 環境 | GPU | CPU / RAM | PCIe | SSD |

| Model | 総parameter規模 | Precision |
|---|---:|---|
| Mixtral-8x7B | 約46.7B | BF16 / optional quantization |
| Mixtral-8x22B | 約141B | BF16 / optional quantization |

主条件はinput 512、output 32、batch 4〜64。

### 比較対象

| Baseline | 特徴 |
|---|---|
| Hugging Face Accelerate | 一般的offload |
| DeepSpeed-FastGen | serving runtime |
| FlexGen | multi-batch階層offload |
| MoE-Infinity | routing履歴を使うexpert cache |
| Fiddler | CPU/GPU expert execution切替 |

### 最大throughput改善

| 比較対象 | 最大speedup |
|---|---:|
| Accelerate | **85.12倍** |
| FastGen | **15.45倍** |
| FlexGen | **2.23倍** |
| MoE-Infinity | **19.06倍** |
| Fiddler | **9.53倍** |

非常に大きな倍率は、一部baselineが巨大22B MoEのSSD / low-memory条件でほぼI/Oを待ち続けていることも含む。通常のGPU-resident推論に対する85倍高速化という意味ではない。

### RTX 3090 / Mixtral-8x22Bでの構成要素ごとの効果

| 構成 | Throughput |
|---|---:|
| Simple pipeline | 0.01 token/s |
| + Multi-batch | 0.97 |
| + 利用expert予測prefetch | 1.127 |
| + Expert順序調整 | **1.325** |
| + Quantization | **1.366** |

最大の改善はmulti-batch化で、**GPU computeを長くしてSSD / CPU I/Oを隠す時間を作ること**がまず重要だと分かる。その後expert予測と実行順序が上積みする。

### H800 / Mixtral-8x22Bでの構成要素ごとの効果

| 構成 | Throughput |
|---|---:|
| Simple pipeline | 1.149 token/s |
| + Multi-batch | 34.07 |
| + 利用expert予測prefetch | 44.17 |
| + Expert順序調整 | 52.85 |
| + Quantization | **53.125** |

H800ではCPU RAMが十分でdiskが主bottleneckではないため、主にCPU↔GPU pipelineとexpertを考慮した実行順の効果を見る結果になる。

### Expert予測精度

論文では複数の予測指標を報告する。

| 指標 | 値 |
|---|---:|
| Layer内で必要expertを先読み候補のどこかに含めた率 | 100% |
| Single sequence平均 | 42.24% |
| 優先して先読みするexpertの選択精度 | 58.89% |

`100%`だけを見ると完全予測に見えるが、これは広い候補集合のどこかに必要expertを含めた指標である。実際に優先prefetchするexpertの精度は約59%であり、指標を分けて読む必要がある。

### GPU memory削減

| 条件 | Memory削減 |
|---|---:|
| ほぼ全tensor offload | 94.1%以上 |
| 3090級の実用設定 | 約74.5%削減と報告 |

memoryを減らすほどI/O量は増えるため、throughputとセットで評価する必要がある。

### Large batch

batch 128でもFlexGenより約15%高いthroughputを報告する。ただしbatch groupを増やすとKV cacheが増加し、Fiddler / MoE-Infinityは22Bでbatch16付近が上限になった条件もある。

### 評価上の制約

- SSD性能はEnvironment 1の約1 GB/sに依存する。
- Environment 2はCPU RAMが十分で、disk I/O評価とは性質が違う。
- expert利用関係の表は事前に作る必要がある。
- routing patternが変わるとexpert予測が外れ得る。
- batch groupを大きくするとKV cache OOMが起こる。
- HQQ / sparse attentionを使う場合、pipelineとは別の品質影響がある。
- 実装はPyTorch + Hugging Face + FlexGen上の研究prototypeで、version差に注意が必要。
