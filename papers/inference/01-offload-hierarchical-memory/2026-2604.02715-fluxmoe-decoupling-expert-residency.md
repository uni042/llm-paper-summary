# FluxMoE: Decoupling Expert Residency for High-Performance MoE Serving

> FluxMoEは、MoEのエキスパート重みを「モデルを読み込みしたらsession終了までGPUに居続ける静的パラメータ」とみなす前提を崩す。各層を実行する直前だけその層のエキスパートをGPUへ**実体化（materialize）**し、使い終えたら物理メモリを解放する。これにより巨大エキスパートプールが占有していたGPUメモリをKVキャッシュへ回し、大バッチ・長文脈で起きるKV入れ替えを防ぐ。必要エキスパートは圧縮済み GPUメモリとCPU DRAMからストリームし、転送時間が層計算時間の裏へ隠れるぎりぎりまでエキスパート常駐を削る。

## まずMoEの「疎な計算」と「密なmemory」の矛盾

Mixture-of-Experts（MoE）では、通常のTransformer FFNの代わりに多数のエキスパート FFNを持つ。

1トークンはルータにより少数エキスパートだけへ送られるため、合計パラメータ数を大きくしても1トークンあたりの計算量は比較的小さい。

しかし一般的なinferenceエンジンはモデル読み込み時に**全エキスパート重みをGPUへ常駐**させる。

つまり

- 計算: 毎トークンで一部エキスパートしか使わない
- メモリ: 全エキスパートを常時置く

という不均衡が生じる。

例えばDeepSeek-R1の671BパラメータをFP8で保持すると約671GBで、16×H100 80GBに載せても集約 HBMの約52%を重みだけで占有するという例を論文は挙げる。

現在層以外のエキスパートはその瞬間使われていないのに、そのメモリをKVキャッシュへ渡せない。

# なぜKV cacheへmemoryを回すとthroughputが上がるのか

デコード時のKVキャッシュは

`batch size × context length`

にほぼ比例して増える。

GPUメモリにKVを多く置ければ

- より多くのリクエストを同時にバッチできる
- より長い文脈を入れ替えせず保持できる

ためスループットが上がる。

論文のMixtral-8×7B計測ではKV予算を20GiBから60GiBへ増やすと、バッチサイズ 128でスループットが**58.8%増加**する。

また20GiB予算では文脈を1024→4096へ伸ばすとスループットが66.7%低下するが、60GiB予算ならその低下を53.5%抑えられる。

原因はKVがGPUに収まらなくなった際のCPU↔GPU入れ替えである。

したがってFluxMoEは

**エキスパートキャッシュヒット率を最大化することより、エキスパート重みが占めるVRAMを減らしてKV常駐を最大化する方が速い領域がある**

と考える。

# Expert pagingという実行モデル

FluxMoEはモデルを

`compute graph + streamed parameters`

として捉える。

Transformerの計算グラフ自体は変えない。

変えるのはエキスパートパラメータが物理GPUメモリに存在する期間だけである。

層 `i`を実行するとき、概念的には

1. 層 `i-1`のエキスパートバッファを解放
2. 層 `i`のエキスパートが常駐であることを確認
3. 層 `i`を計算
4. 同時に層 `i+1`をプリフェッチ

する。

この**滑動常駐窓（sliding residencyウィンドウ）**により、最低限保持するエキスパートは連続2層分程度でよい。

全 `N` 層分を固定常駐する場合に比べ、必須エキスパート使用量は理想的には約 `2/N` まで下げられる。

ただしメモリに余裕があるときは追加エキスパートをGPUに残し、毎回ストリームする量を減らす。

# 「expertを入れ替える」と既存kernelのpointerが壊れないのか

PyTorch/Triton/CUDAカーネルは通常、重みテンソルのポインタがモデル寿命中に安定していることを前提にする。

単純にエキスパートテンソルを空きして別アドレスへ読み込みすると、既存カーネル/モジュールが持つポインタを全部更新しなければならない。

FluxMoEはこれを**PagedTensor**で解決する。

## 仮想addressは固定、物理memoryだけ差し替える

各エキスパートテンソルについてGPU仮想アドレス範囲を最初に予約する。

この仮想アドレスはモデル実行中ずっと変えない。

一方、実際にHBMを消費する物理ブロックは少数プールだけ用意し、必要層へ動的に対応付け／解除する。

例えば論理には層 1〜48の全エキスパートテンソルアドレスが存在して見えるが、物理 HBMが裏付けしているのは現在/次層だけ、という状態を作る。

実装は `CUDA Virtual Memory Management`（CUDA VMM）の

- `cuMemMap`
- `cuMemUnmap`

等を使う。

これによりカーネルから見るポインタは普通の連続テンソルのままで、カーネル内部へページ表の検索処理を追加しなくてよい。

## PagedAttentionとの違い

vLLMのPagedAttentionもvirtualizationを使うが、KVページはリクエストごとに非連続であり、カーネル実行中に論理→物理ブロック表を参照する必要がある。

エキスパート重みは事情が違う。

ある層を実行する前に必要エキスパートテンソルを連続仮想範囲へ対応表しておけば、その層のカーネル実行中は対応付けが固定される。

したがってアドレス変換をカーネル外、起動前に終えられる。

この性質が既存MoEカーネルを変更せず使える理由である。

# 2種類のtensorを別streamで同時に供給する

1エキスパートのFFNは主に

- fusedゲート/up射影重み
- down射影重み

という異なるサイズの2テンソルを持つ。

PagedTensorは両者に独立仮想アドレス領域と物理ブロックプールを作る。

2-層常駐窓用に、各テンソル種別について `2L` ブロック、合計 `4L` 物理ブロックを持つ。

2つの読み込みストリームを使ってゲート/upとdownテンソルを並列に転送/解凍し、ストレージバックエンド帯域を使い切る。

# WAR / RAW synchronizationは何を守るのか

物理ブロックを再利用するには、古いエキスパートを使うカーネルが完全に終わったことを保証しなければならない。

FluxMoEはCUDAイベントで2つの依存関係を守る。

### 書き込み後読み出しではなく、Write-After-Read（WAR）

古い層がまだ物理ブロックを読んでいる間、そのブロックを次エキスパートの読み込みで上書きしてはいけない。

計算完了イベントを待ってからブロックを再対応表する。

### Read-After-Write（RAW）

次層のカーネルはエキスパート読み込み/解凍が完全に終わる前に起動してはいけない。

読み込み完了イベントを計算ストリームが待つ。

この2つにより、パラメータを非同期で入れ替えてもカーネルが部分的/overwritten重みを読むことを防ぐ。

# Expert storage hierarchy

PagedTensorは「どのアドレスへ読み込みするか」を解決するだけで、エキスパート正本をどこに置くかは別問題である。

FluxMoE試作は主に2バックエンドを使う。

1. **圧縮GPU階層（圧縮済み GPUバックエンド）**
2. **CPU固定済み DRAM階層**

## 圧縮GPU tier

エキスパート重みを圧縮した状態でGPUメモリに保持する。

必要時にGPU上で高速解凍してPagedTensorバッファへ実体化する。

試作ではエキスパート exponent bitsへのselective Huffman codingを使う。

圧縮状態でもVRAMは消費するが、CPUからPCIeで送るより高い供給スループットを得られる。

## CPU DRAM tier

より多くのエキスパートを固定済みホスト DRAMへ置き、asynchronous DMAでPCIe転送する。

GPU容量を大きく節約できるが読み込み帯域は遅い。

# なぜbackendへbandwidth比例でexpertを置くのか

圧縮済み GPUとCPU DRAMを同時に使う場合、片方に多く割り当てすぎると遅いバックエンドが重要経路になる。

バックエンド `k` の実効読み込み帯域を `B_k`、そこへ置くパラメータ割合を `x_k` とすると、1層の読み込み時間は概ね

`x_k × P_layer / B_k`

になる。

並列に読み込みするなら、全バックエンドがほぼ同時に終わる配分が最も速い。

そのため

`x_k = B_k / ΣB`

のように**帯域比例**でパラメータを分配する。

例えば圧縮済み GPUバックエンドがCPU DRAMの2倍速ければ、概ね2倍のパラメータ volumeをGPU圧縮階層へ担当させる。

これは「頻出エキスパートをGPUへ、低頻度エキスパートをCPUへ」という頻度キャッシュとは発想が違う。

FluxMoEのストレージ partitionは主に**供給帯域を合成して層全体をdeadlineまでに読み込みする**ためのものだ。

# Budget-Aware Residency Planner

完全ストリーミングでエキスパートメモリを最小にするとKVには有利だが、PCIe/解凍が遅くて計算を待たせる可能性がある。

逆にエキスパートを大量常駐にするとストリーミングコストは減るがKV容量が減る。

FluxMoEはランタイムでこの境界を自動調整する。

## ρ = compute時間 / load時間

計画器は

`ρ = τ_comp(theory) / τ_load`

を見る。

### `ρ > 1`

計算の方が読み込みより長い。

つまりエキスパート読み込みは計算の裏へ完全に隠せている。

まだエキスパート常駐を減らしても性能を落とさず、VRAMをKVへ返せる余地がある。

→ 常駐割合 `α` を下げる。

### `ρ < 0.9`

エキスパート読み込みの方が遅く、順方向がI/O待ちになっている。

→ `α` を上げて、より多くのエキスパートをGPU側へ常駐にする。

### `0.9 <= ρ <= 1`

何もしない。

この未使用領域はPCIe帯域の短期揺らぎで常駐が上下し続けるoscillationを防ぐ。

目標は**読み込み時間と計算時間がほぼ同じになるknee**である。

そこならエキスパートストレージを最大限削りながらI/O遅延をほぼ隠せる。

# KV cacheをhard priorityにする

計画器には性能比だけでなくメモリ safety constraintがある。

GPU総予算を `C_gpu`、現在KV使用量を `C_kv` とすると、エキスパートへ使える上限は

`C_res = C_gpu - C_kv`

である。

エキスパート常駐メモリ `C_exp(α)` は常に

`C_exp(α) <= C_gpu - C_kv`

を満たす。

つまりKVキャッシュが増えたら、たとえエキスパートストリーミングが遅くなってもエキスパート常駐を削る。

これはFluxMoEの価値判断を明確にしている。

**KV入れ替えでバッチ/並行性を失うより、重みストリーミングを増やしてでもKVをGPUに残す**。

# Prefillよりdecodeを主対象にする理由

プリフィルは大量トークンをまとめて処理するため計算-heavyで、層計算時間がエキスパート読み込み時間より長くなりやすい。

論文ではプリフィルで `ρ >> 1` となり、パラメータ実体化が自然に計算へ隠れると説明する。

一方デコードは1トークンずつでメモリ-boundになり、KVキャッシュも時間とともに増える。

そのため

- エキスパート I/Oを隠せるか
- KV capacityを確保できるか

のトレードオフが厳しい。

FluxMoEの常駐計画器は主にデコード phaseを最適化する。

TTFT中心のプリフィルシステムではなく、**steadyトークン生成スループット**を狙う設計である。

# 実装

vLLM v0.10.2上へmiddlewareとして実装する。

規模は約

- C++: 3.1K LoC
- Python: 2.1K LoC
- vLLM本体へのinterface変更: 約20 LoC

である。

論理テンソル抽象化をカーネル外へ置いたため、vLLM/Triton/PyTorch側への侵襲を比較的小さくしている。

試作では理論上の3-状態

- 非圧縮 GPU-常駐
- 圧縮済み GPU-常駐
- CPU-常駐

のうち、常時非圧縮常駐割合 `x=0` とし、圧縮済み GPU + CPUの2バックエンドへ重点を置く。

# 評価条件

主testbed:

- GPU: 4× NVIDIA L40 48GB PCIe
- CPU: Intel Xeon Platinum 8358、計128 vCPU
- ホスト DRAM: 2 TiB
- Disk: 3 TB
- Tensor Parallelism: TP=4

Model:

- Mixtral-8×7B-Instruct: 47Bパラメータ、32層
- Qwen3-Next-80B-A3B-Instruct: 80B合計、3B有効級、48層

バッチサイズは32〜256、文脈は最大4096トークンなどメモリ圧力が強い領域を含む。

# 主要結果

## 1. Qwen3-Nextで最大3.0× throughput

Qwen3-Next-80B-A3B-Instruct、バッチ 256、文脈 4096のメモリ-intensive条件で、通常vLLMに対して**最大3.0× スループット**を達成する。

単純重み-オフロード比較に対しては最大約3.7×。

この条件では通常vLLMがエキスパート重み常駐のためKV予算を十分確保できず、KV入れ替えでスループットを落とす。

FluxMoEはエキスパートをストリーミング対象にしてKVを常駐に保つため、パラメータ I/Oが増えてもシステム全体では速くなる。

## 2. KV budgetの価値を直接確認

Mixtral計測でKV予算 20GiB→60GiBに増やすだけでbatch128スループットが58.8%上がる。

FluxMoEの3× headlineは「エキスパート読み込みカーネルが3倍速い」という結果ではない。

**エキスパートメモリを削ったことでより多くのKVをGPUへ残し、入れ替えとバッチ制約を除去したシステム-レベル高速化倍率**である。

## 3. Mixtralでは通常vLLMがOOMするcapacity領域も実行

よりメモリ-constrainedなMixtral設定では通常vLLMがモデル initializationでOOMする条件がある。

FluxMoEは全エキスパートを非圧縮 GPU常駐にしないため、同じGPUメモリでモデルを起動できる。

これはスループット improvementだけでなく**feasibility extension**でもある。

## 4. RuntimeでresidencyがKV pressureへ追従

バッチ/文脈が増えてKV使用量が増えると計画器はエキスパート常駐 `α` を下げる。

逆に読み込み時間が計算を超えてI/Oボトルネックになれば `α` を戻す。

実験ではこのfeedbackにより、静的常駐設定より読み込み/計算重複実行を保ちながらメモリ圧力へ適応する。

## 5. PagedTensor overheadは最大約3.0%

仮想対応付け、CUDAイベント、実体化管理を追加しても、PagedTensor抽象化単体の管理オーバーヘッドは最大約3.0%と報告する。

これは既存カーネルへアドレス-変換 logicを埋め込まず、対応付けを起動前に完了する設計の利点である。

# MoE-Infinity / ProMoEとの違い

多くのエキスパートオフロード研究は

`次に使うexpertを予測し、hot expertをcacheしてmissを減らす`

ことに重点を置く。

FluxMoEは異なる問いを立てる。

**そもそも全エキスパート重みを永続GPU状態として扱う必要があるのか？**

層実行順序は固定なので、「次にどの層のエキスパート集合が必要か」はルータ予測なしでも分かる。

FluxMoE試作では層単位で全エキスパートテンソルを実体化し、物理常駐だけをvirtualizeする。

したがってルータヒット予測精度へ依存せず、カーネル互換性とメモリ予算制御を中心に据える。

## Expert cacheとの関係

頻度/最近性キャッシュは「どのエキスパートを残すか」を決める。

FluxMoEの常駐計画器はより粗いレベルで

`expert全体へ何GBまでGPU budgetを与えるか`

をKV圧力と読み込み帯域から決める。

将来的には両者を組み合わせ、与えられた常駐予算内で頻出エキスパートを選ぶ設計も可能である。

# なぜNVMeを直接使わないのか

この論文のストレージ階層は主に

- 圧縮済み GPUメモリ
- CPU固定済み DRAM

であり、NVMeエキスパートストリーミングをmain経路にしていない。

理由はデコード層間の短い計算窓内へエキスパートパラメータ読み込みを隠す必要があり、通常の NVMe帯域/遅延では層単位の巨大重みを毎ステップ供給するのが厳しいからである。

SSD/NVMeを追加階層にするなら

- DRAM頻出裏付け格納
- ahead-of-時間層プリフェッチ
- エキスパート-レベル予測/キャッシュ
- compression

等でNVMe読み出しをより早い時点から始める必要がある。

# 限界

1. **CPU DRAMとPCIe帯域が必要**: 2TiBホストメモリとL40 PCIe serverで評価しており、ホスト資源が小さいノードでは成立領域が狭い。
2. **主モデルは2種類**: Qwen3-NextとMixtral中心で、エキスパート architectureが大きく異なるモデルへの一般性は追加検証が必要。
3. **NVMe直接ストリーミング未評価**: エキスパートプールがCPU DRAMにも収まらない兆パラメータ規模では別の下位階層設計が必要。
4. **層単位で全エキスパート実体化**: ルータが実際に選ぶエキスパートだけを細粒度転送する方式ではなく、層重み集合のストリーミング帯域が大きい。
5. **Prototypeはtri-状態全体を実装していない**: 理論上の非圧縮/ 圧縮済み/CPU三段のうち現試作は `x=0` のspecific design。
6. **Planner計測依存**: theoretical計算時間とバックエンド帯域 estimateがハードウェア/ワークロード変化でずれる可能性がある。
7. **PCIe burstへの未使用領域はheuristic**: `θ=0.9` はempiricalで、別システムでは再調整が必要。
8. **TTFTではなくデコードスループット重視**: プリフィル-heavy interactiveワークロードのfirst-トークン遅延最適化は中心ではない。
9. **公式code未確認**: 2026-09-10時点で論文に対応する公開repositoryを一次資料から確認できていない。

# 一般的な実装上の示唆

FluxMoEから得られる重要な考え方は、GPUメモリ予算を

`weightsをまず置き、残りをKVへ渡す`

という静的 priorityにしないことだ。

提供スループットへ直接効くランタイム状態がKVなら、

`KV必要量を先に確保し、weight residencyを残りbudgetへ適応させる`

という逆priorityが合理的な場合がある。

また、仮想アドレスを安定させ物理裏付けだけ差し替えるPagedTensorは、エキスパート以外のlarge immutableパラメータにも応用可能である。

- 複数モデル重みページング
- adapter/LoRAページング
- 層単位圧縮済み重み tiering

などで、既存カーネルにアドレス変換を追加せずメモリ virtualizationを導入する設計パターンになる。

SSD研究の観点では、FluxMoEの計画器が使う

`compute window >= lower-tier load time`

という条件が重要である。

SSDを階層へ追加する場合も、ただ容量を増やすのではなく、どの将来層/エキスパートを**何層前から読み始めれば計算へ完全に隠せるか**を常駐制御と共同設計する必要がある。
