# FluxMoE: Decoupling Expert Residency for High-Performance MoE Serving

> FluxMoEは、MoEのexpert weightを「modelをloadしたらsession終了までGPUに居続ける静的parameter」とみなす前提を崩す。各layerを実行する直前だけそのlayerのexpertをGPUへ**実体化（materialize）**し、使い終えたらphysical memoryを解放する。これにより巨大expert poolが占有していたGPU memoryをKV cacheへ回し、大batch・長contextで起きるKV swappingを防ぐ。必要expertはcompressed GPU memoryとCPU DRAMからstreamし、転送時間がlayer計算時間の裏へ隠れるぎりぎりまでexpert residencyを削る。

## まずMoEの「疎な計算」と「密なmemory」の矛盾

Mixture-of-Experts（MoE）では、通常のTransformer FFNの代わりに多数のexpert FFNを持つ。

1 tokenはrouterにより少数expertだけへ送られるため、total parameter数を大きくしても1 tokenあたりの計算量は比較的小さい。

しかし一般的なinference engineはmodel load時に**全expert weightをGPUへ常駐**させる。

つまり

- compute: 毎tokenで一部expertしか使わない
- memory: 全expertを常時置く

という不均衡が生じる。

例えばDeepSeek-R1の671B parametersをFP8で保持すると約671GBで、16×H100 80GBに載せてもaggregate HBMの約52%をweightだけで占有するという例を論文は挙げる。

現在layer以外のexpertはその瞬間使われていないのに、そのmemoryをKV cacheへ渡せない。

# なぜKV cacheへmemoryを回すとthroughputが上がるのか

decode時のKV cacheは

`batch size × context length`

にほぼ比例して増える。

GPU memoryにKVを多く置ければ

- より多くのrequestを同時にbatchできる
- より長いcontextをswapせず保持できる

ためthroughputが上がる。

論文のMixtral-8×7B profilingではKV budgetを20GiBから60GiBへ増やすと、batch size 128でthroughputが**58.8%増加**する。

また20GiB budgetではcontextを1024→4096へ伸ばすとthroughputが66.7%低下するが、60GiB budgetならその低下を53.5%抑えられる。

原因はKVがGPUに収まらなくなった際のCPU↔GPU swappingである。

したがってFluxMoEは

**expert cache hit率を最大化することより、expert weightが占めるVRAMを減らしてKV residencyを最大化する方が速い領域がある**

と考える。

# Expert pagingという実行モデル

FluxMoEはmodelを

`compute graph + streamed parameters`

として捉える。

Transformerの計算graph自体は変えない。

変えるのはexpert parameterが物理GPU memoryに存在する期間だけである。

layer `i`を実行するとき、概念的には

1. layer `i-1`のexpert bufferを解放
2. layer `i`のexpertがresidentであることを確認
3. layer `i`をcompute
4. 同時にlayer `i+1`をprefetch

する。

この**滑動常駐窓（sliding residency window）**により、最低限保持するexpertは連続2 layer分程度でよい。

全 `N` layer分を固定常駐する場合に比べ、mandatory expert footprintは理想的には約 `2/N` まで下げられる。

ただしmemoryに余裕があるときは追加expertをGPUに残し、毎回streamする量を減らす。

# 「expertを入れ替える」と既存kernelのpointerが壊れないのか

PyTorch/Triton/CUDA kernelは通常、weight tensorのpointerがmodel lifetime中に安定していることを前提にする。

単純にexpert tensorをfreeして別addressへloadすると、既存kernel/moduleが持つpointerを全部更新しなければならない。

FluxMoEはこれを**PagedTensor**で解決する。

## 仮想addressは固定、物理memoryだけ差し替える

各expert tensorについてGPU virtual address rangeを最初に予約する。

このvirtual addressはmodel実行中ずっと変えない。

一方、実際にHBMを消費するphysical blockは少数poolだけ用意し、必要layerへ動的にmap/unmapする。

例えばlogicalにはlayer 1〜48の全expert tensor addressが存在して見えるが、physical HBMがbackingしているのは現在/次layerだけ、という状態を作る。

実装はCUDA Virtual Memory Management（CUDA VMM）の

- `cuMemMap`
- `cuMemUnmap`

等を使う。

これによりkernelから見るpointerは普通のcontiguous tensorのままで、kernel内部へpage-table lookup処理を追加しなくてよい。

## PagedAttentionとの違い

vLLMのPagedAttentionもvirtualizationを使うが、KV pageはrequestごとに非連続であり、kernel実行中にlogical→physical block tableを参照する必要がある。

expert weightは事情が違う。

あるlayerを実行する前に必要expert tensorをcontiguous virtual rangeへmapしておけば、そのlayerのkernel実行中はmappingが固定される。

したがってaddress translationをkernel外、launch前に終えられる。

この性質が既存MoE kernelを変更せず使える理由である。

# 2種類のtensorを別streamで同時に供給する

1 expertのFFNは主に

- fused gate/up projection weight
- down projection weight

という異なるsizeの2 tensorを持つ。

PagedTensorは両者に独立virtual address spaceとphysical block poolを作る。

2-layer residency window用に、各tensor typeについて `2L` blocks、合計 `4L` physical blocksを持つ。

2つのloading streamを使ってgate/upとdown tensorをparallelにtransfer/decompressし、storage backend bandwidthを使い切る。

# WAR / RAW synchronizationは何を守るのか

physical blockを再利用するには、古いexpertを使うkernelが完全に終わったことを保証しなければならない。

FluxMoEはCUDA eventで2つのdependencyを守る。

### 書き込み後読み出しではなく、Write-After-Read（WAR）

古いlayerがまだphysical blockを読んでいる間、そのblockを次expertのloadで上書きしてはいけない。

compute completion eventを待ってからblockを再mapする。

### Read-After-Write（RAW）

次layerのkernelはexpert load/decompressionが完全に終わる前に起動してはいけない。

load completion eventをcompute streamが待つ。

この2つにより、parameterを非同期で入れ替えてもkernelがpartial/overwritten weightを読むことを防ぐ。

# Expert storage hierarchy

PagedTensorは「どのaddressへloadするか」を解決するだけで、expert正本をどこに置くかは別問題である。

FluxMoE prototypeは主に2 backendを使う。

1. **圧縮GPU tier（compressed GPU backend）**
2. **CPU pinned DRAM tier**

## 圧縮GPU tier

expert weightを圧縮した状態でGPU memoryに保持する。

必要時にGPU上で高速decompressionしてPagedTensor bufferへmaterializeする。

prototypeではexpert exponent bitsへのselective Huffman codingを使う。

圧縮状態でもVRAMは消費するが、CPUからPCIeで送るより高い供給throughputを得られる。

## CPU DRAM tier

より多くのexpertをpinned host DRAMへ置き、asynchronous DMAでPCIe transferする。

GPU容量を大きく節約できるがload bandwidthは遅い。

# なぜbackendへbandwidth比例でexpertを置くのか

compressed GPUとCPU DRAMを同時に使う場合、片方に多く割り当てすぎると遅いbackendがcritical pathになる。

backend `k` の実効loading bandwidthを `B_k`、そこへ置くparameter fractionを `x_k` とすると、1 layerのloading timeは概ね

`x_k × P_layer / B_k`

になる。

parallelにloadするなら、全backendがほぼ同時に終わる配分が最も速い。

そのため

`x_k = B_k / ΣB`

のように**bandwidth比例**でparameterを分配する。

例えばcompressed GPU backendがCPU DRAMの2倍速ければ、概ね2倍のparameter volumeをGPU圧縮tierへ担当させる。

これは「hot expertをGPUへ、cold expertをCPUへ」というfrequency cacheとは発想が違う。

FluxMoEのstorage partitionは主に**供給bandwidthを合成してlayer全体をdeadlineまでにloadする**ためのものだ。

# Budget-Aware Residency Planner

完全streamingでexpert memoryを最小にするとKVには有利だが、PCIe/decompressionが遅くてcomputeを待たせる可能性がある。

逆にexpertを大量residentにするとstreaming costは減るがKV容量が減る。

FluxMoEはruntimeでこの境界を自動調整する。

## ρ = compute時間 / load時間

plannerは

`ρ = τ_comp(theory) / τ_load`

を見る。

### `ρ > 1`

computeの方がloadより長い。

つまりexpert loadingはcomputeの裏へ完全に隠せている。

まだexpert residencyを減らしても性能を落とさず、VRAMをKVへ返せる余地がある。

→ residency fraction `α` を下げる。

### `ρ < 0.9`

expert loadの方が遅く、forwardがI/O待ちになっている。

→ `α` を上げて、より多くのexpertをGPU側へresidentにする。

### `0.9 <= ρ <= 1`

何もしない。

このdead zoneはPCIe bandwidthの短期揺らぎでresidencyが上下し続けるoscillationを防ぐ。

目標は**load時間とcompute時間がほぼ同じになるknee**である。

そこならexpert storageを最大限削りながらI/O latencyをほぼ隠せる。

# KV cacheをhard priorityにする

plannerには性能比だけでなくmemory safety constraintがある。

GPU総budgetを `C_gpu`、現在KV使用量を `C_kv` とすると、expertへ使える上限は

`C_res = C_gpu - C_kv`

である。

expert residency memory `C_exp(α)` は常に

`C_exp(α) <= C_gpu - C_kv`

を満たす。

つまりKV cacheが増えたら、たとえexpert streamingが遅くなってもexpert residencyを削る。

これはFluxMoEの価値判断を明確にしている。

**KV swappingでbatch/concurrencyを失うより、weight streamingを増やしてでもKVをGPUに残す**。

# Prefillよりdecodeを主対象にする理由

prefillは大量tokenをまとめて処理するためcompute-heavyで、layer compute時間がexpert load時間より長くなりやすい。

論文ではprefillで `ρ >> 1` となり、parameter materializationが自然にcomputeへ隠れると説明する。

一方decodeは1 tokenずつでmemory-boundになり、KV cacheも時間とともに増える。

そのため

- expert I/Oを隠せるか
- KV capacityを確保できるか

のtrade-offが厳しい。

FluxMoEのresidency plannerは主にdecode phaseを最適化する。

TTFT中心のprefill systemではなく、**steady token generation throughput**を狙う設計である。

# 実装

vLLM v0.10.2上へmiddlewareとして実装する。

規模は約

- C++: 3.1K LoC
- Python: 2.1K LoC
- vLLM本体へのinterface変更: 約20 LoC

である。

logical tensor abstractionをkernel外へ置いたため、vLLM/Triton/PyTorch側への侵襲を比較的小さくしている。

prototypeでは理論上の3-state

- uncompressed GPU-resident
- compressed GPU-resident
- CPU-resident

のうち、常時uncompressed resident fraction `x=0` とし、compressed GPU + CPUの2 backendへ重点を置く。

# 評価条件

主testbed:

- GPU: 4× NVIDIA L40 48GB PCIe
- CPU: Intel Xeon Platinum 8358、計128 vCPU
- Host DRAM: 2 TiB
- Disk: 3 TB
- Tensor Parallelism: TP=4

Model:

- Mixtral-8×7B-Instruct: 47B parameters、32 layers
- Qwen3-Next-80B-A3B-Instruct: 80B total、3B active級、48 layers

batch sizeは32〜256、contextは最大4096 tokenなどmemory pressureが強い領域を含む。

# 主要結果

## 1. Qwen3-Nextで最大3.0× throughput

Qwen3-Next-80B-A3B-Instruct、batch 256、context 4096のmemory-intensive条件で、通常vLLMに対して**最大3.0× throughput**を達成する。

単純weight-offload comparisonに対しては最大約3.7×。

この条件では通常vLLMがexpert weight常駐のためKV budgetを十分確保できず、KV swappingでthroughputを落とす。

FluxMoEはexpertをstreaming対象にしてKVをresidentに保つため、parameter I/Oが増えてもsystem全体では速くなる。

## 2. KV budgetの価値を直接確認

Mixtral profilingでKV budget 20GiB→60GiBに増やすだけでbatch128 throughputが58.8%上がる。

FluxMoEの3× headlineは「expert loading kernelが3倍速い」という結果ではない。

**expert memoryを削ったことでより多くのKVをGPUへ残し、swapとbatch制約を除去したsystem-level speedup**である。

## 3. Mixtralでは通常vLLMがOOMするcapacity領域も実行

よりmemory-constrainedなMixtral configurationでは通常vLLMがmodel initializationでOOMする条件がある。

FluxMoEは全expertをuncompressed GPU residentにしないため、同じGPU memoryでmodelを起動できる。

これはthroughput improvementだけでなく**feasibility extension**でもある。

## 4. RuntimeでresidencyがKV pressureへ追従

batch/contextが増えてKV使用量が増えるとplannerはexpert residency `α` を下げる。

逆にload timeがcomputeを超えてI/O bottleneckになれば `α` を戻す。

実験ではこのfeedbackにより、static residency configurationよりload/compute overlapを保ちながらmemory pressureへ適応する。

## 5. PagedTensor overheadは最大約3.0%

virtual mapping、CUDA event、materialization管理を追加しても、PagedTensor abstraction単体の管理overheadは最大約3.0%と報告する。

これは既存kernelへaddress-translation logicを埋め込まず、mappingをlaunch前に完了する設計の利点である。

# MoE-Infinity / ProMoEとの違い

多くのexpert offload研究は

`次に使うexpertを予測し、hot expertをcacheしてmissを減らす`

ことに重点を置く。

FluxMoEは異なる問いを立てる。

**そもそも全expert weightを永続GPU stateとして扱う必要があるのか？**

layer execution順序は固定なので、「次にどのlayerのexpert setが必要か」はrouter predictionなしでも分かる。

FluxMoE prototypeではlayer単位で全expert tensorをmaterializeし、physical residencyだけをvirtualizeする。

したがってrouter hit prediction精度へ依存せず、kernel互換性とmemory budget controlを中心に据える。

## Expert cacheとの関係

frequency/recency cacheは「どのexpertを残すか」を決める。

FluxMoEのresidency plannerはより粗いlevelで

`expert全体へ何GBまでGPU budgetを与えるか`

をKV pressureとload bandwidthから決める。

将来的には両者を組み合わせ、与えられたresident budget内でhot expertを選ぶ設計も可能である。

# なぜNVMeを直接使わないのか

この論文のstorage hierarchyは主に

- compressed GPU memory
- CPU pinned DRAM

であり、NVMe expert streamingをmain pathにしていない。

理由はdecode layer間の短いcompute window内へexpert parameter loadを隠す必要があり、ordinary NVMe bandwidth/latencyではlayer単位の巨大weightを毎step供給するのが厳しいからである。

SSD/NVMeを追加tierにするなら

- DRAM hot backing store
- ahead-of-time layer prefetch
- expert-level prediction/cache
- compression

等でNVMe readをより早い時点から始める必要がある。

# 限界

1. **CPU DRAMとPCIe bandwidthが必要**: 2TiB host memoryとL40 PCIe serverで評価しており、host資源が小さいnodeでは成立領域が狭い。
2. **主modelは2種類**: Qwen3-NextとMixtral中心で、expert architectureが大きく異なるmodelへの一般性は追加検証が必要。
3. **NVMe直接streaming未評価**: expert poolがCPU DRAMにも収まらないtrillion-scaleでは別の下位tier設計が必要。
4. **Layer単位で全expert materialize**: routerが実際に選ぶexpertだけを細粒度transferする方式ではなく、layer weight setのstreaming bandwidthが大きい。
5. **Prototypeはtri-state全体を実装していない**: 理論上のuncompressed/ compressed/CPU三段のうち現prototypeは `x=0` のspecific design。
6. **Planner profile依存**: theoretical compute timeとbackend bandwidth estimateがhardware/workload変化でずれる可能性がある。
7. **PCIe burstへのdead zoneはheuristic**: `θ=0.9` はempiricalで、別systemでは再調整が必要。
8. **TTFTではなくdecode throughput重視**: prefill-heavy interactive workloadのfirst-token latency最適化は中心ではない。
9. **公式code未確認**: 2026-09-10時点で論文に対応する公開repositoryを一次資料から確認できていない。

# 一般的な実装上の示唆

FluxMoEから得られる重要な考え方は、GPU memory budgetを

`weightsをまず置き、残りをKVへ渡す`

というstatic priorityにしないことだ。

serving throughputへ直接効くruntime stateがKVなら、

`KV必要量を先に確保し、weight residencyを残りbudgetへ適応させる`

という逆priorityが合理的な場合がある。

また、virtual addressを安定させphysical backingだけ差し替えるPagedTensorは、expert以外のlarge immutable parameterにも応用可能である。

- multi-model weight paging
- adapter/LoRA paging
- layer-wise compressed weight tiering

などで、既存kernelにaddress translationを追加せずmemory virtualizationを導入する設計パターンになる。

SSD研究の観点では、FluxMoEのplannerが使う

`compute window >= lower-tier load time`

という条件が重要である。

SSDをtierへ追加する場合も、ただ容量を増やすのではなく、どのfuture layer/expertを**何layer前から読み始めればcomputeへ完全に隠せるか**をresidency controlと共同設計する必要がある。
