# BOOST: Concurrent Access to Host Memory and HBM to Accelerate LLM Inference

> HBMとホストメモリを階層的に入れ替えるのでなく同時アクセスし、GPU実行波ごとに帯域比で重み・KVキャッシュを分散して、Grace Hopper上のLLM推論スループットを高める。
## 書誌情報
- **著者**: Anish Saxena, Jae Hyung Ju, Hritvik Taneja, Po-An Tsai, Aamer Jaleel, Christos Kozyrakis, Moinuddin Qureshi
- **公開**: arXiv preprint
- **種別**: preprint
- **対象**: LLM inference、heterogeneous メモリ、HBM、ホスト メモリ、vLLM、KV キャッシュ
- **実装**: 論文ではvLLM 0.17.0へ約800行のPython/PyTorch変更として実装したと報告している。公開コードURLは一次資料および公開検索で確認できなかった。
## 概要
大規模言語モデルの復号は高帯域メモリの容量だけでなく帯域にも制約される一方、CPU側のホストメモリ帯域は従来の階層型オフロードでは十分に利用されない。本研究は、GPUの各実行波で高帯域メモリとホストメモリへ同時かつ帯域比に比例して要求を振り分けることが重要だと示し、静的な重みには波を意識した剰余ページ配置、動的なKVキャッシュには実行時のデータ形状再配置を用いるBOOSTを提案する。vLLMへ約800行の変更で統合し、カーネルを書き換えずに容量増加と帯域加算を同時に得る。Grace Hopper実機では同一バッチ時の出力トークン時間を平均4.3%改善し、高スループット条件では平均31%の処理量向上を示した。

BOOSTの新規性は、二つのメモリ階層を上位・下位として移送するのではなく、GPUから直接読む対等な帯域源として扱い、各実行波で同時かつ帯域比に比例するアクセスを作る点にある。さらに、この条件をカーネル変更なしで満たすため、静的重みでは協調スレッド配列のアクセス形状を使った決定論的な剰余ページ配置、動的KVキャッシュでは仮想アドレスとブロック種別を実行時に選ぶデータ形状再配置を組み合わせる。従来のランダム比例配置が全期間平均の比例性だけを保証したのに対し、BOOSTは実行波というGPU実行単位の同時性まで管理対象にする。
## 問題設定
大規模言語モデルの復号では、各トークン生成のたびにモデル重みとKVキャッシュを大量に読み直すため、演算能力よりメモリ帯域が律速になりやすい。GPUには高帯域メモリに加えてCPU側ホストメモリへ到達するコヒーレントな経路があり、GH200では後者も高帯域メモリのおよそ10%の読み出し帯域を持つ。しかし従来の推論基盤はホスト側を容量拡張用の下位階層として扱い、使用直前に高帯域メモリへ先読みする。先読みはホストから読んだ各バイトを高帯域メモリへ書くため、その書き込みが需要読み出し帯域を奪う。既存の帯域比例ページ配置も、現代GPUの2MBページでは一つの実行波が触るページ数が少なく、波ごとのホスト比率が大きく揺れる。遅いホスト側へ比例値以上の要求が集中した波では高帯域メモリ側が遊び、平均比率が正しくても性能が落ちる。したがって容量拡張だけでなく、短い時間尺度の各実行波で両階層を同時利用する仕組みが必要になる。
## 新規性
BOOSTの新規性は、二つのメモリ階層を上位・下位として移送するのではなく、GPUから直接読む対等な帯域源として扱い、各実行波で同時かつ帯域比に比例するアクセスを作る点にある。さらに、この条件をカーネル変更なしで満たすため、静的重みでは協調スレッド配列のアクセス形状を使った決定論的な剰余ページ配置、動的KVキャッシュでは仮想アドレスとブロック種別を実行時に選ぶデータ形状再配置を組み合わせる。従来のランダム比例配置が全期間平均の比例性だけを保証したのに対し、BOOSTは実行波というGPU実行単位の同時性まで管理対象にする。
## 手法
### 手法のあらまし
入力は、vLLMが読み込むモデル重み、実行時に増減するKVキャッシュ、各カーネルが協調スレッド配列ごとにどの連続領域を読むかというアクセス形状、そしてホスト対高帯域メモリの実測帯域比である。まずページ割当管理器が静的重みテンソルごとに配置周期をリセットし、帯域比が1対KならK個の高帯域メモリ領域の後に1個のホスト領域を置く。協調スレッド配列の読み出し範囲が2MBページ境界と一致しない場合は、その範囲とページサイズの最小公倍数を一つの大ページ群として扱い、一つの協調スレッド配列が遅速両階層へまたがらないようにする。これにより、ホストへ向かう協調スレッド配列と高帯域メモリへ向かう協調スレッド配列を同じ実行波に混在させ、両経路を並行に飽和させる。動的KVキャッシュでは、割当時の静的縞配置だけではブロックの解放・再利用で対応が乱れるため、仮想アドレス範囲を高帯域メモリ領域とホスト領域へ線形分割し、データ形状再配置器がKVヘッドを外側次元へ並べ替える。実行時には一部のKVヘッドだけがホスト側にあるブロックと全ヘッドが高帯域メモリ側にあるブロックの二種類を用意し、空きリストの比率を見ながら要求へ割り当てる。出力は、カーネルから見れば従来と同じ仮想テンソルであり、カーネル内部のポインタ計算や演算を変えずに、物理的な需要読み出しだけが二階層へ分散される。実行中のデータ移送を行わないため、高帯域メモリ書き込み帯域を消費せず、追加容量と追加読み出し帯域を同時に利用できる。

### ページ割当管理器（Page Allocation Manager; PAM）
静的なモデル重みに対して、カーネル単位・テンソル単位で帯域比を満たす剰余ページ配置を行う。GH200ではOSからGPUメモリをNUMAノードとして扱えるため、2MB領域ごとにmmapとmbindで物理ノードを選び、cudaHostRegisterでGPUから参照可能にする。協調スレッド配列の重み範囲がページ境界とずれる場合は、その範囲と2MBの最小公倍数を大ページ群としてまとめ、一つの協調スレッド配列の需要読み出しが両階層に分割されないようにする。帯域比の逆数が整数でない場合は切り上げてホスト比率を目標以下に保ち、遅い階層の過剰割当による失速を避ける。

### データ形状再配置器（Data Shape Remapper; DSR）
動的に割当・解放されるKVキャッシュについて、静的ページ配置だけでは失われる実行波ごとの帯域比を維持する。KVテンソルをヘッドが連続になる配置へ並べ替え、単一ヘッドだけをホスト側へ置くブロックと全ヘッドを高帯域メモリ側へ置くブロックを作る。要求到着時には二種類の空きブロック比率を監視し、ホスト側KVヘッド片が目標帯域比付近になるよう貪欲に割り当てる。要求長の違いやブロック解放で片方の空きリストが不足した場合も、ホスト比率を目標以下へ落とすか特定要求だけへ混合を局所化し、遅い階層の過剰利用を避ける。

### 全体のデータ／制御の流れ
BOOSTはvLLMのモデル読込器とKVブロック管理器に実装され、GPUカーネルへ新しいコードを追加しない。静的重みは起動時に物理配置を固定し、動的KVは既存の仮想メモリ間接参照を利用してブロック種別を選ぶ。GPUは各データを64バイト単位の通常のコヒーレント需要読み出しとして参照するため、先読み用の高帯域メモリ書き込みや実行時ページ移送が不要になる。設計上の成立条件は、GPUがホスト階層へロード・ストアできること、カーネルが仮想テンソルを介してデータへ到達すること、そして協調スレッド配列ごとのアクセス流が十分規則的であること。
## 評価条件
- **ハードウェア**: 主評価はNVIDIA GH200 Grace Hopper 1基で、96GB HBM、480GB CPUメモリ、実測高帯域メモリ帯域3330GiB/s、CPU-GPU間帯域350GiB/s、帯域比約10%。帯域比の感度評価では80GB H100を2基NVLink接続し、一方を計算、他方を二次メモリとして用いて約12%の比率を模擬した。
- **ソフトウェア**: vLLM 0.17.0へ約800行のPython/PyTorch変更を追加。高帯域メモリとCPUメモリの配置にはLinuxのmmap・mbind、GPU可視化にはcudaHostRegisterを利用する。FlashAttention-3や閉源のcuBLASを含む既存カーネルを変更せず評価している。
主対象はQwen3-Next-80BのMoEモデルとLlama-3.3-70Bの密モデルで、主にFP8を使用する。入力/出力長は密モデルで256/2K、512/4K、1K/8K、MoEで64/512、128/1K、256/2K。プリフィルと復号を分離する構成を前提とし、低遅延評価では最大実行可能バッチを固定して出力トークン時間を測り、高スループット評価では利用可能容量までバッチを自動拡大して毎秒トークン数を測る。比較対象は高帯域メモリのみ、vLLMの非同期先読み、ランダム帯域比例配置、Linux重み付き交互配置、比例連続配置、CUDA統合メモリ。さらに長文脈、バッチサイズ、末尾遅延、帯域比、テンソル並列2で感度を調べる。
実機での主張は主としてGH200単一GPUの復号処理に基づく。二次階層へコヒーレントなロード・ストアが可能な高帯域接続を前提とし、PCIeやCXLのように帯域比が約2%の構成では利得は小さいと論文自身が述べる。将来の帯域比最大40%の予測は解析モデルによる投影であり実機測定ではない。大バッチ密モデルや小バッチMoEでは利得が消える、または負になる境界も評価している。
## 主要結果
同一バッチで容量差を排除した低遅延条件でも、BOOSTはホスト帯域を需要読み出しとして加算することで出力トークン時間を平均4.3%改善した。一方、先読みは高帯域メモリへの書き込み競合により平均6%悪化した。容量も使える高スループット条件では平均31%、最大40%の処理量向上となり、容量を同一にそろえた分解実験では約4%が同時帯域利用そのものの寄与と確認された。したがって主な処理量利得は容量増加だが、容量だけでは得られない追加の帯域利得も実測されている。

- 出力トークン時間 / 平均4.3%改善 (比較対象: HBMのみ; 条件: GH200、Qwen3-Next-80BとLlama-3.3-70B、同一バッチの低遅延復号) — 容量差を固定しても改善するため、ホスト帯域の同時需要読み出しによる純粋な帯域効果を示す。

- 最大処理量 / 平均31%向上、最大40% (比較対象: HBMのみ; 条件: GH200、高スループットで利用可能容量までバッチを拡大) — ホスト容量で同時要求数を増やす効果が主成分で、同時帯域利用が追加利得を与える。

- 先読みとの差 / 処理量で平均15%上回る (比較対象: vLLM非同期先読み; 条件: 主評価の高スループット条件) — 先読みはホストからHBMへの移送書き込みが需要読み出し帯域を消費するため、移送しないBOOSTが有利になる。

- 容量を一致させた帯域寄与 / 処理量と出力トークン時間を約4%改善 (比較対象: 同じ総容量をHBMだけで与えた容量一致条件; 条件: Llama-3.3-70B、1K/8K文脈) — 31%という総合利得のうち、容量拡張とは独立した同時帯域利用の寄与を分離している。

- P99トークン間遅延 / ランダム比例配置より幾何平均7.8%低下 (比較対象: BAPP-R; 条件: Llama-3.3-70B、LongWriter、処理可能な要求率範囲) — 平均性能だけでなく末尾遅延でも、実行波ごとの比率分散を抑える効果が現れる。

- テンソル並列2の出力トークン時間 / 平均6.5%改善 (比較対象: HBMのみ; 条件: H100二次メモリ模擬、Qwen2.5-72BとLlama-3.3-70B、BF16、TP=2) — 単一GPUのGH200だけでなく、複数GPUにまたがる大規模モデルでも帯域加算の効果を確認している。

### 負の結果・境界条件
- 境界条件は明確である。Qwen3-Nextはバッチ16で約2%遅くなり、少数の専門家しか活性化せず協調スレッド配列数が足りないとホスト遅延を隠せない。密モデルLlama-3.3はバッチ256で約0.5%遅くなり、同じ重みタイルを複数の協調スレッド配列が再利用する領域ではGH200のホスト読み出しがL2キャッシュされないことが不利になる。PCIeやCXL相当の帯域比約2%では期待利得が小さい。CUDA統合メモリは作業集合がHBMを超えるとページ移送がスラッシングし、処理量0.19倍まで低下した。

### 結果の読み方
性能は二次階層の帯域比、同時に走る協調スレッド配列数、重みタイル再利用の有無で決まる。ホスト比率を帯域比例値より上げると遅い階層が律速し、逆に下げると追加帯域を使い切れないため、各実行波で比率を安定させることが重要である。MoEはバッチ増加で活性専門家と協調スレッド配列が増えるため利得が伸びるが、密モデルは大バッチでL2再利用が強まり、ホスト読み出しの非キャッシュ性が支配的になる。
## 品質への影響
BOOSTは量子化精度や近似注意を変更せず、同一の重みとKV値を異なる物理メモリから読む配置最適化である。論文は品質指標の変化を報告しておらず、設計上も生成結果を変える近似を導入しない。性能評価は主として遅延・処理量・帯域利用率に集中している。
## 既存研究との差
FlexGen、MoE-Lightning、PRESERVE、TightLLMなどのオフロード系はホストを下位容量として使い、使用前にHBMへ移送するためHBM書き込み帯域を消費する。BOOSTは移送せず、GPUの需要読み出しをHBMとホストへ直接分割する点が異なる。従来の帯域比例ページ配置BAPP-RやLinux重み付き交互配置は全体平均の比例性を狙うが、2MBページ下で実行波ごとの比率を保証しない。BOOSTはカーネルの協調スレッド配列アクセス形状を利用して実行波単位の同時性を作る。KVキャッシュ削減を行うInfiniGenやCPUで注意計算を行うNEOとは競合せず、転送される需要トラフィック自体を二階層で高速化するため直交的に組み合わせられる。
## 限界
第一に、GPUからホスト階層へキャッシュコヒーレントなロード・ストアができることが前提で、帯域比が小さいPCIe/CXL系では利得が限定的である。第二に、GH200ではホスト読み出しがGPUのL2へキャッシュされないため、密モデルの大バッチで重みタイル再利用が増えると性能が悪化し得る。第三に、小バッチMoEでは同時に動く協調スレッド配列が少なく、ホスト側の長い遅延を隠せない。第四に、主評価は単一GH200の復号であり、将来の高帯域比システムに対する最大約3倍の予測は解析モデルであって実機結果ではない。第五に、公開コードURLは確認できず、論文記載の約800行実装を第三者が直ちに再現できる状態かは不明である。

論文著者はvLLM 0.17.0へ約800行のPython/PyTorch変更としてPAMとDSRを実装し、GH200実機およびH100二台のNVLink構成で動作評価している。FlashAttention-3と閉源cuBLASを含む既存カーネルを変更せず動作する。一次資料には公開リポジトリURLが示されておらず、今回の確認でも公式実装URLは特定できなかったため、実装済みだが公開状況は未確認と記録する。
## 研究上の位置づけ
階層メモリ型LLM推論の系譜では、容量不足を補うための先読み・専門家キャッシュ・KVオフロードとは異なり、二次メモリを『退避先』ではなく『追加帯域源』へ変える研究である。特に重要なのは、平均的な帯域比例配置では不十分で、GPUの実行波という短時間の並列実行単位で同時性と比例性を満たす必要があるという観測である。これにより、容量拡張だけでは説明できない約4%の帯域利得を実機で分離している。将来NVLinkや高帯域CPU-GPU接続の比率が上がるほど価値が増す一方、通常PCIe接続GPUでは直接適用の効果が小さいため、現時点ではGrace Hopper系や高帯域分離メモリ系を主対象とする位置付けが妥当である。
