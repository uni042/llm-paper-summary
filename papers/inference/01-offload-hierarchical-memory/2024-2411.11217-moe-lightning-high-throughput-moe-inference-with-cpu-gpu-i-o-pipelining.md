# MoE-Lightning: High-Throughput MoE Inference with CPU-GPU-I/O Pipelining

> エキスパート重みとKVキャッシュをCPU DRAMへ置き、次の重み転送・CPU 注意機構・GPU MoE計算をマイクロバッチ間で同時進行させて、低VRAM GPUのI/O待ちを減らす推論システム。

## 概要
MoE-Lightningは、低VRAM GPUで多数リクエストをまとめて処理する **オフライン / バッチ-指向 提供** を主対象にする。エキスパート重みとKVキャッシュをCPU DRAMへ置き、GPUは主にMoE FFNを計算し、デコード 注意機構はKVがあるCPU側で処理する。

単にCPUへオフロードするだけではCPU–GPU 転送とCPU 注意機構が新しいボトルネックになる。そこで、**あるマイクロバッチをGPUで計算している間に、別マイクロバッチの重み転送やCPU 注意機構を進める**ことで待ち時間を隠す。論文ではこの実行方式を `CGOPipe` と呼ぶ。

さらにハードウェアの計算性能・メモリ帯域・PCIe帯域・容量を測り、注意機構 / MoEをCPUとGPUのどちらへ置くか、バッチ / マイクロバッチをどの大きさにするかを事前に探索する。論文ではこの性能予測モデルを `HRM（Hierarchical Roofline Model）` と呼ぶ。

SSD / NVMeは探索対象から明示的に除外され、**CPU DRAM ↔ GPU VRAM** の重み + KVオフロードが対象である。

## 手法のあらまし

MoE-Lightningの核は、重みとKVを同じオフロード対象としてまとめるのではなく、**転送方向・再利用周期・計算先が違うデータとして別々に扱い、依存しない処理を同時進行させる**ことにある。

### 1. `CGOPipe`：CPU・GPU・I/Oを4種類のflowとして重ねる

論文の **CGOPipe（CPU-GPU-I/Oパイプライン）** は、単純な層パイプラインではなく、1層 / 1 マイクロバッチ内で発生する複数のデータ 移動を別ストリームとして重ねる仕組みである。

主に次の4種類を並行化する。

| Flow | 転送方向 | 目的 |
|---|---|---|
| QKV / KV保存 | GPU → CPU | デコード 注意機構用のKVをCPUへ置く |
| Attention出力 | CPU → GPU | CPU 注意機構後の隠れをGPUへ戻す |
| Weight 先読み | CPU → GPU | 次に必要なMoE 重みを先読み |
| KV関連の次処理 | GPU ↔ CPU | 次micro-バッチのKV入出力を先行 |

重要なのは、これらを一つの大きな同期コピーとして扱わず、**依存関係がないものは別々に進める**ことである。

### 2. Expert weightを小さなchunkに分けて順番に転送する

巨大なエキスパート重みを層単位で一括コピーすると、そのコピーが終わるまで次のGPU計算を始められない。

そこでMoE-Lightningは重みを小さなチャンクに分け、マイクロバッチ計算の合間に順番に運ぶ。論文ではこのチャンクを **ページ化重み** と呼ぶ。

`weight chunk 1を転送 → micro-batch 1を計算 → chunk 2を転送...`

のように流すことで、重み 転送の一部を他の計算へ隠す。

ここでの`page`はOS ページそのものではなく、パイプラインで扱いやすい重み チャンクという意味である。

### 3. CPU attentionを選ぶ理由

KVキャッシュをCPUへ置いたままGPU 注意機構を実行しようとすると、デコード 手順ごとに大量のKVをGPUへ戻す必要がある。

MoE-Lightningは逆に、**KVがあるCPU側で注意機構を実行し、注意機構出力だけGPUへ返す**。

つまりFiddlerが「エキスパート重みを動かす代わりに活性値をCPUへ送る」のと似た考え方を、デコード 注意機構へ適用している。

CPU側にはIntel MKLを使ったGQA向け専用カーネルを実装し、GPUへKVを移す代わりにCPUメモリから直接KVを読んで注意機構を計算する。

### 4. `HRM`：compute・memory・PCIeのどこが遅いかを見て配置を決める

論文固有の **HRM（Hierarchical Roofline Model）** は、各処理について「演算性能が上限になるのか、メモリ / PCIe帯域が上限になるのか」を見積もり、GPU・CPU・CPU–GPU リンク・メモリ容量をまとめて考えるコスト モデルである。

探索変数には、

- 注意機構をCPU/GPUどちらで処理するか
- MoE FFNをCPU/GPUどちらで処理するか
- GPUへ静的に置く重み比率 `r_w`
- GPUへ置くKV比率 `r_c`
- バッチ 大きさ `N`
- マイクロバッチ 大きさ `μ`

が入る。

単純に「VRAMが空くまでオフロードする」のではなく、**CPU/GPUの計算速度、各メモリ帯域、PCIe帯域、容量を同時に見て実行構成を選ぶ**点が特徴である。

### 5. `Micro-batch`はI/Oを隠すための時間窓として使う

バッチを複数のマイクロバッチへ分けると、あるマイクロバッチをGPUで計算している間に、別マイクロバッチの重み / KVを転送できる。

ただしマイクロバッチを細かくし過ぎるとカーネル効率が落ち、粗すぎると転送を隠す機会が減る。

MoE-LightningではHRMがこのトレードオフを含めて`μ`を選ぶ。

可変長リクエストでは単純にリクエスト数を均等分割せず、**トークン数が近くなるようマイクロバッチを構成してパディングを抑える**。

### 6. 実行構成はrequestごとに再探索しない

HRMの探索はランタイム中の各リクエストごとに行うのではなく、モデル / ハードウェア / ワークロード条件に対して事前に構成を決め、その設定を実行時に固定する。

これにより実行中の探索コストを避ける一方、ワークロード分布やハードウェア条件が大きく変われば再探索が必要になる。

## 評価

### まず見るところ
- **結論:** CPU 注意機構とGPU MoEをマイクロバッチ間で重ねると、低VRAM GPUでもバッチスループットを大きく伸ばせる。
- **実速度:** 単一 T4/L4で最大10.3倍、複数比較対象に対して数倍のスループット改善を報告する。
- **品質:** 同じ注意機構 / エキスパート計算を実行するため無損失。
- **メモリ・I/O:** エキスパート重みとKVキャッシュをCPU DRAMへ置く。SSDは使わない。
- **注意点:** 遅延最小化よりバッチスループット向け。バッチ/文脈が大きくなるとCPU 注意機構が新しいボトルネックになる。

### 主なthroughput結果

| 条件 | 改善 |
|---|---:|
| Single T4 / L4、最大 | **10.3倍** |
| Padding込み、vs FlexGen | 最大3.5倍 |
| vs FlexGen(c) | 最大5倍 |
| vs DeepSpeed | 最大6.7倍 |

10.3倍は最良条件の最大値であり、すべてのワークロードで同じ倍率ではない。

### MTBenchの代表例

| 方式 | Throughput |
|---|---:|
| MoE-Lightning(p) | **30.12 tokens/s** |
| FlexGen、同一配置・バッチ設定 | 16.816 tokens/s |
| FlexGen、元設定 | 9.5 tokens/s |

MoE-Lightning(p)では `μ=36, N=504`。同じ配置・バッチ設定をFlexGenへ与えても差が残るため、**構成探索だけでなくCGOPipeの同時実行そのものにも効果がある**。

### HELM / Summarizationの代表例

| 方式 | Throughput |
|---|---:|
| MoE-Lightning | **12.393 tokens/s** |
| FlexGen | 7.14 |
| FlexGen(c) | 4.307 |
| DeepSpeed | 1.447 |

長いプロンプトではI/O / 注意機構の占有が増えるため、CPU 注意機構とマイクロバッチパイプラインの設計差が出やすい。

### Multi-GPU scaling

Mixtral-8x22Bで4×T4と2×T4を比較。

| 比較 | Throughput改善 |
|---|---:|
| 4×T4 vs 2×T4 | 2.77〜3.38倍 |

GPU数は2倍だがスループットは2倍以上伸びる領域がある。GPU追加によって重み / KVを保持できる量が増え、転送を計算へ重ねやすくなるためである。

### CPU attentionの限界

論文のcustom CPU 注意機構カーネルはKVをGPUへ転送する方式より3〜4倍速い条件を示すが、バッチや文脈が大きくなるとCPU側のメモリ帯域 / 計算が律速になる。

つまりKVをCPUへ置くこと自体が常に速いのではなく、**CPU 注意機構を他のGPU計算と同時進行できる範囲で有効**である。

### 評価上の制約

- オフライン / バッチ-指向スループットが主目的。
- interactiveなバッチ=1遅延最小化とは評価軸が異なる。
- CPU DRAMへ全モデル / KVを置ける容量が必要。
- Diskオフロードは未実装・探索対象外。
- multi-node通信はHRMの中心対象ではない。
- KV疎性などの追加最適化は扱わない。
- 実行構成はハードウェア / ワークロードごとに再探索が必要。
