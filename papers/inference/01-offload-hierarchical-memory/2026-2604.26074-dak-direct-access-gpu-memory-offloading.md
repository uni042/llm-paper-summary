# DAK: Direct-Access-Enabled GPU Memory Offloading with Optimal Efficiency for LLM Inference

> 従来のLLMメモリオフロードはCPU側の重みやKVキャッシュを一度GPU HBMへ先読みしてから計算するため、転送書き込みと計算中のHBM読み出しが競合し、先読み用バッファもHBM容量を消費する。DAKはHopper以降のテンソルメモリアクセラレータ（Tensor メモリ Accelerator; TMA）を転用し、CPUメモリ上の重みやKVキャッシュをGPU共有メモリへ直接非同期転送して、その場で行列積や注意機構を実行する。演算ごとの最適オフロード率、転送輻輳制御、TMAマルチキャストを組み合わせ、GH200では既存オフロード方式に対して最大3倍、PCIe接続RTX 6000 Pro Blackwellでも最大1.8倍の性能向上を報告する。

- **実装**: 約1300行のPythonと2700行のCUDA C++で実装し、CUTLASSを用いる。PyTorch向けのSplitK_GEMMとSplitK_FlashAttnを差し替え可能なモジュールとして提供し、公式実装を公開している。
## 問題設定
GPUメモリを超えるLLMを動かすため、FlexGenやvLLM系のオフロードはCPUメモリに置いた重みやKVキャッシュを計算前にHBMへ先読みする。しかしこの経路は『CPUメモリ→HBMへの書き込み→共有メモリへの読み出し』と二段になる。先読み中のHBM書き込みは同時に走るカーネルのHBM読み出しと競合し、GH200では背景コピーだけでローカルメモリ性能が最大約10%低下する。さらに通信を隠すには複数層分の先読みバッファをHBMへ確保する必要があり、容量拡張のために外部メモリを使っているのに貴重なHBMを中継領域へ使う。層単位先読みは転送と計算の時間が一致しにくく、通信側または計算側の空白も残る。このため遠隔メモリの帯域と容量を追加しても、HBMを中継する方式ではローカル帯域との合算性能へ到達しにくい。
## 新規性
DAKは、もともとHBMと共有メモリの非同期転送用に設計されたTMAがCPUホストメモリからGPU共有メモリへの直接転送にも使えることを利用する。遠隔データをHBMへ置かず、演算カーネル内部でローカルHBMとホストメモリを異なるストリーミングマルチプロセッサから同時に読み、合算帯域を使う。さらに全演算へ同じ割合を退避するのではなく、メモリ律速か計算律速かに応じて演算ごとの退避率を理論的に配分し、TMA要求数の制限とマルチキャストで遠隔アクセス特有の輻輳と読み出し増幅を抑える。
## 手法
### 手法のあらまし
DAKはまずモデル重みとKVキャッシュの総量、利用可能なGPUメモリから、システム全体で外部メモリへ置く必要がある割合を決める。その割合を各線形演算や注意機構へ一様に割り当てず、演算ごとの算術強度とローカル・遠隔帯域から最適な比率へ配分する。メモリ律速演算では、ローカルHBMとホスト側の転送時間が釣り合う点まで遠隔側を増やすと両方の帯域を同時に使える。計算律速演算では、遠隔転送が計算時間内に隠れる範囲ならオフロードを増やしても実行時間は増えない。貪欲法はこの折れ点を利用し、低い総オフロード率ではメモリ律速演算をその最適点へ近づけ、その後は計算に隠せる演算へ容量負担を移し、さらに高い比率では遠隔帯域が全体律速になる領域へ進む。論文付録でこの割当の最適性を証明する。

実際の行列演算では、重みまたはKV行列をタイル単位でGPUメモリとホストメモリへ分割する。異なるGPU計算器がローカル側タイルと遠隔側タイルを担当し、各計算器内部では生成側ワープがTMAで次のタイルを共有メモリへ非同期転送し、消費側ワープが現在のタイルをテンソルコアで計算する。遠隔タイルもHBMへは保存せずホストメモリから共有メモリへ直行するため、HBMの中継書き込みを消し、ローカルHBM読み出しとホストGPUリンクを並列に使える。線形層にはSplitK_GEMM、注意機構にはSplitK_FlashAttnを実装し、KVキャッシュは要求の一部をGPU側、一部をホスト側へ置く。

TMAを無制限に遠隔へ投げるとGPU内部相互接続が詰まり、逆にローカルHBMアクセスまで遅くなる。そこで飛行中TMA要求の上限を調整し、ホスト側へ向ける計算器数を制限する能動的な輻輳制御を行う。またCPUメモリはGPU L2にキャッシュされないため、複数の計算器が同じ重みタイルを読むとホストGPU間リンクで同じデータを何度も運ぶ。DAKは計算器群をクラスタ化し、一つの生成ワープがホストから一度だけ読み出したタイルをTMAマルチキャストで複数計算器の共有メモリへ配る。ホスト側データを先に処理するタイル順序も組み合わせ、遠隔読み出し増幅を抑える。

実装はPyTorchから既存線形層と注意層を置換でき、CUDA Graphにも対応する。GPU世代ごとにCUTE計算部品を差し替え、TMAチャンク量や飛行中要求数を調整できるため、NVLink-C2Cだけでなく帯域の低いPCIeでも同じ設計を使う。遠隔帯域が低い場合は最適オフロード率も自動的に小さくなり、容量のために高比率を強制されると遠隔リンクが支配的になって利得が収束する。

### 共有メモリへ直行するTMA遠隔アクセス
ホストメモリの重みやKVキャッシュを一度HBMへコピーせず、TMAを使って演算カーネル内の共有メモリへ直接運ぶ。生成ワープが次のタイルを非同期に取り込み、消費ワープが現在タイルを計算する二重化で遠隔遅延を隠す。ローカル担当の計算器はHBM、遠隔担当はホストメモリを同時に読むため、HBMへの先読み書き込みがローカル読み出しを妨げず、理想的にはHBM帯域とホストGPU間帯域を合算できる。また先読み用の大きなHBMバッファが不要なので、その容量をモデル重みやKVキャッシュへ戻せる。従来方式では遠隔データを計算直前までにHBMへ戻せなければカーネルが停止するが、DAKではタイル単位の生成・消費パイプラインの中へ遠隔取得を組み込むため、粗粒度な層単位先読みの空白も減らせる。

### 演算ごとの最適オフロード率
線形層と注意機構は、バッチや系列長によってメモリ律速と計算律速の度合いが異なる。DAKは各演算の有効帯域曲線の折れ点を計算し、総オフロード量をどの演算へ割り当てるかを貪欲に決める。メモリ律速演算はローカル帯域と遠隔帯域が釣り合う点までは外部化するとむしろ速くなり、計算律速演算は計算時間に隠せる範囲なら外部化しても遅くならない。この性質を順に使うことで、一様配分が一部演算を早く遠隔律速へしてしまう問題を避ける。論文はこの多段配分が定式化した目的関数に対して最適であることを証明している。容量要件で総オフロード率が決まった後も、どの演算にその負担を持たせるかを性能モデルから決めるため、単なる直接アクセスカーネルよりシステム全体の最適化になっている。

### 遠隔TMAの輻輳制御
TMAは非同期でも、飛行中のホスト向け要求を増やしすぎるとGPU内部相互接続が飽和し、ホストアクセスだけでなくHBM側の処理まで遅くなる。DAKはホストタイルを担当する計算器数と同時TMA要求数に上限を設け、行列形状や接続帯域に応じて調整する。重要なのは、遠隔帯域を使い切るため要求を無制限に並列化するのではなく、ローカルHBM経路との共存を維持できる点へ要求密度を抑えることである。さらにタイル数が計算器数で割り切れないと最後の実行波だけ利用率が落ちるため、担当タイル数が均等になるよう配置を整列する。これにより一部の計算器だけが残りタイルを抱えて全体終了を遅らせる状況を避ける。評価では輻輳制御だけで行列積性能を最大1.22倍、実行波整列で最大1.2倍改善しており、直接アクセスの理論帯域を実機上で取り出すために必要な補助機構である。

### TMAマルチキャストによる読み出し増幅除去
CPUホストメモリはGH200のような整合メモリ環境でもGPUのL2を通じて通常キャッシュされない。そのため複数の計算器が同じ重みタイルを別々に読むと、ホストGPU間リンクで同じデータが繰り返し転送される。DAKは複数計算器をクラスタとして扱い、一つの生成ワープだけがホストからタイルを読み、そのタイルをTMAマルチキャストで各計算器の共有メモリへ配布する。バッチが大きいほど同一重みの再利用回数が増えるため効果も大きく、代表行列積でバッチ相当次元512では1.3倍、1024では2.5倍の改善を報告する。つまり外部メモリを直接読むだけでなく、遠隔リンク上で同一データを何回運ぶかまで削減し、遠隔帯域の実効利用率を高めている。

### 全体のデータ／制御の流れ
モデル初期化時に必要総容量から全体オフロード率を求め、各演算の最適率へ分解して重みとKVキャッシュをGPU・ホストへタイル配置する。推論時は差し替えたSplitK_GEMMとSplitK_FlashAttnがローカルHBMとホストメモリを直接読み、TMAで共有メモリへ供給する。輻輳制御器が遠隔要求数を制限し、同一ホストタイルはマルチキャストで複数計算器へ配る。CUDA Graphでデコード起動費も抑え、モデル本体の計算グラフを大きく書き換えずに階層メモリを利用する。
## 評価条件
- **ハードウェア**: GH200: 96GB HBM3、4.0TB/s、480GBホストメモリ、NVLink-C2C接続。、RTX 6000 Pro Blackwell: 96GB GDDR7、1.8TB/s、512GBホストメモリ、PCIe Gen5単方向64GB/s。
- **ソフトウェア**: PyTorchインターフェース、CUDA C++、CUTLASS、CUDA Graph。
- **モデル**: OPT-30B、OPT-6.7B、Llama-2-7B
- **データセット／トレース**: オフラインのバッチ推論。通常は入力長32、各要求32トークン生成。大KV評価ではバッチ・入力長を増やす。
- **比較対象**: FlexGen、vLLM-プリフェッチ、vLLM-uvm
- **正確性・品質**: 重みやKVを変更せず格納場所とデータ経路を変えるため、モデル品質を近似する方式ではない。評価は時間/出力トークンと有効帯域を中心とし、品質差ではなく同じ演算結果を前提とする。
- **重み主体**: バッチ8で0〜100%のオフロード率を掃引し、OPT-30B/6.7Bを中心に有効帯域とトークン当たり時間を比較する。
- **KV併用**: バッチ512などでKVキャッシュが大きい条件を作り、線形層と注意機構が異なる律速になる状況で演算別配分を評価する。
- **容量超過**: OPT-30Bでバッチと入力長を変え、総メモリがGPU容量を超えるために必要となる実際の全体オフロード率で最高性能を比較する。
2種類の相互接続でオフロード率を掃引し、理論上のローカル＋遠隔合算帯域へどこまで近づくかを測る。重み主体、小/大KV、容量超過条件を分け、FlexGen・vLLM先読み・統合仮想メモリと比較する。さらに貪欲配分対一様配分、輻輳制御、TMAマルチキャスト、タイル整列を個別に切り分ける。
単一GPUと接続CPUメモリの階層を対象とするオフライン推論評価で、多利用者オンラインサービングの待ち行列や複数GPU間干渉は扱わない。Hopper/BlackwellのTMAを前提とするため古いGPUへは直接適用できない。
## 主要結果
DAKはHBMを中継する先読み方式より、ローカルメモリと遠隔メモリの帯域を同時に使える条件で大きく高速化する。GH200のOPT-30B・10%オフロードでは約3300GB/sの有効帯域を達成し、重み主体条件で比較方式に対し1.5〜5倍の性能を示す。KVキャッシュも大きいバッチ512では最大2.1倍、実際にGPU容量を超える設定ではvLLM比1.06〜1.83倍を報告する。一方PCIe接続では低〜中オフロード率で大きな利得があるものの、40%を超えるとPCIe帯域そのものが支配的になり方式間の差が縮む。

- GH200重みオフロード性能 / 比較方式比1.5〜5倍、OPT-30B・10%オフロードで約3300GB/s (比較対象: FlexGen、vLLM-プリフェッチ、vLLM-uvm; 条件: GH200、バッチ8、オフロード率0〜100%を掃引) — HBMへの先読み書き戻しを経ず、ローカルHBMとNVLink-C2C側の遠隔帯域を並列利用することで、両帯域の合算に近い有効帯域を引き出せる。

- 大規模KVキャッシュ条件 / 最大2.1倍 (比較対象: 既存のコピー型オフロード方式; 条件: GH200、バッチ512、OPT/Llama系モデルで重みとKVキャッシュを同時に外部化) — 重みだけでなくKVキャッシュも演算カーネルから直接遠隔参照できるため、注意機構側のHBM中継費用も削減できる。

- GPU容量超過時のエンドツーエンド性能 / vLLM比1.06〜1.83倍、FlexGen比1.53〜21倍 (比較対象: vLLM-プリフェッチ、FlexGen; 条件: GH200、OPT-30B、バッチ数と入力長を変えGPU容量を超える実運用型設定) — 単なる固定オフロード率のマイクロベンチマークだけでなく、容量不足から実際に必要となる外部化量でも直接アクセス方式の優位性が残る。

- 演算別オフロード率最適化 / オフロード率60%未満で一様配分に対し最大1.5倍 (比較対象: 全演算への一様オフロード配分; 条件: 重みとKVを含む各種演算へ総オフロード量を割当) — 計算律速で転送を隠せる演算と、ローカル・遠隔帯域を釣り合わせると速くなるメモリ律速演算へ優先配分することが効く。高比率になると全演算が遠隔帯域律速へ近づき差は縮む。

- TMAマルチキャスト / 再利用次元N=512で1.3倍、N=1024で2.5倍 (比較対象: 各計算器がホストメモリから同一タイルを個別取得; 条件: ホスト側重みタイルを複数計算器で共有する行列積) — GPU L2にキャッシュされないホストメモリを何度も読む転送増幅を、一度の遠隔取得と共有メモリへの複製へ置き換える効果が大きい。

- 能動的輻輳制御 / 行列積性能を最大1.22倍改善 (比較対象: 飛行中TMA要求を制限しない直接アクセス; 条件: 遠隔TMA要求がGPU内部相互接続へ集中する条件) — 直接アクセスも無制限に発行するとローカルHBM経路まで競合するため、遠隔要求数の制御が合算帯域を維持するうえで必要である。

### 負の結果・境界条件
- **高オフロード率ではPCIeが物理律速**: RTX 6000 Pro Blackwellでは0〜40%程度の低〜中オフロード率でDAKが大きく優位になるが、それを超えると64GB/s級のPCIe転送そのものが支配的になり、vLLM-プリフェッチやFlexGenとの差が小さくなる。直接アクセスでも外部リンクの物理帯域上限は越えられない。
- **TMA要求を増やしすぎると逆効果**: 遠隔TMAを多数同時発行するとGPU内部相互接続で輻輳が起き、遠隔取得だけでなくローカルHBM側の処理まで遅くなる。直接アクセスを採用するだけでは不十分で、飛行中要求数や遠隔担当計算器数の調整が必要になる。
- **高い容量要求では遠隔帯域支配へ収束**: 総オフロード率が非常に高い領域では、どの演算も遠隔メモリの供給待ちへ近づくため、演算別の最適配分による差も縮小する。容量拡張と速度改善を無制限に同時達成できるわけではない。

### 結果の読み方
DAKの本質は外部メモリを『計算前にHBMへ戻す待避先』ではなく、『演算カーネルが直接消費できる第二の帯域源』として扱うことにある。NVLink-C2Cのように遠隔帯域が大きい環境ではHBMと同時利用する効果が大きく、PCIeのように狭い接続でも計算で隠せる範囲や低オフロード率では優位性が残る。演算別の割当、輻輳制御、マルチキャストは、この直接アクセスを理想合算帯域へ近づけるための補助機構である。外部化量が増えすぎれば最終的には遠隔リンクが律速になるため、容量要件と算術強度に応じた配分が性能を決める。
## 品質への影響
同じ重みとKVキャッシュを別経路で読み込む方式であり、量子化や枝刈り、KV圧縮のような近似を追加しない。したがって方式固有のモデル品質低下はなく、トレードオフは外部帯域、共有メモリ資源、カーネル複雑性、オフロード率に現れる。
## 既存研究との差
- FlexGenやvLLM-プリフェッチのようなコピー型オフロードは、CPU側データを計算前にHBMへ移してから通常カーネルで読む。DAKはホストメモリから共有メモリへTMAで直接供給し、HBMを中継しない。
- 統合仮想メモリ（Unified Virtual メモリ; UVM）はページフォールトやページ移行を介してGPUからホストメモリを扱う。DAKは演算タイルの配置と転送を明示的に決め、カーネル内部でローカル・遠隔タイルを並行処理するため、汎用ページ管理の粒度と移行経路に依存しない。
- 従来の層単位オフロードはどの層を外部化するか、いつ先読みするかを主に扱う。DAKは線形層・注意機構ごとの算術強度から最適な外部化率を決め、その比率を実現する直接アクセスカーネルまで一体で設計する。
## 限界
- TMAの遠隔メモリアクセスを前提とするため、主な対象はHopper/Blackwell世代以降であり、古いGPUへ同じ実装をそのまま移植できない。
- 主評価は単一GPUと接続CPUメモリを使うオフライン推論で、多利用者オンラインサービングの待ち行列、複数GPU間の通信競合、SLO制御は直接評価しない。
- 低帯域PCIeで大きなオフロード率を強制すると外部リンクが物理的な律速になり、直接アクセスとコピー型の性能差が縮む。
- ホストメモリがGPU L2へ通常キャッシュされない性質とTMA要求の輻輳を補うため、演算ごとに専用カーネル、マルチキャスト、要求数調整が必要であり、汎用ランタイムだけで実現する方式より実装負担が大きい。
## 実装状態
公式GitHub `shouxulin/DirectAccessKernel` が公開されている。実装は約1300行のPythonと約2700行のCUDA C++から成り、CUTLASSを利用する。PyTorchから線形層と注意機構をSplitK_GEMM / SplitK_FlashAttnへ差し替える形で利用し、CUDA Graphにも対応する。
## 研究上の位置づけ
階層メモリ・重み/KVオフロード系統のうち、外部メモリをHBMへの待避元ではなく演算が直接読む帯域源へ変える研究に位置づける。FlexGen以降の大容量CPUメモリ活用では『何をいつHBMへ持ってくるか』が中心だったのに対し、DAKは『HBMへ持ってこない』経路を成立させる。SSDやCXLをさらに活用する研究を考える際にも、外部階層を中継バッファへコピーせず計算器近傍へ直接流し、ローカル帯域と並列利用するという原則は重要である。ただしNVMe SSDはTMAで直接共有メモリへ読めないため、GPUダイレクトストレージやCXLを使った別の直接経路・粒度設計が必要であり、その点が次の研究余地になる。
