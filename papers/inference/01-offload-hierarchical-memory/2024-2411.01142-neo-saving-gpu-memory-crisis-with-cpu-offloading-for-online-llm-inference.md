# NEO: Saving GPU Memory Crisis with CPU Offloading for Online LLM Inference

> decode attentionとKV cacheをrequestの一部だけCPUへ移し、GPU側sub-batchと並行実行しながら毎iterationの負荷に応じてoffload量を変えることで、online servingのlatencyを保ったままbatch sizeとthroughputを高めるCPU-GPU協調system。

## 概要

NEOは、GPU memory不足でKV cacheを十分に保持できずbatch sizeが小さくなる問題に対して、**一部requestのdecode attentionとKV cacheをlocal host CPUへ移す**online LLM inference systemである。

単純にKV cacheをCPU DRAMへ置いて必要時にGPUへ戻すと、decodeのたびに大きなKVをPCIe経由で往復させることになり転送がbottleneckになる。NEOはKV cacheをCPU側に置いたrequestについてattentionもCPUで計算し、GPUへは小さいactivationだけを渡す。

FastDecodeのように全requestをCPU attentionへ固定するのではなく、**CPUへ回すrequestとGPUに残すrequestを分けた2つのsub-batchを同時に進める**。さらに実際のonline workloadではrequestごとにprompt / output lengthが変化するため、毎iterationのqueueと推定実行時間を見てoffload量を動的に決める。

## 問題設定

online servingではlatencyを維持しつつthroughputを上げる必要がある。GPU computeには余裕があっても、weightとKV cacheがVRAMを圧迫するとbatch sizeを増やせず、GPU演算資源が使い切れない。

CPU DRAMは容量が大きいためKV cacheの退避先として使えるが、KVを毎token GPUへ戻す方式ではPCIe帯域が支配的になる。一方、decode attentionは低いarithmetic intensityのため、GPUとCPUの演算性能差ほど実効性能差は大きくない。

そこでNEOは、**KV cacheをCPUへ置くrequestはattentionもCPUで実行し、GPU memoryを解放して残りのGPU batchを大きくする**設計を採る。ただしCPUへ送りすぎると今度はCPU memory bandwidthがbottleneckになるため、offload量の動的調整が必要になる。

SSD / NVMeは使わず、local CPU DRAMをoffload先とする研究である。

## 手法

### 1. RequestをCPU側とGPU側の2 sub-batchへ分ける

各iterationで、NEOは主にGPUで処理するsub-batchと、decode attention / KV cacheをCPUへ置くsub-batchを作る。

CPU側requestでもattention以外のlinear / MLP計算はGPUを使う。つまりmodel weight全体をCPUへ移すのではなく、**KV cache依存が大きいdecode attentionだけをCPU側へ切り出す**。

これによりCPUは大量のmodel weight計算を担当せず、比較的memory-bandwidth-boundなattentionへ集中できる。

### 2. Asymmetric GPU-CPU pipelining

2つのsub-batchを同じ形で動かすのではなく、CPU側attentionが進んでいる間にGPU側では別sub-batchのlinear / attention処理を進めるよう、実行stageを非対称に組む。

狙いは

`CPU側のattention時間 ≈ GPU側で並行して進められる処理時間`

となるようにrequest数を調整し、CPU待ち・GPU待ちの両方を小さくすることである。

全requestをCPUへ送るFastDecode型ではCPUが詰まりやすいが、NEOは一部だけoffloadするのでCPU capacity内に収めやすい。

### 3. Load-aware scheduling

real-world workloadではinput / output lengthがrequestごとに違い、生成が進むにつれて各requestのKV cache長も変わる。そのため固定offload比率では最適点が動く。

NEOは毎iteration、GPU decoding queue、CPU decoding queue、prefill待ちrequestを見ながら、

- GPU-onlyで処理する案
- CPU/GPUの2 sub-batchを使う案

を作り、推定throughputが高い方を選ぶ。

partial offloadを使う場合はCPUとGPUの推定busy timeが近くなり、GPUがCPU待ちでidleにならないようrequestを割り振る。scheduler overheadは論文中で**1 iterationあたり3 ms未満**と報告されている。

### 4. CPU用paged attention kernel

NEOはSwiftLLMを基盤に実装され、CPU側attention用に独自のPaged-Attention-for-CPU（PACPU）を実装している。

paged KV cacheはmemoryが連続していないため一般的なCPU BLASだけでは扱いにくい。PACPUはC++ / ISPCを用いて、block tableで参照されるKVをmulti-thread / SIMDで処理する。

### 5. Multi-GPUでもCPU KVを分担する

multi-GPUではmodelをGPU間に分割し、各workerが自分のKV headに対応するCPU KV cacheを持つ。CPU間でKVを交換せず、GPU shardと対応するCPU側partitionを固定することで余計なcross-CPU communicationを避ける。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | T4、A10G、H100 |
| Model | Llama-2-7B、Llama-3.1-8B、Llama-3.1-70B |
| CPU | GPU hostに付属するlocal x86 CPU |
| Workload | Azure code generation trace、OpenAI summarization comparison、synthetic workloads |
| Baseline | vLLM、SwiftLLM、FastDecode+ |
| Offload先 | CPU DRAMのみ |

A10GはAWS g5、T4はg4dn、H100はlocal HGX serverを使用する。FastDecode+は元論文のfull CPU-attention方針をNEO runtime上に再実装した比較版である。

### Online load-latency

同程度のper-token latencyを維持した条件で、NEOはvLLMより処理可能request rateを高めた。

- 2×H100 + Llama-3.1-70B: 約14.3%高いthroughput
- A10G + Llama-3.1-8B: 約6.4%高いthroughput
- T4 + Llama-2-7B: 約5.6倍高いthroughput

T4で差が特に大きいのは、VRAM制約が強くGPU-onlyではKV cacheがbatch sizeを強く制限するためである。

### Workloadを変えた評価

synthetic workloadでinput / output lengthを変えると、最大でH100約14%、A10G約26%、T4約7.5倍のthroughput改善を報告している。

一方、outputが短い場合はCPUへ移すoverheadが利得を上回り、GPU-onlyよりわずかに遅くなる場合もある。NEOは通常GPU-onlyへfallbackできるが、profiling誤差によるsuboptimal decisionは残る。

### CPU性能への感度

A10GでCPU capacityを増やすと、baseline比のthroughput改善は最大79.3%まで伸びた。論文ではCPU core数そのものより**CPU memory bandwidth**との相関が強いと分析しており、decode attentionがmemory-bandwidth-boundであることと整合する。

## 既存研究との差

### FastDecodeとの違い

FastDecodeはKV cacheとdecode attentionをCPUへ全面的に置くため、CPU capacityが不足するとCPU側がsystem bottleneckになる。

NEOは**request単位のpartial offload**にし、GPU attentionも残す。さらに固定配置ではなく毎iterationのqueue状態からCPU/GPU比率を変えるため、input / output lengthが不規則なonline workloadへ適応しやすい。

### FlexGenとの違い

FlexGenは大きなeffective batchを作り、weight / KV I/Oを多数requestへ償却するoffline throughput志向である。NEOはuser-facing servingを対象に、latencyを保ちながら既存host CPUを使ってGPU batch sizeを増やす。

### HeteGenとの違い

HeteGenは主にlinear weightをCPU/GPUへ分割し、weight transferとCPU matrix multiplicationを重ねる。NEOはweightではなく**KV cacheとdecode attention**をrequest単位でCPUへ移す。

## 限界

- 改善幅はCPU memory bandwidthとGPU VRAM圧迫度に強く依存し、H100のようにVRAM余裕が大きい環境では利得が小さくなる。
- outputが短いworkloadではoffload / scheduling overheadが利得を上回る場合がある。
- schedulerはoffline profilingに基づく実行時間推定を使うため、予測誤差でsuboptimalな割当が起こる。
- 論文時点の実装はSwiftLLMベースであり、vLLMそのものへのupstream統合ではない。
- SSD / NVMe offloadやweight offloadは対象外。

## 一般的な実装上の含意

NEOの重要な示唆は、CPU offloadを「GPUに入らないものを全部CPUへ置く」という二値選択にしないことである。**CPU memory bandwidthが許す範囲だけrequestをoffloadし、残りはGPUで処理する**方が、hardware balanceが変わるonline servingでは安定しやすい。

またKV cacheをCPUへ置くなら、毎token KV全体をPCIeで往復させるより、attention計算自体をKVのある場所へ寄せて小さいactivationだけを転送する方が合理的な場合がある。
