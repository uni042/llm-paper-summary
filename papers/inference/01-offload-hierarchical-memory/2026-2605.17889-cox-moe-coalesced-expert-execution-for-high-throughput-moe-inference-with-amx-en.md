# CoX-MoE: Coalesced Expert Execution for High-Throughput MoE Inference with AMX-Enabled CPU-GPU Co-Execution

> 複数microbatchから同じexpertへ送られるtokenをまとめて大きなmatrix multiplicationとして実行し、Intel AMX対応CPUとGPUへexpert計算を分担して、offloaded MoEのthroughputを高める。

## 概要
CoX-MoEは、offloaded MoE servingでexpert weight transferだけでなく、**expertごとのGEMMが小さ過ぎてCPU/GPUのmatrix演算器を十分使えないこと**を問題にする。

複数microbatch / requestから同じexpertへ送られるtokenを一時的にまとめ、大きなbatchとして実行することでGEMM効率を上げる。論文ではこの方式を **coalesced expert execution** と呼ぶ。さらにIntel AMX対応CPUをexpert実行器としてGPUと並行利用し、必要ならattentionの一部をCPUへ移して、空いたVRAMへより多くのexpertを常駐させる。

対象はCPU DRAM + GPU HBMの協調実行で、SSD / NVMe / CXLは使わない。native routerと全expert計算は維持するためlosslessである。

## 手法のあらまし

中心となるのは、**同じexpertのtokenをmicrobatchをまたいでまとめること、利用頻度と計算costからGPUへ常駐させるexpertを選ぶこと、AMX対応CPUもexpert計算へ使うこと**である。

### 1. 同じexpertのtokenをmicrobatch境界を越えてまとめる

通常のserving runtimeでは、microbatchごとにroutingし、そのbatch内だけでexpert GEMMを実行する。このとき各expertへ数tokenしか来ないと、行列のM次元が小さくなり、GPU Tensor CoreやCPU matrix engineを効率よく使えない。

CoX-MoEは複数microbatchのrouting結果を一時的に蓄積し、**同じexpertへ向かうtokenをまとめて一つの大きなGEMMにする**。これが`coalesced`の意味である。

計算量そのものを減らすのではなく、同じFLOPsをより大きなmatrix multiplicationへ変換して、1回の演算でhardwareを使い切りやすくする。

### 2. 集約し過ぎるとrequestが待たされる

coalescingにはtokenが集まるまで待つ必要があるため、batchを大きくし過ぎるとTTFT / TPOTが悪化する。

そこでnon-MoE部分は通常のmicrobatch単位で進めつつ、expert部分だけをより大きなbatchへまとめる。

つまり**requestを細かく進める粒度とexpert GEMMを大きくする粒度を分ける**ことで、throughputとlatencyのバランスを取る。

### 3. 利用頻度と計算costからGPUへ残すexpertを選ぶ

GPU VRAMへ置けるexpert数には限界があるため、事前測定でexpertの利用頻度と実行costを調べ、GPU常駐にするexpertを選ぶ。

論文ではこの選別を **expert-aware stratification** と呼ぶ。考慮するのは主に、

- expertがどれだけ頻繁に選ばれるか
- そのexpertの処理cost
- GPU memory budget

である。

全expertの配置組み合わせを総当たりすると高価なため、似たexpertをまとめたり一部候補だけを試したりして、検討する配置数を減らす。

### 4. Intel `AMX`をCPU expert実行へ使う

AMX（Advanced Matrix Extensions）はIntel Xeonのmatrix演算機能で、BF16 / INT8などのmatrix multiplicationを通常のCPU命令より高throughputで処理できる。

CoX-MoEはCPU DRAMにあるexpertを単に保存するだけでなく、**AMX kernelでその場で計算する**。

同じexpertのtokenをまとめてGEMMを大きくすることはGPUだけでなくAMXにも効き、CPU側のmatrix演算器も使いやすくなる。

### 5. CPUとGPUの片方だけが遅くならないようexpertを分担する

全expertをGPUへ寄せるとPCIe transferとVRAMが詰まり、全expertをCPUへ寄せるとcomputeが遅い。

runtimeはCPU/GPUの計算能力、GPUに常駐しているexpert、PCIe transfer量を見てexpert workloadを分割する。

目的は両deviceの仕事量を完全に同じにすることではなく、**layer全体の完了を待たせている遅い側を短くすること**である。

### 6. AttentionをCPUへ移すのはexpert用VRAMを増やすため

attentionをCPUへ移すのは常時ではない。

attention stateをGPUへ置くより、そのVRAMをよく使うexpertの常駐に使った方がexpert transfer削減の効果が大きい場合にだけCPU attentionを選ぶ。

したがってattention offloadは独立の目的ではなく、**限られたVRAMをattentionとexpertのどちらへ使うかを調整する選択肢**である。

## 評価

### まず見るところ
- **結論:** 同じexpertのtokenをmicrobatch横断でまとめ、AMX CPUもexpert計算へ参加させると、offloaded MoEで小さ過ぎるGEMMを減らしてthroughputを上げられる。
- **実速度:** FlexGen比最大7.1倍、MoE-Lightning比最大2.4倍。当時の主要比較対象に対して1.7〜2.4倍。
- **品質:** native routing / 全expert計算を維持するlossless system最適化。
- **メモリ・I/O:** CPU DRAM + GPU HBM。SSD / NVMeは対象外。
- **注意点:** throughput-oriented。batch=1ではtokenを集める待ち時間が不利になり得て、Intel AMX依存も強い。

### Token集約の効果

事前測定ではmicrobatch単位の小GEMMはGPU / CPUとも演算器を使い切れず、同一expert tokenをまとめるほどmatrix engine効率が上がる。

一方で集約待ちが生じるため、throughputとper-request latencyにはtrade-offがある。

### CPU AMXの役割

AMX CPUを追加のexpert実行器として利用することで、GPU transfer待ちのexpertをCPU側で処理できる。

ただし結果はXeon世代・memory bandwidthに依存し、AMX非対応CPUへ同じspeedupをそのまま当てはめることはできない。

| 指標 | 評価状況 |

### 評価上の制約

- AMX対応Intel CPUが前提。
- CPU memory bandwidth / PCIe bandwidthに依存する。
- token集約は低batch latencyには不利になり得る。
- Apple Siliconや一般consumer CPUではCPU側kernelの作り直しが必要。
