# CoX-MoE: Coalesced Expert Execution for High-Throughput MoE Inference with AMX-Enabled CPU-GPU Co-Execution

> CoX-MoEは複数マイクロバッチの同一専門家向けトークンを集約して大きなGEMMにし、Intel AMX CPUとGPUへ分担実行して小規模GEMMとオフロード転送の非効率を減らす。

## 概要
CoX-MoEは、オフロード MoE 提供でエキスパート重み 転送だけでなく、**エキスパートごとのGEMMが小さ過ぎてCPU/GPUの行列演算器を十分使えないこと**を問題にする。

複数マイクロバッチ / リクエストから同じエキスパートへ送られるトークンを一時的にまとめ、大きなバッチとして実行することでGEMM効率を上げる。論文ではこの方式を **集約エキスパート 実行** と呼ぶ。さらにIntel AMX対応CPUをエキスパート実行器としてGPUと並行利用し、必要なら注意機構の一部をCPUへ移して、空いたVRAMへより多くのエキスパートを常駐させる。

対象はCPU DRAM + GPU HBMの協調実行で、SSD / NVMe / CXLは使わない。ネイティブルータと全エキスパート計算は維持するため無損失である。


CoX-MoEは、同じ専門家へ向かう複数マイクロバッチのトークンをまとめてGEMMを大きくし、AMX CPUとGPUを並行利用してオフロードMoEの演算器利用率を高める。RTX 6000 AdaとAMX対応Xeonの実機評価では、FlexGen比最大7.1倍、MoE-Lightning比最大2.4倍のスループットを報告した。

## 手法のあらまし

中心となるのは、**同じエキスパートのトークンをマイクロバッチをまたいでまとめること、利用頻度と計算コストからGPUへ常駐させるエキスパートを選ぶこと、AMX対応CPUもエキスパート計算へ使うこと**である。

### 1. 同じexpertのtokenをmicrobatch境界を越えてまとめる

通常の提供ランタイムでは、マイクロバッチごとにルーティングし、そのバッチ内だけでエキスパート GEMMを実行する。このとき各エキスパートへ数トークンしか来ないと、行列のM次元が小さくなり、GPU Tensor CoreやCPU 行列 エンジンを効率よく使えない。

CoX-MoEは複数マイクロバッチのルーティング結果を一時的に蓄積し、**同じエキスパートへ向かうトークンをまとめて一つの大きなGEMMにする**。これが`coalesced`の意味である。

計算量そのものを減らすのではなく、同じFLOPsをより大きな行列 乗算へ変換して、1回の演算でハードウェアを使い切りやすくする。

### 2. 集約し過ぎるとrequestが待たされる

集約にはトークンが集まるまで待つ必要があるため、バッチを大きくし過ぎるとTTFT / TPOTが悪化する。

そこでnon-MoE部分は通常のマイクロバッチ単位で進めつつ、エキスパート部分だけをより大きなバッチへまとめる。

つまり**リクエストを細かく進める粒度とエキスパート GEMMを大きくする粒度を分ける**ことで、スループットと遅延のバランスを取る。

### 3. 利用頻度と計算costからGPUへ残すexpertを選ぶ

GPU VRAMへ置けるエキスパート数には限界があるため、事前測定でエキスパートの利用頻度と実行コストを調べ、GPU常駐にするエキスパートを選ぶ。

論文ではこの選別を **エキスパート-考慮 層別化** と呼ぶ。考慮するのは主に、

- エキスパートがどれだけ頻繁に選ばれるか
- そのエキスパートの処理コスト
- GPUメモリ 予算

である。

全エキスパートの配置組み合わせを総当たりすると高価なため、似たエキスパートをまとめたり一部候補だけを試したりして、検討する配置数を減らす。

### 4. Intel `AMX`をCPU expert実行へ使う

AMX（Advanced Matrix Extensions）はIntel Xeonの行列演算機能で、BF16 / INT8などの行列 乗算を通常のCPU命令より高スループットで処理できる。

CoX-MoEはCPU DRAMにあるエキスパートを単に保存するだけでなく、**AMXカーネルでその場で計算する**。

同じエキスパートのトークンをまとめてGEMMを大きくすることはGPUだけでなくAMXにも効き、CPU側の行列演算器も使いやすくなる。

### 5. CPUとGPUの片方だけが遅くならないようexpertを分担する

全エキスパートをGPUへ寄せるとPCIe 転送とVRAMが詰まり、全エキスパートをCPUへ寄せると計算が遅い。

ランタイムはCPU/GPUの計算能力、GPUに常駐しているエキスパート、PCIe 転送量を見てエキスパートワークロードを分割する。

目的は両デバイスの仕事量を完全に同じにすることではなく、**層全体の完了を待たせている遅い側を短くすること**である。

### 6. AttentionをCPUへ移すのはexpert用VRAMを増やすため

注意機構をCPUへ移すのは常時ではない。

注意機構 状態をGPUへ置くより、そのVRAMをよく使うエキスパートの常駐に使った方がエキスパート 転送削減の効果が大きい場合にだけCPU 注意機構を選ぶ。

したがって注意機構オフロードは独立の目的ではなく、**限られたVRAMを注意機構とエキスパートのどちらへ使うかを調整する選択肢**である。

## 評価

### まず見るところ
- **結論:** 同じエキスパートのトークンをマイクロバッチ横断でまとめ、AMX CPUもエキスパート計算へ参加させると、オフロード MoEで小さ過ぎるGEMMを減らしてスループットを上げられる。
- **実速度:** FlexGen比最大7.1倍、MoE-Lightning比最大2.4倍。当時の主要比較対象に対して1.7〜2.4倍。
- **品質:** ネイティブルーティング / 全エキスパート計算を維持する無損失 システム最適化。
- **メモリ・I/O:** CPU DRAM + GPU HBM。SSD / NVMeは対象外。
- **注意点:** スループット-指向。バッチ=1ではトークンを集める待ち時間が不利になり得て、Intel AMX依存も強い。

### Token集約の効果

事前測定ではマイクロバッチ単位の小GEMMはGPU / CPUとも演算器を使い切れず、同一エキスパートトークンをまとめるほど行列 エンジン効率が上がる。

一方で集約待ちが生じるため、スループットとper-リクエスト遅延にはトレードオフがある。

### CPU AMXの役割

AMX CPUを追加のエキスパート実行器として利用することで、GPU 転送待ちのエキスパートをCPU側で処理できる。

ただし結果はXeon世代・メモリ帯域に依存し、AMX非対応CPUへ同じ高速化倍率をそのまま当てはめることはできない。

### 評価上の制約

- AMX対応Intel CPUが前提。
- CPUメモリ帯域 / PCIe帯域に依存する。
- トークン集約は低バッチ遅延には不利になり得る。
- Apple Siliconや一般consumer CPUではCPU側カーネルの作り直しが必要。
