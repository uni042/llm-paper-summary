# CoX-MoE: Coalesced Expert Execution for High-Throughput MoE Inference with AMX-Enabled CPU-GPU Co-Execution

> expert tokenを大きなcoalesced batchに集約し、AMX対応CPUとGPUへ処理を分担して、メモリ制約下のMoE serving throughputを高める。

## 概要
CoX-MoEは、offloaded MoE servingでexpert weight transferだけでなく、**expertごとのGEMMが小さ過ぎてCPU/GPUの演算器を使い切れないこと**を問題にする。

複数microbatch / requestから同じexpertへ送られるtokenをまとめ、大きな`coalesced batch`として実行することでGEMM効率を上げる。さらにIntel AMX対応CPUをexpert実行器としてGPUと並行利用し、必要ならattentionの一部をCPUへ移してVRAMをhot expert residencyへ回す。

対象はCPU DRAM + GPU HBMのco-executionで、SSD / NVMe / CXLは使わない。native routerと全expert計算は維持するためlosslessである。

## 手法のあらまし

CoX-MoEの中心概念は `coalesced expert execution`、`expert-aware stratification`、AMX CPU co-executionである。

### 1. `Coalesced Expert Execution`：microbatch境界を越えて同じexpertのtokenをまとめる

通常のserving runtimeでは、microbatchごとにroutingし、そのbatch内だけでexpert GEMMを実行する。このとき各expertへ数tokenしか来ないと、行列のM次元が小さくなり、GPU Tensor CoreやCPU matrix engineの利用率が低い。

CoX-MoEは複数microbatchのrouting結果を一時的に蓄積し、**同じexpertへ向かうtokenをまとめて一つの大きなGEMMにする**。

これが`coalesced`の意味である。

計算量そのものを減らすのではなく、同じFLOPsをより大きなmatrix multiplicationへ変換してhardware utilizationを上げる。

### 2. 集約し過ぎると待ち時間が増える

coalescingにはtokenが集まるまで待つ必要があるため、batchを大きくし過ぎるとTTFT / TPOTが悪化する。

そこでnon-MoE部分は通常のmicrobatch単位で進めつつ、expert部分だけをより大きなcoalesced batchへまとめる。

つまり**latency-sensitiveな部分の粒度とexpert GEMMの粒度を分離**している。

### 3. `Expert-Aware Stratification`：hot expertをGPUへ残す

GPU VRAMへ置けるexpert数には限界があるため、profilingでactivation frequencyと実行costを測り、GPU residentにするexpertを選ぶ。

論文の **expert-aware stratification** は、expertを単純な人気順だけでなく、

- activation frequency
- expertごとの処理cost
- GPU memory budget

を考慮してGPU / CPU側へ階層化する仕組みである。

全組合せ探索は高価なので、clustering / sampling / probingで候補を絞る。

### 4. Intel `AMX`をCPU expert実行へ使う

AMX（Advanced Matrix Extensions）はIntel Xeonのtile型matrix演算拡張で、BF16 / INT8などのmatrix multiplyを通常AVXより高throughputで処理できる。

CoX-MoEはCPU DRAMにあるexpertを単に保存するだけでなく、**AMX kernelでその場で計算する**。

coalescingでexpert GEMMを大きくすることはGPUだけでなくAMXにも効き、CPU側のmatrix engineを使いやすくする。

### 5. CPU/GPUへexpert計算を分担してstragglerを抑える

全expertをGPUへ寄せるとPCIe transferとVRAMが詰まり、全expertをCPUへ寄せるとcomputeが遅い。

runtimeはCPU/GPUのcompute capacity、resident expert集合、PCIe transfer量を見てexpert workloadを分割する。

目的は両deviceの仕事量を同じにすることではなく、**layer全体の完了時刻を決める遅い側（straggler）を短くすること**である。

### 6. Attention offloadはVRAMをexpertへ回すための選択肢

attentionをCPUへ移すのは常時ではない。

attention stateをGPUへ置くより、そのVRAMをhot expert residencyへ使った方がexpert transfer削減の効果が大きい場合にだけCPU attentionを選ぶ。

したがってattention offloadは独立の目的ではなく、**VRAM allocationをexpert throughputへ最適化するためのknob**として使われる。

## 評価

### まず見るところ
- **結論:** 同じexpertのtokenをmicrobatch横断でまとめ、AMX CPUもexpert計算へ参加させると、offloaded MoEのhardware utilizationを大きく上げられる。
- **実速度:** FlexGen比最大7.1倍、MoE-Lightning比最大2.4倍。SOTA比較では1.7〜2.4倍。
- **品質:** native routing / 全expert計算を維持するlossless system最適化。
- **メモリ・I/O:** CPU DRAM + GPU HBM。SSD / NVMeは対象外。
- **注意点:** throughput-oriented。batch=1ではcoalescing待ちが不利になり得て、Intel AMX依存も強い。

### Coalescingの効果

profilingではmicrobatch単位の小GEMMはGPU / CPUともutilizationが低く、同一expert tokenをまとめるほどmatrix engine効率が上がる。

一方で集約待ちが生じるため、throughputとper-request latencyにはtrade-offがある。

### CPU AMXの役割

AMX CPUを追加のexpert executorとして利用することで、GPU transfer待ちのexpertをCPU側で処理できる。

ただし結果はXeon世代・memory bandwidthに依存し、AMX非対応CPUへ同じspeedupを外挿できない。

### 評価上の制約

- AMX対応Intel CPUが前提。
- CPU memory bandwidth / PCIe bandwidthに依存する。
- coalescingは低batch latencyには不利になり得る。
- Apple Siliconや一般consumer CPUではkernel再設計が必要。
