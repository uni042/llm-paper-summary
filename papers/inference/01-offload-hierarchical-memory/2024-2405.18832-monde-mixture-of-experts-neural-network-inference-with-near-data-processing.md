# MoNDE: Mixture-of-Experts Neural Network Inference with Near-Data Processing

> GPUにないexpert weightを毎回GPUへ運ばず、weightを置いた拡張memory device側でexpert計算を行い、小さいactivationだけを転送することでMoEのdata movementを減らす方式。

## 概要
MoNDEは、あまり使われないexpertのweightをGPUへ運ぶ代わりに、**CXLでhost/GPUへ接続した拡張memory device側でexpert GEMMそのものを実行する**方式である。CXLはCPU・GPUと外部memoryを高速に接続するinterconnectで、この論文では単なる追加memoryではなく、device側にmatrix multiplication用の演算器も置く。

よく使われるexpertは従来通りGPUで実行し、少数tokenしか受けないexpertはactivationだけをCXL deviceへ送り、device内LPDDRに常駐するweightで計算する。つまり、Fiddlerが「CPU DRAMにあるexpertをCPUで実行する」のに対し、MoNDEは**拡張memory deviceに演算器を載せ、その場で実行する**構成である。

対象はSwitch-Large-128とNLLB-MoE。GPU側の性能測定には実機A100を使うが、MoNDE deviceそのものはhardwareの各clock cycleを模擬するsimulatorで評価しており、完成したCXL対応deviceの実機benchmarkではない。

## 手法のあらまし

MoNDEでは、weightを動かす従来方式を **PMove（Parameter Movement）**、activationだけを動かす提案側を **AMove（Activation Movement）** と呼ぶ。この二つをexpertごとに使い分けるのが中核である。

### 1. `PMove`：よく使われるexpertはweightをGPUへ持ってくる

従来のoffloadと同じく、GPUでexpertを計算する場合はexpert parameterをCXL memory側からGPUへ移す。

論文ではこのweight movementを **PMove** と呼ぶ。

データ量は概ねexpert weight sizeに比例し、式上は `2E d_model d_ff` に依存するため、expert数やFFN幅が大きいほど重い。

ただし多数tokenが同じexpertへ流れる場合は、一度weightをGPUへ持ってきた後のGEMMで転送costを多数tokenへ分散しやすい。

### 2. `AMove`：利用tokenが少ないexpertはactivationだけdeviceへ送る

1〜数tokenしか流れないexpertに対して数百MB級weightをGPUへ送るのは割に合わない。

そこでMoNDEではhidden activationだけをCXL deviceへ送り、**weightはdevice内LPDDRに置いたまま**expert GEMMを実行する。

このactivation movementを **AMove** と呼ぶ。

データ量は概ね `2BS d_model` に依存し、batch / sequenceが小さいとPMoveよりかなり小さくなる。

つまり、

- PMove：大きなweightをGPUへ動かす
- AMove：小さなactivationをweightのある場所へ動かす

という反対方向のdata movementを使い分ける。

### 3. Weightの近くにmatrix multiplication用の演算器を置く

この考え方を論文では **Near-Data Processing（NDP）** と呼ぶ。memoryから遠いGPUへ大量dataを送る代わりに、**dataを保存しているdeviceの近くで計算する**方式である。

MoNDEのCXL memoryは単なる容量拡張DRAMではない。device内部にmatrix multiplicationを並列実行する小型演算arrayとlocal bufferを持ち、host/GPUから `gemm` / `gemm+relu` のようなcommandを送ると、**LPDDRからweightを外へ出さずにdevice内で計算できる**想定になっている。

論文がmodel化するMoNDE deviceは、

- 8 memory channel
- 512 GB容量
- 合計約512 GB/s帯域
- 64個の4×4 matrix-multiplication array
- 264 KB buffer
- 1 GHz

という構成である。

したがってこの結果を「普通のCXL RAMへoffloadしただけ」と読むのは正しくなく、**memory + computeを一体化した専用hardware**が前提である。

### 4. 何expertをGPU側へ回すかを実行時に決める

全expertを固定的にGPU / deviceへ分けるのではなく、gate後に各expertへ流れるtoken数を見て、そのiterationで利用tokenが多い上位 `H` expertsをGPU側へ回す。

残りはAMoveでdevice側へactivationを送り、その場で計算する。

`H`は固定値ではなく、

- PCIe / CXL bandwidth
- device側のmemory bandwidth
- activated expert数
- GPU / deviceの処理速度

から決める。

論文ではprofile結果から係数 `α` を調整し、GPUとdeviceのどちらか片方だけが長く待つ状態を減らす。

### 5. GPUとdeviceを同時に使う

利用tokenが多いexpertをGPU、少ないexpertをdeviceへ送った後、両方を同時に走らせる。

layer全体は遅い側が終わるまで待つため、目的は単純にdeviceへできるだけ多く投げることではなく、**GPUとdeviceの処理時間を近づけて片側だけが遅くならないようにすること**である。

論文中の比較表では、このGPU/device協調構成を `MD+LB` と表記する。

### 6. なぜsmall-batchで効きやすいか

1 expertへ流れるtokenが少ないほどAMoveのdata量は小さく、PMoveの固定weight costとの差が大きくなる。

逆にbatchが大きくなって多くのexpertへ多数tokenが流れると、GPUへweightを送ってまとめて計算する方が有利になり、device側で計算する相対利得は小さくなる。

つまりMoNDEは、**expert利用が強く偏り、各expertへ流れるtoken数が少ない場面ほど有利**な設計である。

## 評価

### まず見るところ
- **結論:** 利用tokenが少ないexpertのweightをGPUへ運ばずCXL接続device側で計算すると、特にencoder workloadのparameter movementを大きく減らせる。
- **実速度:** Switchでencoder 3.1倍、NLLBでencoder 6.7倍など大きな改善を示す一方、decoder側の改善は比較的小さい。
- **品質:** 同じnative expertを別deviceで実行するだけなのでlossless。
- **メモリ・I/O:** 通常CPU DRAMやSSDではなく、**CXL接続memory + 専用compute**を想定。
- **評価の強さ／注意点:** **Simulationのみ**。A100 profileは実機だがMoNDE deviceはhardwareのclock cycle単位のsimulatorで、512 GB/s級の将来hardware仮定を含む。

### 比較構成

| 略称 | 内容 |
|---|---|
| GPU+PM | 選ばれたexpert weightをGPUへ移して計算 |
| MD+AM | 全expertをdevice側でactivationだけ移して計算 |
| MD+LB | 利用tokenが多いexpertはGPU、少ないexpertはdeviceで同時実行 |
| Ideal | 全weightがGPUにある理想上限 |

`MD+LB` が提案の主構成である。

### 主なlatency改善

GPU+PMに対するMD+LBのspeedup。

| Model | Encoder | Decoder |
|---|---:|---:|
| Switch-Large-128 | 3.1倍 | 1.1倍 |
| NLLB-MoE | 6.7倍 | 1.9倍 |

論文内の平均的なまとめでは、encoder約4.9倍、decoder約1.5倍。

encoder側の方が大きく伸びるのは、routing / token distributionとweight movementの条件がdevice側計算に有利だからである。

### Abstractで示される最大値

| 比較 | 最大speedup |
|---|---:|
| Parameter-offloading baseline、encoder | 7.5倍 |
| Parameter-offloading baseline、decoder | 3.7倍 |

これは代表的な最大値で、全batch / 全modelの平均ではない。

### CPUでexpert計算する方式との比較

NLLBでCPU計算 + activation movementを使う構成と比べると、MoNDEは次の改善を報告する。

| 部分 | Device側計算のlatency改善 |
|---|---:|
| Encoder | 9.1倍 |
| Decoder | 1.9倍 |

この差の主因として、MoNDE側の想定memory bandwidthがCPUの約2.7倍であることが挙げられる。

### Hardware overhead

| 項目 | 値 |
|---|---:|
| Device内演算logicのarea overhead | 約3.0 mm² |

### 評価上の制約

- CXL接続の計算機能付きmemory deviceそのものは実チップ測定ではない。
- 512 GB/s級memory bandwidthを仮定する。
- GPUへ回すexpert数の調整に性能が依存する。
- encoder / decoderを中心に評価し、online multi-user servingは扱わない。
- KV cache placementは対象外。
- 通常のCPU offload / SSD offloadとはhardware前提が大きく異なる。
