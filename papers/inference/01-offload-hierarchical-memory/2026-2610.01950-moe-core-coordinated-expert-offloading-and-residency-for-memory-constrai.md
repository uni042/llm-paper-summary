# MoE-CORE — メモリ制約下のMoE専門家常駐・転送の協調制御

## 概要

MoE言語モデルは各トークンで一部の専門家（expert）だけを起動するため演算量は抑えられるが、全expertの重みを保存する必要は残る。総パラメータが数百B以上になると、単一NPUのメモリに全expertを置けず、ホストメモリから必要な重みを転送する。転送をrouterの確定後に始める単純なLoad on Demand（LoD）は、H2D転送が次トークン生成のクリティカルパスへ入る。MoE-COREは、prefillとdecodeで必要なexpertの集合と遅延許容度が異なる点に着目し、異なる常駐・転送方式を一つのランタイムで管理する。

長いプロンプトを処理するprefillではexpert層全体を二つのバッファへ交互に載せ、現層の計算と次層の転送を重ねる。一方、decodeでは層ごとに異なるexpertキャッシュ容量を割り当て、ドメインごとの頻出expertで初期化し、トークン単位のルーティング履歴で入替え、次層のrouterを先読みして非同期転送する。主要評価では本来選ばれたexpertをそのまま計算する。別の任意モードでは低スコアのcache missだけを近傍スコアの常駐expertで置換するが、これは近似実行であり主要なexact評価と区別する。

DeepSeek-V4-Flash-W4A8を単一Ascend 950PR、NPUメモリ上限84 GBで評価すると、LoD比の平均TPOTは5ワークロードで1.39〜1.75倍改善した。GLM-5.2-W4A8C8でもTPOTは5件すべてで短くなった。ただし、vLLM Prefetchの極端に遅いTPOTと比較する際は、vLLM側だけ出力上限128トークン、MoE-COREとLoDは1024トークンという異なるプロトコルであり、特にE2EL・TPSの直接比較は妥当でない。

## 問題設定・実測観測

ルーティングされた専門家の集合は `TopK(router(h), k)` で決まる。トークン単位の計算量は選ばれた少数のexpertに比例するが、全expert重みの容量は全層・全expertの合計で決まる。デバイスメモリには固定重みだけでなくKVキャッシュ、活性化、実行ワークスペースも必要なので、コンテキスト長が増えるほどexpertキャッシュに割ける容量が減る。expertをホストへ追い出せば容量問題は解消するが、cache miss時には転送起動費と `expert bytes / 実効H2D帯域` の待ちが生じる。

著者らはDeepSeek-V4-Flash-W4A8の40 MoE層（ゼロ始まり3〜42）で各層84 expertを常駐させた際のヒット率を調査した。層4と7は5つのワークロードすべてで下位10位に入り、層7、9、19、25、27、31、37は全ワークロードで隣接層より低い局所的な谷となった。均一なexpert数を割り当てるだけでは、繰り返しmissしやすい層が残る。

同じ層20のドメイン別頻出expertは、GSM8KでID21、AIME 2026で179、HumanEvalで1、MMLUで172、LongBench v2で235と異なる。上位6expert集合のJaccard重なりは0〜0.200、平均0.116に過ぎず、要求のドメインに応じた初期キャッシュが必要になる。またAIME 2026の層20では、選択境界の6位expertスコア2.5010%と7位2.4493%が0.0517ポイント差だった。低スコアの選択expertを常駐する近接スコアexpertで代替する余地を示すが、**スコアの近さは出力関数の等価性を保証しない**。

## 手法

### 1. prefillとdecodeの独立メモリ領域

MoE-COREはNPUメモリのexpert領域をprefill用とdecode用に物理的に分離し、推論中は両方を確保する。prefill側には最大expert層を丸ごと置ける二つのバッファ `B0`、`B1` を用意する。初期状態で連続する二層のexpertをロードし、層 `l` の計算終了後に空いたバッファへ層 `l+2` の全expertを転送する。その間、別バッファにある層 `l+1` の計算を進める。定常段階の所要時間は概ね `max(現層の計算時間, 次層のH2D時間) + 同期費` になる。

この完全層ステージングは、prefillのトークン数が層ごとの閾値 `N*_l = floor(K_l^(0) / k_l)` に達した場合に使う。`K_l^(0)` は初期キャッシュexpert数、`k_l` はルーティングで選ぶexpert数である。短いprefillでは完全層を載せず、選択expertの常駐方式を使う。転送と計算が重なるのは定常状態であり、最初の二層のロード、最後の排出、同期費はTTFTへ残る。

### 2. 層別キャッシュ容量のオフライン配分

decode側のexpertメモリ容量 `M_dec` に対して、層 `l` の常駐スロット数 `K_l` とexpert一個のサイズ `S_l` は `Σ K_l S_l ≤ M_dec` を満たす。MoE-COREは代表的なルーティング履歴を再生し、各層のキャッシュ容量とヒット率の関係 `H_l(k)` を測る。現在の容量からスロットを減らしてもヒット率があまり下がらない高ヒット層を供与元、スロットを増やすとヒット率が大きく上がる低ヒット層を受け手に選ぶ。供与による損失より受入れによる改善が大きく、メモリ制約を守る場合だけスロットを移す。供与・受入れ候補を毎回再評価し、正の改善がなくなれば止める。

これはトークンごとに容量を変えるのではなく、モデル・ワークロード・利用可能なメモリが変わった時に再実行するオフラインの割当である。評価構成ではDeepSeekの大部分の層へ78スロット、低ヒットの層7、9、19、31、37へ120スロットを割り当てた。GLMはexpert重みが大きいため、単一NPU上で層当たり28スロットに制限された。

### 3. ドメイン別ホットexpertによる初期化

要求を受け付けるスケジューラが数学、コード、QAなどのドメインヒントを渡す。事前プロファイルでは、そのドメインのトークンについて各層・各expertのrouterスコアを平均し、平均スコアの高いexpert順のリストを保存する。層別配分で決めた `K_l` 個のスロットに、そのドメインの上位 `K_l` expertを初期ロードする。

重要なのは「どの層に何個置くか」と「どのexpertを置くか」を別問題として解くことである。ドメイン情報が実際の要求を代表しなければ初期ヒット率は悪化するが、後述のRHACがセッション内の選択履歴に追従して内容を更新する。

### 4. RHAC：履歴と現在routerを組み合わせた置換

Routing-History-Aware Cache（RHAC）は、expertごとに直近 `W` トークンで選ばれた頻度、長期選択頻度の指数移動平均、現在トークンのrouterスコア、最後に選ばれてからの経過トークン数を保持する。これらを層内で正規化し、正の係数を掛けた最近頻度・長期頻度・現在スコアから、古さのペナルティを引いて常駐優先度 `η` を作る。直近と長期の両方で頻出するexpertを守り、現在スコアの高いexpertも保護し、長期間使われないexpertを退去候補にする。

選択されたexpertが不在で、キャッシュが満杯なら、実行中・転送中など保護対象のexpertを除いた常駐集合から最小 `η` のexpertを退去させ、要求されたexpertをロードする。RHACは生成トークンごとに更新される。単なるLRUでは捕らえにくい長期的なルーティング傾向と現在のrouter信号を併用するため、ドメイン初期化だけでは対処できないセッション内の偏りを補う。

### 5. 次層routerの先行評価と非同期プリフェッチ

通常、層 `l+1` のrouterはその層への入力 `h_(l+1,t)` が計算されるまで実行できない。MoE-COREは層 `l` のhidden state `h_(l,t)` を次層の元router `R_(l+1)` に早めに渡し、次層expertランキングを近似する。予測されたexpertがデバイスに存在しなければ、層 `l` の残りの計算と次層attentionを実行している間にH2D転送を開始する。

転送数は、残り計算と次層attentionの合計で隠せる転送時間、未常駐候補数、確保可能なスロット数の最小値に制限する。デフォルトでは層当たり一expertを先読みする。予測が誤れば余分なH2D帯域とキャッシュスロットを消費するため、予測を多くすれば常に速くなるわけではない。真のrouter確定時にまだ不在のexpertは通常のexactロード経路へ回る。

### 6. 任意のAES近似expert置換

Approximate Expert Substitution（AES）は、Top-k境界直上の低スコアexpertがキャッシュにない場合、境界直下にある未選択・常駐expertで代替する機能である。境界直下のスコア `b` と許容幅 `α` により、選択expertで `b ≤ score ≤ (1+α)b` を満たすものだけを置換候補とし、`score > (1+α)b` の高スコアexpertは必ず元expertをロードする。代替候補は `(1−α)b ≤ score ≤ b` の範囲にある未選択常駐expertに限る。双方をスコア順に一対一対応させ、元expertのルーティング係数を維持したまま代替expertのFFN出力を用いる。

AESはexactなモデル計算を変更する。近いrouterスコアが似たFFN出力を保証するわけではない。したがってAESを無効化した主要表のTPOTと、AES有効時の専門家可用率やMTP併用速度は別の実験条件として扱う必要がある。

| 項目 | 原著の具体条件 |

RHACが性能差の最大の要因であり、層別容量・ドメイン初期化は小さいが補完的な利得を示す。プリフェッチを0→1→2→3と増やすとexpertヒット率は89.05→92.43→93.81→94.05%へ単調に増えるが、TPOTは42.6→36.0→35.9→36.5 msとなり、深度3では転送を計算中に隠し切れない。ヒット率だけを最適化しても速度は単調に改善しない。

AESを有効化すると「転送なしで実行できるexpert呼出し」の層平均可用率は92.43%から99.972%へ上がるが、これは元expertのexactヒット率ではなく代替expertによる実行を含む指標である。さらにバッチ1・MTP無効ではAES有効化でTPOTが36.0→37.7 msと4.7%悪化する。代替候補のCPU側計算が追加費用になるため、AESは無条件に有利ではない。

AESとMTPを併用するバッチ2の別実験では、MTP深度1/2/3のTPOTは23.1/21.5/22.3 ms、受理率は95.21/78.33/60.78%であり、深度2が最速だった。これはバッチ1・exactの主表と条件が異なる。原著の表3ではAES有効・バッチ2・MTP深度2のTPOTが22.0 msとも記載されており、同論文内の21.5 msと22.0 msの差について、異なる計測集計または表条件の可能性はあるが、確定できない。両数値を区別して保持する。

## 既存研究との差

MoE-InfinityやFineMoEは活性化履歴とexpertキャッシュを使い、SiDA-MoEやProMoEは別の予測器を用いる。MoE-COREは別予測器を追加せず、**次層の既存routerを前層hidden stateで早めに実行**することによりプリフェッチ候補を得る。また、prefillでは層全体の二重バッファ、decodeでは一部expertの常駐というフェーズ別構成を持ち、層別容量配分・ドメイン初期化・オンラインRHAC・プリフェッチを同じデバイスメモリ制約の中で協調させる。

FiddlerやKTransformersのCPU/GPU協調推論とは異なり、中心はhost側expert計算ではなく、NPU側で必要expertを実行するための転送隠蔽と常駐制御にある。SMoEやBuddyMoEに近いexpert代替はオプションとして切り出し、主要なexact実行の性能評価と混ぜない。KVキャッシュ自体の量子化・圧縮や複数NPUへのexpert配置を同時最適化する方式ではない。

## 限界・再現性

本評価はAscend 950PR単体、NPUメモリ84 GB上限、特定の二つの量子化済みMoEモデル、五つのワークロードに限定される。hostとNPUの転送帯域・起動費、モデルのrouter分布、ドメインヒントの正しさ、KV長、prefillとdecodeの負荷構成によって最適な常駐・転送戦略は変わる。異なるGPU・PCIe構成や複数デバイスへの移植では、先読みが隠せる計算窓とexpertサイズが変わるため速度倍率を再測定する必要がある。

主表はTPOTなどの性能を測るもので、AESを無効化したexactなexpert実行ではモデル計算自体を変更しない。しかしAESを有効化すると選択expertを別expertへ置き換えるため、回答品質への影響が別途必要になる。原著の可用率99.972%は正答率99.972%を意味しない。vLLM Prefetch比較の出力上限が一致しないため、原著の巨大なTPOT倍率を標準的な公平ベンチマークとして扱うべきではない。多NPU配置、KVキャッシュ管理との共同最適化、実際の企業内サービスにおける同時要求のQoSは未解決である。
