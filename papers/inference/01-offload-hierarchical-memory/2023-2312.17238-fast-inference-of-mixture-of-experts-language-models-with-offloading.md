# Fast Inference of Mixture-of-Experts Language Models with Offloading

> MoE expertをCPUへ置き、最近使ったexpertをGPUへ残すLRU cacheと、将来使いそうなexpertの投機的先読みを組み合わせて、GPU memory制約下の重み転送待ちを減らす推論手法。

## 概要
Fast Inference of MoE with Offloading（実装名 **Mixtral-Offloading**）は、Mixtral-8x7Bの巨大なexpert weightをCPU DRAMへ置き、必要なexpertだけGPUへ移すことで、12〜16 GB級VRAMでもMoEを動かす方式を実装した研究である。

各MoE layerは8 expertsからtop-2を選ぶため、1 tokenで実行するexpertは一部だけだが、通常は全expert weightを保持する容量が必要になる。そこで非expert部分と一部expertをGPUへ残し、残りをCPU RAMへ置く。

この研究の主階層は **CPU DRAM ↔ GPU VRAM** であり、SSD/NVMeを直接streamingする方式ではない。またKV cache offloadではなく、expert weight transferが中心である。

さらにVRAMを抑えるため、attentionとexpertをHQQで別々に量子化し、4/3/2-bit構成を評価している。したがって、cache/prefetch自体はlosslessでも、最終的な実運用構成ではquantizationによる別のquality trade-offがある。

## 手法のあらまし

この実装は、**「必要になってからCPUからexpertを読む」だけではPCIe待ちが長すぎる**ため、最近使ったexpertをGPUへ残す `expert cache` と、将来使うexpertを早めに読み込む `speculative expert loading` を組み合わせている。

### 1. Expert weightをCPUの`pinned memory`へ置く

CPU側のexpert tensorは **pinned memory** に置く。CUDAがpageable memoryより効率よくhost-to-device DMA転送できる領域として使い、複数の非同期bufferを介して現在expertのGPU計算と次expertのCPU→GPU転送を重ねる。

このため性能はGPUのGEMM性能だけでなく、PCIe bandwidthとhost memory bandwidthにも強く依存する。

### 2. `Expert cache`：layerごとに最近使ったexpertをVRAMへ残す

各MoE layerに小さなexpert cacheを持ち、最近使ったexpertをGPUへ残す。基本方針はLRUで、同じexpertが近いtokenで再び選ばれればCPU→GPU transferを省ける。論文は12GB GPUでlayer当たりk=2、16GB GPUでk=4のcacheを用いる。

### 3. `Speculative Expert Loading`：未来layerのgateを早めに近似する

論文固有の **speculative expert loading** は、tokenをspeculative decodingする方式ではない。予測するのは次に必要なexpert IDである。

現在layerのhidden stateへ次layerのgating functionを早期適用し、次に選ばれそうなexpertを推定して正式なgate判定前に非同期transferする。予測が当たれば待ち時間を隠蔽でき、外れればnative gateが選んだ正しいexpertを後からloadするため、予測ミスは品質低下ではなく余分なPCIe trafficとして現れる。

### 4. 先読み距離にはtrade-offがある

論文では1 / 2 / 10 layer先などを評価しており、遠い先読みほど転送開始を早められる一方でrouting predictionの精度が下がる。したがって、先読み時間の利得と誤prefetchのbandwidthコストを両立させる必要がある。

### 5. HQQ量子化をattentionとexpertで分ける

VRAM / RAM容量とPCIe transfer量を減らすため、attentionとexpertを別bit幅でHQQ量子化する。expertは全46.7B parameter中45.1B（96.6%）を占めるため、expert側の低bit化は容量と転送量の双方に効く。

### 6. 後続方式との位置付け

この研究は「CPUにあるexpertをGPUへ持ってきてGPUで計算する」方式である。後続のFiddler系のようにCPU上のexpertをCPUで計算してweight transfer自体を避ける方式とは設計点が異なり、CPU DRAM上のMoE expertをGPUへweight transferする基線として重要である。

## 評価

### まず見るところ
- **結論:** expertをCPU DRAMへ置き、VRAM側でcache＋先読みすると、12〜16 GB級GPUでもMixtral-8x7Bを実行できる。
- **実速度:** consumer GPUを含む実機で概ね2〜3 tokens/s級を示す。
- **品質:** cache / speculative loadingはnative expertへfallbackするためlossless。2/3-bit expert量子化には別途quality trade-offがある。
- **ボトルネック:** T4やRTX 3060ではPCIe Gen3が支配的で、GPU compute性能差ほどtokens/sが開かない。
- **評価の強さ／注意点:** **実機**だがbatch=1中心で、全offloaded expertをCPU DRAMへ保持できることが前提。SSD streamingやKV階層は未評価。

### 量子化品質

論文はWikiText-2 / C4 perplexityとMMLUを用いて量子化構成を評価している。

| 構成 | 論文表のmodel size | WikiText-2 PPL | C4 PPL | MMLU |

| Attention 4-bit + Expert 2-bit | 23.99 GB | 3.76 | 6.66 | 69.11% |
| Attention 4-bit + Expert 3-bit | 21.37 GB | 4.05 | 6.87 | 68.47% |

### 評価上の制約

- batch=1 / 単一request中心。
- CPU RAMに全offloaded expertを保持できることが前提。
- SSD / NVMeからのweight streamingは評価しない。
- KV cache offloadは対象外。
- continuous batching / multi-tenant servingは未評価。
- 速度にはHQQ量子化kernelの性能も含まれるため、cache/prefetchだけの純粋speedupではない。
