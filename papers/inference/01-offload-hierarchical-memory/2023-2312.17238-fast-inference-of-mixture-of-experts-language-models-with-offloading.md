# Fast Inference of Mixture-of-Experts Language Models with Offloading

> MoE expertをCPUへ置き、activation-awareなcacheと先読みでGPUメモリ制約下の重み転送を抑える推論手法。

## 概要
Fast Inference of MoE with Offloading（実装名 **Mixtral-Offloading**）は、Mixtral-8x7Bの巨大なexpert weightをCPU DRAMへ置き、必要なexpertだけGPUへ移すことで、12〜16 GB級VRAMでもMoEを動かす方式を実装した研究である。

各MoE layerは8 expertsからtop-2を選ぶため、1 tokenで実行するexpertは一部だけだが、通常は全expert weightを保持する容量が必要になる。そこで非expert部分と一部expertをGPUへ残し、残りをCPU RAMへ置く。

この研究の主階層は **CPU DRAM ↔ GPU VRAM** であり、SSD/NVMeを直接streamingする方式ではない。またKV cache offloadではなく、expert weight transferが中心である。

さらにVRAMを抑えるため、attentionとexpertをHQQで別々に量子化し、4/3/2-bit構成を評価している。したがって、cache/prefetch自体はlosslessでも、最終的な実運用構成ではquantizationによる別のquality trade-offがある。

## 手法のあらまし

この実装は、**「必要になってからCPUからexpertを読む」だけではPCIe待ちが長すぎる**ため、`expert cache` と `speculative expert loading` を組み合わせている。

### 1. Expert weightをCPUの`pinned memory`へ置く

CPU側のexpert tensorは **pinned memory** に置く。これはページアウトされないhost memoryで、CUDAが通常の pageable memory より安定してDMA転送しやすい領域である。

expert weightをCPU RAMへ置くだけでは、毎回のCPU→GPU copyが同期的に発生してGPUが待つ。そこでpinned memoryと複数CUDA streamを使い、

`GPUで現在expertを計算` と `CPUから次expertを転送`

を重ねる。

このため性能はGPUのGEMM性能だけでなく、PCIe bandwidthとhost memory bandwidthにも強く依存する。

### 2. `Expert cache`：layerごとに最近使ったexpertをVRAMへ残す

各MoE layerに小さなexpert cacheを持ち、最近使ったexpertをGPUへ残す。

基本方針はLRUで、同じexpertが近いtokenで再び選ばれればCPU→GPU transferを完全に省ける。

重要なのは、Mixtralではexpert一つのweightが大きく、論文中では約300 MB級になるため、**cache miss 1回のコストがかなり重い**ことである。

そのため数回のhitでも、GPU computeを少し最適化するより効果が大きい場合がある。

### 3. `Speculative Expert Loading`：未来layerのgateを早めに近似する

論文固有の **speculative expert loading** は、tokenをspeculative decodingする方式ではない。

ここで予測するのは**次に必要なexpert ID**である。

現在layerまで得られているactivationを、将来layerのgating functionへ早めに入力し、1層先・2層先・さらに遠い層で選ばれそうなexpertを推定する。そのexpertを正式なgate判定より前にCPUからGPUへ非同期transferする。

実際のlayerへ到達したとき、

- 予測が当たった → すでにVRAMにあるので待たない
- 予測が外れた → native gateが選んだ正しいexpertをその場でloadする

という動作になる。

つまり**予測ミスは品質ではなく余分なPCIe trafficとして支払う**。cache/prefetch部分はnative routingを変更しないlossless型である。

### 4. 先読み距離にはtrade-offがある

論文では1 / 2 / 10 layer先などを試しているが、遠くを予測するほど転送開始を早められる一方、routing predictionは外れやすくなる。

外れたexpertも数百MB単位なので、誤prefetchが増えると本当に必要なtransferとPCIe帯域を奪い合う。

したがって、

`先読みを早く始められる利得` と `誤ったweightを運ぶコスト`

のバランスが必要で、単純にlookaheadを大きくすればよいわけではない。

### 5. HQQ量子化をattentionとexpertで分ける

VRAM / RAM容量とPCIe transfer量を減らすため、attentionとexpertを同じbit幅に固定せず別々にHQQ量子化する。

実運用ではattentionを4-bit程度へ保ち、容量の大部分を占めるexpertを2/3-bitへ落とす構成を評価している。

ここで **HQQ** はweight-only系の低bit量子化で、offload schedulerそのものではない。論文の速度改善には、

- weightが小さくなってtransfer byte数が減る効果
- cache / prefetchによってtransfer回数・待ち時間が減る効果

の両方が含まれるため、分けて読む必要がある。

### 6. Fiddler型との違い

この研究は「CPUにあるexpertをGPUへ持ってきてGPUで計算する」方式である。

後続のFiddler系は逆に、expert weightがCPUにあるならhidden activationだけCPUへ送り、**expertをCPUで計算してweight transfer自体を避ける**選択肢を取る。

Mixtral-Offloadingではexpert一つが大きいためPCIe weight transferが律速になりやすく、この差が後続研究の重要な分岐になる。

## 評価

### まず見るところ
- **結論:** expertをCPU DRAMへ置き、VRAM側でcache＋先読みすると、12〜16 GB級GPUでもMixtral-8x7Bを実行できる。
- **実速度:** consumer GPUを含む実機で概ね2〜3 tokens/s級を示し、単純offloadより大きく改善する。
- **品質:** cache / speculative loadingはnative expertへfallbackするためlossless。2/3-bit expert量子化には別途quality trade-offがある。
- **ボトルネック:** T4やRTX 3060ではPCIe Gen3が支配的で、GPU compute性能差ほどtokens/sが開かない。
- **評価の強さ／注意点:** **実機**だがbatch=1中心で、全expertをCPU DRAMへ保持できることが前提。SSD streamingやKV階層は未評価。

| GPU | VRAM | 接続・位置付け |

A100以外はMixtral全体をそのままVRAMへ置くには厳しい容量で、CPU RAMをcapacity tierとして使う。

### 2-bit expert構成の生成速度

OpenAssistant会話、batch=1でのfull algorithmの結果。

| GPU | 生成速度 |
|---|---:|
| A100 | 3.061 tokens/s |
| RTX 3080 Mobile | 2.655 tokens/s |
| RTX 3060 | 2.278 tokens/s |
| T4 | 2.092 tokens/s |

A100とconsumer GPUの差が通常のdense inferenceほど大きくないのは、offload条件では**computeよりPCIe / memory movementの比率が高い**ためである。

### 3-bit expert構成の生成速度

| GPU | 生成速度 |
|---|---:|
| A100 | 2.845 tokens/s |
| RTX 3080 Mobile | 2.475 tokens/s |
| RTX 3060 | 2.038 tokens/s |
| T4 | 1.603 tokens/s |

bit幅が増えるとexpert weightのtransfer量も増えるため、品質だけでなくI/O時間にも影響する。

### T4でのablation

2-bit expert条件で、各最適化の有無を比較すると次のようになる。

| 方式 | 速度 |
|---|---:|
| Full algorithm | 2.092 tokens/s |
| 先読みなし | 1.567 tokens/s |
| LRU＋先読みなしの構成 | 1.168 tokens/s |
| naive Accelerate | 0.661 tokens/s |

単純なframework offloadから見ると、cacheと非同期prefetchを組み込むことの寄与が大きい。

### 量子化品質

論文はWikiText-2 / C4 perplexityとMMLUを用いて量子化構成を評価している。

| 構成 | 論文表のmodel size | WikiText-2 PPL | C4 PPL | MMLU |
|---|---:|---:|---:|---:|
| Attention 4-bit + Expert 2-bit | 23.99 GB | 3.76 | 6.66 | 69.11% |
| Expert 3-bit構成 | 21.37 GB | 4.05 | 6.87 | 68.47% |
| Mistral-7B 4-bit（参考） | — | — | — | 61.3% |

※ size値は論文表の構成値をそのまま記録している。bit幅だけを見て単純な大小関係を推定せず、各構成の詳細条件とセットで読む方がよい。

### この結果から分かること

- consumer GPUでもMixtral級MoEを実行できる。
- GPUが速くてもPCIeが遅いと生成速度は伸びにくい。
- expertを低bit化するとcapacityだけでなくtransfer byte数も減る。
- cache hitとprefetch成功は直接PCIe待ちの削減につながる。
- 誤prefetchは品質を落とさない代わりにbandwidthを浪費する。

### 評価上の制約

- batch=1 / 単一request中心。
- CPU RAMに全offloaded expertを保持できることが前提。
- SSD / NVMeからのweight streamingは評価しない。
- KV cache offloadは対象外。
- continuous batching / multi-tenant servingは未評価。
- 速度にはHQQ量子化kernelの性能も含まれるため、cache/prefetchだけの純粋speedupではない。

このため、後続研究との比較では **「CPU DRAM上のMoE expertをGPUへweight transferする基線」** として扱うのが適切である。
