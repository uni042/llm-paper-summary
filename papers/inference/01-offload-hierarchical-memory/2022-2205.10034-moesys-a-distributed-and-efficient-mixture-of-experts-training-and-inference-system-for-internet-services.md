# MoESys: A Distributed and Efficient Mixture-of-Experts Training and Inference System for Internet Services

> MoEの不均衡とGPU容量不足を、訓練時のElastic MoE＋2D先読みと、推論時のCPU/GPU ring型section実行で処理し、DeepSpeed比で訓練33%・推論13%のthroughput向上を報告する。

## 概要

混合専門家モデル（Mixture of Experts; MoE）は、各tokenを少数の専門家だけへ送ることで、全parameterを毎回計算せずにmodel capacityを増やせる。ただし「計算する専門家は一部」という疎性と、「全専門家の重みはどこかへ保存しなければならない」という容量問題は別である。さらにrouterが特定の専門家へtokenを集中させると、あるGPUだけが重くなり、他GPUは待つ。

MoESysはこの問題を、訓練と推論で別々の実行機構に分けて扱う。訓練では **Elastic MoE** により不均衡なexpert workloadへ計算資源を合わせ、CPU/GPUなどの階層ストレージ（hierarchical storage）から必要なparameterを **二次元先読み（2D prefetch）** し、通信をまとめることでparameter待ちを隠す。

推論では「全modelがGPU VRAMへ入らない単一node」を対象に、CPU memoryとGPU memoryを一つの大きなring状のsection列として扱う。Modelを複数sectionへ分け、次に必要なsectionをloadしつつ、準備済みsectionの計算をround-robinで進める。GPUだけを高速階層、CPUを単なる倉庫として扱うのではなく、**CPU/GPUをまたいだmodel実行順そのものをpipeline化する**考え方である。

代表結果では、48基のA100で12B parameterのUFO MoEを8日間で訓練した。DeepSpeed比で訓練throughputは33%、一般的な推論throughputは13%向上し、特に専門家利用が不均衡なUFO条件ではthroughput 64%向上とmemory footprint 18%削減を報告している。

## 問題設定

### MoEの「疎な計算」は負荷の均一性を保証しない

Dense Transformerでは各tokenが同じFFNを通る。MoEではgate/routerがtokenごとに少数expertを選ぶため、理論的には計算量を抑えられる。しかしrouting先は入力依存なので、expert Aへ大量のtokenが集まり、expert Bにはほとんど来ないことがある。

ExpertをGPUごとに固定配置していると、この偏りはdevice間の仕事量差になる。最も忙しいGPUが終わるまで同期できないなら、空いているGPUがあってもstep全体は進まない。したがって「平均でexpert利用数が少ない」だけでは高throughputにならず、**load balanceと通信計算重畳**が必要になる。

### ParameterをGPU外へ置くと、次は転送待ちが律速になる

MoEは各tokenで使うexpertが少なくても、全expert weightの総量は大きい。GPU VRAMへ全parameterが入らない場合、CPU DRAMなどへ一部を置き、必要時に移す必要がある。

しかし計算直前になってparameter転送を始めるとGPUがI/O待ちする。逆にすべてを早めにprefetchすると、限られたGPU memoryを圧迫し、使わないexpertまで運ぶ可能性がある。MoESysは「いつ、どの方向の転送を先行させるか」と「どの資源でexpert計算を受け持つか」を同時に扱う。

## 手法のあらまし

訓練側の流れは、routingで生じるexpert負荷を観測し、Elastic MoEで仕事の持ち方を調整しながら、階層storageから次に必要なdataを2D prefetchする。通信はfusionして細かい転送・同期を減らし、parameter準備と計算をできるだけ重ねる。

推論側はより明確で、modelを複数のmemory sectionへ分ける。CPUとGPUのsectionをring状に並べ、あるsectionをGPUで計算している間に次sectionを準備する。計算が終わればbuffer/sectionの役割を順送りし、model全体をround-robinで通過させる。全weightを一度にGPUへ置く必要をなくしつつ、毎sectionで完全同期する単純offloadより転送を隠す。

## 手法

### 1. Elastic MoE — 不均衡routingを固定配置のまま受けない

入力は各expertへrouteされたtoken量である。固定expert parallelismでは、expertごとのtoken数が違っても各GPUの担当は変わらず、busy GPUとidle GPUが生まれる。

MoESysのElastic MoEは、この偏りを「MoE workloadは実行時に伸縮する」と捉える。目的は特定expertの過負荷がstep latencyを決める状況を緩和し、利用可能なdevice並列性をより均等に使うことである。

この機構が特に効くのはUFOのようにroutingが不均衡なtaskである。実際、論文のheadline resultでも一般条件よりunbalanced条件の改善幅が大きい。逆にroutingが元から均衡している場合、load-balance側の追加利得は小さくなる。

### 2. 二次元先読み（2D prefetch） — 二つのdata pathでparameter readinessを前倒しする

Offloadでは「必要なweightがGPUへ着くまで計算できない」ことが問題になる。MoESysは階層memory上で、次に必要になるdata movementを二方向に先行させる2D prefetchを使う。

重要なのは単純に多く読むことではなく、**現在の計算と、次のparameter転送の時間軸を重ねる**ことにある。準備が間に合えばGPUはstorage待ちせず次expertへ進める。

Prefetchが早すぎればmemoryを占有し、遅すぎればstallが残る。このため効果はCPU-GPU接続、GPU間接続、expert size、routing patternに依存する。論文の33% training throughput向上は、このoverlapを含むMoESys全体の効果として読むべきで、prefetch単体の倍率ではない。

### 3. Fusion communication — 小さな通信・同期をまとめる

MoEではexpert routingに伴う通信に加え、parameter移動やparallelism用の通信が発生する。小さなmessageや同期を個別に扱うと、payload以外の起動costが増える。

MoESysは通信をfusionして扱い、階層storageからのparameter readinessとcomputeを合わせてscheduleする。入力は複数の通信operation、出力はよりまとまったtransferである。狙いは通信byte数そのものだけでなく、通信起動と同期の回数を減らし、computeへ重ねやすくすることにある。

### 4. CPU/GPU memory ring — 「巨大modelを順番に載せ替える」推論をpipeline化する

単一node推論でmodelがGPU VRAMより大きい場合、MoESysはCPUとGPU memoryを複数sectionへ分割し、それらをringとして管理する。

概念的には、

`CPU section → GPU sectionで計算 → 次sectionをload → 使用済みsectionを再利用`

という流れを循環させる。Model graphの順序に従い、今必要なsectionをGPU側へ準備し、計算が終わったsectionのbufferを次のtransferへ回す。

これにより「layerごとにCPUから同期copyしてから計算」というstop-and-go型のoffloadを避け、transferとcomputeをpipelineとして扱う。出力modelは元と同じで、近似expertへ置換する方式ではない。

### 5. 訓練と推論で同じ問題を別の粒度から解く

訓練では多数GPUに跨るload imbalanceとcommunication overlapが中心で、推論では単一node上のcapacityとCPU-GPU transferが中心になる。MoESysという一つのsystem名の下にあるが、主機構は同一ではない。

そのため評価を読むときも、「training 33%」と「inference 13%」を同じ最適化の結果として混同しない方がよい。訓練のElastic MoE / 2D prefetchと、推論のmemory ringは異なるbottleneckへ効いている。

## 評価

### まず見るところ

- **大規模訓練:** 12B parameter UFO MoEをA100 ×48で8日間。
- **Training throughput:** DeepSpeed比 +33%。
- **Inference throughput:** DeepSpeed比 +13%（一般条件）。
- **Unbalanced UFO:** throughput +64%、memory footprint -18%。
- **評価の意味:** trainingの値はElastic MoE・prefetch・communication全体、inferenceの値はCPU/GPU memory ringを含むsystem比較。
- **品質:** 近似圧縮ではなくexecution/placement最適化なので、headline評価はmodel qualityではなくsystem efficiency。

### 代表的な評価結果

| 対象 | 条件 | 指標 | MoESysの結果 | 比較 |
|---|---|---|---:|---|
| 訓練 | 12B UFO MoE、A100 ×48 | 完了時間 | 8日 | system feasibility |
| 訓練 | 一般条件 | throughput | +33% | DeepSpeed比 |
| 推論 | 一般条件 | throughput | +13% | DeepSpeed比 |
| 不均衡MoE / UFO | routing imbalanceが大きい条件 | throughput | +64% | 比較system比 |
| 不均衡MoE / UFO | 同上 | memory footprint | -18% | 比較system比 |

### 何を示しているか

33%というtraining resultは、「MoEの疎性だけではなく、expert imbalanceとhierarchical-storage transferをscheduleする価値がある」ことを示す。特に不均衡条件で64%まで差が広がることは、Elastic MoEが狙うbottleneckと評価条件が対応している。

推論13%は、CPU/GPU memory ringでcapacity超過modelを動かしつつ、単純な逐次offloadよりtransfer stallを減らせることを示す。ただしabstractで公開される代表値だけからは、現代のPCIe 5.0/CXL/NVLink-C2C環境で同じ倍率になるとは言えない。

## 既存研究との差

DeepSpeed-MoEは大規模MoEのparallel training/inference基盤を提供するが、MoESysはさらに **不均衡expert workload** と **hierarchical storageからのparameter readiness** を主要なschedule対象へ入れる。

後年のMoE offload研究にはexpert cacheやrouting予測で「どのexpertをGPUへ残すか」を最適化するものが多い。それに対しMoESysは、request-level expert localityを予測するより前の世代の設計で、訓練ではprefetch/communication pipeline、推論ではmodel section全体のring executionを中心にする。

MoE-Infinityのような後続研究がexpert単位のcache/prefetchを深掘りするのに対し、MoESysは **訓練から推論までをhierarchical memoryの実行系として統合的に扱った点** が位置付けになる。

## 限界・実装状況

論文の中心評価はA100世代であり、CPU-GPU bandwidth、GPU memory容量、interconnect特性が現在のsystemとは異なる。2D prefetchやring executionの効果は、transfer/compute比が変わると大きく変動する。

またheadlineの推論結果は単一nodeのoversized modelを対象にする。Multi-tenant serving、continuous batching、KV cache pressure、modern MoEの非常に細かいexpert granularityなどは主要な評価軸ではない。

UFOのような不均衡routingでは大きく効く一方、均衡したroutingではElastic MoEの余地が小さい。逆に極端な偏りではprefetch predictionやcommunication scheduleが追いつかない可能性もあり、workload distribution依存性を持つ。

公開一次資料から公式code repositoryは確認できず、研究実装として扱う。

## 一般的な実装上の含意

MoE offloadでは「何GBをCPUへ逃がせるか」だけでなく、parameterが **いつreadyになるか** が重要である。GPUが必要とする瞬間より十分前にloadを始め、現在computeの裏へ隠せるなら、容量拡張がlatency増加へ直結しにくくなる。

またload imbalanceとmemory hierarchyは独立ではない。hot expertにtokenが集中すれば、そのexpertのcomputeだけでなく関連transferも集中する。したがってexpert placement、prefetch、communication fusionを別々のheuristicとして足すより、一つのruntime scheduleとして考える方が有効になり得る。
