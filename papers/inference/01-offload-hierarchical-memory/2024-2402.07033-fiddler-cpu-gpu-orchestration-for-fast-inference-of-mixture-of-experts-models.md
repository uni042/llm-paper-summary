# Fiddler: CPU-GPU Orchestration for Fast Inference of Mixture-of-Experts Models

> GPUに常駐しないexpertをCPUで直接計算し、重いweight transferをactivation転送へ置き換えるCPU–GPU協調MoE推論方式。

## 概要
Fiddlerは、GPU cache missしたexpertについて、**weightをGPUへ運ぶか、activationだけCPUへ送りCPUでexpertを計算するか**を実行時に選ぶMoE inference systemである。

全expert weightはCPU DRAMへ保持し、GPUにはdense / non-expert部分と人気expertだけを常駐させる。非常駐expertを毎回GPUへ持ってくる方式では、Mixtral expert一つが300 MB級あるため、token数が少ないdecodeではweight transferが計算時間より高くつく。

そこでFiddlerは、少数tokenならCPU計算、多数tokenならweightをGPUへ移してGPU計算、という**crossover point**をhardware profileから求める。CPUは単なるstorage tierではなく、AVX512-BF16 kernelを持つ第二のexpert executorとして扱われる。

## 手法のあらまし

Fiddlerを理解する上で重要なのは、**「CPU offload」ではなく「CPU execution」も選択肢に入っている**ことである。

### 1. まずGPUへ常駐させるexpertを決める

初期化時に、常に必要なnon-expert weightをGPUへ置き、残ったVRAMにcalibration dataで利用頻度の高いexpertを詰める。

この常駐集合はruntimeで毎token入れ替えるcacheというより、**事前に選んだhot expert resident set**に近い。

そのため入力分布がcalibration dataと似ていればhit率が高くなるが、domainが変わればhot expertの順位も変わり得る。

### 2. Gate後の`token count`がCPU/GPU選択のキーになる

MoE routerがexpertを選んだ後、各expertに何token割り当てられたかを数える。

Fiddlerではこの **expertごとのtoken count `s`** が実行先を決める中心的な変数になる。

理由は、CPUとGPUでcostの増え方が違うためである。

- CPU expert計算：token数が増えるほどほぼ線形に重くなる
- GPU expert計算：GEMM自体は速いが、非常駐expertでは数百MBのweight transferという固定costが乗る

そのため少数tokenではCPU、大量tokenではGPUへcross-overする点が存在する。

### 3. CPU経路：`activation movement`で済ませる

CPU実行を選んだ場合、GPUからCPUへ送るのはexpert weightではなくhidden activationである。

Mixtral expertのweightは3つの大きな行列で300 MB超になる一方、数token分のactivationははるかに小さい。

したがって、

`CPU → GPUへexpert weightを300MB級転送`

する代わりに、

`GPU → CPUへ少量activationを送る → CPUでexpert計算 → outputだけGPUへ返す`

方が短いdecodeでは有利になる。

Fiddlerの本質は、**weight movementをactivation movementへ置き換える**ことにある。

### 4. GPU経路：token数が多ければweight transferを償却できる

prefillやbeam searchのように同じexpertへ多数tokenが流れると、300 MB級weightを一度GPUへ持ってきても、その後の大きなGEMMで転送costを償却できる。

その場合はCPUで大量tokenを処理するより、weightを転送してGPUでまとめて計算する方が速い。

このためFiddlerは固定的に「miss expertはCPU」と決めず、**そのiterationのtoken countから毎回選ぶ**。

### 5. `Crossover threshold`はhardware profileから求める

CPU計算時間と、

`weight transfer + GPU expert compute`

の両方を事前にprofileし、token countに対するlatency modelを作る。

両者が交差するtoken数が実行切替thresholdになる。

このthresholdは普遍値ではなく、

- CPU core数 / AVX512性能
- PCIe Gen3 / Gen4
- GPU性能
- expert precision

で変わる。そのためhardwareを変えると再profileが必要になる。

### 6. CPU側の`AVX512-BF16 expert kernel`

通常のPyTorch CPU pathでは小さなMoE expertを十分速く処理できないため、FiddlerはAVX512-BF16を使う専用CPU expert kernelを実装している。

したがって論文のCPU経路の性能は「一般的なCPUなら同じ」とは限らない。特にAVX512-BF16を持たないCPUではcrossover pointがGPU側へ寄る可能性が高い。

### 7. CPUとGPUを並列に使う

同じlayer内でも、あるexpertはGPU、別expertはCPUで実行できる。

両方を並行させることで、GPUだけ・CPUだけのどちらかへ全負荷を寄せず、layer全体の完了時間を短くする。

ここが単純なCPU fallbackではなく **CPU-GPU orchestration** と呼ばれる理由である。

## 評価

### まず見るところ
- **結論:** miss expertを毎回GPUへ運ぶのではなく、少数tokenならCPUで直接計算するとweight transferを避けられる。
- **実速度:** 通常requestでは中程度の改善だが、long prefillやbeam searchでは大きな改善が出る。
- **品質:** native routerが選んだ同じexpertをCPU/GPUどちらかで計算するだけなのでlossless。
- **メモリ・I/O:** 全expertはCPU DRAM、GPUにはdense層＋hot expert。SSD/NVMeやKV offloadは対象外。
- **注意点:** CPU性能、AVX512-BF16、PCIe帯域、calibrationで選んだresident expertのhit率に強く依存する。

| Baseline | 主な方式 |
|---|---|

| Mixtral-Offloading | expert weightをGPUへ転送 |
| llama.cpp | CPU/GPU layer / weight offload系 |

### 通常のsingle-request

入力32 / 64 / 128 / 256、出力64 / 128 / 256 / 512などを評価。

| 比較 | 平均speedup |
|---|---:|
| vs llama.cpp | 1.26倍 |
| single-batch総括 | 1.26倍 |

通常decodeだけを見ると、Fiddlerは桁違いに速くなるわけではなく、主な価値はweight transferを避けられる条件にある。

### Long prefill

入力長512〜4096 tokenで評価。

| 比較 | TTFT改善 |
|---|---:|
| vs DeepSpeed | 1.07倍 |
| vs Mixtral-Offloading | 1.65倍 |

prefillではtoken数が多いためGPU経路が選ばれやすく、CPU/GPU切替の効果は「全部CPU」ではなく適切な分担として現れる。

### Beam search

beam width 4 / 8 / 12 / 16を評価。

| 比較 | speedup |
|---|---:|
| vs llama.cpp | **11.57倍** |

beamで同一stepのtoken数が増えるため、GPU GEMMの効率とCPU/GPU並列性を活かしやすい。

### 別workload / 別model

| 条件 | 結果 |
|---|---:|
| ShareGPT、vs llama.cpp | 1.81倍 |
| LMSYS-Chat-1M、vs llama.cpp | 1.56倍 |
| Phi-3.5-MoE、vs DeepSpeed | 平均6.5倍 |

### Hot expert resident setのhit率

| 環境 | Fiddler | Worst | Random配置 |
|---|---:|---:|---:|
| Environment 1 | 25.2% | 18.7% | 21.9% |
| Environment 2 | 53.0% | 44.6% | 48.8% |

Environment 2はVRAMが大きく、より多くのexpertを常駐できるためhit率も上がる。

一方、Fiddlerの効果はresident hitだけではなく、**miss時にCPU executionを選べること**にもある。

### 評価上の制約

- 主評価はsingle request中心。
- 全weightをCPU DRAMへ保持できる必要がある。
- CPU性能が弱いとCPU pathの利点が減る。
- AVX512-BF16専用kernelへの依存がある。
- calibration dataからhot expertを決めるためdomain shiftの影響を受ける。
- SSD / NVMe tier、KV cache offload、大規模continuous batchingは未評価。
