# HeteGen: Efficient Heterogeneous Parallel Inference for Large Language Models on Resource-Constrained Devices

> GPUに載らないlinear weightの一部をCPUで直接計算し、残りのweight転送・GPU計算と並行実行することで、batch=1の低遅延offload推論を高速化するCPU-GPU協調system。

## 概要

HeteGenは、GPU memoryにモデル全体が収まらない状況で、**CPUを単なるweight置き場にせず計算資源としても同時利用する**LLM inference systemである。

通常のweight offloadでは、CPU DRAMにあるweightを必要になるたびGPUへ転送する。このときPCIe帯域がGPU計算より大幅に遅いため、GPUがweight待ちになる。HeteGenは「そのweightをGPUへ送るよりCPUで直接計算した方が早い部分がある」と考え、linear layerのweightをCPU担当とGPU担当へ分割する。

CPU側のmatrix multiplication、GPUへ送るweightの転送、GPU側のmatrix multiplicationをできるだけ同時進行させ、CPU計算時間と「GPUへの転送＋GPU計算時間」が揃うように分割比率を決める。さらにGPU memoryに余裕がある場合は、効果の大きいweightからGPU常駐へ切り替える。

FlexGenが大batchでweight I/Oを多数requestへ償却してthroughputを高める方向なのに対し、HeteGenは**batch=1を中心としたinteractiveな低latency推論**を主対象にしている。

## 問題設定

論文ではOPT-30Bを例に、model memoryの97%以上をlinear moduleが占めると分析する。そのためHeteGenはKV cacheではなく、主にlinear weightの配置と実行を対象とする。

CPU DRAMはGPU VRAMより大容量だが、CPU→GPU転送は遅い。一方でCPU計算もGPUより遅いものの、PCIe転送より速い処理領域がある。このため全weightをGPUへ転送するより、**CPUで計算する部分とGPUへ送る部分を適切に分ける方が速くなる**というのが中心的な観察である。

SSD / NVMeは主評価では使わない。CPU DRAM ↔ GPU VRAMのweight offload研究として扱うのが正確である。

## 手法

### 1. CPUとGPUでlinear計算を分割する

HeteGenはtensor parallelismに近い形でlinear weightを分割し、一部をCPU、残りをGPUで処理する。

GPU担当weightはCPU DRAMから転送する必要がある一方、CPU担当weightはその場で計算できる。CPU計算とGPU側の転送・計算を並行させ、両者の完了時刻が近くなるようにするとidle timeを小さくできる。

論文ではCPU計算速度とCPU→GPU転送速度から理論的なGPU担当割合 `α` を導き、概ね

`CPU側の計算時間 ≈ GPU側weight転送時間 + GPU計算時間`

となる点を目標にする。GPU計算が非常に高速な場合は、実質的にCPU計算時間と転送時間の釣り合いが重要になる。

### 2. Linear moduleだけをheterogeneous executionにする

全operatorをCPU/GPU分割するのではなく、memoryの大部分を占めるQ/K/V/O projectionとFFNなどのlinear moduleを対象にする。LayerNormなどの小さいmoduleはGPUに残す。

これにより、細かなoperatorまで分散させる通信・管理overheadを避けながら、大きなweight transferだけを削減する。

### 3. Weightのpinning・転送・CPU計算を重ねる

CPU DRAMからGPUへ非同期転送するにはpinned memoryが必要だが、weightをpinする処理自体にも時間がかかる。

HeteGenは、

- 現在moduleのCPU計算
- 現在moduleで必要なweightのGPU転送
- 次module用weightのpinning

を別thread / CUDA streamで並行させる。つまり単に「転送とGPU計算を重ねる」だけでなく、**転送準備までpipeline化する**。

### 4. 実測からCPU/GPU分割比率を補正する

理論式だけではmatrix shapeやsystem状態による性能差を正確に表せないため、HeteGenは各moduleでCPU計算と転送時間を小範囲benchmarkする。

この結果から、CPU計算とcommunicationが最もよく釣り合う `α` を求める。論文ではこれをAlpha Benchmarkと呼ぶが、実質的には**hardware実測に基づいてCPU/GPU分担率を調整するprofile処理**である。

### 5. VRAMに余裕があれば高効果なweightをGPU常駐へ切り替える

最低memory構成では多くのlinearをCPU/GPU分割するが、VRAMが空いている場合まで毎回weightを転送する必要はない。

そこで各moduleについて、GPUへ常駐させた場合の「削減できる時間 / 消費VRAM」を計算し、効率の高いweightからGPUへ配置する。これにより、同じsystemが異なるVRAM予算へ連続的に対応できる。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA A10 24GB |
| CPU | Intel Xeon 2.30GHz、最大16 cores使用 |
| CPU-GPU | PCIe、実測約30GB/s |
| Model | OPT-6.7B / 13B / 30B |
| Batch size | 1 |
| Prefill length | 512 |
| Decode length | 64 |
| Baseline | DeepSpeed Inference、Hugging Face Accelerate、FlexGen |

HeteGenは低latencyを目的とするため、評価ではSSDへweightを置かずCPU DRAMまでのoffloadとしている。

### End-to-end

同程度のGPU memory使用量で比較すると、OPT-6.7B〜30Bの全条件でHeteGenがFlexGenを上回る。OPT-30Bでは最大で**FlexGen比317%のthroughput向上**を報告している。

またOPT-30Bで、HeteGenはGPU memory使用率6.5%〜88.7%の範囲へ配置を調整できたのに対し、論文中のFlexGen構成は6.5%〜26.5%に留まり、それ以上ではOOMになったとしている。

DeepSpeed InferenceはOPT-13B / 30BでOOMとなった。

### Ablation

全機能を100%とした相対performanceは以下。

| 無効化した機能 | Performance |
|---|---:|
| なし | 100% |
| CPU/GPUのhybrid実行なし | 77.7% |
| 非同期parameter管理なし | 94.9% |
| 実測による分担率補正なし | 92.8% |
| VRAM予算に応じたmodule配置なし | 32.1% |

特に、空きVRAMを使って有利なweightをGPU常駐化するschedulerの寄与が大きい。

## 既存研究との差

### FlexGenとの違い

FlexGenはweight / activation / KV cacheをGPU・CPU・SSDへ配置し、大きなeffective batchで同じweightを再利用して**offline throughput**を高める。一方HeteGenはbatch=1を中心に、weight転送そのものをCPU計算へ置き換え、**single-request latency**を減らす。

両者ともCPUを利用するが、FlexGenのCPU attentionは主にKV cache transfer削減、HeteGenのCPU計算は主にlinear weight transfer削減という違いがある。

### 単純CPU offloadとの違い

単純offloadではCPUはparameter storageとして使われ、weightをGPUへ送ってから計算する。HeteGenはCPU側にもlinear計算を残すため、PCIeを通るweight量そのものを減らす。

## 限界

- 実験はOPT系列と単一A10 GPUのみで、Llama系や現代的なGQA / MoEモデルでの実測はない。
- 主評価はCPU DRAM offloadであり、SSD / NVMe offload性能は示していない。
- CPU性能とPCIe帯域に強く依存し、CPUが弱い環境ではCPU担当を増やす利点が小さくなる。
- batch=1の低latency向け設計なので、大batch offline inferenceではFlexGen型scheduleの方が適する場合がある。
- 公式の公開コードは2026-09-06時点で確認できなかった。

## 一般的な実装上の含意

HeteGenから得られる重要な示唆は、offloadを「GPUに載らないweightをどこへ保存するか」だけで考えず、**転送するよりCPUで計算した方が安い部分は計算場所そのものを変える**べきだという点である。

CPU offload runtimeでは、固定のGPU layer数だけを決めるより、operator / matrixごとにCPU compute time・PCIe transfer time・GPU compute timeをprofileし、CPU実行とGPU転送を同時進行させる方が広いhardware構成へ適応しやすい。
