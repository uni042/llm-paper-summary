# HeteGen: Efficient Heterogeneous Parallel Inference for Large Language Models on Resource-Constrained Devices

> GPUに載らない線形 重みの一部をCPUで直接計算し、残りの重み転送・GPU計算と並行実行することで、バッチ=1の低遅延オフロード推論を高速化するCPU-GPU協調システム。

## 概要

HeteGenは、GPU メモリにモデル全体が収まらない状況で、**CPUを単なる重み置き場にせず計算資源としても同時利用する**LLM inference システムである。

通常の重み オフロードでは、CPU DRAMにある重みを必要になるたびGPUへ転送する。このときPCIe帯域がGPU計算より大幅に遅いため、GPUが重み待ちになる。HeteGenは「その重みをGPUへ送るよりCPUで直接計算した方が早い部分がある」と考え、線形 層の重みをCPU担当とGPU担当へ分割する。

CPU側の行列 乗算、GPUへ送る重みの転送、GPU側の行列 乗算をできるだけ同時進行させ、CPU計算時間と「GPUへの転送＋GPU計算時間」が揃うように分割比率を決める。さらにGPU メモリに余裕がある場合は、効果の大きい重みからGPU常駐へ切り替える。

FlexGenが大バッチで重み I/Oを多数リクエストへ分散してスループットを高める方向なのに対し、HeteGenは**バッチ=1を中心とした対話的な低遅延推論**を主対象にしている。

## 問題設定

論文ではOPT-30Bを例に、モデル メモリの97%以上を線形 モジュールが占めると分析する。そのためHeteGenはKV キャッシュではなく、主に線形 重みの配置と実行を対象とする。

CPU DRAMはGPU VRAMより大容量だが、CPU→GPU転送は遅い。一方でCPU計算もGPUより遅いものの、PCIe転送より速い処理領域がある。このため全重みをGPUへ転送するより、**CPUで計算する部分とGPUへ送る部分を適切に分ける方が速くなる**というのが中心的な観察である。

SSD / NVMeは主評価では使わない。CPU DRAM ↔ GPU VRAMの重み オフロード研究として扱うのが正確である。

## 手法

### 1. CPUとGPUでlinear計算を分割する

HeteGenはテンソル parallelismに近い形で線形 重みを分割し、一部をCPU、残りをGPUで処理する。

GPU担当重みはCPU DRAMから転送する必要がある一方、CPU担当重みはその場で計算できる。CPU計算とGPU側の転送・計算を並行させ、両者の完了時刻が近くなるようにすると待ち時間を小さくできる。

論文ではCPU計算速度とCPU→GPU転送速度から理論的なGPU担当割合 `α` を導き、概ね

`CPU側の計算時間 ≈ GPU側weight転送時間 + GPU計算時間`

となる点を目標にする。GPU計算が非常に高速な場合は、実質的にCPU計算時間と転送時間の釣り合いが重要になる。

### 2. Linear moduleだけをCPU/GPU分担の対象にする

全演算子をCPU/GPU分割するのではなく、メモリの大部分を占めるQ/K/V/O projectionとFFNなどの線形 モジュールを対象にする。LayerNormなどの小さいモジュールはGPUに残す。

これにより、細かな演算子まで分散させる通信・管理オーバーヘッドを避けながら、大きな重み 転送だけを削減する。

### 3. Weightのpinning・転送・CPU計算を重ねる

CPU DRAMからGPUへ非同期転送するにはpinned メモリが必要だが、重みをpinする処理自体にも時間がかかる。ここでpinned メモリは、OSが移動させないよう固定してGPUへ直接転送しやすくしたホスト メモリを指す。

HeteGenは、

- 現在モジュールのCPU計算
- 現在モジュールで必要な重みのGPU転送
- 次モジュール用重みをpinned メモリとして準備する処理

を別thread / CUDA ストリームで並行させる。つまり単に「転送とGPU計算を重ねる」だけでなく、**転送準備まで前倒しして同時進行させる**。

### 4. 実測からCPU/GPU分割比率を補正する

理論式だけでは行列 shapeやシステム状態による性能差を正確に表せないため、HeteGenは各モジュールでCPU計算と転送時間を小範囲ベンチマークする。

この結果から、CPU計算とcommunicationが最もよく釣り合う `α` を求める。論文ではこれをAlpha ベンチマークと呼ぶが、実質的には**ハードウェア実測に基づいてCPU/GPU分担率を調整する処理**である。

### 5. VRAMに余裕があれば高効果なweightをGPU常駐へ切り替える

最低メモリ構成では多くの線形をCPU/GPU分割するが、VRAMが空いている場合まで毎回重みを転送する必要はない。

そこで各モジュールについて、GPUへ常駐させた場合の「削減できる時間 / 消費VRAM」を計算し、効率の高い重みからGPUへ配置する。これにより、同じシステムが異なるVRAM予算へ連続的に対応できる。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA A10 24GB |
| CPU | Intel Xeon 2.30GHz、最大16 cores使用 |
| CPU-GPU | PCIe、実測約30GB/s |
| Model | OPT-6.7B / 13B / 30B |
| バッチ サイズ | 1 |
| プリフィル length | 512 |
| デコード length | 64 |
| 比較対象 | DeepSpeed Inference、Hugging Face Accelerate、FlexGen |

HeteGenは低遅延を目的とするため、評価ではSSDへ重みを置かずCPU DRAMまでのオフロードとしている。

### End-to-end

同程度のGPU メモリ使用量で比較すると、OPT-6.7B〜30Bの全条件でHeteGenがFlexGenを上回る。OPT-30Bでは最大で**FlexGen比317%のスループット向上**を報告している。

またOPT-30Bで、HeteGenはGPU メモリ使用率6.5%〜88.7%の範囲へ配置を調整できたのに対し、論文中のFlexGen構成は6.5%〜26.5%に留まり、それ以上ではOOMになったとしている。

DeepSpeed InferenceはOPT-13B / 30BでOOMとなった。

### 構成要素ごとの効果

全機能を100%とした相対性能は以下。

| 無効化した機能 | Performance |
|---|---:|
| なし | 100% |
| CPU/GPUのhybrid実行なし | 77.7% |
| 非同期パラメータ管理なし | 94.9% |
| 実測による分担率補正なし | 92.8% |
| VRAM予算に応じたモジュール配置なし | 32.1% |

特に、空きVRAMを使って有利な重みをGPU常駐化するスケジューラの寄与が大きい。

## 既存研究との差

### FlexGenとの違い

FlexGenは重み / 活性値 / KV キャッシュをGPU・CPU・SSDへ配置し、大きなバッチで同じ重みを多数リクエストへ使い回して**offline スループット**を高める。一方HeteGenはバッチ=1を中心に、重み転送そのものをCPU計算へ置き換え、**single-リクエスト 遅延**を減らす。

両者ともCPUを利用するが、FlexGenのCPU 注意は主にKV キャッシュ 転送削減、HeteGenのCPU計算は主に線形 重み 転送削減という違いがある。

### 単純CPU offloadとの違い

単純オフロードではCPUはパラメータ storageとして使われ、重みをGPUへ送ってから計算する。HeteGenはCPU側にも線形計算を残すため、PCIeを通る重み量そのものを減らす。

## 限界

- 実験はOPT系列と単一A10 GPUのみで、Llama系や現代的なGQA / MoE モデルでの実測はない。
- 主評価はCPU DRAM オフロードであり、SSD / NVMe オフロード性能は示していない。
- CPU性能とPCIe帯域に強く依存し、CPUが弱い環境ではCPU担当を増やす利点が小さくなる。
- バッチ=1の低遅延向け設計なので、大バッチ offline inferenceではFlexGen型実行計画の方が適する場合がある。
- 公式の公開コードは2026-09-07時点で確認できなかった。

## 一般的な実装上の含意

HeteGenから得られる重要な示唆は、オフロードを「GPUに載らない重みをどこへ保存するか」だけで考えず、**転送するよりCPUで計算した方が安い部分は計算場所そのものを変える**べきだという点である。

CPU オフロード ランタイムでは、固定のGPU 層数だけを決めるより、演算子 / 行列ごとにCPU 計算 時間・PCIe 転送 時間・GPU 計算 時間をprofileし、CPU実行とGPU転送を同時進行させる方が広いハードウェア構成へ適応しやすい。
