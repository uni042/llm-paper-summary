# Cost-Efficient LLM Serving in the Cloud: VM Selection with KV Cache Offloading

> SLO・モデル/入出力長・GPU価格/VRAM/帯域からKVオフロード率と実効TPSを予測し、AWS上で最も安価に要件を満たすVMを自動選択する。
## 書誌情報
- **著者**: Kihyun Kim, Jinwoo Kim, Hyunsun Chung, Myung-Hoon Cha, Hong-Yeon Kim, Youngjae Kim
- **著者・所属**: Sogang University; ETRI
- **公開**: arXiv:2504.11816v1
- **種別**: arXivプレプリント
- **対象**: KVキャッシュオフロード、クラウドLLMサービング、VM選択、SLO、コスト最適化
- **実装**: Python 3.10.14、NumPy 1.24.3、FlexGenを基盤とする公開ソフトウェア。
## 概要
クラウドLLM推論ではGPU価格・性能・VRAM・PCIe帯域がVMごとに異なり、KVキャッシュのオフロードは安価なGPUで大バッチを可能にする一方、転送遅延でSLOを破ることがある。InferSaveはモデル、入出力長、バッチ、予算、目標TPSからモデル・活性値・KV容量を計算し、各AWS GPU VMで必要なKVオフロード率を導出する。プリフィルとデコードの計算量・GPU/CPU転送量を式で予測し、理論FLOPSと実測差はVM別の線形Compute Time Calibration Functionで補正する。SLOを満たす候補のうちコスト効率最大のVMとオフロード構成を選ぶ。AWS T4/A10G/L4/L40s実測で、オンライン400 TPSではg4dn.xlargeを選び最大性能VMより73.7%低コスト、オフラインではKVオフロードを考慮することで最大約20%の節約を報告する。

InferSaveはユーザーの最大時間単価、対象モデル、平均入出力長、バッチサイズ、目標TPSを入力し、各VMで必要となるKVオフロード率をまずメモリ式から算出する。その率をプリフィル・デコードの転送時間モデルへ組み込み、モデル演算量から得る理論計算時間と合わせてVMごとのTPSを予測する。理論FLOPSは実LLM性能を正確に表さないため、T4/A10G/L4/L40sなどVMごとに事前測定した線形Compute Time Calibration Functionで計算時間を補正する。最後にSLOを満たさないVMを落とし、時間課金の切上げまで含むコスト効率指標で最良候補を選ぶ。これにより『オフロードするか』と『どのGPU VMを借りるか』を同じソルバで決める。

代表結果として、オンライン400 TPS費用はOPT-2.7B、バッチ 32、128入力/512出力、3000要求でMax-Performanceに対してg4dn.xlarge $0.71、620.17 TPS；g6e.xlarge $2.699に対し73.7%低コスト。SLO超過性能を買わず、必要性能を満たす最安側VMへ落とせる。
## 問題設定
クラウド上のLLM推論では、安価なGPU VMはVRAMが小さくKVキャッシュが収まらない一方、高価なVMを選べばSLOを大幅に超える性能を買ってGPU利用率と費用を無駄にする。KVキャッシュをCPUへオフロードすれば低価格VMでも長文・大バッチを処理できるが、プリフィル時のGPU→CPU書出しとデコード時のCPU→GPU読戻しがPCIe帯域を消費し、厳しいオンラインSLOでは逆効果になる。既存のクラウドLLM配置研究はGPU異種性やフェーズ分割を扱うがKVオフロードをVM選択と一体化せず、オフロード研究もどのクラウドVMを買うべきかまでは決めない。したがってモデル、バッチ、入出力長、SLO、VM価格、VRAM、FLOPS、転送帯域を同時に扱う必要がある。
## 新規性
InferSaveはユーザーの最大時間単価、対象モデル、平均入出力長、バッチサイズ、目標TPSを入力し、各VMで必要となるKVオフロード率をまずメモリ式から算出する。その率をプリフィル・デコードの転送時間モデルへ組み込み、モデル演算量から得る理論計算時間と合わせてVMごとのTPSを予測する。理論FLOPSは実LLM性能を正確に表さないため、T4/A10G/L4/L40sなどVMごとに事前測定した線形Compute Time Calibration Functionで計算時間を補正する。最後にSLOを満たさないVMを落とし、時間課金の切上げまで含むコスト効率指標で最良候補を選ぶ。これにより『オフロードするか』と『どのGPU VMを借りるか』を同じソルバで決める。
## 手法
### 手法のあらまし
第1段階では利用者から予算上限、対象モデル、平均入力長、平均出力長、バッチサイズ、目標TPSを受け取り、候補クラウドVMのGPU型、VRAM容量、理論演算性能、CPU-GPU転送帯域、時間単価を読み込む。第2段階ではモデルの層数、隠れ次元、注意ヘッド等から重み、活性値、全系列分KVキャッシュの必要容量を解析的に計算し、各VMのVRAMへ照合する。全状態が収まるVMはオフロード率0、モデル本体や実行に必要な最小KVすら置けないVMは不適格とし、中間候補ではモデルと活性値を置いた残りVRAMへKVを最大限残して不足分の比率をCPUオフロード率として求める。第3段階ではこの率を性能モデルへ渡す。プリフィルは各層で計算と新規KVのGPU→CPU書出しを重ねられると仮定して長い方を所要時間とし、デコードは各トークンで過去KVをCPU→GPUへ戻す転送が必要なため補正済み計算時間へ転送時間を加える。計算時間は理論FLOPSだけで決めず、各GPU VMで事前に複数バッチを実測して得た計算時間補正式（Compute Time Calibration Function; CTCF）の傾きと切片を適用する。これを全層・全出力トークンへ展開し、候補ごとの総遅延とTPSを予測する。第4段階ではTPSがSLO未満のVMを除外し、SLOを超える過剰性能は価値として水増ししないよう実効TPSを上限処理する。総トークン量からタスク時間を計算し、クラウド課金単位への切上げとVM時間単価を組み合わせて費用を算出し、SLOを満たす中で最も費用効率の高いVMを返す。出力には選択VMだけでなく予測TPS、必要KVオフロード率、予測費用、代替候補を含めるため、利用者は性能余裕と価格差を確認できる。オフロード率が高いほど安価な小容量GPUを使える一方、PCIe転送が増えてSLOを破る可能性が高まり、この相反を候補ごとに明示的に評価する。

### メモリ適合性とオフロード率推定
モデル重み、活性値、KVキャッシュをモデル構造とバッチ・系列長から解析的に計算し、各VMのVRAMへ照合する。まず重みと実行時活性値を常駐させた後にKVへ使える残容量を求める。総KVまで収まるVMはオフロード不要、モデル重み自体が入らないVMや少なくとも一層を実行するためのKV作業領域すら確保できないVMは候補から除外する。その中間ではGPUに保持できるKV量を総KV量から引き、CPUへ移す必要がある割合を0〜1のオフロード係数として算出する。係数はOOM回避の可否だけで終わらず、後段のプリフィル書出し量とデコード読戻し量へ直接入るため、安価な小容量VMほど増える転送ペナルティを定量化できる。入力長、出力長、バッチが変わればKV容量も変わるので、同じモデル・同じVMでもワークロードごとに率を再計算する。これにより『入る／入らない』の二値判定ではなく、どの程度CPU階層へ逃がせば成立するかを性能モデルへ接続する。

### オフロード込み性能モデル
プリフィルではLLM演算と生成KVのGPU→CPU書出しが並行できると仮定し、両者の長い方を1層時間とする。デコードでは過去KVをCPUからGPUへ戻す転送が計算に追加されるため、補正済み計算時間と転送時間の和で1トークン・1層時間を求める。線形層と自己注意のFLOP式、GPU理論FLOPS、双方向PCIe帯域、オフロード率、バッチ、入出力長を明示的に使い、全層・全出力トークンへ展開してTPSを算出する。これにより同じGPUでもオンライン短入力とオフライン長入力で異なるオフロード価値を表現する。

### 計算時間補正式
メーカー公称FLOPSをそのまま演算時間へ変換すると、LLMのメモリ律速、GPU利用率、プリフィルとデコードの演算形状差により実測とずれる。InferSaveは各AWS GPU VMで複数バッチを事前実行し、理論計算時間を実時間へ写す一次式alpha*T+betaを最小二乗で求める。OPT-2.7Bの例ではg4dn.xlargeのプリフィル平均誤差4.47%、g5.2xlarge 2.60%、g6.xlarge 2.23%となり、別検証ではT4デコード約1%、L4プリフィル約2%の誤差を報告する。この補正を候補VMごとに保存し、理論スペックだけによる誤選択を減らす。

### SLO制約付きコスト効率選択
予測TPSがユーザー指定SLOを下回るVMをまず除外し、残りについて実効TPSをmin(actual,SLO)として過剰性能を価値として数えない。バッチ総トークン数を実効TPSで割ってタスク時間を求め、クラウドの時間課金を表す切上げとVM時間単価を組み合わせてコスト効率を計算する。最大性能VMがSLOを大幅に超えても、その超過分は評価されないため安価なVMが選ばれ得る。オンライン400 TPSではT4のg4dn.xlarge、600 TPSではL4のg6.xlargeが選ばれ、用途に応じた価格性能点へ自動的に移る。

### 全体のデータ／制御の流れ
要求解析、メモリ適合性判定、KVオフロード率算出、プリフィル／デコード性能モデル、VM別CTCF、SLOフィルタ、コスト効率ランキングからなるPythonソルバ。
## 評価条件
- **ハードウェア**: AWS us-east-1のg4dn.xlarge/T4 16GB、g5.xlarge/A10G 24GB、g6.xlarge/L4 24GB、g6e.xlarge/L40s 48GB。論文記載価格は0.71、1.466、1.167、2.699ドル/時、PCIe帯域はT4 6GB/s、他3種12GB/s。
- **ソフトウェア**: Python 3.10.14、NumPy 1.24.3、FlexGenベースのInferSave。公開GitHub実装あり。
OPT-1.3B/2.7B/6.7Bを単一GPUでバッチ 1〜64評価。代表結果はOPT-2.7B、バッチ 32、最大予算3ドル/時。オンラインは入力128・出力512、3000要求、SLO 400/600 TPS。オフラインは入力1024・出力128、1000要求、SLO 100/200 TPS。各VMで3回測定し平均。2024年12月〜2025年3月、AWS us-east-1a〜1fへ分散して実施。
単一GPU VMを対象とし、マルチGPU・分散クラスタ最適化は扱わない。VM別CTCFは事前プロファイルを必要とし、評価はAWS 4種GPUとOPT系モデルが中心。
## 主要結果
InferSaveはSLOを満たす範囲で最大性能GPUより安価なVMを選び、オンライン400 TPSではg4dn.xlargeが620.17 TPSを0.71ドルで提供し、g6e.xlargeの2.699ドルに対して73.7%低コストとなる。600 TPSではg6.xlargeを選び56.75%低コスト。長入力のオフラインではKVオフロードにより低VRAM VMを候補に残し、100 TPSでg4dn.xlargeを選択して総費用2.13ドル、最大性能VMより約21%安く、200 TPSでも低価格VMを選択する。CTCFはT4デコード約1%、L4プリフィル約2%の予測誤差を示す。

- オンライン400 TPS費用 / g4dn.xlarge $0.71、620.17 TPS；g6e.xlarge $2.699に対し73.7%低コスト (比較対象: Max-Performance; 条件: OPT-2.7B、バッチ 32、128入力/512出力、3000要求) — SLO超過性能を買わず、必要性能を満たす最安側VMへ落とせる。

- オンライン600 TPS費用 / g6.xlarge $1.167、800.15 TPS；g6e.xlarge比56.75%低コスト (比較対象: Max-Performance; 条件: 同オンライン ワークロード) — SLOが厳しくなると選択VMをT4からL4へ引き上げる。

- オフライン100 TPS / g4dn.xlarge、100% KV オフロード、169.17 TPS、総費用$2.13 (比較対象: g6e.xlarge $2.699; 条件: 1024入力/128出力、1000要求) — 長入力ではKVオフロードを許すことで安価な16GB GPUを候補にできる。

- CTCF予測誤差 / g4dn.xlargeデコード約1%、g6.xlargeプリフィル約2% (比較対象: 実測時間; 条件: OPT-2.7B、512入力/128出力) — 公称FLOPSだけより実LLM性能に近いVM比較を可能にする。

- オフライン節約効果 / 論文全体でKV オフロード考慮により最大約20.19%、議論では条件により最大28%のコスト削減機会 (比較対象: オフロード非考慮/最大性能選択; 条件: 長入力バッチ ワークロード) — オフロードは全 ワークロードで有利ではなく、緩いSLOと長入力で特に価値が高い。

### 負の結果・境界条件
- オンラインの代表ワークロードではKV全量がGPUへ収まるため、オフロードを考慮しないInferSaveと最大性能方策が同じg6e.xlargeを選ぶ場合があり、オフロード自体は常に有益ではない。安価VMでオフロード率が高いと転送遅延により厳しいSLOを満たせず候補から外れる。

### 結果の読み方
KVオフロードの価値は単純なOOM回避ではなく、SLOに余裕がある時にVRAM容量の小さい安価GPUを使える選択肢を増やすことにある。性能予測へ転送費を入れることで、オフロード率を上げすぎてSLOを破る構成と、高性能すぎて費用を浪費する構成の双方を避ける。
## 品質への影響
同一モデルを同一精度で実行し、品質指標を変更しない。最適化対象はTPS/SLO、タスク完了時間、クラウド費用。
## 既存研究との差
Melange等はGPU異種性と要求特性から配置を選ぶがKVオフロードの容量・転送費を候補生成へ入れない。SplitWise/ThunderServeはプリフィル/デコードを別GPUへ分けるが高速相互接続を前提とし、一般的な単一VMの選択問題とは異なる。FlexGen等は所与のハードウェア上でオフロード実行を最適化するのに対し、InferSaveはオフロード率による性能低下を予測して『そのVMを借りるべきか』を決める上位層の資源選択器である。
## 限界
評価とソルバは単一GPU VMを前提とし、複数GPUや分散クラスタ、GPU間KV転送を含む配置最適化は未対応。性能モデルはVMごとのCTCF事前プロファイルに依存するため、新GPU、ドライバ、推論ランタイム、モデル族へ移る際は再測定が必要。評価モデルはOPT 1.3B/2.7B/6.7Bが中心で、MoEやGQAを持つ最新大規模モデルへの予測精度は未実証。クラウド価格も時点・地域依存であり、スポット価格や動的価格、起動待ち時間はモデル化していない。
## 実装状態
Python 3.10.14とNumPy 1.24.3で実装され、FlexGenのKVオフロードを利用する。完全なソースコードと関連ツールはGitHubのlass-lab/InferSaveで公開。AWS実機4 GPU VMで検証。
## 研究上の位置づけ
階層メモリ/オフロードをクラウド経済性へ接続する運用最適化研究。SSD/CPUオフロード技法そのものの帯域を改善するのではなく、転送帯域と容量を性能モデルへ組み込み、どのハードウェア階層をどのSLOで使うと費用対効果が高いかを決める。今後、NVMe帯域・SSD価格・量子化KV・複数GPUを変数へ加えれば、より広い階層メモリ配置ソルバへ拡張できる。
