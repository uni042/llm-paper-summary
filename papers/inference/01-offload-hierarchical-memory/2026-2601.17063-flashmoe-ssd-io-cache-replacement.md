# FlashMoE: Reducing SSD I/O Bottlenecks via ML-Based Cache Replacement for Mixture-of-Experts Inference on Edge Devices

> 全専門家重みをDRAMにも載せられない個人PC級環境で、MoEの専門家をNVMe SSDへ置き、実際に使う専門家だけをVRAMへ読み込む推論システム。SSD読出し回数を減らすため、単純なLRU/LFUではなく、各専門家の「最後に使ってからの時間」と「これまでの使用頻度」から次回利用までの遠さを小型ニューラルネットで予測し、将来使われにくい専門家から追い出す。

## 概要

FlashMoEが対象にするのは、**GPUのVRAMだけでなくCPUのDRAMにもモデル全体を置けない個人PC級の環境で、大規模な混合専門家モデル（Mixture of Experts; MoE）を動かす**という問題である。

MoEでは、全パラメータの大部分を多数の**専門家（expert）**と呼ばれるFFNが占める。ただし1トークンを処理するときに実際に使うのは、そのうちルータ（router）が選んだ少数の専門家だけである。

例えば1層に64専門家あって各トークンが2専門家だけを使うなら、その瞬間に必要なのは64個すべてではない。この疎性を利用すれば、使っていない専門家をGPU外へ置ける。

従来のMoEオフロード研究では、専門家をCPU DRAMへ置き、必要なものだけGPUへ送る方式が多い。しかしモデル全体が数十〜数百GB級になると、個人PCの32〜64GB程度のDRAMにも入りきらない。

そこでFlashMoEは、**SSDを専門家重みの最下位保存先として使う**。attention、normalization、routerなど常時必要な部分は起動時にメモリへ置き、専門家重みだけをlayer・expert単位のファイルとしてNVMe SSDへ保存する。実際にrouterが選んだ専門家だけをSSDから読み、VRAM上の小さな専門家cacheへ載せる。

このとき最大の問題になるのが**cache miss**である。必要な専門家がVRAMに残っていればそのまま計算できるが、なければSSDから読む必要がある。論文の環境では1専門家の読出しがおよそ3 msで、decode時間の70%以上が専門家loadになる条件もある。

したがってFlashMoEの中心課題は、「SSDを使えるようにすること」だけではなく、**どの専門家をVRAMへ残せばSSD読出し回数を最小化できるか**である。

## 問題設定

### なぜSSD容量が大きくても、そのままでは遅いのか

NVMe SSDは数TBまで安価に増やせるため、モデル容量問題には強い。しかしGPUから見ればVRAMやCPU DRAMよりはるかに遅い。

推論中に毎token、各MoE layerで必要expertをSSDから読み直すと、GPUの行列演算よりI/O待ちの方が長くなる。

このため実際の性能は、SSDの最大帯域だけでなく

`1回のexpert読出し時間 × cache miss回数`

に強く依存する。

FlashMoEの実機では専門家1個のloadが約3 msである。一方、後述するcache replacement用の小型ニューラルネット推論は約158 µsであり、十分に軽い。この差を利用し、少し賢いcache判断へ計算を使ってでもSSD missを減らす。

### Cache hit / missとは何か

VRAMに4専門家分だけ置けるとする。

```text
VRAM cache: [expert 2][expert 7][expert 11][expert 15]
```

次にrouterがexpert 7を選べば、すでにVRAMにあるので**cache hit**である。SSD I/Oは不要になる。

一方expert 20が必要なら**cache miss**で、SSDからexpert 20を読み込まなければならない。Cacheが満杯なら、4個のうちどれかを追い出す必要もある。

その「誰を追い出すか」がcache replacement policyである。

## 既存のcache policyが十分でない理由

### LRU — 最も長く使っていないものを追い出す

**最終使用時刻優先（Least Recently Used; LRU）**は、最後に使われてから最も時間が経ったexpertを追い出す。

直近に使ったものは近いうちに再利用されやすい、という時間的局所性を利用する。実装が簡単で高速だが、「昔よく使われていた人気expert」が少しの間使われないだけで追い出されることがある。

### LFU — 使用回数が少ないものを追い出す

**最少使用頻度優先（Least Frequently Used; LFU）**は、これまで使われた回数が少ないexpertを追い出す。

長期的な人気度を利用できるが、最近routing patternが変わった場合でも、昔の高頻度expertを長く残し続ける可能性がある。

LRUとLFUはそれぞれ、

- LRU: 最近性（recency）
- LFU: 頻度（frequency）

という一種類の情報しか見ない。

FlashMoEは両方を軽量モデルへ入れ、「このexpertは次にいつ使われそうか」を直接近似する。

## 手法のあらまし

FlashMoEの設計は大きく二部分からなる。

第一に、モデルを**常駐部分とSSD専門家部分へ物理的に分割**する。起動時にモデル全体を一度DRAMへ読む必要をなくし、専門家は必要時だけSSDから直接loadする。

第二に、VRAM上のexpert cacheで何を残すかを、学習済みの小型FFNで決める。

学習時には、将来のrouting traceをすべて知っている理想的cache policyを教師にする。実行時には未来は見えないので、現在まで観測できるrecencyとfrequencyだけからその判断を近似する。

## 手法

### 1. Expert / non-expertをファイル段階で分離する

通常のモデルcheckpointは、attention weight、normalization、router、全expert weightなどをまとめて保持している。

もしこの巨大checkpointを一度CPU DRAMへ展開してからexpertをSSDへ逃がすなら、起動時だけでもモデル全体がDRAMに入る必要がある。FlashMoEが狙う「DRAMにも入らないモデル」では成立しない。

そこで事前に、

- 常時必要なnon-expert weight
- `layer i / expert j`ごとのexpert weight

を別ファイルへ分割する。

起動時にはnon-expert部分だけを読む。Expertはrouterが必要としたときに、そのexpertファイルだけSSDからloadする。

この構成により、**モデル全体を一度もDRAMへ常駐させずに起動できる**。

### 2. Prefillでは同じexpertをtokenごとに何度も読まない

入力処理（prefill）では、多数tokenを一度に処理する。同じlayer内で複数tokenが同じexpertを選ぶことがある。

素朴にtokenごとにSSD loadすると、expert 5を10 tokenが選んだだけで同じweightを10回読むことになる。

FlashMoEは各layerで、batch内に選ばれた**一意なexpert集合**を先に求める。同じexpertは一度だけloadし、そのexpertへ割り当てられた複数tokenをまとめてMLPへ通す。

したがってprefillで必要なのは「token数 × expert load」ではなく、主に「そのlayerで実際に使われたunique expert数 × expert load」となる。

### 3. Decodeでは小さなexpert cacheをVRAMへ置く

逐次生成（decode）では1回に処理するtoken数が少なく、expert loadを大きなbatchへ償却しにくい。そのためSSD missがより直接latencyへ出る。

各MoE layerに一定数のexpert slotを用意し、最近または将来使いそうなexpertをVRAMへ保持する。

Cache容量はVRAM budgetに合わせて変える。Cache hitならexpert weightをそのまま使い、missならSSDから読み、必要なら既存expertを1個evictする。

### 4. Belady optimal policyを「未来を知っている教師」として使う

Cache replacementにおける理論的な理想の一つが**Belady最適法（Belady's optimal policy）**である。

未来のaccess列をすべて知っていると仮定し、cacheから追い出す必要が出たとき、**次に使われる時刻が最も遠いitem**を追い出す。

例えば今cacheにA/B/Cがあり、未来の利用順が

```text
A: 2 step後
B: 30 step後
C: 5 step後
```

と分かっていれば、Bをevictするのが最善である。

当然、実際のonline inferenceでは未来routingは分からないのでBeladyをそのまま使えない。FlashMoEはoffline routing trace上でBelady判断を計算し、それを**oracle教師**として小型モデルへ学ばせる。

### 5. 入力特徴はrecencyとfrequencyだけに絞る

各expertについて、

- **recency**: 最後に使われてから何access経過したか
- **frequency**: これまで何回routingされたか

を正規化して入力する。

モデルは3層の小型FFNで、hidden size 128、活性化関数はSiLU。各layer用モデルは約113 KBと非常に小さい。

目的は「routingそのものを予測する大規模モデル」を作ることではなく、cache miss時に数百µs以内でeviction候補を評価できることにある。

### 6. 学習では将来再利用距離を近似する

Routing traceを全て記録すれば、各expertが「次に何step後に使われるか」を後から計算できる。

Beladyが重視するのはこの**将来再利用距離（future reuse distance）**である。

FlashMoEはrecency/frequencyから将来再利用距離またはeviction優先度を近似し、次回利用が遠そうなexpertほど追い出しやすくする。

TriviaQAの512 sample、各最大512 tokenのrouting traceを使ってpolicyを作る。OLMoE-1B-7BではA100 1枚・batch 32でrouting trace取得が20分未満、feature生成・学習を含むpipeline全体が約2時間と報告される。

### 7. Policy推論をSSD I/Oと重ねる

Cache policyがSSD loadと同程度に遅ければ、hit率を上げても意味がない。

論文環境では

- 1 expert SSD load: 約3 ms
- cache policy推論: 平均158 µs

で、policyの方が一桁以上短い。

さらにpolicy推論をexpert I/Oと非同期に重ねることで、eviction判断の大部分をSSD待ち時間の裏へ隠す。

この設計により「賢いcache policyを入れたせいでCPU/GPU計算が新しいbottleneckになる」ことを避ける。

## 評価

### まず見るところ

- **主な利点**: SSDから読むexpert回数を減らし、decodeのI/O待ちを削減する。
- **OLMoE cache hit**: LRU比+21%、LFU比+51%。
- **I/O量**: LRU比22%、LFU比35%削減。
- **token生成速度**: cache policyだけをLRUから置換するとOLMoEで約22%、Qwen3で約7%向上。
- **cold start**: model全体を最初にDRAMへ通さない分割構成により初期loadを大幅短縮。
- **品質**: routerが選んだ本来のexpertを必ず実行する。Cache miss時は待ってSSDから読むだけなので、cache予測が外れても品質ではなくlatencyに効く。
- **注意**: 高速PCIe 5.0 SSD、単一desktop、約1GBへ制限したDRAMという特殊条件を含む。

## 主要結果の読み方

FlashMoEの中心は、SSD自体を速くすることではない。

SSDを使うと容量問題は解けるが、miss 1回のcostが大きいため、**どのexpertを残すかというcache decisionの価値がDRAM offloadより大きくなる**。

そのため、LRU/LFUのようなほぼ無料のpolicyより少し計算量が多くても、policy推論がSSD loadより十分短いなら採算が合う。

またBeladyを直接使っているわけではない点も重要である。Beladyは未来を知るためonlineでは実現不能であり、FlashMoEではあくまで「理想的なcache判断を作る教師」としてoffline利用する。

## 品質への影響

Cache policyは、routerがどのexpertを選ぶかを変更しない。

必要expertがVRAMにあれば即実行し、なければSSDから読み込んでから同じexpertを実行する。

したがって予測が外れた場合に増えるのはSSD待ち時間であり、近似expertへの置換やexpert skippingによるモデル品質低下は導入しない。

## 既存研究との差

- **Fiddler / DAOP**: 主にGPU↔CPU DRAM階層でexpertをoffloadする。FlashMoEは全expertがDRAMにも入らない条件を対象にSSDをlast-level model storeとする。
- **MoE-Infinity**: request全体のrouting patternや過去類似requestから将来expert利用を予測する。FlashMoEは各expertのrecency/frequencyという局所統計からBelady型evictionを学習する。
- **LRU / LFU / ARC / LeCaR**: 汎用cache replacement。FlashMoEはSSD expert missのcostが大きいMoE推論専用にoffline routing traceからpolicyを学習する。
- **LLM in a Flash**: dense FFNのactivation sparsityを使って必要weightだけflashから読む。FlashMoEは明示的なMoE expert routingを利用し、expert単位でcacheする。

## 限界

- 評価は高速なPCIe 5.0 NVMe SSDとRTX 5070 Tiを備えた単一desktopが中心。
- 低速SSD、別filesystem、別OS、PCIe世代で同じtrade-offになるとは限らない。
- Cache policyはTriviaQA routing traceから学習するため、domain shiftやrouting distribution変化への頑健性は十分検証されていない。
- Fiddler/DAOPはDRAM offloadを主眼とするため、約1GBへDRAMを制限した条件では設計上不利。この比較は厳しいmemory制約下でのsystem差として読む必要がある。
- Belady教師を作るためoffline routing trace収集と事前学習が必要で、完全training-freeではない。
- SSD耐久性、write amplification、複数request同時serving時のexpert cache interferenceは主要評価対象ではない。
- 公式公開実装は本文から確認できない。

## 一般的な実装上の含意

SSD expert offloadでは、最大シーケンシャル帯域だけを見ても性能を予測できない。

実際には、

1. 1 expertのload latency
2. 何回missするか
3. 同じexpertをどれだけ再利用できるか
4. replacement policyの計算cost
5. policy計算をI/Oへ重ねられるか

が重要になる。

特に、**I/O 1回が数ms、判断処理が数百µsなら、より高度なcache policyへ計算を使う余地がある**。

またexpert/non-expertをcheckpoint段階で分けておけば、起動時にモデル全体をDRAMへ通さず、cold startとmemory capacityの両方を改善できる。この点はSSD-backed MoE servingの実装設計として再利用しやすい。
