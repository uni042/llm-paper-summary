# TwinPilots：GPUとCPUの協調による大規模言語モデル推論

## 概要

TwinPilotsは、モデルの重みと鍵・値キャッシュ（KVキャッシュ）が画像処理装置（GPU）の高帯域幅メモリに収まらない状況で、中央処理装置（CPU）を単なる重みの保管先ではなく、GPUと並行する計算装置として扱う推論方式である。従来のオフロードはGPUが計算するために重みをホストメモリからPCI Express（PCIe）経由で読み込む。画像処理装置の演算器が速くても、PCIeの読み込みが支配的なら、演算器はデータ到着を待ち続ける。TwinPilotsは、ある演算の大きな重みをGPUへ運ぶ代わりに、CPUでその演算を済ませて小さな中間結果だけを転送する方が短時間になる場合を利用する。

Transformer層を7つの演算に分割し、各演算について中央処理装置実行時間と画像処理装置実行に必要な転送時間を測定する。これらを二つの実行装置の負荷均衡問題に置き換え、オフライン計画器がCPUとGPUの担当を決める。さらに画像処理装置へ常駐させる層を選び、現在層の計算、次層のデータ読み込み、前層のKVキャッシュ書き戻しを重ねる。SYSTOR 2024の査読済み最終版の公式概要は、NVIDIA A10G（24GB）とAMD EPYC 7R32（256GB）を用い、OPT/Llamaの13B・30B・33Bを評価して、既存方式比で推論処理量最大3.39倍、データ転送最大72.1%削減と報告する。

**版の注意：** 公開されている7ページの著者稿は、RTX 4090・Xeon Silver 4310、OPT-30B/66Bを使った別の評価構成で、最大3.21倍の処理量改善を報告する。以下では、正式版の公式概要から確認できる値と、著者稿のアルゴリズム・実験を明示的に分ける。著者稿の図表の数値を正式版の実測値として混用しない。

## 問題設定と動機

30B級モデルの重みだけでも数十GBを必要とし、画像処理装置のメモリ24GBでは保持できない。画像処理装置が次のTransformer層を実行するたびに重みやKVキャッシュをホストDRAMから移動すると、PCIe 4.0 x16の公称帯域32GB/sはGPU内部メモリの約1TB/sに比べて桁違いに小さい。大きな行列積の演算時間を減らしても、転送待ちが減らなければ次トークンを出すまでの時間は短くならない。

FlexGen型の方式は、多数の要求を層ごとにまとめて処理し、同じ重みを何度も利用することで全体処理量を高める。しかし層の切り替えを待つ要求が増えると、対話用途で重要な各利用者の応答間隔が長くなる。画像処理装置の計算と次層の転送を重ねるだけの方式も、画像処理装置の計算時間が転送時間より著しく短いと、隠蔽できる転送が少ない。著者らは、この非対称性を「画像処理装置演算を増やす」問題ではなく、「中央処理装置で計算する時間とGPUが必要とする転送時間の長い方を短縮する」問題として扱う。

中央処理装置側へ演算を移すことは万能ではない。中央処理装置が計算を担当しすぎれば、今度はCPU側が遅くなり画像処理装置を待たせる。反対にGPU側へ寄せすぎると、PCIeの転送時間が支配する。CPUにどの演算を任せるかは、演算ごとの重みの大きさ、CPUの実測計算時間、バッチ規模、PCIe帯域に応じて変わる。TwinPilotsはこの交換条件を、モデルの反復構造を利用して推論開始前に決める。

## 手法

### 1. Transformer層の7演算への分割

著者稿の表1では、Transformer層をQ・K・Vの三つの射影、注意得点計算（SCORE）、注意出力射影（OUT）、二段の多層パーセプトロン（MLP1、MLP2）に分割する。Q・K・Vは入力活性値とそれぞれの重み行列を掛ける処理であり、SCOREは過去の鍵・値を参照して注意出力を作る。OUTはその結果を出力射影し、MLP1とMLP2が次層へ渡す活性値を生成する。こうして分けると、たとえばQ・K・Vの重みは中央処理装置メモリに置いたままCPUで射影を計算し、生成した小さな活性値だけを画像処理装置へ送る配置を選べる。

重要なのは、演算の前後でデータ量が大きく変わることである。重み行列全体を転送する場合と、計算済みの小さな中間結果を渡す場合とではPCIeに流れるバイト数が異なる。著者稿の図5(a)は演算ごとの転送時間、中央処理装置計算時間、生成結果サイズを比較し、画像処理装置での計算時間よりデータ読み込みが長い演算があることを示す。したがって、GPUへの転送を回避できる演算を選ぶことが性能の主要な手段となる。

### 2. 負荷均衡の数理モデルと事前計画器

演算 i の中央処理装置計算時間を c_i、画像処理装置側のデータ読み込みを含む処理時間を g_i、CPU担当を示す二値変数を x_i とする。中央処理装置側の総時間は Σ c_i x_i、画像処理装置側の総時間は Σ g_i(1−x_i) であり、両者の最大値 λ を最小化する配置を選ぶ。制約は Σ c_i x_i ≤ λ、Σ g_i(1−x_i) ≤ λ、x_i∈{0,1} である。著者稿の第3.1節はこれを異種機械の負荷均衡問題として説明する。実際の演算依存関係は別途守らなければならず、この目的関数だけであらゆる転送・同期遅延が消えると主張してはいない。

著者稿のアルゴリズム1では、モデル構成、バッチ数、PCIe帯域、各演算の中央処理装置測定時間を入力し、画像処理装置側の転送費用を必要データサイズ／帯域から推定する。計画器が配置を出力した後は、各生成ステップで再探索せず、固定された演算配置に沿って実行する。これは層構造と復号手順が規則的であるために成立する設計である。一方、CPUやGPUの負荷が急変するオンライン環境で、要求ごとに最適配置を即座に更新する方式ではない。

### 3. GPU常駐層と作業領域の分離

著者稿の第3.3節は、画像処理装置のメモリの空き容量を「常時使う重み」と「その時点の層の作業領域」に分ける。まず先頭側の一部Transformer層を画像処理装置に固定し、これらの層は重み転送なしにGPUで計算する。固定しない層の重みはホストメモリに置き、前節の演算単位の中央処理装置/GPU分担を適用する。モデル全体がGPUに入らない場合でも、常駐層の重みを毎トークン転送しなくて済む。

埋め込み層については、重み行列のうち必要な行だけを参照する疎なアクセス特性を利用し、著者稿ではホストメモリからページ単位で直接参照する方式を採る。また著者稿では固定層・非固定層ともKVキャッシュをホストメモリに置くと説明する。これは画像処理装置の余剰容量を無制限にKVキャッシュへ割り当てる設計とは異なり、固定重みと各層の作業集合を中心に容量を管理する。メモリ容量を超えて固定層を増やすことはできないため、常駐層数と転送削減の間に制約がある。

### 4. 依存関係を守った非同期実行

著者稿のアルゴリズム2では、現在層の各演算を中央処理装置/画像処理装置の指定装置で実行する一方、次層のGPU担当演算が必要とする重みやKVキャッシュを先に読み込む。前層で生成したKVキャッシュのホスト側への書き戻しも別の転送系列として進める。Q・K・V、SCORE、OUT、MLPの間にはデータ依存があるため、必要な入力が未完成の演算は待機し、画像処理装置側の処理の終端では同期を行う。転送と計算を無条件に同時開始するのではなく、依存関係を満たす範囲で重ねる。

著者稿の図7は、画像処理装置だけで全演算を処理する配置、Q・K・VをCPUへ移す配置、さらにSCOREとOUTまでCPUへ移す配置を比較する。Q・K・Vだけを移した場合はGPUが必要とする大きな重み転送を減らしつつCPUの処理時間を転送の陰に隠せる。しかしSCOREとOUTまでCPUへ寄せるとCPUの総処理時間が長くなり、今度はCPU待ちが律速になる。この具体例が、中央処理装置への移動量を最大化するのではなく二つの処理時間を均衡させる理由である。

### 著者稿の図8における比較と機構の検証

著者稿の図8(a)は、バッチ数1、2、4、8、16、32を変えたOPT-30B/66Bの復号処理量を比較する。小さいバッチでは、TwinPilotsがFlexGen比最大3.19倍、DeepPlan比最大3.21倍の処理量を示す。バッチが大きいほど計算時間も増え、中央処理装置/GPU分担の選択余地が狭まるが、著者稿は提案する転送・計算の重畳によって比較方式を上回ると説明する。ここでの倍率は「どの条件でも3.21倍」ではなく、対象バッチ・モデルにおける最大値である。

図8(b)の応答間隔は、あるトークンを生成してから次のトークンを生成するまでの利用者別時間として定義される。TwinPilotsはFlexGen比最大68.7%、DeepPlan比最大68.9%短縮したと著者稿が報告する。処理量を上げるために多数の要求を層単位でまとめると個別応答が悪化し得るが、提案方式はCPUとGPUの負荷均衡によって一つの生成反復を短縮するため、処理量と応答間隔を同時に改善できるという主張を検証している。

図8(c)ではIntel PCMを用いてPCIe上の転送バイト数を測定する。著者稿の最大75.7%削減は生成トークン当たりの転送量であり、モデルのパラメータ数や画像処理装置のメモリ使用量が75.7%減るという意味ではない。転送削減には、CPUで演算して重みの移動を回避する効果と、固定層の重みを再転送しない効果が両方含まれる。したがってCPU演算配置だけの効果と、固定層による追加利得を区別する必要がある。

図8(d)は、CPU計算とGPU側の転送・計算の時間の均衡を調べる。OPT-30B/66Bのように重みがGPU容量を超える場合、GPUだけに演算を置くFlexGenは転送待ちが大きくなる。逆に注意得点計算だけをCPUへ移すFlexGen-CPUでは、各演算の転送費用とCPU時間を最適化した配置にはならない。TwinPilotsは7演算の費用を比較してCPUとGPUの完了時刻を近づけるため、律速側の待ち時間を削る。

構成要素の比較では、事前計画器のみを用い固定層を使わないTwinPilots-uと、両方を使う完全版を区別している。これにより、中央処理装置/GPUの担当変更による利得とGPU常駐層による追加の転送削減を混同せずに読める。またOPT-6.7Bのように重みがGPUに収まる場合、提案方式は全重みをGPUへ固定し、FlexGenと同等の性能になると説明する。CPUを使うこと自体が常に性能を高めるわけではないという負の条件である。

## 既存研究との比較

FlexGenはGPU・中央処理装置・場合によってはストレージ間で重みやKVを配置し、層をまとめて処理することで転送を複数要求へ償却する。TwinPilotsは層内の個々の演算について中央処理装置で直接計算するか画像処理装置へデータを送るかを選ぶため、単純な重みオフロードとは異なる。DeepPlanなど転送とGPU演算の重畳を重視する方式に対しても、重畳できるGPU演算時間が短いときにCPU側の有用な計算を増やす点が異なる。

HeteGenは線形層の重みをCPU担当部分とGPU担当部分へ分割する設計である。一方TwinPilotsの著者稿は、Q・K・V、SCORE、OUT、MLP1、MLP2という演算単位で担当装置を選び、データ依存関係を守りながら実行する。NEOやAPEXなど後続のオンラインCPU/GPU協調サービングは要求到着・バッチ変動に対する動的な判断を重視するが、TwinPilotsの核はモデルとバッチ条件を固定した事前計画と、GPU容量不足時のPCIe転送をCPU計算へ置き換える判断にある。

## 限界・負の結果・再現性

最大性能値は、画像処理装置のメモリに重み全体が収まらず、GPUへのデータ転送がCPU計算より相対的に重い条件で得られる。モデルが画像処理装置のメモリに収まるOPT-6.7Bの条件では、CPUへ仕事を割り振ることは必ずしも有益でなく、GPUに全重みを固定した配置が選ばれる。著者稿の図7が示すように、中央処理装置へ演算を移しすぎれば中央処理装置側の総時間が転送時間を超え、CPUが新しい律速となる。CPUの実効性能、PCIe帯域、バッチ規模の変化で最適配置は変わる。

事前計画器は規則的な復号手順を前提とし、要求到着や系列長が刻々と変わるオンライン負荷への適応性能は主な評価対象ではない。公開著者稿では入力896・出力128トークンを固定しているため、短文・超長文・出力長の分布ずれで同じ利得が得られるかは直接検証できない。CPUで演算を行うことによるCPUの電力、他のCPUサービスとの競合、複数GPUで同じホストメモリ帯域を共有したときの性能についても、確認した著者稿だけでは十分な定量評価を示せない。

公開著者稿は7ページであり、査読済み最終版は13ページ、画像処理装置・中央処理装置・モデルの評価構成も異なる。最終版の図表全体を直接照合できなかったため、最終版に固有の構成要素除去結果や最悪条件を推測して書いていない。著者稿の図8は転送量や負荷均衡の機構説明に使い、正式版の最大性能値はACMおよび所属機関の公式概要を出典として分けて記録した。公式実装コードの公開先は確認できないため、再現に必要な具体的なソース改変や実行コマンドは未確認とする。
