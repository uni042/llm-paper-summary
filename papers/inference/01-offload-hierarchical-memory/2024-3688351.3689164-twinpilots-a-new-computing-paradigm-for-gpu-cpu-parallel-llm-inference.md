# TwinPilots: A New Computing Paradigm for GPU-CPU Parallel LLM Inference

> Transformer layerをQ/K/V・attention・MLPなどへ分け、各処理をCPUで直接計算する時間とGPUへdataを運んで計算する時間を比較して実行先を決め、CPU計算とPCIe転送を同時進行させる推論system。

## 概要

TwinPilotsは、GPU memoryにLLM全体が収まらない環境で、CPUを単なるparameter置き場ではなく**GPUと並列に動く計算主体**として使う推論systemである。

一般的なCPU offloadでは、GPUに必要なweightやKV cacheをCPU memoryからPCIe経由で移す。このときGPU自体は高速でもdata待ちで何も計算できない時間が増えやすい。TwinPilotsは、ある処理について「大きなdataをGPUへ送ってGPUで計算する」より「CPUでそのまま計算して小さな中間結果だけ渡す」方が速い場合があることを利用する。

Transformer layerを複数の処理へ細分化し、処理ごとのCPU計算時間とGPU側のdata loadを含む処理時間から配置を決める。CPU側とGPU側の総処理時間を近づけることで、**CPU計算とGPU用data loadingを並行させ、1 tokenを生成するまでの待ち時間を短くする**ことを狙う。

## 問題設定

GPU memory不足時の推論では、parameterやKV cacheをCPU DRAMへ置けても、毎layerで大量dataをGPUへ読み込む必要があるとPCIe帯域がbottleneckになる。

一方、CPUはGPUよりmatrix multiplicationが遅いが、CPU上にある大きなweightをGPUへ転送する時間まで含めると、処理によってはCPUで直接計算した方が短い。さらにQ/K/V projectionなどでは、大きなweightを送る代わりにCPUで計算後の比較的小さなactivationだけを渡せる。

そこでTwinPilotsは、**CPUで直接計算する場合と、GPUへdataを運んで計算する場合を同じ候補として比較する**。

SSD / NVMeは主対象ではなく、CPU DRAMとGPU VRAMを使うCPU-GPU協調推論である。

## 手法

### 1. Transformer layerを処理単位へ分ける

論文ではlayerを主にQ、K、V、attention score、attention output、MLPの2段などへ分け、それぞれについて必要data、生成される中間result、CPU/GPU実行時間をprofileする。

layer全体ではなく細かく分けることで、たとえばQ/K/VだけCPUへ置き、残りをGPUで実行するといった配置が可能になる。

### 2. CPU実行とGPU実行のcostを比較する

GPU側costはkernel時間だけでなく、CPU memoryにあるweight / KV cacheをPCIe経由で読み込む時間も含める。CPU側costはその処理をhost CPUで直接計算する時間である。

CPUへ置けばPCIe trafficを減らせるがCPU処理時間は増えるため、単純にCPUへ多く移すほど良いわけではない。

### 3. CPU側とGPU側の総処理時間を近づける

TwinPilotsは各処理をCPU/GPUのどちらへ置くかを、**CPUとGPUの片方だけに仕事が偏らないよう分ける問題**として扱う。

事前測定から得た処理時間を使い、CPU側に割り当てた処理の総時間と、GPU側のdata loading + computeの総時間のうち、長い方がなるべく短くなる配置を求める。

LLM decodeは同じlayer構造を繰り返すため、毎token複雑な動的探索を行うのではなく、model・batch size・sequence lengthに応じたplanを事前に用意して使う。

### 4. 現在の計算で使わないVRAMもcacheに使う

model全体はVRAMに収まらなくても、ある瞬間の計算で本当に必要なtensorはmodel sizeよりはるかに小さい。TwinPilotsは残ったVRAMへ再利用価値の高いweightやKV dataを保持し、不要なtransferを減らす。

### 5. Data loading・KV書き戻し・computeを同時進行させる

現在layerをCPU/GPUで計算している間に、次layerでGPU実行する処理のdataを読み込み、前layerで生成されたKV cacheを書き戻す。

これによりCPU compute、GPU compute、CPU↔GPU data movementを可能な範囲で同時進行させる。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA A10G 24GB |
| CPU | AMD EPYC 7R32 |
| CPU memory | 256GB |
| Model | OPT / Llama |
| Model size | 13B / 30B / 33B |
| 実装 | PyTorch |

SYSTOR 2024最終版の公式abstractでは、当時の主要な既存方式に対して**推論throughput最大3.39倍**、**CPU↔GPU data transfer最大72.1%削減**を報告している。

性能向上の中心はCPU自体を高速化することではなく、大きなweight / KV dataを毎回PCIeで移す代わりに、CPUで一部処理を実行して小さな結果だけをGPU側へ渡し、data loadingとCPU computeを重ねられる点にある。

著者稿には異なるhardware・数値が残るversionも流通しているため、本ページの代表評価値はACM/SYSTOR最終版の3.39倍 / 72.1%を採用する。

## 既存研究との差

### FlexGenとの違い

FlexGenはGPU / CPU / SSDのtensor配置と大batchの計算順を最適化して、weight I/Oを多数requestへ分散するoffline throughput志向である。

TwinPilotsはCPUを積極的な計算主体として使い、**処理ごとにCPU computeとGPUへのdata transferのどちらが安いかを比較する**。CPUで計算した方が安い処理では、weightをGPUへ送ること自体を避ける。

### HeteGenとの違い

HeteGenは主にlinear weightをCPU担当部分とGPU担当部分へ分割し、同じlinear operationをCPU/GPUで分担する。

TwinPilotsは処理そのものを単位にCPU/GPUへ割り当てるため、Q/K/V、attention、MLPなど異なる処理間で負荷を分ける設計である。

### NEO / APEXとの違い

NEO / APEXはonline servingでrequest単位にKV cacheとdecode attentionをCPUへ移し、毎iterationの負荷に応じて動的にCPU/GPUを使う。

TwinPilotsはより前段の研究で、規則的なdecode workloadをprofileして**処理の実行先を事前計画する**方向が中心である。

## 限界

- 最終版の評価は単一A10G + host CPUを中心としており、H100級GPUやmulti-GPUでの効果は十分示されていない。
- CPU/GPU配置はprofiling結果に依存し、batch sizeやsequence length、hardware構成が変わるとplanを作り直す必要がある。
- online servingのrequest arrivalや不規則なoutput lengthへ毎iteration適応するschedulerではない。
- CPU compute性能とPCIe bandwidthの比率によって最適配置が大きく変わる。
- 2026-09-07時点で公式code repositoryは確認できなかった。

## 一般的な実装上の含意

TwinPilotsの重要な示唆は、CPU offloadを「GPUで計算するためのdata置き場」とだけ考えないことである。**data transfer時間まで含めてcostを比較すると、CPUで直接計算した方が速い処理が生じる**。

そのためCPU/GPU協調runtimeでは、処理ごとにCPU compute、GPU compute、PCIe transferをprofileし、転送byteだけでなく**1 tokenの処理完了までにかかる総時間**が小さくなる実行先を選ぶ設計が有効である。
