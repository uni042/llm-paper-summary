# TwinPilots: A New Computing Paradigm for GPU-CPU Parallel LLM Inference

> TwinPilotsはTransformer処理ごとにCPU計算とGPU転送・計算の速さを比較し、CPU計算とPCIe転送を並行させてGPUオフロードの生成待ちを減らす。

## 概要

TwinPilotsは、GPUメモリにLLM全体が収まらない環境で、CPUを単なるパラメータ置き場ではなく**GPUと並列に動く計算主体**として使う推論システムである。

一般的なCPUオフロードでは、GPUに必要な重みやKVキャッシュをCPUメモリからPCIe経由で移す。このときGPU自体は高速でもデータ待ちで何も計算できない時間が増えやすい。TwinPilotsは、ある処理について「大きなデータをGPUへ送ってGPUで計算する」より「CPUでそのまま計算して小さな中間結果だけ渡す」方が速い場合があることを利用する。

Transformer層を複数の処理へ細分化し、処理ごとのCPU計算時間とGPU側のデータ 読み込みを含む処理時間から配置を決める。CPU側とGPU側の総処理時間を近づけることで、**CPU計算とGPU用データ 読み込みを並行させ、1トークンを生成するまでの待ち時間を短くする**ことを狙う。

SYSTOR 2024最終版の公式abstractでは、既存方式比で推論スループット最大3.39倍、CPUとGPU間のデータ転送72.1%削減を報告する。

## 問題設定

GPUメモリ不足時の推論では、パラメータやKVキャッシュをCPU DRAMへ置けても、毎層で大量データをGPUへ読み込む必要があるとPCIe帯域がボトルネックになる。

一方、CPUはGPUより行列 乗算が遅いが、CPU上にある大きな重みをGPUへ転送する時間まで含めると、処理によってはCPUで直接計算した方が短い。さらにQ/K/V projectionなどでは、大きな重みを送る代わりにCPUで計算後の比較的小さな活性値だけを渡せる。

そこでTwinPilotsは、**CPUで直接計算する場合と、GPUへデータを運んで計算する場合を同じ候補として比較する**。

SSD / NVMeは主対象ではなく、CPU DRAMとGPU VRAMを使うCPU-GPU協調推論である。

## 手法

### 1. Transformer layerを処理単位へ分ける

論文では層を主にQ、K、V、注意機構 score、注意機構 出力、MLPの2段などへ分け、それぞれについて必要データ、生成される中間結果、CPU/GPU実行時間をプロファイルする。

層全体ではなく細かく分けることで、たとえばQ/K/VだけCPUへ置き、残りをGPUで実行するといった配置が可能になる。

### 2. CPU実行とGPU実行のcostを比較する

GPU側コストはカーネル時間だけでなく、CPUメモリにある重み / KVキャッシュをPCIe経由で読み込む時間も含める。CPU側コストはその処理をホスト CPUで直接計算する時間である。

CPUへ置けばPCIe 通信量を減らせるがCPU処理時間は増えるため、単純にCPUへ多く移すほど良いわけではない。

### 3. CPU側とGPU側の総処理時間を近づける

TwinPilotsは各処理をCPU/GPUのどちらへ置くかを、**CPUとGPUの片方だけに仕事が偏らないよう分ける問題**として扱う。

事前測定から得た処理時間を使い、CPU側に割り当てた処理の総時間と、GPU側のデータ 読み込み + 計算の総時間のうち、長い方がなるべく短くなる配置を求める。

LLMデコードは同じ層構造を繰り返すため、毎トークン複雑な動的探索を行うのではなく、モデル・バッチ 大きさ・系列 長さに応じた計画を事前に用意して使う。

### 4. 現在の計算で使わないVRAMもcacheに使う

モデル全体はVRAMに収まらなくても、ある瞬間の計算で本当に必要なテンソルはモデル 大きさよりはるかに小さい。TwinPilotsは残ったVRAMへ再利用価値の高い重みやKVデータを保持し、不要な転送を減らす。

このキャッシュ領域が効くのは、直後の層や次の生成反復で同じ重み・KV状態を再利用できる場合である。CPUで計算する処理を増やしてGPUへ送る重みを減らしても、GPU側に残したデータがすぐ追い出されればPCIe転送は再発する。そこで計算に必須な作業領域を確保した残りだけを再利用用へ回し、保持できたデータについては次回のCPU→GPU転送を丸ごと省く。つまりTwinPilotsのGPUメモリ利用は、単なる容量不足対策ではなく、CPU実行で削った転送量とGPU側再利用を組み合わせて転送待ちをさらに減らす役割を持つ。

### 5. Data loading・KV書き戻し・computeを同時進行させる

現在層をCPU/GPUで計算している間に、次層でGPU実行する処理のデータを読み込み、前層で生成されたKVキャッシュを書き戻す。

これによりCPU計算、GPU計算、CPU↔GPUデータ 移動を可能な範囲で同時進行させる。

性能向上の中心はCPU自体を高速化することではなく、大きな重み / KVデータを毎回PCIeで移す代わりに、CPUで一部処理を実行して小さな結果だけをGPU側へ渡し、データ 読み込みとCPU計算を重ねられる点にある。

著者稿には異なるハードウェア・数値が残るversionも流通しているため、本ページの代表評価値はACM/SYSTOR最終版の3.39倍 / 72.1%を採用する。

## 既存研究との差

### FlexGenとの違い

FlexGenはGPU / CPU / SSDのテンソル配置と大バッチの計算順を最適化して、重み I/Oを多数リクエストへ分散するオフラインスループット志向である。

TwinPilotsはCPUを積極的な計算主体として使い、**処理ごとにCPU計算とGPUへのデータ 転送のどちらが安いかを比較する**。CPUで計算した方が安い処理では、重みをGPUへ送ること自体を避ける。

### HeteGenとの違い

HeteGenは主に線形重みをCPU担当部分とGPU担当部分へ分割し、同じ線形 operationをCPU/GPUで分担する。

TwinPilotsは処理そのものを単位にCPU/GPUへ割り当てるため、Q/K/V、注意機構、MLPなど異なる処理間で負荷を分ける設計である。

### NEO / APEXとの違い

NEO / APEXはオンライン 提供でリクエスト単位にKVキャッシュとデコード 注意機構をCPUへ移し、毎反復の負荷に応じて動的にCPU/GPUを使う。

TwinPilotsはより前段の研究で、規則的なデコードワークロードをプロファイルして**処理の実行先を事前計画する**方向が中心である。

## 限界

- 最終版の評価は単一A10G + ホスト CPUを中心としており、H100級GPUやmulti-GPUでの効果は十分示されていない。
- CPU/GPU配置はprofiling結果に依存し、バッチ 大きさや系列 長さ、ハードウェア構成が変わると計画を作り直す必要がある。
- オンライン 提供のリクエスト 到着や不規則な出力 長さへ毎反復適応するスケジューラではない。
- CPU計算性能とPCIe帯域の比率によって最適配置が大きく変わる。
- 2026-09-07時点で公式code repositoryは確認できなかった。

## 一般的な実装上の含意

TwinPilotsの重要な示唆は、CPUオフロードを「GPUで計算するためのデータ置き場」とだけ考えないことである。**データ 転送時間まで含めてコストを比較すると、CPUで直接計算した方が速い処理が生じる**。

そのためCPU/GPU協調ランタイムでは、処理ごとにCPU計算、GPU計算、PCIe 転送をプロファイルし、転送バイトだけでなく**1トークンの処理完了までにかかる総時間**が小さくなる実行先を選ぶ設計が有効である。
