# DASH: Beyond Capacity: Scalable MoE LLM Inference via High-Bandwidth Flash with Direct GPU and HBM Paths

> High-Bandwidth FlashからexpertをGPU／HBMへ直接供給し、従来NVMeを超える大容量MoE推論を狙う階層メモリ設計。

## 概要
DASHは、将来の **HBF（High-Bandwidth Flash）** をGPU近傍の大容量memory tierとして使うMoE向けarchitectureである。

通常NVMeのようにCPU / PCIe software stackを経由するのではなく、UCIeでGPU I/O die・HBM base die・HBF base dieを近距離接続し、expert weightをHBFから供給する。HBF→GPUの`Direct path`と、HBF→HBM base die→GPUの`Relay path`をexpertごとに使い分け、両方を同時に動かす。

またKV cacheも同じHBF/HBM階層で扱うが、weightとKVのtraffic patternは別に最適化する。現時点で実HBF siliconは存在しないため、GPU kernel timingのみH100で実測し、HBF / UCIe / NAND部分はevent-driven simulatorで評価している。

## 手法のあらまし

DASHでは `Direct / Relay path`、`HBF transfer region`、`Lookahead Expert Execution`、KVの`direct write / coalesced writeback`が主要概念になる。

### 1. `HBF`：SSDよりGPU memoryに近いflash tierを想定する

HBF（High-Bandwidth Flash）は通常のNVMe SSDを高速化しただけの前提ではない。

多数NAND die / planeを並列化し、base die側にlogicとSRAMを持たせ、UCIe経由でHBM / GPU近傍へ接続する想定である。

論文の基本構成では、

- HBF: 2 × 512 GB
- HBM: 2 × 24 GB
- D2D link: usable 1.6 TB/s級

を想定する。

したがって、現行NVMeの3〜10 GB/s級readと直接比較するのは適切でない。

### 2. `Direct Path`：HBFからGPUへ直接送る

Directではexpert weightをHBF base dieからGPU I/O側へ直接transferする。

利点はHBMを経由せず、relay copyとHBM bandwidth消費を避けられること。

一方でNAND read latencyのばらつきをGPU側が直接受けやすく、read completionが遅れるとGPU stallになりやすい。

### 3. `Relay Path`：HBM base dieをbufferとして使う

Relayでは、

`HBF → HBM base die → GPU`

の経路を使う。

HBM側bufferがNAND read timingのばらつきを吸収しやすい一方、HBM bandwidthとbuffer capacityを消費する。

つまり、

- Direct = pathは短いがflash latencyの影響を受けやすい
- Relay = 1段増えるがbufferingしやすい

というtrade-offがある。

### 4. ExpertごとにDirect / Relayを分けて両方同時に使う

DASHの中心は、全expertをDirectまたはRelayの一方へ固定することではない。

各expertのread timing / transfer conditionを見てpathを割り当て、**DirectとRelayを並列に使ってaggregate bandwidthを上げる**。

同じexpert weightを二重複製する必要はなく、expert単位でどちらかの経路を担当させる。

比較baselineの`DirectOnly` / `RelayOnly`は、この二経路併用の効果を分離するための構成である。

### 5. `Transfer Region`：HBF base dieのSRAMでdouble bufferする

HBF base dieには18 MiB SRAM、usable 16 MiBを想定し、8 MiBずつ二つのtransfer regionへ分ける。

一方をGPUへ送っている間に、もう一方へNANDから次dataをreadするdouble-buffer構成で、NAND sensing latency `tR` を隠す。

ここでのbufferはexpert cacheではなく、**flash page readとD2D transferをpipelineするための短期SRAM staging area**である。

### 6. `Lookahead Expert Execution`：router条件を満たすmodelだけ早期にexpertを決める

一部MoE routerでは、expert rankingに使う項のうち入力依存部分を早めに計算できる。

DASHの **Lookahead Expert Execution** は、その条件を満たすrouterについて通常のtop-k確定より前にexpert候補を決め、HBF readをoutput projectionなどと重ねる仕組みである。

ただしこれはどのMoEでも使える一般predictorではない。

論文は **scale-invariantかつexpert biasなし** などのrouter条件を要求し、条件を満たさないmodelではlookaheadを使えない。

### 7. KV cacheはweightと別のwrite policyにする

expert weightはread-mostlyだがKVはgeneration中に増え続けるため、同じflash policyでは扱わない。

DASHでは、

- prefill KV：大きいためpage-alignedにHBFへdirect write
- decode KV：小さい更新をHBMへ一旦蓄積し、大きなwriteへまとめてHBFへwriteback

とする。

小さなdecode writeを毎token NANDへ出すとprogram latencyとreadが競合するため、**HBMをwrite coalescing bufferとして使う**。

### 8. WeightとKVのerase blockを分ける

HBF上でweight-owned blockとKV-owned erase blockを分離し、KV更新のgarbage collectionでread-mostlyなmodel weightを巻き込んで移動しないようにする。

これはflash固有のwrite amplification / GC問題を、LLM data typeごとに分離する設計である。

## 評価

### まず見るところ
- **結論:** HBFのDirect / HBM Relayをexpertごとに併用すると、一経路だけの構成よりthroughputをほぼ2倍へ伸ばせるというsimulation結果。
- **実速度:** 5モデル幾何平均でRelayOnly比1.90倍、DirectOnly比1.84倍。ただし現行SSD実機の結果ではない。
- **品質:** expert / KVの計算内容は変えず配置・経路だけを変えるためlossless。
- **メモリ・I/O:** **HBF + UCIe + HBM**という将来hardware前提。通常NVMe / CPU DRAM offloadとは分離して読む必要がある。
- **注意点:** HBF silicon、UCIe data path、NAND enduranceはsimulation / projectionであり、製品実測値ではない。

### 5モデル幾何平均

| 比較 | Throughput | E2E latency |
|---|---:|---:|
| DASH vs RelayOnly | **1.90倍** | **42.2%減** |
| DASH vs DirectOnly | **1.84倍** | **40.8%減** |

一経路を高速化したのではなく、**二つのdata pathを同時利用してflash read / transferの偏りを減らした効果**として読むべき結果である。

### 大きなKV cacheを持つ条件

Llama 4 MaverickでKV cacheを約197.4 GBまで拡張。

| KV配置 | 容量 |
|---|---:|
| HBF側 | 172.96 GB |
| HBM decode KV | 24.46 GB |

この条件でもRelayOnly比でthroughput 1.92倍、latency 48.0%減を報告する。

### Continuous batching

Qwen3、prompt 4K、decode 128、`Bmax=32`、512-token chunkで評価。

RelayOnly saturationの75%負荷時：

| 指標 | RelayOnly | DASHの削減率 |
|---|---:|---:|
| P90 E2E | 28.847 s | **53.5%減** |
| TPOT | 148 ms | **62.2%減** |

### CPU-GPU Hybrid oracleとの比較

Xeon 8452Y上のshape-equivalent expertを使ったCPU-GPU hybrid oracleに対してDASHは8.22〜12.32倍高速とする。

ただしこれは**実CPU system対、仮想HBF architecture**の比較なので、現行hardware同士のbenchmarkとして扱わない方がよい。

### Simulator validation

| 項目 | 値 |
|---|---:|
| GPU timing実測数 | 1107 |
| Timing model中央値誤差 | 0.51% |

GPU compute部分は実測で校正されているが、HBF / UCIe / NAND subsystem全体が実機化されたわけではない。

### NAND / enduranceの仮定

read latency `tR`、program latency、D2D bandwidth、page sizeをsweepする。endurance 0.645年という値も示されるが、これはSLC 100k P/E、WAF=1、duty=1等を置いたprojectionであり製品保証値ではない。

### 評価上の制約

- HBF siliconは未実装。
- UCIe / base-die pathもsimulation。
- 現行NVMe SSDのqueue / filesystem / PCIe software stackとは前提が異なる。
- Lookaheadはrouter構造に制約がある。
- enduranceは仮定に基づくprojection。
- 実機でのthermal / power / firmware影響は未検証。
