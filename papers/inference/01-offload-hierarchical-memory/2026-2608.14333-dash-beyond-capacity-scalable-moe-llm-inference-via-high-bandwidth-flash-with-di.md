# DASH: Beyond Capacity: Scalable MoE LLM Inference via High-Bandwidth Flash with Direct GPU and HBM Paths

> 通常SSDよりはるかに高帯域な将来型FlashをGPU/HBMの近くへ接続し、expert weightをGPUへ直接送る経路とHBMをbufferにする経路を同時利用して、大容量MoEのweight転送待ちを減らす設計。

## 概要
DASHは、将来の **HBF（High-Bandwidth Flash）** をGPU近傍の大容量memoryとして使うMoE向けarchitectureである。HBFは通常NVMe SSDより多くのNANDを並列に動かし、GPU/HBMの近くへ高速linkで接続することを想定したFlashで、2026-09時点では製品化済みhardwareではない。

通常NVMeのようにCPUやOSのstorage処理を経由するのではなく、**UCIeというchip間高速linkでGPU側・HBM側・HBF側のchipを直接つなぐ**。expert weightは、HBFからGPUへ直接送る経路と、HBFから一度HBM側bufferへ入れてからGPUへ送る経路をexpertごとに使い分け、両方を同時に動かす。

またKV cacheも同じHBF/HBM階層で扱うが、weightとKVではread / writeの性質が違うため別の転送方法を使う。現時点で実HBF hardwareは存在しないため、GPU kernel timingのみH100で実測し、HBF / UCIe / NAND部分は**各処理の発生時刻を模擬するhardware simulator**で評価している。

## 手法のあらまし

DASHの主要な仕組みは、**HBF→GPUの直接転送、HBMをbufferにする転送、Flash readとGPU transferを重ねる小容量buffer、router条件が合うmodelでの早期expert決定、KV writeを大きくまとめる処理**である。

### 1. `HBF`：通常SSDよりGPU memoryに近いFlashを想定する

HBF（High-Bandwidth Flash）は通常のNVMe SSDを単純に高速化しただけの前提ではない。

多数のNAND die / planeを並列化し、Flash側chipに制御logicとSRAMを持たせ、UCIe経由でHBM / GPU近傍へ接続する想定である。

論文の基本構成では、

- HBF: 2 × 512 GB
- HBM: 2 × 24 GB
- chip間link: 実効1.6 TB/s級

を想定する。

したがって、現行NVMeの3〜10 GB/s級readと直接比較するのは適切でない。

### 2. HBFからGPUへ直接送る経路

論文では **Direct Path** と呼ぶ。expert weightをHBF側からGPUへ直接transferする。

利点はHBMを経由せず、追加copyとHBM bandwidth消費を避けられること。

一方でNAND read latencyのばらつきをGPU側が直接受けやすく、read完了が遅れるとGPUがweightを待つ時間が増える。

### 3. HBMをbufferとして使う経路

論文では **Relay Path** と呼び、

`HBF → HBM側buffer → GPU`

の経路を使う。

HBM側bufferがNAND read時間のばらつきを吸収しやすい一方、HBM bandwidthとbuffer容量を消費する。

つまり、

- Direct = 転送段数は少ないがFlash readの遅れがGPUへ直接響く
- Relay = 1段増えるがHBMへ先に貯めておける

というtrade-offがある。

### 4. Expertごとに2経路を分け、同時に使う

DASHの中心は、全expertをDirectまたはRelayの一方へ固定することではない。

各expertのread完了時刻や転送条件を見て経路を割り当て、**DirectとRelayを並列に使って合計転送帯域を高める**。

同じexpert weightを二重複製する必要はなく、expert単位でどちらかの経路を担当させる。

比較表の`DirectOnly` / `RelayOnly`は、この二経路併用の効果を見るための構成である。

### 5. HBF側の小容量SRAMを2分割してreadとtransferを重ねる

HBF側chipには18 MiB SRAM、実利用16 MiBを想定し、8 MiBずつ二つの領域へ分ける。論文ではこの領域を **transfer region** と呼ぶ。

一方の領域からGPUへdataを送っている間に、もう一方へNANDから次dataを読む。これによりFlash readが終わってからGPU転送を始めるのではなく、両処理を交互に重ねる。

ここでのbufferはexpertを長く保持するcacheではなく、**Flash page readとchip間transferを同時進行させる短期buffer**である。

### 6. Router構造が対応していればexpertを早めに決める

一部MoE routerでは、expert rankingに使う値のうち入力依存部分を通常より早い時点で計算できる。

DASHの **Lookahead Expert Execution** は、その条件を満たすrouterについて通常のtop-k確定より前にexpert候補を決め、HBF readを他のGPU計算と重ねる仕組みである。

ただしどのMoEでも使える一般predictorではない。論文は、入力vectorのscaleが変わってもrankingが変わらず、expertごとの固定biasがないなど、特定のrouter条件を要求する。条件を満たさないmodelではこの早期決定を使えない。

### 7. KV cacheは小さいwriteをHBMへ貯めてからFlashへ書く

expert weightは主にreadするdataだが、KVはgeneration中に増え続けるため、同じFlash処理では扱わない。

DASHでは、

- prefill KV：まとまった大きさなのでFlashのpage境界に合わせてHBFへ直接write
- decode KV：毎tokenの小さな更新をHBMへ一旦貯め、大きなwriteにまとめてHBFへ書く

とする。

小さなdecode writeを毎token NANDへ出すとFlash write待ちとreadが競合するため、**HBMを小writeをまとめるbufferとして使う**。

### 8. WeightとKVを別のFlash erase blockへ置く

NAND Flashは小さなpage単位でread/writeできる一方、消去はより大きなerase block単位になる。KVを頻繁に更新すると、同じerase blockにある変更不要なweightまで別場所へ移してから消去する必要が生じる場合がある。

DASHはweight用とKV用のerase blockを分け、**KV更新のためにmodel weightまで余計に移動することを避ける**。

## 評価

### まず見るところ
- **結論:** HBFの直接転送とHBM経由転送をexpertごとに併用すると、一経路だけの構成よりthroughputをほぼ2倍へ伸ばせるというsimulation結果。
- **実速度:** 5 modelの平均的な倍率でRelayOnly比1.90倍、DirectOnly比1.84倍。ただし現行SSD実機の結果ではない。
- **品質:** expert / KVの計算内容は変えず配置・経路だけを変えるためlossless。
- **メモリ・I/O:** **HBF + UCIe + HBM**という将来hardware前提。通常NVMe / CPU DRAM offloadとは分離して読む必要がある。
- **注意点:** HBF chip、UCIe data path、NAND寿命はsimulation / 仮定に基づく値であり、製品実測値ではない。

### 5 modelの平均的な結果

| 比較 | Throughput | E2E latency |
|---|---:|---:|
| DASH vs RelayOnly | **1.90倍** | **42.2%減** |
| DASH vs DirectOnly | **1.84倍** | **40.8%減** |

一経路を高速化したのではなく、**二つのdata pathを同時利用してFlash read / transferの偏りを減らした効果**として読むべき結果である。

### 大きなKV cacheを持つ条件

Llama 4 MaverickでKV cacheを約197.4 GBまで拡張。

| KV配置 | 容量 |
|---|---:|
| HBF側 | 172.96 GB |
| HBM decode KV | 24.46 GB |

この条件でもRelayOnly比でthroughput 1.92倍、latency 48.0%減を報告する。

### Continuous batching

Qwen3、prompt 4K、decode 128、最大batch 32、prefillを512-tokenずつ処理する条件で評価。

RelayOnlyが処理できる最大request rateの75%を与えた時：

| 指標 | RelayOnly | DASHの削減率 |
|---|---:|---:|
| P90 E2E | 28.847 s | **53.5%減** |
| TPOT | 148 ms | **62.2%減** |

### CPU-GPU協調方式との理想化比較

Xeon 8452Y上で同じshapeのexpertを実行するCPU-GPU協調方式と比較し、DASHは8.22〜12.32倍高速とする。

ただしこれは**実CPU systemと、simulation上の将来HBF architectureを比較した結果**なので、現行hardware同士のbenchmarkとして扱わない方がよい。

### SimulatorのGPU部分の確認

| 項目 | 値 |
|---|---:|
| GPU timing実測数 | 1107 |
| Timing model中央値誤差 | 0.51% |

GPU compute部分は実測で校正されているが、HBF / UCIe / NAND subsystem全体が実機化されたわけではない。

### NAND寿命の仮定

Flash read latency、write latency、chip間bandwidth、page sizeを複数条件に変えて評価している。寿命0.645年という値も示されるが、これは**SLC方式のNANDが10万回消去できる、余計なdata書き換えがない、常時同じ負荷で使う**などの仮定を置いた計算値であり、製品保証値ではない。

### 評価上の制約

- HBF hardwareは未実装。
- UCIeを使ったGPU/HBM/HBF間data pathもsimulation。
- 現行NVMe SSDのqueue / filesystem / PCIe software stackとは前提が異なる。
- Lookaheadはrouter構造に制約がある。
- Flash寿命は仮定に基づく計算値。
- 実機でのthermal / power / firmware影響は未検証。
