# DASH: Beyond Capacity: Scalable MoE LLM Inference via High-Bandwidth Flash with Direct GPU and HBM Paths

> 通常SSDよりはるかに高帯域な将来型フラッシュをGPU/HBMの近くへ接続し、エキスパート重みをGPUへ直接送る経路とHBMをバッファにする経路を同時利用して、大容量MoEの重み転送待ちを減らす設計。

## 概要
DASHは、将来の **HBF（High-帯域 フラッシュ）** をGPU近傍の大容量メモリとして使うMoE向け構成である。HBFは通常NVMe SSDより多くのNANDを並列に動かし、GPU/HBMの近くへ高速リンクで接続することを想定したフラッシュで、2026-09時点では製品化済みハードウェアではない。

通常NVMeのようにCPUやOSのストレージ処理を経由するのではなく、**UCIeというチップ間高速リンクでGPU側・HBM側・HBF側のチップを直接つなぐ**。エキスパート重みは、HBFからGPUへ直接送る経路と、HBFから一度HBM側バッファへ入れてからGPUへ送る経路をエキスパートごとに使い分け、両方を同時に動かす。

またKVキャッシュも同じHBF/HBM階層で扱うが、重みとKVでは読み出し / 書き込みの性質が違うため別の転送方法を使う。現時点で実HBF ハードウェアは存在しないため、GPUカーネル 時刻のみH100で実測し、HBF / UCIe / NAND部分は**各処理の発生時刻を模擬するハードウェア シミュレータ**で評価している。

## 手法のあらまし

DASHの主要な仕組みは、**HBF→GPUの直接転送、HBMをバッファにする転送、フラッシュ読み出しとGPU 転送を重ねる小容量バッファ、ルータ条件が合うモデルでの早期エキスパート決定、KV 書き込みを大きくまとめる処理**である。

### 1. `HBF`：通常SSDよりGPU memoryに近いFlashを想定する

HBF（High-帯域 フラッシュ）は通常のNVMe SSDを単純に高速化しただけの前提ではない。

多数のNAND ダイ / プレーンを並列化し、フラッシュ側チップに制御論理回路とSRAMを持たせ、UCIe経由でHBM / GPU近傍へ接続する想定である。

論文の基本構成では、

- HBF: 2 × 512 GB
- HBM: 2 × 24 GB
- チップ間リンク: 実効1.6 TB/s級

を想定する。

したがって、現行NVMeの3〜10 GB/s級読み出しと直接比較するのは適切でない。

### 2. HBFからGPUへ直接送る経路

論文では **直接 Path** と呼ぶ。エキスパート重みをHBF側からGPUへ直接転送する。

利点はHBMを経由せず、追加コピーとHBM帯域消費を避けられること。

一方でNAND読み出し遅延のばらつきをGPU側が直接受けやすく、読み出し完了が遅れるとGPUが重みを待つ時間が増える。

### 3. HBMをbufferとして使う経路

論文では **中継 Path** と呼び、

`HBF → HBM側buffer → GPU`

の経路を使う。

HBM側バッファがNAND読み出し時間のばらつきを吸収しやすい一方、HBM帯域とバッファ容量を消費する。

つまり、

- 直接 = 転送段数は少ないがフラッシュ読み出しの遅れがGPUへ直接響く
- 中継 = 1段増えるがHBMへ先に貯めておける

というトレードオフがある。

### 4. Expertごとに2経路を分け、同時に使う

DASHの中心は、全エキスパートを直接または中継の一方へ固定することではない。

各エキスパートの読み出し完了時刻や転送条件を見て経路を割り当て、**直接と中継を並列に使って合計転送帯域を高める**。

同じエキスパート重みを二重複製する必要はなく、エキスパート単位でどちらかの経路を担当させる。

比較表の`DirectOnly` / `RelayOnly`は、この二経路併用の効果を見るための構成である。

### 5. HBF側の小容量SRAMを2分割してreadとtransferを重ねる

HBF側チップには18 MiB SRAM、実利用16 MiBを想定し、8 MiBずつ二つの領域へ分ける。論文ではこの領域を **転送 領域** と呼ぶ。

一方の領域からGPUへデータを送っている間に、もう一方へNANDから次データを読む。これによりフラッシュ読み出しが終わってからGPU転送を始めるのではなく、両処理を交互に重ねる。

ここでのバッファはエキスパートを長く保持するキャッシュではなく、**フラッシュ ページ読み出しとチップ間転送を同時進行させる短期バッファ**である。

### 6. Router構造が対応していればexpertを早めに決める

一部MoEルータでは、エキスパート 順位付けに使う値のうち入力依存部分を通常より早い時点で計算できる。

DASHの **先読みエキスパート Execution** は、その条件を満たすルータについて通常の上位k確定より前にエキスパート候補を決め、HBF読み出しを他のGPU計算と重ねる仕組みである。

ただしどのMoEでも使える一般予測器ではない。論文は、入力ベクトルのscaleが変わっても順位付けが変わらず、エキスパートごとの固定biasがないなど、特定のルータ条件を要求する。条件を満たさないモデルではこの早期決定を使えない。

### 7. KV cacheは小さいwriteをHBMへ貯めてからFlashへ書く

エキスパート重みは主に読み出しするデータだが、KVはgeneration中に増え続けるため、同じフラッシュ処理では扱わない。

DASHでは、

- プリフィル KV：まとまった大きさなのでフラッシュのページ境界に合わせてHBFへ直接書き込み
- デコード KV：毎トークンの小さな更新をHBMへ一旦貯め、大きな書き込みにまとめてHBFへ書く

とする。

小さなデコード 書き込みを毎トークン NANDへ出すとフラッシュ 書き込み待ちと読み出しが競合するため、**HBMを小書き込みをまとめるバッファとして使う**。

### 8. WeightとKVを別のFlash erase blockへ置く

NAND フラッシュは小さなページ単位で読み出し/書き込みできる一方、消去はより大きな消去 ブロック単位になる。KVを頻繁に更新すると、同じ消去 ブロックにある変更不要な重みまで別場所へ移してから消去する必要が生じる場合がある。

DASHは重み用とKV用の消去 ブロックを分け、**KV更新のためにモデル重みまで余計に移動することを避ける**。

## 評価

### まず見るところ
- **結論:** HBFの直接転送とHBM経由転送をエキスパートごとに併用すると、一経路だけの構成よりスループットをほぼ2倍へ伸ばせるというシミュレーション結果。
- **実速度:** 5 モデルの平均的な倍率でRelayOnly比1.90倍、DirectOnly比1.84倍。ただし現行SSD実機の結果ではない。
- **品質:** エキスパート / KVの計算内容は変えず配置・経路だけを変えるため無損失。
- **メモリ・I/O:** **HBF + UCIe + HBM**という将来ハードウェア前提。通常NVMe / CPU DRAMオフロードとは分離して読む必要がある。
- **注意点:** HBF チップ、UCIeデータ 経路、NAND寿命はシミュレーション / 仮定に基づく値であり、製品実測値ではない。

| 比較 | Throughput | E2E 遅延 |
|---|---:|---:|
| DASH vs RelayOnly | **1.90倍** | **42.2%減** |
| DASH vs DirectOnly | **1.84倍** | **40.8%減** |

一経路を高速化したのではなく、**二つのデータ 経路を同時利用してフラッシュ読み出し / 転送の偏りを減らした効果**として読むべき結果である。

### 大きなKV cacheを持つ条件

Llama 4 MaverickでKVキャッシュを約197.4 GBまで拡張。

| KV配置 | 容量 |
|---|---:|
| HBF側 | 172.96 GB |
| HBM デコード KV | 24.46 GB |

この条件でもRelayOnly比でスループット 1.92倍、遅延 48.0%減を報告する。

### Continuous batching

Qwen3、プロンプト 4K、デコード 128、最大バッチ 32、プリフィルを512-トークンずつ処理する条件で評価。

RelayOnlyが処理できる最大リクエスト 率の75%を与えた時：

| 指標 | RelayOnly | DASHの削減率 |
|---|---:|---:|
| P90 E2E | 28.847 s | **53.5%減** |
| TPOT | 148 ms | **62.2%減** |

### CPU-GPU協調方式との理想化比較

Xeon 8452Y上で同じshapeのエキスパートを実行するCPU-GPU協調方式と比較し、DASHは8.22〜12.32倍高速とする。

ただしこれは**実CPU システムと、シミュレーション上の将来HBF 構成を比較した結果**なので、現行ハードウェア同士のベンチマークとして扱わない方がよい。

### SimulatorのGPU部分の確認

| 項目 | 値 |
|---|---:|
| GPU 時刻実測数 | 1107 |
| Timing モデル中央値誤差 | 0.51% |

GPU計算部分は実測で校正されているが、HBF / UCIe / NAND subsystem全体が実機化されたわけではない。

### NAND寿命の仮定

フラッシュ読み出し遅延、書き込み遅延、チップ間帯域、ページ 大きさを複数条件に変えて評価している。寿命0.645年という値も示されるが、これは**SLC方式のNANDが10万回消去できる、余計なデータ書き換えがない、常時同じ負荷で使う**などの仮定を置いた計算値であり、製品保証値ではない。

### 評価上の制約

- HBF ハードウェアは未実装。
- UCIeを使ったGPU/HBM/HBF間データ 経路もシミュレーション。
- 現行NVMe SSDのqueue / filesystem / PCIe software stackとは前提が異なる。
- 先読みはルータ構造に制約がある。
- フラッシュ寿命は仮定に基づく計算値。
- 実機でのthermal / power / firmware影響は未検証。
