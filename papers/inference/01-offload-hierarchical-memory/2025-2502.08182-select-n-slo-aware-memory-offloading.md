# Memory Offloading for Large Language Model Inference with Latency SLO Guarantees

> Select-NはSLO・系列長・バッチサイズに応じてGPUに残す層とCPUへ退避する層の間隔を動的に調整し、オフロード量とスループットを両立する。

## 概要

Select-NはSLO・系列長・バッチサイズに応じてGPUに残す層とCPUへ退避する層の間隔を動的に調整し、オフロード量とスループットを両立する。 主要評価ではSLOを維持し、FlexGen比でホストメモリ利用量を最大2.37倍、スループットを最大1.85倍にした。

- **著者・所属**: Peking University、Alibaba Cloud Computing、Michigan Tech。
- **公開**: arXiv:2502.08182v1
- **種別**: プレプリント
- **対象**: モデル重みオフロード、階層メモリ、SLO、PCIe帯域競合、動的メモリ管理、プリフェッチ
- **実装**: vLLMを基盤に実装し、計算用と転送用に別CUDAストリームを使う。Transformerモデルを包めるPythonライブラリとして実装したと記載される。
## 問題設定
LLM推論でGPUメモリが不足したとき、モデル状態をCPUのホストメモリへ退避すれば、より大きなモデルやバッチを少ないGPUで扱える。しかし既存方式は対話サービスの遅延サービス水準目標（service-level objective: SLO）とメモリ節約を同時に扱いにくい。DeepSpeed Inferenceは現在計算中の層だけをGPUへ残すためホストメモリ利用量は大きいが、現代のLLMではPCIeによる次層転送が1層の計算時間より長くなりやすく、プリフェッチで隠し切れない。論文の動機実験では転送時間がプリフィルで3.5倍、デコードで13.8倍長く、遅延が最大9.5倍、スループットが最大8.2倍低下した。一方FlexGenはモデルサイズ、バッチ、系列長、理論GPU性能などから固定の退避率を事前計算するため、SLOを守ろうとすると実測より悲観的な計算時間やPCIe競合時の最悪帯域を仮定せざるを得ない。その結果、本来ホストへ移せる状態をGPUに残し、バッチ拡大の余地を失う。したがって必要なのは、実際のモデル実行時間と現在の帯域競合に基づき、SLOを越えない範囲で退避量を最大化する仕組みである。
## 新規性
Select-Nは退避率を連続値で直接探索する代わりに、オフロード間隔（オフロード interval）という整数パラメータへ問題を縮約する。間隔iなら各i層のうち最後の1層をホストへ置き、それ以外をGPUへ残す。間隔が小さいほど多くの層を退避できるが転送頻度が増え、間隔が大きいほどGPUメモリ消費は増えるがSLOを守りやすい。さらに、退避層のロードを直前の1層ではなく区間先頭から開始し、複数層分の計算時間でPCIe転送を隠す。モデル導入時には実機プロファイルからSLO・系列長・バッチサイズごとの最小安全間隔を表にし、運用時には同じPCIeバスを共有するGPU群の帯域競合を監視して反復ごとに間隔を調整する。静的な容量最適化ではなく、SLOを制約とした階層メモリ制御へ変換した点が中心的な新規性である。
## 手法
### 手法のあらまし
Select-Nはオフライン分析器、GPUごとの実行時メモリ管理器、PCIeバスごとの実行時帯域調整器の三つから成る。新しいモデルを導入すると、専用サーバ上で実際にプロンプトを流し、プリフィル・デコードの層実行時間と転送時間を測る。ここから、SLO、入力系列長、バッチサイズの組合せごとに、SLOを満たす最小のオフロード間隔を性能レコードへ保存する。要求到着時には待ち時間を差し引いた残りSLOと要求形状から表を参照し、初期間隔を即座に得る。

メモリ管理器では、間隔iごとに1層をCPU DRAMへ置く。通常の『次の層になってからプリフェッチ』ではなく、その退避層を含む区間の先頭層を計算し始めた時点でロードを開始する。計算ストリームとコピー用CUDAストリームを並行させることで、i層近い計算区間の背後に転送を隠す。小さいiはより多くの重みをホストへ追い出せるが、必要PCIe帯域が増える。大きいiは逆にGPU内状態を増やし、転送待ちとSLO違反を抑える。

複数GPUが同じPCIeバスを共有すると、オフラインで得た最小間隔のままでは帯域総量がバス容量を超える可能性がある。このため帯域調整器は各GPUについて、SLOから決まる最小間隔とGPU容量から決まる最大間隔を持ち、各反復で実行可能な間隔組合せを評価する。合計PCIe使用量が容量以内で、全要求のSLOを満たす組合せの中から、ホストメモリ利用量を最大化するものを選ぶ。SLO自体が達成不能なら上位スケジューラへ要求を返し、別ノードなどへ逃がせる設計にする。

### オフロード間隔による容量・遅延制御
Select-Nは、GPUからCPUへ移す層の割合を直接の浮動小数点比率として扱うのではなく、オフロード間隔iという整数へ写像する。間隔iでは連続するi層を一つの区間とみなし、そのうち1層だけをCPUホストメモリへ退避し、残りをGPUに常駐させる。したがってiを小さくすると退避層が増えてGPU HBMを大きく節約できる一方、PCIe転送回数と必要帯域が増える。反対にiを大きくすると転送頻度が下がりTTFTやTPOTを守りやすくなるが、GPU側へ残す重みが増えて大きいバッチを収容しにくくなる。この単調な関係を利用し、要求の系列長・バッチサイズ・残りSLOに対して『SLOを満たせる最小のi』を選ぶことで、遅延制約を破らない範囲でホストDRAM利用量を最大化する。ここで重要なのは、同じTransformer内の層がほぼ同形で、同じ要求形状なら各層の実行時間が安定するという観測である。そのため一つの区間で得られる計算時間を、後段で必要になる退避層の転送隠蔽時間として予測できる。例えば小さ過ぎるiでは転送が次の利用時刻までに終わらずGPUが待機してSLO違反となり、大き過ぎるiでは転送待ちは消えるものの追加のGPU常駐層が性能改善に寄与せず容量だけを消費する。Select-Nはこの境界を実測プロファイルから特定し、容量と遅延を一つの離散パラメータで制御する。追加コストはモデル・要求形状ごとの事前プロファイルと、運用時に間隔に応じて層をCPU/GPU間移動するPCIeトラフィックである。層ごとの計算時間が大きく変動するモデルや、動的な専門家選択で経路が変わるMoEではこの予測可能性が弱まり、同じ制御則をそのまま使うと安全側の余裕が必要になる。

### 区間先頭からの早期プリフェッチ
DeepSpeed InferenceやFlexGenは退避層の直前になってから次の層をロードするため、1層分の計算時間しか転送隠蔽に使えない。Select-Nは退避層を含む区間の最初の層からロードを始める。例えば間隔8なら、退避層が必要になるまで複数層を計算する時間を転送窓として使える。計算と転送を別CUDAストリームで走らせ、必要地点で同期することで、PCIeが層計算より遅いA10級環境でも待ち時間を減らす。この早期開始が、単に退避層数を減らすだけでなくSLOと容量を細かく交換できる理由になる。

### 実測ベースのオフライン性能レコード
モデル導入時に、実運用と同じGPU・CPU・PCIe構成を持つ帯域競合のない専用環境でプロンプトを実際に処理し、プリフィルとデコードそれぞれについて層計算時間、転送時間、系列長、バッチサイズとSLOの関係を測定する。その結果から各要求形状でSLOを満たせる最小オフロード間隔を性能レコードへ保存する。FlexGenのようにGPUの理論ピークFLOPSから実行時間を下限推定すると、実際のカーネル効率、メモリ律速、バッチサイズによる利用率差を十分表せず、安全側へ大きく寄せる必要がある。Select-Nは実測値を使うため、SLO違反になる境界の直前までホストメモリ利用量を増やせる。オンライン処理では要求が到着した時点の待ち時間をSLO予算から差し引き、残り時間と系列長・バッチサイズをキーに表を参照するだけなので、要求ごとに重い探索を行わない。これにより事前プロファイルのコストとオンライン判断の軽さを分離している。ただしGPU世代、PCIe構成、モデル実装、カーネル、量子化方式などが変われば測定境界も変化するため、性能レコードは配備構成ごとに作り直す必要がある。さらに、表にない要求形状への補間や急激な実行時間変動には誤差が入り得るため、後段の帯域調整器とSLO安全側制御が必要になる。

### PCIe帯域競合に応じた反復単位調整
複数GPUが同じPCIeバスを共有する場合、各GPUが個別には安全な間隔を選んでも、同時転送で帯域が不足してSLO違反を起こせる。帯域調整器は各GPUの最小・最大間隔と、候補間隔ごとの予測帯域を使い、総帯域がPCIe容量以下になる組合せを選ぶ。競合が強い時は一部GPUの間隔を大きくしてGPU側保持量を増やし、転送頻度を下げる。競合が消えれば小さい間隔へ戻してホスト利用量を増やす。この更新を出力トークン生成の反復単位で行うため、固定最悪ケース帯域を仮定するFlexGenより実帯域を活用できる。

### 達成不能SLOの上位スケジューラへの返却
Select-Nでは、性能レコードからSLOを満たすために必要な最小オフロード間隔が決まり、同時にGPU容量から『これ以上はGPUへ重みを残せない』最大間隔が決まる。通常はこの二つの境界の間に有効な間隔が存在し、そこからホストメモリ利用量が最大になる値を選べる。しかしモデルがGPU容量に対して大き過ぎる、要求の残りSLOが短過ぎる、あるいはPCIe競合が強過ぎる場合には、SLO側が要求する最小間隔が容量側の最大間隔を上回り、どの配置を選んでも制約を同時に満たせない。このときSelect-Nは無理にローカルGPUで実行して後からSLO違反を起こすのではなく、その要求を上位スケジューラへ返す。上位層はオフロード不要のGPU、空いているPCIeバス、より大容量のノードなどへ再配置できるため、局所メモリ管理の失敗をクラスタ全体のSLO違反へ波及させにくい。これはSelect-Nが単なるオフロード実装ではなく、受理可能性を明示する資源管理器として働く部分である。一方、論文自身は返却後のクラスタ規模ルーティング戦略を主題にしておらず、別ノードが見つからない場合の待ち行列制御や公平性は上位システム側に残る。

### 全体のデータ／制御の流れ
実装はvLLMを基盤とし、Transformers系モデルを包むPythonライブラリとして構成される。対象は単一サーバ内のGPU-HBMとCPU-DRAMの二階層で、層重み・モデル状態をPCIe越しに移動する。プリフィルとデコードは原則として別インスタンスへ分離され、それぞれTTFTとTPOTに異なる間隔を設定できる。KVキャッシュ自体のSSD退避、分散GPU間の遠隔メモリ、NVLink-C2CのようなCPU-GPU密結合メモリは対象外で、後発のSuperInferなどとはハードウェア前提が異なる。Select-Nの主要価値はPCIe制約下で『できるだけ多くホストへ置く』のではなく、『SLOを守れる最小GPU常駐量』を実測とオンライン帯域状況から決める点にある。
## 評価条件
- **ハードウェア**: 4枚のNVIDIA A10 GPUを備えた実機サーバ。動機実験ではA10 24GB、PCIe実効帯域24GB/sを使用し、評価では同一PCIeバスを2 GPUが共有する競合条件も作る。
- **ソフトウェア**: vLLM、CUDA ストリーム、Python library implementation
- **モデル**: OPT-6.7B、OPT-13B、Qwen2-beta-7B、Llama2-13B
- **データセット／トレース**: 主評価は系列長・バッチサイズ・語彙サイズを調整可能な合成データローダ、ShareGPTとAlpacaも適用可能と説明するが、主要数値は合成要求で測定
- **比較対象**: DeepSpeed Inference、SLO対応に修正したFlexGen、オフロードなしのnaive vLLM
- **正確性・品質**: 重みの量子化・枝刈り・近似を行わず、モデル状態の配置とプリフェッチ時刻だけを変えるため、生成結果の正確性を比較する評価は行わない。性能評価ではオフロードなしvLLMを遅延基準とし、TTFTとTPOTのSLO達成を確認する。
- **SLO維持評価**: OPT-6.7BとQwen2-beta-7Bでプリフィルとデコードを分離。デコードのバッチサイズ128、プリフィル32とし、オフロードなし実行のTTFT/TPOTを参照して複数のSLO強度を設定する。
- **メモリ節約評価**: OPT-13B、バッチサイズ4/8/16/32でSelect-NとFlexGenを比較。Select-Nは実測性能レコードから間隔を変え、FlexGenはコストモデルから退避率を決定する。
- **性能レコード精度**: OPT-6.7B、系列長64、プリフィルバッチ16、デコードバッチ128、SLO target 50%で、分析器が選んだ間隔3と8を非最適な間隔と比較する。
- **帯域競合評価**: 同一PCIe帯域を共有する2 GPUでOPT-13BとLlama2-13Bを同時実行。系列長64、バッチ8/16/32、TPOT SLOを100msに固定し、FlexGenと比較する。
メモリ節約量、TTFT、TPOT、スループットを主要指標とする。まずDeepSpeedとの比較でSLOを満たせるかを確認し、次にFlexGenと同一バッチ条件でホストメモリへ移せる量とスループットを測る。さらに最適間隔の前後を明示的に試して性能レコードの境界が妥当かを検証し、最後に複数GPUがPCIeを同時利用する条件でオンライン帯域調整器の効果を切り分ける。
単一サーバのPCIe接続GPU-CPU階層を対象とする。評価GPUはA10世代に限定され、H100/GH200のNVLink-C2CやSSD、複数ノード構成は扱わない。主要ワークロードは合成データであり、実トレースの到着分布やバースト性を用いたクラスタ規模評価ではない。
## 主要結果
Select-Nは、ホストメモリを最大限利用しながらTTFT/TPOTのSLOを守るという設計目標に対し、DeepSpeed Inferenceの過剰退避とFlexGenの保守的な固定退避の中間点を動的に選べた。主要評価ではSLOを一貫して維持し、FlexGenより最大2.37倍多くホストメモリを利用しながら最大1.85倍のスループットを達成する。PCIe競合条件ではFlexGenが小さいバッチでTPOT SLOを破る一方、Select-Nは間隔を反復単位で調整し、最大2.9倍のスループットを示した。

- DeepSpeedに対するSLO維持 / DeepSpeedは指定SLOを最大8.08倍超過し、Select-N比でスループット6.8〜8.23倍低下 (比較対象: DeepSpeed Inference; 条件: OPT-6.7B/Qwen2-beta-7B、プリフィル・デコード分離) — 1層だけGPUに残す方式ではPCIe転送を1層計算で隠せず、特にメモリ律速のデコードで待ちが支配する。

- ホストメモリ活用 / FlexGenより最大2.37倍高いメモリ節約量 (比較対象: SLO対応FlexGen; 条件: OPT-13B、バッチ4/8/16/32) — ピーク性能による静的下限推定ではなく、実測時間からSLO境界を決めるため、必要以上にGPUへ重みを残さずに済む。

- スループット / FlexGen比最大1.85倍 (比較対象: SLO対応FlexGen; 条件: OPT-13B、複数バッチサイズ) — より多くの状態をホストへ移すことで、同じGPU容量でより大きい入力規模・バッチを扱える。

- 性能レコードの最適間隔 / プリフィル3、デコード8がSLOを守りつつ最小GPUメモリ (比較対象: 非最適オフロード interval; 条件: OPT-6.7B、系列長64、プリフィルbatch16、デコードbatch128、SLO target 50%) — 小さすぎる間隔は転送増でSLO違反、大きすぎる間隔は性能をほぼ改善せずGPUメモリだけ増やす。

- PCIe競合下スループット / 小バッチ条件でFlexGen比最大2.9倍 (比較対象: FlexGen; 条件: OPT-13BとLlama2-13Bを2 GPUで同時実行、系列長64、バッチ 8/16/32、TPOT SLO 100ms) — 固定最悪帯域を仮定せず、実際の共有バス状況に応じて各GPUの間隔を変える効果。

### 負の結果・境界条件
- 中心仮定は、同一要求形状に対するTransformer各層の実行時間が十分安定していることである。異種層構造、MoEの動的専門家選択、条件付き計算では単純な層時間の決定性が弱くなる可能性がある。
- 性能レコードはモデル、GPU、系列長、バッチサイズ、SLOの組合せごとに事前生成する必要があり、モデル更新やハードウェア変更時には再プロファイルが必要になる。
- 評価は4枚のNVIDIA A10とPCIe接続に限定され、GH200のNVLink-C2C、CXL、SSDなど帯域特性が大きく異なる階層では最適な制御粒度が変わる。
- 主要ワークロードは合成データローダで、実サービスの要求到着バースト、長さ分布、モデル多重化を含むオンラインクラスタ評価ではない。
- 論文はオープンソース化予定とするが、arXiv付帯情報から公式コード公開を確認できず、再現性は実装記述に依存する。

### 結果の読み方
Select-Nの重要点は、CPUへのオフロード量を単なる『入るだけ追い出す容量問題』ではなく、『遅延SLOを制約にした動的資源配分問題』として扱ったことにある。DeepSpeed型ではホスト活用を最大化し過ぎて転送待ちがSLOを壊し、FlexGen型ではSLOを守るため最悪ケース推定に寄り過ぎてGPUを余分に占有する。Select-Nは実測した層実行時間を利用し、SLOを守れる最小間隔を境界として選ぶことで両極端を避ける。さらに実運用のPCIe競合を反復ごとに観測し、帯域不足時だけGPU常駐量を増やすため、静的な1/n帯域仮定よりホストDRAMを攻めて使える。後発のSuperchip向け方式と比べると転送帯域自体を高速化する研究ではなく、PCIeという遅い既存階層で安全な退避量を適応制御する研究である。
## 品質への影響
重みやKVの数値内容を変換せず、モデル状態の配置だけを変えるため生成品質への直接影響はない。性能改善はSLO達成率、メモリ容量、スループットに現れ、精度・品質の改善を主張するものではない。
## 既存研究との差
- DeepSpeed InferenceはGPU常駐量をほぼ最小化し、次層だけをプリフェッチする。Select-NはSLOを第一制約にし、複数層分の計算時間を転送隠蔽へ使える間隔を選ぶため、容量最大化より応答性を優先する。
- FlexGenはモデル・要求・理論性能から退避率を静的に求める。Select-Nは実機プロファイルでSLO境界を測り、さらにPCIe競合へオンラインで追従するため、最悪ケース見積もりによるGPUメモリ過剰確保を減らす。
- NEOなどのCPUオフロード系はオンライン推論時のGPUメモリ危機を緩和するが、Select-Nの主軸はTTFT/TPOTという明示的SLOを守る範囲でホストメモリ利用量を最大化する制御則にある。
- 後発のSuperInferはGH200のNVLink-C2C高帯域を使ってKVキャッシュを頻繁に回転させ、要求スケジューリングと転送エンジンを共同設計する。Select-Nは通常PCIe環境でモデル層状態を対象にし、既存帯域の範囲内で退避頻度を減らす点が異なる。
- FlexGenやLLM in a Flashのようなオフロード研究が『限られたGPUでモデルを動かす』ことを主目的にするのに対し、Select-Nは対話型オンラインサービスでSLOを維持しながらメモリ節約を収益化できるかを主問題にする。
## 限界
- 各層の実行時間が同じ、または十分予測可能という前提が重要である。Mixture-of-エキスパートのようにトークンごとに活性化経路が変わるモデルや、層ごとに構造が大きく異なるモデルでは性能レコードの単純化が成立しにくい。
- モデル・GPU・系列長・バッチ・SLOの組合せごとに性能レコードを事前作成するため、配備構成が頻繁に変わる環境ではプロファイル費用とレコード管理が増える。
- 帯域調整器は候補間隔の組合せを評価する設計で、GPU数や候補範囲が大きくなるほど探索コストが増える。論文は4 GPU規模で実証しており、大規模共有バス・CXLファブリックへのスケーラビリティは未評価である。
- 主評価はNVIDIA A10とPCIe 24GB/s級の環境であり、NVLink-C2Cやより新しいGPUでは転送/計算比が変わるため、報告された最適間隔や性能差はそのまま移植できない。
- 実サービスの到着トレースではなく主に合成データローダを使うため、キューイング遅延やバースト、複数モデル間の要求変動を含むSLO達成率は十分に評価されていない。
- 論文はオープンソース化へのコミットを記すものの、一次資料上で公開コードURLを確認できず、完全な再現手順は公開実装に比べ弱い。
## 実装状態
vLLM上に実装し、計算とデータ転送を別CUDAストリームへ分離したPythonライブラリとしてTransformerモデルを包む。論文はオープンソース化予定と明記するが、arXiv v1の付帯情報にはコードURLがなく、2026-09-11時点で公式リポジトリを確認できなかった。
## 研究上の位置づけ
階層メモリ・オフロード系統では、Select-Nは『どのデータをどこへ置くか』よりも『どの程度の退避ならオンラインSLOを壊さないか』を明示的に解く研究として位置付けられる。GPU HBMとCPU DRAMの容量差を利用する従来発想は維持しつつ、層実行時間の決定性からオフロード間隔という単一ノブを導出し、オフライン実測とオンライン帯域調停を分離した。これにより、DeepSpeedの過剰な転送とFlexGenの過剰なGPU常駐の間を動的に移動できる。後続研究から見ると、通常PCIe上でSLO-aware オフロードを成立させる基準点であり、SuperchipやCXL、SSDを含む多階層へ拡張するときに『転送媒体の高速化』と『SLO制御』を切り分けて比較するための重要な先行研究になる。
