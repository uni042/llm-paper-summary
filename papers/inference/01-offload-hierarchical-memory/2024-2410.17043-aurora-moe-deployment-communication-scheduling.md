# Optimizing Mixture-of-Experts Inference Time Combining Model Deployment and Communication Scheduling

> MoEのエキスパート配置・異種GPU割当・全対全通信順序を共同最適化し、4クラスタ条件を理論化して異種同居では二部マッチング近似を用い、最大3.54倍高速化する。

## 概要
Auroraは、混合専門家モデル（Mixture-of-エキスパート; MoE）推論で支配的になる全対全通信の帯域競合、同期通信によるGPU遊休、異種GPUへの配置を別々に扱わず、エキスパート配置・GPU割当・通信順序を一体で最適化する。排他的配置／異モデル間の同居と、同種／異種GPUの組合せから4条件を定式化し、3条件では最適解を導出する。最も難しい異種GPU上の同居条件は3次元マッチングとしてNP困難であることを示し、2段の二部マッチングへ分解する近似法を用いる。Google由来のMoE統計を使うシミュレーションでは、同種環境で最大2.38倍、異種環境で最大3.54倍の推論高速化と、Lina比最大1.50倍のGPU利用率向上を報告する。

Auroraは、エキスパートを1GPUに1個置く排他的配置と、異なる2モデルのエキスパートを同じGPUへ置く同居配置を、同種GPU・異種GPUの2軸と組み合わせて4条件に分ける。各条件で推論時間をゲート、全対全通信、FFN、集約の終了時刻から定式化し、通信順序、GPU割当、同居相手の選択を最適化問題として解く。排他・同種、排他・異種、同居・同種では最適解を導出し、同居・異種だけは3次元マッチングとしてNP困難であるため、エキスパート同居とGPU割当を2つの二部ボトルネックマッチングへ分解する。

代表結果として、排他・同種GPUでの推論高速化はB/16・B/32、COCO/ImageNet由来交通、100Gbps同種クラスタでSJFに対して最大1.38x。短い転送を優先するだけでは受信側帯域競合を避けられず、交通行列全体から競合しない順序を作るAuroraが同期通信の最後尾を短縮した。
## 問題設定
MoE推論ではゲートがトークンを複数GPU上のエキスパートへ振り分けるため、各層で往復2回の全対全通信が生じる。トークン偏りがあると同じ受信GPUへ通信が集中して帯域競合が起き、同期型の全対全通信では遅い転送が終わるまで他GPUも次の計算へ進めない。さらに人気の低いエキスパートを持つGPUは待ち時間が長く利用率が低い。既存方式は負荷均衡、通信高速化、同一モデル内のエキスパート同居などを個別に扱うことが多く、異種GPUの計算性能・帯域差と複数モデルの同居を含めた配置と通信順序の共同最適化が不足していた。
## 新規性
Auroraは、エキスパートを1GPUに1個置く排他的配置と、異なる2モデルのエキスパートを同じGPUへ置く同居配置を、同種GPU・異種GPUの2軸と組み合わせて4条件に分ける。各条件で推論時間をゲート、全対全通信、FFN、集約の終了時刻から定式化し、通信順序、GPU割当、同居相手の選択を最適化問題として解く。排他・同種、排他・異種、同居・同種では最適解を導出し、同居・異種だけは3次元マッチングとしてNP困難であるため、エキスパート同居とGPU割当を2つの二部ボトルネックマッチングへ分解する。
## 手法
### 手法のあらまし
入力は各MoE層でGPU間を流れるトークン量を表す交通行列、各GPUの計算時間・通信帯域、各エキスパートの処理トークン数である。まず全対全通信について、各GPUの送信量と受信量の最大値が下界となり、同じ宛先への帯域競合を避ける順序へトークン転送を並べ替えることでこの下界を達成する通信スケジュールを構成する。同種GPUで1エキスパートずつ置く場合は配置差がないため、この通信時間最小化がそのまま推論時間最小化になる。異種GPUで排他的に置く場合は、処理トークン数の多いエキスパートから高性能GPUへ降順対応させ、同じ通信順序最適化を組み合わせる。2モデルを同居させる場合、同一モデルのエキスパート同士ではなく異モデルのエキスパートを同じGPUへ置き、片方が同期通信を待つ間にもう片方の計算・通信を重ねられる余地を作る。同種GPUでは、2モデルの交通行列を同居候補ごとに合成し、最大送受信量を最小にする組合せをボトルネック二部マッチングで求める。異種GPUでは同居ペアとGPUの双方を同時に選ぶ最適化が3次元マッチングとなるため、最初にエキスパート同士の最適同居を二部マッチングで求め、次に得られたペアを異種GPUへ割り当てる別のボトルネックマッチングを解く。これにより多項式時間で実用的な近似解を得る。

### 帯域競合を避ける全対全通信順序
交通行列は送信元GPUと受信先GPUの組ごとのトークン量を表す。Auroraは各GPUについて総送信量と総受信量を計算し、その最大値を、どの順序でも下回れない通信時間の下界として使う。次に、同じ時刻に複数送信元が同一受信GPUへ集中して帯域を奪い合わないよう、送信相手と順番を組み替える。これにより個々の短い転送を優先するのではなくクラスタ全体の競合を避け、最後の転送が終わる時刻を下界まで縮める。同期型全対全通信では全GPUが最後尾の転送を待つため、この最大完了時刻の短縮がそのままFFN開始の前倒しにつながる。交通行列が事前統計から外れると順序は最適でなくなるが、評価では大きなノイズでも利得が残る。

### 異種GPUへの人気順割当
異種クラスタでは同じエキスパートを置いてもGPUごとにFFN計算時間とネットワーク帯域が異なるため、配置先が層全体の同期完了時刻を左右する。Auroraは各エキスパートが処理するトークン数を負荷の尺度として多い順に並べ、GPU側も計算・通信性能の高い順に並べて対応付ける。人気エキスパートを低性能GPUへ置くと大量トークンの計算と通信が最後尾になり、他GPUが待つ時間が増えるため、その逆配置を避ける。論文はこの降順対応が排他・異種条件の推論時間を最小化すると示す。配置後の全対全通信には同種条件で導いた競合回避順序を適用できるので、GPU割当と通信順序を組み合わせて層の完了時刻を抑える。

### 異モデル間エキスパート同居
複数エキスパートを1台へ置くとき、同一モデル内のエキスパート同士は同じ同期全対全通信の障壁を共有するため、一方が待っている時間へもう一方の独立処理を十分に差し込めない。Auroraは異なる2モデルから1エキスパートずつを同じGPUへ置き、片方のモデルが通信待ちの間に他方のゲート、FFN、通信、集約を進められる余地を作る。同種GPUではGPU性能差を考えなくてよいため、問題はどのエキスパート同士を組にするかへ縮約できる。各候補ペアについて2モデルの交通行列を合成し、合成後の最大送受信量を辺重みとする二部グラフを構成する。そして完全マッチング中の最大辺重みを最小化するボトルネックマッチングを解き、通信の最後尾が最も短い同居組合せを選ぶ。

### 異種同居条件の二段マッチング近似
異種GPUで2モデルを同居させる場合は、モデルAのエキスパート、モデルBのエキスパート、配置先GPUという3要素を同時に決める必要がある。各3要素の組に、そのGPU上で生じる推論時間を重みとして与えると最適化は3次元マッチングとなりNP困難である。Auroraはこの同時最適化を直接総当たりせず、まずGPU割当を無視して2モデル間のエキスパート同居だけをボトルネック二部マッチングで決める。その結果できたエキスパート対を新しい単位として、次に各対と異種GPUの間でもう一度ボトルネックマッチングを解き、最大推論時間が小さくなる配置を選ぶ。分解により理論最適性は失うが計算量を多項式へ落とせる。評価では総当たり最適解より平均7%長いだけで、他方式より大幅に短い。

### 全体のデータ／制御の流れ
Auroraは実行前または再計画時に交通行列とクラスタ性能情報から配置・通信計画を作り、その計画に従ってエキスパートをGPUへ配置し、各全対全通信の送信順序を制御する。計画後の要求分布が変化すると最適性は低下するため、論文は交通統計へ最大75%のノイズを加えた感度評価を行い、将来課題として動的再最適化を挙げる。
## 評価条件
- **ハードウェア**: 評価は実機クラスタではなくシミュレーション。全GPUは大型スイッチへ接続される。同種クラスタは各GPUのネットワーク帯域を100Gbpsとし、異種クラスタは100、80、50、40Gbpsの4種類を同数ずつ配置する。排他的配置では各MoEモデルが帯域を独立利用し、同居配置では同じGPUに置かれたモデル間だけ帯域競合する。
- **ソフトウェア**: 論文の理論モデルとアルゴリズムを用いたシミュレーション評価。通信順序の比較対象は最短ジョブ優先（Shortest Job First; SJF）とランダム通信順序、異種GPU割当はランダム割当、同居はランダム同居とLinaの同一モデル内同居機構を比較する。Linaについては訓練固有の全対全通信優先機構を除き、関連するエキスパート同居部分を実装して比較する。
Googleの公開済み本番モデル統計を使い、B/16とB/32という2つのMoEモデル、各8エキスパート、4層分の交通情報をCOCOとImageNet条件から取り出してシミュレーション入力とする。4つの配置条件すべてで推論時間を測り、GPU利用率はゲート・FFN・集約の計算時間を総推論時間で割って定義する。異種同居条件では総当たり探索で得た最適解とも比較する。交通予測誤差への頑健性は第1層の交通行列を最適化入力にし、他3層の交通を順次ノイズとして加えて0〜75%の不正確さを模擬する。
評価はGoogle由来のMoE交通統計を使うシミュレーションであり、実GPU上のNCCL実行、カーネル干渉、PCIe/NVLink階層、スイッチ多段構成、要求到着の待ち行列、モデル品質は直接測定していない。クラスタ網は単一大型スイッチとして抽象化され、モデルは各8エキスパートのB/16・B/32に限定されるため、より大規模なLLM型MoEへ結果をそのまま外挿するには追加実機検証が必要である。
## 主要結果
Auroraは4条件すべてで比較対象より短い推論時間を示す。排他・同種では帯域競合を避ける通信順序によりSJF比最大1.38倍、排他・異種では人気エキスパートを高性能GPUへ割り当ててランダム配置比1.36〜1.81倍となる。異モデル間の同居効果が大きく、同種GPUではLina比1.25〜2.38倍、異種GPUでは1.91〜3.54倍高速化する。GPU利用率もLina比1.28〜1.50倍へ改善し、NP困難な異種同居条件の近似解は総当たり最適解の平均1.07倍に収まる。

- 排他・同種GPUでの推論高速化 / 最大1.38x (比較対象: SJF; 条件: B/16・B/32、COCO/ImageNet由来交通、100Gbps同種クラスタ) — 短い転送を優先するだけでは受信側帯域競合を避けられず、交通行列全体から競合しない順序を作るAuroraが同期通信の最後尾を短縮した。

- 排他・異種GPUでの推論高速化 / 1.36–1.81x (比較対象: ランダムGPU割当; 条件: 100/80/50/40Gbpsの異種クラスタ) — 処理トークン数の多い人気エキスパートを高性能GPUへ割り当てることで、同期層の最大完了時間を抑えた。

- 同居・同種GPUでの推論高速化 / 1.25–2.38x (比較対象: Lina; 条件: 異なる2モデルからエキスパートを同一GPUへ同居) — 同一モデル内同居では共有する同期通信障壁を避けにくいのに対し、異モデル間同居は片方の待ち時間へ他方の処理を重ねやすい。

- 同居・異種GPUでの推論高速化 / 1.91–3.54x (比較対象: LinaおよびランダムGPU割当+ランダム同居; 条件: 異種GPU上で2モデルを同居) — 同居相手とGPU割当の双方を最適化する効果が重なり、4条件中で最大の改善幅となった。

- GPU利用率 / Lina比1.28–1.50x、排他Aurora比1.57–1.72x (比較対象: LinaおよびAurora排他配置; 条件: 同居条件) — 異モデル同居で同期通信中の遊休時間を別モデルの処理へ使うため利用率が上がる。ただし同居による資源競合で推論時間自体も伸びるため、排他配置比で理想的な2倍には届かない。

- 異種同居近似の最適解との差 / 平均1.07x (比較対象: 総当たり探索の最適解; 条件: 同居・異種GPU条件) — NP困難な3次元マッチングを2段の二部マッチングへ分解しても、評価した交通条件では最適解に近い推論時間を維持した。

- 交通入力誤差への頑健性 / 最大性能劣化15.8% (比較対象: 正確な交通入力; 条件: 交通不正確さ0〜75%) — 75%ノイズでも異種排他では約1.90倍から1.60倍、異種同居では約2.0倍から1.80倍程度へ低下するに留まり、固定計画でも改善が残る。

### 負の結果・境界条件
- 異種同居条件では理論最適解を多項式時間で保証できず、Auroraは平均1.07倍の近似に留まる。交通行列が不正確になるほど高速化幅は低下し、最大15.8%の性能劣化を観測する。同居はGPU利用率を上げる一方、2エキスパートが計算資源を共有するため排他的なAuroraより各モデルの推論時間が長くなり得る。

### 結果の読み方
結果は、MoE推論の遅延が単なる総通信量ではなく、同期障壁の最後尾、受信帯域競合、人気エキスパートの配置先、同居するモデルの組合せで決まることを示す。特に異モデル間同居は通信待ちを別モデルの仕事で埋められるため、通信だけを速くする方式よりGPU遊休も同時に減らせる。
## 品質への影響
モデルのルーティング結果や重みを変更せず配置と通信順序を変えるため、論文は精度劣化を主要論点として扱っていない。ただし評価はシミュレーションであり、実機での通信順序制御や資源干渉が数値へ与える影響は未検証である。
## 既存研究との差
FasterMoE、Tutel、DeepSpeed-MoE等は全対全通信そのものの高速化や負荷均衡を主眼にするのに対し、Auroraは交通行列から転送順序を決め、さらにGPU割当とエキスパート同居まで同じ推論時間目的へ統合する。Linaは同一モデル内の複数エキスパートを同一GPUへ詰めて資源利用を改善するが、同じ同期全対全通信の障壁を共有する。Auroraは異なるモデル同士を同居させ、片方の待ち時間へ他方を重ねる点が中心的な差である。FlexMoEやProphet等の配置・複製系は人気度に応じてエキスパート位置を変えるが、Auroraは異種GPU性能と全対全通信順序を理論モデルへ同時に入れる。
## 限界
主要な制約は評価が実機ではなくシミュレーションである点で、NCCL等の集合通信実装、カーネル実行競合、GPUメモリ容量、PCIe/NVLink階層、多段ネットワーク、実際の要求到着揺らぎを含まない。交通行列を事前に知ることを基本とし、75%ノイズでも改善は残るものの性能は低下する。異種同居条件はNP困難で最適性を保証せず、評価上は平均1.07倍の差である。対象は各8エキスパートのB/16・B/32統計で、現代の大規模LLM型MoEにおける数十〜数百エキスパート、専門家並列とテンソル並列の併用は直接評価していない。著者も将来課題として異なるネットワーク構成・通信方式、変動負荷への動的適応、ジョブスケジューリングや網構成との統合を挙げる。
## 実装状態
2024年10月公開のarXivプレプリント。著者Rui Panの公式サイトとMax Planck Societyの公開基盤で全文PDFを確認した。論文はアルゴリズムとシミュレーションを提示するが、本文・一次公開先からAurora専用の公開コードリポジトリは確認できず、実機推論基盤へ統合済みとは判断できない。
## 研究上の位置づけ
MoE推論システム研究のうち、エキスパート配置と通信スケジューリングを共同最適化する系統に位置する。特に『通信量を減らす』のではなく、既に生じる不均一なトークン交通を競合しない順序へ並べ、人気エキスパートを適切なGPUへ置き、異モデル同居で同期待ちを隠すという三層の最適化を統一する。オフロード系がGPUメモリ容量とCPU/SSD転送を扱うのに対し、AuroraはGPUクラスタ内の専門家並列通信と配置が主対象であり、将来的にはエキスパートキャッシュや階層メモリ方式へ通信・配置最適化を組み合わせる比較軸になる。
