# Memory-Sovereign Inference: Output-Exact Execution Beyond Full Residency

> ストレージ支援推論の「全重みを常駐させない実行」を、表現量・意味的要求量・資源上限・出力完全一致・再利用遷移に分解して証明する枠組み。Qwen3-Nextで43.59 GiBの意味的要求を34 GiB枠内で64出力完全一致させる。

## 概要

Memory-Sovereign Inferenceは、**ストレージから重みを読みながらLLMを動かせた、という事実だけでは「メモリ容量を超えたモデルを正しく実行した」とは証明できない**というシステム評価上の問題を扱う。Linuxではファイルを読むとページキャッシュがcgroupへ課金される場合があり、プロセスの常駐集合サイズ（Resident Set Size; RSS）だけを見れば実際のホスト使用量を過小評価できる。GPUでもプロセス局所の値だけでは他プロセスやallocator外のボード使用量を見落とす。また非同期I/Oは古いバッファを誤って再利用しても、たまたま妥当な文章を生成して気づかない可能性がある。

論文はこの曖昧さを、実行証明書 `C=(I,B,A,E,L)` へ分解する。`I`はモデル表現と実際に意味的に要求されたバイト、`B`はメモリ階層ごとの境界、`A`はその境界が強制上限・物理容量・監査値のどれか、`E`は何をどこまで同一と比較したか、`L`は再利用バッファの寿命・世代遷移について実際に試験した範囲を記録する。速度だけでなく「何がメモリに収まらないのか」「誰が上限を保証するのか」「どの出力まで同じなのか」を反証可能にするのが中心貢献である。

主実験ではQwen3-Next Q4_K_Mの完全な正規テンソル表現が45.08 GiBで、32Kプリフィル中に標準ルータが48層×512個の管理対象専門家をすべて選択する。重複・重なりを除いた意味的要求下限は43.59375 GiBで、11 GiBホスト強制枠＋23 GiB GPU監査予算からなる宣言34 GiB常駐枠を9.59375 GiB上回る。それでもLRU64経路はRTX 3090上で契約内に収まり、64出力をゼロキャッシュオラクルと完全一致させた。

別の一致 ソース実験では、カーネルページキャッシュを使うバッファ付き経路は出力自体は正しいものの11 GiB上限へ到達し、33,481件の`memory.max`イベントを記録して事前の合格条件に失敗した。1窓のブロック O_DIRECTと8窓の非同期O_DIRECTはどちらも資源契約と出力一致を満たし、6組の反転順序比較で非同期側の壁時計時間はブロック側の32.3%だった。ただしこの差はキュー深さ、I/Oと計算の重畳、バッファ寿命実装を同時に変更しており、「非同期化だけで3.10倍」と分解してはいない。

## 背景：オフロード研究で「モデルが載った」をどう証明するか

GPUメモリに全重みが載らない場合、CPU DRAMやSSDへ重みを逃がし、必要な層・専門家だけをGPUへ運ぶ方式が使われる。MoEでは一トークンが全専門家を使わないため、とくにストレージ階層との相性がよい。しかし「モデル全体が45 GiBでGPUが24 GiBだから、生成できれば容量超過推論を証明した」とは限らない。ある入力が実際には10 GiB分の専門家しか選ばなければ、その実行だけから45 GiBの需要を示せないためである。

そこで本研究は**表現量とワークロード需要量を別々に証明する**。さらに、必要になった重み量と実際にストレージから読んだバイトも分ける。キャッシュ命中があれば意味的には重みを必要としていても物理I/Oは発生しないし、alignmentや再読があれば物理I/Oは意味的需要より増える。この区別がないと、キャッシュやプリフェッチの効果と「そもそも必要なかった重み」を混同する。

もう一つは資源計測の境界である。プロセスRSSはページ キャッシュを直接表さず、CUDAのプロセス値はwhole-board利用量と一致しない場合がある。本研究は「ホストはcgroup 離散 上限」「GPUは物理ボード容量＋whole-board sampled audit」のように、資源ごとに証拠の強さを明記する。GPUは離散 partitionではなく監査値なので、ホストと同じ強さの主張をしていない点も重要である。

## 問題設定

研究が証明したいのは単なる低メモリ動作ではなく、少なくとも次の三点を同時に満たす実行である。

- ワークロードが意味的に要求したユニーク重み量が、宣言された同時常駐枠を超える。
- 実行中のホスト・GPU使用量が、権威ある資源境界の内側にある。
- ストレージ・キャッシュを介した実行結果が、指定したオラクルと指定した出力範囲で一致する。

非同期化を加える場合はさらに、I/O ウィンドウやGPU スロットを再利用する時に、古いリクエストの完了通知・世代番号・民生参照が次のリクエストへ混ざらないことも必要になる。これは性能最適化の付帯条件ではなく、正しさの一部として扱われる。

## 手法のあらまし

論文は新しい単一キャッシュ 方針を提案するというより、ストレージ支援推論を検証可能にする共通Planと証明書を組み合わせる。

1. モデルテンソルを正規化したオブジェクトとして構成品目し、論理バイトとalignment後の物理バイトを分離する。
2. ルータが実際に選んだオブジェクトの重複なし和集合から意味的要求下限を作る。
3. ホストウィンドウ数とGPU 専門家 スロット数を独立に上限化する。
4. 不一致時だけ上限付き ソース serviceへ読み出しを発行し、完了したウィンドウを予約済みGPU スロットへcopyする。
5. 機器 イベントで公開可能になった世代だけを民生へ渡し、使用終了後にticketを解放する。
6. 全出力ロジット、route、ソース/destination 識別子までオラクルと比較し、検証範囲外の状態は明示的に除外する。

## 手法

### 1. 証明書 `C=(I,B,A,E,L)`

`I`（構成品目）は四つの量を分ける。完全なテンソル payload `T_repr`、実モデルグラフが少なくとも一度消費したユニーク論理バイト下限 `U_sem^LB`、キャッシュ/ソース 方針が要求した重複除去union `U_sched`、再読やpaddingを含む累積通信量 `Q_run`である。

これにより、たとえば「43.6 GiBを意味的に使ったが、LRU 命中によって毎回43.6 GiBをSSDから読んだわけではない」と表現できる。容量証明とI/O効率を同じバイト数で代用しないのが重要である。

`B`と`A`は各階層の上限とその権威を組にする。離散-enforced 上限、物理容量、instrumented high-water mark、sampled auditは証拠強度が異なるため、同一視しない。`E`は比較対象、同値関係、出力horizonを固定し、`L`はバッファ再利用で検査した遷移を列挙する。

### 2. 正規object inventoryと意味的需要

各アダプタは読み込み時にnative テンソルの正確な範囲をオブジェクトとして構成品目する。Qwen AWQ、Qwen3.6 Q4_K_M、Gemma QAT Q4_0、Qwen3-Next Q4_K_Mでは命名やbundle規則が異なるため、共通の「ファイルサイズ」だけでは扱わない。

意味的需要は、authoritative モデル グラフが実際に選択し消費した管理対象オブジェクトの正規unionとして計算する。重複するextentや同じオブジェクトの複数回利用は一回だけ数える。これによって、MoEの疎ルーティングでも「このワークロード自身が常駐枠を超える量を要求した」と示せる。

### 3. bounded source serviceと独立したhost/GPU容量

キャッシュ 不一致はソース serviceへ送られ、限られた数のホスト ウィンドウへ読み込まれる。完了したウィンドウは予約されたGPU スロットへcopyされ、機器 イベントがreadyになってから民生へ公開される。ホスト ウィンドウ数とGPU スロット数は独立に管理されるため、「ホスト側I/O並列度を増やしたらGPU キャッシュ容量まで増えた」といった交絡を避けられる。

O_DIRECT経路ではページ キャッシュへの暗黙の常駐を避け、alignmentを含む物理ソース バイトを記録する。バッファ付き経路も比較対象として残し、出力が正しくてもホスト 離散 上限へ張り付けば資源契約では不合格にする。

### 4. stable slot、ticket、generationによる寿命管理

非同期I/Oでは、ソース ウィンドウの読み込み完了、GPU copy、カーネル 民生の使用終了が別々の時刻になる。ウィンドウを早く再利用し過ぎれば、前世代のcopy中に新しい重みで上書きできる。逆に保守的に待ち過ぎれば並列性が失われる。

PlanはウィンドウとGPU スロットに独立したライフサイクルを持たせ、ticketとgenerationで「どのリクエストがどの世代を消費しているか」を追う。ready publicationは機器 イベント後に行い、民生終了までスロットを解放しない。reset/shutdown時にも未回収ticketやウィンドウが残らないことを検査する。

### 5. temporal / spatial amortization

一度読み込んだ専門家をLRU64で保持する時間的再利用と、複数I/O ウィンドウを並行して計算と重ねる空間・時間的重畳を別の仕組みとして扱う。主32K+64実験では長いプリフィルがデコード用キャッシュを温めるため、後続デコードはwarm状態で始まる。

別の一致 ソース実験ではキャッシュ 方針をLRU64に固定し、ソース ownershipだけをバッファ付き P、blocking O_DIRECT D、8-ウィンドウ asynchronous O_DIRECT Fへ変える。これにより「ページ キャッシュへ逃げる経路」と「明示的に上限付きなdirect I/O」の資源挙動を比較する。

## 評価

### まず見るところ

- **容量超過の証拠:** 完全表現45.08 GiB、意味的要求下限43.59375 GiBに対し、宣言常駐枠は34 GiB。
- **主実行:** 32,768-トークン プリフィル + 64 出力、RTX 3090、層 LRU64。
- **出力一致:** 64 トークン ID、64本すべての151,936-float logit 行、3,408 route イベント、response、民生/destination 識別子がzero-キャッシュ 理想条件とbitwise一致。
- **資源:** ホスト 離散 11 GiB、GPU audited 23 GiB on 24 GiB physical board。主セルでは入替え/OOM/メモリ.max/foreign-計算 イベントは0。
- **非同期ソース:** 6対比較でF/D壁時計比0.3229。平均101.739 s→32.852 s。ただし待機列 深さ・重畳・ライフサイクルを同時変更。
- **負の結果:** バッファ付き Pは理想条件-exactでも11 GiB ceilingに達し33,481 メモリ.max eventsを出し、事前の資源合格条件には失敗。

### 主実験の条件

| 項目 | 条件 |
|---|---|
| モデル | Qwen3-Next Q4_K_M |
| GPU | RTX 3090、物理24 GiB |
| GPU契約 | whole-board監査予算23 GiB |
| ホスト契約 | complete process treeにcgroup 離散 11 GiB |
| 入力 | 32,768 トークン mechanics プロンプト |
| 出力 | 64 トークン |
| キャッシュ | 層 LRU64 |
| オラクル | 同一実行識別子のprespecified zero-キャッシュ |
| 完全表現 | 45.08 GiB |
| 意味的要求下限 | 43.59375 GiB |
| 宣言全体-residency envelope | 34 GiB |

### 主実験の結果

| 指標 | 結果 | 解釈 |
|---|---:|---|
| 意味的要求下限 − 常駐枠 | +9.59375 GiB | ワークロード自身が同時常駐枠を超える重みを必要とした |
| プリフィル | 86.355 s | 長いプリフィルでLRU64をwarm |
| デコード | 6.454 s / 63 transitions | 9.762 transitions/s |
| complete-process-tree ホスト peak | 1,496,981,504 バイト | 11 GiB 離散 上限内 |
| whole-board GPU peak | 13,218,807,808 バイト | 23 GiB audit budget内 |
| 64 トークン IDs | 完全一致 | zero-キャッシュ 理想条件比較 |
| 64 全体 logit rows | 38,895,616 バイト/armが一致 | 最終トークンだけでなく全語彙logitを比較 |
| route events | 3,408件すべて一致 | MoE ルーティングまで確認 |
| 入替え/OOM/メモリ.max events | 0 | 主セルの資源契約を通過 |

ここで「43.59 GiBを要求した」の意味は、同時に全オブジェクトがliveだったという意味ではない。32Kプリフィル中にauthoritative グラフが少なくとも一度使用したユニーク管理専門家 バイトの下限である。また非専門家 テンソルをすべて含むワークロード需要総量でもない。この限定を明記することで、容量主張を必要以上に広げない。

### LRU64再利用の診断

主張の中心ではない機構診断として、512入力+64出力では再利用なし5.037 トークン/s、LRU64あり11.636 トークン/sを報告する。これは同一識別子でretentionが効く理由を示すが、一つの短いwarm-キャッシュ観測であり、キャッシュ 方針一般の比較研究ではない。

### matched source実験

モデルバイト、グラフ、sampler、LRU64、8,192-トークン自然文、128 greedy outputs、オブジェクト順序、11 GiB ホスト契約、23 GiB GPU契約を固定し、ソース実装を三つに変える。

| 経路 | ソース | 資源結果 | 正しさ | 完全wall time |
|---|---|---|---|---:|
| P | カーネル ページ キャッシュを使うバッファ付き | 11 GiB ceiling、33,481 上限 events | 理想条件-exact | 合格条件外 |
| D | 1 fixed ウィンドウ blocking O_DIRECT | 正のmargin、上限 イベント 0 | 理想条件-exact | 平均101.739 s |
| F | 8 registered ウィンドウ async O_DIRECT | 正のmargin、上限 イベント 0 | 理想条件-exact | 平均32.852 s |

6つの事前順序付きcounterbalanced D/F 組で、幾何平均F/D wall比は0.322913、95% paired-log t intervalは[0.320090, 0.325762]だった。物理ソース バイト/出力比は1.0で、Fは各cell 55,520 ソース 演算を発行・完了し、peak 深さは8、終了時に全ウィンドウがfreeへ戻る。

この比較は「同じバイトを読むなら並列I/Oが速い」ことを示すが、FはDに対して待機列 深さ、重畳、ライフサイクル implementationをまとめて変更している。論文自身も同一implementationで待機列 深さだけをsweepしない限り、3.10倍の逆数を単一要因へ帰属できないとしている。

### fault / fail-closed評価

後期のQwen3-NextとGemma 4 buildでは、事前に定義した14個の制御/障害 cellがvalidatorを通過した。fatalなcellでは無効な状態を公開せず、recoverable cellでは制御と一致する。これはnamed transitionについてfail-closedに振る舞う証拠である。

ただし、14件の成功から一般的な故障率、race freedom、全interleavingの安全性を推定してはいない。またこの障害 campaignの二値は主32K+64セルと同一ではないため、証拠packageとしては関連するが「主実行そのものに障害を注入した」とは主張しない。

### 評価上の制約

- 主実験は一つのQwen3-Next量子化、mechanics プロンプト、ランタイム、RTX 3090、64-出力 horizonに限定される。
- semantic-demand値はmanaged 専門家 bundleの下限であり、全テンソルが同時liveだったという意味ではない。
- 全体-出力 理想条件はrecurrent/混成-状態 バイトや未改変上流 ランタイム全体の一致を検査しない。
- GPUは離散 partitionではなくsampled auditである。
- 6対の非同期比較は一つの固定ワークロード populationで、他のプロンプト、機器、ストレージへ直接一般化できない。
- RTX 3080 Tiを使う別記録では物理CPUとprovider ストレージ モデルが記録されず、ハードウェア-normalized ストレージ claimには使えない。
- 「資源 admissibility」を「他手法より製品性能が高い」という主張へ読み替えない。

## 既存研究との差

FlexGen、LLM in a Flash、MoE-Infinity、WiSPなどのオフロード研究は、限られたDRAM/VRAMでモデルを実行する機構、キャッシュ、プリフェッチ、I/O スケジューラを主に改善する。本研究はそれらと同じ軸で新しい最適キャッシュを競うのではなく、**ストレージ支援推論の主張を第三者が反証できるよう、必要バイト・資源authority・出力exactness・ライフサイクルを共通証明書へ揃える**ことを主眼に置く。

とくに「低RSS」「生成成功」「トークン一致」のどれか一つを十分条件にしない。ページキャッシュを含むprocess-tree charge、whole-board GPU観測、全語彙logit、route、ソース/destination 識別子まで別々に保存することで、性能結果と正しさ結果を分離する。

## 限界・実装状況

この研究の強みは主張範囲を狭く固定している点でもある。64トークン完全一致は長期生成の完全一致を意味せず、Qwen3-Nextでの結果はGemmaや別MoEの性能を保証しない。GPU境界も監査であり離散 enforcementではない。

また、論文には意図的な停止結果も含まれる。GPT-OSSのpacking最適化は物理carrier問題を解消できず、Llama-3.3の配置結果は資源条件を満たしてもタスク-受入れ criterionに失敗した。こうした負の結果を「局所的に動いたのでシステム成功」と昇格させない姿勢が、本稿の証明書設計と整合している。
