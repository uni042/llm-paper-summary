# EPS-MoE: Expert Pipeline Scheduler for Cost-Efficient MoE Inference

> expert単位にtokenをhorizontal splitし、負荷別GEMM選択とSM制限でall-to-all通信を計算へ重畳するMoE向けExpert Pipeline Scheduler。

## 概要

Mixture-of-Experts（MoE）では各tokenをrouterがTop-K expertへ送り、選ばれたexpertのFFNだけを計算する。総parameter数を大きくしても1 token当たりの活性parameterを抑えられる一方、複数GPUへexpertを分散すると**tokenをexpert所有GPUへ送るdispatch all-to-all**と、expert出力を元GPUへ戻すcombine通信が必要になる。

さらにexpertごとのtoken数はroute結果でばらつく。GPUでは同じ形の小GEMMをexpertごとにまとめるGroupGEMMが使われるが、token数が少ないdecodeと、token数が多いprefillでは最適kernelが同じとは限らない。論文のmicrobenchmarkではinput row数が2048未満ではGroupGEMMが有利だが、4096以上ではDenseGEMMの方が高効率になる領域を観測する。

通信と計算を単純に「all-to-all完了→全expert GEMM→all-to-all」の順で実行すると、通信中はTensor Coreが遊び、GEMM中はnetwork側を十分使えない。しかもGEMMや通信kernelはGPUの全SMを占有しなくてもthroughputが飽和する領域があり、余ったSMを別kernelへ回せる。

EPS-MoEはこの2つの観察を使い、MoE FFNをexpert group単位のpipelineへ分解する。token tensorを**行方向（token方向）にsplit**し、対応expert weightもexpert単位で分け、必要tokenだけを次groupへ送る。各groupではloadに応じてGroupGEMM/DenseGEMMを選び、GEMMとall-to-allへ必要最小限のSMを割り当てて並行実行する。

8×H800のDeepSeekV2では報告済み約100K tokens/sのprefillを121.8Kへ、Mixtral 8×7Bは71.84K→94.89K、DBRXは37.23K→56.74Kへ改善する。最大改善はDBRXの52.4%である。

## 問題設定

### MoEでは「疎だから計算が少ない」だけでは速くならない

1 tokenがTop-K expertだけ使うので理論FLOPsはdense FFNより小さくできる。しかしbatch内では異なるtokenが異なるexpertを選ぶ。batchが大きくなると多くのexpertが同時に活性化され、weight memory trafficも増える。

例えばMixtral 8×7Bは1 token当たり活性parameterは約12.6Bでも、大batchでは合計46B parameter相当を読む場合がある。expertをGPU間へ分ければweightを分散できるが、その代わりtoken activationをall-to-allで交換する。

Top-Kが大きいほど1 tokenを複数deviceへ送るため通信量も増える。GEMMだけを高速化すると逆に全体時間に占める通信比率が増え、次のbottleneckになる。

### GroupGEMMは常にDenseGEMMより良いわけではない

GroupGEMMはexpertごとの異なるweight matrixへ異なるtoken groupをまとめて投入でき、small expert workloadでは便利である。一方input rowsが十分大きいと、regularなDenseGEMMの方がTensor Core利用率を上げやすい。

EPS-MoEのprofilingではm<2048ではGroupGEMMが優位、m≥4096では同じ計算量ならDenseGEMMが上回る傾向を示す。またGroupGEMMは一定loadを超えるとgroup数や使用SM数を増やしてもthroughputがほぼ伸びない。

つまり「expert数が多いから常にGroupGEMM」という固定選択では、prefillの大loadで性能を捨てる。EPS-MoEはpipeline分割とkernel typeをload-awareに選ぶ。

### 通信kernelも全SMを必要としない

all-to-allはnetworkだけでなくGPU SMも使う。しかしA100/NVLinkの測定では10〜20 SM程度を超えても通信latencyがほぼ改善しない領域がある。Silu activation等のmemory-bound kernelも、loadに応じて40〜60 SMで性能が飽和する。

したがって1 kernelへ全SMを占有させるのではなく、throughputをほぼ保てるところまでSMを絞り、残りSMで別のcompute/communicationを同時進行できる。

## 手法

### 1. Model構造に合わせてAttentionとMoEのparallelismを分ける

EPS-MoEは「全layerを同じTP」で処理しない。AttentionとMoE FFNを別に考え、Attention TP + MoE TP、Attention DP + MoE EP、Attention TP + MoE EPを比較する。

Expert Parallelism（EP）はexpert weightをdevice間へ分散し、tokenを所有expertへ送る方式である。MoE部のweight read量を1/Dへできる一方、dispatch/combine all-to-allが発生する。

DeepSeekV2のMLAのようにAttention側TPが追加communicationを作る構造ではAttention DP + MoE EPを選び、MHA/GQA/MQAでAttention weight自体が大きい場合はTP + EPを選ぶ。このparallel strategyが後段pipelineで使える通信primitiveを決める。

### 2. TP+EPではAllReduceを分解してpipeline可能にする

通常TPではncclAllReduceを使うが、一枚岩のcollectiveのままではexpert all-to-allとGEMMへ細かく重畳しにくい。

EPS-MoEはdispatch側でAllReduceを **ReduceScatter + all-to-all**、combine側で **all-to-all + AllGather** へ分ける。これによりall-to-all部分をexpert pipelineの各chunkと対応付け、GEMMとのoverlap点を作る。

通信量の解析ではDP+EP < TP+EP < TP+TPとなり、MoE FFNのmemory I/OもEPを使う2方式がTP+TPより小さい。モデルのAttention構造とweight replication trade-offに応じて選択する。

### 3. Horizontal Split — token行方向に分け、weightはexpert単位に保持する

pipelineを作る方法には、input matrixを行方向に分けるhorizontal splitと、feature列方向に分けるvertical splitがある。

vertical splitでは各pipeline stageが同じexpert weightを繰り返し読む形になりやすく、output activationのI/Oもstage数Nに比例して増える。horizontal splitならtoken subsetだけを各stageへ流し、expert weightはexpert group単位に分割できるためweightの反復I/Oを避けられる。

各stageでは「このexpert groupが必要とするtokenだけ」を送信する。Expert0にtoken [0,1,5,9]だけ必要なら、それだけをGPUへ送り、そのexpert groupの計算が終わり次第、次communicationを開始できる。

### 4. Load-aware GroupGEMM / DenseGEMM switching

pipeline number PNを増やすと1 stage当たりのexpert数・token loadが変わる。small loadでは複数expertをGroupGEMMでまとめる方が効率的だが、expert groupが1つになる／mが大きい条件ではDenseGEMMへ落とす方が速い。

EPS-MoEはprofilingしたkernel throughput curveを基に、現在stageのloadへ適した実装を選ぶ。DeepSeekV2のfine-grained expertsではこの切替だけ（PN=1、pipeline overlapなし）でもprefillを約5〜12%改善する条件がある。

### 5. Expert Pipeline — token単位で通信と計算を前倒しする

全expert計算が終わるまでcombine通信を待つのではなく、あるtokenについて選択expertの計算が全て終わった時点で、そのtokenのLocalReduceと次のall-to-allを開始する。

同時に別token/expert groupではGEMMを続ける。これによりcommunication・compute・memory-bound reduceを異なるstageとして流し、layer内部でpipeline化する。

### 6. SM Resource Control — overlapのために「あえて全SMを使わない」

GEMMとall-to-allを同時launchしても、片方が全SMを占有すればoverlapしない。EPS-MoEはmicrobenchmarkで「これ以上SMを増やしてもthroughputがほとんど伸びない」点を探し、その数にkernelを制限する。

例えばcommunicationは10〜20 SM、Silu等はloadに応じ40〜60 SM程度で飽和する。Group/Dense GEMMも一定範囲でSMを減らしても性能を維持できるため、余剰SMを通信へ渡す。

つまりoverlapは単にCUDA streamを分けるだけではなく、**各kernelのresource saturation pointを利用して同居させる**。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| models | DeepSeekV2、Mixtral 8×7B、DBRX、Snowflake Arctic |
| DeepSeekV2 / DBRX | 8×H800-80GB SXM |
| Mixtral | 4×H800-80GB SXM |
| 評価中心 | prefill throughput / TTFT |
| pipeline parameter | Pipeline Number（PN） |
| 比較 | model既存実装、vLLM、TP+EP、PN=1/2/5/20等 |

### 代表結果

| model | baseline | EPS-MoE | 改善 |
|---|---:|---:|---:|
| DeepSeekV2 | 100K tokens/s | 121.8K | +21.8% |
| Mixtral 8×7B | 71.84K tokens/s | 94.89K | +32.2% |
| DBRX | 37.23K tokens/s | 56.74K | +52.4% |

DeepSeekV2ではsequence 1KでPN=5が+21.81%、2Kで+20.53%、4Kで+16.89%、8Kで+12.75%となる。sequenceが伸びて1 stage当たりGEMMが大きくなると、通信overlapの相対利得や最適PNが変わるため、pipelineを細かくすれば常に良いわけではない。

MixtralではTP+EPだけでもTTFTを約8〜14%減らすが、kernel switchingを含むPN=1で約16〜20%、PN=2までpipeline化すると多くの条件で約18〜24%へ広がる。DBRXではPN=2で約23〜30%短縮する条件がある。

## 既存研究との差

Expert Parallelismはexpertを分散してmemoryを減らすが、通常はdispatch→GEMM→combineを大きなoperator単位で処理する。Kernel fusion/GroupGEMM最適化はcomputeを速くするが、速くした分communication比率が増える。

EPS-MoEは**expert sparsityをpipeline partitionへ利用し、kernel shape選択とSM resource partitionをcommunication overlapまで一体で決める**。特定collectiveだけを高速化するのではなく、MoE FFN layer内の実行順序を組み替える。

## 限界

最適PN、GroupGEMM/DenseGEMM境界、SM割当はGPU世代、expert数、Top-K、batch/sequence length、interconnectに依存する。論文で観測したm=2048/4096付近や10〜20 communication SMを別GPUへ固定適用するものではない。

pipelineを細かくし過ぎるとstage管理・kernel launch・communication chunk overheadが増える。DeepSeekV2でもPN=20がPN=5を下回る条件があり、常に最大分割が最速ではない。

またheadlineはprefill throughput中心であり、decodeではtoken loadが小さくGroupGEMM側の条件が変わる。online servingのrequest-level latencyやmulti-node networkで同じ改善率を得るかは別途評価が必要である。
