# EPS-MoE: Expert Pipeline Scheduler for Cost-Efficient MoE Inference

> 専門家単位にトークンを水平 分割し、負荷別GEMM選択とSM制限で全対全通信通信を計算へ重畳するMoE向けExpert Pipeline Scheduler。

## 概要

Mixture-of-Experts（MoE）では各トークンをルーティングがTop-K 専門家へ送り、選ばれた専門家のFFNだけを計算する。総パラメータ数を大きくしても1 トークン当たりの活性パラメータを抑えられる一方、複数GPUへ専門家を分散すると**トークンを専門家所有GPUへ送る分配 全対全通信**と、専門家出力を元GPUへ戻す結合通信が必要になる。

さらに専門家ごとのトークン数はroute結果でばらつく。GPUでは同じ形の小GEMMを専門家ごとにまとめるGroupGEMMが使われるが、トークン数が少ないデコードと、トークン数が多いプリフィルでは最適カーネルが同じとは限らない。論文のマイクロベンチマークでは入力 row数が2048未満ではGroupGEMMが有利だが、4096以上ではDenseGEMMの方が高効率になる領域を観測する。

通信と計算を単純に「全対全通信完了→全専門家 GEMM→全対全通信」の順で実行すると、通信中はTensor Coreが遊び、GEMM中はネットワーク側を十分使えない。しかもGEMMや通信カーネルはGPUの全SMを占有しなくてもスループットが飽和する領域があり、余ったSMを別カーネルへ回せる。

EPS-MoEはこの2つの観察を使い、MoE FFNを専門家 グループ単位のパイプラインへ分解する。トークン テンソルを**行方向（トークン方向）に分割**し、対応専門家 重みも専門家単位で分け、必要トークンだけを次グループへ送る。各グループでは読み込みに応じてGroupGEMM/DenseGEMMを選び、GEMMと全対全通信へ必要最小限のSMを割り当てて並行実行する。

8×H800のDeepSeekV2では報告済み約100K トークン/sのプリフィルを121.8Kへ、Mixtral 8×7Bは71.84K→94.89K、DBRXは37.23K→56.74Kへ改善する。最大改善はDBRXの52.4%である。

## 問題設定

### MoEでは「疎だから計算が少ない」だけでは速くならない

1 トークンがTop-K 専門家だけ使うので理論FLOPsは密 FFNより小さくできる。しかしバッチ内では異なるトークンが異なる専門家を選ぶ。バッチが大きくなると多くの専門家が同時に活性化され、重み メモリ trafficも増える。

例えばMixtral 8×7Bは1 トークン当たり活性パラメータは約12.6Bでも、大バッチでは合計46B パラメータ相当を読む場合がある。専門家をGPU間へ分ければ重みを分散できるが、その代わりトークン 活性値を全対全通信で交換する。

Top-Kが大きいほど1 トークンを複数deviceへ送るため通信量も増える。GEMMだけを高速化すると逆に全体時間に占める通信比率が増え、次のボトルネックになる。

### GroupGEMMは常にDenseGEMMより良いわけではない

GroupGEMMは専門家ごとの異なる重み matrixへ異なるトークン グループをまとめて投入でき、small 専門家 ワークロードでは便利である。一方入力 rowsが十分大きいと、regularなDenseGEMMの方がTensor Core利用率を上げやすい。

EPS-MoEのプロファイリングではm<2048ではGroupGEMMが優位、m≥4096では同じ計算量ならDenseGEMMが上回る傾向を示す。またGroupGEMMは一定読み込みを超えるとグループ数や使用SM数を増やしてもスループットがほぼ伸びない。

つまり「専門家数が多いから常にGroupGEMM」という固定選択では、プリフィルの大読み込みで性能を捨てる。EPS-MoEはパイプライン分割とカーネル typeを負荷認識に選ぶ。

### 通信kernelも全SMを必要としない

全対全通信はネットワークだけでなくGPU SMも使う。しかしA100/NVLinkの測定では10〜20 SM程度を超えても通信遅延がほぼ改善しない領域がある。Silu 活性値等のメモリ律速 カーネルも、読み込みに応じて40〜60 SMで性能が飽和する。

したがって1 カーネルへ全SMを占有させるのではなく、スループットをほぼ保てるところまでSMを絞り、残りSMで別のcompute/通信を同時進行できる。

## 手法

### 1. Model構造に合わせてAttentionとMoEのparallelismを分ける

EPS-MoEは「全層を同じTP」で処理しない。AttentionとMoE FFNを別に考え、Attention TP + MoE TP、Attention DP + MoE EP、Attention TP + MoE EPを比較する。

Expert Parallelism（EP）は専門家 重みをdevice間へ分散し、トークンを所有専門家へ送る方式である。MoE部の重み read量を1/Dへできる一方、分配/結合 全対全通信が発生する。

DeepSeekV2のMLAのようにAttention側TPが追加通信を作る構造ではAttention DP + MoE EPを選び、MHA/GQA/MQAでAttention 重み自体が大きい場合はTP + EPを選ぶ。この並列 戦略が後段パイプラインで使える通信primitiveを決める。

### 2. TP+EPではAllReduceを分解してpipeline可能にする

通常TPではncclAllReduceを使うが、一枚岩の集合通信のままでは専門家 全対全通信とGEMMへ細かく重畳しにくい。

EPS-MoEは分配側でAllReduceを **ReduceScatter + 全対全通信**、結合側で **全対全通信 + AllGather** へ分ける。これにより全対全通信部分を専門家 パイプラインの各chunkと対応付け、GEMMとの重畳点を作る。

通信量の解析ではDP+EP < TP+EP < TP+TPとなり、MoE FFNのメモリ I/OもEPを使う2方式がTP+TPより小さい。モデルのAttention構造と重み replication trade-offに応じて選択する。

### 3. Horizontal Split — token行方向に分け、weightはexpert単位に保持する

パイプラインを作る方法には、入力 matrixを行方向に分ける水平 分割と、feature列方向に分ける垂直 分割がある。

垂直 分割では各パイプライン 段が同じ専門家 重みを繰り返し読む形になりやすく、出力 活性値のI/Oも段数Nに比例して増える。水平 分割ならトークン subsetだけを各段へ流し、専門家 重みは専門家 グループ単位に分割できるため重みの反復I/Oを避けられる。

各段では「この専門家 グループが必要とするトークンだけ」を送信する。Expert0にトークン [0,1,5,9]だけ必要なら、それだけをGPUへ送り、その専門家 グループの計算が終わり次第、次通信を開始できる。

### 4. Load-aware GroupGEMM / DenseGEMM switching

パイプライン number PNを増やすと1 段当たりの専門家数・トークン 読み込みが変わる。small 読み込みでは複数専門家をGroupGEMMでまとめる方が効率的だが、専門家 グループが1つになる／mが大きい条件ではDenseGEMMへ落とす方が速い。

EPS-MoEはプロファイリングしたカーネル スループット curveを基に、現在段の読み込みへ適した実装を選ぶ。DeepSeekV2のfine-grained エキスパートではこの切替だけ（PN=1、パイプライン 重畳なし）でもプリフィルを約5〜12%改善する条件がある。

### 5. Expert Pipeline — token単位で通信と計算を前倒しする

全専門家計算が終わるまで結合通信を待つのではなく、あるトークンについて選択専門家の計算が全て終わった時点で、そのトークンのLocalReduceと次の全対全通信を開始する。

同時に別トークン/専門家 グループではGEMMを続ける。これにより通信・compute・メモリ律速 reduceを異なる段として流し、層内部でパイプライン化する。

### 6. SM Resource Control — overlapのために「あえて全SMを使わない」

GEMMと全対全通信を同時launchしても、片方が全SMを占有すれば重畳しない。EPS-MoEはマイクロベンチマークで「これ以上SMを増やしてもスループットがほとんど伸びない」点を探し、その数にカーネルを制限する。

例えば通信は10〜20 SM、Silu等は読み込みに応じ40〜60 SM程度で飽和する。Group/Dense GEMMも一定範囲でSMを減らしても性能を維持できるため、余剰SMを通信へ渡す。

つまり重畳は単にCUDA ストリームを分けるだけではなく、**各カーネルの資源 saturation pointを利用して同居させる**。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| models | DeepSeekV2、Mixtral 8×7B、DBRX、Snowflake Arctic |
| DeepSeekV2 / DBRX | 8×H800-80GB SXM |
| Mixtral | 4×H800-80GB SXM |
| 評価中心 | プリフィル スループット / TTFT |
| パイプライン パラメータ | Pipeline Number（PN） |
| 比較 | モデル既存実装、vLLM、TP+EP、PN=1/2/5/20等 |

### 代表結果

| モデル | 比較対象 | EPS-MoE | 改善 |
|---|---:|---:|---:|
| DeepSeekV2 | 100K トークン/s | 121.8K | +21.8% |
| Mixtral 8×7B | 71.84K トークン/s | 94.89K | +32.2% |
| DBRX | 37.23K トークン/s | 56.74K | +52.4% |

DeepSeekV2では系列 1KでPN=5が+21.81%、2Kで+20.53%、4Kで+16.89%、8Kで+12.75%となる。系列が伸びて1 段当たりGEMMが大きくなると、通信重畳の相対利得や最適PNが変わるため、パイプラインを細かくすれば常に良いわけではない。

MixtralではTP+EPだけでもTTFTを約8〜14%減らすが、カーネル switchingを含むPN=1で約16〜20%、PN=2までパイプライン化すると多くの条件で約18〜24%へ広がる。DBRXではPN=2で約23〜30%短縮する条件がある。

## 既存研究との差

Expert Parallelismは専門家を分散してメモリを減らすが、通常は分配→GEMM→結合を大きな演算子単位で処理する。Kernel 融合/GroupGEMM最適化はcomputeを速くするが、速くした分通信比率が増える。

EPS-MoEは**専門家 sparsityをパイプライン partitionへ利用し、カーネル 形状選択とSM 資源 partitionを通信 重畳まで一体で決める**。特定集合通信だけを高速化するのではなく、MoE FFN 層内の実行順序を組み替える。

## 限界

最適PN、GroupGEMM/DenseGEMM境界、SM割当はGPU世代、専門家数、Top-K、バッチ/系列 length、interconnectに依存する。論文で観測したm=2048/4096付近や10〜20 通信 SMを別GPUへ固定適用するものではない。

パイプラインを細かくし過ぎると段管理・カーネル launch・通信 chunk オーバーヘッドが増える。DeepSeekV2でもPN=20がPN=5を下回る条件があり、常に最大分割が最速ではない。

またheadlineはプリフィル スループット中心であり、デコードではトークン 読み込みが小さくGroupGEMM側の条件が変わる。online 推論提供のリクエスト-level 遅延やmulti-node ネットワークで同じ改善率を得るかは別途評価が必要である。
