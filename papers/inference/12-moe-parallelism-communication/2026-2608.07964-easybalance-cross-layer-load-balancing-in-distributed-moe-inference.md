# EasyBalance: Cross-Layer Load Balancing in Distributed MoE Inference

## 概要
専門家並列（expert parallelism; EP）ではトークンを担当専門家のGPUへall-to-allで配送し、専門家計算後に結果を戻す。ルーティングが偏ると、軽いGPUも最重負荷GPUの終了を待つため、専門家数を均等配置しても実行時間は最大負荷に支配される。従来の専門家複製や移動はホット専門家を分散できるが、追加メモリ、パラメータ転送、タスク別ルーティング統計への依存が生じる。

EasyBalanceは専門家配置を変更せず、マイクロバッチ間に依存がないことを利用する。各マイクロバッチは自身の層順序だけ守ればよいため、あるバッチを次層へ進め、別バッチを前層に待たせられる。異なる層のMoE負荷を同じ実行段階で組み合わせ、ピークGPUが異なる負荷同士を相殺する。ベクトル負荷 `w_j` に対して `max(sum w_j) <= sum max(w_j)` が成立するため、著者のモデルでは組合せは最悪でも別々に実行した計算負荷を超えない。

8×A800-SXM4 80GB上でQwen3-30B-A3B、Moonlight-16B-A3B、Qwen3-235B-A22BをLongBenchで評価する。多くの条件でGPU未利用率を40%以上削減し、Qwen3-30B・2wikimqaでは4マイクロバッチのスケジューリング費が0.277 ms/stepに対しend-to-end 8.21 sで、制御費は小さい。

## 問題設定
MoE推論では各層のルータがトークンごとに上位k専門家を選ぶ。EPでは専門家をD台へ分散し、層lのGPU別トークン負荷を `w^(l)` とすると、同期的な集約のため実効計算量は `max(w^(l))` に支配される。学習時に負荷均衡損失を入れていても、推論入力ごとの専門家選択は偏り得る。

専門家複製はホット専門家のコピーを増やすためGPUメモリを消費し、専門家移動はパラメータ通信と同期を追加する。さらに論文のLongBench観測ではルーティング偏りがタスクで変わるため、あるタスクの統計から作った配置が別タスクで最適とは限らない。規模が大きくなるほど複製・移動の費用も増える。

## 手法
### 層間の「自然な冗長性」
EasyBalanceは別層の専門家を、追加コピーを作らず利用できる既存の計算資源とみなす。ただし層lの入力を層l+1の専門家へ流すわけではない。各マイクロバッチは正しい層の専門家を使い続け、複数マイクロバッチを異なる層位置へずらして同時に進める。

例えば負荷ベクトル `w1` と `w2` のピークGPUが異なれば、別々に実行したときの `max(w1)+max(w2)` より、組み合わせた `max(w1+w2)` が小さくなる。ピークGPUが一致すると等号に近づき利得が消えるが、論文ではGPU台数が増えるほど複数負荷のピーク一致確率が下がると説明する。

### マイクロバッチの選択と遅延
各MoE計算ステップで待機集合 `S` から実行集合 `RunSet` を選ぶ。選ばれたバッチだけMoE計算を行い、次のattention、routing、all-to-all dispatchへ進む。選ばれなかったバッチは現在層に残り、後のステップで別層負荷との相殺機会を待つ。全バッチが最終層を終えるまでこれを繰り返す。

未来層のルーティングは現在から分からないため、スケジューラは現在の負荷メタデータだけで貪欲に決める。主方式MaxUtilはGPU利用率が最大になる部分集合を探索するが、マイクロバッチ数nに対してO(2^n)になる。論文は線形時間のCumUtilとDiffPeakも評価し、最大性能はMaxUtilに劣るものの通常実行より改善することを示す。

### 小さすぎる実行集合の抑制
偏りだけを最小化すると、一度に少数バッチしか実行せず、計算と通信の重畳効果を失う可能性がある。EasyBalanceは最小実行集合サイズmを設け、`|RunSet| >= m` を要求する。待機バッチがm未満なら全て実行する。

実験からmはマイクロバッチ数の0.5〜0.75倍を推奨し、標準設定では4分割に対してm=3を用いる。この制約は負荷均衡だけを追って総スループットを悪化させるのを防ぐ。

## 評価
### 評価条件
|項目|内容|
|---|---|
|GPU|単一ノード8×NVIDIA A800-SXM4 80GB、NVLink|
|モデル|Qwen3-30B-A3B-Instruct-2507、Moonlight-16B-A3B-Instruct、Qwen3-235B-A22B-Instruct-2507|
|ベンチマーク|LongBench、13代表タスク|
|標準EP|8|
|小モデル条件|各GPU batch 16×4K、全体batch 128相当|
|235B条件|各GPU 12×512|
|マイクロバッチ|4分割、m=3|
|指標|end-to-end latency、effective workload、GPU under-utilization|
|反復|latencyは8回平均|

### 主要結果
|条件|指標|通常EP|EasyBalance|意味|
|---|---|---|---|---|
|Qwen3-30B、2wikimqa、EP=8|GPU未利用率|0.37|0.21|約43%削減|
|Qwen3-30B、repobench-p、EP=8|GPU未利用率|0.38|0.23|約39%削減|
|Moonlight-16B、repobench-p、EP=8|GPU未利用率|0.46|0.29|約37%削減|
|Qwen3-30B、2wikimqa、4 micro-batches|スケジューラ費|なし|MaxUtil 0.277 ms/step|end-to-end 8.21 sに対し小さい|
|Qwen3-30B、2wikimqa|end-to-end|micro-batchなし10.15 s|通常micro-batch 8.60 s|EasyBalance以前にもmicro-batch重畳自体が効く|

全体ではGPU未利用率を多くの条件で40%以上減らし、モデル・タスクを跨いでend-to-end latencyを改善する。EP=2/4/8の比較でもEPが大きいほど元の偏りが増える一方、EasyBalanceは一貫して未利用率を下げる。したがって層間相殺は特定の一つのタスク分布に固定した配置変更より柔軟である。

## 既存研究との差
専門家負荷均衡（EPLB）は専門家複製や配置変更で同一層内の負荷を均す。EasyBalanceは専門家とGPUの対応を一切変えず、マイクロバッチの進行層をずらして異なる層の負荷を合成する。そのためタスク切替時に配置プロファイルを作り直す必要がなく、追加専門家コピーも不要である。

これは通常のマイクロバッチ化とも異なる。通常は通信と計算を重ねるため同じパイプラインを細分化するが、EasyBalanceは各マイクロバッチの層位置を意図的に非同期化し、GPU別専門家負荷のピークを相殺するために実行集合を選ぶ。

## 限界
MaxUtilは候補部分集合を探索するためマイクロバッチ数に対して指数時間となり、大きなnでは線形ヒューリスティックへ切り替える必要がある。mを小さくしすぎると通信・計算重畳を失い、大きすぎるとスケジューリング自由度が減る。

利得は層間でピークGPUが異なることに依存する。複数層のルーティング偏りが同じGPUへ連続して集中する場合、`max(sum w_j)` が `sum max(w_j)` に近づき相殺効果が小さくなる。論文の評価は単一8×A800ノードが中心で、ノード間ネットワークを跨ぐ大規模EPで同じオーバーヘッド特性が維持されるかは未評価である。
