# ECHO: Early-layer Collaborative Hierarchical Orchestration with Bonus Logits in Speculative Decoding

> 対象モデルの前半層を高頻度の候補木探索、後半層を低頻度の厳密検証へ分け、中間状態再利用と補助ロジットで候補を更新し、追加ドラフトモデルなしで2.4〜2.9倍級の生成高速化を報告する。

## 概要

ECHOは、**ドラフトモデル不要の投機的デコードでも、候補を作る処理と対象モデルによる検証処理の両方が十分安くなければ高速化できない**という問題を扱う。別の小型モデルを置かない自己投機方式は配備が単純だが、対象モデルの一部をドラフトとして繰り返し使い、そのたびに全層へ候補を通して検証すると、後半層の計算が速度利得を食い潰す。また検索型の候補再利用は非常に安い一方、過去のトークン遷移が現在の文脈に合わず、候補が陳腐化すると受理率が落ちる。

ECHOはTransformer層の役割を対称に扱わず、前半層を「安価に候補を識別・拡張する側」、最終層を「対象モデル本来の分布で最終判断する側」として分業させる。前半層だけを高頻度に回す内側ループで候補木を広げ、十分な候補が集まった時だけ後半層を走らせる外側ループへ移る。内側で計算済みの中間状態を外側へ引き継ぐため、同じ前半層を検証時にやり直さない。さらに最終層で得た高品質な補助ロジットを次周期の候補木へ戻し、検索由来の古い候補を修正する。

複数モデル・ベンチマークの集約では、Llama-3.2-1Bで2.87倍、Llama-2-7Bで2.71倍、CodeLlama-7Bで2.60倍、Llama-3-8Bで2.42倍、Llama-2-13Bで2.90倍の自己回帰生成比高速化を報告する。大規模モデルでもCodeLlama-34Bで3.13倍、Llama-2-70Bで2.32倍を示す。論文要旨がまとめる代表範囲は2.4〜2.9倍であり、個別構成ではそれを超える値もある。

## 背景：投機的デコードの速度は「受理数／検証費」で決まる

投機的デコード（speculative decoding）は、安価なドラフトで複数トークンを先読みし、対象モデルの一回のforwardでまとめて検証する。候補が多く受理されれば、対象モデルを一トークンずつ呼ぶ回数を減らせる。ただし候補を作るコスト、候補木を保持するメモリ、対象モデルの検証コストが追加されるため、受理トークン数が増えただけでは高速化を保証しない。

独立した小型ドラフトモデルを使う方式はドラフトが安い一方、別モデルの配備・重みメモリ・訓練や整合が必要になる。自己投機（self-speculation）は対象モデルの早い層を途中で切ってドラフトとして使うことで追加パラメータを避けるが、早期層の予測分布は最終層ほど正確ではない。候補品質を上げようとして早期終了位置を深くすればドラフトが重くなり、浅くすれば受理率が落ちる。

ECHOはこの交換条件を一回の固定早期終了で解くのではなく、**安い前半層を複数回、高価な後半層を少ない回数**という頻度差へ変換する。さらに後半層の結果を次のドラフト改善へ再利用し、候補品質と検証頻度を協調させる。

## 問題設定

入力は現在の確定接頭辞、検索などから得た候補、前周期に残った補助情報である。目標は、対象モデル本来の分布による最終受理を保ちながら、平均受理トークン数（Mean Accepted Tokens; MAT）を増やし、対象モデル後半層の実行回数を減らすことである。

単純に前半層だけで候補を作ると、候補が弱いタスクでは外側検証で大量に棄却される。逆に外側検証を頻繁に行うと、後半層が再び支配的になる。中間状態を保存すれば再計算を減らせるが、その分だけKVキャッシュとhidden stateの保持量が増える。したがって、早期終了層、木の幅・深さ、内側ループ回数は速度とメモリの共同パラメータになる。

## 手法のあらまし

ECHOは一つの対象モデルを、前半検証器と後半検証器として時間的に使い分ける。

1. 検索候補と前周期情報から候補木を初期化する。
2. 前半層だけを走らせ、早期層の補助ロジットで候補木を高頻度に拡張・修正する。
3. 各候補の中間hidden stateとKV状態を保存する。
4. 外側ループでは保存状態から後半層だけを実行し、対象モデル最終分布で一括検証する。
5. 最終層の補助ロジットを次周期へ戻し、高信頼候補の追加や既存経路の修正に使う。

この循環により、後半層の一回の実行から「今回の厳密検証」と「次回ドラフト品質改善」の二つの価値を取り出す。

## 手法

### 1. 階層二重ループ

対象Transformerを所定の早期終了層で前半と後半に分ける。内側ループは前半層だけを複数回実行し、候補木を段階的に広げる。外側ループは低頻度で起動し、候補を後半層へ通して対象モデル本来の最終分布を得る。

この構造の目的は、全層forwardを「候補を少し更新するたび」に発生させないことである。前半層が十分安く、かつ候補順位づけに必要な識別力を持つほど利得が大きい。早期層が弱いモデルやタスクでは、内側ループを増やしても受理数が増えず、余分な計算になる。

### 2. Early-layer Bonus Logitsによる候補更新

前半層の中間表現から補助ロジットを作り、既存候補の有望度を再評価する。検索だけに頼る方式では、過去に観測したトークン遷移が現在文脈とずれても候補に残り続ける。補助ロジットは現在のhidden stateを反映するため、候補木をその場で修正できる。

このロジットは最終出力を決める権威的分布ではなく、**探索用の安価な順位信号**である。前半層が誤った候補を高く評価しても後半層で棄却できるため、直接の品質劣化ではなく受理率・速度の低下として現れる。ただし候補木が大きいほど中間状態保持量と前半計算も増える。

### 3. 中間状態再利用による外側検証

内側ループで候補を前半層へ通した時点で、その候補に対応するhidden stateとKV状態を保持する。外側検証では入力から全層を再計算せず、この中間状態を後半層の入口として使う。

これがECHOの主要な計算節約である。自己投機でありがちな「ドラフトのために前半層を計算した後、検証でまた前半層からやり直す」重複を避ける。代償は状態保持用メモリであり、候補数・早期終了位置・系列長によって増えるため、メモリ制約の強い環境では候補幅を無制限には増やせない。

### 4. Final-layer Bonus Logitsのフィードバック

外側検証では最終層まで計算するため、候補の受理判定だけでなく、対象モデルが本来次に高く評価するトークンについて高品質な情報も得られる。ECHOはこれを捨てず、次の内側ループへ戻す。

最終層の補助ロジットは、陳腐化した検索候補の修正や、高信頼候補の追加に使われる。つまり外側ループは「検証器」であると同時に「次周期の教師信号生成器」でもある。高価な最終層forwardの情報利用率を上げる設計と解釈できる。

### 5. 一度の微調整

論文は追加の独立ドラフトモデルや恒常的な追加配備パラメータを必要としない一方、最良の加速には一度の微調整が必要だと明記する。このため「完全学習不要の自己投機」とは区別する必要がある。

微調整の価値は、早期層の補助信号を最終層の判断へ近づけ、内側ループで有望な候補を増やすことにある。学習を省いた構成でも動作するが、候補品質と速度の上限は下がり得る。

## 評価

### まず見るところ

- **速度:** 論文要旨では複数条件で2.4〜2.9倍級。個別にはCodeLlama-34Bで3.13倍、Llama-2-70Bで2.32倍。
- **受理効率:** Llama-2-7Bの集約MATは5.07、Llama-2-13Bは4.16と報告される。
- **モデル範囲:** Llama-3.2-1BからLlama-2-70Bまで複数規模で評価。
- **タスク範囲:** Spec-Benchに加えHumanEval、GSM8Kを使用し、翻訳・要約・QA・数学・RAG・マルチターンなどを含む。
- **配備:** 独立ドラフトモデルは不要。ただし最良性能にはone-shot fine-tuning依存がある。

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| ベンチマーク | Spec-Bench、HumanEval、GSM8K |
| モデル系列 | Llama-2、Llama-3、Llama-3.2、CodeLlama |
| 規模 | 1B級〜70B |
| 主指標 | 自己回帰生成比speedup、Mean Accepted Tokens（MAT） |
| 比較群 | 検索型・自己投機型を含む既存投機デコード |
| 学習条件 | 最良加速には一度の微調整を使用 |
| 追加ドラフト重み | 不要 |

### 代表的な速度結果

| モデル | ECHO speedup |
|---|---:|
| Llama-3.2-1B | 2.87× |
| Llama-2-7B | 2.71× |
| CodeLlama-7B | 2.60× |
| Llama-3-8B | 2.42× |
| Llama-2-13B | 2.90× |
| CodeLlama-34B | 3.13× |
| Llama-2-70B | 2.32× |

大きいモデルほど必ず倍率が高いわけではない。後半層の一回当たりコストは増えるが、受理率、候補木形状、中間状態保持、GPU上のバッチ効率も変わるためである。たとえばCodeLlama-34Bでは3倍超だが、Llama-2-70Bは2.32倍であり、モデル規模だけから高速化率を予測できない。

### 受理数と速度の関係

| 条件 | MAT |
|---|---:|
| Llama-2-7B 集約 | 5.07 |
| Llama-2-13B 集約 | 4.16 |

MATは一回の対象モデル検証で何トークン前進できるかを表すため重要だが、MATだけで壁時計速度は決まらない。前半ループの追加forward、木管理、中間状態読み書き、後半層の実行効率を含めて初めて実測speedupになる。ECHOの評価はこの意味で、受理効率と実測速度を分けて見る必要がある。

### 評価上の制約

- 最良値はone-shot fine-tuningを含むため、完全な訓練不要手法との比較では条件を揃える必要がある。
- 早期終了層を深くすると候補品質は上がりやすいが内側ループが重くなり、浅くすると逆の交換条件になる。
- 候補木を広げるほど中間hidden state・KV状態の保持量が増える。
- 速度倍率はモデル、タスク、GPU、候補木、早期終了位置に依存し、2.4〜2.9倍を全条件へ一律に適用できない。
- 補助ロジットは最終分布を置き換えないため、品質保持の原理と速度改善の程度は別問題である。

## 既存研究との差

検索型投機方式は、過去に現れたn-gramやトークン遷移からほぼ計算なしで候補を作れるが、現在文脈への適応が弱い。自己投機方式は対象モデルの途中層をドラフトへ使うため追加モデルを不要にできるが、ドラフトと検証の重複計算が残りやすい。

ECHOは両者を単に組み合わせるのではなく、**前半層・最終層の情報を異なる時間尺度で循環させる**。前半層ロジットが検索候補を補正し、保存した中間状態が後半検証の再計算を省き、最終層ロジットが次周期の候補を改善する。この閉ループが論文固有の設計である。

## 限界・実装状況

追加ドラフトモデルを配備しない利点はあるが、中間状態を多く保持するため、メモリが厳しい端末では木幅や内側ループ数を抑える必要がある。早期終了位置と候補構成はハードウェア・モデルごとの調整対象になる。

また、最良速度には微調整が必要であり、重みを一切変更できない環境では同じ値を期待できない。論文の速度値は指定された実装・ベンチマークでの結果であり、長大文脈や高並行サービング時のKV容量圧力まで同じ割合で改善することを示すものではない。
