# DSD: A Distributed Speculative Decoding Solution for Edge-Cloud Agile Large Model Serving

> 端末側下書きモデルとクラウド側目標モデルによる分散投機的復号をDSD-Simでモデル化し、学習型の適応窓制御で投機窓幅を調整して処理量を最大9.7%向上する。
## 書誌情報
- **著者**: Fengze Yu, Leshu Li, Brad McDanel, Sai Qian Zhang
- **公開**: arXiv:2511.21669
- **種別**: arXivプレプリント
- **対象**: 分散投機的復号、端末・クラウド推論、適応窓制御、LLMシミュレーション
- **実装**: SimPyとVIDURを基盤とするDSD-Sim、および5特徴量の残差多層パーセプトロンによる適応窓制御の研究実装である。
## 概要
DSDは投機的復号（speculative デコード）を端末側の下書きモデル（draft model）とクラウド側の目標モデル（target model）へ分散し、ネットワーク往復時間、バッチ処理、経路選択、検証依存を含めて評価・制御する枠組みである。DSD-SimはVIDURのGPU遅延予測器とSimPyの要求単位スケジューラを組み合わせ、実機から得た受理履歴を使って分散投機を再現する。さらに適応窓制御（適応型 Window Control）は待ち行列深度、受理率、往復時間、トークン間時間、直前窓幅を入力する小型DNNで投機窓幅と統合・分散方式を動的制御する。20個の目標モデルと600〜1000個の下書きモデル規模で、固定窓幅に対し処理量を最大9.7%向上し、トークン間時間を最大10.7%削減した。

本論文は、端末側下書きとクラウド側検証を分離した投機的復号を、通信・待ち行列・まとめ処理まで含む要求単位の離散事象系として扱うDSD-Simを構築する。単一ノード推論時間は既存のVIDUR予測器を実GPU測定で拡張・校正し、投機トークンの受理列は実機から採取した追跡データを使うため、単純な一定受理確率だけで動作を合成しない。さらに適応窓制御は、目標待ち行列の利用率、直近受理率、通信往復時間、出力一トークン時間、直前の投機窓という五つの観測値から次の窓長を予測する小型残差多層パーセプトロンを用いる。窓長二から十二とクラウド単独実行を多数条件で全探索して教師値を作るため、手作業の閾値調整に依存せず、通信と計算の状態に応じて投機量そのものを切り替えられる点が論文固有の中心である。

代表結果として、スループットはGSM8K, 20 targets/600 drafts, 10ms RTTで静的 Windowに対してup to +9.7% vs 静的 gamma=4。network/load/acceptanceを見たwindow適応が固定gammaよりtarget利用率を高める。
## 問題設定
従来の投機的復号は、小型の下書きモデルが複数候補トークンを作り、大型の目標モデルが一括検証することで自己回帰生成の逐次性を緩和する。しかし多くの方式は下書きモデルと目標モデルが同一計算機、または通信遅延をほぼ無視できる小規模構成に置かれることを前提としている。資源の限られた端末側へ小型下書きモデルを置き、巨大な目標モデルをクラウド側へ置くと、投機と検証の各反復ごとに往復通信が発生する。さらに多数の端末が少数の目標サーバを共有するため、目標側待ち行列、要求のまとめ方、経路選択、受理率、投機窓長が相互に影響する。窓を長くすると一回の検証で多く進める可能性があるが、下書き時間と棄却時の無駄が増える。窓を短くすると棄却損失は減るが、検証回数と通信回数が増える。したがって固定窓や受理率だけを見る単純な閾値制御では、通信混雑、目標サーバ飽和、端末性能差が時間とともに変わる大規模環境で一貫して良い設定を選べない。

## 手法
### 手法のあらまし
入力は、端末側下書きモデル群、クラウド側目標モデル群、各装置のモデルとGPU種類、端末とクラウド間の往復通信時間と揺らぎ、要求到着時刻、入力長、出力長、実機から取得した投機トークン受理列、経路選択規則、まとめ処理規則、投機窓制御規則である。設定解析器は高水準の構成記述から端末プール、目標サーバプール、各通信路を展開する。要求が到着すると、まず経路選択器が乱択、順番割当、最短待ち行列などの規則で目標クラスタを決める。次に要求は事前計算または復号用の待ち行列へ入り、先入れ先出し、長さを考慮したまとめ処理などの規則に従って実行集団を作る。分散実行を選んだ場合、端末側下書きモデルは現在の投機窓長だけ候補トークンを逐次生成し、その候補列と必要情報を通信路へ送る。通信路は設定された往復時間と揺らぎを遅延事象として適用する。クラウド側目標モデルは候補をまとめて検証し、先頭から受理できるトークンを確定し、最初の不一致では目標モデル自身のトークンを採用して残り候補を破棄する。確定した接頭辞は端末側へ返され、生成終了条件を満たすまで同じ反復を続ける。各GPU処理時間はVIDUR由来の予測器へ演算種類、形状、装置を渡して得る。著者らはA40上の小型モデル測定を追加し、A40、A100、H100上のQwen系・Llama系モデルで予測値を実測へ照合する。シミュレータは初回トークン時間、一出力トークン時間、端から端の遅延、受理率、窓長履歴、全体処理量、目標GPU利用率、通信待ち時間を記録する。適応窓制御の学習段階では、作業負荷、通信条件、装置構成を変えた二千超の状況について、投機窓二から十二とクラウド単独実行を全探索する。各候補設定のサービス目標重み付き評価値を比較し、最良設定を教師値とする。制御器は五次元入力を受ける二ブロック残差多層パーセプトロンで、滑らかな活性化関数を使い、絶対誤差損失とAdamW最適化で百エポック学習する。実行時には現在と直近履歴から目標待ち行列利用率、受理率、通信往復時間、一トークン時間、前回窓長を作り、制御器が次の窓長を連続値で出す。その値を一から十二へ制限し、係数0.4の指数移動平均で急変を抑え、整数へ丸める。予測値が一以下の状態が続く場合は、端末下書きと通信を使わずクラウド目標モデルだけで生成する統合実行へ切り替える。ただし一時的な通信揺らぎで実行方式が往復しないよう、通常二反復連続で条件を満たすまで切替を保留する。出力は、各要求の遅延と受理履歴、全体処理量と資源利用率、および各反復で選ばれた投機窓・実行方式である。前段の入力追跡データから装置・通信モデルを通し、後段の性能解析と制御学習へ接続する一連の経路が明示されている。追加費用は端末側下書き計算、反復ごとの通信、制御器推論であり、通信遅延が大きい場合や受理率が低い場合には分散化の利得が失われる。実際、往復時間がおよそ五十から六十ミリ秒付近を超えるとクラウド単独実行との優劣が逆転するため、制御器は窓調整だけでなく実行方式切替も必要とする。

### 分散投機的復号シミュレータ
DSD-Simは端末下書きとクラウド検証を単なる二つの推論時間の和として扱わず、要求到着、経路選択、待ち行列、まとめ処理、下書き生成、通信送受信、目標検証、受理・棄却、次反復を個別の離散事象として進める。端末と目標サーバは並行する過程として表現され、多数端末が同じ目標サーバへ集中したときの待ち行列増大や、まとめ処理待ちと通信待ちの重なりを再現できる。入力追跡データには実機で得た受理列を埋め込み、各候補トークンが受理されたかを一定確率から乱数生成せず実際の下書き・目標モデル対の挙動として再生する。これにより投機窓を変えたときの進行量、検証回数、通信回数を要求ごとに追跡し、初回トークン時間、一出力トークン時間、処理量、利用率を同じ系で比較できる。

### 異種装置と通信の校正
単一ノードの事前計算・復号時間はVIDURの性能予測器を利用するが、端末環境を扱えるようA40とQwen-7B、Llama2-7B等の測定を追加する。さらにQwen-72BやLlama2-70BをA100、H100等で実測し、予測器が各演算形状に対してどの程度一致するかを確認する。平均絶対誤差は事前計算7.4%、復号5.2%で、通信往復時間は近距離クラウドを想定した10ミリ秒と上限寄りの30ミリ秒を代表条件として与える。大規模評価では20台の目標サーバと600または1000台の下書き装置を組み合わせる。予測器がNCCL通信などを省略するため実測より楽観的になる限界も明示し、シミュレーション結果を無条件に実機値と同一視しない。

### 適応窓制御
適応窓制御は、現在の目標待ち行列利用率、直近の候補受理率、通信路ごとの往復時間、直近の一出力トークン時間、前回選択した投機窓長を入力する。これらはそれぞれクラウド混雑、下書き品質、通信費用、目標処理速度、制御履歴を表し、単一の受理率閾値だけでは見えない分散系の状態を与える。学習用教師値は二千超の状況で窓二から十二と統合実行を全探索し、サービス目標を反映した評価値が最良の設定を選んで作る。五次元入力の小型残差多層パーセプトロンが次窓を予測するため、巨大な制御モデルを追加せず要求反復ごとに更新できる。評価では固定窓に対し最大9.7%の処理量向上と最大10.7%の一出力トークン時間削減を得ており、通信と待ち行列を含む観測から投機量を決める価値を示す。

### 安定化と実行方式切替
学習器の生の予測をそのまま使うと、通信揺らぎや待ち行列変動で窓長が毎反復大きく振れ、分散実行とクラウド単独実行が頻繁に切り替わる可能性がある。そこで予測値を許容範囲へ制限し、係数0.4の指数移動平均で高周波変動を減らした後、整数窓へ量子化する。さらに分散実行中に窓一相当の予測が出ても直ちに方式を変えず、通常二回連続で条件が続いた場合だけクラウド単独へ移る粘着的切替を使う。各端末・目標対ごとに平滑化状態を持つため、通信路ごとの状態差を保持しつつ全体待ち行列情報も判断へ反映できる。往復時間が五十から六十ミリ秒程度を超えて分散化の通信費用が並列性の利益を上回る領域では、窓を微調整し続けるより統合実行へ退避できる。

### 全体のデータ／制御の流れ
端末側の下書きモデル群、クラウド側の目標モデル群、通信路、設定解析器、要求単位の離散事象スケジューラ、GPU実行時間予測器、性能解析器、適応窓制御器から構成される。要求は経路選択、待ち行列、まとめ処理、下書き、通信、検証を順に通り、観測された待ち行列と通信・受理状態が次の窓制御へ戻る閉ループを形成する。
## 評価条件
- **ハードウェア**: NVIDIA A40、NVIDIA V100、NVIDIA A100、NVIDIA H100、NVIDIA A6000
- **ソフトウェア**: DSD-Sim、SimPy、VIDUR、AWC WC-DNN
- **データセット／トレース**: GSM8K、CNN/DailyMail、HumanEval
- **比較対象**: 静的 window gamma=4、acceptance-threshold 動的 window、Random ルーティング、Round-Robin、FIFO batching、Length-Aware Batching、cloud-only/fused execution
GPU predictorを実hardwareで校正後、20 targetと600/1000 draft、RTT 10/30ms等をシミュレーションし各policyを3 run平均で比較する。
distributed draft-target speculative デコード。network RTTが50〜60ms付近を超えるとdistributed advantageが消えfusedが有利になる。
## 主要結果
AWCをJSQ + length-aware batchingと組み合わせると、静的 windowに対して全12 ワークロード/configurationで最高スループットを示し、最大9.7%向上した。TPOTは全条件で概ね6〜10%低下し最大10.7%削減、TTFTも0.5〜4.1%改善範囲だった。GSM8Kのpolicy stackではスループット 25.1→28.1 req/s、TPOT 45→37ms。distributed executionは低RTTでcloud-onlyより有利だが50〜60ms付近でnetwork オーバーヘッドが勝りfusedと逆転する。

- スループット / up to +9.7% vs 静的 gamma=4 (比較対象: 静的 Window; 条件: GSM8K, 20 targets/600 drafts, 10ms RTT) — network/load/acceptanceを見たwindow適応が固定gammaよりtarget利用率を高める。

- TPOT / up to -10.7% (比較対象: 静的 Window; 条件: GSM8K config 1; 40.1ms to 36.2ms) — 過大/過小speculationを避けることでverificationと通信の無駄を減らす。

- simulator accuracy / 7.4% プリフィル MAE, 5.2% デコード MAE (比較対象: real GPU measurements; 条件: Qwen/Llama models on A40/A100/H100) — distributed system探索に使うsingle-node 遅延 predictorが実測へ概ね整合する。

- network crossover / distributed/fused crossover around 50-60ms RTT (比較対象: cloud-only fused execution; 条件: fixed system configuration while varying RTT) — edge draftの並列性はWAN 遅延が大きいとverification round-tripに相殺される。

### 負の結果・境界条件
- AWCのスループット改善は最大9.7%であり、distributed SD自体の絶対高速化倍率は大きくない。
- VIDURはNCCL等を省略し遅延を一貫して過小予測する傾向がある。
- JSQは約1000 draftを超える高負荷で特定fast serverが飽和しRound-Robinへ追いつかれる。

### 結果の読み方
distributed speculative デコードではgammaはalgorithm parameterではなくnetwork RTT、queue depth、target utilizationと結合したsystem control knobになる。AWCの利得は控えめだが、edge-cloud条件では固定windowが不安定になることとmode switchingの必要性を定量化した点が重要である。
## 品質への影響
target modelによる標準accept/reject verificationを維持するため生成品質は変えない。
## 既存研究との差
既存の代表的な投機的復号研究は、下書きモデルの構造、候補木、複数候補頭、受理率向上など、同一ノード上で目標モデルの逐次復号をどこまで並列化できるかを主に扱う。これに対しDSDは、小型下書きモデルを多数の端末へ、大型目標モデルを少数のクラウドサーバへ分離し、各検証反復に通信遅延と共有待ち行列が入る状況を対象にする。また、事前計算と復号を別GPUへ分離する既存の分離サービングとは異なり、分離する役割は候補生成と目標検証である。適応窓制御は単純な受理率閾値だけでなく、目標待ち行列、通信往復時間、一出力トークン時間、直前窓長を同時に観測して次の投機量を決め、条件が悪い場合は端末下書きを使わないクラウド単独実行へ退避する。
## 限界
- 主要な大規模結果は離散事象シミュレーションであり、六百から千台の端末を実ネットワークへ接続した完全実機展開の測定ではない。
- 基礎となる単一ノード予測器はNCCL通信や一部非カーネル処理を省略するため、実測遅延を系統的に小さく予測する傾向がある。
- 適応窓制御の最大処理量改善は9.7%で、分散化だけで桁違いの高速化を得る方式ではない。価値は条件変動下で悪い窓を避ける安定性にある。
- 通信往復時間がおよそ五十から六十ミリ秒を超えると、端末側並列性より反復通信費用が支配的になり、クラウド単独実行の方が有利になる。
## 実装状態
DSD-SimはSimPyによる要求単位の離散事象スケジューラとVIDUR由来のGPU時間予測器を組み合わせる研究実装である。適応窓制御は五入力の小型残差多層パーセプトロンで、二千超の状況に対する窓長全探索から教師値を作る。論文本文から公式コード公開先は確認できなかった。
## 研究上の位置づけ
分散投機的復号において、通信・待ち行列・まとめ処理・投機窓を同時に定量化する初期のシステム比較基準である。将来の端末クラウド協調方式では、候補モデルの精度だけでなく通信条件に応じた実行方式切替が必要であることを示す。
