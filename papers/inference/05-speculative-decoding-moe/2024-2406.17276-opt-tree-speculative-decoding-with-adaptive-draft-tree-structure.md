# OPT-Tree: Speculative Decoding with Adaptive Draft Tree Structure

> 木型投機的復号では、候補数が同じでも「一本道に深く使うか」「複数枝へ広く使うか」で受理トークン数が変わる。OPT-Treeはその形を手作業で固定せず、ドラフト確率から期待受理長を計算し、入力ごとに価値の高い候補だけで木を組み直す。

## 概要

投機的復号（speculative decoding）は、小さなドラフトモデルが先に候補トークンを生成し、大きな対象モデルがそれらを一括検証することで、対象モデルの前向き計算1回あたり複数トークンを進める方式である。木型方式では候補を分岐させることで、ドラフトの不確実性をカバーできる。

しかしBinary treeやEAGLEで使われる固定木は、すべての入力へ同じ幅・深さを適用する。ドラフト分布が鋭い箇所では高確率経路へ深く予算を使った方がよく、分布が平坦な箇所では枝を増やした方がよい。固定木はこの変化を利用できない。

OPT-Treeは、木の各ノードまで到達するドラフト確率の積を、そのノードが受理長へ寄与する近似確率として扱う。総ノード数nの下でこれらの和が最大になる部分木を選び、期待受理長（expected acceptance length）を最大化する。木を深くするほどドラフトモデル実行回数も増えるため、期待受理長の追加利得が十分小さくなったところで展開を打ち切る。

## 問題設定

### 同じ25ノードでも木の形で価値が変わる

投機木の検証では、根から連続して対象モデルと一致した最長経路が実際の受理列になる。そのため、低確率の深い枝へノードを使っても受理長へほとんど寄与しない。一方、確率の高い経路を途中で打ち切ると、本来受理できた先のトークンを逃す。

したがって最適化したい量は単純な「候補ヒット数」ではなく、各深さで受理される確率を積み上げた期待受理長である。

### 木を大きくすればよいわけではない

候補ノードを増やすと対象モデルの一括検証で受理候補を増やせるが、自己回帰ドラフトモデルでは木を1層伸ばすごとにドラフト前向き計算が必要になる。深すぎる木は対象モデルの検証回数を減らす代わりにドラフト時間を増やし、実時間速度を悪化させる。

OPT-Treeはノード予算だけでなく、追加ドラフトstepの費用も停止条件へ入れる。

## 手法

### 1. ノード価値を「根からの確率積」で定義する

ある候補ノードvまでの経路に含まれるドラフト条件付き確率を掛け合わせ、
(hat p(v)=prod_{uin P(v)}p_d(u))
とする。ドラフトモデルが対象モデル分布をよく近似しているなら、この値はそのノードまで連続して受理される確率と正に相関する。

子ノードの (hat p) は必ず親以下になる。この単調性が、後段の部分木選択を単純化する。

### 2. 期待受理長をノード価値の和として近似する

長さAまで受理される確率を各深さで足し合わせると、受理長の期待値になる。OPT-Treeではこれを木中の (hat p) の総和で近似する。

したがって、ノード数nの木を作る問題は「(hat p) の総和が最大になるnノードの根付き部分木を選ぶ」問題へ変わる。

### 3. 一度大きな候補木を伸ばし、上位nノードを残す

各ドラフトstepで末端ノードの次トークン分布を計算し、高い (hat p) を持つ候補を追加する。十分に展開した木から (hat p) 上位nノードを選ぶ。

子の値は親以下なので、上位nノードの集合に子が含まれるならその親も必ず含まれる。したがって複雑な連結制約最適化を別途解かなくても、単純な上位n選択が根付き部分木になる。

### 4. 期待値の増分が小さければ木を深くしない

理論上は、もう1層展開してnノード最適部分木の期待値が増えなくなるまで続ければよい。しかしドラフト計算は無料ではない。

そこで実装では、木を1層伸ばした時の期待値増分が閾値δ以下なら停止する。δは、ドラフト1stepの時間を対象モデル1stepの時間で割った比率μより大きく設定する。論文ではLLaMA-2-68Mドラフトでδ=0.2、EAGLEドラフトでδ=0.8が良い例を示す。ドラフトが軽いほど深く探索し、相対的に高価なら早く止めるという意味になる。

### 5. 選んだ木を対象モデルで一括検証する

最終OPT-Treeに木用の注意マスクを付け、対象モデルへ一度に入力する。対象モデルの予測と木を照合し、根から連続して一致する最長候補を受理する。

OPT-Treeが変更するのは候補木の生成形だけで、検証規則は投機的復号そのものなので、通常の受理規則を使う限り対象モデルの出力を保つ。

## 評価

### 評価条件

| 項目 | 条件 |
| --- | --- |
| 対象モデル | LLaMA-2-7B、13B、70B、Vicuna-33B |
| ドラフト | LLaMA系68M/1B/7B、Vicuna-7B、対応EAGLEドラフト |
| 課題 | MT-Bench、GSM8K |
| 比較木 | Binary、固定EAGLE tree、OPT-Tree |
| 復号 | 主評価は貪欲復号（greedy decoding）、temperature 0 |
| GPU | 7B: 1×RTX 4090、13B: 1×NVIDIA L20、70B/Vicuna-33B: 4×A100 PCIe 40GB |
| 木ノード数 | GPU/対象モデルに応じ25、50、60から速度が最大になる設定を選択。EAGLE固定木は25ノード |
| 指標 | 平均受理長（Mean Acceptance Length, MAL）、token/s、自己回帰復号比speedup |

### MT-Benchの代表結果

| 対象 / ドラフト | 固定EAGLE木 speedup | OPT-Tree speedup | MAL: EAGLE → OPT |
| --- | ---: | ---: | ---: |
| LLaMA-2-7B / L-68M | 1.49× | **1.69×** | 2.47 → 2.58 |
| LLaMA-2-13B / L-68M | 1.75× | **1.80×** | 2.42 → 2.58 |
| LLaMA-2-7B / EAGLE | 2.51× | **2.56×** | 3.73 → 4.36 |
| LLaMA-2-13B / EAGLE | 2.76× | **2.86×** | 3.80 → 4.35 |
| LLaMA-2-70B / L-7B | 1.80× | **1.85×** | 4.97 → 7.74 |
| LLaMA-2-70B / EAGLE | 2.99× | **3.05×** | 3.67 → 4.06 |
| Vicuna-33B / EAGLE | 2.21× | **2.24×** | 2.69 → 3.06 |

LLaMA-2-70Bへ7Bドラフトを使う例では、OPT-TreeはMALを4.97から7.74へ大きく伸ばすが、速度は1.80×から1.85×への小幅改善に留まる。強いドラフトで深い木を作ると受理長は増えても、そのドラフト自身の計算費用が大きいためである。この結果は「受理長最大化」と「実時間最大化」が同一ではないことを示す。

GSM8Kでも同じ傾向で、EAGLEドラフトとOPT-Treeの組合せでは最大約3.21倍の自己回帰比speedupを報告する。

### 木予算を増やした時の挙動

強いドラフトと十分なノード予算を使うと、一回の対象モデル検証で10トークン超を受理できるケースがある。一方で木を深くし過ぎるとドラフト時間が支配的になるため、δによる停止が必要になる。

## 既存研究との差

Binary treeやEAGLEの既定木は、事前に決めた形をすべての入力で使う。OPT-Treeは同じドラフトモデルを使ったまま、各復号stepの確率分布に応じて木形状を変える。

後続のTALONのような確信度閾値方式と比べると、OPT-Treeはノードごとの経路確率から木全体の期待受理長を明示的な目的関数として計算し、その最大部分木を選ぶ。代わりに、候補木を展開・順位付けするオンライン管理費用が発生する。

## 限界・実装状況

ドラフト確率が対象モデルの受理確率とよく相関するという近似に依存する。ドラフトモデルの較正が悪い場合、高い (hat p) を持つ枝が対象モデルでは外れる可能性がある。

また最適なδとノード予算は、対象/ドラフトモデルの速度比とGPUに依存する。論文でも25/50/60から実測速度に合わせて選んでおり、一つの設定が全環境で最適ではない。

主評価はbatch 1寄りの単一要求復号であり、連続バッチ配信では要求ごとに異なる木をまとめる効率も別途問題になる。

公式実装は著者のOPT-Treeリポジトリで公開されている。
