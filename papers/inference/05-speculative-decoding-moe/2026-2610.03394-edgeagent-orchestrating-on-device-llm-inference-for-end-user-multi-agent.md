# EdgeAgent: Orchestrating On-Device LLM inference for End-User Multi-Agent Systems on CPU-GPU Unified Memory Architectures

> 端末の統一メモリ向けに、CPUとGPUのゼロコピー協調実行、下書き予算の動的配分、道具待ちエージェントの退避を組み合わせ、複数エージェント推論を最大1.77倍高速化した実行系。

## 概要

個人端末の上で複数の言語モデルエージェントを動かす使い方が広がっている。秘匿性の高いデータを端末の外へ出さない利点がある一方、実行基盤には三つの困難がある。第1に、CPUとGPUが1つの物理メモリを共有する統一メモリ構造（UMA）では、逐次生成の段階で小さなバッチの読み出しが帯域を支配し、CPUとGPUを同時に動かすとバスを奪い合って互いを遅くする。第2に、投機的復号（小さい下書きの候補を対象モデルがまとめて検証する高速化）の効きは課題で大きく違う。構造化されたコード生成は予測しやすく長い下書きが効くが、熟考する推論は外れやすく、長い下書きは棄却された候補の読み出しで帯域を浪費する。第3に、エージェントは道具呼び出しで頻繁に止まり、その間も実行枠を占有すると後続が待たされる。

本論文の実行系は、この三つを別々ではなく一つの帯域配分の問題として扱う。実行層では、グラフコンパイラの制約を迂回してCPUとGPUが同じテンソルへ重ならない領域を書き合うゼロコピーのテンソル並列（計算を行列の分割で複数装置へ分ける方式）を実現し、CPU側は行列拡張に合わせた詰め込み配置、GPU側は通常配置という非対称な重み配置で両方の計算資源を使う。調整層では、各列の過去の受理長を予測しやすさの指標として下書き予算を動的に配り、道具待ちに入ったエージェントをその場で退避させて空いた枠へ待機中の課題を埋め戻す。

**代表結果:** Apple M4で、統一メモリ向け実行だけでもバッチ型投機的復号比1.29倍の高速化があり、1秒から100秒の道具待ちを注入した極端な条件では、全体の所要時間が213.1秒から120.6秒へ縮み、1.77倍の高速化になった。同時実行エージェント数4のときの全体処理量は、推論特化モデルで毎秒33.6トークンである。

## 問題設定

資源の観点で問題を分解する。統一メモリでは帯域が単一の共有資源であり、入力処理の段階では計算量が多くCPUとGPUの合算が効くが、逐次生成の段階ではバッチが小さく帯域が支配的になり、協調実行の利得が消える。論文の予備測定でも、行列が大きくなるほどCPUとGPUの同時実行の利得が目減りする帯域の壁が確認されている。次に下書き予算である。バッチ内で一律の下書き長を課す既存方式は、予測しやすい列では上限に張り付いて受理の機会を逃し、予測しにくい列では棄却される候補へ帯域を使う。最後に停止である。道具の応答待ちは秒単位で予測できず、静的バッチでは止まったエージェントが先頭を塞ぐ形で全体を遅らせる。端末では計算資源も帯域も余裕がないため、この三つを同時に解かないと、どれか一つの改善が別の浪費で相殺される。

## 手法のあらまし

処理は二層で進む。下層の実行層は、重みをCPU向けとGPU向けに違う配置で事前に詰め、実行時はコピーなしに同じ共有バッファの別領域へ両装置が書き込むテンソル並列で1回の順伝播を行う。CPU側の核は行列拡張に合わせたタイル化と仕事の奪い合いで効率を上げる。上層の調整層は、各エージェント列について過去に受理された下書き長を保持し、それを予測しやすさの指標として次のラウンドの下書き予算を決める。道具呼び出しで止まった列は退避して実行枠から外し、待機中の列を即座に埋め戻す。生成が再開できる状態になった列は後のラウンドで戻る。この二層により、帯域は予測の当たる列と実際に動いている列へ優先的に配られる。

## 手法

### 1. 統一メモリ向けゼロコピー実行 — 非対称配置でCPUとGPUを同時に使う

この機構が観測するのは、CPUとGPUが書き込むテンソル領域が重ならないことと、各装置の計算特性である。保持する状態は、CPU側では16×64のタイルへ詰め込んだFP16重み、GPU側では線形配置の重みという、装置ごとに異なる事前配置である。行う動作は計算の分割であり、1つの演算を両装置へ分け、同じ物理バッファのずれた領域へ排他的に書かせることで、コピーも全体の同期もなしに結果を合わせる。通常のグラフコンパイラはテンソル単位で競合を判定するため、この重ならない書き込みを危険とみなして同期を挿入し、熱心実行へ落ちてしまう。本方式は専用の障壁でこの過剰な保護を迂回する。減るボトルネックは、コピーと同期の費用と、逐次生成で遊ぶCPU計算資源である。追加で消費する資源は、重みの二重配置に要るメモリと、実装の複雑さである。失敗条件は帯域の飽和そのものであり、読み出し量が帯域上限に達する条件では分割しても利得が出ない。論文の評価でも、この実行層単独の利得は1.29倍にとどまり、残りは調整層が担う。

### 2. 受理長に基づく下書き予算配分 — 当たる列へ帯域を寄せる

この機構が観測するのは、各列で直近に受理された下書きトークンの長さである。保持する状態は列ごとの受理長の履歴であり、これをその列の予測しやすさの実測指標として使う。行う動作は予算の配分であり、受理が長い列には次のラウンドで長い下書きを許し、受理が短い列には短く抑える。減るボトルネックは、棄却される候補の生成と検証に使われる帯域の浪費である。予測しにくい推論列で深い下書きを作っても大半が捨てられるため、早めに打ち切る方が全体の処理量が上がる。論文の分離評価では、この動的配分だけで静的配分比1.12倍の高速化があった。追加で消費する資源は履歴の保持と配分の計算で、小さい。失敗条件は履歴と現在の難しさのずれであり、課題の途中で性質が変わる列では、予算の追随が遅れて一時的に過大または過小になる。

### 3. 退避と譲渡 — 道具待ちの列を枠から外して埋め戻す

この機構が観測するのは、エージェントが外部道具の呼び出しに入り生成が止まったことである。保持する状態は、退避した列の文脈と再開に必要な実行状態である。行う動作は枠の再利用であり、止まった列をその場で実行バッチから外し、待機中の別の列を空いた枠へ入れる。再開可能になった列は後のラウンドで戻す。減るボトルネックは、先頭の停止が後続全体を待たせる行列の詰まりである。追加で消費する資源は、退避と復帰の状態管理であり、生成そのもののコピーは統一メモリのため小さい。失敗条件は停止が短い場合であり、頻繁な退避と復帰の管理費用が隠せる待ち時間を上回ると逆効果になり得る。論文の極端条件（1秒から100秒の待ち）ではこの機構が大きく効き、所要時間の短縮の主因になった。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| ゼロコピー協調実行 | 装置ごとの書込み領域と計算特性 | 非対称配置でテンソル並列 | コピー・同期費用と遊休CPU | 重みの二重配置と実装の複雑さ |
| 受理長による予算配分 | 列ごとの受理履歴 | 下書き長を列ごとに変える | 棄却候補への帯域浪費 | 性質が変わる列で追随が遅れる |
| 退避と譲渡 | 道具待ちの発生 | 止まった列を外し別列を入れる | 先頭詰まりによる待ち | 短い停止では管理費用が勝ち得る |

### 4. 1ラウンドの流れ — 検証から調整まで

複数エージェントの1ラウンドは次のように進む。各列は割り当てられた下書き長で候補を作り、対象モデルがまとめて検証する。受理された長さは列ごとの履歴へ記録され、次ラウンドの予算に反映される。検証の合間に道具呼び出しへ入った列は退避され、その枠は待機列が使う。全列がこの循環を回すことで、帯域と計算枠は常に、予測が当たっていて実際に動いている列へ寄る。近似の区別として、下書き予算の変更は受理される生成列そのものを変えず、検証済みの投機的復号の枠内にある。変わるのは速度と資源配分だけである。

## 評価

結論は三点である。第1に、実行層だけでも1.29倍の高速化があり、統一メモリでも協調実行の余地がある。第2に、受理長による予算配分が1.12倍を上乗せし、帯域の浪費を抑えた。第3に、道具待ちが極端な条件では退避機構が効いて全体で1.77倍に達した。評価は実機の端から端までの測定であり、条件ごとの内訳も分けて報告されている。

- 消費電力の評価は論文では報告がなく未評価である。
- 生成品質の比較は投機的復号の検証前提に基づき、課題成否の体系的な評価は限定的である。

</details>

全体として、本論文の価値は個別機構の倍率より、端末の共有帯域を巡る三つの浪費（コピーと同期、棄却候補、停止による占有）を一つの配分問題として設計し直した点にある。

## 既存研究との差

クラウド向けサービング基盤は、複数GPUと大バッチを前提に処理量を最大化し、帯域が装置ごとに分かれている世界で設計されている。本論文は帯域が単一共有資源である端末へ前提を置き換え、実行層の協調方法そのものを統一メモリ向けに作り直した。投機的復号の先行研究は下書き長を一律に扱うことが多いのに対し、本論文は受理履歴で列ごとに予算を変える。また道具待ちへの対応を、実行枠の退避と埋め戻しという調整層の仕事として明示的に扱った点も、生成の高速化だけを見る研究とは異なる。

## 限界・実装状況

読み手の注意点として、評価は単一のチップと8B級モデルに限られ、帯域特性の違う端末や、メモリ容量の厳しい端末での挙動は未検証である。道具待ちの条件は合成注入であり、実ワークロードの分布では退避の利得が小さくなる可能性がある。受理履歴に基づく配分は、課題の性質が途中で変わる列では追随遅れが起きる。実装状況としては試作系がApple M4上で動作し実測されているが、公式コードのURLは一次資料で確認できなかった。一般の推論基盤への統合状況も未評価である。

## 一般的な実装上の含意

共有帯域の環境では、計算を分ける前に、帯域を何が浪費しているかを列挙すべきである。棄却される投機候補も、止まったままの実行枠も、帯域と枠の占有という形で費用になる。受理履歴のような安い実測指標で配分を動かす方法は、予測器を別に学習するより端末向きである。また停止を前提にするエージェント実行では、退避と再開を調整層の基本機能として設計する必要がある。
