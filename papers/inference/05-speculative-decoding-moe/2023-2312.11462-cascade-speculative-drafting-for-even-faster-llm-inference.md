# Cascade Speculative Drafting for Even Faster LLM Inference

> draft model自身をさらに投機するVertical Cascadeと、後方tokenほど小さいdraftへ切替えるHorizontal Cascadeで投機的復号のdraft費用を削る。

## 概要

投機的復号（speculative decoding）は、小さいdraft modelが先の候補tokenを複数作り、大きいtarget modelがそれらを一度に検証する。targetが先頭から何tokenか受理できれば、通常ならそのtoken数だけ必要だったtarget forwardを1回へまとめられる。正しいaccept/reject規則を使えば、最終的な出力分布はtarget model単独の自己回帰生成と一致する。

ただし通常の投機的復号には、見落とされやすい**draft側の逐次ボトルネック**がある。K個の候補を作るには、小さいとはいえdraft modelをK回自己回帰実行する。draftを小さくすれば1回は速いがtargetとの一致率が下がり、draftを大きくすればacceptanceは高まってもK回分のdraft計算が重くなる。このため実際にはtargetより2桁ほど小さいmodelがdraftに選ばれることが多い。

Cascade Speculative Drafting（CS Drafting）は、「1つのdraft modelにK token全部を同じ方法で作らせる」という前提を崩す。**Vertical Cascade**はdraft model自身のtoken生成を、さらに小さいmodelによる投機的復号で加速する。**Horizontal Cascade**は、1回のdraft列の前半と後半では価値が違うことを利用し、受理されやすい先頭tokenには強いmodel、受理されにくい後方tokenにはより安いmodelを割り当てる。

両cascadeの最下層には、neural modelより桁違いに安い統計draft **Max-Gram（MaG）** を置く。MaGは既存promptや直前生成列に現れた最大一致ngramを使い、見つからなければWikipediaから作ったbigram分布へfallbackする。上位のneural draftがMaG候補をreviewするので、統計model単独の低い品質をそのままtargetへ渡さずに済む。

FLAN-T5 familyの理論化されたStandardized Walltime Improvementでは、通常の投機的復号に対してGSM8Kで最大44%、MMLUで最大81%の追加speedupを報告する。単一NVIDIA A40上のVicuna-7Bでは、通常投機的復号が約44 tokens/sなのに対しCS Draftingは約56 tokens/s、Tree Attentionと組み合わせるとGSM8K 63.81、MMLU 63.37 tokens/sまで向上する。

## 問題設定

### Draft modelが速くても、K回の逐次実行は残る

通常の投機的復号では、targetが1回検証する前にdraft modelが

[
x_{t+1}
ightarrow x_{t+2}
ightarrow cdots 
ightarrow x_{t+K}
]

とK回自己回帰生成する。target forwardの回数は減るが、draftのcritical pathはK step残る。

targetとの一致率だけを考えれば大きなdraftが有利だが、draft 1 stepの時間も大きくなる。逆に極小draftは速いが、早い位置でrejectされるとtarget 1回あたりの確定token数が減る。CS Draftingはこの「draft品質とdraft latency」の交換条件を、model階層そのものへ分解する。

### Draft列の後ろほど「計算を掛ける価値」が低い

投機的復号でj番目のdraft tokenがtargetに採用されるには、その前の1〜j-1番目が全て受理される必要がある。各tokenのacceptance probabilityを単純化してpとすれば、j番目まで到達する確率は概ね (p^j) のように指数的に下がる。

したがって、先頭tokenと末尾tokenへ同じ大きさのdraft modelを使うのは資源配分として非対称である。後ろのtokenは、予測自体が正しくても前tokenのrejectで捨てられる可能性が高いため、安いmodelへ任せた方が期待walltimeを下げられる。

## 手法

### 1. Vertical Cascade — draft modelを「小model + reviewer」に分解する

通常はtarget Tに対しdraft Dが自己回帰生成する。Vertical Cascadeでは、D自身を小model Sのtargetとして投機的復号する。

つまり
**統計draft → 小neural draft → 大neural draft → 最終target**
というreview階層を作る。最下層だけが候補を直接生成し、その候補を上位modelがまとめて検証・修正して、さらに上へ渡す。

この再帰構造により、大きいdraft modelがK tokenを1つずつ生成する必要を減らす。上位draftは「generator」より「reviewer」として使われる割合が増えるため、targetへの高い一致率を保ちながらdraft latencyを下げられる。

### 2. Draft階層内だけlenienceを使い、最終出力は変えない

論文はreviewを緩める **lenience** も利用する。draft階層の中間reviewでは、本来ならrejectする候補を少し受け入れやすくして、下位modelの候補をより長く通す。

ここで重要なのは、lenienceを**最終target reviewには適用しない**ことだ。中間draftが多少誤った候補を通しても、最後にtargetが通常の厳密なspeculative sampling規則で検証する。このため中間cascadeの速度最適化が最終出力分布を変えない。

### 3. Horizontal Cascade — 後ろのtokenほど小さいmodelへ切り替える

Horizontal Cascadeはdraft positionごとにmodelを変える。先頭はtargetとの一致が重要なので比較的大きいdraft modelを使い、位置が後ろになるにつれて小さいmodelへ切り替える。

例えば先頭数tokenをFLAN-T5-baseで、その後をFLAN-T5-small、さらに後ろをMaGで作る、といった構成を取れる。前述の通り後方tokenはtargetまで到達する確率が低いので、高価なmodelを使う期待価値が小さい。

Vertical Cascadeが「1つのmodelの生成自体を別modelで投機する」縦方向の階層化なのに対し、Horizontal Cascadeは「draft列の位置ごとに計算予算を変える」横方向の階層化である。両者は独立なので同時に使える。

### 4. Max-Gram — neural autoregressive generationの最下層をなくす

cascade最下層に通常のtiny neural LMを置くと、結局そこには自己回帰forwardが残る。MaGはこれを統計的文字列再利用で置き換える。

生成済みprefix末尾と、元promptや既存token列の中で一致する最大ngramを探し、その続きtokenを候補とする。長い一致がなければWikipedia由来bigramへfallbackする。

LLM生成では入力中の固有名詞、コード、定型句、質問文の一部が回答で再利用されることが多いため、単純な統計modelでも一定数の候補をほぼ無コストで供給できる。MaG単独ではtarget一致率が低いが、上にneural reviewerを置くことでその弱点を吸収する。

### 5. EWIF/SWIで「modelごとの1 forward cost」を分けて比較する

CS Draftingは複数modelを階層化するため、単純なacceptance rateだけでは速度を評価できない。論文はmodel 1 forwardのcost ratioとacceptance probabilityから**Expected Walltime Improvement Factor（EWIF）**を解析し、実験では**Standardized Walltime Improvement（SWI）**を使う。

SWIは各model forwardの時間を実測値またはparameter数で固定して、GPUノイズから独立したalgorithmic speedupを比較する指標である。一方、実GPU上のtokens/sも別に測定する。理論上のcascade利得と実wall-clockを分けている。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| Encoder-decoder target | FLAN-T5-XXL |
| neural drafts | FLAN-T5-base / FLAN-T5-small |
| Decoder-only target | Vicuna-7B |
| Vicuna draft | 68M model + Max-Gram |
| Tasks | GSM8K、MMLU |
| decoding | zero-shot CoT、主にgreedy |
| wall-clock GPU | 単一 NVIDIA A40 |
| 比較 | 自己回帰、通常speculative decoding、Medusa、Tree Attention併用 |
| 指標 | SWI、tokens/s |

### FLAN-T5の標準化walltime

| 条件 | GSM8K | MMLU |
|---|---:|---:|
| 通常SD / base draft | 約2.99倍 | 約3.42倍 |
| CS / base + MaG | 約3.27倍 | 約4.21倍 |
| CS / base + small + MaG | 約3.43倍 | 約4.32倍 |

同じモデル群でも、draftを1枚増やせば常に改善するわけではない。GSM8Kではbase+MaGからbase+small+MaGへの差は小さく、cascade階層数と追加review costの釣り合いがある。

論文は通常speculative decodingの最速構成に対し、GSM8Kで最大44%、MMLUで最大81%の追加SWI改善を報告している。

### Vicuna-7Bの実wall-clock

| 方法 | GSM8K tokens/s | MMLU tokens/s |
|---|---:|---:|
| 自己回帰 | 33.34 | 33.11 |
| 通常Speculative Decoding | 44.31 | 43.65 |
| CS Drafting | 56.72 | 55.60 |
| Medusa | 61.87 | 56.19 |
| CS + Tree Attention | 63.81 | 63.37 |

CS Drafting単体でも通常SDを約27〜28%上回る。Tree Attentionと組み合わせるとMedusaも上回り、cascade draftingが候補探索方式と排他的ではないことを示す。

Horizontal Cascadeを外すablationではVicuna-7B/GSM8Kのwalltimeが56.16から53.55 tokens/sへ落ち、後方tokenへ安いmodelを割り当てる効果が独立に確認されている。

## 既存研究との差

通常speculative decodingはtarget + 1 draftという2階層で、draft自身は自己回帰生成する。CS Draftingはそのdraftをさらに投機する**再帰的なspeculative execution**へ拡張する。

MedusaやTree Attentionは複数候補をtargetへ効率良く検証する側を改善する。一方CS Draftingは「候補を作る段階の計算配分」を改善するため、Tree Attentionと併用できる。

また単純なmodel cascadeが入力ごとに「easyなら小model、hardなら大model」を選ぶのに対し、Horizontal Cascadeは**同じ1回のdraft列の中で位置ごとにmodel sizeを変える**点が異なる。

## 限界

複数neural modelを同時に保持すると追加VRAMが必要であり、target・draft familyが大きい環境ではmemory overheadが問題になる。MaG自体は小さいが、base/small modelを複数置く構成は単一draftより複雑である。

Horizontal Cascadeの最適な切替位置やVertical Cascadeの階層数は、各modelの実forward latencyとacceptance rateに依存する。論文のA40・FLAN-T5/Vicuna条件を別GPUや現代的continuous-batching servingへそのまま移すことはできない。

また実験は主にbatch 1のinteractive inferenceを想定する。大batchではtarget forwardの効率が上がり、draft reviewの相対costも変わるため、現在のvLLM/SGLang環境で同じ相対speedupを得るかは未評価である。
