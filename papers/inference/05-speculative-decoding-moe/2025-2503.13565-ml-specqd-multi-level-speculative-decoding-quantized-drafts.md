# ML-SpecQD: Multi-Level Speculative Decoding with Quantized Drafts

> BF16対象の直接MXFP4版を第一段ドラフトにし、その生成を小型ドラフトで再び投機して、専用ドラフト学習なしに最大2.72倍高速化する。

## 概要

通常の投機的復号（speculative decoding; SD）は、小さなドラフトモデルに複数トークンを先読みさせ、大きな対象モデルが一度の順伝播で検証する。高速化は「ドラフトがどれだけ速いか」と「ドラフトトークンがどれだけ受理されるか」の両方に依存する。ところが対象モデルと十分に整合した小型ドラフトを用意するには、専用の事前学習や整列が必要になることが多い。

ML-SpecQDは、BF16対象モデルの重みをそのままMXFP4へ直接変換したモデルを第一段ドラフトに使う。モデル構造と学習済み重みの由来が対象と同じなので、極小モデルほど高速ではない一方、対象モデルとの予測整合性が高い。さらに、そのMXFP4ドラフト自身の逐次生成を別の小型ドラフトで投機する。つまり「BF16対象 ← MXFP4同型ドラフト ← 小型ドラフト」という階層を作り、対象モデルへ低受理率の小型ドラフトを直接ぶつけず、より高速なMXFP4層で一度吸収する。

評価はIntel Core Ultra 9 285KのCPUで行われ、Llama2 7B質問応答ではBF16 greedy比2.22倍、Qwen2.5-Coder 7Bコード生成では2.72倍の幾何平均高速化を得た。後者では単純な0.5Bドラフトも2.64倍と強いが、MXFP4 7Bを第一段、MXFP4化した0.5Bを第二段にした多段構成が最速になった。

## 問題設定

投機的復号では、極小ドラフトほど一トークン生成は速くなるが、対象モデルとの能力差が大きくなると受理率が下がる。受理されないトークンが増えると対象モデルの検証呼び出し回数が増え、ドラフトの小ささがそのままエンドツーエンド高速化へ結び付かない。

逆に対象モデルと近い大きさ・能力のドラフトは受理率が高いが、ドラフト自身の逐次生成が遅い。ML-SpecQDはこの二律背反に対し、「対象モデルそのものを低ビット化した、学習不要で高整合な中間ドラフト」を挿入し、その中間ドラフトの遅さをさらに小型ドラフトで隠す。

論文の解析は主に**単一ユーザー／バッチ1、比較的短い文脈（おおむね4K以下）、重み読出しが支配的なメモリ帯域律速のデコード**を想定する。長文脈で注意計算が支配的になる場合や、大バッチで検証計算が計算律速になる場合は前提が変わる。

## 手法

### 1. BF16対象モデルをMXFP4へ直接変換してドラフト化する

第一段ドラフトは別途学習した小型モデルではなく、BF16対象モデルの重みをMXFP4へ直接キャストした同一アーキテクチャのモデルである。論文のMXFP4形式では32要素ごとに共有スケールを持ち、FP4要素と8ビットのスケールを保持する。このためBF16重みよりメモリから読むデータ量を約3.76分の1へ減らせる。

重要なのは、量子化モデルを最終出力モデルとして使うのではなく**ドラフトとして使う**ことである。量子化による予測差があっても、最終的な採否はBF16対象モデルが検証するため、投機的復号の出力は対象モデルの出力に従う。MXFP4モデルには「対象に近いので高い受理率を得やすい」「追加学習なしに対象モデルから生成できる」という役割がある。

### 2. 受理率とドラフト速度の積で投機効率を考える

一回の投機でドラフトがN個の候補を出し、そのうち先頭G個が受理されたとすると、受理率は `α=G/N` になる。ドラフトが対象モデルよりS倍高速なら、論文は1ラウンドの概算高速化を `(G+1)/(1+N/S)` と整理する。

この式が示すのは、単にSを大きくすればよいわけではないことだ。例えば対象より4倍程度高速なドラフトでも、対象との整合性が高く受理率が80〜90%なら、20〜100倍小さいが受理率がその半分程度のドラフトと同等の速度域に入れる。MXFP4同型ドラフトはこの「極端には小さくないが、受理率が高い」側を狙う。

### 3. MXFP4ドラフトをさらに小型モデルで投機する

多段構成では、BF16対象モデルはMXFP4版を第一段ドラフトとして使う。一方、そのMXFP4版が候補トークンを逐次生成するときには、68M LlamaやQwen2.5-Coder 0.5Bのような小型モデルを第二段ドラフトとして使う。

小型モデルが対象BF16へ直接候補を出す構成では、能力差による低受理率を対象モデルが直接負担する。ML-SpecQDでは小型モデルの検証を高速なMXFP4中間モデルが担当し、MXFP4側で受理された系列をBF16対象がさらに検証する。これにより「小型ドラフトの高速さ」と「対象由来MXFP4の高い整合性」を階層的に組み合わせる。

実装はHugging Face TransformersのAssisted Decodingを複数ドラフトへ拡張し、各段で異なるトークナイザも扱えるUniversal Assisted Generation経路を利用する。API上は複数モデルを `generate` に渡す構成へ拡張している。

### 4. MXFP4を帯域律速のまま走らせるCPUマイクロカーネル

MXFP4で重み読出し量を減らしても、FP4を毎回FP32へ展開してスケールを掛ける処理が重ければ、今度は算術処理が律速になる。そこで著者らはTPP PyTorch C++ ExtensionsとLIBXSMM上にMXFP4 GEMMマイクロカーネルを実装した。

第一の工夫は**遅延スケーリング**で、32要素の部分内積を先に累積し、その後で共有スケールを掛ける。各重みへ個別にスケールを適用するよりFP32乗算を減らせる。第二の工夫はFP4値と活性値をINT8表現へ寄せ、AVX2のVNNI INT8 FMAを使うことだ。これによりFP32 FMAより高い演算スループットを使い、重み圧縮後もカーネルをメモリ帯域律速側に保つ。

## 評価

### 代表的な評価条件

| 項目 | 設定 |
|---|---|
| CPU | Intel Core Ultra 9 285K、24コア（P-core 8 + E-core 16）、最大5.2 GHz |
| メモリ | DDR5-7200、実測読出し帯域104 GB/s |
| 質問応答 | BF16 Llama2 7B、HAGRID 100プロンプト、小型ドラフト68M Llama |
| コード生成 | BF16 Qwen2.5-Coder 7B、MBPP 100プロンプト、小型ドラフトQwen2.5-Coder 0.5B |
| 投機長 | 8 assistant draft tokens |
| 実装 | Hugging Face Assisted Decoding + TPP PyTorch C++ Extensions + LIBXSMM/PARLOOPER |
| 主対象 | 単一ユーザー、低バッチ、比較的短い文脈のメモリ帯域律速デコード |

### 質問応答：Llama2 7B

| 構成 | BF16 greedy比 |
|---|---:|
| BF16 greedy | 1.00倍 |
| 68M小型ドラフトによるSD | 1.81倍 |
| MXFP4 7BドラフトによるSD | 1.86倍 |
| ML-SpecQD（MXFP4 7B + 68M） | 2.22倍 |

MXFP4ドラフトは68Mドラフトより桁違いに大きいにもかかわらず、平均受理率が71.2%で、68Mドラフトの41.7%より約1.7倍高い。専用学習済み68Mドラフトを用意しなくても1.86倍まで到達し、さらに68Mを第二段に置くと2.22倍へ伸びる。ここでは「対象由来の高受理率」が中間ドラフトを置く理由を直接裏付けている。

### コード生成：Qwen2.5-Coder 7B

| 構成 | BF16 greedy比 |
|---|---:|
| BF16 greedy | 1.00倍 |
| Qwen2.5-Coder 0.5Bドラフト | 2.64倍 |
| MXFP4 7Bドラフト | 2.03倍 |
| ML-SpecQD（MXFP4 7B + MXFP4 0.5B） | 2.72倍 |

Qwen系では0.5Bモデル自体が高品質なドラフトで、約62%の受理率を持つため、単段SDだけで2.64倍と強い。一方MXFP4 7Bは約91%の高受理率を持つが、0.5Bより大きいため単段では2.03倍に留まる。両者を階層化すると2.72倍となり、この論文の最大値になる。つまりML-SpecQDの利得は「小型ドラフトが弱いときだけ」ではなく、強い小型ドラフトがある場合でも中間MXFP4段で上積みできる例を示している。

### マイクロカーネルの構成要素除去

コード生成でMXFP4 GEMMのFMAをFP32からVNNI INT8へ変えると、単段MXFP4 SDは1.90倍から2.03倍、多段SDは2.16倍から2.72倍へ伸びた。特に多段では中間MXFP4モデルが複数候補をまとめて検証するため、Nが大きいGEMMの効率が全体速度へ強く効く。

N=8のMXFP4 GEMMではVNNI INT8版が84 GB/s、プラットフォームピークの81%に達し、FP32 FMA版より2.3倍高速だった。アルゴリズムとして多段投機を作るだけでなく、低精度ドラフトの検証カーネルを実際に帯域上限近くまで走らせることが2.72倍というエンドツーエンド値に必要である。

## 既存研究との差

従来の階層型投機では、段数ごとに専用の小型ドラフトを学習・整列する方式がある。ML-SpecQDは、対象モデルを直接低ビット化した版を中間段にするため、追加のドラフト学習なしで階層を増やせる。

単一の量子化ドラフトを使う自己投機とも異なり、MXFP4ドラフト自身をさらに小型モデルで投機する。量子化は最終品質を直接妥協するためではなく、**対象モデルに近い予測分布を持つ高速な検証中間層を作る手段**として使われる。

## 限界

BF16対象に加えてMXFP4同型ドラフトもメモリへ保持するため、追加メモリはBF16対象の約25%になる。メモリ容量が極端に厳しい環境では、この追加常駐量が導入障壁になる。

また、論文の高速化はメモリ帯域律速を強く仮定している。大バッチや長文脈で対象モデルの複数トークン検証が計算律速になると、「複数候補を一回の対象モデル呼び出しで安く検証できる」という前提が弱くなる。さらに、既に非常に小さく高受理率のドラフトが存在する場合、MXFP4中間段の上積みは小さくなり得る。論文自身も、例えば対象より10倍小さく受理率70%程度のドラフトがある場合は従来SDとの差が限定的になり得るとしている。

## まとめ

ML-SpecQDの核心は、量子化を単なるモデル圧縮としてではなく、**投機階層の中間モデルを学習なしで作る方法**として使う点にある。対象由来MXFP4モデルで高受理率を確保し、その比較的大きいドラフトの逐次生成を小型ドラフトで高速化する。さらにCPU向けMXFP4 GEMMをVNNI INT8 FMAで最適化し、アルゴリズム上の階層化を実測速度へ結び付けている。
