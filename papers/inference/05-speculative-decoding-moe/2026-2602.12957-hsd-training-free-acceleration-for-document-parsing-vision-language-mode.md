# HSD: 文書画像解析の領域並列性とページ全体の整合性を両立する階層型投機的復号

## 概要

文書画像をMarkdownや構造化テキストへ変換する視覚言語モデルは、表・数式・本文・読順を一貫して扱えるが、長いページの結果を自己回帰的に1トークンずつ生成するため、出力が長いほど遅延が増える。軽量な文書解析パイプラインはページを段落・表・数式などの領域に分割して並列認識できる一方、領域を独立に処理すると、段組をまたぐ読順やページ全体の構造を誤りやすい。著者らはこの二つの方式を競合関係とせず、**軽量パイプラインの領域下書きを、強力な視覚言語モデルで段階的に検証する**方式を提案する。

HSD（Hierarchical Speculative Decoding）は、まず軽量なパイプラインで領域分割と粗い認識結果を一度に生成する。次に領域画像ごとに並列の投機的検証を行い、文字・数式・表の局所的な誤りを修正する。最後にページ画像全体を与えて、局所結果を統合した下書きをもう一度検証し、段組・読順・領域間の整合性を修復する。領域並列化で得られる速度と、ページ全体を読むモデルの文脈理解を**二段階で併用**する点が特徴である。

OmniDocBench v1.5では、HunyuanOCRを対象に端から端までの処理が2.78倍、dots.ocrでは2.42倍、Qwen3-VL-8Bでは2.61倍になった。HunyuanOCRの特定文書種類では7.04倍の結果も報告される。しかし最大7.04倍はすべての文書の平均ではない。さらに受理判定は確率分布を厳密に保存する拒否サンプリングではなく、しきい値を用いる許容型であるため、**「ほぼ品質を維持」と「数学的に無損失」は区別する必要がある**。

## 背景と課題

従来の文書解析は、レイアウト検出、読順推定、文字認識、表・数式認識、結果の組立てを別モジュールに分けることが多い。この方式は専門化された小型モデルを並列実行しやすく、長い文書を高速に処理できる。ただし最初のレイアウト境界が誤ると後段の認識器が別領域の文脈を見られず、誤りが連鎖する。対照的に、文書全体を画像として入力してMarkdown等を一気に出力する端から端までの視覚言語モデルは、複数列の読順や離れた段落の関係を扱いやすいが、長い出力系列を順次生成する費用が高い。

既存の混合型方式は、領域ごとに視覚言語モデルを並列実行して速度を得るが、各領域が独立しているためページ全体の整合性を失いやすい。HSDはこの欠点を解消するため、領域ごとの結果を最終成果とせず、**ページ全体での再検証のための高品質な下書き**として使う。局所段階で文字や数式をある程度確定しておけば、ページ全体の段階では最初から長い結果を逐次生成する必要がなく、構造的な修正に集中できる。

一般的な投機的復号では、ドラフトモデルが現在の受理済み接頭辞を条件に次の複数トークンを生成し、大型モデルがまとめて検証する。HSDでは軽量な文書解析パイプラインが**ページ当たり一度だけ**領域下書きを作る。検証が進むたびに下書きを再生成しないため、ドラフト作成の費用が小さい一方、現在の受理済み接頭辞と事前下書きの位置がずれていく問題が生じる。著者らはこの問題を解くため、受理済みトークンと下書きの照合、および接頭辞木による複数候補の一括検証を組み合わせた。

## 手法

### 1. ページ分割と固定下書きの作成

ページ画像を $x$、最終的な文書解析器を $p_\theta$ とする。軽量なパイプライン $q_\phi$ はページの領域集合 $\mathcal R=\{r_i\}_{i=1}^{M}$ を推定し、各領域の認識結果を固定下書き $\tilde{Y}^{(i)}$ として出力する。領域には段落、表、数式などが含まれ、下書きは文字列・構造化記法として用意される。論文の既定設定ではPP-StructureV3がレイアウト解析と下書き生成を担当する。

重要なのは、軽量パイプラインの結果を最終答えとして採用するのではなく、**視覚言語モデルが検証する候補**として扱う点である。下書きが正確なら多くのトークンをまとめて受理でき、誤っていれば視覚言語モデルがその部分を訂正する。従来のドラフトモデルのように生成途中で何度も起動するのではなく、一回の下書きを後段の二つの検証で再利用するため、ドラフト側の費用を抑えられる。

### 2. 第1段：領域単位の局所並列検証

領域 $r_i$ に対応する切出し画像 $z_i$ と下書き $\tilde{Y}^{(i)}$ を、視覚言語モデルの検証演算 $\mathrm{SpecDecode}(p_\theta,z_i,\tilde{Y}^{(i)})$ に渡す。各領域の検証は独立しているため並列化でき、ページ全体の長い結果を一系列として出力するより、遅延の律速となる最長系列を短くしやすい。文字・数式・表の局所的な認識誤りをこの段階で修正し、より品質の高い領域別結果 $\hat Y^{(i)}$ を得る。

しかし切出し画像にはページ全体の段組や読順の情報が欠ける。レイアウト分割の境界が間違っていれば、領域内だけの検証では修正できない場合もある。著者は第1段のみの方式では品質が大きく低下することを実験で示しており、**領域並列化の速度だけで最終品質を評価してはいけない**。この段階は高速な中間処理であり、最終結果ではない。

### 3. 第2段：ページ全体の大域検証

第1段で得た領域結果を集め、ページ全体の下書き $\tilde{Y}^{pg}=\{\hat Y^{(i)}\}$ を作る。これをページ画像 $x$ とともに同じ視覚言語モデルへ渡し、$\mathrm{SpecDecode}(p_\theta,x,\tilde{Y}^{pg})$ を実行する。モデルはページ全体を見ながら領域間の読順、段組、表の連続性、見出しの階層などを確認し、局所段階に残った誤りを訂正する。

第2段はページ全体を扱うため完全に並列ではないが、入力下書きが第1段で精緻化されているので、検証で受理できるトークンが多く、ゼロから長いMarkdownを逐次生成するより少ない生成ステップで済む。ページ全体の情報を最後に使うことが、領域分割の誤りや局所的な読み順の不整合を修復する鍵となる。

### 4. 受理済み接頭辞と固定下書きの照合

下書きは最初に一度だけ生成されるため、視覚言語モデルが訂正を加えると、現在の受理済み接頭辞と下書きの位置が一致しなくなる。HSDの分離型投機的検証（Decoupled Speculative Verification; DSV）は、受理済み系列の末尾 $n$ トークンを参照窓として取り出し、固定下書きの内部から同じ並びが現れる位置を探す。見つかった位置の直後に続く部分系列を、次に受理され得る候補として抽出する。

参照窓の長さは既定で3トークンである。複数の位置が一致した場合は、下書き中の複数の続きが候補になる。たとえば表のセルや見出しなど同じ短い文字列が繰り返される場合、一致位置が複数見つかる。これらを一つずつ別の検証パスで処理すると重複計算が多いため、次の接頭辞木へまとめる。参照窓が短すぎると偶然一致が増え、長すぎると候補が見つからない可能性があるため、窓長は重要な設計パラメータとなる。

### 5. 接頭辞木と一括検証

抽出した候補系列を接頭辞木（Prefix Tree）にまとめ、共通する冒頭部分を一度だけ表現する。各ノードは、そのノードへ至るトークン列を表し、枝分かれによって複数の候補の続きを保持する。木を一列のパック系列へ変換し、**各ノードは受理済み接頭辞と自分の祖先ノードにだけ注意できる**という木構造の注意マスクを用いる。これにより、別の候補枝の未来トークンを参照せずに、複数の候補を一回のモデル前向き計算で検証できる。

検証時は、各ノードの候補集合の中でモデルが最も高く評価した候補トークン $u^*$ を選ぶ。同じ文脈で語彙全体から選んだ最大確率トークン $\hat u$ と比較し、$\log p(u^*)-\log p(\hat u)\geq\log\tau$ なら候補を受理して木を進む。条件を満たさない場合は枝をたどるのを止め、モデル自身の最有力トークンを採用する。これを繰り返して複数トークンを一括受理する。

ここで $\tau=0.75$ は許容型の受理しきい値であり、$u^*$ が語彙全体の最有力トークンと完全一致しなくても受理され得る。**厳密な分布保存型の投機的復号とは異なる**ことに注意する。著者が主張する「ほぼ無損失」は、評価した文書解析の品質がほぼ維持されたという経験的な意味であり、すべての入力で元モデルの出力分布が数学的に同じになるという意味ではない。

## 評価条件

| 項目 | 一次論文の条件 |
|---|---|
| 対象モデル | HunyuanOCR、dots.ocr、Qwen2.5-VL-3B/7B、Qwen3-VL-2B/8B |
| GPU | NVIDIA A100 |
| 実装 | Hugging Face Transformers、FlexAttentionを利用し比較条件を統一 |
| 既定の下書き生成 | PP-StructureV3。別のパイプラインも比較 |
| 照合窓・受理しきい値 | $n=3$、$\tau=0.75$ |
| パックした検証木の上限 | 128トークン |
| 評価集合 | OmniDocBench v1.5（1,355ページ）、olmOCR-Bench（1,403 PDF・7,010テスト）、Ocean-OCR-Bench（英中200画像） |
| 効率指標 | 復号ループの実測高速化、端から端までの実測高速化、平均受理トークン数 |
| 品質指標 | 文書解析得点、編集距離、F1、精度・再現率、BLEU、METEORなど各評価の公式指標 |

復号ループの高速化は、ドラフト生成、並列検証、受理・巻戻し、KVキャッシュ管理、通信費用を含むが、ループ外の前処理や画像の入力処理は含まない。一方、端から端までの高速化はページ画像入力から最終結果までを測り、視覚符号化・入力処理を含むがディスク入出力は除外する。**この二つの倍率を混同しない**。平均受理長（Average Acceptance Length; AAL）は検証一回あたり何個の候補トークンを受理したかを示すが、それ自体は速度倍率ではない。

## 主要結果

### モデルごとの端から端までの高速化

| モデル | OmniDocBench v1.5のAAL | 復号のみ高速化 | E2E高速化 |
|---|---:|---:|---:|
| Qwen2.5-VL-7B | 3.56 | 2.13倍 | 2.10倍 |
| Qwen2.5-VL-3B | 2.52 | 2.14倍 | 2.12倍 |
| Qwen3-VL-8B | 3.98 | 2.62倍 | 2.61倍 |
| Qwen3-VL-2B | 3.33 | 2.20倍 | 2.18倍 |
| dots.ocr | 3.98 | 2.44倍 | 2.42倍 |
| HunyuanOCR | 4.55 | 2.82倍 | **2.78倍** |

HunyuanOCRではOmniDocBench v1.5で2.78倍、olmOCR-Benchで2.46倍、Ocean-OCR-Benchで3.29倍を報告する。Qwen2.5-VL-3BでもOmniDocBench v1.5で2.12倍、olmOCR-Benchで2.64倍、Ocean-OCR-Benchで2.72倍となる。異なる文書集合やモデルに対して、改善幅は変わるが全体として正の高速化が見られる。

OmniDocBench v1.5の文書種類別では、HunyuanOCRの新聞で4.30倍、財務報告で7.04倍という高い値がある一方、スライドは1.58倍、雑誌は1.72倍にとどまる。下書きの品質、ページ内の領域数、出力の長さ、画像入力処理と復号の比率が異なるためである。**最大7.04倍を全ページ平均の性能として報告しない**。

### 品質維持の程度と二段階の必要性

| dots.ocrの評価 | OmniDocBench v1.5 | olmOCR-Bench | Ocean-OCR-Bench |
|---|---:|---:|---:|
| 軽量パイプライン下書きのみ | 86.73 | 65.80 | 85.20 |
| 端から端までの元モデル | 88.41 | 79.90 | 91.45 |
| 第1段のみ（領域検証） | 70.47 | 67.30 | 86.92 |
| **第1段＋第2段（HSD）** | **88.81** | **79.40** | **92.56** |

第1段のみではOmniDocBenchの品質が88.41から70.47へ大幅に低下する。領域ごとの認識を並列化するだけでは、ページ全体の読順・レイアウトの誤りを修復できないことを示す。第2段を追加すると88.81まで回復し、元モデルの88.41をわずかに上回る。ただしolmOCR-Benchでは元モデル79.90に対して79.40と0.50点低く、**すべての評価で完全に品質一致したわけではない**。このため「near-lossless（ほぼ無損失）」という表現が妥当であり、厳密な無損失性の証明ではない。

### 構成要素除去と既存投機的復号との比較

OmniDocBench v1.5でdots.ocrを使った構成要素除去では、ページ単位の投機的復号のみでAAL 2.49、復号のみ2.11倍、E2E 2.09倍となる。領域検証とページ検証を組み合わせるとAAL 3.98、復号のみ2.44倍、E2E 2.42倍へ改善する。局所段階の下書き精緻化が、ページ全体の候補受理率と最終速度を高めるという機構を支持する。

Qwen2.5-VL-3Bを同じ対象モデルにした既存方式との比較では、OmniDocBench v1.5のE2E高速化が、EAGLE-2の1.69倍、ViSpecの1.75倍、Sparrowの1.57倍に対し、HSDは2.12倍だった。olmOCR-BenchでもHSD 2.64倍に対してEAGLE-2 1.86倍、ViSpec 1.90倍である。ただしこれらの方式は、原著の設定で文書解析へ適応させたドラフト・検証構成であり、一般的なチャット生成全体に対する性能順位を意味しない。

視覚トークン圧縮（Visual Token Compression; VTC）を採用するDeepSeek-OCRへHSDを追加した実験では、VTCのみを1.00倍の基準として、OmniDocBench v1.5で1.56倍、olmOCR-Benchで1.41倍、Ocean-OCR-Benchで1.91倍となる。**入力側の視覚トークン削減と、出力側の階層的な投機的検証は別の最適化軸**であり、組み合わせられることを示す。ただし追加速度倍率は元のVTC実装を基準にしており、一般的な文書解析器へ無条件に乗算できる値ではない。

## 既存研究との差

HSDの独自性は、軽量な文書解析パイプラインを単なる前処理として使うのではなく、**下書きを一度だけ生成する投機的復号器**として扱うことにある。通常の投機的復号は現在の受理済み系列に合わせてドラフトを逐次更新するが、HSDは固定された下書きの中から現在の接頭辞と一致する箇所を探し、続きの候補を接頭辞木へまとめる。これにより、ドラフト生成と検証を分離し、パイプラインの高い並列性を活かす。

さらに、領域ごとの検証で局所的な誤りを直し、ページ全体の検証で構造的な誤りを直すという二階層の設計を採る。既存の領域並列型文書解析が失いやすい大域文脈を、最後の検証で回復する。これは一般的な生成モデルの投機的復号へそのまま適用できるものではなく、**文書画像の領域分割と構造化出力というタスク特性を利用した方式**である。

## 限界・適用上の注意

第一に、軽量パイプラインの下書き品質に依存する。文字認識が難しい手書き、劣化したスキャン、複雑なレイアウトでは候補の受理率が低下し、投機的検証の利益が減る。下書きが誤った領域境界を持つ場合、第1段では修正できず、第2段のページ全体検証へ負担が集中する。高速化は長文出力と多くの独立領域を持つ文書で大きい一方、短い文書や入力処理の比率が高い文書では小さくなる。

第二に、受理しきい値0.75は候補トークンを元モデルの最大確率トークンと完全一致しなくても許容する。原著の品質表は経験的な近似無損失を示すが、元モデルと全く同じ出力を返すという数学的な保証はない。表の0.5点程度の低下や上昇を含め、文書解析の実務では誤読の重要度に応じた品質監査が必要になる。

第三に、木構造の検証には特殊な注意マスクとパック処理が必要であり、推論エンジンがそのまま対応しているとは限らない。論文はHugging Face TransformersとFlexAttentionで評価しているため、vLLM、llama.cpp、Ollamaへ容易に組み込めると断定できない。CUDAカーネル、KVキャッシュ更新、候補木の動的なバッチ処理、画像の入力処理との統合が追加実装の課題になる。

第四に、評価GPUはNVIDIA A100であり、RTX 4070 Super 12GBのような小容量GPUへそのまま速度倍率を外挿できない。文書解析用の視覚言語モデル、軽量パイプライン、領域別の並列検証を同時に動かすため、モデル常駐容量とバッチサイズが制約される。メモリが足りずCPUオフロードが必要な場合、データ転送費用が高速化を相殺する可能性がある。

第五に、文書解析の品質は単一の文字一致率だけでは測れない。段組の読順、表のセル結合、数式の構造、文書全体の階層関係が重要であり、異なるベンチマークの得点を単純に比較できない。HSDの主張は、文書解析の複数の品質指標を概ね保ちながら実測遅延を下げたことであって、すべての文書・言語・品質基準で元モデルと完全一致したことではない。
