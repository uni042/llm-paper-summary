# RLM-Cascade: Response-Level Speculative Decoding for Cost-Efficient LLM API Serving

> 投機的デコードを応答単位へ粗くしてAPI越しに適用するプロキシ。単純なターンは安いモデルだけで返し、複雑なターンは下書きを高性能モデルが判定し、ツール選択は直行させることで費用を45.8パーセント削減した。

## 概要

最先端モデルのAPI費用は小規模モデルの50倍から100倍に達し、セッションあたり数十ターンを発行するエージェント型の利用では費用が支配的になる。費用を下げる古典的な道具である投機的デコードは、ドラフトと検証の両モデルが語彙を共有し、ロジットへアクセスできることが前提で、別プロバイダのHTTP APIとして提供されるモデル同士では成立しない。もう一方のカスケードや振り分けは、リクエスト全体をどちらか1つのモデルへ寄せるため、安いモデルが失敗したときの受け止めがない。

RLM-Cascadeは、投機の単位をトークンから応答全体へ粗くすることで、この前提を外す。プロキシがAPI呼び出しを横取りし、安いDeepSeek-V4-Proが応答の下書きを作り、高性能なclaude-opus-4-8が下書きを採用するか、書き直して返すかを自然言語の判定で決める。さらに前段の規則ベースの複雑度ルーターが3つの経路へ振り分ける。単純なターンは検証を省いて下書きだけで返す経路、複雑なターンは下書きと検証の経路、ツール選択ターンはスキーマ遵守を保証するため高性能モデルへ直行する経路である。代表結果として、本番のClaude Codeワークロード125件で下書き利用率88.8パーセント、API費用は直接のOpus利用に対して45.8パーセント削減され、中央値の応答時間は3698ミリ秒から2026ミリ秒へ1.83倍改善した。品質は20課題のベンチマークで合格率100パーセントと、直接利用の95パーセントを上回った。

## 問題設定

資源の非対称は明確である。検証モデルの出力価格は100万トークンあたり27.50ドル、ドラフトは3.48ドルで約8倍の開きがあり、入力側でも同様の差がある。一方でエージェントのターンは一様ではない。本番セッションでは70から80パーセントがツール選択ターンで、JSONスキーマへ厳密に従う必要があり、壊れた出力は実行ループそのものを止める。残りのテキスト生成ターンは形式の自由度が高く、下書きと検証の pipeline に向く。さらにテキスト生成の中でも、挨拶や単純な質問と、セキュリティや複雑なコード生成では必要な品質が違う。既存の振り分けはリクエスト単位で1モデルに決めるため、安いモデルの失敗を高いモデルの目で拾う構造がなく、投機的デコードはAPIの壁で使えない。本論文は、モデルの内部へ触れずに、両モデルを同一リクエストへ順に適用する余地がプロキシ層にあることに着目する。

## 手法のあらまし

クライアントのAPIの向き先をプロキシへ変えるだけで導入でき、クライアント側の変更は要らない。リクエストが届くと、まずルーターがツール欄の有無、単純な接頭辞、複雑キーワード、入力長を順に見る。ツール欄があれば検証モデルへ直行し、単純と判定されればドラフトモデルだけが応答して返す。複雑な場合は、元のシステムプロンプトとメッセージをそのままドラフトモデルへ渡して下書きを作り、次に元のリクエストへ下書きを連結し、品質向上層としての指示文で包んで検証モデルへ渡す。検証モデルは下書きをそのまま採用する合図か、書き直した応答を囲みタグつきで返す。応答がクライアントへ返った後、トレースと費用の記録は非同期で行われ、応答経路の遅延へは乗らない。

## 手法

### 1. 応答単位の投機 — 判定を自然言語へ置き換える

トークン単位の方式では、ドラフトの各トークンを検証モデルの確率とドラフトの確率の比で受理し、分布の一致が保証される。応答単位ではこの積を応答全体へ拡張した量が概念上の対応物になるが、API越しには確率を計算できない。そこで検証は、検証モデル自身の自然言語の判断で代理する。検証側の指示文は、下書きの書き直しではなく誤りの検出が仕事であること、既定は承認であること、事実誤りや本当のコードの欠陥、決定的な手順の欠落、要求の根本的な誤解がある場合だけ書き直すことを明示する。この承認寄りの偏りが、文体の不一致だけで書き直しが膨らむことを防ぐ仕掛けである。代償として、トークン単位のような分布の無損失性は失われ、品質は実測で担保するしかない。得られるものは適用範囲で、語彙も提供者も異なる任意のAPIモデルの組へ、下書きと検証を合成できる。

### 2. 規則ベースの複雑度ルーター — モデルを呼ばずに経路を決める

ルーターはモデル呼び出しなしの定数時間で動き、規則は順に評価される。第1に、ツール欄が空でないリクエストは検証モデルへ直行する。ドラフトモデルはツール利用のJSONスキーマへ安定して従えないためである。第2に、テキスト生成リクエストについては、「what is」や「summarize」のような単純な接頭辞は下書きのみの経路へ、classやsecurityやsqlといった複雑キーワード、あるいは1500文字を超える入力は下書きと検証の経路へ送られ、既定も検証経路である。このルーターが費用構造を決める。下書きのみの経路は検証モデル費用の約2パーセント、採用の経路は約20パーセント、書き直しの経路は約115パーセントであり、期待費用は各経路の比率の加重和になる。論文の費用モデルでは、書き直し比率の最悪条件でも、下書きのみの比率が13.3パーセントを超えれば純粋な節約になることが示され、本番の64から70パーセントは大きな安全余裕を持つ。誤りの代価は非対称で、複雑なターンを単純と誤る誤りは品質リスクを生むが、単純なターンを複雑と誤る誤りは費用が約1.2ポイント悪化する程度にとどまるため、ルーターは品質側へ倒して設計されている。

### 3. ハイブリッドなツール呼び出し戦略 — 到達範囲を正直に区切る

エージェントのターン種別に合わせ、ツール選択ターンは投機の対象から外す。本番セッションではターンの70から80パーセントがツール選択であり、投機が届くのは残りの20から30パーセントだけである。この区切りは弱点の告白であると同時に、スキーマ違反で実行ループを壊す事故を構造的に避ける判断である。費用削減の主張も、この到達範囲の中で読む必要がある。テキスト生成部分で約47パーセントの削減率でも、セッション全体への効きはターン構成で薄まる。論文は100件/日の規模で月額2000から3000ドル規模の削減という換算を示している。

### 4. 費用モデルと可観測性 — 運用で検証できる形にする

費用は判定ごとの式として定式化され、下書きのみ、採用、書き直しの各経路について、ドラフトの入出力価格と検証モデルの入出力価格から基準費用との比が導かれる。理論上の期待節約率と実測の節約率の差は、ツール直行の間接費とトークン長のばらつきで説明される。可観測性は運用の前提として組み込まれ、リクエストごとの入れ子トレース、判定分布と節約率と遅延の百分位を示すライブダッシュボード、Prometheus形式のメトリクスが用意される。プロバイダ間の故障への備えとして、下書きが失敗したら検証モデルへ直行し、検証が失敗したら下書きをそのまま返す縮退動作と、モデルの版固定による静かな品質変化の防止が実装されている。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 複雑度ルーター | ツール欄、接頭辞、キーワード、入力長 | 3経路へ規則で振り分ける | 検証モデル呼び出しの削減 | キーワード規則のため意味的な難しさは拾えない |
| 下書き生成 | 元のリクエスト | 安いモデルが応答全体の下書きを作る | 生成費用 | 下書きの質が採用率を左右する |
| 応答単位の検証 | 元の要求と下書き | 採用の合図か書き直しを返す | 品質の担保 | 無損失性はなく、書き直しは基準より高くつく |
| ツール直行 | ツール欄のあるターン | 検証モデルが直接応答する | スキーマ遵守 | ターンの7から8割は投機の対象外 |
| 可観測性 | 全リクエスト | トレースとメトリクスを非同期に記録 | 運用での検証可能性 | 記録基盤の運用費用が別途かかる |

## 評価

### まず見るところ

- **結論:** 費用の利得の主役は検証の効率ではなく、下書きのみ経路がワークロードの多数派であることにある。だからこそ遅延まで同時に改善する。
- **速度・効率:** 端から端までの遅延は平均で1.65倍、中央値で1.83倍速い。一方で初回トークンまでの時間は2.1倍悪化し、逐次実行の代償が残る。
- **品質:** 20課題では合格率100パーセントで直接利用の95パーセントを上回るが、標本は小さく二値判定である。
- **費用:** 全期間の実測で45.8から47.4パーセントの削減。ただし書き直し経路は基準より約15パーセント高く、費用が逆転する事例も1件報告されている。
- **評価の強さ／注意点:** 本番実測である代わりに再現性は低く、価格もモデル版も当時の条件に依存する。

**数値の読み方。** 節約率と遅延改善は、経路の混合比の関数として読む必要がある。下書きのみ経路の比率が下がれば、節約は費用モデルの表のとおり急速に痩せる。逆に初回トークン時間の悪化は構造的で、対話型のストリーミング用途ではこの方式の適性が変わる。品質の上回りは、検証の指示文が制約充足へ注意を向けさせるためという仮説が提示されているが、統制実験は今後の課題とされている。

## 既存研究との差

FrugalGPT等の振り分けは、学習した方針でリクエストを1つのモデルへ割り当て、LLMカスケードは信頼度で格上げを決める。どちらも同一リクエストへ両モデルを適用しない。トークン単位の投機的デコードは両モデルを使うがロジットを前提とする。本論文の差分は、投機の単位を応答へ粗くし、検証を自然言語の判定へ置き換えることで、APIしかない異種モデルの組へ下書きと検証の構造を持ち込んだことと、ツール選択ターンの切り分けまで含めて本番の費用で検証したことにある。vLLMやOrca等のモデル層のサービングとは直交し、組み合わせ可能と位置づけられている。

## 限界・実装状況

初回トークン時間の2.1倍の悪化は構造的で、ストリーミングが重要な対話用途には向かない。並行に下書きと検証を始める案は、捨てる下書きの計算を無駄にする代償つきで今後の課題とされる。ルーターはキーワード規則であり、意味的な難しさを拾えず、学習型ルーターへの置き換えが今後の第一課題として挙げられている。書き直し経路では費用逆転が起こりうることも実測で示された。本番配備されオープンソース公開とされるが、本文中にリポジトリのURLは示されていない。

## 一般的な実装上の含意

API費用の最適化では、検証の効率化より先に、そもそも高いモデルを呼ばなくてよいリクエストの比率を測るべきである。混合比が損益分岐を大きく上回るワークロードでは、単純な規則ルーターでも大きな節約になる。逆に、応答単位の検証のような近似を入れるときは、承認を既定にする指示設計と、判定分布と費用を常時観測できる仕組みが、品質事故を防ぐ前提になる。ツール呼び出しのような形式が厳密なターンは、最適化の対象から外す判断自体が設計の一部である。
