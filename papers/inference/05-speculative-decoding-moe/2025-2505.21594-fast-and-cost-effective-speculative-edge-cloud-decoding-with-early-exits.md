# Fast and Cost-effective Speculative Edge-Cloud Decoding with Early Exits

> Cloud 対象の早期出口から暫定トークンを返し、edge ドラフトを最終検証と並行して先行生成することで待ち時間を隠し、Jetson Nano＋A100でpre-drafting単体最大11%級の追加改善を示す。

## 概要

投機的復号（投機的復号）は、小さい **下書きモデル** が複数トークン候補を先に作り、大きい **対象モデル** がそれらを一度に検証する。候補がよく当たれば、対象モデルを1 トークンずつ逐次実行するより少ない順伝播回数で生成を進められる。最終的なaccept/rejectは対象モデルが決めるため、ドラフトは速度を上げる補助役である。

エッジ・クラウド構成では、小型ドラフトを端末へ置けばcloud側で下書きモデルを動かす費用を減らせる。しかし通常の流れは「端末でドラフト → ネットワーク送信 → cloudで対象検証 → 結果受信 → 次ドラフト」と直列で、cloudが検証している間の端末はほぼ待機する。特にJetson Nanoのような遅いclientではドラフト時間とネットワーク 遅延が大きく、vanilla 投機的復号自体がcloud自己回帰より遅くなるモデル pairもある。

Fast Speculative Decoding（FSD）は、この待ちを **早期出口（early exit）** で埋める。Target モデルの途中の層に軽量な出力ヘッドを付け、最終層まで計算が終わる前に「最終結果になりそうなトークン」をclientへ順次返す。Clientはそれぞれの候補から次roundのドラフトを先行生成してキャッシュする。最終出口が届いたとき、そのトークンと一致するearly-exit由来ドラフトがあれば即座に次検証へ進める。

Jetson NanoとA100、Vicuna-68M ドラフト＋Llama2-7B 対象の評価では、edge-cloud 投機的復号がcloud自己回帰に対して有利になる条件で最大35%の遅延削減を報告する。さらにFSDのpre-draftingはvanilla 投機的復号に対し、Jetson上の同モデル pairで平均1.11倍の追加高速化倍率を示す。Unitree Go2上のvision-language モデル（VLM）制御ではcloud自己回帰比21%高速化を報告する。

## 問題設定

### 通常の投機的復号ではdraftとverificationが直列になる

1 roundで下書きモデルが `γ` 個のトークンを生成し、その候補列を対象モデルへ送る。Targetは一度の順伝播で候補を検証し、何トークン受理できるかを決める。その結果が返ってきてから、下書きモデルは次roundを始める。

同じGPU内ならドラフト/対象間の通信は軽いが、edgeとcloudへ分割するとclient-server通信 `T_c` が入る。さらにedge ドラフトの順伝播時間 `T_p` がcloud 対象の `T_q` に比べて大きいと、対象の順伝播回数を減らしてもドラフト＋通信コストが勝ち、自己回帰より遅くなる。

したがって重要なのは下書きモデルを小さくすることだけではなく、**対象 検証中にclient側で有用な仕事を進められるか**である。

### 早期出口は最終答えとして使わず、先行計算のhintとして使う

Early exitは対象モデルの中間層 隠れ 状態からトークンを予測する。浅い層ほど早く結果が出るが、最終層のトークンと一致しない可能性が高い。

FSDはこの不確実なトークンをそのまま最終出力にしない。あくまで「次ドラフトを先に計算するための分岐候補」として使い、最終対象 出力が届いた後に一致する分岐だけを採用する。したがってearly-exit誤りの主な影響は品質ではなく、無駄なclient計算とキャッシュ missとして現れる。

## 手法のあらまし

Serverの対象モデルには複数層位置へearly-exit adapterを追加する。Verificationを開始すると、各exitが候補トークンとconfidenceを生成し、serverは有望なearly resultを順次clientへ送る。

Clientは受信した候補ごとにthreadを立て、その候補を「次トークンとして正しかった」と仮定して `γ` トークン分のドラフトを先行生成する。生成済みドラフトは候補トークンをkeyとしてキャッシュ/priority queueへ保存する。

最終対象 出力が届いたとき、対応するkeyのpre-ドラフトがキャッシュにあればhitであり、ドラフト 遅延を待たず次roundへ進む。なければmissとしてvanilla 投機的復号と同じようにドラフトを生成する。つまりFSDの速度は「early exitが最終結果と一致する確率」と「pre-ドラフトが最終結果到着までに生成し終わるか」に依存する。

## 手法

### 1. Target modelへearly-exit adapterを付ける

Target backbone自体を置き換えず、選んだ中間層へ小さなadapterとlanguage-モデル ヘッドを追加する。これらを学習し、途中隠れ 状態から次トークン分布を出せるようにする。

論文の代表構成ではVicuna-7BとLlama2-7Bに31個、Vicuna-13Bに39個のexitを持たせる。追加パラメータは7B級で約101M、Llama2-7Bでは全体の約1.48%である。Backboneを凍結し、early-exit側を学習するため、対象本体を再学習する方式ではない。

入力は検証中の中間隠れ 状態、出力はearly トークン候補とconfidenceである。この出力は最終生成トークンではなく、clientの投機的 workを早く始めるtriggerになる。

### 2. Confidence付きearly resultをserverから順次送る

Serverは各early exitで候補トークンを得る。複数exitがほぼ同時に結果を出すため、すべてを無秩序にclientへ投げると通信とthread数が膨らむ。

FSDはearly resultへconfidenceを付け、priorityを付けてclientへ処理させる。最終層に近いexitほど一般に精度は高いが到着が遅く、浅いexitは早いが外れやすい。この「早さと一致率」の交換条件が、どのcandidateから先にpre-ドラフトするかへ直結する。

### 3. Client側で候補ごとのdraftを並列に先行生成する

Clientがearly トークンを受け取ると、そのトークンが正しいと仮定した次roundのドラフトを小型モデルで生成する。複数early exit候補について並列に走らせ、結果をキャッシュへ保持する。

ここで計算を投機する対象は **対象モデルの最終トークンではなく、その先のドラフト 系列** である。これによりserverが対象の残り層を実行している時間を、clientの次round準備へ変換する。

Client 資源には上限があり、Jetson NanoではCPU thread数と4GB メモリがボトルネックになる。論文Table 5ではVicuna-68Mで最大15 early-exit thread、Vicuna-160Mでは7 threadまでとしている。RTX clientではそれぞれ30、15 threadまで増やせる。

### 4. Final verification後にcache hitならdraft時間を消せる

最終対象 resultがclientへ届いたら、そのトークンをkeyとしてpre-ドラフト キャッシュを引く。

- **Hit:** 一致するearly exitから作った次ドラフトが既にあるため、すぐserverへ送れる。
- **Miss:** 正しいトークンに対応するドラフトがないので、その時点から通常通りドラフトする。

Target モデルによるfinal 検証は省略しないため、early exitが外れた場合もそのprediction自体を最終出力へ採用しない。従ってFSDのbenefitはキャッシュ hit時のドラフト 遅延隠蔽、コストはmissした分岐に使った端末計算とthread/キャッシュ管理である。

## 評価

### 代表的な評価条件

| 項目 | 設定 |
|---|---|
| Server | NVIDIA A100 |
| Client | NVIDIA Jetson Nano / RTX 2080 Ti node |
| 主要ドラフト-対象 | Vicuna-68M / Llama2-7B |
| 他モデル pair | Vicuna-68M / Vicuna-7B、Vicuna-160M / Vicuna-13B |
| Draft長 | 代表設定 `γ=4`、感度評価では最大10 |
| Benchmark | MT-Bench、HumanEval、GSM8K、Alpaca、CNN/DailyMail、Natural Questions |
| 比較 | cloud autoregressive（AR）、vanilla edge-cloud 投機的復号（SD）、FSD |
| 実機demo | Unitree Go2、VLM-based control |

### System latencyの中身

Table 5の `γ=4` では、Vicuna-68M/Llama2-7BについてJetson clientのdrafting 遅延は301 ms、対象 検証は522 ms、client-server 通信は96 msである。RTX clientではdrafting 99 ms、対象 467 ms、通信 47 msとなる。

この差から、Jetsonではclient計算と通信を隠せる価値が大きい一方、そもそものvanilla SDがARに勝てないモデル pairも生じることが分かる。

### 代表的な評価結果

| 条件 | 比較 | 結果 | 読み取れること |
|---|---|---:|---|
| Vicuna-68M/Llama2-7B、Jetson平均 | AR → vanilla SD | 約1.34–1.35× | ドラフト/通信 コストを受理トークン数で回収できる組合せ |
| 同、HumanEval | AR → vanilla SD | 1.53× | headlineの「最大35% 遅延削減」に相当する代表条件 |
| Vicuna-68M/Llama2-7B、Jetson平均 | SD → FSD | 1.11× | pre-drafting自体の追加効果 |
| Vicuna-68M/Vicuna-7B、Jetson平均 | AR → SD | 1×未満 | edge 投機的復号自体が常に有利ではない |
| Vicuna-160M/Vicuna-13B、Jetson平均 | AR → SD | 1×未満 | ドラフトが重いと通信・client待ちが勝つ |
| Unitree Go2 VLM control | cloud AR → 提案系 | 21%高速化 | robotics demoでエンドツーエンド効果を確認 |

FSDはvanilla SDに対しては全モデル pair・両clientで平均約1.04〜1.11×の改善を報告する。つまり「35%」の大部分はedge-cloud 投機的復号そのものの効果を含み、**early-exit pre-draftingだけの上積みは数%〜11%程度**と読むのが正確である。

### Draft長 `γ` のtrade-off

Draft トークン数を増やすと1回の対象 検証で多く進める可能性がある一方、client側のドラフト時間も増える。GSM8K・Vicuna-68M/Vicuna-7B・RTX条件では、FSDのSD比改善は `γ` とともに増える傾向を示すが、vanilla SD自体は `γ>5` でARより遅くなる領域がある。

したがって「長いドラフトほど良い」わけではなく、受理率、ドラフト/対象 遅延比、ネットワーク 遅延、early-exit キャッシュ miss率を合わせて調整する必要がある。

## 既存研究との差

通常の投機的復号はドラフトと対象を同じserver側へ置くことが多い。Edge-cloud分割はAPI コストや端末privacy上の利点を持つ一方、ネットワーク round-tripと遅いedge computeがcritical pathへ入る。

FSDの差は、early exitを「推論を途中で打ち切る」用途ではなく、**対象の残り層とclientの次ドラフトを並行させるための先読みhint** として使う点にある。最終対象 検証を残すため、early exit accuracyは出力品質ではなくキャッシュ hit率と無駄計算量へ変換される。

## 限界・実装状況

第一に、FSDの上積みはearly-exit candidateが最終出力と一致し、かつpre-ドラフトがfinal result到着前に完了する場合に限られる。Client thread数が少ない、下書きモデルが遅い、exit数が多い場合は、先行計算を完了できない可能性がある。

第二に、vanilla edge-cloud 投機的復号そのものが常にcloud ARより速いわけではない。論文Table 6ではJetson上の二つのモデル pairで平均高速化倍率が1×未満になる。従って「edgeへドラフトを置けば必ず低遅延」という結論ではない。

第三に、論文は遅延 モデルと実測システム 指標を示すが、ネットワーク topology、API batching、real WAN jitter、複数client同時実行ではtrade-offが変わる。Server側バッチ サイズを増やすとスループット/コストは改善し得る一方、Table 9ではバッチ 32でA100 遅延が5倍超に増える例もあり、interactive 遅延とは別に考える必要がある。

公式コード repositoryはメタデータ確認時点で確認できず、実装は論文記述ベースである。

## 一般的な実装上の含意

分散投機的復号では、対象 順伝播回数だけでなく `draft latency + network latency + verification latency` の重なり方を見る必要がある。端末を遊ばせないために未来の仕事を投機する場合、そのpredictionが外れたコストを品質ではなく計算資源側へ閉じ込められる設計は扱いやすい。

また早期出口を最終出力へ直接使わなくても、**次段の仕事を前倒しするhint** として使える。これはLLM推論だけでなく、検証付きパイプラインで「最終確定前に安全に準備できる仕事」を見つける一般的なschedule patternでもある。
