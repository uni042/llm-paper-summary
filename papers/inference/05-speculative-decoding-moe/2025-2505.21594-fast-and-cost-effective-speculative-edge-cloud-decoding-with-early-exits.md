# Fast and Cost-effective Speculative Edge-Cloud Decoding with Early Exits

> Cloud targetの早期出口から暫定tokenを返し、edge draftを最終検証と並行して先行生成することで待ち時間を隠し、Jetson Nano＋A100でpre-drafting単体最大11%級の追加改善を示す。

## 概要

投機的復号（speculative decoding）は、小さい **draft model** が複数token候補を先に作り、大きい **target model** がそれらを一度に検証する。候補がよく当たれば、target modelを1 tokenずつ逐次実行するより少ないforward回数で生成を進められる。最終的なaccept/rejectはtarget modelが決めるため、draftは速度を上げる補助役である。

エッジ・クラウド構成では、小型draftを端末へ置けばcloud側でdraft modelを動かす費用を減らせる。しかし通常の流れは「端末でdraft → network送信 → cloudでtarget検証 → 結果受信 → 次draft」と直列で、cloudが検証している間の端末はほぼ待機する。特にJetson Nanoのような遅いclientではdraft時間とnetwork latencyが大きく、vanilla speculative decoding自体がcloud自己回帰より遅くなるmodel pairもある。

Fast Speculative Decoding（FSD）は、この待ちを **早期出口（early exit）** で埋める。Target modelの途中のlayerに軽量な出力headを付け、最終layerまで計算が終わる前に「最終結果になりそうなtoken」をclientへ順次返す。Clientはそれぞれの候補から次roundのdraftを先行生成してcacheする。最終出口が届いたとき、そのtokenと一致するearly-exit由来draftがあれば即座に次verificationへ進める。

Jetson NanoとA100、Vicuna-68M draft＋Llama2-7B targetの評価では、edge-cloud speculative decodingがcloud自己回帰に対して有利になる条件で最大35%のlatency削減を報告する。さらにFSDのpre-draftingはvanilla speculative decodingに対し、Jetson上の同model pairで平均1.11倍の追加speedupを示す。Unitree Go2上のvision-language model（VLM）制御ではcloud自己回帰比21%高速化を報告する。

## 問題設定

### 通常の投機的復号ではdraftとverificationが直列になる

1 roundでdraft modelが `γ` 個のtokenを生成し、その候補列をtarget modelへ送る。Targetは一度のforwardで候補を検証し、何token受理できるかを決める。その結果が返ってきてから、draft modelは次roundを始める。

同じGPU内ならdraft/target間の通信は軽いが、edgeとcloudへ分割するとclient-server通信 `T_c` が入る。さらにedge draftのforward時間 `T_p` がcloud targetの `T_q` に比べて大きいと、targetのforward回数を減らしてもdraft＋通信costが勝ち、自己回帰より遅くなる。

したがって重要なのはdraft modelを小さくすることだけではなく、**target verification中にclient側で有用な仕事を進められるか**である。

### 早期出口は最終答えとして使わず、先行計算のhintとして使う

Early exitはtarget modelの中間layer hidden stateからtokenを予測する。浅いlayerほど早く結果が出るが、最終layerのtokenと一致しない可能性が高い。

FSDはこの不確実なtokenをそのまま最終出力にしない。あくまで「次draftを先に計算するための分岐候補」として使い、最終target outputが届いた後に一致する分岐だけを採用する。したがってearly-exit誤りの主な影響は品質ではなく、無駄なclient計算とcache missとして現れる。

## 手法のあらまし

Serverのtarget modelには複数layer位置へearly-exit adapterを追加する。Verificationを開始すると、各exitが候補tokenとconfidenceを生成し、serverは有望なearly resultを順次clientへ送る。

Clientは受信した候補ごとにthreadを立て、その候補を「次tokenとして正しかった」と仮定して `γ` token分のdraftを先行生成する。生成済みdraftは候補tokenをkeyとしてcache/priority queueへ保存する。

最終target outputが届いたとき、対応するkeyのpre-draftがcacheにあればhitであり、draft latencyを待たず次roundへ進む。なければmissとしてvanilla speculative decodingと同じようにdraftを生成する。つまりFSDの速度は「early exitが最終結果と一致する確率」と「pre-draftが最終結果到着までに生成し終わるか」に依存する。

## 手法

### 1. Target modelへearly-exit adapterを付ける

Target backbone自体を置き換えず、選んだ中間layerへ小さなadapterとlanguage-model headを追加する。これらを学習し、途中hidden stateから次token分布を出せるようにする。

論文の代表構成ではVicuna-7BとLlama2-7Bに31個、Vicuna-13Bに39個のexitを持たせる。追加parameterは7B級で約101M、Llama2-7Bでは全体の約1.48%である。Backboneを凍結し、early-exit側を学習するため、target本体を再学習する方式ではない。

入力はverification中の中間hidden state、出力はearly token候補とconfidenceである。この出力は最終生成tokenではなく、clientのspeculative workを早く始めるtriggerになる。

### 2. Confidence付きearly resultをserverから順次送る

Serverは各early exitで候補tokenを得る。複数exitがほぼ同時に結果を出すため、すべてを無秩序にclientへ投げると通信とthread数が膨らむ。

FSDはearly resultへconfidenceを付け、priorityを付けてclientへ処理させる。最終layerに近いexitほど一般に精度は高いが到着が遅く、浅いexitは早いが外れやすい。この「早さと一致率」の交換条件が、どのcandidateから先にpre-draftするかへ直結する。

### 3. Client側で候補ごとのdraftを並列に先行生成する

Clientがearly tokenを受け取ると、そのtokenが正しいと仮定した次roundのdraftを小型modelで生成する。複数early exit候補について並列に走らせ、結果をcacheへ保持する。

ここで計算を投機する対象は **target modelの最終tokenではなく、その先のdraft sequence** である。これによりserverがtargetの残りlayerを実行している時間を、clientの次round準備へ変換する。

Client resourceには上限があり、Jetson NanoではCPU thread数と4GB memoryがbottleneckになる。論文Table 5ではVicuna-68Mで最大15 early-exit thread、Vicuna-160Mでは7 threadまでとしている。RTX clientではそれぞれ30、15 threadまで増やせる。

### 4. Final verification後にcache hitならdraft時間を消せる

最終target resultがclientへ届いたら、そのtokenをkeyとしてpre-draft cacheを引く。

- **Hit:** 一致するearly exitから作った次draftが既にあるため、すぐserverへ送れる。
- **Miss:** 正しいtokenに対応するdraftがないので、その時点から通常通りdraftする。

Target modelによるfinal verificationは省略しないため、early exitが外れた場合もそのprediction自体を最終出力へ採用しない。従ってFSDのbenefitはcache hit時のdraft latency隠蔽、costはmissした分岐に使った端末計算とthread/cache管理である。

## 評価

### 代表的な評価条件

| 項目 | 設定 |
|---|---|
| Server | NVIDIA A100 |
| Client | NVIDIA Jetson Nano / RTX 2080 Ti node |
| 主要draft-target | Vicuna-68M / Llama2-7B |
| 他model pair | Vicuna-68M / Vicuna-7B、Vicuna-160M / Vicuna-13B |
| Draft長 | 代表設定 `γ=4`、感度評価では最大10 |
| Benchmark | MT-Bench、HumanEval、GSM8K、Alpaca、CNN/DailyMail、Natural Questions |
| 比較 | cloud autoregressive（AR）、vanilla edge-cloud speculative decoding（SD）、FSD |
| 実機demo | Unitree Go2、VLM-based control |

### System latencyの中身

Table 5の `γ=4` では、Vicuna-68M/Llama2-7BについてJetson clientのdrafting latencyは301 ms、target verificationは522 ms、client-server communicationは96 msである。RTX clientではdrafting 99 ms、target 467 ms、communication 47 msとなる。

この差から、Jetsonではclient計算と通信を隠せる価値が大きい一方、そもそものvanilla SDがARに勝てないmodel pairも生じることが分かる。

### 代表的な評価結果

| 条件 | 比較 | 結果 | 読み取れること |
|---|---|---:|---|
| Vicuna-68M/Llama2-7B、Jetson平均 | AR → vanilla SD | 約1.34–1.35× | draft/communication costを受理token数で回収できる組合せ |
| 同、HumanEval | AR → vanilla SD | 1.53× | headlineの「最大35% latency削減」に相当する代表条件 |
| Vicuna-68M/Llama2-7B、Jetson平均 | SD → FSD | 1.11× | pre-drafting自体の追加効果 |
| Vicuna-68M/Vicuna-7B、Jetson平均 | AR → SD | 1×未満 | edge speculative decoding自体が常に有利ではない |
| Vicuna-160M/Vicuna-13B、Jetson平均 | AR → SD | 1×未満 | draftが重いと通信・client待ちが勝つ |
| Unitree Go2 VLM control | cloud AR → 提案系 | 21%高速化 | robotics demoでend-to-end効果を確認 |

FSDはvanilla SDに対しては全model pair・両clientで平均約1.04〜1.11×の改善を報告する。つまり「35%」の大部分はedge-cloud speculative decodingそのものの効果を含み、**early-exit pre-draftingだけの上積みは数%〜11%程度**と読むのが正確である。

### Draft長 `γ` のtrade-off

Draft token数を増やすと1回のtarget verificationで多く進める可能性がある一方、client側のdraft時間も増える。GSM8K・Vicuna-68M/Vicuna-7B・RTX条件では、FSDのSD比改善は `γ` とともに増える傾向を示すが、vanilla SD自体は `γ>5` でARより遅くなる領域がある。

したがって「長いdraftほど良い」わけではなく、受理率、draft/target latency比、network latency、early-exit cache miss率を合わせて調整する必要がある。

## 既存研究との差

通常のspeculative decodingはdraftとtargetを同じserver側へ置くことが多い。Edge-cloud分割はAPI costや端末privacy上の利点を持つ一方、network round-tripと遅いedge computeがcritical pathへ入る。

FSDの差は、early exitを「推論を途中で打ち切る」用途ではなく、**targetの残りlayerとclientの次draftを並行させるための先読みhint** として使う点にある。最終target verificationを残すため、early exit accuracyは出力品質ではなくcache hit率と無駄計算量へ変換される。

## 限界・実装状況

第一に、FSDの上積みはearly-exit candidateが最終outputと一致し、かつpre-draftがfinal result到着前に完了する場合に限られる。Client thread数が少ない、draft modelが遅い、exit数が多い場合は、先行計算を完了できない可能性がある。

第二に、vanilla edge-cloud speculative decodingそのものが常にcloud ARより速いわけではない。論文Table 6ではJetson上の二つのmodel pairで平均speedupが1×未満になる。従って「edgeへdraftを置けば必ず低latency」という結論ではない。

第三に、論文はlatency modelと実測system metricを示すが、network topology、API batching、real WAN jitter、複数client同時実行ではtrade-offが変わる。Server側batch sizeを増やすとthroughput/costは改善し得る一方、Table 9ではbatch 32でA100 latencyが5倍超に増える例もあり、interactive latencyとは別に考える必要がある。

公式code repositoryはメタデータ確認時点で確認できず、実装は論文記述ベースである。

## 一般的な実装上の含意

分散speculative decodingでは、target forward回数だけでなく `draft latency + network latency + verification latency` の重なり方を見る必要がある。端末を遊ばせないために未来の仕事を投機する場合、そのpredictionが外れたcostを品質ではなく計算資源側へ閉じ込められる設計は扱いやすい。

また早期出口を最終出力へ直接使わなくても、**次stageの仕事を前倒しするhint** として使える。これはLLM推論だけでなく、検証付きpipelineで「最終確定前に安全に準備できる仕事」を見つける一般的なschedule patternでもある。
