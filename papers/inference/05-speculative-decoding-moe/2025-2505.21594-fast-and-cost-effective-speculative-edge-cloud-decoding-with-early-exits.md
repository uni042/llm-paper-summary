# Fast and Cost-effective Speculative Edge-Cloud Decoding with Early Exits

> Cloud 対象の早期出口から暫定トークンを返し、エッジ ドラフトを最終検証と並行して先行生成することで待ち時間を隠し、Jetson Nano＋A100でpre-drafting単体最大11%級の追加改善を示す。

## 概要

投機的復号（投機的復号）は、小さい **下書きモデル** が複数トークン候補を先に作り、大きい **対象モデル** がそれらを一度に検証する。候補がよく当たれば、対象モデルを1 トークンずつ逐次実行するより少ない順伝播回数で生成を進められる。最終的なaccept/rejectは対象モデルが決めるため、ドラフトは速度を上げる補助役である。

エッジ・クラウド構成では、小型ドラフトを端末へ置けばクラウド側で下書きモデルを動かす費用を減らせる。しかし通常の流れは「端末でドラフト → ネットワーク送信 → クラウドで対象検証 → 結果受信 → 次ドラフト」と直列で、クラウドが検証している間の端末はほぼ待機する。特にJetson Nanoのような遅いクライアントではドラフト時間とネットワーク 遅延が大きく、基本方式 投機的復号自体がクラウド自己回帰より遅くなるモデル 組もある。

Fast Speculative Decoding（FSD）は、この待ちを **早期出口（早期 出口）** で埋める。Target モデルの途中の層に軽量な出力ヘッドを付け、最終層まで計算が終わる前に「最終結果になりそうなトークン」をクライアントへ順次返す。Clientはそれぞれの候補から次ラウンドのドラフトを先行生成してキャッシュする。最終出口が届いたとき、そのトークンと一致する早期出口由来ドラフトがあれば即座に次検証へ進める。

Jetson NanoとA100、Vicuna-68M ドラフト＋Llama2-7B 対象の評価では、エッジ-クラウド 投機的復号がクラウド自己回帰に対して有利になる条件で最大35%の遅延削減を報告する。さらにFSDのpre-draftingは基本方式 投機的復号に対し、Jetson上の同モデル 組で平均1.11倍の追加高速化倍率を示す。Unitree Go2上のvision-language モデル（VLM）制御ではクラウド自己回帰比21%高速化を報告する。

## 問題設定

### 通常の投機的復号ではdraftとverificationが直列になる

1 ラウンドで下書きモデルが `γ` 個のトークンを生成し、その候補列を対象モデルへ送る。Targetは一度の順伝播で候補を検証し、何トークン受理できるかを決める。その結果が返ってきてから、下書きモデルは次ラウンドを始める。

同じGPU内ならドラフト/対象間の通信は軽いが、エッジとクラウドへ分割するとクライアント-サーバー通信 `T_c` が入る。さらにエッジ ドラフトの順伝播時間 `T_p` がクラウド 対象の `T_q` に比べて大きいと、対象の順伝播回数を減らしてもドラフト＋通信コストが勝ち、自己回帰より遅くなる。

したがって重要なのは下書きモデルを小さくすることだけではなく、**対象 検証中にクライアント側で有用な仕事を進められるか**である。

### 早期出口は最終答えとして使わず、先行計算のhintとして使う

Early 出口は対象モデルの中間層 隠れ 状態からトークンを予測する。浅い層ほど早く結果が出るが、最終層のトークンと一致しない可能性が高い。

FSDはこの不確実なトークンをそのまま最終出力にしない。あくまで「次ドラフトを先に計算するための分岐候補」として使い、最終対象 出力が届いた後に一致する分岐だけを採用する。したがって早期出口誤りの主な影響は品質ではなく、無駄なクライアント計算とキャッシュ 不一致として現れる。

## 手法のあらまし

Serverの対象モデルには複数層位置へ早期出口 アダプタを追加する。Verificationを開始すると、各出口が候補トークンと信頼度を生成し、サーバーは有望な早期 結果を順次クライアントへ送る。

Clientは受信した候補ごとにスレッドを立て、その候補を「次トークンとして正しかった」と仮定して `γ` トークン分のドラフトを先行生成する。生成済みドラフトは候補トークンをkeyとしてキャッシュ/priority 待機列へ保存する。

最終対象 出力が届いたとき、対応するkeyのpre-ドラフトがキャッシュにあれば命中であり、ドラフト 遅延を待たず次ラウンドへ進む。なければ不一致として基本方式 投機的復号と同じようにドラフトを生成する。つまりFSDの速度は「早期 出口が最終結果と一致する確率」と「pre-ドラフトが最終結果到着までに生成し終わるか」に依存する。

## 手法

### 1. Target modelへearly-exit adapterを付ける

Target 基盤モデル自体を置き換えず、選んだ中間層へ小さなアダプタとlanguage-モデル ヘッドを追加する。これらを学習し、途中隠れ 状態から次トークン分布を出せるようにする。

論文の代表構成ではVicuna-7BとLlama2-7Bに31個、Vicuna-13Bに39個の出口を持たせる。追加パラメータは7B級で約101M、Llama2-7Bでは全体の約1.48%である。Backboneを凍結し、早期出口側を学習するため、対象本体を再学習する方式ではない。

入力は検証中の中間隠れ 状態、出力は早期 トークン候補と信頼度である。この出力は最終生成トークンではなく、クライアントの投機的 workを早く始める起動条件になる。

### 2. Confidence付きearly resultをserverから順次送る

Serverは各早期 出口で候補トークンを得る。複数出口がほぼ同時に結果を出すため、すべてを無秩序にクライアントへ投げると通信とスレッド数が膨らむ。

FSDは早期 結果へ信頼度を付け、priorityを付けてクライアントへ処理させる。最終層に近い出口ほど一般に精度は高いが到着が遅く、浅い出口は早いが外れやすい。この「早さと一致率」の交換条件が、どのcandidateから先にpre-ドラフトするかへ直結する。

### 3. Client側で候補ごとのdraftを並列に先行生成する

Clientが早期 トークンを受け取ると、そのトークンが正しいと仮定した次ラウンドのドラフトを小型モデルで生成する。複数早期 出口候補について並列に走らせ、結果をキャッシュへ保持する。

ここで計算を投機する対象は **対象モデルの最終トークンではなく、その先のドラフト 系列** である。これによりサーバーが対象の残り層を実行している時間を、クライアントの次ラウンド準備へ変換する。

Client 資源には上限があり、Jetson NanoではCPU スレッド数と4GB メモリがボトルネックになる。論文Table 5ではVicuna-68Mで最大15 早期出口 スレッド、Vicuna-160Mでは7 スレッドまでとしている。RTX クライアントではそれぞれ30、15 スレッドまで増やせる。

### 4. Final verification後にcache hitならdraft時間を消せる

最終対象 結果がクライアントへ届いたら、そのトークンをkeyとしてpre-ドラフト キャッシュを引く。

- **Hit:** 一致する早期 出口から作った次ドラフトが既にあるため、すぐサーバーへ送れる。
- **Miss:** 正しいトークンに対応するドラフトがないので、その時点から通常通りドラフトする。

Target モデルによるfinal 検証は省略しないため、早期 出口が外れた場合もその予測自体を最終出力へ採用しない。従ってFSDのbenefitはキャッシュ 命中時のドラフト 遅延隠蔽、コストは不一致した分岐に使った端末計算とスレッド/キャッシュ管理である。

## 評価

### 代表的な評価条件

| 項目 | 設定 |
|---|---|
| Server | NVIDIA A100 |
| Client | NVIDIA Jetson Nano / RTX 2080 Ti ノード |
| 主要ドラフト-対象 | Vicuna-68M / Llama2-7B |
| 他モデル 組 | Vicuna-68M / Vicuna-7B、Vicuna-160M / Vicuna-13B |
| Draft長 | 代表設定 `γ=4`、感度評価では最大10 |
| Benchmark | MT-Bench、HumanEval、GSM8K、Alpaca、CNN/DailyMail、Natural Questions |
| 比較 | クラウド autoregressive（AR）、基本方式 エッジ-クラウド 投機的復号（SD）、FSD |
| 実機demo | Unitree Go2、VLM-based 制御 |

### System latencyの中身

Table 5の `γ=4` では、Vicuna-68M/Llama2-7BについてJetson クライアントのdrafting 遅延は301 ms、対象 検証は522 ms、クライアント-サーバー 通信は96 msである。RTX クライアントではdrafting 99 ms、対象 467 ms、通信 47 msとなる。

この差から、Jetsonではクライアント計算と通信を隠せる価値が大きい一方、そもそもの基本方式 SDがARに勝てないモデル 組も生じることが分かる。

### 代表的な評価結果

| 条件 | 比較 | 結果 | 読み取れること |
|---|---|---:|---|
| Vicuna-68M/Llama2-7B、Jetson平均 | AR → 基本方式 SD | 約1.34–1.35× | ドラフト/通信 コストを受理トークン数で回収できる組合せ |
| 同、HumanEval | AR → 基本方式 SD | 1.53× | headlineの「最大35% 遅延削減」に相当する代表条件 |
| Vicuna-68M/Llama2-7B、Jetson平均 | SD → FSD | 1.11× | pre-drafting自体の追加効果 |
| Vicuna-68M/Vicuna-7B、Jetson平均 | AR → SD | 1×未満 | エッジ 投機的復号自体が常に有利ではない |
| Vicuna-160M/Vicuna-13B、Jetson平均 | AR → SD | 1×未満 | ドラフトが重いと通信・クライアント待ちが勝つ |
| Unitree Go2 VLM 制御 | クラウド AR → 提案系 | 21%高速化 | robotics demoでエンドツーエンド効果を確認 |

FSDは基本方式 SDに対しては全モデル 組・両クライアントで平均約1.04〜1.11×の改善を報告する。つまり「35%」の大部分はエッジ-クラウド 投機的復号そのものの効果を含み、**早期出口 pre-draftingだけの上積みは数%〜11%程度**と読むのが正確である。

### Draft長 `γ` のtrade-off

Draft トークン数を増やすと1回の対象 検証で多く進める可能性がある一方、クライアント側のドラフト時間も増える。GSM8K・Vicuna-68M/Vicuna-7B・RTX条件では、FSDのSD比改善は `γ` とともに増える傾向を示すが、基本方式 SD自体は `γ>5` でARより遅くなる領域がある。

したがって「長いドラフトほど良い」わけではなく、受理率、ドラフト/対象 遅延比、ネットワーク 遅延、早期出口 キャッシュ 不一致率を合わせて調整する必要がある。

## 既存研究との差

通常の投機的復号はドラフトと対象を同じサーバー側へ置くことが多い。Edge-クラウド分割はAPI コストや端末privacy上の利点を持つ一方、ネットワーク ラウンド-tripと遅いエッジ 計算がcritical pathへ入る。

FSDの差は、早期 出口を「推論を途中で打ち切る」用途ではなく、**対象の残り層とクライアントの次ドラフトを並行させるための先読みhint** として使う点にある。最終対象 検証を残すため、早期 出口 accuracyは出力品質ではなくキャッシュ 命中率と無駄計算量へ変換される。

## 限界・実装状況

第一に、FSDの上積みは早期出口 candidateが最終出力と一致し、かつpre-ドラフトがfinal 結果到着前に完了する場合に限られる。Client スレッド数が少ない、下書きモデルが遅い、出口数が多い場合は、先行計算を完了できない可能性がある。

第二に、基本方式 エッジ-クラウド 投機的復号そのものが常にクラウド ARより速いわけではない。論文Table 6ではJetson上の二つのモデル 組で平均高速化倍率が1×未満になる。従って「エッジへドラフトを置けば必ず低遅延」という結論ではない。

第三に、論文は遅延 モデルと実測システム 指標を示すが、ネットワーク トポロジー、API batching、実 WAN jitter、複数クライアント同時実行ではtrade-offが変わる。Server側バッチ サイズを増やすとスループット/コストは改善し得る一方、Table 9ではバッチ 32でA100 遅延が5倍超に増える例もあり、interactive 遅延とは別に考える必要がある。

公式コード repositoryはメタデータ確認時点で確認できず、実装は論文記述ベースである。

## 一般的な実装上の含意

分散投機的復号では、対象 順伝播回数だけでなく `draft latency + network latency + verification latency` の重なり方を見る必要がある。端末を遊ばせないために未来の仕事を投機する場合、その予測が外れたコストを品質ではなく計算資源側へ閉じ込められる設計は扱いやすい。

また早期出口を最終出力へ直接使わなくても、**次段の仕事を前倒しするhint** として使える。これはLLM推論だけでなく、検証付きパイプラインで「最終確定前に安全に準備できる仕事」を見つける一般的なschedule patternでもある。
