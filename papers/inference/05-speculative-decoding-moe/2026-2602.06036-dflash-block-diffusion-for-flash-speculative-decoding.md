# DFlash: Block Diffusion for Flash Speculative Decoding

> 対象 隠れ featuresで条件付けしたblock-diffusion drafterが候補列を1回で並列生成し、投機ドラフト自身の逐次待ちを除くDFlash。

## 概要

投機的復号（投機的復号）は、軽量な下書きモデルに未来の候補トークンを作らせ、大きな対象 LLMがそれらをまとめて検証する。対象が候補を受理できる限り、1回の大モデル順伝播で複数トークン分先へ進めるため、通常の1-トークン-at-a-time デコードより速くできる。最終採否は対象モデルが行うので、正しい検証を使えば出力分布は対象単独生成と一致する。

ただしEAGLE系を含む多くの高性能ドラフトは、**候補を作る部分自身が自己回帰的**である。例えば16個の候補を作るなら、小さいドラフトとはいえ16 stepを順番に実行する。このドラフト時間は候補数にほぼ比例し、対象 検証を並列化しても消えない。高い受理長を狙って候補を増やすほどドラフト 遅延も増えるため、実測高速化倍率が2〜3倍付近で頭打ちになる原因の一つになる。

Diffusion Language Model（拡散型言語モデル; dLLM）は、複数のmasked トークン位置を同時に予測できる点で自己回帰モデルと異なる。しかし最終回答をdLLMだけで生成すると、現在のopen モデルではAR LLMより品質が低いことが多く、品質を上げるために何stepもdenoisingすると並列性の利点も薄れる。

DFlashの着眼点は、dLLMを**最終回答モデルにしない**ことである。軽量なblock diffusion モデルに候補blockを1 順伝播で並列生成させ、品質保証は強いAR 対象 LLMの投機的 検証へ任せる。ドラフトは完全な文章品質を持つ必要がなく、「対象が受理できる候補を安く作る」ことだけに特化できるため、denoising stepを極端に少なくしてdiffusionの並列性を活かせる。

さらに小さいdiffusion drafter単体では対象と予測がずれて受理率が低いため、対象 LLMの複数層から抽出したcontext 隠れ featuresをドラフト 注意機構のKVへ注入する。これによりドラフト コストを低く保ったまま受理率 lengthを伸ばす。Qwen3-8Bのgreedy評価では7タスク平均4.86倍、最大6.08倍の実時間高速化を得て、同条件のEAGLE-3より大幅に高い高速化倍率を示す。

## 問題設定

### 投機的復号の速度は「受理長」だけでは決まらない

1回の投機周期でドラフトにかかる時間を (T_{ドラフト})、対象 検証を (T_{verify})、平均受理トークン数を (	au) とすると、1受理トークン当たりの時間は概念的に

[
rac{T_{ドラフト}+T_{verify}}{	au}
]

で決まる。

AR drafterが (gamma) トークンを生成する場合、ドラフト時間はおおむね (gamma) 回の逐次stepへ比例する。大きな下書きモデルを使えば対象との一致が増えて (	au) は伸びるが、1step自体が重くなる。小さいドラフトなら速いが予測品質が落ち、対象が早い位置でrejectする。この「ドラフト速度と受理率」の交換条件が投機的復号の中心課題になる。

Block diffusionなら、(gamma) 個のmasked位置を1回の順伝播で同時に予測できるため、候補数を増やしてもAR ドラフトのように (gamma) 回の逐次依存を払わない。DFlashはここを高速化対象にする。

### なぜ普通のdiffusion drafterだけでは足りないのか

並列に候補を出せても、対象と候補分布がずれて最初の数トークンでrejectされれば (	au) が短く、検証の仕事を回収できない。論文では対象 featureを使わない小型diffusion ドラフトでは高速化倍率がおおむね2〜3倍に留まる。

そこでDFlashは対象 LLMが既に計算したcontext representationをドラフトへ渡す。これは対象そのものをもう一度実行するのではなく、直前の検証で得られる隠れ featuresをドラフトの条件として再利用する設計である。

## 手法

### 1. Block Diffusion Drafting — block全体を1 forwardで予測する

各投機周期は、前回対象 検証が確定したclean トークンをanchorとして始まる。その後ろに複数のmasked トークン位置を置き、軽量ドラフト Transformerがblock内を双方向に見ながら、それらのトークンを同時に予測する。

通常のAR ドラフトが

[
x_1 
ightarrow x_2 
ightarrow cdots 
ightarrow x_gamma
]

と逐次進むのに対し、DFlashは (x_1,ldots,x_gamma) を同じ順伝播で提案する。このためドラフト側のcritical pathをトークン数から切り離しやすい。

生成されたblockは対象 LLMへ渡され、標準的な投機的 検証で先頭から受理可能なトークン列だけ確定する。不一致が出た位置以降は捨てるため、diffusion ドラフトの誤りが最終出力品質へ直接残らない。

### 2. Target Feature KV Injection — 強いtarget文脈を軽量draftへ注入する

小型ドラフトが長いcontextを自力で再表現すると、対象との能力差が大きくなる。DFlashは対象 LLMの複数層からcontext 隠れ featuresを抽出し、ドラフトの各注意機構層へKey/Valueとして注入する。

重要なのは、対象 featureを単にドラフト入力へ足し合わせるのではなく、注意機構が参照できる**追加KV context**として与える点である。ドラフト トークンはblock内の他トークンに加え、対象が作った高品質なcontext representationへ直接注意機構できる。

ablationでは、より多くの対象 隠れ 層を与えるほど受理率 lengthは改善する一方、事前に保持する隠れ-feature ストレージはほぼ線形に増える。そのため対象 feature数にも品質とメモリの交換条件がある。

### 3. Draft層数は深ければ深いほど速いわけではない

ドラフト Transformerを深くすると候補品質が上がり、対象に受理される長さ (	au) は伸びる。しかし1回の並列 ドラフト 順伝播自体が重くなる。

Qwen3-8B系のablationでは3-層から8-層へ増やすにつれて受理長は伸びるが、全体高速化倍率は5-層付近が最良になる。例えばMath500では3-層 4.69倍/(	au=5.64)、5-層 4.71倍/(	au=5.99)、8-層 4.64倍/(	au=6.33)だった。受理長最大と実時間最速が一致しない例である。

### 4. Speculative用途に合わせてtraining blockを作る

一般的なblock diffusion 学習は系列を固定blockへ分け、その中の位置をrandom maskして復元させる。DFlashでは実推論時、各ドラフト blockの先頭には必ず対象 検証で確定したclean トークンが存在する。

この条件に合わせるため、学習時にはresponse中からanchor トークンをランダムに選び、その位置をblock先頭のclean トークンとして残し、後続位置をmaskする。anchorをepochごとに変えることで、同じ系列から異なる対象 contextを効率よく学習する。

複数masked blocksは1系列へ連結し、block間注意機構を禁止するsparse maskを使ってFlex Attentionでまとめて順伝播/逆伝播する。Long-context 学習でもmask block数を固定するため、全文脈を全位置でドラフト訓練するより計算量を抑えられる。

### 5. block先頭ほど重くするloss weighting

Speculative 検証は左から順に行われ、早いトークンがrejectされると、その後ろの候補が正しくても採用されない。したがってblock内の1番目の予測誤りは、最後の予測誤りより高速化倍率へ大きな損害を与える。

DFlashは位置kのlossへ指数減衰重み

[
w_k=exp(-(k-1)/gamma)
]

を掛け、block前半のトークンを重点学習する。通常のlanguage modeling accuracyを均等に最大化するのではなく、**受理率 lengthを伸ばすための誤り位置の非対称性**を学習 目的関数へ入れている。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| 対象 models | Qwen3-4B / 8B、Qwen3-Coder-30B-A3B、Llama-3.1-8B等 |
| 主GPU | 単体NVIDIA H200 |
| 推論提供評価 | SGLang、単体NVIDIA B200 |
| math | GSM8K、MATH-500、AIME25 |
| コード | HumanEval、MBPP、LiveCodeBench |
| chat | MT-Bench、Alpaca |
| 比較 | EAGLE-3、通常AR 比較対象 |
| Qwen3主設定 | DFlash block サイズ 16 |
| 指標 | wall-clock 高速化倍率、受理率 length (	au)、推論提供 TPS |

### 単一要求のspeedup

| 条件 | EAGLE-3 | DFlash | 読み取り |
|---|---:|---:|---|
| Qwen3-8B greedy・7タスク平均 | 2.02倍（tree 60） | 4.86倍 | 並列 draftingでドラフト critical pathを短縮 |
| Qwen3-8B MATH-500 | 2.05倍 | 6.08倍 | (	au) 3.49→7.87 |
| Qwen3-8B HumanEval | 2.17倍 | 5.14倍 | コードでも同じ傾向 |
| Qwen3-8B temperature=1平均 | 1.88倍 | 4.03倍 | samplingでも優位性を維持 |
| Qwen3-4B greedy平均 | 2.08倍 | 4.91倍 | モデル サイズを跨いで改善 |

Qwen3-8Bのgreedy設定ではDFlashの平均受理率 lengthは6.49、EAGLE-3 tree-60は3.40である。DFlashはドラフトを並列化しただけでなく、対象 feature conditioningによって受理長自体も伸ばしている。

### Serving frameworkでの同時要求

実サービスでは同時要求が増えると対象 検証が大きなバッチになり、対象側の計算効率が上がるため、投機的復号の相対利得は単一要求より縮みやすい。

SGLang/B200のLlama-3.1-8B評価でもDFlashはconcurrency 1〜32の全範囲でEAGLE-3を上回るが、高速化倍率は低並列時ほど大きい。GSM8KではDFlashが2.4倍→1.6倍、HumanEvalでは2.8倍→1.8倍と縮む。この結果は、DFlashのボトルネックが並列ドラフトから対象 検証側へ移ることを示す。

別のQwen3系SGLang評価ではQwen3-8Bで最大5.1倍を報告しており、フレームワーク統合後も並列 draftingの利得が残る。

### Long-context adaptation

4K文脈で学習したbase drafterは、contextが8K/16Kへ伸びると受理率 lengthが低下する。DFlashはLongAlign-10Kから1.6K samplesだけを3 epoch追加学習し、長文脈へ適応できることを示す。

16Kではhotpotqaが3.61→6.05、qasperが3.57→6.00、gov_reportが2.67→3.81へ改善する。32K gov_reportでも2.09→3.56となる。対象 featureを注入するだけで無条件に長文脈へ一般化するわけではなく、ドラフト側にも軽量なcontext adaptationが必要である。

## 既存研究との差

EAGLE-3などの下書きモデルは対象 隠れ representationsを利用して高い候補品質を得るが、候補トークン自体は自己回帰的に生成する。tree draftingで複数分岐を持っても、ドラフト step間には逐次依存が残る。

DFlashは対象 featureを利用するという「強いドラフト」の考え方を維持しつつ、ドラフト generatorをblock diffusionへ変える。diffusion LLMを対象 LLMと競合する最終generatorとして使うのではなく、**多少粗くても対象 検証で訂正可能な候補を高速に並列生成する専用部品**として位置付けた点が主な差になる。

## 限界

並列 ドラフトにしても、最終的な対象 検証は必要である。同時実行数が増えて対象 検証が計算律速になると、ドラフト時間を減らして得られる割合は小さくなり、推論提供 高速化倍率は低下する。

ドラフト層数、block サイズ、対象 隠れ feature数にも明確な交換条件がある。大きいblockや深いドラフトは受理率 lengthを伸ばせるがドラフト 遅延とメモリを増やす。論文のablationでも8-層は5-層より長い受理長を得ながら高速化倍率では劣る。

また4Kで訓練したドラフトは長文脈で劣化し、追加微調整が必要だった。対象モデル family、context length、sampling条件が大きく変わる場合も、公開チェックポイントの受理率をそのまま期待できない。
