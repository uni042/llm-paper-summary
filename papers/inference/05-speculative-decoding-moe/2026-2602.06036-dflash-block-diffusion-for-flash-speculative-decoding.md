# DFlash: Block Diffusion for Flash Speculative Decoding

> target hidden featuresで条件付けしたblock-diffusion drafterが候補列を1回で並列生成し、投機draft自身の逐次待ちを除くDFlash。

## 概要

投機的復号（speculative decoding）は、軽量なdraft modelに未来の候補トークンを作らせ、大きなtarget LLMがそれらをまとめて検証する。targetが候補を受理できる限り、1回の大モデルforwardで複数トークン分先へ進めるため、通常の1-token-at-a-time decodeより速くできる。最終採否はtarget modelが行うので、正しいverificationを使えば出力分布はtarget単独生成と一致する。

ただしEAGLE系を含む多くの高性能draftは、**候補を作る部分自身が自己回帰的**である。例えば16個の候補を作るなら、小さいdraftとはいえ16 stepを順番に実行する。このdraft時間は候補数にほぼ比例し、target verificationを並列化しても消えない。高い受理長を狙って候補を増やすほどdraft latencyも増えるため、実測speedupが2〜3倍付近で頭打ちになる原因の一つになる。

Diffusion Language Model（拡散型言語モデル; dLLM）は、複数のmasked token位置を同時に予測できる点で自己回帰モデルと異なる。しかし最終回答をdLLMだけで生成すると、現在のopen modelではAR LLMより品質が低いことが多く、品質を上げるために何stepもdenoisingすると並列性の利点も薄れる。

DFlashの着眼点は、dLLMを**最終回答モデルにしない**ことである。軽量なblock diffusion modelに候補blockを1 forwardで並列生成させ、品質保証は強いAR target LLMのspeculative verificationへ任せる。draftは完全な文章品質を持つ必要がなく、「targetが受理できる候補を安く作る」ことだけに特化できるため、denoising stepを極端に少なくしてdiffusionの並列性を活かせる。

さらに小さいdiffusion drafter単体ではtargetと予測がずれて受理率が低いため、target LLMの複数層から抽出したcontext hidden featuresをdraft attentionのKVへ注入する。これによりdraft costを低く保ったままacceptance lengthを伸ばす。Qwen3-8Bのgreedy評価では7タスク平均4.86倍、最大6.08倍の実時間高速化を得て、同条件のEAGLE-3より大幅に高いspeedupを示す。

## 問題設定

### 投機的復号の速度は「受理長」だけでは決まらない

1回の投機周期でdraftにかかる時間を (T_{draft})、target verificationを (T_{verify})、平均受理トークン数を (	au) とすると、1受理token当たりの時間は概念的に

[
rac{T_{draft}+T_{verify}}{	au}
]

で決まる。

AR drafterが (gamma) tokenを生成する場合、draft時間はおおむね (gamma) 回の逐次stepへ比例する。大きなdraft modelを使えばtargetとの一致が増えて (	au) は伸びるが、1step自体が重くなる。小さいdraftなら速いが予測品質が落ち、targetが早い位置でrejectする。この「draft速度と受理率」の交換条件が投機的復号の中心課題になる。

Block diffusionなら、(gamma) 個のmasked位置を1回のforwardで同時に予測できるため、候補数を増やしてもAR draftのように (gamma) 回の逐次依存を払わない。DFlashはここを高速化対象にする。

### なぜ普通のdiffusion drafterだけでは足りないのか

並列に候補を出せても、targetと候補分布がずれて最初の数tokenでrejectされれば (	au) が短く、verificationの仕事を回収できない。論文ではtarget featureを使わない小型diffusion draftではspeedupがおおむね2〜3倍に留まる。

そこでDFlashはtarget LLMが既に計算したcontext representationをdraftへ渡す。これはtargetそのものをもう一度実行するのではなく、直前のverificationで得られるhidden featuresをdraftの条件として再利用する設計である。

## 手法

### 1. Block Diffusion Drafting — block全体を1 forwardで予測する

各投機周期は、前回target verificationが確定したclean tokenをanchorとして始まる。その後ろに複数のmasked token位置を置き、軽量draft Transformerがblock内を双方向に見ながら、それらのtokenを同時に予測する。

通常のAR draftが

[
x_1 
ightarrow x_2 
ightarrow cdots 
ightarrow x_gamma
]

と逐次進むのに対し、DFlashは (x_1,ldots,x_gamma) を同じforwardで提案する。このためdraft側のcritical pathをtoken数から切り離しやすい。

生成されたblockはtarget LLMへ渡され、標準的なspeculative verificationで先頭から受理可能なtoken列だけ確定する。不一致が出た位置以降は捨てるため、diffusion draftの誤りが最終出力品質へ直接残らない。

### 2. Target Feature KV Injection — 強いtarget文脈を軽量draftへ注入する

小型draftが長いcontextを自力で再表現すると、targetとの能力差が大きくなる。DFlashはtarget LLMの複数層からcontext hidden featuresを抽出し、draftの各attention層へKey/Valueとして注入する。

重要なのは、target featureを単にdraft入力へ足し合わせるのではなく、attentionが参照できる**追加KV context**として与える点である。draft tokenはblock内の他tokenに加え、targetが作った高品質なcontext representationへ直接attentionできる。

ablationでは、より多くのtarget hidden layersを与えるほどacceptance lengthは改善する一方、事前に保持するhidden-feature storageはほぼ線形に増える。そのためtarget feature数にも品質とメモリの交換条件がある。

### 3. Draft層数は深ければ深いほど速いわけではない

draft Transformerを深くすると候補品質が上がり、targetに受理される長さ (	au) は伸びる。しかし1回のparallel draft forward自体が重くなる。

Qwen3-8B系のablationでは3-layerから8-layerへ増やすにつれて受理長は伸びるが、全体speedupは5-layer付近が最良になる。例えばMath500では3-layer 4.69倍/(	au=5.64)、5-layer 4.71倍/(	au=5.99)、8-layer 4.64倍/(	au=6.33)だった。受理長最大と実時間最速が一致しない例である。

### 4. Speculative用途に合わせてtraining blockを作る

一般的なblock diffusion trainingは系列を固定blockへ分け、その中の位置をrandom maskして復元させる。DFlashでは実推論時、各draft blockの先頭には必ずtarget verificationで確定したclean tokenが存在する。

この条件に合わせるため、学習時にはresponse中からanchor tokenをランダムに選び、その位置をblock先頭のclean tokenとして残し、後続位置をmaskする。anchorをepochごとに変えることで、同じ系列から異なるtarget contextを効率よく学習する。

複数masked blocksは1系列へ連結し、block間attentionを禁止するsparse maskを使ってFlex Attentionでまとめてforward/backwardする。Long-context trainingでもmask block数を固定するため、全文脈を全位置でdraft訓練するより計算量を抑えられる。

### 5. block先頭ほど重くするloss weighting

Speculative verificationは左から順に行われ、早いtokenがrejectされると、その後ろの候補が正しくても採用されない。したがってblock内の1番目の予測誤りは、最後の予測誤りよりspeedupへ大きな損害を与える。

DFlashは位置kのlossへ指数減衰重み

[
w_k=exp(-(k-1)/gamma)
]

を掛け、block前半のtokenを重点学習する。通常のlanguage modeling accuracyを均等に最大化するのではなく、**acceptance lengthを伸ばすための誤り位置の非対称性**をtraining objectiveへ入れている。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| target models | Qwen3-4B / 8B、Qwen3-Coder-30B-A3B、Llama-3.1-8B等 |
| 主GPU | 単体NVIDIA H200 |
| serving評価 | SGLang、単体NVIDIA B200 |
| math | GSM8K、MATH-500、AIME25 |
| code | HumanEval、MBPP、LiveCodeBench |
| chat | MT-Bench、Alpaca |
| 比較 | EAGLE-3、通常AR baseline |
| Qwen3主設定 | DFlash block size 16 |
| 指標 | wall-clock speedup、acceptance length (	au)、serving TPS |

### 単一要求のspeedup

| 条件 | EAGLE-3 | DFlash | 読み取り |
|---|---:|---:|---|
| Qwen3-8B greedy・7タスク平均 | 2.02倍（tree 60） | 4.86倍 | parallel draftingでdraft critical pathを短縮 |
| Qwen3-8B MATH-500 | 2.05倍 | 6.08倍 | (	au) 3.49→7.87 |
| Qwen3-8B HumanEval | 2.17倍 | 5.14倍 | codeでも同じ傾向 |
| Qwen3-8B temperature=1平均 | 1.88倍 | 4.03倍 | samplingでも優位性を維持 |
| Qwen3-4B greedy平均 | 2.08倍 | 4.91倍 | model sizeを跨いで改善 |

Qwen3-8Bのgreedy設定ではDFlashの平均acceptance lengthは6.49、EAGLE-3 tree-60は3.40である。DFlashはdraftを並列化しただけでなく、target feature conditioningによって受理長自体も伸ばしている。

### Serving frameworkでの同時要求

実サービスでは同時要求が増えるとtarget verificationが大きなbatchになり、target側の計算効率が上がるため、speculative decodingの相対利得は単一要求より縮みやすい。

SGLang/B200のLlama-3.1-8B評価でもDFlashはconcurrency 1〜32の全範囲でEAGLE-3を上回るが、speedupは低並列時ほど大きい。GSM8KではDFlashが2.4倍→1.6倍、HumanEvalでは2.8倍→1.8倍と縮む。この結果は、DFlashのボトルネックが並列draftからtarget verification側へ移ることを示す。

別のQwen3系SGLang評価ではQwen3-8Bで最大5.1倍を報告しており、framework統合後もparallel draftingの利得が残る。

### Long-context adaptation

4K文脈で学習したbase drafterは、contextが8K/16Kへ伸びるとacceptance lengthが低下する。DFlashはLongAlign-10Kから1.6K samplesだけを3 epoch追加学習し、長文脈へ適応できることを示す。

16Kではhotpotqaが3.61→6.05、qasperが3.57→6.00、gov_reportが2.67→3.81へ改善する。32K gov_reportでも2.09→3.56となる。target featureを注入するだけで無条件に長文脈へ一般化するわけではなく、draft側にも軽量なcontext adaptationが必要である。

## 既存研究との差

EAGLE-3などのdraft modelはtarget hidden representationsを利用して高い候補品質を得るが、候補token自体は自己回帰的に生成する。tree draftingで複数分岐を持っても、draft step間には逐次依存が残る。

DFlashはtarget featureを利用するという「強いdraft」の考え方を維持しつつ、draft generatorをblock diffusionへ変える。diffusion LLMをtarget LLMと競合する最終generatorとして使うのではなく、**多少粗くてもtarget verificationで訂正可能な候補を高速に並列生成する専用部品**として位置付けた点が主な差になる。

## 限界

parallel draftにしても、最終的なtarget verificationは必要である。同時実行数が増えてtarget verificationが計算律速になると、draft時間を減らして得られる割合は小さくなり、serving speedupは低下する。

draft層数、block size、target hidden feature数にも明確な交換条件がある。大きいblockや深いdraftはacceptance lengthを伸ばせるがdraft latencyとメモリを増やす。論文のablationでも8-layerは5-layerより長い受理長を得ながらspeedupでは劣る。

また4Kで訓練したdraftは長文脈で劣化し、追加fine-tuningが必要だった。target model family、context length、sampling条件が大きく変わる場合も、公開checkpointの受理率をそのまま期待できない。
