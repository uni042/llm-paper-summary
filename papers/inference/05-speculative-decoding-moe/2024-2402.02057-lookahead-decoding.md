# Break the Sequential Dependency of LLM Inference Using Lookahead Decoding

> Lookahead Decodingは、別のdraft modelに未来を予測させるのではなく、**target LLM自身を複数の未来位置へ並列に走らせ、その途中で偶然できた正しそうなn-gramを再利用する**方式である。計算量は大きく増やすが、batch=1 decodeで余りがちなGPU演算能力を使って逐次step数を減らし、追加model・training・外部corpusなしで元LLMの出力分布を保つ。

## 概要

LLMの自己回帰復号（autoregressive decoding）では、token `t+1` が確定するまで `t+2` を正しく計算できない。

そのため通常は、

`1 token生成 → 次の1 token生成 → 次の1 token生成 → ...`

と巨大modelを逐次forwardする。

batch size 1では1 forwardで使う演算量が小さい一方、model weightは毎回HBMから読む必要がある。このためdecodeはしばしば**演算量不足ではなくmemory bandwidth不足**になる。

一般的な投機的復号（speculative decoding）は、小さいdraft modelが未来tokenを先に作り、target modelがまとめて検証することでtarget forward回数を減らす。

しかし、

- target modelごとに相性のよいdraft modelが必要
- draft modelのweightとKV cacheが必要
- draftのtrainingや配布が必要な場合がある
- target architectureやtokenizerが変わるとdraftを再準備する必要がある

という運用負担がある。

Lookahead Decodingは、**draft modelそのものを無くす**。

代わりにtarget LLM自身を使って未来positionを並列更新するヤコビ復号（Jacobi decoding）を走らせる。Jacobi iterationは最終的なsequenceへすぐ収束しなくても、その途中の軌跡に「後で本当に現れる短いtoken列」が頻繁に出現する。

Lookahead Decodingはこの短い列をn-gramとしてcacheし、現在の確定prefixに接続できる候補をtarget LLMで一括検証する。

つまり、

**「未来を正確に一発で当てる」のではなく、「大量の並列試行から再利用可能な局所n-gramを拾う」**

のが発想の中心である。

## 背景: Jacobi decodingとは何か

### 通常のautoregressive decoding

4 token先まで生成したい場合、通常は、

1. `y1`を計算
2. `y1`を使って`y2`を計算
3. `y1,y2`を使って`y3`を計算
4. `y1,y2,y3`を使って`y4`を計算

と4回順番にforwardする。

### Jacobi decodingは未来位置を仮置きして一斉更新する

Jacobi decodingでは未来の複数positionにまず仮tokenを置く。

例えば、

`[現在prefix] [A] [B] [C] [D]`

のように未来4 positionを適当に初期化し、その全positionをtarget LLMで**同時に**更新する。

1 iteration後に、

`[E] [F] [G] [H]`

次のiterationで、

`[I] [J] [K] [L]`

というように更新する。

十分反復すると通常autoregressive decodingの固定点へ収束し得る。

ただし、最終sequence全体が収束するまで待つと、普通に1 tokenずつ生成するより大量の計算が必要になる場合がある。

Lookahead Decodingは**完全収束を待たない**。

Jacobi trajectoryの途中に現れる局所的に正しいn-gramだけを回収する。

## 手法のあらまし

Lookahead Decodingは各decode stepで2つのbranchを同時に動かす。

### Lookahead branch

未来`W` positionを並列にJacobi更新し、直近`N-1`回のiteration historyと現在iterationを縦方向につないで長さ`N`のn-gramを作る。

得られたn-gramを**n-gram pool**へ保存する。

### Verification branch

現在の確定sequence末尾と接続できそうなn-gramをpoolから最大`G`個選ぶ。

それらをtarget LLMで並列検証し、targetの出力と一致した連続prefixを一度に確定する。

### 同じforwardへまとめる

lookahead用tokenとverification用tokenは専用attention maskで同じmodel forwardへまとめられる。

したがって1 stepで、

- 今回の正規tokenを確定する
- 未来n-gramを新しく探索する
- 過去に見つけたn-gramを検証する

を並列に進める。

## 手法

### 1. 2次元lookahead windowを持つ

Lookahead branchは、

- 横方向: 未来token position
- 縦方向: 過去のJacobi iteration

からなる固定サイズの2次元windowを持つ。

主なparameterは、

- `W`: 何token先まで同時に探索するか
- `N`: 何iteration分をつないでn-gramを作るか

である。

例えば`W=5, N=4`なら、5つの未来positionを毎step更新し、直近4世代のtrajectoryを斜めに読むことで複数の4-gram候補を作る。

### 2. trajectoryを斜めに読むとn-gram候補になる

ここが最も直感的でない部分である。

Jacobi iterationでは、未来position `p` の新tokenは、その前方positionの過去iteration結果を文脈として計算される。

そのため、

- 古いiterationのposition 1
- 次iterationのposition 2
- さらに次iterationのposition 3
- 現iterationのposition 4

をつなぐと、**時間方向に伝播してきた局所continuation**になる。

sequence全体はまだ収束していなくても、この短い斜めn-gramだけは正しいcontinuationになっていることがある。

Lookahead Decodingはこれを大量に回収する。

### 3. n-gram poolへ候補を蓄積する

lookahead branchで得たn-gramはそのstepで使えなくても捨てない。

n-gram poolへcacheし、後の生成位置で使える可能性を残す。

例えばコード生成では、

- `for i in range`
- `return self.`
- `if __name__ ==`

のような局所patternが繰り返し出現しやすい。

一度lookahead trajectoryに現れたn-gramが、数step後に本当に必要なcontinuationとして再登場すれば、その時にverificationへ使える。

この性質がcode completionで特に高いspeedupが出る理由の一つである。

### 4. 現在末尾と接続できる候補だけをverificationへ送る

pool内の全n-gramを毎回検証するとcostが爆発する。

そこでverification branchは、n-gramの先頭tokenが現在生成sequenceの末尾と一致するものなど、**現在prefixへ接続できる有望候補**だけを選ぶ。

さらに最大候補数を`G`で制限する。

論文では実用上`G=W`を推奨しており、lookahead側のcandidate生成量とverification costを釣り合わせる。

### 5. target LLM自身でcandidateを検証する

候補n-gramはあくまでJacobi trajectoryから拾った投機候補なので、そのまま出力しない。

target LLMを使い、n-gramの先頭から順に、

`targetがこの位置で出すtoken == candidate token`

かを確認する。

greedy decodingなら一致する最長prefixを受理する。

複数tokenが連続一致すれば、target autoregressive stepを複数回省略できる。

### 6. samplingでもoutput distributionを保てる

samplingでは単純なtoken一致だけではtarget distributionを保存できない。

Lookahead Decodingはdisjointな複数n-gramを順方向に検証し、prefixが不一致になった候補を落とすsampling verificationを定義している。

重要な工夫は、lookahead branch側では候補を**greedyに生成**しておくことである。

通常のspeculative samplingではreject補正のためdraft distributionを保存する必要があるが、n-gram poolの全candidateについて巨大なvocabulary distributionをcacheするとmemoryが大きすぎる。

lookahead candidateをgreedy生成すればdraft distributionはone-hotになるため、poolにはtoken IDだけ保存すればよい。

論文はこのverificationがtargetのsampling distributionを保つことを証明している。

したがってLookahead Decodingは単なる「greedy近似高速化」ではなく、**exact / distribution-preserving decoding**として設計されている。

### 7. Lookahead branchとVerification branchを1 forwardへ統合する

2つのbranchを別々にtarget modelへ通すとweight read回数が増えて利点が薄れる。

そこで専用attention maskを使い、同一forward内に、

- lookahead window更新用token
- verification candidate token

をまとめて配置する。

各tokenが見るべきprefixだけを見せ、候補同士の不正な情報漏れを防ぐ。

この設計により、target weightを1回読んで大量の独立token computationをまとめて実行できる。

### 8. 余分なFLOPsを逐次step削減と交換する

Lookahead Decodingは計算量削減手法ではない。

むしろ1 step当たりの計算量は大幅に**増える**。

A100向けの推奨設定例では、

| Model | W | N |
|---|---:|---:|
| 7B | 15 | 5 |
| 13B | 10 | 5 |
| 34B | 7 | 5 |

で、論文の概算ではvanilla decodeと比べ1 step当たりFLOPsがそれぞれ約120×、80×、56×になる。

それでもbatch=1 decodeではGPUがmemory-bandwidth-boundで演算器が余っているため、wall-clock時間はFLOPs倍率ほど増えない。

その代わり1回に複数tokenを確定し、**必要なsequential step数を減らす**。

これがLookahead Decodingの最重要trade-offである。

## Lookahead Parallelism

### candidate verificationは互いに独立している

複数n-gram候補のverificationは互いに独立しているため、異なるGPUへ分配できる。

候補AをGPU 1、候補BをGPU 2というように実行しても、candidate同士でactivationを交換する必要がない。

論文はこれを**先読み並列性（Lookahead Parallelism; LP）**として、通常のtensor parallelismやpipeline parallelismとは別のparallelism axisとして使う。

### GPUを増やしてthroughputではなくlatencyを下げる

一般的なmodel parallelismでは、1 requestを複数GPUへ分割してもcommunication overheadで小batch latencyが悪化する場合がある。

Lookahead Parallelismは追加GPUを「より多くのcandidateを同時検証する資源」として使うため、余剰FLOPsをsequential-step削減へ振り向けやすい。

code completionでは8 GPU strong scalingで最大約4×のspeedupを報告する。

## 評価

### まず見るところ

- **単一GPU:** LLaMA-2 / CodeLlamaの各taskでおおむね1.5〜2.3×。MT-BenchではFlashAttention込みで最大約1.8×。
- **code:** 反復n-gramが多いため最大約2.3×とchatより効きやすい。
- **複数GPU:** Lookahead Parallelismによりcode completionで最大約4×。
- **品質:** greedyでexact、samplingでもtarget distributionを維持するverificationを定義。
- **代償:** 1 stepのFLOPsは数十〜100倍級に増え得る。
- **危険領域:** large batchやcompute-bound環境では追加FLOPsを無料で隠せず、逆に遅くなり得る。

## 通常のSpeculative Decodingとの違い

通常方式は、

`small draft model → candidate → large target verification`

である。

Lookahead Decodingは、

`large target自身のparallel Jacobi trajectory → n-gram pool → same target verification`

である。

したがって追加checkpointやdraft trainingは不要だが、target LLMをcandidate discoveryにも使うためFLOPs消費は大きい。

## RESTとの違い

RESTは外部corpusから現在contextに一致するcontinuationを検索してdraftに使う。

Lookahead Decodingは外部corpusを持たず、**現在のtarget inference中に自分でn-gramを発見してpoolへ蓄積する**。

そのため外部data dependencyはないが、candidate discoveryのためにtarget FLOPsを消費する。

## EAGLEとの違い

EAGLEはtarget内部featureを学習済み軽量draft moduleで予測するため、candidate生成が安く、batch=1ではより大きなspeedupを得やすい。

Lookahead Decodingは学習不要だが、candidate生成にtarget model自身の大量FLOPsを使う。

導入時のtrade-offは、

- **専用draftを学習・配布できる:** EAGLE型
- **何も学習せずtargetだけで完結したい:** Lookahead型

と整理できる。

## 限界

- 最大の弱点は**追加FLOPsが非常に大きい**こと。
- batch sizeが大きくGPU computeが既に飽和していると、追加FLOPsが直接latencyへ出て遅くなる可能性がある。
- `W`, `N`, `G`の良い値はmodel size・GPU・workloadに依存する。
- n-gram repetitionが少ないopen-ended textではcodeほどcandidate hitが高くない。
- n-gram poolとlookahead windowのmemory / attention token数が増える。
- theoretical scalingは、より大きなstep compressionを得るためにFLOPsを指数的に増やすためdiminishing returnがある。
- throughput重視のlarge-batch servingより、batch=1などlatency-sensitiveな推論に適している。

## 一般的な実装上の含意

Lookahead Decodingの重要な示唆は、LLM decode最適化では**FLOPs削減が常に正義ではない**ことである。

GPUがmemory bandwidth待ちで演算器を余らせているなら、追加計算を大量に入れてでも、

- 1回のweight readで多くのcandidateを処理する
- 1回のforwardで複数tokenを確定する
- sequential dependencyそのものを減らす

方がwall-clock latencyを下げられる。

これは「計算量最小化」ではなく、**memory bandwidthとcomputeの不均衡を利用するsystem optimization**である。

また、未来sequence全体を正確に予測できなくても、parallel iterationの途中から短いn-gramだけを回収して再利用するという発想は、draft generationを「完全な小型language model」に限定しないことを示している。
