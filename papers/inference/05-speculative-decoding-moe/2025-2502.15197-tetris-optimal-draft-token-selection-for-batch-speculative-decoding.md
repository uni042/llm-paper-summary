# TETRIS: Optimal Draft Token Selection for Batch Speculative Decoding

> 投機的復号（Speculative Decoding; SD）で速いドラフトモデルが多めの候補を作り、遅い対象モデルが並列検証する構造はそのままに、**対象モデルへ送る候補を要求ごとではなくバッチ全体で選び直す**。各要求の連続候補について「そこまで全部受理される確率」を計算し、限られた検証容量 (C) を確率の高い前方トークンへ配る。vLLMの64要求バッチでは最良既存方式比で総スループット最大5.25%、平均エンドツーエンド遅延最大6.13%改善した。

## 概要

通常の投機的復号では、小さなドラフトモデルが (k) 個の候補を自己回帰的に生成し、大きな対象モデルがそれらを一度に検証する。候補が連続して受理されれば、一回の対象モデル実行で複数トークン進められる。一方、途中の一トークンが棄却されると、その後ろの候補は依存する接頭辞が無効になるためまとめて捨てる。

単一要求だけなら、ドラフト窓を長くするか短くするかをその要求の受理率に合わせればよい。ところがバッチ配信では対象モデルが一度に検証できる候補総数に上限があり、要求ごとの「ドラフトしやすさ」も異なる。全要求へ同じ (k) を割り当てると、受理率の低い要求の後方候補にも高価な検証枠を使い、別要求の受理されやすい候補を検証できない。

TETRISは、ドラフトモデルに容量より少し多く候補を作らせ、その中から対象モデルへ送る候補だけを選別する。重要なのは個々のトークン確率ではなく、要求内の依存関係を含めた**累積受理確率**である。ある要求の第3候補を受理するには第1・第2候補もすべて受理される必要があるため、第3候補の価値は三つの条件付き受理確率の積になる。

この値を全要求で横断比較し、現在選んだ各要求の「次の候補」だけを最大ヒープで競わせる。容量 (C) 個に達するまで最も有望な候補を順に採用することで、難しい要求には短い窓、易しい要求には長い窓を自動配分する。理論上は真の受理確率が分かりドラフト時間を無視できる条件で、一段階のスループットを最適化する。

## 問題設定

対象モデルの検証計算は投機的復号の主要コストであり、サーバーの並列実行容量が有限なら「何個ドラフトするか」より「限られた (C) 個の検証枠をどの要求へ渡すか」が重要になる。

既存の固定窓方式は、全要求が同程度の受理率を持つ暗黙の仮定に近い。動的投機的復号（Dynamic Speculative Decoding; DSD）もバッチ全体へ一つの窓長を決める方式では、同じバッチ内で易しい要求と難しい要求が混在する不均一性を十分に利用できない。

さらに候補は要求内では直列依存する。第 (j) トークンだけ確率が高くても、その前の (1,dots,j-1) が棄却されれば第 (j) 候補まで到達しない。そのため「各候補を単独の確率で上位 (C) 個選ぶ」だけでは実行可能なドラフト集合にならない。

TETRISはこの制約を保ったまま、要求間では候補を並列資源として競わせる。これにより対象モデル検証という希少資源を、期待受理数が高い場所へ寄せる。

## 手法

### 1. 要求内の候補を累積受理確率で評価する

要求 (i) の第 (j) ドラフト候補の条件付き受理確率を (p_{i,j}) とする。この候補まで実際に到達して受理されるには、同じ要求の第1候補から第 (j) 候補までが連続して受理されなければならない。

そこでTETRISは第 (j) 候補の価値を単独の (p_{i,j}) ではなく、
[
prod_{t=1}^{j} p_{i,t}
]
で評価する。後方へ進むほど前方の失敗リスクが積み上がるため、受理率が低い要求では自然に値が急減する。

入力はドラフトモデルが生成した各要求の候補列と候補受理率の推定値、出力は対象モデルへ実際に送る候補集合である。モデル重みや最終サンプリング規則自体を変更する方式ではない。

### 2. 容量より多くドラフトして選択肢を作る

通常方式が対象モデルの容量 (C) ちょうどまでしかドラフトしないと、選択器が再配分できる候補が存在しない。TETRISは各要求へ少数の追加ドラフトを生成させ、バッチ全体では (C) より大きな候補集合を作る。

追加候補は全て検証するわけではない。対象モデルへ送る数は従来と同じ (C) に固定するため、比較上の対象モデル検証容量は増やさない。余分なドラフト計算と引き換えに、より受理されやすい (C) 個を選べる自由度を得る。

実測では追加1〜2トークンが良い場合が多く、追加数を増やし過ぎると現在の逐次ドラフト実装ではドラフト時間が増えて利得が縮む。つまり候補プールを増やすこと自体には明確な費用がある。

### 3. 最大ヒープでバッチ横断の検証枠を配分する

アルゴリズムは各要求の第1候補を最大ヒープへ入れて開始する。累積受理確率が最も高い候補を一つ取り出して採用したら、その要求の次候補をヒープへ追加する。これを採用数が (C) に達するまで繰り返す。

この手順なら、第 (j+1) 候補が選ばれる前に必ず同じ要求の第 (j) 候補が選ばれるため、要求内の連続性を壊さない。同時に、各反復では全要求の現在フロンティアから最も期待値の高いものを選ぶので、検証容量を要求間で動的に移せる。

論文はこの処理の時間計算量を (O(Clog N)) と示す。実装ではGPU上の最大値散布演算（scatter-max）を使い、TETRIS管理処理のオーバーヘッドを0.3 ms未満に抑えている。これは報告環境のドラフト1トークン当たり2.5 ms超より小さい。

### 4. 真の受理率の代わりにドラフトモデル確率を使う

理論上の受理率は対象モデルの確率 (p_M) とドラフトモデルの確率 (p_S) の両方に依存する。しかし検証前には (p_M) をまだ計算していないため、真の受理率は選択時点で利用できない。

実装ではドラフトモデルの出力確率を代理値として使う。ドラフトモデル自身が自信を持つ候補ほど対象モデルにも受理されやすいという相関を利用するが、これは完全な推定ではない。

この推定誤差が大きいと、ヒープ順位も誤る。したがってTETRISの利得はドラフトモデルの速度だけでなく、ドラフト確率が実際の受理確率をどれだけ順位付けできるかにも依存する。

### 5. 理論最適性と実際のパイプラインを分ける

真の受理確率が既知でドラフト時間を無視する場合、論文はTETRISが一段階の期待スループットで最適であることを示す。さらに一要求内の候補が同一受理率を持つという仮定の下では、全体スループットについても最適性を示す。

ただし現行vLLM実装はドラフト→選択→対象検証を逐次に実行する。この場合、余分な候補を作る時間はそのままレイテンシへ加算される。論文はドラフト側と対象側を並列化したパイプラインなら、この追加時間を対象モデル実行の陰へ隠せると分析するが、この最大利得は実測ではなく予測値である。

## 評価

### 主な評価条件

| 項目 | 条件 |
|---|---|
| 実装 | vLLM、逐次ドラフト・対象検証パイプライン |
| バッチ負荷 | 常に64要求 |
| Setting 1 | Vicuna-68M → Vicuna-33B、テンソル並列4、4×L40（合計180GB） |
| Setting 2 | Llama-3.2-1B-Instruct FP8 → Llama-3.1-70B-Instruct、テンソル並列8、8×L40（合計360GB） |
| Setting 3 | Llama-3.2-1B-Instruct FP8 → Llama-3.1-405B-Instruct FP8、テンソル並列8、8×H100（合計640GB） |
| ワークロード | ShareGPT、Chatbot Arena、Domain Tough Questions、Sonnet合成課題 |
| 比較対象 | 標準投機的復号（Standard SD）、動的投機的復号（DSD）、SDなし |
| 追加候補 | 主比較では最大3個。対象モデルへ送る候補総数は比較間で固定 |
| 主要指標 | 検証成功率（Verification Success Rate; VSR）、総スループット、平均エンドツーエンド遅延、対象効率率（Target Efficiency Rate; TER） |

### 実測結果

| 結果 | 最大改善 | 比較対象 | 意味 |
|---|---:|---|---|
| 総スループット | 5.25% | 各条件の最良既存方式 | ドラフト時間を含む現在の逐次vLLM実装でも改善が残る |
| 総スループット | 9.27% | 標準SD | 固定窓だけよりバッチ横断再配分の効果が大きい条件がある |
| 平均エンドツーエンド遅延 | 6.13% | 最良既存方式 | サーバー内部だけでなく要求完了時間も短縮 |
| 平均エンドツーエンド遅延 | 9.32% | 標準SD | 固定窓との最大差 |
| VSR | 20ポイント超〜最大約33ポイント | 標準SD | 同じ対象モデル検証枠へ、受理されやすい候補を送れている |
| Medusa統合 | 3.19% | Medusa単体 | 一回で複数候補を作れるドラフト方式とも組み合わせ可能 |

VSRは「受理トークン数 / 検証へ送った候補数」であり、選択器そのものの質を見やすい。ただしVSRが30ポイント上がっても、そのまま30%のエンドツーエンド高速化にはならない。追加ドラフト時間とボーナストークン生成が別にあるためである。

### 並列パイプラインでの予測

現在の逐次vLLMではドラフト時間を隠せないため、論文は対象効率率TERから、ドラフトと対象モデルを並列化した場合のスループットを別途推定する。予測改善は7.79〜12.04%で、最大12.04%はSetting 3・Toughである。

この12.04%は**現在の実装で実測した値ではない**。論文自身が、並列投機パイプラインがvLLMへ未統合であるため予測値として区別している。

### 負の結果・感度

追加ドラフトを増やせば常に速くなるわけではなく、現行逐次実装では1〜2個程度が良く、追加生成費が大きくなると性能が下がる。ドラフト品質を意図的に変えた混合課題ではSetting 2のSonnetで最良ベースライン比 -0.81%となる条件も報告されている。

したがってTETRISは「候補選択が常に無料」という方式ではなく、対象検証の節約と追加ドラフトの費用を比較して使う必要がある。

## 既存研究との差

標準SDは各要求へ固定窓を使い、SmartSpec系はバッチへ共通の動的窓を決める。EAGLE-2やMDSDにも確率ベースの貪欲候補選択はあるが、主に一要求内の候補木を扱う。

TETRISの差は、複数要求を同じ対象モデル検証容量 (C) の競合相手として扱う点にある。要求内の依存を累積確率で保ちつつ、要求間では受理されやすいフロンティアへ容量を移すため、ドラフトモデルや検証カーネルを変更せずにバッチ資源配分を改善できる。

## 限界・実装状況

最大の実装上の制約は、評価時点のvLLMが逐次投機パイプラインであることにある。対象モデルは追加ドラフト生成中に待つため、追加候補の計算が遅いドラフトモデルではTETRISの選択利得を打ち消す。

真の受理率は事前には分からず、ドラフトモデル出力確率を代理にする。ドラフトと対象モデルの分布差が大きい条件では順位付けが悪化する可能性がある。

理論最適性にも仮定がある。特に全体最適性は要求内で受理率が同一とする簡略化とドラフト時間無視の条件に依存するため、実システムで無条件の最適性を保証するものではない。

著者公式コードは公開されており、vLLM上で再現可能である。今後、PEARLやMinionsのような並列ドラフト・検証パイプラインと組み合わせると、論文で予測した追加利得を実測できる余地がある。
