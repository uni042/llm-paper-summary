# Making Every Verified Token Count: Adaptive Verification for MoE Speculative Decoding

> draft treeの各候補について受理される見込みと実際の検証時間を比較し、費用対効果の高い枝だけをtarget MoEで検証する手法。

## 概要
EVICTは、MoE speculative decodingで**draft treeを何nodeまでtarget modelで検証するか**を動的に決める手法である。

Dense modelではverification tokenを少し増やしても同じweightを再利用しやすいが、MoEでは1 node追加しただけで新しいexpertが必要になり、verification costが急に増えることがある。

そのため「acceptanceが高そうなnodeをできるだけ多く検証する」だけでは効率が悪い。EVICTは各nodeの受理確率と、そのtree形状を実際に検証したときの時間を比較し、**1単位の検証時間あたりに何token受理できそうか**が最も高い範囲だけを残す。

選んだnodeについてはtarget modelが通常通り厳密verificationするので、削るのは候補の広さであり、model計算自体を近似するわけではない。

## 手法のあらまし

### 1. Nodeごとのacceptance probabilityを持つ

draft treeの各nodeについて、「このtokenまでtargetにacceptされる確率」を推定する。

高確率nodeは検証する価値が高く、低確率nodeはそのために新しいexpertを追加起動する価値が低い。

### 2. 子nodeを残すなら、その手前のpathも残す

treeの途中nodeだけを単独で選ぶことはできず、そのnodeへ至る祖先tokenも順番に検証する必要がある。

EVICTは、**あるnodeを残すならrootからそこまでのpathも全部残す**という制約の範囲で候補を選ぶ。

論文ではこの性質を `ancestor-closed prefix` と呼ぶ。

### 3. Verification costを実測ベースで見る

MoEではcostがtoken数だけでは決まらない。

同じ10 tokenでも、全tokenが同じexpertへ集中する場合と、毎token別expertへ散る場合ではweight readとGEMM量が違う。

そこでEVICTはtoken数、tree形状、active expert数などからverification latencyを事前に測り、**その候補treeを本当に検証したら何msかかるか**を見積もる。

### 4. 受理見込みと検証時間の比でtree sizeを変える

単純なacceptance最大化ではなく、**検証に使う時間に対して受理tokenがどれだけ増えそうか**を最大化する。

このためdecode stepごとにtree sizeが変わる。

- 受理される見込みが高いstep → 広めに検証
- 新しく多くのexpertを使うため検証が重いstep → treeを小さくする

### 5. 可変treeでもGPU起動overheadを増やしすぎない

adaptive treeはshapeが毎回変わるため、CPU側で実行順を組み直したりGPU kernelを何度も起動したりするoverheadが増えやすい。

EVICTは頻出するtree形状のGPU実行手順をあらかじめ記録して再利用するCUDA Graphを使い、SGLangの実行経路へ組み込む。

つまりalgorithmだけでなく、**tree形状が変わってもCPU側の準備時間を増やしすぎないruntime統合**が重要になる。

## 評価

### まず見るところ
- **結論:** 受理されにくく、しかも新しいexpertを多く必要とするdraft枝を検証しないことで、MoE verificationを軽くできる。
- **実速度:** autoregressive比最大2.35×、EAGLE-3比平均1.21×。
- **品質:** 選択nodeはtargetで厳密verificationするため**lossless**。
- **注意点:** tree選択そのもののCPU overheadを抑えるruntime実装が必要。

| 項目 | 内容 |

### Speedup

| 比較対象 | 結果 |
|---|---:|
| Autoregressive generation | 最大 **2.35×** |
| EAGLE-3 | 平均 **1.21×** |

### Qwen3-30B-A3Bでの削減

| 指標 | 削減率 |
|---|---:|
| Verification token数 | **74.7%** |
| Active expert数 | 32.5% |
| Verification latency | 26.6% |

verification tokenを約75%減らしてもactive expertは32.5%しか減らない。

これは、少数のdraft tokenでも別々のexpertへ散ると多くのweightを読む必要があるMoE特有のcost構造を示している。

### CUDA Graph統合の意味

adaptive tree選択だけをalgorithmとして入れると、CPU側のshape選択・kernel launch overheadが増える。

CUDA Graph統合を外すと利得が小さくなり、runtime optimizationが手法成立の一部である。

### 品質

選択したtree prefixについてtarget modelのrouter/logitsを通常通り計算するため、sampling correctnessは維持する。

### 制約

- CPU/SSD offloadのI/O削減手法ではない。
- datacenter GPU runtime前提。
- acceptance probabilityが外れると速度だけが悪化する。
- consumer GPUやenergy/tokenは未評価。
