# Making Every Verified Token Count: Adaptive Verification for MoE Speculative Decoding

> 下書き treeの各候補について受理される見込みと実際の検証時間を比較し、費用対効果の高い枝だけを対象モデル MoEで検証する手法。

## 概要
追い出しは、MoE speculative デコードで**下書き treeを何nodeまで対象モデル モデルで検証するか**を動的に決める手法である。

Dense モデルでは検証 トークンを少し増やしても同じ重みを再利用しやすいが、MoEでは1 node追加しただけで新しいエキスパートが必要になり、検証 コストが急に増えることがある。

そのため「acceptanceが高そうなnodeをできるだけ多く検証する」だけでは効率が悪い。追い出しは各nodeの受理確率と、そのtree形状を実際に検証したときの時間を比較し、**1単位の検証時間あたりに何トークン受理できそうか**が最も高い範囲だけを残す。

選んだnodeについては対象モデル モデルが通常通り厳密検証するので、削るのは候補の広さであり、モデル計算自体を近似するわけではない。

## 手法のあらまし

### 1. Nodeごとのacceptance probabilityを持つ

下書き treeの各nodeについて、「このトークンまで対象モデルにacceptされる確率」を推定する。

高確率nodeは検証する価値が高く、低確率nodeはそのために新しいエキスパートを追加起動する価値が低い。

ただしacceptance probabilityだけで順位を付けるとMoE特有のコストを見落とす。ほぼ同じ受理確率の2 nodeでも、一方がすでに検証 バッチで使うエキスパートだけを再利用し、もう一方が新しいエキスパート集合を追加activateするなら後者の限界コストは大きい。追い出しは候補benefitを対象モデル側の実測コストと組み合わせることで、単なるhigh-confidence 枝刈りではなく『受理される見込みに対して検証 資源を使う価値があるか』を評価する。

### 2. 子nodeを残すなら、その手前のpathも残す

treeの途中nodeだけを単独で選ぶことはできず、そのnodeへ至る祖先トークンも順番に検証する必要がある。

追い出しは、**あるnodeを残すならrootからそこまでのpathも全部残す**という制約の範囲で候補を選ぶ。

論文ではこの性質を `ancestor-closed prefix` と呼ぶ。

この制約によりtree 枝刈りは任意nodeのknapsackではなく、prefix構造を保つ選択になる。深いnodeのacceptanceが高くても、その祖先のどこかが低確率ならそこまで検証するコストを全て支払わなければ深いnodeへ到達できない。したがって追い出しは局所node スコアだけでなくrootからの累積benefit/コストを見て、途中で枝を切る方が得な場合はそのdescendantもまとめて除外する。

### 3. Verification costを実測ベースで見る

MoEではコストがトークン数だけでは決まらない。

同じ10 トークンでも、全トークンが同じエキスパートへ集中する場合と、毎トークン別エキスパートへ散る場合では重み readとGEMM量が違う。

そこで追い出しはトークン数、tree形状、active エキスパート数などから検証 遅延を事前に測り、**その候補treeを本当に検証したら何msかかるか**を見積もる。

### 4. 受理見込みと検証時間の比でtree sizeを変える

単純なacceptance最大化ではなく、**検証に使う時間に対して受理トークンがどれだけ増えそうか**を最大化する。

このためデコード stepごとにtree sizeが変わる。

適応tree sizeは、下書き品質が時間とともに変化する場合にも効く。easy spanでは同じ下書き branchが長くacceptされやすく、少し広いtreeへ対象モデル 計算を使う価値が高い。一方、難しいトークン付近ではbranchが分岐してエキスパート 被覆も広がりやすく、同じ固定tree sizeを使うとrejectされる候補のために多数エキスパートを起動する。stepごとにprefixを縮めることで、この局所的なacceptanceとMoE 活性値の変動へ追従する。

- 受理される見込みが高いstep → 広めに検証
- 新しく多くのエキスパートを使うため検証が重いstep → treeを小さくする

### 5. 可変treeでもGPU起動overheadを増やしすぎない

適応型 treeはshapeが毎回変わるため、CPU側で実行順を組み直したりGPU カーネルを何度も起動したりするオーバーヘッドが増えやすい。

追い出しは頻出するtree形状のGPU実行手順をあらかじめ記録して再利用するCUDA Graphを使い、SGLangの実行経路へ組み込む。

つまりalgorithmだけでなく、**tree形状が変わってもCPU側の準備時間を増やしすぎない実行時統合**が重要になる。

実際の運用では、候補を減らす判断と正確な出力を保つ検証を分けて考える必要がある。手法が捨てるのは対象モデルへ渡す候補枝であり、残した枝の確率分布やルータの計算を近似することではない。したがって受理確率の予測が外れた場合に起きるのは主に速度低下で、採用した枝の検証結果を別の出力へ置き換える品質低下ではない。この性質が、適応的な候補数制御を安全に試せる根拠になる。

また、枝の選択はトークン数だけを見て決めると誤る。候補が増えると、検証対象のエキスパート集合、重みの読み出し量、行列積の分割が同時に変わるためである。実測した遅延を用いて根からの累積費用を比較し、受理見込みの増分が費用を上回る範囲だけを残すことが重要になる。固定の木の大きさを全入力へ適用する方式より、入力の難しさとエキスパートの広がりに合わせて計算量を調整できる。

この判断は、受理確率、候補の深さ、必要なエキスパート数を同時に見て行う。候補を残すほど確定できる可能性は増えるが、検証に必要な重みの読み出しも増えるため、各段階で追加の利得を測ることが要点になる。

## 評価

### まず見るところ
- **結論:** 受理されにくく、しかも新しいエキスパートを多く必要とする下書き枝を検証しないことで、MoE 検証を軽くできる。
- **実速度:** autoregressive比最大2.35×、EAGLE-3比平均1.21×。
- **品質:** 選択nodeは対象モデルで厳密検証するため**無損失**。
- **注意点:** tree選択そのもののCPU オーバーヘッドを抑える実行時実装が必要。

### CUDA Graph統合の意味

適応型 tree選択だけをalgorithmとして入れると、CPU側のshape選択・カーネル launch オーバーヘッドが増える。

CUDA Graph統合を外すと利得が小さくなり、実行時 optimizationが手法成立の一部である。

### 品質

選択したtree prefixについて対象モデル モデルのルータ/logitsを通常通り計算するため、サンプリング correctnessは維持する。

### 制約

- CPU/SSD オフロードのI/O削減手法ではない。
- datacenter GPU 実行時前提。
- acceptance probabilityが外れると速度だけが悪化する。
- consumer GPUやenergy/トークンは未評価。
