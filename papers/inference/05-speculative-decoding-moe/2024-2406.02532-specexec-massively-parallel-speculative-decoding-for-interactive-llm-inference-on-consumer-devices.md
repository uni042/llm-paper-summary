# SpecExec: Massively Parallel Speculative Decoding for Interactive LLM Inference on Consumer Devices

> ドラフトで高確率な候補木を作り、退避中70B級対象モデルの1回の重み走査で数百〜数千候補を並列評価するSpecExec。厳密分布を保ち最大約20トークン/反復を進める。

## 概要

70B級以上の大規模言語モデルを単一の消費者向けGPUで動かすと、重み全体がVRAMへ収まらず、各層をCPU DRAMやSSDからGPUへ順次読み込む**重み退避（weight offloading）**が必要になる。この環境では行列演算そのものよりPCI Express経由の重み転送が支配的になり、対象モデルを1トークンだけ評価しても、数百〜数千トークンを同じ層重みでまとめて評価しても「巨大な重みを一度読み込む」費用が共通する。

SpecExecはこの性質を投機的復号（speculative decoding）へ利用する。小さいドラフトモデルで将来の高確率な接頭辞を大量に列挙し、候補を木構造へまとめ、退避された対象モデルはその木全体を一つの大バッチとして1回だけ評価する。対象モデルが計算した各prefixの次トークン確率をキャッシュし、その後の生成は**通常どおり対象モデルの厳密な確率分布から逐次サンプリング**する。

重要なのは、SpecExecがドラフト木のトークンをそのまま「受理」して出力する方式ではない点である。ドラフトは将来必要になりそうな対象モデル確率を先回りしてキャッシュする役割だけを持つ。キャッシュに次prefixの確率があれば重い対象モデルを再実行せず生成を進め、外れた時だけ次の候補木を再計算する。したがって同じ乱数系列を使えば逐次対象モデルと同一のサンプル列を得られる。

Llama2-70B、Llama3-70B、Mixtral-8x7B等で、SpecExecは一度の対象モデル反復あたり10〜20トークン程度を進める条件を示し、退避推論では逐次実行比で最大18倍級の高速化を報告する。RTX 4090等の消費者向けGPUでも数トークン/秒の対話速度へ70B級モデルを引き上げることが主眼である。

## 問題設定

### 退避推論では重み転送が毎トークン繰り返される

Llama2-70Bを16ビットで保持すると重みは約140 GB級になり、RTX 3090の24 GB VRAMへ収まらない。論文はPCIe 4.0とDDR5を仮定しても、重みを逐次供給するだけで1トークンあたり数秒規模の下限が生じる例を示す。

一方、層重みをGPUへ読み込んだ後の行列積は、バッチ1から数百候補へ広げても転送時間ほど急には増えない。このためオフロード環境では「対象モデルを何回呼ぶか」を減らすことが、通常のGPU常駐推論よりはるかに重要になる。

### 通常の投機的復号は大きな候補予算を使い切れない

従来の投機的復号はドラフトモデルが1本または少数の候補列を作り、対象モデルがその列を検証する。候補を長くしても途中で一度不一致になると後続を使えず、1反復で進めるトークン数はおおむね10程度で飽和しやすい。

静的な候補木を使う方式もあるが、分岐幅や深さを固定すると、モデル・温度・データ分布・ハードウェアによって最適構造が変わる。SpecExecは、利用可能な大バッチ予算を「確率の高いprefixから埋める探索問題」として扱う。

## 手法

### 1. ドラフト木は「未来の対象確率をキャッシュする住所録」

現在prefixを (p) とし、ドラフトモデルがその先の候補木を構築する。木の各ノードは一つのトークンを追加したprefixであり、木サイズ (K)、最大深さ (D)、ドラフト探索の並列幅 (B) を持つ。

対象モデルは木の全ノードを一括forwardし、各ノードに対して「そのprefixの次トークン分布」を計算する。結果は `cache[prefix + token] = next_probs` のような形で保持される。実際の生成ループは現在prefixに対応する対象確率から普通に1トークンをサンプルし、新prefixの確率がキャッシュにあればそのまま次へ進む。

キャッシュから外れたprefixへ進んだ時点でのみ、再びドラフト木構築と対象モデルの大バッチ評価を行う。このため候補木が当たった長さが、そのまま「1回の重み走査で何トークン分の対象確率を前計算できたか」になる。

### 2. 出力分布を変えない

通常の投機的復号ではドラフト分布と対象分布の比を使う受理・棄却処理が必要になる。SpecExecではドラフトが出力トークンを決めず、対象モデルの確率表を先に埋めるだけなので、最終サンプリングは常に対象モデル分布そのものから行う。

したがってドラフト木が不正確でも生成品質は変わらない。影響は「キャッシュヒットが短くなり、対象モデルの再走査回数が増える」という性能側へ現れる。論文は同じ擬似乱数シードなら逐次サンプリングと同じ生成列になる性質を強調する。

### 3. 累積確率の高いprefixを優先する候補木探索

候補木全体を闇雲に広げると、極めて低確率な枝へ貴重なバッチ枠を使ってしまう。SpecExecは「対象生成がそのprefixへ到達する確率」が高いノードを優先して木へ入れる。

ドラフトモデルが与える各枝の条件付き確率を掛け合わせ、負の対数累積確率を経路コストとして見れば、高確率prefix探索を単一始点最短路（single-source shortest path; SSSP）に置き換えられる。実装はDijkstra法を並列化したように、現在有望な (B) prefixをまとめてドラフトモデルへ通し、展開後も上位 (K) の候補を残す。

この方法なら木の分岐数・深さを固定テンプレートへ縛らず、ドラフト分布が尖っている場所では深く、複数候補が拮抗する場所では横へ広がる。

### 4. 退避対象モデルは木全体を一括評価する

候補木には木状注意マスクを使い、各ノードが自分の祖先prefixだけを参照するようにする。これにより数百〜数千の候補prefixを大バッチへ詰めても、各prefixの対象確率を一回の層走査で正しく計算できる。

層ごとの対象重みは専用CUDAストリームで先読みし、現在層を計算中に次層の転送を重ねる。さらにドラフト木を作っている時間にも対象モデル先頭層のロードを始め、対象モデル側のI/O待ちを隠す。4ビットGPTQ対象モデルも利用でき、重み容量とPCIe転送量をさらに減らせる。

### 5. 予算を大きくし過ぎると逆に遅くなる

SpecExecは「大きいバッチがほぼ無料」というオフロード特性を利用するが、候補生成と対象側行列計算が完全に無料なわけではない。ドラフト予算を増やすほど1反復の平均生成トークン数は増える一方、ドラフト探索と対象forward時間も増える。

評価では最大受理長を得る予算と最大トークン/秒を得る予算が一致しない。A100退避条件ではSpecExecの速度最適点が概ね1024〜2048候補に現れる一方、別GPUや4ビット対象ではより小さい予算が良い場合がある。

## 評価

### 代表的な評価条件

| 項目 | 条件 |
| --- | --- |
| 対象モデル | Llama2-70B、Llama3-70B、Mixtral-8x7B |
| ドラフト | 主にLlama2-7B / Llama2-7B-Chat、Llama3-8B等 |
| 対象精度 | FP16またはGPTQ 4ビット |
| GPU | A100、RTX 4090、RTX 3090、RTX 2080 Ti等 |
| ワークロード | OpenAssistant、WikiText2、MT-Bench、C4 |
| 生成 | 各promptから32トークン以上、バッチ1の対話型設定 |
| 候補予算 | 数百〜2048程度を中心に比較 |
| 比較 | 逐次オフロード、SpecInfer、Sequoia等 |

論文の速度倍率は、対象モデルをVRAMへ完全常駐させた通常servingに対するものではなく、**巨大モデルの重みをホストから供給する退避条件**で読む必要がある。

### 代表的な結果

| 条件 | 1対象反復あたり生成量 | 速度 | 逐次比 | 読み取れること |
| --- | ---: | ---: | ---: | --- |
| A100 / Llama2-7B draft → Llama2-70B / OpenAssistant / budget 2048 | 20.60 token | 3.12 tok/s | 18.7倍 | 大候補木で重み走査回数を大幅削減 |
| A100 / 同系統 / GPTQ4 / budget 128 | 12.10 token | 6.02 tok/s | 8.9倍 | 4ビット化で絶対速度が上がり、最適候補数は小さくなる |
| A100 / Llama3-8B → Llama3-70B / MT-Bench | 18.16 token | 2.79 tok/s | 16.6倍 | 対話ベンチマークでも大きな先読み長を維持 |
| RTX 4090 / Llama2-7B → Llama2-70B / budget 256 | 13.46 token | 5.66 tok/s | 8.3倍 | 消費者GPUで70B退避推論を対話可能な速度へ引き上げる |
| RTX 3090 / budget 256 | 約14.3 token | 3.68 tok/s | 10.6倍 | GPU世代・I/O条件が違ってもオフロード律速なら利得が残る |
| RTX 2080 Ti / 1.3B draft / budget 128 | 7.34 token | 1.86 tok/s | 6.1倍 | 古いGPUでも大規模並列検証が有効 |

論文のheadlineである「最大約20トークン/反復」は常に20トークンを確定するという意味ではない。ドラフト木が対象分布の高確率領域をどれだけ覆えたかで変わる。また18.7倍は特定の逐次退避基準に対する倍率であり、GPU常駐70BモデルやクラウドGPU servingとの倍率ではない。

### ドラフトモデル品質と候補木

OpenAssistant上の分析では、Llama2-70B-Chatの次トークン確率は上位少数候補へ強く集中し、上位1〜4トークンで確率質量の大半を覆う場面が多い。7B級ドラフトは1B級よりこの高確率候補を当てやすく、13Bへ増やしても改善が小さい条件がある。

つまりドラフトを大きくすれば無条件に良いわけではない。候補木の確率被覆が改善する利得と、ドラフト探索そのものの時間を同時に見る必要がある。

## 既存研究との差

通常の投機的復号は「ドラフト列を対象モデルで検証し、受理できるところまで一気に進む」。SpecExecは「将来使う可能性の高い多数prefixについて、対象モデル自身の次トークン確率を先にキャッシュする」。最終サンプリングを対象分布だけで行うため、ドラフト分布に対する受理率補正が中心ではない。

SpecInferなどの木型投機方式に対しては、候補木を静的形状へ固定せず、累積ドラフト確率に基づくSSSPとして予算を高確率prefixへ配る点が差になる。特に退避推論では数百〜数千候補を一括処理しても対象重み転送回数は1回なので、通常のGPU常駐環境より「幅広い木」を使う経済性が高い。

## 限界・実装状況

対象モデルがVRAMへ完全常駐し計算律速になれば、大候補木の追加FLOPsがそのまま負担になり、SpecExecの前提は弱くなる。論文自身もSpecExecがローカル推論全体の最速実装を目指すのではなく、退避モデルでの対象走査回数を減らす方式として位置付ける。

ドラフト木の構築時間、候補木用KV状態、対象forwardのバッチ計算量は候補予算とともに増える。分布が平坦でドラフトが対象の高確率prefixを覆えない課題ではキャッシュミスが増え、利得は縮む。一方で予測外れは出力品質を変えず、性能悪化として現れる点は重要な安全性である。
