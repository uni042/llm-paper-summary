# RAC：要求適応型の投機的復号構成選択

## 概要

RAC（Request-Adaptive Configuration selection）は、投機的復号（Speculative Decoding）で使う**草稿モデル**と**草稿長**を要求ごとに同時選択する方式である。草稿モデルが提案したトークン列を目標モデルがまとめて検証する際、草稿の品質が悪ければ棄却が増え、草稿が長すぎれば草稿生成・検証に無駄が生じる。逆に、複雑な要求でも短すぎる草稿長に固定すると、採択可能なトークンを十分に先読みできない。RACはこの二つの制御変数を、要求の特徴と直近要求の実測履歴に応じて選ぶ。

一次資料はAAMAS 2026の**3ページ拡張要旨**であり、完全な長編論文ではない。表1ではVicuna-33B-v1.3を目標モデルとし、HumanEvalの生成速度を通常の自己回帰復号29.369 token/sからRACの59.343 token/sへ改善した（**2.021倍**）。GSM8Kは29.938から54.472 token/s（1.819倍）、Hybridは29.522から50.030 token/s（1.695倍）である。通常の投機的復号に対しても全3条件で改善するが、改善幅は通常復号との比較より小さい。原著の実験表と抽象部で用いられた「最大1.37倍（通常の投機的復号比）」は、表1の同一条件の比率からは直接再現できないため、表の実数値を優先して記載する。

本研究の新規性は、草稿を検証するアルゴリズムそのものの変更よりも、**実行する前の構成選択を履歴付きの意思決定問題へ変換した点**にある。現在の要求だけを見て草稿長を決める方式との差を、履歴の扱いと報酬定義に沿って整理する。

## 問題設定と従来方式の制約

通常の自己回帰復号では、目標モデルが一度の順伝播で次のトークンを生成する。投機的復号は軽量な草稿モデルに複数トークンを先に提案させ、目標モデルで一括検証して順次生成の依存を減らす。しかし実効速度は、草稿モデルの速度、目標モデルとの出力分布の一致、草稿長、検証費用に依存する。草稿モデルを大きくすると候補精度は改善し得るが、草稿生成自体が重くなる。草稿長を増やすと採択候補の上限は増える一方、低い採択率では無駄な草稿計算が増える。

論文は、従来の固定構成が、意味内容・要求長・タスクの違いを取り込めず、さらに要求列の時間的相関を利用しないことを問題とする。既存の適応手法としてSpecDec++、MetaSD、SWIFTを挙げ、現在要求の特徴に基づく調整だけでは直前の実行で観測された傾向を十分に使えないと位置付ける。ただし、この比較は著者の問題設定であり、これらの先行研究が一切履歴を使えないと一般化するものではない。

RACの最適化単位はGPU全体のバッチではなく**個々の入力要求**である。スケジューラが要求をどのGPUへ配置するか、KVキャッシュをどの階層へ退避するかを解く研究とは異なり、既に与えられた目標モデルの投機的生成を、要求に適した設定で走らせることを狙う。したがって対象は投機的復号の構成制御であり、負荷分散や分散推論を直接解く方式ではない。

## 手法

### 1. マルコフ決定過程への定式化

要求番号を `t` とすると、状態は論文式(1)の `s_t = [f_t, h_t]` である。`f_t` は現在要求の特徴、`h_t` は直近 `k` 要求の構成と性能を要約した履歴である。これにより同じ入力長の要求でも、タスク・意味内容・直近の採択挙動が異なれば別の草稿構成を選択できる。

現在要求の特徴 `f_t = [e_t, y_t, l_t, p_t]` は、(a)意味埋め込み `e_t`、(b)タスク種別 `y_t`、(c)入力長 `l_t`、(d)複数草稿モデルに対するパープレキシティ `p_t` からなる。意味埋め込みは内容の違い、タスク種別はコード生成・数学問題などの要求性質、入力長は計算負荷、パープレキシティは草稿候補の適合性を表す特徴として利用する。パープレキシティを全草稿モデルで計算する前処理費用や、埋め込みをどのモデルで生成するかは3ページ要旨に詳述されていないため、オンラインで無償に得られると仮定しない。

履歴 `h_t` は過去 `k` 件の選択構成と実測性能をまとめる。著者の公式実装READMEでは、履歴窓をGRUで符号化し、採択率や速度向上などの実行フィードバックを含めると説明されている。これは実装説明に基づく補足であり、論文本文の式(1)自体は履歴の詳細符号化構造まで明示していない。履歴を使うことは、直近要求に偏った系列で有利になり得るが、ワークロードが急変したときに過去情報が逆効果となる可能性もある。この可能性を示す切替実験は拡張要旨にはない。

### 2. 草稿モデルと草稿長を組にした行動

論文式(2)の行動 `a_t` は、草稿モデル集合 `M_q` からのモデル選択 `M_t^q` と、候補草稿長集合 `W` からの長さ `w_t` の組である。片方だけを適応化するのではなく、両者を同時に選ぶ点が設計の核である。評価では草稿モデル候補として**Vicuna-160MとVicuna-68M**を用い、草稿長は**3～10トークン**の候補から選ぶ。

選択後はその構成で通常の投機的復号を実行する。目標モデルの検証規則をRAC独自の近似規則へ変更したとは論文に記されていない。草稿モデルの切替が必要な場合、モデルの常駐数、重みメモリ、切替の実装費用がシステムのボトルネックになり得るが、モデルを何枚のGPUへどう配置したかは拡張要旨から確認できない。従って「モデル切替に費用がない」「両草稿モデルが常にGPU常駐」とは断定しない。

### 3. 速度を目的とする報酬と方策学習

報酬は式(3)の `r = S_RAC / S_AR` で、RACで得たトークン生成速度を通常の自己回帰復号の平均速度で正規化する。これはトークン毎秒の相対改善を直接最適化する設計である。目的関数を単純な草稿採択率だけにしないため、草稿の採択数が増えても計算費用で全体速度が落ちる構成を必ずしも好まない。反面、報酬に生成品質、メモリ容量、消費電力、99パーセンタイル遅延を直接含めるとは記載されていない。

RACは拡散モデルに基づく方策を、Soft Actor-Critic（SAC）の強化学習枠組みと組み合わせる。方策は状態から草稿モデル・長さの組を出力し、実行速度のフィードバックを使って将来の選択を改善する。拡散方策の具体的なネットワーク層数、拡散反復回数、SACの温度や学習率、方策評価の推論時間は3ページ版には記載がない。したがって本稿では、拡散方策がどのように離散的な草稿モデル候補へ写像されるかを勝手に補完しない。

### 4. 要求間フィードバックの実行順

処理は「現在要求の特徴を抽出 → 過去要求の履歴表現と結合 → 方策が草稿モデルと長さを選択 → その設定で投機的復号 → 速度や採択の実績を履歴へ反映 → 次要求へ」の循環である。現在要求を選ぶ際に、その要求の最終的な実測速度を既に知っているわけではない。実行後に得られる値と事前特徴を分けることで、未来情報の混入を避ける必要がある。

この設計の利点は、最適な構成が要求の内容に依存する場合、固定の草稿モデル・固定長を全要求へ強制せずに済むことである。追加費用は特徴抽出、方策の実行、履歴保持、場合によっては草稿モデルの切替であり、これらを含む端から端までの実測と、方策計算だけの時間の両方が再現性に重要となる。

### 評価結果と比較

#### 1. 主要結果（原著表1の数値）

| 方式 | HumanEval token/s（対AR） | GSM8K token/s（対AR） | Hybrid token/s（対AR） | 表中平均倍率 |
|---|---:|---:|---:|---:|
| 自己回帰（AR） | 29.369（1.000倍） | 29.938（1.000倍） | 29.522（1.000倍） | 1.000倍 |
| 通常の投機的復号 | 45.287（1.542倍） | 42.977（1.435倍） | 40.274（1.364倍） | 1.432倍 |
| Lookahead | 40.487（1.378倍） | 45.527（1.521倍） | 36.991（1.252倍） | 1.384倍 |
| PLD | 42.058（1.432倍） | 44.036（1.470倍） | 40.676（1.377倍） | 1.426倍 |
| SAM-Decoding | 46.382（1.579倍） | 46.612（1.556倍） | 43.721（1.481倍） | 1.539倍 |
| Assisted Generation | 45.205（1.539倍） | 45.843（1.531倍） | 37.972（1.286倍） | 1.452倍 |
| SWIFT | 30.648（1.044倍） | 25.874（0.864倍） | 23.392（0.792倍） | 0.900倍 |
| **RAC** | **59.343（2.021倍）** | **54.472（1.819倍）** | **50.030（1.695倍）** | **1.845倍** |

HumanEvalではRACが通常の投機的復号より14.056 token/s高く、同条件の速度比は59.343/45.287 ≈ **1.310倍**となる。GSM8Kでは54.472/42.977 ≈ **1.267倍**、Hybridでは50.030/40.274 ≈ **1.242倍**である。これらは同じ表の絶対速度から再計算した比率であり、自己回帰復号を基準にした2.021倍等とは異なる。RACの表中平均1.845倍は3条件の自己回帰基準倍率の平均であり、通常投機的復号の平均1.432倍と単純に比較すれば約1.288倍である。

著者は要旨で「通常の投機的復号に対して最大1.37倍」と記すが、表1の3条件では最大が約1.310倍であり、この1.37倍に対応する条件は拡張要旨の表に明示されない。したがって最大1.37倍を表1の検証済み実測値と同一視せず、**要旨の主張と表の可観測範囲の差**として保留する。表1の数値は端から端までのトークン生成速度として報告されているが、方策の前処理費用をどの範囲まで含めたかも本文だけでは特定できない。

#### 2. 固定構成と適応構成の差

通常の投機的復号は全3データセットで自己回帰復号を上回り、固定構成にも基本的な利得がある。その上でRACが改善するため、主張の中心は「投機的復号を使うか否か」ではなく「使う場合に要求ごとに構成を変える価値」である。HumanEvalはコード生成、GSM8Kは数学問題であり、出力の性質が違う条件の両方で改善する点が本表から読み取れる。Hybridについては混合条件の詳細が不明なので、実サービスの到着分布へ直接一般化しない。

SAM-Decodingは通常投機的復号より各条件で速いが、RACはそのSAM-Decodingも上回る。たとえばHumanEvalでは59.343/46.382 ≈ 1.279倍、GSM8Kでは54.472/46.612 ≈ 1.169倍、Hybridでは50.030/43.721 ≈ 1.144倍である。これは「比較対象に最も近い方式」を選んでも利得が残ることを示す。ただし、各手法の草稿モデルやハードウェア最適化が完全に一致するかは本文から十分に検証できない。

#### 3. 悪化例と測定されていない内部指標

比較手法SWIFTはGSM8Kで0.864倍、Hybridで0.792倍と自己回帰復号より遅くなる。これは投機的な処理を加えるだけでは必ず高速化しないという具体的な負の結果である。ただし、SWIFTの悪化原因が草稿モデル選択なのか、方式固有の計算なのかを表1だけで分離できないため、RACの各機構がSWIFTの問題を直接解決したとは断定しない。

原著には「履歴を除く」「拡散方策を通常のSAC方策に替える」「草稿モデルだけ選ぶ」「草稿長だけ選ぶ」といった構成要素除去の表がない。採択率、草稿長の選択分布、選択器の推論時間、要求長別の性能、バッチサイズ別の性能、GPUメモリ占有量、電力消費、99パーセンタイル遅延も報告されない。したがってどの構成要素が何割の改善に寄与したかを定量的に配分できない。これは拡張要旨という資料形態による制約であり、存在しない実験値を補わない。

## 実装状況・再現性

著者の公式公開先は `https://github.com/JhSheng/RAC-` で、方策・推論・ベンチマーク等のディレクトリを持つ。READMEではPython 3.10以上、PyTorch 2.0以上を示し、履歴をGRUで符号化すると説明している。論文PDFの方策定式化と公式実装説明の対応は確認できるが、今回コードを実行したわけではないため、再現成功とは記載しない。コード公開の存在と論文数値の独立再現性は別である。

モデル集合の拡大時には、候補ごとの草稿モデル重み、事前特徴抽出、草稿長の探索空間が増える。拡散方策を用いる選択器が十分軽いか、要求の到着頻度が高いときに選択処理が律速にならないか、過去履歴をGPU間・サーバ間でどう共有するかは、原著の拡張要旨だけでは判断できない。これらは実運用への導入を検討する際の未評価事項として扱う。

## 既存研究・サーベイ系統との関係

固定の草稿モデル・固定草稿長による投機的復号、採択率に基づく草稿長調整、複数草稿モデルを使う方式と比べ、RACは**要求特徴と過去要求の実行結果を状態に統合して、モデル選択と長さ選択を同時に学習する**点が異なる。速度改善は検証の仕組みの変更ではなく、構成選択の改善に対応する。したがって投機的復号の「草稿生成器」「検証器」よりも「動的構成制御・適応スケジューリング」の系統と結び付けるのが適切である。

GPUメモリ・KVキャッシュの最適化や、分散サービングの負荷分散とは補完関係にある。複数要求をまとめる連続バッチ環境で、個々の要求に異なる草稿モデルを選んだ場合のバッチ効率は本論文の表1では分からない。特に、推論基盤へ統合するには、草稿モデル切替と連続バッチの干渉、方策実行費用、品質の同一性を別途測定する必要がある。

## 限界

RACの実証可能な主張は、**Vicuna-33B-v1.3を目標モデルとした3種類のベンチマークで、要求単位の草稿モデル・草稿長選択が固定的な複数方式より高い生成速度を示した**ことである。原著表1の最大はHumanEvalの2.021倍（自己回帰復号比）であり、GSM8K・Hybridでもそれぞれ1.819倍・1.695倍を報告する。

一方、(1) GPU・バッチ・到着率の詳細、(2) 方策の計算・学習費用、(3) 履歴と拡散方策の個別寄与、(4) モデル系列・草稿候補の一般化、(5) 正答率と尾部遅延、(6) 要旨の「1.37倍」と表1の数値の対応は未確認である。3ページ拡張要旨からこれ以上の性能保証を導くことはできない。RACは有望な動的構成選択の研究だが、実GPUサービングへの採用可否はこれらの追加測定に依存する。
