# EAGLE: Speculative Sampling Requires Rethinking Feature Uncertainty

> EAGLEは、別の小型LLMに未来tokenを予測させる代わりに、**target LLM内部の高水準な特徴量（feature）を小さな1-layer decoderで先読みする**投機的復号（speculative decoding）方式である。特徴量だけでは「次にどのtokenをsampleしたか」が分からず未来featureが一意に決まらないため、実際にsampleされたtokenを1 stepずらして入力へ加え、その分岐不確実性を解消する。

## 概要

通常の自己回帰復号（autoregressive decoding）では、巨大なLLMを1回forwardしても原則1 tokenしか確定しない。

batch sizeが小さいdecodeでは、行列演算そのものより巨大なmodel weightをGPUのHBMから読み出すmemory trafficが支配的になりやすい。そのため1回のtarget forwardで複数tokenを確定できれば、同じweight readをより多くのtokenへ使い回せる。

一般的な投機的復号では、小さいdraft modelが数tokenを先に生成し、巨大なtarget modelがその候補をまとめて検証する。候補がtargetの分布とよく一致すれば、1回のtarget forwardで数token進める。

問題は、**軽いdraft modelほどtarget modelとの予測差が大きくなりやすい**ことである。

EAGLEはここで「tokenそのものを小型modelで予測する」発想を変える。target LLMが各tokenについて内部で作っている、語彙logit直前の高水準な特徴表現をdraft対象にする。

論文では特に**上から2番目の層の特徴量（second-to-top-layer feature）**を使う。このfeatureを予測できれば、target modelが元から持つLM headをそのfeatureへ適用して次token分布を得られる。

ただしfeature予測には一つ重要な落とし穴がある。同じfeatureからでも、samplingで次tokenに「am」が選ばれるか「always」が選ばれるかによって、次のfeatureは大きく変わる。つまりfeatureだけを見ても未来featureは一意に決まらない。

EAGLEの核心は、**予測済みfeatureに加えて、実際に1 step先でsampleされたtokenを入力する**ことにある。

これにより「どのbranchを進んだ後のfeatureを予測すべきか」が明確になり、軽量draft moduleでもtarget内部状態をかなり正確に追従できる。

## 問題設定

### token-levelのdraftはtarget modelの内部情報を捨てている

LLMは内部で高次元のhidden featureを何十層もかけて計算し、最後にLM headで数万語彙の確率分布へ変換する。

通常のdraft modelは、確定したtoken IDだけを入力として次tokenを予測する。これはtarget modelが作った豊富な内部表現を一度tokenへ圧縮し、その情報を捨てた後でもう一度小型modelで意味表現を作り直しているとも言える。

EAGLEの実験では、同程度の小さなnetworkを使った場合、token列を自己回帰するよりtargetの上位feature列を自己回帰した方がdraft予測精度が高い。Vicuna 7Bを使ったablationでは、featureを使う構成がtoken-only構成よりdraft accuracyを大きく改善し、speedupも約1.5×から約1.9×へ上がった。

### featureは連続だから簡単、とは限らない

featureはtokenより高水準で滑らかな表現なので予測しやすい。しかしsamplingがあると、同じ現在featureから複数の正しい未来featureが存在する。

例えば現在の文脈が `I` で、次token分布から

- `am`
- `always`

のどちらもsampleされ得るとする。

`I am` の次にtarget modelが作るfeatureと、`I always` の次に作るfeatureは異なる。

現在feature `f_I` だけを入力して「次featureは何か」と学習させると、draft moduleは複数の未来を1つの連続vectorへ押し込もうとしてしまう。この曖昧さを論文は**特徴不確実性（feature uncertainty）**として扱う。

### sampling結果を条件にすればbranchが確定する

そこでEAGLEはfeature系列とtoken系列を1 stepずらして組み合わせる。

概念的には、

`現在までのfeature + そのbranchを選んだ実token → 次feature`

を学習する。

「どのtokenがsampleされたか」が分かれば、未来featureのbranchも決まる。これがEAGLEで最も重要な設計である。

## 手法のあらまし

1 decode cycleは概ね次のように進む。

1. target LLMが現在の確定済みcontextを処理し、上から2番目の層のfeatureを得る。
2. LM headからtarget token分布を得てtokenをsampleする。
3. EAGLE draft moduleへ、直前featureと1 step進めたtokenを入力する。
4. draft moduleが次のsecond-to-top-layer featureを予測する。
5. target modelの元LM headをその予測featureへ適用し、次のdraft tokenを得る。
6. 予測featureとsample済みdraft tokenを再びdraft moduleへ入れ、数step先まで自己回帰的に候補を伸ばす。
7. 複数候補をtreeへまとめ、target LLMで一括検証する。
8. targetのaccept/reject規則に従って受理できるprefixだけを確定し、次cycleへ進む。

要するに、

`target feature → 小型moduleで未来featureを予測 → 元LM headでdraft token化 → targetで検証`

という構造である。

## 手法

### 1. draft対象はsecond-to-top-layer feature

EAGLEが予測するのは最終logitでもtoken IDでもなく、target LLMの**最後のTransformer layerへ入る直前付近のfeature**である。

この位置のfeatureは既に文脈情報を高水準に含んでいる一方、最終LM headを再利用してtoken確率へ変換できる。

そのためEAGLE draft moduleは、巨大な語彙分布を一から学ぶ必要がない。

### 2. draft moduleは1層の軽量Transformer decoder

元target LLMを小さくコピーするのではなく、featureを自己回帰するための軽量な1-layer Transformer decoderを追加する。

論文のtrainable parameter数はtarget modelに応じて、

- 7B: 約0.24B
- 13B: 約0.37B
- 33B: 約0.56B
- 70B: 約0.99B
- Mixtral 8x7B: 約0.28B

である。

これは無視できるほどゼロではないが、別の数十億parameter draft LLMを持つより小さい。

### 3. featureと「1 step先へずらしたtoken」を同時入力する

EAGLEの入力設計で最も重要なのが**shifted token**である。

単に現在featureと同じ位置のtokenを入れるのではなく、そのfeatureから実際にsampleされた次tokenを組み合わせる。

これによりdraft moduleは、

- `f_I` の後に `am` が選ばれたbranch
- `f_I` の後に `always` が選ばれたbranch

を区別できる。

論文のablationでは、

- token only
- feature only
- feature + unshifted token
- feature + shifted token（EAGLE）

を比較し、単にfeatureを使うこと以上に**sampling結果を1 stepずらして与えること**が大きく効くことを示している。

### 4. 予測featureからtarget自身のLM headを使う

EAGLEはdraft tokenを生成するための独自巨大vocabulary headを別途学習するのではなく、target modelのLM headを再利用する。

予測feature `f'` をLM headへ入れ、

`f' → target LM head → draft token distribution`

とする。

feature予測がtarget内部状態に近ければ、token分布もtargetの分布へ近くなり、後段のacceptanceが高くなる。

### 5. draftをchainだけでなくtreeへ広げる

1本のdraft chainだけを作ると、途中の1 tokenが外れた時点で後続候補を全て捨てることになる。

そこでEAGLEは複数候補をtree状に展開する。

各nodeは候補tokenを表し、複数branchをtarget LLMへまとめて投入する。tree attention maskを使い、各candidate nodeが

- 確定済みcontext
- 自分のancestor branch

だけを参照するようにする。

これにより複数pathを1回のtarget forwardで検証できる。

論文ではtree化によってchainより平均受理長（average acceptance length）が約0.6〜0.75 token程度伸びる条件を示している。

### 6. target modelは変更しない

EAGLEの学習ではtarget LLMを固定し、追加draft moduleだけを学習する。

ShareGPTの68,000 dialogue iterationを使ってdraft moduleを学習している。

ここはMedusa-2のようにtarget backbone自体を共同fine-tuneする方式との大きな違いである。

### 7. draftが外れても品質ではなく速度へ効く

EAGLEのfeature予測は近似なので当然外れる。

しかしdraft結果をそのまま最終出力にするのではない。target modelによる投機的sampling検証を通す。

正しいrejection sampling規則を使うことで、**greedyだけでなくtemperature > 0のsamplingでも元target LLMと同じ生成分布を保てる**。

したがってfeature予測ミスの主な影響は、

- candidateがrejectされる
- 1回に確定できるtoken数が減る
- speedupが下がる

ことであり、受理規則を守る限り「誤ったdraftをそのまま出力して品質が落ちる」ものではない。

### 8. feature誤差は蓄積するが、破局的には増えにくい

featureを自己回帰予測すると、1回の予測誤差が次のfeature予測へ伝播する。

論文は、入力featureに0個、1個、2個、3個、4個の誤差が含まれる場合のacceptanceを調べている。

完全に正確なfeatureから始める場合より、1個誤差が入るとacceptanceは下がる。一方、1個から2〜4個へ誤差数が増えてもacceptanceが急激には崩れない。

つまりEAGLEはfeature errorを完全に消しているわけではないが、ある程度の誤差蓄積に耐える。

## 評価

### まず見るところ

- **速度:** Vicuna / LLaMA2-Chatのgreedy生成では概ね約3×級。LLaMA2-Chat 70Bではtaskにより約2.7〜3.5×。
- **1回のtarget forwardで進む量:** MT-Benchのtemperature=0では平均受理長が約3.6〜4.0 token。
- **sampling:** temperature=1でも平均受理長は約3.2〜3.5 token程度を維持し、生成分布を保つ。
- **throughput:** batchを大きくするとlatency speedupは縮むが、最大batchまで含めたthroughputは約2×。
- **MoE:** Mixtral 8x7Bでは1.50×で、dense LLaMA系より利得が小さい。
- **注意:** `EAGLE + gpt-fast` の160.4 tokens/sはEAGLE単体のspeedupではなく、compiler/kernel/quantization最適化との組合せである。

## Medusaとの違い

Medusaは1つのtarget hidden stateから複数future positionのtokenを**並列・独立に直接予測**する。

EAGLEはfuture featureを**自己回帰的に**予測するため、直前のdraft結果を次のpredictionへ使える。

さらにsamplingでどのbranchへ進んだかをshifted tokenで明示するため、Medusa型の独立future-token headよりdraft-target一致率を高めやすい。

## 通常のdraft modelとの違い

通常のspeculative samplingは別の小型LLMをtoken-levelで自己回帰する。

EAGLEはtarget内部の高水準featureを再利用するので、小さいdraft networkでもtargetのsemantic stateへ近い場所から予測を始められる。

一方、modelごとに対応するEAGLE moduleを学習する必要は残る。

## Lookahead Decodingとの違い

Lookahead Decodingは追加学習やdraft modelを必要とせず、Jacobi型のparallel iterationから未来n-gram候補を発見するtraining-free方式である。

EAGLEは追加moduleの学習costを払う代わりに、target featureを直接使って高いacceptanceを狙う。

したがって、

- **導入の軽さ:** Lookahead
- **高いbatch-1 speedup:** EAGLE

という設計上のtrade-offがある。

## 限界

- target modelごとに専用draft moduleの学習が必要。
- draft moduleは0.24B〜0.99B程度あり、完全に無料ではない。
- batch sizeが大きくなるほどvanilla decoding側のGPU利用率も上がり、相対speedupが縮む。
- candidate treeを増やしすぎるとtarget verification costが増える。
- MoEではcandidateごとのexpert activationが増えるため、dense modelほど大きなspeedupが得られない場合がある。
- target architectureからsecond-to-top-layer featureを取り出し、既存KV cacheとtree verificationへ統合するruntime変更が必要。
- 公式repositoryの現在のmain branchはEAGLE-2/3を中心に発展しているため、EAGLE-1を再現する際はversionを区別する必要がある。

## 一般的な実装上の含意

EAGLEが示した重要な点は、speculative decodingのdraftを「小さいtoken generator」とだけ考える必要はないことである。

巨大target modelが既に計算した内部featureは、次のtokenより多くのsemantic informationを含む。そのfeatureをdraft側へ引き渡せば、小さいnetworkで一から文脈を再構築する無駄を減らせる。

一方、featureを予測する場合は連続vectorの回帰精度だけを見ても不十分である。samplingという離散的なbranch選択を条件へ入れなければ、「同じ現在featureに複数の正しい未来がある」という構造的な曖昧さが残る。

この**内部表現の再利用 + 離散branch情報の明示**がEAGLEの本質である。
