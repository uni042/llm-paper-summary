# SpecInfer: Accelerating Generative Large Language Model Serving with Tree-based Speculative Inference and Verification

> SpecInferは、通常ならtarget LLMを1 tokenごとに呼ぶところを、**小さいmodelが先に複数の未来候補を作り、それらをtreeとしてtarget LLMにまとめて検査させる**ことで、1回のtarget-model passから複数tokenを確定しようとするsystemである。

## 概要

通常の自己回帰復号（autoregressive decoding）では、次tokenを1つ生成してからでないと、その次のtokenを確定できない。この依存関係そのものは言語modelの意味上必要だが、実装上は大きな問題になる。

数十B〜数百B parameterのLLMでは、1 tokenを出すたびに巨大なmodel weightをGPU HBMから読み、model parallel構成ならGPU間通信も発生する。weightをCPU DRAMへ退避しているsystemなら、さらにCPU→GPU転送まで繰り返す。

つまり「1 token進むたびにtarget model全体へ1回アクセスする」という構造が重い。

SpecInferは、target modelより40〜100倍程度小さい複数の小型投機model（small speculative model: SSM）を先に走らせ、次に来そうなtokenを複数step・複数branch予測する。それらを共通prefixでtoken treeへまとめ、**target modelを“次token生成器”ではなく“候補treeの検証器”として1回だけ実行する**。

候補がtarget modelの本来の出力と長く一致すれば、1回のtarget passで2 token、3 token、場合によってはそれ以上まとめて確定できる。外れたbranchは捨てるので、draft modelの予測自体を最終出力として信用する必要はない。

## 問題設定

### 通常decodeは1 request内の並列性が小さい

prompt処理では多数tokenを並列計算できる。一方decodeでは、token `t+1` を確定するにはtoken `t` の結果が必要なので、1 request内では基本的に1 tokenずつ進む。

GPUから見ると、各stepで同じ巨大weightを読みながら処理するtoken数が少ないため、matrix multiplicationの演算能力よりmemory bandwidthが律速になりやすい。

### 単一draft列だけでは『最初の外れ』に弱い

一般的な投機的復号（speculative decoding）は、小さいdraft modelに数tokenを直列で提案させ、target modelでまとめて検証する。

ただしdraft列の2 token目が外れると、それより後ろのtokenがどれだけよくても使えない。したがってdraft modelとtarget modelの一致率が低い区間では、長い候補列を作っても無駄になりやすい。

SpecInferは1本の線形候補ではなく、**複数の候補branchを持つtree**を作る。あるbranchが外れても、同じprefixから伸びた別branchがtarget出力と一致していれば、そちらへ進める。

### treeをbranchごとに検証したら意味がない

候補を10本作ってもtarget LLMを10回実行していたら高速化にならない。

そのためSpecInferのsystem上の核心は、**tree内の全候補nodeをtarget LLMの1 verification passで処理するtree attention**にある。

## 手法のあらまし

1回のdecode cycleは次のように進む。

1. 現在まで確定したtoken列を複数SSMへ渡す。
2. 各SSMがbeam searchなどで複数の未来token列を提案する。
3. 共通prefixを共有するように候補列を1つのtoken treeへmergeする。
4. target LLMでtree内の全nodeを並列にforwardする。
5. rootからtarget LLMの出力と一致するchildを辿る。
6. 一致が続いた分だけ複数tokenを一度に確定する。
7. 最初に一致するchildがなくなった地点では、target LLM自身が出したtokenを1つ採用して次cycleへ進む。

したがってdraftが完全に外れても、target LLM自身の正しいnext tokenは必ず得られる。draftが当たったときだけ追加tokenを“無料に近い形”で前倒しできる。

## 手法

### 1. 複数SSMで候補の多様性を作る

単一の小型modelにはcapacity gapがあり、target LLMと常に同じ続きは出せない。

SpecInferは複数のSSMを使う。OPT-175Bに対するOPT-125M/350Mのように同じmodel familyの小型版を使えるほか、retrievalなどuser-defined predictorも候補生成器として組み込める。

複数SSMを別GPUで並列実行できれば、SSM数を増やしてもspeculation latency自体は大きく伸びない。一方で候補数が増えるほどtreeが大きくなり、target側のverification costは増える。

そのため「候補は多ければ多いほどよい」わけではない。

### 2. 集団boost調整でSSM同士をわざと多様化する

複数SSMが全員同じ箇所で当たり、同じ箇所で外れるなら、複数使う意味が小さい。

SpecInferの集団boost調整（collective boost-tuning）は、SSMを順番にfine-tuneする。

最初のSSMがtarget LLMと正しく一致したtraining sampleを記録し、次のSSMは**まだ前のSSMが当てられていないsampleを重点的に学習する**。これを繰り返すことで、各SSMに異なる“得意区間”を持たせる。

狙いは各SSM単体を最大精度にすることではなく、**複数SSMの候補をunionしたときにtarget出力をtree内へ含む確率を上げること**である。

### 3. 候補列をtoken treeへmergeする

たとえば2つのSSMが

- `The → cat → is → ...`
- `The → cat → was → ...`

を提案した場合、`The → cat` までは同じなので2本を別sequenceとして持つ必要はない。

SpecInferは共通prefixを同じnodeとして共有し、分岐する地点だけchildを増やす。

これにより重複tokenのverificationを減らし、複数候補をcompactに表現できる。

### 4. tree attentionで『各nodeは自分の祖先だけを見る』

普通のcausal attentionでは、sequenceのtoken `j` は自分より前のtokenだけを見る。

Treeでは単純な位置順では不十分である。branch Aのtokenがbranch Bのtokenを見てはいけないからだ。

SpecInferではtree maskを作り、各nodeが

- 既に確定済みのprefix
- rootからそのnodeまでの祖先node

だけへattentionできるようにする。

このmaskを使えば、treeのnodeを大きなbatchのようにtarget LLMへ一度に流しても、**各branchを独立した通常sequenceとして計算した場合と同じattention依存関係**を再現できる。

これがtree-based parallel decodingの核である。

### 5. target modelの出力と一致するbranchだけ採用する

target LLMはtree各nodeに対して「このprefixなら次tokenは何か」を出す。

検証はrootから始める。

現在nodeに、target LLMが選んだtokenと同じtokenを持つchildがあれば、そのchildをacceptして次へ進む。さらにそのchildでも一致するchildがあれば続ける。

一致するchildがなくなったら、その地点でtarget LLM自身が出したtokenを採用して終了する。

したがってSSMの候補は**探索を速めるhint**でしかなく、最終token列はtarget LLMの逐次decodeと一致する。

### 6. KV cacheをbranchごとに複製しない

treeの各branchごとに別KV cacheを持つと、共通prefix分まで複製されmemoryが膨らむ。

SpecInferは深さ優先探索（depth-first search: DFS）順にtreeを辿り、1組のKV cacheを共有しながらbranchに応じて更新する。

共通prefixのK/Vは一度だけ保持し、branchで異なる部分だけを一時的に差し替える。これによりtree候補数が増えてもKV memoryの重複を抑える。

### 7. 学習型schedulerがtreeの大きさを調整する

簡単な文脈ならdraftを深く伸ばした方が得だが、難しい文脈では大きなtreeを作っても外れやすくverification overheadだけ増える。

SpecInferはtarget LLMの最後のhidden featureを入力にする小さな3-layer MLPを使い、各beam width / depth設定で「何tokenくらい連続一致しそうか」を予測する。

候補設定ごとに、

`予想一致token数 / (speculation時間 + verification時間)`

に相当する効率を見積もり、最も得なconfigurationを選ぶ。

つまりdraft tree sizeを固定せず、**今の文脈が予測しやすいかどうかに応じてbranch数と深さを変える**。

## 評価

### まず見るところ

SpecInferのheadline speedupは、draft model自体がtargetより高品質だから生じるのではない。

価値は、**target LLMを呼ぶ回数を減らせること**にある。そのため、target weight accessやGPU間通信、CPU→GPU weight transferが高価な環境ほど効果が大きい。

論文ではtarget LLMのdecode step数を最大4.4倍、平均約3.7倍削減したと報告する。ただしend-to-end speedupはdraft/verification overheadがあるためこれより小さい。

### 条件

| 項目 | 内容 |
|---|---|
| Target models | LLaMA-7B / 65B、OPT-13B / 30B |
| SSM例 | LLaMA-68M、OPT-125Mなど |
| Datasets | CIP、ChatGPT Prompts、WebQA、Alpaca、PIQA |
| Hardware | AWS g5.12xlarge ×2 |
| GPU | 各node 4×NVIDIA A10 24GB |
| CPU / RAM | 各node 48 cores / 192GB |
| Network | 100Gbps Ethernet |
| Runtime | FlexFlowベース |

### 分散LLM推論

modelを複数GPUへ分散する条件では、既存LLM serving systemに対して**1.5〜2.8倍**のend-to-end speedupを報告する。

ここでは1 decode stepごとにmodel-parallel communicationが必要なので、verification step数を減らすと通信回数も減る。

### offloading推論

model weightをCPU DRAM側へ置き、必要weightをGPUへ転送する条件では**2.6〜3.5倍**のspeedupを報告する。

分散GPUより改善幅が大きいのは、1 target stepを減らすたびに高価なCPU→GPU weight transferまで減らせるためである。

これはFlexGenなどのoffloading systemと組み合わせたときにspeculative decodingの価値が特に大きいことを示している。

### treeの大きさには最適点がある

SSM数、beam width、beam depthを増やすとtarget outputをtree内に含む確率は上がる。一方で、tree node数が増えるほどtarget verificationのFLOPsとmemoryも増える。

そのため最大match lengthだけでなく、**1秒あたり何token確定できるか**でtree configurationを選ぶ必要がある。learning-based schedulerはこのtrade-offを扱うためのcomponentである。

## 既存研究との差

### 線形speculative decodingとの違い

通常のdraft-target方式は1本のcandidate sequenceを作る。SpecInferは複数候補をtreeで持つため、早い位置で1候補が外れても別branchがtarget出力と一致していれば検証を続けられる。

### 後続のMedusa / EAGLEとの関係

Medusaはtarget modelへ複数prediction headを付け、外部draft modelなしでtree候補を作る。EAGLEはhidden featureをdraftすることで高いaccept率を狙う。

候補の作り方は違うが、**複数candidate tokenをtreeとしてまとめ、target modelで並列検証する**というsystem形態ではSpecInferが重要な先行例である。

## 限界

- 複数SSMを保持・実行するため追加GPU memoryとcomputeが必要。
- treeを大きくしすぎるとverification FLOPs、KV管理、memoryが増えて逆効果になる。
- speedupはSSMとtargetの一致率に強く依存する。
- collective boost-tuningとmatching-length predictorのoffline trainingが必要な構成がある。
- 主評価はA10 clusterであり、現在のH100/B200世代ではtarget/draftの相対costやmemory-bandwidth balanceが変わる。
- serving concurrencyが非常に高くtarget model自体のbatch効率が十分高い場合、single-request latency中心のspeculation gainがそのままsystem throughput gainにはならない。

## 一般的な実装上の含意

SpecInferから得られる重要な考え方は、speculative decodingの価値を**acceptance rateだけで評価しない**ことである。

systemとして効くのは、

1. 1 target passで平均何token確定するか
2. target pass 1回のweight / communication / offload costがどれだけ高いか
3. draft tree生成とverificationの追加costがどれくらいか
4. treeを増やしたときKV memoryがどれだけ増えるか

の組合せである。

特にweight offloadやdistributed inferenceのように「target modelを1回呼ぶこと自体」が高価な環境では、多少draft側の計算を増やしてもtarget pass回数を減らす価値が大きい。
