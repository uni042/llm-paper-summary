# SpecInfer: Accelerating Generative Large Language Model Serving with Tree-based Speculative Inference and Verification

> 複数の小型draft modelが作る候補token列をtreeへ統合し、target LLMでtree全体を1回に並列検証して、1回のweight読出しで複数tokenを確定するspeculative inference system。

## 問題
通常のautoregressive decodingは1回のtarget LLM forwardで1 tokenしか進まず、特にweight読出し、GPU間activation通信、CPU DRAMからのweight offload転送が律速になる。

## 手法
複数のsmall speculative modelと外部予測器から候補列を作り、共通prefixをtoken treeへ統合する。tree attentionにより全branchをtarget LLMの1回の検証passで処理し、実際のtarget出力と一致した経路から複数tokenを確定する。draft構成は予測一致長と実測costから選択する。target分布に従う検証により生成品質を保つ。

## 評価条件・主要結果
ASPLOS 2024最終版ではLLaMA-7B / 65B、OPT-13B / 30Bをtarget、LLaMA-68M / OPT-125Mをsmall speculative modelとして、CIP、ChatGPT Prompts、WebQA、Alpaca、PIQAを評価する。実験環境は2台のAWS g5.12xlargeで、各4× NVIDIA A10 24GB、48 CPU core、192 GB DRAM、node間100 Gbps Ethernet。

分散LLM推論では既存serving system比1.5〜2.8倍、CPU DRAMへweightを退避するoffloading推論では2.6〜3.5倍の高速化を報告する。token tree verificationは1回のtarget検証で複数候補を並列処理し、target modelのdecode stepとweight / communication access回数を減らす。

## 限界
複数draft modelの保持・実行costが増え、候補treeが大きすぎると検証計算とmemoryが増える。効果はdraftとtargetの一致率に依存する。評価hardwareはA10 cluster中心であり、現行の高速acceleratorで同じ倍率になるとは限らない。

## 既存との差
単一の線形draft列ではなく複数候補をtreeへまとめ、tree全体を並列検証する点が中心。後続のMedusaやEAGLE等でもtree verificationの基礎として参照される。

## 一般的な実装上の含意
weight読出し、GPU間通信、CPU→GPU転送が高価な環境ほど、1回のtarget passで確定できるtoken数を増やす価値が大きい。artifactではserver-grade GPU評価とoffloading評価の両方を再現可能なscriptとして提供している。

## 実装状況
公式実装はFlexFlowへ公開されている。ASPLOS artifact appendixはSpecInfer code、dataset、再現scriptを含むartifactを公開済みとし、Apache License v2.0、CUDA/NCCL/MPI/UCX等の依存とAWS g5.12xlargeによる再現手順を記載する。
