# SpecInfer: Accelerating Generative Large Language Model Serving with Tree-based Speculative Inference and Verification

> SpecInferは、通常なら対象 LLMを1 トークンごとに呼ぶところを、**小さいモデルが先に複数の未来候補を作り、それらを木構造として対象 LLMにまとめて検査させる**ことで、1回の対象-モデル 処理回から複数トークンを確定しようとするシステムである。

## 概要

通常の自己回帰復号（自己回帰 デコード）では、次トークンを1つ生成してからでないと、その次のトークンを確定できない。この依存関係そのものは言語モデルの意味上必要だが、実装上は大きな問題になる。

数十B〜数百B パラメータのLLMでは、1 トークンを出すたびに巨大なモデル 重みをGPU HBMから読み、モデル 並列構成ならGPU間通信も発生する。重みをCPU DRAMへ退避しているシステムなら、さらにCPU→GPU転送まで繰り返す。

つまり「1 トークン進むたびに対象 モデル全体へ1回アクセスする」という構造が重い。

SpecInferは、対象 モデルより40〜100倍程度小さい複数の小型投機モデル（小さい 投機的 モデル: SSM）を先に走らせ、次に来そうなトークンを複数ステップ・複数分岐予測する。それらを共通接頭辞でトークン 木構造へまとめ、**対象 モデルを“次トークン生成器”ではなく“候補木構造の検証器”として1回だけ実行する**。

候補が対象 モデルの本来の出力と長く一致すれば、1回の対象 処理回で2 トークン、3 トークン、場合によってはそれ以上まとめて確定できる。外れた分岐は捨てるので、ドラフト モデルの予測自体を最終出力として信用する必要はない。

## 問題設定

### 通常decodeは1 request内の並列性が小さい

prompt処理では多数トークンを並列計算できる。一方デコードでは、トークン `t+1` を確定するにはトークン `t` の結果が必要なので、1 リクエスト内では基本的に1 トークンずつ進む。

GPUから見ると、各ステップで同じ巨大重みを読みながら処理するトークン数が少ないため、行列 乗算の演算能力よりメモリ 帯域が律速になりやすい。

### 単一draft列だけでは『最初の外れ』に弱い

一般的な投機的復号（投機的 デコード）は、小さいドラフト モデルに数トークンを直列で提案させ、対象 モデルでまとめて検証する。

ただしドラフト列の2 トークン目が外れると、それより後ろのトークンがどれだけよくても使えない。したがってドラフト モデルと対象 モデルの一致率が低い区間では、長い候補列を作っても無駄になりやすい。

SpecInferは1本の線形候補ではなく、**複数の候補分岐を持つ木構造**を作る。ある分岐が外れても、同じ接頭辞から伸びた別分岐が対象出力と一致していれば、そちらへ進める。

### treeをbranchごとに検証したら意味がない

候補を10本作っても対象 LLMを10回実行していたら高速化にならない。

そのためSpecInferのシステム上の核心は、**木構造内の全候補ノードを対象 LLMの1 検証 処理回で処理する木構造 注意**にある。

## 手法

1回のデコード 周期は次のように進む。

1. 現在まで確定したトークン列を複数SSMへ渡す。
2. 各SSMがbeam 探索などで複数の未来トークン列を提案する。
3. 共通接頭辞を共有するように候補列を1つのトークン 木構造へmergeする。
4. 対象 LLMで木構造内の全ノードを並列に順伝播する。
5. 根から対象 LLMの出力と一致する子を辿る。
6. 一致が続いた分だけ複数トークンを一度に確定する。
7. 最初に一致する子がなくなった地点では、対象 LLM自身が出したトークンを1つ採用して次周期へ進む。

したがってドラフトが完全に外れても、対象 LLM自身の正しいnext トークンは必ず得られる。ドラフトが当たったときだけ追加トークンを“無料に近い形”で前倒しできる。

## 手法

### 1. 複数SSMで候補の多様性を作る

単一の小型モデルには容量 gapがあり、対象 LLMと常に同じ続きは出せない。

SpecInferは複数のSSMを使う。OPT-175Bに対するOPT-125M/350Mのように同じモデル familyの小型版を使えるほか、retrievalなどuser-defined 予測器も候補生成器として組み込める。

複数SSMを別GPUで並列実行できれば、SSM数を増やしても投機 遅延自体は大きく伸びない。一方で候補数が増えるほど木構造が大きくなり、対象側の検証 コストは増える。

そのため「候補は多ければ多いほどよい」わけではない。

### 2. 集団boost調整でSSM同士をわざと多様化する

複数SSMが全員同じ箇所で当たり、同じ箇所で外れるなら、複数使う意味が小さい。

SpecInferの集団boost調整（collective boost-tuning）は、SSMを順番にfine-tuneする。

最初のSSMが対象 LLMと正しく一致した学習 標本化を記録し、次のSSMは**まだ前のSSMが当てられていない標本化を重点的に学習する**。これを繰り返すことで、各SSMに異なる“得意区間”を持たせる。

狙いは各SSM単体を最大精度にすることではなく、**複数SSMの候補をunionしたときに対象出力を木構造内へ含む確率を上げること**である。

### 3. 候補列をtoken treeへmergeする

たとえば2つのSSMが

- `The → cat → is → ...`
- `The → cat → was → ...`

を提案した場合、`The → cat` までは同じなので2本を別系列として持つ必要はない。

SpecInferは共通接頭辞を同じノードとして共有し、分岐する地点だけ子を増やす。

これにより重複トークンの検証を減らし、複数候補をcompactに表現できる。

### 4. tree attentionで『各nodeは自分の祖先だけを見る』

普通のcausal 注意では、系列のトークン `j` は自分より前のトークンだけを見る。

Treeでは単純な位置順では不十分である。分岐 Aのトークンが分岐 Bのトークンを見てはいけないからだ。

SpecInferでは木構造 maskを作り、各ノードが

- 既に確定済みの接頭辞
- 根からそのノードまでの祖先ノード

だけへ注意できるようにする。

このmaskを使えば、木構造のノードを大きなバッチのように対象 LLMへ一度に流しても、**各分岐を独立した通常系列として計算した場合と同じ注意依存関係**を再現できる。

これが木構造-基づく 並列 デコードの核である。

### 5. target modelの出力と一致するbranchだけ採用する

対象 LLMは木構造各ノードに対して「この接頭辞なら次トークンは何か」を出す。

検証は根から始める。

現在ノードに、対象 LLMが選んだトークンと同じトークンを持つ子があれば、その子を受理して次へ進む。さらにその子でも一致する子があれば続ける。

一致する子がなくなったら、その地点で対象 LLM自身が出したトークンを採用して終了する。

したがってSSMの候補は**探索を速めるhint**でしかなく、最終トークン列は対象 LLMの逐次デコードと一致する。

### 6. KV cacheをbranchごとに複製しない

木構造の各分岐ごとに別KV キャッシュを持つと、共通接頭辞分まで複製されメモリが膨らむ。

SpecInferは深さ優先探索（depth-first 探索: DFS）順に木構造を辿り、1組のKV キャッシュを共有しながら分岐に応じて更新する。

共通接頭辞のK/Vは一度だけ保持し、分岐で異なる部分だけを一時的に差し替える。これにより木構造候補数が増えてもKV メモリの重複を抑える。

### 7. 学習型schedulerがtreeの大きさを調整する

簡単な文脈ならドラフトを深く伸ばした方が得だが、難しい文脈では大きな木構造を作っても外れやすく検証 オーバーヘッドだけ増える。

SpecInferは対象 LLMの最後の隠れ 特徴量を入力にする小さな3-層 MLPを使い、各beam width / depth設定で「何トークンくらい連続一致しそうか」を予測する。

候補設定ごとに、

`予想一致token数 / (speculation時間 + verification時間)`

に相当する効率を見積もり、最も得なconfigurationを選ぶ。

つまりドラフト 木構造 サイズを固定せず、**今の文脈が予測しやすいかどうかに応じて分岐数と深さを変える**。

## 評価

### まず見るところ

SpecInferのheadline 高速化倍率は、ドラフト モデル自体が対象より高品質だから生じるのではない。

価値は、**対象 LLMを呼ぶ回数を減らせること**にある。そのため、対象 重み accessやGPU間通信、CPU→GPU 重み 転送が高価な環境ほど効果が大きい。

論文では対象 LLMのデコード ステップ数を最大4.4倍、平均約3.7倍削減したと報告する。ただしエンドツーエンド 高速化倍率はドラフト/検証 オーバーヘッドがあるためこれより小さい。

### 条件

| 項目 | 内容 |
|---|---|
| Target モデル | LLaMA-7B / 65B、OPT-13B / 30B |
| SSM例 | LLaMA-68M、OPT-125Mなど |
| Datasets | CIP、ChatGPT Prompts、WebQA、Alpaca、PIQA |
| Hardware | AWS g5.12xlarge ×2 |
| GPU | 各ノード 4×NVIDIA A10 24GB |
| CPU / RAM | 各ノード 48 cores / 192GB |
| Network | 100Gbps Ethernet |
| ランタイム | FlexFlowベース |

### 分散LLM推論

モデルを複数GPUへ分散する条件では、既存LLM 提供 システムに対して**1.5〜2.8倍**のエンドツーエンド 高速化倍率を報告する。

ここでは1 デコード ステップごとにモデル-並列 communicationが必要なので、検証 ステップ数を減らすと通信回数も減る。

### offloading推論

モデル 重みをCPU DRAM側へ置き、必要重みをGPUへ転送する条件では**2.6〜3.5倍**の高速化倍率を報告する。

分散GPUより改善幅が大きいのは、1 対象 ステップを減らすたびに高価なCPU→GPU 重み 転送まで減らせるためである。

これはFlexGenなどのオフロード システムと組み合わせたときに投機的 デコードの価値が特に大きいことを示している。

### treeの大きさには最適点がある

SSM数、beam width、beam depthを増やすと対象 出力を木構造内に含む確率は上がる。一方で、木構造 ノード数が増えるほど対象 検証のFLOPsとメモリも増える。

そのため最大match lengthだけでなく、**1秒あたり何トークン確定できるか**で木構造 configurationを選ぶ必要がある。学習-基づく スケジューラはこのtrade-offを扱うための構成要素である。

## 既存研究との差

### 線形speculative decodingとの違い

通常のドラフト-対象方式は1本の候補 系列を作る。SpecInferは複数候補を木構造で持つため、早い位置で1候補が外れても別分岐が対象出力と一致していれば検証を続けられる。

### 後続のMedusa / EAGLEとの関係

Medusaは対象 モデルへ複数予測 ヘッドを付け、外部ドラフト モデルなしで木構造候補を作る。EAGLEは隠れ 特徴量をドラフトすることで高い受理率を狙う。

候補の作り方は違うが、**複数候補 トークンを木構造としてまとめ、対象 モデルで並列検証する**というシステム形態ではSpecInferが重要な先行例である。

## 限界

- 複数SSMを保持・実行するため追加GPU メモリと計算が必要。
- 木構造を大きくしすぎると検証 FLOPs、KV管理、メモリが増えて逆効果になる。
- 高速化倍率はSSMと対象の一致率に強く依存する。
- collective boost-tuningとmatching-length 予測器のoffline 学習が必要な構成がある。
- 主評価はA10 clusterであり、現在のH100/B200世代では対象/ドラフトの相対コストやメモリ-帯域 balanceが変わる。
- 提供 concurrencyが非常に高く対象 モデル自体のバッチ効率が十分高い場合、single-リクエスト 遅延中心の投機 gainがそのままシステム スループット gainにはならない。

## 一般的な実装上の含意

SpecInferから得られる重要な考え方は、投機的 デコードの価値を**受理率 率だけで評価しない**ことである。

システムとして効くのは、

1. 1 対象 処理回で平均何トークン確定するか
2. 対象 処理回 1回の重み / communication / オフロード コストがどれだけ高いか
3. ドラフト 木構造生成と検証の追加コストがどれくらいか
4. 木構造を増やしたときKV メモリがどれだけ増えるか

の組合せである。

特に重み オフロードやdistributed inferenceのように「対象 モデルを1回呼ぶこと自体」が高価な環境では、多少ドラフト側の計算を増やしても対象 処理回回数を減らす価値が大きい。
