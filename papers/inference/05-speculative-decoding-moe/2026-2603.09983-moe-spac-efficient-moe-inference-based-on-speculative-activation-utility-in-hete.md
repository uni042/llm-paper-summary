# MoE-SpAc: Efficient MoE Inference Based on Speculative Activation Utility in Heterogeneous Edge Scenarios

> MoE-SpAcは、投機的復号で先に見える専門家需要を集計し、VRAMに残す専門家・先読みする重み・CPUで計算する専門家を制約付きで同時に配置して、端末の転送待ちを減らす。

## 概要
MoE-SpAcは、speculative デコードで先に見えるfuture トークンのルーティング情報を、**エキスパート キャッシュ / 先読み / CPU-GPU配置を決めるための予測信号として再利用する**edge向けsystemである。

この予測は、将来の需要を完全に言い当てることを目的としない。限られたVRAMと帯域の中で、どの重みを残し、どれを先に運び、どれをCPUで処理するかの優先順位を改善するために使う。外れた場合は正しいエキスパートを追加で読み込む必要があるため、利得は予測の当たりやすさと転送を計算に重ねられる時間に左右される。

通常のデコードでは1 step先のルータ情報しか得られないが、speculative verificationでは複数draft トークンについてtarget側のエキスパート 活性値をまとめて観測できる。MoE-SpAcはこの「少し先の需要」を、各エキスパートを近い将来どれだけ使いそうかという優先度へ変換する。

その優先度を基に、

- GPUへ常駐させるエキスパート
- CPUで直接計算するエキスパート
- 先に転送するエキスパート
- GPU キャッシュから追い出すエキスパート

を一つの方針で決める。

つまりspeculative デコードをトークン生成高速化だけに使わず、**メモリ管理のために将来のエキスパート需要を先に知る仕組みとして使う**のが主眼である。

RTX 4090上のQwen3-30B-A3B／DeepSeek-V2-Lite評価では、SOTA speculative decoding比較対象比+42% TPS、通常比較対象群比平均4.04倍、Qwen3ではllama.cpp+SD／HybriMoE比+52.9% TPSを報告する。targetのnative routing／verificationを変えず、target検証で候補を確定する無損失範囲の結果である。

## 手法

### 1. `Speculative Utility Estimator`：近い将来どのexpertが必要かを点数化する

speculative verificationで先に確認できたトークン列から、どのエキスパートが何回使われそうかを集計し、各エキスパートの優先度を更新する。

単純なLRUやglobal popularityと違い、**過去に何度使ったかだけでなく、draftが示す近い将来の需要**を使う。

### 2. 同じ優先度をcache / prefetch / evictionへ共通利用する

キャッシュに残す基準、先読みする基準、追い出す基準を別々に作ると、同じエキスパートを一方では残し、別の判断では追い出すといった競合が起きやすい。

MoE-SpAcでは同じ優先度を使い、

- 近く使う可能性が高いエキスパート → GPUに残す、または先に転送する
- 近く使う可能性が低いエキスパート → GPUから追い出す、またはCPUで実行する

と判断する。

同じutilityを共有することで、キャッシュ policyと先読み policyが互いに打ち消すのを防げる。例えば近い将来何度も使うと予測したエキスパートを先読みした直後に、過去利用だけを見るLRUが追い出してしまえば転送が無駄になる。逆に将来需要が低いエキスパートをキャッシュへ残すために、必要エキスパートの先読み領域を圧迫する可能性もある。将来の活性値回数を共通の価値尺度にすることで、常駐容量とPCIe帯域を同じエキスパート需要へ向けられる。

### 3. CPUとGPUのどちらでexpertを処理するかも同時に決める

各エキスパートについて、CPUでそのまま計算する場合と、GPUへ重みを送ってGPUで計算する場合の所要時間を比較する。

判断には、

- VRAM容量
- CPU エキスパート実行時間
- GPU エキスパート実行時間
- PCIe 帯域
- 先読みできる時間

などを使う。

目的は、CPUかGPUの一方だけを忙しくするのではなく、**両方の処理ができるだけ同じ頃に終わるように仕事を分け、遅い側の待ち時間を減らすこと**である。

ここでGPU実行が常に最善とは限らない。GPUにないエキスパートは重み全体をPCIeで転送してからGEMMする必要があり、トークン数が少ないエキスパートではそのtransfer costがCPU上で直接計算する時間を上回る場合がある。反対に多くのトークンが集まるエキスパートではCPU GEMMが長くなり、転送を払ってもGPUで処理した方が早い。MoE-SpAcはspeculative windowから将来のトークン数も見積もり、エキスパートごとのCPU計算・GPU計算・転送時間を同じ配置問題へ入れる。

### 4. 配置と実行場所を制約付きの組み合わせ問題として解く

エキスパートごとに「GPUへ置く」「CPUで実行する」「先に転送する」といった選択肢があり、同時にVRAM容量やPCIe帯域の上限もある。

MoE-SpAcはこれを単純な順位順ではなく、**限られたメモリと帯域の中で全エキスパートの配置・実行場所をまとめて選ぶ問題**として解く。

この組み合わせは、あるエキスパートをGPUへ載せる判断が他エキスパートのVRAMとPCIe機会を奪うため独立には決められない。論文はonline integer optimizationで全体の完了時間を小さくする配置を選び、speculative utilityの高いエキスパートへ優先的に高速資源を割り当てる。毎エキスパートを個別のthresholdで処理するより、GPU capacityを超えないこととCPU/GPU ワークロード balanceを同時に保証しやすい。

これにより、GPUへ送るよりCPUでそのまま計算した方が早いエキスパートも選べる。

### 5. 転送とCPU/GPU計算を非同期に重ねる

実際の実行時では、

- draft generation
- target verification
- 重み transfer
- CPU エキスパート compute
- GPU エキスパート compute

をできるだけ同時並行で進める。

将来需要の予測だけ良くても、各処理を順番に待つ実装では効果が小さいため、**転送待ちを別の計算の裏へ隠す実行engine**が重要になる。

非同期engineは、draftが次のエキスパート需要を示した時点でtransferを発行し、現在のtarget/draft計算やCPU エキスパート computeと並行させる。native ルーティングが確定するまで何もしない方式では、せっかくspeculative デコードで得たlookahead時間を使えない。予測miss時には正しいエキスパートの追加transferが必要になるが、hitしたエキスパートについてはそのI/Oの大部分を前段computeへ重ねられるため、utility predictionを実際の遅延削減へ変換できる。

### 6. Native routingは変えない

エキスパートを別エキスパートへ置換する方式ではなく、**正しいnative エキスパートをどこで・いつ実行するか**だけを変える。

したがってresource スケジューリング自体は無損失である。

## 評価

このため、需要予測の精度だけでなく、配置判断と非同期実行を一体で評価することが重要になる。
予測と実行の両方がそろって初めて、待ち時間の短縮として現れる。
したがって、配置の正しさと処理の重なりを併せて見る必要がある。
特に小さなバッチでは、転送の固定費とCPU計算の速さが判断を左右する。
そのため、平均スループットだけでなく、需要が外れたときの追加転送と待ち時間も併記するのが望ましい。

### まず見るところ
- **結論:** speculative デコードで少し先に分かるエキスパート需要を使うと、キャッシュ・先読み・CPU/GPU分担を別々に決めるより効率よく協調できる。
- **実速度:** RTX 4090実機で既存speculative デコード / heterogeneous実行比較対象を大幅に上回る。
- **品質:** target verificationとnative エキスパートを維持するため**無損失 スケジューリング**。
- **注意点:** draft トークンの受理率、CPU/GPU性能差、PCIe帯域が変わると先読み情報の価値も変わる。

native target verificationとnative エキスパート実行を保つため、キャッシュ/先読み policy自体でmodel出力は変えない。

### 制約

- draft acceptanceが低いと、先に見えるエキスパート需要が実際の生成と一致しにくくなる。
- speculative windowが短いと先読み時間が不足する。
- CPU/GPU性能比とPCIe帯域へ強く依存。
- 配置の組み合わせ計算と非同期実行時の実装コストがある。
- 複数リクエストが同時に走ったときの資源競合、SSD tier、energy/トークンは十分評価されていない。
