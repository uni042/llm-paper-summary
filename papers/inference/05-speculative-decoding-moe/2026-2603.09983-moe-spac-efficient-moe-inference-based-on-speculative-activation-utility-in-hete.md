# MoE-SpAc: Efficient MoE Inference Based on Speculative Activation Utility in Heterogeneous Edge Scenarios

> speculative decodingで少し先に見えるexpert需要を利用し、どのexpertをGPUへ残す・先読みする・CPUで実行するかをまとめて決めるedge向けMoE推論方式。

## 概要
MoE-SpAcは、speculative decodingで先に見えるfuture tokenのrouting情報を、**expert cache / prefetch / CPU-GPU配置を決めるための予測信号として再利用する**edge向けsystemである。

通常のdecodeでは1 step先のrouter情報しか得られないが、speculative verificationでは複数draft tokenについてtarget側のexpert activationをまとめて観測できる。MoE-SpAcはこの「少し先の需要」を、各expertを近い将来どれだけ使いそうかという優先度へ変換する。

その優先度を基に、

- GPUへ常駐させるexpert
- CPUで直接計算するexpert
- 先に転送するexpert
- GPU cacheから追い出すexpert

を一つの方針で決める。

つまりspeculative decodingをtoken生成高速化だけに使わず、**memory管理のために将来のexpert需要を先に知る仕組みとして使う**のが主眼である。

## 手法のあらまし

### 1. `Speculative Utility Estimator`：近い将来どのexpertが必要かを点数化する

speculative verificationで先に確認できたtoken列から、どのexpertが何回使われそうかを集計し、各expertの優先度を更新する。

単純なLRUやglobal popularityと違い、**過去に何度使ったかだけでなく、draftが示す近い将来の需要**を使う。

### 2. 同じ優先度をcache / prefetch / evictionへ共通利用する

cacheに残す基準、先読みする基準、追い出す基準を別々に作ると、同じexpertを一方では残し、別の判断では追い出すといった競合が起きやすい。

MoE-SpAcでは同じ優先度を使い、

- 近く使う可能性が高いexpert → GPUに残す、または先に転送する
- 近く使う可能性が低いexpert → GPUから追い出す、またはCPUで実行する

と判断する。

### 3. CPUとGPUのどちらでexpertを処理するかも同時に決める

各expertについて、CPUでそのまま計算する場合と、GPUへ重みを送ってGPUで計算する場合の所要時間を比較する。

判断には、

- VRAM容量
- CPU expert実行時間
- GPU expert実行時間
- PCIe bandwidth
- 先読みできる時間

などを使う。

目的は、CPUかGPUの一方だけを忙しくするのではなく、**両方の処理ができるだけ同じ頃に終わるように仕事を分け、遅い側の待ち時間を減らすこと**である。

### 4. 配置と実行場所を制約付きの組み合わせ問題として解く

expertごとに「GPUへ置く」「CPUで実行する」「先に転送する」といった選択肢があり、同時にVRAM容量やPCIe帯域の上限もある。

MoE-SpAcはこれを単純な順位順ではなく、**限られたmemoryと帯域の中で全expertの配置・実行場所をまとめて選ぶ問題**として解く。

これにより、GPUへ送るよりCPUでそのまま計算した方が早いexpertも選べる。

### 5. 転送とCPU/GPU計算を非同期に重ねる

実際のruntimeでは、

- draft generation
- target verification
- weight transfer
- CPU expert compute
- GPU expert compute

をできるだけ同時並行で進める。

将来需要の予測だけ良くても、各処理を順番に待つ実装では効果が小さいため、**転送待ちを別の計算の裏へ隠す実行engine**が重要になる。

### 6. Native routingは変えない

expertを別expertへ置換する方式ではなく、**正しいnative expertをどこで・いつ実行するか**だけを変える。

したがってresource scheduling自体はlosslessである。

## 評価

### まず見るところ
- **結論:** speculative decodingで少し先に分かるexpert需要を使うと、cache・prefetch・CPU/GPU分担を別々に決めるより効率よく協調できる。
- **実速度:** RTX 4090実機で既存speculative decoding / heterogeneous実行baselineを大幅に上回る。
- **品質:** target verificationとnative expertを維持するため**lossless scheduling**。
- **注意点:** draft tokenの受理率、CPU/GPU性能差、PCIe帯域が変わると先読み情報の価値も変わる。

### 主要throughput結果

| 比較 | 改善 |
|---|---:|
| SOTA speculative baseline比 | **+42% TPS** |
| 通常baseline群比 | 平均 **4.04×** |
| Qwen3: llama.cpp + SD / HybriMoE比 | 平均 **+52.9% TPS** |

### Latency

Qwen3条件ではlatencyを平均約45.6%削減。

### 何が効いているか

| 機構 | 役割 |
|---|---|
| Future-demand score | speculative tokenから近い将来のexpert需要を予測 |
| Cache policy | 近く使うexpertをGPUへ残す |
| CPU/GPU分担 | 転送するよりCPU実行が得なexpertを選ぶ |
| 非同期実行 | transfer / compute / verificationを重ねる |

### 品質

native target verificationとnative expert実行を保つため、cache/prefetch policy自体でmodel出力は変えない。

### 制約

- draft acceptanceが低いと、先に見えるexpert需要が実際の生成と一致しにくくなる。
- speculative windowが短いと先読み時間が不足する。
- CPU/GPU性能比とPCIe帯域へ強く依存。
- 配置の組み合わせ計算と非同期runtimeの実装コストがある。
- 複数requestが同時に走ったときの資源競合、SSD tier、energy/tokenは十分評価されていない。
