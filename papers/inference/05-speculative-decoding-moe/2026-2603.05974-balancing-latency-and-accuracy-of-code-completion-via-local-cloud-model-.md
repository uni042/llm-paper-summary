# Balancing Latency and Accuracy of Code Completion via Local-Cloud Model Cascading

> 端末の小規模モデルを既定とし、信頼度と利用者の拒否行動で大規模モデルへ切り替えるカスケード補完で、遅延を最大47.9パーセント減らしながら完全一致率を平均8.9パーセント上げる。

## 概要

行単位のコード補完は、開発者が入力するそばから現在の行の続きを提案する機能であり、提案が遅れると開発者は待たずに打ち続けて提案が無駄になり、精度が低いと信頼を失う。調査では開発者の44パーセントが文単位の補完を0.5秒以内に期待し、45パーセントが低品質な補完を現行ツールの最大の問題に挙げる。静的解析の方式は単一トークンには速いが複数トークンの生成に弱く、クラウドの大規模言語モデルは高品質だが推論の遅延と費用が大きく、端末の小規模モデルは速いが複雑な場面で精度が足りない。本論文のMCComは、端末に置いた小規模モデルを既定とし、大規模モデルは必要なときだけ呼ぶモデルカスケードでこの交換を解く。

呼び分けが本論文の核である。生成中は小規模モデルの先頭3トークンの平均確率を信頼度として閾値0.8と比べ、低ければ大規模モデルへ回す。生成後は、提案を受け入れずに打ち続ける、削除するといった利用者の行動を暗黙の拒否とみなし、その場合にだけ大規模モデルを呼ぶ。協調の仕組みは二つある。一つは二段の投機的デコードで、文脈中の一致から作った下書きで小規模モデル自身を速くし、拒否された小規模モデルの出力を大規模モデルの下書きとして再利用する。もう一つは反復検索で、拒否された出力を手掛かりにリポジトリから関連コードを取り直し、大規模モデルの入力を豊かにする。使える小規模モデルが公開に無かったため、著者らは121Mパラメータのモデルを新たに学習し、最先端の7Bモデルの平均73.8パーセントの性能を得ている。

**代表結果:** RepoEvalと、行を完全な文として扱い挿入位置を無作為化した新設のStmtEvalで、MCComは大規模モデルだけの方式より推論遅延を5.8から47.9パーセント減らし（平均25.6パーセント）、大規模モデルの使用量を平均46.3パーセント削減しながら、完全一致率が2.9から13.5パーセント、平均8.9パーセント改善した。速くなるだけでなく、反復検索で大規模モデルの入力が良くなるため精度も上がる点が特徴である。

## 問題設定

ボトルネックは、対話的な補完における往復の遅延と、大規模モデルの呼び出し費用である。クラウド呼び出しにはネットワークの約200ミリ秒という前提が置かれ、補完のたびに払えば体感の遅延を支配する。一方で小規模モデルだけで済ませると、複雑で曖昧な場面での誤りが残る。著者らの観測では、学習した121Mの小規模モデルは検索なしでも検証集合の37.8パーセントを正解でき、端末上ではA800上の7Bモデルの2倍速い。つまり相当な割合の補完は小規模モデルで足り、カスケードの余地がある。難しさは二点ある。第一に、いつ大規模モデルへ切り替えるかであり、積極的すぎれば遅延が戻り、控えめすぎれば精度を落とす。第二に、切り替えたときに小規模モデルの仕事を無駄にしない協調であり、下書きと検索の手掛かりとして再利用できなければ、カスケードは単なるやり直しになる。さらに、補完候補同士の重なりという観測が協調を支える。小規模モデルの補完の14.4パーセントは左文脈にも現れ、大規模モデルの出力との編集類似度は平均78.4パーセントあり、下書きとして使い回せるだけの一致がある。

## 手法のあらまし

補完の開始では、現在の文脈からリポジトリ内の関連コード断片をBM25で検索する。端末側では、補完位置の直前の行と文脈や検索断片との一致を探し、一致した行の次の文を下書きとして小規模モデルが投機的デコードで生成する。生成中の信頼度が低ければ大規模モデルへ回し、生成された提案は利用者へ即座に示される。利用者が受け入れれば終了する。拒否されれば、拒否された出力を手掛かりに検索をやり直して断片を選び直し、クラウド側の大規模モデルが小規模モデルの出力を下書きとして投機的デコードで最終の補完を作る。つまり小規模モデルの出力は、成功すればそのまま答えになり、失敗しても下書きと検索クエリとして二重に再利用される。

## 手法

### 1. 振る舞い駆動のルーティング — 信頼度と利用者の拒否で切り替える

この機構が観測するのは、小規模モデルが生成した先頭の数トークンの確率と、提案に対する利用者の行動である。保持する状態は信頼度の閾値であり、処理は二段構えである。生成中は先頭Nトークンの平均確率を信頼度とし、閾値を超えれば端末側の生成を受け入れ、下回れば大規模モデルへ回す。感度分析でNは3に決められ、Nが1では精度が0.41と低く、4や5へ増やすとF1の伸びはわずかなのに1トークンあたり約18ミリ秒の遅延が増えるためである。生成後は、タブキーでの受け入れを終了の合図とし、打ち続ける行動を暗黙の拒否として大規模モデルを呼ぶ。これにより減るボトルネックは大規模モデルの呼び出し回数とそれに伴う往復遅延であり、平均46.3パーセントの使用量削減として現れた。追加費用は信頼度の計算だけでほぼ無視できる。誤った場合の挙動として、信頼度が高くても誤った提案は利用者の拒否で救済される一方、利用者が誤った提案を受け入れてしまう場合はカスケードでは検出できない。また小規模モデルが弱いと拒否が増えて切り替えが頻発し、利得が痩せることが限界として明記される。

### 2. 二段の投機的デコード — 文脈の一致と小規模モデルの出力を下書きにする

この機構が観測するのは、補完位置の直前の行と、文脈および検索断片の中の過去の出現である。保持する状態は一致した行の後継文であり、処理は一段目と二段目で異なる。一段目では、直前の非空行を文脈と検索断片から探し、見つかればその次の非空でコメントでない文を下書きとし、小規模モデルがその下書きを並列に検証しながら生成する。行の途中まで書かれた補完では、現在の断片で始まる行を探して残りの接尾辞を下書きにする。下書き作りは完全一致の探索であり、別の神経モデルを使う場合の下書き遅延を持たない。二段目では、拒否された小規模モデルの出力そのものが大規模モデルの下書きになり、大規模モデルは1回の順伝播で複数トークンを検証し、最初に食い違った位置から生成を再開する。これにより減るボトルネックは、逐次生成のトークンごとの順伝播であり、除去実験では小規模モデル側の投機的デコードで遅延が19.3パーセント減り、両段を外すと遅延が17.6から41.9パーセント増える。追加費用は検証の計算であり、下書きが外れるほど検証の無駄が増えるが、正しさは大規模モデルの検証で担保される無損失型の加速である。

### 3. 反復検索 — 拒否された出力を大規模モデルの文脈作りに使う

この機構が観測するのは、拒否された小規模モデルの出力が含む意味的な手掛かりである。保持する状態は、リポジトリの他ファイルを空行で区切った検索コーパスと、初回検索のスコアである。処理は、初回は左文脈の末尾と右文脈の先頭を連結したクエリでBM25により上位の断片を取る。拒否後は、小規模モデルの出力だけで別にスコアを計算し、元の文脈のスコアと、小規模モデルの信頼度で重み付けして正規化した上で合算し、断片を選び直す。信頼度で重みを調整するのは、低信頼の出力が誤った方向へ検索を引っ張る悪影響を抑えるためである。論文中の例では、小規模モデルも大規模モデルも単独では正解できなかった補完が、誤った出力に文字列リテラル1つの違いしかないことに着目し、その出力をクエリにすることで正解と完全一致する断片を引き当て、大規模モデルが正解へ到達した。これにより減るボトルネックは計算ではなく、大規模モデルが文脈不足で誤る精度側の損失である。除去実験では反復検索により平均1.2パーセント、RepoEvalのAPI課題では1.9パーセントの改善があり、費用は平均7ミリ秒と小さい。誤った場合として、インポート文の補完などでは無関係な内容を引くことがあり、RepoEvalの行課題では利得がわずかにとどまる。

### 4. 専用に学習した121Mの小規模モデル — カスケードの土台を作る

この機構が観測するのは、公開の小規模コード補完モデルが要件を満たさないという前提である。保持する状態は学習済みの121Mパラメータのモデルであり、処理はThe Stack V2のPython部分から作った4,100万件の行単位補完で学習することである。構造はLLaMA系で語彙を16,256へ絞り、70Mから0.2Bまでの4規模を試して0.1B級が効率と精度の釣り合いで最良と判断された。学習は次のトークン予測を1割、文の途中を埋める形式を9割とし、事前学習の後に合成コードを混ぜた部分集合で微調整する。これにより得られるのは、端末で7Bモデルの2倍速く動き、平均で7Bモデルの73.8パーセントの性能を持つ土台であり、カスケードの節約幅はこの土台の強さに比例する。追加費用は一度きりの学習であり、弱い土台では拒否と切り替えが増えて全体の利得が消える関係が限界の節で明言される。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| ルーティング | 先頭3トークンの確率と利用者行動 | 閾値と拒否で大規模モデルへ切替 | 呼び出し回数と往復遅延 | 受け入れられた誤りは検出できない |
| 一段目の投機的デコード | 直前の行の一致 | 後継文を下書きに小規模モデルが検証 | 端末側の逐次生成 | 一致が無い場面では効かない |
| 二段目の投機的デコード | 拒否された出力 | 大規模モデルが下書きを並列検証 | クラウド側の生成遅延 | 外れた下書きは検証が無駄になる |
| 反復検索 | 拒否された出力と信頼度 | 重み付き再スコアで断片を選び直す | 大規模モデルの文脈不足 | 誤出力が検索を引っ張る場合がある |

## 評価

結論は、カスケードが単なる費用削減ではなく、遅延の削減と精度の改善を同時に達成できる、というものである。大規模モデルだけの方式と比べ、遅延は左右文脈がある条件で11.4から47.9パーセント減り、完全一致率は平均8.9パーセント上がった。精度が上がる理由は反復検索であり、小規模モデルの失敗が大規模モデルの文脈を改善する情報に変わるためである。小規模モデルを2回呼ぶ方式と比べると、遅延は17.5パーセント増えるが完全一致率は平均29.1パーセント改善し、大規模モデルを2回呼ぶ方式と比べると遅延を平均53.6パーセント減らして完全一致率の低下は1.0パーセントにとどまる。検索を反復するRepoCoderと比べても、完全一致率で3.3から12.6パーセント上回り遅延も小さい。読み方として、左文脈だけの条件では利得が痩せる。RepoEvalのAPI課題のように小規模モデルの精度が低い場面では大規模モデルの呼び出しが減らず、遅延の改善が小さくなることが報告され、カスケードの利得が土台の精度に条件付けられることが分かる。検索器の選択では、BM25が密な検索器と完全一致率で互角でありながら遅延は7ミリ秒対約65ミリ秒であり、対話的な補完では疎な検索で足りることも示された。

## 既存研究との差

モデルカスケードやモデルルーティングの先行研究は、どのモデルへ回すかを決めるが、中間の応答を捨てるのが普通だった。本論文の差は、対話的な補完という場面で、利用者の暗黙のフィードバックを切り替え信号として使うことと、拒否された応答を下書きと検索の手掛かりとして再利用することにある。RepoCoderの反復検索は大規模モデルだけで検索と生成を繰り返すのに対し、本論文は端末の小規模モデルの出力を反復の起点にする。CSDraftingのカスケード投機的デコードは全モデルを同じ装置に置き小規模モデルを下書き専用とするのに対し、本論文は小規模モデルを利用者へ直接応答する主体として扱い、端末とクラウドに分ける。

## 限界・実装状況

限界は、小規模モデルが弱い場合に利得が痩せること、評価がPythonの行単位補完に限られること、端末側にRTX 3080Ti級を仮定しており一般の開発者環境より高い可能性があること、大きな粒度の補完は未評価であることである。言語に依存しない設計であることは述べられるが、多言語の評価は高品質な端末向けモデルの不足から行われていない。実装状況は、公式コードとデータが公開され、論文はPACMSEに掲載された版であり、DOIが付与されている。小規模モデルの学習手順とデータの前処理も本文に詳しく記される。

## 一般的な実装上の含意

対話的なシステムでは、利用者の行動そのものが無料で信頼できる品質信号になる場合があり、モデルの自己申告の信頼度と組み合わせると、切り替え判定を学習なしに構成できる。またカスケードでは、弱いモデルの失敗出力を捨てずに、強いモデルの下書きと検索クエリへ転用すると、失敗が費用でなく情報に変わる。切り替えの利得は弱いモデルの絶対性能に比例するため、カスケードの設計と土台モデルの整備は一体で考える必要がある。
