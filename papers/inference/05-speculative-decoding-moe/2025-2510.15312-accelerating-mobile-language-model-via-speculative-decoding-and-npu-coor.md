# Accelerating Mobile Language Model via Speculative Decoding and NPU-Coordinated Execution

## 概要

sd.npuは、スマートフォン上で検索拡張生成（retrieval-augmented generation; RAG）を動かすとき、モバイル神経処理装置（neural processing unit; NPU）の演算器を使い切れない問題を、実行時制御と推測復号（speculative decoding）の両側から解決するシステムである。検索済み文書を大量に読む文脈処理（prefill）は長い入力をまとめて計算する一方、回答生成の復号（decode）は通常1トークンずつ進む。モバイルNPUは固定形状の計算グラフを前提にするため、この二つを同じグラフで効率良く処理できず、切替に大きな遅延が発生する。

さらにNPUは大きな行列を一度に処理する設計なので、1トークンずつの復号ではメモリ律速になり演算器が遊休する。既存の検索型推測復号は検索文書から後続トークンを予測してまとめて検証するが、検索文書の語彙表現がモデルの実際の出力とずれるため棄却が多く、推測列も短い。論文では単純なグラフ切替が文脈長1Kの復号遅延の29%を占め、検索型推測復号では検証演算の22%が棄却分、70%以上の演算能力が十分に使われていないと分析する。

提案システムは三つの機構を組み合わせる。第一に、モデルを連続した層ブロックへ分け、分割文脈処理の計算と復号用グラフの読込を重ねる段階的グラフ切替。第二に、文脈処理で得た出力確率を再利用し、検索文書の表現をモデルが好むトークン列へ近づける文脈内分布校正。第三に、以前棄却された推測列のうち後続ステップで再利用できる部分を検出し、NPUが効率良く処理できる長さまで検証列を伸ばす推測列延長である。

Redmi K60 Pro、Redmi K70 Pro、OnePlus 13上でQwen2.5-0.5B/1.5BとLLaMA3.2-3Bを動かし、文書要約、検索質問応答、画面操作、短文返信を測定した。比較方式と端末・モデル条件に応じ、トークン当たり遅延で1.06〜3.81倍、エネルギー消費で1.07〜4.71倍の改善を報告する。品質を変える近似生成ではなく、通常の推測復号と同様に検証器の受理規則で出力を確定する点も重要である。

## 問題設定

モバイルNPUは、行列演算器を高密度に使うために入力形状、演算計画、バッファ配置を事前に固定した計算グラフを利用する。文脈処理では128または256トークン程度の入力をまとめて扱えるが、復号では通常1トークンだけを処理する。大きい文脈処理グラフを1トークンに流用するとパディングによる無駄が増え、論文の測定では最大8倍遅くなる。反対に復号専用グラフへ切り替えるには、文脈処理用グラフを外して復号用の重み・計算計画を読み込む必要がある。両方を常駐させるだけの端末メモリは必ずしもない。

通常の推測復号では、軽い下書き器が複数トークンを予測し、大きい検証器が一度に受理可能な接頭辞を決める。ところがモバイル端末に別の下書きモデルを常駐させるとメモリと電力が増える。検索拡張生成では元文書を下書きの供給源にできるが、文書の語彙表現とモデルが出したい語列が一致しないと、意味が近くても最初の不一致以降が棄却される。論文の観測では推測候補の75%以上が8トークン未満で、NPUの行列タイルを効率良く使う32トークン程度に届かない。

著者らはNPUの検証実行時間が一定の長さまでほぼ一定になる「一定費用領域」に注目する。この領域では、検証した候補の長さより**実際に受理されたトークン数**が性能を左右する。短い推測列や低い受理率では、検証1回分の固定費を払っても有効な出力が少ない。したがってグラフ切替だけを高速化しても復号の遊休が残り、推測列だけを長くしても棄却が増えるという二重の課題がある。

## 手法

### 1. モデル分割と段階的グラフ切替

初期化時にLLMを連続したTransformer層からなる複数ブロックP1〜PNへ分け、各ブロックの文脈処理用グラフG1と復号用グラフG2について、実機で計算時間と読込時間を測る。実行時には長い検索文脈を固定長の塊へ分割して処理する。通常方式は全塊の文脈処理を終えてからG2を一括読込するため、その間NPUが復号を始められない。

sd.npuは塊を処理している間に、既に切替可能な後段ブロックからG2へ段階的に読み込む。論文の6ブロック・2塊の例では、P1とP2をG1で計算している間にP6のG2を読込み、次のP3とP4の計算中にP5のG2を読込む。G2へ切り替わった後段ブロックは、長い塊をG2の入力形状に合う小塊へ分け、同じ処理を繰り返して文脈処理の結果を保つ。この計算上の等価性により、文脈処理がまだ続く段階から復号用グラフの準備を進められる。

どのブロックの読込をどの計算に重ねるかは、事前計測値を使って決める。対象ブロックjの読込時間が次のk個の計算時間の合計以下になる最小のkを選び、読込を隠蔽できる区間へ割り当てる。ブロックの並べ替えを含む最適な重ね合わせ問題は難しいため、著者らはこの貪欲規則を採用する。読込が計算より長ければ完全隠蔽できず、細かい分割はグラフ管理の複雑さを増やす。実機評価では2ブロック分割で十分に切替費用を隠せたため、N=2を共通設定にしている。

### 2. 文脈内分布校正

検索文書の原文をそのまま下書きに使うと、検証モデルの好む語順・語彙と一致せず棄却が増える。sd.npuは、文脈処理で各位置の次トークン確率が既に計算されていることを利用する。各位置の上位候補から「現在の文脈トークン→モデルが出しやすい次トークン」という組を作り、検索済み文書中で対応する箇所を探す。見つかった箇所からさらに確率の高い後続トークンを辿り、モデルの予測傾向に沿うトークン木を構成する。

例えば文書中の表現が「Clinton's security detail has arrived ...」でも、モデルが「Clinton arrived ...」を高確率とみなすなら、校正された候補列を後者に近づけられる。これは別のLLMを使って文書を書き換えるのではなく、文脈処理で得た確率分布を使って検索候補を選び直す操作である。追加のモデル順伝播や端末内の再学習は不要だが、確率候補の標本化とトークン木の管理には軽い処理費用がかかる。

校正後のトークン木を検索型下書き器の入力にすると、検証器が受理しやすい候補を取り出せる。目的は文意の近さではなく、検証器のトークン単位の受理規則へ合致することである。誤った候補は通常の検証で棄却されるため、校正処理は出力を勝手に確定しない。

### 3. 棄却列の再利用とNPU向け推測列延長

一度棄却されたトークン列にも、後続の出力と一致する区間が残る場合がある。著者らの手動分類では、棄却候補のうち「必要な語の欠落」15.4%と「同義語による位置ずれ」23.1%には再利用可能な後続区間があり、完全に冗長な候補61.5%は捨てるべきだった。つまり、棄却されたという事実だけで全トークンを永久に破棄すると、次のステップで役立つ情報まで失う。

sd.npuは検証時に候補xとモデル予測yを照合し、最初の不一致位置以降で `x_i=y_i` が連続する最長区間を探す。その区間を次回の下書きへ付け足し、短い検索候補をNPUが処理しやすい長さへ延長する。全区間と将来ステップを網羅的に探索すると費用が大きいため、長い一致区間を優先する規則を使い、保持期間や総下書き長に上限を設ける。実験では上限を32トークンとする。

重要なのは、**再利用候補を即座に正解として出力するのではなく、次の検証器へ再提出する**ことである。これにより、受理規則を保ったままNPUの一定費用領域へより長い候補を投入できる。ただし検索文書と出力の重なりが少ない場合には再利用候補が乏しく、トークン木構築と候補照合の費用だけが残る。

### 4. 1要求の処理順

要求が届くと、検索で得た文書を文脈へ加え、固定長の塊へ分ける。NPUが文脈処理を進める間に、ブロックごとの復号グラフを裏で読み込む。文脈処理の出力確率から校正済みトークン木を作り、検索文書や過去会話を含む下書きデータベースへ追加する。復号段階では下書き候補を取得し、棄却後も再利用できる一致区間を延長しながら、検証器がまとめて候補を判定する。受理済み接頭辞だけを出力へ確定し、応答終了時には新しい対話をデータベースへ反映する。

これらの機構は異なる律速を担当する。段階的グラフ切替は文脈処理と復号の境界で生じる読込待ちを削り、分布校正は検証器が棄却する候補の割合を下げ、候補延長は同じNPU検証費用で処理するトークン数を増やす。したがって単一機構の改善だけをシステム全体の性能として扱うことはできない。

## 主要結果

### 遅延とエネルギー

スマートフォン3機種、3モデル、4タスクの条件を通じ、sd.npuは比較対象に応じ平均トークン当たり遅延を1.06〜3.81倍改善した。推測復号を使わないmllm(NPU)に対して1.14〜3.81倍、mllm(CPU)に対して1.06〜1.78倍、検索型NG+に対して1.11〜2.53倍、モデル型SpecInferに対して1.09〜1.80倍の範囲である。検索文書と出力が似やすい文書要約では、下書き候補が受理されやすいため大きな利得が得られた。

エネルギー削減は比較対象によって1.07〜4.71倍で、mllm(NPU)比1.35〜4.18倍、mllm(CPU)比1.11〜2.50倍、NG+比1.07〜3.07倍、SpecInfer比1.77〜4.71倍である。別の下書きモデルを実行するSpecInferは端末上でメモリと計算費用が増え、検索型でも棄却の多いNG+はNPUの実行回数を十分減らせない。なお、端末ごとにNPU性能が異なるため、Redmi K70 ProではNPU計算が律速になり、速度改善が相対的に小さかった。

### 構成要素除去：実測トークン遅延

Redmi K60 Proの文書要約で、元のNPU推論、段階的グラフ切替のみ、既存推測復号のみ、両者の単純併用、sd.npu全機構を比較した。単位はミリ秒/トークンで、小さいほど良い。

| モデル | 元NPU | グラフ切替のみ | 既存推測復号のみ | 単純併用 | sd.npu |
|---|---:|---:|---:|---:|---:|
| Qwen2.5-1.5B | 57.41 | 47.72 | 35.04 | 25.35 | **15.08** |
| Qwen2.5-0.5B | 24.46 | 23.43 | 18.75 | 18.45 | **7.17** |
| LLaMA3.2-3B | 71.71 | 70.03 | 47.93 | 46.25 | **41.62** |

Qwen2.5-1.5Bでは単純併用25.35から全機構15.08へ改善し、分布校正と候補延長の効果が残っている。Qwen2.5-0.5Bでは元NPU24.46から7.17へ大きく改善する一方、3Bでは71.71から41.62に留まる。大きなモデルは計算本体が支配的になり、切替費用の隠蔽や推測復号で削れる割合が相対的に小さくなる。

### 受理長、メモリ、内部遅延

既存検索型下書き器PLDとSAMへ分布校正・延長を追加すると、平均受理長はPLD比1.05〜1.25倍、SAM比1.06〜1.24倍になった。例えば文書要約のQwen2.5-1.5BではPLDが2.53トークンから2.91、SAMが3.60から4.21へ伸びる。これは**A100を搭載したサーバーでの受理長分析**であり、スマートフォンの速度倍率そのものではない。

ピークメモリはmllm(NPU)に近く、全測定で追加500MB未満と報告する。Qwen2.5-1.5Bではsd.npuが3.14GB、mllm(NPU)が3.05〜3.12GB、mllm(CPU)が6GB超である。別の下書きモデルを使うSpecInferは0.84〜1.22GBの追加メモリを要するため、端末の限られたRAMでは不利になる。

OnePlus 13の文書要約での遅延内訳では、元mllm(NPU)の復号が全体の67〜74%を占め、sd.npuの復号時間は5.25〜8.15倍短縮した。一方、分布校正では文脈トークンごとの候補標本化費用、下書き木の構築では復号ステップ当たり3ms未満の処理費用が発生する。本文では文脈トークン当たり約2msの校正処理を記載しており、入力長が極端に増えればこの費用も無視できない。

## 既存研究との差

mllmのようなモバイル推論基盤はNPUへ演算を委譲するが、文脈処理と復号の形状差に伴うグラフ再構成待ちや、短い推測列での行列演算器の遊休までは一括で解決しない。sd.npuは計算グラフを層ブロックへ分割し、文脈処理を続けながら復号用グラフへ置き換えるため、単なるNPUカーネル高速化とは異なる。

EAGLE系などのモデル型推測復号は別の下書きモデルを保持し、その出力を大きいモデルで検証する。モバイルでは追加モデルがRAMと電力を消費するため、sd.npuはRAGの検索文書を下書き源とする。PLDやSAMのような検索型方式とも異なり、文脈処理で既に計算したモデル確率からトークン木を校正し、過去に棄却した候補の再利用区間まで探索する。検索候補の語彙ずれと短い検証列という二つの弱点をNPUの固定費用モデルに合わせて改善する。

## 限界

本評価はQualcomm系SoCの商用スマートフォン3機種と、最大3B規模のモデルを中心とする。Apple Neural Engineや他社NPUで同じグラフ分割・読込APIや演算器飽和点が使えることは示されていない。端末ごとのNPU実行性能差が大きく、K70 ProではNPU計算律速のため利得が小さい。モデルがさらに大きい場合にも、グラフ切替を隠して削れる割合は減る可能性がある。

提案方式は検索文書や対話履歴から下書きを作るため、元文書と回答の語彙重なりが小さい生成では受理長を伸ばしにくい。分布校正と棄却列再利用は候補を作るための追加処理であり、入力が非常に長い場合や検証器がほとんど候補を受理しない場合はその費用が相対的に重くなる。検証によって生成品質は保つが、検索品質や回答の事実性そのものを改善する機構ではない。

モデル分割とグラフ切替は事前の端末別プロファイルを必要とする。論文の実機ではN=2が十分だったが、全端末・全モデルで最適とは限らない。読込時間が計算時間を上回る条件では、貪欲な重ね合わせでも待ち時間を完全に隠せない。動的なOS負荷、温度制御、他アプリとの競合で事前測定値が変わる場合の頑健性も主要評価ではない。

エネルギー結果はroot権限を得られた端末に限られ、K70 Proを含まない。さらに受理長の一部分析はA100サーバー上で行われ、スマートフォンの全結果と同一条件ではない。mllm実装では注意など一部の精度敏感な演算をCPU/GPUへ委譲する注記があり、システム名の「NPU中心」を、全演算が例外なくNPUだけで実行される意味に読み替えてはならない。
