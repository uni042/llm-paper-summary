# An Interpretable Latency Model for Speculative Decoding in LLM Serving

> 投機的 デコードの低負荷時の速さだけでなく、リクエスト 率が上がると下書き・検証の負荷依存コストがバッチとともに増えて高速化倍率が縮む現象を、Little's Lawから推定した実効バッチ サイズと少数のコスト係数で説明する提供 遅延 モデル。

## 問題設定

投機的 デコード（投機的復号）は、小さい下書き モデルが複数トークン候補を先に生成し、大きい対象モデル モデルがまとめて検証することで、対象モデル モデルの逐次デコード回数を減らす。しかし多くの評価はバッチ=1や固定バッチで行われ、連続 batchingを使う実際の提供ではリクエスト数に応じて実効バッチ サイズが変わる。

そのため、低負荷では速い設定でも高負荷では下書き計算や検証がバッチ方向に増幅され、高速化倍率が縮む、あるいは通常デコードより遅くなることがある。本論文は、提供 実行時内部を細かく再現するのではなく、外から測れるリクエスト 率と遅延からこの変化を説明できる簡潔なモデルを作る。

## 新規性

- 連続 batching下の平均同時リクエスト数を直接観測せず、Little's Lawで `実効batch size = request rate × latency` として推定する。
- リクエスト 遅延を読み込みに依存しない固定コストと、実効バッチ サイズに比例する負荷依存 コストへ分け、投機的 デコードではプリフィル・下書き・検証へさらに分解する。
- 下書き 長さ、acceptance 率、drafter / verifier サイズから、低負荷と高負荷で最適なspeculation設定が変わる理由を閉形式で説明する。
- dense モデルだけでなく、同時リクエストや下書き トークンが増えると活性化エキスパートの被覆が変わるMoE向け補正も示す。

## 手法

### 1. 実効batch sizeをLittle's Lawで推定

安定したpre-飽和領域では、平均同時リクエスト数 `B` を `RPS × L` と置く。リクエスト 遅延を

`L = C1 + B × C2`

とすると、

`L = C1 / (1 - RPS × C2)`

になる（Eq. 1）。`C1` は読み込み-独立 コスト、`C2` はリクエストが同時に増えたときの限界コストを表す。スケジューラやカーネルを逐一モデル化せず、提供 stack全体の平均効果を2係数へ吸収する。

### 2. Speculative decodingのspeedupをload依存で分解

通常デコードと投機的 デコードそれぞれに `C1` と `C2` を当てはめると、高速化倍率は固定コスト比 `C1,R` と負荷依存 コスト比 `C2,R` に分けられる（Eq. 2）。

- `C1,R < 1` なら低負荷でspeculationが有利。
- `C2,R < 1` なら読み込みが上がっても有利さが増す。
- `C2,R > 1` なら同時リクエストが増えるほどspeculation側の追加コストが膨らみ、高速化倍率が縮む。

実測では多くのacceptance 率 / 下書き 長さ設定で `C2,R > 1` となり、非常に高いacceptance 率を除いて高負荷ほど高速化倍率が侵食される（Fig. 2b、Fig. 3）。

### 3. Prefill・draft・verificationへcostを分解

1回の投機的 cycleを、プリフィル コスト、`k` トークンを逐次作る下書き コスト、`k`候補を並列確認する検証 コストへ分ける。acceptance probability `α` と下書き 長さ `k` から1 cycleあたりの期待確定トークン数 `E` を求め、必要cycle数を `生成token数 / E` とする。

これを固定コストと負荷依存 コストの両方へ適用したEq. 3により、acceptance 率と下書き 長さごとに別々だった遅延曲線を共通の提供 モデルで説明する。

### 4. MoEではexpert coverageを補正

MoEではバッチや1回の検証 トークン数が増えると、一度に触れるエキスパート集合が広がる。そのためdense モデルと同じパラメータ scalingだけでは低負荷側のコストを説明しにくい。論文はエキスパート 被覆を使う補正を加え、sparse 活性値による低負荷時のずれを説明する。

エキスパート 被覆が効く理由は、MoEの1 cycleのコストがトークン数へ線形に比例しないからである。少数リクエストではactive エキスパート集合が疎で、検証 トークンを増やすと新しいエキスパート 重みやカーネル 動作が増えやすい。一方バッチが十分大きいと多くのエキスパートがすでに被覆され、追加トークンの限界コストが変わる。モデルへ被覆項を入れることで、dense パラメータ countだけでは表せないこの活性値 飽和を低次元コスト モデルへ取り込む。

この補正は、同じトークン数でも同時実行されるエキスパートの重なり方によって実測時間が変わることを表す。したがって係数を比較するときは、モデル規模だけでなく、バッチの大きさとエキスパート被覆の状態も同じ条件にそろえる必要がある。

## 評価条件

- 提供 stack: vLLM 0.13.0
- 読み込み 生成器: GuideLLM 0.5.2
- リクエスト 率: 同期からプリエンプション直前まで9段階
- プリフィル / デコード 長さ: 256 / 512 / 768 / 1024 トークン
- acceptance 率: 50%〜100%
- 下書き 長さ: 1〜10 トークン
- モデル: Llama 3.1 8B / 70B、gpt-oss-20b、Qwen3 系列、Qwen3-30B-A3B、Qwen3-235B-A22B等
- ハードウェア: 原則NVIDIA A100 SXM 1枚、Llama 70Bは4枚、Qwen3-235B-A22Bは8枚。dense Qwen3ではH100でも頑健性を確認。

飽和境界ではプリエンプション等で遅延が不安定になるため、モデル 適合はその直前までの安定領域に限定している。

## 主要結果

- 通常デコードと投機的 デコードの双方で、モデル・系列長・speculation設定が異なっても、`L/C1` を `RPS×C2` に対して正規化すると同じ `1/(1-x)` 曲線へ収束する（Fig. 1、Fig. 2a）。
- Qwen3-8Bでは低負荷側を支配する `C1,R` は各設定で1未満だが、負荷依存な `C2,R` は非常に高いacceptance 率を除き1より大きく、読み込み上昇時に高速化倍率が縮む理由を説明できる（Fig. 2b）。
- 全プリフィル/デコード設定で下書き 長さを探索しても、`C1,R` を最小にする下書き 長さと `C2,R` を最小にする下書き 長さは大きく異なる。バッチ=1向けに最適化した長い下書きは高スループット 提供では不利になり得る（Fig. 3、§4.3）。
- プリフィル・下書き・検証分解を入れたspeculation-aware モデルはacceptance 率 / 下書き 長さを跨いで fitted `C1`, `C2` をよく再現し、現在 acceptance 率とRPSから実行中に下書き 長さを選ぶ用途を示す（Fig. 4c–d、§4.4）。
- H100およびp95/p99 遅延でも同じモデル構造がおおむね成立する（Appendix A.5–A.6）。

本論文の主結果は「最大何倍高速」という単一値ではなく、**投機的 デコードの高速化倍率がサーバ 読み込みでどう変化するかを少数パラメータで予測・説明できること**にある。

このモデルを使うと、運用者はまず低負荷時の固定コストと、同時実行数の増加に伴う限界コストを別々に測定できる。次に実効バッチ サイズをリクエスト 率と遅延の積から求め、候補となる下書き 長さごとに同じ式を当てはめる。低負荷時だけを見て長い下書きを選ぶのではなく、現在の読み込みで予測遅延が最小となる設定を選択できるため、提供環境の変動に追従しやすい。

ただし係数は装置、実行時、系列長、モデルの組み合わせごとに再推定する必要がある。`C1` と `C2` は論文の物理定数ではなく、測定した遅延曲線を簡潔に表す近似係数だからである。したがって別のGPUやスケジューラへそのまま移植するのではなく、安定領域の測定点を取り直し、飽和境界を越えない範囲でモデルを検証することが実装上の前提になる。

## 既存研究との差

SpecInfer、EAGLE、Medusa、Lookahead デコードなどが「どう複数トークン候補を作り、どう効率よく検証するか」を改善するのに対し、本論文は新しいデコーダを提案しない。既存投機的 デコードを提供 構成要素として扱い、連続 batchingで読み込みが変化したときの遅延曲線を説明する。

有効スループット型のシステム 最適化器が実測から良い設定を選ぶ方向に対して、本論文は「なぜその設定が読み込みによって良くなったり悪くなったりするか」を分解可能なコスト モデルとして与える点が異なる。

## 限界

- モデルはプリエンプションが始まる前の安定領域を対象とし、飽和後の待ち行列爆発やプリエンプション動作を直接モデル化しない。
- 平均遅延を中心とした低次元モデルであり、裾 遅延分布そのものの完全な予測モデルではない。
- acceptance probabilityを簡潔な独立確率として扱うため、実際のトークン列で相関するacceptance 挙動を完全には表さない。
- vLLMを中心に評価しており、他スケジューラ/実行時で係数は再fitが必要。
- 公式実装repositoryは一次資料から確認できなかった。

## 一般的な実装上の含意

投機的 デコードを実運用 提供へ入れる際、バッチ=1 ベンチマークで最も速い下書き 長さを固定するだけでは不十分である。リクエスト 率、acceptance 率、drafter / verifier構成から固定コストと負荷依存 コストを分けて測れば、読み込み上昇でspeculationが逆効果になる前に下書き 長さやspeculationの有無を切り替えられる。

またMoEではトークン acceptanceだけでなく、検証で何個のエキスパートへアクセスが広がるかも提供 コストへ効くため、投機的 デコードとエキスパート residency / キャッシュ設計を別々に最適化しない方がよい。
