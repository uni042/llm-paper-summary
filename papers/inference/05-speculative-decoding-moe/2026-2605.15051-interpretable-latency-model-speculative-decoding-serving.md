# An Interpretable Latency Model for Speculative Decoding in LLM Serving

> speculative decodingの低負荷時の速さだけでなく、request rateが上がるとdraft・verificationの負荷依存costがbatchとともに増えてspeedupが縮む現象を、Little's Lawから推定した実効batch sizeと少数のcost係数で説明するserving latency model。

## 問題設定

Speculative decoding（投機的復号）は、小さいdraft modelが複数token候補を先に生成し、大きいtarget modelがまとめて検証することで、target modelの逐次decode回数を減らす。しかし多くの評価はbatch=1や固定batchで行われ、continuous batchingを使う実際のservingではrequest数に応じて実効batch sizeが変わる。

そのため、低負荷では速い設定でも高負荷ではdraft計算やverificationがbatch方向に増幅され、speedupが縮む、あるいは通常decodeより遅くなることがある。本論文は、serving runtime内部を細かく再現するのではなく、外から測れるrequest rateとlatencyからこの変化を説明できる簡潔なmodelを作る。

## 新規性

- continuous batching下の平均同時request数を直接観測せず、Little's Lawで `実効batch size = request rate × latency` として推定する。
- request latencyをloadに依存しない固定costと、実効batch sizeに比例するload-dependent costへ分け、speculative decodingではprefill・draft・verificationへさらに分解する。
- draft length、acceptance rate、drafter / verifier sizeから、低負荷と高負荷で最適なspeculation設定が変わる理由を閉形式で説明する。
- dense modelだけでなく、同時requestやdraft tokenが増えると活性化expertのcoverageが変わるMoE向け補正も示す。

## 手法

### 1. 実効batch sizeをLittle's Lawで推定

安定したpre-saturation領域では、平均同時request数 `B` を `RPS × L` と置く。request latencyを

`L = C1 + B × C2`

とすると、

`L = C1 / (1 - RPS × C2)`

になる（Eq. 1）。`C1` はload-independent cost、`C2` はrequestが同時に増えたときの限界costを表す。schedulerやkernelを逐一model化せず、serving stack全体の平均効果を2係数へ吸収する。

### 2. Speculative decodingのspeedupをload依存で分解

通常decodeとspeculative decodingそれぞれに `C1` と `C2` を当てはめると、speedupは固定cost比 `C1,R` とload-dependent cost比 `C2,R` に分けられる（Eq. 2）。

- `C1,R < 1` なら低負荷でspeculationが有利。
- `C2,R < 1` ならloadが上がっても有利さが増す。
- `C2,R > 1` なら同時requestが増えるほどspeculation側の追加costが膨らみ、speedupが縮む。

実測では多くのacceptance rate / draft length設定で `C2,R > 1` となり、非常に高いacceptance rateを除いて高負荷ほどspeedupが侵食される（Fig. 2b、Fig. 3）。

### 3. Prefill・draft・verificationへcostを分解

1回のspeculative cycleを、prefill cost、`k` tokenを逐次作るdraft cost、`k`候補を並列確認するverification costへ分ける。acceptance probability `α` とdraft length `k` から1 cycleあたりの期待確定token数 `E` を求め、必要cycle数を `生成token数 / E` とする。

これを固定costとload-dependent costの両方へ適用したEq. 3により、acceptance rateとdraft lengthごとに別々だったlatency曲線を共通のserving modelで説明する。

### 4. MoEではexpert coverageを補正

MoEではbatchや1回のverification token数が増えると、一度に触れるexpert集合が広がる。そのためdense modelと同じparameter scalingだけでは低負荷側のcostを説明しにくい。論文はexpert coverageを使う補正を加え、sparse activationによる低負荷時のずれを説明する。

expert coverageが効く理由は、MoEの1 cycleのcostがtoken数へ線形に比例しないからである。少数requestではactive expert集合が疎で、verification tokenを増やすと新しいexpert weightやkernel workが増えやすい。一方batchが十分大きいと多くのexpertがすでにcoverageされ、追加tokenの限界costが変わる。モデルへcoverage項を入れることで、dense parameter countだけでは表せないこのactivation saturationを低次元cost modelへ取り込む。

## 評価条件

- serving stack: vLLM 0.13.0
- load generator: GuideLLM 0.5.2
- request rate: synchronousからpreemption直前まで9段階
- prefill / decode length: 256 / 512 / 768 / 1024 token
- acceptance rate: 50%〜100%
- draft length: 1〜10 token
- model: Llama 3.1 8B / 70B、gpt-oss-20b、Qwen3 family、Qwen3-30B-A3B、Qwen3-235B-A22B等
- hardware: 原則NVIDIA A100 SXM 1枚、Llama 70Bは4枚、Qwen3-235B-A22Bは8枚。dense Qwen3ではH100でもrobustnessを確認。

saturation境界ではpreemption等でlatencyが不安定になるため、model fittingはその直前までの安定領域に限定している。

## 主要結果

- 通常decodeとspeculative decodingの双方で、model・sequence長・speculation設定が異なっても、`L/C1` を `RPS×C2` に対して正規化すると同じ `1/(1-x)` 曲線へ収束する（Fig. 1、Fig. 2a）。
- Qwen3-8Bでは低負荷側を支配する `C1,R` は各設定で1未満だが、load-dependentな `C2,R` は非常に高いacceptance rateを除き1より大きく、load上昇時にspeedupが縮む理由を説明できる（Fig. 2b）。
- 全prefill/decode設定でdraft lengthを探索しても、`C1,R` を最小にするdraft lengthと `C2,R` を最小にするdraft lengthは大きく異なる。batch=1向けに最適化した長いdraftは高throughput servingでは不利になり得る（Fig. 3、§4.3）。
- prefill・draft・verification分解を入れたspeculation-aware modelはacceptance rate / draft lengthを跨いで fitted `C1`, `C2` をよく再現し、current acceptance rateとRPSから実行中にdraft lengthを選ぶ用途を示す（Fig. 4c–d、§4.4）。
- H100およびp95/p99 latencyでも同じmodel構造がおおむね成立する（Appendix A.5–A.6）。

本論文の主結果は「最大何倍高速」という単一値ではなく、**speculative decodingのspeedupがserver loadでどう変化するかを少数parameterで予測・説明できること**にある。

## 既存研究との差

SpecInfer、EAGLE、Medusa、Lookahead Decodingなどが「どう複数token候補を作り、どう効率よく検証するか」を改善するのに対し、本論文は新しいdecoderを提案しない。既存speculative decodingをserving componentとして扱い、continuous batchingでloadが変化したときのlatency曲線を説明する。

Goodput型のsystem optimizerが実測から良い設定を選ぶ方向に対して、本論文は「なぜその設定がloadによって良くなったり悪くなったりするか」を分解可能なcost modelとして与える点が異なる。

## 限界

- modelはpreemptionが始まる前の安定領域を対象とし、saturation後のqueue爆発やpreemption動作を直接model化しない。
- 平均latencyを中心とした低次元modelであり、tail latency分布そのものの完全な予測modelではない。
- acceptance probabilityを簡潔な独立確率として扱うため、実際のtoken列で相関するacceptance behaviorを完全には表さない。
- vLLMを中心に評価しており、他scheduler/runtimeで係数は再fitが必要。
- 公式実装repositoryは一次資料から確認できなかった。

## 一般的な実装上の含意

Speculative decodingをproduction servingへ入れる際、batch=1 benchmarkで最も速いdraft lengthを固定するだけでは不十分である。request rate、acceptance rate、drafter / verifier構成から固定costとload-dependent costを分けて測れば、load上昇でspeculationが逆効果になる前にdraft lengthやspeculationの有無を切り替えられる。

またMoEではtoken acceptanceだけでなく、verificationで何個のexpertへアクセスが広がるかもserving costへ効くため、speculative decodingとexpert residency / cache設計を別々に最適化しない方がよい。
