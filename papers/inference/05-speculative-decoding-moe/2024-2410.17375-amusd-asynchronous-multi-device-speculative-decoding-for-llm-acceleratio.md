# AMUSD: Asynchronous Multi-Device Speculative Decoding for LLM Acceleration

## 概要
投機的復号（speculative decoding）は、小さなドラフトモデル（draft model）が複数tokenを先に生成し、大きな検証モデル（verify model）がそれらをまとめて判定することで、検証モデルを1 tokenずつ呼ぶ逐次回数を減らす。しかし通常の同期型実装では「ドラフト生成中は検証GPUが待つ」「検証中はドラフトGPUが待つ」という交互実行になる。複数GPUが使える場合、この待機時間は装置利用率の損失になる。

非同期マルチデバイス投機的復号（Asynchronous Multi-Device Speculative Decoding; AMUSD）は、ドラフトと検証を別GPU・別processへ置き、両者を常時並行させる。ドラフト側は検証を待たず先の候補を生成し続け、検証側は現在利用可能な候補列をまとめて検証する。不一致が判明した場合だけ、ドラフトbufferとKV cacheを最後に確定した位置まで巻き戻す（rollback）。このため、先行計算を許しながら検証モデルが確定した系列との整合性を回復できる。

## 問題設定
同期型投機的復号では、一回の反復が「(k) tokenをドラフト→対象モデルで一括検証→受理位置を確定→次のドラフト」の直列鎖になる。ドラフトが十分速くても検証中は停止するため、2台のGPUへモデルを分けただけでは計算を重ねられない。

一方、単純にドラフトを走らせ続けると、検証モデルが位置 (i) で候補を拒否した時点で、(i) より後ろの候補は誤ったprefixから生成されたものになる。その候補だけでなくドラフトモデルのKV cacheも無効なので、token列と内部状態の両方を確定位置へ戻す必要がある。非同期化の利得は「隠せた待ち時間」と「拒否後に捨てる先行計算」の差で決まる。

## 手法
### 二つの連続process
AMUSDはドラフトprocessと検証processを独立に起動する。ドラフトprocessは自身のGPU上にドラフトモデルと局所token tensor、KV cache (S_d) を持ち、1 tokenずつ連続生成して共有draft buffer (D) へ追加する。検証processは別GPU上に検証モデル、局所tensor、KV cache (S_v) を持ち、draft位置 (p_d) が確定位置 (p_v) より先へ進むと、区間 (D[p_v:p_d]) をまとめて検証する。

同期型の固定ドラフト長 (k) を待つのではなく、検証側はその時点で利用可能なtoken数を処理する。この間もドラフトGPUはさらに先を生成できるため、検証時間を次候補のドラフト時間で隠す。論文の例では同じ経過時間で、同期型がtoken 6まで検証済みなのに対し非同期型はtoken 8まで検証済みとなる。

### 不一致時のrollback
検証列とドラフト列が位置 (i) で初めて不一致になると、検証processは一致したprefixだけを確定buffer (V) へ追加し、rollback flag (R) を立てる。ドラフトprocessはこれを検出すると、自身の局所tensorを (p_v) までcropし、ドラフトKV cacheも同じ確定位置へ戻して、修正済みprefixから生成を再開する。検証processはrollback完了を待ってから次の検証へ進む。

共有bufferはdraft側とverify側でwriterが一つずつなので、論文の設計では通常の相互排他lockを置かずに済む。rollbackは非同期化によって新たに生じる「検証前に作り過ぎたtoken」を破棄する機構であり、受理率が低いほど無駄計算が増える。

### process間通信
実装はPython multiprocessingを使い、main processがready/start/end/closeなどのeventを管理する。draft tensorとverify tensorはCPU共有メモリに置き、各GPU processは常に共有tensorを直接演算するのではなく、自分のdevice-local tensorを保持して必要時だけ同期する。draft側は新token追加時とrollback時、verify側は新しいdraft範囲を受け取る時に更新するため、GPU間の状態整合をCPU共有メモリ経由で簡素化している。

この方式は投機的復号の受理規則自体を変更せず、実行順序だけを非同期化する。したがって論文の評価設定では生成textは通常の検証モデルと同一で、速度差は近似品質ではなく装置並列性から得る。

## 評価条件
| 観点 | 条件 |
|---|---|
| ハードウェア | NVIDIA A100×4、AMD EPYC 7313 16-core |
| 検証モデル | Llama-3.1-8B |
| ドラフトモデル | Llama-3.2-1B |
| 単体速度 | draft約10 ms/token、verify約25 ms/token |
| 比較 | Llama-3.1-8B自己回帰、同期型speculative decoding、AMUSD |
| データ | HumanEval 164問、MT-Bench 80 multi-turn、RefactorChat 100件・各8 turn |
| 生成上限 | 最大4096 token |
| 指標 | mean token time、自己回帰比speedup、GPU utilization/power/energy |

## 主要結果
HumanEvalでは自己回帰22.15 ms/token、同期型17.88、AMUSD14.08で、AMUSDは自己回帰比1.57倍、同期型比約1.27倍である。MT-Benchは21.89/20.64/16.75 ms/tokenで1.31倍、RefactorChatは27.42/19.18/13.96 ms/tokenで最大1.96倍となる。三datasetを通した同期型投機的復号からの改善は平均約29%と報告される。

長いRefactorChatで利得が大きいのは、両processの重畳時間を長く確保できるためである。代表例では同期型の一検証あたり受理draft数が5.35 tokenなのに対しAMUSDは2.75 tokenと**受理効率自体は低い**。それでもAMUSDの方が速く、受理長だけでなくドラフトと検証の同時実行がwall-clock性能を決めることを示す重要な負の結果である。

資源評価では、自己回帰・同期型は実質GPU0だけを動かすのに対し、AMUSDはGPU0/1を同時利用する。そのため瞬時電力はAMUSDが約300W、単一GPU方式が約150〜220Wで高い。一方、終了が速いためtoken当たり総エネルギーは自己回帰より低く、同期型投機的復号よりはわずかに高い。つまりAMUSDは追加GPUと瞬時電力を使って遅延を下げる方式で、エネルギーも無条件に最良という結果ではない。

## 既存研究との差
通常の投機的復号、EAGLE、Medusaなどは主に「より良い候補をどう作るか」「何tokenを一括検証するか」を改善する。AMUSDは候補生成アルゴリズムを置き換えず、ドラフトと検証を別deviceへ分離して生産者・消費者型に並行化するシステム最適化である。このため他のdraft品質改善と原理的には直交し、組み合わせ余地がある。

## 限界
追加deviceが必要なので、単一GPU環境では主要な利得を得られない。ドラフトが検証より先行し過ぎ、受理率が低い場合はrollbackで大量の候補計算を捨てる。論文自身の代表例でもAMUSDの受理token数/verify stepは同期型より低いため、速度比はdraft/verifyの速度比、出力長、受理率へ強く依存する。

実験はLlama-3.1-8B + Llama-3.2-1B、A100環境、単一要求型の三datasetに限られる。大規模continuous batching、複数tenant、GPU間ネットワーク越しの分離、異種accelerator構成は評価していない。また二GPU同時利用はthroughput目的の他requestを載せられる資源を消費するため、単一request latencyが良くてもクラスタ全体の費用対性能が必ず改善するとは限らない。
