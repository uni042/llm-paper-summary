# AMUSD: Asynchronous Multi-Device Speculative Decoding for LLM Acceleration

## 概要

大規模言語モデルの逐次生成は、前に確定したトークンを次の入力に使うため、対象モデルを一度に多数の生成位置へ適用しにくい。投機的復号では、計算量の小さいドラフトモデルが先の候補を作り、大きな検証モデルが候補列を一括検証する。しかし従来の同期型実装は「候補を作る→検証する→次の候補を作る」を繰り返すため、片方が動く間にもう片方のモデルが待機する。二つのモデルを別々のGPUへ配置しても、この実行順序を変えなければGPUを同時に使い切れない。

AMUSDは、ドラフトと検証を独立したGPUプロセスへ分け、候補生成と検証を常時重ねる方式である。ドラフト側は検証完了を待たずに先のトークンを生成し続け、検証側は現在利用可能な候補区間をまとめて確かめる。両者の結果が一致しないときには、ドラフトが先行して作った候補だけでなく、ドラフトモデルの鍵・値キャッシュも最後に確定した位置まで戻す。この巻き戻しにより、先行実行で発生する誤った接頭辞の状態を持ち越さずに済む。

著者は検証モデルにLlama-3.1-8B、ドラフトモデルにLlama-3.2-1Bを使い、A100環境で三つの生成課題を評価した。平均トークン時間は、自己回帰生成に対してHumanEvalで1.57倍、MT-Benchで1.31倍、RefactorChatで1.96倍の高速化となった。同期型投機的復号との比較でも平均約29%の改善を報告する。一方、二つのGPUを同時に動かすため瞬時消費電力は高く、候補の受理数も同期型より少ない例がある。したがって利得は受理率の高さだけでは説明できない。

## 問題設定

### 同期型投機的復号で残る待機

同期型の投機的復号は、まずドラフトモデルが一定個数の候補トークンを作り、その候補を検証モデルが並列に評価する。受理できた接頭辞を確定した後で次のドラフトへ進むため、二つの計算段階は直列に連なる。ドラフトが高速でも検証中はドラフトが停止し、検証GPUはドラフト中に待つ。論文の単独モデル計測ではドラフトが約10ミリ秒/トークン、検証モデルが約25ミリ秒/トークンであり、交互実行ではこの待機が目立つ。

### 非同期化が引き起こす整合性の問題

検証を待たずにドラフトを進めれば、先行した候補は検証されていない接頭辞から生成される。もし検証モデルが途中の位置で異なるトークンを確定すると、その後ろのドラフト列は誤った履歴に基づくことになる。表示用のトークン配列だけを削除しても不十分で、ドラフトモデルの鍵・値キャッシュには誤った履歴の内部状態が残る。正しい位置まで内部状態を戻してから候補生成を再開しなければ、後続の検証に渡す系列が壊れる。

このため非同期化の成否は、検証時間と候補生成時間をどれだけ重ねられるかに加え、不一致時に破棄する先行計算がどれほど増えるかで決まる。候補受理率が低いと巻き戻しが頻発し、二台のGPUを使っても有利にならない可能性がある。論文は、並列化の利益と巻き戻し費用を実装と実測の両面から扱う。

## 手法

### 二つの継続プロセスと共有状態

アルゴリズムではドラフトモデルを `Md`、検証モデルを `Mv` とし、候補列 `D`、確定列 `V`、ドラフトの位置 `pd`、検証済み位置 `pv`、巻き戻しフラグ `R` を用いる。さらにそれぞれのモデルの鍵・値キャッシュを `Sd` と `Sv` として保持する。初期入力を両モデルへ与え、位置を入力末尾に合わせた後、候補生成プロセスと検証プロセスを並行して走らせる。

ドラフト側は `Md` から新しいトークンを生成し、候補列 `D` の位置 `pd` へ追加して `Sd` を更新し、`pd` を進める。この処理を検証待ちなしで繰り返す。検証側は `pd>pv` なら区間 `D[pv:pd]` を取り出し、`Mv` でまとめて照合する。固定長の候補が揃うのを待つ必要はなく、検証時点で到着済みの候補数を処理できる。

論文の図では、同期型が6番目までしか検証を終えていない時点で、AMUSDは8番目まで検証を進めている。この差はドラフトの品質が向上したからではなく、検証中にも別GPUが将来の候補を生成していたことによる。実装上は確定位置と先行位置を共有し、どの区間を検証するかを二つのプロセス間で決める。

### 不一致時の巻き戻し

検証した候補列と検証モデルの結果が位置 `i` で初めて不一致になった場合、検証側はそれ以前に一致した部分だけを確定列へ追加し、`pv` を確定位置へ進めて `R` を真にする。ドラフト側は巻き戻し指示を見つけると、先行候補の末尾を削除し、局所トークン配列とドラフト鍵・値キャッシュ `Sd` を `pv` の状態へ戻す。その後、確定した接頭辞から再び候補生成を始め、巻き戻し完了を通知する。

検証側は巻き戻し完了を待って次の検証へ進むため、誤った接頭辞の上で作られた候補を確定しない。逆にすべて一致した場合は、検証済みの候補列を確定列へ追加し、`pv` を `pd` へ進める。終了トークンが確定するか最大生成長に達した時点で両プロセスを終了する。巻き戻しは追加の同期点を作るが、不一致のない区間では候補生成と検証を並行させられる。

### CPU共有メモリと局所GPU配列

実装はPythonの複数プロセスを使い、制御プロセスが準備、開始、終了、クローズなどのイベントを管理する。候補列と確定列の共有表現はCPU共有メモリ上に置くが、各GPUは毎回CPU配列を直接計算するのではなく、装置内に局所トークン配列を持つ。ドラフト側は新トークン追加や巻き戻しの際に、検証側は新しい候補区間を取り込む際に必要な同期を行う。

候補列にはドラフト側だけが書き込み、確定列には検証側だけが書き込む。著者はこの単一書込者の設計により、通常の候補・確定配列へ相互排他ロックを置かずに済むと説明する。鍵・値キャッシュは各GPUに残し、巻き戻し時に局所状態を切り詰める。共有メモリの利用は装置間の状態伝達を単純化するが、トークン配列のコピーやイベント同期の費用が完全に消えるわけではない。

### 生成品質と投機的復号の関係

AMUSDの目的は、候補モデルをより正確にすることではなく、同じ検証規則を保ったまま実行順序を変えることである。検証側が確定した列を正本とし、ドラフトが作った未検証の列は必要に応じて捨てる。著者は評価で自己回帰方式と同一の生成テキストが得られたと報告するが、これは論文の実装・設定で確認された結果である。異なる確率的サンプリング方式や分散環境へ無条件に拡張してよい保証とは区別する必要がある。

## 評価

### 実験環境と比較方式

| 観点 | 一次論文の条件 | 結果の読み方 |
|---|---|---|
| 計算機 | NVIDIA A100を4枚、AMD EPYC 7313 16コア | 評価機に4枚あるが方式は2枚を並行利用 |
| 検証モデル | Llama-3.1-8B | 自己回帰方式の基準モデル |
| ドラフトモデル | Llama-3.2-1B | 投機的復号の候補生成 |
| 単独モデル時間 | ドラフト約10、検証約25ミリ秒/トークン | 非同期化の重畳余地を示す |
| HumanEval | Python関数実装164問 | コード生成の評価 |
| MT-Bench | 複数往復対話80件 | 会話型の評価 |
| RefactorChat | コード改修の長い対話100件、各8往復 | 長文生成での重畳効果 |
| 生成長 | 最大4096トークン | 多くは終了トークンで早期終了 |
| 比較 | 自己回帰、同期型投機的復号、AMUSD | 同じ検証モデルで比較 |

### 平均トークン時間と速度差

| データ | 自己回帰 | 同期型投機的復号 | AMUSD | 自己回帰比 |
|---|---:|---:|---:|---:|
| HumanEval | 22.15ミリ秒 | 17.88ミリ秒 | 14.08ミリ秒 | 1.57倍 |
| MT-Bench | 21.89ミリ秒 | 20.64ミリ秒 | 16.75ミリ秒 | 1.31倍 |
| RefactorChat | 27.42ミリ秒 | 19.18ミリ秒 | 13.96ミリ秒 | 1.96倍 |

すべてのデータで、同じ大きなモデルを1トークンずつ動かす自己回帰方式よりAMUSDの平均トークン時間が短い。同期型投機的復号に対しても短く、論文要旨は平均29%の改善と記す。例えばHumanEvalでは22.15から14.08ミリ秒へ短縮したため、速度比は22.15÷14.08で約1.57倍になる。これは検証モデルの重みを削減した効果ではなく、候補生成と検証の待ち時間を重ねた効果である。

RefactorChatは8往復のソフトウェア改修対話であり、長い生成が多いほど重畳の効果を維持しやすい。論文の代表例では、同期型投機的復号は検証1回あたり平均5.35個のドラフトトークンを受理したのに対し、AMUSDは2.75個にとどまった。それでもAMUSDの方が早く検証済みトークンを積み上げている。つまり候補受理効率が高いことと、実時間での生成速度が高いことは別であり、AMUSDは並行動作によって受理効率の低下を補っている。

### GPU利用率と電力・エネルギー

同期型投機的復号と自己回帰方式では、実質的に片方のGPUだけが動き、もう一方はほぼ待機する。AMUSDではドラフトと検証が別GPUで同時に進むため、二枚の利用率が上がる。著者の図は、方式ごとのGPU利用率、瞬時電力、1サンプルの総消費エネルギーを比較している。単純に利用率が高いことを省電力と読み替えてはいけない。

AMUSDの瞬時電力は二枚の合計で約300ワット、単一GPU中心の方式は約150〜220ワットである。終了までの時間が短いため、生成トークン当たりのエネルギーは自己回帰方式より低くなるが、同期型投機的復号よりわずかに高いと著者は述べる。したがって遅延短縮と電力・GPU占有の交換条件が存在する。論文の電力値は測定環境に依存し、GPUが4枚搭載される機械全体の設備電力を示すものではない。

### 評価から確認できる機構の働き

同期型で交互に発生する待ちを、非同期方式では候補生成と検証の重畳に置き換えられたことが三課題すべての時間短縮につながる。代表的な長い対話で候補受理数が低下しても処理量が増えたという結果は、AMUSDが単にドラフトの予測品質を改善した方式ではないことを裏付ける。一方、短い応答や拒否の多い系列では先行ドラフトの破棄が相対的に大きくなり得るが、論文はあらゆる受理率での最悪性能を系統的に示してはいない。

## 既存研究との差

従来の投機的復号は小さなドラフトと大きな検証モデルを交互に動かす。EAGLEやMedusaなどの研究は候補生成の構造や候補の当たりやすさを改善するが、AMUSDは候補生成と検証の時間配置そのものを変える。候補生成アルゴリズムを置き換える研究と、異なるGPUで同時実行する本研究は原理的には別の最適化軸である。ただし両者を組み合わせた際の定量的な相乗効果をこの論文が実証したわけではない。

AMUSDは検証モデルの出力品質を維持するための巻き戻しを持ち、未検証候補を正本として公開しない。この点で、候補を無条件に確定する単純な並列生成とは異なる。また二つのGPUへモデルを配置しただけではなく、共有候補列、確定位置、局所キャッシュ、巻き戻しイベントを組み合わせて両プロセスを継続的に進める点が実装上の新規性である。

## 限界

最大の前提は、ドラフトと検証を別々の計算装置で動かせることである。単一GPUで二つのモデルを時間分割実行する環境では、論文が示した継続並列化の利得をそのまま期待できない。二台のGPUを一つの要求へ割り当てるため、同じ装置で別要求を同時処理する機会費用も発生する。単一要求の生成遅延が短くなっても、クラスタ全体の処理量や費用対性能が改善するとは限らない。

巻き戻しは未検証の先行候補を破棄するため、受理率が低いほどドラフトの無駄計算が増える。論文の代表例でも同期型の受理数5.35に対しAMUSDは2.75であり、速度改善と候補受理数の改善は同じ意味ではない。検証モデルが相対的に速い場合や短い出力が多い場合には、候補を先行生成する余地が小さくなる。共有メモリ経由のコピーとイベント同期の費用もゼロではない。

評価はLlama-3.1-8BとLlama-3.2-1Bの組、A100環境、HumanEval・MT-Bench・RefactorChatの三課題に限定される。複数利用者の連続バッチ処理、GPU間ネットワーク越しの分離、異種アクセラレータ、モデルサイズを大幅に変えた場合の挙動は評価されていない。実験では出力テキストが一致したが、異なる乱数設定や確率的受理規則を持つ実装すべての品質保証として扱うことはできない。

エネルギー評価では瞬時電力が約二倍となり、トークン当たりの消費エネルギーは同期型よりわずかに高い。速度だけを目的にした導入では電力上限やGPU台数の制約が問題となり得る。実験の三課題で得た最大1.96倍を、任意の負荷や装置での保証値として使用することも適切ではない。
