# SPECTRE: Hybrid Ordinary-Parallel Speculative Serving for Resource-Efficient LLM Inference

> 複数LLMを同時提供するクラウドでは、人気の大型モデルが混雑する一方、小型モデル用GPUが余ることがある。SPECTREはその空き小型モデルを遠隔下書きモデルとして使って大型モデルの投機的デコードを支援し、下書き生成と大型モデル検証を直列に行う通常型と、両方を重ねる並列型を失敗率に応じて切り替える。余剰GPUを新規専用drafterなしで再利用するserving手法。

## 概要

SPECTREが対象にするのは、**複数種類のLLMを同じクラウドで提供しているときのGPU利用率の偏り**である。

例えば、ある時間帯には235B級の大型モデルへ要求が集中してGPUが混雑している一方、0.6Bや1.5Bの小型モデルサービスは要求が少なく、GPUがかなり空いていることがある。通常はこの空き計算能力を大型モデルへ直接移せない。小型モデルと大型モデルは別サービスとして動いているからである。

SPECTREは、小型モデルを一時的に**下書きモデル（draft model）**として使う。小型モデルが「次の数トークンはこうなりそう」と先に候補を作り、大型の**目標モデル（target model）**がまとめて検証する。これは**投機的デコード（speculative decoding）**と呼ばれる。

投機的デコードでは、最終的なトークンは必ずtarget側で確認される。したがってdraftが間違えても、その候補は捨てられるだけで、target単独で生成した場合と同じ出力意味論を保てる。

ただし、draftを別GPU・別サービスへ置くと新しい問題が出る。

- draft生成を待ってからtarget検証すると、両GPUを十分重ねて使えない。
- draftとtargetを完全に並列化すると、targetの結果によって先に作っていたdraftが無効になり、計算を捨てることがある。
- 小型モデル自身の通常ユーザーもいるため、speculative用requestを優先しすぎると本来の小型モデルserviceを悪化させる。

SPECTREは、この三つをserving scheduler側で調整する。

## まず投機的デコードを整理する

通常の自己回帰生成では、大型LLMは1回のforwardで基本的に1トークンずつ確定する。

```text
target: token 1を計算
        ↓
target: token 2を計算
        ↓
target: token 3を計算
```

大型モデルは1回のforwardが高価なので、これを何百回も繰り返すと遅い。

投機的デコードでは、小型draftが先に複数候補を作る。

```text
draft:  A → B → C → D を予測
                 ↓
target: A,B,C,D をまとめて検証
                 ↓
正しかったprefixだけ採用
```

例えばA/B/Cまではtargetも同意し、Dだけ違ったなら、1回のtarget検証で3トークンを確定できる。

このとき重要なのが**受理長（accepted length）**である。draft候補がよく当たればtarget 1回あたり多くのトークンが進む。外れやすいとdraft計算が無駄になる。

## 問題設定

### 普通の投機的デコードでは専用draft GPUが必要になる

高速化のためだけに小型draft modelを別GPUへ置くと、そのGPUは追加コストになる。

一方、multi-model servingでは既に小型モデルserviceが存在し、低traffic時には計算能力が余っていることがある。

SPECTREはこの**既存の余剰GPU能力**を共有drafterとして再利用する。つまり「speculative decoding専用GPUを増やす」のではなく、「すでにonlineだが暇なmodelを借りる」という発想である。

### 遠隔drafterでは通信と同期が増える

Draftとtargetが別GPU・別serverなら、

1. target側のprefix情報をdraftへ渡す
2. draftが候補tokenを生成する
3. 候補をtargetへ返す
4. targetが検証する

という通信が必要になる。

このためdraftが十分速くなければ、targetがdraft待ちになって逆効果になる。

### 「並列化すれば常に速い」わけではない

普通の投機的デコードでは、draft生成が終わってからtarget検証する。論文ではこれを**通常型（ordinary）**と呼ぶ。

```text
draft生成 → target検証 → draft生成 → target検証
```

一方、**並列型（parallel）**ではtargetが現在候補を検証している間に、draftが次roundの候補を先回りして作る。

```text
target: [検証 round n]------[検証 round n+1]
draft :       [次候補生成]------[次候補生成]
```

理想的には時間を重ねられる。

しかしtargetが候補をrejectすると、それ以降の文脈が変わる。draftが古い文脈を前提に先回りして作った候補は使えず、**巻き戻し（rollback）**が必要になる。

したがってparallel方式は、rollbackが少ないときだけ得になる。

## 手法のあらまし

SPECTREは各batchで、最近のrollback率を見てordinary / parallelを切り替える。

判断の基準は経験的な固定値だけではない。Draft生成時間、target検証時間、1回に投機するtoken数、平均受理長から、「これ以上rollbackするとparallel化の重畳利得より無駄計算が大きくなる」という**臨界rollback率**を導く。

さらに、共有draft serverではspeculative requestを優先しつつ、小型model自身の通常trafficを定期的に処理する。

Target側がtensor parallelismなどで極端に速い場合は、draftがprefix処理に時間を使いすぎないよう、draftにだけpromptを圧縮して渡す。

## 手法

### 1. Ordinary mode — 安全だが重畳しにくい

通常型では、draftが候補を作り終わってからtargetへ送る。

Target検証でrejectが起きても、次のdraft生成は正しい確定prefixから始められるため、先行計算の無駄が少ない。

一方、draft生成中はtargetが候補待ちになり、target検証中はdraftが次仕事を十分進められないため、二つのserviceを直列に使う時間が増える。

### 2. Parallel mode — target検証中に次draftを作る

並列型では、targetがround nを検証している間にdraftがround n+1相当のcontinuationを生成する。

Draftが速く、候補も高確率で受理されるなら、draft latencyをtarget検証の裏へ隠せる。

ただし前roundでrejectされると、先行draftは誤ったprefixから生成しているため無効になる。この無駄がrollback costである。

### 3. 臨界rollback率を計算する

論文では、

- `B`: batch size
- `γ`: 1 roundでdraftするtoken数
- `L`: 平均受理長
- `T_D`: draft 1 stepの時間
- `T_T`: target verificationの時間

からordinaryとparallelのthroughputを近似する。

この二つが同じになるrollback率`r*`を求めると、「観測rollback率が`r*`より低ければparallel、高ければordinary」という選択規則が得られる。

重要なのは式そのものより、**draftとtargetの相対速度が変われば最適方式も変わる**ことである。

- draftが非常に速い → ordinaryでも待ちが小さい
- targetが速くdraftが遅い → parallel重畳の価値が増える
- draft精度が悪くrollbackが多い → parallelの先行計算が無駄になる

という三者のtrade-offを同じ判定に入れている。

### 4. 実行中のrollback率からmodeを切り替える

Requestの内容によってdraftの当たりやすさは変わる。

そのためSPECTREはworkload全体で一つのmodeを固定せず、直近roundのrollback率を観測してbatch単位で切り替える。

長文やtaskが変わってdraft qualityが落ちた場合にはordinaryへ戻り、安定して当たる区間ではparallelへ進む。

### 5. 共有draft serverではspeculative requestを優先する

Draft modelは本来、小型モデルを直接使いたいユーザーのrequestも処理している。

大型targetのspeculative requestを通常requestと完全FIFOで混ぜると、draft responseが遅れてtarget GPUまで待たせる可能性がある。Target側は高価な大型GPUなので、この待ちはsystem全体で損が大きい。

そこでspeculative requestを優先する。

ただし優先し続けると通常requestが飢餓するため、連続`K=10` speculative stepの後は通常requestを1 round処理する。

これは「大型modelを速くするために小型modelユーザーを無視する」のではなく、**target GPU idleの損失と小型service公平性を両立する**ための規則である。

### 6. Targetが速すぎる場合はdraft promptだけ圧縮する

Qwen3-235B-A22BをTP=8で動かすような条件では、target側の検証が並列化で速くなり、逆に小型draft側が律速になることがある。

長いpromptをdraftへそのまま処理させると、draft prefix KV構築だけで時間を使う。

SPECTREはdraft側に限り、promptの先頭と末尾を残して中間を省く圧縮を使う。評価例ではretained ratio `p=0.1`。

これはtarget inputを変えるわけではない。Draft候補の当たりやすさは落ちる可能性があるが、最終tokenはtargetが検証するため、commitされる出力の意味論は維持される。

### 7. Remote serviceとしての故障処理も入れる

別serverのdrafterを使うため、network delayやstale responseも起こり得る。

実装はrequest ID / round IDでreplyを照合し、古いreplyを破棄する。Timeoutが連続すればcircuit breakerでremote speculationを一時停止し、target単独生成へfallbackできる。

この点は、単機GPU上のspeculative decodingをそのままnetwork越しへ移しただけではないことを示す。

## 評価

### まず見るところ

- **結論**: 空いている小型model serviceをdrafterとして借り、大型modelのthroughputを専用draft GPUなしで改善できる。
- **最大級の改善**: Qwen3-32B / LongBench / batch 64で自己回帰生成比2.28倍。
- **大型MoE**: Qwen3-235B-A22B TP=8でも最強baseline比12〜19%改善。
- **共有traffic**: draft側に通常QPSがあってもtarget throughput低下を2%未満に抑える条件を示す。
- **品質**: target verificationを通るためlossless speculative semanticsを維持する。
- **注意**: MineDraft比較はframework/version差を含み、SGLang実装PRは2026-09-03に未mergeのままclosed。

## 主要結果の読み方

SPECTREの新しさは、投機的デコードそのものより**multi-tenant servingの余剰資源をどのように再利用するか**にある。

通常、speculative decodingは「targetを速くするためにdraft modelを追加する」ので、GPU台数が増える。その追加GPU費用がspeedupの価値を相殺する場合がある。

SPECTREでは小型modelがもともと提供中で、そのGPUが低利用率な時間だけdrafterとして貸し出される。このため同じGPU fleet全体の利用率を上げられる。

また、parallel speculative decodingも常に有効ではない。Draft候補の品質とtarget/draftの相対速度に応じて直列・並列を切り替える必要がある。

この二点を合わせて、**「余ったmodel serviceをただdrafterにする」だけではなく、shared serving systemとして成立させる**ことが論文の中心である。

## 品質への影響

Target側で候補を検証し、受理されたtokenだけをcommitするため、通常のlossless speculative decoding semanticsを維持する。

Draft prompt compressionはproposal qualityや平均受理長を変える可能性があるが、target自体のpromptや最終verificationを省略するわけではない。

したがって主な失敗は品質低下ではなく、受理率低下によるperformance lossとして現れる。

## 既存研究との差

- **通常のspeculative decoding**: 専用draft modelをtargetの近くへ置く。SPECTREは別tenantの低利用率model serviceをremote drafterとして共有する。
- **Parallel speculative decoding**: draft/target重畳を固定利用する方式に対し、SPECTREはrollback率からordinary/parallelを動的選択する。
- **EAGLE-3等の専用drafter**: proposal qualityを高めるmodel設計が中心。SPECTREはservice-level resource reuseとschedulingが中心。
- **multi-model serving scheduler**: model placementだけでなく、余剰model computeを別model requestのdecode高速化へ転用する点が特徴。

## 限界

- 実験はH200中心で、network topologyやGPU世代が変わればdraft/target latency比と臨界rollback率も変わる。
- 評価model pairは3組で、任意の小型modelが任意のtargetの良いdrafterになる保証はない。
- Prompt retained ratio 0.1は特定TP8条件の設定で、他task・modelで同じ値が最適とは限らない。
- Tail latencyや厳格なSLO下でのdraft-sharing評価はthroughput評価ほど広くない。
- MineDraft比較にはvLLM/SGLangのframework差とOOM差が混ざる。
- SGLang PR #22272は2026-09-03に`merged_at=null`のままclosedで、公式mainline機能としては扱えない。
- Remote drafter利用価値は、実際に小型model serviceに余剰capacityがあることを前提とする。

## 一般的な実装上の含意

LLM servingでは、GPUを「model A専用」「model B専用」と固定的に見るだけでなく、**あるmodel serviceの余剰計算を別serviceの補助計算へ転用できるか**を考える余地がある。

ただし補助計算を並列化するときは、

1. 補助結果が無効になる確率
2. 補助側と本処理側の相対速度
3. network latency
4. 補助service本来のtraffic
5. failure時のfallback

まで含める必要がある。

この考え方はremote draftだけでなく、embedding、reranking、prefetch prediction、KV変換など「別serviceの空き資源で先回り計算する」設計にも一般化できる。
