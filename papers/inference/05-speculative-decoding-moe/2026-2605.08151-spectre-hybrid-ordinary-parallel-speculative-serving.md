# SPECTRE: Hybrid Ordinary-Parallel Speculative Serving for Resource-Efficient LLM Inference

> SPECTREは、余った小型モデルGPUを遠隔下書き器として大型モデルの検証に再利用し、下書きと検証を直列・並列の間で切り替えて、通信待ちとロールバックを抑える。

## 概要

SPECTREが対象にするのは、**複数種類のLLMを同じクラウドで提供しているときのGPU利用率の偏り**である。

例えば、ある時間帯には235B級の大型モデルへ要求が集中してGPUが混雑している一方、0.6Bや1.5Bの小型モデルサービスは要求が少なく、GPUがかなり空いていることがある。通常はこの空き計算能力を大型モデルへ直接移せない。小型モデルと大型モデルは別サービスとして動いているからである。

SPECTREは、小型モデルを一時的に**下書きモデル（下書きモデル）**として使う。小型モデルが「次の数トークンはこうなりそう」と先に候補を作り、大型の**目標モデル（目標モデル）**がまとめて検証する。これは**投機的デコード（投機的 デコード）**と呼ばれる。

投機的デコードでは、最終的なトークンは必ず目標側で確認される。したがって下書きが間違えても、その候補は捨てられるだけで、目標単独で生成した場合と同じ出力意味論を保てる。

ただし、下書きを別GPU・別サービスへ置くと新しい問題が出る。

- 下書き生成を待ってから目標検証すると、両GPUを十分重ねて使えない。
- 下書きと目標を完全に並列化すると、目標の結果によって先に作っていた下書きが無効になり、計算を捨てることがある。
- 小型モデル自身の通常ユーザーもいるため、投機的用リクエストを優先しすぎると本来の小型モデルサービスを悪化させる。

SPECTREは、この三つを提供処理 スケジューラ側で調整する。

Qwen3-235B-A22BのTP=8・バッチ128では、最強比較対象に対するスループットがLongBench-v2で19%、MRCRで12%、ShareGPTで14%向上した。Qwen3-32BのLongBench・バッチ64では自己回帰比2.28倍で、下書き側の通常要求を同時に処理しても目標側低下は2%未満だった。
## まず投機的デコードを整理する

通常の自己回帰生成では、大型LLMは1回の順伝播で基本的に1トークンずつ確定する。

```text
target: token 1を計算
        ↓
target: token 2を計算
        ↓
target: token 3を計算
```

大型モデルは1回の順伝播が高価なので、これを何百回も繰り返すと遅い。

投機的デコードでは、小型下書きが先に複数候補を作る。

```text
draft:  A → B → C → D を予測
                 ↓
target: A,B,C,D をまとめて検証
                 ↓
正しかったprefixだけ採用
```

例えばA/B/Cまでは目標も同意し、Dだけ違ったなら、1回の目標検証で3トークンを確定できる。

このとき重要なのが**受理長（受理された length）**である。下書き候補がよく当たれば目標 1回あたり多くのトークンが進む。外れやすいと下書き計算が無駄になる。

## 問題設定

### 普通の投機的デコードでは専用draft GPUが必要になる

高速化のためだけに小型下書きモデルを別GPUへ置くと、そのGPUは追加コストになる。

一方、multi-モデル 提供処理では既に小型モデルサービスが存在し、低traffic時には計算能力が余っていることがある。

SPECTREはこの**既存の余剰GPU能力**を共有drafterとして再利用する。つまり「投機的 デコード専用GPUを増やす」のではなく、「すでにオンラインだが暇なモデルを借りる」という発想である。

### 遠隔drafterでは通信と同期が増える

下書きと目標が別GPU・別serverなら、

1. 目標側の接頭辞情報を下書きへ渡す
2. 下書きが候補トークンを生成する
3. 候補を目標へ返す
4. 目標が検証する

という通信が必要になる。

このため下書きが十分速くなければ、目標が下書き待ちになって逆効果になる。

### 「並列化すれば常に速い」わけではない

普通の投機的デコードでは、下書き生成が終わってから目標検証する。論文ではこれを**通常型（通常）**と呼ぶ。

```text
draft生成 → target検証 → draft生成 → target検証
```

一方、**並列型（並列）**では目標が現在候補を検証している間に、下書きが次roundの候補を先回りして作る。

```text
target: [検証 round n]------[検証 round n+1]
draft :       [次候補生成]------[次候補生成]
```

理想的には時間を重ねられる。

しかし目標が候補をrejectすると、それ以降の文脈が変わる。下書きが古い文脈を前提に先回りして作った候補は使えず、**巻き戻し（ロールバック）**が必要になる。

したがって並列方式は、ロールバックが少ないときだけ得になる。

## 手法

SPECTREは各バッチで、最近のロールバック率を見て通常 / 並列を切り替える。

判断の基準は経験的な固定値だけではない。下書き生成時間、目標検証時間、1回に投機するトークン数、平均受理長から、「これ以上ロールバックすると並列化の重畳利得より無駄計算が大きくなる」という**臨界ロールバック率**を導く。

さらに、共有下書き serverでは投機的 リクエストを優先しつつ、小型モデル自身の通常trafficを定期的に処理する。

目標側がtensor 並列化などで極端に速い場合は、下書きが接頭辞処理に時間を使いすぎないよう、下書きにだけプロンプトを圧縮して渡す。

## 手法

### 1. Ordinary mode — 安全だが重畳しにくい

通常型では、下書きが候補を作り終わってから目標へ送る。

目標検証でrejectが起きても、次の下書き生成は正しい確定接頭辞から始められるため、先行計算の無駄が少ない。

一方、下書き生成中は目標が候補待ちになり、目標検証中は下書きが次仕事を十分進められないため、二つのサービスを直列に使う時間が増える。

### 2. Parallel mode — target検証中に次draftを作る

並列型では、目標がround nを検証している間に下書きがround n+1相当のcontinuationを生成する。

下書きが速く、候補も高確率で受理されるなら、下書き 遅延を目標検証の裏へ隠せる。

ただし前roundでrejectされると、先行下書きは誤った接頭辞から生成しているため無効になる。この無駄がロールバック コストである。

### 3. 臨界rollback率を計算する

論文では、

- `B`: バッチサイズ
- `γ`: 1 roundで下書きするトークン数
- `L`: 平均受理長
- `T_D`: 下書き 1 ステップの時間
- `T_T`: 目標 検証の時間

から通常と並列のスループットを近似する。

この二つが同じになるロールバック率`r*`を求めると、「観測ロールバック率が`r*`より低ければ並列、高ければ通常」という選択規則が得られる。

重要なのは式そのものより、**下書きと目標の相対速度が変われば最適方式も変わる**ことである。

- 下書きが非常に速い → 通常でも待ちが小さい
- 目標が速く下書きが遅い → 並列重畳の価値が増える
- 下書き精度が悪くロールバックが多い → 並列の先行計算が無駄になる

という三者のトレードオフを同じ判定に入れている。

### 4. 実行中のrollback率からmodeを切り替える

リクエストの内容によって下書きの当たりやすさは変わる。

そのためSPECTREはワークロード全体で一つのmodeを固定せず、直近roundのロールバック率を観測してバッチ単位で切り替える。

長文やタスクが変わって下書き 品質が落ちた場合には通常へ戻り、安定して当たる区間では並列へ進む。

### 5. 共有draft serverではspeculative requestを優先する

下書きモデルは本来、小型モデルを直接使いたいユーザーのリクエストも処理している。

大型目標の投機的 リクエストを通常リクエストと完全FIFOで混ぜると、下書き responseが遅れて目標 GPUまで待たせる可能性がある。目標側は高価な大型GPUなので、この待ちはシステム全体で損が大きい。

そこで投機的 リクエストを優先する。

ただし優先し続けると通常リクエストが飢餓するため、連続`K=10` 投機的 ステップの後は通常リクエストを1 round処理する。

これは「大型モデルを速くするために小型モデルユーザーを無視する」のではなく、**目標 GPU idleの損失と小型サービス公平性を両立する**ための規則である。

### 6. Targetが速すぎる場合はdraft promptだけ圧縮する

Qwen3-235B-A22BをTP=8で動かすような条件では、目標側の検証が並列化で速くなり、逆に小型下書き側が律速になることがある。

長いプロンプトを下書きへそのまま処理させると、下書き 接頭辞 KV構築だけで時間を使う。

SPECTREは下書き側に限り、プロンプトの先頭と末尾を残して中間を省く圧縮を使う。評価例ではretained 比率 `p=0.1`。

これは目標 入力を変えるわけではない。下書き候補の当たりやすさは落ちる可能性があるが、最終トークンは目標が検証するため、commitされる出力の意味論は維持される。

### 7. Remote serviceとしての故障処理も入れる

別serverのdrafterを使うため、ネットワーク delayやstale responseも起こり得る。

実装はリクエスト ID / round IDでreplyを照合し、古いreplyを破棄する。Timeoutが連続すればcircuit breakerで遠隔 speculationを一時停止し、目標単独生成へfallbackできる。

この点は、単機GPU上の投機的 デコードをそのままネットワーク越しへ移しただけではないことを示す。

## 評価

### まず見るところ

- **結論**: 空いている小型モデルサービスをdrafterとして借り、大型モデルのスループットを専用下書き GPUなしで改善できる。
- **最大級の改善**: Qwen3-32B / LongBench / バッチ 64で自己回帰生成比2.28倍。
- **大型MoE**: Qwen3-235B-A22B TP=8でも最強比較対象比12〜19%改善。
- **共有traffic**: 下書き側に通常QPSがあっても目標 スループット低下を2%未満に抑える条件を示す。
- **品質**: 目標 検証を通るため無損失 投機的 semanticsを維持する。
- **注意**: MineDraft比較はframework/version差を含み、SGLang実装PRは2026-09-03に未mergeのままclosed。

## 主要結果の読み方

SPECTREの新しさは、投機的デコードそのものより**複数利用者 提供処理の余剰資源をどのように再利用するか**にある。

通常、投機的 デコードは「目標を速くするために下書きモデルを追加する」ので、GPU台数が増える。その追加GPU費用が高速化倍率の価値を相殺する場合がある。

SPECTREでは小型モデルがもともと提供中で、そのGPUが低利用率な時間だけdrafterとして貸し出される。このため同じGPU fleet全体の利用率を上げられる。

また、並列 投機的 デコードも常に有効ではない。下書き候補の品質と目標/下書きの相対速度に応じて直列・並列を切り替える必要がある。

この二点を合わせて、**「余ったモデルサービスをただdrafterにする」だけではなく、共有 提供処理 システムとして成立させる**ことが論文の中心である。

## 品質への影響

目標側で候補を検証し、受理されたトークンだけをcommitするため、通常の無損失 投機的 デコード semanticsを維持する。

下書き プロンプト 圧縮はproposal 品質や平均受理長を変える可能性があるが、目標自体のプロンプトや最終検証を省略するわけではない。

したがって主な失敗は品質低下ではなく、受理率低下による性能 損失として現れる。

## 既存研究との差

- **通常の投機的 デコード**: 専用下書きモデルを目標の近くへ置く。SPECTREは別tenantの低利用率モデルサービスを遠隔 drafterとして共有する。
- **並列 投機的 デコード**: 下書き/目標重畳を固定利用する方式に対し、SPECTREはロールバック率から通常/並列を動的選択する。
- **EAGLE-3等の専用drafter**: proposal 品質を高めるモデル設計が中心。SPECTREはサービス-水準 資源 reuseとスケジューリングが中心。
- **multi-モデル 提供処理 スケジューラ**: モデル 配置だけでなく、余剰モデル 計算を別モデル リクエストのデコード高速化へ転用する点が特徴。

## 限界

- 実験はH200中心で、ネットワーク topologyやGPU世代が変われば下書き/目標 遅延比と臨界ロールバック率も変わる。
- 評価モデル pairは3組で、任意の小型モデルが任意の目標の良いdrafterになる保証はない。
- プロンプト retained 比率 0.1は特定TP8条件の設定で、他タスク・モデルで同じ値が最適とは限らない。
- Tail 遅延や厳格なSLO下での下書き-sharing評価はスループット評価ほど広くない。
- MineDraft比較にはvLLM/SGLangのframework差とOOM差が混ざる。
- SGLang PR #22272は2026-09-03に`merged_at=null`のままclosedで、公式mainline機能としては扱えない。
- 遠隔 drafter利用価値は、実際に小型モデルサービスに余剰容量があることを前提とする。

## 一般的な実装上の含意

LLM 提供処理では、GPUを「モデル A専用」「モデル B専用」と固定的に見るだけでなく、**あるモデルサービスの余剰計算を別サービスの補助計算へ転用できるか**を考える余地がある。

ただし補助計算を並列化するときは、

1. 補助結果が無効になる確率
2. 補助側と本処理側の相対速度
3. ネットワーク 遅延
4. 補助サービス本来のtraffic
5. failure時のfallback

まで含める必要がある。

この考え方は遠隔 下書きだけでなく、embedding、reranking、プリフェッチ prediction、KV変換など「別サービスの空き資源で先回り計算する」設計にも一般化できる。
