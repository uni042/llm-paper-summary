# Accelerating LLM Inference with Staged Speculative Decoding

## 概要

小バッチの自己回帰復号では、モデルの重みを毎トークン読み込む一方で行列演算のバッチが小さいため、GPUの演算器を十分に使えない。本研究は投機的復号（speculative decoding）の候補を一本の直線ではなく木構造へ広げ、さらに小型のドラフトモデルも別の極小モデルで投機実行する「段階投機的復号」を提案する。大きな対象モデルを一度実行する間に複数の候補トークンを検証して、重み読出しあたりの確定トークン数を増やす設計である。

論文のRTX 4090実機実験では、対象モデルがGPT-2-Large（762Mパラメータ）、第一ドラフトが40M GPT-2、第二ドラフトがKatz backoff trigramである。HumanEvalの164プロンプトに対し、決定的復号の生成速度は通常の150 token/sから標準投機で350 token/s、段階投機で475 token/sとなる。段階投機は通常比3.16倍、標準投機比1.36倍である。Top-kサンプリングでは298 token/sとなり、通常比1.98倍、標準投機比1.36倍だった。速度向上はモデルの精度を落として出力を近似するためではなく、対象モデルの検証を通す投機的な計算の並べ替えから得る。

投機的復号は、ドラフトモデルが提案した候補を対象モデルが検証し、受理されたトークンをまとめて確定する。候補が拒否されればその先は捨てられるため、ドラフトと対象の一致率が低いほど利得は縮む。木構造は複数の可能な継続を浅い分岐で検証し、第二段のドラフトは第一ドラフトが候補を作る費用自体を減らす。この二つを同時に改善する点が本研究の主張である。

## 問題設定と性能上の制約

一般的なデコーダ型LLMは入力を事前充填してKVキャッシュを作った後、次トークンの確率を出し、選んだトークンを次の入力として繰り返す。復号時にはモデル重みを何度もGPUメモリから読み込む。単一要求・小バッチでは1回の重み読出しに対する演算回数が少なく、演算強度が低い。論文のFP16・バッチ1のGPT-2-Largeでは演算強度を約1とし、RTX 4090での通常復号が150 token/s、演算利用率が約0.13%にとどまる例を示す。

標準投機的復号は小さなドラフトが複数トークンを予測し、大きな対象モデルがそれらを一度に検証する。検証が一括で済むため重みを読み込む回数が減るが、候補列の後ろへ進むほど前のトークンすべてが受理されている必要がある。仮に各位置で受理率が一定でも、長い連続受理の確率は位置数に応じて急速に下がる。したがって線形候補を無制限に長くしても、検証に使った計算が無駄になる。

さらに第一ドラフトもTransformerであり、小バッチでは重み読出し帯域に律速される。標準投機の候補数を増やすと、対象モデルの一括検証よりドラフト側の逐次候補生成に時間がかかる逆転が起きる。そこで本研究は「大モデルが一回に検証する候補の有効性」と「候補を生成する小モデルの費用」を同時に下げる。

## 手法

### 1. 線形候補を木へ変える理由

線形の投機候補は、最も確率が高い次トークンを繰り返し選んで長い一本道を作る。候補が深くなるほど、その前に一つでも不一致があると後続が無効になる。木構造では、同じ候補数を使うなら長い一本道の末尾を伸ばすより、浅い位置で第2候補や第3候補を含める方が対象モデルの実際の継続に合う経路を増やせる。結果として一回の対象モデル検証で確定できるトークン数の期待値を高める。

木の内部ノードは第一ドラフトを実行して次の分岐を作る必要があるが、葉ノードはそれ以上ドラフトを呼ばなくても検証バッチに含められる。木を幅広くすると、内部ノードに対して葉ノードの数を増やせるため、候補数の割にドラフトの追加呼出しが少なくなる。木の同じ深さの複数ノードはドラフトモデルへバッチとして投入でき、第一ドラフトも重み読出しの費用をまとめられる。木の深さに対応する回数だけドラフトを実行する構成へ近づける。

### 2. 木の位置情報・注意マスク・KV管理

対象モデルへ木全体を一つのバッチとして渡すとき、通常の直列系列向け因果注意をそのまま適用してはいけない。異なる分岐のトークン同士が互いを見てしまうと、実際にはあり得ない文脈を条件として検証することになる。論文は既存のKVキャッシュへの注意と新規候補バッチ内の自己注意を分け、位置埋め込みを木の深さに合わせ、バッチ内の因果マスクを祖先・子孫関係だけに許可するよう構成する。

木の各ノードのKV状態は一時領域へ保存する。対象モデルの検証で採用された経路が確定したら、その経路に対応するKVスライスだけを本体のKVキャッシュへ追加する。採用されなかった別枝のKVを本体へ混ぜると、その後の生成分布が変わってしまう。候補木の並列検証を成立させるためには、木の構造に合う注意マスクとKVの選別が不可欠である。

### 3. 第一ドラフトの候補生成も投機実行する

木構造で候補を広げても、40Mの第一ドラフトが各内部ノードを逐次生成していては、候補作成が新しいボトルネックになる。そこで第一ドラフトの前にさらに小さな第二ドラフトを置き、第一ドラフトに対しても投機的復号を適用する。論文では第二ドラフトとしてKatz backoff trigramを用いる。これは大きなニューラルネットではなく、直前の少数トークンから次の候補を予測する統計的言語モデルである。

構成は「対象モデル762M GPT-2-Large → 第一ドラフト40M GPT-2 → 第二ドラフトKatz三連接モデル」となる。第二ドラフトは空白、改行、定型構文のような予測しやすい部分を高速に提案し、第一ドラフトがそれを検証する。さらに第一ドラフトの候補木を対象モデルが検証する。最終出力は常に対象モデルの分布に従うよう受理・棄却を行うため、第二ドラフトの確率をそのまま最終回答に使う方式ではない。

### 4. 第二ドラフトの構築と分布保持

第二ドラフトのKatz backoff trigramは、第一ドラフトモデルを温度1.5で約2時間動かして生成した1億2000万トークンから構築する。第一ドラフトが頻繁に出す定型的な継続を、さらに安価なモデルで先読みするための設計である。コード生成では空白やインデントのような低エントロピー部分が多く、N-gramでも有用な候補を提案できる。

決定的復号では対象モデルが選ぶ最尤トークンと整合する候補だけを確定する。確率的サンプリングでは受理・棄却の補正により対象分布を維持することが重要である。論文は対象モデルの出力品質を変えないことを設計要件とし、近似的な低精度モデルへ置き換えて品質を犠牲にする方法とは区別する。補正を省いてドラフトの候補をそのまま出すなら、この論文の分布保持の主張は成立しない。

### 5. メモリ帯域を演算へ交換する設計

投機的復号では、候補を一括検証するため対象モデルの演算量は増え得る。しかしバッチ1で重み読出し帯域が律速のとき、重みを一度読んで複数トークンを検証できれば、1確定トークンあたりの帯域負担が減る。木構造は受理される候補数を増やし、第二段投機は第一ドラフトの帯域負担を減らす。小バッチに特有の低い演算強度を改善する方式であり、十分に大きなバッチで演算器が既に飽和しているサービングへ同じ倍率を期待するべきではない。

## 評価

### 実験条件と比較対象

| 項目 | 一次論文の条件 |
|---|---|
| GPU | NVIDIA RTX 4090、他の負荷がない状態 |
| 対象モデル | GPT-2-Large 762M、The StackのPython部分で微調整 |
| 第一ドラフト | 40MパラメータのGPT-2、同じPythonデータで学習 |
| 第二ドラフト | Katz backoff trigram、第一ドラフト生成の120Mトークンから構築 |
| 評価データ | HumanEval 164問のプロンプト |
| 比較 | 通常の逐次復号、標準投機的復号、段階投機的復号 |
| 復号設定 | 決定的復号、Top-kサンプリング（k=50、温度1） |
| 速度指標 | 一秒あたりの確定出力トークン数 |
| 帯域指標 | 通常復号のメモリ帯域消費を1とした相対値 |

この条件はコード生成の小バッチを想定している。HumanEvalの164問を使うが、主指標はコードのpass@1の改善ではなく、対象モデルの出力分布を維持したまま何トークンを毎秒確定できるかである。ドラフトが間違えても対象モデルが最終検証するため、ドラフトの予測正答率だけを性能と同一視しない。

### 確定トークン速度

| 復号方式 | 通常逐次復号 | 標準投機 | 段階投機 | 段階投機の改善 |
|---|---:|---:|---:|---|
| 決定的 | 150 token/s | 350 token/s | 475 token/s | 通常比3.16倍、標準比1.36倍 |
| Top-k（k=50、T=1） | 150 token/s | 219 token/s | 298 token/s | 通常比1.98倍、標準比1.36倍 |

決定的復号では、対象モデルが一意に選ぶ次トークンをドラフトが予測しやすいため、一回の検証で複数のトークンを確定できる。標準投機で150から350 token/s、段階投機でさらに475 token/sへ改善した。段階投機の標準投機に対する利得は約36%であり、3.16倍という値は**通常の逐次復号を分母にした倍率**である。

Top-kでは確率的な選択によって候補が棄却されやすくなる。標準投機は219 token/s、段階投機は298 token/sで、どちらも決定的復号より利得が小さい。それでも段階投機は標準投機より約36%速い。確率的復号で通常比3.16倍という値を使うのは誤りである。

### 相対メモリ帯域

| 条件 | 通常逐次復号 | 標準投機 | 段階投機 |
|---|---:|---:|---:|
| 決定的復号の相対帯域 | 1.00 | 0.31 | 0.23 |
| Top-kの相対帯域 | 1.00 | 0.48 | 0.35 |

帯域消費が決定的復号で0.23へ下がったことは、段階投機が通常の約23%の重み読出し帯域で同じ出力系列を確定したことを意味する。標準投機の0.31からも改善しており、速度の改善が帯域律速の緩和と整合する。ただし帯域が23%になったから速度が単純に1/0.23倍になるわけではない。ドラフト実行、木構築、注意マスク、KV整理、Python制御など別の費用が残るためである。

### 生成内容による感度と実装オーバーヘッド

論文はプロンプトごとの速度差が大きいことを負の結果として挙げる。現実的なコード生成プロンプトでも約2倍から最大10倍の利得まで変動し、インデントや空白の多いコードはN-gram段が容易な継続を先読みできるため速い。複雑な条件分岐や予測しにくいトークンが密な生成では、対象モデルへ頻繁に戻るため利得が小さくなる。3.16倍は全プロンプトで保証される値ではない。

プロファイルでは実装時間の約35%がPython基盤のオーバーヘッドだった。これは対象モデルの数学的な検証処理だけでなく、試作ランタイムの木管理や制御費が測定に含まれていることを示す。より効率的な実装なら改善余地がある一方、実際の別システムへ移植したときに同じ倍率を出す保証もない。

### 受理元の観察と品質保持

論文は生成トークンが第二ドラフト、第一ドラフト、対象モデルのどの段階で提案されたかを可視化する。空白や定型的な構文はN-gram段からの候補が多く、条件分岐のような難しい箇所は大きな対象モデルの判断を必要とする。これは各段階が予測しやすさの異なる部分を分担するという直感を支持するが、有限の候補木と予算のため、容易なトークンが常に最下段で確定するわけではない。

最終的な出力分布は対象モデルの検証により維持する設計であり、生成品質を落として速度を稼ぐ方式ではない。評価の中心は同じ対象モデルを用いた生成速度と帯域であり、HumanEvalのコード正答率が通常復号より改善したという新しい品質向上の主張ではない。出力分布を保つことと、あらゆるサンプリング条件で同一の出力文字列が得られることも区別する。

## 既存研究との差

標準投機的復号はドラフトモデルの一本道を対象モデルへ渡すため、長い候補列の後半が無駄になりやすい。本研究は浅い位置で分岐する木にして、同じ候補予算でも受理される継続を増やす。加えて第一ドラフトの生成も第二ドラフトで投機実行するため、対象モデルの検証回数だけでなく候補生成側の帯域費も減らす。

単純な量子化やKVキャッシュ圧縮は一回のモデル実行で扱う重み・キャッシュの費用を減らす。段階投機は大モデルの逐次呼出しをまとめ、複数候補を一括検証することでメモリ帯域を有効利用する。両者は異なる軸の最適化であり、論文も小バッチの帯域律速条件を主対象としている。

## 限界と負の結果

実測は単一RTX 4090、GPT-2-Large 762M、HumanEvalのコード生成に集中する。7Bや70Bモデル、複数GPU、連続バッチ化したクラウドサービング、長文脈生成に同じ倍率が成立するとは示していない。著者は大型モデルや追加投機段への拡張を将来案として述べるが、20B級モデルの実測結果ではない。

Top-kのような確率的復号では候補棄却が増え、通常比の速度利得は決定的復号の3.16倍から1.98倍へ下がる。生成内容が高エントロピーだとドラフトの先読みが外れやすく、利得が小さい。さらにPython実装の制御費が約35%あるため、試作の実測値を純粋なアルゴリズム上限と解釈できない。木の位置情報・注意マスク・KV管理を正しく実装しなければ、対象モデルの出力分布保持という重要な性質も失われる。
