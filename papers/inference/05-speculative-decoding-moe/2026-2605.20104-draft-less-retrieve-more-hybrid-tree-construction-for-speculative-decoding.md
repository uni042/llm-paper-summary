# Draft Less, Retrieve More: Hybrid Tree Construction for Speculative Decoding

> 動的剪定は投機木を速くするが、剪定した枝の中に本来受理できる候補があれば平均受理長が落ちる。Graftは剪定で空いた候補枠を捨てず、対象モデルの過去検証から得た安価な検索候補で「接ぎ木」する。対象モデルが一度に検証するノード総数は増やさず、ドラフト計算だけを安い検索へ置換する。

## 概要

木型投機的復号では、候補木を大きくすれば対象モデルが一回で受理できる経路を見つけやすい。しかしEAGLE-3のような自己回帰ドラフト木は、木を深く・広く作るほどドラフトモデルの前向き計算、KVキャッシュ読出し、VRAM帯域を消費する。受理長が増えても候補生成が重ければエンドツーエンド速度は伸びない。

そこでECHOなどの動的深さ方式は、ドラフト確信度が低い場所で木を早めに打ち切る。この剪定はドラフト時間を減らす一方、最終木は元の密な木の部分木にしかならない。削った候補を後から復元しない限り、密な木で受理できた経路を失う可能性があり、平均受理長（Mean Accepted Length, MAT）には構造上の上限が生じる。

Graftは剪定を「候補削除」ではなく「候補予算の解放」と捉える。低確信枝を削って空いたノード枠へ、検索で得た安価な候補を追加する。検索候補はGPU常駐の隣接行列から作り、その行列は対象モデルの検証結果でオンライン更新する。最終的な候補数は元のEAGLE-3固定木と同じ上限に保つため、対象モデル側の一括検証費用を増やさず、ドラフト計算の一部を安価な候補生成へ置換できる。

## 問題設定

### 剪定だけでは元の密木を超えられない

元の密な候補木を (T_E)、動的剪定後を (T_pi) とすると、剪定だけなら常に (T_pisubseteq T_E) である。同じ対象モデル検証規則なら、候補を削ることで得られる最大受理長は密木を超えない。

剪定は分母側の候補生成時間を減らすが、分子側のMATも落とす可能性がある。特に深さごとに何度も剪定判断すると、それぞれの誤判定確率が小さくても「どこか一箇所で有効経路を切る」累積確率が増える。

Graftはこの失われた候補枠へ、元の部分木にはなかった検索枝Gを足し、
(T_G=T_picup G)
とする。総ノード数は元の固定予算以下だが、集合としては元密木の単なる部分木でなくなるため、剪定だけの構造上限から外れる。

### 検索にも費用をかけ過ぎてはいけない

検索候補を作るためにCPU検索、外部データストア、追加の対象モデル推論を使うと、節約したドラフト時間を相殺する。したがって検索はGPU内で小さな状態を参照し、既に実行する対象モデル検証から更新できる必要がある。

Graftの隣接行列はこの条件を満たすよう設計される。

## 手法

### 1. 少数の較正済み深さだけで剪定判断する

Graftはすべての深さで細かく剪定判断しない。検証用データで確信度が受理可否を比較的よく分ける深さを選び、浅・中・深など少数の剪定チェックポイントだけを使う。

低確信と判定したら、それ以降の自己回帰ドラフト展開を止める。早い段階で止めるほど残るドラフトノード (K^{draft}) は少なくなり、そのぶん検索へ使える (K^{ret}) が増える。

固定検証予算 (K_{max}) は、
(K_{max}=K^{draft}_s+K^{ret}_s)
として常に保つ。したがって剪定が強い要求でも対象モデルへ渡す最大候補数を増やさない。

### 2. GPU常駐の隣接行列から検索枝を作る

検索状態Mは、あるトークンIDを行とし、その後に来やすい上位kトークンIDを保持するGPU常駐の隣接行列である。CPUとの同期や大規模近傍探索を必要としない。

現在トークンからMを辿ることで、ドラフトモデルを何層も自己回帰実行する代わりに複数トークンの候補経路を安価に構成する。剪定で空いた「位相的な穴」へ、この検索枝を接続する。

検索枝は単にprompt中のn-gramを再利用するだけではなく、対象モデル自身が過去の検証で与えた分布から更新されるため、生成が進むほど現在文脈に適応する。

### 3. 対象モデル検証の全ノードでMを更新する

対象モデルは最終ハイブリッド木を一回で検証し、各候補ノードに対する次トークン分布を得る。Graftは受理されたノードだけでなく、棄却された候補ノードについても、その位置で対象モデルが与えた上位k後続トークンをMへ書き戻す。

つまり棄却候補も「そのprefixなら対象モデルは次に何を好んだか」という学習信号になる。追加の対象モデル前向き計算は不要で、通常の木検証結果を副産物として使う。

長文脈ではpromptの事前入力処理（prefill）で得た分布もMの初期化へ使う。文脈が長いほど再利用可能な局所遷移が増え、同時に自己回帰ドラフトのKV読出しは重くなるため、検索置換の価値が大きくなる。

### 4. 最終木を通常の対象モデル規則で一括検証する

残したドラフト枝と接ぎ木した検索枝を統合し、標準の木注意マスクで対象モデルへ一回だけ渡す。対象モデルの検証規則自体は変更しない。

検索候補が誤っていても単に棄却されるため、生成分布を近似候補へ置き換えるわけではない。したがってGraftは訓練不要かつ無損失の投機的復号として扱える。

## 評価

### 評価条件

| 項目 | 条件 |
| --- | --- |
| GPU | 8×NVIDIA H20 |
| 復号 | 原則貪欲復号（greedy decoding） |
| 短文モデル | Vicuna-13B、LLaMA-3.1-8B、Qwen3-8B/32B/235B |
| 短文課題 | HumanEval、GSM8K、CNN/DM、Alpaca、MT-Bench |
| 長文モデル | LLaMA-3.1-8B、Qwen3-4B/8B/14B |
| 長文課題 | QMSum、GovReport、MultiNews、LCC、RepoBench-P |
| 主要比較 | EAGLE-3、ECHO、DDD、TR、Medusa等。長文はEAGLE3-64K、MagicDec、TokenSwift等 |
| 実装 | 短文/長文はHugging Face Transformers、高batchはSGLang v0.5.4 |
| 指標 | MAT、自己回帰比speedup、長文ではprefill後のdecode時間、SGLangではthroughput |

### 短文の代表結果

| モデル | EAGLE-3系平均speedup | Graft平均speedup | 相対改善 |
| --- | ---: | ---: | ---: |
| Vicuna-13B | 3.91× | **4.20×** | +7.4% |
| LLaMA-3.1-8B | 3.73× | **3.97×** | +5.9%前後 |
| Qwen3-8B | 2.10× | **2.43×** | +15.3% |
| Qwen3-32B | 2.12× | **2.49×** | +17.4% |
| Qwen3-235B | 1.71× | **2.09×** | +21.8% |

最大値はVicuna-13B/HumanEvalの5.41×である。Qwen3-235Bでは候補受理が難しくEAGLE-3の平均速度が1.71×に留まるが、Graftは2.09×へ改善する。モデルが大きいほど、無駄なドラフト計算を減らす価値が相対的に上がる。

剪定のみのECHOと比べても、Graftは全モデル群で平均speedupとMATの両方を改善する。これは「剪定で速くなっただけ」ではなく、検索が削除候補のカバレッジを実際に補っていることを示す。

### 長文脈

長文では共有promptのprefill時間を除き、decode時間だけでspeedupを比較する。QMSum、GovReport、MultiNews、LCC、RepoBench-PでEAGLE3-64Kより一貫して改善し、文脈長4K〜32Kのアブレーションでは、文脈が長くなるほど検索状態が豊かになる一方、ドラフトKV読出しも重くなるためGraftの利点が増える傾向を示す。

### 高batch配信

Qwen3-8BをSGLangでbatch 1〜16まで評価する。HumanEvalではbatch 16でEAGLE-3が2416.28 token/s、Graftが2525.83 token/sで、MATも3.10から3.24へ上がる。

ただし高batch版はCUDA Graphと固定shapeを壊さないため、単一要求版のように実際のドラフト深さを可変にせず、固定木を作った後で低確信ノードを検索ノードへ置換する簡略実装である。著者らも検索カーネルとスケジューリングは未最適化としている。

## 既存研究との差

EAGLE-3は密な固定木を作り高い候補カバレッジを得る。ECHO/DDD等は低確信な後段を剪定してドラフト費用を減らすが、元木の部分木に留まるためMATを失いやすい。

Graftは「剪定で削る」と「検索で増やす」を固定予算内で連結する点が違う。検索のみを固定少量足す方式では、ドラフトが難しい要求でも検索へ十分な枠を割けない。Graftでは剪定量そのものが検索予算になるため、要求難易度へ追従する。

## 限界・実装状況

主要評価は8×H20であり、GPUメモリ帯域・モデル分割・通信構成が異なる環境では倍率も変わる。特にQwen3-235Bは複数GPU実行なので、小規模単GPUモデルへ同じ改善率を外挿できない。

高batch版はまだ完全最適化ではなく、動的深さをそのままSGLangの固定CUDA Graphへ統合していない。DFlash型ブロックドラフトへの適用も論文では予備的実験であり、本格的な配信実装ではない。

また検索行列は生成中の対象モデル信号で徐々に良くなるため、非常に短い生成や繰り返しの少ない文脈では利得が小さくなり得る。
