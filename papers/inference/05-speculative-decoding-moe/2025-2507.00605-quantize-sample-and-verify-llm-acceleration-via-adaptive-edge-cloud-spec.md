# Quantize-Sample-and-Verify: LLM Acceleration via Adaptive Edge-Cloud Speculative Decoding

## 概要
エッジ・クラウド投機的復号（edge-cloud 投機的復号）では、端末上の小型言語モデル（small language モデル; SLM）が複数のドラフトトークンを生成し、クラウド上の大規模言語モデル（large language モデル; LLM）がまとめて検証する。計算だけ見ればSLMが軽いため有利だが、端末からクラウドへ候補トークンとその確率情報を送る必要があり、低帯域回線では通信時間がLLM計算の削減分を打ち消す。

確率ベクトルを量子化すれば通信量は減るが、「元分布から標本した後に確率情報を量子化する」標本-quantize（S-Q）方式では、クラウドが検証時に使うproposal分布と実際に候補を生成した分布が一致しない。そのため通常の投機的復号が持つ「最終出力分布は対象 LLMと同じ」という性質が崩れ、とくにsampling temperatureが高い条件で品質差が現れる。

提案するQuantize-Sample（Q-S）は順序を逆転させ、**先にSLM確率分布を量子化し、その量子化分布から候補を標本し、クラウドも同じ量子化分布をproposalとして検証する**。これにより標準の投機受理・残差sampling則を適用でき、最終トークン分布がLLM分布と一致することを理論的に保証する。さらに通信速度とsemantic uncertaintyに応じてドラフト長と量子化精度を同時に選ぶ動的制御を加え、通信を含むトークン スループットを最大化する。

## 問題設定
1回の反復でSLMが \(L^t\) 個のドラフトトークンを生成すると、cloudへ送る情報にはトークン IDと検証用proposal確率が含まれる。語彙数を \(V\)、トークンごとの量子化確率情報を \(b^t\) bit、uplink速度を \(C_u^t\) とすると、論文のpacket-level モデルではuplink時間は
\[
T_u^t=\frac{L^t(\lceil\log_2 V\rceil+b^t)}{C_u^t}
\]
で表される。長いドラフトはLLM呼出し回数を減らせる可能性がある一方、送信量とSLM逐次生成時間を増やす。

bit数を減らせば通信は速くなるが、proposal分布が粗くなり受理率へ影響する。さらにtemperature上昇でSLM/LLMのentropyが増えると、proposalと対象の重なりも変わる。したがってドラフト長と量子化精度を固定せず、経路 状態と現在のsemantic uncertaintyを同じ最適化へ入れる必要がある。

## 手法
### Quantize-Sampleによる厳密な分布保存
端末はSLMの語彙確率 \(q\) を格子量子化して \(\hat q\) を作り、候補トークンを元の \(q\) ではなく \(\hat q\) から標本する。cloudへは候補IDと \(\hat q\) を復元できる量子化indexを送り、LLM 対象分布 \(p\) と \(\hat q\) を使って通常の投機的 検証を行う。

proposalそのものが \(\hat q\) から生成されているので、受理確率と棄却時のresidual samplingを \(\hat q\) に対して正しく計算すれば、確定トークンの分布は \(p\) と一致する。論文は命題としてこの同値性を示す。量子化誤差を小さくして「近似的に品質を保つ」のではなく、投機的復号の分布補正機構へ量子化分布を正しく組み込むことで対象 分布を保存する。

S-Qでは候補を元 \(q\) から標本した後に送信分布だけを量子化するため、candidate generatorとverifierが異なるproposalを仮定する。実験ではこの不整合が高temperatureでROUGE-2低下として現れる。

### 確率ベクトルの格子量子化
確率simplex上で、各確率 \(q_i=o_i/\ell\) と表せる離散格子 \(Q_\ell\) を構成し、元分布に近い格子点へ写像する。\(\ell\) を大きくすれば確率解像度は上がるが、格子点indexを送るbit数も増える。論文のquantizerは \(O(V\log V)\) で、現代GPU上ではバッチ当たり数microseconds程度の追加時間としている。

ここで圧縮しているのはトークン値ではなく、edge→cloudへ送るproposal probability vectorである。通信削減と検証 受理率の交換条件を直接操作するための量子化である。

### 通信込み遅延モデル
1反復の時間を、SLMの \(L^t\) トークン逐次生成 \(L^tT_{\rm SLM}\)、uplink \(T_u^t\)、LLM並列検証 \(T_{\rm LLM}\)、downlink \(T_d^t\) の和として記述する。LLMは複数ドラフト トークンを一度に検証するため、対象計算は \(L\) 倍にならない一方、SLM生成と送信はドラフト長の影響を受ける。

各位置の受理確率から期待accepted トークン数を求め、単位時間当たり確定トークン数をスループット目的にする。これにより、受理率だけを上げる高精度・長ドラフトが通信遅延のせいで逆効果になる条件も評価できる。

### DDQNによる動的制御
状態にはuplink 経路 状態と生成分布のuncertaintyを含め、actionとして次反復のドラフト長 \(L^t\) と格子精度 \(\ell^t\)、すなわち送信bit数を選ぶ。方策は二重深層Qネットワーク（Double Deep Q-Network; DDQN）の軽量Q-ネットワークをoffline学習し、各反復が最終スループットへ与える寄与をreward化する。

低rate時には低bit化の価値が大きく、entropyが高い時にはproposal精度を上げる価値が増える。固定bit幅・固定ドラフト長や「全トークンが受理されたらドラフトを1伸ばし、途中棄却ならaccepted数へ戻す」単純heuristicより、両状態を同時に見て設定を選ぶ。

## 評価条件
| 観点 | 条件 |
|---|---|
| cloud LLM | OPT-13B |
| edge SLM | OPT-125M |
| タスク | CNN/DailyMail abstractive summarization |
| ハードウェア測定 | NVIDIA A100 40GB、バッチ サイズ 1 |
| edge 遅延 | OPT-125MもA100で測定し、代表edge GPUとのトークン生成速度比でscale |

| 代表平均uplink | low-rate 350 kbps、high-rate 4 Mbps |
| downlink | delay-freeを仮定 |
| 比較 | LLM単独、通信なしcloud-only SD、S-Q、静的 Q-S、heuristic 適応型、動的 Q-S |
| 品質 | ROUGE-2、トークン Shannon entropy |
| 効率 | トークン スループット (トークン/s) |

## 主要結果
sampling temperatureを0〜1へ変えると、S-Qは高temperature側でLLMのROUGE-2から外れる一方、Q-Sは静的/動的のどちらでもLLMと同じトークン品質を維持する。これはQ-Sの分布保存命題に対応し、量子化通信を入れても対象モデルの出力分布を変えないことを確認する評価である。

スループットは平均350 kbpsの低rateと4 Mbpsの高rateを分けて評価する。通信費がないcloud-only 投機的復号が上限として最速であり、edge-cloud方式も回線が速くなるほどそれへ近づく。一方Q-S edge-cloudはLLM単独より高いトークン スループットを示す範囲があり、低rateでも品質を犠牲にせず投機による計算削減を利用できる。

動的 Q-Sは全temperature範囲で静的 比較対象とheuristic 適応型 policyを上回る。temperatureが上がると受理率が難しくなり全方式のスループットは下がるが、経路とentropyの両方を観測してドラフト長・bit精度を変える方策の優位は維持される。評価が実証するのは、(1) Q-Sなら通信圧縮と対象-分布保存を両立できること、(2) 時変経路とsemantic uncertaintyを共同制御へ入れると固定設定より高スループットになること、の二点である。

## 既存研究との差
従来のedge-cloud 投機的復号ではproposal確率を無損失に送るか、標本後の確率を量子化して帯域を減らす構成がある。前者は通信量が大きく、後者はcandidate生成分布と検証分布の不一致で対象 分布保証を失う。Q-Sは処理順をquantize→標本へ変えるだけで、この不一致を解消する。

また通常の投機的復号最適化はドラフト/対象の計算比と受理率を主に見るが、本論文はuplink/downlinkを遅延式へ明示的に入れ、ドラフト長と送信確率精度を共同で制御する。したがって計算カーネルだけでなく、SLMとLLMが物理的に離れた配置での通信-compute trade-offを対象にする。

## 限界
評価はOPT-125M/OPT-13B、CNN/DailyMail、A100上の制御測定と経路 シミュレーションに限定される。edge側実行時間は実スマートフォン等でエンドツーエンド測定したものではなく、A100実測を代表edge GPUとの速度比でscaleした値である。downlinkも遅延なしと仮定し、packet loss、無線jitter、cloud queueing、端末thermal throttlingは扱わない。

DDQNはoffline学習を必要とし、実環境の経路/semantic 状態が学習分布から外れると最適性は保証されない。さらにQ-Sは対象分布を厳密に保存するが、粗い量子化でproposalと対象の重なりが悪化すれば受理率は下がるため、「品質保存」と「スループット改善」は別の性質である。
