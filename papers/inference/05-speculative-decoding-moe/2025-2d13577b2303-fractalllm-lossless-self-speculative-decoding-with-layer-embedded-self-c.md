# FractalLLM：デコーダ層内に圧縮モデルを埋め込む自己投機的復号

## 概要

FractalLLMは、自己回帰言語モデルのトークン逐次生成を減らすため、元のデコーダの途中に小さな圧縮モデルを挿入する自己投機的復号（Self-Speculative Decoding）の方式である。独立した草稿モデルを別途学習するのではなく、元モデルのデコーダ層・埋込み・言語モデル出力ヘッドを8ビット線形量子化した補助経路を作り、元の層を実行する途中で複数の未来トークン候補を生成する。候補は元モデルの完全な順伝播で検証するため、著者らは通常の決定的な自己回帰復号と同一の出力を保てると説明する。

論文のRTX 3090実験では、CodeLlama-13BのHumanEvalで基準の1.79トークン/秒が4.43トークン/秒となり、2.47倍の高速化を報告する。Llama-3 8BではCNN/DailyMail要約の1.01から2.15トークン/秒、2.12倍である。一方で、**これらの実験ではKVキャッシュを使っていない**。通常のvLLMやllama.cppなどで行うキャッシュ付き生成に対して同じ倍率が出ると結論付けてはいけない。この制約は論文のLimitationsに明記されており、評価を解釈する際に最も重要である。

## 問題設定：草稿の質と生成回数の交換条件

通常の自己回帰復号は、1トークンを確定するたびにモデルの順伝播を行う。投機的復号では、安価な草稿器が複数トークンを先に提案し、重い標的モデルがまとめて検証する。草稿が長く受理されれば標的モデルの逐次呼び出し回数を減らせるが、草稿の生成に時間がかかると利益は相殺される。FractalLLMの問題設定は、この二つの費用を同一モデル内部の計算共有によって同時に抑えることである。

外部の小型草稿モデルを別に使う場合、追加のモデル重みや実行環境が必要になる。複数の未来予測ヘッドを付ける方式では追加学習が必要になることがある。既存の自己投機的復号では、元モデルの浅い層だけを走らせることで草稿を作れるものの、草稿生成自体はトークンごとの逐次処理になりやすい。FractalLLMは「1回の元モデル順伝播の途中で複数の草稿を更新する」ことを狙う。

著者らは総生成時間を `T_total = N_phase × T_phase` と整理する。`N_phase`は草稿・検証の組を繰り返す回数、`T_phase`は1組の処理時間である。草稿の精度が高ければ受理長が伸びて`N_phase`が減るが、草稿器を大きくすると`T_phase`が増える。したがって単に草稿を多く生成する、あるいは圧縮モデルを大きくするだけでは最速にならない。挿入層数と草稿窓幅を調整する理由がここにある。

## 手法

### 1. 元モデルの途中へ「フラクタル層」を挿入する

Fractal Layerは、元のデコーダ層`L_i`の直前へ、元モデル由来の圧縮デコーダ層、圧縮埋込み層、圧縮言語モデル出力ヘッドを挿入した構造である。圧縮経路は8ビットの線形量子化で作る。元モデルの層を削除して置き換えるわけではなく、通常の検証経路は保持する。元モデルの層`L_1 ... L_(i-1)`が作った途中隠れ状態`h_(i-1)`を補助経路の入力にするため、最初の`i-1`層を草稿トークンごとに再実行する必要がない。

挿入位置は重要である。浅い位置で草稿を作れば残りの元モデル計算を利用できるが、途中特徴が未熟で草稿精度が低い可能性がある。深い位置ではより情報量の多い特徴を使える一方、補助経路が扱う層構成と計算量が変わる。論文は挿入位置と層数の感度を調べるが、任意のモデルで最適位置を自動選択する一般アルゴリズムまでは提示していない。

### 2. 草稿窓を設け、圧縮上位層から候補を並列に得る

草稿段階では、既存の接頭列の末尾に、文脈情報をまだ持たない特別な草稿用トークンを`w`個追加する。`w`が草稿窓幅である。挿入位置の手前まで元モデルで計算した隠れ状態を、圧縮した上位層`L'_i ... L'_l`へ通し、接頭列末尾と新規草稿スロットに対応する予測分布を一括して求める。圧縮した出力ヘッドの最大確率トークン選択（argmax）によって、接頭列末尾由来の1個と追加スロット由来の`w`個、合計`w+1`個の候補を作る。

この段階では草稿のすべてが元モデルによって承認されたわけではない。圧縮経路はあくまで予測器であり、元モデルの次トークンと異なる候補も生成する。草稿窓を長くし過ぎると、不正確な候補に対する注意・前向き伝播の計算が増え、検証で早期に棄却される可能性が高まる。`w`を大きくするほど有利とは限らない理由である。

### 3. 草稿を再埋込みして元モデルの中間表現へ合流させる

候補ができたら、接頭列と候補トークンを圧縮埋込み層で再埋込みし、圧縮した下位層`L'_1 ... L'_(i-1)`へ通す。これにより、候補トークンを含む系列の更新された中間隠れ状態`ĥ_(i-1)`を得る。次に元モデルの`h_(i-1)`と合流させるが、**既存接頭列の隠れ状態は元モデルの値を保持し、草稿位置だけを圧縮経路の値へ置き換える**。この合流結果を元の層`L_i`へ渡す。

この処理は、接頭列に対して元モデルがすでに行った計算を壊さず、未来トークンの予測だけを段階的に更新するための設計である。複数のFractal Layerを元モデル内に設ければ、後段の層で前段の草稿を再度改善できる。著者らは、`n`個のFractal Layerと窓幅`w`によって、1回の順伝播で最大`w+n+1`個の草稿候補を扱えると記す。ただし候補数は最終的な受理数ではない。受理されるのは元モデルと一致する連続接頭部分だけである。

草稿の中に終了トークン（End of Sequence; EOS）が現れた場合も、その時点では生成終了としない。次の完全モデル検証で承認された場合だけ終了とし、未検証のEOS候補は破棄する。終了判定を草稿に任せてしまうと元モデルの生成列と食い違うため、この扱いは出力同一性を守る上で必要になる。

### 4. 検証段階では補助経路を迂回する

草稿を提案した後、検証段階では挿入した圧縮ネットワークをすべて迂回し、元モデルの完全な順伝播を使って候補を照合する。草稿が最初に不一致となった位置では、元モデルの予測を採用して残りの草稿を捨て、新たな草稿・検証組へ進む。これにより、圧縮モデルの近似誤差が最終出力へ直接残らない。

論文でいう「損失なし（lossless）」は、検証規則に従った最終トークン列が基準の決定的な自己回帰生成と一致するという意味である。確率的サンプリングの任意設定や、KVキャッシュを導入した際の完全一致を独立に検証した結果ではない。また、補助層の量子化が8ビットだから元モデルまで8ビット量子化されるわけでもない。近似されるのは草稿生成側であり、検証の元モデルは元の精度で走る。

## 評価条件

| 項目 | 一次論文の設定 |
|---|---|
| 元モデル | Llama-3 3B、Llama-3 8B、CodeLlama-13B |
| GPU | NVIDIA RTX 3090 |
| 草稿経路 | 元モデル由来の8ビット線形量子化した補助層 |
| 比較 | 通常の自己回帰復号（Baseline） |
| 3B/8Bのデータ | GSM8K、XSUM、CNN/DailyMailから各300入力を無作為抽出 |
| 13Bのデータ | HumanEval全テスト集合 |
| 指標 | トークン/秒、基準比高速化倍率、推定浮動小数点演算量（FLOPs） |
| 感度 | Fractal Layer数`n`と草稿窓幅`w`、層の挿入位置 |
| 重要な制約 | **KVキャッシュ不使用**の簡略化実験 |

測定は実GPUで行われているが、一般的な本番サービング条件と同一ではない。とくにKVキャッシュなしの基準復号は、各生成ステップで過去トークンに対する計算を繰り返しやすく、キャッシュ付きの標準実装より遅くなり得る。したがって論文のトークン/秒は、同じGPUを使った別の推論基盤の実測値と直接比較してはならない。

## 主要結果

### 生成スループット

| モデル・課題 | 通常復号（tok/s） | FractalLLM（tok/s） | 高速化 | 通常復号のFLOPs | FractalLLMのFLOPs |
|---|---:|---:|---:|---:|---:|
| Llama-3 3B / GSM8K | 12.20 | 14.60 | 1.20倍 | 2.5×10¹⁴ | 2.7×10¹⁴ |
| Llama-3 3B / XSUM | 5.74 | 8.49 | 1.48倍 | 4.6×10¹⁴ | 5.0×10¹⁴ |
| Llama-3 3B / CNN/DailyMail | 3.13 | 5.51 | 1.69倍 | 7.8×10¹⁴ | 8.3×10¹⁴ |
| Llama-3 8B / GSM8K | 4.26 | 7.47 | 1.75倍 | 7.6×10¹⁴ | 9.0×10¹⁴ |
| Llama-3 8B / XSUM | 2.25 | 4.06 | 1.80倍 | 1.1×10¹⁵ | 1.4×10¹⁵ |
| Llama-3 8B / CNN/DailyMail | 1.01 | 2.15 | 2.12倍 | 1.8×10¹⁵ | 2.2×10¹⁵ |
| CodeLlama-13B / HumanEval | 1.79 | 4.43 | 2.47倍 | 4.1×10¹⁵ | 4.0×10¹⁵ |

これらは論文のTable 1・Table 2に示された同一実験設定の数値である。3BのGSM8KではFLOPsが約8%増える一方、速度は20%改善する。計算量の増減だけでは実行速度を説明できないことが分かる。8BのCNN/DailyMailではFLOPsが約22%増えても生成速度が2.12倍になる。反対にCodeLlama-13BのHumanEvalでは、元モデルの完全順伝播回数が減る効果が補助層の計算費用を上回り、推定FLOPs自体がわずかに減少している。

表の`Acc.`は生成品質の正答率ではなく、基準に対する**高速化倍率**を表す。最終出力の同一性は手法の検証規則に基づく主張であり、上表の`1.20×`などを精度改善と解釈するのは誤りである。論文が比較する主指標は処理速度と演算量であり、別の新しい生成品質モデルを訓練した研究ではない。

### 草稿窓幅とFractal Layer数の感度

著者らはLlama-3 3BのGSM8Kから100例を抽出し、Fractal Layer数`n`と草稿窓幅`w`を変えて生成速度を測定した。Figure 3の傾向では、少数のFractal Layerに過大な草稿窓を与えると速度が下がり、層数を増やすと候補の修正精度が改善する。ただし層数を増やし過ぎれば補助経路の計算が増え、1回の草稿・検証組の時間が伸びる。`w`を`n`と同程度かやや小さくする設定が比較的良いと報告される。

たとえば図の良好な組合せでは14トークン/秒台後半に達するが、草稿層が少ないのに窓を長くした領域では10トークン/秒前後まで落ちる。これは「候補を多く提案すれば必ず高速化する」という直感が成り立たない実例である。速度は受理候補数だけでなく、誤候補の検証費用、補助層の計算、元モデルを何回呼び直すかで決まる。

付録の挿入位置解析では、28層のデコーダへ7個のFractal Layerをほぼ均等に配置し、GSM8Kから10例を用いて層ごとの平均正解草稿数を観察する。これにより挿入位置の効果を検討しているが、最適な配置位置をモデル・負荷ごとに自動決定する機構は完成していない。配置を固定しても一般に最良となる保証はない。

### 損失なし検証の意味と未測定項目

最終出力の同一性は、元モデルの完全検証で草稿の誤りを訂正することに由来する。草稿がどれほど粗くても、正しく検証している限り元モデルの決定的生成から逸脱しない。しかし草稿が粗ければ多くの候補が棄却され、標的モデルの呼び出し回数が減らず、速度は悪化する。このため、正確さの保証と高速化の保証は別である。

一次論文は、通常のKVキャッシュ付き生成、長時間の同時要求サービング、CPU/GPUオフロード、VRAMのピーク占有量、別種の量子化方式の比較について、主要表と同程度の独立した測定結果を示していない。圧縮層の追加重みはゼロではないため、「外部草稿モデルが不要」を「メモリ増加なし」と同一視するのも不適切である。

## 既存研究との差

EAGLEなどは専用の草稿予測器を学習し、特徴量から先読み候補を生成する。MEDUSAは追加の先読みヘッドを使う。通常の自己投機的復号は元モデルの浅い層だけを使うが、候補を逐次生成する場合がある。FractalLLMは元モデル由来の圧縮層を**モデル内部の複数位置へ埋め込み、途中特徴を共有しながら草稿を複数生成する**点が異なる。

提案のもう一つの特徴は、草稿経路を検証時に完全に迂回できることである。これにより元モデルの出力同一性を維持しやすい。もっとも、元モデルの層間へ圧縮ネットワークを挿入するため、単に外部の草稿モデルを追加する方式とは実装・メモリ配置が異なる。一般的な推論基盤に組み込むには、層間の隠れ状態、補助埋込み、草稿スロット、検証段階の実行経路を統合する必要がある。

## 限界と実装上の含意

最も大きい制約は、**主要実験がKVキャッシュを使用していない**点である。KVキャッシュ付きの自己回帰生成では、過去トークンの中間状態を再利用するため、基準復号の費用構造が変わる。FractalLLM側でも、元モデルのKVと草稿側の途中状態をどう保存・更新・巻き戻すかを設計しなければならない。論文は接頭部キャッシュの実用的管理を将来課題と明記している。

第二に、Fractal Layer数と配置位置の選択が手作業に依存する。層数が少な過ぎると候補が不正確になり、層数が多過ぎると補助計算が増える。さらに挿入位置が浅いか深いかで、候補の文脈情報と元モデルとの整合性が変わる。モデルが変われば最適構成も変わる可能性がある。

第三に、論文の評価はRTX 3090を用いた特定のLlama/CodeLlama構成に限られる。RTX 4070 Superなど別GPUや、テンソル並列・連続バッチ処理・高同時接続での速度は未測定である。とくに13Bモデルの通常運用で必要な重みメモリと、圧縮した補助層を追加するメモリを別々に見積もる必要がある。論文の2.47倍という最大値だけをローカル環境の期待値に使うのは適切でない。

第四に、決定的な検証出力と確率的サンプリングの分布同一性は区別すべきである。論文の草稿選択にはargmaxが用いられ、元モデルと一致する出力を検証する設計である。温度付きサンプリングや複雑な停止条件、複数要求のキャッシュ共有に対する分布保証は、この実験から一般化できない。

## まとめ

FractalLLMは、元モデル内部に8ビット圧縮した補助層を埋め込み、1回の順伝播中に草稿を複数回更新してから元モデルで一括検証する方式である。独立した草稿モデルの追加学習なしに最大2.47倍の高速化を示した点は興味深いが、測定の前提はKVキャッシュ不使用である。実用的なローカル推論やサービングへ適用する場合、まずKVキャッシュ付き基準との公平な比較と、草稿側の状態管理・メモリ増加・層挿入位置の選定を検証する必要がある。
