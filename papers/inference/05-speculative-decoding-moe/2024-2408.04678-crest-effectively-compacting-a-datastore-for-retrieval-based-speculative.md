# CREST：検索ベース投機的復号のデータストアを頻出n-gram辞書へ圧縮する

## 概要

投機的復号では、軽量な方法で複数の次トークン候補を作り、大きな言語モデルがまとめて検証する。小型の草稿モデルを別途学習する代わりに、RESTは過去のテキストデータから直近のトークン列に完全一致する文脈を検索し、その続きを候補として提示する。追加の草稿モデルは不要だが、RESTは元のテキストと接尾辞配列をデータストアとして保持するため、学習データを増やすほど格納容量も増える。

CREST（Compact Retrieval-Based Speculative Decoding）は、RESTの全文保存方式を改め、**短くて頻出するn-gramをキー、そこから生成した候補トークン木を値とする辞書**を保持する。まれな文脈や長い文脈を無制限に残さず、少数の重要なキーを選んで保存するため、ストレージを小さくできる。さらに、検索に引っ掛かるが品質の低い木を減らすことで、平均受理長が改善する場合がある。原著は、RESTと同等の受理長を10.6〜13.5倍小さな容量で達成し、同じ容量では受理長を16.5〜17.1%改善したと報告する。

ただしこの成果は主に**草稿トークンの受理長とデータストアの容量**に関する。CRESTの理想化した辞書検索は定数時間を狙えるが、実装ではPostgreSQLの木索引を使い、ディスク入出力・データベース照会・候補木の構築・検証費用を含む生成速度を直接保証しない。論文の理論的な探索計算量、実装方式、測定した受理長を分けて理解する必要がある。

## 問題設定：RESTの接尾辞配列はなぜ圧縮しにくいか

RESTは会話データをトークン列へ平坦化し、一定の大きさのチャンクへ分け、各チャンクの接尾辞配列を作る。接尾辞配列は各位置から始まるトークン列を辞書順に並べた位置索引である。生成時には、直近の最大16トークンと一致する文脈を探し、見つからなければ15、14と短くして最短2トークンまで検索する。見つかった文脈の直後に続くトークン列を集め、最大64トークンの候補木へ統合してターゲット言語モデルへ検証させる。

この表現は同じトークンを多数の異なるn-gramの文脈と続きを構成するために再利用する。密に保存できる一方で、途中のトークンを1個削ると、その位置をまたぐ複数の文脈・続きを同時に破壊する。単に低頻度の文字列だけを削ってデータストアを小さくすることが難しい。元データを追加すれば一致する文脈が増える可能性があるが、容量も線形に増えてしまう。

また、RESTはチャンクごとに接尾辞配列を二分探索する。チャンク数をc、各チャンクのトークン数をn_cとすると、原著は検索費用を概ねO(c log n_c)と説明する。チャンクサイズを固定した実装では総データ量に伴ってcが増えるため、検索費用も増える。理想的に単一チャンクへ統合してもO(log n)である。CRESTは元のテキスト全体の検索から、事前に構築したn-gram辞書の検索へ変更する。

## 手法

### 1. 文脈と続きを切り離して辞書化する

CRESTは元データの連続トークン列をそのまま保持する代わりに、各n-gram文脈に対する候補トークン木を前もって作り、`n-gram → token tree`という独立した項目として保存する。入力は過去の会話データとRESTの検索可能なデータストアであり、処理は文脈の列挙・頻度計測・選別・候補木構築である。出力は文脈キーと木の対応表になる。

文脈ごとの木を独立させると、ある項目を削っても別のn-gramの文脈を壊さない。これは元のRESTの密な表現より初期の保存量が大きくなる可能性があるが、**選別して項目を丸ごと削除できる**という利点を得る。保存する項目を少数に絞れば、元テキストと接尾辞配列を保持するより小さなデータストアを構成できる。

辞書のキーは、推論中に生成した直近のトークン列と完全一致させる。値は検証用トークン木なので、照会時に元データ中の一致位置を集めて木を一から組み立てる必要がない。理想的なハッシュ表なら平均O(1)でキー検索できる。原著はこれをRESTの理想O(log n)探索と対比するが、後述の実装では木索引を使っており、この理想的計算量をそのまま実測値と見なすことはできない。

### 2. 頻出・短n-gramを残す

CRESTが保持する文脈を選ぶ基準は、長さが短く、出現頻度が高いことである。RESTの既存結果では、最大16トークンの文脈を試しても、実際の草稿性能の多くは長さ5以下の文脈で達成できるとされる。著者らはShareGPTとThe Stackのトークン列から、長さ1〜5のn-gramの種類数を数え、ShareGPT約9,155万種類、The Stack約1億2,600万種類と報告する（Table 1）。全ての種類に64トークンの木を付けると、32ビットのトークンIDだけでも非常に大きくなる。

出現頻度は長い裾を持つため、頻出のごく一部を残すだけでも多くの照会に対応できる。著者らは同じnだけで上位t個を残す方式と、n=1から最大mまで各長さで上位t個を残す方式を比較した。前者ではn=2が最も良い受理長を得る傾向があるが、後者のように複数長を混ぜた方が全体の受理長が高くなる。頻出3-gramは、まれな2-gramよりも良い候補を返すことがあるため、nの短さだけでは品質を判断できない。

興味深いのは、項目を増やすと受理長が単調に伸びるわけではない点である。REST型の照会は長い文脈から検索を始め、最初に一致したnで探索を止める。まれな長文脈の木が保存されていると、それが一致してしまい、頻出の短文脈から得られたはずの豊かな候補木を使わないことがある。CRESTは低品質な木につながりやすい文脈を削ることで、容量を削減しながら受理長を改善する可能性がある。これは単なる圧縮率の議論ではなく、**照会時の候補選択の偏りを制御する**効果である。

### 3. ディスク上で検索できる辞書の実装

最初の試作ではPython辞書をpickleで直列化したが、これでは照会時に大きな辞書を主記憶へ展開する必要がある。原著はディスク上のまま検索可能な辞書を目指してPostgreSQLを採用し、各トークン木を個別にpickle化してBLOBとして保存する。候補木に含まれる注意マスクには0と1の長い連続が多いため、Pythonのlzmaで圧縮して保存する。

ここで理想化したハッシュ辞書と実際のPostgreSQLの実装を区別する必要がある。著者らは、PostgreSQLの主キー索引が木ベースであるため実際の検索はO(log n)だが、専用のハッシュ型索引ならO(1)を狙えると説明する。つまり論文の「O(1)に改善」は実装済みのデータベースが必ずO(1)で応答したという実験結果ではない。さらに、ディスク上の木の読出し、圧縮の展開、候補木をターゲット言語モデルへ渡す処理には別途時間がかかる。

### 4. 推論時の処理順序

オフラインでShareGPTまたはThe StackからRESTデータストアを構築し、頻出n-gramの候補を列挙する。選んだ各n-gramでRESTを照会し、得られた続きを候補木にまとめてCRESTの辞書へ保存する。推論時にはターゲット言語モデルの直近トークン列を使って辞書の文脈キーを探し、保存済みの木を読み出して検証させる。ターゲット言語モデルが受理したトークンだけを出力へ追加し、受理できない部分は通常のターゲットモデルの検証規則に従う。

RESTと同じく別の草稿言語モデルを学習する必要はない。ただし静的な過去データとターゲットモデルの出力分布が離れると、辞書の候補が当たりにくくなる。特に頻出短文脈を優先する設計は、専門分野の稀な文脈で必要な候補を落とす可能性がある。採用前には、実際の生成ドメインに近いデータストアで受理長とストレージを測定する必要がある。

## 評価条件

| 項目 | 原著の条件 | 解釈 |
|---|---|---|
| 計算資源 | NVIDIA L4 GPU 1基、8 vCPU | 特定のGPU/CPU構成での検証 |
| 会話用データ | ShareGPT 120,675サンプル、REST格納1.1GB | Vicuna-7B＋MT Benchで評価 |
| コード用データ | The Stack 90,016サンプル、REST格納924MB | CodeLlama-7B＋HumanEvalで評価 |
| MT Bench | 80件の複数ターン質問、最大生成1024トークン | 対話タスクの受理長 |
| HumanEval | 164件のコード問題、最大生成512トークン | コード生成の受理長 |
| REST側の設定 | 候補木最大64トークン、一致文脈最大5000件、各文脈の続き10トークン | 比較のためRESTの既定値を維持 |
| CRESTのn範囲 | ShareGPTはn≤4、The Stackはn≤5 | 頻出短文脈を保存 |
| 主な指標 | データストアのディスク容量、平均受理トークン長 | 生成速度・端末間転送量の直接比較ではない |

RESTの比較対象には元データの1、2、4、8、16、32、64、100%を無作為に採用したデータストアを用いる。CRESTでは同程度の保存量になるよう上位n-gram数を調整する。原著は、RESTのデータストアファイルを圧縮した場合との比較ではなく、RESTを検索可能な状態で保存する容量と、木を圧縮したまま検索できるCRESTの容量を比較したと明記する。容量の測定条件は公平性の判断に影響する。

## 主要結果：容量削減と受理長の改善

| 条件 | REST | CREST | 解釈 |
|---|---:|---:|---|
| ShareGPT→Vicuna-7B→MT Bench、最大データストア | 平均受理長1.77 | 1.90 | 最大規模の比較でもCRESTが上回る |
| The Stack→CodeLlama-7B→HumanEval、最大データストア | 平均受理長2.17 | 2.37 | コード生成でもCRESTが上回る |
| 同等の平均受理長 | 基準容量 | 10.6〜13.5分の1の容量 | 原著要旨の容量削減レンジ |
| 同程度の保存容量 | 基準受理長 | 16.5〜17.1%長い受理長 | 原著要旨の相対改善レンジ |

MT Benchの1.77→1.90は約7.3%の増加、HumanEvalの2.17→2.37は約9.2%の増加である。これは原著要旨の「同容量で16.5〜17.1%」と数値が異なるが、**比較するデータストア容量や最大値の取り方が異なる**ため矛盾と断定できない。上表の最大規模の絶対値を、要旨の同容量条件の改善率と混ぜないことが重要である。受理長の増加がそのまま生成速度の増加率になるわけでもない。データベース照会時間と大きなモデルの検証時間の比によって実際の速度向上は変わる。

単一nだけの上位t件選択（Figure 8）では、n=2の辞書が両データセットで比較的良い受理長を示す。一方、n≤mの複数長を混ぜた選択（Figure 9）では、最大m=2が最良とは限らず、特にコードデータでは長いn-gramも有効である。コードには反復的な構造が多く、長めの一致文脈が続きを予測しやすい可能性があると著者らは考察する。したがってデータストアの構築では、会話とコードを同じn範囲で最適化できると仮定しない。

## 感度分析と負の結果

Figure 9のThe Stackでは、約180万n-gramを保存したところで平均受理長が2.51に達し、その後さらに項目を増やすと低下する。これは最初の20会話だけを使った部分評価であり、全HumanEvalにおける2.37とは比較範囲が違う。項目を増やすほど良いという単純な規則は成り立たず、まれな文脈を追加すると、より良い短文脈の候補を検索前に打ち切ってしまうことがある。

Table 2は、候補木の最大64トークンに対して実際の平均木サイズが小さいことを示す。ShareGPTのn=1は30.36トークン、n=5は16.98、The Stackのn=1は31.92、n=5は23.12である。まれなn-gramほど十分な続きを集めにくく、検証器が処理できる64トークンを埋められない。データを追加する場合、RESTでは元テキストが増えて容量も増えるが、CRESTでは保存するn-gram数を固定したまま既存キーの木を充実させる余地がある。ただし木を増やせばその分の保存量も増えるので、容量が完全に一定になると保証するものではない。

初期の辞書化では全ての短n-gramと木を保存すると元RESTより非常に大きくなる。ShareGPTとThe Stackの1〜5-gramは約9,155万、約1億2,600万種類あり、仮に全キーへ64トークン木を保存すると数十GB規模になり得る。**辞書へ変えただけで圧縮されるのではなく、頻度に基づいて大半を捨てる工程が本質**である。どのn-gramを残すか、データの偏り、保存した木のサイズが結果を左右する。

## 既存方式との差

通常の小型草稿モデルを使う投機的復号では、草稿モデルの学習・常駐メモリ・実行時間が必要になる。RESTはこれを静的なテキスト検索で置き換え、学習なしで任意のターゲット言語モデルへ候補を出す。CRESTはRESTの検証方式を変更するのではなく、検索に使うデータストアの表現を変える。RESTが全文と接尾辞配列から一致位置を探して候補木をその場で作るのに対し、CRESTは頻出文脈ごとの木をあらかじめ保存する。したがって、学習済みの小型モデルを追加せず、検索容量と検索の仕方を改善する方向の研究である。

また、単純なテキスト圧縮と違って、CRESTの選別は検索結果の品質も変える。RESTの接尾辞配列は全データを保持するため、検索が最初に見つけた長文脈の候補木を使うことがある。CRESTはその文脈自体を保存しない選択ができるため、頻出短文脈からの豊かな候補へ誘導できる。これが「小さくして受理長が増える」という結果の仕組みである。

## 限界・実装上の注意

第一に、実装はPostgreSQL上の木索引であり、理想ハッシュ辞書のO(1)検索は実証済みの計測値ではない。ディスク上のBLOBの読出しとlzma展開、Pythonの処理、候補木のターゲット言語モデルへの受渡しには費用がかかる。実運用では、照会のp50/p95遅延、CPU使用量、I/O帯域、データストアのキャッシュヒット率を別途測定する必要がある。

第二に、原著の主指標は受理長であり、生成全体のtokens/s、TTFT、TPOT、品質保持を含むエンドツーエンドのサービス性能を広範囲に示した結果とは区別する。受理長が伸びても、辞書検索の費用が大きければ高速化が相殺され得る。GPUはL4、ターゲットは7B級で、巨大モデルや大規模バッチ、同時多数リクエストへの一般化は未検証である。

第三に、静的な過去会話・コードデータから辞書を作るため、実際のユーザーのドメインとデータストアの分布が違うと頻出文脈が役に立たない。会話とコードで最適なnの範囲が異なることも原著が示す。頻出n-gram優先は低頻度の固有名詞や特殊なコード片の続きを候補として保持しにくくする可能性がある。

第四に、データストアを構築するオフライン費用と更新手順は別の運用課題である。原著はRESTを一度構築し、それを照会してCRESTの各木を作るため、単に元データを捨てればよいわけではない。新しいデータの追加、頻度順位の再計算、木の再構築、既存のPostgreSQL索引更新が必要になる。再構築費用を含めた総所有コストは論文の受理長指標だけでは判断できない。
