# Scaling Laws for Speculative Decoding

## 概要
本論文は、投機的復号 (speculative decoding) の性能を「ドラフトモデルの事前学習量」「ドラフトモデル容量」「オンライン復号のbatch size」の三軸で系統的にスケールし、平均受理トークン数または処理能力が対数線形に伸びる経験則を整理する。EAGLE系のようなドラフトモデルでは、候補生成器を強くすれば受理率は上がるが、ドラフト自身のforward費も増えるため、受理率最大点と壁時計速度最大点は一致しない。

著者らはこの三軸をScyllaへ具体化する。ドラフトを別途事前学習し、decoder深度を増やし、復号時にはbatch sizeに応じて検証する候補経路数top-kを動的に減らす。Vicuna、Llama 2/3、Qwen2.5で受理率を評価し、Qwen2.5-72Bの社内推論エンジンではEAGLE2に対し最大約2倍級の実スループットを示す。

## 問題設定
投機的復号では小さいドラフトが複数token候補を作り、大きい対象モデル (target model) が候補列を一括検証する。ドラフトが弱ければ拒否が多く対象モデルforward回数を十分減らせない。逆にドラフトを大きくしすぎたり、1回に検証する候補経路を増やしすぎると、ドラフト計算と対象モデルの検証FLOPsが増えて速度が落ちる。

さらにbatchが増えると対象モデルの重み読出しを複数要求で共有できる一方、候補経路数top-kとの積で算術強度 (arithmetic intensity) が上がり、メモリ帯域律速から計算律速へ移る。したがって小batchで最適なtop-kを大batchへ固定する設計は、受理率が高くてもスループットを悪化させ得る。

## 手法
### 事前学習token量のスケーリング
EAGLE2と同じSFT条件を維持しつつ、ドラフトをCommon Crawl 80%、C4 15%、GitHub 5%の混合データで事前学習する。token予算を1B、2B、5B、10B、20B、50B、100Bと変え、平均受理トークン数との関係を測る。経験則は Acceptance ≈ alpha log10(T_pretrain) + beta で、論文の総合fitはalpha≈0.08、beta≈5.05である。平均受理は1B付近の5.13から50B付近まで伸びるが、50〜100Bでは増分がほぼ飽和し、fitのR²は0.89である。

重要なのは学習量に明確な逓減がある点である。事前学習を増やしてもオンライン推論FLOPsは増えないが、50B以降はオフライン学習費に対する受理率増分が小さい。Scylla自体はこの観測から10B事前学習を採用する。

### ドラフト容量のスケーリング
ドラフトのhidden幅やhead数は固定し、decoder層だけを1、2、5層へ増やして約138M、275M、413Mへ拡大する。出力側に二乗平均平方根正規化 (Root Mean Square Normalization; RMSNorm) も加える。経験則は Acceptance ≈ alpha log10(D) + beta で、Dはdecoder数、総合fitはalpha≈0.74、beta≈4.61である。六つのベンチマークで5〜10 decoderまで概ね改善が続く。

ただしdecoderを増やすと毎回の候補生成FLOPsも増えるため、「最も高い受理率」が最速とは限らない。容量スケーリングは対象モデルforward削減とドラフトforward増加の交換条件である。

### batch sizeと屋根線モデル
Qwen2.5-72Bを例に、ドラフト・検証のFLOPsとread/write trafficから算術強度 I(b, top-k) を導出する。GPUの臨界算術強度 I_crit=P_peak/B_mem より小さい間はメモリ律速だが、batchとtop-kを増やしてI_critを超えると計算律速になり、それ以上の候補並列化がスループットを下げる。

そこで各batchで I(b, top-k_opt)=I_crit となるtop-kを選ぶ。測定ではbatch≥8から固定top-kの非最適性が顕在化し、最大スループットはbatchに対して概ね Throughput ≈ 286.79 log2(b) + 7.54 で伸びる。top-k_optはbatchとともに減らす逆平方根型のfitとなり、受理率の多少には比較的鈍感である。つまりScyllaは高品質ドラフトを作るだけでなく、オンラインbatchに合わせて検証幅を変える。

## 評価条件
| 観点 | 条件 |
|---|---|
| 対象モデル | Vicuna-7B/13B、Llama2-Chat-7B/13B/70B、Qwen2.5-7B/72B、Llama3-Instruct-8B/70B |
| タスク | MT-Bench、HumanEval、GSM8K、Alpaca、CNN/DailyMail、Natural Questions |
| GPU | NVIDIA H800。7B/8B/13Bはsingle GPU、70B/72Bは4 GPU |
| SFT | ShareGPT-68Kを2 epoch。EAGLE3比較用にUltraChat-200K×8相当も別評価 |
| 比較 | Medusa、EAGLE、EAGLE2、EAGLE3 |
| 品質保証 | target modelを凍結し、受理基準を変えないlossless acceleration |
| 指標 | 1 draft-verification cycle当たり平均accepted tokens、tokens/s |
| batch速度評価 | Qwen2.5-72B、4×H800、batch 1〜64 |

## 主要結果
Scyllaは温度0でEAGLE2に対し受理性能を28〜53%、温度1でも24〜42%改善する。例えばVicuna-13Bの平均accepted tokensはEAGLE2 4.65に対しScylla 6.31、Llama2-Chat-13Bは4.68→6.13、Qwen2.5-7Bは4.05→5.28である。論文冒頭の表現では温度0でEAGLE2より絶対1.5〜2.2 token、EAGLE3より約0.3 token高い。

実スループットはQwen2.5-72Bの4×H800で、非投機baseline / EAGLE2 / Scylla+最適top-kがbatch 1で60/200/250 token/s、batch 16で750/830/1650、batch 32で1239/910/2050、batch 64で1763/980/2150である。EAGLE2は小batchでは速いが、固定的に大きな候補検証が計算律速へ入りbatch 32以降で逆に低下する。Scyllaはtop-kをbatch適応させるため、大batchでも約2倍のEAGLE2スループットを維持する。

一方、非投機baselineに対する倍率はbatchとともに縮む。batch 64ではScyllaは2150/1763≈1.21倍であり、対象モデル単体もbatchingによりGPU利用率が上がるため、投機的復号の余地自体が小さくなる。通信オーバーヘッドとカーネル利用率により屋根線モデルの理論値と実測にも差があり、解析式をそのまま実時間値として扱えない。

## 既存研究との差
EAGLE系は主にドラフト表現・訓練法を改善するのに対し、本論文はドラフトの学習量・容量・オンライン検証幅を同じ資源最適化問題として扱う。特にbatch sizeを「単なる運用パラメータ」でなく、検証top-kとGPU屋根線の関係から最適化すべき第三のスケーリング軸とした点がシステム上の特徴である。

## 限界
三つの法則はいずれも評価したTransformer型ドラフトに対する経験則で、係数を他アーキテクチャへそのまま移せる理論保証はない。論文自身も混合専門家 (Mixture-of-Experts; MoE) への拡張を未検証としている。また事前学習量を増やすと推論費は増えないがオフライン費は増え、容量拡大はオンラインのドラフト計算を直接増やす。強化学習による人間フィードバック (Reinforcement Learning from Human Feedback; RLHF) をドラフトへ適用する効果も未評価である。大batchではtarget model自体の利用率が高まり、投機的復号の相対利得が1倍へ近づくため、常に2倍高速という結果ではない。
