# Jina-OCR-v1：共有草稿ブロックで文書復号を高速化するFastMTP

## 概要

文書画像からMarkdownを生成する画像言語モデルは、文字認識だけでなく数式、表、読順、段組などを一回の生成で処理できる。しかし一ページの出力が長くなりやすく、画像側のトークン圧縮だけでは自己回帰復号の時間が残る。Jina-OCR-v1は、DeepSeek-OCRの圧縮画像エンコーダと専門家混合（Mixture of Experts; MoE）復号器を土台とし、複数トークン予測（multi-token prediction; MTP）の草稿器を追加してこの部分を短縮する。

中核はFastMTPである。同じ草稿ブロックを再帰的に最大3回使って未来トークンを予測し、元の復号器でまとめて検証する。最終的に受理するのは元の復号器の貪欲出力と一致する接頭辞だけなので、**同じ対象モデルの通常の貪欲復号と出力トークン列が一致する**。この意味で投機的復号は出力無損失である。ただし、モデルの後学習で得た品質が別のモデルと一致することを意味しない。

原著はNVIDIA L4で、vLLM 0.20.1のバッチ1・通常実行（eager）において、草稿3段で通常の自己回帰復号に対して1.95倍のトークン生成速度を報告する。一方、CUDAグラフ（CUDA Graph）を使った高速な基準実装では草稿1段が最適となり、改善は最大1.17倍に縮む。A100での文書ページ処理量は2.57ページ/秒で、評価した候補の中では最高だったが、この数字にはモデル構造、出力の短さ、複数要求バッチ処理が含まれるため、FastMTP単独の高速化倍率ではない（原著§6.3、§6.4）。

## 問題設定

### 文書解析で長い復号列が生じる

OCRの生成出力には、本文、表のセル、数式のLaTeX表記、見出しや構造記号などが含まれる。ページの視覚情報を圧縮しても、復号器は出力トークンを一つずつ確定しなければならない。巨大な画像言語モデルでは画像入力トークンも多く、少ないGPUでの実行が難しい。DeepSeek-OCRは既に画像側を強く圧縮し、MoEによって一トークンで活性化する重みを小さくしていたが、逐次復号の回数は残っていた。

文書認識の出力は自然言語の自由生成より局所的に規則性が強い。文字列や表構造の続きを小さな草稿器で予測しやすく、草稿が対象モデルの出力と一致するなら複数トークンを一度に確定できる。論文はこの特性を利用する。対象モデルの確率分布を近似して最終出力を変えるのではなく、**貪欲復号の一致検査によって元の出力を保持する**方式を選ぶ。

### 草稿器の段数と追加計算の交換関係

草稿を長くすると、一回の対象モデル検証で多くのトークンを確定できる可能性が増える。一方、草稿器の追加実行も費用を持ち、後方の草稿ほど不一致率が高い。対象モデルの一回の処理費用がCUDA Graphで小さくなると、草稿器の相対費用が大きくなり、長い草稿が必ずしも最速でなくなる。Jina-OCR-v1は、この違いを同じモデルの二つの実行モードで測定している点が推論基盤研究として重要である。

## 手法

### 1. 圧縮視覚入力とMoE復号器

視覚側はDeepSeek-OCRのDeepEncoderを継承する。SAM由来の局所特徴抽出器、16倍の畳み込み圧縮、CLIP由来の全体特徴抽出器を組み合わせる。1,024×1,024画像では4,096個のパッチ情報を256個の視覚トークンへ圧縮する。動的解像度モード（Gundam）では局所タイルを最大9個追加し、一タイル当たり100トークンなので、合計は最大1,156視覚トークンとなる（原著表1）。

言語側は総パラメータ約3B、トークンごとの活性パラメータ約570MのDeepSeek系MoE復号器である。12層、隠れ次元1,280、64個のルーティング対象専門家と2個の共有専門家、上位6専門家の選択を用いる。画像エンコーダも含めた全体モデルは約3.4Bで、活性化するパラメータは1B未満と説明される。視覚トークンを圧縮し、復号時の計算量を小さくすることが低価格GPUでの実行を支える。

### 2. 一つの共有草稿ブロックを三段へ再帰適用

FastMTPは、未来の各位置に別の巨大な草稿モデルを置くのではなく、一つの密な草稿ブロック $B_\theta$ を繰り返し使う。現在位置の対象モデルの隠れ状態、次トークンの埋め込み、直前の草稿状態を射影・正規化して草稿ブロックへ渡し、次の隠れ状態とトークン予測を得る。これを最大 $K=3$ 回行う。段数を増やしても草稿ブロックのパラメータ数が段数に比例して増えない点が特徴である。

学習時には系列位置 $p$ と再帰深度 $k$ の二次元格子上で草稿を計算し、推論時に進む斜め方向の経路へ対応させる。各深度の予測を対象モデルの次位置の隠れ状態・確率分布へ合わせる。埋め込み、出力正規化、言語モデル出力層は対象モデルと共有し、草稿側で主に学習するのは共有ブロック、入力射影、正規化器である（原著§3.1、図3）。

### 3. 貪欲検証と一致接頭辞の受理

草稿器が未来トークン $\hat{x}_1,\ldots,\hat{x}_K$ を提案したら、対象復号器が対応位置の貪欲トークン $v_r=\arg\max_x q_r(x)$ を計算する。先頭から一致する最大の長さ $m$ を求め、草稿の先頭 $m$ 個を確定する。最初に不一致が生じた位置では対象モデルの貪欲トークンを確定し、その後の草稿を破棄する。全草稿が一致した場合には、対象モデルがさらに予測したボーナストークンを確定できる。

この処理では乱数に基づく受理確率や残差分布からの再標本化を行わない。各ステップで確定するトークンが対象モデルの貪欲選択と一致するため、同じ対象モデル・同じ入力・同じ決定的な実行条件なら、草稿の受理率にかかわらず通常の貪欲復号と同じ列になる。出力無損失という主張は、この**同一対象モデルとの比較**に限られる。

### 4. 草稿器の学習目標

FastMTPの学習では、各深度の予測に対してトークン交差エントロピー、対象モデルの出力分布とのKLダイバージェンス、隠れ状態との平均二乗誤差を組み合わせる。原著式(5)では、それぞれの重みが0.85、0.45、0.45であり、深い草稿への重みを $\beta=0.6$ の減衰で調整する。対象復号器は固定し、草稿ブロックと関連する射影・正規化器だけを更新する。

草稿の学習が良ければ、一回の検証で確定できるトークン数が増える。ただし、深い草稿の一致率が下がると、増加する確定トークンより追加計算費用が大きくなる。論文は学習時の損失だけでなく、実行時の受理率と処理費用を分けて測定する。

### 5. 後学習と文書構造の品質

FastMTPだけでOCR品質を改善するのではない。元の復号器に対し、指示追従の教師あり微調整、古い印刷物や劣化文書への頑健性微調整、数式・表・構造に対する検証可能報酬を用いたGRPOを組み合わせる。数式と表が少ない自然文書だけではそれらの報酬が発火しないため、数式や複雑な表を多数含む合成ページ群（JinaOCRSynth）も用意する。

報酬は参照解と照合できる構造的なテストであり、単なる正誤二値ではなく部分点を与える。繰り返し出力や書式違反も評価する。これによって生成されるMarkdownの品質や長さを制御するが、**この後学習による改善は投機的復号の出力無損失性とは別の効果**である。モデル間の品質差をFastMTPの受理処理に帰属させるべきではない。

## 評価

### 評価条件の分離

| 項目 | 条件 |
|---|---|
| 投機的復号単体 | NVIDIA L4、vLLM 0.20.1、バッチ1、olmOCR-Bench。通常実行とCUDA Graphを別々に評価 |
| 文書サービング | NVIDIA A100 SXM4 40GB、同時32要求、olmOCR-Bench 1,403ページ |
| 品質 | OmniDocBench v1.6、olmOCR-Bench。各データセットの公式指標 |
| 比較方式 | 通常の貪欲自己回帰復号（k=0）、FastMTP k=1/2/3。文書品質ではDeepSeek-OCR等の既存OCRモデル |
| モデル規模 | 画像エンコーダ約380M、MoE復号器総3B・活性約570M、全体総約3.4B |
| 評価対象 | 数式、表、段組、古い印刷物、見出し・脚注、読み順、出力形式の構造的正確さ |

L4上のバッチ1投機的復号実験とA100上の同時32要求ページ処理実験は**別GPU・別並列度**である。後者の2.57ページ/秒を前者の1.95倍から直接導出することはできない。

### FastMTPの速度と草稿段数

原著表8は通常実行とCUDA Graph実行の二つの基準を分けている。通常実行では草稿なしが42.7トークン/秒、k=1が64.0、k=2が77.9、k=3が約1.95倍となる。段数を増やすほど受理可能なトークンは増えるが、後方の条件付き受理率は一段目約0.83から三段目約0.65へ下がる。すべての段が同じ確率で通るわけではない。

CUDA Graphを有効にすると草稿なしでも158.3トークン/秒となり、通常実行の42.7トークン/秒に対して約3.71倍高速化する。この速い基準に対するFastMTPの最良点はk=1で約1.17倍である。k=3では受理トークン数の増加より草稿・検証の追加費用が重くなり、k=1を上回らない。論文の「L4で約2倍」は通常実行基準の値であり、**CUDA Graphを有効にした最適化済み基準でも2倍になるという意味ではない**。

原著は一投機ステップで確定できる平均トークン数を $\tau$、通常自己回帰一ステップを1とした相対費用を $c$ とし、速度比を $S=\tau/c$ として分解する。k=3の平均確定トークン数は通常実行で2.73、CUDA Graph実行で2.74とほぼ同じである。それでも速度比が異なるのは、対象モデルの一ステップ費用と草稿器の追加費用の相対関係が変わるからである。受理率だけで投機的復号の速度を予測してはいけない。

### ページ処理量と出力長

A100・同時32要求のolmOCR-Benchでは、Jina-OCR-v1のページ処理量は2.57ページ/秒、DeepSeek-OCRは2.10、DeepSeek-OCR-2は1.50、LightOnOCR-2は1.33である（図5、表7）。Jinaの出力は平均1,085トークン/ページであり、長い出力を生成する他方式より一ページを短く処理できる。例えばSurya OCR 2は出力トークン処理量が3,760トークン/秒と高い一方、平均3,568トークン/ページを出すため、ページ処理量は1.05ページ/秒にとどまる。

**ページ/秒 = 出力トークン/秒 ÷ 一ページ当たり出力トークン数**という関係から、トークン/秒が高いモデルほどページ処理量も高いとは限らない。Jinaの高いページ処理量には、FastMTPだけでなく、短く構造化された出力、圧縮された画像入力、MoEの活性パラメータの少なさが寄与する。図5の順位を「FastMTPだけで既存モデルをすべて上回った」と解釈するのは誤りである。

### 文書解析品質

OmniDocBench v1.6では総合91.14、olmOCR-Benchでは総合83.4を報告する。前者ではPaddleOCR-VL-1.6が96.34、HunyuanOCR-1.5が94.74と上回り、Jina-OCR-v1は専門OCRモデルの中で3位である。DeepSeek-OCR-2の90.25は上回る。後者でもchandra-ocr-2の85.8、dots.mocrの83.9より低く、全てのベンチマークで首位ではない。

| 品質指標 | Jina-OCR-v1 | 比較・読み方 |
|---|---:|---|
| OmniDocBench v1.6 総合 | 91.14 | PaddleOCR-VL-1.6は96.34、HunyuanOCR-1.5は94.74 |
| OmniDocBench 数式CDM | 93.28 | DeepSeek-OCR-2は91.84 |
| OmniDocBench 表TEDS | 84.68 | DeepSeek-OCR-2は83.89 |
| olmOCR-Bench 総合 | 83.4 | chandra-ocr-2は85.8、dots.mocrは83.9 |
| olmOCR-Bench 表 | 88.8 | 構造を含む文書での評価の一側面 |
| olmOCR-Bench 複数列 | 42.6 | 他の項目より低く、段組の難しさが残る |

評価セットによって集計方法が異なるため、91.14と83.4を直接差し引いて性能低下と判断できない。olmOCR-Benchのヘッダ・フッタ項目は、目に見える全内容を転記するモデルに不利になるなど評価設計の違いがある。論文も他方式の公開スコアを用いるため、全方式を同じ条件で再学習・再評価した比較ではない。

### 高速化と品質の切り分け

投機的復号の無損失性は、同じJina-OCR-v1対象復号器でk=0とk>0の貪欲出力が一致するという意味である。DeepSeek-OCRやPaddleOCRなど別のモデルとの正答率比較は、事前学習、後学習、データ、出力形式の差が混ざる。FastMTPを取り外しただけの完全な学習・サービング条件統一実験と、各公開モデルのランキングは区別する必要がある。

特にGRPOによる報酬改善は、数式・表の構造を検証可能にした合成ページを使う。これは推論エンジンの投機的検証処理とは別の学習段階の工夫であり、投機的復号が数式の正答率を直接改善したという説明は不正確である。

## 既存研究との差

Medusaは複数の独立草稿ヘッドを、Hydraは段階的な草稿依存を利用する。FastMTPは一つの草稿ブロックを深さ方向へ再利用し、段数が増えても草稿パラメータ数が比例増加しない。EAGLE系の特徴空間草稿を利用するが、文書OCRの局所規則性を生かし、貪欲検証によって元の出力を保つ点が実運用に適する。

DeepSeek-OCRは既に画像圧縮とMoEで効率を上げていた。Jina-OCR-v1はその上で逐次復号のボトルネックに取り組み、文書構造の学習を改良した。画像入力トークン削減と生成トークン数削減と投機的復号は異なる段階の最適化であり、速度評価ではどの段階を測っているかを分ける必要がある。

## 限界・負の結果・実装上の注意

第一に、FastMTPの速度改善は実行モードに強く依存する。CUDA Graphなしではk=3が最良で1.95倍だが、CUDA Graphありではk=1が最良で1.17倍に縮む。最適化済みサービング環境に通常実行基準の約2倍をそのまま外挿してはいけない。長い草稿は後方の受理率が下がり、検証費用が利益を上回ることがある。

第二に、出力無損失性は同じ対象モデルの貪欲復号との比較に限られる。温度付き標本化や異なるモデルへの一般化、GPUカーネルの非決定性を含む任意の実行条件での完全な出力一致を保証するものではない。学習後のJinaモデル自体はDeepSeek-OCRとは異なる出力を持つ。

第三に、A100での2.57ページ/秒は同時32要求、olmOCR-Bench 1,403ページの測定である。L4でのバッチ1投機的復号試験とはGPUも並列度も異なる。平均出力長が短いことがページ処理量に大きく寄与するため、トークン/秒だけを比較してもサービング能力を評価できない。

第四に、文書品質は首位ではない。OmniDocBenchではPaddleOCR-VLやHunyuanOCRが上回り、olmOCR-Benchではchandra-ocr-2やdots.mocrが上回る。特に段組、古い印刷物、複雑な表などの個別項目で弱い場合がある。速度と品質のパレート比較は、用途に必要な項目ごとに行う必要がある。

第五に、FastMTPの草稿器は対象モデルに合わせて追加学習する必要があり、任意の既存モデルへ無調整で挿せる汎用推論プラグインではない。画像エンコーダ・MoE復号器・草稿ブロックの実行基盤が対応することも必要である。モデルは公開されているが、原著本文から公式コードリポジトリURLを独立に特定できず、環境ごとの再現手順は別途確認を要する。

第六に、RTX 4070 Super 12GBでの推論速度は論文未評価である。モデル総3.4Bの量子化によって重み容量が収まっても、画像トークン、KVキャッシュ、草稿器、vLLMのバッファが追加で必要になる。L4の速度やA100のページ処理量をそのまま見込む根拠はない。
