# REST: Retrieval-Based Speculative Decoding

> RESTは、投機的復号（投機的 デコード）で必要になる「次に来そうなトークン列」を小型ニューラル ドラフト モデルに作らせる代わりに、**大量の既存文章から似た続き方を検索して候補として使う**方式である。候補は対象 LLM自身が検証するため、検索が外れても生成品質を犠牲にしない。

## 概要

通常の自己回帰復号（自己回帰 デコード）では、対象 LLMを1回順伝播して1 トークンを確定し、そのトークンを入力へ追加して次の順伝播へ進む。

大規模LLMでは1 トークンあたりの演算量だけでなく、毎ステップで巨大な重みをGPU メモリから読むこと自体が高価である。バッチ サイズ 1では特にメモリ-帯域-上限になりやすく、GPUの行列演算能力を十分使えない。

一般的な投機的復号は、対象より小さいドラフト モデルに数トークンを先に提案させ、その候補を対象 モデルへまとめて通して検証する。ドラフトがよく当たれば1回の対象 処理回で複数トークンを確定できる。

しかしこの方式には、

- 対象 モデルごとに相性のよいドラフト モデルを用意する必要がある
- ドラフト モデルの重み用VRAMが追加で必要
- ドラフト モデル自身の順伝播 コストがある
- モデル 構造やトークン化器が変わるとドラフトを作り直す必要がある

という負担がある。

RESTはここで「次トークンはニューラル モデルで予測しなくても、**過去の文章に同じような文脈があれば、その続きが強い候補になる**」と考える。

コードには定型的なAPI呼出しや構文、チャットには頻出表現が多い。現在文脈の末尾と同じトークン列がコーパス内に見つかれば、その直後のトークン列をドラフトとして使える。

RESTはこの検索を非常に軽く実行し、複数の検索済み 続きを1本ずつ検証するのではなくTrie形式の木構造へまとめ、対象 LLMの1回の木構造 検証で処理する。

## 問題設定

### draft modelはtarget modelより軽いが、無料ではない

投機的 デコードではドラフト モデルが対象より十分小さいことが前提になる。しかし、小型モデルでも重み 保存領域とGPU 計算を消費する。

さらに独自 モデルや特殊微調整 モデルでは、品質の高い互換性のある ドラフト モデルが必ず存在するわけではない。

RESTはドラフト モデルを**パラメータ-無償な検索 エンジン**へ置き換えることで、この依存をなくす。

### retrievalは『意味が似ている文』を探す必要はない

RESTの主方式は埋め込みを使った意味 検索ではない。

目的は「今の文脈と意味が近い文書を探す」ことではなく、**次トークン候補としてそのまま使える文字列を極めて低コストで見つけること**である。

そのため現在文脈末尾のトークン列とデータ格納域中のトークン列の**完全一致 一致**を利用する。

コードでは同じ識別子や構文 パターン、チャットでは頻出句が繰り返されるため、完全一致 接尾辞だけでも有用な候補が得られる。

### retrieval自体が遅ければtarget passを減らす意味がない

対象 LLMを1回省くために数十msの密-ベクトル 探索を行うと、利点を失う可能性がある。

そこでRESTは接尾辞 配列などCPU上で軽量に検索できるデータ 構造を使い、論文評価では検索 オーバーヘッドを全デコード時間の6%未満に抑えている。

## 手法

1回のREST デコード 周期は次のように進む。

1. 現在まで確定したトークン列の**末尾**を照会にする。
2. データ格納域から、その末尾トークン列と一致する過去文脈を探す。
3. 一致箇所の直後に実際に続いていたトークン列を複数取り出す。
4. それらを共通接頭辞でまとめたTrieを作る。
5. 頻度の高いノードを中心に候補木構造を最大約64 ノードへ絞る。
6. 木構造を対象 LLMへ1回だけ順伝播し、各ノードの次トークン分布を並列計算する。
7. 対象 LLMの本来の生成規則と一致した分岐だけを根から順に受理する。
8. 不一致した地点で対象 LLM自身のトークンを採用し、次周期へ進む。

検索候補が完全に外れても、最低1 トークンは対象 モデル自身から得られる。よく当たったときだけ1回の対象 処理回で複数トークンを前へ進める。

## 手法

### 1. datastoreを『context → continuation』として作る

RESTでは、外部文章 コーパスをトークン化し、各位置について「この文脈の後にはどのトークン列が続いていたか」を検索できる形にする。

HumanEvalのコード生成ではThe Stack由来の約270万Python 標本化を使い、大きい データ格納域は約27GBである。チャット生成ではUltraChatを使い、大きい データ格納域は約12GBである。

ここでデータ格納域は対象 モデルの重みを学習するための学習 データではない。推論時に「過去に同じ文字列があったか」を引くための検索 出典である。

そのため対象 LLMを再学習する必要はない。

### 2. 現在contextの『最長suffix』から一致箇所を探す

生成済み文脈全体がコーパス内に完全一致する可能性は低い。一方、末尾数トークンだけなら同じパターンが存在する可能性が高い。

RESTは最初に最大16 トークン程度の接尾辞から検索し、一致が見つからなければ接尾辞を徐々に短くする。

概念的には、

`最後の16 tokenで検索 → 無ければ15 token → 14 token → …`

と進み、最も長く一致する接尾辞を使う。

接尾辞が長いほど候補の文脈特異性は高い。一方、短くするとヒット数は増えるが無関係な続きも増える。

### 3. suffix arrayでexact matchを軽量化する

コーパス全体を毎ステップ線形走査することはできない。

RESTは接尾辞配列（接尾辞 配列）のような索引を使って、現在接尾辞と同じトークン 系列が現れる位置を高速に検索する。

接尾辞配列は、コーパス内の各位置から始まるトークン 接尾辞を辞書順に並べた索引である。同じ接頭辞を持つ接尾辞が近くへ集まるため、binary 探索で一致範囲を求められる。

ニューラル 検索器をGPUで順伝播する必要がなく、CPU 検索だけで済むのがRESTの軽量性につながる。

### 4. 一致箇所の『その後』をdraft候補として取得する

一致したコーパス位置ごとに、その直後のトークン列を最大10 トークン程度取得する。

たとえば現在文脈末尾が

`for i in range (`

で、コーパス中に同じ接尾辞が100回あったなら、それら100箇所の後ろに実際に続いていたトークン列がドラフト候補になる。

同じ続きが何度も出現していれば、その候補は頻度が高い。

RESTはこの**コーパス 頻度を候補の信頼度代理**として使う。

### 5. 候補列をTrieへまとめる

100個の続きを別々に対象 LLMへ通すと重複計算が多い。

たとえば、

- `self . model (`
- `self . tokenizer (`
- `self . config .`

の3候補は最初の `self .` を共有している。

RESTはこれらをTrie、つまり**共通接頭辞を1つのノードとして共有する木構造**へまとめる。

各ノードには、その接頭辞が検索済み 続き中に何回現れたかという頻度を持たせる。

この頻度が高いノードほど対象 出力になる可能性が高いとみなし、候補木構造を絞るときに優先する。

### 6. treeを無制限に大きくせず、上位nodeだけを使う

検索 ヒットが大量にあるとTrieも巨大になる。候補を増やすほど対象 出力を含む確率は上がるが、検証 計算とメモリも増える。

RESTの主設定では頻度の高いノードを中心に**最大64 候補 トークン程度**を採用する。

つまり「検索済み 続きを全部検証」するのではなく、コーパス中で何度も現れた分岐へ検証 予算を優先配分する。

### 7. breadth-first orderへ並べてtree attentionを行う

GPUへ木構造 データ 構造をそのまま渡すことはできないため、Trie ノードを幅優先探索（幅優先 探索: BFS）順などで1本のpseudo-系列へ並べる。

ただし普通の因果 注意 マスクを使うと、分岐 Aのトークンが分岐 Bのトークンを見てしまう。

そこで木構造 注意 マスクを使い、各候補 トークンが、

- 既に確定済みの元の 文脈
- 木構造 根から自分までの祖先 ノード

だけを参照できるようにする。

これにより木構造 ノードを1回のバッチ化 対象 順伝播で処理しながら、各分岐を個別系列として処理した場合と同じ依存関係を保てる。

### 8. target modelがaccept/rejectを決めるのでlossless

検索はあくまでドラフト 出典である。

最終的にトークンを採用するかどうかは対象 LLMの条件付き 確率で決まる。

貪欲復号（貪欲 デコード）なら、各ノードで対象 モデルの最大値選択 トークンと一致する子だけを受理する。

核サンプリング（nucleus サンプリング）のような確率的サンプリングでも、投機的 デコードの受理/棄却 規則を適用して対象 分布を保つ。

最初の不一致以降のドラフト トークンは破棄し、その地点では対象 モデル自身から標本化したトークンを採用する。

したがって検索 コーパスに誤った続きしかなくても、**速くならないだけで対象 モデルの出力品質を検索側へ置き換えない**。

## 評価

### まず見るところ

RESTの効果はワークロードの**文字列反復性**に強く依存する。

コードでは同じ構文・API・定型部分が多いため検索 続きが長く当たりやすく、2倍超の高速化倍率が出る。自由形式 チャットでは一致 長さが短く、高速化倍率は1.6〜1.8倍程度へ下がる。

つまりRESTは「一般的なニューラル ドラフトを不要にする万能方式」ではなく、**既存コーパスから長い続きを引ける領域ほど強いドラフト 仕組み**である。

### 実機条件

| 項目 | 内容 |
|---|---|
| GPU | NVIDIA A6000 ×1 |
| CPU | 96 cores |
| バッチ サイズ | 1 |
| Repetition | 各結果3回平均 |
| Code モデル | CodeLlama-7B / 13B |
| Chat モデル | Vicuna-7B / 13B |
| Code ベンチマーク | HumanEval |
| Chat ベンチマーク | MT-Bench |
| Code データ格納域 | The Stack由来Python コーパス |
| Chat データ格納域 | UltraChat |

### HumanEval / greedy decoding

| Model | 通常デコード | REST | 高速化倍率 |
|---|---:|---:|---:|
| CodeLlama-7B | 27.89 ms/トークン | 11.82 ms/トークン | **2.36×** |
| CodeLlama-13B | 44.32 ms/トークン | 19.53 ms/トークン | **2.27×** |

nucleus サンプリングでも7Bで約2.12×、13Bで約2.17×を報告する。

### MT-Bench

チャットではコードより反復 パターンが弱いため改善は小さい。

- Vicuna-7B 貪欲: 約1.69×
- Vicuna-13B 貪欲: 約1.77×
- Vicuna-7B nucleus: 約1.62×
- Vicuna-13B nucleus: 約1.71×

それでも追加ドラフト モデルを持たずに対象 処理回回数を減らせている。

### 平均で何tokenずつ進めるか

論文のMean Generated Lengthは、1 対象 検証で平均何トークン確定できたかを見る指標である。

HumanEvalではおよそ2.65〜2.69 トークン、MT-Benchでは約1.97〜2.01 トークンだった。

この値は検索 / 木構造 construction / 検証 オーバーヘッドを無視した場合の高速化倍率上限に近い。

たとえば平均2.7 トークン確定できてもエンドツーエンド 高速化倍率が2.36倍に留まるのは、検索 検索や64-ノード 木構造 検証にも追加時間が必要だからである。

### retrieval cost

論文では検索 オーバーヘッドは全体の6%未満に抑えられている。

これはRESTが密 埋め込み 探索ではなく完全一致 接尾辞 検索を選んだ理由と整合する。

公式リポジトリでは軽量版データ格納域も提供しており、ShareGPT系チャット データ格納域は約465MB、The Stack系コード データ格納域は約924MB程度の小さい 構成を構築できる。大規模評価用はそれぞれ約12GB / 27GBである。

## 既存研究との差

### neural draft speculative decodingとの違い

通常の投機的 デコードでは、対象より小さいニューラル モデルが候補 トークンを生成する。

RESTでは**コーパス 検索がドラフト モデルの代わり**になるため、ドラフト 重み、ドラフト 学習、ドラフト 順伝播が不要になる。

一方、コーパスに似た続きがなければ候補品質は低くなる。ニューラル ドラフトは未知文脈にもgeneralizeできるが、RESTはtextual repetitionへ強く依存するというトレードオフがある。

### LLMAとの違い

同時期の検索-assisted デコードであるLLMAは、主に現在リクエストが参照している文書など少数のreferred 文脈から続きを再利用する。

RESTはより大きな外部データ格納域を作り、**多数の過去instanceからcurrent 接尾辞と一致する続きを集めて木構造化する**点が異なる。

### SpecInferとの関係

SpecInferは複数小さい モデルから作った候補を木構造へまとめる。RESTは候補 出典を検索へ置き換える。

どちらも最後は対象 モデルによる木構造 検証を使うため、**候補 生成と検証を分離する**という投機的 提供 構造は共通している。

## 限界

- コーパスに似た続きが少ない自由形式 領域では受理 長さが短くなる。
- 完全一致 接尾辞 一致なので意味に似ていて表面形が違う続きは拾えない。
- 大規模データ格納域は12〜27GB級の追加保存領域 / メモリを必要とする。
- 検索 索引をCPUで維持するためホスト resourceも必要。
- 主評価はバッチ サイズ 1であり、高同時実行数 提供でのスループット gainは別途検証が必要。
- データ格納域は対象 トークン化器でトークン化する必要があり、トークン化器が変われば索引を作り直す必要がある。
- 木構造 サイズを増やしすぎると対象 検証 オーバーヘッドが増える。
- コーパス 分布がdeployment ワークロードと異なると検索 ヒット / 続き 品質が低下する。

## 一般的な実装上の含意

RESTが示す重要な点は、投機的 デコードのドラフト 出典が必ずしもニューラル ネットワークである必要はないことである。

特に、

- コード 生成
- SQL
- 構成 file
- template文書
- 領域-特定定型文

のように反復パターンが多いワークロードでは、過去出力や領域 コーパスを**ドラフト トークン キャッシュ**として再利用できる。

この場合、ドラフト モデルを追加するよりも、CPU上のcompactな完全一致-一致 索引の方が安い可能性がある。

さらに、候補 出典を検索 / 小さい モデル / n-gram キャッシュなど複数用意し、それらを同じ木構造 検証 backendへ統合する設計も考えられる。SpecInferや後続木構造-基づく デコードと組み合わせると、ドラフト生成器と対象 検証を独立構成要素として扱うシステム 設計につながる。
