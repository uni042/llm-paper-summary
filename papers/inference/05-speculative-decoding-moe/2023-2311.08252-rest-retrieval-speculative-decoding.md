# REST: Retrieval-Based Speculative Decoding

> RESTは、投機的復号（speculative decoding）で必要になる「次に来そうなtoken列」を小型neural draft modelに作らせる代わりに、**大量の既存textから似た続き方を検索して候補として使う**方式である。候補はtarget LLM自身が検証するため、検索が外れても生成品質を犠牲にしない。

## 概要

通常の自己回帰復号（autoregressive decoding）では、target LLMを1回forwardして1 tokenを確定し、そのtokenを入力へ追加して次のforwardへ進む。

大規模LLMでは1 tokenあたりの演算量だけでなく、毎stepで巨大なweightをGPU memoryから読むこと自体が高価である。batch size 1では特にmemory-bandwidth-boundになりやすく、GPUの行列演算能力を十分使えない。

一般的な投機的復号は、targetより小さいdraft modelに数tokenを先に提案させ、その候補をtarget modelへまとめて通して検証する。draftがよく当たれば1回のtarget passで複数tokenを確定できる。

しかしこの方式には、

- target modelごとに相性のよいdraft modelを用意する必要がある
- draft modelのweight用VRAMが追加で必要
- draft model自身のforward costがある
- model architectureやtokenizerが変わるとdraftを作り直す必要がある

という負担がある。

RESTはここで「次tokenはneural modelで予測しなくても、**過去のtextに同じような文脈があれば、その続きが強い候補になる**」と考える。

codeには定型的なAPI呼出しや構文、chatには頻出表現が多い。現在contextの末尾と同じtoken列がcorpus内に見つかれば、その直後のtoken列をdraftとして使える。

RESTはこのretrievalを非常に軽く実行し、複数のretrieved continuationを1本ずつ検証するのではなくTrie形式のtreeへまとめ、target LLMの1回のtree verificationで処理する。

## 問題設定

### draft modelはtarget modelより軽いが、無料ではない

speculative decodingではdraft modelがtargetより十分小さいことが前提になる。しかし、小型modelでもweight storageとGPU computeを消費する。

さらにproprietary modelや特殊fine-tune modelでは、品質の高いcompatible draft modelが必ず存在するわけではない。

RESTはdraft modelを**parameter-freeなretrieval engine**へ置き換えることで、この依存をなくす。

### retrievalは『意味が似ている文』を探す必要はない

RESTの主方式はembeddingを使ったsemantic retrievalではない。

目的は「今の文脈と意味が近いdocumentを探す」ことではなく、**次token候補としてそのまま使える文字列を極めて低costで見つけること**である。

そのため現在context末尾のtoken列とdatastore中のtoken列の**exact match**を利用する。

codeでは同じidentifierやsyntax pattern、chatでは頻出phraseが繰り返されるため、exact suffixだけでも有用な候補が得られる。

### retrieval自体が遅ければtarget passを減らす意味がない

target LLMを1回省くために数十msのdense-vector searchを行うと、benefitを失う可能性がある。

そこでRESTはsuffix arrayなどCPU上で軽量に検索できるdata structureを使い、論文評価ではretrieval overheadを全decode時間の6%未満に抑えている。

## 手法のあらまし

1回のREST decode cycleは次のように進む。

1. 現在まで確定したtoken列の**末尾**をqueryにする。
2. datastoreから、その末尾token列と一致する過去contextを探す。
3. 一致箇所の直後に実際に続いていたtoken列を複数取り出す。
4. それらを共通prefixでまとめたTrieを作る。
5. 頻度の高いnodeを中心に候補treeを最大約64 nodeへ絞る。
6. treeをtarget LLMへ1回だけforwardし、各nodeの次token分布を並列計算する。
7. target LLMの本来の生成規則と一致したbranchだけをrootから順にacceptする。
8. mismatchした地点でtarget LLM自身のtokenを採用し、次cycleへ進む。

retrieval候補が完全に外れても、最低1 tokenはtarget model自身から得られる。よく当たったときだけ1回のtarget passで複数tokenを前へ進める。

## 手法

### 1. datastoreを『context → continuation』として作る

RESTでは、外部text corpusをtokenizeし、各位置について「このcontextの後にはどのtoken列が続いていたか」を検索できる形にする。

HumanEvalのcode生成ではThe Stack由来の約270万Python sampleを使い、large datastoreは約27GBである。chat生成ではUltraChatを使い、large datastoreは約12GBである。

ここでdatastoreはtarget modelのweightを学習するためのtraining dataではない。inference時に「過去に同じ文字列があったか」を引くためのlookup sourceである。

そのためtarget LLMを再学習する必要はない。

### 2. 現在contextの『最長suffix』から一致箇所を探す

生成済みcontext全体がcorpus内に完全一致する可能性は低い。一方、末尾数tokenだけなら同じpatternが存在する可能性が高い。

RESTは最初に最大16 token程度のsuffixから検索し、一致が見つからなければsuffixを徐々に短くする。

概念的には、

`最後の16 tokenで検索 → 無ければ15 token → 14 token → …`

と進み、最も長く一致するsuffixを使う。

suffixが長いほど候補の文脈specificityは高い。一方、短くするとhit数は増えるが無関係なcontinuationも増える。

### 3. suffix arrayでexact matchを軽量化する

corpus全体を毎step線形scanすることはできない。

RESTは接尾辞配列（suffix array）のような索引を使って、現在suffixと同じtoken sequenceが現れる位置を高速に検索する。

接尾辞配列は、corpus内の各位置から始まるtoken suffixを辞書順に並べたindexである。同じprefixを持つsuffixが近くへ集まるため、binary searchで一致範囲を求められる。

neural retrieverをGPUでforwardする必要がなく、CPU lookupだけで済むのがRESTの軽量性につながる。

### 4. 一致箇所の『その後』をdraft候補として取得する

一致したcorpus位置ごとに、その直後のtoken列を最大10 token程度取得する。

たとえば現在context末尾が

`for i in range (`

で、corpus中に同じsuffixが100回あったなら、それら100箇所の後ろに実際に続いていたtoken列がdraft候補になる。

同じcontinuationが何度も出現していれば、その候補は頻度が高い。

RESTはこの**corpus frequencyを候補の信頼度proxy**として使う。

### 5. 候補列をTrieへまとめる

100個のcontinuationを別々にtarget LLMへ通すと重複計算が多い。

たとえば、

- `self . model (`
- `self . tokenizer (`
- `self . config .`

の3候補は最初の `self .` を共有している。

RESTはこれらをTrie、つまり**共通prefixを1つのnodeとして共有するtree**へまとめる。

各nodeには、そのprefixがretrieved continuation中に何回現れたかというfrequencyを持たせる。

このfrequencyが高いnodeほどtarget outputになる可能性が高いとみなし、候補treeを絞るときに優先する。

### 6. treeを無制限に大きくせず、上位nodeだけを使う

retrieval hitが大量にあるとTrieも巨大になる。候補を増やすほどtarget outputを含む確率は上がるが、verification computeとmemoryも増える。

RESTの主設定では頻度の高いnodeを中心に**最大64 candidate token程度**を採用する。

つまり「retrieved continuationを全部検証」するのではなく、corpus中で何度も現れたbranchへverification budgetを優先配分する。

### 7. breadth-first orderへ並べてtree attentionを行う

GPUへtree data structureをそのまま渡すことはできないため、Trie nodeを幅優先探索（breadth-first search: BFS）順などで1本のpseudo-sequenceへ並べる。

ただし普通のcausal attention maskを使うと、branch Aのtokenがbranch Bのtokenを見てしまう。

そこでtree attention maskを使い、各candidate tokenが、

- 既に確定済みのoriginal context
- tree rootから自分までのancestor node

だけを参照できるようにする。

これによりtree nodeを1回のbatched target forwardで処理しながら、各branchを個別sequenceとして処理した場合と同じdependencyを保てる。

### 8. target modelがaccept/rejectを決めるのでlossless

retrievalはあくまでdraft sourceである。

最終的にtokenを採用するかどうかはtarget LLMのconditional probabilityで決まる。

貪欲復号（greedy decoding）なら、各nodeでtarget modelのargmax tokenと一致するchildだけをacceptする。

核サンプリング（nucleus sampling）のような確率的samplingでも、speculative decodingのaccept/reject ruleを適用してtarget distributionを保つ。

最初のmismatch以降のdraft tokenは破棄し、その地点ではtarget model自身からsampleしたtokenを採用する。

したがってretrieval corpusに誤ったcontinuationしかなくても、**速くならないだけでtarget modelの出力品質をretrieval側へ置き換えない**。

## 評価

### まず見るところ

RESTの効果はworkloadの**文字列反復性**に強く依存する。

codeでは同じsyntax・API・boilerplateが多いためretrieval continuationが長く当たりやすく、2倍超のspeedupが出る。open-ended chatではmatch lengthが短く、speedupは1.6〜1.8倍程度へ下がる。

つまりRESTは「一般的なneural draftを不要にする万能方式」ではなく、**既存corpusから長いcontinuationを引けるdomainほど強いdraft mechanism**である。

### 実機条件

| 項目 | 内容 |
|---|---|
| GPU | NVIDIA A6000 ×1 |
| CPU | 96 cores |
| Batch size | 1 |
| Repetition | 各結果3回平均 |
| Code models | CodeLlama-7B / 13B |
| Chat models | Vicuna-7B / 13B |
| Code benchmark | HumanEval |
| Chat benchmark | MT-Bench |
| Code datastore | The Stack由来Python corpus |
| Chat datastore | UltraChat |

### HumanEval / greedy decoding

| Model | 通常decode | REST | Speedup |
|---|---:|---:|---:|
| CodeLlama-7B | 27.89 ms/token | 11.82 ms/token | **2.36×** |
| CodeLlama-13B | 44.32 ms/token | 19.53 ms/token | **2.27×** |

nucleus samplingでも7Bで約2.12×、13Bで約2.17×を報告する。

### MT-Bench

chatではcodeよりrepeat patternが弱いため改善は小さい。

- Vicuna-7B greedy: 約1.69×
- Vicuna-13B greedy: 約1.77×
- Vicuna-7B nucleus: 約1.62×
- Vicuna-13B nucleus: 約1.71×

それでも追加draft modelを持たずにtarget pass回数を減らせている。

### 平均で何tokenずつ進めるか

論文のMean Generated Lengthは、1 target verificationで平均何token確定できたかを見る指標である。

HumanEvalではおよそ2.65〜2.69 token、MT-Benchでは約1.97〜2.01 tokenだった。

この値はretrieval / tree construction / verification overheadを無視した場合のspeedup上限に近い。

たとえば平均2.7 token確定できてもend-to-end speedupが2.36倍に留まるのは、retrieval lookupや64-node tree verificationにも追加時間が必要だからである。

### retrieval cost

論文ではretrieval overheadは全体の6%未満に抑えられている。

これはRESTがdense embedding searchではなくexact suffix lookupを選んだ理由と整合する。

公式repositoryでは軽量版datastoreも提供しており、ShareGPT系chat datastoreは約465MB、The Stack系code datastoreは約924MB程度のsmall configurationを構築できる。大規模評価用はそれぞれ約12GB / 27GBである。

## 既存研究との差

### neural draft speculative decodingとの違い

通常のspeculative decodingでは、targetより小さいneural modelがcandidate tokenを生成する。

RESTでは**corpus lookupがdraft modelの代わり**になるため、draft weight、draft training、draft forwardが不要になる。

一方、corpusに似たcontinuationがなければ候補品質は低くなる。neural draftは未知contextにもgeneralizeできるが、RESTはtextual repetitionへ強く依存するというtrade-offがある。

### LLMAとの違い

同時期のretrieval-assisted decodingであるLLMAは、主に現在requestが参照しているdocumentなど少数のreferred contextからcontinuationを再利用する。

RESTはより大きな外部datastoreを作り、**多数の過去instanceからcurrent suffixと一致するcontinuationを集めてtree化する**点が異なる。

### SpecInferとの関係

SpecInferは複数small modelから作ったcandidateをtreeへまとめる。RESTはcandidate sourceをretrievalへ置き換える。

どちらも最後はtarget modelによるtree verificationを使うため、**candidate generationとverificationを分離する**というspeculative serving architectureは共通している。

## 限界

- corpusに似たcontinuationが少ないopen-ended domainではaccept lengthが短くなる。
- exact suffix matchなのでsemanticに似ていて表面形が違うcontinuationは拾えない。
- 大規模datastoreは12〜27GB級の追加storage / memoryを必要とする。
- retrieval indexをCPUで維持するためhost resourceも必要。
- 主評価はbatch size 1であり、高concurrency servingでのthroughput gainは別途検証が必要。
- datastoreはtarget tokenizerでtokenizeする必要があり、tokenizerが変わればindexを作り直す必要がある。
- tree sizeを増やしすぎるとtarget verification overheadが増える。
- corpus distributionがdeployment workloadと異なるとretrieval hit / continuation qualityが低下する。

## 一般的な実装上の含意

RESTが示す重要な点は、speculative decodingのdraft sourceが必ずしもneural networkである必要はないことである。

特に、

- code generation
- SQL
- configuration file
- template文書
- domain-specific定型文

のように反復patternが多いworkloadでは、過去outputやdomain corpusを**draft token cache**として再利用できる。

この場合、draft modelを追加するよりも、CPU上のcompactなexact-match indexの方が安い可能性がある。

さらに、candidate sourceをretrieval / small model / n-gram cacheなど複数用意し、それらを同じtree verification backendへ統合する設計も考えられる。SpecInferや後続tree-based decodingと組み合わせると、draft生成器とtarget verificationを独立componentとして扱うsystem designにつながる。
