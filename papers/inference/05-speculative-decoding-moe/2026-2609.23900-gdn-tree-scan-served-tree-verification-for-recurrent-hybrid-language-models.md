# GDN Tree-Scan: Served Tree Verification for Recurrent-Hybrid Language Models

> 再帰状態を持つハイブリッドLLMの木型投機検証で、枝ごとのGDN状態を親子関係どおりに走査し、受理枝だけを永続化することで、Qwen3.6-27B-FP8のデコード処理量を27.0%改善する。

## 概要

GDN Tree-Scanは、**注意機構だけのTransformer向けに作られた木型投機的デコードを、そのまま再帰状態を持つハイブリッド言語モデルへ移すと意味的に壊れる**という問題を扱う。通常の木型検証では、各候補トークンが接頭辞と自分の祖先だけを参照するよう注意マスクを作れば、兄弟枝どうしの情報漏洩を防げる。しかしGated-DeltaNet（GDN）のような再帰層では、注意とは別に「直前までの系列を圧縮した状態」が次トークン計算へ渡る。この状態まで親子関係どおりに分岐させなければ、注意マスクは正しくても存在しない履歴を条件に候補を検証してしまう。

提案手法は、FlashAttention-2へ木構造の可視性を与える処理、候補枝ごとにGDN状態を親から子へ走査する処理、検証後に受理された鎖だけを再生して永続状態へ反映する処理、複数ドラフトの確定をGPU上で行う処理を一つのvLLM経路へ統合する。重要なのは「木を速く計算する」ことだけではなく、**逐次デコードと同じ状態系譜を保ったまま木をまとめて計算する**ことである。

公開Qwen3.6-27B-FP8、バッチ1、温度0.6のSWE/Codexデコード条件では、6ノードの根付き分岐木が1イベント当たりの確定トークン数を4.11から4.82へ増やし、トークン重み付きデコード速度を18.80から23.88 token/sへ高めた。改善率は27.0%である。一方、各要求を同じ重みで集計すると17.80から18.51 token/sで4.0%改善に留まる。さらにタスク全体ではプリフィル時間の比率が大きい。このため「27%高速化」は、指定されたデコード区間と集計方法における結果として読む必要がある。

## 背景：なぜ注意マスクだけでは足りないのか

投機的デコード（speculative decoding）は、安価なドラフト側で複数トークン候補を先に作り、高価な対象モデルでまとめて検証する。木型方式では一本の候補列だけでなく複数の分岐を一度の前向き計算へ詰める。注意だけのTransformerなら、候補ノードが「接頭辞＋自分の祖先」以外を見ないように木型注意マスクを作ることで、各枝を独立した自己回帰履歴として扱える。

再帰型モデルでは事情が異なる。GDN層はトークン列を一つの内部状態へ逐次畳み込み、その状態を次位置へ渡す。候補をメモリ上で単に行方向へ並べ、直前に置かれた候補の状態を次行へ渡すと、論理的には兄弟であるノードが物理配置上の直前ノードを親としてしまう。つまり**注意の祖先関係と再帰状態の祖先関係が食い違う**。この誤りは候補受理率だけの問題ではなく、対象モデルそのものとは異なる条件付き分布を評価する正しさの問題になる。

したがって再帰型ハイブリッドLLMのserved verifierには、少なくとも「木型注意」「枝局所の再帰状態」「棄却・受理規則」「次イベントへ公開する状態」の4つを同じ木構造へ整合させる必要がある。GDN Tree-Scanはこの実装契約をvLLMの実行境界まで具体化する研究と位置づけられる。

## 問題設定

入力は、すでに確定した接頭辞、複数のドラフト候補、各候補ノードの親番号である。出力は、対象モデルの逐次自己回帰生成と整合する確率で確定されたトークン列と、その列の末尾に対応するGDN永続状態でなければならない。

難しいのは、木全体を一括処理したいという性能上の要求と、各枝を逐次処理した場合と同じ状態遷移を再現したいという正しさの要求が衝突する点である。枝ごとにモデルを完全に直列実行すれば正しいが、木型検証の並列性を失う。逆に全候補を一列として高速処理すると、兄弟枝の状態混入が起こる。

さらに、検証中には受理されない枝の状態も一時的に計算する。これをそのままグローバル状態へ書き戻すと、次の生成イベントが棄却済み履歴から始まる。したがって「一時状態を作る場所」と「次イベントが参照する永続状態」を分ける必要がある。

## 手法のあらまし

GDN Tree-Scanの処理は、候補木を一つの大きなforwardへ押し込むだけではない。注意層と再帰層で別々に木構造を実装し、最後に受理鎖へ状態を収束させる。

1. 候補トークンと親配列から祖先関係を作り、FlashAttention-2側では各ノードが接頭辞と祖先だけを見るようにする。
2. GDN層では各候補を位相順に走査し、根は接頭辞状態、子は論理的な親ノードの一時状態を入力として一段の状態遷移を計算する。
3. 対象モデルの確率からGPU上で受理鎖を確定する。
4. 受理された鎖だけを再生・公開し、棄却枝の一時状態は次イベントへ残さない。

この分解により、候補探索の幅を広げるための一時的な計算と、サービスが将来に持ち越すモデル状態を分離する。

## 手法

### 1. FlashAttention-2による木型注意

通常の因果マスクは「自分より前の位置」をすべて参照可能にする。しかし木を一次元へ詰めた場合、物理的に前にある兄弟ノードまで見えてしまう。GDN Tree-Scanは候補の親番号から祖先集合を構築し、各候補行が接頭辞と自分の祖先だけへ注意を向ける木型バイアスをFlashAttention-2へ与える。

入力は候補トークン、親配列、既存接頭辞で、出力は枝間の注意漏洩を防いだ注意結果である。この処理はTransformer部分の因果性を守るが、GDN状態の因果性までは保証しない。論文のポイントは、**木型注意を正しくしただけでは再帰ハイブリッドモデルの検証は完成しない**と切り分けたことにある。

### 2. 枝局所GDN走査

各GDN層では候補ノードを親が子より先に現れる位相順で処理する。根候補は確定接頭辞のGDN状態から始め、子候補は親候補を一段進めた一時状態を読む。得られた新状態は候補ノード専用領域へ置き、そのノードの子だけが再利用する。

これにより、GPU上では複数候補をまとめて扱いながら、論理的には「各枝を根から逐次実行した状態遷移」を再現する。一時状態のメモリ量と親対応管理が追加コストになる。木を大きくするほど候補状態の保持量と走査仕事量も増えるため、候補数を増やせば常に速くなるわけではない。

### 3. 受理鎖だけの再生と永続化

木のforwardが終わると、対象モデルの確率とドラフト候補に基づいて受理・棄却を決める。ここで得られるのは、木全体ではなく根から連続する一つの受理鎖である。GDN Tree-Scanはこの受理鎖に属する状態だけを次イベント用の永続状態へ反映する。

棄却枝の状態は、検証のために正しく計算されていても公開しない。この分離によって、投機幅を広げたことが後続トークンの履歴を汚染するのを防ぐ。正しさの観点では「候補計算が正しい」ことと「公開される最終状態が正しい」ことを別々に満たしている。

### 4. GPU側の複数ドラフト確定

検証結果を候補ごとにCPUへ戻して受理鎖を決めると、木を広げるほどデバイス―ホスト制御往復が増える。GDN Tree-Scanは複数ドラフトの確定をデバイス側で行い、対象確率と木構造から受理鎖を選ぶ。

これはモデルの確率分布を近似する機構ではなく、確定処理の配置を変える最適化である。性能利得は、候補木が十分な追加確定トークンを生むことと、木型forwardの追加コスト・状態管理・確定処理がその利得を食い潰さないことの両方に依存する。

## 評価

### まず見るところ

- **主結果:** 6ノード木でトークン重み付きデコード速度は18.80→23.88 token/s、27.0%改善。
- **受理側の変化:** 確定トークン/イベントは4.11→4.82で17.2%増加。
- **集計方法による差:** 要求均等の速度は17.80→18.51 token/sで4.0%改善に留まる。
- **正しさ:** 40ターンの再帰オラクル確率再採点で、差は観測されたnative flip floor内。ただし完全な分布距離証明ではない。
- **エンドツーエンド:** プリフィルが大きいため、27.0%をタスク全体の短縮率として解釈しない。

### 評価条件

| 項目 | 条件 |
|---|---|
| 対象モデル | Qwen3.6-27B-FP8 |
| 配信基盤 | vLLMへ統合 |
| ワークロード | SWE/Codex系4タスク |
| バッチ | 1 |
| サンプリング温度 | 0.6 |
| 比較基準 | native five-step MTP（E5） |
| 提案構成 | 6ノードroot-branch tree |
| 主要速度指標 | トークン重み付きデコードtoken/s、要求均等token/s |
| 正しさ確認 | 40ターンのrecurrent-oracle probability rescore |

### 主要結果

| 指標 | 基準 | GDN Tree-Scan | 変化 |
|---|---:|---:|---:|
| 確定トークン/イベント | 4.11 | 4.82 | +17.2% |
| トークン重み付きデコード速度 | 18.80 token/s | 23.88 token/s | +27.0% |
| 要求均等デコード速度 | 17.80 token/s | 18.51 token/s | +4.0% |
| 検証forward時間 | native近傍 | 6ノード木でもnear-native | 木の追加確定数が利得源 |
| 分布等価性 | nativeの数値揺らぎを基準 | p-rescore差が観測flip floor内 | 限定的な経験的証拠 |

トークン重み付き値と要求均等値の差は重要である。長い要求や多くのトークンを含む要求が改善すると前者へ強く効く一方、各要求を同じ一票として扱う後者では改善が小さくなる。したがってサービス全体でのユーザー体感を評価する場合、どちらの集計を採用したかを明示する必要がある。

また、デコード区間が速くてもプリフィルが全体時間の大部分なら、エンドツーエンド短縮は小さくなる。論文自身もこの点を分離しており、木型検証の速度値をタスク壁時計時間へそのまま外挿していない。

### 正しさ評価と未評価項目

40ターンの再帰オラクル確率再採点では、Tree-Scanと基準の差はnative実行自身に見られる数値的なflip floor内へ収まる。ただし、これは全出力分布の全変動距離（total variation distance）を計算した証明ではない。複数乱数種、大きいバッチ、要求単位の統計検定も主結果では完了していない。

このため、現時点で強く言えるのは「指定された条件で、枝局所再帰状態を含むserved verifierが基準と整合する経験的証拠を得た」という範囲である。モデル・バッチ・木形状が変わっても完全に同一であるという一般証明ではない。

## 既存研究との差

SpecInferやSequoiaのような木型投機方式は、候補木の構築と並列検証を中心に扱う。注意専用モデルでは木型因果マスクが主な正しさ条件になる。状態空間・再帰モデル向け研究は内部状態の分岐や再生を扱うが、GDN Tree-Scanは**vLLMのserved実行、FlashAttention-2、GDNの状態書き戻し、GPU側確定までを一つの検証契約として閉じる**点に特徴がある。

特に、性能最適化だけでなく「棄却枝の状態を次イベントへ出さない」という状態公開境界を明示した点が重要である。再帰ハイブリッドモデルへ既存の投機デコード実装を移植する際、注意マスクの互換性だけを確認しても不十分であることを具体例として示している。

## 限界・実装状況

評価は公開Qwen3.6-27B-FP8、バッチ1、限られたSWE/Codexタスクが中心であり、他の再帰ハイブリッド構造へそのまま一般化できるとは限らない。木を大きくしたときの一時状態メモリ、バッチ増加時の枝数との積、GPU型番を跨ぐ性能特性は主結果から確定できない。

27.0%はデコードのトークン重み付き集計で、要求均等では4.0%である。エンドツーエンド時間はプリフィル支配であり、オンラインサービス全体の改善率とは分けて読む必要がある。分布等価性も限定的な再採点証拠であり、完全な確率分布証明ではない。
