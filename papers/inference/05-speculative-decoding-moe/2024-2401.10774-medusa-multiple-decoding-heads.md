# Medusa: Simple LLM Inference Acceleration Framework with Multiple Decoding Heads

> Medusaは、投機的復号（speculative decoding）用に**別の小型draft modelを用意せず、target LLM自身のhidden stateから複数の未来tokenを予測する小さなheadを足す**方式である。候補をtreeへまとめてtarget backboneで一括検証し、1回の大きなmodel forwardで複数tokenを確定する。

## 概要

通常の自己回帰復号（autoregressive decoding）は、1 tokenを出すたびに大規模LLM全体を1回forwardする。

batch size 1では1 stepで処理するtoken数が少ない一方、model weightは毎step HBMから読み出す必要がある。そのためGPUの演算器が十分あっても、weightを読むmemory bandwidth側が律速になりやすい。

一般的なdraft-target型speculative decodingは、小さいdraft LLMに数tokenを先に生成させ、それをtarget LLMでまとめて検証することでtarget forward回数を減らす。

ただし、

- target modelに合うdraft modelを別途探す / 学習する必要がある
- draft modelのweightをGPU memoryへ置く必要がある
- distributed targetとは別にdraft execution pathを管理する必要がある
- sampling generationではdraftとtargetの分布差がacceptanceを下げやすい

という運用上の負担がある。

Medusaは、target modelの最後のhidden representationが既に「次tokenだけでなく、その先のtokenについても相当な情報を含んでいる」ことを利用する。

通常のLM headに加えて、

- Medusa head 1: 1つ先の未来token
- Medusa head 2: 2つ先
- Medusa head 3: 3つ先
- …

を予測する軽量headを付ける。全headは**同じbackbone hidden stateを入力にして並列実行**できるので、別draft transformerを何stepもautoregressiveに回すより安い。

ただし各未来位置でtop-k候補を出すと、候補の組合せは指数的に増える。そこで有望な組合せだけをtoken treeへしぼり、tree attentionでtarget backboneへまとめて通す。

## 問題設定

### 『次tokenを当てる』だけでは複数token確定できない

通常LM headが予測するのは次の1 tokenだけである。

1回のbackbone forwardから3 token進みたいなら、少なくとも

- 次token候補
- 2 token先候補
- 3 token先候補

をbackboneを再実行せずに用意する必要がある。

Medusa headsはこのfuture-position predictionを担当する。

### 未来へ行くほどprediction uncertaintyが増える

同じhidden stateから1 token先を予測するのは比較的簡単だが、4 token先・5 token先は途中tokenがまだ確定していないため不確実性が大きい。

そのため各headからargmax 1個だけを使うと、遠いheadが外れた時点でそこから先を利用できない。

Medusaは各headのtop-k候補を組み合わせ、**未来に複数branchを持たせる**ことで、1本の予測列が少し外れても別branchに正解が含まれる確率を上げる。

### しかし候補の直積はすぐ巨大になる

4 headが各5候補を出すだけでも単純な全組合せは `5^4 = 625` 通りになる。

これを全部target modelで検証すると、autoregressive decodingより重くなり得る。

Medusaではoffline statisticsからよく成立する候補position combinationを選び、**denseな全組合せではなくsparse tree**だけを検証する。

この「candidate coverageを上げたいがverification token数は増やしたくない」というtrade-offがMedusaのsystem designの中心にある。

## 手法のあらまし

1 decode cycleは次のように進む。

1. target backboneを現在tokenまで通常どおりforwardする。
2. 通常LM headは次token分布を出す。
3. 複数Medusa headが同じhidden stateからさらに未来のtoken候補を並列予測する。
4. 各headのtop候補を事前に選んだsparse tree patternへ組み合わせる。
5. tree nodeをtarget backboneへ1回にまとめて通し、tree attention maskでbranchを分離する。
6. target modelの出力に照らして、rootから連続して正しいcandidateをacceptする。
7. 最も長くacceptできたprefixを確定し、次cycleへ進む。

Medusa headは最終回答を直接決めるのではなく、**target backboneへ検証させる候補を安く作る役割**である。

## 手法

### 1. 各Medusa headは小さな残差MLP + LM head

Medusa headはtarget model全体のcopyではない。

backbone最終hidden state `h` を受け、軽いresidual blockを通して語彙logitへprojectする。

概念的には、

`h → small residual transform → original LM projection → future-token logits`

という構造である。

各headは異なるfuture offsetを担当する。同じ `h` を共有するのでhead同士はparallelに計算できる。

backboneが数十億parameterなのに対し追加headは非常に小さいため、別draft transformerをGPUへ常駐させるよりmemory / compute overheadを抑えやすい。

### 2. headごとにtop-k候補を取る

future tokenを1個に固定せず、それぞれのheadから上位候補を複数取る。

例えば、

- head 1: `is`, `was`
- head 2: `a`, `the`
- head 3: `good`, `large`

のような候補が出る。

ただし全直積を作らず、どのrank combinationをtreeへ含めるかを制限する。

### 3. sparse Medusa treeでverification budgetを配る

Medusaはtraining / calibration statisticsから、future positionごとのtop-k predictionがどのrankで当たりやすいかを見る。

たとえば「1 token先ではtop-1が強いが、3 token先ではtop-2まで持たないとcoverageが低い」といった傾向が得られる。

その確率とtree node budgetから、有望なpathだけを残したsparse treeを構成する。

つまり同じ64 candidate tokenを検証するなら、ランダムにbranchを作るのではなく**acceptされる確率が高いbranchへnode budgetを集中する**。

論文のablationでもdense / randomなtreeよりoptimized sparse treeの方が効率的である。

### 4. tree attentionで候補branchをtarget modelへ一括投入する

SpecInferと同じく、candidate treeの各nodeは自分のancestorだけを見る必要がある。

branch Aの2 token目がbranch Bの1 token目へattentionしてしまうと、本来存在しないsequenceを検証することになる。

そこでtree attention maskを使い、各nodeが

- 確定済みcontext
- rootから自分までのancestor candidate

だけを参照できるようにする。

これにより多数candidate nodeを1つのbatched forwardとして処理しつつ、各pathに対するtarget-model logitを正しく得られる。

### 5. Medusa-1: backboneを凍結してheadだけ学習する

Medusa-1では既存target LLMを一切変更せず、追加headだけをfine-tuneする。

これには大きな利点がある。

- base modelの能力を変えない
- training対象parameterが少なく済む
- 既存checkpointへ後付けしやすい
- target backbone自身でcandidateを厳密検証すれば、元modelと同じdecoding結果を保てる

したがってMedusa-1は**既存modelへ追加するlossless acceleration layer**として扱いやすい。

公式実装ではVicuna 7B / 13B / 33B向けhead weightも公開されている。

### 6. Medusa-2: backboneも『未来を予測しやすい表現』へ共同学習する

Medusa-1の問題は、元backboneが「未来headから数token先を予測しやすいhidden state」を作る目的ではtrainingされていないことである。

Medusa-2はbackboneとheadsを一緒にfine-tuneし、通常next-token能力を維持しながらfuture headsの予測性も高める。

ただし単純にmulti-step lossを足して最初からjoint trainingすると、base modelの通常能力を壊す可能性がある。

そのため論文ではhead warm-upを含む段階的trainingとloss / learning-rate設計を用い、**元model品質を維持しつつspeculative predictabilityを追加する**。

Medusa-2はhead accuracyが高くなりspeedupも大きいが、backbone checkpoint自体が変わるため、Medusa-1と同じ意味での「元checkpointと完全同一のlossless acceleration」ではない。

### 7. training dataが無ければself-distillationする

既にfine-tune済みのmodelへMedusaを追加したいが、そのmodelの元training dataが手元にない場合がある。

Medusaは自己蒸留（self-distillation）を提案する。

seed promptをbase modelへ与え、base model自身にresponseを生成させ、そのsynthetic prompt-response pairをMedusa training dataとして使う。

これによりoriginal private dataなしでも、「このmodelがどんなcontinuationを生成するか」をheadsへ学習させられる。

### 8. 厳密acceptanceとtypical acceptanceを分ける

greedy decodingで元modelと完全に同じtoken列を求める場合、candidateはtarget modelのargmaxと一致したときだけacceptする。

samplingでもrejection samplingを正しく使えばtarget distributionを保てる。

一方Medusaは**典型受理（typical acceptance）**も提案する。これはtarget modelが十分高い確率を与えており、「その分布から見て典型的」と判断できるcandidateなら、厳密なsampling結果と同一でなくてもacceptしやすくする。

これによりacceptance lengthは伸び、sampling generationをさらに速くできる。ただしこれは「同じrandom seedでtarget-only samplingと完全同じsequenceを再現する」保証を緩めた**quality-speed trade-off**である。

論文はMT-Bench等で生成品質を測り、速度を上げても品質をほぼ維持できる領域を示している。

## 評価

### まず見るところ

headlineは、

- **Medusa-1:** 生成品質を損なわず2.2×超
- **Medusa-2:** 約2.3〜3.6×

である。citeturn341808view0

ただしこの倍率は「追加headの計算が3倍速い」という意味ではない。

Medusaは1 target forwardで平均して複数tokenを確定し、**巨大backboneを実行する回数を減らす**。head計算とtree verificationは追加costなので、平均accept token数がそのままspeedupにはならない。

### 評価対象

論文・公式実装ではVicuna-7B / 13B / 33BやZephyr-7Bなどを扱い、主にbatch size 1のlocal / interactive inferenceを中心に評価する。公式repositoryもsingle-GPU batch-size-1 inferenceを主要supportとして説明している。citeturn360960search0

### Medusa-1

backboneをfreezeしたMedusa-1は2.2×超のspeedupを報告する。citeturn341808view0

この構成の意味は、「base modelを再trainingせず、その上にfuture headsだけを追加してtarget verification回数を減らせる」ことである。

別draft modelを用意しなくてもよく、distributed target modelのdevice placementをdraft側に合わせて再設計する必要も少ない。

### Medusa-2

joint trainingするMedusa-2ではhead prediction accuracyが上がり、2.3〜3.6×までspeedupを伸ばす。citeturn341808view0

大きな改善は、backbone hidden state自体がmulti-step predictionへ適応するため、同じtree budgetでtarget outputを含むbranchが長くなりやすいことによる。

ただしMedusa-2ではtraining costとmodel-quality validationが追加で必要になる。

### structured taskほど速くなりやすい

Medusaの利得はprompt typeで変わる。codeやinformation extractionのようにcontinuation uncertaintyが比較的小さいtaskではfuture headが当たりやすく、creative writingのように次token候補が広いtaskではtree acceptanceが短くなりやすい。

そのため1つのheadline speedupをすべてのworkloadへそのまま適用すべきではない。

### treeを増やしすぎるとcompute-boundになる

candidate node数を増やすとaccept率は上がる一方、target modelが1 verification passで処理するtoken数も増える。

通常decodeはmemory-boundなので少数candidateをまとめるのは有利だが、treeを大きくしすぎるとmatrix computeが増え、最終的にはcompute-boundへ寄る。

したがってMedusaでは「最大acceptance」ではなく、**verification cost込みのwall-clock latencyを最小化するtree size**が必要になる。

## 既存研究との差

### 通常のdraft-target speculative decodingとの違い

通常方式ではsmall transformerを別modelとして持ち、autoregressiveにcandidate tokenを生成する。

Medusaはtarget backboneのhidden stateを共有し、future predictionは軽量headだけでparallelに行う。

このためdraft model weightと別decode loopを持たずに済む。

### SpecInferとの違い

SpecInferは複数small modelが作ったcandidateをtreeへまとめる。Medusaは**candidate sourceをtarget model上のfuture headsへ内蔵する**。

tree verificationの考え方は近いが、draft generationのsystem complexityを大幅に減らす点がMedusaの中心である。

### EAGLEとの関係

Medusaは同じhidden stateから数token先のtoken identityを直接予測するため、future distanceが伸びるほどuncertaintyが大きい。

EAGLEはこの問題を「tokenを直接当てるより、次stepのhidden featureをautoregressiveに予測する方がよい」と捉え直し、feature-level draftへ進む。

したがってEAGLEはMedusaのmulti-token-head方式に対する直接的な後続方向として理解できる。

## 限界

- Medusa headの追加trainingが必要。
- Medusa-1は元checkpointを保ちやすいが、future head accuracyには上限がある。
- Medusa-2はより速い一方、backboneを再trainingするためmodel能力の再検証が必要。
- candidate treeを大きくするとverification FLOPs / memoryが増える。
- speedupはtaskのpredictabilityに依存する。
- 主要評価・公式初期runtimeはbatch size 1中心で、高concurrency servingではbenefitが変わる。
- typical acceptanceはaccept率を高めるが、厳密なtarget samplingとの同一性とは別の品質基準で評価する必要がある。
- head数を増やせば無条件に速くなるわけではなく、遠いfuture headほどprediction uncertaintyが増える。

## 一般的な実装上の含意

Medusaが示した重要な設計点は、speculative decodingのdraftを**独立modelとして持つ必要はない**ことである。

大規模target modelでは1回のbackbone passが高価なので、最後のhidden stateから少量の追加computeで未来candidateを複数作れるなら、多少verification FLOPsを増やしてでもtarget pass回数を減らす価値がある。

実装上は、

1. future headsの追加memory
2. tree node数
3. 1 cycleあたりのaccept token数
4. target verificationのcompute増加
5. batch / concurrency

を同時に測る必要がある。

またMedusa headsは量子化やtarget backboneのkernel最適化と競合するものではなく、**1回のtarget passを速くする技術**と**target pass回数を減らす技術**として組み合わせられる。
