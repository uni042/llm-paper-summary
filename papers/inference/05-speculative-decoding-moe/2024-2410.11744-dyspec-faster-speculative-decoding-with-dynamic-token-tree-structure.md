# DySpec: Faster Speculative Decoding with Dynamic Token Tree Structure

> ドラフト確率を対象モデルの受理確率の代理にして投機木を実行時に動的構築し、限られた検証予算を高確率枝へ集中して固定木より長い受理系列と低遅延を狙う。

## 概要

投機的復号（speculative decoding）では、軽量なドラフトモデルが複数候補を作り、大型の対象モデル（target model）がまとめて検証する。木構造の候補を使えば一度に複数の未来を試せるが、固定木は「どの枝が有望か」が入力やサンプリング温度によって変わっても同じ形を使うため、限られた候補数を低確率枝へ浪費する。

DySpecは予備実験で、ドラフトモデルが高確率を付けたトークンほど対象モデルでも受理されやすいという相関を確認し、ドラフト確率を受理可能性の代理として使う。固定した投機予算 (N) の中で、現在最も高確率な候補ノードを優先的に展開し、受理された場合に進む子と、拒否された場合の次候補となる兄弟をヒープへ追加する。これにより各入力・温度の確率分布に合わせて木の深さと幅が変わる。

木構築をそのまま行うと候補追加ごとにドラフトモデルを走らせるため高価になる。DySpecは確率閾値を使って同じ深さの有望候補をまとめて生成し、候補数 (N) に比例していたドラフト前向き計算を木の深さに近い回数へ抑える。68Mドラフト→7B/13B対象モデルでは木構築を含む非モデル処理が全体の2%未満で、7B→70BのCPUオフロード条件でも同様に小さい。

評価ではLlama2-7B/13B/70B、C4・OpenWebText・CNN/DailyMailを使う。特に7Bドラフト→70B対象モデルのCPUオフロード条件では対象モデル1ステップが非常に高価で、C4・温度0で自己回帰復号5.5965秒/トークンに対しDySpecは0.53696秒/トークン、平均受理長9.10を報告する。対象モデルが圧倒的に重いほど、候補木の質を上げて対象モデル呼出し回数を減らす価値が大きくなる。

## 背景: 投機木では「候補数」より候補予算の使い方が重要

通常の投機的復号は、ドラフトした系列が対象モデルと一致する間だけ先へ進める。木型の投機では同じ位置に複数候補を持てるため、1位候補を外しても別枝が一致すれば検証を継続できる。しかし対象モデルに一括入力できる候補ノード数には計算量・メモリ上の上限があり、どの枝へノードを割り当てるかが受理長を決める。

SpecInferのような固定木では、全入力に同じ木形状を使う。ところが低温度では確率が少数トークンへ集中しやすく、深い一本道寄りの木が有利になり、高温度では確率質量が分散して横方向の分岐へ多く割く方が有利になる。DySpecはこの違いを実行時のドラフト確率から直接読み取り、木を作り替える。

## 問題設定

目標は、対象モデルが一度に検証する候補数 (N) を固定したまま、期待受理長を最大化する木を低オーバーヘッドで作ることである。真の対象モデル受理確率を木構築前に知ることはできないため、利用可能な信号はドラフトモデルの確率である。

もう一つの問題は、理想的な貪欲展開だけを実装すると、1ノード展開するたびにドラフトモデルの次トークン分布が必要になり、木構築時間が増えることである。対象モデルが比較的小さい条件では、このドラフト側オーバーヘッドが高速化を相殺する可能性がある。

## 手法

### 1. ドラフト確率を受理率の代理にする

DySpecは、ドラフト確率と対象モデルの受理確率に強い正の相関があるという観測から出発する。各候補接頭辞の価値を、その接頭辞へ到達する確率と次候補確率から評価し、対象モデルを実際に走らせずに「このノードへ候補予算を使う価値」を近似する。

この代理が有効なら、高確率候補を優先して木に入れるほど対象モデルが一致する枝を見つけやすくなり、同じ候補数でも平均受理長を伸ばせる。逆にドラフトモデルと対象モデルの分布がずれると、この優先度は悪化する。

### 2. ヒープで子・兄弟を動的に展開する

現在最も価値が高い未展開候補を最大ヒープから取り出し、木へ追加する。ノードを展開すると、受理された場合に続く「子」と、その位置で現在候補が拒否された場合に試す「兄弟」を新たな候補としてヒープへ入れる。これを候補予算 (N) に達するまで繰り返す。

その結果、確率が尖った入力では深い枝へ、確率が平坦な入力では複数枝へ自然にノードが配られる。固定木のように温度ごとに形を手動調整する必要がない。

### 3. 閾値付き層単位生成で木構築費を抑える

逐次的な貪欲展開は最大 (N) 回のドラフト前向き計算を要求し得る。DySpecは確率閾値 (C) を設け、十分高確率な候補を同じ深さでまとめて展開することで、ドラフト計算を木の深さ (D) に近づける。論文では (C) を概ね (1/n) 程度に設定し、候補数64の木は深さ10未満、候補数768でも深さ30未満に収まる例を示す。

木構築アルゴリズム自体は (O(Nlog N)) で、C++実装の管理費は68M→7B/13B条件で総実行時間の2%未満と報告される。

### 4. 対象モデルによる一括検証

構築した木は対象モデルへ一括入力し、木注意を使って各候補を正しい祖先文脈の下で評価する。対象モデルの確率に基づく通常の受理判定を行うため、DySpecの木選択は速度に影響するが、対象モデルが定める最終生成分布を置き換えない。

1回の検証で長い接頭辞が受理されれば、その分だけ高価な対象モデルの逐次ステップをまとめて消せる。したがって7Bドラフト→70B対象のように対象モデル1回が非常に重い条件では、木構築とドラフト追加計算の相対費用が小さくなる。

## 評価

### 代表的な評価条件

| 項目 | 条件 |
| --- | --- |
| ドラフト→対象モデル | Llama-68M→Llama2-7B、Llama-68M→Llama2-13B、Llama2-7B→Llama2-70B |
| データ | C4、OpenWebText、CNN/DailyMail |
| 生成条件 | 先頭128トークンを入力し、128トークン生成 |
| 温度 | 対象モデル温度を複数条件で評価、ドラフト温度は0.6 |
| 主な候補予算 | 7B/13B評価では64ノードを代表条件として使用 |
| ハードウェア | NVIDIA A100 40GB 1基、CPU 32コア |
| 70B条件 | 対象モデル重みをCPUへオフロードし、重みロードを計算へ重畳 |
| 比較 | 自己回帰復号、SpecInfer、Sequoia |
| 指標 | 秒/トークン、平均受理長、木構築など非モデル処理の割合 |

### 代表的な評価結果

| 条件 | 自己回帰 / 既存方式 | DySpec | 読み取れること |
| --- | --- | --- | --- |
| 68M→7B, C4, 温度0 | 自己回帰0.02303秒/トークン、Sequoia 0.00871 | 0.00730秒/トークン、受理長5.25 | 小型対象モデルでも動的木の受理長増加が実時間へ反映 |
| 68M→13B, C4, 温度0 | 自己回帰0.03033、Sequoia 0.01141 | 0.00969秒/トークン、受理長4.98 | 対象モデルが大きくなるほど検証回数削減の価値が上がる |
| 7B→70B, C4, 温度0 | 自己回帰5.59650、Sequoia 0.88920 | 0.53696秒/トークン、受理長9.10 | CPUオフロードで対象モデルが極端に高価な条件では大幅な短縮 |
| 7B→70B, C4, 温度0.6 | 自己回帰5.34781 | 0.78912秒/トークン、受理長6.21 | 高温度で分布が広がると受理長は低下するが利得は残る |
| 木構築管理費 | — | 主要7B/13B条件で総時間の2%未満 | 動的木そのものが新しい律速になりにくい |

論文が強調する最大値は、低温度のLlama2-70B条件で処理量最大9.1倍、遅延最大9.4倍級の改善である。ただしこの条件は70B重みをCPUから読み込む対象モデル側が極端に高価であり、通常の全GPU常駐条件へ倍率をそのまま適用できない。温度を上げると候補確率が分散し、受理長と高速化率が下がる傾向も評価に現れる。

## 既存研究との差

SpecInferなどの固定木は、事前に決めた幅・深さへ候補を均等に近く割り当てる。Sequoiaは木構造最適化を行うが、DySpecは実行時に得られるドラフト確率を使って入力ごとに木を作る点が中心的な違いである。

そのためDySpecは「固定予算の最適配置」を狙い、ドラフトモデルや対象モデルそのものを変更しない。ドラフト分布が対象受理率のよい代理であるほど有利で、両者の分布差が大きい条件では固定木に対する優位が縮む可能性がある。

## 限界・実装状況

動的木の品質はドラフト確率と対象モデル受理率の相関に依存する。高温度では確率質量が広がり、同じ候補数で対象モデルが受理する枝を覆いにくくなる。また、候補予算を増やせば受理長は伸びても検証計算と木構築費が増える。

70Bの代表的な大幅改善はCPUオフロードで対象モデル1ステップが非常に高価な実験であるため、GPUメモリへ70Bを常駐できる構成とは律速が異なる。公式コードURLは今回確認した一次資料範囲では確定できなかった。
