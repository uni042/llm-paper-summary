# Approximate Speculative Decoding：低regret例外とgreedy suffix再利用による投機的復号

## 概要

標準的なgreedy投機的復号では、小さなdraftモデルが候補トークン列を作り、大きなtargetモデルが1回のforward passでそれらを検証する。draftとtargetのgreedy tokenが一致する限り連続して受理するが、最初の不一致が生じた時点で後続候補を捨てる。targetの上位2候補のlogit差が極めて小さい場合でも、強い不一致と同じように打ち切るため、検証済みの後続計算が無駄になる。

Approximate Speculative Decoding（ASD）はこの制約を緩める。targetがdraft tokenよりgreedy tokenをどの程度好むかをlogit差（local regret）で測り、小さい不一致を要求単位の予算内で例外受理する。重要なのは、その例外を受理した後のdraft suffixが、**例外を含む実際のprefixの下でtargetのgreedy tokenと一致する**なら、そのsuffixを新たなtarget passなしに再利用できる点である。例外はあくまで近似だが、後続の一致部分は実際のprefixに対してgreedyである。

Qwen3-14BとDSpark-14Bの7タスクでは、同じ厳密SD検証器に対し固定出力長のtokens/sが平均7.78%改善した。DSpark、EAGLE3、Medusaを横断した10条件では3.05〜15.26%の改善を報告する。ただし**ASDは出力列やtarget分布を保存しない**。HumanEvalで−0.61ポイント、MT-Benchで−0.64ポイント、他の設定では最大−1.52ポイントの正答率・評価値低下があり、速度と品質の交換条件が存在する。

## 問題設定と従来法との差

標準greedy検証では、draft列x_1,…,x_Kに対し、targetが各位置のdraft prefixに条件付けたlogitを並列計算する。最初の不一致位置までの一致prefixを確定し、不一致位置ではtargetのgreedy tokenを1つ回復する。これによりtarget単独greedyと完全に同じ生成列が得られる。一方、targetはすでに不一致位置以降のdraft prefixに条件付けたlogitも計算している。もし不一致draft tokenを受け入れるなら、その後のtarget logitは**その不一致を含む履歴**に対応しているため、後続の一致トークンを無駄にせず確定できる可能性がある。

従来の緩和型投機的復号には、意味類似度や確率差に基づく閾値、局所的な受理率向上などがある。ASDの違いは、(1)位置ごとのtarget logit regret、(2)1ブロック内の例外数、(3)要求全体に持続する累積regretを同時に制限し、(4)その条件下で最長の連続prefixを選ぶことにある。新しいdraftモデルの学習は不要で、既存target検証passのlogitを再利用する。したがってEAGLE3やMedusaなど異なるdraft方式にも後付けできる。

## 手法

### target logit regretと許容条件

履歴h_0とdraft列x_1:Kに対し、targetのteacher-forced検証で位置iのlogit z_iを得る。targetのgreedy tokenをy_i*=argmax_v z_i(v)とし、draft tokenとの不一致の大きさを

\[
r_i=z_i(y_i^*)-z_i(x_i)\geq0
\]

と定義する。softmaxの正規化定数は差を取ると消えるため、r_iは条件付き対数確率の差でもある。greedy tokenと一致する位置ではr_i=0であり、通常の厳密受理ができる。不一致位置では局所閾値gに対してr_iが小さく、さらにブロック例外数Mと要求全体の累積regret予算Bの範囲内であれば例外受理する。

Bは各要求で持続する台帳として保持し、ある検証ブロックで例外を使った後も残りの生成に影響する。gだけを使う局所閾値方式と異なり、同じ要求で小さな例外を無制限に積み重ねることを防ぐ。Mは1ブロック内に例外が集中することを防ぐ。B=0では厳密なtoken ID一致検証へ切り替え、同値のlogitが複数ある場合も通常のgreedy挙動を保つ。

### 最長prefixとsuffix再利用

各位置iで「greedy一致」または「regret、B残量、Mの全条件を満たす例外」を許容する真偽値f_iを計算し、f_1から連続して真になる最長prefixを採用する。採用prefix内の例外の後にgreedy一致が続けば、そのsuffixは実際に採用したprefixに条件付けたtarget passで検証済みである。追加の近似判定やtarget forwardは不要になる。

採用長がKより短ければ次のtarget logitから回復tokenを1つ追加し、K全体を採用できればbonus tokenを追加する。採用した列に合わせてtarget KV、draft KV、累積regret台帳を同期させ、採用しなかったproposal suffixのKVを破棄する。キャッシュの更新を誤ると、次のtarget検証の履歴が実際の出力とずれ、結果の正当性が失われるため、実装上の重要な注意点である。

検証後に追加する処理はdraft長Kに比例するO(K)のマスク・累積演算で、追加のtarget forwardは発生しない。targetの各位置のgreedy token、最大logit、draft tokenに割り当てられたlogitがあれば足りるため、テンソル並列実装で巨大な追加K×語彙サイズのlogitバッファを必ずしも生成する必要はない。

### 厳密性の境界

ASDが保証するのは、許容した例外のlocal regretと累積予算の上限である。greedy一致したsuffixが正しいのは、**例外を受け入れた履歴に対して**であり、元のtarget単独greedy列と同一であることを意味しない。近似例外の後では、その後の生成分岐が大きく変わる可能性がある。累積logit regretの上限は、最終回答の意味的一致、事実正確性、コード実行成功率、安全性を保証するものではない。

著者は数学問題で異なる途中式が同じ答えになる例を示すが、これは出力の同値性の証明ではなく、タスク単位の評価が必要な動機である。ASDを厳密なtarget分布保存型のspeculative samplingと混同してはならない。

## 評価条件

| 項目 | 原著の条件 |
|---|---|
| target/drafter | Qwen3-14B/8B＋DSpark、Llama-3.1-8B/Qwen2.5-7B＋EAGLE3、Llama-3.1-8B＋Medusa |
| GPU・実行環境 | NVIDIA L20（約46GB）、Linux5.4、Python3.12.13、PyTorch2.8.0+cu128、Transformers4.55.2、vLLM0.11.0 |
| タスク | GSM8K、MATH-500、HumanEval、MBPP、MMLU、MT-Bench、Alpaca |
| 主設定 | 要求regret予算B=8、局所閾値g=0.25、ブロック例外上限M=2 |
| 主な速度測定 | 固定workload（64要求×256生成トークン）でtokens/s、厳密SDとASDを同じtarget/draftで比較 |
| 品質監査 | 自然EOS、正答率・評価スコア、生成長、出力hash差分を別測定 |
| 繰返し | 原則4回、strict–ASD–strictの順で比較、ベースラインのドリフト3%以内を採用 |
| 大型モデル補足 | DeepSeek-V4-Flash＋DSpark、H20×8、FP4→FP8互換経路、acceptance・品質のみ |

ハイパーパラメータの選択にはGSM8Kの独立した固定workloadと自然EOSのスライスを使い、他タスクの測定前に固定した。固定workloadで速度を測ると、出力長の差が速度に混入しない。自然EOSで正答率と出力hashの差を測ると、ASDによる軌跡変更を隠さずに評価できる。これら2種類の評価は目的が異なるため、固定workloadのTPSを自然EOSのエンドツーエンド完了時間と混同しない。

原著表1の数値。7タスクのTPS改善平均は7.78%、平均受理長は3.85から4.20へ増えた。最大改善はMATH-500の11.73%、最小はMBPPの3.64%。全タスクで速度改善するが、HumanEvalとMT-Benchでは品質指標が低下している。品質差の単位や指標はタスクごとに異なるため、異種タスクの品質差を単純平均して「平均正答率改善」としてはならない。

原著表1にはtarget-only基準のspeedup（例：GSM8K厳密5.58倍、ASD6.30倍）と、別列の厳密SD比TPS改善10.08%が併記される。6.30/5.58−1≒12.9%であり、表示された10.08%とは一致しない。これは集計・測定条件や丸めの違いを含み得るが、**表の二つの列を単純に割って同一のTPS改善率として再計算することはできない**。本稿では原著の独立した報告列をそのまま区別して記載する。

### 予算・閾値・例外上限のアブレーション

原著表3ではGSM8KにおいてB=4/8/12/16を変えると固定workloadのTPS改善が4.96/6.53/6.98/6.64%となり、予算を増やすほど単調に速くなるわけではない。局所閾値g=0.125/0.25/0.5/∞では2.84/6.53/7.62/6.62%であり、閾値を緩めすぎても最大利得が得られるとは限らない。M=1/2/∞では6.20/6.53/6.70%となり、例外を無制限に増やす利得は小さい一方、品質制約を失う危険が増す。

自然EOSのGSM8K監査（n=256、1seed）では、g=0.25の設定で要求の95.3%をカバーし、TPSが7.2%改善し、測定した正答率差は0だった。これは「すべての生成結果が同じ」ことを意味しない。実際、GSM8KやMATH-500では生成hashの相違が95%を超えており、回答が同じでも推論経路が大幅に変わることを示す。

### 検証器オーバーヘッドと大型モデルへの転用

同期プロファイルではASDの検証器ロジックがAlpacaで0.083ms/出力トークン、GSM8Kで0.045ms/トークン増える一方、target検証時間はそれぞれ1.479ms、1.509ms/トークン減少した。速度改善は検証器の追加処理が無料だからではなく、target passあたりの確定トークン数が増えることによる。

DeepSeek-V4-Flash（原著の表記に284B/285Bの揺れがある）とDSparkをH20×8で使う実験では、FP4のdraftをFP8対応GPU上で動かすため追加Q/DQ変換が必要になる。著者はこの環境でGSM8K/MATH-500の受理トークン数が約10〜16%増えると報告するが、**FP4→FP8互換経路のオーバーヘッドがあるためエンドツーエンドのTPS高速化の証拠としては使っていない**。別モデルのacceptance改善をL20上の速度比へ外挿できない。

## 限界と運用上の注意

ASDは低regretの例外を受け入れることでgreedy列から分岐する。局所logit差が小さくても、数学的推論、コード生成、ツール呼出し、医療・法務などの高リスク用途でタスク品質が維持される保証はない。要求単位の予算Bは累積logit regretを制御するだけで、意味や事実の正しさを制御するものではない。自然EOSのタスク別正答率、生成長、hash差分、長い対話の後続挙動を実運用のワークロードで検証する必要がある。

性能評価は固定workloadでのTPSが中心であり、ネットワーク、バッチ競合、複数ユーザー、KV退避を含む大規模サービングのP99レイテンシは直接測っていない。モデルとdraftの組合せが変わればlogit差の分布も変わるため、B/g/Mを再校正すべきである。厳密なtarget出力の再現が必要な用途ではB=0に設定して通常のgreedy検証へ戻すか、ASDを採用しないことが妥当である。

### 近似を許す際の実装・監査項目

実装ではtargetのargmaxを決めるtie-breakの規則と、draft tokenに対応するlogitの取得精度を固定する必要がある。異なるGPUの浮動小数点丸めで小さなlogit差の符号や閾値判定が変わると、受理prefixが変わる可能性がある。さらに、例外を受理した後にtarget側とdraft側のKVキャッシュが異なるprefixを保持していないかを検査し、未受理suffixを明示的に破棄することが不可欠である。

実験の95%信頼区間はTPS改善のばらつきを表すもので、自然EOSでの正答率が非劣性であることの統計的証明ではない。HumanEval、MBPP、MATH-500のような異なる採点法の結果を一つの「正答率改善」として平均することもできない。品質面の運用判断には、タスク別の失敗事例、誤答の深刻度、出力長変化、seed間のばらつき、異なる入力分布での再評価が必要である。

なお、原著の大型モデル実験で受理率が上がった事実と、別GPU上での実測tokens/sの改善を一つの速度比として結合することはできない。FP4/FP8変換の費用、モデルの並列化、draft生成の費用、検証passの同期を含む独立した計測が必要である。
