# SP-MoE: Speculative Decoding and Prefetching for Accelerating MoE-based Model Inference

> speculative decodingでdraft tokenを作っている間に、target MoEが検証時に使いそうなexpert重みをCPUからGPUへ先読みし、verification開始後のweight待ちを減らす手法。

## 概要
SP-MoEは、speculative decodingのdraft処理を単にtokenを先に生成するためだけでなく、**target modelが将来使うexpertを早く知るための時間として利用する**。

CPU offloadされたMoEでは、target routerがexpertを確定してからweight転送を始めると、その転送待ちがそのまま生成時間へ加わる。SP-MoEはdraft生成中にtarget側のexpert候補を推定し、その間にCPU→GPU転送を始める。

ただしdraft tokenが増えるほど候補expertもばらけやすくなり、すでにGPUに置かれているexpertを頻繁に追い出したり、不要なPCIe転送を増やしたりする危険がある。そこで `cutoff layer`、段階的prefetch、転送の優先度制御を入れ、**どこまで先読みするか**まで最適化する。

品質面は通常のspeculative decodingと同じくtarget modelが最終verificationを行うため、prefetch予測ミスは基本的に速度へだけ影響する。

## 手法のあらまし

### 1. Draftの中間表現をtarget gateへ通す

draft modelの各層で得たattention出力を取り出し、target model側のgating networkへ入力する。

これにより、targetを本当にその層まで実行する前に「このtokenはどのexpertへ行きそうか」を推定する。

別の専用predictorを学習するのではなく、**draft modelの中間表現＋target gateを組み合わせてroutingを先読みする**点が特徴である。

### 2. `Expert Lookahead Buffer`：予測したexpertを先読み予定表として保持する

予測したexpert IDと確信度を、token×layer単位で `Expert Lookahead Buffer` に保存する。

runtimeはこの表を見ながら、verificationで近いうちに必要になりそうなexpertからprefetchする。

### 3. `Cutoff Layer`：深く先読みしすぎない

全layer分を一気にprefetchすると、将来使わないexpertまでGPUへ入り、必要なexpertをGPUから追い出したりPCIe転送を圧迫したりする。

SP-MoEでは、各転送にかかる時間と現在の計算時間を見積もり、prefetchを行う深さにcutoffを設ける。

つまり「予測できるだけ先まで読む」のではなく、**今の帯域とcache容量で得になる範囲だけ読む**。

### 4. 3段階のprefetch

転送は大きく3段階に分かれる。

- Phase I：最も必要になる可能性が高いexpertを早く送る
- Phase II：空いている帯域で追加候補を送る
- Phase III：verification直前に残りの高確率候補を送る

これにより、今すぐ必要な正しいexpertの転送と、まだ必要か確定していない先読み転送が同じPCIe帯域を奪い合うのを抑える。

### 5. `Reordered Inference`：準備できたexpertから先に計算する

verificationではexpertを元の順番通り待つのではなく、

1. すでにGPUにあるexpert
2. 転送中のexpert
3. まだ転送を始めていないexpert

の順に計算する。

GPUにあるexpertを計算している間に転送中expertを到着させ、I/O待ちを隠す。

### 6. Draft lengthは長いほど良いわけではない

speculationを長くするとprefetchに使える時間は増えるが、同時に候補expert集合も広がる。

SP-MoEでは、**draftを長くして先読み時間を増やす利点と、触るexpertがばらけて無駄な転送が増える欠点の両方**を考える必要がある。

## 評価

### まず見るところ
- **結論:** speculative draftをexpert先読みへ再利用すると、CPU offloadのweight I/Oをverification前へ移せる。
- **実速度:** RTX 3090/4090/A100で実測し、modelによって1.1〜3.5倍程度。
- **品質:** target verificationを維持するため**lossless**。
- **注意点:** draftを長くしすぎると、使うexpertが広がってGPU上のexpert入れ替えと不要転送が増える。

### 最大値

DeepSeek-Lite + HumanEval + A100では、Mixtral-Offloading系baselineに対して最大約3.5×を報告する。

### Cutoffの意味

prefetch depthを増やすと初めはhit率が上がるが、5層超など深くしすぎるとGPU上の既存expertを追い出す回数とPCIe競合が増え、性能が逆に落ちる条件がある。

### 制約

- batch 1中心。
- 1本のdraft列を使う基本的なspeculative decoding中心。
- 複数候補を木状に広げるspeculationや大規模continuous batchingは未評価。
- predictor missは品質ではなく余分なI/Oとして現れる。
- draft tokenがtargetに受理される率と、同じexpertを繰り返し使える度合いの両方に依存する。
