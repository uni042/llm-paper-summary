## 概要
本研究は、単体では70B級LLMを保持できないIntel AI PC群を、通常のLAN/WAN越しにlayer pipelineとして束ねる分散推論systemである。Hugging Face checkpointをcontiguous layer rangeへ分割し、各stageをINT4 OpenVINO IRとして事前compileする。オンラインでは各PCが自分のstageとstateful KV cacheだけを保持し、hidden stateを隣stageへTCP転送する。

単純なpipeline化だけでは、per-stage graphでOpenVINO GPU pluginのKV最適化が発火せずmonolithic modelより13〜23%遅くなる。またautoregressive decodeでは毎tokenでnetwork round-tripが発生する。論文はこれを、(1) graphへ `beam_idx` Gatherを注入してIndirectKVCache fusionを復活、(2) speculative decoding（投機的復号）のrejected KVを物理削除せずattention maskで無効化、(3) independent InferRequestを使ったmulti-user micro-batching、の三機構で埋める。

## 問題設定
Intel Lunar Lake/Panther Lake系AI PCは32GB級unified memoryとcapable iGPUを持つが、70B INT4 modelを一台へ載せるには不足する。layer pipelineなら各deviceはmodelの一部だけを保持すればよく、tensor parallelismのようなlayer内all-reduceも不要で、隣stageへactivationだけを流せる。

一方autoregressive inferenceはtraining pipelineと違い、1 tokenが前tokenへ逐次依存するためsingle streamでは各stageが順番待ちになりやすい。さらにstage数だけnetwork hopが増え、Wi-FiやWANではround-trip latencyがtoken latencyへ直結する。modelを分割したことでcompiler optimizationまで失えば、memory capacityは増えても性能が実用域へ届かない。

## 手法
### 1. per-stage export
各stageは連続するdecoder layerだけをsafetensorsから選択loadする。Hugging FaceのDynamicCacheとRotaryEmbeddingはそのままでは `torch.export` / ONNX tracingが難しいため、attentionをexplicit K/V tensor入力へ書き換え、RoPEのcos/sinを外部事前計算する。そのうえでreal tensorを使った `torch.jit.trace` からOpenVINO IRへ変換し、ReadValue/AssignによりKVをstateful化する。

weightはNNCFでsymmetric INT4、group size 128へ圧縮する。first shardはembedding、last shardはLM headも持つ。manual attention rewriteはHugging Face native forwardに対して最大差5×10^-7以内を確認している。

### 2. IndirectKVCache fusionの復活
naive shardはmonolithic `openvino_genai.LLMPipeline` より遅かった。原因は、OpenVINO GPU pluginがbeam search等で使う `beam_idx` に対応したGatherをgraph中に見つけると発火するIndirectKVCache transformationが、custom shard exportには存在しないことだった。

そこでexport後のgraphへ `beam_idx` Parameterと `Gather(ReadValue, beam_idx, axis=0)` を注入する。実際にbeam searchを使わなくても、このgraph patternによりpluginがKV reorder/cache pathを融合する。これでshardはmonolithic throughputの4%以内まで回復し、未注入版の13〜23% penaltyを除く。この機構は全後段最適化の土台である。

### 3. mask-based KV rewind
speculative decodingでは小さいdraft modelがK tokensを提案し、targetがK+1位置を一度に検証する。rejectされたdraft tokenは本来targetのKV cacheから消す必要があるが、OpenVINO stateful graphにはPagedAttentionのようなcheap rewind APIがない。

`query_state()/set_state()` でK/V tensorを物理sliceして書き戻すと、Arc B390 iGPU・72-token cacheで1回約46.6〜49.9msかかる。K=3のtarget verify自体が約47msなので、物理trimだけでspeculationの利益が消える。

提案はreject位置をcacheから削除せず、その後の全forwardで `attention_mask[j]=0` にする。RoPEの `position_ids` はphysical cache lengthではなくlogical sequence lengthを追う。するとrejected K/Vはmemoryには残るがattentionへ寄与せず、physical trimとbit-identicalな出力をほぼzero-costで得られる。cache bloatはreject分だけ増えるが、長いgenerationではlive token数が線形増加するため比率は1へ近づく。

### 4. pipeline micro-batching
各OpenVINO InferRequestは独立したReadValue/Assign state、すなわち独立KV cacheを持つ。stageごとに複数InferRequestを用意し、request Aがstage 1を走っている間にrequest Bをstage 0へ入れる。training micro-batchと同様にpipeline bubbleを別user streamで埋めるが、token orderとcache stateはstreamごとに分離する。

この方式のaggregate throughput上限は概ね `min(N_users,N_stages)` で、single-user latencyを下げる機構ではない。per-stream `compile_model` はmemoryを使い、Lunar Lake 16GB共有budgetでは1 streamあたり約6GBという制約も報告する。

### 5. network relay
隣stage間はpersistent TCP connectionを使い、20-byte headerとraw tensorを送る。Llama 8B decodeのhidden stateは `[1,1,4096]` FP32で約16KB/hop。TCP_NODELAYを有効にしてNagle delayを避ける。LANではpayload転送bandwidthよりsocket/OS round-trip latencyが支配的なので、FP16へ半減しても速くならない。

final LM headからcoordinatorへ戻すfull logitsはvocab 128,256なら約501KBあり、WANではmulti-segment TCP costが大きい。greedy/spec accept判定にargmaxとtop probabilityだけが必要な条件ではtop-1 token id+probability（約8 bytes）だけ返し、bit-exact correctnessを保つ追加最適化も行う。

## 評価条件
主testbedは3台のWindows 11 AI PC。ASUS Zenbook S 14×2はCore Ultra 7 258V (Lunar Lake) + Arc 140V + 32GB LPDDR5X、HP OmniBook X 16はCore Ultra X7 358H (Panther Lake) + Arc B390 + 32GB DDR5。OpenVINO 2026.1.0、Python 3.11、802.11ax Wi-Fiで、16KB raw TCP RTTは約6.5ms。

代表modelはLlama 3.1 8B INT4。monolithic baseline、2-stage/3-stage shard、speculation K sweep、2/3 concurrent streams、simulated WAN latencyを比較する。さらにIntel Tiber Cloudの4-node Lunar Lake構成でLlama 3.1 70B INT4を評価し、単一deviceへ収まらないmodelへのcapacity scalingを確認する。

## 主要結果
### shard自体の復元
beam_idx Gatherを入れたv5_beam shardはmonolithicの4%以内へ戻る。spec decodeはsingle-nodeで8 prompt平均22.66→29.98 tok/s、1.33倍。prompt種別で1.11〜1.50倍の幅があり、常に同倍率ではない。3-stage shardでも21.56→28.38 tok/sで1.32倍となり、shardingとspeculationがcleanly composeする。

長いgenerationではdraft acceptanceが上がり、128 tokensで1.33倍・70.7% acceptance、512で1.56倍・90.6%、1024で1.57倍・95.1%、2048で1.58倍・97.5%。2048ではmasked rejectによるphysical cache bloat ratioは1.02倍まで低下する。

### 2-node full stack
2-stage single streamは16.33 tok/sで、同hardwareのmonolithic single-node 24.54 tok/sより遅い。ここへ2-stream micro-batchingを入れると29.34 tok/s（distributed baseline比1.80倍）、さらにmask-based spec decode K=3を重ねると43.97 tok/sとなる。これはmonolithic **single-user** baselineの1.79倍だが、2 usersのaggregate値であり、1 userのlatencyが1.79倍改善したわけではない。

61ms/tokenのbreakdownはstage 0 compute 20ms、stage 1 compute 22ms、TCP RTT 6ms、Python/OpenVINO dispatch+mask construction 13ms。networkは約10%で、LANではcomputeとruntime overheadの方が大きい。

### WAN感度
2-stage、2-stream、K=3でone-way hop latencyを0/10/50/100msへ増やすとfull-stack aggregateは41.01/37.35/18.25/11.20 tok/s。naive single-stream distributedは14.51/9.89/4.72/2.77で、relative gainは2.83倍から4.04倍へ広がる。100ms/hopでもfull stackはper-stream 5.6 tok/sで論文のinteractive floor 5 tok/sを上回る。

3-stageでは2-stream K=5が50.55 tok/s、3-streamが64.67 tok/s。3 streamsはaggregateを14.1 tok/s増やす一方、per-user throughputは約21.6 tok/sへ下がる。WAN 100ms/hopでは大きいK=10が有利になり、2-stream 14.97 tok/sを得る。

### compressionの正負結果
inter-stage activationをFP32 16KBからFP16 8KBへしても13.57→12.71 tok/sと改善せず、INT8 4KBは15.10 tok/sだがgenerationを破壊した。LANではbandwidthではなくRTTが律速であるため、activation compressionは有効でないという負の結果である。

一方final logitsのtop-1圧縮は、3-stage LANで42.42→47.38 tok/s（1.12倍）、Tiber Cloud DERP relayでは2.80→22.88 tok/s（8.17倍）。501KB logitsのmulti-segment network costだけはWANで大きく、ここは圧縮対象を選ぶ価値がある。

### 70B
4-stage Llama 3.1 70B INT4はtarget-only 1.74 tok/s。speculation K=3/5/10/15で3.86/4.78/5.42/4.76 tok/sとなり、K=10がsingle-stream peakで3.1倍。2-streamはaggregate最大6.43 tok/sだがper-stream 3.21 tok/sで5 tok/s interactive floorを下回る。

1024-token generationではK=10で5.72 tok/s・72.2% acceptanceと128-token時より良いが、4096 tokensでは5.00 tok/s・66.3%へ下がり、KV cache pressureが支配し始める。つまりspeculationの長文利得は無制限には続かない。

## 既存研究との差
Petals、Parallax等のdecentralized inferenceはNVIDIA系hardwareやDHT/Internet routingを対象とする。本研究はIntel consumer iGPU + OpenVINOへ特化し、runtimeでmodelを分割するのでなく各stageを事前compileしてcompiler fusionまで維持する。speculative decodingでもPagedAttention/rewind APIを前提とせず、stateful KV cacheの「rejectを削除せずmaskする」というOpenVINO向け実装を示す。

## 限界
性能はOpenVINOのIndirectKVCache transformationとIntel GPU pluginの挙動へ強く依存し、他vendor/runtimeへ同じgraph surgeryがそのまま適用できるとは限らない。Intel AI PC fleetも全世代で安定したわけではなく、paper中では一部Arrow Lake-S Xe-LPG instanceが70B stageでdriver/iGPU memory-pressure由来とみられるfailureを起こし、Lunar Lake-class Arc 140V以上をend-to-endで必要とするとしている。

single streamのdistributed pipelineはmonolithicより遅く、利得の中心は「単体に収まらないmodelを動かすcapacity」と「複数userでbubbleを埋めるaggregate throughput」である。WAN評価もsleep injection、proxy、DERP relayで結果が大きく異なり、実networkのjitter/congestionを一つの数値へ一般化できない。

mask-based rewindはbit-exactだがrejected K/Vをphysical cacheから回収しないため、長期sessionでは余分なmemoryを使う。70B 4096-tokenでは実際にKV pressureでthroughputが落ちる。activation INT8 compressionがqualityを壊す、FP16 compressionがLANで無効、4-stage 70B multi-userはper-stream interactive thresholdを下回るなど、負の条件も存在する。
