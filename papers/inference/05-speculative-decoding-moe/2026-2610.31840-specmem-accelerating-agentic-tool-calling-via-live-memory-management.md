# SpecMem: Accelerating Agentic Tool Calling via Live Memory Management

> 投機的デコードのドラフト源である過去のツール呼び出しストアを、検証済み呼び出しのオンライン書き戻しと利用者ごとの有界なLRU管理で生かし続け、凍結ストアで劣化する受理率を維持して実時間で最大1.74倍高速化し、不可逆な呼び出しの投機実行は検証まで遅らせる方式。

## 概要

ツール呼び出しを行うエージェントは正確さの面では最適化が進んできたが、実運用で増えていくコストは遅延である。すべてのツール呼び出しは自己回帰的にデコードされるため、呼び出しのたびに生成コストがかかる。投機的デコードは、安いドラフトを対象モデルに検証させることで出力を変えずに高速化する手法であり、実運用では利用者の行動が繰り返される傾向があるため、過去の呼び出しは強いドラフトになる。しかし既存のシステムはセッションをまたぐメモリを持たないか、ドラフトストアを一度構築した後は決して更新しない。

本論文のSpecMemは、ドラフトストアを静的な索引ではなく管理されるライフサイクルとして扱う。検証が済んだ呼び出しは発行した利用者のストアへその場で書き戻され、ストアは容量で有界化されて最近使われていないものから追い出される。さらに、送金やテーブル削除のような不可逆な副作用のあるツールについては、ドラフトと検証は投機的に行っても実行だけは検証確定まで遅らせるゲートを設ける。

代表結果として、複数セッション・複数利用者のクエリストリーム上で、凍結ストアの平均受理トークン数（MAT）がセッションを追うごとに劣化する一方でSpecMemは水準を維持し、ウォームアップ後のMATで27パーセントの差がついた。実時間のデコード高速化は通常の自己回帰デコード比で最大1.74倍である。

## 問題設定

投機的デコードの高速化率は、ドラフトが対象モデルの出力とどれだけ長く一致するか、つまり受理されるトークン数で決まる。ツール呼び出しでは、同じ利用者が同じツールを構造は同じで数値引数だけ変えて繰り返し呼ぶことが多いため、過去の検証済み呼び出しを検索してドラフトにする方式が成立する。先行方式のToolSpecはこの検索ストアを使うが、評価用のストアはウォームアップ時に構築されて凍結される。

凍結が問題になるのは、実運用ではウォームアップ後も新しい仕事が到着し続けるからである。新規タスクはストアに存在せず、既存タスクも再発行のたびに数値引数が攪拌されるため、凍結ストアが差し出すドラフトは次第に対象の現在の出力からずれていく。公開ベンチマークは単発タスクの集合で利用者も時間も概念がないため、この劣化は単一セッションの評価では見えない。本論文はまずベンチマークを複数利用者・複数セッションのストリームへ拡張し、そのうえでストアの鮮度という変数を分離して測る。

もう一つの問題は安全性である。ツールの遅延を隠すためにドラフトを検証完了前に実行する投機実行は、読み取り専用ツールなら誤っても作業の無駄で済むが、送金や削除のような外部へ可視な不可逆の副作用を持つツールでは、検証で棄却されても効果が確定してしまう。冪等かどうかは判定基準にならない。ファイルを二度消しても状態は同じだが、誤った削除は損失である。本論文は、投機してよいかを検索の信頼度ではなく、ツールの宣言された副作用で決めるべきだと位置づける。

## 手法のあらまし

SpecMemは利用者ごとに、クエリの埋め込みと正規化された呼び出しの組を保持するストアを持つ。新規クエリが来ると、その埋め込みと最も近い自利用者のエントリを検索し、類似度がしきい値0.35を超えれば保存済み呼び出しをドラフトとして返して最近使用したものへ昇格させる。ストアが空か類似度が不足する場合は、集団の履歴で種付けした小さな共有ストアへ、それも無ければツール名と引数のプレースホルダだけからなるスキーマのみの骨格へ段階的に戻る。対象モデルによる検証が済んだ呼び出しは、ドラフトの受理率にかかわらず発行利用者のストアへ書き戻される。ストアは利用者あたり容量48件で有界化され、あふれた場合は最も長く使われていないエントリが追い出される。副作用のあるツールについては、スキーマに宣言された投機可否フラグを見て、不可逆なものだけ実行を検証後へ遅らせる。

## 手法

### 1. 検索ベースのドラフト生成 — 過去の自分の呼び出しを下書きにする

各利用者のストアは、利用者識別子をキーとする順序付きマップで、過去のクエリ埋め込みと正規化された呼び出しの組を保持する。ドラフト生成時には到来クエリを埋め込み、コサイン類似度が最も高い自利用者のエントリを探す。類似度がしきい値0.35を超えれば、その保存済み呼び出しがドラフトとなり、エントリは最近使用したものとして昇格する。呼び出しはキーを並べ替えて正規化されてから比較されるため、受理の判定は通信形式の揺れではなく意味的な一致を反映する。コールドスタート時は、集団履歴で種付けした共有ストア、最後にスキーマのみの骨格という順に後退する。骨格は正しい呼び出しが必ず共有する接頭辞しか含まないため弱いが、履歴が無い条件での下限として機能する。この機構が減らすのは対象モデルの逐次デコードであり、ドラフトが外れても検証で棄却されるだけで出力は変わらない。

### 2. オンライン書き戻しと有界エビクション — ストアを生かし続ける

検証済み呼び出しは、ドラフトがどれだけ受理されたかに関係なく、その都度発行利用者のストアへクエリ埋め込みをキーとして挿入される。対象モデルの出力はドラフトの成否にかかわらず完全な形で得られるため、確認済み呼び出しはその利用者の現在の行動についての最も新しい証拠になる。各利用者のストアは容量で有界であり、本格実行では48件、あふれた場合は最も長く使われていないエントリが追い出される。頻度ベースの追い出しも差し替え可能な代替として示されている。追加で消費する資源は検索と書き戻しの処理であり、実測では1クエリあたり約9.4ミリ秒から9.5ミリ秒が計時ループ内に含まれても実時間の高速化を相殺しなかった。容量を無制限にした条件との差は0.04から0.05 MAT程度で、容量がおおよそ32件を下回ると受理が目に見えて劣化した。

### 3. 副作用ゲート — 実行だけを検証の後ろへ置く

投機実行の可否は、各ツールのスキーマに宣言される投機可否フラグで決める。読み取り専用、副作用なし、効果がトランザクションでバッファされるか補償可能な呼び出しは投機可能とし、冪等かどうかを問わず不可逆で外部可視な副作用を持つ呼び出しは不可とする。ゲートが遅らせるのは実行だけであり、不可なツールのドラフト生成と検証は通常どおり投機的に行われるため、安全な呼び出しの高速化は影響を受けない。代償は、正しかった不可逆ドラフトについても投機実行の利益を放棄することであり、論文はその件数を数えて費用として示している。誤った場合の費用は、ツールごとに著者が割り当てた深刻度で重み付けして測る。呼び出しごとに条件が変わる場合、例えば冪等キーが与えられたときだけ安全な支払いには、呼び出し単位の三値ゲートが必要であり、二値フラグより厳密に強いことが限界として述べられている。

### 4. 評価用ストリームの構築 — 凍結の劣化を見える形にする

手法の一部として、単発ベンチマークを複数利用者・複数セッションのストリームへ変換する構築法も提案されている。タスクは模擬利用者へ重ならないよう配分され、各利用者のタスクは順序付きセッションで再発行され、再発行のたびに数値引数が攪拌されるため、繰り返しは構造的であっても逐語的ではない。セッション0が全方式共通のコールドスタートであり、各利用者のタスクの一部は後のセッションで初めて現れるため、ウォームアップ後も新規の仕事が到着し続ける。構築法はベンチマークに依存せず全方式へ同一に適用されるため、特定方式を有利にはしない。

## 評価

### まず見るところ

結論は、受理率の利得はストアの検索方法ではなく鮮度から来るということである。アブレーションでは、ストアを生かし続けることが利得のほぼ全てを説明し、利用者ごとの分割とエビクションは受理率をむしろわずかに下げた。ただし分割は利用者間の履歴混入を断つ分離のために、エビクションは増え続けるストアを有界に保つために必要であり、著者は受理率が最適でない構成を運用構成として推奨している。凍結ストアとの差は、新規の仕事がどれだけ到着するかで決まり、新規呼び出しの比率が高い領域ほど差が広がる。

## 既存研究との差

ToolSpecはスキーマ認識のドラフト生成と信頼度ゲート付き検索でツール呼び出しを高速化したが、その評価用ストアは構築後に凍結される。本論文はドラフトの作り方ではなく、ストアのライフサイクル、すなわち書き戻し、範囲、有界化と追い出しを研究対象にし、凍結という前提が長期運用で受理率をどう劣化させるかを定量化した。また投機実行の安全性について、検索の信頼度で実行可否を決める発想を実測で退け、ツールの宣言された副作用に基づくゲートへ置き換えた点も異なる。

## 限界・実装状況

- 利用者とセッションは合成ストリームであり、未加工の実運用の複数セッションテレメトリによる検証は今後の決定的な試験として残されている。実データでは繰り返しの強さが異なるため、差の大きさは変わりうる
- 副作用ゲートはツールのスキーマへの正しい注釈を前提とする。呼び出しごとに安全性が変わるケースには呼び出し単位の三値ゲートが必要で、本論文の二値フラグでは扱えない
- MATは貪欲出力に対する代理指標であり、学習済みドラフトモデルを使う実配備での受理や標本化時の受理は測定範囲が異なる
- 公式コードは本論文分としては未公開で、ハーネス等の公開は予定と記載されている。評価は単一GPU上の提供であり、大規模な同時提供での分離やプライバシーの運用面は未評価である

## 一般的な実装上の含意

キャッシュやドラフトストアのような履歴に基づく最適化は、構築時の性能ではなく、運用中に新しさをどう取り込むかで寿命が決まる。鮮度を保つ機構と、範囲の分離や有界化のような運用上の性質は分けて測るべきであり、受理率だけを見ると分離や追い出しは無駄に見えるが、分離は利用者間の情報混入を断つために必要である。また、不可逆な操作の投機実行は、予測の信頼度が高くても安全にはならない。実行可否は予測器の出力ではなく、操作そのものの宣言された性質で決めるべきである。
