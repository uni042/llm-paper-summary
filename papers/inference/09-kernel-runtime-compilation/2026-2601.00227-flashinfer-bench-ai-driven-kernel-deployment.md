# FlashInfer-Bench: Building the Virtuous Cycle for AI-driven LLM Systems

> 実LLM serving由来のGPUカーネル課題を統一トレースで検証し、エージェント生成カーネルをSGLang/vLLMへ低オーバーヘッドで動的適用する閉ループ基盤。
## 書誌情報

- **著者・所属**: University of Washington、Carnegie Mellon University、NVIDIA、UC Berkeley、Independent。

## 概要
FlashInfer-Benchは、LLMエージェントが生成したGPUカーネルを実際のLLM推論系へ継続導入する際に、演算仕様、実ワークロード、候補実装、正しさ・性能評価、本番適用が分断されている問題を扱う。FlashInfer トレースという統一スキーマでDefinition・ワークロード・Solution・Evaluationを不変レコード化し、SGLang実行から採取した実形状を含む41カーネル設定・1,600ワークロードを構築する。決定的演算、低精度演算、確率的samplingを別々の検証器で評価し、隔離実行と複数GPUスケジューラで大量候補を安全に測定する。さらにflashinfer_bench.apply()が検証済み最速カーネルをSGLang/vLLMへ動的差替えし、生成→評価→フィードバック→本番適用の閉ループを形成する。B200上のエージェント評価では正しさ上位がGPT-5 83.9%、o3 71.3%、Gemini-2.5-Pro 48.8%で、32件の誤り中30件がコンパイル失敗だった。本番差替えの呼出し費は1〜2us、E2Eオーバーヘッドは0.8%未満である。

本研究は、演算の意味、具体的な実行入力、候補実装、実測評価を一つの追跡可能な形式にまとめ、その同じ記録を生成エージェントへのフィードバック、公開比較、本番差替えのすべてで利用する点に特徴がある。実際の推論処理から採取した形状やキャッシュ配置を保存するため、単なる合成ベンチマークより本番に近い課題を扱える。正しさの確認も、通常の決定的演算だけでなく、低精度演算と確率的サンプリングを別の基準で検証する。さらに、検証を通過した候補だけから入力条件ごとの最速実装を事前に索引化し、実行時には軽量な検索だけで推論エンジンの呼出し先を差し替える。これによって、評価基盤そのものが本番用の実装登録簿として機能する。

代表結果として、leaderboard correctnessは実LLM serving由来カーネル ワークロードでFlashInfer-Bench snapshotに対してGPT-5 83.9%、o3 71.3%、Gemini-2.5-Pro 48.8% pass。frontier modelでもproduction カーネルの完全な正しさは未達で、評価・修正loopが必要。
## 問題設定
大規模言語モデルがGPU向け計算カーネルを生成できても、その成果を実際の推論基盤の性能改善へ結び付けるまでには複数の断絶がある。実運用の注意機構や専門家混合、サンプリングでは、可変な形状、ページ化されたKVキャッシュ配置、低精度データ型、確率的な出力規則などを正確に伝える必要があるが、従来の単純な演算課題ではこれらを十分表せない。また、合成した少数の形状だけで高速化しても、本番の入力長や同時実行数の分布に対して有効とは限らない。さらに、生成した実装が正しいか、速いか、安全に実行できるかを確認した後も、推論エンジンへ人手で組み込む作業が残る。このため、生成、検証、改善、配備という一連の過程が自動で循環せず、生成モデルの進歩が本番性能へ還元されにくい。

## 手法
### 手法のあらまし
まず演算定義には、入力と出力、データ型、固定次元と可変次元、形状制約、参照実装を記述する。次に具体ワークロードとして、推論エンジンを実際に動かした際のテンソルや形状を結び付ける。対象には密行列積、グループ化問い合わせ注意、潜在注意、専門家混合、正規化、サンプリングなどが含まれ、主要モデルをSGLang上で走らせて得た入力を形状に基づいて重複除去する。候補実装にはソースコード、呼出し口、対象GPUなどを保存し、評価記録には使用環境、正しさ判定、実行時間を残す。大量評価ではGPUごとの排他制御、予熱実行、CUDAイベント計時を用い、通常は長寿命ワーカーで高速に処理する一方、繰り返し失敗する候補は独立プロセスへ隔離してCUDA状態の汚染や残留メモリ利用を防ぐ。複数GPUへの割当では、基準実装が既に載っているか、コンパイル済みキャッシュがあるかを費用として扱い、ハンガリアン法で小さな処理群を割り当て、実測結果で費用推定を更新する。生成エージェントには初回実装の評価記録を返し、コンパイル失敗、実行失敗、数値誤差、速度不足を材料に修正させ、複数回の中から正しく最も速い候補を残す。配備段階では、許容誤差を満たした評価記録から入力形状などを鍵に最速候補を選ぶ索引を事前構築し、頻繁に選ばれる実装を事前コンパイルする。実行時は入力から鍵を生成して定数時間の検索を行い、未コンパイル分のみ必要時にコンパイルする。これにより、実ワークロードの観測、候補生成、頑健な検証、性能比較、実推論への差替えが一つの循環として接続される。

### 統一追跡記録
演算が何を計算するかという意味仕様、実際に投入された具体入力、エージェントが作成した候補実装、その候補を特定GPUで測った結果を別々のファイル体系として扱わず、一つの参照関係で結び付ける。演算定義には形状制約や参照実装まで含めるため、可変長列やページ化KVキャッシュのような不規則な入力も再現できる。評価は候補実装とワークロードの組に対して不変記録として残るので、後から基準が変わっても、どのコードをどの入力と環境で測定した結果かを追跡できる。この形式を生成時、公開ランキング、本番差替えで共通利用することにより、各段階で仕様を手作業で変換する際の情報欠落を防ぐ。

### 実運用ワークロード収集
単純な正方行列や固定系列長だけを生成して性能を測るのではなく、実際の推論エンジンへ会話入力を流し、主要モデルの実行中に現れる形状やキャッシュ配置を採取する。対象演算は行列積だけでなく、通常およびページ化された注意機構、潜在注意、専門家混合、RMS正規化、確率的サンプリングまで広げる。固定パラメータの組合せを別の演算定義として分離し、可変部分については実負荷から得た入力を形状統計に基づき重複除去する。これにより、生成エージェントは本番で実際に頻出する小バッチ、長文脈、不均一なページ表などに対して最適化を試せる。評価結果も同じ具体入力に紐付くため、合成課題でだけ高速な候補を本番へ誤って採用する危険を減らす。

### 頑健な自動評価基盤
候補コードを高速に大量評価するだけでなく、壊れた生成コードや評価系を悪用するコードを前提に安全性を設計する。通常の決定的演算は参照値との誤差と非数値の発生を検査し、低精度演算は量子化誤差を許容する専用基準を使う。確率的サンプリングは一回の出力一致を求めず、反復実行で得た経験分布と期待分布の全変動距離を測り、上位k個や累積確率による許可集合から外れた値が出ないことも確認する。性能測定ではGPUごとの排他制御と予熱を行い、CUDAイベントでデバイス実行時間を測る。通常は長寿命ワーカーで高速に回すが、繰り返し失敗する候補は独立プロセスで実行し、終了時にCUDA文脈ごと破棄する。この二経路により、大規模探索の処理量と、残留メモリ参照などを防ぐ隔離性を両立する。

### 評価結果を返す生成改善ループ
生成モデルへ演算仕様だけを一度渡して終えるのではなく、最初の候補を実GPUでコンパイル・実行・計測し、その評価記録を次の修正入力として返す。失敗した場合はコンパイルエラー、実行時エラー、数値不一致などを具体的な観測として与え、成功した場合は基準実装に対する速度比を与える。エージェントはこの情報を使って次の候補を作り、複数回の試行から正しく最も速い実装を選ぶ。評価指標は単純な正解率だけでなく、各ワークロードで基準より所定倍率以上速く、かつ正しい割合を速度閾値ごとに集計するため、正しさと性能を同じ曲線で比較できる。論文の分析では、失敗の大半がコンパイル段階にあり、最新GPU命令や複雑なタイル化の利用が弱いことまで明らかにしており、この評価記録自体が今後の学習データや強化学習報酬として利用できる。

### 本番カーネル動的差替え
検証済み候補をランキングに載せるだけでなく、推論エンジンの実呼出しへ直接反映する仕組みを備える。事前段階で、誤差基準を満たした評価記録から形状などの特徴を鍵として抽出し、その鍵ごとに最速実装を選ぶ索引を作る。頻繁に使われる候補は起動前に事前コンパイルし、残りは必要になった時点でコンパイルする。実行中は関数引数から同じ鍵を作り、定数時間の索引検索で候補を決めるため、複雑な探索を要求処理のたびに行わない。装飾子型と命令型の二つの呼出し方法を用意し、差替え対象がない場合や機能を無効化した場合は元の実装へ透過的に戻る。FlashInferとの統合では環境変数だけで一般的な演算をこの経路へ送れるため、SGLangやvLLM本体へ候補ごとの手動修整を入れずに、生成された新しいカーネルを継続導入できる。

### 全体のデータ／制御の流れ
全体は、実負荷観測、統一記録への保存、生成エージェントによる候補作成、分散評価サービスによる検証、評価結果を使った再生成、公開比較、検証済み候補の本番差替えという循環で構成される。推論エンジン側で新しいモデルや入力分布が現れれば、その実行を再びワークロードとして採取できるため、静的な一回限りのベンチマークではなく、運用環境の変化を次の最適化へ還流させることを狙っている。
## 評価条件
- **ハードウェア**: 生成agentの主要評価はNVIDIA B200。トレース例もB200上で実測し、エンドツーエンド評価はSGLangでLlama-3.1-8B-Instructを配信する。
- **ソフトウェア**: FlashInfer-Bench、FlashInfer、SGLang、PyTorch、Triton、CUDAを利用。トレース例ではPyTorch 2.8.0+cu128、Triton 3.4.0、CUDA 12.8。
- **比較対象**: FlashInfer、PyTorch（対応FlashInfer カーネルがない場合）、native SGLang FlashInfer backend
- **正確性・品質**: 通常演算はreferenceとの数値誤差とNaN/Infを検査。低精度演算は要素一致率等の専用基準を用いる。samplingは期待確率分布と反復実行の経験分布のtotal variation distanceを測り、top-k/top-p mask違反も即失敗とする。
現版は単一GPU上のLLM推論カーネルが中心で、multi-GPU collectiveや通信カーネルは未対応。対応hardware・model・programming languageも限定される。
## 主要結果
FlashInfer-Benchの現行snapshotでは、生成agentはRMSNormのようなメモリ-bound演算では人手最適化へ近づく一方、GEMMやGQAなどcompute-bound演算では多くのワークロードでSOTAの半分未満に留まる。correctness上位はGPT-5 83.9%、o3 71.3%、Gemini-2.5-Pro 48.8%。観測した32件のcorrectness errorのうち30件はcompile failureで、数値・ランタイム errorは2件だけだった。TritonはCUDAより正しさと速度を得やすいが、CUDAは成功時の上限が高い。production差替えはカーネル call当たり1〜2us、E2E オーバーヘッド 0.8%未満で、差替えたカーネル速度の差がSGLangのE2E 遅延へ反映された。

- leaderboard correctness / GPT-5 83.9%、o3 71.3%、Gemini-2.5-Pro 48.8% pass (比較対象: FlashInfer-Bench snapshot; 条件: 実LLM serving由来カーネル ワークロード) — frontier modelでもproduction カーネルの完全な正しさは未達で、評価・修正loopが必要。

- correctness error breakdown / 32 errors中30 compile failures、2 ランタイム/numerical failures (比較対象: 全観測correctness errors; 条件: agent-generated カーネル) — 主障害はアルゴリズム理解よりAPI・dtype・ホスト/device文脈など実装生成の成立性にある。

- hard カーネル capability / GEMM(Triton)、GQA(CUDA/Triton)で半数超のワークロードがSOTA性能の50%未満 (比較対象: FlashInfer等SOTA カーネル; 条件: B200、feedback-loop agent) — compute-bound カーネルではtiling、パイプライン、hardware intrinsic活用が依然弱い。

- apply dispatch オーバーヘッド / カーネル call当たり1〜2us、E2E オーバーヘッド <0.8% (比較対象: native SGLang FlashInfer backend; 条件: Fused Add RMSNorm / Llama-3.1-8B-Instruct、バッチ 1/16/64) — 動的 registry lookupをproduction pathへ入れても固定費は小さい。

- batch64 isolated カーネル 遅延 / FlashInfer 0.0112ms、Gemini-2.5-Pro Triton 0.0160ms、GPT-5 Triton 0.0247ms (比較対象: 同一RMSNorm definition; 条件: バッチ 64) — validated generated カーネル間の速度差をトレースが定量化する。

- エンドツーエンド 遅延 / FlashInfer fallback 934ms、Gemini-2.5-Pro substitution 939ms、GPT-5 substitution 1055ms (比較対象: 同一SGLang serving構成; 条件: 代表RMSNorm substitution experiment) — カーネル単体の優劣が同方向のE2E差として現れ、deployment loopが実効的である。

### 負の結果・境界条件
- agentはBlackwellのtcgen05等の新hardware intrinsicを十分使えず、attention CUDAでもonline softmax以外のtiling/tensor-core/パイプライン最適化を実装できなかった。GPT-5 high-reasoningへ最適化方針を明示しても、10回の試行で正しい高度CUDA カーネルを生成できない事例がある。また現行datasetはmulti-GPU/communication カーネルを含まず、本番coverageは限定的である。

### 結果の読み方
主要成果は『LLMが人間カーネル技術者を既に上回った』ことではなく、失敗しやすい生成カーネルを実ワークロード・隔離correctness検証・定量性能評価でふるい、改善トレースをagentへ返し、合格品だけをproductionへ導入できる運用基盤を示した点にある。トレースがデータセット形式とdeployment registryを兼ねるため、serving ワークロードの変化を次のagent学習・探索へ戻せる。
## 品質への影響
apply()はreference semanticsを満たすvalidated solutionのみ選択し、モデル品質を変更する近似手法ではない。確率samplingも分布検定を行うため、単発出力一致を強制して誤ったカーネルを通すことを避ける。
## 既存研究との差
- **KernelBench/TritonBenchとの差**: 既存ベンチマークがLLMのカーネル生成能力評価を主目的とするのに対し、FlashInfer-Benchは実serving ワークロード、継続leaderboard、validated solution registry、production substitutionまで閉じる。
- **BackendBenchとの差**: PyTorch backend生成評価よりもLLM inference固有のattention、MoE、paged KV、sampling、低精度カーネルを中心に、実engine入力トレースとdeploymentを直接扱う。
- **TVM/Ansor/Meta-Scheduleとの差**: 人手で定義された探索空間とcost modelを探索する自動tuningに対し、LLM agentがTriton/CUDA source自体を生成・修正する開放的探索を、厳格なexecution feedbackで支える。
- **FlashInferとの差**: FlashInferは高性能カーネル libraryそのもの。FlashInfer-BenchはFlashInferを比較対象兼integration targetとして、agent生成候補を比較・検証し、必要なら実行時に置換する上位の継続最適化層。
## 限界
- 現行coverageは単一GPUの計算カーネル中心で、multi-GPU collective、通信カーネル、ネットワーク処理は対象外。
- 41 Definition・1,600 ワークロードは主要LLM推論演算を広く含むが、すべてのmodel、GPU世代、DSL、serving configurationを覆うわけではない。
- 生成agentの評価はB200中心で、hardware世代が変わると最良solutionやagentの失敗傾向も変わり得る。
- 隔離、hidden ワークロード、専用validatorでreward hackingを抑えるが、correctness oracle自体の抜けを完全には排除できない。
- 最速カーネルの動的差替えは局所カーネル性能を利用する仕組みで、global スケジューラやメモリ capacityとの共同最適化は別課題。

## 研究上の位置づけ
リポジトリではカーネル-ランタイム-compilation系統に置く。特に『AIがカーネルを生成する』研究と『vLLM/SGLang/FlashInferが本番推論を実行する』研究の間にある検証・継続配備層を担う。実ワークロードをトレース化し、agent feedbackとproduction dispatchの双方が同じimmutable evaluation recordを参照するため、将来の自律的ランタイム最適化やオンラインhardware-specializationの基盤として重要である。
