# Open-TQ-Metal：Apple Siliconで圧縮KVのまま注意を計算する融合カーネル

## 書誌・一次資料

Sai Vegasenaによる2026年4月公開のプレプリント。正規識別子は `arXiv:2604.16957`。2026年4月18日付の第1版（全8ページ）を読み、本文のアルゴリズム1、式1〜6、表1〜6、図1〜4、負の結果と限界を確認した。対象はApple SiliconのMetal演算器とMLX実行環境であり、CUDA GPUの実測結果ではない。特に「注意カーネル48倍」と「LLM全体の生成処理量」は測定対象が異なるため、混同しない。

## 概要

70B級モデルを端末上で動かすとき、重みを4ビット化しても長文脈の鍵・値（KV）キャッシュが巨大になる。Llama 3.1 70Bは4ビット重みだけで約39.1GBを必要とし、128Kトークンの16ビットKVキャッシュが約40GB加わる。合計約79.1GBとなり、64GBの統合メモリを持つMacには収まらない。KVを4ビットに量子化すれば保存容量は減るが、従来型の処理では注意計算の前に大きな行列を16/32ビットへ戻し、一時メモリとメモリ帯域を再び消費する。

Open-TQ-Metalは、圧縮されたKVを直接読み、Metalカーネルのレジスタ内で4ビット値を復元しながら問い合わせとの内積、安定なオンラインソフトマックス、値の加重和を一体化する。長文脈では鍵・値列を512トークンごとに分け、独立した部分注意を計算してから、各部分の最大ロジットと指数和を使って正しく統合する。入力文脈の前処理と一トークンずつの復号では最適な演算方式が異なるため、前処理はMLXの通常注意を使い、復号だけ融合4ビット注意へ切り替える。

Llama 3.1 70Bの128K文脈では、注意カーネル単体が逆量子化後に注意を実行する方式の480.6msから9.9msへ短縮され、約48倍となる。KVキャッシュは40GBから12.5GBへ減り、重みと実行時費用を含む総量53.6GBで64GB端末に収まる。実際の全体生成速度は6.0トークン/秒であり、カーネルの48倍をそのまま全体速度と解釈してはならない（原著表2、表4〜5）。

## 問題設定：圧縮しても復元行列を作れば帯域が戻る

自動回帰生成では、過去トークンの鍵と値を毎回読み出して次のトークンの注意を計算する。層数 `L`、KVヘッド数 `H_kv`、文脈長 `S`、ヘッド次元 `d`、要素当たりバイト数 `b` に対して、単純なKV保存量は `2 L H_kv S d b` となる。Llama 3.1 70Bでは80層、KVヘッド8、ヘッド次元128、文脈128K、16ビット要素2バイトなので、KVだけで約40GBとなる（原著式1）。この量は重みの量子化だけでは消えない。

4ビット保存では二つの値を1バイトへ詰める。原著は32要素を一組とする非対称4ビット量子化を使い、組ごとに最大値と最小値から倍率 `s` と零点 `z` を計算する。元の値 `x` は4ビット整数 `q` へ丸められ、利用時に `x̂=(q−z)s` で近似復元する。倍率と零点の保存費用を含めると、理想的な16ビット→4ビットの4倍ではなく、実効約3.2倍の圧縮となる（原著式2〜3）。

問題は、保存時に4ビットへ圧縮しても、注意計算の直前にKVの全行列をFP32へ逆量子化してメモリへ書き戻す実装では、巨大な一時行列が生じる点にある。長文脈ほどこの一時行列の書込み・読込みが増え、4ビット保存による帯域削減を打ち消す。著者はGemma 4の条件で、逆量子化された一時行列が数百MBになる例を挙げる。Open-TQ-Metalの中心課題は、圧縮率の改善そのものではなく、注意演算の途中に非圧縮行列を実体化しないことである。

## 手法

### 1. 4ビットKVのレジスタ内復元と融合注意

融合4ビット注意カーネル（fused int4 SDPA）は、問い合わせベクトル `q`、4ビットで詰められた鍵・値、組ごとの倍率と零点を入力する。まず問い合わせをヘッド次元の平方根で前処理し、各過去トークンの圧縮鍵をGPUレジスタへ読み込む。4ビット値をビット演算で取り出し、倍率と零点で復元した鍵との内積から注意ロジットを得る。対応する値も必要になった時点でレジスタ内復元し、オンラインソフトマックスの加重和へ直接加える。復元されたKV行列全体をGPUメモリに書き出さない（原著アルゴリズム1）。

オンラインソフトマックスでは、処理済みトークンの最大ロジット `m`、指数和 `ℓ`、値の重み付き累積和 `o` を保持する。新しいロジット `a_i` を読んだとき、新最大値 `m'=max(m,a_i)` を計算し、古い累積和を `exp(m−m')` で再尺度化してから新しい `exp(a_i−m')` を加える。最後に `o/ℓ` を返す。これは全トークンのロジット行列を保存せずに数値的に安定した正規化を行う方法である。注意の精度を維持する鍵は、最大値を更新したとき過去の累積値も同じ基準へ変換する点にある。

### 2. 4ビット抽出のベクトル化とGPU実行単位

単純に4ビット値を一つずつシフト・マスクすると、整数演算と制御が増える。著者はMLXの量子化内積で使うパターンを採用し、圧縮した32ビット語を16ビット語として解釈して、`0x000F`、`0x00F0`、`0x0F00`、`0xF000` のマスクで4つの4ビット部分を並列に扱う。問い合わせ側を16の冪で事前に尺度調整しておけば、個別にビットシフトしてから掛ける処理を減らせる（原著式4）。これは4ビット表現を保ったままGPUのSIMD実行に適合させる実装上の工夫である。

Apple Siliconでは32レーンのSIMDグループを基本単位とする。Llamaのヘッド次元128では各レーンが4要素を担当し、一つのSIMDグループでヘッド全体を覆える。Gemmaのヘッド次元はより大きく、異なるスレッドグループ構成が必要になる。グループ化問い合わせ注意（GQA）では、複数の問い合わせヘッドを対応するKVヘッドへ写像して同じ圧縮KVを参照する。圧縮形式だけでなく、GPUレーンの配置とモデルのヘッド構造が性能に影響する。

### 3. 長文脈を分割する並列注意と安定な統合

128Kトークンを単一のスレッドグループで順番に処理すると、長い依存鎖ができて並列性が不足する。Open-TQ-Metalは鍵・値列を512トークンごとの部分へ分割し、各部分を別のスレッドグループで処理する分割鍵並列（split-K parallelism）を用いる。各部分は、その区間の注意出力 `o_c`、最大ロジット `m_c`、指数和 `ℓ_c` を返す。全区間の最大値 `m_global` を求めた後、各区間の寄与を `ℓ_c exp(m_c−m_global)` で再尺度化し、重み付き平均を取る（原著式5）。

部分注意の結果を単純に平均すると、区間ごとのソフトマックス分母が異なるため、全体の注意と一致しない。最大値と指数和を統合する式を使うことで、分割した結果が全体のソフトマックスと整合する。著者はMetalの複数ディスパッチが一つの `eval_gpu()` 内で必ず順序通りに実行されるとは限らない問題に対し、部分計算と統合を別々のMLX Primitiveへ分け、後段が前段の出力に依存する計算グラフで順序を保証する。単なる並列分割だけでなく、実行順序の競合を避ける実装が必要である。

### 4. 前処理と復号の切替え

融合カーネルは問い合わせが一つで過去のKVが長い復号段階に最適化されている。入力をまとめて読む前処理段階は多数の問い合わせを一度に処理するため、MLX標準の尺度付き内積注意を使った方が効率的な場合がある。著者の経路では、前処理中はFP16の鍵・値で通常注意を計算し、計算後にKVを4ビットへ圧縮して保存する。復号では問い合わせ数が一つでキャッシュ長が一定以上の場合に、融合4ビット注意を使う（原著§3.3）。

これにより前処理の密な演算性能と復号の圧縮メモリ性能を両立する。ただし前処理段階のKV一時表現が完全に消えるわけではなく、特に大きなバッチや同時要求での一時メモリ圧力は、復号時のキャッシュ容量だけでは評価できない。著者は本方式を主に一要求の長文脈生成へ適用しており、多数要求を同時に処理するサービング基盤での評価は別途必要である。

### 5. macOSのメモリ固定と全体実行

4ビット重み39.1GBを64GBの統合メモリに置いていても、macOSがその一部をSSDへページアウトすると、モデル重みを繰り返し読み込む生成段階で大きな遅延が生じる。著者はMLXの有線メモリ上限設定を使って重みを物理メモリへ固定し、128K文脈のLlama 70Bで0.6から6.0トークン/秒へ改善したと報告する（原著§3.4）。この約10倍はページング対策の効果であり、融合注意カーネル単体の48倍とは異なる。

実際の生成では、前処理→4ビットKVの保存→復号トークンの問い合わせ生成→圧縮KVからの融合注意→分割部分の統合→次トークン生成→KVの追加、という流れになる。重みの読込み、KVの管理、トークン生成の他の層も全体時間に含まれる。カーネルの高速化だけでは重み帯域の限界を超えられず、これが全体速度とカーネル速度の倍率差を生む。

## 異なるモデルで量子化が失敗する理由

通常の注意ロジットは `α qᵀk` と書け、一般的な尺度係数は `α=1/√d` である。Llamaのヘッド次元128では約0.0884だが、著者が評価したGemma 4は問い合わせと鍵の正規化方法が異なり、`α=1.0` を使う。角度に変換して量子化するPolarQuantでは、角度誤差 `δθ` によるロジット誤差が概ね `α‖q‖‖k‖(1−cos δθ)` に比例するため、同じ角度誤差でも尺度係数が大きいモデルでは誤差が増幅される（原著式6）。

表1では、PolarQuantの4ビット設定の余弦類似度がLlama 70Bで0.958、Gemma 31Bで0.621となり、Gemma側では生成が破綻する。これに対し、32要素組の4ビット量子化では類似度がLlamaで0.998、Gemmaで0.992となり、対象実験では実用的な出力を保つ。著者は、角度量子化の方向性誤差と、組ごとのアフィン量子化の要素誤差が、注意内積に与える影響の違いとして説明する。尺度係数だけで全モデルの量子化成否が決まるという普遍的な定理ではなく、評価した二つのモデル系列での観察である。

さらに、1ビットの射影方式QJLでは層ごとのスコア相関が約0.85〜0.87でも、深い層を通ると誤差が累積し、70Bの80層やGemmaの60層で反復的な出力になると報告する。著者は初期10層だけQJLを使い残りを4ビットにする混合案も調べたが、メモリ削減は約1.7%で品質上の危険に見合わないと判断した。小規模モデルで成立した圧縮方式が深いモデルでも成立するとは限らないという負の結果である。

### カーネル単体とエンドツーエンドの差

表2の48倍は、長さ128KのKVを丸ごと逆量子化してから注意を計算する比較カーネルに対する値である。モデル全体では各層の重み行列を読み込み、注意以外の演算を実行し、KVの追加や生成状態の管理を行う。Llama 70Bの重みは約39GBあり、論文は約400GB/秒のメモリ帯域に対して重み読込みだけで最低約98ms/トークンという下限を議論する。この制約下では注意を9.9msに短縮しても、全体が48倍速くなるわけではない（原著§7.1）。

表5ではOpen-TQ-Metalの6.0トークン/秒に対し、mlx-lmの別条件での7.3トークン/秒という値が併記されるが、mlx-lmは同じ64GB端末で128K文脈を収容できない。従ってこれは同一128K条件での単純な速度勝負ではない。著者は、同じ端末で実現可能な文脈上限をmlx-lm約73K、llama.cpp約50K、Ollama約40Kと報告する。比較方式のキャッシュ形式と設定に依存する数値であり、各フレームワークの将来版や別ハードウェアまで不可能だと断定する根拠にはならない。

### 圧縮の品質と負の結果

著者はLlamaで同じ入力を貪欲復号した場合、4ビットKV経路とFP16経路が同じ最上位トークンを選んだと報告する。ただし、この一致は論文で実際に試した入力条件の結果であり、128K〜236Kのすべての課題で意味品質が一致することの証明ではない。Gemma 4では角度量子化が破綻する例を示し、4ビットの鍵と値を別々に量子化した場合、値の量子化が注意出力へ直接伝播して品質へ大きく影響する傾向を報告する。4ビット鍵・FP32値の類似度0.998に対し、FP32鍵・4ビット値は0.994である。

構成要素・代替策の比較では、2Bのドラフトモデルを使う投機的復号の受理率が31B/70Bの対象で約25%にとどまり、著者が必要と見積もる約60%を下回った。別の混合専門家（MoE）構成では有効パラメータ約4Bの条件で59トークン/秒を得たと報告するが、これはLlama 70Bと同じモデル品質やパラメータ総数の厳密な対照ではない。圧縮注意だけでなく重み帯域を減らす設計が重要だという方向性を示す補助実験である。

## 既存研究との差

KIVI、KVQuant、GEARなどのKV圧縮研究は、保存するKVのビット数を減らしてメモリ消費を抑える。Open-TQ-Metalが重視するのは、圧縮したKVを注意の直前に大きな行列へ復元せず、圧縮データの読込みから注意出力までを一つのMetalカーネル内で処理する点である。オンラインソフトマックスと分割鍵並列は既存のFlashDecoding系の考え方を引き継ぐが、MLXの非同期ディスパッチを考慮して依存グラフを二段階へ分ける必要がある。

PolarQuantは角度変換、QJLは符号だけの射影、TurboQuantは量子化と残差符号化を組み合わせる。それぞれ圧縮率が高い一方、著者の二モデル系列では注意の尺度係数や深い層での誤差累積によって品質が破綻する場合があった。Open-TQ-Metalは比較的素直な組別4ビット量子化を選び、圧縮率だけでなく深いモデルの生成品質とMetalカーネル実装可能性を重視している。これはすべての他方式が一般に劣るという意味ではない。

## 限界と実用上の注意

第一に、長文脈での品質評価は限定的である。128Kや236Kの複雑な長文脈検索・多段推論について、RULERやLongBenchの包括的な正答率比較が行われたわけではない。最上位トークン一致は重要な確認だが、温度付きサンプリングや多数ステップにわたる生成の頑健性まで保証しない。236Kはメモリ容量の上限推定であり、その文脈長で6.0トークン/秒と同じ速度を測った結果ではない。

第二に、Gemma 4の一部設定では圧縮方式の数値誤差が累積する問題がある。論文はGemmaの角度量子化失敗だけでなく、4ビットKVでも長さ約950トークン付近に品質上の制約があると記述する。従って「すべてのモデルで128K文脈が高品質で動く」とは言えない。長文脈実現の主張はLlama 3.1 70Bの特定構成について読む必要がある。

第三に、融合注意は一問い合わせの復号を主対象とする。前処理段階ではFP16の鍵・値を使うため、入力をまとめて処理する場合の一時メモリや複数要求同時実行のスケーリングは、復号時の圧縮率からは推定できない。モデル重みを固定できない場合のSSDページングも深刻な性能要因であり、カーネルだけ移植して同じ処理量になるとは限らない。

第四に、GPUカーネル48倍の比較対象は全行列を逆量子化する方式であり、他の高性能な融合注意実装や最新のMetal実装をすべて同一条件で測った結果ではない。全体生成速度は重み読込みとKV管理の費用に制約される。論文の比較時点以後のmlx-lm、llama.cpp、Ollamaの改善を否定するものではない。

第五に、評価はApple M1 MaxとmacOS 15に依存する。MetalのSIMD幅、MLXの計算グラフ、統合メモリのページングを利用しているため、CUDA、ROCm、Vulkanへの直接移植やWindows PCでの性能を示す証拠ではない。別環境ではカーネルの再設計とベンチマークが必要である。
