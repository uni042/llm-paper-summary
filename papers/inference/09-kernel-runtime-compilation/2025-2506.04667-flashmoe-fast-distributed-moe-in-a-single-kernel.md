# FlashMoE: Fast Distributed MoE in a Single Kernel

> 分散MoE全体を単一の常駐GPUカーネルへ融合し、装置起点通信とタイル単位スケジューリングでCPU起動・同期待ちを除き、8基H100で最大6.4倍の遅延改善と5.7倍のスループットを示す。

## 概要

混合専門家モデル（Mixture of Experts; MoE）は、各トークンについて多数の専門家のうち一部だけを実行するため、総パラメータ数を増やしても1トークン当たりの演算量を抑えられる。ただし専門家が複数GPUへ分散されると、ルータが選んだ専門家の所在地へトークンを送る **分配** と、専門家出力を元の順序へ戻す **結合** が必要になる。従来はこれを一括通信（All-to-All）と複数のGPUカーネルで処理するため、通信同期とCPUからのカーネル起動の間にGPUの空き時間が生じる。

FlashMoEは「通信を少し速くする」のではなく、分散MoE層の実行単位そのものを組み替える。ゲート、分配、専門家のFFN、結合、GPU間通信を **1個の常駐カーネル（persistent カーネル）** に入れ、その内部で小さなタイル単位の仕事を依存関係が満たされた順に実行する。GPU間通信もCPUや同期的集合通信から起動せず、NVSHMEMを使った装置起点の一方向通信（device-initiated one-sided 通信）にする。

この構成では、あるGPUが通信完了を待っている間にも別タイルの専門家計算を進められる。また、実際にrouteされたトークンだけを送るため、専門家 capacityまでゼロ埋めしたpayloadをネットワークへ流す必要もない。8基のH100上で単一MoE層を測った評価では、16Kトークンで最大6.4倍の順伝播 遅延改善、17.7M トークン/s、平均SM利用率93.17%を報告した。比較対象がFP16なのに対しFlashMoEはFP32で評価されており、それでも高い実効性能を示している。

## 問題設定

### なぜMoEは「疎だから速い」だけでは済まないのか

MoE層では各トークンをtop-k個の専門家へ送る。専門家並列（Expert Parallelism; EP）では専門家を複数GPUへ分割して保持するため、ルータが選んだ専門家がローカルGPUにない場合はトークン活性値を別GPUへ送らなければならない。計算終了後には出力を元GPUへ戻して重み付きで結合する。

一般的な実装では、全GPUが参加するAll-to-Allを分配と結合で使う。これは分かりやすいが、遅いGPUが一つあると他GPUも集合通信完了まで待つ。論文は既存研究を踏まえ、MoE通信が実行時間の大きな割合を占め得ることに加え、この同期点がstragglerの影響を全GPUへ伝播させることを問題視する。

### 通信と計算を重ねても、カーネル起動が残る

既存方式にも通信と専門家計算を分割し、互いに重ねる方式はある。しかし細かく分けるほどCPU側から起動するGPUカーネル数が増える。論文の2基A100でのプロファイルでは、1 MoE層のGPU operation数はFlashMoEが1なのに対し、COMET 33、Megatron-CUTLASS 85、Megatron-Transformer Engine 261、Megatron+DeepEP 432、DeepSpeedMoE 550だった。

多数の短いカーネルは起動gap、GPU間での開始時刻のずれ、カーネル境界ごとの大域 メモリ往復を作る。MoEのルーティングは入力依存なので、固定的なCUDA Graphだけではこの動的依存を簡単には吸収できない。FlashMoEの狙いは、通信計算重畳だけでなく、**それを実現するためのCPU orchestration自体をcritical pathから外すこと**にある。

## 手法のあらまし

FlashMoEでは分散MoE層を、GPU上で動き続ける一つのカーネルとして起動する。その内部で仕事を「タスク（タスク）」へ分解し、ほぼ全thread blockを計算担当のProcessor、一つの管理blockをSchedulerとSubscriberへ役割分担する。

入力トークンをgateした後、remote GPUへ必要なtileを一方向転送する。受信側Subscriberは到着したpacketをタスク descriptorへ変換し、Schedulerが依存関係を満たしたタスクを空いているProcessorへ渡す。ProcessorはFFNのGEMMや結合を行い、必要ならそのまま次のGPU通信を起動する。このため「全GPUの分配完了→全GPUでcompute→全GPUの結合」という大きな障壁を、tileごとの細かなデータフローへ置き換えられる。

## 手法

### 1. 単一常駐カーネル — CPU起動列をなくす

入力はトークン行列、専門家重み、ルーティング結果である。通常はgate、permute/分配、通信、専門家 GEMM、活性値、結合などが別々のGPU operationになるが、FlashMoEでは一つのpersistent カーネル内部からこれらを実行する。

カーネルがMoE層の処理中ずっとGPU上に残るため、各段階のたびにCPUへ制御を戻して次カーネルをlaunchする必要がない。したがって出力は従来と同じMoE 層 resultだが、途中のホスト synchronizationとlaunch gapを削れる。

### 2. Actor型Scheduler / Subscriber / Processor — tileの準備ができ次第進める

FlashMoEはGPU block/warpへ三つの役割を与える。ProcessorはGEMM、element-wise演算、結合、tile通信など実処理を担当する。Subscriberは他GPUから届いたpacketを読み、どのtileのどの処理が可能になったかをタスクへ変換する。Schedulerはready タスクを空いているProcessorへ割り当てる。

N個のthread blockのうちN-1個をProcessorとし、残る1 blockを小さな「OS block」として使う。その中で三つのwarpをSubscriber、一つをSchedulerに割り当てる。管理に使うSM資源を限定し、残りを計算へ回す構成である。

重要なのは、GPU全体で一つの段階を終えるのを待たず、**あるtileの入力が揃えばそのtileだけ先へ進める**ことだ。これが通信待ちの裏で別tileの計算を走らせる細粒度の重畳につながる。

### 3. 統一task abstraction — FFNとcombineを同じ実行系へ載せる

専門家FFNは行列積と活性化、結合は専門家 出力とルーティング 重みの積和という異なる演算だが、FlashMoEはmetadata・二項テンソル演算・活性値からなるタスク descriptorとして統一する。

これによりSchedulerから見れば「どのdevice/tileに対して、どの演算を実行するか」を同じ形式で扱える。Processor側ではタスクごとの演算を `__device__` 関数として呼び、活性値や加算もregister上で融合する。異なるMoE段階を別カーネルにする必要を減らすための内部表現である。

### 4. 対称テンソル配置 — 一方向GPU通信を同期なしで安全にする

装置起点通信にはNVSHMEMの区分化大域アドレス空間（Partitioned Global Address Space; PGAS）を使う。ただし複数GPUが同じ受信バッファへ非同期に書けば競合する。

そこでFlashMoEは専門家 並列 rank、分配/結合の通信round、staging バッファ、局所 専門家、capacity、隠れ dimensionを明示的な軸に持つ **対称テンソル配置（symmetric テンソル layout）** を作る。分配と結合の各roundに送受信用slotを分離し、同時writeが同じ座標へ衝突しないようにする。

MoEでは2通信roundを扱うため、通常は元トークン バッファの約4倍のstaging領域を使う。論文では人気モデルを想定した推論時の追加メモリはGPU容量の2%以下としている。メモリを少し余分に使う代わりに大域 barrierを避ける設計である。

### 5. In-place padding — 空tokenをネットワークへ送らない

MoE ルーティングは不均衡なので、専門家ごとの実トークン数は最大capacityより少ないことが多い。集合通信通信ではバッファ 形状を揃えるため、空きslotをゼロトークンでpaddingし、そのゼロまで転送する実装がある。

FlashMoEはremoteへpadding済みバッファ全体を送るのではなく、有効なトークンだけを送り、受信側の対称バッファ内でalignment用paddingを行う。つまり計算しやすい固定tile形状は維持しながら、ネットワークpayloadから不要なゼロを外す。

この効果はルーティングが偏り、実トークン数が専門家 capacityを大きく下回るほど大きい。一方で対称バッファ自体には余白が必要になるため、通信量削減と追加バッファ容量の交換条件がある。

## 評価

### まず見るところ

- **対象:** エンドツーエンド LLM 推論提供ではなく、単一の分散MoE 層 順伝播。
- **GPU:** H100 80GB ×8、NVLink。
- **比較対象:** COMET、FasterMoE、Megatron-CUTLASS、Megatron-Transformer Engine。
- **精度:** FlashMoEはFP32、比較対象はFP16。論文はFlashMoE側に不利な条件と位置付ける。
- **最大遅延改善:** 8 GPUで最大6.4倍、4 GPU・16K トークンでMegatron-TE比4.6倍。
- **SM利用率:** FlashMoE 93.17%。
- **スループット:** 8 GPUで17.7M トークン/s、FasterMoE比5.7倍超。
- **専門家 scaling:** 128 エキスパートで4 H100最大4倍、8 H100最大6.6倍の遅延改善。

### 数字を読む際の注意

FlashMoEの主評価は **モデル全体の生成速度ではない**。注意機構、KV キャッシュ、sampling、continuous batchingを含むLLM server全体では、MoE 層以外の時間も残るため、単一層の5.7倍をそのままトークン/sへ外挿できない。

またFlashMoEのFP16経路は論文時点で十分にtuningされておらず、評価ではFlashMoEのみFP32を使用する。これは通信byte数と演算量では不利だが、同一精度比較ではないため、「FP16同士なら必ず同じ倍率になる」とも言えない。

## 既存研究との差

FasterMoEやTutelはAll-to-Allと専門家 computationの重畳を狙うが、同期集合通信と複数カーネルという実行構造は残る。Lancetはさらに広い計算を通信へ重ねるが、やはりbarrierを持つ集合通信の影響を受ける。

COMETやDeepEPはGPU起点通信や細粒度重畳という方向では近い。しかしFlashMoEはgateから結合までを一つのpersistent カーネルへ入れ、タスク スケジューラもGPU内部で完結させる点を中心差としている。したがって「より良いAll-to-All実装」というより、**All-to-All中心の段階型executionをタスク-drivenなGPU-native dataflowへ置き換える**研究として見ると分かりやすい。

## 限界・実装状況

論文自身が挙げる第一の制約は実装複雑性である。完全融合したpersistent カーネルはGPU 構成と分散システム双方の専門知識を要求し、一般的なフレームワークへ移植するコストが高い。

第二にFP16 pathのtuningが未成熟で、主結果はFlashMoE FP32対比較対象 FP16という非対称条件である。第三に対象は順伝播 inferenceで、学習へ広げるには逆伝播計算と勾配 通信も同じタスク システムへ融合する必要がある。

さらに評価は単一ノードH100/NVLinkと単一MoE 層が中心で、複数ノードRDMA、実LLM 推論提供の注意機構/KV/スケジューラとの干渉、異なるGPU世代でのoccupancyは主評価されていない。論文はmulti-nodeで利得が拡大する可能性を述べるが、これは測定結果ではなく将来予測として区別する必要がある。

公式コードは公開されている。

## 一般的な実装上の含意

通信計算重畳では「何% 重畳できたか」だけでなく、そのために何個のカーネルを起動し、どれだけホスト synchronizationを増やしたかを見る必要がある。細粒度化で通信待ちを隠しても、launch gapへ置き換わればGPU利用率は上がらない。

FlashMoEの設計は、動的で不均衡なワークロードほど「固定段を順に実行する」より「readyになった小タスクをdevice側スケジューラが処理する」方が合うことを示す。一方、これを実用化するには追加バッファ、スケジューラ占有、tile サイズ、register pressureまで同時に調整する必要がある。
