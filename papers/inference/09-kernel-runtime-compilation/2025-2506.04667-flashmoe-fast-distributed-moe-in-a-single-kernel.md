# FlashMoE: Fast Distributed MoE in a Single Kernel

> 分散MoE全体を単一の常駐GPUカーネルへ融合し、装置起点通信とタイル単位スケジューリングでCPU起動・同期待ちを除き、8基H100で最大6.4倍の遅延改善と5.7倍のスループットを示す。

## 概要

混合専門家モデル（Mixture of Experts; MoE）は、各トークンについて多数の専門家のうち一部だけを実行するため、総パラメータ数を増やしても1トークン当たりの演算量を抑えられる。ただし専門家が複数GPUへ分散されると、ルータが選んだ専門家の所在地へトークンを送る **dispatch** と、専門家出力を元の順序へ戻す **combine** が必要になる。従来はこれを一括通信（All-to-All）と複数のGPUカーネルで処理するため、通信同期とCPUからのカーネル起動の間にGPUの空き時間が生じる。

FlashMoEは「通信を少し速くする」のではなく、分散MoE層の実行単位そのものを組み替える。ゲート、dispatch、専門家のFFN、combine、GPU間通信を **1個の常駐カーネル（persistent kernel）** に入れ、その内部で小さなタイル単位の仕事を依存関係が満たされた順に実行する。GPU間通信もCPUや同期的collectiveから起動せず、NVSHMEMを使った装置起点の一方向通信（device-initiated one-sided communication）にする。

この構成では、あるGPUが通信完了を待っている間にも別タイルの専門家計算を進められる。また、実際にrouteされたトークンだけを送るため、expert capacityまでゼロ埋めしたpayloadをネットワークへ流す必要もない。8基のH100上で単一MoE層を測った評価では、16Kトークンで最大6.4倍のforward latency改善、17.7M tokens/s、平均SM利用率93.17%を報告した。比較対象がFP16なのに対しFlashMoEはFP32で評価されており、それでも高い実効性能を示している。

## 問題設定

### なぜMoEは「疎だから速い」だけでは済まないのか

MoE層では各トークンをtop-k個の専門家へ送る。専門家並列（Expert Parallelism; EP）では専門家を複数GPUへ分割して保持するため、ルータが選んだ専門家がローカルGPUにない場合はトークンactivationを別GPUへ送らなければならない。計算終了後には出力を元GPUへ戻して重み付きで結合する。

一般的な実装では、全GPUが参加するAll-to-Allをdispatchとcombineで使う。これは分かりやすいが、遅いGPUが一つあると他GPUもcollective完了まで待つ。論文は既存研究を踏まえ、MoE通信が実行時間の大きな割合を占め得ることに加え、この同期点がstragglerの影響を全GPUへ伝播させることを問題視する。

### 通信と計算を重ねても、カーネル起動が残る

既存方式にも通信と専門家計算を分割し、互いに重ねる方式はある。しかし細かく分けるほどCPU側から起動するGPUカーネル数が増える。論文の2基A100でのプロファイルでは、1 MoE層のGPU operation数はFlashMoEが1なのに対し、COMET 33、Megatron-CUTLASS 85、Megatron-Transformer Engine 261、Megatron+DeepEP 432、DeepSpeedMoE 550だった。

多数の短いカーネルは起動gap、GPU間での開始時刻のずれ、カーネル境界ごとのglobal memory往復を作る。MoEのroutingは入力依存なので、固定的なCUDA Graphだけではこの動的依存を簡単には吸収できない。FlashMoEの狙いは、通信計算重畳だけでなく、**それを実現するためのCPU orchestration自体をcritical pathから外すこと**にある。

## 手法のあらまし

FlashMoEでは分散MoE層を、GPU上で動き続ける一つのカーネルとして起動する。その内部で仕事を「タスク（task）」へ分解し、ほぼ全thread blockを計算担当のProcessor、一つの管理blockをSchedulerとSubscriberへ役割分担する。

入力トークンをgateした後、remote GPUへ必要なtileを一方向転送する。受信側Subscriberは到着したpacketをtask descriptorへ変換し、Schedulerが依存関係を満たしたtaskを空いているProcessorへ渡す。ProcessorはFFNのGEMMやcombineを行い、必要ならそのまま次のGPU通信を起動する。このため「全GPUのdispatch完了→全GPUでcompute→全GPUのcombine」という大きな障壁を、tileごとの細かなデータフローへ置き換えられる。

## 手法

### 1. 単一常駐カーネル — CPU起動列をなくす

入力はtoken行列、expert重み、routing結果である。通常はgate、permute/dispatch、通信、expert GEMM、activation、combineなどが別々のGPU operationになるが、FlashMoEでは一つのpersistent kernel内部からこれらを実行する。

カーネルがMoE層の処理中ずっとGPU上に残るため、各段階のたびにCPUへ制御を戻して次kernelをlaunchする必要がない。したがって出力は従来と同じMoE layer resultだが、途中のhost synchronizationとlaunch gapを削れる。

### 2. Actor型Scheduler / Subscriber / Processor — tileの準備ができ次第進める

FlashMoEはGPU block/warpへ三つの役割を与える。ProcessorはGEMM、element-wise演算、combine、tile通信など実処理を担当する。Subscriberは他GPUから届いたpacketを読み、どのtileのどの処理が可能になったかをtaskへ変換する。Schedulerはready taskを空いているProcessorへ割り当てる。

N個のthread blockのうちN-1個をProcessorとし、残る1 blockを小さな「OS block」として使う。その中で三つのwarpをSubscriber、一つをSchedulerに割り当てる。管理に使うSM資源を限定し、残りを計算へ回す構成である。

重要なのは、GPU全体で一つの段階を終えるのを待たず、**あるtileの入力が揃えばそのtileだけ先へ進める**ことだ。これが通信待ちの裏で別tileの計算を走らせる細粒度の重畳につながる。

### 3. 統一task abstraction — FFNとcombineを同じ実行系へ載せる

専門家FFNは行列積と活性化、combineはexpert outputとrouting weightの積和という異なる演算だが、FlashMoEはmetadata・二項tensor演算・activationからなるtask descriptorとして統一する。

これによりSchedulerから見れば「どのdevice/tileに対して、どの演算を実行するか」を同じ形式で扱える。Processor側ではtaskごとの演算を `__device__` 関数として呼び、activationや加算もregister上で融合する。異なるMoE段階を別kernelにする必要を減らすための内部表現である。

### 4. 対称テンソル配置 — 一方向GPU通信を同期なしで安全にする

装置起点通信にはNVSHMEMの区分化大域アドレス空間（Partitioned Global Address Space; PGAS）を使う。ただし複数GPUが同じ受信bufferへ非同期に書けば競合する。

そこでFlashMoEはexpert parallel rank、dispatch/combineの通信round、staging buffer、local expert、capacity、hidden dimensionを明示的な軸に持つ **対称テンソル配置（symmetric tensor layout）** を作る。dispatchとcombineの各roundに送受信用slotを分離し、同時writeが同じ座標へ衝突しないようにする。

MoEでは2通信roundを扱うため、通常は元token bufferの約4倍のstaging領域を使う。論文では人気モデルを想定した推論時の追加メモリはGPU容量の2%以下としている。メモリを少し余分に使う代わりにglobal barrierを避ける設計である。

### 5. In-place padding — 空tokenをネットワークへ送らない

MoE routingは不均衡なので、expertごとの実token数は最大capacityより少ないことが多い。collective通信ではbuffer shapeを揃えるため、空きslotをゼロtokenでpaddingし、そのゼロまで転送する実装がある。

FlashMoEはremoteへpadding済みbuffer全体を送るのではなく、有効なtokenだけを送り、受信側の対称buffer内でalignment用paddingを行う。つまり計算しやすい固定tile形状は維持しながら、ネットワークpayloadから不要なゼロを外す。

この効果はroutingが偏り、実token数がexpert capacityを大きく下回るほど大きい。一方で対称buffer自体には余白が必要になるため、通信量削減と追加buffer容量の交換条件がある。

## 評価

### まず見るところ

- **対象:** end-to-end LLM servingではなく、単一の分散MoE layer forward。
- **GPU:** H100 80GB ×8、NVLink。
- **比較対象:** COMET、FasterMoE、Megatron-CUTLASS、Megatron-Transformer Engine。
- **精度:** FlashMoEはFP32、比較対象はFP16。論文はFlashMoE側に不利な条件と位置付ける。
- **最大遅延改善:** 8 GPUで最大6.4倍、4 GPU・16K tokenでMegatron-TE比4.6倍。
- **SM利用率:** FlashMoE 93.17%。
- **スループット:** 8 GPUで17.7M tokens/s、FasterMoE比5.7倍超。
- **expert scaling:** 128 expertsで4 H100最大4倍、8 H100最大6.6倍のlatency改善。

### 数字を読む際の注意

FlashMoEの主評価は **モデル全体の生成速度ではない**。attention、KV cache、sampling、continuous batchingを含むLLM server全体では、MoE layer以外の時間も残るため、単一layerの5.7倍をそのままtokens/sへ外挿できない。

またFlashMoEのFP16経路は論文時点で十分にtuningされておらず、評価ではFlashMoEのみFP32を使用する。これは通信byte数と演算量では不利だが、同一精度比較ではないため、「FP16同士なら必ず同じ倍率になる」とも言えない。

## 既存研究との差

FasterMoEやTutelはAll-to-Allとexpert computationの重畳を狙うが、同期collectiveと複数kernelという実行構造は残る。Lancetはさらに広い計算を通信へ重ねるが、やはりbarrierを持つcollectiveの影響を受ける。

COMETやDeepEPはGPU起点通信や細粒度重畳という方向では近い。しかしFlashMoEはgateからcombineまでを一つのpersistent kernelへ入れ、task schedulingもGPU内部で完結させる点を中心差としている。したがって「より良いAll-to-All実装」というより、**All-to-All中心の段階型executionをtask-drivenなGPU-native dataflowへ置き換える**研究として見ると分かりやすい。

## 限界・実装状況

論文自身が挙げる第一の制約は実装複雑性である。完全融合したpersistent kernelはGPU architectureと分散system双方の専門知識を要求し、一般的なframeworkへ移植するコストが高い。

第二にFP16 pathのtuningが未成熟で、主結果はFlashMoE FP32対baseline FP16という非対称条件である。第三に対象はforward inferenceで、trainingへ広げるにはbackward計算とgradient communicationも同じtask systemへ融合する必要がある。

さらに評価は単一ノードH100/NVLinkと単一MoE layerが中心で、複数ノードRDMA、実LLM servingのattention/KV/schedulerとの干渉、異なるGPU世代でのoccupancyは主評価されていない。論文はmulti-nodeで利得が拡大する可能性を述べるが、これは測定結果ではなく将来予測として区別する必要がある。

## 一般的な実装上の含意

通信計算重畳では「何% overlapできたか」だけでなく、そのために何個のkernelを起動し、どれだけhost synchronizationを増やしたかを見る必要がある。細粒度化で通信待ちを隠しても、launch gapへ置き換わればGPU利用率は上がらない。

FlashMoEの設計は、動的で不均衡なworkloadほど「固定stageを順に実行する」より「readyになった小taskをdevice側schedulerが処理する」方が合うことを示す。一方、これを実用化するには追加buffer、scheduler占有、tile size、register pressureまで同時に調整する必要がある。
