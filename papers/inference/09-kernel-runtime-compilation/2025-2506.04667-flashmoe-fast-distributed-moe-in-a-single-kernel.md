# FlashMoE: Fast Distributed MoE in a Single Kernel

> 分散MoEはCPU管理のスケジューリング、ホスト起点通信、多数のカーネル起動によりGPUが待ちやすい。8基のH100、最大128専門家、16Kトークンの評価で、比較方式よりGPU利用率最大9倍、遅延最大6分の1、スループット最大5.7倍、重畳効率最大4倍を報告する。

## 概要

分散MoEはCPU管理のスケジューリング、ホスト起点通信、多数のカーネル起動によりGPUが待ちやすい。FlashMoEは専門家への振分け、専門家計算、結果統合とGPU間通信を一つの常駐GPUカーネルへ融合し、装置起点の一方向通信で細粒度に重ねる。

8基のH100、最大128専門家、16Kトークンの評価で、比較方式よりGPU利用率最大9倍、遅延最大6分の1、スループット最大5.7倍、重畳効率最大4倍を報告する。

この論文の要点は、単純に演算回数を減らすのではなく、実際の実行系で支配的になる待ち時間、メモリ、通信、資源競合のいずれかを観測し、その原因へ直接手を入れることにある。したがって代表値を読む際には、比較対象、装置、入力長、精度条件を切り離さずに解釈する必要がある。

## 問題設定

分散MoEはCPU管理のスケジューリング、ホスト起点通信、多数のカーネル起動によりGPUが待ちやすい。大規模言語モデルではモデル規模だけでなく、入力長、生成長、並列度、要求の混在、装置性能差によって律速点が変化する。固定的な構成は実装が単純な一方、条件が変わったときに遊休資源や不要な転送、過剰な計算を生みやすい。

既存方式の問題は、局所的な効率だけを改善しても処理全体の待ち時間へ反映されない点にある。たとえば計算を削減しても通信待ちが残れば速度は上がらず、メモリを節約しても管理処理が増えれば遅延は改善しない。本研究は、対象とする資源を明確にし、その資源を使う処理の粒度を変える。

## 手法のあらまし

分散MoEはCPU管理のスケジューリング、ホスト起点通信、多数のカーネル起動によりGPUが待ちやすい。FlashMoEは専門家への振分け、専門家計算、結果統合とGPU間通信を一つの常駐GPUカーネルへ融合し、装置起点の一方向通信で細粒度に重ねる。

処理の流れは、現在の入力または実行状態を取得し、必要な処理量や配置を決め、その決定をランタイムまたはカーネルへ反映し、得られた状態を次の処理へ引き継ぐ、という形で整理できる。判断のための追加処理が節約量を上回らないことが重要である。

## 手法

### 1. 状態の観測と表現

方式は、問題に応じてモデル状態、要求特性、通信状態、数値精度、注意履歴、生成進捗などを観測する。ここで得た情報は、どの計算を残すか、どの資源へ割り当てるか、どの時点で処理を終えるかを決める入力になる。

観測情報を毎回高価に作り直すと最適化の意味が薄れる。そのため、事前に求められる情報は較正・索引・プロファイルとして保持し、実行時には軽量な統計や既存状態を再利用する。動的な条件だけを更新することで管理費用を抑える。

### 2. 資源配分または計算削減

分散MoEはCPU管理のスケジューリング、ホスト起点通信、多数のカーネル起動によりGPUが待ちやすい。FlashMoEは専門家への振分け、専門家計算、結果統合とGPU間通信を一つの常駐GPUカーネルへ融合し、装置起点の一方向通信で細粒度に重ねる。

重要なのは、削減対象をハードウェアが効率良く扱える単位へまとめることである。トークン、専門家、要求、GPU、数値精度、状態遷移などの単位で選択し、細かな分岐や小さな転送を増やしすぎないようにする。

この設計により、理論上の削減を実際の帯域、遅延、スループット、エネルギー、容量の改善へ接続する。どの指標が改善するかは論文ごとに異なるため、単一の高速化倍率だけではなく、削減した資源と残る律速を合わせて見る。

### 3. 実行時の制御と安全側の経路

動的方式では、観測値から次の構成を選び、その構成で処理した結果を再び状態へ反映する。予測や近似を使う場合、誤差が大きい条件では保守的な構成へ戻すことができる設計が望ましい。無損失性を主張する方式では、最終的な検証経路が出力品質を保つ。

追加費用には、状態更新、探索、索引参照、同期、精度変換などが含まれる。これらが主処理より大きくならない範囲でのみ利得が生じるため、実装では更新頻度と処理粒度を調整する必要がある。

### 4. 一つの要求が通る流れ

一つの要求または学習単位が入ると、まず現在の状態を読み、対象論文の方針に従って処理量・配置・優先度を決める。次に決定済みの構成でモデル処理を行い、結果と実行統計を得る。

継続処理では、その結果を次の判断へ渡す。これにより個々の最適化が孤立せず、要求全体の処理時間や資源使用量へ反映される。複数要求を扱う場合は、個別要求の効率とシステム全体の公平性・利用率の両方を見る必要がある。

### 5. なぜ効くか

この方式が効く条件では、従来方式が余分に使っていた支配的資源を直接減らせる。計算律速なら不要な演算、帯域律速なら転送量、通信律速なら同期や通信量、待ち行列律速なら資源配分の偏りを減らす。

逆に対象外の資源が律速になると改善幅は縮む。したがって、導入時には論文と同じ条件を再現するだけでなく、自分の環境でどの資源が支配的かを測定し、最適化前後で律速がどこへ移ったかを確認する必要がある。

## 評価

8基のH100、最大128専門家、16Kトークンの評価で、比較方式よりGPU利用率最大9倍、遅延最大6分の1、スループット最大5.7倍、重畳効率最大4倍を報告する。

評価値はカーネル単体か処理全体か、実機か数値実験か、容量削減か壁時計時間かを区別して読む。特に大きな倍率は、その部分が全処理時間に占める割合以上には処理全体を高速化しない。

品質については、近似や削減を含む場合に元モデルとの精度差を同時に確認する必要がある。速度・容量・エネルギーだけが改善しても、必要な品質条件を満たさなければ配信系としての改善とは言えない。

## 既存研究との差

既存研究は固定構成、単一資源の最適化、均一な要求や装置を仮定するものが多い。対象論文は、実際に変動する状態を観測するか、実行系の構造そのものを組み替えることで、より細かい資源配分を可能にする点に差がある。

この差は他方式との併用可能性にも影響する。同じ帯域や同じ計算を削減する方式同士は利得が重複する一方、異なる律速を狙う方式は相補的になり得る。統合時には個別倍率を単純に掛け合わせず、処理全体を再測定する。

## 限界・実装状況

H100単一ノード中心の評価で、複数ノードのネットワーク特性や異なるGPU世代では通信方式と常駐カーネルの利得を再評価する必要がある。

また、論文で使われたモデル、GPU、入力分布から離れるほど代表値の再現性は下がる。研究実装を本番へ導入する場合は、異常時のフォールバック、監視指標、品質劣化の上限も含めて検証する必要がある。

## 一般的な実装上の含意

実装ではまず律速を測り、その律速に直接対応する指標を設定する。平均値だけでなく末尾遅延、最大メモリ、通信待ち、GPU利用率などを同時に測ると、最適化によって律速が別の場所へ移ったことを検出しやすい。

動的制御を採用する場合は、判断器そのものの費用を測る。処理量が小さい要求では制御費用が相対的に大きくなるため、一定以下の規模では通常経路へ戻すなどの境界条件を設けると実運用しやすい。
