# Compass: A Decentralized Scheduler for Latency-Sensitive ML Workflows

> モデル配置を織り込むタスク配置とGPUキャッシュ管理を統合した完全分散型スケジューラで、混在する機械学習ワークフローの平均遅延をHEFTの18.0秒から2.5秒へ下げ、キャッシュヒット率99パーセントを出す。

## 概要

画像処理や自然言語処理を対話的に提供するサービスは、一つの入力に対して複数の機械学習モデルを順に適用する実行形態を取る。例えば会議の自動字幕では、言語モデルで入力を処理し、翻訳モデルで各言語へ訳し、結果を統合する。このような実行は、頂点がモデルの計算、辺が前後関係を表すデータフローグラフとして表せる。各段の計算はGPUを持つワーカーで走るが、モデルは数百メガバイト級の大きさがあり、必要なモデルがGPUメモリに載っていないと、読み込みの間その段は始められない。つまり遅延は、タスクをどこへ置くかと、GPUメモリに何を載せておくかの共同決定で決まるのに、従来はこの二つが別々に扱われてきた。

さらにスケジューラの形も問題になる。中央集権型は全体を協調して決められる反面、全ワーカーが中央へ状態を相談し通知を受けるため、相談自体がボトルネックになり得る。エッジのクラスタでは実行時間が読みにくく、負荷もキャッシュの中身もすぐ変わるため、最初に固定した計画は早く古くなる。本論文のシステムは、論文第1版ではNavigatorという名前で提案される、完全分散型のスケジューラである。全ワーカーが対等で、負荷とGPUキャッシュの中身を含む全体状態を複製して持ち、どのワーカーも全タスクの配置を決められる。配置は、依存関係とモデルの在処と負荷から作る計画段階と、実行中の変化へ追随する動的調整段階の二段で進む。GPUメモリはキャッシュとして管理し、ヒット率を遅延の主要因として正面から扱う。

**代表結果:** 4種のワークフローを混在させる高負荷の実験で、本方式は先行スケジューラより2倍から6倍速く、パイプラインの種類によっては20倍から30倍の差がついた。平均遅延は2.5秒で、JITの5.0秒、ハッシュ方式の10.5秒、HEFTの18.0秒を大きく下回り、GPUのキャッシュヒット率は99パーセント、消費エネルギーとGPU利用率は比較方式と同程度だった。シミュレーションでは同じワークロードを半分のサーバ数で処理できた条件もある。

## 問題設定

資源の観点で核心は、GPUメモリが小さく高価で、モデルという大きな対象の置き場所が遅延を支配することである。ホストメモリは大きくてもGPUメモリは限られ、モデルが載っていないワーカーへタスクを置くと、PCIe経由の転送時間がそのまま段の開始を遅らせる。逆にモデルの在処だけを見て同じワーカーへタスクを集めると、そのワーカーのキューが伸びて過負荷になる。入力データの転送も同様で、後段を別ワーカーへ置けば中間データのネットワーク転送が入り、同居させれば待ちが発生し得る。この三つの費用、モデルの読み込み、データ転送、キューの待ちを同時に見積もる配置が必要になる。

計画の陳腐化も資源の問題である。実行時間の見積もりは外れるものであり、到着するジョブも変動する。計画を固定する方式は、見積もりと実態のずれを吸収できない。かといって中央へ毎回相談すれば、その往復と中央の処理が新しいボトルネックになる。本論文は、状態の複製コストが現代の高速な複製技術では十分に安いという前提に立ち、分散したまま全体状態を共有する道を選ぶ。共有される情報が古くなる影響自体も、感度実験の対象にしている。

## 手法のあらまし

ジョブが到着すると、まず計画段階が割り当て表を作る。データフローグラフの各タスクについて、後続タスクまでの距離と実行時間から上向きの順位を計算し、順位の高いタスクから順に、全ワーカーの中で最も早く開始できるワーカーへ割り当てる。開始時刻の見積もりには、そのワーカーのキューの完了時刻、入力データの転送完了時刻、そして必要モデルがそのワーカーのGPUキャッシュにあるか、空き容量へ読み込めるか、追い出しを伴うかが入る。実行が始まった後は動的調整段階が、全体状態の変化を見て割り当てを直す。GPUメモリ側では、先に入ったものから出す方式と、キューの先を見て今後要るモデルを残す方式を比べ、後者を採る。全体状態は共有状態表として全ワーカーへ複製され、更新頻度は調整可能で、負荷情報は新鮮さが効き、キャッシュ情報は多少古くても許容できることが実験で示される。

## 手法

### 1. 計画段階 — モデルの在処まで織り込む最も早い開始時刻の割り当て

この機構が観測するのは、ワークフローのプロファイル置き場にある静的情報、つまりタスクごとの予想実行時間、入出力の大きさ、モデルの大きさと、全体状態の監視が配る動的情報、つまり各ワーカーのキューの完了見込みとGPUキャッシュの空き容量である。保持する状態は、タスクの順位表と、タスクからワーカーへの割り当て表である。処理は、まず後続への影響が大きいタスクほど先に決まるよう、実行時間と出力転送時間と後続の順位から再帰的に順位を付け、順位の降順に、各ワーカーでの開始時刻を見積もって最小のワーカーを選ぶことである。開始時刻の内訳が本論文の固有部分で、必要モデルがキャッシュにあれば読み込みはゼロ、空きへ収まれば転送時間のみ、収まらなければ追い出しのペナルティまで加える。古典的なHEFTとの差は、HEFTが機械の負荷を見ないこと、キャッシュとデータの在処を考えないことであり、その差が高負荷での大きな遅延差として現れる。これにより減るボトルネックは、モデルの読み込み待ちと、過負荷ワーカーへの集中である。追加費用は全ワーカー分の見積もり計算であり、順位計算の多くはグラフ読み込み時に一度だけ行って保存し、実行時は更新で済ませる。誤った場合の挙動として、実行時間の見積もりが外れれば割り当ては次善になるが、それは次段の動的調整が受け止める前提である。

### 2. 動的調整段階 — 固定した計画を実行中に直す

この機構が観測するのは、実行中のワーカー状態の変化、つまりキューの伸縮、実績の実行時間、キャッシュの中身の変化である。保持する状態は現在の割り当て表と複製された全体状態である。処理は、計画段階の割り当てを初期値として、状態が大きく変わったときにタスクの行き先を組み替えることである。これにより減るボトルネックは、見積もりの外れや到着の変動によって計画が古くなることであり、除去実験では動的調整を切ると性能が大きく劣化することが示される。追加費用は状態の監視と再計算であり、中央への相談をしないため、判断は手元の複製状態で完結する。失敗条件として、複製状態の更新が遅れると古い情報で組み替えることになるが、感度実験によれば負荷情報は更新間隔200ミリ秒程度までは品質が保たれ、それを超えると劣化が進む。キャッシュ情報はモデルの入れ替え自体が稀なため、より古くても許容できるという非対称性も確認されている。

### 3. GPUキャッシュ管理 — 先のキューを見て追い出しを決める

この機構が観測するのは、各ワーカーのGPUメモリにあるモデルの集合と、そのワーカーに並ぶキューの今後のタスクが必要とするモデルである。保持する状態はキャッシュの内容と空き容量の台帳であり、全体状態の一部として他ワーカーからも見える。処理は、容量が足りないときに、単に古いものから出す先入れ先出しではなく、キューの先を見て、近い将来に使うモデルを残し、使わないモデルを追い出すことである。これにより減るボトルネックは、必要なモデルが載っていないことによる読み込み待ちであり、実験ではキャッシュヒット率99パーセントが達成された。追加費用はキューの走査と台帳の複製である。誤った場合の挙動として、先読みが外れれば残したモデルが使われず、追い出したモデルの再読み込みが起きるが、除去実験ではモデルの在処を無視する設定で遅延が8倍に悪化し、ヒット率も99パーセントから90パーセントへ落ちるため、この機構が利得の最大の源泉の一つであることが分かる。

## 評価

結論は、タスク配置とGPUメモリ管理の統合と分散化が、資源を増やさずに遅延を大きく下げる、というものである。低負荷では全方式が最適に近い中で本方式が最も最適に近く、高負荷では差が開き、翻訳と質疑応答のパイプラインでHEFTやハッシュ方式の2倍から4倍、画像説明と3次元知覚のパイプラインでは20倍から30倍速かった。後二者は実行時間自体が短いため、悪い配置の固定費用が相対的に大きく響くという読み方が論文で示される。到着率を変えた実験でも本方式が最も理想に近く、HEFTは負荷を見ないため高負荷で崩れ、JITはその場の割り当ては機敏でもジョブ内の coordination を欠いて及ばなかった。実生産トレースを再縮尺した実験でも、本方式の完了時間が最も良く、ハッシュ方式はバーストに最も弱かった。スケーラビリティのシミュレーションでは最大250ワーカーまで調べられ、同じ処理をより少ないサーバで賄える効率が示された。除去実験の内訳では、モデルの在処の考慮を外すと8倍の劣化、動的調整を切ると大きな劣化、先読みの追い出しは高負荷で有効と、利得の出所が分解されている。エネルギーとGPU利用率が同程度で遅延だけが下がるため、利得は資源の追加ではなく配置の質から来ている。

## 既存研究との差

HEFT系の計画方式との差は、負荷とモデルの在処とデータの在処を開始時刻の見積もりへ入れたことと、計画を実行中に直す動的調整を加えたことにある。中央集権のスケジューラとの差は、全体状態を複製して全ワーカーが対等に判断する分散構造であり、相談の往復をなくした。GPUメモリをキャッシュとして扱い、そのヒット率を配置の目的へ組み込んだ点も、配置とメモリ管理を別々に扱う従来の分業と異なる。

## 限界・実装状況

限界は、実機評価の規模が小さく大規模な主張がシミュレーションに依存すること、実行時間などの見積もりを与えるプロファイルが前提であること、状態情報の鮮度、特に負荷情報の更新間隔が品質を左右すること、一つのタスクは一つのサーバで走るという前提を置いていることである。実装状況は、公式コードのURLが本文で明示されていないためcodeはnullとした。通信層にRDMAとDPDKを使う実装、共有状態表の設計、シミュレータの構成は本文に記される。なおシステム名は版によりCompassとNavigatorの表記があり、本稿の題名は候補情報側のCompassを採り、本文では第1版の呼称であるNavigatorの提案として記述した。

## 一般的な実装上の含意

モデルやデータのような大きな対象の読み込みが遅延を支配する系では、配置の判断へ対象の在処を必ず入れるべきであり、それを外すだけで桁違いに悪化し得る。また、状態の複製が安くなった現在では、中央集権でしか得られないと思われていた全体最適に近い判断を、分散のまま実現できる。情報の種類ごとに許容できる古さが違う点も、監視設計の指針になる。
