# ExpertWeave：MoEのexpert直接微調整アダプタを共有配信する仮想メモリ・再ルーティング設計

## 概要

大規模な混合専門家モデル（Mixture-of-Experts、MoE）は、トークンごとに少数のexpertだけを実行する。特定用途向けの軽量微調整にはLoRAが広く用いられるが、MoEでは重要なexpertの重みそのものを選択的に更新する **Expert-Specialized Fine-Tuning（ESFT）** もある。ESFTでは、層ごと・タスクごとに微調整されたexpertの個数と位置が異なる。従来のLoRA配信は基盤重みに低ランク差分を加算する設計であり、ESFTで必要な「routerが選んだ元expertを、タスク固有の別重みに差し替える」動作には直接対応しない。

ExpertWeaveは、**基盤MoEを一つだけ共有し、複数ESFTアダプタのexpert重みを動的に差し替えて同時配信する**。設計の核は、仮想アドレス上だけで連続したexpert重みテンソルを用意し、実際に存在するexpertだけに物理メモリを割り当てる仕組みと、MoE routerが返したexpert番号をトークン単位で差し替える融合rerouting演算子である。これにより既存のGrouped Matrix Multiplication（GMM）を改造せず、異なるESFTアダプタのトークンを一つのバッチで処理できる。

著者らは16BのMoE基盤モデルと10種類の実ESFTアダプタを用い、Ascend NPU上のvLLM-Ascendで検証した。単一64GB NPUで二つのアダプタを扱う際、個別mergedモデル方式のKVキャッシュ容量約6K tokensに対し、ExpertWeaveは572K tokens超を確保した。融合reroutingの追加遅延はmicrobenchmarkで1%未満、複数アダプタのオンライン配信ではbase-only方式よりTPOTが概ね4〜11%長い。これは**全条件で高速になる技術ではなく、モデル共有とアダプタの正確な切替を小さな実行時費用で実現する技術**である。

## 問題設定と前提

### ESFTはLoRAの低ランク差分とは違う

一般的なLoRAは重み行列 `W` に小さい低ランク更新 `A_i B_i` を加え、アダプタiの出力を `xW + xA_iB_i` として計算する。PunicaやS-LoRAはこの加算構造を利用し、アダプタごとの小行列を効率よくバッチ処理する。対してESFTは、学習データのrouter活性からタスクに重要なexpertを選び、選ばれたexpertの重みを直接微調整する。原著の説明では、関連度の累積が閾値pを超えるまで上位expertを選択するため、ある層で3個、別の層で7個という不均一な更新集合が生じる。router自体は更新しない。

MoEの通常推論では、routerが各トークンに対してtop-kの基盤expert番号を出力し、token dispatchが同じexpertに向かうトークンをまとめる。expert重みは概念的に `[M,H_out,H_in]` の3次元テンソルへ積み、GMMがまとめて実行する。ESFTでアダプタiがexpert jを更新していたら、そのトークンに限ってexpert jの**更新済み重み**を使用し、未更新なら基盤expert jを使用する必要がある。複数アダプタが同居すると、同じ元expert番号でもトークンのアダプタIDにより参照先が異なる。

### なぜ素朴な重み配置は破綻するか

独立したアダプタ用テンソルを別途作ると、GMM側が基盤重みとアダプタ重みの二つのテンソルを読めるように改造しなければならない。既存の高性能GMMを変更しないため、全expertを単一テンソルへ並べる方法もあるが、アダプタごとに最大expert数 `E_max` 分の領域を**全層で**予約すると、実際には存在しないexpertにも物理メモリを浪費する。N個のアダプタを扱うと論理形状は `[M + N E_max,H_out,H_in]` となる。

原著Table 1の10アダプタでは、層ごとの最大expert数が13、平均expert数はアダプタにより3.85〜9.50と不均一である。例えば `gate-translation` は最大13個に対し平均4.69個、同アダプタ内のパディング率は0.64である。著者の定義する全アダプタ同居時のメモリ断片化係数は `F_mem=1.51` で、単純パディングなら必要量より51%大きい確保量になる。KVキャッシュと競合するNPUメモリでこの無駄は無視できない。

## 手法

### 1. 連続した仮想expert重みテンソルと物理ページの分離

ExpertWeaveはGMMから見えるexpertテンソルの**仮想アドレス空間**を最初に連続予約するが、未使用領域へ物理ページを割り当てない。基盤expert数をM、アダプタiの予約開始expert番号を `Δ_i = M + i E_max`、層lで実際に存在する微調整expert数を `e_i^(l)` とする。論理上のアダプタ領域は `[Δ_i, Δ_i+E_max)` だが、物理ページを対応付けるのは `[Δ_i, Δ_i+e_i^(l))` の部分だけである。これならGMMの入力ポインタと添字規則は通常の連続テンソルと同じまま、未使用パディングには実メモリを使わない。

NPUごとに物理メモリプールを置き、固定粒度（論文の例は2MB）のページを確保・再利用する。各仮想テンソルに付随するexpert memory managerは、アダプタのロード時に必要なページをプールから受け取り、対応する仮想範囲へマッピングしてから重みをコピーする。アンロード時は逆にアンマップしてページをプールへ戻す。AscendCLの `aclrtReserveMemAddress`、`aclrtMallocPhysical`、`aclrtMapMem`、`aclrtUnmapMem`、`aclrtFreePhysical` を使用する。つまり**予約した仮想容量と、実際にKVキャッシュを圧迫する物理容量を切り離す**ことが肝要である。

### 2. expert境界と物理ページ境界の不一致を吸収

expert一個分の重みサイズがページサイズの整数倍とは限らない。各アダプタを必ずページ境界から配置すると、最後のページの未使用部分が蓄積し、仮想パディングをなくしても内部断片化が残る。さらに隣接するアダプタの先頭がページ境界と一致しない場合、単純なページ所有権管理ではマッピングの衝突や誤解放が起きる。

ExpertWeaveはexpertとページの対応関係を追跡し、部分使用ページの残りを後続アダプタが使えるsub-page allocationを実装する。参照カウントによって、共有されたページを一方のアダプタのアンロード時に早まって解放しない。原著Figure 3では、1 expertが1.5ページ相当を占める例を使い、2 expertに3ページをマップし、別アダプタの境界と部分ページを調整する様子を示す。仮想的な連続性と物理的なページ再利用を両立するには、この境界処理まで必要である。

### 3. ESFT expert mapによるトークン単位のrerouting

層lごとに `Π^(l)` という `[N,M]` の整数マップを持つ。`Π^(l)[i,j]` は、アダプタiで基盤expert jが未更新ならj、更新済みならそのexpertを置いた仮想テンソル中の位置 `Δ_i + δ_ij^(l)` を返す。要求が到着するとアダプタID（AID）を各トークンへ付与し、基盤モデル要求には特別な値−1を使う。MoE routerが出すtop-kの元expert番号に対し、`TopK'(x) = {Π^(l)[A(x),j] : j ∈ TopK(x)}` を適用して番号だけを差し替える。

重要なのは、**routerのスコア計算、token dispatch、GMMのexpert計算を変更しない**点である。routerが選んだexpert jを「同じ機能のタスク別微調整版」へ向け直すだけなので、ESFTの意味論を保ったまま、別アダプタのトークンを同一バッチへ混ぜられる。未更新expertは基盤モデルの重みを共有し続ける。原著Figure 4はM=64、top-k=6、アダプタ2個、予約最大8 expertの具体例を示す。

### 4. reroutingを融合演算子にしてprefillの起動費を抑える

AID配列のbroadcast、マップ内offset計算、gatherを個別のPyTorch演算として実行すると、トークンが多いprefillで複数カーネル起動とデータコピーが生じる。そこで著者はAscend NPUのvector coreを用い、これらを一つの融合reroutingカーネルへまとめる。これは各MoE層のrouter出力とGMMの間で動き、変更済みtop-k配列をGMMへ渡す。オンラインのcontinuous batchingやchunked prefillでもトークン単位のAIDが保持されるため、異なるアダプタ要求の混合を妨げない。

処理全体は、(1)要求ごとのAIDをバッチへ添付、(2)通常のMoE routerでtop-k選択、(3)融合reroutingでアダプタ固有expert番号へ置換、(4)仮想重みテンソル上の既存GMMを実行、(5)通常のMoE出力統合、となる。物理ページ管理はロード／アンロード時、reroutingは推論時の各MoE層で行う。後者のオーバーヘッドを小さくしなければメモリ節約がスループット悪化で相殺されるため、融合は重要な設計要件である。

## 評価

### 複数アダプタのオンライン配信

8 NPU、TP=8/EP=8で、5・10・20アダプタを同時提供した。均等負荷（α=1）ではBase-only比のTTFT追加負担が5アダプタで約8%、20アダプタで約11%。TPOTの追加負担はアダプタ数に応じて概ね4〜11%で、prefill throughputの変動は2%未満だった。α=0.3および0.1の偏った到着率でも定性的な傾向は同様である。Base-onlyはタスク別ESFTを使っていないため、これは「同一精度条件での性能比較」ではなく**アダプタ切替に要する追加コストの評価**である。

別の比較では、ExpertWeaveが2 NPU（TP=2/EP=2）を共有し、mergedモデル2インスタンスがそれぞれ2 NPU、合計4 NPUを使う。両者の総メモリ消費を近づけるため、ExpertWeaveは各NPUの90%、merged側は各インスタンス45%のメモリ利用率を設定した。アダプタはgate-mathとgate-intent、合計到着率10 req/s、負荷偏りを変化させる。**NPU台数は揃っていない**ことを明示した上で、ExpertWeaveはprefill throughputを約7〜14%、decode throughputを約14〜18%改善した。理由は、独立インスタンスでは人気アダプタ側のNPUだけが飽和し、低人気側が遊ぶのに対し、共有バッチなら全NPUを両サービスに使えるためである。

### 微視的評価・メモリ容量・精度

| 評価 | 条件・比較対象 | 数値と解釈 |

| KV容量・3アダプタ | 64GB NPU | merged方式は約88GB超でOOM、ExpertWeaveは477K tokensのKV容量を維持 |

メモリ実験でいう「94.4倍」は、**個別mergedモデルを2個常駐させた場合に残るKV容量が約6Kしかない**という比較条件に依存する。基盤モデル1個を提供する場合の810K tokensと比べてExpertWeaveの572K tokensが大きいわけではない。またKV容量が増えても、到着率やモデル・バッチによってdecode throughputが比例して増えるとは限らない。GSM8Kと意図認識で同じ精度を得たことは、ESFT expertの参照先が正しく切り替わっていることの機能検証であり、未評価タスクまで無劣化を保証しない。

## 既存研究との差

PunicaとS-LoRAは、LoRAの低ランク行列をバッチ化して加算することに最適化されている。ExpertWeaveはLoRAの加算を速くするのではなく、**MoE expert自体の差し替え**を、既存GMMを変更せずに実行する。したがってメモリ管理の単位もLoRA行列やKVページではなく、層ごとに存在数が変わるexpert重みである。ESFTがrouterを更新しないことを利用して、元expert番号の置換だけで正しい微調整expertへ誘導できる。

MoEのオフロード系研究はexpertをCPU/SSDから呼び出す転送遅延を中心に扱うことが多いが、ExpertWeaveは**複数の異なるESFTモデルを同じNPUで共存させる**ための仮想メモリと実行経路を設計する。単一モデルのexpertのキャッシュ命中率改善とは目的が異なり、アダプタごとに層別expert数が違うことによるパディング断片化を直接対象にする。

## 限界・実装状況

本論文の評価基盤はAscend NPUであり、仮想メモリAPIと融合reroutingカーネルはAscendCLの仕組みに依存する。CUDA GPUやCPUの一般的なvLLMへそのまま移植できることは実証されていない。ベースモデルは16Bの一系列、実ESFTアダプタは5領域10種類（20アダプタ実験では複製を使用）であり、異なるexpert配置・大規模MoE・多数同時更新の挙動は追加検証が必要である。

また、アダプタ数増加時のTTFT/TPOTには4〜11%程度の追加負担があり、base-onlyより常に速いわけではない。融合しないreroutingの29%悪化は、各MoE層で追加演算を行う設計の危険を示す。mergedモデルとの性能比較はNPU台数・メモリ配分が異なるため、同一ハードウェア条件での純粋な速度差とは区別する。Poisson到着の100秒トレースは実運用の長期障害、急激なアダプタ入替、複雑なメモリ断片化履歴を十分に表さない可能性がある。論文v1は公式コードを「近日公開」としており、今回の一次資料から公開済みリポジトリを確認できない。
