## 概要

複数GPUで大規模言語モデルを実行すると、各GPUでの行列積・注意計算だけでなく、分割した入力や出力の集約・再配布が必要になる。一般的な実装は計算カーネルとNCCL通信を別々に起動し、別CUDAストリームで重畳する。しかし計算がまとまった出力を完成するまで通信を始められない場合、演算の途中で生じる細かな待ち時間を隠せない。計算と通信を一つの融合カーネルへまとめても、従来方式の多くは単一NVLink領域に限られる。

mKernelは、ノード内のNVLink/NVSwitchとノード間RDMAを、計算タイルの準備完了に合わせて同時進行させるライブラリである。永続GPUカーネル内のSMを計算と通信に役割分担し、残作業量と観測した処理時間から役割数を変える。ノード間転送はGPUがホスト共有リングへ小さな命令を発行し、CPUプロキシがRDMA verbsでNICへ送る。データ本体は登録済みGPUメモリからNICが直接読み書きし、CPUでコピーしない。

2ノード×8基H200のConnectX-7とAWS EFAの2環境で、GEMM+AllReduceは非融合cuBLAS+NCCL比最大1.72倍、Ring Attentionは最大1.88倍、AllGather+GEMMは最大1.41倍の速度改善を報告する。対象は分散カーネル単体であり、モデル全体のトークン生成速度が同じ倍率で改善することを意味しない。また、SM動的配分の検証は単一ノードであり、ノード間実行時の動的制御効果を同じ条件で直接検証したものではない。

## 問題設定とボトルネック

テンソル並列では、入力を集めてGEMMするAllGather+GEMM、GEMM出力を全GPUへ共有するGEMM+AllReduce、部分出力を分散させるGEMM+ReduceScatterなどが頻繁に現れる。シーケンス並列のRing Attentionでは、K/Vの分割片をGPU間で循環させながら局所的な注意を計算する。MoEのエキスパート並列では、トークンを担当エキスパートへ転送してから各GEMMを実行する。これらは通信の方向・データ依存関係が異なる。

ノード内はNVLink/NVSwitchが高速であるのに対し、ノード間ネットワークは帯域・レイテンシの制約が大きい。すべてのGPUから同じデータを別ノードへ送ると、遅いネットワーク上で重複した転送が生じる。逆に転送単位を小さくし過ぎると、NICへの命令発行と完了通知が支配的になる。局所計算タイル、ノード間転送チャンク、ホストプロキシへの命令束の大きさを独立に設計する必要がある。

また、計算SMと通信SMの配分を固定すると、入力サイズによって通信が律速になったり、計算資源が不足したりする。GPU内の通信を担当するSMが少なすぎれば計算が入力待ちで止まり、通信に割り当て過ぎればGEMMの並列度が下がる。最適な配分はカーネルごとだけでなく、同じカーネルの実行途中でも残作業量によって変化する。

## 手法

### 1. タイル単位の永続カーネルとSM役割分担

mKernelは通常の「GEMM完了→通信カーネル起動」という順序ではなく、永続カーネルの内部でタイル単位の計算と転送を進める。スレッドブロックに計算役、NVSwitchを使うノード内通信役、RDMAへデータを渡す通信役を割り当てる。計算側が一部タイルを完成した時点で準備完了フラグを立て、通信側は必要なタイルが揃ったチャンクから転送する。

同じGPUのSM資源を計算・通信に分けるため、通信を専用カーネルとして後から起動する必要がない。計算側は次のタイルを処理する間に通信側が前のタイルを送る。転送が入力を供給するタイプでは、到着したタイルからGEMMを始め、未到着のタイルを待つ間に別の利用可能なタイルを処理する。データ依存関係に合わせて処理順序を変える点が、単なる二ストリーム重畳との違いである。

### 2. 階層的な通信経路とレールピア

ノード内ではNVSwitchの集約・複製機能を利用し、別ノードへ送る前に局所で部分結果をまとめる。GEMM+AllReduceでは各GPUの出力をノード内で縮約し、ノード間では各GPUが結果の1/8だけを送るように分担する。受信後にノード内へ複製することで、各GPUが全結果をノード間で重複転送する構造を避ける。

AllGather+GEMMでは、各入力シャードを宛先ノードへ一度だけ送り、ノード内ではマルチキャストで各GPUへ共有する。GEMM側は最初に自GPUのシャード、次に同ノードのシャード、最後に遠隔シャードを処理し、到着待ちを減らす。Ring AttentionでもK/V片をノード間で必要以上に複製せず、ノード内のGPU間循環と組み合わせる。ノード間で送るチャンクの粒度は、計算タイルの粒度と必ずしも一致させない。

### 3. GPU発行・CPUプロキシ経由のRDMA

GPUの通信ブロックは、転送先、送信元・宛先のオフセット、バイト数、チャンク識別子を含む48バイトの命令を、ピン留めされたホストメモリ上のリングバッファへ書き込む。GPUは命令本体を書いた後でヘッダを確定し、CPUプロキシはヘッダを確認してからRDMA verbsを使ってNICへ転送を発行する。キューのクレジットと未完了要求数に上限を設け、NICへ無制限に投入しない。

CPUプロキシは準備できた命令を最大8件程度まとめて投入する。ただし、8件揃うまで必ず待つわけではなく、短い収集時間の後に部分バッチを送る。これにより小さなタイルが到着するたびのホスト発行費用を減らしながら、最後の少数チャンクが過度に待たされることを防ぐ。命令のバッチ化とネットワークチャンク自体の大きさを分離している。

ConnectX-7のInfiniBandでは、同一信頼接続内でデータ書込みに続いてフラグ書込みを発行し、受信GPUがフラグを見て完了を判定する。AWS EFAのSRDでは独立した書込み間の順序が保証されないため、write-with-immediateの完了を受信プロキシが確認してからGPUメモリ上の到着フラグを公開する。通信路によって異なる完了通知を抽象化し、同じ融合カーネルをInfiniBandとEFAの両方で使えるようにする。

### 4. SM配分の動的制御

静的配分では、例えば通信SMを2、4、8、16、32、64のように変え、カーネルごと・入力サイズごとに最良値を探す必要がある。mKernelは各ブロックのサイクルカウンタから計算タスクと通信タスクの単位費用を推定し、残りの計算タスク数・通信タスク数に応じて、両側の予想完了時間が近づくよう通信SMの目標数を更新する。

計算ブロック・通信ブロックはタイルやメッセージの境界で共有目標値を読み、自分の役割を切り替える。通信が入力を供給する場合には、入力待ちで止まった計算ブロックが一時的に通信を支援する。こうしてGEMMがほぼ終わった後は通信にSMを多く回すなど、実行中の律速の変化に追従する。これはワープ構成そのものを動的に作り直す方式ではなく、ブロックの役割を変える方式である。

### 5. 実装した5種類の融合カーネル

| 分野 | カーネル | 主なデータ依存 | 論文の代表的な転送単位 |
|---|---|---|---|
| テンソル並列 | AllGather+GEMM | 入力通信→計算 | 入力128行 |
| テンソル並列 | GEMM+ReduceScatter | 計算→通信 | 2〜32タイル |
| テンソル並列 | GEMM+AllReduce | 計算→通信 | 4タイル、約256KiB |
| エキスパート並列 | MoE Dispatch+GEMM | トークン通信→計算 | 16トークン、512KB |
| シーケンス並列 | Ring Attention | 各段でK/V転送と計算 | K/Vの128行タイル |

AllGather+GEMMは遠隔入力の到着を待つ順序を工夫し、GEMM+ReduceScatterは所有者のバッファへTMAの原子的加算を行う。MoE Dispatch+GEMMはエキスパートへ送るトークンをネットワークチャンクへまとめ、受信したトークンをGEMMへ供給する。Ring Attentionは各GPUのK/V片を循環させつつ注意を計算する。五つのカーネルは同じ通信基盤を使うが、タイル準備完了と転送開始の依存条件は個別に定義される。

## 評価

### 実機環境と比較対象

| 項目 | 条件 |
|---|---|
| EFAクラスタ | 2ノード×8基H200、ノード間AWS EFA、各ノード16×200Gb/s NIC |
| ConnectX-7クラスタ | 2ノード×8基H200、ノード間InfiniBand、各ノード8×400Gb/s NIC |
| ノード内 | NVLink/NVSwitch |
| 公称ネットワーク | 両クラスタともGPU当たり400Gb/s相当 |
| ソフトウェア | CUDA 12.9、Hopper sm_90a、GPUごとに1プロセス |
| 主な非融合比較 | cuBLAS GEMMまたはFlashAttentionとNCCL collectiveの組合せ |
| 追加比較 | Triton-distributed、FLUX、Mercury、DeepEP+DeepGEMM、MagiAttention、ring-flash-attention |
| 測定 | ウォームアップ後、全rankで最も遅いrankの時間を採用。複数起動を連続計測し最後に同期 |

ここでの性能はH200クラスタで測定した分散カーネルの実行時間またはGPU当たりTFLOPSであり、LLMの生成tokens/sではない。モデル全体の推論要求でどの程度の時間がこれらのカーネルに使われるかによって、エンドツーエンドの利得は変わる。

### カーネル別の主要結果

| 対象 | EFAの改善 | ConnectX-7の改善 | 比較対象・注意 |
|---|---|---|---|
| AllGather+GEMM | 最大1.41倍 | 最大1.34倍 | cuBLAS+NCCL |
| GEMM+AllReduce | 最大1.53倍 | 最大1.72倍 | cuBLAS+NCCL |
| GEMM+ReduceScatter | 大きな問題で1.02〜1.27倍 | 条件依存 | M≥16Kでの非融合比較 |
| MoE Dispatch+GEMM | 3.1〜4.5倍 | 条件依存 | all-to-all後にGEMMする基準。計算編成差を含む |
| Ring Attention | 最大1.78倍 | 最大1.88倍 | FlashAttention+NCCLの非融合比較 |

GEMM+AllReduceの最大1.72倍は、NVSwitch内で局所縮約し、ノード間では各GPUが出力の1/8を送る階層的な通信によって、転送量と計算待ちを同時に減らした結果である。AllGather+GEMMの最大1.41倍は、遠隔シャードをノード単位で一度送ることと、利用可能な入力からGEMMを進めることに対応する。いずれも「通信カーネルを一つ減らした」だけではなく、ネットワークへ送るデータ量とタイミングを変えている。

Ring Attentionは短いシーケンスで特に利得が大きく、通信を計算で隠しにくい領域で融合の効果が現れる。追加比較ではMagiAttention比1.4〜3.3倍、ring-flash-attention比2.3〜5.6倍、Mercury比2.2〜8.6倍、Triton-distributed比1.1〜1.7倍と報告される。ただし各実装が対応する形状・環境は同一ではなく、Triton-distributedの評価版は最長シーケンスで実行失敗している。未実行条件を速度ゼロとして倍率へ混ぜてはいけない。

MoE Dispatch+GEMMのEFAでの3.1〜4.5倍は大きいが、非融合比較は均等なルーティングを仮定し、エキスパートGEMMのグループ化を行わない。したがって通信重畳だけの純粋な効果ではなく、エキスパート計算の編成改善を含む。さらに論文で評価したDeepEP+DeepGEMM実装はEFAに対応しないため、EFA図にある同方式の棒はConnectX-7での測定を参照として表示したもの。異なるネットワーク上の棒を直接比較する際はこの制約を明記する。

### 動的SM配分と感度評価

通信SM数を静的に変えると、最良値は入力形状・カーネルに応じて2〜64の範囲で変わる。通信SMが不足したAllReduceでは、最悪の静的配分が最良配分の約25倍遅い例もある。逆に通信SMを過剰にするとGEMMの計算SMが不足する。したがって単一の固定SM数をすべてのカーネルに適用するのは不適切である。

GPU上の動的制御器は、21の構成に対して静的最良配分との比較で幾何平均1.18倍の改善を報告する。GEMM+AllReduceの例では計算タスクが先に終わると通信SM目標が増え、最後には残る通信作業へSMを集中する。MoE Dispatch+GEMMでは計算・通信の残作業に応じて目標を更新する。ただし、著者はテストベッド制約から動的SM制御の測定を単一ノードに限定している。16GPUのノード間環境で同じ改善を直接測定したわけではない。

### GPUDirect Asyncとの比較と負の結果

ConnectX-7環境では、GPUからNICへ直接発行するGPUDirect Async（IBGDA）も実装し、CPUプロキシ経由のGPU発行方式と比較した。論文はIBGDAに一貫したスループット上の優位が見られなかったと報告する。すなわち「CPUプロキシを完全に除けば必ず速い」という単純な仮説は支持されない。重要なのはチャンク準備時点、NIC発行のバッチ化、転送完了の通知といった通信経路全体の設計である。

GEMM+ReduceScatterでは利得が大きな入力に偏り、小さな入力に対して常に大幅な改善を示すわけではない。Ring Attentionでは比較実装の一部が長いシーケンスを処理できない。MoEでは基準の演算構成が異なる。これらは本方式の一般性を評価する際に省略してはならない条件である。

## 既存研究との差

従来のNCCLと計算カーネルの別ストリーム重畳は、演算単位の依存が残り、計算タイルが完成した直後の小さな通信機会を活用しにくい。FLUXやTriton-distributed、Mercuryなどは通信融合やタイル単位の処理を進めてきたが、ノード間RDMAの経路や通信完了の保証、SMの役割調整を統合するには追加の工夫が必要だった。

mKernelはノード内とノード間を分けて転送を階層化し、計算タイル、ネットワークチャンク、NIC命令束を異なる粒度で扱う。さらにInfiniBandとEFAの完了通知の違いを吸収し、同じ永続カーネルからGPU発行・CPUプロキシ経由の通信を実行する。SM動的制御は、事前に固定した最適配分だけでなく、カーネルの実行中に計算と通信の残作業が変わることへ対応する。

## 限界と再現性

評価対象は16基H200、2ノードの高帯域クラスタであり、さらに大きなノード数、低帯域ネットワーク、異種GPU、障害・輻輳を含む運用環境での利得は直接実証していない。論文は二ノードを超える転送でリング転送を想定するが、二ノード測定を多数ノードへそのまま外挿することはできない。

5カーネルは分散学習・推論の双方に使えるが、ベンチマークは主にカーネルの計算・通信性能である。LLMのデコード遅延、KVキャッシュ容量、トークン生成の品質、モデル全体の電力効率は独立したエンドツーエンド測定として提示されていない。カーネル単体1.72倍がモデル全体の生成速度1.72倍を意味しない。

動的SM配分の実験は単一ノードであり、ノード間のネットワーク変動に追従する効果の一般化には注意が必要である。GPU発行・CPUプロキシ方式はCPU負荷やピン留めメモリ、キュー管理の費用を伴い、極端に小さなメッセージやホスト負荷が高い環境では別の律速が生じ得る。EFAとInfiniBandで異なる完了通知を必要とする点も実装複雑性の一部である。

MoE dispatchの高倍率は基準のエキスパート計算編成差を含み、DeepEPのEFA非対応のため比較環境が一致しない箇所がある。異なるカーネルや比較方式の最大値を合算したり、全入力形状の平均倍率として扱ったりしてはならない。著者公式リポジトリは公開されているが、第三者追試や全ハードウェアでの再現性は本稿では確認していない。

## 主要結果の解釈

mKernelの主要な貢献は、ノード内GPU通信とノード間RDMAを「演算が終わった後の別処理」ではなく、計算タイルの準備完了に従う同時進行の仕事として設計したことにある。階層的なデータ移動で遅いネットワークへの重複転送を抑え、SM役割の調整で計算・通信の律速が変わる状況へ対応する。GPUが発行した転送をCPUプロキシがNICへまとめて渡す方式でも、IBGDAとほぼ同等の性能を得たことは実装上の有用な知見である。

実務では、対象モデルの実行時間のうちどの分散カーネルが律速か、ノード間帯域とトポロジー、MoEルーティングの偏り、通信チャンク粒度、SM配分の変化を測定して導入するべきである。カーネル性能の改善をモデル全体の速度・費用の改善へ結び付けるには、別途エンドツーエンド測定が必要である。
