# LightSeq：Transformer推論を演算融合・候補選択・メモリ再利用で高速化する

## 概要

LightSeqは、可変長の系列を扱うTransformer系モデルをGPU上で高速に推論するためのライブラリである。一般的な学習フレームワークでは細粒度の演算を順次呼び出すため、各GPUカーネルの起動や中間テンソルの書込み・読込みが推論遅延を押し上げる。文章生成では語彙全体から少数候補を選ぶ探索と、可変長テンソルを繰り返し確保する費用も加わる。LightSeqは行列積の間の演算融合、階層型自己回帰探索（Hierarchical Auto Regressive Search; HARS）、中間テンソルのGPUメモリ再利用を一つの実行基盤にまとめる。

原著は2021年のNAACL産業トラックで報告された。Tesla P4/T4上でTensorFlow、PyTorch、FasterTransformerと比較し、機械翻訳などの測定条件でTensorFlow比最大14倍、FasterTransformer比最大1.4倍の高速化を示す。T4半精度では実行時間に占める一般行列積（General Matrix Multiplication; GEMM）の割合がTensorFlowの24.5%からLightSeqの87.0%へ上昇した。これは演算以外の起動・データ移動費用が減ったことを示す時間内訳であり、GPU稼働率が87%になったという意味ではない。

2021年当時のTransformer baseを中心とする研究であり、現在の大規模生成モデル、長文脈のKVキャッシュ、複数GPUの連続バッチ推論を直接比較したものではない。一方、推論の律速が行列積そのものではなく周辺処理へ移るというシステム上の問題を、具体的なカーネル構成と実測で説明した基礎的な実装研究である。

## 問題設定

Transformerの注意層やフィードフォワード層では、行列積の前後に正規化、残差加算、形状変換、活性化、Softmaxが挟まる。汎用フレームワークでそれぞれを独立カーネルとして実行すると、GPU上の中間配列をメモリへ書き戻して次のカーネルが読み直す。小バッチ・短系列では行列積自体の計算時間が短いため、カーネル起動と中間データ転送が相対的に大きくなる。自動微分を支える汎用性は学習時には必要だが、推論専用経路では不要な費用を残しやすい。

自己回帰生成では、各ビームから語彙全体の次トークン確率を計算し、最もよい少数の候補だけを残す。語彙が数万規模なら、採用しない大多数の候補にも確率計算と並べ替えの費用を支払う。原著はTransformer baseで出力側の確率計算と上位候補選択が遅延の約30%を占める例を示している。

さらに、入力長、生成長、ビーム幅が要求ごとに変わると、一時テンソルの形状も変わる。推論中にGPUメモリを確保・解放し続ければ割当て費用と断片化が生じる。LightSeqは、計算を融合するだけでなく、出力側の探索とテンソルの生存期間も設計対象とする。

## 手法

### 1. 行列積間の演算融合

重い線形変換はcuBLASのGEMMを利用し、その間の軽量な処理を専用CUDAカーネルへ統合する。例えばTensorFlowによる層正規化では、平均と分散を求めて結果を変換するために三回のカーネル起動と二つの中間結果が必要になる場合がある。LightSeqはこれらを一回のカーネルへまとめ、中間値を外部メモリへ往復させない。

原著図2のTransformer符号器層は、問い合わせ・鍵・値の射影、注意重みの積、Softmax、値との積、出力射影、フィードフォワード演算を含む。LightSeqはGEMM間の正規化・残差・形状変換などをまとめ、符号器一層を六つのGEMMと六つの専用カーネルで構成する。一般的な細粒度の実装に対しカーネル起動数を約四分の一以下に抑えると報告する。重要なのはモデルの行列積の数学的計算量を消したのではなく、周辺の起動と中間データの入出力を減らした点である。

融合を進めると、GEMM以外の時間が小さくなり、次にGEMMが主要な律速になる。融合カーネルを大きくするほどレジスタや共有メモリの制約も強くなり得るため、別のGPU世代や層形状で最適な融合境界が同じとは限らない。

### 2. 階層型自己回帰探索 HARS

通常のビーム探索では、全語彙に対してSoftmaxの条件付き確率を計算して中間結果を保存し、その結果を読み出して上位のビーム・トークン対を選ぶ。LightSeqは「まず粗く候補を拾い、少数だけを詳しく順位付けする」という二段階へ変える。

具体的には各ビームのlogit列をk群に分割し、群iの最大値を `m_i` とする。これらの最小値 `R = min_i m_i` を粗い閾値に用い、`R` より大きいlogitだけを抽出する。各群には最大値が存在するため、上位候補を含む小集合を高速に選びやすい。抽出を一つのGPUカーネルで実行した後、残った数十候補へ確率計算と上位選択を適用する。語彙全体に重い後処理をかける方式より中間メモリ転送を減らせる。

原著図3はビーム幅2、語彙数8の簡単な例で、この粗い抽出と再順位付けの流れを示す。実際の語彙は数万規模であり、最終的な選択候補数が小さいほど節約効果が大きい。ただし、数値丸め、同点候補、確率の正規化まで含めた厳密な出力一致は論文の性能表だけでは証明されないため、実装移植時には確認が必要である。

### 3. 動的GPUメモリの再利用

LightSeqはサービス開始時に最大系列長などの上限形状を設定し、中間結果に必要な最大領域を見積もって確保する。さらに、計算依存関係上同時に存在しないテンソルには同じGPUメモリ領域を割り当てる。ある演算が終わり、結果をもう参照しないなら、その領域を別の演算の一時バッファとして再利用できる。

この方法は実行中の割当て呼び出しを減らすだけでなく、複数モデルを同時配置する際の容量にも効く。原著はT4で、バッチ8、系列長256、ビーム幅4、語彙3万の条件でTransformer bigモデルを最大8個配置できた例を示す。ここでの「8個」は同時配置可能なモデル数であって、単一モデルの推論速度が8倍になったという意味ではない。最大系列長を事前設定する方式なので、上限を超える入力への対応や、過大な事前確保の無駄も設計上の注意点となる。

## 評価

原著の評価はGPU世代、数値精度、バッチ、系列長、生成方式を区別している。機械翻訳にはWMT14英独翻訳を用い、Transformer baseに近い構成で両言語の語彙を各5万サブワードに設定する。生成のサンプリング実験は無作為初期化したTransformerと合成データを用いるため、生成品質の改善を主張する根拠ではない。FasterTransformerとの比較は当時のv2.1を基準とし、現在の推論エンジンと比較したものではない。図5・図6は主にTensorFlowを1とした相対速度の曲線であり、掲載されていない絶対ミリ秒値を補完してはならない。

評価を読む際には、三つの異なる効果を分離する必要がある。第一に、融合によって実行するカーネル数が減り、細かな処理のための起動とメモリ往復が減る。第二に、階層型探索によって語彙全体に高価な候補選択を適用する必要が減る。第三に、中間領域の再利用によってGPUメモリの確保回数と占有量が減る。これらは相互に関係するが、同じ測定値で一括して証明できるわけではない。例えば行列積の時間比率が増えたことは第一の効果と整合するが、同時配置できるモデル数の増加は主に第三の効果である。さらに翻訳のビーム探索と生成の確率的サンプリングでは第二の効果の大きさが変わる。原著の図ごとに比較対象と測定条件を確認することが重要である。

### 演算時間の構成要素

図4ではTensorFlow半精度の内訳がGEMM24.5%、型変換39.7%、上位候補選択3.2%、要素加算2.5%、その他30.1%である。LightSeq半精度はGEMM87.0%、キャッシュ更新6.4%、層正規化3.6%、HARS2.9%、その他0.1%となる。これは、汎用実装で多数の独立カーネルを呼ぶ周辺処理が減り、相対的に行列積の割合が増えたことを示す。原著はTensorFlow側で80種類以上のGPUカーネルを呼ぶことにも触れ、型変換の融合などが改善要因と説明している。

GEMM割合が大きくなったことは、GEMM自体が高速化したという証明ではない。総時間が減った結果、残る主要演算の構成比が増えたと読むべきである。LightSeq単精度ではGEMM82.0%、キャッシュ更新10.1%、層正規化3.0%、HARS2.6%、その他2.3%であり、半精度ではキャッシュ更新の比率が低い。これは扱うデータ量の差と整合するが、原著は単一要因としての因果を切り分けてはいない。

### バッチと系列長による性能の違い

図5のビーム探索では、P4単精度・T4半精度とも多くの条件でLightSeqがFasterTransformerを上回る。原著の本文は、小バッチではFasterTransformerが有利になる条件がある一方、バッチと系列が大きいと差が広がることも指摘する。TensorFlow比の改善は短い系列や小バッチで特に大きい傾向があり、起動と中間データ移動が全体時間の多くを占める領域で融合の効果が目立つ。

図6のサンプリングでは、T4半精度、top-p=0.75またはtop-k=32で比較する。LightSeqがFasterTransformerより速い点は多いが、全てのバッチと系列で優位とは限らない。ビーム探索よりサンプリングの後処理は単純なため、HARSの寄与を同じ大きさと仮定できない。原著は、最適化後の時間の80～90%がGEMMに費やされる状況では、周辺処理をさらに融合するよりGEMM最適化が今後の焦点になると述べている。

### 生成方式の違いが改善倍率へ及ぼす影響

機械翻訳のビーム探索では、語彙全体の確率計算と上位候補選択が負担になりやすい。そのため、候補を絞ってから再順位付けするHARSの削減対象が大きい。一方、生成のtop-k・top-pサンプリングでは選択する候補の扱いが異なり、原著図6は機械翻訳の図5ほど大きな改善倍率を示さない。論文は、T4半精度の生成実験で小バッチ・短系列ではLightSeqが有利である一方、大バッチ・長系列ではFasterTransformerが優位になる条件を報告している。これは同じ融合・メモリ再利用の設計でも、生成方式と実行形状によって律速が変わることを示す。

原著が示すGEMM時間比率の増大も同様に解釈する必要がある。非GEMMの費用を減らした後は、行列積を速くすることが次の改善の中心となる。行列積が支配的な条件では周辺演算の追加融合だけでは速度向上に上限がある。論文末尾は整数演算のみを使う推論や疎な行列積を今後の研究方向として挙げるが、それらをLightSeqの2021年実測結果として数えてはならない。

### 比較対象の範囲

TurboTransformersは原著時点で生成に必要な探索やキャッシュ更新を十分にサポートしておらず、完全な機械翻訳の同条件比較から外されている。限定的なデコーダ層だけの測定で約2倍の高速化が示されても、それを翻訳全体の性能差として使うことはできない。またWMT14を利用したという事実は、翻訳品質のBLEU値が改善したことを意味しない。論文の主眼は推論時間とメモリ使用である。

## 先行研究との差

FasterTransformerはCUDAによるTransformer推論の専用実装であり、LightSeqと直接比較される。一方、LightSeqは演算融合だけでなく、生成後処理の階層化とテンソル寿命に基づくメモリ共有、複数のモデル系列・探索方式を同一ライブラリで扱う。TurboTransformersは当時の符号器最適化に重点があり、対応する生成処理の範囲が異なる。汎用学習フレームワークとの大きな速度差と、既存CUDA専用実装との比較倍率を混同してはならない。

## 適用時に確認すべき実装上の条件

実際の推論基盤へ移す際には、入力長の上限、利用する数値精度、探索方式、実行バッチの形状を先に固定して比較する必要がある。カーネル融合は形状によって計算とメモリ転送の比率が変わるため、短い系列で速くても長い系列で同じ改善を得るとは限らない。候補探索についても、ビーム探索を使わない生成では節約対象が異なる。モデルを複数常駐させる場合は、単体の遅延だけでなく、実際に利用できるメモリ容量と要求間の干渉を測るべきである。

一時領域を再利用するには、各テンソルが最後に参照される時点を正しく把握する必要がある。計算の依存関係を誤って同時に必要な二つのテンソルを同じ領域へ割り当てれば、結果が破損する。逆に安全側へ寄せて全ての中間領域を分離すれば、メモリ節約効果は失われる。論文の設計は、この寿命情報を実行順序と対応付けることで、計算結果を保持する必要がなくなった領域を後続演算へ引き渡すものと理解できる。

同時に、モデルの重みそのものと中間テンソルを混同してはならない。原著が示す複数モデルの同時配置は、中間領域の再利用で空いたメモリを活用する例であり、重みの量子化や圧縮によってモデル一つ当たりのパラメータ容量を減らしたという主張ではない。新しいモデルへ応用する場合、重み、注意計算用の鍵・値、作業領域、出力候補を分けて計測する必要がある。

## 限界と現代的意義

2021年のP4/T4、Transformer baseを対象とした評価を、現在の巨大な生成専用LLMへそのまま適用できない。現代のサービングでは長文脈KVキャッシュ、ページ化、連続バッチ、複数GPUの通信、モデル重みの帯域制約などが追加される。LightSeqの原著にはvLLMやSGLangとの直接比較がないため、これらより速いと結論づけることはできない。

HARSの候補抽出では閾値と同点処理、確率の正規化に注意が必要で、性能表だけでは数値完全一致を保証しない。メモリ再利用は設定した最大系列長に依存し、過大な上限は事前確保領域を増やす。演算融合による改善はGPU世代や形状にも依存する。原著の最大倍率は一部の測定点の結果であり、すべてのバッチ、精度、生成方式へ一般化してはならない。

それでも、推論システムを「行列積だけ」でなく、GPUカーネルの起動、語彙探索、中間テンソルの寿命という複数の費用から設計する視点は今も有効である。原著がGEMM比率の増大を次の最適化課題として示したことは、律速が最適化の進展によって移動するという重要な観察である。
