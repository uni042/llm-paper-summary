# Magellan：LLMと進化的探索でコンパイラ最適化の判断規則を発見する

## 概要と推論基盤サーベイでの位置付け

**Magellan**は、コンパイラの最適化パスにある人手設計の判断規則を、LLMによるコード生成と進化的探索によって置き換える研究である。単にソースコードを生成するのではなく、コンパイラ内部で使う**再利用可能なC++のヒューリスティクス**を生成し、実際にコンパイラをビルドし、最終アプリケーションのバイナリサイズや実行時間を測って評価する。得られた結果を次の生成へ戻し、改善を繰り返す。

推論基盤との接点は、XLAなどの計算グラフ最適化、TPU向けの自動シャーディング、コンパイラ生成コードの品質にある。Gemmaを含む実モデル由来の計算グラフも扱うが、研究の主対象は**一般的なコンパイラ最適化方針の発見**であり、vLLMやSGLangなどのLLMサービングシステムのエンドツーエンド速度を直接改善した実測研究ではない。コンパイラを使う推論基盤へ間接的に応用可能な研究として位置付ける。

主要結果は、LLVMの関数インライン化で人手の基準より最終バイナリサイズを**5.23%**削減したこと、時間を変えた評価で**5.75～5.95%**、複数の製品バイナリで平均**8.79%**のサイズ削減を報告したことにある。実行時間の最適化は難しく、最初の探索では基準を超えられず、Gemini-2.5-Proの候補を種にGemini-3-Proで探索を継続した場合に**0.61%**改善した。XLAの等価グラフ抽出では**7%**のコスト改善を報告する。各数字は異なる目的関数・ワークロードでの値であり、一つの速度倍率として合算してはいけない。

## 問題設定：コンパイラの判断規則は手作業で複雑になる

コンパイラは、関数のインライン展開、レジスタ割当、グラフの書換え、計算の分割など、多くの最適化判断を行う。これらは組合せが爆発するため、常に全候補を探索して最適解を得ることは難しい。そこで長年にわたり、入力コードの特徴を見て「この関数を展開する」「この生存区間を優先する」と判断するヒューリスティクスが手作業で作られてきた。

ヒューリスティクスは実装が高速で既存のコンパイラへ組み込みやすいが、ハードウェア、アプリケーション、コンパイラ自身が変化すると調整が必要になる。機械学習モデルをコンパイラへ組み込む方式もあるが、学習用データ、モデルの推論ランタイム、特徴抽出器、保守などの追加負担がある。Magellanは**最終的にコンパイラへ残るのは通常のC++判断コード**とすることで、ニューラルネットワークをコンパイラ実行時に組み込まずに最適化規則を発見する。

従来のLLMによるコンパイラ最適化研究には、プログラムごとに最適化パスの順番を選ぶ方式や、コンパイラの代わりに最終コードを直接生成する方式がある。Magellanはこれらとは異なり、**コンパイラのパス自身が使う決定ロジック**を変更する。発見した規則は一度作れば別のプログラムのコンパイルにも適用できることを狙う。

## 手法：1. LLMが編集可能なC++ポリシーを提案する

MagellanはAlphaEvolveをコード生成と進化的探索の外側の枠組みとして使う。開発者は改善したいコンパイラのソースファイルで、変更を許す領域を`EVOLVE-BLOCK`コメントで囲む。LLMはこの領域のコードを編集し、既存のLLVM APIを通じてコンパイラが利用できる判断規則を提案する。対象はLLVMのインライン判断など、入力特徴から最終的な可否や優先度を返す部分である。

提案は必ずしも全コードをゼロから書く必要はない。論文は、あらかじめ用意された38個の特徴を組み合わせる**部分的な判断規則**と、LLVMの呼出し命令`CallBase`から周囲の制御フローや関数属性を参照して判断する**完全な判断規則**を比較する。部分的な規則は探索空間が狭く初期改善が速い一方、完全な規則はAPIを直接使えるため、既存の特徴にない判断条件を発見できる。

この段階で重要なのは、LLMが出すコードを**コンパイラの正規インターフェースに合わせる**ことである。LLVMの既存インライン判断機構は合法性のチェックを先に行い、生成したポリシーは合法な候補の中から判断する。生成コードを任意に実行しても常に正しいコンパイルが得られるという一般保証ではなく、実験ではコンパイラ側の合法性チェックとビルド・実行検証を利用している。

## 手法：2. 実コンパイラを再ビルドしてマクロベンチマークで測る

生成されたC++判断規則をコンパイラへ挿入し、コンパイラを再ビルドする。そのコンパイラで対象アプリケーションをコンパイルし、最終バイナリのサイズや実行時間を測る。バイナリサイズは`llvm-size`などで、実行時間は`perf stat`などで評価する。最終リンク後の実行ファイルや実際のアプリケーションを使うため、局所的な命令数や推定コストが改善しても最終性能が悪くなるというずれを検出できる。

例えば関数インライン化は、関数呼出しを消して実行時間を減らす一方、関数本体を呼出し側へ複製してバイナリサイズを増やすことがある。しかし一度しか呼ばれない関数を展開すると、元の関数定義そのものが不要になり、定数伝播や不要コード除去も進むため、逆にサイズが減る場合がある。最終成果物で評価することで、このようなコンパイラ最適化の相互作用を学習信号へ取り込める。

大きなアプリケーションを毎回ビルド・実行する評価は高価である。論文は最終的なマクロベンチマークを報酬にする一方、計算費用が大きい場合は静的コストモデルなどの代理指標へ置き換えられると述べる。ただし代理指標の採用は現実の性能とのずれを増やし得るため、実測を使う場合と同等の保証にはならない。

## 手法：3. 判断規則の構造と数値閾値を分けて探索する

LLMがコード構造と閾値を同時に変更すると、どの変更が性能へ寄与したか分かりにくく、無効なプログラムや極端な数値が多くなる。MagellanはLLMに**記号的なハイパーパラメータを持つ判断規則のテンプレート**を作らせ、閾値の具体的な値は外部の自動調整器（autotuner）に任せる。テンプレートを固定したまま複数の数値組合せを評価し、最良の組合せをLLM側へ戻す。

論文は自動調整器にVizierを使い、サイズ最適化の実験では外側の1反復ごとに10組のパラメータを試す。コンパイラの判断コードの構造を毎回生成し直さなくても、多数の数値設定を探索できる。結果として、LLMが完全な規則と閾値を直接提案する場合は無効候補率が**65%超**だったのに対し、自動調整を使う場合は**13%**へ減り、無駄な候補が約5分の1となった。

LLMの役割は「どんな特徴を見てどう判断するか」という離散的なプログラム構造の発見、調整器の役割は「閾値をいくつにするか」という連続・離散の数値探索である。両者を分けることで、モデル呼出しやコンパイラの再ビルド回数を抑えながら、細かなパラメータを多数試せる。

## 手法：4. 評価結果を進化的探索へ戻す

候補の実測報酬、調整ログ、プロファイル結果をAlphaEvolveへ返し、性能の良い候補を残しながら新しいコード変種を生成する。LLMが提案するポリシー、実際のコンパイル・実行、調整器による閾値探索、評価結果に基づく次候補生成という閉ループを繰り返す。単発のコード生成ではなく、**実測値を使った探索**が中心である。

ただし探索対象が大きく、報酬がノイズを含むと、良い候補に到達するまで時間がかかる。最終的なポリシーが短いC++コードであっても、その発見には多数のコンパイラビルドとベンチマーク実行が必要である。探索費用と、得られたポリシーを後で何度も再利用する便益を分けて評価する必要がある。

## 評価条件と実験の構成

| 項目 | 一次論文の条件 | 注意点 |
|---|---|---|
| 生成モデル | 原則Gemini-2.5-Pro、速度最適化の継続実験でGemini-3-Pro | LLMの世代と初期候補が結果へ影響 |
| 進化探索 | AlphaEvolve、必要時にVizier自動調整 | 自動調整なしとの比較あり |
| コンパイラ | Google内部のclang/LLVM（2025年夏ごろのLLVM mainに近い）、XLA | 上流の公開LLVMリリースと完全同一ではない |
| サイズ最適化 | 内部検索アプリケーション、複数の製品バイナリ、複数時点のスナップショット | バイナリの最終サイズを評価 |
| 性能最適化 | clangをマクロベンチマーク、同一PGOプロファイル、ThinLTO、`-O3` | 実行時間はノイズが多く探索が難しい |
| レジスタ割当 | LLVM RegAllocGreedyの生存区間優先度 | 大規模製品検索ワークロード |
| XLAグラフ抽出 | Enzyme-JAX由来の等価グラフ書換え後の最小コスト抽出 | 計算グラフのコストを最小化 |
| XLA自動シャーディング | Gemma・拡散モデル等のグラフ、公開5例と非公開20例の競技設定 | TPU間通信・再分割・メモリ制約を含む |
| 主な指標 | バイナリサイズの削減率、実行時間の改善率、グラフコスト、無効候補率 | LLM推論トークン毎秒ではない |

この研究の性能数値は、異なるベンチマークと目的関数を跨いでいる。LLVMのサイズ削減5.23%を「推論が5.23%速い」と解釈することはできない。XLAのグラフコスト7%改善も、モデルの実測エンドツーエンド実行時間7%短縮とは限らない。

## 評価結果：1. LLVM関数インライン化のサイズ削減

関数インライン化は、関数呼出しを呼出し先の命令列へ置き換える最適化である。呼出し費用を減らせる一方、コードの複製でサイズが増え得るため、サイズと性能の両方を考えた判断規則が必要になる。論文はLLVMの手作業のインライン判断を基準とし、最終リンク済みバイナリのサイズで評価した。

| 探索設定 | 結果 | 条件 |
|---|---|---|
| 38特徴を用いた部分ポリシー | **4.27%サイズ削減** | 約1.5日間の逐次探索 |
| LLVM APIを直接使う完全ポリシー | **5.23%サイズ削減** | 同じ約1.5日間、広い探索空間 |
| 完全ポリシー＋自動調整 | **5%超のサイズ削減** | 10外側反復、100候補、約5時間 |
| 時系列汎化 | **5.75～5.95%サイズ削減** | 連続した月の4スナップショット |
| 複数製品バイナリ | **平均8.79%サイズ削減** | 10本以上の製品バイナリ、ニューラル方式は8.52% |

部分ポリシーは既存の特徴を使うため早く改善するが、探索可能な規則が限定されて早めに頭打ちになる。完全ポリシーは初期の失敗が多いものの、LLVM APIからより豊富な情報を得られるため最終的に高い削減率へ達した。自動調整を組み合わせると、数値閾値の探索をLLMのコード再生成から切り離せるため、同等以上の結果へより短い時間で到達した。

時系列汎化では、ある時点で作った規則を数か月後のアプリケーションスナップショットへ適用しても5.75～5.95%のサイズ削減が維持された。製品バイナリを跨ぐ評価では平均8.79%で、比較するニューラルポリシーの8.52%をわずかに上回る。ただし製品バイナリごとに差があり、平均値が全対象の優越を意味するわけではない。

## 評価結果：2. 発見した規則の構造と保守性

発見した完全ポリシーの実行ロジックは**143行**で、コメント・空行を除いた人手設計の実装**2,115行**より約15倍短い。短い理由は、分岐条件や例外的な扱いを絞り、重要な判断へ集中したためと説明される。ただし、行数が少ないことだけで将来の保守性や全目的での性能が保証されるわけではない。

発見された規則は、一度しか使われない関数を積極的にインライン化することで元の関数定義を削除可能にし、読み取り専用の関数を展開して後続の不要コード除去を促す。呼出し先の命令数だけでなく、制御フローの複雑さ、定数引数、型の一致などを使って、展開後の最適化余地を推定する。これは「サイズを減らすならインライン化を抑制する」という単純な方針と異なる。

## 評価結果：3. 実行時間の最適化では失敗例もある

実行時間の最適化では、clang自身をマクロベンチマークとし、同一のプロファイル誘導最適化（PGO）データ、ThinLTO、`-O3`を使う。サイズと違って実行時間はノイズが大きく、コンパイラの再ビルドと実行を伴うため、1候補の評価が高価になる。自動調整器は外側の1反復で40組の数値設定を試す。

Gemini-2.5-Proでゼロから探索した場合、60反復後も基準に対して**約2.4%悪化**したところで頭打ちになった。Gemini-3-Proを同じ初期条件から使っても、100反復・約1週間の逐次評価で基準の0%を超えられなかった。つまり、より強いLLMへ変えるだけでは探索空間の壁を越えられなかった。

そこでGemini-2.5-Proが作った最良候補を初期種にしてGemini-3-Proの探索を継続すると、最終的に**0.61%の実行時間改善**を達成した。改善幅はサイズ削減の5%前後より小さいが、手作業で最適化されたLLVMの基準を実アプリケーションの実行時間で超えた点に意味がある。性能改善は探索初期条件と報酬の性質に強く依存するため、成功例だけで自動発見が常に勝つと結論してはいけない。

## 評価結果：4. レジスタ割当とXLAの計算グラフ最適化

レジスタ割当では、LLVMの`RegAllocGreedy`が生存区間を処理する優先度規則を探索する。大規模製品検索ワークロードで、最終的に非常に単純な定数値ポリシーへ収束し、複雑な人手規則とほぼ同等の性能となった。論文は基準に対する性能を**-0.55%から-0.15%**へ改善したと報告する。これは0.15%の性能向上ではなく、負の差が小さくなったという結果である。

XLAのグラフ書換えでは、等価な計算式を多数保持するe-graphから、各等価クラスで一つのノードを選び、依存を満たしつつ最小コストの計算グラフを抽出する。組合せが大きく、正確な最小化は難しい。Magellanはこの抽出判断規則を生成し、手作業の規則に対して**7%のコスト改善**を報告した。これはモデル推論時間の実測7%改善と同一ではない。

自動シャーディングでは、計算グラフの各ノードへ分割戦略を割り当て、TPU間の通信、再分割、メモリ制約を満たしながら全体コストを減らす。Gemmaや拡散モデルに由来するグラフを含むASPLOS 2025のIOPDDL競技設定を使い、公開5件で探索、非公開20件で評価する。1週間の進化探索後に上位競技提出と同程度の性能を得たと報告するが、全ケースの絶対遅延やLLMサービングの同時要求性能を示したわけではない。

## 既存研究との差と推論基盤への接続

従来のニューラルなコンパイラ判断器は、特徴を集め、学習したモデルをコンパイラへ組み込む必要がある。Magellanは学習済みのLLMを**開発時の探索エンジン**として使い、最終的に残るのは普通のC++判断コードとする。したがって、最終ポリシーを実行するたびにLLM推論が必要なわけではない。

コンパイラの最適化パス順序をプログラムごとに選ぶ研究とも異なる。Magellanはコンパイラのパス自体が持つ決定ロジックを変えるため、発見した規則を別のプログラムにも再利用できる。XLAの自動シャーディングのような推論関連のコンパイル課題にも適用できるが、同じポリシーがLLMのプレフィル・デコード・通信の全条件を改善するという検証は行っていない。

実際のLLM推論システムへ導入するなら、対象コンパイラ、モデル形状、デバイス数、通信トポロジー、メモリ予算を含む評価ベンチマークを用意し、既存のXLAやTensorRT-LLMなどの最適化と比較する必要がある。論文は汎用の探索枠組みを示すが、完成した全てのポリシーが公開ランタイムへそのまま統合できるわけではない。

## 限界：悪化条件・再現性

第一に、評価はGoogle内部のコンパイラ・アプリケーションを多く含む。内部検索アプリケーションや製品バイナリの具体的内容を完全に再現できない場合、サイズ削減率の再現には制約がある。LLVM mainに近い内部版を使用しており、一般公開版と同一コミットではない。

第二に、探索には大量のコンパイラビルド、アプリケーション実行、LLM呼出しが必要である。最終的なC++ポリシーが短くても、その発見に1.5日から1週間の逐次探索を要した実験がある。探索費用を無視して、無料で性能が改善する方式として扱うことはできない。

第三に、サイズ最適化の成功が実行時間の成功を意味しない。速度目標ではGemini-2.5-Pro単独が-2.4%の悪化で頭打ちになり、Gemini-3-Pro単独でも基準を超えられなかった。継続探索で0.61%改善したことは有望だが、改善幅は小さく、初期候補と測定ノイズに依存する。

第四に、XLAのグラフコスト7%改善は実機でのトークン毎秒7%改善ではない。自動シャーディングの競技スコアも、実際のLLM推論サービングでのTTFT（初トークン遅延）やTPOT（出力トークン間遅延）とは異なる。推論用途へ一般化するには実際のモデル・同時要求・ハードウェアで測る必要がある。

第五に、生成コードが短いことは保守性を保証しない。LLVMの合法性チェックを利用する実験であっても、生成ポリシーの安全性・最悪時の性能・将来のLLVM API変更への追従は別の検証を要する。公開の完全なMagellan実装と内部評価環境を一次資料から特定できなかったため、`code: null`とした。
