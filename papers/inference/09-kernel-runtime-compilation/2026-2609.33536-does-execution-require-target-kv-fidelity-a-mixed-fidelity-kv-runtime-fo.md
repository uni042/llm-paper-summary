# ElasticKV：低精度KVでも推論を止めない混合忠実度ランタイム

## 概要

大規模言語モデルの複数要求処理では、キー・値キャッシュ（KV cache）がGPUの高帯域メモリを圧迫する。通常のページ式サービングでは、注意計算を実行するには指定された精度のKVがGPUに存在しなければならない。容量が不足すると、要求の待機、実行中断（preemption）、過去文脈の再計算が生じる。本研究は**精度が完全でないKVでも、処理を進める方が総遅延を小さくできる**という観察から、KVの精度を実行時に変更するElasticKVを提案する。

ElasticKVでは通常の16ビットKVをTARGET、上位8ビットのみを持つ低精度KVをBASEと呼ぶ。BASEは単なる圧縮保管形式ではなく、注意計算が直接参照できる**実行可能状態**である。GPUに空きがないときは一部のTARGETをBASEへ降格し、容量が回復したらCPU側に保持した復元用情報からTARGETへ非同期で昇格する。これを実現するため、物理ブロックを対にしたメモリ配置、二経路の注意カーネル、メモリ不足予測に基づく精度制御を統合した。

A100 80GBでLlama-3.1-8B-InstructとQwen3-8Bを処理した高同時実行条件では、通常のvLLM（全KVをGPUに保持）と比べ、平均初回トークン遅延（time to first token; TTFT）が3.8～4.0分の1、90パーセンタイルTTFTが最大9.1分の1になった。これは単一トークン計算を9.1倍高速化した結果ではない。中断と再開に伴う待機時間を回避した効果が主因である（原著§4.3、図4）。

## 問題設定と着眼点

### KVの容量不足と「実行可能性」の混同

KVをGPUからCPUへ退避させる方式では、容量は拡張できても、対象のKVがGPUに戻るまで要求を再開できない。量子化も、あらかじめ設定された精度を唯一の実行形式とする限り、容量が尽きた瞬間の要求待機は避けられない。著者らは、保存先やビット幅だけでなく「どの表現なら計算を続けてよいか」を実行環境の契約として分離する。

従来の状態はTARGETまたはABSENTの二択に近い。ElasticKVではABSENT、BASE、TARGETの三状態を設け、BASEとTARGETの両方を実行可能とする。高精度TARGETが望ましいのは変わらないが、GPU不足時にBASEで前進できれば、全要求を待機させるより短い遅延で処理できる。特にGPUの容量境界付近では、少数のブロックを一時的にBASEにするだけで大きな中断を防げる。

### 単に半分に量子化しても容量は返らない

ページ式KV管理では論理ブロックごとに固定長の物理ブロックを割り当てる。16ビットから8ビットへ縮めても、同じ物理ブロックの後半が未使用になるだけなら、割当器が利用できる空きブロックは増えない。論文の図3(a)は、二つの論理ブロックを個別に低精度化しても物理ブロックの解放数がゼロになる問題を示す。したがって、精度の切替、実メモリ回収、注意カーネルの対応を同時に設計しなければならない。

## 手法

### 1. TARGETとBASEの表現および復元情報

実装上のTARGETは元の16ビット表現であり、BASEはその上位8ビットを残した形式である。BASEを注意演算で使用するときは、保持した上位ビットを元の位置へ置き、失われた下位ビットをゼロで埋めて演算用の16ビット値を組み立てる。これは数値を近似する操作であり、**BASEだけから元のTARGETを厳密に復元できるわけではない**。元の精度へ戻すためのCPU側のバックアップが必要で、復元元を確保できないブロックは降格対象から除外する（§3.3）。

注意の始端で重要になりやすい注意シンク（attention sink）と最近のトークンをTARGETのまま保護し、主として中間部分をBASE化する。新しく追加するKVはTARGETで書き込み、後から必要に応じて降格する。すべてのトークンを恒常的に8ビット化する方式ではない。

### 2. 二つの論理ブロックを一組にするペア式配置

BASEの容量はTARGETの半分なので、二つの論理ブロックを一つの物理ブロックに詰めれば、もともと二つ必要だった物理ブロックの一つを解放できる。ElasticKVは二つの論理KVブロックを固定の対（pair）として管理する。両方がTARGETなら物理ブロックを二つ使い、BASEへ降格すると両方の高位8ビットを一つの物理ブロックへ詰め直す。解放された一つはGPU割当器へ返され、別の要求が使える。

この配置は論理ブロック番号を変えない。上位のスケジューラから見た論理ページの名前空間を維持し、物理配置だけを変更するため、既存のページ式KV管理に接続できる。昇格時は空き物理ブロックを一つ確保し、CPUの復元元を利用して二つのTARGETブロックへ戻す。小さすぎる可変断片に分割して管理メタデータを増やす方式と異なり、固定の対単位で再利用可能容量を保証するのが設計上の重要点である（図3）。

### 3. 二経路注意演算（dual-mode attention）

全要求がTARGETだけを参照するバッチでは、既存のTriton注意演算経路をそのまま使用する。BASEを含むバッチのみ専用の混合精度経路へ送る。各系列はTARGET/BASEのブロック状態列を持ち、一般には明示的なモード表を参照する。シンクと最近部分を保護するため、多くの系列はTARGET–BASE–TARGETという規則的な三領域になり、この場合は境界位置だけを持つ簡潔な表現で済む。

専用カーネルはBASEブロックの上位バイトを読み、レジスタ内で下位をゼロ埋めした演算値にして注意計算を進める。元のTARGETだけの処理では不要なモード判定を通さない設計であり、GPUに十分な余裕があるときの通常処理性能を守る。BASEを含む要求が進行できるのは、割当器の空きが増えるだけでなく、**その低精度KVを実際の注意演算が消費できる**からである。

### 4. 先読み不足検査と同期降格

スケジューラの現在の要求集合から、次の処理段階に必要なKV物理ブロック数を副作用のない試行で推定する。必要量を $D_t$、空き容量を $F_t$ とすれば不足量は $\Delta_t=\max(0,D_t-F_t)$ である。不足がゼロなら既存の割当経路を維持する。正なら、保護対象や復元元のないペアを除いた候補から降格する。

不足量ちょうどのペアだけを毎回降格すると、微小な不足が繰り返されて同期処理の固定費用が増える。そのため、降格を始めた場合には最小バッチ数 $B_{min}^d$ を設け、不足量と比較してまとまった数を処理する。余分に空いた容量 $E_t$ は直ちに昇格へ使わず、後続の割当を安定化する余剰として記録する。降格は物理ブロックを返してから要求を継続する必要があるため、同期処理である。

### 5. 余剰を保護する非同期昇格

昇格は品質回復のために望ましいが、空きが出るたび即座にTARGETへ戻すと、次の要求で再び不足して降格する振動が生じる。ElasticKVは最近の降格による余剰を減衰する予約量 $R_t$ として保持する。原著の更新則は $R_t=\max(0,R_{t-1}-\lambda)+E_t$、昇格可能予算は $P_t=\max(0,F_t^{post}-R_t)$ である。予約が減るにつれ余裕分を徐々に昇格へ回す。

昇格は必要な要求割当が終わった後、転送余裕があるときにCPU側のバックアップから非同期に実行する。復元完了までBASEは実行可能なまま保持されるため、昇格そのものを要求の待機理由にしない。降格は不足を防ぐための緊急操作、昇格は資源が空いた際の品質回復操作という非対称な役割である。

### 6. 実装上の接続点

著者実装はvLLM v0.15.0のKVCacheManagerを拡張し、論理ブロックの精度状態・物理対応・CPU復元元・遷移中状態を管理する。Python側で不足量検査と遷移計画を実装し、Triton側に `ELASTIC_TRITON_ATTN` を追加する。既存の要求順序スケジューラを全面置換する方式ではなく、スケジューラの割当前後に精度制御を差し込む。専用注意経路の品質と速度は、ブロック状態の規則性やメタデータ処理量に左右される。

### 実験条件と比較対象

### 同時実行数を増やした場合のサービング性能

原著§4.3・図4では、容量不足になる前の三方式の性能は近い。要求数が容量境界を越えると、通常vLLMとExact-offloadは中断と再開によりTTFTが急増する。一方、ElasticKVは一部KVをBASEにして実行を継続する。Qwen3-8B・最大同時36要求ではFull-GPUが4,989回、Exact-offloadが579回の中断を起こすのに対し、ElasticKVは0回である。中断を消すことが、平均遅延だけでなく裾の長い遅延の抑制につながる。

| 指標 | 比較 | 原著が報告する高負荷時の結果 | 読み方 |
|---|---|---|---|
| 平均TTFT | Full-GPU比 | 3.8～4.0倍短縮 | 初回出力待機の短縮。トークン計算自体の倍率ではない |
| P90 TTFT | Full-GPU比 | 最大9.1倍短縮 | 中断による尾部遅延の回避 |
| 平均TTFT | Exact-offload比 | 2.0～2.6倍短縮 | CPU退避を許す方式との差 |
| P90 TTFT | Exact-offload比 | 2.5～4.7倍短縮 | 転送完了待ちの削減 |
| 出力トークン処理量 | Full-GPU比 | 2.45～2.63倍 | 高負荷でのシステム全体の処理量 |
| 出力トークン処理量 | Exact-offload比 | 1.17～1.23倍 | CPU退避方式との差 |

この表は原著の二モデルにまたがる条件別範囲であり、同じ一条件で全ての倍率が同時に成立するわけではない。TPOTも比較され、Full-GPUの高負荷時TPOTはElasticKVの約2.5倍になる。したがって本研究の効果はTTFTだけの指標操作ではないが、主な利得がメモリ圧力と要求中断に依存する点は変わらない。

### ShareGPTと実運用トレース

ShareGPTの要求到着率を増やす実験では、最高22要求/秒の条件でFull-GPUはLlamaで1,297回、Qwenで1,574回の中断を起こした。Exact-offloadはそれぞれ1,392回、1,594回であり、ElasticKVは両モデルとも0回だった。このときBASEとして実際に注意計算に使われた割合はLlamaで2.6%、Qwenで3.6%にとどまる。大量のKVを常時低精度化しなくても、容量境界の少数ブロックを逃がすことで中断を防げることを示す（付録表6）。最高到着率でのP90 TTFTはFull-GPU比4.3～6.5倍、Exact-offload比3.1～4.0倍短縮した。

Mooncakeの本番トレースでは、要求長・到着間隔の変動を含めて実効サービス水準を比較する。8基のAMD MI355Xで70BモデルをTP2×DP4配置した評価では、Exact-offloadに対する平均Eff@300が34.1%改善し、全窓で中断がなく、終了までの残務処理時間が平均70.5%短縮された。単機A100との数値を直接比較して「AMDの方が高速」と読むことはできない。モデル規模、時間窓、到着率の伸縮、並列方式が違うからである。

### 品質への影響と負の結果

LongBenchの21タスク平均を表1で比較する。BASE露出上限は、対象の実行中にBASEを注意計算へ用いた割合の上限であり、全KVがその割合だけ恒常的に8ビットであるという意味ではない。

| 精度運用 | Llama-3.1-8B | Qwen3-8B |
|---|---:|---:|
| 静的FP16 | 49.89 | 49.59 |
| 静的FP8 | 48.72 | 49.07 |
| ElasticKV・BASE上限5% | 50.06 | 49.59 |
| ElasticKV・BASE上限10% | 50.06 | 49.52 |
| ElasticKV・BASE上限20% | 50.04 | 49.42 |
| 全KVをBASEで実行 | 48.45 | 47.87 |

低いBASE露出率では平均品質がFP16に近い。一方、**全KVをBASEに固定するとLlamaで1.44点、Qwenで1.72点低下**する。表の小さな正の差を品質改善の証拠として解釈すべきではない。原著もばらつきによる非単調な差と述べる。つまり本方式は「8ビットでも必ず品質同一」ではなく、「低精度を必要時だけ使い、品質影響を小さく抑える」設計である。

付録表10には重要な不利な比較がある。固定FP8のFlashInfer実行とElasticKVの専用Triton実行を比較すると、LlamaのP90 TTFTは1.47秒対2.87秒、出力処理量は1,003.12対914.25トークン/秒で、固定FP8が良い。Qwenでも1.50秒対1.98秒、949.04対854.92トークン/秒で固定FP8が良い。ただしカーネルが一致しておらず、精度契約も異なるため、方式固有の優劣を厳密に切り分けた比較ではない。この負の結果を省くと、ElasticKVがあらゆる低精度KV方式より高速という誤解を招く。

### 追加コストと感度

最大同時38要求のLlama実験では、制御処理0.32ms/step、同期降格2.82ms/step、追加メタデータ1.23ms/step、合計4.37ms/stepの追加クリティカルパス費用が測定された（§4.7、表2）。同期降格が起きるのは全ステップの約11.1%であり、上記2.82msは全ステップで均した値である。非同期昇格の時間はこの合計に含まれない。余裕のある低負荷では、この制御費用が無視できない場合がある。

KV予算を縮めると、通常方式が中断する境界を越えてもElasticKVは比較的安定し、最も厳しい試験でもBASE露出率は約13%だった。入力を32Kトークンに延ばした感度評価では、Exact-offloadに対する平均TTFT改善はLlamaで21.7%、Qwenで21.8%、BASE露出率はそれぞれ6.3%、15.9%だった（図8）。最大の3.8～4.0倍という値をこの32K条件に流用してはいけない。

## 既存研究との差

既存のKV量子化は保存量を、退避は保存場所を、疎な注意は参照する要素を主に変える。ElasticKVが新しく扱うのは、**要求を実行してよいKVの状態集合**である。高精度TARGETだけを唯一の実行可能状態とする制約を緩め、必要時だけ低精度BASEを使う。物理メモリ回収と注意演算の実行可能性を同時に満たす点で、単なるKV圧縮手法とは異なる。

静的FP8は全期間で8ビットを実行形式にするため、容量境界を押し上げるが、FP8が欠ければやはり待機する。ElasticKVはTARGET 16ビットとBASE 8ビットを動的に共存させる。原理上はTARGETを8ビット、BASEを4ビットにする拡張も考えられるが、論文が実装・評価したのは16/8ビットの組だけである。

## 限界・実装上の注意

第一に、BASEでの注意計算は下位8ビットを捨てた近似であり、出力が元モデルと厳密一致する保証はない。露出率が大きくなれば品質が落ちる。特に長い推論系列、数値計算、特定の重要トークンに敏感な課題でどの程度の誤差が累積するかは、LongBench平均だけでは保証できない。

第二に、TARGETへの昇格にはCPU側の復元元が必要である。復元元のないブロックを降格しない制約は、利用可能な降格候補を減らす。CPUメモリや転送帯域の余裕が小さい環境では、昇格の遅れやバックアップ維持の費用が問題になる。

第三に、二つの論理ブロックを対にして物理メモリを回収する設計は、BASEがTARGETの半分であることに依存する。別の圧縮率・可変ビット幅へ一般化するには再設計が必要であり、今回の実験から任意の量子化方式への互換性を主張できない。

第四に、固定FP8との比較は別の注意カーネルを使うため、低精度方式の本質的優劣と実装最適化の差が混ざる。固定FP8が高速な実測も存在する。ElasticKVは高精度の維持とメモリ圧力時の実行継続を重視する設計であり、絶対処理量だけなら最適解とは限らない。

第五に、主要な速度改善は容量境界に達する高同時実行環境で現れる。要求数が少ないとき、GPUメモリが十分あるとき、KVより行列積が律速のときには、大幅なTTFT短縮は期待できない。検証はA100およびMI355Xであり、RTX 4070 Super 12GB、Windows 11、CPUオフロード主体の単一ユーザー推論で同じ倍率を見込む根拠はない。

第六に、著者実装はvLLM v0.15.0に依存するPython/Tritonの改変である。既存の量子化KV、他の注意バックエンド、複雑な分散スケジューラとの統合には追加の検証が要る。論文本文から公式公開リポジトリを特定できず、再現実装の配布状態は未確認である。
