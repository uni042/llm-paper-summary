# Towards a Solution to the Management Scaling Paradox in Distributed LLM Inference

> 分離型推論でKVキャッシュ管理のユーザ空間オーバーヘッドがヒット率とともに膨らむ逆説を定量化し、カーネル内のコンテンツアドレス型PGASで無調整にチャンクを引けるRMCによりTTFTを1.1〜1.3倍短縮する提案。

## 概要

大規模言語モデルのサービングでは、入力を一括処理するプリフィルと、1トークンずつ生成するデコードを別ノードへ分ける分離型構成が広がっている。この構成で最初のトークンまでの時間（Time To First Token; TTFT）を縮める鍵は、過去のリクエストと共通する接頭辞のKVキャッシュ（過去トークンのキーとバリューを保持し再計算を省く仕組み）をノード間で再利用するプリフィックスキャッシュであり、本番ワークロードではヒット率45〜71パーセントが報告される。ところが現行の最先端スタックであるLMCacheとMooncakeの組み合わせは、このキャッシュの管理をすべてユーザ空間で行い、調整用のRPC、チャンク単位のロック、冗長なメモリコピー、PythonのGIL（Global Interpreter Lock）の下での直列化されたハッシュ計算、RDMA転送の断片化といった管理費を払っている。

本論文が名付けた管理スケーリングの逆説とは、この管理費がキャッシュの効果と逆方向に育つことである。ヒット率が上がると節約できるプリフィル計算は減っていくのに、管理費はキャッシュ済みチャンク数に比例して増えるため、キャッシュが最も効くはずの局面で管理費が到達可能なTTFTの79パーセントを占め、理想なら4.6倍の高速化が約2.6倍へ頭打ちになる。著者らはこの構造をTTFTの分解式で定式化し、計装した実測で裏付ける。

提案するRMC（Remote Memory for Cache）は、管理をユーザ空間からOSカーネルへ移すフレームワークである。発想の起点は、vLLMが単一ノード内のKVキャッシュ共有にカーネルの共有メモリ（/dev/shm）を既に使っていることであり、RMCはこれをRDMAバックの遠隔ページフォルトでクラスタ規模へ広げる。核はコンテンツアドレス型の仮想メモリ領域（Virtual Memory Region; VMR）で、256トークン分のチャンクの仮想アドレスと所在ノードを、トークン内容のハッシュだけから全ノードが独立に計算できる。メタデータサーバも分散ハッシュテーブルも調整RPCも要らない。

**代表結果:** RTX 4090の2ノード、200Gbps RDMA、Llama-3.1-8B-Instructの分離型構成で、4つのワークロード（2,048〜7,680トークン、ヒット率44〜63パーセント）について、RMCの収束時TTFTはLMCacheとMooncakeより1.1〜1.3倍短く、キャッシュなしの再計算のみと比べ最大2.1倍（7,680トークン条件で853ミリ秒から401ミリ秒）だった。管理費を除いた計算と通信だけの下限との差は4〜35ミリ秒に収まり、ユーザ空間の管理費のほぼ全量が消えている。

## 問題設定

資源の観点では、分離型構成のTTFTは三つの費用の綱引きである。KVキャッシュはトークンあたりの占有量がモデル構造で固定されており、Llama-3.1-8Bでは1トークン128KB、256トークンのチャンクで32MBになる。キャッシュミスならこのチャンクのプリフィル計算を払い、ヒットならRDMA転送で済む。著者らの実測では転送は再計算より22倍安い。したがってヒット率が上がるほどTTFTは下がるはずである。

ところがユーザ空間の管理層は、ヒットしたチャンク1個ごとに、ハッシュ計算、ロック取得、メタデータサービスへの往復、GPUからCPUバッファへのステージングコピー、細切れのRDMA転送といった一定の管理費を課す。論文の分解式では、TTFTは未ヒット分のプリフィル、常時かかるステージング、ヒット分に比例する管理費の和として表され、ヒット率が1へ近づくとプリフィル項は消えるのに管理費項だけが残る。管理費がプリフィル単価を超えると、キャッシュを増やすこと自体がスループットを悪化させる条件になる。さらにユーザ空間のスケジューラはキャッシュの空き状況を要求割り当て時に一度だけ確認して固定するため、同時要求が同じチャンクを重複して再計算する群れ現象も起きる。

根っこにあるのは層の重複である。ユーザ空間のスタックは、メモリ割り当て、エビクション、RDMA登録といった、カーネルがページテーブルとページ割り当てで既に行っている仕事を複製している。すべてのRDMA転送はカーネルが登録したメモリ領域を必要とし、すべてのバッファはカーネル管理の仮想ページに裏付けられるため、ユーザ空間層はカーネルを迂回できず、その上に調整を積み増すだけになる。本論文の問いは、カーネルのその関与を直接のものにして、分散キャッシュ層自体をカーネルへ担わせられるか、である。

## 手法のあらまし

RMCでは、全ノードが同じPGAS（Partitioned Global Address Space; 単一の仮想アドレス空間をノード間で分割し、どの領域も一様なアドレスで指せるモデル）領域をカーネルレベルのmmapでマップする。各256トークンチャンクは固定サイズのVMRへ対応し、その仮想アドレスはトークン内容のxxHash64をスロット数で割った余りから決まる決定的な関数である。プリフィルノードがチャンクを計算すると、そのVMRへmmap経由で書き込み、所有ノード番号を全ノードのブロックディレクトリ（共有メモリ上の compact な配列）へ片方向RDMA書き込みで放送する。読み手はアドレスを計算し、ディレクトリで所有者を引き、ページフォルトを契機にカーネルが所有者から単一のRDMA読み取りでチャンク全体を取り寄せる。チャンクは書き込み後は不変（write-once）であり、エビクションはカーネルのLRUが担い、無効化もディレクトリへのゼロ書き込みの放送で済む。

## 手法

### 1. コンテンツアドレス型PGAS — ハッシュだけでアドレスと所在が決まる

この機構が観測するのは、チャンク境界までのトークン列そのものである。保持する状態は全ノードで同一のパラメータ（基底アドレス、スロット総数、VMRサイズ）だけであり、処理はトークン列のxxHash64を取り、スロット数で割った余りにVMRサイズを掛けて基底へ足し、仮想アドレスを出すことである。1KBのトークンデータへの1回のハッシュで済み、クラスタ規模によらず定数時間であり、所在を聞く相手が存在しない。これが可能なのはKVキャッシュの二つの性質による。第一にトークンあたりの占有量がモデル構造で固定されるため、領域サイズを配置時に決め打ちできる。第二に、同じトークン列は常にビット単位で同一のKVテンソルを生むため、内容のハッシュがそのままキャッシュの索引にも所在にもなる。これにより減るボトルネックは、メタデータサービスへの往復、分散ハッシュテーブルの維持、調整RPCのすべてである。追加で消費する資源はハッシュ計算のみで、失敗条件はハッシュ衝突だが、64ビットハッシュで有効チャンク10万個でも衝突確率は10のマイナス9乗未満とされ、衝突時はプリフィルへフォールバックして正しい結果を返すため、古いデータを掴むことはない。また接頭辞の依存性（境界までのKVはそれ以前の全トークンで決まる）により、ヒットの取りこぼしも原理的に起きない。

### 2. チャンク単位VMRとwrite-onceコヒーレンス — ロックなしで一貫させる

この機構が観測するのは、計算済みチャンクの書き込みと、エビクションの発生である。保持する状態は、全層分のKVを連続領域に収めた固定サイズVMRと、スロットごとの所有ノード番号を8バイトで保持するブロックディレクトリである。処理は、プリフィルノードがVMRへ書き込んだ後に所有者番号を全ノードのディレクトリへ片方向RDMA書き込みで放送し、読み手は所有者からチャンク全体を単一のRDMA演算で転送することである。連続レイアウトのため、ステージングバッファも、層ごとの反復も、転送の断片化もない。コヒーレンスはwrite-once意味論で保たれる。チャンクは一度計算されれば退避まで不変であり、ディレクトリエントリは8バイトのアラインされたストアで原子的に更新できるため、ロックが不要になる。二つのノードが同じチャンクを同時に計算しても、決定性により結果はビット単位で同一なので、競合書き込みも安全である。エビクション時はカーネルが所有者番号をゼロへ戻す放送を行い、全ノードで無効化する。これにより減るボトルネックは、チャンク単位のロック取得と、PythonのGILの下での直列化、転送前後のCPU側ステージングである。追加費用は所有権放送の片方向書き込みであり、読み手が古いエントリを見る結果整合性は最終的（eventual）だが、古いゼロは無駄な再計算を、古い所有者はプリフィルへのフォールバックを招くだけで、誤った結果にはならない設計である。

### 3. ブロックディレクトリによるプレフィックス照合とスケジューリング

この機構が観測するのは、到着したリクエストのトークン列とブロックディレクトリの内容である。保持する状態は共有メモリ上のディレクトリであり、100万スロットでも8MBに収まる。処理は一回の走査で、各チャンクについてVMRアドレスを計算してディレクトリを引き、所有者が非ゼロの最後のチャンクを最長ヒット接頭辞とし、ヒット数が最大のノードを転送先に選ぶことである。ディレクトリが共有メモリにあるため、コーディネータとvLLMのスケジューラがRPCなしに直接読める。これにより減るボトルネックは、要求割り当て時に一度だけ空き状況を確認して固定する古いスナップショットの問題で、チャンクは書かれた直後からクラスタ全体に見える。追加で消費する資源は走査の計算だけであり、失敗条件は前節のとおり古いエントリによる再計算の無駄に限定される。

### 4. カーネルレベルのフォルト処理とvLLM統合

この機構が観測するのは、未マップのVMRへのアクセスで起きるページフォルトである。保持する状態は、配置時に一度だけRDMA NICへ登録したPGAS領域全体と、カーネルが管理するLRUリストである。処理は、フォルトハンドラがディレクトリから所有者を読み、片方向RDMA読み取りでチャンク全体を取り寄せ、ローカルページを埋めて処理を再開することであり、利用側のプロセスからは透過的である。従来の遠隔メモリ系が4KB単位でフォルト処理するため、32MBのチャンクで約8,000回のフォルトと個別転送が発生していたのに対し、RMCはチャンク全体を1回のトラップと1回のRDMA演算で処理し、カーネルモジュール側の先行測定ではページフォルト総数を最大80パーセント、TLBシュートダウンを4倍削減する粒度である。これにより減るボトルネックは、ユーザ・カーネル境界の往復と中間バッファコピーである。追加費用はカーネルモジュールという実装形態そのものであり、約2,000行のCで先行研究RMAIのカーネル内PGAS基盤の上に構築され、vLLM側の統合はPagedAttentionのバックエンドを差し替える約200行のPythonのCacheEngineで済む。資源不足時はカーネルのLRUがVMRを回収し、接頭辞を守り葉のチャンクから退避させる接頭辞配慮のエビクションも可能な構造である。

|---|---|---|---|---|

## 評価

結論は、管理費はユーザ空間でキャッシュを管理する限り構造的に避けられず、カーネルへ移したRMCではそのほぼ全量が消えて、計算と通信だけの下限に4〜35ミリ秒まで迫る、というものである。評価は実機の分離型クラスタであり、主指標はTTFTである。比較対象のLMCacheとMooncakeは本番運用実績のある最先端スタックであり、管理費を除いた下限は、そのスタックへ細粒度のタイムスタンプを計装してプリフィル時間とRDMAの線路時間だけを取り出した測定値で、別実装ではない点に注意が要る。読み方として、RMCの利得倍率はワークロードのチャンク数とともに育つ。管理費がチャンクあたり約8.6ミリ秒のほぼ線形で増えるため、文脈が長くクラスタが大きいほど逆説は鋭くなり、RMCの優位も広がるというのが論文の主張である。逆にコールドスタートでは、分離型キャッシュはヒット率ゼロでもステージングと転送を払うため、同一ノードの再計算より遅く、交差するのは3〜4リクエスト目あたりである。

### オーバーヘッド源の分析

支配的なのはMooncakeの転送エンジンで、転送ごとに2回のHTTPと1回のZMQの往復（100マイクロ秒〜5ミリ秒）があり、さらに32MBの領域を64KBへ断片化するため1チャンクが512回のRDMA演算になり、NIC帯域を使い切れない。LMCache側の管理層は、GILの下でのsha256_cborハッシュ（チャンクあたり3回）、取得あたり4N個のミューテックスロック、チャンク単位のストリーム同期で、W4でも約4ミリ秒と全体の3パーセント未満に留まる。つまり管理費の主犯は転送経路の断片化と調整往復であり、RMCの単一演算転送が最も効く相手である。

### 評価上の制約

- 対象はLlama-3.1-8Bの単一モデル、RTX 4090の小規模クラスタに限られ、大規模クラスタや他モデルでの検証はない。
- 指標はTTFTのみで、デコード側のTPOTやスループット、グッドプットは測られていない。
- ヒット率はワークロードごとに固定された条件であり、実運用の到着過程や競合下での挙動は未評価である。

## 既存研究との差

LMCacheが識別と階層管理を、Mooncakeが所在追跡とRDMA転送を担う従来構成との差は、管理の所在をユーザ空間からカーネルへ移し、所在追跡そのものを内容ハッシュによる決定的計算へ置き換えた点にある。vLLMやSGLangのローカルなプリフィックスキャッシュはノードを跨げず、CacheGenやCacheBlendはプリフィル費用の削減が目的で跨ノードの検索を持たない。遠隔メモリ系のInfiniswapやLeapなどは4KB〜2MBの粒度でコンテンツアドレス型でもない。著者らの先行研究RMAIはカーネル内PGASとVMRをMoEエキスパート読み込みへ使ったが、番地はモデル構造依存でトークン内容からは引けなかった。RMCはその基盤へ、内容アドレス、write-onceコヒーレンス、ブロックディレクトリによるスケジューリングを持ち込んだ点が新しい。

## 限界・実装状況

限界は、第一にカーネルモジュールという実装形態の重さで、デバッグが難しく、バグがシステム全体のクラッシュへつながり得て、開発サイクルも遅い。第二に、LinuxとRDMA対応NICが前提で、データセンター外への適用は想定されていない。第三に、評価が単一モデル・小規模クラスタ・TTFTのみであり、GPUダイレクトRDMAとの統合は、ページ フォルト駆動のVMRライフサイクルとGPUメモリのピン留めが衝突するため将来課題として残されている。ノード障害時はそのノードのVMRへ届かなくなるが、決定的番地のため生存ノードがトークン列から再計算して復旧できる設計である。実装状況はプロトタイプであり、公式コードの公開先は論文中に示されていない。

## 一般的な実装上の含意

下位層が既に提供している機能を上位層が複製すると、その複製の管理費は最適化対象の指標そのものに比例して育つ、というのがこの逆説の一般形である。分散キャッシュを設計するときは、まず「この調整はOSやハードウェアの既存機構で代替できないか」を見るべきであり、特にデータのサイズが配置時に固定され、内容から索引が決定的に決まる対象では、所在表を持つより所在を計算する方が調整費を構造的に消せる。MoEエキスパートのパラメータ、LoRAアダプタ、パイプライン並列の中間活性値など、同じ二条件を満たす対象へは同じ設計が移せる。
