# FlashOverlap：完了通知と並べ替えによる計算・通信の重畳

## 概要

FlashOverlapは、複数GPUで大規模言語モデルを推論・学習するとき、行列積（general matrix multiplication、GEMM）と、それに依存するGPU間集団通信を重ねて実行する仕組みである。テンソル並列では、各GPUが計算した部分結果を全GPUで合計するAllReduceや、部分ごとに配布するReduceScatterを行う。専門家並列ではAll-to-All通信が必要になる。通常はGEMMの出力が完成するまで通信を待つため、計算と通信が直列化される。FlashOverlapはGEMM内部で計算が終わった出力タイルを識別し、残りのタイルを計算しながら完成分の通信を始める。

本研究の中心は、GEMMを小さなカーネルへ分割することも、集団通信をGEMM内へ手作業で融合することもなく、元の高性能なGEMM主ループを維持して細粒度重畳を実現する点にある。通信準備済みタイルの完了通知、通信に適した連続領域への並べ替え、通信後の順序復元、波群の自動分割を組み合わせる。RTX 4090の演算子単位の比較では非重畳実行比で最大1.65倍、A800上のLLM推論・学習・動画生成の端から端の比較では1.05～1.13倍の処理量改善を報告する。これらは**異なる測定範囲の数値**であり、単一GPU上のLLM復号速度が1.65倍になるという意味ではない。

## 問題設定

複数GPUによる大規模モデル実行では、重み・活性化・専門家のいずれかをGPU間で分割する。計算結果の共有に必要な通信は、AllReduce（全体への総和共有）、ReduceScatter（部分ごとの集約・配布）、All-to-All（相互送受信）などである。これらの通信は直前のGEMM出力に依存するため、単純なスケジューリングではGEMM全体を待ってから通信する。

従来の「分割型」はGEMMを小さな演算へ分割して、その間に通信を挟む。既存のcuBLAS/NCCLを利用しやすいが、小さなGEMMではGPUの行列演算器を十分に使えず、通信を細かくしすぎると通信帯域も活用できない。「融合型」は計算と通信を一つのカーネルへ統合する。細粒度で重ねられる反面、通信方式ごとに独自実装が必要で、GEMMのタイル設計や演算性能に干渉しやすい。

FlashOverlapは「(1)タイル単位に近い細粒度、(2)GEMMの計算性能を維持、(3)既存通信APIをそのまま利用」という3条件を同時に満たすことを狙う。通信を開始する単位を小さくすると早く開始できるが、送るデータが小さすぎると帯域効率が下がる。反対に大きな単位へまとめると通信帯域は向上するが、最初の送信が遅れる。このトレードオフが実装上の主要課題である。

## 手法

### 1. GEMM完了通知（Signaling）

GEMMは出力行列を多数のタイルへ分割し、GPUのストリーミングマルチプロセッサ（streaming multiprocessor、SM）で並列計算する。すべてのタイルが同時に終わるわけではなく、SMに配分されたタイル群は時間軸上で「波（wave）」としてまとまって完成する。著者らの例ではRTX 4090のGEMM（M=2048、N=K=8192）で512タイルが128個のSMへ分配され、4つの波として完成した。

FlashOverlapは、計算を終えたタイルが属する通信群のカウンタを原子的に増加させる。別のCUDAストリームで待機する通知用カーネルがカウンタを監視し、群内のすべてのタイルが完了した時点でその群の通信を開始する。GEMM本体は残りのタイルを継続計算する。これにより、全出力が完成するまで待つ必要がない。タイルごとの通知自体は細かすぎるため、実際の送信開始単位には複数タイルを束ねた波、さらに複数の波を束ねた波群を使う。

波群の選び方は重要である。タイル一枚の送信では十分な通信帯域を使えない場合があり、論文は4基のRTX 4090によるAllReduceで192KBのタイル一枚では帯域利用率が13%にとどまる例を示す。一方で巨大な波群は通信開始を遅らせる。波群の大きさは固定せず、通信と計算の時間関係に応じて調整する。

### 2. 通信前の並べ替えと通信後の復元（Reordering）

GEMMのタイルが完了する順序と、出力行列のメモリアドレス順序は一致しない。さらに2次元タイルは元の行列上で連続したアドレス領域とは限らない。NCCLの通常の集団通信APIは送受信に連続バッファを必要とするため、完成タイルをそのまま一括送信しにくい。

そこでGEMMの出力を保存する最終処理（epilogue）で、完成順に沿ってタイルを連続領域へ格納する。通信後には次の要素ごとの演算（RMSNorm等）へ順序復元を融合する。通信前の順序変更はGEMMの主ループを変更せず、通信後の順序復元も次の演算へ吸収することで、専用の大きな並べ替えカーネルを増やさない。

AllReduceでは、参加GPU間で対応する要素の順序が一致していれば、元の行列順と異なっても集約計算自体は正しい。ReduceScatterでは、配布先と要素位置の対応を維持する必要がある。All-to-Allでは行・トークンの送信先制約を守る必要がある。論文は通信種別ごとに並べ替え可能な範囲を整理し、通信の数学的意味を変えずに連続領域を形成する設計を示す。

重要なのは、通信中のバッファ順序は元の行列順でなくてもよいが、全GPU間の要素対応と通信後の最終結果は一致しなければならないことである。したがってこれは近似演算や精度を落とす高速化ではない。並べ替え対応表は小さく、主なコストはメモリアクセス順序と最終処理に生じる追加処理である。

### 3. 波群分割の予測探索（Predictive Search）

T個の波の間に通信開始境界を置くか否かを選ぶと、最後の波は必ず通信するため、可能な波群分割は概念上2^(T−1)通りになる。例えば5波なら、1波・2波・2波の3群に分けることも、2波・3波の2群に分けることもできる。すべての分割を実測して最適解を探すのは高価であり、GEMM形状やGPU間帯域が変わると最適解も変わる。

FlashOverlapは計算と通信の遅延を予測するモデルを使い、候補分割を絞って性能を推定する。これにより通信開始の早さと帯域効率の両方を考慮して波群を決める。論文の付録に示す評価では、予測探索は総当たり探索の最適性能に対して99%超の性能を達成し、予測器の平均誤差率は5%未満と報告する。ただしこの値は論文の計測環境・行列形状に対するもので、未知のGPUや負荷急変下で常に同じ精度を保証するものではない。

### 4. 実装と実行時の流れ

実装はCUTLASSのテンプレートGEMMを基盤とする。主ループはそのまま残し、通信前の並べ替えをGEMMのepilogueへ融合する。GEMMのCUDAストリームとは別のストリームでカウンタ監視とNCCL通信を実行する。カウンタが所定の完了タイル数に達するまで通信ストリームが待ち、達したら対応する連続領域の集団通信を開始する。通信終了後の順序復元はRMSNorm等へ融合できる。

この構成により、AllReduce・ReduceScatter・All-to-Allのような通信種別が変わっても、計算と通信を重ねる枠組みを使い回せる。通信APIそのものの内部実装を再開発する必要がない一方、GEMMの出力配置と次段演算を組み合わせる実装は必要である。通信ライブラリやGPU世代に依存する制約がなくなるわけではない。

論文はA800と4090でGPU間の接続帯域が大きく異なることを評価に組み込む。NVLinkで通信が比較的速いA800では重畳による追加利得が小さくなりやすく、PCIe越しの4090では通信時間を隠す効果が大きくなる。なお、Llama3-70BとMixtral-8x7Bの学習では単一ノードに収めるため層数をそれぞれ8層と4層へ減らしており、全層の通常学習を測った結果ではない。端から端の評価はA800であり、4090上で同じ1.05～1.13倍を再現したことを意味しない。

## 評価結果：主な実験結果

### 演算子単位の高速化

RTX 4090上では、FlashOverlapが非重畳実行比1.02～1.65倍、分割型比較では0.98～1.46倍の範囲だったと本文に記載される。分割型比較の下限0.98倍は、**常に分割型より高速というわけではない**ことを示す。GEMMが小さい、通信の占める割合が小さい、または融合型がメモリアクセスを削減できる形状では、FlashOverlapの優位が縮む。

著者らは重畳で得られる理論上の最大性能に対して69～98%を達成したと報告する。これは「非重畳比69～98%高速化」ではなく、**理論上の最良の重畳性能にどれだけ近づいたか**の比率である。GPU間帯域、GEMMサイズ、通信データサイズの関係によって最適な波群は変化する。

### 端から端の性能

A800上のvLLMを使ったLlama3-70B推論、Megatron-LMによるLlama3-70BとMixtral-8x7Bの学習、xDiTによるStep-Video-T2V生成で、対象の線形層とその直後の通信をFlashOverlapへ置換して測定する。論文§6.3は、各タスクの端から端の処理量で**1.05～1.13倍**の改善を報告する。演算子の最大1.65倍を全モデルの処理量へそのまま適用できないのは、モデル全体には注意演算、他の線形層、通信以外の処理などが残るためである。

A800はNVLinkで通信が比較的速く、重畳余地が少ない。動画生成は入力トークン数が大きくGEMM+通信の負荷が高いため、端から端の改善が相対的に大きいと著者らは分析する。推論ではLlama3-70BのTP=8・チャンクサイズ16384という特定条件で測定しており、単一GPU・バッチ1の復号には直接当てはめられない。

### 構成要素の効果と注意点

波群を小さくすると早く通信できるが帯域が低くなり、波群を大きくすると通信帯域を使いやすいが開始が遅くなる。論文の図14は固定の波群サイズと予測探索の比較を示し、最適分割がGEMM形状に依存することを示す。並べ替えは通信を細粒度で行うために必要だが、計算主ループを変えずにepilogueと後続演算へ融合することで追加コストを抑える。

非重畳の比較基準はcuBLAS+NCCLの直列実行であり、融合型・分割型との比較ではそれぞれの対応GPUや通信方式に差がある。例えばFLUXは論文で使ったRTX 4090サーバのGPU間ピアツーピアアクセスが利用できないため、4090側で同じ条件の比較が成立しない。したがって特定方式との優劣を全GPU環境へ一般化するのは避けるべきである。

## 既存方式との差

分割型は既存通信APIをそのまま使えるがGEMMの形状を細分化して計算性能を損なう。融合型は通信開始を細粒度で制御できるが、通信処理をカーネル内に実装するため適応負担が大きい。FlashOverlapは完了通知を使ってGEMMを一つのカーネルのまま維持し、通信のためにタイル順序を変えることでNCCL APIを再利用する。計算と通信の分離を保ちながら、通信開始だけを細かく制御する点が独自である。

本手法はモデル重みの圧縮、KVキャッシュの削減、投機的復号のようにトークン数やメモリ使用量を直接減らす方式ではない。通信を伴う並列実行で、計算待ちと通信待ちの重なりを増やす方式である。MoEの専門家並列や複数GPUテンソル並列など、通信が実際のボトルネックである環境に適する。

## 実装・適用上の制約

著者の公式実装はCUDA/CUTLASS/NCCLを利用する。公開READMEではRTX 3090、RTX 4090、A800、A100を評価済みとし、SM 80/86/89に対応すると記載する。GEMMのM・Nが128の倍数でない場合の境界処理は未実装とされる。AllReduceとReduceScatterのデモは公開されるが、All-to-Allのデモと端から端の例は未完了の項目として残る。論文で実験したすべての構成が公開リポジトリの現状でそのまま再現可能と断定しない。

ローカルのRTX 4070 SuperはSM 89世代だが、単一GPU構成ではGPU間通信が発生しないため、この重畳方式の直接の適用対象ではない。将来、PCIe接続の複数GPUでテンソル並列を構築した場合には関連する可能性がある。ただしGPU世代の互換性だけでは動作保証にならず、通信接続・GPU間ピアアクセス・GEMM形状・ビルド依存関係を別途確認する必要がある。

## 限界

通信が短い、GEMMが短い、または既存実装で十分に通信が隠蔽されている場合、通知・並べ替え・複数ストリームの固定費が相対的に増える。波群分割の予測器は負荷と帯域が急変する環境で精度を落とし得る。集団通信のAPIは再利用できても、正しい順序復元を伴うカーネル統合は必要であり、任意のモデルへ設定なしで差し込めるわけではない。

また、評価の端から端高速化は最大1.13倍程度で、演算子単位の最大1.65倍より小さい。これらを混同してLLM推論全体が1.65倍になると述べるのは不適切である。品質の近似を伴わないため生成内容の正しさを維持する設計だが、通信順序の誤実装や同期の不備は結果の破損につながるため、GPU構成ごとの正しさ検証が必要である。
