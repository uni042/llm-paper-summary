# Deep Kernel Fusion for Transformers

> SwiGLU前半を単一CUDAカーネルへ深く融合して中間活性のHBM往復を削減し、事前プロファイルでGPU・バッチ別のタイル方式を選んでSGLangのデコードを最大13.2%高速化する。
## 書誌情報
- **著者**: Zixi Zhang, Zhiwen Mo, Yiren Zhao, Robert Mullins
- **著者・所属**: Imperial College London; University of Cambridge
- **公開**: arXiv
- **種別**: Preprint
- **対象**: SwiGLU、CUDAカーネル融合、HBM帯域、Tensor Core、SGLang、テンソル並列
- **実装**: DeepFusionKernelをCUDAで実装しSGLangへ統合する。事前プロファイルで候補カーネルを選択後、CUDA Graphへ取り込むため推論反復ごとの分岐・選択費用は発生しない。一次資料から論文固有の公式コード公開URLは確認できない。
## 概要
長文脈・長生成の大規模言語モデル推論ではKVキャッシュが増えて実用バッチサイズが小さくなり、SwiGLU型MLPの巨大な重みを毎トークン高帯域メモリから読む費用が支配的になる。DeepFusionKernelは、SGLangやvLLMで二つ以上のCUDAカーネルに分かれる上射影・ゲート射影・SiLU・要素積を単一カーネルへ深く融合し、大きな中間活性を高帯域メモリへ書き戻さずレジスタ・共有メモリ上で流す。行優先と列優先のタイル順序を用意し、モデル形状、バッチ、GPUごとに短い事前測定で最速候補を選ぶ軽量カーネルスケジューラとSGLang統合を組み合わせる。Llama 3.1 70Bを4基のA100またはH100 80GBでテンソル並列4、FP16として評価し、出力1024トークンではSGLang比でA100最大9.7%、H100最大13.2%のデコード処理率向上を示す。出力16384までの長生成でも改善を維持し、注意機構のKV負荷が増えてもMLPの重み交通削減が有効であることを示す。

DeepFusionKernelはSwiGLUの二つの入力射影とSiLU・要素積を一つのCUDAカーネルにまとめ、巨大な中間活性をHBMへ書かずオンチップで次処理へ渡す。さらに、活性行の再利用を優先する行優先タイルと、重みタイルの再利用を優先する列優先タイルを含む複数候補を用意し、モデル形状、バッチサイズ、GPU世代、分散構成ごとに短い事前プロファイルで最速候補を選択する。融合を静的なコンパイル規則として固定せず、実サービング環境でハードウェア依存のメモリ・計算比を測って選ぶ点と、選択後はCUDA Graphへ取り込み反復時の分岐費用を消す点が特徴である。

代表結果として、A100最大デコード速度向上はLlama 3.1 70B FP16、TP=4、B=16、出力1024でSGLangに対して+9.7%（453.75→497.69 トークン/s）。小〜中バッチの帯域律速域で中間HBM交通削減がモデル全体処理率へ反映される。
## 問題設定
エージェント型の長文脈推論では、一要求が通常の対話より桁違いに多くのトークンを処理し、KVキャッシュがGPUメモリを圧迫するため大きなバッチを組みにくい。小バッチの自己回帰デコードではTensor Coreの演算能力を使い切る前に高帯域メモリからモデル重みを読み込む時間が支配し、とくにSwiGLU MLPは上射影、ゲート射影、活性化、要素積、下射影という複数処理と巨大な重みを持つ。SGLangやvLLMの既存実装は上射影とゲート射影をまとめても、中間活性を一度HBMへ物質化してから次カーネルで読み戻すため、演算量が少ないデコードではこの往復が相対的に大きい。単純にすべてを融合するとレジスタ・共有メモリ圧やタイル再利用の方向が悪化し、GPUやバッチサイズによっては逆効果になるため、融合深度だけでなくループ順序とタイル形状を実行条件へ合わせる必要がある。
## 新規性
DeepFusionKernelはSwiGLUの二つの入力射影とSiLU・要素積を一つのCUDAカーネルにまとめ、巨大な中間活性をHBMへ書かずオンチップで次処理へ渡す。さらに、活性行の再利用を優先する行優先タイルと、重みタイルの再利用を優先する列優先タイルを含む複数候補を用意し、モデル形状、バッチサイズ、GPU世代、分散構成ごとに短い事前プロファイルで最速候補を選択する。融合を静的なコンパイル規則として固定せず、実サービング環境でハードウェア依存のメモリ・計算比を測って選ぶ点と、選択後はCUDA Graphへ取り込み反復時の分岐費用を消す点が特徴である。
## 手法
### 手法のあらまし
SwiGLUは入力XからUp重みとGate重みの二つの行列積を計算し、Gate側へSiLUを適用してUp側と要素積し、その結果をDown重みとの行列積へ渡す。既存の二カーネル実装では前半の二行列積と活性化をまとめても、その出力A2をHBMへ書き、後段のDown行列積が再び読む。DeepFusionKernelは前半の二行列積とゲート演算をタイル単位で同一カーネル内へ融合し、入力・重みタイルを共有メモリやレジスタへロードした後、Tensor Coreの積和結果にSiLUと要素積を適用し、不要な中間テンソルのグローバルメモリ往復を除く。タイル走査には二つの主候補があり、行優先は同じ入力行を複数重みタイルへ使い回して活性の再読出しを減らし、列優先は同じ重みタイルを複数入力へ使い回して巨大重みの読出しを減らす。小バッチ・大モデルのデコードでは重みが主役なので列優先が有利になりやすい一方、バッチが増えると入力再利用の価値が上がる。タイル寸法もレジスタ数、共有メモリ占有、Tensor Core利用率の交換条件を持つため、軽量スケジューラが対象モデル・バッチ・GPU上で候補を短時間測定して最高処理率の実装を選ぶ。分散推論ではUp/Gateを列分割、Downを行分割することでSwiGLU中間値を各GPU内へ留め、ブロック末尾のAllReduce一回だけで最終出力を統合する。選択したカーネルはSGLangのFlashInfer・CUDA Graph実行へ組み込み、以後のデコード反復では動的選択を行わない。

### SwiGLU深層融合カーネル
上射影とゲート射影のGEMM、SiLU、要素積を一つのCUDA演算へ統合し、中間A_up、A_gate、A_silu、A2を別々の大規模HBMテンソルとして何度も物質化する経路を削減する。入力と重みのタイルをオンチップへ運び、Tensor Coreの部分積をレジスタで保持したままゲート処理まで進めるため、演算FLOP数を増やさずグローバルメモリ交通を削減する。Softmaxのような大域縮約はSM間依存が強く深い融合に不向きだと切り分け、タイル局所性の高いSwiGLU前半に対象を絞ることで、融合による同期・占有率悪化を避ける。

### プロファイル駆動カーネルスケジューラ
融合カーネルの最適なループ順序とタイル形状は、重み容量、入力バッチ、GPUの演算対帯域比、分散通信条件によって変わる。そこで行優先・列優先と複数タイル寸法を候補として準備し、推論開始前に対象条件上で短時間ベンチマークする。行優先は入力活性の局所性、列優先は重みキャッシュ再利用を高めるため、小バッチの長生成では後者、より大きいバッチでは前者が選ばれやすい。最速候補を決めた後はSGLangがCUDA Graphへ固定するので、毎トークンのデコード時に探索や条件分岐を繰り返さず、事前測定費用を長い生成へ償却できる。

### テンソル並列対応の通信配置
Llama 3.1 70Bを4GPUで動かす際、UpとGateの重みは出力列方向に分割し、各GPUが自分の中間特徴を局所的に計算する。Down重みは行方向に対応させることで、Up/GateからDownへ渡る大きな中間活性をGPU間で集める必要をなくし、SwiGLUブロック末尾で部分出力を一回AllReduceするだけにする。DeepFusionKernelはSGLangの既存集団通信を変更せず、この配置の中で各GPUのMLPメモリ交通を減らす。したがって通信アルゴリズムの改善ではなく、通信量を増やさずローカルカーネルを短縮する設計であり、通信ジッタは基準系と同じまま残る。

### 全体のデータ／制御の流れ
SGLangの既存推論スタックへ融合カーネルと事前選択スケジューラを挿入し、注意機構、KV管理、AllReduce、要求スケジューリングは既存実装を再利用する。そのため最適化範囲をSwiGLU MLPへ限定しながら、単体カーネルではなくモデル全体のデコード処理率で効果を測る。
## 評価条件
- **ハードウェア**: 4×NVIDIA A100 80GB SXMまたは4×NVIDIA H100 80GB SXMを用い、テンソル並列4でLlama 3.1 70Bを実行する。H100はA100より演算能力が大きく、論文は1979 TFLOPs/s対312 TFLOPs/sとして、演算能力増加に対して帯域が相対的制約として残る点を議論する。
- **ソフトウェア**: SGLang v0.4.6.post4へDeepFusionKernelを統合し、FlashInferとCUDA Graphsを有効化する。比較はSGLang既定カーネル、vLLM v0.10.1.1、PyTorch分散推論。
- **モデル**: Llama 3.1 70B FP16
- **データセット／トレース**: 合成デコード設定：入力長1、出力長1024、長生成設定：出力長1024/4096/16384
- **比較対象**: SGLang default カーネル、vLLM、PyTorch distributed inference
- **正確性・品質**: 同一のLlama 3.1 70B FP16計算を実行し、融合カーネルは中間値の物質化順序を変えるだけでモデル・生成条件を変えない。主評価はデコードスループットで、各構成を4回測り平均と標準偏差を報告する。
- TP=4
- 入力長1
- 基本評価の出力長1024
- バッチ1/2/4/8/16/32/64
- 長生成はバッチ1/4/16、出力1024/4096/16384
- 事前プロファイラで融合カーネル候補を選択
- 選択後CUDA Graphで固定
まずモデル全体のデコードでバッチ1〜64を掃引し、A100/H100それぞれについてPyTorch、SGLang、DeepFusionKernelの処理率を比較する。次に長文生成を想定して出力長を1024、4096、16384へ伸ばし、バッチ1、4、16でSGLang、vLLM、DeepFusionKernelを比較し、KVキャッシュと注意機構の負担が増えた状態でもMLP融合の利得が維持されるかを確認する。DeepFusionKernelは同じSGLang集団通信を使うため、GPU間通信方式は統制されるが、実測のばらつきには通信ジッタが含まれる。
評価は70B級FP16モデル、4GPUテンソル並列、A100/H100 SXMという単一ノード中心の構成に限定される。異なるGPU間接続、ノード間ネットワーク、量子化モデル、MoE、他のMLP形状を網羅的には測らない。最適化対象はデコードのSwiGLUであり、入力処理や注意機構そのものは変更しない。
## 主要結果
DeepFusionKernelは4GPUテンソル並列のLlama 3.1 70BデコードでSGLangの既定実装を一貫して上回り、出力1024ではA100で最大9.7%、H100で最大13.2%の処理率向上を示した。A100のバッチ16では453.75から497.69 トークン/s、H100のバッチ2では107.05から121.13 トークン/sへ改善する。一方、バッチが大きく演算律速へ近づくとA100バッチ64の改善は1.3%まで縮む。出力を16384まで伸ばした長生成でも全評価点でSGLang/vLLMを上回り、KVキャッシュ・注意機構の費用が増加してもMLPのHBM交通削減が残ることを確認した。実用上は、モデルや推論スケジューラを変更せず既存SGLangへ局所的に導入でき、長生成の総トークン数が大きいほど小さな一トークン当たり短縮を繰り返し積み上げられる。

- A100最大デコード速度向上 / +9.7%（453.75→497.69 トークン/s） (比較対象: SGLang; 条件: Llama 3.1 70B FP16、TP=4、B=16、出力1024) — 小〜中バッチの帯域律速域で中間HBM交通削減がモデル全体処理率へ反映される。

- H100最大デコード速度向上 / +13.2%（107.05→121.13 トークン/s） (比較対象: SGLang; 条件: Llama 3.1 70B FP16、TP=4、B=2、出力1024) — 演算能力が大きいH100でも小バッチではメモリ帯域が相対的ボトルネックとして残る。

- A100大バッチでの改善 / +1.3%（1391.76→1410.39 トークン/s） (比較対象: SGLang; 条件: B=64、出力1024) — 演算律速へ寄ると融合によるメモリ交通削減の限界利得は小さくなる。

- A100長生成 B=1 / 出力16384で34.97→36.79 トークン/s (比較対象: SGLang; 条件: TP=4、FP16) — KVキャッシュ増大後もMLPが十分な割合を占めるため利得を維持する。

- H100長生成 B=4 / 出力4096で219.48→234.61 トークン/s (比較対象: SGLang; 条件: TP=4、FP16) — 長生成・軽い並行実行でも選択カーネルが既定SGLangを上回る。

### 負の結果・境界条件
- 利得は全条件で一定ではなく、A100ではバッチ64で1.3%まで低下する。論文は異なるGPUクラスタ間接続を網羅せず、GPU間通信の変動を定量分離していない。DeepFusionKernelは既存AllReduceをそのまま用いるため通信ボトルネックそのものは改善せず、高並行度では通信ジッタが処理率分散を増やす。

### 結果の読み方
深い融合の価値はカーネル起動回数削減より、巨大な中間活性をHBMへ往復させないことにある。長文脈でKVキャッシュが大きくなると注意機構費用は上がるが、SwiGLU重みも毎トークン読み込む必要があるため、MLPの局所最適化は長生成でも消えない。事前プロファイルがGPU・バッチに合うタイル順序を選ぶことで、固定融合の逆効果を避ける。
## 品質への影響
FP16の同一数式を計算順序・タイル配置だけ変更し、量子化・枝刈り・推測生成を導入しない。論文は品質指標を別途測定していないが、アルゴリズム上は生成意味品質との交換条件を持たない。
## 既存研究との差
SGLangやvLLMは既にGEMMと要素演算の浅い融合を用いるが、DeepFusionKernelはUp/Gate GEMMとSiLU・ゲート積を単一CUDAカーネルへ押し込み、大規模な中間活性のHBM物質化を避ける。WelderやTVMの一般コンパイラ融合はグラフ・パターン規則から候補を決めるのに対し、本手法はSwiGLUへ特化した複数のタイル走査を用意し、配信先GPUと実バッチ上のプロファイルで選択する。BlockbusterのSwiGLU融合試作と比べても、SGLang統合、テンソル並列、CUDA Graph、長生成のモデル全体処理率まで評価する点がシステム寄りである。
## 限界
評価はLlama 3.1 70B FP16と4基A100/H100のテンソル並列に集中し、量子化、MoE、異なるFFN比率、ノード間ネットワークを網羅しない。GPU間通信方式はSGLang既存実装を継承し、その時間変動を独立に定量化していないため、規模拡大で通信が支配する条件の効果は不明である。最適候補を選ぶ事前プロファイルが必要で、頻繁にモデル形状やバッチ領域が変わる配信では再測定が必要になり得る。融合対象はタイル局所性の高いSwiGLU前半であり、Softmaxのような大域縮約まで同じ方法で深く融合できない。
## 実装状態
CUDAのDeepFusionKernelと軽量プロファイル駆動スケジューラをSGLangへ統合して実機評価している。PyTorch 2.6.0、SGLang v0.4.6.post4、vLLM v0.10.1.1等の版は明記されるが、論文固有コードの公式公開URLは一次資料で確認できない。
## 研究上の位置づけ
LLM推論のカーネル・ランタイム共同設計に位置し、注意機構・KVキャッシュ中心の最適化に対して、長生成の小バッチではSwiGLU MLPの重み交通も主要ボトルネックになることを示す。汎用コンパイラではなくモデル構造に特化した深い融合と、実行時条件を測る軽量スケジューラの組合せで、局所カーネル改善を既存配信基盤のモデル全体速度へ接続する。
