# Perseus：複数ノードMoE巨大GPUカーネルの隠れた通信直列化を解消する

## 概要

専門家混合モデル（Mixture of Experts、MoE）では、各トークンを選択された専門家のGPUへ送り、計算結果を次の層へ返す必要がある。専門家を複数GPU・複数ノードに分散すると、転送と計算の重畳が推論性能を左右する。最近の巨大融合GPUカーネル（megakernel）は、層全体の一括通信ではなく、専門家計算の小さなタイルが完成するたびにGPUから通信を発行し、受信側が到着済みのタイルから処理を始める。単一ノードでは有効だが、遠隔直接メモリアクセス（Remote Direct Memory Access、RDMA）を使う複数ノードでは性能が急落する場合がある。

本論文は、通信遅延の根本原因を**データ転送と完了通知の間の順序保証が、ネットワークインターフェース（NIC）の転送パイプラインを繰り返し排出してしまうこと**と特定する。CPUプロキシ経由のRDMAでは、各タイルのPUTの後に完了通知を送るためのfenceが必要になり、そのたびに多数の未完了転送を待ってしまう。計算の小さい専門家では、この隠れた直列化が計算と通信の重畳余地を消す。

提案システム**Perseus**は、(1)GPU側でデータ転送と通知を分離し、宛先群ごとに順序保証をまとめる**分離通知（decoupled signaling）**、(2)CPUプロキシが転送完了を待つ代わりに、NICのハードウェアfenceフラグで通知の順序を保証する**NIC側順序制御（NIC-side ordering）**を組み合わせる。論文は、プロキシ経由のLibfabric上でMoEの端から端の処理を最大**10.3倍**、IBRC上で最大**2.47倍**高速化したと報告する。これは複数ノードの特定の通信律速条件での倍率であり、単一GPUや通常のLLM推論全般の速度改善を意味しない。

## 問題設定：MoEの専門家並列と通信・計算重畳

MoEの各層は、ルータがトークンごとに少数の専門家を選び、その専門家の重みを持つGPUへ入力を送る。専門家計算後の出力を集めるまで次の層へ進めないため、専門家間の全対全（all-to-all）通信が推論のクリティカルパスに入る。従来のNCCL型一括集合通信では、全GPUが通信を完了してから専門家計算へ進むため、転送中のGPU計算資源が待ちやすい。

巨大融合GPUカーネルは、この粗い同期を避ける。専門家出力を小タイルに分け、あるGPUがタイルを計算した時点で非同期PUTを発行し、受信GPUに「このタイルは読める」というシグナルを送る。受信側は他のタイルの到着を待たずに処理を始められる。単一ノードではGPU間の高速接続が短い通信遅延を提供するため、タイル単位の重畳が効果を発揮する。

複数ノードになると、同じ仕組みをRDMAネットワークへ持ち出す必要がある。GPUが通信要求を出しても、実際のRDMA送信はCPU側のプロキシが仲介する方式と、GPUがNICへ直接要求する方式がある。前者のプロキシ方式では、PUTしたデータが相手のメモリに到着する前に「到着済み」のシグナルを送ると誤動作する。したがってPUTとシグナルの間には順序保証が必要だが、その実装がGPUの細粒度重畳と相性が悪い。

論文の図1では、通信律速のQwen3-30Bが8ノードへ拡張された際に、単一ノード基準の理想的な拡張に比べ最大約10倍遅くなる例を示す。一方、専門家当たりの計算量が大きいLlama4は、通信が遅くてもその時間を計算で隠しやすく、同じ程度の悪化を示さない。これは**MoEであればすべて同じ効果が得られるわけではなく、専門家の演算密度と通信量の比が重要**であることを示す。

## 隠れた直列化の原因

### 1. PUT・FENCE・SIGNALの繰り返し

タイルごとの通知を正しく順序付ける典型的な実装は、PUT（データ転送）→FENCE（先行転送の完了待ち）→SIGNAL（到着通知）という三段階を一組として実行する。これを各専門家タイルが独立に発行すると、CPUプロキシの送信キューには多数の三つ組が交互に入る。

プロキシ型RDMAのfenceは単にソフトウェアの軽いメモリバリアではない。プロキシがNIC上の未完了転送を確認し、先行転送が完了するまで後続の通知を送らないため、NICのパイプラインが実質的に排出される。転送の同時数が増えるほど、一つのfenceが待つ先行通信も増える。GPU側はタイルを非同期に発行しているつもりでも、NICへ到達する段階で直列化してしまう。

論文のQwen3-30Bの例では、96の遠隔専門家転送があると、従来方式は**96回のパイプライン排出**を生む。8ノード・96同時転送では、通知付きPUTの実効転送量が通知なしPUTの**わずか2%**にまで落ちる測定がある。これは転送データ量そのものが増えたためではなく、正しい通知順序を保証する方式の費用が並列性を破壊するためである。

### 2. 通信律速と計算律速の違い

タイルの専門家計算時間が通信の待ち時間より十分長ければ、NICの遅延をGPU演算の背後に隠せる。大きな専門家計算を持つモデルではその余裕がある。一方、小さな専門家を多数呼ぶQwen3のような構成では、タイルの計算がすぐ終わり、次に必要なデータや通知がまだ届かないためGPUの演算器が空く。論文のGPUストリーミングマルチプロセッサ（SM）の実行トレースは、通信律速の構成で待機が多いことを示す。

したがって改善すべき対象は、通信の総バイト数やネットワーク帯域だけではない。**タイルが読めることを知らせる通知を正しい順序で発行しながら、NICの並列転送を止めないこと**が問題の中心となる。

## 手法

### 1. 分離通知：データ転送を先行させ、宛先ごとに順序保証をまとめる

Perseusの第一の工夫は、各GPUスレッドブロック（Cooperative Thread Array、CTA）がPUTとSIGNALを一体で発行しないことだ。まず全CTAが担当タイルのPUTを非同期に発行し、宛先群の共有カウンタを更新する。各群のリーダーCTAだけが群内のPUT発行を確認し、一度だけfenceを実行してから、その群に属する全タイルの通知をまとめて送る。リーダー以外のCTAは通知待ちの間に別の計算へ戻れる（論文アルゴリズム1）。

これによりNICは多数のPUTを先に受け取り、ネットワーク上で並列に進められる。PUTとSIGNALが交互に入るのではなく、PUTのまとまった列の後にfenceとSIGNALの列が続く。重要なのは、**各PUTの直後にfenceを置く必要はなく、先行するすべてのPUTと、その完了を示す通知の間に正しい順序があればよい**という点である。

Qwen3の96遠隔専門家の例では、12の宛先処理要素（PE）に分けた群ごとに一回のfenceを置けば、96回を**12回**へ減らせる。これは8分の1、すなわちfence回数を8倍削減する。図6は、従来方式の96組のPUT/FENCE/SIGNALに対し、Perseusでは96個のPUTを先に並べ、12個だけにNIC側fenceフラグを付けた96通知を後から送る構造を示す。

分離通知はGPU側の通信発行順序を変えるもので、ネットワークに存在しない帯域を増やすわけではない。データ依存のあるPUTがすべて完了してから通知が有効になるという正しさは保持する。群が大きすぎると群内の遅い転送が他の通知を遅らせる可能性もあり、群サイズは同時転送数とメッセージ長に応じて選ぶ必要がある。

### 2. NIC側順序制御：CPUプロキシの待機をハードウェアへ移す

分離通知だけでは、群ごとのfenceがCPUプロキシを停止させる問題が残る。Perseusの第二の工夫は、LibfabricのFI_FENCEやInfiniBand verbsのIBV_SEND_FENCEに相当するNICの順序保証フラグを利用し、**プロキシが送信完了をポーリングして待つ代わりに、NICが通知を先行PUT完了まで遅らせる**ことだ。

プロキシはfence要求を受けたときに自身で送信キューを排出せず、次のSIGNALへハードウェアfenceフラグを付けてNICへ渡す。NICは同じ接続上の先行操作が完了するまでフラグ付き通知の実行を遅らせる。これによりプロキシは待機せずに次の要求を送信できる。CPUプロキシが停止することによるキュー詰まりを解消する設計である。

ただし**NIC側順序制御だけ**では、通知ごとにフラグを付けるとNIC内部の順序待ちが多発し、パイプラインが依然として詰まりうる。図2は、(a)従来のPUT/FENCE/SIGNAL、(b)分離通知だけ、(c)NIC側順序だけ、(d)両方を組み合わせたPerseusを比較する。Perseusでは群の最初の通知だけがfenceフラグを持ち、残りの通知はその後に続くため、**プロキシ停止なし**と**NIC内部のfence回数削減**を同時に実現する。

### 3. GPUカーネルと通信層の接続

PerseusはMoEの専門家演算そのものを新しい数値近似へ置き換えるのではなく、専門家間のタイル転送と通知の順序を最適化する。各GPUのCTAは専門家入力・出力のタイルを転送用バッファへ置き、非同期PUTを発行し、群の進捗を共有カウンタで管理する。群リーダーがfence付き通知を出すと、受信側GPUは通知を見て対応タイルの次段階を開始できる。データ到着前の通知を許さないという安全性を守りつつ、送信側ではタイル転送をまとめて流す。

この変更は、計算・通信重畳を前提とする巨大融合GPUカーネルで特に効く。通常の集合通信型MoEは、すでに大きな同期点を持つため、同じタイル通知の直列化が支配的であるとは限らない。Perseusは巨大カーネルの通信発行方式とRDMA輸送層を共同で最適化する提案である。

## 主要結果

### 1. 端から端のMoE推論遅延

| 比較 | 報告された最大改善 | 解釈 |
|---|---:|---|
| Perseus / 従来Libfabricプロキシ | **10.3倍** | 隠れたfence直列化が強い条件でのMoE順伝播高速化 |
| Perseus / 従来IBRCプロキシ | **2.47倍** | InfiniBandプロキシでも順序制御の改善が有効 |
| PerseusをIBRCで実行 / 未最適化IBGDA GPU直接通信 | **最大1.2倍** | CPUプロキシ方式でも直列化を除けばGPU直接方式に匹敵しうる |
| Triton-Distributed ALLTOALLで輸送層変更 | **最大79倍** | 通信マイクロベンチマークの改善でありLLM全体の倍率ではない |

これらの結果は、ネットワーク転送の理論帯域が不足しているだけでは説明できない性能悪化を、通信プロトコルの順序保証の変更で回復できることを示す。とくに通信律速のMoEで、タイル到着を待つGPUの空き時間が減ることが端から端の利得につながる。一方、計算律速モデルでは元から通信を計算で隠せるため、同じ倍率を期待できない。

### 2. 96並列転送のスループット回復

論文のマイクロベンチマークでは、8ノード、96並列、4KBメッセージの条件で、通知付きPUTの転送量は通知なしPUTの**2%**まで低下する。Perseusを適用すると、同じ比較基準の**74%**まで回復する（図14）。これは「2%から74%」であって、通信リンクの絶対帯域が74倍になったという意味ではない。もとの通知なしPUTを100%とした相対値であり、完全に100%へ回復しているわけでもない。

メッセージが大きい条件では、Perseusは通知なしPUTの基準へ近づくと報告する。小メッセージでは通知とfenceの固定費用が相対的に大きく、並列転送の制御方式の影響が強い。通信が大きな一括転送に置き換わる場合や、すでにNICが十分に並列化できている場合は、追加改善が小さくなる可能性がある。

### 3. スケーリングとGPU計算資源の稼働率

| 指標 | 従来方式 | Perseus | 意味 |
|---|---:|---:|---|
| Qwen3の16ノード弱スケーリング悪化倍率 | 19倍 | 3.5倍 | ノード数増加に伴う通信直列化の悪化を抑制 |
| Qwen3-30B、4ノード・1KのTensorCore利用率（単一ノード比） | 31% | 95% | 通信待ちによるGPU空転が大きく減少 |
| GPT-OSS-120B、同条件のTensorCore利用率 | 75% | 98% | 計算の重畳余地が回復 |

図14と表2の数値は、単にRDMAの転送が速くなっただけでなく、GPUが通信待ちをせず専門家計算を続けられるようになったことを示す。特にQwen3では単一ノードを100%としたTensorCore利用率が31%から95%へ上昇し、巨大カーネル本来の計算・通信重畳が回復する。

ただし16ノードでも悪化倍率3.5は残っており、完全な線形スケーリングを達成したわけではない。ネットワークの物理的な帯域・遅延、負荷不均衡、専門家配置など、fence直列化以外の制約は引き続き存在する。

### 4. NCCL型集合通信との関係

Triton-Distributed ALLTOALLの比較では、未最適化のGPU発行通信がNCCLに対して平均18.7倍遅い条件があり、Perseus導入後には逆にNCCLより最大11倍速いと報告する（図13の説明）。この対比は、GPU発行という形式だけで高速化が決まるのではなく、**転送と通知の順序保証がGPU発行通信の利益を消していた**ことを示す。

しかしNCCLとの比較は特定のALLTOALLマイクロベンチマークであり、NCCLを使うすべてのMoE推論構成で11倍高速になるという主張ではない。通信量、メッセージ長、ノード数、専門家配置によって集合通信の費用も変わる。論文の数値を実サービスの総トークン生成速度へそのまま換算するのは適切でない。

## 既存研究との差

NCCL型の集合通信を中心とするMoE専門家並列では、通信と計算を層単位で区切り、集合的な同期がボトルネックになる。巨大融合GPUカーネル研究はこの問題に対し、タイル単位の非同期通信と計算重畳を導入した。しかし既存のGPU発行通信ライブラリを複数ノードへ持ち出すと、CPUプロキシ・NICの順序保証で隠れた直列化が生じることをPerseusは示す。

本研究の新規性は、MoEの演算を量子化・近似することでも、単にNCCLを別ライブラリへ置き換えることでもない。**通信発行順序（PUTとSIGNALの分離）**と**転送順序を保証する主体（CPUプロキシからNICへ）**を同時に変更し、正しい到着通知を保ちながらNICのパイプラインを空にしない点にある。

この工夫はRDMA輸送層にも及ぶため、MoE以外のGPU発行ALLTOALLへも応用できる。一方、GPU内で完結する単一ノード推論や、そもそもCPUプロキシによるfence待機がない通信経路では、同じ問題構造が存在しない場合がある。

## 限界・適用条件・負の結果

第一に、通信が律速であることが大きな利得の前提となる。Llama4のように専門家当たりの計算が重い場合、通信遅延が計算の背後に隠れるため、Qwen3と同じ端から端の倍率を期待できない。大規模な専門家を持つMoEのすべてが通信律速とは限らない。

第二に、分離通知の群サイズは性能に影響する。群を大きくするとfence回数を減らせる一方、群内の転送完了を待つ必要があり、通知の遅延や不均衡が生じる可能性がある。論文図7・図8は群サイズと遅延の関係を測定し、単純に最大群へまとめるだけで最適になるわけではないことを示す。NIC側順序だけ、分離通知だけの構成も両方併用には及ばない条件がある。

第三に、NICのfenceフラグとCPUプロキシの実装に依存する。FI_FENCEやIBV_SEND_FENCEの順序意味論、接続ごとの保証範囲、NIC世代による実装差を理解する必要がある。通信が完了する前に通知を可視化すると誤った計算結果になるため、単なるfence削除ではなく、**必要な順序保証を別の場所へ移す**ことが本質である。

第四に、最大10.3倍・2.47倍は特定の通信律速構成での端から端MoE順伝播の改善であり、一般のユーザー向けLLMサービングの要求処理量、初回トークン遅延、バッチサイズなどを包括的に比較した結果ではない。GPU間通信をほぼ使わない小規模モデルや単一GPUでの性能を改善する根拠はない。

第五に、96並列4KB転送の74%回復や16ノードの3.5倍悪化残存は、Perseusが物理ネットワークの限界を消すわけではないことを示す。帯域不足、ネットワーク競合、モデル側のルーティング偏り、巨大カーネルの実装効率などは別の制約として残る。プロキシ型とGPU直接型の優劣もNIC・ソフトウェア版・負荷で変わる。
