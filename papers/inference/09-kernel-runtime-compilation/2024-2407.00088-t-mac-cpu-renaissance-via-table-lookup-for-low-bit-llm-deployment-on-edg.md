# T-MAC：低ビット重みの乗算をCPU上の部分和表参照へ変換する推論カーネル

## 概要

重みのみを低ビット量子化した大規模言語モデルでは、重みは1〜4ビットでも活性値は8〜16ビット以上の精度を保つことが多い。CPUが直接扱える演算命令は、このような低ビット重みと高精度活性値の組合せに最適化されているとは限らない。従来の推論実装は、圧縮された重みを展開・逆量子化してから高精度の積和演算を行うため、重みのメモリ量を減らしても実際の演算費用が比例して下がらない。

T-MACは、重みをビット面に分け、活性値の小グループについて可能な符号パターンの部分和を表にしておく。重み側のビット列を索引として表を引き、取り出した値を加算することで、低ビット重みを高精度値へ戻す処理と多数の乗算を避ける。表をCPUのレジスタへ収める配置、軸の並べ替え、タイル化、表の量子化・対称性利用、SIMD表参照命令を組み合わせて、低ビット化の利得を実際のCPU速度へ結び付ける。

Apple M2 Ultra、Jetson AGX Orin、Surface Book 3、Raspberry Pi 5を使い、低ビットLlamaとBitNetを評価する。論文はカーネルの最大6.6倍、平均3.6倍の改善、モデル全体で条件により2〜4倍の生成速度改善を報告する。BitNet-b1.58-3BではM2 Ultraの1コアで約30トークン/秒、8コアで約71トークン/秒、Raspberry Pi 5で約11トークン/秒を示す。改善倍率は演算単体かモデル全体か、ビット幅・CPU・スレッド数によって異なるため区別する必要がある。

## 問題設定

低ビット重みと高精度活性値の行列積は混合精度行列積（mixed-precision GEMM）である。たとえばW4A16は重み4ビット、活性値16ビットを意味する。CPUの通常の行列積は同じ精度の数値型同士を効率よく計算する設計が多く、W3A16やW2A16をそのまま扱えない。そのため重みをいったん8ビットなどへ展開し、積和命令へ渡す。3ビット重みは8ビットの境界と合わず、詰め込み・展開の処理も複雑になる。

従来のllama.cppでは、4ビットから2ビットへ重みを減らしても演算時間が必ずしも減らず、3ビットでは4ビットより約15%遅くなる例が論文の測定にある。圧縮率と演算効率が別物であることを示す結果である。端末側の単一要求の復号は、毎トークン重みを読みながら行列・ベクトル積を行うことが多く、逆量子化やメモリ帯域が律速になりやすい。

T-MACの設計目標は、量子化ビット幅ごとに異なる高精度演算カーネルを作る代わりに、ビット面と表参照という共通の計算形へ変換し、重みビット数を下げたときに必要な処理も減る構造を作ることである。ただし、表参照では索引に応じた不規則なアクセスと一時表の容量が増えるため、演算回数の削減だけでは速くならない。

## 手法

### 重みのビット面分解

重みWがbビットなら、各ビット面W_iの重み付き和としてWを表現し、活性行列Aとの積をビット面ごとの積の和へ分解する。基本形はA W = Σ_i 2^i A W_iである。各W_iは一ビットの値からなるため、一般の高精度乗算ではなく、活性値の符号付き和へ変換できる。重みの符号化に応じて線形変換の係数と補正項も必要であり、単純な正負の和だけで全量子化方式を表せるわけではない。

オフラインでは重みをビット面へ分解し、近接するg個のビットを一つの索引にまとめて、CPUで連続して読みやすい配置へ整える。オンラインでは活性値のg個の要素から、可能な2^g通りの符号付き和を事前計算する。g=4なら16通りで、例えば活性値(a1,a2,a3,a4)に対して、すべて正の和、いくつかを負にした和などを表に入れる。重みの4ビット索引に対応する部分和を引いて加算するだけで、そのグループの寄与を求められる。

重みビット幅bに応じてビット面をb回処理するので、表参照の主な処理量はbにほぼ比例する。これは重みを高精度へ展開して同じ幅の乗算を続ける方式とは異なる。一方、活性値が変わると表を再計算する必要があるため、表構築費用と表の再利用回数が性能を左右する。

### 表中心のデータ配置とレジスタ常駐

表参照は索引ごとに異なる場所を読むため、表を通常のメモリへ置くと不規則なアクセスが遅くなる。T-MACは表をCPUのレジスタに収め、ARMのTBLやx86のPSHUFなどのSIMD表参照命令で複数の索引をまとめて処理する。g=4の16要素表は128ビットの表参照命令と相性がよく、gを5以上へ増やすと表が32要素以上となって追加レジスタや複数命令が必要になる。

さらに、軸の並べ替えとタイル化によって、一度構築した活性値表を多くの重み行へ使い回す。重みの並びをSIMDのメモリ転送単位へ合わせる並べ替えや、重みの索引を取り出す際の無駄を減らす交互配置も行う。表そのものだけでなく、参照結果の中間ベクトルもレジスタを使うため、レジスタの過剰使用による退避が起きないよう、タイルの大きさを機種ごとに調整する。

### 表の容量削減と精度の扱い

表の要素数は2^gで増えるため、表を小さくする工夫が必要になる。正負を反転させた対称的なパターンをまとめる方法や、表の値を低精度へ量子化する方法を使い、表の占有量と参照費用を減らす。表の量子化は演算誤差を生むため、単に表を小さくしただけで常に同等の出力が得られるわけではない。

また、参照結果を8ビットのまま高速に加算する選択的な最適化がある。通常は桁あふれを避けるため広い整数型へ変換するが、低精度の平均化命令を利用して費用を下げる。論文はこの高速集約が最大1.29倍の追加高速化をもたらす一方、無視できない精度低下があり得ると明記する。高速集約は標準で無条件に適用する機構ではなく、品質との交換条件を伴う任意の選択肢である。

### 実装と推論基盤への統合

著者らはTVMを使ってC++のカーネルを生成し、実行時のTVM依存を取り除いてllama.cppのスレッド群から呼び出す構造にした。ARM NEONとIntel AVX2の命令を利用し、表参照と集約を並列化する。表参照命令は主に8ビットの索引・値に適しているため、16ビットの表値を使う場合は上位・下位の8ビットを別々に参照して再結合する方法も用いる。

重みビット幅が1、2、3、4と変わっても、ビット面の処理回数と係数を変える共通の構造を保つ。これはCPUの異なるSIMD命令やキャッシュ容量に完全に依存しないという意味ではなく、共通アルゴリズムの上に機種別の配置・命令選択を実装するという意味である。

## 主要結果

### カーネル単体とモデル全体

単一スレッドの行列・ベクトル積では、1/2/3/4ビットの条件で最大11.2倍、5.8倍、4.7倍、3.1倍の高速化を報告する。これらは異なるビット幅・行列形状のカーネル最大値であり、モデル全体の生成がすべて同倍率で速くなるわけではない。複数スレッドではメモリ帯域の制約が強まり、2ビットの行列・ベクトル積の高速化は対象4機種で約4.0倍、4.0倍、5.3倍、2.5倍となる。

行列・行列積の評価では、入力系列長256で複数スレッドを用いる。M2 UltraではAppleの行列演算補助機構が強いため、表参照方式の優位性が相対的に小さい場合がある。一方、Pi 5やOrin、Surfaceでは2ビット条件で最大4.0〜5.3倍の高速化が見られる。表参照がすべてのCPUと演算形状で最速とは限らないことを示す。

モデル全体では、Pi 5の単一スレッドで3種類の対象モデルについて2.8倍、6.7倍、5.8倍の改善を報告する。複数スレッドのM2 Ultraでは1.1倍、2.3倍、1.7倍と改善幅が縮む。モデル全体には表参照で高速化されない演算も含まれ、CPUの帯域やスレッド並列化も影響するためである。BitNet-b1.58-3BではM2 Ultraで1コア約30トークン/秒、8コア約71トークン/秒、Pi 5で約11トークン/秒に達する。

### 消費電力と総エネルギー

M2 Ultraの複数スレッドでLlama-2-7B-4bit、Llama-2-7B-2bit、BitNet-3Bを測定した図9では、平均消費電力がそれぞれ10.3%、10.3%、17.3%減り、総エネルギーは20.6%、61.2%、51.3%減る。消費電力とエネルギーは別指標であり、速度改善によって処理時間が短くなることも総エネルギー削減へ寄与する。

論文の概要や結論では最大70%程度のエネルギー削減を総括するが、図9の三モデルの個別測定値を示すときは上記の20.6%、61.2%、51.3%を用いるべきである。総括値を特定モデルの測定値へ置き換えることはしない。

### 構成要素除去と誤差

基本の表参照だけでは、メモリ配置が悪く従来llama.cppより最大17%遅くなる条件がある。表の量子化で競争力を高め、タイル化で最大1.45倍、連続メモリに合わせた並べ替えで追加1.39倍、重みの交互配置で追加1.42倍という改善を示す。これらは構成要素を段階的に有効化した特定条件の数値であり、独立な全機種共通倍率として掛け算してはならない。

任意の高速8ビット集約は最大1.29倍の追加改善がある一方、精度低下の可能性を持つ。論文はカーネル単位・モデル単位の誤差分析も行い、量子化や集約方式が品質に与える影響を確認する。表参照自体の計算上の等価性と、表値の量子化・高速集約による追加近似を区別することが重要である。

## 既存研究との差

llama.cppなどの一般的な重みのみ量子化カーネルは、詰め込んだ重みを命令が扱える整数精度へ展開し、積和演算を行う。T-MACは重みのビット面を表の索引にし、活性値の符号付き部分和を先に作って参照するため、重みの精度を下げたときにビット面処理の回数も減る。特に3ビットのようにバイト境界と合わない精度で、展開の不利を避けやすい。

GPUの専用行列演算命令やTensor Coreを前提とする方式とは異なり、汎用CPUのSIMD表参照命令を利用する。もっとも、表参照のランダムアクセスと表容量という別の費用があるため、レジスタ配置と表圧縮が性能の本体となる。単なる数学的な乗算削減だけでなく、CPUの命令・メモリ階層へ対応させた実装が寄与である。

## 限界・適用条件

第一に、表の作成には活性値ごとの準備費用がある。表を十分再利用できない行列形状では、この費用を償却しにくい。表のサイズはグループ長gに対して2^gで増えるため、レジスタ数や表参照命令の幅に合わない設定は逆効果となる。CPUの帯域、キャッシュ、SIMD命令により性能が大きく変わる。

第二に、カーネルの高速化がそのままモデル全体の速度へ移るわけではない。モデルには注意、正規化、サンプリングなど別の演算もあり、複数スレッドでは帯域制約もある。M2 Ultraの行列・行列積のように、既存の行列演算補助機構が強い条件ではT-MACの相対優位が縮む。

第三に、表値の量子化や高速8ビット集約は追加誤差を伴い得る。高速集約の最大倍率を、無条件の精度維持と同時に達成できると断定してはならない。低ビット重みモデル自体の精度は元の量子化方式にも依存する。

第四に、比較対象のllama.cppは2024年5月時点の版であり、現行版のカーネルや新しいCPU命令へ対する優位性をこの結果だけで保証することはできない。評価は主に端末側CPUであり、GPU主体の大規模バッチ提供、長文脈KV管理、複数ノードの分散推論を直接扱わない。
