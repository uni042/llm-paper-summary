# MatMamba：一つのMamba2重みから多数の推論規模を切り出す入れ子モデル

## 概要

MatMambaは、状態空間モデルMamba2の内部演算次元を入れ子構造にし、**一度学習した重み集合から、推論時の計算予算に応じて異なるサイズの部分モデルを取り出す**アーキテクチャである。通常は1B、3B、7Bのようにモデルサイズごとに独立学習し、それぞれ別の重みを配備する。MatMambaは最大サイズのモデルの先頭部分に小さなモデルのパラメータを含める構造を採り、複数の粒度を共同学習することで、モデルの再学習なしにサイズを選べるようにする。

この考え方はMatryoshka Representation LearningとMatFormerに近いが、TransformerのFFNだけでなくMamba2のゲート・投影・畳み込み・状態更新ヘッドなど、内部次元に依存する多数のパラメータを入れ子にする。学習時に明示的に最適化する粒度は4段階である。推論時はその4段階だけでなく、層ごとに異なる内部次元を選ぶMix’n’Matchによって中間の計算規模も構成できる。

原著は画像モデル35M/135M、言語モデル130M/370M/790M/1.4Bを学習した。言語モデルはFineWebで学習し、入れ子の各粒度が対応するMamba2ベースラインと競合するスケーリングを示す。画像検索では、135Mモデルの大きなエンコーダでデータベースを符号化し、同じモデルの小さな部分モデルでクエリを符号化しても表現空間の整合が保たれる。原著§4.1.2は計算量を55%減らしつつ、検索精度の低下を0.5%未満に抑えた例を報告する。

ここでの利点は**複数サイズを別々に再学習しないこと**であり、1.4Bモデルの推論そのものが同規模Mamba2より常に高速になるという主張ではない。部分モデルは小さな内部演算を使うことで必要な計算量を減らす。共同学習時には複数粒度のforwardを行う追加費用があるため、「小モデルが無料で得られる」は推論配備時の追加学習不要という意味に限定すべきである。

## 問題設定

複数の端末、GPU、レイテンシ制約へ対応するには、モデルサイズの選択肢が必要になる。大きなモデルを小型端末へそのまま載せるとメモリ・演算予算が足りず、小型モデルだけを配備すると利用可能なGPU資源を使い切れない。独立したサイズを多数学習する方法は学習コストと重み保管コストが増え、サイズ間の内部表現も一致しない。

独立学習した小型モデルと大型モデルは、同じタスクに使えても埋め込み空間が一致するとは限らない。たとえば画像検索でデータベースを大型エンコーダで埋め込み、クエリだけ小型エンコーダで埋め込むと、距離比較が破綻することがある。モデルを共有重みの入れ子にして共同学習できれば、大小のモデル間で意味的な整合を維持しやすくなる。これは単なるパラメータ数削減とは異なる利点である。

既存のMamba2は長い系列を効率的に処理できる一方、ブロックの内部次元やヘッド数を推論時に自在に変えるようには設計されていない。単純に重み行列の一部を切り落とすと、各サブモデルの性能が保証されず、Mamba2の内部テンソルの形状整合も壊れる。MatMambaは、最初から各部分モデルを含む構造を設計し、共同最適化することでこの問題を扱う。

## 手法

### 1. Mamba2ブロックの内部次元を入れ子化する

最大モデルの内部次元を `d_model` とし、MatMambaの実行粒度を `mat_dims` とする。内部の拡張率を `expand`、ヘッド幅を `headdim` とすると、選択粒度で使用する内部次元は `mat_d_inner = expand × mat_dims`、使用ヘッド数は `mat_n_heads = mat_d_inner / headdim` となる。後者が整数になるよう、次元とヘッド幅の整合を満たす必要がある。

原著付録の擬似コードでは、入力ゲート投影 `W_z`、入力変換 `W_x`、状態更新の時間刻み `W_dt`、畳み込み `W_conv_x`、出力投影 `W_out` を選択次元に応じてスライスする。状態に関わる `W_B`、`W_C`、対応する畳み込み `W_conv_BC` などは共通の部分を保持する。状態空間演算の `A` と `D`、時間刻み `dt` についても選択ヘッド数だけを使う。

具体的には、入力投影で `W_z[:mat_d_inner,:]` と `W_x[:mat_d_inner,:]` を使い、`W_B`、`W_C`、`W_dt[:mat_n_heads,:]` と連結する。深さ方向畳み込みは選択された内部チャネル分だけ処理し、状態更新カーネル `mamba_chunk_scan_combined` に選択ヘッドだけを渡す。最後に `W_out[:, :mat_d_inner]` で元のモデル次元へ射影する。出力テンソルの外部形状は `(batch, seq_len, d_model)` のままなので、後続層やヘッドは同じインターフェースで受け取れる。

この「外側の次元は維持し、内側の計算幅を縮める」点が、単純にモデル全体の埋め込み次元を削る方式と異なる。各層の外部入出力が同じ形状だからこそ、層ごとに異なる粒度を混ぜられる。実装では状態更新カーネルのヘッド数、畳み込みのgroups、投影のスライスがすべて一致していなければならない。

### 2. Matryoshka共同学習

入れ子粒度を `M1 ⊂ M2 ⊂ ... ⊂ Mg` とし、`Mi` の全パラメータが大きい `Mj` に含まれるようにする。原著の基本実験は `g=4` である。学習時には各粒度のforwardを行い、それぞれの損失から共有パラメータへ勾配を集めて更新する。原著は複数粒度のforwardと勾配蓄積を用い、最終的に共有重みを更新すると説明する。

小さい粒度の重みは大きな粒度にも含まれるため、先頭の次元には複数粒度から学習信号が届く。これにより重要な情報が小さい部分モデルにも入りやすくなる。最大モデルだけを学習して推論時に重みを切るpost-hoc pruningとは異なり、各部分モデルの精度を学習目的へ明示的に含める。

一方で学習時の費用は最大粒度1回のforwardだけでは済まない。4粒度のforward、勾配蓄積、学習時の状態・活性保持が必要となる。したがって複数モデルを個別に学習する場合と比べて総費用がどれだけ減るかは、学習構成と比較基準を揃えて測る必要がある。「100個のモデルを無償で学習する」という意味ではない。

### 3. 推論時の粒度選択

著者実装の`MatMamba2`は、通常のMamba2と同じ形状のテンソルを入出力する。例えば`d_model=512`のブロックで`mrl_level=2`を指定すると、内部では約半分の次元を使うが、出力は依然として`d_model=512`である。`mrl_level`を省略すれば通常の最大粒度として動作する。利用側のレイヤーインターフェースを変更せずに、内部の計算量を制御できる。

言語モデルのバックボーンでも同じ選択を適用できる。公式READMEは`MatMambaLMHeadModel`で`mrl_level=2`を渡し、同じ`(batch, seq_len, vocab_size)`のlogitsを返す例を掲載している。最大モデルの重みを保有したまま、推論時に使用する内部演算だけを減らすため、実行時間は短くなり得るが、**ロード済みの最大モデルの重みを自動的にすべて解放できるとは限らない**。GPUメモリ節約の度合いは重みの切り出し方法とロード方式によって変わる。

### 4. Mix’n’Match：層ごとの異なる内部幅

明示的に学習した粒度の間に必要な推論予算がある場合、各層の`mat_dims`を異なる値へ設定するMix’n’Matchを使う。たとえば一部の層は大きな内部幅、別の層は小さな内部幅にする。外部入出力が同じ`d_model`なので、このような異種幅の連結が可能である。著者実装では`mixnmatch=True`と`mixnmatch_dims`を層ごとに設定する。

層数が多いほど粒度組合せの数は急増し、明示学習した4つの一様粒度だけでは表せない中間サイズを作れる。原著の図3では、Mix’n’Matchの精度・計算量が明示学習粒度の間を滑らかに補間し、ときには単純な線形補間を超える傾向がある。ただし任意の層別組合せが常に最適という意味ではない。実際には、与えられた遅延やメモリ予算に対して層別粒度を探索する必要がある。

この方式は投機的デコードのdraft/targetとして同じ重みの異なる粒度を使う可能性にも関係するが、原著の主評価は弾力的モデル抽出であり、実際の投機的デコード受理率やE2E高速化を検証したものではない。表現空間を共有することと、確率分布が投機的生成に都合よく一致することは別の条件である。

### 5. 公式実装上の制約

公式READMEは、粒度を初めて実行するとJIT/Tritonの自動チューニングによって初回呼び出しが遅くなる可能性を明記している。したがって推論レイテンシを測る際には初回コンパイルとウォームアップ後の定常実行を分ける必要がある。動的に粒度を頻繁に変えるサービングでは、粒度ごとのカーネルキャッシュが十分に準備されているかが実用性能を左右する。

また、選択内部次元がヘッド幅の倍数でなければ状態更新カーネルを正しく呼べない。任意の整数パラメータ数を連続的に選べるわけではなく、形状制約に合う離散的な幅を組み合わせる。共有重みのスライスは、単に同一モデルの重みを量子化することとも異なる。MatMambaの部分モデルには明示的に学習した先頭チャネル群が使われる。

### 言語モデル：各粒度でのスケーリング

MatMamba-LMは130Mから1.4Bまでの4規模で、FineWebによる言語モデリングを評価する。原著§4.2では、明示的に学習した各粒度のモデルが、対応する小型Mamba2をゼロから学習したベースラインと同等かそれ以上の傾向を示すと説明する。最大モデルのパラメータを共有した小型部分モデルが、同規模の独立モデルに対して著しく劣るなら、弾力的推論の利点は小さい。ここでは各粒度を共同学習することでその問題を緩和している。

原著は言語モデルのスケーリング曲線を中心に提示しており、今回照合できた本文・公式READMEから全モデルのPPL絶対値を一意に抽出できなかったため、表に推測値を置かない。確認できた定量条件は130M/370M/790M/1.4Bのモデル規模と各4粒度である。言語側の実際のTTFT・TPOT・同時要求処理率を、画像側の高速化結果から推定してはならない。

言語モデルの主な評価ポイントは、同じ重みで小さい粒度へ切り替えたときに言語モデリング品質が滑らかに変化するか、明示的に学習していない中間粒度のMix’n’Matchでも大きく品質崩壊しないか、という二点である。これは量子化や後学習の剪定と異なり、モデルの初期学習段階から多粒度の品質を最適化していることに由来する。

### 画像モデル：高解像度の推論性能

原著§4.1.1と図4では、入力解像度を変えてMatMamba-VisionとViT-B/16を比較する。512px以下ではViTのほうが速い条件がある。理由として、短い系列ではTransformerのGPU並列性とFlashAttention等の最適化が有利になることを挙げている。1024px以上の高解像度では、系列長の増加に対してMamba系が処理率・遅延で有利になり、推論メモリの伸びもViT-B/16よりやや小さいと報告する。

これはMatMambaが常にTransformerより速いという結果ではない。**512px以下ではViTが速い**という明確な逆転条件がある。画像の高解像度での優位は長い系列への適性を示すが、LLMの自己回帰デコード、KVキャッシュ、同時サービングの速度を直接測ったものではない。GPU種類・バッチ・実装最適化が変われば境界となる解像度も変わり得る。

### 画像検索：同じ埋め込み空間を共有する効果

原著§4.1.2と図5は、ImageNet-1Kのデータベースを大型エンコーダで埋め込み、クエリだけ小さい部分モデルで処理する1-NN検索を評価する。独立学習した小型Mamba2をクエリエンコーダとして用いると、データベース側と埋め込み空間が整合せず検索精度が下がる。MatMambaの部分モデルは最大モデルと重みを共有しているため、同じ埋め込み空間で比較しやすい。

| 条件 | 原著の観察 | 解釈 |
|---|---|---|
| MatMamba-Vision 35M/135M | 大小の部分モデル間で検索表現の整合を維持 | 独立学習した異サイズモデルより跨粒度検索に適する |
| 135Mモデルの部分粒度 | 計算量約55%削減、検索精度低下0.5%未満 | 大型データベース埋め込みを再計算せず小型クエリ処理へ切替可能 |
| Mix’n’Match | 明示学習粒度の間を精度・計算量で滑らかに補間する傾向 | 中間GPU予算へ適応する余地がある |
| 512px以下の画像入力 | ViT-B/16が最速となる条件あり | 短系列ではMamba系の優位は自動的ではない |
| 1024px以上の画像入力 | Mamba系が遅延・処理率で有利な傾向 | 長い系列の効率改善が顕在化する |

55%は画像検索のクエリエンコーダの計算量削減であり、言語モデルの推論時間55%短縮を意味しない。精度低下0.5%未満も同じ画像検索条件での結果であり、言語モデルのゼロショット正答率が0.5%しか落ちないという意味ではない。

### 学習コストとモデル規模の感度

4粒度を共同学習するため、最大粒度1回だけの学習と比べてforwardの回数・勾配蓄積が増える。一方、最大モデルを一度学習しておけば、配備時に別サイズごとの独立学習や蒸留を繰り返さずに済む。実際の損益分岐は、必要なサイズの数、共同学習の追加費用、独立学習の費用、配備先での実行頻度によって変わる。

Mix’n’Matchでは各層の内部幅が違うため、全層同じ小型幅へ縮める場合と比較して精度・計算量のパレート曲線が改善する可能性がある。ただし原著の図示は一部の構成例であり、全ての組合せの品質保証ではない。モデルサイズと計算量を混同せず、実際のカーネル実行・重みロード・メモリ常駐の方式を含めた測定が必要である。

## 既存研究との差

MatFormerはTransformerのFFNに入れ子構造を導入し、同一重みから複数のモデルサイズを取り出す。MatMambaはその考え方をMamba2へ拡張するが、単にFFN幅を変えるだけではない。状態更新のヘッド数、入力・ゲート投影、畳み込み、出力投影など、SSM特有の演算を同時に縮小する。これによってMamba2の長系列効率を保ちながらモデルサイズの弾力性を得る。

一般的な剪定は学習後の重みを除去し、必要なら追加の微調整を行う。MatMambaは小さい部分モデルを学習目的へ最初から含めるため、後付け剪定とは品質の最適化経路が異なる。量子化は数値精度を下げるのに対し、MatMambaは演算する内部次元やヘッド数を減らす。両者は原理上組み合わせられるが、原著は量子化したMatMambaの実測を主張していない。

独立学習したモデル群と比較したときの重要な差は、重み共有だけでなく表現空間の共有である。画像検索の大型DBエンコーダと小型クエリエンコーダを混用できることは、単純に「小型モデルが高精度」という以上の性質を示している。LLMのdraft/target共有へ応用する場合にもこの性質は興味深いが、投機的生成の実測結果としては扱わない。

## 限界・実装状況

最大言語モデルは1.4Bであり、30B/70B級の推論サービングへ同じ効率・品質が成立するかは未検証である。共同学習に追加費用がかかり、最大重み集合をメモリへロードしたまま内部演算だけを減らす構成では、重みメモリの節約は演算削減率に比例しない。サイズ変更を頻繁に行う運用では、Triton JIT/autotuneによる初回レイテンシとカーネルキャッシュの管理が重要になる。

原著の主な速度評価は画像モデルの高解像度入力であり、自己回帰言語モデルのTTFT、TPOT、同時要求数、バッチ感度、GPUごとの推論速度を網羅するものではない。特に画像の1024pxでの優位を、LLMの1024トークン生成でも同様と解釈するのは誤りである。低解像度ではViTが速いという負の結果も残すべきである。

公式実装は`MatMamba2`、`MatMambaLMHeadModel`、`MatMamba2Vision`を提供し、`mrl_level`と`mixnmatch_dims`で推論幅を制御する。公式READMEにあるモデル・重みリンクは再現の入口になるが、今回の調査では論文評価時のcommit固定や、RTX 4070 SUPER 12GBでの実測は行っていない。既存ランタイムへ統合するには、状態更新カーネルが可変ヘッド数と可変内部次元を扱えること、粒度ごとの初回コンパイルが運用上許容できること、部分モデルの品質が対象用途で十分であることを確認する必要がある。
