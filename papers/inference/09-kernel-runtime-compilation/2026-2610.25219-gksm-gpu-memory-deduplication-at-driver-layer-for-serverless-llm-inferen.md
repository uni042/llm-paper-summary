# gKSM: GPU Memory Deduplication at Driver Layer for Serverless LLM Inference

> ドライバ層で重複した重みページを検出して物理ページを共有し、転送前の重複除去と書き込み時コピーで分離を保つことで、フレームワークを改変せずに同居インスタンスのメモリ重複を最大59.8パーセント削減する方式。

## 概要

サーバーレス型の推論サービスでは、事業者が1台のアクセラレータへ複数の利用者のインスタンスを同居させ、計算資源の時間的な空きを埋め合わせる運用が一般的である。ところが各インスタンスはモデルの重み、キーと値のキャッシュ、実行時状態を独立に保持する。公開された実トレースの分析では、単一インスタンスの平均メモリ利用率は約5割、計算利用率のピークでも約2割にとどまり、重みがメモリの大半を占めてキャッシュや活性値は全体の25パーセント未満だった。つまり計算は空いているのにメモリが先に満杯になり、同居できるインスタンス数が重みのコピーで決まってしまう。

重複の規模は大きい。同一基盤モデルから微調整した派生モデル同士では重みの15.2から81.6パーセントが共通であり、クラスタ規模のトレース再生では、重みを共有しない方式や通常の負荷分散で重複メモリが最大で約2000ギガバイト、重複率で約7割に達した。同一モデルを同じ計算機へ寄せる移行型の方式でも重複率は5割を超えた。スケジューリング層の工夫は、異なるフレームワーク同士の共有や派生モデル間の部分的な重複を扱えず、移行そのものが尾遅延と分離の弱体化を招く。

本論文の提案は、重複への対処をスケジューリング層からメモリ層へ移し、ドライバ層でページ単位に重複を検出して物理ページを共有する透過的な仕組みである。主要な結果は三つある。第一に、実機の4台構成で、同じモデル系統を同じ装置へ寄せる配置と組み合わせた場合にメモリ使用量を59.8パーセント削減した。第二に、メモリ制約下の単体構成で、同一モデルのインスタンスを4個同居させた条件の合計スループットが比較対象の2.05倍から2.15倍になり、比較対象がメモリ不足で起動できない5個同居でも処理を継続した。第三に、クラスタ規模のシミュレーションでは、2計算機ノードの時点で処理可能な割合が99.97パーセントに達し、移行型の方式の78.2パーセント、共有しない方式の26.9パーセントを大きく上回った。以下では、なぜデバイス側では単純な重複除去ができないのか、提案が三つの障害をどう分けて解いたのか、利得がどの条件で生まれどこで細るのかを順に説明する。

## 問題設定

プロセッサ側のメモリでは、カーネルがページを走査して内容の一致するページを1個の物理コピーへ統合し、書き込みが起きたら書き込み時コピー（書き込んだ側だけに私用コピーを作る仕組み）で分離を保つ重複除去が長く使われてきた。これをデバイス側へそのまま持ち込むと、三つの構造的な障害に当たる。

第一に、データと管理情報の居場所が分かれている。重複したページの実体はデバイス側メモリにあるのに、割り当ての記録や権限や共有状態といった管理情報はホスト側で扱う必要がある。ページをホストへ戻してハッシュを計算すると転送量が膨らみ、ホスト側の計算自体も並列度でデバイスに劣る。逆に管理の全てをデバイス側へ寄せることも、複雑な表構造の操作がデバイス側の実行環境に合わず現実的でない。

第二に、重みの読み込み経路である。インスタンスの開始時には重みをホストからデバイスへ転送するのが通常であり、先に転送してから重複を潰す流れでは、重い転送を二重に行い、潰す前の一時的な重複がメモリ不足の引き金になる。数ギガバイトから数十ギガバイトの重みを多数のインスタンスが同時に読み込む状況では、この無駄は無視できない。

第三に、共有後の書き込み分離である。プロセッサ側ではカーネルが書き込み時コピーを標準で備えるが、デバイス側のドライバは一部が非公開で、共有ページに対する同様の意味論を提供しない。仮想メモリを細かく操作する公式の仕組みは権限の変更や再配置の部品は提供するものの、書き込みを検出して私用コピーへ切り替える一連の処理までは面倒を見ない。ドライバ本体へ大きく手を入れれば作れるが、版の更新のたびに壊れる危険があり、安定性の面でも避けたい。提案はこの三点を、計算の分担、転送経路への割り込み、特権レベルの分割という別々の手で解く。

## 手法のあらまし

処理の流れは、開始時、実行中、書き込み時の三場面に分かれる。開始時には、ホストからデバイスへのメモリコピー経路に割り込み、ページごとにハッシュを計算して共有表を引く。既に同じ内容のページが共有されていれば、新しい物理確保を解放して仮想アドレスを既存の共有ページへ向け直し、データ自体は転送しない。一致がなければ通常どおり転送し、そのページを将来の重複検出のために共有表へ登録する。実行中は、背景の走査スレッドがキャッシュなどの動的ページを周期的に調べ、ハッシュが複数回の走査で変わらなかった安定ページだけを共有候補にする。共有されたページは読み取り専用に設定され、誰かが書き込むと障害が発生する。カーネル側の軽いフックが障害を記録して利用者空間へ知らせ、利用者空間の処理担当が私用コピーを作ってそのインスタンスの仮想アドレスだけを向け直す。クラスタ規模では、新しいインスタンスを置くときに、共有できる見込みの大きさから増分メモリ費用を見積もり、費用が最も小さい装置を選ぶ配置方針を併用する。重複の判定は常に、ハッシュの一致を候補の発見に使い、最終的には内容の完全一致を確認してから共有する二段構えであり、ハッシュの衝突で誤って別内容を共有することはない。

## 手法

### 1. 協調ハッシュ管理 — 計算はデバイス、表はホスト

重複検出の中心は、ページ内容のハッシュをどう安く計算するかである。提案では非暗号型の高速ハッシュをデバイス側のカーネルで一括計算し、ホスト側はページごとの仮想アドレス、権限、ハッシュ値を保持する管理表と、ハッシュ値で引ける全体の共有表を管理する。実測では、同じハッシュ計算の処理量がホスト側の毎秒9.92ギガバイトに対してデバイス側で毎秒167.70ギガバイトと16.9倍に達し、暗号型ハッシュをホストで計算する場合とは桁が違う。ハッシュが一致した候補については内容を厳密に比較し、完全に一致したときだけ仮想アドレスを共有ページへ向け直す。衝突したページは独立したまま残るため、速いハッシュを使っても正確さは損なわれない。追加で消費するのは管理表のメモリと一括計算の起動費用であり、ページをホストへ戻す転送は発生しない点が、この分担の効く理由である。

### 2. 転送前重複除去 — 重みは運ぶ前に潰す

重みについては背景走査を待たず、読み込みの経路そのものへ割り込む。重みは転送前はホスト側メモリに完全な形で存在するため、ハッシュ計算、候補の照会、内容の厳密比較の全てをホスト側で完結できる。一致が確認できれば、そのページの物理確保を即座に解放し、仮想アドレスを既存の共有物理ページへ接続する。データはバスを一度も通らない。一致がなければ通常どおり転送し、ページを共有表と固定したホスト側バッファへ登録して将来の照合に備える。共有済みの重みページには印を付け、背景走査の対象から外すことで二重の仕事も避けている。これにより、重複した重みについては転送帯域と一時的なメモリ占有の両方が消え、多数のインスタンスが同時に起動する場面でもメモリ不足の危険が下がる。失敗時の扱いも単純で、照合に失敗したページは通常の転送へ戻るだけであり、開始処理が止まることはない。

### 3. 特権をまたぐ書き込み分離 — 検出はカーネル、実務は利用者空間

共有ページは全て読み取り専用に設定される。あるインスタンスが書き込むと装置側でページ障害が起きる。提案では、装置側の仮想メモリ機構が持つ再試行可能な障害経路へ軽いフックだけを追加し、障害アドレス、障害の種類、インスタンスと装置の識別子を記録して待ち行列へ入れ、文字デバイス経由で利用者空間へ渡す。重い実務、つまり私用コピーの確保と複製、仮想アドレスの向け直し、権限の書き込み可への変更、所有権の移譲は、全て利用者空間の担当スレッドが公式の仮想メモリ操作で行う。共有ページの所有者が書き込んだ場合は、共有相手の中から同じ装置上の別インスタンスへ所有権を移してから書き込んだ側へ私用コピーを渡し、参照が全て外れたページは通常の書き込み可能なページへ戻す。カーネル側の変更を障害の報告だけに絞ったことで、ドライバ更新への耐性と安定性を保ちながら書き込み時コピーと等価な意味論を実現している。代償は往復の遅延であり、同時書き込みが増えると待ち行列と錠の競合で処理が頭打ちになる点は評価で確認されている。

### 4. 安定ページ走査と再利用を意識した配置

重み以外の動的ページ、とくにキャッシュや活性値は書き換えが多く、共有した直後に書き込まれると分離の往復費用が利益を上回る。そこで背景走査では、ページのハッシュが連続する複数回の走査で不変だった場合にだけ安定と判定して共有する。機会が見つからない走査が続くと間隔を指数的に延ばし、上限を設けることで、走査自体の費用と新しい共有機会への反応速度を釣り合わせる。共有の範囲は同一装置内に限る。他の装置や遠隔ノードのメモリを共有すると、デコードの各ステップで繰り返される読み取りが装置間リンクやネットワークの帯域に縛られ、地元の高速メモリとの差がそのまま遅延になるためである。この制約がある以上、重複の機会は同居のさせ方で決まる。配置方針は、各インスタンスの需要を共有可能な部分と私用の部分へ分け、既存インスタンスとの再利用見込みを差し引いた増分費用を装置ごとに見積もり、計算の余裕で絞った候補の中から増分費用が最小の装置を選ぶ。同点なら計算余裕の大きい装置を優先し、混雑の偏りを避ける。配置はあくまで機会を作る役割であり、実際の共有はページ単位の照合を通過したものだけに起きる。

| 安定ページ走査 | 動的ページのハッシュ履歴 | 連続して不変なページだけを共有候補にする | 無駄な分離の往復 | 安定判定までの時間差 |
| 配置方針 | 需要の内訳と既存配置 | 再利用見込みを差し引いた増分費用が最小の装置を選ぶ | 同居時の共有機会 | 計算混雑との釣り合い |

1個のインスタンスの生涯を通すと、開始時に重みが転送前照合で共有され、実行中は安定した動的ページが背景走査で段階的に共有され、書き込みが起きたページだけが分離処理で私用へ戻る。読み取りは常に対象の仮想アドレスから地元のメモリへ直接届くため、定常状態の推論経路へ追加の仕事は入らない。

## 評価

### まず見るところ

結論は、重複の除去がそのまま同居容量と処理能力へ変換されること、そして利益の大きさが配置と負荷条件に強く依存することである。メモリ削減は配置を工夫しない場合で2割から4割、同じモデル系統を寄せる配置で約6割に達する。スループットの利益はメモリに余裕がある間は小さく、比較対象がメモリ不足で退避や起動不能へ陥る条件で跳ね上がる。品質については、共有が内容の完全一致を条件とし書き込みを分離するため、生成品質の変化は原理的に生じない設計であり、論文も品質指標の比較ではなく遅延と処理量で効果を測っている。評価は実機測定が中心で、クラスタ規模だけがトレース再生のシミュレーションである点に注意が要る。

### 感度・スケーリング・ストレス条件

装置数を増やすと1台あたりの重複機会が分散し、共有のみの削減率は下がる一方、配置込みでは高い削減を維持できる。同時書き込みの競合では分離処理の処理量が毎秒約8300件で飽和し、それ以上は遅延だけが伸びる。負荷率を上げた条件では計算が律速になり、スループットの優位は縮小する。

### 立ち上がり・内部挙動

重みの共有は開始時の照合で即座に効き、動的ページの共有は安定判定を経て段階的に増える。分離処理の発生は190件規模と少なく、定常状態では読み取り専用ページへの書き込み自体が稀であることが、往復方式でも実用になる理由である。

## 既存研究との差

従来のサーバーレス推論の研究は、重みの局所性を使う配置、利用頻度に応じた退避、同一モデルの移行とバッチ統合など、スケジューリング層で重複の害を和らげる方向だった。これらは重複した物理コピーの存在自体は消せず、フレームワークが違えば統合できず、派生モデル間の部分的な重複も拾えない。本論文は対処する層をドライバへ下げ、フレームワークの違いを越えてページ単位で重複を消す点が根本的に異なる。プロセッサ側の重複除去との差も明確で、データと管理の分離、転送前照合の必要性、書き込み時コピーの不在という、デバイス側固有の三障害へそれぞれ専用の仕組みを用意した点が新規性の中身である。装置側メモリ管理の従来研究が断片化の解消やキャッシュ管理の最適化を扱ってきたのに対し、独立したインスタンス間での物理ページ共有そのものを実現した点も一線を画す。

## 限界・実装状況

- 共有範囲は同一装置内に限られ、装置をまたぐ重複は配置で寄せる以外の方法がない。クラスタ全体での最適化は配置方針の範囲にとどまる。
- 共有ページの存在自体が情報漏えいの経路になり得る点は論文も認めており、対策は信頼できる範囲内でのみ重複除去を有効にする運用に委ねられている。公開重みについては漏れる情報は限定的とされるが、キャッシュ由来の漏えいは残る論点である。
- 書き込み分離は利用者空間への往復を含むため、書き込みの多い動的ページでは利益より費用が勝つ可能性がある。安定判定で避ける設計だが、判定の閾値や間隔の最適値までは詰められていない。
- 実装は約4000行の試作であり、対象は特定ベンダーの実行基盤とドライバ版に依存する。他の実行基盤や将来のドライバ版への移植性は未評価である。
- 評価の文脈長と同時要求数は控えめで、長文脈化と大規模同居が進んだ条件での再検証が必要である。消費電力の評価も未実施である。
- 論文中に公式コード公開の案内は確認できず、再現は論文の記述に頼ることになる。

## 一般的な実装上の含意

重複への対処は、配置や移行の知恵を尽くす前に、物理層で重複そのものが消せないかを問う価値がある。消せる場合、利益は崖型に現れる。つまり平時には小さく見えても、退避や起動不能という不連続な劣化を遠ざける効果が本命であり、平均値だけでなく崖の位置で評価すべきである。また、重い処理を特権側へ入れず、検出だけを特権側、実務を利用者空間へ分ける分割は、閉じたドライバや基盤の上で新しい意味論を足す際の再利用可能な型である。共有の機会は同居のさせ方で決まるため、メモリ層の機構と配置方針は別々にではなく一組で設計する必要がある。
