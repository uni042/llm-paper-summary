# Triton：タイルを中心にGPUカーネルを記述・最適化する言語とコンパイラ

## 概要

深層学習の演算を高速なGPUカーネルにするには、数式を記述するだけでは足りない。入力配列のどの部分をまとめて読み出し、何回再利用し、どのスレッドに配り、いつ共有メモリへ移すかによって性能が大きく変わる。既存のcuBLASやcuDNNが対象とする標準演算なら高性能な実装を利用できるが、新しい行列演算や不規則な参照を伴う演算では、そのまま使えない。個別にCUDAを手書きすると専門知識と開発時間が必要になり、形状やGPU世代の変化にも対応しにくい。

2019年のTriton論文は、この溝を埋める抽象として、**静的な形状を持つ多次元部分配列「タイル」**をプログラミング言語と中間表現の両方で第一級に扱う。プログラマは一つのプログラム実行単位が処理するタイルを記述し、内部のスレッド配置、階層的なタイル分割、連続したメモリ読出し、共有メモリ利用、同期などをコンパイラに委ねる。構成要素はC風のTriton-C、LLVMを拡張したTriton-IR、実行時コンパイラTriton-JIT、パラメータ自動調整器である。

論文はGeForce GTX 1070で行列積と畳み込みを測定し、cuBLAS 10.0と概ね同等の行列積性能を得た。いくつかの行列積ではデバイスのピーク性能の90%以上を達成し、当時の他の領域特化言語による実装より2〜3倍高速な条件も示す。ただし浅いTransformer形状ではcuBLASが優れ、全形状でベンダーライブラリを上回るわけではない。**この結果は2019年の実装とGTX 1070に対する評価**であり、後年のTensor Coreや現行Tritonの性能を直接測ったものではない。

## 問題設定：なぜタイルが必要なのか

行列積 `C = A × B^T` では、出力の各要素は内積だが、各要素を独立に計算すると入力を何度もグローバルメモリから読み直す。出力の矩形領域を一括処理し、AとBの小行列を一度読み込んで複数の積和へ使えば、メモリ転送当たりの演算量を増やせる。さらにGPUのメモリ要求は一定のまとまりで処理されるため、隣接するスレッドが近接したアドレスを読むよう配置しないと、必要以上の転送が生じる。性能の中心は数式そのものより、**再利用単位と実行配置をどう決めるか**にある。

CUDAはスレッドと共有メモリを直接制御できる一方、スレッド配置や同期を明示する負担が大きい。既存の高水準方式にはテンソル演算を既定の実装へ対応付けるもの、多面体モデルでループを変形するもの、スケジュールを人が与えるものがある。しかし2019年時点では、特殊な添字計算や非アフィンなメモリアクセス、GPUのメモリ階層を組み合わせた演算に対応しきれない場合があった。Tritonは、完全な自動テンソル計算と手書きスレッド制御の中間にタイル単位の明示性を置く。

この選択には代償もある。高水準の行列積演算子を一行書くだけの仕組みと比べ、Triton-Cの利用者はどの矩形領域を計算し、どのループで積和するかを記述する必要がある。タイル内の低水準実装は自動化するが、演算アルゴリズムの選択そのものを完全に自動化するわけではない。

## 手法

### 1．Triton-C：形状付きタイルの計算を記述する

論文のTriton-CはCに近い構文へ、多次元タイル型、調整可能な定数、軸の追加と配列のブロードキャスト、述語付き実行、タイル内積などを加える。たとえば `float[TM,TN]` の出力蓄積タイルと、`float[TM,TK]`・`float[TN,TK]` の入力タイルを使い、`dot(A,trans(B))` を繰り返して積和する。`TM`、`TN`、`TK` は実行前に確定する調整対象の形状であり、処理するデータの値に応じて無制限に変わる動的配列ではない。

境界では、行数や列数がタイル幅の倍数でないことがある。Triton-Cはタイルの論理条件を用いた述語付き読出し・書込みを表現し、範囲外を無効化できる。ブロードキャストでは小さい形状を論理的に拡張して演算するため、配列要素を手で複製する必要がない。これらの情報は後段へ引き継がれ、タイルごとの有効要素やメモリ参照の構造をコンパイラが知る手掛かりになる。

### 2．実行モデル：プログラム単位はスレッドではなくタイル

CUDAではスレッドブロック内の個々のスレッドを意識して演算を書くが、初期Tritonのプログラムは見かけ上、単一の逐次プログラムとして記述される。各プログラムインスタンスはグリッド内の担当範囲を持ち、その範囲に対応するタイルを処理する。タイルの各要素を実際のGPUスレッドへ割り当てるのはコンパイラの役割である。

このため、ユーザーはスレッド間通信や共有メモリ上のバリアを直接プログラムへ散りばめなくてよい。行列積の例では、出力タイルを担当するプログラムが入力タイルを読み、積和を蓄積し、最後に出力タイルを一括で書き戻す。プログラムはデータ依存を示し、低水準の同期や並列実行の選択は後段が担う。

### 3．Triton-IR：タイル形状を保持するLLVM拡張

Triton-Cから作る中間表現はLLVMを土台としつつ、スカラーへ早期分解しない。`i32<8,8>` のようなタイル型、形状変更、ブロードキャスト、タイル単位の条件付き実行を持つ。通常の基本ブロック、静的単一代入形式、制御フローグラフを維持しながら、タイルのデータフローを解析できるようにする。調整可能な形状は実行時コンパイル前に具体値へ確定される。

タイルを保持することが重要なのは、各要素の依存関係だけでなく、**タイル全体としてどのメモリ領域をまとめて参照するか**を最適化器が把握できるからである。たとえば配列の形状変更とブロードキャストは、どの値が何度参照されるかを表現する。コンパイラはその情報を使って、不要なメモリ読出しを減らし、連続アクセスを選び、共有メモリへ一時配置する判断を行える。

### 4．機械非依存の最適化と機械依存の最適化

前段の最適化はGPUの特定世代に依存しないタイル計算の単純化を担当する。後段はGPUの実行階層とメモリ階層を考慮し、タイルをより小さい単位へ分け、スレッドの配置と記憶場所を決める。これらを分けることで、同じ計算を異なる入力形状や実行環境へ再コンパイルする構造を作る。

論文が詳しく扱う階層的タイル化では、プログラム単位のタイルをマイクロタイルへ、さらにナノタイルへ分割する。大きいタイルは再利用効率を高めるが、必要な共有メモリやレジスタが増え、並列に走れる処理単位を減らすことがある。小さすぎるタイルは並列性を増やしても同じ入力を繰り返し読みやすい。タイルの各階層の形状は、演算密度と並列性の両方を決める設計変数となる。

### 5．メモリ合体、共有メモリ割当、同期の自動化

メモリ合体の最適化は、同時に動くスレッドが近いアドレスを読むよう、マイクロタイル内の要素配置を決める。離れたアドレスを散発的に読むと、DRAMから使わないデータまで転送することになる。タイル型からアクセスパターンを把握して、可能な場合は連続した転送へ変換する。

内積などで再利用する入力は共有メモリへ置く方が有利な場合がある。コンパイラは値が生存する区間を調べ、同時に生きるタイルが共有メモリ容量を超えないよう配置を決める。論文は変数の生存区間と記憶領域割当を結び付ける。共有メモリの読書きは非同期に進むため、読取りが書込みより先行する危険や、書込みが前の読取りを壊す危険をデータフロー解析で検出し、必要なバリアを自動挿入する。これは性能だけでなく計算結果の正しさを保つための処理である。

### 6．Triton-JITと自動調整

実行時コンパイラは具体化したタイル中間表現からGPU向けのコードを生成する。自動調整器はタイル化のメタパラメータを抽出し、複数の候補をベンチマークして良い構成を選ぶ。論文の試作では、タイル幅32〜128、マイクロタイル幅8〜32、ナノタイル幅1〜4の2の冪乗候補を探索する。対象は主として階層タイル化のパラメータであり、後年のTritonが備える広範な最適化や自動調整をすべて含むわけではない。

入力形状ごとに良い構成が変わるため、単一の固定タイル幅を全ての行列へ使うより柔軟である。ただし候補のコンパイルと実測が必要で、調整時間は無償ではない。論文自身も、より効率的な探索方式を今後の改善余地としている。

### 7．具体例：行列積と特殊な畳み込み

行列積では出力の矩形タイルを割り当て、K方向の入力タイルを順次読み込んで積和する。各タイル内の蓄積を保持することで、入力の再利用を増やす。出力範囲を越える端のタイルは述語付き書込みで安全に処理する。入力形状によって最適なタイル階層が異なるため、コンパイラがメモリ合体や並列性を調整する。

通常畳み込みは、画像から切り出した受容野を論理的な行列積として扱う暗黙的行列積方式を再実装する。ずらし畳み込みでは、入力チャネルごとの空間シフトをポインタの増分表で表現し、シフトしたデータを別配列へ物理的に作り直すのではなく、読み出す位置を変更して積和へ流す。これにより、別のシフトカーネルと行列積を連続起動する実装の余計な転送を避けられる。

## 評価

### 実験条件と測定対象

| 項目 | 論文の設定 | 解釈上の注意 |
|---|---|---|
| GPU | NVIDIA GeForce GTX 1070 | 現代のTensor Core搭載GPUとは世代が異なる |
| ベンダー実装 | cuBLAS 10.0、cuDNN 7.0 | 2019年時点の比較 |
| 他の言語・コンパイラ | AutoTVM、Tensor Comprehensions、PlaidML | 適用可能なものは形状ごとに調整 |
| 行列積 | 正方形行列、DeepSpeech2由来、Transformer由来 | 形状で演算密度・並列性が変わる |
| 畳み込み | ResNet由来5条件、DeepSpeech2由来2条件 | cuDNNの暗黙的行列積方式と比較 |
| ずらし畳み込み | ResNet由来の5条件 | 別シフト＋cuBLASと融合版を比較 |
| 指標 | 浮動小数点演算処理率、ピーク比、実装間相対性能 | LLM全体の応答時間ではない |

この論文の実験対象はニューラルネットワークの**個別演算カーネル**である。後年のLLM推論基盤でTritonが使われることは重要だが、2019年の数値をLLM全体の処理率や生成遅延の改善値として記録してはいけない。

### 行列積：ベンダー実装との近さと負の結果

| 比較条件 | 原著の結果 | 読み方 |
|---|---|---|
| 複数の行列積形状 | TritonとcuBLASが概ね同等 | 高水準タイル記述からベンダー級の演算効率を得られる |
| 一部の行列積 | GTX 1070ピークの90%以上 | 演算密度が高い形状での実測であり、全形状ではない |
| 他の領域特化言語 | 多くの条件でTritonが約2〜3倍高速 | 対象はAutoTVM等の当時の実装と調整条件 |
| 32の倍数の形状のTVM | Tritonとの差は2倍未満 | 他言語が常に大差で遅いわけではない |
| 浅いTransformerの行列積 | cuBLASがTritonより速い | cuBLASの3次元分割で追加並列性を確保できる |

図8では正方形行列に加え、DeepSpeech2とTransformerの形状を用いて演算処理率を比較する。大きな行列では入力再利用が効く一方、出力の二次元形状が小さく内積方向だけが深い場合は、通常のタイル分割では同時実行数が不足する。cuBLASは深い内積をさらに分割する3次元の方法で並列性を増やし、浅いTransformer形状で優位となる。この負の結果は、タイル中心の抽象を採用すれば全ての形状で最適になるという誤解を防ぐ。

図1の屋根線モデルによる比較も、演算強度を変えるために行列の片方の寸法を変えた実験である。演算強度が小さいときはメモリ帯域、十分大きいときは演算器が律速となる。図に示された曲線は、タイル化がデータ再利用と演算器利用率を改善できることを示すが、全入力でピーク性能へ張り付くという主張ではない。

### 畳み込み：暗黙的行列積とずらし処理の融合

図10ではResNetとDeepSpeech2の畳み込み形状を用い、Tritonの暗黙的行列積実装とcuDNN 7.0の同方式を比較する。ResNet由来のいくつかの条件ではTritonがcuDNNの暗黙的行列積より高速だが、cuDNNには3×3畳み込み向けの別アルゴリズムもあるため、**cuDNNが提供する最良の畳み込み全体よりTritonが常に速い**とは結論できない。DeepSpeech2由来の条件では両者が概ね同等だった。

図11のずらし畳み込みでは、チャネルごとのシフト処理を別カーネルで行ってからcuBLASを呼ぶ方式と、Tritonでシフトアドレス計算を行列積へ組み込む方式を比較する。融合方式はシフト処理の費用をほぼ隠し、シフトなしの1×1畳み込みに近い処理率を得た。重要なのは、単にcuBLASの再実装をしたことではなく、**既製ライブラリへそのまま渡しにくい新しい演算を、一つのGPUカーネルにまとめられる**という点である。

### どこまで検証されたか

論文はカーネル単位の浮動小数点演算処理率を測定し、複数の入力形状を比較した。一方、長い系列を処理する大規模言語モデルの端点処理率、モデル全体の学習時間、GPU間通信、現代GPUのTensor Core利用率、複雑な非同期コピーとパイプライン化などは評価していない。Tritonの汎用性を論じる場合は、**当時の行列積と畳み込みに対する実証**と、後年のシステムへの応用可能性を分けて扱う必要がある。

## 既存方式との差

Tensor ComprehensionsやDieselのような多面体的な方法はアフィンな配列添字のループ変換に強いが、特殊な添字計算の表現に制約がある。HalideやTVMは演算とスケジュールを分離するが、2019年の比較では手動・自動のスケジュール指定とGPUコード生成の性能が課題となった。Tritonはタイルを言語と中間表現に残し、タイル内の配置と同期をコンパイラが導くため、GPUに必要な構造を保ちつつ低水準の記述量を減らす。

一方、CUDAで専門家が直接書くマイクロカーネルは細部まで制御できるが、移植と調整に手間がかかる。Tritonは演算のタイル分割をプログラマが考え、実行配置をコンパイラへ渡すという中間点を採る。高水準の一行演算より多くの記述を要する代わりに、ベンダーライブラリが扱わない融合や特殊なメモリアクセスを実装しやすくする。

## 限界・実装世代の区別

2019年の実装はC風のTriton-CとLLVM拡張Triton-IRを前提とする。現行TritonはPythonを用いた記述や後年の中間表現・GPU最適化を備えているが、**現行の仕組みを2019年論文がすでに実装・評価したと扱わない**。特に論文の今後の課題にはTensor Coreへの対応や量子化カーネル、高水準言語との統合が含まれていた。今日それらが利用可能であることと、当時の評価結果は別の時点の事実である。

単一のGTX 1070での測定から、H100などの現代GPU、異種GPU、複数ノード、PCIe/NVLinkを跨ぐ処理、混合精度のLLM推論へ同じ倍率を外挿できない。ベンダーライブラリは形状に特化した複数のアルゴリズムを使うため、Tritonが特定の暗黙的行列積実装に勝つことを、全ての畳み込み条件での勝利と見なせない。タイル化に適さない制御構造やメモリアクセスでは、記述の自由度や性能に別の制約が現れ得る。

自動調整器は候補を実際にコンパイル・実行して比較するので、候補数と形状数が増えれば準備費用が増える。論文時点の探索は主として階層タイルサイズの全探索であり、広い最適化空間を高速に探索する一般解ではない。したがって「自動で速いコードを作れる」という主張は、**記述した演算と探索した形状・パラメータの範囲で**解釈するのが正確である。

## 監査上の注意点

旧原稿の中心説明は概ね一次論文に沿っていたため、今回の再監査では、タイル型と実行単位の関係、共有メモリ割当とRAW/WAR依存による同期、調整器の具体的探索範囲、浅いTransformer形状でcuBLASが優位になる負の結果、ResNet畳み込みでのcuDNN比較対象の限定を明確化した。現行Tritonの実装や性能を2019年の成果へ遡及して付け加えていない。
