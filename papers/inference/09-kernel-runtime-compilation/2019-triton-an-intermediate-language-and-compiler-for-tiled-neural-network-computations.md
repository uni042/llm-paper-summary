# Triton: an intermediate language and compiler for tiled neural network computations

> CUDAのスレッド単位ではなく、静的形状の多次元部分配列「タイル（tile）」をプログラムの基本単位にする。Triton-C→Triton-IR→Triton-JITのコンパイル経路で、メモリ合体アクセス、共有メモリ利用、タイル階層化などをコンパイラへ移し、GTX 1070上の行列積ではcuBLASと概ね同等、一部でデバイスピークの90%以上を達成する。

## 概要

深層学習で新しい演算を提案しても、cuBLASやcuDNNに既製カーネルがなければ、高性能なGPU実装を得るにはCUDAのスレッド配置、共有メモリ、レジスタ、メモリアクセスを手作業で最適化する必要がある。従来の高水準コンパイラは記述性を上げる一方、非アフィンなアクセスやGPU固有のメモリ階層を十分扱えず、手書きベンダーライブラリより2〜3倍遅い場合があった。

2019年のTritonは、スカラー式やループではなく**タイル**を第一級の中間表現に置く。プログラマは「このプログラムインスタンスが行列のこの矩形領域を処理する」と記述し、タイル内要素をどのCUDAスレッドへ割り当てるか、どの値を共有メモリへ置くか、タイルサイズをいくつにするかはコンパイラと自動調整器へ委ねる。

構成は、C風のTriton-C、LLVMを拡張したTriton-IR、機械非依存・機械依存のタイル最適化を行うTriton-JIT、自動調整器（auto-tuner）からなる。タイル型をIRに残すことで、スカラーへ早く分解してしまうコンパイラよりも、データ再利用と並列性を同時に見ながらGPUコードを生成できる。

NVIDIA GeForce GTX 1070で行列積、通常畳み込み、shift convolutionを評価する。行列積ではcuBLAS 10.0と概ね同等で、いくつかの形状ではデバイスピーク性能の90%以上に達し、AutoTVM、Tensor Comprehensions、PlaidML等より最大約3倍高速な条件を示す。畳み込みでもcuDNNのIMPLICIT_GEMMを再実装して同等級の性能を得る。

## 問題設定

GPUカーネルには、アルゴリズム記述と実行スケジュールの間に大きなギャップがある。行列積であれば数式は単純でも、高性能化にはグローバルメモリを連続アクセスさせ、共有メモリへ適切にステージし、レジスタ再利用を増やし、十分なワープ数を維持する必要がある。

CUDAではこれらを直接指定できるが、ハードウェア世代や入力形状が変わると最適なタイル・スレッド構成も変わる。逆にTensor ComprehensionsやTVMのような高水準DSLではアルゴリズムは簡潔に書けても、2019年当時は非アフィンアクセスを含むshift convolutionなどを十分表現できず、生成コードのGPU利用率もベンダーライブラリへ届かないケースがあった。

Tritonの設計判断は、抽象度を「テンソル演算全体」でも「個別スレッド」でもなく、その中間の**タイル**に置くことである。タイルは共有メモリやレジスタへ載せる再利用単位と対応しやすく、コンパイラがGPUのメモリ階層と並列性を推論するのに十分な構造を残す。

## 手法

### 1. Triton-Cで計算をパラメトリックなタイルとして記述する

Triton-CはC/CUDAに似た構文を持つが、変数がスカラーだけでなく `float[TM,TK]` のような静的形状タイルを持つ。行列積なら、出力の (TM	imes TN) タイルを一つのプログラムインスタンスが担当し、入力A/Bのタイルを読み、`dot`で積和し、出力タイルを書き戻す。

タイルサイズ (TM,TN,TK) はチューニング可能なメタパラメータであり、アルゴリズム本体から分離される。境界条件も要素ごとの分岐ではなくタイル述語として表現できるため、コンパイラがマスク付きロード/ストアへ落としやすい。

### 2. Triton-IRがタイル形状を失わずに解析・変換する

Triton-CはLLVM系のTriton-IRへ変換される。通常のLLVM IRへ即座にスカラー化するのではなく、IR自体にタイル型、broadcast、reshape、タイル単位の制御フローを持たせる。

この表現により、どの軸が連続しているか、どのタイル間で値を再利用できるか、どの次元を並列化できるかを後段の最適化パスが認識できる。プログラマはCUDAのthreadIdxやshared memory配置を直接書かず、コンパイラがタイルの意味から低水準配置を導く。

### 3. 機械非依存パスでタイル演算を単純化する

コンパイラ前半では対象GPUに依存しない形で、タイル演算の畳み込み、冗長計算除去、ループ/データフロー整理を行う。高水準のタイル構造を維持したまま式を整理するため、後段がメモリ再利用を見失いにくい。

ここで重要なのは、GPU特有の最適化をソースへ埋め込まず、意味保存変換として分離している点である。同じTritonプログラムを異なる形状・GPUへ再コンパイルできる余地を作る。

### 4. 機械依存パスでGPUの階層へタイルを割り当てる

後半はタイルを階層的に分解し、プログラムインスタンス、ワープ/スレッド、レジスタなどへ配置する。メモリ合体（coalescing）、共有メモリ上の再利用、同期、レジスタ圧力を考慮し、LLVM/PTXへ落とせる形へ変換する。

論文の主要な最適化は階層タイル化（Hierarchical Tiling）で、粗いタイル、マイクロタイル、ナノタイルのサイズを変えながら、並列性とデータ再利用を調整する。この粒度選択がGPU性能に直結する。

### 5. 自動調整器がタイルサイズを実測で探索する

論文実装の自動調整器は、階層タイル化に付随するメタパラメータをプログラムから抽出し、候補を実際にベンチマークして選ぶ。代表探索範囲はタイル32〜128、マイクロタイル8〜32、ナノタイル1〜4の2冪候補である。

つまりプログラマは「高速なCUDAコードの完成形」ではなく「探索可能なタイルプログラム」を書く。入力形状ごとに有利な構成を自動選択できるため、手書きテンプレートを演算ごとに用意する方式より移植性を狙える。

## 評価

### 評価条件

|項目|条件|
|---|---|
|GPU|NVIDIA GeForce GTX 1070|
|ベンダー比較|cuBLAS 10.0、cuDNN 7.0|
|DSL比較|AutoTVM、Tensor Comprehensions、PlaidML|
|行列積|正方形、DeepSpeech2由来、Transformer由来の複数形状|
|畳み込み|ResNet/DeepSpeech2由来の複数形状|
|追加例|shift convolutionの融合実装|
|調整|階層タイルのメタパラメータを形状ごとに探索|
|主要指標|TFLOP/s、ベンダー実装・他DSLとの相対性能|

### 代表結果

|条件|比較|Triton|読み取れること|
|---|---|---:|---|
|複数行列積|cuBLAS 10.0|概ね同等|タイル抽象でも手調整BLAS級の性能を狙える|
|一部行列積|GTX 1070ピーク|90%以上|コンパイラ生成でも演算器を高く利用できる|
|行列積|他DSL|最大約3×高速|当時のスカラー/ループ中心DSLに対するタイルIRの利点|
|通常畳み込み|cuDNN IMPLICIT_GEMM|多くの形状で同等級|行列積以外にもタイル最適化を再利用できる|
|shift convolution|素朴なshift＋別GEMM|融合実装が大幅に高速|ベンダーライブラリに直接ない新演算を融合できる|

cuBLASが常に負けるわけではない。浅いTransformer形状など、cuBLASが3次元アルゴリズムで深いreductionを分割して並列性を増やせる条件ではcuBLASがTritonより速い。論文自身がこの差を示しており、Tritonの主張は「全形状でベンダーを超える」ことではなく、汎用プログラマブルな抽象から同等級へ近づけることである。

## 既存研究との差

TVM/Halide系はアルゴリズムとスケジュールを分離し、ループ変換を探索する。TritonはよりGPUの実行モデルに近いタイルを言語/IRの基本単位にし、共有メモリ配置やスレッドへの要素割当をコンパイラが推論する。

CUDAのmicro-kernelは最も細かく制御できる一方、再利用性と可搬性が低い。Tritonは「どの出力タイルを計算するか」はプログラマに明示させつつ、「そのタイルをどのスレッド・メモリ階層で処理するか」をコンパイラ側へ移す中間点を取る。

現在のTritonはPython埋め込みDSLやMLIR系実装へ発展しており、2019年論文のTriton-C/LLVMベースIRと現行実装は同一ではない。ただし、**タイル中心のプログラミングモデルでCUDA級カーネルを高生産性に書く**という設計原理は現在のTritonへつながっている。

## 限界・実装状況

2019年評価はGTX 1070一世代・単一GPUであり、Tensor Coreを本格利用する現代GPUや、FlashAttentionのような複雑な非同期パイプラインを直接評価した論文ではない。ここでの性能値をA100/H100世代へ外挿してはいけない。

自動調整も論文時点では主に階層タイルサイズの全探索であり、探索空間が大きい演算ではコンパイル・ベンチマークコストが増える。また、タイル化しやすい演算ほど恩恵が大きく、グローバル同期や不規則な制御を多用するアルゴリズムまで自動的に最適化できるわけではない。

公開実装はその後大きく発展し、現行のTritonはPyTorch 2系のコンパイラ生成カーネルなどにも使われる。ただしこの解説の評価結果は2019年論文の実装・GTX 1070条件に基づく。
