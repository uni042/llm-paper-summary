# WavePP：接頭辞再利用を伴うパイプライン入力処理の要求受付を並行化する

## 概要

大規模言語モデルの入力処理（prefill）を複数GPUのパイプライン並列（pipeline parallelism、PP）で実行すると、ある段が一つの要求を計算する間に別の段は別の要求を処理できる。しかし各段が自分の層のキャッシュを独立に管理すると、ある段で見つかった接頭辞が別の段でも再利用可能とは限らない。再利用できる範囲の合意、キャッシュを削除されないように保護する処理、未計算部分のメモリ確保を同期的に行うと、GPUに次の入力を供給する頻度が下がり、段の間に空き時間が発生する。

WavePPは、要求受付（admission）をモデル実行と別スレッドで進め、前の要求のGPU計算と並行して次の要求の準備を終える実行基盤である。接頭辞の候補を分割された索引から高速に探し、各段・各キャッシュ種別で共通に使える位置へ揃える。合意した既存ブロックには参照保護（lease）を設定し、まだ計算していない末尾のためには容量の事前予約（capacity escrow）を行う。準備が整った要求は処理波（wave）に分割し、パイプラインを埋めるように波の大きさを動的に選ぶ。

同一のTensorRT-LLM 1.3.0rc26のカーネルと4段パイプラインでGLM 5.2およびMiniMax M2.7を比較すると、40条件中37条件で入力処理量が改善した。接頭辞が長く未計算部分が4,096トークン、同時128要求という高負荷条件では、GLMの入力処理量が416,294から1,212,572トークン/秒（2.91倍）、MiniMaxが551,143から1,113,196トークン/秒（2.02倍）へ増えた。ただしこの処理量は**キャッシュから再利用した入力トークンも数える**ため、GPUが新たに計算したトークン数の倍率ではない。

## 問題設定と前提

パイプライン並列では、モデルの層を$P$個の連続した段へ分割する。段0がある入力片を計算し、その中間活性化を段1へ送る間、段0は次の入力片を計算できる。入力片を十分に供給できなければ、遅い段が全体の処理量を決めるだけでなく、他の段も空転する。接頭辞キャッシュが効くと、各要求の未計算部分が短くなり、1要求から生じる処理片が減るため、要求受付が追いつかない問題はむしろ強くなる。

各段は自分が担当する層の鍵・値（KV）キャッシュを保持する。モデルに再帰状態を持つ線形注意層が混在する場合、状態のスナップショットは一部の位置にしか保存されない。通常の注意層ではブロック単位で接頭辞を復元できても、再帰層ではその位置に対応する状態が存在しない場合がある。Kimi K3のような混合モデルでは、多頭潜在注意（MLA）のキャッシュとKimi Delta Attention（KDA）の再帰状態を両方考慮しなければならない。

接頭辞の再利用可能な終端位置を段$r$、キャッシュ種別$c$ごとに$p_{r,c}$とすると、候補となる共通位置は$\min_{r,c}p_{r,c}$である。しかしこの最小値だけでは安全とは言えない。再帰状態の保存位置が離散的なので、最小値の位置に全段で利用できる状態がないことがある。また照会中にキャッシュが削除される可能性もある。したがって、候補の早期発見と、実際のキャッシュ木を使った確定検証を分ける必要がある。

従来の単純な受付では、各段でキャッシュ木を走査して局所的な再利用位置を求め、全段で合意した後に再度走査して保護する。木の変更を守る排他制御や段間通信のため、複数の要求が同時に準備されると受付が直列化しやすい。さらに、接頭辞を保護しても、残りの入力片のための空きブロックが確保されていなければ、その要求は実行できない。複数要求が接頭辞だけを保護してメモリを埋めると、誰も末尾を計算できなくなる危険がある。

## 手法

### 1. 要求受付とGPU実行を分ける二経路

各段は要求受付・通信・再利用位置の合意・容量確保を行うWAVEスレッドと、モデル実行および物理的なキャッシュブロックの具体化を行うLOOPスレッドを持つ。段0が受付の主導役であり、要求を受け取ると他段へ通知する。受付の通信は段0からの配信と全段からの集約を組み合わせ、複数要求を一つの通信ラウンドにまとめる。GPUへ渡す実行計画と活性化の転送は別の通信経路で扱う。

この分離により、WAVE側で段間の合意が完了するのを待っている間も、LOOP側は既に受付済みの要求を計算できる。全段が物理的な末尾ブロックを作り終えるまで段0を止める必要はなく、各段は自分の処理波が到着する前に局所的なブロック確保と要求メタデータを完成させる。後段がまだ準備中でも、段0の準備が整えば最初の処理波を開始できる。

ただしこの非同期化は「どの段でも任意の順番で実行してよい」という意味ではない。段0は各処理片の要求ID、開始位置、長さを明示的に他段へ送り、受け手は同じ順番・トークン境界を使う。位置が一致しなければ、誤ったキャッシュで計算を続けず実行を失敗させる。局所的なキャッシュ管理と共通の実行順序を切り分けた点が重要である。

### 2. 接頭辞の候補を見つける分割ヒント索引

WavePPは、実際のキャッシュ木のブロックを保持しない軽量なヒント索引を持つ。各入力ブロック$B_i$について、直前の接頭辞ハッシュ$H_{i-1}$、追加鍵、ソルトを組み込んだ$H_i=hash(B_i,extraKeys_i,salt,H_{i-1})$を計算する。索引はキャッシュ窓とハッシュをキーに参照数を保持し、キャッシュ木にブロックが追加・削除されるたびに更新する。ブロックが別階層へ退避されても再利用可能性が残るため、退避だけでは索引から削除しない。

通常の注意キャッシュでは、候補となる接頭辞長を倍々に増やして探索し、最初の不一致後に二分探索する。これにより、$N$個の候補ブロックを線形に調べる代わりに、おおむね$O(\log N)$回の索引照会で最長候補を得る。要求全体のハッシュ作成には$O(N)$の処理が必要な点は変わらない。再帰状態のスナップショットは疎なので、注意側の候補位置から後方へ探索し、実際に保存されている状態境界まで下げる。

各段の候補を集めて共通の終端を選ぶ。ただし索引は照会中にも更新され得るので、ここで得るのはあくまでヒントである。確定時には実キャッシュ木を再走査して保護する。200Kトークン、同時64要求の負荷試験では、最適化した分割索引により中央値の探索時間が64.4ミリ秒から24マイクロ秒に短縮し、99百分位でも2.35ミリ秒だった。これは要求全体の入力処理時間ではなく、接頭辞候補の照会部分の測定である。

### 3. 局所リースによる接頭辞の保護

共通候補が決まると、各段はその範囲の実キャッシュブロックへ参照を設定し、要求が物理的に具体化されるまで削除・退避の対象にされないようにする。論文の「リース」は時間期限を持つ賃借権ではなく、要求のキャッシュ参照へ所有権を引き継ぐまで保持する参照である。木の排他制御を保持したまま段間通信しないよう、確定した局所的な参照を報告する前にロックを解放する。

索引が古かった場合、ある段は合意した位置まで確保できないことがある。WavePPは各段が実際に保護できた終端を照合し、必要に応じて共通位置を下げる。再帰状態の保存位置が段によって違う場合は、一度下げた位置でも別段のスナップショットが欠けていることがあり、さらに前の共通位置へ戻る。通常の実験ではこの不一致は観測されなかったが、頻繁な要求取消しを伴う極端な負荷では一度発生したと原著は記す。

接頭辞の参照保護は他要求のための空きメモリを減らすので、リースの取得は受付可能になった要求の先着順で行う。リースを同時に持てる要求数をバッチ上限とメモリ余裕で制限し、パイプライン段数$P$と最大波予算$M$に比例する$2PM$のトークン余裕を確保する。巨大な単一要求だけは、この余裕条件を一部緩和して進行不能を防ぐ。

### 4. 容量の事前予約（capacity escrow）

リースで既存接頭辞を保護した直後に、未計算の末尾のために各層で必要な容量を予約する。空きブロックだけでなく、将来退避または削除して回収できるブロックも候補にする。退避先のホストメモリが必要なら、その転送先容量も先に確保する。予約は回収候補の参照を持つが、実際のデータ移動やキャッシュ木からの切離しはまだ行わない。

この設計では、別の要求が予約候補の既存ブロックを再利用し始めることができる。確定時に参照数が増えていたら、その候補を無理に消さず同じキャッシュ窓から代替候補を取得する。代替を確保してから元の予約を解放するため、既存要求の再利用を壊さず末尾容量を守れる。合意した再利用位置が112Kから96Kへ下がった200K入力の例では、末尾は88Kから104Kへ増えるため、差分の容量を追加予約してから確定する。

すべての段でリースと容量予約の確定に成功したときだけ、段0は実行計画へ進める。失敗時には予約を解放してからリースを解放し、再試行または待機へ戻す。実際の末尾ブロック割当て、退避・削除、キャッシュ木への接続は、LOOP側がその要求を実行する直前に局所的に行う。早すぎる物理的削除を避けつつ、実行に必要な容量を前もって保証する点が、単なる接頭辞ヒット判定との違いである。

### 5. 最大パイプライン利用率を狙う処理波の調整

受付が高速でも、各要求の末尾を常に最大予算$M$の処理波へ詰め込むと、同時に走らせる波の数が不足する。例えば合計$2M$トークンしか準備できていないとき、$M$ずつなら2波だが、$M/2$ずつなら4波となり、4段パイプラインを埋めやすい。一方、波を細かくしすぎるとGPU起動や段間活性化転送の固定費が増える。

WavePPの最大パイプライン利用率計画器（Maximum Pipeline Utilization、MPU）は、受付済みの未実行トークンと既に実行中の波を数え、パイプラインが十分に埋まる範囲で波予算を選ぶ。実行リングは$R=2P$波を保持し、段ごとに実行中の波と待機波を確保できる。計画器は$M$から半減を繰り返した候補と最小予算$b_{min}$を用い、波の数が不足すると小さくする。急な変動を防ぐため、予算を増減する際の持続判定やヒステリシスも入れる。

段0は先着順の要求を波へ詰め、各要求が持つ「レーン」を複数波にわたり維持する。小さな余りへ無理に長い要求の断片を詰めると波が増えすぎるため、断片の下限を設定する。これはGPU演算時間を厳密に予測する計画器ではなく、残存トークンと処理波数を代理量として使う実装である。長い末尾をまとめる方が有利な条件では、動的分割が逆効果になり得る。

| GLM 5.2、長入力90%再利用、同時8 | 316,516 | 278,418 | **−12.0%** | 低同時性では提案方式が負ける |
| MiniMax M2.7、長入力90%再利用、同時8 | 250,815 | 206,548 | **−17.6%** | 37/40改善であり全条件改善ではない |
| GLM 5.2、未計算4K、同時128 | 416,294 | 1,212,572 | +191.3%、2.91倍 | 多数の短い末尾を高速に受付できる |
| MiniMax M2.7、未計算4K、同時128 | 551,143 | 1,113,196 | +102.0%、2.02倍 | 高負荷での受付詰まりを緩和 |

単位は、キャッシュから再利用した入力を含む総入力トークン/秒である。高い倍率を「GPUが毎秒処理する新規トークンが2.91倍」と言い換えてはならない。未計算4Kの同時128要求では、入力処理完了時間の中央値もGLMで約71%、MiniMaxで約55%短縮した。冷たい要求と混合要求は全条件で改善したが、長い接頭辞を再利用する低同時性の2条件など、計3条件では逆転した。

### 2. Kimi K3の8段PPと他基盤

| 条件 | WavePPの結果 | 比較・解釈 |

| 28条件全体 | 21条件で最高処理量 | 他の7条件では別方式が上回る |
| 同時8要求以上の18条件 | **18条件で最高処理量** | PPの複数段を埋められる負荷で強い |
| 全28条件の幾何平均 | SGLang PP8比+9.2%、vLLM PP8比+15.7% | 基盤間の構成差を含む |
| 131K・90%再利用、同時32 | 289,096入力トークン/秒 | 完了時間中央値13.2秒、95百分位17.0秒 |
| 262K・90%再利用、同時32 | 218,743入力トークン/秒 | SGLang PP8は184,753、完了時間44.1秒（WavePPは35.8秒） |

Kimi K3はMLAキャッシュとKDA再帰状態を併用するため、各段の再利用可能位置の合意が特に難しい。WavePPはその合意と容量予約を先に進めることで高同時性で優位になる。ただし同時1要求ではパイプラインを満たす独立した仕事が少なく、テンソル並列（TP）の方が速い。混合要求では処理量と中央値が良くても末尾遅延が悪化する条件があるため、サービス水準の95百分位制約は別途評価すべきである。

## 既存研究との違い

Sarathi-Serveや既存のチャンク化入力処理は、入力処理と生成の干渉やバッチの均衡を主に扱う。WavePPは、接頭辞キャッシュを各段が独立管理する構成で、要求が実行可能になるまでの分散した合意・保護・容量予約をGPU実行と並行化する。接頭辞を速く探すだけでは末尾容量を確保できず、容量を先に確保するだけでは全段の再利用可能な終端が一致しないため、複数の機構を連結している。

vLLMやSGLangの既存パイプライン実装は、共有された論理状態や順序づけられた要求列によって段間の調整を行う。WavePPは局所的なキャッシュ木の更新・退避・削除を各段に許しつつ、処理波の実行順序だけを共通化する。混合注意モデルの再帰状態スナップショットも、通常のKVブロックとは異なる再利用境界を持つものとして扱う点が特徴である。

MPUは、GPUカーネル自体の計算量を減らすものではない。要求受付によって準備できた処理片の量と、パイプラインに既に入っている処理波を見て、空き段を減らすために波の予算を調整する。したがって、モデルの計算時間が支配的な冷たい長入力では改善が小さく、短い末尾を大量に処理する高同時性で効果が大きい。

## 限界・再現上の注意

論文の対象は分離型推論の入力処理担当であり、生成段階を含む全体の利用者応答時間を一律に短縮したことは示していない。実験はPP4とPP8、指定モデル、B300/GB300、特定のキャッシュ予算に限定される。段間の層数が不均等な構成、異種GPU混在、多数の複製インスタンスにまたがる要求振分けでは同じ結果を保証しない。

非同期の合意・参照保護・容量予約には、取消しと競合に対する追加の状態管理が必要である。論文は極端な要求取消し負荷で一度、局所リースの終端が段間で一致しなかった事例を報告している。共通位置を下げる再調整や再試行は実装されているが、実運用での無制限な取消し・資源圧迫に対する完全な進行保証が実証されたわけではない。予約に失敗した要求は待機へ戻るため、短期的な待ち時間が増えることもある。

処理量の定義はキャッシュ再利用分を含むため、接頭辞が長いほど同じ新規計算量でも入力トークン/秒は大きくなる。4段PPの比較は同じカーネルで因果解釈しやすいが、Kimi K3の基盤横断比較は異なる実装・メモリ構成・並列方式を含む。最良の処理量だけを見てGPU計算カーネルの性能優劣と解釈してはならない。

負の結果として、GLMとMiniMaxの長接頭辞再利用・同時8要求でそれぞれ12.0%、17.6%処理量が低下した。Kimi K3の同時1要求ではテンソル並列に大きく劣る。混合要求では95百分位の完了時間が最良PP方式より長い条件があり、MPUの構成要素除去でも262K再利用・同時32要求で9.7%悪化した。よって、同時要求数、接頭辞長、未計算部分の長さ、要求分布によって設定を切り替える必要がある。

公式実装の公開URLは原著中に確認できない。著者はTensorRT-LLM上での実装と具体的な実験条件を説明しているが、上流TensorRT-LLMへ統合された機能とみなす根拠はない。再現には、接頭辞索引とキャッシュ木の整合、リース参照数、退避先容量の予約、段間合意、実行波の順序を同時に検証する必要がある。
