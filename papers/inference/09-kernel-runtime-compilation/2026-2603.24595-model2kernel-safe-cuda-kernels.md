# Model2Kernel: Model-Aware Symbolic Execution For Safe CUDA Kernels

> モデル側からCUDA呼出し条件を抽出するHFProbeと、動的テンソル・全CUDAスレッドを記号化するcuKLEEを組み合わせ、LLM推論カーネルの未知メモリバグ353件を9誤検出で検出した。
## 書誌情報
- **著者**: Mengting He, Shihao Xia, Haomin Jia, Wenfei Wu, Linhai Song
- **著者・所属**: The Pennsylvania State University; State Key Lab of Processors, Institute of Computing Technology, CAS; Peking University
- **公開**: arXiv
- **種別**: Preprint
- **対象**: LLM推論安全性、CUDA、記号実行、メモリ安全性、vLLM、カーネル検証
- **実装**: 論文はcuKLEEをKLEE v3.1上の約31,000行C++として実装し、HFProbe用にvLLM/TransformersのGPU実行・重み読込み・KVキャッシュ経路を模擬するバックエンドを構築している。確認時点で一次資料から公式公開コードURLは特定できなかった。
## 概要
LLM推論のCUDAカーネルは、モデル依存テンソル形状、可変長入力、巨大なスレッド並列、32ビット添字計算が組み合わさるため、特定モデル・長文条件でのみ現れる整数オーバーフローや範囲外アクセスを含み得る。Model2Kernelは、モデルがどのカーネルをどの引数関係で呼ぶかをGPUなしで観測するHFProbeと、CUDA向け記号実行器cuKLEEを結合する。HFProbeはPythonの呼出しグラフ、偽GPUバックエンド、モデル設定変異から、モデル構造で固定される値とユーザー入力で変化する値を推定する。cuKLEEは動的テンソルを離散メモリ領域として抽象化し、テンソルAPI、CUDAスレッド識別子、起動構成を記号変数化して、範囲外アクセス、整数オーバーフロー、データ競合、NULL参照の成立可能性をZ3で検査する。120モデル・173カーネルで未知353件を発見し、誤検出は9件だった。

Model2Kernelの新規性は、CUDAカーネルだけを孤立して解析せず、上位のLLMモデル実装からカーネル引数の意味と関係を抽出して記号実行へ戻す点にある。HFProbeはGPU不要の模擬実行と静的呼出し解析、設定変異を組み合わせ、隠れ次元などの構造固定値とバッチ・系列長・トークン数に比例する値を分類する。cuKLEEは各テンソルを互いに離れた記号メモリ領域として扱い、140種類のTensor/TensorIteratorメソッドを要約し、スレッド・ブロック識別子も記号化することで、動的配列と大量スレッドを一つの解析状態で扱う。

代表結果として、未知メモリバグ検出は120モデル、173 CUDAカーネルで事前未発見に対して353件（integer overflow 328、out-of-bounds 25）。LLM推論で使われるカーネルに、長文・大バッチ・モデルshape依存で顕在化する安全性欠陥が広く残っている。
## 問題設定
LLM推論基盤はモデルごとに異なるテンソル形状や隠れ次元をCUDAラッパへ渡し、ユーザーのバッチ数・系列長・トークン数によって実行時の添字範囲や起動グリッドも変わる。このため、同じCUDAカーネルでもあるモデルや通常入力では安全なのに、長文や別アーキテクチャでは32ビット整数がオーバーフローして範囲外アクセスを起こすことがある。動的検査は実際に危険入力を与えなければ発見できず、既存のGPU静的解析や記号実行は実行時サイズのテンソル、PyTorchラッパ、数千スレッド、可変起動構成を扱えない。すべての引数を無制約の記号値にすると非現実的な巨大形状まで探索して大量の誤検出と経路爆発を起こす。したがって、モデルと推論フレームワークが現実にカーネルへ与える制約を自動抽出し、その条件下でCUDA固有のメモリ安全性を網羅的に検証する必要がある。
## 新規性
Model2Kernelの新規性は、CUDAカーネルだけを孤立して解析せず、上位のLLMモデル実装からカーネル引数の意味と関係を抽出して記号実行へ戻す点にある。HFProbeはGPU不要の模擬実行と静的呼出し解析、設定変異を組み合わせ、隠れ次元などの構造固定値とバッチ・系列長・トークン数に比例する値を分類する。cuKLEEは各テンソルを互いに離れた記号メモリ領域として扱い、140種類のTensor/TensorIteratorメソッドを要約し、スレッド・ブロック識別子も記号化することで、動的配列と大量スレッドを一つの解析状態で扱う。
## 手法
### 手法のあらまし
処理はモデル側の文脈生成とカーネル側の記号実行に分かれる。HFProbeはまずHugging Face形式モデルのforward()からPython ASTを解析し、nn.Moduleの__call__やフィールド参照を追跡してCUDA Python bindingへ到達する呼出しグラフを作る。次にvLLMやTransformersを改変した模擬バックエンドでモデルを実行する。実際のCUDA bindingは偽関数へ置換し、呼出しスタック、引数型、テンソル形状・dtype、整数テンソルの範囲、プリミティブ値を記録する。GPU重みはロードせず、必要な形状の偽テンソルだけを作るためGPUなしでモデル経路を通せる。静的には到達可能だが通常設定では呼ばれないカーネルがあれば、GPT-5 agentによるconfig.json変異とフレームワーク設定の既知マッピングを使って追加構成を生成し、失敗構成を除外する。収集した呼出しから、各引数についてバッチ数BS、系列長SL、総トークン数TC=BS×SLへの線形関係、アーキテクチャで不変な値、引数同士の等値関係、観測最大値による上限を推定して解析文脈を作る。cuKLEEはPython bindingの先にあるホストwrapperからLLVM IRを記号実行し、wrapper内で計算されるgrid/block、共有メモリ量、hidden sizeなども含めてカーネル呼出しへ到達する。入力テンソルごとにbase address、要素数、次元数、各次元、要素サイズを記号変数化し、領域を互いに十分離れたものとして扱う。Tensor APIは実装へ潜らず意味制約だけを付加する。blockIdx/threadIdx/gridDim/blockDimはCUDA起動条件付きの記号変数とし、ワーク分配ループも全スレッドを列挙せず代表的な記号スレッドで扱う。範囲外アクセスは有効テンソル領域外へのポインタ成立性、整数オーバーフローはint32加算・乗算の範囲超過、NULL参照は未知base、データ競合は異なる二つの記号スレッドが同一アドレスへ競合アクセスできるかとしてZ3へ問い合わせる。これにより、モデル固有の現実的制約を保ったまま入力空間の危険条件を探索する。

### HFProbeによるモデル文脈抽出
HFProbeはモデルのPython実装と推論フレームワークを解析し、どのモデルがどのCUDAカーネルをどの引数関係で呼ぶかを収集する。forward()からの経路・フィールド感応なAST呼出し解析に加え、vLLM/TransformersのCUDA bindingを偽関数へ置き換え、GPU計算や実重み読込みを行わずに制御フローを実行する。呼出しごとにテンソル形状、dtype、整数値範囲、プリミティブ値を保存し、hidden sizeのようなアーキテクチャ固定値、バッチ/sequence/トークン countに連動する値、等値関係、残余の上限へ分類する。この文脈によってcuKLEEへ非現実的な自由度を与えず、実モデルが作り得る状態へ探索空間を絞る。

### 設定変異によるカーネル到達範囲拡張
一つの既定configでモデルを実行しただけでは、量子化方式やattention backend、MoE構成など特定設定でしか使われないCUDAカーネルへ到達できない。HFProbeは静的呼出しグラフで『到達可能だが未観測』のカーネルを検出すると、GPT-5のagent modeでconfig.json候補を生成し、さらにフレームワーク固有の環境変数・起動設定マッピングも使って経路を活性化する。実行に失敗する変異は破棄し、成功した構成の観測だけを解析文脈へ統合する。評価では1,274の異なるモデル構成から8,562の一意な解析文脈を生成しており、設定変異を無効化するとvLLMで発見した39件中32件を見逃すため、モデル依存経路を網羅する中心機構になっている。

### cuKLEEの動的テンソルメモリ抽象化
通常のKLEE型メモリモデルではsymbolicなmallocサイズが後続領域のアドレスまでsymbolicにし、どのポインタがどのテンソルへ属するかの判定が急速に難しくなる。cuKLEEは推論フレームワークが別々に割り当てた入力テンソル同士をカーネルが跨いだポインタ算術に使わないという観察から、各テンソルを十分離れた離散領域として配置する。base address、要素数、次元数、各shape、要素サイズを記号変数として持たせ、numelやsize、sum等140種類のTensor/TensorIterator APIは実装を展開せず、返値や新テンソルとの関係を制約として要約する。これにより動的shapeを保持しながらライブラリ内部の状態爆発を避け、実際のwrapper計算とメモリアクセス境界を追跡できる。

### CUDAスレッド記号化とバグ述語
cuKLEEはblockIdx、threadIdx、gridDim、blockDimのx/y/z成分を記号変数として導入し、threadIdx.x < blockDim.xのような起動制約を付与する。個々の数千スレッドを別状態で実行せず、記号スレッド一つで全IDの可能性を代表させ、ワーク分配ループも終了条件を制約へ足して一度だけ本体を解析する。データ競合では同じ起動条件を共有する二つ目の記号スレッドを作り、異なるIDの二スレッドが同一実効アドレスへアクセスし、少なくとも片方がwriteとなる条件を解く。さらにout-of-bounds、int32加算・乗算overflow、NULL pointer dereferenceを個別の制約充足問題としてZ3へ渡すため、CUDA固有の並列添字バグをモデル文脈と同時に検証できる。

### 全体のデータ／制御の流れ
Model2Kernelは、上位モデルから現実的な呼出し制約を作るHFProbeと、その制約をwrapperおよびCUDAカーネルのLLVM IRへ注入するcuKLEEの二段構成である。静的到達解析と模擬実行がカバレッジを補完し、設定変異で未観測経路を増やし、解析文脈ごとに記号実行する。GPU実機テストではなくモデル制約付きの記号検証なので、危険入力そのものを事前に知らなくてもバグ条件を導出できる。
## 評価条件
- **ハードウェア**: HFProbeはGPU不要、既存比較ツールは必要に応じ簡略化CUDAカーネルで評価
- **ソフトウェア**: KLEE v3.1、LLVM IR、Z3、vLLM、Hugging Face Transformers、GPT-5 agent modeによる設定変異、Honeycomb、GKLEE、ESBMC-GPU
- **モデル**: vLLM text-generationモデル62種、Hugging Faceのcustom CUDA カーネル利用モデル54種、最近の研究成果物由来モデル4種
- **データセット／トレース**: 120モデル、173 CUDAカーネル、170,875行Python、139,951行CUDA、既知vLLMメモリバグ20件
- **比較対象**: Honeycomb、GKLEE、ESBMC-GPU、HFProbeなしcuKLEE、小入力での実GPU動的実行、設定変異なしHFProbe
- **正確性・品質**: 発見候補を手動確認し真陽性・誤検出へ分類する。対象バグ種は整数オーバーフロー、範囲外アクセス、データ競合、NULLポインタ参照。既知vLLMバグ20件では既存ツールとの検出数比較を行うが、既存ツールが現代vLLMコードを直接扱えないため簡略化が必要だった点を明示する。
- cuKLEEの初期ユーザー入力範囲はバッチ size <=1000、sequence length <=1,000,000を既定とし、total トークン count=BS×SLの関係を付与する。
- 各カーネル解析は最大1時間。
- HFProbeはGPU bindingをfake functionへ置き換え、重みをロードせずshapeだけを保持し、遅延KV キャッシュ割当も模擬する。
- GPT-5 agentで生成した無効config変異は実行失敗時に破棄する。
- 20既知vLLMバグの内訳はinteger overflow 10件、追加バッファ overflow 8件、NULL dereference 2件。
3ソースからモデルとCUDAカーネルを収集してHFProbeで到達経路・引数関係を抽出し、1,274のモデル構成を8,562の一意解析文脈へ統合してcuKLEEを実行する。未知バグではソース別の真陽性・誤検出を数え、既知バグではHoneycomb/GKLEE/ESBMC-GPUとのcoverageを比較する。構成要素除去実験ではHFProbeなし、cuKLEEの代わりに実GPU小入力実行、設定変異なしを比較して、それぞれの誤検出、検出数、解析時間、timeoutへの影響を測る。総解析時間とagentコストも報告し、実用上の計算負荷を示す。
120モデル・173 CUDAカーネルの大規模静的/動的混合検証だが、Hugging Face形式かつTensor入力のCUDAカーネルへ対象を限定する。Triton、TensorFlow、NPU命令、複数GPU間アクセスの一部は範囲外。性能ベンチマークではなく安全性検出性能の評価である。
## 主要結果
Model2Kernelは120モデル・173 CUDAカーネルを解析し、未知のメモリ安全性バグ353件を発見した。内訳は32ビット整数オーバーフロー328件と範囲外アクセス25件で、データ競合とNULL参照の未知例は0件、誤検出は9件だった。ソース別ではvLLM 39件、Hugging Faceカスタムカーネル290件、研究成果物24件の真陽性を報告する。既知vLLMバグ20件では15件を検出し、Honeycomb 0件、GKLEE 5件、ESBMC-GPU 3件を上回る。HFProbeを外すと誤検出が5,527件へ増え平均解析時間も2.5倍になるため、モデル文脈で記号空間を絞る設計が精度と速度の両方に不可欠である。

- 未知メモリバグ検出 / 353件（integer overflow 328、out-of-bounds 25） (比較対象: 事前未発見; 条件: 120モデル、173 CUDAカーネル) — LLM推論で使われるカーネルに、長文・大バッチ・モデルshape依存で顕在化する安全性欠陥が広く残っている。

- 誤検出 / 9件、誤発見率約2.49% (比較対象: 353真陽性; 条件: 全未知バグ候補の手動確認) — モデル呼出し制約を注入することで、無制約記号実行にありがちな非現実的shape由来の警告を大幅に抑える。

- 既知vLLMバグcoverage / 20件中15件 (比較対象: Honeycomb 0、GKLEE 5、ESBMC-GPU 3; 条件: 既知20 CUDAメモリバグ、比較器向け簡略化を含む) — 動的テンソルとモデル依存launch条件を扱えることが従来GPU解析器との差になる。

- HFProbe除去アブレーション / 誤検出5,527件、平均解析時間2.5倍、1時間timeout 23カーネル（HFProbe有りより16件増） (比較対象: 完全Model2Kernel; 条件: cuKLEEへモデル文脈を与えない) — 記号実行器の能力だけでは不十分で、現実のモデル制約を上位層から抽出することが探索空間制御に直結する。

- 設定変異の寄与 / 無効化するとvLLMで発見した39件中32件を見逃す (比較対象: 設定変異あり; 条件: 既定モデル設定だけでHFProbeを実行) — 量子化・backend・モデルconfigで条件付きに呼ばれるカーネルを能動的に起動する必要がある。

- 解析コスト / 総985.95時間（cuKLEE 902.19、HFProbe 103.66）+ GPT agent $442.16 (比較対象: なし; 条件: 全評価。8,562解析文脈、各カーネル最大1時間) — GPU不要でも計算量は大きく、特に大規模融合カーネルの記号探索が支配的である。

### 負の結果・境界条件
- 8,562解析文脈のうち778件が1時間上限へ達し、すべて600行超級の大きなカーネルを含んでいた。大規模融合カーネルでは経路爆発がなお主要制約である。
- 既知20件のうち5件を見逃した。原因には複数GPUアクセスを静的に扱えない例、tensor shape metadataと実メモリlayoutの不一致、2件のtimeout、未対応std::map依存が含まれる。
- HFProbeはfake カーネル境界を跨ぐtensor値を追跡せず実重みもロードしないため、その抽象化不足が9誤検出中6件の原因になった。
- 実GPUで小さなバッチ/sequenceだけを動的実行する代替では、入力範囲が狭すぎて対象バグを検出できなかった。
- Tritonカーネル、TensorFlowモデル、NPU、一般的な非Tensor CUDA入力は現方式の対象外である。

### 結果の読み方
最大のポイントは、CUDA記号実行を単独で強化したことより、解析対象を『カーネルコード』から『モデルがそのカーネルをどう使うか』へ拡張した点にある。hidden sizeやtensor dimensionを無制約にすれば、ソルバーは現実のモデルでは存在しない巨大shapeを容易に見つけ、警告数も解析時間も膨張する。逆に実GPUテストだけでは極端な長文やバッチ条件を網羅できない。HFProbeが実モデルから制約を抽出し、cuKLEEがその制約内を記号的に広く探索する組合せにより、動的テストと純粋静的解析の弱点を相互補完する。353件の多くがinteger overflowであることは、コンテキスト長やバッチ規模の拡大で既存のint32前提が安全でなくなるという推論基盤特有のリスクも示す。
## 品質への影響
モデルの生成品質や推論近似には影響しない。検出対象の欠陥はクラッシュだけでなく誤ったメモリアクセスによる推論結果破壊、モデル重み改変、GPUメモリ攻撃につながり得るため、運用信頼性とセキュリティ品質を直接扱う。
## 既存研究との差
- **Compute Sanitizer等の動的検査との差**: 動的検査は実行した入力・スレッド経路で起きた不正アクセスを検出するが、危険条件を事前に知る必要がある。Model2Kernelはモデルから得たバッチ/sequence/トークン範囲を記号化し、実GPUで巨大入力を走らせずにその範囲内の危険条件をソルバーで探索するため、極端だが合法な長文条件も対象にできる。
- **GPUVerify/GKLEE等の静的GPU解析との差**: 従来解析器は孤立したカーネルや固定サイズバッファを前提にしやすく、PyTorch Tensorの実行時shapeやwrapperが計算するlaunch configurationを扱いにくい。cuKLEEはTensor領域とTensor APIを専用抽象化し、HFProbeがモデル由来の制約を与えることで現代LLM推論コードを対象にする。
- **一般的なKLEE記号実行との差**: symbolic mallocサイズを連続アドレス空間へ置くと、後続allocation位置までsymbolicになりpointer所属判定が難しくなる。cuKLEEはframework管理Tensorを互いに離れた領域へ置き、CUDA thread/block IDも記号変数化して、一つの状態で多数スレッドを代表する。これはLLM CUDA wrapperの構造に合わせた専用化である。
- **カーネル性能最適化系統との差**: Harness Engineeringや自動カーネル生成が速度と正当性を両立した候補生成を扱うのに対し、Model2Kernelは既存カーネルがモデル依存条件でメモリ安全性を破らないかを検証する。高速化とは独立した安全性レイヤーであり、生成・最適化された候補を本番へ昇格する前の自動検証器として補完的に利用できる。
## 限界
- 現実装はHugging Face形式モデルとTensor入力を持つCUDAカーネルへ限定され、Triton、TensorFlow、NPUカーネルは未対応である。
- 各カーネルの記号実行を1時間で打ち切るため、600行超の大型融合カーネルを中心に778解析文脈がtimeoutし、全経路を網羅できない。
- HFProbeはGPU計算と重み読込みを模擬するため、fake カーネル境界を跨ぐtensor値や実重み依存条件を失い、誤検出の原因になる。
- 設定変異は到達範囲を大幅に増やすが、現実に取り得る全configを列挙するものではなく、条件付きカーネルの未観測は残り得る。
- cuKLEEはKLEEのC/C++向け経路探索戦略を継承しており、CUDA特有のSIMT・融合カーネルに最適化された探索ではない。
- 複数GPU間メモリアクセス、std::map等未対応ライブラリ、shape metadataと実メモリlayoutが不一致なコードでは既知バグを見逃した。
- 総解析時間約986時間と設定変異agent費用が必要で、大規模継続統合へ入れるには差分解析や並列化、timeout管理が必要になる。
## 実装状態
論文ではHFProbeとcuKLEEの実装規模・構成を詳細に説明しているが、2026-09-14の確認ではarXiv一次資料に公式コード公開URLを確認できなかった。したがって手法は実装済み・大規模評価済みだが、外部再現用コード公開状況は未確認として扱う。
## 研究上の位置づけ
LLM推論基盤の信頼性・セキュリティとGPUカーネル検証の交点に位置する。推論システム研究ではスケジューリング、KVキャッシュ、カーネル高速化が性能中心になりやすい一方、コンテキスト長やモデル多様化で古い整数幅・shape前提が破れると、同じ最適化カーネルが本番障害や攻撃面になる。Model2Kernelはモデル構造を解析文脈として使うことで、検証対象を下位CUDAだけに閉じない点が重要である。今後はTritonや自動生成カーネルを含むCI/CDへ統合し、性能ハーネスの昇格条件にメモリ安全性証明を追加する方向、CUDA向け経路探索器を導入して大型融合カーネルのtimeoutを減らす方向が自然な発展になる。
