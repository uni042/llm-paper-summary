# X-Stage: Modeling Post-Issue Backpressure in GPU Communication–Computation Fusion

> 遠隔書き込みの発行後区間を排出率と有限容量でモデル化し、バースト間隔から背圧の蓄積と回復を予測してスケジュールを直すことで、専門並列で最大1.62倍、テンソル並列で最大1.75倍、系列並列で最大1.43倍の高速化を実測した。

## 概要

複数GPUで大規模モデルを動かすと、テンソル並列、専門並列、系列並列のいずれでもGPU間通信が計算の合間に現れる。最近の融合カーネルは、ホストへ戻らずにカーネル内部から相手GPUのメモリへ直接書き込む遠隔書き込みを使い、タイル単位で通信と計算を重ねる。このとき重なりがうまくいくかは、通信の総量だけでは決まらない。同じバイト数、同じ計算でも、書き込みのまとまり（バースト）の間隔が違えば、送信側の停滞は変わる。

本論文が特定したのは、遠隔書き込みが送信側で受け付けられてから相手先のメモリで見えるようになるまでの区間であり、これをX-Stageと呼ぶ。実測の振る舞いは3つの様相を示す。回復した状態からの短いバーストは、背圧のない発行下限で終わる。短い間隔でバーストを繰り返すと排出律速になり、間隔を広げるほど後の発行の停滞が同じ量だけ減って、やがて下限へ戻る。十分に大きな単独バーストは、過去の滞留がなくても容量の折れ点を越えて自分自身を背圧する。つまりこの区間は、完了まで発行者を止めるものでも、無制限に先行できるものでもなく、有限の余裕を持ち、計算の合間に圧力が抜ける段階である。

この振る舞いを、Burst-Gapモデルとして3つの量で表す。回復状態での発行下限、有効排出率、有効未完了容量である。実測系では排出率は約717GB毎秒、容量は約4.25MiBと較正された。これらは応用とは独立に、間隔を変える実験と単独バーストの実験から別々に決め、応用側はバーストの到着とその間の計算時間だけを与えて、滞留が溜まるか回復するかを予測する。

設計への使い方は2通りである。バーストが続いて余裕を使い切る場合は、実行可能な独立した計算を割り込ませて到着を整形し、排出の時間を作る。既存の計算が十分な排出窓になる場合は、発行後にその計算へ戻るだけで自然な重なりになる。代表結果として、専門並列のMegaMoEでは到着の整形で融合カーネルが幾何平均1.18倍、最大1.62倍高速になり、テンソル並列の行列積と全削減の融合では1.59〜1.75倍、系列並列の注意と全対全の融合では送信側で最大1.43倍の高速化が得られた。いずれも実機測定である。

## 問題設定

遠隔書き込みには、区別すべき3つの時点がある。送信側で受け付けられ発行者が先へ進める時点、相手先のメモリで見えるようになる時点、そして順序付けや信号の条件を満たして相手が安全に使える時点である。正しさの仕組みは後者2つを扱うが、送信側の計算がいつ再開できるかは最初の時点と、その後の下流の進み具合で決まる。従来の融合方式の抽象は、誰が発行するか、いつ発行するか、相手がいつ使えるかをよく表す一方、受け付け済みの通信がどれだけ滞留し、いつ圧力として送信側へ戻るかを定量化しない。

演算子単位のモデルでは、融合した遅延を計算時間と通信時間の大きい方と近似する。これは総量のモデルであり、バーストの間隔という情報を捨てている。間隔が違えば、一方は合間に圧力が抜けて停滞せず、他方は有限の容量を使い切って計算側まで止まるという、結果の違う2つの実行が同じ予測になってしまう。また、発行区間を測る通常の方法では、相手先で見える時点を発行の終わりと混同しがちで、送信側が見ている発行時間そのものを捉えられない。

したがって不足しているのは、発行後の区間についての、較正可能で予測に使えるモデルである。必要な性質は、プラットフォーム側の量とカーネル側の量を分離すること、単独バーストの容量限界と繰り返しバーストの滞留蓄積を別々に表すこと、そして予測した発行の遅れが実際に計算側の停滞になる条件までつなぐことである。本論文はこの3点を、マイクロベンチマークによる特徴付けから始めて満たしていく。

## 手法のあらまし

処理の流れは、特徴付け、モデル化、適用の3段である。まず、遠隔書き込みのバーストと、遠隔書き込みを出さない間隔を交互に繰り返す実験と、回復状態から単独バーストの大きさを変える実験で、回復、排出律速、容量の折れ点という3つの様相を分離して観測する。次に、発行下限、排出率、有効容量の3量からなるモデルを作り、均一な繰り返しについては周期の式で、非均一な実行については周期ごとの滞留の漸化式と容量の検査で予測する。最後に、各カーネルについてバースト列と間の計算をモデルへ写し、圧力の指標と滞留の変化と容量検査を計算する。滞留が溜まる場合は独立した計算を割り込ませ、既存の計算で回復する場合はその窓を使う。予測した発行の遅れは、局所バッファの再利用時点まで残っている場合にだけ計算側の停滞になる。

## 手法

### 1. 特徴付け — 回復と排出律速と容量限界を分けて観測する

この機構が観測するのは、送信側から見た発行時間である。並行する発行者の数と1発行者あたりのバイト数でバースト量を決め、2種類の実験を行う。周期実験ではバーストと、遠隔書き込みを出さない間隔を交互に繰り返し、間隔を変えて回復を測り、間隔ゼロで排出律速の定常状態へ追い込む。単独実験では回復状態からバースト量だけを変え、過去の滞留なしに容量限界が現れるかを測る。局所メモリへの書き込みを対照として、通常の発行ループ自体の効果と遠隔経路固有の圧力を分ける。

観測結果は、間隔を広げると後の発行の停滞がほぼ1対1で減って下限へ戻ること、周期の曲線が「完了まで止まる」形ではなく排出律速の平坦部から回復側へ切り替わる形をすること、単独バーストにも折れ点があることの3点である。これにより、間隔の時間は通信完了の後に追加される無駄時間ではなく、発行済み通信の排出と重なっていることが分かる。追加費用は測定自体のコストだけであり、この段階は製品の実行には入らない。失敗時の挙動として、この特徴付けを混ぜて測ると、容量限界を速度限界と誤読したり、蓄積を単独バーストの大きさの問題と誤読したりする危険があり、2種類の実験を分けたこと自体が方法上の要点である。

### 2. Burst-Gapモデル — 3つの較正量で滞留の蓄積と回復を予測する

モデルが保持する状態は、周期ごとの残留滞留量である。入力は各バーストの量、回復状態での発行下限、その後の計算間隔であり、プラットフォーム側の量として有効排出率と有効容量を使う。均一な繰り返しでは、周期は「発行下限＋間隔」と「バースト量÷排出率」の大きい方で決まり、発行時間も同様の式で表せる。回復に必要な最小間隔はこの式から直接出る。非均一な実行では、周期ごとに「その周期に排出できる量に対する到着量の比」である正規化圧力を計算し、滞留の変化をバイト数で積み上げる。圧力が毎周期1以下なら滞留は増えず、1を超える周期があっても後の軽い周期で回復できることを、漸化式が履歴として表す。

容量の検査は別に必要である。単独バーストの滞留の増分は、発行中に排出される分を差し引いて計算し、既存の滞留との合計が有効容量を超える場合は、そのバーストは下限の発行時間では収まらず、背圧の始まりとして検出される。実測系での較正値は、排出率が約717GB毎秒、発行者が148並行のとき単独バーストの折れ点が1発行者あたり約33KiB、発行下限約0.76マイクロ秒から容量約4.25MiBである。3量はそれぞれ、間隔ゼロの傾き、大きな間隔での平坦部、単独バーストの折れ点という互いに重ならない実験領域から決めるため、応用に合わせた再調整なしに予測へ使える。モデルの限界として、これは集約した流れの近似であり、特定のハードウェアの待ち行列の主張ではない。発行者の並びが周期内で大きく変わる場合は、より細かい到着の記録が要る。

### 3. 適用の判断 — 到着の整形と自然な窓の利用

この機構への入力は、カーネルのバースト列と計算間隔をモデルへ写した結果、すなわち周期ごとの圧力、滞留の変化、容量検査の成否である。判断は2つに分かれる。滞留が溜まり続ける場合は、依存関係上実行可能な独立した計算をバーストの間に割り込ませ、排出の時間を作る。これは通信量も計算量も変えず、順序だけを変える操作である。既存の計算間隔が回復に必要な間隔を上回る場合は、発行後にその計算へ戻るだけでよく、到着を変える必要はない。

もう1つの判断は、予測した発行の遅れが計算側へ届くかどうかである。発行者と計算側の間には局所の蓄積バッファがあり、遅れがバッファの再利用時点までに消えれば計算は止まらない。バッファの段数を増やせば伝播は遅らせられるが、持続的な速度の不一致は最終的に余裕を使い切るため、根本の対処にはならない。失敗時の挙動として、平均の圧力が1以下でも、局所的な並びで滞留が容量へ近づく場合があり、平均だけで判断せず周期ごとの漸化式と容量検査を通すことが求められる。逆に、計算間隔がもともと長いカーネルでは、整形をしても利得が出ないことが予測でき、実際にそのような対照例では両方式とも停滞がほぼゼロで速度差も小さかった。

### 4. 専門並列への適用 — MegaMoEのタイル順序を組み替える

専門並列のMegaMoEでは、専門家のグループごとに第1の線形計算をまとめて行い、その後第2の線形計算のタイルが続く元の順序だと、第2の計算の後処理が相手先への書き込みを短い間隔で集中して発行する。個々のバーストは容量検査を通るが、間隔が短く圧力が1を超える周期が続くため、滞留が容量へ近づく。提案する割り込み方式は、実行可能になった第1の線形計算のタイルを第2のタイルの間に移し、有用な計算で排出窓を作る。通信量、経路、依存関係は変えない。

実測では、偏った経路分布での発行区間の中央値が元の7.9〜9.9マイクロ秒から3.6〜3.9マイクロ秒へ狭まり、局所メモリへの対照と0.5マイクロ秒以内で一致した。計算側の停滞についても、モデル予測と独立した測定が、元の方式で0.65〜4.31マイクロ秒の停滞を、割り込み方式で最大0.05マイクロ秒へ消えることを一致して示した。失敗条件も明確で、経路が均一な構成では通信側の利得が小さく、専門家をまたぐ割り込みで重みの局所性が落ちて約0.94倍へ逆転する構成があった。したがって整形は、圧力の予測と作業集合の大きさの両方を見て選ぶべきものと結論されている。

### 5. 系列並列とテンソル並列への適用 — 既存の計算窓を使う

系列並列では、注意の後の全対全通信を注意カーネルへ融合する。出力タイルが完成するたびに書き込みのバーストが出るが、次の出力までの間にはキーと値のタイルを巡回する計算があり、これが自然な排出窓になる。出力タイルの大きさが固定なら、系列長が伸びるほど窓は広がり、バーストあたりのバイト数は増えない。容量検査でも、全発行者が揃った最悪の場合の単独バーストの増分は約4.1MiBで容量約4.25MiBの内側に収まり、回復に必要な間隔約6.0マイクロ秒に対して実測の窓は最小の系列長でも約80マイクロ秒あった。

テンソル並列では、行列積と全削減の融合について、塊の切り方をモデルで監査する使い方が中心であり、性能結果そのものは報告されるが、滞留の推移の詳細な検証は専門並列と系列並列の機構測定が担う。追加の実験として、射影の行列積と全対全の融合でも2.14〜2.29倍の高速化が報告されているが、これは重なりに加えて前段の並べ替え処理そのものが消える効果を含むため、純粋な重なりの利得とは分けて読む必要がある。

## 評価

### まず見るところ

- **結論:** 発行後の区間は有限で回復可能であり、その予測はスケジュールの良し悪しを実際に言い当てる。利得は並列方式をまたいで現れるが、機構の検証が厚いのは専門並列と系列並列である。
- **速度・効率:** 専門並列の融合カーネルで幾何平均1.18倍・最大1.62倍、テンソル並列の融合で1.59〜1.75倍、系列並列の送信側で最大1.43倍。測定の境界が方式ごとに違うため、倍率同士を単純に比べないこと。
- **品質:** 計算結果を変えない研究であり、品質の論点はない。その代わり、正しさの仕組み（順序付けや信号）はモデルの対象外で別途必要だと明確にされている。
- **評価の強さ／注意点:** 8GPUの単一プラットフォームでの実測であり、較正量の移植には再検証が要る。テンソル並列については機構の検証ではなく性能報告が中心である。

## 既存研究との差

従来の融合方式は、発行の役割分担、発行時点、相手が使える時点の表現には長けるが、発行後の送信側の状態を持たなかった。X-Stageはその欠けた部分を、較正可能な3量で補うものであり、既存の融合の枠組みと競合するというより、その上にスケジュール判断の基準を足す位置づけである。到着率や平均占有で総量を扱う古典的な性能モデルとも、対象が「カーネル内部の送信側の回復と有限容量」である点で異なる。専門家の通信を減らす配置や負荷分散の研究は通信量そのものを変えるが、本論文の整形は量を変えず到着過程だけを変える。注意の融合についても、注意カーネル自体の改良ではなく、その出力境界に付く通信の排出窓として計算間隔を読む点が新しい。

## 限界・実装状況

- 較正量はプラットフォームと遠隔書き込み経路と発行者構成に依存し、移植には再測定が要る。
- モデルは集約した流れの近似であり、周期内での発行者の並びの変動が大きい場合は細かい到着記録が要る。
- 予測は送信側の進みについてであり、相手の受け取り準備や正しさの同期は別途必要で、通信が次の計算の入力になる融合では受信側の準備と組み合わせて判断する必要がある。
- 整形は経路が均一な構成では重みの局所性を損ねて逆効果になる場合があり、常時有効な変換ではない。
- 実装は著者による評価用の改変であり、汎用基盤へ組み込まれた形ではない。論文中に公式コードの公開先は示されていない。

## 一般的な実装上の含意

通信と計算の重なりを設計するときは、総量の釣り合いだけでなく、到着の時間分布を見るべきである。同じ総量でも、短い間隔に集中すれば有限のバッファや下流の余裕を使い切り、計算側へ停滞が伝わる。逆に、既存の計算の中に十分な排出窓があるかを測れば、追加の仕組みなしに重ねられる場所が見つかる。実務的には、発行後の余裕を「排出率・発行下限・容量」のような較正可能な量として持ち、スケジュール変更の前に滞留の漸化式で監査する手順が、他の融合パターンにも転用できる。局所バッファを増やす対策は伝播を遅らせるだけで、持続的な速度不一致は解消しない点も一般的な注意点である。
