# FluidGPU（旧Tessera）：異種GPUへカーネル単位で推論を分離する

## 概要

本論文は、性能と価格の異なるGPUが混在するクラスタで、**モデルのフェーズやTransformerブロックより細かいCUDAカーネル単位**に処理を配置する推論実行基盤を提案する。worklistにある旧名称は「Tessera: Unlocking Heterogeneous GPUs through Kernel-Granularity Disaggregation」だが、2026年9月19日のarXiv v3公式PDFの表題・本文では **FluidGPU: Fine-Grained Kernel Disaggregation for Large Model Inference on Heterogeneous GPUs** と改称されている。識別子は同一のarXiv:2604.10180であり、別論文として二重登録してはいけない。最新版を一次資料として採用する。

FluidGPUの要点は、GPU Aで速い演算とGPU Bで速い演算が、同じprefill・decode・attention・FFNの内部に混在することにある。従来のprefill/decode分離（PD）やattention/FFN分離（AF）では、単位内のカーネルをまとめて移すため、この違いを利用できない。著者らはカーネルの読書き領域と依存関係をPTXレベルで特定し、異種GPUごとの実行時間、データ転送量、通信遅延を組み込んだ配置を生成する。実行時は通信と他要求の計算を重ね、負荷によって低遅延型と高処理量型の配置を切り替える。

LLM、状態空間モデル、視覚言語モデル、画像生成モデルを含む実機評価では、適用可能なPD分離比でオフライン処理量が平均1.5倍・最大2.3倍、AF分離比で平均1.35倍・最大1.7倍になった。価格を含む処理量/ドルでもPD比最大1.6倍を報告する。ただしこれは実験したGPU組合せと料金モデルでの値であり、任意の異種GPUに普遍的な倍率ではない。

## 問題設定

### GPU世代とカーネルの性能順序は一致しない

データセンターにはA100、H100、L40s、RTX Pro 6000などが共存する。GPUの総合性能を単一の順位で表しても、個々のカーネルの適性は分からない。たとえばメモリ帯域に律速される行列ベクトル積ではA100のHBM帯域がL40sより大きく、論文の測定では約1.9倍速い。他方、同じモデル中のFlashAttentionではキャッシュ容量や演算器特性が効き、L40sが最大約2.1倍速い条件がある。A100とL40sの実測で、個数としては平均67%のカーネルがL40sで速いが、A100側の総実行時間に占めるそれらの割合は平均36%であり、単純なカーネル数の多数決も最適配置を与えない。

GPT-oss 20Bの解析では、prefill内の45%、decode内の57%のカーネルがL40sの方で速い。attentionブロック内では71%、FFN内では33%がL40s有利だった。したがって「prefillはGPU A、decodeはGPU B」あるいは「attentionはA、FFNはB」といった一括割当では、同一領域内の相反する適性を吸収できない。カーネル単位の配置は細かくなるほど転送と同期が増えるため、**カーネル単体の最速GPUを選ぶだけでは不十分**である。

### 正しさと通信の両立

元の単一GPU実行では、前段カーネルの出力が後段カーネルから同じアドレス空間で参照される。複数GPUへ分けると、読取り前に適切なバイト範囲を転送しなければ古い値を読む。特にPyTorchやJIT生成カーネルではCUDA API引数だけから正確なアクセス領域を推定できず、誤った依存関係は数値的な破損を招く。逆に全バッファを毎回転送すると通信費で利益を失う。この正しさ・転送量・待機時間の三者を同時に扱うことが研究課題である。

## 手法

### 1. PTX計装によるメモリ範囲と依存グラフの抽出

最初に実行をプロファイルし、GPUごとの各カーネル実行時間を測る。cuBLASなど既知のライブラリ演算ではAPIの意味から入力・出力バッファを特定できる。ユーザー定義・JIT生成など不透明なカーネルでは、PTXのメモリ命令へ計装を挿入し、実際にアクセスされたアドレス範囲の最小・最大を記録する。これにより、単に引数が同じという推測ではなく、書き込み後に別カーネルが同じ領域を読むRAW依存を抽出できる。

解析結果は有向依存グラフ（DDG）となり、ノードがカーネル、辺がデータ依存と必要な転送バイト範囲を表す。異なる反復間で参照されるKVキャッシュも、複数反復のプロファイルで書き込みと次反復の読取りを検出する。形状やCUDA Graphが異なる場合はパターンごとにDDGを準備して再利用する。データ依存分岐のうち未計測またはCUDA Graph化不能な経路は、危険な推測配置をせず単一GPUへ退避する。つまり完全に任意の動的プログラムを無条件に分割できる方式ではない。

### 2. 目的別MILPによる配置計画

各カーネルkをGPU gへ置く二値変数x(k,g)を定義し、各カーネルを必ず1台へ割り当てる。GPUごとの計算時間T(g)は、割り当てたカーネルの実測時間の総和。依存辺が異なるGPUを跨ぐ場合には、転送バイト数d、GPU間帯域bw、基礎遅延lから概ねl+d/bwの転送費を計算し、GPUごとの通信時間M(g)に集計する。辺が跨ぐかどうかを表す変数の積は線形化して混合整数線形計画へ落とす。

オフラインの大量要求では、パイプラインが十分に埋まると計算と通信を重ねられるため、GPU gの段階時間をW(g)=max(T(g),M(g))とみなし、全GPUの最大段階時間を最小化する。低負荷のオンライン要求では同時要求が足りず通信を隠し切れないため、計算時間と依存辺の転送時間の和を最小化する遅延指向の配置を使う。**同じ配置を全負荷へ押し付けず、低負荷では転送を減らす**点が重要である。

代表例のGPT-oss 20B・A100+L40sでは1つのDDGに約500カーネル、Gurobiによる1 DDGの最適化は約20ms、実行パターン全体の配置生成は約5秒だった。これらは事前計算であり、各リクエストの生成時に毎回MILPを解くわけではない。GPU数とカーネル数が増えると計画コストは上昇するが、同形状の層・実行パターンを再利用する。

### 3. GPUワーカーと依存局所の非同期転送

各GPUにワーカーを配置し、DDGの割当カーネルだけを実行する。別GPUからデータを受け取る辺では受信処理を対象カーネルより先に登録し、実行後に送信を登録する。GPU起点のNCCL/InfiniBand GPUDirect Asyncを使ってCPU側の細かな同期を避け、計算用と通信用のCUDAストリームを分離する。CUDAイベントによって直接の依存辺だけを待つため、無関係なカーネルは転送と並走できる。

CUDA GraphをGPUごとの部分グラフへ分割し、転送・イベントノードを挿入してキャッシュする。各ワーカーは個々のカーネルをCPUから逐次起動するのではなく、部分グラフをまとめて再生する。GPU間をまたぐ辺が多すぎる場合は通信費が支配的になるため、配置計画がその費用を含めて分割の採否を判断する。

### 4. 要求間パイプラインと優先度

単一要求では前段GPUから後段GPUへの転送中に計算器が遊ぶ。複数要求を並行実行し、ある要求がデータを待つ間に別要求の準備済みカーネルを走らせる。単に同時要求を増やすだけでは全要求が同じ進捗で通信待ちに入る場合があるため、到着順にCUDAストリームの相対優先度を付け、早い要求を先行させて通信フェーズをずらす。完了した要求のストリーム・優先度枠は再利用する。

KVキャッシュについては、各GPUに複製を維持し、毎回全量を送らず、vLLMのページ表とスロット情報から新規トークンのK/V差分だけを非同期転送する。次反復でその範囲を読む前には転送完了イベントを待つ。論文の測定ではこの差分同期の追加遅延は全デコード遅延の0.1%未満だった。これはKV全量を毎回同期する方式の測定値ではない。

### 5. オンライン監視と既存並列化との合成

オンライン監視器は要求遅延、カーネル群の遅延、通信時間、待ち行列圧力を収集し、負荷に応じて低遅延方針と高処理量方針を切り替える。方針切替にはGPUワーカーを反復境界で同期する必要があり、実測で約30msの停止が生じるため、観測窓Wと閾値βの選択が重要になる。論文の既定はW=300ms、β=1.5である。

テンソル並列や専門家並列の集合通信を勝手に分割するのではなく、既存のTP/EP/SP等の通信区間の間にある計算カーネルへ配置を適用する。Qwen3 235Bの8 B200+8 H100評価では、B200/H100を組にして各TPランク内でカーネルを分離する。入力依存のMoE経路については、未観測の専門家経路を元の配置へ戻す制約がある。

## 評価

### 実験環境と比較対象

主な異種GPU組合せはA100+L40s、H100+RTX Pro 6000、B200+H100で、それぞれ200Gbps RDMA NICを備える。大規模構成は2 A100+1 L40s、および8 B200+8 H100の最大16GPU。推論基盤はvLLM v0.18.0、通信はNCCL。比較対象はprefill/decode分離（DistServe系）、attention/FFN分離（MegaScale-Infer系）、独立GPUへ要求を割り振る方式、および単独GPUの同種比較である。ベースラインはGPU構成ごとに調整している。

モデルはLlama-3 8B、GPT-oss 20B、Mamba-Codestral 7B、Qwen2.5-VL 7B、Stable Diffusion 3.5。LLM/SSMにはSplitwise会話負荷（入力中央値1020トークン、出力中央値129トークン）、MLLMにはCOCOの512×512画像、画像生成にはPartiPromptsの1024×1024・28段階ノイズ除去を用いた。オフラインは最大持続処理量、オンラインはGPT-oss 20BのPoisson到着とAzure会話トレースを測定する。LLM・SSM・MLLMの処理量単位は出力tokens/s、画像生成はimages/minであり混ぜて平均する際は注意が必要である。

### オフライン処理量とコスト

| 比較・条件 | 指標 | FluidGPUの結果 | 解釈 |
|---|---|---|---|
| PD分離比・適用可能な構成 | 最大持続処理量 | 平均1.5倍、最大2.3倍 | フェーズ内のGPU適性差を利用 |
| AF分離比・適用可能な構成 | 最大持続処理量 | 平均1.35倍、最大1.7倍 | ブロック内のGPU適性差を利用 |
| GPT-oss 20B・A100+L40s | 出力tokens/s | 要求分配2052、FluidGPU2641 | 同じ2GPUを使って約28.7%改善 |
| PD分離比・GPU賃料を考慮 | 処理量/ドル | 平均1.5倍、最大1.6倍 | 料金仮定を含む改善 |
| H100+RTX Pro 6000対単独H100 | 平均処理量 | 約2.3倍 | 異種2台対高性能1台の比較 |
| 同組合せ・単独H100基準 | 処理量/ドル | 1.64倍 | 2台H100より賃料29.3%低いとの前提 |

PD分離は画像生成には適用不能、AF分離はMambaや画像生成に適用不能であり、欠損値をゼロとして比較していない。H100+RTX Pro 6000の「2.3倍」は**単独H100比の処理量**であり、論文冒頭の「既存分離比最大2.3倍」と比較対象が異なる。料金効率の1.64倍とも混同しない。

### オンライン遅延、スケール、要素除去

GPT-oss 20Bのオンライン評価では、50ms/tokenのSLOを満たせる要求到着率が最良ベースラインより最大1.3倍高い。A100+L40s、16req/sのP99では、PD分離のTTFTがFluidGPU比1.28倍、TPOTが1.11倍、AF分離ではTTFTが1.20倍、TPOTが1.26倍であった。これはtail latencyの比較であり、オフライン処理量の倍率とは別である。

大規模クラスタのGPT-oss 20B（2 A100+L40s）とQwen3 235B（8 B200+8 H100）では、PD分離比1.5倍、AF分離比1.4倍のオフライン処理量を報告する。既存のTP構成を保ったまま各ランクの計算を細分化できることを示すが、すべての並列通信が自由に再配置可能になったわけではない。

パイプラインの要素除去では、GPT-oss 20B・A100+L40sの処理量がパイプラインなし1443、優先度なし2123、優先度あり2641 tokens/sとなる。通信を無視した理想値2734 tokens/sに対し、優先度ありは96.6%へ到達する。通信待ちの割合はほぼ50%から4%未満へ減少し、単なるGPU配置変更ではなく**要求間パイプラインが通信を隠す**ことが測定上確認される。

200→25Gbpsへ帯域を制限しても、オフラインの処理量は2641→2490 tokens/sで6%未満の減少にとどまる。ただし低負荷のオンラインでは通信を隠せないため、転送を減らす配置へ切り替える。方針切替が頻繁すぎる場合は遅延最大1.32倍、切替が遅すぎる場合は最大1.55倍の悪化があり、適応機構そのものにも調整費用がある。

## 限界と負の結果

第一に、現行のMILPはGPUごとのメモリ容量制約を明示的に含まず、初期化時に全モデル重みを各GPUへ複製する。したがって異種GPUの片側にモデル全体が収まらない場合の自動分割・オフロード解決策ではない。使わない重みの回収は固定方針のオフライン負荷では可能と論じるが、実装上の制約を解消した一般的な容量最適化ではない。

第二に、カーネル実行経路のプロファイルとCUDA Graphの再生可能性が前提である。未観測の入力依存経路、再生不能な経路、専門家の新しいルーティングは元のGPU配置へ退避する。PTX計装の事前処理は10秒以内と測定されるが、GPU別カーネルプロファイルの費用を含まず、全構成の完全な探索費用と同義ではない。多様な形状・GPU組合せを頻繁に追加する運用では事前準備の管理が増える。

第三に、細分化により転送辺が増える。高負荷時は要求間で隠せても、低負荷・高通信遅延では通信が要求の臨界経路へ入る。著者らはそのために遅延指向配置を設け、最悪時には単独GPUへ戻す。ネットワーク帯域低下で6%未満という結果は、測定したA100+L40sとGPT-oss 20Bのオフライン条件に限定される。

第四に、実測のGPU、モデル、入力分布、賃料の範囲外へ倍率を一般化できない。例えば安価なGPUが必ずしもどのカーネルでも速いわけではなく、最適化の利益はGPU間の性能の相補性、通信費、並列要求数に依存する。評価は実機の処理量・遅延を示すが、他クラスタでの運用費全体、障害時の可用性、長期運用のコストまで実証したものではない。

## 既存研究との差と位置付け

DistServe/SplitwiseのPD分離はprefillとdecodeを異なる資源へ配置する。MegaScale-InferのAF分離はattentionとFFNを分ける。これらはTransformerの構造に基づくため、MambaやStable Diffusionへそのまま適用できない場合がある。FluidGPUはモデルの意味上の層・フェーズに依存せず、実際のカーネルとRAW依存を単位とする。分離粒度を細かくするだけでなく、通信費を最適化へ入れ、優先度付き要求間パイプラインと負荷連動切替で細分化の副作用を抑える点が貢献である。

本研究をKVキャッシュ圧縮やモデル量子化の研究と同一視すべきではない。モデルのパラメータ表現や注意計算式を変えるのでなく、既存モデルの**どの演算をどのGPUで実行するか**を最適化するシステム研究である。量子化済みモデルや他の推論最適化と理論上は補完関係にあるが、任意の組合せについて実測済みとは限らない。
