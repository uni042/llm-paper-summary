# 動的タスクグラフでLLMエージェント群の競合と無駄な推論を削減するLATTE

## 概要

複数の大規模言語モデル（LLM）を役割分担して実行するエージェントシステムでは、同じ作業の重複、ファイルの競合更新、長い通信、担当者の待機が発生しやすい。固定のパイプラインや中央の指揮者が全てを割り当てる方式は一貫性を保ちやすい反面、実行中に新しい依存関係が見つかっても構造を変更しにくい。各エージェントに自由な協調を任せる方式は柔軟だが、共有状態の認識がずれ、同じファイルを上書きしたり、未完成の作業を完了と誤認したりする。本論文はこの二者択一を避け、エージェント自身が実行中に共有タスクグラフを更新するLATTE（Language Agent Teams for Task Evolution）を提案する。

LATTEはタスクを有向非巡回グラフ（DAG）の節として管理し、節間の依存関係、担当者、進捗状態を明示する。Workerは自分の局所作業から新しいタスクを発見し、完了や作業取得を提案できる。Leadは全体に影響する変更を承認し、停止したWorkerの再割当や高リスク作業の検証を行う。依存関係を満たした作業だけを並列実行し、共有グラフの更新を直列化することで、柔軟な探索と状態の一貫性を両立させる。

実験は探索的データ分析、コードのデバッグ、Pythonライブラリ拡張の三種類で、Claude Sonnet 4.6とGPT-5.2を使った5エージェント構成を比較する。LATTEの成功試行集計は平均148,000トークン、3.5分、成功率約80%で、固定グラフ方式の297,000トークン、6.0分、58%より効率と成功率が高い。特に共有ファイルの上書き、同時書き込み、破棄される出力文字数を減らしている。

本研究はLLMの重み演算、量子化、KVキャッシュを直接高速化するものではない。**エージェントの不要な推論呼び出し、過剰な文脈、通信、失敗による再実行を減らすシステム層の効率化**である。したがってGPUカーネル研究と同じ指標で比較せず、タスク当たりの成功率、消費トークン、完了時間、競合を合わせて評価する必要がある。

## 問題設定と設計原理

### 固定的な分担と無秩序な分散の限界

固定パイプラインは、開始前に工程が分かる作業に適している。しかし探索的分析やデバッグでは、調査を進めるまで新しい問題が分からない。最初の計画だけで全作業を割り当てると、想定外の依存関係を発見したWorkerが待たされたり、既に不要になった作業を続けたりする。中央集権的なLead-Worker方式では、Leadが全ての作業割当と結果の統合を行うため、Lead自身の処理能力がボトルネックになりやすい。

一方、分散型の自由なエージェント群は、各自の局所状態だけを頼りに動くため、別のWorkerが変更したファイルや前提条件を知らずに処理を進める場合がある。重複した調査、同じ関数への同時書き込み、古い状態を前提にした修正は、追加トークンだけでなく成果物の破損や再作業を招く。LLMの推論費用を減らすには、モデル呼び出し単価だけでなく、**正しい完成物を得るまでの総作業量**を減らす必要がある。

### 設計上の四要件

著者らは、局所的な探索と全体の一貫性を両立する混合型協調、作業可能な節の数に応じた適応的なWorker起動、停止・誤りの検出と再割当、各エージェントに必要な範囲だけを渡す文脈制限を要件に置く。特にLeadへ全Workerの長い実行履歴を渡すのではなく、Leadはグラフと要約された通信を見て全体の状態を把握する。Workerは担当タスクと直接の前提だけを受け取り、不要な長文脈を処理しない。

## 手法

### 1. 進化するタスク依存グラフ

時点`t`のグラフを`G_t=(V_t,E_t,λ_t)`と表す。`V_t`はサブタスク、`E_t`は先行関係、`λ_t`は各タスクの担当エージェントと状態の対応である。状態には未着手、割当済み、実行中、完了、検証済みがある。辺`(u,v)`がある場合、`u`が終わるまで`v`を開始できない。グラフは循環を持たないよう維持され、依存関係のないタスクは並列に進められる。

未着手で全ての先行タスクが完了した節の集合を、実行可能な前線（frontier）`F_t`とする。各ラウンドではこの前線にある節だけを新たに取得できる。Worker数を`|W|`とすれば、同時に起動するWorker数は最大で`min(|F_t|,|W|)`となる。先行タスクが残っている節を先走って実行しないため、並列性を利用しつつ無駄な投機的作業を抑える。

### 2. 七つのグラフ更新操作

| 操作 | 主な呼出者 | 意味 |
|---|---|---|
| Discover | LeadまたはWorker | 新しいサブタスクと依存関係を追加 |
| Assign | Lead | 未割当のタスクをWorkerへ割り当てる |
| Claim | Worker | 実行可能なタスクを自発的に取得 |
| Complete | Worker | 自分のタスクの終了を報告 |
| Release | Lead | 停止した作業を未着手へ戻して再割当可能にする |
| Close | Lead | 全体判断でタスクを強制的に閉じる |
| Verify | Lead | 不確実なタスクの検証を追加する |

各操作には前提条件と事後条件があり、グラフが循環しないことや、担当外の作業を誤って完了しないことを確認する。Workerは局所情報からDiscoverやCompleteを提案できるが、全体へ影響するRelease、Close、VerifyはLeadが制御する。Claimでは空いているWorkerが前線の仕事を自分から取得できるため、Leadによる全件の割当待ちを避ける。同じ節への同時Claimは制御器が直列化して競合を解決する。

### 3. LeadとWorkerの役割を分ける

Leadはタスクの全体像とグラフ状態を管理し、依存関係が満たされるか、再割当が必要か、検証を追加すべきかを判断する。Workerは自分の担当節を処理し、途中で見つけた作業をDiscoverで追加する。グラフ更新の提案と承認を分けることで、局所的な柔軟性と全体の整合性を両立する。これは分散システムの作業窃取やタスクグラフ実行の考え方をLLMエージェントへ移したものと解釈できる。

実行ループでは、まず応答が止まったWorkerを心拍で監視し、実行可能な前線を計算し、作業中・新規割当・必要なLeadを選んで並列実行する。各ラウンドの終了時にグラフを更新し、完了した節と新しく発見した節を反映する。停止したWorkerの節はReleaseで再び取得可能にできる。必要ならLeadがVerifyを呼び、全件を一律に再検査するのではなく、誤りの危険が高い節を選んで監査する。

### 4. 文脈の制限と監査可能性

Workerへ渡す文脈は、担当節の説明と直接の先行タスクの成果に制限する。Leadへはグラフとエージェント間の通信を渡すが、各Workerの全実行履歴を連結しない。この制限は、入力トークン数の削減と、無関係な情報による推論の混乱を減らすことを狙う。グラフの節と状態が構造化されているため、どのWorkerが何を担当し、どの依存関係を解消したかを追跡できる。これは自由な会話ログだけに依存するエージェント構成より、失敗の原因や作業の重複を監査しやすい。

## 評価条件

| 項目 | 内容 |

| タスク | 探索的データ分析、信号処理ライブラリのデバッグ、Python文字列処理ライブラリ拡張 |
| チーム | Leadを含む5エージェント |
| 基盤モデル | Claude Sonnet 4.6、GPT-5.2 |
| 比較方式 | LATTE、Lead-Worker、分散型、固定グラフ、MetaGPT |

データ分析では隠されたデータの特徴を見つけ、デバッグではテストを通過するよう既存の信号処理コードを修正し、ライブラリ拡張では既存クラス2つと新規モジュール6つを完成させる。三つのタスクは、実行中に未知の依存関係が現れる場合と、最初から工程が分かる場合を比較するために選ばれている。チーム人数はMetaGPTとの比較を揃えるため5に固定され、エージェント数を増やした際のスケーリングは直接評価していない。

## 評価結果

### タスクの正しさ、消費トークン、完了時間

| 3タスク・2モデル集計 | LATTE | Lead-Worker | 分散型 | 固定グラフ | MetaGPT |
|---|---:|---:|---:|---:|---:|
| 成功率 | 80±4% | 70±5% | 74±4% | 58±5% | 34±7% |
| トークン数 | 148±14千 | 379±51千 | 419±47千 | 297±40千 | 397±59千 |
| 完了時間 | 3.5±0.3分 | 5.9±0.6分 | 3.7±0.3分 | 6.0±0.6分 | 11.5±1.2分 |

原著表2は成功した試行についての費用と時間を集計し、別途失敗を考慮した期待費用も示す。LATTEは固定グラフと比べてトークン数を約半分、完了時間を約4割短縮し、成功率を約22ポイント高める。Lead-Workerと比べてもトークン数が大幅に少なく、完了時間が短い。一方、分散型との完了時間差は3.5分対3.7分と小さく、著者の正規化分析でも有意差は報告されていない（p=0.34）。「全ての方式に対して時間が統計的に有意に短い」とは言えない。

正規化したトークン費用ではLATTEが47.5%、固定グラフが86.9%、Lead-Workerが104.2%、分散型が120.9%、MetaGPTが228.7%と報告される。これは表2の生トークン数とは異なる正規化・プール集計であり、47.5%を「全条件でトークンが47.5%になった」と解釈してはならない。成功率の集計もLATTE約79.7%、固定グラフ約57.6%、Lead-Worker約70.1%、分散型約73.9%、MetaGPT約33.9%で、LATTEと分散型の差はp=0.16で有意ではない。

### タスクごとの差と固定計画が有利な条件

データ分析ではLATTEの成功率96%、Lead-Worker94%、分散型93%、固定グラフ88%、MetaGPT75%だった。デバッグではLATTE100%、Lead-Worker90%、分散型100%、固定グラフ44%、MetaGPT32%で、未知のバグや依存関係が出る条件で固定計画が弱い。ライブラリ拡張ではLATTE40%、固定グラフ40%で同程度であり、最初から実装すべきモジュールが分かるタスクでは動的な再計画の品質上の利益が小さい。動的グラフが常に成功率を高めるわけではない。

タスク別の時間は、データ分析でLATTE3.2分対分散型2.9分、デバッグでLATTE5.3分対分散型6.1分、ライブラリ拡張でLATTE2.1分対分散型2.2分である。データ分析では分散型がわずかに速い。したがって速度の優位は作業の性質によって変わり、正しさと総トークンを同時に確認する必要がある。

### 競合、無駄な出力、通信の削減

| 協調指標（試行平均） | LATTE | Lead-Worker | 分散型 |
|---|---:|---:|---:|
| 既存作業の上書き回数 | 4.3 | 22.8 | 35.4 |
| 同じ関数への同時書き込み | 1.0 | 8.5 | 11.5 |
| 破棄された出力文字数 | 5,236 | 45,436 | 78,062 |
| エージェント間メッセージ数 | 20.4 | 31.4 | 34.8 |
| 送信文字数 | 42,484 | 50,073 | 60,394 |

LATTEはLead-Workerに比べ上書きを約5.3分の1、分散型に比べ約8.2分の1へ減らす。競合した同一関数への同時書き込みもLead-Workerの8.5回、分散型の11.5回に対して1.0回だった。破棄された出力は、最終成果物へ残らない文字列であり、無駄な推論と修復作業の代理指標である。実際のGPU消費電力を直接測った数値ではないが、同じタスクを完成させるまでの不要なLLM生成を減らす効果を示す。

通信もLead-Worker31.4通、分散型34.8通に対してLATTE20.4通である。全Workerが毎ラウンド稼働する分散型と異なり、LATTEではエージェントが実際に動いたラウンドの割合は48.7%で、Lead-Workerの約80%より低い。仕事がないときにエージェントを起動しないことが、トークン削減と待機計算削減につながる。

### 停止したWorkerの再割当と末尾遅延

LATTEでは36%の試行でReleaseが呼ばれ、停止した作業の再割当が行われた。19%の試行でVerifyが呼ばれ、Leadが不確実な節を選んで追加検証した。検証を伴う難しい試行は平均18.1ラウンド、検証なしで成功した試行は平均8.1ラウンドだった。これは検証を行うと必ず遅くなるという因果関係ではなく、難しい作業で選択的に検証が呼ばれるという観測である。

タスク節の平均完了時間はLATTE39.2秒、固定グラフ75.6秒で、95百分位は130秒対294秒だった。停止したWorkerを放置せず、依存関係が満たされた仕事を他のWorkerへ回せることが、遅いタスクによる全体の足止めを軽減する。これは推論エンジンのトークン間遅延ではなく、エージェントのサブタスク単位の完了時間である。

## 既存研究との差

MetaGPTやChatDevは事前に役割と工程を決める。Lead-Worker方式は中央のLeadへ割当と統合が集中する。自由な分散型は適応しやすいが、共有状態の競合が増える。LATTEはグラフの前線を使って実行可能な仕事を明示し、Workerが局所的に新しい節を発見しつつ、Leadが全体整合性に関わる操作を直列化する。分散システムの動的タスクグラフ、作業窃取、心拍監視、再割当の考え方をLLMエージェントの推論呼び出し管理へ適用した点が特徴である。

推論システムの観点では、モデル1回の前向き計算を高速化するのではなく、**必要な推論呼び出し回数と文脈の大きさを減らす**。同じGPU上でのモデル処理能力が不変でも、重複生成や競合修復が減ればタスク当たりの総トークンと完了時間を下げられる。この効果はGPUカーネルの最適化、量子化、KVキャッシュの改善と併用可能だが、原著はその組合せによる速度倍率を測定していない。

## 限界と適用条件

第一に、LATTEは開始時のグラフ作成と継続的な更新の費用を要する。単純で短い作業や単一エージェントで十分なタスクでは、この計画費用が節約量を上回る可能性がある。固定グラフが最初から適切なライブラリ拡張では成功率がLATTEと同じ40%であり、常に動的協調が必要というわけではない。

第二に、実験はデータ分析、デバッグ、ライブラリ拡張という、サブタスクへ分割しやすい作業に限られる。曖昧で分割境界が不明な自由形式の推論、実世界の外部状態を伴う操作、長期間にわたるタスクなどへの汎化は未確認である。チーム人数も5体に固定され、10体、100体と増やした場合の通信・競合・Leadの負荷は直接評価していない。

第三に、成功判定には各タスクの非公開テストが使われ、モデルはClaude Sonnet 4.6とGPT-5.2の二種類である。タスクとモデルの選択が変われば成功率やトークン量の順位が変わる可能性がある。300試行は比較に有用だが、複雑な長期業務の低頻度障害を評価するには十分とは限らない。

第四に、Leadが共有グラフの更新を直列化するため、極端に多数のWorkerが同時にタスクを発見する場合はLeadが新しいボトルネックになり得る。原著は5エージェント構成で競合を減らしたが、大規模分散環境の一貫性保証や故障復旧を完全に実証したわけではない。タスク完了の報告を誤るWorkerや、Lead自身が誤判断する場合の検証設計も引き続き重要である。

第五に、トークン削減はLLMサービスの請求額を減らす方向に働くが、GPUを固定時間で借りる自前サービングでは利用率、待ち行列、モデルの共有状況によって金額換算が変わる。原著の3.5分対6.0分はエージェントチームの作業完了時間であり、GPUカーネルの1.7倍高速化を示すものではない。費用評価ではタスク成功率を揃えた上で、総生成トークン、呼び出し数、待ち時間、再試行費用を確認する必要がある。
