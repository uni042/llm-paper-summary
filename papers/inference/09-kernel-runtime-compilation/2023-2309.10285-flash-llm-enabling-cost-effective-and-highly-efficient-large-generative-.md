# Flash-LLM: Enabling Cost-Effective and Highly-Efficient Large Generative Model Inference with Unstructured Sparsity

## 概要

Flash-LLMは、非構造枝刈りを施した大規模生成モデルの重みをGPUへ効率的に読み込むため、疎行列として転送し、GPU内部で密行列に戻してから行列演算器で計算する推論カーネルである。通常の疎行列積はゼロ要素の乗算を省くことに注目するが、現代のGPUでは高性能なTensor Coreが密な固定形状の行列積を得意とするため、任意の位置にゼロがある疎行列を直接扱うのが難しい。そこで「ゼロの計算を省く」よりも「ゼロの重みを外部メモリから読まない」ことを優先する。

この逆転が有効になる理由は、自己回帰生成時の線形演算が細長い行列積となり、演算器より高帯域幅メモリからの重み読込が先に律速になるためである。著者らはOPT-66Bの生成で、バッチ8、16、32、64に対するTensor Core利用率が約5.0%、10.1%、19.9%、39.7%にとどまる一方、外部メモリ帯域は飽和していると報告した。演算器に余力があるなら、疎データを共有メモリへ復元してゼロを含む密行列積を実行しても、外部メモリ転送を減らした利得が上回り得る。

Flash-LLMはタイル化したCSL疎形式、レジスタと共有メモリを使う復元処理、二段階のデータ転送・演算重畳、事前の疎データ並べ替えを組み合わせる。著者らはA100でOPT-30B、OPT-66B、OPT-175Bを対象に評価し、疎行列積の単体ではSputnik比平均2.9倍、SparTA比平均1.5倍、モデル全体のトークン毎GPU秒ではDeepSpeed比最大3.8倍、FasterTransformer比最大3.6倍の改善を報告した。ただしこれは枝刈り済みモデルの評価であり、密な元モデルを無損失に高速化する手法ではない。

## 問題設定

### 自己回帰生成の重み帯域律速

入力文をまとめて処理する事前充填では、行列の両方向に多数のトークンがあり、密行列積の演算器を使い切りやすい。一方、トークン生成段階では一反復で各要求から新たに処理するトークンが一つ程度なので、重み行列の大きさに比べてバッチ方向が極端に短い。著者らは重み行列を `M×K`、活性値を `K×N` とし、`N` がバッチ数程度である細長い行列積に注目する。

OPT-66Bのプロファイルでは、問い合わせ・鍵・値の射影、出力射影、全結合層の二つの行列積という主要な四種類の演算が、推論時間の76.8%とメモリ使用量の83.8%を占める。半精度の密行列積における演算強度は、近似的に `M×N/(M+N)` となり、`N` が小さい場合は `M` を増やしても上限が低い。例えば `N=16` なら演算強度は16付近を超えにくい。GPUの演算性能が高くても、巨大な重みを毎反復読み込む費用が支配的となる。

### 非構造枝刈りとGPU演算器の不整合

非構造枝刈りは、重み行列の任意の位置をゼロにできるため、ブロック単位などの構造化枝刈りより精度を保ちやすい。論文はOPT-30Bの80%枝刈りで精度が85.55%から84.11%へ下がる例を挙げる。しかし疎位置を逐一検査してゼロ乗算を飛ばす従来カーネルは汎用CUDAコア中心となり、Tensor Coreの高いピーク性能を利用しにくい。疎であることだけでは密なcuBLASより速いとは限らない。

A100のTensor Coreは固定形状の密行列積を高速に処理できるが、任意のゼロ要素だけを命令単位で飛ばすことはできない。構造化2:4疎性を利用する方式は別の制約を持ち、任意位置を80〜90%削除した非構造疎性をそのまま表現できない。Flash-LLMはこの不整合を、GPU外部メモリと内部演算器で別々の表現を使うことで回避する。

## 手法

### 疎として読み込み密として計算する原理

Flash-LLMでは、非構造疎重み `A` と密な活性値 `B` の積を計算する。外部メモリには `A` の非ゼロ値とその位置情報だけを保存し、GPUブロックは対象タイルの疎データをレジスタへ読み込む。共有メモリ上でゼロを埋めた密タイルを作り、非ゼロ値を本来の位置へ配置する。完成した密タイルと活性値の密タイルをTensor Coreへ供給し、通常の密行列積として出力タイルを計算する。

ゼロ要素の乗算を再び実行するので、算術演算回数だけを数えれば非効率に見える。しかし生成時にはTensor Coreの演算能力が余り、外部メモリの重み読込が律速となる。疎性を `β` とすると、著者らの近似式では疎読込時の演算強度は `M×N/(M×(1−β)+N)` となり、密読込時より高くなる。大きな重み行列の転送量を減らし、余っている行列演算能力で復元後の冗長計算を吸収する設計である。

### タイル化CSL形式

重みをTensor Coreのタイル演算に合う単位へ分割し、各タイルの非ゼロ値と位置を連続して格納する。タイル化したCSL形式では、各タイルの疎データの開始位置と長さを示すオフセット情報、実際の非ゼロ値と位置情報を分けて保持する。これにより、任意の非構造疎性を維持しながら、タイルごとに必要な部分だけを外部メモリから読み込める。

タイルごとに非ゼロ数が違うため、次タイルの長さを知らないままではデータ読込を効率よく予約できない。実装はオフセット情報を先読みしてレジスタへ準備し、現在タイルの演算中に次の疎データの位置を決める。タイル境界の索引参照と不規則な読込が連続パイプラインを止めないようにすることが、単なる圧縮形式との違いである。

### レジスタから共有メモリへの復元

疎データを最初から共有メモリへ置くと、そこから非ゼロ値を読み直して密タイルへ書き込む余分な共有メモリ往復が発生する。Flash-LLMは各スレッドのレジスタを中間置き場として利用し、疎値と位置をレジスタへ受け取る。共有メモリ上の出力タイルをゼロ初期化し、各非ゼロ値を対応する位置へ散布する。復元後は密行列積向けの命令でTensor Coreへ供給できる。

この復元処理は疎位置に応じた不規則な共有メモリ書込を含み、バンク競合が生じる可能性がある。著者らは事前に疎データの順序を並べ替え、同じメモリバンクへ集中するアクセスを減らす。推論の毎反復で重い並べ替えを行うのではなく、重みを準備する段階で配置を調整しておくことが重要である。

### 二段階の重畳パイプライン

GPUブロックは現在の重みタイルをTensor Coreで計算する間、次のタイルの疎データを外部メモリからレジスタへ読み、別の共有メモリ領域に展開する。密な活性値タイルの読込も同時に進める。二重バッファを用い、転送、疎から密への復元、行列積が直列に並ばないようにする。非同期転送命令を利用して、演算器が外部メモリ読込完了を待つ時間を隠す。

この実装ではレジスタと共有メモリの使用量が大きくなり、同時実行できるブロック数が減り得る。したがって、すべての形状に同じパイプラインを適用すればよいわけではない。著者らは同期とメモリ障壁の範囲をできるだけ狭め、ブロック内の命令並列性を増やして少ないブロック数でも帯域待ちを隠すよう調整する。圧縮率だけでなく復元と転送の隠蔽が性能を左右する。

### 推論エンジンへの統合

提案カーネルはFasterTransformerへ統合され、モデルの線形層を非構造疎重みに対応させる。生成の鍵・値キャッシュや注意計算そのものを圧縮する方式ではなく、主に重み行列積の転送量を減らす。対象モデルの枝刈り率と精度を別途確認する必要があり、実行カーネルだけで元の密モデルと同じ出力が保証されるわけではない。

## 評価

### 評価条件

| 観点 | 論文の設定 | 読み方 |
|---|---|---|
| GPU | NVIDIA A100-SXM 80GBを備えるサーバ | 主にA100でカーネルとモデル全体を評価 |
| CPU・環境 | Xeon Platinum 8369B、Ubuntu 18.04、CUDA 11.8 | 特定世代の実装 |
| 対象モデル | OPT-30B、OPT-66B、OPT-175B | 重み規模による効果を比較 |
| 生成バッチ | 8、16、32、64 | 細長い行列積の律速が変わる |
| 疎性 | 70%、80%、90%など | 枝刈り品質と転送量の交換条件 |
| カーネル比較 | cuBLAS、cuSPARSE、Sputnik、SparTA | 疎行列積単体の比較 |
| 推論比較 | DeepSpeed、FasterTransformer | モデル全体のトークン毎GPU秒 |

### カーネル単体の速度

著者らの単体疎行列積評価では、Flash-LLMはSputnikに対し平均2.9倍、SparTAに対し平均1.5倍の速度を報告する。従来の汎用CUDAコア中心の疎演算より、疎データをTensor Coreへ効率的に供給できることが主要因である。非構造疎性の割合が高いほど外部メモリから読む重みが減るため、帯域律速の条件では利得が大きくなる。一方、枝刈り率が同じでもタイルごとの非ゼロ分布が異なると復元と索引読込の費用が変わり、すべての疎行列で同一倍率にはならない。

### モデル全体の処理量とGPU費用

OPT-30B、OPT-66B、OPT-175Bのモデル全体では、トークン毎GPU秒という指標でDeepSpeed比最大3.8倍、FasterTransformer比最大3.6倍の改善を報告する。これはGPU一枚あたりの生成処理量を表し、単一トークンの遅延や同時利用者の待ち時間と同じ指標ではない。重みの圧縮によって必要なGPUメモリが減るため、より少ないGPUでモデルを保持できる場合がある。GPU台数の削減とGPU当たり処理量の増加を合わせて評価している点が、単体カーネルの高速化率だけを見る場合との違いである。

論文のOPT-66Bの事例では、Flash-LLMが最大522トークン/秒/GPUに達したのに対し、比較したDeepSpeedは139、FasterTransformerは144程度と報告される。比較対象は大きなバッチでメモリ不足により実行できない条件があり、Flash-LLMがより大きいバッチを処理できることも処理量差へ寄与する。実行不能の条件を無視して同一バッチでの純粋なカーネル倍率と解釈するのは適切でない。

### 枝刈り品質と速度の交換条件

非構造枝刈りを80%適用した品質例では、OPT-30Bの精度指標が85.55%から84.11%へ、GPT-NeoX-20Bの例では83.03%から82.31%へ下がる。これはモデルの重みを変えたことに伴う品質差であり、疎読込・密計算カーネル自体の数値誤差と区別する必要がある。論文の処理量改善を「完全に同じ密モデルの出力を保って高速化」と説明するのは不正確である。

バッチが大きくなるとTensor Coreの利用率も上がるため、冗長なゼロ乗算を許容する余裕は小さくなる。バッチ8では利用率が約5%だった例でも、バッチ64では約40%へ増えている。さらに疎性を極端に高めればメモリ転送は減るが、枝刈り精度が悪化する可能性がある。最適な疎性とバッチ範囲は、GPU帯域、演算器能力、品質許容範囲を合わせて決める必要がある。

## 既存研究との差

cuSPARSEやSputnikは非構造疎行列積でゼロの演算を飛ばすことを重視するが、汎用CUDAコアの演算性能に制約されやすい。SparTAは構造化疎性をTensor Coreへ載せるため、任意の80〜90%非構造疎性をそのまま扱うものではない。Flash-LLMは外部メモリ上で疎に保ち、GPU内部では密へ戻すことで両者の利点を組み合わせる。

GPUの性能がメモリ帯域より演算能力側に律速される大きな行列積では、ゼロを含めて密計算する余分な演算が支配的になり、同じ設計が有利とは限らない。Flash-LLMの独自性は、生成段階の細長い行列積というワークロードの性質を利用して、疎性をメモリ転送削減に使う点にある。

## 限界

第一に、モデルの重みを非構造枝刈りした状態が前提となる。枝刈りの方法や再学習費用はモデル準備側の問題であり、カーネルを差し替えるだけで密な元モデルが同じ精度のまま小さくなるわけではない。評価でも精度低下が観測されるため、速度とモデル品質の両方を測定する必要がある。

第二に、細長い行列積でメモリ帯域が支配的であることを利用する設計である。大きなバッチや事前充填で演算律速になると、密復元後の冗長なゼロ乗算が重荷になり得る。復元用のレジスタと共有メモリ、タイルごとの不規則な非ゼロ分布、事前並べ替えの費用も考慮が必要である。

第三に、主な実装はA100世代のTensor Core、CUDA非同期転送、共有メモリ構成へ最適化されている。GPU世代や演算器命令の形状、共有メモリ容量が変わればタイル幅と重畳パイプラインの調整が必要になる。CPUやSSDへの重み退避、複数ノード通信、複数利用者の要求スケジューリングを包括的に評価したものではない。

第四に、トークン毎GPU秒の改善には、メモリに収まるGPU台数やバッチ数の差が含まれる。これを単一GPU・単一要求の遅延短縮率として転用してはいけない。枝刈り率、対象モデル、比較エンジンの版、バッチ条件を揃えた上で評価する必要がある。
