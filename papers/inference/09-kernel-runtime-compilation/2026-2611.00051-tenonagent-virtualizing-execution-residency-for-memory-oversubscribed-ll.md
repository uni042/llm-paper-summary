# TenonAgent: Virtualizing Execution Residency for Memory-Oversubscribed LLM Agents

> LLMエージェントのサンドボックス常駐を仮想化し、アクション境界の予測受付と再起動安全な解体、実行中のカーネル側ペーシングでホストメモリの過剰割当てを安全に行うランタイムを提案した研究。

## 概要

LLMエージェントは、遠隔のモデル呼出し、シェルコマンド、コード実行、検索などを交互に行う、長寿命で状態を持つワークフローである。ツール実行は隔離されたサンドボックス（コンテナやマイクロ仮想マシン）の中で行われ、サンドボックスはファイルやプロセスやキャッシュを保持するため、通常はワークフローの終わりまで生かし続ける。ここにメモリの問題が生じる。エージェントのメモリ需要はフェーズで激しく変わり、モデル応答を待つ間はほぼ何も割り当てないのに、前のアクションで確保したメモリは残り続ける。全サンドボックスを生涯ピークに合わせて確保すると待ちフェーズで容量が遊び、逆に詰め込むと複数のサンドボックスが同時に成長してメモリ不足障害を起こし、ワークフロー全体の再試行という高くつく失敗になる。

TenonAgentは、エージェントの論理的な生存期間とサンドボックスの物理的な常駐を切り離す。外部コントローラーが会話や軌跡や永続ワークスペースを持つため、サンドボックスは安全な境界で解体し、必要になったら作り直せる。制御は2つの時間スケールで行う。アクション境界では、需要予測に基づく受付制御と、ホスト全体のメモリ圧力に応じた常駐の保持・回収を決める。実行中は、sched_extを使ったカーネルゲートが、成長しそうなサンドボックスの実行許可を絞って同時成長を抑える。代表結果として、4 vCPU・8GiBの制約条件で、無管理実行に対してScienceAgentBenchで43.4分から7.9分への5.5倍の高速化を達成し、提出ワークフローのピーク需要合計が物理容量の8.6倍に達するバーストでもタスク成功率100パーセントを保った。既存のエージェントレベル予約に対しては最大で約5倍、cgroup系のAgentCgroupに対しては最大37倍速かった。

## 問題設定

CPUは時間で分け合えるが、メモリは一度割り当てられると実行が止まっても占有され続ける。この非対称性がエージェント基盤を難しくする。論文のプロファイルでは、代表的なソフトウェア工学エージェントの実行で、アクション実行時にCPUやページフォルトやメモリ割当てが鋭く跳ね、待ちフェーズでは割当てが止まるのに残留メモリは約150メガバイトの水準で残り続ける様子が観測された。境界ポリシーの予備実験では、同時実行数が1のときはサンドボックス保持が再構築を避けられて速いが、20へ増やすと保持した残留メモリが全ホストで積み上がり、保持の利点が消えて逆転する。つまり最適な境界ポリシーは負荷で変わり、静的な保持か解体かの二択では足りない。

もう1つの難しさは、解体が常に安全とは限らないことである。生きているプロセスや接続の中にしかない状態に次のアクションが依存するなら、サンドボックスを壊すとワークフローを壊す。逆に、完了したアクションが状態を永続領域へ外へ出し終え、決定的に再構築できる境界なら、壊しても論理的な同一性は保てる。したがって常駐制御は「壊してよいか」という正しさの条件と、「今壊すべきか」という圧力の条件を分けて扱う必要がある。さらに境界での制御だけでは、受付後に始まる実行中の成長は止められない。受付、常駐、実行中成長の3つを束ねることが、過剰割当てを安全にする条件になる。

## 手法のあらまし

TenonAgentの処理は、アクション完了とアクション準備完了という2つの境界イベントを軸に回る。アクションが完了すると、コントローラーは結果を記録し、その境界が再起動安全かどうかを決定的な検査で判定し、受付時の論理課金を解放した上で、全体の圧力状態に応じてサンドボックスを保持するか解体するかを決める。次のアクションが準備できると、必要ならサンドボックスを再実体化し、予測した需要に基づいて論理受付と物理ゲートを通してから実行を始める。実行中は100ミリ秒周期のコントローラーがcgroupのメモリ計測から各サンドボックスの成長を見積もり、圧力状態に応じて実行許可集合を更新してBPFマップ経由でsched_extスケジューラへ渡す。圧力は余裕のある緑、予防回収に入る黄、成長を強く絞る赤の3状態で、受付済みアクションの予想成長まで含めて判定する。

## 手法

### 1. 常駐の仮想化と再起動安全契約 — 壊してよい境界だけを壊す

分離の土台は、論理エージェントを外部コントローラーの状態と永続ワークスペースで定義し、サンドボックスをプロセスやキャッシュや接続を持つ使い捨ての実行基盤として扱うことである。再起動安全の判定は大規模言語モデルによる判断ではなく決定的な実行時検査で行い、完了したアクションが論理状態を外へ出し終えていること、必須の状態が生きているプロセスや接続の中だけに残っていないこと、永続成果物が記録されていることを要求する。解体の手順も順序が固定されており、新規派遣を止めて適格性を確認し、永続領域の成果物を耐久ストレージへ出し、回復記録を確定してから初めてサンドボックスを壊す。途中で失敗したら解体は中止され、サンドボックスは常駐のままになるという、失敗時に閉じる契約である。再実体化では、記録された土台環境から新しい実体を作り、確定済みの成果物を入れ、状態の完全性を確認してから次のアクションを派遣する。完了したアクションの再生や、任意のプロセスメモリの復元はしない。この契約の代償は適用範囲の狭さで、常駐型のシェルや背景サービスを必要とするワークフローは常駐専用のままになり、回収の対象から外れる。

### 2. アクション記述子と因果的な需要予測 — 実行前に需要を見積もる

各アクションについて、TenonAgentはアクション種別、予測平均メモリ、予測ピークメモリ、重いメモリ需要のリスク、優先度からなる記述子を作る。予測器は、そのアクションの文脈、同じタスクの完了済みアクションの要約、プロンプトと現在アクションと直近軌跡からのテキスト特徴を使い、ランダムフォレストで平均とピークと重い需要のリスクを別々に予測する。因果性が設計の要点で、予測に使えるのはそのアクションが始まる前に分かる情報だけであり、実測結果や未来のアクションは使わない。完了後の実測はタスク内の履歴へ追加され、後続アクションの予測だけに効く。予測の質は受付の攻め方へ直結する。過大予測は同時実行を絞って遊びを生み、過小予測は同時成長を許してメモリ不足を招く。論文の直接評価では、意味だけを使う静的予測器や直前アクションの履歴だけを使う予測器より、両方を合わせた現行予測器が誤差と重い需要の見逃しの両方で優った。誤予測が残る前提で、後の実行中制御が安全側の受け皿になる二段構えである。

### 3. 水位を意識した受付と待ちフェーズの常駐 — 境界での粗い制御

受付では、各アクションへ論理課金を割り当てる。課金は予測平均と予測ピークの間の補間で決まり、受付済み課金の合計が設定した窓へ近づくほどピーク寄りへ寄せる。つまり空いているときは平均で攻めて同時実行を増やし、混んできたらピークで保守的に数える適応的な数え方である。待ち行列は軽いアクション用と重いアクション用に分かれ、通常は軽い方を優先して空きを埋めるが、最も古い重いアクションには論理クレジットが貯まって保護されるため、重いアクションが永久に後回しになることはない。常駐制御は圧力状態で切り替わる。緑では待ち時間が解体と再実体化の費用を償う場合だけ回収し、基本的には保持する。黄と赤では回収を優先し、再起動安全なサンドボックスを実測ワーキングセットの大きい順に解体する。再実体化も圧力で変わり、緑では予測的な先行再実体化を許すが、黄では推測的な作業を止め、赤では新規の再実体化自体を始めない。境界制御が減らすボトルネックは、待ちフェーズに残る残留メモリの積み上がりであり、追加費用は解体と再構築の入出力と時間である。

### 4. sched_extゲートによる実行中ペーシング — 成長そのものを資源として扱う

実行中の制御が扱う資源は現在の占有量ではなく、これから増える成長である。小さくても猛烈に割り当てるサンドボックスは危険で、大きくても安定しているサンドボックスは安全だという観測に基づく。コントローラーは100ミリ秒周期でcgroupのメモリ計測を読み、各サンドボックスの成長率を指数移動平均で見積もり、1秒先の需要を投影する。緑では全サンドボックスを実行させる。黄では、混雑制御と同じ加算的増加と乗算的減少で同時成長の予算を調整し、余裕に収まる成長だけを許可する。赤では許可する成長サンドボックスを最大1つへ絞り、余裕に収まる場合だけ探査として通す。許可と不許可はcgroup単位でBPFマップへ公開され、sched_extスケジューラが不許可の実行可能タスクを待ち行列に留めることで、割当てを行うサンドボックスがCPU時間を得る速度を落とす。これは既存の割当てを取り戻す仕組みではなく、成長の機会を先に絞る仕組みである。そのため、推定が外れたり制御周期の間に急増したりする分は、赤領域として確保した緊急余裕で吸収する設計になっており、余裕の大きさが信頼性と性能の交換条件になる。

## 評価

### まず見るところ

- **結論:** 制約の厳しい条件ほどTenonAgentの優位が大きく、無管理実行の失敗と再試行による膨張を消すことで、単なる高速化ではなく信頼性の改善がそのまま処理時間の改善になっている。
- **速度・効率:** 主指標はバッチ全体の完了時間とワークフローの中央値遅延で、失敗したワークフローの再試行費用を含めて測られている。ピークメモリと失敗件数も併記される。
- **品質:** オンラインの実エージェント評価では、タスク精度はTenonAgentの有無でほぼ一致した。再起動安全な境界の割合が高く、解体がタスクの進行を壊していないことの傍証になっている。
- **評価の強さ／注意点:** 主比較は軌跡再生による再現可能な条件であり、実エージェントのオンライン評価は1つの負荷水準と2つのモデル設定に限られる。再生は失敗への適応をしない固定手順である点に注意が要る。

数字の読み方として、無管理実行の遅さの主因は通常実行の遅さではなく、メモリ不足とタイムアウトで失敗したワークフローを最大5回まで再投入する費用である。4 vCPU・8GiBでは、AgentCgroupがSWE-benchで120.6分、ScienceAgentBenchで293.4分まで膨らんだのに対し、TenonAgentは21.3分と7.9分で終えた。付録の原因分析では、AgentCgroupの静的な高低分類と固定のメモリ上限が、しきい値を超えた正当な作業を直接リクレームのスラッシングへ落とすことが膨張の仕組みだと説明されており、容量を事後に罰する方式と成長を事前に絞る方式の差がここに出ている。資源に余裕のある条件では差は縮み、8 vCPU・16GiBのOrchardでは無管理の9.6分に対し9.3分とわずかな差になる。つまり本方式の価値は余裕のない条件での崩壊防止に集中している。

移植性の結果も設計の主張を裏付ける。バックエンドをFirecrackerへ替えても、TenonAgentは全予算で試行成功率100パーセントを保ち、100パーセント成功を達成した最良の静的設定に対して完了時間で1.97倍から4.83倍、中央値遅延で1.7倍から4.2倍速かった。常駐の仮想化が特定のコンテナ実装ではなく、隔離機構に依らない制御であることが示されている。除去実験では、実行中成長制御を外すと完了時間が44.3パーセント増えてメモリ不足が3件出て、常駐固定にすると中央値遅延が111.3パーセント増えた。予測器を静的なものへ替えると同時実行が34から20へ落ちて中央値遅延が132.2パーセント増えており、3つの機構がそれぞれ別の失敗様式を抑えていることが分かる。感度分析では、黄と赤の領域を小さくしすぎると緊急余裕が足りず成功率が落ち、大きくしすぎると予防回収や停止が早まって遅くなるため、両方12.5パーセントの参照設定が経験的な最適点だった。

## 既存研究との差

エージェント実行の最適化では、AltoやAutellixやParrotなどが分散した複合システムの編成を扱い、ContinuumやThunderAgentは複数ターンのKVキャッシュ保持などGPU側を扱う。本論文はそれらと直交するホスト側のCPUメモリとサンドボックス常駐を対象にする。隔離基盤としてはFirecrackerやgVisorなどがあり、状態を持つワークフロー向けにはCRIUやDeltaBoxのようなチェックポイント復元があるが、それらは実行実体の同一性を重いメモリイメージで保存する。本論文は、意味的な境界で論理状態だけを永続化し、物理実体は作り直すという軽い仮想化を選んだ点が異なる。AgentCgroupとの差は、容量の上限を事後に強制するのではなく、成長の機会をCPUスケジューリングで事前に絞る点にある。

## 限界・実装状況

- 対象資源はホストメモリ容量だけであり、CPU競合、メモリ帯域、入出力は明示的には扱っていない。データ集約的なワークロードではそちらが先に詰まる可能性がある。
- 常駐仮想化は、モデル推論の待ち時間という遊び時間に依存する。推論が速くなって待ちが縮むと、再構築費用が回収量を上回る条件が出てくる。
- アクション境界が見える専用サンドボックスが前提であり、協調しない複数テナントが1つのサンドボックスを共有する条件は扱っていない。再起動安全の対象も制限された実行モデルに限られる。
- 公式コードの公開先は論文中に示されていない。sched_extへの依存も、利用できるカーネル環境を選ぶ条件になる。

## 一般的な実装上の含意

状態を持つ実行基盤でメモリを詰めたいときは、「壊してよいか」の正しさ条件と「今壊すべきか」の圧力条件を分離し、正しさ側は失敗時に閉じる決定的な検査にすることが安全である。また、容量の上限を事後に罰する方式はスラッシングで大きく崩れるため、割当ての機会そのものをスケジューリングで絞る方が、過剰割当てには向く。受付の課金は、混雑度に応じて平均見積もりとピーク見積もりの間を滑らかに移すことで、遊びと過剰受付の両方を抑えられる。境界制御だけでは実行中の成長は止まらないため、粗い時間スケールと細かい時間スケールの制御を組み合わせることが要点である。
