# lm-Meter: Unveiling Runtime Inference Latency for On-Device Language Models

## 概要

端末内の大規模言語モデル（LLM）では、総実行時間だけを測っても、入力を一括処理するプリフィルと、出力トークンを一つずつ生成する復号のどちらが遅いのかを判断できない。さらにモバイルGPUではドライバが非公開で、カーネル単位の実行時間、キュー待機、ホスト側の発行遅延をアプリケーションから直接見ることが難しい。lm-Meterは、推論ランタイムの意味的な処理境界と、GPUコマンドの実行時刻を同時に取得するオンライン遅延計測器である。外部ホストによる事後解析を前提とせず、端末内で推論を続けながら観測結果を取り出すことを目的とする。

著者らはMLCとTVMに約3,500行の計測コードを実装し、Google Pixel 8 Pro、Pixel 7、Pixel 6で検証した。Pixel 8 Proの16種類のGPUカーネルでは、複製カーネルによる基準測定に対する平均精度96.82%、中央値97.35%を達成する。最も資源が制限される省電力CPU周波数設定でも、計測を有効にしたことによる処理量の低下はプリフィル2.58%、復号0.99%に留まる。従来のMELTing Pointは同条件でプリフィル22%、復号93%超の処理量低下を生じ、継続計測に適さないことが示された。

この計測器を用いた実証分析は、単なる計測精度評価を超える。Pythiaの70Mから1.4Bへの拡大では、Pixel 8 Proのプリフィルの入力トークン当たり遅延が0.012秒から1.9秒へ158倍に増える一方、復号の出力トークン当たり遅延は0.015秒から0.15秒への10倍に留まる。また量子化Gemma-2-2B-itの短い復号ではGPUの遊休時間が21%を超え、行列積カーネル群が実行時間の60%超を占める。こうした端末固有の律速を可視化する点が研究の主な貢献である。

## 問題設定

LLMの生成では、入力文脈をまとめて処理するプリフィル、過去の鍵値キャッシュを参照しながら1トークンずつ処理する復号、確率分布を求めるソフトマックス、次トークンを選ぶサンプリングなどが異なる計算特性を持つ。サーバーGPUではプリフィルが高い並列性を得やすく、バッチ1の復号が律速になりやすい。しかしモバイル端末は演算資源とメモリ帯域が限られ、周波数制御や熱制限もあるため、同じ関係が成立するとは限らない。実際、著者らは端末上では大きなモデルのプリフィルが強い律速になり得ることを後段の実験で示す。

Androidアプリの高水準APIから時刻を取ると、Java/KotlinとネイティブC++の境界、ライブラリ呼出し、キューへの登録、GPU実行、結果回収が混在する。モデルが遅い原因がGPU計算なのか、ホストからの発行待ちなのか、特定段階の実装なのかを切り分けられない。一方、Android GPU Inspector（AGI）やPerfettoは外部ホストでの解析や事後処理が必要で、端末内で即座に計測結果を使う制御ループには組み込みにくい。

さらにTVMのようなコンパイラは逆量子化、行列積、正規化などを融合カーネルへまとめる。高水準の演算子単位で時間を計っても、実際のGPU発行単位とは一致しない。GPUカーネルのソースを変更する方法は閉じたモバイルドライバでは適用できない。したがって、推論段階を理解するランタイム側と、GPUコマンドの生存期間を記録する実行API側を組み合わせる必要がある。

## 手法

### 推論段階別の軽量タイマ

lm-MeterはMLCのネイティブC++実行系に、埋め込み、プリフィル、復号、ソフトマックス、サンプリングの開始・終了境界を明示的に設ける。各境界でC++標準の単調時計 `std::chrono::steady_clock` を呼び、段階名、系列番号、時刻を記録する。単調時計は時刻同期による壁時計の補正で逆行せず、短い処理と長い処理を同じ基準で比較できる。アプリケーションの画面更新や言語境界を含む粗い計測とは異なり、ネイティブ推論のどの段階に時間がかかったかを直接把握できる。

段階別計測の出力は、段階ごとの遅延と生成位置を対応付けた系列である。これにより、入力が長いときのプリフィル時間と、生成トークンが増えるにつれて変化する復号時間を別々に観察できる。ただしCPU側の段階タイマだけでは、内部でGPUが待っている時間と実際にカーネルを走らせている時間を分離できない。そのため次のGPUイベント追跡と組み合わせる。

### OpenCLイベントによるカーネル実行時刻の復元

MLC/TVMがGPUへ発行する各カーネルやデータ転送のコマンドに、OpenCLのイベント `cl_event` を対応付ける。`clGetEventProfilingInfo` を使って、コマンドがキューに登録された時刻（queued）、ホストから装置へ提出された時刻（submit）、装置が実行を開始した時刻（start）、実行を終えた時刻（end）の4点を取得する。これらはナノ秒単位の時刻であり、GPUカーネルのソースコードを変更する必要がない。

各コマンドについて、カーネル名、コマンドキューへの参照、CPU側登録時刻、4つのGPU側時刻を小さな記録構造に保持する。`queued→submit` はホスト側から装置への投入待ち、`submit→start` は装置側のスケジューリング待ち、`start→end` はGPU実行時間に対応する。生成後に時系列へ並べ直せば、カーネル間の隙間、同時に発行されたデータ転送、計算器が遊休している区間を復元できる。推論段階タイマとの対応を使うことで、例えば復号の遅さが行列積なのか、注意なのか、ホスト側の待機なのかを識別する。

この方法はOpenCLの標準イベントを利用するため、ドライバ内部の非公開実装を解析せずに済む。ただし実際に論文で完成・評価した実装はAndroid上のMLC/TVMとOpenCLが中心であり、VulkanやMetalに類似の仕組みを適用できるという設計上の見通しを、移植済み実装と取り違えてはならない。公式実装の対応表でもiOS、Jetson、llama.cppなどは未提供または開発予定である。

### 観測誤差の校正と基準値の作り方

測定器自身が処理時間を増やすため、計測値が正しいかを別の方法で検証する。段階別ではAndroid GPU Inspectorを基準にし、カーネル別では独自の複製法を用いる。対象カーネルをモデルの生成コード中で連続してn回追加実行し、追加前後の段階時間差をnで割って、1回当たりのカーネル実行時間を推定する。元カーネルの依存関係を保ち、コンパイラが複製を削除しないよう未使用コード除去と死コード除去を無効化する。

カーネルが1ミリ秒超ならn=50、短い場合はn=1,000とする。検証時にはCPU/GPU周波数を固定し、余分なアプリを停止して動的電圧・周波数制御の揺らぎを減らす。これは通常のオンライン計測時に毎回カーネルを複製するという意味ではない。**複製は評価用の基準値を得るオフライン手続き**であり、通常推論のlm-Meterはイベント時刻だけを収集する。

計測精度 `α=100×(1−|t_meter−t_reference|/t_reference)` は基準遅延への相対一致率で、大きいほど良い。尺度化誤差 `ε*=1000×|t_meter−t_reference|[ms]/t_reference[ms]` は実行1ミリ秒当たりのマイクロ秒誤差で、小さいほど良い。短いサンプリング処理では数十マイクロ秒の固定誤差が相対精度を大きく悪化させるため、両指標を併記する意義がある。

### 計測結果からの分析と量子化指標

lm-Meter自身はモデルを自動切替したり、GPU周波数を制御したりしない。出力するのは段階・カーネルの実測値と時系列であり、将来の適応制御器が使える観測基盤である。論文では、このデータを使ってモデル系列ごとの正答率と入力・出力トークン当たり遅延の関係を調べる。量子化の評価では、精度維持率、プリフィル遅延改善率、復号遅延改善率を調和平均した `H_Q`（調和量子化得点）を定義し、一つだけ悪化する構成を低く評価する。

具体的にはタスクiの量子化後精度を元モデル精度で割った `M_a`、元のプリフィル遅延を量子化後の遅延で割った `M_prefill`、元の復号遅延を量子化後の遅延で割った `M_decode` を用い、`H_Q = 3/(1/M_a + 1/M_prefill + 1/M_decode)` とする。単に4ビットへすれば必ず良いわけではなく、算術能力を失って精度がほぼゼロになれば他の2指標が良くても調和平均は低下する。著者らはこの得点で量子化による実機の利得と品質低下を同時に評価する。

## 主要結果

### 計測精度とオーバーヘッド

|条件・指標|lm-Meter|比較対象|読み取れること|
|---|---:|---:|---|
|Pixel 8 Pro、Llama-3.2-3B、プリフィル時間|3433.8628 ms|AGI 3433.8142 ms|段階別精度99.99%、大きい段階の差は約0.05ms|
|Pixel 8 Pro、Gemma-2-2B、プリフィル時間|9301.1318 ms|AGI 9301.0589 ms|段階別精度99.99%、モデル差が大きくても一致|
|Pixel 8 Pro、Gemma-2-2B、復号時間|54.5909 ms|AGI 54.5557 ms|段階別精度99.94%|
|Pixel 8 Pro、16カーネル平均精度|96.82%|複製法基準|中央値97.35%、最も低いカーネルは91.51%|
|Pixel 7、16カーネル平均精度|96.61%|複製法基準|中央値97.81%、最悪カーネル90.31%|
|省電力、プリフィル処理量低下|2.58%|MELTing Point 22%低下|オンライン計測による干渉が小さい|
|省電力、復号処理量低下|0.99%|MELTing Point 93%超低下|継続的な復号カーネル追跡が可能|

段階別では大きなプリフィル・復号の一致率が99.9%以上でも、非常に短いサンプリングでは相対精度が75〜92%に下がる。これはサンプリングが約0.05〜0.18ミリ秒と短く、OSスケジューリングの揺らぎやCPU/GPU同期遅延が占める割合が大きいためである。したがって「全段階で99.99%精度」とは言えない。カーネル単位でも100マイクロ秒程度の短い演算は長い行列積より相対誤差が大きいが、Pixel 8 Proのプリフィルの主要行列積4種類は98.69〜99.86%の精度で計測できる。

実行負担の測定では、Performance設定のプリフィルは計測有無とも0.680 token/s、復号は8.327から8.319 token/sへ低下する。Conservative設定の復号は7.954から7.885 token/s、省電力設定のプリフィルは0.658から0.641 token/s、復号は2.703から2.676 token/sとなる。処理量低下を計算費用として測定しているので、これらの数値を「計測により推論が高速化した」と解釈してはいけない。

### モデル世代・規模による精度と速度の交換条件

比較課題は、知識系のARC-EasyとARC-Challenge、推論系のHellaSwagとGSM8Kに分けている。論文の標本化対象は順に238問、112問、100問、131問で、同じモデルでも課題の性質に応じて精度と速度の均衡点が変わるかを調べる。特に簡単な選択問題と多段階の数学問題を同じ精度指標だけで並べないよう、課題ごとにモデル規模と入力・出力トークン当たりの遅延を比較している。


Pixel 8 Proで同じ0.5B級のQwenを比較すると、Qwen-1.5はARC-Challenge 29.3%、HellaSwag 49.1%、GSM8K 17.1%、復号22.76 token/sである。Qwen-2.5はそれぞれ35.6%、52.2%、41.6%まで向上する一方、復号は17.29 token/sへ24%低下する。単にパラメータ数が同程度でも、モデル世代とアーキテクチャの違いが端末の生成速度へ影響する。論文はこの差を「精度が上がったから推論も改善した」と短絡しないために段階別計測を用いる。

Pythia 70Mから1.4Bへ規模を上げると、Pixel 8 Proのプリフィルの入力トークン当たり遅延は0.012秒から1.9秒へ158倍に増える。復号の出力トークン当たり遅延は0.015秒から0.15秒への10倍である。この観測はサーバーGPUで復号を主な律速とみなす一般的な直感とは異なり、モバイル端末のプリフィル並列性と帯域制約を重視すべきことを示す。ARC-Easyでは小型化しても正答率の低下が比較的穏やかな一方、GSM8Kでは小型モデルの数学推論精度が極端に低く、低遅延だけでは実用モデルを選べない。

### 量子化の正負両面

4ビット量子化の調和量子化得点 `H_Q` は、Pythiaではモデル規模とともに改善し、難しいARC-ChallengeとGSM8Kで1.4Bが有利になる。一方、SmolLM2では135M〜360Mがより良い均衡点になる。Pythiaの平均得点はARC-Easyで0.982、ARC-Challengeで1.243、GSM8Kで1.260となり、単純な課題では量子化利得が小さく、難しい課題ではモデル規模との組合せが効くことを示す。

負の結果としてSmolLM2-1.7BのGSM8Kは、4ビット量子化で精度がほぼゼロとなり、調和量子化得点が大きく落ちる。著者らは3種類の4ビット量子化方式でも同様の低精度を観測している。したがって4ビット化がすべてのモデルと課題で品質を維持するわけではない。特に算術的に敏感な層の誤差が多段階推論へ影響する可能性があり、精度と実測遅延を同時に測る必要がある。

### GPUカーネルの内訳と長い復号

Pixel 8 Proで4ビットGemma-2-2B-itの復号を追跡すると、GPU遊休が総時間の21%超を占め、行列積融合カーネル3種類（K10、K12、K13）が60%超を占める。`fused_rope`、`tir_kv_cache_transpose_append`、正規化など短いカーネルは頻繁に起動するものの実行時間の寄与は10%未満で、起動回数の多さがカーネル間の空隙を増やす。これは行列積最適化だけでなく、発行待ちの削減やカーネル融合にも改善余地があることを示す。

ページ化注意の `batch_decode_paged_kv` は、過去トークンが増えるにつれ参照するKVキャッシュも増えるため、復号ステップにほぼ線形に遅延が伸びる。256トークン生成条件では250ステップ付近で1トークン当たり約0.9msに達する。一方、16トークン生成時と256トークン生成時を比べると、GPU遊休比率は21%から12%へ低下する。長い生成では注意計算が重くなるが、相対的なGPU遊休比率は小さくなるため、短い生成と長い生成で最適化すべき律速が異なる。

## 既存研究との差

Android GPU InspectorとPerfettoはGPU実行追跡に強いが、外部ホストによるログ処理が必要で、LLMの意味的な推論段階をその場で統合して返す用途には向かない。MELTing Pointはオンラインでカーネル平均時間を得られるものの、個別発行の開始・終了時刻やGPU遊休の連続タイムラインを提供せず、論文の省電力条件では大きな計測費を生じる。nnPerfは小型畳み込みモデル等を中心に設計され、可変長トークン列と段階別推論の特徴を直接扱わない。

lm-Meterの差は、MLCネイティブ実行系の意味的な段階計測とOpenCLイベントの4時刻を組み合わせることである。カーネル名とキュー待機を含む時系列を取得し、段階別の処理時間と同時に可視化できる。外部のGPUプロファイラを置き換える万能ツールというより、端末上のLLM推論で継続的に使える軽量観測器として位置付けられる。

## 限界

実証端末はGoogle Tensor系列のPixel 8 Pro、7、6であり、Apple Silicon、Qualcomm、Jetson、Intel NPUなどで同じ精度と計測費を達成することは論文から保証されない。イベント時刻取得はOpenCLの実装に依存し、MetalやVulkanへの拡張可能性と、実際に動作検証済みであることは別である。公式実装の対応表もAndroid GPU上のMLC LLMを公開済みの主対象としている。

計測器自体は推論高速化器ではなく、観測に数%以下の処理量費用が発生する。特に数十マイクロ秒級のサンプリングでは固定のタイマ費やスケジューリングの揺らぎが相対誤差を増やす。すべての段階や短時間カーネルで同じ99.99%精度を保証できない。

実証分析は4ビットの学習後量子化を主に扱い、枝刈り、蒸留、異なる量子化ビット幅や複数アクセラレータ協調を網羅していない。量子化による算術性能の悪化例もあるため、モデル・タスク・端末を変えたときの一般化は慎重に判断すべきである。GPU遊休の21%や行列積の60%という値も、Pixel 8 Pro上の特定のGemma-2構成・復号条件の測定値であり、すべてのモバイル推論へ適用できる普遍的な内訳ではない。

論文が示すエネルギー計測や、観測に基づくモデル切替・周波数制御は将来の拡張であり、実装済みの自動適応制御器ではない。端末内の電力最適化や複数モデルの自動選択に関する効果を、lm-Meter単体の実測成果として扱ってはならない。
