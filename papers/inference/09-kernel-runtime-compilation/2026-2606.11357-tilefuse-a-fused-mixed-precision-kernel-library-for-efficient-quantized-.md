# TileFuse: A Fused Mixed-Precision Kernel Library for Efficient Quantized LLM Inference on AMD NPUs

> AMD XDNA2 NPU向けに、逆量子化を融合した混合精度カーネルとメタデータ同梱の事前タイリングと全アレイGEMVを共設計し、AWQ形式をそのまま動かせるようにしたTileFuseの研究。

## 概要

ノートPC向けSoCには、CPUと内蔵GPUに加えてNPU（ニューラルプロセッシングユニット）が載るようになった。電力と熱の予算が厳しいエッジでLLMを動かす受け皿として期待される一方、実際の利用は進んでいない。理由は素の計算能力ではなくソフトウェアにある。各社のNPUスタックは独自仕様で、公開されるのは高レベルの配備インターフェースが中心であり、カーネルやデータ移動を低レベルで制御できない。そのため、AWQ（Activation-aware Weight Quantization）のような広く配布されている量子化形式、特にグループ単位のスケールとゼロ点を持つ非対称な形式がそのままでは載らず、利用者はモデルをNPU専用の量子化方式へ作り替える必要があった。

本論文のTileFuseは、AMDのXDNA2 NPUが持つ再構成可能な空間アレイと、オープンな低レベル開発フローであるIRON（MLIR-AIE）を土台に、この向きを逆転させる。重みは圧縮されたINT4またはINT8のまま計算コアまで運ばれ、アンパック、逆量子化、行列演算が1つのカーネルの流れの中で行われる。量子化メタデータはオフラインの事前タイリングで重みタイルへ同梱され、大きなMLP層でもDMAのストライド制約に当たらない配置へ並べ替えられる。生成側のGEMVは、メモリコアを中継に使うデータフローで4行8列の全アレイへ広げられる。代表結果として、カーネル評価では全精度ベースラインに対してGEMMで最大121.6パーセント、GEMVで最大281パーセントの性能向上を示し、強力な内蔵GPUベースラインに対してGEMMで2倍超の性能とエネルギー効率を出した。エンドツーエンドでは、Ryzen AI 7 350上でLlama3-8Bのプリフィル遅延がプロンプト2048トークンで2.00倍低下し（8246.9ミリ秒から4129.9ミリ秒）、プラットフォームのエネルギー消費は64.6パーセント削減された。ただしトークン生成ではNPUのディスパッチ負担が支配的で内蔵GPUに劣り、使い分けが結論になっている。

## 問題設定

対象はバッチ1が普通のエッジ推論であり、プリフィルは行列積（GEMM）が、トークン生成は行列ベクトル積（GEMV）が支配的である。量子化形式は、重みだけを低ビット化し活性値を16ビットに保つW4A16とW8A16で、W4A16はグループサイズ128のグループ単位非対称量子化、W8A16はチャネル単位対称量子化を主に扱う。逆量子化には重み本体に加えてスケールとゼロ点というメタデータが要る。

難しさは4つある。第1に逆量子化の置き場所である。分離型では量子化重みを読み、BF16へ展開してメモリへ書き戻し、再び読む往復が生じる。融合すればこの往復は消えるが、タイル型GEMMでは同じ重みタイルが複数の活性値タイルと掛け合わされるため、消費のたびに逆量子化すると作業が重複する。第2にメタデータの供給である。各計算タイルへのストリーミング経路は限られており、重み、活性値、メタデータを3本の独立した流れとして届けることはできない。第3に大きな層である。出力タイルの列はアレイの8列へ巡回的に割り当てられるため、行優先の配置では同じ列が次に担当するタイルが大きく離れ、DMAのストライドレジスタの上限を超えると1つのGEMMを複数回のカーネル呼出しへ割らなければならず、大きな負担になる。既定の配置では対応できる次元は8K未満に限られるが、MLP層はこれを超える。第4にGEMVの利用率である。量子化で重みの転送量が減る一方、逆量子化の計算が増えるため、GEMVはメモリ律速から計算律速側へ寄る。ところが既存のGEMVデータフローは計算行を1行しか使わず、32コア中8コアしか働いていない。これらはいずれもカーネル単体の工夫では解けず、重み配置、メタデータ配置、マイクロカーネル、アレイレベルのデータフローの共設計が要る、というのが本論文の問題設定である。

## 手法のあらまし

TileFuseの処理はオフラインと実行時に分かれる。オフラインでは、量子化済み重みを事前タイリングし、各タイルへ逆量子化に要るメタデータを同梱し、同じアレイ列が担当するタイルがメモリ上で連続するインターリーブ列優先の配置へ並べ替える。実行時には、重みは圧縮形式のままDMAで計算コアへ流され、マイクロカーネルがアンパックと逆量子化を行い、結果をコアのローカルメモリへ置いて再利用しながら行列演算へ渡す。GEMVでは重みの束をシムコアからメモリコアへ送り、メモリコアが同じ列の4つの計算コアへ配ることで全アレイを使う。エンドツーエンド実行では、トランスフォーマの線形層をNPUへ、注意や正規化などの演算を内蔵GPUへ振り、依存関係に従って逐次に実行する。プリフィルの大きなGEMMではNPUの起動と再構成の負担が償却されるが、生成の小さなGEMVでは償却されず、この非対称が評価結果と使い分けの結論を形作る。

## 手法

### 1. 重みの事前タイリング — メタデータを同梱し、大きな層を流せる配置にする

観測対象は配備時点で既知の重み行列であり、処理はすべてオフラインで実行時の負担はゼロである。保持する状態は3階層の配置である。最下層は8×8の重みブロック内の並び、中層はタイル内での重みとメタデータの同梱、最上層は行列全体でのタイルの並びである。同梱の仕方として、W4A16ではタイルの圧縮INT4値を連続して置き、その後にBF16のスケールとINT8のゼロ点を続ける。例えば128×64のタイルでは、グループサイズ128のため列ごとに1組のスケールとゼロ点で足り、64個のスケールと、DMAの転送単位に合わせるために複製した128個のゼロ点が重みの直後に置かれる。余分な容量は1.5パーセント程度である。W8A16では対称量子化のためスケールだけを同様に付ける。この配置により、計算コアは重みの流れ1本から逆量子化に要る情報をすべて得られ、独立したメタデータの流れが要らなくなる。大きな層への対策はインターリーブである。同じアレイ列が担当するタイル列同士をメモリ上で連続させることで、DMAは大きなストライドなしに連続読みでき、対応できる次元は8K未満から32Kまで広がる。あわせて、タイル優先の配置はDRAMのバースト転送にも合い、形状が変わっても性能が安定する。この機構が減らすボトルネックは、メタデータ供給の経路不足と、大きな層での分割呼出しと非効率なストリーミングである。誤った前提への挙動として、配置は重みが静的であることに依存するため、実行時に重みが変わる運用には向かない。

### 2. 融合マイクロカーネル — 逆量子化を1回だけ行い、ローカルメモリで再利用する

入力は事前タイリング済みの重み流れとBF16の活性値タイルである。AIEの行列演算プリミティブはBF16の8×8ブロックに最適化されているため、処理はこの粒度で進む。W4A16では、まず1バイトに詰められた2つの4ビット値をビットマスクとシフトで取り出してINT8のレーンへ広げるアンパックを行い、次にスケールとゼロ点を使ってBF16へ逆量子化する。W8A16ではゼロ点の引き算はなく、INT8値をBF16へ変換してチャネル単位のスケールを掛ける。要点は再利用の管理である。逆量子化した重みブロックを計算コアのローカルメモリへ置き、複数の活性値スライスに対して使い回すことで、重みタイルあたりの逆量子化は1回で済む。ローカルメモリへの出し入れという追加作業は、VLIW命令の並列性で逆量子化や行列演算と重ねて隠す。この機構が減らすボトルネックは、BF16重みを大域メモリへ書き戻す往復と、重複する逆量子化の両方である。GEMV側のマイクロカーネルは別に調整されている。既存実装は16×8の重みブロックで1反復に16出力しか作れずベクトルハードウェアを使い切れなかったため、64×8のブロックをベクトルレジスタへ載せ、1×8の活性値断片を64行で共有して1反復に64出力を蓄積する形へ広げ、コアあたりの利用率を上げた。追加費用はローカルメモリの容量消費と命令列の複雑さであり、タイル形状が最小粒度の倍数でないモデルでは埋め草（パディング）による過剰計算が生じる。実際、Qwen2.5-3BのMLP中間次元はこの条件に合わず、生成で不利になる一因として報告されている。

### 3. GEMVデータフロー — メモリコアを中継して全アレイへ重みを配る

観測対象はアレイ内のデータの流れである。ベースラインの配布では、各シム列が重みを1つの計算行へ直接流すため、使われるのは32コア中8コアだけである。全行へ広げようにも、GEMVでは各計算コアが異なる重みタイルを受け取る必要があり、列あたり1つしかないシムコアからは4行分の独立した流れを自然には作れない。TileFuseの配布は2段構成である。第1段でシムコアが、列の4つの計算行に対応する4タイルの束を連続してメモリコアへ流し込む。第2段でメモリコアがその4タイルを列内の4つの計算コアへ配る。活性値ベクトルはアレイ全体で共有され、各コアは担当する出力要素についてアンパック、逆量子化、乗算、蓄積をローカルに完結させるため、部分和がこの配布経路を流れることはない。その結果、同時に処理できる出力タイル群は8から32へ増える。この機構が減らすボトルネックは、計算律速側へ寄ったGEMVでの空間利用率である。追加費用はメモリコア経由の局所的なデータ移動であり、除去実験では、混合精度でGEMVが計算律速側へ移った後にこのデータフローとマイクロカーネルの最適化が効き、組み合わせで全精度ベースライン比最大281パーセントの向上になったことが示されている。逆に、元のメモリ律速のままでは計算側の最適化はほとんど効かないという条件依存性も読み取れる。

### 4. エンドツーエンド実行と再構成可能性の使い方

エンドツーエンドの枠組みはC++にPythonバインディングを付けた独自実装で、Hugging Face形式の重みを読み、事前タイリングとトークナイズを行い、トランスフォーマの実行ループを回す。線形層は事前コンパイルされたXDNA2カーネルを呼び、注意（FlashAttention-2）、ソフトマックス、残差加算、正規化などの演算は内蔵GPUのHIPとlibtorchのカーネルで実行する。NPUと内蔵GPUの同時実行は行わず、依存関係に従ってどちらかへ逐次に投入する演算子単位の振り分けである。XDNA2の再構成可能性は、計算コアのプログラム、メモリ配置、DMAのバッファ記述子のパターン、コア間のデータ移動経路を、ワークロードに合わせて生成できる点に使われている。一方で、カーネルのディスパッチとアレイの構成には実行時の負担があり、数十ミリ秒走るプリフィルのGEMMでは償却されても、数百マイクロ秒の生成GEMVでは支配的になる。TileFuseはこの負担を消すのではなく、大きな演算へ寄せることで償却し、小さな演算では内蔵GPUへ逃がす設計判断を評価とともに示している。負担の中身は、事前にコンパイルされたカーネルの起動、その計算プログラムの有効化、DMAの記述子と同期オブジェクトの設定、コア間のデータ移動経路の接続であり、いずれも演算そのものの大きさとは無関係に演算子ごとに発生する固定費である。したがって、同じカーネルでも、1回の実行時間が長い演算子にまとめて適用するほど固定費の割合は下がり、短い演算子が大量に連なる経路では固定費が累積して全体を支配する。この固定費の見方が、プリフィルと生成で結論が分かれる理由を一貫して説明する。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 事前タイリング | 静的な量子化済み重み | メタデータを同梱し列単位で連続配置する | メタデータ経路と大きな層の分割 | 重みの静的性への依存 |
| 融合マイクロカーネル | 圧縮重みの流れと活性値 | アンパックと逆量子化を1回だけ行いローカルで再利用する | BF16書き戻しの往復と重複変換 | ローカルメモリ容量 |
| GEMVデータフロー | シムとメモリと計算のコア配置 | メモリコア経由で4行へ重みを配る | GEMVの空間利用率 | 中継のデータ移動 |
| 演算子振り分け | 演算の種別と大きさ | 線形層はNPU、その他は内蔵GPUで逐次実行 | 起動負担の償却 | 並行実行はしない |

## 評価

### まず見るところ

- **結論:** プリフィルではNPUが内蔵GPUを上回り、エネルギーも大きく下がる。生成では逆転する。NPUの価値は演算の大きさと起動負担の償却で決まる。
- **速度・効率:** カーネル単体では形状に対する性能が滑らかで、ピークはKrackan Pointで12TOPS、Strix Pointで9TOPSである。内蔵GPUは形状によってギザギザの変動を示す条件がある。
- **品質:** 既製の量子化形式をそのまま実行するため、品質は元の量子化の特性に従う。タスク品質やパープレキシティの比較は論文では未評価である。
- **メモリ・入出力:** 重みは圧縮形式のまま流れるため転送量が減り、メタデータの複製は1.5パーセント程度の追加で収まる。
- **評価の強さ／注意点:** 実機2機種でカーネル、エンドツーエンド、電力、除去実験まで揃う。ただし機種間のNPU性能差の原因は公開仕様では説明できておらず、経験的な観測として扱われている。

### 評価上の制約

- 評価はAMDのXDNA2を載せた2機種のみであり、他社NPUへの一般化は設計原理の移植可能性として論じられる段階である。
- エンドツーエンドはNPUと内蔵GPUの逐次実行であり、同時実行による更なる短縮は未評価である。
- 生成性能はドライバと再構成の負担に支配されており、カーネル自体の改善だけでは結論が変わらない。

## 既存研究との差

GPUとCPU向けの量子化推論は、AWQやGPTQなどの量子化手法と、llama.cpp、QServe、MARLIN、PowerInferといった成熟したカーネルとシステムの蓄積があるが、対象はNPUではない。モバイルとクライアントNPU向けの研究では、Qualcomm向けのScalingLLMがNPUの構造に合わせたブロック量子化を設計して精度と性能を両立させたが、標準のAWQそのものは実装していない。XDNA2向けの先行研究は、BFP16の汎用GEMMで高いスループットを示したが、大きなFFN形状を覆えず、精度もエンドツーエンド推論には足りなかった。FastFlowLMはRyzen AI NPU向けの配備ランタイムだが、低レベルカーネルの設計は公開されていない。最も近いGemma3のエッジ配備研究は量子化モデルのエンドツーエンド配備を示すが、本論文の差は、既製のAWQ形式のW4A16とW8A16を直接支える再利用可能な融合カーネルライブラリとして、逆量子化の同梱配置、大きな行列のストリーミング、GEMVのデータフローを分離して説明し測った点にある。

## 限界・実装状況

- トークン生成ではNPUが内蔵GPUに劣る。演算が数百マイクロ秒に対してディスパッチと再構成の負担がミリ秒級であり、対話型の生成主体の用途では現状のままでは不利である。
- 最適化はXDNA2の再構成可能な空間アレイと低レベル制御に依存する。他のNPUやGPUへ移せるのは事前タイリングの考え方までで、具体的な配置はアーキテクチャごとに作り直す必要がある。
- 機種間の性能差、特に下位機種のNPUが上位機種を上回る現象は原因が特定できておらず、実効帯域や電力・熱や実行時の差という推測にとどまる。
- タイル粒度に合わないモデル形状では埋め草による過剰計算が生じる。Qwen2.5-3Bの生成での不利の一因として報告されている。
- エンドツーエンドの正しさ確認は行われているが、生成品質の定量比較は報告されていない。量子化形式そのものは既製のため、品質は元の形式の評価に委ねられる。
- コードはMLIR-AIEのフォークのブランチとして公開されている。独自の実行枠組みによる評価であり、既存の推論ランタイムへ統合された形ではない。

## 一般的な実装上の含意

エッジデバイス向けの推論基盤を設計する際は、量子化形式をハードウェアへ合わせる前に、重みの静的な再配置でハードウェア側を形式へ合わせられないか検討する価値がある。メタデータを重みに同梱して流れを1本にすること、逆量子化の結果をローカルに保持して再利用すること、大きな行列をDMAの制約に合う連続配置へ並べ替えることは、NPU以外でも使える設計要素である。また、起動と再構成の固定費が大きいアクセラレータでは、演算の大きさで配置先を分けることが本質的であり、カーネル単体の高速化とエンドツーエンドの優劣は別々に測る必要がある。生成のように小さな演算が連続する経路では、ドライバとランタイムの負担がカーネル性能を覆い隠すため、評価は必ずエンドツーエンドの遅延と電力まで含めて行うべきである。
