# TileLang: A Composable Tiled Programming Model for AI Systems

> GPUカーネルの「何を計算するか」をタイル単位のデータ流として書き、「どのスレッドがどの配置で、どの命令を使い、転送と計算をどう重ねるか」を別のスケジュール層へ分離する。高水準な記述を保ちながら、FlashAttention-3級の複雑なパイプラインまで表現・自動推論できることを狙う。

## 概要

LLMの実行時間を支える行列積や注意計算は、数式だけなら単純でも、GPU上で速くするには大量の装置依存知識が必要になる。例えば大域メモリ（global memory）から共有メモリ（shared memory）へどの形のタイルを運ぶか、どの要素を各スレッドへ割り当てるか、メモリバンク競合をどう避けるか、Tensor Core向け命令へどう落とすか、データ転送と行列積を何段のソフトウェアパイプラインで重ねるかを調整しなければならない。

TritonのようなGPU用ドメイン固有言語（domain-specific language, DSL）はこの負担を大きく下げたが、TileLangはさらに「計算のデータ流」と「スケジュール空間」を明示的に分ける。利用者はT.copy、T.gemm、T.reduceのようなタイル演算で計算論理を書き、必要に応じてタイル形状やパイプライン段数を指定する。コンパイラ側がレイアウト推論、スレッド束縛、ハードウェア命令へのテンソル化、ソフトウェアパイプライン化を組み合わせて低レベルGPUコードへ下げる。

この設計は「全部自動で最適化する」ことよりも、通常は自動化しつつ、性能専門家が必要な箇所だけ低レベル制御へ降りられることを重視する。評価ではNVIDIA H100/A100、AMD MI300XなどでFlashAttention、Mamba-2の線形注意、GEMM、量子化行列積、多頭潜在注意（multi-head latent attention, MLA）を実装し、手書きまたは高度に最適化された実装に近い、あるいは一部で上回る性能を示す。

## 問題設定

### 高性能カーネルではデータ流と実行スケジュールが絡み合う

例えば行列積は「AとBを読み、積をCへ加算する」と書くだけなら短い。しかし実GPUでは、大域メモリから共有メモリへタイルを運び、共有メモリからレジスタへ配置し、Tensor Coreが要求する形へ断片を割り付ける必要がある。さらに次のタイルを先読みして、現在のタイルの演算と転送を重ねないとメモリ待ちが残る。

これらをCUDAで直接書くと性能は出しやすいが、コードが装置世代と命令へ強く結び付く。一方、抽象化し過ぎると、FlashAttentionのようにメモリ階層や非同期命令を細かく使うカーネルを十分表現できない。TileLangはこの中間を狙う。

### 「タイル」を共通単位にする

タイルとは、大きなテンソルをGPUがまとめて処理しやすい小ブロックへ切ったものを指す。TileLangではロード、行列積、還元、保存をタイル単位で書くため、計算の意味とGPUの局所データ再利用を同じ抽象単位で扱える。

そのうえで「このタイルをどのスレッドへ割るか」「どのメモリ配置を使うか」「どの命令へ変換するか」はスケジュールとして分離する。これがTileLangの中心的な設計である。

## コンパイルとスケジュール

### 1. タイル演算でデータ流を記述する

利用者はPython風の前段言語で、カーネル境界、共有メモリ/レジスタ断片の確保、T.copy、T.gemm、T.reduceなどを記述する。例えばGEMMなら、A/Bのタイルを共有メモリへコピーし、T.gemmで局所結果へ積算し、最後に出力へ戻す。

前段コードは構文木を経てTVMの中間表現（intermediate representation, IR）へ変換される。そこからTileLang固有の最適化パスがレイアウト、スレッド束縛、パイプライン、ハードウェア命令を具体化し、CUDAまたはHIP系コードへ落とす。

### 2. レイアウト推論とスレッド束縛

難所の一つは、各バッファ要素をどのスレッドのレジスタへ持たせるかである。TileLangは演算ごとの制約強度を使ってレイアウトを推論する。Tensor Coreを使うGEMMは厳しい配置制約を持つ一方、要素ごとの加算は自由度が高い。そこで制約の強い演算から順にレイアウトを決め、その結果を共有バッファへ伝播する。

論文の例では、GEMM出力Cのスレッド配置が先に決まり、その後Cへ加えるバイアスDの配置を、同じスレッドが必要要素へアクセスできるよう推論する。コピー演算についても、推論後にループをスレッド並列化・ベクトル化し、さらにレイアウト入替え（layout swizzling）で共有メモリのバンク競合を避ける。

つまり利用者が「各要素をthreadIdx.xの何番へ置くか」を逐一書かなくても、タイル演算間の制約から実行配置を導く。

### 3. 高性能命令へのテンソル化

同じ計算でもGPUには複数の実装命令がある。TileLangはタイル演算をTensor Coreや装置固有命令へ写すテンソル化（tensorization）を扱う。既存のTile LibraryやCUTLASS/CUTE等へ接続する経路と、TileLang内部で命令実装を直接記述する経路を持つ。

前者は新しい装置への対応が速い一方、外部テンプレートへ依存する。後者はコンパイルやレイアウト制御の自由度を上げられるが、対象命令ごとに実装を用意する必要がある。論文時点では迅速な対応のためライブラリ利用を既定としている。

### 4. ソフトウェアパイプラインを依存関係から生成する

高速GEMMや注意では、次のデータを共有メモリへコピーしている間に現在のタイルを演算する必要がある。TileLangはCopyとGEMMなどの計算ブロック間の依存を解析し、正しい順序を保ったまま転送と演算を重ねるパイプラインを生成する。

利用者は基本的に段数num_stagesを指定すればよく、Ampereでは非同期コピー（asynchronous copy）のcp.async、Hopperではより新しい転送・Tensor Core命令へ下げられる。一方、特殊なカーネルでは利用者が順序や段を明示することもできる。

### 5. 自動化と手動制御を両立する理由

完全自動化だけでは、まだコストモデルが学習していない新演算や特殊データ型で性能を引き出しにくい。完全手動では開発費が高い。TileLangは、データ流は簡潔に書き、一般的なレイアウト/並列化/パイプラインは推論し、必要な箇所だけ専門家が上書きできる構造にすることで両極端を避ける。

### 評価条件

| 項目 | 条件 |
| --- | --- |
| 主なGPU | NVIDIA H100 80GB、NVIDIA A100 80GB、AMD Instinct MI300X 192GB。GEMM比較ではRTX 4090も使用 |
| ソフトウェア | H100はCUDA 12.4、MI300XはROCm 6.1.0、Ubuntu 20.04 |
| カーネル | FlashAttention、Mamba-2 chunk-scan/chunk-state、GEMM、MLA、逆量子化GEMM |
| 比較対象 | FlashAttention-3、Triton、PyTorch、cuBLAS、rocBLAS、FlashMLA、FlashInfer、Marlin、BitsandBytesなど |
| 評価軸 | カーネル遅延/高速化、ベンダーライブラリ比、コード行数、GPU間の移植性 |
| 実行形態 | 実GPU上のカーネルベンチマーク。モデル全体のE2E推論評価ではない |

### 主要結果

| カーネル・装置 | 比較対象 | TileLang | 差 | 意味 |
| --- | --- | --- | --- | --- |
| FlashAttention / H100 | FlashAttention-3 | 1.36倍高速 | 小系列で特に優位、8k級では近い性能 | 固定タイルの手書き実装より形状へ適応できるケースがある |
| FlashAttention / H100 | Triton / PyTorch | 1.41倍 / 1.70倍高速 | 一貫して高速 | 高水準DSLでもHopper固有パイプラインを引き出せる |
| Mamba-2 chunk-scan / chunk-state | Triton | 平均1.77倍 / 2.10倍高速 | 線形注意でも改善 | 注意以外の状態空間系カーネルにも適用できる |
| GEMM / RTX4090, A100, H100, MI300X | ベンダーBLAS | 1.10倍 / 0.97倍 / 1.00倍 / 1.04倍 | 概ね同等 | 汎用DSLで手調整ライブラリ級の行列積性能 |
| GEMM / 同4 GPU | Triton | 1.08倍 / 1.03倍 / 1.13倍 / 1.25倍 | 全環境で上回る | NVIDIA/AMD双方でスケジュール表現が有効 |
| MLA / H100 | Torch | 1075.9倍高速 | FlashMLA性能の最大98% | Torch基準の巨大倍率より、手書きFlashMLAへ98%到達した点が実用上重要 |
| MLA / MI300X | Torch | 129.2倍高速 | 手書きAITER性能の95% | AMDでも同じ抽象化を移植できる |

MLAの「Torch比1000倍超」はTorch側が高度最適化された専用基準ではないため、単独の見出し値として読むと誤解しやすい。より意味のある比較は、H100で手書きFlashMLAの最大98%、MI300XでAITERの95%へ達している点である。

## 既存研究との差

Tritonもタイル指向のGPUプログラミングを提供するが、TileLangはメモリ階層のバッファ、レイアウト、スレッド束縛、パイプラインをより明示的に構成できる。論文は、Tritonの簡潔さを保ちつつ、専門家がメモリ配置や特殊命令へ降りられる範囲を広げることを狙っている。

ThunderKittensのようなテンプレート中心方式と比べると、TileLangはPythonだけでカーネル全体を記述し、通常のパイプライン化などをコンパイラへ任せられる。一方で必要なら明示的なスケジュールも書けるため、「高水準DSL」対「手書きテンプレート」という二択を避けている。

## 限界・実装状況

TileLangは任意の新演算を完全自動で最適化する自動スケジューラではない。高性能を得るにはタイル形状や段数などの選択が依然重要であり、論文も動的形状向けタイル選択やより良いコストモデルを今後の課題に挙げる。

また一部の組み込み演算はCUTLASSや手書きCUDA/HIPラッパへ依存しており、著者らはTileLang自身でTile Libraryを構築してこの依存を減らすことを今後の方向としている。CPUやNPUなどGPU以外への一般化も将来課題である。

評価はカーネル単位が中心なので、特定LLMのE2E推論で同じ高速化率がそのまま得られるとは限らない。対象カーネルが全実行時間のどれだけを占めるかでモデル全体の利得は変わる。

公式実装は https://github.com/tile-ai/tilelang で公開されている。
