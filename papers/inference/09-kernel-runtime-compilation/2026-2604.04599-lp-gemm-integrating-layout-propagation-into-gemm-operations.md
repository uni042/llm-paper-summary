# LP-GEMM：連続行列積の中間配置を伝播して詰め替えを削減する

## 概要と研究対象

LP-GEMMは、一般行列積（General Matrix Multiplication; GEMM）を1回ずつ最適化するだけでは、複数の行列積を直列に実行する際に冗長なメモリ再配置が発生する問題を扱う。OpenBLASなどの数値線形代数ライブラリは、個々の行列積の実行前に行列を演算しやすいブロック配置へ詰め込み、終了後に呼出元が期待する標準配置へ戻す。ところが次の行列積が直前の出力を入力として受け取ると、標準配置へ戻した直後に同様の詰め込みを再実行することになる。

著者らは、行列積の境界で中間表現を標準配置へ戻すという前提を緩め、最初の行列積で生成した詰め込み配置を後続の行列積へ引き継ぐ。これを初期（ini-GEMM）、中間（mid-GEMM）、終端（end-GEMM）の3カーネルで実現し、最終的な外部可視出力だけ標準配置へ戻す。x86とRISC-VのCPUでOpenBLASなどと比較し、特に短い系列の注意層や連続行列積で高速化を確認した。

論文の対象はCPUの行列積と注意層である。Llama-3.2-1Bを用いた検証は、PyTorchから重みと中間結果を取り出してC++の注意層実装と比較する形であり、実運用のGPUサーバや大規模LLMのエンドツーエンド生成速度を直接測定した研究ではない。この境界は適用判断に重要である。

## ボトルネック：BLASの境界が強制する再配置

GEMMは `C = αAB + βC` を計算する。高速な実装では、行列をキャッシュやレジスタの大きさに合わせてタイルへ分割し、各タイルの要素を連続するバッファへ並べ直す詰め込み（packing）を行う。小さなマイクロカーネルがレジスタ内の積和演算を行い、結果を所定の行列配置へ書き戻す。これは単発のGEMMでは合理的だが、`C=AB; E=DC` のような連続処理ではCの書戻しと再詰め込みが不要になり得る。

従来のBLAS呼出しでは各演算の入出力が呼出元に見えるため、内部配置を勝手に維持できない。LP-GEMMは「途中のGEMMが返す値は内部配置のまま」という新しい呼出し規約を設け、連鎖の外側だけ標準配置へ合わせる。最終的な数値の意味は保持しつつ、途中のメモリ移動を省く。ここでの改善は乗算回数を減らすものではなく、同じ積和演算に付随する読み書きと並べ替えを減らすものである。

著者らは、入力の詰め込み配置、計算順序、結果の保存配置という三つを区別する。通常のGEMMではマイクロカーネルの計算順序と標準保存配置が異なるため、結果の並べ替えが必要になる。LP-GEMMでは、計算で生じたブロック順序をそのまま次の入力配置として利用できるよう、これらを一致させる。行列を転置して表す形式を採用し、出力側のタイル順序が次のGEMMの乗数側に合うよう設計する。

## 手法

### 三つのカーネルと処理順

### 初期カーネル：詰め込み配置を確立する

最初のini-GEMMは、通常のOpenBLASとほぼ同じように入力をタイルへ詰め込んで計算する。ただし結果を標準配置へ戻すマイクロカーネルではなく、伝播用マイクロカーネルで保存する。入力は元の通常行列、出力は次のGEMMが直接読める内部配置の行列である。最初の詰め込み自体は残るため、単発GEMMでの性能はOpenBLASに近い。

### 中間カーネル：入力の再詰め込みを省く

mid-GEMMは前段がすでに詰め込み配置で出力した行列を受け取り、乗数側の再詰め込み処理を省略する。元のOpenBLASのループのうち不要な詰め込み処理を取り除き、マイクロカーネルの結果を次段に適した順序で書く。二段以上の連鎖では、この処理を必要な回数だけ繰り返せる。単純な二つのGEMMなら初期と終端だけでよく、中間は三つ以上のGEMMで使用する。

この省略は単なるバッファの再利用ではない。後続の演算が要求するタイルの並び、行列の転置、読み出しストライドをそろえることが前提である。配置が異なる入力を誤ってmid-GEMMへ渡すと、値の意味が壊れるため、呼出側が配置を追跡する必要がある。

### 終端カーネル：標準配置へ復帰する

end-GEMMはmid-GEMMと同じように既に詰め込まれた入力を消費するが、最終出力だけ標準配置に戻すマイクロカーネルを使う。したがって外部から見える演算連鎖の出力は通常のGEMMと同じ意味になる。途中のini/midは厳密には標準BLAS API互換ではない点を著者ら自身が明記しており、「既存BLASを変更せず差し替えられる」という意味ではない。

### 配置の制約と未対応の境界条件

論文では、前から値が入っているCに `βC` を加える場合、そのCも伝播用配置に詰め直す必要があると述べる。この特殊ケースへの完全対応は実装していない。さらに、非連続領域や行列の一部分を演算するため、保存するブロック順序とストライドを指定する追加引数を設ける。つまり、数学的なGEMM一般の意味と、今回のLP-GEMM実装がサポートする呼出し条件は区別する必要がある。

### 注意層への組込み

実際のTransformerでは行列積が純粋に連続するわけではない。Q・K・V投影の間にヘッド分割、回転位置埋め込み（Rotary Position Embedding; RoPE）、注意スコアの正規化（Softmax）、スケーリング、出力投影が挟まる。これらが内部配置を理解しないと、行列積だけ高速化しても中間変換の費用で相殺される。

著者らはLlama-3.2-1Bの注意層を模したC++実装を用意し、PyTorchから重み、乱数入力、各段階の中間結果を出力して数値の整合を照合した。Q・K・Vをヘッドごとに分けて扱う際のストライドは入力次元とヘッド幅から決められるため、コンパイル時に計算可能な形へ調整する。RoPEはヘッド内の行ごとに回転するため伝播配置へ比較的自然に適合するが、Softmaxは行方向の総和を必要とし、タイル境界で非連続アクセスが発生する。そこで複数行をまとめて処理する形へ変更し、配置変換を追加せずに演算する。

この手法は注意層全体を一つの巨大な融合カーネルへ閉じ込めるわけではない。中間のRoPEやSoftmaxを伝播配置に対応させ、独立したGEMMカーネル間でレイアウトを共有する点に特徴がある。ただし、Softmaxのように行全体を横断する処理は伝播配置と相性が完全には一致せず、追加のアドレス計算費用が残る。

## 評価

### 評価条件

| 項目 | 原著で確認した設定 |
|---|---|
| x86 CPU | Intel Xeon Gold 6252、AVX-512、3.6GHz、L1 32KiB、L2 1024KiB |
| RISC-V CPU | Banana Pi BPI-F3、SpacemiT K1/X60、RVV 1.0、1.6GHz、L1 32KiB |
| 実行方式 | 両環境とも単一スレッド。スレッド並列化の効果を含めない |
| 主比較対象 | OpenBLAS。追加比較にBLIS、x86のみIntel MKL・oneDNN・FlashGEMM |
| 単発GEMM | gemmbench由来の行列サイズ、各構成10回の平均から比較 |
| 注意層 | Llama-3.2-1Bを模したC++実装、埋め込み次元2048、MLP重み次元8129 |
| 注意層の反復 | 各構成50回の類似実行の平均 |
| 注意層の系列長 | 主に500トークン以下。長文脈・大規模バッチの検証ではない |
| 連続GEMM | DNN由来の3段GEMMベンチマーク。OpenBLAS・FlashGEMMと比較 |
| 指標 | 各処理の実行時間から算出したOpenBLAS基準の高速化率 |

単一スレッドと500トークン以下という条件は、GPU上で大きなバッチの長文脈LLMを生成する環境と大きく異なる。本文の「注意層で最大約2倍」は、このCPU上の注意層を模した比較の結果であり、GPU推論サービス全体の改善率ではない。

### 主要結果とその読み方

| 評価 | 比較対象 | 報告結果 | 結果の意味 |
|---|---|---|---|
| x86の連続GEMM | OpenBLAS | 平均約2.25倍高速化 | 行列積間の詰め替え削減が寄与 |
| 単発GEMMのmid/end | OpenBLAS | 高速化率の中央値約1.5倍、上位四分位は2倍超 | 入力詰め込み省略の効果が大きい |
| 単発GEMMのini | OpenBLAS | おおむね同程度 | 初段には詰め込み費用が残る |
| x86の注意層 | OpenBLAS | 小さい入力で最大約2倍 | 短系列で詰め替え費用が相対的に大きい |
| x86のMLP部分 | OpenBLAS | 高速化率はおおむね1.1倍前後 | 大きい重み行列の演算費用が支配的 |
| RISC-Vの注意系 | OpenBLAS | 条件により最大約5倍と記載 | ベースラインの出力再配置が遅いことも利得に寄与 |
| 3段GEMM | OpenBLAS、FlashGEMM | 多くの構成で双方より高速 | 融合しない配置伝播でも利得がある |

最も重要な観察は、行列サイズが増えるほど詰め替えの相対的な重要性が低下することである。おおまかに、行列要素の移動は二次、行列積の演算量は三次に増えるため、計算が支配的な大行列では詰め替えを削減しても速度向上が限定される。逆に小さな行列や短い系列では、演算そのものよりメモリ配置の処理が占める割合が大きくなる。

RISC-Vの大きな改善率は、提案方式だけの一般的な優位性として扱うべきではない。原著は、比較対象のOpenBLASのRISC-Vカーネルが出力を不連続に書き戻す実装上の非効率を持ち、その回避が高速化の大きな要因だと説明する。別の最適化済みBLASを基準にすれば、同じ倍率が得られる保証はない。x86ではIntel MKLやoneDNNの単発GEMMがLP-GEMMを上回る条件もあり、LP-GEMMの利点は個別のマイクロカーネルを極限まで高速化したことではない。

三段連続GEMMの比較でも、最初のini-GEMMが実行時間の大半を占めるため、後段で詰め替えを省けても利得には上限がある。これに対し長い連鎖でmid-GEMMの回数が増えれば、詰め替え削減の機会は増えるが、そのまま線形に高速化が伸びるとは限らない。演算サイズ、入力配置、非線形処理の有無、キャッシュ容量を含めた評価が必要である。

## 既存研究との相違

OpenBLASとMKLは通常、独立した行列積の性能を最適化する。LP-GEMMは演算列を見て中間の配置を伝播するため、最適化単位が個別GEMMから演算連鎖へ移る。oneDNNやNeoCPUにも配置伝播の考え方はあるが、演算グラフを解析して配置や変換境界を決める側面が強い。LP-GEMMは最初の行列積そのものに初期変換を組み込み、GEMMの入口と出口のカーネルを分けることで、明示的な再配置を減らす。

FlashGEMMは複数GEMMの融合で中間データ移動を削減するが、融合対象の間にRoPEやSoftmaxなどの非GEMM処理があると、追加実装が必要になる。LP-GEMMは融合を前提とせず、中間演算が伝播配置を理解できればGEMMの境界をまたいで配置を保持する。この差は注意層への組込みで特に重要である。ただし、配置を追跡する仕組みと追加引数を呼出側が扱う必要があるため、統合費用がゼロではない。

## 適用範囲と限界

本研究の高速化は、CPU単一スレッド・特定のOpenBLAS実装・小規模注意層という条件で確認された。CUDAカーネル、GPUのテンソルコア、複数GPU間の通信、推論サーバのバッチ処理、KVキャッシュの長期保持、数千〜数万トークンの注意計算は主たる評価対象ではない。RTX 4070 SuperなどのGPUへ直接同じ倍率を当てはめることはできない。適用対象は、CPUで小さなGEMMを連続実行する推論経路や、独自のBLASカーネルを組み込める軽量な実行系である。

内部の伝播配置を維持するini/midは通常のBLAS出力規約を満たさない。外部の演算やライブラリへ結果を渡す時点でendによる標準配置への復帰が必要であり、その境界が頻繁に現れると利得は減る。また、`βC` が非ゼロで事前のCが存在する場合の一部の配置処理は未対応である。著者らは機能同等性を検証したが、すべてのBLAS呼出し形式へ透過的に適用できるわけではない。

短系列の注意層で最大2倍という結果は、MLP部分の約1.1倍とは異なる。LLM全体では注意層とMLPの時間割合に応じて総合改善率が決まり、注意層だけの倍率を全体へ掛けることはできない。逆に、推論をCPU上の小バッチで実行し、各層の詰め替えが目立つ環境では、低ビット量子化や演算器の強化とは別の改善軸として検討できる。
