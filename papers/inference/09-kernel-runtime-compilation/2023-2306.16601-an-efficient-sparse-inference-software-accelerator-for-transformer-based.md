# An Efficient Sparse Inference Software Accelerator for Transformer-based Language Models on CPUs

> 4x1ブロック疎性とINT8を前提に、VNNI向けJIT生成SpMMカーネルでCPUの疎なトランスフォーマー推論を高速化するスタック。既存疎ライブラリを1桁上回り、密GEMM比でも最大5倍。

## 概要

トランスフォーマーの推論を速くするために重みを枝刈りして疎にしても、実行するソフトウェアが疎な計算を効率よく処理できなければ、実速度は出ない。特に産業用途の推論は今も多くがCPUで動いているが、既存の疎行列ライブラリは32ビット浮動小数点中心で、ブロック形状も2x2のような正方形が前提であり、量子化と疎性を組み合わせたモデルを速く回す受け皿がなかった。

本論文は、疎性パターン、カーネル、推論フレームワークを一体で設計したソフトウェアスタックを提案する。重みは4要素を1ブロックとする4x1の構造化疎性で枝刈りし、さらにINT8へ量子化する。カーネルは、Intelのベクトルニューラルネットワーク命令（Vector Neural Network Instructions; VNNI。8ビット整数の積和をまとめて行う命令）に合わせて即時コンパイル（JIT）で生成する疎行列・密行列積（SpMM）カーネルであり、疎な線形演算へ後段の演算子を融合する仕組みと組み合わせる。代表結果として、90種類の行列形状と疎性率70から90パーセントの条件で、既存の疎ライブラリoneMKLやTVMを1桁上回り、密行列用のoneDNNに対しても最大5倍の性能を示した。モデル単位では、BERT系の疎モデルでNeural MagicのDeepSparseへ同一Xeon上で最大1.5倍、ONNX Runtimeへ最大37倍、PyTorchへ最大345倍の高速化を、製品利用を想定した遅延制約の下で実測している。

## 問題設定

疎な推論がCPUで速くならない理由は3つある。第1に疎性パターンの不一致である。非構造化疎性はゼロの位置が不規則でメモリアクセスが乱れ、2:4のようなパターンは対象CPUの命令に対応していない。第2にデータ型である。oneMKLの疎GEMMはFP32のみで、INT8の積和命令を使えないため、量子化した疎モデルの利得を受け取れない。第3に周辺演算の費用である。注意機構にはバイアス加算や活性化などの小さな演算が多く、疎な線形演算だけ速くても、メモリ往復を伴う後段演算が全体を引っ張る。本論文は、命令が最も効率よく動くブロック形状から疎性パターンを逆算し、カーネルと融合と量子化をその前提で揃えることで、この3点を同時に解く。

そもそもCPUを狙う理由は、産業界の推論の大部分が今もCPUで実行されているという現実にある。GPUは学習と大規模な生成で中心的な役割を持つが、既存の業務システムへ組み込まれた推論、遅延の制約が厳しい分類や検索の処理、クラウドの汎用インスタンスで動くサービスでは、CPUが依然として主要な実行環境である。ところがフレームワークや推論ツールキットは密なモデルを前提に作られており、疎なモデルを受け付けても最適化できない。疎性の研究がGPU向けに偏る中で、CPU側の実行基盤が空白だったことが、本論文の出発点である。疎モデルを作る側の研究（どの重みを落とすか）と、実行する側の研究（落とした重みをどう速く計算するか）は本来一体であり、片方だけが進んでも製品の遅延は改善しない。本論文は実行側を正面から扱い、しかも疎モデルの作り方まで含めて一貫した条件で測っている。

## 手法のあらまし

まず重み行列を4x1ブロック単位で枝刈りし、疎性率80から90パーセントの疎モデルを作る。作り方は2通りあり、密な事前学習モデルから下流タスクの微調整中に枝刈りする方法と、疎な事前学習モデルのパターンを固定して微調整する方法である。次にIntel Neural Compressorで精度を監視しながらINT8へ量子化する。推論時は、疎な重みと密な入力の積をJIT生成のSpMMカーネルが担い、注意機構の線形演算を疎版へ置き換え、後段演算を融合する。ランタイム側ではバッファ再利用を最大化するメモリ割当と、並列インスタンス間での重み共有でオーバーヘッドを抑える。

## 手法

### 1. 4x1疎性パターン — VNNIの命令形状に合わせる

ブロックの縦の大きさ4は、VNNI命令が4組の8ビット整数ペアをまとめて処理する構造から決まる。非ゼロの重みブロックをブロードキャストしてVNNI形式のブロックを作り、入力側は重みのマスクに合わせてAVX512の置換・シャッフル命令で並べ替えてもう1つのブロックを作り、両者をVNNIへ流して積和する。2x2のような正方ブロックはメモリアクセスが不連続になりやすく、N:Mパターンは対象命令に対応しないため除外した。パターンが命令と一致するおかげで、疎性率が高いほど飛ばせる計算がそのまま速度へ変換される。代償として、疎性の次元が4で割り切れない場合はパディングが必要になる。

### 2. JIT生成SpMMカーネル — 形状ごとに機械語を組み立てる

カーネルは、行列形状ごとにJITで機械語を生成する。疎な重みは推論中不変なので、必要な疎インデックスを実行前に読み込んでおくことで、実行時の経路決定の費用を省ける。タイリングはN方向に64を既定とし、形状ごとにオフラインで調整できる。マルチスレッド化は、重み行列をN方向のブロック列へ再配置し、ブロック列単位でスレッドへ割り当てることで、コア間の余分な通信を避けながら、1スレッドから4スレッドまでほぼ線形に近い拡大を示した。入力の並べ替えは実行時に行うため、疎性パターンが変わっても同じ枠組みで対応できる。

### 3. 疎な注意と演算子融合 — 後段演算のメモリ往復を消す

注意機構の線形演算を疎版へ置き換えただけでは、バイアス加算、形状変更、GELU、和、量子化といった後段演算が残り、それぞれがメモリとの往復を生む。本論文は計算グラフを深さ優先でたどり、要素ごと演算・二項演算・形状操作の3種を線形演算の後段チェーンとして融合する。要素演算はレジスタ内のデータを再利用して実行し、低精度の要素演算については、入力が0から255の範囲しか取らないことを利用して、演算チェーン全体の結果を事前に計算した参照表（ルックアップテーブル）で置き換える。これにより疎化で減らした計算が、周辺演算の費用で相殺される事態を防ぐ。

### 4. フレームワーク側の最適化 — 割当とスレッド管理

演算子レベルでは密な演算にもJITカーネルを用意し、形状が同じなら最初に生成したカーネルをキャッシュして再利用する。ランタイムでは、要求のたびに新しいバッファを作る既定の割当をやめ、再利用を最大化する専用アロケータと、並列実行される複数インスタンスで重みの単一コピーを共有する仕組みを実装した。これらは地味だが、遅延制約のある製品条件ではカーネル性能と同じくらい効く。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 4x1疎性パターン | 重み行列 | 4要素ブロック単位で枝刈りしVNNIの処理単位と一致させる | 疎計算の命令効率 | 4で割り切れない形状にパディングが要る |
| JIT SpMMカーネル | 疎な重みと密な入力 | 形状ごとに機械語を生成し、入力をマスクに合わせて並べ替える | 疎GEMMの実行時間 | 初回生成の費用（キャッシュで償却） |
| 演算子融合と参照表 | 線形演算の後段演算 | グラフ探索で融合し、低精度要素演算は事前計算表で置換 | メモリ往復と起動費用 | 融合パターンの事前定義が必要 |
| ランタイム最適化 | バッファ要求と並列インスタンス | バッファ再利用と重み共有 | 割当費用とメモリ使用量 | 実装の複雑さ |

## 評価

### まず見るところ

- **結論:** 疎性パターンを命令形状に合わせると、CPUでも疎推論が密推論を明確に上回る。カーネルで1桁、モデルでも既存ソリューションを大きく上回る差が実測された。
- **速度・効率:** カーネル単体では既存疎ライブラリ比で幾何平均10倍超、oneDNNの密GEMM比でも疎性率90パーセントで幾何平均3.6倍である。
- **品質:** 近似手法だが、疎性率80から90パーセントで精度低下は1パーセント以内に収まるよう疎モデルを構築している。
- **評価の強さ／注意点:** 対象はBERT系のエンコーダモデルで、生成型の大規模言語モデルやデコーダの逐次生成は評価していない。比較の一部はXeon対EPYCという異なるインスタンス間の数値を含む。

**数値の読み方。** 最大値と幾何平均を分けて読む必要がある。ONNX Runtime比345倍という数字は、Xeon対EPYCのインスタンス差と、相手側が疎モデルを最適化できない条件が重なった最大値であり、同一条件の幾何平均では6倍から17倍程度である。一方、カーネル単体の幾何平均で10倍超という値は、条件を揃えた比較でも1桁の差が残ることを示し、こちらが方式の実力を表す。

論文の考察では、比較対象ごとの性格も分析されている。oneMKLは追加の調整なしに疎カーネルを動かせる手軽さで最も優れる一方、TVMはAVX512への最適化が十分でなく全体に低調であり、LIBXSMMは小さい行列積では強いが構造化疎性に対応しない。密側のoneDNNは広い形状で安定した性能と良好なスレッド拡大を示す。つまり提案カーネルの優位は、単に実装が新しいからではなく、対象とする形状・データ型・疎性パターンの組み合わせが既存ライブラリの想定から外れていたために生じた空白を埋めた結果と読める。また疎性率を70から90パーセントまで5刻みで変えた測定では、DistilBERT、BERT-Base、BERT-Largeで性能がほぼ線形に伸びる一方、BERT-Miniでは一部の形状でスレッドとタスクの割り当てが不均衡になり負の拡大が見られたことも正直に報告されている。小さいモデルでは並列化の粒度そのものが律速になるという、実務で効く知見である。遅延制約なしの最大スループットと最小遅延でも、ほぼ全ての構成で提案スタックが他方式を上回ったとされる。

## 既存研究との差

CPU向けの疎推論ではSparseDNNやNeural MagicのDeepSparseが先行し、疎GEMMライブラリとしてはoneMKL、TVM、LIBXSMMがある。しかしoneMKLはFP32のみで正方ブロック前提、LIBXSMMは構造化疎性に対応せず、フレームワーク系は疎モデルを最適化できない。本論文の差分は、VNNIの処理単位から逆算した4x1パターンを定義し、INT8量子化と組み合わせ、JITカーネル・演算子融合・ランタイム最適化までを一体のスタックとして実装し、公開したことにある。先行する実行系とのもう一つの違いは、疎モデルの作り方まで含めて条件を公開している点である。疎性率、精度の落ち幅、学習の手順が表として示されているため、利用者は自分のモデルで再現する際の目安を持てる。実行系の性能はモデルの作り方に強く依存するので、この透明性は単なる親切ではなく、結果の解釈に必要な情報である。特に、疎な事前学習モデルから始める方法と、密なモデルから微調整で疎にする方法の両方が示され、精度の差が小さいことが確認されている点は、既存の資産へ適用する際の判断材料になる。

## 限界・実装状況

対象ハードウェアはIntel Xeonが中心で、他アーキテクチャへの展開は今後の課題として挙げられている。著者らは将来の方向として、他の計算機アーキテクチャへの対応と、クラウドでの費用対性能の観点からの比較を充実させることを挙げている。費用の観点は、同じ遅延でも資源の単価が違えば最適な構成が変わるため、実務の選択では性能そのものと同じくらい重要である。評価モデルはBERT系に限られ、数十億パラメータ級の生成モデルでの検証はない。また疎モデルの作り方（微調整の手順）が性能と精度の前提になっており、任意の学習済みモデルへ即座に適用できるわけではない。実装はIntel Extension for TransformersとしてGitHubで全ソースコードが公開されており、再現性は高い。

## 一般的な実装上の含意

疎性で速くしたいなら、パターンを先に決めてカーネルを合わせるのではなく、ターゲット命令が最も効率よく処理できる形状からパターンを決めるべきである。言い換えると、圧縮の形式は数学的な都合だけで決めるものではなく、実行する機械の得意な形に寄せて初めて意味を持つ。また、カーネル単体の高速化だけでは製品条件の遅延は改善しきれず、後段演算の融合やバッファ管理といった周辺の最適化がエンドツーエンドの差になる。最大値の倍率ではなく幾何平均で比較する姿勢も、実行系の評価では重要である。加えて、疎なモデルを作る側と実行する側を別々に最適化すると、せっかく作った疎性を実行系が活かせず、理論上の削減が壁時計の改善に結びつかない。疎性の粒度、データ型、並べ替えの責任範囲を、モデルの変換手順と実行系の契約として最初に固定し、両側がその契約に合わせて実装することが、再現性のある高速化につながる。遅延の制約がある製品では、平均の速さだけでなく、制約を超える頻度や最悪条件での振る舞いまで含めて評価すべきであり、本論文が遅延制約下のスループットを主指標に置いた姿勢は、その意味でも実務に近い。最後に、実行系の差は利用する計算資源の世代や構成で大きく変わるため、導入判断では自前の代表的な負荷で測り直すことが欠かせない。他者の公表値との差は、方式の差だけでなく、形状の選び方や調整の深さの差を含むからである。
