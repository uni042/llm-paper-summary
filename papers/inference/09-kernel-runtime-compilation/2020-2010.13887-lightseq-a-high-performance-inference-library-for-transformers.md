# LightSeq: A High Performance Inference Library for Transformers

## 概要

LightSeqは、Transformerの推論を汎用学習フレームワークから直接実行するときに生じる多数の小規模GPU演算、自己回帰探索の不要な候補処理、可変長系列に伴うメモリ割当を、推論専用のCUDA実装で削減するライブラリである。2020年に公開された研究であり、後年の大規模言語モデル提供基盤を直接評価したものではない。対象は機械翻訳、文章生成、分類などのTransformer系列で、PyTorchやTensorFlowで学習したモデルの推論配備を想定する。

中核は三つの独立した最適化である。第一に、行列積（GEMM）以外のバイアス加算・活性化・層正規化・残差処理などを粗粒度カーネルへ融合する。第二に、階層型自己回帰探索（HARS）で語彙全体を毎回確率計算・上位選択する代わりに、各ビームから上位候補を先に抽出し、候補集合だけを精密に再順位付けする。第三に、可変長系列でも最大形状を見積もって一時バッファを事前確保し、依存しない中間結果の領域を再利用する。

論文の機械翻訳評価ではTensorFlow比で最大14倍、当時のFasterTransformer比で最大1.4倍の高速化を報告する。T4上の半精度実行のプロファイルでは、TensorFlowの行列積が全時間の約24.5%であったのに対し、LightSeqでは87.0%となり、周辺の小演算と探索処理を削ることで主要演算へ時間を集中させている。一方、ビーム探索での小バッチ条件ではFasterTransformerが上回る例もあり、最大倍率が全条件に当てはまるわけではない。

## 問題設定とボトルネック

Transformerの自己注意と前向きネットワークは大きな行列積を含むが、その前後にはバイアス加算、活性化、層正規化、残差加算、テンソル形状変換、確率正規化などの演算が多数存在する。汎用学習フレームワークは任意のモデル構造や逆伝播を支援するため、これらを細かなGPUカーネルとして組み合わせることが多い。演算1回の計算量が小さくても、カーネル起動、GPUグローバルメモリへの中間結果書き込み、次の演算による再読み込みが積み重なる。生成時はこれを各出力トークンについて繰り返すため、推論時間に対する非行列積処理の割合が高くなる。

特にビーム探索では、各ビームが語彙数万の候補スコアを持つ。通常の処理は全候補に確率計算を適用してから上位候補を選び、その後ビームに対応する履歴・キャッシュを更新する。しかし最終的に採用されるのは少数のトークンだけであり、採用されない大部分の候補をGPUメモリへ書き出すことは無駄になりやすい。論文ではTransformer-baseの例で確率計算と上位選択が遅延の約30%を占めると指摘する。

もう一つの問題は入力系列と生成系列の長さが要求ごとに変わることである。固定形状を前提にした最適化コンパイラだけでは、各一時テンソルの大きさや生存期間が変化する要求を扱いにくい。要求のたびに個別確保・解放すると、割当費用だけでなく断片化やピーク使用量が増える。LightSeqは推論専用の既知の演算依存を使い、GPUカーネル融合・候補選別・一時領域再利用を組み合わせる。

## 手法

### 1. 行列積間の小演算を融合するCUDA実行経路

入力のトークン埋め込みから注意演算、前向きネットワークまでを、cuBLASによる一般行列積と独自CUDAカーネルの組合せで実行する。Transformerの注意部分ではQ・K・Vの線形変換、スコア行列、確率正規化、値ベクトルとの積、出力射影を扱う。これらの大きな行列積はcuBLASへ任せる一方、行列積の間にある形状変更、バイアス、活性化、正規化、残差のような要素演算を可能な範囲で融合する。入力と出力の依存関係を保ちながら、一時結果をGPUグローバルメモリへ繰り返し書き出す回数を減らす設計である。

具体例として、TensorFlowの層正規化は平均と分散を計算する還元演算と最終変換のために複数のカーネル起動・中間結果を必要とする。LightSeqでは専用カーネル1回にまとめ、途中の平均・分散を独立したグローバルメモリ配列として残さない。論文のTransformerエンコーダ層では、6個の独自カーネルと6個のGEMMへ整理され、一般的な細粒度実装に比べてカーネル数を4分の1程度以下にする。

この機構が効くのは、各小演算のGPU起動と中間メモリ転送が無視できない場合である。逆に行列積自体が支配的になった後は、小演算の融合だけでさらに大きな高速化を得る余地は小さくなる。新しい注意方式や活性化を追加すると専用カーネルの保守が必要になるため、汎用性との交換条件がある。

### 2. 階層型自己回帰探索（HARS）

ビーム探索では、各ビームの次トークンに対する語彙全体の対数スコアが入力となり、次時刻へ残す少数のビームとトークンが出力となる。通常は各ビームの全語彙について確率正規化を行い、その結果をGPUメモリへ保存し、全候補から上位を選択する。HARSはこれを「候補の粗い取得」と「少数候補の精密な再順位付け」に分ける。

候補取得段階では、各ビームの対数スコア列をビーム幅に応じた複数グループへ分割し、各グループの最大値を計算する。次にグループ最大値のうち最小値を閾値Rとし、Rを超えるスコアだけを候補としてGPUメモリへ残す。グループごとに最大値が少なくとも一つ存在するため、ビーム探索で必要な上位候補を含む集合を構成できる。論文の実装では取得を単一のカーネルで行い、数万語の候補を数十程度へ減らしてから従来の確率計算と上位選択を実行する。

最終的なビーム更新は粗い閾値だけで決めず、取得した候補に対して元の確率・系列スコアを用いて再順位付けする。これは候補集合の縮小によって中間確率配列やソート対象を減らす仕組みであり、単に語彙数を削って生成品質を変える近似手法とは異なる。ビーム幅やスコア分布によって候補集合の大きさは変わるため、利得は一様ではない。またビーム探索より計算の軽い上位k標本化・累積確率標本化では、HARSが削れる余分な処理自体が小さい。

### 3. 動的GPUメモリの事前確保と領域再利用

LightSeqは最大系列長などから中間テンソルの最大形状を事前に定め、サービス起動時に必要な領域を確保する。実行時に要求の長さが変わっても、毎回の個別GPU割当を避けられる。さらに、演算の依存グラフを調べ、同時に必要とならない中間結果には同じ物理メモリ領域を使わせる。例えば前段で使用を終えた一時領域を、後段の別演算の出力領域として再利用する。

入力は最大長・バッチなどの形状上限と演算間の依存関係で、出力は一時領域の共有配置である。論文は動的メモリの割当を8分の1程度に減らせると述べ、T4でTransformer-bigを最大8モデル同時に置ける例を示す。この例の条件はバッチ8、系列長256、ビーム幅4、語彙数3万である。8モデルという数値は無条件のGPU常駐可能モデル数ではなく、論文の指定構成に限定される。

最大形状を予約する方式は、要求長の上限が明確であるサービスに適する。上限を大きく設定しすぎると事前確保領域が膨らみ、極端な長さ変動や上限外の要求を扱う柔軟性が下がる。また、再利用できるのは依存が切れた一時結果であり、復号中に必要なキャッシュを勝手に上書きできるわけではない。

### 4. 学習済みモデルから推論サービスまで

利用者はPyTorchやTensorFlowで学習した重みを取り込み、LightSeqの対応するTransformer系推論経路へ変換する。モデルの前向き計算では行列積と融合カーネルを実行し、生成タスクではHARSまたは上位k・累積確率標本化などの出力探索を使い、動的メモリ再利用器が中間領域を管理する。分類、BERT系、GPT系、翻訳Transformerなど複数の構造に対応するが、任意の未知アーキテクチャを自動的に高速化する万能コンパイラではない。

三つの機構は異なる律速を狙う。演算融合は層内の小カーネル起動と中間メモリI/Oを、HARSは出力探索の語彙候補処理を、メモリ再利用は可変形状の割当・ピーク容量を削減する。GPUが行列積でほぼ埋まる条件ではHARSや融合の追加効果が小さくなり、逆に小バッチ・短系列で探索処理が相対的に大きい場合には利得が出やすい。

## 評価条件

論文はGPU上でのTransformer機械翻訳・生成を対象とし、最新の大規模言語モデルのオンライン同時要求負荷を測定したものではない。比較は同世代のTensorFlow、PyTorch、FasterTransformer v2.1を中心に行い、TurboTransformersは生成機能が限定的なため主要生成比較から除外している。

| 評価項目 | 論文の設定 | 比較・指標 |
|---|---|---|
| 機械翻訳 | WMT14英独翻訳、Transformer-base相当、語彙を各5万に分割 | TensorFlow、PyTorch、FasterTransformer。ビーム探索での推論速度 |
| GPU | NVIDIA Tesla P4およびT4 | P4は単精度、T4は半精度を中心に比較 |
| バッチ・系列長 | バッチ1〜128、系列長32・64などの複数組合せ | 条件別のTensorFlow比高速化率 |
| 生成 | ランダム初期化Transformerと試験用データ | 上位k=32、累積確率閾値0.75などの標本化処理 |
| GPU時間内訳 | T4で半精度と単精度の推論を計測 | GEMM、キャッシュ更新、層正規化、HARS、その他の時間比率 |
| メモリ収容 | Transformer-big、バッチ8、系列長256、ビーム幅4、語彙3万 | 動的領域の再利用と同時モデル収容数 |

本論文の速度評価は生成時のGPU推論経路を対象とし、ネットワーク越しの要求受付や分散配置、モデル読み込み時間、オンラインサービス全体の待ち行列時間を直接測っていない。評価のGPUは当時のP4/T4であり、後年のAmpere・Hopper世代へ同じ倍率を移す根拠にはならない。

## 評価結果

### 1. 演算融合後のGPU時間配分

| T4での内訳 | TensorFlow 半精度 | LightSeq 半精度 | LightSeq 単精度 |
|---|---:|---:|---:|
| 行列積（GEMM） | 24.5% | 87.0% | 82.0% |
| キャッシュ更新 | 個別計測値なし | 6.4% | 10.1% |
| 層正規化 | 個別計測値なし | 3.6% | 3.0% |
| 階層型自己回帰探索 | 個別計測値なし | 2.9% | 2.6% |

TensorFlowでは小カーネルや型変換、上位選択などが時間を消費し、行列積は全体の約4分の1だった。LightSeqではこれらの非行列積部分を削り、行列積の時間割合が半精度で87%、単精度で82%に達する。これは「行列積が以前より遅くなった」という意味ではなく、周辺処理が短縮された結果、残る実行時間の多くが本来の計算に充てられるという意味である。論文はTensorFlowの型変換・その他で80を超えるカーネル起動が生じる一方、LightSeqは型変換を重み読込へ融合することを示している。

キャッシュ更新の6.4〜10.1%は残存費用であり、層数・キャッシュ精度などの削減が将来の改善候補とされる。行列積が80〜90%を占める段階では、さらに周辺演算だけを融合しても速度向上余地は小さいという負の示唆も重要である。

### 2. 機械翻訳での比較

論文の図5では、P4とT4でバッチ・系列長を変えたTensorFlow比の高速化率を比較する。総括値はTensorFlow比最大14倍、FasterTransformer比最大1.4倍である。ただし最大値はすべてのGPU・バッチ・長さに共通する値ではない。小バッチ・短系列ではTensorFlowとの隔たりが大きく、専用実装の効果が強い。一方、同じ専用CUDA実装同士の比較では、ビーム探索で小バッチの一部にFasterTransformerが優位な条件があり、バッチや系列長が大きいほどLightSeqが優位になる傾向を報告する。

| 条件 | 観測・主張 | 解釈 |
|---|---|---|
| T4半精度の翻訳 | TensorFlow比最大約14倍 | 一般実行系の小演算・探索オーバーヘッドを削減 |
| 専用CUDA実装との比較 | FasterTransformer比最大約1.4倍 | 演算融合以外の探索・メモリ管理も寄与 |
| P4単精度 | T4半精度より相対高速化率が小さい傾向 | GPU性能・精度形式により律速が異なる |
| 小バッチの一部 | FasterTransformerがLightSeqを上回る | LightSeqが全条件で最速とは限らない |
| 大バッチ・長系列の一部 | LightSeqの優位が拡大 | 同期・探索・領域管理の費用差が残る |

元の論文図はTensorFlowを基準にした相対倍率を示す。個別条件の絶対ミリ秒値を論文本文の図から厳密に読めない箇所については、図にない数値を補完していない。後年の公式リポジトリで公開された性能表が存在しても、同じ実験版・同じモデル条件と確認できない限り、論文図の値と混同しない。

### 3. 標本化方式では高速化傾向が変わる

文章生成の上位k標本化と累積確率標本化については、論文図6がT4半精度での比較を示す。ビーム探索では候補系列の再順位付けが重いが、標本化では探索が単純で、HARSで省ける処理が少ない。そのため翻訳のビーム探索ほど大きな倍率にはならない。図6では多くの小バッチ・短系列条件でLightSeqがFasterTransformerを上回る一方、大バッチ・長系列では逆転する条件もある。翻訳の図5とは優劣が変わることが、アルゴリズムごとに最適化効果を評価する必要性を示す。

### 4. 動的メモリの収容力

論文は依存しない中間結果へ同じメモリを割り当て、動的領域の確保量を8分の1程度へ削減できると述べる。T4上でTransformer-bigを最大8モデル同時配置した例は、バッチ8、系列長256、ビーム幅4、語彙数3万の条件である。これはモデル重みそのものを8分の1へ圧縮した結果ではなく、実行時の中間テンソル用バッファを再利用した結果である。モデル重みの容量削減と、サービス内での一時領域共有は区別しなければならない。

## 既存研究との差

TensorFlow・PyTorchはモデル構造の柔軟性と学習支援を優先するのに対し、LightSeqはTransformer系列に対象を絞って専用のCUDA実行経路を作る。FasterTransformerもCUDAによる推論専用実装であり、比較上の本質は「CUDAを使うか」だけではない。LightSeqは層内の演算融合に加え、HARSによる生成探索の候補縮小と可変形状メモリの再利用を一つのライブラリで実装し、実行経路全体を改善する。

TurboTransformersは当時エンコーダや一部の復号層を中心とし、論文の生成比較に必要なビーム探索・キャッシュ更新などを同条件で提供できなかった。このためLightSeqが生成タスクで速いという主張を、TurboTransformersに対する公平な総合速度比較の結果としては扱わない。後年のLightSeqプロジェクトには学習や他モデル向けの機能が追加されているが、2020年公開論文の実験対象とは分けて記録する。

## 限界と適用範囲

本研究はNVIDIA GPUとCUDA・cuBLASを前提とし、CPUや異なるGPUバックエンドで同じ性能を示したものではない。専用カーネルは対応アーキテクチャの追加・保守費用があり、任意のTransformer変種や最新の注意演算を自動最適化するわけではない。最大形状の事前確保も、上限の読めない極端な可変長要求では予約容量と柔軟性の交換条件が生じる。

生成性能の中心はWMT14英独翻訳とランダム初期化Transformerによる標本化試験であり、現在の数百億パラメータ規模のモデル、混合専門家、ページ化鍵値キャッシュ、複数利用者の連続バッチ、プリフィル・復号分離などは評価していない。論文の最大14倍を現代のvLLMやSGLangに対する高速化率と解釈してはならない。ビーム探索の小バッチ条件ではFasterTransformerが上回り、標本化では比較傾向が変わるため、万能な高速化方式ではない。

GPU時間の大部分を行列積へ集中させた結果、残りの性能改善には行列積自体の最適化が重要になると論文は指摘する。これは演算融合の限界を示す結果である。またメモリ再利用で削るのは中間領域であって、モデル重みや全復号履歴の鍵値キャッシュを無条件に圧縮する方式ではない。実装の公開先は著者らの公式リポジトリで確認できるが、論文時点の実験環境と現行コードの機能を混同しない。
