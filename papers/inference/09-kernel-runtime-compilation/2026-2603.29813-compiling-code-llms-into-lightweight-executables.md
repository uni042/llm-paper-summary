# Compiling Code LLMs into Lightweight Executables

> ブロック単位のコードブック量子化と、行列ベクトル積をBLASへ置き換えるLLVMパスを組み合わせ、7B級コードモデルを一般的なノートPCで最大10.5倍速く、6.4倍小さいメモリで動かす枠組み。

## 概要

コード生成の支援はクラウド上の言語モデルを使う形が主流だが、秘匿性の高いコードを外部へ送る不安、応答の遅延、ネットワークへの依存という問題がある。開発者の手元のノートパソコンで動かせばこれらは解消するが、現実の壁は資源である。数十億パラメータのコード向けモデルは単精度で20から30GBを要し、一般的な16GBのメモリに収まらず、高性能なGPUも通常は搭載されていない。従来の研究はパラメータの削減やビット幅の低減といったモデル側の工夫が中心で、推論プログラムそのものの低水準な最適化は手付かずだったため、圧縮しても実行が速くならない場合があった。

本論文のDittoは、この問題をプログラム最適化の問題として捉え直す。第一の部品は量子化であり、重みをベクトルの集まりとみてクラスタリングし、代表値の表と低ビットの索引だけを保存することで、ディスクとメモリの両方を小さくする。第二の部品はコンパイル時の最適化であり、推論時間の8割超を占める行列ベクトル積の素朴なループを、LLVMの中間表現の水準で検出し、ハードウェア向けに調整されたBLASライブラリの呼び出しへ置き換える。出力は、対象モデルを実行する軽量な実行ファイルである。

**代表結果:** Apple M4、メモリ24GBの個人向け装置で、Code Llama、MagicCoder、OpenCodeInterpreterの各7B版を評価すると、Dittoはメモリを約26GBから4.1から4.2GBへ6.4倍減らし、推論速度を毎秒0.4から0.5トークンから3.5から4.7トークンへ最大10.5倍にし、エネルギーもトークンあたり36から45ジュールから3.8から5.1ジュールへ最大10.5倍減らした。品質はコード生成のpass@1で平均0.27パーセントの低下にとどまり、最大の低下でも1.83パーセントだった。8ビット量子化の比較対象に対しても、pass@1で最大6.96ポイント高く、最大2.2倍速く、メモリは1.6倍小さい。

## 問題設定

逐次生成では、トークンを1つ出すごとに重み行列全体をメモリから流し込む行列ベクトル積が必要であり、個人向け装置では計算能力よりもメモリ帯域と容量が律速になる。モデルがメモリに収まらなければそもそも動かず、収まっても素朴な二重ループの実装ではキャッシュの区切りやベクトル化や融合積和命令を使えず、ハードウェアの性能を引き出せない。つまり壁は二重であり、重みの表現を小さくすることと、残った計算を実行効率の高い形へ変えることの両方が要る。

既存の量子化研究は前者だけを扱い、推論プログラムの実装は利用者や手作業の調整に委ねられてきた。手作業の最適化は特定ハードウェアへの依存と保守の負担を生む。本論文の着眼点は、行列ベクトル積という推論の支配的な演算が、ループの形として機械的に検出可能なパターンを持つことであり、コンパイラのパスとして自動化すれば、モデルごとに手作業を繰り返さずに済むという点にある。対象は静的型付け言語、特にCで書かれた推論実装であり、llama2.c系の軽量な実装を土台とする。

## 手法のあらまし

処理は二段階で進む。まず量子化器が、モデルの重みテンソルをブロックへ分け、ブロックごとにK平均法で代表値の表であるコードブックを作り、各重みを最も近い代表値の索引へ置き換えて低ビットでビット詰めして保存する。既定の設定は4ビット、ブロックの大きさ256である。敏感な一部のテンソルは混合精度の指定により単精度のまま残される。次に推論プログラムが合成され、量子化されたテンソルについては索引を展開して代表値を引く専用カーネルが、単精度のままのテンソルについては素朴な行列積の関数が使われるよう振り分けられる。最後にLLVMパスが素朴な行列積のループを検出してBLASの呼び出しへ置き換え、通常の最適化で不要になったループを除去して、実行ファイルが生成される。

## 手法

### 1. ブロック単位のコードブック量子化 — 重みを代表値の索引へ変える

この機構が観測するのは、モデルの重みテンソルの値の分布である。保持する状態は、ブロックごとのコードブックと、各重みの低ビット索引をビット詰めした列である。処理は、重みをブロックに分け、ブロック内でK平均法により代表値を求め、各重みを最近い代表値の番号へ置き換えることであり、4ビットなら各重みは16通りの中から選ばれた番号として保存される。これにより減るボトルネックは、重みの保存と読み込みの量であり、単精度32ビットから4ビットへの圧縮がメモリ容量と帯域の両方を緩める。追加で消費する資源はコードブック自体と、推論時に索引を展開して代表値を引き直す処理であり、ブロックを小さくするほどコードブックの割合と精度の交換が変わる。誤った場合の挙動として、値の分布が偏ったテンソルでは代表値への丸め誤差が品質を落とすため、敏感なテンソルを単精度で残す混合精度の逃げ道が用意される。ビット幅3、4、8ではバイト境界にきれいに収まる詰め方の高速経路が用意され、それ以外のビット幅は汎用の展開処理へ落ちる。品質の実測では、この丸めが最良解の正しさをほぼ保つ一方、複数候補の中に正解が含まれる割合にはやや大きな影響が出ており、量子化が解の多様性を狭める方向に働くことが示される。

### 2. 量子化された行列ベクトル積のカーネル — 展開と内積を熱いループに収める

この機構が観測するのは、量子化テンソルか単精度テンソルかを示す印である。保持する状態は、スレッドごとに割り当てた連続した作業用バッファであり、モデルごとに一度だけ確保され、行ごとに使い回される。処理は、量子化側では各出力行について、詰められた索引を展開し、対応するブロックのコードブックから重みを復元して作業バッファへ置き、活性値ベクトルとの内積を取ることであり、行の処理はOpenMPで並列化され、内積はベクトル命令と複数の累積器で待ち時間を隠すよう手作業で調整される。単精度側は素朴な二重ループのまま残され、次段のコンパイルパスの置き換え対象になるよう意図的に素朴に書かれる。これにより減るボトルネックは、行ごとのメモリ確保と解放の繰り返しであり、7B級モデルではトークンあたり約140万回の行処理があるため、この削減が効く。追加費用は作業バッファの容量であり、スレッド数と最大の行長の積に比例する。誤った場合、つまりビット幅が高速経路に合わない場合は汎用の展開へ落ちて遅くなるが、正しさは保たれる。

### 3. LLVMパスによる行列ベクトル積のBLAS置換 — 素朴なループを検出して置き換える

この機構が観測するのは、コンパイルされた中間表現の中のループ構造である。保持する状態は、検出された候補のポインタや帰納変数や行の先行次元といった、置き換えに必要な束縛情報である。処理は三段階である。第一に、深さ2以上のループの最内側で、添字のアフィンな計算の多様な形に対応する組み合わせ部品を使って、積和の縮約と出力への保存のパターンを照合する。第二に、累積の更新以外の副作用や別名関係のある読み込みがないかを依存関係の解析で確認し、行列の配置が行優先か列優先かをアドレス計算から推定して、合わない候補を捨てる。第三に、外側ループの直前へBLASの呼び出しを挿入し、元の保存を消して、不要コード除去と制御流れの単純化に後始末を任せる。これにより減るボトルネックは、素朴なループが使えないキャッシュ区切りやベクトル化といったハードウェア最適化の不在であり、macOSではAppleのAccelerate、LinuxではOpenBLASやMKLといった対象向けの実装が使われる。追加費用はコンパイル時だけであり、実行時の負担はない。誤った場合の挙動は保守的で、照合や合法性確認に失敗した候補は置き換えず元のループのまま残すため、誤った置換による静かな誤動作は起きない設計であり、評価した全モデルで全ての行列ベクトル積が照合に成功したと報告される。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| コードブック量子化 | 重みの値の分布 | ブロックごとに代表値を求め索引化 | 容量と帯域 | 丸め誤差と展開処理 |
| 量子化カーネル | テンソルの種別 | 索引を展開して内積を取る | 確保の繰り返しと待ち時間 | 作業バッファを消費 |
| LLVMパス | 中間表現のループ | 検出、合法性確認、BLAS呼び出しへ置換 | ハードウェア最適化の不在 | 対象は検出可能な形に限る |

## 評価

結論は、量子化とコンパイル最適化の併用が、品質をほぼ保ったまま個人向け装置での実行を実用域へ引き上げる、というものである。品質では、HumanEval+とMBPP+でのpass@1の平均低下が0.27パーセントにとどまり、Code Llamaではむしろ1.25ポイント、MagicCoderでは0.23ポイントの改善も見られた。一方でpass@5の低下は最大4.45ポイントと大きく、量子化が最良解の質より解の多様性を削ることが読み取れる。8ビット量子化との比較では、pass@1で平均4.27ポイント、pass@5で平均4.06ポイント上回り、統計検定でもほぼ全条件で有意だった。4ビットという、より強い圧縮で8ビットより品質が高いのは直感に反するが、ブロック単位のコードブックが値の分布へ適応するためであり、単純な一様な量子化との違いがここに出ている。

効率の内訳も重要である。メモリの6.4倍削減は理論上の8倍より小さいが、これはコードブックや整列や展開用バッファの追加分によるもので、著者らはその理由を明示している。速度の最大10.5倍は、重みが小さくなってメモリ交通が減る効果と、BLAS置換で計算効率が上がる効果の合成であり、消費電力が装置全体でほぼ一定の18ワットに張り付くため、エネルギーの削減率は速度の改善率とほぼ一致する構造になっている。つまりエネルギー効率の主張は独立の節約ではなく、高速化の裏返しとして読むのが正確である。除去実験では、量子化だけと置換だけの寄与が分けられ、両方の併用で最大の効果になることが示される方向である。未評価の事項として、ビット幅の探索は今後の課題とされ既定の4ビット以外は系統的に測られていないこと、対象がC系の実装とApple M4の単一環境に限られること、7B以外の規模での挙動が示されていないことがある。エネルギー測定も電力の実測値が一定である前提の推定であり、装置や負荷が変われば前提が崩れる可能性がある。

## 既存研究との差

従来のコードモデル向けの軽量化は、パラメータ数やビット幅の削減というモデル側の工夫が中心で、推論プログラムの実装最適化は扱われてこなかった。本論文の差は、量子化とコンパイラによるプログラム書き換えを一つの枠組みに統合し、問題をプログラム最適化として定式化した点にある。積量子化の着想をブロック単位のコードブックへ具体化した点と、行列ベクトル積の検出を中間表現のパターン照合として実装し、合法性確認まで含めて自動化した点が技術的な中核である。8ビット量子化の先行方式との比較で、より強い圧縮とより高い品質を両立させたことも差として示される。

## 限界・実装状況

限界は、対象がC系の推論実装と静的型付け言語へ寄っていること、評価がApple M4の単一環境と7B級3モデルに限られること、ビット幅やブロック大きさの系統的な探索が未完であること、エネルギーの数値が電力一定の推定に基づくこと、量子化で解の多様性が削られる傾向があることである。実装状況は、約4000行の実装構成、3段階のビルド手順、量子化の既定設定、評価した全モデルで置換が成功したことが本文に記され、再現に必要な情報は比較的厚い。コード公開先の確定したURLは本文の範囲で確認できなかったためcodeはnullとした。

## 一般的な実装上の含意

圧縮と実行の最適化は別々に考えると効果が頭打ちになる。重みを小さくしても実行ループが素朴では帯域の利得を使い切れず、逆にループだけ速くしても容量の壁は越えられない。支配的な演算が機械的に検出できる形をしているなら、手作業のカーネル調整をコンパイラのパスへ移すことで、モデルごとの繰り返し作業を消せる。その際、置換できない候補は元のまま残す保守的な設計が、自動最適化を安全に使う前提になる。
