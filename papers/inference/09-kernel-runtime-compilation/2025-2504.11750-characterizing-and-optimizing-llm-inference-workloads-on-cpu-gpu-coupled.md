# SKIP：CPU–GPU結合アーキテクチャにおけるLLM推論の律速診断と融合候補探索

## 概要

この論文が明らかにするのは、**CPUとGPUの接続帯域を高くすれば、対話型LLMの応答も常に速くなるわけではない**という点である。著者らは、PCIe接続のA100/H100と、Grace CPUとHopper GPUを高速接続するGH200を比較した。GH200は大量の仕事をGPUへ流し込む条件では高性能だが、少数要求の推論ではGPUが短いカーネルを処理し終えるのをCPUの発行処理が追い掛ける形となり、GPU性能が高いほどCPU側の遅さが露出する。

単にGPU使用率やモデル全体の実行時間を測るだけでは、この逆転を十分に説明できない。著者らはシステム対応カーネル推論プロファイラ（System-Aware Kernel Inference Profiler; SKIP）を作り、PyTorch演算子からCUDA起動呼出し、GPUカーネルへ至る依存関係を時刻と対応付ける。そこから総カーネル起動・待機時間（Total Kernel Launch and Queuing Time; TKLQT）を求め、CPU律速からGPU律速へ切り替わるバッチ規模を推定する。さらに、繰り返し現れるカーネル列の近接度を計算し、起動回数を減らせる融合候補を提示する。

重要なのは、**SKIPによる実測・律速診断**と、**融合した場合の理想化された潜在高速化**を区別することである。後者は実装した融合カーネルの速度を測った結果ではない。原著はGPUカーネルの実装・融合コンパイルを将来課題としている。

## 問題設定：結合方式とバッチサイズの交差

従来の疎結合方式では、CPUとGPUが別々のメモリ領域を持ち、PCIe経由で通信する。密結合寄りのGH200では、Grace CPUとHopper GPUがNVLink-C2Cで結ばれ、仮想アドレス空間の共有と高速なメモリ接続を使う。ただし、GH200のCPUメモリとGPUメモリは物理的に一体化した単一プールではない。著者らは、物理メモリまで共有するMI300Aのような緊密結合方式と区別している。今回の実測対象はGH200と二つのPCIe系であり、MI300Aの推論実測値を示した論文ではない。

長文の事前処理（prefill）では大きな行列計算がまとまって走り、バッチ増加とともにGPUの演算・メモリ性能が支配的になる。他方、小バッチでは一つのカーネルがすぐ終了し、CPUが次のカーネルを準備して起動する固定費が無視できなくなる。高速GPUと高帯域接続を持つGH200でも、CPUの単一スレッド性能やソフトウェア実装が十分でなければ、GPUが待つ時間が長くなる。この条件依存性を「CPU律速」「GPU律速」として分離することが目的である。

既存の枠組み負担（framework tax）の研究は、バッチ増加に対する全体遅延の曲線から枠組み側の律速を推測する。一方、本研究は各CUDAカーネルの起動時刻と実行開始時刻を結び、何が待機時間を作ったのかをより細かく追う。これはモデルの数学的演算数の削減ではなく、同じ推論計算を異なるCPU–GPU構成で走らせた際の実行制御コストを可視化する研究である。

## 手法：SKIPによる実行追跡

### 1. 演算子からカーネルまでの依存関係を再構築する

SKIPはPyTorch Profilerが収集した時刻付きイベントを入力とする。CPU上の親ATen演算子、その内側で呼ばれる子演算子、CUDAランタイムの起動呼出し、実際のGPUカーネルを別々のノードとして扱う。子イベントの開始時刻が親演算子の実行区間に入るかを調べて演算子間の親子関係を付け、CUDA側はCUPTIが付ける相関識別子（correlation ID）で起動呼出しとGPUカーネルを対応付ける。スレッドとストリームの情報も利用して、同名のカーネルが繰り返し出ても別々の実行を混同しないようにする。

この結果、たとえば高水準の注意演算子一つが、いくつのGPUカーネルに展開され、各起動にどれほど待ち時間が付き、GPU上で何時間実行されたかを追跡できる。一般的なGPU内カーネル解析だけではCPU側の演算子発行の系列が見えず、PyTorchの演算子追跡だけではGPUキューでの滞留を特定しにくい。SKIPは両者を同じ依存グラフへ写像する点に特徴がある。

### 2. TKLQTで起動負担と待機負担を一緒に測る

カーネルjを起動するCUDA呼出しの開始時刻を `t_start(launch_j)`、対応するGPUカーネルの実行開始時刻を `t_start(kernel_j)` とする。個別の起動・待機時間を

`tl_j = t_start(kernel_j) - t_start(launch_j)`

と定義し、全n個について `TKLQT = Σ_j tl_j` と集計する。この差にはCPUの起動処理、ドライバ処理、必要なデータ移動に加え、前のカーネルがGPUを占有していたためにキューで待つ時間も入る。**したがってTKLQTを単純なCPU起動費用と同一視してはならない。** CPU律速の小バッチではキュー待ちが小さいので主に起動費用を反映し、GPU律速の大バッチではキュー待ちが大きくなって値が増える。

補助指標の平均カーネル実行時間（Average Kernel Duration; AKD）は各カーネルの実行時間を平均したもので、処理自体の重さを示す。推論遅延（Inference Latency; IL）は最初の親演算子開始から最後のカーネル終了までとし、GPU遊休時間は `IL − Σ kernel_duration` として見積もる。これらを組み合わせ、起動側がGPUへ十分な仕事を供給できない状態と、GPUが処理しきれずキューを蓄積する状態を区別する。

### 3. TKLQTの変曲点から最適化対象を選ぶ

バッチサイズを1、2、4、8…と増やし、TKLQTとGPU遊休時間の変化を観察する。小バッチでTKLQTがほぼ横ばいなら、キュー滞留が少なく、起動負担が主な要因と解釈する。ある規模を超えてTKLQTが急に増え始めれば、GPU上の処理が蓄積し始めたと考える。著者らはこの変曲点を、CPU側の最適化が効きやすい領域とGPU計算の改善が重要な領域の境界として使う。

ここでの境界は機種だけで決まる固定値ではない。エンコーダかデコーダか、モデルの大きさ、バッチ、系列長、GPUカーネルの粒度によって変化する。CPU側を改善したいからといって、すべてのバッチでカーネル融合を最大化するのは合理的ではない。GPUが既に飽和している場合、起動回数を減らしてもキュー待ちが支配的であり、改善余地が小さい。

### 4. 近接度による融合候補の提示

SKIPの時系列から、連続して現れるカーネル列 `C=(k_i, …, k_(i+L−1))` の出現回数 `f(C)` を数える。先頭カーネルの出現回数 `f(k_i)` で割った `PS(C)=f(C)/f(k_i)` を近接度（proximity score）と呼ぶ。たとえば同じ先頭カーネルが10回現れ、その直後に同じ3カーネル列が9回続けば近接度は0.9となる。閾値T以上の列を、発行回数をまとめられる融合候補として抽出する。PS=1は、その先頭カーネルが現れるたび同じ列が続くことを意味する。

この指標が重要なのは、演算子名から人手で融合パターンを決めずに、**実際の実行系列の反復性**から候補を探せることである。頻繁に同じ列が現れるなら、融合しても多くの実行で同じ最適化を利用できると期待できる。ただし連続出現の頻度は、データ依存性・メモリ競合・融合後のレジスタ圧力・共有メモリ消費まで証明しない。PSが高いことは融合の正当性や実測高速化の保証ではない。論文は実行系列から候補を提示し、起動削減に基づく理想化利得を計算した段階である。

### 1. 大バッチでのGH200優位と、小バッチでの逆転

Llama-3.2-1Bのバッチ16では、GH200の事前処理がIntel+H100より1.9倍、AMD+A100より2.7倍速い。GPU側へ十分な計算が投入されると、GH200の高帯域メモリと結合方式が利点になる。一方、BERTのバッチ1ではGH200の遅延がIntel+H100の2.8倍、AMD+A100の1.9倍に達する。これは同じGH200でも、仕事量により優劣が反転する直接の証拠である。GPU実行カーネルそのものが遅いのではなく、CPU側が次の仕事を供給する速度が制約になる。

BERTのバッチ8でもGH200はIntel+H100比1.7倍、AMD+A100比1.5倍遅い。GH200の帯域が高いことだけを根拠に、対話型の少数要求で必ず応答が速いと主張するのは誤りである。ただしこの比較にはCPUマイクロアーキテクチャとPyTorchの実装成熟度の差も混在する。GH200の遅延差をNVLink-C2C自体の欠点だと因果的に断定することもできない。

### 2. CPU律速領域の広さを測る

BERTとXLM-RoBERTaのTKLQT曲線では、PCIe接続の両システムが概ねバッチ8付近で変曲するのに対し、GH200はバッチ32付近まで低いキュー滞留の領域が続く。これは「GH200はGPUが遅い」という意味ではなく、GPUが仕事を早く片付けるためCPU発行が相対的に不足する領域が広いことを意味する。著者らは、エンコーダのCPU・GPU使用率が比較的釣り合う領域をPCIe系でバッチ4～8、GH200で16～32と報告する。デコーダではそれぞれ2～4、4～8であり、モデルの演算密度によって最適バッチ帯域は異なる。

TKLQTが上昇する領域はGPUのキュー待ちが支配的であり、カーネル起動回数だけを減らす融合が有効とは限らない。したがって、融合候補を実装する前にTKLQT曲線でCPU律速を確認し、改善後にGPU遊休時間・CPU遊休時間・初回トークン遅延を再測定するのが合理的である。

### 3. カーネル融合の固定費と理想化結果

Gemma-2Bのバッチ1・入力1024では、即時実行の基準に対して `torch.compile` のdefault、reduce-overhead、max-autotuneがそれぞれ1.203、1.2394、1.317倍の速度を示す。しかしコンパイル時間は0.40644秒から6.2844、12.7469、387.3秒へ増える。繰り返し同じ形状で実行する長寿命のサービスなら初期費用を償却できるが、入力形状やバッチが変わる用途では再コンパイル・形状制約を考慮しなければならない。原著は可変長のKVキャッシュやバッチ変更への柔軟性が落ちる点も述べている。

近接度に基づく融合では、GPT-2で最大2.7倍、XLM-RoBERTaで最大6.8倍という理想化された潜在高速化が示される。ただしこれは「融合後の実行時間が測定された」という意味ではない。著者らはカーネル列をまとめることで起動回数が減るという仮定の下で推定し、Tritonなどを使った実装と実測は将来の仕事としている。融合に伴うレジスタ増加、占有率低下、追加メモリ、実装可能性が速度を下げる場合、この上限値には達しない。

## 既存研究との差と位置付け

FlashAttentionは注意演算の入出力移動を削減する特定演算向けの融合であり、CUDA Graphsや `torch.compile` は計算グラフをまとめて実行時の起動を減らす。本論文はそれらの代替ランタイムを完成させたのではない。異なるCPU–GPU結合方式で**どのカーネルがいつCPUから起動され、どの領域で起動税が律速になるか**を測り、繰り返し現れるカーネル列を融合候補として列挙する診断層を提案した点が新しい。

GPU内部の命令・演算効率を測るNsight Compute、GPUトレースを可視化するNsight Systems、PyTorchの演算子イベントを収集するProfilerは、それぞれ観測範囲が異なる。SKIPはPyTorch演算子とCUDA相関IDを対応付け、CPU発行とGPU実行をつないだ時間指標を構成する。訓練用のトレースシミュレータと異なり、実際の推論ワークロードでCPU律速の閾値と融合候補を抽出することに焦点を当てている。

## 限界・負の結果・実装への示唆

第一に、対象は四モデルと三プラットフォームで、主としてFP16・PyTorchの事前処理遅延を測っている。大規模な70B級モデル、量子化重み、複数GPUのテンソル並列、長文脈KVキャッシュの階層オフロード、実サービスの連続バッチや要求到着分布を直接検証したわけではない。モデルが大きくなるとGPU演算・メモリ転送が支配的になり、ここで見たCPU起動律速が同じ程度に残る保証はない。

第二に、比較したCPUは異なる命令セット・コア構成・単一スレッド性能を持ち、ソフトウェアの最適化状況も同じではない。GH200の低バッチでの不利を「Arm CPU一般の限界」や「統合メモリの欠点」と一般化することはできない。高帯域接続があるとGPU側の待ちが減り、CPUの発行能力が相対的に目立つ、という条件付きの結論である。

第三に、TKLQTは起動処理とGPU待機を足し合わせる指標なので、値が大きいことだけでCPU律速と判断できない。バッチを変えた曲線の形、GPU遊休時間、カーネル実行時間を合わせて解釈する必要がある。またGPU遊休時間の単純な計算はカーネル並列実行の重なりがある場合に注意を要するため、GPUストリームの挙動と突き合わせるべきである。

第四に、融合候補の出現頻度が高くても、数学的に融合可能とは限らない。カーネル間の同期・メモリ依存・形状変化を満たす必要があり、融合でGPU占有率が落ちることもある。近接度は優先順位付けの手掛かりであり、実装可能性の証明ではない。原著は融合コンパイラの実装を行っていないため、潜在高速化値を実サービスの速度予測に使ってはならない。

第五に、手元のWindows環境のような単一GPUの利用者に適用する場合も、CPUから短いカーネルを大量に起動する処理なら発行負担を疑う、という診断思想は有用である。しかしGH200の1.9～2.7倍という倍率やGrace CPUの特徴は別のCPU・GPU・ランタイムへ移せない。PyTorchやCUDAのプロファイラで、カーネル起動間隔、GPU遊休、バッチ依存を測ったうえで対策を決めるべきである。
