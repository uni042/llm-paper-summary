# Unfolding the Leech Lattice: Fused Multi-Shell Decoding and VRAM Layouts for 2-Bit LLM Weights

## 概要
本論文は、Leech格子ベクトル量子化（Leech-lattice vector quantization; LLVQ）を「2 bit/weightで保存できる」という圧縮アルゴリズムの段階から、実際のGPUデコードへ載せる段階まで実装し、そのとき生じる**保存bit数と実行時VRAM bit数の乖離**を測るシステム研究である。先行LLVQの2-bit設定は24重みを一つの高次元格子点へ写すが、そのレートに必要なmulti-shell符号帳は301クラス、約1.1×10^14点に及び、単純なlookup tableとしてGPUへ置けない。先行CUDA kernelが扱っていたsingle-shellだけでは論文上の2-bit設定を実際に復号できないため、本研究はfull multi-shell decoderを構築する。

中心的な発見は、ファイル上2.000 bit/weightでも、低遅延に復号するためGPU上で符号を展開すると4.80 bit/weightを読むことになり得る点である。提案したbinary bit-plane配置はFP16 GEMVより2.15倍速い一方、同じ2-bit保存形式でもQTIPのtrellis kernelは2.40倍少ないbyteしか読まず2.27倍速い。つまり極低bit量子化のサービング性能は「圧縮率」だけでなく、復号器がHBMから何byte読むかと、符号帳構造をどこまで規則的なGPU命令へ落とせるかで決まる。

## 問題設定
バッチ1の自己回帰デコードでは、大きな重み行列に対する行列ベクトル積（matrix-vector multiplication; GEMV）がメモリ帯域律速になりやすい。理想的にはFP16の16 bit/weightを2 bitへ落とせば重み転送量を大幅に減らせる。しかしベクトル量子化では、圧縮indexを実重みへ復元するためのclass、符号、振幅、scale、補助streamなどが必要であり、これらをGPUが直接扱えなければ、保存時のbit rateと実行時のread trafficは一致しない。

Leech格子では24次元ブロックを巨大なコードブックから選ぶ。2-bit相当の完全な表現は301個のequivalence classを横断し、47-bit級のdirection indexとgain等を復号する必要がある。全コードブックをlookup table化するのは現実的でなく、実行中に複雑なclass分岐を行えばwarp divergenceや命令数が増える。本論文の問いは「この巨大で組合せ的な符号を、GPUデコードでmemory-bound GEMVとして成立させられるか」と「成立させるために何bit/weightをVRAM上で実際に支払うか」である。

## 手法
### 301クラス符号のoffline unfolding
デコードkernel内で47-bit indexから301クラスの組合せ構造を毎回解くのでなく、モデルload時に符号をGPU向けの規則的なlayoutへ**展開（unfold）**する。著者のPlanes14系配置では、各24重みブロックに必要なclass/gain/sign/magnitude情報をbit-planeへ変換し、laneごとに同じshift・mask・predicated selectionを実行できる形にする。これによりclassごとの分岐をkernelから排除し、warp内で同じ命令列を走らせる。

この設計は計算を減らす代わりにVRAMを増やす。ファイルでは2.000 bit/weight相当のindexでも、展開後の最良実行点は4.804 bit/weightを読み込む。つまりoffline展開は「複雑なindex decodeを毎token支払う」コストを「一度展開して多めのbyteを毎token読む」コストへ変換する。LLMデコードが帯域律速なら、展開し過ぎると今度は転送量が支配的になるため、layout自体が最適化変数となる。

### 逆量子化とGEMVの融合
展開済み情報からFP16重み行列を一旦VRAMへ復元して通常GEMVを呼ぶと、復元重みのwriteとreadが追加され、量子化の帯域利得が失われる。そこでCUDA kernel内で符号の読出し、Leech lattice成分の再構成、scale適用、入力activationとの積和を融合する。中間のdense weight tensorをglobal memoryへmaterializeしない。

正しさはfloat64参照実装と照合し、4B構成では1,105,920出力rowを確認する。またファイル形式のbijective indexingも全150,681,600 blockで検証している。最終的にはfused engineとdense FP16でgreedy生成token fingerprintを比較し、documented tie-breakを除き一致することまで確認する。したがって速度測定の前提となるdecoder correctness自体を独立に監査している。

### VRAM layoutを性能変数として扱う
論文は同じ量子化情報を複数のbit-exact layoutへ変換し、単一process・同一shapeでbyte数とGEMV時間を比較する。binary bit-planeはone-hot mask型より小さく、同程度のbandwidth利用率で高速だった。さらに4.3 bit/weightより下へ詰めると第2の不規則streamが必要になり、約3.6 bit/weightでは復号が単純なshift/maskだけでは済まなくなる。著者は3.59 bit/weight案を事前に定めた性能基準で棄却しており、「最小bit layoutが最速」とはしていない。

この比較の意味は、圧縮formatとkernelを分離しないことである。GPUが読むbyte数、復号命令、branching、shared-memory tableの大きさを含めて初めて実行時rateが決まる。QTIPは2 KiB程度のtrellis stateをshared memoryへ置けるため、巨大コードブックを展開するLLVQより実VRAM trafficが小さい。

### 比較のためのcontrol
単なるCUDA launch geometryやruntime差をspeedupへ誤認しないため、重みbyteを読まないno-weights controlも置く。ところがQTIP trellis kernelはこのcontrolより速く、control自体がGPUの真の下限ではなく実装geometryの下限だと判明する。また別memory hierarchyとしてA100でも測り、そこでは全LLVQ armがFP16より遅い。したがってL40S/Ada上のspeedupを一般GPU特性として主張しない。

## 評価条件
主なkernel評価はバッチ1のdecode-phase GEMVで、NVIDIA L40S/Adaを中心に、FP16、公式AWQ 4-bit、QTIP 2-bit系kernel、および4種のLLVQ VRAM layoutを同一processで測る。性能は実読込byte、byte-boundに対する到達率、kernel latencyで比較し、QTIPとの直接比較では双方がそれぞれのmemory-bandwidth boundの約61%と65%に達する。

end-to-endではQwen3の4B、8B、14B級を使い、output head条件を同じに固定した比較でformat+kernelの寄与を測る。4BについてはWikiText-2 perplexityとMMLUも測り、圧縮品質を速度と同時に評価する。さらにA100でも再測定し、hardware依存性をnegative controlとして扱う。論文・著者artifactはすべてbatch 1 decodeの主張であり、prefillやcontinuous batchingの速度は対象外である。

## 主要結果
binary bit-plane layoutの実行時read rateは4.80 bit/weightで、名目2-bitの2.4倍に膨らむが、それでもFP16 GEMVに対し2.15倍のkernel速度を得る。対してQTIP trellis kernelは提案layoutより2.40倍少ないbyteを読み、2.27倍速い。両者のbyte-bound到達率が61%対65%と近いため、著者はこの差を主としてkernel演算能力ではなく**memory traffic差**と解釈する。巨大コードブックを高速実行のため展開した代価がそのまま転送量へ現れた結果である。

end-to-endの生の4B比較ではLLVQ fused engineが87.0 token/s、2.60 GBで、著者側FP16 armの43.5 token/sより約2倍速い。ただしFP16 armには語彙出力headで毎token 778 MBをcopyする既知のruntime handicapがあるため、この2倍値をkernel成果として採用していない。output headを両armで同一にすると、format+kernelだけの改善は4B 1.11倍、8B 1.29倍、14B 1.41倍となる。モデルが大きいほどweight trafficの寄与が増える方向と整合する。

品質コストは無視できない。Qwen3-4BでFP16はWikiText-2 perplexity 12.24、MMLU 70.3%、公式AWQ 4-bitは13.52、70.0%なのに対し、当該LLVQ 2-bit artifactは16.94（FP16比1.384倍）、55.6%（-14.7ポイント）である。分野別にはabstract algebraやaccountingがchance付近まで崩れる一方、history/law/psychologyは80%以上を保つ。著者はperplexityだけでは2-bit reasoning劣化を捉えられないと明記する。

規模を上げるとAWQとのMMLU差は4Bで14.5ポイント、8Bで7.5、14Bで6.1へ縮むが、3点だけなのでscaling lawは主張しておらず、32Bも未実施である。またA100では全LLVQ configurationがFP16を下回るため、L40Sでのspeedupはmemory hierarchyとkernel/runtimeの組合せに依存する。

## 既存研究との差
先行Leech-lattice量子化は低bitでのrate-distortion品質を示したが、主張するmulti-shell 2-bit codebookをGPUデコードへ載せる実装が欠けていた。本論文は量子化objectiveそのものより、その符号を**実際にserveすると何が起きるか**を主題にする。とくにon-disk 2 bitという数値を性能代理にせず、in-VRAM read rateとfused GEMVまで測定した点が核心である。

AWQとの比較ではbit幅だけでなくruntimeが違うため、著者は異なるengine間のthroughput比を意図的に出さない。QTIPとは同一process・同一shapeでkernelを比較し、QTIPが勝つnegative resultもそのまま報告する。この測定設計により「2-bitだから4-bitより必ず速い」という単純な結論を避けている。

## 限界
第一に、圧縮率と品質の交換条件が大きい。4BではMMLUが14.7ポイント落ち、2-bitがreasoning能力を強く傷つける。規模とともに差は縮むものの14Bまでしか測っておらず、大規模化で消えるとは結論できない。

第二に、ハードウェア依存性が強い。L40S/Adaではweight traffic削減が効く一方、A100ではLLVQ armがFP16より遅い。したがって4.80 bit/weightや1.11〜1.41倍という値は特定GPU・batch 1・当該kernelの測定であり、一般的な「2-bit LLM速度」とみなせない。

第三に、実行時4.80 bit/weightは保存時2.00 bit/weightから大きく膨らむ。より詰めた3.59 bit案は不規則decodeコストで事前基準を満たせず棄却された。つまり巨大コードブックでは、保存効率を上げるほどdecoder complexityが増え、帯域削減を速度へ変換できなくなる領域がある。

最後に、評価範囲はbatch 1 decode GEMVが中心で、prefill、大batch、continuous batching、複数requestを含むproduction servingは未評価である。専用formatはGGUF/AWQ/safetensors互換でもなく、当該artifactを読むにはプロジェクト固有runtimeが必要である。
