# FlexQ：INT6量子化とBinary Tensor Coreカーネルの共同設計

## 概要

FlexQは、LLMの重みと活性値を6bitへ量子化して品質を維持しつつ、GPU上で本当に高速に実行するための方式である。INT4はメモリ削減効果が大きい一方で精度低下が問題になることがあり、INT8は品質を保ちやすいが重み帯域の削減余地が小さい。INT6は中間的な選択肢だが、一般的なNVIDIA GPUのTensor CoreにはネイティブなINT6行列積がない。単に6bitのデータを格納しても、実際の演算をINT8へ展開すれば計算と転送の利益を十分に得られない。

著者はこの問題を**量子化方式と演算カーネルを同時に設計する**ことで解く。重みを全層で6bitにし、活性値も基本6bitにする一方、誤差に敏感なFFNの`down_proj`入力だけ8bitを使う。演算では6bit値をビット平面へ分解し、1bitの行列積を行えるBinary Tensor Core（BTC）で複数回の行列積とビット重み付き和を構成する。専用のメモリ配置と復元融合によって、INT6非対応ハードウェア上でも量子化の性能上の利点を引き出す。

原著v2の実験ではWikiText2のLLaMA系列でFP16からの困惑度増加を多くの条件で0.1程度以下に抑え、RTX 3090 TiでcuBLAS W8A8比カーネル平均1.78〜1.82倍、ABQ-LLMの対応カーネル比1.24〜1.27倍を示す。FasterTransformerへ統合したA6000実測ではSmoothQuant比で1.25〜1.33倍のE2E速度比、メモリ使用量で1.19〜1.24倍の削減比を報告する。ただし比較基準はカーネル、E2E、FP16、SmoothQuantでそれぞれ異なるため、最大値を単一の「一般的な高速化率」とみなせない。

## 問題設定

重みのみの量子化と異なり、W6A6では活性値も低ビット化するため、各層でオンライン量子化が必要になる。活性値の外れ値を含む広い分布を6bitで表すと、同じスケールへ押し込まれた小さい値の表現が粗くなる。逆に細かいグループ単位でスケールを分ければ誤差は減るが、グループごとに復元係数を適用する計算が増える。さらに、6bitは2の冪のデータ幅ではなく、GPUのロード粒度、共有メモリbank、行列積命令の形状と合いにくい。

論文は、INT6を**単にINT8で演算するのでは高速化が限定される**点を出発点とする。BTCが持つ1bit演算の高い理論スループットを利用するには、ビット平面をBTCの入力タイルへ合わせて再配置し、ワープ単位で部分和をまとめ、メモリ転送を演算と重ねる必要がある。したがってモデル精度の量子化手法とGPUカーネルのレイアウトを独立に選べない。

## 手法

### 1. 全重みW6・原則A6のグループ量子化

重みと活性値の連続する要素をグループへ分け、グループごとに共通の対称量子化スケールを持たせる。基本のグループサイズは128。チャネル全体に一つのスケールを使う場合と比べ、局所的な値域に合わせて量子化できるため、小さい値が大きな外れ値に埋もれる問題を減らす。これにより6bitでの精度保持を図るが、スケール値の保存・復元が追加で必要になる。

重みは推論中に変わらないため、事前に量子化してビット詰めまで済ませられる。一方、活性値は層ごと・入力ごとに変わるので、実行中に量子化とビット詰めを行う。FlexQはこの処理を既存演算と融合し、別カーネルの起動や余分なメモリ転送を抑える。量子化された整数の積和の後にグループごとの重みスケールと活性値スケールを掛け、出力をFP16へ復元する。

### 2. `down_proj`だけA8に残す感度対応

LLaMA-7BとLLaMA-2-7Bの線形層を個別に量子化して困惑度への影響を調べたところ、FFNの`down_proj`入力は6bit活性値に敏感だった。GLU系モデルではこの入力に大きな外れ値が出るため、6bitの単一範囲で表すと誤差が増えやすい。`o_proj`、`gate_proj`、`up_proj`などでは比較的損失が小さい条件があり、すべての活性値を8bitへ戻す必要はない。

この観測から、重みは**全層W6**のまま、通常層はA6、`down_proj`入力のみA8とする。つまり全体は厳密なW6A6一律ではなく、W6A6とW6A8の混合である。これを「6bitの重み・活性値をすべて使う」と説明すると設計の核を失う。OPTのような非GLU構造では著者はW6A6を一律適用しており、モデル系統によって混合精度の設定が異なる。

この感度の知見は論文内の層別困惑度実験に基づく。著者は最終的な量子化手順を校正データ不要と説明するが、層選択の一般化可能性まで自動的に証明したわけではない。別のモデルで外れ値が現れる層が違う場合には、W6A8の配置を再検討する必要がある。

### 3. 6bit行列積をBTCの1bit行列積へ分解

GPUのBinary Tensor Coreが提供する1bit行列積命令を用い、重みWと活性値Xの各整数をビット位置ごとに分解する。各ビット平面の積をBTCで計算し、ビット位置の重みに従って合計することで、6bit同士、あるいは6bit×8bitの整数行列積を構成する。原著§4.2はこの計算を複数の1bit行列積の和として定式化し、グループごとのスケール係数を含む式(6)へ拡張する。

この設計の重要点は、**ネイティブINT6 Tensor Coreが存在するという主張ではない**ことだ。BTCの1bit演算を組み合わせてINT6相当の計算を実装するので、ビット平面の展開や集約に追加命令が必要になる。それでもBTCの演算スループットが高いため、レイアウトとデータ転送を最適化すれば通常のINT8演算に対して優位になる条件がある。

### 4. ビット詰めと連続アクセス

FlexQ-W6Axカーネルでは、BTCの`m8n8k128`に合わせて活性値のM次元とK次元を分割し、ビット位置を明示したチャンク配列へ並べ替える。原著では概念的に `[M,K,q]` を `[K/chunk_k, M/chunk_m, q, chunk_m, chunk_k]` へ変換し、`chunk_k=128`、`chunk_m=min(M,8)`とする。重みも対応するタイル形状へ整える。これにより各BTC命令が必要なビット面を連続して読み出せる。

ワープ内のビット交換には`__ballot_sync`を利用し、グローバルメモリの読み書きは128bit粒度の連続アクセスへ寄せる。細かいINT6の値を素朴に詰めた場合の非連続ロードやアラインメント不一致を減らす狙いである。小バッチのGEMVでは重みの再利用が少ないため、L2キャッシュを汚さないよう重みロードへ`evict_first`の優先度を与える。活性値は再利用率が比較的高いため同じ退避指定をしない。

### 5. bank conflict回避、warp集約、復元融合とパイプライン

共有メモリは32bankで構成され、同時アクセスが同一bankへ集中するとトランザクションが分割される。FlexQはBTCが読み取るビット平面の配置をbank競合が起きにくい形へ整え、共有メモリから演算器への供給効率を上げる。さらにBTCからの部分和をwarp内で集約し、共有メモリへ一度書き戻してから再読出しする処理を減らす。

グループごとの逆量子化は行列積カーネル内で融合する。これにより中間の量子化整数行列を別カーネルへ渡さず、積和とスケール適用を近接して実行できる。最後に複数段のソフトウェアパイプラインで次タイルのロードを現在タイルのBTC演算と重ねる。原著Table 6では、単純なBTC版よりwarp集約、特に多段パイプラインが遅延を大きく改善しており、ビット幅だけでなくデータ供給が実性能を左右することが分かる。

## 評価

### モデル・環境・比較対象

精度はPyTorch/Transformersで測定し、LLaMA 1（7B〜65B）、LLaMA-2（7B〜70B）、LLaMA-3（8B）、OPT（6.7B〜30B）を対象とする。WikiText2とC4の困惑度、PIQA・ARC-E/C・BoolQ・HellaSwag・WinoGrandeのゼロショット正答率を用いる。精度比較にはSmoothQuant、OmniQuant、I-LLM、DuQuantを採用し、DuQuantはLWCを併用した版である。

速度評価はRTX 3090 Ti 24GBとA6000 48GB、CUDA 12.1で行う。カーネル単体ではcuBLAS W8A8、ABQ-LLM W6A6/W6A8と比較し、バッチ1/4/8を調べる。E2EはFasterTransformerへFlexQを統合し、FP16、CUTLASS W8A16、SmoothQuant W8A8を比較する。ABQ-LLMは主に極低bit量子化向けのためE2E比較には入れていない。カーネルとE2Eで比較対象が異なる点を区別する必要がある。

### 量子化後の困惑度

| モデル・データセット | FP16 | FlexQ | SmoothQuant | DuQuant |
|---|---:|---:|---:|---:|
| LLaMA-1 7B / WikiText2 | 5.68 | 5.70 | 6.03 | 5.74 |
| LLaMA-2 7B / WikiText2 | 5.47 | 5.52 | 6.20 | 5.53 |
| LLaMA-2 70B / WikiText2 | 3.31 | 3.34 | 3.69 | 3.35 |
| LLaMA-3 8B / WikiText2 | 6.14 | 6.24 | 7.07 | 6.27 |
| LLaMA-3 8B / C4 | 8.88 | 9.05 | 9.57 | 9.10 |

原著Table 2の値。困惑度は低いほど良い。FlexQはFP16に近く、特にSmoothQuantより低いが、FP16と完全一致ではない。例えばLLaMA-3 8BのWikiText2では6.14→6.24と0.10悪化し、C4では8.88→9.05と0.17悪化する。要旨の「WikiText2で増加0.1以下」はC4まで同じ上限を意味しない。

OPTでは非GLUモデルに一律W6A6を使う。原著Table 5ではOPT-6.7BのWikiText2でFP16 10.86、FlexQ 10.91、SmoothQuant 11.34、OPT-30BでFP16 9.56、FlexQ 9.60、SmoothQuant 9.67となる。ただしOPT-13BのWikiText2はFP16 10.13に対してFlexQ 10.37であり、すべてのモデルで「増加0.1以下」ではない。論文が評価したモデル系統ごとの差を残す。

### ゼロショット精度と不利な条件

原著Table 3/4の六課題平均では、LLaMA-1 7BのFP16 64.09、FlexQ 63.80、SmoothQuant 62.81、DuQuant 63.75。LLaMA-2 7BではFP16 63.72、FlexQ 63.66、SmoothQuant 62.76。LLaMA-3 8BではFP16 74.22、FlexQ 74.27、SmoothQuant 71.68となる。LLaMA-3の平均ではわずかにFP16を上回るが、これは評価誤差や課題ごとの変動を含みうるため、量子化により一般的に推論能力が向上すると解釈しない。

課題単位では負の結果もある。LLaMA-2 7BのBoolQはFP16 71.13に対してFlexQ 69.82で低下する。LLaMA-2 70BのHellaSwagは80.87→80.72、WinoGrandeは76.95→76.40。モデル・課題によって改善と悪化が混在するため、「ほぼ無損失」は評価集合の平均的な説明であって全タスクの保証ではない。

### カーネル速度とE2E速度

RTX 3090 Tiの線形層カーネルでは、バッチ1/4/8におけるcuBLAS W8A8比平均1.78/1.81/1.82倍、ABQ-LLMの対応カーネル比1.24/1.24/1.27倍と報告する。ABQ-LLMが特定の行列形状でcuBLASより遅くなる例も示され、比較方式のビット演算が常に有利ではないことが分かる。カーネル単体の速度は全モデルの生成速度とは区別する。

A6000のFasterTransformer統合では、LLaMA-13BでFP16比最大2.38倍の速度改善、メモリ容量比2.28倍の圧縮を報告する。SmoothQuant比ではLLaMA/OPT系列を通じE2E1.25〜1.33倍、メモリ使用量の削減比1.19〜1.24倍。Figure 12の同一バッチ比較では、バッチ8でLLaMA-7B/13BのFP16比最大1.89/2.01倍、SmoothQuant比はそれぞれ1.2〜1.32/1.19〜1.28倍である。2.38倍はFP16比較の最大条件であり、SmoothQuant比1.33倍と同列に扱えない。

### 構成要素除去：最も効いたのは多段パイプライン

原著Table 6はRTX 3090 Ti、GEMV `(1,4096)×(4096,4096)` の測定。cuBLAS W8A8の37.02µs、素朴なBTC版29.44µs、warp集約追加26.54µs、多段パイプライン追加16.12µs、キャッシュ退避追加15.03µs。パイプライン追加で10µs超の削減があり、BTCの演算器を使うだけでなく転送を隠蔽することが重要である。

融合逆量子化を外すと14.92µsとわずかに速くなるが、これは**逆量子化処理をしない条件**なので出力の同一品質を維持した最終システムの比較ではない。逆量子化を含む完成カーネルの15.03µsと混同しない。著者は融合逆量子化の追加費用をこのGEMVで1%未満と報告している。

## 既存研究との差

SmoothQuantは主に活性値の外れ値の量子化困難さを重み側へ移すW8A8方式である。FlexQはより小さいW6A6/W6A8のデータ幅を選び、精度保持と演算器への適合を同時に設計する。DuQuantは量子化前の分布整形に強みがあるが、FlexQは校正データ不要のグループ量子化と専用BTCカーネルで速度を狙う。

ABQ-LLMもビット演算を用いるが、主に2bit等の極低bitに焦点があり、FlexQは6bitで品質を保ちながら高速化する。カーネルの比較ではABQ-LLMを採用する一方、E2EではSmoothQuantを主比較とする。QServeのW4A8KV4やFP6重み量子化方式と違い、FlexQは**重み・活性値双方のINT6相当演算**を主題とし、ネイティブにない整数精度をBTCで実現する点に特徴がある。

## 限界・導入条件

第一に、BTCの利用可能性とビット演算命令、共有メモリbank、warp内通信、キャッシュヒントがGPUアーキテクチャに依存する。RTX 3090 Ti/A6000の結果をCPU、他社GPU、将来のTensor Coreへ無条件に外挿できない。特に通常のCUDA GEMMへ単に6bit重みを渡しただけでは論文の性能は再現しない。

第二に、活性値のオンライン量子化とビット詰め、逆量子化の費用が残る。バッチや行列形状によって転送律速・演算律速の割合が変わるため、1.78〜1.82倍というカーネル平均値と、E2Eの1.25〜1.33倍の差が生じる。小バッチではL2の重み再利用が乏しいため`evict_first`が効くが、大バッチでも同じキャッシュ方針が最適とは限らない。

第三に、精度はモデルの外れ値位置と活性値分布に左右される。著者はGLU系の`down_proj`を特別扱いするが、未知のアーキテクチャでは別の層が敏感な可能性がある。OPTでは混合精度を用いずW6A6一律であり、LLaMA系の実装詳細をそのまま適用してはいけない。校正不要という性質は任意のモデル・任意のデータ分布で品質無損失という保証ではない。

第四に、評価は論文のFasterTransformer実装と特定の量子化カーネルに限定される。vLLMやSGLangの実際の連続バッチング、PagedAttention、KVキャッシュ管理、分散MoE、投機的復号と組み合わせたE2E性能は本論文の測定対象ではない。モデルロード時間、量子化前処理、量子化重みの配布、長期稼働時の運用費用もE2Eの速度倍率に含まれるとは限らない。
