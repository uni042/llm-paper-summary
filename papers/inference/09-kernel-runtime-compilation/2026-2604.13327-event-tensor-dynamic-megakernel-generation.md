# Event Tensor: A Unified Abstraction for Compiling Dynamic Megakernel

> タイル依存関係を記号形状のイベントテンソルとして表し、可変形状とMoEのデータ依存分岐を再コンパイルせず静的・動的メガカーネルへ変換するコンパイラ抽象。

## 概要
Event Tensorは、複数演算子を一つの常駐メガカーネルへ融合するとカーネル起動待ちと演算子境界の大域同期を減らせる一方、連続バッチの可変形状やMoEの実行時ルーティングを静的タスクグラフで表しにくい問題を扱う。タイル単位のタスク完了イベントをデータテンソルと同じ多次元・記号形状の『イベントテンソル』としてコンパイラ中間表現へ昇格し、実行時データで通知先や起動タスク数を決められるようにする。Event Tensor Compiler（ETC）はこれを静的SM割当またはGPU上の動的タスクキューへ変換し、単一の常駐カーネルへ融合する。8×B200で通信・計算融合を最大1.40倍、MoE層を最大1.23倍高速化し、Qwen3低バッチ推論でvLLM比最大1.48倍、ウォームアップを123秒から35秒へ短縮する。

Event Tensorは、同期イベントを個別のセマフォとして散在させず、タスク完了を表すイベントをデータテンソルと同様の多次元配列としてコンパイラ中間表現へ組み込む。各要素は何個の先行タスクを待つかを持ち、生成側タスクが通知し、利用側タスクが待機または起動される。イベントテンソル自体に記号次元を持たせることで、バッチ数や系列長が変わっても一つの依存関係テンプレートを具体化できる。さらにMoEのtop-k結果や専門家ごとのタイル数を実行時テンソルとしてイベント添字や起動範囲へ接続し、コンパイル時には不明なデータ依存のタスクグラフも表現する。

代表結果として、計算通信融合は8×B200、GEMM+Reduce-Scatter / All-Gather+GEMM、8192 トークン、TP=8でcuBLAS+NCCLに対して最大1.40倍高速化。イベント単位の依存で通信完了を全体待ちせず、準備できた計算タイルから重ねる。
## 問題設定
通常のGPU実行では、LLMの1デコード反復に含まれる多数の演算子をCPUから順番にカーネル起動する。起動1回が約5〜10µsなのに対し高速な小カーネルは約2µsで終わる場合があり、低バッチ推論では起動自体が主要な遅延になる。また別カーネルへ分かれていると、後段が前段の一部タイルだけを待てばよい場合でもカーネル境界で大域的に同期し、演算子間の並列性を使えない。複数演算子を一つの常駐メガカーネルへ融合すればこの問題を減らせるが、実運用では連続バッチで形状が変わり、MoEではトークンの専門家割当が実行時データで決まる。既存の静的タスクグラフやCUDA Graphは形状ごとの再捕捉を必要とし、手書きメガカーネルは複雑なタイル依存を個別に管理するため保守性が低い。
## 新規性
Event Tensorは、同期イベントを個別のセマフォとして散在させず、タスク完了を表すイベントをデータテンソルと同様の多次元配列としてコンパイラ中間表現へ組み込む。各要素は何個の先行タスクを待つかを持ち、生成側タスクが通知し、利用側タスクが待機または起動される。イベントテンソル自体に記号次元を持たせることで、バッチ数や系列長が変わっても一つの依存関係テンプレートを具体化できる。さらにMoEのtop-k結果や専門家ごとのタイル数を実行時テンソルとしてイベント添字や起動範囲へ接続し、コンパイル時には不明なデータ依存のタスクグラフも表現する。
## 手法
### 手法のあらまし
入力の計算グラフは、各演算子をGPUのストリーミングマルチプロセッサ（SM）が処理するタイル単位タスクへ分割し、データテンソルに加えてイベントテンソルで生成側・利用側の依存を記述する。例えば分割縮約では、ある行の部分和タイルが全部終了した時点だけを同じイベント要素へ通知し、その行の最終和タイルだけを解放するため、別行の部分和と最終和を並行実行できる。記号形状を使えば、バッチ1でも2でも同じイベントテンソル式を実行時の具体形状へ展開でき、形状ごとの再コンパイルは不要になる。MoEではtop-kルーティングが各トークンの通知先専門家イベントを決め、専門家別タイル数の接頭和がイベント発火時に起動するGroupGEMMタイル範囲を決める。ETCはこの表現へ通常のグラフ最適化とタイル最適化を適用した後、静的または動的スケジューリングへ変換する。静的方式では各SMのタスク順を事前計算し、一つの常駐ループがキューを順番に実行しながらイベントのnotify/waitを行う。動的方式では、依存が満たされたイベントが実行可能タスクをGPU上のキューへ投入し、空いたSMが原子的に取り出すため、MoEの不均衡や通信遅延の揺らぎへ適応できる。最後に演算子間で入力到着前に重みを先読みするパスなどを適用し、形状・データ依存を含んだまま単一のAOTコンパイル済み常駐カーネルを生成する。

### イベントテンソルによる細粒度依存表現
各イベント要素はSM粒度のタスク集合が完了したことを表し、初期待ち数、通知、待機を持つ。コンパイラは生成側タイルの終了時に通知、利用側タイルの開始前に待機を挿入する。イベントを多次元テンソルへまとめることで、数百万規模になり得るタイル間依存を個別ノードとして実体化せず、添字式で圧縮して表現できる。データテンソルの座標とイベントテンソルの座標を写像するため、ある出力タイルが本当に必要とする入力タイルだけを待たせられ、演算子全体の完了障壁を除ける。これが注意機構内の独立枝、MLPやMoEの複数波、通信とGEMMの重畳を可能にする。

### 記号形状とデータ依存の動的性
形状依存では、イベントテンソルとタスクグリッドの次元にバッチ数や系列長の記号を残し、一つの依存テンプレートを実行時の具体値へ展開する。そのため、CUDA Graphのように候補形状ごとに捕捉・管理する必要がない。データ依存ではMoEのルータが計算したtop-kを使い、各トークンのグルーピングタイルがどの専門家イベントへ通知するかを実行時に決める。さらに専門家ごとの必要GroupGEMMタイル数を接頭和配列から読み、イベント発火時に可変個の消費タスクを起動する。依存鎖自体は前向きだが、個々の辺とタスク数を実行時データから決められるため、専門家偏りを静的に列挙する必要がない。

### 静的・動的スケジューリング変換
予測可能な密計算やリング型All-Gatherでは、各SMへ実行順を事前割当する静的方式を使う。タスク取得の原子操作が不要で同期費用が小さく、低バッチの遅延重視条件に向く。通信時間やMoEの専門家負荷が揺れる場合は動的方式を使い、イベントの待ち数がゼロになった瞬間に消費タスクをGPU上の準備キューへ投入し、空いたSMが取得する。これにより一部SMが長いタスク列を抱える間に他SMが遊ぶ状態を減らす。動的方式にはキュー操作費があるため常に優位ではなく、ETCは同じイベントテンソル表現から両方式を選択できること自体を設計上の利点としている。

### 全体のデータ／制御の流れ
ETCはApache TVM上に実装され、グラフ最適化、タイル化とハードウェア命令割当、イベントテンソル依存を使うスケジューリング変換、重み先読み、常駐GPUコード生成の順で処理する。静的方式ではホスト側でSM別タスク列を作り、動的方式では最小限のGPU上スケジューラを生成する。形状やMoEルーティングをランタイム入力として受けてもバイナリ自体は事前生成済みなので、サービング開始時のJITコンパイルや多数のCUDA Graph再捕捉を避けられる。
## 評価条件
- **ハードウェア**: 8×NVIDIA B200をNVLink接続したサーバ。Ubuntu 24.04、PyTorch 2.8.0、CUDA 13.0、driver 580.82.07。
- **ソフトウェア**: Apache TVM上のETC。比較対象はcuBLAS+NCCL、TP-Async、Triton Distributed 0.0.2-rc、cuBLASMp、Triton 3.4.0、FlashInfer 0.2.14.post1、vLLM 0.11.0rc2、SGLang 0.5.3rc0。
- **比較対象**: cuBLAS+NCCL、TP-Async、Triton Distributed、cuBLASMp、Triton、FlashInfer、vLLM、SGLang
計算通信融合では8 GPU・8192トークン・TP=8でGEMM+Reduce-ScatterとAll-Gather+GEMMを測定する。MoEではQwen3-30B-A3Bの128専門家・top-k=8を単一B200で可変トークン数評価する。エンドツーエンドではQwen3-30B-A3BとQwen3-32Bを用い、入力512トークンから100トークン生成し、バッチ1〜128のTPOTをvLLM/SGLangと比較する。Qwen3-32Bでは4-way TPも測る。さらにQwen3-32Bのエンジン起動から初要求までのウォームアップ時間と、静的・動的スケジューラの除去比較を行う。
B200世代の単一ノード8 GPUを中心とした実機評価。低バッチのデコードと融合カーネルを重点評価し、プリフィルや大バッチ単体演算はメガカーネル利得が小さいとして主対象外。コンパイラ抽象はGPU世代非依存を意図するが、他世代で同じ数値利得を実証したわけではない。
## 主要結果
ETCは、演算子単体の最適化ではなく演算子境界をまたぐ細粒度パイプライン化で利得を得る。8×B200のGEMM+Reduce-ScatterとAll-Gather+GEMMでは非融合cuBLAS+NCCL比で最大1.40倍、Qwen3-30B-A3Bの完全MoE層では最良のTriton/FlashInfer比較対象比で最大1.23倍高速化する。低バッチのQwen3-30B-A3Bではバッチ1でvLLM比1.48倍、SGLang比1.20倍、Qwen3-32BではvLLM比最大1.15倍、SGLang比最大1.09倍である。TP=4では0.99〜1.06倍でvLLMと同等に留まり、CPU側分散スケジューリング費の小さいSGLangが優位な条件もある。ウォームアップはvLLM 123秒、SGLang 583秒に対しETC 35秒で、動的形状をAOTで扱う効果が大きい。

- 計算通信融合 / 最大1.40倍高速化 (比較対象: cuBLAS+NCCL; 条件: 8×B200、GEMM+Reduce-Scatter / All-Gather+GEMM、8192 トークン、TP=8) — イベント単位の依存で通信完了を全体待ちせず、準備できた計算タイルから重ねる。

- MoE層性能 / 最良比較対象比最大1.23倍 (比較対象: Triton 3.4.0 / FlashInfer 0.2.14.post1; 条件: Qwen3-30B-A3B、1024 トークン付近) — ルーティング結果で動的にタスクを起動し、GroupGEMM段間の大域同期と専門家負荷不均衡を減らす。

- 低バッチQwen3-30B-A3B TPOT / バッチ=1でvLLM比1.48倍、SGLang比1.20倍 (比較対象: vLLM 0.11.0rc2、SGLang 0.5.3rc0; 条件: プリフィル 512、デコード 100 トークン) — カーネル起動費が相対的に大きい低バッチで、常駐メガカーネルと演算子間重畳が効く。

- Qwen3-32B TP=4 / vLLM比0.99〜1.06倍 (比較対象: vLLM; 条件: 4-way tensor parallel) — 分散低バッチではCPUスケジューリングや通信費が露出し、単一GPUほど大きな利得は出ない。

- エンジンウォームアップ / ETC 35秒、vLLM 123秒、SGLang 583秒 (比較対象: vLLM / SGLang JIT + CUDA Graph capture; 条件: Qwen3-32B) — 記号形状の単一AOTメガカーネルにより、vLLM 67回、SGLang 51回の実行時グラフ捕捉を不要にする。

- スケジューリング方式の差 / MoE 1024 トークンで動的方式が静的比約4%高く、密TP=4では静的方式が非融合比6〜8%高い (比較対象: ETC 静的 / 動的 / unfused megakernel; 条件: data-dependent vs regular ワークロード) — 不規則負荷では動的負荷分散、規則的低遅延負荷では静的キューの低オーバーヘッドが有利。

### 負の結果・境界条件
- ETCが常に最速ではない。Qwen3-32Bの4-way TPではvLLM比0.99倍まで下回る条件があり、SGLangはCPU側分散スケジューラの低い費用により優位な設定がある。コンパイラ生成GEMMタイルが一部形状でcuBLASほど調整されていないことも小さな劣化要因である。動的スケジューラは規則的な分散Transformer層ではタスクキュー操作、とくに遠隔キュー操作の費用が大きく、静的方式より明確に遅い。

### 結果の読み方
イベントテンソルの効果は、カーネル起動を一つへ減らすだけでなく、従来は演算子境界で隠れていたタイル単位の依存を公開する点にある。規則的な処理では依存順を事前に固定して同期費を最小化でき、MoEや通信揺らぎでは実行時に空いたSMへ仕事を渡すことでストラグラーを減らせる。形状を記号のままコンパイルできるため、この融合を多くの実行時形状へ再捕捉なしで適用できる。
## 品質への影響
演算の配置・融合・実行順序を最適化するシステムで、近似推論やモデル圧縮ではない。モデル品質を意図的に変える方式ではないが、浮動小数点演算順の変更に伴うビット単位の差は品質評価項目として扱っていない。
## 既存研究との差
CUDA Graphは起動費を減らすが既存カーネル境界を保持し、形状ごとの捕捉が必要になる。従来のTVM、XLA、torch.compileなどは主に演算子単位のコード生成とグラフ最適化を行う。既存メガカーネル研究は単一バッチの密モデルや特定の手書きスケジューラへ対象が狭い。Event Tensorはタイル完了イベントを記号形状の第一級中間表現にして、形状変化とMoEルーティングのデータ依存性を同じ抽象で表し、同じプログラムから静的・動的スケジューラを生成する点が異なる。
## 限界
実機評価はB200世代の単一ノードが中心で、異なるGPU世代や大規模複数ノードで同じスケジューリング交換条件が成立するかは未検証である。低バッチ分散推論ではCPU側スケジューリングと通信費が露出し、ETCがvLLMやSGLangを上回らない条件もある。静的方式はデータ依存の負荷偏りへ弱く、動的方式は規則的処理でキュー操作費が大きいため、最適方式の選択自体がワークロード依存である。現在の入力ではイベントテンソル付きタスクグラフを明示的に記述する必要があり、標準計算グラフから完全自動生成する高位パスは将来課題としている。
## 実装状態
Apache TVM上のコンパイラパス群として実装し、MLSys 2026採録版で8×B200の実機評価を行っている。論文は主要オープンソースシステムへ組込み済みと述べるが、arXivページでETC単体の公式コードURLは確認できない。
## 研究上の位置づけ
LLM推論のカーネル・ランタイム・コンパイラ系統に位置し、とくに常駐メガカーネルを実運用の動的形状とMoEへ拡張する研究である。サービング側の連続バッチや要求スケジューリングとは独立したGPUバックエンドとして利用でき、上位ランタイムが選んだバッチを低遅延に実行する役割を持つ。
