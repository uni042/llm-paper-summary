# Flex Attention: A Programming Model for Generating Optimized Attention Kernels

> 高速な融合注意カーネルを「注意変種ごとに手書きする」方式から、利用者が意味だけを書きコンパイラが高速カーネルへ落とす方式へ変える。FlexAttentionはスコア修正関数（score modification function; `score_mod`）とマスク関数（mask modification function; `mask_mod`）を高水準インターフェースにし、TorchInductorがFlashAttention型テンプレートへ融合する。疎なマスクはBlockMaskへ事前圧縮し、完全に不要なタイルを読み書き・計算しない。

## 概要

FlashAttentionは注意行列を高帯域メモリ（High Bandwidth Memory; HBM）へ実体化せず、タイル化とカーネル融合で非常に高速に実行する。しかし高速化の核がモノリシックな専用カーネルに埋め込まれるため、ALiBi、局所窓、文書マスク、PrefixLM、soft-cap、ページ化注意などの新しい注意変種を試すたびに専用実装が必要になる。

この問題を論文は「ソフトウェア抽選（software lottery）」と表現する。研究上は数行のPyTorch演算で記述できる変種でも、その組合せに最適化済みカーネルが存在するかどうかで実用速度が大きく変わる。複数の変種を合成すると組合せ数が増え、手書き実装を用意する方法はさらに破綻しやすい。

FlexAttentionは、注意そのものの実行骨格は高性能な手書きテンプレートとして保持し、利用者が変更したい意味だけを小さな関数で渡す。コンパイラはその関数の前向き・後向きグラフを解析して注意主ループへインライン化し、必要な演算融合と自動微分を行う。

さらにマスクの疎性はBlockMaskへ変換する。要素単位の巨大な (N	imes N) ブール行列を毎回読み込むのではなく、タイル単位で「全要素が有効」「一部のみ有効」「全要素が無効」を区別し、全無効タイルはカーネル自体が飛ばす。これが柔軟性を実際の高速化へ変換する第二の柱になる。

## 問題設定

従来のスケールドドット積注意では、(QK^T) を計算し、マスクや位置バイアスを加え、softmaxを通して (V) と積算する。注意変種の多くは、実はこの「softmax直前のスコアをどう変えるか」と「どの ((q,k)) 組を無効にするか」の違いとして表せる。

ところが一般的なPyTorch演算として注意行列を構築すると、(N^2) の中間テンソルやマスクをHBMへ書き出し、FlashAttentionが避けたI/Oを復活させてしまう。逆にFlashAttentionのCUDA/Tritonカーネルへ手作業で変種ロジックを入れれば速いが、実装・検証・後向き計算の負担が高い。

したがって必要なのは、利用者には高水準の関数記述を許しながら、実行時にはその関数呼出しを別カーネルとして残さず、融合注意の内側へコンパイルする仕組みである。

## 手法

### 1. `score_mod`でスコア変換を関数として記述する

`score_mod(score, b, h, q_idx, kv_idx)` は一つの注意スコアと、そのバッチ・ヘッド・クエリ位置・KV位置を受け、変更後スコアを返す。ALiBiなら位置差に比例するバイアスを足し、soft-capならtanh型の上限制約を掛ける、といった変種をこの一関数で表す。

重要なのは、利用者が注意行列全体を生成しない点である。コンパイル時に関数グラフを捕捉し、タイル内のスコアがレジスタ上にある段階へ演算を挿入するため、中間の (N^2) スコア行列を書き戻さない。

複数のスコア変換も通常の関数合成として記述できる。変種A×変種Bごとに専用カーネルを増やさず、意味の組合せをソース側で表現できる。

### 2. `mask_mod`をBlockMaskへ変換して疎タイルを飛ばす

`mask_mod(b, h, q_idx, kv_idx)` はその注意接続を許可するかをブール値で返す。因果マスク、スライディング窓、文書境界、PrefixLMなどを位置インデックスの条件式として書ける。

この関数を注意タイル内の全要素へ毎回適用するだけでは、柔軟でも高速ではない。FlexAttentionは事前にBlockMaskを構築し、注意行列をブロックへ分割して、完全有効ブロックと部分ブロックの位置だけを圧縮保持する。完全マスク済みブロックはリストに入らず、QK積そのものを実行しない。

完全有効ブロックでは要素ごとの`mask_mod`判定も不要で、部分ブロックだけに判定を適用する。これにより構造化疎性をGPUが扱いやすい連続タイルへ変換する。

### 3. 手書きテンプレートへコンパイラ生成コードを埋め込む

完全自動コード生成だけに頼るのではなく、FlashAttention型の高性能な注意主ループは専門家が用意したテンプレートとして残す。PyTorchのコンパイル基盤は`score_mod`と`mask_mod`の演算グラフを生成し、そのコード片を主ループへ組み込む。

このハイブリッド設計により、メモリ移動・タイル分割・オンラインsoftmaxなど性能へ強く効く部分は安定したテンプレートを使い、研究者が頻繁に変える意味部分だけをコンパイルする。後向き計算も自動微分（automatic differentiation; autograd）から生成できる。

すなわち入力はQ/K/Vと二つの小関数、出力はその意味を保った融合GPUカーネルであり、利用者がCUDA同期・共有メモリ・レジスタ配置を直接管理する必要を減らす。

### 4. ページ化注意でも論理インデックスを保つ

ページ化注意（PagedAttention）では、KVキャッシュの論理位置と物理メモリ位置が一致しない。利用者の`score_mod`/`mask_mod`を物理位置向けに書き直させると、抽象化が崩れる。

FlexAttentionは物理ブロックから論理ブロックへの写像をページテーブル更新時に保持し、カーネル内の物理KV位置を論理位置へ戻してから利用者関数を呼ぶ。論文はこの写像更新を定数時間の追加処理として構成する。

H100のケーススタディでは、FlexAttentionへページ化を加えた平均ランタイム増加は1%未満だった。論文が引用するvLLMの20〜26%の注意カーネル追加費用より小さく、専用の別ページ化カーネルを作らず間接アクセスを融合できる利点を示す。

### 5. 学習とデコードの両方を同じ抽象で扱う

学習時はQ/K長がともに大きく、前向きと後向きの両方が必要になる。デコード時はクエリ長1に対して長いKVを読むため、律速構造が異なる。FlexAttentionは同じ高水準記述を使いながら、コンパイラ側で学習用注意とデコード用テンプレートへ落とす。

グループ化クエリ注意（Grouped Query Attention; GQA）も扱え、PyTorch APIでは`enable_gqa`として公開されている。したがって特定の論文専用DSLではなく、通常のPyTorchモデルへ組み込むランタイム機能として設計されている。

## 評価

### 主な評価条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA H100（650W制限、HBM帯域2.4 TB/s）、A100（330W制限）、A6000 |
| データ型 | bfloat16 |
| カーネル評価 | KVサイズ256 MiB、ヘッド次元64、系列長1K〜64K（デコードは最大132K） |
| 注意変種 | noop、causal、ALiBi、sliding window、PrefixLM、soft-cap、document mask、neighbor attention |
| 比較対象 | FlashAttention-v2/v3、FlashDecoding、PyTorch SDPAのcuDNN・memory-efficient・math |
| エンドツーエンド学習 | torchtune、Llama 3-8B、Alpaca、文書マスク |
| エンドツーエンド推論 | gpt-fast、Llama 3.1-8B（1×H100）、Llama 3.1-70B（4×H100） |

### 代表結果

| 条件 | FlexAttentionの結果 | 読み方 |
|---|---:|---|
| 因果注意・学習前向き | FlashAttention-v2比1.00〜1.22倍 | 既に専用カーネルが強い基本形でも競合 |
| 因果注意・学習後向き | 0.86〜1.05倍 | 全条件で専用カーネルを上回るわけではない |
| 7注意変種、FAv2がネイティブ対応 | 0.68〜1.43倍 | 柔軟性の代わりに一部条件では性能低下もある |
| FAv2が未対応でSDPA要素マスクへフォールバック | 5.49〜8.00倍 | 専用実装がない「ソフトウェア抽選」を避ける効果が大きい |
| デコード、クエリ長1 | FlashDecoding比0.93〜1.45倍 | 通常条件ではほぼ同等〜上回る |
| GQA + ALiBiデコード | 5.37倍 | FlashDecoding側に専用最適化がない組合せで大差 |
| BlockMask除去との比較 | 1.3〜1.8倍高速 | ブロック疎性利用が主要因 |
| Llama 3.1-8B推論 | SDPA比1.22〜2.04倍 | 系列長が長いほど注意カーネル差が全体速度へ出る |
| Llama 3.1-70B推論 | SDPA比0.99〜1.66倍 | 短め条件ではほぼ同等のケースもある |
| ページ化注意 | 平均追加費用1%未満 | 論理→物理写像を融合してページ管理費を小さく保つ |

論文は数値誤差も比較し、FlexAttentionがfp16/bf16で基準カーネルに対して追加の数値誤差を導入しないことを確認する。これは近似注意ではなく、指定した注意意味を融合実行するプログラミングモデルである。

### エンドツーエンドで効く条件

torchtuneの文書マスクでは、SDPAが (B	imes N	imes N) のブールマスクを読み込むため、系列長2Kから8Kへ伸ばすと学習スループットが25%落ちる。一方FlexAttentionはBlockMaskと (B	imes N) の文書IDを使い、長文でより良くスケールする。

論文全体ではエンドツーエンド学習を2.4倍超、推論を最大2.04倍改善した。ただしこれは「どの注意変種でも2倍」という意味ではなく、既存基盤が巨大な要素マスクや非最適フォールバックへ落ちる条件で差が拡大する。

## 既存研究との差

FlashAttentionは高性能な特定注意パターンを手書き最適化する。PyTorchのスケールドドット積注意（Scaled Dot-Product Attention; SDPA）は複数バックエンドを選べるが、変種によっては要素単位マスクへフォールバックする。

FlexAttentionは両者の中間ではなく、**高水準の意味記述から高性能な融合カーネルを生成する層**を追加する。高速な主ループをテンプレートとして固定することで純粋な汎用コンパイラより性能予測性を持ち、利用者関数をコンパイルすることで専用カーネル群より組合せ爆発へ強い。

BlockMaskも単なる疎行列フォーマットではなく、任意の`mask_mod`から自動生成され、完全有効タイルと部分タイルを区別して要素判定を必要な場所だけへ限定する。この接続がプログラマビリティとGPU効率を両立させる。

## 限界・実装状況

全変種・全GPUで手書き最良カーネルを上回るわけではない。実測でもFAv2対応変種では0.68倍、学習後向きでは0.86倍まで落ちる条件がある。極端に特殊なデータ依存ロジックやブロック疎性へ落としにくいマスクでは、テンプレートとコンパイラが十分な最適化を見つけられない可能性がある。

BlockMaskはマスク生成・保持の前処理を必要とするため、マスクが頻繁に完全変更される短い処理では固定費用が相対的に大きくなり得る。ページ化注意もGPUメモリ内のKVページを前提とした評価で、ホストやSSDへのスワップ費用は扱っていない。

一方、研究プロトタイプのままではなくPyTorch本体の`torch.nn.attention.flex_attention`へ統合されている。論文artifactはPyTorch 2.5+、NVIDIA計算能力8.0+、AMD ROCm 6.2+を対応範囲として記載し、H100/A100向け再現手順も公開する。現在のPyTorch APIではBlockMask生成、GQA、スコア修正などが直接利用できる。
