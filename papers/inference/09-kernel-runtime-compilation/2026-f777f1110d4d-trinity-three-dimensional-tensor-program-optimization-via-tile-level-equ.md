# Trinity：タイル単位の等価性飽和によるテンソル計算の三次元共同最適化

## 概要

Transformerの推論カーネル最適化では、計算グラフ上の演算融合・代数変形と、GPU上のタイル分割・共有メモリ配置・並列化を別々のコンパイラ段階で決めることが多い。しかし、どの演算を融合するのが最適かはタイル内に中間値を保持できるかに依存し、どのタイル構成が最適かは計算式をどう変形したかに依存する。この分離によって、FlashAttentionのように代数変形とデータ移動・実行順序を同時に変える最適化を一般的なコンパイラが自動発見しにくい。

Trinityは、代数的同値性、メモリ入出力（I/O）、計算の実行構成という三つの相互依存する軸を、タイル単位の中間表現（intermediate representation、IR）で一体的に表す。等価性飽和（equality saturation）によって多数の意味的に等価なプログラムを一つの等価グラフ（e-graph）へ圧縮し、メモリ読み書きとループの意味を守りながら書き換える。さらに、カーネル内のロードとカーネル境界を越えるロードで費用が違うことを考慮した二段階の候補抽出を行い、最終的にはGPU上で候補を実測して最速を選ぶ。

原著は、通常のTransformerだけでなく、事前正規化（Pre-Norm）、QK正規化（QK-Norm）、KeyFormer、RoCo、SwiGLUのフィードフォワード網などで、TensorRTやTorchInductor、Mirage、FlashInferと比較する。H100のLLaMA3 8B相当構成ではTensorRTに対し通常Transformerで1.71倍、事前正規化で1.43倍、QK正規化で1.63倍などの高速化を報告する。論文全体の最大値はTensorRT比2.09倍、TorchInductor比2.35倍、Mirage比3.07倍である。ただし、これは指定したブロックのGPUカーネル実測であり、LLMサービス全体のトークン生成速度ではない。

## 問題設定

従来のグラフ最適化は、テンソル演算の順序変更や融合、代数的な等価変形を扱うが、各演算の内部でどのタイルを読み書きするかは見えない。一方、演算子単位のコンパイラは、既に固定された計算グラフに対してループやメモリ配置を調整するが、演算子境界を越える式変形ができない。この二段階方式では、最終的に同じ数式を計算する複数の実行戦略のうち、メモリ帯域・共有メモリ容量・GPU世代に適したものを横断的に探索できない。

FlashAttentionは代表例である。通常の注意では`QK^T`、Softmax、`PV`を別々に処理すると中間の二次元注意行列をメモリへ書き戻す。オンラインSoftmaxへ式を組み替え、問い合わせ・鍵・値をタイル単位で処理し、最大値・分母・出力累積を共有メモリに保持することで、大きな中間行列の書き戻しを避けられる。これには代数変形、メモリ配置、ループ順序・融合の三つが同時に必要であり、単一の演算子を高速化するだけでは発見できない。

さらに、全結合層のQKV投影と注意を融合すれば、Q、K、Vを全頭についていったん書き出してから読み直す費用も削れる可能性がある。しかし、頭単位の投影と注意の反復空間が一致するか、ループを融合しても依存関係が破れないか、オンチップ容量に収まるかを同時に判定しなければならない。Trinityの狙いは、こうした手作業の熟練を必要とする変換を、正しさを保ちながら自動的に探索することである。

## 手法

### 1. タイルを第一級に扱う中間表現

TrinityのIRは、タイルに対する明示的な`load`と`store`、行列積や要素ごとの算術、縮約、指数関数、形状変更、`seq`による逐次実行、`loop`による繰り返しを持つ。テンソルの宣言では、入力・出力は大域メモリに置き、中間変数はオンチップにも大域メモリにも配置できることを区別する。タイルは例えば64×64のようなGPUで処理する小ブロックであり、演算の意味を保ちながら、どのタイルをいつロードし、どこへ保持し、どのループを一つのカーネルにするかを変更できる。

グラフ最適化のようにテンソル演算だけを見るのでも、Tritonのように低水準の実装構文をすべて直接探索するのでもなく、ハードウェアで意味のあるタイル粒度を選ぶことが重要である。ここではループ融合・分割・不変式の移動、代数的因数分解、行列演算の変形が、同じIR上の書き換えとして表される。読み書きの順序を変える場合は、書き込み先と読み出し先の重なり、ループ間依存、元の計算の意味が変わらないことを検査する。

### 2. 状態を持つプログラムに対する等価性飽和

等価性飽和は、式を書き換えたら古い式を捨てる方式ではなく、等価な式を等価クラスへ追加していく。例えば`(a×2)+(a×2)`に分配則を適用すると`a×(2+2)`が同じ等価クラスに含まれ、定数畳み込みによって`a×4`も同時に保持できる。最終的なハードウェア費用が分かるまで一つの表現へ決め打ちしないので、先の局所変換が後の最適化を妨げにくい。

ただし、メモリ読み書きやループは純粋な数式ではない。`store`を無制限に入れ替えると、後続の`load`が読む値が変わり得る。Trinityはメモリ操作を明示したまま代数変換を可能にする式伝播、逐次命令列の右結合正規化による等価グラフの増殖抑制、意味的依存関係の検査を導入する。書き換えの候補が多くても、意味を保存しない変換を排除し、表現の冗長な組合せを削ることで探索を現実的にする。

ループ変換には、ループ融合、分割、不変式の外出し、逆向きのループ挿入、ループ本体の代数的因数分解がある。興味深いのは、計算回数を増やすループ挿入も候補に含める点である。通常の最適化では冗長な再計算を避けるが、少量の再計算を許してカーネル間のメモリ往復や起動費用を減らす方が速い場合がある。したがって「演算回数が最小の式」が必ず「GPU上で最速の式」ではない。

### 3. コンテキスト依存の費用と二段階抽出

等価グラフから最速候補を抽出する際、ロードの費用はどのループ・カーネルに属するかで変わる。中間タイルが同じカーネル内の共有メモリに残るなら安いが、カーネル境界を越えてHBMへ書き戻すなら高い。通常の等価グラフの最小費用抽出はノードごとに固定の費用を置くため、この差を表現しにくい。Trinityはまずループ構造を選んで実行コンテキストを定め、その後にその構造に応じた演算・メモリ費用で候補を抽出する二段階方式を使う。

抽出後はIRをTritonのGPUカーネルへ変換し、候補をプロファイルして実測で選ぶ。等価性飽和によって膨大な等価プログラムを列挙せずに保持し、候補抽出ではモデル化した費用で絞り込み、最終的に実機測定でGPU固有の事情を反映する。この構成は純粋な静的費用モデルだけに依存するものではない。論文ではベンチマークごとに最大512候補を抽出し、プロファイル段階を8 GPUで並列化している。

### 4. 注意の完全融合の自動発見

通常の注意を初期IRとして与えると、TrinityはまずオンラインSoftmax型の演算へ式を組み替え、部分的な縮約と正規化をタイルループへ移す。さらに代数的因数分解でループ内の不要な依存を取り除き、注意全体を一つのカーネルへ融合する。ここまでは手作業で設計されたFlashAttentionと同等の構造である。

さらにTrinityは、前段のQKV投影と頭ごとの形状変更を融合し、注意のループと反復空間を合わせる。QKVを全頭分作って保存する代わりに、頭ごとにQKVを計算して直ちに注意へ渡す。ループ変数が異なっても反復回数が同じ場合は、反復空間を再添字付けして融合可能と判定する。これによりQKV投影、形状変更、注意を単一カーネルで実行し、途中のQなどを大域メモリへ書き戻す費用とカーネル起動・同期を減らす。原著ではH100で手作業のFlashInfer実装に対して最大1.35倍の性能改善を報告する。

### 5. モデル差分とGPU差分への適応

事前正規化ではRMSNormをQKV投影の前に実行する必要がある。Trinityはループ挿入で正規化の計算を投影ループへ持ち込み、分配則と因数分解でスケーリングや依存を整理し、正規化後の中間テンソルを大域メモリへ書き出さずに注意へつなぐ。KeyFormerやRoCoでは、注意に加えてKVキャッシュの追跡・破棄に関係する追加の縮約やスコア演算があるが、これらも単一カーネルへ含める候補を探索できる。

GPUごとの最適解も同じとは限らない。H100のように帯域が広い装置では、中間タイルを一時的にHBMへ退避して共有メモリの圧迫を減らし、大きなタイルを使う方が速い場合がある。一方RTX 4090では、追加のHBM転送が律速になりやすく、タイルを小さくしてでも中間値をオンチップに残す方が速い条件がある。Trinityは両方を意味的に等価な候補として保持し、GPUごとに別のカーネルを選択できる。

## 評価

### 実験条件と比較範囲

論文はLLaMA3 8B相当（隠れ次元4096、32頭）とFalcon 7B相当（隠れ次元4544、71頭）の二構成で、通常Transformer、Pre-Norm、QK-Norm、KeyFormer、RoCo、SwiGLU FFNの6種類を対象とする。投機的復号の検証に相当する16トークンのブロックを、1008トークンの接頭辞の上で検証し、KVキャッシュ長1024とする。測るのは主として注意ブロックまたはFFNの**カーネル遅延**であり、サーバの連続バッチ処理やネットワークを含む生成全体の処理量ではない。

比較対象はTensorRT 10.10.0.31、TorchInductor 2.8.0、FlashInfer 0.5.3、FlashTensor、Relax、Mirageなど。GPUはA100 40GB、H100 80GB、RTX 4090、RTX 5090で、著者らは浮動小数点演算順序による丸め差を除いて元のプログラムと数値的に同等であることを検証した。GPU世代により利用可能な比較先が異なり、MirageはRTX 5090をサポートしていないため、全組合せで同一の比較表が揃うわけではない。

| H100・LLaMA3 8B相当のブロック | TensorRT比の高速化 |
|---|---:|
| 通常Transformer | 1.71倍 |
| Pre-Norm | 1.43倍 |
| QK-Norm | 1.63倍 |
| KeyFormer | 1.29倍 |
| RoCo | 1.37倍 |
| SwiGLU FFN | 1.10倍 |

論文全体の複数GPU・モデル構成における最大値はTensorRT比2.09倍、TorchInductor比2.35倍、Mirage比3.07倍である。これらは上表の同一条件に必ず対応するわけではないため、全条件でその倍率を達成したとは言わない。通常Transformerでは手作業で高度に最適化されたFlashInferに対してH100で1.35倍であり、単なる未最適化PyTorch実装との比較だけではない。Pre-NormではMirage比1.40倍の例を示し、RMSNormを投影・注意へ融合したことの効果を分離している。

### ハードウェア適応と探索時間

KeyFormerでは10通りのGPU・モデル構成に対して8種類、RoCoでは5種類の最速カーネルが見つかっており、一つの固定カーネルを全装置へ流用していない。H100では大きなタイルを使うため途中で大域メモリへ一時退避する戦略が有利になる例があり、RTX 4090ではオンチップに中間値を保持する小タイル戦略が勝つ。前者の広い帯域と後者の帯域制約の差を実測で示すことで、メモリI/Oとループ構成を共同探索する必要性を裏付ける。

コンパイル時間の比較では、Mirageの全列挙探索は演算子数が増えると探索が急増し、11演算子を超える大きなプログラムは分割なしで扱えない。TrinityはQK-Normの21演算子、RoCoの22演算子、SwiGLU FFNの12演算子を分割せず、それぞれ375秒、710秒、266秒で最適化できると報告する。等価グラフは10の17乗を超える等価候補の空間を圧縮して扱えるが、これは**10の17乗個の実カーネルをコンパイルして測定した**という意味ではない。候補抽出とプロファイルによって探索を絞り込む。

公開再現実験資材では、最適化器で候補IRを生成し、Tritonカーネルへ変換し、GPU上のプロファイルで最良候補を選んで比較する三段階の手順を示す。実測は3回測定した最小値を報告する方式であり、負荷変動下の中央値やp99遅延を測ったものではない。比較先の一部には手作業の調整が必要で、比較の公平性は各実装の設定にも依存する。

## 既存研究との差

TensorRTやTorchInductorは生産環境で使われるコンパイラであり、既知の融合や演算子内の最適化に強い。一方、Trinityは計算グラフをまたぐ代数変形と、タイル単位のメモリ・実行順序を同時に変更する。FlashInferは注意の手作業カーネルに強いが、前後のQKV投影やモデル固有の追加演算まで自動で一体融合する一般的な探索器ではない。Trinityは注意自体のオンラインSoftmax構造を再発見した上で、さらに前段を融合する。

Mirageも共同最適化を目指すが、メモリI/Oとループ構造を第一級の書き換え対象にせず、探索空間が大きくなると分割や全列挙の限界に直面する。TrinityはタイルIRの意味を保つ書き換えと等価グラフの共有によって、全体を分割しない候補探索を可能にする。特徴は「等価性飽和を使う」ことだけでなく、状態を伴うタイルプログラムに対する意味保存、実行コンテキスト依存の費用モデル、実機プロファイルを結合した点にある。

## 限界

第一に、実験は選ばれたTransformer変種と入力形状のカーネル最適化であり、一般的なLLMサービング全体の速度向上を直接示さない。モデルの量子化、複数要求のスケジューリング、CPU/GPUオフロード、MoEのエキスパート配置、長文脈の動的なバッチ分布で同じ倍率が得られるとは限らない。入力の形状やGPUが変われば最適カーネルを再選択する必要がある。

第二に、候補の探索とプロファイルには時間とGPU資源が必要である。研究では最大512候補を抽出し、8 GPUで並列プロファイルしており、利用者の単一GPU環境で同じ探索時間・性能を再現できるとは限らない。コンパイルに数百秒を費やす方式は、静的形状や繰り返し利用されるカーネルには向くが、頻繁に変化する入力形状へ毎回適用するには費用対効果の検討が必要である。

第三に、書き換えは数学的な意味の保存を検査するが、浮動小数点の演算順序変更による丸め差はあり得る。論文は元プログラムとの数値的な同等性を検証したが、厳密なビット一致を主張していない。特定のモデルの最終生成品質や確率分布がどの程度変わるかを包括的に測った研究でもない。

第四に、IRはタイルを基本とした規則的な計算に適する。データ依存の不規則な制御や特殊なハードウェア演算を扱う場合、表現・書き換え規則・費用モデルを拡張する必要がある。既存の手作業カーネルを全用途で置き換えたとは言えない。著者らが示す価値は、対象範囲で熟練者の複合最適化を自動探索できることにある。
