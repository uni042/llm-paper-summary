# Syncopate：通信チャンクと計算タイルの依存を利用したマルチGPU演算の自動重畳

## 概要

複数GPUへ分割したLLMの学習・推論では、行列積や注意計算の途中で他GPUのデータを集めたり、計算結果を他GPUへ還元したりする。GPUの演算性能が高くても、全収集（AllGather）、還元散布（ReduceScatter）、全還元（AllReduce）などの通信待ちが処理時間を支配することがある。通信と計算を異なるCUDAストリームで同時実行する従来方式は、しばしば**カーネル全体**を単位として重ねるため、入力データの一部が先に到着しても、その部分を処理する計算を開始できない。カーネル起動と全体同期の費用も生じる。

Syncopateはこの粒度を、**通信チャンク（chunk）**と**計算タイル（tile）**へ細分化する。局所的なTritonカーネルとGPU間の通信計画を入力し、各タイルがどの通信チャンクを必要とするかを解析する。データが到着したタイルから計算するよう順序を書き換え、必要な待機信号と非同期通信を自動挿入する。論文の中心は新しいLLMモデルや注意数式ではなく、**分散演算子の通信・計算スケジュールをコンパイルする基盤**である。

著者はNVIDIA H100を8基、NVLink接続した単一ノードで、Llama-3/Qwenの層形状に基づく行列積と注意演算を評価した。全体平均1.3倍、最大4.7倍の高速化を報告し、特定の高度に最適化された手書き行列積と比較した性能は4GPU時で平均99.8%、8GPU時で104%だった。ただし、これらの数値は比較群や演算形状が異なる集計であり、4.7倍が全LLMのエンドツーエンド生成速度に当てはまるという意味ではない。

## 問題設定：粗い通信・計算重畳の限界

### カーネル境界が不要な待ちを生む

GPU `A` が計算した結果をGPU `B` が使うとき、すべての転送が完了するまで`B`側の大きな計算カーネルを待たせると、先に到着したデータの計算資源が遊ぶ。逆に計算カーネル全体を通信と重ねる設計では、必要データの到着とタイルの実行時刻を正確に合わせられない。通信を複数の小さいカーネルへ分割すれば重畳機会は増えるが、起動費用、同期、通信断片化が増える。

さらに、最も遅いタイルや最後の通信チャンクが全体の終了時刻を決める**通信尾部（communication tail）**が生じる。実行順序をデータ到着順に合わせれば、この待ちを短縮できる可能性がある。しかし、各演算子の手書きカーネルへ通信・待機処理を埋め込む方法は、行列形状、GPU数、転送経路が変わるたびに再実装を要する。

### グローバルな分割計画と局所カーネルの間の欠落

分散コンパイラは、どのテンソルをどのGPUへ置き、どの集団通信を行うかという大局的な計画を探索できる。一方、局所カーネルはTriton等で高効率に書かれる。この二つの中間に、通信チャンクの到着と計算タイルの依存を結び付ける層がないため、良い分割計画があっても**演算子内部での細粒度重畳**を活かしきれない。Syncopateは分割計画を置き換えるのではなく、その実行段階を最適化する。

## 手法：通信計画から実行可能な分散カーネルまで

### 1. 入力は局所Tritonカーネルと通信計画

開発者は通常の単一GPU向けTritonカーネルを書き、計算タイルの形状、タイル識別子、タイルを列挙するスケジューラに軽量な注釈を付ける。注釈は数値計算の意味を変えず、どのプログラム反復がどのタイルを処理するかをコンパイラへ知らせる。通信側には、どのGPUからどのGPUへ、どのテンソル領域を、どの順序で移動するかを表す計画を渡す。

通信計画は手作業のテンプレートから作成してもよく、既存の分散コンパイラの中間表現から変換してもよい。これにより、利用者が全収集や還元散布の通信順序を選んだ後、Syncopateが細粒度の計算重畳を実現するという責任分離ができる。カーネル利用者が通信と計算の同期命令をすべて手書きする必要はない。

### 2. 通信チャンクの抽象化：タイルより大きく、テンソル全体より小さい

チャンクは**一度の論理通信として扱うテンソル領域**であり、内部に一つ以上の計算タイルを含む。チャンクの大きさは論理的な転送単位を表し、実際にどの通信命令で運ぶかとは独立している。この中間粒度を設けることで、タイル単位の過剰な同期を避けつつ、テンソル全体を待つ粗い同期より細かく実行できる。

通信演算は大きく二種類である。点対点転送（P2P）は、送信元ランク、送信先ランク、対象チャンク、依存先を持つ。送信側が転送を起動するpushと、受信側がデータを要求するpullの双方を表現できる。集団通信（Collective）は、AllGatherやReduceScatterなどの種別、参加ランク、入力・出力チャンク、依存先を持つ。各演算は他ランクの先行演算を参照できるので、リング状の段階的転送や複数段の還元も表現できる。

この抽象化は、通信経路そのものをGPUのコピーエンジンやSM命令へ早期に固定しない。したがって同じ通信計画を複数の物理的転送方式へ変換でき、実機に合わせた自動調整が可能になる。

### 3. 既存コンパイラの中間表現から通信計画を生成

分割に基づく中間表現（partition-based IR）では、各テンソルのGPU配置と論理的な分割境界から、必要な転送と集団通信を推定する。ループに基づく中間表現（loop-based IR）では、ループの通信点と反復範囲を解析し、連続する転送をチャンクへまとめる。どちらも最終的には共通のチャンク依存グラフへ変換する。

原著はDomino、Alpa、Mercuryの既存通信計画を受け取る統合を評価した。これらの分散コンパイラが探索した**グローバルな並列化戦略は固定**し、Syncopateによる演算子内部の実行方式だけを変更している。したがって統合時の性能差は、全く異なるモデル分割戦略を比較した結果ではなく、同じ大局的計画をどれだけ細かく実行できるかを比較したものである。

### 4. チャンク・タイル依存グラフを構築

コンパイラは、各チャンクの生産者・消費者と通信演算間の順序制約を解析する。計算側のタイル識別子、テンソルの配置、チャンクの軸情報を用いて、どのタイルがどのチャンクを読む・書くかを特定する。例えば、ある行列積タイルが別GPUから到着するチャンクを必要とするなら、そのチャンクの転送完了前にタイルを実行してはならない。一方、別チャンクだけで計算できるタイルは待つ必要がない。

この依存関係から必要最小限の待機点を挿入し、タイルスケジューラを**通信の到着順に沿う実行順序**へ書き換える。局所Tritonカーネルの演算内容を変更せず、タイルを処理する順番と非同期通信・同期だけを変えることが狙いである。これによりデータ競合や未到着データの読み取りを防ぎつつ、通信と計算の時間を重ねる。

### 5. 同じ通信計画を複数の物理バックエンドへ変換

論理的に同じチャンク転送でも、ハードウェア上では複数の実装がある。Syncopateはコピーエンジン、テンソルメモリアクセラレータ（TMA）を専用SMまたは計算と同居するSMで利用する方式、ロード・ストア命令を専用SMまたは同居SMで実行する方式など、五つの実装経路を扱う。転送専用資源を使えば計算SMを温存できる一方、小さな転送や還元を大量に行う場合は命令経路の方が適することもある。

同じチャンク依存グラフを保持したまま物理経路だけ差し替えられるため、通信アルゴリズムを作り直す必要がない。GPUのストリーミングマルチプロセッサ（SM）の一部を通信へ割り当てる場合には、その数も自動調整対象にする。通信へSMを割り当てすぎると行列積が遅くなり、少なすぎると帯域を使い切れないためである。

### 6. 通信中心の自動調整：チャンクサイズ・SM・タイル順序

通信と計算の重畳効率は、チャンクを細かくすれば単調に改善するわけではない。大きいチャンクは一回の転送効率が良いが重畳できる回数が少ない。小さいチャンクは早く計算を始められるが、転送管理と同期の費用が増える。Syncopateはチャンク分割数、転送バックエンド、通信へ割り当てるSM数、計算タイルの形状・巡回順序を探索する。

候補生成時には、コピーエンジンが効率よく扱える最小転送量、TMAのアラインメント制約、共有メモリ容量など、実行可能性の制約を満たさない構成を除外する。グローバル通信計画は維持したまま、局所的な実装パラメータだけを調整するため、既存の分散コンパイラによる並列化探索と組み合わせられる。

### 7. 実行時の流れ

利用者が局所Tritonカーネルと通信計画を登録すると、コンパイラはチャンク・タイルの依存を作り、通信を待つ必要のあるタイルと先に計算できるタイルを分ける。次に複数の転送経路とタイル順序を生成し、対象GPUで調整して高速な構成を選ぶ。生成した分散演算子はランク数・GPUメッシュなどの実行時情報を受け取り、データ到着を信号で確認しながらタイル計算を進める。元の局所カーネルを通信と同期のために手作業で全面改修しなくてよい点が、手書きの細粒度重畳カーネルとの差である。

## 実装・再現可能性

実装はTritonを対象とするソース変換コンパイラと実行時ライブラリで構成される。通信計画、信号生成、通信コード生成、計算カーネル変換、分散演算子インターフェースをモジュール化している。原著のアーティファクト付録にはCPUだけで実行できる依存解析・変換の単体試験と、複数GPUを使う正当性・速度試験の両方が記載されている。

固定されたアーティファクト評価版のGitコミットは `ce2b13e496eb6629ab42aac2aec1d9e31e084ba6` である。CPU側のコンパイラ単体試験はLinux、Python 3.10以上、PyTorch、pytestで実行可能だが、論文の性能値を再現するにはNVLink/NVSwitch接続のHopper級GPUを4基または8基搭載したLinuxノード、DockerとNVIDIA Container Toolkit、比較対象の外部実装が必要である。外部の比較方式すべてが公開リポジトリへ同梱されているわけではない。

## 主要結果

### 全体的な高速化の範囲

論文要旨は、複数GPUの演算子を含む評価で**平均1.3倍、最大4.7倍**の高速化を報告する。この数値は、手作業最適化済みカーネルから単純なNCCL呼び出しまで幅広い比較対象を含む。最大値を一般的なLLM推論の高速化倍率とみなすことはできない。Syncopateが最も有利になるのは、通信・計算をカーネル境界でしか重ねられず、チャンクの到着順を活用できていない比較方式である。

### 高度な手書きGEMMとの比較

| GPU数・対象 | 原著の結果 | 解釈 |
|---|---|---|
| 4基H100、AG-GEMM/GEMM-RSを中心とした最良手書き実装 | Syncopateは平均**99.8%**の性能 | 自動生成でも手書き最速とほぼ同等 |
| 8基H100、同様の最良手書き実装 | Syncopateは平均**104%**の性能 | 通信チャンクをまとめて同期点を減らす利点 |
| GEMM-AR、小規模7B/8B形状 | TritonDistributedをやや下回る | 全条件で最高速ではない |
| GEMM-AR、大きなモデル形状 | 大規模になると最上位の性能 | 規模に応じた重畳計画の効果 |
| リング注意・長系列・8GPU | 比較方式より良好な傾向 | 通信と計算の交互進行を細かく調整できる |

4GPUで99.8%という値は「最良比較方式より0.2%だけ遅い」程度を意味するが、これは集計された演算子集合の平均である。個々の演算子や形状では上下する。8GPUで104%となる理由として、論文は複数タイルを通信チャンクへまとめることで細かい完了確認と同期点の数を減らし、重畳を維持しながら制御費用を抑える点を挙げる。

### 既存分散コンパイラとの統合

Domino、Alpa、Mercuryが選んだ通信計画を固定してSyncopateへ渡すと、4GPU・8GPUのGEMMと注意で、各コンパイラが元々生成する演算子より終了遅延が短くなった。ここで比較しているのは**分割戦略そのものの良否ではない**。同じ通信順序を用いても、通信チャンクと計算タイルの依存を見てカーネル内へ通信を配置すれば追加の利得が得られるという実証である。

分割に基づくDomino/Alpaとループに基づくMercuryの双方を同じ通信チャンク表現へ落とせることは、コンパイラを特定の一つの並列化アルゴリズムへ固定しないという設計目標を裏付ける。各比較方式の元実装とSyncopate統合版の正確な倍率は演算子・GPU数によって異なるため、論文要旨の最大4.7倍を全統合例へ一律に適用しない。

## 構成要素除去・感度分析

### 通信バックエンド選択

同じ論理通信計画でも、コピーエンジン、TMA、SMのロード・ストアで実行速度は大きく変わる。AG-GEMMとGEMM-RSではコピーエンジンとSM内TMAが高いTFLOPSを示し、単純なCUDAロード・ストア方式は帯域を使い切れない場合がある。最良と最悪のバックエンドの差は、Syncopateと複数の比較方式の差に匹敵し得る。したがって通信の重畳を自動化するだけでなく、**転送手段をハードウェア・演算子ごとに選ぶこと**が重要である。

### 通信SM数

405Bや70B由来のGEMM形状で、通信へ割り当てるSM数を変えると中間に最適点が現れる。少なすぎるとGPU間通信の帯域を使い切れず、多すぎると主計算に必要なSMを奪う。モデル形状によって最適な割当数が変わるため、固定比率を全演算子に使うより自動探索が有利になる。これは「通信を多く並列化すれば必ず速い」という単調な関係ではない。

### チャンク分割数

A2A-GEMMやGEMM-ARでは、通信チャンクを一つの巨大領域として扱う場合も、極端に細かく分ける場合も効率が悪くなる。原著の感度試験では、GEMM-ARで**2～3分割、約128MB**付近が良好な例として示される。大きいチャンクは転送効率が高いが重畳の機会が少なく、小さいチャンクは多くの信号・同期費用を発生させる。最適値は演算子、GPU数、転送経路で変わるため、128MBを普遍的な推奨値とするのは誤りである。

### タイル巡回順序と共有メモリ

同じ計算タイル集合を処理しても、タイルの巡回順序を変えるとデータ到着待ちと局所性が変化する。原著はタイル形状、パイプライン段数、共有メモリ消費量を変えた有効な候補を比較し、適切な順序が計算と通信のバランスを改善することを示した。単純なタイル番号順では、先に届いているチャンクのタイルを後回しにしてしまう可能性がある。依存を守る範囲で実行順序を変えること自体が最適化対象となる。

## 既存研究との差

NCCLとTritonを別々に起動する方式は実装が容易だが、通信が終わるまで計算の一部を待たせやすい。Domino、Alpa、Mercuryなどの分散コンパイラは大局的な通信計画を探索できるが、生成した演算子内部のタイル・チャンク依存に基づく実行までは十分に扱わない。ThunderKittensやTritonDistributed、AsyncTP、Fluxなどは手書きまたは専用DSLによる細粒度重畳を実現するが、異なる演算子へ移植するには通信と計算の手作業での統合が必要になる。

Syncopateは**既存の局所Triton計算**と**高位の通信計画**を分離したまま入力し、間を埋める依存解析・コード生成・バックエンド調整を自動化する。分割アルゴリズムを新たに発明するのではなく、既存アルゴリズムの実行時に生じる待ちを削減するためのコンパイラ層である。この区別によって、なぜ高位コンパイラと競合せず組み合わせられるかが理解できる。

## 限界・適用範囲

**主な実験は単一ノードのHopper級マルチGPUである。** 8基H100とNVLink総帯域900GB/秒を用い、複数ノードをまたぐネットワーク転送の本格的な速度試験は主要評価の対象外である。異なるGPU世代やPCIe接続、低速ネットワークでは最適なチャンクサイズや通信経路が変わり、同じ倍率は保証されない。

**GPU間通信がない単一GPUのローカルLLMには直接の利点がない。** 本研究の最適化対象は複数GPUでのGEMM・注意の通信重畳であり、RTX 4070 Super 12GB単体でのCPUメモリオフロードやWindows上のllama.cppの復号速度改善を示すものではない。単一GPUのメモリ不足に対する階層オフロード研究とも異なる。

**TritonとCUDA系通信機構への依存がある。** 現行実装はTritonソース変換とNVSHMEM、TMA等を対象とし、任意の言語やGPUバックエンドへそのまま適用できない。著者は他の領域特化言語（DSL）への拡張を今後の課題としている。TMAのアラインメントや通信エンジンの転送サイズ制約など、物理的な制約を満たす必要がある。

**実際のエンドツーエンドLLM生成速度は別問題である。** 主要な評価はLLM由来の形状を持つ分散演算子であり、モデルの重み読込み、KV割当、CPUスケジューリング、推論サービス全体の通信をすべて含んだ性能ではない。全体平均1.3倍、最大4.7倍という要旨の数字を、すべてのLLMサービスへ適用することはできない。

**通信計画と局所タイルの構造が必要である。** 利用者は局所Tritonカーネルへタイル形状・識別子・巡回順序の注釈を付け、通信計画を指定または高位コンパイラから受け取る。任意のブラックボックス演算子の内部を何も知らずに最適化する方式ではない。動的な形状や複雑な依存が増えるほど解析と再調整の費用が問題となり得る。

**再現には外部実装と十分なハードウェアが必要である。** 公開アーティファクトのCPU単体試験は比較的容易だが、論文の全性能値を再現するには4～8基のHopper GPU、NVLink/NVSwitch、Linux、Docker、NVIDIA Container Toolkit、および比較対象の外部実装が必要である。論文は外部比較方式がすべて同梱されていないことを明記している。
