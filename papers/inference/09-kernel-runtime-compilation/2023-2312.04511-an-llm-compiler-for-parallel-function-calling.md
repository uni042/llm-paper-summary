# LLMCompiler：依存関係を解決してツール呼出しを並列化する実行基盤

## 概要

言語モデルに検索、計算、データ取得などの外部関数を使わせる場合、素朴な方式では「一つの関数を呼ぶ、結果を読む、次の関数を決める」という往復を繰り返す。独立した検索が複数あるだけでも、各関数の待ち時間とモデルの再推論時間が直列に積み重なる。複数の関数をまとめて呼べる仕組みがあっても、ある関数の出力を別の関数の入力へ渡す依存関係や、途中結果に応じて実行計画を変える問題は残る。

LLMCompilerは、このツール呼出しをコンパイラに似た三段階へ分離する。関数呼出し計画器（Function Calling Planner）が問題をタスクへ分解し、依存関係を持つ有向非巡回グラフを生成する。タスク取得器（Task Fetching Unit）が依存先の結果を変数へ代入し、実行可能になったタスクを実行器（Executor）へ送る。実行器は依存しない関数を非同期に並列実行する。必要なら実行結果を計画器へ戻し、新しいタスクグラフを作る。

原著の2024年改訂版では、GPT系モデルとLLaMA-2 70Bを用いて、独立な関数群、複雑な依存関係、途中結果に基づく再計画を評価した。HotpotQAでは逐次方式ReAct比1.80倍、Movie Recommendationでは3.74倍、依存付きParallelQAでは最大2.27倍の遅延改善を報告する。これは外部関数の待ち時間とLLM呼出し回数を削減したアプリケーション層の効果であり、モデル一回のトークン生成速度を3.74倍にした結果ではない。

## 問題設定

質問が複数の情報源を必要とするとき、例えば二つの企業の時価総額を別々に検索して比較する処理では、検索二件は互いに独立している。最終的な比較計算だけが両方の検索結果を必要とする。ReActのように検索結果を一件ずつ観測して次の行動を決める方式では、独立な検索も直列に処理しやすく、検索待ちとモデル呼出しが積み重なる。

一方、単純に全関数を同時実行することもできない。ある検索結果から抽出した識別子を次の検索へ渡す場合や、複数の数値の合計を出してから大小比較する場合には、先行タスクが完了しなければ後続タスクの引数が定まらない。さらに、途中結果によって次に必要な操作が変わる問題では、初期の計画だけでは完結しない。

研究の目的は、モデルを内部から高速化することではなく、外部ツールを含む全体処理の依存関係を明示して並列実行できる部分を見つけること、逐次的なモデル再呼出しを減らすこと、必要なときだけ再計画することである。最終的な答えの正確さを保ちつつ、待ち時間とAPI利用費用を下げる点が評価対象となる。

## 手法

### 1. 関数呼出し計画器

計画器は、利用可能なツールの名称・説明・引数仕様と、必要に応じた例示を入力として受け取る。質問を複数のタスクへ分解し、どのツールをどの引数で呼ぶか、どのタスクの結果を必要とするかを生成する。先行タスクの出力が必要な引数には`$1`や`$2`のような参照変数を置き、結果が確定するまでは実行しない。例えば二件の検索をタスク1・2として並列に置き、両者の数値を使う比較計算をタスク3として表す。

依存グラフは実行順序を明示するが、個々の検索結果を待つ間にモデルが再度全体の思考を行う必要はない。計画器は言語モデルであり、ツールの引数を正しい構文で出すためのプロンプトと例示が重要である。計画の品質が低い場合、誤った依存関係や存在しないツールを生成する可能性があるため、計画を生成しただけで正しい実行が保証されるわけではない。

### 2. タスク取得器と実行器

タスク取得器は、依存関係が解消されたタスクを貪欲に選び、利用可能な実行器へ送る。先行タスクが終了すると、その出力を後続タスクの引数にある参照変数へ代入する。この置換と待ち行列の管理は通常のプログラムで実装でき、各依存関係の解消に追加の言語モデル呼出しを必要としない。

実行器は、取得器から渡されたタスクを非同期に実行する。対象は検索API、電卓、情報取得関数、別の言語モデルを使う専門エージェントなどである。依存しないタスク同士を同時に実行し、完了した結果を取得器へ返す。各タスクは中間結果を保持し、すべての必要な結果が揃うと最終回答を生成する。これにより、ツールの待ち時間を重ね合わせ、単純な直列実行よりも短い全体遅延を狙う。

### 3. 動的再計画と計画の逐次出力

初期計画では予測できない条件分岐が生じた場合、実行器からの途中結果を計画器へ戻し、新しいタスク群と依存関係を生成する。原著は「24のゲーム」を木探索として解く例で、候補の結果を見て次の展開を決める動的な処理を示した。これはすべての依存関係を最初に固定する方式と異なるが、再計画のたびにモデル推論の費用が発生する。

計画器の出力を最後まで待つと、タスク数の多い問題では計画生成そのものが直列の律速になる。そこで計画器がタスクを逐次出力し、先に出力されたタスクの依存関係が満たされ次第、取得器と実行器が処理を開始する。原著のParallelQAでは、この逐次出力により最大約1.3倍の遅延改善が報告される。実行時間の長い計算関数があると、後続計画の生成をその待ち時間へ重ね合わせやすい。

### 4. 既存方式との違い

ReActは各ツール結果をモデルへ戻して次の行動を決めるため、複雑な分岐には柔軟だが、独立した操作まで逐次になりやすい。ReWOOは計画と観測を分離してモデル呼出しを減らすが、原著によれば並列関数実行と動的再計画を同じ形では扱わない。単純な並列関数呼出しは独立な関数をまとめるには有効だが、依存付きの複数段処理は別途調停が必要になる。LLMCompilerは依存グラフと実行待ち行列を中心に据え、依存付き・独立・再計画の三種類を統一的に扱う。

### 独立関数と依存付き関数の差

HotpotQAでは二つの情報を別々に取得できる問題が多く、逐次的な検索を並列化する効果が直接表れる。GPT系の改良ReActは7.12秒、LLMCompilerは3.95秒であり、約1.80倍の速度差がある。ただし正答率は62.47%から62.00%へわずかに下がっており、速度改善と精度改善を常に同時に達成したわけではない。Movie Recommendationでは20.47秒から5.47秒へ短縮し、正答率も72.47%から77.13%へ上がった。元のReActでは同じツールの繰返し呼出しや途中での早期停止があり、著者らは比較を公平にするため改良プロンプト版も用意している。

依存付きのParallelQAでは、先行関数の結果が揃うまで後続の計算や比較を待つ必要がある。GPT系では35.90秒から16.69秒へ短縮し、2.15倍の速度比となった。LLaMA-2 70Bでは原著HTMLの表1にReAct 15.47秒、LLMCompiler 26.20秒と表示される一方、速度比2.27倍が併記されており算術的に整合しない。正答率は59.59%から68.14%と記載されるが、当該条件の遅延改善率は原著PDFの表を再確認するまで確定しない。モデルや課題による速度差を無条件に一般化してはならない。

### 費用と再計画の評価

費用削減は、同じ問題でモデルへ渡す入力トークン数と再推論回数を減らすことに主に由来する。HotpotQAでは入力トークン数が約2900から1300へ、Movie Recommendationでは約20000から2800へ減っている。原著の費用表は使用したGPTモデルの当時の価格を前提とするため、現在のAPI価格にそのまま当てはめられない。出力トークンや外部関数の利用料金が変われば総費用の比較も変わる。

Game of 24は中間結果を見ながら探索方針を変える必要がある。GPT系では241.2秒から83.6秒、LLaMA-2 70Bでは952.06秒から456.02秒へ短縮したが、いずれもツールや探索手順の並列性に依存する。さらにWebShopのような対話型環境でも評価されているが、原著の最大101.7倍という速度比は特定の比較条件であり、一般のツール実行全体の保証値ではない。


### 運用時の検証観点

依存グラフの最適化では、並列に実行してよい操作と、順序を守る必要がある操作を明確に分ける必要がある。二つの独立した検索は同時に呼べるが、同じデータベースの行を更新する二つの関数を無条件に並列化すると、結果が実行順序によって変わり得る。原著の評価は主として情報取得、計算、探索を対象としており、一般の副作用を持つ業務APIの整合性まで保証したものではない。

実運用で再現性を確認するなら、計画器が生成した依存グラフ、各ツールの開始・終了時刻、参照変数の解決内容、モデルの入力・出力トークン数、再計画回数を別々に記録することが望ましい。そうすれば、速度改善がツール待ちの重ね合わせによるものか、モデル再呼出し回数の削減によるものか、あるいは単に比較対象のループを回避したためかを区別できる。

## 既存研究との差と推論基盤への意味

LLMCompilerの主張は、モデルの重みを量子化したり注意カーネルを置き換えたりせずに、外部関数の依存関係と待ち時間を整理するだけでもエンドツーエンドの応答時間を短縮できるという点にある。独立したAPI呼出しを同時に実行すること、依存付き処理の引数を正しく受け渡すこと、途中結果による再計画を許すことを同じ実行系で扱う。

現在の推論サーバにとっては、モデル内部のトークン生成性能と、アプリケーション全体の要求完了時間を分けて考える参考になる。モデル推論の速度が同じでも、外部ツール待ちを重ねるとユーザー体感遅延は下がる。一方、並列呼出しは同時実行数を増やし、APIのレート制限や外部サービスの負荷を高める可能性がある。モデルサーバの処理量、ツール側の並列上限、依存グラフの正確さを合わせて評価する必要がある。

## 限界・失敗条件

第一に、計画器が生成する依存関係が誤れば、正しいツールを呼べなかったり、結果の変数を誤って参照したりする。依存グラフを用いること自体が計画の正確さを保証するわけではない。初期計画では未知の分岐を扱うために再計画が必要であり、そのたびにモデル推論の遅延と費用が発生する。ツールが互いに独立でない問題や、外部状態を書き換える副作用を持つ関数では、単純な並列実行によって意味が変わる危険もある。

第二に、速度の改善率はツールの実行時間、独立タスクの数、モデルの計画生成速度に依存する。ParallelQAのLLaMA-2 70B条件では原著HTML表の個別遅延と速度比が整合せず、改善率を確定できない。並列にできるタスクが少ない場合、計画生成と依存管理の費用が利得を上回る可能性がある。計画の逐次出力は計画器の待ち時間を隠せるが、全ての問題で同じ効果を得られるわけではない。

第三に、費用比較は論文当時のGPTモデルのトークン価格と、特定の問題集合に依存する。検索APIなどの外部ツール料金、同時実行制限、障害時の再試行、長い結果の圧縮費用を一般的に評価したものではない。原著はアプリケーション層のツール呼出しを対象としており、GPUのカーネル時間、KVキャッシュ量、複数モデル間の重み配置などの下位推論性能は測定していない。
