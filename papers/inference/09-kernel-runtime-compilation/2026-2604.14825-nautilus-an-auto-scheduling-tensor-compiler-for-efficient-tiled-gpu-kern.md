# Nautilus：注意計算を高水準の数式から自動でGPUカーネル化する

## 概要

大規模言語モデル（Large Language Model; LLM）の注意計算を高速化するには、数学的に同じ式でも、演算の融合、行列の分割幅、共有メモリの配置、並列実行単位、GPU世代ごとの命令特性を考慮しなければならない。FlashAttention系のカーネルはこれらを手作業で高度に調整してきた。一方、既存のタイル型コンパイラはGPU内の小領域を効率よく処理できても、入力の数学的な演算列をどの順で融合し、どこに中間値を残すかという高水準の探索を利用者へ任せがちである。

Nautilusはテンソル式から始めて、計算グラフ上の演算融合と還元の再構成を自動探索し、式の書換えとタイル型コンパイラによる低水準最適化を順に適用する。中核は、スカラー中間表現、仮想レジスタタイル中間表現、メモリアクセスタイル中間表現という3段階の表現と、タイル最適化器が扱いやすい規則的な計算構造を維持する自動スケジューラである。一般の注意式からFlashAttention-3に近い融合カーネルを自動発見できる点を主要貢献とする。

NVIDIA GH200とRTX 5090で5種類のTransformer系モデル・計150設定を評価した。注意計算の相対処理量はGH200でFlashAttention-2比平均1.22倍、RTX 5090で同方式比平均1.26倍、同GPUの標準スケールドドット積注意（Scaled Dot-Product Attention; SDPA）比平均1.42倍である。数値は注意演算の実行時間から算出した処理量であり、モデル全体のトークン生成速度が同じ倍率で向上したことを意味しない。

## 問題設定

注意演算は行列積、最大値の還元、指数関数、総和、正規化、値行列との積など複数の演算からなる。単純な実装では各段階の中間行列を大域メモリへ書き戻すため、演算量だけでなくメモリ転送が支配的になる。FlashAttentionは行列を小領域へ分け、最大値と正規化の統計量を逐次更新して中間行列の書戻しを避ける。だが、この変形を数学的な入力記述から汎用コンパイラが自動で導くことは難しい。とりわけ二つの還元ループを融合する場合、変換の合法性、依存関係、後段タイル化との相性を同時に満たす必要がある。

既存のTVMやHalideのようなスケジュール型コンパイラは演算と実行計画を分離するが、利用者が変換列を指定する負担が大きい。TritonやTileLangはGPUタイルの実装効率に優れる一方、数式全体からの還元融合などを自動探索する機能が限定される。Nautilusは高水準の探索空間を扱いつつ、後段が最適化しやすいタイル形状を残すことで両者を接続する。

## 手法

### 1. 計算ブロックグラフと変換スケジュール

入力はTVMのテンソル式言語（Tensor Expression; TE）で記述した演算である。深層学習フレームワークの演算もTVM Relaxからテンソル式へ変換できる。Nautilusはこれをスカラー中間表現へ落とし、ループと計算文の依存関係を**ブロックグラフ**として管理する。各ノードは計算またはループを表し、変換スケジュールはそのグラフ上の操作列である。単に行列の分割幅を選ぶだけでなく、計算文をどのループへ移し、どの中間値を残し、どのループを融合するかを高水準で記述できる。

この表現の重要性は、変換の順番が後段で実行可能なプログラム構造を左右することにある。例えば先に演算を融合すると中間値の保存が不要になる一方、還元を複雑に入れ子にするとタイル型コンパイラが認識できる規則的な行列演算から外れてしまう。Nautilusの自動スケジューラは変換候補を生成する際、後段のタイル最適化器が受け取れる形を保つ制約を組み込む。

### 2. 二段階タイル化と演算融合

NautilusはループをGPUのスレッドブロック間で分ける外側のタイル化と、ブロック内で処理する内側のタイル化を組み合わせる。複数の計算文にまたがる依存関係を調べ、どのループに演算を融合するかを探索する。局所性を高めるため、単純な要素ごとの演算は可能な限り深いループへ移すが、融合によって共有メモリやレジスタが不足する場合には必ずしも有利ではない。

演算融合には二つの基本操作がある。**通常融合**は直接連続する要素演算・還元演算を同じループへ移す。**逐次更新融合（rolling update）**は還元演算同士の間にある要素演算も巻き込み、先行する還元ループの中で後続の還元を更新できるようにする。注意計算のオンライン最大値・総和更新を得るために重要な変換である。逐次更新融合は対象の後続演算が還元であることなど合法性条件があり、Nautilusは先読みして融合可能な後続還元を探す。見つからない場合は新しいカーネル境界を設ける。

還元の逐次更新によって複数の中間行列を大域メモリへ書き戻さずに済む一方、長い依存連鎖を作る可能性がある。そこでスケジューラは依存の走査（scan）を分割し、タイル型最適化器が苦手とする形を規則化する。融合の強さだけでなく、後段の実行効率を含めて探索する点が、単純な貪欲融合との違いである。

### 3. 局所化、再計算と記憶領域の圧力

中間テンソルを大域メモリから共有メモリ・レジスタへ移すと読み書きは速くなるが、GPUの高速な記憶領域は容量が小さい。長期間生存する大きな中間バッファを局所化しすぎると、同時に実行できるスレッドブロック数が減り、占有率を損なう。Nautilusはバッファの大きさと生存期間を分析し、再読込されるデータを局所化するか、短い式なら利用地点で再計算するかを選ぶ。

再計算による中間値の再生成（rematerialization）と生存期間の分割は、追加の演算量と局所メモリ削減を交換する。特に長い注意系列では、中間の注意行列を保持するよりも局所タイル内で必要な統計を再計算した方が有利な場合がある。逆に短い系列では、複雑な融合の準備費用が上回り得るため、後段の自動調整で別のタイル寸法やコンパイラを選ぶ。

### 4. 三つの中間表現を用いた段階的な低水準化

スカラー中間表現はループ構造と計算文を明示するため、高水準の融合・分割を適用しやすい。その次の**仮想レジスタタイル中間表現（Virtual-Register Tile Intermediate Representation; VR-tile IR）**では、タイルの中間結果をメモリアクセスではなく値として表す。ループは繰返し間で受け渡す値を引数・戻り値に持つ式として扱える。これにより、ループの外と内を跨ぐ乗除算の相殺や指数関数の底の変換など、数学的な式書換えを行いやすい。

最後の**メモリアクセスタイル中間表現（Memory-Access Tile Intermediate Representation; MA-tile IR）**では、値をどのテンソル領域から読み、どこへ書くかを明示する。これは既存のタイル型コンパイラが扱う入力に近く、NautilusはTriton、Tawa、TileLangのいずれかへ変換する。高水準の変換、式書換え、GPUタイル最適化を単一の中間表現で無理に扱わず、それぞれの得意な抽象度で実施することが設計上の要点である。

### 5. 自動スケジュール探索と実測調整

自動スケジューラはブロックグラフを前順に走査し、合法な変換候補を規則に従って組み立てる。生成されたスケジュール種をTVM MetaScheduleの自動調整器へ渡し、タイル寸法、ワープ数、パイプライン段数、後段コンパイラの選択を探索する。学習した費用モデルで候補を予測し、有望なものを実GPUで実行して最短時間のカーネルを選ぶ。各設定の評価では256回の実測を自動調整予算とした。

スケジュール探索そのものは多くの条件で1分以内に終わるが、実際の候補カーネルをコンパイル・実行する調整は数秒から10分かかる。したがって生成済みカーネルの実行が高速であっても、**初回の最適化費用がゼロではない**。固定した演算形状を繰返し使う場合に償却しやすいが、形状が毎回大きく変わる場合には事前生成やキャッシュ戦略が必要となる。

## 評価

### 比較条件と指標

論文はNVIDIA GH200 Grace Hopper Superchip上のH100と、Blackwell世代のRTX 5090を使用した。モデルはLlama 2 7B、Qwen2 7B、Qwen3 8B、GLM-4 9B、ViT 1.2Bで、通常注意、因果注意、グループ化問い合わせ注意（Grouped Query Attention; GQA）を含む。入力系列長は1,024～32,768、バッチ数は1と8、精度はFP16とFP8-E4M3を用いる。比較にはFlashAttention-2、PyTorch SDPA、FlexAttention、Tawa、TileLang、Triton、cuDNNなどを含む。

| 項目 | 実験設定 |
|---|---|
| GPU | NVIDIA GH200（H100）、NVIDIA RTX 5090 |
| モデル | Llama 2 7B、Qwen2 7B、Qwen3 8B、GLM-4 9B、ViT 1.2B |
| 注意方式 | 通常・因果・GQA |
| 系列長 | 1,024～32,768トークン |
| バッチ数 | 1、8 |
| 精度 | FP16、FP8-E4M3 |
| 自動調整 | 各設定でGPU実測256回 |
| 時間計測 | モデル単位はCUDA Events、演算子単位はNsight Systems。ウォームアップ後10回の平均 |
| 集約 | 設定ごとの相対処理量の幾何平均 |

「モデル全体の推論」と題する評価節でも、論文の相対処理量は注意演算に必要な理論浮動小数点演算数を測定時間で割った値である。特定のモデル・注意演算の性能と、トークン生成全体の処理量を同一視しない。また、全比較方式がすべての形状・精度を実装しているわけではなく、比較できる条件に差がある。

### 主な性能結果

| GPU・精度 | 比較対象 | Nautilus相対処理量（幾何平均） | 解釈 |
|---|---|---:|---|
| GH200・FP16 | FlashAttention-2 | 1.22倍 | 5モデル平均で約22%高い注意処理量 |
| GH200・FP16 | PyTorch SDPA | 1.23倍 | 同条件で約23%高い |
| GH200・FP16 | FlexAttention | 1.13倍 | 比較対象によって差は縮む |
| GH200・FP16 | Tawa | 1.16倍 | 自動スケジュールと後段選択の効果 |
| GH200・FP8 | FlexAttention FP8 | 1.16倍 | 低精度でも改善 |
| GH200・FP8 | Tawa FP8 | 1.20倍 | 自動調整が効く |
| RTX 5090・FP16 | FlashAttention-2 | 1.26倍 | GPU世代が変わっても改善 |
| RTX 5090・FP16 | PyTorch SDPA | **1.42倍** | 同GPUでの最大の平均改善比較 |
| RTX 5090・FP16 | TileLang | **1.01倍** | 最良のタイル型基盤との差はごく小さい |

モデル別に見るとGH200のViTではFlexAttention比1.54倍で、Llamaの1.06倍、Qwen2の1.05倍より改善が大きい。ViTの注意構成は標準的なLLMとはヘッド数や隠れ次元が異なり、固定的な手書き構成の最適化が弱い場合に探索の利点が出やすい。RTX 5090ではTileLang比の幾何平均が1.01倍に留まり、Nautilusが既存の高性能後段を選択してその周辺パラメータを改善する方式であることが分かる。**「42%向上」はRTX 5090でのSDPA比較**であり、最速のTileLang比42%向上ではない。

### 演算子単位の感度・構成要素除去

短い系列では軽量な64×128タイル・4ワープを選び、Tawaの128×128タイル・8ワープの既定値より良い場合がある。FP8では系列長に応じてパイプライン段数を1～4へ変える。RTX 5090では共有メモリ容量に合わせた分割寸法と逐次更新融合が効き、長い系列で既定のTileLangとの差を作る。Neptuneの性能は比較したTawa/TileLangの0.5～0.8倍で、Tritonに固定した後段コード生成が制約になったと報告する。これは高水準のスケジュール品質だけでなく後段生成器の選択が重要であることを裏付ける。

| GH200・通常注意・系列長256 | 実行時間 |
|---|---:|
| Nautilus完全版 | **7.43 μs** |
| 自動調整なし | 9.09 μs |
| 自動調整と式書換えなし | 9.45 μs |
| 自動スケジュールなし | 10.93 μs |

この構成要素除去は同一演算子で段階的に機能を無効化したものである。完全版と自動調整なしとの差は1.66 μs、さらに式書換えを外した差は0.36 μs、スケジューリングまで外すと1.48 μsの悪化が加わる。ただし差分は相互作用を含むため、各機能の独立した加算可能な利益と解釈すべきではない。実装全体の利点は、複数の高水準・低水準選択肢を連続して最適化できることにある。

### 数値精度と手書き実装との比較

FP64注意計算を参照にした数値誤差評価では、Qwen2.5の実入力を用いた3種類の注意演算の平均二乗平方根絶対誤差（Root Mean Square; RMS）がNautilusで $4.96\times10^{-5}$、Tri-Daoで $4.90\times10^{-5}$、FlexAttentionで $5.02\times10^{-5}$ だった。完全に誤差ゼロという意味ではないが、既存の正確な注意実装と同程度の丸め誤差である。近似的なFlashAttention-4は正確な注意計算との比較対象を揃えるため除外されている。

手書きのcuDNNなどとの比較では、長い系列を中心に同等以上となる設定が多いと報告する。一方、全設定で手書き実装を上回るわけではない。後段のコンパイラが対応しない特殊な演算形状や、生成したコードのメモリ利用が悪い場合には手書き実装が有利になり得る。

### 定量結果を実運用へ換算する際の解釈

注意計算だけの処理量が増えても、生成の全工程には重みを読み込む線形演算、正規化、活性関数、トークン選択、要求管理、鍵・値の確保などが残る。仮に注意演算が全工程の半分を占め、その部分だけが1.42倍速くなるとすれば、残りが不変なら全体の改善は約1.17倍に留まる。これは論文で実測した全工程の値ではなく、注意演算以外が改善しない場合の計算例である。実際には注意演算の割合が文脈長や同時実行数によって変わるため、短い入力での単一要求と長い入力での複数要求とでは効果が異なる。

本研究の比較対象は各条件で利用可能な実装に限られるため、最も近い後段生成器との比較を優先して読む必要がある。RTX 5090では標準の注意実装に対して平均42%の改善があっても、最適化済みのTileLangに対しては平均1%である。これを区別すると、主要な貢献が未知の新しい注意演算ではなく、高水準の数式から最適化済みの演算形態を自動的に発見し、ハードウェアごとに適切な生成器を選ぶことだと分かる。実装を保守する側にとって、手書きカーネルをGPU世代ごとに作り直す負担を減らせる可能性が重要である。ただし自動探索にも調整時間がかかるため、配備時の生成費用と実行時の節約量を別々に計測する必要がある。

## 既存研究との差

TVM・Halideは数学的な演算とスケジュールを分離するが、複雑な演算融合の変換列を自動発見する負担が残る。Triton・TileLangは既にタイル化された演算をGPUへ写像するのが得意で、高水準の還元融合を利用者へ任せる。Neptuneは高水準スケジュールをタイル最適化器へ渡す先行方式だが、後段がTritonへ固定される。Nautilusはブロックグラフ上の自動融合、仮想レジスタ表現による式書換え、複数後段からの選択を一体化する。

vLLMやTensorRT-LLMのようなサービング基盤は要求スケジューリングや鍵・値キャッシュ管理を扱い、Nautilusはその下層の注意カーネル生成を対象とする。両者は置換関係ではなく補完関係である。Nautilusを導入しただけでサービングの動的バッチングやキャッシュ割当が改善するわけではない。

## 限界

実測GPUはGH200とRTX 5090に限られ、RTX 4070 Superなど別世代への相対性能は論文から直接推定できない。自動調整は設定ごとに256回の実測を行うため、初回最適化費用は数秒から10分に及ぶ。カーネル形状が頻繁に変化する運用では、生成コードのキャッシュや事前調整が必要である。

モデル評価は主に注意演算であり、モデル全体の行列積、重み読み込み、通信、メモリ割当を含むサービングの総合的な性能評価とは分ける必要がある。GPU世代や系列長で最適な後段コンパイラが変わる。すべての演算形状で同一の最適化が有効なわけではない。論文が示す数学的に等価な式変換と、FP16/FP8実装で生じる丸め誤差の差も区別する。

公式コードの公開先は今回の一次資料確認では特定できなかった。従って現時点でWindows環境へ導入可能な実装として案内することはできない。実装可能性と性能の主張は、論文の試作システム・実験条件に限って評価すべきである。
