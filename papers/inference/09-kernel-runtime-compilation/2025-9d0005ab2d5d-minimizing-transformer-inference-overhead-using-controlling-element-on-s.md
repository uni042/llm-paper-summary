# Minimizing transformer inference overhead using controlling element on Shenwei AI accelerator

> Whisper推論の実測分解で読み込みと起動が全体の最大96パーセントを占めることを示し、アクセラレータ上の制御要素へ制御を寄せる三層スケジューリング、ゼロコピー、高速読み込みで起動費用と読み込み時間を桁違いに削る研究。

## 概要

Transformerの推論を速くする研究の多くは、注意機構や行列積といった演算そのものを対象にする。しかし実際の実行時間には、演算以外の部分、すなわちモデルファイルの検証と読み込み、カーネルを1回起動するたびに発生するホストとデバイスのやり取り、メモリコピーが大きく乗る。特に小さいモデルや短い入力では、1回あたり数マイクロ秒の起動費用が何万回も積み重なり、演算時間を上回る。本論文はこの制御側の費用を正面から測り、アクセラレータ側の制御要素を使って消しに行く研究である。

題材は音声認識モデルのWhisperである。Whisperは音声を30秒単位の区間へ切り、符号化器を1回、復号器を多数回回す構造を持つため、起動とコピーの回数が構造的に多い。著者らはTesla V100S上のPyTorch実行を、モデル読み込み、API呼び出し、GPU計算、その他へ分解し、読み込みとAPI呼び出しの合計が全体の79から96パーセントに達すること、大きなモデルでは読み込み時間22534ミリ秒のうち検証が7717.77ミリ秒、初期化が10549.78ミリ秒を占めることを示した。

対策は三つある。第一に、申威AI（SWAI）アクセラレータの管理処理要素（MPE）に制御を移す三層スケジューリングで、PCIeを越える起動をチップ内の関数呼び出しに近い形へ変え、起動回数を元の約1万分の1へ減らす。第二に、セグメントとページの融合でMPEと計算処理要素（CPE）が同じ物理アドレスを共有するゼロコピーにより、カード内コピーをほぼ消す。第三に、配布ごとのハッシュ検証と、推論では不要な線形層のパラメータ再初期化を省く高速読み込みである。

**代表結果:** 大きなWhisperモデルの読み込み時間は、PyTorchの22128.31ミリ秒から1041.72ミリ秒へ約21倍短くなった。起動オーバーヘッドは、大きなモデルと260秒音声の条件で8578600マイクロ秒から270マイクロ秒へ落ち、単位時間あたりの起動費用は約0.5マイクロ秒と、CUDA起動の典型値4.9マイクロ秒を大きく下回る。総合のオーバーヘッドはPyTorchの半分以下、最良条件では約5パーセントまで下がったと報告される。

## 問題設定

ボトルネックは計算資源ではなく制御の往復である。ホストとデバイスが分かれた構成では、演算子ごとにカーネル起動とメモリコピーが発生する。先行測定では、パラメータ転送なしでもデバイス1台あたりの平均起動時間は約6マイクロ秒、基本モデルのカーネル計算時間は10マイクロ秒未満であり、起動が計算に匹敵する。Whisperではこの構造が増幅される。30秒の音声区間ごとに符号化が1回と復号が約60回走り、符号化の1層だけで約56回の起動が発生する。著者らは起動時間を層数と音声長から見積もる式まで作り、実測とのずれが20パーセント未満であることを確認している。

既存対策の中心は演算子融合である。LightSeqは層正規化などを専用カーネルへまとめ、符号化層あたりの起動を6回まで減らし、TurboTransformersも融合で起動頻度を下げた。しかし融合は起動回数を減らすだけで、ホストが演算子ごとにデバイスを駆動する構造自体は残るため、起動費用は消えない。また読み込み側では、モデルの検証に使うSHA-256ハッシュ計算がファイルサイズに比例し、大きなモデルでは7717.77ミリ秒とパラメータ読み込み自体の約2倍かかること、学習再開のためのパラメータ再初期化が推論では無駄であることが、従来の読み込み手順の中に埋もれていた。本論文の着眼点は、制御をホストからアクセラレータ上の制御要素へ移し、読み込み手順から推論に不要な作業を取り除くことで、起動と読み込みの両方を構造ごと削ることにある。

## 手法のあらまし

処理の流れは次のとおりである。まず高速読み込みで、検証をモデル入手時の1回へ寄せ、パラメータ読み込みとモデル初期化を統合し、中間バッファを介さず読み込んだ値をそのままモデルへ組み込む。読み込み後はモデル全体をデバイスへ送る。推論が始まると、ホストはメルスペクトログラム処理の後にPCIe経由の起動を1回行うだけで、以降の制御はカード上のMPEが担う。MPEは符号化と復号の各段を計算グラフとして構築し、1回の起動で多数の演算をCPE群へ割り当てる。MPEとCPEの間のデータは共有メモリ領域を介して受け渡され、カード内コピーは発生しない。生成されたテキストだけがホストへ戻される。

## 手法

### 1. 三層スケジューリング — 制御をMPEへ移し、起動をグラフ単位へまとめる

この機構が観測するのは、符号化器と復号器の演算子の列と、その起動回数である。保持する状態は、MPEが構築する計算グラフであり、符号化と復号の各段について複数演算子を1つのグラフへまとめたものを持つ。処理は、従来はホスト、デバイスの二層で演算子ごとにPCIeを越えて起動していたものを、ホスト、MPE、CPEの三層にし、ホストからの起動を区間の開始時の1回へ圧縮し、残りの段取りをMPEがチップ内で行うことである。これにより減るボトルネックは起動オーバーヘッドであり、1回の起動はPCIe通信から関数呼び出しに近い形へ変わり、所要時間は約10分の1、回数はグラフの大きさ次第で数千分の1から1万分の1まで減る。追加で消費する資源はMPE側のグラフ構築時間である。誤った場合ではなく構造上の弱点として、グラフ構築が直列に挟まると利得を食うため、次節の非同期実行と組み合わせる前提の設計になっている。また音声区間の長さが現在の復号の完了まで決まらないため、次の符号化グラフを常時先行構築できるわけではないという境界も論文は明記する。

### 2. 非同期実行 — CPEの計算中に次のグラフを組む

この機構が観測するのは、CPEが現在のグラフを計算している間のMPEの空き時間である。保持する状態は、符号化器を自己注意とフィードフォワードネットワークへ分割した部分グラフの構築順序である。処理は、CPEが自己注意を計算する間にMPEがフィードフォワード側のグラフを組み、その計算中に復号側のグラフ構築を始め、さらに現在のラウンドのテキスト生成を次ラウンドの復号計算へ遅らせて重ねることである。これにより減るボトルネックは、三層化で新たに生じたグラフ構築オーバーヘッドの直列待ちである。追加費用は構築順序の管理の複雑さであり、得られる効果は実測で示される。同期実行と比べ、グラフ構築を含む時間は大きなモデルと260秒音声で14895ミリ秒から7048ミリ秒へ、ほぼ半減した。区間長が可変で次の符号化グラフを先に組めない場合は重ね合わせが部分的にとどまり、利得が縮む。

### 3. セグメント・ページ融合のゼロコピー — MPEとCPEに同じ物理アドレスを見せる

この機構が観測するのは、MPEとCPEの間のデータ受け渡しである。通常は両者の仮想アドレス空間へ別々の物理範囲を割り当て、同じチップ内でもコピーで受け渡すため、頻繁な交換ではコピー費用が積み上がる。保持する状態は共有メモリ領域であり、MPE側は多段ページテーブル経由で、CPE側はセグメントテーブル経由で、同一の物理アドレスへ対応付けられる。処理はこの対応付けにより、両者が別々の仮想アドレスから同じ物理領域を直接読めるようにすることである。これが安全な理由は実行形態にある。Transformer推論ではMPEが流れを組み、CPEが計算し、MPEが後処理をするという交互の直列実行であり、同じメモリへ同時アクセスする場面が生じない。減るボトルネックはカード内コピーであり、実測ではMPEとCPEの間のコピー時間がミリ秒級から0.2から0.5マイクロ秒へ落ちた。追加で消費するのはアドレス対応付けの管理であり、同時アクセスが起きるような並行ワークロードへそのまま広げると競合を防ぐ仕組みが別途必要になる点が適用境界である。ホストとデバイスの間のコピーは残り、最適化後も最大で約50ミリ秒程度に抑えられるという位置付けである。

### 4. 高速読み込み — 検証と再初期化を推論経路から外す

この機構が観測するのは、読み込みの4段階、すなわちモデル検証、パラメータ読み込み、モデル初期化、デバイスへの転送にかかる時間である。実測では大きなモデルで検証7717.77ミリ秒と初期化10549.78ミリ秒が全体の81パーセントを占め、初期化の中では512個の線形層の初期化が1層平均11ミリ秒、合計5.6秒で初期化全体の53.13パーセントだった。処理は三つある。検証は配布のたびではなくモデル入手時にだけ行う。線形層のパラメータ再設定は学習の収束を助けるためのもので、学習済みパラメータを読み込む推論では不要なので省き、初期化をパラメータ読み込みと統合する。パラメータやメルフィルタや重みを一時メモリへ置かず、読み取り直後にモデルへ直接組み込む。これにより減るボトルネックは読み込み時間そのもので、大きなモデルで22128.31ミリ秒から1041.72ミリ秒へ、基本モデルでも2317.6ミリ秒から186.57ミリ秒へ短縮された。トレードオフとして、配布ごとの完全性検証を省く分、入手時の検証と保管側の完全性管理が前提になる。改変検知を配布ごとに要求する運用では、この省略はそのまま使えない。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 三層スケジューリング | 演算子列と起動回数 | 制御をMPEへ移し演算をグラフ単位で起動 | 起動オーバーヘッド | グラフ構築時間が新たに生じる |
| 非同期実行 | CPE計算中のMPEの空き | 計算と次グラフ構築を重ねる | グラフ構築の直列待ち | 区間長が可変だと先行構築に限界 |
| ゼロコピー | MPEとCPE間の受け渡し | セグメントとページで同一物理領域を共有 | カード内コピー | 同時アクセス前提の用途へは広げにくい |
| 高速読み込み | 読み込み4段階の時間 | 検証を入手時へ寄せ初期化と読み込みを統合 | 読み込み時間 | 配布ごとの検証を運用側で担保する必要 |

## 評価

結論は、Whisperのような小規模から中規模のモデルでは、演算ではなく制御側の費用が推論時間を支配しており、その費用はアクセラレータ側の制御要素と読み込み手順の見直しで桁違いに削れる、というものである。内訳の実測が主張の土台であり、基本モデルと短い音声では読み込みが全体の56パーセント、大きなモデルでは83パーセントを占め、長い音声ではAPI呼び出しが主成分へ入れ替わる。つまり支配要因は条件で移るが、どちらも制御側である点は一貫する。

内訳の細部も条件依存性を裏付ける。基本モデルと11秒音声では、最初期にだけ走るデバイス解放処理がAPI呼び出し時間の35.19パーセントを占め、これはモデルの大きさや入力によらずほぼ一定の固定費であるため、小さい条件ほど相対的に重い。音声が260秒へ伸びると起動処理の累積が増え、起動だけで全体の30パーセントを超える。逆に大きなモデルと長い音声ではカーネル実行そのものがAPI呼び出しと計算の合計の40.06パーセントまで育ち、制御側の比率は下がる。つまり本論文の方式は、制御側が支配的な条件で最大の利得を持ち、計算側が支配的になる条件では利得の上限が下がるという、感度の方向まで内訳から読み取れる。グラフ構築という新しい費用についても、11秒音声ではAPI呼び出しの10分の1未満、260秒音声の最悪条件でもその半分程度にとどまることが確認されており、三層化の追加費用が元の起動費用を上回らない範囲に収まっている。

速度面の代表値は三つある。起動オーバーヘッドは基本モデルで568640マイクロ秒と788600マイクロ秒から約11マイクロ秒へ、大きなモデルでは1970400マイクロ秒と8578600マイクロ秒から250マイクロ秒と270マイクロ秒へ落ちた。読み方は、起動回数の削減と1回あたり費用の削減が同時に効いた結果であり、モデルが大きく音声が長いほど元の起動回数が多いため、絶対削減量が大きくなる。メモリコピーは、大きなモデルと長い音声でPyTorch-GPUの749ミリ秒に対し、カード内コピーがほぼ消え、残るホスト間転送を含めても最大約50ミリ秒級へ抑えられた。読み込みは大きなモデルで約21倍の短縮である。品質面では、提案は演算内容を変えないため認識精度の変化は評価対象になっておらず、パラメータ再初期化の省略が推論結果へ影響しないことが前提として説明される。未評価の点として、Whisper以外のモデルでの内訳、複数リクエストを同時に捌くサービング条件、SWAI以外のアクセラレータでの再現は論文の範囲外である。

## 既存研究との差

演算子融合で起動回数を減らすLightSeqやTurboTransformersとの差は、起動の発生場所そのものを変えた点にある。融合はホスト駆動のまま回数を減らすが、本論文は制御をカード上のMPEへ移し、演算を計算グラフ単位で渡すことで、起動をPCIe往復からチップ内の段取りへ変えた。カーネル起動費用の分析研究や、動的並列による起動削減の研究が費用の存在と部分的な削減を示したのに対し、本論文は読み込み、起動、コピーの三費用を1つの実測分解で捉え、読み込み手順の無駄まで含めて削る全体像を提示した点が異なる。

## 限界・実装状況

限界は、評価がWhisperとSWAIアクセラレータの組み合わせに限られること、分析の基準がV100S上のPyTorchであり最適化側とハードウェアが異なること、複数リクエストの同時処理やバッチ処理での制御費用の振る舞いが未評価であること、検証の省略が入手時の完全性確認を前提にすることである。大きなモデルや長い入力ではGPU計算自体の比率が上がるため、制御費用の削減がエンドツーエンドへ効く割合は条件で下がる。実装状況は、SWAIカード上の試作実装として実験が行われており、公開コードの案内は論文にない。データは対応著者への依頼で入手可能と記される。

## 一般的な実装上の含意

小さいモデルや短い入力ほど、演算ではなく起動と読み込みが時間を支配するという視点は、他の推論基盤でも当てはまる。最適化の前に実行時間を演算と制御へ分解し、支配要因がどちらかを確認すべきである。また、制御をデバイス側へ寄せて処理をグラフ単位で渡す設計、読み込み手順から推論に不要な検証や初期化を外す設計は、特定のアクセラレータに依存しない再利用可能な原則である。共有メモリによるゼロコピーは、アクセスが交互で競合しないという実行形態の性質を根拠にしており、性質を確認せずに真似ると競合を招く点も含めて読み取るべきである。
