# NeuronMM: High-Performance Matrix Multiplication for LLM Inference on AWS Trainium

> Trainium向けに、重みの特異値分解のランクをタイル境界へ揃え、二つの行列積を中間結果のSRAMキャッシュと暗黙の転置で融合することで、AWS公式カーネル比でエンドツーエンド推論を平均1.66倍高速化する行列積カーネル。

## 概要

AWS TrainiumはAmazonが開発した推論・学習用アクセラレータで、GPUより安価に大規模言語モデルを動かせる候補として注目される。しかしTrainiumはシストリックアレイ型のハードウェアであり、オンチップのSRAM（データを置くSBUFが24MB、部分和を溜めるPSUMが2MB）が小さく、しかも配置をソフトウェアが明示的に管理しなければならない。そのため行列積では、計算エンジンがデータを待って遊ぶ時間や、HBMとSRAMの間の転送、行列の転置といったデータ移動の費用が、計算そのものの費用を上回りやすい。

本論文のNeuronMMは、このデータ移動を減らすために二つの改良を重ねる。第一に、MLP層の大きな重み行列を特異値分解（Singular Value Decomposition; SVD）で二つの低ランク行列へ分解し、行列積の計算量と転送量そのものを減らす。その際、保持するランクをTrainiumのタイル境界の倍数へ揃えるブロック整列により、パディングによる無駄とSRAMの溢れを避ける。第二に、分解で生じる二段の行列積XUVを一つのカーネルへ融合するTrainiumFusionである。中間結果を行ごとにまとめてSBUFへキャッシュして再利用することで再計算を消し、転置が必要な中間行列は行列の恒等式を使って入力の順序を入れ替えることで転置済みの形を直接作り、明示的な転置を消す。

**代表結果:** AWS公式のNKI行列積カーネルとの比較で、逐次実行の低ランク版に対してはカーネル単体で平均1.35倍、非圧縮の通常行列積に対しては平均2.09倍（系列長32Kでは2.22倍）の高速化であり、HBMとSBUFの間のトラフィックは平均で9.93GBから2.47GBへ減った。MLP層へ組み込んだエンドツーエンド評価では、Llama-3.2とQwen3の4モデルで平均1.66倍、最大でLlama-3.2-3Bの圧縮率0.2における2.49倍の高速化を、平均精度の低下を0.10以下に抑えて達成している。圧縮だけでも速くなるが、ハードウェアに合わせた融合がなければ利得の半分近くを取りこぼす、というのが論文の中心的な主張である。

## 問題設定

ボトルネックは三つに分解される。第一は入出力のボトルネックである。重みWをUとVへ分解すると、元の行列積XWはXUVという二段の行列積になる。これを素朴に逐次実行すると、一段目の中間結果Y=XUを一度HBMへ書き戻し、二段目で読み直す必要がある。論文が示すDeepSeek-V3のup射影のプロファイルでは、圧縮版は直接メモリアクセスの転送時間が65パーセント増え、HBMとSBUFの間のトラフィックが2倍以上になり、テンソルエンジンの利用率が大きく落ちている。つまり圧縮で計算量を減らしても、中間結果の往復がそれを食い潰す。

第二は再計算である。中間結果をHBMへ出さないために二つの行列積を融合すると、今度は出力の列ブロックごとに同じ中間ブロックを何度も計算し直すことになる。出力幅が16384でブロック幅が512なら再計算の係数は16倍になり、論文の実測では素朴な融合カーネルは逐次実行より11倍以上遅く（18.06ミリ秒対1.57ミリ秒）、FLOPsは4倍、HBMトラフィックは10.5倍に膨らんだ。再計算を避けるには行全体を一度に出力すればよいが、それは24MBのSBUFへ収まらない。

第三は転置のオーバーヘッドである。Trainiumのテンソルエンジンは、固定側の入力行列を転置したレイアウトで受け取る仕様である。入力活性値Xの転置はモデルのデータフロー上避けられない入出力転置だが、二段目の入力になる中間結果Yの転置はカーネル内部で生じる中間転置であり、系列長に比例して大きくなる。既存のSVD圧縮研究は圧縮率と精度の交換だけを見ており、こうしたアクセラレータ固有の転送・再計算・転置の費用を扱っていない点が、本論文の出発点である。

## 手法のあらまし

処理はオフラインの圧縮と推論時のカーネルに分かれる。オフラインでは、MLP層の各重みについて入力活性値の共分散から作ったスケーリング行列を掛けて特異値分解し、上位ランクだけを残して二つの低ランク行列UとVへまとめ、圧縮で落ちた精度をLoRAによるファインチューニングで回復してからLoRA分を本体へ吸収させる。ランクは目標圧縮率から決めるが、最後にタイルサイズの倍数へ丸めることでブロック境界へ揃える。注意層の重みは圧縮しない。推論時には、入力Xの行ストリップごとに、まずXUを計算してその転置をSBUFのキャッシュへ置き、次にVの全ての列ストリップと掛けて出力行の全ブロックを作る二段構成の融合カーネルが動く。ブロックサイズは、算術強度がハードウェアの計算律速の閾値を超え、かつピークSBUF使用量が24MBへ収まる範囲で、性能モデルから選ぶ。

## 手法

### 1. ブロック整列SVD — ランクをタイル境界へ揃える圧縮

この機構が観測するのは、各MLP層へ入る入力活性値の統計である。ランダムに選んだ入力文で順伝播を記録し、共分散行列のコレスキー分解からスケーリング行列Sを作る。保持する状態は、重みにSを掛けた行列WSの特異値分解と、その上位r個の特異値・特異ベクトルである。処理は、WSを分解して上位r成分だけを残し、特異値の平方根を両側へ分配してU側とV側の二行列へ再構成することであり、パラメータ数は元のk×nからr×(k+n)へ減る。ここでNeuronMM固有なのはランクrの決め方で、目標圧縮率から求めたランクをブロックサイズ（タイルサイズの整数倍）の倍数へ丸める。これにより低ランク行列の内側次元が常にブロック境界と一致し、ブロック内部のパディングが消えてテンソルエンジンとSBUFの利用率が上がる。減るボトルネックは重みの転送量と行列積の計算量そのものである。追加費用はオフラインの分解と精度回復の学習であり、近似である以上、圧縮率を上げすぎると品質が崩れる失敗条件がある。論文では圧縮率0.4から0.5の間でパープレキシティが38.87から51.29へ跳ね上がることが示され、実運用の評価は0.1と0.2に抑えられている。精度回復は、圧縮したUとVを凍結し、LoRAの低ランク更新だけを学習して最後に本体へ足し込む形で行う。

### 2. 中間ストリップのキャッシュ — 融合しても再計算しない

この機構が観測するのは、中間行列XUのうち入力の行ストリップに対応する部分（XU）_{m*}であり、その形状はブロック高さB_Mとランクrで決まる。保持する状態は、この中間ストリップを転置した形で置くSBUF内の専用キャッシュバッファである。処理は、外側のループで行ストリップを一つ選び、まずXとUのブロックをHBMから読み込んで中間ストリップ全体を一度だけ計算してキャッシュへ入れ、その後にVの列ストリップを順に読み込みながら、キャッシュ済みの中間ブロックを再利用してその行の出力ブロックを全て作ることである。これにより、中間結果のHBMへの書き戻しと読み直しが消え、同時に列ブロックごとの再計算も消える。効く理由は、中間ストリップの大きさが例えば1024×r×2バイト程度とSBUFへ十分収まるためであり、これは特異値分解でランクrが元の次元より小さくなっているからこそ可能な設計である。追加で消費する資源はSBUFの容量そのもので、キャッシュが他の入力ブロックと容量を奪い合う。資源不足時の挙動として、ブロックを大きくしすぎるとSBUFからHBMへのスピルが発生し、論文の実測ではブロック高さ2048以上でスピルの再読み込みが観測されて遅延が反転増加している。素朴な融合が11倍遅かったのに対し、このキャッシュが融合を実用速度へ引き上げる要である。

### 3. 暗黙の転置と入出力レイアウト — 中間転置を消し、境界の転置はDMAへ逃がす

この機構が観測するのは、テンソルエンジンの低レベル命令が固定側入力へ転置レイアウトを要求するという制約である。二段目の計算では一段目の結果Yの転置Y^Tが固定側に必要になるが、NeuronMMは恒等式（XU）^T = U^T X^Tを使い、命令へ渡す入力の順序を入れ替えることで、転置済みの中間結果を最初からその形で生成する。保持する状態は追加のバッファではなく命令の呼び出し順序だけであり、明示的な転置のためのデータ移動と同期が丸ごと消える。境界で避けられない入力Xの転置については、テンソルエンジンで転置して計算サイクルを浪費するのではなく、DMAエンジンに転送中の転置を任せる。DMAの実効帯域は下がるが、テンソルエンジンは行列積に専念でき、次のタイルの転送と現在のタイルの計算を重ねられる。出力側も同様で、次のカーネルが転置形を欲する場合は出力の転置形を直接作り、高レベルフレームワークへ戻す場合は通常レイアウトで出すよう、入力の順序の入れ替えだけで切り替える。失敗条件として、この工夫はXUVという三行列の積の形に依存するため、分解を使わない通常の行列積や、消費側のレイアウト要求が異なる構成ではそのまま使えない。

### 4. ブロックサイズの性能モデルとMLPカーネルへの拡張

ブロックサイズの選択は、算術強度とピークSBUF使用量という二つの式でモデル化される。算術強度はブロック高さB_Mが大きいほど上がりデータ再利用が効くが、ピーク使用量も増えて24MBを超えるとスピルする。NeuronMMは、bfloat16での計算律速の閾値である222 FLOPs/バイトを算術強度が超える最小のB_Mを求め、そこから使用量モデルで容量内に収まる組み合わせを選ぶ。実測でも、B_Mが128から1024へ増える間は遅延が31.25ミリ秒から10.99ミリ秒へ下がり、1024を超えるとスピルで悪化する傾向がモデルの予測と一致した。最後に、このXUVカーネルはMLP層全体へ拡張される。SwiGLU型のMLPではゲート射影とアップ射影を並列に計算し、スカラーエンジンとベクターエンジンでSiLUと要素積をオンチップで済ませて転置形のままHBMへ出し、ダウン射影側のカーネルがその転置形をそのまま入力として受け取ることで、層内部での転置を完全に消している。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| ブロック整列SVD | 活性値の共分散と目標圧縮率 | ランクをブロック境界へ丸めて低ランク化しLoRAで回復 | 計算量と重み転送量 | 圧縮率過大で品質が崩れる |
| 中間ストリップのキャッシュ | 行ストリップ分の中間結果 | SBUFへ一度だけ置きVの全列へ再利用 | HBM往復と再計算 | SBUF容量を占有しスピルの危険 |
| 暗黙の転置 | 命令の入力順序 | 恒等式で転置形を直接生成し境界転置はDMAへ | 中間転置の移動と同期 | XUVの形への依存 |
| 性能モデル | 算術強度とSBUF使用量の式 | 計算律速と容量制約からブロック寸法を選択 | テンソルエンジンの遊び | モデル前提外の形状では再調整 |

## 評価

結論は、特異値分解による圧縮だけでも速くなるが、Trainium向けの融合を加えて初めて利得が最大化する、というものである。内訳を見ると、AWS公式カーネルで通常行列積XWと逐次実行の低ランク版XUVを比べた圧縮だけの効果が平均1.54倍（FLOPsは26パーセント減、トラフィックは9.93GBから6.52GBへ34パーセント減）であり、そこへTrainiumFusionを加えるとさらに平均1.36倍になる。融合の内訳は、中間結果をHBMへ出さないことによるトラフィックの2.64倍削減（6.52GBから2.47GB）と、中間転置の消去による転置関連FLOPsの3.5倍削減（78.92GFLOPsから22.55GFLOPs）であり、その結果テンソルエンジンのモデルFLOPs利用率は65パーセントから85パーセントへ上がった。読み方として、圧縮は計算量を減らすが転送の構造は変えず、融合は転送の構造を変えるが計算量は変えないため、二つは直交する利得であり、片方だけでは天井が低いことが分かる。

エンドツーエンドでは、圧縮率0.1と0.2、4モデル、9データセットの範囲で高速化は1.21倍から2.49倍、平均精度の低下は最大でも0.10以内だった。例えばQwen3-1.7Bの圧縮率0.2では1.74倍の高速化に対して平均精度の低下は0.03であり、高速化あたりの精度低下を示す指標γも多くが10パーセント未満に収まる。ただし品質は無損失ではなく、Llama-3.2-1BではWikiText-2のパープレキシティが圧縮なしの9.75から圧縮率0.2で18.87へ悪化しており、言語モデリングの絶対品質で見ると代償は小さくない。LoRAのファインチューニングは常識推論の精度低下をほぼ回復させることがQwen3-1.7Bで示されているが、パープレキシティ側の悪化まで消えるわけではない点に注意が要る。応答指標では、Llama-3.2-1Bで圧縮率を0から0.2へ上げると、エンドツーエンド遅延が41.22秒から22.14秒へ減って1.86倍速くなり、スループットは毎秒49.69トークンから92.52トークンへ、最初のトークンまでの時間は82.22ミリ秒から61.20ミリ秒へ、出力トークンあたり時間は39.65ミリ秒から20.41ミリ秒へ改善した。

## 既存研究との差

従来の特異値分解による圧縮研究、例えば活性値を考慮するASVDやFWSVD、適応的にランクを決めるAdaSVDやDobi-SVDは、どのランクで切れば精度が保てるかという圧縮側の設計が中心で、分解後の二つの行列積をアクセラレータ上でどう実行するかは扱ってこなかった。本論文の差は二点ある。一つは、ランクの選択自体をハードウェアのブロック境界へ結び付け、圧縮率だけでなくタイル整列まで設計対象にしたこと。もう一つは、分解で新たに生じる中間結果の転送・再計算・転置という実行側の費用を、キャッシュと暗黙の転置と性能モデルでまとめて解いたことである。つまり圧縮手法の改良ではなく、圧縮とカーネル設計の協調設計として位置付けられる。

## 限界・実装状況

限界は明確である。第一に、圧縮の適用先はMLP層のみであり、注意層へ広げるとファインチューニングをしても精度低下が大きかったと論文自身が述べている。第二に、評価は単一NeuronCoreかつHBMへ収まる小規模モデルに限られ、テンソル並列などの複数コア実行や大規模モデルでの挙動は未評価である。第三に、手法はTrainiumのSBUFとPSUMの容量、テンソルエンジンの転置仕様、NKIという専用言語に強く依存し、GPUなど他アクセラレータへは設計思想の一部しか移植できない。第四に、圧縮は近似であり、特に言語モデリングのパープレキシティの悪化は圧縮率0.2でも無視できず、品質要件が厳しい用途では圧縮率の選択が制約になる。実装状況として、公式コードがGitHubで公開され、NeuronX Distributed Inferenceの上で動く形が示されているが、上流の公式カーネルへ統合されたという記述はない。

## 一般的な実装上の含意

圧縮で行列を分割すると計算量は減るが、中間結果という新しいデータ移動が生まれるため、圧縮率だけで効率を判断せず、中間結果がどのメモリ階層を往復するかまで含めて評価すべきである。また、低ランク化で生まれた小さい内側次元は、オンチップメモリへ中間結果を丸ごと置く設計を可能にする場合があり、圧縮とキャッシュ戦略はセットで設計すると相乗効果が出る。さらに、転置のようなレイアウト変換は、明示的な変換処理として実装する前に、演算の恒等式や入力順序の入れ替えで結果の形そのものを変えられないか検討する価値がある。
