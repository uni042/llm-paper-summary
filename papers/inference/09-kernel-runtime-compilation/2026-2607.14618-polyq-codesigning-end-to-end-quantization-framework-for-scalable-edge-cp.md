# PolyQ: Codesigning End-to-End Quantization Framework for Scalable Edge CPU LLM Inference

> 平均ビット予算に合わせてチャネルごとにビット幅を配り、並べ替えをコンパイル時に統合して実行時の配置費用を消すことで、小数ビット単位の量子化をCPU上で実用的に動かす量子化とコンパイラの共同設計の研究。

## 概要

端末側の推論では、最も普遍的に使える計算資源はCPUである。しかしCPU向けの低ビット量子化には2つの壁がある。第1に、従来の選択肢は層ごとに2ビット、3ビット、4ビットといった整数の粗い段階しかなく、メモリ予算に対して使い切れないか超過するかのどちらかになりやすい。論文の例では、8Bモデルに3.9GBの予算を与えた場合、均一な3ビットでは3.0GBしか使えず予算の77.1%にとどまり、パープレキシティは8.099だった。第2に、チャネル単位で細かくビットを変える混合精度は、理論上は予算へぴったり合わせられるが、実行時に活性を並べ替える費用が大きく、表引き方式のカーネルとも相性が悪い。5ビットから7ビットのような中間幅は表の大きさが32から128要素へ膨らみ、ベクトル命令の効率を壊す。

提案枠組みは量子化とコンパイラを一体で設計する。量子化側では、活性のエネルギーを重み付けした誤差の代理指標でチャネルごとの重要度を測り、利用者が指定した平均ビット予算の下で誤差が最小になるようビット幅を配分する。使えるビット幅は2、3、4、8、16に限定し、CPUのベクトル命令と表引きに合う単位へ丸める。コンパイラ側では、チャネルを並べ替えて同じビット幅のブロックへまとめ、層をまたいで両立する並べ替えを統合し、配置の正規化を実行時からコンパイル時へ移す。代表的な定量結果として、平均3ビット目標では従来方式よりパープレキシティが2.4%から32.1%改善し、先の例では予算の99.8%を使ってパープレキシティが6.078まで下がった。活性の並べ替えトラフィックは最大70.8%減り、トークンあたりのエネルギーの追加は最適化された表引き基盤と比べて2%未満だった。評価は3つのモデルと3種類のCPUでの実機測定である。

## 問題設定

量子化でビットを下げると重みの読み込み量と保存容量が減るが、量子化の段取りを外れ値へ合わせると通常の値の分解能が失われ、品質が落ちる。層単位の均一量子化はこの調整が粗く、予算の余りを活かせない。一方で細かい混合精度は、チャネルごとに必要な並べ替えを演算子ごとに実行時に行うため、活性の読み書きが増えて利得を食う。GPU向けに設計された混合精度方式はCPUの実行基盤を持たないものも多く、CPU上での直接比較すらできない。本論文の問題設定は、ビット配分の細かさと実行効率を別々に解くのではなく、配分した結果をコンパイラが実行可能な形へ整えるまでを1つの設計として扱うことにある。量子化器だけでは解けず、コンパイラだけでも解けない問題として捉えている点が着眼点である。

## 手法のあらまし

流れは導入時の処理が中心である。まず校正データから各入力チャネルの活性の二乗平均を測り、候補ビット幅ごとに重みの再構成誤差へ重み付けして、チャネルごとの誤差表を作る。次に平均ビット予算を制約として、誤差の合計が最小になるようビット幅を配分する。これは水を注ぐように、ビットを増やしたときの誤差の減り方が大きいチャネルから優先的に配る考え方である。次に命令集合に合う量子化単位へ配分を丸め、実現される平均ビットが目標からずれないようにする。ビット幅が決まったら、コンパイラがチャネルを並べ替えて同じビット幅のチャネルをブロックへ集め、ビット幅ごとのカーネルを割り当て、連続する演算子で両立する並べ替えを統合して、実行時に残る並べ替えを最小化する。実行時は通常の推論として、ブロックごとに割り当てられたカーネルで計算する。

## 手法

### 1. 活性を考慮したチャネル単位の誤差代理指標と予算配分 — 効く場所へビットを配る

この機構が観測するのは、校正データにおける各入力チャネルの活性の大きさと、候補ビット幅で量子化したときの重みの再構成誤差である。保持する状態はチャネルごとの誤差表であり、ビット幅ごとの予想誤差を並べたものである。処理としては、再構成誤差の二乗に活性の二乗の期待値を掛けて出力への影響の代理指標とし、平均ビット予算の制約の下で代理誤差の合計を最小化する配分を求める。選択するのは各チャネルのビット幅であり、削除や転送は行わない。

減るボトルネックは、予算の余りを残したまま全体を一律に低ビット化することで生じる品質損失である。重要なチャネルへ多めにビットを配ることで、同じ平均ビットでも誤差が小さくなる。追加で消費する資源は校正データでの活性統計の収集と配分計算であり、導入時に一度だけかかる。誤った配分時の挙動として、校正データと実際の入力分布がずれると、重要度の推定が外れて品質が想定より落ちる可能性がある。論文は複数モデルで同じ手順が安定して動くことを示しているが、分布ずれへの感度は独立には未評価である。実測では、3ビット目標でも大半のチャネルは2ビットから4ビットの範囲に収まり、8ビットと16ビットへ昇格するのは代理指標で顕著と判定された小さな割合だけであり、実現平均は目標から0.016ビット以内に収まった。

### 2. 命令集合に合わせた量子化単位への丸め — 配分をCPUで実行可能な形にする

第2の機構が観測するのは配分されたビット幅の並びである。保持する状態は、ベクトル命令と表引きカーネルが効率よく扱えるビット幅の集合であり、具体的には2、3、4、8、16である。処理としては、配分結果をこの集合の値へ寄せ、さらにカーネルがまとめて処理する単位に合わせて調整する。先行方式にあった5ビットから7ビットのような中間幅は、表の大きさが指数的に増えてベクトル効率を壊すため採用しない。

この機構が選択するのは実行可能なビット幅への丸めであり、減るボトルネックは、細かい配分がそのままではカーネルで実行できず、8ビットへの逆量子化へ落ちて利得を失う問題である。追加で消費する資源は丸めによる配分の粗さであり、目標平均とのずれとして現れる。実測では3.0ビットから6.0ビットの走査範囲で最大のずれは0.045ビットにとどまり、実用上は予算どおりに実現できている。丸めを誤ると予算超過か品質低下のどちらかになるため、論文は丸め後の実現平均を全モデルで検証している。

### 3. コンパイル時の配置正規化 — 並べ替えを実行時から追い出す

第3の機構が観測するのは、モデル全体の計算グラフと各演算子のチャネル順序である。保持する状態は、演算子ごとに決めたチャネルの並べ替えと、同じビット幅のチャネルを集めたブロック構成、そして層をまたいで統合された並べ替え計画である。処理としては、チャネルを並べ替えてビット幅が均一なブロックを作り、ブロックごとにベクトル命令と表引きに適したカーネルを割り当て、連続する演算子間で両立する並べ替えを伝播させて統合する。グラフ全体で伝播させる点が、テンプレート方式や演算子周辺だけの局所的な統合と違う。

この機構が転送を減らす対象は活性の並べ替えトラフィックである。並べ替えなしでは1トークンあたり3.28MBから14.50MBの並べ替え読み書きが発生していたが、提案方式では1.00MBから2.95MBまで減り、最良の先行方式と比べても46.6%から70.8%少なかった。減るボトルネックは、混合精度の実行時に毎トークン発生する配置費用である。追加で消費する資源はコンパイル時の計画計算であり、実行時には残らない。統合できない並べ替えが残る場合は、その演算子で明示的な並べ替えが残り、利得が部分的に縮む。論文の数値はまさにその残存量を測ったものであり、ゼロにはならないが大幅に減ることが示されている。

### 4. データと制御の流れ

導入時には、校正、配分、丸め、並べ替え計画、カーネル割当ての順に処理が進み、実行可能なモデルが生成される。実行時には、入力がブロック構成に沿って流れ、各ブロックが割り当てられたビット幅のカーネルで計算され、並べ替えは統合済みの箇所では発生しない。ビット予算を変えると配分からやり直すことになるが、同じ予算指定が品質、最大メモリ、遅延の全てを予測可能に動かす点が、論文が設計曲線と呼ぶ性質である。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 誤差代理指標と配分 | 活性統計と再構成誤差 | 予算内で誤差最小のビット配分 | 予算の余りと品質損失 | 校正データへの依存 |
| 量子化単位への丸め | 配分されたビット幅 | 実行可能な幅の集合へ寄せる | カーネル実行可能性 | 配分がやや粗くなる |
| 配置正規化 | 計算グラフ全体 | 並べ替えを統合しブロック化 | 実行時の並べ替え量 | コンパイル時の計画費用 |

## 評価

### まず見るところ

結論は、小数単位の平均ビット予算が、品質、メモリ、遅延、エネルギーの全てに対して予測可能な設計変数として機能することである。品質では3ビット目標で従来方式より2.4%から32.1%良いパープレキシティが得られ、低ビット域で品質が崩壊する境界の直後に回復点が存在し、その回復点でのメモリ量まで示されている。速度では、最適化された表引き基盤と比べてプリフィル遅延の差が数%以内、デコードスループットの差も概ね1割以内に収まり、ビット予算を2から3、3から4へ上げると遅延がほぼビット比どおりに増える予測可能性が確認された。エネルギーの追加は0.8%から1.9%だった。評価の強さは、3モデルと3種類のCPUで実測し、品質と実行性能とエネルギーを同じ枠組みで測った点にある。

数値の読み方として、パープレキシティの改善幅がモデルで大きく違うのは、低ビット域での崩壊の深さがモデルごとに違うためである。5ビットから6ビットでは全方式がほぼ同じ品質へ収束し、先行方式が僅かに良い場面もあるため、提案の利得は低ビット域に集中していると読むべきである。感度としては、予算を上げるほど品質が滑らかに改善し、遅延とスループットもビット比にほぼ比例して動くため、予算がそのまま設計のつまみになる。最悪条件に近いのは2ビット近傍の崩壊域であり、回復点より下では下流精度も大きく落ちることが示されている。

論文では未評価の軸として、校正データと実分布のずれへの感度、バッチが大きい場合の挙動、GPU上での比較、長期的な実運用での安定性がある。実行性能の直接比較はCPU実行経路を持つ方式に限られており、GPU専用方式とは品質のみの比較である点も制約である。

## 既存研究との差

先行する量子化研究は、ビット配分の精度を上げる方向と、実行カーネルを速くする方向が別々に進んできた。活性を考慮する方式や混合精度を自動探索する方式は配分を細かくしたが、CPUで実行可能な形への整形は弱かった。表引き方式の実行基盤は低ビットを速く実行できるが、ビット幅の選択肢は整数の粗い段階だった。本論文は、配分の集合自体を実行基盤が扱える幅に制限し、並べ替えをグラフ全体でコンパイル時に処理することで、細かい配分と実行効率を両立させた点が差である。何を動かす研究かで言えば、量子化の誤差指標だけでなく、コンパイラの配置計画までを動かす研究である。

## 限界・実装状況

限界として、品質評価は特定のテキストと下流タスクの範囲に限られ、校正データへの依存に対する検証は薄い。実行性能はバッチ1を中心に測られており、同時要求が多いサービング条件での挙動は未評価である。対象はCPU専用推論に限られ、GPUや専用アクセラレータとの比較は品質面のみである。コードの公式アドレスは本文に明示されていないため、フロントマターでは null とした。実装は試作段階の枠組みとして評価されており、広く使われる推論基盤へ統合済みという記述はない。ハードウェア依存としては、ベクトル命令と表引きカーネルの対応がCPUの種類ごとに必要になる点が挙げられる。

## 一般的な実装上の含意

量子化の利得は、誤差を小さくする配分だけでは決まらず、その配分を実行時にどれだけ安く実現できるかで決まる。配分の自由度を増やす場合は、同時に配置と並べ替えの費用をコンパイル時へ寄せる設計が必要である。また、平均ビットのような連続的な予算を設計変数として露出すると、品質とメモリと遅延の交換関係が1つの曲線として扱えるようになり、端末ごとの調整が容易になる。回復点のように品質が急に立ち上がる境界を実測で特定しておくことも、実用的な予算設定には欠かせない。
