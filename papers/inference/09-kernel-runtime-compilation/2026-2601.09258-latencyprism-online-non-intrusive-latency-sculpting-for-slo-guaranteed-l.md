# LatencyPrism：分散LLM推論の無停止・低負荷遅延監視

## 概要

LatencyPrismは、本番の大規模言語モデル（LLM）推論で、ユーザーの体感品質に影響する遅延の一時的な増大を、サービスを止めずに検知し、原因の切り分けに必要な実行情報を取得するシステムである。平均スループットや要求全体の平均遅延だけでは、生成途中に数秒の空白が発生するような現象を見落としやすい。さらに入力長、バッチサイズ、キャッシュ命中率などが動的に変わるため、単一の固定遅延閾値では正常な長文要求を異常と誤認し、逆に短文要求の性能低下を見逃す。

提案は、CPU・Python実行時・GPUカーネル・通信・機器状態の情報を同一時刻軸と意味情報で結び、**負荷に応じて本来かかるはずの時間**を予測し、実際の時間が予測から大きく外れたときだけ詳細追跡を起動する。常時監視の軽量モード（Sentinel）と異常時の詳細モード（Deep-Dive）を分離することで、低負荷の連続観測と高解像度の原因分析を両立する。

著者は数千のXPUを持つ本番クラスタで半年以上運用したと報告する。A100、SGLang v0.5.4、Qwen3-32Bを中心とする評価では、常時監視の処理量低下が0.5%未満、遅延増加が0.1%未満で、異常検知の動的窓方式はF1値0.985を示した。ただし「サービス水準目標（service-level objective; SLO）を保証する」という題名は、異常検知と診断による運用支援を指し、全てのSLO違反を自動的に防ぐ制御器が実装されたことを意味しない。

## 背景と問題設定

本番LLM推論は、訓練やオフライン推論とは負荷の性質が異なる。要求の入力・出力長は不規則で、到着率が時間帯によって変動し、複数モデルが同じGPUや通信帯域を共有することもある。モデルの切替やソフトウェア更新も頻繁である。生成はトークン単位の反復計算なので、1回の反復でGPUが詰まっても、要求全体の集計値ではその短い異常が薄まる。一方、ハードウェア監視だけでは、GPU周波数低下やPCIe転送の遅れがどのPython関数やモデルのどの段階に対応するのか分からない。

論文§2は三つの運用上の難しさを挙げる。第一に、平均値への集約で短い生成停止を見落とすこと。第二に、動的な負荷で正常遅延の分布が変わるため固定閾値が役立たないこと。第三に、アプリケーションログとGPUカーネルの時刻や識別子が一致せず、原因箇所を特定できないことである。通常のGPUプロファイラは深い追跡ができるが、常時実行すると負荷が大きかったり、対象サービスの起動条件変更を要したりする。逆にeBPFなどの軽量なシステム観測だけではGPU内部の意味情報が不足する。

このため必要なのは、単に遅延を測る道具ではなく、負荷に応じた正常状態の推定、短い異常の即時検知、CPU側の関数とGPU側の実行をつなぐ意味的な相関、複数ノードの時刻整合、詳細追跡の動的な起動と解除を一体で実装した監視基盤である。

## 手法

### 1. 観測・理解・適応の三層構成

図1の全体設計は観測層（Perception）、理解層（Comprehension）、適応層（Adaptation）に分かれる。観測層はCPUスケジューリング、システムコール、ネットワーク入出力、Python関数呼出し、GPUカーネル実行、メモリコピー、GPU使用率、温度・周波数などを収集する。理解層はそれらを時刻と呼出し関係で結び、LLM推論の反復と事前充填（prefill）・復号（decode）の段階を識別する。適応層は正常時の遅延を予測し、異常が疑われた場合に通知と詳細追跡を開始する。

「非侵襲（non-intrusive）」は計測対象へ全く作用しないという意味ではない。論文§3.1は、利用者がアプリケーションのコードや起動コマンドを変更したり、サービスを再起動したりしなくてよいという運用上の定義を採用する。実装ではptrace、eBPF、CUPTI等の実行時プローブを使うため、計測そのもののオーバーヘッドは残る。収集したデータは共有メモリ経由で別プロセスへ搬送し、追跡終了後にプローブを解除することで影響を抑える。

### 2. ソフトウェアとGPU実行の時刻・意味の整合

論文§4.1ではPython実行時の関数フレームを動的に観測し、関数名、呼出し時間、モデル構造などの情報を取得する。GPU側はCUDA Runtime/Driver APIの呼出しとカーネル・メモリコピーを対応付け、CPU側の論理操作がどのGPU実行を起動したかを復元する。eBPFはCPUスケジューリングとネットワークの状態を補う。NCCLの通信識別子、ランク、ノード名、GPU識別子を対応付ければ、論理的な集合通信が物理的にどのGPU間で実行されたかを調べられる。

異なる計測系の時刻はそのまま比較できないため、同期用の基準イベントと時刻較正を用いて統一時刻軸へ載せる。これによりPython関数の開始・終了、GPUカーネル実行、転送、CPU待機、GPU周波数変化を同じ時系列に重ねられる。図4はソフトウェア側のAPI呼出しとGPU実行の対応付けを示す。これらは本番サービスの異常原因を後から再現するのが難しいという問題に対する観測設計である。

### 3. 推論反復の自動識別と負荷依存の遅延基準

LLMの復号は反復的なので、頻繁に呼ばれ実行時間が比較的安定する関数を手掛かりに、長いイベント列をバッチ単位の反復へ区切る。事前充填は入力長やKVキャッシュ命中率による変動が大きく、復号は比較的規則的なため、論文は復号段階を異常検知の中心に置く。これはTTFTを測れないという意味ではなく、異常基準の学習対象を安定した段階に絞る設計上の選択である。

復号時間はバッチサイズB、過去のKV長Kなどに依存し、単純化すれば`O(B×K)+O(B)`の計算・メモリ負荷を持つ。しかし実際の推論エンジンではGPU計算と通信・CPU処理を重ねるため、全体時間は`max(計算時間, 通信・処理時間)`に近い非線形な折れ曲がりを持つ。著者は単純な線形回帰でなく、勾配ブースティング決定木（gradient boosting decision trees; GBDT）を使って正常遅延を予測する。特徴にはバッチサイズと`B×(入力長+出力長)`に相当するKV負荷量を用い、実行エンジン固有の処理結果に過度に依存する特徴を意図的に避ける。これにより新しい負荷や異なる実装へ移った際の頑健性を重視する。

### 4. 軽量監視と異常時詳細追跡

Sentinelモードでは入力長・バッチサイズなどの最小限の情報と主要な反復時間だけを収集する。GBDTが予測した時間と実際の時間の差から、実測が予測より遅い場合に注目する正の予測誤差を計算する。誤差を滑動窓で平滑化し、学習時の誤差分布から求めた平均と標準偏差に基づく動的な管理上限を超えたら異常とする（原著式1）。標準設定は3σの管理限界と窓長10である。

異常が疑われるとDeep-DiveモードがGPUカーネル、Python関数、システムイベントなどの詳細追跡を動的に起動し、前後の実行文脈を保存する。常時すべてのカーネルを記録する方式と異なり、詳細な計測負荷を異常が起きた時間に限定する。論文は詳細追跡で約7%の負荷が発生すると報告するため、異常検知が頻発する場合に常時監視と同じ低負荷が維持されるわけではない。

## 評価条件と結果

標準評価はNVIDIA A100、SGLang v0.5.4、Qwen3-32Bで行う。常時監視の負荷試験はバッチサイズ1〜512、入力長1〜2048、出力長1〜512と広い範囲を使う。異常の模擬ではCPU・GPU計算競合、周波数制限、メモリ逼迫、NVLink・PCIe転送競合などの条件を作り、異常検知と原因分析に必要なイベントを採取する。異なるソフトウェア環境への一般化試験では、vLLM v0.10.0でDeepSeek-R1-Distill-Llama-70Bをテンソル並列度4で動かす条件も使う。

|---|---|---|---|

| Sentinel常時監視 | 推論遅延の増加 | 0.1%未満 | A100/SGLang中心の評価 |
| Deep-Dive詳細追跡 | 観測負荷 | 約7% | 異常時に限定して起動する |
| 動的窓（Dynamic-Window） | Precision / Recall / F1 | 0.971 / 0.999 / **0.985** | 表5、窓長10、3σの動的閾値 |

| 固定窓（Fixed-Window） | Precision / Recall / F1 | 1.000 / 0.993 / 0.997 | 同じ試験ではF1がより高いが、固定閾値15%に依存 |

表5のF1値0.985は四捨五入すると0.98〜0.99となり、要旨の「0.98」と整合する。一方、同じ異常模擬条件では固定窓方式がF1=0.997、偽陽性率0%で、動的窓より良い値もある。著者は固定15%の閾値を本番の多様な負荷へ適用する難しさを重視し、動的閾値を採用する。したがって「全指標で提案方式が固定閾値を上回る」という主張はしない。

表4の全特徴GBDTは誤差1.53%と高精度だが、SGLang固有の後処理関連特徴へ依存する。一方、物理特徴GBDTは誤差6.06%と悪化する代わりに、KV負荷などの解釈可能な因子を学習する。図5では、未見の負荷、雑音を含む本番データ、vLLMへの移行という異なる条件で予測が安定していくことを示す。雑音を含むデータでは約1,000サンプルで安定し、90%以上のサンプルで予測誤差が10%未満と報告する。これらは平均的な予測誤差と異常検知のF1値を混同せずに読む必要がある。

詳細追跡の検証では、CPU・GPU・通信に由来する性能低下について、Pythonの実行文脈とGPUカーネル、機器状態の対応を使い原因候補を絞り込む。著者は原因局所化の分析スクリプトを下流応用の例と位置付けており、LatencyPrismの中心機能が全ての異常原因を自動修復するわけではない。異常検知、原因局所化、復旧操作は別々の段階である。

## 既存研究との差

一般的なGPUプロファイラはカーネルやメモリ転送を詳しく見られるが、利用者が起動条件を変更する必要があったり、常時運用に不向きだったりする。Pythonフレームワーク内蔵のプロファイラはアプリケーションの意味情報に強い一方、外部のGPU競合や物理通信を見落とすことがある。eBPF中心のシステム監視は低負荷でもGPUカーネルの内部事情を把握しにくい。LatencyPrismは、これらの情報源を動的に結び、LLM推論の反復を単位とする遅延モデルへ落とし込む。

新規性は個々の計測技術ではなく、異なる時刻系の整合、推論の反復認識、負荷依存の正常遅延予測、異常時の詳細追跡を無停止で組み合わせる運用設計にある。推論基盤を更新しても、バッチサイズやKV負荷などの物理的に意味のある特徴へ依拠することで、実装固有の特徴だけを使うモデルより移植性を高めようとする。

## 限界・負の結果

第一に、「無侵襲」はサービスのコード変更や再起動が不要という運用上の意味であり、プローブ自体は対象の実行へ介入し、負荷もゼロではない。詳細追跡の約7%は本番運用で無視できない場合がある。第二に、GBDTによる正常遅延の学習には十分な正常データが必要であり、負荷が急変する条件や未知のハードウェアに移行した直後の精度は保証されない。第三に、復号を主に監視する設計のため、事前充填だけに生じる異常や要求待ち行列の問題を完全に包含するわけではない。

第四に、表4では物理特徴だけを使う方式は全特徴方式より予測精度が低い。解釈可能性と移植性を重視した設計上の交換関係である。第五に、表5では固定窓方式のF1が動的窓を上回る条件があり、動的方式の優位は多様な本番条件で閾値を手動調整しなくてよいことにある。第六に、数千XPUで半年以上の本番運用という著者報告と、公開された再現可能な実験の範囲は区別する必要がある。第七に、異常検知はSLO違反のリスクを早く認識させるが、計算資源を自動再配置して違反を防ぐ完全な閉ループ制御器を評価したものではない。
