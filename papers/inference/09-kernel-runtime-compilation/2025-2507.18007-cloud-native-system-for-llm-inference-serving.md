# Cloud Native System for LLM Inference Serving：層別マイクロサービスの選択的オートスケール

## 書誌・位置づけ

Minxian Xu、Junhan Liao、Jingfeng Wu、Yiyuan He、Kejiang Ye、Chengzhong Xuによる2025年7月24日公開のarXiv v1。原稿にはACMの論文体裁が使われるが、誌名の巻号が`0`、DOIが`10.1145/nnnnnnn.nnnnnnn`というプレースホルダーのため、これを査読済みの正式出版情報として採用しない。対象は大規模言語モデルのクラウド推論サービングであり、モデルの重み圧縮や学習高速化ではない。

## 概要

本研究は、LLM推論を一体のモデルプロセスとして固定配置する方式では、あるTransformer層だけが過負荷になってもモデル全体を複製するしかなく、必要な資源へ局所的に対処しにくいと指摘する。提案する構成は、モデルの各Transformer層を独立したマイクロサービスに分割し、サービス間をgRPCで接続する。KubernetesによるPod管理とIstioサービスメッシュを利用し、実行中の層別遅延とGPU利用率を監視して、遅い層のPodだけをHorizontal Pod Autoscaler（HPA）で増やす。これにより全層を同じ割合で増設するより細かく負荷を分散できる、という仮説を検証する。

実験はLLaMA-2-13B、A100 80GBを備えた3ノードのKubernetesクラスタで行う。40層のうち特に第27層に大きな最大遅延が現れ、負荷時には第30層の230倍を超える最大遅延を観測した。そこでボトルネック層にHPAを有効化した条件を、HPA無効の条件と比較する。バッチサイズ62では対象ボトルネック層の遅延が15.23秒から12.28秒へ、全体処理率が4.07から5.05 QPSへ改善した。前者は約19.4%減、後者は約24.1%増に相当する。

この結果は**Kubernetesの既存機構を層別配置へ適用したシステム評価**であり、特別なAttentionカーネルやKV圧縮方式の発明ではない。追加Pod・レプリカが使用するGPUメモリ、サービス間の通信量、Pod起動時間、課金費用を定量比較していないため、性能改善をそのまま「同一GPU費用での効率改善」と解釈してはならない。

## 問題設定

LLMのprefillは入力長に比例して大きな計算を要求し、decodeはトークン単位の逐次生成と重み・KVアクセスが律速になりやすい。サービスへ到着する入力長・出力長・同時要求数が変動するため、静的なGPU割当はピーク時に遅延を増やし、閑散時にはGPUを遊休させる。従来のモデル単位のレプリカ増設では、特定層の処理だけが遅い場合にも他の層まで複製する必要がある。

原著§2は課題を、要求のリソースプロファイルが不正確、スケジューリングとオーケストレーションが硬直的、モデル構成要素の負荷が不均等、という三系統へ分ける。要求到着時に生成長を正確に予測できないこと、prefill/decodeの異質性、GPU・ネットワークの異質性、バースト負荷の予測困難さがそれぞれの背景にある。

本研究の具体的な評価対象は、この広い課題のうち**モデル内の層別負荷の不均等を観測し、最も遅い層を独立スケールする**部分である。LLM全体の任意の演算を自動分割する汎用コンパイラや、GPU間の最適な配置を数学的に求める最適化器を提案したわけではない。原著にあるクラウドネイティブの一般的利点と、実際に実装・測定された仕組みは区別する必要がある。

## 手法：層別マイクロサービスの構成

### 1. モデルの層を独立したサービスへ分離

従来のモノリシックなLLaMA-2-13B実行を、Transformer層単位のサービス群へ分解する。前段サービスが層の隠れ状態を生成し、次段サービスへgRPCで受け渡すことで推論パイプラインを構成する。サービスを分けることで層ごとのリソース利用率、待ち行列、forward処理時間を独立に観測できる。PodはKubernetesで管理され、Istioがサービス間トラフィックを制御する。

この分割はボトルネック層だけを複製できるという利点を持つ一方、同一プロセス内のGPUカーネル呼出しでは不要だった通信、シリアライズ、サービスルーティング、Pod間のデータ転送を追加する。隠れ状態を各層の境界で受け渡すため、層数が多いほど通信回数も増える。原著はgRPCを採用しているが、転送バイト数、NVLinkの実効利用率、CPU側オーバーヘッドを個別に定量化していない。この追加費用は単一GPUに収まる小規模モデルで特に無視できない。

### 2. 層別プロファイリングで遅延の偏りを検出

PrometheusとGrafanaでGPU利用率、メモリ帯域、層ごとのforward時間を100ms間隔で収集する。Locustが50〜2048トークンの入力を含む要求を発生させ、同時負荷を変えながら各層の最大遅延分布を取得する。図3では、40層のうち第27層が第30層に比べ230倍を超える最大遅延を示し、右裾の長い遅延分布が現れる。

この観測は、各層の演算量が同じでも実際のサービス遅延は配置、競合、待ち行列、メモリ帯域などで大きく変わり得ることを示す。ただし「第27層の演算が230倍重い」という意味ではない。比較対象は**層別の観測最大遅延**であり、同時要求の待機時間やリソース競合が含まれる。最大値は外れ値やサンプル数に敏感なので、平均・分位点の確認が必要になる。

### 3. ボトルネック層のHPAによる水平拡張

HPAを無効にした構成をベースラインとし、ボトルネック層のサービスにGPU利用率の目標値とカスタム遅延閾値を与えてHPAを有効にする。監視値が設定閾値を超えると対象層のPodレプリカ数を増やし、Istio側で新しいPodへ要求を分散する。負荷が落ちればレプリカを減らし、遊休資源を回収できるという設計である。

入力は層別監視値と現在のPod状態、内部処理はHPAの閾値判定とPod増減、出力は対象層のレプリカ数・ルーティング先の変化である。複製対象をモデル全体ではなく層に限定することが方式の核となる。追加コストはPodの立ち上げ、対象層重みの複製、サービスディスカバリ、分散した状態管理である。原著ではGPU利用率・遅延の具体的な閾値、Pod増設数、スケール反応時間の詳細な値が十分に示されず、再現時の重要な未確定条件として残る。

### 4. 実装対象と未実装要素の区別

原著§3はロードバランシング、オートスケーリング、移行、負荷予測、アプリケーションプロファイリング、細粒度モジュール化という六つの構成要素を概説する。ただし§4の実験で定量的に比較しているのは、**層別プロファイリングに基づくボトルネック層のHPA**である。時系列予測器による先行スケール、稼働中KVキャッシュの無停止移行、複数GPUへの最適配置探索について、独立したアルゴリズムや評価結果を提示しているわけではない。システム全体の構想と実測された寄与を混同しない。

## 評価

### 評価環境と測定条件

原著§4.1によれば、Kubernetesクラスタは3ノードで各ノードにNVIDIA A100 80GBを備え、GPU間はNVLinkで接続される。モデルはLLaMA-2-13Bで、各Transformer層を別サービスへ分割した。サービス間はgRPC、トラフィック制御はIstio、監視はPrometheus/Grafana、負荷生成はLocustである。入力長は50〜2048トークン、監視サンプリング間隔は100ms。評価対象はバッチサイズを変えた推論遅延とQPSである。

| 項目 | 原著の実験設定 |
|---|---|
| モデル | LLaMA-2-13B、Transformer層をサービス分割 |
| クラスタ | Kubernetes 3ノード、各A100 80GB、NVLink |
| 通信・制御 | gRPC、Istio、Kubernetes HPA |
| 観測 | Prometheus/Grafana、100ms間隔 |
| 負荷生成 | Locust、入力50〜2048 tokens |
| ベースライン | HPA無効、ボトルネック層を自動増設しない |
| 提案構成 | ボトルネック層にHPA、GPU利用率と遅延閾値でPod増減 |
| 主指標 | 推論遅延、全体QPS、層別最大遅延 |

論文は平均遅延・ピーク遅延・ジッタを測る意図を述べるが、本文から確定できる代表的な数値はバッチ62の遅延とQPSである。TTFT、TPOT、P50/P95/P99の各値、KVキャッシュの移動時間、同時利用GPU時間、Podレプリカ数、HPA収束時間は本文の数値として十分に示されていない。再現評価ではこれらを別途取得すべきである。

### 主要結果と数値の読み方

原著§4.2、Figure 3・4から確認できる値を整理する。

| 条件・指標 | HPAなし | 層別HPAあり | 差分・解釈 |
|---|---:|---:|---|
| バッチ62、対象ボトルネック層の推論遅延 | 15.23秒 | 12.28秒 | 2.95秒減、約19.4%短縮 |
| バッチ62、全体処理率 | 4.07 QPS | 5.05 QPS | +0.98 QPS、約24.1%増 |
| 高負荷時の層別最大遅延 | 第27層が第30層の230倍超 | 比較値の個別数値は未記載 | 負荷集中の局所性を示すが演算量差ではない |

遅延の短縮率は`(15.23−12.28)/15.23 = 0.1937`、処理率の増加率は`(5.05−4.07)/4.07 = 0.2408`である。遅延について「1.24倍速い」と表現するなら15.23/12.28≈1.24倍であり、24.1%のQPS増加と数値が似ていても異なる指標である。実験条件を揃えずに倍率だけ引用してはならない。

Figure 3の第27層と第30層の230倍差は**最大観測遅延の比**であり、LLaMA-2-13Bの層そのものの理論FLOPsが230倍異なるという意味ではない。原著は高負荷での右裾の長い遅延をボトルネックとして捉え、HPAによる負荷分散が尾部遅延を軽減すると解釈している。ただし分位点の具体値と測定ばらつきが十分に示されていないため、厳密なP99改善率や統計的有意性を主張できない。

### 比較対象・構成要素除去の限界

原著はHPA有効/無効の二条件を比較するが、層別マイクロサービスを**分割せずに同じGPU予算で運用したモノリシック実装**との詳細な定量比較は示していない。つまり「同じ層別分割の上でHPAを有効にしたら改善した」という結果と、「層別分割自体が従来の高性能サービングより優れている」という主張は別である。

また、ボトルネック層だけのHPAとモデル全体のHPA、GPU使用量を固定したレプリカ再配分、予測型HPA、Pod増設数を固定した実験などを切り分けた構成要素除去はない。Kubernetesの既存HPAが負荷に応じてレプリカを増やせばQPSが増えるのは自然だが、その代わりに消費したGPU資源量が不明である。したがって「より少ないGPUで同じSLOを満たした」との結論は導けない。

## 既存研究との差

PagedAttentionはKVキャッシュのGPUメモリ断片化を抑え、Continuous Batchingは実行中のリクエストをバッチへ出し入れしてGPU利用率を高める。DistServeはprefill/decodeの性質の違いに合わせてリソースを分離し、Llumnixは要求移行による負荷平準化を扱う。本研究の特徴はこれらのモデル内部実行・段階分離・要求移行とは異なり、**Transformerの層をサービス境界にし、既存のKubernetes HPAを層単位に適用する**点にある。

層別のレプリカ増設はGPU上で単一モデルを効率よく走らせる方法ではなく、クラスタ運用時のボトルネックへ資源を局所投入する方法である。高速なカーネルと組み合わせる余地はあるが、gRPCによる層間通信とHPAの制御遅延を考慮しなければ、低負荷や短い入力で従来方式より遅くなる可能性がある。既存のサービングフレームワークへ移植するには、KVキャッシュを層ごとにどこへ保持するか、デコード時の状態整合、サービス再配置の扱いを設計する必要がある。

## 限界・負の結果・実装時の注意

1. **追加資源の費用を測っていない。** HPAによってPodを増やすので、増設したレプリカのGPU時間・VRAM・電力・課金額が性能利得の対価となる。QPS 24%増をコスト当たり処理率24%増と読み替えられない。
2. **通信の増分が不明。** 40層の境界をgRPCで越える構成はシリアライズ・ネットワーク・同期コストを伴う。NVLinkがあってもアプリケーション層のオーバーヘッドは消えない。通信帯域、転送遅延、各サービスのキュー長は独立に評価すべきである。
3. **HPAの閾値・反応時間が不十分。** 監視間隔100msは明記されるが、Pod追加までの秒数、閾値、最小/最大レプリカ数、warmup中のモデルロード費用は定量化されていない。バースト時に追従できるかはこの値に左右される。
4. **比較条件の不足。** HPA無効との比較はあるが、同一GPU予算のモノリシック、全モデルレプリカHPA、静的最適配置との比較がない。実験結果は層別HPAの有用性を示すが、一般に最適なアーキテクチャである証明ではない。
5. **生成品質とSLOの未評価。** 分散した各層の実装で生成トークンが元のLLaMAと同一か、長文脈時のKV状態が正しいか、TTFT・TPOT・P99がどの程度改善するかは十分に検証されていない。
6. **ハードウェア外挿の制限。** A100 80GB×3のクラスタにおける測定を、単一GPU 12GBやPCIeのみのノード間通信へ直接適用できない。層別通信が律速になる可能性がある。
7. **原著の書誌プレースホルダー。** PDF冒頭のACM巻号・DOIは未確定のテンプレート値なので、査読済み論文や正式JACM出版と記載しない。一次資料はarXiv v1として固定する。

## 実装・サーベイ上の示唆

この研究を推論システムの比較に入れる場合は、モデルの計算高速化ではなく、**層単位のクラスタ資源スケール**というカテゴリへ分類するのが適切である。性能比較表にはA100×3、LLaMA-2-13B、バッチ62、HPA無効との比較という条件を必ず付ける。特に、QPSが24.1%改善したことを「GPU当たり24.1%高速化」と記さない。再現時にはPod追加数、総GPU秒、層間通信量、TTFT/TPOT、P99、KV保持位置を計測し、同じGPU予算のモノリシック構成をベースラインへ追加するのが妥当である。
