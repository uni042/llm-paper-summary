# NM-SpMM: Accelerating Matrix Multiplication Using N:M Sparsity with GPGPU

> N:Mスパース行列積について疎性で計算律速からメモリ律速へ移ることを分析し、階層的ブロッキングと疎性に応じたパッキングおよびパイプラインで、汎用実装nmSPARSEより2.1倍速くするGPUカーネル。

## 概要

深層学習、とりわけ大規模言語モデルの推論では、線形層の行列積が計算とメモリの大部分を占める。重みを枝刈りして疎にすれば計算量は減るが、不規則な疎性はGPUで並列に処理しにくく、負荷の偏りと不規則なメモリアクセスで理論上の削減が実測の高速化へ結びつかない。N:Mスパース性は、連続するM個の枝刈り単位のうちN個だけを残す規則的な疎性であり、計算量と重みのメモリアクセスをN/Mへ減らしつつ、精度との釣り合いを取りやすい。本論文は単位を要素ではなくベクトルとし、長さの異なるベクトルと多様なNとMの組み合わせを、特定ハードウェアに依存せず扱える汎用実装を作る。

課題は、疎性の程度で詰まり方が変わることである。著者らは算術強度、すなわちメモリアクセスあたりの計算量を疎性ごとに式で表し、ルーフライン分析と組み合わせた。中程度の疎性では残る計算が多く計算律速だが、疎性が約70パーセントを超えると、圧縮される重み側の作業量とフットプリントは比例して減るのに、相手の行列側は同じ割合では減らず、メモリ律速へ移る。この分析に基づき、密な行列積の階層的ブロッキングを土台に、疎性に応じたメモリアクセスとパイプラインを使い分けるのがNM-SpMMである。

**代表結果:** Llamaモデルの線形層から抽出した行列形状100件、疎性50.0パーセント、62.5パーセント、75.0パーセント、87.5パーセントでの実機評価で、NM-SpMMは汎用N:Mスパース性の最先端とされるnmSPARSEより全体で2.1倍速く、密な行列積のcuBLASに対しては1.4倍から6.3倍の高速化を示し、疎性による計算削減から得られる理論最大値へ近づいた。A100でのルーフライン測定では、4水準の疎性で理論ピーク性能の96パーセント、93パーセント、95パーセント、88パーセントに達した。

## 問題設定

対象は、密な行列積のうち一方の重み行列をN:Mスパース化した半疎な行列積である。重み側は残ったベクトルだけを圧縮行列へ詰め、どのベクトルが残ったかを行列の索引で別に保持する。計算量はN/Mへ減り、重み側の読み出しも同じ割合で減るが、代わりに索引の読み出しと、索引を介して相手行列の列を選ぶ間接アクセスが生じる。この間接アクセスが共有メモリやレジスタの使い方を崩すと、削減した計算量以上に待ち時間が増える。

既存方式の不足は三つある。第一に、NVIDIAのスパーステンソルコアは2対4の要素単位パターンなど限られた比率しか扱えず、専用ハードウェアへ依存する。第二に、任意の比率を扱う汎用実装nmSPARSEは、N:Mパターンがもたらす局所性を十分に使っておらず、疎性の水準ごとの最適化もない。第三に、非構造な疎性を扱うSputnikのようなライブラリは、不規則アクセスと負荷不均衡のオーバーヘッドが大きい。さらに、疎性を上げるほど算術強度が下がるため、単一の最適化では全水準をカバーできない。計算律速の領域で効く工夫と、メモリ律速の領域で効く工夫を分けて設計する必要がある、というのが本論文の出発点である。

## 手法のあらまし

処理の流れは次のとおりである。まず枝刈り済みの重みを、残ったベクトルだけの圧縮行列と、残存位置を示す索引行列へ変換しておく。実行時は入力行列と圧縮行列と索引行列を、GPUの共有メモリへ入る大きさのブロックへ切り、スレッドブロックごとに共有メモリへ載せて部分積を計算し、レジスタ内の累算器へ足し込む。ブロック内ではワープ単位、さらにスレッド単位へ二段階に切り分け、各スレッドは索引を見て相手行列の必要な列を取り出し、外積を累算する。疎性が中程度なら相手行列のブロックをそのまま載せ、高疎性なら事前に用意した列情報で必要な列だけを詰めて載せる。ロードと計算は二重バッファで重ね、索引はレジスタへ先読みする。ブロック寸法は行列の大きさが小、中、大の三区分で推奨値が用意され、共有メモリ容量の制約式から残りの寸法が決まる。

## 手法

### 1. 性能分析モデル — 疎性で律速が移ることを先に測る

この機構が観測するのは、疎性の水準、ベクトルの長さ、ブロック寸法から決まる算術強度である。保持する状態は分析式そのもので、部分行列の計算量を、その読み出し量で割った値として算術強度を定義する。疎性が上がると分子の計算量は比例して減るが、分母では重み側の項しか比例して減らず、相手行列側の項が残るため、算術強度は単調に下がる。著者らは疎性70パーセントを境に中程度と高疎性を分け、代表水準として50.0パーセント、62.5パーセント、75.0パーセント、87.5パーセントを選ぶ。この分析が選択するのは後段の最適化の方向であり、計算律速なら計算命令でロードを隠し、メモリ律速ならフットプリント削減を優先する。これにより減るボトルネックは、律速を取り違えた最適化の無駄である。追加資源は分析自体にはほぼかからない。誤り時の挙動として、遷移点はハードウェアの算術強度に依存してずれるため、著者らも境界は機種ごとに変わり得ると明記しており、固定した70パーセントを他機種へそのまま当てはめることはできない。

### 2. 階層的ブロッキング — 密な行列積の局所性を疎な計算へ持ち込む

この機構が観測するのは入力行列の寸法と、共有メモリの容量である。保持する状態は三段階のブロック寸法であり、共有メモリ単位の寸法、ワープ単位の寸法、スレッド単位の寸法を、容量の制約式とレジスタ上限255本の制約のもとで決める。選択されるのは各ブロックが担当する部分行列であり、入力行列、圧縮行列、索引行列の小片を共有メモリへ載せて何度も再利用し、ワープ内では32スレッドを4掛ける8の格子へ並べて共有メモリのバンク競合を避け、各スレッドは自分の小片の外積をレジスタで累算する。これにより減るボトルネックはグローバルメモリへの繰り返しアクセスであり、N:Mパターンは負荷不均衡を生まないため、密な行列積のブロッキングをそのまま土台にできる点が著者らの主張である。スレッド単位の小片を大きくすると計算対メモリアクセス比は上がるが、レジスタ消費が増えて同時に走るワープ数が減る占有率との交換になる。小さい行列へ大きい区分の寸法を使うと効率が落ちることは評価でも確認されており、寸法の選び違いがそのまま性能低下になる。

### 3. 疎性に応じたメモリアクセス — 高疎性では必要な列だけを詰める

この機構が観測するのは索引行列であり、高疎性の場合にオフラインの前処理で、各ブロックで実際に必要な相手行列の列の集合を列情報として抽出し、あわせて索引の並べ替えとレイアウト変換を行う。保持する状態はこの列情報で、追加のGPUメモリは索引側に対して1パーセントから10パーセント程度とされる。実行時に選択されるのは読み込む列であり、列情報を使って必要な列だけを詰めて共有メモリへ載せるパッキングにより、相手行列のフットプリントとグローバルメモリの読み出しを減らし、算術強度を引き上げる。パッキング時の読み出しは、枝刈りウィンドウのパターンが揃えばN/Mまで下がり得るとされる。逆に中程度の疎性では有効データが作業集合の大半を占めるため、詰めずにそのまま載せる非パッキングを選び、前処理と列情報の読み出しの費用を避ける。これにより減るボトルネックは、高疎性で支配的になる無駄な読み出しである。誤り時の挙動として、パッキングは列情報を先に読む分だけ開始が遅れる依存を生み、次節のパイプラインで隠す設計になっている。列情報の抽出は重みのパターンが固定されている前提のオフライン処理であり、推論中にパターンが変わる使い方では前処理をやり直す費用がかかる。

### 4. パイプライン設計 — 律速側に応じて隠す対象を入れ替える

この機構が観測するのは、ロードと計算の依存関係である。保持する状態は二重バッファ化した共有メモリ上のブロックと、レジスタへ先読みした索引である。中程度の疎性では計算律速なので、現在のブロックを計算している間に次のブロックをもう一方のバッファへ非同期に載せ、計算命令でロードの遅延を隠す。高疎性ではメモリ律速で、しかもパッキングのために列情報を先に読む必要があるため、逆にグローバルメモリから共有メモリへのロード命令で計算命令の遅延を隠す向きに組み替える。内側のカーネルでも次のワープ小片を先に読み、索引を共有メモリから毎回引かずレジスタへ先読みすることで、間接アクセスの影響を小さくする。これにより減るボトルネックは、ロードと計算の直列化による計算ユニットの空転である。追加で消費する資源は二重バッファ分の共有メモリであり、ブロック寸法を圧迫する。誤り時の挙動として、計算とロードの量の釣り合いが崩れる機種では隠蔽が効かず、評価でも浮動小数点性能に対して帯域が相対的に低いRTX 3090とRTX 4090では、疎性0パーセントの時点で間接アクセスのオーバーヘッドを隠し切れなかったと報告される。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 性能分析モデル | 疎性とブロック寸法 | 算術強度を計算し律速の遷移を判定する | 最適化の方向の取り違え | 遷移点が機種依存 |
| 階層的ブロッキング | 行列寸法と共有メモリ容量 | 三段階に切り共有メモリとレジスタで再利用する | グローバルメモリへの反復アクセス | レジスタ増による占有率低下 |
| パッキング／非パッキング | 索引行列と疎性の水準 | 高疎性では必要な列だけ詰め、中程度ではそのまま載せる | 高疎性での無駄な読み出し | 列情報の前処理と追加メモリ |
| パイプライン | ロードと計算の依存 | 二重バッファと索引先読みで遅延を隠す | 計算ユニットの空転 | 共有メモリの二重使用 |

## 評価

結論は、汎用GPUの通常の浮動小数点演算だけでも、局所性と疎性適応を徹底すれば、N:Mスパース行列積が計算削減の理論値に近い高速化へ届く、ということである。段階的最適化の除去に相当する比較では、疎性50.0パーセントと62.5パーセントの計算律速領域では階層的ブロッキングだけの版が既に強く、後段の追加は小さい。一方で75パーセントと87.5パーセントのメモリ律速領域では、フットプリント削減とパイプラインの版が大きく効く。分析モデルの予測どおりに効く場所が分かれることが、この論文の評価の核である。

関連方式との比較では、A100上でNM-SpMMはcuBLASに対して疎性50.0パーセントで1.8倍、62.5パーセントで2.4倍、75.0パーセントで3.5倍、87.5パーセントで6.3倍であり、nmSPARSEに対しては同じ順に1.5倍、1.8倍、1.5倍、1.2倍である。nmSPARSE自身もcuBLAS比で1.2倍、1.3倍、2.4倍、5.3倍と速いが、局所性と疎性適応の不足分だけ差が付いたと読める。非構造な疎性を扱うSputnikは不規則アクセスのため最も遅い部類にとどまる。全体の総括として著者らはnmSPARSE比2.1倍、cuBLAS比1.4倍から6.3倍とまとめている。総括のレンジと個別水準の値は別の集計であり、混同しないよう注意が要る。

ルーフライン分析では、4096立方の行列でNM-SpMMがピークの88パーセントから96パーセントへ達するのに対し、nmSPARSEは49パーセントから73パーセントにとどまり、高疎性ではフットプリント削減によって算術強度そのものがnmSPARSEより高くなることが示される。ブロッキング寸法の評価では、小さい行列には小さい区分のカーネル、大きい行列には大きい区分のカーネルがそれぞれ最良であり、寸法を使い分ける必要性が裏付けられた。疎性0パーセント、すなわち密な計算として動かした場合でもA100ではcuBLASとほぼ同等であり、間接アクセスのオーバーヘッドはA100では隠せている。ただしRTX 3090とRTX 4090では帯域に対して計算性能が高く、同じ条件でも隠し切れず、機種による差が残る。

注意点として、評価はカーネル単体の行列積であり、モデル全体のエンドツーエンドの推論遅延や精度は測られていない。枝刈り後のモデル精度は本論文の対象外で、既存の精度維持研究と組み合わせる前提である。データセットはLlamaの線形層から抽出した形状100件で、入力の長さに相当する寸法は256から4096までであり、大きなバッチや長い文脈でのサービング負荷そのものではない。

## 既存研究との差

NVIDIAのスパーステンソルコア向け方式は、扱えるパターンが2対4などに限られ専用ハードウェアを前提とするのに対し、本論文はベクトル単位の任意のN:M比率を汎用GPUの通常演算で扱う。Spathaのようなベクトル形式の方式は二段階の枝刈りで作るパターンがアルゴリズム側のN:Mパターンと一致せず、精度維持研究と組み合わせにくいと著者らは位置づける。nmSPARSEとの差は、パターンの対応範囲ではなく最適化の中身にあり、階層的ブロッキングによる局所性の活用と、疎性の水準ごとにメモリアクセスとパイプラインを切り替える疎性適応を加えた点が新しい。非構造な疎性を扱うSputnikに対しては、規則性そのものが負荷均衡と局所性を生むという対比で差を示している。

## 限界・実装状況

限界は、評価がFP32のカーネル単体に限られ、低精度形式やテンソルコアを使う構成、モデル全体のエンドツーエンドの推論性能、枝刈り後の精度が未評価である点、形状がLlamaの線形層由来の100件と比較的限られる点、律速の遷移点や隠蔽の成否がGPUの計算と帯域の釣り合いに強く依存し、RTX 3090とRTX 4090では利得が縮む点である。高疎性向けの列情報はオフライン前処理を前提とし、重みパターンが動的に変わる用途は対象外である。実装状況は、C++とCUDAによる公式コードがGitHubで公開されており、オープンソースと明記される。上流の推論ランタイムへ統合されたという記述は論文中にない。

## 一般的な実装上の含意

疎なカーネルの最適化は、疎性の水準で律速が計算からメモリへ移ることを前提に設計すべきであり、単一の最適化を全水準へ当てはめないことが重要である。算術強度を式で見積もってから、計算律速なら計算でロードを隠し、メモリ律速なら読み出すデータそのものを間引く、という順序は他の構造化疎性や量子化カーネルにも応用できる。また、規則的な疎性は負荷均衡を保証するため、密なカーネルの実績あるブロッキングを土台にできる、という見立ても再利用できる。
