# Mirage: A Multi-Level Superoptimizer for Tensor Programs

> Mirageは「既知のアルゴリズムに対して良いGPUスケジュールを探す」だけでも、「数式を書き換えて既存カーネルを組み合わせる」だけでもない。テンソル計算をGPUのカーネル・スレッドブロック・スレッド階層をまたぐμGraphで表し、**数式の形、融合境界、並列化方法を同じ探索の中で変える**ことで、人手では実装量が大きい複合最適化を自動発見する。

## 概要

GPU向けテンソルプログラムの最適化には複数の層がある。例えば、`A×B + A×C`を`A×(B+C)`へ変えるのは代数変換、複数演算を一つのカーネルへ融合するのはカーネル構成の変更、どの次元をどのブロックやスレッドへ割り当てるかはスケジュール変換である。従来のテンソルコンパイラはこのうち一部を固定して残りを探索することが多く、階層をまたぐ組合せを自動では見つけにくい。

Mirageはテンソルプログラムを**μGraph**という階層グラフで表す。上位のカーネルグラフは複数GPUカーネル間の依存を、各カーネル内部のブロックグラフはスレッドブロック単位の処理を、さらにスレッドグラフはスレッド単位の演算を表す。同じ計算を別のμGraphへ変換できるため、代数変換とスケジュール変換、新しい融合カーネルの生成を一つの探索空間に置ける。

問題は探索空間が急増することである。Mirageは各部分グラフを抽象式で要約し、目的出力へ寄与しない候補や同じ意味を持つ重複候補を早期に枝刈りする。その後、残った候補が入力プログラムと同値かを有限体上のランダム試験で確率的に検証し、最後にデータ配置、演算順序、メモリ配置を詰めてCUDAコードを生成する。

評価ではA100/H100上でGQA、QKNorm、RMSNorm、LoRA、GatedMLP、normalized Transformerを扱い、既存の高度最適化手法に対して最大3.3倍のカーネル高速化を示す。一方、モデル全体に組み込んだ改善は最大約1.9倍で、探索自体は最大数時間を要する。したがってこれは要求ごとの動的最適化ではなく、**配備前に高価な探索を一度行い、その結果を繰り返し使う**方式である。

## 背景と問題設定

### スケジュール探索だけではアルゴリズムを越えられない

TVM、Ansor、Tritonのような方式は、与えられた計算をどのタイルへ分け、どの順序で実行するかを最適化するのが得意である。しかし、入力された計算式そのものが固定なら、別の等価な数式へ変形した方が融合しやすいケースを探索できない。

逆にTASOやPETのようなグラフ・代数最適化は、等価な演算グラフを探索できるが、各演算内部のブロック/スレッド構成までは同時に変えない。結果として、数式の書換えと新規カーネル生成を組み合わせて初めて成立する最適化は人手実装に残る。

Mirageの狙いは、この境界を外すことである。例えばFlashAttention型の最適化は、単なる演算順変更ではなく、中間行列をグローバルメモリへ書かないためにブロック内部の処理構造まで変える必要がある。Mirageはこの種の変形を探索可能な表現へ落とし込む。

### スーパーオプティマイザでは「正しい候補を速く捨てない」ことが難しい

候補を総当たりすれば組合せ数が爆発する。一方、強すぎる枝刈りは最良候補を消す。さらに、数式を大胆に組み替えた候補が元の計算と等価かを検証しなければならない。

そこでMirageは、探索時には抽象式で「この候補が最終出力の必要な式を含み得るか」を安価に判定し、候補生成後には別の等価性検証器を通す。探索の高速化と正しさの確認を分離した構成である。

## 手法

### 1. μGraphでGPUの3階層を同じ表現へ入れる

入力はテンソル演算グラフである。Mirageはこれを、カーネル、スレッドブロック、スレッドの3段階をネストしたμGraphへ変換する。

カーネルグラフでは複数CUDAカーネル間のデータ依存を表す。各カーネルの内部にはブロックグラフがあり、共有メモリへ載せるタイルやブロック演算を記述する。さらにその内部のスレッドグラフでレジスタ上の細かな計算を表す。

この統一表現により、「二つの上位演算を一つのカーネルへ融合する」「ブロック内部で二つの行列積を並行実行する」「中間値を共有メモリへ保持する」といった異なる階層の変更を一つの候補として表せる。

### 2. μGraph生成器が代数変換と構造変換を同時探索する

生成器は入力μGraphから、演算を追加・置換・融合して別の候補を作る。ここで探索しているのは、既存ライブラリカーネルのパラメータだけではない。元の計算と数学的に等価な別表現や、従来存在しなかった融合境界も候補になる。

例えばLoRAの
`W×X + B×A×X`
を、そのまま3回の行列積として実行するのではなく、連結を使って行列積をまとめ、共有メモリ上で後段を融合できる形へ変える。このように「どの式を計算するか」と「どうGPUへ載せるか」が連動する。

### 3. 抽象式で探索を枝刈りする

全候補を具体テンソル式のまま比較すると高価なので、Mirageは部分μGraphの意味を抽象式で表す。抽象式は最終出力へ必要な代数構造を粗く保持し、候補が目的の式を包含し得ない場合や、既に同等の候補を探索済みの場合に枝を打ち切る。

この枝刈りは単なるヒューリスティックではなく、論文が定義する範囲では最適解を失わない条件を持つ。一方、探索上限や対応演算集合そのものは有限なので、任意のCUDAプログラム全体から絶対最適を保証するわけではない。

評価では、この抽象式枝刈りを外すとRMSNormのブロックグラフ探索が6演算程度で10時間枠へ達し、11演算を必要とする最良候補まで到達できない。枝刈りは実用的な探索深さを成立させる主要要素である。

### 4. 確率的等価性検証で誤った書換えを除く

生成された候補は、元プログラムと同じ結果を計算する必要がある。Mirageは指数演算が経路上で高々一回現れるLaxプログラムについて、有限体上でランダム入力を生成し、元μGraphと候補μGraphの出力一致を調べる。

非同値な候補が複数回の試験をすべて通過する確率は試験回数とともに任意に小さくできるという保証を使う。実装では高速化のためGPU上で有限体試験を行い、浮動小数点のオーバーフロー/アンダーフロー等を拾う追加試験も入れる。

この検証は「実行が速そうだから採用する」前に機能同値性を確認する防波堤である。ただし現実の実装では探索速度を優先して簡略化した試験も使っており、形式証明そのものではない。

### 5. 検証後にレイアウト・演算順・メモリ配置を最適化する

機能的に同値なμGraphだけに絞った後で、テンソルレイアウト、演算スケジュール、メモリ配置を最適化する。レイアウト選択は制約付き最適化として扱い、Z3を用いて対応可能な配置からコストが小さいものを選ぶ。

演算順はブロック内同期を減らすように調整する。メモリ配置では中間テンソルの寿命が重ならない領域を再利用し、共有メモリやレジスタの使用量を抑える。

これらを候補生成と同時に全探索せず、等価性検証後に後処理することで、グラフ構造とレイアウトの組合せ爆発を避ける。

### 6. CUDAコードを生成しPyTorchへ統合する

最適μGraphからCUDAコードを生成し、コンパイルして呼び出し可能なカーネルへする。実装はcuDNN/cuBLAS、CUTLASS、CUDA PTXを利用し、JITコンパイルしたカーネルを少数行の変更でPyTorchへ組み込める。

したがって出力は「推奨スケジュール」ではなく実行可能なGPUコードである。探索費用は配備前に一度支払い、同じ形状の要求で生成カーネルを繰り返し再利用する。

## 1プログラムを最適化する流れ

入力テンソルプログラムをLax部分へ分割し、各部分を初期μGraphへ変換する。生成器が抽象式を使いながら候補μGraphを広げ、成立しない候補を枝刈りする。

候補が得られると等価性検証器が元プログラムとの機能一致を確認する。通過した候補に対してレイアウト、演算順、メモリ配置を最適化し、実機で性能を測定する。

最終候補をCUDAへコード生成し、PyTorchプログラムへ置換する。入力形状や対象GPUが変われば最良μGraphも変わり得るため、必要ならその条件について再探索する。

## 評価

### 評価条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA A100 40GB、H100 40GB |
| 主マイクロベンチ | GQA、QKNorm、RMSNorm、LoRA、GatedMLP、normalized Transformer |
| 元モデル例 | LLaMA-3-70B、Chameleon-7B、LLaMA-2-7B、GPT-3-7B-LoRA、Falcon-7B、nGPT-1B |
| 文脈長 | GQA 8K、QKNorm 4K |
| 並列 | GQAは4 GPUテンソル並列。その他は主に単GPU |
| 精度 | 半精度浮動小数点（FP16） |
| 比較対象 | TASO/PET、PyTorch + torch.compile + FlashAttention、TensorRT / TensorRT-LLM、FlashAttention / FlashDecoding、Triton |
| 測定 | ランダム入力で各実験1,000回、平均実行時間。全方式でCUDA Graphを使用 |
| モデル全体 | Chameleon、nGPT、LLaMA-3、LoRAへ生成カーネルを統合 |
| 探索上限 | 既定でカーネルグラフ最大5演算、各ブロックグラフ最大11演算 |

### 主な結果

| 条件 | 結果 | 何が効いたか |
|---|---:|---|
| 6種マイクロベンチ総括 | 最良既存手法比 最大**3.3倍** | 代数変換・スケジュール・新規融合カーネルの組合せ |
| GQA | 既存手書きカーネル比 最大**2.2倍** | グリッド寸法と並列化次元を条件ごとに探索 |
| GQA | デバイスメモリアクセス 最大**7倍削減** | Q/KV系列・ヘッド・バッチの分割方法を変更 |
| GQAアブレーション | TensorRT-LLMと同じグリッド寸法に固定すると**18%低下** | 固定ヒューリスティックを外す価値 |
| QKNorm + Attention | 最大**1.4倍** | 正規化と注意を一つのカスタムカーネルへ融合 |
| LoRA | **1.1〜2.4倍** | 3つの行列積と加算を再構成・融合 |
| GatedMLP | A100 **1.5倍**、H100 **2.7〜3.3倍** | 2行列積をブロック内並行化しSiLU/Mulまで融合 |
| normalized Transformer | TensorRTより遅いケースあり | 軽い計算では共有メモリ往復の固定費が支配 |
| モデル全体 | PyTorch基準で速度比 **0.9〜1.9倍** | カーネル利得が全モデル時間へは希釈される |
| RMSNorm探索 | 11演算上限でMirage **28秒**、抽象式枝刈りなし **10時間超** | 枝刈りが深い探索を可能にする |
| 最適化アブレーション | 各要素を1つ外すと **5〜70%性能低下** | スレッドグラフ、レイアウト、順序、メモリ計画が全て寄与 |
| 全探索時間 | Laxプログラム当たり最大**約4時間** | 配備前の一回限りの費用 |

### 最大3.3倍とモデル全体の倍率は分けて読む

3.3倍は個々のテンソルプログラムの最良ケースであり、LLM要求全体が3.3倍になるという意味ではない。モデル全体では、未置換演算、CPU処理、カーネル起動、通信などが残るため改善は0.9〜1.9倍の範囲になる。

normalized TransformerではTensorRTへ届かないケースもあり、探索で融合できたから必ず速いわけではない。共有メモリへ一度載せる設計自体の固定費が、演算の軽いカーネルでは支配的になる。

### ハードウェアごとに最適構造が変わる

GatedMLPはA100で1.5倍、H100で最大3.3倍と差が大きい。これは同じ数式でもGPU世代のSM数、共有メモリ、非同期転送能力などによって最良の分割・融合が変わることを示す。

Mirageの価値は「一つの万能カーネル」を得ることではなく、対象形状と対象GPUに合わせて探索をやり直せることにある。

## 既存研究との差

Triton、TVM、Ansorのようなスケジュール中心の最適化は、ユーザーが与えたアルゴリズムを効率良くGPUへ写像する。一方Mirageは、アルゴリズム自体の等価変形も探索し、その変形を成立させる新しいカーネル構造まで同時に生成する。

TASO/PET等の代数・グラフ最適化に対しては、グラフの書換え後に既存カーネルへ落とすだけでなく、ブロック・スレッド階層まで同一表現で持つ点が異なる。

手書きFlashAttention/TensorRTカーネルに対しては、専門家が条件ごとに実装する複数の変種を自動探索で発見できることを狙う。ただし探索可能な演算集合とコード生成器の能力に依存するため、人間が書ける任意CUDAを完全に包含するわけではない。

## 限界・実装状況

第一に、探索は高価である。最大約4時間を要する条件があり、形状が毎要求大きく変わる処理をオンラインでその場最適化する用途には向かない。形状が繰り返し現れる配備前最適化で費用を償却する前提が強い。

第二に、確率的等価性検証の強い保証はLaxプログラムという演算クラスに依存する。ReLUのような非Lax演算には別のソルバ型検証器を用意しているが、新演算の数学的性質を記述する追加作業が必要になる。

第三に、浮動小数点では数学的同値性と数値的同一性が一致しない場合がある。Mirageは追加の浮動小数点試験を入れるが、演算順変更による丸め誤差まで完全に消すわけではない。

第四に、生成カーネルの性能は対象GPUに依存する。A100で最良のμGraphがH100でも最良とは限らず、別世代へ持ち込むなら再探索が望ましい。

第五に、モデル全体の改善はマイクロベンチほど大きくない。カーネル外の処理が支配的なワークロードでは、スーパー最適化の効果はアムダール則で制限される。

## サーベイ上の含意

MirageはLLM高速化を「新しい手書きカーネルを発明する問題」から、**意味を保ったプログラム構造そのものの探索問題**へ押し広げる。特に、代数変換とGPUスケジュールを別工程にせず、互いに依存する選択肢として探索する点が重要である。

推論基盤へ取り込む場合は、オンラインスケジューラとは役割が違う。Mirageが生成するのは形状・GPUに特化した高速カーネルであり、vLLM等の要求スケジューリングやKV管理の下層に置かれる。したがって評価では、カーネル倍率だけでなくモデル全体へ統合した速度、探索費用、対象形状の再利用頻度まで見る必要がある。
