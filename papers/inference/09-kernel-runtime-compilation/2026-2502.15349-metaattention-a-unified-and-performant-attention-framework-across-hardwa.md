# MetaAttention：注意演算の共通記述から複数GPU基盤向けカーネルを生成する

## 概要

MetaAttentionは、異なる注意機構をハードウェアごとに手作業で実装する費用を削減しながら、専用実装に近い実行性能を得るためのカーネル生成基盤である。査読付き会議版の名称はMetaAttentionだが、著者が公開した先行プレプリントarXiv:2502.15349の題名は「AttentionEngine: A Versatile Framework for Efficient Attention Mechanisms on Diverse Hardware Platforms」である。両者は著者・基本設計・最大10.4倍という結果が対応する一方、**本稿で詳細な数値・実験条件を確認したのは公開プレプリント版**である。会議版の未照合の図表が完全に同一だとは断定しない。

中核の着想は、標準的なソフトマックス注意（softmax attention）と、状態を逐次更新する線形・再帰型注意を、関連度計算（relevance scoring）と集約（aggregation）という二つの意味操作へ抽象化することにある。利用者はマスク、尺度変換、正規化、ゲート処理などを関数として記述し、基盤側が演算グラフを構築する。生成器は中間テンソルのタイル形状、記憶階層、転送と計算のパイプライン段数を探索し、対象GPUに合わせてカーネルを生成する。

この方法は単なる高水準APIではない。注意演算の構造を保存したまま最適化するため、汎用の演算子単位コンパイラでは発見しにくいオンライン正規化、演算融合、再帰状態のチャンク並列化を実現する。さらに、問い合わせ・鍵の次元と値の次元が異なるモデルでも、無駄なゼロ埋めを避けられる。著者公開プレプリントのH100評価では、一部の既存実装が十分に対応していない演算構成で最大10.4倍のカーネル速度改善、複数モデルの推論全体で平均1.4倍を報告する。ただし、この最大値は全モデル・全GPUでの平均ではない。

## 問題設定と従来方式の制約

注意演算は系列長が増えると計算量とメモリアクセスの両面で支配的になる。プレプリント表1ではLLaMA-3Bの推論における注意演算の実行時間割合が系列長2,048で55%、8,192で82%と報告される。この割合は測定対象のモデル・実装に依存するため、あらゆるLLMに一般化できる定数ではないが、長文脈で注意演算を最適化する重要性を示す。

FlashAttention系列は標準的な注意演算に対して非常に強力である。しかし、モデルが採用する演算がソフトマックス以外へ変わる、問い合わせ・鍵と値の次元が異なる、再帰状態を更新する、といった変更が入ると、専用の演算融合・メモリ配置・スケジューリングを再設計する必要がある。プレプリントではDeepSeek-V2-Liteの問い合わせ・鍵の次元192と値の次元128、DiffTransformer-3Bの128と256という不一致を具体例に挙げる。両者を同じ次元へパディングする実装は余分な計算とデータ転送を生む。

逆に、一般的な深層学習コンパイラは利用者が記述した行列積、要素ごとの演算、行方向の縮約を個別の演算子として最適化しがちである。オンラインソフトマックスのように行最大値と指数和をタイル間で更新し、中間の注意行列を丸ごと保存しない変形には、注意演算固有の意味を把握する必要がある。FlexAttention等の柔軟な仕組みも、標準的な並列注意を中心に設計されているため、再帰型の状態更新や異種GPUへの展開では別の実装上の制約を受ける。

MetaAttentionが解こうとするのは「一つの注意演算を最高速にする」問題だけではない。**新しい注意機構の実装を追加するとき、モデルごと・GPUごとに新しいカーネルを手書きせず、意味のある最適化空間を再利用する**という開発効率の問題である。対応する演算パターンを記述できる範囲では性能と保守性の両方を狙うが、全ての任意のテンソル演算を表現できる万能コンパイラという主張ではない。

## 手法：関連度計算と集約を核にした二系統の注意記述

### 1. 並列型の関連度計算と集約

並列型（parallel pattern）は問い合わせQ、鍵K、値Vを入力とし、関連度行列を `Q @ K^T` に相当する積で求め、その値を変更・正規化した重みSとVから `S @ V` に相当する集約を行う。利用者が変更できるのは、問い合わせの尺度変換、スコアのマスクや活性化、行方向の正規化などである。たとえば標準ソフトマックス注意ではQに次元の平方根による尺度補正を適用し、因果マスクを加え、スコアをソフトマックスで正規化する。ReLU注意ではスコアの負値をゼロにする関数を用い、標準ソフトマックスとは異なる計算を指定する。

ここで重要なのは、利用者がPython関数として書いた処理を、そのまま独立したGPU演算子の列にするのではない点である。前処理・行方向の縮約・後処理を、行列積のタイル処理と融合できる位置へ挿入する。問い合わせ・鍵・値の次元が不一致でも、演算に必要な寸法のままタイルを設計できるため、値次元に合わせてスコア側を無理に拡張する必要がない。

### 2. 再帰型の状態更新

再帰型（recurrent pattern）は過去の全トークン間の関連度行列を明示的に作る代わりに、KとVに由来する情報を状態hへ順次蓄積し、現在のQからその状態を読み出す。論文はMamba2、RetNetの再帰版、ゲート付き保持機構などを対象に含める。利用者は鍵へのゲート適用や、過去状態への減衰・ゲート適用を記述する。これにより並列注意と異なる依存関係を同じ高水準の意味操作へ接続する。

再帰状態を更新する演算には逐次依存があり、並列型と同じ二つの行列積をそのまま適用することはできない。MetaAttentionは別の再帰型カーネル雛形を持ち、可能な部分をチャンク化してテンソル演算器を活用する。従って「同じ抽象化で表現できる」と「同じ低水準カーネルを実行する」は別である。利用者が書く意味操作を共通化し、実行計画は計算パターンごとに生成することが性能上の要点となる。

### 3. オンライン行正規化の三段階インターフェース

ソフトマックスを行列全体の生成後に計算すると、スコア行列の保存と再読込が必要になる。MetaAttentionはオンライン行正規化（online row-wise normalization）を、`online_prologue`、`online_fwd`、`online_epilogue` の三段階で定義できる。最初に行最大値と指数和の状態を初期化し、次に各タイルで局所最大値と指数和を更新し、最後に正規化を確定する。タイル間で引き継ぐ値は全スコア行列より小さく、行列積・指数・縮約を融合できる。

このインターフェースの利点は、標準ソフトマックスに限らず、行方向の縮約を伴う他の注意機構へも同じ実行基盤を再利用できることにある。一方、利用者が指定するオンライン更新関数が正しい結合則・数値安定性を持たなければ、カーネルを高速化しても出力の正しさは保証されない。公開プレプリントは正規化状態を前進・後退計算グラフへ取り込むことを説明するが、任意のユーザー関数に対する形式的な正しさ証明を示すものではない。

## 手法：中間テンソルを中心にした二段階スケジューリング

### 4. 計算グラフからカーネル雛形へ

フロントエンドは利用者が指定した要素演算・行方向縮約を計算グラフとして追跡し、テンソル形状と依存関係を記録する。勾配の対応関係もグラフに保持し、前進と後退の実行コードを生成する。バックエンドはこのグラフをトポロジカル順に並べ、式の生成と対象雛形に応じたコード生成を分ける。並列注意の雛形はオンライン正規化と融合を重視し、再帰注意の雛形はチャンク並列化を重視する。プレプリントの実装はTileLang、CuTe等を利用し、NVIDIAとAMDの基盤に合わせて低水準コードへ落とす。

この段階では、利用者が新しい注意方式を追加したときにも既存の雛形と探索器を使える。一方、対応していない種類の状態変換や特殊な同期が必要な場合は、新しい雛形や低水準実装の追加が必要になる。生成されたカーネルの性能は、抽象化の表現力だけでなく、その対象GPU向け雛形の実装品質にも依存する。

### 5. IntermediateTensorとDeviceConfig

探索空間の中心は中間テンソル（IntermediateTensor）である。各中間値に対し、`tile` はタイル形状、`mem` は格納する記憶階層、`pipelineStage` は転送と計算のパイプライン段数を表す。計算グラフ上の出力形状から入力へタイル条件を伝播し、Q・K・V・スコア・集約の中間値が整合する候補を作る。タイルを大きくすると行列積の利用率は上がり得るが、レジスタや共有メモリの消費が増える。

装置設定（DeviceConfig）は、基準タイル形状（`basetile`）と各記憶階層の容量（`memoryInfo`）を持つ。基準形状は行列演算器の命令形状やアクセス粒度への整合を制約し、容量はレジスタ・共有メモリ・大域メモリへ置ける中間値の量を制約する。したがって、同じ注意記述でもH100とMI250で選ばれるタイルと配置は同じとは限らない。装置ごとの制約を明示することが、コードの移植性と実測性能の接点になる。

### 6. タイル候補の列挙と記憶階層の段階的引き下げ

探索の外側はタイル構成の列挙である。グラフと装置の基準タイル形状から実行可能な候補を導出し、各候補について内側の資源配置探索を実行する。内側ではまず中間テンソルを高速なレジスタへ置くと仮定し、サイズの大きいテンソルから順に配置を検討する。容量・整列制約に違反する場合は、一部の中間値を共有メモリや大域メモリへ下げて再検討する。全ての候補が不可能なら、そのタイル構成を破棄する。

実行可能な候補についてプロファイリングを行い、測定した遅延が最小の計画を採用する。外側のタイル候補列挙と内側の配置探索を分けるため、タイル寸法の組合せと記憶階層の組合せを単純に全列挙するより探索範囲を絞れる。ただし、これは最適性の一般的な数学的保証ではない。候補集合の設計、カーネル雛形、測定ノイズ、コンパイル費用に依存し、測定対象の形状・GPUが変われば再探索が必要となる。

## 評価：条件と比較対象

著者公開プレプリントの実験は、Ubuntu 20.04上のNVIDIA H100とAMD Instinct MI250で行われた。H100側はCUDA 12.4、Triton 2.3.1、MI250側はROCm 6.2.4、Triton 3.1.0と記載される。注意演算のマイクロベンチマーク（microbenchmark）では、バッチ1または8、系列長2,048・4,096・8,192を中心に、標準ソフトマックス、Sigmoid、ReLU、並列保持機構、Mamba2、再帰保持機構、ゲート付き保持機構を評価する。

比較対象は演算の種類により異なる。標準ソフトマックスではFlashAttention 2/3、SigmoidではFlashSigmoid、Mamba2では公式Triton実装、線形注意ではFlash Linear Attentionを用いる。手書きの融合カーネルが存在しない構成ではPyTorchを比較対象にし、プログラミング基盤としてFlexAttentionやFlashInferとも比較する。**最大10.4倍の値にはPyTorch等の比較対象が含まれ、全てがFlashAttention 3に対する改善ではない**。演算単体の実測と、モデル全体の推論・学習速度は分けて解釈する必要がある。

モデル全体の評価ではH100単一GPUでTransformers実装の注意演算を置き換える。対象はDeepSeek-V2-Lite、DiffTransformer-3B、Mamba2-2.7B、YOCO-160Mであり、半精度FP16を使う。学習側ではDiffTransformer-3B、YOCO-160M、ReLU注意を用いるViT-S/16を対象とする。AMD側はH100と同一の全構成ではなく、ソフトマックス、ReLU、Mamba2、再帰保持機構から選んだ部分集合を測定する。したがって、両GPU間の絶対速度をそのまま比較した実験ではない。

## 評価：定量結果と機構との対応

| 評価範囲 | 条件・比較対象 | 報告値 | 読み取り上の注意 |
|---|---|---|---|
| 標準ソフトマックス注意のカーネル | H100、DeepSeek-V2-LiteおよびDiffTransformer-3Bの非対称次元、FlashAttention系列 | 前進平均1.88倍、後退平均1.52倍 | 同じヘッド次元のLLaMA-3.1-8Bでは同等程度 |
| 非標準注意のカーネル | H100、Sigmoid/ReLU/並列保持機構、方式ごとの既存実装 | 平均3.6倍、範囲1.1〜10.4倍 | 最大値は対応の薄い演算・比較実装を含む |
| Mamba2の状態空間演算 | H100、公式Triton実装 | 前進平均1.99倍、後退平均1.65倍 | モデル全体の速度ではない |
| RetNet/ゲート付き保持機構 | H100、Flash Linear Attention | 前進平均1.33倍、後退平均1.93倍 | 演算種別・形状によるばらつきがある |
| モデル全体の推論 | H100単一GPU、4モデル、FP16、注意演算の置換 | 平均1.4倍 | DeepSeek-V2-Liteの代表条件では1.85倍 |

非対称なヘッド次元に対する前進1.88倍・後退1.52倍という結果は、単にGPUのピーク性能を上げたためではない。値次元が問い合わせ・鍵の次元と異なる場合に、専用のタイルと演算融合を生成してパディングを回避するという手法上の差と対応する。標準的なLLaMA構成では高度に最適化された既存実装に近い性能であり、MetaAttentionが全条件で既存専用カーネルを上回るわけではない。

Sigmoid、ReLU、並列保持機構で最大値が大きいのは、既存の手書き融合カーネルが不足している構成に対し、意味を保った融合と行方向正規化を適用できるためである。Mamba2と保持機構での改善は、再帰型雛形とチャンク並列化による状態更新の実装差を示す。ただし、これらの演算単体の改善をそのままLLMサーバの総スループット改善へ読み替えてはいけない。

モデル全体の推論平均1.4倍は、カーネル置換の効果が他の演算とメモリアクセスにより薄まることを示す。プレプリントではDeepSeek-V2-Liteの例で注意演算が推論時間の約85%を占め、注意演算を2.2倍に高速化した条件で推論全体が1.85倍になったと報告する。これは注意以外の処理が残るためであり、注意演算単体の倍率と全体の倍率が異なることを具体的に裏付ける。

AMD MI250の平均3.3倍・2.0倍は、装置設定とカーネル雛形をAMD向けに切り替えられることの実験的証拠である。一方、H100と同じ全演算・全形状の横並び評価ではないため、「MI250の方がH100より高速」と解釈することはできない。また、公開実装がサポートするGPUと原著が測定したGPUは明示されており、他の世代や消費者向けGPUの動作・性能は追加検証が必要である。

## 限界：既存研究との差と実装上の意味

FlashAttention 2/3は標準ソフトマックス注意を非常に効率よく実行するための専門実装であり、MetaAttentionはそれを単純に置き換える最高速カーネルというより、**注意機構の種類と対象GPUが変わっても同じプログラミングモデルを使えるようにする基盤**である。FlexAttentionやFlashInferは柔軟な注意演算の指定と実行を支援するが、論文が強調する差は並列型と再帰型を横断する抽象化、非対称ヘッド次元、AMD向けの生成と記憶配置探索である。

公開実装はSJTU-IPADS/MetaAttentionで、注意演算の例とNVIDIA H100・AMD MI250向けの性能再現手順を提供する。リポジトリは論文図11と図14に対応するベンチマークを明示し、比較ライブラリの更新によって数値が多少変わり得ると注意する。コード公開と再現用スクリプトの存在は、任意のGPUで同じ速度改善を保証することとは異なる。特にRTX 4070 Super等のAda世代消費者GPUでの検証は、公開された主要な再現条件に含まれない。

この研究の追加費用は、カーネル生成・コンパイル・候補計画のプロファイリングと、対象演算・対象GPUに対応した雛形の維持である。形状が頻繁に変わるサービスでは最適計画の探索結果をどの粒度で再利用できるかが重要になるが、公開プレプリントはオンラインの多租借サービング全体でのP99遅延、起動時間、動的バッチ混在、モデル入替え費用を体系的に評価していない。これらを測らずに本番LLMサーバの総費用削減を断定できない。

さらに、対象GPUはH100とMI250を中心とし、対象モデルも限定される。マイクロベンチマークの大幅な速度向上には既存専用実装がない場合が含まれるため、成熟した専用カーネルが利用可能な標準注意では利得が小さくなる。正規化や状態更新をユーザーが独自に記述する場合は、数値安定性、勾配の正しさ、対応する演算雛形の制約を検証する必要がある。再帰型の一般的な状態遷移すべてを表現できるとまでは原著は証明していない。

**査読版とプレプリントの境界**も重要である。2026年PPoPP会議版の書誌と10.4倍という主張は会議公式ページで確認したが、ここで詳細に示した数値・実験環境は2025年の著者公開プレプリント本文に基づく。最終会議版の全文を別途入手した際は、図表・実装変更・著者追加を照合し、差分があればこの原稿を修正するべきである。会議版未確認の細部を最終版固有の確定事項として扱わない。
