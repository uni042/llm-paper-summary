# FlashMem: Supporting Modern DNN Workloads on Mobile with GPU Memory Hierarchy Optimizations

> モバイルGPUで全重み事前読み込みをやめ、負荷容量を考慮したオフライン計画で重みの断片を計算と重ねてテクスチャメモリへ流すことで、11モデルでメモリ2.0〜8.4倍削減と初期化込み1.7〜75.0倍高速化を実現する実行枠組み。

## 概要

スマートフォン上で深層ニューラルネットワーク（DNN）を動かす枠組みは通常、推論を始める前にモデルの全重みをメモリへ読み込み、モバイルGPUが得意とするテクスチャメモリ向けの配置へ変換し終えてから計算を始める。この事前読み込みは推論中のストレージアクセスをなくす代わりに、二つの代償を払う。第一にピークメモリであり、OnePlus 12上でMNNを使った測定では、音声認識のWhisperはピーク4,077MB、画像生成のSD-UNetはピーク4,858MBを消費し、複数モデルを順に使う多モデル用途では到底収まらない。第二に初期化の遅延であり、同じ測定でSD-UNetは読み込み4,159ミリ秒と変換17,588ミリ秒に対して推論自体は1,647ミリ秒、GPT-Neoでも変換2,898ミリ秒に対して推論337ミリ秒と、計算より準備の方がはるかに重い。モデルを一度だけ長く使うなら初期化は薄まるが、カメラの拡張現実や翻訳のように検出、認識、生成のモデルを短く切り替える用途では、モデルごとにこの準備を繰り返すため致命的になる。

FlashMemは、重みを全量保持する前提そのものを外す。重みを一様なチャンクへ分け、どの層の計算中にどのチャンクを統合メモリからテクスチャメモリへ変換するかを、デプロイ前にオフラインで静的に計画する。その計画どおりに実行時は重みをオンデマンドで流し込み、計算とデータ移動を重ねるため、保持するのは使用中の重みと変換途中の分だけになる。計画を作る際の鍵は、演算子ごとに「追加のデータ移動をどれだけ重ねても遅くならないか」がまったく違うことであり、本論文はこの耐性をプロファイルから学習して計画の制約へ入れる。

**代表結果:** OnePlus 12、バッチサイズ1、11モデルでの実機評価で、FlashMemは既存枠組みに対して平均メモリ使用量を2.0倍から8.4倍削減し、初期化と実行を合わせた遅延では1.7倍から75.0倍の高速化を記録した。直前の研究試作であるSmartMemとの個別比較では、GPT-Neo 1.3Bで15.8倍、SD-UNetで9.3倍の高速化と、DeepViTでは平均メモリ826MBから165MBへの5.0倍削減が得られ、どの比較枠組みも実行できなかったGPT-Neo 2.7Bを1,132MBで実行できた。ただし同じモデルを何度も繰り返す温かい開始では、事前読み込み済みのSmartMemの推論単体時間の方が短い場面がある点も論文は明記する。

## 問題設定

モバイルGPUのメモリは階層になっている。CPUとGPUが共有する統合メモリと、2次元の局所性に特化した専用キャッシュを持つテクスチャメモリである。重みはディスクから統合メモリへ入り、そこで2.5Dテクスチャ配置、すなわち多次元テンソルを深さ4程度の小さな2次元タイルへ組み替えた配置へ変換されてテクスチャメモリへ移り、演算装置で使われる。テクスチャメモリを使う実行自体は統合メモリだけの場合より最大3.5倍速いと先行研究が示すが、その恩恵を得るための変換と複製が、事前読み込み方式では全重み分だけ初期化時に集中する。

既存対策の不足は、変換を速くすることと、読み込みをなくすことが別々に進んできた点にある。SmartMemは計算グラフ側の配置変換の冗長さを消して推論を速くしたが、全重みを先に読み込む構造は変えていない。逆に単純な先読み、例えば次の層の重みだけを前もって運ぶ方式は、変換がディスク読み込みに追いつかず最大でFlashMemの4.3倍遅くなることが本論文の比較で示される。つまりボトルネックは、どの層の余力でどれだけ運ぶかという配分の問題であり、演算子の性質を無視した一律の重ね合わせでは、敏感な演算子を遅くするか、運び切れずに待ちが出る。本論文の着眼点は、この配分を制約充足問題として定式化し、演算子ごとの耐性を実測で与えて解くことにある。

対象とする多モデル方式は先入れ先出し型、すなわちモデルを順番に実行していく形であり、高優先度モデルが割り込むプリエンプティブな方式は対象外と明記される。また各モデルが連続して大量に呼ばれる用途ではなく、モデルが入れ替わるたびに初期化が効いてくる用途が主眼である。

## 手法のあらまし

処理はオフラインと実行時の二段に分かれる。まずモデルを計算グラフとして解析し、各演算子について、追加のデータ移動を重ねたときの遅延増加をプロファイルし、回帰モデルで負荷容量、つまりその層が大きな遅延増加なしに同時に変換できるデータ量を予測する。次に重ね合わせ計画生成ソルバーが、各重みについて、ディスクから統合メモリへ読み始める最も早い層と、統合メモリからテクスチャメモリへ変換するチャンクの割り当てを層ごとに決める。融合された演算子が計画の容量を圧迫する場合は、融合を部分的にほどいて変換を挟める境界を増やす。最後に、各カーネルをテンプレートで書き換え、次のタイルの重みを先読みしながら現在のタイルを計算する、分岐のないパイプライン実行にする。実行時は計画どおりに重みが流れ、初期化と推論は分離されず一体化した時間として進む。ソルバーはオフラインでモデルごとに一度だけ動くため、推論時のオーバーヘッドにはならない。

## 手法

### 1. 重ね合わせ計画生成の定式化 — 何をいつ、どの層の余力で運ぶか

この機構が観測するのは、実行順序が線形に決まった計算グラフ、各重みが最初に使われる層の位置、そして後述する層ごとの負荷容量である。保持する状態は計画そのものであり、各重みについて二種類の決定を持つ。一つは事前読み込み集合に入るかどうかと、統合メモリへ読み始める最も早い層であり、読み始めから消費までの層数の差を読み込み距離と呼ぶ。もう一つは、重みを一様サイズのチャンクへ割った上で、各層が何チャンクをテクスチャメモリへ変換するかという割り当てである。目的関数は、事前読み込みする重みの総量と、読み込み距離の合計を重み付きで最小化することであり、制約として、すべてのチャンクが消費前に変換され終えること、変換は読み込み開始以降でのみ行えること、各層時点での変換中メモリがピーク上限以下であること、各層の変換量が負荷容量以下であることが課される。問題は制約プログラミング充足問題へ帰着され、Google OR-Toolsで解かれる。

これにより減るボトルネックは、全重みの同時保持によるピークメモリと、初期化への変換の集中である。重みが必要になる直前寄りに分散して運ばれるため、保持期間が短くなり、変換は計算の裏に隠れる。追加で消費する資源はオフラインのソルバー時間であり、150秒の制限内で、GPT-Neo Smallでは45秒で最適解、大規模モデルでは121秒から136秒で実行可能解が得られたと報告される。失敗時の挙動も設計されており、制約が厳しくて解が見つからない場合は、容量を緩めるソフトな閾値調整、選んだ重みの事前読み込みへの繰り入れ、貪欲なヒューリスティクスへの切り替えという段階的なフォールバックで、必ず実用時間内に計画を返す。実行経路が実行時に決まる動的ネットワークでは分岐の探索でソルバー時間が増えることが隅の事例として挙げられ、将来課題とされる。

### 2. 負荷容量の決定 — 演算子の重ね合わせ耐性を実測で分ける

この機構が観測するのは、各演算子に追加のデータ転送を重ねたときのカーネル遅延の増加である。予備実験では、SoftmaxやLayerNormは少量の転送でも大きく遅くなり、活性化や加算などの要素単位演算子は大きな転送まで耐え、行列積は中間で比較的大きな流入にも耐えることが示された。そこで演算子を三類へ分ける。要素単位型はメモリ律速だが単純で中程度の容量、行列積や畳み込みなどの再利用型はデータ再利用と計算量が大きく高い容量、SoftmaxやLayerNormなどの階層型は同期が多く容量が低い、という整理である。保持する状態は、10モデル以上から集めたプロファイルで学習したXGBoost回帰モデルであり、追加負荷に対する遅延を予測する。処理は、この予測から層ごとの容量閾値を決めることで、階層型では追加読み込みの許容を0パーセント、再利用型では20パーセント、要素単位型では300パーセントという、基準遅延の短さまで考慮した非対称な閾値が採用される。

これにより減るボトルネックは、重ね合わせ自体が計算を遅くする干渉である。容量を超えて運ぶ層では変換が計算と競合して全体が遅くなり、逆に余力のある層を使い切らなければ運び切れず待ちが出るため、層ごとの上限を実測で与えることが計画の実現可能性を決める。誤予測時の挙動として、容量を過大に見積もればその層の遅延が増え、過小に見積もれば重みが事前読み込みへ回ってメモリ削減が痩せる。単純方式との比較がこの機構の価値を裏付けており、同じ演算子種別の層だけから先読みする方式でも不均衡が残ってFlashMemより最大2.4倍遅かった。

### 3. 適応的融合 — 融合しすぎたカーネルをほどいて運ぶ境界を取り戻す

この機構が観測するのは、融合されたカーネルが計画へ与える容量の損失である。演算子の融合はカーネル起動と中間メモリを減らす有効な最適化だが、k個の演算子を1カーネルへ融合すると、データ移動を挟める段階がk個から1個へ減り、合計容量は各容量の和ではなく最小値程度まで縮む。その結果、運び切れない重みが事前読み込みへ追いやられる。保持する状態は融合ペナルティというスコアで、融合のせいで新たに事前読み込みへ入る重みの費用と、読み込み距離の増加を重み付きで合計したものである。処理は、ソルバーが容量不足を検出したときにペナルティの高い融合から順に候補を選び、分割後に容量の合計が元の容量へ利得係数を掛けた値を上回る場合にだけ二つのサブカーネルへ割り、グラフを更新してソルバーを再実行することである。具体例として、行列積と加算とGeLUの融合は、行列積と加算の再利用型と、GeLUの要素単位型へ割ることで両方の容量を回復する。一方で階層型の融合は容量耐性が低く同期の要求も強いため、分割せず保持する。

これにより減るボトルネックは、融合による計画の自由度の喪失である。追加費用は、分割で増えるカーネル起動と中間メモリであり、利得条件を満たす場合にだけ割ることで、融合本来の利得をむやみに捨てない設計になっている。分割しても容量が足りなければ、重みは事前読み込みへ回るため、結果はメモリ削減幅の縮小として現れる。

### 4. テクスチャ向けカーネル書き換え — 分岐なしのパイプラインで流し続ける

この機構が観測するのは、計画が各演算子へ割り当てた読み込みのタイミングである。保持する状態は、演算子種別ごとの再利用可能なカーネルテンプレートであり、Jinjaで記述され、計算グラフから自動で具体化される。処理は、各反復の冒頭で次のタイルの重みを先読みし、続いて現在のタイルを計算するという均一な順序へループを組み替えることである。読み込むか計算するかをスレッドごとに条件分岐で決める素朴な方法は、SIMT実行での分岐発散を招いて効率を落とすため、分岐そのものを構造から消す。パイプラインが回り始めると、先読みの待ち時間は前の反復の演算の裏に隠れ、最後に余りの演算を処理する締めの反復が置かれる。2.5Dタイル配置と組み合わせることで、テクスチャキャッシュの局所性と連続したデータ移動の両方が得られる。

これにより減るボトルネックは、重みの到着待ちによる演算装置の遊休と、分岐発散による実行効率の低下である。追加費用はテンプレート整備という開発側の費用であり、モデルごとにカーネルを手書きする必要をなくすことが明示的な狙いである。計画どおりにデータが届かない場合の特別な回復処理は論文では述べられず、計画自体が容量制約で到着を保証する前提に立つ。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 計画生成ソルバー | グラフ、消費位置、層別容量 | 読み込み開始層とチャンク割り当てを制約充足で決定 | ピークメモリと初期化集中 | オフラインで最大150秒の解探索 |
| 負荷容量予測 | 演算子への追加転送時の遅延 | 三類の演算子ごとに許容閾値を設定 | 重ね合わせによる干渉 | 見積り誤差で利得が痩せる |
| 適応的融合 | 融合のペナルティスコア | 利得条件を満たす融合だけ分割し再計画 | 融合による容量の喪失 | 起動回数と中間メモリが増える |
| カーネル書き換え | 計画の読み込みタイミング | 先読みと計算を分岐なしで交互実行 | 到着待ちと分岐発散 | テンプレート整備が必要 |

## 評価

結論は、全重み事前読み込みを計画的なストリーミングへ置き換えると、初期化込みの遅延と平均メモリが同時に大きく下がり、その利得はモデルが大きいほど増える、というものである。内訳分析では、SmartMemを土台に計画生成ソルバーを足すだけで5.3倍から8.1倍の高速化と2.1倍から3.8倍のメモリ削減が出ており、適応的融合がさらに1.5倍から5.1倍の高速化、カーネル書き換えが1.0倍から2.55倍の高速化を上乗せする。つまり主役は計画生成であり、他の二つは計画が成立する余地と実行効率を広げる役割だと読み取れる。畳み込み主体のモデルでは利得が小さめで、SD-UNetのメモリ削減は2.5倍、DepthAnything Smallは1.7倍にとどまる。理由はWinograd変換のような畳み込み重みの変換が重ね合わせできず、一時的なメモリも増えるためと説明される。

交換条件も示される。事前読み込み率を上げるほど実行遅延は下がるが初期化が支配的になって合計は増え、平均49.3パーセントの重みを重ね合わせた点で、追加遅延がほぼ無視できる水準でメモリを大きく下げられる釣り合いが得られた。エネルギーでは、平均電力はSmartMemよりやや高いものの、時間が短いためDeepViTでエネルギー4.5ジュールと、MNN比83パーセント、SmartMem比87パーセントの削減になった。注意点として、同じモデルを3回から12回連続で使う温かい開始では事前読み込み済みのSmartMemの方が速く、FlashMemの土俵はコールド開始とモデルの切り替えである。また精度については全枠組みが同じ事前学習モデルで同じ精度を確認したとして、性能のみが報告される。

## 既存研究との差

配置変換の冗長さを消すSmartMemとの差は、変換の速さではなく、変換と読み込みをいつ行うかという時間軸の設計を追加した点にある。モデルをブロックへ分けてディスクとメモリの間で入れ替えるSwapNetのような方式はメモリ上限を超える実行を可能にするが、テクスチャメモリ階層と演算子ごとの重ね合わせ耐性は扱わない。モバイルCPU向けにスライスと読み込みと計算の計画を行うFlexNNとも、対象がモバイルGPUとテクスチャ変換である点で異なる。先読み一般との差は、次に使うものや同種のものという局所規則ではなく、全層の容量と全重みの消費位置を同時に解く大域計画である点にあり、その差が最大4.3倍の遅延差として実測されている。

## 限界・実装状況

限界は、対象が先入れ先出し型の多モデル実行に限られ、プリエンプティブな割り込みは扱わないこと、実行経路が動的に変わるネットワークではソルバーの探索が膨らんで将来課題とされていること、畳み込み重みの変換は重ね合わせできず畳み込み主体モデルでは利得が痩せること、量子化モデルが評価から外れていること、同じモデルの連続実行では事前読み込み方式に劣る場面があることである。電力とメモリ削減の定量的な交換分析も今後の課題とされる。実装状況は、SmartMemを基盤にOR-ToolsのCP-SATソルバー、XGBoostの容量予測、Jinjaテンプレートによるカーネル生成を組み合わせた研究実装であり、公式コードの公開先は論文中に示されていない。ソルバーはオフライン実行で推論時間には含まれないが、モデルごとに最大150秒の制限で計画を作る前提がある。

## 一般的な実装上の含意

初期化が支配的な実行系では、初期化と推論を分けて最適化するより、一体の時間として設計し直す方が大きな利得が出る。また、データ移動と計算の重ね合わせは一律に最大化すべきものではなく、演算子ごとに重ねてよい量が桁違いに違うため、実測した耐性をスケジューリングの制約へ入れることが前提になる。融合のような局所最適化も、移動を挟める境界を消す副作用を持つため、全体計画の観点から割り戻せる仕組みとセットで使うべきである。
