# TurboTransformers: An Efficient GPU Serving System For Transformer Models

## 概要

TurboTransformersは、入力系列の長さが揃わないTransformer要求をGPUで低遅延・高スループットに処理するランタイムとサービング枠組みである。従来の固定長向けランタイムは入力長ごとの事前調整やゼロ埋めが必要で、学習フレームワークのキャッシュ型GPU割当器は一度使った大きな中間領域を保持し続けることがある。提案システムは、GEMM（行列積）間の演算融合とSoftmax・LayerNormの並列縮約、系列長を受け取ってから行う中間領域の再利用、実測コストを使う動的計画法による要求バッチ分割を組み合わせる。AMD Ryzen 7 3700XとRTX 2060で行ったBERTサービス実験では、要求長2〜100、最大バッチ20の条件で、安定処理の飽和点がPyTorch非バッチの99応答/秒から、Turboランタイムのみで237、単純バッチで323、提案スケジューラ付きで402応答/秒へ上昇した（6.3節、図15）。要求を短い順にまとめることで、長い要求とのゼロ埋めが減った結果である。一方、並べ替えにより長い要求が待つため、同じ入力条件では単純バッチの方が遅延が小さい場合がある。固定長ベンチマークではTurboはTensorRTに平均約13%遅く、長系列ほど最適化対象外の行列積が全体を支配する（6.2.3節、図14）。

## 問題設定

Transformerは系列全体を並列に処理するため、要求の入力長ごとに中間テンソルの形状が変わる。GPU実行で一般的なバッチ処理は、複数要求を一度に処理してGPUを使い切る助けになる一方、各要求をバッチ内の最長系列へゼロ埋めする。短い系列が混ざると不要な演算が増え、バッチを大きくする利益を打ち消すことがある（1節、2.1節、5節）。

演算面では、推論には逆伝播がないため、学習用フレームワークが保持する中間状態を省き、複数の軽い演算を一つのGPUカーネルにまとめられる。しかし小さな入力では、個々のカーネルを何度も起動する時間が実計算より長くなりうる。さらにSoftmaxやLayerNormの縮約演算は、同期や共有メモリの使用、命令間依存によってGPU並列性を活かしきれない（4.1節）。

メモリ面では、各演算の中間テンソルがいつ使われるかは計算グラフから分かるが、そのサイズは入力系列長で変わる。都度GPUメモリを確保・解放すれば管理処理が推論を止め、確保済み領域をキャッシュすればピーク使用後にメモリが残る。要求長を考慮しつつ、割当の速さと使用量を両立する必要がある（4.2節）。

## 手法のあらまし

システムは推論ランタイムとサービス枠からなる。モデルを読み込む際、ランタイムはTransformerの計算グラフから行列積以外の演算をまとめ、独自のCUDA実装へ置き換える。入力系列長が分かると、中間テンソルの使用開始・終了演算とサイズを調べ、同時に生存しないテンソルが同じメモリ位置を使うよう割当を計算する。サービス枠は到着要求を待ち行列に置き、要求長とバッチサイズごとの実測推論時間を参照して、ゼロ埋めを含む処理費用が小さくなるグループへ分割する。各グループは同じ系列長としてゼロ埋めされ、ランタイムへ渡される。推論結果は呼び出し元へ返る。頻出入力への応答キャッシュも構成要素に含むが、論文の主要評価では無効化されている（3〜5節、6.3節）。

## 手法

### 推論ランタイム: 演算の融合と並列縮約

推論用ランタイムは、前向き計算のグラフを演算子とテンソルの関係として保持し、行列積と次の行列積の間にある要素単位演算をまとめる。例えば活性化関数、バイアス加算、転置などを一つのカーネルへ融合する。中間値の書き戻し・再読込と起動回数が減るため、とくに演算量の小さな短系列で効果が見込める（4.1.1節）。

SoftmaxとLayerNormでは、複数の一次元配列の和・最大・平均・分散を求める縮約を並行して処理する。従来の方式が各ワープを順に縮約し、途中結果の共有メモリ書込と同期を繰り返すのに対し、TurboTransformersは複数ワープの縮約をまとめ、同期回数、境界要素の分岐、命令依存を減らす。LayerNormでは分散を `E(x²) − E(x)²` として計算し、値と二乗値を同時に縮約する。これにより従来式で必要な別々の縮約を減らす（4.1.2節、式1、図4〜5）。

### 系列長対応のメモリ割当

ランタイムは計算グラフ上で各中間テンソルが初めて使われる演算、最後に使われる演算、サイズを記録する。入力長が決まると、テンソルをサイズの大きい順に走査し、既存チャンクの中から、使用期間が重ならず必要サイズを収められる最小の空き位置を探す。使用期間が重ならない二つのテンソルには同じ位置を割り当てられるので、系列長が変わるたびに固定の最大形状を確保する必要がない（4.2節、アルゴリズム1）。

GPUメモリは例えば2MB単位のチャンクとして保持し、要求内で再利用する。適切な場所がなければ、既定サイズとテンソルサイズの1.2倍の大きい方で新規チャンクを追加する。使わないチャンクはその推論で解放する設定が基本で、一定回数アイドル後に解放する代替案も述べている。配置探索は最悪 `O(n²)` だが、同型の繰り返し層では一度求めた配置を再利用する。要求長200から240への変化例では、必要に応じて一つのチャンクを追加し、各テンソルの位置を更新する（4.2節、図6）。

### 系列長対応のバッチスケジューラ

サービス枠は待ち行列内の要求を系列長の昇順に並べ、どこで区切ると合計実行時間が最小になるかを動的計画法で求める。各系列長・バッチサイズの推論時間を表すコスト表は、対象GPUでの起動時ウォームアップ計測から作る。候補のバッチに含まれる全要求は最長系列に合わせて実行されるため、同じコストを個数分掛けた値を、その先頭までの最小費用へ加える。分割位置の選択と逆追跡で、処理するバッチ列を得る（5節、式2、アルゴリズム2）。要求数を `n` とすると探索の計算量は `O(n²)` である。

要求到着が多くGPUが常時稼働する場合は、ランタイムが空いた時点で即座にスケジュールする方式を使う。低負荷時は待ち時間と最大バッチ数のいずれかの上限に達してからまとめる方式がある。要求を長さ順に並べることで早着の長要求を遅らせる可能性があるため、キュー先頭の経過時間と現在バッチの予測実行時間が遅延制約の半分を超えそうなら、早めにスケジューラを動かす。複数サーバーでは上位の負荷分散器が各サーバーの過負荷を避ける前提である（5節）。

## 評価

### 結論

RTX 2060を用いた評価では、推論ランタイム単体は可変長入力のBERT等でPyTorchより高速になり、BERTの中間テンソル最大使用量は12.15MBだった。要求長2〜100のBERTサービスでは、可変長に応じて分割するスケジューラにより、単純バッチより最大安定処理量が増えた。反対に、固定長で事前調整されたTensorRTやFasterTransformersは平均速度で上回る。提案の中心的価値は、固定形状に最適化した単体カーネルの最高速ではなく、可変長サービスで性能とメモリ保持を両立する点にある。

可変長ランタイム比較は逐次的に異なる長さを実行するテストで、同時到着要求を扱うサービング評価とは別である。固定長ベンチマークも特定形状の事前調整を許すため、可変長性能の比較とは条件が異なる。短い系列では融合・起動削減が効くが、長い系列ではGEMMの比率が増え、非GEMM中心の最適化余地が相対的に小さくなる（6.2.1節、図10）。

### 品質と精度

基本TurboランタイムはFP32行列積で測定される。Turbo-TCはTensor Coreを利用し、論文はFP32版に対してわずかな許容可能な精度差があると記す一方、系列長5〜500のサービス実験では精度低下なしと報告する。モデルタスクの正解率や言語モデル品質を広範に比較する評価は掲載されていない（6.2.1節、6.3節）。

### 評価上の制約

- 全体性能測定の主な環境は単一RTX 2060であり、現代の大規模生成LLMや分散GPUサービングへ結果をそのまま一般化できない。
- 推論モデルはBERT系エンコーダと機械翻訳Seq2Seqデコーダで、評価は分類・変換を中心とする。自己回帰LLMの長時間デコードやKVキャッシュ管理は対象外。
- 合成・ランダム入力長を主に使い、長さ分布や到着分布が異なる実運用トラフィックの評価は限定的。バッチスケジューラのコスト表はGPU・モデル条件に依存し、全条件で測った場合のウォームアップに数十分かかると報告する。
- 固定長比較の一部システムには入力形状ごとの事前調整を認めている。可変長サービス方式と同一の運用条件ではない。
- 可変長サービスの動的計画法はスループットを優先し、長要求の遅延を悪化させることがある。サービス負荷がそのGPUでSLOを満たせる容量を超える場合は、キューが伸び続ける前提が崩れる。

## 既存研究との差

PyTorchなど学習由来のランタイムは柔軟な形状を扱えるが、非融合演算の起動やキャッシュ型メモリ管理の固定費を負う。TensorRT、TensorFlow-XLA、FasterTransformersなど固定長・事前調整型の実装は、高速化できる反面、形状ごとの調整やゼロ埋めを伴い可変長サービスに直接は適用しにくい。TurboTransformersは独自CUDAランタイムに加え、グラフ上のテンソル寿命から入力ごとのメモリ位置を決め、要求長ごとの実測コストからバッチ境界も決める点で、単一カーネルまたは単一実行形状の最適化からサービス全体へ範囲を広げる（2.2節、4〜6節）。

## 限界・実装状況

論文付録はランタイムをBSDライセンスで公開し、C++/CUDAとPython API、再現用スクリプトを提示する。記載された対応GPU世代はPascal、Volta、Turing。評価の主環境は2020年前後のソフトウェアとRTX 2060であるため、現在のフレームワークとの性能順位を示すものではない。動的計画法のコスト表を全系列長・バッチサイズで計測する場合は起動時ウォームアップが数十分かかり、系列長やモデルの変化にも追従する必要がある。現代の自己回帰LLMのKVキャッシュ割当・継続バッチングは論文のスコープ外である。

## 一般的な実装上の含意

可変長要求のバッチ効率は、最大バッチ数だけでなく、系列長分布、ゼロ埋めの無駄、短要求と長要求の遅延差で評価する必要がある。入力形状を見てからメモリを毎回新規確保する設計と、過去の最大値を保持し続ける設計の間には、グラフ上で寿命が重ならない領域を再利用する選択肢がある。また、長さ別・バッチ別の実測推論コストをスケジューラへ渡せば、ハードウェア上の理論計算量だけでは捉えにくい効率差も編成へ反映できる。ただし、コスト表の更新費用、長要求の待ち時間、実負荷に対するSLOを合わせて測る必要がある。
