# RSR-core：低ビット行列ベクトル積を実行カーネルへ落とし込む

## 概要

RSR-coreは、二値または三値の重み行列に繰り返し現れる列パターンをまとめる冗長セグメント削減（Redundant Segment Reduction; RSR）アルゴリズムを、CPUおよびGPUで直接実行できる形に実装した推論エンジンである。低ビット重みを持つ大規模言語モデルでは、生成トークンごとに同じ重み行列と異なる活性ベクトルとの行列ベクトル積が繰り返される。重みを単に1ビットや1.58ビットへ量子化するだけでなく、**重みの繰り返し構造を事前に整理して、推論時の加算とメモリアクセスを減らす**ことが主眼となる。

元のRSRアルゴリズムは数学的には演算を削減できても、Python上で集約・並べ替え・散布を行うと呼び出し費用や不規則メモリアクセスが支配的になりやすい。著者らは重み前処理を一度だけ実行し、実行時には専用のC/CUDAカーネルで入力ベクトルを集約して出力へ散布する構成を開発した。CPUでは集約と読み込みを融合し、CUDAでは64ビットに圧縮したグループ情報、共有メモリ上の部分和、コンパイル時に決めるブロック高さなどを使う。

論文の表1では、Falcon3-10B-1.58bのCPU生成がHugging Face/PyTorchのbfloat16経路の表示0.2トークン/秒に対して11.3トークン/秒（著者報告62倍）、CUDA生成が25.2から47.4トークン/秒（約1.9倍）となる。Llama3-8B-1.58bやBitNet-2B-4Tも比較対象に含まれる。CPUの非常に大きな倍率は低ビット専用実装とbfloat16標準経路の差を含むため、同条件で高度に最適化された別の三値カーネルすべてに対して62倍速いという意味ではない。

## 問題設定とアルゴリズムの位置づけ

行列ベクトル積`y=Mv`を考える。`M`は推論中に固定された重み、`v`は各生成ステップで更新される活性ベクトルである。通常は出力の各行について入力の全要素との積和を計算する。重みが二値`{0,1}`や三値`{-1,0,+1}`に量子化されている場合、積の値自体は単純だが、一般の密行列演算はその限られた値の組み合わせを十分に利用しない可能性がある。モデルの復号は行列ベクトル積を多数回呼ぶため、実装の微小な呼び出し費用や読み出し費用も積み重なる。

RSRは行列を`k`行ずつの水平ブロックへ分ける。各ブロックに含まれる列の短い重みパターンは、二値なら高々`2^k`種類であり、列数がそれより多ければ同じパターンが繰り返され得る。例えばあるブロックで複数列のパターンが一致していれば、それぞれの列に対して同じ重みパターンを別々に乗じる代わりに、対応する入力`v_j`を先に加算し、得られた和へパターンを一度適用できる。**重みの構造を再利用するため、入力ベクトルが変わっても前処理結果を使い回せる**ことがポイントである。

この方法は低ビット量子化の品質を改善する手法ではない。固定された量子化重みを与えた場合に、行列ベクトル積の計算結果を維持しつつ実行費用を下げる方式である。元の浮動小数点重みから二値・三値へ変換した時点で生じるモデル品質差はRSRの「正確な演算」という主張の対象外である。また浮動小数点の加算順序が変わると丸め差が生じ得るため、実装が完全なビット単位同一結果を保証するとまでは読み替えない。

## 手法

### 1. 重みの一度きりの前処理

前処理では行列`M`を`k`行のブロックに分割し、ブロック内の各列が持つ二値・三値パターンを符号化する。次に同一パターンを持つ列をグループ化し、列の並べ替え順序、グループの境界、計算結果を戻すための散布先を保存する。二値では`2^k`、三値の符号化では`4^k`のバケット空間を用いる計数ソート（counting sort）を採用し、比較ソートの`O(n log n)`ではなく`O(n+バケット数)`相当でグループ化する。

ブロック高さ`k`は重要な調整変数である。小さすぎると一度にまとめる行数が少なく、グループ管理の費用が大きい。大きすぎるとパターンの種類が指数的に増え、同じパターンの重複が減って前処理のバケット費用も増える。したがって最適な`k`は重みの形状、二値か三値か、CPU/GPUのメモリ構造で異なる。公式実装はCPU/GPU別の最良`k`を事前ベンチマークで求め、モデル前処理へ渡せるようにしている。

前処理成果は推論時の入力ベクトルに依存しないため、同じ重みを使う限り複数要求に再利用できる。論文は前処理成果の保存量を元のモデル以下に抑える設計と説明するが、事前処理時間やディスク占有量がゼロになるわけではない。モデルの重み更新やLoRAの統合で実効行列が変われば、以前のパターン構造をそのまま使えるか再検証が必要となる。

### 2. CPUカーネルでの入力集約と出力散布

オンライン推論では、前処理で作った同一パターンのグループごとに入力ベクトルの要素を集め、部分和を計算する。その部分和へグループの重みパターンを適用し、対応する出力行へ寄与を加える。著者らのC実装は、入力要素の読み込みと集約を一つの走査に融合し、Pythonからの中間配列生成を避ける。二値カーネルでは、ランダムな位置の値を集める際にベクトルギャザー命令を使うより、展開したスカラー読み込みと先読みヒントの組み合わせが有利だったと述べる。

三値では各グループが正の寄与を与える出力行と負の寄与を与える出力行を持つ。実装は長さの変わる散布先リストを作る代わりに、正負それぞれの固定長ビットマスクを持ち、立っているビットを走査する。グループ情報をコンパクトにすることで、入力集約後の不規則な出力更新を抑える。CPUでは異なる行ブロックを並列処理し、複数の線形層が同じ活性ベクトルを使う場合には呼び出しをまとめる。たとえば`W_q`、`W_k`、`W_v`のような兄弟層を一括実行し、活性量子化やPythonディスパッチを重複させない。

この「層間の一括実行」は単独の行列ベクトル積の演算削減とは別の最適化である。最終的な生成速度には、低ビットの行列演算、CPU並列化、呼び出し回数削減がすべて影響する。論文の大きなエンドツーエンド倍率をRSRの数学的な演算削減だけへ帰属してはいけない。

### 3. CUDAカーネルでのグループ処理

GPUでは一つの行ブロックをCUDAの一つのスレッドブロックに割り当て、その中のワープが異なるグループを並列処理する。各グループの位置、長さ、散布マスクを64ビットの語へ詰めるため、グループごとのメタデータ読み込みを少なくできる。前処理時にグループ内の入力インデックスを整列しておくことで、オンラインの読み出し局所性を改善する。重みがゼロ寄与しか持たないグループは前処理で除去する。

出力への更新が競合すると原子加算や同期が費用になるため、ワープごとの共有メモリ上に部分和を保持してから出力へ反映する。ブロック高さ`k`ごとにコンパイル時特殊化を行い、散布ループを展開して分岐を減らす。CPUとGPUのどちらでも、前処理の圧縮されたメタデータがオンラインのメモリ帯域を節約する一方、グループ化の粒度が悪い場合は追加の間接参照と同期費用が利得を食い得る。

### 4. モデル導入の流れ

公開コードでは、Hugging Faceから三値モデルを取得し、`integrations/hf/model_prep.py`で重みを前処理してローカルの再利用可能な成果を作る。`integrations/hf/model_infer.py`は前処理済みモデルを読み込み、`rsr`と`hf`の実行経路を切り替えて推論できる。PyTorch統合には通常の線形層を置き換える`RSRLinear`が用意され、カーネルとモデルの間に抽象化層を置く。公式コードはCPUのCコンパイラ・AVX2・OpenMP、GPU側ではCUDAとPyTorch拡張の構築環境を要求する。

前処理済みの重みを実行時に読み込む方式なので、実運用では初回の変換時間、成果の保存容量、対応するモデルの線形層形式、量子化重みの分布、CUDAの構築互換性が導入条件となる。論文の「既存推論パイプラインへ統合できる」という主張は、すべての未量子化モデルを自動的に同等精度のまま高速化するという意味ではない。

## 評価条件と主要結果

### 比較の意味

論文は二値行列とfloat32ベクトルの単体行列ベクトル積をCPU/CUDAで測り、別に三値（1.58ビット）言語モデルのトークン生成速度を測っている。単体演算の結果を、そのまま全モデルの生成速度に読み替えない。表1の生成比較では主にHugging Face/PyTorchのbfloat16経路が基準であり、BitNet専用経路との比較も別に示す。GPU機種、CPU型番、バッチ条件など、原著の本文で明示されない詳細については本解説で補わない。

|実行先|モデル|比較経路・トークン/秒|RSR・トークン/秒|原著の速度倍率|
|---|---|---:|---:|---:|
|CPU|Falcon3-10B-1.58b、HF bfloat16|0.2|11.3|62.0倍|
|CPU|Llama3-8B-1.58b、HF bfloat16|0.2|13.4|53.8倍|
|CPU|BitNet-2B-4T、HF bfloat16|2.1|28.8|13.9倍|
|CPU|BitNet-2B-4T、既存BitNet|14.2|29.3|2.1倍|
|CUDA|Falcon3-10B-1.58b、HF bfloat16|25.2|47.4|1.9倍|
|CUDA|Llama3-8B-1.58b、HF bfloat16|31.9|59.3|1.9倍|
|CUDA|BitNet-2B-4T、HF bfloat16|33.1|57.4|1.7倍|
|CUDA|BitNet-2B-4T、既存BitNet|41.6|57.1|1.4倍|

CPUでの大きな改善は、低ビット重みの規則性を利用するネイティブ実装と、bfloat16の通常行列積という実装差が大きい条件である。一方、すでに低ビット演算を利用するBitNetを基準にすると、CPUでは約2.1倍、CUDAでは約1.4倍となり、比較対象が重要であることが分かる。CUDAのFalcon3とLlama3では約1.9倍の生成速度となるが、CPUの「最大62倍」をGPUでも再現できるという意味ではない。

表のCPU Falcon3では表示値`11.3÷0.2=56.5`、Llama3では`13.4÷0.2=67.0`となり、原著の印字倍率62.0と53.8には一致しない。元の0.2トークン/秒が小数第1位へ丸められた表示である可能性があるため、**表の絶対値と原著の報告倍率を区別し、表示値だけから正確な比率を再現できるとは断定しない**。他の行も丸め誤差がある。論文の「exact computation」は量子化後の固定行列に対する演算上の正確性であり、元の高精度モデルと生成品質が同じという意味ではない。

### 単体演算と前処理の影響

論文の図2は二値重みの行列ベクトル積をCPU/CUDAで比較する。ここでは入力ベクトルをfloat32とし、重みのパターンをまとめるアルゴリズムそのものの効果を測る。著者らはPythonの処理をC/CUDAへ移したことに加え、計数ソート、16ビットの置換・境界情報、固定長ビットマスク、CPUでの融合、GPUでの共有メモリを性能上の要因として説明する。しかし、各最適化を個別に外したときの独立した倍率は本文の表1からは得られない。公開コードのベンチマークは`k`ごとの性能を測れるが、論文の結果を無条件に別のCPU/GPUへ移せるわけではない。

前処理は一度きりなので、長期間にわたって同じモデルを何度も推論する配信では費用を償却できる。逆にモデルを頻繁に交換する用途や短い単発実行では、前処理時間と成果ファイルの保存が相対的に重い。論文が示すトークン/秒は通常、前処理を終えた推論経路の測定であり、ダウンロード・変換・コンパイル・初回ロードまで含む総所要時間とは区別する必要がある。

## 既存研究との差

RSRの先行研究は、低ビット行列に存在する繰り返しパターンを用いて演算を削減する理論・アルゴリズムを与えていた。RSR-coreの新規性は、その演算順序をCPUとCUDAのカーネルに移し、データ配置とメタデータを圧縮し、モデル導入・ベンチマークまで接続したことにある。一般的な重み量子化手法のようにビット幅を選んでモデルを圧縮するだけではなく、**同じ量子化済み行列をどう実行するか**を最適化する。

低ビット言語モデルの実用性を論じる際には、元の高精度モデルからどれだけ品質を失うかと、量子化後のモデルをどれだけ速く動かせるかを分ける必要がある。本論文が強く裏付けるのは後者である。さらに、CPUの巨大な改善倍率は比較する基準実装に依存するため、推論基盤を選ぶ際には既存の低ビット専用カーネルを基準にした値を重視する方が適切である。

## 限界と適用条件

第一に、RSRが利用するのは二値・三値行列の短い列パターンの重複である。通常の任意精度浮動小数点重みには同じ形で適用できず、重みの量子化・変換と、そのモデル品質の評価が別途必要となる。第二に、ブロック高さ`k`とグループの重複度で利得が変わる。入力次元、行数、GPU世代、CPUキャッシュ構造によって最適な前処理が異なる。第三に、前処理成果の保存と読み込みが必要で、頻繁に更新される重みには追加の運用負担がある。

第四に、評価表の主な比較対象はPyTorchのbfloat16経路であり、あらゆる最新低ビット専用カーネルとの包括比較ではない。第五に、生成速度の表は代表的な三値モデルでの測定であり、一般のMoE、長文脈KVキャッシュ制約、分散配信、複数要求同時実行時の遅延・処理量について同じ倍率を保証しない。第六に、原著のCPU表には丸めた絶対値と印字倍率の不整合があり、正確な倍率再現には元の未丸め測定値が必要である。

公式コードは再現可能性を高めるが、インストールにコンパイラやCUDA環境が必要であり、すべてのGPU・モデル版で同じ性能になるとは限らない。CPU/GPUの選択、最良`k`の事前探索、モデル前処理、通常経路との比較条件を記録して初めて適切な性能比較ができる。
