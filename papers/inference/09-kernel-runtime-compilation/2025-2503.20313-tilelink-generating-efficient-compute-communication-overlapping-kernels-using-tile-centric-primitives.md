# TileLink: Generating Efficient Compute-Communication Overlapping Kernels using Tile-Centric Primitives

> タイル中心プリミティブから計算・通信融合カーネルを生成し、8×H800で非重畳比1.17〜20.76倍、8モデルのエンドツーエンドでPyTorch比平均1.32倍を達成する。

## 概要

テンソル並列や系列並列では、AllGather、ReduceScatter、All-to-Allなどの集合通信とGEMM・注意計算が同じ層の中で交互に現れる。通信を隠すには両者を重ねて実行したいが、演算子を小さく分割して複数ストリームへ流す方式はホスト同期や小粒度GEMMの効率低下を招き、通信・計算を一つのGPUカーネルへ融合する方式は高性能な反面、CUDA・バリア・通信命令を手作業で扱う必要がある。

TileLinkは、通信側と計算側が異なるタイル形状・最適化を選べるよう設計空間を分離し、両者の接続だけをタイル中心プリミティブで記述する。後段はタイルIDをデータ形状、ランク、通信チャネルへ写像し、プリミティブを低水準のデータ転送命令・同期・計算へ下げる。これにより、手書き融合カーネルに近い細粒度重畳をコンパイルで生成する。

8×H800ではMLP、専門家混合（Mixture of Experts; MoE）、系列並列注意を対象に、非重畳基準より1.17〜20.76倍の高速化を報告する。8種類のLLMをPyTorchへ統合したエンドツーエンド評価では、8×H800で平均1.32倍、2ノード16×H800で平均1.29倍となった。

## 問題設定

演算子分割方式では、AllGatherとGEMMなどを細かい断片へ割り、依存しない断片を別ストリームで並行させる。しかし断片が小さくなるとGPUの演算器を埋めにくくなり、L2キャッシュ局所性も悪化する。さらに断片間同期をホストが仲介すると、重畳で隠したい通信時間とは別の制御オーバーヘッドが増える。

融合方式は通信担当の直接メモリアクセス（Direct Memory Access; DMA）エンジンやストリーミングマルチプロセッサ（Streaming Multiprocessor; SM）と、計算担当SMを同じカーネル内で協調させるため高効率である。しかし、通信と計算が異なるタイル幅を持つ場合の生産者・消費者依存、GPU間ランク、通信チャネル、オンデバイスバリアを手作業で正しく対応させる必要がある。TileLinkが解くのは、性能を保ちながらこの低水準実装負担をコンパイラへ移すことである。

## 手法

### 前段: 計算・通信の設計空間分離

TileLinkの前段では、GEMMやFlashAttentionなどの計算と、AllGather・ReduceScatterなどの通信をそれぞれ独立にタイル化できる。通信タイルと計算タイルを同じ寸法へ強制しないため、各演算が単体で効率の良い粒度を選べる。

両者の依存はタイル中心プリミティブで表す。プリミティブは「どのタイルのデータを送り、どのタイルが到着を待つか」を抽象化し、ポインタ計算、ランク間データ移動、バリア操作などをアプリケーション側から隠す。これが、約数千行のCUDAを要する手書き融合方式に対し、数百行規模のPythonで同種のカーネルを記述できる理由である。

### 後段: タイル写像と低水準命令生成

後段コンパイラはタイルIDから、対象テンソルの範囲を決める形状写像、送受信相手を決めるランク写像、実際の通信路を決めるチャネル写像を構成する。規則的な場合はコンパイル時のアフィン変換として静的に決め、MoEのように実行時ルーティングで通信相手が変わる場合は動的写像を使う。

この写像に基づき、タイルプリミティブをDMA転送、SM上の削減、デバイス内バリアなどへ下げ、計算命令と同じGPUカーネルへ統合する。例えばMLPのAllGather+GEMMではAllGatherをDMAへ割り当て、GEMM+ReduceScatterではscatterをDMA、reductionをSMへ割り当てる混成写像を用いる。通信と計算で別ハードウェア資源を使うことで、データ依存を守ったまま重なる区間を増やす。

### MLP・MoE・注意への適用

テンソル並列MLPでは、前半のAllGather+GEMMと後半のGEMM+ReduceScatterをそれぞれ重畳する。MoEではAllGather、token gather、GroupGEMM、scatter、Top-k reduction、ReduceScatterまでの長い生産者・消費者鎖を同じプリミティブで記述し、動的写像によって専門家ルーティングへ追従する。

系列並列の自己注意では、FlashAttention計算とAllGatherを重ねる。入力長16k〜128kで、通信だけを別途待つ時間の一部を注意計算の背後へ隠す。つまりTileLinkは一種類のGEMM融合器ではなく、通信パターンと計算タイルの接続を共通抽象化した生成基盤として設計されている。

## 評価

### 代表的な評価条件

| 項目 | 条件 |
| --- | --- |
| ハードウェア | 主評価は8×NVIDIA H800、マルチノードは2ノード計16×H800 |
| 単層ワークロード | テンソル並列MLP、MoE、系列並列自己注意 |
| 比較対象 | cuBLAS+NCCL、Async-TP PyTorch、FLUX、vLLM演算子、RingAttention、非重畳PyTorch |
| 注意の系列長 | 16k、32k、64k、128k |
| エンドツーエンド | GPT-3、LLaMA2、Mixtral、Qwen1.5を含む8モデル |
| 8GPU E2E条件 | バッチ4、系列長8192 |
| 16GPU E2E条件 | 2ノード、ノード内テンソル並列・ノード間データ並列、バッチを倍増 |

### 代表的な評価結果

| 条件 | 指標 | 比較対象 | TileLink | 改善・差 | 読み取れること |
| --- | --- | --- | --- | --- | --- |
| 8×H800、MLP前半 | AllGather+GEMM速度 | cuBLAS+NCCL / FLUX | 1.27倍 / FLUX性能の94.5% | FLUXに近い | 高水準記述でも手書き融合へ接近 |
| 8×H800、MLP後半 | GEMM+ReduceScatter速度 | cuBLAS+NCCL / FLUX | 1.25倍 / FLUX比1.28倍 | 手書き方式を上回る条件あり | 計算・通信の独立最適化が有効 |
| 8×H800、MoE | 全MoE層 | vLLM | 平均1.14倍 | 最大は非重畳比20.76倍 | 動的写像が複雑なMoE通信にも適用可能 |
| 8×H800、注意16k〜128k | 注意速度 | PyTorch / RingAttention | 平均5.04倍 / 1.97倍 | 通信の43.9%を平均で隠蔽 | 長文系列で重畳効果を内部指標でも確認 |
| 8モデル、8×H800 | E2E実行時間 | PyTorch | 平均1.32倍 | Dense平均1.20倍、MoE平均1.54倍 | 単層利得の一部がモデル全体へ残る |
| 8モデル、16×H800 | E2E実行時間 | PyTorch | 平均1.29倍 | 8GPUよりやや低下 | ノード間通信が追加されると利得が縮む |

単層の最大20.76倍はMoEの特定条件における非重畳基準との比較であり、モデル全体が20倍になることを意味しない。実際、8モデルのエンドツーエンド平均は1.32倍である。新ガイドで区別すべき「カーネル単体」と「エンドツーエンド」の差が明確に現れる評価である。

また、自己注意では平均43.9%の通信時間を隠せたという内部指標があり、単に高速化しただけでなく、TileLinkが狙う計算・通信重畳が実際に起きていることを裏付ける。16GPUで1.29倍へ少し低下する結果は、ノード間通信の追加分まで完全には隠せない境界条件を示す。

## 既存研究との差

Async-TP PyTorchやCentauriのような演算子分割系は開発しやすい一方、小カーネル化とホスト同期の費用を抱える。FLUXやCoCoNetのような融合系は高性能だが、通信命令や同期を含むカーネルを低水準で個別実装する必要がある。

TileLinkは「コンパイルで融合する」点に加え、計算タイルと通信タイルを同じ形へ縛らず、タイル中心プリミティブを介して接続する点が差になる。これにより、MLPだけでなくMoEの動的通信やFlashAttentionまで同じ抽象化で扱い、FLUX・RingAttentionと同程度または一部条件で上回る性能を狙う。

## 限界・実装状況

現行実装の後段はNVIDIA GPUを対象としており、AMD GPUやNPUなど別アクセラレータへは低水準コンパイラと通信命令の対応が必要である。論文自身も複数バックエンド対応を将来課題としている。

また評価対象は主に層内並列の通信重畳であり、パイプライン並列のようなモデルレベル通信は実装範囲外である。16GPU評価で8GPUより平均利得が下がることからも、ノード境界の帯域・遅延が支配的になる構成では、タイル内重畳だけで全通信を隠せるわけではない。
