# FastTree: Optimizing Attention Kernel and Runtime for Tree-Structured LLM Inference

> プレフィックス共有のある推論で、共有KVの読み直しとテンソルコアの無駄を解くため、共有文脈を持つクエリをまとめて計算するアテンションカーネルと、木の分割を実行時に最適化する仕組みをSGLangへ追加した。スループットは最大2.2倍になった。

## 概要

近年のLLMの使い方は、単独の質問に答えるだけのものから、プログラムの中で多数のクエリを発行するものへ広がっている。few-shot学習、思考の木のような探索、複数の文書への質問応答などでは、異なるクエリ同士が共通のトークンのプレフィックス（接頭辞）を共有する。異なるプログラムの間でも、長いシステムプロンプトのような共通部分が共有される。こうした「木構造のプレフィックス共有」を持つ推論を、論文は木構造LLM推論と呼ぶ。

メモリの面では、基数木（radix tree）でシステム全体のKVキャッシュを組織し、共有部分を再利用する最適化が既に存在し、GPUメモリの使用量を大きく減らしてきた。しかし計算の面では、従来のアテンションカーネルはクエリごとにKVキャッシュを連結し、個別のスレッドブロックへ割り当てるという従来のパターンのままである。この素朴な分離には2つの無駄がある。第一に、共有されているKVキャッシュを、クエリの数だけ遅いグローバルメモリから読み直すことになる。第二に、クエリ単独の形ではテンソルコアの最小形状の要件を満たせず、埋め草（パディング）なしでは高性能な演算器を使えないことである。共有メモリの使い方も非効率になる。

FastTreeは、木構造のKVキャッシュをメモリ配置だけでなく計算の指針として使い、共有文脈を持つクエリ群をまとめて処理するアテンションカーネルを導入する。共有KVは一度だけ読み込まれて高速な共有メモリに乗り、複数のクエリがそれを使い回すため、メモリ取引が減り、テンソルコアの利用も進む。あわせて、与えられたKVキャッシュの木に対して、どのクエリ同士をグループにするかを実行時に決める最適化を備える。

**代表結果:** SGLangの上に構築され、エンドツーエンドのスループットをSGLangと比べて最大2.2倍に改善した。カーネル単体の比較では、既存のアテンションカーネルに対して最大で10倍を超える高速化の条件もあった。

## 問題設定

対象は、プレフィックス共有のあるLLM推論、特にデコード段階のアテンション計算を高速化する問題である。前提として、KVキャッシュは基数木で管理され、共有はメモリ上では実現しているものとする。解くべきは計算のパターンである。

難しさは2層ある。カーネルの層では、共有部分を一度だけ読み、複数のクエリで使い回しながら、テンソルコアの形状要件を満たすタイル構成にする必要がある。実行時の層では、グループ化の決め方が難しい。クエリ間で共有されるプレフィックスの長さはまちまちであり、どの範囲を1つのグループとしてまとめるかで、読み込みの削減量とタイルの効率が変わる。決定の空間は巨大であり、最適な分割を厳密に求めることは現実的でない。さらに、非常に長い文脈がグループの中に混ざると、そのグループ全体の処理が長文脈に引きずられるテール効果（末尾の遅い処理が全体を律速すること）が起きる。

## 手法のあらまし

FastTreeは、カーネルと実行時の2層で構成される。カーネルの層では、共有文脈とそれに連なるクエリ群をまとめて処理するアテンションカーネルを用意し、共有KVを共有メモリへ一度だけ載せてテンソルコアで計算する。実行時の層では、木構造へ適応する最適化として、貪欲なヒューリスティクスで木を分割し、オーバーヘッドが最小になる文脈とクエリのグループを作る。長い文脈は分割して、テール効果を緩和する。システムはSGLangの上に構築され、デコードのアテンションを最適化の対象とし、プリフィルには既存の高速カーネルを使う。以下、各層を説明する。

## 手法

### 1. 木構造に合わせたアテンションカーネル

従来の計算パターンでは、各クエリは自分の文脈（共有部分＋固有部分）を連結したものを入力とし、個別にアテンションを計算する。共有部分はクエリごとに重複してグローバルメモリから読まれる。FastTreeのカーネルは、基数木のノードに対応する文脈と、それを共有するクエリの集合をまとめて受け取り、共有KVを共有メモリへ一度だけ読み込む。複数のクエリのクエリベクトルが同じKVタイルに対して計算されるため、読み込みの回数が減るだけでなく、行列としての形が大きくなり、テンソルコアの形状要件を満たして高い演算効率が得られる。グループ化されたクエリは、文脈の長さや木の形に応じて異なるタイルサイズのフェーズへ分けて処理される。

### 2. 木構造へ適応する実行時最適化（グループ化の計画）

どのクエリ同士をグループにするかは、木の形によって最適が変わる。FastTreeは、貪欲なヒューリスティクスで木を分割し、文脈とクエリのグループ（グループ化計画）を決める。貪欲な選択は、共有による読み込み削減の利益と、グループ化に伴うオーバーヘッドの釣り合いを局所的に評価しながら進む。評価では、この貪欲な最適化によって最大で1.9倍の追加の高速化が得られた条件があり、木の形に応じてノードを連結したり分けたりする判断が効いていることが示された。たとえば、ある構成では、木の下位のノードを連結して大きなグループを作る方針が選ばれている。

### 3. 長い文脈の分割によるテール効果の緩和

グループの中に極端に長い文脈が含まれると、その処理時間がグループ全体を支配し、他のクエリの完了を遅らせる。FastTreeは長い文脈を分割して処理することで、このテール効果を緩和する。文脈の分割はグループ化計画と組み合わせて行われ、長さのばらつきが大きい木でも、全体の処理時間が一部の長文脈に引きずられにくくなる。

## 評価

評価はNVIDIA H100（80GB、CUDA 12.2）で行われた。カーネルはTritonで実装され、SGLangのプラグインとして組み込まれている。Hopper固有の機能（TMAなど）は使われておらず、今後の最適化の余地として残されている。評価は、カーネル単体のベンチマークと、エンドツーエンドのスループットの2層である。

カーネル単体では、木の形を変えた合成的な条件（各レベルのノード数と文脈長を変える）でアテンション計算を測り、代表的なアテンションカーネル群と比較した。FastTreeは各比較対象を上回り、条件によっては10.6倍や2.1倍といった高速化が報告されている。グループ化クエリ注意（GQA）の比率が低い条件ほど、既存カーネルに対する優位が大きい。これは、GQA自体が複数のクエリヘッドを1つのKVヘッドへ集約することで、共有メモリの無駄とテンソルコアの低利用を部分的に緩和しているためである。ただしGQA比率が16という高い条件でも、FastTreeはより大きなタイルでより多くのクエリを集約してKVを再利用できるため、既存カーネルを上回った。木構造の最適化を行う他の方式（2種）との比較でも、貪欲な最適化なしの構成ですらFastTreeが上回り、カーネルと実行時の両面の最適化の積み重ねが効いている。

エンドツーエンドでは、Llama-2-7BとMistral-7Bを対象に、3,193トークンのシステムプロンプトを共有する4種類のベンチマーク（多層のシステムプロンプト、複数のfew-shot学習、多重の推論チェーン、多文書の質問応答）を実行し、共通プレフィックスを持つリクエストのバッチについてスループットを測った。結果として、SGLang（Tritonカーネル）に対して平均で2.3倍と1.9倍、高速なバックエンドを持つSGLangに対しても1.6倍と1.9倍の高速化が得られ、全体の最大は2.2倍と集計されている。実行時間の内訳を見ると、デコードの占める割合が大きいワークロードほど改善が効いており、最適化対象をデコードに絞った設計と整合している。

この結果の読み方として、共有の恩恵が二重に出ている点が重要である。共有プレフィックスが長いベンチマークでは、読み直しの削減そのものが大きくなるだけでなく、グループとしてまとめられるクエリの数が増えるため、タイルが大きくなってテンソルコアの効率も上がる。逆に、共有が浅く木が細かく枝分かれする条件では、グループ化の利益が減り、実行時の計画の良し悪しが結果を左右する。貪欲な最適化の寄与が条件によって最大1.9倍にも達したことは、固定のグループ化規則では拾えない利益が、木の形に適応することで得られている証拠である。モデル側の集約であるGQAとの関係も示唆的で、GQA比率が上がると既存カーネル側の無駄が減って差は縮むものの、大きなタイルによる再利用の利益は残るため、FastTreeの優位は消えなかった。

## 既存研究との差

基数木によるKVキャッシュの共有は、メモリ使用量の削減としては確立していたが、計算はクエリごとの従来パターンのままだった。FastTreeは、共有の構造を計算の指針として使うことで、読み込みの冗長性とテンソルコアの低利用を同時に解いた点が異なる。木構造の最適化を行う他の方式と比較しても、カーネルの設計（フェーズごとのタイルサイズの使い分けなど）と実行時のグループ化計画の両面で最適化を積み重ねており、貪欲な探索なしでもそれらを上回る。GQAのようなモデル側の集約とは直交する最適化であり、GQA比率が高いモデルでも利得が残ることが示されている。

## 限界・実装状況

最適化の対象はデコード段階のアテンションに限られ、プリフィルや、プリフィルとデコードの混在に対する最適化は、原理的な障害はないものの工学的な作業として残されている。プリフィルは冗長なKV読み込みやテンソルコアの低利用に悩まされにくいため、利得は限られると論文は見ている。また、実装はHopper固有の機能を使っておらず、ハイパーパラメータはH100向けに調整されているため、他のGPUでは再調整が必要である。利得の大きさは、プレフィックス共有の量と木の形に依存し、共有の少ないワークロードでは効果が薄い。コードは成果物として公開されている。

## 一般的な実装上の含意

キャッシュの共有は、メモリを節約するだけでは不十分であり、計算のパターンが共有の構造に追随しなければ、読み込みの冗長性として利得が漏れる。データの持ち方と計算の仕方を同じ構造（ここでは木）でそろえることが、共有の効果を性能へ変換する条件である。これは、プレフィックスキャッシュを持つサービングシステム全般に当てはまる。

また、グループ化のような実行時の判断は、入力の形（木の形）によって最適が変わるため、固定の規則ではなく、費用と利益を見積もる軽い探索で決めることが有効である。長い文脈の分割によるテール効果の緩和は、長さのばらつきが大きいバッチ処理全般に応用できる考え方である。
