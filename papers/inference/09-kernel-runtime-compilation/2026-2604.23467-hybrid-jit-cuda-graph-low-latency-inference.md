# Hybrid JIT-CUDA Graph Optimization for Low-Latency Large Language Model Inference

> 静的Transformer演算をCUDA Graph再生、動的制御を実行時コンパイルへ分け、短系列・バッチ1推論の起動オーバーヘッドと尾部遅延を削減する。
## 書誌情報
- **著者**: Divakar Kumar Yadav, Tian Zhao
- **公開**: arXiv:2604.23467v1
- **種別**: arXivプレプリント
- **対象**: CUDA Graph、実行時コンパイル、低遅延推論
- **実装**: PyTorch 2.3、CUDA 12.4、FlashAttention v2、nvFuser LayerNorm、vLLM由来paged KV カーネルを静的グラフへ組み込み、動的サンプリングを実行時コンパイル側へ分離する研究実装。
## 概要
対話型の短系列LLM推論では、演算そのものだけでなく反復するGPUカーネル起動とホスト制御が初回トークン・尾部遅延を押し上げる。本論文はTransformer実行を静的部分と動的部分へ分け、静的演算をCUDA Graphで捕捉・再生し、可変長処理やサンプリングを実行時コンパイルへ残す二経路ランタイムを提案する。NVIDIA H100上のLLaMA-2 7B、FP16、バッチ1、10〜500トークンでTensorRT-LLM等と比較し、初回トークン時間を最大66%削減し、P99デコード遅延も平均20.2%低減した。

提案ランタイムはTransformer推論を静的・反復可能な演算と、shape・制御が実行時に変わる演算へ明示的に分割し、前者をCUDA Graph捕捉・再生、後者を実行時コンパイル済みカーネルで処理する。さらにグラフ捕捉を別ストリーム・別処理系で非同期化してデコードと重ね、必要なグラフを再利用することで、CUDA Graphの低起動費と実行時コンパイルの柔軟性を同時に利用する。

代表結果として、TTFT at 500-トークン promptはH100, LLaMA-2 7B, FP16, バッチ=1でTensorRT-LLM 88 ms; HuggingFace 48.96 msに対して17.79 ms。長めの評価promptでも個別dispatchとランタイム graph managementの費用を抑え、対話型初動遅延を大幅に短縮する。
## 問題設定
自己回帰LLMでは各トークン生成で多数の小さなGPUカーネルを繰り返し起動するため、短い対話要求やバッチ1では演算時間に対するホスト側dispatch、同期、カーネル起動の比率が大きくなる。CUDA Graphは一連のGPU処理を捕捉して低オーバーヘッドで再生できるが、固定shapeと決定的制御を要求するため、可変長attention、KV更新、確率的samplingなど動的なデコード処理を全面的にグラフ化しにくい。一方、実行時コンパイルだけでは動的性を扱えるが、個々のカーネル起動とPython制御の変動が残る。
## 新規性
提案ランタイムはTransformer推論を静的・反復可能な演算と、shape・制御が実行時に変わる演算へ明示的に分割し、前者をCUDA Graph捕捉・再生、後者を実行時コンパイル済みカーネルで処理する。さらにグラフ捕捉を別ストリーム・別処理系で非同期化してデコードと重ね、必要なグラフを再利用することで、CUDA Graphの低起動費と実行時コンパイルの柔軟性を同時に利用する。
## 手法
### 手法のあらまし
ランタイムは推論処理を二つの協調経路へ分ける。動的文脈生成側は前処理、可変長の制御、サンプリングなど入力や生成状態に依存して形や分岐が変わる処理を実行時コンパイルで扱い、静的グラフ生成側はTransformerの反復可能な演算列をCUDA Graphとして捕捉する。静的側にはFlashAttention v2、nvFuserによるLayerNorm、vLLM由来のpaged KVキャッシュ・カーネルなどを組み込み、捕捉後は個別カーネルをホストから毎回dispatchせず一括再生する。二経路はプロセス間通信とCUDAイベントで依存を同期し、グラフ捕捉・再生成を別ストリームで非同期実行することで、次に必要なグラフ準備が前景デコードを停止しないようにする。動的サンプリングはグラフへ固定せず実行時コンパイル側へ残すため、デコードの柔軟性を維持する。入力長や状態に応じて再利用可能な静的グラフを選び、動的部分だけを都度処理することで、完全なeager実行の起動費と、完全グラフ化の静的制約の中間を狙う。評価では非同期グラフ再生成を無効化すると初回トークン時間が17.5%悪化し、動的処理の実行時コンパイルを外してPythonへ戻すとトークン当たり遅延が28%増えるため、二経路の重なりと役割分担が相補的に効く。

### 静的・動的演算の分割
Transformer実行を一律に最適化せず、shapeと制御が安定して反復するattention・正規化・KV関連の静的演算と、入力長、生成状態、samplingに依存する動的演算へ分類する。静的側だけをCUDA Graphへ載せることで、固定shape・決定的制御というグラフの制約を満たしやすくし、動的側は実行時コンパイルへ残して機能上の柔軟性を維持する。この境界設定により、全処理をeager実行して起動費を払い続ける方式と、全処理をグラフ化して動的性を失う方式の両方を避ける。

### CUDA Graph捕捉・再生
FlashAttention v2、nvFuser LayerNorm、paged KVキャッシュなど反復可能なGPU演算列を一度捕捉し、以後はCUDA Graphを再生して複数のカーネル起動を一括投入する。ホスト側が各カーネルを個別dispatchする回数を減らすため、演算量が小さく起動費の比率が高いバッチ1・短系列で特に効果が出る。H100上の10〜500トークン評価ではTensorRT-LLMに対する初回トークン時間が最大66%短縮され、長めの500トークンでも17.79ms対88msという差が報告される。

### 動的処理の実行時コンパイル
サンプリングや可変状態処理を静的グラフへ無理に固定せず、実行時コンパイル済みカーネルとして処理する。これによりトークンごとに変わる制御やshapeを許容しながら、Python eagerへ全面的に戻るよりdispatch費を抑える。アブレーションでこの経路を外して動的処理をPython実行へ戻すとトークン当たり遅延が28%増えており、CUDA Graphだけでは吸収できない動的部分の低オーバーヘッド化に必要である。静的経路と分離することで、動的処理がグラフ再生の決定性を壊すことも防ぐ。

### 非同期グラフ生成と協調同期
グラフ捕捉や再生成を前景のデコードと同じ同期経路で行うと、捕捉そのものが待ち時間になり低遅延化の利点を削る。そこで静的グラフ生成を別処理系・別CUDAストリームへ置き、動的文脈生成側とプロセス間通信で必要情報を渡し、CUDAイベントで実行依存だけを同期する。利用可能なグラフは再利用し、再捕捉が必要な場合も可能な範囲でデコードと重ねる。非同期再生成を無効化したアブレーションでは初回トークン時間が17.5%増えるため、単なるCUDA Graph採用ではなく捕捉をクリティカルパスから外すことが重要である。

### 全体のデータ／制御の流れ
動的処理を担当する実行時コンパイル文脈生成プロセス、静的演算を捕捉・再生するCUDA Graph生成プロセス、両者を結ぶプロセス間通信、CUDAイベント同期、非同期捕捉ストリーム、グラフ再利用キャッシュから構成される。
## 評価条件
- **ハードウェア**: NVIDIA H100 GPU
- **ソフトウェア**: PyTorch 2.3、CUDA 12.4、TensorRT-LLM 1.0、FlashAttention v2、nvFuser、vLLM paged KV カーネル、Nsight Systems
- **比較対象**: HuggingFace Transformers / PyTorch Eager、TensorRT-LLM 1.0
全方式をH100・FP16・バッチ 1で揃え、warm-start後に1000 inference iterationsをCUDA EventsとNsight Systemsで計測する。TTFT表では10〜500トークンの各点を比較し、P99表では生成長ごとの尾部遅延を比較する。さらに非同期graph regenerationを外した場合と、動的処理のJITを外してPythonへ戻した場合を個別に測り、二機構の寄与を分離する。
単一H100、LLaMA-2 7B、FP16、バッチ=1、10〜500トークンという対話型短〜中系列に限定された評価であり、高バッチ、複数GPU、他モデル、量子化、長文コンテキストへの一般化は未検証である。
## 主要結果
H100・LLaMA-2 7B・FP16・バッチ 1の短〜中系列条件で、ハイブリッド方式は全ての測定prompt長で低い初回トークン時間を示した。10トークンでは13.36ms、100トークンでは11.09ms、500トークンでも17.79msで、TensorRT-LLMの16ms、28ms、88msを下回る。論文はTensorRT-LLM比で初回トークン時間を最大66.0%削減したと要約する。P99トークン当たり遅延は1000試行平均でTensorRT-LLMより20.2%、PyTorch Eagerより43.5%低減した。非同期グラフ再生成を無効にすると初回トークン時間が17.5%増え、動的処理の実行時コンパイルを外すとトークン当たり遅延が28%増えるため、静的グラフ再生だけではなく、捕捉の非同期化と動的経路の低オーバーヘッド化の双方が効いている。

- TTFT at 500-トークン prompt / 17.79 ms (比較対象: TensorRT-LLM 88 ms; HuggingFace 48.96 ms; 条件: H100, LLaMA-2 7B, FP16, バッチ=1) — 長めの評価promptでも個別dispatchとランタイム graph managementの費用を抑え、対話型初動遅延を大幅に短縮する。

- maximum TTFT reduction / up to 66.0% (比較対象: TensorRT-LLM; 条件: prompt lengths 10-500) — 静的演算をグラフ再生へまとめる効果が、起動オーバーヘッドの比率が高い単一要求で顕著に現れる。

- P99 トークン 遅延 / average -20.2% vs TensorRT-LLM; -43.5% vs PyTorch Eager (比較対象: TensorRT-LLM / PyTorch Eager; 条件: 1000 trials, generation lengths 10-500) — 平均値だけでなく尾部のdispatch変動も抑え、応答のジッタ低減に寄与する。

- ablation / no async graph regeneration: TTFT +17.5%; no JIT 動的 path: トークン 遅延 +28% (比較対象: full hybrid ランタイム; 条件: 構成要素 ablation) — CUDA GraphとJITを単に併置するだけでなく、非同期捕捉と動的経路の分離が相補的に必要である。

### 負の結果・境界条件
- P99表では生成長が長くなるとハイブリッド方式のトークン当たり遅延も増え、500トークンでは23.68msとなりTensorRT-LLMの16.65msを上回る個別点がある。論文の平均P99改善は全長平均での結果であり、長生成の全点で優位ではない。
- 評価は単一H100・バッチ 1・LLaMA-2 7Bに限定され、高スループットバッチや複数GPUでの効果は示されていない。

### 結果の読み方
この結果は、低遅延推論では全演算を一つのコンパイル方式へ寄せるより、静的性の高い部分だけをCUDA Graphへ固定し、変動部分をJITへ残す方が有効な領域があることを示す。特にバッチ 1の対話型処理ではGPU計算以外の起動・同期費が相対的に大きいため、非同期captureで準備費をクリティカルパスから外すことがTTFTとジッタを改善する。ただし長い生成ではP99の個別点が逆転するため、適用範囲は短〜中系列の遅延重視ワークロードとして解釈すべきである。
## 品質への影響
重み、注意値、KV内容を近似せず実行スケジュールとdispatch方式を変えるため、モデル出力品質を犠牲にする最適化ではない。主な交換条件はグラフ管理複雑性、shape適合性、長生成時の動的経路費である。
## 既存研究との差
TensorRT-LLMのような高度に最適化された推論基盤に対し、短系列・バッチ 1で残るgraph managementやdispatchの尾部費用を対象にする。TorchDynamo/TorchInductorが演算融合・コンパイルを中心にするのに対し、提案方式は静的サブグラフをCUDA Graphへ明示的に固定し、動的制御だけをJIT経路へ分離する。persistent カーネル系がカーネル内部へ処理を集約するのとは異なり、既存カーネル群の捕捉・再生を主手段にする。
## 限界
- LLaMA-2 7B、単一H100、FP16、バッチ 1のみであり、現代の大規模モデルや高バッチサービングへの一般化は不明である。
- 500トークン生成のP99ではハイブリッド23.68msがTensorRT-LLM 16.65msを上回り、長生成の全点で優位ではない。
- CUDA Graphの再利用効率はshape・制御の安定性に依存し、動的性が高いワークロードでは捕捉・再生成費が増える。
- スループット、GPUメモリ消費、複数同時要求の公平性は主要評価指標ではない。
## 実装状態
PyTorch 2.3 / CUDA 12.4上で二プロセス協調、CUDA Graph、JIT、FlashAttention v2、nvFuser、paged KV カーネルを統合した研究実装。公式コードURLは確認できなかった。
## 研究上の位置づけ
カーネル起動費が支配的な対話型推論で、静的性に応じて実行機構を使い分けるハイブリッド・ランタイム設計の一例であり、persistent カーネルや全面コンパイルと比較する補完的な系統である。
