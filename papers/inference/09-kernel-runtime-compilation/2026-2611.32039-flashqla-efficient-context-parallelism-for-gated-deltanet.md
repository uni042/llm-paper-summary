# FlashQLA: Efficient Context Parallelism for Gated DeltaNet

> Gated DeltaNetの文脈並列で、減衰窓に基づく境界状態準備の削減、カード内外の二重並列での要約共有、遅延モデルによる分割選択を組み合わせ、単一GPUで順伝播1.7〜3.1倍、8GPU・100万トークンで順伝播最大4.8倍を達成した実行フレームワーク。

## 概要

Gated DeltaNet（GDN）は、線形アテンションの一種で、固定サイズの再帰状態をトークンごとに更新しながら系列を読む。注意の計算量が系列長の二乗にならない代わりに、状態の更新には順序依存がある。実装では連続トークンをチャンクにまとめ、チャンク内は拡張WY表現で行列積として並列に計算するが、チャンク間の状態伝播は逐次のままで、系列が長くなるほど依存チェーンが伸びる。バッチサイズやヘッド数が大きい条件では他の並列度でGPUを埋められるが、小バッチやテンソル並列で1GPUあたりのヘッド数が減る条件では、この逐次部分がそのまま実行時間を決める。

系列方向の並列度を増やす文脈並列（context parallelism; CP）は、系列を分割して各分割を並列に計算する。ただし各分割は直前の分割が作った境界状態から始めなければならず、その入口状態を用意する境界状態の事前処理（状態要約の準備と境界状態の補正）が必要になる。先行実装であるFLAのKCPでは、この事前処理が8GPU・100万トークンの順伝播時間の50.8%を占めた。つまり並列化しても、事前処理という新しい逐次仕事が利得の半分を食う構造になっている。

FlashQLAはこの事前処理を3つの方向から削る。第1に、GDNのゲート減衰はヘッドごとに速さが違い、多くのヘッドでは古い履歴の寄与が急速に消えるため、要約準備を実効的な履歴の範囲（減衰窓）までに打ち切る。第2に、カード内CPとカード間CPを重ねるDual CPでは、両階層で重複する要約計算を共有し、境界状態の補正を階層的に行う。第3に、分割すれば常に速くなるわけではないため、遅延の代理モデルで分割の有効化と分割長をワークロードごとに選ぶAuto CPを置く。あわせてカーネル側も、代数的な簡約、CPを意識した融合、手作業のワープ特化で作り替える。代表結果は、単一GPUでFLA比の順伝播1.7〜3.1倍・逆伝播最大4.4倍、8GPU・最大100万トークンでDual CPの順伝播最大4.8倍であり、実モデルQwen3.8-2.4T-A95BのGDN演算子でも32Kトークンで3.25倍、64Kトークンで3.56倍の順伝播高速化が測られている。

## 問題設定

ここで余っているのはGPUの演算器であり、足りないのは系列方向の並列度である。GDNのチャンク内計算は行列積として効率がよい一方、チャンク間の状態伝播は前のチャンクの最終状態がなければ始められない。系列長が伸びるほどチャンク数が増え、逐次区間が長くなる。テンソル並列の次数を上げると1GPUあたりのヘッド数が減り、ヘッド方向の並列度も細るため、長文脈・小バッチ・高テンソル並列という条件が重なると、演算器を持て余したまま依存チェーンを待つ時間が支配的になる。

文脈並列はこの依存を、分割ごとの入口状態を先に計算することで解く。各分割について、直前までの履歴が状態へ与える影響を要約（局所的な状態要約と遷移の積）として求め、それらを順に合成して各分割の入口状態を復元する（境界状態の補正）。問題は、要約の準備自体が分割内のチャンクに対する逐次再帰であり、本体計算と同程度の費用がかかることである。分割を細かくするほど本体の並列度は上がるが、準備と補正の費用とスケジューリングのオーバーヘッドも増える。カード間CPとカード内CPを単純に重ねると、同じチャンクに対する要約準備が二重に行われる。したがって課題は「分割すること」ではなく、「準備の仕事量そのものを減らし、二階層で共有し、割に合わない条件では分割しない判断まで含めて設計すること」になる。

## 手法のあらまし

入力はGDNの順伝播・逆伝播に現れるキー、クエリ、値、ゲートの列であり、処理は大きく4段からなる。まず各ヘッドのゲート減衰から減衰窓を見積もり、境界状態の要約準備を、その窓の外側にある履歴を落として実行する。次にAuto CPが、遅延の代理モデルを使ってカード内CPを使うかどうかと分割長を決める。複数GPUではDual CPが、カード内分割の要約を軽い集約でカード間の要約へ変換して共有し、全GPUで要約を集めた後に階層的に境界状態を補正する。最後に、各分割が自分の入口状態から本体計算を並列に実行する。本体計算のカーネルは、ゲートを分離する代数変形で式を簡単にし、段階に合った融合とワープ特化で実装される。要約の準備が減り、重複が消え、分割の判断が自動化されることで、依存チェーンの長さではなく分割数で実行時間が決まる形に近づく。

## 手法

### 1. 減衰を意識した準備 — 効かない履歴を要約計算から落とす

この機構が観測するのは、ヘッドごとのゲート値の列である。GDNの状態はデータ依存の減衰を受けながら更新されるため、十分に古いトークンの寄与は減衰の累積でほぼ消える。論文は累積減衰が閾値（評価では e のマイナス10乗）以下になるまでの長さを、そのヘッドの減衰窓として定義する。実測では、32Kトークンの系列でQwen3.8-27Bのヘッドの66.9%、Qwen3.8-2.4T-A95Bのヘッドの80.7%が、8Kトークン未満の減衰窓を持っていた。つまり大半のヘッドでは、境界状態の要約を作るのに全履歴をたどる必要がない。

処理は、要約準備の再帰を減衰窓の範囲に限ることである。窓の外側の履歴は、状態への寄与が閾値以下まで減衰しているため、準備の計算から落としても境界状態は実質変わらない。出力は従来と同じ形の状態要約と遷移の積であり、後段の補正はそのまま使える。効く理由は、準備の逐次再帰の長さが系列長ではなく実効履歴の長さで決まるようになるためで、長文脈ほど削減量が大きくなる。失敗条件は、減衰の遅いヘッドや入力によって減衰が変わる場合で、その場合は窓が系列全体に広がり、削減は効かない。論文も、窓が見つからないヘッドでは全履歴の準備へ戻す設計にしている。なお、この打ち切りが損失や下流精度へ与える影響の測定は論文にない。

### 2. Dual CP — カード内とカード間の要約計算を共有する

この機構が扱うのは、カード間分割とカード内分割という2階層の文脈並列である。素朴に組み合わせると、各GPUがまず自分の担当区間のカード間要約を作り、次にその区間をさらに割ってカード内要約を作るため、同じチャンク列に対する要約準備が二重に走る。Dual CPは、各局所要約が状態に対するアフィン変換として表せることを使い、カード内分割の要約を順序どおりに合成するだけでカード間の要約を導く。共有されるのは要約計算であり、追加の仕事は軽い集約だけになる。

補正は階層的に行う。全GPUのカード間要約をオールギャザーで集め、各GPUが自分の入口状態を復元し、それを初期値としてカード内の各分割の入口状態を補正する。効果の実測として、8GPU・100万トークン・32ヘッドの条件で、事前処理の遅延は素朴な組み合わせの8.617ミリ秒から1.907ミリ秒へ減り、4.52倍になった。追加費用は要約の集約とオールギャザーの通信であり、本体の並列度がもともと十分な条件では、分割自体の利得が小さいためDual CPの優位も縮む。逆にヘッド数が少ない条件では、カード内の並列度を増やす効果が最も大きく出る。

### 3. Auto CP — 遅延モデルで分割の可否と分割長を選ぶ

この機構が観測するのは、バッチサイズ、ヘッド数、系列長といったワークロードの形である。カード内CPは細かく割るほど並列度が増える一方、準備と補正とスケジューリングの費用も増えるため、常に有効化するのでも固定の分割長でも最適にはならない。Auto CPは、カーネル遅延を「クリティカルなスケジュール深さ、CTAの総数、固定オーバーヘッド」で近似する軽い代理モデルを持ち、実行ウェーブの境界付近の候補だけを列挙する波を意識した探索で、予測遅延が最小になる分割長を選ぶ。さらに、予測した最良のCP構成とCPなしの実行を比べ、速くなると予測できる場合だけCPを有効化する。

効く理由は、分割の損得がカーネル効率と事前処理の費用まで含めて初めて決まるためで、ハードウェアの並列度だけを見る単純な規則では捉えられないからである。失敗条件は代理モデルの予測が外れる場合だが、論文の検証では、90件のワークロードで推論の94.4%、学習の90.0%で最適構成を選び、平均の遅延後悔は0.15%と0.37%にとどまった。追加費用はオンラインの候補評価だけであり、候補数を絞ることで小さく抑えられている。

### 4. カーネルの共同設計 — 代数簡約、融合、ワープ特化

本体計算のカーネルもCPの実行計画に合わせて作り替える。第1に、ゲートを分離する代数変形でGDNの定式化を簡単化し、遷移の累積を数値的に安定な形で保つ。第2に、チャンク単位、CP分割単位、系列単位という粒度の違う段階のうち、同期を壊さない範囲で処理を1カーネルへ融合し、中間テンソルの書き戻しとカーネル起動を減らす。比較対象のFLAは、拡張WY表現の構築、状態伝播、出力計算を別カーネルに分けて中間結果を実体化する構成であり、この差が単一GPUの基礎性能の差になる。第3に、手作業のワープ特化で、段階ごとに違う並列性と同期の要求へ役割を割り当てる。追加費用は実装の複雑さであり、対象はGDN専用である。他の線形アテンションへの拡張は、アフィン要約に基づく枠組みが土台になると著者らは位置づけるが、本論文の実装と評価はGDNに限られる。

## 評価

### まず見るところ

- **結論:** FlashQLAは単一GPUでも8GPUでもFLA系の実装を上回り、利得は系列が長く、1GPUあたりのヘッド数が少ない条件ほど大きい。ボトルネックだった境界状態の事前処理は、減衰を使う準備の削減とDual CPの共有で実際に縮んでいる。
- **速度・効率:** すべて実機の遅延測定であり、カーネル単体の理論計算量の話ではない。ただし対象はGDN演算子の順伝播・逆伝播であり、モデル全体の効果はTTFTで約5%減と、演算子の倍率よりずっと小さい。
- **品質:** 計算結果を近似で変える方式ではないが、減衰窓の外側を落とす準備については、損失や下流タスクでの精度検証が論文にない。数値の同一性や誤差の評価は未評価である。
- **評価の強さ／注意点:** 実装同士の比較はFlashQLA v0.1.4とFLA v0.5.1で、GPUの型番は本文に明示されていない。推論のサービング指標（スループット、TPOTなど）の測定はなく、順伝播・逆伝播の遅延が中心である。

この評価で最初に押さえるべきなのは、倍率の出どころである。単一GPUの順伝播で1.7〜3.1倍という数字は、文脈並列だけの効果ではない。内訳の評価が示すように、カーネル最適化だけでもFLA比1.45倍があり、そこへカード内CPとAuto CPで2.81倍、減衰を意識した準備で3.67倍、8GPUのDual CPで14.30倍（単一GPUのFLA基準、ヘッド数16・100万トークン）へ積み上がる。つまり「並列化の方式」と「事前処理の削減」と「カーネル実装」の3層が重なっており、どれか1層だけを自分の環境へ持ち込んでも同じ倍率は出ない。逆に言えば、事前処理が順伝播の50.8%を占めるという測定があるため、準備を削る2つの機構（減衰窓と要約共有）が倍率の主因であることは内訳からも裏づけられる。

条件による利得の動きも一貫している。順伝播の利得はテンソル並列の次数が高いほど、系列が長いほど大きい。これは、並列度が細る条件と依存チェーンが伸びる条件ほど、系列方向の並列化が効くためである。逆伝播では、総トークン数を32Kに固定して系列の本数を変えると、FLAは本数が少ないほど遅くなるのに対し、FlashQLAは遅延がほぼ安定する。系列内の並列度を確保できれば、バッチの組み方への感度が下がるという読み方ができ、パイプライン並列の学習で気泡を減らす効果も著者らは示唆する。複数GPUでは、ヘッド数64ではFlashQLAのKCPがFLA KCP比で約1.5〜2倍にとどまる一方、ヘッド数16ではDual CPの追加利得が最大になり、素朴な二重適用と比べても最大4.3倍速い。並列度が余っている条件で二重適用をすると、H=64では準備の費用が利得を上回ってFlashQLA KCPより遅くなる例もあり、Auto CPのような可否判断が要る理由が実測からも分かる。

実モデルの測定は、合成ワークロードの倍率が誇張でないことを支える。Qwen3.8-2.4T-A95Bの実際の活性値とゲート値を使ったGDN演算子の順伝播では、TP8で32Kトークン3.25倍、64Kトークン3.56倍と、系列が長いほど倍率が伸びる。一方でモデル全体のTTFTは32Kトークンで約5%減にとどまる。GDN演算子がTTFTに占める割合が小さいためであり、この方式の効果を「モデルが数倍速くなる」と読むのは誤りで、「長文脈でGDN層の逐次部分が支配的になる条件ほど効く」と読むのが正確である。学習側のスケーリングでも、8GPUへの強スケーリングはH=16・100万トークンでDual CPが6.45倍、FLA KCPが4.34倍と差がつき、理想線形に近い側へ寄っている。

Auto CPの評価は、方式の部品としての完成度を示す。遅延モデルは4つの中核カーネルについて、分割長を変えたときの実測遅延の波形（実行ウェーブの切り替わりで生じる段差を含む）をよく再現し、90件のワークロードでの選択は前述のとおりほぼ最適だった。静的な規則との比較では、固定分割より一貫して速く、ハードウェアの並列度だけを見る規則に対しては推論で最大3倍の差がついた。規則がカーネル効率と事前処理の費用を見ないことが、そのまま遅延の差になる。注意点として、評価は著者らのカーネル群と8GPUサーバに閉じており、GPU型番が明示されていないため、他のGPUでの再現性は論文からは判断できない。また、精度・損失の評価、サービング条件での評価、GDN以外の線形アテンションでの評価は未評価である。

## 既存研究との差

FLAは線形アテンション全般に使えるTriton実装を提供し、単一GPUの土台になってきた。KimiのKCPは系列をデバイス間で割り、局所要約と境界状態の補正で文脈並列を実現したが、事前処理の費用は残った。FlashQLAはこの2つに対し、事前処理そのものを減らす減衰配慮型の準備、カード内並列まで含めた二階層の要約共有、分割判断の自動化、カーネルの作り替えを重ねた点が差である。対象をGDNに絞る代わりに、ゲート減衰というGDN固有の性質を実行方式へ取り込んでいる。

## 限界・実装状況

- ハードウェア依存条件: 評価は8GPUサーバに限られ、GPU型番が明示されていない。カーネルはTileLangによるGDN専用実装で、他のGPUや他の線形アテンションでの効果は未評価である。
- モデル／ワークロード依存条件: 減衰を意識した準備は、減衰の速いヘッドが多いモデルで効く設計であり、減衰の遅いモデルや入力では利得が縮む。精度や損失への影響は論文で評価されていない。
- 実装状況: 公式コードが公開されている。公開後にFlashInferとcuDNNの最適化実装が同様の考え方を取り入れたとされ、上流への浸透は進みつつあるが、本論文の評価は著者らの実装での測定である。
- 評価範囲: 推論サービングのスループットやTPOTではなく、順伝播・逆伝播の遅延が中心である。

## 一般的な実装上の含意

並列化の方式を足す前に、その方式が新たに生む逐次仕事（ここでは境界状態の事前処理）の占有率を測ることが先である。占有率が半分に達するなら、本体計算の並列化より事前処理の削減と共有のほうが効く。また、モデルの数学的な性質（ゲート減衰）が実行方式の削減根拠になる場合は、性質の分布を実モデルで測ってから設計すると、削減が効く条件と効かない条件を先に切り分けられる。分割の可否判断を遅延モデルで自動化する形も、並列化の損得が条件依存で大きく変わる系では再利用できる。
