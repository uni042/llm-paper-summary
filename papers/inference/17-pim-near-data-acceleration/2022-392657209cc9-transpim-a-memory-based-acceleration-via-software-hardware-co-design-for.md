# TransPIM: A Memory-based Acceleration via Software-Hardware Co-Design for Transformer

## 概要
TransPIMは、Transformerを高帯域メモリ（High Bandwidth Memory; HBM）上のメモリ内処理（Processing-in-Memory; PIM）とニアメモリ計算（Near-Memory Computing; NMC）で高速化するため、データ配置・実行順とHBM内部ハードウェアを一体で設計したアクセラレータである。出発点は、Transformerでは大きな重みと中間表現を動かす割にデータ再利用が低く、GPUの演算ピークよりメモリ移動が律速になりやすいという観測である。既存のPIMアクセラレータを層単位でそのまま適用すると、中間データを層ごとに再配置する費用が大きく、著者らの事前解析ではデータ移動だけで実行時間の60%以上、ビット直列PIMで不得意な削減演算だけで約30%を占める条件があった。

TransPIMはこの二つを別々に処理する。ソフトウェア側では入力トークンをHBMバンクへ分割し、そのトークンに対応する計算を以後の層でも同じバンクで進める「トークン単位データシャーディング（token-based data sharding）」を採用する。ハードウェア側では、PIMが得意な行列演算はバンク内で並列実行しつつ、削減やSoftmaxのようなビット直列処理に不向きな演算を補助演算器（Auxiliary Computing Unit; ACU）へ移し、さらにバンク間のデータ交換をリング放送（ring broadcast）と専用バッファで高速化する。論文の評価では既存メモリ基盤方式に対して3.7〜9.1倍、GPUに対して22.1〜114.9倍の高速化を報告し、既存Transformer用ASICより高いスループットも示す。

## 問題設定
従来の層単位データフローでは、あるTransformer層を多数トークンについて処理してから次層へ進むため、PIMで演算そのものをメモリ近傍へ移しても、層境界で中間値を別のバンクや領域へ複製・再配置する必要がある。注意機構では系列長が増えるほど扱うスコア行列が二次的に増えるため、この移動費用は長系列ほど深刻になる。

一方、HBMセル近傍のビット直列PIMは大規模な行列積を多数のバンクで並列処理するのに向くが、行方向の部分和をまとめる削減、指数・除算を含むSoftmax、バンク間で必要なキー（key）・値（value）の共有は得意ではない。すべてをPIMへ押し込むと、これらの演算と通信が新たな律速になる。TransPIMは「トークンごとの局所性を層間で保つ」データフローと「不得意演算だけNMC側で補う」HBM改造を対応させる。

## 手法
### 1. トークン単位データシャーディング
系列長を (L)、埋め込み次元を (D)、使用するメモリバンク数を (N) とすると、入力の (L	imes D) 行列をトークン方向にほぼ均等に分割し、各バンクへ (L/N) 個のトークンを割り当てる。以後、各バンクは割り当てられたトークンについて全結合層、注意機構、フィードフォワードネットワーク（Feed-Forward Network; FFN）を層をまたいで処理する。入力・観測対象はトークン位置であり、出力は「どのバンクがどのトークンの中間値を保持し続けるか」という固定的な配置になる。

全結合層ではQ/K/V重みを各バンクへ用意し、各バンクが自身のトークン部分行列からQ/K/Vの部分行列を計算してその場に保持する。層を切り替えるたびに全トークン中間値を別配置へ戻す必要がないため、層単位割当より中間データ移動を減らせる。反面、同一演算へ全バンクを集中的に使う層単位方式より並列性が下がる場合があり、特にトークン数が少ないとバンクを埋められず利得が小さくなる。

### 2. 注意機構の局所計算とバンク間放送
注意機構では、各バンクがまず自分のシャード内のQ/Kから局所注意スコアを計算する。しかし各クエリは他バンクのキーにも注意する必要があるため、キー部分行列をバンク間で順次放送してシャード間の交差注意を求める。Softmax後に値を掛ける段階でも同様に、値部分行列を放送して各バンクが自分の出力トークンを完成させる。

この通信をホストやHBM外部へ往復させず、HBM内部のバンクグループバス・チャネルバスとリング放送機構で処理する。論文では、専用放送・コピー用バッファを加えたデータ経路により、同じトークン単位方式でもバッファなし構成よりデータ移動時間を4.1倍削減している。したがってトークン配置だけでなく、注意機構が必ず要求する全体情報の交換を内部帯域へ載せることが重要である。

### 3. PIMと補助演算器の分担
行列積など並列性の高い演算はビット直列PIMへ残す一方、各バンクに補助演算器（ACU）を置き、ベクトル削減とSoftmaxを処理する。ACUはビット直列加算木、バッファ、逆数計算用のパイプライン除算器などを備え、PIMだけでは低スループットになる削減をニアメモリ側で集約する。

この分担の効果は評価内訳にも現れ、TransPIMはPIM単独構成より削減演算に費やす時間を35.3倍、NMC単独構成より56.1倍減らした。ACUの並列度を増やすほど削減は速くなるが面積も増えるため無制限には増やせず、論文は加算木・サブアレイ並列度について性能・エネルギー・面積の設計空間を探索している。

### 4. デコーダでの処理
エンコーダでは多数の入力トークンを均等分割できる一方、自己回帰デコーダは各反復で新しいトークンが1個しか増えない。TransPIMは既存トークンのシャーディングを維持し、新規Q/K/Vを一つのバンクで作って必要なQを他バンクへ配布し、各バンクが保持する過去トークンとの部分注意を計算する。部分和はバンク間で段階的に削減する。

このためデコーダでも既存の履歴データを集中的に再配置せずに済むが、1反復1トークンではトークン単位並列性を十分引き出しにくい。実際、GPT-2言語モデルでは次善のLayer-TransPIMに対する速度利得が1.4倍に縮み、エンコーダ主体の長系列ワークロードほど大きな差は出ていない。

## 評価条件
評価は実チップのTransPIMではなく、Verilog HDLで実装・合成した追加回路の面積・電力値と、Ramulatorを拡張した詳細シミュレータを組み合わせる。HBMはHBM2を想定し、最大8スタック、ホスト-HBM帯域256 GB/s、ACUは500 MHzとしている。追加回路は65 nmライブラリで合成後、HBM評価用の22 nmへスケールし、8 GB HBM2あたりの追加面積は2.15 mm²、元DRAMに対して約4.0%と見積もられている。

比較対象にはNVIDIA RTX 2080 Ti、Google Cloud TPUv3 8コア、PIM単独方式、Newtonを基にしたニアバンク処理方式（near-bank processing）、層単位／トークン単位の各データフローが含まれる。GPU/TPUはTensorFlowモデルをJITコンパイルし、初回コンパイルを除いた反復の平均遅延を測る。PIM系は同一HBM条件を揃え、全結合・FFNは8ビット、Softmaxは指数範囲確保のため16ビットで評価する。

ワークロードはRoBERTaによるIMDB分類とTriviaQA質問応答、PegasusによるPubMed/Arxiv要約、GPT-2-mediumによるデコーダ専用言語モデルである。実行時間／バッチ、GPU基準の高速化、GOP/J、内部演算・データ移動内訳、バンク利用率、帯域利用量、面積・電力、HBMスタック増加時のスケーリングまで測る。

## 主要結果
GPU比較ではToken-TransPIMがRTX 2080 Tiに対して22.1〜114.9倍、TPUv3に対して8.7〜57.4倍高速だった。エネルギー効率はGPU比138.1〜666.6倍、TPU比39.5〜376.7倍で、特に長系列ほど差が大きい。一方、IMDBのようにトークン数が少ないと1バンク当たり最低1トークンという制約でPIM並列性を埋められず、速度利得は小さくなる。これは「長系列ほどデータ移動削減とメモリ内並列性が効く」という機構と評価結果が対応している。

PIM単独の層単位方式に対しては約9倍級、同じPIM単独でもトークン単位シャーディングを与えた方式に対してなお3.7倍高速である。内訳では、トークン単位シャーディングだけでデータ移動遅延をシステム別に約4.5〜4.8倍削減し、ワークロード別にはIMDB 1.3倍、PubMed 10.1倍、Arxiv 5.0倍、TriviaQA 1.9倍の改善となった。長系列の注意機構では層単位方式の移動量が系列長に対して二次的に増えるのに対し、トークン単位方式では移動量の増加を線形側へ抑えられるため、PubMed/Arxivで差が大きい。

ハードウェア側では、専用データ経路がバッファなしTransPIMに対してデータ移動を4.1倍削減し、ACUが削減演算の時間をPIM単独比35.3倍、NMC単独比56.1倍削減した。平均バンク計算利用率はToken-TransPIMが45.8%でLayer-TransPIMの30.8%より1.5倍高い。Layer-TransPIMの帯域使用量は最大1699 GB/sに達するのに対しToken-TransPIMは最大762 GB/sで、同じ8スタック・合計2 TB/s級の内部帯域でも不要な移動量を減らしていることが分かる。

ASIC比較では平均734 GOP/sを示し、A³の221 GOP/s、SpAttenの360 GOP/sに対して約2.0〜3.3倍のピークスループット相当となる。PegasusのPubMed/ArxivではGPU比83.9倍／114.9倍で、SpAttenがGPT-2デコーダについて報告した35倍という値を上回る。ただしモデル・タスク条件は同一ではないため、これは完全な同条件速度比較ではなくアーキテクチャ規模を揃えた参考比較である。

電力は評価したRoBERTa/Pegasus条件で従来DRAMシステムの60 W電力予算を下回り、入力長128から4096へ伸ばしたときの増加は約4 Wだった。HBMスタック数を増やす評価では、長系列で演算資源を十分使えるほどほぼ線形に近いスケーリングを示す。一方、短系列やデコーダ1トークン反復では並列性不足によりスケールしにくい。

## 既存研究との差
従来のメモリ基盤機械学習アクセラレータはCNNなど演算密度の高いモデルを主対象とし、層単位でデータを配置・実行する設計が多かった。TransPIMはTransformer固有の低再利用・注意機構の全トークン依存を前提に、まずトークンをバンクへ固定して層間の局所性を作り、そのうえで避けられないK/V交換をHBM内部のリング放送へ載せる。

また「PIMならデータ移動が消える」と仮定せず、PIMが苦手な削減・Softmaxとバンク間通信を明示的に別ハードウェアへ割り当てる。データフロー変更、PIM/NMC演算分担、内部通信路の三つを同時に設計し、その各要素を内訳評価で切り分けた点が中心的な差である。

## 限界
評価値の大部分は、Verilog合成から得た回路特性とRamulatorベースのシミュレーションを組み合わせた専用HBM構成の結果であり、既存GPUへソフトウェアだけを追加して得られる速度ではない。比較GPUもRTX 2080 Ti、TPUはTPUv3で、モデルはRoBERTa、Pegasus、GPT-2-mediumであるため、別世代ハードウェアや別のTransformer形状へ絶対倍率を移すことはできない。

トークン単位方式は長系列で有利だが、短系列ではHBMバンクを埋めるトークンが不足する。デコーダ専用GPT-2でも1反復1トークンのため、次善方式に対する速度差は1.4倍まで縮んだ。さらに注意機構ではK/Vのバンク間交換そのものは消せず、リング放送帯域が不足すれば再び通信律速になる。したがって利得は「大きな系列、十分なバンク並列性、内部放送帯域を活用できる」という条件に強く依存する。
