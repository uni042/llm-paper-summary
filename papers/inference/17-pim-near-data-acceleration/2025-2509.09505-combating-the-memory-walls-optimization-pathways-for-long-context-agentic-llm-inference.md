# Combating the Memory Walls: Optimization Pathways for Long-Context Agentic LLM Inference

> PLENAは長文脈推論の帯域・容量の二重memory wallを、flattened systolic array、W/A/KV別の低精度化、native FlashAttentionの3経路で同時に攻め、simulationでA100比最大2.23倍のthroughputを示す。

## 概要

エージェント型LLMでは、1回の質問へ短く答えるchatbotよりも、Webページ全体、画面状態、長いtool call履歴、code repositoryの一部などを文脈へ繰り返し保持する。文脈が長くなるほど各layerのKVキャッシュが増え、decode時には新tokenを1個生成するたびに大量の既存K/Vへaccessする。

PLENAが問題にするmemory wallは二種類ある。第一は **容量wall（capacity wall）** で、長いKV cacheとmodel weightがHBMへ収まりにくくなり、batch sizeを増やせない。第二は **帯域wall（bandwidth wall）** で、計算器のFLOPSが余っていても、weightやKVをoff-chip memoryから供給する速度が追い付かない。

この二つは通常のsystolic arrayにも悪影響を与える。長文脈推論ではmemory capacityの制約からbatch dimensionが小さくなりやすく、GEMMは一辺が短く一辺が長い「fat」な形になる。正方形の大きなsystolic arrayへそのまま載せると、短いdimensionに対応するprocessing element（PE）が空き、理論演算器数ほど利用できない。

PLENAはこの問題を三つの経路で同時に解く。**Pathway 1** はsmall-batch GEMMに合わせて配列を細長くするflattened systolic array、**Pathway 2** はweight・activation・KV cacheを同じbit幅にせず感度に応じて別precisionへするasymmetric quantization、**Pathway 3** は長文脈で支配的になるattentionをoff-chip往復なしに処理するnative FlashAttention supportである。

さらに、これらを個別hardware blockとして終わらせず、custom ISA、compiler、quantization toolkit、transaction-level simulator、analytical model、design-space explorationまで一つのstackへまとめる。ISCA 2026版では、同じmultiplier数とmemory条件でA100 GPU比最大2.23倍、TPU v6e比最大4.70倍のthroughput、A100比最大4.04倍のenergy efficiencyを報告する。ただしperformanceは製造chipの実測ではなく、RTL synthesis結果とsimulator/modelに基づく。

## 問題設定

### 長文脈では「計算量」より先にKVの置き場所が詰まる

通常のdecodeではbatchを増やすとGEMM効率を上げやすい。しかし各sequenceが128K token級のKV cacheを持つと、batchを1→2→4と増やすだけでもHBM容量を大きく消費する。容量制約でbatchを小さくせざるを得ないため、acceleratorのmatrix unitは大規模batch向けの形を活かせなくなる。

一方、KVを低bit化すれば容量は空くが、activationやweightまで同じprecisionへ落とすとaccuracyが崩れやすい。したがって「全部4 bit」という一括量子化より、どのtensorが容量・帯域をどれだけ占め、どのtensorが誤差へ敏感かを分けて扱う必要がある。

### Attentionは長文脈になるほど別の帯域問題を持つ

FlashAttentionはQK^T、softmax、PVをtile化し、中間attention matrixをHBMへ書き戻さずon-chip memory内で処理することでmemory trafficを減らす。しかし一般的な固定function acceleratorではtransposeやsoftmax、head並列、tile間reductionがhardware dataflowと噛み合わず、CPU補助や余分なbuffer transposeが必要になることがある。

PLENAは「GEMM acceleratorにFlashAttentionを後付けする」のではなく、Matrix/Vector/Scalar unitとmemory access命令を最初からattention dataflowに対応させる。

## 手法のあらまし

PLENAの入力は、量子化済みTransformer modelと、prefill/decodeのworkload条件である。Compilerはmodel operationを47命令のPLENA ISAへloweringし、Matrix Unit・Vector Unit・Scalar Unitとon-chip SRAMを使うexecution sequenceへする。

Matrix Unitのsystolic arrayは、通常の正方形ではなく短辺をsmall batch dimensionへ合わせた細長い構成を採る。Off-chipではweightとKVを主に低bit microscaling形式で保存し、activationや誤差に敏感なnon-GEMM operationはより高いprecisionをon-chipで維持する。

AttentionではMatrix SRAMからKをtranspose済みの順序で読み出せるため、K^Tを別HBM bufferとして保持しない。FlashAttentionのtile処理をISA命令として流し、QK^T→softmax→PVをon-chipへ留める。

## 手法

### 1. Flattened systolic array — small-batch GEMMの形へ演算器を合わせる

通常の128×128や64×64のsystolic arrayでは、GEMMのM dimensionが1〜4程度しかない場合、多くのrowが空く。PLENAは同じ総multiplier数でも、4×1024や32×2048のように一方向へ長いsub-array構成を使う。

入力は `M×K` activationと `K×N` weightで、output-stationary dataflowによりpartial sumをPE内へ残しながらK directionを長くstreamする。短辺をMへ合わせることで、小batchでも多数のmultiplierが同時に仕事を持てる。

さらにarrayを複数coreへpartitionでき、attentionではheadごとに並列化する。つまりFFNのfat GEMMと、head dimensionが比較的小さいattentionの両方で同じmatrix hardwareを遊ばせにくくする。

この方式はbatchが十分大きく正方形arrayを既に高利用率で使える場合には利得が縮む。PLENAの形状は「long contextによるcapacity制約→small batch→fat GEMM」という因果へ特化している。

### 2. Asymmetric microscaling quantization — W/A/KVを別precisionにする

PLENAの「asymmetric」はzero-pointの有無だけを指すのではなく、**Weight（W）、Activation（A）、KV cacheに異なるdata format・bit幅を割り当てる**設計を指す。

WeightとKVはHBM容量・帯域を大きく消費するため、MXINT/MXFPなどblock-wise microscalingの4-bit級形式を積極的に使う。ActivationやLayerNorm/SiLUなど誤差へ敏感な途中値は、on-chip Vector SRAMではより高precisionのMiniFloat/FP系を使い、低bit誤差が全layerへ累積するのを抑える。

代表的な構成にはW4/A4/KV4があり、capacityを空けることでlong-context時にもbatchを増やせる。単に1 token当たりのbyte数を減らすだけでなく、空いたHBMをbatchへ再投資してmatrix utilizationを上げることがPathway 1との相乗効果になる。

### 3. Output-guided clippingとselective rotation — 4 bit化の誤差源を狙う

低bit microscalingではoutlierがblock全体のscaleを広げ、通常値のresolutionを粗くする。PLENAはweight quantization時に、weight自身の誤差だけではなく **layer output norm error** が小さくなるclipping rangeを探索する。

Activation/KVにはHadamard rotationを使ってoutlierを平滑化できるが、PLENAは全箇所へ無条件にrotationしない。Calibrationで効果があるmatmul種別だけを選ぶ **selective rotation** を使う。現在の公開toolkitでも候補matmulを順に有効化し、perplexityが改善するものだけ採用する探索が用意されている。

入力はcalibration sampleとquantized candidate、出力はlayer/blockごとのclipping/rotation decisionである。追加calibration costとruntime rotation hardwareを払う代わりに、HBMに置くW/KVを低bit化してもquality lossを抑える。

### 4. Native FlashAttention — K^TをHBMへ複製せずattentionをon-chipで閉じる

長文脈ではattentionのQK^TとPVが大きなmemory trafficを生む。PLENAはMatrix/Vector SRAMとISAへFlashAttentionのtile executionを組み込み、中間attention matrixをHBMへmaterializeしない。

特にMatrix SRAMは **transpose-on-read** を持ち、同じK dataを通常順・転置順のどちらでも追加latencyなく供給できる。QK^T用にK^Tを別bufferへ作ってHBM容量を倍増させる必要がない。

SoftmaxやnormalizationはVector/Scalar unitで処理し、tile resultをそのまま次operationへ渡す。これによりPathway 2で圧縮したKVを、Pathway 3でも不要なoff-chip往復なしに使える。

### 5. ISA・compiler・simulator — 3経路を一つのprogramming modelへつなぐ

PLENAは47命令のcustom ISAを持ち、hardware loop、tile-level schedule、MX datatype、attention/FFN operationを表現する。PyTorch側のmodel operationはcompilerがassembly templateへloweringする。

公開stackにはtransaction-level emulator、analytical latency model、utilization modelがあり、HBM/DRAM挙動を含むarchitecture parameterを変えてTTFTやTPSを推定できる。Projectの説明ではtransaction-level simulatorはRTL simulationより約200倍高速で、誤差5%未満を目標/報告している。

Design-space explorationではarray shape、SRAM/HBM、quantization configurationを別々に固定せず、accuracy・latency・areaなどを同時に探索する。PLENAの主張は、これらを単一のhardware parameter tuningではなくco-designとして扱う点にある。

### System throughput

ProjectのISCA 2026版tableでは、A100 systemを1.00×とした相対throughputが次のようになる。PLENAは16 accelerator構成、GPU baselineは4 accelerator構成で、memory条件を揃えるようmodel化されている。

| Model / workload | A100 | H100 | TPU v6e | PLENA |
|---|---:|---:|---:|---:|
| LLaMA-3.1-8B / GSM8K (1.4K/0.2K) | 1.00× | 2.48× | 0.88× | 1.91× |
| LLaMA-3.1-8B / long-context | 1.00× | 2.34× | 0.46× | 1.45× |
| LLaMA-3.3-70B / BFCL (114K/5K) | 1.00× | 2.04× | 0.46× | 2.23× |
| LLaMA-3.3-70B / OSWorld (90K/8K) | 1.00× | 2.34× | 0.85× | 2.21× |

この表は重要なnegative resultも含む。PLENAはA100やTPU v6eには大きく勝つが、**H100より常に速いわけではない**。8B workloadではH100の相対throughputがPLENAより高く、70B BFCLではPLENAがわずかに上回る。したがってheadlineの2.23×は「全現行GPUに2.23×」という意味ではない。

### Headline結果

| 指標 | 結果 | 解釈 |
|---|---:|---|
| Throughput vs A100 | 最大2.23× | long-context 70B workloadでmemory/shape最適化が効く |
| Throughput vs TPU v6e | 最大4.70× | square systolic + memory条件との差が大きい |
| Energy efficiency vs A100 | 最大4.04× | 低bit memory trafficとarray utilizationの両方が寄与 |
| Flattened-array energy | FFN/FlashAttentionで最大約52%削減 | 同じ演算器資源でもarray shapeがenergyへ効く |
| 旧arXiv版のheadline | 2.24× A100 / 3.85× TPU v6e | 版更新でISCA版の比較値が変わっている |

以前のrepository本文にあったA100 2.24× / TPU v6e 3.85×は初期arXiv版の値である。現在のISCA 2026版・公式project pageは2.23× / 4.70×と4.04× energy efficiencyを示しているため、ここでは新しい値を基準にした。

### 量子化結果の読み方

PLENAはW/A/KVすべてを無差別に同じ形式へ落とすのではなく、W/KVを強く圧縮し、sensitiveなintermediate valueを高precisionで保つ。Output-guided clippingとselective rotationを追加することで、4-bit級のconfigurationでもperplexity悪化を抑える。

ここでquantizationは単なるmodel compressionではない。HBMの空きが増えるとlong-context batch capacityが増え、flattened arrayの利用率も上がる。したがってquality tableとsystem throughputを別々の最適化として読むのではなく、**precision→capacity→batch shape→array utilization** という因果で読む必要がある。

## 既存研究との差

GPTQ、OmniQuant、QuaRotのような量子化研究は主にmodelの数値表現を改善する。FlashAttentionはattention memory trafficを減らすalgorithm/kernelである。TPU型systolic acceleratorはGEMMを高効率にする。

PLENAはこれらの一部分だけを新しくするのではなく、long-context agentic workloadで三者が相互依存する点を設計中心に置く。低bit化でcapacityを増やし、small-batch/fat GEMMをflattened arrayで処理し、長文脈attentionをnative FlashAttentionでHBM往復なしに処理する。

またcompiler・ISA・simulator・DSEまで含めるため、「提案arrayだけ理想条件で評価したaccelerator」よりsoftware stackを含む。ただしproduction serverでfabricated PLENA chipを動かしたend-to-end測定ではない点は区別が必要である。

## 限界・実装状況

最大の制約は、throughputとenergyの主結果がsimulation/modelに基づくことである。RTLはsynthesisされているが、siliconでA100/H100と同じworkloadを実測した比較ではない。Memory controller、NoC、実製造variation、runtime overheadなどはmodel精度に依存する。

Flattened arrayはlong-context・small-batchに合わせた設計なので、大batchでsquare GEMMが支配的なworkloadではH100等のgeneral acceleratorが有利になり得る。実際、公式system tableでも8B workloadではH100がPLENAを上回る。

Quantizationはcalibrationを必要とし、model/configurationにより数GPU-hour〜数十GPU-hour規模の前処理がある。Selective rotationやformat choiceもmodel familyが変われば再探索が必要になる可能性がある。

一方、公開実装状況は初期preprint時点より進んでいる。PLENA_Simulator repositoryにはtransaction-level emulator、analytical model、compiler、quantization関連codeが含まれ、full-stackの再現・探索に使える。

## 一般的な実装上の含意

長文脈推論では、memory capacityとbandwidthを別問題として解くと最適化が噛み合わない場合がある。KVを圧縮してcapacityを空けた結果batch sizeを上げられるなら、その新しいGEMM shapeに合うcompute architectureも必要になる。

またhardware acceleratorを評価するときはpeak TOPSより、**実際のmatrix shapeで何%のPEが働くか**を見る必要がある。Agentic workloadのようにcontextが巨大でbatchが小さい場合、同じmultiplier数でもarray aspect ratioだけで実効利用率が大きく変わる。
