# Combating the Memory Walls: Optimization Pathways for Long-Context Agentic LLM Inference

> 長文脈エージェント推論の帯域・容量の二重メモリ壁に対し、平坦化シストリック配列、非対称4ビット量子化、FlashAttention専用支援を共同設計し、シミュレーションでA100比最大2.23倍、TPU v6e比最大4.70倍のスループットを示す。

## 概要

一般的な大規模言語モデル（Large Language Model; LLM）のデコードでは、1ステップごとに重みを読み、過去トークンの鍵・値キャッシュ（Key-Value cache; KVキャッシュ）へ注意を計算する。短い会話ではフィードフォワードネットワーク（Feed-Forward Network; FFN）の大規模行列積が支配的になりやすいが、エージェント型LLMではツール履歴、画面状態、検索結果などが文脈へ累積し、数万〜十万トークン級まで伸びる。するとKVキャッシュが膨らみ、注意計算が読むデータ量も増え、**演算性能より先にメモリ容量と帯域が限界になる**。

PLENAは、この変化を単なる「より低ビットにする問題」とせず、ハードウェア形状まで含む三つの経路で扱う。第一に、小さな有効バッチでも行列演算器を埋めやすい**平坦化シストリック配列（flattened systolic array）**を採用する。第二に、重み・活性値・KVキャッシュで外れ値特性が違うことを利用する**非対称量子化（asymmetric quantization）**を設計し、重みには出力誤差を基準とするブロック単位クリッピング、活性値とKVキャッシュには選択的回転を適用する。第三に、注意の中間行列を外部メモリへ書き戻さないよう**FlashAttentionのオンチップ実行支援（native FlashAttention support）**を組み込む。

これらを独自命令セット（Instruction Set Architecture; ISA）、コンパイラ、トランザクションレベル・シミュレータ（transaction-level simulator）、RTL、精度と遅延を同時に扱う設計空間探索へ統合する点がPLENAの特徴である。7 nmを想定したシミュレーションでは、同等の乗算器数とメモリ条件でエージェント型ワークロードにおいてA100比最大2.23倍、TPU v6e比最大4.70倍のスループットを報告する。

ただし、これは製造済みPLENAチップの実測ではない。また4ビットの重み・活性値・KVキャッシュ（W4A4KV4）は容量と帯域を大きく削減する代わりに品質を完全には維持せず、最大バッチを詰める比較では初回トークン遅延（Time To First Token; TTFT）がA100より長くなる条件もある。したがって「最大高速化」だけでなく、品質、バッチ、TTFT、シミュレーションという前提を合わせて読む必要がある。

## 問題設定

### 長文脈では二つのメモリ壁が同時に現れる

エージェント型推論では、通常のチャットより桁違いに長い履歴を保持する。論文はLongWriterの例として約5千トークンのプリフィル後に最大約8.5万トークンを生成する状況を挙げ、長期生成ではFFNより注意計算が支配的になる領域が現れると説明する。Llama-3-70Bで128K文脈をFP16のKVキャッシュとして保持すると、単一バッチでも約39 GBになる。

ここで容量不足は単に「モデルが載らない」だけではない。同じHBM容量の中でKVキャッシュが増えるほど同時に処理できる要求数、すなわちバッチサイズが小さくなる。デコードの行列積では入力側の行数がバッチに比例するため、バッチが小さいと大きな正方形シストリック配列の一部しか使えず、ピーク演算性能が高くても利用率が落ちる。

さらに、長いKVキャッシュを毎ステップ読み続けるため帯域壁も強くなる。KVキャッシュ、重み、注意の中間テンソルがHBMとの間を往復すれば、算術演算器を増やしてもデータ待ち時間が残る。PLENAはこの**容量壁 → 小バッチ化 → 演算器利用率低下**と、**帯域壁 → 外部メモリ待ち**を一つの共同設計問題として扱う。

### 従来の専用行列演算器が長文脈デコードに合いにくい理由

従来のシストリック配列は64×64のような比較的正方形の形状が多く、大きなGEMMでは高い利用率を得やすい。一方、長文脈デコードではFFNの行列積のM次元、すなわち有効バッチが小さくなりやすい。Mが配列の高さより小さいと、物理MACが空いたままになる。

注意計算でも、ヘッドごとの行列積は幅が限られ、単一ヘッドだけを巨大配列へ載せても効率が悪い。そこでPLENAは配列を細長くし、FFNでは小さいMへ合わせ、注意では複数ヘッドを並列に流す。この「計算形状と物理配列形状を合わせる」ことが第一の設計原理になる。

### 単純な4ビット化だけでは品質が崩れる

メモリ容量と帯域を同時に減らす最も直接的な方法は、重み、活性値、KVキャッシュを低ビット化することである。しかしLLMのテンソルには少数の大きな外れ値があり、量子化範囲を外れ値へ合わせると多数の通常値の分解能が失われる。

さらにPLENAが使うマイクロスケーリング形式では、重みと活性値・KVキャッシュで「回転が効くか」が同じではない。論文の構成要素除去実験（ablation）では、重みだけに回転を使うとむしろパープレキシティ（perplexity; PPL）が悪化する一方、活性値とKVキャッシュでは外れ値抑制として選択的回転が有効だった。したがって全部へ同じ量子化前処理を適用せず、データ種別ごとに保護方法を変える必要がある。

## PLENAの処理全体

一つの推論要求は、概念的には次の経路を通る。

1. PyTorch側のモデルをPLENAコンパイラが専用命令へ落とし、FFN、注意、ベクトル演算を対応する演算資源へ割り当てる。
2. 重みは出力再構成誤差を基準とするブロック単位クリッピングを用いて低ビット化する。
3. 活性値とKVキャッシュは必要な層だけ選択的に回転し、外れ値を平滑化して低ビット化する。
4. FFNと注意の行列積は平坦化シストリック配列へ流す。注意では複数ヘッドを並列処理しやすいようマッピングする。
5. FlashAttentionは中間の注意行列をHBMへ退避せず、オンチップSRAM内で完結させる。KVの転置に必要なアクセスはSRAM構成側で支援する。
6. HBMからのデータは先読みし、演算と重ねる。長文脈デコードでは容量削減によってより大きなバッチを保持し、演算器利用率を引き上げる。
7. 設計段階では、精度・遅延など複数目的を設計空間探索し、配列寸法やベクトル幅、量子化形式を選ぶ。

このようにPLENAの利得は一つのカーネル高速化ではなく、**低ビット化で容量と帯域を減らす → より多くの要求を載せる → 平坦化配列でその形状を効率良く実行する → 注意の外部メモリ交通をさらに減らす**という連鎖から生じる。

## 手法

### 1. 平坦化シストリック配列

PLENAの行列演算器は、従来の64×64のような正方形ではなく、評価構成では4×1024のような細長い形状を使う。FFNデコードでバッチサイズが小さい場合、配列の短辺をM次元へ合わせることで、未使用行を減らせる。

注意計算では別の利点がある。ヘッド単位の行列積を一つずつ巨大配列へ流す代わりに、細長い配列上で複数ヘッドを並列に進める。これにより長文脈で注意計算の比率が増えても、行列演算器の利用率を保ちやすい。

代償として、単純な正方形配列より制御や加算木が増え、面積・電力はわずかに増える。論文はこの追加費用よりも、実ワークロードで空いていたMACを使える効果の方が大きく、実効エネルギー効率が改善すると報告する。

### 2. 重み向けの出力誤差基準クリッピング

重み量子化では、単純な最近傍丸めだけでなく、ブロックごとのクリッピング範囲を探索する。このとき重み自身の誤差だけを見るのではなく、量子化後のGEMM出力がどれだけ元出力からずれるかを評価する**出力ノルム誘導クリッピング（output-norm guided clipping）**を使う。

これは「重み値を最も忠実に復元する量子化」と「モデルの出力を最も保つ量子化」が一致しないためである。Llama-3-8Bの構成要素除去実験では、重み誤差基準より出力誤差基準の方がPPLを低く保った。

また、重みでは回転が常に有効とは限らない。PLENAのマイクロスケーリング整数形式（MXINT）では、重みへ回転を入れるとPPLが悪化するケースを観測しており、重み側はクリッピング中心にする。

### 3. 活性値・KVキャッシュ向けの選択的回転

活性値とKVキャッシュは重みより値域が広く、外れ値の影響が強い。そこでPLENAはすべての層へ一律に回転を適用するのではなく、モデルごと・層ごとに有効な箇所を探索して**選択的回転（selective rotation）**を適用する。

回転は外れ値を複数次元へ分散し、低ビット量子化で一部の巨大値だけにスケールを支配される問題を緩和する。論文では活性値・KVキャッシュ側では選択的回転がPPLを改善する一方、重み側では逆効果になり得ることを示す。この非対称性が、W/A/KVを同じ処理で量子化しない理由である。

### 4. FlashAttentionのネイティブ支援

通常の注意計算でQK^Tやsoftmax後の中間行列をHBMへ書き戻すと、系列長が長いほど外部メモリ交通が増える。FlashAttentionはタイル単位で計算して中間結果をオンチップに保持することで、この往復を避ける。

PLENAはこれをソフトウェア上のカーネルとしてだけでなく、オンチップSRAMと命令セットで直接支援する。特にQK^Tで必要になるKの転置アクセスを、巨大な明示転置バッファを作るのではなく、SRAMから行・列の両方向で読み出せる構造として扱う。

この機構により大きな注意中間テンソルをHBMへ書かずに済み、帯域消費を抑えられる。加えてメモリ先読みでアクセス遅延を演算と重ねる。

### 5. ハードウェア・ソフトウェア共同設計探索

PLENAは固定のアクセラレータ1案だけを提示するのではなく、配列長、ベクトル幅、量子化精度などを設計変数として探索する。評価ではLlama 3.2-1BとLlama-3-8Bを用い、遅延とPPLのパレート前線を多目的最適化する。

能動学習（active learning）にBoTorchを用いた探索は、無作為探索より良い遅延・PPL交換条件を見つけた。最終システム比較では、BLEN=32、MLEN=2048、VLEN=2048、W/A/KV=4/4/4の構成を採用している。

ここで重要なのは、量子化方式と演算器形状を別々に最適化していない点である。量子化でバッチ容量が増えると最適な配列形状も変わるため、精度・容量・帯域・利用率を同じ探索へ入れる。

### 量子化品質

4ビット化は無損失ではない。Llama-3-8BのWikiText-2ではFP16のPPLが6.13なのに対し、PLENAのW4A4KV4は7.22である。ただし同じ4/4/4条件のQuaRotは8.16であり、PLENAの出力誤差基準クリッピングと選択的回転が劣化を抑えている。

下流タスクでも同じ傾向がある。Llama-3-8Bの6タスク平均精度はFP16が73.22、QuaRotが65.18、PLENAが70.39で、FP16との差は残るが既存4ビット方式との差を縮める。Llama-3-70BでもFP16 79.94、QuaRot 69.21、PLENA 76.20である。

長文脈・エージェント系タスクでは、16ビット基準に対しW4A4KV4のPLENAはHumanEval pass@1が89.6→84.1、BFCL-W精度が27→24へ低下する一方、GSM8Kの完全一致率は97.85で同値だった。したがって「4ビットでも品質を維持」という単純な結論ではなく、タスクごとに劣化幅が異なる。

### 構成要素除去実験と内部挙動

量子化の構成要素除去では、単純なMXFP4がMXINT4より一貫して悪く、重みだけの量子化では回転が逆効果になることが示された。一方、活性値とKVキャッシュでは選択的回転が有効で、全系では出力誤差基準クリッピングと選択的回転を組み合わせるとPPLが改善する。

配列形状については、64×64の既存設計に対しPLENAは4×1024を用いる。論理合成ベースの評価で、標準GSM8Kと長文脈OSWorld-Lの双方において実効FLOPs/面積を高め、とくに長文脈で配列の空きを減らす。FlashAttentionのオンチップ支援と組み合わせることで、プリフィル・デコード双方の注意・FFN時間を削減する。

## 既存研究との差

量子化研究だけを見ると、GPTQ、AWQ、OmniQuant、SmoothQuant、QuaRotなどは既存GPUや一般演算器上で低ビット実行を成立させることを主眼とする。PLENAはそれに対し、量子化で生じるデータ形状とバッチ容量の変化を前提に**演算器の物理形状まで変える**。

専用アクセラレータ研究だけを見ると、MicroScopiQなども低精度計算器を設計するが、PLENAは長文脈エージェント推論で注意比率が上がり、小バッチ化することを明示的な設計条件にする。そのため平坦化シストリック配列とFlashAttention支援を量子化と同じ設計空間で扱う。

また、単なるハードウェア案ではなく、ISA、コンパイラ、トランザクションレベル・シミュレータ、RTL、多目的設計空間探索まで揃える点も特徴である。論文の価値は「4ビット専用チップが速い」ことだけではなく、長文脈で変化する律速をハードウェア・ソフトウェア共同設計へ落とす方法論にある。

## 限界・実装状況

最大の制約は、システム性能が製造チップではなく7 nm想定のトランザクションレベル・シミュレーションから得られていることである。A100/H100は実在GPUの仕様を使う一方、PLENAはモデル化された専用アクセラレータなので、コンパイラ、メモリ制御、実装上のばらつきまで含む実機比較ではない。

比較では総HBM容量・帯域や乗算器数を概ね揃えているが、シリコン面積、製造世代、汎用機能を完全に同条件へ揃えた比較ではない。したがって「A100の代替として2.23倍」と直接読むより、論文が設定したハードウェア予算下での設計比較と解釈すべきである。

量子化にも品質低下が残る。とくにHumanEvalやBFCL-WではFP16との差があり、W4A4KV4をそのまま品質制約の厳しい本番へ適用できるとは限らない。モデルやタスクごとの再較正が必要になる。

さらに最大バッチ比較では、PLENAが低ビット化によってより大きなバッチを搭載するためTPSが上がる一方、プリフィル量が増えてTTFTが悪化する。対話的用途ではTPSだけでなくTTFTのサービス水準目標（Service Level Objective; SLO）を満たすかを別途見る必要がある。

論文は将来課題としてGPUとの異種混在推論（heterogeneous inference）を挙げる。現時点のPLENAは既存GPUへソフトウェアだけで導入できる方式ではなく、専用ハードウェアとコンパイラの共同実装を前提とする。

## 一般的な実装上の含意

長文脈化では、短文脈ベンチマークで最適だった演算器形状がそのまま最適とは限らない。KVキャッシュ増大によってバッチが小さくなり、注意の比率が上がるなら、ピークTOPSより「実際の行列形状で何%のMACが動くか」を測る必要がある。

また、容量削減と帯域削減は独立ではない。KVキャッシュを4分の1にすると同じHBMへより多くの要求を載せられるが、その結果プリフィルの総計算量やTTFTが増えることもある。圧縮方式を評価するときは、**同じバッチでの速度**と**容量を使い切った最大スループット**を分けて測るべきである。

量子化についても、重み・活性値・KVキャッシュへ同じ処理を機械的に適用せず、外れ値構造と誤差伝播が異なることを前提に設計するとよい。PLENAの負の結果である「重み回転は悪化し得る」は、構成要素ごとの検証が必要な例になっている。
