# HPIM: Heterogeneous Processing-In-Memory-based Accelerator for Large Language Models Inference

## 概要

HPIMは、単一リクエスト・単一バッチのLLMデコードにおいて、重みを毎トークン読み込むGEMVの帯域制約と、KVキャッシュを使う注意演算の低遅延・複雑な演算制約を、異なるPIM（Processing-In-Memory）メモリ階層で処理するハードウェア・ソフトウェア協調設計である。大容量・高帯域のHBM3のbank近傍へ重み中心のGEMVを割り当て、低遅延でSoftmaxなどの複雑な演算を実装しやすいSRAM-PIMへ注意を割り当てる。両者の処理を、クエリ・キー・値生成、注意、射影、FFNの間で細粒度に重ね、自己回帰デコードの**トークン内部**に残る並列性を利用する。

原著v3はOPT 350M〜30B、FP16、バッチ1を対象に、SRAM-PIMのVerilog合成とHBM3のDRAMsim3拡張を組み合わせたcycle-accurate simulatorで評価した。NVIDIA A100 GPU比で最大23.1倍のE2Eレイテンシ短縮、既存PIMのIANUS比で最大1.56倍のデコード速度、CXL-PNM比で最大4.88倍のデコードスループットを報告する。これらは**設計モデルに基づくシミュレーション結果**であり、製造したHPIMチップを実機A100と同条件で測定した結果ではない。また、大きなバッチではHPIM-S-MBがA100に逆転されるという負の結果も報告する。

## 問題設定：デコードGEMVの帯域制約と注意の遅延制約

LLMのprefillでは複数トークンをまとめて処理するGEMMが中心だが、自己回帰デコードでは1トークンずつ重み行列を読むGEMVが中心となる。GEMVは計算量に比べて読み込む重み量が大きく、GPUの演算器を十分に使い切れない。原著Fig. 3はOPT-13B、入力512トークン・出力32トークンのA100測定を示し、全実行時間の73.8%がGEMV中心のデコード処理に割かれる。これはそのモデル・入力長・出力長での比率であり、全てのLLM推論で73.8%と断定する値ではない。

デコードの中にも異なる二種類の負荷がある。QKV射影とFFNは大量の固定重みを読み込むため、帯域が支配的なweight-intensive演算となる。これに対して注意演算は、KVキャッシュの不規則なアクセス、`QK^T`と`SV`のGEMV、Softmaxの最大値・総和の還元、転置や同期を含み、低遅延と柔軟な制御が重要なlatency-critical演算となる。どちらも単に「メモリ律速」だとして同じPIMへ置くと、容量・帯域・レイテンシ・非線形演算器の要件が衝突する。

SRAM-PIMは高速で制御回路や非線形演算を組み込みやすいが、面積当たり容量が小さい。HBM-PIMは重みを大量に保持し、bank内の内部帯域を利用できるが、DRAMのrow activationやrefresh、複雑なロジックの実装制約によりSRAMほど低遅延で柔軟ではない。HPIMはこの異種メモリの役割を分け、巨大な重みをHBM側へ置き、注意・SoftmaxをSRAM側で高速に実行する。

## 手法

### 1. コンパイラがモデルグラフを解析し、prefillとdecodeで配置を変える

原著§III-Aのコンパイラは、LLMの計算グラフとHPIMの構成情報を受け取り、演算ノードをGEMM、GEMV、Softmax、正規化、残差加算などへ分類する。prefillでは主にGEMMが支配的なため、演算をSRAM-PIM側のTensor Compute Unit（TCU）へ集中させる。一方decodeでは、QKV射影とFFNなどの重みGEMVをHBM-PIMへ、`QK^T`、Softmax、`SV`などの注意と非線形処理をSRAM-PIMへ割り当てる。実行に必要な命令列と転送・同期のスケジュールを生成し、データの往復を減らす。

この区別は、単に「HBMに重み、SRAMにKVを置く」という固定的なキャッシュ配置ではない。演算種別とprefill/decodeの段階に応じて、同じ行列演算でも最適な実行ユニットが変わる。prefillではGEMM性能を優先し、decodeではGEMVの帯域と注意の低遅延を優先する。演算の種類を見ずにすべてをHBM-PIMへ押し込む方式と異なり、複雑なSoftmaxをSRAM側で処理できる。

### 2. HBM3近傍PIMで重みGEMVを並列化する

HPIMのHBM-PIMはHBM3を基礎とし、各DRAM dieに複数channel・pseudo-channel・bank group・bankを持つ。各bankに単純なmultiply-accumulate処理ユニットを置き、重みをbank近傍から読み出して計算する。入力活性を共有バッファへロードし、複数bankへ配布してGEMVの積和を並列化する。重みをHBM外へ大量に転送せず、bank内部の帯域を使うことが目的である。

原著Fig. 7と§IV-Bでは、8枚のDRAM dieを積層するHBM3構成を示し、1スタック24GB、4スタックで合計96GBの容量を持つ設計を採用する。HBM3の各dieは2channel、各channelに2pseudo-channel、各pseudo-channelに8bank group×4bankを持つ。bankごとのPIMユニットは単純なMAC命令を実行し、複雑な制御やSoftmaxを直接bank内に実装しない。これにより、DRAMに複雑なロジックを集積する難しさを避けながら内部帯域を利用する。

原著Fig. 8とAlgorithm 1は、Q/K/V重みを注意ヘッド単位で分割し、channelへ交互に割り当て、bank内ではrow-bufferに合う形へ配置する。ヘッド並列（HP）とヘッド内部のtensor parallel（TP）を組み合わせ、ヘッド数とchannel数が一致しない場合にも負荷を均等化する。重みを単純な連続配列として置くのではなく、アクセス順序とbank衝突を減らすデータ配置までコンパイラが決める。

### 3. SRAM-PIMで注意と非線形演算を低遅延化する

SRAM-PIM側は、GEMM向けのTCU、SoftmaxやGELU・LayerNormなどのベクトル演算を担うVCU、注意GEMV用のPIMユニット、転置ユニット、ローカルメモリと命令スケジューラを持つ。原著Table IIIの設計ではSRAM-PIM 32コア、800MHz、TCUは64×64のProcessing Element配列、PIMユニットは16MBのSRAM-PIM macroを持つ。ローカルメモリと転置ユニットを設けることで、HBM側から受け取ったK/Vを注意に適した形式へ変換し、複雑な非線形演算をHBM側へ押し戻さない。

注意ヘッド数が32コアと同程度ならヘッドごとに独立して実行し、ヘッド数が多い場合は複数回に分け、少ない場合は1ヘッドを複数コアへ分割する。複数コアへ分割した場合、`QK^T`の部分スコアからSoftmaxの全体最大値・指数和をAll-Gatherでまとめ、正規化後に`SV`の部分結果を合成する。原著Fig. 9は2コアで1ヘッドを分割した場合の処理を示し、Softmaxのグローバル還元を正しく保つことが、単純なヘッド分割と異なる点である。

### 4. トークン内部のパイプラインで待ちを重ねる

自己回帰生成では次のトークンを出すまで次トークンの処理を開始できないが、**一つのトークンの内部には重み読出し・QKV生成・転置・注意・FFNの部分的な並列性がある**。HPIMはHBM-PIMでK/V重みを読み出す間にSRAM側で転置準備を進め、Qの生成とKの転置を重ね、`QK^T`を計算している間にVを用意する。SoftmaxはSRAM側のVCUで処理し、正規化済みスコアをPIMへ戻して`SV`を計算する。その間HBM側では次のヘッド群や後続のFFN重みの準備を進める。

原著Fig. 10は32ヘッドのprefillとdecodeのタイムラインを示す。prefillではTCUによるGEMMと非線形処理を中心に実行し、decodeではHBM側の重みGEMVとSRAM側の注意を重ねる。目的はトークン間の自己回帰依存をなくすことではなく、1トークン内のクリティカルパスを短縮することである。原著Fig. 15のOPT-13Bでは、HBM-PIM側が計算を続ける一方、SRAM-PIM側に55.3%のidle時間がある。パイプラインで完全にすべての演算器を稼働させられるわけではなく、両系統の負荷不均衡が残る。

## 評価

### シミュレーション環境と比較条件

原著§VIはOPT系列350M、1.3B、6.7B、13B、30B、FP16、バッチ1を対象とする。HPIMは実際に製造したチップではなく、SRAM-PIMのVerilog HDL設計を12nmで合成し、HBM-PIMをDRAMsim3の拡張モデルでcycle-accurateにシミュレートする。NoCはNoximでモデル化する。A100 GPUと、既存PIM設計IANUS、CXL-PNMを比較するが、メモリ容量、ピーク演算量、帯域、構成要素は同一ではないため、性能倍率を純粋なアーキテクチャだけの因果効果と解釈しない。

| モデル | OPT 350M/1.3B/6.7B/13B/30B | Llama、Qwen、MoEは主E2E評価対象外 |
| 数値精度 | FP16 | 量子化によるモデル品質変化を扱わない |

### A100とのE2E推論レイテンシ（Fig. 11）

原著Fig. 11は各OPTサイズ・入力/出力長でHPIMの全体推論レイテンシをA100と比較する。モデルが小さく出力が長い条件では、A100のGEMVが特に帯域律速となり、HPIMの重み近傍計算が有利になる。図中のピーク倍率はOPT-350M、入力64・出力128で**23.1倍**である。OPT-350Mの他の条件では入力128・出力384で20.4倍、256・768で16.3倍、512・1536で11.3倍と倍率が低下する。モデルサイズが大きくなると倍率はさらに小さく、OPT-30Bでは図中約3.8倍、3.7倍、3.5倍、3.1倍の範囲にある。

| モデル | 原著Fig. 11の主な速度倍率（A100/HPIM） | 解釈 |
|---|---|---|
| OPT-350M | **23.1、20.4、16.3、11.3倍** | 最大値は小型・短入力条件 |
| OPT-1.3B | 12.8、11.1、9.2、6.7倍 | 条件が重くなると倍率低下 |
| OPT-6.7B | 5.7、5.2、4.5、3.6倍 | 中規模では数倍 |
| OPT-13B | 3.8、3.7、3.3、2.9倍 | 大きなモデルでは差が縮む |
| OPT-30B | 3.8、3.7、3.5、3.1倍 | 大型モデルで23.1倍ではない |

この速度比は**cycle-accurateシミュレータが推定したE2Eレイテンシ**の比であり、実際のシリコンでの発熱・電源・配線・製造ばらつきを含む実測ではない。また、HPIMの96GB HBM3はA100の80GB HBM2eより大容量・高帯域である。そこで著者は、帯域をA100より小さくしたHPIM-Sでも比較し、OPT-6.7Bと13Bの条件で約2.3〜3.9倍の速度改善を報告する（Fig. 12）。HPIM-Sの改善が残ることは異種PIM配置とパイプラインの効果を支持するが、SRAM容量・演算構成は依然異なる。

### 既存PIMとの比較（Fig. 14）

IANUSはNPUとPIMを組み合わせた設計であり、HPIMは注意をSRAM-PIMへ配置してNPUの資源未利用を避ける。原著Fig. 14(a)はOPT-13Bのデコード遅延を比較し、最大**1.56倍**の改善を示す。IANUSは複数デバイスのPCIe接続を要する構成であり、HPIMは単一の異種PIM構成としてデータ移動を抑える。これは同一クロック・同一メモリ階層の置換実験ではなく、システム全体の比較である。

CXL-PNMはCXL接続の近傍メモリ演算を利用する設計であり、外部接続帯域が律速になり得る。原著Fig. 14(b)はOPT-13Bのデコードトークン/秒を比較し、HPIMが最大**4.88倍**高いスループットを示す。Fig. 14(a)のIANUS比較は遅延、Fig. 14(b)のCXL-PNM比較はスループットであり、二つの倍率を直接掛けたり同じベースラインとして平均したりしない。

### 面積・電力・演算分解と負の結果

原著Fig. 13はSRAM-PIM部分の合成面積を252.9mm²と推定し、PIMユニットが64%、TCUが27%を占めると報告する。SRAM-PIM部分の電力はprefillで13.5W、decodeで1.2Wと見積もる。ただしこれは**SRAM-PIMサブシステムの推定値**であり、4スタックHBM3、メモリI/O、電源回路、パッケージ全体を含むシステム電力ではない。図のエネルギー分解ではprefillのGEMMを担うTCUが61%、注意関連PIMユニットが22%を占める。

原著Fig. 15はOPT-13Bのデコードで、重みGEMVをHBM-PIMへ、注意をSRAM-PIMへ割り当て、QKV生成と注意を重ねることがクリティカルパス短縮に寄与することを示す。SRAM-PIM側には55.3%のidle時間が残り、HBM-PIMの計算利用率は42%である。したがってすべての演算器が常に高稼働という主張はできない。SRAMとHBMの役割分担が適切でも、層ごとの負荷と同期で空き時間が生じる。

原著§VI-Cの多バッチ評価は、Qwen3-30B-A3BとPhi-mini-MoEを対象にHPIM-S-MBという派生構成を用いる。バッチ8〜32ではA100より低遅延だが、バッチ64〜128では優位性が縮み、**大きなバッチではA100が逆転する**。これはHPIMが単一バッチの低レイテンシを優先しており、データセンターの高スループット多バッチ推論へそのまま最適とは限らないことを示す重要な負の結果である。

原著§VI-Dの熱解析はDRAMsim3の拡張と有限要素法の組合せで、評価条件ではHBM3のピーク局所温度が44℃未満と推定する。これは電力・配置の仮定に依存する粗粒度の熱解析であり、実パッケージの熱測定ではない。特に4スタックHBM3とSRAMロジックの3D実装・配線・熱設計の難しさが完全に解消されたという保証ではない。

## 既存研究との差

IANUSはNPUとPIMを組み合わせて高い演算性能と帯域を狙うが、NPUの資源未利用やデバイス間通信が課題となる。CXL-PNMは外部メモリ近傍でGEMVを実行するが、CXLの帯域が制約となる。HPIMはHBM3内部の重み帯域とSRAM-PIMの低遅延・非線形演算を単一のコンパイラ・スケジューラで結び、**トークン内部の注意とGEMVの重畳**を中心に設計する点が異なる。

純粋なHBM-PIMは重みGEMVには向くが、SoftmaxやKVの不規則アクセスを効率よく処理しにくい。純粋なSRAM-PIMは低遅延だが巨大なLLMの重みを保持できない。HPIMは両者の得意な演算を分けるため、単一のメモリ技術では満たせない容量・帯域・低遅延・演算多様性の条件を両立させようとする。

GPU上のカーネル最適化やKVキャッシュ圧縮とは異なり、HPIMは新しいハードウェア構成そのものを提案する。従って既存のGPUへソフトウェアパッチを適用すれば同じ速度倍率が得られる手法ではない。LLM推論基盤の将来的なハードウェア設計として位置づけるべきである。

## 限界と実装上の注意

**実シリコンではなくシミュレーション。** SRAM-PIMのRTLを合成し、DRAMsim3拡張とNoCモデルで時間を推定するが、製造・実測されたHPIMシステムのE2E速度や消費電力ではない。23.1倍の速度比はこの評価系の条件付き結果であり、現行GPU上で再現できる数字ではない。

**バッチ1に最適化。** 主評価はバッチ1のFP16 OPTモデルであり、大きなバッチではHPIM-S-MBがA100に逆転される。多数の同時リクエストを扱うサービングでは、GEMMへの変化、HBM帯域共有、バッチスケジューリングを含めて再設計が必要となる。

**帯域・容量の比較条件。** HPIMのHBM3容量96GB・帯域3276.8GB/sはA100の80GB・1935GB/sと異なる。HPIM-Sによる低帯域比較はこの差を補うが、すべてのハードウェア資源を一致させたアブレーションではない。既存PIMとの比較でもNPUや外部接続の有無が異なるため、性能差のすべてを単一のパイプライン機構に帰属させない。

**モデル系列・精度の制約。** 主評価はOPT 350M〜30BのFP16であり、GQA/MQA、MoE、FP8/INT4重み、KV量子化、長文脈の現行LLMへの適用は直接評価されていない。単一バッチでの重みとKVの容量比は、モデル構成とコンテキスト長で変わるため、HBM側に重みを置く最適配置も変わり得る。

**熱・電力・面積の見積り範囲。** SRAM-PIM部分の252.9mm²と13.5W/1.2Wは、チップ全体の面積・消費電力ではない。HBM3、PHY、NoC、パッケージ、冷却、電源回路を含む実装コストは別に見積もる必要がある。熱解析も粗粒度のシミュレーションであり、実機の熱制約を完全に解決した証拠ではない。
