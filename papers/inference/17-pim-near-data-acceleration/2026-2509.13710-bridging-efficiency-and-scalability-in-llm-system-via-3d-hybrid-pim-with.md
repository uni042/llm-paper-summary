# CompAir：DRAMとSRAMのメモリ内演算を融合するLLM推論アーキテクチャ

## 概要

大規模言語モデルの推論では、モデル重みを大量に読み出す逐次復号と、多数の入力トークンを並列に処理する入力事前計算とで、計算装置に求められる性質が異なる。メモリ内演算（processing-in-memory、PIM）は重みや中間値の移動を抑えるが、DRAM上のPIMだけでは高バッチ時の行列演算性能が不足し、SRAM上のPIMだけではモデル重みを収める容量が足りない。両者を単に並置すると、DRAMからSRAMへ重みを移す通信が律速となる。さらにSoftmax、回転位置埋め込み、正規化のような非線形演算を中央の処理器へ集める方式では、長い文脈でバンク間の移動が増える。

CompAirは、この三つの問題に対応するため、DRAM-PIMバンクとSRAM-PIMの小型演算マクロを3次元ハイブリッド接合し、データ移動中に演算する2次元チップ内通信網（CompAir-NoC）を加える。利用者にはDRAMバンク単位の一斉実行に近い命令を見せ、内部ではパケットごとの処理経路へ変換する。対象はLLMの入力事前計算と逐次復号であり、単なる重み圧縮ではなく、メモリ階層、演算場所、通信、命令生成を一体設計したハードウェア研究である。

原著のサイクル精密シミュレーションでは、純DRAM-PIMのCENTを中心とした比較で、入力事前計算1.83～7.98倍、復号1.95～6.28倍の性能改善を報告する。GPUとHBM-PIMの混合方式に対しては、同程度の処理量の条件でエネルギー消費3.52分の1という比較も示す。ただし、**これらは構成・バッチ・文脈長・並列化方式を指定したアーキテクチャ評価であり、製造済みCompAirチップの実測値ではない**。またSRAMを増やせば常に省エネルギーになるわけではなく、接合面の転送エネルギーが増える場合もある。

## 問題設定

### 異なる演算形状とメモリの適性

入力事前計算（prefill）では多数のトークンをまとめて行列として処理できるため、重みを一度読み込んで複数の入力に使い回す行列積が中心となる。逐次復号（decode）では次の一トークンを繰り返し生成し、特に小バッチ時には重み読み出し量に対する演算回数が小さく、行列・ベクトル積がメモリ帯域で制約される。DRAM-PIMは大容量の重みを置きつつ比較的広い内部帯域を使える反面、高い演算密度を要求するバッチ処理には不利である。SRAM-PIMは小容量ながら近接した計算素子による高速な積和演算を実行でき、同じ重みを再利用する場面で有利になる。

しかし、SRAMだけで大規模モデルの重みを保持する案は、必要なマクロ数と面積・電力の面で成立しにくい。論文では70BモデルのQ/K/V投影だけでも192GBのSRAMが必要になる例を挙げ、重みをDRAMから供給し直すことを前提とする。そこでDRAMとSRAMを別デバイスや別チャネルに置くと、外部I/O帯域が先に飽和する。原著の例では、あるDRAMチャネルの内部帯域512GB/sに対して外部I/Oは32GB/sであり、小型SRAM-PIMでも演算器を使い切るには64GB/sの供給が必要になる。両者を**同じチャネルの同じバンクに近接配置すること**が設計上の出発点である。

また、注意の鍵・値行列は入力系列に応じて変化するため、全結合層の固定重みほどSRAM上で使い回せない。したがって「全演算をSRAM-PIMに寄せる」のではなく、全結合層のバッチ行列積をSRAM側、動的な注意行列をDRAM側に残す分担が必要となる。グループ化問い合わせ注意（grouped-query attention、GQA）のように鍵・値が複数頭で共有される場合は例外があり、最適な実行場所は系列長と並列化に依存する。

### 非線形演算と通信の結合

Softmaxの指数関数・総和、RMSNormの正規化、回転位置埋め込み（RoPE）の要素交換は、単純な行列積とは異なる粒度の演算を要求する。従来のDRAM-PIMでは専用の非線形演算器を中央の制御部に置き、バンクから値を送って処理して戻す設計がある。しかし、長文脈ではこの往復がボトルネックになり、論文の分析では非線形演算に伴う通信が全遅延の最大25%を占める条件がある。全バンクに専用演算器を複製すると面積負担が大きい。CompAirは通信網のルータを単なる中継器ではなく、小規模な計算地点として使う。

## 手法

### 1. バンク単位の3次元接合と列デコーダ分離

各CompAirデバイスは32チャネル、各チャネル16バンクを持つ。DRAM-PIMのバンクは32MBの記憶領域と16入力のBF16積和演算器を備え、その直下の論理ダイにSRAM-PIMマクロ4個と通信ルータ4個を配置する。バンク同士は1対1で接合され、バンクあたり256本の接合配線を介してデータを渡す。論文のシステム例では32デバイスをCXLスイッチで結び、装置間の点対点通信と集約通信を担わせる。非線形演算を装置ごとの中央制御器から除くことで、各チャネル内の通信網へ仕事を分散する。

SRAM側を積層するだけでは十分ではない。従来DRAM-PIMの列デコーダは、演算器を置くために読み出し幅を絞る場合があり、接合配線が広くてもDRAMから十分なデータを引き出せない。CompAirは列選択を分離し、SRAM向けの8:1デコーダとDRAM向けの4:1デコーダを設ける。これにより通常のDRAM操作を維持しつつ、SRAM側への重み供給を太くする。原著のLlama-13B例では、この再編成単独で端から端までの速度が1.15～1.5倍改善する条件を示す。改善の因果は「SRAM演算器の増設」ではなく、増設した演算器を空転させない供給帯域の確保にある。

SRAM-PIMの容量はバンクあたり4個の8KB相当マクロを基本とし、DRAMバンクの面積に収まる構成を採用する。SRAMへ置く重みは固定保持ではなく、対象演算ごとに書き込み、演算後に必要に応じて入れ替える。このため小バッチ時は重み再ロードの費用が利得を上回ることがあり、SRAM側が常に有利という仮定を置かない。

### 2. 演算場所の分担と通信経路

推論の全結合層では、バッチをまたいで同じ重みを再利用できるQ/K/V投影やFFNの大きな行列積をSRAM-PIMで処理する。一方、系列ごとに変化する鍵・値を使う注意の`QK^T`と`SV`は、通常の多頭注意ではDRAM-PIMを主に用いる。結果を他バンクへ送る必要があるときは、装置内の2次元メッシュ通信網が値を運び、途中のルータで部分的な計算を行う。どのバンクへデータを置くか、どの演算をSRAM側へ送るかは、再利用性と通信の交換条件で決まる。

CompAir-NoCは4×16の2次元メッシュで、各ルータにBF16対応のCurry ALUを2個配置する。通常のルータはパケットを受け取り、宛先へ送るだけだが、このALUは転送中の小さなデータ単位（フリット）を使って加減乗除を実行できる。例えばSoftmaxでは、各バンクが計算した部分結果を木構造で集約し、指数計算・総和の後に正規化情報を各バンクへ配る。中央の非線形処理器に全データを往復させる必要が減り、長文脈ほどこの違いが効く。

### 3. Curry ALUによる転送途中の非線形演算

Curry ALUの設計上の狙いは、複数入力が揃うまでルータ内で待つ一般的なデータフロー方式を避けることである。ルータの引数レジスタ（`ArgReg`）へ演算の固定引数や途中値を保持し、流れてくるフリットの値をもう一方の入力として単項演算に分解して処理する。これによりルータの転送パイプラインを大幅に伸ばさずに演算を付加する。演算命令と値をパケットに持たせるため、データの転送経路がそのまま演算順序を表す。

RoPEのように隣接要素を交換する操作は、ベクトルを大きな演算器へ送り直す代わりに、フリットの経路・交換操作として実装する。原著ではLlama2-7BのQまたはKの並べ替えをバンク当たり34サイクルで完了する例を示す。指数関数や平方根は単発の専用演算器ではなく、Taylor展開やNewton反復をルータ内の反復計算へ写像する。例えば指数計算は反復回数を`ArgReg`へ持たせ、乗算・除算・加算を段階的に実行する。近似精度と反復回数の設計が必要であり、任意の非線形関数を無料で実行できるわけではない。

総和・配布では、バンク単位の木構造を構成して中間結果を通信網内に保持する。16入力の総和なら4層の二分木として分割し、各段の部分和を次段へ渡す。中央演算器へ集めてから再配布するのと異なり、転送と集約が一体化するため、通信負荷の高い注意処理で効果が現れる。

### 4. 二階層の命令セットと自動経路生成

DRAM-PIMは多数のバンクへ同じ命令を出す単一命令・複数データ（SIMD）に向くが、ルータやSRAM-PIMを細かく使うには複数命令・複数データ（MIMD）の柔軟性が必要となる。全DRAMバンクに独立命令制御器を増設すると面積が増えるため、CompAirは利用者向けの行単位命令セット（Row-Level ISA）と内部のパケット単位命令セット（Packet-Level ISA）を分ける。

行単位には`SRAM_Write`、`SRAM_Compute`、`NoC_Scalar`、`NoC_Access`、`NoC_BCast`、`NoC_Reduce`、`NoC_Exchange`を用意する。例えば`SRAM_Write`でDRAMの重みをSRAMへ渡し、`SRAM_Compute`で入力を与えて行列演算し、`NoC_Reduce`でバンク間の部分結果を集約する。プログラマは行のアドレス、対象バンクのマスク、演算の種類を指定すればよい。

内部変換器は依存関係を解析し、ある`NoC_Scalar`の出力が次の`NoC_Scalar`の入力になるとき、各演算ごとにDRAMへ書き戻さず、複数処理を1つのパケット経路へ融合する。パケットが複数ルータを通る間に演算を順次適用し、最後に必要な結果だけ書き戻す。これにより制御をSIMD風に保ちながら、通信網の経路ごとの柔軟性を利用する。代償として、命令変換の正しさ、ルータ内のレジスタ使用、経路競合を管理する必要がある。

## 評価

### 評価方法・条件

論文のCompAir全体は**サイクル精密シミュレーション**である。DRAMと通信網はRamulator 2.0とBookSim、SRAM-PIMは既発表チップの仕様、デバイス間通信はCENTのモデルを利用した。通信ルータのRTLはSynopsys Design CompilerとUMC 28nmライブラリで合成し、面積を評価している。比較先は純DRAM-PIMのCENT、およびA100とHBM-PIMを組み合わせるAttAccである。GPU実機上の一般的なvLLM推論測定と読み替えない。

| 条件 | 論文の設定 |
|---|---|
| 対象モデル | Llama系列7B・13B・70B、Qwen-72B、GPT3-175B |
| 数値形式 | BF16（DRAM-PIM、SRAM-PIM、ルータ演算） |
| メモリ構成 | 32チャネル/デバイス、16バンク/チャネル、DRAM 32MB/バンク、SRAM-PIM 4マクロ/バンク |
| 通信網 | 4×16メッシュ、72ビットフリット、ルータあたりCurry ALU 2個 |
| 比較先 | CENT（DRAM-PIMのみ）、AttAcc（A100＋HBM-PIM） |
| 並列化 | デバイス数32・96の構成や、テンソル並列度1～32を検討。代表条件はTP=8 |

### 感度・構成要素除去・悪化条件

SRAM-PIMの効果はバッチ数に強く依存する。バッチ1では重み再ロード費用が高く、SRAMを追加してもDRAM-PIMより有利にならない。バッチが増えると全結合層の重み再利用が増え、性能差が拡大する。文脈長が伸びると鍵・値を扱う注意演算と非線形処理の比重が増え、SRAMによる全結合層高速化の相対利得は約2.5倍へ収束する一方、Curry ALUの通信削減が効きやすくなる。すなわち二つの機構は同じ負荷で同じ割合だけ効くわけではない。

並列度も単調増加ではない。テンソル並列度を1から32へ上げる実験では、各デバイスへ割り当てられる演算量が小さくなり、バンク利用率が落ちる。著者らは多くのモデルでTPを8以下にする範囲を適切と判断した。したがって「装置を増やせば速度が比例して伸びる」とは言えない。Curry ALUのみを加えたCENT、SRAM追加だけのCompAir_Base、列デコーダを最適化したCompAir_Optを比較する構成要素除去実験は、非線形演算、重み再利用、読み出し幅の寄与を分離する目的を持つ。

ルータの面積合成では、バンク当たりSRAM-PIMとルータを合わせて0.8195平方ミリメートルであり、対象DRAMバンクの積層面積に収まると報告する。Curry ALUの面積はルータ面積の2.94%にとどまる。中央の専用非線形演算器との比較では、非線形処理全体の遅延を約30%減らし、長文脈の遅延を約25%減らす条件がある。一方、SRAM-PIMの演算性能が入力帯域で制約される領域では、電圧を下げても遅延が変わらない境界が存在し、マクロ形状や幅の選択によって性能が変わる。

エネルギー評価は特に注意が必要である。SRAMとDRAMの間の転送が増えるため、CompAirの消費エネルギーは純DRAM-PIMより**増える場合がある**。A100＋HBM-PIMより低エネルギーという総括を、CENTより常に省エネルギーという主張へ拡張してはならない。グループ化問い合わせ注意（GQA）では鍵・値の共有により`QK^T`のSRAM実行が有利になる条件があるが、`SV`では依然DRAM-PIMのエネルギー優位が大きい。長文脈・高い並列度では接合面転送が増え、SRAM側の使用を増やすことが逆効果になる。

## 既存研究との差

CENTはDRAM-PIMを中心にCXLで複数デバイスを連携し、中央の非線形演算器を使う構成である。CompAirは同じDRAM-PIMの容量と内部帯域を活用しながら、バンクごとのSRAM-PIMを追加し、固定重みを再利用できる演算を近傍の高速演算器へ渡す。これにより高バッチ時の計算律速を解消しやすくする。さらにCurry ALUをルータへ分散させ、中央処理器への非線形演算往復と集約通信の混雑を減らす。単純な「DRAM-PIM＋SRAM-PIM」という足し算ではなく、列デコーダの再編成と経路を融合する命令変換が必要な点が特徴である。

AttAccはGPUとHBM-PIMを組み合わせる方式で、GPUの演算能力とPIMの帯域を使う。CompAirはGPUを前提としない構成を目指し、シミュレーション上で同程度の処理量をより低いエネルギーで実現する条件を示す。ただし、比較先の装置数やメモリ技術が異なり、実機ソフトウェア環境で同じAPI・モデル精度・電力測定条件を再現した結果ではない。したがってハードウェア費用、製造歩留まり、運用上の可用性まで含めた優位は未確定である。

## 限界・適用条件

第一に、**CompAir全体は製造された実機ではない**。DRAM、SRAM、NoC、デバイス間通信を別々の既存仕様とシミュレータで組み合わせた評価であり、実際の3次元接合、熱、クロック、実装配線、量産歩留まりが統合時にどうなるかは未検証である。ルータの論理合成は実施しているが、システム全体のシリコン実測を意味しない。

第二に、性能改善の大きさは負荷分布とモデル構造に依存する。バッチ1や重み再利用の少ない注意演算ではSRAMを使う効果が薄い。極端に大きいテンソル並列度ではバンク利用率が低下する。GQAのような鍵・値共有方式は実行場所の最適解を変え得る。論文で試したLlama、Qwen、GPT3の範囲を超えたMoEのエキスパート配置や投機的復号、実サービスの到着分布について同じ倍率を保証できない。

第三に、性能とエネルギーの交換条件がある。SRAM-PIMを増やすと重み再利用で速くなる場合がある一方、DRAMとの転送が増えてエネルギーが悪化する。通信網のCurry ALUも、関数近似の反復回数、経路競合、演算順序によって負担が変わる。原著のハードウェア合成とサイクル精密モデルは有力な設計根拠だが、製造・運用・ソフトウェアスタックの最終検証を置き換えない。

第四に、量子化やモデル品質の変化を比較した論文ではない。BF16を用いた演算性能とメモリ構成の研究であり、回答正確性や学習済みモデルの精度改善を示すものではない。推論トークン速度と応答品質、事前計算と逐次復号、シミュレーションと実測を区別して読む必要がある。
