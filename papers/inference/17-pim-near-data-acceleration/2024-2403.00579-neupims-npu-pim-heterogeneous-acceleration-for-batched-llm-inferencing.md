# NeuPIMs: NPU-PIM Heterogeneous Acceleration for Batched LLM Inferencing

## 概要

NeuPIMsは、複数の大規模言語モデル（LLM）推論要求をまとめて処理するとき、行列積中心の計算と注意機構のメモリ帯域中心の計算が交互に現れる問題を、ニューラル処理装置（NPU）とメモリ内処理（PIM）の異種構成で改善するシステム研究である。Transformer復号器のQKV射影と前向きネットワークは、バッチをまとめると行列同士の積（GEMM）になり、演算器の性能を活用しやすい。一方、各要求の過去トークンに対する注意計算は、長い鍵値キャッシュを読む行列ベクトル積（GEMV）となり、メモリ帯域が律速になりやすい。

NPUは大きなGEMMを得意とするが、低算術強度のGEMVでは演算器が遊びやすい。PIMはメモリ近傍でGEMVを実行して帯域を有効利用できるが、GEMMのような計算量の大きい処理は苦手である。両者を単純に接続しても、メモリ操作とPIM操作が排他的に動く従来の構成や、同じ要求の層内データ依存によって片方が待機する。

NeuPIMsは二つの対策を組み合わせる。ハードウェアではDRAMの各バンクに通常メモリアクセス用とPIM演算用の二つの行バッファを持たせ、両者の操作を重ねられるようにする。実行時にはバッチを独立した二つの小分けバッチへ分け、一方がNPUでGEMMを実行する間、もう一方がPIMで注意のGEMVを処理する。シミュレータによる評価ではGPUのみの構成に対して最大約3倍、NPUのみの構成に対して約2.4倍、単純なNPU＋PIM統合に対して約1.6倍の処理量改善を報告する。

## 問題設定

LLMの復号器ブロックは、QKV生成、複数頭注意、前向きネットワークからなる。QKVと前向きネットワークの重みはバッチ内の複数要求で共通なので、要求数が増えるほど重みを再利用した行列同士の積として処理しやすくなる。一方、注意機構は要求ごとに異なる過去トークンの鍵値キャッシュを参照するため、バッチ間で同じ鍵値を共有できない。長い履歴を読むとメモリ帯域が支配的になる。

論文はGPT-3の13B・175Bを例に屋根線モデルを用い、入力をまとめて処理する段階では行列積が計算律速、自己回帰で1トークンずつ生成する段階では帯域律速になりやすいことを示す。GPUだけで処理すると、重みや鍵値を保存する容量はほぼ使い切る一方、計算器の利用率は40%未満となる例がある。単に演算器のピーク性能を上げても、帯域制約を解決できない。

PIMを加えれば注意のGEMVをメモリ近傍へ移せるが、二つの障害が残る。第一に、従来のPIM装置は通常のメモリ読書きとPIMコマンドを排他的に実行するため、NPUが重みを読む間にPIMが停止しやすい。第二に、同じ要求のQKV出力が注意の入力になるので、単一要求のGEMMとGEMVを任意に同時実行できない。NeuPIMsはこのハードウェア側とアルゴリズム側の制約を別々に解く。

## 手法

### 1. GEMMとGEMVの装置割当

NPUは複数のシストリック配列を持つ計算中心のアクセラレータとして構成し、QKV射影、出力射影、前向きネットワークの行列積を処理する。PIMはDRAMバンク近傍に計算機能を持たせ、鍵値キャッシュを参照する注意の行列ベクトル積を担当する。各装置の得意な演算へ仕事を割り当てることで、計算能力とメモリ帯域の両方を活用する。

ただし同じメモリ空間を共有するだけでは、PIMとNPUの操作が交互になり、片方の装置が遊ぶ。したがって単純な異種統合を比較対象に置き、装置割当だけでなく並列実行を可能にする追加の仕組みを導入する。

### 2. 二重行バッファによるメモリ操作の並行化

従来のPIMでは、通常のメモリアクセスとPIM演算のために同じ行バッファを利用し、モード切替が必要になる。NeuPIMsはDRAMの各バンクへ二つの行バッファを設け、通常の読書きとPIM演算を別の経路で扱う。これによりNPUが通常メモリアクセスを行う間も、PIM側で行列ベクトル積を進められるようにする。

この設計では行バッファを二つにするだけでなく、メモリコントローラが通常のDRAMコマンドとPIMコマンドを混在させ、DRAMのタイミング制約を破らないよう発行する必要がある。論文は行の活性化待ちを抑えるためにコマンドの配置を工夫し、複数のGEMV操作をまとめる複合コマンドを追加して制御費用を償却する。通常アクセスとPIMの並行化は物理的なメモリ資源の衝突を緩和するための対策である。

### 3. 小分けバッチの交互実行

同じ要求ではQKV生成の後で注意を計算するため、依存関係を無視してGEMMとGEMVを同時実行できない。そこでバッチを二つの独立した小分けバッチに分割する。小分けバッチAがNPUでQKVや前向きネットワークを処理している間に、小分けバッチBはPIMで注意を計算する。次の段階で役割を入れ替え、両装置に仕事を供給し続ける。

この方式は単一要求内の依存を消すのではなく、異なる要求群の独立性を利用するパイプラインである。複数要求が同時に存在しなければ重ね合わせる仕事がなくなるため、単一要求の遅延が必ず大幅に改善する仕組みではない。対象はバッチ化された提供処理のスループットである。

### 4. 系列長を考慮した小分けバッチの分割

注意計算の時間は各要求の履歴長に依存する。二つの小分けバッチの要求数を同じにしても、一方に長文脈の要求が集中すればPIMの処理時間が偏り、NPUとのパイプラインが待ち状態になる。NeuPIMsは系列長からPIMの注意計算時間を推定し、二つの小分けバッチの系列長の合計が釣り合うよう要求を割り当てる。

この負荷均衡は単純な要求数の均等分割ではない。実行時に各要求の系列長を追跡し、反復単位のスケジューリングで新規要求の追加と終了要求の削除を扱う。各反復で装置間の仕事量を近づけることが、二重行バッファのハードウェア並行性を処理量へ変えるために必要になる。

### 5. 既存の提供基盤との接続

NeuPIMsは反復単位のバッチ更新や、鍵値キャッシュをページ単位で管理する既存の提供基盤の考え方を利用する。要求の開始・終了が不定期に起きても、反復境界でバッチを組み直し、メモリ領域を効率的に確保する。ページ化した鍵値キャッシュは大きな連続領域を事前予約する必要を減らし、より多くの要求を同時に保持できる。

装置間の演算割当、二重行バッファ、コマンドスケジューリング、小分けバッチの負荷均衡が協調して初めて効果が出る。単にNPUを速くしたりPIMを追加したりするだけでは、別の装置が待機する問題が残る。

## 評価条件

| 項目 | 条件 | 比較上の注意 |
|---|---|---|
| モデル | GPT-3系の4規模 | 現代のMoEや別の注意方式を網羅するものではない |
| 負荷 | ShareGPT、Alpacaの入力・出力系列長分布 | 実際の要求文を使うがハードウェアはシミュレーション |
| NPU | シストリック配列を持つ計算中心装置 | ONNXimを基にモデル化 |
| PIM | DRAM内の行列ベクトル演算器 | DRAMsim3を基にした独自PIMシミュレータ |
| 比較対象 | GPUのみ、NPUのみ、単純なNPU＋PIM統合 | 提案は二重行バッファと小分けバッチ交互実行を追加 |
| 主指標 | 処理量、NPU・PIM利用率、バッチ構成の効果 | GPU上の実測トークン毎秒ではない |

論文はNeuPIMsのシミュレータを著者リポジトリで公開している。したがって「実機GPUで3倍を測定した」という説明は不正確であり、比較対象もシミュレーション上の装置構成である。DRAMのタイミング、PIMコマンド、シストリック配列の性能をモデル化したシステム評価として読む必要がある。

## 主要結果

### 1. 処理量の改善

| 比較基準 | NeuPIMsの報告改善 | 説明 |
|---|---:|---|
| GPUのみ | 最大約3倍 | 帯域中心の注意をPIMへ移し、演算中心の処理をNPUへ割当 |
| NPUのみ | 約2.4倍 | NPUが苦手なGEMVをPIMへ分担 |
| 単純なNPU＋PIM統合 | 約1.6倍 | 二重行バッファと小分けバッチ交互実行の追加効果 |

比較基準ごとに装置構成が異なるため、3倍、2.4倍、1.6倍を掛け合わせて総合改善率を計算してはならない。最も重要なのは単純統合比1.6倍であり、異種装置を同時実行できるようにした設計の寄与を示す。GPUのみとの3倍は、装置のアーキテクチャと実行方式を同時に変えた比較である。

### 2. 装置利用率

論文はNPU・PIMの計算利用率が、単純な統合構成ではそれぞれ約28%・17%だったのに対し、提案構成では約65%・26%へ改善したと報告する。二重行バッファによってメモリ操作の排他制約を緩めても、同じ要求内の演算依存が残るため、独立した小分けバッチを交互に実行する必要がある。二つの工夫が別々の待機要因を減らすことで、処理量の改善につながる。

利用率はピーク演算能力に対する割合であり、要求の応答時間そのものではない。NPUの利用率が上がっても、PIM側の系列長が偏れば待機が残るため、負荷の分割とタイミング制御が重要になる。

### 3. GPUのみの構成での制約

論文はRTX 3090 24GBとA100 40GB上の複数LLMを例に、GPUの容量利用率がほぼ100%に近い一方、計算器の利用率が40%未満にとどまることを示す。容量が不足するためGPU台数を増やしても、帯域と計算の不均衡が残る場合がある。これはPIMによる鍵値キャッシュ近傍の演算を導入する動機であり、GPUの演算器を増やすだけでは解決しにくい問題を示している。

### 4. 系列長分布とバッチ分割の影響

注意処理時間は履歴長に依存するため、同じ要求数の二分割でも仕事量が等しいとは限らない。NeuPIMsは小分けバッチ内の系列長の合計を揃えるよう割当を調整し、PIMが一方の長い系列を処理する間にNPUが遊ぶ状態を減らす。短い要求と長い要求が混在する提供負荷では、このような長さを意識した分割が特に重要になる。

ただし小分けバッチが小さすぎるとNPUのGEMMが小規模になり、計算効率が低下する可能性がある。逆に大きすぎると独立した仕事を重ねる余地が減る。提案は要求数だけでなく系列長を用いて、この交換条件を調整する。

## 既存研究との差

既存のGPU中心の提供基盤は、連続バッチや鍵値キャッシュのページ管理によって要求を効率よくまとめる。一方、注意演算のメモリ帯域制約とGEMMの計算特性の違いは残る。NeuPIMsは演算の種類に応じてNPUとPIMへ分担することで、メモリ近傍の演算能力を直接活用する。

単純なNPU＋PIM統合と比べると、二重行バッファによる通常メモリ操作とPIMコマンドの並行化がハードウェア側の違いであり、小分けバッチ交互実行がソフトウェア側の違いである。両者を合わせて装置間の待機を減らす点が研究の中核となる。単一カーネルの最適化や単なるモデル圧縮ではなく、メモリ装置と実行スケジュールの協調設計である。

## 限界と実運用上の注意

結果は主としてシミュレータに基づくため、実機製造後の配線・電力・熱・DRAM歩留まり・コントローラ実装などの費用を含めた評価ではない。PIM用の二重行バッファとコマンド拡張は既存の市販GPUへソフトウェア更新だけで追加できるものではない。RTX 4070級の個人向けGPUや一般的なCPUオフロードへそのまま導入できる仕組みではない。

またバッチ間の独立性を利用するため、同時要求数が少ない場合は重ね合わせる仕事が不足し、処理量の利得が小さくなり得る。推論の総処理量を増やすことと単一要求の最初のトークン遅延を短くすることは異なる。系列長分布が偏るとPIM処理時間も偏り、負荷均衡の精度が性能へ影響する。

対象モデルは当時のGPT-3系であり、混合専門家、最新の注意カーネル、分散プリフィル・復号分離などを含む現代の提供基盤全体を検証したわけではない。3倍の処理量を最新のH100や別世代のPIMへそのまま外挿できない。評価の再現には著者の公開シミュレータ、装置モデル、系列長トレースの条件を確認する必要がある。
