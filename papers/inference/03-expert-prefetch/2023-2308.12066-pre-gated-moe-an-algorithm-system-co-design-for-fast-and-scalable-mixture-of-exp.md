# Pre-gated MoE: An Algorithm-System Co-Design for Fast and Scalable Mixture-of-Expert Inference

> 次layerのrouting判定を1 block前で行い、必要expertを早めに確定してCPU→GPU転送を現在blockの計算と重ねることで、expert weight待ちを減らすMoE offload方式。

## 概要

Pre-gated MoEは、GPUへ全expertを常駐できないMoEで、**router結果が出るまで次expertのweight transferを始められない**という逐次依存を壊す手法である。

通常はblock `N` のgateでそのblockに必要なexpertが分かり、その直後にexpertを実行する。CPU offloadではこの順序だと、gate後のCPU→GPU転送がそのままGPUの待ち時間になる。

提案はgateの役割を1 block前へずらし、block `N` の計算中にblock `N+1`で必要になるexpertを確定する。これにより、次layer expertのweight transferを現在blockのexpert / non-expert計算と同時に進められる。

重要なのは、これは**将来expertを統計的に当てる軽量predictorではない**点である。モデル構造側のrouting位置を変更し、次layerで使うexpertを実際のrouter判断として早く確定するalgorithm-system co-designである。

対象はSwitch Transformer系。expertはCPU DRAM、dense/non-expert weightはGPUに置く。SSD/NVMe、KV cache offload、CXL/HBFは扱わない。

## 手法のあらまし

### 1. 従来の逐次依存

CPU-offloaded MoEでは通常、

`Gate → expert selection → CPU→GPU weight transfer → expert GEMM`

の順になる。

expert selectionが終わるまで何を転送すべきか分からないため、PCIe transferを早く開始できない。

### 2. `Pre-gate`：次blockのroutingを前倒しする

Pre-gated MoEではblock `N` 内で、block `N+1`用のexpert selectionを先に実行する。

その結果が出た時点で、次blockで必要なexpert weightをCPU DRAMからGPUへ非同期prefetchする。

現在blockのexpert計算やnon-expert計算が続いている間に転送を進めるため、次block開始時にはweightが到着していることを狙う。

### 3. OnDemand / Prefetchとの違い

論文では主に3方式を比較する。

| 方式 | いつ転送するか | 何を転送するか | 問題 |
|---|---|---|---|
| MoE-OnDemand | 現blockのgate後 | 選択expertのみ | GPUが転送完了を待つ |
| MoE-Prefetch | gate前 | 次blockの全expert | 不要expertまで大量に転送する |
| Pre-gated MoE | 1 block前のpre-gate後 | 次blockで実際に必要なexpert | 必要量だけを早めに転送できる |

つまり、**必要expertだけを選ぶ精度を保ったまま、転送開始だけを早める**のが狙いである。

### 4. 先読み距離 `N`

標準は1 block先を読む `N=1`。

より遠い `N=2/3` も評価しているが、古いhidden stateから遠いlayerのroutingを決めるほど本来のroutingとのずれが大きくなるため、距離を伸ばせば無条件に良くなるわけではない。

`N=1` は、現在blockの計算時間を転送に使える一方でrouting品質も保ちやすい実用点として扱われる。

### 5. 初回・最終blockの扱い

最初のMoE blockには前段pre-gateがないため通常処理が必要になる。

最終blockでは次blockのprefetchが不要である。

したがってmodel中央ではpre-gatingを使い、端部だけ通常gate相当の処理を残す。

### 6. 実装

NVIDIA FasterTransformerを拡張し、gate、CPU→GPU expert transfer、expert GEMM、non-expert computationを別々に進められるGPU実行queueとCPU側bufferを使って同時実行する。

expert本体はCPU DRAMに保持し、GPUには実行中・直近必要なexpertだけを置く。

## 評価

### まず見るところ
- **結論:** routingを1 block早く確定すると、CPU offloadのPCIe待ちをかなり隠せる。
- **速度:** OnDemand比でend-to-end約1.5〜1.6倍。GPU-only throughputの約81%まで回復。
- **品質:** `N=1`では通常MoEとほぼ同等。統計predictorでexpertを近似する方式とは異なる。
- **メモリ:** peak GPU memoryはGPU-onlyの約23%。Large-128のような単一GPUに収まらない構成も実行可能。
- **注意点:** Switch系構造に依存し、一般的なdecoder-only MoEへそのまま適用できるとは限らない。

### 実機環境

| 項目 | 設定 |
|---|---|
| CPU | AMD EPYC 7V12 64-core |

| Runtime | FasterTransformer拡張 |

### Models / tasks

| 項目 | 内容 |
|---|---|
| Models | Switch Base-8 / 64 / 128 / 256、Large-128 |
| Tasks | XSum、CB Web QA、SQuAD |
| Baselines | GPU-only、MoE-OnDemand、MoE-Prefetch |

### 単一MoE block

| 比較 | 結果 |
|---|---:|
| vs MoE-OnDemand | 平均約1.7×、最大約1.9×高速 |
| vs MoE-Prefetch | 平均約42×、最大約125×高速 |
| GPU-onlyとの差 | 平均約19%の追加遅延 |

全expertを先に読むMoE-Prefetchは、expert数が増えるほど不要転送が支配的になる。

### End-to-end throughput

Switch-Base群では平均約111 tokens/sで、

- MoE-OnDemand比：約1.5×
- MoE-Prefetch比：約27×
- GPU-onlyの約81%

まで回復した。

GPU-onlyがOOMになるLarge-128でも約42 tokens/sで動作し、OnDemand比約1.6×、Prefetch比約52×。

### GPU memory

peak GPU memoryはGPU-onlyの約23%、すなわち約4.2×削減。

OnDemandとの差は約0.2%に留まり、prefetchのために大きな追加cacheを必要としない。

### 品質

SQuADでは `N=1` のPre-gated MoEは通常MoEとほぼ同等。

| Model | 通常MoE EM / F1 | Pre-gated N=1 EM / F1 |
|---|---:|---:|
| Base-8 | 77.4 / 85.8 | 78.2 / 86.0 |
| Large-128 | 82.4 / 90.1 | 81.9 / 90.2 |

差は小さく、主要な改善源は近似ではなくtransfer overlapである。

### 制約

- Switch Transformer中心。
- batch=1中心。
- CPU DRAMに全expertを保持できる前提。
- A100 + FasterTransformerのサーバ環境。
- SSD/NVMe、KV offload、continuous batchingは未評価。
