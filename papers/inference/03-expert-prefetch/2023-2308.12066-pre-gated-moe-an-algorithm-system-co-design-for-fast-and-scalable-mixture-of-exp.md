# Pre-gated MoE：次層の専門家を先に選び、CPUからGPUへの重み転送を計算と重ねる

## 概要

Pre-gated MoEは、混合専門家モデル（Mixture-of-Experts、MoE）をGPUメモリより大きな規模で動かす際、CPU主記憶から専門家重みを読み込む時間を削減するための、モデル側のルーティング変更と実行系の協調設計である。通常のMoEでは、ある層のルータがその層で実行する専門家を選ぶため、ルータの計算が終わるまで必要な重みを確定できない。専門家の重みをCPUへ退避した場合、選択が終わってからCPU→GPU転送を開始し、その後で専門家を実行する逐次依存が生じる。Pre-gated MoEは第n層の事前ゲート（pre-gate）が第n+1層で使う専門家を先に選ぶようにモデルを微調整し、第n層の専門家演算中に次層の重みを転送する。

著者らは単一のA100 80GBと大容量CPU主記憶を使い、SwitchTransformerの複数規模を評価した。Switch-Baseの構成全体で平均111トークン/秒、必要時だけ重みを読むMoE-OnDemandに対して平均1.5倍、各層の全専門家を先読みするMoE-Prefetchに対して平均27倍の処理量を報告する。105.6GBのSwitch-Large・128専門家では、GPU常駐方式が容量不足で実行できない一方、Pre-gated MoEは42トークン/秒で実行した。GPUメモリを無限と仮定する理想比較方式の処理量に対してSwitch-Baseでは81%に達するが、理想GPUのみの方式と同じ物理条件で比較できたという意味ではない。モデル品質は同じ事前学習済み重みから同じ回数の微調整を行った通常MoEと比較しており、全課題で完全一致したわけではない。

## 問題設定

MoEの計算量は各トークンが活性化する少数の専門家に依存するが、重みをGPUへ常駐させるときの必要容量は全専門家に依存する。専門家数が増えるほど、計算量の増加よりも重み容量の増加が大きくなり、GPUに収まらなくなる。単一GPUに置けない重みをCPUへ退避すると、各層のルータの決定を待ってから専門家を転送する時間が露出する。MoEの疎性は「転送する専門家が少ない」という利点を持つが、「どの専門家が必要かが実行直前まで分からない」という障害も生む。

従来の必要時転送（MoE-OnDemand）は選ばれた専門家だけをGPUへ載せるためメモリ効率が高い。しかし、ルータ決定、転送、専門家実行が直列になり、GPUが転送待ちをする。先読み（MoE-Prefetch）は転送を早められるが、次層でどの専門家が必要か分からないため全専門家を載せる必要があり、CPU―GPU帯域を浪費し、GPUメモリ消費も大きい。GPU常駐方式は転送待ちがない理想的な性能上限だが、専門家総容量が80GBを超えるモデルでは実行できない。

Pre-gated MoEの研究上の問いは、実行時のルータ選択を「現在層から次層へ」移動することで、転送対象を正確に先に確定できるか、そして微調整後のモデル品質を保てるかである。単なる過去の専門家頻度から次層を予測するのではなく、モデル内のゲート自体を次層の選択に合わせて学習する。したがって元モデルのルーティング決定を完全に不変のまま保持する方式ではない。微調整の必要性と、遠い層の選択を早く決めるほど品質が落ちやすい点を含めて評価する必要がある。

## 手法

### 1．次層の専門家を選ぶ事前ゲート

通常のMoEブロックでは、現在の隠れ状態をゲートへ入力し、そのブロックの専門家を選択する。事前ゲートは同じ位置の隠れ状態から、**次のMoEブロックで実行する専門家のマスク**を出力するように役割を変更する。第n層で得た選択結果は第n+1層の専門家演算に使われる。選択結果を生成する段階と、その結果に従って専門家を実行する段階の依存を層をまたぐ関係へ変えるため、第n層の演算と第n+1層の専門家転送を並行して進められる。

ここで、事前ゲートは次層の選択を固定するための学習済み関数であり、現在層のルータ結果を単に一層前へキャッシュする仕組みではない。次層の隠れ状態がまだ完成していない段階で選択するため、通常のルータと同じ専門家を必ず選ぶとは限らない。著者らは公開済みSwitchTransformerの事前学習重みを使い、通常MoEと事前ゲート版を同じ微調整条件で比較した。したがって「既存重みを使える」は「学習なしでルーティングを変更できる」と同義ではない。

最初のMoEブロックでは前層の事前ゲートが存在しないため、通常のルーティングと同じ流れを使う必要がある。以後のブロックで事前ゲートを連続して使い、次層の専門家マスクを先に生成する。事前ゲートを二層・三層先へ伸ばす実験も行われたが、隠れ状態から遠い層の専門家を選ぶほど、現在の情報と将来の必要専門家の関係が弱くなり、品質が低下する傾向がある。標準設定は一層先を選ぶN=1である。

### 2．CPUに全専門家重みを置く実行系

実行系では、注意機構や正規化などの非専門家重みをGPUに常駐させ、専門家重みの全体をCPU主記憶へ置く。各層で実際に活性化する専門家だけをCPUからGPUへ転送するため、専門家総数が多くてもGPU上の一時容量は活性専門家数に近い。GPU側には現在層の専門家と、先読み中の次層の専門家が一時的に共存する。したがってピークメモリは、非専門家重みの容量に、隣接する二つの層の活性専門家重みを足したものが主成分になる。全専門家を一度にGPUへ載せる必要はない。

第n層の事前ゲートが次層のマスクを生成すると、実行系は次層の活性専門家のCPU→GPU転送を非同期に開始する。GPUでは第n層の現在専門家と非MoE演算を進める。次層の実行時点までに転送が終われば、転送待ちは隠れる。重み転送時間が現在層の演算時間より長い場合、差分の待ち時間は残る。事前ゲートは転送対象を早期に確定する仕組みであり、PCIeの物理帯域を増やすわけではない。

CPU側の重みをGPUへ搬送する方式は、GPUメモリを削減する一方でCPU主記憶の容量と帯域を必要とする。論文の実験機は1.8TBのDDR4を備えるため、一般的な32GBのPCで105.6GBのモデルを同様に動かせることを示すものではない。非専門家重みや活性値、実行中の一時バッファもGPUメモリを使う。したがって「GPUメモリを約4倍節約」は「必要GPUメモリが常に四分の一以下」という普遍的な法則ではない。

### 3．転送時間を計算と重ねる条件

通常の必要時転送の一層の時間を、ルータ選択、選択済み専門家の転送、専門家計算の合計と考える。Pre-gated MoEでは次層のルータ選択を前層に移すため、転送と前層の計算を重ねられる。概念的には、次層へ移るまでに残る転送待ちは「次層の必要重み転送時間から、前層の重ね合わせ可能な計算時間を引いた正の部分」となる。ただしこの単純な差分は非MoE演算、バッファの割当、転送起動費用などを省略した説明であり、論文の全実行時間をその式だけで再現するものではない。

転送する専門家が少ないほど、重ね合わせ可能な計算時間で転送を隠しやすい。逆に、活性専門家の数を増やして密モデルに近づけると、転送量が増えてGPU常駐方式との性能差が広がる。MoE-Prefetchとの差は縮むことがある。これは、全専門家を事前転送する方式が、活性専門家数の増加に伴って「無駄な転送」が相対的に減るためである。論文図14は、64専門家中の活性数を1、4、16、32、64と増やす実験でこの限界を示す。

### 4．キャッシュとの関係

著者らはGPU上へ一部の専門家を常駐させるキャッシュを追加し、最近使用、頻度、スタック型の置換方針も比較した。キャッシュは繰り返し使われる専門家の再転送を減らせるが、その分だけGPUメモリを占有する。事前ゲートで次層の転送を先に始められる場合、単に頻度の高い専門家を常駐させるだけでは得られない転送・計算の重ね合わせを利用できる。両者は排他的な設計ではなく、GPUメモリ予算と要求分布に応じて併用する余地がある。

## 評価

### 1．評価機器・モデル・比較対象

論文第V節は、AMD EPYC 7V12 64コアCPU、DDR4主記憶1.8TB、NVIDIA A100 80GBを1基、PCIe Gen4の理論転送帯域32GB/sを持つ機器を使う。GPU常駐、必要時転送（MoE-OnDemand）、全専門家先読み（MoE-Prefetch）、Pre-gated MoEを比較する。GPU常駐は全モデル重みがGPUへ収まると仮定する性能上限として用い、105.6GBのSwitch-Largeでは実機GPUの容量を超えるため実行不能である。

モデルはSwitch-Baseの8・64・128専門家、Switch-Largeの128専門家を主に使い、追加の容量実験でSwitch-Baseの256専門家も扱う。原著表Iの重み容量はSwitch-Baseの8専門家が2.8GB、64専門家が15.2GB、128専門家が30.0GB、Switch-Largeの128専門家が105.6GBである。これらは重み容量の比較であり、KVキャッシュや一時活性を含む実行時ピークメモリとは区別する。品質評価はXSumの要約、CB Web QAとSQuADの質問応答を用い、ROUGE-1/2、完全一致率、F1を比較する。

### 2．遅延と処理量

原著図10では、単一MoEブロックの遅延がMoE-OnDemand比で平均1.7倍、最大1.9倍短くなり、MoE-Prefetch比で平均42倍、最大125倍短くなる。MoE-Prefetchは活性化しない専門家まで転送するため、専門家数が増えるほど転送費用が増える。GPU常駐の理想構成に対しては、Switch-Baseでブロック遅延の追加費用を小さく抑えるが、完全に同じ時間にはならない。

原著図11の全体処理量では、Switch-Base構成群の平均が111トークン/秒、MoE-OnDemand比1.5倍（最大1.6倍）、MoE-Prefetch比27倍（最大55倍）である。理想GPU常駐方式の81%に達するという記述はこのSwitch-Baseの処理量に関する比較であり、GPUメモリ使用量が81%という意味ではない。Switch-Large・128専門家では42トークン/秒で、MoE-OnDemand比1.6倍、MoE-Prefetch比52倍を報告する。GPU常駐方式は105.6GBの重みが80GBに収まらず、速度の実測比較ができない。

### 3．メモリ容量と品質

図12では、専門家重みをCPUへ置く三方式がGPU常駐よりピークメモリを減らす。MoE-Prefetchは全専門家を転送するため、GPU常駐時のピーク容量の平均51%を使う。MoE-OnDemandは活性専門家だけを転送するため最も低容量で、Pre-gated MoEは次層の先読み分があるものの、MoE-OnDemandよりわずか約0.2%高い程度に抑えたと報告する。本文のGPU常駐比約4.2倍の削減は対象モデルと指標に依存し、すべての層やモデルで固定比率ではない。

原著表IIの品質比較では、Switch-Base 8専門家のXSum ROUGE-1が通常34.6、Pre-gated 34.7、CB Web QA完全一致率が26.0から28.2、SQuAD完全一致率が77.4から78.2となる。一方、Switch-Base 128専門家ではXSum ROUGE-1が38.1から38.0、CB Web QA完全一致率が27.4から25.8に低下する。Switch-Large 128専門家ではXSum ROUGE-1が40.2から40.1、CB Web QA完全一致率が31.0から30.5、SQuAD完全一致率が82.4から81.9となる。全モデル・全課題で品質が改善したわけではなく、概ね近い成績を維持したというのが適切である。

### 4．負の結果と構成依存

原著図13では、次の一層を選ぶN=1が、二層・三層先を選ぶN=2/3より品質を保ちやすい。早い選択ほど転送に使える時間が増える可能性があるが、将来層の専門家選択を現在の隠れ状態だけで決めることは難しくなる。図14では、64専門家のうち活性化する数を1から64へ増やすと、すべてのCPUオフロード方式がGPU常駐に対して不利になる。活性数が増えれば転送量が増え、Pre-gated MoEの利得は疎性の低下とともに縮む。

図15はGPUキャッシュを併用した場合の処理量を示し、1%、10%、20%の専門家をGPUへ残す設定と複数の置換方針を比較する。キャッシュを増やせば必ず性能が単調改善するとは限らず、残す専門家の選択とGPU容量の交換条件がある。GPU常駐を含む全方式が、専門家数、活性率、モデルの層数、PCIe帯域に応じて異なる性能を示すため、単一の最大倍率だけを用いて導入可否を判断すべきではない。

## 既存研究との差

MoE-OnDemandは選択済み専門家だけを転送するので容量効率が高いが、ルータ決定後に転送するため待ち時間が露出する。MoE-Prefetchは次層を早めに転送するが、必要な専門家を知らないため全専門家を先読みし、帯域とGPUメモリを浪費する。Pre-gated MoEは**モデルのルーティング依存そのものを層間へ移動する**ことで、必要な専門家だけを前層の計算と重ねて転送できる。単純な専門家人気度の予測、LRUキャッシュ、静的配置とは異なり、モデル側の学習済み事前ゲートと実行時の転送制御を一体として設計している。

この設計は、現在層の専門家選択を完全に保持したまま実行時だけ最適化する方式ではない。次層の専門家を先に選ぶため、ルータを微調整し、品質を評価し直す必要がある。したがって、学習済みMoEをそのまま動かすオフロードエンジンとの比較では、速度だけでなく微調整費用と品質差も含めるべきである。単一GPUのCPU―GPU転送を対象とする研究であり、多数GPU間の専門家配送を最適化する分散MoE研究とは問題の中心が異なる。

## 限界

第一に、実験機はA100 80GBと1.8TBのCPU主記憶を備える。単一GPUで巨大モデルを動かせることを示すが、CPUメモリ32GB、GPUメモリ12GBの一般的なPCでSwitch-Large 105.6GBをそのまま実行できることを意味しない。CPU側に全専門家重みを保持する容量、PCIe帯域、非専門家重みとKVキャッシュのGPU占有を別途見積もる必要がある。

第二に、事前ゲートの導入にはモデルの微調整が必要である。通常のMoEと同じ事前学習重みから同じ回数の微調整をした評価では品質は概ね近いが、CB Web QAなどで低下した条件もある。二層・三層先を予測すると品質がさらに悪化するため、転送開始を早めるほどよいわけではない。既存の商用MoEへ学習なしで適用できる保証はない。

第三に、活性専門家が多い場合やPCIe帯域が不足する場合には、前層の計算時間だけでは次層の重み転送を隠せない。モデルが密な計算へ近づくほど、必要時転送も事前転送も不利になり、GPU常駐方式との差が広がる。図14の負の結果は、疎性の高いMoEを対象とする設計の適用範囲を示している。

第四に、評価は主にSwitchTransformerと単一A100で行われた。最新の共有専門家、複数トークンのTop-k、異なるルータ、複数要求をまとめる連続バッチ化、NVMeからの専門家直接ロード、複数GPUの分散通信で同じ倍率になるとは検証されていない。実装時には事前ゲートの学習、CPUメモリ容量、転送の重ね合わせ、品質を独立に測る必要がある。

さらに、専門家の転送時間を前層の計算へ重ねるには、転送用の一時領域が確保され、転送が実際に非同期で進むことが必要である。GPU側のメモリ割当や実行順序が転送を妨げる場合、事前ゲートが正しい専門家を選べても待ち時間は残る。原著の評価は転送と演算を重ねられる実行系を含むため、モデルのゲートだけを変更しても同じ高速化にはならない。逆に、既に専門家の大部分がGPUへ常駐している環境では、CPUからの転送を隠す利点自体が小さくなる。したがって適用前には、実際の転送量、転送と演算の重なり時間、必要な一時領域、品質の変化をそれぞれ測定する必要がある。
