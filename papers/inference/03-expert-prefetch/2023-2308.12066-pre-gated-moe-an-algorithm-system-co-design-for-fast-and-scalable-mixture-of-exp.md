# Pre-gated MoE: An Algorithm-System Co-Design for Fast and Scalable Mixture-of-Expert Inference

> 次の層のルーティング判定を1ブロック前で行い、必要エキスパートを早めに確定してCPU→GPU転送を現在ブロックの計算と重ねることで、エキスパート重み待ちを減らすMoEオフロード方式。

## 概要

Pre-gated MoEは、GPUへ全エキスパートを常駐できないMoEで、**ルータ結果が出るまで次エキスパートの重み転送を始められない**という逐次依存を壊す手法である。

通常はブロック `N` のゲートでそのブロックに必要なエキスパートが分かり、その直後にエキスパートを実行する。CPUオフロードではこの順序だと、ゲート後のCPU→GPU転送がそのままGPUの待ち時間になる。

提案はゲートの役割を1ブロック前へずらし、ブロック `N` の計算中にブロック `N+1` で必要になるエキスパートを確定する。これにより、次層エキスパートの重み転送を現在ブロックのエキスパート計算や非エキスパート計算と同時に進められる。

重要なのは、これは**将来エキスパートを統計的に当てる軽量予測器ではない**点である。モデル構造側のルーティング位置を変更し、次層で使うエキスパートを実際のルータ判断として早く確定するアルゴリズム／システム協調設計である。

対象はSwitch Transformer系。エキスパートはCPU DRAM、密な非エキスパート重みはGPUに置く。SSD/NVMe、KVキャッシュのオフロード、CXL/HBFは扱わない。

## 手法のあらまし

### 1. 従来の逐次依存

CPUへエキスパートを退避したMoEでは通常、`ゲート → エキスパート選択 → CPU→GPU重み転送 → エキスパート行列計算` の順になる。エキスパート選択が終わるまで何を転送すべきか分からないため、PCIe転送を早く開始できない。

このときGPU上に次の計算が存在していても、選択された重みが届くまではそのエキスパート計算へ進めない。エキスパート数が増えて総モデル容量が大きくなるほど「全重みをGPUに置く」解決策は使いにくくなり、必要分だけ読む方式では転送待ちが主要な遅延になる。

### 2. `Pre-gate`：次ブロックのルーティングを前倒しする

Pre-gated MoEではブロック `N` 内で、ブロック `N+1` 用のエキスパート選択を先に実行する。その結果が出た時点で、次ブロックで必要なエキスパート重みをCPU DRAMからGPUへ非同期に先読みする。

現在ブロックのエキスパート計算や非エキスパート計算が続いている間に転送を進めるため、次ブロック開始時には重みが到着していることを狙う。転送時間が現在ブロックの残り計算時間より短ければ、CPU→GPU転送の大部分を待ち時間として表面化させずに済む。

ここで前倒しするのは単なるヒントではなく、学習時から組み込んだ事前ゲートのルーティング決定である。そのため「元のルータで最終確認し、予測が外れたら別重みを追加ロードする」構造ではなく、事前ゲートが選んだ経路をモデル自身の経路として使う。

### 3. OnDemand / Prefetchとの違い

論文では主に3方式を比較する。

| 方式 | いつ転送するか | 何を転送するか | 問題 |
|---|---|---|---|
| MoE-OnDemand | 現ブロックのゲート後 | 選択エキスパートのみ | GPUが転送完了を待つ |
| MoE-先読み | ゲート前 | 次ブロックの全エキスパート | 不要エキスパートまで大量に転送する |
| Pre-gated MoE | 1ブロック前の事前ゲート後 | 次ブロックで実際に必要なエキスパート | 必要量だけを早めに転送できる |

オンデマンド方式は転送量が最小だが、選択結果が出てから読み始めるので転送が直列化される。全エキスパート先読みは開始時刻を早められるが、実際には選ばれない重みまでPCIeへ流すため、エキスパート数が増えるほど通信量が急増する。

Pre-gated MoEはこの2つの失敗を分離して考える。**必要エキスパートだけを読むというオンデマンド方式の転送量**と、**実行より前に転送を始める先読み方式の時間的余裕**を同時に得ることが狙いである。したがって改善幅は、現在ブロックの計算時間でPCIe転送をどこまで隠せるかに依存する。

### 4. 先読み距離 `N`

標準は1ブロック先を読む `N=1`。より遠い `N=2/3` も評価しているが、古い隠れ状態から遠い層のルーティングを決めるほど本来のルーティングとのずれが大きくなるため、距離を伸ばせば無条件に良くなるわけではない。

`N=1` は、現在ブロックの計算時間を転送に使える一方でルーティング品質も保ちやすい実用点として扱われる。距離を増やすと転送猶予は長くなるが、モデル内部で本来利用したかった最新表現からゲート判断が離れるため、品質との交換になる。

### 5. 初回・最終ブロックの扱い

最初のMoEブロックには前段の事前ゲートがないため通常処理が必要になる。最終ブロックでは次ブロックの先読みが不要であるため、モデル中央と同じ処理を機械的に適用しない。

この端部処理により、すべてのブロックで完全に転送を隠せるわけではない。エンドツーエンドでは最初のロードや隠し切れない転送が残るため、単一MoEブロックで得た高速化よりモデル全体の高速化が小さくなる。

### 6. 実装

NVIDIA FasterTransformerを拡張し、ゲート、CPU→GPUエキスパート転送、エキスパート行列計算、非エキスパート計算を別々に進められる実行キューとCPU側バッファを使って同時実行する。

エキスパート本体はCPU DRAMに保持し、GPUには実行中・直近必要なエキスパートだけを置く。したがってGPUメモリ削減は「重みを圧縮した」結果ではなく、巨大なエキスパート集合の常駐先をCPUへ移し、必要なものだけ一時的にGPUへ持ってくることで得る。

## なぜこの設計で速くなるのか

Pre-gated MoEはPCIe帯域そのものを高速化しない。必要な重みの転送時間を、別の計算がすでにGPU上で進んでいる時間へ移すことで、転送をクリティカルパスから外す。したがって現在ブロックの計算が十分長く、転送と計算が並行できる条件ほど効果が大きい。

反対に、CPU→GPU帯域が極端に遅い、選択エキスパート数が多い、あるいは現在ブロックの計算が短い場合は、次ブロック開始までに転送が終わらず待ち時間が残る。またモデル構造を事前ゲート前提で学習するため、既存の任意MoEをランタイムだけで置き換える方式ではない。

## 評価

### まず見るところ
- **結論:** ルーティングを1ブロック早く確定すると、CPUオフロードのPCIe待ちをかなり隠せる。
- **速度:** OnDemand比でエンドツーエンド約1.5〜1.6倍。GPU-onlyスループットの約81%まで回復。
- **品質:** `N=1`では通常MoEとほぼ同等。統計予測器でエキスパートを近似する方式とは異なる。
- **メモリ:** 最大GPUメモリはGPU-onlyの約23%。Large-128のような単一GPUに収まらない構成も実行可能。
- **注意点:** Switch系構造に依存し、一般的なデコーダ専用MoEへそのまま適用できるとは限らない。

### Models / tasks

| 項目 | 内容 |
|---|---|
| Models | Switch Base-8 / 64 / 128 / 256、Large-128 |
| Tasks | XSum、CB Web QA、SQuAD |
| 比較対象 | GPU-only、MoE-OnDemand、MoE-先読み |

### 単一MoE block

| 比較 | 結果 |
|---|---:|
| vs MoE-OnDemand | 平均約1.7×、最大約1.9×高速 |
| vs MoE-先読み | 平均約42×、最大約125×高速 |
| GPU-onlyとの差 | 平均約19%の追加遅延 |

全エキスパートを先に読むMoE-先読みは、エキスパート数が増えるほど不要転送が支配的になる。

### End-to-end throughput

Switch-Base群では平均約111 トークン/sで、MoE-OnDemand比約1.5×、MoE-先読み比約27×、GPU-onlyの約81%まで回復した。

GPU-onlyがOOMになるLarge-128でも約42 トークン/sで動作し、OnDemand比約1.6×、先読み比約52×。

### GPU memory

最大GPUメモリはGPU-onlyの約23%、すなわち約4.2×削減。OnDemandとの差は約0.2%に留まり、先読みのために大きな追加キャッシュを必要としない。

### 品質

SQuADでは `N=1` のPre-gated MoEは通常MoEとほぼ同等。

| Model | 通常MoE EM / F1 | Pre-gated N=1 EM / F1 |
|---|---:|---:|
| Base-8 | 77.4 / 85.8 | 78.2 / 86.0 |
| Large-128 | 82.4 / 90.1 | 81.9 / 90.2 |

差は小さく、主要な改善源は近似ではなく転送と計算の重畳である。

### 制約

- Switch Transformer中心。
- バッチ1中心。
- CPU DRAMに全エキスパートを保持できる前提。
- A100 + FasterTransformerのサーバ環境。
- SSD/NVMe、KVオフロード、連続バッチ処理は未評価。
