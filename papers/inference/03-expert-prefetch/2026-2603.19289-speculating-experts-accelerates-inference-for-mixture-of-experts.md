# Speculating Experts Accelerates Inference for Mixture-of-Experts

> 次層expertを予測してweight transferだけでなくexpert GEMMまで投機実行し、native routing確定後にcommit/fallbackするCPU-offloaded MoE方式。

## 概要

この論文はexpert prefetchを一段進め、**次layerのexpert weightを先に送るだけでなく、そのexpert計算自体も先に実行する**。

通常prefetchでは、weightがGPUへ到着していてもnative gateが確定するまでexpert GEMMは始められない。

Speculating Expertsは現在layerのhidden stateから次layer router入力に近い`quasi-hidden state`を作り、次expertを予測する。予測したexpertをtransferし、別CUDA streamでFFNまで投機実行する。

次layerのnative routerが同じexpertを選べば投機結果をcommitし、外れればnative expertをload / computeし直す。

そのためモデル品質は維持されるが、miss時には不要なPCIe transferとGPU computeが発生する。

## 手法のあらまし

### 1. `Quasi-Hidden State`

隣接layerのhidden representationは完全には同じでないが、routing predictionに使える程度の類似性がある。

現在layerのhidden stateから次layer router入力の近似を作り、それを将来expert予測へ使う。

### 2. `Router-PF`

quasi-hidden stateを次layerのnative routerへ直接入力する方式。

追加predictorを学習せず元routerを利用できる一方、router自体の計算costは残る。

### 3. `Estimator-PF`

native routerより軽い推定器で次expertを予測する方式。

prediction overheadは減るが、router approximation errorが増える可能性がある。

### 4. `Hybrid-PF`

layerごとのrouter driftやconfidenceに応じてRouter-PF / Estimator-PFを切り替える。

予測しやすいlayerでは軽量方式、driftが大きいlayerでは保守的方式を使う。

### 5. Transfer + Expert GEMMを投機実行

expert IDを予測したら、CPU DRAMからGPUへweightを非同期transferする。

さらに別streamでexpert FFNを実行する。

prefetchのみなら隠せるのはtransfer時間だけだが、この方式では**transfer + expert compute**の両方を次layer到達前へ押し出せる。

### 6. Commit / Fallback

native router確定後、

- prediction hit → 投機結果を再利用
- miss → 正しいexpertをloadして再計算

する。

expert substitutionを確定出力へ使わないためlosslessである。

### 7. Router driftが大きいlayerでは投機しすぎない

予測が悪いlayerで積極的にspeculateすると、無駄transfer / computeが増えて逆に遅くなる。

そのためlayer別のdriftを測り、投機policyを調整する。

## 評価

### まず見るところ
- **結論:** expert prefetchに投機GEMMを加えるとTPOTをさらに数〜十数%削減できる。
- **速度:** on-demand offload比で概ね5〜14%改善。
- **品質:** native routerへfallbackするためlossless。
- **コスト:** miss時の無駄PCIe trafficとGPU computeが新たなリスク。
- **注意点:** 大幅高速化ではなく、既存offload pipelineへの上積み型最適化。

### Speedup

on-demand CPU expert loadingに対してTPOTを最大約14%、概ね5〜14%削減する。

利得が大きいのは、

- router driftが小さい
- 次layerまで十分なslackがある
- expert transfer / GEMMを現在layer computeへ重ねられる

条件。

### Prefetchだけとの差

投機GEMMを追加しても、予測器・CUDA stream・miss時recomputeのoverheadがあるため、prefetch-onlyからの上積みは限定的。

したがってheadlineは「数倍高速化」ではなく、**既存CPU-offload runtimeをさらに数〜十数%詰める**タイプの結果として読むべきである。

### Miss cost

prediction missでは、

1. 誤expertのweight transfer
2. 誤expert GEMM
3. native expertの追加transfer / GEMM

が発生する。

miss率が高いlayerでは投機しない方がよい。

### 制約

- CPU DRAM offloadのみ。
- SSD/NVMe未評価。
- mobile SoC未評価。
- multi-request continuous batching未評価。
- speedupはhardware / layer driftに強く依存。
