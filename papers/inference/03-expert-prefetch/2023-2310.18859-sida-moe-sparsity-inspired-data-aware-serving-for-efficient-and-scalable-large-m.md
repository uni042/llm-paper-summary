# SiDA-MoE: Sparsity-Inspired Data-Aware Serving for Efficient and Scalable Large Mixture-of-Experts Models

> 小型LSTMで各tokenが使うexpertを先に予測し、予測したexpertだけをCPUからGPUへ読み込む。予測結果そのものをroutingに使うため、外れると元modelと異なるexpertを実行し得る近似方式。

## 概要

SiDA-MoEは、Switch Transformerの大部分を占めるexpert weightをCPU DRAMへ置き、**次batchが使うexpertを小型LSTMで先に予測してGPUへ載せる**推論systemである。

大規模Switchでは全parameterのほぼ全てがexpert由来になる一方、1回のforwardで実際に使うexpertは少ない。SiDAはこの性質を利用し、入力ごとにGPUへ置くexpert集合を入れ替える。

特徴的なのは、LSTM predictorが単なるprefetchの参考情報ではなく、**元routerが選ぶexpert IDとその重み付けまで近似し、その予測結果を実際のroutingに使う**点である。そのためProMoEやExpertFlowのように「予測が外れてもnative routerの正しいexpertを必ず実行する」lossless prefetchとは異なる。

予測精度が高ければGPU memoryとtransfer待ちを大幅に減らせるが、外れれば元modelと異なるroutingになり得る。実際、task accuracyは概ね保たれる一方、pretrained perplexityはかなり悪化する条件がある。

## 手法のあらまし

### 1. 小型LSTMで将来のrouting表を先に作る

SiDAは2-layer LSTM + sparse attentionを使い、各MoE layer / tokenについて、

- どのexpertを使うか
- 各expertの出力をどの程度混ぜるか

を予測する。

予測結果はtoken / layerごとに参照できる表として保存し、後続の推論処理がそれを見て必要expertを準備する。論文ではこの部分を`Hash Predictor`と呼ぶが、本質は**推論本体より先にrouting結果の予測表を作る処理**である。

### 2. 元routerの全scoreではなく、上位候補だけを教師として学習する

元routerが全expertへ出すscoreを小型LSTMで完全再現するのは難しいため、scoreが高い上位`T` expertだけを教師として学習する。

論文ではこれを`Truncated Knowledge Distillation`と呼び、標準設定は`T=30`。expert IDを当てるlossと、上位expertのscore分布を元routerへ近づけるlossを組み合わせる。

短文SST2ではTop-1、MRPC / MultiRCではTop-3予測を使う。

### 3. 次batchの予測を現在batchの推論中に進める

batch `X_j` のrouting予測をCPU側で作っている間に、GPUは直前batch `X_i` を実行する。

つまり、

`predict(X_{i+1}) || infer(X_i)`

と1 batchずらして同時実行し、**GPUがrouting予測の完了を待たなくて済むようにする**。

batch size 1でも隣接request間でこのpipelineを作る点が特徴である。

### 4. 予測したexpertだけGPUへ置く

各layerで予測表を見て、次に必要とされたexpertがGPUに無ければCPU DRAMから転送する。

不要になったexpertはGPUから外し、**そのrequestで近く使うexpert集合だけ**をGPUへ維持する。

Switch-base-128 / 256のようにexpert weightが数十GBあるmodelほどこの効果が大きい。

### 5. 予測ミスはmodel出力そのものへ影響する

SiDAではpredictorがroutingを近似するため、予測ミスが発生するとnative routerとは異なるexpertが実行され得る。

この意味で、

- prefetchだけ予測するProMoE / ExpertFlow
- 正確な次layer routingを前倒しするPre-gated MoE

とは性質が異なる。

速度とmemoryを得る代わりに、**元modelと同じexpert選択をどこまで保てるか**が品質リスクになる。

### 6. 長文ほどGPUへ置く必要があるexpert集合が広がる

長いinputでは1 request内で触れるexpert種類が増え、GPUへ保持すべきexpertも増える。

そのため短文SST2で最もmemory削減が大きく、MultiRCのような200〜500 token入力では削減率が縮む。

## 評価

### まず見るところ
- **結論:** routingをLSTMで先読みすると大規模SwitchのGPU memoryとlatencyを大きく減らせる。
- **速度:** Switch-base-256ではSST2で最大約3.93× throughput改善。
- **メモリ:** 短文ではbase-128/256で60〜80%超のGPU memory削減。
- **品質:** task accuracy/F1は概ね高く保つが、pretrained perplexityは明確に悪化するためlosslessではない。
- **注意点:** A100 + Switch中心で、predictorを学習したdataと実際の入力傾向が変わる場合や長文での予測精度低下が主要リスク。

### 実機環境

| 項目 | 設定 |
|---|---|
| GPU | NVIDIA A100 80 GB |
| CPU | Intel Xeon Platinum 8358 |
| Batch | 1 |
| Expert backing store | CPU DRAM |
| Predictor | 2-layer LSTM + sparse attention |

### Models / tasks

| 項目 | 内容 |
|---|---|
| Models | Switch-base-8 / 64 / 128 / 256 |
| Tasks | SST2、MRPC、MultiRC |
| Baselines | Standard、DeepSpeed-MoE、Tutel |

Switch-base-256では総54.62 GB中約54.11 GB、99%超がMoE parameterであり、expert sparsityの効果が特に大きい。

### Predictor accuracy

| Model | SST2 | MRPC | MultiRC |
|---|---:|---:|---:|
| Switch-base-8 | 99.00% | 97.41% | 91.74% |
| Switch-base-128 | 98.78% | 98.65% | 90.49% |

長文MultiRCでは予測精度が低下する。

### Throughput

baseline平均比の代表値。

| Model | SST2 | MRPC | MultiRC |
|---|---:|---:|---:|
| Base-128 | 2.60× | 2.52× | 1.26× |
| Base-256 | **3.93×** | 3.83× | 1.57× |

短文ほど1 requestで必要になるexpert種類が少なく、prefetch / cacheの効果が大きい。

### GPU memory

短文SST2ではbase-128 / 256で60〜80%超の削減を報告する。

MRPCでも、

- base-128：約6.28 GB削減
- base-256：約19.84 GB削減

MultiRCでは、

- base-128：約4.52 GB
- base-256：約9.92 GB

の削減で、長文になるほど必要expert集合が広がる。

### 元modelとの一致度

fine-tuned taskではbase-8で最大約99%、base-128で最大約96%のtask結果の一致度を報告する。

一方、pretrained perplexityは以下のように悪化する。

| Model | Original PPL | SiDA PPL |
|---|---:|---:|
| Base-8 | 6.68 | **18.49** |
| Base-64 | 4.93 | 11.84 |
| Base-128 | 4.86 | 11.73 |
| Base-256 | 4.59 | 8.11 |

この差から、`routing prediction accuracyが高い = native modelと同じ品質` と解釈してはいけない。

### 制約

- router predictorの追加学習が必要。
- predictorはinput domain / sequence lengthに依存する。
- 厳密losslessではない。
- A100サーバ + Switch系列中心。
- SSD/NVMe、KV cache、decoder-only MoE、continuous batchingは未評価。
