# CasMoE: A Cascaded Framework for Efficient MoE Inference on Resource-constrained Devices

## 概要

混合専門家モデル（MoE）は多数の専門家重みを持ちながら、各トークンでは少数の専門家だけを実行する。しかし専門家の総重量は大きく、GPUにすべて常駐させると容量不足になりやすい。論文はMixtral-8×7Bの例で、全体の推論時メモリ需要が約87GBなのに対し、密な層と実際に活性化する専門家の重みは約24GBであると説明する。CPU側へ非活性専門家を退避し、必要なものだけGPUへ移せば容量は節約できるが、専門家が決まってから転送するとPCIeの待機が推論時間へ直接加算される。

CasMoEは入力文を受け取った時点で**全MoE層の専門家活性パターン**を一括予測し、専門家重みを先読みする。過去に似た入力がある場合は専門家活性照合器（EAM）が履歴を検索し、似た入力がない場合は専門家活性予測器（EAP）が学習済みモデルでパターンを推定する。二つの経路をコサイン類似度の閾値で切り替える段階的計画器により、毎回重い予測器を動かさず、深い層の転送も早い時点で始められる。

著者らは4台のRTX 4090とデュアルXeon Gold 6330を用い、Mixtral-8×7Bの混合精度構成をGLUE、MMLU、WMT16で測定した。論文の貢献欄はオンデマンド専門家転送に対して処理率65.13%改善を掲げる。ただし**出力品質は完全無損失ではない**。GLUE平均は全専門家GPU常駐時0.73に対しCasMoE 0.71、MMLUは0.792に対し0.572、WMT16は43.366に対し34.153である。予測した専門家集合を選択へ反映するため、正しい専門家が必ず実行される通常の先読み専用方式とは異なる。速度と品質の交換条件を明示して読む必要がある。

## 問題設定

### 容量不足と専門家転送の待機

MoE層ではルータがトークン表現xから各専門家の重み付けスコアを求め、上位k個の専門家を選択する。GPUの容量が足りない場合、非活性専門家をCPUの主記憶に置き、選ばれた専門家の重みをPCIe経由で読み込む。論文はMixtral-8×7BとSST-2の例で、必要時ロードが推論時間の40.8%を占めると報告する。転送待ちを減らすため次層の全専門家を先に送る方法は、使われない重みも移すため転送量とGPUメモリを浪費する。

先行方式は隣接層の専門家活性が似ることを利用して次層の選択を予測するが、層ごとに予測する方式では深い層の転送を十分早く始められない。入力文全体から将来の専門家を一括予測する方式は転送時間を長く隠せる一方、入力文だけでは各トークンの中間状態がまだ分からないため、予測を誤る可能性がある。CasMoEは過去履歴の高速検索と学習型予測器を組み合わせ、この精度・費用の対立を扱う。

### 先読みだけでなく専門家選択を変える設計

本論文の計画器は、推定した専門家活性パターンを各層の上位k選択へ変換して推論へ渡す。したがって「最終的な専門家選択は常に元のルータと完全一致し、出力は必ず無損失」という説明は一次論文の実測と整合しない。実際、正確な専門家を選ぶ全常駐方式とオンデマンド方式の精度は等しいが、CasMoEにはGLUE・MMLU・翻訳で差が生じる。専門家予測の精度と、モデルの下流課題での正答率を分けて評価する必要がある。

## 手法

### 1. 入力文ごとの専門家活性パターンを校正データから作る

事前段階では、入力文と正解応答の組を用意し、学習済みMoEモデルを実行して各層でどの専門家が選ばれたかを追跡する。単純な出現回数だけでは、重要なトークンで選ばれた専門家と、寄与の小さいトークンで選ばれた専門家を区別できない。そこでルータの重み付け係数αと、当該専門家が選ばれたことを表す指示関数を使い、入力文に対する各専門家の重み付け活性を累積する。

入力文iについて、MoE層数L、各層の専門家数Kの行列 `EP_i ∈ R^(L×K)` を作り、入力文 `X_i` と対にして校正データ集合Dを構成する。後段の検索器と学習器は、この同じ専門家活性行列を予測する。全層の活性パターンを一つの対象として扱うことが、層単位の次専門家予測と異なる点である。予測対象は各トークンの実際のルータ結果を完全に復元するものではなく、入力文から代表的な専門家集合を得るための集約表現である。

### 2. 非パラメトリックな専門家活性照合器（EAM）

校正入力文を文埋め込みモデルでベクトル化し、その埋め込みをキー、対応する `EP_i` を値として専門家パターンデータベース（PDB）へ保存する。近似最近傍探索には階層的な小世界グラフ索引（HNSW）を使い、入力文と登録済み入力文のコサイン類似度で近い候補を取り出す。上位k′件の専門家活性行列を平均して、検索経路の推定行列を得る。

EAMは追加のBERT推論を要しないため高速だが、過去の入力文が現在の入力と十分似ていることが前提になる。入力文の表面上の類似が高くても専門家選択が異なる場合、誤った専門家を先読みする危険がある。PDBは静的な索引ではなく、オンラインで新しい入力と専門家活性を一時バッファへ蓄え、容量Cに達したら更新する。実験ではC=30とする。更新によって未知の入力への被覆は増やせるが、索引維持と記憶領域の費用が生じる。

### 3. 学習型の専門家活性予測器（EAP）

類似入力を十分に見つけられない場合は、軽量なBERT系符号器で入力文を表現し、MoE層ごとに一つ用意した多層パーセプトロン（MLP）予測頭で `EP` の各行を出力する。論文の実装は6層TinyBERTと2層MLPで、隠れ層64・中間層128を代表設定とする。各予測頭の出力次元は対象層の専門家数Kであり、入力文一つから全層の候補を一度に生成する。

符号器の学習には同一入力文の複製を正例とする対照学習を用い、InfoNCE損失で表現を安定化する。専門家活性の予測値と校正時の正解パターンの差にはHuber損失を用い、総損失を `α L_cont + L_hb` とする。Huber損失は誤差の小さい範囲で二乗誤差、大きい範囲で絶対誤差に近い挙動を取るため、極端な誤差への感度を調整できる。実験ではAdamを使い、学習率6×10⁻⁷、損失重み0.05とする。

### 4. 段階的計画器と類似度ゲート

オンラインでは、まず入力文を埋め込みへ変換し、EAMがPDBから近傍の活性行列を検索する。最も近い候補のコサイン類似度が閾値ε以上なら検索結果を使い、閾値未満ならEAPを起動する。EAMとEAPの結果を無条件に平均するのではなく、信頼度で経路を切り替える。類似した入力が頻繁に到来する場合は、重い予測器の呼出しを避けられる。

計画器の出力である全層の活性行列から、各層の上位k個の専門家を選び、CPUからGPUへの先読みを開始する。層1の計算を始める前に深い層の候補も把握できるため、後段の専門家転送を前段の計算と重ねられる。検索の閾値を緩めればEAP呼出しは減るが誤検索の危険が増え、厳しくすれば予測器の計算費用が増える。この切替が処理率と品質を調整する主要な制御点である。

全専門家GPU常駐と必要時転送の二方式は同じ専門家を実行するため、GLUEの8課題すべてで同じ正解率を示す。CasMoEは平均0.71で全常駐の0.73に近いが、完全一致ではない。Mixtral-Offloadingの平均0.59、AdapMoEの0.64より高い一方、個別にはMNLIで全常駐0.54に対して0.50、QQPで0.72に対して0.70、RTEで0.77に対して0.74と低下する。SST-2は0.89に対して0.88である。

### 2. MMLUとWMT16の品質比較（表2）

MMLUは全常駐の0.792に対してCasMoE 0.572であり、絶対差は0.220、相対保持率は約72.2%である。WMT16のSacreBLEUは43.366に対して34.153で、相対保持率は約78.8%である。Mixtral-OffloadingのMMLU 0.626はCasMoEより高く、AdapMoEは0.507で低い。翻訳ではCasMoE 34.153がMixtral-Offloading 27.720、AdapMoE 25.024を上回る。したがって「全評価でCasMoEが次点」と単純化してはいけない。

|方式|MMLU正解率|WMT16 SacreBLEU|
|---|---:|---:|
|全専門家GPU常駐|0.792|43.366|
|オンデマンド転送|0.792|43.366|
|SE-MoE|0.792|43.366|
|Mixtral-Offloading|0.626|27.720|

論文本文にはMMLUの保持率を「57.2%」と表現する箇所があるが、表2の0.572は絶対正解率であり、全常駐0.792に対する保持率は約72.2%である。本文中の百分率と表の値は整合しないため、数値を混同せず表2の生値を優先する。AdapMoEのMMLU欄には全入力でメモリ不足が発生して評価数が減った旨の注記もあるため、比較条件が完全に同じとは限らない。

### 3. 処理率と遅延（図3〜5）

論文の貢献欄はオンデマンド転送方式と比べて処理率65.13%改善を報告する。GLUEの図5ではSE-MoEに対して約10倍、オンデマンド転送に対して約2倍という説明もある。これらは測定課題や指標の集計条件が異なるため、すべてのGLUE課題で常に65.13%または10倍改善したという意味ではない。図5の説明ではGLUEの多くの部分集合で処理率3.0を超える値が報告されるが、数値の単位と基準方式を明示せず他研究と直接比較しない。

図3・4はMMLUとWMT16で遅延・処理率を比較し、入力文時点で全層の専門家を予測する方式が、層ごとの専門家決定を待つ方式より転送を重ねやすいことを示す。ただし品質表で明らかなように、処理率の改善を品質完全維持の証拠としては扱えない。先読みする専門家集合を固定することで転送待ちを減らす一方、元のルータが選ぶ専門家集合と異なる場合には下流課題の正答率が変わる。

### 4. 検索器と予測器の構成要素除去（表3）

CoLAの比較では全常駐が正解率0.72、処理率2.963、EAP単独が0.71・2.971、EAPとEAMの組合せ（閾値ε=0.3）が0.72・3.074となる。検索経路を追加するとEAPの呼出しを省け、予測品質と処理率を改善できる場合がある。著者らはEAPの予測正解率約98%、計算時間10.73ms、記憶量300MBを報告し、EAM単独の計算時間は1.22msとする。検索器が高速でも、索引を構築・更新する費用がゼロという意味ではない。

|CoLAの構成|正解率|処理率|解釈|
|---|---:|---:|---|
|全専門家GPU常駐|0.72|2.963|品質上限寄りの基準|
|EAP単独|0.71|2.971|学習型予測器だけでは固定費が残る|
|EAP＋EAM（ε=0.3）|0.72|3.074|近傍検索でEAP呼出しを減らす|

### 5. 専門家活性ラベルの設計（表4）

単純な専門家出現回数から作ったラベルを使う方式は、CoLAの正解率が0.62に留まる。ルータ重みを含む本研究の専門家活性パターン（EP）では0.72で、全常駐の0.72と同じ値になった。出現回数だけでは、トークンごとの重要度が異なる専門家を同等に扱ってしまい、学習器が適切な選択を予測しにくい。EPは活性頻度だけでなくルータ重みを含めるため、入力文から全層パターンを回帰する対象として扱いやすい。

## 既存研究との差

SE-MoEは次層の全専門家を先に移すため、選択を外しにくいが不要な転送が多い。Mixtral-Offloadingは層間の活性類似を利用して次層の専門家を予測し、最近使用されていない重みをキャッシュから追い出す。AdapMoEは感度に応じて次層へ先読みする専門家数を変える。これらに対しCasMoEは入力文全体の意味表現から**全層の活性行列を一度に予測**し、検索と学習器を信頼度で切り替える。

EAMのHNSW索引は過去の似た入力が多いときに有利であり、EAPのTinyBERTは未知の入力でも専門家活性を推定する。専門家の活性回数とルータ重みをまとめたラベルを学習対象とし、検索器と予測器が同じ行列形式を返すため、後段の上位k選択へ統一的に渡せる。これは単純な「検索が当たらなければモデルを呼ぶ」という一般的な段階化ではなく、MoEの専門家先読み用に活性行列・索引・学習損失・切替閾値を設計したものである。

## 限界と負の結果

最大の注意点は**品質が完全には保存されない**ことである。全常駐とオンデマンド転送は正しい専門家を使うためGLUE平均0.73だが、CasMoEは0.71となる。MMLUでは0.792から0.572、WMT16では43.366から34.153へ低下する。論文の要約にある「96.6%保持」を全課題に適用してはならない。課題ごとの誤予測、専門家集合の変更、混合精度の影響を分離して読む必要がある。

履歴検索はPDBの被覆に依存する。初めて現れる入力文や分布が大きく変わった入力ではEAMの類似度が下がり、EAPの計算費用が増える。類似度閾値を緩くすると誤った履歴を再利用する危険があり、厳しくするとEAP呼出しが増える。PDBのオンライン更新はC=30のバッファを使うため、更新の頻度・索引再構築の費用・長期的な分布ずれに対する安定性を別途評価する必要がある。

実験は4台のRTX 4090とXeon Gold 6330を使ったMixtral-8×7Bに集中する。別の専門家数やゲート構造、異なるGPUメモリ容量、PCIe帯域、NVMeからの多段オフロードへ同じ倍率が適用できるとは限らない。推論要求の同時到着分布や非常に長い文脈での負荷変動について、主要結果から一般的な性能保証を導くことはできない。コード公開先は一次資料から特定できない。

## 実装状況

PyTorchを基盤に、専門家活性の事前追跡、文埋め込みとHNSW索引、6層TinyBERTと層別MLP、コサイン類似度による切替、CPU→GPU専門家先読みを組み合わせた研究試作である。評価ではGLUE、MMLU、WMT16の品質と処理率・遅延を実機測定している。公式の公開コードURLはAAAI掲載ページと本文から確認できなかったため、コードが公開済みであるとは記載しない。
