# Cache-Aware Joint Router Adaptation for Memory-Efficient MoE Inference

> **この研究の中心は「次に使うexpertを何でも先読みする」ことではない。MoE本来のTop-K実行規則は残したまま、GPUに今あるexpertのうち何を残すべきかをmodel側に学ばせ、必要な場合だけ次layerのexpertを限定的に先読みする。**

## 概要

専門家混合（Mixture-of-Experts; MoE）モデルは、1 tokenを処理するとき全expertを計算するのではなく、routerが選んだ少数expertだけを実行する。たとえば128 expertsのうちTop-8だけを使えば、計算量はかなり疎になる。

ただし、**計算しないexpertもweightとしてはmodel内に存在する**。全expert weightがGPU HBMへ収まらない環境では、使うexpertだけCPU memoryやstorageからGPUへ読み込む必要がある。

decodeではtokenごと・layerごとに必要expertが変わるため、cache missが多いと、MoEの少ない計算量よりexpert-weight転送の方が遅くなる。

そこでGPU上に一部expertだけを常駐させる**expert cache**を置く。しかしcache容量が小さいと、次に何を使うか分からないままexpertを追い出す必要がある。

既存方式は大きく二つに分かれる。

- **置換（replacement）**: LRU/LFUのように過去の利用履歴から何を残すか決める。
- **先読み（prefetch）**: 次に使うexpertを予測し、必要になる前に転送する。

前者は将来を見ないためmissが増えやすい。後者は予測を外すと、使わないexpertを転送して帯域を浪費する。

本研究はこのcache管理をruntime heuristicだけに任せず、**model自身へcacheしやすいpriorityを学ばせるpost-training問題**として扱う。

提案には二つのdeployment modeがある。

1. **時間router（Temporal Router）**: 次tokenでも同じlayerで再利用されそうなexpertを予測し、今cacheにあるexpertを賢く残す。新しいexpertを先読みしない。
2. **時空間router（Spatio-Temporal Router）**: 次layerへ到達する前のhidden stateから将来expertを予測し、必要ならnon-resident expertを限定的に先読みする。

## expert cacheを具体例で考える

Qwen3-30B-A3Bの評価設定では、1 MoE layerに128 routed expertsがあり、1 tokenあたりTop-8を実行する。一方GPU cacheには20 expertsしか置かない設定を使う。

あるtokenでnative routerが

`{3, 8, 11, 17, 25, 41, 70, 96}`

を選んだとする。

cacheにこの8個すべてがあればweight転送なしで計算できる。

しかしexpert 70と96が無ければ、この2個をdemand-loadする必要がある。cacheが20個で満杯なら、代わりにresident expertを2個evictしなければならない。

問題は、**どれをevictするか**である。

今tokenでは使わなかったexpert 12が次tokenですぐ必要になるかもしれない。LRUなら「最近使っていない」だけで12を捨てる可能性がある。

Cache-Aware Joint Router Adaptationは、この「今は不要だが次に必要になるexpert」をhidden stateから予測して残す。

## native routerとcache routerは何が違うのか

ここが最も重要な前提である。

### native router

native routerはmodel本来のMoE routerで、hidden stateからexpert scoreを出し、**実際に計算するTop-K expert**を決める。

### auxiliary cache router

提案法が追加する軽量routerは、**どのexpertをGPUに置いておくと将来転送が減るか**を予測する。

つまり、

`hidden state → native router → 実行するexpert`

と

`hidden state → cache router → cacheに残す / 先読みするexpert`

を別decisionにする。

補助routerがexpert 5を高priorityと予測しても、native routerがexpert 5をTop-Kに選ばなければそのtokenでは計算しない。

逆にnative routerが必要としたexpertがcacheに無ければ、補助routerの予測より実需要を優先して必ずloadする。

したがってcache予測を外しても「必要expertを省略した近似計算」にはならない。失うのは転送時間である。

## 手法のあらまし

### 1. Temporal Router: 次token用にresident expertを残す

Transformer decodeでは、隣接token間でexpert利用に局所性がある。同じ文章・計算の続きを処理しているため、現在tokenで使われたexpertやその近傍expertが次tokenでも選ばれやすい場合がある。

Temporal Routerは現在のhidden stateから、**同じMoE layerの次tokenで必要になりそうなexpert分布**を予測する。

現在のnative-router distributionとTemporal Routerの未来予測を足し、resident expertsにpriorityを付ける。

cache更新では、現在tokenで実際に使ったTop-K expertは保護し、それ以外でpriorityの低いexpertからevictする。

### 2. Temporal Routerはprefetchしない

Temporal Routerの特徴は、未来需要を予測しても**non-resident expertを先にloadしない**ことにある。

やることは「すでにGPUにあるexpertの中で、どれを残すか」を改善するだけである。

そのため予測が当たれば次tokenのdemand missが減る。一方予測を外しても、使わないexpertを先に転送する余計なtrafficは発生しない。

この性質から、帯域が非常に細く、誤prefetchのcostが大きい環境ではTemporal Router単独が有力なoperating pointになる。

### 3. Spatio-Temporal Router: 次layerのexpertを到着前に予測する

Temporal Routerは「同じlayerの次token」しか見ない。

しかしTransformerはlayerを順に実行するので、target MoE layerへ到達する前には、その直前layerのhidden stateがすでに計算済みである。

Spatio Routerはこの**因果的に先に利用できるhidden state**から、次に実行されるMoE位置で必要になりそうなexpertを予測する。

例えばtoken `t` のlayer 20を実行する前にはlayer 19のhidden stateがある。これを使えばlayer 20のnative routingが確定するより少し早くexpert需要を推測できる。

最初のMoE layerの場合は同じtokenの前layerが無いため、前tokenの最後のMoE layerから得た情報を使う。

### 4. pre-access refinement: cacheを先に組み替える

Spatio-Temporal Routerは、target layerへ到達する前に現在cacheへpriorityを付ける。

上位candidateの中にnon-resident expertがあり、現在residentの最低priority expertより重要だと予測した場合、前者をproactive loadして後者と入れ替える。

これが**事前cache改善（pre-access refinement）**である。

予測が当たれば、native routerがそのexpertを要求した時点ですでにGPUにあるのでdemand missが消える。

ただし外れれば、使わないexpertを転送しただけになる。

### 5. refinement budget `R`で先読み量を制限する

そこで1回のrefinementで検討するexpert数を`R`に制限する。

- `R`が小さい → proactive trafficは少ないがcoverageも低い。
- `R`が大きい → より多くの将来expertをcoverできるが誤prefetchも増える。

論文では`R`をtraining後にも変更できる設計にしており、runtimeでbandwidth条件に合わせてprefetch aggressivenessを調整できる。

### 6. cache-aware post-training

補助routerは、将来必要になるexpertへ高priorityを出すようpost-trainingする。

hardなTop-B cache selectionは離散decisionなので、そのままgradientを流しにくい。そこでtraining時はsoftなTop-B membershipを近似し、**未来のnative-router distributionをcache priorityでどれだけcoverできるか**をlossにする。

同時にlanguage-modeling lossも残し、cache効率だけを追ってtask performanceを壊さないようにする。

### 7. 「native routingを保つ」の意味に注意

論文はinference-timeのTop-K ruleを変えない。auxiliary routerが実行expertを直接置換することはない。

ただしmain experimentではbackboneとnative routerのparameterもcache-aware objectiveでjoint post-trainingする。

そのため、post-training前後でnative routerの**確率分布や実際のTop-K pattern自体は変化し得る**。

つまり、

> 元modelのrouting traceを完全固定したままcacheだけ改善した

という研究ではない。

この違いを切り分けるため、論文はbackbone/native routerを固定してauxiliary routerだけ学習するablationも行う。

## 評価指標の読み方

### cache hit rate

native routerが選んだexpertのうち、access前にGPUへresidentだった割合。

高いほどdemand loadは減る。

### proactive load

native routerがまだ要求していないexpertを予測だけで先にloadした回数。

これはhit率を上げられるが、外れた場合もbandwidthを消費する。

### expert-weight traffic

demand loadとproactive loadを合わせて、実際に何回expert weightを移動したかを見る。

prefetch policyを比べるときはこちらが重要である。

極端な例として、将来使う可能性のあるexpertを全部prefetchすればhit率100%に近づけられるが、転送量は巨大になる。したがって**hit率だけでprefetch方式を評価してはいけない**。

## 評価

### modelとtask

- Qwen3-30B-A3B-Instruct-2507: 48 routed layers、128 experts/layer、Top-8。
- GPT-OSS-20B: 24 routed layers、32 local experts/layer、Top-4。
- task: GSM8K、MATH、CommonsenseQA。

main cache capacityはQwen3で20、GPT-OSSで8 experts。Spatio-Temporal Routerのmain refinement budgetはそれぞれ15と6。

### Temporal Router

Qwen3ではTemporal Routerのhit率が

- GSM8K: **73.13%**
- MATH: **75.00%**
- CommonsenseQA: **91.61%**

となり、LRU/LFU/LRFUなどのclassical replacementを一貫して上回る。

ここでの価値はhit率そのものだけではない。Temporal Routerはproactive loadを0に保つので、改善が余分な先読みtrafficによって作られたものではない。

### Spatio-Temporal Router

Qwen3の3 taskで、評価した最強prefetch baselineに対して

- load-adjusted hit rate: **+1.15〜18.03 percentage points**
- expert-weight traffic: **4.6〜53.3%削減**

を報告する。

特に後者は「expert transferの回数」を直接数えたalgorithmic gainであり、raw hitだけを見るより意味がある。

一方GPT-OSSでは改善幅はtask依存で、すべての条件で大差を付けるわけではない。

### joint adaptationとauxiliary-only

backboneを固定してauxiliary routerだけ学習すると、baseline task accuracyを保ちやすい反面、cache improvementは控えめになる。

backbone/native routerまでjoint post-trainingしたmain設定ではcache gainが大きい。

これは、**既存routingを予測するだけより、model自身を少しcache-friendlyなroutingへ適応させた方が転送を減らせる**ことを示す一方、元routing semanticsを完全固定していないというtrade-offでもある。

## 主要結果をwall-clock speedupと混同しない

論文の主要効率評価はexpert-routing traceに同期したcache simulatorである。

cache missやproactive insertionを「expert weight transfer 1回」として数えるため、algorithmとして何回weightを運ぶかは比較できる。

しかし、実systemでは

- expert size
- PCIe / NVLink bandwidth
- pinned memory
- DMA latency
- transferとcomputeのoverlap
- batch size
- multi-request contention

によって1 transferのcostが変わる。

したがって「traffic 53.3%削減 = latency 53.3%短縮」ではない。

特にcomputeとtransferを完全にoverlapできるsystemではtraffic reductionがlatencyへそのまま出ない。一方、PCIe miss待ちでGPUがstallする小batch環境なら大きく効く可能性がある。

## 既存研究との差

### LRU/LFUとの違い

LRU/LFUはpast accessだけを見る。Temporal Routerはcurrent hidden stateから**future same-layer demand**を学習する。

### ProMoE系prefetchとの違い

future expert prediction自体は既存研究にもある。

本研究の特徴は、

- まずprefetchなしのretentionだけでも学習する。
- native Top-Kとcache priorityを別routerへ分ける。
- backbone/native routerまでcache-aware objectiveでjoint adaptationできる。
- refinement budgetでproactive trafficを明示的に制限する。

点にある。

### cache policyだけの研究との違い

通常はfixed modelから出たrouting traceを前提にcache algorithmを比較する。

本研究はmodel-side post-trainingまで含め、「cacheしやすいrouting behavior」そのものを作る方向へ踏み込む。

## 限界と適用境界

- **主要結果はtrace-driven simulation。** 実機PCIe/NVLink latencyやend-to-end tokens/sは未評価。
- **joint trainingでは元routingが変わる。** 純粋なcache replacementだけの公平比較ではない。
- **post-training costが必要。** training-freeに既存modelへ即導入する方式ではない。
- **auxiliary routerのcompute overheadがある。** 軽量でも各MoE positionで追加predictionが必要。
- **Spatio-Temporal Routerは誤prefetchを起こす。** `R`を大きくし過ぎるとhitが増えてもtrafficが悪化し得る。
- **cache capacity依存。** cacheが十分大きければLRUでもmissが少なく、追加routerの価値は縮む。
- **task/model依存性。** GPT-OSSではQwen3ほど一貫したgainではない。
- **offloading backendを規定しない。** CPU DRAM、NVMe、remote memoryなど、どこからexpertをloadするかは別問題。

## 実装上の含意

最初からSpatio-Temporal Routerまで導入する必要はない。

帯域が厳しい環境では、まず**Temporal Router型のlearned retention**を導入し、proactive loadを増やさずmissがどれだけ減るかを見る方が安全である。

その後、実機profilingで「demand miss待ちがGPU stallの主因」と分かった場合だけSpatio refinementを追加し、`R`をbandwidthに合わせて調整する。

また評価ではhit rateだけでなく、

`demand loads + proactive loads`

を必ず数えるべきである。cache hitだけをKPIにすると、過剰prefetch policyを誤って高評価しやすい。
