# Cache-Aware Joint Router Adaptation for Memory-Efficient MoE Inference

> **この研究の中心は「次に使うエキスパートを何でも先読みする」ことではない。MoE本来のTop-K実行規則は残したまま、GPUに今あるエキスパートのうち何を残すべきかをモデル側に学ばせ、必要な場合だけ次層のエキスパートを限定的に先読みする。**

## 概要

専門家混合（Mixture-of-エキスパート; MoE）モデルは、1 トークンを処理するとき全エキスパートを計算するのではなく、ルータが選んだ少数エキスパートだけを実行する。たとえば128 エキスパートのうちTop-8だけを使えば、計算量はかなり疎になる。

ただし、**計算しないエキスパートも重みとしてはモデル内に存在する**。全エキスパート 重みがGPU HBMへ収まらない環境では、使うエキスパートだけCPU メモリやstorageからGPUへ読み込む必要がある。

デコードではトークンごと・層ごとに必要エキスパートが変わるため、キャッシュ ミスが多いと、MoEの少ない計算量よりエキスパート-重み転送の方が遅くなる。

そこでGPU上に一部エキスパートだけを常駐させる**エキスパート キャッシュ**を置く。しかしキャッシュ容量が小さいと、次に何を使うか分からないままエキスパートを追い出す必要がある。

既存方式は大きく二つに分かれる。

- **置換（replacement）**: LRU/LFUのように過去の利用履歴から何を残すか決める。
- **先読み（先読み）**: 次に使うエキスパートを予測し、必要になる前に転送する。

前者は将来を見ないためミスが増えやすい。後者は予測を外すと、使わないエキスパートを転送して帯域を浪費する。

本研究はこのキャッシュ管理を実行時 heuristicだけに任せず、**モデル自身へキャッシュしやすい優先度を学ばせるpost-training問題**として扱う。

提案には二つの配備モードがある。

1. **時間ルータ（Temporal ルータ）**: 次トークンでも同じ層で再利用されそうなエキスパートを予測し、今キャッシュにあるエキスパートを賢く残す。新しいエキスパートを先読みしない。
2. **時空間ルータ（Spatio-Temporal ルータ）**: 次層へ到達する前の隠れ 状態から将来エキスパートを予測し、必要ならnon-常駐 エキスパートを限定的に先読みする。

## expert cacheを具体例で考える

Qwen3-30B-A3Bの評価設定では、1 MoE 層に128 routed エキスパートがあり、1 トークンあたりTop-8を実行する。一方GPU キャッシュには20 エキスパートしか置かない設定を使う。

あるトークンで元の ルータが

`{3, 8, 11, 17, 25, 41, 70, 96}`

を選んだとする。

キャッシュにこの8個すべてがあれば重み転送なしで計算できる。

しかしエキスパート 70と96が無ければ、この2個をdemand-読み込みする必要がある。キャッシュが20個で満杯なら、代わりに常駐 エキスパートを2個追い出ししなければならない。

問題は、**どれを追い出しするか**である。

今トークンでは使わなかったエキスパート 12が次トークンですぐ必要になるかもしれない。LRUなら「最近使っていない」だけで12を捨てる可能性がある。

キャッシュ認識型共同ルータ適応は、この「今は不要だが次に必要になるエキスパート」を隠れ状態から予測して残す。

## native routerとcache routerは何が違うのか

ここが最も重要な前提である。

### native router

元の ルータはモデル本来のMoE ルータで、隠れ 状態からエキスパート スコアを出し、**実際に計算するTop-K エキスパート**を決める。

### auxiliary cache router

提案法が追加する軽量ルータは、**どのエキスパートをGPUに置いておくと将来転送が減るか**を予測する。

つまり、

`hidden state → native router → 実行するexpert`

と

`hidden state → cache router → cacheに残す / 先読みするexpert`

を別decisionにする。

補助ルータがエキスパート 5を高優先度と予測しても、元の ルータがエキスパート 5をTop-Kに選ばなければそのトークンでは計算しない。

逆に元の ルータが必要としたエキスパートがキャッシュに無ければ、補助ルータの予測より実需要を優先して必ず読み込みする。

したがってキャッシュ予測を外しても「必要エキスパートを省略した近似計算」にはならない。失うのは転送時間である。

## 手法のあらまし

### 1. Temporal Router: 次token用にresident expertを残す

Transformer デコードでは、隣接トークン間でエキスパート利用に局所性がある。同じ文章・計算の続きを処理しているため、現在トークンで使われたエキスパートやその近傍エキスパートが次トークンでも選ばれやすい場合がある。

Temporal ルータは現在の隠れ 状態から、**同じMoE 層の次トークンで必要になりそうなエキスパート分布**を予測する。

現在の元ルータ分布と時間ルータの未来予測を足し、常駐エキスパートに優先度を付ける。

キャッシュ更新では、現在トークンで実際に使ったTop-K エキスパートは保護し、それ以外で優先度の低いエキスパートから追い出しする。

### 2. Temporal Routerはprefetchしない

Temporal ルータの特徴は、未来需要を予測しても**non-常駐 エキスパートを先に読み込みしない**ことにある。

やることは「すでにGPUにあるエキスパートの中で、どれを残すか」を改善するだけである。

そのため予測が当たれば次トークンのdemand ミスが減る。一方予測を外しても、使わないエキスパートを先に転送する余計な通信量は発生しない。

この性質から、帯域が非常に細く、誤先読みのコストが大きい環境では時間ルータ単独が有力な運用点になる。

### 3. Spatio-Temporal Router: 次layerのexpertを到着前に予測する

Temporal ルータは「同じ層の次トークン」しか見ない。

しかしTransformerは層を順に実行するので、対象モデル MoE 層へ到達する前には、その直前層の隠れ 状態がすでに計算済みである。

Spatio ルータはこの**因果的に先に利用できる隠れ 状態**から、次に実行されるMoE位置で必要になりそうなエキスパートを予測する。

例えばトークン `t` の層 20を実行する前には層 19の隠れ 状態がある。これを使えば層 20の元の ルーティングが確定するより少し早くエキスパート需要を推測できる。

最初のMoE 層の場合は同じトークンの前層が無いため、前トークンの最後のMoE 層から得た情報を使う。

### 4. pre-access refinement: cacheを先に組み替える

Spatio-Temporal ルータは、対象モデル 層へ到達する前に現在キャッシュへ優先度を付ける。

上位candidateの中にnon-常駐 エキスパートがあり、現在常駐の最低優先度 エキスパートより重要だと予測した場合、前者をproactive 読み込みして後者と入れ替える。

これが**事前キャッシュ改善（pre-access refinement）**である。

予測が当たれば、元の ルータがそのエキスパートを要求した時点ですでにGPUにあるのでdemand ミスが消える。

ただし外れれば、使わないエキスパートを転送しただけになる。

### 5. refinement budget `R`で先読み量を制限する

そこで1回の改善処理で検討するエキスパート数を`R`に制限する。

- `R`が小さい → proactive 通信量は少ないが被覆も低い。
- `R`が大きい → より多くの将来エキスパートをcoverできるが誤先読みも増える。

論文では`R`を学習後にも変更できる設計にしており、実行時に帯域条件に合わせて先読みの積極性を調整できる。

### 6. cache-aware post-training

補助ルータは、将来必要になるエキスパートへ高優先度を出すようpost-trainingする。

離散的なTop-Bキャッシュ選択は離散決定なので、そのまま勾配を流しにくい。そこで学習時は軟らかなTop-B所属を近似し、**未来の元ルータ分布をキャッシュ優先度でどれだけ覆えるか**を損失にする。

同時に言語モデル損失も残し、キャッシュ効率だけを追ってタスク性能を壊さないようにする。

### 7. 「native routingを保つ」の意味に注意

論文は推論時のTop-K規則を変えない。補助ルータが実行エキスパートを直接置換することはない。

ただし主実験では基盤モデルと元ルータのパラメータもキャッシュ認識型の目的関数で共同事後学習する。

そのため、post-training前後で元の ルータの**確率分布や実際のTop-K パターン自体は変化し得る**。

つまり、

> 元モデルのルーティング トレースを完全固定したままキャッシュだけ改善した

という研究ではない。

この違いを切り分けるため、論文は基盤モデル／元ルータを固定して補助ルータだけ学習する除去実験も行う。

## 評価指標の読み方

### cache hit rate

元の ルータが選んだエキスパートのうち、access前にGPUへ常駐だった割合。

高いほどdemand 読み込みは減る。

### proactive load

元の ルータがまだ要求していないエキスパートを予測だけで先に読み込みした回数。

これはhit率を上げられるが、外れた場合も帯域を消費する。

### expert-weight traffic

要求時読み込みと先行読み込みを合わせて、実際に何回エキスパート重みを移動したかを見る。

先読み 方針を比べるときはこちらが重要である。

極端な例として、将来使う可能性のあるエキスパートを全部先読みすればhit率100%に近づけられるが、転送量は巨大になる。したがって**hit率だけで先読み方式を評価してはいけない**。

## 評価

### modelとtask

- Qwen3-30B-A3B-Instruct-2507: 48 routed 層、128 エキスパート/層、Top-8。
- GPT-OSS-20B: 24 routed 層、32 local エキスパート/層、Top-4。
- タスク: GSM8K、MATH、CommonsenseQA。

主キャッシュ容量はQwen3で20、GPT-OSSで8エキスパート。時空間ルータの主改善予算はそれぞれ15と6。

### Temporal Router

Qwen3ではTemporal ルータのhit率が

- GSM8K: **73.13%**
- MATH: **75.00%**
- CommonsenseQA: **91.61%**

となり、LRU/LFU/LRFUなどの従来型置換を一貫して上回る。

ここでの価値はhit率そのものだけではない。Temporal ルータはproactive 読み込みを0に保つので、改善が余分な先読み通信量によって作られたものではない。

### Spatio-Temporal Router

Qwen3の3 タスクで、評価した最強先読み 比較対象に対して

- 読み込み-adjusted hit rate: **+1.15〜18.03 percentage points**
- エキスパート-重み 通信量: **4.6〜53.3%削減**

を報告する。

特に後者は「エキスパート転送の回数」を直接数えたアルゴリズム上の利得であり、生のヒット率だけを見るより意味がある。

一方GPT-OSSでは改善幅はタスク依存で、すべての条件で大差を付けるわけではない。

### joint adaptationとauxiliary-only

基盤モデルを固定して補助ルータだけ学習すると、比較対象のタスク精度を保ちやすい反面、キャッシュ改善は控えめになる。

基盤モデル／元ルータまで共同事後学習した主設定ではキャッシュ利得が大きい。

これは、**既存ルーティングを予測するだけより、モデル自身を少しキャッシュしやすいルーティングへ適応させた方が転送を減らせる**ことを示す一方、元ルーティングの意味を完全固定していないというトレードオフでもある。

## 主要結果をwall-clock speedupと混同しない

論文の主要効率評価はエキスパート-ルーティング トレースに同期したキャッシュ simulatorである。

キャッシュミスや先行挿入を「エキスパート重み転送1回」として数えるため、アルゴリズムとして何回重みを運ぶかは比較できる。

しかし、実systemでは

- エキスパート size
- PCIe / NVLink 帯域
- pinned メモリ
- DMA 遅延
- 転送と計算のoverlap
- バッチ size
- multi-リクエスト contention

によって1 転送のコストが変わる。

したがって「通信量 53.3%削減 = 遅延 53.3%短縮」ではない。

特に計算と転送を完全にoverlapできるsystemでは通信量 reductionが遅延へそのまま出ない。一方、PCIe ミス待ちでGPUが停止する小バッチ環境なら大きく効く可能性がある。

## 既存研究との差

### LRU/LFUとの違い

LRU/LFUは過去のアクセスだけを見る。時間ルータは現在の隠れ状態から**将来の同じ層の要求**を学習する。

### ProMoE系prefetchとの違い

将来エキスパート予測自体は既存研究にもある。

本研究の特徴は、

- まず先読みなしのretentionだけでも学習する。
- 元の Top-Kとキャッシュ 優先度を別ルータへ分ける。
- backbone/元の ルータまでキャッシュ-aware objectiveでjoint adaptationできる。
- refinement budgetでproactive 通信量を明示的に制限する。

点にある。

### cache policyだけの研究との違い

通常は固定モデルから出たルーティングトレースを前提にキャッシュアルゴリズムを比較する。

本研究はモデル側の事後学習まで含め、「キャッシュしやすいルーティング挙動」そのものを作る方向へ踏み込む。

## 限界と適用境界

- **主要結果はトレース-driven シミュレーション。** 実機PCIe/NVLink 遅延やエンドツーエンド トークン/sは未評価。
- **joint trainingでは元ルーティングが変わる。** 純粋なキャッシュ replacementだけの公平比較ではない。
- **post-training コストが必要。** training-freeに既存モデルへ即導入する方式ではない。
- **auxiliary ルータの計算 オーバーヘッドがある。** 軽量でも各MoE positionで追加predictionが必要。
- **Spatio-Temporal ルータは誤先読みを起こす。** `R`を大きくし過ぎるとhitが増えても通信量が悪化し得る。
- **キャッシュ capacity依存。** キャッシュが十分大きければLRUでもミスが少なく、追加ルータの価値は縮む。
- **タスク/モデル依存性。** GPT-OSSではQwen3ほど一貫したgainではない。
- **オフロード backendを規定しない。** CPU DRAM、NVMe、remote メモリなど、どこからエキスパートを読み込みするかは別問題。

## 実装上の含意

最初からSpatio-Temporal ルータまで導入する必要はない。

帯域が厳しい環境では、まず**時間ルータ型の学習済み保持**を導入し、先行読み込みを増やさずミスがどれだけ減るかを見る方が安全である。

その後、実機計測で「要求時ミス待ちがGPU停止の主因」と分かった場合だけ時空間改善を追加し、`R`を帯域に合わせて調整する。

また評価ではhit rateだけでなく、

`demand loads + proactive loads`

を必ず数えるべきである。キャッシュ hitだけをKPIにすると、過剰先読み 方針を誤って高評価しやすい。
