# ProMoE: Fast MoE-based LLM Serving using Proactive Caching

> 数layer先で使うexpertを予測してCPUからGPUへ先読みし、誤予測転送を小単位で止められるようにし、GPU上にあるexpertから先に計算することで、expert weight待ちを減らすlossless MoE serving方式。

## 概要

ProMoEは、GPUに入り切らないMoE-LLMをCPU DRAMへoffloadしたとき、**必要expertがGPUにないと分かってからweightを読み始めるのでは遅すぎる**という問題を扱う。

将来のroutingを軽量predictorで推定し、必要になりそうなexpertを低優先度でGPUへ先読みする。ただしpredictorはnative routerを置き換えない。実際のgate結果が出た時点で正しいexpertを必ず実行するため、SiDA-MoEとは異なりlosslessである。

ProMoEの特徴は予測精度だけでなく、

- 実際に使う時刻よりどれだけ早く予測できたか
- 誤予測したweight転送をどれだけ早く止められるか
- 正しいexpertを待つ間に、すでにGPU上にあるexpertをどこまで計算できるか

まで含めてprefetchを設計している点にある。

## 手法のあらまし

### 1. Predictor：数layer先のexpert集合を予測する

過去のgate outputや中間情報を使い、数layer先で必要になりそうなexpert集合を予測する。

ここで重要なのは**expert IDを正しく当てるだけでは不十分**という点である。予測が実際のgate直前に出てもCPU→GPU転送が間に合わないため、早い段階で予測できることも重要になる。

### 2. `GOODPRED`：正しさだけでなく「使う時までにどれだけ届いたか」も測る

ProMoEはprefetch品質を`GOODPRED`という指標で評価する。

これは、

- 予測したexpertが実際に必要だった割合
- 実行時点までにそのexpert weightがどれだけGPUへ到着していたか

を合わせて見る指標である。

同じ予測精度でも、より早く予測して転送時間を稼げたpredictorを高く評価できる。

### 3. Expert weightを小分けして転送する

expert全体を1回の大きなtransferとして送ると、誤予測したweightの転送を始めた後に、本当に必要なexpertを急いで送りたくても長時間待つ必要がある。

そこでexpert weightを3 chunkへ分けて転送し、最大1 chunk程度の待ちで優先順位を切り替えられるようにする。

### 4. 正しいroutingが分かったら不要転送を早く止める

現在layerのnative gateが終了すると、本当に必要なexpert集合が確定する。

その時点で、不要と分かった予測expertのtransferを止め、GPUにない正しいexpertの転送を最優先へ切り替える。

これにより誤予測でPCIe帯域を浪費する時間を減らす。

### 5. GPU上にあるexpertから先に実行する

同一layerのexpertをrouter順に待つのではなく、

1. すでにGPU上にあるexpert
2. 現在転送中のexpert
3. まだ転送を始めていないexpert

のように実行順を変える。

cache済みexpertを計算している間にGPUにないweightを読み込み、**GPUが何もせずPCIe転送だけを待つ時間**を減らす。

### 6. PrefillとDecodeでは問題の出方が違う

prefillでは多数tokenが同時にroutingされるため、1 layerで触るexpert種類が広がり、最近使ったexpertを残すだけのcacheでは入れ替えが頻発しやすい。

一方decodeは1 tokenずつ進むためexpert計算自体が短く、1回のPCIe missの待ち時間が相対的に大きい。

ProMoEは両方に同じcache policyだけを当てるのではなく、prediction + 誤転送停止 + 実行順変更でそれぞれの待ち時間を減らす。

### 7. Losslessである理由

予測はweightを先に置くためだけに使われる。

native gateの結果が予測と異なった場合でも、正しいexpertをon-demandで読み、元modelと同じexpert計算を実行する。

したがって品質と速度を交換するexpert substitutionとは異なる。

## 評価

### まず見るところ
- **結論:** predictionだけでなく、誤予測転送を途中で止められることと、expert実行順の変更まで組み合わせるとCPU offload待ちを実際に短くできる。
- **速度:** Transformers実装でprefillはLRU比平均2.32×、decodeは1.33×。llama.cppでも改善。
- **品質:** native expertを必ず実行するためlossless。
- **メモリ/I/O:** CPU DRAM→GPU expert weight transferが対象。SSD/NVMeは扱わない。
- **注意点:** RTX 4090単一request中心で、continuous batching / vLLM servingは未評価。

### Transformers実装

| Phase | vs Static cache | vs LRU |
|---|---:|---:|
| Prefill | **1.52×** | **2.32×** |
| Decode | **1.52×** | **1.33×** |

prefillでLRUとの差が大きいのは、長いpromptで多数expertを触りcacheの入れ替えが頻発しやすいため。

### Qwen2系のcache-rate sweep

prefillでは、

- LRU比：平均約1.75×、最大約2.20×
- Static比：約1.43×

を報告する。

推論が直接待たされるweight loading時間はStaticで約55〜75%を占めるのに対し、ProMoEでは約11%まで低下する条件がある。

### llama.cpp実装

| Phase | vs LRU | vs Static |
|---|---:|---:|
| Prefill | 1.532× | 1.104× |
| Decode | 1.14× | 1.269× |

frameworkが変わっても改善するが、絶対値はmemory manager / kernel実装に依存する。

### Batch effect

Qwen2系でbatchを1→4へ増やすと、LRU比speedupは約1.16×→1.34×へ増える。

複数tokenが同時に多くのexpertを触るほどLRUの入れ替えが増え、proactive cacheの利点が大きくなる。

### 要素別評価

| Component | 効果の代表値 |
|---|---:|
| 誤予測転送の早期停止 | base比約1.27× |
| GPU上にあるexpertから先に実行 | base比約2.29× |

単なるpredictor追加だけでなく、**誤予測転送を止める仕組みと計算順序変更**がend-to-end速度に大きく効く。

### 制約

- 単一request / edge serving中心。
- vLLM / TGI continuous batchingは未評価。
- predictor miss時はnative expertを結局読むため、帯域不足が極端な環境では待ち時間が残る。
- INT4 / FP16、expert shape、PCIe bandwidthに性能が依存。
- SSD/NVMe tierは扱わない。
