# ProMoE: Fast MoE-based LLM Serving using Proactive Caching

> ProMoEは、GPUに入らないMoE 専門家をCPU DRAMへ置くとき、**キャッシュ 未ヒットが起きてから専門家を読むのではなく、数層先で必要になりそうな専門家を先にGPUへ運び、誤予測だった転送は細粒度で止め、すでに到着した専門家から先に計算する**方式である。予測を外しても標準 ルータが選んだ正しい専門家を必ず実行するため、速度だけを変える無損失なオフロード最適化である。

## 概要

MoE（Mixture-of-専門家）では各トークンが全専門家を使うわけではなく、層ごとに一部だけを選ぶ。

例えばDeepSeek-MoE 16.4Bは1 層に64 専門家を持つが、1 トークンで使うのは6 専門家である。この疎性を使えば、全専門家をGPUへ常駐させず、大半をCPU DRAMへ置いて必要な専門家だけGPUへ読み込める。

容量問題はこれで解けるが、次に**PCIe転送待ち**が問題になる。

通常のLRU キャッシュでは、ルータが「専門家 17が必要」と確定し、その専門家がGPU キャッシュに無いと分かった時点で初めてCPU→GPU転送を始める。転送中はその専門家を計算できないため、読み込み時間がそのまま推論の待ち時間、すなわちcritical pathへ入る。

論文のDeepSeek-MoE例では、専門家の50%をキャッシュしていてもデコード時のTPOTが67.9 ms、そのうち欠落 専門家のfetchが58.1 msを占める条件がある。単にLRU 方針を賢くするだけでは、**未ヒットした後に読む限り待ち時間そのものは消えない**。

さらにmodern decoder-のみ MoEは学習時に読込 balancingを強くかけるため、昔のSwitch Transformer系ほど「一部専門家だけが極端にhot」という分布にならない。専門家 accessが比較的均等だと、LRUや静的 hot-setのヒット 率を上げる余地も小さい。

ProMoEはこの問題を「キャッシュ ヒット率を最大化する問題」ではなく、**専門家の転送をいつ始め、どれだけGPU計算の裏へ隠せるか**という時間配置の問題として扱う。

そのため構成は大きく2つに分かれる。

1. **予測器（予測器）**：将来層で必要になる専門家を早めに予測する。
2. **先読み器（prefetcher）**：予測専門家をGPUへ運びつつ、標準 gateの確定結果に合わせて転送優先度と専門家実行順を切り替える。

## なぜ「予測精度」だけでは足りないのか

専門家 プリフェッチでは、予測が正しくても**遅すぎれば役に立たない**。

たとえば専門家 Aが次層で必要になることを99%の精度で予測できても、その予測が実行直前にしか出ないなら、数百MBの重みをPCIeで運ぶ時間を隠せない。

逆に精度80%でも、数層早く予測できて必要重みの大半を事前転送できるなら、実際の待ち時間は小さくなる可能性がある。

そこでProMoEは予測器を、

- **Accuracy**：必要専門家をどれだけ正しく当てたか
- **FetchRate**：予測した専門家のうち、実際に使う時刻までにどれだけ転送を完了できたか

の両方で評価する。

論文の指標は、

`GoodPred = Accuracy × FetchRate`

である。

つまりGoodPredは、**「正しく、かつ間に合った専門家がどれだけあるか」**を一つの値にまとめる。

これにより「正確度は高いが予測が遅い方式」と「少し外すが十分早く予測できる方式」をシステム性能に近い基準で比較できる。

## 手法

ProMoEの1 層付近の流れを簡略化すると次のようになる。

1. CPU上の予測器が、少し先の層で使われそうな専門家を予測する。
2. 予測専門家を**低優先度**でCPU DRAMからGPU キャッシュへ先読みする。
3. GPUは現在層の注意やMoE計算を進める。
4. 現在層の標準 gateが終わると、本当に必要な専門家集合が一度に確定する。
5. 予測が外れていたら、不要な低優先度転送を止め、正しい欠落 専門家を**高優先度**へ切り替える。
6. 同じ層内では、すでにGPUへ到着している専門家から先に計算する。
7. 欠落 専門家を転送している時間を、キャッシュ-ヒット 専門家の計算でできるだけ隠す。
8. 全専門家の結果を最後に元ルータ 重みで合成する。

重要なのは、**予測器がルーティングを決めない**ことである。

最終的にどの専門家を実行するかは標準 gateが決める。予測器は「先にどの重みを運んでおくか」だけを決めるため、誤予測は品質劣化ではなく余計なI/Oや待ち時間として現れる。

## 手法

### 1. 軽量学習型predictorでlayerごとのrouting相関を覚える

ProMoEは各層へ小さな2-層 MLP 予測器を用意する。1 予測器は約2M パラメータである。

offlineでモデルへ実データを流し、

- ある層へ入る中間表現
- 後続層の標準 gateが実際に選んだ専門家

をトレースとして収集する。

予測器はこの対応関係を学び、online時には現在の中間表現から将来専門家を予測する。

これはトークン IDだけで全層を予測する方法より文脈情報を多く含むため精度が高い。論文ではトークン-基づく 予測器の平均正確度が58.3%だったのに対し、ProMoEの学習した 予測器は平均84.7%を報告する。

一方で予測器を通す時間も必要である。CPU上の1 予測は約200 µsで、単一層のGPU計算に比べ小さいものの、毎層「予測 → 転送」を完全直列にすると、その200 µs分だけ専門家転送開始が遅れる。

### 2. 先読み間隔（stride prefetching）でpredictionとtransferをpipeline化する

ProMoEは予測距離を1段伸ばす**先読み間隔（stride プリフェッチ）**を使う。

単純な層単位方式では、

`layer iのpredict → layer i+1用expertをfetch`

を順に行う。

stride方式では予測器とfetcherをパイプライン化し、ある層向けの重みを転送している間に、さらに次の層を予測する。

予測距離を伸ばすと隠れ 状態の差が大きくなり正確度は少し落ちる。論文では約5%の正確度低下がある。しかし転送開始を早めてFetchRateを上げられるため、最終的なGoodPredは改善する。

ここがProMoEの設計思想をよく表している。**予測精度を最大にすることではなく、実際に必要になるまでに重みが届くことを最大化する。**

### 3. speculative transferと確定transferを2段階のpriorityで扱う

prefetcherには2種類のタスクを持たせる。

- **低優先度（low priority）**：予測器が「使いそう」と予測した投機的 プリフェッチ
- **高優先度（high priority）**：標準 gateが確定した後、本当に必要だと分かった専門家

通常は低優先度タスクでPCIe帯域を空きなく使う。

しかし確定欠落 専門家が出たら高優先度タスクへ切り替える。

これにより「予測が当たれば早く届く」「外れても正しい専門家へすぐ切り替える」という二段構えにする。

### 4. Expertを3 chunkへ分け、誤予測転送の足止めを短くする

CUDAの大きな非同期copyを開始した後、そのcopyを途中の任意byte位置で即座にpreemptすることはできない。

もし1 専門家全体を1 タスクとして転送している最中に標準 gateが別専門家を要求すると、本当に必要な専門家は現在のcopy完了まで待たされる。

そこでProMoEは専門家 重みを**chunk単位**へ分ける。

MoE 専門家は一般に3つの線形 重みから構成されるため、実装では自然に3 chunkへ分ける。

すると、誤予測専門家のchunk 2を転送中に高優先度タスクが来ても、最大で「chunk 2の完了」まで待てばよい。専門家全体の転送完了を待つ必要はない。

これは転送byte数を減らす機構ではない。**間違った投機的 I/Oが正しいI/Oを塞ぐ最大時間を小さくする機構**である。

### 5. 早期割込み（early preemption）：expertを使う直前ではなくgate直後にmissを確定する

通常のランタイムでは、専門家をID順に処理し、実際に専門家 2へ到達したとき初めて「専門家 2がキャッシュにない」と気付くことがある。

しかしMoE gateが終わった瞬間には、その層で必要な専門家一覧はすでに全部分かっている。

ProMoEはgate直後へhookを入れ、

1. その層で必要な専門家集合を取得
2. 予測していたが不要と確定した低優先度タスクを削除
3. 必要だが未到着の専門家を高優先度タスクとして追加

する。

つまりpassiveな「専門家へ到達してからキャッシュ 未ヒット処理」を、**gate直後のproactiveな確定プリフェッチ**へ変える。

これにより欠落 専門家の転送を、同じ層内の別専門家計算と重ねられる時間が増える。

### 6. 実行順変更（reordered inference）：GPUにあるexpertから先に計算する

通常枠組みが専門家 ID順に、

`1 → 2 → 4 → 5`

と実行するとする。

専門家 1, 4, 5はGPU キャッシュにあるが、2だけ欠落なら、専門家 1の後で専門家 2を待つことになる。専門家 4, 5は今すぐ計算できるのにGPUが止まる。

MoEの各専門家計算は互いに依存せず、最後にweighted sumするだけなので、実行順は交換できる。

ProMoEは、

1. キャッシュ済み専門家
2. すでに転送中の専門家
3. まだ転送開始していない専門家

の順へ並べ替える。

上の例なら、

`1 → 4 → 5 → 2`

とする。

専門家 4, 5を計算している間に専門家 2を転送できるため、PCIe待ちをGPU計算の裏へ隠しやすくなる。

### 7. Reordered inferenceはprefillのcache thrashingも抑える

プリフィルでは多数トークンを同時処理するため、1 層でほぼ全専門家が使われることがある。

この状態ではLRU キャッシュへ専門家をID順に出し入れすると、まだ後で使うキャッシュ済み専門家を早いIDの欠落 専門家が追い出し、直後に再度読み込む**キャッシュ thrashing**が起こる。

ProMoEはキャッシュ済み専門家を先に使ってから欠落 専門家を入れるため、単にGPU idleを減らすだけでなく、こうした不要な追い出しも減らす。

論文のablationではプリフィルで予測単独の効果は小さく、early preemptionと特にreordered inferenceを入れたとき改善が大きい。つまりheadline 高速化倍率は「予測器が高精度だったから」だけでは説明できない。

## 実装

ProMoEは約6,600行のC++拡張として実装され、

- Hugging Face Transformers
- llama.cpp

の両方へ統合されている。

GPU 専門家 キャッシュは層ごとのLRUを基本とし、メモリ fragmentationを避けるため連続領域を事前確保する。

予測器のトレース収集＋学習はモデルごとに一度必要で、単一GPUでおよそ1〜2時間とされる。

当時のvLLM / TGIは量子化MoEの対応と、専門家を全て揃えてからfused カーネルを走らせる実行形態がProMoEの「届いた専門家から順に計算する」方式と合いにくかったため、直接統合していない。

## 評価

### まず見るところ

- **headline:** 既存枠組み内蔵オフロード方式に対し、プリフィル平均2.20×・最大3.21×、デコード平均2.07×・最大5.02×。
- **より公平なキャッシュ 比較対象比:** hand-crafted 静的/LRU キャッシュとの比較では倍率は小さくなる。つまり最大5.02×は「最強のキャッシュ 比較対象に5倍」ではない。
- **プリフィル:** 多数専門家を使うため予測だけでは足りず、reordered inferenceによるthrashing回避が重要。
- **デコード:** 専門家 reuseが多少ありLRUも働くが、欠落 専門家転送を計算と重ねることで追加改善する。
- **品質:** 標準 gateの専門家を必ず実行するので無損失。
- **重要な反例:** Mixtralではデコード時にCPU側で専門家計算するllama.cpp オフロードがProMoEより速い条件がある。GPUへ重みを運ぶこと自体が常に最善ではない。

### abstractの2.20× / 2.07×は何か

最新版abstractは複数枠組みの既存オフロード solutionに対する集約として、

- プリフィル: **平均2.20×、最大3.21×**
- デコード: **平均2.07×、最大5.02×**

を掲げる。

ただしこれは「LRUより常に2倍以上」という意味ではない。上記の通り、強いキャッシュ 比較対象とのデコード差は1.1〜1.5×程度の条件も多い。

### Prefill ablation

TransformersではLRU 比較対象から、

- naive プリフェッチだけ: 効果が小さい、条件によって悪化
- early preemption追加: 改善
- reordered inferenceまで追加: 比較対象比最大約2.39×級

となる。

プリフィルではほぼ全専門家を使うため、予測して先読みするだけではキャッシュ内容を入れ替えているだけになりやすい。**実行順を変えてthrashingとblockingを減らすことが大きな寄与**になる。

### Cache容量を変えた場合

QW-2ではキャッシュ率を増やすにつれ、ProMoEがcritical path上で専門家 読込へ費やす割合は約69.68%から30.96%へ低下する。一方静的 キャッシュは約77.44%から56.04%までしか下がらない条件がある。

デコードでもProMoEのcritical-path 読込はDS-1 / QW-2で約25.61% / 29.20%まで下がる一方、LRUは約45.52% / 50.89%残る。

### Batch size

バッチを1→4へ増やすと、プリフィルではもともと多くの専門家を使うため遅延増加が比較的小さく、スループットを伸ばしやすい。

デコードではバッチが増えるほどactivated 専門家種類が増え、1 iterationの読込量も増えるため、スループット増加は線形にならない。

QW-2のllama.cppではProMoEのLRU比高速化倍率がバッチ 1の約1.16×からバッチ 4の約1.34×へ増える。バッチ増加でLRU thrashingが悪化するためである。

### Mixtralの反例

Mixtralは8 専門家中2つ、**25%**を毎トークン activateする。他の評価モデルは概ね10%前後である。

このようにactive 専門家比率が高いと、毎トークン大量の重みをCPU→GPUへ運ぶコストが重い。

llama.cppのデコードでは、CPUに重みを置いたままCPUで専門家計算する層 オフロードがProMoEを上回る条件がある。

これは「専門家はGPUで計算した方が必ず速い」のではなく、

`CPU compute時間` と `CPU→GPU weight転送 + GPU compute時間`

のどちらが短いかで実行場所を選ぶ必要があることを示す。

## 既存研究との差

### Mixtral-Offloadingとの違い

Mixtral-オフロードもLRUと専門家先読みを使うが、ProMoEは**予測精度だけでなくlead 時間をGoodPredで明示的に評価し、誤予測転送のpreemptionと専門家実行順までランタイムへ組み込む**。

### Pre-gated MoEとの違い

Pre-gated MoEはモデル構造を変え、次層のルーティングを前倒しして実際のgate結果として早く確定する。

ProMoEは既存モデルのルーティングを変更せず、別予測器をプリフェッチ hintとして使う。そのため誤予測はあり得るが、標準 gateへfallbackして無損失を保つ。

### SiDA-MoEとの違い

SiDA-MoEは予測器のルーティング結果自体を実推論に使うため、予測 未ヒットがモデル出力へ影響し得る。

ProMoEでは予測器はデータ movement専用なので、予測 未ヒットは遅延 / PCIe 通信量へしか影響しない。

## 限界

- 予測器をモデルごとにoffline 学習する必要がある。
- 予測器精度は入力domainが大きく変わると低下し得る。
- 主評価はconsumer PC・バッチ 1中心で、大規模multi-tenant 提供とは条件が違う。
- SSD / NVMeは扱わず、CPU DRAMに全オフロード済み 専門家が収まることを前提とする。
- 専門家を小chunkに分けるほどpreemptionは速くなるが、タスク管理やcopy発行オーバーヘッドが増えるため任意に細かくできるわけではない。
- modern fused MoE カーネルは「全専門家 重みが揃ってから一括GEMM」を前提にする場合があり、到着済み専門家から順に実行するProMoEとはランタイム設計が衝突し得る。
- active 専門家比率が高いモデルでは、GPUへ重みを運ぶよりCPUで直接専門家を計算した方がよい場合がある。

## 一般的な実装上の含意

ProMoEの重要な示唆は、オフロード キャッシュでは**ヒット 率だけを最適化しても不十分**という点である。

実際の遅延を決めるのは、

- 正しい専門家を予測できたか
- 何ms前に予測できたか
- 必要時刻までに何byte届いたか
- 誤プリフェッチが本当に必要な転送を塞いでいないか
- GPUにある仕事を先に実行できるか

である。

したがってSSD/NVMeへ階層を伸ばす場合も、単純なキャッシュ ヒット率だけでなく、**予測 lead 時間、partial-読出し進捗、preemption granularity、ready タスクのreordering**まで含めて見る価値がある。

特にstorageが遅くなるほど、GoodPredのような「正しさ × 間に合った割合」の考え方は重要になる。
