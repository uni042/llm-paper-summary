# ProMoE: Fast MoE-based LLM Serving using Proactive Caching

> 将来expertを軽量予測し、chunked prefetch・early preemption・実行順序変更でCPU→GPU転送を隠すlossless MoE serving方式。

## 概要

ProMoEは、GPUに入り切らないMoE-LLMをCPU DRAMへoffloadしたとき、**expert cache missが確定してからweightを読むのでは遅すぎる**という問題を扱う。

将来のroutingを軽量predictorで推定し、必要になりそうなexpertを低優先度でGPUへ先読みする。ただしpredictorはnative routerを置き換えない。実際のgate結果が出た時点で正しいexpertを必ず実行するため、SiDA-MoEとは異なりlosslessである。

ProMoEの特徴は、予測精度だけではなく、

- どれだけ早く予測できたか
- 誤予測transferをどれだけ早く止められるか
- 正しいexpertを待つ間に別expertを計算できるか

まで含めてprefetchを設計している点にある。

そのため `GOODPRED`、`chunked prefetch`、`early preemption`、`reordered inference` が中心概念になる。

## 手法のあらまし

### 1. Predictor：数層先のexpert集合を予測する

過去のgate outputや中間情報をsliding windowとして使い、数層先で必要になりそうなexpert集合を予測する。

ここで重要なのは**expert IDを正しく当てるだけでは不十分**という点である。

予測が実際のgate直前に出てもtransferが間に合わないため、ProMoEは「予測が正しく、かつ実行までに十分fetchできたか」を評価する。

### 2. `GOODPRED`：accuracy × fetch readiness

ProMoEはprefetch品質をGOODPREDで評価する。

概念的には、

- prediction accuracy
- expert weightが実行時点までにどれだけ到着したか

を組み合わせた指標である。

これにより、同じ予測精度でも先行時間の長いpredictorを高く評価できる。

### 3. `Chunked Prefetch`

MoE expert FFNは複数linear weightからなる。

expert全体を1 transferとして送ると、低優先度の誤予測transferが始まった後、正しいmiss expertを緊急転送したくても長時間interruptできない。

そこでweightを3 chunkへ分けて転送し、最大1 chunk程度の待ちでpriorityを切り替えられるようにする。

### 4. `Early Preemption`

現在層のnative gateが終了すると、本当に必要なexpert集合が確定する。

その時点で、不要と分かったprediction transferを即座に止め、native miss expertの転送を高優先度へ切り替える。

これにより誤予測のbandwidth wasteを抑える。

### 5. `Reordered Inference`

同一層のexpertをrouter順に待つのではなく、

1. GPU cache hitしているexpert
2. transfer中のexpert
3. まだtransferを始めていないexpert

のように実行順を変える。

cache済みexpertを計算している間にmiss weightを読むことで、PCIe待ちをexpert GEMMへ重ねる。

### 6. PrefillとDecodeではボトルネックが違う

prefillでは多数tokenが同時にroutingされるため、1層で触るexpert集合が広がり、LRU cache thrashingが起きやすい。

一方decodeは1 tokenずつ進むためexpert GEMM時間が短く、1回のPCIe missが相対的に重い。

ProMoEは両方に同じcache policyを当てるのではなく、prediction + preemption + reorderingによってそれぞれのstallを減らす。

### 7. Losslessである理由

予測はweight placementのhintにだけ使われる。

native gateの結果が予測と異なった場合でも、正しいexpertをon-demandで読み、native computationを実行する。

したがって品質改善を速度と交換するexpert substitutionとは異なる。

## 評価

### まず見るところ
- **結論:** predictionだけでなくtransferの中断性とexpert実行順まで最適化すると、consumer GPUでもCPU offload待ちを実際に短くできる。
- **速度:** Transformers実装でprefillはLRU比平均2.32×、decodeは1.33×。llama.cppでも改善。
- **品質:** native expertを必ず実行するためlossless。
- **メモリ/I/O:** CPU DRAM→GPU expert weight transferが対象。SSD/NVMeは扱わない。
- **注意点:** RTX 4090単一request中心で、continuous batching / vLLM servingは未評価。

### Transformers実装

| Phase | vs Static cache | vs LRU |
|---|---:|---:|
| Prefill | **1.52×** | **2.32×** |
| Decode | **1.52×** | **1.33×** |

prefillでLRUとの差が大きいのは、長いpromptで多数expertを触りcache thrashingしやすいため。

### Qwen2系のcache-rate sweep

prefillでは、

- LRU比：平均約1.75×、最大約2.20×
- Static比：約1.43×

を報告する。

critical path上のweight loading時間はStaticで約55〜75%を占めるのに対し、ProMoEでは約11%まで低下する条件がある。

### llama.cpp実装

| Phase | vs LRU | vs Static |
|---|---:|---:|
| Prefill | 1.532× | 1.104× |
| Decode | 1.14× | 1.269× |

フレームワークが変わっても改善するが、絶対値はmemory manager / kernel実装に依存する。

### Batch effect

Qwen2系でbatchを1→4へ増やすと、LRU比speedupは約1.16×→1.34×へ増える。

複数tokenが同時にexpertを触るほどLRUのthrashingが増え、proactive cacheの利点が大きくなる。

### Ablation

| Component | 効果の代表値 |
|---|---:|
| Early preemption | base比約1.27× |
| Reordered inference | base比約2.29× |

単なるpredictor追加だけでなく、**誤予測転送を止める仕組みと計算順序変更**がend-to-end速度に大きく効く。

### 制約

- 単一request / edge serving中心。
- vLLM / TGI continuous batchingは未評価。
- predictor miss時はnative expertを結局読むため、帯域不足が極端な環境ではstallが残る。
- INT4 / FP16、expert shape、PCIe bandwidthに性能が依存。
- SSD/NVMe tierは扱わない。
