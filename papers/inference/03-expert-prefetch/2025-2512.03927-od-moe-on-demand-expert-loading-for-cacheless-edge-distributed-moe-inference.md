# OD-MoE: On-Demand Expert Loading for Cacheless Edge-Distributed MoE Inference

> 常設expert cacheを持たず、軽量化した別modelで数layer先のexpertを予測し、複数worker GPUへ必要expertだけを実行直前に読み込む。予測が外れた場合はnative routerの正しいexpertを追加ロードする分散edge MoE方式。

## 概要

OD-MoEは、GPUへhot expertを固定常駐する通常のcache方式をやめ、**必要expertを実行直前だけworker GPUへ載せ、計算後すぐ解放する**設計である。

構成はmain node、shadow node、8 worker nodesの計10台。

- main：attention / gateなどnon-expert部分とnative routing
- shadow：元modelを軽量化したmodelを並行実行し、数layer先のexpertを予測
- workers：予測されたexpert weightを読み込んでFFNを実行

に役割を分ける。

予測ミス時もmain nodeのnative gate結果に従って正しいexpertを後からloadするため、品質はlossless。代わりにnode間通信とshadow model計算のコストを負担する。

## 手法のあらまし

### 1. `SEP`：軽量化した別modelで将来routingを予測する

shadow nodeは元modelの構造を保った軽量版をFP16 / INT8 / NF4で実行し、数layer先のexpert routingを予測する。

論文では`Shadow-Emulative Predictor (SEP)`と呼ぶ。単純classifierでexpert IDだけを当てるのではなく、**元modelのtoken処理を軽量modelで少し先まで追跡し、そのrouter出力を将来予測として使う**方式である。

### 2. Main modelとshadow modelの状態を定期的に揃える

autoregressive生成ではshadow側の予測tokenやKV状態が少しずつmain側とずれる。このずれが蓄積すると将来routing予測も外れやすくなる。

そのため、

- shadow側で使うtokenをmainの実生成tokenへ合わせる
- 必要なKV状態を同期する

ことで、shadow modelがmain modelから離れ過ぎないようにする。

この同期を省くと長いgenerationでrouting recallが急落する。

### 3. 8 workerを4 groupに分け、計算と次expertのloadを交代で進める

MixtralのTop-2に合わせ、8 workerを2台ずつ4 groupへ分ける。

あるgroupがlayer `l` のexpertを計算している間に、他groupが `l+1`,`l+2`,`l+3` で必要になりそうなexpertをloadする。

layerが進むたびに「今計算するgroup」と「先のexpertをloadするgroup」を順番に交代し、network / storageからのloadをexpert computeと同時に進める。

### 4. 常設cacheを持たない

workerはexpertを恒久的にcacheしない。

予測されたexpertを実行直前にloadし、計算後は解放する。

hot expert用にGPU memoryを固定予約しないため、layerごとのexpert需要が大きく変わっても、その時必要なexpertへmemoryを使える。

### 5. Prediction missは速度だけを損なう

SEP予測とnative gateが一致すればexpertは準備済み。

不一致ならnative expertを追加loadしてから実行する。

したがって誤予測したexpertを代用品として使わず、出力品質を変えない。

### 6. GPU memory削減の代わりにnode間通信が増える

main / shadow / worker間でtoken状態やKV状態を送るため、worker GPU memoryを小さくできる代わりにnetwork trafficが増える。

論文の実機は1 Gbps Ethernetで、この帯域とshadow-main状態同期の頻度がend-to-end性能に直接効く。

## 評価

### まず見るところ
- **結論:** 常設expert cacheを持たなくても、高い予測精度を持つshadow modelとworker pipelineがあればedge clusterでMoEを動かせる。
- **速度:** decode平均約3.69 t/s。既存offload系を上回るがall-GPUには届かない。
- **品質:** predictionはloading専用で、native expertへfallbackするためlossless。
- **メモリ:** worker GPUを各約1GBまで削れる一方、shadow nodeに約45GB必要。
- **注意点:** 10-node構成と状態同期trafficが大きな実装コスト。

### Testbed

| Role | 台数 | 主用途 |
|---|---:|---|
| Main | 1 | non-expert計算 / native gate |
| Shadow | 1 | 将来expert予測 |
| Worker | 8 | expert load / compute |

Networkは1 Gbps Ethernet。

### 将来expertを予測集合へ含められる割合

| Shadow precision | Expert recall |
|---|---:|
| FP16 | **99.94%** |
| INT8 | 97.34% |
| NF4 | 95.67% |

### GPU memory

総GPU memoryは約60GB。

- main：約7GB
- shadow：約45GB
- workers：各約1GB

全expertをcacheする構成の約1/3まで削減する。

### Throughput

| Method | 平均 output throughput |
|---|---:|
| OD-MoE | **3.37 t/s** |
| Mixtral Offloading | 2.17 |
| MoE-Infinity | 0.67 |
| HOBBIT | 0.76 |
| AdapMoE | 3.04 |

OD-MoEのdecode単体は平均約3.69 t/s。

all-GPU Transformerは約4.89 t/sで、完全全載せには及ばない。

### TTFT

平均TTFTは約2244 ms。

AdapMoE約1387 ms、Mixtral Offloading約1845 msより遅く、shadow model準備や状態同期がprefill側では不利になる。

### State alignmentの重要性

INT8 shadowでmainとの状態同期を外すと、routing recallはtoken 1で100%近くてもtoken 256付近で約30%、平均約45%まで低下する。

長いgenerationほどshadow modelをmainの実状態へ戻す同期が必要になる。

### 制約

- 10 node必要。
- shadow nodeが大容量GPU memoryを消費。
- 1 Gbps network同期が性能へ影響。
- 主評価はMixtral-8x7B。
- TTFTでは一部baselineに劣る。
