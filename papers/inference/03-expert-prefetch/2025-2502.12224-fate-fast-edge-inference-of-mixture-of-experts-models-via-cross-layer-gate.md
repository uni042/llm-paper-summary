# Fate: Fast Edge Inference of Mixture-of-Experts Models via Cross-Layer Gate

> 現在層のルータ入力から次層で使うエキスパートを予測し、浅い層には多めのエキスパートをGPUへ置き、深い層は先読みで補う。さらに利用頻度の低いエキスパートだけを強く量子化してedge環境の転送待ちとメモリ使用量を減らす。

## 概要

Fateは、別のpredictor networkを追加せず、**隣接層のルータ入力が似ている**という性質を使って次層 エキスパートを予測するedge向けMoE オフロード方式である。

浅い層はエキスパート選択が比較的ばらけて予測しにくい一方、深い層は一部エキスパートへ選択が偏りやすく予測しやすい、という観察をGPU キャッシュの配分にも使う。

そのため、

- 現在層の状態から次層 エキスパートを予測して先読みする
- 浅い層には多めのエキスパートをGPUへ常駐させる
- 最近使ったエキスパートと長期的によく使うエキスパートの両方を見てキャッシュを入れ替える
- 利用頻度の低いエキスパートだけをINT2へ落とすmixed-bit 量子化

を一つの設計として組み合わせる。

先読み自体はnative ルーティングの補助だが、最速構成ではエキスパート 重みをINT2へ量子化するため、system全体としては完全無損失ではない。

## 手法のあらまし

### 1. 現在layerのrouter入力から次layer expertを予測する

層 `i` と `i+1` のルータ入力表現には高いcosine similarityがある。

Fateは現在層の中間表現を使って、次層で選ばれそうなエキスパートを追加predictorなしで推定する。

GPU上で別modelを動かさないため、予測オーバーヘッドを小さくできる。

この予測はnative ルータを置き換えるのではなく、次層の重み transferを早く始めるためのhintとして使う。現在層を計算している間に次層候補エキスパートをCPUからGPUへ動かし、実際に次層へ到達した時点では本来のルータ結果を使う。予測が当たれば転送待ちを隠せるが、外れた場合は不足エキスパートをon-demandで追加loadするため、予測誤りそのものが別エキスパートへ誤ルーティングするわけではない。したがって先読み部分は品質を変えず、品質差が生じるのは主に後段の低bit量子化設定である。

### 2. Prefillでは複数tokenの予測expertをまとめる

プリフィルでは多数トークンが同時に流れるため、トークンごとの予測エキスパートをまとめると、実際に次層で使われるエキスパート集合を高い割合で先読みできる。

この複数トークンの利用頻度を転送順にも使い、よく使うエキスパートをGPUで計算している間に、利用頻度の低いエキスパートをCPUからGPUへ送る。

### 3. 浅いlayerには多めのexpertをGPUへ置く

浅い層ではエキスパート選択が均等に近く、次に使うエキスパートを予測しにくい。

そこで浅い層の一定範囲 `L` までは、できるだけ多くのエキスパートをGPUへ常駐させて予測ミスによる転送待ちを避ける。

深い層はルーティングが一部エキスパートへ偏りやすいため、小さいキャッシュでも先読みで補える。

これはGPU キャッシュを全層へ均等分割する方式との違いである。浅い層で予測精度が低いのにキャッシュまで小さくすると、毎回異なるエキスパートがmissしてPCIe待ちが露出しやすい。一方、深い層ではルーティング候補が偏り、次層予測も当たりやすいため、常駐数を減らしても必要エキスパートを計算前に準備しやすい。Fateは『予測が難しい場所ほど常駐 capacityで守り、予測しやすい場所ほど先読みへ依存する』という形で限られたVRAMを非均等に配る。

### 4. 最近使ったexpertと長期的によく使うexpertを両方残す

単純LRUでは、たまたま直近で一度使われたエキスパートと、長期間にわたり何度も使われるエキスパートをうまく区別できない。

FateはARC（適応型 Replacement キャッシュ）を使い、**最近使われたエキスパート用の領域と、繰り返し使われるエキスパート用の領域を分け、その比率をワークロードに合わせて自動調整する**。

この二種類を分ける理由は、MoE ルーティングに短期的な局所性と長期的な人気度の両方があるからである。直近リクエストだけで急に使われたエキスパートをすべて残すと、長期間頻出するエキスパートが追い出される可能性がある。逆に累積頻度だけを見ると、現在のリクエストで急に必要になったエキスパートへ適応しにくい。ARCはmissの出方に応じてrecency側とfrequency側の容量比を動かし、ワークロードが変化したときに固定LRU/LFUより追従しやすくする。

### 5. 利用頻度の低いexpertだけをINT2へ落とす

基本はINT4 エキスパートを使い、プリフィルで利用頻度の低いエキスパートだけ一部INT2へ落とす。

よく使うエキスパートをINT2にすると品質影響が大きいため、cold側だけを低bit化する。

Qwen1.5ではINT2比率25%などを例に、品質劣化を約1%以内へ抑える運用点を探す。

### 6. Decodeはprefillと別扱い

デコードでは1 トークンずつしか進まず、プリフィルのように多数トークンのエキスパート利用傾向をまとめて判断できない。

そのため全エキスパートをINT4中心で扱い、次層 エキスパート予測の正確さを優先する。

## 評価

### まず見るところ
- **結論:** 隣接層の表現だけで次層 エキスパートを予測しても、edge PCでは十分大きな先読み効果が得られる。
- **速度:** プリフィルでLoad-on-Demand比最大約4.5×、EAP比最大約1.9×。
- **品質:** INT4は小劣化だが、INT2を広げると明確に低下する。最速構成は近似。
- **メモリ:** 予測しにくい浅い層へキャッシュを多く割き、深い層は予測先読みで補う。
- **注意点:** 浅い層をどこまで常駐させるかとINT2比率はmodel / ワークロードごとの調整が必要。

隣接表現の平均similarityは代表値で約93.05%、88.83%、83.84%。

| Phase | Prediction accuracy |

### Prefill throughput

高性能PCではLoad on Demand比最大約4.5×、EAP比約1.9×。

DeepSeek prompt 512では最大約804 トークン/sを報告する。

低性能PCでもLoad on Demand比約1.8×、EAP比約1.5×。

### Decode

Qwenでは約14 トークン/s。DeepSeekではLoad on Demand比最大約3.7×、EAP比約2.2×。

全条件ではLoad on Demand比最大約2.3×、EAP比約1.6×程度の改善として整理される。

### Quantization quality

Qwen1.5 MMLUの代表値。

| Precision | Accuracy |
|---|---:|
| Original | 59.6 |
| INT8 | 59.6 |
| INT4 | 59.4 |
| INT2 | 55.1 |

INT4は小差だがINT2は約4.5 point低下するため、cold エキスパートだけを選択的にINT2化する。

### 制約

- PCIe3環境ではI/Oが強い律速。
- 浅い層を多く常駐させる境界 `L` はmodel依存。
- INT2比率もquality target依存。
- prediction miss時のon-demand loadは残る。
- SSD/NVMeは主要tierではない。
