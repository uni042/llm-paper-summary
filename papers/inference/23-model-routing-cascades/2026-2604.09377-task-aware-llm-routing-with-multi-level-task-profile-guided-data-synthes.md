# Task-Aware LLM Routing with Multi-Level Task-Profile-Guided Data Synthesis for Cold-Start Scenarios

> ドメイン内学習データがないコールドスタートでもLLMルーティングを可能にするため、階層タスク分類から質問応答データを合成して学習し、潜在タスクタイプ変数と分類由来の事前分布による正則化で回帰型ルーターの汎化を高めた研究。

## 概要

大規模言語モデルはモデルごとに性能と費用が大きく違い、簡単な質問へ最大のモデルを使うのは無駄で、難しい質問へ小さいモデルを使うと品質が落ちる。そこでクエリごとに候補モデルの中から、利用者の費用と性能の重み付けに合うものを選ぶルーティングが使われる。既存のルーターは、対象ドメインの質問集合へ全候補モデルを実際に走らせ、正解率などの性能とトークン費用を測った教師データで学習するのが前提だった。新しいサービスや個人の用途ではこの教師データを用意できず、別ドメインで学習したルーターを持ち込むと分布のずれで、費用許容度に応じて大きいモデルへ切り替えるだけの単純な規則より悪化することさえある。これがコールドスタート問題である。

本論文は2段構えでこれを解く。第1段はデータ合成である。ドメインの短い説明だけを種に、大規模言語モデル自身にドメイン、サブカテゴリ、難易度の3階層のタスク分類を再帰的に作らせ、品質評価役の自己批判で冗長や抜けを直し、難易度レベルのタスクプロファイルごとに多様な質問応答ペアを合成する。全候補モデルをこの合成質問へ走らせれば、対象ドメインの実データなしにルーターの教師データが得られる。第2段はルーター本体のTRouterである。クエリの表面特徴から直接性能と費用を回帰する代わりに、潜在変数としてのタスクタイプを間に挟み、クエリがどのタイプらしいかという分布と、タイプとモデルの組ごとの指標予測を組み合わせて予測する。合成分類から得た事前分布でこの分布を正則化する点が、分布のずれへの強さの源泉になる。

代表結果として、従来指標で測る評価では、合成データだけで学習したコールドスタート条件で効用合計（費用優先、均衡、性能優先の3設定の効用の和）が0.5274（合成はgpt-4.1）から0.5382（合成はgemini-2.5-flash）となり、教師データを使わない最良の比較対象である規則ベースの0.4913や、別ドメインで学習したRouterDCの0.4676を上回った。ドメイン内データで学習できる条件でも効用合計0.5925で、回帰型のMetricRouterの0.5741やRouterDCの0.5667を超え、正解を知るオラクルの0.7037に次ぐ位置にある。

## 問題設定

ルーティングの目的関数は、クエリqとモデルmについて、性能rと費用cへ利用者の重み（性能の重みと費用の重みの和は1）を掛けた効用U＝性能の重み×rマイナス費用の重み×cを最大化するモデル選択である。性能はタスクごとに正解率やF1などで測られ、費用は入出力トークン数へモデル単価を掛けて決まる。学習型ルーターには分類型と回帰型がある。分類型は教師データ上で効用最大のモデルを正解ラベルとして学習し、回帰型は性能と費用そのものを予測して推論時に効用を計算するため、利用者の重みの変更やモデル枠のある一括ルーティングへ柔軟に対応できる。本論文は回帰型を土台にする。

不足している資源は計算ではなく教師信号である。教師データを得るには、質問集合の各質問へ候補モデル全部を走らせて性能と費用を測る必要があり、候補が増えるほど費用が膨らむ。新規ドメインでは質問集合自体がない。さらに、別ドメインの教師データで学習しても、質問の分布とモデル間の優劣の付き方がドメインで変わるため汎化しない。論文の実測でも、別ドメイン学習のRouterDCとMetricRouterは単純な規則ベースに及ばない条件がある。つまり問題は「ルーターの表現力」ではなく「対象ドメインの分布を表す学習信号を、実データ収集なしにどう作るか」と「限られた信号から分布のずれに強い予測をどう組むか」の2点に分解できる。本論文は前者に合成、後者にタスクタイプという中間表現で答える。

## 手法のあらまし

処理は学習時と推論時で分かれる。学習時はまず、種になるドメイン説明からタスクタイプ生成器が3階層の分類を再帰的に展開し、タスクタイプ品質評価器が自己批判を繰り返して分類を整える。次に質問応答ペア生成器が、難易度レベルのタスクタイプとその親の説明を合わせたタスクプロファイルごとに質問応答ペアを合成し、意味的類似度が高い重複を捨てる。全候補モデルを合成質問へ走らせ、性能と費用を測って教師データを完成させる。この教師データでTRouterを学習する。TRouterは文埋め込みでクエリとタスクタイプ定義を符号化し、タスク認識モジュールがクエリのタイプ分布を出し、指標予測モジュールがタイプとモデルの組ごとに性能と費用を予測して分布で重み付けする。推論時は新しいクエリについて全候補モデルの予測効用を計算し、最大のモデルを選ぶ。

## 手法

### 1. 階層タスク分類の構築 — 生成器と品質評価器で分類を作る仕組み

タスクタイプ生成器が観測するのは人手で書いたドメイン説明であり、保持する状態はドメイン、サブカテゴリ、難易度の3階層からなる分類木である。各タスクタイプには短い名前、定義、例が付く。生成器は親タイプの定義を条件付きプロンプトとして子タイプを複数作り、互いに重ならないように再帰的に展開する。過度な細分化を防ぐため、ノード数の上限をプロンプトの制約として与える。

品質評価器は、生成された子タイプの集合を無作為な順序で読み直し、冗長さが小さいか、具体的か、抜けがないかという基準で自己批判する。修正が要ると判断すれば集合を直し、連続する複数回の評価で修正不要になるまで繰り返す。これにより減るボトルネックは、分類の質がそのまま合成データの分布の質を決めるという依存である。分類に重なりや抜けがあると、合成質問は偏った分布になり、ルーターはテスト時の分布を取りこぼす。追加費用は大規模言語モデルによる生成と評価の呼び出しであり、論文の実装では開始時の6ドメインから10ドメインへ広げ、ドメインあたり最大10サブカテゴリと5段階の難易度まで展開している。分類が実分布とずれた場合は合成全体がずれるため、この段階の人手による種ドメインの与え方が品質の上限を決める。

### 2. 質問応答ペア生成 — プロファイルごとに多様な質問を合成する仕組み

質問応答ペア生成器が観測するのは、難易度レベルのタスクタイプの名前と説明に親タイプの説明を合わせたタスクプロファイルであり、保持する状態は生成済みペアの集合とその埋め込みである。生成はバッチ単位で進み、新しいペアと既存ペアの意味的類似度を文変換モデルで計算し、最大類似度が0.9を超えるペアは近重複として捨てる。プロファイルあたりの目標数（実装では40ペア）に達するまで生成と選別を繰り返す。

難易度レベルで条件付けることが効く理由は、費用と性能がタスクの種類と難易度に強く結びついているためである。ドメインやサブカテゴリの粒度で条件付けると、似た質問ばかりが増えて検証済みペア数の伸びが鈍るのに対し、難易度レベルではほぼ線形に多様なペアが増えることが論文の比較で示されている。gpt-4.1による合成では10ドメイン、103サブカテゴリ、447の難易度ノード、17880ペアが得られた。追加費用は合成と候補モデル全実行の計算であり、実データを集めて人手でラベル付けする費用との交換になる。合成ペアの個々の正しさは網羅的には検証されておらず、ノイズは残る。ただし後段のTRouterが個別ペアではなくタイプ単位の分布として信号を使うため、単一ペアのノイズには比較的強い、というのが論文の設計判断である。

### 3. TRouter — 潜在タスクタイプを挟む回帰型ルーター

TRouterが観測するのはクエリ本文であり、保持する状態はタスクタイプ定義の埋め込みと、タイプとモデルの組ごとに学習した指標予測器である。理論的な骨格は、クエリとモデルの組に対する指標の条件付き分布を、潜在タスクタイプで周辺化して表すことにある。性能はタイプとモデルが決まればクエリ自体には依存しない、タイプはモデルには依存せずクエリだけで決まる、という2つの条件付き独立を置くと、予測は「クエリがタイプである確率」と「タイプとモデルに対する指標」の積の和になる。

実装は2つのモジュールからなる。タスク認識モジュールは、クエリ埋め込みと全タスクタイプ埋め込みを連結して多層パーセプトロンへ通し、温度付きソフトマックスでタイプ分布を出す。学習では正解タイプへの交差エントロピー損失が、変分下限における事前分布への正則化項に対応する。指標予測モジュールは、指標とモデルの組ごとに、タイプ埋め込みへの多層パーセプトロンの出力をタイプ分布で重み付けして合計し、性能と費用の予測値を出す。学習は二乗誤差で行い、認識の損失と合わせて最適化する。推論時は候補モデルごとに予測効用を計算し、最大のものを選ぶ。

この中間表現が効く理由は、クエリの表面特徴と指標の関係を直接覚えるのではなく、「どの種類の課題か」という意味構造を経由させるため、分布がずれてもタイプ単位の優劣関係が残りやすいことにある。タスク正則化を外すとMetricRouterと等価になり、論文の比較では同じ合成データでも全ショット数でTRouterが上回り、MetricRouterはショット数を増やす途中で不安定に上下する。追加費用は推論時の埋め込み計算とタイプ数×モデル数分の小さな予測であり、候補モデルの実行費用に比べれば無視できる水準である。誤り時の挙動としては、タイプ認識が外れると重み付けがずれて予測効用が歪むが、分布として複数タイプへ確率を分散させるため、単一タイプへの決め打ちよりは劣化が緩やかになる。

### 4. データと制御の流れ

学習時の一巡は、ドメイン説明、分類の構築、プロファイル別合成、候補モデルの全実行による測定、ルーター学習の順である。推論時は、クエリの埋め込み、タイプ分布の推定、モデル別効用の計算、最大効用モデルの選択、という流れで、選択されたモデルだけが実際に実行される。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| タスクタイプ生成器 | ドメイン説明 | 3階層の分類を再帰的に展開する | 教師データの分布設計 | 種ドメインの人手指定が要る |
| タスクタイプ品質評価器 | 子タイプの集合 | 自己批判を繰り返して冗長と抜けを直す | 分類の質と合成の偏り | 大規模言語モデルの追加呼び出し |
| 質問応答ペア生成器 | タスクプロファイル | バッチ生成と類似度0.9超の重複除去を繰り返す | 多様な教師信号 | 合成ノイズが残る |
| タスク認識モジュール | クエリ埋め込み | タイプ分布を推定し事前分布で正則化する | 分布のずれへの強さ | 認識誤りが効用予測へ伝わる |
| 指標予測モジュール | タイプ埋め込み | タイプとモデルの組ごとに性能と費用を予測し分布で合成する | 効用最大のモデル選択 | タイプ粒度の設計に依存する |

## 評価

### まず見るところ

- **結論:** 合成データはコールドスタートの実用的な代替になり、TRouterはコールドスタートとドメイン内の両方で既存ルーターを上回る。ただし正解を知るオラクルとの差は残り、ドメイン内データが使えるなら使った方がよい。
- **速度・効率:** ルーター自体の推論費用は小さく、主張の中心は遅延ではなく効用である。費用の節約は、難しいクエリだけを大きいモデルへ回す選択の結果として現れる。
- **品質:** 生成品質そのものは選択された候補モデルに依存する。合成データのノイズと、審査役による性能推定の偏りが選択品質の上限になる。
- **評価の強さ／注意点:** 性能の測り方が結果を左右する。従来指標と審査役評価の2通りで結論の向きは一致するが、数値の水準は大きく違い、論文自身が評価手順の統一を推奨している。

## 既存研究との差

RouterDCは対照学習による分類型、GraphRouterは課題とクエリとモデルの異種グラフ上の辺予測、MetricRouterは文埋め込みからの回帰であり、いずれもドメイン内の教師データを前提に予測器の構造を工夫する研究だった。FrugalGPTのようなカスケード方式はテスト集合全体へ固定のモデル列を割り当てるため、クエリ単位の選択とは粒度が違う。本論文の差は2つある。第1に、教師データの作り方自体を対象にし、ドメイン説明から分類と質問を合成してテスト時分布を近似する枠組みをルーティングへ初めて持ち込んだ点である。第2に、回帰型ルーターへ潜在タスクタイプと合成分類由来の事前分布を導入し、予測をタイプ単位の構造で正則化した点である。

## 限界・実装状況

- 種になるドメインの指定には最小限の人手が要る。対象業務の高水準な文脈が分かっている前提であり、完全に無人の立ち上げではない。裏返せば、低品質な子タイプの剪定や人手の事前知識の注入という制御点にもなる。
- 合成した質問応答ペアは網羅的には検証されていない。タイプ単位で信号を集約する設計が単一ペアのノイズへの耐性になっているというのが論文の主張であり、実測のショット数実験がそれを支えるが、保証ではない。
- 審査役による性能推定はモデルの偏りを持ち込む。主実験では審査役にgpt-4.1-nanoを選び、候補がQwen系とGemma系であることで自己選好の偏りを避ける配慮がされているが、評価手順とテスト条件の評価方法を揃えることが実務上の前提になる。
- 公式コードはGitHubで公開されており、合成と学習の再現は可能である。ただし合成には有料の大規模言語モデルの呼び出し費用がかかる。

## 一般的な実装上の含意

ルーティングを新規ドメインへ導入する際は、予測器の構造より先に「対象分布を表す学習信号をどう作るか」を設計すべきである。ドメインの分類を先に作り、その分類の粒度で信号を集約すると、個々のサンプルのノイズに強い学習ができる。また、費用と性能のように課題の種類へ強く依存する指標は、クエリの表面特徴から直接回帰するより、課題タイプのような意味的な中間表現を経由させる方が分布のずれに強い。評価手順については、学習時と運用時で性能の測り方を揃えることが、合成データ利用の前提条件になる。
