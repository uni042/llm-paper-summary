# KVMem: Virtualizing Million-Token Agent Workspaces on a Consumer GPU

> KVMemは「100万トークンをGPUで一度に注意機構する」仕組みではない。**エージェントが過去に処理した100万トークン規模の履歴を検索可能な論理ワークスペースとして保持し、その時の質問に必要な一部だけをモデル本来の文脈 窓へ戻して推論する**仕組みである。しかも古い履歴をテキストとして保存するのではなく、すでに計算済みのKV キャッシュをGPU、CPU メモリ、NVMeへ階層化して保存するため、選び直した履歴を毎回最初からプリフィルし直す費用を減らせる。

## まず2種類の「context不足」を分けて考える

長時間動くLLM エージェントでは、shell コマンド、ツール 結果、コード diff、誤差 ログ、会話履歴などが何時間も蓄積する。

このとき問題になる上限は1つではない。

### 1. GPUのKV cache容量

Transformerは過去トークンへ注意機構するため、各層で鍵/値をKV キャッシュとして保持する。文脈が長くなるほどKV キャッシュはほぼトークン数に比例して増える。

モデル 重み自体がGPUへ収まっていても、長いエージェント セッションではKV キャッシュだけでVRAMを圧迫する。

### 2. Model自身のnative context window

仮にKV キャッシュをCPUやSSDへ退避できても、モデルが一度に扱える文脈 長さには上限がある。

例えば論文のQwen3.6/3.8-27B構成ではネイティブ 文脈が256K トークンである。1M トークン分の履歴をSSDへ保存できても、1回のforward passで1M トークンすべてを注意機構へ渡せるわけではない。

したがって単純なKV オフロードだけでは

`GPU memory capacity問題`

は解けても

`native context window問題`

は解けない。

KVMemはこの2つを同時に扱うため、**論理ワークスペース（論理 作業領域）**と**実行ビュー（実行 ビュー）**を分離する。

## Logical workspaceとexecution view

KVMemではエージェントがこれまで蓄積した履歴全体を論理 作業領域として保持する。

この作業領域はGPUに常駐する必要も、モデルのネイティブ 文脈内へ全部入る必要もない。

一方、実際の1回の推論でモデルが見る履歴だけを実行 ビューとしてGPU上へ実体化する。

例えば

- accumulated 作業領域: 1,000,000 トークン
- ネイティブ モデル 文脈: 256,000 トークン
- 現在 検索 予算: 64,000 トークン

なら、100万トークンは検索可能なメモリとして残すが、その問い合わせで実際に注意機構へ入る履歴は選択された数万トークン程度に制限する。

この意味でKVMemの「1M-トークン 作業領域」は**1M-トークン 完全な-文脈 注意機構**とは異なる。

## 既存のcontext overflow対策は何が問題なのか

### 要約・圧縮（compaction）

古い履歴をLLMで要約へ圧縮すれば文脈は小さくできる。

しかしエージェントでは、後から必要になる情報が細かいことがある。

- 正確な誤差 message
- 以前試したコマンドのoption
- ファイル 経路
- ツール 呼ぶの順序
- 以前の失敗理由

要約作成時点で重要でないと判断されたdetailは消えてしまい、後から復元できない。

### Text retrieval

古い履歴をテキストのまま外部データベースへ保存し、現在問い合わせに近い塊だけ検索する方法もある。

こちらは原文を保持できるが、取得したテキストをLLMへ再投入すると、その部分について**もう一度プリフィルしてKVを作り直す**必要がある。

エージェント自身はそのテキストを過去stepで一度処理済みなのに、検索のたびに同じ計算を繰り返す。

KVMemはここを変え、過去contentを「テキスト」ではなく**計算済みKV 状態**として保持する。

## KV stateをmemoryとして再利用するとはどういうことか

プリフィルでは各トークンについて層ごとの鍵/値が作られる。

通常、そのセッションが終わるかKVが追い出すされると状態は捨てられる。

KVMemでは処理済み履歴を固定トークン数の**KV ブロック**へ分割し、GPUから溢れたブロックを

`GPU → CPU DRAM → NVMe`

というメモリ 階層へ退避する。

後でその履歴が必要になったとき、元テキストを再tokenize・再プリフィルする代わりに、保存していたKV ブロックをGPUへ戻す。

これが「KV-文脈 仮想化」の中心である。

## Virtual memoryとの類似

通常のOS仮想メモリでは、プロセスから見えるaddress space全体を物理DRAMへ置く必要はない。

今使うページだけDRAMへ置き、低温 ページをSSDへ逃がす。

KVMemも概念的には近い。

- 論理 作業領域 = エージェントから見える大きなメモリ空間
- KV ブロック = ページ
- GPU KV 容量 = 高速だが小さい物理 メモリ
- CPU DRAM / NVMe = 遅いが大きいbacking 階層
- 現在 問い合わせ = 今どのページが必要かを決めるアクセス signal

ただしOS ページ 欠落と違い、KVMemは単純な最近使用順だけでページを選ばない。現在問い合わせとの**意味的関連性**を使う。

## Model-native attention-space index

KVMemは別のembedding モデルへテキストを通して検索索引を作ることを必須にしない。

代わりに、モデル自身がすでに注意機構計算で作った鍵表現を利用して履歴上 ブロックを要約し、現在 問い合わせとの関連度を測る。

公式実装の標準的な `mean-k` では、ブロック内鍵の平均をブロック 要約として持ち、問い合わせに対してどのブロックが注意機構上重要になりそうかを点数する。

公式実装には現在、

- `mean-k`
- `per-token`
- `sub-block-mean-k`
- `key-direction-fixed4`
- `key-direction-adaptive`

など複数検索 scorerがある。

これらは「何をメモリとして保存するか」を変えるのではなく、**保存済みブロックのどれを今回実行対象 ビューへ戻すか**を変える。

## Query-conditioned retrieval

エージェントの次の質問が変われば、必要な過去も変わる。

例えば長いコーディング セッションで

- 「最初に出たデータベース 誤差は何だったか」
- 「直前に変更したCSSを戻して」

では必要な履歴 ブロックが違う。

KVMemは問い合わせごとに履歴上 ブロックを点数し、予算内で上位ブロックを選ぶ。

選ばれたブロックは単純な点数順ではなく、最終的には**元の時系列順**へ並べ直して実行 ビューへ実体化する。

これはエージェント履歴の因果順序を極力保つためである。

## 3つの容量budget

公式QW3実装ではKVMemの容量を主に3つのパラメータで分離している。

### `--ctx`

エージェントが蓄積できる論理 作業領域上限。

GPU外へ保存された履歴も含む。

### `--kvmem-budget`

現在 問い合わせのために履歴上 作業領域から選択し、実行対象 実行 ビューへ戻すトークン数の上限。

論理 作業領域が1M トークンでも、この予算が64Kなら一度に取り出す履歴は64K程度へ制限される。

### `--kvmem-gen-budget`

これから生成する出力 トークン用の予約領域。

取得済み 履歴でネイティブ 文脈 窓を全部埋めると、回答を生成する空間がなくなる。そのため生成用容量を先に確保する。

したがって実行時には概念的に

`current-step context + retrieved history + generation reserve <= native context / GPU KV budget`

となる必要がある。

## GPU・CPU・NVMe tier

高温 ブロックはGPUに置き、より低温なブロックをCPU DRAM、さらに大きな作業領域ではNVMeへ置く。

公式exampleでは128-トークン ブロック、32K 履歴上 予算、8K 生成 予約、16 GB CPU 階層、64 GB NVMe 階層などを個別指定できる。

この階層化の目的は単純な容量 extensionだけではない。

NVMeから毎回大量ブロックを読むと遅延が大きいので、検索により**今回必要な小さな作業 集合だけを上位階層へ昇格する**必要がある。

つまりKVMemの性能は

`retrieval accuracy × materializeするdata量 × tier bandwidth/latency`

のトレードオフで決まる。

## Text retrievalと比べた重要な違い

同じ過去ブロックを選べたとしても、テキスト RAGとKVMemでは後段費用が違う。

### Text RAG

`検索 → textをpromptへ追加 → Transformer全layerで再prefill → 新しいKV生成`

### KVMem

`検索 → 保存済みKVをmaterialize → 既存stateを再利用`

このため長い取得済み 文脈では、KVMemは検索後の再プリフィル 費用を大きく減らせる。

一方、KVMemはモデル内部表現に依存するため、テキスト 文書のようにモデルをまたいで汎用再利用しにくい。

## QW3 runtimeとの関係

公開実装は汎用vLLM pluginではなく、Qwen3.6/3.8系へ特化したCUDA-ネイティブ ランタイム **QW3** に組み込まれている。

QW3は

- モデル 読み込み
- tokenizer
- CUDA 実行
- KV ライフサイクル
- ページ化された KV
- continuous batching
- MTP 投機 デコード
- FP8 KV
- NVFP4 重み 経路

などをランタイム内部で管理する。

KVMemがモデル内部の鍵 表現、ページ化された KV、メモリ ライフサイクルまで触るため、既存エンジンの外側に単純なキャッシュ serverを足す設計より深くランタイムへ統合されている。

現時点の生成 バックエンドはNVIDIA CUDA向けで、AMD/ROCm、Metal、CPU 生成は未対応である。

## Optional prefix cacheとの違い

公式実装には `--kvmem-prefix-cache` もあるが、これはKVMem本体と同じものではない。

KVMem本体は大きな履歴上 作業領域から関連ブロックを選択する仕組みである。

接頭部 キャッシュは同一trajectoryで完全一致する入力 接頭部を再利用し、追加suffixだけプリフィルする最適化で、より厳しいcontinuation/checkpoint invariantを持つ。

したがってKVMemの見出し結果効果を「単なる接頭部 キャッシュ」と理解するのは誤りである。

# 評価

論文はLongMemEval、MemoryAgentBench、AgentLongBench、DeepSWE等の長大履歴 エージェント ワークロードを評価する。

比較対象は代表的に

- 完全な 文脈
- Sliding Window
- Compact-だけ
- Compact + RAG
- KVMem

である。

ここで重要なのは、完全な 文脈が入らない256K超の条件では完全な 文脈自体を実行できない点である。

## LongMemEval-S

公式paper用表では回答精度は

- 完全な 文脈: 86.60%
- Sliding Window: 26.80%
- Compact-だけ: 45.60%
- Compact+RAG: 86.20%
- KVMem: 85.60%

となる。

KVMemはCompact+RAGとほぼ同程度の有用性だが、final 問い合わせ到着から最初の回答トークンまでのpre-answer 遅延は

- Compact+RAG: 26.63 s
- KVMem: 0.48 s

である。

この差の中心は、RAGで取得した長いテキストを再プリフィルするか、計算済みKVを再利用するかにある。

## MemoryAgentBench >256K

256Kを超えてネイティブ 完全な 文脈が使えない領域では、公式表で全体 点数は

- Sliding Window: 23.94%
- Compact-だけ: 27.54%
- Compact+RAG: 43.66%
- KVMem: 38.58%

となる。

ここでは有用性だけならCompact+RAGが高い。

一方pre-answer 遅延は

- Compact+RAG: 106.02 s
- KVMem: 1.81 s

と大きく異なる。

つまりKVMemは全ベンチマークで常に精度最高という手法ではなく、**有用性をある程度維持しながら検索後の再計算を大幅に減らす**設計と読むべきである。

## AgentLongBench

### <=256K

Task 成功:

- 完全な 文脈: 59.54%
- Compact+RAG: 47.49%
- KVMem: 60.87%

KVMemのpre-answer 遅延は0.38 sである。

### 512K

Task 成功:

- Sliding Window: 25.00%
- Compact-だけ: 22.50%
- Compact+RAG: 49.50%
- KVMem: 53.00%

KVMem 遅延は0.62 s、Compact+RAGは263.70 s。

### 1M

Task 成功:

- Sliding Window: 20.00%
- Compact-だけ: 32.00%
- Compact+RAG: 58.00%
- KVMem: 50.00%

KVMem 遅延は0.73 s、Compact+RAGは416.38 s。

ここでも1M条件では有用性単体はCompact+RAGが上回るため、「KVMemが常に最も賢いメモリ」という結果ではない。

強みは、1M規模までアドレス可能 履歴を広げても、問い合わせ時に数百秒規模のテキスト re-プリフィルを要求しない点にある。

## DeepSWE long-context

arXiv abstractの見出し結果ではQwen3.8-27Bを使うDeepSWE 長大文脈 testでタスク 成功が

`43.8%（compaction only） → 48.4%（KVMem）`

へ改善する。

コーディング エージェントでは、以前のツール 出力や誤差 ログの細部を要約で消さずに再取得できることが有用性改善につながる可能性を示す。

ただしこの差を純粋な保存 高速化倍率と混同してはいけない。KVMemは実行対象 文脈へ入れる情報そのものも変えるため、システム 性能だけでなく検索 品質も結果へ影響する。

# 24GB laptopで「1M tokens / 約50 tok/s」の意味

論文は24 GB RTX 5090 Laptop GPU上でQwen3.6/3.8-27B NVFP4 + MTPを動かし、最大1M-トークン 作業領域をvirtualizeして単一セッションで約50 トークン/sと報告する。

この見出し結果は次のように読む必要がある。

### 1M tokens

過去100万トークンが**アドレス可能 作業領域**としてGPU/CPU/NVMe上に残っているという意味。

1 iterationで100万トークン全部へ完全な 注意機構しているわけではない。

### 256K native contextの4倍

Qwen側が一度に扱うネイティブ 文脈は256Kなので、KVMemはその外側へ履歴 メモリを作っている。

問い合わせごとに必要ブロックを選んでネイティブ 窓内へ戻すことで、論理 履歴だけを4倍へ広げる。

### 約50 tok/s

単一セッション ローカル 生成の値であり、高同時実行 提供 スループットではない。

multi-利用者 ワークロードでCPU/NVMe 検索が競合した場合に同じ50 tok/sを維持できることを意味しない。

# 既存研究との差

## 通常のKV offload

KVDrive、LMCache、CPU/NVMe オフロード等は主に**ネイティブ 文脈内で作られたKVをどこへ置くか**を扱う。

KVMemはそれに加えて、ネイティブ 文脈から溢れた履歴を永続的 searchable 作業領域へ変える。

## Text-based agent memory

RAGやベクトル データベースはテキスト/文書を検索し、選択テキストを再び入力としてモデルへ入れる。

KVMemはモデル-ネイティブ KVを検索し、再プリフィルを避ける。

## Context compression

圧縮/要約は古い履歴を小さい表現へ不可逆変換する。

KVMemは元のKV ブロックを保存するため、後から別問い合わせで異なるブロックを呼び戻せる。

ただし今回選ばれなかったブロックは実行対象 注意機構から見えないため、完全な 文脈と同値ではない。

# 限界

1. **検索近似**: 問い合わせごとに一部ブロックだけ選ぶため、必要ブロックを点数できなければメモリ lossが起こる。
2. **1Mは完全な 注意機構ではない**: 論理 作業領域 大きさと実行対象 文脈 大きさを混同すると性能を過大評価する。
3. **モデル依存索引**: 鍵表現を使うモデル-ネイティブ 検索は再プリフィルを省ける反面、別モデルへ保存状態をそのまま移植しにくい。
4. **ハードウェア依存**: NVMe 遅延、CPU RAM容量、PCIe 帯域でmaterialization 費用が変わる。
5. **ランタイム portability**: 公開QW3はQwen3.6/3.8系とNVIDIA CUDAへ強く最適化され、AMD/Metal/CPU 生成は未対応。
6. **高い-同時実行評価**: 見出し結果約50 tok/sは単一セッション。multi-テナント 提供時の公平性、tail 遅延、NVMe 待ち行列 競合は別問題である。
7. **有用性 トレードオフ**: MemoryAgentBench >256KやAgentLongBench 1MではCompact+RAGの有用性がKVMemより高い設定もあり、全タスクで品質優位ではない。
8. **状態 consistency**: 選んだ履歴上 ブロックを現在の実行 ビューへ組み込む際、時系列・position・混成 モデルのrecurrent 状態との整合性を守る必要があり、実装は単純なバイト キャッシュより複雑になる。

# 一般的な実装上の示唆

KVMemから得られる重要な示唆は、エージェント メモリを

`text history`

だけでなく

`再利用可能なmodel execution state`

として扱えることである。

長時間エージェントでは同じ過去を何度もRAGで拾ってプリフィルし直す可能性がある。保存費用が許容できるなら、KVのような計算済み状態を永続的 階層へ置くことで**計算 キャッシュと意味上 メモリを統合**できる。

また、メモリ 階層を設計するときは容量だけでなく

- 論理 履歴 大きさ
- 実行対象 検索 予算
- 生成 予約
- 階層 帯域
- 検索 精度

を別パラメータとして扱う必要がある。

「SSDへ全部置けば文脈が無限になる」のではなく、**巨大な低温 作業領域から何をどれだけ速く高温 実行 ビューへ昇格できるか**が本質的な問題になる。
