# KVMem: Virtualizing Million-Token Agent Workspaces on a Consumer GPU

> GPU・CPU DRAM・NVMeへ退避した過去のKV状態をattention空間の索引で検索し、必要blockだけを現在のcontextへ再構成することで、consumer GPU上でnative contextを超えるagent workspaceを扱うKV virtualization system。

## 概要

長時間動くLLM agentでは、履歴がGPUのKV容量だけでなくmodelのnative context window自体も超える。従来のsummary圧縮は情報を失い、text retrievalは一度処理済みの内容を再prefillするcostが生じる。

KVMemは古い履歴をtextではなくpaged KV stateとしてGPU memory・host memory・NVMeに保持し、現在のqueryに必要なblockだけを検索してactive contextへmaterializeする。これによりaddressableなworkspace sizeをactive context sizeから分離する。

## 手法

- overflowしたKVをpage単位で階層memoryへ退避する。
- model自身のattention表現から軽量indexを作り、現在のqueryに関連する過去blockを選ぶ。
- 選択blockを時系列とposition整合性を保ってactive execution viewへ組み込み、native context windowとGPU KV budget以内で推論する。
- textへ戻して再prefillするのではなく、既に計算済みのKV stateを再利用する。

## 評価

LongMemEval、MemoryAgentBench、AgentLongBenchなど、最大100万token規模のagent履歴で評価している。論文はDeepSWE long-context testでQwen3.8-27Bのtask successがcompaction-onlyの43.8%から48.4%へ改善したと報告する。

local deploymentでは24GB RTX 5090 Laptop GPU上のQwen3.6/3.8-27B NVFP4 + MTPで最大1M-token workspaceをvirtualizeし、single-sessionで約50 token/sを報告する。これはmodelのnative 256K contextの4倍に相当する。

## 既存研究との差

一般的なKV offloadがnative context内のKVをHBM外へ逃がすことを主眼とするのに対し、KVMemは**native contextを超えて蓄積したagent履歴そのものをaddressableなKV workspaceとしてvirtualizeする**。またtext retrievalと異なり、recallした履歴を再tokenize・再prefillしない。

## 限界

- retrievalで選ばれなかった過去blockはactive attentionから見えないため、完全なfull-context attentionと同値ではない。
- agent benchmark中心で、一般的なhigh-concurrency servingでのthroughput/SLO特性は別途評価が必要。
- 階層memory性能とNVMe I/O特性への依存がある。

## 一般的な実装上の含意

長時間agentではKV cacheを単なる一時cacheではなく、GPU HBMより大きいpersistent execution stateとして扱う設計が有効になり得る。特にtextへ戻して再prefillする方式と、KVをそのまま保存・検索する方式のtrade-offを分離して評価する必要がある。
