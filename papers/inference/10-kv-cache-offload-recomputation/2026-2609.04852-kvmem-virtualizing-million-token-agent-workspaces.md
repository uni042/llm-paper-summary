# KVMem: Virtualizing Million-Token Agent Workspaces on a Consumer GPU

> KVMemは「100万tokenをGPUで一度にattentionする」仕組みではない。**agentが過去に処理した100万token規模の履歴を検索可能な論理ワークスペースとして保持し、その時の質問に必要な一部だけをmodel本来のcontext windowへ戻して推論する**仕組みである。しかも古い履歴をtextとして保存するのではなく、すでに計算済みのKV cacheをGPU、CPU memory、NVMeへ階層化して保存するため、選び直した履歴を毎回最初からprefillし直すcostを減らせる。

## まず2種類の「context不足」を分けて考える

長時間動くLLM agentでは、shell command、tool result、code diff、error log、会話履歴などが何時間も蓄積する。

このとき問題になる上限は1つではない。

### 1. GPUのKV cache容量

Transformerは過去tokenへattentionするため、各layerでKey/ValueをKV cacheとして保持する。contextが長くなるほどKV cacheはほぼtoken数に比例して増える。

model weight自体がGPUへ収まっていても、長いagent sessionではKV cacheだけでVRAMを圧迫する。

### 2. Model自身のnative context window

仮にKV cacheをCPUやSSDへ退避できても、modelが一度に扱えるcontext lengthには上限がある。

例えば論文のQwen3.6/3.8-27B構成ではnative contextが256K tokenである。1M token分の履歴をSSDへ保存できても、1回のforward passで1M tokenすべてをattentionへ渡せるわけではない。

したがって単純なKV offloadだけでは

`GPU memory capacity問題`

は解けても

`native context window問題`

は解けない。

KVMemはこの2つを同時に扱うため、**論理ワークスペース（logical workspace）**と**実行ビュー（execution view）**を分離する。

## Logical workspaceとexecution view

KVMemではagentがこれまで蓄積した履歴全体をlogical workspaceとして保持する。

このworkspaceはGPUに常駐する必要も、modelのnative context内へ全部入る必要もない。

一方、実際の1回の推論でmodelが見る履歴だけをexecution viewとしてGPU上へmaterializeする。

例えば

- accumulated workspace: 1,000,000 token
- native model context: 256,000 token
- current retrieval budget: 64,000 token

なら、100万tokenは検索可能なmemoryとして残すが、そのqueryで実際にattentionへ入るhistoryは選択された数万token程度に制限する。

この意味でKVMemの「1M-token workspace」は**1M-token full-context attention**とは異なる。

## 既存のcontext overflow対策は何が問題なのか

### 要約・圧縮（compaction）

古い履歴をLLMでsummaryへ圧縮すればcontextは小さくできる。

しかしagentでは、後から必要になる情報が細かいことがある。

- 正確なerror message
- 以前試したcommandのoption
- file path
- tool callの順序
- 以前の失敗理由

summary作成時点で重要でないと判断されたdetailは消えてしまい、後から復元できない。

### Text retrieval

古い履歴をtextのまま外部databaseへ保存し、現在queryに近いchunkだけ検索する方法もある。

こちらは原文を保持できるが、取得したtextをLLMへ再投入すると、その部分について**もう一度prefillしてKVを作り直す**必要がある。

agent自身はそのtextを過去stepで一度処理済みなのに、retrievalのたびに同じ計算を繰り返す。

KVMemはここを変え、過去contentを「text」ではなく**計算済みKV state**として保持する。

## KV stateをmemoryとして再利用するとはどういうことか

prefillでは各tokenについてlayerごとのKey/Valueが作られる。

通常、そのsessionが終わるかKVがevictされると状態は捨てられる。

KVMemでは処理済みhistoryを固定token数の**KV block**へ分割し、GPUから溢れたblockを

`GPU → CPU DRAM → NVMe`

というmemory hierarchyへ退避する。

後でそのhistoryが必要になったとき、元textを再tokenize・再prefillする代わりに、保存していたKV blockをGPUへ戻す。

これが「KV-context virtualization」の中心である。

## Virtual memoryとの類似

通常のOS仮想memoryでは、processから見えるaddress space全体を物理DRAMへ置く必要はない。

今使うpageだけDRAMへ置き、cold pageをSSDへ逃がす。

KVMemも概念的には近い。

- logical workspace = agentから見える大きなmemory空間
- KV block = page
- GPU KV capacity = 高速だが小さいphysical memory
- CPU DRAM / NVMe = 遅いが大きいbacking tier
- current query = 今どのpageが必要かを決めるaccess signal

ただしOS page faultと違い、KVMemは単純な最近使用順だけでpageを選ばない。現在queryとの**意味的関連性**を使う。

## Model-native attention-space index

KVMemは別のembedding modelへtextを通して検索indexを作ることを必須にしない。

代わりに、model自身がすでにattention計算で作ったKey表現を利用してhistorical blockを要約し、current queryとの関連度を測る。

公式実装の標準的な `mean-k` では、block内Keyの平均をblock summaryとして持ち、queryに対してどのblockがattention上重要になりそうかをscoreする。

公式実装には現在、

- `mean-k`
- `per-token`
- `sub-block-mean-k`
- `key-direction-fixed4`
- `key-direction-adaptive`

など複数retrieval scorerがある。

これらは「何をmemoryとして保存するか」を変えるのではなく、**保存済みblockのどれを今回active viewへ戻すか**を変える。

## Query-conditioned retrieval

agentの次のquestionが変われば、必要な過去も変わる。

例えば長いcoding sessionで

- 「最初に出たdatabase errorは何だったか」
- 「直前に変更したCSSを戻して」

では必要なhistory blockが違う。

KVMemはqueryごとにhistorical blockをscoreし、budget内で上位blockを選ぶ。

選ばれたblockは単純なscore順ではなく、最終的には**元の時系列順**へ並べ直してexecution viewへmaterializeする。

これはagent履歴の因果順序を極力保つためである。

## 3つの容量budget

公式QW3実装ではKVMemの容量を主に3つのparameterで分離している。

### `--ctx`

agentが蓄積できるlogical workspace上限。

GPU外へ保存されたhistoryも含む。

### `--kvmem-budget`

current queryのためにhistorical workspaceから選択し、active execution viewへ戻すtoken数の上限。

logical workspaceが1M tokenでも、このbudgetが64Kなら一度に取り出すhistoryは64K程度へ制限される。

### `--kvmem-gen-budget`

これから生成するoutput token用の予約領域。

retrieved historyでnative context windowを全部埋めると、回答を生成する空間がなくなる。そのためgeneration用capacityを先に確保する。

したがって実行時には概念的に

`current-step context + retrieved history + generation reserve <= native context / GPU KV budget`

となる必要がある。

## GPU・CPU・NVMe tier

hot blockはGPUに置き、よりcoldなblockをCPU DRAM、さらに大きなworkspaceではNVMeへ置く。

公式exampleでは128-token block、32K historical budget、8K generation reserve、16 GB CPU tier、64 GB NVMe tierなどを個別指定できる。

この階層化の目的は単純なcapacity extensionだけではない。

NVMeから毎回大量blockを読むとlatencyが大きいので、検索により**今回必要な小さなworking setだけを上位tierへ昇格する**必要がある。

つまりKVMemの性能は

`retrieval accuracy × materializeするdata量 × tier bandwidth/latency`

のtrade-offで決まる。

## Text retrievalと比べた重要な違い

同じ過去blockを選べたとしても、text RAGとKVMemでは後段costが違う。

### Text RAG

`検索 → textをpromptへ追加 → Transformer全layerで再prefill → 新しいKV生成`

### KVMem

`検索 → 保存済みKVをmaterialize → 既存stateを再利用`

このため長いretrieved contextでは、KVMemは検索後の再prefill costを大きく減らせる。

一方、KVMemはmodel内部表現に依存するため、text documentのようにmodelをまたいで汎用再利用しにくい。

## QW3 runtimeとの関係

公開実装は汎用vLLM pluginではなく、Qwen3.6/3.8系へ特化したCUDA-native runtime **QW3** に組み込まれている。

QW3は

- model loading
- tokenizer
- CUDA execution
- KV lifecycle
- paged KV
- continuous batching
- MTP speculative decoding
- FP8 KV
- NVFP4 weight path

などをruntime内部で管理する。

KVMemがmodel内部のKey representation、paged KV、memory lifecycleまで触るため、既存engineの外側に単純なcache serverを足す設計より深くruntimeへ統合されている。

現時点のgeneration backendはNVIDIA CUDA向けで、AMD/ROCm、Metal、CPU generationは未対応である。

## Optional prefix cacheとの違い

公式実装には `--kvmem-prefix-cache` もあるが、これはKVMem本体と同じものではない。

KVMem本体は大きなhistorical workspaceから関連blockを選択する仕組みである。

prefix cacheは同一trajectoryで完全一致するprompt prefixをreuseし、追加suffixだけprefillするoptimizationで、より厳しいcontinuation/checkpoint invariantを持つ。

したがってKVMemのheadline効果を「単なるprefix cache」と理解するのは誤りである。

# 評価

論文はLongMemEval、MemoryAgentBench、AgentLongBench、DeepSWE等のlong-history agent workloadを評価する。

比較対象は代表的に

- Full Context
- Sliding Window
- Compact-only
- Compact + RAG
- KVMem

である。

ここで重要なのは、full contextが入らない256K超の条件ではFull Context自体を実行できない点である。

## LongMemEval-S

公式paper用tableでは回答accuracyは

- Full Context: 86.60%
- Sliding Window: 26.80%
- Compact-only: 45.60%
- Compact+RAG: 86.20%
- KVMem: 85.60%

となる。

KVMemはCompact+RAGとほぼ同程度のutilityだが、final query到着から最初の回答tokenまでのpre-answer latencyは

- Compact+RAG: 26.63 s
- KVMem: 0.48 s

である。

この差の中心は、RAGで取得した長いtextを再prefillするか、計算済みKVを再利用するかにある。

## MemoryAgentBench >256K

256Kを超えてnative full contextが使えない領域では、公式tableでoverall scoreは

- Sliding Window: 23.94%
- Compact-only: 27.54%
- Compact+RAG: 43.66%
- KVMem: 38.58%

となる。

ここではutilityだけならCompact+RAGが高い。

一方pre-answer latencyは

- Compact+RAG: 106.02 s
- KVMem: 1.81 s

と大きく異なる。

つまりKVMemは全benchmarkで常にaccuracy最高という手法ではなく、**utilityをある程度維持しながらretrieval後の再計算を大幅に減らす**設計と読むべきである。

## AgentLongBench

### <=256K

Task success:

- Full Context: 59.54%
- Compact+RAG: 47.49%
- KVMem: 60.87%

KVMemのpre-answer latencyは0.38 sである。

### 512K

Task success:

- Sliding Window: 25.00%
- Compact-only: 22.50%
- Compact+RAG: 49.50%
- KVMem: 53.00%

KVMem latencyは0.62 s、Compact+RAGは263.70 s。

### 1M

Task success:

- Sliding Window: 20.00%
- Compact-only: 32.00%
- Compact+RAG: 58.00%
- KVMem: 50.00%

KVMem latencyは0.73 s、Compact+RAGは416.38 s。

ここでも1M条件ではutility単体はCompact+RAGが上回るため、「KVMemが常に最も賢いmemory」という結果ではない。

強みは、1M規模までaddressable historyを広げても、query時に数百秒規模のtext re-prefillを要求しない点にある。

## DeepSWE long-context

arXiv abstractのheadlineではQwen3.8-27Bを使うDeepSWE long-context testでtask successが

`43.8%（compaction only） → 48.4%（KVMem）`

へ改善する。

coding agentでは、以前のtool outputやerror logの細部をsummaryで消さずに再取得できることがutility改善につながる可能性を示す。

ただしこの差を純粋なstorage speedupと混同してはいけない。KVMemはactive contextへ入れる情報そのものも変えるため、system performanceだけでなくretrieval qualityも結果へ影響する。

# 24GB laptopで「1M tokens / 約50 tok/s」の意味

論文は24 GB RTX 5090 Laptop GPU上でQwen3.6/3.8-27B NVFP4 + MTPを動かし、最大1M-token workspaceをvirtualizeしてsingle-sessionで約50 token/sと報告する。

このheadlineは次のように読む必要がある。

### 1M tokens

過去100万tokenが**addressable workspace**としてGPU/CPU/NVMe上に残っているという意味。

1 iterationで100万token全部へfull attentionしているわけではない。

### 256K native contextの4倍

Qwen側が一度に扱うnative contextは256Kなので、KVMemはその外側へhistory memoryを作っている。

queryごとに必要blockを選んでnative window内へ戻すことで、logical historyだけを4倍へ広げる。

### 約50 tok/s

single-session local generationの値であり、高concurrency serving throughputではない。

multi-user workloadでCPU/NVMe retrievalが競合した場合に同じ50 tok/sを維持できることを意味しない。

# 既存研究との差

## 通常のKV offload

KVDrive、LMCache、CPU/NVMe offload等は主に**native context内で作られたKVをどこへ置くか**を扱う。

KVMemはそれに加えて、native contextから溢れたhistoryをpersistent searchable workspaceへ変える。

## Text-based agent memory

RAGやvector databaseはtext/documentを検索し、選択textを再びpromptとしてmodelへ入れる。

KVMemはmodel-native KVを検索し、再prefillを避ける。

## Context compression

compression/summaryは古いhistoryを小さいrepresentationへ不可逆変換する。

KVMemは元のKV blockを保存するため、後から別queryで異なるblockを呼び戻せる。

ただし今回選ばれなかったblockはactive attentionから見えないため、full contextと同値ではない。

# 限界

1. **retrieval近似**: queryごとに一部blockだけ選ぶため、必要blockをscoreできなければmemory lossが起こる。
2. **1Mはfull attentionではない**: logical workspace sizeとactive context sizeを混同すると性能を過大評価する。
3. **model依存index**: Key表現を使うmodel-native retrievalは再prefillを省ける反面、別modelへ保存stateをそのまま移植しにくい。
4. **hardware依存**: NVMe latency、CPU RAM容量、PCIe bandwidthでmaterialization costが変わる。
5. **runtime portability**: 公開QW3はQwen3.6/3.8系とNVIDIA CUDAへ強く最適化され、AMD/Metal/CPU generationは未対応。
6. **high-concurrency評価**: headline約50 tok/sはsingle-session。multi-tenant serving時のfairness、tail latency、NVMe queue contentionは別問題である。
7. **utility trade-off**: MemoryAgentBench >256KやAgentLongBench 1MではCompact+RAGのutilityがKVMemより高い設定もあり、全taskで品質優位ではない。
8. **state consistency**: 選んだhistorical blockを現在のexecution viewへ組み込む際、時系列・position・hybrid modelのrecurrent stateとの整合性を守る必要があり、実装は単純なbyte cacheより複雑になる。

# 一般的な実装上の示唆

KVMemから得られる重要な示唆は、agent memoryを

`text history`

だけでなく

`再利用可能なmodel execution state`

として扱えることである。

長時間agentでは同じ過去を何度もRAGで拾ってprefillし直す可能性がある。保存costが許容できるなら、KVのような計算済みstateをpersistent tierへ置くことで**compute cacheとsemantic memoryを統合**できる。

また、memory hierarchyを設計するときはcapacityだけでなく

- logical history size
- active retrieval budget
- generation reserve
- tier bandwidth
- retrieval precision

を別parameterとして扱う必要がある。

「SSDへ全部置けばcontextが無限になる」のではなく、**巨大なcold workspaceから何をどれだけ速くhot execution viewへ昇格できるか**が本質的な問題になる。
