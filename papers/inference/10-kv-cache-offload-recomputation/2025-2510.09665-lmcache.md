# LMCache: An Efficient KV Cache Layer for Enterprise-Scale LLM Inference

> LMCacheの本質は、KVキャッシュ（KV キャッシュ）を「1台のGPU上で1 リクエストのデコードを速くする一時バッファ」から、**複数リクエスト・複数推論エンジン・複数保存 階層の間で保存・検索・転送できる独立データ オブジェクト**へ昇格させることにある。同じ文書やシステム 入力を別リクエストが使うなら過去KVを再利用し、プリフィル GPUとデコード GPUを分離するなら同じ仕組みでKVを別エンジンへ渡す。そのために、小さく分散したKV ページを大きな塊へ集約して高速転送し、計算とI/Oを重ね、vLLM/SGLangとは標準接続器で接続する。

## まずKV cacheはなぜ「外へ出す」必要があるのか

通常の自己回帰LLMでは、新しいトークンを1個生成するたびに過去トークンへ注意機構する。

過去トークンの鍵/値を毎回再計算するのは高価なので、一度計算した状態をGPU メモリへKV キャッシュとして保存する。

従来は

`request開始 → prefillでKV生成 → decode中だけ保持 → request終了で破棄`

というリクエスト-ローカルな扱いでもよかった。

しかし実運用 ワークロードでは、同じ過去文脈を別リクエストから何度も使うことが増えた。

### 例1: multi-turn conversation

ターン 1で長い履歴をプリフィルした後、ターン 2ではほぼ同じ履歴に数行だけ追加される。

過去KVを保存しておけばターン 2で履歴全体を再プリフィルしなくてよい。

### 例2: 検索拡張生成（Retrieval-Augmented Generation: RAG）

多くの利用者が同じ長い文書 塊を参照する場合、文書部分のKVは問い合わせをまたいで再利用できる。

### 例3: 事前充填・復号分離（prefill-decode disaggregation）

プリフィル専用GPUが入力のKVを作り、デコード専用GPUがトークン 生成を担当する構成では、入力処理器が作ったKVをデコーダへ移さなければならない。

この3例に共通するのは、KVが「GPU内部だけの状態」ではなく、**リクエスト/エンジン境界を越えて運ぶデータ**になる点である。

## Cross-query cachingとPD disaggregationは同じ問題として扱える

一見すると

- 横断的問い合わせ 再利用: 同じ文脈を後のリクエストで使う
- PD 分離: 同じリクエストのKVを別GPUへ渡す

は別機能に見える。

LMCacheは両方を

`engineからKVを取り出す → backendへ保存/転送する → 必要なengineへ戻す`

という同じデータ 経路で扱う。

違うのは保存先バックエンドである。

### Cross-query reuse

`GPU → CPU/disk/remote cache → 後続requestのGPU`

### PD transfer

`prefill GPU → P2P/network backend → decode GPU`

この統一がLMCacheのアーキテクチャ上の重要点である。

# なぜ単純なGPU→CPU copyでは遅いのか

vLLM等は**ページ化注意機構（PagedAttention）**のためKVを多数の小ページへ分割して管理する。

小ページはGPU メモリ fragmentationを抑えるには都合がよいが、そのままI/O単位にすると問題が起きる。

## 小さいtransferでは帯域を使い切れない

PCIe、NVLink、ネットワーク、SSDには高いピーク 帯域があっても、1回の転送を開始するたびに

- API 呼ぶ
- DMA setup
- synchronization
- メタデータ processing

などの固定オーバーヘッドがある。

16〜64 KB程度のページを1枚ずつ送ると、データ本体より固定費用が支配し、リンクのピーク 帯域へ届かない。

論文のmicrobenchmarkでは400 Gbps級転送を十分飽和させるにはMB級、概ね16 MB程度の転送 粒度が必要になる条件を示す。

つまりKV メモリ 管理器に適したページ 大きさと、I/Oに適した転送 大きさは一致しない。

# 大粒度チャンク（chunk）へまとめる

LMCacheは複数KV ページを**大粒度チャンク（塊）**へまとめてからI/Oを発行する。

既定では256-トークン程度を1 塊として扱う。

ただしページ化された KVはGPU上で物理的に連続していないため、そのまま大きなDMA リクエストを出せない。

そこでcustom CUDA カーネルで

1. 分散したページ化された KVから必要部分を収集
2. 連続したストリーミング バッファへ詰める
3. 大きなDMAでCPU/保存/ネットワークへ送る

という経路を使う。

読み込み時は逆に

1. バックエンドからcontiguous バッファへ取得
2. GPU上のページ化された 配置へ分散

する。

これにより推論エンジン側の細粒度メモリ 割当と、保存/ネットワーク側の大粒度I/Oを両立させる。

## 「chunkを大きくする」だけでは足りない

大きなバッファを毎回追加割り当てるしたり、全層 KVをまとめてコピーするとメモリ オーバーヘッドが増える。

LMCacheは層単位のパイプラインと組み合わせ、常時必要なストリーミング バッファを抑える。

# 層単位の計算・I/O重畳（compute-I/O overlap）

Transformerは層 1→2→3…と順に計算する。

ある層を計算している間、次層のKVを先読みできれば転送待ちを隠せる。

LMCache 接続器はモデル 実行器へ層-水準 フックを提供し、概念的には

`load layer 0 KV`

`wait layer 0 → compute layer 0 / prefetch layer 1`

`wait layer 1 → compute layer 1 / prefetch layer 2`

…

とパイプラインする。

保存も同様に、計算済み層のKVを後続層計算と並行してオフロードする。

別CUDA ストリームを使い、GPU 計算とDMA 転送をできるだけ同時進行させる。

論文評価では非同期読み込みによりエンドツーエンド 遅延を**1.46×改善**する条件を報告する。

ここで重要なのは、I/O 帯域が十分高くても逐次に待てば遅延は残ることだ。

LMCacheの性能は

`大粒度化でbandwidthを出す + pipelineで待ち時間を隠す`

の両方に依存する。

# Query単位でもI/Oを重ねる

あるリクエストが接頭部 キャッシュ ヒットしていても、そのKVがCPU/遠隔 保存にあり読み込みに時間がかかる場合、GPU スケジューラがそのリクエストだけを待つ必要はない。

LMCache 接続器はスケジューラへ「何トークン分のキャッシュがヒットしたか」を返すが、KV 読み込みがまだ準備できていない場合にはリクエストを一時的にwaiting 待ち行列へ戻せる。

その間に別リクエストをGPUで処理し、I/Oと計算をリクエスト間でも重ね合わせする。

したがってLMCacheは保存 層だけではなく、推論 スケジューラと連携して**I/O待ちをGPU アイドル 時間にしない**ようにしている。

# Zero-copyは何を減らすのか

KVを複数階層へ書くとき、単純実装では

`GPU → CPU buffer A → disk`

`GPU → CPU buffer B → remote storage`

のように同じデータを複製しがちである。

LMCacheは参照数（reference count）でバッファ ownershipを管理し、同じsource バッファを複数destination 操作から共有する。

すべての個人向けが完了した時点でバッファを解放する。

これにより不要なホスト-メモリ コピーとメモリ footprintを抑える。

KV キャッシュは数GB〜数十GBになるため、1回余分にコピーするだけでも帯域と容量の両方へ大きく効く。

# Dynamic offloading

GPU メモリを最大限キャッシュに使いたい一方、これから来るリクエスト用の空き KV ページも必要である。

すべての空き ページをCPUへ事前複製するとホスト メモリとPCIe 帯域を浪費する。

逆に何もオフロードしていないとGPU 割当 圧力が来た時に急いでコピーする必要があり、リクエストを待ちさせる。

LMCacheはオフロード済み範囲と未オフロード範囲をpointerで管理し、空き GPU ページのうち一定量をahead-の-時間に複製する。

これは

`copyしすぎによるbandwidth浪費`

と

`copy不足によるallocation stall`

のトレードオフを制御する仕組みである。

# なぜconnectorが重要なのか

KV キャッシュ システムをvLLM内部へ直接書き込めば、最初は動く。

しかし推論 エンジンは頻繁に変わる。

- スケジューラ API
- KV ブロック 配置
- モデル 実行器
- 注意機構 バックエンド
- メモリ 管理器

が更新されるたび、external キャッシュ システムも壊れやすい。

LMCacheはこの依存を**KVコネクタ（KV 接続器）**へ閉じ込める。

接続器が

- 接頭部 一致確認
- 割当後メタデータ構築
- 層 KV 読み込み/保存 フック
- スケジューラとのready/wait coordination

を標準化し、LMCache本体の保存/バックエンド logicをエンジン変更から分離する。

この設計は後にvLLM等のecosystemで接続器 抽象化が重要になる背景でもある。

# Data planeとcontrol plane

LMCacheは「バイトを速く動かす」だけでなく、KVを最初-分類 オブジェクトとして操作するAPIを持つ。

主な操作には

- 検索
- move
- pin
- clear / cleanup
- 圧縮

などがある。

## データ経路（data plane）

実際のKV 転送を担当する。

GPU↔CPU、ディスク、遠隔 バックエンド、peer GPU等のデータ movementを実行する。

## 制御経路（control plane）

「そのKVがどこにあるか」「消してよいか」「移動すべきか」といったメタデータ/制御を管理する。

上位ルータはこのAPIを使って

`必要prefix KVがすでにあるnodeへrequestを送る`

といったキャッシュ-aware ルーティングも実装できる。

つまりKV キャッシュを保存 システムの管理対象へ変えることが目的である。

# 対応storage tier

LMCacheはバックエンド 抽象化を通して、実装・deploymentに応じて

- GPU HBM
- CPU DRAM
- ローカル ディスク
- 遠隔 ディスク/保存
- Redis
- オブジェクト 保存
- NFS
- GPU-直接 保存系経路

などへKVを置ける。

すべてのバックエンドが同じ性能という意味ではなく、LMCacheは**異種階層へ同じKV オブジェクト semanticsを提供する層**である。

# 評価条件

正式監査で確認した主な条件は次の通り。

| 項目 | 内容 |
|---|---|
| LMCache | v0.3.6 |
| vLLM | v0.10.2 GPU 接頭部 キャッシュ / v0.11.0 ネイティブ CPU オフロード |
| Hardware | 主に8× NVIDIA H100、PD分離はNVLink、感度評価にB200 |
| モデル | Llama-3.1-8B/70B、Qwen2.5-Coder-32B、Qwen3-Coder-480B-A35B-FP8、Qwen2.5-72B等 |
| ワークロード | multi-往復 Q&1つの、LongBench、vLLM ランダム ワークロード、企業トレース 再生 |
| 指標 | TTFT、ITL、スループット、KV 転送 遅延 |

単一-node CPU オフロードでは10K-トークン 文書 文脈 + short 質問を中心に、最大500 GB CPU KV容量を設定する。

PD評価では8K input / 200 出力 トークン等を使う。

# 主要結果

## 1. Single-node CPU offload

best 比較対象と比べ、条件に応じて

- TTFT: **1.9〜8.1×短縮**
- 同程度TTFTを保てる問い合わせ 率: **2.3〜14×向上**
- QPS=1でITL: **7〜92%削減**

を報告する。

abstractの「最大15× スループット」は複数ワークロードをまとめた見出し結果であるため、repositoryでは比較条件が明示された2.3〜14×等も併記して解釈する。

### なぜTTFTが下がるのか

接頭部 KVがCPUに存在するリクエストでは

`documentをGPUで再prefillする時間`

と

`CPUからKVをloadする時間`

の速い方を選べる。

高速なKV データ 経路とI/O 重ね合わせにより、再利用可能な長接頭部ほど読み込み側が有利になる。

## 2. CPU→GPU loading bandwidth

LMCacheはCPU→GPU KV 読み込みで約**400 Gbps**、比較するvLLM ネイティブ 経路は約**88 Gbps**と報告する。

これはGPU/PCIe ピークそのものだけの差ではなく、小ページを塊化し、収集/分散・batched DMAを最適化したデータ 経路差を含む。

「LMCacheはPCIe自体を5倍速くした」という意味ではない。

## 3. 企業trace replay

企業由来のトークン-長さ 分布を公開モデルへ再生する評価では、basic vLLM比で

- TTFT: **3.7〜6.8×短縮**
- ITL: **19〜58%削減**

を報告する。

注意点として、proprietary モデルそのものを再現した実験ではなく、企業トレースのリクエスト characteristicsを公開モデルへ適用したトレース-driven 評価である。

## 4. Remote storage

15 Gbps 中心 遠隔 保存条件ではスループットを約**1.3〜3×**改善する。

ただし遠隔 KV 読み込みは常にプリフィルより速いわけではない。

ネットワークが遅い、文脈が短い、モデルのプリフィルが速い場合には、KVを遠隔から運ぶより再計算した方が速い。

この点はB200 sensitivityでも明確になる。

## 5. Prefill-decode disaggregation

vLLM ネイティブ 転送と比べ

- 意味する TTFT: **1.5〜1.8×低下**
- 意味する ITL: **1.1〜1.7×低下**

を報告する。

PDでは接頭部 再利用ではなく、入力処理器が作ったKVをデコーダへ渡す通信primitiveとしてLMCacheを使う。

同じ接続器/データ 経路を2用途に使える点がアーキテクチャ上の強みである。

# 「KVをloadするか、recomputeするか」はhardwareで変わる

B200 sensitivity評価は重要である。

モデル/ハードウェアが速くなるほどプリフィル 計算自体が短くなるので、古いGPUでは得だったKV 読み込みが新GPUでは割に合わなくなる可能性がある。

評価では32 Gbps ネットワークだと、遠隔 KV 読み込みがプリフィルより有利になるのは非常に長い文脈、概ね256K トークン超の領域になる。

一方64/128 Gbpsでは評価範囲の文脈で読み込み優位が広がる。

したがってキャッシュ ヒットしたから必ず読み込みするのではなく、将来的には

`KV size / network bandwidth / storage latency`

対

`prefill tokens / GPU compute speed / current queue`

を比較して読み込み/再計算を動的に選ぶ必要がある。

# Context truncationがcache hitを壊す

実運用でよく行われる文脈 切詰めにも重要な副作用がある。

会話が長くなったとき古い接頭部を切り落とすと、内容は大部分同じでもトークン列の接頭部 整列が変わる。

接頭部 キャッシュは通常、先頭から連続して一致するトークン列を再利用するため、途中を削ったリクエストは以前のKVと一致しなくなる。

企業トレースでは切詰めにより接頭部 ヒット率が約**85%から45%**まで低下する例を報告する。

これはキャッシュ システムの性能が保存 帯域だけでなく、アプリ側の入力 構築 policyにも大きく依存することを示す。

# 既存systemとの差

## vLLM / SGLang native cache

エンジン内部のローカル 最適化としてCPU オフロード/接頭部 キャッシュを実装できる。

LMCacheはエンジン外に独立層を置き、横断的問い合わせ、cross-エンジン、multi-階層 保存を統一する。

## LMCacheとstorage systemの違い

Mooncake、InfiniStore、3FS等は高速保存/ネットワーク 基盤そのものを主対象にする。

LMCacheはその上に乗り、**ページ化された 推論 エンジンのKV 配置と保存/ネットワークをつなぐデータ 経路・接続器・KV semantics**を提供する。

したがってバックエンドを置き換えてもLMCache 層を再利用できる。

## KV compression研究との違い

KVServeやCacheGen等はKV データ量を減らすことが主題になる。

LMCacheの中心は基本的に無損失な

- 転送 粒度
- 配置
- pipelining
- ゼロコピー
- orchestration

である。

圧縮は制御 APIから組み込めるoptionの1つだが、LMCache本論文の主性能要因ではない。

# 限界

1. **キャッシュ 再利用がないワークロードには効きにくい**: ヒットしないKVを保存してもI/O オーバーヘッドだけ増える。
2. **遠隔 階層は帯域依存**: 遅い ネットワークでは再計算より遅い。
3. **commercial endpoint比較はblack-box**: ハードウェア/implementationを完全統一したmethod比較ではない。
4. **企業評価はトレース 再生を含む**: proprietary モデル本体の再現ではない。
5. **中心 controller scalability**: クラスタ規模でのメタデータ consistency/failure handlingは主性能評価の中心ではない。
6. **エンジン/バックエンドごとに優位幅が違う**: SGLang ネイティブ CPU オフロード等との差が小さい条件もあり、全configurationで絶対優位ではない。
7. **GPU世代で読み込み/再計算境界が動く**: B200のようにプリフィルが高速化すると、低帯域遠隔 キャッシュの価値が下がる。
8. **SSDは対応階層だが主評価ではない**: ローカル NVMe 待ち行列 深さ、ランダム I/O、書く 経路、プリフェッチ、GPU-直接 保存のjoint 最適化には余地が残る。

# SSD / hierarchical memory研究への示唆

LMCacheはSSDをバックエンドとして使えるが、論文の主要エンドツーエンド評価はCPU DRAMとnetworked 保存が中心である。

SSD研究の観点では、LMCacheが示した

`small GPU pages → large transfer chunk → asynchronous layer pipeline`

という構造が重要である。

NVMeを本格的なKV 階層にする場合にはさらに

- 待ち行列 深さ
- 読む amplification
- ランダム/順次 配置
- ブロック popularity
- プリフェッチ timing
- GPU 待ち行列との重ね合わせ

を考慮する必要がある。

また、キャッシュ ヒットの有無だけでなく**読み込みと再計算の費用比較**をスケジューラへ入れる考え方は、SSD 階層でもそのまま重要になる。

# 研究上の含意

LMCacheが広げた見方は、KV キャッシュを単なるメモリ 最適化ではなく**AI-ネイティブ データ 面**として扱うことにある。

複数エンジンが

`tokenを入力してtokenを出す独立server`

ではなく、

`共有KV stateを読み書きするcompute node`

として連携するなら、スケジューラは計算 読み込みだけでなくデータ 局所性も見てリクエスト 配置を決められる。

将来的には

- GPU 計算 局所性
- KV 局所性
- 保存 階層
- ネットワーク congestion
- recomputation 費用

を同じスケジューラが扱う方向につながる。
