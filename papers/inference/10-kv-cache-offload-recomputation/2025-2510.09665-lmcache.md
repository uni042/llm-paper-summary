# LMCache: An Efficient KV Cache Layer for Enterprise-Scale LLM Inference

> LMCacheの本質は、KVキャッシュ（KV cache）を「1台のGPU上で1 requestのdecodeを速くする一時buffer」から、**複数request・複数推論エンジン・複数storage tierの間で保存・検索・転送できる独立data object**へ昇格させることにある。同じdocumentやsystem promptを別requestが使うなら過去KVを再利用し、prefill GPUとdecode GPUを分離するなら同じ仕組みでKVを別engineへ渡す。そのために、小さく分散したKV pageを大きなchunkへ集約して高速転送し、計算とI/Oを重ね、vLLM/SGLangとは標準connectorで接続する。

## まずKV cacheはなぜ「外へ出す」必要があるのか

通常の自己回帰LLMでは、新しいtokenを1個生成するたびに過去tokenへattentionする。

過去tokenのKey/Valueを毎回再計算するのは高価なので、一度計算したstateをGPU memoryへKV cacheとして保存する。

従来は

`request開始 → prefillでKV生成 → decode中だけ保持 → request終了で破棄`

というrequest-localな扱いでもよかった。

しかしproduction workloadでは、同じ過去contextを別requestから何度も使うことが増えた。

### 例1: multi-turn conversation

turn 1で長いhistoryをprefillした後、turn 2ではほぼ同じhistoryに数行だけ追加される。

過去KVを保存しておけばturn 2でhistory全体を再prefillしなくてよい。

### 例2: 検索拡張生成（Retrieval-Augmented Generation: RAG）

多くのuserが同じ長いdocument chunkを参照する場合、document部分のKVはqueryをまたいでreuseできる。

### 例3: 事前充填・復号分離（prefill-decode disaggregation）

prefill専用GPUがpromptのKVを作り、decode専用GPUがtoken generationを担当する構成では、prefillerが作ったKVをdecoderへ移さなければならない。

この3例に共通するのは、KVが「GPU内部だけの状態」ではなく、**request/engine境界を越えて運ぶdata**になる点である。

## Cross-query cachingとPD disaggregationは同じ問題として扱える

一見すると

- cross-query reuse: 同じcontextを後のrequestで使う
- PD disaggregation: 同じrequestのKVを別GPUへ渡す

は別機能に見える。

LMCacheは両方を

`engineからKVを取り出す → backendへ保存/転送する → 必要なengineへ戻す`

という同じdata pathで扱う。

違うのは保存先backendである。

### Cross-query reuse

`GPU → CPU/disk/remote cache → 後続requestのGPU`

### PD transfer

`prefill GPU → P2P/network backend → decode GPU`

この統一がLMCacheのarchitecture上の重要点である。

# なぜ単純なGPU→CPU copyでは遅いのか

vLLM等は**ページ化注意機構（PagedAttention）**のためKVを多数の小pageへ分割して管理する。

小pageはGPU memory fragmentationを抑えるには都合がよいが、そのままI/O単位にすると問題が起きる。

## 小さいtransferでは帯域を使い切れない

PCIe、NVLink、network、SSDには高いpeak bandwidthがあっても、1回のtransferを開始するたびに

- API call
- DMA setup
- synchronization
- metadata processing

などの固定overheadがある。

16〜64 KB程度のpageを1枚ずつ送ると、data本体より固定costが支配し、linkのpeak bandwidthへ届かない。

論文のmicrobenchmarkでは400 Gbps級transferを十分飽和させるにはMB級、概ね16 MB程度のtransfer granularityが必要になる条件を示す。

つまりKV memory managerに適したpage sizeと、I/Oに適したtransfer sizeは一致しない。

# 大粒度チャンク（chunk）へまとめる

LMCacheは複数KV pageを**大粒度チャンク（chunk）**へまとめてからI/Oを発行する。

既定では256-token程度を1 chunkとして扱う。

ただしpaged KVはGPU上で物理的に連続していないため、そのまま大きなDMA requestを出せない。

そこでcustom CUDA kernelで

1. 分散したpaged KVから必要部分をgather
2. 連続したstreaming bufferへ詰める
3. 大きなDMAでCPU/storage/networkへ送る

というpathを使う。

load時は逆に

1. backendからcontiguous bufferへ取得
2. GPU上のpaged layoutへscatter

する。

これにより推論engine側の細粒度memory allocationと、storage/network側の大粒度I/Oを両立させる。

## 「chunkを大きくする」だけでは足りない

大きなbufferを毎回追加allocateしたり、全layer KVをまとめてcopyするとmemory overheadが増える。

LMCacheはlayer単位のpipelineと組み合わせ、常時必要なstreaming bufferを抑える。

# 層単位の計算・I/O重畳（compute-I/O overlap）

Transformerはlayer 1→2→3…と順に計算する。

あるlayerを計算している間、次layerのKVを先読みできればtransfer待ちを隠せる。

LMCache connectorはmodel runnerへlayer-level hookを提供し、概念的には

`load layer 0 KV`

`wait layer 0 → compute layer 0 / prefetch layer 1`

`wait layer 1 → compute layer 1 / prefetch layer 2`

…

とpipelineする。

storeも同様に、計算済みlayerのKVを後続layer計算と並行してoffloadする。

別CUDA streamを使い、GPU computeとDMA transferをできるだけ同時進行させる。

論文評価では非同期loadingによりend-to-end delayを**1.46×改善**する条件を報告する。

ここで重要なのは、I/O bandwidthが十分高くてもserialに待てばlatencyは残ることだ。

LMCacheの性能は

`大粒度化でbandwidthを出す + pipelineで待ち時間を隠す`

の両方に依存する。

# Query単位でもI/Oを重ねる

あるrequestがprefix cache hitしていても、そのKVがCPU/remote storageにありloadに時間がかかる場合、GPU schedulerがそのrequestだけを待つ必要はない。

LMCache connectorはschedulerへ「何token分のcacheがhitしたか」を返すが、KV loadがまだ準備できていない場合にはrequestを一時的にwaiting queueへ戻せる。

その間に別requestをGPUで処理し、I/Oとcomputeをrequest間でもoverlapする。

したがってLMCacheはstorage layerだけではなく、inference schedulerと連携して**I/O待ちをGPU idle timeにしない**ようにしている。

# Zero-copyは何を減らすのか

KVを複数tierへ書くとき、単純実装では

`GPU → CPU buffer A → disk`

`GPU → CPU buffer B → remote storage`

のように同じdataを複製しがちである。

LMCacheは参照数（reference count）でbuffer ownershipを管理し、同じsource bufferを複数destination operationから共有する。

すべてのconsumerが完了した時点でbufferを解放する。

これにより不要なhost-memory copyとmemory footprintを抑える。

KV cacheは数GB〜数十GBになるため、1回余分にcopyするだけでもbandwidthとcapacityの両方へ大きく効く。

# Dynamic offloading

GPU memoryを最大限cacheに使いたい一方、これから来るrequest用のfree KV pageも必要である。

すべてのfree pageをCPUへ事前複製するとhost memoryとPCIe bandwidthを浪費する。

逆に何もoffloadしていないとGPU allocation pressureが来た時に急いでcopyする必要があり、requestをstallさせる。

LMCacheはoffload済み範囲と未offload範囲をpointerで管理し、free GPU pageのうち一定量をahead-of-timeに複製する。

これは

`copyしすぎによるbandwidth浪費`

と

`copy不足によるallocation stall`

のtrade-offを制御する仕組みである。

# なぜconnectorが重要なのか

KV cache systemをvLLM内部へ直接書き込めば、最初は動く。

しかしinference engineは頻繁に変わる。

- scheduler API
- KV block layout
- model runner
- attention backend
- memory manager

が更新されるたび、external cache systemも壊れやすい。

LMCacheはこの依存を**KVコネクタ（KV connector）**へ閉じ込める。

connectorが

- prefix match確認
- allocation後metadata構築
- layer KV load/store hook
- schedulerとのready/wait coordination

を標準化し、LMCache本体のstorage/backend logicをengine変更から分離する。

この設計は後にvLLM等のecosystemでconnector abstractionが重要になる背景でもある。

# Data planeとcontrol plane

LMCacheは「byteを速く動かす」だけでなく、KVをfirst-class objectとして操作するAPIを持つ。

主なoperationには

- lookup
- move
- pin
- clear / cleanup
- compression

などがある。

## データ経路（data plane）

実際のKV transferを担当する。

GPU↔CPU、disk、remote backend、peer GPU等のdata movementを実行する。

## 制御経路（control plane）

「そのKVがどこにあるか」「消してよいか」「移動すべきか」といったmetadata/controlを管理する。

上位routerはこのAPIを使って

`必要prefix KVがすでにあるnodeへrequestを送る`

といったcache-aware routingも実装できる。

つまりKV cacheをstorage systemの管理対象へ変えることが目的である。

# 対応storage tier

LMCacheはbackend abstractionを通して、実装・deploymentに応じて

- GPU HBM
- CPU DRAM
- local disk
- remote disk/storage
- Redis
- object storage
- NFS
- GPU-Direct Storage系path

などへKVを置ける。

すべてのbackendが同じ性能という意味ではなく、LMCacheは**異種tierへ同じKV object semanticsを提供する層**である。

# 評価条件

正式監査で確認した主な条件は次の通り。

| 項目 | 内容 |
|---|---|
| LMCache | v0.3.6 |
| vLLM | v0.10.2 GPU prefix caching / v0.11.0 native CPU offload |
| Hardware | 主に8× NVIDIA H100、PD分離はNVLink、感度評価にB200 |
| Model | Llama-3.1-8B/70B、Qwen2.5-Coder-32B、Qwen3-Coder-480B-A35B-FP8、Qwen2.5-72B等 |
| Workload | multi-round Q&A、LongBench、vLLM random workload、企業trace replay |
| Metric | TTFT、ITL、throughput、KV transfer latency |

single-node CPU offloadでは10K-token document context + short questionを中心に、最大500 GB CPU KV容量を設定する。

PD評価では8K input / 200 output token等を使う。

# 主要結果

## 1. Single-node CPU offload

best baselineと比べ、条件に応じて

- TTFT: **1.9〜8.1×短縮**
- 同程度TTFTを保てるquery rate: **2.3〜14×向上**
- QPS=1でITL: **7〜92%削減**

を報告する。

abstractの「最大15× throughput」は複数workloadをまとめたheadlineであるため、repositoryでは比較条件が明示された2.3〜14×等も併記して解釈する。

### なぜTTFTが下がるのか

prefix KVがCPUに存在するrequestでは

`documentをGPUで再prefillする時間`

と

`CPUからKVをloadする時間`

の速い方を選べる。

高速なKV data pathとI/O overlapにより、reuse可能な長prefixほどload側が有利になる。

## 2. CPU→GPU loading bandwidth

LMCacheはCPU→GPU KV loadingで約**400 Gbps**、比較するvLLM native pathは約**88 Gbps**と報告する。

これはGPU/PCIe peakそのものだけの差ではなく、小pageをchunk化し、gather/scatter・batched DMAを最適化したdata path差を含む。

「LMCacheはPCIe自体を5倍速くした」という意味ではない。

## 3. 企業trace replay

企業由来のtoken-length distributionを公開modelへreplayする評価では、basic vLLM比で

- TTFT: **3.7〜6.8×短縮**
- ITL: **19〜58%削減**

を報告する。

注意点として、proprietary modelそのものを再現した実験ではなく、企業traceのrequest characteristicsを公開modelへ適用したtrace-driven evaluationである。

## 4. Remote storage

15 Gbps central remote storage条件ではthroughputを約**1.3〜3×**改善する。

ただしremote KV loadは常にprefillより速いわけではない。

networkが遅い、contextが短い、modelのprefillが速い場合には、KVをremoteから運ぶより再計算した方が速い。

この点はB200 sensitivityでも明確になる。

## 5. Prefill-decode disaggregation

vLLM native transferと比べ

- mean TTFT: **1.5〜1.8×低下**
- mean ITL: **1.1〜1.7×低下**

を報告する。

PDではprefix reuseではなく、prefillerが作ったKVをdecoderへ渡す通信primitiveとしてLMCacheを使う。

同じconnector/data pathを2用途に使える点がarchitecture上の強みである。

# 「KVをloadするか、recomputeするか」はhardwareで変わる

B200 sensitivity評価は重要である。

model/hardwareが速くなるほどprefill compute自体が短くなるので、古いGPUでは得だったKV loadが新GPUでは割に合わなくなる可能性がある。

評価では32 Gbps networkだと、remote KV loadがprefillより有利になるのは非常に長いcontext、概ね256K token超の領域になる。

一方64/128 Gbpsでは評価範囲のcontextでload優位が広がる。

したがってcache hitしたから必ずloadするのではなく、将来的には

`KV size / network bandwidth / storage latency`

対

`prefill tokens / GPU compute speed / current queue`

を比較してload/recomputeを動的に選ぶ必要がある。

# Context truncationがcache hitを壊す

productionでよく行われるcontext truncationにも重要な副作用がある。

conversationが長くなったとき古いprefixを切り落とすと、内容は大部分同じでもtoken列のprefix alignmentが変わる。

prefix cacheは通常、先頭から連続して一致するtoken列をreuseするため、途中を削ったrequestは以前のKVとmatchしなくなる。

企業traceではtruncationによりprefix hit率が約**85%から45%**まで低下する例を報告する。

これはcache systemの性能がstorage bandwidthだけでなく、application側のprompt construction policyにも大きく依存することを示す。

# 既存systemとの差

## vLLM / SGLang native cache

engine内部のlocal optimizationとしてCPU offload/prefix cacheを実装できる。

LMCacheはengine外に独立layerを置き、cross-query、cross-engine、multi-tier storageを統一する。

## LMCacheとstorage systemの違い

Mooncake、InfiniStore、3FS等は高速storage/network substrateそのものを主対象にする。

LMCacheはその上に乗り、**paged inference engineのKV layoutとstorage/networkをつなぐdata path・connector・KV semantics**を提供する。

したがってbackendを置き換えてもLMCache layerを再利用できる。

## KV compression研究との違い

KVServeやCacheGen等はKV data量を減らすことが主題になる。

LMCacheの中心は基本的にlosslessな

- transfer granularity
- placement
- pipelining
- zero-copy
- orchestration

である。

compressionはcontrol APIから組み込めるoptionの1つだが、LMCache本論文の主性能要因ではない。

# 限界

1. **cache reuseがないworkloadには効きにくい**: hitしないKVを保存してもI/O overheadだけ増える。
2. **remote tierは帯域依存**: slow networkではrecomputeより遅い。
3. **commercial endpoint比較はblack-box**: hardware/implementationを完全統一したmethod比較ではない。
4. **企業評価はtrace replayを含む**: proprietary model本体の再現ではない。
5. **central controller scalability**: cluster規模でのmetadata consistency/failure handlingは主性能評価の中心ではない。
6. **engine/backendごとに優位幅が違う**: SGLang native CPU offload等との差が小さい条件もあり、全configurationで絶対優位ではない。
7. **GPU世代でload/recompute境界が動く**: B200のようにprefillが高速化すると、低帯域remote cacheの価値が下がる。
8. **SSDは対応tierだが主評価ではない**: local NVMe queue depth、random I/O、write path、prefetch、GPU-Direct Storageのjoint optimizationには余地が残る。

# SSD / hierarchical memory研究への示唆

LMCacheはSSDをbackendとして使えるが、論文の主要end-to-end評価はCPU DRAMとnetworked storageが中心である。

SSD研究の観点では、LMCacheが示した

`small GPU pages → large transfer chunk → asynchronous layer pipeline`

という構造が重要である。

NVMeを本格的なKV tierにする場合にはさらに

- queue depth
- read amplification
- random/sequential layout
- block popularity
- prefetch timing
- GPU queueとのoverlap

を考慮する必要がある。

また、cache hitの有無だけでなく**loadとrecomputeのcost比較**をschedulerへ入れる考え方は、SSD tierでもそのまま重要になる。

# 研究上の含意

LMCacheが広げた見方は、KV cacheを単なるmemory optimizationではなく**AI-native data plane**として扱うことにある。

複数engineが

`tokenを入力してtokenを出す独立server`

ではなく、

`共有KV stateを読み書きするcompute node`

として連携するなら、schedulerはcompute loadだけでなくdata localityも見てrequest placementを決められる。

将来的には

- GPU compute locality
- KV locality
- storage tier
- network congestion
- recomputation cost

を同じschedulerが扱う方向につながる。
