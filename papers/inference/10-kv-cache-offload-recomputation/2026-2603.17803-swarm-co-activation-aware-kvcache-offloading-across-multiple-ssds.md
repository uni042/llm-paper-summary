# Swarm: Co-Activation Aware KVCache Offloading Across Multiple SSDs

## 書誌情報

- **著者**: Tuowei Wang, Liyun Chu, Ruwen Fan, Ju Ren
- **公開**: arXiv, 2026-03-18
- **arXiv**: 2603.17803
- **分類**: Inference / KV キャッシュ オフロード / SSD / multi-端末 I/O
- **一次資料**: https://arxiv.org/abs/2603.17803

## 一文要約

注意機構で一緒に参照されやすいKV キャッシュを事前にまとめ、そのグループ内のKVを複数SSDへ分散配置することで、1回のKV読み出しを複数SSDから並列に行い、単一SSDの帯域上限を超える実効I/O帯域を得る方式。

## 問題設定

長い文脈や複数リクエストで再利用されるKV キャッシュはGPU HBMだけでは保持しにくく、CPU DRAMへ退避しても大規模・長寿命なキャッシュでは容量と費用が問題になる。NVMe SSDは大容量かつ安価だが、一般的な1台のSSDはGPUやDRAMより狭いPCIe linkにつながるため、必要なKVをSSDから戻す時間が注意機構計算の待ち時間になりやすい。

疎な注意機構を使って「必要なKVだけ読む」方法はI/O量そのものを減らせるが、SSD 1台あたりの帯域上限は変わらない。Swarmは、KVの参照パターンに**複数SSDを同時に読める並列性**が含まれていないかに着目する。

## 手法

### 一緒に使われるKVを測る

Swarmは事前プロファイリングで、あるKV entryが注意機構に選ばれたときに他のどのentryも同時に選ばれることが多いかを数える。論文はこの安定した同時参照傾向をKV キャッシュ共活性（KVCache Co-活性値）と呼ぶ。

これは単なるembeddingの近さではなく、実際の注意機構選択で「1つのを読むリクエストではBやCも一緒に読むことが多い」というI/O アクセス パターンを表す。

### 共活性するKVをcluster化する

各KV entryをnode、同時参照の強さをedgeとしてgraphを作り、互いに一緒に使われやすいentryをクラスタへまとめる。厳密な組合せ最適化は高費用なので、同時参照される相手が多いentryをクラスタの代表（medoid）に選び、その代表と共活性が強いentryを順に加えるheuristicを使う。

あるKVが複数の異なるグループと頻繁に一緒に使われる場合は、SSD容量を少し余分に使って複製する。これにより、1つの配置へ無理に固定して不要なKVまで読むことを避ける。

### cluster内部を複数SSDへ散らす

重要なのは、共活性するKVを同じSSDへまとめるのではなく、**同時に必要になるKVを複数SSDへ均等に散らす**点である。クラスタを読み出すとき各SSDが別々のKVを同時に返せるため、1台のSSD帯域ではなく複数台の合計帯域を利用できる。

クラスタの代表entry、直近トークンのローカル window、頻繁に使う高頻度 クラスタはCPU DRAMへ残す。incoming 問い合わせとDRAM上の代表entryを比較して読むクラスタを決めるため、どのクラスタが必要かを判断するためだけにSSDを先に読む必要はない。

### runtimeで負荷を均等化する

同じKVが複数SSDへ複製されている場合、どのコピーから読むかでSSDごとの負荷が偏る。Swarmはランタイムで各SSDの読み込みを見て読み出し先を選び、複数SSDが同時に働くようにする。またデコードが進んで新しいKVが増えると参照傾向も変わるため、クラスタ membershipとDRAM キャッシュを更新する。

静的配置だけでは、同じ高頻度 クラスタへのリクエストが集中したとき特定SSDだけ待ち行列が伸び、理論上は複数端末へ分散していてもaggregate 帯域を使えないことがある。複製されたentryについて現在待ち行列の短いSSDを選び、必要に応じてクラスタ配置を更新することで、共活性に基づく並列性をランタイムの実負荷へ合わせる。つまりオフライン プロファイリングは『一緒に読む集合』を作り、オンライン スケジューリングは『その集合を今どの端末から読むか』を調整する役割分担になっている。

## memory / I/O構成

Swarmは主として **GPU HBM → CPU DRAM → 複数NVMe SSD** の3階層を想定する。

- GPU HBM: 実際の注意機構計算に必要なKVを置く高速層。
- CPU DRAM: クラスタ代表、ローカル-window KV、高頻度 クラスタなど、選択や頻繁なアクセスに必要な部分を保持する。
- SSD: 大容量KVの主な退避先。共活性クラスタのentryを複数端末へ分散する。

この方式はSSDから読むバイト数をゼロにするのではなく、**同じ読み出しを複数端末へ分割して並列化することでI/O時間を縮める**。したがってSSD台数と独立したPCIe帯域を利用できるハードウェア構成が重要になる。

## 評価条件と主要結果

論文は4つの実ワークロード dataset、5種類のLLM、2種類のSSDを使って評価している。

- I/O時間を平均 **2.41×短縮**。
- 実効帯域利用率を平均 **2.72×改善**。
- 8 SSD構成では最大 **37.67 GB/s** の帯域を報告し、論文の評価環境ではDRAMからGPUへKVを移す経路に近い水準までSSD aggregate 帯域を高めた。

これらはSwarmの評価構成での値であり、SSD数、PCIe 構造、KV sparsity、ワークロードの共活性安定性によって効果は変わる。

## 既存研究との差

### CPU DRAMへのKV offload

DRAM オフロードはSSDより低遅延だが、長寿命・大規模KVを多数保持すると容量と費用が問題になる。SwarmはDRAMを索引 / 高頻度 キャッシュとして残しつつ、bulk KVをSSDへ置く。

### 単一SSD型KV offload

既存のSSD-backed KV キャッシュはI/O量削減、プリフェッチ、GPUからのI/O制御などで待ち時間を減らす。Swarmの中心は**複数SSDの合計帯域をKV アクセス パターンに合わせて引き出すデータ 配置**であり、単一端末の高速化とは異なる。

### 疎なKV選択

疎な注意機構は読むKV数を減らす。Swarmはその選択パターンから「一緒に選ばれやすいKV」を学び、残ったI/Oを複数SSDへ並列化するため、sparsityとmulti-端末 配置を組み合わせる立場にある。

## 限界

- 複数SSDと、それらの帯域を同時利用できるPCIe 構造が必要で、SSD 1台の環境には中心的な利点がない。
- 事前プロファイリングで得た共活性パターンが実ワークロードでもある程度安定していることを前提とする。ワークロードが大きく変わる場合はクラスタ更新が必要になる。
- KVの複製はI/O並列性を高める代わりに保存容量を追加で消費する。
- DRAMを完全には不要にせず、索引、ローカル window、高頻度 キャッシュ用の容量を要求する。
- 本論文の主な改善指標はSSD I/Oであり、エンドツーエンド 提供性能はモデル、注意機構実装、GPU計算、batchingなど他のボトルネックにも左右される。

## 一般的な実装上の含意

保存 オフロードでは「どのデータをSSDへ置くか」だけでなく、**同時に読むデータをどの端末へ散らすか**がaggregate 帯域を決める。アクセス correlationが安定している場合、頻繁に一緒に使うデータを同じ端末へ寄せる通常のlocality重視配置とは逆に、独立I/O 端末へ分散する方が遅延を下げられる場合がある。

KV キャッシュは注意機構 sparsityによってアクセス 集合を小さくできるため、そのアクセス 集合内部の共起情報を保存 配置へ利用できる。これはKV以外でも、予測可能なグループ アクセスを持つ大規模モデル stateを複数保存へ置く場合に応用可能な設計原理である。

## 引用関係

SwarmはCPU DRAM オフロード、疎注意機構によるKV選択、SSD-backed KV キャッシュを前提に、単一SSD 帯域が残るボトルネックを複数端末のparallel I/Oで解く方向へ進める。系統上は、SSD I/OをGPU側から制御するTuttiやin-保存 注意機構のInstAttentionとは異なり、**KVの配置そのものをアクセス correlationに合わせる**研究として位置付けられる。
