# Swarm: Co-Activation Aware KVCache Offloading Across Multiple SSDs

## 書誌情報

- **著者**: Tuowei Wang, Liyun Chu, Ruwen Fan, Ju Ren
- **公開**: arXiv, 2026-03-18
- **arXiv**: 2603.17803
- **分類**: Inference / KV cache offload / SSD / multi-device I/O
- **一次資料**: https://arxiv.org/abs/2603.17803

## 一文要約

attentionで一緒に参照されやすいKV cacheを事前にまとめ、そのグループ内のKVを複数SSDへ分散配置することで、1回のKV読み出しを複数SSDから並列に行い、単一SSDの帯域上限を超える実効I/O帯域を得る方式。

## 問題設定

長いcontextや複数requestで再利用されるKV cacheはGPU HBMだけでは保持しにくく、CPU DRAMへ退避しても大規模・長寿命なcacheでは容量とcostが問題になる。NVMe SSDは大容量かつ安価だが、一般的な1台のSSDはGPUやDRAMより狭いPCIe linkにつながるため、必要なKVをSSDから戻す時間がattention計算の待ち時間になりやすい。

疎なattentionを使って「必要なKVだけ読む」方法はI/O量そのものを減らせるが、SSD 1台あたりの帯域上限は変わらない。Swarmは、KVの参照パターンに**複数SSDを同時に読める並列性**が含まれていないかに着目する。

## 手法

### 一緒に使われるKVを測る

Swarmは事前profilingで、あるKV entryがattentionに選ばれたときに他のどのentryも同時に選ばれることが多いかを数える。論文はこの安定した同時参照傾向をKV cache共活性（KVCache Co-Activation）と呼ぶ。

これは単なるembeddingの近さではなく、実際のattention選択で「Aを読むrequestではBやCも一緒に読むことが多い」というI/O access patternを表す。

### 共活性するKVをcluster化する

各KV entryをnode、同時参照の強さをedgeとしてgraphを作り、互いに一緒に使われやすいentryをclusterへまとめる。厳密な組合せ最適化は高costなので、同時参照される相手が多いentryをclusterの代表（medoid）に選び、その代表と共活性が強いentryを順に加えるheuristicを使う。

あるKVが複数の異なるgroupと頻繁に一緒に使われる場合は、SSD容量を少し余分に使って複製する。これにより、1つの配置へ無理に固定して不要なKVまで読むことを避ける。

### cluster内部を複数SSDへ散らす

重要なのは、共活性するKVを同じSSDへまとめるのではなく、**同時に必要になるKVを複数SSDへ均等に散らす**点である。clusterを読み出すとき各SSDが別々のKVを同時に返せるため、1台のSSD帯域ではなく複数台の合計帯域を利用できる。

clusterの代表entry、直近tokenのlocal window、頻繁に使うhot clusterはCPU DRAMへ残す。incoming queryとDRAM上の代表entryを比較して読むclusterを決めるため、どのclusterが必要かを判断するためだけにSSDを先に読む必要はない。

### runtimeで負荷を均等化する

同じKVが複数SSDへ複製されている場合、どのcopyから読むかでSSDごとの負荷が偏る。Swarmはruntimeで各SSDのloadを見て読み出し先を選び、複数SSDが同時に働くようにする。またdecodeが進んで新しいKVが増えると参照傾向も変わるため、cluster membershipとDRAM cacheを更新する。

## memory / I/O構成

Swarmは主として **GPU HBM → CPU DRAM → 複数NVMe SSD** の3階層を想定する。

- GPU HBM: 実際のattention計算に必要なKVを置く高速層。
- CPU DRAM: cluster代表、local-window KV、hot clusterなど、選択や頻繁なaccessに必要な部分を保持する。
- SSD: 大容量KVの主な退避先。共活性clusterのentryを複数deviceへ分散する。

この方式はSSDから読むbyte数をゼロにするのではなく、**同じ読み出しを複数deviceへ分割して並列化することでI/O時間を縮める**。したがってSSD台数と独立したPCIe帯域を利用できるhardware構成が重要になる。

## 評価条件と主要結果

論文は4つの実workload dataset、5種類のLLM、2種類のSSDを使って評価している。

- I/O時間を平均 **2.41×短縮**。
- 実効bandwidth利用率を平均 **2.72×改善**。
- 8 SSD構成では最大 **37.67 GB/s** のbandwidthを報告し、論文の評価環境ではDRAMからGPUへKVを移す経路に近い水準までSSD aggregate bandwidthを高めた。

これらはSwarmの評価構成での値であり、SSD数、PCIe topology、KV sparsity、workloadの共活性安定性によって効果は変わる。

## 既存研究との差

### CPU DRAMへのKV offload

DRAM offloadはSSDより低latencyだが、長寿命・大規模KVを多数保持するとcapacityとcostが問題になる。SwarmはDRAMをindex / hot cacheとして残しつつ、bulk KVをSSDへ置く。

### 単一SSD型KV offload

既存のSSD-backed KV cacheはI/O量削減、prefetch、GPUからのI/O制御などで待ち時間を減らす。Swarmの中心は**複数SSDの合計bandwidthをKV access patternに合わせて引き出すdata placement**であり、単一deviceの高速化とは異なる。

### 疎なKV選択

疎なattentionは読むKV数を減らす。Swarmはその選択patternから「一緒に選ばれやすいKV」を学び、残ったI/Oを複数SSDへ並列化するため、sparsityとmulti-device placementを組み合わせる立場にある。

## 限界

- 複数SSDと、それらの帯域を同時利用できるPCIe topologyが必要で、SSD 1台の環境には中心的な利点がない。
- 事前profilingで得た共活性patternが実workloadでもある程度安定していることを前提とする。workloadが大きく変わる場合はcluster更新が必要になる。
- KVの複製はI/O並列性を高める代わりにstorage容量を追加で消費する。
- DRAMを完全には不要にせず、index、local window、hot cache用の容量を要求する。
- 本論文の主な改善指標はSSD I/Oであり、end-to-end serving性能はmodel、attention実装、GPU計算、batchingなど他のbottleneckにも左右される。

## 一般的な実装上の含意

storage offloadでは「どのdataをSSDへ置くか」だけでなく、**同時に読むdataをどのdeviceへ散らすか**がaggregate bandwidthを決める。access correlationが安定している場合、頻繁に一緒に使うdataを同じdeviceへ寄せる通常のlocality重視配置とは逆に、独立I/O deviceへ分散する方がlatencyを下げられる場合がある。

KV cacheはattention sparsityによってaccess setを小さくできるため、そのaccess set内部の共起情報をstorage placementへ利用できる。これはKV以外でも、予測可能なgroup accessを持つ大規模model stateを複数storageへ置く場合に応用可能な設計原理である。

## 引用関係

SwarmはCPU DRAM offload、疎attentionによるKV選択、SSD-backed KV cacheを前提に、単一SSD bandwidthが残るbottleneckを複数deviceのparallel I/Oで解く方向へ進める。系統上は、SSD I/OをGPU側から制御するTuttiやin-storage attentionのInstAttentionとは異なり、**KVの配置そのものをaccess correlationに合わせる**研究として位置付けられる。
