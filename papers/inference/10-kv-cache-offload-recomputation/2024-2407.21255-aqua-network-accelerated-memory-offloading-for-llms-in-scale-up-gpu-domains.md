# Aqua: Network-Accelerated Memory Offloading for LLMs in Scale-Up GPU Domains

> 同じNVLink / NVSwitch接続内で余っている別GPUのHBMを、KV キャッシュなどの一時退避先として借り、CPU DRAMへ退避するより高速に要求を入れ替えて公平なonline 推論提供を行うメモリ システム。

## 概要

Aquaは、LLM 推論提供で要求が一時的に集中してKV キャッシュがHBMを使い切ると、後続要求が長く待たされTTFTが悪化する問題を扱う。

要求を途中で一時停止して別要求へGPU時間を渡せば待ち時間を減らせるが、そのたびにKV キャッシュなどの要求 状態をCPU DRAMへ退避・復帰するとPCIe転送が重く、スループットが落ちる。

Aquaはこの退避先をCPU DRAMだけに固定せず、**同じNVLink / NVSwitch接続内で使われていない別GPUのHBMを借りる**。GPU間接続はPCIeより高帯域なので、空きHBMを高速な一時退避メモリとして使い、要求切替のdata movementを短縮する。

さらに「どのGPUがどれだけHBMを貸せるか」「どのモデルと同じ高速接続内に置くか」「貸した側のloadが増えたらいつ返すか」まで管理する。

## 問題設定

LLM 推論ではモデル 重みに加えて要求ごとのKV キャッシュが増えるため、要求集中時にはGPU演算性能よりHBM容量が先に限界へ達しやすい。

vLLMのような推論提供 エンジンでは、新しい要求を待ち行列に置いてメモリが空くのを待たせる。このとき先に入った長い要求が後続要求を待たせる状態が起こる。一般に `head-of-line blocking` と呼ばれるが、ここでは**長い要求が先頭にいるため短い要求まで開始できない状態**を意味する。

要求を短い時間単位で交代させれば公平性は上がるが、要求を止めるたびにKV キャッシュをCPU DRAMへ移すとPCIeがボトルネックになる。論文では公平スケジューラを単純にvLLMへ追加すると要求 完了 timeが約50%悪化する例を示す。

Aquaの観察は、同じGPU サーバ内でも全ジョブが同時にHBM不足になるとは限らないことにある。視覚 / 音声 / 一部LLM ワークロードではGPU計算を十分使っていてもHBMが数十GB余る場合がある。そこで**別ジョブの余剰HBMをKV不足のジョブへ貸す**。

## 手法

### 1. どのjobがmemoryを貸せるか、借りる必要があるかを事前測定する

各モデル / ワークロードについて、SLOを守ったままどれくらいHBMが余るかを測る。

- **生成側:** 性能目標を維持してもHBMが余るジョブ
- **消費側:** KV キャッシュなどのため追加メモリを必要とするジョブ

という役割に分ける。

生成側の要求量が増えて貸せるメモリが減った場合は、借りていた側からHBMを回収する。

### 2. 貸し手と借り手を同じ高速GPU間接続内へ配置する

別GPUのHBMを高速に使うには、生成側と消費側が同じNVLink / NVSwitch接続内にいる必要がある。

Aquaはモデル配置時に、空きメモリ量だけでなく**高速GPU間転送が使える組み合わせか**も考えて生成側と消費側を対応付ける。

1台の生成側へ多数消費側を集中させるとGPU間帯域が競合するため、基本設計では1 生成側対1 消費側に近い対応を使う。

### 3. 借りたHBMを普通のswap領域のように扱う

消費側側は、退避先が別GPU HBMかCPU DRAMかを毎回意識しない。

Aqua-libが一時退避用tensorの物理位置を管理し、生成側側のloadが増えたら、そのtensorをCPU DRAMへ移してHBMを返せるようにする。

論文ではこの「必要に応じて容量を貸し借りできるメモリ」を `elastic memory` と呼ぶ。

### 4. Requestを途中で入れ替えてGPU時間を公平に配る

AquaはvLLMへ要求 先取りを導入し、長い要求だけがGPUを占有し続けないようにする。

プリフィル 要求とデコード 要求では1 反復あたりの計算量が違うため、それぞれに一定のトークン枠を用意し、その中で**これまで受けたGPU計算時間が少ない要求を優先**する。

バッチから外れた要求のKVを退避し、再開する要求のKVを戻す。

### 5. 小さいKV blockをまとめて大きなGPU間転送にする

PagedAttentionのKV キャッシュは多数の小ブロックへ分かれている。小さいcopyを大量に発行するとNVLinkの最大帯域を使い切れない。

Aquaは複数ブロックを一時バッファへまとめ、大きなtransferとして別GPUへ送る。戻すときもまとめて受信し、元ブロック位置へ配り直す。

A100の測定では4MB転送が約50GB/sなのに対し、64MBでは約200GB/sまで上がるとしており、**論理的なKV ブロックサイズと、実際にネットワークへ流すtransferサイズを分ける**ことが重要になる。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| 主testbed | 8× NVIDIA H100 80GB |
| GPU-GPU | NVLink / NVSwitch、約450GB/s |
| Host DRAM | 1.5TB |
| GPU-host | PCIe Gen5、約50GB/s |
| 副testbed | 2× A100 80GB、NVLink約300GB/s |
| LLM | Llama 3.1 8B / 70B、Yi-34B-200K、OPT-30B |
| その他model | Stable Diffusion系、MusicGen、AudioGen等 |
| Dataset | ShareGPT、arXiv summarization等 |
| Engine | vLLM、FlexGen |

### Request集中時のonline serving

Llama 3.1 70Bで要求 rateを一時的に2倍へ増やすワークロードでは、通常vLLMの待ち行列化によりTTFTが最大約20秒へ伸びる。

Aquaを使った公平スケジューラではremote GPU HBMへの高速退避により、**TTFTを最大20倍改善**し、CPU DRAMへ退避するvLLM版よりTPOTも最大1.5倍改善した。

### Long-prompt / memory-constrained inference

OPT-30B、8K プロンプトのFlexGen ワークロードでは、KV / 推論 状態がGPUへ収まらずホスト DRAMへの退避が必要になる。

Aqua Tensorを別GPU HBMへ置くことで、通常のDRAM スワップに対して**生成 スループットを4倍**へ改善した。

### Prefix cacheとmemory貸出側への影響

100K トークン級の接頭部 キャッシュを再利用するYi-34B-200Kでは、キャッシュをremote HBMへ置くことでlong プロンプトのTTFTを約3.5倍改善した。

メモリを貸す側の影響は、視覚 モデルではほぼなく、AudioGen等ではスループット差5%未満、tensor-parallel Llama 70Bでも平均TPOT悪化は約5%だった。

生成側 loadが増えた場合は貸していたメモリを回収し、消費側性能を落として生成側側のSLAを守れることも確認している。

## 既存研究との差

### vLLM / CPU DRAM swapとの違い

vLLMの退避先は主にCPU DRAMで、transfer 帯域はPCIeへ制約される。Aquaは同じNVLink / NVSwitch接続内の**peer GPU HBMを先に使う高速な退避先**とするため、要求を頻繁に入れ替えやすい。

### FlexGenとの違い

FlexGenは1つのジョブ内でGPU / CPU / SSDへの配置とスケジュールを最適化する。Aquaは複数ジョブが同居する環境で、**別ジョブが使っていないGPU メモリを借りる**ことが中心であり、クラスタ内のモデル配置まで含む。

### Pie / SuperInferとの違い

PieとSuperInferはGH200のlocal CPU DRAMを高速CPU-GPU接続経由でKV 階層として使う。AquaはCPU メモリではなく**別GPUの余剰HBM**を使い、複数モデル間の資源 imbalanceを利用する。

## 限界

- 同じNVLink / NVSwitch接続内に十分なunused HBMを持つ別ジョブが必要。
- 貸す側と借りる側が同時にメモリ帯域律速になると、GPU間通信量が貸す側の性能へ影響する。
- 生成側 / 消費側分類は過去ワークロード プロファイルに依存し、要求 分布が大きく変わると推定が外れる可能性がある。
- 高速GPU間接続を越えたrack-scale remote メモリは主対象ではない。
- remote HBMを借りられない場合はCPU DRAMへfallbackするため、その条件では通常のPCIe スワップ性能へ戻る。
- モデル 配置を変更できるmulti-tenant 演算子を前提とし、単一消費側 PC向けではない。

## 一般的な実装上の含意

Aquaは、GPU メモリを「そのGPUで動くモデル専用」と固定せず、**高速GPU間接続内ではメモリ 容量をジョブ間で貸し借りできる資源**として扱えることを示す。

特にHBM容量とcompute利用率の偏りがモデルごとに異なる環境では、追加GPUを起動する前にspare HBMをスワップ 階層として使うことで要求 burstを吸収できる。

また高速interconnectでも小さいtransferでは帯域を使い切れないため、paged KVの論理的 ブロック管理と物理的 transferサイズを分離して大きくまとめる必要がある。
