# Aqa (Aqua): Network-Accelerated Memory Offloading for LLMs in Scale-Up GPU Domains

> **一覧用要約**：Aqa（リポジトリではAqua）は同一NVLink/NVSwitch領域内の余剰GPUメモリを、他の推論ジョブのKVキャッシュや推論状態の高速退避先として貸し借りする。貸し手・借り手の事前分類、モデル配置、弾力的テンソル管理、公平な先取りスケジューリングを組み合わせ、要求集中時の初回応答時間と処理率を改善する。

## 概要

本論文は、大規模言語モデルを複数の利用者へ提供する環境で、GPUメモリ不足によって要求が長時間待たされる問題を扱う。推論基盤はモデル重みに加えて、各要求の過去トークンに対応するキー・値キャッシュをGPUの高帯域メモリに保持する。要求が急増すると空きメモリが足りなくなり、後続要求を待ち行列へ入れる入場制御が必要になる。先行する長い要求がGPUメモリを占め続けると、後続要求の初回トークンまでの時間が大きく悪化する。

要求を短い時間枠で切り替える先取りスケジューリングを導入すれば、待ち行列の先頭で長い要求が他の要求を塞ぐ状況を減らせる。しかし切替時にKVキャッシュなどの推論状態をCPUメモリへ退避・復帰すると、PCIe転送が遅く、要求完了時間と全体処理率が悪化する。Aqaの着想は、同じ複数GPUサーバ内でも、全てのジョブが同時にGPUメモリ容量を使い切るとは限らないという点にある。視覚・音声生成のように演算性能が先に律速となるジョブでは、高速なGPUメモリが余る場合がある。

Aqaは、この余剰メモリを別ジョブの推論状態の一時退避先として貸し出す。GPU間のNVLink/NVSwitchはCPUメモリへのPCIe転送より高帯域であるため、要求の切替に必要な退避・復帰を高速化できる。事前に各ジョブをメモリの貸し手と借り手へ分類し、同じ高速接続領域へ適切に配置する。実行時には弾力的テンソル管理器が貸出先のGPUメモリとCPUメモリを切り替え、貸し手の負荷が増えたらメモリを返す。さらにvLLMへ公平な先取りスケジューラを組み込み、プリフィルと復号の両段階を考慮して要求を入れ替える。

主要評価はNVLink/NVSwitchで接続された8基のH100 80GBを用いる。要求集中時の初回トークン時間を最大20倍改善し、長いプロンプトを持つメモリ不足の推論ではCPUメモリへの退避に比べて生成スループットを約4倍へ改善する。これらは異なるワークロードの結果であり、同一の条件で同時に20倍と4倍を得たという意味ではない。また、原著の本文で使われるシステム名は**Aqa**であり、公開リポジトリや既存の収録題名では**Aqua**と表記される。この名称差は同一論文の別表記として扱い、別論文として重複登録しない。

## 問題設定：公平な先取りと高い処理率が衝突する

### 入場制御が引き起こす先頭要求による待ち

通常の推論基盤では、現在の要求群をバッチとして処理し、GPUメモリが空くまで新しい要求を待たせる。バッチ処理は処理率を高める一方、先に入った要求の処理が長引くと後続要求の開始が遅れる。原著図1では、vLLMで要求率を一時的に増やすと、初回トークン時間が大幅に伸びる例を示す。これに対して公平な時間分割を加えると各要求は早く計算機会を得られるが、切替時の状態退避によって要求完了時間が悪化する。

原著は、単に先取りを導入した場合の性能悪化について本文内に複数の表現を使っている。序論では要求完了時間が2倍以上に増えると記述する一方、背景では約50%増加と述べる。測定条件の詳細を揃えず一つの固定値として断定することは避け、**CPUメモリへの頻繁な退避が処理率を損なう**という共通の結論を採用する。

### KVキャッシュの大きさとGPUメモリ競合

標準的なTransformerでは、各要求の過去トークンのキーと値を保持する。単一要求のKVキャッシュ容量は、通常は系列長に対して線形に増える。複数要求を同時に処理すれば、その総和がGPUメモリを消費する。原著序論にはKVキャッシュが系列長の二乗で増えるという記述があるが、一般的な標準KVキャッシュの保存容量に対しては正確ではない。二乗に増えるのは素朴な注意演算のトークン対の数であり、KV保存容量とは区別すべきである。Aqaの問題設定は、要求数や系列長が増えることでGPUメモリ容量が不足するという点にある。

CPUメモリへ退避すれば容量不足は緩和するが、GPUとCPUの間のPCIe帯域は同じサーバ内のGPU間高速接続より低い。要求の切替を頻繁に行うと、推論状態の退避と復帰のためにGPUが待つ時間が増える。Aqaは退避先をCPUメモリだけに固定せず、別GPUの空き高帯域メモリを中間階層として利用する。

## 手法

### 1. メモリの貸し手と借り手を測定から分類する

Aqa-profilerは、各モデルの負荷とGPUメモリ使用量を調べ、性能目標を維持したままメモリを貸せるジョブを生産者（producer）、追加のGPUメモリを必要とするジョブを消費者（consumer）に分類する。音声・画像生成では、バッチを増やしても処理率が頭打ちになった時点でメモリが余る場合がある。原著図3ではA100 80GB上で、処理率が飽和しても数十GBの空きメモリが残る例を示す。

ただし、LLMでは単にバッチを最大まで増やすと初回応答時間や出力トークン間隔が悪化するため、処理率だけで余剰メモリを判定できない。原著§4.1は、LLMの初回トークン時間とトークン間遅延の制約を考慮した分類が必要であると説明する。貸し手にとっての余剰メモリは、物理的に空いている量ではなく、**サービス品質を守ったまま提供できる量**である。

### 2. 貸し手と借り手を同じ高速接続領域へ配置する

Aqa-placerは、モデルをサーバへ割り当てる際に、各モデルの余剰または不足メモリ量と、貸し手・借り手の数の均衡を考慮する。高速なGPU間転送を使うため、メモリを貸すモデルと借りるモデルを同じNVLink/NVSwitch領域へ配置する必要がある。単にクラスタ全体で空きメモリの総量が十分でも、遠いGPUにしか空きがなければ同じ速度を得られない。

原著§5の配置問題は、各モデルを一つのサーバへ割り当て、テンソル並列の分割片を同じサーバに保ち、サーバのGPU数を超えないという制約を持つ。さらにサーバごとのメモリ需要と供給を釣り合わせ、貸し手一台に多数の借り手を集中させないよう貸し手・借り手の数も均衡させる。これはGPU間帯域の過剰な競合を防ぐためである。著者らはGurobiで最適化問題を解き、最大128GPUのクラスタについて5秒以内に最適値から2%以内の解を得たと報告する。

配置は実行時の一要求ごとに解くものではなく、モデル配置を決める管理段階の処理である。貸し手の負荷が変化した場合、実行時のメモリ管理器は貸出メモリを返すが、その結果としてクラスタ全体の配置が最適でなくなる可能性がある。モデルを再配置する頻度と移動費用の交換条件は原著で今後の課題とされる。

### 3. 弾力的テンソル管理器で物理位置を隠蔽する

Aqa-libは、推論基盤が扱うテンソルの物理的な退避先を管理する。借り手はAqa Tensorを作り、貸し手GPUの空きHBMへ退避する。貸し手の空き容量が不足する場合はCPUメモリへ退避する。推論基盤側は論理的なテンソルを扱い、物理位置の変化は管理器が追跡する。これによりvLLMやFlexGenの大規模な書換えを避けられる。

貸し手側で新しい要求が増えてメモリを使う必要が生じた場合、Aqa-libは貸出メモリを回収する。借り手のテンソルは必要に応じてCPUメモリへ移されるため、貸し手のサービス品質を守れる。弾力性とは、借り手が一度獲得したGPUメモリを永続的に占有できるという意味ではなく、貸し手の状況に応じて退避先が変化することである。

### 4. 公平な先取りスケジューラで要求を短い時間枠へ分ける

Aqaは、vLLMに完全公平スケジューラに類する方式を導入し、各要求へ計算機会を配る。単純に生成済みトークン数が少ない要求を優先すると、プリフィル段階の要求が優先されすぎ、プリフィルと復号を同じバッチへ混ぜてGPUを効率利用する最適化を損なう。原著§7はこの問題を避けるため、バッチ内の枠をプリフィルトークン用と復号トークン用へ分ける。

復号枠はGPUメモリに収まる最大要求数を上限とし、復号済みトークン数が少ない要求から選ぶ。プリフィル枠には処理済みプリフィルトークン数が少ない要求を割り当てる。空いた復号枠はプリフィル側へ再配分できる。一定回数の推論反復ごと、または要求が完了した時点でバッチを組み直し、次のバッチへ入らない要求のKVキャッシュを退避し、再開する要求の状態を復帰する。高速退避が可能だからこそ、先取りの頻度を上げても処理率を保ちやすい。

### 5. 小さなKVブロックを大きなGPU間転送へまとめる

vLLMのKVキャッシュは層ごと、トークンブロックごとに分散している。小さなコピーを大量に発行するとNVLinkの帯域を十分に使えない。原著はA100間の転送で、4MBのバッファは約50GB/秒、64MBでは約200GB/秒になる例を示す。Aqaは小さなKVテンソルを一時バッファへ集めて大きなコピーとして送信し、受信後に元の配置へ散布する。

この集約・散布の処理は、KVキャッシュの論理ブロック管理を変更するものではない。アプリケーション側では小さなブロックのまま扱い、物理転送の単位だけを大きくする。転送を高速化するための一時バッファとコピー処理が追加されるが、GPU間接続の実効帯域が上がれば退避時間全体を短縮できる。

### 6. 実装規模と整合性の確保

原著§8では、Aqa-libをPyTorchテンソルを使う約500行のPythonライブラリとして実装し、vLLM v0.5.3へ公平スケジューラ約150行、KVブロックの集約用CUDAカーネル約200行を追加したと説明する。既存のvLLMやFlexGenとの退避先の統合は50行未満の変更で行った。配置スケジューラは約700行、メモリ貸借を調停するコーディネータは約250行である。

GPUメモリからCPUメモリへの移動中に計算が走ると、テンソルの内容が壊れる危険がある。著者らは推論基盤の実行ループにGPU計算が行われない境界があることを利用し、安全な時点でメモリ移動を行う。これはGPUメモリの物理位置を透過的に変える際の重要な整合性条件である。

## 評価

### 実機構成と指標

| 項目 | 原著の条件 |
|---|---|
| 主実機 | NVIDIA H100 80GBを8基搭載するサーバ。 |
| GPU間接続 | NVLink/NVSwitch、約450GB/秒。 |
| CPUメモリ | 1.5TB。 |
| GPU-CPU接続 | PCIe Gen5、約50GB/秒。 |
| 副実機 | NVIDIA A100 80GBを2基、NVLink約300GB/秒。 |
| 推論基盤 | vLLM、FlexGen。 |
| 主なLLM | Llama 3.1 8B/70B、Yi-34B-200K、OPT-30B。 |
| 他の貸し手 | Stable Diffusion系、AudioGen、MusicGen等の生成モデル。 |
| ワークロード | ShareGPT、長文要約、8Kプロンプト、要求集中など。 |
| 指標 | 初回トークン時間、出力トークン間隔、要求完了時間、生成スループット、貸し手への影響。 |

### 要求集中時の初回応答時間

原著は要求率が急増する条件で、通常のvLLMが待ち行列を長くし、初回トークン時間を大幅に悪化させることを示す。CPUメモリへの退避を使う公平スケジューラは初回応答を改善するが、頻繁な退避・復帰によって要求完了時間が伸びる。Aqaでは余剰GPUメモリを高速な退避先にすることで、初回トークン時間を最大20倍改善したと報告する。初回トークン時間は要求の開始しやすさを表し、生成中のトークン間隔や全体スループットとは別の指標である。

### 長いプロンプトを持つメモリ不足推論

OPT-30Bを単一GPUで実行し、長さ8,192トークンのプロンプトを10分間処理する実験では、モデル重みと推論状態がGPUメモリに収まらず、退避が必要となる。FlexGenの通常のCPUメモリ退避と比較し、Aqaの別GPUメモリ退避は生成スループットを約4倍にした（原著図9b）。これは高負荷の要求集中による初回トークン時間改善とは異なる実験である。GPUメモリを貸せる別ジョブが存在し、高速GPU間接続が使えることが前提になる。

### 長い共通接頭辞のキャッシュ再利用

Yi-34B-200Kの長い共通接頭辞をキャッシュして再利用する実験では、CPUメモリから状態を読み戻すと初回トークン時間に大きなスパイクが生じる。原著図9aは、キャッシュ再利用時の初回トークン時間が最大約4秒へ増える例を示す。Aqaの高速な退避先を使うと、長いプロンプトの初回トークン時間を約3.5倍改善し、同じバッチに入った後続要求の待ち時間も減らせる。これは単にKV容量を増やすだけでなく、キャッシュを復帰させる転送経路の改善である。

### メモリを貸す側への影響

メモリ貸借は借り手に利益をもたらす一方、貸し手のGPUメモリ帯域を消費する。原著図10では画像生成の貸し手への処理率影響はほぼなく、音声生成では5%未満である。LLMの貸し手では平均トークン間隔が約4.5ms悪化する例があり、テンソル並列で動くLlama 3.1 70Bでも平均トークン間隔の悪化は約5%だった（図11）。従って貸し手への影響はゼロではないが、借り手の4倍改善と比較して小さい条件が報告される。

貸し手の負荷が増えた場合は、Aqa-libが貸出メモリを回収してCPUメモリへ退避先を移す。このとき借り手は高速退避の利益を失う可能性があるが、貸し手のサービス品質を優先する。したがってAqaの性能は、クラスタ内で余剰メモリが安定して存在する割合にも依存する。

### 配置スケジューラの解法と規模

Aqa-placerは、モデルをどのサーバへ置くかを整数最適化として定式化する。モデルの分割片が同じサーバへ収まる制約、サーバのGPU数、メモリ需要と供給、貸し手・借り手の数の均衡を同時に扱う。原著では128GPUまでの問題について5秒以内に最適値から2%以内の解を得た。これは配置計算の結果であり、推論処理率が2%以内で最適になるという意味ではない。ジョブ移動の実際の費用を含めて再配置頻度を最適化することは未解決である。

## 既存研究との差

通常のvLLMのCPUメモリ退避はPCIe帯域に制限される。Aqaは同一高速GPU間接続領域の余剰HBMを先に利用し、要求の先取り切替を低費用で行えるようにする。FlexGenは一つの推論ジョブのGPU・CPU・SSDの階層配置を最適化するが、Aqaは**複数ジョブ間で空きGPUメモリを貸し借りする**点が中心的に異なる。HeteGenはCPUとGPUの演算分担で重み転送を減らす方式であり、Aqaは推論状態の退避先と先取りスケジューリングを改善するため、補完的な関係にある。

CUDA統合メモリはGPUとCPUを跨ぐ仮想アドレス空間を提供するが、推論状態のどのテンソルを先に退避・復帰するかをアプリケーションが十分に制御できない場合がある。Aqaは推論基盤の実行境界とキャッシュ構造を理解し、KV状態を意識した退避と先取りを行う。さらに単に空きGPUメモリを発見するだけでなく、配置スケジューラで貸し手と借り手を同じ高速接続領域へ置く。

## 限界と適用条件

第一に、同じNVLink/NVSwitch領域に余剰GPUメモリを持つ貸し手が必要である。全GPUが同時にメモリ容量律速になる場合、Aqaの高速退避先は不足し、CPUメモリへの退避に戻る。単一GPUしかない家庭用PCや、GPU間接続が遅い環境では同じ利得を期待できない。

第二に、貸し手と借り手の双方がGPUメモリ帯域を大量に使うと、GPU間転送による競合が発生する。原著は貸し手の性能悪化が小さい例を報告するが、帯域の競合制御を完全にモデル化したものではない。配置スケジューラが貸し手と借り手の数を均衡させるのも、このリスクを減らすためである。

第三に、事前のワークロード分類は要求到着率やバッチの構成が変化すると古くなる。貸し手の負荷が増えればメモリを返せるが、その結果として配置の効率が下がる。どの頻度でジョブを再配置すべきか、移動費用をどう扱うかは原著の今後の課題である。

第四に、GPU間高速接続領域を超えた遠隔メモリへの一般化は主要な実測対象ではない。ラック規模の高速接続へ概念を拡張できる可能性には言及するが、遠隔の通信遅延や帯域競合まで含めて同じ改善率を保証するものではない。

第五に、最大20倍の初回トークン時間改善と4倍の生成スループット改善は異なる評価であり、同時達成した値として記述してはならない。貸し手の処理率やトークン間隔への小さな悪影響もあり、全ジョブにとって無条件に利益があるわけではない。

## 再監査で修正した重要点

- 原著本文の名称はAqa、公開実装・既存収録名はAquaであり、同一研究の別表記として扱う。
- KVキャッシュの保存容量と、注意演算の二次計算量を混同しない。単一要求の標準KV保存量は通常系列長に対して線形である。
- 初回トークン時間、出力トークン間隔、要求完了時間、生成スループットは異なる指標であり、倍率を混ぜない。
- GPU間の高速メモリ貸借だけでなく、事前分類、モデル配置、弾力的テンソル管理、先取りスケジューラが一体となっている。
- GPU間転送は小さなKVブロックを集約することで実効帯域を改善する。原著の4MB対64MBの比較はA100間転送の例である。
- 余剰メモリがなくなればCPUメモリへ退避先が戻り、貸し手の性能を優先する。
