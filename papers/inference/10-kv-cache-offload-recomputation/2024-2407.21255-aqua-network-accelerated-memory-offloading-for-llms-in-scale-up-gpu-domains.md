# Aqua: Network-Accelerated Memory Offloading for LLMs in Scale-Up GPU Domains

> 同一NVLink / NVSwitch domain内で余っている別GPUのHBMをKV cacheなどのinference stateのswap先として借り、host DRAMより高速なpagingでpreemptive fair schedulingを実用化するmulti-tenant inference memory system。

## 概要

Aquaは、LLM servingでrequest burstが起きてKV cacheがHBMを使い切ると、通常のadmission controlでは後続requestが長くqueueに残りTTFTが悪化する問題を扱う。

preemptive schedulingでrequestを細かくtime-shareすれば待ち時間を減らせるが、requestを切り替えるたびにKV cacheなどのinference stateをhost DRAMへpage-out / page-inするとPCIe転送がbottleneckになり、throughputが落ちる。

Aquaはこのswap先をCPU DRAMではなく、**同じscale-up domain内で空きHBMを持つ別GPU**へ変える。NVLink / NVSwitchはPCIeより高帯域なので、memoryが余っているGPUを「remote HBM tier」として使い、preemptionのdata movementを高速化する。

さらに、どのGPUがmemoryを提供できるかをprofileし、memoryを必要とするjobと同じ高速interconnect内へ配置し、提供GPUのloadが増えたらmemoryを返すところまでsystemとして管理する。

## 問題設定

LLM inferenceではmodel weightに加えてrequestごとのKV cacheが増えるため、burst時にHBM容量が先に限界へ達しやすい。vLLMのようなserving engineは新規requestをqueueしてcapacityが空くのを待たせるため、先に入った長いrequestが後続を塞ぐhead-of-line blockingが発生する。

一方、OSのようにpromptをtime sliceでpreemptすれば公平にGPU時間を配れるが、preemptionではrequest stateのpagingが必要になる。host DRAMへのpagingはPCIe帯域に制約され、論文ではfair schedulerを単純にvLLMへ加えるだけではrequest completion timeが約50%悪化すると報告している。

Aquaの観察は、multi-tenant GPU serverでは全jobが同時にHBM容量不足になるとは限らず、compute-boundなvision / audio / LLM workloadではpeak throughput時にも数十GBのHBMが余る場合がある、というもの。この**他GPUのunused HBMをmemory-bound jobへ貸す**ことでcompute allocationとmemory allocationを分離する。

## 手法

### 1. Aqua-profilerでproducer / consumerを分類する

各modelとworkloadをprofileし、SLAを満たす範囲でどの程度HBMが余るかを測る。

- **producer:** peak throughput / SLAを維持してもHBMが余るjob
- **consumer:** KV cacheや長contextにより追加memoryが必要なjob

LLMでは単純にbatchを増やしてpeak throughputを探すのではなく、TTFT / TBT SLAを満たせる最大request rateを探索し、その時点の空きHBMを提供可能容量として扱う。

producer loadが予測より増えた場合は、後述のAqua-libが貸していたmemoryをreclaimする。

### 2. Aqua-placerで高速interconnect内へproducerとconsumerを配置する

peer GPU HBMを借りるには、producerとconsumerが同じNVLink / NVSwitch domain内にいる必要がある。

Aqua-placerはまずmodelをserverへ割り当て、その後producerとconsumerをmatchingする。単に空きmemory量だけを見るのではなく、同じ高帯域domain内でpagingできる組み合わせを増やすことが目的である。

1 producerを多数consumerへ共有するとNVLink帯域が集中するため、論文のdesignでは基本的に1 producer対1 consumerへ制限する。

### 3. Aqua-libでremote HBMをelastic tensorとして扱う

Aqua-libはremote GPU HBMまたはfallbackのCPU DRAMに置かれた領域を **Aqua Tensor** として抽象化する。

consumer側はswap tensorの物理位置を意識せず利用でき、producerのloadが上がればAqua-libがそのtensorをDRAMへ移してproducerへHBMを返せる。

これにより「空いているGPU memoryを一度貸したら固定」ではなく、producer workloadの変化へ追従するelastic memory poolになる。

### 4. Preemptive Completely Fair SchedulingをLLM向けに調整する

AquaはvLLMへpreemptiveなfair schedulerを実装する。

単純に生成token数が少ないrequestを優先するとprefill requestばかり選ばれ、chunked prefillによるprefill / decode混在の効率が失われる。そのためbatchをprefill token枠とdecode token枠へ分け、各phase内で最もcomputeを受けていないrequestから選ぶ。

一定iterationごと、またはrequest完了時にbatchを組み直し、外れたrequestのKVをswap-out、戻るrequestをswap-inする。

### 5. 小さいKV blockをまとめてNVLink転送する

vLLMのKV cacheはlayerごとに小さいbufferへ分散している。小さいcopyを多数発行するとNVLinkの帯域を使い切れない。

Aquaは複数の小さいtensorをGPU上のtemporary bufferへ集めてから大きなtransferとしてremote GPUへ送り、逆方向ではまとめて受けてからscatterする。

A100のmicrobenchmarkでは4MB transferが約50GB/sなのに対し、64MBでは約200GB/sまで上がるとしており、transfer granularityの調整が重要になる。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| 主testbed | 8× NVIDIA H100 80GB |
| GPU-GPU | NVLink / NVSwitch、約450GB/s |
| Host DRAM | 1.5TB |
| GPU-host | PCIe Gen5、約50GB/s |
| 副testbed | 2× A100 80GB、NVLink約300GB/s |
| LLM | Llama 3.1 8B / 70B、Yi-34B-200K、OPT-30B |
| その他model | Stable Diffusion系、MusicGen、AudioGen等 |
| Dataset | ShareGPT、arXiv summarization等 |
| Engine | vLLM、FlexGen |

### Bursty online serving

Llama 3.1 70Bでrequest rateを一時的に2倍へ増やすworkloadでは、通常vLLMのqueueingによりTTFTが最大約20秒へ伸びる。

Aquaを使ったCFSではremote GPU HBMへの高速swapにより、**TTFTを最大20倍改善**し、host DRAMへswapするvLLM+CFSよりTPOTも最大1.5倍改善した。

### Long-prompt / memory-constrained inference

OPT-30B、8K promptのFlexGen workloadでは、KV / inference contextがGPUへ収まらずhost DRAMへのswapが必要になる。

Aqua Tensorを別GPU HBMへ置くことで、通常のDRAM swapに対して**generation throughputを4倍**へ改善した。

### Prefill cacheとproducerへの影響

100K token級のprefix cacheを再利用するYi-34B-200Kでは、cacheをremote HBMへ置くことでlong promptのTTFTを約3.5倍改善した。

memoryを貸すproducer側の影響は、vision modelではほぼなく、AudioGen等ではthroughput差5%未満、tensor-parallel Llama 70Bでも平均TPOT悪化は約5%だった。

producer loadが増えた場合はmemoryをreclaimし、consumer throughputを落としてproducerのSLAを守れることも実機で確認している。

## 既存研究との差

### vLLM / host DRAM swapとの違い

vLLMのswap先は主にCPU DRAMで、paging bandwidthがPCIeへ制約される。Aquaは同一scale-up domain内の**peer GPU HBMをfirst-classなswap tierとして使う**ため、preemptionを頻繁に行ってもdata movementを短くできる。

### FlexGenとの違い

FlexGenはsingle-job内でGPU / CPU / SSDへの配置とscheduleを最適化する。Aquaはmulti-tenant環境で、**別jobが使っていないGPU memoryをconsumerへ貸す**ことが中心であり、cluster placementまで含む。

### Pie / SuperInferとの違い

PieとSuperInferはGH200のlocal CPU DRAMを高速C2C経由のKV tierとして使う。AquaはCPU memoryではなく**peer GPU HBM**を利用し、複数modelのresource imbalanceを利用する。

またSuperInferが1つのserving instance内でSLOに応じてrequest KVをHBM / DRAM間でrotationするのに対し、Aquaはproducer / consumer modelのmatchingとelastic remote HBM allocationまで扱う。

## 限界

- 同じNVLink / NVSwitch domain内に十分なunused HBMを持つproducer jobが必要。
- producerとconsumerが同時にmemory-bandwidth-heavyになると、peer memory trafficがproducer側のperformanceへ影響する。
- producer / consumer分類は過去workload profileに依存し、request distributionが大きく変わると推定が外れる可能性がある。
- scale-up domainを越えるrack / network-level remote memoryは主対象ではない。
- remote HBMを借りられない場合はCPU DRAMへfallbackするため、その条件では通常のPCIe swap性能へ戻る。
- model placementを変更できるmulti-tenant operatorを前提とし、単一GPU consumer PC向けの方式ではない。

## 一般的な実装上の含意

Aquaは、GPU memoryを「そのGPUで動くmodel専用」と固定せず、**高速GPU-GPU fabric内ではmemory capacityをjob間で分離して貸し借りできるresource**として扱えることを示す。

特にHBM capacityとcompute利用率の偏りがmodelごとに異なるmulti-tenant環境では、追加GPUを起動する前にspare HBMをswap tierとして使うことでburstを吸収できる。

ただし高速interconnectでも小粒度transferでは帯域を使い切れないため、paged KVのlogical block管理とphysical transfer granularityを分離して大きくまとめる必要がある。
