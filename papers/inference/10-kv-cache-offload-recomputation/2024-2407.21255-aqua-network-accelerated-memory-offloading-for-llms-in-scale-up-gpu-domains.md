# Aqua: Network-Accelerated Memory Offloading for LLMs in Scale-Up GPU Domains

> 同じNVLink / NVSwitch接続内で余っている別GPUのHBMを、KV cacheなどの一時退避先として借り、CPU DRAMへ退避するより高速にrequestを入れ替えて公平なonline servingを行うmemory system。

## 概要

Aquaは、LLM servingでrequestが一時的に集中してKV cacheがHBMを使い切ると、後続requestが長く待たされTTFTが悪化する問題を扱う。

requestを途中で一時停止して別requestへGPU時間を渡せば待ち時間を減らせるが、そのたびにKV cacheなどのrequest stateをCPU DRAMへ退避・復帰するとPCIe転送が重く、throughputが落ちる。

Aquaはこの退避先をCPU DRAMだけに固定せず、**同じNVLink / NVSwitch接続内で使われていない別GPUのHBMを借りる**。GPU間接続はPCIeより高帯域なので、空きHBMを高速な一時退避memoryとして使い、request切替のdata movementを短縮する。

さらに「どのGPUがどれだけHBMを貸せるか」「どのmodelと同じ高速接続内に置くか」「貸した側のloadが増えたらいつ返すか」まで管理する。

## 問題設定

LLM inferenceではmodel weightに加えてrequestごとのKV cacheが増えるため、request集中時にはGPU演算性能よりHBM容量が先に限界へ達しやすい。

vLLMのようなserving engineでは、新しいrequestをqueueに置いてmemoryが空くのを待たせる。このとき先に入った長いrequestが後続requestを待たせる状態が起こる。一般に `head-of-line blocking` と呼ばれるが、ここでは**長いrequestが先頭にいるため短いrequestまで開始できない状態**を意味する。

requestを短い時間単位で交代させれば公平性は上がるが、requestを止めるたびにKV cacheをCPU DRAMへ移すとPCIeがbottleneckになる。論文では公平schedulerを単純にvLLMへ追加するとrequest completion timeが約50%悪化する例を示す。

Aquaの観察は、同じGPU server内でも全jobが同時にHBM不足になるとは限らないことにある。vision / audio / 一部LLM workloadではGPU計算を十分使っていてもHBMが数十GB余る場合がある。そこで**別jobの余剰HBMをKV不足のjobへ貸す**。

## 手法

### 1. どのjobがmemoryを貸せるか、借りる必要があるかを事前測定する

各model / workloadについて、SLOを守ったままどれくらいHBMが余るかを測る。

- **producer:** 性能目標を維持してもHBMが余るjob
- **consumer:** KV cacheなどのため追加memoryを必要とするjob

という役割に分ける。

producerのrequest量が増えて貸せるmemoryが減った場合は、借りていた側からHBMを回収する。

### 2. 貸し手と借り手を同じ高速GPU間接続内へ配置する

別GPUのHBMを高速に使うには、producerとconsumerが同じNVLink / NVSwitch接続内にいる必要がある。

Aquaはmodel配置時に、空きmemory量だけでなく**高速GPU間転送が使える組み合わせか**も考えてproducerとconsumerを対応付ける。

1台のproducerへ多数consumerを集中させるとGPU間帯域が競合するため、基本設計では1 producer対1 consumerに近い対応を使う。

### 3. 借りたHBMを普通のswap領域のように扱う

consumer側は、退避先が別GPU HBMかCPU DRAMかを毎回意識しない。

Aqua-libが一時退避用tensorの物理位置を管理し、producer側のloadが増えたら、そのtensorをCPU DRAMへ移してHBMを返せるようにする。

論文ではこの「必要に応じて容量を貸し借りできるmemory」を `elastic memory` と呼ぶ。

### 4. Requestを途中で入れ替えてGPU時間を公平に配る

AquaはvLLMへrequest preemptionを導入し、長いrequestだけがGPUを占有し続けないようにする。

prefill requestとdecode requestでは1 iterationあたりの計算量が違うため、それぞれに一定のtoken枠を用意し、その中で**これまで受けたGPU計算時間が少ないrequestを優先**する。

batchから外れたrequestのKVを退避し、再開するrequestのKVを戻す。

### 5. 小さいKV blockをまとめて大きなGPU間転送にする

PagedAttentionのKV cacheは多数の小blockへ分かれている。小さいcopyを大量に発行するとNVLinkの最大帯域を使い切れない。

Aquaは複数blockを一時bufferへまとめ、大きなtransferとして別GPUへ送る。戻すときもまとめて受信し、元block位置へ配り直す。

A100の測定では4MB転送が約50GB/sなのに対し、64MBでは約200GB/sまで上がるとしており、**logicalなKV blockサイズと、実際にnetworkへ流すtransferサイズを分ける**ことが重要になる。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| 主testbed | 8× NVIDIA H100 80GB |
| GPU-GPU | NVLink / NVSwitch、約450GB/s |
| Host DRAM | 1.5TB |
| GPU-host | PCIe Gen5、約50GB/s |
| 副testbed | 2× A100 80GB、NVLink約300GB/s |
| LLM | Llama 3.1 8B / 70B、Yi-34B-200K、OPT-30B |
| その他model | Stable Diffusion系、MusicGen、AudioGen等 |
| Dataset | ShareGPT、arXiv summarization等 |
| Engine | vLLM、FlexGen |

### Request集中時のonline serving

Llama 3.1 70Bでrequest rateを一時的に2倍へ増やすworkloadでは、通常vLLMのqueueingによりTTFTが最大約20秒へ伸びる。

Aquaを使った公平schedulerではremote GPU HBMへの高速退避により、**TTFTを最大20倍改善**し、CPU DRAMへ退避するvLLM版よりTPOTも最大1.5倍改善した。

### Long-prompt / memory-constrained inference

OPT-30B、8K promptのFlexGen workloadでは、KV / inference stateがGPUへ収まらずhost DRAMへの退避が必要になる。

Aqua Tensorを別GPU HBMへ置くことで、通常のDRAM swapに対して**generation throughputを4倍**へ改善した。

### Prefix cacheとmemory貸出側への影響

100K token級のprefix cacheを再利用するYi-34B-200Kでは、cacheをremote HBMへ置くことでlong promptのTTFTを約3.5倍改善した。

memoryを貸す側の影響は、vision modelではほぼなく、AudioGen等ではthroughput差5%未満、tensor-parallel Llama 70Bでも平均TPOT悪化は約5%だった。

producer loadが増えた場合は貸していたmemoryを回収し、consumer性能を落としてproducer側のSLAを守れることも確認している。

## 既存研究との差

### vLLM / CPU DRAM swapとの違い

vLLMの退避先は主にCPU DRAMで、transfer bandwidthはPCIeへ制約される。Aquaは同じNVLink / NVSwitch接続内の**peer GPU HBMを先に使う高速な退避先**とするため、requestを頻繁に入れ替えやすい。

### FlexGenとの違い

FlexGenは1つのjob内でGPU / CPU / SSDへの配置とscheduleを最適化する。Aquaは複数jobが同居する環境で、**別jobが使っていないGPU memoryを借りる**ことが中心であり、cluster内のmodel配置まで含む。

### Pie / SuperInferとの違い

PieとSuperInferはGH200のlocal CPU DRAMを高速CPU-GPU接続経由でKV tierとして使う。AquaはCPU memoryではなく**別GPUの余剰HBM**を使い、複数model間のresource imbalanceを利用する。

## 限界

- 同じNVLink / NVSwitch接続内に十分なunused HBMを持つ別jobが必要。
- 貸す側と借りる側が同時にmemory-bandwidth-heavyになると、GPU間trafficが貸す側のperformanceへ影響する。
- producer / consumer分類は過去workload profileに依存し、request distributionが大きく変わると推定が外れる可能性がある。
- 高速GPU間接続を越えたrack-scale remote memoryは主対象ではない。
- remote HBMを借りられない場合はCPU DRAMへfallbackするため、その条件では通常のPCIe swap性能へ戻る。
- model placementを変更できるmulti-tenant operatorを前提とし、単一consumer PC向けではない。

## 一般的な実装上の含意

Aquaは、GPU memoryを「そのGPUで動くmodel専用」と固定せず、**高速GPU間接続内ではmemory capacityをjob間で貸し借りできるresource**として扱えることを示す。

特にHBM容量とcompute利用率の偏りがmodelごとに異なる環境では、追加GPUを起動する前にspare HBMをswap tierとして使うことでrequest burstを吸収できる。

また高速interconnectでも小さいtransferでは帯域を使い切れないため、paged KVのlogical block管理とphysical transferサイズを分離して大きくまとめる必要がある。
