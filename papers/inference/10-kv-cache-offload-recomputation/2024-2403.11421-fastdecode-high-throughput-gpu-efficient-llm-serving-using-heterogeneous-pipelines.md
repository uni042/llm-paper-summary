# FastDecode: High-Throughput GPU-Efficient LLM Serving using Heterogeneous Pipelines

> KV キャッシュとそれを読むアテンション計算を複数CPU nodeへ置き、GPUにはモデル 重みを使う計算を集中させることで、KV転送を避けながら大バッチでGPU スループットを高める異種 推論提供 システム。

## 概要

FastDecodeは、KV キャッシュをCPU メモリへ退避するだけではPCIe転送がボトルネックになる問題に対し、**KV キャッシュだけでなく、それを利用するアテンション計算もCPU側へ移す**LLM 推論提供 システムである。

Transformerのデコード計算を、過去トークンとKV キャッシュを使うメモリ律速な **R-Part** と、モデル パラメータを共有する線形 / MLP中心の計算負荷型な **S-Part** に分ける。S-PartはGPUで大バッチ実行し、R-Partは複数のremote CPU nodeでKV キャッシュの近くから実行する。

GPUとCPUの間では巨大なKV キャッシュそのものを往復させず、現在トークンのQ/K/Vとアテンション出力だけを送る。このためGPUからKV キャッシュをほぼ排除でき、GPU メモリをバッチ拡大に使える。

これは**重み オフロードではなくKVキャッシュ オフロード / アテンション compute オフロード**である。モデル 重みはGPU側のS-workerに保持する。

## 問題設定

デコードでは線形 層のGPU効率はバッチを大きくすると改善する一方、アテンションは各系列固有のKV キャッシュを読むためメモリ律速のままである。さらにKV キャッシュ容量はバッチ sizeと系列 lengthの両方に比例して増える。

vLLMのようにKV キャッシュをホスト メモリへスワップする方式では、長い系列でKV全体のCPU↔GPU転送が重くなる。FastDecodeは「KVをGPUへ運ぶ」のではなく、**メモリ律速なアテンション側をKVのあるCPUへ寄せる**ことで、この転送をなくす。

論文の7B相当の例では、バッチ=1024のKV キャッシュは約4.29GBなのに対し、CPU nodeへ送るQ/K/V等の中間ベクトルは約33.5MBで、通信量が2桁以上小さいと見積もっている。

## 手法

### 1. R-PartとS-Partへ分解する

FastDecodeではデコード時の処理を次の2つに分ける。

- **R-Part:** 現在トークンのQと過去K/Vを使うアテンション計算。モデル パラメータを持たず、系列ごとのKV キャッシュに依存する。
- **S-Part:** Q/K/V 射影、アテンション後の射影、MLPなど、系列間で同じパラメータを共有する部分。

R-Partはバッチを大きくしてもGPU compute効率があまり上がらずメモリ 帯域に支配される。一方S-Partは大バッチ化でGPU利用率が大きく改善する。

### 2. GPUのS-workerとCPUのR-workerに分担する

S-workerはGPU上にモデル 重みを保持し、S-Partを処理する。Q/K/Vが得られると各系列分を対応するR-workerへ送る。

R-workerはremote CPU node上にKV キャッシュを保持し、新しいK/Vを追加してアテンションを計算し、出力ベクトルだけをGPUへ返す。R-Partにはモデル パラメータがないため、系列単位で複数CPUへ分散しやすい。

remote CPUを使う理由は、GPU node内のCPUだけではトークン化や調整と競合し、R-Partに必要な集約する メモリ 帯域を確保しにくいためである。

### 3. S-PartとR-Partを2-stage pipelineで重ねる

小バッチ AのR-PartをCPUが処理している間に、GPUは小バッチ BのS-Partを進める。この2-段階 パイプラインでCPUとGPUを同時利用する。

ただしS-Partの処理量はバッチ sizeでほぼ固定なのに対し、R-Partは系列が長くなるほど重くなる。そのままでは生成後半でCPU側が遅くなり、GPUが待つ。

### 4. 長短sequenceを混ぜてCPU負荷を安定化する

FastDecodeは大バッチを一度に開始せず、小さいマイクロバッチを一定間隔で追加する **系列単位 負荷安定化型 スケジュール** を使う。

生成開始直後の短い系列と生成後半の長い系列が同時に存在するようにし、CPUが保持・処理する系列長の総量を時間方向に均す。論文の解析では、一斉開始と比べて最大R-Part ワークロードを理想的にはほぼ半分にできる。

実機ではこのスケジュールにより最大遅延を一斉実行時の66〜70%程度へ抑え、持続可能 スループットを8〜11%改善した。条件を変えた評価では13%改善している。

### 5. GPU batch sizeと必要CPU数をprofileから決める

CPUを増やしすぎるとGPU待ちになり、少なすぎるとGPUがCPU待ちになる。そこでFastDecodeは、GPU上のS-Part 遅延をバッチ sizeごとにマイクロベンチマークし、系列 lengthとR-Part ワークロードから必要なR-worker数を見積もる。

特にCPU側では集約する メモリ 帯域を主要資源として扱い、遅延制約を満たす最大バッチ sizeと、それを支えられるCPU数を決める。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA A10 24GB ×1 |
| GPU node host memory | 256GB |
| R-worker | 最大4 node、各node dual-socket AMD EPYC |
| Network | InfiniBand |
| Model | Llama-7B / Llama-13B / OPT-175B |
| Precision | FP16、quantization / pruningなし |
| Generated sequence length | 1024 tokens |
| Baseline | vLLM、TensorRT-LLM、FastLLM、vanilla PyTorch Llama |

評価コストを下げるためモデルの層数を削減した実行も使い、層数と遅延がほぼ線形であるという測定に基づいてfull モデルのスループット / 遅延を推定している。この点は実測結果を読む際の重要な注意点である。

### Throughput

Llama-7Bでは、vLLMの452 トークン/sに対しFastDecodeはバッチ=1024で2279 トークン/s。バッチ=128でも1052 トークン/sを出している。

Llama-13Bでは、vLLMの350 トークン/sに対しバッチ=1024で1441 トークン/s、バッチ=128で660 トークン/sだった。

論文全体では同一GPUを使うvLLM比 **1.88〜5.04倍**のスループットを報告している。大バッチほどスループットは高いが、128→1024の8倍バッチ化でスループット増加は約2倍に留まり、遅延とのトレードオフがある。

### Latencyとscaling

FastDecode バッチ=128の平均トークン 遅延はLlama-7Bで120.8ms、13Bで191.6ms。最大スループット設定では小バッチ設定より遅延が約3.5倍になる。

R-workerを1→8 CPU socketへ増やした場合、系列 length 1024では7Bで72.8%、13Bで84.1%のstrong-scaling 効率を示す。一方系列 length 128では13Bでも8 socketへの拡張効率が37.6%まで落ち、CPUを増やしすぎるとS-workerがボトルネックになる。

プロファイリングでは、ある13B構成でQ/K/VのGPU→CPU copyに約3ms、ネットワーク転送に約7.4ms、1 トークン 反復全体に約43msかかり、分散 特徴ベクトル通信が約25%のオーバーヘッドを占めた。

## 既存研究との差

### vLLMとの違い

vLLMはPagedAttentionでGPU メモリ fragmentationを抑え、必要に応じてKV ページをホスト メモリへスワップする。FastDecodeはKVをGPUへ戻すのではなく、**アテンション計算自体をKVのあるCPUへ移す**ため、長い系列でのKV スワップ 通信量を避ける。

### FlexGenとの違い

FlexGenは重み・活性値・KV キャッシュをGPU / CPU / SSDへ配置し、主にoffline 大バッチ スループットを高める。FastDecodeはモデル 重みをGPUに残し、KV キャッシュとアテンションだけを分離して分散 CPUへ置くため、対象となるオフロード objectが異なる。

### HeteGenとの違い

HeteGenは線形 重みの一部をCPUで直接計算して**重み転送**を減らす。FastDecodeは線形 / MLPをGPUへ集中させ、CPUは**KV キャッシュを使うアテンション計算**を担当する。CPU-GPU協調という点は共通するが、CPUへ移す計算はほぼ逆である。

## 限界

- CPU nodeを複数追加する前提で、単一消費側 PC向けのオフロード方式ではない。
- ネットワーク通信はKV転送より小さいものの無視できず、実測では特徴ベクトル通信が約25%の反復 オーバーヘッドを占める構成がある。
- 系列が短い場合はR-Partが軽く、CPUを増やしても尺度しにくい。
- スループット最大化には大バッチが必要で、トークンごとの 遅延とのトレードオフが大きい。
- Llama / OPT評価の一部は層数を減らしたモデルからfull モデル性能を推定している。
- 2026-09-06時点で著者による公式実装の公開は確認できなかった。vLLMへの導入提案も特徴 要求止まりで、upstream実装にはなっていない。

## 一般的な実装上の含意

FastDecodeは、KVキャッシュ オフロードで重要なのは「KVをどこへ保存するか」だけではなく、**KVを毎トークン読むアテンション計算をどこで実行するか**だと示している。

CPU メモリへKVを置く場合、毎トークン KV全体をGPUへ戻すより、Q/K/Vやアテンション outputのような小さい活性値だけを送り、メモリ律速部分をCPU側で処理する方が有利になり得る。また、CPU/GPUを分業させる場合は平均処理量だけでなく、系列 lengthの増加による時間変動をスケジューラで平滑化する必要がある。
