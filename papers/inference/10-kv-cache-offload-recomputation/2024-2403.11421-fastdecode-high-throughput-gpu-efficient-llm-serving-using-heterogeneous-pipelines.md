# FastDecode: High-Throughput GPU-Efficient LLM Serving using Heterogeneous Pipelines

> KV cacheとそれを読むattention計算を複数CPU nodeへ置き、GPUにはmodel weightを使う計算を集中させることで、KV転送を避けながら大batchでGPU throughputを高めるheterogeneous serving system。

## 概要

FastDecodeは、KV cacheをCPU memoryへ退避するだけではPCIe転送がbottleneckになる問題に対し、**KV cacheだけでなく、それを利用するattention計算もCPU側へ移す**LLM serving systemである。

Transformerのdecode計算を、過去tokenとKV cacheを使うmemory-boundな **R-Part** と、model parameterを共有するlinear / MLP中心のcompute-heavyな **S-Part** に分ける。S-PartはGPUで大batch実行し、R-Partは複数のremote CPU nodeでKV cacheの近くから実行する。

GPUとCPUの間では巨大なKV cacheそのものを往復させず、現在tokenのQ/K/Vとattention出力だけを送る。このためGPUからKV cacheをほぼ排除でき、GPU memoryをbatch拡大に使える。

これは**weight offloadではなくKV-cache offload / attention compute offload**である。model weightはGPU側のS-workerに保持する。

## 問題設定

decodeではlinear layerのGPU効率はbatchを大きくすると改善する一方、attentionは各sequence固有のKV cacheを読むためmemory-boundのままである。さらにKV cache容量はbatch sizeとsequence lengthの両方に比例して増える。

vLLMのようにKV cacheをhost memoryへswapする方式では、長いsequenceでKV全体のCPU↔GPU転送が重くなる。FastDecodeは「KVをGPUへ運ぶ」のではなく、**memory-boundなattention側をKVのあるCPUへ寄せる**ことで、この転送をなくす。

論文の7B相当の例では、batch=1024のKV cacheは約4.29GBなのに対し、CPU nodeへ送るQ/K/V等の中間vectorは約33.5MBで、通信量が2桁以上小さいと見積もっている。

## 手法

### 1. R-PartとS-Partへ分解する

FastDecodeではdecode時の処理を次の2つに分ける。

- **R-Part:** 現在tokenのQと過去K/Vを使うattention計算。model parameterを持たず、sequenceごとのKV cacheに依存する。
- **S-Part:** Q/K/V projection、attention後のprojection、MLPなど、sequence間で同じparameterを共有する部分。

R-Partはbatchを大きくしてもGPU compute効率があまり上がらずmemory bandwidthに支配される。一方S-Partは大batch化でGPU利用率が大きく改善する。

### 2. GPUのS-workerとCPUのR-workerに分担する

S-workerはGPU上にmodel weightを保持し、S-Partを処理する。Q/K/Vが得られると各sequence分を対応するR-workerへ送る。

R-workerはremote CPU node上にKV cacheを保持し、新しいK/Vを追加してattentionを計算し、出力vectorだけをGPUへ返す。R-Partにはmodel parameterがないため、sequence単位で複数CPUへ分散しやすい。

remote CPUを使う理由は、GPU node内のCPUだけではtokenizationやcoordinationと競合し、R-Partに必要なaggregate memory bandwidthを確保しにくいためである。

### 3. S-PartとR-Partを2-stage pipelineで重ねる

mini-batch AのR-PartをCPUが処理している間に、GPUはmini-batch BのS-Partを進める。この2-stage pipelineでCPUとGPUを同時利用する。

ただしS-Partの処理量はbatch sizeでほぼ固定なのに対し、R-Partはsequenceが長くなるほど重くなる。そのままでは生成後半でCPU側が遅くなり、GPUが待つ。

### 4. 長短sequenceを混ぜてCPU負荷を安定化する

FastDecodeは大batchを一度に開始せず、小さいmicro-batchを一定間隔で追加する **sequence-level load-stabilizing schedule** を使う。

生成開始直後の短いsequenceと生成後半の長いsequenceが同時に存在するようにし、CPUが保持・処理するsequence長の総量を時間方向に均す。論文の解析では、一斉開始と比べて最大R-Part workloadを理想的にはほぼ半分にできる。

実機ではこのscheduleにより最大latencyを一斉実行時の66〜70%程度へ抑え、sustainable throughputを8〜11%改善した。条件を変えた評価では13%改善している。

### 5. GPU batch sizeと必要CPU数をprofileから決める

CPUを増やしすぎるとGPU待ちになり、少なすぎるとGPUがCPU待ちになる。そこでFastDecodeは、GPU上のS-Part latencyをbatch sizeごとにmicro-benchmarkし、sequence lengthとR-Part workloadから必要なR-worker数を見積もる。

特にCPU側ではaggregate memory bandwidthを主要resourceとして扱い、latency制約を満たす最大batch sizeと、それを支えられるCPU数を決める。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA A10 24GB ×1 |
| GPU node host memory | 256GB |
| R-worker | 最大4 node、各node dual-socket AMD EPYC |
| Network | InfiniBand |
| Model | Llama-7B / Llama-13B / OPT-175B |
| Precision | FP16、quantization / pruningなし |
| Generated sequence length | 1024 tokens |
| Baseline | vLLM、TensorRT-LLM、FastLLM、vanilla PyTorch Llama |

評価costを下げるためmodelのlayer数を削減した実行も使い、layer数とlatencyがほぼ線形であるという測定に基づいてfull modelのthroughput / latencyを推定している。この点は実測結果を読む際の重要な注意点である。

### Throughput

Llama-7Bでは、vLLMの452 token/sに対しFastDecodeはbatch=1024で2279 token/s。batch=128でも1052 token/sを出している。

Llama-13Bでは、vLLMの350 token/sに対しbatch=1024で1441 token/s、batch=128で660 token/sだった。

論文全体では同一GPUを使うvLLM比 **1.88〜5.04倍**のthroughputを報告している。大batchほどthroughputは高いが、128→1024の8倍batch化でthroughput増加は約2倍に留まり、latencyとのtrade-offがある。

### Latencyとscaling

FastDecode batch=128の平均token latencyはLlama-7Bで120.8ms、13Bで191.6ms。最大throughput設定では小batch設定よりlatencyが約3.5倍になる。

R-workerを1→8 CPU socketへ増やした場合、sequence length 1024では7Bで72.8%、13Bで84.1%のstrong-scaling efficiencyを示す。一方sequence length 128では13Bでも8 socketへのscaling効率が37.6%まで落ち、CPUを増やしすぎるとS-workerがbottleneckになる。

profilingでは、ある13B構成でQ/K/VのGPU→CPU copyに約3ms、network転送に約7.4ms、1 token iteration全体に約43msかかり、distributed feature-vector通信が約25%のoverheadを占めた。

## 既存研究との差

### vLLMとの違い

vLLMはPagedAttentionでGPU memory fragmentationを抑え、必要に応じてKV pageをhost memoryへswapする。FastDecodeはKVをGPUへ戻すのではなく、**attention計算自体をKVのあるCPUへ移す**ため、長いsequenceでのKV swap trafficを避ける。

### FlexGenとの違い

FlexGenはweight・activation・KV cacheをGPU / CPU / SSDへ配置し、主にoffline large-batch throughputを高める。FastDecodeはmodel weightをGPUに残し、KV cacheとattentionだけを分離してdistributed CPUへ置くため、対象となるoffload objectが異なる。

### HeteGenとの違い

HeteGenはlinear weightの一部をCPUで直接計算して**weight転送**を減らす。FastDecodeはlinear / MLPをGPUへ集中させ、CPUは**KV cacheを使うattention計算**を担当する。CPU-GPU協調という点は共通するが、CPUへ移す計算はほぼ逆である。

## 限界

- CPU nodeを複数追加する前提で、単一consumer PC向けのoffload方式ではない。
- network通信はKV転送より小さいものの無視できず、実測ではfeature-vector通信が約25%のiteration overheadを占める構成がある。
- sequenceが短い場合はR-Partが軽く、CPUを増やしてもscaleしにくい。
- throughput最大化には大batchが必要で、per-token latencyとのtrade-offが大きい。
- Llama / OPT評価の一部はlayer数を減らしたmodelからfull model性能を推定している。
- 2026-09-06時点で著者による公式実装の公開は確認できなかった。vLLMへの導入提案もfeature request止まりで、upstream実装にはなっていない。

## 一般的な実装上の含意

FastDecodeは、KV-cache offloadで重要なのは「KVをどこへ保存するか」だけではなく、**KVを毎token読むattention計算をどこで実行するか**だと示している。

CPU memoryへKVを置く場合、毎token KV全体をGPUへ戻すより、Q/K/Vやattention outputのような小さいactivationだけを送り、memory-bound部分をCPU側で処理する方が有利になり得る。また、CPU/GPUを分業させる場合は平均処理量だけでなく、sequence lengthの増加による時間変動をschedulerで平滑化する必要がある。
