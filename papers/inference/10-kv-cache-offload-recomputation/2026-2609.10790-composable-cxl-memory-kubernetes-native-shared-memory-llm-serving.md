# Composable CXL Memory as a Kubernetes-Native Shared Memory for LLM Serving

> 共有CXLメモリをKubernetesの動的資源として割り当て、複数ノードから同じKVキャッシュを再利用して長い接頭辞の初動遅延を5.5〜36.6倍短縮する実現可能性研究。
## 書誌情報
- **著者**: Hongjian Fan, Kevin Zhang, David Habinsky, Sean Dykstra
- **著者・所属**: Seagate Technology, LLC Research Group。
- **公開**: arXiv:2609.10790v1
- **種別**: Preprint
- **対象**: CXL共有メモリ、KVキャッシュ退避、Kubernetes動的資源割当、ノード間接頭辞再利用、メモリ分離
- **実装**: Kubernetesの動的資源割当ドライバ、CXL領域を構成する管理部、各ホストでDAX機器を作る機構、Podへの機器注入、推論基盤向け共有KV格納部を実装して実機評価している。論文はSeagate公式GitHub組織を公開先として示すが、特定の単一リポジトリ名は本文から確定できない。
## 概要
複数ノードで大規模言語モデルを提供すると、GPUメモリやホスト主記憶に置いたKVキャッシュは高速でも別ノードから再利用できない。本研究は、複数ホストへ同時接続できるCXLメモリをKubernetesの動的資源割当（DRA）で要求時に構成し、同じ物理領域を推論基盤（vLLM）と分散推論基盤（llm-d）の共有KVキャッシュ階層として使う。各ホストには同一名の機器として領域を見せ、共有領域内部に占有表、キー表、検査値を置くことで外部の索引サービスを不要にする。2ノード、512GiBの共有CXL、Qwen2.5-7B-Instructによる実機評価では、別ノードからの長い接頭辞再利用で最初のトークンまでの時間を5.5〜36.6倍短縮し、同一ノード再利用との差を1〜4%に抑えた。ただしGPUとCXLの間はホスト主記憶を経由し、実効転送量は装置帯域を大きく下回るため、著者は完成した性能評価ではなく実現可能性の検証と位置付ける。

本研究はCXLメモリを追加の主記憶として固定配置するのではなく、Kubernetesの動的資源割当（DRA）から要求時に生成する共有クラスタ資源へ変換する。各CXL装置に接続された複数ホストを同じ資源の利用先として公開し、要求が割り当てられた時点で領域を構成し、各ホストのDAX機器へ実体化する。さらにKVブロックの占有表、キー表、検査値を共有領域そのものへ置き、別の索引サービスを使わずに複数処理から同じKVブロックを探索できる。

代表結果として、別ノードでの最初のトークンまでの時間は共有CXLから別ノードの処理Bが接頭辞KVを再利用、各条件60測定で再計算のみでは560.7、2223.6、4895.0、11816.9msに対して約2K: 101.6ms、8K: 175.0ms、16K: 224.6ms、32K: 322.6ms。接頭辞が長いほど再計算回避の効果が増え、改善倍率は5.5、12.7、21.8、36.6倍へ拡大する。
## 問題設定
大規模言語モデルの長い接頭辞を再利用するには、容量の大きいKVキャッシュを複数の推論処理から参照できる必要がある。GPUメモリは最も速いが一つのGPUに閉じ、ホスト主記憶も一つのノードに閉じる。RDMAや物体格納型の共有階層はノードを越えられるが、通信網と転送手順を経由する。CXLの構成可能メモリは同じ物理領域を複数ホストへ同時接続できるが、既存研究の多くは領域がすでに作成済みであることを前提とし、Kubernetesが共有性、容量、作成と削除の寿命を管理できない。また別の推論処理が同じKVブロックを見つけるための索引と整合性確認も必要である。
## 新規性
本研究はCXLメモリを追加の主記憶として固定配置するのではなく、Kubernetesの動的資源割当（DRA）から要求時に生成する共有クラスタ資源へ変換する。各CXL装置に接続された複数ホストを同じ資源の利用先として公開し、要求が割り当てられた時点で領域を構成し、各ホストのDAX機器へ実体化する。さらにKVブロックの占有表、キー表、検査値を共有領域そのものへ置き、別の索引サービスを使わずに複数処理から同じKVブロックを探索できる。
## 手法
### 手法のあらまし
制御面では、動的資源割当ドライバがCXL装置ごとの空き容量と、その装置へ接続されたホスト集合をKubernetesへ公開する。利用要求が実際のPodへ結び付くと、複数の制御処理のうち一つだけを所有者として選び、削除途中でも領域を解放できるよう保護情報を付けた後、装置管理部へ領域作成を依頼する。装置管理部は要求容量の領域を構成して複数ポートへ割り当て、各ホスト側の補助処理がDAX機器を作る。同じ割当識別子を全ホストの機器名として使うため、Podは配置先ごとの機器番号を知らなくても同じ物理領域へ接続できる。削除用情報は複数箇所へ残し、制御処理の再起動後も領域を回収できる。

データ面では、推論基盤（vLLM）のKV退避用接続部から共有CXL領域を直接写像する。領域先頭には形式識別子、配置情報、モデル構成を置き、その後にスロット占有表、64ビットのキー表、CRC32検査値、固定長のKVデータ領域を並べる。最初に接続した処理が領域を初期化し、後続処理はモデル、型、ブロック寸法が一致することを確認して参加する。書込み側は原子的な占有表更新で空きスロットを確保し、キーと検査値を公開する。読出し側は占有だけでなくキー一致と検査値まで確認するため、別のキーを誤って命中扱いする問題を避ける。

実際の転送はGPUからCXLへ直接行わない。保存時はGPUからホスト上の一時領域へ移し、そこからCXLへ複写する。読出し時もCXLからホスト一時領域、そこからGPUという二段階で移す。CXL側はDAXとしてページキャッシュを介さず共有物理メモリへアクセスする。通信要求を毎回発行する必要はないが、この二段階複写のため装置の測定帯域を十分に使い切れない。

評価では、同じ長い接頭辞を持つ二つの要求を用意する。最初の要求を処理Aへ送りKVを共有階層へ保存し、二つ目を同じAへ送る条件と別ノードの処理Bへ送る条件を比較する。別ノード条件ではGPU内キャッシュとCPU主記憶への退避は利用できないため、共有CXLだけが命中できる。接頭辞長を約2千、8千、1.6万、3.2万トークンへ変え、キャッシュなし、GPU内、CPU主記憶、共有CXLの四方式を繰り返し測定する。

### 要求時に構成する共有CXL資源
CXL装置を単一ノード専用機器として登録せず、接続された全ホストから利用できる一つの共有資源としてKubernetesへ示す。利用要求が配置された後に所有制御処理を一つ選び、装置管理部へ領域作成を依頼し、各ホストでDAX機器へ実体化する。同じ割当識別子を各ホストの機器名へ使うため、利用側の設定は配置ノードに依存しない。削除時の回収情報も複数箇所へ保存するので、制御処理が途中で再起動しても共有容量を回収できる。これにより、従来は運用者が事前構成していた共有メモリを、通常のクラスタ資源と同じ寿命管理へ組み込む。

### 共有領域内部に置くKV索引
KVブロックの有無を外部データベースへ問い合わせず、共有CXL領域そのものに占有表、キー表、CRC32検査値を置く。ブロックの内容ハッシュから探索開始位置を決め、書込み側は原子的な占有更新でスロットを確保する。読出し側は占有状態だけでなく保存キーと検査値まで確認する。初期版の開発中には占有表だけを見て別ブロックを誤命中させる欠陥が実際にあり、キー表追加によって修正された。未保存キー12,298件で誤命中0、約1.2TBの書込みで検査値不一致0という確認も行い、共有索引の基本的な正しさを評価している。

### ホスト経由のノード間KV再利用
各推論処理は同じCXL領域を共有写像し、別ノードで生成されたKVを通常のメモリ読出しとして取得する。現試作ではGPUとCXLを直接接続せず、保存時はGPUからCPU側一時領域を経てCXLへ、再利用時はCXLからCPU側一時領域を経てGPUへ転送する。このためノードをまたぐ再利用でもネットワーク越しの外部KVサービスへ要求を送る必要がなく、同じ物理共有領域からブロックを引き出せる。別ノード条件ではGPU内キャッシュや各ノード固有のCPU主記憶が利用できないため、この共有階層が再利用経路そのものになる。長い接頭辞では再計算を回避する効果が転送費用を上回り、大きな初動遅延削減につながる。一方、32K条件の実効読出しは5.81GB/sで、27.1GB/sの装置帯域の21%に留まる。著者は一トークン当たりの限界転送でも約3.3倍の余地があると分析しており、GPU直接転送や複写経路の短縮が次の主要改善点になる。

### 全体のデータ／制御の流れ
Kubernetesの制御面が共有CXL領域の作成、複数ホスト接続、Podへの公開、削除時回収を担当する。推論側では各処理が同じ領域を写像し、領域内の索引を通じてKVブロックを共有する。GPU内やCPU内のノード局所階層とは別の共有階層として働くため、要求の処理先が別ノードへ移っても長い接頭辞を再利用できる。
## 評価条件
- **ハードウェア**: 2台の計算ノードを用いる。各ノードはAMD EPYC 9254 24コア、128GB DDR5、NVIDIA L4 24GBを1基搭載する。CXL装置はSeagateのFPGA試作メモリ装置で、CXL 1.1をPCIe Gen5 x16上で2ポート提供し、合計1TiBのDDR4資源のうち512GiBを両ホストへ同時割当する。比較用の通信経路として100GbE ConnectX-6 DxによるRoCEv2直結も備える。
- **ソフトウェア**: Kubernetes v1.35.7、推論基盤（vLLM）v0.23.0、分散推論基盤（llm-d）、Qwen2.5-7B-Instruct bf16を使う。テンソル並列は1。共有CXL格納部は推論基盤のKV退避接続部へ組み込み、Kubernetes側では動的資源割当（DRA）、コンテナ機器インターフェース（CDI）、Redfish経由の装置管理を組み合わせる。
- **比較対象**: 再計算のみ、GPU内接頭辞キャッシュ、CPU主記憶へのKV退避、共有CXLメモリ
各試行では同じ長い接頭辞を持つ二つの要求を作る。最初の要求を処理Aへ送り、生成したKVを対象階層へ保存する。二つ目の要求は同じAへ送る同一ノード条件と、別ノードの処理Bへ送る別ノード条件に分ける。別ノード条件ではBがその接頭辞を一度も処理していないため、GPU内接頭辞キャッシュとCPU主記憶への退避は命中できず、共有CXLだけが別ノードから再利用できる。比較方式は再計算のみ、GPU内接頭辞キャッシュ、32GiBのCPU主記憶KV退避、512GiB共有CXLの4種類。接頭辞長は約2千、8千、1.6万、3.2万トークンで、同一ノード・別ノード、20セッション、3反復を組み合わせ、合計1920組の要求を測る。乱数的なハッシュ差を避けるため両処理のPYTHONHASHSEEDを0へ固定し、退避単位は256トークンとする。主指標は利用者から見た最初のトークンまでの時間と外部KV命中率である。方式順序は反復ごとに変更し、共有領域も毎回初期化する。さらに未保存キーの誤命中、最初の要求への命中漏れ、領域初期化の記録を検査する。
実際の2ノードCXL装置、L4 GPU、推論基盤を用いる実機評価であり、シミュレーションではない。ただし著者は第1版の実現可能性調査と明記している。プリフィルとデコードを分離した構成ではなく、両処理が完全な推論エンジンを持つ。単一GPU/ノードかつ同時負荷なしなので、有効スループット、混雑時の尾部遅延、プリフィルとデコードの競合は測っていない。RDMAを使う共有KV方式、GPUからCXLへの直接DMA、複数利用者での容量競合も比較対象外である。
## 主要結果
共有CXL階層だけが別ノードで長い接頭辞のKVを命中させ、GPU内またはCPU主記憶のノード局所キャッシュは処理先が変わると再計算へ戻る。接頭辞が約2千から3.2万トークンへ長くなるにつれ、共有CXLからの読出し時間より再計算時間の増加が大きくなるため、別ノードでの最初のトークンまでの時間は5.5倍から36.6倍まで改善する。外部命中率は256トークン単位の境界から決まる理論上限にほぼ一致し、別ノードと同一ノードの差は1〜4%に収まる。一方、CXL装置自体は27GB/sを超える帯域を示すのに、ホスト主記憶を経由するKV読出し経路は約5.8GB/sであり、転送経路には大きな最適化余地が残る。

- 別ノードでの最初のトークンまでの時間 / 約2K: 101.6ms、8K: 175.0ms、16K: 224.6ms、32K: 322.6ms (比較対象: 再計算のみでは560.7、2223.6、4895.0、11816.9ms; 条件: 共有CXLから別ノードの処理Bが接頭辞KVを再利用、各条件60測定) — 接頭辞が長いほど再計算回避の効果が増え、改善倍率は5.5、12.7、21.8、36.6倍へ拡大する。

- 別ノード外部KV命中率 / 95.4%、98.0%、99.0%、99.5% (比較対象: 256トークン単位の境界から決まる命中上限; 条件: 約2K、8K、16K、32K接頭辞) — 完全な256トークンブロックはほぼすべて再利用され、残る不命中の大半は末尾の部分ブロックで説明できる。

- 共有による追加遅延 / 別ノード/同一ノードの時間比はおおむね1.01〜1.04 (比較対象: 同じ共有CXL階層を同一ノードから再利用; 条件: 同じ接頭辞長で比較) — この試験機では、同じ物理CXL領域を別ノードから読むこと自体の追加費用は小さい。

- 記憶階層の実測特性 / CXLは461〜507ns、27.1〜28.5GB/s (比較対象: ローカルDRAMは111ns、134GB/s、100GbE RoCEv2は1.13μs、12.25GB/s; 条件: 試験機上のメモリ測定) — CXLはローカル主記憶より遅い一方、この構成のRDMA経路より低遅延かつ高帯域の共有階層になる。

- KV読出し経路の実効帯域 / 約5.8GB/s (比較対象: CXL装置の実測帯域は約27GB/s; 条件: CXL→ホスト一時領域→GPUの二段階転送) — 装置帯域の約5分の1しか使えておらず、GPU直接転送などによる数倍規模の改善余地が残る。

- 共有データの整合性 / 約1.2TBの書込みでCRC32不一致0件、未保存キー12,298件で誤命中0件 (比較対象: 共有索引とデータ整合性の検査; 条件: 別ノード再利用試験と専用検査) — 試作環境の測定範囲では、物理データ破損と索引の誤陽性は観測されなかった。

### 負の結果・境界条件
- 現方式は完成した本番向け実装ではない。GPUとCXLの間でホスト主記憶を経由するため、約27GB/sの装置帯域に対して実効読出しは約5.8GB/sに留まる。スロットの追い出し、期限切れ、LRU、背景回収がなく、容量が埋まった後の長時間運用を扱わない。評価は2ノード、単一L4/ノード、一つのモデル、長い接頭辞を意図的に100%再利用する逐次条件に限られ、同時要求、容量圧迫、複数利用者、共有RDMA方式との比較はない。Kubernetes側の空き容量通知にも遅れがあり、近接した複数要求が同じ空き容量を見て構成時に失敗する可能性がある。

### 結果の読み方
重要な点はCXLの生の帯域値だけではなく、同じ物理メモリ領域をクラスタ管理下で複数の推論処理へ渡し、別ノードから実際にKVを再利用できたことである。ノード局所キャッシュは配置変更時に命中を失うのに対し、共有CXLでは同一ノードとの差を数%に抑えて再利用を維持した。ただし最初のトークンまでの大幅改善は、背景負荷がなく長い接頭辞が必ず再利用される条件で測った上限寄りの値であり、本番の有効スループットや混雑時尾部遅延へ直接外挿してはいけない。
## 品質への影響
近似量子化やKV削除を行わずbf16のKVを保存するため、品質を意図的に落とす方式ではない。同一入力10件の比較では6件がバイト単位で一致し、4件は別GPU間のbf16丸め差により最大1 ULPだけ異なった。CRC32不一致はなく、著者はこの差を共有メモリ破損ではなく浮動小数点演算の再現性差として扱う。
## 既存研究との差
既存の外部KVキャッシュはDRAM、SSD、RDMA等を組み合わせて大容量化するが、本研究は複数ホストへ同時写像されるCXLメモリを共有階層にする。既存のCXL向けKV研究に対しては、共有領域があらかじめ存在するという前提を外し、Kubernetesの動的資源割当で要求時の領域作成、複数ノードへの接続、Podへの公開、削除時の回収まで扱う点が主な差である。またKV索引を共有メモリ内部へ置くため、外部の索引サービスや遠隔検索要求を使わず、別ノードの推論処理が同じ領域を直接調べられる。
## 限界
著者自身が第1版の実現可能性調査と位置付けている。プリフィルとデコードを分離した構成ではなく、両処理が完全な推論エンジンを持つ。2ノード、単一NVIDIA L4/ノード、逐次実行という条件なので、有効スループット、待ち行列混雑時の尾部遅延、プリフィルとデコードの競合は評価していない。RDMAを用いる共有KV方式、GPUからCXLへの直接DMA、複数利用者での資源競合、容量圧迫時の追い出しも未評価である。現実装はホスト主記憶経由で約5.8GB/sしか出ず、CXL装置の約27GB/sを十分使えていない。スロットの再利用管理も簡素で、長時間運用に必要な期限切れや回収機構が残る。
## 実装状態
Kubernetesの動的資源割当ドライバ、CXL装置管理部、ホスト側DAX実体化、コンテナ機器注入、推論基盤向け共有KV格納部を実装し、Seagate試作CXL装置でエンドツーエンド評価している。論文はSeagate公式GitHub組織を公開先として示すが、本文から特定の単一リポジトリ名を一意に確定できないため、公開実装の入口として組織URLのみ記録する。
## 研究上の位置づけ
KVキャッシュ退避・階層メモリとCXLメモリ分離の交点に位置する。単一ノードの容量拡張だけでなく、要求の配置先が変わっても接頭辞KVを再利用できる共有クラスタ階層を実証した点が重要である。SSDやNVMeは容量単価で有利だが通常は同じ物理領域を複数ホストから通常のメモリ読出しとして扱えない。CXLはより高速で共有性を持つ一方、容量と費用に制約がある。将来のGPU、DRAM、CXL、NVMeを組み合わせた多階層KV管理では、複数ノードで頻繁に再利用する高温度の接頭辞をCXLへ、低頻度で大容量なデータをNVMeへ置く中間階層として接続しやすい。
