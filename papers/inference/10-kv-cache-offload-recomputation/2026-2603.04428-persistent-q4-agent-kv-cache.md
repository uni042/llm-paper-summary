# Agent Memory Below the Prompt: Persistent Q4 KV Cache for Multi-Agent LLM Inference on Edge Devices

> 複数エージェントのKVをQ4ブロックとしてSSDへ永続化し、再プリフィルせず注意機構へ直接復元することで、固定KV容量あたり約4倍の文脈を保持し先頭トークン遅延を最大136倍短縮する。
## 書誌情報
- **著者**: Yakov Pyotr Shkolnikov
- **著者・所属**: 独立研究者
- **公開**: arXiv:2603.04428v1

- **対象**: KVキャッシュ永続化、Q4量子化、SSDオフロード、複数エージェント、Apple Silicon、階層メモリ
- **実装**: 著者公開のMITライセンス実装agent-メモリがあり、MLX向けOpenAI互換API、エージェント別256トークンブロック、Q4 safetensors保存、BatchQuantizedKVCache、ベンチマークを含む。
## 概要
本研究は、エッジ端末上で複数の大規模言語モデル（LLM）エージェントを切り替えると、各エージェントのKVキャッシュが統合メモリを圧迫し、追い出し・切替・再起動後に長いプリフィルを再計算する問題を扱う。Apple M4 ProではGemma 3 12Bの8K文脈をFP16で保持すると、約10.2GBのKV予算に3エージェントしか収まらない。提案系はエージェントごとのKVを256トークン単位の独立ブロックへ分け、4ビット量子化（Q4）のままsafetensorsへSSD永続化し、再利用時にはプロンプト全体を再入力せず注意機構へ直接復元する。量子化KVを複数エージェントでまとめるBatchQuantizedKVCache、プリフィルとデコードを交互実行する協調スケジューラ、フェーズ間で既存KVへ追記する文脈注入も統合する。Gemma 3 12B、DeepSeek-Coder-V2-Lite 16B、Llama 3.1 8BをM4 Proで評価し、固定KV容量あたり概ね4倍の文脈を保持し、復元による先頭トークン遅延を最大136倍短縮する。

KV量子化、ディスク永続化、バッチ推論自体は個別には既存技術である。本方式の特徴は、それらをエージェント単位の独立KV名前空間、Q4のまま保存・読込・注意計算する一貫経路、複数量子化KVを同一前向き計算へ結合するバッチ機構、会話フェーズ間の単調なKV拡張として統合し、固定メモリのApple Silicon上で注意状態の仮想メモリとして動かす点にある。SSDへ退避したKVを再計算用の入力履歴ではなく、注意層が直接利用できる実行状態として復元することで、文脈長に比例するプリフィル計算をI/O中心の復元へ置換する。

代表結果として、Gemma 3 12Bの4K先頭トークン遅延はM4 Pro、バッチ=1、streaming、64出力トークン、6回中央値でKVなしの全プリフィルに対してcold 15,736 ms → warm SSD 577 ms / hot メモリ 719 ms。永続KVを直接復元すると約27倍のSSD復元高速化となり、長いプリフィルをサブ秒級I/Oへ置換できる。
## 問題設定
複数エージェント型の大規模言語モデル（LLM）では、各エージェントが独立した会話履歴と注意状態を持つため、エージェント数と文脈長に比例してKVキャッシュ容量が増える。24GB統合メモリのM4 Proでは、モデル重みとOS等を除くとKVへ約10.2GBしか残らず、Gemma 3 12Bの8K文脈をFP16で保持できるのは3エージェント程度である。容量超過時にKVを捨てる方式では、再びそのエージェントへ戻るたびに全入力をプリフィルし直す必要があり、Gemmaの4Kで15.7秒、32Kで172秒に達する。エッジ端末ではデータセンターGPUよりプリフィルが遅いため、単なるキャッシュ追い出しが対話遅延へ直結し、サーバ再起動でも同じ状態が失われる。
## 新規性
KV量子化、ディスク永続化、バッチ推論自体は個別には既存技術である。本方式の特徴は、それらをエージェント単位の独立KV名前空間、Q4のまま保存・読込・注意計算する一貫経路、複数量子化KVを同一前向き計算へ結合するバッチ機構、会話フェーズ間の単調なKV拡張として統合し、固定メモリのApple Silicon上で注意状態の仮想メモリとして動かす点にある。SSDへ退避したKVを再計算用の入力履歴ではなく、注意層が直接利用できる実行状態として復元することで、文脈長に比例するプリフィル計算をI/O中心の復元へ置換する。
## 手法
### 手法のあらまし
要求受信から保存までの経路は次のように構成される。まずOpenAI互換APIがエージェントID、新しいプロンプト、生成設定を受け、エージェントIDに対応するメタデータ、保存済みプロンプト文字列、SSD上のKVブロックの有無を確認する。保存状態がある場合は、新プロンプトを生文字列で比較し、完全一致、保存済み文字列への追記、十分な共通接頭辞を持たない分岐の三つへ分類する。完全一致なら保存済み範囲のプリフィルを全て省略し、追記なら保存位置までのQ4 KVを復元して新しい末尾だけをモデルへ通す。分岐が大きい場合は誤った位置表現を使わないよう通常プリフィルへ戻る。KV本体は各エージェント専用の256トークン固定ブロックへ分割し、モデル層ごとにキーと値を4ビット量子化値、および復号に必要なbfloat16のスケール・バイアスとして保持する。ブロックはsafetensorsへ直列化してSSDへ書き出され、復元時には必要なブロックだけを読み込む。モデルごとにKVヘッド数や次元が異なるため、ModelCacheSpecがGemma/LlamaのGQA、DeepSeekのMLA、Gemmaの滑動窓注意などのレイアウト差を吸収する。複数エージェントが同時に実行可能な場合、BatchQuantizedKVCacheが系列長の短いKVへ左側パディングを加え、量子化状態のまま一つのバッチへ結合する。プリフィルは既定512トークンのチャンク単位で交互に進め、デコードも各反復で実行可能エージェントをまとめて前向き計算へ渡す。計算で増えたKVは再びエージェント単位へ分割し、パディングを除いて各専用ブロックへ戻す。MLXは複数スレッドから同時に評価すると不安定なため、モデル実行は単一スケジューラスレッドで協調的に時分割する一方、次に利用しそうなエージェントのSSD読込を別エージェントの生成中へ重ね、I/O待ちを隠す余地を作る。要求終了時には更新されたプロンプト文字列、ブロック境界、Q4 KVを対応付けて永続保存する。多段会話では前フェーズの文字列をそのまま接頭辞として残し、新情報を末尾へ追記するテンプレートを使うため、次フェーズでも差分プリフィルが成立する。このように、受信→接頭辞判定→SSD復元→差分プリフィル→量子化KVバッチ→デコード→再分離→永続保存を一つの連続経路として構成し、SSDを単なるバックアップではなく注意状態の下位メモリ階層として利用する。

### エージェント分離型の永続ブロックプール
KVキャッシュを256トークン固定ブロックへ分割し、エージェントIDごとの独立名前空間で管理する。各層のブロックはQ4に詰めた値とbfloat16のスケール・バイアスを持ち、safetensorsとしてSSDへ保存する。エージェントごとのファイルを分離するため、切替、サーバ再起動、端末再起動後にも対象エージェントだけを復元でき、別エージェントの注意状態を誤って共有しない。ModelCacheSpecが層数、KVヘッド数、K/V次元、量子化形式を抽象化し、GQAとMLAのレイアウト差をブロック管理の下へ隠す。メモリが逼迫したときは低活動エージェントをSSDへ追い出し、活発な作業集合だけを統合メモリへ残せるため、統合メモリを高速層、SSDを永続層とする仮想KVメモリとして機能する。

### 保存から注意計算まで一貫したQ4 KV
KVは保存時だけ圧縮して利用時に毎回FP16へ全面展開するのではなく、ディスク、統合メモリ、注意計算の経路でQ4表現を維持し、mlx-lmの量子化注意演算へ直接渡す。量子化群サイズ64ではFP16に対する理論保存比が約0.281となり、各層で約72%の容量を削減する。Gemma 3 12Bでは4K文脈の保持数が固定10.2GB予算で6から24、8Kで3から12、16Kで1から6へ増え、32KではFP16が一つも保持できない条件でもQ4なら3文脈を保持できる。容量削減はRAM常駐率を高めるだけでなく、SSDへ退避した場合の読込量も同時に減らす。追加コストは量子化誤差と量子化注意カーネルの処理であり、品質影響を別途困惑度で測定する。

### 接頭辞照合と差分プリフィル
保存状態と新要求の対応を確認する際、トークンID列だけに依存するとBPEの境界変化で同じ文字列部分が異なる分割になる可能性があるため、生のプロンプト文字列を使って一致関係を判定する。完全一致なら保存KV全体を直接復元し、保存プロンプトが新プロンプトの先頭に一致する追記なら既存KVを復元して新しい末尾だけをプリフィルする。共通接頭辞が十分でない分岐では安全のため再利用しない。複数フェーズの会話テンプレートは過去文脈を書き換えず新しい情報を末尾へ追加する形を保つので、この追記判定が成立しやすい。これにより、フェーズが進むほど長くなる履歴の再計算を避けながら、誤った位置へ古いKVを接続する危険を抑える。

### 量子化KVのバッチ化と協調スケジューリング
複数エージェントのQ4 KVを同じ前向き計算へ投入するため、短い系列を左埋めしてバッチ軸へ結合し、量子化注意を実行して新KVを追記した後、各エージェントへ再分割して埋め部分を除く仕組みを実装する。プリフィルは既定512トークンのチャンクへ分け、複数エージェントを交互に進めた後、デコードも反復単位で交互実行する。MLXは複数スレッドからの同時評価が安定しないため、推論は単一スケジューラスレッド上の協調的な時分割とする。一方、別エージェントが生成中に次のSSDキャッシュを読み込むことでI/O待ちを計算の背後へ隠す余地を作る。真の並列デコードではない点を明確にしつつ、複数休止エージェントの復帰を実サービス経路へ統合する。

### 会話フェーズをまたぐKV作業記憶
交渉や討論のような複数フェーズ処理では、各フェーズ終了時のKVを永続化し、次フェーズのプロンプトを以前の文字列を接頭辞として含む単調増加形に組み立てる。復元したKVへ新フェーズのトークンだけを追加することで、長い履歴全体をフェーズごとに再入力せず、注意状態そのものを作業記憶として継承する。保存文字列の途中を書き換えると再利用範囲が失われるため、性能はプロンプト構造が追記型であることに依存する。この制約を運用規約として明示することで、永続化を単なる休止・再開から、長時間の複数エージェント協調へ拡張する。実験では5フェーズ会話でも総実行時間の削減が残り、単一復元だけでなくワークフロー全体で再利用利益が累積する。

### 全体のデータ／制御の流れ
ModelCacheSpecがモデル依存レイアウトを吸収し、Gemma 3のGQAと滑動窓注意、Llama 3.1のGQA、DeepSeek-Coder-V2-LiteのMLAを同じブロックプールへ載せる。上位層はエージェント状態の保存・復元、量子化KVバッチ、OpenAI互換APIを共通化し、統合メモリを作業集合、内部SSDを永続階層として扱う。
## 評価条件
- **ハードウェア**: 主要実験はApple MacBook Pro M4 Pro（MX2E3LL/A、24GB統合LPDDR5X、273GB/s）1台で実施する。論文は内部NVMeを最大約7GB/sとし、モデル重み6.8GBとOS等約7GBを差し引いた約10.2GBをKV予算として容量計算する。離散GPUや複数GPUは実測していない。
- **ソフトウェア**: Apple MLX / mlx-lm上の公開実装agent-メモリを使用する。Q4 KVはsafetensorsへ保存し、mlx-lmの量子化注意演算を利用する。量子化KVのバッチ処理用にBatchQuantizedKVCacheを追加し、推論は単一スケジューラスレッドで時分割する。比較対象にはvllm-mlxのFP16接頭辞キャッシュを含む。
- **モデル**: Gemma 3 12B Instruct、DeepSeek-Coder-V2-Lite 16B Instruct、Llama 3.1 8B Instruct
- **データセット／トレース**: 約37.7KトークンのWikipedia由来長文脈、WikiText-2、5フェーズの囚人のジレンマ型会話、10専門エージェントのWikipedia質問
- **比較対象**: KVなしの全プリフィル、RAM内hot キャッシュ、SSD warm restore、vllm-mlx FP16 prefix キャッシュ
- **正確性・品質**: SSD永続化そのものは同じKV状態の復元を狙うが、Q4量子化は近似である。品質はFP16 KVとのWikiText-2困惑度比較で測り、Gemma -0.7%、DeepSeek +3.0%、Llama +2.8%を報告する。
- **TTFT評価**: 文脈長1K〜32K、温度0、出力64トークン、ストリーミング要求で、KVなしの再プリフィル、SSDからのQ4復元、メモリ常駐復元を比較する。各設定を原則6回実行し中央値を用いる。
- **同時処理評価**: 2エージェントの非ストリーミング条件でシステム全体の生成トークン毎秒を測り、復元済みKVによるプリフィル削減が複数要求でも残るか確認する。
- **再起動比較**: Llama 3.1 8Bでvllm-mlxのFP16接頭辞キャッシュと比較し、プロセス再起動後にもSSD永続KVが再プリフィルを避けられるかを各3回中央値で測る。
- **品質とワークフロー**: WikiText-2を512トークン窓・256ストライドでQ4/FP16比較し、加えて5フェーズ4エージェント会話と10専門エージェントルーティングで実ワークフローの総時間と復元遅延を測る。
Gemma 394、DeepSeek 378、Llama 360の計1,132測定に加え、36件のずらし到着試験を行う。文脈長を1K〜32Kへ変え、冷状態の再プリフィル、SSD復元、統合メモリ常駐復元を比較する。容量評価ではFP16とQ4の理論・実容量を約10.2GBのKV予算へ当てはめる。復元利益だけでなく生成速度、同時処理率、再起動耐性、複数フェーズ処理、困惑度まで測り、SSD永続化が有利な条件と不利な条件を分けている。
全主要結果は単一M4 Proであり、PCIe接続GPU、複数GPU、ネットワークストレージへそのまま外挿できない。TTFT主要表は単一要求・固定64出力トークンでプリフィル比率が高い。品質評価は短いWikiText-2窓中心で、長文での累積量子化誤差、事実精度、長期作業記憶品質を直接測らない。
## 主要結果
キャッシュ未使用の先頭トークン遅延は文脈長にほぼ比例して増える一方、SSDからのQ4復元と統合メモリ常駐復元は長文でも大幅に短い。Gemmaは4Kで15,736msからSSD復元577ms、32Kで172,096msから1,819msへ縮み、メモリ常駐32Kでは1,264msで最大約136倍となる。Llamaは16Kで47,629msからSSD431msへ縮み111倍、DeepSeekは32Kで47,315msからSSD633msへ縮み約75倍である。Q4容量削減はGemmaの固定KV予算で概ね4倍のエージェント文脈を許す。ただし単発の冷開始では提案系のオーケストレーション負荷が残り、価値は再利用、切替、再起動がある条件で最大化する。

- Gemma 3 12Bの4K先頭トークン遅延 / cold 15,736 ms → warm SSD 577 ms / hot メモリ 719 ms (比較対象: KVなしの全プリフィル; 条件: M4 Pro、バッチ=1、streaming、64出力トークン、6回中央値) — 永続KVを直接復元すると約27倍のSSD復元高速化となり、長いプリフィルをサブ秒級I/Oへ置換できる。

- 最大先頭トークン遅延高速化 / Gemma最大136倍、DeepSeek最大約76倍、Llama最大111倍 (比較対象: 各文脈長のcold プリフィル; 条件: Gemma/DeepSeekは最大32K、Llamaは最大16K) — 再プリフィル側だけが文脈長に比例して伸びるため、長文ほど復元経路の相対利益が拡大する。

- 固定KV予算で保持できるGemmaエージェント数 / 4K: 6→24、8K: 3→12、16K: 1→6、32K: 0→3 (比較対象: FP16 KV; 条件: M4 ProでKV予算10.2GB、Q4理論比0.281) — Q4により1文脈のKVが約72%小さくなり、複数エージェントを追い出さず保持できる範囲が大きく広がる。

- 2エージェントwarmシステム処理率 / 1K: Gemma 22.6 / DeepSeek 63.0 / Llama 37.8 tok/s、4K: 19.6 / 52.6 / 34.5、16K: 11.9 / 27.9 / 26.1 (比較対象: 同条件coldでは1K 10.4/35.5/16.6、4K 3.5/13.5/5.9、16K 0.8/3.1/1.3 tok/s; 条件: バッチ=2、non-streaming、6回中央値) — 復元済みKVではプリフィルが消えるため、同時処理時も生成側の計算が支配的になり総処理率が大きく上がる。

- vllm-mlxとの再起動耐性 / agent-メモリはLlama 1K〜16Kでwarmとrestartが同じ260〜431ms (比較対象: vllm-mlx FP16 prefixは再起動後1K 2,262ms、2K 4,134ms、4K 8,079ms; 条件: Llama 3.1 8B、各3回中央値) — 揮発性接頭辞キャッシュに対し、ディスク永続化はプロセス再起動後にも再プリフィルを避ける。

- 5フェーズ作業の総時間 / Gemma 72.9s→56.1s（23%減）、DeepSeek 33.6s→27.8s（17%減） (比較対象: 各フェーズで文脈を再計算; 条件: 囚人のジレンマ型5フェーズ会話) — 単一復元の大きな倍率がそのまま全処理倍率にはならないが、フェーズ間KV継承でも実時間短縮が残る。

- Q4 KVの困惑度変化 / Gemma -0.7%、DeepSeek +3.0%、Llama +2.8% (比較対象: FP16 KV; 条件: ローカルWikiText-2 7,935トークン、512窓・256ストライド) — 短い評価窓ではQ4誤差は小さいが、長文や層別感度を保証する結果ではない。

### 負の結果・境界条件
- 冷状態の単発要求では提案実装のオーケストレーション負荷が残り、Llama 4Kでagent-メモリ 10,235msに対しvllm-mlx 4,394msなど再利用しない要求では不利である。生成速度も提案経路は概ね39〜46 tok/sでvllm-mlxの49〜55 tok/sより低い。短文脈では統合メモリ常駐の復元がSSD復元より遅い条件もあり、ブロックプールの層別探索・検査・散在アクセスが小ファイルの順次SSD読込より高コストになる。2エージェントのずらし到着実験では総壁時計時間は逐次実行とほぼ同じで、理論的なI/O隠蔽が大きな全体高速化としては示されていない。

### 結果の読み方
主要利益は計算器そのものを高速化することではなく、一度計算した注意状態をSSDへ保持し、後で計算結果そのものを復元することである。したがって再利用率が高く、エージェント切替や再起動が多く、文脈が長いほど有利になる。Q4で容量も縮めるため、追い出し頻度を下げる効果と、追い出した場合の復元I/Oを減らす効果が同時に働く。逆に一度しか使わない要求、短文脈、長いデコードが支配する要求では追加実装負荷や生成速度差が目立つ。
## 品質への影響
Q4 KVは短いWikiText-2窓でGemma -0.7%、Llama +2.8%、DeepSeek +3.0%の困惑度差を示す。Gemmaの改善は測定雑音の可能性があり、信頼区間、長文での誤差蓄積、層ごとの量子化感度は評価していない。永続化自体は同じKV状態の復元を目的とし、品質変化は主に量子化に由来する。
## 既存研究との差
vLLMやSGLangは主にGPU/CPUメモリ上でページや共有接頭辞を再利用するが、再起動や容量超過後のSSD永続復元を主目的にしない。vllm-mlxはApple SiliconでFP16接頭辞キャッシュと連続バッチ処理を提供するがディスクへ永続化しない。llama.cppにはスロット保存・復元や量子化機構があるものの、本方式は自動的な複数エージェント用ブロックプール、量子化KVのバッチ実行、フェーズ間作業記憶を一つの運用経路へ統合する。LMCacheのような階層KV技術とは対象が近いが、本研究は固定統合メモリのエッジ端末、エージェント分離、再起動耐性へ焦点を置く。
## 限界
評価はApple M4 Pro 24GBの1台だけで、複数GPU、PCIe接続の離散GPU、ネットワーク共有ストレージ、複数端末間のKV転送を実測していない。3モデルまでで70B級以上は未評価である。Q4品質は512トークン窓に限られ、長文での累積誤差、層別感度、信頼区間がない。出力を64トークンへ固定した主要TTFT評価はプリフィル比率が高く、長い生成では全体高速化率が小さくなる。MLXのスレッド非安全性から推論は単一スケジューラスレッドの時分割であり、CPU/GPUをまたぐ真の並列エージェント実行ではない。KVはモデルと量子化方式に依存するためモデル更新で無効化される。SSD書込み耐久性、暗号化、破損回復など長期運用の論点も主要評価外である。
## 実装状態
著者公開の `yshk-mxim/agent-メモリ` が存在し、MITライセンスでOpenAI互換API、永続Q4 safetensors、ブロックプール、量子化KVバッチ、ベンチマーク群を含む。論文は同実装を用いて1,132件の主要測定と36件のずらし到着試験を行っている。MLX/Apple Silicon向けの具体的な実装であり、CUDA環境へそのまま移植できるとは確認されていない。
## 研究上の位置づけ
本研究はKVキャッシュ圧縮だけでなく、SSDを注意状態の永続階層として使うエッジ推論システムに位置づく。階層メモリ研究の観点では、GPUまたは統合メモリ上のKVを捨てるか保持するかの二択ではなく、エージェントIDとプロンプト接頭辞を鍵にSSDへページアウトし、再プリフィルという計算を避けて戻す具体例である。特にQ4へ統一することでI/O量と容量を同時に削減し、順次SSD読込が一部の短文脈で散在メモリアクセスより速いという実測も示す。一方、専用I/Oスケジューリング、完全非同期プリフェッチ、SSD帯域共有、将来アクセス予測は未発展であり、既存の階層KV・プリフェッチ研究を組み合わせる余地が大きい。
