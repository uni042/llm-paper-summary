# SwiftCache: Efficient LLM Serving for Multi-turn Conversations with Heterogeneous KV Cache Sharing

> SwiftCacheの発想は、CPUやSSDへKV cacheを逃がす前に、**同じserver内で別modelが使っていないGPU memoryを借りられないか**というものだ。長い会話を処理するmodelを主モデル（master）、KV需要が小さいmodelを作業モデル（worker）として、workerの空きHBMへmasterのprefix KVを保存する。GPU間はNVLinkで直接つながっているため、CPU memoryからPCIe経由でKVを戻すより高速に再利用できる。さらにmaster自身には全layerのKVを置かず、現在計算しているlayer分だけをstreamすることで、local HBMのcontext容量も増やす。

## まずmulti-turn conversationで何が起きるのか

LLMには会話を永続的に覚える内部memoryがあるわけではない。通常のchat serviceではturnが増えるたび、過去のuser/assistant messageを新しいpromptのprefixとして再びmodelへ渡す。

例えば

- turn 1: 2K token
- turn 2まで: 4K token
- turn 10まで: 30K token

のようにconversation historyは累積する。

毎turnすべてをprefillし直すのは無駄なので、過去prefixについて一度計算したKey/Valueを**prefix KV cache**として保存する。

次turnでは

`過去historyのKVをreuse + 新しく追加されたtokenだけprefill`

すればよい。

このprefix reuseはmulti-turn workloadで非常に有効だが、historyが長くなるほど保存すべきKVも大きくなる。

## なぜCPU/SSD offloadではTTFTが悪化するのか

GPU HBMに入りきらないKVはCPU DRAMやSSDへ退避できる。

しかし次turnでそのprefixをreuseするには、attention計算前にKVをGPUへ戻す必要がある。

一般的なGPU serverではCPU↔GPU pathはPCIeを通る。論文のmotivation環境では

- PCIe 4.0: peak 約32 GB/s
- NVLink: peak 約400 GB/s

という大きな帯域差がある。

LWM-1M-Textを2×96GB H20で測る例では、historical tokenが5K程度の時点でPCIe KV loadは約75 ms、new-token computationは約27 msで、すでにtransferの方が重い。historyを50Kまで増やすとtransfer overhead比率は約73.2%から86.2%へ上がる。

つまりmulti-turnでは、新しいuser input自体は短いのに、**昔のKVを戻す時間だけがturnごとに増えて最初のtokenまでの時間（Time To First Token: TTFT）を支配する**。

## もう一つの問題: modelが1M context対応でもHBMに入るとは限らない

model specification上の最大context windowと、実hardwareで実際に保持できるKV量は別問題である。

論文ではLWM-1M-Textはmodelとして1M-token contextを持つが、KV memory制約により

- 32GB V100: 約18K token
- 96GB H20: 約160K token

程度しか実行できない例を示す。

つまり「1M context対応model」を買っても、HBM容量が足りなければそのcontextを使えない。

SwiftCacheは

1. KV reloadを速くする
2. master GPUに常駐させるKV量を減らす

の2つを同時に狙う。

# 観測1: modelごとにprefix cache需要が全く違う

同じserverで複数modelをserveしていても、すべてが長いchat workloadを処理するわけではない。

論文のprofilingではprefix cache hit率に大きな差がある。

| Workload | Prefix cache hit rate | 傾向 |
|---|---:|---|
| Summarization | 6.3% | cache需要が低い |
| Code Completion | 0.1% | cache需要が非常に低い |
| Multi-turn Conversation | 90.7% | cache需要が高い |
| Question Answering | 81.8% | cache需要が高い |

multi-turn modelは大量KVを保持したい一方、code completion modelのGPUではprefix KV用領域が余る可能性がある。

従来は各modelが自分のGPU memoryだけを管理するため、この空きHBMは他modelから使えない。

SwiftCacheはこの**model間のmemory需要非対称性**を利用する。

# 観測2: 異なるmodel間のNVLinkも余っている

Tensor Parallelismなどでは同じmodelを構成するGPU同士は頻繁に通信する。

一方、GPU 0でQwen3-32B、GPU 1でQwen3-8Bのように別modelを動かす場合、両modelは通常独立しており、GPU間NVLinkをほとんど使わない。

したがってserver全体を見ると

- worker GPU: HBMが余る
- master-worker間NVLink: bandwidthが余る
- master GPU: KV memoryが不足

という組合せが生まれる。

SwiftCacheはworkerの余剰HBMをmasterの外部KV tierとして使い、そのdataをNVLinkで直接運ぶ。

CPUを経由しないためPCIe bottleneckも避けられる。

# Master / Worker構成

KV需要の大きいmodelを**master**、小さいmodelを**worker**と呼ぶ。

workerは自分のrequestを普通にserveしながら、使っていないKV-cache blockの一部をmasterへ貸す。

masterのprefix KVは

- master local HBM
- worker GPU HBM

のどちらかに存在する。

workerへ置いたKVを使うrequestが来たら、必要なlayer分をNVLinkでmasterへstreamする。

ここで単純に「全layer KVをworkerからmasterへまとめてコピー」すると、結局master側にも巨大なbufferが必要になる。そこで**層ストリームキャッシュ（Layer Stream Cache: LSC）**を使う。

# 層ストリームキャッシュ（Layer Stream Cache: LSC）

Transformerはlayer 1、layer 2、...と順番に実行する。

layer iのattentionが読むのはlayer i用のKVだけであり、同じ瞬間に全layerのKVを読むわけではない。

従来systemは全layer分をlocal HBMへ常駐させるが、SwiftCacheは

`今使うlayerのKVだけlocalへ置く`

設計へ変える。

## 例: 3 layerならなぜcapacityが増えるのか

極端に単純化し、local HBMが各layerについて10K token分のKVを持てるとする。

通常は

- layer 1: 10K
- layer 2: 10K
- layer 3: 10K

と全layer分を同時保持するため、最大sequenceは10K tokenになる。

他2 layerのKVをworker側へ置き、masterでは現在layer分だけを入れ替えるなら、同じlocal KV memoryを1 layer用bufferとして再利用できる。

理想的には30K token分の1-layer KVを一度に置けるため、最大context長を伸ばせる。

実modelはlayer数もmemory allocationももっと複雑だが、原理はこれである。

## 通常キャッシュ（Regular Cache: RC）も残す

すべてのKVをworkerへ置く必要はない。

masterに余ったlocal HBMがあれば、full-layer KV blockを**通常キャッシュ（Regular Cache: RC）**として保持する。

RC hitならNVLink transferすら不要なので最速である。

したがってmaster側は

- RC: localに完全常駐できるhot prefix
- LSC: workerからlayer-wiseにstreamするprefix

の二段構成になる。

# KV blockのmemory量

1 layer・1 blockのKV memoryは概念的に

`M_block = 2 × B × H_kv × D_kv × dtype_bytes`

で決まる。

- `2`: KeyとValue
- `B`: 1 block内token数
- `H_kv`: KV head数
- `D_kv`: 1 headのdimension
- `dtype_bytes`: FP16等のelement size

workerが貸せるmemory量から「masterのfull-layer blockを何個保存できるか」を計算し、その量に応じてLSC capacityを決める。

master local HBMの残りはRCに回す。

このためworker側の空きmemoryが増えるほど、masterはより多くのprefixをpeer GPUへ保存できる。

# 転送を計算の裏へ隠す

NVLinkがPCIeより速くても、layerごとに同期して

`KV load → compute → KV load → compute`

と順番に待てばtransfer latencyは残る。

SwiftCacheはKV load/storeを非同期化し、Transformer layer内の計算と重ねる。

## Load pipeline

layer iを計算している間に、次のlayer i+1用KVをworkerからLSCへ先読みする。

特にlayer iのFFN計算中はlayer i+1のKVをまだ使わないため、NVLink transferを重ねられる。

## Store pipeline

新しいtokenのKVはlayerのQKV projection後に生成される。

生成されたKVは後続computeと並行してworkerへ非同期で書き戻せる。

Qwen3-32Bのlatency breakdownでは、overlap前でもKV load/storeはprefill latencyのそれぞれ約1.4%未満 / 1.1%未満で、pipeline後は有効transfer overheadが0.1%未満まで下がると報告される。

「peer GPUへKVを置くと毎layer network待ちになるのでは」という懸念に対し、NVLink bandwidthとlayer pipelineで大部分を隠す設計になっている。

# Workerはmemoryを貸したら自分のrequestを処理できなくならないか

workerのloadは一定ではない。

今はcode completion requestが少なくmemoryが余っていても、数秒後にはworker自身のtrafficが増えるかもしれない。

そのため貸出量を固定すると、masterのcacheがworkerを圧迫する。

SwiftCacheは**弾性キャッシュ（Elastic Cache）**でworker自身とmasterの間のcapacityを動的に伸縮する。

## 従来の層優先配置（layer-major layout）の問題

一般的なKV layoutを

`(layer, block, block_elements)`

の順に置くと、各layerのblock群が連続する。

この状態で全layerについて1 blockずつ容量を減らすには、layerごとの境界を詰め直すdata movementが必要になる。

頻繁に貸出量を変えるには重い。

## ブロック優先配置（block-major layout）

SwiftCacheはworker cacheを

`(block, layer, block_elements)`

へ並べ替える。

同じlogical blockに属する全layer分を一つの連続単位として持つ。

するとcapacityを1 block増減するときは末尾のblock unitを追加・解放すればよく、既存KVをshiftしなくてよい。

論文では従来のresizeを概ね

`O(n_layers × n_blocks)`

に対し、block-majorではmetadata変更中心の**O(1)** resizeとして扱う。

# 異種modelでblock sizeが違う問題

masterが32B、workerが8Bならlayer数、KV head数、head dimensionが違い、1 KV blockあたりmemory量も違う。

worker blockを1個返しただけではmaster blockがきれいに入らずfragmentationする可能性がある。

そこでSwiftCacheは両modelのblock memory量の最小公倍数から**最小弾性単位（Minimum Elastic Unit: MEU）**を作る。

簡単に言えば、

`master blockもworker blockも端数なしで区切れる最小のmemory chunk`

単位で貸し借りする。

これにより異なるarchitecture間でもmemory alignmentを保ってcapacityをreallocateできる。

# Coordination

master / workerにはそれぞれcache managerとcoordinatorがあり、worker loadが低い時はblockをdonateし、worker需要が増えたらreclaimする。

masterは借りていたKV blockのplacementを追跡し、workerがmemoryを取り戻す際には必要なcacheをevict/再配置して整合性を保つ。

重要なのは、workerを単なる「KV専用GPU」にするのではなく、**worker自身のmodel servingを継続したまま余剰だけを貸す**点である。

# 評価条件

主評価は単一server内の4× NVIDIA H20 96GB構成で行う。

- GPU: 4× H20 96GB
- 高速GPU間接続: NVLink
- Model: Qwen3 family（8B / 14B / 32B等）、LWM-1M-Text
- Workload: ShareGPT、L-Eval
- Baseline: vLLM + LMCache、vLLM + chunked prefill、SGLang + HiCache
- 実装: Python/Triton inference path、C++ scheduler/cache manager、GPU間KV transfer

context-length感度では96GB H20だけでなく80GB、32GB、24GB級GPU条件も比較する。

# 主要結果

## 1. P99 TTFTを最大69%削減

end-to-end multi-turn servingでは、ShareGPT / L-EvalでSGLang + HiCacheに対しP99 TTFTを約67〜69%削減する。

vLLM + LMCacheに対しても約54〜58%低い。

効果の理由は2つある。

1. worker HBMによりprefix cache capacityが増え、CPU/SSD tierへ落ちにくくなる。
2. peer-resident KVを使う場合もPCIeではなくNVLinkでreloadする。

したがって「NVLinkが速い」だけでなく、**低速tierへ落ちるcache miss自体を減らすcapacity効果**も含む。

## 2. 最大context長を最大3.98×へ拡張

8K-token chunked prefillを使うvLLM baselineに対し、GPU HBM容量に応じて約1.58〜3.98×のmaximum context lengthを実現する。

最大headlineの3.98×は、LSCによってmaster local HBMへ全layer KVを同時常駐させなくてよくなった効果である。

これはmodelのarchitectural context window自体を3.98倍に変更したわけではない。

**同じmodelが元から許すcontext windowのうち、HBM不足で使えなかった範囲を実hardware上で使えるようにした**という意味である。

## 3. Workerへの干渉は限定的

masterがworker HBMとNVLinkを借りるため、worker側が完全にfreeというわけではない。

評価ではworkerのTTFT増加は最大約9.7%、TPOT / throughput側の悪化は概ね7%未満の範囲と報告される。

つまりmasterだけを速くしてworkerを大幅に犠牲にしたsystemではないが、zero interferenceでもない。

worker loadが高いときにmemoryをreclaimするelastic controlが重要になる。

## 4. Layer-wise transferはほぼ隠せる

Qwen3-32Bで、99%のrequestについてKV loadは約11 ms未満、storeは約6 ms未満という測定が報告される。

さらにcomputeとのoverlap後は実効transfer overheadがprefill全体の0.1%未満になる。

この結果は、peer GPUをmemory tierとして使う設計が成立するには**link bandwidthだけでなくlayer-level overlapが重要**であることを示す。

# なぜmulti-model serverで特に有効なのか

単一modelだけを全GPUへspreadしているserverでは「別modelのidle HBM」が存在しない。

SwiftCacheの狙いは、複数の異種modelを同居させるproduction serverで

- model A: chatが多くKV-heavy
- model B: short code completion中心でKV-light
- model C: summarization中心でprefix reuseが少ない

という需要差がある状況である。

model単位で固定partitionするとB/Cのunused HBMはAから見えない。

SwiftCacheはmemoryをserver-level poolに近づけ、**model間statistical multiplexingをKV cacheにも適用する**研究と理解できる。

# 既存研究との差

## CPU / SSD KV offload

LMCacheやHiCacheなどはCPU memory、local/remote storageを含む階層cacheを使う。

SwiftCacheはそれらより高速なpeer GPU HBMを追加tierとして使い、同一server内NVLinkを優先する。

## Peer-GPU offload

Aqua等にも別GPUのmemoryを使う発想はあるが、SwiftCacheはmulti-turn prefix reuseへ焦点を当て、

- cross-model idle-HBM donation
- layer stream cache
- local regular cache
- O(1) elastic resize
- heterogeneous-model alignment

を一体化する。

## Chunked prefill

chunked prefillは長いprefillを小さく分けてpeak activation/interferenceを抑えるが、全layer KVを保持する基本memory構造は変わらない。

SwiftCacheはKV自体のresidencyをlayer-wiseに分解するため、最大context lengthへの作用点が異なる。

# 限界

1. **同一server内高速linkが必要**: 主設計はNVLink/NVSwitch前提で、server間networkへそのまま拡張した評価ではない。
2. **idle workerが必要**: 全modelのKV需要が同時に高い場合、貸せるHBMがなくなる。
3. **worker interferenceは0ではない**: memory bandwidthとNVLinkを消費し、TTFT/TPOTに数%程度の悪化が出る。
4. **model placement依存**: どのmodelを同じserverへco-locateするかで利用できるmemoryとlink topologyが変わる。
5. **異種block alignment**: MEUで扱えるが、architecture差が大きいmodel pairでは貸借granularityが粗くなりmemory利用効率が下がる可能性がある。
6. **cache localityの変化**: workerがload増加でmemoryをreclaimするとmaster prefixをevict/移動する必要があり、traffic変動が激しいとcache churnが増える。
7. **official code未確認**: 2026-09-10時点で論文に対応する公式公開repositoryを確認できていない。
8. **対象はlossless capacity/transfer optimization**: KVを圧縮・選択する研究ではないため、peer HBM総容量を超える巨大working setでは最終的にCPU/SSD等の下位tierが依然必要になる。

# 一般的な実装上の示唆

SwiftCacheの重要な視点は、GPU memoryを**model所有の固定resource**ではなく、server内で貸し借りできるresourceとして見ることである。

複数model servingではGPU compute utilizationだけでなく

- HBM free space
- KV cache hit demand
- NVLink/NVSwitch utilization

にもmodel間の非対称性がある。

これを同時にpoolingすれば、追加GPUなしでhot serviceのmemory capacityを増やせる可能性がある。

また、KVのようにlayerごとにしか使わないstateについては、全layerを同時常駐させる必要があるかを再検討できる。

`次layerのstate transfer < 現layerの隠せるcompute時間`

を満たせる高速tierがあるなら、layer streamingで容量を大きく削減できる。

この考え方はpeer HBMだけでなく、将来のCXL memoryや高帯域flash tierでも応用可能だが、tier latencyが長くなるほどprefetch精度とoverlap可能時間が重要になる。
