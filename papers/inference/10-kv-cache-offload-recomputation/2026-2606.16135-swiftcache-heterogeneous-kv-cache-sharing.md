# SwiftCache: Efficient LLM Serving for Multi-turn Conversations with Heterogeneous KV Cache Sharing

> SwiftCacheの発想は、CPUやSSDへKV キャッシュを逃がす前に、**同じserver内で別モデルが使っていないGPU メモリを借りられないか**というものだ。長い会話を処理するモデルを主モデル（マスター）、KV需要が小さいモデルを作業モデル（ワーカー）として、ワーカーの空きHBMへマスターの接頭部 KVを保存する。GPU間はNVLinkで直接つながっているため、CPU メモリからPCIe経由でKVを戻すより高速に再利用できる。さらにマスター自身には全層のKVを置かず、現在計算している層分だけをストリームすることで、ローカル HBMの文脈容量も増やす。

## まずmulti-turn conversationで何が起きるのか

LLMには会話を永続的に覚える内部メモリがあるわけではない。通常の対話 サービスではターンが増えるたび、過去の利用者/assistant messageを新しい入力の接頭部として再びモデルへ渡す。

例えば

- ターン 1: 2K トークン
- ターン 2まで: 4K トークン
- ターン 10まで: 30K トークン

のように会話 履歴は累積する。

毎ターンすべてをプリフィルし直すのは無駄なので、過去接頭部について一度計算した鍵/値を**接頭部 KV キャッシュ**として保存する。

次ターンでは

`過去historyのKVをreuse + 新しく追加されたtokenだけprefill`

すればよい。

この接頭部 再利用は複数ターン ワークロードで非常に有効だが、履歴が長くなるほど保存すべきKVも大きくなる。

## なぜCPU/SSD offloadではTTFTが悪化するのか

GPU HBMに入りきらないKVはCPU DRAMやSSDへ退避できる。

しかし次ターンでその接頭部を再利用するには、注意機構計算前にKVをGPUへ戻す必要がある。

一般的なGPU serverではCPU↔GPU 経路はPCIeを通る。論文のmotivation環境では

- PCIe 4.0: ピーク 約32 GB/s
- NVLink: ピーク 約400 GB/s

という大きな帯域差がある。

LWM-1M-Textを2×96GB H20で測る例では、履歴上 トークンが5K程度の時点でPCIe KV 読み込みは約75 ms、新しい-トークン 計算は約27 msで、すでに転送の方が重い。履歴を50Kまで増やすと転送 オーバーヘッド比率は約73.2%から86.2%へ上がる。

つまり複数ターンでは、新しい利用者 input自体は短いのに、**昔のKVを戻す時間だけがターンごとに増えて最初のトークンまでの時間（Time To 最初 トークン: TTFT）を支配する**。

## もう一つの問題: modelが1M context対応でもHBMに入るとは限らない

モデル specification上の最大文脈 窓と、実ハードウェアで実際に保持できるKV量は別問題である。

論文ではLWM-1M-Textはモデルとして1M-トークン 文脈を持つが、KV メモリ制約により

- 32GB V100: 約18K トークン
- 96GB H20: 約160K トークン

程度しか実行できない例を示す。

つまり「1M 文脈対応モデル」を買っても、HBM容量が足りなければその文脈を使えない。

SwiftCacheは

1. KV 再読み込みを速くする
2. マスター GPUに常駐させるKV量を減らす

の2つを同時に狙う。

# 観測1: modelごとにprefix cache需要が全く違う

同じserverで複数モデルをserveしていても、すべてが長い対話 ワークロードを処理するわけではない。

論文のprofilingでは接頭部 キャッシュ ヒット率に大きな差がある。

| ワークロード | Prefix キャッシュ ヒット 率 | 傾向 |
|---|---:|---|
| Summarization | 6.3% | キャッシュ需要が低い |
| Code Completion | 0.1% | キャッシュ需要が非常に低い |
| Multi-ターン Conversation | 90.7% | キャッシュ需要が高い |
| 質問 Answering | 81.8% | キャッシュ需要が高い |

複数ターン モデルは大量KVを保持したい一方、コード 完了 モデルのGPUでは接頭部 KV用領域が余る可能性がある。

従来は各モデルが自分のGPU メモリだけを管理するため、この空きHBMは他モデルから使えない。

SwiftCacheはこの**モデル間のメモリ需要非対称性**を利用する。

# 観測2: 異なるmodel間のNVLinkも余っている

テンソル Parallelismなどでは同じモデルを構成するGPU同士は頻繁に通信する。

一方、GPU 0でQwen3-32B、GPU 1でQwen3-8Bのように別モデルを動かす場合、両モデルは通常独立しており、GPU間NVLinkをほとんど使わない。

したがってserver全体を見ると

- ワーカー GPU: HBMが余る
- マスター-ワーカー間NVLink: 帯域が余る
- マスター GPU: KV メモリが不足

という組合せが生まれる。

SwiftCacheはワーカーの余剰HBMをマスターの外部KV 階層として使い、そのデータをNVLinkで直接運ぶ。

CPUを経由しないためPCIe ボトルネックも避けられる。

# Master / Worker構成

KV需要の大きいモデルを**マスター**、小さいモデルを**ワーカー**と呼ぶ。

ワーカーは自分のリクエストを普通にserveしながら、使っていないKV-キャッシュ ブロックの一部をマスターへ貸す。

マスターの接頭部 KVは

- マスター ローカル HBM
- ワーカー GPU HBM

のどちらかに存在する。

ワーカーへ置いたKVを使うリクエストが来たら、必要な層分をNVLinkでマスターへストリームする。

ここで単純に「全層 KVをワーカーからマスターへまとめてコピー」すると、結局マスター側にも巨大なバッファが必要になる。そこで**層ストリームキャッシュ（層 ストリーム キャッシュ: LSC）**を使う。

# 層ストリームキャッシュ（Layer Stream Cache: LSC）

Transformerは層 1、層 2、...と順番に実行する。

層 iの注意機構が読むのは層 i用のKVだけであり、同じ瞬間に全層のKVを読むわけではない。

従来システムは全層分をローカル HBMへ常駐させるが、SwiftCacheは

`今使うlayerのKVだけlocalへ置く`

設計へ変える。

## 例: 3 layerならなぜcapacityが増えるのか

極端に単純化し、ローカル HBMが各層について10K トークン分のKVを持てるとする。

通常は

- 層 1: 10K
- 層 2: 10K
- 層 3: 10K

と全層分を同時保持するため、最大sequenceは10K トークンになる。

他2 層のKVをワーカー側へ置き、マスターでは現在層分だけを入れ替えるなら、同じローカル KV メモリを1 層用バッファとして再利用できる。

理想的には30K トークン分の1-層 KVを一度に置けるため、最大文脈長を伸ばせる。

実モデルは層数もメモリ 割当ももっと複雑だが、原理はこれである。

## 通常キャッシュ（Regular Cache: RC）も残す

すべてのKVをワーカーへ置く必要はない。

マスターに余ったローカル HBMがあれば、完全な-層 KV ブロックを**通常キャッシュ（Regular キャッシュ: RC）**として保持する。

RC ヒットならNVLink 転送すら不要なので最速である。

したがってマスター側は

- RC: ローカルに完全常駐できる高温 接頭部
- LSC: ワーカーから層単位にストリームする接頭部

の二段構成になる。

# KV blockのmemory量

1 層・1 ブロックのKV メモリは概念的に

`M_block = 2 × B × H_kv × D_kv × dtype_bytes`

で決まる。

- `2`: 鍵と値
- `B`: 1 ブロック内トークン数
- `H_kv`: KV ヘッド数
- `D_kv`: 1 ヘッドの次元
- `dtype_bytes`: FP16等のelement 大きさ

ワーカーが貸せるメモリ量から「マスターの完全な-層 ブロックを何個保存できるか」を計算し、その量に応じてLSC 容量を決める。

マスター ローカル HBMの残りはRCに回す。

このためワーカー側の空きメモリが増えるほど、マスターはより多くの接頭部をpeer GPUへ保存できる。

# 転送を計算の裏へ隠す

NVLinkがPCIeより速くても、層ごとに同期して

`KV load → compute → KV load → compute`

と順番に待てば転送 遅延は残る。

SwiftCacheはKV 読み込み/保存を非同期化し、Transformer 層内の計算と重ねる。

## Load pipeline

層 iを計算している間に、次の層 i+1用KVをワーカーからLSCへ先読みする。

特に層 iのFFN計算中は層 i+1のKVをまだ使わないため、NVLink 転送を重ねられる。

## Store pipeline

新しいトークンのKVは層のQKV projection後に生成される。

生成されたKVは後続計算と並行してワーカーへ非同期で書き戻せる。

Qwen3-32Bの遅延 breakdownでは、重ね合わせ前でもKV 読み込み/保存はプリフィル 遅延のそれぞれ約1.4%未満 / 1.1%未満で、パイプライン後は有効転送 オーバーヘッドが0.1%未満まで下がると報告される。

「peer GPUへKVを置くと毎層 ネットワーク待ちになるのでは」という懸念に対し、NVLink 帯域と層 パイプラインで大部分を隠す設計になっている。

# Workerはmemoryを貸したら自分のrequestを処理できなくならないか

ワーカーの読み込みは一定ではない。

今はコード 完了 リクエストが少なくメモリが余っていても、数秒後にはワーカー自身の通信量が増えるかもしれない。

そのため貸出量を固定すると、マスターのキャッシュがワーカーを圧迫する。

SwiftCacheは**弾性キャッシュ（Elastic キャッシュ）**でワーカー自身とマスターの間の容量を動的に伸縮する。

## 従来の層優先配置（layer-major layout）の問題

一般的なKV 配置を

`(layer, block, block_elements)`

の順に置くと、各層のブロック群が連続する。

この状態で全層について1 ブロックずつ容量を減らすには、層ごとの境界を詰め直すデータ movementが必要になる。

頻繁に貸出量を変えるには重い。

## ブロック優先配置（block-major layout）

SwiftCacheはワーカー キャッシュを

`(block, layer, block_elements)`

へ並べ替える。

同じ論理 ブロックに属する全層分を一つの連続単位として持つ。

すると容量を1 ブロック増減するときは末尾のブロック 単位を追加・解放すればよく、既存KVをshiftしなくてよい。

論文では従来のサイズ変更を概ね

`O(n_layers × n_blocks)`

に対し、ブロック-主要ではメタデータ変更中心の**O(1)** サイズ変更として扱う。

# 異種modelでblock sizeが違う問題

マスターが32B、ワーカーが8Bなら層数、KV ヘッド数、ヘッド 次元が違い、1 KV ブロックあたりメモリ量も違う。

ワーカー ブロックを1個返しただけではマスター ブロックがきれいに入らずfragmentationする可能性がある。

そこでSwiftCacheは両モデルのブロック メモリ量の最小公倍数から**最小弾性単位（Minimum Elastic Unit: MEU）**を作る。

簡単に言えば、

`master blockもworker blockも端数なしで区切れる最小のmemory chunk`

単位で貸し借りする。

これにより異なるアーキテクチャ間でもメモリ 整列を保って容量をreallocateできる。

# Coordination

マスター / ワーカーにはそれぞれキャッシュ 管理器とcoordinatorがあり、ワーカー 読み込みが低い時はブロックをdonateし、ワーカー需要が増えたら回収する。

マスターは借りていたKV ブロックの配置を追跡し、ワーカーがメモリを取り戻す際には必要なキャッシュを追い出す/再配置して整合性を保つ。

重要なのは、ワーカーを単なる「KV専用GPU」にするのではなく、**ワーカー自身のモデル 提供を継続したまま余剰だけを貸す**点である。

# 評価条件

主評価は単一server内の4× NVIDIA H20 96GB構成で行う。

- GPU: 4× H20 96GB
- 高速GPU間接続: NVLink
- モデル: Qwen3 系列（8B / 14B / 32B等）、LWM-1M-Text
- ワークロード: ShareGPT、L-Eval
- 比較対象: vLLM + LMCache、vLLM + chunked プリフィル、SGLang + HiCache
- 実装: Python/Triton 推論 経路、C++ スケジューラ/キャッシュ 管理器、GPU間KV 転送

文脈-長さ感度では96GB H20だけでなく80GB、32GB、24GB級GPU条件も比較する。

# 主要結果

## 1. P99 TTFTを最大69%削減

エンドツーエンド 複数ターン 提供では、ShareGPT / L-EvalでSGLang + HiCacheに対しP99 TTFTを約67〜69%削減する。

vLLM + LMCacheに対しても約54〜58%低い。

効果の理由は2つある。

1. ワーカー HBMにより接頭部 キャッシュ 容量が増え、CPU/SSD 階層へ落ちにくくなる。
2. peer-常駐 KVを使う場合もPCIeではなくNVLinkで再読み込みする。

したがって「NVLinkが速い」だけでなく、**低速階層へ落ちるキャッシュ 未検出自体を減らす容量効果**も含む。

## 2. 最大context長を最大3.98×へ拡張

8K-トークン chunked プリフィルを使うvLLM 比較対象に対し、GPU HBM容量に応じて約1.58〜3.98×のmaximum 文脈 長さを実現する。

最大見出し結果の3.98×は、LSCによってマスター ローカル HBMへ全層 KVを同時常駐させなくてよくなった効果である。

これはモデルのarchitectural 文脈 窓自体を3.98倍に変更したわけではない。

**同じモデルが元から許す文脈 窓のうち、HBM不足で使えなかった範囲を実ハードウェア上で使えるようにした**という意味である。

## 3. Workerへの干渉は限定的

マスターがワーカー HBMとNVLinkを借りるため、ワーカー側が完全に空きというわけではない。

評価ではワーカーのTTFT増加は最大約9.7%、TPOT / スループット側の悪化は概ね7%未満の範囲と報告される。

つまりマスターだけを速くしてワーカーを大幅に犠牲にしたシステムではないが、zero 干渉でもない。

ワーカー 読み込みが高いときにメモリを回収する伸縮可能 制御が重要になる。

## 4. Layer-wise transferはほぼ隠せる

Qwen3-32Bで、99%のリクエストについてKV 読み込みは約11 ms未満、保存は約6 ms未満という測定が報告される。

さらに計算との重ね合わせ後は実効転送 オーバーヘッドがプリフィル全体の0.1%未満になる。

この結果は、peer GPUをメモリ 階層として使う設計が成立するには**リンク 帯域だけでなく層-水準 重ね合わせが重要**であることを示す。

# なぜmulti-model serverで特に有効なのか

単一モデルだけを全GPUへspreadしているserverでは「別モデルのアイドル HBM」が存在しない。

SwiftCacheの狙いは、複数の異種モデルを同居させる実運用 serverで

- モデル 1つの: 対話が多くKV-heavy
- モデル B: short コード 完了中心でKV-light
- モデル C: 要約中心で接頭部 再利用が少ない

という需要差がある状況である。

モデル単位で固定partitionするとB/Cのunused HBMは1つのから見えない。

SwiftCacheはメモリをserver-水準 共有領域に近づけ、**モデル間statistical multiplexingをKV キャッシュにも適用する**研究と理解できる。

# 既存研究との差

## CPU / SSD KV offload

LMCacheやHiCacheなどはCPU メモリ、ローカル/遠隔 保存を含む階層キャッシュを使う。

SwiftCacheはそれらより高速なpeer GPU HBMを追加階層として使い、同一server内NVLinkを優先する。

## Peer-GPU offload

Aqua等にも別GPUのメモリを使う発想はあるが、SwiftCacheは複数ターン 接頭部 再利用へ焦点を当て、

- 横断的モデル アイドル-HBM donation
- 層 ストリーム キャッシュ
- ローカル 通常 キャッシュ
- O(1) 伸縮可能 サイズ変更
- heterogeneous-モデル 整列

を一体化する。

## Chunked prefill

chunked プリフィルは長いプリフィルを小さく分けてピーク 活性値/干渉を抑えるが、全層 KVを保持する基本メモリ構造は変わらない。

SwiftCacheはKV自体の常駐を層単位に分解するため、最大文脈 長さへの作用点が異なる。

# 限界

1. **同一server内高速リンクが必要**: 主設計はNVLink/NVSwitch前提で、server間ネットワークへそのまま拡張した評価ではない。
2. **アイドル ワーカーが必要**: 全モデルのKV需要が同時に高い場合、貸せるHBMがなくなる。
3. **ワーカー 干渉は0ではない**: メモリ 帯域とNVLinkを消費し、TTFT/TPOTに数%程度の悪化が出る。
4. **モデル 配置依存**: どのモデルを同じserverへco-locateするかで利用できるメモリとリンク 構造が変わる。
5. **異種ブロック 整列**: MEUで扱えるが、アーキテクチャ差が大きいモデル pairでは貸借粒度が粗くなりメモリ利用効率が下がる可能性がある。
6. **キャッシュ 局所性の変化**: ワーカーが読み込み増加でメモリを回収するとマスター 接頭部を追い出す/移動する必要があり、通信量変動が激しいとキャッシュ churnが増える。
7. **official コード未確認**: 2026-09-10時点で論文に対応する公式公開repositoryを確認できていない。
8. **対象は無損失 容量/転送 最適化**: KVを圧縮・選択する研究ではないため、peer HBM総容量を超える巨大作業 集合では最終的にCPU/SSD等の下位階層が依然必要になる。

# 一般的な実装上の示唆

SwiftCacheの重要な視点は、GPU メモリを**モデル所有の固定資源**ではなく、server内で貸し借りできる資源として見ることである。

複数モデル 提供ではGPU 計算 utilizationだけでなく

- HBM 空き space
- KV キャッシュ ヒット demand
- NVLink/NVSwitch utilization

にもモデル間の非対称性がある。

これを同時にpoolingすれば、追加GPUなしで高温 サービスのメモリ 容量を増やせる可能性がある。

また、KVのように層ごとにしか使わない状態については、全層を同時常駐させる必要があるかを再検討できる。

`次layerのstate transfer < 現layerの隠せるcompute時間`

を満たせる高速階層があるなら、層 ストリーミングで容量を大きく削減できる。

この考え方はpeer HBMだけでなく、将来のCXL メモリや高帯域flash 階層でも応用可能だが、階層 遅延が長くなるほどプリフェッチ精度と重ね合わせ可能時間が重要になる。
