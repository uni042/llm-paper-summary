# KEEP: A KV-Cache-Centric Memory Management System for Efficient Embodied Planning

> 具身計画で頻繁に更新される長い記憶をKVキャッシュとして再利用する際、更新箇所以降のキャッシュ無効化とCPUからGPUへの読み込み待ちが増える問題に対し、更新頻度に応じた記憶グループ化、文脈依存の多段重要度伝播による選択的再計算、層をまたぐ先読み読み込みを組み合わせて、精度を保ちながら初回トークン時間を短縮するシステム。ALFREDとWAH-NLで実機評価され、完全再計算やCacheBlendと比べて計画成功率をほぼ維持または改善しつつ初回トークン時間を短縮している。

- **公開**: DAC 2026 / arXiv:2602.23592v2, 2026-03-17
- **種別**: Conference paper / preprint
- **対象**: KVキャッシュ、具身計画、階層メモリ、KV再計算、プリフィル高速化
- **実装**: vLLM上に約2.8K行のPython/PyTorch 2.0コードとして実装され、公式コードが公開されている。
## 概要
長期の具身計画では、エージェント状態、物体状態、過去行動、完了タスクなどの記憶を毎ステップの長い入力へ含める。生成する行動は短い一方、入力は数万トークンになり得るため、プリフィルが計画遅延の大半を占める。同じ記憶片のKVキャッシュを再利用すれば計算を省けるが、物体状態のような動的記憶が変わると、その位置以降のキャッシュが無効化される。KEEPは記憶の更新頻度を使って静的・動的グループを別粒度で管理し、必要な記憶間の注意関係だけを再計算し、CPU RAMに置いたKVを層間で先読みすることで、キャッシュ再利用率と計画精度を両立する。
## 問題設定
具身計画では、各ステップでエージェント自身の状態、物体の位置や属性、過去の行動、完了したタスクなどを記憶として入力へ戻す。こうした記憶は計画の重複探索を減らす一方、入力長を数万トークン規模まで押し上げ、短い行動生成に比べてプリフィル計算が支配的になる。記憶のKVキャッシュを保存して再利用する方法は一般の検索拡張生成では有効だが、具身環境では『牛乳を机から取る』だけでも牛乳と机の状態が変わる。固定長ブロックや前方一致だけに依存すると、小さな更新でも同じブロック内や後続部分のKVを再計算する必要がある。逆にブロックを細かくしすぎると、別ブロックの記憶同士が本来持つ注意関係を失い、計画精度が落ちる。さらにKVをCPU RAMへ置く場合、層ごとの再計算量と読み込み量が逆方向に偏るため、単純な『次層を先読み』だけでは転送器とGPUの双方に待ち時間が生じる。
## 新規性
KEEPはこの問題を三つの機構で分解する。第一に、記憶片の更新頻度を観測して静的グループと動的グループを切り替え、静的な記憶はまとめてKVを計算して内部の注意関係を残し、動的な記憶は記憶片単位に分けて更新時の無効化範囲を小さくする。第二に、現在の問い合わせから直接重要な記憶だけでなく、その記憶が強く参照する別の記憶へ重要度を伝播させ、安定するまで反復して再計算対象を決める。第三に、再計算対象から外れた記憶は後続層でも再計算されないという性質を使い、早い層で余っている転送時間に後段層向けKVを前倒しで読み込む。これにより、キャッシュの再利用率、記憶間相互作用、CPU-GPU転送の重なりを同時に改善する。
## 手法
### 手法のあらまし
処理は記憶構築、検索、重要度評価と再計算、層間読み込み、次の計画ステップへの更新という流れで進む。まず文埋め込みモデルで意味の近い記憶片をグループ化し、直近tステップで変化した記憶を含むかを監視する。全要素がtステップ変化しなければ静的グループとしてまとめてKVを計算し、どれかが更新されれば動的グループとして記憶片ごとにKVを持つ。論文ではt=10を用いる。問い合わせ時は静的グループをグループ単位、動的グループを記憶片単位で検索する。ここで静的側は記憶同士の文脈を保ったまとまりとして再利用し、動的側は更新された一部分だけを差し替えやすくするため、更新頻度と文脈保持の両方に合わせてキャッシュ粒度が決まる。モデルの各層では、最初に問い合わせから各記憶への平均注意重みを重要度の初期値とし、上位割合の記憶集合から他記憶への注意重みを使って重要度を更新する。この集合が変わらなくなるまで反復し、最終集合だけを次層で再計算する。第一層では全記憶を再計算し、後続層ほど再計算割合を減らす。これにより問い合わせから直接は目立たないが、重要な記憶と強く結び付く記憶も再計算へ戻せる。再計算しないと確定した記憶については、その後の層でも新しいKVを生成しないためCPU側KVを読む必要がある。現在層の計算より次層の読み込みが早く終わった場合、転送器を休ませず、再計算されないことが確定した記憶についてさらに先の層のKVを前倒しで読み込む。実装では層iのプリフィル、同層の重要度評価、次層以降のKV読み込みを三つの実行系列で重ね、依存関係が満たされたところで次層へ進む。計画行動が生成されて環境状態が変わると、該当する記憶片を更新し、更新履歴に応じて静的・動的分類を見直す。この一連の循環により、全面再計算を避けながら記憶間の重要な相互作用だけを回復し、CPU RAMからGPUへの転送待ちも隠す。

### 静的・動的記憶構築
意味的に近い記憶片をグループ化し、直近tステップの更新履歴で管理粒度を変える。静的グループは複数記憶を一緒にプリフィルしてグループ内の注意関係をKVへ残す。動的グループは記憶片ごとに独立してKVを計算するため、一つの物体状態が変化しても他の記憶片まで無効化しにくい。グループの状態が変わった時だけ新しい粒度でKVを作り直すため、毎ステップ全面再計算するより更新費用を抑えられる。検索も同じ粒度に合わせ、静的側ではまとまりを壊さず、動的側では必要な記憶だけを選べる。この切り替えは更新の多い記憶だけを細かく扱うため、すべてを小ブロック化した場合の文脈喪失を避けられる。静的から動的、動的から静的への遷移時には対象グループのKVを新しい方式で再計算し、その費用は数十ステップに一度程度の低頻度に抑える。

### 多段記憶再計算
単純な上位注意重みだけでは『鍵→机』のように問い合わせから間接的に重要な記憶を拾えない。そこで問い合わせからの平均注意重みで重要度を初期化し、現在の上位記憶集合が強く注意する別記憶へ重要度を伝播する。上位集合が安定するまで反復した後、その集合のKVだけを次層で再計算する。トークン単位ではなく記憶片単位で再計算するため、再計算しないKVは連続したブロックとして読み込みやすく、細粒度の部分更新に伴う入出力を減らす。重要度伝播は同じ層のMLP計算と並行できる。重要度集合は固定位置ではなく現在の問い合わせと記憶全体の注意関係から毎層更新されるため、状況によって必要な結び付きが変わる具身計画へ適応できる。再計算割合は第一層で最大とし、後段ほど減らして計算量を抑えつつ、重要な相互作用を段階的に回復する。

### 層均衡型記憶読み込み
初期層ほど再計算割合が高くCPUから読むKVが少ない一方、後段層ほど再計算割合が低く読み込み量が多い。次層だけを先読みする通常のパイプラインでは、前半は転送器が余り、後半はGPUが転送待ちになる。KEEPでは、一度『再計算しない』と決まった記憶は後続層でも再計算できないことを利用し、次層の読み込みが終わった転送器にさらに先の層のKVを前倒しさせる。これにより前半の空き転送時間を後半の負荷へ移し、層間の読み込み量を平準化する。前倒しできるのは、以前の層で再計算対象から外れ、その後は新しい隠れ状態が存在しないため将来層でも再計算されない記憶である。この確定情報を利用するので、未知の将来選択を推測して誤ったKVを先読みする方式ではなく、依存関係を守ったまま転送の空き時間を埋められる。

### 全体のデータ／制御の流れ
実装はvLLM上の約2.8K行のPython/PyTorch 2.0コードで、KVの格納場所をハッシュ表で管理する。`load_メモリ` が指定記憶・指定層のKVをGPUへ読み込み、`プリフィル_層` が重要記憶のKVを再計算し、`importance_evaluation` が注意重みから次層の再計算対象を決める。実行時には三つのスレッドを使い、層iのプリフィル計算、同層の重要度評価、層i+1およびさらに後段で必要になるKVの読み込みを重ねる。同期点は、次層の計算前に重要度評価と必要KV読み込みが完了していること、重要度評価前に当該層の注意計算が完了していることを保証する。KVの大部分はCPU RAMへ置き、必要な記憶だけをGPUへ運ぶ設計である。
## 評価条件
- **ハードウェア**: NVIDIA A6000 GPU×1（各モデルを単一GPUへ配置）
- **ソフトウェア**: vLLM基盤、PyTorch 2.0、sentence-transformers-mpnet-base-v2を記憶の意味クラスタリングに使用
- **モデル**: Qwen-2.5-14B、Qwen-2.5-32B（INT4重みのみ量子化）
- **データセット／トレース**: ALFRED、WAH-NL
- **比較対象**: LoTA Full Recompute、LoTA + Full Reuse、LoTA + CacheBlend、LLM-Planner、FLARE、KARMA
- **正確性・品質**: KEEPはKVを近似圧縮するのではなく、静的記憶のまとまりと重要な記憶間相互作用を選択的再計算で回復する。完全再計算と比べるとALFREDでQwen-14BはSR 44.63%に対し44.30%、Qwen-32Bは45.81%に対し45.50%で、精度差を小さく保ちながらTTFTを短縮している。
具身計画ベンチマークALFREDとWAH-NLで、各ステップに環境物体状態、エージェント状態、タスク履歴を記憶として更新し、LLMプランナが次の行動を予測する。計画精度はタスク成功率（Success Rate; SR）と副目標成功率（Subgoal Success Rate; Sub-SR）、計画効率は先頭トークンまでの時間（Time To First トークン; TTFT）で評価する。プリフィルが計画遅延の90%以上を占めるためTTFTを主な遅延指標とする。比較ではQwen-2.5-14BとQwen-2.5-32Bを使用し、32BはINT4の重みのみ量子化を適用する。記憶取得方針はLoTA系の設定に従う。さらに記憶片数を増やした時のTTFT伸び、三つの主要機構を一つずつ外す除去実験、再計算割合を変える感度分析を行う。
主結果は単一NVIDIA A6000上の実機評価であり、具身計画ベンチマークに特化している。CPU RAMからGPUへKVを読み込む階層構成を評価しているが、SSD/NVMeや複数GPU・複数ノードへの拡張は主評価ではない。記憶の更新頻度や意味構造が具身タスク特有であるため、一般の長文対話や検索拡張生成へ同じ改善幅がそのまま出るとは限らない。
## 主要結果
KEEPは、完全再計算に近い計画精度を維持しながら、記憶更新に伴うKV無効化とCPU-GPU読み込み待ちを減らした。ALFREDではQwen-2.5-14Bで完全再計算のSR 44.63%に対して44.30%を保ちつつTTFTを0.410秒から0.236秒へ短縮し、Qwen-2.5-32B INT4ではSR 45.81%に対して45.50%を保ちつつ1.213秒から0.635秒へ短縮した。CacheBlendとの比較では32BでSRを41.37%から45.50%へ4.13ポイント改善し、TTFTを1.209秒から0.635秒へ約1.90倍短縮した。記憶片数が40まで増える条件では、完全再計算に対するTTFT改善が32Bで2.68倍まで広がり、記憶更新量が増えるほど静的・動的分離の効果が現れる。

- ALFRED 成功率 / 45.50% (比較対象: LoTA + CacheBlend 41.37%; 条件: Qwen-2.5-32B INT4) — 多段の重要度伝播で現在の問い合わせから間接的に重要な記憶も再計算し、固定位置や局所差分だけで再計算対象を決める方式より記憶間の注意関係を回復した。

- ALFRED TTFT / 0.635秒 (比較対象: LoTA + CacheBlend 1.209秒; 条件: Qwen-2.5-32B INT4) — 更新頻度に応じた管理粒度でKV無効化を抑え、層をまたぐ先読みで後段の読み込み待ちを減らした結果、約1.90倍短縮した。

- ALFRED TTFT / 0.236秒 (比較対象: LoTA Full Recompute 0.410秒; 条件: Qwen-2.5-14B) — 成功率を44.63%から44.30%とほぼ維持しながら、再利用可能な記憶KVを残すことで約1.74倍短縮した。

- 40記憶片でのTTFT / 完全再計算比2.68倍短縮、CacheBlend比2.17倍短縮 (比較対象: LoTA Full Recompute / CacheBlend; 条件: ALFRED、Qwen-2.5-32B INT4) — 記憶片が増えるほど更新による再計算範囲が大きくなるため、静的・動的分離による無効化削減の相対効果が大きくなる。

- WAH-NL 副目標成功率とTTFT / 20.25%、0.601秒 (比較対象: CacheBlend 16.88%、1.148秒; 条件: Qwen-2.5-32B INT4) — 別の具身計画ベンチマークでも精度改善と約1.91倍のTTFT短縮が同時に確認された。

### 負の結果・境界条件
- **完全再計算との差**: ALFREDではQwen-14Bで完全再計算44.63%に対し44.30%、Qwen-32B INT4で45.81%に対し45.50%と小幅な成功率低下が残る。
- **静的・動的構築を外した場合**: ALFREDの除去実験でSRが44.30%から37.36%へ低下し、TTFTも0.230秒から0.355秒へ悪化する。管理粒度を固定すると静的記憶間の注意関係を失い、更新による再計算も増える。
- **多段再計算を外した場合**: SRが44.30%から41.78%へ2.52ポイント低下する一方、TTFTは0.230秒から0.228秒とほぼ変わらない。主な役割が速度ではなく重要な記憶間相互作用の回復であることを示す。
- **層均衡読み込みを外した場合**: SRは44.30%で変わらないがTTFTが0.230秒から0.273秒へ約1.20倍悪化する。前半層の転送空きと後半層の読み込み待ちを平準化する効果が速度改善に寄与している。

### 結果の読み方
三機構の役割は分離している。静的・動的記憶構築は更新時のKV無効化削減と静的記憶内の注意関係保持の両方に効き、多段再計算は主に精度を回復し、層均衡読み込みは主に転送待ちを隠す。したがってKEEPの高速化は単なるキャッシュ再利用率向上ではなく、どの粒度でKVを作るか、どの記憶を再計算するか、いつCPU RAMからGPUへ運ぶかを連動させた結果である。
## 品質への影響
完全再計算と比べて成功率は0.31〜0.33ポイント程度低いが、Full Reuseより大幅に高く、CacheBlendも上回る。したがって完全な無損失方式ではなく、選択的再計算による小さな精度差と大きなプリフィル短縮を交換する方式として捉えるべきである。
## 既存研究との差
- 一般の前方一致キャッシュや固定長ブロック再利用ではなく、具身記憶の更新頻度を直接使ってKV計算粒度を切り替える。
- CacheBlendのように局所的なKV差分や固定位置から再計算トークンを選ぶのではなく、問い合わせから記憶、さらに記憶から別記憶へ注意重要度を多段伝播し、間接的に重要な記憶を再計算する。
- トークン単位の部分更新ではなく記憶片単位で再計算することで、再利用KVを連続ブロックとして読み込みやすくする。
- CPU RAMに置くKVの単純な次層先読みではなく、前半層の余った転送時間を使って後段層向けKVまで前倒しし、層ごとの読み込み負荷を平準化する。
## 限界
- 評価はALFREDとWAH-NLの具身計画に限定され、一般の長文対話・検索拡張生成・コード生成で同じ更新頻度構造が成立するかは未評価。
- 主評価は単一NVIDIA A6000であり、複数GPU、複数ノード、PCIe以外の相互接続、SSD/NVMe階層は検証していない。
- 静的・動的判定の閾値t=10は典型的な一タスク長として固定しており、更新頻度が急変する環境での自動適応は示されていない。
- 重要度伝播は注意重みに依存するため、注意重みが計画上の因果的重要性を十分表さない場合には必要記憶を落とす可能性がある。完全再計算比で成功率はわずかに低い。
- 後続層で再計算しないという単調な再計算集合を利用した読み込み最適化のため、層ごとに再計算対象を再増加させる方式へはそのまま適用できない。
## 実装状態
公式コードが公開され、vLLMを基盤に約2.8K行のPython/PyTorch 2.0として実装されている。論文はDAC 2026として提示されている。
## 研究上の位置づけ
KEEPはKVキャッシュの容量圧縮そのものではなく、頻繁に書き換わるエージェント記憶を対象とした『KV再利用・選択的再計算・CPU退避読み込み』の統合管理に位置する。特に本リポジトリのKVキャッシュ退避／再計算系では、CacheBlend系の再計算精度とCPU-GPU階層の読み込みパイプラインを、具身記憶の更新頻度というアプリケーション側の構造と結びつけた点が重要である。SSD活用の観点では、静的記憶ほど低速大容量階層へ置きやすいという示唆があるが、論文自体はCPU RAMまでしか評価していないため、SSDへ拡張した性能主張はできない。
