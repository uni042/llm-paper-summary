# NEO: Saving GPU Memory Crisis with CPU Offloading for Online LLM Inference

> 一部requestだけKV cacheとdecode attentionをCPUへ移し、残りrequestはGPUで処理しながら、CPU/GPUが同時に終わるようoffload量を毎iteration調整してVRAM不足を緩和するonline serving system。

## 概要

NEOは、GPU memory不足でKV cacheを十分に保持できずbatch sizeが小さくなる問題に対して、**一部requestのdecode attentionとKV cacheだけをlocal CPUへ移す**online LLM inference systemである。

KV cacheをCPU DRAMへ置いて毎token GPUへ戻すと、大きなKV転送がPCIeを占有する。NEOはCPUへoffloadしたrequestについてattention計算もCPUで行い、GPUとは現在tokenの小さいactivationだけをやり取りする。

FastDecodeのように全requestのattentionをCPUへ固定するのではなく、**CPU担当requestとGPU担当requestを同時に進め、CPUの処理能力に収まる量だけoffloadする**。request長やqueue状態は時間とともに変わるため、毎iterationでCPU/GPUの予想処理時間を見てoffload量を調整する。

SSD / NVMeは使わず、local CPU DRAMをKVの退避先とする。

## 問題設定

online servingではlatencyを維持しながらthroughputを上げる必要がある。GPU computeに余裕があっても、model weightとKV cacheがVRAMを圧迫するとbatch sizeを増やせず、GPUの演算能力を使い切れない。

CPU DRAMは容量が大きいのでKV cacheを置けるが、KV全体を毎token PCIeで往復させるのは高コストである。一方decode attentionは大量のKVを読む割に計算量が少なく、GPUとCPUの演算性能差ほど実行時間差が大きくならない場合がある。

そこでNEOは、**KVをCPUへ置いたrequestについてはattentionもそのCPU側で実行する**。これによりGPU VRAMを空けてGPU側batchを大きくできる。

ただしCPUへ送りすぎると今度はCPU memory bandwidthがbottleneckになるため、offload量を固定しない。

## 手法

### 1. RequestをCPU attention側とGPU attention側へ分ける

各iterationで、

- GPU上でattentionまで処理するrequest群
- KVをCPUに置き、attentionだけCPUで処理するrequest群

へ分ける。

CPU側requestでもQ/K/V projectionやMLPなどの大きなlinear計算はGPUで行う。CPUへ移すのは主に**KVを大量に読むdecode attention**であり、model weight全体をCPUへ移すわけではない。

### 2. CPU側attentionとGPU側処理を同時に進める

CPU担当requestのattentionを実行している間に、GPUは別requestのlinear / attention処理を進める。

CPUへ割り当てるrequest数は、

`CPU attention時間 ≈ その間にGPUが進められる処理時間`

となる程度に調整する。

これによりCPUだけが遅れてGPUが待つ状態と、CPUが早く終わって遊ぶ状態の両方を減らす。

論文ではこの非対称な役割分担を `Asymmetric GPU-CPU pipelining` と呼ぶ。

### 3. 毎iterationのqueueからoffload量を決める

実workloadではinput / output lengthがrequestごとに異なり、生成が進むにつれてKV cache長も増える。

NEOは毎iteration、

- GPU decode queue
- CPU decode queue
- prefill待ちrequest

を確認し、GPUだけで処理する場合とCPU/GPUを併用する場合のthroughputを予測する。

CPU/GPU併用が有利なら、両者の予想busy timeが近くなるようrequestを割り振る。scheduler overheadは**1 iterationあたり3 ms未満**と報告される。

### 4. CPU側でもpaged KV cacheを直接読めるattention kernelを使う

vLLM型のKV cacheは小blockへ分かれており、memory上で連続していない。通常のCPU BLASへそのまま渡すのは難しい。

NEOはC++ / ISPCでCPU用paged attention kernel（PACPU）を実装し、block tableを参照しながら複数CPU coreとSIMDでKVを処理する。

### 5. Multi-GPUでは各GPUに対応するCPU側KVを固定する

multi-GPUでは各GPU workerが担当するKV headに対応するCPU KV cacheを持つ。

CPU間でKVを移動せず、GPU shardとCPU側KV partitionの対応を固定して、余計なCPU間通信を避ける。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | T4、A10G、H100 |
| Model | Llama-2-7B、Llama-3.1-8B、Llama-3.1-70B |
| CPU | GPU hostに付属するlocal x86 CPU |
| Workload | Azure code generation trace、OpenAI summarization comparison、synthetic workloads |
| Baseline | vLLM、SwiftLLM、FastDecode+ |
| Offload先 | CPU DRAMのみ |

A10GはAWS g5、T4はg4dn、H100はlocal HGX serverを使用する。FastDecode+は全requestのattentionをCPUへ置く方針をNEO runtime上に再実装した比較版である。

### Online load-latency

同程度のper-token latencyを維持した条件で、NEOはvLLMより処理可能request rateを高めた。

- 2×H100 + Llama-3.1-70B: 約14.3%高いthroughput
- A10G + Llama-3.1-8B: 約6.4%高いthroughput
- T4 + Llama-2-7B: 約5.6倍高いthroughput

T4で差が特に大きいのは、VRAM制約が強くGPU-onlyではKV cacheがbatch sizeを強く制限するためである。

### Workloadを変えた評価

synthetic workloadでinput / output lengthを変えると、最大でH100約14%、A10G約26%、T4約7.5倍のthroughput改善を報告する。

一方outputが短い場合はCPU offloadとschedulingの追加処理が利得を上回り、GPU-onlyよりわずかに遅くなる場合もある。NEOはその場合GPU-onlyへ戻せるが、実行時間予測が外れると最適でない判断が残る。

### CPU性能への感度

A10GでCPU capacityを増やすと、baseline比throughput改善は最大79.3%まで伸びた。CPU core数そのものより**CPU memory bandwidth**との相関が強く、decode attentionが主にmemory readで律速されることと整合する。

## 既存研究との差

### FastDecodeとの違い

FastDecodeはKV cacheとdecode attentionをCPUへ全面的に置くため、CPU capacityが不足するとCPU側が全体を待たせる。

NEOは**request単位で一部だけCPUへ移し、GPU attentionも残す**。さらに固定配置ではなく毎iterationのqueue状態からCPU/GPU比率を変えるため、不規則なonline workloadへ適応しやすい。

### FlexGenとの違い

FlexGenは大きなbatchを作り、weight / KV I/Oを多数requestへ分散してoffline throughputを高める。NEOはuser-facing servingを対象に、latencyを保ちながら既存host CPUを使ってGPU batch sizeを増やす。

### HeteGenとの違い

HeteGenは主にlinear weightをCPU/GPUへ分割する。NEOはweightではなく**KV cacheとdecode attention**をrequest単位でCPUへ移す。

## 限界

- 改善幅はCPU memory bandwidthとGPU VRAM圧迫度に強く依存し、H100のようにVRAM余裕が大きい環境では利得が小さい。
- outputが短いworkloadではoffload / scheduling overheadが利得を上回る場合がある。
- schedulerは事前測定した実行時間を使うため、workloadやhardware状態が変わると予測誤差が出る。
- 論文時点の実装はSwiftLLMベースで、vLLM本体へのupstream統合ではない。
- SSD / NVMe offloadやweight offloadは対象外。

## 一般的な実装上の含意

NEOの重要な示唆は、CPU offloadを「GPUに入らないものを全部CPUへ置く」という二値選択にしないことである。

**CPU memory bandwidthで処理できる範囲だけrequestをoffloadし、残りはGPUで処理する**方が、hardware balanceやrequest長が変わるonline servingでは安定しやすい。

またKV cacheをCPUへ置くなら、毎token KV全体をPCIeで往復させるより、attention計算自体をKVのある場所へ寄せて小さいactivationだけを転送する方が合理的な場合がある。
