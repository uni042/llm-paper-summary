# NEO: Saving GPU Memory Crisis with CPU Offloading for Online LLM Inference

> 一部リクエストだけKV キャッシュとデコード 注意機構をCPUへ移し、残りリクエストはGPUで処理しながら、CPU/GPUが同時に終わるようオフロード量を毎iteration調整してVRAM不足を緩和するオンライン 提供 システム。

## 概要

NEOは、GPU メモリ不足でKV キャッシュを十分に保持できずバッチ 大きさが小さくなる問題に対して、**一部リクエストのデコード 注意機構とKV キャッシュだけをローカル CPUへ移す**オンライン LLM 推論 システムである。

KV キャッシュをCPU DRAMへ置いて毎トークン GPUへ戻すと、大きなKV転送がPCIeを占有する。NEOはCPUへオフロードしたリクエストについて注意機構計算もCPUで行い、GPUとは現在トークンの小さい活性値だけをやり取りする。

FastDecodeのように全リクエストの注意機構をCPUへ固定するのではなく、**CPU担当リクエストとGPU担当リクエストを同時に進め、CPUの処理能力に収まる量だけオフロードする**。リクエスト長や待ち行列状態は時間とともに変わるため、毎iterationでCPU/GPUの予想処理時間を見てオフロード量を調整する。

SSD / NVMeは使わず、ローカル CPU DRAMをKVの退避先とする。

## 問題設定

オンライン 提供では遅延を維持しながらスループットを上げる必要がある。GPU 計算に余裕があっても、モデル 重みとKV キャッシュがVRAMを圧迫するとバッチ 大きさを増やせず、GPUの演算能力を使い切れない。

CPU DRAMは容量が大きいのでKV キャッシュを置けるが、KV全体を毎トークン PCIeで往復させるのは高コストである。一方デコード 注意機構は大量のKVを読む割に計算量が少なく、GPUとCPUの演算性能差ほど実行時間差が大きくならない場合がある。

そこでNEOは、**KVをCPUへ置いたリクエストについては注意機構もそのCPU側で実行する**。これによりGPU VRAMを空けてGPU側バッチを大きくできる。

ただしCPUへ送りすぎると今度はCPU メモリ 帯域がボトルネックになるため、オフロード量を固定しない。

## 手法

### 1. RequestをCPU attention側とGPU attention側へ分ける

各iterationで、

- GPU上で注意機構まで処理するリクエスト群
- KVをCPUに置き、注意機構だけCPUで処理するリクエスト群

へ分ける。

CPU側リクエストでもQ/K/V 射影やMLPなどの大きな線形計算はGPUで行う。CPUへ移すのは主に**KVを大量に読むデコード 注意機構**であり、モデル 重み全体をCPUへ移すわけではない。

データ経路としては、GPUが現在トークンの射影などを計算した後、CPU担当リクエストについては現在トークン側の小さいクエリ / 活性値だけをホストへ渡す。CPUはDRAMに残してある長い過去KVをその場で読み、デコード 注意機構を計算して小さい注意機構出力をGPUへ返す。これにより文脈長に比例して増える過去KVを毎トークン PCIeでGPUへ戻す代わりに、トークンごとの小さな活性値だけを往復させられる。したがって長い文脈ほど転送削減の価値が増える一方、短いリクエストではCPU起動・同期・小転送の固定費が相対的に大きくなりやすい。

### 2. CPU側attentionとGPU側処理を同時に進める

CPU担当リクエストの注意機構を実行している間に、GPUは別リクエストの線形 / 注意機構処理を進める。

CPUへ割り当てるリクエスト数は、

`CPU attention時間 ≈ その間にGPUが進められる処理時間`

となる程度に調整する。

これによりCPUだけが遅れてGPUが待つ状態と、CPUが早く終わって遊ぶ状態の両方を減らす。

論文ではこの非対称な役割分担を `Asymmetric GPU-CPU pipelining` と呼ぶ。

### 3. 毎iterationのqueueからoffload量を決める

実ワークロードでは入力 / 出力 長さがリクエストごとに異なり、生成が進むにつれてKV キャッシュ長も増える。

NEOは毎iteration、

- GPU デコード 待ち行列
- CPU デコード 待ち行列
- プリフィル待ちリクエスト

を確認し、GPUだけで処理する場合とCPU/GPUを併用する場合のスループットを予測する。

CPU/GPU併用が有利なら、両者の予想busy timeが近くなるようリクエストを割り振る。スケジューラ オーバーヘッドは**1 iterationあたり3 ms未満**と報告される。

### 4. CPU側でもpaged KV cacheを直接読めるattention kernelを使う

vLLM型のKV キャッシュは小ブロックへ分かれており、メモリ上で連続していない。通常のCPU BLASへそのまま渡すのは難しい。

NEOはC++ / ISPCでCPU用paged 注意機構 カーネル（PACPU）を実装し、ブロック tableを参照しながら複数CPU コアとSIMDでKVを処理する。

### 5. Multi-GPUでは各GPUに対応するCPU側KVを固定する

multi-GPUでは各GPU workerが担当するKV ヘッドに対応するCPU KV キャッシュを持つ。

CPU間でKVを移動せず、GPU shardとCPU側KV partitionの対応を固定して、余計なCPU間通信を避ける。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | T4、A10G、H100 |
| Model | Llama-2-7B、Llama-3.1-8B、Llama-3.1-70B |
| CPU | GPU ホストに付属するローカル x86 CPU |
| ワークロード | Azure code generation トレース、OpenAI summarization comparison、合成 ワークロード |
| 比較対象 | vLLM、SwiftLLM、FastDecode+ |
| オフロード先 | CPU DRAMのみ |

A10GはAWS g5、T4はg4dn、H100はローカル HGX serverを使用する。FastDecode+は全リクエストの注意機構をCPUへ置く方針をNEO ランタイム上に再実装した比較版である。

### Online load-latency

同程度のトークンごと 遅延を維持した条件で、NEOはvLLMより処理可能リクエスト rateを高めた。

- 2×H100 + Llama-3.1-70B: 約14.3%高いスループット
- A10G + Llama-3.1-8B: 約6.4%高いスループット
- T4 + Llama-2-7B: 約5.6倍高いスループット

T4で差が特に大きいのは、VRAM制約が強くGPU-onlyではKV キャッシュがバッチ 大きさを強く制限するためである。

### Workloadを変えた評価

合成 ワークロードで入力 / 出力 長さを変えると、最大でH100約14%、A10G約26%、T4約7.5倍のスループット改善を報告する。

一方出力が短い場合はCPU オフロードとスケジューリングの追加処理が利得を上回り、GPU-onlyよりわずかに遅くなる場合もある。NEOはその場合GPU-onlyへ戻せるが、実行時間予測が外れると最適でない判断が残る。

### CPU性能への感度

A10GでCPU 容量を増やすと、比較対象比スループット改善は最大79.3%まで伸びた。CPU コア数そのものより**CPU メモリ 帯域**との相関が強く、デコード 注意機構が主にメモリ readで律速されることと整合する。

## 既存研究との差

### FastDecodeとの違い

FastDecodeはKV キャッシュとデコード 注意機構をCPUへ全面的に置くため、CPU 容量が不足するとCPU側が全体を待たせる。

NEOは**リクエスト単位で一部だけCPUへ移し、GPU 注意機構も残す**。さらに固定配置ではなく毎iterationの待ち行列状態からCPU/GPU比率を変えるため、不規則なオンライン ワークロードへ適応しやすい。

### FlexGenとの違い

FlexGenは大きなバッチを作り、重み / KV I/Oを多数リクエストへ分散してオフライン スループットを高める。NEOはuser-facing 提供を対象に、遅延を保ちながら既存ホスト CPUを使ってGPU バッチ 大きさを増やす。

### HeteGenとの違い

HeteGenは主に線形 重みをCPU/GPUへ分割する。NEOは重みではなく**KV キャッシュとデコード 注意機構**をリクエスト単位でCPUへ移す。

## 限界

- 改善幅はCPU メモリ 帯域とGPU VRAM圧迫度に強く依存し、H100のようにVRAM余裕が大きい環境では利得が小さい。
- 出力が短いワークロードではオフロード / スケジューリング オーバーヘッドが利得を上回る場合がある。
- スケジューラは事前測定した実行時間を使うため、ワークロードやハードウェア状態が変わると予測誤差が出る。
- 論文時点の実装はSwiftLLMベースで、vLLM本体へのupstream統合ではない。
- SSD / NVMe オフロードや重み オフロードは対象外。

## 一般的な実装上の含意

NEOの重要な示唆は、CPU オフロードを「GPUに入らないものを全部CPUへ置く」という二値選択にしないことである。

**CPU メモリ 帯域で処理できる範囲だけリクエストをオフロードし、残りはGPUで処理する**方が、ハードウェア 均衡やリクエスト長が変わるオンライン 提供では安定しやすい。

またKV キャッシュをCPUへ置くなら、毎トークン KV全体をPCIeで往復させるより、注意機構計算自体をKVのある場所へ寄せて小さい活性値だけを転送する方が合理的な場合がある。
