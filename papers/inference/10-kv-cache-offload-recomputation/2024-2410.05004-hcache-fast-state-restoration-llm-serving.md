# Fast State Restoration in LLM Serving with HCache

> GPUから追い出した会話状態を、巨大なKVキャッシュそのものでも元トークン列でもなく中間活性として保存し、I/Oと再計算を重ねて高速にKVへ復元する状態再利用方式。

## 概要

複数ターン会話や検索拡張生成（Retrieval-Augmented Generation; RAG）では、同じ長い文脈を後続要求でも再利用する。最も速いのは前回のキー・バリューキャッシュ（Key-Value cache; KVキャッシュ）をGPUに残すことだが、GPUメモリは限られるため、多数の休止セッションを同時に保持できない。そこで既存システムは、KVをCPUメモリやSSDへ退避して後で読み戻すか、元トークンを再度プリフィルしてKVを再計算する。

KV退避は計算を省ける代わりに保存量と転送量が大きい。トークン再計算は外部I/Oを抑えられる代わりに、長い文脈をTransformerへもう一度通す計算が必要になる。HCacheは、この二者択一の中間に「各層の中間活性を保存し、再開時にそこからKVを作り直す」という第三の状態表現を置く。KVより保存・転送量を小さくしつつ、元トークンから全計算をやり直すより計算量を減らす。

ただし中間活性を保存するだけでは速くならない。復元時にはストレージから活性を読むI/Oと、それを用いて各層のKVを再構成するGPU計算が同時に発生し、保存時と復元時で望ましいデータ並びも異なる。HCacheは、計算とI/Oを重ねるバブルフリー復元スケジューラ（bubble-free restoration scheduler）と、レイアウト不一致を吸収するチャンク型ストレージ管理（chunk-based storage manager）を加える。

Llama2-7B、Llama2-13B、OPT-30Bなどを用いた実タスク評価では、KVオフロード比で初回トークン遅延（Time To First Token; TTFT）を最大1.93倍改善しながら保存量を1.92〜2.40倍削減し、元トークン再計算比ではTTFTを最大5.73倍短縮する。生成中のトークン間時間（Time Between Tokens; TBT）への追加負担は4%未満と報告される。

## 問題設定

Transformerの各層は過去トークンのK/Vを保存し、デコード時に繰り返し参照する。同じ会話が再開したとき、このKVが残っていればプリフィルを省ける。しかしKVは「層数 × トークン数 × K/V次元」に比例して増えるため、GPU上に残せるセッション数には限界がある。休止セッションを追い出すと、次回アクセス時に状態復元が必要になる。

第一の既存策はKVオフロードである。GPUで作ったKVをホストメモリやSSDへ書き出し、再開時にそのままGPUへ戻す。この方法は再計算をほぼ避けられるが、KV全体を保存・転送するI/OがTTFTを支配しやすい。第二は元トークンからの再計算で、保存データは小さいがプリフィル計算を繰り返す。高速GPUと遅いストレージ、または逆の組み合わせで、どちらが有利かも変わる。

HCacheは、KVより前の中間活性を復元チェックポイントとして使う。これにより、保存データ量と再計算量を両方「中間」に置ける。しかし、復元はI/OとGPU計算の混合処理となるため、どちらかを直列に待つと利点が失われる。また、保存処理は層ごとに書きやすい一方、復元処理はトークン方向のまとまった読出しが必要になり、素朴なファイル配置では細粒度ランダムI/Oが増える。

## 手法

### 1. KVではなく中間活性を復元点として保存する

通常のTransformer層では、入力となる隠れ状態からQ/K/V射影を計算し、K/Vをキャッシュへ追加する。HCacheはこの層入力側の中間活性を保存しておき、セッション再開時に活性を読み込んで必要なK/V射影を再実行する。

この選択により、元トークンからモデル全層を通し直すより再計算範囲を狭められ、KVそのものを全量保存するよりI/O量を減らせる。つまり、計算資源とストレージ帯域を交換可能な二つの資源として同時に利用する設計である。

### 2. バブルフリー復元スケジューラでI/Oと計算を重ねる

復元対象を小さな単位へ分割し、ある部分の活性をストレージから読んでいる間に、すでに読み終えた部分からGPU上でKVを計算する。全活性の読込み後に計算を始める直列方式と異なり、I/OとGPU計算の待ち時間を相互に隠す。

ここで「バブルフリー」はI/O時間が消えるという意味ではない。計算と転送のうち長い方が下限になるため、両者の速度比に合わせた分割と順序が必要になる。ストレージが遅い環境ではI/Oを多めに先行させ、GPU計算が相対的に遅い環境では過剰な先読みを避ける。この資源補完性がHCacheの中間表現を実用的にする。

### 3. チャンク型ストレージで保存順と復元順の不一致を吸収する

状態保存では、新しいトークンが各層を順に通過するため、層方向にまとまった書込みが自然になる。一方、復元では複数トークンの活性をまとめて読み、層ごとのK/V計算へ供給したい。単一の連続配置をどちらかへ最適化すると、他方で小さなランダムI/Oが増える。

HCacheは状態をチャンクへ分割し、保存と復元の双方で十分大きな連続I/Oを作れるよう管理する。これにより、論理的な「layer-before-token」と「token-before-layer」の順序差を、物理ストレージ上の細かなアクセス増加へ直結させない。

### 4. 生成中の保存負担を二段階に分ける

新しく生成した状態を毎トークン即座に重い形式で永続化すると、通常のデコードTBTを悪化させる。HCacheは生成経路への保存負担を分離し、復元性能を優先した配置を後段で整える。評価ではこの追加負担を含めてもTBTへのオーバーヘッドは4%未満に抑えられたと報告する。

### 5. 複数GPUでは重複読出しを避ける

テンソル並列では各GPUがKV計算のため隠れ状態を必要とするが、全GPUが同じ活性をストレージから重複して読むとI/Oが増幅する。HCacheはGPUごとに異なるトークン範囲を読み、NVLink上のall-gatherで全体を再構成する。パイプライン並列では、各GPUが担当層の状態を並列に復元できる。

この設計は「SSDから読む帯域」と「GPU間リンク帯域」を分けて利用する。高速NVLinkがある環境では、ストレージへの重複アクセスを避けた方が有利になるという判断である。

## 評価

### 評価条件

| 項目 | 条件 |
|---|---|
| 基本サーバー | 4× NVIDIA A100 40GB SXM4、NVLink |
| ホスト | 2× AMD EPYC 7642、256GB DDR4 |
| ストレージ | 4× Samsung PM9A3 4TB enterprise SSD |
| モデル | Llama2-7B、Llama2-13B、OPT-30B |
| 負荷 | ShareGPT系を含む実タスク／実トレース |
| 比較方式 | KVオフロード、元トークンからの再計算、理想復元 |
| 主指標 | TTFT、TBT、保存容量、負荷率変化時の復元性能 |
| 感度 | GPU、ストレージ速度、文脈長を変更。クラウド環境ではホストDRAMも保存先として使用 |

### 代表的な評価結果

| 比較 | 指標 | HCacheの結果 | 読み取れること |
|---|---|---|---|
| KVオフロード | TTFT | 最大1.93倍改善 | KV全量転送より、活性I/O + 部分再計算の方が速い条件がある |
| KVオフロード | 保存容量 | 1.92〜2.40倍少ない | GPU外の状態保持容量も削減できる |
| 元トークン再計算 | TTFT | 最大5.73倍短縮 | 既存活性を復元点にすることで長い再プリフィルを回避できる |
| 通常デコード | TBT追加負担 | 4%未満 | 状態保存を導入しても生成経路の定常オーバーヘッドを抑える |
| ハードウェア感度 | GPU/保存装置を変更 | 利得は計算速度とI/O速度の比で変化 | 固定倍率ではなく、資源バランスに依存する方式 |

TTFTの改善は、HCacheがI/Oを完全に排除した結果ではない。KVオフロードよりI/Oを減らし、再計算方式より計算を減らしたうえで、残った二つを重ねた結果である。したがって、GPUだけを高速化、あるいはSSDだけを高速化した場合に同じ倍率が得られるとは限らない。

負荷率が高くなると、状態復元と新規生成が同じGPU・I/O資源を奪い合う。HCacheの評価はこの競合も含めてTTFT/TBTを測っており、復元単体マイクロベンチマークだけではない。一方、最良値だけを本番SLAへ直接当てはめず、自環境の休止時間・再入場率・ストレージ構成で確認する必要がある。

## 既存研究との差

KVオフロードは「計算済み状態をそのまま保存する」ため再計算が少ないが、状態が大きい。再計算は「入力トークンだけを残す」ため保存量は小さいが、復元時の計算が大きい。HCacheはその中間に、計算済みだがKVより小さい中間活性を置く。

さらに、本論文は保存形式の提案だけでなく、I/Oと計算を同時進行させるスケジューラと、保存・復元のアクセス順差を処理するストレージ配置までを一つの復元経路として設計する。中間表現を変えるだけでは生じる新しいI/O問題をシステム側で解いている点が差である。

## 限界

- セッションが再利用されなければ、状態保存の費用を回収できない。再入場率が低い負荷では単純破棄が有利な可能性がある。
- 利得はGPU計算性能とホスト/SSD帯域の比に依存する。極端に遅いストレージではI/Oが、低速GPUでは再計算が支配する。
- モデル構造や重み版が変わると、保存済み中間活性との互換性を維持できない場合がある。
- 複数GPUでの重複I/O削減は高速GPU間接続を利用するため、PCIeのみの構成では通信費用が異なる。
- TTFT/TBTと保存量を中心に評価しており、長期永続化、障害復旧、マルチテナントの隔離・暗号化などは別の運用課題である。
- 中間活性もゼロコストではなく、保存容量・書込み帯域・管理メタデータを必要とする。
