# SpeCache: Speculative Key-Value Caching for Efficient Generation of LLMs

> SpeCacheは、**KV キャッシュを消してVRAMを空けるのではなく、16-bitの完全な正本をCPUに残したまま、今のトークンが実際に強く参照する少数のKVだけをGPUへ戻す**方式である。さらに、現在の出力トークンとは別に「次のトークンがどの過去トークンを参照しそうか」を予測する投機トークンも同時に流し、次ステップ用KVのCPU→GPU転送を現在のGPU計算と重ねる。これにより、長文脈でKV キャッシュがVRAMを圧迫する問題を抑えつつ、単純なKV オフロードで発生する転送待ちも減らす。

## 概要

Transformerの逐次生成では、過去トークンのキー/値をKVキャッシュ（KV cache）として保存する。これがあるため、次トークンを生成するたびに過去トークン全体のキー/値を再計算する必要はない。一方でKV キャッシュは文脈長にほぼ比例して増え、長文を扱うほどGPU VRAMを圧迫する。

既存の対策には、重要でないKVを捨てる削除（eviction）、複数KVをまとめる統合（merging）、値を低bit化する量子化（quantization）がある。しかし、いったん消したり粗くしたKVが後のトークンで急に重要になっても、元の情報を完全には取り戻せない。

逆に、16-bit KVをすべてCPU DRAMへ退避（offload）すれば正本は失わない。ただし毎デコード ステップで大量のKVをCPUからGPUへ読み戻すと、PCIeなどのCPU-GPU転送が新しい待ち時間になる。

SpeCacheはこの2つの問題を分離して考える。

1. **容量問題**は、完全な16-bit KVをCPUへ置き、GPUには非常に小さい低bitコピーだけを常駐させることで解く。
2. **転送問題**は、各クエリが実際に強く参照するKVがごく一部であることを利用し、その少数だけを16-bitでGPUへ戻すことで解く。
3. さらに、必要KVが分かってから転送を始めると遅いので、**次トークンが必要とするKVを1 ステップ前から予測して先読み（prefetch）**する。

重要なのは、GPU上の1/2-bit KVが「最終的なKV キャッシュそのもの」ではなく、**CPUにある16-bit正本のうち何を先読みすべきか判断する索引兼近似表現**としても使われる点である。

## 問題設定

### 長contextではKV cacheがモデル重み並みに大きくなる

KV キャッシュは各層・各トークンについてキー/値を保持するため、系列が伸びるほど容量も線形に増える。論文は例として、LLaMA-2-7Bで系列 length 2k、バッチ size 16の場合、KV キャッシュの要素数が8.4Bに達し、モデル自身のパラメータ数を上回ることを挙げている。

この状態では、GPU計算能力が余っていてもVRAM不足のためバッチを増やせない。したがって長文脈 推論提供では、KV容量そのものがスループットを制限し得る。

### 「昔は重要でなかったKV」が後で重要になる

アテンションは一般に疎で、各クエリが大きなアテンション 重みを与える過去トークンは一部に偏る。SpeCacheのプロファイリングでは、LLaMA-3-8B・PG19・系列 length 8196の条件で、**約0.5%のキーだけでクエリのアテンション massの90%を覆える**ことを観測している。

しかし「どの0.5%が重要か」はクエリごとに変わる。

そのため、過去のアテンション スコアを累積して重要でないKVを永久に捨てる方式では、現在は不要でも数ステップ後に必要になるKVを先に削除してしまう可能性がある。SpeCacheがCPUに16-bit正本を残す理由はここにある。

### 全KVを毎回CPUから戻すのは遅い

一方、正本をCPUへ置くだけでは十分ではない。各ステップで全KVをGPUへ読み戻せば、長文脈では転送時間がデコード計算を上回る。

SpeCacheはMistral-7B-Instruct-v0.2、32k 文脈、NVIDIA A6000で転送をプロファイリングし、非連続な小領域の転送には追加オーバーヘッドがあるものの、top-1%だけに絞れば**全KV転送より転送遅延を約95%削減できる**と報告している。

したがって課題は、「アテンションを始める前に、次に重要になる少数のKVをどう特定するか」である。

## 手法

SpeCacheでは、1本の生成を次の3段階で進める。

1. **事前充填（prefill）**でプロンプトを処理する。各層で作った16-bit KVはCPUへ退避し、GPUには1/2-bitへ量子化した小さなコピーを残す。
2. **事前デコード（pre-decoding）**を1回だけ追加する。最初の正確な出力トークンを使って、次ステップでどのKVが重要になりそうかを先に推定し、その16-bit KVをCPUからGPUへ先読みする。
3. 通常の**デコード**では、正確な出力を作るトークンと、次ステップの参照先を予測するための投機トークンを2本同時に計算する。投機トークンから次ステップのtop-k KV indexを得ると、現在の後段層を計算している間に該当KVをCPUから読み込む。

つまり各ステップは概ね、

`現在tokenを計算 + 次token用の参照先を予測 → 次stepの16-bit KVを先読み → 次stepへ`

というパイプラインになる。

## 手法

### 1. CPUに16-bit正本、GPUにlow-bitコピーを置く

プリフィル中、SpeCacheは層ごとにKVを生成する。アテンション 層の計算が終わると、その層のKVについて2つの処理を行う。

- 元の16-bit KV キャッシュはCPU DRAMへ退避する。
- GPU側には1-bitまたは2-bitへ量子化したKVコピーを残す。

16-bit正本をCPUへ移すので、GPUは次層のKVを作るための空き容量を確保できる。プロンプト全体のプリフィルが終わった時点では、GPU上に主として低ビットコピーがあり、CPU側に全トークン分の16-bit正本がある状態になる。

ここで低ビットコピーには2つの役割がある。1つは、top-k以外のKVについて近似的なアテンション計算に使うこと。もう1つは、**どの過去トークンが重要かをアテンション スコアから判定し、CPU側のどの16-bit KVを次に戻すか決めること**である。

### 2. attention sparsityを使って16-bitで戻すKVを絞る

各クエリについて、GPU上の低ビット KVを使ってアテンション スコアを計算し、そのスコアが大きいtop-kのKV indexを求める。

例えば32k トークンすべてを16-bitで戻すのではなく、そのうち特に重要な64組だけを16-bitで戻す、といった使い方をする。論文の主な実装ではtop-64の16-bit KVを先読みしている。

アテンション計算時には、そのtop-k部分だけ低ビット値をCPUから取得した16-bit正本へ置き換える。残りは低ビット表現のまま利用する。

したがってSpeCacheは「必要KVだけを完全精度で取得する」方式ではあるが、アテンション全体がfull 16-bitと完全に同じという意味での無損失（lossless）推論ではない。**正本を捨てないため将来必要になったKVを復元できること**と、**各ステップの全KVを16-bitで計算すること**は別である。

### 3. 投機tokenで「次stepのquery」を1 step早く作る

top-k KVを選ぶには、本来は次ステップのクエリが必要である。しかし次ステップに入ってからクエリを計算し、そこで初めてCPU転送を始めると、その転送が重要な 経路に入る。

SpeCacheはこの順序を逆転させるため、各ステップで2 トークンを同時にデコードする。

- **出力トークン側**: ユーザーへ返す正規の生成を進める。
- **投機トークン側（speculative token）**: 次ステップで使われるクエリを近似し、どのKVが重要になりそうかを予測するためだけに使う。

投機トークンは最終出力として信用する必要がない。必要なのは、次の真のクエリと似たアテンション先を選べる程度に近いことだけである。

この設計により、投機トークンのアテンション スコアから次ステップのtop-k indexを得た時点でCPU→GPU転送を開始できる。転送中にも現在ステップの後続層計算を進められるため、I/OをGPU計算の裏へ隠せる。

### 4. 最初のstepだけpre-decodingを挟む

通常デコードに入る前には、まだ「1 ステップ前の投機トークン」が存在しない。そこでSpeCacheは最初だけ事前デコード（pre-decoding）を1回追加する。

プリフィルが生成した最初の正確なトークン `T1` を低ビット KVで処理し、暫定的な投機トークン `T2'` と、`T1` が強く参照するtop-k indexを得る。そのindexに対応する16-bit KVをCPUから先読みしておく。

これで最初の本デコード ステップ開始時から、必要なtop-k 16-bit KVがGPUに揃う。

### 5. 通常decodeでは「現在の正確な生成」と「次の予測」を同時進行する

ステップ `t` の開始時、GPUには概ね次がある。

- 現在の正規トークン `Tt`
- 次を予測する投機トークン `T't+1`
- 全履歴の低ビット KV キャッシュ
- `Tt`向けに前ステップで先読み済みのtop-k 16-bit KV

この2 トークンを同じモデル 重みとKVを共有して同時に順伝播する。

`Tt`側からは次の正規出力 `Tt+1` を得る。同時に、`T't+1`のアテンション スコアから次ステップ用top-k indexを記録し、その16-bit KVをCPUから先読みする。不要になった16-bit top-k KVはGPUから外し、新しく生成された16-bit KVの正本はCPUへ追加する。

このメモリ操作は、可能な限り後続層のGPU計算と並行させる。

論文の主張ではデコードはメモリI/O boundになりやすいため、2 トークンをまとめて処理してFLOPsが増えても、モデル 重みやKVの読み出しを共有でき、単一ステップ 遅延の増加は小さい。ここが「投機トークンを1本余計に計算しても得になる」根拠である。

### 6. GPU側KVの1-bit / 2-bit量子化

GPUに常駐する検索用KVコピーにはKIVI系の学習後量子化（post-training quantization）を使う。2-bitは既存KIVIを利用し、追加学習を必要としない。

1-bitでは単純にmin/maxへ丸めると値の絶対値が過大になり、生成品質が大きく落ちるため、SpeCacheは各量子化 intervalの中点へ写すようzero 点と尺度を変更している。

この1-bitコピーが高精度な出力そのものを担うのではなく、16-bit top-kを混ぜてアテンション情報を補うため、単純な1-bit KV キャッシュより品質を大きく回復できる。

## 1 stepのデータの流れ

| 段階 | GPU上の主な情報 | CPU上の主な情報 | 何をするか |
|---|---|---|---|
| Prefill | 生成中layerのKV、low-bitコピー | 完了layerの16-bit KV正本 | layerごとに量子化し、正本をCPUへ退避 |
| Pre-decode | low-bit KV | 全16-bit KV | 最初のtop-kを予測し16-bit KVをprefetch |
| Decode step t | low-bit全KV + `Tt`用top-k 16-bit KV | 全16-bit KV正本 | `Tt`と投機tokenを同時計算 |
| step tの途中 | 次stepのtop-k index | 対応する16-bit KV | 後続layer計算と並行してCPU→GPU転送 |
| step終了 | 次step用top-k 16-bit KV | 新規KVも正本へ追加 | 古いtop-kを入れ替えて次stepへ |

## なぜ効くのか

SpeCacheの改善は、1つの圧縮技術だけによるものではない。

まず、16-bit KVの大部分をCPUへ移すことで、GPU VRAMに空きが生まれる。その空きを使ってバッチ sizeを大きくできるため、スループットが上がる。

次に、全KVではなくtop-kだけをCPUから戻すため、転送量が大きく減る。アテンションがクエリ依存に疎であるほど、この効果は大きい。

最後に、そのtop-k選択を投機トークンで1 ステップ前倒しすることで、CPU-GPU転送をGPU計算と重複実行できる。単なる「必要なKVだけ取る」方式より、転送待ちを重要な 経路から外しやすい。

## 評価

### 結論

LongBenchとNeedle-in-a-Haystackでは、GPU上のKV容量をfull 16-bitの約10%程度まで減らした条件でも、単純な1-bit量子化や追い出し系方式より高い品質を維持した。

スループット面では、単一NVIDIA A6000上のMistral-7B-Instruct-v0.2で、KV削減によって許容バッチ sizeを大きくできた結果、文脈が長いほど高速化倍率が大きくなった。

### 品質: 「正本を残す」効果

LongBenchでは、Mistral-7B-Instruct-v0.2でfull 16-bit KVの平均スコアが42.3なのに対し、SpeCacheはGPU KV容量0.10×の条件で40.4だった。LLaMA-3-8B-Instructでもfull KVの42.7に対し、0.11×で41.9である。

特に1-bit KIVI単体では大きく品質が落ちる条件でも、CPU上の16-bit正本からtop-kを戻すことで多くを回復している。

したがって「10×圧縮でも品質を保つ」という結果は、単純に1-bit化が高精度だからではない。**低ビット全体 + クエリごとに選び直す16-bit top-k**という組合せが効いている。

### throughput: 長contextほどVRAM節約がbatch sizeに効く

Mistral-7B-Instruct-v0.2、単一A6000でのデコード スループットは次の通り。

| Context | Full KV | SpeCache 2-bit | SpeCache 1-bit |
|---|---:|---:|---:|
| 2k | batch 44 / 190.3 | batch 272 / 418.5（2.2×） | batch 410 / 526.3（2.8×） |
| 8k | batch 11 / 47.0 | batch 82 / 133.7（2.8×） | batch 134 / 177.7（3.8×） |
| 32k | batch 3 / 10.3 | batch 22 / 34.6（3.4×） | batch 36 / 47.3（4.6×） |

ここで重要なのは、**4.6×は単一要求の1 トークン 遅延が4.6×速くなったという意味ではない**ことである。KVのGPU占有量を減らして同時バッチを大幅に増やせたことが主なスループット改善要因である。

### 転送profiling

32k 文脈のMistral-7B-Instruct-v0.2では、top-1% KVだけを転送することで全KV転送より約95%短いtransfer 遅延を得た。非連続領域のscatter的な転送は連続転送より遅いものの、転送量削減の方が大きく効くという結果である。

## 既存研究との差

### eviction / mergingとの違い

H2OやStreamingLLMなどはGPUからKVを削除して容量を減らす。将来そのKVが重要になっても、正本が残っていなければ元に戻せない。

SpeCacheはCPUに全16-bit正本を残すので、クエリが変われば別のKVを次ステップで再取得できる。**固定されたキャッシュ内容ではなく、クエリごとにGPU上の高精度KV集合を入れ替える**点が中心差分である。

### 単純offloadとの違い

単純オフロードは容量問題を解けても、毎ステップ大量のKVをCPU→GPU転送するため遅い。SpeCacheはアテンション 疎性で転送対象を絞り、さらに投機トークンでその転送を1 ステップ先行させる。

### 純粋なKV量子化との違い

KIVIなどはGPU上のKV自体を低bit化して容量を減らす。SpeCacheでは低ビット KVを残しつつ、重要部分だけCPUの16-bit正本で差し替えるため、極端な量子化時の品質低下を補いやすい。

## 一般的な実装への示唆

SpeCacheから得られる一般化しやすい設計原則は、**低精度表現を最終データとしてだけでなく、高精度な下位階層データを検索するメタデータとして使う**ことである。

GPUには「全履歴の粗い地図」を置き、CPUには「完全な詳細データ」を置く。各ステップで地図から必要箇所を予測し、詳細データだけを先読みする。この構造はKV キャッシュに限らず、GPU/CPU/SSDの階層メモリを使う推論にも応用可能な考え方である。

また、オフロード系では転送量だけでなく**転送開始時刻**が重要である。同じbytesを運ぶ場合でも、必要になってから運ぶのか、1 段階前から予測して運ぶのかで重要な 経路への影響が変わる。

## 限界・注意点

- CPUには全16-bit KVを保持するため、GPU VRAMの代わりに大容量CPU DRAMが必要になる。
- GPU上のアテンションはtop-k以外を低ビットで扱うので、full 16-bit推論と数学的に完全一致する無損失方式ではない。
- 投機トークンが次のクエリのアテンション先をうまく予測できない場合、重要KVを16-bitで先読みできず品質または効率が落ちる。
- 疎 KVは非連続メモリ転送になりやすく、framework側のgather/scatter オーバーヘッドがある。論文では転送量削減がこれを上回る条件を示している。
- スループットの主な実機評価は単一NVIDIA A6000とMistral-7B-Instruct-v0.2であり、PCIe世代、CPU メモリ 帯域、GPU、モデル architectureが変われば最適top-kや重複実行可能量も変わる。
- 推論提供全体の要求 スケジューリングやmulti-GPU クラスタ load balancingは主題ではない。
