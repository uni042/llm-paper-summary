# Prompt Cache: Modular Attention Reuse for Low-Latency Inference

> 複数要求で再利用されるプロンプト断片のKV状態をモジュール単位で事前計算し、位置整合を保って合成することで初回トークン遅延を削減する。
## 書誌情報
- **著者**: In Gim, Guojun Chen, Seung-seob Lee, Nikhil Sarda, Anurag Khandelwal, Lin Zhong
- **公開**: Proceedings of Machine Learning and Systems 6 (MLSys 2024)
- **種別**: conference
- **対象**: KVキャッシュ、プリフィル、プロンプト再利用、低遅延推論
- **実装**: HuggingFace Transformers上の約3千行のPython試作実装。Llama2、Falcon、MPT等で離散位置IDを扱うため各モデル約20行程度の変更を加え、CPU DRAMとGPU HBMの両方へモジュールを保存できる。
## 概要
LLMサービスではシステム指示、文書、テンプレートなど同じ文章断片が要求をまたいで繰り返されるが、通常のKVキャッシュは単一要求内のデコード再利用に留まり、次の要求では長い入力を再びプリフィルする。Prompt キャッシュは再利用部分をプロンプトモジュールとして明示し、そのKV注意状態を事前計算してCPUまたはGPUメモリへ保存する。要求時には必要なモジュールの状態と未キャッシュ部分だけの新規計算を結合し、先頭トークン生成までの計算を減らす。位置依存KVを安全に再利用するため、プロンプトマークアップ言語で各モジュールへ固定位置IDを割り当て、離散的な位置IDを保ったまま複数モジュールを組み合わせる。

Prompt キャッシュは要求間のKV再利用を明示的なプロンプト構造へ変換する。再利用したい文章をプロンプトモジュールとしてスキーマに定義し、各モジュールへ将来の要求でも変わらない位置IDを割り当ててKV状態を事前計算する。さらに、相対位置を保てば位置IDに空隙があってもモデル品質が大きく崩れないという観測を利用し、要求ごとに必要なモジュールだけを選択・連結できるようにした。

代表結果として、GPU TTFT高速化はLlama2 7B、LongBench平均約5Kトークン、RTX 4090/A40/A100で通常KVキャッシュに対してGPUメモリ保存で5〜10倍、CPUメモリ保存で1.5〜3倍。キャッシュ済みKVをGPUから直接読む構成が上限、CPUから転送する構成が下限に相当し、再計算削減が転送費を上回る。
## 問題設定
通常のKVキャッシュは、ある要求のプリフィルで計算したキー・値状態を同じ要求の後続デコードで再利用するため、要求をまたぐ重複計算は残る。実サービスではシステム指示、共通文書、テンプレートなど数千トークンの同じ文章が別要求に繰り返し現れ、そのたびに注意状態を再計算することが先頭トークン時間のボトルネックになる。既存の同一接頭辞共有だけでは、共通文書が入力途中に現れる場合や複数文書から必要な組合せだけを選ぶ場合を扱いにくい。さらにKVは位置符号化を含むため、文章が同じでも別の位置へ移せば計算済み状態をそのまま流用できず、類似度検索だけでは正しい位置と再利用対象の識別を同時に保証できない。したがって、再利用断片を明示し、要求ごとの組合せ変更を許しながら位置整合を保つ仕組みが必要になる。
## 新規性
Prompt キャッシュは要求間のKV再利用を明示的なプロンプト構造へ変換する。再利用したい文章をプロンプトモジュールとしてスキーマに定義し、各モジュールへ将来の要求でも変わらない位置IDを割り当ててKV状態を事前計算する。さらに、相対位置を保てば位置IDに空隙があってもモデル品質が大きく崩れないという観測を利用し、要求ごとに必要なモジュールだけを選択・連結できるようにした。
## 手法
### 手法のあらまし
入力から生成までの流れは、スキーマ定義、事前符号化、要求の具体化、KV合成、先頭トークン生成、通常デコードの六段階である。第一に、利用者はプロンプトマークアップ言語（Prompt Markup Language; PML）で、システム指示、共有文書、テンプレートなど再利用する文章を名前付きプロンプトモジュールとしてスキーマへ登録する。スキーマ内の順序と各モジュールの最大長から、それぞれが占有する位置ID範囲を固定する。第二に、サーバはモジュールのトークン列をその固定位置IDとともに対象LLMへ入力し、全Transformer層でキー・値状態を一度計算する。得られたKVをGPU HBMへ置けば低遅延で再利用でき、CPU DRAMへ置けば容量を増やせる代わりに利用時の転送が必要になる。第三に、新しい要求は同じスキーマを参照し、必要なモジュール名と、パラメータ値、要求固有の自由文を指定する。サーバはモジュール名から保存済みKVを直接取得し、可変パラメータと自由文だけを対象LLMで新規計算する。第四に、キャッシュ済みKVと新規KVを各トークンの固定位置ID順に並べ、要求全体を表すKVキャッシュを組み立てる。モジュールを省略した場所は位置IDの空隙として残るが、選択されたモジュールの位置IDは事前符号化時から変わらないため保存状態を再利用できる。第五に、この合成KVを過去文脈として対象LLMへ渡し、未キャッシュ部分に必要な注意計算だけで先頭トークンを生成する。共通長文のプリフィルを繰り返す代わりに、主な費用をKVのメモリ読み出しと未キャッシュ部分の計算へ置き換えることがTTFT短縮の直接要因である。第六に、先頭トークンが出た後は通常のKVキャッシュと同じく新しいトークンのKVを一つずつ追加してデコードするため、後続トークン当たりの計算量は減らない。したがって本方式が最も効くのは、長い共通入力が頻繁に再利用され、生成長に対してプリフィル遅延の比率が大きいワークロードである。

### PMLスキーマと固定位置ID
再利用可能な文章を名前付きモジュールとして宣言し、スキーマ内の位置に基づく固定位置ID領域をあらかじめ確保する。要求側はモジュール名を指定するだけなので、サーバは入力文字列から類似断片を探索せずキャッシュ位置を直接特定できる。排他的な候補はunionとして同じ開始位置を共有し、入れ子モジュールで階層構造も表現する。要求ごとに一部モジュールを省略して位置IDに空隙ができても、選ばれたモジュール自身の位置IDは符号化時から変わらないため、保存済みKVを再計算せず利用できる。代償として利用者またはプロンプト生成系がスキーマ構造を準備する必要がある。

### パラメータ化モジュール
テンプレート全体を毎回別モジュールにせず、可変部分だけを最大トークン長付きパラメータとして予約する。例えば共通の旅行計画テンプレートで日数だけが変わる場合、日数の位置をパラメータ領域として確保し、それ以外の固定文章をキャッシュ対象にする。事前符号化ではパラメータ領域へ所定長の空白相当トークンを置いて後続文章の位置IDを固定し、固定文章部分のKVを保存する。実行時には実際の日数や利用者属性などの値だけをその予約位置へ入れて新規にKVを計算し、前後のキャッシュ済み状態と位置順に結合する。この設計により、文章の大半が共通で一部だけ変化する要求を別々の完全プロンプトとして再計算せずに済み、再利用率を高く保てる。パラメータ値が予約した最大トークン長を超えると後続モジュールの固定位置と衝突するため、その場合はより大きい予約領域を持つスキーマへ変更する必要がある。予約領域を過大にすると利用可能な位置IDを浪費するので、柔軟性と文脈長の間に設計上の交換関係がある。

### モジュール符号化とキャッシュ推論
モジュールが初めて必要になった時、サーバはそのトークン列を固定位置ID付きでLLMへ通し、各層のキー・値状態をCPUまたはGPUメモリへ保存する。要求時には選択モジュールのKVを読み出し、未キャッシュ文章だけを通常どおりプリフィルして得たKVと連結する。GPU保存ならデバイス内コピー中心で低遅延だが容量が限られ、CPU保存なら大容量を使える代わりにホスト・デバイス転送が発生する。長文では自己注意を再計算する費用が転送費より速く増えるため、共通文脈が長いほど再利用の利得が大きくなる。キャッシュされない割合が高い場合は利得が縮む。

### 離散位置ID対応
モジュールを抜き差しすると位置IDが連続しなくなるため、既存Transformersの位置符号化を小規模に変更する。RoPEでは位置ごとの回転行列を位置IDで参照できる表として用意し、ALiBiでは同様にバイアス行列を指定位置へ対応させる。これにより、例えば前のモジュールを省略しても後続モジュールを元のスキーマ位置のまま処理でき、符号化済みKVを再利用できる。論文の観測では相対位置を保った離散位置IDで品質は概ね維持されるが、モジュール独立符号化はモジュール外への注意を省く近似なので、すべてのタスクで出力同一を保証するわけではない。

### 全体のデータ／制御の流れ
試作はHuggingFace TransformersとPyTorch上に実装される。CPUとGPUの二階層にキャッシュを置けるが、置換・プリフェッチ方針は本論文の対象外である。PyTorchの通常連結が毎回新規メモリを確保する問題に対して再利用可能なバッファ連結を実装する。同じモジュールを含む複数要求をバッチ処理する場合は、PagedAttention型のポインタ共有と組み合わせればKV重複を減らせる。
## 評価条件
- **ハードウェア**: CPUはIntel i9-13900K＋128GB DDR5-5600とAMD Ryzen 9 7950X＋128GB DDR4-3600。GPUはRTX 4090、NVIDIA A40、A100で、A40/A100ノードは16コアAMD EPYC 7763と224GB RAMを備える。GPU評価は単一GPU 40GB以内に収まるモデルを使う。
- **ソフトウェア**: HuggingFace Transformers/PyTorch上の約3千行の試作。Llama2、CodeLlama、MPT、Falconを使用し、通常KVキャッシュを比較対象とする。CPUメモリ保存とGPUメモリ保存の両構成を評価する。
LongBenchの21データセット・6カテゴリから4K〜10K文脈を使い、文書部分をキャッシュ対象モジュール、タスク固有指示を未キャッシュ部分として設定する。先頭トークン時間（TTFT）を通常KVキャッシュと比較し、GPUではCPUメモリ保存とGPUメモリ保存、CPU推論ではCPUメモリ保存を測る。品質はLlama2、MPT、Falconで決定論的生成を用い、F1、ROUGE-L、正解率などLongBench指標を比較する。合成入力では文脈長とモデルサイズに対する計算・転送費の伸びを調べる。
主評価はプリフィル相当のTTFT短縮であり、先頭トークン後のデコード時間は通常KVキャッシュと同じ。単一GPUに収まるモデルと長文ベンチマークを中心とし、大規模分散サービングや動的キャッシュ置換は評価対象外である。コード生成、個人化、パラメータ化テンプレートの事例も示す。
## 主要結果
Prompt キャッシュは長い共通入力を再計算せずKV状態を読み出すことでTTFTを大幅に短縮する。LongBench平均約5KトークンではGPUメモリ保存時5〜10倍、CPUメモリからGPUへ転送する場合でも1.5〜3倍の短縮を示す。CPU推論では注意計算が相対的に高価なため最大70倍まで改善した。一方、デコード時間自体は変わらず、長い出力ではエンドツーエンド改善率が小さくなる。

- GPU TTFT高速化 / GPUメモリ保存で5〜10倍、CPUメモリ保存で1.5〜3倍 (比較対象: 通常KVキャッシュ; 条件: Llama2 7B、LongBench平均約5Kトークン、RTX 4090/A40/A100) — キャッシュ済みKVをGPUから直接読む構成が上限、CPUから転送する構成が下限に相当し、再計算削減が転送費を上回る。

- CPU TTFT高速化 / Intelで最大70倍、AMDで最大20倍 (比較対象: 通常KVキャッシュ; 条件: Llama2 7B、LongBench、i9-13900KとRyzen 9 7950X) — CPUでは長文注意計算が高価なため、メモリコピーへ置き換える効果がGPUより大きい。

- 3K文脈のTTFT / 900 msから90 ms (比較対象: 通常KVキャッシュ; 条件: RTX 4090、Llama2 7B、3K文脈) — TTFTは約10倍短縮する一方、後続トークン時間は双方約32 msで同じ。

- KV保存メモリ / Llama 7Bで0.50 MB/トークン、Llama 70Bで2.5 MB/トークン (比較対象: なし; 条件: 16-bit KV状態) — 大規模モデルでは1Kトークンのモジュールだけで数GBとなり、GPUだけで多数モジュールを保持するのは難しい。

- コード生成事例 / GPU TTFT 4倍改善 (比較対象: 通常生成; 条件: CodeLlama 7B、複数ソースファイルをモジュール化) — 構造化された再利用文脈を複数組み合わせる用途でも出力を保ったまま高速化できる。

### 負の結果・境界条件
- Prompt キャッシュが直接減らすのは先頭トークンまでの入力計算で、後続デコードのトークン時間は変わらない。そのため生成トークン数が多いほど総応答時間に占める効果は薄まる。CPU保存はGPU保存よりホスト・デバイス転送が増え、キャッシュされない文章比率が高いデータでは改善も小さい。さらにKV保存量はモデル規模とキャッシュトークン数に比例し、Llama 70Bでは1Kトークン当たり約2.5GBとなる。

### 結果の読み方
通常プリフィルの自己注意計算は文脈長に対して二次的に増えるのに対し、キャッシュKVのメモリコピーは線形に増えるため、長い共通文脈ほど差が広がる。大きいモデルでも注意計算量の増加に対してコピー増加は小さく、再利用率が高いサービスほど有利になる。
## 品質への影響
モジュールを独立に符号化するためモジュール外への注意を省く近似は入るが、LongBenchのLlama2、MPT、Falconでは多くの指標が比較対象と近く、論文は全体として精度を維持すると評価する。ただしPassage Retrievalなど個別条件では数ポイントの低下も見られるため完全な数値同一性を保証する方式ではない。
## 既存研究との差
PagedAttentionの接頭辞共有は同一先頭部分の再利用が中心だが、Prompt キャッシュは固定位置IDと明示スキーマにより途中の複数断片を選択して組み合わせる。AttMemo型の類似度検索とは異なり、再利用対象を利用者がモジュールとして明示するため検索誤判定を避ける。KV圧縮・枝刈り方式が単一要求のキャッシュ量を減らすのに対し、本方式は要求間で計算済みKVそのものを共有し、主にプリフィル計算を省く。
## 限界
効果は同じ文章断片が複数要求で再利用されることを前提とし、ほぼ全入力が毎回異なる場合はキャッシュ機会が少ない。TTFTのみを直接削減し、通常デコードの計算量は変えない。KV状態の保存量はモデル規模に比例して大きく、GPU容量だけで多数の長文モジュールを保持するのは難しい。CPU保存ではホスト・デバイス転送が必要である。論文はGPU/CPU間の置換、プリフェッチ、圧縮を将来課題としており、大規模な実運用キャッシュ管理は未解決である。またモジュール独立符号化は注意範囲を制限する近似で、全タスクで厳密に同一出力を保証しない。
## 実装状態
著者コードと評価データが公開され、HuggingFace Transformers/PyTorch上の約3千行の試作として実装済み。Llama2、Falcon、MPTの位置符号化へ離散位置ID対応を加え、CPU/GPU双方のキャッシュ保存を実装する。論文時点では本格的な置換・先読みポリシーを備えたサービング基盤ではなく、モジュール再利用機構の試作である。
## 研究上の位置づけ
要求間KV再利用を、単純な共通接頭辞から構造化された任意の共通文脈へ拡張した初期のサービング研究として位置付けられる。長文RAG、共通システム指示、テンプレート、共有文書のようにプリフィル重複が大きいワークロードで、CPU/GPU階層キャッシュやPagedAttentionと組み合わせる基盤要素を提示した。後続のプロンプトキャッシュや文脈ロード高速化研究と比較する際は、TTFT削減とキャッシュ容量・転送の交換関係を明示した点が重要である。
