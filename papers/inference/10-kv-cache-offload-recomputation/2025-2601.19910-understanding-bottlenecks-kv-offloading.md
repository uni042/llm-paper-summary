# Understanding Bottlenecks for Efficiently Serving LLM Inference With KV Offloading

> KV再利用で省いたプリフィル計算と、CPUから戻すKV転送をH100実測・式で比較し、キャッシュ量が増えるといつPCIeが律速へ逆転するかを明らかにする分析。

## 概要

H100×8・PCIe 5.0×16とLMCacheでLlama-3.1-70B/Qwen3-235B-A22Bを実測し、PCIe継続帯域は公称64GB/sに対し15GB/s、κcritはLlama約14.3→3.3、Qwen約7.8→1.8へ下がった。ShareGPT/NarrativeQA/FinQAの中央値κ比率は約100/5000/10000、Qwenの65K cached＋64 newでは転送が計算の86倍で実行時間の約99%を占め、再利用計算を省いてもPCIeが律速になることを示した。

本研究は新しいKV オフロード ランタイムを提案するのではなく、**CPU DRAMからKVを戻す費用が、prefix キャッシュで節約したプリフィル計算をいつ上回るのか**を定量化する。

prefix キャッシュでは過去のKVを再利用して新規suffixだけを計算できる。しかしKVをCPUへオフロードすると、cached トークンが多いほどPCIe 転送が増える。document QAや長いmulti-turn conversationでは「計算する新規トークンは少ないのに、読み戻すcached KVは非常に多い」という状態になり、従来計算-上限と考えられていたプリフィル自体がメモリ-上限へ変わる。

論文はこの境界を`κcrit`という指標で表し、ShareGPT / NarrativeQA / FinQA等のワークロードとH100実機で検証する。

## 手法・分析枠組み

### 1. 「戻すcached token数 ÷ 新規計算token数」をκratioとする

CPU DRAMから戻すcached トークン数を`K`、GPUで新規にプリフィルするトークン数を`T`として、

`κratio = K / T`

を定義する。

κ比率が大きいほど、1 トークン分の新規計算に対して多くのKV データをPCIeで運ぶ必要がある。

例えばκ比率=100なら、1 トークンを新しく計算する間に100 トークン分の過去KVを読み戻す構図になる。

### 2. 「転送の方が計算より遅くなる境界」をκcritとする

1 new トークンのプリフィル FLOPsを`Fpf`、1 cached トークンあたりのKV バイト量を`Bkv`、実効GPU 計算を`Ceff`、ホスト→GPU 帯域を`BW`とすると、

`κcrit = (Fpf / Bkv) × (BW / Ceff)`

と表せる。

`κratio > κcrit`ならKV 転送時間がGPU 計算時間を上回り、プリフィルは「計算待ち」ではなく**データ転送待ち**になる。

この式を、

- **モデル 要因:** 1 トークンを計算する仕事量に対してKVが何バイトあるか
- **ハードウェア 要因:** GPUの計算速度に対してCPU→GPU転送がどれだけ速いか

へ分けられるため、モデル アーキテクチャと接続網を独立に比較できる。

### 3. Model architectureごとのKV負荷を比較する

密 / MoE、GQA / MLAで`Fpf / Bkv`が大きく変わる。

たとえばDeepSeek-V3はMLAによってKV 占有量が約70KB/トークンなのに対し、Qwen3-235B-A22Bは約192KB/トークンで、DeepSeek-V3の方がオフロード ボトルネックに耐えやすい。

ただし実ワークロードのκ比率は100〜数千になるため、MLAでKVを圧縮してもPCIe ボトルネックそのものは消えないと分析する。

## 評価

### 実機条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA H100 SXM5 80GB ×8 |
| CPU | AMD EPYC 7R13 48 コア |
| ホスト メモリ | DDR4-3200 2TB |
| CPU-GPU | PCIe 5.0 x16 |
| ランタイム | vLLM 0.10.1 + LMCache 0.3.5 |
| モデル | Llama-3.1-70B、Qwen3-235B-A22B |
| ワークロード | ShareGPT、NarrativeQA、FinQA / 合成 |

分析ではB200、A100、DeepSeek-V3等も理論性能モデルで比較しているが、主要な実測はH100 システムで行う。

### PCIeの公称帯域だけを見ると大きく楽観視する

PCIe 5.0の理論ホスト→端末帯域64GB/sを使うと、κcritはLlamaで約14.3、Qwenで約7.8と見積もられる。

しかし実際に測定した継続転送帯域は**15GB/s**で、peakの約23%しかない。これを使うとκcritはLlama約3.3、Qwen約1.8となり、実測されたメモリ-上限遷移に近づく。

つまりKV オフロード設計ではspec sheetのPCIe 帯域ではなく、NUMA、コピー オーバーヘッド、転送粒度を含む**実際に継続して出せる帯域**を使わないと性能予測を大きく誤る。

### 実workloadはκcritを大きく超える

論文が調べた中央値では、

- ShareGPT: κ比率 ≈ 100
- NarrativeQA: κ比率 ≈ 5000
- FinQA: κ比率 ≈ 10000

となり、多くのハードウェア / モデル構成のκcritより1〜数桁大きい。

Qwenで65K cached トークン + 64 new トークンの条件では、PCIe オーバーヘッドがプリフィル 計算の**86倍**となり、実行時間の約99%が転送に費やされた。

### GPU utilization / power

KV-オフロード済み ワークロードではGPUがデータ待ちになるため、GPUの消費電力は最大TDPの約22〜28%に留まった。高価なGPU 計算がほぼidleになっていることを、遅延だけでなくpower面からも示している。

## 設計上の示唆

### Faster interconnect

NVLink C2Cのような高速CPU-GPU 接続網はκcritを大きく引き上げる。論文のモデルではGB200 / NVLink C2CでPCIe 5.0比**約5.3×**改善する。

さらにCPU / GPUが実質的に同じHBM 共有領域を共有する理想的な共有-HBM構成では、NVLink C2Cからさらに約9×の余地を示す。ただしこれは将来アーキテクチャのモデル評価であり、実機結果ではない。

### Model architecture

MLAなどで1 トークンあたりのKV バイト量を減らすと、メモリ-上限になる境界を後ろへずらせる。DeepSeek-V3はGQA系MoEよりメモリ-上限への遷移を遅らせるが、典型的なdocument ワークロードでは依然として帯域不足になる。

### Scheduler

既存iteration-水準 スケジューラは「トークン数」を予算として扱うが、オフロード済み KV リクエストでは1 トークンでも転送 費用が大きく異なる。

そのためスケジューラは新規トークン数だけでなく、**そのリクエストが何バイトのcached KVを読み戻すか**まで考えてリクエストを組み合わせるべきだと提案する。

## 既存研究との差

### DirectKV / Pie / SuperInferとの違い

DirectKV、Pie、SuperInferはそれぞれ「CPU上のKVを直接読む」「必要になる前にGPUへ戻す」「SLOに応じてKVを入れ替える」といった方法でKV 転送を速くするランタイムである。

本研究は個別の解法ではなく、**そもそもcached KVが新規計算量の何倍になると既存オフロード方式がI/O-上限になるかを予測する共通評価軸**を与える。

### KV compressionとの違い

KV量を減らす手法自体を提案しない。MLA等によるKV バイト削減を式へ入れて、「どれほど圧縮すればボトルネックがどこまで遅れるか」を比較できる。

## 限界

- 新しいランタイム / スケジューラのエンドツーエンド実装を提示する論文ではなく、主貢献は分析とcharacterization。
- 実機評価はH100 + PCIe 5.0中心で、GH200 / GB200 C2Cの数値は主にanalytical モデルによる予測。
- DeepSeek-V3のMLAは実装オーバーヘッドのため実機characterizationを十分に行えておらず、モデル-水準比較の一部は理論値。
- sustained PCIe 帯域はシステム 構造やNUMA、ソフトウェア stackに依存するため、15GB/sという値を他環境へそのまま一般化できない。
- ワークロードのprefix 再利用分布が変わればκ比率も大きく変わる。
- 2026-09-06時点で公式code repositoryは確認できなかった。

## 一般的な実装上の含意

KV オフロードを導入する際は「VRAMに収まるか」だけでなく、**cached トークン数 / 新規計算トークン数と実効接続網 帯域の比**を先に測るべきである。

特にprefix 再利用率が高いRAG / document QA / long conversationでは、計算を節約するほど逆にデータ 転送比率が上がり、GPU 計算が余ることがある。KV 再利用・オフロード・スケジューラを別々に最適化するのではなく、一つのI/O/計算 均衡として扱う必要がある。
