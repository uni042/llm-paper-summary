# Understanding Bottlenecks for Efficiently Serving LLM Inference With KV Offloading

> CPUから戻すcached KVの量が、新しく計算するprefill token量に対してどれくらい増えるとPCIe転送の方がGPU計算より遅くなるかを式とH100実測で示し、prefix reuseが多いほどKV offloadが早くI/O律速になることを分析した研究。

## 概要

本研究は新しいKV offload runtimeを提案するのではなく、**CPU DRAMからKVを戻すcostが、prefix cacheで節約したprefill計算をいつ上回るのか**を定量化する。

prefix cachingでは過去のKVを再利用して新規suffixだけを計算できる。しかしKVをCPUへoffloadすると、cached tokenが多いほどPCIe transferが増える。document QAや長いmulti-turn conversationでは「計算する新規tokenは少ないのに、読み戻すcached KVは非常に多い」という状態になり、従来compute-boundと考えられていたprefill自体がmemory-boundへ変わる。

論文はこの境界を`κcrit`という指標で表し、ShareGPT / NarrativeQA / FinQA等のworkloadとH100実機で検証する。

## 手法・分析枠組み

### 1. 「戻すcached token数 ÷ 新規計算token数」をκratioとする

CPU DRAMから戻すcached token数を`K`、GPUで新規にprefillするtoken数を`T`として、

`κratio = K / T`

を定義する。

κratioが大きいほど、1 token分の新規計算に対して多くのKV dataをPCIeで運ぶ必要がある。

例えばκratio=100なら、1 tokenを新しく計算する間に100 token分の過去KVを読み戻す構図になる。

### 2. 「転送の方が計算より遅くなる境界」をκcritとする

1 new tokenのprefill FLOPsを`Fpf`、1 cached tokenあたりのKV byte量を`Bkv`、実効GPU computeを`Ceff`、host→GPU bandwidthを`BW`とすると、

`κcrit = (Fpf / Bkv) × (BW / Ceff)`

と表せる。

`κratio > κcrit`ならKV transfer時間がGPU compute時間を上回り、prefillは「計算待ち」ではなく**data転送待ち**になる。

この式を、

- **model factor:** 1 tokenを計算する仕事量に対してKVが何byteあるか
- **hardware factor:** GPUの計算速度に対してCPU→GPU転送がどれだけ速いか

へ分けられるため、model architectureとinterconnectを独立に比較できる。

### 3. Model architectureごとのKV負荷を比較する

Dense / MoE、GQA / MLAで`Fpf / Bkv`が大きく変わる。

たとえばDeepSeek-V3はMLAによってKV footprintが約70KB/tokenなのに対し、Qwen3-235B-A22Bは約192KB/tokenで、DeepSeek-V3の方がoffload bottleneckに耐えやすい。

ただし実workloadのκratioは100〜数千になるため、MLAでKVを圧縮してもPCIe bottleneckそのものは消えないと分析する。

## 評価

### 実機条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA H100 SXM5 80GB ×8 |
| CPU | AMD EPYC 7R13 48 cores |
| Host memory | DDR4-3200 2TB |
| CPU-GPU | PCIe 5.0 x16 |
| Runtime | vLLM 0.10.1 + LMCache 0.3.5 |
| Models | Llama-3.1-70B、Qwen3-235B-A22B |
| Workloads | ShareGPT、NarrativeQA、FinQA / synthetic |

分析ではB200、A100、DeepSeek-V3等も理論性能モデルで比較しているが、主要な実測はH100 systemで行う。

### PCIeの公称帯域だけを見ると大きく楽観視する

PCIe 5.0の理論host→device帯域64GB/sを使うと、κcritはLlamaで約14.3、Qwenで約7.8と見積もられる。

しかし実際に測定した継続転送帯域は**15GB/s**で、peakの約23%しかない。これを使うとκcritはLlama約3.3、Qwen約1.8となり、実測されたmemory-bound遷移に近づく。

つまりKV offload設計ではspec sheetのPCIe bandwidthではなく、NUMA、copy overhead、transfer粒度を含む**実際に継続して出せる帯域**を使わないと性能予測を大きく誤る。

### 実workloadはκcritを大きく超える

論文が調べた中央値では、

- ShareGPT: κratio ≈ 100
- NarrativeQA: κratio ≈ 5000
- FinQA: κratio ≈ 10000

となり、多くのhardware / model構成のκcritより1〜数桁大きい。

Qwenで65K cached tokens + 64 new tokensの条件では、PCIe overheadがprefill computeの**86倍**となり、実行時間の約99%がtransferに費やされた。

### GPU utilization / power

KV-offloaded workloadではGPUがdata待ちになるため、GPUの消費電力は最大TDPの約22〜28%に留まった。高価なGPU computeがほぼidleになっていることを、latencyだけでなくpower面からも示している。

## 設計上の示唆

### Faster interconnect

NVLink C2Cのような高速CPU-GPU interconnectはκcritを大きく引き上げる。論文のmodelではGB200 / NVLink C2CでPCIe 5.0比**約5.3×**改善する。

さらにCPU / GPUが実質的に同じHBM poolを共有する理想的なunified-HBM構成では、NVLink C2Cからさらに約9×の余地を示す。ただしこれは将来architectureのmodel評価であり、実機結果ではない。

### Model architecture

MLAなどで1 tokenあたりのKV byte量を減らすと、memory-boundになる境界を後ろへずらせる。DeepSeek-V3はGQA系MoEよりmemory-boundへの遷移を遅らせるが、典型的なdocument workloadでは依然として帯域不足になる。

### Scheduler

既存iteration-level schedulerは「token数」をbudgetとして扱うが、offloaded KV requestでは1 tokenでもtransfer costが大きく異なる。

そのためschedulerは新規token数だけでなく、**そのrequestが何byteのcached KVを読み戻すか**まで考えてrequestを組み合わせるべきだと提案する。

## 既存研究との差

### DirectKV / Pie / SuperInferとの違い

DirectKV、Pie、SuperInferはそれぞれ「CPU上のKVを直接読む」「必要になる前にGPUへ戻す」「SLOに応じてKVを入れ替える」といった方法でKV transferを速くするruntimeである。

本研究は個別の解法ではなく、**そもそもcached KVが新規計算量の何倍になると既存offload方式がI/O-boundになるかを予測する共通評価軸**を与える。

### KV compressionとの違い

KV量を減らす手法自体を提案しない。MLA等によるKV byte削減を式へ入れて、「どれほど圧縮すればbottleneckがどこまで遅れるか」を比較できる。

## 限界

- 新しいruntime / schedulerのend-to-end実装を提示する論文ではなく、主貢献は分析とcharacterization。
- 実機評価はH100 + PCIe 5.0中心で、GH200 / GB200 C2Cの数値は主にanalytical modelによる予測。
- DeepSeek-V3のMLAは実装overheadのため実機characterizationを十分に行えておらず、model-level比較の一部は理論値。
- sustained PCIe bandwidthはsystem topologyやNUMA、software stackに依存するため、15GB/sという値を他環境へそのまま一般化できない。
- workloadのprefix reuse分布が変わればκratioも大きく変わる。
- 2026-09-06時点で公式code repositoryは確認できなかった。

## 一般的な実装上の含意

KV offloadを導入する際は「VRAMに収まるか」だけでなく、**cached token数 / 新規計算token数と実効interconnect bandwidthの比**を先に測るべきである。

特にprefix reuse率が高いRAG / document QA / long conversationでは、計算を節約するほど逆にdata transfer比率が上がり、GPU computeが余ることがある。KV reuse・offload・schedulerを別々に最適化するのではなく、一つのI/O/compute balanceとして扱う必要がある。
