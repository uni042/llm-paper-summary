# CacheFlow: Efficient LLM Serving with 3D-Parallel KV Cache Restoration

> 以前処理した長いプレフィックスのKVキャッシュがGPU外に退避されているとき、全部をI/Oで戻すか全部を再計算するかの二択にせず、プレフィックスの一部はGPUで再計算し、別部分は外部メモリから読み戻して同時進行させる手法。さらにこの分担をトークン方向だけでなく層方向・複数GPU方向にも広げ、同じバッチ内の複数要求がGPU計算資源とI/O帯域を奪い合う状況までまとめてスケジュールする。

- **実装**: vLLMとLMCacheを基盤に実装して評価。arXiv v1時点で独立した公式コードリポジトリは確認できない。

## 概要

CacheFlowが扱うのは、**「前に一度計算した長い文脈をもう一度使いたいが、そのKVキャッシュはGPUメモリから追い出されている」**という状況である。

LLMは入力処理（プリフィル）を行うと、各層・各トークンについて注意機構（注意機構）で使うKey/Valueを計算し、**KVキャッシュ（KVキャッシュ）**として保存する。同じプレフィックスを後で再利用できれば、入力文を最初からモデルへ通す必要がない。

しかし長文のKVキャッシュは非常に大きい。多数ユーザー、RAG、長い対話、エージェント処理を同時に扱うとGPU HBMへ全部置いておけないため、CPUメモリや別のメモリ階層へ退避する。

その要求が再び来たとき、GPUでデコードを始めるにはKVを復元しなければならない。基本的な方法は二つある。

1. **読み戻す**: 退避しておいたKVをI/OでGPUへ戻す。
2. **再計算する**: 元のトークンをもう一度プリフィルし、KVをGPUで作り直す。

読み戻しはGPU計算を節約できるが、ネットワークやPCIeなどのI/O帯域が遅いと待ち時間が長い。再計算はI/Oを使わないが、長いプレフィックスほど注意機構計算が重くなる。

CacheFlowの発想は、どちらか一方を選ぶのではなく、**同じKV復元の中で両方を同時に進め、先に終わった側からプレフィックスを埋めていく**ことである。

さらに、この並列化を

- トークン方向
- Transformer層方向
- 複数GPU方向

の3次元へ広げる。論文が「3D-並列の 復元」と呼ぶのはこのためである。

## 問題設定

### なぜKVを読み戻すだけでは遅いのか

例えば30Kトークンのプレフィックスについて数GBのKVがCPU側にあるとする。GPUへ戻す時間は、ほぼ

`転送するKV量 ÷ 実効I/O帯域`

で決まる。

10 Gbps程度の経路なら、GPUの計算性能がどれだけ高くても、転送が終わるまで注意機構を始められない。KV 再利用のために保存したのに、復元I/Oが最初のトークンまでの時間を支配する。

この最初の出力までの時間を**最初のトークンまでの時間（Time To First Token; TTFT）**という。

### なぜ再計算だけでも遅いのか

KVを保存せず、プレフィックス トークンから再プリフィルすればI/Oは要らない。

しかしTransformerの注意機構では後ろのトークンほど参照する過去トークンが多くなる。単純化すると、プレフィックスの後半を再計算するほど注意機構の仕事が増える。

6K程度なら再計算が比較的安くても、30K、100Kと伸びると、GPU計算時間が急速に増える。

つまり、

- I/Oが遅い環境 → 再計算した方がよい部分がある
- 長いプレフィックス後半 → 再計算が高いのでKVを読んだ方がよい

という交差が生じる。

### 既存hybrid方式だけでは何が足りないのか

「リクエスト Aは全部読み戻す、リクエスト Bは全部再計算する」という要求単位の選択では粒度が粗い。

一つの長いリクエストの中でも、先頭トークンは再計算が比較的安く、後半トークンは高い。層ごとにも復元を分けられる。複数GPUでパイプライン 並列性を使うなら、それぞれのGPUは別のモデル shardを持つため、同時に復元できる余地がある。

CacheFlowは、この内部並列性をまとめて利用する。

## 手法のあらまし

最も直感的なのはトークン-wise方式である。

長い保存済みプレフィックスを小さな分割片へ分け、**先頭側からGPU再計算を進めるポインタ**と、**末尾側からKV読出しを進めるポインタ**を同時に動かす。

```text
prefix:
|----|----|----|----|----|----|----|----|
 ↑compute →                   ← I/O ↑
```

先頭側は再計算が比較的安い。末尾側は再計算すると注意機構 コストが大きいので、保存KVを読む価値が高い。両ポインタが出会えば全プレフィックスのKV復元が終わる。

短い系列では、このトークン方向分割だけでは十分な重畳時間が取れないため、層方向にも分ける。さらにパイプライン 並列性ではGPUごとに必要KVを独立復元できるよう、stage境界のhidden 活性値も保存する。

最後に複数リクエストが同時復元するときは、各リクエストが勝手に計算/I/Oを使わず、global スケジューラがどのリクエストへI/O帯域を与えるかを決める。

## 手法

### 1. Token-wise restoration — prefixの前半を再計算、後半を読み戻す

CacheFlowは保存済みプレフィックスを通常512トークン程度の分割片へ分割する。

前から進む計算 ポインタは、元トークンをGPUでプリフィルしてKVを作る。後ろから進むI/O ポインタは、退避先から保存済みKVをGPUへ読み戻す。

この二つは同時に進む。

なぜ逆方向なのかが重要である。

プレフィックスの先頭分割片を再計算するときは注意機構対象が短い。一方、プレフィックス末尾の分割片を再計算すると、それ以前の長い文脈すべてへ注意機構を計算する必要があるため高価になる。

したがって、

- **前半**: 再計算向き
- **後半**: I/O復元向き

という非対称性がある。

単純な「半分再計算・半分load」ではなく、計算とI/Oの進行速度に応じて境界が決まるため、どちらか一方が早く終わって遊ぶ時間を減らせる。

### 2. 再計算とI/Oを重ねるとはどういうことか

GPUがプレフィックス先頭をプリフィルしている間、I/O エンジンは別のKV 分割片をGPUメモリへ転送する。

二つが完全に別資源なら、例えば

- 再計算だけ: 300 ms
- I/Oだけ: 400 ms

を順番にやれば700 ms掛かるが、同時に走らせれば理想的には長い方の400 ms付近へ近づけられる。

実際にはPCIe、メモリ 帯域、CUDA実行などで競合するため完全には重ならない。それでもGPU利用率とI/O利用率を同時に高く保つことがCacheFlowの狙いである。

### 3. Layer-wise restoration — 短いsequenceでは層方向に並列化する

トークン方向の利点は、プレフィックスが十分長いほど大きい。短いプレフィックスでは分割片数が少なく、計算とI/Oを長時間重ねる余地がない。

そこでCacheFlowは別方式として、Transformerの**層方向（層方向）**にも分割する。

概念的には、

- GPU計算: 層 0側から必要KVを再計算
- I/O: 最終層側から保存KVを読み戻す

と進める。

トークン方向と同様、両側から仕事を進めて出会わせる。

どちらが有利かはプレフィックス長・GPU速度・I/O帯域に依存するため、事前測定で**交差長**を測り、短い系列では層方向、長い系列ではトークン方向を選ぶ。

### 4. Multi-GPU restoration — pipeline stageを順番待ちさせない

パイプライン並列処理（PP）では、モデルの層を複数GPUへ分ける。

通常の再計算では、GPU 1が前半層を計算し、そのhidden 活性値をGPU 2へ渡し、GPU 2が後半層を計算するという依存がある。KV 復元でもこの依存をそのまま辿ると、後段GPUは前段が終わるまで待つ。

CacheFlowはパイプライン stage境界の**hidden 活性値**も保存しておく。

そうすると各GPUは、前段を最初から再実行しなくても、自分のstage開始地点の活性値から自分のモデル shard用KVを復元できる。

これにより複数GPUがそれぞれ

- 自分のstageで再計算する
- 自分のKVをI/Oで読む

処理を同時に進められる。

これが3Dの3軸目、GPU方向の並列化である。

### 5. なぜhidden activationを追加保存する価値があるのか

KVだけ保存するより、stage境界活性値も保存すれば保存領域量は増える。

しかしその代わり、GPU間の逐次依存を切り、複数GPUを復元段階から並列稼働させられる。

つまりCacheFlowは、**少し追加状態を保存することで将来の復元並列性を買う**設計である。

これは「何をキャッシュするか」を単純な再利用率だけでなく、後の復元クリティカルパスまで考えて決める例でもある。

### 6. Batch-aware scheduler — 複数requestがI/Oを奪い合うときの優先順位

実際の提供処理では、一つのリクエストだけを復元するとは限らない。

複数リクエストが同時に戻ってくると、

- GPU 計算
- I/O 帯域

という二つの有限資源を共有する。

各リクエストが独立に「自分の後半KVをloadする」と決めると、I/Oが混雑し、結果として全リクエストのTTFTが悪化する場合がある。

CacheFlowのバッチ-aware スケジューラは、各リクエストの計算 ポインタとI/O ポインタをglobalに管理する。

特に、**これから再計算すると高価になる長いプレフィックス部分**へI/Oを優先する。短い・安い部分はGPUで再計算させ、I/O帯域は「再計算で代替しにくい部分」へ回す。

したがってスケジューラの役割は単なる公平配分ではなく、計算とI/Oの**機会費用**を比較して帯域を割り当てることである。

### 7. 3D-parallelの意味

論文の「3D」は、データ並列・テンソル並列のような一般的3D 並列性名称ではない。KV 復元を次の3軸へ分解する意味で使われる。

| 軸 | 並列化するもの | 目的 |
|---|---|---|
| Token | プレフィックスの前後分割片 | 再計算とI/Oを同時進行 |
| Layer | Transformer前後層 | 短い系列でも重畳余地を作る |
| GPU | パイプライン stages | 複数GPUの復元を独立化 |

その上にバッチ-aware スケジューリングがあり、複数リクエスト間の資源 共有を調整する。

## 評価

### まず見るところ

- **結論**: KV復元を全部load・全部再計算の二択にせず、計算とI/Oを同時に使うことでTTFTを10〜62%削減。
- **長文ほど効く**: 6K→30Kで比較対象との差が1.1倍→1.7倍へ拡大。
- **資源利用**: 復元中にGPU平均88%、I/O平均78%を同時利用。
- **multi-GPU**: GPU軸最適化を外すと0.21→0.29秒、38%悪化。
- **品質**: KV圧縮・枝刈りは行わず、保存KVまたは再計算KVを使うため直接のモデル品質trade-offはない。
- **注意**: 公式コード公開は確認できず、NVIDIA GPUと10〜80 Gbpsの評価範囲に依存する。

## 主要結果の読み方

CacheFlowの本質は、新しい圧縮方式ではなく**資源 重複実行**にある。

KVを保存しておくと「再計算しなくてよい」という利点があるが、保存場所がGPU外なら復元I/Oが必要になる。逆に再計算はI/Oを避けられるがGPUを使う。

この二つは別資源を使うので、どちらか一方を遊ばせるより同時に働かせた方がよい。

ただし単純に50/50へ分けるのではなく、トークン位置によって再計算コストが違い、系列長によって層方向との優劣が変わり、multi-GPUでは依存関係があり、バッチ内では帯域競合もある。

そのためCacheFlowは「hybrid 復元」を単なる比率調整ではなく、**トークン / 層 / GPU / リクエストの依存関係を持つスケジューリング問題**として扱っている。

## 品質への影響

KVを量子化、圧縮、トークン 枝刈りする方式ではない。

一部KVは保存済みの正確な KVを読み、一部は元トークンから通常のプリフィルで再計算する。したがって設計そのものがモデル意味論を近似するわけではなく、直接的な生成品質低下は導入しない。

## 既存研究との差

- **LMCache / HiCache**: KVをGPU外へ保存・復元するメモリ hierarchyが主眼。CacheFlowは復元時にGPU再計算も同時利用する。
- **Cake**: 計算/load hybridをトークン方向で行う考え方に近い。CacheFlowは層軸とmulti-GPU軸まで広げ、バッチ内資源 contentionも統合する。
- **HCache**: hidden 状態を使う復元と関連する。CacheFlowでは特にパイプライン stage境界活性値を保存し、GPUごとの独立復元へ使う。
- **Mooncake等の分離型 KV 転送**: KVを高速に移動する仕組みとは補完的。CacheFlowは「転送帯域が有限なとき、どこを転送しどこを計算するか」を決める。

## 限界

- 評価はNVIDIA L40S/A100/H100と10〜80 GbpsのI/O条件が中心で、別accelerator・保存領域階層への一般化は未検証。
- multi-GPUの理想的なscaleは均等partitionや十分な独立性を仮定し、実機ではstage imbalanceで弱まる。
- hidden 活性値を追加保存するため、KV-のみ キャッシュよりキャッシュ容量が増える。
- 計算とI/Oが実際にはメモリ 帯域等を共有する場合、理想的な重複実行は得られない。
- ワークロードによって保存済みプレフィックスの長さやバッチ構成が変わるため、最適なトークン/層分担も変化する。
- 公式コードリポジトリはarXiv v1時点で確認できない。

## 一般的な実装上の含意

階層メモリを使うLLM システムでは、キャッシュ ミス時の復元を「I/O処理」だけとして設計しない方がよい。

データを戻す間にGPUが空いているなら、GPUで一部を再計算することで復元クリティカルパスを短くできる。逆にGPUが忙しくI/Oが空いているなら、保存データを多く読む方がよい。

したがって一般には、

1. **再計算コスト**
2. **I/O コスト**
3. **両者をどれだけ重ねられるか**
4. **位置によってコストが変わるか**
5. **複数リクエスト/GPUで資源 contentionがあるか**

を同時に見るべきである。

この考え方はKVだけでなく、MoE エキスパート、活性値 checkpoint、SSD基盤の 重みなどにも応用できる。**「保存するか再計算するか」ではなく、「どの部分をどちらに任せ、どう同時実行するか」**が重要になる。
