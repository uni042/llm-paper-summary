# HeadInfer: Memory-Efficient LLM Inference by Head-wise Offloading

> HeadInferの中心は、**「1 層分のKV キャッシュすらGPUへ丸ごと戻す必要はない」**という点にある。Multi-Head 注意機構では各注意機構 ヘッドを独立に計算し、最後に結果を連結できる。そこで全KVの正本をCPU DRAMへ置き、GPUには現在処理する1個または少数ヘッド分だけを読み込む。これにより層単位オフロードよりさらにGPU側の最低KV容量を下げ、24GBのRTX 4090でも100万〜400万トークン級の文脈を処理可能にする。ただしこれは「数百万トークンを高速対話型生成できる」という意味ではなく、極端な文脈を**近似なしでメモリ上成立させる**ことを主目的とする研究である。

## まずKV cacheがなぜ長文脈で支配的になるのか

自己回帰Transformerは、新しいトークンを1個生成するたびに過去トークンへ注意機構する。

各層では過去トークンについて鍵と値を一度計算し、**KVキャッシュ（KV キャッシュ）**として保存しておく。そうすれば次トークン生成時に過去全トークンの鍵/値を再計算せずに済む。

バッチ 大きさを `B`、層数を `L`、文脈 長さを `S`、KV hidden dimensionを `D`、1要素のバイト数を `b` とすると、KV容量は概ね

`2 × B × L × S × D × b`

に比例する。

`2` は鍵と値の2種類を表す。

つまりモデル 重みは固定でも、KV キャッシュは文脈長 `S` に比例して増え続ける。

論文ではLlama-3-8BをBF16・バッチ 1で100万トークンまで扱う例について、概算GPU メモリを

- モデル パラメータ: 約15 GB
- 活性値: 約64 GB
- KV キャッシュ: 約128 GB
- 合計: 約207 GB

とする。

24GB RTX 4090では重みだけなら8B モデルを置けても、長文脈のKVと活性値が全く収まらない。

## 従来の「layer-wise offload」では何が残るのか

最も素直な対策は、KV キャッシュをCPU DRAMへ退避し、必要な層だけGPUへ戻す方法である。

Transformerが層 1を計算するときは層 1のKV、層 2なら層 2のKVだけ必要なので、全モデル分を同時にGPUへ置く必要はない。

これは**層単位オフロード（層単位 オフロード）**である。

例えば32 層なら、理想的にはGPU常駐KVを全体の約1/32まで下げられる。

しかし数百万トークン級になると、**1 層分だけでも大きい**。

特に個人向け GPUでは、モデル 重みと活性値を置いた残りVRAMが数GBしかないため、1 層の全注意機構 ヘッド分を丸ごと戻すだけでもOOMになる。

HeadInferはオフロード粒度を

`model全体 → layer → attention head`

ともう1段細かくする。

# なぜattention headを1個ずつ計算しても答えが変わらないのか

Multi-Head 注意機構では、1 層のhidden dimensionを複数ヘッドへ分割する。

ヘッド `h` は自分専用の

- 問い合わせ `Q^(h)`
- 鍵 `K^(h)`
- 値 `V^(h)`

を使って

`A^(h) = softmax(Q^(h) K^(h)^T / sqrt(d_k)) V^(h)`

を計算する。

各ヘッドの注意機構計算は、他ヘッドのKVを必要としない。

最後に

`concat(A^(1), A^(2), ..., A^(H))`

として結合し、出力 射影へ渡す。

したがって数学的には

- 全ヘッドを同時にGPUへ置いて並列計算する
- ヘッド 1を計算して結果を保存し、KVを入れ替えてヘッド 2、3…と順番に計算する

のどちらでも、同じ完全な-精度 KVを使う限り注意機構結果は同じになる。

HeadInferはこの**ヘッド 独立性**をメモリ削減へ使う。

## 最小GPU KV量はどこまで下がるか

1 層に `H` ヘッド、モデル全体で `L` 層あるとする。

### 全KV常駐

GPU上KV比率は

`α = 1`

### Layer-wise offload

同時に1 層だけなら

`α ≈ 1/L`

### HeadInfer最小構成

同時に1 ヘッドだけなら

`α ≈ 1/(L×H)`

になる。

つまり層単位 オフロードよりさらに約 `H` 倍細かくできる。

Llama-3系のGrouped-問い合わせ 注意機構では実際にオフロード対象となるKV ヘッド数の扱いはアーキテクチャに依存するが、基本原理は「現在必要なヘッド グループだけGPUへ置く」ことである。

# HeadInferの実行方法

## 1. CPU DRAMにfull KVの正本を置く

HeadInferのコア方式では、トークンを削除したりKVを低ビット化したりしない。

生成済み全トークンの完全な-精度 KVをCPU DRAM側へ保持する。

したがって過去のKVが後で必要になっても情報は失われていない。

これはH2O、StreamingLLM、HeadKV等のように「重要でないトークン/ヘッドを捨てる」近似方式との大きな違いである。

## 2. GPUには現在のhead groupだけを置く

ある層の注意機構を計算するとき、CPUから必要なヘッド グループの全文脈 KVをGPUへ読み込む。

GPUでそのヘッド グループの注意機構 出力を計算したら、結果を残してKV バッファを次グループへ使い回す。

最小構成なら1 ヘッド分だけでよい。

## 3. 新しく生成したKVをCPUへ書き戻す

現在トークンの鍵/値はGPUで生成される。

GPU側バッファに追加した後、オフロード対象ヘッドのKV 更新をCPU側の完全な キャッシュへ非同期で書き戻す。

こうしてCPU側が長期的な正本になり、GPU側は小さな作業 集合として機能する。

# Ping-pong bufferでPCIe待ちを隠す

ヘッドを1個ずつ処理すると、単純実装では

`head 1をCPU→GPU load → compute → head 2をload → compute ...`

となり、毎回PCIe待ちが重要 経路へ入る。

HeadInferは2組のバッファを交互に使う**ピンポンバッファ（ping-pong バッファ）**で転送と計算を重ねる。

例えば

1. バッファ 1つののヘッド 1をGPUで注意機構計算
2. 同時にバッファ Bへヘッド 2 KVをCPUからプリフェッチ
3. ヘッド 1計算終了後に1つの/Bを交換
4. ヘッド 2計算中にヘッド 3を1つのへプリフェッチ

というパイプラインにする。

新KVのCPUへの書き戻しも後続計算と非同期に重ねる。

長文脈ほど注意機構計算時間自体が伸びるため、PCIe 転送を隠せる時間も増える。

## Memoryは事前確保する

数百万トークンでヘッドごとに毎回allocate/freeするとallocator オーバーヘッドとfragmentationが大きい。

そのためCPU側完全な KV領域とGPU側ping-pong バッファをあらかじめ確保する。

# 1 headずつにするとGPUが遅くならないのか

ここがHeadInferの重要なトレードオフである。

ヘッド単位へ細かくするとメモリは最小になるが、

- カーネル 起動回数が増える
- 小さいカーネルになりGPU parallelismが落ちる
- PCIe 転送回数が増える

ため、短文脈では不利になる。

そこでHeadInferは常に1 ヘッドずつにはしない。

## 適応的head grouping

文脈が短くVRAMに余裕があるときは複数ヘッドを1 グループとしてまとめて処理する。

論文のLlama-3-8B実装例では概ね

- 1〜500K: 全ヘッドをまとめる
- 500K〜1M: 2 グループ
- 1M〜2M: 4 グループ
- 2M〜4M: 8 グループ

へ段階的に細粒度化する。

8 グループの最も細かい設定では実質1 ヘッド相当だけをGPUに置く。

つまりHeadInferは

`memory不足になるまでは大きいgroupで高速に処理し、必要になった時だけ細かくする`

設計である。

これは固定ヘッド-wise オフロードより現実的な理由である。

# Chunked prefillが必要な理由

KVだけをCPUへ逃がしても、プリフィル中の活性値が大きければOOMする。

長い入力を一度に順伝播すると、線形 層等の中間活性値が系列 長さに比例して増える。

そこで入力を例えば10K トークンずつの**分割事前充填（chunked プリフィル）**へ分ける。

各塊を順番に処理し、中間活性値は塊終了後に解放する。

これにより活性値 peakは

`全context長`

ではなく

`chunk size`

に近い量へ制限できる。

HeadInferは

- 系列軸: chunked プリフィル
- 層軸: 層単位 処理
- ヘッド軸: ヘッド-wise オフロード

と3次元でメモリ 粒度を細かくする研究と理解すると分かりやすい。

# Roofline解析は何を示しているのか

**ルーフライン解析（roofline 分析）**は、カーネルが

- GPU演算能力に制約される計算律速（計算-上限）
- メモリ/PCIe 帯域に制約される帯域律速（メモリ-上限）

のどちらかを、1 バイト当たりの演算量で見る方法である。

HeadInferではCPU↔GPU 転送が増えるため、単にメモリが減ってもPCIe律速になれば実用性がない。

## Prefill: 長文脈ではcompute-boundになりやすい

論文のRTX 4090解析では、短文脈ではオフロード オーバーヘッドが目立つ。

- `S <= 1K`: メモリ-上限側へ寄り、オフロードで遅くなる
- 約2K: 転換 点
- `S >= 10K`: プリフィルは十分計算-上限

と分析する。

長い文脈では注意機構計算量自体が大きく、ヘッド KV 転送を計算の裏へ重ねやすい。

このため論文は10K トークンを主な塊 大きさとして採用する。

## Decode: memory-boundなので厳しい

一方デコードは1 トークンずつ進むため算術密度が低く、もともとメモリ-上限である。

CPUから長文脈 KVを毎トークン読み込むとPCIe帯域が直接スループットを制限する。

したがってHeadInferは「デコードも高速になるシステム」ではない。

極端な文脈をメモリ上成立させる代わりに、長文脈 デコード 遅延は大きくなる。

これは見出し結果の4M トークンを解釈するうえで重要である。

# 評価環境

主実機は次の構成である。

- GPU: NVIDIA RTX 4090 24GB級
- CPU: AMD EPYC 7B13 ×4、計256 コア
- ホスト RAM: 1 TB DDR5
- PCIe: Gen4、pinned ホスト メモリでH2D/D2H約25 GB/s
- NVMe: 512 GB Gen4 ×2

モデルは

- Llama-3-8B
- Llama-2-7B
- Mistral-7B
- Qwen2-7B
- Gemma-2-9B
- Llama-3-70B

を評価する。

長大文脈 ベンチマークにはLongBench v2、SCBench、NIAH、RULER等を用いる。

# 主要結果

## 1. Llama-3-8B・1M tokenでGPU KV 128GB → 1GB

論文の代表例では1M-トークン Llama-3-8Bについて

- 比較対象 KV: 約128 GB
- HeadInfer GPU-常駐 KV: 約1 GB

まで削減する。

総GPU メモリは

- 標準 BF16推定: 約207 GB
- HeadInfer: 約17 GB

となり、約92%削減する。

実測値は約17 GBで推定と近い。

ここで消えた127GB分のKVがなくなったわけではなく、**CPU DRAMへ移った**点が重要である。

## 2. RTX 4090 24GBでLlama-3-8Bを4M tokenまで実行

最大文脈長比較ではLlama-3-8Bについて

- Standard: 25K
- Chunked プリフィル: 30K
- 4-ビット KV 量子化: 45K
- 層単位 オフロード: 45K
- HeadInfer: 4096K

まで拡張する。

約4M トークンでGPU側瞬間KVは数GBまで抑えられる一方、CPU側には約500GB級のKVが必要になる条件がある。

したがって「24GB GPUだけで4M トークンが完結」ではなく、**24GB GPU + 数百GB級ホスト RAMを使ったheterogeneous-メモリ 推論**である。

## 3. 他modelでもGPUよりCPU RAMが上限になる

同じ24GB RTX 4090で最大文脈は

| モデル | Standard | 層単位 オフロード | HeadInfer |
|---|---:|---:|---:|
| Llama-3-8B | 25K | 45K | 4096K |
| Llama-2-7B | 10K | 60K | 1024K |
| Mistral-7B | 30K | 45K | 4096K |
| Qwen2-7B | 35K | 50K | 4200K |
| Gemma-2-9B | 10K | 35K | 1300K |

となる。

この領域ではGPU VRAMではなく1TB ホスト RAMやモデル自身の文脈 対応が次の制約になる。

## 4. Llama-3-70Bでもpipeline parallelismと併用

大きい モデルでは重み自体が1 GPUに収まらない。

HeadInferはパイプライン parallelismと組み合わせ、Llama-3-70Bで

- Standard: 約10K
- HeadInfer + 10K 塊: 約950K
- HeadInfer + 5K 塊: 約1000K

まで伸ばす例を示す。

つまりヘッド-wise KV オフロードはsingle-GPU 8Bだけに限定されたメモリ trickではないが、重み parallelismは別途必要である。

# 「4M tokenを処理できる」と「4M tokenが速い」は違う

Appendixの遅延を見ると、この区別が非常に重要である。

Llama-3-8Bの適応型 HeadInferではプリフィル 遅延が概ね

- 100K: 約30.2 s
- 400K: 約351 s
- 1M: 約2033 s
- 2M: 約7952 s
- 4M: 約27114 s

まで増える。

4M プリフィルは約7.5時間に相当する。

デコード 1 トークン当たりも

- 100K: 約0.66 s
- 400K: 約3.03 s
- 1M: 約6.41 s
- 2M: 約13.7 s
- 4M: 約27.2 s

になる。

したがって4M 見出し結果は

**「個人向け GPU VRAMが原因で不可能だった正確 推論をメモリ上可能にした」**

という成果であり、対話型 chat向け性能を示すものではない。

## なぜそれでも意味があるのか

研究用途では

- モデルが本当に数百万トークンを無損失に処理できるか検証する
- 長大文脈 ベンチマークをGPU不足でtruncateせず評価する
- 疎/approximate methodの精度 比較対象を作る

ために、遅くても正確 実行 経路が必要になる。

HeadInferはその容量 比較対象として価値がある。

# Long-context benchmarkでscoreが上がる理由

HeadInfer コアはモデルの注意機構計算を近似していない。

それでもベンチマーク 点数が標準 推論より高く見えることがある。

理由は、標準側が24GB GPUに収まる25K〜数十K 文脈までしか処理できず、長い入力をtruncateするからである。

SCBenchでは同一RTX 4090で

- Standard: 最大25K
- Chunked プリフィル: 30K
- 層単位 オフロード: 45K
- HeadInfer: 1024K

まで処理し、HeadInferが9 taskすべてで高い点数を示す。

これはHeadInferがモデルの推論能力そのものを改善したというより、**本来モデルへ与えるべき長い文脈を切らずに渡せるようになった**効果である。

# Core HeadInferはlossless、sparsity extensionは別物

論文AppendixにはDuoAttention等のヘッド-wise sparsityと組み合わせる拡張もある。

そこでは一部ヘッドのKVを短いwindowへ制限するため、近似が入る。

しかし主な 見出し結果である

- 1M KV 128GB→1GB
- 総 207GB→17GB
- 24GB RTX 4090で4M トークン

は**完全な KVをCPUに保持するコア 正確 経路**として扱うべきである。

repositoryではこの2つを混同しない。

# 既存研究との差

## Layer-wise KV offload

LayerKV等は1 層単位でKVをGPUへ戻す。

HeadInferはその中をさらにヘッド単位へ分解し、minimum 作業 集合を1 ヘッドまで縮める。

## CPU attention方式

FastDecode、NEO等は一部注意機構計算自体をCPUへ移す。

HeadInferは注意機構 計算をGPUに残し、KV 保存だけCPUへ置く。

そのためGPU 計算を使える一方、PCIe 転送との重ね合わせが重要になる。

## Token eviction / sparse attention

H2O、StreamingLLM等は一部トークンのKVを削除し容量と計算を減らす。

HeadInfer コアは全トークン/完全な KVをCPUに保持するため、exactnessを優先する。

## KV quantization

KIVI等はKVのビット幅を下げる。

HeadInferは精度を変えず、**常駐 粒度**を変える。

両者は原理上組み合わせ可能だが、paperのコア contributionはオフロード粒度である。

# 限界

1. **CPU RAMが非常に大きく必要**: 4M Llama-3-8B級では数百GBのホスト メモリが必要で、普通の個人向け PC全体としては軽量ではない。
2. **デコードはPCIe律速**: 数百万文脈では1 トークン生成に秒〜数十秒かかり、対話型 提供には不向き。
3. **プリフィルも絶対時間は巨大**: 4M トークンの正確 プリフィルは時間単位になる。
4. **細粒度化のオーバーヘッド**: 1 ヘッドずつではカーネル 起動/転送回数が増え、短文脈では標準注意機構より遅い。
5. **適応型 thresholdはハードウェア依存**: 500K/1M等のグループ境界はRTX 4090等のメモリ/帯域条件に依存し、別GPUでは再調整が必要。
6. **ホスト 帯域依存**: PCIe 4.0 pinned-メモリ スループット約25 GB/sを前提とした評価で、mobile/older PCIeではさらに遅くなる。
7. **高い-concurrency 提供研究ではない**: 主評価はsingle-リクエスト 長大文脈 容量で、複数sessionが同時にCPU DRAM/PCIeを競合するproduction SLOは扱わない。
8. **モデルのネイティブ positional 対応は別問題**: メモリ上4M トークンを扱えても、そのモデルが4M 文脈を学習・position 拡張上正しく使える必要がある。

# 一般的な実装上の示唆

HeadInferから得られる最も一般的な教訓は、オフロードの最低常駐 集合を決めるときに

`model → layer`

で止めず、演算の独立性があれば

`layer → head → tile`

まで分解できないかを見ることである。

ただし粒度を細かくするほど

- 転送回数
- カーネル 起動回数
- スケジューリング メタデータ

が増える。

したがって最適解は「常に最細粒度」ではなく、**メモリ constraintを満たす範囲で最も大きなグループを使う適応型 粒度**になる。

また、HeadInferのroofline結果は階層メモリ研究にも重要である。

同じCPU/SSD オフロードでも

- プリフィルのように計算時間が長くI/Oを隠せる段階
- デコードのようにメモリ-上限でI/Oが重要 経路へ乗る段階

では適切な階層が違う。

SSD/NVMeをさらに下位階層に置く場合、デコードで必要KVを毎stepSSDから読む設計はほぼ成立しないため、予測プリフェッチ・疎 検索・CPU DRAM キャッシュ等を組み合わせる必要がある。
