# HeadInfer: Memory-Efficient LLM Inference by Head-wise Offloading

> HeadInferの中心は、**「1 layer分のKV cacheすらGPUへ丸ごと戻す必要はない」**という点にある。Multi-Head Attentionでは各attention headを独立に計算し、最後に結果を連結できる。そこで全KVの正本をCPU DRAMへ置き、GPUには現在処理する1個または少数head分だけを読み込む。これによりlayer単位offloadよりさらにGPU側の最低KV容量を下げ、24GBのRTX 4090でも100万〜400万token級のcontextを処理可能にする。ただしこれは「数百万tokenを高速interactive生成できる」という意味ではなく、極端なcontextを**近似なしでmemory上成立させる**ことを主目的とする研究である。

## まずKV cacheがなぜ長文脈で支配的になるのか

自己回帰Transformerは、新しいtokenを1個生成するたびに過去tokenへattentionする。

各layerでは過去tokenについてKeyとValueを一度計算し、**KVキャッシュ（KV cache）**として保存しておく。そうすれば次token生成時に過去全tokenのKey/Valueを再計算せずに済む。

batch sizeを `B`、layer数を `L`、context lengthを `S`、KV hidden dimensionを `D`、1要素のbyte数を `b` とすると、KV容量は概ね

`2 × B × L × S × D × b`

に比例する。

`2` はKeyとValueの2種類を表す。

つまりmodel weightは固定でも、KV cacheはcontext長 `S` に比例して増え続ける。

論文ではLlama-3-8BをBF16・batch 1で100万tokenまで扱う例について、概算GPU memoryを

- model parameter: 約15 GB
- activation: 約64 GB
- KV cache: 約128 GB
- 合計: 約207 GB

とする。

24GB RTX 4090ではweightだけなら8B modelを置けても、長contextのKVとactivationが全く収まらない。

## 従来の「layer-wise offload」では何が残るのか

最も素直な対策は、KV cacheをCPU DRAMへ退避し、必要なlayerだけGPUへ戻す方法である。

Transformerがlayer 1を計算するときはlayer 1のKV、layer 2ならlayer 2のKVだけ必要なので、全model分を同時にGPUへ置く必要はない。

これは**layer単位offload（layer-wise offload）**である。

例えば32 layerなら、理想的にはGPU常駐KVを全体の約1/32まで下げられる。

しかし数百万token級になると、**1 layer分だけでも大きい**。

特にconsumer GPUでは、model weightとactivationを置いた残りVRAMが数GBしかないため、1 layerの全attention head分を丸ごと戻すだけでもOOMになる。

HeadInferはoffload粒度を

`model全体 → layer → attention head`

ともう1段細かくする。

# なぜattention headを1個ずつ計算しても答えが変わらないのか

Multi-Head Attentionでは、1 layerのhidden dimensionを複数headへ分割する。

head `h` は自分専用の

- query `Q^(h)`
- key `K^(h)`
- value `V^(h)`

を使って

`A^(h) = softmax(Q^(h) K^(h)^T / sqrt(d_k)) V^(h)`

を計算する。

各headのattention計算は、他headのKVを必要としない。

最後に

`concat(A^(1), A^(2), ..., A^(H))`

として結合し、output projectionへ渡す。

したがって数学的には

- 全headを同時にGPUへ置いて並列計算する
- head 1を計算して結果を保存し、KVを入れ替えてhead 2、3…と順番に計算する

のどちらでも、同じfull-precision KVを使う限りattention結果は同じになる。

HeadInferはこの**head independence**をmemory削減へ使う。

## 最小GPU KV量はどこまで下がるか

1 layerに `H` head、model全体で `L` layerあるとする。

### 全KV常駐

GPU上KV比率は

`α = 1`

### Layer-wise offload

同時に1 layerだけなら

`α ≈ 1/L`

### HeadInfer最小構成

同時に1 headだけなら

`α ≈ 1/(L×H)`

になる。

つまりlayer-wise offloadよりさらに約 `H` 倍細かくできる。

Llama-3系のGrouped-Query Attentionでは実際にoffload対象となるKV head数の扱いはarchitectureに依存するが、基本原理は「現在必要なhead groupだけGPUへ置く」ことである。

# HeadInferの実行方法

## 1. CPU DRAMにfull KVの正本を置く

HeadInferのcore方式では、tokenを削除したりKVを低bit化したりしない。

生成済み全tokenのfull-precision KVをCPU DRAM側へ保持する。

したがって過去のKVが後で必要になっても情報は失われていない。

これはH2O、StreamingLLM、HeadKV等のように「重要でないtoken/headを捨てる」近似方式との大きな違いである。

## 2. GPUには現在のhead groupだけを置く

あるlayerのattentionを計算するとき、CPUから必要なhead groupの全context KVをGPUへ読み込む。

GPUでそのhead groupのattention outputを計算したら、結果を残してKV bufferを次groupへ使い回す。

最小構成なら1 head分だけでよい。

## 3. 新しく生成したKVをCPUへ書き戻す

現在tokenのKey/ValueはGPUで生成される。

GPU側bufferに追加した後、offload対象headのKV updateをCPU側のfull cacheへ非同期で書き戻す。

こうしてCPU側が長期的な正本になり、GPU側は小さなworking setとして機能する。

# Ping-pong bufferでPCIe待ちを隠す

headを1個ずつ処理すると、単純実装では

`head 1をCPU→GPU load → compute → head 2をload → compute ...`

となり、毎回PCIe待ちがcritical pathへ入る。

HeadInferは2組のbufferを交互に使う**ピンポンバッファ（ping-pong buffer）**で転送と計算を重ねる。

例えば

1. buffer Aのhead 1をGPUでattention計算
2. 同時にbuffer Bへhead 2 KVをCPUからprefetch
3. head 1計算終了後にA/Bを交換
4. head 2計算中にhead 3をAへprefetch

というpipelineにする。

新KVのCPUへの書き戻しも後続computeと非同期に重ねる。

長contextほどattention計算時間自体が伸びるため、PCIe transferを隠せる時間も増える。

## Memoryは事前確保する

数百万tokenでheadごとに毎回allocate/freeするとallocator overheadとfragmentationが大きい。

そのためCPU側full KV領域とGPU側ping-pong bufferをあらかじめ確保する。

# 1 headずつにするとGPUが遅くならないのか

ここがHeadInferの重要なtrade-offである。

head単位へ細かくするとmemoryは最小になるが、

- kernel launch回数が増える
- 小さいkernelになりGPU parallelismが落ちる
- PCIe transfer回数が増える

ため、短contextでは不利になる。

そこでHeadInferは常に1 headずつにはしない。

## 適応的head grouping

contextが短くVRAMに余裕があるときは複数headを1 groupとしてまとめて処理する。

論文のLlama-3-8B実装例では概ね

- 1〜500K: 全headをまとめる
- 500K〜1M: 2 groups
- 1M〜2M: 4 groups
- 2M〜4M: 8 groups

へ段階的に細粒度化する。

8 groupsの最も細かい設定では実質1 head相当だけをGPUに置く。

つまりHeadInferは

`memory不足になるまでは大きいgroupで高速に処理し、必要になった時だけ細かくする`

設計である。

これは固定head-wise offloadより現実的な理由である。

# Chunked prefillが必要な理由

KVだけをCPUへ逃がしても、prefill中のactivationが大きければOOMする。

長いpromptを一度にforwardすると、linear layer等の中間activationがsequence lengthに比例して増える。

そこで入力を例えば10K tokenずつの**分割事前充填（chunked prefill）**へ分ける。

各chunkを順番に処理し、中間activationはchunk終了後に解放する。

これによりactivation peakは

`全context長`

ではなく

`chunk size`

に近い量へ制限できる。

HeadInferは

- sequence軸: chunked prefill
- layer軸: layer-wise processing
- head軸: head-wise offload

と3次元でmemory granularityを細かくする研究と理解すると分かりやすい。

# Roofline解析は何を示しているのか

**ルーフライン解析（roofline analysis）**は、kernelが

- GPU演算能力に制約される計算律速（compute-bound）
- memory/PCIe bandwidthに制約される帯域律速（memory-bound）

のどちらかを、1 byte当たりの演算量で見る方法である。

HeadInferではCPU↔GPU transferが増えるため、単にmemoryが減ってもPCIe律速になれば実用性がない。

## Prefill: 長文脈ではcompute-boundになりやすい

論文のRTX 4090解析では、短contextではoffload overheadが目立つ。

- `S <= 1K`: memory-bound側へ寄り、offloadで遅くなる
- 約2K: turning point
- `S >= 10K`: prefillは十分compute-bound

と分析する。

長いcontextではattention計算量自体が大きく、head KV transferをcomputeの裏へ重ねやすい。

このため論文は10K tokenを主なchunk sizeとして採用する。

## Decode: memory-boundなので厳しい

一方decodeは1 tokenずつ進むため算術密度が低く、もともとmemory-boundである。

CPUから長context KVを毎token読み込むとPCIe帯域が直接throughputを制限する。

したがってHeadInferは「decodeも高速になるsystem」ではない。

極端なcontextをmemory上成立させる代わりに、長context decode latencyは大きくなる。

これはheadlineの4M tokenを解釈するうえで重要である。

# 評価環境

主実機は次の構成である。

- GPU: NVIDIA RTX 4090 24GB級
- CPU: AMD EPYC 7B13 ×4、計256 cores
- Host RAM: 1 TB DDR5
- PCIe: Gen4、pinned host memoryでH2D/D2H約25 GB/s
- NVMe: 512 GB Gen4 ×2

modelは

- Llama-3-8B
- Llama-2-7B
- Mistral-7B
- Qwen2-7B
- Gemma-2-9B
- Llama-3-70B

を評価する。

long-context benchmarkにはLongBench v2、SCBench、NIAH、RULER等を用いる。

# 主要結果

## 1. Llama-3-8B・1M tokenでGPU KV 128GB → 1GB

論文の代表例では1M-token Llama-3-8Bについて

- baseline KV: 約128 GB
- HeadInfer GPU-resident KV: 約1 GB

まで削減する。

総GPU memoryは

- standard BF16推定: 約207 GB
- HeadInfer: 約17 GB

となり、約92%削減する。

実測値は約17 GBで推定と近い。

ここで消えた127GB分のKVがなくなったわけではなく、**CPU DRAMへ移った**点が重要である。

## 2. RTX 4090 24GBでLlama-3-8Bを4M tokenまで実行

最大context長比較ではLlama-3-8Bについて

- Standard: 25K
- Chunked Prefill: 30K
- 4-bit KV quantization: 45K
- Layer-wise offload: 45K
- HeadInfer: 4096K

まで拡張する。

約4M tokenでGPU側瞬間KVは数GBまで抑えられる一方、CPU側には約500GB級のKVが必要になる条件がある。

したがって「24GB GPUだけで4M tokenが完結」ではなく、**24GB GPU + 数百GB級host RAMを使ったheterogeneous-memory inference**である。

## 3. 他modelでもGPUよりCPU RAMが上限になる

同じ24GB RTX 4090で最大contextは

| Model | Standard | Layer-wise offload | HeadInfer |
|---|---:|---:|---:|
| Llama-3-8B | 25K | 45K | 4096K |
| Llama-2-7B | 10K | 60K | 1024K |
| Mistral-7B | 30K | 45K | 4096K |
| Qwen2-7B | 35K | 50K | 4200K |
| Gemma-2-9B | 10K | 35K | 1300K |

となる。

この領域ではGPU VRAMではなく1TB host RAMやmodel自身のcontext supportが次の制約になる。

## 4. Llama-3-70Bでもpipeline parallelismと併用

large modelではweight自体が1 GPUに収まらない。

HeadInferはpipeline parallelismと組み合わせ、Llama-3-70Bで

- Standard: 約10K
- HeadInfer + 10K chunk: 約950K
- HeadInfer + 5K chunk: 約1000K

まで伸ばす例を示す。

つまりhead-wise KV offloadはsingle-GPU 8Bだけに限定されたmemory trickではないが、weight parallelismは別途必要である。

# 「4M tokenを処理できる」と「4M tokenが速い」は違う

Appendixのlatencyを見ると、この区別が非常に重要である。

Llama-3-8Bのadaptive HeadInferではprefill latencyが概ね

- 100K: 約30.2 s
- 400K: 約351 s
- 1M: 約2033 s
- 2M: 約7952 s
- 4M: 約27114 s

まで増える。

4M prefillは約7.5時間に相当する。

decode 1 token当たりも

- 100K: 約0.66 s
- 400K: 約3.03 s
- 1M: 約6.41 s
- 2M: 約13.7 s
- 4M: 約27.2 s

になる。

したがって4M headlineは

**「consumer GPU VRAMが原因で不可能だったexact inferenceをmemory上可能にした」**

という成果であり、interactive chat向け性能を示すものではない。

## なぜそれでも意味があるのか

研究用途では

- modelが本当に数百万tokenをlosslessに処理できるか検証する
- long-context benchmarkをGPU不足でtruncateせず評価する
- sparse/approximate methodのaccuracy baselineを作る

ために、遅くてもexact execution pathが必要になる。

HeadInferはそのcapacity baselineとして価値がある。

# Long-context benchmarkでscoreが上がる理由

HeadInfer coreはmodelのattention計算を近似していない。

それでもbenchmark scoreがstandard inferenceより高く見えることがある。

理由は、standard側が24GB GPUに収まる25K〜数十K contextまでしか処理できず、長いinputをtruncateするからである。

SCBenchでは同一RTX 4090で

- Standard: 最大25K
- Chunked Prefill: 30K
- Layer-wise offload: 45K
- HeadInfer: 1024K

まで処理し、HeadInferが9 taskすべてで高いscoreを示す。

これはHeadInferがmodelの推論能力そのものを改善したというより、**本来modelへ与えるべき長いcontextを切らずに渡せるようになった**効果である。

# Core HeadInferはlossless、sparsity extensionは別物

論文AppendixにはDuoAttention等のhead-wise sparsityと組み合わせる拡張もある。

そこでは一部headのKVを短いwindowへ制限するため、近似が入る。

しかしmain headlineである

- 1M KV 128GB→1GB
- total 207GB→17GB
- 24GB RTX 4090で4M token

は**full KVをCPUに保持するcore exact path**として扱うべきである。

repositoryではこの2つを混同しない。

# 既存研究との差

## Layer-wise KV offload

LayerKV等は1 layer単位でKVをGPUへ戻す。

HeadInferはその中をさらにhead単位へ分解し、minimum working setを1 headまで縮める。

## CPU attention方式

FastDecode、NEO等は一部attention計算自体をCPUへ移す。

HeadInferはattention computeをGPUに残し、KV storageだけCPUへ置く。

そのためGPU computeを使える一方、PCIe transferとのoverlapが重要になる。

## Token eviction / sparse attention

H2O、StreamingLLM等は一部tokenのKVを削除し容量と計算を減らす。

HeadInfer coreは全token/full KVをCPUに保持するため、exactnessを優先する。

## KV quantization

KIVI等はKVのbit幅を下げる。

HeadInferはprecisionを変えず、**residency granularity**を変える。

両者は原理上組み合わせ可能だが、paperのcore contributionはoffload粒度である。

# 限界

1. **CPU RAMが非常に大きく必要**: 4M Llama-3-8B級では数百GBのhost memoryが必要で、普通のconsumer PC全体としては軽量ではない。
2. **DecodeはPCIe律速**: 数百万contextでは1 token生成に秒〜数十秒かかり、interactive servingには不向き。
3. **Prefillも絶対時間は巨大**: 4M tokenのexact prefillは時間単位になる。
4. **細粒度化のoverhead**: 1 headずつではkernel launch/transfer回数が増え、短contextでは標準attentionより遅い。
5. **Adaptive thresholdはhardware依存**: 500K/1M等のgroup境界はRTX 4090等のmemory/bandwidth条件に依存し、別GPUでは再調整が必要。
6. **Host bandwidth依存**: PCIe 4.0 pinned-memory throughput約25 GB/sを前提とした評価で、mobile/older PCIeではさらに遅くなる。
7. **High-concurrency serving研究ではない**: 主評価はsingle-request long-context capacityで、複数sessionが同時にCPU DRAM/PCIeを競合するproduction SLOは扱わない。
8. **Modelのnative positional supportは別問題**: memory上4M tokenを扱えても、そのmodelが4M contextを学習・position extension上正しく使える必要がある。

# 一般的な実装上の示唆

HeadInferから得られる最も一般的な教訓は、offloadの最低resident setを決めるときに

`model → layer`

で止めず、演算の独立性があれば

`layer → head → tile`

まで分解できないかを見ることである。

ただし粒度を細かくするほど

- transfer回数
- kernel launch回数
- scheduling metadata

が増える。

したがって最適解は「常に最細粒度」ではなく、**memory constraintを満たす範囲で最も大きなgroupを使うadaptive granularity**になる。

また、HeadInferのroofline結果は階層memory研究にも重要である。

同じCPU/SSD offloadでも

- prefillのように計算時間が長くI/Oを隠せるphase
- decodeのようにmemory-boundでI/Oがcritical pathへ乗るphase

では適切なtierが違う。

SSD/NVMeをさらに下位tierに置く場合、decodeで必要KVを毎stepSSDから読む設計はほぼ成立しないため、予測prefetch・sparse retrieval・CPU DRAM cache等を組み合わせる必要がある。
