# Sutradhara: An Intelligent Orchestrator-Engine Co-design for Tool-based Agentic Inference

## 概要

Sutradharaは、ツール利用型エージェントの性能問題を「LLM推論エンジン単体の高速化」ではなく、エージェントを制御するオーケストレータと推論エンジンの協調設計として扱う。一般的なエージェントでは、LLMがツール呼び出しを生成し、外部ツールが完了するまで待ち、その結果を次のプロンプトへ追加して再びLLMを呼ぶ。この反復構造では、個々の初回トークン時間（Time To First Token; TTFT）が短くても、ユーザーへ最終回答の最初のトークンが表示されるまでの初回トークン表示時間（First Token Rendered; FTR）が長くなる。

著者らが6,000件の生産相当エージェント要求を分析すると、ツール実行はFTRの中央値で約32%、90パーセンタイルで61%、99パーセンタイルで85%を占める。さらに次反復プロンプトの50〜80%は、現在のツール結果を待たなくても確定できる。にもかかわらず従来系では、デコード→全ツール完了→次プレフィルを直列化し、ツール待ち時間とGPU計算を重ねられていない。

もう一つの問題はキーバリュー（Key-Value; KV）キャッシュのスラッシングである。エージェントはシステムプロンプトや会話履歴を反復間で大量に再利用するが、一般的な最少最近使用（Least Recently Used; LRU）退避は「次反復で再利用されるブロック」と「最終回答など再利用されないブロック」を区別しない。その結果、高並行時に有用なprefixが追い出され、次反復でプレフィルを再計算する。

Sutradharaはこの二層の情報断絶を、5つの薄いAPIで埋める。ツール非依存prefixを先行プレフィルする「ツール認識プロンプト分割」、デコード途中で完成したツール呼び出しを即時投入する「ストリーミングツール起動」、KVブロックへ意味タグと再利用優先度を付ける「オーケストレータ認識キャッシュ管理」を組み合わせる。vLLM v0.11.0上の評価では、同じ中央値FTRで最大77%高い投入負荷を維持するか、同一負荷で中央値FTRを最大15%削減する。末尾FTRも最大11%、末尾エンドツーエンド（End-to-End; E2E）遅延も最大9%削減する。

## 問題設定

通常のLLMサービングは、各推論要求を独立した「プレフィル＋自己回帰デコード」とみなし、要求単位のバッチング、スケジューリング、prefixキャッシュを最適化する。一方、エージェント要求は複数のLLM呼び出しとツール実行を一つのユーザー要求の内部で連鎖させる。論文のトレースでは、中央値の反復深さは約2だが末尾では7まで増え、1反復当たりツール呼び出し数は中央値2、最大21に達する。プロンプト長も中央値約20Kトークン、末尾ではその約3倍まで伸びる。

この構造では、オーケストレータは「どのprompt部分がツール結果へ依存するか」「どのツールが実行中か」「どの文脈が次反復で再利用されるか」を知っている。一方、vLLMなどの推論エンジンはKV物理配置、プレフィル/デコードのスケジューリング、キャッシュ退避を制御する。しかし標準の要求応答APIでは、両者が互いの情報を使えない。

そのためSutradharaは、モデル内部のattention kernelや重みを変更するのではなく、オーケストレータが持つ意味情報をエンジンへ渡し、エンジン側の既存機能をより適切なタイミングと優先度で使う。狙いは、ツール時間を隠蔽できる計算と重ねること、および次反復で再利用されるKVを退避から守ることで、エージェント要求全体のクリティカルパスを短縮することである。

## 手法

### 1. ツール認識プロンプト分割

反復 (i) のデコードがツール呼び出しを生成した時点で、オーケストレータは次反復 (i+1) のプロンプトを二つへ分割する。前半 (P_{i+1,a}) はシステム指示、会話履歴、固定テンプレートなどツール出力に依存しない部分で、後半 (P_{i+1,b}) はツール結果を含む部分である。

オーケストレータは `submit_partial_prefill()` で前半を直ちにエンジンへ送り、外部ツールが走っている間にGPUでプレフィルを進める。エンジンは継続ハンドルとKVを保持し、この部分を最高再利用優先度で保護する。ツール結果が返ると `extend_prefill()` で後半を同じKVへ追加し、残りだけをプレフィルした後にデコードへ進む。ツールが失敗またはタイムアウトした場合は、部分プレフィルを破棄してピン留め資源を解放する。

この機構の利得上限は、ツール実行時間と先行プレフィル時間の重なりで決まる。ツールが非常に短く部分プレフィルの方が長ければ、残りのプレフィルは結局クリティカルパスへ残る。また、次プロンプトの大部分が直前のツール出力へ依存する場合は、先行実行できる割合そのものが小さくなる。

### 2. デコード中のストリーミングツール起動

中間反復では、LLMが複数ツール呼び出しをJSON配列として生成することがある。通常のオーケストレータは全デコード完了後にJSONを解析し、そこで初めて各ツールを投入する。Sutradharaは `register_streaming_callback()` でトークン単位のコールバックを登録し、逐次JSONパーサが一つのツールオブジェクトの閉じ括弧を認識した時点で、そのツールだけを即時起動する。

入力は生成途中の構造化ツール記述、出力は非同期のツール実行タスクである。後続ツールのJSONをLLMがまだデコードしている間に、先に完成したツールは外部サービス上で実行できるため、「全デコード時間＋全ツール時間」という直列和を短くできる。ツールfan-outが大きく、先頭ツールの処理が長いほど重畳余地が大きい。一方、ツール呼び出しが1件だけ、デコードが極端に短い、またはストリーム途中で安全に確定できない出力形式では利得が縮む。

### 3. 意味優先KVキャッシュ管理

オーケストレータは `tag_kv_blocks()` と `set_reuse_priority()` を使い、KVブロックへ意味と再利用価値を渡す。システムプロンプトは要求間でも共有され得るため高優先、ユーザー固有queryは主に同一要求内で再利用、ツール出力は後続反復で条件付き再利用、最終応答は再利用されないため低優先、先行部分プレフィルはツール待ち中に失うと計算が無駄になるため最高優先とする。

容量不足時の退避順は、概ね「最終応答 → ツール出力 → ユーザーquery → システムプロンプト → 部分プレフィル」の順で、同一優先度内だけLRUを使う。この順序により、ツール待ちで一時停止中の要求の高価値prefixを、別要求の一時的KVが追い出す連鎖を抑える。論文はHBM内キャッシュのみを評価し、追い出されたブロックは再計算するが、CPU等へKVをオフロードする階層型システムでも「どのブロックを先に戻すか」という優先情報として同じ考え方を利用できる。

### 4. 要求単位スケジューリングと薄い協調API

個別LLM呼び出しを単純な先入れ先出し（First-In First-Out; FIFO）で並べると、多くの反復を発行するエージェント要求が、先に到着した別エージェント要求を不公平に追い越すことがある。Sutradharaの比較baseline自体にエージェント要求の到着時刻を基準にした要求認識スケジューリングを入れ、Sutradhara固有の3最適化とスケジューラ改善を混同しないようにしている。

協調APIは、部分プレフィル投入、プレフィル延長、ストリーミングコールバック、KV意味タグ付け、再利用優先度設定の5個である。実装は約3,500行のPythonで、vLLM v0.11.0のv1スケジューラへ局所的な変更を加え、オーケストレータは非同期イベント駆動で構成する。モデル構造、学習、推論kernel自体は変更しない。

## 評価

### 評価基盤とワークロード

主評価モデルはQwen3-14BのBF16で、128K文脈を扱えるA100 80GB上に1モデルを配置する。共配置型はA100 1基、プレフィル/デコード分離型はA100 80GBを2基使い、NVLinkで接続する。baselineはvLLM、チャンクプレフィル256、prefixキャッシュ有効、要求認識スケジューリング有効である。

生産相当評価では、6,000件の分析トレースからツールfan-outが大きい120要求を層化抽出し、記録済みprompt、ツール出力、デコード長を再生する。到着はポアソン過程とし、5シードの平均と信頼帯を報告する。オープンソース側ではBerkeley Function Calling Leaderboard（BFCL）v4 Web Searchから56件、SWE-Benchから60件を使う。BFCLは平均4.23反復、ツール約2件/反復、ツール時間はE2Eの約40%。SWE-Benchは平均20反復、ツール約2件/反復、ツール時間は約30%であり、異なる反復深さとツール特性を持つ。

### スループットとFTR/E2E

生産相当トレースでは、同じ中央値FTRでSutradharaはbaselineより最大77%高い投入負荷を維持する。逆に投入負荷を固定すると中央値FTRを最大15%削減する。90パーセンタイルFTRでは、同一遅延で最大45%高い負荷を維持するか、同一負荷で最大11%遅延を削減する。90パーセンタイルE2E遅延も最大9%改善する。

FTRの改善がE2Eより大きいのは、最終反復のユーザー向けデコードには後続ツールがなく、プロンプト分割やストリーミング投入で隠せる処理が残っていないためである。この結果は、Sutradharaがデコードkernelを高速化する方式ではなく、中間反復の直列区間を重畳してユーザーが待つクリティカルパスを縮める方式であることを示す。

### 一般化評価

プレフィル/デコード分離型でも、評価した投入負荷で中央値・90パーセンタイルFTRを12〜16%削減し、共配置型以外でも同じ協調方式が機能する。Gemma-3-27Bでは中央値FTRを13.3%、E2Eを9.2%削減する。GemmaはQwen3-14Bよりプレフィル1.34倍、デコード1.60倍遅く、FTRに占めるツール比率が12.9%から9.0%へ下がるため、ツール時間を隠すSutradharaの相対利得も小さくなる。

オープンソーストレースでは、BFCLが0.5/1.5/2.0 QPSで中央値FTRを7.2/10.0/8.0%、SWE-Benchが0.05/0.10/0.25 QPSで13.2/13.0/8.2%改善する。生産相当トレースより改善幅が小さいのは、ツールfan-outが少なくデコードとの重畳余地が小さいこと、append-only promptでは前反復のprefixキャッシュがすでに効きやすく、部分プレフィルの追加効果が小さいためである。

### 構成要素除去実験

0.0075 QPSで各機構を累積追加すると、baselineのFTR/E2Eは37.45/61.57秒である。プロンプト分割だけで35.17/59.39秒となり、FTR 6.1%、E2E 3.5%改善する。ストリーミング起動を追加すると32.07/56.03秒となり、分割のみからさらにFTR 8.3%、E2E 5.5%改善、baseline比では累積14.4%/9.0%となる。

さらに意味優先KV管理を追加すると31.39/54.93秒となり、追加寄与はFTR/E2Eとも1.8%、累積では16.2%/10.8%となる。KVの寄与が相対的に小さいのは、キャッシュ命中向上が主に再プレフィルを減らす一方、最終デコードやツール時間そのものは短縮しないためである。

内部指標では全体KVキャッシュ命中率が21.8%から44.6%へ上がる。反復深さ0では要求間で共有されるシステムpromptの保持が効き、深い反復では同一要求内の部分プレフィルや過去ツール出力を残すことで要求内ヒットが増える。したがって、意味優先退避が単に別のLRU順序を与えたのではなく、実際に再利用可能prefixを残したことが確認できる。

## 既存研究との差

一般的なvLLMやSGLangは、LLM呼び出し内部のバッチング、PagedAttention、prefixキャッシュを高度に最適化するが、ツール依存関係を知らない。エージェントフレームワーク側も反復構造を知るが、KVブロックやGPUスケジュールを制御できない。Sutradharaはこの境界を完全に取り除くのではなく、5つの狭いAPIだけを追加して必要な意味情報を共有する。

また、ツール実行中のKVを固定時間だけ保持するContinuum型の時間生存期間（Time To Live; TTL）方式に対し、Sutradharaは「何秒保持するか」ではなく「何のKVか」「再利用予定があるか」を優先度として渡す。論文のTTL=6秒比較では、SutradharaがContinuumより中央値FTRを17%削減する。ツール時間は90パーセンタイルで中央値の1.60〜3.28倍までばらつくため、固定TTLは長すぎれば容量を占有し、短すぎれば必要なKVを追い出すという問題がある。

## 限界

プロンプト分割は、オーケストレータが次promptのどこへツール結果を挿入するかを把握できることが前提である。ツール出力によって先頭のシステム指示やそれ以前の文脈構造まで書き換わるアプリケーションでは、先行プレフィル可能な割合が減る。ストリーミングツール起動も、生成途中で一つのツール呼び出しを安全に確定できる構造化出力を前提とする。

評価は主にA100 80GB、vLLM v0.11.0、Qwen3-14Bを中心にし、ツール実行は記録済み出力と実測分布を用いたトレース再生である。実際の外部サービス障害、課金、レート制限、ツール結果の内容変化を含むオンライン系全体を最適化したものではない。意味優先キャッシュの評価もHBM内で追い出されたKVを再計算する設定であり、CPU/SSDオフロードと組み合わせた場合の絶対性能は別途測定が必要である。

また、ツールがFTRの大部分を占めるほど重畳余地が大きい反面、Gemma-3-27BのようにLLM計算比率が増えると相対利得は小さくなる。したがって最大77%の容量改善や15%のFTR削減は、ツールfan-out、ツール遅延、prompt依存関係、モデル計算量が評価条件に近い場合の上限値として読むべきであり、すべてのエージェントworkloadに一定倍率で適用されるわけではない。
