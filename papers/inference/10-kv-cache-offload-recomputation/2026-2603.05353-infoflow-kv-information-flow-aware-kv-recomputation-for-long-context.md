# InfoFlow KV: Information-Flow-Aware KV Recomputation for Long Context

> InfoFlow KVは、文書単位で事前計算したキー・バリュー（Key-Value; KV）キャッシュを再利用する長文脈の検索拡張生成（Retrieval-Augmented Generation; RAG）で、問い合わせから文脈への注意質量を使って再計算すべきトークンを選ぶ。推論時と同じ回転位置埋め込み（Rotary Positional Embedding; RoPE）の位置関係で選択し、独立チャンクでは並べ替えも組み合わせる。4基のNVIDIA H100を使う系列並列（sequence parallelism）の32K入力では、再計算率15%で初回トークン遅延（Time to First Token; TTFT）をRing Attentionの2350.1 msから914.0 msへ短縮した。

## 概要

長文脈RAGでは、検索で得た多数の文書をモデルへ読み込むプリフィル（prefill）が大きな計算コストになる。同じ文書が別の問い合わせでも再利用されるなら、文書ごとにKVキャッシュをあらかじめ作って保存し、後の要求で再利用すればプリフィルを省ける。しかし、各文書を独立に処理して作ったKVを後から単純に連結しても、全文書を一度に因果注意（causal attention）へ通した場合と同じ状態にはならない。後ろ側の文書は、前に置かれた別文書の内容を見ずに計算されているからである。

InfoFlow KVは、この「安いが文書間依存を失うキャッシュ再利用」と「正確だが高価な全再計算」の間を狙う。問い合わせから各文脈トークンへ向かう注意重みを集約し、生成へ情報を伝えやすいトークンだけを再計算する。さらに、選択時のRoPE位置を実際の連結後の位置へ合わせ、順序交換が許される独立文書では重要トークンの密度を使ってチャンク順も調整する。モデルの追加学習は必要ない。

論文はQwen3-14B、Llama-3.1-8B-Instructなどの大規模言語モデル（Large Language Model; LLM）とQwen3-VL-8Bの視覚言語モデル（Vision-Language Model; VLM）で評価する。代表的な効率評価では、4基のH100、再計算率15%の系列並列で、16K入力のTTFTが707.8 msから427.6 ms、32K入力では2350.1 msから914.0 msへ低下した。32Kでは単一GPUの全プリフィル3190.5 msに対して3.49倍の高速化である。一方で、全文脈の完全再計算と同じ表現を復元する方式ではなく、選択予算・チャンク分割・入力構造によって品質は変わる。

## 問題設定

通常の長文脈推論では、プリフィル時に各トークンのKVを前から順に計算する。因果注意では後ろのトークンほど多くの先行トークンを参照できるため、ある文書のKVは、その前にどの文書が置かれたかにも依存する。これに対し、キャッシュ再利用型RAGは文書ごとにKVを独立計算しておき、問い合わせ時に必要な文書のキャッシュを連結する。保存済みKVを再利用できる点は効率的だが、独立計算時には存在しなかった文書間の注意経路は後から連結するだけでは復元されない。

この欠落を最も確実に直す方法は、取得文書全体を問い合わせごとにもう一度プリフィルすることである。しかし長い入力ほど計算量とTTFTが増え、事前キャッシュを用意した意味が薄れる。そこで、全文ではなく一部トークンだけを連結後の文脈で再計算する選択的KV再計算が使われる。問題は「どのトークンを限られた再計算予算へ割り当てるか」である。

既存方式のCacheBlendは、独立計算した表現と全体文脈で得られる表現の差を手掛かりにする。EPICは位置に基づく選択規則を使う。これらは再計算対象を絞れる一方、そのトークンが最終的な問い合わせや生成へ実際に情報を伝えられるかを直接の基準にはしていない。InfoFlow KVは、問い合わせがどの文脈トークンへ注意を向けるかを、意味的関連性と情報伝播可能性を同時に反映する信号として使う。

もう一つの問題がRoPEである。文書を単独で事前計算すると各チャンク内の位置は局所的に始まるが、実際に複数チャンクを連結した後には全体の位置番号が割り当てられる。RoPEは相対的な位置関係を注意スコアへ反映するため、局所位置のまま重要度を測ると、本番推論時とは異なる幾何でトークンを順位付けすることになる。本論文は選択段階からこの位置ずれを避ける。

## 手法のあらまし

入力は、検索済みの文書チャンク、それぞれについて事前計算したKVキャッシュ、問い合わせ、そして許容する再計算率である。まず文書キャッシュを論理的に連結し、推論時に使う全体RoPE位置を復元する。その位置関係の下で問い合わせから文脈へ向かう注意を測り、再計算候補へ情報流スコアを与える。

次に、予算内で上位トークンを選ぶ。独立した検索文書のようにチャンク順を変更できる場合だけ、重要トークンの密度に基づいてチャンクを並べ替え、変更後の全体位置で選択をやり直す。最後に、選ばれたトークンだけをグローバルな因果文脈の下で再計算し、そのKVで事前キャッシュ中の対応箇所を置き換える。選ばれなかった大部分のKVはそのまま再利用する。

この流れにより、全文脈のKVを作り直す計算量と、独立キャッシュを無修正で使う品質低下の間に調整可能な点を置く。系列並列では、全KVをGPU間で全収集（all-gather）する代わりに、選択された少数トークンを中心に通信・再計算できるため、文脈長が伸びるほど通信削減の効果も大きくなる。

## 手法

### 1. 問い合わせ条件付きの情報流スコア

InfoFlow KVは、連結された文脈と問い合わせの間で得られる注意行列から、各文脈トークンが問い合わせトークンから受け取る注意質量を集約する。この値を再計算対象の順位付けに使う。入力は問い合わせと文脈トークン、処理は注意重みの集約、出力は文脈トークンごとの重要度順位である。

ここで狙っているのは、単に表現誤差が大きいトークンを探すことではない。たとえ独立計算と全体計算の差が大きくても、問い合わせがほとんど参照しないトークンなら、その再計算に予算を使っても最終回答へ寄与しにくい。逆に問い合わせから強く参照されるトークンは、後続生成へ情報を運ぶ経路上にある可能性が高い。著者らはこの性質を「情報流」として扱う。

再計算率が15%なら、全トークンのうちスコア上位15%を選び、残り85%は事前キャッシュを保持する。したがって追加計算は再計算率に依存する。予算を小さくすれば高速になるが、文書間依存の回復に必要なトークンを落とす可能性が増える。逆に予算を大きくすれば全プリフィルへ近づき、キャッシュ再利用の計算上の利点が縮む。

### 2. 推論時と整合するRoPE位置で選ぶ

文書単位の事前計算では、各チャンクが局所位置を持つ。しかし複数チャンクを問い合わせの前へ連結した実推論では、各トークンの位置は全体配置に従う。InfoFlow KVは再計算対象を決める前に、このグローバル位置を再構成してRoPEを適用する。

この処理の入力はチャンク配置と各トークンの局所位置、出力は最終推論と整合した全体位置である。その上で情報流スコアを計算するため、「選ぶときの位置関係」と「選んだ後に実際に生成するときの位置関係」が揃う。論文の構成要素除去実験（ablation）では、このグローバル位置を使う設定が比較した位置設定より一貫して良い結果を示し、位置幾何の不一致が選択品質を落とし得ることを確認している。

RoPE整合は追加のモデル学習を必要としない一方、キャッシュを単純連結するだけの方式より位置管理が複雑になる。また、これは独立キャッシュそのものを完全な全体文脈KVへ変換する操作ではない。あくまで「どこを再計算すべきか」を本番と同じ位置条件で判断しやすくする機構である。

### 3. 独立チャンクでは重要度に基づいて並べ替える

検索で得た複数文書のように、互いの内部順序は保ちつつ文書同士の順番を変えてよい場合、InfoFlow KVは最初の選択結果からチャンクごとの重要トークン密度を求める。重要トークンを多く含むチャンクを問い合わせに近い側へ移し、配置変更後のRoPE位置で情報流スコアを再計算する。

この機構が効く理由は、因果注意と位置関係のため、どこへ置くかによって後続問い合わせへ情報を伝えやすい度合いが変わるからである。単なる検索順位の置換ではなく、取得済み文脈をKV再利用しやすい配置へ調整する処理である。

ただし、この並べ替えは任意であり、単一の長文書、時系列記録、プログラムなど、チャンク間の順序自体が意味を持つ入力には使えない。論文の表でも「InfoFlow KV単体」と「InfoFlow KV＋並べ替え」が常に同じ方向へ改善するわけではなく、タスクやモデルによって差がある。したがって並べ替えは一般的な常時有効機構ではなく、順序交換可能なRAGチャンク向けの追加選択肢である。

### 4. 選択KVだけを再計算して既存キャッシュへ差し戻す

選択が終わると、対象トークンだけを連結後の全体因果文脈で再計算し、新しく得たKVで事前キャッシュの対応位置を置き換える。入力は選択済みトークンと既存KV、処理は限定的な順伝播、出力は「大部分が再利用KV、一部がグローバル文脈で更新されたKV」という混合キャッシュである。

この設計では、全トークンを再計算しないのでプリフィル計算を減らせる。さらに系列並列では、Ring Attentionのように全文脈へまたがる注意を計算する場合と比べ、再計算対象だけをGPU間で共有すればよい。論文は、選択トークンが同じ系列並列チャンク内にある場合には再計算の多くがローカルに完結し、GPU間通信を減らせると説明する。

一方、注意スコア計算と選択にも費用があるため、短い入力、キャッシュ再利用回数が少ない入力、再計算率が高い設定では相対的な利得が小さくなる。InfoFlow KVの狙いは、KVキャッシュ容量そのものを圧縮することではなく、事前キャッシュ再利用時に必要な再計算量と通信量を減らすことである。

## 評価

### まず見るところ

評価は「同じ再計算予算で回答品質をどこまで戻せるか」と「その再計算を実行したときTTFTをどこまで減らせるか」の二つに分けて読む必要がある。品質評価では原則として各再計算法の再計算率を15%へ揃える。効率評価では4基のH100を使った系列並列で、単一GPU全プリフィル、Ring Attention、InfoFlow KVを比較する。

InfoFlow KVの結果は、独立チャンクのKVをそのまま連結する「再計算なし」より大きく品質を回復し、同予算のCacheBlendやEPICと比べても多くの設定で高い値を示す。効率面では文脈が長いほど差が広がり、32K入力でRing Attention比約2.57倍、単一GPU全プリフィル比3.49倍のTTFT高速化となる。

### 評価条件

| 項目 | 設定 |
|---|---|
| 大規模言語モデル（LLM） | Qwen3-14B、Llama-3.1-8B-Instruct、ChatGLM系。付録ではLlama-3-3B-Instructも比較 |
| 視覚言語モデル（VLM） | Qwen3-VL-8B |
| 長文脈QA | 2WikiMQA、MuSiQue、HotpotQA、NarrativeQA |
| 追加評価 | LongBench v2の短質問部分集合。10K〜210K文脈、180サンプル |
| VLM評価 | RealWorldQA、ChartQA、OCRBench、HRBench4K、InfoVQA |
| 主な再計算予算 | 比較法間で原則15% |
| 比較対象 | 再計算なし、CacheBlend、EPIC、付録ではKVLink5、TurboRAG、PCWなど |
| 効率測定 | 4基のNVIDIA H100による系列並列。8K、16K、32K入力 |
| 効率指標 | 初回トークン遅延（TTFT）と単一GPU全プリフィル比の高速化 |
| 品質指標 | 長文脈QAでは主にF1または正解率。VLMは各ベンチマーク固有指標 |

### 主な性能結果

| 条件 | 比較対象 | InfoFlow KV | 改善・読み方 |
|---|---:|---:|---|
| 8K、4×H100 | Ring Attention 247.5 ms | 232.0 ms | 差は小さい。短い文脈では選択処理の固定費を償却しにくい |
| 16K、4×H100、再計算15% | Ring Attention 707.8 ms | 427.6 ms | Ring Attention比約1.66倍、単一GPU全プリフィル1285.8 ms比3.01倍 |
| 32K、4×H100、再計算15% | Ring Attention 2350.1 ms | 914.0 ms | Ring Attention比約2.57倍、単一GPU全プリフィル3190.5 ms比3.49倍 |
| 同一系列並列・15%、2WikiMQA | Ring Attention F1 0.4894 | 0.5149 | TTFTを下げながらF1も+0.0255 |
| 同一系列並列・15%、MuSiQue | Ring Attention F1 0.3210 | 0.3354 | F1 +0.0144 |
| 同一系列並列・15%、HotpotQA | Ring Attention F1 0.5653 | 0.5783 | F1 +0.0130 |
| LongBench v2短質問、Qwen3-14B | CacheBlend 0.2611、EPIC 0.2056 | 0.2889 | 15%再計算で両比較法を上回る。完全プリフィル0.3833には届かない |

8KではRing Attentionとの差が14.5 msにとどまる一方、32Kでは1436.1 msまで広がる。この傾向は、文脈全体をまたぐ注意・通信の費用が系列長とともに増える一方、InfoFlow KVは再計算対象を一部に限定する設計と整合する。ただし、GPU台数や通信トポロジが変われば倍率も変わるため、32Kの3.49倍を一般的な高速化率として扱うべきではない。

### 品質・感度・内部挙動

Llama-3.1-8B-Instructでは、15%再計算のInfoFlow KVが2WikiMQA 0.4208、MuSiQue 0.2996、HotpotQA 0.5123、NarrativeQA 0.3141を記録し、平均0.3867となる。再計算なしの平均0.3148より回復し、同じ表でCacheBlendやEPICより高い設定が多い。Qwen3-14Bでは同じ4課題平均が0.4162で、全文プリフィルの0.4114と近い一方、これは一部課題での増減が相殺された平均であり、「常に完全プリフィルより高品質」という意味ではない。

視覚言語評価でも、視覚チャンク数を増やすと再計算なしの性能が落ちる。InfoFlow KVは同じチャンク数・予算の既存再計算法に対して多くの指標で競争力を持つが、完全に分割しない標準推論との差は残る。したがって、この方式は近似を無条件に無損失化するものではなく、限られた再計算予算をどこへ使うかを改善する方式である。

RoPE位置に関する構成要素除去では、推論時と整合したグローバル位置で選ぶ設定が比較した位置設定より安定して良い。これは「問い合わせとの意味的な関連性」だけでなく、「その位置から後続生成へ情報を渡しやすいか」という位置構造も再計算対象選択に効いていることを裏付ける。

### 評価上の制約

- 主な比較は15%という固定再計算率で行われる。別の計算予算で同じ優位性が維持される範囲は、掲載された感度評価の範囲を超えて一般化できない。
- TTFTの代表値は4基のNVIDIA H100による系列並列の特定構成である。別GPU、別相互接続、別ランタイムでは通信と選択処理の比率が変わる。
- 32Kで完全プリフィルより大きく高速化しても、完全プリフィルのKVと数値的に同一のキャッシュを作るわけではない。品質は再計算対象の選択に依存する。
- チャンク並べ替えは独立文書に限定される。意味上の順序が必要な長文書・時系列入力・コード断片へ機械的に適用できない。
- 論文は取得後のKV再利用を扱う。検索器そのものの精度や取得文書の選び方を改善する手法ではない。

## 既存研究との差

CacheBlendは、文書ごとの事前キャッシュと全文脈で得られる表現の不一致を手掛かりに再計算箇所を選ぶ。これは「どこでキャッシュ誤差が大きいか」を見る考え方である。InfoFlow KVは評価軸を変え、問い合わせから実際に強く参照され、後続生成へ情報を渡せるトークンを優先する。したがって差は単なる別のスコア関数ではなく、再計算予算を「表現差の修復」から「回答生成へつながる情報経路の回復」へ寄せた点にある。

EPICなどの位置ベース方式に対しては、固定の位置規則だけを使わず、問い合わせ条件付きの注意信号と推論時RoPE位置を組み合わせる。さらに、順序交換可能な複数文書ではチャンク配置自体を情報流に合わせて変更できる点が追加差分になる。

Ring Attentionとの比較は目的が異なる。Ring Attentionは系列並列で全文脈の注意を成立させる実行方式であり、InfoFlow KVは事前キャッシュが存在する前提で再計算対象を限定する近似的な再利用方式である。したがってTTFTの差は「同じ計算をより速く実装した」差ではなく、「必要とみなす再計算とGPU間通信を減らした」ことから生じる。

## 限界・実装状況

InfoFlow KVは事前計算KVを複数要求で再利用できる環境ほど有利である。一度しか使わない文脈では、事前キャッシュの準備や選択処理を償却しにくい。短い入力では8K評価のようにRing Attentionとの差が小さく、長文脈ほど優位性が明確になる。

方式は問い合わせ注意を重要度の代理信号として使うため、限られた予算で必要な依存をすべて回復できる保証はない。再計算率を下げすぎた場合、複数文書をまたぐ推論に必要なトークンを落とす可能性がある。また、独立キャッシュを混ぜる以上、全文脈を最初から処理したKVと完全に一致することは目的としていない。

論文のarXiv v3はICML 2026論文であり、一次資料にはプロジェクトページが記載されている。一方、このリポジトリで確認している書誌メタデータ上では公式コードURLを確定していない。実運用へ組み込む場合は、キャッシュ作成・保存、グローバル位置管理、選択用注意計算、選択トークンの通信と再計算を既存サービング基盤へどう統合するかが追加実装点になる。

## 一般的な実装上の含意

事前キャッシュを使う長文脈RAGでは、「キャッシュがあるか」だけでなく、そのキャッシュがどの因果文脈で作られたかを区別する必要がある。異なる文書を独立にKV化して後から連結する方式は、計算量を大きく減らせる一方、文書間依存を暗黙に捨てている。したがって再利用率だけを最適化すると回答品質を損ねる可能性がある。

InfoFlow KVの結果は、限られた再計算予算を一様に配るより、問い合わせとの関係と位置構造を使って集中配分する方が有効であることを示す。また系列並列では、演算量だけでなく「どのKVをGPU間で共有する必要があるか」がTTFTを左右する。KV再利用方式を評価するときは、再計算率、GPU間通信量、TTFT、回答品質を同じ条件で対応付けて見る必要がある。
