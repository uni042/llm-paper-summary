# Elastic KV Cache for LLM Serving: A Working Reclamation Mechanism, and Why Chunked Prefill Already Closes the Gap

> vLLMは大きなプリフィルに備えて一時活性値用GPUメモリを常時予約するため、デコード中はその領域が遊ぶ。Elastic KVキャッシュはCUDA仮想メモリを使い、デコード中だけその予約領域をKVキャッシュへ貸し、プリフィル直前に返す機構を実装する。しかし実験ではプリフィル 分割片を小さくする単純設定でもほぼ同じTTFTでより多くKVを確保でき、複雑なelastic機構の実用上の優位を見つけられなかったという否定的な結果が中心。

## 書誌情報

- **著者**: Sathishkumar Sivashanmugam
- **公開**: 2026-08-24, arXiv v1
- **種別**: プレプリント（preprint）
- **主題**: KVキャッシュ容量、入力処理（プリフィル）、CUDA仮想メモリ管理（CUDA Virtual Memory Management; VMM）、vLLM、メモリ再利用
- **実装**: userspace CUDA VMM、PyTorch pluggable 割当器、KV ブロック-プール 判定門、スケジューラ 制御器として実装。注意機構 カーネルやGPU ドライバの修正は不要。

## 概要

この論文は、提案機構そのものよりも**「複雑な仕組みを作って正しく動かしたが、もっと単純な既存設定がほぼ同じ問題を解いていた」**という否定的な結果が重要な研究である。

LLM 提供処理ではGPUメモリの大部分を、

- モデル重み
- KVキャッシュ（KVキャッシュ）
- 一時活性値

が取り合う。

KVキャッシュを多く置けるほど、より多くのリクエスト・より長い文脈を同時にデコードできる。一方、長い入力をプリフィルするときは巨大な活性値が一時的に必要になる。

vLLMは安全にプリフィルできるよう、起動時に最大級プリフィルで必要になる活性値領域を見積もり、その分を**常時KV プールから差し引いて予約**する。

問題は、デコード-のみ時間にはその大きな活性値 作業領域を使わないことである。対話 提供処理では長い時間デコードだけが続くため、「使っていない予約メモリをその間だけKVキャッシュへ貸せないか」という発想が自然に出る。

Elastic KVキャッシュはこれを実際に実装する。

しかし著者が比較すると、vLLMの`max_num_batched_tokens`を小さくし、プリフィルを小さな分割片へ分割するだけで活性値 最大値自体を小さくできる。結果として、elasticに貸し借りするより**最初から小さい予約領域にする方が簡単で、KV容量も大きく、TTFT悪化も約1%しかない**条件が見つかる。

したがって論文の結論は「Elastic KVキャッシュを導入すべき」ではなく、「機構は成立するが、現在のvLLMでは単純な分割 プリフィルが強い比較対象なので、elastic メモリ 共有が本当に必要な領域は狭い」というものになる。

## 問題設定

### Prefillとdecodeでは必要メモリの種類が違う

入力処理（プリフィル）では、プロンプト中の多数トークンをまとめてTransformerへ通す。

このとき各層で大きな行列演算を行うため、一時的な中間活性値が増える。プロンプト 分割片が大きいほど活性値 最大値も大きくなりやすい。

一方、逐次生成（デコード）では各リクエストにつき1stepで1token程度しか増えないため、プリフィルほど大きな一時活性値は要らない。その代わり、多数リクエストの長い履歴を保持するKVキャッシュが大きくなる。

つまり理想的には、

- プリフィル時: 活性値へ多め
- デコード時: KVキャッシュへ多め

とGPU メモリの用途を時間で変えたい。

### なぜvLLMは最初から全部KVへ使わないのか

もしデコード時の空きだけ見てKVを最大化すると、突然大きなプリフィル リクエストが来たとき活性値を置く場所がなくなり、OOMになる。

そこでvLLMは起動時profilingで最大活性値 最大値を見積もり、常にその余白を残す。

これは安全だが、デコード-のみ期間には予約領域がアイドルになる。

論文のQwen2.5-7B / A100 40GB例では、プリフィル 分割片 大きさを2048から32768へ大きくするとKV 容量が約366K トークンから308K トークンへ減り、約3.1 GiB級の活性値 予約領域が生じる。

## 手法のあらまし

Elastic KVキャッシュは、GPU上のKV バッファに**大きな連続仮想アドレス範囲**を最初から確保しておく。

その仮想範囲を、

- 常に物理メモリが割り当てられている基部部分
- デコード中だけ追加で物理メモリを割り当てるelastic部分

に分ける。

注意機構 カーネルからは一つの連続KV バッファに見えるが、裏側ではelastic部分だけを対応付け/割当解除できる。

スケジューラは次のバッチがデコード-のみならelastic メモリを確保してKV ブロック プールを増やす。プリフィルが来る直前には、そのKV ブロックを使っているリクエストがないことを確認してプールから外し、物理メモリ 対応付けを解除して活性値へ返す。

この仕組み自体は正しく動作し、大きなプリフィル前にメモリを返せばOOMを避けられる。

## 手法

### 1. CUDA VMM — 仮想アドレスと物理GPUメモリを分離する

通常の`cudaMalloc`では、あるポインタへ割り当てた物理メモリを途中から部分的に増減するのは扱いにくい。

仮想メモリ管理（Virtual Memory Management; VMM）はOSの仮想メモリに近く、まず大きな**仮想アドレス範囲**を予約し、その一部へ後から物理メモリハンドルを割り当てられる。

Elastic KVキャッシュは、各層のKV領域について

```text
[ base KV | elastic KV ]
```

という連続virtual rangeを予約する。

基部部分は常時対応付けし、elastic部分だけをデコード/プリフィル状態に応じて追加・解除する。

### 2. なぜkernelを変更しなくてよいのか

物理的にはelastic領域が存在したり消えたりするが、仮想アドレス上ではKV バッファの位置は変わらない。

注意機構 カーネルは従来どおり「この基部 ポインタからブロック id分進んだ場所」にアクセスするだけでよい。

つまりメモリ 割当器とスケジューラ側で可変性を実現し、注意機構 カーネルへ特殊なページ faultや分岐を入れない**カーネル-透過的**な設計である。

### 3. Commit — decode中に空きreserveをKVへ貸す

次のバッチがデコード-のみだとスケジューラが分かれば、elastic部分へ物理GPU メモリを対応付けする。

その後、新しく使えるKV ブロック IDをブロック プールへ追加する。

これで通常なら活性値 予約領域として遊んでいた領域へ、追加リクエストのKVを格納できる。

### 4. Decommit — prefill前にKV blockを回収する

プリフィルが来る前にはelastic メモリを活性値へ返す必要がある。

しかしelastic KV ブロックをまだリクエストが使っている状態で割当解除すれば破壊的になる。

そこで制御器は、まずelastic ブロックを新規割り当て対象から外し、既存使用分がなくなるまで**排出**する。その後物理対応付けを解除する。

これにより注意機構 カーネルから見て無効なKV ポインタを踏むことを防ぐ。

### 5. Schedulerが1step先を知ることを利用する

LLM スケジューラは次バッチを組む時点で、

- デコード トークンだけを処理するのか
- 新しいプリフィルを含むのか

を知っている。

Elastic KVキャッシュはこの情報を使い、デコード-のみなら確保、プリフィル直前なら確保解除する。

完全に予測不能な将来を当てるのではなく、**スケジューラがすでに持っている次ステップ情報**でメモリ 状態を切り替える。

### 6. Static overcommitが危険であることを実証する

「デコードで使えるなら、予約領域を最初からKVへ足しておけばいい」とすると、プリフィルが来た瞬間OOMになる。

論文では予約領域全量を静的にKVへ足すとKV 容量が約314K→370K トークンへ増える一方、62K-トークン プリフィル 集中処理で約2.3 GiBの活性値が必要になりOOMする。

動的切替ならプリフィル前にelastic部分を数msで確保解除し、この集中処理を完走する。

したがって機構の正しさ自体は確認されている。

## ここからが論文の重要なnegative result

### 7. Prefill chunkを小さくすると、そもそもreserveが小さくなる

vLLMは長いプロンプトを一度に全部プリフィルせず、小さな分割片へ分けて処理できる。

例えば32K トークンを一度に処理するより、8Kずつ4回に分ければ、1回に必要な活性値 最大値は小さくなる。

活性値 予約領域も小さくできるので、起動時からより多くGPU メモリをKVキャッシュへ割り当てられる。

この方法はVMM 確保/確保解除、ブロック 排出処理、制御器 処理規則を追加しない。単なるスケジューラ パラメータである。

### 8. 「小さいchunkはTTFTを大きく悪化させる」という前提を実測する

分割片を小さくすればプリフィル カーネルの起動回数は増え、バックグラウンド デコードと交互実行する回数も増えるため、TTFTが悪化しそうに見える。

ところが実測では8192-トークン 分割片と32768-トークン 分割片の中央値 TTFT差は約1%しかなかった。

理由として論文は、プリフィルが計算-上限で総FLOPs自体は大きく変わらず、バックグラウンド デコードが使うトークン 予算も小さいため、分割片間へデコードを挟むヘッド-of-line ペナルティが想定ほど大きくないことを挙げる。

## 評価

### まず見るところ

- **機構**: CUDA VMMで活性値 予約領域をKVへ安全に貸し借りできることは実証。
- **切替コスト**: 3.09 GiB / 28 層で確保解除 3.8 ms、再確保 23.8 ms。
- **安全性**: 静的 over確保は長いプリフィルでOOM、動的 切替は完走。
- **しかし**: 分割片 8192の方がElastic 32768よりKV 容量が大きく、中央値 TTFT差も約1%。
- **結論**: 評価範囲ではElasticが単純な 分割片 削減を上回る構成を見つけられない。
- **価値**: working 機構と同じくらい、複雑なoptimizationが不要だったことを示す否定的な結果が重要。

## 主要結果の読み方

この論文は「動的メモリ 回収は失敗した」という単純な話ではない。

技術的には、

- カーネルを変えず
- CUDA VMMだけで
- デコード中はKV 容量を増やし
- プリフィル前に安全に回収し
- CUDA グラフやプレフィックス キャッシュと共存する

機構を作れている。

しかしシステム研究では、**機構が動くことと、それが最善の設計であることは別**である。

Elastic KVキャッシュが解こうとした問題は「大きい プリフィルに備えた予約領域がデコード中に遊ぶ」ことだった。ところがプリフィル 分割片を小さくすれば予約領域自体を小さくできる。

その単純な 比較対象がほぼ遅延 ペナルティなしでより多くKVを確保できたため、少なくとも評価環境では複雑な貸し借り機構を導入する理由が弱くなった。

この否定的な結果は重要で、今後似たメモリ 共有機構を提案する研究は、**分割型 プリフィルのような既存パラメータ tuningを強い比較対象として比較すべき**ことを示す。

## 品質への影響

KV内容や注意機構計算は変更しない。

論文は切替前後でbit-identical 生成を確認しており、機構自体にモデル品質trade-offはない。

riskは品質ではなく、メモリ回収タイミングを誤って使用中ブロックを割当解除するようなシステム correctness側にあるため、ブロック 排出とプール 判定門が重要になる。

## 既存研究との差

- **vAttention**: ドライバ 修正を使ったUVM demand paging等でKV メモリを仮想化する。Elastic KVキャッシュはuserspace CUDA VMMで活性値 予約領域とKV プールを時間共有する。
- **Jenga等のKV sizing**: 固定メモリ 予算内でKV 割り当てを調整する。Elasticは同じ物理メモリの用途をプリフィル/デコード 段階で切り替える。
- **Chunked プリフィル**: 本来は提供処理 fairness/遅延等のためのスケジューラ機構だが、活性値 最大値削減というメモリ効果が強く、Elasticの直接比較対象になる。

## 限界

- 主評価はA100 40GB、Qwen2.5-7B、vLLM 0.23.0中心。
- H100/B200、別モデル、別提供処理 エンジンでは活性値/KV比率が異なり結論が変わり得る。
- メモリ-上限 プリフィルでは小さい 分割片の性能ペナルティが大きくなり、Elasticが有利になる可能性が残る。
- Tensor 並列性で予約領域比率が小さくなり、elastic 余地も縮小する。
- VMM 再割当 コストやfragmentation特性はGPU/ドライバ世代に依存する。
- 論文の評価範囲では単純な 分割片 削減を上回る領域を発見できていないため、production導入を支持する性能証拠は弱い。

## 一般的な実装上の含意

この研究から最も一般化しやすい教訓は、**新しい動的機構を作る前に、静的パラメータを変えるだけで同じ資源不足を解消できないか確認する**ことである。

LLM 提供処理のメモリ問題では、

1. 本当に使われていないメモリがあるか
2. その予約領域がなぜ必要なのか
3. ワークロード パラメータを変えれば予約領域自体を減らせないか
4. 動的 回収の切替コストはいくらか
5. 単純な 比較対象より容量 / 遅延 / reliabilityで明確に勝つか

を順に見るべきである。

また否定的な結果を残す価値も大きい。機構が正しく動くところまで実装したうえで「現状では不要」と示せば、後続研究が同じ複雑化を繰り返すのを防げる。
