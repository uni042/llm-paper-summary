# HybridGen: Efficient LLM Generative Inference via CPU-GPU Hybrid Computing

> HybridGenはKVをCPU/GPUへ分けて各側で注意を計算しGPUで正規化し、次層CPU計算・PCIe転送・GPU計算も重ねて長文デコードの転送／CPU律速を減らす方式。

## 概要

長文生成でKVをCPUへ退避すると、GPU側のKV転送またはCPU側注意計算のどちらかが律速になる。HybridGenはKV所在に応じて注意スコアをCPU/GPUへ分割し、選択したVとスコアだけをGPUで統合し、次層CPU計算・転送・GPU計算を重ねる。A100/H100/RTX 5090実機で評価し、InfiniGen比最大1.41倍、Keyformer比1.86倍、FlexGenやMoE-Lightning比最大3.2倍の速度向上と、完全注意との差平均0.02の精度差を報告した。

## 問題設定
長文生成では各トークンの鍵・値（KV）を全層で保持するKVキャッシュが文脈長に比例して増え、GPUメモリだけでは保持できなくなる。そこでKVをCPU DRAMへ退避する方式が使われるが、GPUで注意機構を計算する方式では生成トークンごとに大量のK/VをCPUからGPUへ戻す必要があり、文脈が長いほどPCIe転送が律速になる。逆にCPU側で注意機構を計算すれば転送は減るものの、CPUの行列・ベクトル計算能力がGPUより低いため、長文ではCPU側の注意計算が律速になる。論文の動機分析では64K文脈の例でCPU側処理量がGPU側の約5倍まで偏る場合があり、既存方式がCPUかGPUの片側だけを主計算主体にすることで、もう片側の計算能力を十分使えていない点を問題視する。さらにCXL拡張メモリを容量確保に使うと、DRAMより遠いNUMA階層へのアクセス遅延がCPU注意計算へ直接乗りやすい。
## 新規性
HybridGenは、注意機構をCPUかGPUのどちらか一方へ丸ごと置くのではなく、KVキャッシュの所在に合わせて注意スコア計算を分割し、CPUとGPUがそれぞれ手元のKV部分を同時に処理する。CPUが計算した局所スコアと必要なVだけをGPUへ送り、GPU側の局所スコアと結合して全トークンに対する正規化・値集約を行うため、KV全量の往復を避けつつGPU計算能力も使える。さらに、層間で入力表現が大きく変わらない性質を利用してCPUが次層の注意スコアを投機的に先行計算し、CPU側処理とGPUの現層計算を重ねる。実行時にはCPU計算時間・転送時間・GPU段階時間を観測してCPU側で扱うトークン数Kと選択方式を切り替え、容量階層ではCPU計算に必要なKベクトルをDRAM、GPUへ送るだけのVベクトルをCXLへ優先配置する。計算分割、動的負荷調整、意味別メモリ配置を同じ実行経路へ統合する点が中心的な新規性である。
## 手法
### 手法のあらまし
各デコード層で、GPUはGPUメモリに残っているKVに対する注意スコアを計算する。一方CPUはCPU側に退避されたKに対して同じ問い合わせベクトルとの内積を計算し、その局所スコアを得る。CPU側KVすべてをGPUへ送る代わりに、選択されたトークンのスコアと対応するVだけをGPUへ転送する。GPUはCPU側とGPU側のスコアを論理トークン順へ結合し、全体のsoftmaxを計算してVの重み付き和を作る。その後の注意出力、全結合ネットワーク（FFN）などはGPUで通常どおり進める。

このCPU処理をGPU処理と重ねるため、HybridGenは層iのGPU計算中にCPUが層i+1向けの注意スコアを先行計算する。次層の正確な入力がまだ得られていない時点では現層入力を近似として使い、連続層の隠れ状態が類似するという観測を利用する。CPU結果が必要になる頃にはGPU側の現層処理が進んでいるため、CPU計算時間の大部分を隠せる。誤差はトークン選択の近似として現れ、最終的なK選択下限で品質を制約する。

CPU側で何トークンを処理するかは固定しない。フィードバックスケジューラがGPU段階時間T_gpu、CPU注意スコア時間T_cpu、CPUからGPUへの転送時間T_txを継続的に観測する。CPU処理と転送がGPU段階より短く、十分隠せる場合はCPU側候補Kを増やして精度を上げる。反対にCPU側が遅ければKを減らす。品質評価から事前に決めたK_minまで減らしても追いつかない場合は、全CPU側Kを先にスコアリングしてから上位Kを取る方式から、軽量予測器で先に候補Kを選んで必要部分だけスコアリングする方式へ切り替え、CPU計算量そのものを削減する。

メモリ階層ではKとVの役割を分ける。CPUはKを直接読んで注意スコアを計算するため、Kを低遅延のCPU DRAMへ優先配置する。VはCPU計算では使わず、選択後にGPUへ送るだけなので、DRAM不足時にはCXL拡張メモリへ置き、CXLからGPUへのDMA転送に任せる。これによりCXLの高いCPUアクセス遅延を注意計算のクリティカルパスから外す。DRAMも不足すると、古く生成されたKから退避対象を選ぶ。

### CPU-GPU分割注意スコア計算
入力は現在トークンの問い合わせベクトルと、GPU・CPUの各階層に分散して保持された過去トークンのK/Vである。GPUはGPU上のKに対する局所スコアを、CPUはCPU DRAM上のKに対する局所スコアを並列に計算する。CPUからGPUへはKV全量ではなく、選択したトークンの注意スコアと対応Vだけを送る。GPUは両側のスコアを結合して全体softmaxとV集約を行うため、論理的には一つの注意機構として出力を後段のTransformer計算へ渡せる。CPU側でスコアを作ることでK転送を削り、GPU側にも計算を残すことでCPU単独注意の計算律速を避ける。代償はCPU側スコア計算と部分V転送、および選択したトークンだけを用いる近似誤差である。

### 層間投機によるCPU計算の重ね合わせ
Transformerは層iの出力が層i+1の入力になるため、そのままではCPUとGPUを層単位に直列実行するしかない。HybridGenは連続層の入力表現が高く類似するという実測を利用し、層iのGPU計算中にCPUが層iの入力を代用して層i+1で必要になるCPU側注意スコアを先行計算する。出力は次層で使う候補トークンの重要度と局所スコアで、GPUが次層へ到達するまでCPU計算時間を隠す。入力近似が外れると選択順位が変わり得るため、これは厳密な計算再順序化ではなく精度交換を伴う投機である。

### フィードバック型K・選択方式制御
スケジューラは各段階の実測時間T_gpu、T_cpu、T_txを入力として、CPU側から利用するトークン数Kを毎回調整する。CPU計算と転送がGPU処理に隠れている間はKを増やし、より多くの過去トークンを注意計算へ残す。CPU側がクリティカルパスへ出るとKを減らし、事前の精度評価から設定したK_minを下限とする。K_minでも遅い場合、全CPU側Kを計算してから上位Kを決める後段選択から、軽量な重要度予測で候補を絞ってから内積を計算する前段選択へ切り替える。これにより速度だけを追ってKを無制限に削るのではなく、最低品質制約を守りつつCPUとGPUの処理時間を揃える。

### K/Vの意味に基づくDRAM-CXL配置
CPU注意スコア計算はKを必ず読むがVは読まないというアクセス意味を利用する。CPU計算の入力になるKは低遅延のDRAMへ残し、選択後にGPUへ運ぶだけのVはDRAMが足りなくなった時点でCXL拡張メモリへ置く。CPUがKを読むたびに遠いCXLへアクセスする経路を避ける一方、Vは選択された分だけCXLからGPUへDMA転送するので、CPUを中継する必要がない。単純なページ交互配置ではKとVの区別なく両階層へ散るため、注意スコア計算のたびにCPUがNUMA遅延を受け、CXL容量を増やしても計算時間が悪化し得る。HybridGenではKのCPU計算をDRAMに閉じ込め、Vの大容量保持だけを遠い階層へ逃がすことで、容量拡張とCPU計算速度を両立させる。代償としてK/V別の配置台帳と転送経路管理が必要になり、DRAM自体もKで満杯になれば古いKをさらに退避するため、この利点にも容量上限がある。

### GPU追い出しと論理トークン順の復元
GPUメモリ圧力が高まると古いKVをCPU側へ退避し、どのトークンがGPU、DRAM、CXLのどこにあるかをトークン Mapperが継続的に管理する。CPUとGPUは物理的に別々の部分集合について注意スコアを計算するため、そのまま結合すると元の系列順と配置順が一致しない。そこでトークン ConcatenatorがCPU側スコア、GPU側スコア、対応Vを元の生成トークン順へ並べ直してから全体softmaxと値集約へ渡す。これにより配置や追い出し先が反復ごとに変わっても、後段の注意機構は一貫した論理系列として扱える。追い出しはGPU容量を確保する一方、CPU側トークンが増えるほどCPUスコア計算とV転送が増えるため、単なる容量管理だけでは性能を保証できない。フィードバックスケジューラがKと選択方式を同時調整し、物理配置変化による負荷増大をGPU計算時間内へ収めようとする点まで含めて一つの機構である。

### 全体のデータ／制御の流れ
デコード時の一層を時間順に見ると、まずGPUが現層の局所注意と後段計算を行うのと並行して、CPUは次層向けの選択・局所注意スコアを投機的に作る。CPU側ではDRAM上のKを読み、選択されたVはDRAMまたはCXLからGPUへ送る。GPU側では自分が保持するKVについて局所スコアを計算し、CPUから届いたスコアとVをトークン順に結合して全体のsoftmaxと値集約を行う。各反復のT_gpu、T_cpu、T_txは次回のKと選択方式へフィードバックされる。この循環により、文脈長やGPU/CPU性能が変わっても片側へ固定した構成より負荷を均衡させる。FlexGen上の試作ではPython側で分割注意・先読み・制御を管理し、C++側のPyTorch CPUアロケータでDRAM/CXL配置を行う。失敗条件はCPUがK_min・前段選択でもGPU段階に追いつかない場合、PCIe/CXL転送がGPU計算より長い場合、層間入力類似性が低く投機選択が外れる場合、または品質制約が大きなKを要求して負荷均衡余地がなくなる場合である。
## 評価条件
- **ハードウェア**: Machine A: Intel Xeon Gold 5320 + NVIDIA A100 80GB + 128GB CPU DRAM、Linux 5.14、CUDA 12.1、Machine B: Intel Xeon Gold 6530 + NVIDIA H100 NVL 94GB + 512GB CPU DRAM、CUDA 12.5、Machine C: Intel Xeon 6960P + NVIDIA RTX 5090 32GB + 128GB CPU DRAM + 128GB CXLメモリ（DDR4-3200、PCIe 5.0）、CUDA 12.8
- **ソフトウェア**: FlexGen基盤のHybridGen試作、PyTorch（CPUアロケータをmbind対応へ変更）、Linux NUMAメモリ配置、LM Evaluation Harness（品質評価）
- **モデル**: OPT 1.3B〜13B、Llama系 1B/3B/7B/8B級、Qwen2.5 1.5B〜14B
- **データセット／トレース**: PIQA、OpenBookQA、COPA、RTE
- **比較対象**: FlexGen、MoE-Lightning、Keyformer、H2O、StreamingLLM、InfiniGen
- **正確性・品質**: HybridGenはCPU側の全トークンへ常に厳密な注意計算を行う方式ではなく、トークン選択と層間入力の投機的近似を含む。したがって完全注意とビット単位に同一ではない。著者らはK_minをオフライン品質評価から決め、実行時にそれを下回らない制約を設ける。PIQA、OpenBookQA、COPA、RTEの3-shotでは完全注意との平均精度差0.02を報告し、固定・攻撃的な選択方式より品質低下を抑えている。
- **通常性能評価**: 三つのCPU-GPU構成でOPT、Llama、Qwen系を評価する。既定は系列長2K、バッチ1で、モデルサイズ・GPU世代・バッチ数を変えて既存の全量KV退避、CPU注意、前段・後段KV選択方式と比較する。
- **長文評価**: Qwen2.5-7BとLlama-3.1-8B級モデルを中心に系列長を2Kから32Kへ伸ばし、CPU注意計算とCPU-GPU転送が増える条件でHybridGenの動的K制御と選択方式切替が速度を維持できるか測る。
- **バッチ拡大**: OPT-13Bなどでバッチを増やし、GPU計算・CPU計算・転送の相対比が変化したときの速度向上を確認する。固定したCPU/GPU分担ではなく、実測フィードバックでKを変える効果を見る。
- **CXL階層評価**: RTX 5090機の128GB DRAM + 128GB CXLメモリで、K/Vを意味に関係なくページ単位で交互配置する方式と、KをDRAMへ優先しVをCXLへ置くHybridGenの意味別配置を比較する。モデルが大きくなりCXL利用量が増える条件ほど差を見る。
- **品質評価**: LM Evaluation HarnessでPIQA、OpenBookQA、COPA、RTEを3-shot評価し、完全注意と選択型方式の精度差を比較する。HybridGenはK_minを事前品質測定で決め、実行時制御がその下限を下回らない。
- **スケジューラ分解評価**: 前段選択を固定する高速設定、後段選択を固定する高精度設定、選択方式だけを適応する設定、Kも適応する完全設定を比較し、速度と精度の寄与を分離する。
評価は単一GPU世代に限定せずA100、H100 NVL、RTX 5090を用い、サーバCPUとCXL拡張メモリを含む三つの実機構成で行う。比較対象はGPU側で全KVを処理する退避方式、CPU注意方式、注意前に候補を減らす方式、注意スコア後に候補を減らす方式を含む。系列長、モデルサイズ、バッチ、メモリ階層を変え、さらに品質とスケジューラ分解を測ることで、単なる1構成の最適化ではなくCPU/GPUの負荷不均衡へ適応する設計の効果を検証する。
中心評価は生成時デコードのKVキャッシュ処理であり、プリフィル全体の最適化が主題ではない。CXLの意味別配置はCXL搭載Machine Cでの評価に基づき、他のCXL製品・遠隔メモリ構成へ一般化できるかは未検証である。試作はFlexGenとPyTorch CPUアロケータ改変に基づき、vLLM/SGLangなど本番サービング基盤への統合性能は評価していない。
## 主要結果
HybridGenは、CPUまたはGPUの片側だけで注意機構を処理する比較方式に対し、KVの物理配置に合わせてCPUとGPUへ注意スコア計算を分け、実行時にCPU側トークン数と選択方式を調整することで一貫した速度改善を示した。論文の総括ではInfiniGen比で平均最大1.41倍、Keyformer比1.86倍、全量注意・退避系のFlexGenやCPU注意系MoE-Lightningに対して最大3.2倍の速度向上を報告する。長文になるほど全KV転送またはCPU単独計算の負担が増えるため、CPU/GPUを重ね合わせる利点が大きくなる。CXL環境ではKをDRAM、VをCXLへ分ける配置が単純なページ交互配置より有利で、容量拡張のNUMA遅延をCPU注意のクリティカルパスから外す設計意図を実測で支持した。品質面では完全注意との平均精度差を0.02に抑え、速度だけを優先する固定の前段選択より品質を保った。

- InfiniGenに対する平均速度向上 / 最大1.41倍 (比較対象: InfiniGen; 条件: 複数モデル・三つの実機構成を含む論文総括) — 注意計算前にKV候補を減らす既存方式に対しても、CPU/GPU協調と動的負荷調整で追加改善した。

- Keyformerに対する平均速度向上 / 最大1.86倍 (比較対象: Keyformer; 条件: 複数モデル・実機評価の総括) — CPU側で全候補スコアを計算してから選択する後段方式のCPU負荷を、分割計算と選択方式切替で緩和した。

- 全量KV処理系に対する最大速度向上 / 最大3.2倍 (比較対象: FlexGen / MoE-Lightningなど全量注意・退避系; 条件: 長文を含む評価) — GPUへ全KVを戻す転送律速とCPUへ注意を寄せる計算律速の双方を避けた効果が大きい条件。

- Qwen2.5-7B長文での前段選択方式比 / 平均最大1.82倍 (比較対象: StreamingLLM / InfiniGen系の前段選択; 条件: 系列長2K〜32K) — 文脈長に応じてCPU/GPU負荷が変わっても固定方式より高い処理性能を維持した。

- Llama-3.1-8B長文での前段選択方式比 / 平均最大2.34倍 (比較対象: 前段KV選択方式; 条件: 系列長2K〜32K) — 長文化で既存方式の固定した計算場所・選択量が律速になりやすい条件ほど動的協調の利得が増えた。

- 長文での後段選択方式比 / Qwen系最大2.66倍、Llama系最大3.18倍 (比較対象: Keyformer / H2O系の後段選択; 条件: 系列長2K〜32K) — CPU側で全候補の注意スコアを作る負荷が文脈長とともに増える比較方式に対し、必要時に前段選択へ切り替える効果が表れた。

- OPT-13Bのバッチ拡大時速度向上 / 前段方式比最大1.5倍、後段方式比最大1.87倍 (比較対象: KV選択比較方式; 条件: バッチ数を増加させた実機評価) — 単一バッチだけでなく計算比率が変わる条件でもフィードバック制御が有効だった。

- 品質差 / 完全注意との平均精度差0.02 (比較対象: 完全注意; 条件: PIQA、OpenBookQA、COPA、RTE、3-shot) — 選択型の近似方式だが、最低K制約と適応制御により主要品質指標をほぼ維持した。

### 負の結果・境界条件
- **後段選択固定は長文でCPU律速**: CPU側の全オフロードトークンについて注意スコアを計算してから上位Kを選ぶ方式は精度を保ちやすいが、文脈長が増えるほどCPU計算量が線形に増え、最も遅い固定構成になる。HybridGenが選択方式自体を切り替える理由である。
- **前段選択固定は速度優先だが品質余地が小さい**: 注意内積の前に候補を絞る方式はCPU計算を最も減らせる一方、重要トークンを外す近似が強くなり、固定で攻撃的に使うと完全注意に対する精度差が大きくなる。HybridGenはCPUに余裕がある局面ではKを増やすか後段選択を使う。
- **単純なDRAM/CXL交互配置はCPU計算を遅くする**: KとVを意味に関係なくページ単位でDRAMとCXLへ散らすと、CPUが注意スコア計算のたびにCXL上のKへアクセスしNUMA遅延を受ける。容量を増やすだけでは性能が伸びず、K/Vの役割別配置が必要だった。
- **CPU側負荷を完全には消せない**: KをK_minまで減らし前段選択へ切り替えてもCPU計算や転送がGPU段階より長い構成では、CPU側処理がクリティカルパスへ残る。HybridGenは負荷を均衡させるが、CPU/GPU性能差や帯域制約そのものを取り除くわけではない。

### 結果の読み方
結果の中心は、KVキャッシュの容量問題を単なる『どこへ退避するか』ではなく、『KVが置かれた場所でどの計算を済ませ、CPU・転送・GPUの三段階をどこまで重ねられるか』という実行時負荷均衡問題として扱ったことにある。全量GPU注意は転送が、全量CPU注意はCPU計算が、固定KV選択はワークロード変化への追従不足がそれぞれ律速になる。HybridGenはCPU/GPUの両方に局所スコア計算を残し、観測時間に応じてKと選択方式を変えるため、系列長・モデル・GPU世代が変わっても比較的安定した改善を得る。CXL評価はさらに、容量階層ではデータの大きさだけでなく『どちらの演算器が読むか』を配置判断へ入れることが重要だと示す。
## 品質への影響
厳密な完全注意ではなく、CPU側KVの選択と次層入力の投機近似を含む損失あり方式である。実行時スケジューラは速度のためにKを減らすが、オフライン評価で定めたK_minより小さくしない。主要品質評価では完全注意との差が平均0.02と小さい一方、固定の前段選択を強く使う方式では品質低下が大きくなるため、実運用ではモデル・タスクごとのK_min校正が前提になる。
## 既存研究との差
- FlexGenのようにKVキャッシュをCPUへ退避して必要時にGPUへ戻す方式に対し、HybridGenはKV全量を移動せず、CPU側に残したKについてCPUで注意スコアを先に計算することでCPU-GPU転送量を減らす。
- MoE-Lightningのように注意機構をCPU側へ寄せる方式に対し、CPUとGPUの両方が各自の局所KVに対する注意スコアを同時に計算するため、CPU計算能力だけが長文性能を決める構成を避ける。
- InfiniGenやStreamingLLMのような注意計算前のKV選択と、KeyformerやH2Oのような注意スコア後の選択を固定方式として選ぶのではなく、実測したCPU/GPU/転送時間に応じてKと選択時点を動的に切り替える。
- 通常のCXL容量拡張がページやテンソル単位でデータを配置するのに対し、CPU計算で読むKとGPUへ転送するVの役割差を使い、KをDRAM、VをCXLへ優先する。これによりCXL容量を使いながらCPUのNUMAアクセスを減らす。
- 既存のKVキャッシュ圧縮・枝刈り研究が『何トークン残すか』を主題とするのに対し、HybridGenは選択自体に加え『どの演算器で局所注意を計算し、いつその計算を重ねるか』まで共同で制御する。
## 限界
- CPU側KVのトークン選択と層間入力の投機近似を含むため厳密な無損失注意ではなく、モデル・タスクごとに最低Kを校正する必要がある。
- CPU計算と転送をGPU段階に隠せることが速度向上の重要条件であり、CPUが遅い、PCIe/CXL帯域が狭い、または品質制約でK_minが大きい場合はCPU側が律速として残る。
- 連続層の入力表現が類似するという性質を次層の投機計算に利用するため、その類似性が低いモデルや層では選択誤差が増える可能性がある。
- CXLの意味別配置は128GB CXLメモリを持つ一つのRTX 5090実機で評価され、異なるCXL世代・スイッチ構成・遠隔メモリで同程度の利得が得られるかは未検証。
- 試作はFlexGenを基盤としPyTorch CPUアロケータへ変更を加えている。vLLMやSGLangへの統合は設計上可能と述べるが、本番サービング基盤での多要求連続バッチ、スケジューリング競合、運用負荷は評価していない。
- 評価の中心はデコード時KV処理で、プリフィルや分散複数GPUでのKV配置、複数利用者間のキャッシュ共有などは主対象ではない。
- KとVを別階層へ置くとメモリ管理・トークン位置管理・DMA経路が複雑になり、単純なKV退避よりランタイム実装コストが高い。
## 実装状態
FlexGen上に実装した実機試作。Python側で注意スコア計算の分割、CPU/GPU重ね合わせ、フィードバックスケジューラ、先読みパイプラインを実装し、PyTorch CPUアロケータのC++側を変更してLinux mbindによるDRAM/CXL配置を行う。A100、H100 NVL、RTX 5090で評価済み。論文一次資料からHybridGen専用の公開コードリポジトリは確認できなかった。
## 研究上の位置づけ
HybridGenは、長文LLM推論のKVキャッシュ問題を階層メモリ容量だけでなくCPU-GPU間の計算配置問題として扱う研究である。KVをCPUへ置くと『GPUへ戻す転送』か『CPUで注意を計算する時間』のどちらかが律速になるという二者択一を崩し、データの所在地に合わせて注意スコア計算そのものを分割する。さらに、実行時の段階時間からCPU側トークン数と選択方式を変えるため、静的オフロードと静的KV枝刈りの間を連続的に調整する設計になっている。リポジトリではオフロード／階層メモリ系とKVキャッシュ管理系の交点に位置し、特にCXLを単なる大容量メモリとしてではなくK/Vのアクセス意味に応じて使い分ける点が、今後のCPU・GPU・CXL・SSD多階層配置にも応用可能な設計原則を示す。SSD/NVMeを直接評価する論文ではないが、『計算に必要な部分は近い階層、転送だけする部分は遠い階層』という分離はSSD活用研究との接続点になり得る。
## 監査メモ
arXiv v1の動機、設計、実装、三機種評価、長文・バッチ・CXL・品質・スケジューラ分解を確認した。1.41倍、1.86倍、最大3.2倍は比較対象が異なるため同一基準の三つの倍率として混同しない。長文評価の1.82倍/2.34倍は前段選択系に対する平均最大値、2.66倍/3.18倍は後段選択系に対する値。品質差0.02は四つの3-shotベンチマークにおける完全注意との平均差であり、厳密な無損失性を意味しない。CXL性能主張はMachine Cの実機条件に限定して解釈する。
