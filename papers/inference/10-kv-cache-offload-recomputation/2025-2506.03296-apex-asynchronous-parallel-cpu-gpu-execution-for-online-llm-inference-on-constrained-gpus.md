# APEX: Asynchronous Parallel CPU-GPU Execution for Online LLM Inference on Constrained GPUs

> 一部要求のKV キャッシュとデコード アテンションをCPUへ移しつつ、アテンション前の線形計算はCPU/GPU向け要求を一つのGPU バッチでまとめ、CPU結果を必要になる直前まで待たないことでCPU アテンションをGPU計算の裏へ隠す方式。

## 概要

APEXは、NEOやFastDecodeと同じくKV キャッシュとデコード アテンションの一部をCPUへ移してGPU メモリを空けるが、主眼は**CPU オフロードそのものではなく、CPUとGPUをどう重ねて実行するか**にある。

NEOは要求を2つの小バッチへ分け、片方のCPU アテンションと片方のGPU処理を重ねる。混合 プリフィル/デコードでは有効だが、デコードのみに近いワークロードでは、GPUが同じ線形層を小さいバッチごとに2回実行することになりやすく、バッチをまとめた方が効率の良いGPUを十分に使えない。

APEXはこの問題に対し、CPU アテンションへ回す要求とGPU アテンションへ残す要求を**アテンション直前の線形計算までは一つのGPU バッチとしてまとめて処理する**。その後アテンションだけCPU/GPUへ分岐し、CPU側結果は終わった瞬間には待たず、次に本当に必要になる直前まで同期を遅らせる。

これによりCPU アテンションへ与えられる実行時間を伸ばし、GPUがCPU待ちになる確率を下げる。さらに事前測定したCPU/GPU実行時間から、GPUのみ、NEO型の2-バッチ パイプライン、APEX型の長い非同期重複実行をワークロードごとに切り替える。

## 問題設定

NEOはonline CPU オフロードを実用化したが、デコード中心 ワークロードでは2-小バッチ構造が不利になる場合がある。

論文の観察ではデコード時のバッチ sizeが比較的小さい範囲では、GPU 線形層の実行時間はバッチ sizeを半分にしても大きく短くならない。そのため1つのバッチを2つへ分けると、線形計算を2回走らせるコストだけが増えやすい。

さらにCPU アテンションはGPU アテンションよりかなり遅く、論文のプロファイル例ではバッチ=4でCPU 3031 µsに対しGPU 170 µsだった。NEOのように短いパイプライン 窓だけでCPU計算を隠そうとすると、CPUへ割り当てられる要求数が少なくなりCPU アイドルが発生しやすい。

APEXは、**バッチ 分割を避けてGPU 線形 効率を保ち、CPU アテンションへほぼ1 反復分の長い実行時間を与える**ことでこの問題を解く。

SSD / NVMeは使わず、CPU DRAM上のKV キャッシュとCPU アテンションを対象とする。

## 手法

### 1. CPU/GPU向けrequestをまとめ、linearを一度だけ実行する

CPU アテンション予定要求とGPU アテンション予定要求を、Q/K/V 射影などアテンション前の線形計算までは同じGPU バッチへ入れる。

その後、CPUへオフロードする要求のQ/K/Vだけホストへ転送し、GPU 要求はGPU アテンション、CPU 要求はCPU アテンションを並行実行する。

これによりNEO型の2-小バッチで起こる

`linear(batch A) + linear(batch B)`

を

`linear(batch A + B)`

へまとめ、GPUのバッチ処理効率を維持する。

### 2. CPU attention結果を「終わった瞬間」ではなく「必要になる直前」に待つ

通常ならCPU アテンションが終わるまで、その層のアテンション後処理を待つ必要がある。

APEXはCPU側要求について、アテンション結果を即座にGPUへ戻して同期せず、GPU側が別要求 / 別段階を進められる間は処理を継続する。CPU結果は**次サイクルでその要求のアテンション後 線形が必要になる直前**まで待つ。

論文の **Asynchronous 重複実行** は、この「CPU処理と独立なGPU処理をできるだけ長く同時に進め、依存が発生する直前だけ同期する」実行方法を指す。

### 3. どの実行方式が有利かを事前測定から判定する

APEXはNEO方式を完全に捨てるのではなく、CPU アテンションが十分速い場合やプリフィルが長くCPU計算を隠せる場合には2-小バッチ型パイプラインも選ぶ。

事前に

- GPU 線形時間
- GPU アテンション時間
- CPU アテンション スループット
- バッチ size / 系列 lengthごとの実行時間

を測り、各方式の推定スループットを比較する。

論文のデコードのみ近似では、典型的な線形 / アテンション比の場合、CPU アテンション速度がGPUの約13%以上ないと2-小バッチ方式の追加コストを回収しにくいと分析する。実測CPUはGPUの10%未満になることが多いため、デコード中心ではAPEX型の長い重複実行が選ばれやすい。

### 4. GPU-firstでCPUはmemory pressure時だけ使う

GPUに全要求のKV キャッシュが収まる場合はGPUのみを選ぶ。CPUはGPUより遅いため、メモリ 圧力がない状況で無理にオフロードしない。

GPU メモリが不足したときにだけCPU 要求 待ち行列を使い、現在のプリフィル / デコード構成に応じて2-小バッチ型パイプラインかAPEX型重複実行を選ぶ。

### 5. CPU側にもpaged KVを直接読むattention kernelを用意する

APEXはNEOを拡張して実装され、CPU paged アテンションをLlamafile系行列 カーネルで再実装している。paged KVは小さいブロックへ分かれているため、CPU側でもそのブロック配置を直接たどりながらアテンションできる専用実装を使う。

小バッチではNEOのISPC カーネルより遅い場合があるが、大きいバッチでは最大約2倍高速と報告する。

Python 主要 スレッドがGPU カーネルを起動し、別スレッドがCPU アテンションを担当する。C++処理中はPythonのglobal lockを外し、CPU/GPUを実際にparallel実行する。

threading オーバーヘッドを償却するため、CPU 要求数が少なすぎる場合はCPU アテンションを起動しない閾値も設けている。

## 評価

### 条件

| 項目 | T4環境 | A10環境 |
|---|---|---|
| GPU | NVIDIA T4 16GB | NVIDIA A10 24GB |
| CPU | 2×Xeon Gold 6130、計32 cores | 2×Xeon Gold 6342、計48 cores |
| RAM | 180 GiB | 250 GiB |
| Model | Llama-2-7B | Llama-3.1-8B |
| Baseline | vLLM、NEO | vLLM、NEO |

ワークロードはAzure LLM 推論 トレース、LiveBench、Dolphin-r1、OpenAI Summarization Comparisonを用いる。

### Throughput

A10では実ワークロードに対して、NEO比で約6〜16%、vLLM比で約11〜22%のスループット改善を報告している。

T4ではデコード比率の高いOSC ワークロードで差が大きく、**NEO比最大72%、vLLM比最大96%**の改善を§5.2で報告している。

T4で効果が大きいのは、GPUがA10より弱いためCPU/GPU性能差が相対的に小さく、さらにVRAM制約が強いためCPU オフロードで増やせるバッチ sizeの価値が高いからである。

### Output lengthを変えた評価

A10で平均output lengthを伸ばすと、NEO比改善は

- 50〜200 トークン: 約5%
- 200〜500 トークン: 約17〜31%
- 500 トークン超: 最大約37%

へ増える。デコード時間が長いほどCPU アテンションをGPU側の別処理へ隠せる割合が増えるためである。

### Latency

T4ではaverage トークンごとの 遅延をNEOのおよそ半分まで削減した条件があり、A10でもNEOよりわずかに低い。スループット増加のために遅延を犠牲にする方式ではない。

### Ablation

主要3要素は

- CPU結果の同期を遅らせるAsynchronous 重複実行
- 新CPU paged-attention カーネル
- 実測値から戦略を選ぶ性能 モデル

である。

アブレーションではAsynchronous 重複実行が最も大きな寄与を持ち、条件によりNEO比53〜100%の改善を生む。CPU カーネルはさらに約13〜21%、戦略選択は短めのoutputで最大31%程度の追加効果を示す。

## 既存研究との差

### NEOとの違い

NEOはCPU/GPU 要求を2 小バッチへ分割してパイプライン化する。APEXはデコード中心時にこのバッチ 分割がGPU 線形を二重実行させる点を問題視し、**線形は全要求をまとめて一度だけ実行し、アテンション後の同期を遅らせる**。

またNEOのheuristic スケジューリングに対し、APEXは事前測定したCPU/GPU実行時間を使って戦略を選択する。

### FastDecodeとの違い

FastDecodeはデコード アテンションをCPUへ大きく移す固定的な構成で、十分なCPU資源を前提とする。APEXはGPU-firstで、VRAM不足時だけ必要量をCPUへ回し、CPU 性能に応じて実行方式を変える。

### FlexGenとの違い

FlexGenはoffline バッチ スループットを高めるため重み / KVの階層配置とスケジュールを最適化する。APEXはonline 推論提供、とくにchatやreasoningの長いデコードを対象に、CPU アテンションとGPU処理の時間的重複実行を最適化する。

## 限界

- 評価GPUはT4とA10のみで、A100 / H100のような大容量・高性能GPUで同じ利得が出るかは未確認。
- CPU アテンション性能とCPU/GPU性能比に依存し、CPUが相対的に弱い環境ではオフロードの効果が小さくなる。
- 戦略選択はoffline プロファイリングに依存するため、ハードウェア状態やワークロード変動でプロファイルと実測がずれる可能性がある。
- Python multi-thread 実行環境由来のオーバーヘッドがあり、CPU 要求数が少ない場合はparallel executionを起動しにくい。
- arXiv v4時点で公式コード repositoryは確認できなかった。
- arXiv v4ではT4のNEO比最大値について、概要 / §5.2が72%とする一方、conclusionに49%という古い値が残っている。ここでは実験節と最新概要の72%を採用する。

## 一般的な実装上の含意

APEXの重要な点は、異種 executionでは「CPUへ何を移すか」だけでなく、**CPU結果をいつ待つか**が性能を大きく左右することを示した点である。

依存関係が許すならCPU処理の完了直後に同期する必要はなく、GPU側が独立して進められる処理を先に実行して本来の実行時間からCPU 遅延を外す方がよい。

またCPU/GPU オフロード 戦略は固定ruleより、演算子ごとのプロファイルから「このハードウェア・バッチ・系列 lengthで本当に重複実行の利得があるか」を判定する方が、異なるGPU/CPU比率へ適応しやすい。
