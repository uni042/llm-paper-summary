# APEX: Asynchronous Parallel CPU-GPU Execution for Online LLM Inference on Constrained GPUs

> KV cacheとdecode attentionをCPUへoffloadする際、linear層はCPU/GPU requestを一つのGPU batchでまとめて実行し、CPU attention結果の同期を遅らせてGPU計算と長時間重ねることで、NEO型batch splittingのoverheadを減らすhybrid serving scheduler。

## 概要

APEXは、NEOやFastDecodeと同じくKV cacheとdecode attentionの一部をCPUへ移してGPU memoryを空けるが、主眼は**CPU offloadそのものではなく、CPUとGPUをどう重ねて実行するか**にある。

NEOのAsymmetric Pipeliningはrequestを2つのsub-batchへ分割してCPU/GPU計算を重ねる。mixed prefill/decodeでは有効だが、decode-onlyに近いworkloadでは、GPUが同じlinear層を小さいsub-batchごとに2回実行することになりやすく、batchをまとめた方が効率の良いGPUを十分に使えない。

APEXはこの問題に対し、CPU attentionへ回すrequestとGPU attentionへ残すrequestを**pre-attention linearまでは一つのGPU batchとしてまとめて処理する**。その後attentionだけCPU/GPUへ分岐し、CPU側結果はすぐ待たず、次に本当に必要になる直前まで同期を遅らせる。

これによりCPU attentionへ与えられる実行時間を伸ばし、GPUがCPU待ちになる確率を下げる。さらにoffline profilingからCPU/GPU実行時間を予測し、GPU-only、NEO型Asymmetric Pipelining、APEXのAsynchronous Overlapをworkloadごとに切り替える。

## 問題設定

NEOはonline CPU offloadを実用化したが、decode-heavy workloadでは2-sub-batch構造が不利になる場合がある。

論文の観察ではdecode時のbatch sizeが比較的小さい範囲では、GPU linear層の実行時間はbatch sizeを半分にしても大きく短くならない。そのため1つのbatchを2つへ分けると、linear計算を2回走らせるcostだけが増えやすい。

さらにCPU attentionはGPU attentionよりかなり遅く、論文のprofile例ではbatch=4でCPU 3031 µsに対しGPU 170 µsだった。NEOのように短いpipeline windowだけでCPU計算を隠そうとすると、CPUへ割り当てられるrequest数が少なくなりCPU idleが発生しやすい。

APEXは、**batch splittingを避けてGPU linear efficiencyを保ち、CPU attentionへほぼ1 iteration分の長い実行windowを与える**ことでこの問題を解く。

SSD / NVMeは使わず、CPU DRAM上のKV cacheとCPU attentionを対象とする。

## 手法

### 1. Unified batchでlinearを一度だけ実行する

CPU attention予定requestとGPU attention予定requestを、Q/K/V projectionなどpre-attention linearまでは同じGPU batchへ入れる。

その後、CPUへoffloadするrequestのQ/K/Vだけhostへ転送し、GPU requestはGPU attention、CPU requestはCPU attentionを並行実行する。

これによりNEO型の2-sub-batchで起こる

`linear(batch A) + linear(batch B)`

を

`linear(batch A + B)`

へまとめ、GPUのbatch処理効率を維持する。

### 2. CPU attention結果の同期を遅らせる

通常ならCPU attentionが終わるまで、そのlayerのpost-attention処理を待つ必要がある。

APEXはCPU側requestについて、attention結果を即座にGPUへ戻して同期せず、GPU側が別request / 別stageを進められる間は処理を継続する。CPU結果は**次cycleでそのrequestのpost-attention linearが必要になる直前**まで待つ。

これによりCPUはGPU attentionだけでなく、GPU側のlinearや他layer処理を含むより長い時間帯の裏でattentionを進められる。

### 3. Asymmetric Pipeliningが本当に有利かperformance modelで判定する

APEXはNEO方式を完全に捨てるのではなく、CPU attentionが十分速い場合やprefillが長くCPU計算を隠せる場合にはAsymmetric Pipeliningも選ぶ。

offline profilingで

- GPU linear時間
- GPU attention時間
- CPU attention throughput
- batch size / sequence lengthごとの実行時間

を測り、2-sub-batch方式のthroughputがGPU-onlyを上回る条件を解析式で判定する。

論文のdecode-only近似では、典型的なlinear / attention比の場合、CPU attention速度がGPUの約13%以上ないとAsymmetric Pipeliningのoverheadを回収しにくいと分析する。実測CPUはGPUの10%未満になることが多いため、decode-heavyではAsynchronous Overlapが選ばれやすい。

### 4. GPU-firstでCPUはmemory pressure時だけ使う

GPUに全requestのKV cacheが収まる場合はGPU-onlyを選ぶ。CPUはGPUより遅いため、memory pressureがない状況で無理にoffloadしない。

GPU memoryが不足したときにだけCPU request queueを使い、現在のprefill / decode構成に応じてAsymmetric PipeliningかAsynchronous Overlapを選ぶ。

### 5. CPU paged attention kernelと非同期runtime

APEXはNEOを拡張して実装され、CPU paged attentionをLlamafile系matrix kernelで再実装している。小batchではNEOのISPC kernelより遅い場合があるが、大きいbatchでは最大約2倍高速と報告する。

Python main threadがGPU kernelをlaunchし、別threadがCPU attentionを担当する。Pybind11でC++処理中にGILをreleaseし、CPU/GPUを実際にparallel実行する。

threading overheadを償却するため、CPU request数が少なすぎる場合はCPU attentionを起動しないthresholdも設けている。

## 評価

### 条件

| 項目 | T4環境 | A10環境 |
|---|---|---|
| GPU | NVIDIA T4 16GB | NVIDIA A10 24GB |
| CPU | 2×Xeon Gold 6130、計32 cores | 2×Xeon Gold 6342、計48 cores |
| RAM | 180 GiB | 250 GiB |
| Model | Llama-2-7B | Llama-3.1-8B |
| Baseline | vLLM、NEO | vLLM、NEO |

workloadはAzure LLM inference trace、LiveBench、Dolphin-r1、OpenAI Summarization Comparisonを用いる。

### Throughput

A10では実workloadに対して、NEO比で約6〜16%、vLLM比で約11〜22%のthroughput改善を報告している。

T4ではdecode比率の高いOSC workloadで差が大きく、**NEO比最大72%、vLLM比最大96%**の改善を§5.2で報告している。

T4で効果が大きいのは、GPUがA10より弱いためCPU/GPU性能差が相対的に小さく、さらにVRAM制約が強いためCPU offloadで増やせるbatch sizeの価値が高いからである。

### Output lengthを変えた評価

A10で平均output lengthを伸ばすと、NEO比改善は

- 50〜200 tokens: 約5%
- 200〜500 tokens: 約17〜31%
- 500 tokens超: 最大約37%

へ増える。decode時間が長いほどAsynchronous OverlapでCPU計算を隠せる割合が増えるためである。

### Latency

T4ではaverage per-token latencyをNEOのおよそ半分まで削減した条件があり、A10でもNEOよりわずかに低い。throughput増加のためにlatencyを犠牲にする方式ではない。

### Ablation

主要3要素は

- Asynchronous Overlap
- 新CPU paged-attention kernel
- analytical modelによるstrategy選択

である。

ablationではAsynchronous Overlapが最も大きな寄与を持ち、条件によりNEO比53〜100%の改善を生む。CPU kernelはさらに約13〜21%、analytical modelは短めのoutputで最大31%程度の追加効果を示す。

## 既存研究との差

### NEOとの違い

NEOはCPU/GPU requestを2 sub-batchへ分割してpipeline化する。APEXはdecode-heavy時にこのbatch splittingがGPU linearを二重実行させる点を問題視し、**linearはunified batchで一度だけ実行し、attention後の同期を遅らせる**。

またNEOのheuristic schedulingに対し、APEXはoffline profileから得たCPU/GPU実行時間を使うperformance modelでstrategyを選択する。

### FastDecodeとの違い

FastDecodeはdecode attentionをCPUへ大きく移す固定的な構成で、十分なCPU資源を前提とする。APEXはGPU-firstで、VRAM不足時だけ必要量をCPUへ回し、CPU performanceに応じて実行方式を変える。

### FlexGenとの違い

FlexGenはoffline batch throughputを高めるためweight / KVの階層配置とscheduleを最適化する。APEXはonline serving、とくにchatやreasoningの長いdecodeを対象に、CPU attentionとGPU処理の時間的overlapを最適化する。

## 限界

- 評価GPUはT4とA10のみで、A100 / H100のような大容量・高性能GPUで同じ利得が出るかは未確認。
- CPU attention性能とCPU/GPU性能比に依存し、CPUが相対的に弱い環境ではoffloadの効果が小さくなる。
- performance modelはoffline profilingに依存するため、hardware状態やworkload変動でprofileと実測がずれる可能性がある。
- Python multi-thread runtime由来のoverheadがあり、CPU request数が少ない場合はparallel executionを起動しにくい。
- arXiv v4時点で公式code repositoryは確認できなかった。
- arXiv v4ではT4のNEO比最大値について、abstract / §5.2が72%とする一方、conclusionに49%という古い値が残っている。ここでは実験節と最新abstractの72%を採用する。

## 一般的な実装上の含意

APEXの重要な点は、heterogeneous executionでは「CPUへ何を移すか」だけでなく、**CPU結果をいつ待つか**が性能を大きく左右することを示した点である。

依存関係が許すならCPU処理の完了直後に同期する必要はなく、GPU側が独立して進められる処理を先に実行してcritical pathからCPU latencyを外す方がよい。

またCPU/GPU offload strategyは固定ruleより、operatorごとのprofileから「このhardware・batch・sequence lengthで本当にoverlapの利得があるか」を判定する方が、異なるGPU/CPU比率へ適応しやすい。
