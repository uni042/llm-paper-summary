# SuperInfer: SLO-Aware Rotary Scheduling and Memory Management for LLM Inference on Superchips

> GH200のHBMが混雑したとき、応答開始やトークン間隔の目標に遅れそうなリクエストを優先してKV キャッシュをCPU DRAMとの間で入れ替え、小さいKV ブロックをまとめて双方向転送することで高速C2C linkを使い切るオンライン 提供 システム。

## 概要

SuperInferは、KV キャッシュ不足時にリクエストを単純に待たせる・スワップするだけでは、高い-読み込み時に先に入った長いリクエストが後続を塞ぐ **ヘッド-of-line blocking** が起き、user-facing 遅延目標を守れない問題を扱う。

ここで見る主な目標は、

- **TTFT（Time To 最初 トークン）:** リクエストを受けてから最初のトークンが返るまで
- **TBT（Time 間 トークン）:** デコード中にトークンとトークンの間がどれだけ空くか

である。論文の **SLO（Service Level 目的）** は、これらを「この時間以内に収めたい」というservice側の目標値として扱う。

対象はGH200のようなCPU-GPU Superchipで、HBMと大容量CPU DRAMをNVLink-C2Cで高速接続できる環境である。SuperInferはCPU DRAMをKV キャッシュの一時退避先として使うだけでなく、**どのリクエストをHBMに残し、どれをDRAMへ一時退避するかを、TTFT/TBTの遅れ具合から能動的に入れ替える**。

さらに、vLLM型のpaged KV キャッシュは小さいブロックに分散しており、そのままコピーするとC2C帯域をほとんど使えない。そこで小さいKV ブロックを大きな転送へまとめ、CPU→GPUとGPU→CPUを同時に流して高い-帯域 linkを使い切る。

## 問題設定

PieはGH200の高速C2Cを使ってKV キャッシュをCPU メモリへ拡張するが、主眼は「GPU計算を止めずに使えるCPU容量を増やす」ことにあり、リクエストごとのTTFT / TBT urgencyは直接扱わない。

SuperInferは、メモリ 容量が足りるかどうかだけでなく、**waiting リクエストがTTFT目標にどれだけ遅れているか、すでにデコード中のリクエストがTBT目標にどれだけ遅れているか**を同じスケジューラで扱う。

また、論文では既存オフロード実装をGH200へそのまま持ってきてもNVLink-C2C帯域の5%未満しか使えない場合があると分析しており、ハードウェア 帯域だけでは十分でないことを示す。

## 手法

### 1. Requestを「待機中・HBM上で実行中・CPUへ一時退避中」で管理する

論文のRotaSchedはリクエストを主に

- **waiting:** まだ実行開始していない
- **running:** HBM上のKVで実行中
- **rotary:** KVをCPU DRAMへ置いて一時停止中

の状態で管理する。

GPU メモリがOOM直前になるまで待つのではなく、遅延目標まで余裕があるrunning リクエストを一時退避し、目標に遅れそうなwaiting / rotary リクエストをHBMへ戻す。

### 2. TTFTとTBTの「目標からの遅れ」を同じ値に変換する

各リクエストについて、SLO上「本来どこまで進んでいるべきか」に対する遅れを **Virtual Lag Time（VLT）** として表す。

つまりVLTは、waiting リクエストの「最初のトークンが遅れそう」という問題と、デコード中リクエストの「次トークンが遅れそう」という問題を**同じ遅延スコアへ変換する**ための値である。

VLTが大きいリクエストほどSLO違反へ近いので優先し、VLTが小さいリクエストは一時退避候補にする。論文のLargest-VLT-最初は、単純に**最も遅れているリクエストから優先する方針**を指す。

係数を変えることで、TTFT重視・TBT重視の均衡も調整できる。

### 3. 小さいKV blockをまとめて大きなtransferにする

PagedAttentionではKV ブロックが小さく散らばるため、ブロックごとにコピー カーネルを起動すると高いC2C 帯域を使えない。

論文のDuplexKVは、**コピー時だけ小さいKV 区間を数MB級の大きな転送へまとめる**。これによりカーネル 起動 オーバーヘッドと小粒度転送の帯域損失を減らす。

論理にはページ/ブロック単位でKVを管理しつつ、物理 転送だけを大きくまとめる点が重要である。

### 4. CPU→GPUとGPU→CPUを同時に流す

論文の **完全な-duplex 転送** は、スワップ-in（CPU→GPU）とスワップ-out（GPU→CPU）を同時に進め、linkの両方向を使うことを指す。

ただし単純に双方向コピーを同時実行すると、スワップ-in先のHBM ブロックが同時にスワップ-out元になるなどデータ raceが起こる。

そこでSuperInferは、すでに書き終えた古いKV ブロックをリクエスト停止前からCPUへ先に複製しておく。論文の **eager ブロック rotation** はこの先行コピーを指す。

リクエストを実際に一時停止するときは、最後に更新された新しいブロックだけをCPUへ送ればよい。古いブロックはCPU側コピーを再利用できるため、CPU→GPUで別リクエストを戻しながらGPU→CPUで最新差分を送れる。

### 5. 次iterationのscheduleとKV移動を現在のGPU計算と重ねる

iteration tでGPUがモデルを実行している間に、ホスト側では次iterationのスケジューリングとKV rotationを進める。転送とスケジューラ オーバーヘッドをGPU 実行の裏へ隠すことで、frequent rotationによる待ちを抑える。

このパイプラインでは、現在iterationが使うKV配置を途中で変更せず、次iterationで有効にする入替えをホスト側で先に準備する。GPU計算終了の境界で必要な転送完了と予定を同期してから次iterationへ進むため、制御処理を重ねても現在計算が不完全なKVを読む必要はない。高速C2CとDuplexKVでrotation時間を短くし、その大部分を現在iterationの計算内へ収めることが、リクエストを頻繁に入れ替えてもスループットを落としにくくする条件になる。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Hardware | NVIDIA GH200 NVL2 |
| 各GPU | 144GB HBM |
| 各CPU | 480GB DRAM |
| CPU-GPU | NVLink-C2C、900GB/s bidirectional |
| モデル | LLaMA-3-8B / Qwen2.5-32B / Mixtral-8x7B |
| Dataset | ShareGPT / LMSYS-Chat-1M |
| 比較対象 | vLLM / TensorRT-LLM / LightLLM / LTR / NEO |
| 実装 | vLLM 0.6.6.post1ベース |

### 主要結果

高い リクエスト 率では、SuperInferは比較対象群に対し**TTFT SLO attainmentを最大74.7%改善**しつつ、TBT SLO attainmentとスループットは概ね同程度を維持した。

ここでSLO attainmentは、設定したTTFT/TBT目標を守れたリクエストの割合を表す。

低読み込みではGPU メモリに余裕があるためrotationがほぼ不要になり、比較対象と同等性能へ戻る。

DuplexKVのmicrobenchmarkではQwen2.5-32BのKVを双方向に合計16GB転送する条件で、naive コピーが約10GB/s級だったのに対し、DuplexKVはD2H約181GB/s・H2D約179GB/sを同時に達成し、理想的なDRAM帯域上限に対してE2E時間約1.1倍まで近づいた。

## 既存研究との差

### Pieとの違い

Pieは層 アクセス順序を使ってKVをプリフェッチし、CPU メモリ 拡張量をオンラインで増減する。一方SuperInferは、**リクエストごとのTTFT/TBTの遅れを見てHBMへ置くリクエスト自体を入れ替える**。

Pieが容量 / スループット中心なのに対し、SuperInferは高い-読み込み時のTTFT / TBT SLO attainmentを主指標とする。

### NEOとの違い

NEOは一部リクエストの注意機構とKVをCPUへ置き、CPU/GPUで並列処理する。SuperInferは注意機構自体はGPUで実行し、CPUは主にKVの退避階層として使う。その代わり高速C2Cを前提にリクエスト rotationを頻繁に行う。

### DirectKVとの違い

DirectKVはCPU上のKVをGPU HBMへ一度コピーせず、GPU カーネルから直接読む。SuperInferはKVをHBM / DRAM間で明示的に入れ替えつつ、**どのリクエストをいつ入れ替えるか**と**双方向転送の使い方**を最適化する。

両者はGH200を対象にするが、DirectKVは注意機構 カーネル / 遠隔-メモリ アクセス寄り、SuperInferは提供 スケジューラ / メモリ management寄りである。

## 限界

- GH200級の高速coherent CPU-GPU 接続網を前提とし、PCIe環境では頻繁なrotationが成立しにくい。
- スケジューラは設定したTTFT / TBT SLOに依存し、最適パラメータはservice要件ごとに変わる。
- eager ブロック rotationではCPU側にsynced KV コピーを保持するため、DRAM容量と転送 trafficを消費する。
- 評価は単一Superchip内のメモリ hierarchyが中心で、rack-scale disaggregated KV キャッシュとは別問題である。
- vLLM forkとして実装されており、2026-09-06時点でupstream vLLM本体へ統合された機能ではない。

## 一般的な実装上の含意

SuperInferは、高速ホスト メモリを利用する場合、オフロード量だけを最適化しても不十分で、**リクエスト スケジューリングとデータ 移動を同時設計する必要がある**ことを示す。

またC2C 帯域が非常に高くても、小さいpaged KV ブロックを1つずつコピーするとソフトウェア オーバーヘッドで帯域を失う。高速接続網向けランタイムでは、論理 ページ管理と物理 転送粒度を分離し、コピー時だけ大きなバッチへまとめる設計が重要になる。
