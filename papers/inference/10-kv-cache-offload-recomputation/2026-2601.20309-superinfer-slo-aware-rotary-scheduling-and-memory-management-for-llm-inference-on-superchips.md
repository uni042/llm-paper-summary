# SuperInfer: SLO-Aware Rotary Scheduling and Memory Management for LLM Inference on Superchips

> GH200のHBMが混雑したとき、応答開始やtoken間隔の目標に遅れそうなrequestを優先してKV cacheをCPU DRAMとの間で入れ替え、小さいKV blockをまとめて双方向転送することで高速C2C linkを使い切るonline serving system。

## 概要

SuperInferは、KV cache不足時にrequestを単純に待たせる・swapするだけでは、high-load時に先に入った長いrequestが後続を塞ぐ **head-of-line blocking** が起き、user-facing latency目標を守れない問題を扱う。

ここで見る主な目標は、

- **TTFT（Time To First Token）:** requestを受けてから最初のtokenが返るまで
- **TBT（Time Between Tokens）:** decode中にtokenとtokenの間がどれだけ空くか

である。論文の **SLO（Service Level Objective）** は、これらを「この時間以内に収めたい」というservice側の目標値として扱う。

対象はGH200のようなCPU-GPU Superchipで、HBMと大容量CPU DRAMをNVLink-C2Cで高速接続できる環境である。SuperInferはCPU DRAMをKV cacheの一時退避先として使うだけでなく、**どのrequestをHBMに残し、どれをDRAMへ一時退避するかを、TTFT/TBTの遅れ具合から能動的に入れ替える**。

さらに、vLLM型のpaged KV cacheは小さいblockに分散しており、そのままcopyするとC2C帯域をほとんど使えない。そこで小さいKV blockを大きなtransferへまとめ、CPU→GPUとGPU→CPUを同時に流してhigh-bandwidth linkを使い切る。

## 問題設定

PieはGH200の高速C2Cを使ってKV cacheをCPU memoryへ拡張するが、主眼は「GPU計算を止めずに使えるCPU容量を増やす」ことにあり、requestごとのTTFT / TBT urgencyは直接扱わない。

SuperInferは、memory capacityが足りるかどうかだけでなく、**waiting requestがTTFT目標にどれだけ遅れているか、すでにdecode中のrequestがTBT目標にどれだけ遅れているか**を同じschedulerで扱う。

また、論文では既存offload実装をGH200へそのまま持ってきてもNVLink-C2C帯域の5%未満しか使えない場合があると分析しており、hardware bandwidthだけでは十分でないことを示す。

## 手法

### 1. Requestを「待機中・HBM上で実行中・CPUへ一時退避中」で管理する

論文のRotaSchedはrequestを主に

- **waiting:** まだ実行開始していない
- **running:** HBM上のKVで実行中
- **rotary:** KVをCPU DRAMへ置いて一時停止中

の状態で管理する。

GPU memoryがOOM直前になるまで待つのではなく、latency目標まで余裕があるrunning requestを一時退避し、目標に遅れそうなwaiting / rotary requestをHBMへ戻す。

### 2. TTFTとTBTの「目標からの遅れ」を同じ値に変換する

各requestについて、SLO上「本来どこまで進んでいるべきか」に対する遅れを **Virtual Lag Time（VLT）** として表す。

つまりVLTは、waiting requestの「最初のtokenが遅れそう」という問題と、decode中requestの「次tokenが遅れそう」という問題を**同じ遅延スコアへ変換する**ための値である。

VLTが大きいrequestほどSLO違反へ近いので優先し、VLTが小さいrequestは一時退避候補にする。論文のLargest-VLT-Firstは、単純に**最も遅れているrequestから優先するpolicy**を指す。

係数を変えることで、TTFT重視・TBT重視のbalanceも調整できる。

### 3. 小さいKV blockをまとめて大きなtransferにする

PagedAttentionではKV blockが小さく散らばるため、blockごとにcopy kernelを起動すると高いC2C bandwidthを使えない。

論文のDuplexKVは、**copy時だけ小さいKV segmentを数MB級の大きなtransferへまとめる**。これによりkernel launch overheadと小粒度transferの帯域損失を減らす。

logicalにはpage/block単位でKVを管理しつつ、physical transferだけを大きくまとめる点が重要である。

### 4. CPU→GPUとGPU→CPUを同時に流す

論文の **full-duplex transfer** は、swap-in（CPU→GPU）とswap-out（GPU→CPU）を同時に進め、linkの両方向を使うことを指す。

ただし単純に双方向copyを同時実行すると、swap-in先のHBM blockが同時にswap-out元になるなどdata raceが起こる。

そこでSuperInferは、すでに書き終えた古いKV blockをrequest停止前からCPUへ先に複製しておく。論文の **eager block rotation** はこの先行copyを指す。

requestを実際に一時停止するときは、最後に更新された新しいblockだけをCPUへ送ればよい。古いblockはCPU側copyを再利用できるため、CPU→GPUで別requestを戻しながらGPU→CPUで最新差分を送れる。

### 5. 次iterationのscheduleとKV移動を現在のGPU計算と重ねる

iteration tでGPUがmodelを実行している間に、host側では次iterationのschedulingとKV rotationを進める。transferとscheduler overheadをGPU executionの裏へ隠すことで、frequent rotationによるstallを抑える。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Hardware | NVIDIA GH200 NVL2 |
| 各GPU | 144GB HBM |
| 各CPU | 480GB DRAM |
| CPU-GPU | NVLink-C2C、900GB/s bidirectional |
| Model | LLaMA-3-8B / Qwen2.5-32B / Mixtral-8x7B |
| Dataset | ShareGPT / LMSYS-Chat-1M |
| Baseline | vLLM / TensorRT-LLM / LightLLM / LTR / NEO |
| 実装 | vLLM 0.6.6.post1ベース |

### 主要結果

high request rateでは、SuperInferはbaseline群に対し**TTFT SLO attainmentを最大74.7%改善**しつつ、TBT SLO attainmentとthroughputは概ね同程度を維持した。

ここでSLO attainmentは、設定したTTFT/TBT目標を守れたrequestの割合を表す。

低loadではGPU memoryに余裕があるためrotationがほぼ不要になり、baselineと同等performanceへ戻る。

DuplexKVのmicrobenchmarkではQwen2.5-32BのKVを双方向に合計16GB転送する条件で、naive copyが約10GB/s級だったのに対し、DuplexKVはD2H約181GB/s・H2D約179GB/sを同時に達成し、理想的なDRAM帯域上限に対してE2E時間約1.1倍まで近づいた。

## 既存研究との差

### Pieとの違い

Pieはlayer access順序を使ってKVをprefetchし、CPU memory extension量をonlineで増減する。一方SuperInferは、**requestごとのTTFT/TBTの遅れを見てHBMへ置くrequest自体を入れ替える**。

Pieがcapacity / throughput中心なのに対し、SuperInferはhigh-load時のTTFT / TBT SLO attainmentを主metricとする。

### NEOとの違い

NEOは一部requestのattentionとKVをCPUへ置き、CPU/GPUで並列処理する。SuperInferはattention自体はGPUで実行し、CPUは主にKVの退避tierとして使う。その代わり高速C2Cを前提にrequest rotationを頻繁に行う。

### DirectKVとの違い

DirectKVはCPU上のKVをGPU HBMへ一度copyせず、GPU kernelから直接読む。SuperInferはKVをHBM / DRAM間で明示的に入れ替えつつ、**どのrequestをいつ入れ替えるか**と**双方向transferの使い方**を最適化する。

両者はGH200を対象にするが、DirectKVはattention kernel / remote-memory access寄り、SuperInferはserving scheduler / memory management寄りである。

## 限界

- GH200級の高速coherent CPU-GPU interconnectを前提とし、PCIe環境では頻繁なrotationが成立しにくい。
- schedulerは設定したTTFT / TBT SLOに依存し、最適parameterはservice要件ごとに変わる。
- eager block rotationではCPU側にsynced KV copyを保持するため、DRAM容量とtransfer trafficを消費する。
- 評価は単一Superchip内のmemory hierarchyが中心で、rack-scale disaggregated KV cacheとは別問題である。
- vLLM forkとして実装されており、2026-09-06時点でupstream vLLM本体へ統合された機能ではない。

## 一般的な実装上の含意

SuperInferは、高速host memoryを利用する場合、offload量だけを最適化しても不十分で、**request schedulingとdata movementを同時設計する必要がある**ことを示す。

またC2C bandwidthが非常に高くても、小さいpaged KV blockを1つずつcopyするとsoftware overheadで帯域を失う。高速interconnect向けruntimeでは、logical page管理とphysical transfer粒度を分離し、copy時だけ大きなbatchへまとめる設計が重要になる。
