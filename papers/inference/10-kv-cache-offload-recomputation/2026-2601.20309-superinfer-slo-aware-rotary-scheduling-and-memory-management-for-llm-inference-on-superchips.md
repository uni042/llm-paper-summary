# SuperInfer: SLO-Aware Rotary Scheduling and Memory Management for LLM Inference on Superchips

> GH200のHBMとCPU DRAMの間でrequestのKV cacheをSLO進捗に応じて能動的に入れ替え、細切れKVをまとめたfull-duplex転送でNVLink-C2Cを使い切るonline serving system。

## 概要

SuperInferは、KV cache不足時にrequestを単純に待たせる・swapするだけでは、high-load時に新規requestが長く待つ **head-of-line blocking** が起き、TTFT / TBTのSLOを守れない問題を扱う。

対象はGH200のようなCPU-GPU Superchipで、HBMと大容量CPU DRAMをNVLink-C2Cで高速接続できる環境である。SuperInferはCPU DRAMをKV cacheの一時退避先として使うだけでなく、**どのrequestをHBMに残し、どれをDRAMへ一時退避するかをSLO進捗から能動的に回転させる**。

さらに、vLLM型のpaged KV cacheは小さいblockに分散しており、そのままcopyするとC2C帯域をほとんど使えない。そこでDuplexKVがKV layoutとcopy方法を変え、swap-in / swap-outを同時に流してhigh-bandwidth linkを使い切る。

## 問題設定

PieはGH200の高速C2Cを使ってKV cacheをCPU memoryへ拡張するが、主眼は「GPU計算を止めずに使えるCPU容量を増やす」ことにあり、requestごとのTTFT / TBT urgencyは直接扱わない。

SuperInferは、memory capacityが足りるかどうかだけでなく、**waiting requestがTTFT SLOにどれだけ遅れているか、すでにdecode中のrequestがTBT SLOにどれだけ遅れているか**を同じschedulerで扱う。

また、論文では既存offload実装をGH200へそのまま持ってきてもNVLink-C2C帯域の5%未満しか使えない場合があると分析しており、hardware bandwidthだけでは十分でないことを示す。

## 手法

### 1. RotaSchedでrequestを能動的にrotationする

requestを主に

- waiting: まだ実行開始していない
- running: HBM上のKVで実行中
- rotary: KVをCPU DRAMへ置いて一時停止中

の状態で管理する。

GPU memoryがOOM直前になるまで待つのではなく、SLO上の優先度が低いrunning requestをrotaryへ移し、遅れているwaiting / rotary requestをHBMへ戻す。

### 2. Virtual Lag TimeでTTFTとTBTの遅れを共通尺度にする

各requestについて、SLO上「本来どこまで進んでいるべきか」に対する遅れを **Virtual Lag Time（VLT）** として表す。

VLTが大きいrequestほどSLO違反へ近いので優先し、VLTが小さいrequestは一時退避候補にする。Largest-VLT-First policyで、TTFT待ちとdecode中TBTの両方を一つのpriority queueに載せる。

係数を変えることで、TTFT重視・TBT重視のbalanceも調整できる。

### 3. DuplexKVで細切れKV transferを大きくまとめる

PagedAttentionではKV blockが小さく散らばるため、blockごとにcopy kernelを起動すると高いC2C bandwidthを使えない。

DuplexKVはblock-firstなlayoutとbatched transfer kernelを使い、小さいsegmentを数MB級の大きなtransferへまとめる。これによりkernel launch overheadと小粒度transferの帯域損失を減らす。

### 4. swap-in / swap-outをfull-duplexで同時実行する

単純に双方向copyを同時実行すると、swap-in先のHBM blockが同時にswap-out元になるなどdata raceが起こる。

SuperInferは、すでに書き終えたKV blockをrequest preemption前からCPUへ先に複製する **eager block rotation** を使う。preemption時には最新のdirty blockだけを送ればよく、古いsynced blockはCPU側copyを使えるため、H2DとD2Hを同時に流せる。

### 5. scheduler・transfer・model executionをiteration間でpipeline化する

iteration tでGPUがmodelを実行している間に、host側では次iterationのschedulingとKV rotationを進める。transferとscheduler overheadをGPU executionの裏へ隠すことで、frequent rotationによるstallを抑える。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Hardware | NVIDIA GH200 NVL2 |
| 各GPU | 144GB HBM |
| 各CPU | 480GB DRAM |
| CPU-GPU | NVLink-C2C、900GB/s bidirectional |
| Model | LLaMA-3-8B / Qwen2.5-32B / Mixtral-8x7B |
| Dataset | ShareGPT / LMSYS-Chat-1M |
| Baseline | vLLM / TensorRT-LLM / LightLLM / LTR / NEO |
| 実装 | vLLM 0.6.6.post1ベース |

### 主要結果

high request rateでは、SuperInferはbaseline群に対し**TTFT SLO attainmentを最大74.7%改善**しつつ、TBT SLO attainmentとthroughputは概ね同程度を維持した。

低loadではGPU memoryに余裕があるためrotationがほぼ不要になり、baselineと同等performanceへ戻る。

DuplexKVのmicrobenchmarkではQwen2.5-32BのKVを双方向に合計16GB転送する条件で、naive copyが約10GB/s級だったのに対し、DuplexKVはD2H約181GB/s・H2D約179GB/sを同時に達成し、理想的なDRAM帯域上限に対してE2E時間約1.1倍まで近づいた。

## 既存研究との差

### Pieとの違い

Pieはlayer access順序を使ってKVをprefetchし、CPU memory extension量をonlineで増減する。一方SuperInferは、**request単位のSLO urgencyを見てHBM residencyそのものを入れ替える**。

Pieがcapacity / throughput中心なのに対し、SuperInferはhigh-load時のTTFT / TBT SLO attainmentを主metricとする。

### NEOとの違い

NEOは一部requestのattentionとKVをCPUへ置き、CPU/GPUで並列処理する。SuperInferはattention自体はGPUで実行し、CPUは主にKVの退避tierとして使う。その代わり高速C2Cを前提にrequest rotationを頻繁に行う。

### DirectKVとの違い

DirectKVはCPU-resident KVをGPU kernelからzero-copyで直接読むことでstagingをなくす。SuperInferはKVをHBM / DRAM間で明示的にrotationしつつ、**どのrequestをいつ入れ替えるか**と**transfer engineの双方向帯域**を最適化する。

両者はGH200を対象にするが、DirectKVはattention kernel / remote-memory access寄り、SuperInferはserving scheduler / memory management寄りである。

## 限界

- GH200級の高速coherent CPU-GPU interconnectを前提とし、PCIe環境では頻繁なrotationが成立しにくい。
- schedulerは設定したTTFT / TBT SLOに依存し、最適parameterはservice要件ごとに変わる。
- eager block rotationではCPU側にsynced KV copyを保持するため、DRAM容量とtransfer trafficを消費する。
- 評価は単一Superchip内のmemory hierarchyが中心で、rack-scale disaggregated KV cacheとは別問題である。
- vLLM forkとして実装されており、2026-09-06時点でupstream vLLM本体へ統合された機能ではない。

## 一般的な実装上の含意

SuperInferは、高速host memoryを利用する場合、offload量だけを最適化しても不十分で、**request schedulingとdata movementを同時設計する必要がある**ことを示す。

またC2C bandwidthが非常に高くても、小さいpaged KV blockを1つずつcopyするとsoftware overheadで帯域を失う。高速interconnect向けruntimeでは、logical page管理とphysical transfer粒度を分離し、copy時だけ大きなbatchへまとめる設計が重要になる。
