# Accelerating LLM Inference via Dynamic KV Cache Placement in Heterogeneous Memory System

> 頻繁に参照されるKVを高速HBM、そうでないKVを大容量DRAMへ置く配置問題をモデル化し、未来のattention参照先を完全に知る理想条件との比較から、実用schedulerにどれだけ改善余地が残るかを測るsimulation研究。

## 概要

この研究は、GH200のように高速HBMと大容量LPDDRを高速interconnectで組み合わせられるhardwareで、**どのKVを高速で小さいmemoryへ置き、どのKVを遅い代わりに大容量のmemoryへ置くべきか**を扱う。

attention sparsityによって各decode stepで読むKV量を減らせても、「今は重要でないtokenが後で重要になる」ため全KVを捨てることはできない。そこで低頻度KVを大容量DRAMに保持し、将来よく参照されるKVをHBMへ移す階層配置が考えられる。

ただし本論文は実用的な予測schedulerを提案するものではない。未来のattention access patternを事前に知っているという**現実には使えない理想条件**を置き、そこで最適化した配置と単純な配置を比較することで、**「もし将来参照をうまく予測できればどこまで速くできるか」という上限**を測る。

## 問題設定

HBMは高速だが容量が小さく、off-package DRAMは大容量だが帯域が低い。decodeはmemory bandwidth-boundなので、頻繁に読むKVがslow tierへあるとthroughputが下がる。

一方、token importanceはdecode中に変化する。あるstepでattention scoreが低かったKVも、後のstepでは再び高くなる場合があるため、単純に「cold KVをslow tierへ固定」するだけではoptimalにならない。

このため、

- HBM / DRAMのread bandwidth
- interconnect migration bandwidth
- HBM capacity
- 各KVの将来access頻度
- migration自体のtraffic

を同時に考えた配置問題として定式化する。

model weightは常時HBMに置き、**KV cacheだけを配置対象**とする。

## 手法

### 1. HBMと外部DRAMを同時に読むときのstep時間をモデル化する

各decode stepで、HBM側と外部DRAM側から同時にdataを読むと仮定し、step latencyを両memory pathの遅い方で決める。

KVをHBMへ移す / DRAMへ追い出すtrafficも各memory bandwidthとinterconnect bandwidthを消費するため、単純にhot KVを頻繁に入れ替えればよいわけではない。

### 2. 各stepで「何を上げ、何を下げるか」を最適化対象にする

各stepで、

- HBM → DRAMへ移すKV
- DRAM → HBMへ移すKV
- 新しいKVをどちらへ書くか

を選択対象とし、HBM容量制約の下でtotal decode latencyを最小化する。

ここで単純なhot/cold分類だけでは足りない。HBMとDRAMを同時に読めるなら、全hot KVをHBMへ集めるより、両tierの読出し時間が近づくようworking setを分割した方がaggregate bandwidthを使い切れる場合がある。またDRAM→HBM昇格は将来のreadを速くする一方、その瞬間にはinterconnectと両memoryの帯域を消費する。したがって『次stepで何回読まれるか』だけでなく、移動に払うbyteと、その移動が何stepで回収できるかまで含めて配置を決める必要がある。

### 3. 未来のattention参照を完全に知る条件で上限を探す

実runtimeでは未来のattention patternは分からないが、本論文では上限値を求めるため既知と仮定する。

探索では、

- `W`: 何token先まで未来のaccess patternを見るか
- `R`: 「移した方がよい」と判断したKVのうち実際に何割を移すか

を変えながら、頻繁に使われるKVをHBMへ寄せる利得とmigration overheadを釣り合わせる。

論文で使う **Simulated Annealing** は、組合せが非常に多い配置候補から良い設定を探索する最適化手法である。ここで重要なのはアルゴリズム名ではなく、**未来を完全に知る理想schedulerに近い比較点を作るために使っている**ことである。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| 評価方式 | behavioral simulation |
| Model | LLaMA-3.1-8B |
| Workload | LongBench / NarrativeQA、約30K prompt + 10K decode |
| HBM bandwidth | 4.9 TB/s |
| HBM capacity | 24GB（model約16GB、KV用約8GB） |
| Off-package DRAM | 480GB |
| DRAM bandwidth | 500GB/s |
| Interconnect | 900GB/s |
| Architecture reference | NVIDIA GH200相当 |

実際のattention traceをLLaMA-3.1-8Bから取得し、そのaccess patternをmemory simulatorへ入力する。

### 比較policy

- **Static:** HBMが埋まるまで書き、その後はDRAMへ置いて移動しない。
- **Reactive / LRU:** 必要なKVがHBMになければ戻し、最近使っていないKVをDRAMへ追い出す。
- **Page-granularity:** 16-token page単位で移動する理想化policy。
- **SA-guided:** 未来accessを既知とした上限評価。
- **Unlimited HBM:** 容量制約なしの理想hardware。

### 主要結果

未来accessを使うSA-guided配置は、static placementに対して**最大5.87倍**のthroughput差を示した。

これは「実装済みschedulerが5.87倍速い」という意味ではなく、**単純配置と、未来を完全に知る理想配置の間にそれだけのgapがある**という結果である。

sensitivity評価では、SA-guidedは多くの条件でstatic比約4〜5倍を維持する一方、reactive / page-level policyはattention sparsityが低くworking setが大きいとmigration overheadが増えて利得が小さかった。

またtoken importanceの時間変化が小さい場合は、hot KVを一度HBMへ置けば長く使えるためdynamic placementの効果が高い。重要tokenが頻繁に入れ替わる場合はmigration costが増え、理想policyでも利得が縮む。

## 既存研究との差

### Pie / SuperInferとの違い

PieやSuperInferは実機GH200上でrequest / layer単位のKV movementを実装する。本論文は**token-level placementのperformance limitをsimulationで調べる**もので、実用runtimeは提供しない。

### KV Cache Optimizationとの違い

H2OやQUEST系は不要KVのaccessを減らす / skipすることが中心。本研究ではKV自体は保持したまま、**access frequencyに応じてfast / slow memoryのどちらへ置くか**を変える。

### DirectKVとの違い

DirectKVはCPU側KVをGPUから直接読むkernelを最適化する。本研究は「どう読むか」ではなく、**どのKVをHBM / external DRAMへ置けば両memoryの帯域を最も有効に使えるか**という配置問題に焦点を置く。

## 限界

- **実機評価ではなくsimulation**であり、報告する5.87倍は実装済みspeedupではない。
- 上限policyは未来のattention accessを完全に知っているためreal-time schedulerでは実現できない。
- memory-bandwidth-boundを中心にしたmodelで、kernel launch、compute、software overheadなどは簡略化される。
- HBM capacityを24GBへ制限したGH200相当モデルであり、実際のGH200 96GB HBM構成そのものを再現した評価ではない。
- LLaMA-3.1-8B / NarrativeQA中心で、GQA・MoE・多様なworkloadへの一般化は未検証。
- 実用的なfuture-access predictorやonline placement algorithmは今後の課題。

## 一般的な実装上の含意

この研究の価値は特定algorithmではなく、**単純なHBM-first placementと理想的なdynamic placementの間に大きなperformance gapがある**ことを定量化した点にある。

特に今後host / peer memory帯域がHBMへ近づくほど、「slow tierは容量だけを増やす場所」ではなく、両tierのbandwidthを並列に使う設計が重要になる。

実用runtimeでは、将来attentionを完全予測する代わりに、recent attention、token reuse、prefetch predictorなどから次のhot KVを予測し、migration costを上回る場合だけHBMへ昇格させる方向が考えられる。
