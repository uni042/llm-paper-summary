# Accelerating LLM Inference via Dynamic KV Cache Placement in Heterogeneous Memory System

> 頻繁に参照されるKVを高速HBM、そうでないKVを大容量DRAMへ置く配置問題をモデル化し、未来の注意機構参照先を完全に知る理想条件との比較から、実用スケジューラにどれだけ改善余地が残るかを測るシミュレーション研究。

## 概要

この研究は、GH200のように高速HBMと大容量LPDDRを高速接続網で組み合わせられるハードウェアで、**どのKVを高速で小さいメモリへ置き、どのKVを遅い代わりに大容量のメモリへ置くべきか**を扱う。

注意機構 sparsityによって各デコード 段階で読むKV量を減らせても、「今は重要でないトークンが後で重要になる」ため全KVを捨てることはできない。そこで低頻度KVを大容量DRAMに保持し、将来よく参照されるKVをHBMへ移す階層配置が考えられる。

ただし本論文は実用的な予測スケジューラを提案するものではない。未来の注意機構 アクセス パターンを事前に知っているという**現実には使えない理想条件**を置き、そこで最適化した配置と単純な配置を比較することで、**「もし将来参照をうまく予測できればどこまで速くできるか」という上限**を測る。

## 問題設定

HBMは高速だが容量が小さく、off-package DRAMは大容量だが帯域が低い。デコードはメモリ 帯域-上限なので、頻繁に読むKVが遅い 階層へあるとスループットが下がる。

一方、トークン importanceはデコード中に変化する。ある段階で注意機構 点数が低かったKVも、後の段階では再び高くなる場合があるため、単純に「低頻度 KVを遅い 階層へ固定」するだけでは最適にならない。

このため、

- HBM / DRAMのread 帯域
- 接続網 移動 帯域
- HBM 容量
- 各KVの将来アクセス頻度
- 移動自体のtraffic

を同時に考えた配置問題として定式化する。

モデル 重みは常時HBMに置き、**KV キャッシュだけを配置対象**とする。

## 手法

### 1. HBMと外部DRAMを同時に読むときのstep時間をモデル化する

各デコード 段階で、HBM側と外部DRAM側から同時にデータを読むと仮定し、段階 遅延を両メモリ 経路の遅い方で決める。

KVをHBMへ移す / DRAMへ追い出すtrafficも各メモリ 帯域と接続網 帯域を消費するため、単純に高頻度 KVを頻繁に入れ替えればよいわけではない。

### 2. 各stepで「何を上げ、何を下げるか」を最適化対象にする

各段階で、

- HBM → DRAMへ移すKV
- DRAM → HBMへ移すKV
- 新しいKVをどちらへ書くか

を選択対象とし、HBM容量制約の下で総 デコード 遅延を最小化する。

ここで単純な高頻度/低頻度分類だけでは足りない。HBMとDRAMを同時に読めるなら、全高頻度 KVをHBMへ集めるより、両階層の読出し時間が近づくよう作業 集合を分割した方がaggregate 帯域を使い切れる場合がある。またDRAM→HBM昇格は将来のreadを速くする一方、その瞬間には接続網と両メモリの帯域を消費する。したがって『次段階で何回読まれるか』だけでなく、移動に払うバイトと、その移動が何段階で回収できるかまで含めて配置を決める必要がある。

### 3. 未来のattention参照を完全に知る条件で上限を探す

実ランタイムでは未来の注意機構 パターンは分からないが、本論文では上限値を求めるため既知と仮定する。

探索では、

- `W`: 何トークン先まで未来のアクセス パターンを見るか
- `R`: 「移した方がよい」と判断したKVのうち実際に何割を移すか

を変えながら、頻繁に使われるKVをHBMへ寄せる利得と移動 オーバーヘッドを釣り合わせる。

論文で使う **シミュレーションした Annealing** は、組合せが非常に多い配置候補から良い設定を探索する最適化手法である。ここで重要なのはアルゴリズム名ではなく、**未来を完全に知る理想スケジューラに近い比較点を作るために使っている**ことである。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| 評価方式 | behavioral シミュレーション |
| モデル | LLaMA-3.1-8B |
| ワークロード | LongBench / NarrativeQA、約30K 入力 + 10K デコード |
| HBM 帯域 | 4.9 TB/s |
| HBM 容量 | 24GB（モデル約16GB、KV用約8GB） |
| Off-package DRAM | 480GB |
| DRAM 帯域 | 500GB/s |
| Interconnect | 900GB/s |
| アーキテクチャ 参照 | NVIDIA GH200相当 |

実際の注意機構 トレースをLLaMA-3.1-8Bから取得し、そのアクセス パターンをメモリ simulatorへ入力する。

### 比較policy

- **静的:** HBMが埋まるまで書き、その後はDRAMへ置いて移動しない。
- **Reactive / LRU:** 必要なKVがHBMになければ戻し、最近使っていないKVをDRAMへ追い出す。
- **Page-粒度:** 16-トークン ページ単位で移動する理想化方針。
- **SA-guided:** 未来アクセスを既知とした上限評価。
- **Unlimited HBM:** 容量制約なしの理想ハードウェア。

### 主要結果

未来アクセスを使うSA-guided配置は、静的 配置に対して**最大5.87倍**のスループット差を示した。

これは「実装済みスケジューラが5.87倍速い」という意味ではなく、**単純配置と、未来を完全に知る理想配置の間にそれだけのgapがある**という結果である。

sensitivity評価では、SA-guidedは多くの条件で静的比約4〜5倍を維持する一方、reactive / ページ-水準 方針は注意機構 sparsityが低く作業 集合が大きいと移動 オーバーヘッドが増えて利得が小さかった。

またトークン importanceの時間変化が小さい場合は、高頻度 KVを一度HBMへ置けば長く使えるため動的 配置の効果が高い。重要トークンが頻繁に入れ替わる場合は移動 費用が増え、理想方針でも利得が縮む。

## 既存研究との差

### Pie / SuperInferとの違い

PieやSuperInferは実機GH200上でリクエスト / 層単位のKV 移動を実装する。本論文は**トークン単位 配置の性能 上限をシミュレーションで調べる**もので、実用ランタイムは提供しない。

### KV Cache Optimizationとの違い

H2OやQUEST系は不要KVのアクセスを減らす / スキップすることが中心。本研究ではKV自体は保持したまま、**アクセス 頻度に応じて速い / 遅い メモリのどちらへ置くか**を変える。

### DirectKVとの違い

DirectKVはCPU側KVをGPUから直接読むカーネルを最適化する。本研究は「どう読むか」ではなく、**どのKVをHBM / 外部 DRAMへ置けば両メモリの帯域を最も有効に使えるか**という配置問題に焦点を置く。

## 限界

- **実機評価ではなくシミュレーション**であり、報告する5.87倍は実装済み高速化倍率ではない。
- 上限方針は未来の注意機構 アクセスを完全に知っているため実時間 スケジューラでは実現できない。
- メモリ-帯域-上限を中心にしたモデルで、カーネル 起動、計算、ソフトウェア オーバーヘッドなどは簡略化される。
- HBM 容量を24GBへ制限したGH200相当モデルであり、実際のGH200 96GB HBM構成そのものを再現した評価ではない。
- LLaMA-3.1-8B / NarrativeQA中心で、GQA・MoE・多様なワークロードへの一般化は未検証。
- 実用的な将来-アクセス predictorやオンライン 配置 アルゴリズムは今後の課題。

## 一般的な実装上の含意

この研究の価値は特定アルゴリズムではなく、**単純なHBM-最初 配置と理想的な動的 配置の間に大きな性能 gapがある**ことを定量化した点にある。

特に今後ホスト / peer メモリ帯域がHBMへ近づくほど、「遅い 階層は容量だけを増やす場所」ではなく、両階層の帯域を並列に使う設計が重要になる。

実用ランタイムでは、将来注意機構を完全予測する代わりに、最近 注意機構、トークン 再利用、プリフェッチ predictorなどから次の高頻度 KVを予測し、移動 費用を上回る場合だけHBMへ昇格させる方向が考えられる。
