# Tutti: Making SSD-Backed KV Cache Practical for Long-Context LLM Serving

> TuttiはGPU主導の非同期SSD読込みでKV要求をまとめ、CPU発行の小I/Oを排してGPUへ直接転送し、SSD容量を使いながらKV復元待ちを減らす方式。

## 概要

SSD-backed LMCacheをHBM-only、CPU DRAM、通常SSD/GDS経路と比較し、厳しいSLO条件でGDS版比TTFT78.3%削減、処理率2倍、提供コスト27%削減を報告した。GPU停止をほぼゼロにしSSD帯域を飽和させた結果で、SSD媒体自体がDRAM並みに速くなった意味ではない。

## 一文要約

NVMe SSD上へ退避したKVキャッシュを戻す際、CPUが大量の小さなI/O要求を発行する従来方式をやめ、GPU自身がSSDへの非同期I/Oを制御してKVをまとめて転送することで、SSD容量を使いながらDRAM基盤の キャッシュに近い推論性能を狙うシステム。

## 問題設定

長文脈や共有プレフィックスを多用するLLM 提供処理では、再利用可能なKVキャッシュがGPU HBMだけでなくCPU DRAM容量も超え得る。そのためNVMe SSDを下位メモリ 階層として使いたいが、ページ化 KVキャッシュはGPU メモリ上で断片化しており、SSDから復元すると多数の小さな無作為 I/Oになりやすい。

GPU Direct Storage (GDS)を使ってCPU DRAMへの中継コピーを避けても、各I/Oの開始・管理をCPUが担当する構成では、CPU側の低いI/O発行並列性がSSD 帯域を使い切れず、KV待ちでGPUが停止する。この論文は、**SSDの容量ではなく、CPU中心のI/O 制御 経路がSSD基盤の KVキャッシュの実用性能を制限している**と捉える。

## 手法

### 1. GPU-native KV cache object store

KVキャッシュ ブロックを通常のファイル I/OとしてCPUから細かく操作する代わりに、GPUからまとめて扱える対象として表現する。GPU メモリが物理的に断片化していても、KVを構成する領域を対象として一括管理し、細粒度I/O要求を大量にCPUへ発行する必要を減らす。

CPUは各層で必要なI/O カーネルを非同期にGPUへ起動する役割に留まり、その後のデータ 経路とI/O 制御 経路から外れる。これにより、KV ブロック数に比例してCPUがI/Oを逐次管理する構造を避ける。

### 2. GPU io_uringによる非同期direct object I/O

Linuxの非同期I/O インターフェースであるio_uringに相当する待ち行列操作をGPU側から扱えるよう保存領域 積み重ねを再構成する。GPUがSSDへの読み出し / 書き込み要求を高い並列性で発行し、NVMe SSDとGPU HBMの間を直接に転送する。

目的は単なるCPU DRAM コピー削減ではなく、**I/O リクエストを発行する主体そのものをCPUからGPUへ移すこと**にある。これにより多数のKV 断片を復元するときもSSD 待ち行列を十分に埋め、デバイス 帯域を使いやすくする。

### 3. slack-aware I/O scheduling

GPUがI/O 制御も担当すると、保存領域処理用カーネルがLLM推論カーネルとGPU 資源を奪い合う可能性がある。Tuttiは各層の計算時間などからI/Oを進められる余裕時間を見て保存領域処理を配置し、KV取得を計算と重複実行させつつ推論カーネルへの干渉を抑える。

つまり「I/Oを早く開始する」だけでなく、**どの時間帯ならI/O 制御用GPU処理を走らせてもモデル計算を遅らせにくいか**を利用してGPU 停止を隠す。

## memory / I/O構成

- **ローカルGPU HBM**: 実行中のモデルと現在必要なKVキャッシュを保持。
- **CPU DRAM**: Tuttiの主なKV退避先ではない。CPUをSSD↔GPU データ 経路から外すことが設計上の中心。
- **NVMe SSD**: 大容量KVキャッシュの永続的 / 下位階層 保存。
- **転送経路**: NVMe SSD ↔ GPU HBMの直接 I/Oを利用。
- **制御主体**: CPU中心ではなくGPU中心。CPUは層単位のI/O カーネル 起動等を非同期に行う。
- **実機 / シミュレーション**: 実装をvLLMへ統合した実機評価。

## 評価条件

論文は長文脈 提供処理 ワークロードで、HBM-のみ vLLM、CPU DRAMを下位階層に使うLMCache、通常のSSD基盤の LMCache、GDS-有効化済み SSD基盤の LMCache等と比較する。主な評価指標はTTFT、リクエスト 速度、GPU 停止、保存領域 スループット、提供処理 コストで、SSD基盤の キャッシュがDRAM基盤の キャッシュにどこまで近づけるかを見る。

## 主要結果

arXiv 要旨で報告されている主要値は以下。

- GDS-有効化済み SSD基盤の LMCacheと比べ、厳しいSLO条件で **TTFTを78.3%削減**。
- 達成可能な **リクエスト 速度を2倍**に改善。
- **提供処理 コストを27%削減**。
- SSD 帯域を飽和させ、GPU 停止をほぼゼロまで減らし、DRAM基盤の LMCacheに近い推論性能を実現したと報告。

これらはSSDをDRAMと同じ速度にする結果ではなく、従来SSD構成で支配的だったCPU側I/O発行とGPU待ちを取り除くことで、保存領域 帯域を実際の提供処理性能へ結び付けた結果と解釈できる。

## 既存研究との差

### LMCache / GDS-backed KV offloadとの差

LMCache等の階層KVキャッシュはGPU外へKVを保存して再利用できるが、SSD 階層ではGDSを使ってデータ コピーを直接化してもI/O開始・管理にCPUが残る。Tuttiは**データ 経路だけでなくI/O 制御 経路もGPU側へ寄せる**点が中心的な差。

### InstAttentionとの差

InstAttentionはKVと注意機構計算自体を計算機能付き保存領域へ移し、KVをGPUへ戻さない方向を取る。Tuttiは通常のNVMe SSDを大容量キャッシュ 階層として使い、必要なKVをGPU HBMへ高速に戻して既存GPU推論を継続する。したがって、前者は「計算をデータへ移す」、後者は「データをGPUへ戻すI/O 積み重ねをGPU中心に作り直す」という違いがある。

### CPU DRAM offloadとの差

CPU DRAM オフロードはPCIe / NVLink-C2C等を介したメモリ 転送が中心で、容量はホストDRAMに制限される。Tuttiはより低速だが大容量・低コストなNVMe SSDを対象にし、保存領域 キューの並列性とI/O 制御オーバーヘッドを主問題として扱う。

## 限界

- SSD基盤の KVキャッシュなので、キャッシュ ミスやI/O量が計算と重複実行できない条件では保存領域 遅延 / 帯域の影響を受ける。
- GPU側へI/O 制御を移すため、保存領域処理とモデル カーネルのGPU 資源競合を管理する必要がある。
- GPU 直接 I/Oを利用できるハードウェア / ソフトウェア 積み重ねが前提となり、一般的なCPU-仲介型 保存領域 経路へそのまま適用できる設計ではない。
- arXiv preprint段階であり、最終査読版の公開 状態は未確認。

## 一般的な実装含意

SSD オフロードでは「SSDの公称帯域」だけを見ても実効性能は決まらない。LLMのKVキャッシュのように論理的には大きいが物理的には多数のページへ分かれたデータでは、**誰がI/O リクエストを作り、何件同時に待ち行列へ投入できるか**がGPU待ち時間を左右する。

そのため今後の階層KVキャッシュでは、HBM / DRAM / SSDという配置 方策だけでなく、保存領域 リクエスト発行、メモリ 対応付け、GPU カーネル スケジューリングまでを提供処理 実行系と共同設計する価値が高い。特にエージェント型 ワークロードや長い会話でプレフィックス再利用量が増えるほど、SSD 階層を「容量だけ大きい遅いキャッシュ」から「計算と重複実行可能な実用階層」へ変えるI/O 制御設計が重要になる。

## 引用関係・関連研究

- **PagedAttention / vLLM**: KVキャッシュをページ単位で管理する提供処理基盤。TuttiはvLLMへ統合して評価する。
- **LMCache**: GPU外のDRAM / SSDへKVを保存・共有する階層キャッシュ基盤。Tuttiの主要比較対象。
- **CacheGen**: KVキャッシュを圧縮・ストリーミングしてネットワーク / 保存領域 転送 コストを下げる系統。Tuttiは表現圧縮よりI/O 制御 経路を主に改善する。
- **GeminiFS**: GPUが保存領域 データ 経路を直接扱うファイル-システム設計で、TuttiのGPU-centric 保存領域設計と技術的に近い基盤。
- **InstAttention / InstInfer**: 保存領域側で注意機構を実行し、KV 転送自体を避ける別方向の保存領域活用研究。
