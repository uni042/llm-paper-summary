# Tutti: Making SSD-Backed KV Cache Practical for Long-Context LLM Serving

## 書誌情報

- **公開日**: 2026-05-05

## 一文要約

NVMe SSD上へ退避したKV cacheを戻す際、CPUが大量の小さなI/O要求を発行する従来方式をやめ、GPU自身がSSDへの非同期I/Oを制御してKVをまとめて転送することで、SSD容量を使いながらDRAM-backed cacheに近い推論性能を狙うsystem。

## 問題設定

長contextや共有prefixを多用するLLM servingでは、再利用可能なKV cacheがGPU HBMだけでなくCPU DRAM容量も超え得る。そのためNVMe SSDを下位memory tierとして使いたいが、paged KV cacheはGPU memory上で断片化しており、SSDから復元すると多数の小さなrandom I/Oになりやすい。

GPU Direct Storage (GDS)を使ってCPU DRAMへのbounce copyを避けても、各I/Oの開始・管理をCPUが担当する構成では、CPU側の低いI/O発行parallelismがSSD bandwidthを使い切れず、KV待ちでGPUが停止する。この論文は、**SSDの容量ではなく、CPU中心のI/O control pathがSSD-backed KV cacheの実用性能を制限している**と捉える。

## 手法

### 1. GPU-native KV cache object store

KV cache blockを通常のfile I/OとしてCPUから細かく操作する代わりに、GPUからまとめて扱えるobjectとして表現する。GPU memoryが物理的に断片化していても、KVを構成する領域をobjectとして一括管理し、細粒度I/O要求を大量にCPUへ発行する必要を減らす。

CPUは各layerで必要なI/O kernelを非同期にGPUへlaunchする役割に留まり、その後のdata pathとI/O control pathから外れる。これにより、KV block数に比例してCPUがI/Oを逐次管理する構造を避ける。

### 2. GPU io_uringによる非同期direct object I/O

Linuxの非同期I/O interfaceであるio_uringに相当するqueue操作をGPU側から扱えるようstorage stackを再構成する。GPUがSSDへのread / write要求を高いparallelismで発行し、NVMe SSDとGPU HBMの間をdirectに転送する。

目的は単なるCPU DRAM copy削減ではなく、**I/O requestを発行する主体そのものをCPUからGPUへ移すこと**にある。これにより多数のKV fragmentを復元するときもSSD queueを十分に埋め、device bandwidthを使いやすくする。

### 3. slack-aware I/O scheduling

GPUがI/O controlも担当すると、storage処理用kernelがLLM推論kernelとGPU resourceを奪い合う可能性がある。Tuttiは各layerの計算時間などからI/Oを進められる余裕時間を見てstorage処理を配置し、KV取得を計算とoverlapさせつつ推論kernelへの干渉を抑える。

つまり「I/Oを早く開始する」だけでなく、**どの時間帯ならI/O control用GPU処理を走らせてもmodel計算を遅らせにくいか**を利用してGPU stallを隠す。

## memory / I/O構成

- **local GPU HBM**: 実行中のmodelと現在必要なKV cacheを保持。
- **CPU DRAM**: Tuttiの主なKV退避先ではない。CPUをSSD↔GPU data pathから外すことが設計上の中心。
- **NVMe SSD**: 大容量KV cacheのpersistent / lower-tier store。
- **転送経路**: NVMe SSD ↔ GPU HBMのdirect I/Oを利用。
- **制御主体**: CPU中心ではなくGPU中心。CPUはlayer単位のI/O kernel launch等を非同期に行う。
- **実機 / simulation**: 実装をvLLMへ統合した実機評価。

## 評価条件

論文は長context serving workloadで、HBM-only vLLM、CPU DRAMを下位tierに使うLMCache、通常のSSD-backed LMCache、GDS-enabled SSD-backed LMCache等と比較する。主な評価指標はTTFT、request rate、GPU stall、storage throughput、serving costで、SSD-backed cacheがDRAM-backed cacheにどこまで近づけるかを見る。

## 主要結果

arXiv abstractで報告されている主要値は以下。

- GDS-enabled SSD-backed LMCacheと比べ、厳しいSLO条件で **TTFTを78.3%削減**。
- 達成可能な **request rateを2倍**に改善。
- **serving costを27%削減**。
- SSD bandwidthを飽和させ、GPU stallをほぼゼロまで減らし、DRAM-backed LMCacheに近い推論性能を実現したと報告。

これらはSSDをDRAMと同じ速度にする結果ではなく、従来SSD構成で支配的だったCPU側I/O発行とGPU待ちを取り除くことで、storage bandwidthを実際のserving性能へ結び付けた結果と解釈できる。

## 既存研究との差

### LMCache / GDS-backed KV offloadとの差

LMCache等の階層KV cacheはGPU外へKVを保存して再利用できるが、SSD tierではGDSを使ってdata copyをdirect化してもI/O開始・管理にCPUが残る。Tuttiは**data pathだけでなくI/O control pathもGPU側へ寄せる**点が中心的な差。

### InstAttentionとの差

InstAttentionはKVとattention計算自体を計算機能付きstorageへ移し、KVをGPUへ戻さない方向を取る。Tuttiは通常のNVMe SSDを大容量cache tierとして使い、必要なKVをGPU HBMへ高速に戻して既存GPU推論を継続する。したがって、前者は「計算をdataへ移す」、後者は「dataをGPUへ戻すI/O stackをGPU中心に作り直す」という違いがある。

### CPU DRAM offloadとの差

CPU DRAM offloadはPCIe / NVLink-C2C等を介したmemory transferが中心で、容量はhost DRAMに制限される。Tuttiはより低速だが大容量・低costなNVMe SSDを対象にし、storage queueのparallelismとI/O control overheadを主問題として扱う。

## 限界

- SSD-backed KV cacheなので、cache missやI/O量が計算とoverlapできない条件ではstorage latency / bandwidthの影響を受ける。
- GPU側へI/O controlを移すため、storage処理とmodel kernelのGPU resource競合を管理する必要がある。
- GPU direct I/Oを利用できるhardware / software stackが前提となり、一般的なCPU-mediated storage pathへそのまま適用できる設計ではない。

## 一般的な実装含意

SSD offloadでは「SSDの公称bandwidth」だけを見ても実効性能は決まらない。LLMのKV cacheのように論理的には大きいが物理的には多数のpageへ分かれたdataでは、**誰がI/O requestを作り、何件同時にqueueへ投入できるか**がGPU待ち時間を左右する。

そのため今後の階層KV cacheでは、HBM / DRAM / SSDというplacement policyだけでなく、storage request発行、memory mapping、GPU kernel schedulingまでをserving runtimeと共同設計する価値が高い。特にagentic workloadや長いconversationでprefix再利用量が増えるほど、SSD tierを「容量だけ大きい遅いcache」から「計算とoverlap可能な実用tier」へ変えるI/O control設計が重要になる。

## 引用関係・関連研究

- **PagedAttention / vLLM**: KV cacheをpage単位で管理するserving基盤。TuttiはvLLMへ統合して評価する。
- **LMCache**: GPU外のDRAM / SSDへKVを保存・共有する階層cache基盤。Tuttiの主要比較対象。
- **CacheGen**: KV cacheを圧縮・streamingしてnetwork / storage transfer costを下げる系統。Tuttiはrepresentation圧縮よりI/O control pathを主に改善する。
- **GeminiFS**: GPUがstorage data pathを直接扱うfile-system設計で、TuttiのGPU-centric storage設計と技術的に近い基盤。
- **InstAttention / InstInfer**: storage側でattentionを実行し、KV transfer自体を避ける別方向のstorage活用研究。
