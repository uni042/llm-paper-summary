# SpeContext: Enabling Efficient Long-context Reasoning with Speculative Context Sparsity in LLMs

> 蒸留言語モデルの注意分布を「本体LLMがどの過去トークンを見るか」の安価な予測器として使い、重要KVを推論前に選択する。これによりKV検索とCPU-GPU転送を本体計算から切り離し、非同期先読み・差分更新・適応オフロードまで一体化する。

## 概要

長文脈LLMでは、生成が進むほど鍵・値キャッシュ（Key-Value cache; KVキャッシュ）が増える。GPUメモリに全KVを置けない環境ではCPU DRAMへ退避し、各生成ステップで必要なKVだけGPUへ戻す疎注意・KV検索が有力になる。しかし従来方式は、**本体LLMの各層を実行してからその層で重要KVを選ぶ**構造が多く、検索→転送→注意計算が直列化する。KVを減らしても検索とPCIe転送がクリティカルパスに残り、長文脈推論ではFlashInferの全注意より遅くなる場合さえある。

SpeContextの着眼点は、重要KVを選ぶ検索器の目的が「本体LLMと同じ情報へ注目すること」なら、知識蒸留（knowledge distillation）済みの小型モデルを検索器として再利用できるという点にある。蒸留言語モデル（Distilled Language Model; DLM）は教師LLMの出力分布へ近づくよう学習されるため、内部の注意対象にも相関があると考え、情報理論の相互情報量（mutual information）とデータ処理不等式（data processing inequality）からこの関係を説明する。

実装ではEAGLE-3由来DLMから、重要トークン選択に不要な部分を落とし、埋め込みとQK射影を中心にした**軽量検索ヘッド（lightweight retrieval head）**を本体LLMの前段へ置く。検索ヘッドは本体入力だけで重要トークン集合を先に出せるため、本体の各層計算とKV転送の依存関係を切れる。さらに隣接生成ステップで選択される重要トークンが80%以上重なる観測を使い、新たに必要になったKVだけを送る**弾性ロード（elastic loading）**を導入する。

最後に、系列長が伸びるとGPU常駐可能なKV量が変わるため、固定の「全オフロード／全常駐」ではなく、理論メモリモデルから系列長しきい値を計算し、必要になった時点で層単位にKVをCPUへ移す**適応メモリ管理（adaptive memory management）**を加える。アルゴリズム、データフロー、メモリ配置の3層を同時に扱う点がSpeContextの本体である。

評価では、クラウド相当の80GB GPUでHugging Face Eager全注意比最大24.89倍、FlashInfer比最大2.20倍のスループットを報告する。8GB RTX 4060 Laptop GPUを4GB使用制限で動かすエッジ条件ではEager比最大10.06倍、ShadowKV比最大1.17倍である。KV予算1K以上ではLongBench上で全注意相当の精度へ到達する一方、予算512ではClusterKVより精度がやや低いという負の条件も報告されている。

## 問題設定

### 長文脈KV圧縮は「何を残すか」だけでは足りない

KV検索型の疎注意では、CPU側などに全KVを保持し、各ステップで重要そうな一部だけGPUへ載せる。理論上は注意の計算量とGPUメモリを減らせるが、従来の層内検索は本体LLMの中間状態を使うため、各層で検索結果が確定するまでKV転送を開始できない。結果として、検索・ホストメモリアクセス・PCIe転送が逐次生成の待ち時間へそのまま乗る。

さらに推論が進むと系列長は1トークンずつ増える。固定オフロード方針では、少し系列が伸びただけでGPUメモリ境界を越えて急にCPU転送が増え、論文では80%以上の性能低下が起こり得ると報告する。つまり必要なのは疎性そのものではなく、**検索を本体より前へ出すこと、転送を計算へ重ねること、GPU常駐量を系列長に応じて変えること**である。

### 蒸留モデルを検索器にする理由

Quest、ClusterKV、ShadowKVなどは異なる重要度推定を使うが、検索結果と本体LLMの注目先がずれるほど品質が落ちる。SpeContextは「教師LLMと蒸留モデルの出力分布が揃うなら、入力文脈から抽出する情報にも共通性が残る」と考える。

重要なのはDLMをそのままもう一個走らせない点である。検索に必要なのは最終生成ではなく注意重みであり、フィードフォワードネットワーク（Feed-Forward Network; FFN）やV射影などは省ける。これにより検索ヘッドのパラメータを90%以上削減し、検索を前段へ追加する費用を抑える。

## SpeContextの処理全体

1. コンパイル時にモデル、GPUメモリ量、KV予算、系列長から各層のKVをGPUに保持できる系列長しきい値を計算する。
2. 要求が来ると軽量検索ヘッドが本体LLMと同じ入力を先に処理し、注意ヘッド単位で重要トークンのインデックスを出す。
3. 前ステップの重要集合と比較し、新しく必要になったKVだけをCPUからGPUへ弾性ロードする。
4. 複数CUDAストリームを用い、KV先読みと本体LLMの計算を並行させる。
5. 系列長がしきい値を越えるたび、下位層からKVをCPUへ段階的にオフロードし、残りの層のGPU常駐量を最大化する。
6. 本体LLMはGPU上に準備されたKV予算だけで注意計算を行い、次トークン生成後に検索集合とKV配置を更新する。

## 手法

### 1. 蒸留モデルから軽量検索ヘッドを作る

検索ヘッドはDLMの埋め込みとQK射影を保持し、注意重みから重要トークンを選ぶ。元のDLMが2K文脈までしか扱えない場合は、学習不要のYaRNで長文脈へ拡張する。検索目的には注意重みがあればよいため、生成に必要な残りの層を削除でき、論文ではパラメータ数を90%以上削減する。

トークン選択はバッチ全体で一つの集合を作るより、注意ヘッド単位で行う。ヘッドごとに参照先が異なるため、この細粒度選択の方が本体LLMの重要トークンとの一致率が高かった。MHA、GQA、MQA、MLAという異なる注意構造に合わせてKVヘッドとの対応を処理する。

追加費用は検索ヘッドの重みとフルKキャッシュである。8B級モデル向け検索ヘッド重みは約60MBと報告される。DLM自体はEAGLE-3の学習成果を利用し、論文が引用する条件ではRTX 3090で約24時間の学習を要する。

### 2. 本体より先に検索して非同期先読みする

従来の層内検索は本体の現在層のQ/Kなどへ依存するため、検索後にKV転送を始めるしかない。SpeContextの検索ヘッドは本体入力だけで選択を完了できるため、必要KVのインデックスがLLM層実行前に分かる。

そこで複数CUDAストリームを使い、ある計算をGPUで進めている間に別ストリームでCPU DRAMからKVを先読みする。これにより「転送時間を削る」のではなく、可能な部分をLLM計算時間の裏へ隠す。KV転送が計算より長い場合は完全には隠せないため、次の弾性ロードが必要になる。

### 3. 弾性ロードで差分KVだけを更新する

隣接生成ステップの重要トークン集合は80%以上重なり、次ステップで入れ替わるのは概ね20%程度だった。SpeContextは前回集合 S_last と今回集合 S_now を比較し、GPUに既にあるKVを再利用して、新規集合だけをコピーする。

固定KV予算なら、追い出す要素と新しく入れる要素の数は一致する。実装はTensor.copy_()によるインプレース更新で済み、完全なKV予算を毎回送り直さない。論文ではこの仕組みによりKV転送量を最大90%削減すると報告する。

この利得は時間的局所性に依存する。連続ステップで注目先が大きく変わる入力では集合重複が下がり、転送削減量も小さくなる。

### 4. 系列長に追従する適応メモリ管理

GPUへ全層KVを置ける間は、CPUから読むより常駐させた方が速い。SpeContextはモデル重み、DLM、KV、作業領域とGPU容量を式でモデル化し、「何層分のKVをGPUへ常駐できるか」を最大化する。

推論開始時に系列長しきい値 S^T を計算し、系列がしきい値を越えるごとに1層ずつKVをCPUへ退避する。たとえばLlama3-8Bで末尾2層をCPUへ出して開始し、さらに文脈が伸びれば30層目も退避する、といった段階的な切替を行う。

固定全オフロードよりCPU-GPU転送を減らし、固定全常駐よりOOMを避ける。ここでの出力は「各時点でGPUに残す層数」と「CPU層のためのKV予算バッファ」である。

## 既存研究との差

Quest、ClusterKV、ShadowKVのような方式は、本体推論中の層ごと検索で重要KVを決める。そのため選択精度を上げても、検索結果が出るまで転送を開始できない。SpeContextはDLMの注意を代理信号に使い、**本体より前にグローバルな重要KVを決める**ことでデータ依存そのものを外す。

また単なるCPUオフロード方式と異なり、全量を毎ステップ往復させない。隣接ステップの重要集合の重複を利用して差分だけ更新し、さらにGPUに残す層数も系列長へ追従させる。アルゴリズム上の疎性を、実際の転送量とGPU容量へつなぐシステム共同設計が主眼である。

## 限界・実装状況

検索精度はDLMと本体LLMの情報焦点が似ていることに依存する。KV予算512ではClusterKVよりLongBench精度がやや低く、強い疎化では品質損失が先に現れる。

弾性ロードは隣接ステップの選択集合が大きく重なるほど有利であり、注意先が急変する入力では差分転送の利得が縮む。さらにCPU-GPU接続帯域が変われば、非同期化で隠せる割合も変わる。

論文のクラウド環境記述には本文の「A100-80GB」とTable 2の「A800 80GB」という不整合があるため、再現時はTable 2だけでハードウェア型番を断定せず著者実装・補足資料を確認する必要がある。
