# ParisKV: Fast and Drift-Robust KV-Cache Retrieval for Long-Context LLMs

## 書誌情報

- **著者:** Yanlin Qi, Xinhang Chen, Huiqiang Jiang, Qitong Wang, Botao Peng, Themis Palpanas
- **掲載:** 43rd International 会議 on Machine Learning (ICML 2026) 採択
- **arXiv:** 2602.07721（v3, 2026-05-28）
- **公式実装:** https://github.com/amy-77/ParisKV

## 一文要約

完全精度のKV キャッシュをCPU DRAMへ置いたまま、GPU上の小さなキー要約だけで現在のクエリに重要なトークンを二段階検索し、選ばれたKVだけをGPUからCPU メモリへ直接読みに行くことで、長い生成中に検索indexが古くなる問題とCPU検索・CPU主導転送の待ち時間を同時に減らすKV 検索 システム。

## 問題設定

長文脈のデコードでは、KV キャッシュが文脈長に比例して増え、全KVをGPU HBMへ置く容量と毎ステップで全KVを読むメモリ 帯域の両方がボトルネックになる。KVをCPU DRAMへオフロードし、アテンションに重要なTop-k トークンだけをretrieveすればGPU側のKV量を減らせるが、既存方式には主に二つの問題がある。

1. プリフィル時のキー分布から作ったクラスタ中心を使う方式では、デコードで新しいキーが増えるにつれて分布が変化し、クラスタ中心と現在のキー分布がずれて重要トークンの検索再現率が低下する。
2. CPU上で候補検索を行ってからCPUがKV転送を指示する方式では、検索と細粒度data movementそのものが遅延になり、KVを減らした効果を相殺しやすい。

ParisKVは**検索判断をGPU内へ残し、CPU DRAMを完全精度 KVの大容量裏付け用 storeとしてだけ使う**構成でこの二つを分離する。

## 手法

### 1. decode中に古くなりにくいdata-independentな方向cluster

プリフィルで各キーを正規化し、クエリと共通の直交回転をかけて方向情報を均し、複数の小さなsubspaceへ分割する。各subspaceでは学習dataからクラスタ中心を作る代わりに、単位球面を均等に覆う固定の方向重心を使う。

この重心はプリフィル時のキー分布そのものへfitしていないため、デコードで新しいキーが増えて分布が変化しても「プリフィル時に学習したクラスタ中心が古くなる」という種類のdriftを避けられる。新しく生成されたキーも同じ変換と固定重心で逐次indexへ追加できる。

### 2. GPU上の粗い候補選択

完全精度 KVをCPUへオフロードした後も、各キーが各subspaceでどの方向重心へ属するかという小さなIDをGPUへ残す。

デコード クエリについて各subspaceで近い重心を選び、その重心と衝突するキーへ投票を与える。複数subspaceの投票を合計し、高スコアの少数キーだけを次段の候補にする。これは全キーについて完全精度 inner productを計算するより軽く、global 並べ替えも避ける専用GPU カーネルで実装される。

### 3. 4-bit key要約による候補の再順位付け

粗い候補選択だけでは重要キーの順位を正確に決めにくいため、ParisKVは各キーのsubspace方向を**1-bit sign + 3-bit magnitude**の4-bit表現へ圧縮してGPUへ保持する。さらに量子化でinner productがずれる量を補正する尺度をプリフィル時に計算して保存する。

候補に対してだけ、この4-bit要約と現在のクエリから元のアテンション スコアに近いinner productを推定し、最終Top-kを選ぶ。完全精度 キーをCPUから読む前に候補をかなり絞れるため、検索のためだけに大量のKVをCPU–GPU間で動かす必要がない。

### 4. UVAによる選択KVのon-demand fetch

最終Top-kが決まると、GPU カーネルが統合仮想アドレス空間（Unified Virtual Addressing; UVA）を使ってCPU DRAM上の完全精度 KVから選択された部分だけを直接参照する。CPU側で検索して明示的なmemcpyを大量発行する重要な 経路を避け、CPU メモリは容量拡張、GPUは検索判断とアテンション計算を担当する。

KVはGPU上のsink領域、直近トークンを保持するlocal領域、CPUへオフロードする検索領域、生成直後のupdate バッファへ分ける。update バッファが一定量たまった時だけ古いlocal KVをCPUへ送り、同時にGPU側の検索メタデータを更新することで、毎デコード ステップのindex更新コストもまとめて償却する。

## 評価条件

正確度評価ではQwen3-4B系、Qwen3-8B、DeepSeek-R1-Llama-8Bを使い、GPQA-Diamond、MATH500、AIME 2025、LongBench-V2、RULERなどで長入力・長生成の双方を評価している。ParisKVの最終検索 容量上限は主要実験で固定Top-100。

効率評価ではLlama-3.1-8BとQwen3-8Bを用い、64K / 128K / 256K / 384K 文脈でバッチ 拡張を測り、さらに512K / 1024K 文脈をバッチ 1で評価している。full アテンションはFlashAttention-2、KV 検索 比較対象にはMagicPIG、PQCache、RetroInfer、ShadowKV、Questなどを含む。

論文の1M-トークン級オフロード実験ではCPU DRAM容量が実際の拡張上限になり、384Kでさらにバッチを増やせる余地があっても利用可能なCPU メモリ 167 GBが制約になったと報告している。

## 主要結果

- 64K / 128K / 256K 文脈のpeak デコード スループットは、full アテンションに対してLlama-3.1-8Bで **2.3× / 2.1× / 2.7×**、Qwen3-8Bで **2.3× / 2.2× / 2.8×**。
- full アテンションが384Kでバッチ 1でもOOMになる評価条件でもParisKVは動作し、バッチ 3まで尺度した。
- Llama-3.1-8B・1024K・バッチ 1ではデコード 遅延が約 **49 ms/ステップ**で、MagicPIGの約830 ms/ステップに対して約 **16.9×**、PQCacheの約2179 ms/ステップに対して約 **44.4×**低い。
- RULER 128Kでは疎 / 検索方式中で平均 **83.49**を記録し、RetroInfer 77.45、Quest 79.34、ShadowKV 80.29を上回った。full アテンションは84.12。
- 長文生成 reasoningでは9設定中7設定でfull アテンションと同等以上の正確度を報告する一方、AIME 2025など個別設定ではfull アテンションを下回る場合もあり、近似検索が常に無損失という意味ではない。

専用カーネルでは、Torch実装との比較で衝突処理9.2×、UVA KV 取得約40×、融合した 再順位付け 3–4×などのカーネル水準の改善を報告している。ただしこれらは個別演算子比較であり、エンドツーエンド 高速化倍率とは区別する必要がある。

## 既存研究との差

RetroInferやRetrievalAttentionもCPU側の大きなKV集合からクエリ依存に必要KVだけを選ぶが、ParisKVは**候補選択と再順位付けをGPU上の圧縮メタデータだけで完結させ、最終Top-kの完全精度 KVだけをUVAでCPUから読む**点を強く押し出す。

また、プリフィル キーから学習したクラスタを使う検索では長いデコード中に新規キーが増えるとindexと分布がずれる。ParisKVは正規化・回転後の空間へデータ非依存な固定方向重心を置き、デコード中の分布変化で重心自体が古くなる問題を避ける。

PQCacheのように強く圧縮した表現から検索する方式に対しては、粗い衝突選択の後で4-bit方向コードからアテンション inner productを再推定する二段階構成にし、検索コストと再現率を分けて調整する。

## 限界

- 完全精度 KVを消すのではなくCPU DRAMへ保持するため、百万トークン級では大容量ホスト メモリが必要であり、論文自身の実験でもCPU メモリが拡張上限になっている。
- UVAによる細粒度remote accessと専用CUDA カーネルを前提とするため、CPU–GPU接続、ホスト メモリ 帯域、GPU architectureが異なる環境で同じ高速化倍率になるとは限らない。
- GPU上には重心 ID、4-bit キー コード、補正尺度などの検索 メタデータを保持する必要があり、KV全体より小さいものの文脈長に対するメタデータ コストは残る。
- 固定Top-kの近似アテンションなので、重要トークンがTop-kから漏れるワークロードでは正確度低下があり得る。論文でも全タスクでfull アテンションを上回るわけではない。
- index メタデータの追加・update、正規化・回転、候補選択・再順位付けの計算が増えるため、短文脈やKVがHBMへ十分収まる条件ではオーバーヘッドが利益を上回り得る。

## 一般的な実装上の含意

CPU DRAMをKV キャッシュの容量拡張に使う場合、**CPUへ検索処理まで移す必要はない**。GPUへ「検索に十分な小さいメタデータ」だけを残し、検索判断をGPUで行って最終dataだけをremote メモリから読む構成なら、ホスト 容量を使いながらCPU 調整を重要な 経路から外せる。

また、長文生成 ワークロードではプリフィル時に最適だったindexがそのまま有効とは限らない。indexを頻繁に再学習するのではなく、分布依存性の低い表現へ変換して固定partitionを使う設計は、KV 検索以外の長時間streaming indexにも応用可能な考え方である。

## 引用関係

- **先行:** RetrievalAttention、MagicPIG、PQCache、RetroInfer、ShadowKVなどのクエリ依存 KV 検索 / CPU-assisted 疎 アテンション。
