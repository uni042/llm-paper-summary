# ParisKV: Fast and Drift-Robust KV-Cache Retrieval for Long-Context LLMs

## 書誌情報

- **著者:** Yanlin Qi, Xinhang Chen, Huiqiang Jiang, Qitong Wang, Botao Peng, Themis Palpanas
- **掲載:** 43rd International Conference on Machine Learning (ICML 2026) 採択
- **arXiv:** 2602.07721（v3, 2026-05-28）
- **公式実装:** https://github.com/amy-77/ParisKV

## 一文要約

full-precisionのKV cacheをCPU DRAMへ置いたまま、GPU上の小さなkey要約だけで現在のqueryに重要なtokenを二段階検索し、選ばれたKVだけをGPUからCPU memoryへ直接読みに行くことで、長い生成中に検索indexが古くなる問題とCPU検索・CPU主導転送の待ち時間を同時に減らすKV retrieval system。

## 問題設定

長contextのdecodeでは、KV cacheがcontext長に比例して増え、全KVをGPU HBMへ置く容量と毎stepで全KVを読むmemory bandwidthの両方がbottleneckになる。KVをCPU DRAMへoffloadし、attentionに重要なTop-k tokenだけをretrieveすればGPU側のKV量を減らせるが、既存方式には主に二つの問題がある。

1. prefill時のkey分布から作ったcluster中心を使う方式では、decodeで新しいkeyが増えるにつれて分布が変化し、cluster中心と現在のkey分布がずれて重要tokenの検索recallが低下する。
2. CPU上で候補検索を行ってからCPUがKV転送を指示する方式では、検索と細粒度data movementそのものがlatencyになり、KVを減らした効果を相殺しやすい。

ParisKVは**検索判断をGPU内へ残し、CPU DRAMをfull-precision KVの大容量backing storeとしてだけ使う**構成でこの二つを分離する。

## 手法

### 1. decode中に古くなりにくいdata-independentな方向cluster

prefillで各keyを正規化し、queryと共通の直交回転をかけて方向情報を均し、複数の小さなsubspaceへ分割する。各subspaceでは学習dataからcluster中心を作る代わりに、単位球面を均等に覆う固定の方向centroidを使う。

このcentroidはprefill時のkey分布そのものへfitしていないため、decodeで新しいkeyが増えて分布が変化しても「prefill時に学習したcluster中心が古くなる」という種類のdriftを避けられる。新しく生成されたkeyも同じ変換と固定centroidで逐次indexへ追加できる。

### 2. GPU上の粗い候補選択

full-precision KVをCPUへoffloadした後も、各keyが各subspaceでどの方向centroidへ属するかという小さなIDをGPUへ残す。

decode queryについて各subspaceで近いcentroidを選び、そのcentroidと衝突するkeyへvoteを与える。複数subspaceのvoteを合計し、高scoreの少数keyだけを次段の候補にする。これは全keyについてfull-precision inner productを計算するより軽く、global sortも避ける専用GPU kernelで実装される。

### 3. 4-bit key要約による候補の再順位付け

粗い候補選択だけでは重要keyの順位を正確に決めにくいため、ParisKVは各keyのsubspace方向を**1-bit sign + 3-bit magnitude**の4-bit表現へ圧縮してGPUへ保持する。さらに量子化でinner productがずれる量を補正するscaleをprefill時に計算して保存する。

候補に対してだけ、この4-bit要約と現在のqueryから元のattention scoreに近いinner productを推定し、最終Top-kを選ぶ。full-precision keyをCPUから読む前に候補をかなり絞れるため、検索のためだけに大量のKVをCPU–GPU間で動かす必要がない。

### 4. UVAによる選択KVのon-demand fetch

最終Top-kが決まると、GPU kernelが統合仮想アドレス空間（Unified Virtual Addressing; UVA）を使ってCPU DRAM上のfull-precision KVから選択された部分だけを直接参照する。CPU側で検索して明示的なmemcpyを大量発行するcritical pathを避け、CPU memoryは容量拡張、GPUは検索判断とattention計算を担当する。

KVはGPU上のsink領域、直近tokenを保持するlocal領域、CPUへoffloadするretrieval領域、生成直後のupdate bufferへ分ける。update bufferが一定量たまった時だけ古いlocal KVをCPUへ送り、同時にGPU側の検索metadataを更新することで、毎decode stepのindex更新costもまとめて償却する。

## 評価条件

accuracy評価ではQwen3-4B系、Qwen3-8B、DeepSeek-R1-Llama-8Bを使い、GPQA-Diamond、MATH500、AIME 2025、LongBench-V2、RULERなどで長入力・長生成の双方を評価している。ParisKVの最終retrieval budgetは主要実験で固定Top-100。

効率評価ではLlama-3.1-8BとQwen3-8Bを用い、64K / 128K / 256K / 384K contextでbatch scalingを測り、さらに512K / 1024K contextをbatch 1で評価している。full attentionはFlashAttention-2、KV retrieval baselineにはMagicPIG、PQCache、RetroInfer、ShadowKV、Questなどを含む。

論文の1M-token級offload実験ではCPU DRAM容量が実際のscaling上限になり、384Kでさらにbatchを増やせる余地があっても利用可能なCPU memory 167 GBが制約になったと報告している。

## 主要結果

- 64K / 128K / 256K contextのpeak decode throughputは、full attentionに対してLlama-3.1-8Bで **2.3× / 2.1× / 2.7×**、Qwen3-8Bで **2.3× / 2.2× / 2.8×**。
- full attentionが384Kでbatch 1でもOOMになる評価条件でもParisKVは動作し、batch 3までscaleした。
- Llama-3.1-8B・1024K・batch 1ではdecode latencyが約 **49 ms/step**で、MagicPIGの約830 ms/stepに対して約 **16.9×**、PQCacheの約2179 ms/stepに対して約 **44.4×**低い。
- RULER 128Kではsparse / retrieval方式中で平均 **83.49**を記録し、RetroInfer 77.45、Quest 79.34、ShadowKV 80.29を上回った。full attentionは84.12。
- long-generation reasoningでは9設定中7設定でfull attentionと同等以上のaccuracyを報告する一方、AIME 2025など個別設定ではfull attentionを下回る場合もあり、近似検索が常にlosslessという意味ではない。

専用kernelでは、Torch実装との比較でcollision処理9.2×、UVA KV fetch約40×、fused reranking 3–4×などのkernel-level改善を報告している。ただしこれらは個別operator比較であり、end-to-end speedupとは区別する必要がある。

## 既存研究との差

RetroInferやRetrievalAttentionもCPU側の大きなKV集合からquery-dependentに必要KVだけを選ぶが、ParisKVは**候補選択と再順位付けをGPU上の圧縮metadataだけで完結させ、最終Top-kのfull-precision KVだけをUVAでCPUから読む**点を強く押し出す。

また、prefill keyから学習したclusterを使う検索では長いdecode中に新規keyが増えるとindexと分布がずれる。ParisKVは正規化・回転後の空間へdata-independentな固定方向centroidを置き、decode中の分布変化でcentroid自体が古くなる問題を避ける。

PQCacheのように強く圧縮した表現から検索する方式に対しては、粗いcollision選択の後で4-bit方向codeからattention inner productを再推定する二段階構成にし、検索costとrecallを分けて調整する。

## 限界

- full-precision KVを消すのではなくCPU DRAMへ保持するため、million-token級では大容量host memoryが必要であり、論文自身の実験でもCPU memoryがscaling上限になっている。
- UVAによる細粒度remote accessと専用CUDA kernelを前提とするため、CPU–GPU接続、host memory bandwidth、GPU architectureが異なる環境で同じspeedupになるとは限らない。
- GPU上にはcentroid ID、4-bit key code、補正scaleなどのretrieval metadataを保持する必要があり、KV全体より小さいもののcontext長に対するmetadata costは残る。
- 固定Top-kの近似attentionなので、重要tokenがTop-kから漏れるworkloadではaccuracy低下があり得る。論文でも全taskでfull attentionを上回るわけではない。
- index metadataの追加・update、正規化・回転、候補選択・rerankingの計算が増えるため、短contextやKVがHBMへ十分収まる条件ではoverheadが利益を上回り得る。

## 一般的な実装上の含意

CPU DRAMをKV cacheの容量拡張に使う場合、**CPUへ検索処理まで移す必要はない**。GPUへ「検索に十分な小さいmetadata」だけを残し、検索判断をGPUで行って最終dataだけをremote memoryから読む構成なら、host capacityを使いながらCPU orchestrationをcritical pathから外せる。

また、long-generation workloadではprefill時に最適だったindexがそのまま有効とは限らない。indexを頻繁に再学習するのではなく、分布依存性の低い表現へ変換して固定partitionを使う設計は、KV retrieval以外の長時間streaming indexにも応用可能な考え方である。

## 引用関係

- **先行:** RetrievalAttention、MagicPIG、PQCache、RetroInfer、ShadowKVなどのquery-dependent KV retrieval / CPU-assisted sparse attention。
- **RetroInferとの関係:** 両者ともCPU DRAMを大容量KV storeとして使うが、ParisKVはGPU-residentな圧縮metadataによるcoarse-to-fine retrievalとUVA direct fetchへ重点を置く。
- **近接:** Quest、FreeKV、SOCKET、Twilightなどのdecode-stage sparse attention / KV selection方式ともaccuracy比較を行う。
