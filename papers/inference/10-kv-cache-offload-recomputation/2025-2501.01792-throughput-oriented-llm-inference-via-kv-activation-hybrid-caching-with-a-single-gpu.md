# Throughput-Oriented LLM Inference via KV-Activation Hybrid Caching with A Single GPU

> 過去トークンをKVまたは小さい中間活性値で混在保存し、重み転送中に活性値からKVを再生成して、PCIe転送量とGPU再計算量の大きい方を抑える方式。

## 概要

RTX 4090 24GB＋882GB DDR4でOPT-6.7B〜66Bを評価し、KV/活性値混合キャッシュのスループットはFlexGen比で複数条件平均2.19倍、活性値のみの変種比1.35倍となった。


取得は、モデル 重みとKV キャッシュの両方をホスト メモリへオフロードするスループット重視推論で、**過去トークンの状態を、KVそのものとして保存するか、K/Vを作る直前の小さい中間活性値として保存するかを混在させる**システムである。

ここでいう **活性値 チェックポイント** は、あとでK/Vを作り直せるよう途中の計算結果を保存しておく方式を指す。KVをそのまま保存する場合より小さいが、使う前にK/V 射影を再実行する必要がある。

KV キャッシュだけを使うと再計算は不要だが、ホスト→GPUへ運ぶdataが大きくPCIe待ちが増える。逆に活性値だけを保存するとキャッシュ容量と転送量は約半分になるが、K/Vを毎回GPUで再生成する計算が増える。

取得はこの2つの中間を取り、トークン ブロックの一部をKV形式、一部を活性値形式で保存する。**重みをCPUからGPUへ読み込んでいる時間に活性値からKVを再生成**し、PCIe transferとGPU 再計算のどちらか一方だけが長く余らない比率を選ぶ。

arXiv初版ではシステム名がHybridServe、論文名が `Efficient LLM Inference with Activation Checkpointing and Hybrid Caching` だったが、ICCD 2025最終版ではシステム名が取得、論文名も現在のものへ変更されている。同一研究として本ページへ統合する。

## 問題設定

FlexGen型の単一GPU オフロードでは、大バッチで重みを再利用できる一方、要求ごとに異なるKV キャッシュは共有できないため、バッチ sizeと文脈 lengthに比例してPCIe 通信量が増える。

KVだけをCPUへ置く場合、GPUはKVや重みの到着待ちでアイドルになる。活性値 チェックポイントなら同じトークン/層についてKとVの2 tensorではなく、その元になる活性値 1つを保持すればよいため、**ホスト メモリ 占有量とtransfer量を約半分にできる**。

ただし活性値からK/Vを生成する行列 積が必要になるため、全キャッシュを活性値へ変えるとGPU compute側がボトルネックになる。

取得の問題は、**限られたホスト/GPU メモリの中でKVと活性値を何対何で保存すれば、PCIeとGPUの双方を最もよく使えるか**である。

## 手法

### 1. KV blockとACT blockを同じcache内で管理する

キャッシュをトークン ブロック単位に分け、各ブロックを

- **KV ブロック:** K/Vをそのまま保持し、GPUへ転送すれば即アテンションに使える
- **活性値 ブロック:** その層への入力活性値を保持し、GPUでK/Vを再生成して使う

のどちらかとして保存する。

同じトークン ブロックなら活性値 ブロックはKV ブロックの約半分の容量で済む一方、再計算コストが発生する。

### 2. 各blockの「形式」と「置き場所」を対応表で追跡する

取得はvLLMのpaged キャッシュを拡張し、各論理的 ブロックについて

- KV / 活性値のどちらか
- ホスト / GPUのどこにあるか
- 実際に使っている物理的 ブロック番号

を一つの対応表で管理する。論文の統合された ブロック tableはこの管理表を指す。

アテンション実行時はKV ブロックを直接使い、活性値 ブロックはK/Vを再生成したバッファへ変換してから、両者をまとめて通常のアテンションへ渡す。

### 3. GPU memoryではactivationを優先して保持する

ホスト メモリにはKVと活性値の両方を置けるが、限られたGPU メモリは主に活性値 ブロックへ使う。

活性値をGPUへ残せれば、次デコード ステップではPCIe transferなしにK/V再生成を開始でき、重みを待ってGPUが空く時間を再計算で埋めやすい。

### 4. 2つのbufferを交互に使い、loadとcomputeを重ねる

各デコード 反復では主に、

1. 活性値 ブロックを読み込みK/Vを再生成する
2. 次層の重みと既存KV ブロックをホストから先読みする
3. 再生成KVと転送KVを結合してアテンションを実行する

という処理を並行させる。

論文の **二重 バッファリング** は、2組のバッファを用意する。

現在小バッチをGPUで処理している間にもう片方へ次小バッチのデータを受け取ることで、読み込みと計算を交互に重ねる仕組みである。

### 5. KV/ACT比率をweight load時間へ合わせる

理想的には、活性値からKVを生成する時間とKVをPCIeで読む時間が、重み transfer中にちょうど隠れる程度になるのがよい。

取得は重み load 遅延、KV ブロック size、活性値 ブロック size、GPUに保持できる活性値数、ホスト メモリ予算から、KVと活性値の初期割当を決める。

### 6. 再計算が多いrequestと転送が多いrequestを同じmini-batchへ混ぜる

要求ごとにKV/活性値比率が異なると、ある小バッチでは再計算する過多、別の小バッチではtransfer過多になりうる。

そこで小バッチ内の

`activationからKVを再生成する時間 / KVを読み込む時間`

が1に近づくよう要求を組み合わせる。論文のbin 詰め込みは、この**計算寄り要求と転送寄り要求を釣り合うようにグループ化する処理**を指す。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA RTX 4090 24GB |
| CPU | dual-socket Intel Xeon Gold 6326 |
| Host memory | 882GB DDR4 |
| CPU-GPU | PCIe 4.0 x16 |
| Model | OPT-6.7B / 13B / 30B / 66B |
| Baseline | FlexGen、DeepSpeed-Inference、ACT-only variant |
| 実装 | vLLM拡張、Python + C++/CUDA/PyTorch |

OPT-6.7Bは重み自体はGPUへ収まるが、キャッシュ方式によるPCIe 通信量差を見るため評価対象に含めている。13B〜66Bでは重み オフロードも必要になる。

### 主要結果

ICCD最終版では、取得の混合 キャッシュはFlexGenに対して**複数条件を倍率で平均した値で2.19倍のスループット**、活性値 キャッシュだけを使う変種に対して**1.35倍**を報告している。

プレプリントの詳細評価では、FlexGen比の平均改善はOPT-6.7Bで約2.05倍、OPT-66Bで約2.33倍と、モデルが大きいほど利得が増える。大きなモデルほど重み transferが長くなり、その時間に隠せるKV 再計算が増えるためである。

また活性値 キャッシュのみから混合 キャッシュへ変えるだけでも平均1.35倍改善しており、**全部transferでも全部再計算するでもなく、両者を釣り合わせること自体に効果がある**。

## 既存研究との差

### FlexGenとの違い

FlexGenは重み / KVをホストへ置き、large バッチと層ごとの スケジュールで重み transferを要求間に償却する。しかしKV キャッシュ transferは要求ごとに増える。

取得はKVそのものの一部を**半分程度の容量で済む活性値 表現へ置換し、重み I/O中にGPUでK/Vを再生成する**ことで、KV transfer ボトルネックをcomputeへ変換する。

### KVPRとの違い

KVPRもKV transferの一部をGPU 再計算へ置換するが、CPU側から活性値を送ってその反復で「どの範囲を再計算するするか」を決める。

取得はよりキャッシュ管理寄りで、**トークン ブロックをKV形式または活性値形式として長期的に保持し、ホスト メモリ容量・GPU キャッシュ・小バッチ形成まで一体で管理する**。

### Token IDからのfull recomputationとの違い

トークン IDだけ保存してKVを再構築すると、そのトークンまでのTransformer処理を広くやり直す必要がある。

取得は各層への入力活性値をチェックポイントとして持つため、該当層のQKV 生成から再開でき、射影 / FFNなど前段の再計算を避けられる。

## 限界

- スループット重視 / 緩和遅延 ワークロードが主対象で、対話的 推論提供のTTFT / TPOT最適化が中心ではない。
- 評価はsingle RTX 4090とOPT系列に限定され、GQAを多用するLlama系やmulti-GPUでの利得は最終版では十分示されていない。
- 活性値 キャッシュはKVより小さいが、KV キャッシュとは別の表現をホスト メモリに維持するキャッシュ管理 complexityが増える。
- optimal KV/活性値比率は重み load time、PCIe 帯域、GPU compute性能に依存するためハードウェアごとの調整が必要。
- 重みがほぼ常駐できる環境では、再計算を隠す重み transfer 窓が短くなり利得が小さくなる可能性がある。

## 一般的な実装上の含意

取得はKV キャッシュを単一形式で保存する必要はないことを示す。**同じ過去状態を「そのまま使える大きいキャッシュ」と「少し計算すれば復元できる小さいチェックポイント」の混合で保持する**と、メモリ容量・PCIe帯域・GPU computeの3資源を交換できる。

特に重み オフロードが避けられない環境では、GPUが重み待ちになる時間を再計算へ使えるため、再計算は単なる追加コストではなくI/O待ち時間を埋める仕事として扱える。
