# Throughput-Oriented LLM Inference via KV-Activation Hybrid Caching with A Single GPU

> 過去tokenを、すぐ使えるKVそのものと、K/Vを作る前のより小さい中間activationの2形式で混在保存し、weight転送中にactivationからKVを再生成してPCIe転送量とGPU再計算量を釣り合わせる方式。

## 概要

CAPTUREは、model weightとKV cacheの両方をhost memoryへoffloadするthroughput-oriented推論で、**過去tokenの状態を、KVそのものとして保存するか、K/Vを作る直前の小さい中間activationとして保存するかを混在させる**systemである。

ここでいう **activation checkpoint** は、あとでK/Vを作り直せるよう途中の計算結果を保存しておく方式を指す。KVをそのまま保存する場合より小さいが、使う前にK/V projectionを再実行する必要がある。

KV cacheだけを使うと再計算は不要だが、host→GPUへ運ぶdataが大きくPCIe待ちが増える。逆にactivationだけを保存するとcache容量と転送量は約半分になるが、K/Vを毎回GPUで再生成する計算が増える。

CAPTUREはこの2つの中間を取り、token blockの一部をKV形式、一部をactivation形式で保存する。**weightをCPUからGPUへ読み込んでいる時間にactivationからKVを再生成**し、PCIe transferとGPU recomputationのどちらか一方だけが長く余らない比率を選ぶ。

arXiv初版ではsystem名がHybridServe、論文名が `Efficient LLM Inference with Activation Checkpointing and Hybrid Caching` だったが、ICCD 2025最終版ではsystem名がCAPTURE、論文名も現在のものへ変更されている。同一研究として本ページへ統合する。

## 問題設定

FlexGen型のsingle-GPU offloadでは、大batchでweightを再利用できる一方、requestごとに異なるKV cacheは共有できないため、batch sizeとcontext lengthに比例してPCIe trafficが増える。

KVだけをCPUへ置く場合、GPUはKVやweightの到着待ちでidleになる。activation checkpointなら同じtoken/layerについてKとVの2 tensorではなく、その元になるactivation 1つを保持すればよいため、**host memory footprintとtransfer量を約半分にできる**。

ただしactivationからK/Vを生成するmatrix multiplicationが必要になるため、全cacheをactivationへ変えるとGPU compute側がbottleneckになる。

CAPTUREの問題は、**限られたhost/GPU memoryの中でKVとactivationを何対何で保存すれば、PCIeとGPUの双方を最もよく使えるか**である。

## 手法

### 1. KV blockとACT blockを同じcache内で管理する

cacheをtoken block単位に分け、各blockを

- **KV block:** K/Vをそのまま保持し、GPUへ転送すれば即attentionに使える
- **ACT block:** そのlayerへの入力activationを保持し、GPUでK/Vを再生成して使う

のどちらかとして保存する。

同じtoken blockならACT blockはKV blockの約半分の容量で済む一方、再計算costが発生する。

### 2. 各blockの「形式」と「置き場所」を対応表で追跡する

CAPTUREはvLLMのpaged cacheを拡張し、各logical blockについて

- KV / ACTのどちらか
- host / GPUのどこにあるか
- 実際に使っているphysical block番号

を一つの対応表で管理する。論文のUnified block tableはこの管理表を指す。

attention実行時はKV blockを直接使い、ACT blockはK/Vを再生成したbufferへ変換してから、両者をまとめて通常のattentionへ渡す。

### 3. GPU memoryではactivationを優先して保持する

host memoryにはKVとACTの両方を置けるが、限られたGPU memoryは主にACT blockへ使う。

activationをGPUへ残せれば、次decode stepではPCIe transferなしにK/V再生成を開始でき、weightを待ってGPUが空く時間を再計算で埋めやすい。

### 4. 2つのbufferを交互に使い、loadとcomputeを重ねる

各decode iterationでは主に、

1. ACT blockを読み込みK/Vを再生成する
2. 次layerのweightと既存KV blockをhostからprefetchする
3. 再生成KVと転送KVを結合してattentionを実行する

という処理を並行させる。

論文の **double buffering** は、2組のbufferを用意し、現在mini-batchをGPUで処理している間にもう片方へ次mini-batchのdataを受け取ることで、loadとcomputeを交互に重ねる仕組みである。

### 5. KV/ACT比率をweight load時間へ合わせる

理想的には、ACTからKVを生成する時間とKVをPCIeで読む時間が、weight transfer中にちょうど隠れる程度になるのがよい。

CAPTUREはweight load latency、KV block size、ACT block size、GPUに保持できるACT数、host memory予算から、KVとACTの初期割当を決める。

### 6. 再計算が多いrequestと転送が多いrequestを同じmini-batchへ混ぜる

requestごとにKV/ACT比率が異なると、あるmini-batchではrecompute過多、別のmini-batchではtransfer過多になりうる。

そこでmini-batch内の

`activationからKVを再生成する時間 / KVを読み込む時間`

が1に近づくようrequestを組み合わせる。論文のbin packingは、この**計算寄りrequestと転送寄りrequestを釣り合うようにグループ化する処理**を指す。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA RTX 4090 24GB |
| CPU | dual-socket Intel Xeon Gold 6326 |
| Host memory | 882GB DDR4 |
| CPU-GPU | PCIe 4.0 x16 |
| Model | OPT-6.7B / 13B / 30B / 66B |
| Baseline | FlexGen、DeepSpeed-Inference、ACT-only variant |
| 実装 | vLLM拡張、Python + C++/CUDA/PyTorch |

OPT-6.7Bはweight自体はGPUへ収まるが、cache方式によるPCIe traffic差を見るため評価対象に含めている。13B〜66Bではweight offloadも必要になる。

### 主要結果

ICCD最終版では、CAPTUREのhybrid cacheはFlexGenに対して**複数条件を倍率で平均した値で2.19倍のthroughput**、activation cacheだけを使うvariantに対して**1.35倍**を報告している。

preprintの詳細評価では、FlexGen比の平均改善はOPT-6.7Bで約2.05倍、OPT-66Bで約2.33倍と、modelが大きいほど利得が増える。大きなmodelほどweight transferが長くなり、その時間に隠せるKV recomputationが増えるためである。

またactivation cacheのみからhybrid cacheへ変えるだけでも平均1.35倍改善しており、**全部transferでも全部recomputeでもなく、両者を釣り合わせること自体に効果がある**。

## 既存研究との差

### FlexGenとの違い

FlexGenはweight / KVをhostへ置き、large batchとlayer-wise scheduleでweight transferをrequest間に償却する。しかしKV cache transferはrequestごとに増える。

CAPTUREはKVそのものの一部を**半分程度の容量で済むactivation representationへ置換し、weight I/O中にGPUでK/Vを再生成する**ことで、KV transfer bottleneckをcomputeへ変換する。

### KVPRとの違い

KVPRもKV transferの一部をGPU recomputationへ置換するが、CPU側からactivationを送ってそのiterationで「どの範囲をrecomputeするか」を決める。

CAPTUREはよりcache-management寄りで、**token blockをKV形式またはACT形式として長期的に保持し、host memory容量・GPU cache・mini-batch形成まで一体で管理する**。

### Token IDからのfull recomputationとの違い

token IDだけ保存してKVを再構築すると、そのtokenまでのTransformer処理を広くやり直す必要がある。

CAPTUREは各layerへの入力activationをcheckpointとして持つため、該当layerのQKV generationから再開でき、projection / FFNなど前段の再計算を避けられる。

## 限界

- throughput-oriented / relaxed-latency workloadが主対象で、interactive servingのTTFT / TPOT最適化が中心ではない。
- 評価はsingle RTX 4090とOPT系列に限定され、GQAを多用するLlama系やmulti-GPUでの利得は最終版では十分示されていない。
- activation cacheはKVより小さいが、KV cacheとは別のrepresentationをhost memoryに維持するcache-management complexityが増える。
- optimal KV/ACT比率はweight load time、PCIe bandwidth、GPU compute性能に依存するためhardwareごとの調整が必要。
- weightがほぼ常駐できる環境では、recomputationを隠すweight transfer windowが短くなり利得が小さくなる可能性がある。

## 一般的な実装上の含意

CAPTUREはKV cacheを単一形式で保存する必要はないことを示す。**同じ過去状態を「そのまま使える大きいcache」と「少し計算すれば復元できる小さいcheckpoint」の混合で保持する**と、memory容量・PCIe帯域・GPU computeの3資源を交換できる。

特にweight offloadが避けられない環境では、GPUがweight待ちになる時間を再計算へ使えるため、recomputationは単なる追加costではなくI/O待ち時間を埋める仕事として扱える。
