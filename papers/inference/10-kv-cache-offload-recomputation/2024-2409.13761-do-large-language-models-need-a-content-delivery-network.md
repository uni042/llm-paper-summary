# Do Large Language Models Need a Content Delivery Network?

> 外部知識を毎回文章としてプリフィルするのではなく、**その文章をモデルが一度処理して得たKVキャッシュを「配送できる知識オブジェクト」として扱う**。保存・転送・複数文書の合成を推論エンジン外の知識配送網（Knowledge Delivery Network; KDN）へ切り出し、検索拡張生成（Retrieval-Augmented Generation; RAG）で繰り返されるプリフィル計算を再利用へ置き換える。著者らのLMCacheによる予備評価では、Llama 3.1 70B・2×A40上で、微調整より新知識導入40倍高速、文脈内学習より推論コスト約2.5分の1、応答遅延約3.7分の1だった。

## 概要

大規模言語モデル（Large Language Model; LLM）へ学習後の外部知識を与える代表的方法には、モデル重みへ埋め込む**微調整（fine-tuning）**と、要求の入力へ文章を付ける**文脈内学習（in-context learning）**がある。前者は一度学習すれば推論時に長い知識文書を読み直さずに済むが、知識の追加・削除・組み合わせに時間がかかり、どの知識を今回使うかを要求単位で切り替えにくい。後者は文書を入力に足すだけなので柔軟だが、同じ文書を何千回使っても毎回プリフィル計算を繰り返す。

本論文が第三の選択肢として整理するのが**KVキャッシュ学習（KV-cache learning）**である。知識文書を一度プリフィルし、その各層のキー・値状態を保存しておけば、次回から文章そのものをもう一度モデルへ通さず、その状態を読み込んで生成へ進める。知識はモデル重みから分離されたままなので、文脈内学習に近いモジュール性を保ちつつ、反復プリフィルを省ける。

ただしKVキャッシュは巨大で、従来の推論エンジンではGPUメモリ内部の一時状態として強く結合されている。単純に「保存して再利用する」だけでは、容量、GPUへの転送帯域、先頭接頭辞しか再利用できない制約、複数文書の合成、モデル更新時の互換性が問題になる。そこで著者らは、ウェブのコンテンツ配送網（Content Delivery Network; CDN）がコンテンツ本体と配信処理を分離したのと同様に、KVキャッシュ管理をLLM推論エンジンから独立させるKDNを提案する。

## 背景：なぜ「知識をどこに置くか」が推論システムの問題になるのか

### 微調整と文脈内学習は逆方向の長所を持つ

微調整では、知識コーパスを使ってモデルパラメータを更新する。推論時には知識文書を長い入力として渡さなくてもよいため、応答までの計算は小さい。一方、知識が更新されるたびに再学習が必要になり、複数の顧客・文書集合・権限制御に応じて「この要求ではこの知識だけ使う」という切り替えが難しい。

文脈内学習では、検索した文書をそのままプロンプトへ入れるため、知識追加はほぼ即時で、要求ごとに利用文書を自由に選べる。しかしLLMは受け取った長文を毎回プリフィルする。同じ社内規程や製品マニュアルを何度検索しても、注意計算とKV生成を要求ごとにやり直す。

KDNの問題設定は、この二つを単純な「精度の違い」ではなく、**モジュール性と推論効率の交換条件**として捉え直す点にある。

### KVキャッシュは「計算結果としての知識」

自己注意（self-attention）では、入力トークンから各層のキーと値を生成する。逐次デコードでは過去トークンのキー・値を再計算せずKVキャッシュとして保持するのが通常である。

知識文書が多数の要求で再利用されるなら、文書から得たKVを一要求の寿命だけで捨てる必要はない。KDNではこれをモデル外へ保存し、将来の要求へ配る。つまり、

1. テキストを保存する方式は「安い保存・高い再計算」、
2. モデル重みに埋め込む方式は「高い更新費・安い要求時処理」、
3. KVキャッシュ方式は「大きな保存データ・小さい再計算」

という異なる資源配分になる。

## KDNの設計

### 1. KVキャッシュ保存：知識をモデルから独立したオブジェクトにする

KDNの保存部は、知識テキストと対応するKVキャッシュを永続化する。LLMエンジン側からは、おおむね「このテキストのKVを保存する」「このテキストに対応するKVを取得する」という境界を持たせる。

この分離が重要なのは、KV管理の改善をvLLMなど各推論エンジンへ個別に実装しなくてよくなるためである。保存階層をGPU高帯域メモリ（High Bandwidth Memory; HBM）だけに閉じず、CPUメモリ、ローカルストレージ、遠隔ストレージまで広げられる。

ただしKVは元テキストより大きくなる場合があり、モデル・層数・KVヘッド数・精度に依存する。したがって保存容量だけを見れば、テキストを保存して毎回再計算する方が安い場合もある。KDNが有利なのは、知識の再利用頻度が高く、再計算費を十分に償却できるときである。

### 2. KVキャッシュ配送：圧縮して「再計算するより速く」GPUへ運ぶ

保存先をGPU外へ広げると、次の律速は転送になる。KDNは既存研究のKV圧縮・ストリーミングを配送層へ組み込む構想である。論文はCacheGenのような量子化・符号化、不要要素を削る方式などを部品として挙げる。

ここで成立条件は明快で、**保存KVの読み出し＋転送＋復元が、元テキストをLLMで再プリフィルするより安いこと**である。知識が短い、GPUが空いている、ストレージやネットワークが遅い、といった条件では利得は縮む。

またNVLink、遠隔直接メモリアクセス（Remote Direct Memory Access; RDMA）、PCI Express（PCIe）など複数の経路があるため、どのKVをどの階層へ複製するかはCDNのキャッシュ配置に近い問題になる。

### 3. KVキャッシュ合成：RAGの「複数文書」を接頭辞制約から解放する

単純な接頭辞キャッシュは、保存したテキストが新しい要求の先頭と完全一致するときには有効だが、RAGでは複数の検索文書を要求ごとに異なる順番・組み合わせで連結する。この場合、文書A単体で作ったKVを文書Bの後ろへそのまま置くと、Aを計算したときには存在しなかった前文脈との注意関係が欠ける。

KDNの合成部は、CacheBlendのような選択的再計算を使って、独立に保存した複数文書のKVを要求時に組み合わせる構想である。重要なのは「全プリフィルをゼロにする」ことではなく、**再計算が必要な部分だけを復元し、全文の再プリフィルより小さくする**ことである。

この機構がないとKDNは単純なprefix cacheの大規模版に留まり、RAGで最も欲しい「任意の検索文書集合を使う」柔軟性を失う。

### 4. 保存中のKVを編集する余地

KV管理を推論エンジンから分離すると、保存中の状態に対して圧縮だけでなく、注意の誘導などのオフライン処理を施す余地も生まれる。論文はこれを今後の設計空間として論じている。

ただし、ここはLMCacheの予備評価で確立された主要結果ではない。KDNは完成した単一アルゴリズムというより、**KVを共有資源にしたときに必要になる保存・配送・合成機構を一つのシステム境界として定義する提案**と読むのが正確である。

## 一要求の流れ

RAG要求を例にすると、処理は次のようになる。

1. 検索器が今回使う知識文書を選ぶ。
2. KDNが各文書に対応するKVキャッシュの有無と保存場所を調べる。
3. 再利用できるKVは保存層から取得し、必要なら圧縮状態から復元してGPUへ配送する。
4. 複数文書を連結する場合は、合成部が文脈依存部分を選択的に再計算する。
5. LLMエンジンは完成したKV状態とユーザー固有部分だけを処理して生成へ移る。
6. 未登録の知識は一度プリフィルし、そのKVを後続要求のためKDNへ保存する。

反復利用される知識ほど2〜4の配送費を一度のプリフィル再計算より小さくできるため、ヒット率がシステム価値を左右す。

## 評価

本論文はHotInfra 2024のワークショップ論文であり、KDN全体を成熟した配信基盤として網羅的にベンチマークしたものではない。LMCacheプロトタイプを用いた**予備的なRAG評価**で、三つの知識注入方式のモジュール性と効率を比較している。

### 主な評価条件

| 項目 | 条件 |
|---|---|
| 用途 | 検索拡張生成（Retrieval-Augmented Generation; RAG） |
| 知識庫 | 合計200万トークン |
| 1要求 | 8,000トークンの外部知識 + 2,000トークンの会話履歴 |
| モデル | Llama 3.1 70B |
| ハードウェア | NVIDIA A40 ×2 |
| 提案系 | KDNプロトタイプ LMCache を用いるKVキャッシュ学習 |
| 比較対象 | 微調整、文脈内学習 |
| モジュール性指標 | 新しい知識庫の導入時間 |
| 効率指標 | 1要求あたり推論コスト、最初の応答までの遅延 |

### 代表的な結果

| 方式 | 新知識導入時間 | 推論コスト/要求 | 応答遅延/要求 | 読み方 |
|---|---:|---:|---:|---|
| 微調整 | 10時間 | $0.0052 | 2.63秒 | 推論は軽いが知識更新が重い |
| 文脈内学習 | 0 | $0.0149 | 10.91秒 | 知識追加は即時だが毎回長文をプリフィル |
| KVキャッシュ学習 + KDN | 0.25時間 | $0.0059 | 2.97秒 | 更新の柔軟性と推論時再利用を両立 |

KDNは微調整に対して新知識導入時間を10時間から0.25時間へ短縮し、**40倍**高速だった。一方、文脈内学習に対しては推論コストを$0.0149から$0.0059へ減らし、約**2.5倍低コスト**、応答遅延を10.91秒から2.97秒へ減らし、約**3.7倍高速**だった。

ここで注意すべきなのは、KDNの$0.0059と2.97秒は微調整の$0.0052と2.63秒をわずかに上回る点である。KDNの主張は全項目で個別最良というより、**文脈内学習のモジュール性に近い状態で、微調整に近い要求時効率へ寄せること**にある。

## 既存方式との差

既存の接頭辞キャッシュは「同じ先頭入力をもう一度使う」ときの推論最適化であり、通常は推論エンジン内部のGPUメモリ管理として扱われる。KDNはその境界を広げ、KVをモデル外の永続知識として、複数エンジン・複数記憶階層の間で管理する。

CacheGenはKV配送を、CacheBlendは非接頭辞を含むKV合成を改善する技術であり、KDNはそれらを競合手法として置き換えるのではなく、**配送網の構成部品として束ねるアーキテクチャ**を提案する。このため、本論文の新規性は個別カーネルの高速化より「どの機能を推論エンジンから切り離すか」にある。

## 限界・成立条件

第一に、KVキャッシュはモデル依存である。同じ知識テキストでも、モデル、層構成、重み、KV形式が変われば保存KVをそのまま再利用できない。モデル更新時の無効化・版管理が必要になる。

第二に、KVは大きい。再利用頻度が低い文書まで無制限に保存すると、保存費と配送帯域が再計算費を上回る。人気度を予測した配置、複製、追い出し、圧縮率の選択がKDN側の新しいスケジューリング問題になる。

第三に、RAGで複数文書を任意に組み合わせるには、単純なKV連結では足りない。合成時の選択的再計算が増えれば、文脈内学習との差は小さくなる。

第四に、評価は200万トークンの知識庫、8K+2K入力、Llama 3.1 70B、2×A40という一つの予備設定である。大規模な同時要求、裾遅延、遠隔ストレージ、異なる再利用率、モデル更新を含むKDN全体の運用特性は、この論文だけでは確定していない。

## 実装上の含意

この論文を階層メモリ研究として読むと、「GPUに載らないKVをどこへ逃がすか」だけでなく、**いつ再計算するより配送した方が安いか**が中心になる。SSDや遠隔メモリを使う場合も、転送帯域だけでなく再利用確率、圧縮・復元時間、合成時の部分再計算を含めた損益分岐点を測る必要がある。

またKDNを推論エンジンから独立させる設計は、vLLMや他のサービング基盤が更新されてもKV階層を別に発展させやすい。一方で、高性能化にはエンジン内部のページ管理や分離プリフィル（disaggregated prefill）との密接な連携が必要になるため、API分離とデータパス統合の両立が実装上の難所になる。
