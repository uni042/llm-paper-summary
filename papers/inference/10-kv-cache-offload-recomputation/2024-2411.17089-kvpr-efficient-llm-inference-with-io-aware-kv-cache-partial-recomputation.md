# KVPR: Efficient LLM Inference with I/O-Aware KV Cache Partial Recomputation

> CPU上のKV cacheを全部GPUへ戻さず、一部はより小さい中間activationだけを送りGPUでK/Vを作り直し、残りのKV転送と同時に進めてPCIe待ちを減らす方式。

## 概要

KVPRは、KV cacheをCPU DRAMへoffloadしたときにPCIe転送がdecodeのbottleneckになる問題に対し、**KV cacheの一部を転送せずGPUで再計算する**研究である。

通常は過去tokenのKV cacheをCPUからGPUへ読み込んでattentionを計算する。KVPRでは過去tokenに対応する、K/Vを作る前の中間activationの一部を先にGPUへ送り、そのactivationからK/Vを再計算する。同時に、残りのKV cacheはCPUからGPUへ非同期転送する。

GPUは「KVを待ってidleになる」のではなく、**転送待ち時間をKV再計算に使う**。どこまで再計算し、どこから転送するかは固定せず、model・sequence length・batch size・GPU性能・PCIe帯域を事前測定して自動決定する。

近似attentionやKV削除ではなく、最終的なKVは再計算分と転送分を結合して通常どおりattentionを行うため、**計算結果を変えずに「運ぶ仕事」と「作り直す仕事」を交換するlosslessなsystem optimization**である。

## 問題設定

KV cache offloadはVRAMを節約できる一方、sequence lengthとbatch sizeが増えるほどCPU→GPU transferが大きくなる。

論文のA100 / PCIe 4.0 x16環境では、batch=32・sequence length=1024で、OPT-30Bの1 layer分のKV cache転送が約27.3 msなのに対し、対応するK/V projection再計算は約0.61 msであり、**KVを運ぶ方が計算し直すより1桁以上高い**条件が存在する。

ただし全部再計算するとGPU computeがbottleneckになる。したがってKVPRは、**転送と再計算がほぼ同時に終わる比率**を求める。

SSD / NVMeから直接KVを読む研究ではなく、主評価は**CPU DRAM ↔ GPU HBM間のPCIe I/O**である。

## 手法

### 1. Activationを先に送りKVの一部を再計算する

CPU側にはKV cacheだけでなく、そのKVを生成した入力activationを保持する。

各layerで、schedulerが再計算対象にした部分のactivationを先にGPUへ送り、K/V projectionをGPUで再実行する。activationは対応するK/Vの2つのcacheをまとめて送るより小さいため、同じtoken範囲をKVとして転送するよりPCIe trafficを減らせる。

残りのKV cacheは通常どおりCPUからGPUへ送り、最後に再計算分と結合してattentionを実行する。

### 2. 再計算とKV transferを並行させる

KVPRの核心は、単に「一部を再計算する」ことではなく、**GPUでK/Vを作り直す処理とPCIeで残りKVを運ぶ処理を同時進行させる**点にある。

再計算側が先に終わればGPUは残りKV待ちになり、転送側が先に終わればPCIe側の余力を使い切れない。そのため両者の時間が揃う比率を狙う。

### 3. 実測値から「何割を再計算するか」を自動決定する

profilerはmodel、batch size、sequence length、GPU performance、PCIe bandwidthなどを測定する。

schedulerはその情報から、再計算するKV量と転送するKV量を**制約条件の下で総時間が小さくなる組合せを解く最適化**で決める。論文のlinear programmingはこの割合決定に使われる。

latency重視ではtoken方向に少量ずつ進めるschedule、throughput重視では複数request/layerの転送と計算をまとめて重ねるscheduleを使い分ける。runtimeはactivation / KV cacheのmemory管理とCUDA streamによる非同期転送・計算を実行する。

### 4. Weight loadingともpipeline化する

weightもCPUへoffloadするthroughput-oriented構成では、KV再計算だけを単独で行うとweight transferが次のbottleneckになる。

KVPRはKV recomputationと次に必要なweight loadingも重ね、small batchでKVが小さい場合にも余計な再計算costが本来の実行時間へ出にくいようにする。

### 5. KV quantizationとも併用できる

論文では、複数要素をまとめた単位ごとにscaleを持たせるgroup-wise 4-bit KV cache compressionも評価している。KVを圧縮すればtransfer量そのものが減るが、KVPRはその上で残ったI/Oとrecomputationを重ねられるため、両者は競合する手法ではなく併用可能である。

量子化を併用すると最適な再計算比率も変わる。KVを4 bitへ圧縮すればCPU→GPUで運ぶbyteが減るため、full-precision KVを前提にしたときより転送側が早く終わり、再計算へ回す割合を小さくした方がよい場合がある。一方で転送したKVにはdequantizationの費用も加わるため、profilerは圧縮後の実測転送時間と復号費用を含めて再び分担を決める必要がある。つまりKV量子化はI/Oそのものを小さくするつまみ、KVPRは残ったI/OをGPU計算へ置き換えて同時進行させるつまみであり、両方を使う場合もhardwareごとにbalance pointを測ることが重要になる。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA A100 40GB |
| CPU | AMD EPYC 64 cores, 2.6GHz |
| CPU-GPU | PCIe 4.0 x16、32GB/s |
| Model | OPT-6.7B / 13B / 30B、追加評価でLlama2-7B / 13B |
| Latency baseline | DeepSpeed Inference、Hugging Face Accelerate |
| Throughput baseline | FlexGen |
| 実装 | Transformers 4.46.1 + FlexGenベース |

### 主要結果

latency-oriented評価では、OPT-6.7BでHugging Face Accelerate比**最大35.8% latency削減**を報告した。

throughput-oriented評価ではFlexGen比で、

- OPT-6.7B: 最大15.1%
- OPT-13B: 最大46.2%
- OPT-30B: 最大29.0%

のdecode throughput改善を報告している。

また代表構成ではdecode時の平均GPU utilizationがFlexGenの85%からKVPRの99%へ上がった。MHA runtime breakdownではKV transferの割合が58%から38%へ低下し、代わりにGPU computeが2.3%から13.3%へ増えており、**I/O待ちを意図的に余っていたGPU計算へ置換している**ことが分かる。

8×A100 + 1 CPUの追加評価ではFastDecodeとも比較し、CPU attentionへ依存する方式と異なりGPUごとのrecomputationを使うため、複数GPUが1 CPUを共有する場合のCPU compute bottleneckを避ける方向も示している。

## 既存研究との差

### FlexGenとの違い

FlexGenはKV / weight transferを別のGPU計算と重ねるが、KVが大きくなるとPCIe transfer自体が長すぎて隠し切れない。

KVPRは**transferする仕事そのものを減らし、その分をGPU recomputationへ変換する**ため、PCIe時間とGPU時間の比率を能動的に調整できる。

### FastDecode / NEOとの違い

FastDecodeやNEOはKVがあるCPU側へattention計算を寄せる。これによりKV transferは減るが、CPU memory bandwidth / computeへ依存し、複数GPUでCPUを共有するとCPU側がbottleneckになりやすい。

KVPRはattention自体はGPUで行い、KVの一部だけGPUで再生成するため、CPU computeへの依存を小さくする。

### TwinPilots / HeteGenとの違い

TwinPilotsやHeteGenはCPUとGPU間でoperation / linear計算を分担する。KVPRはCPUを計算主体として使うのではなく、**GPU computeとPCIe I/Oのtrade-offをKV単位で調整する**。

### ALISAとの違い

ALISAにも一部KVを再計算して残りを転送する考え方があるが、KVPRはrecomputationとtransferを非同期に重ね、hardware profileから最適な分担を決める。またthroughput-orientedなscheduleまで対象を広げている。

## 限界

- activationを保持するため、KV cacheだけを保存する方式よりCPU memory消費が増える。
- 効果はGPU computeとPCIe bandwidthの比率に依存し、I/Oが十分速い環境では再計算の利得が小さくなる。
- 主評価はA100 + PCIe 4.0であり、NVLink-C2Cやより高速なhost-device interconnectでは最適splitが変わる。
- recomputationはdecodeだけを対象とし、prefill性能は改善しない。
- model architectureやquantizationによってK/V projection costが変わるため、profileなしの固定ratioでは性能を保証しにくい。

## 一般的な実装上の含意

KVPRは、cacheを「保存するか捨てるか」だけで考えず、**I/O costがrecompute costより高ければ部分的に計算し直す**という選択肢をruntimeに持たせる価値を示す。

特にGPUが高速化する一方でPCIe bandwidthの伸びが相対的に小さい環境では、古い中間結果を運ぶより、より小さいupstream activationを運んでGPUで再生成する方が合理的になる領域が広がる。
