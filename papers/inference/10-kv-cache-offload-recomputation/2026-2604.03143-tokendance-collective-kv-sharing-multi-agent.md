# TokenDance: Scaling Multi-Agent LLM Serving via Collective KV Cache Sharing

> 全収集型マルチエージェントの共有文脈をラウンド単位で一括再利用し、兄弟KVキャッシュを1本のマスターと疎な差分だけで保存する。A100実機で同時エージェント数をvLLM比最大2.7倍、KV保存量を最大17.5倍圧縮する。
## 書誌情報
- **著者**: Zhuohang Bian, Feiyang Wu, Chengrui Zhang, Hangcheng Dong, Yun Liang, Youwei Zhuo
- **著者・所属**: Peking University、Shanghai Jiao Tong University。
- **公開**: arXiv:2604.03143v1
- **種別**: プレプリント
- **対象**: マルチエージェントサービング、KVキャッシュ共有、集合的再利用、差分保存、融合復元
- **実装**: LMCacheとvLLM V1上に試作され、約3,000行のPythonと約500行のCUDA/C++を追加して、ラウンド対応セグメント索引、集合的KV再利用、差分対応保存、疎差分融合復元を実装する。論文本文から著者公式の公開コードURLは確認できなかった。
## 概要
TokenDanceは、同期ラウンドで全エージェントの出力を集めて再配布する全収集（All-Gather）型のマルチエージェント処理に着目し、各要求がほぼ同じ共有文脈を持つのにKVキャッシュを個別計算・個別保存している無駄を削減するサービング方式である。ラウンド構造を実行基盤まで保持し、共有ブロックの位置補正と重要位置選択を要求ごとではなくラウンド単位で一度だけ行う。さらに1本の完全なマスターKVキャッシュと、各エージェント固有部分だけのブロック疎差分からなるミラー表現へ変換し、復元をGPU転送経路へ融合する。GenerativeAgentsとAgentSociety、Qwen2.5-7B/14B、A100実機の評価では、vLLMの接頭辞キャッシュ比で同じ遅延目標下の同時エージェント数を最大2.7倍へ増やし、エージェント当たりKV保存量を最大17.5倍圧縮し、要求単位の位置非依存キャッシュ方式に対して事前充填を最大1.9倍高速化した。

TokenDanceは、最適化単位を1要求から全収集ラウンドへ引き上げる。アプリケーションが論理ブロック境界を予約区切りトークンで明示し、同一ラウンドの互換要求をKV Collectorがまとめることで、共有ブロックに対するRoPE回転と差分解析を一度だけ実行する。さらに集合的再利用結果から最も共通構造に近い1要求をマスターとして選び、他の兄弟キャッシュはマスターとの差がある32トークン単位ブロックだけをミラー差分として保存する。読み出し時は完全なミラーを再構築せず、既存の層単位GPU転送中に差分を融合適用するため、保存量削減を実行時の追加メモリ往復で相殺しない。

代表結果として、同一SLO下の同時エージェント容量はGenerativeAgents/AgentSociety、Qwen2.5-7B/14B、A100-80GB、ラウンド遅延SLO 1,500ms。でvLLM with prefix キャッシュに対してvLLM比最大2.7倍。共有計算とKV保存重複を同時に減らすことで、固定GPUメモリで活動状態に保てるエージェント数が増える。
## 問題設定
マルチエージェントLLMでは、各エージェントが私有履歴を保持しつつ、各ラウンドで全エージェントの出力を中央スケジューラが集約し、次ラウンドの全員へ共有する全収集（All-Gather）型の通信が頻出する。この構造では全員が同じ共有出力ブロックを持つが、私有履歴長やブロック順序が異なるため共有部分の絶対位置がずれる。接頭辞キャッシュは先頭一致しか扱えず、CacheBlendなどの位置非依存キャッシュは任意位置を再利用できるものの、各要求を独立に処理して同じRoPE位置補正や重要位置選択をエージェント数だけ繰り返す。さらに再利用後のKVキャッシュは91〜97%のブロックが互いに同じであるにもかかわらず、各エージェントが完全な密KVコピーを保持する。A100-80GB上のQwen2.5-14Bでは、同じ250サブ要求でもマルチエージェント負荷が41.5GiB、独立要求が24.8GiBのKVを消費し、前者はキャッシュ領域の99.3%へ達する。従来のエージェント対応スケジューラは実行順を改善しても、このラウンド横断の計算重複と保存重複を除去できない。
## 新規性
TokenDanceは、最適化単位を1要求から全収集ラウンドへ引き上げる。アプリケーションが論理ブロック境界を予約区切りトークンで明示し、同一ラウンドの互換要求をKV Collectorがまとめることで、共有ブロックに対するRoPE回転と差分解析を一度だけ実行する。さらに集合的再利用結果から最も共通構造に近い1要求をマスターとして選び、他の兄弟キャッシュはマスターとの差がある32トークン単位ブロックだけをミラー差分として保存する。読み出し時は完全なミラーを再構築せず、既存の層単位GPU転送中に差分を融合適用するため、保存量削減を実行時の追加メモリ往復で相殺しない。
## 手法
### 手法のあらまし
まずアプリケーションは、私有履歴、各エージェントの前ラウンド出力、ラウンド課題などの論理ブロック間へ予約区切りトークンを挿入する。実行基盤は固定長チャンクのハッシュ索引ではなく区切り境界で分割したセグメント索引を使い、同じ内容の共有出力を絶対位置が違っても同一オブジェクトとして認識する。次にvLLM V1アダプタが各スケジューラ段階で同一ラウンドの要求を収集し、実行長、可視キャッシュ区間、スロット対応が互換な要求を1群へまとめる。KV Collectorは群内要求を層ごとに同期して進め、共有部分のRoPE回転とキー差分解析、重要位置選択を群全体で一度だけ行い、各要求では私有履歴など実際に異なる位置だけ再計算する。ここで各要求の共有構造からの累積偏差を計測し、偏差が最小の要求をマスターへ選ぶ。この再利用計画は保存層へ引き継がれ、マスターは完全な密KVとして保存し、残りのミラーはマスターと異なるブロック索引とK/V補正値だけを保持する。読み出しではLMCacheの層単位転送経路へミラー情報を渡し、2つの一時バッファを交互に使ってマスターチャンクを読みながら、差分があるブロックだけCUDAカーネルでその場補正し、位置を復元してページ化KV領域へ書き込む。したがって完全なミラー用テンソルを生成する追加の密コピーが不要になる。ラウンド構造を認識できない要求や互換条件を満たさない群は通常の単一要求経路へ安全に戻る。

### ラウンド対応プロンプト界面と集合的KV再利用
予約区切りトークンでアプリケーションの論理ブロック境界をトークン化後まで保存し、セグメント単位のハッシュ索引へ置き換える。同一内容の共有ブロックは、各エージェントの私有履歴長や並び順が違って絶対位置がずれても同一候補として認識できる。互換要求群では、位置非依存キャッシュに必要なRoPE回転、キー差分、重要位置選択を要求ごとに繰り返さず1回へ集約し、最後の要求固有位置更新だけを個別に行う。現在の試作はCacheBlendの選択的再計算を基盤にするが、位置集合を受け取り補正済みK/Vを返せる別の位置非依存方式へ差し替えられる設計である。これによりエージェント数に比例して増えていた再利用解析費をラウンド内で償却する。

### マスター・ミラー型の差分対応保存
集合的再利用時に得た偏差情報から、共通構造に最も近い要求を1本のマスターとして完全保存する。他要求はミラーとし、マスターと値が異なる位置を32トークン単位のブロックへまとめ、変更ブロック索引とK/V補正値だけを保持する。GenerativeAgentsでは完全キャッシュが通常500〜700ブロックあるのに、ミラー当たりの変更はQwen2.5-7Bで平均53.2ブロック、14Bで59.6ブロックに留まるため、密コピーを大量に保持する必要がない。明示的な再利用計画がない場合はトークン類似度からマスター候補を選び、一般要求でも既存保存基盤として動作できる。

### 層転送へ融合した疎差分復元
単純な復元ではマスター全体を一度別バッファへ複写し、差分位置を書き換えた後に再びページ化KVへ転送するため、圧縮したはずのデータで追加の密な書込み・読出しが発生する。TokenDanceはLMCacheの既存層転送に差分適用を融合し、マスターチャンクをピンポンバッファへ読み込む最中に、当該層で差分を持つブロックだけK/V補正カーネルで更新してそのままページ化KVへ送る。差分のないブロックは補正を飛ばし、密なミラーを一度も実体化しない。現在は注意タイル読込みそのものではなく注意実行前の転送経路へ融合しており、さらに深い融合は将来拡張として残る。

### 全体のデータ／制御の流れ
LMCacheを外部KV保存層、vLLM V1を要求スケジューリング・実行層として利用し、その間にラウンド認識、KV Collector、差分保存バックエンド、GPU復元コネクタを追加する。アプリケーションには区切りトークン挿入という最小限の変更を要求するが、全収集構造を持たない負荷は通常経路へ戻す。約3千行のPythonと500行のCUDA/C++の試作で、通信構造を第一級のサービング情報として扱う。
## 評価条件
- **ハードウェア**: NVIDIA A100-80GB GPU。単一GPU上でローカルサービング容量を比較する。
- **ソフトウェア**: vLLM V1とLMCacheを基盤とし、位置非依存キャッシュの比較・基盤方式としてCacheBlendを利用する。TokenDanceは約3,000行のPythonと500行のCUDA/C++を追加する。
- **データセット／トレース**: GenerativeAgents multi-agent トレース、AgentSociety multi-agent トレース
- **比較対象**: vLLM + prefix キャッシュ、CacheBlend Ordinary Path、CacheBlend per-リクエスト PIC recovery
GenerativeAgentsとAgentSocietyの同期ラウンドトレースを再生し、エージェント数を1〜10、投入率を1〜16 QPSで走査する。ラウンド遅延1,500msのサービス水準目標（SLO）を満たす最大エージェント数、KVキャッシュ占有量、復元遅延を主要指標とする。計算要因はGenerativeAgentsの1ラウンドを3、5、10、15、20エージェントおよび1〜16 QPSで再生し、要求単位の位置非依存再利用に対する集合的再利用の速度向上を測る。保存要因は32トークンブロック単位でマスターとの差分量を計測し、密復元と融合差分復元を比較する。品質は温度0の同一入力でvLLMとの応答分岐が初めて起きるラウンドを8シナリオで比較する。
実機GPU評価でありシミュレーション性能モデルではない。対象は全収集型の同期ラウンドを持つ社会シミュレーション系ワークロードと2種類のQwen2.5モデルであり、異なる通信パターンや大規模複数GPU構成への一般化は直接測定していない。
## 主要結果
TokenDanceは、エージェント数が少ない1〜2件では共有できる重複が小さいため既存方式との差が小さいが、同時エージェント数とモデルサイズが増えるほど集合的再利用と差分保存の効果が大きくなる。計算面では同じ共有ブロックに対する位置補正・重要位置解析をラウンドで一度へ集約し、保存面では兄弟キャッシュの大半を1本のマスターへ畳み込む。この2つが同時に効くことで、単に1ラウンドを高速化するだけでなく、固定80GBのGPUへ常駐できるエージェント数そのものを増やす。融合復元も密な再構築より高速で、圧縮の利得をオンライン実行で維持する。

- 同一SLO下の同時エージェント容量 / vLLM比最大2.7倍 (比較対象: vLLM with prefix キャッシュ; 条件: GenerativeAgents/AgentSociety、Qwen2.5-7B/14B、A100-80GB、ラウンド遅延SLO 1,500ms。) — 共有計算とKV保存重複を同時に減らすことで、固定GPUメモリで活動状態に保てるエージェント数が増える。

- 位置非依存キャッシュに対する事前充填速度 / 最大1.9倍 (比較対象: per-リクエスト position-independent キャッシュ; 条件: 代表的な全収集型マルチエージェントラウンド。) — 同じ共有ブロックのRoPE回転と重要位置選択を各要求で繰り返さずラウンド単位へ償却する。

- 集合的再利用の局所速度向上 / 最大2.57倍 (比較対象: serial per-リクエスト PIC recovery; 条件: GenerativeAgents、エージェント数3〜20、QPS 1〜16。ピークは10エージェント条件。) — 要求単位ではエージェント数に比例する再利用解析が、共有処理により亜線形へ変わる。ただし15〜20エージェントではスケジューリング負荷が増え、追加利得が一部相殺される。

- マスター・ミラーKV圧縮率 / 7Bで11.2倍、14Bで17.5倍 (比較対象: one dense KV キャッシュ per agent; 条件: GenerativeAgents、32トークン単位ブロック。ミラー変更ブロックは平均53.2個と59.6個。) — 完全キャッシュ500〜700ブロックの大半が兄弟要求間で同一なため、モデルが大きいほど差分保存の絶対利得が増える。

- 融合差分復元速度 / 密復元比およそ1.4〜2.6倍 (比較対象: dense Mirror materialization; 条件: GenerativeAgents/Qwen2.5-7B、1〜10エージェント、QPS 1〜8。) — 完全ミラーの一時実体化を避け、既存GPU転送中に差分だけ補正することで追加メモリ往復を削減する。

### 負の結果・境界条件
- 1〜2エージェントでは横断共有の余地が小さく、各方式の性能差は小さい。集合的再利用も10エージェントを超えると群管理・スケジューリングの費用が増え、15〜20エージェントでは単純に群を大きくするほど速度向上が伸び続けない。また現在の差分融合は注意カーネル内部のタイル読込みまでは融合されておらず、差分メタデータが整列しない場合は密復元へ戻る。品質面ではvLLMと完全一致しないシナリオが5/8あるが、これは基盤のCacheBlend選択的再計算が持つ近似差であり、TokenDance固有の追加誤差ではない。

### 結果の読み方
利得の源泉はマルチエージェントで共通する全収集通信構造であり、一般の独立要求を速くする仕組みではない。共有率、エージェント数、1要求当たりKV量が増えるほど、ラウンド単位で計算をまとめ差分だけ保存する価値が高まる。反対に共通構造が薄い負荷では通常経路へ戻す設計が重要になる。
## 品質への影響
TokenDanceの集合的実行とマスター・ミラー表現は、同じCacheBlend位置非依存再利用を要求単位で行った場合と同一の復元KVを生成するため、TokenDance部分は追加近似を導入しない。vLLMとの出力差はCacheBlendの選択的再計算に由来し、論文では8シナリオ中3件が全トレース一致、残り5件の差もその基盤方式へ帰属すると確認する。
## 既存研究との差
vLLM/SGLangの接頭辞キャッシュは要求先頭からの一致を再利用するため、私有履歴長が異なる兄弟エージェントの共有出力を認識しにくい。CacheBlend、EPIC、KVLink、KVCommなど位置非依存方式は任意位置を扱えるが、基本単位は1要求であり、同じ共有ブロックの位置補正・差分解析をエージェントごとに繰り返す。MooncakeやCacheGenなどは個々のKVを圧縮・移動し、Tokencakeなどのエージェント対応スケジューラは実行順・退避を最適化するが、兄弟キャッシュ間の90%以上の重複を1本へ統合しない。TokenDanceは通信ラウンドを第一級単位として、計算共有とキャッシュ間差分圧縮を一体化する点が異なる。
## 限界
前提となる強い共有構造は、中央スケジューラが各ラウンドの全エージェント出力を全員へ再配布する全収集型アプリケーションである。非同期エージェントや部分的な通信グラフでは同じ共有率を期待できない。評価は単一A100-80GB、Qwen2.5-7B/14B、GenerativeAgentsとAgentSocietyへ集中しており、複数GPU・異種GPU・本番の混合負荷は未評価である。アプリケーションが論理ブロック境界へ予約トークンを挿入する必要があり、現在の融合復元は注意カーネル内部ではなく転送経路止まりである。基盤にCacheBlendを用いるため、その選択的再計算の数値近似は継承する。著者公式の公開実装URLも本文から確認できない。

## 研究上の位置づけ
KVキャッシュ最適化のうち、単一要求内の量子化・枝刈り・CPU/SSD退避ではなく、同一ラウンドに属する複数要求間の冗長性を除く系統に位置する。位置非依存キャッシュを下位機構として利用しながら、その処理単位を要求から集合へ拡張するため、既存の単一キャッシュ圧縮や階層オフロードとも直交的に組み合わせられる。マルチエージェントの通信構造をサービング基盤へ露出させるという設計方向を明示した点が、今後のエージェント特化推論基盤にとって重要である。
