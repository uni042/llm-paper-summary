# KVDrive: A Holistic Multi-Tier KV Cache Management System for Long-Context LLM Inference

## 一文要約

GPU HBM・CPU DRAM・NVMe SSDの3階層へKV cacheを置き、**直近のattentionで再利用されそうなKVだけをGPUへ残すこと、必要KVの選択・転送・GPU計算を小さなbatch単位で並行実行すること、SSDから必要blockだけを疎に読むこと**を組み合わせ、長contextでKV全体を毎回転送するI/O待ちを減らす。

## 書誌情報

- **著者:** Jian Lin, Jiazhi Mi, Zicong Hong, Haodong Wang, Qianli Liu, Haoyue Zhang, Peng Li, Song Guo
- **公開:** arXiv preprint, 2026-05-18
- **arXiv:** 2605.18071
- **分野:** cs.CL

## 概要 / 問題設定

長contextのdecodeではKV cacheがGPU HBMに収まらないため、CPU DRAMへ退避し、attentionに必要なKVだけをGPUへ戻す方式が使われる。しかしcontextやbatchが大きくなると、必要KVを探す処理とhost→GPU転送がdecode時間の大きな割合を占める。またCPU DRAM自体も容量上限があるためSSDまで使う必要があるが、KV全体をlayer単位でSSDから読むとGPUがI/O待ちになる。

KVDriveはこの問題を、単にattentionをさらに疎にするのではなく、**GPU内cache、decode pipeline、HBM/DRAM/SSD間のdata movementを一体で管理するsystem問題**として扱う。

## 手法

### 1. attentionに基づくGPU内cache管理

各decode stepで重要と判定されたKVには、近い将来のtokenでも再び重要になりやすい時間的局所性がある。KVDriveは最近数stepで重要だったKVを**sliding window（直近数step分の重要KVを保持し、stepが進むたび差分だけ入れ替える窓）**としてGPUへ残す。

退避時には単純なLRU/LFUではなく、現在のattention scoreが低く次stepでも使われにくいKVを先に外す。さらにlayer・attention headごとに再利用性が異なるため、offline profilingで「追加GPU memoryに対してhost→GPU転送をどれだけ減らせるか」を測り、window容量をlayer/head別に配分する。これにより同じGPU cache budgetでも転送削減効果の大きい場所へmemoryを重点配分する。

### 2. 必要KVの選択・転送・計算を重ねるelastic pipeline

通常のoffload方式では、(1) attentionに必要なKVをindexから選ぶ、(2) DRAM/SSDからGPUへfetchする、(3) attention/FFNを計算する、という処理を順番に行うため、fetch中にGPUが待つ。

KVDriveはdecode batchをmicro-batchへ分け、この3段階を独立stageとして動かす。あるmicro-batchをGPUで計算している間に、別micro-batchでは必要KVの選択や転送を進めることで、CPU処理・I/O・GPU計算を重ねる。index size、GPU cache size、micro-batch sizeは、検索cost・転送量・GPU memory・accuracyのtrade-offを見ながら調整する。

### 3. HBM / DRAM / SSDの協調管理

CPU DRAMだけで足りないKVはNVMe SSDへ置く。ただしFlexGen型のようにlayer全体をSSDから読むのではなく、queryで必要になったKV blockだけを疎にfetchする。

prefill時には後で重要になりやすいKVを優先して高速tierへwarm-upし、SSD上では連続して読みやすいlayoutを作る。複数tier間の同期も必要blockだけを並行して行い、SSDの大容量を使いながら転送量を抑える。

### 4. 軽量な検索index

KVをchunk化し、各pageの代表keyと上位centroidからなる階層indexをGPUに置く。全keyをそのままindexにする方式よりGPU memoryを減らしつつ、queryに関連するKV blockを絞り込む。論文では比較するspatial chunking系indexと同等のretrieval precisionを保ちながらindex footprintを50%削減し、lookupを最大2倍高速化したと報告している。

## 評価条件

実機prototypeを以下の3環境で評価している。

- NVIDIA L20 48 GB + Intel Xeon Platinum 8457C + DDR5 100 GB + NVMe U.2 SSD
- NVIDIA H20 96 GB + AMD EPYC 9K84 + DDR5 200 GB + NVMe U.2 SSD
- NVIDIA RTX 4090 24 GB + Intel Xeon Gold 6430 + DDR5 120 GB + NVMe U.2 SSD

主なmodelはLlama-3-8B-1048K、Qwen-3-8B、Phi-4-Mini-128K。RULERとLongBenchで品質も確認し、Quest、ShadowKV、PQCache、MagicPIG、RetroInfer、FlexGenなどと比較している。

## 主要結果

- L20環境では最も強い比較対象のShadowKVに対し、generation throughputを**最大約70%改善**した。
- H20とRTX 4090でも、各環境の最良baselineに対し**1.23–1.53倍**のthroughputを報告している。論文全体では最大**1.74倍**の改善を報告する。
- 6.25%のsparsity budgetで、重要KVを毎step捨てる場合から直近3step相当を保持するwindowへ広げると、step当たりhost→GPU転送量が500 MB超から12.5 MB未満まで低下した例を示す。
- SSDを含むDRAM+SSD構成ではDRAM-only構成よりthroughputは約40%低下するが、DRAM容量を超える大きなbatch/contextを実行できる。FlexGen型の全layer fetchより、必要blockだけを読む方式が大幅に高速だった。
- RULER / LongBenchでは、比較したsparse-attention offload方式と概ね同程度の品質を維持した。

## 既存研究との差

Quest、ShadowKV、RetroInfer、PQCacheなどは、主に「どのKVが重要かを小さいindexで推定し、CPU DRAMから必要KVだけを読む」部分を改善する。KVDriveはそこに加えて、**一度GPUへ読んだ重要KVを複数step再利用するcache管理、selection/fetch/computeのpipeline化、SSDまで含む3階層配置**を同時に設計する。

FlexGenのようなstorage offloadは大容量を扱える一方、layer単位の粗いtransferではsparse attentionが実際には使わないKVまで読み込む。KVDriveはattentionで選ばれたblockだけをSSDから同期することでI/O amplificationを抑える。

TuttiやSwarmとは焦点も異なる。TuttiはGPU自身がSSD I/Oを発行してCPU control overheadを減らし、Swarmは複数SSDへKVを配置してaggregate bandwidthを高める。一方KVDriveは**SSDから読むdata量そのものをattention sparsityとGPU cache reuseで減らし、DRAM/SSD fetchをGPU計算と重ねる**ことが中心であるため、storage I/O pathを高速化する研究とは補完関係にある。

## 限界

- 性能はattention sparsityと重要KVの時間的局所性に依存する。attention patternが大きく変わるmodel/workloadではGPU内windowの再利用効果が小さくなり得る。
- layer/head別window、centroid数、chunk size、micro-batch sizeにはtrade-offがあり、論文でもworkload/context/batchによって最適値が変わる。
- SSDを追加してもDRAM-onlyと同じ速度にはならず、評価ではDRAM+SSD構成に約40%のthroughput低下が残る。
- 評価はtext LLMが中心で、multimodal modelへの適用はfuture workとされている。
- arXiv v1時点では、論文prototypeを再現できる公式code repositoryをarXivページから確認できない。

## 一般的な実装上の含意

長contextのKV offloadでは「低速tierからKVを速く読む」だけでなく、**そもそも何byte読むか、読んだKVを何step再利用するか、I/O待ちをどのGPU計算の裏へ隠すか**を同時に決める必要がある。SSD tierを実用化する場合、storage bandwidthの改善だけでなく、attention側のsparse accessをstorage block layoutと揃えて不要I/Oを避ける設計が重要になる。

またGPU memoryの残量を単なるfree spaceとして扱うより、再利用性の高いKVを残すcacheへ使えばPCIe/NVMe transferを減らせる。これはGPU HBM・CPU DRAM・SSDを独立tierとして最適化するより、end-to-end decode pipeline全体で配置とscheduleを決める方が有利になり得ることを示す。

## 引用関係

KVDriveはQuest、ShadowKV、InfiniGen、MagicPIG、PQCache、RetroInferなどのactive-session KV offload / sparse attention系を比較対象とし、FlexGenをstorageまで含むcoarse-grained offloadの比較対象としている。TuttiやSwarmと同じくSSD tierを扱うが、KVDriveはattention-awareなdata削減とmulti-tier schedulingを主題とする。
