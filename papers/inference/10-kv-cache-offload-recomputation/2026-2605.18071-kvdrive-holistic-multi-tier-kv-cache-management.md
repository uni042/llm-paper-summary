# KVDrive: A Holistic Multi-Tier KV Cache Management System for Long-Context LLM Inference

> KVDriveはHBM・DRAM・NVMeの三層でKVを管理し、再利用度に応じた選択・転送・注意計算を小バッチで重ね、SSDから必要ブロックだけを読み長文I/Oを減らす方式。

## 一文要約

GPU HBM・CPU DRAM・NVMe SSDの3階層へKV キャッシュを置き、**直近の注意機構で再利用されそうなKVだけをGPUへ残すこと、必要KVの選択・転送・GPU計算を小さなバッチ単位で並行実行すること、SSDから必要ブロックだけを疎に読むこと**を組み合わせ、長文脈でKV全体を毎回転送するI/O待ちを減らす。

- **著者:** Jian Lin, Jiazhi Mi, Zicong Hong, Haodong Wang, Qianli Liu, Haoyue Zhang, Peng Li, Song Guo
- **公開:** arXiv preprint, 2026-05-18
- **arXiv:** 2605.18071
- **分野:** cs.CL

## 概要 / 問題設定

L20/H20/RTX 4090実機でLlama-3-8Bなどを比較し、L20ではShadowKV比最大約70%、H20/RTX 4090では各最良比較対象比1.23〜1.53倍（全体最大1.74倍）の生成スループットを示した。6.25%疎性予算では段階当たりホスト→GPU転送を500MB超から12.5MB未満へ下げた。

長文脈のデコードではKV キャッシュがGPU HBMに収まらないため、CPU DRAMへ退避し、注意機構に必要なKVだけをGPUへ戻す方式が使われる。しかし文脈やバッチが大きくなると、必要KVを探す処理とホスト→GPU転送がデコード時間の大きな割合を占める。またCPU DRAM自体も容量上限があるためSSDまで使う必要があるが、KV全体を層単位でSSDから読むとGPUがI/O待ちになる。

KVDriveはこの問題を、単に注意機構をさらに疎にするのではなく、**GPU内キャッシュ、デコード パイプライン、HBM/DRAM/SSD間のデータ 移動を一体で管理するシステム問題**として扱う。

## 手法

### 1. attentionに基づくGPU内cache管理

各デコード 段階で重要と判定されたKVには、近い将来のトークンでも再び重要になりやすい時間的局所性がある。KVDriveは最近数段階で重要だったKVを**sliding window（直近数段階分の重要KVを保持し、段階が進むたび差分だけ入れ替える窓）**としてGPUへ残す。

退避時には単純なLRU/LFUではなく、現在の注意機構 点数が低く次段階でも使われにくいKVを先に外す。さらに層・注意機構 ヘッドごとに再利用性が異なるため、オフライン プロファイリングで「追加GPU メモリに対してホスト→GPU転送をどれだけ減らせるか」を測り、window容量を層/ヘッド別に配分する。これにより同じGPU キャッシュ 予算でも転送削減効果の大きい場所へメモリを重点配分する。

### 2. 必要KVの選択・転送・計算を重ねるelastic pipeline

通常のオフロード方式では、(1) 注意機構に必要なKVを索引から選ぶ、(2) DRAM/SSDからGPUへ取得する、(3) 注意機構/FFNを計算する、という処理を順番に行うため、取得中にGPUが待つ。

KVDriveはデコード バッチをmicro-バッチへ分け、この3段階を独立段階として動かす。あるmicro-バッチをGPUで計算している間に、別micro-バッチでは必要KVの選択や転送を進めることで、CPU処理・I/O・GPU計算を重ねる。索引 大きさ、GPU キャッシュ 大きさ、micro-バッチ 大きさは、検索費用・転送量・GPU メモリ・精度のトレードオフを見ながら調整する。

### 3. HBM / DRAM / SSDの協調管理

CPU DRAMだけで足りないKVはNVMe SSDへ置く。ただしFlexGen型のように層全体をSSDから読むのではなく、問い合わせで必要になったKV ブロックだけを疎に取得する。

プリフィル時には後で重要になりやすいKVを優先して高速階層へウォームアップし、SSD上では連続して読みやすい配置を作る。複数階層間の同期も必要ブロックだけを並行して行い、SSDの大容量を使いながら転送量を抑える。

### 4. 軽量な検索index

KVを塊化し、各ページの代表鍵と上位中心点からなる階層索引をGPUに置く。全鍵をそのまま索引にする方式よりGPU メモリを減らしつつ、問い合わせに関連するKV ブロックを絞り込む。論文では比較する空間的 chunking系索引と同等の検索 精度を保ちながら索引 占有量を50%削減し、lookupを最大2倍高速化したと報告している。

この索引はKV本体を置き換える圧縮ではなく、低速階層から何を取得するかを決めるメタデータである。索引自体が大きすぎるとKVを節約して空けたHBMを検索構造が消費し、lookupが遅ければI/O開始も遅れる。ページ代表と中心点の二段階にすることで、まず粗く候補 ページを絞り、詳細KVは必要ページだけDRAM/SSDから読む。したがって索引 占有量・選択 遅延・検索 再現率の3者を同時に抑えることがパイプライン成立の条件になる。

## 評価条件

実機prototypeを以下の3環境で評価している。

- NVIDIA L20 48 GB + Intel Xeon Platinum 8457C + DDR5 100 GB + NVMe U.2 SSD
- NVIDIA H20 96 GB + AMD EPYC 9K84 + DDR5 200 GB + NVMe U.2 SSD
- NVIDIA RTX 4090 24 GB + Intel Xeon Gold 6430 + DDR5 120 GB + NVMe U.2 SSD

主なモデルはLlama-3-8B-1048K、Qwen-3-8B、Phi-4-Mini-128K。RULERとLongBenchで品質も確認し、Quest、ShadowKV、PQCache、MagicPIG、RetroInfer、FlexGenなどと比較している。

## 主要結果

- L20環境では最も強い比較対象のShadowKVに対し、生成 スループットを**最大約70%改善**した。
- H20とRTX 4090でも、各環境の最良比較対象に対し**1.23–1.53倍**のスループットを報告している。論文全体では最大**1.74倍**の改善を報告する。
- 6.25%のsparsity 予算で、重要KVを毎段階捨てる場合から直近3step相当を保持するwindowへ広げると、段階当たりホスト→GPU転送量が500 MB超から12.5 MB未満まで低下した例を示す。
- SSDを含むDRAM+SSD構成ではDRAM-だけ構成よりスループットは約40%低下するが、DRAM容量を超える大きなバッチ/文脈を実行できる。FlexGen型の全層 取得より、必要ブロックだけを読む方式が大幅に高速だった。
- RULER / LongBenchでは、比較した疎-注意機構 オフロード方式と概ね同程度の品質を維持した。

## 既存研究との差

Quest、ShadowKV、RetroInfer、PQCacheなどは、主に「どのKVが重要かを小さい索引で推定し、CPU DRAMから必要KVだけを読む」部分を改善する。KVDriveはそこに加えて、**一度GPUへ読んだ重要KVを複数段階再利用するキャッシュ管理、選択/取得/計算のパイプライン化、SSDまで含む3階層配置**を同時に設計する。

FlexGenのような保存 オフロードは大容量を扱える一方、層単位の粗い転送では疎 注意機構が実際には使わないKVまで読み込む。KVDriveは注意機構で選ばれたブロックだけをSSDから同期することでI/O amplificationを抑える。

TuttiやSwarmとは焦点も異なる。TuttiはGPU自身がSSD I/Oを発行してCPU control オーバーヘッドを減らし、Swarmは複数SSDへKVを配置してaggregate 帯域を高める。一方KVDriveは**SSDから読むデータ量そのものを注意機構 sparsityとGPU キャッシュ 再利用で減らし、DRAM/SSD 取得をGPU計算と重ねる**ことが中心であるため、保存 I/O 経路を高速化する研究とは補完関係にある。

## 限界

- 性能は注意機構 sparsityと重要KVの時間的局所性に依存する。注意機構 パターンが大きく変わるモデル/ワークロードではGPU内windowの再利用効果が小さくなり得る。
- 層/ヘッド別window、中心点数、塊 大きさ、micro-バッチ 大きさにはトレードオフがあり、論文でもワークロード/文脈/バッチによって最適値が変わる。
- SSDを追加してもDRAM-だけと同じ速度にはならず、評価ではDRAM+SSD構成に約40%のスループット低下が残る。
- 評価はtext LLMが中心で、multimodal モデルへの適用は将来 workとされている。
- arXiv v1時点では、論文prototypeを再現できる公式code repositoryをarXivページから確認できない。

## 一般的な実装上の含意

長文脈のKV オフロードでは「低速階層からKVを速く読む」だけでなく、**そもそも何バイト読むか、読んだKVを何段階再利用するか、I/O待ちをどのGPU計算の裏へ隠すか**を同時に決める必要がある。SSD 階層を実用化する場合、保存 帯域の改善だけでなく、注意機構側の疎 アクセスを保存 ブロック 配置と揃えて不要I/Oを避ける設計が重要になる。

またGPU メモリの残量を単なるfree spaceとして扱うより、再利用性の高いKVを残すキャッシュへ使えばPCIe/NVMe 転送を減らせる。これはGPU HBM・CPU DRAM・SSDを独立階層として最適化するより、エンドツーエンド デコード パイプライン全体で配置と予定を決める方が有利になり得ることを示す。

## 引用関係

KVDriveはQuest、ShadowKV、InfiniGen、MagicPIG、PQCache、RetroInferなどの実行対象-session KV オフロード / 疎 注意機構系を比較対象とし、FlexGenを保存まで含むcoarse-grained オフロードの比較対象としている。TuttiやSwarmと同じくSSD 階層を扱うが、KVDriveは注意機構-考慮したなデータ削減とmulti-階層 スケジューリングを主題とする。
