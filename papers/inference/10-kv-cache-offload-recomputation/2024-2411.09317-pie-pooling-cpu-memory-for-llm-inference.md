# Pie: Pooling CPU Memory for LLM Inference

> 一部のKV キャッシュをCPU DRAMへ置き、使う数層前にGPUへ戻して転送を現在層の計算と重ね、GPUを待たせない範囲までオフロード量を自動で増やすKVキャッシュ オフロード システム。

## 概要

Pieは、KV キャッシュをCPU メモリへオフロードするとGPU メモリは空く一方、必要になってからスワップインするとCPU→GPU転送待ちがデコード 遅延へ直接乗る問題に対し、**次に使う層のKVを事前に読み戻し、現在のGPU計算と転送を重ねる**研究である。

対象はNVIDIA GH200 Grace Hopperのように、CPU DRAMとGPU HBMを通常のPCIeより高速に直接つなぐ **NVLink-C2C** を備えた環境である。KV キャッシュのaccess順序は層単位でほぼ決まっているため、数層先で必要になるKVを利用順どおりの待ち行列から先読みし、CPU メモリを「GPU計算を止めずに使える追加メモリ」として扱う。

さらにオフロード量を固定せず、転送時間・GPU計算時間・スループットを実行中に監視し、CPUへ逃がすKV容量を増減する。論文の **適応型 expansion** は、**転送がGPU計算より長くなって待ち時間を生む直前まで、CPU側へ置くKVを段階的に増やす仕組み**を指す。

これは重み オフロードではなく、**KV キャッシュを対象とするCPUメモリ extension**である。モデル 重みは基本的にGPU側へ保持する。

## 問題設定

KV キャッシュをCPUへ置けばより大きなバッチを処理できるが、オフロードしすぎるとスワップインがGPU計算に間に合わず、逆に遅延とスループットが悪化する。

Pieは「CPU メモリをどこまで使えば、GPU計算を待たせずに有効なKV容量だけ増やせるか」を中心問題とする。

GH200ではCPU-GPU接続が非常に高速だが、論文の実測では大きなtransferでCPU→GPU約419 GB/s、GPU→CPU約371 GB/s程度で、HBM内部よりは低い。また小さいtransferでは帯域を使い切れない。そのためCPU メモリをGPUから細かく直接読むのではなく、**層ごとのまとまったKVを必要になる前に転送する**設計を採る。

## 手法

### 1. KV cacheをlayer単位でCPUへ配置する

PieはKV キャッシュをトークン ブロックだけでなく層方向にも分け、各層についてGPU側キャッシュ領域とCPU側キャッシュ領域を管理する。

一部層のKVをCPUへ退避し、GPUでその層が必要になる前にスワップインする。計算終了後は別の層をスワップアウトしてGPU側spaceを再利用する。

層 access順序はTransformer 順伝播でほぼ決まっているため、「次にどのKVが必要か」を一般的なキャッシュ 予測より高い確度で予測できる。

### 2. 利用順どおりに数layer先を先読みし、GPU計算と重ねる

次に必要になる層を利用順どおりの待ち行列（FIFO）で追跡し、現在層のGPU計算中に将来層のKVをCPU→GPUへ転送する。同時に処理済み層のKVをGPU→CPUへ戻す。

転送が層 compute time以内に終われば、GPU側の本来の計算はスワップ完了を待たずに済む。論文ではこの状態を **性能透過的 swapping**、つまり「スワップしていても表面上の実行時間をほぼ増やさない転送」と呼ぶ。

### 3. 「GPUを待たせず使えるCPU容量」だけを段階的に増やす

Pieでは単にCPU DRAMを全部キャッシュとして使うのではなく、**転送をGPU計算の裏へ隠せる範囲のCPU容量だけ**を実効的 拡張された メモリとして扱う。

実行開始時はCPU extensionを小さくし、

- CPU-GPU linkが飽和していない
- スワップ 遅延がGPU compute 遅延を超えていない
- expansionを増やしてスループットが改善している

間だけオフロード量を増やす。条件を満たさなくなれば維持または縮小する。

### 4. vLLMのKV block管理をlayerごとに拡張する

実装はvLLMを基盤とし、層ごとに異なるGPU キャッシュ容量を持てるようブロック 管理器を変更する。

キャッシュ extensionを増減するときは、各層のKV領域がどこにあるかを示す対応表を更新し、サービスを停止せずに層ごとの キャッシュ領域を再配置する。論文では約3,000行のPythonと約100行のC++/CUDAを追加したとしている。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Hardware | NVIDIA GH200 Grace Hopper |
| GPU memory | 96GB HBM3 |
| CPU memory | 480GB LPDDR5X |
| CPU-GPU | NVLink-C2C、公称900GB/s |
| Model | OPT-13B / OPT-30B / Llama-13B |
| Dataset | ShareGPT / Alpaca |
| Baseline | vLLM、FlexGen |

要求 到着は一定平均rateのランダム到着を表すポアソン 分布で生成し、online 推論提供のスループットとトークンごとの 遅延を評価する。

### 主要結果

GPU側KV キャッシュ容量を制限した条件で、PieはvLLMに対しShareGPTで最大**1.9倍**、Alpacaで最大**1.5倍**のスループットを示した。要求 rateを変えた評価でも、ShareGPTで約1.6〜1.9倍、Alpacaで約1.2〜1.6倍のスループット改善を報告している。

適切なexpansionを選ぶと、同等性能を保ちながらGPU メモリ使用量を最大**1.67倍削減**できたとしている。

適応型 expansionは全候補を試して得た最適設定に対してオーバーヘッドが2%未満で、多くのワークロードではKV キャッシュ warm-up中に最適付近へ収束した。

FlexGenとのOPT-30B比較では、ShareGPTで最大**9.4倍**のスループットを報告している。ただしFlexGenは重みもCPUへオフロードする方策が選ばれる条件があり、Pieとは利用するオフロード対象と遅延志向が異なるため、単純なKVオフロード同士の比較ではない。

## 既存研究との差

### vLLMとの違い

vLLMはGPU KV不足時に要求を一時停止したりCPUへスワップしたりできるが、必要になってからキャッシュを戻すとtransfer待ちが本来の処理時間へ加わる。

Pieは層 access順序を利用して**必要になる前にKVを先読みし、スワップをGPU計算で隠す**ことを主眼にする。

### FlexGenとの違い

FlexGenは重み・活性値・KVをGPU / CPU / SSDへ配置し、大バッチのoffline スループットを最適化する。Pieはモデル 重みをGPUへ置いたまま、主にKV容量だけをCPU メモリへ拡張し、online ワークロードで低遅延を維持する。

### DirectKVとの違い

PieはCPU上のKVを使用前にGPU HBMへ**スワップインしてから**アテンションを実行する。DirectKVはGH200/GB200の高速C2Cをさらに利用し、**CPU上のKVをGPU HBMへ一度コピーせず、GPU カーネルから直接読む**。

したがってDirectKVはPieの「高速linkならCPUをKV 階層として使える」という方向を、明示的なスワップを省くゼロコピー accessへ進めた後続研究と位置づけられる。

## 限界

- 性能上の中心的前提がGH200級の高速CPU-GPU interconnectであり、通常PCIe環境では同じ範囲の「スワップ待ちを隠す」動作は難しい。
- キャッシュ容量を増やしすぎるとスワップ 遅延がcomputeを超え、転送待ちが表面化する。
- モデル 重み オフロードを主対象とせず、モデル自体がGPUへ収まらない構成にはそのまま適用できない。
- 評価モデルはOPT / Llamaの13B〜30Bで、現代的なGQAやより巨大なモデルでの評価はない。
- 2026-09-06時点で著者による公式コード repositoryは確認できなかった。

## 一般的な実装上の含意

Pieの重要な示唆は、ホスト メモリを単なるoverflow先ではなく、**次のaccess時刻が分かるdataについて、転送をcomputeで完全に隠せる範囲だけ動的に利用するメモリ 階層**として扱うことにある。

特にKV キャッシュは層 access順序が明確なので、一般的なLRUより先読みしやすい。高速C2C環境では「どれをCPUへ逃がすか」だけでなく、「何層先までスワップを先行させれば本来の実行時間に転送待ちを出さずに済むか」を実行環境で制御する価値が大きい。
