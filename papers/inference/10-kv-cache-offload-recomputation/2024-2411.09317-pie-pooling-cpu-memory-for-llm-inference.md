# Pie: Pooling CPU Memory for LLM Inference

## 概要

Pieが扱う問題は、言語モデル推論で鍵・値キャッシュ（KVキャッシュ）をGPUの高帯域メモリからCPUメモリへ退避すると、同時処理可能な要求は増えるものの、必要時の読み戻しが逐次生成を停止させることである。CPUメモリを増やした分だけ必ず処理能力が増えるわけではない。GPUが層を計算しようとした時点で必要なKVがまだCPU側にあれば、その層の計算は転送完了まで待機する。そこでPieは「容量を増やすこと」と「1トークンの計算時間を延ばさないこと」を同時に満たすCPU側メモリの利用範囲を求める。

提案の中心は、層単位の**性能透過的な退避・復帰（performance-transparent swapping）**と**適応的容量拡張（adaptive expansion）**である。自己回帰Transformerでは、現在のトークンが第1層から最終層まで決まった順序で処理される。この順序を利用し、現在計算している層より先のKVをCPUからGPUへ先読みし、処理済み層のKVを逆方向へ退避する。転送が現在の計算と重なって完了すれば、CPUを使ったことによる追加の計算待ちは生じない。さらに実行中の転送時間、待機の有無、処理能力を観測して、CPUに置く層数を段階的に調整する。

著者はNVIDIA GH200 Grace Hopper上でOPT-13B、OPT-30B、Llama-13Bを用いて評価した。物理GPU KV領域が同じvLLMとの比較では、ShareGPTで最大1.9倍、Alpacaで最大1.5倍の処理能力を示す。拡張なしのPieとの比較ではOPT-30BのShareGPTで最大1.86倍、Alpacaで1.58倍である。CPU利用を増やし過ぎると転送待ちが発生して性能が悪化するため、これは無制限のメモリ拡張ではなく、計算時間の裏に転送を隠せる範囲だけを使う方式である。

## 問題設定と対象となるメモリ階層

推論要求が増えると、各要求の過去トークンについて層ごとの鍵・値を保持するため、KVキャッシュがGPUメモリを圧迫する。原著が例示するOPT-13Bでは1トークン当たりのKVが約800KBであり、2048トークンの1要求だけで約1.6GBになる。GPU上に置ける同時要求数が少ないと、新たな要求は待ち行列に入る。したがってトークン当たりの端点遅延には、実際に層を計算する時間だけでなく、実行順番が回るまでの待ち時間も含まれる。キャッシュ容量の拡張は、前者を増やさず後者を減らせる場合に意味を持つ。

比較対象のvLLMはページ化された注意（PagedAttention）によってGPU内の断片化を抑えるが、GPU KV容量が不足して要求を退避・再開する場合、再開時のデータ転送や再計算を待つ。FlexGenはモデル重み、活性値、KVをGPU・CPUなどへ配分し、事前計測に基づく配置を行うが、必要になった時点での転送が計算を停止させ得る。Pieはモデル重みそのものの退避を主眼とせず、層単位KVの利用時刻を予測できることに着目する。

実機のGH200はGPU側に96GB HBM3、CPU側に480GB LPDDR5Xを持つ。両者を結ぶNVLink Chip-to-Chipは公称900GB/sであるが、著者の実測ではCPUからGPUへ約419GB/s、GPUからCPUへ約371GB/sであり、GPU内のHBM帯域と同じではない。16MBを超える大きな転送では帯域の約95%を利用できる一方、小さな転送やCPUメモリへのGPUからの直接アクセスでは効率が落ちる。よってPieはKVを細かく直接参照するのでなく、層ごとにまとまった領域を先に転送してからGPUで計算する。

## 手法

### 層単位の実効容量モデル

全体で`n`層、GPUでKVに使える物理容量を`a`GB、CPUへ退避する層数を`m`とする。退避しなければ各層へ`a/n`GBを割り当てる。`m`層をCPUに置き、GPU上の残る`n-m`層で同じ物理容量を分ければ、各層の実効KV容量は`a/(n-m)`GBへ増える。すべての論理層がその容量を使えるとみなした拡張倍率は`n/(n-m)`である。これは物理HBMが増えることではなく、層間でGPUの同じ領域を時間分割して使うことによる論理的な拡張である。

実際にはGPU・CPU側の転送用二重緩衝領域も必要になるため、原著は転送中の4領域とGPU上の2領域を考慮した拡張比`(a+b)/a=(n+4)/(n-m+2)`を導く。ここで`b`はCPUから性能低下なく使える実効追加容量である。単純な`n/(n-m)`は構想を説明する式、後者は転送緩衝領域を含めた実装上の容量計算であり、同一の値として扱わない。

転送待ちを隠すには、層当たりの退避・復帰時間`t_swap`と計算時間`t_compute`の関係が重要である。概念上、CPUに置く`m`層の転送総時間`t_swap×m`を、`n`層の計算時間`t_compute×n`の中へ収めなければならない。CPUに置く層を増やすと実効バッチ容量は増えるが、同時に転送するKVも増えるため、この不等式には上限がある。しかも計算時間はバッチやモデルで変わり、転送時間は通信競合で変わるため、事前に一つの最適倍率を固定するのは難しい。

### 層順序を使った先読み・退避とFIFO

各トークンは層`1,2,...,n`を順番に通る。現在層`k`を計算している間、すでに処理した層`k-1`などはしばらく再利用されないので退避候補となり、これから必要になる層`k+1`などは復帰候補となる。Pieは次回使用までの距離が最も短いCPU側の層を「最も熱い層」、最後に計算を終えたGPU側の層を「最も冷たい層」として扱う。転送装置に空きがあれば熱い層を先読みし、冷たい層を退避する。

重要なのは、CPU側にある層よりもGPU側の退避候補がまだ早く再利用されるなら、むやみに退避を行わないことである。CPU上で長く待てる層だけを選ぶと、同じ層を短い間隔で往復させる無駄が減る。原著の9層の例では、1層の転送が2層分の計算時間を要し、CPU上に2層を保持しながら転送中の2層を扱う。定常状態では退避された層が順序どおりに先読みされ、先入れ先出し待ち行列（FIFO）のように動く。各層がCPU側と転送中に合計8層分の計算時間を過ごす例が示される。

この順序付けは単純な最近使用時刻の追跡ではない。Transformerの層実行順を利用するため、次の層アクセスを高い確度で知ることができる。GPU側の計算が第`k`層へ到達する前に、当該層の復帰を完了させることが必須である。間に合わなければGPUは停止し、性能透過性は破れる。FIFOは転送回数を減らしやすいが、通信帯域が不足した状況でも待ち時間を必ず消せるという保証ではない。

### 位置対応表と二段階の転送完了管理

Pieは各論理層のKVが現在CPU・GPUのどちらにあるかを位置対応表（mapping table）で管理する。表にはCPU側・GPU側のアドレスと転送時刻が含まれ、スワップ処理の制御器は現在の層番号と表を参照して転送を発行する。層ごとに固定のGPU領域を割り当てるのではなく、計算が進むにつれて物理領域の割当先を変更するため、この対応表が必要になる。

転送開始時にはまず宛先領域を確保してポインタを登録するが、この時点ではデータが存在するとみなさない。非同期転送が完了したことを確認してから、対応表上の存在状態を更新する。現在層の計算を開始する直前にはGPUポインタと転送完了状態を確認し、必要なKVがなければ待つ。この二段階管理を省くと、コピー途中のKVを計算カーネルが読んでしまう。したがって性能透過性を追求する一方、データ整合性のための待機条件は明示的に残している。

### 実行中の適応的拡張

Pieは初期状態で全層をGPU側に置き、実行を進めながらCPU側へ置く層数を増やす。転送開始時に、今回の計算でCPUから復帰させるべき層が存在しないなら、転送帯域に余裕がある可能性がある。こうした状況では拡張を一段増やし、GPU上の層当たりキャッシュ容量を大きくする。一方、復帰が計算に間に合わずGPUが待機したなら、CPU側へ置く層数を減らして拡張倍率を下げる。

ただし転送待ちがないというだけで拡張を際限なく増やすわけではない。直前の設定で得られた処理能力と比較し、追加容量による改善が止まれば拡張を抑える。低負荷ではときどき増加を試し、効果がなければ戻す。予期しない短時間のCPU・GPU間通信競合では一時的な待機を許容し、競合が継続する場合に拡張を縮める。こうして事前の詳細な性能計測を要求せず、実行中の装置・負荷変動へ追従する。

### vLLM上のメモリ再配置

実装ではvLLMのブロック管理器を、層ごとに異なる容量を持てるよう変更した。拡張倍率を増やす際は、層の新しい連続領域を確保してから、その層が次に転送されるタイミングでKVを新領域へ配置する。各ブロックの層内オフセットは保ち、対応表から得る基底アドレスだけを変える。全層が一度ずつ転送され、新容量が実体化してから、増加したブロックを空き領域一覧へ公開する。再配置途中にまだ存在しないブロックを要求へ割り当てないための順序である。

容量を減らす場合も同様に、層の転送時に小さな連続領域へ移すが、縮小後の上限を超えるブロックを使う新規要求は割り当てない。全層の縮小が完了してから空きブロック一覧を更新する。著者は既存vLLMへ約3000行のPython、約100行のC++/CUDAを追加し、層単位転送用CUDAカーネルも実装した。モデル別の変更は50行未満で済むと報告する。既存の要求受信インターフェースを大きく変更せず、キャッシュ制御部で追加機構を扱う設計である。

| モデル | OPT-13B、OPT-30B、Llama-13B |

原著は「同じ物理GPU KV容量でvLLMと比較する実験」と「Pie自身の拡張倍率1を基準にする実験」を別に示す。後者の1.86倍などを、前者の1.9倍と同じ比較として混同してはならない。特にGPU物理容量が十分大きい条件ではvLLMでも要求退避・再計算がほとんど発生しないため、Pieの改善率は小さくなる。

### 物理容量と拡張倍率を変えた処理能力

| 条件 | 比較基準 | Pieの主要結果 | 読み取り |
|---|---|---|---|
| OPT-30B、ShareGPT | Pieの拡張倍率1 | 最大1.86倍の処理能力 | 長い系列で追加KV容量が効く |
| OPT-30B、Alpaca | Pieの拡張倍率1 | 最大1.58倍 | 短い負荷でも一定の効果 |
| OPT-13B、ShareGPT | Pieの拡張倍率1 | 最大1.54倍 | モデルとKV容量で最適倍率が異なる |
| Llama-13B、Alpaca | Pieの拡張倍率1 | 最大1.27倍 | 利得が比較的小さい条件もある |
| 同じ物理KV容量、ShareGPT | vLLM | 最大1.9倍 | 容量不足時の再計算・待機を抑える |
| 同じ物理KV容量、Alpaca | vLLM | 最大1.5倍 | 大容量時はvLLMへ収束 |

OPT-13BのShareGPTでは、GPUの物理KV領域が3GBの場合は拡張倍率1から2まで処理能力が増える。一方、物理KV領域7GBでは倍率1.4～1.6付近から転送費用が優勢になる。したがって「拡張倍率2が常に最良」とは言えず、同じモデルでも利用可能なHBM容量によって上限が変わる。容量が大きい場合はGPU計算自体が律速となり、追加KV領域を増やしても処理能力は伸びない。

### 要求到着率と待ち行列・計算遅延

| 観点 | 条件・比較 | 一次論文の結果 |
|---|---|---|
| 到着率の感度 | OPT-30B、物理KV 3GB、Alpaca | 拡張による処理能力改善1.2～1.6倍 |
| 到着率の感度 | OPT-30B、物理KV 3GB、ShareGPT | 同1.6～1.9倍 |
| 低負荷 | Alpacaで毎秒15要求未満、ShareGPTで毎秒3要求未満 | そもそもKV容量が飽和せず、拡張の効果が小さい |
| 自動拡張の制御費用 | 各設定を総当たりで選んだPie-optimal比 | 処理能力の損失は2%未満 |
| 逐次生成遅延 | 拡張倍率1.0→2.0 | 計算時間を概ね維持し、待ち行列時間を削減 |
| 過剰拡張の負例 | 拡張倍率2.2対2.0 | 転送待ちが顕在化し、計算時間と待ち行列時間の両方が悪化 |
| 最適拡張の例 | 原著図9(c) | 適応制御が倍率2.08を選択し処理能力最大化 |

この評価は「CPUへ退避したKVが増えると必ず高速化する」という主張ではない。待ち行列が支配的な高負荷では、KV容量を増やして同時処理数を増やす効果が大きい。一方、低負荷ではそもそも待ち行列が短く、転送の追加費用を正当化できない。倍率2.2で悪化した例は、性能透過性が失われる境界を直接示している。制御器はこの境界を実測して倍率を戻すため、静的に大きな倍率を指定する方式より頑健になる。

### FlexGenとの比較と公平性

| 条件 | 比較対象 | Pieの処理能力 |
|---|---|---|
| OPT-30B、Alpaca | FlexGen | 7.8倍 |
| OPT-30B、ShareGPT | FlexGen | 9.4倍 |

この比較には重要な非対称性がある。FlexGenはGPUメモリが96GB未満の設定で重みもCPUへ退避する配置を選ぶため、KVのみを主対象とするPieとは転送対象が異なる。またFlexGenは入力系列長を揃えるためのパディングを必要とする。著者はFlexGenの配置コストモデルを120種類の設定で事前計測し、その準備に数時間を要したと説明する。Pieが実際に利用したCPU側の実効追加容量は、評価設定すべてで15GB未満である。480GBのCPUメモリをすべて高速なGPU容量として使ったわけではない。

このため、7.8倍・9.4倍という差は、特定のハードウェア、モデル、要求長の下で、事前配置型の重み・KV退避とオンラインのKV専用先読みを比較した結果として読むべきである。異なるGPU世代やPCIeのみの装置、別の重み配置条件で同じ倍率が得られると断定しない。

## 既存研究との相違

vLLMのページ化キャッシュはGPU内のメモリ断片化を抑えるのが中心であり、GPUとCPUの間で層の使用時刻を利用した先読みを最適化するものではない。Pieは同じvLLMを基盤にしつつ、層のアクセス順序と転送完了時刻を使い、GPU計算の待ち時間を増やさない容量拡張を狙う。したがってページ化キャッシュとPieの層単位退避は、競合するだけでなく別のメモリ階層で補完し合う。

FlexGenは重み・活性値・KVの配置をまとめて最適化するのに対し、PieはGPUへ収まるモデルを前提としてKVだけを層ごとに移す。予測できる層順序を利用し、計算と転送の重なりを第一の制約に置く点が異なる。CPUメモリをGPUから直接読むゼロコピー方式とも異なり、Pieでは計算直前までにKVをGPUへ戻す必要がある。後続研究で直接CPU側KVを参照する方式が登場しても、それをPie自身の実装結果と混同してはならない。

## 限界と負の結果

最大の制約はGH200級の高速なCPU・GPU間接続である。原著が測定した数百GB/sの実効転送帯域を、一般的なPCIe接続へそのまま外挿することはできない。低帯域の環境では同じ大きさのKVを層計算の裏で転送し切れず、性能透過的な容量拡張が成立する範囲は小さくなる。転送が間に合わないときはGPUを待機させるため、転送待ちを「常にゼロ」と保証する方式ではない。

またモデル重みがGPUへ収まる構成を主に扱い、モデル自体をCPUへ大規模に退避する場合の最適化は評価していない。評価モデルはOPT-13B/30BとLlama-13Bであり、より新しい混合専門家モデル、極端な長文脈、低帯域の小型GPU、複数GPU間の分散KV転送まで同じ利得を示す実験ではない。負荷が軽く待ち行列が短いと、拡張しても処理能力はほぼ増えない。逆に過剰拡張では転送待ちと待ち行列が同時に悪化する。

位置対応表、非同期転送の完了管理、転送用緩衝領域、層単位の再配置は追加費用を要する。大きな層単位転送が効率的な一方、KV容量や要求数が小さいと転送粒度が過大になる場合がある。適応制御も起動直後に最適倍率を知っているわけではなく、著者は多くの負荷でキャッシュのウォームアップ期間内に収束すると報告するにとどまる。突発的な別処理の通信では一時的な遅延が発生し得る。公開された一次資料から著者公式の再現用コードURLは確認できず、記載した性能は原著の実機評価に基づく。
