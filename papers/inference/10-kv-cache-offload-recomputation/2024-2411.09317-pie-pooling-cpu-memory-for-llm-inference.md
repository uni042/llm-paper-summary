# Pie: Pooling CPU Memory for LLM Inference

> GH200の高速CPU-GPU interconnectを使い、KV cacheをlayer単位でCPUへ先回りswapしながらGPU計算と重ね、online監視でoffload量を自動調整してHBM容量を実質的に拡張するKV-cache offload system。

## 概要

Pieは、KV cacheをCPU memoryへoffloadするとGPU memoryは空く一方、必要になってからswap-inするとCPU→GPU転送待ちがdecode latencyへ直接乗る問題に対し、**次に使うlayerのKVを事前に読み戻し、現在のGPU計算と転送を重ねる**研究である。

対象はNVIDIA GH200 Grace HopperのようにCPU DRAMとGPU HBMが高速なNVLink-C2Cで接続された環境で、通常PCIeよりはるかに大きいhost-device bandwidthを利用する。KV cacheのaccess順序がlayer単位で予測できることを利用し、FIFOで数layer先をprefetchすることで、CPU memoryを「GPU計算を止めずに使える追加memory」として扱う。

さらにoffload量を固定せず、転送時間・GPU計算時間・throughputをonline監視して、CPUへ逃がすKV容量を増減する **adaptive expansion** を導入する。これによりworkloadや帯域が変わっても、転送がcritical pathへ出る直前の範囲までCPU memoryを利用する。

これはweight offloadではなく、**KV cacheを対象とするCPU-memory extension**である。model weightは基本的にGPU側へ保持する。

## 問題設定

KV cacheをCPUへ置けばより大きなbatchを処理できるが、offloadしすぎるとswap-inがGPU計算に間に合わず、逆にlatencyとthroughputが悪化する。

Pieは「CPU memoryをどこまで増やせば、GPU computationを一切待たせずに有効容量だけ増やせるか」を中心問題とする。

GH200ではCPU-GPU接続が非常に高速だが、論文の実測では大きなtransferでCPU→GPU約419 GB/s、GPU→CPU約371 GB/s程度で、HBM内部よりは低い。また小さいtransferでは帯域を使い切れない。そのためCPU memoryを直接読むのではなく、**大きなlayer単位transferを先回りして行う**設計を採る。

## 手法

### 1. KV cacheをlayer単位でCPUへ配置する

PieはKV cacheをtoken blockだけでなくlayer方向にも分け、各layerについてGPU側cache領域とCPU側cache領域を管理する。

一部layerのKVをCPUへ退避し、GPUでそのlayerが必要になる前にswap-inする。計算終了後は別のlayerをswap-outしてGPU側spaceを再利用する。

layer access順序はTransformer forwardでほぼ決まっているため、一般的なcache predictionより高い精度でprefetchできる。

### 2. FIFOで数layer先のswapをGPU計算と重ねる

次に必要になるlayerをFIFO queueで追跡し、現在layerのGPU計算中に将来layerのKVをCPU→GPUへ転送する。同時に処理済みlayerのKVをGPU→CPUへ戻す。

転送がlayer compute time以内に終わる範囲なら、foreground GPU計算はswapを待たない。論文はこれを **performance-transparent swapping** と呼ぶ。

### 3. Effective memoryとしてCPU容量を段階的に増やす

Pieでは単にCPU DRAMを全部cacheとして使うのではなく、「GPUを止めずに使えるCPU領域」だけをeffective extended memoryと定義する。

実行開始時はCPU extensionを小さくし、

- CPU-GPU linkが飽和していない
- swap latencyがGPU compute latencyを超えていない
- expansionを増やしてthroughputが改善している

間だけoffload量を増やす。条件を満たさなくなれば維持または縮小する。

### 4. vLLMのblock managerをlayer-awareに拡張する

実装はvLLMを基盤とし、layerごとに異なるGPU cache容量を持てるようblock managerを変更する。

cache extensionを増減するときはmapping tableを使って各layerのbase addressを切り替え、serviceを停止せずにper-layer cache領域を再配置する。論文では約3,000行のPythonと約100行のC++/CUDAを追加したとしている。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| Hardware | NVIDIA GH200 Grace Hopper |
| GPU memory | 96GB HBM3 |
| CPU memory | 480GB LPDDR5X |
| CPU-GPU | NVLink-C2C、公称900GB/s |
| Model | OPT-13B / OPT-30B / Llama-13B |
| Dataset | ShareGPT / Alpaca |
| Baseline | vLLM、FlexGen |

request arrivalはPoisson distributionで生成し、online servingのthroughputとper-token latencyを評価する。

### 主要結果

GPU側KV cache容量を制限した条件で、PieはvLLMに対しShareGPTで最大**1.9倍**、Alpacaで最大**1.5倍**のthroughputを示した。request rateを変えた評価でも、ShareGPTで約1.6〜1.9倍、Alpacaで約1.2〜1.6倍のthroughput改善を報告している。

適切なexpansionを選ぶと、同等performanceを保ちながらGPU memory使用量を最大**1.67倍削減**できたとしている。

adaptive expansionはexhaustive searchで得た最適設定に対してoverheadが2%未満で、多くのworkloadではKV cache warm-up中に最適付近へ収束した。

FlexGenとのOPT-30B比較では、ShareGPTで最大**9.4倍**のthroughputを報告している。ただしFlexGenはweightもCPUへoffloadするpolicyが選ばれる条件があり、Pieとは利用するoffload対象とlatency志向が異なるため、単純なKV-offload同士の比較ではない。

## 既存研究との差

### vLLMとの違い

vLLMはGPU KV不足時にrequest preemptionやCPU swapを使えるが、必要になってからcacheを戻すとtransfer待ちがforeground latencyに出る。

Pieはlayer access順序を利用して**必要になる前にKVをprefetchし、swapをGPU計算で隠す**ことを主眼にする。

### FlexGenとの違い

FlexGenはweight・activation・KVをGPU / CPU / SSDへ配置し、大batchのoffline throughputを最適化する。Pieはmodel weightをGPUへ置いたまま、主にKV容量だけをCPU memoryへ拡張し、online workloadで低latencyを維持する。

### DirectKVとの違い

PieはCPU上のKVを使用前にGPU HBMへ**swap-inしてから**attentionを実行する。DirectKVはGH200/GB200の高速C2Cをさらに利用し、GPU kernelがCPU-resident KVを直接読み、staging bufferそのものをなくす。

したがってDirectKVはPieの「高速linkならCPUをKV tierとして使える」という方向を、zero-copy accessへ進めた後続研究と位置づけられる。

## 限界

- 性能上の中心的前提がGH200級の高速CPU-GPU interconnectであり、通常PCIe環境では同じ範囲のperformance-transparent swappingは難しい。
- cache容量を増やしすぎるとswap latencyがcomputeを超え、performance transparencyが崩れる。
- model weight offloadを主対象とせず、model自体がGPUへ収まらない構成にはそのまま適用できない。
- 評価modelはOPT / Llamaの13B〜30Bで、現代的なGQAやより巨大なmodelでの評価はない。
- 2026-09-06時点で著者による公式code repositoryは確認できなかった。

## 一般的な実装上の含意

Pieの重要な示唆は、host memoryを単なるoverflow先ではなく、**次のaccess時刻が分かるdataについて、転送をcomputeで完全に隠せる範囲だけ動的に利用するmemory tier**として扱うことにある。

特にKV cacheはlayer access順序が明確なので、一般的なLRUよりprefetchしやすい。高速C2C環境では「どれをCPUへ逃がすか」だけでなく、「何layer先までswapを先行させればcritical pathから外せるか」をruntimeで制御する価値が大きい。
