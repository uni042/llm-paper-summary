# Mixture of Quantized Experts (MoQE): Complementary Effect of Low-bit Quantization and Robustness

> MoQEは「MoEは1 tokenで少数expertしか計算しないのに、なぜ推論は遅く大きいのか」を**expert weightの保存量と読出し帯域**の問題として捉え、modelの92%以上を占めるexpert weightだけを強く低bit化する研究である。

## 概要

混合エキスパート（Mixture-of-Experts: MoE）は、たとえば32個のFFN expertを用意しても、1 tokenではrouterが選んだ1個だけを計算できる。そのためparameter数を大きく増やしながら、理論FLOPsはdense modelと近いままにできる。

しかし「計算しないexpert」はmemoryから消えるわけではない。deployment時には32 expertすべてのweightを保存し、routingに応じて必要なexpertを読み出せるようにしておく必要がある。

論文の5.3B・32-expert modelでは、fp16 model sizeが約9.91GBで、その**92.8%がMoE expert weight**である。同等FLOPsのdense modelは約1.18GBにすぎない。さらにA100上の同一batch条件では、dense modelが14.02 sentences/sなのに対し、fp16 MoEは5.37 sentences/sまで低下した。

つまりMoEは計算量を増やしていないのに、巨大なexpert weightを読むmemory trafficのため遅くなっている。

MoQEの方針は単純である。

- model容量の大半を占める**expert FFNだけを低bit化する**。
- quantizationに弱いdense FFN、self-attention、cross-attentionは高精度のまま残す。
- expertは3-bitまで追加学習なしで耐えやすく、2-bitのみ量子化考慮学習（quantization-aware training: QAT）で補う。

この設計により、model全体を一律に低bit化するより品質を守りながら、memoryを支配する部分だけを強く圧縮できる。

## 問題設定

### MoEでは『active parameters』と『stored parameters』が違う

MoEの効率を説明するときは「1 tokenで何parameterをactivateするか」がよく使われる。しかしdeployment memoryでは、**その瞬間に使わないexpertも保存しておかなければならない**。

32 expertからtop-1を選ぶ場合、計算するexpert FFNは1個でも、routerが次のtokenで別expertを選ぶ可能性があるため32個全部が必要である。

このためMoEの実運用では、

1. modelがGPU memoryへ収まるか
2. expert weightをHBMから読む帯域が足りるか
3. offloadする場合はCPU/GPU間へ何byte運ぶか

がFLOPsとは別のbottleneckになる。

### 全layerを同じbit幅へ落とす必要はない

量子化（quantization）は、fp16 weightをたとえば4-bit整数へ置き換え、scaleと組み合わせて近似する方法である。

bit数を減らすほどmemoryとbandwidthは減るが、weight値の細かな違いを表現できなくなる。特にweight distributionに極端な外れ値（outlier）があると、広い数値rangeを少数のquantization levelへ割り当てる必要があり、通常値の表現が粗くなる。

MoQEはmodel component別に感度を測り、**expert FFNは他のlinear layerより低bit量子化へ強い**ことを見つける。そこで敏感な部分まで無理に圧縮せず、expertだけを狙う。

## なぜexpert FFNは低bit化に強いのか

### expert weightはdense FFNより値のrangeが狭い

論文は偶数layerにMoE expert FFN、奇数layerに通常dense FFNを置くmodelでweight distributionを比較している。

dense FFN、とくに2つ目のlinear layerには大きなoutlierが現れ、weight rangeが広い。一方expert FFNはdistributionが比較的狭く、極端な値が少ない。

同じ2-bit / 3-bit quantizerを使ったとき、rangeが狭いexpert weightの方が1 quantization stepあたりの誤差を小さくできる。

### component別実験でもexpertだけ頑健だった

著者らはmodelを

1. expert FFN
2. dense FFN
3. self-attention
4. cross-attention

に分け、各部分だけを低bit化した。

3-bitではexpert FFNの品質低下は小さい一方、dense FFNは大きく悪化する。2-bitではdense FFNを量子化するとほぼtask能力を失う条件があるが、expert FFNはまだ意味のある品質を保つ。

この観察が「expertだけを強く量子化し、共有部は高精度で残す」というMoQEの根拠である。

## 手法のあらまし

MoQEの実行は次のように整理できる。

1. 学習済みMoE modelを用意する。
2. expert FFNの各weight matrixをchannel単位で量子化する。
3. self-attention、cross-attention、通常dense FFNはfp16のまま保持する。
4. 8/4/3-bitでは追加学習なしの学習後量子化（post-training quantization: PTQ）を使う。
5. 2-bitでは量子化誤差が大きいためQATを行う。
6. inference時は低bit expert weightを専用GPU kernelで読み、dequantizationとmatrix multiplicationを実行する。

重要なのは、routerやexpert数を変えない点である。**どのexpertを選ぶかというMoEの計算graphはそのままに、expertのweight表現だけを軽くする**。

## 手法

### 1. expert weightだけをweight-only quantizationする

MoQEはactivationを整数化せず、weightだけを低bitにする重みのみ量子化（weight-only quantization）である。

これには2つ利点がある。

- activation quantization由来の追加quality lossを避けられる。
- model sizeとweight read bandwidthというMoEの主要問題を直接減らせる。

MoE inferenceでは大量のexpert weightを読むことが問題なので、weight-onlyでもsystem上の効果が大きい。

### 2. matrix全体で1 scaleではなくchannelごとにscaleを持つ

量子化では整数値だけでなく「整数1 stepが元weightの何に相当するか」を示すscaleが必要になる。

matrix全体へ1個のscaleを使うと、一部channelのoutlierがmatrix全体のrangeを広げてしまう。

MoQEは**channel単位量子化（channel-wise quantization）**を使い、output channelごとに別scaleを持つ。これにより各channelのrangeへ合わせてquantization gridを細かくできる。

scale自体はfp16で保存するが、1 channelにつき1値なので追加容量はmatrix parameterの1%未満である。

### 3. linear quantizationを主に使う

論文は線形量子化（linear quantization）と対数量子化（log-scale quantization）を比較する。

低bit expertではlinear方式が良好だったため、主要実験ではchannel-wise linear quantizationを使う。

概念的には各weightを、そのchannelの最大絶対値から決めたscaleで割り、利用可能な整数rangeへ丸める。inference時にはscaleを掛けて近似weightとして使う。

### 4. 3-bitまではPTQ、2-bitだけQAT

8-bit、4-bit、3-bitは学習済みweightを変換するだけのPTQで評価する。

3-bit expertでも元MoEとの差を小さく保てるため、deployment前の追加trainingを必要としない。

2-bitでは量子化levelが少なすぎてPTQだけでは誤差が大きい。そのためtraining中からquantization errorを入れてmodelを適応させるQATを使う。

この違いは実務上重要で、MoQEの「超低bit化」はすべてtraining-freeという意味ではない。

### 5. expert以外を高精度に残す

model全体の圧縮率だけを最大化するならattentionやdense FFNも量子化したくなる。しかしcomponent感度実験では、それらを2〜3-bitへ落とすと品質悪化が大きい。

MoQEは**92.8%を占めるexpertだけを圧縮すれば十分大きなmemory効果が得られる**ため、残りの共有部はfp16で残す。

これは一種の粗い混合精度（mixed precision）設計で、「expertは低bit、共有部は高bit」というcomponent-level allocationになっている。

### 6. 4-bitだけはruntimeまで最適化して速度を測る

weightを4分の1へ圧縮しても、毎回fp16へ展開してから通常GEMMを呼ぶだけではdequantization overheadで速度が出ない。

論文は低bit expert用GPU runtimeを用意し、4-bit weightの読み出しとdequantizationを効率化する。

一方3-bit / 2-bitには同等に最適化されたkernelがなく、論文表でもthroughputは `Not optimized` とされている。

したがって**model sizeの改善とwall-clock speedupは別の結果**として読む必要がある。

## 評価

### まず見るところ

MoQEの重要な結果は「2-bitなら5倍速い」ではない。

主結果は、

- expertだけなら3-bitまでPTQで品質を保ちやすい
- 2-bit + QATでもdense fp16 model以上のBLEUを維持できる
- model sizeはfp16 MoEの約20%まで減らせる
- ただし実測speedupを示す最適化runtimeは主に4-bitで、速度向上は1.24倍

という**quality・capacity・speedの分離**である。

### 基本条件

| 項目 | 内容 |
|---|---|
| Task | 多言語機械翻訳 |
| Main model | 5.3B parameters、32 experts、top-1 routing |
| Dense comparison | 同じtraining data / FLOPs級のdense model |
| Hardware | NVIDIA A100 ×1 |
| Software | Ubuntu 20.04 / CUDA 11.6 |
| Metric | BLEU、model size、end-to-end throughput |
| Decoding | beam size 5 |

公開WMT系datasetと大規模内部multilingual datasetの両方を使い、robustnessがdataset固有ではないかも確認している。

### fp16 MoEはdenseより大きく、むしろ遅い

baselineでは、

| Model | Throughput | fp16 size |
|---|---:|---:|
| Dense | 14.02 sentences/s | 1.18 GB |
| 32-expert MoE | 5.37 sentences/s | 9.91 GB |

となる。

MoEはBLEUを上げるが、model sizeが8.38倍になり、memory bandwidth pressureによってthroughputはdenseの約0.38倍まで低下している。

### 量子化後のquality / size

| 構成 | 平均BLEU | fp16 MoE比size | throughput |
|---|---:|---:|---:|
| fp16 MoE | 46.35 | 1.00× | 1.00× |
| int8 expert | 46.34 | 0.54× | 1.16× |
| int4 expert | 46.18 | 0.32× | 1.24× |
| int3 expert | 46.01 | 0.26× | kernel未最適化 |
| int2 expert + QAT | 45.90 | 0.20× | kernel未最適化 |
| fp16 Dense | 45.06 | — | — |

2-bitではfp16 MoEより品質は下がるが、同じtraining dataのdense fp16 modelよりBLEUは高い。

### 79.6%削減と4.9倍圧縮

2-bit expert + QATでは、model全体のsizeをfp16 MoEから**79.6%削減**し、およそ4.9倍小さくする。

expert以外はfp16のままなので理論上8倍にはならない。それでもexpertがmodelの大半を占めるため、全体sizeへ大きく効く。

### 4-bit速度は1.24倍

int4ではmodel sizeが約0.32倍になるが、A100実測throughputはfp16 MoEの**1.24倍**である。

つまり「weight byte数が約3分の1」でも、model全体の実行にはattention、routing、dequantization、kernel overheadなどが残るため、速度は3倍にはならない。

この差は後続のMoE quantization研究でも重要で、**bit幅削減率をそのままsystem speedupへ変換してはいけない**。

## 既存研究との差

### dense LLM quantizationとの違い

dense modelではほぼすべてのFFN weightが毎token使われるため、layerごと・channelごとの量子化感度を考える必要がある。

MoQEはMoE特有の構造を使い、「巨大容量の原因であり、しかも量子化に強いexpert FFN」に圧縮を集中する。

### expert pruning / offloadとの違い

expert pruningはexpert自体を消すため、routerが本来そのexpertを使う機会を失う。

expert offloadはfull-precision weightをCPU/SSDへ残すが、必要時のtransferが発生する。

MoQEはexpertを全部残したまま1 expertあたりのbyte数を減らす。そのためoffloadと排他的ではなく、**低bit expertをCPU/SSDから転送すればI/O量も減らせる**ので組み合わせ可能である。

### 後続mixed-precision MoEとの違い

MoQEは全expertを同じbit幅へ量子化する。expertごとの利用頻度やimportanceに応じて2/4/8-bitを変える方式は扱わない。

その意味でMoQEは、後続のexpert-wise mixed precision研究に対する単純で重要なbaselineである。

## 限界

- 主評価は多言語機械翻訳MoEであり、Mixtral / DeepSeek / Qwen系decoder-only MoEではない。
- 3-bit以下の高速GPU kernelは評価時点で未整備。
- 2-bitはQATが必要で、完全training-freeではない。
- 全expertを一律bit幅へするため、expertごとの感度差を活用しない。
- activation、KV cache、routerは低bit化の対象外。
- size reductionとthroughput speedupの倍率は大きく異なる。

## 一般的な実装上の含意

MoQEから得られる重要な示唆は、MoE compressionでは**「modelのどこが容量を占めるか」と「どこが量子化に強いか」の積で対象を決める**ことである。

expertはmodel容量の大半を占め、かつこのmodelではoutlierが少なく低bit耐性が高かった。そのため共有部を無理に圧縮しなくても大きなmemory reductionが得られた。

またoffload systemの観点では、expert 1個を4-bitにすればCPU→GPU / SSD→RAMのtransfer byte数も小さくなる。したがってquantizationは単なるmodel-storage技法ではなく、**階層memoryのI/O圧縮**としても評価する価値がある。

一方、そのbyte削減を実速度へ変えるには対応kernelが必要である。3-bit / 2-bitの未最適化結果は、compression algorithmとruntime implementationを別々に設計してはいけないことを示す。
