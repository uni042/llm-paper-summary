# DynaMo: Runtime Switchable Quantization for MoE with Cross-Dataset Adaptation（旧題 MoQa）

> 入力データの傾向が変わったとき、エキスパートごとのビット幅と変化に敏感な一部チャネルだけを更新し、モデル全体を量子化し直さずに精度を保つMoE量子化方式。

## 概要
DynaMoは、**データセットが変わると重要エキスパートも変わる**ことを前提にした混合精度量子化である。旧版MoQaではエキスパートを主に二群へ分けていたが、v3 DynaMoではINT2/4/6/8の複数群と、dataset変更時に一部チャネルだけ切り替える実行時機構へ拡張された。

## 手法のあらまし

### 1. まずexpertごとに「低bit化したときの影響」を測る

DynaMoは単純なルーティング頻度だけではなく、

- そのデータでどれだけ使われるか
- ルーティング時にどの程度強く選ばれるか
- 他datasetでも同じエキスパートが重要か
- エキスパート間の重み相関

などを組み合わせ、**そのエキスパートを低ビット化したときにどれだけ品質へ影響が出そうか**を推定する。

論文ではこの値を `significance` と呼ぶ。

複数指標を使う理由は、ルーティング頻度だけでは量子化誤差の大きさを表せないからである。頻繁に選ばれるエキスパートでも低ビット化して出力がほとんど変わらないなら高精度を残す優先度は下げられる。一方、選択回数が少なくても特定datasetでルーティング スコアが高く、そのエキスパートの重みが量子化へ敏感なら、低ビット化した少数回の誤差が品質へ大きく効く可能性がある。DynaMoは利用頻度・寄与の強さ・重み側の感度を合わせて、datasetごとに精度を残す価値を見積もる。

### 2. v3ではexpertをINT8 / INT6 / INT4 / INT2へ分ける

旧MoQaは重要度の高低を二群へ分ける説明が中心だったが、DynaMoでは各エキスパートが「高ビット群にも低ビット群にもある程度近い」といった中間的な所属度を持てる分類を使い、INT8 / INT6 / INT4 / INT2へ割り当てる。

論文ではこの分類を `fuzzy clustering` と呼ぶ。境界にあるエキスパートを無理に最初から一群へ固定せず、最終的には容量を節約するため低ビット側へ寄せる。

この多段階化により、重要エキスパートだけINT8、やや重要なエキスパートはINT6/4、影響の小さいエキスパートはINT2という連続的な容量配分ができる。二値の高ビット/低ビット分類では境界付近のエキスパートをどちらかへ丸める必要があり、容量を余計に使うか品質を余計に落とすかのどちらかになりやすい。中間ビットを用意することで、総メモリ 予算の中で重要度に近い精度を割り当てやすくなる。

### 3. Dataset変化に敏感なchannelだけ高精度で別保存する

datasetが変わるたびに全エキスパートを再量子化するとコストが大きい。そこで、入力分布が変わったときに量子化誤差やエキスパート重要度へ強く効くチャネルだけをFP16で別途保持する。

論文ではこの少数チャネルを `salient channel` と呼ぶ。

全重みの約1%だけをFP16 キャッシュとして持ち、新datasetへ切り替わった際はこの部分を使って必要なビット構成だけを更新する。

dataset切替で問題になるのは、エキスパート全体の重みが変わることではなく『どのチャネルの量子化誤差が新しい入力分布で目立つか』が変わる点である。変化に敏感なチャネルだけ高精度copyを残しておけば、全エキスパートのFP16 重みを別途保持したり、モデル全体を最初から再量子化したりせず、その部分を差し替えて新しい精度構成へ適応できる。少量キャッシュはcross-dataset adaptationの復元材料として働く。

### 4. `runtime switchable`はtoken単位ではない

名前からトークンごとに精度を切り替えるように見えるが、主な切替単位は **dataset / ワークロードの変更時** である。

つまり、

`dataset A向けbit配置 → dataset Bへ切替 → expert重要度を更新 → 変化に敏感な少数channelを使ってbit配置を更新`

という運用で、デコード トークンごとにINT2/INT8を動的変更する方式ではない。

したがって実行時 切替可能という名称でも、各トークンのルータ結果に合わせて毎回重み表現を作り直すコストは負わない。ワークロード切替時にだけ較正情報とsalient チャネルを使って構成を更新し、その後の多数リクエストでは同じ低ビット 重みを繰り返し使う。切替頻度が低いサービングでは更新コストを長い実行期間へ償却できる一方、datasetが極端に短い周期で入れ替わる環境では adaptation オーバーヘッドの比率が大きくなる。

### 5. 低bit weightを毎回完全展開せずに計算するkernel

低ビット 重みは複数値を1つの整数へ詰めて保存し、CUDA カーネル内で必要な値だけ取り出しながらFP16計算へ渡す。

低ビット重みを毎回大きなFP16行列へ展開してからGEMMするよりメモリ トラフィックを減らせるため、cross-dataset adaptationだけでなく実生成速度まで評価できる構成になっている。

## 評価

### まず見るところ
- **結論:** ワークロードが変わると重要エキスパートも変わるため、ビット配置を固定せず少量の重要チャネルだけ更新すると再較正を軽くできる。
- **品質:** 約3bit級でGPTQよりPPL・zero-shot精度を改善する。
- **実速度:** **A100でFP16比約2.9〜3.1倍**の生成速度。
- **切替オーバーヘッド:** dataset切替時の追加処理は一桁〜10%程度。
- **注意点:** 動的なのは主にdataset切替時で、トークン単位精度 ルーティングではない。

ここでいう切替は、推論中に全重みを毎回量子化し直す処理ではない。入力データ集合の統計から重要チャネルを決め、あらかじめ用意した低ビット表現とFP16表現を選び直す処理である。この分離により、データ集合が変わったときも全モデルの再較正を避けられる一方、重要チャネルを保持する追加メモリと切替時の更新時間は必要になる。したがって、入力分布が頻繁に変わる提供では適応性が利点になり、単一分布を長時間処理する提供では固定量子化の単純さが勝る。

評価値を読むときは、PPLやゼロショット精度の改善が量子化配置の効果であり、生成速度の倍率は低ビット実行そのものと実装の効果も含むことに注意する必要がある。DynaMoの中心的な貢献は、異なるデータ集合へ移るたびにモデル全体を作り直さず、感度の高い部分だけを再構成して品質を保つ点にある。

ここから、DynaMoの利点は「常に動的にビットを変えること」ではなく、**dataset変化へ対応するためにモデル全体を再量子化し直さなくてよい**ことにある。

逆に、一つの固定domainだけを長期間処理するdeploymentではcross-dataset切替機構の価値は小さく、通常の静的mixed 精度でも十分な場合がある。DynaMoは入力分布が切り替わるサービングで、再較正コストと追加FP16 キャッシュを払って適応性を得る設計である。
