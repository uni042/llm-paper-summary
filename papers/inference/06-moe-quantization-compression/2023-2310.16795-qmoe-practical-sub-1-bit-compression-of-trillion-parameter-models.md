# QMoE: Practical Sub-1-Bit Compression of Trillion-Parameter Models

> trillion-parameter級MoEのexpert重みを3値化し、よく現れる値の並びをまとめて圧縮保存し、その圧縮形式を直接読む専用kernelで推論する方式。

## 概要
QMoEは、MoEの「計算は疎だが重みは巨大」という問題を、再学習なしのデータ依存量子化と実行系の同時設計で解く圧縮・推論フレームワークである。対象はSwitchTransformerで、base128（約7B）、large128（約26B）を検証し、主目標をc2048（約1.6Tパラメータ）に置く。c2048をBF16の約3.2TBから158.6GBまで圧縮し、1台のcommodity serverで扱える容量へ落とした点が中心成果である。

## 手法のあらまし

### 1. expertごとにGPTQをかける

QMoEの量子化自体はGPTQ系で、calibration入力から各expertの入力分布を集め、量子化後出力と元出力の差が小さくなるように重みを補正する。

ただしMoEではexpert数が非常に多いため、expertを1個ずつ処理すると量子化時間が膨らむ。そこで複数expertの入力・重みと、**どの重みを変えると出力誤差が増えやすいかを表す二次的な感度情報**をまとめて処理する batched GPTQ を使う。

実際、Switch-base-128の一層では、expertを1個ずつ処理する場合の174.1秒から、16 expertをまとめると28.8秒まで短縮している。

### 2. `ternary` は「3値重み」、sub-1-bitは保存平均

QMoEの最も特徴的な設定が **ternary quantization** である。各重みをおおむね `負 / 0 / 正` の3値へ落とす。

ここで論文がいう **0.807 bit/parameter** は、各重みを0.807 bitで直接演算するという意味ではない。

ternary化するとゼロが非常に多くなるため、その偏りを圧縮符号化した結果として、**メタデータ込みの保存量を平均1 bit未満にできる**という意味である。

### 3. よく現れる3値の並びを辞書化してさらに圧縮する

c2048ではternary化後の重みの約88.6%がゼロになる。この偏りを利用し、よく現れるternaryの組合せを辞書へ登録する。

複数のternary値列を1つの16-bit番号へ対応付け、その番号から最大28重み分を復元する。論文ではこの方式を `dictionary coding` と呼ぶ。

単純に各重みを2 bitで保存するより、**頻出する値の並びを1つの短い番号へ置き換えることで容量をさらに削る**。

### 4. 圧縮形式のまま計算できる専用kernelを作る

圧縮ファイルを小さくしても、毎回大きなFP16配列へ展開してからGEMMすると速度面の利点が消える。

そこでCUDA kernel内で、

`辞書から値を復元 → 必要なscaleを適用 → matrix-vector積`

をまとめて行う。GPUの小さなthread groupが行列の一部を担当し、圧縮重みを完全展開せずに直接計算する。

つまりQMoEは、**量子化方式だけでなく保存形式と実行kernelまで一体化して初めてsub-1-bitを実用化した研究**と見るのが分かりやすい。

## 評価

### まず見るところ
- **結論:** 1.6T級MoEでも、expertをternary化して値の偏りを利用して圧縮すれば、TB単位から百GB台まで縮められる。
- **圧縮:** c2048は約3.2TBから158.6GB。全モデル平均では約0.807 bit/parameter。
- **品質:** 2 bitはかなり良好。ternaryは劣化が増えるが、単純に丸める方式より大幅に良い。
- **実速度:** 圧縮形式を直接読む専用kernelを持ち、形状によってBF16 cuBLASより速い。
- **注意点:** 0.8bitは保存平均であって、通常の0.8bit算術演算ではない。trillion-scaleのBF16 E2E比較は同一hardware上では現実的に行えない。

### 評価対象

| 項目 | 内容 |

### c2048の品質

| 方式 | C4 loss | 読み方 |
|---|---:|---|
| BF16 | 1.18 | 基準 |
| QMoE 2 bit | 1.20 | 約1.7%悪化 |
| QMoE ternary | 1.26 | 約6.7%悪化 |
| 単純丸め 2 bit | 1.33 | QMoEより明確に悪い |
| 単純丸め ternary | 2.15 | 大きく崩れる |

追加domainでも、c2048のBF16 / 2 bit / ternaryは、Arxivで1.31 / 1.34 / 1.42、GitHubで0.99 / 1.05 / 1.13、Wikipediaで1.20 / 1.24 / 1.32だった。

### 圧縮率

| モデル | expert圧縮倍率 | 全体圧縮倍率 | 最終サイズ |
|---|---:|---:|---:|
| base128 | 17.06倍 | 11.76倍 | 1.27GB |
| large128 | 18.34倍 | 13.32倍 | 3.96GB |
| c2048 | 20.07倍 | 19.81倍 | 158.6GB |

c2048ではBF16約3.2TBから158.6GBまで縮小する。ここがこの論文の最も大きな実用上の成果である。

### 量子化にかかる時間

| モデル | 条件 | 量子化時間 |
|---|---|---:|
| base128 | A6000 / 10K samples | 8.4分 |
| large128 | A6000 | 22分 |
| c2048 | A6000 / 160K samples | 16.0時間 |

trillion-scaleでも1日未満に収めているが、これは複数expertをまとめてGPTQ処理する実装最適化の効果が大きい。

### 実行kernel

A6000 / RTX 3090では、圧縮値の復元とmatrix-vector積をまとめたkernelが一部の行列形状でBF16 cuBLASより最大35%速い。128-token生成のend-to-endは、論文が置いた理想化BF16下限に対して5%未満の差だった。

ただしBF16 c2048をそのまま置くにはA6000が65台超、RTX 3090なら130台超必要になるため、**「同じ1台のGPUでBF16とQMoEを直接比較したspeedup」ではない**ことに注意が必要である。

## 監査結果
- arXivはv1のみで、タイトル・著者・公開日を一次資料で確認した。
- 所属はElias FrantarがISTA、Dan AlistarhがISTA / Neural Magicであることを本文先頭で確認した。
- 公式 `IST-DASLab/qmoe` リポジトリに量子化、compressed inference、CUDA kernel、SwitchTransformer実行コードと実験コマンドが公開されていることを確認した。
- c2048の158.6GB、19.81×、0.807 bit/parameterはTable 7、単一A6000での圧縮時間はTable 8、compressed kernelの最大35%高速化とE2E <5% overheadはSec. 5.3 / Fig. 5で確認した。
- E2E BF16比較は実GPU群で同一条件比較した値ではなく、expert weightを共有させた**理想化BF16下限推定**である。実際のBF16 c2048には65台超のA6000または130台超のRTX 3090が必要と論文自身が明記しているため、性能比較ではこの制約を保持する。
