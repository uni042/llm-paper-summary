# Huff-LLM: End-to-End Lossless Compression for Efficient LLM Inference

> FP16/BF16重みを小bit群へ分割Huffman圧縮し、1cycle decoderを演算器直前へ置いて損失なしのまま容量・帯域・遅延を減らすHuff-LLM。

## 概要

LLMの重み圧縮では、INT8/INT4量子化や枝刈りが一般的である。これらは大きな圧縮率を得られる一方、元の重みを厳密には復元できない**非可逆圧縮（lossy compression）**であり、平均accuracyが近くても個々の出力が変わる可能性がある。

Huff-LLMは別の設計点を狙い、FP16/BF16のbit列を**完全に復元できる可逆圧縮（無損失 compression）**のまま、モデルをcloud・disk・DRAM・オンチップ重み バッファまで圧縮状態で保持する。演算器へ重みを送り込む直前だけHuffman decoderで元の16bit値へ戻すため、数値演算そのものは非圧縮モデルと同一になる。

通常のHuffman codingを16bit 重みへそのまま適用すると、最大65,536種類のsymbolを扱う巨大decoderが必要になる。しかもHuffman コードは可変長なので、decoderが毎cycle 重みを1個出せないとsystolic arrayへバブルが入り、MAC配列全体を止める。このハードウェア制約が、無損失 compressionをLLM inferenceの高速化へ使いにくかった理由である。

Huff-LLMは16bitを小さいbit群へ分割し、各群ごとに小さなHuffman codebookを持つ。FP16ではsignを非圧縮、5bit exponent・上位5bit mantissa・下位5bit mantissaを別々に圧縮する **1-5-5-5 分割** を採用する。5bit symbolなら32-entry CAMで1-cycle デコード可能であり、圧縮率をほとんど失わずdecoderを小さくできる。

シミュレーションとFPGA/論理合成評価では、モデル容量・重み帯域を15〜32%削減し、LLaMA系で推論遅延を最大31%、energyを最大26%削減する。decoder area オーバーヘッドは128×128 systolic array基準で約6.13%である。

## 問題設定

### losslessでも「DRAMで展開したら」速度は上がらない

一般的な無損失 モデル compressionは、ネットワーク転送やdisk容量を減らす用途なら容易である。しかしGPU/NPUへ読み込む前に全重みを元サイズへdecompressすると、実行中のDRAM/HBM占有量と重み 帯域は非圧縮モデルと同じになる。

層ごとにdecompressする方法ならDRAM容量は減らせるが、各層実行前に大きな重み matrixを展開する時間が入る。既存研究では圧縮できてもinferenceが約33%遅くなる例があり、「保存容量削減」と「実行高速化」が一致しない。

Huff-LLMは圧縮重みを**演算器の直前まで展開しない**。DRAM→重み バッファへの転送byte数自体が減るので、メモリ-帯域-boundなLLM GEMMの遅延とenergyも減らせる。

### なぜ普通のHuffman decoderを置くだけでは駄目なのか

Huffman codingは出現頻度の高いsymbolへ短いcodewordを割り当てる。平均bit数は減るがcodeword長が不定なので、serial decoderではあるcycleにsymbolが出て次cycleはまだcodeword途中、というバブルが生じる。

Systolic arrayは各PEへ重み/活性値を規則正しく送り続けるdataflowで性能を出すため、decoder バブルがあると配列全体が待ちする。1 cycleで必ず1 symbolをデコードするには、入力bitsを全codeword候補と並列比較するCAMが使えるが、16bit symbolなら候補数が多過ぎて現実的でない。

したがって課題は圧縮率だけでなく、**小さいdecoderで毎cycle元重みを供給できるsymbolization**を作ることである。

## 手法

### 1. 16bit浮動小数を小さいsymbolへ分割する

FP16は1bit sign、5bit exponent、10bit mantissaからなる。Llama-3-8BのFP16重み全体を16bit symbolとして見るとentropyは約10.54 bit/パラメータで、理論的には大きく圧縮できる。しかし16bit Huffman decoderは大き過ぎる。

Huff-LLMはsignをそのまま残し、残りを5+5+5bitへ分割する。各5bit群は32種類しかないので32-entry CAMで並列lookupできる。3群のentropy合計とsignを合わせても約10.61 bit/パラメータで、16bit全体を直接entropy codingする10.54とほぼ同じ圧縮性を保つ。

BF16ではbit分布が異なるため1-4-4-7 分割を使い、圧縮しやすいexponent側を中心に符号化する。つまり固定の「16bitを4等分」ではなく、float formatの統計とdecoder コストを合わせて分割を決める。

### 2. 圧縮weightをメモリ階層全体で保持する

Huffman encoding自体はofflineで一度だけ行う。cloud/disk上のモデル file、main メモリ、acceleratorの重み バッファにも圧縮bitstreamを置く。

そのため容量削減だけでなく、DRAMからon-chip バッファへ読むbyte数、バッファに必要な容量、バッファからdecoderへ供給するtrafficも同時に減る。従来の「DRAMへ載せる前に展開する」無損失圧縮との差はここにある。

### 3. 1-cycle Huffman decoderでbubbleを消す

各5bit decoderは、compressed ストリームを保持するregisterと現在codeword先頭を示すpointerを持つ。最長codeword長 (L_{max}) 分を取り出し、32-entry CAM内の全codewordと同時比較して、対応する5bit source symbolとコード length Lを1 cycleで得る。

pointerをLだけ進め、不足したcompressed bitsだけバッファから補充する。3つの5bit decoderを並列動作させ、非圧縮sign bitと連結すれば1つのFP16 重みを毎cycle再構成できる。

可変長codingを「平均では速い」decoderにするのではなく、accelerator dataflowが要求する**固定1 重み/cycle**へ合わせた点が重要である。

### 4. Systolic ArrayとVector Acceleratorの直前へ挿入する

Systolic arrayでは各columnへ重みが流れ込む直前にHuffman Decoderを置き、重み バッファを3 bankへ分けて5bit群のcompressed ストリームを供給する。MAC/PE側は通常の16bit 重みを受け取るため変更不要である。

Simba/NVDLA系のvector 構成でも、局所 重み メモリとvector MACの間へ同じdecoderを置く。圧縮形式は演算器へ漏れず、既存dataflowを変えずにメモリ movementだけを縮めるco-designになっている。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| モデル | Llama、OPT、Qwen、Vicuna、3B〜13B |
| 重み形式 | FP16 / BF16 |
| accelerator 1 | 128×128 systolic array、16 TOPS、1 GHz |
| accelerator 2 | Simba-like vector、4 TOPS、2 GHz |
| DRAM帯域 | 64 / 128 GB/s、追加で256 GB/s |
| シミュレーション | modified SCALE-Sim、Timeloop/Accelergy等 |
| ハードウェア検証 | 5bit Huffman decoderのVerilog synthesis |
| 比較指標 | bits/param、遅延、energy、area |

LosslessなのでMMLU等のaccuracyを再比較する必要はなく、元重みをbit-exactに復元すること自体が品質保持条件である。ベンチマーク名は主に入力トークン長の違いによるシステム挙動を見るために使う。

### 圧縮率

| モデル例 | FP16 bits/param | 圧縮比 | BF16 bits/param | 圧縮比 |
|---|---:|---:|---:|---:|
| Llama-3-8B | 10.96 | 1.46× | 11.68 | 1.37× |
| Llama-2-13B | 10.88 | 1.47× | 11.59 | 1.38× |
| OPT-13B | 13.68 | 1.17× | 11.59 | 1.38× |
| Qwen2.5-7B | 10.96 | 1.46× | 11.68 | 1.37× |

モデルや浮動小数formatによりentropyが違うため、無損失圧縮率は固定ではない。FP16 Llama/Qwenは約31〜32%容量削減に近い一方、OPT/Vicunaは約15%程度に留まる。

### latency・energy・area

LLaMA系では遅延削減が26〜31%、energy削減が16〜26%。圧縮率の低いOPT系では遅延 13〜15%、energy 3〜10%程度となる。圧縮できるbyteが多いほど重み transfer削減が大きくなるためである。

128×128 systolic arrayへdecoderを組み込んだ論理合成ではarea オーバーヘッド 6.13%。full-chipではバッファ等も面積分母に入るので相対オーバーヘッドはさらに小さくなると論文は述べる。

256 GB/sまでDRAM 帯域を上げると比較対象自体が計算律速になり、Huff-LLMの遅延利得は消える条件がある。それでもメモリ access量は減るためenergyは約24%削減できた。この結果は「圧縮率＝速度改善率」ではなく、ルーフライン上でメモリ律速か計算律速かが実時間利得を決めることを示す。

## 既存研究との差

Quantizationは重み bit数を減らすが元値を変える。Huff-LLMは元のFP16/BF16 bit patternを完全復元するため、モデル出力の数値的挙動を圧縮前と同じに保つ。

ZipNN等の無損失圧縮はストレージ/ネットワークを主対象にし、NeuZip系は実行時メモリにも圧縮重みを置くが層ごとの展開コストが残る。Huff-LLMは**on-chip バッファまでcompressed representationを維持し、MACへ入る直前に1-cycle復号**することで、無損失 compressionを帯域最適化へ変える。

## 限界

Huff-LLMはcommodity GPUへそのままsoftwareだけで導入する方式ではない。CAMを含む専用decoderをaccelerator data pathへ組み込むハードウェア supportが必要である。

圧縮率は重み bit distributionに依存し、FP16 OPTのようにentropyが高いモデルでは利得が小さい。またメモリ 帯域が十分高くGEMMが計算律速なら遅延改善は消える。

論文の遅延/energyは主に構成 シミュレーションと構成要素 synthesisに基づく。実製品chipでのfull-システム measurementとは区別する必要があり、decoder、バッファ banking、ルーティングを含むphysical design後の値は別途検証が必要である。
