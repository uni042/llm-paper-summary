# InfiniPot: Infinite Context Processing on Memory-Constrained LLMs

## 概要

InfiniPotは、長い入力をすべて読み終わってから鍵・値キャッシュ（KVキャッシュ）を削減する方式ではなく、**入力を読んでいる途中から固定容量内で何度も圧縮する**長文脈処理の仕組みである。メモリの最大エントリ数をMとし、入力の読み込みでキャッシュが満杯になるたびに、重要なエントリをC個へ絞って次のチャンクを受け入れる。この継続的文脈蒸留（Continual Context Distillation、CCD）により、総入力長が伸びても保持するKVのエントリ数は一定にできる。追加学習は必要としない。

何を残すかについて、触媒プロンプト（Catalyst Prompt、CaP）から将来参照されそうな代表的情報を推定し、圧縮下新規性（Novelty under Compression、NuC）から既存文脈では予測しにくい固有情報を拾う。さらに保持したトークンの回転位置埋込みを再割当する文脈再設定RoPE（Context-Reset RoPE、CR-RoPE）で位置の分布外問題を抑える。LLaMA-3-8Bの4Kメモリ条件ではLongBench平均41.50点で、単純な4K切捨ての37.20点を上回る。Mistral系の4K固定KV予算で最大100万トークンの検索実験も行ったが、「無限長でも全情報を損失なく保持する」ことを示したわけではない。

## 問題設定

長い入力を扱うためにコンテキスト長を延ばしたモデルや位置埋込みを変更したモデルは、必要なKVキャッシュの容量そのものを必ずしも減らさない。長入力を一度すべて処理してから重要KVを選ぶSnapKV型の手法も、圧縮後のキャッシュは小さくできるが、プリフィルの途中には入力全体を保持するメモリが必要となる。モバイルや小容量アクセラレータでは、最終キャッシュサイズだけでなく**処理の全期間で固定メモリ予算を超えない**ことが制約になる。

固定窓のストリーミングでは古い情報を捨てやすく、文書の冒頭にしかない人名や数値が後で質問される場合に失敗する。重要度を注意重みから計算しようとしても、未来の質問や後続文書をまだ見ていないため、どの過去トークンが将来必要か分からない。さらに圧縮を繰り返すと古いが固有の事実が平均的な内容に埋もれ、重要度の高い一般的なトークンばかり残る危険がある。InfiniPotは「代表性」と「新規性」を別々に計測することでこの二つの失敗を抑える。

## 手法

### 1. 固定容量の継続的文脈蒸留

KVの最大保持数を `|M|`、圧縮後に残すエントリ数を `|C|` とし、`|C| < |M|` とする。最初は入力を順次処理してMまで蓄積する。満杯になると、現存するKVから重要なC個を選んでそれ以外を捨てる。空いたM−C個の枠に次の入力を流し込み、再び満杯になれば既存の蒸留済みKVと新しいKVをまとめて再評価する。この「入力→選別→追加入力」の循環がCCDであり、入力全体のKVを一時的に別領域へ退避してから圧縮する方式とは異なる。

保持集合の大きさCと容量Mの比率は事前に設定する。圧縮率が高いほど新しいチャンクを多く受け入れられるが、一回の蒸留で捨てる情報も増える。情報密度の高い区間であっても自動的に保持数を増やす機能は論文の主要実装に含まれない。したがって「無限」という名称は計算可能な総入力長に固定上限を置かないという意味であり、無制限の情報保持を保証するものではない。

### 2. CaPで将来の重要性を近似する

未来のトークンが現在のトークンtへ向ける注意重みの合計を、本来の将来重要度と考える。しかし実際のストリーミング処理では未来の文脈がまだない。CaPはキャッシュが満杯になる直前に短い補助プロンプトを挿入し、その補助トークンから既存トークンへの注意量を「将来参照されやすさ」の代理値として計測する。たとえば「この節の重要点を要約せよ」という一般指示を与えると、後で要約や質問に役立ちそうな内容へ注意が集まりやすい。

CaPは重要度測定のためだけに使い、測定後はキャッシュから取り除く。実際の入力文書へ恒久的に付加して生成内容を変えるものではない。CaPの注意量はヘッド単位で算出するため、保持するトークン集合が注意ヘッドごとに異なる可能性がある。質問が事前に分かる場合はその質問をCaPへ含めると関連部分をより選びやすいが、未知の未来質問へ一般化する場合には質問非依存の一般要約指示を使う。

### 3. NuCで予測しにくい固有情報を保護する

NuCは、あるトークンが直前の圧縮済み文脈からどれだけ予測しにくいかを負の対数尤度で測る。予測しやすい定型表現や繰返しは小さい値、初出の固有名詞や珍しい事実は大きい値になりやすい。圧縮のために過去全体を保存していないので、実際には保持済みの圧縮トークン列と現在の未圧縮区間を条件にした近似新規性を使う。CaPの代表性だけでは捨てられる少数の固有情報を、NuC用の専用枠で救う狙いである。

NuCはトークン単位の指標であり、CaPはヘッド単位の注意指標である。この粒度の違いから、二つの数値を単純に加算して一斉に順位付けするのではなく、まずC個のうちT個をNuC上位へ割り当て、残りのC−T個をCaP上位から選ぶ。論文の主要実験ではNuC枠の割合を50%とする。NuCだけを使うとヘッド間で同じトークンが残りやすく、キャッシュの多様性が失われるため、CaPとの併用が重要となる。

### 4. CR-RoPEで位置の範囲を再設定する

長い系列から離れた位置のトークンだけを残すと、元の位置番号を使い続ける場合には学習時の最大位置を超えたり、位置間隔が大きく飛んだりする。InfiniPotはRoPEを適用する前の鍵を保持し、蒸留のたびに残したC個のトークンへ0からC−1までの連続位置を割り当て直す。これがCR-RoPEである。新しい入力を処理するときも固定容量の位置範囲を使えるため、モデルの学習時より極端に大きい位置番号を直接扱わずに済む。

位置の再設定は各トークンを生成するたびではなく、CCDが発生したときにまとめて行う。論文はStreamingLLM型の逐次再適用に比べて、RoPEの再計算回数を入力長Lに対する `L/|M|` 程度へ減らせると説明する。ただし元の絶対位置やトークン間距離を厳密に保つわけではないので、位置に依存する課題で必ず損失がないとは言えない。

## 評価

### 実験条件

| 観点 | 一次資料の設定 |
|---|---|
| 計算機 | NVIDIA A100 80GB。モバイル端末実機ではない |
| 実装 | PyTorch/Hugging Face Transformers 4.44、FlashAttention2 2.6.3、SnapKV実装を基盤 |
| 主モデル | LLaMA-2-7B、LLaMA-3-8B、Mistral-7B v0.2/v0.3などの指示追従モデル |
| 補足モデル | LLaMA-3.1/3.2、Gemma-2、Phi-3の追加実験 |
| 主課題 | LongBenchの文書QA、複数文書QA、要約、少数例学習、合成課題、コードなど |
| 長距離検索 | Needle in a Haystackのパスキー検索、入力4K〜1Mトークン |
| メモリ条件 | KV保持数2Kまたは4Kを中心に、1K〜8Kの感度分析 |
| 比較対象 | 切捨て、固定窓、StreamingLLM、H2O、TOVA、SirLLM、SnapKV、長文脈学習モデル |
| 指標 | LongBench平均、検索正答率、KVメモリ、初回トークン時間、生成処理量、全体時間 |

「メモリ4K」はKVエントリ数の予算であり、重み・活性値・ワークスペースを含むGPU全体の使用量が4Kバイトという意味ではない。主な効率測定もA100上の実験であり、低メモリの端末へ実際に載せた性能ではない。

### LongBenchの主要結果

| モデル・メモリ条件 | 比較手法 | LongBench平均 | 解釈 |
|---|---|---:|---|
| LLaMA-3-8B、4K | 単純切捨て | 37.20 | 固定長の古い情報を捨てる基準 |
| 同上 | SirLLM | 35.43 | 新規性中心だけでは不足 |
| 同上 | TOVA | 36.26 | 注意による選別の基準 |
| 同上 | InfiniPot | **41.50** | 代表性・新規性・位置再設定を併用 |
| Mistral-7B v0.3、4K | 単純切捨て | 40.07 | 同じ容量の基準 |
| 同上 | InfiniPot | **44.22** | モデルを替えても改善 |
| LLaMA-2-7B、2K | 単純切捨て | 31.24 | より小さい予算 |
| 同上 | InfiniPot | **31.32** | 改善はごく小さく、万能ではない |
| Mistral-7B v0.1、4K | 固定窓 | 32.22 | 最近文脈中心の基準 |
| 同上 | InfiniPot | **34.36** | 限られたKV内で情報保持を改善 |

LLaMA-3の41.50点は学習時の全長8Kを使う無制約基準42.91点には及ばない。InfiniPotが全ての長文脈モデルを上回ると単純化すべきではない。またLLaMA-2の2Kでは31.24から31.32への僅差であり、モデルとメモリ条件によって利得が大きく変わる。

### 触媒プロンプトと新規性の構成要素分析

| LLaMA-3-8B、4K | LongBench平均 |
|---|---:|
| CaPもNuCもなし | 36.26 |
| CaPのみ（NuC 0%） | 39.89 |
| NuC 25%＋CaP 75% | 40.65 |
| NuC 50%＋CaP 50% | **41.50** |
| NuC 75%＋CaP 25% | 41.08 |
| NuCのみ | 35.43 |

CaPを加えるだけで代表的な情報を保持しやすくなり、さらにNuCを半分組み合わせると固有情報も残りやすい。NuC単独ではヘッド間の保持集合が似通い、性能が36.26から35.43へむしろ低下する。これは両指標が単純に足し算可能な万能スコアではなく、保持枠の配分を工夫する必要があることを示す。質問をCaPに含められるQA課題では、一般指示のQA平均30.54に対して質問付き指示は35.71となるが、未来の質問を知らないオンライン入力で同じ利得を仮定できない。

### 長距離検索と実行効率

Needle in a Haystackでは、LLaMA-3とMistral-v0.3の4K保持で512K入力まで高い検索精度を保ち、Mistral-v0.1では128Kまで比較的安定した。さらにMistral-v0.3の条件では1Mトークンまでの入力でパスキー検索を評価し、CR-RoPE、CaP、NuCを組み合わせた場合に高い正答率を示した。これは合成検索課題の結果であり、100万トークン中のすべての情報を任意の複雑な推論で使えるという保証ではない。

実行効率ではGovReportとMistral-7B v0.3を用い、入力長に伴うGPUメモリ、初回トークンまでの時間、生成トークン毎秒、全体時間を比較した。全KV保持やSnapKVは入力が長くなるとプリフィル時のメモリが増え、SnapKVは長い入力を最初に読み込む費用が残る。StreamingLLMはメモリを固定できるが、逐次トークン処理とRoPE再適用が遅延を増やす。InfiniPotは長さ50K超の条件でSnapKVに匹敵または上回るプリフィル速度を示し、生成段階でも高い処理量と短い全体時間を報告する。ただし具体的な時間比は図・付録の条件に依存し、論文全体に一律の高速化倍率を設定するのは適切でない。

## 既存研究との差

StreamingLLMは注意シンクと最近のトークンを残すことで固定容量を守るが、途中の固有情報を捨てる。H2O、TOVA、SirLLMなどの選択的KV保持も、生成中の過去キャッシュ圧縮を中心に設計される。SnapKVは入力末尾の質問から重要KVを選べるが、長い入力全体を一度保持できることが前提であり、厳格なピークメモリ制約を満たさない。InfiniPotは入力途中から圧縮し、未来が不明でもCaPの代理注意とNuCの予測困難性を併用し、RoPEの位置を毎回再設定する。これらを統合することで、メモリ上限を守りながら長い入力を順次処理する点が主な違いである。

## 限界と適用範囲

第一に、保持数と圧縮率は事前設定であり、情報密度が突然上がった場合に自動的に増やす機構はない。何度も圧縮するため、一度捨てた固有情報は後で回復できない。長期依存の保持についても多様な条件で網羅的な検証は済んでいないと著者らが明記している。

第二に、CaPは質問が分かっている場合と未知の場合で効果が違う。質問付きCaPを使う実験の成績を、未来の質問を一切知らない逐次処理へそのまま外挿できない。NuCの比率50%も特定の実験での選択であり、全モデル・全タスクで最適とは限らない。位置再設定は位置番号を学習範囲へ戻すが、元文書の正確な絶対位置や距離を保持するものではない。

第三に、実験はA100 80GB上でのソフトウェア評価であり、研究の動機となるスマートフォンや組込みNPUの実機では検証されていない。GPU全体のメモリが固定という意味でもなく、KVの保持数を上限化する方式である。最大1Mトークンの成果は合成的な検索課題であり、すべての自然言語理解課題で長さに依存せず高品質を保つ保証ではない。
