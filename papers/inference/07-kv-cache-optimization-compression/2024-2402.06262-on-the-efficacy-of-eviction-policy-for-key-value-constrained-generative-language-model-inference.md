# On the Efficacy of Eviction Policy for Key-Value Constrained Generative Language Model Inference

> RoCoはKV tokenの重要度を累積attentionではなく平均attentionで測り、attention標準偏差で追い出し候補を動的に選び、固定window依存を減らしながらfull-cacheに近い生成品質を保つ。

## 概要

自己回帰LLMは、過去tokenごとに計算済みのkey/valueを **KVキャッシュ（Key-Value cache）** へ保存する。次token生成時に過去全tokenのK/Vを再計算しなくて済む一方、KV容量はlayer数、batch size、sequence lengthにほぼ比例して増える。長文脈や多数requestを扱うと、モデルweight以外にKVだけでも大きなGPUメモリを消費する。

KV容量を固定budgetへ抑える代表的な方法が、過去tokenの一部を追い出す **KV eviction** である。しかし「どのtokenが将来必要か」はまだ生成していないqueryに依存する。そこでH2OやScissorHandsのような手法は過去のattentionを重要度の近似として使い、さらに直近tokenはまだ重要度が定まっていないとしてlocal window内を保護する。

本論文の中心は、既存policyを「重要度scoreの計算」と「eviction候補範囲の作り方」の二つに分けて調べた点にある。累積attentionは、古いtokenほどattentionを受ける機会が多いのでscoreが膨らむ **最近性偏り（recency bias）** を持つ。一方、固定local windowは「新しいtokenは一定stepだけ不安定」という仮定を置くため、window sizeに結果が敏感になる。

提案するRoCo（Robust Cache Omission）は、重要度には **平均attention score（Mean Attention Score; MAS）** を使い、候補範囲にはattention scoreの **標準偏差（standard deviation）** を使う。LLaMA2-7B-chatのAlpacaEvalでは250-token KV budgetでfull cacheのGPT-4 win rate 75.6に対しRoCo 75.5を維持し、prefillのblock-wise evictionではblock size 16で16倍の処理高速化を報告する。

## 問題設定

### KV evictionは「重要tokenを残せばよい」だけではない

理想的には、将来の生成で高いattentionを受けるtokenを残し、使われないtokenを捨てたい。しかし推論時には未来のattention matrixは見えないため、過去までの観測から将来価値を推定する。

ここで累積attentionをそのまま足すと、sequenceの早い位置にあるtokenは多くのfuture tokenからscoreを受ける。一方、最近追加されたtokenは観測回数が少ない。実際の平均的な重要度が同じでも、古いtokenが有利になる。このため「蓄積量」と「1回当たりの重要度」が混ざる。

### 固定local windowにも別の仮定がある

新しいtokenはattention履歴が少ないので、直後に追い出すと判断誤りが起きやすい。そこで既存policyは末尾r tokenを保護し、それより古いtokenだけをeviction候補にすることが多い。

問題は、tokenごとに重要度が安定するまでの時間が同じではないことだ。論文はattention確率の標準偏差を追跡し、多くのtokenが短い上昇期間の後に安定的な下降へ入る一方、その長さが固定ではないと観察する。したがって一律r-step保護より、**各tokenのattentionがどれだけ安定したか**を直接使う方が自然だと考える。

## 手法のあらまし

RoCoは各cached tokenについて二種類の統計を持つ。

1. future tokenから受けたattention確率の **平均** — tokenを残す価値の推定。
2. attention確率の **標準偏差** — その重要度推定がまだ揺れているかどうかの指標。

Evictionが必要になると、まず標準偏差を使って「重要度がまだ不安定なので保護するtoken」と「十分安定して比較できるtoken」を分ける。その候補集合の中から平均attentionが小さいtokenを削除する。つまり **meanで重要度、standard deviationで判断の信頼性** を分担させる。

## 手法

### 1. 平均attention score — token ageによる偏りを減らす

token (i) が後続tokenから受けたattentionを単純加算するのではなく、attentionを受けた回数で割って平均化する。

直感的には、

`importance = これまで受けたattentionの合計 / 観測回数`

である。

これにより100 step存在したtokenと10 step前に現れたtokenを、「積算できた時間」ではなく1回当たりのattentionで比較しやすくなる。入力は既にattention計算で得られる値なので、別の予測modelを学習する必要はない。

論文はfull KV cacheで後から得られるglobal importanceとlocal proxyの一致度を比較し、mean-based scoreが累積scoreより高い整合性を持つことを示す。ここがRoCoの重要度score側の改善である。

### 2. Attention標準偏差 — 固定windowをtoken別の安定度へ置き換える

平均attentionだけで即座にevictすると、新しく入ったtokenは観測数が少なく推定が不安定である。RoCoは各tokenについてattentionの分散・標準偏差も逐次更新する。

標準偏差が大きいtokenは、「今は平均値が低く見えても、まだattention挙動が揺れている」と解釈して保護する。逆に標準偏差が低いtokenはimportance推定が比較的安定しているため、eviction候補へ入れやすい。

この設計では「直近64 tokenを必ず残す」のような位置だけのルールではなく、古さに関係なく各tokenのattention統計から候補範囲を作る。その結果、local-window sizeという追加hyperparameterへの依存を減らせる。

### 3. Eviction時の流れ

KV budgetに空きがある間は新しいK/Vを通常通り追加する。budgetが満杯になり新tokenを保存する必要が出ると、RoCoは現在のcached tokenのmeanとstandard deviationを参照する。

まずattentionがまだ不安定なtokenを保護し、残る安定tokenからmean attentionが最小のものをevictする。削除後は新tokenをcacheへ加え、生成が進むたび既存tokenのmean/std統計を更新する。

出力は「圧縮されたKV cache」であり、モデルweightやattention演算式自体は変えない。したがって計算節約の代償は、消したtokenへ将来queryが強くattentionした場合の品質低下として現れる。

### 4. Prefillとdecodeの両方を扱う

自己回帰decodeでは1 tokenずつKVが増えるので、その都度または一定間隔でevictionできる。長いpromptのprefillでは全tokenを一度に処理するため、1 token単位の細かいevictionは管理costが大きい。

EasyKVはprefill向けにblock-wise evictionを実装し、複数tokenをまとめて処理する。block sizeを大きくするとeviction判断回数を減らせるため高速になるが、一括処理が粗くなるので生成品質との交換条件が生じる。論文のTable 6ではblock sizeを1→2→4→8→16と増やしたとき処理speedupは概ね1×→2×→4×→8×→16×となる一方、BLEU/ROUGE-2はわずかに低下する。

## 評価

### まず見るところ

- **評価stage:** prefillと自己回帰decodeの両方。
- **task:** 言語モデリング、要約、context reconstruction、instruction following。
- **model:** LLaMA2、WizardLM、Zephyr系を含む。
- **比較policy:** Random、StreamingLLM系recency、ScissorHands、H2O、TOVAなど。
- **AlpacaEval:** LLaMA2-7B-chatで250-token budget時、full cache 75.6に対しRoCo 75.5。
- **要約:** 250-token budgetのinstruction-following評価でRoCoが既存policyを上回る。
- **Prefill効率:** block size 16で16×、品質低下は小さいという結果。
- **実装:** EasyKVを公式公開。

### 代表的な結果

| 条件 | 指標 | RoCo | 比較 | 読み取れること |
|---|---:|---:|---:|---|
| LLaMA2-7B-chat、250-token KV budget、AlpacaEval | GPT-4 win rate | 75.5 | full cache 75.6 | 厳しい固定budgetでもfull-cache品質に近い |
| 同系のAlpacaEval評価 | win rate | 66.3 | H2O 63.0、ScissorHands 62.1、TOVA 60.1 | eviction policyの差がinstruction品質へ出る |
| LLaMA2-7B-chat | ROUGE-L | 72.5 | H2O 69.9、TOVA 68.3 | token保持判断が長文生成品質へ反映 |
| Prefill block-wise eviction、block=16 | 処理speedup | 16.0× | block=1を1.0× | 判断粒度を粗くするとprefill overheadを大幅削減 |
| 同条件 | BLEU / ROUGE-2 | 40.2 / 45.4 | block=1: 41.2 / 46.2 | 高速化には小さな品質低下が伴う |

ここでAlpacaEvalの75.5は、Table 5でfull KV cache平均75.6に対する値である。別表の66.3などは異なる設定の比較なので、同じ数字として混ぜない。

### 何を証明しているか

Mean attentionの評価は「累積scoreのrecency biasを減らす」機構を検証し、standard deviationを用いるscope評価は「固定local windowよりwindow-size変化へrobust」という主張を検証する。最終task評価では、この二つを組み合わせたRoCoが単なるproxy改善に留まらず生成品質へつながるかを確認している。

一方、主目的はKV **容量制約下の品質維持**であり、vLLM等のproduction servingで同時request数やP99 latencyが何倍改善するかを示す論文ではない。block-wise prefillの16×もeviction処理粒度に関する値で、LLM end-to-end generationが16×になるという意味ではない。

## 既存研究との差

H2Oはheavy-hitter tokenを累積attentionで残す考え方を持つが、RoCoはその累積値にtoken age biasがある点を分析対象にし、平均attentionへ置き換える。

ScissorHandsなどlocal-windowを併用する方式に対しては、「最近のtokenを一定数必ず残す」という位置ベースの保護を、attention variabilityというtoken固有の統計へ置き換える。したがってRoCoの新規性は新しい巨大predictorではなく、**importanceとconfidenceを別統計へ分離したtraining-free eviction rule** にある。

EasyKVはRoCoだけでなくrandom、recency、H2O系などを同じinterfaceで切り替え、prefill / decode / auto modeを扱えるため、policy比較用の実装基盤としても使える。

## 限界・実装状況

RoCoは過去attentionが将来重要度を予測するという前提に依存する。evictしたtokenのK/Vは失われるため、後になってそのtokenが重要になっても完全cacheと同じ出力を保証する方式ではない。

Budgetが極端に小さい場合や、長距離依存を持つtaskでは品質劣化が大きくなり得る。標準偏差による保護も未来を直接見ているわけではなく、「統計が安定したtokenなら平均scoreで判断しやすい」というheuristicである。

また論文評価は主に単一model生成品質とprefill処理を対象とし、continuous batching、prefix sharing、paged KV、multi-tenant servingと組み合わせたGPU memory fragmentationやtail latencyは主評価ではない。

公式実装EasyKVは公開されており、LLaMA/LLaMA2/Mistral、MHA/MQA/GQA、prefill/decodeを扱う。ただしproduction runtimeへそのまま統合した場合のkernel efficiencyは別途評価が必要である。

## 一般的な実装上の含意

KV evictionではscore式だけでなく、「どのtokenを比較対象へ入れるか」が同程度に重要である。新tokenを一律windowで守るより、scoreの不確実性を別統計として持つ設計は、他のcache policyにも適用できる。

また累積統計をimportanceへ使う場合は、観測回数そのものがscoreへ混ざっていないか確認する必要がある。RoCoのmean化は単純だが、token ageとimportanceを分離するという意味で再利用しやすい。
