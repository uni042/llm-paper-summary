## 概要
検索拡張生成 (retrieval-augmented generation; RAG) では、検索した複数文書を毎リクエスト長い文脈として再度プリフィルすると、長文脈ほど注意計算が支配的になる。文書ごとに事前計算したキー・値キャッシュ (key-value cache; KV cache) を再利用すれば計算は省けるが、各文書を単独で計算したKVには他文書や今回のユーザー質問との交差注意 (cross-attention) が入っていない。単純なKV連結ではこの「意味的断絶」が残り、全再計算に比べ精度が落ちる。

ProphetKVは、限られた再計算予算を文書中のすべてのトークンへ均等に使うのではなく、**今回のユーザー質問が実際に強く参照する文脈トークン**へ集中させる。第1段階で質問トークンから既存KVへの注意だけを軽量に計算し、全層の重要度を融合する。第2段階で融合スコア上位の文脈トークンだけを全層にわたり完全再計算する。こうして質問に必要な交差注意を優先的に修復し、20%程度の再計算で全プリフィルに近い品質を狙う。

## 問題設定
位置非依存の文書KV再利用では、文書 (d_i) のKVを他文書や質問から切り離して事前計算する。このKVは同じ文書を異なる検索順位・組合せでも使い回せる一方、本来のフルプリフィルなら生じる文書間・質問→文書の注意関係を欠く。既存の部分再計算法はKVの大きさや低層情報から重要トークンを選ぶが、深層で初めて重要になるトークンを見落としやすい。

さらに、各層のKVを正確に見てから重要度を決めようとすると、層 (l) のKVを得るために層 (l-1) まで全文脈を計算しなければならない。全層でこれを行うと、回避したかったフルプリフィルを事実上実行する「選択のデッドロック」が生じる。ProphetKVは短い質問列だけを各層へ通し、既存の文書KVを参照することで、この循環を避ける。

## 手法
### 質問注意を重要度の代理にする
論文は、生成時に実際に注意される文書トークンと、事前のユーザー質問が注意するトークンの重なりが高いことを実測する。位置 (t) の文脈トークンに対し、質問トークン群からそのキーへ向かう平均注意量を価値関数の実用的代理 (alpha_l(t)) とする。これは「全生成過程を先に実行しなければ分からない重要度」の代わりに、生成前から観測できる信号である。

この選択信号が効く理由は、位置非依存KVの誤差が単なるKV数値誤差ではなく、今回の質問に必要な交差注意の欠落として現れるからである。質問がほとんど参照しないトークンを正確に再計算しても最終出力への寄与は小さい一方、質問が強く参照するトークンのKVを修復すれば、同じ再計算数で意味的損失をより大きく減らせる。

### 第1段階: 全層の軽量重要度収集
全文脈を再プリフィルせず、短いユーザー質問だけをTransformerの全層へ通し、各層で質問トークン→既存文書KVの注意重みを計算する。層ごとに注意行列の列和から各文脈トークンの (alpha_l(t)) を得る。この計算量は各層で (O(|Q|	imes s)) で、質問長 (|Q|) が文脈長 (s) より十分短いRAGでは、文脈全体の (O(s^2)) 注意をやり直すより軽い。

注意重みは各層で正規化されているため、ProphetKVは層ごとの値を一様平均し、
(ar{alpha}(t)=L^{-1}sum_lalpha_l(t))
という1本の大域重要度へ融合する。低層だけで代表させず全層を観測することで、深層で意味的重要性が現れるトークンも候補へ残す。

### 第2段階: 固定上位集合の完全再計算
融合スコア (ar{alpha}(t)) の上位 (k) トークンを再計算集合として選び、そのトークンについては全Transformer層を通して完全に再計算する。選択集合を層間で固定するため、各層でテンソル形状が変わらず、GPUでのスループットやカーネル利用を損ないにくい。更新されたKVだけを事前計算キャッシュへ反映し、残りは再利用する。

この二段階化により、第1段階は「どこを直すか」を低コストで予測し、第2段階は「選んだ場所を正確に直す」役割を担う。再計算率を下げすぎると重要トークンを取り切れず品質が落ち、逆に上げるほど全再計算へ近づいて速度利得が減る。

## 評価条件
| 観点 | 条件 |
|---|---|
| モデル | Llama-3.1-8B-Instruct、Qwen2.5-14B-Instruct、Qwen3-14B |
| GPU | NVIDIA A100、H100、L20の異種クラスタ |
| ベンチマーク | RULER（主に8K文脈）、LongBench |
| 文書分割 | LangChainで512トークン区間 |
| 比較対象 | CacheBlend、KVShare、EPIC、再計算なしのNaive Reuse、全再計算 |
| 実装 | Hugging Face Transformers。特定CUDAカーネル差を避け、アルゴリズム差を比較 |
| 主な効率指標 | 初回トークン時間 (time to first token; TTFT) |
| 主設定 | 文脈トークンの20%を再計算 |

## 主要結果
20%再計算時、Llama-3.1-8B-Instructでは全再計算のRULER平均88.82に対しProphetKVは84.71、LongBenchでは50.19に対し50.80である。Qwen2.5-14B-Instructでは90.28→88.60、54.86→53.43、Qwen3-14Bでは91.79→89.89、61.06→59.52となる。すべての個別タスクで完全一致するわけではないが、平均ではフルプリフィルにかなり近い品質を20%計算で回復している。

同じ20%予算で、論文は既存の最良法に対する精度改善をRULERで8.8%〜24.9%、LongBenchで18.6%〜50.9%と報告する。特に複数値・複数質問のように、干渉する長文脈から質問に対応する箇所を正確に拾うタスクで差が大きい。これは質問注意を選択信号に使う機構と、必要箇所だけを再計算する品質回復の対応を示す。

H100上の16K文脈では、Llama-3.1-8B-InstructのTTFTが全再計算5.23秒、ProphetKV 1.13秒、CacheBlend 1.29秒、EPIC 1.08秒である。Qwen2.5-14B-Instructでも9.94秒→2.12秒、Qwen3-14Bでも8.70秒→1.84秒となる。8K〜16Kでは全再計算比で最大約5倍まで短縮する一方、4Kでは固定的なカーネル起動・キャッシュ管理費の割合が増え、全方式で同じ倍率は得られない。つまり長文脈ほど部分再計算の計算削減が壁時計時間へ反映されやすい。

構成要素除去実験 (ablation) では、理想的なオラクル情報を使って各選択基準だけを比較すると、理想価値関数が再計算率約0.02で収束するのに対しProphetKVは約0.04、CacheBlendは約0.06を必要とする。論文はこの差を選択収束速度約33%改善と解釈している。また再計算率を掃引すると、ProphetKVは10%〜30%再計算で精度低下を5%未満に抑えるのに対し、比較法は同程度の回復に40%〜80%を要する場合がある。区間サイズ (chunk size) を小さくすると全方式が悪化し、512トークン以上ではProphetKVがほぼ損失なしへ近づく。小区間ほど欠落する区間間注意が増えるためである。

## 既存研究との差
CacheBlendやKVShareのように低層のKV統計から「一般に重要そうなトークン」を選ぶ方式に対し、ProphetKVは**そのリクエストの質問**を選択条件にする。また低層の重要度を全層へ流用せず、質問→文書KV注意だけを全層で軽量に測ってから融合するため、層ごとの意味変化を扱いつつフルプリフィルを避ける。

## 限界
効果は「質問長が長大な文脈より十分短い」というRAGの典型条件を利用しており、質問自体が非常に長い場合は第1段階の (O(|Q|	imes s)) 費用が増える。再計算率が小さすぎる、区間が細かすぎて区間間注意の欠落が増える、あるいは質問注意が最終生成時の重要度をうまく予測しない入力では品質利得が縮む。20%設定でも全再計算を常に再現するわけではなく、タスクごとの残差はある。また論文の実装比較はHugging Face Transformers上でアルゴリズム差を隔離しており、FlashAttention等の特定高速カーネルを組み込んだ本番サービング基盤での絶対TTFTは別途評価が必要である。
