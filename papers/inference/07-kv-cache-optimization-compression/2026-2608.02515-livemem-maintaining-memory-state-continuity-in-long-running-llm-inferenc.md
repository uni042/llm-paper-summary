# LiveMem: Maintaining Memory State Continuity in Long-Running LLM Inference

> 有界KV窓とは別に固定容量の再帰状態を各層へ持たせ、退避済み履歴の影響を長時間エージェント推論へ継続させる内在メモリ方式。

## 概要

長時間動く助手やエージェントでは履歴が文脈窓を超える。古い文章を検索できる検索拡張生成（RAG）や要約は「必要になった情報を後から再構成する」仕組みだが、作業文脈が入れ替わるたびにモデル内部の計算状態を連続して持ち越すものではない。LiveMemはこの問題を**文脈交代下の状態連続性**として定義する。

LiveMemは事前学習済み全注意LLMの各層へGated DeltaNet-2（GDN2）の再帰メモリ枝を追加する。通常注意はsystem promptと最近のチャンクだけを固定容量KV窓に残し、古いチャンクを先入れ先出しで退避する。一方GDN2は履歴を固定サイズの状態行列 `S_t` へ逐次圧縮し、退避後もその状態を保持する。現在queryは `S_t^T q_t` で過去状態を読み、結果を通常注意出力へ加える。

単に枝を付けるだけではモデルがそれを無視するため、文脈交代を実際に起こすメモリ指向の教師あり微調整（SFT）と強化学習（RL）を行う。LongMemEvalでは根拠文が現在の注意窓から完全に退避された条件でもメモリ状態から回答できる例を示し、証拠距離64K付近でも情報利用が残る。一方、この状態は損失圧縮であり、任意文字列の正確なneedle検索を置き換えるものではない。

## 問題設定

有界KVキャッシュだけなら古いトークンを捨てた瞬間にその情報への直接経路がなくなる。外部検索は必要な履歴を再挿入できるが、検索queryを発行する前から継続していた潜在状態を持つわけではない。

再帰状態を追加しても、学習中に答えが常に通常注意窓へ残っていれば、損失は主経路だけで下がり、メモリ枝は使われない。LiveMemでは「古いチャンクを実際に退避した状態で答えさせる」訓練とサービング規則を揃え、再帰状態を負荷を担う経路にする必要がある。

また固定状態は履歴長に比例して容量を増やせない。したがって完全な記録ではなく、将来予測に有用な特徴を残し、不要情報を忘れる機構が必要になる。

## 手法

### GDN2状態更新

各層のメモリ状態を行列 `S_t` とする。まず学習した対数減衰ゲート `g_t` により、以前の状態を行方向に減衰させる。次にerase gate `b_t` とkey `k_t` で既存の対応を消し、write gate `w_t` とvalue `v_t` から新しい関連を作る。

概念的には、古い関連を `S_t^T(b_t ⊙ k_t)` で読み出して差し引き、新しい `k_t ρ_t^T` を状態へ加える。現在queryに対する読み出し `r_t = S_t^T q_t` は通常attention outputへ加算される。状態サイズは履歴トークン数に依存しない。

### 文脈交代

入力をチャンクへ分割し、主注意側はsystem instructionをattention sinkとして固定しつつ、最近チャンクのFIFO窓だけを保持する。容量を超えると最古チャンクのKVを解放する。

解放前にそのチャンクはGDN2状態を更新済みなので、古いトークンそのものは主注意から見えなくなっても、その影響はSに残る。この「KVを捨てた後に唯一残る経路」を意図的に作ることで、メモリ枝を状態連続性の担い手にする。

### メモリ指向post-training

backboneを凍結し、まず長文QAでメモリ枝を起動する。続くSFTでは複数質問、会話、分類等を混ぜ、古い証拠が窓外へ出る文脈交代を学習中にも適用する。

その後のRLでは回答精度を報酬にし、固定容量状態の中で何を残し何を忘れるかを調整する。学習時に退避を経験させることが、単なる追加branchを実際の推論経路へ変える鍵である。

### サービング状態

要求ごとに最近のKV窓と固定サイズのGDN2状態を保持する。履歴が増えてもGDN2状態の容量は増えないため、長時間セッションの状態メモリを履歴長から切り離せる。

ただし主attentionはbackboneの位置表現を使い続ける。再帰状態が無限に更新可能でも、現在実装の実用文脈長はbackbone側の位置外挿能力にも制約される。

## 評価条件

| 項目 | 内容 |
|---|---|
| backbone | Qwen3-4Bを中心とする全注意LLM |
| 学習 | backbone凍結、memory side pathをSFT + RL |
| 文脈管理 | system prompt保持 + FIFOチャンク退避 |
| 主評価 | LongMemEval、Wiki QA、会話、長文QA、test-time learning |
| 比較 | base/truncation、RAG、他の内在メモリ方式 |
| 重要分析 | evidence eviction、evidence distance、state-vs-truncation |
| 性質 | 固定容量・損失型の内部状態 |

## 主要結果

| 条件 | 指標 | 結果 | 読み取れること |
|---|---|---:|---|
| LongMemEval、根拠が完全退避 | 正答能力 | baseより明確に残存 | KV窓外の情報が状態経路から利用される |
| evidence distance | 利用可能距離 | 64K付近でも効果 | 最近窓だけでは説明できない持続性 |
| 複数タスク総合 | overall | 評価した内在メモリ方式で上位 | 状態連続性が複数用途へ移る |
| needle型正確検索 | 品質 | 弱い | 固定状態は損失圧縮で完全アーカイブではない |

論文の主張は「外部検索より常に高精度」というものではなく、検索と異なる内部状態の連続性を提供することにある。正確な古い文字列の復元が必要な用途ではRAG等との併用が自然である。

## 既存研究との差

RAGは過去データを外部に保持し、現在queryに応じて必要箇所を再挿入する。LiveMemはqueryに依存せず全履歴を固定状態へ逐次反映し、現在文脈が変わっても潜在状態を連続させる。

δ-Mem等の内在メモリ方式に対しては、通常注意の有界KV窓と再帰side pathを明示的に併用し、訓練時から古いチャンクを退避して「状態がなければ答えられない」条件を作る点を重視する。

## 限界

固定状態は損失圧縮なので、needle-in-a-haystackのようなランダム文字列・完全一致検索には弱い。完全な履歴保存が必要なら外部アーカイブを併用する必要がある。

現在の実装はbackboneの位置符号化上限を引き継ぐため、状態自体の寿命とモデルが処理できる絶対位置範囲は同じではない。またSFT時とサービング時のチャンク境界が完全に同一ではない評価条件があり、この差への感度は十分に分離評価されていない。
