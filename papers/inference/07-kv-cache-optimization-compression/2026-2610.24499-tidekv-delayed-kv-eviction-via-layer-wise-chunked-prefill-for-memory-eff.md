# TideKV: Delayed KV eviction via layer-wise chunked prefill for memory-efficient long-context LLM inference

> プリフィルを層優先に並べ替えて各層の完了まで追い出しを遅らせ、層末圧縮を二度走査で省メモリに実行することで、選択の質と最終キャッシュを保ったまま構築ピークを最大83.89パーセント削減する方式。

## 概要

長文脈の推論でメモリを圧迫するのは、デコード中に保持するキーと値のキャッシュだけではない。入力プロンプトを処理するプリフィルの最中には、全層分の未圧縮キャッシュに加えて、全系列分の隠れ状態、中間の活性値、注意のスコア行列が同時に居座る。論文の例では、約80億パラメータのモデルで128Kトークンのプロンプトが作る未圧縮キャッシュだけで約16ギガバイトに達し、他の構成要素と合わせると組み込み向け装置の容量を容易に超えてメモリ不足で落ちる。最終的に残すキャッシュをいくら小さく設計しても、構築の途中のピークが装置に収まらなければ推論は始まらない。

既存の圧縮方式は二つの流派に分かれ、どちらも半分だけ正しい。全プロンプトを処理してから層ごとに選択して圧縮する方式は、選択の時点で全プロンプトを見渡せるため質を保てるが、各層が全系列を一度に処理する以上、構築ピークは高いままである。逆に、プロンプトを断片ごとに処理しながら逐次追い出す方式はピークを早く下げられるが、捨てる対象を決める時点で後半の文脈がまだ存在せず、後から重要になるトークンを早々に捨てる近視眼的な選択になる。視界と滞留はトレードオフに見えるが、論文はこれが実行順序の問題であることを示す。

提案は、プリフィルの実行順序を断片優先から層優先へ並べ替える。通常は各断片が全層を通るのに対し、提案では1つの層が全断片を処理し終えてから次の層へ進む。各層の中では断片が因果順に処理され、その層の未圧縮キャッシュに対して注意を向けるため、層の中での見え方は全プロンプト実行と変わらない。層が終わった時点で初めて、その層のキャッシュを選択器で予算まで圧縮し、未圧縮分を解放する。この結果、未圧縮キャッシュが居座るのは処理中の1層だけになり、一時的な活性値は1断片分に限られ、全系列分の隠れ状態が層間をつなぐ橋として残る。代表結果として、データセンター向け装置での64K文脈の測定では、構築時の一時メモリが7.281ギガバイトから1.173ギガバイトへ83.89パーセント減り、最終キャッシュと構築後の定常メモリは比較対象と完全一致した。消費者向け装置では64Kでプロセス全体のピークが26.47パーセント減って初回トークンまでの時間の増加は1.06パーセントにとどまり、128Kでは比較対象がメモリ不足になる一方で提案は18.529ギガバイトで完走した。組み込み向け装置でも、比較対象が64Kから既に失敗する条件で128Kまで完走している。

## 問題設定

この問題は、残す対象を決める選択の問題と、どの順序で実行し、いつ追い出しを効かせるかという日程の問題を分けることで見通しがよくなる。選択器はトークンの重要度の規則であり、日程はその規則をどの情報のもとで、いくらのメモリを使って適用するかである。従来の議論は選択器の改良に集中し、日程は全プロンプト実行か逐次追い出しの二択が暗黙の前提だった。

メモリの内訳を分解すると、ピークを決めるのは最終キャッシュではない。構築中のピークは、滞留するプロンプトのキャッシュ、全系列の隠れ状態の橋、処理中の活性値、圧縮のための一時領域の合計であり、これにモデルの重みや実行基盤の作業領域や割り当て器の保持分が乗る。全プロンプト実行では活性値が全系列分に膨らみ、素朴な層末圧縮では観測窓と全接頭辞のスコア行列が一時領域を支配する。つまり、滞留キャッシュだけを絞ってもピークは下がり切らない。提案の狙いは、最終キャッシュの大きさを一切変えずに、この構築中の作業集合の方を、順序の並べ替えと圧縮手順の省メモリ化で削ることにある。評価でも、割り当て量、割り当て器が予約した量、プロセス全体で見た量を分けて測り、どの層で削減が実現しているかを区別している点が、この問題設定と対応している。

## 手法のあらまし

処理は層を外側、断片を内側とする二重の輪である。各層では、入力の隠れ状態の断片が因果順に処理され、その層の未圧縮キャッシュが蓄積していく。後の断片は、それまでの全断片に対する未圧縮の履歴を見て注意を計算するため、層内では全プロンプト実行と同じ情報が保たれる。観測窓となる最後の問い合わせは別に保持される。全断片が終わると層末の圧縮が走る。圧縮は、観測側の問い合わせと接頭辞のキーのスコアをブロック単位で二度走査する方式で、最初に正規化のための統計を蓄積し、次に正規化済みの重みからトークンごとの重要度を作って上位を残し、必須の直近トークンや先頭の注目トークンを加えて予算ちょうどの集合を作る。スコア行列そのものは実体化されないため、圧縮の一時メモリはプロンプト長に依存しない。圧縮済みキャッシュと絶対位置の情報を確定させ、未圧縮分を解放してから次の層へ進む。完了した層は圧縮済みキャッシュだけを持ち、未来の層は何も持たない。全層が終わると、圧縮済みの初期キャッシュがデコードへ渡され、生成は短くなったキャッシュ長ではなく元の絶対位置から再開される。選択器と層ごと・注意頭ごとの予算配分は差し替え可能であり、日程の不変条件とは独立に選べる。

## 手法

### 1. 層優先の遅延追い出し — 未圧縮は1層だけ、活性値は1断片だけ

中核の不変条件は単純である。どの瞬間でも、未圧縮の全プロンプト分のキャッシュが存在するのは処理中の1層だけで、一時的な注意と中間層の活性値は1断片分に限られ、完了した層は圧縮済みキャッシュだけを保持する。通常の実行では断片が全層を通るため、未圧縮キャッシュは全層分が同時に育つ。これを層優先へ反転させると、未圧縮キャッシュの滞留は層数倍から1層分へ落ちる。隠れ状態は断片のスロットを使い回す橋として全系列分が残るため、この項は線形のまま残るが、活性値の項は断片と全系列の比で縮む。重要なのは、層内では後の断片が未圧縮の履歴全体を見るため、選択の前に履歴が圧縮されることが決して起きない点である。追い出しは隠れ状態の確定後に効くため、その層が作った表現そのものは圧縮の影響を受けない。誤って捨てる危険は選択器側の性質に帰着し、日程の変更は追加の近似を持ち込まない。代償として、隠れ状態の橋の読み書き、層境界での同期、断片の起動回数の増加といった実行上の費用が増え、初回遅延との交換条件になる。

### 2. 省メモリな層末圧縮 — スコア行列を作らない二度走査

層末の圧縮自体がピークを作っては元も子もない。素朴な実装は、観測窓の全問い合わせと全接頭辞キーのスコア行列を実体化し、その大きさはプロンプト長に比例して構築ピークを支配しかねない。提案の圧縮手順はキーをブロックへ分け、二度の走査で処理する。一度目は、ブロックごとの最大値の更新と指数和の蓄積で、正規化に必要な統計だけを保持しながら数値的に安定な形で走査する。二度目は、正規化済みの重みを再計算してトークンごとの重要度へ集約し、必須集合を除いた残りの枠について上位を保持する小さな山積み構造で選び抜く。保持するのはブロック1個分と統計と選択結果だけであり、一時メモリはブロック大きさと予算で決まり、プロンプト長から切り離される。同じスコアを二度計算する分の演算は増えるが、それは初回遅延の内訳として実測され、報告されている。注意頭の共有があるモデルでは、重要度をキーと値の頭の単位へ集約してから選択し、保持位置を頭の組の中で共有することで、圧縮後の配置の整合を保つ。

### 3. 予算配分と選択器の差し替え可能性

日程は選択の規則から意図的に切り離されている。観測窓で接頭辞を採点する方式、直近を残す方式、層や頭ごとに予算を変える方式など、層末で全履歴を見て決める形の選択器であれば同じ枠組みで動く。予算は層ごとに一様にも、圧縮の難しい層へ厚くにも配分でき、頭ごとの配分では長さの異なるキャッシュを平坦な配置と頭ごとの開始位置で保持する。論文は4系統の選択器を同じ枠組みで評価し、いずれも対照との品質差が小さいことを確認している。裏を返せば、構築中に履歴を書き換える前提の選択器や、別のキャッシュ表現を要求する方式は、そのままでは組み込めず追加の適応が要る。この境界は論文も明示している。実装は、層と断片の輪を回す日程係、層末の圧縮器、層をまたぐキャッシュ管理、デコードへの接続部、メモリの会計係からなる参照実装として構成され、注意や正規化や中間層の演算そのものは既存の融合カーネルをそのまま使う。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 層優先の日程 | 断片化された入力と層の列 | 1層が全断片を終えてから次層へ進み、層境界でのみ圧縮する | 未圧縮キャッシュと活性値の滞留 | 橋の読み書きと境界同期の増加 |
| 遅延追い出し | 層の未圧縮キャッシュ全体 | 全プロンプトを見た後に選択器で予算まで圧縮し、未圧縮分を解放する | 選択の近視眼性 | 圧縮が終わるまで1層分の滞留は残る |
| 二度走査の圧縮 | 観測窓の問い合わせと接頭辞キー | 正規化統計と重要度をブロック単位で作り、スコア行列を実体化しない | 圧縮の一時メモリ | スコアの再計算による演算増 |
| 予算配分 | 層と頭の圧縮しやすさ | 予算を層ごと頭ごとに配分し、保持集合の大きさを予算ちょうどに保つ | 品質とメモリの釣り合い | 配分の設計が品質に直結する |

生成開始までの流れを通すと、入力は断片に分かれて層ごとに橋を書き換えながら進み、各層の終わりで圧縮済みキャッシュが1層分ずつ積み上がり、最後にそれらが初期キャッシュとしてデコードへ渡る。デコード側から見れば、得られるものは通常の圧縮で得る初期キャッシュと同等であり、違いは構築の過程のメモリの山の形だけである。

## 評価

### まず見るところ

結論は、順序の変更が最終キャッシュと品質を変えずに構築ピークだけを削ること、そしてその削減が装置の実行可能範囲そのものを広げることである。品質については、同じ選択器と同じ予算での対照で、下流課題のスコア差がほぼ誤差の範囲に収まり、表現のずれも通常の断片化が持ち込む数値誤差の床と一致した。速度については無償ではなく、初回遅延の増加と引き換えであり、増加率は装置と文脈長で大きく違う。評価は3種の実機で行われ、割り当て器や注意の実装を変えた頑健性の確認、150件の連続要求での安定性まで含む点が手厚い。一方で、対象は単一要求、約80億パラメータ級の2モデルが中心であり、連続バッチ処理や大規模サービングへの統合は今後の課題として残されている。

| ハードウェア | データセンター向け装置（40ギガバイト）、消費者向け装置（24ギガバイト）、組み込み向け統合装置（64ギガバイト、低消費電力の動作形態） |
| モデル／モデル規模 | 約80億パラメータ級の指示調整モデル2種、16ビット浮動小数点系 |
| 精度形式 | 重みと計算は16ビット系、最終キャッシュの物理予算は標準で4096トークン（512メガバイト相当） |
| ランタイム／実装 | 公開推論基盤上の参照実装、注意は高速な融合実装が主経路 |
| データセット／ワークロード | 長文脈の理解課題集（16課題）と、制御された検索・集約課題集（4Kから128K、長さごとに100例） |
| バッチ／同時要求数 | バッチ大きさ1、断片の大きさは標準で2048トークン |
| 入力長／出力長／文脈長 | 文脈長は8Kから128K、遅延の測定は32トークン生成 |

重要な前提として、全ての対照はモデル、プロンプト、精度、選択器の設定、物理予算、デコード設定、注意の実装、割り当て器、測定手順を一致させてある。したがって差は日程の変更だけに帰着する設計である。

### 主な比較対象

| 比較対象 | 方式・比較上の意味 |
|---|---|
| 選択器対照（全プロンプト後に圧縮） | 同じ選択器を通常順序で適用したもの。日程変更の純粋な効果を測る主対照 |
| 逐次追い出し方式 | 構築中に予算へ合わせて追い出す方式。視界を犠牲にピークを下げる流派の代表 |
| キャッシュ量子化方式 | 残す要素の精度を下げて小さくする方式。要素を捨てる提案とは別の圧縮軸 |
| 頭ごとの退避方式 | 注意頭の単位でホスト側へ退避する方式。ピークは下げるがデコード速度を犠牲にする |

### 感度・スケーリング・ストレス条件

文脈が長いほど削減率は上がり、8Kでは割り当て量で3.74パーセント減にとどまるものが、64Kでは26.85パーセント減、128Kでは41.26パーセント減に達する。短い文脈ではピークに占める構築分の割合が小さいため、提案の旨みは長文脈に集中する。隠れ状態の橋と処理中層のキャッシュは文脈長に比例して残るため、削減にも上限があり、128Kから先やバッチを増やした条件では再び壁に当たる可能性を論文も認めている。

### 立ち上がり・内部挙動

履歴を学ぶ仕組みはないため立ち上がりの問題はない。内部挙動としては、即時追い出しの対照では断片が進むほど表現のずれが蓄積するのに対し、提案では最後まで床の水準に留まることが、ずれの推移でも示されている。

## 既存研究との差

全プロンプト後に選択する方式は、選択の質と引き換えに構築ピークを放置してきた。逐次追い出しの方式はピークを下げるが、選択の視界を犠牲にした。活性値を分割する方式や退避する方式はピークを下げるが、未圧縮のデコード用キャッシュを残したり、ホストとの転送費用を払ったりする。本論文の差は、選択器を改良するのではなく実行の日程を組み替え、視界とピークとオンデバイス完結を同時に満たした点にある。選択器と日程を分離したことで、既存の選択器の蓄積をそのまま取り込める設計になっており、圧縮研究の成果と直交する層の貢献として位置づけられる。

## 限界・実装状況

- 隠れ状態の橋と処理中層のキャッシュは文脈長に比例して残るため、削減には上限がある。論文自身が、より大きなバッチと128K超での評価を今後の課題としている。
- 初回遅延は増える。増加率は条件により1.06パーセントから16.74パーセントまで開き、初回応答の厳しい用途では採用できない条件があり得る。
- 統合先は参照実装の段階であり、連続バッチ処理、接頭辞の再利用、図実行、分散サービングとの統合は将来課題として挙げられている。本番のサービング基盤へそのまま入る完成度ではない。
- 履歴を圧縮せずに保持する前提の選択器など、層末で全履歴を見て決める形でない方式は追加の適応なしには組み込めない。
- 評価は3種の実機で行われたが、いずれも単一装置であり、複数装置の並列実行との干渉は未評価である。コードは要請に応じた提供とされ、公開リポジトリの案内は確認できなかった。

## 一般的な実装上の含意

最終状態の大きさと、そこへ到達する過程のピークは、別々に設計し別々に測る必要がある。多くのメモリ最適化は最終状態だけを見ており、構築や移行の過程の山が実行可否を決める場面では不十分である。また、近似の追加なしに順序の並べ替えだけで得られる削減は、品質リスクを伴わないため採用の順序として先に検討すべきであり、評価では割り当て量、予約量、プロセス量を分けて、削減がどの層に現れたかを確認する姿勢も再利用できる。
