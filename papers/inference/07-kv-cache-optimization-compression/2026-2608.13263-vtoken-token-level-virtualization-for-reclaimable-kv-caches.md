## 概要

大規模言語モデル（LLM）の推論では、過去トークンの鍵・値（KV）キャッシュが系列長と同時要求数に比例して増える。ページ化注意（PagedAttention）は固定長ブロックを非連続配置して外部断片化を抑えるが、H2OやScissorhandsなどの削除方策は「残すトークン」をブロックより細かい単位で選ぶ。このため、16トークン入りのブロックで15個を論理削除しても、残る1個のために物理ブロック全体を解放できない。vTokenは削除方策と物理配置の間に論理トークン表を置き、生存トークンを非同期で詰め直してブロックを返却する仕組みを提案する。

単一のNVIDIA H100（80 GB）で、同じトークン削除判断を行う単純削除実装（Naive-Evict）と比較した結果、保持KVブロック数は27.2～72.3%減少し、遅延のサービス水準（SLA）を守る選択点で処理量は最大1.37倍となった。制約されたKVブロック予算で実行可能な同時要求数は、実験条件によって5→8、11→22、3→6へ拡大した。一方、共有接頭辞を使わない条件では、表1に処理量2.9%低下と95パーセンタイル遅延2.9%増加も報告される。したがって常時高速な方式ではなく、KV容量が律速となる条件で効くメモリ管理層である。

## 問題設定と既存方式

ページ化注意では各要求の論理ブロック表から物理GPUブロックを引き、注意カーネルが固定長ブロック内のKVを参照する。ブロック全体を単位として確保・解放するため、別要求へ渡せるのは完全に空いたブロックだけである。トークン重要度に基づく削除ではブロック内の一部だけが無効化され、解放可能なブロックが少なくなる。論文はブロックbの生存数n_bとブロック容量Sを用い、内部断片化率を F = 1 - Σn_b/(N S) と定義する。16KトークンのLlama-3.1-8B、ShareGPT/LongBench、バッチ16の予備測定では、割当ブロックの多くが利用率50%以下となり、内部の無駄は40～60%に達した。

ブロックサイズを16から4や8へ縮小すれば穴は小さくなるが、管理情報、アドレス変換、非連続KV転送の負担が増える。反対にトークンごとにGPUメモリを直接割り当てる方式は、割当粒度と注意カーネルの連続アクセス前提に合わない。既存のH2OやRandomは削除すべきトークンを選ぶ「方策」であり、削除されたトークンが占めていた物理スロットを別要求へ再利用可能にする「実行時管理」を提供しない。vTokenの新規性は重要度スコアそのものではなく、この方策とブロック管理を分離する境界にある。

## 手法：論理トークンと物理KVの分離

### 1. トークン表と論理的な生存状態

各要求に対して、論理トークン識別子を物理ブロック番号、ブロック内オフセット、生存ビットへ写すトークン表（TokenTable）を持つ。削除方策は `evict_token(req_id, token_id)` により対象を論理的に無効化し、`sync_new_tokens` により新規生成トークンを登録する。この時点ではKVの移動も物理ブロック解放も発生しない。再配置完了後に `apply_moves` が新しい物理位置を確定する。上位方策は物理ブロックを直接操作せず、実行時管理層が解放時期と配置を決める。

表の正本はCPU側にあり、スロット変換を速めるためGPU側に参照用キャッシュを置く。新規トークンだけなら追記し、削除・移動など構造が変わった場合に写像を更新する。トークン当たり16バイトと保守的に仮定すると、16Kトークンの表は256 KBである。論文はこの管理量を評価対象7B/8Bモデルの約2 GBのFP16 KV本体と比較して0.1%未満と説明する。ただし表の容量が小さいことと、再配置計画のCPU時間が小さいことは別である。

### 2. 断片化の検知と再配置計画

各ブロックの生存トークン数を更新し、断片化率が閾値を超え、空きブロック数が低水位へ近づき、十分な回収候補がある場合に再配置を検討する。代表設定では断片化率の閾値を0.25とする。計画器は一要求の低利用率ブロック群から生存トークン数を合算し、必要な移動先ブロック数を切り上げ計算する。移動先を確保した後に、解放できる移動元ブロック数が移動先消費を上回る場合だけ計画を受理する。

この制約が必要なのは、詰め直しには一時的な退避先が先に必要だからである。退避先の余裕（headroom）は既存のKVブロック予算内に予約し、無制限の別プールとして追加しない。空きが不足する場合は新規要求の受理を抑制し、利益が出ない計画は延期する。移動計画は各生存トークンの論理ID、移動元（ブロック、位置）、移動先（ブロック、位置）を保持し、同じ要求で移動が重複実行されないようにする。

### 3. 注意計算を妨げない非同期コピー

注意演算は高帯域メモリ（HBM）の読み出しに敏感であるため、KVコピーを注意カーネルと同時に走らせると帯域を奪い合う。vTokenは現在の前向き計算が終わった後、専用CUDAストリームへKV移動を発行する。サンプリングや次要求の準備とコピーを重ね、次の注意演算が移動後のスロットを参照する直前にCUDAイベント依存を挿入する。これによりCPUの全体同期を避けながら、未完了のコピーを注意演算が読まないようにする。

移動完了前に元ブロックを解放せず、完了後にトークン表とスロット写像を切り替える。論文が掲げる不変条件は、生存トークンとKV値の保存、一意な物理写像、次の注意演算より前のコピー完了、利益のある一貫した計画の四つである。コピーが計算と資源競合しない保証ではなく、競合の強い注意区間を避ける工程設計である。

### 4. 既存カーネル・CUDAグラフとの互換性

注意カーネルへ渡す線形スロット番号は、従来の論理ブロック表ではなく、トークン表が返す物理ブロックID×ブロックサイズ＋オフセットから組み立てる。スロット写像は注意カーネルの内部ではなく入力準備段階で更新するため、ページ化注意カーネル本体やKVテンソルの形状を変更しない。CUDAグラフの捕捉済み入力領域を保持し、その内容を再生前に書き換えることでグラフ再捕捉も避ける。

削除方策の実装者は犠牲トークン選択（SelectVictims）だけを記述し、トークン表更新、移動、解放は共通の実行時管理が担当する。論文の実装量比較では、ブロックを直接扱う方式は4～6ファイルで500行超の変更が必要なのに対し、vToken経由の方策追加は1～2ファイル・50行未満としている。ただしこれは著者らの試作における開発変更量であり、他の推論エンジンへの移植費用の測定ではない。

## 評価条件

| 項目 | 原著での条件 |
|---|---|
| 実装 | vLLM v0.18.0、PyTorch v2.10.0、CUDAグラフ有効 |
| 計算資源 | 単一NVIDIA H100、GPUメモリ80 GB |
| 主モデル | Mistral-7B、Llama-3.1-8B |
| 容量確認 | Qwen2.5-14B |
| 入力 | ShareGPT、LongBench。共有接頭辞試験は合成要求 |
| KV削除方策 | H2O、Scissorhands、Random |
| 比較 | Native vLLM（全保持）、Naive-Evict（同一トークン削除だが物理回収なし）、vToken |
| 復号 | 温度0、同じ入力・削除判断・メモリ予算。通常 gpu_mem_util=0.90 |
| サービス指標 | 同時要求数を走査し、Naive-Evictの参照同時数8におけるp95遅延の1.05倍をSLA閾値とする |
| 容量試験 | gpu_mem_util=0.35 / 0.50など、退避余裕も同じKV予算に算入 |

単純削除実装との対比較では、両方式が同じ削除対象トークンを選ぶ。したがって、保持ブロック数の差を「どのトークンを忘れるか」という方策の差と混同しない。サービス水準の達成点は最大同時要求数と必ずしも一致せず、遅延閾値を満たす点のうち処理量最大の構成を比較している。

| 対象・条件 | 比較指標 | 基準 | vToken | 解釈 |

| Llama-3.1-8B / Mistral-7B | ブロック利用率 | Naive-Evict | 論文表現で約21.88% / 21.67%改善 | 利用率の相対増加と百分率ポイントは混同しない |

| Llama-3.1-8B / KV予算0.35 | 最大実行可能同時数 | 5 | 8 | 60%拡大 |

保持ブロック削減と処理量改善は同じ指標ではない。容量を回収しても、GPU計算が律速の条件では処理量は比例して増えない。Llama-3.1-8B、LongBench、H2O、出力長12,288の容量試験では、KV利用可能ブロックは予算0.35で5,427、0.50で11,519だった。全保持では1要求あたり1,020ブロックを要する一方、削除後の理想的な詰め込みは512ブロックである。vTokenは理想容量へ近づけることで同時数を伸ばした。0.35予算で8要求の境界点は180.3トークン/秒で、同方式の5要求でのピーク203.2トークン/秒より低い。最大同時数と最高処理量が一致しないことを示す。

構成要素除去実験では、トークン表の間接参照だけを有効にし、削除と再配置を止めた条件の処理量・p95変化はNative vLLM比1.0%未満だった。主なCPU側費用は移動計画の機会判定であり、非同期コピーは明示的な同期待ちを避ける。ただしコピー自体のGPU資源消費は消えない。ブロックサイズを16、32、48と変えた感度試験では、代表ワークロードの処理量とp95遅延は32で最良、48は容量節約があっても性能が悪化した。削除率を0.3から0.7へ上げると回収容量と速度は改善するが、生成品質を守る削除率の選択は削除方策側の責任である。

## 共有接頭辞・負の結果・生成の正しさ

共有接頭辞を再利用する場合、vTokenは共有ブロックを保守的に移動対象から外し、各要求固有の接尾部だけを回収する。Llama-3.1-8B、共有接頭辞8Kトークン・私有接尾部8Kトークンの合成実験では、共有度2、4、8で共有接頭辞候補をすべて除外しながら、保持ブロック数をそれぞれ33.0%、32.3%、42.2%削減した。

| 共有度 | 保持ブロック削減 | 処理量差 | p95遅延差 | 注意点 |
|---:|---:|---:|---:|---|
| 1（共有なし） | 28.6% | **-2.9%** | **+2.9%** | メモリ削減しても速度は悪化 |
| 2 | 33.0% | +76.1% | -40.2% | 共有ブロックを移動せず私有接尾部を回収 |
| 4 | 32.3% | +97.2% | -40.9% | 共有度が高いほど容量効果が現れる |
| 8 | 42.2% | +146.5% | -47.8% | 比較対象は接頭辞共有を有効にしたNaive-Evict |

この表は全条件で処理量が改善するという主張への反例である。共有度1ではKV容量の節約より管理・移動費用が相対的に大きく、性能が小幅に悪化する。逆に共有度が高い条件では、共通ブロックを保護しても私有接尾部を圧縮する利得が大きい。これらは合成ワークロードの相対結果であり、実際の要求分布で同じ倍率になる保証ではない。

移動前後の生存トークンIDとKVテンソルのハッシュ照合では、評価した移動イベントで一意性と内容保存が維持された。144組の決定的復号ではROUGE-L F1平均差が-0.0016、93.1%が絶対差0.01以下、出力長比の中央値は0.99だった。これは物理再配置による追加の品質変化が小さいことを示すが、トークン削除方策そのものが元の全保持モデルと同じ品質を保つ証明ではない。

## 既存研究との差と適用限界

H2O、Scissorhands、Randomは「何を残すか」を決める。ページ化注意は「物理ブロックをどう管理するか」を決める。vTokenは両者の間に論理トークンの生存状態を公開する境界を設け、同じ削除判断を実際に再利用可能なGPU容量へ変換する。別の重要度学習器や圧縮符号を提案する論文ではなく、削除方策を実装から切り離す実行時抽象化の研究である。

評価対象は単一GPUの単一KVキャッシュ群と主にFP16 KVであり、テンソル並列、複数KV群、異種GPU間移送を実測していない。共有接頭辞はコピーオンライトで再配置するのではなく、保守的に除外する。GPU容量が十分で全保持できる場合、Native vLLMを選ぶ方が単純であり、vTokenの管理費用を払う必要がない。コピーと注意演算の資源競合、移動計画のCPU費用、断片化閾値の調整、削除率と品質の交換条件は運用上の制約として残る。

コード公開については、一次論文にvLLM上の試作実装を記述する一方、著者公式の公開リポジトリURLを確認できなかった。したがって`code`は`null`とし、実装が未公開であると断定はしない。一次資料の結果は単一H100の評価であり、現代の異種GPU構成やCPUオフロードへそのまま外挿しない。
