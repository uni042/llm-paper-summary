# PRESERVE: Prefetching Model Weights and KV-Cache in Distributed LLM Serving

> tensor-parallel LLM推論のAllreduce中に次に必要なmodel weightとKV cacheをHBMからaccelerator内L2 cacheへ先読みし、通信待ち時間をmemory readに使ってdecode latencyを隠すgraph-level prefetch framework。

## 概要

PRESERVEは、distributed LLM inferenceで発生するcollective communicationを単なる待ち時間にせず、**その間に次に使うweightとKV cacheをHBMからon-chip L2 cacheへprefetchする**研究である。

Tensor parallelismでは各layerの途中でAllreduce等が入り、その間compute coreは十分に使われない。一方decodeでは次operatorが必要とするweight / KVをHBMから読む時間も大きい。PRESERVEはこの2つを重ね、communication終了時点で次のdataをL2へ用意しておく。

GEMM+Allreduce fusionのように隣接operatorだけを融合する方式と異なり、graph全体を見てprefetch operatorを自動挿入するため、間に複数operatorがあるKV cacheにも適用できる。

## 手法

### 1. Allreduce中にweight / KVをL2へprefetchする

各communication operatorを起点に、その後に実行されるMatMulやSelf-Attentionが必要とするdataを調べ、通信とparallelなstreamでHBM→L2 readを開始する。

communication終了後、compute operatorはHBMではなくL2 hitからdataを取得できるため、**通信latencyとHBM read latencyを別々に支払うのではなく同時に消化する**。

### 2. Graph optimizerがprefetch位置を自動決定する

user codeへ手作業でprefetchを埋め込まず、ML compilerが作ったcomputation graphをPRESERVEが解析する。

各communication nodeから次のcommunication nodeまでを探索し、MatMul / Self-Attentionが必要とするweight / KVについてprefetch operatorを挿入する。runtimeではprefetch streamとmain streamをeventで同期する。

### 3. L2容量を超えるprefetchを避ける

何でも早くprefetchするとL2内の有効dataを追い出して逆効果になる。そこでcompiler時にprefetch済みdata量を追跡し、設定したL2 budgetを超える場合は追加prefetchを停止する。

つまりPRESERVEは単なる`load earlier`ではなく、**graph上の利用順序とcache容量を同時に考えるprefetch insertion**である。

### 4. WeightとKVを同じ仕組みで扱う

projection / MLPではmodel weight、attentionではKV cacheをprefetchする。同じcommunication windowを異なる種類のmemory readへ利用できる点が特徴である。

このため本研究はKV専用ではないが、KV cacheをon-chip memoryへprefetchする代表的なintra-GPU memory-hierarchy研究として本系統に分類する。

## 評価

### 実機条件

| 項目 | 条件 |
|---|---|
| Accelerator | Huawei Ascend 910B NPU × 最大8 |
| L2 | 192MB / device |
| HBM | 64GB / device、1.6TB/s |
| Interconnect | HCCS full-mesh |
| Models | Llama3-8B / 70B、Qwen2-7B / 72B、Phi-3-small / medium |
| Quantization | 主評価はINT8、追加比較でFP16 |
| Batch | 主探索1〜64、追加評価では最大1024 |
| Sequence | 主探索2K〜32K、追加評価では最大64K |

### End-to-end

batch=4、max sequence=16Kでは、2 / 4 / 8 NPU構成に対して多くのmodelでspeedupを確認した。

代表例は以下。

- Llama3-8B、4 NPU: 128.2s → 80.6s、**1.59×**
- Phi3-small、4 NPU: 128.4s → 79.9s、**1.61×**
- Llama3-70B、4 NPU: 501.5s → 368.7s、**1.36×**
- Phi3-medium、4 NPU: **1.43×**

全体では1.09〜1.61×のend-to-end speedupを報告している。communication / compute比が大きい比較的小型modelで利得が大きい。

### Batch / context依存

大modelを4 NPUで調べた追加評価では最大**1.82×**。長context・小batchほど利得が大きい。

batchが増えるとMLPがcompute-boundになり、さらにKV cacheがL2に収まりにくくなるため効果が低下する。非常に長いcontextでも同様にKVがL2容量を超えるとself-attention側のprefetch効果が落ちる。

### GEMM+Allreduce fusionとの比較

Llama3-70B FP16、4×Ascend 910Bで比較すると、小batchではPRESERVEが最大1.19×速い。一方batch 512以上ではfused GEMM+Allreduce側が優勢になり、batch=1024 / short contextではPRESERVEが0.93×まで低下する条件がある。

つまりPRESERVEはonline / resource-constrainedなsmall-batch serving向けで、非常に大きいoffline batchでは従来のcompute-communication fusionが有利になり得る。

### Hardware design-space exploration

実機評価とは別にaccelerator performance modelを使ってL2 cache size等を探索している。

prefetchなしではperformance-per-area上の最適L2が8MBだったのに対し、PRESERVEを前提にすると104MBまで増えた。throughput densityは11.8→14.8 token/s/mm²となり、**1.25×のperformance / cost改善**を示した。

これは実機の追加speedupではなく、hardware design-space simulationの結果として区別する必要がある。

## 既存研究との差

### GEMM + Allreduce fusionとの違い

既存のfusionは隣接するGEMMとAllreduceを細かく分割してoverlapするが、data dependency上、離れたoperatorのmemory readまでは隠せない。特にKV cacheはattentionと次communicationの間に複数operatorがあるため対象にしにくい。

PRESERVEはcommunication中に**将来のmemory readそのものを先行実行**するので、weightだけでなくKVにも適用できる。

### Asynchronous KV Cache Prefetchingとの違い

2025年のAsynchronous KV Cache Prefetchingはattention kernel内部で、現在KV blockの計算中に次blockをHBM→L2へprefetchする。single GPUでも使えるkernel-level optimizationである。

PRESERVEはdistributed inferenceのcollective communicationをprefetch windowとして使い、graph levelでweightとKVの両方を対象にする。両者はL2 prefetchという発想を共有するが、overlapさせる相手が異なる。

## 限界

- collective communicationがあるtensor-parallel環境を前提とし、single GPUにはそのまま適用できない。
- batchやKV容量が増えてprefetched dataがL2へ収まらないと利得が急減する。
- communicationが短すぎてもprefetchを隠す時間が足りず、長すぎても全latencyをmemory readだけでは埋めきれない。
- 実機評価はAscend 910B中心で、NVIDIA / AMDで同じgraph optimizer実装を直接評価してはいない。
- graph compiler / runtimeへprefetch operatorとcache usage trackingを組み込む必要がある。
- hardware design-spaceの1.25×はsimulation結果であり、104MB L2搭載実機の測定値ではない。
- 2026-09-06時点で公式code repositoryは確認できなかった。

## 一般的な実装上の含意

Distributed inferenceではcommunicationとcomputeだけでなく、**communicationと次operatorのmemory readをoverlapできる**。特にdecodeのようにHBM-boundなworkloadでは、communication中にcoreがidleでもmemory subsystemまでidleとは限らないため、別resourceを同時利用する余地がある。

またprefetchをsystemへ入れる場合、単純な早読みではなく、L2 capacity・data lifetime・次の利用位置をcompilerが追跡しないとcache pollutionで逆効果になる。
