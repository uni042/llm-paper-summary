# PRESERVE: Prefetching Model Weights and KV-Cache in Distributed LLM Serving

> tensor parallel推論のGPU間集約通信中に、次に使うweightとKV cacheをHBMからL2 cacheへ先読みし、通信待ちとmemory readを同時に進める分散推論手法。

## 概要

PRESERVEは、distributed LLM inferenceで発生するcollective communicationを単なる待ち時間にせず、**その間に次に使うweightとKV cacheをHBMからon-chip L2 cacheへprefetchする**研究である。

Tensor parallelismでは各layerの途中でAllreduce等が入り、その間compute coreは十分に使われない。一方decodeでは次の演算が必要とするweight / KVをHBMから読む時間も大きい。PRESERVEはこの2つを重ね、通信終了時点で次のdataをL2へ用意しておく。

隣り合うGEMMと通信だけを直接融合する方式と異なり、**計算graph全体から「通信の後に何を使うか」を調べて先読み処理を自動挿入する**ため、間に複数の演算があるKV cacheにも適用できる。

## 手法

### 1. GPU間通信中に、次に必要なweight / KVをL2へ運ぶ

各communication operatorを起点に、その後に実行されるMatMulやSelf-Attentionが必要とするdataを調べ、通信とは別の実行streamでHBM→L2 readを開始する。

communication終了後、compute operatorはHBMまで取りに行く代わりにL2にあるdataを使いやすくなるため、**通信時間とHBM read時間を別々に支払わず、同時に消化する**。

### 2. Compilerが「どこで何を先読みするか」を決める

user codeへ手作業でprefetchを埋め込まず、ML compilerが作った計算graphをPRESERVEが解析する。

各communication nodeから次のcommunication nodeまでを見て、途中のMatMul / Self-Attentionが使うweight / KVについてprefetch operatorを挿入する。runtimeでは、先読みが完了する前に本計算が対象dataを使わないよう同期する。

つまり、論文の `graph optimizer` は**計算順序を見て、先読み可能なdataと挿入位置を自動で決めるcompiler処理**である。

### 3. L2へ先読みしすぎて必要dataを追い出さないようにする

何でも早くprefetchするとL2容量を使い切り、先に入れた有効dataが新しいprefetchによって追い出される可能性がある。

そこでcompiler時にprefetch済みdata量を追跡し、設定したL2 budgetを超える場合は追加prefetchを停止する。

一般に `cache pollution` と呼ばれるこの問題を避けるため、PRESERVEは単なる「早くloadする」方式ではなく、**利用順序とL2容量を見ながら先読み量を制限する**。

### 4. WeightとKVを同じ仕組みで扱う

projection / MLPではmodel weight、attentionではKV cacheをprefetchする。同じcommunication windowを異なる種類のmemory readへ利用できる点が特徴である。

このため本研究はKV専用ではないが、KV cacheをon-chip memoryへprefetchする代表的なintra-GPU memory-hierarchy研究として本系統に分類する。

## 評価

### 実機条件

| 項目 | 条件 |
|---|---|
| Accelerator | Huawei Ascend 910B NPU × 最大8 |
| L2 | 192MB / device |
| HBM | 64GB / device、1.6TB/s |
| Interconnect | HCCS full-mesh |
| Models | Llama3-8B / 70B、Qwen2-7B / 72B、Phi-3-small / medium |
| Quantization | 主評価はINT8、追加比較でFP16 |
| Batch | 主探索1〜64、追加評価では最大1024 |
| Sequence | 主探索2K〜32K、追加評価では最大64K |

### End-to-end

batch=4、max sequence=16Kでは、2 / 4 / 8 NPU構成に対して多くのmodelでspeedupを確認した。

代表例は以下。

- Llama3-8B、4 NPU: 128.2s → 80.6s、**1.59×**
- Phi3-small、4 NPU: 128.4s → 79.9s、**1.61×**
- Llama3-70B、4 NPU: 501.5s → 368.7s、**1.36×**
- Phi3-medium、4 NPU: **1.43×**

全体では1.09〜1.61×のend-to-end speedupを報告している。通信時間が全体に占める割合の大きい比較的小型modelで利得が大きい。

### Batch / context依存

大modelを4 NPUで調べた追加評価では最大**1.82×**。長context・小batchほど利得が大きい。

batchが増えるとMLP計算自体の比重が増え、さらにKV cacheがL2に収まりにくくなるため効果が低下する。非常に長いcontextでも同様に、prefetchしたKVがL2容量を超えるとself-attention側の利得が落ちる。

### GEMM+Allreduce fusionとの比較

Llama3-70B FP16、4×Ascend 910Bで比較すると、小batchではPRESERVEが最大1.19×速い。一方batch 512以上ではGEMMとAllreduceを直接重ねる方式が優勢になり、batch=1024 / short contextではPRESERVEが0.93×まで低下する条件がある。

つまりPRESERVEはonline / small-batch serving向けで、非常に大きいoffline batchでは従来のcompute-communication fusionが有利になり得る。

### Hardware design-space exploration

実機評価とは別にaccelerator performance modelを使ってL2 cache size等を探索している。

prefetchなしではperformance-per-area上の最適L2が8MBだったのに対し、PRESERVEを前提にすると104MBまで増えた。throughput densityは11.8→14.8 token/s/mm²となり、**1.25×のperformance / cost改善**を示した。

これは実機の追加speedupではなく、**将来hardwareでL2容量を変えた場合を数値modelで評価したsimulation結果**として区別する必要がある。

## 既存研究との差

### GEMM + Allreduce fusionとの違い

既存のfusionは隣接するGEMMとAllreduceを細かく分割してoverlapするが、離れた演算で将来必要になるmemory readまでは隠しにくい。

PRESERVEはcommunication中に**将来のmemory readそのものを先行実行**するので、weightだけでなくKVにも適用できる。

### Asynchronous KV Cache Prefetchingとの違い

Asynchronous KV Cache Prefetchingはattention kernel内部で、現在KV blockの計算中に次blockをHBM→L2へprefetchする。single GPUでも使えるkernel-level optimizationである。

PRESERVEはdistributed inferenceのcollective communicationをprefetchに使える時間として利用し、graph levelでweightとKVの両方を対象にする。両者はL2 prefetchという発想を共有するが、**先読みと同時に走らせる処理が、attention計算かGPU間通信か**という違いがある。

## 限界

- collective communicationがあるtensor-parallel環境を前提とし、single GPUにはそのまま適用できない。
- batchやKV容量が増えてprefetched dataがL2へ収まらないと利得が急減する。
- communicationが短すぎると十分なdataを先読みできず、逆に長すぎても全通信時間をmemory readだけで埋められるわけではない。
- 実機評価はAscend 910B中心で、NVIDIA / AMDで同じcompiler実装を直接評価してはいない。
- compiler / runtimeへprefetch operatorとL2使用量追跡を組み込む必要がある。
- hardware design-spaceの1.25×はsimulation結果であり、104MB L2搭載実機の測定値ではない。
- 2026-09-06時点で公式code repositoryは確認できなかった。

## 一般的な実装上の含意

Distributed inferenceではcommunicationとcomputeだけでなく、**communicationと次operatorのmemory readをoverlapできる**。特にdecodeのようにHBM read待ちが大きいworkloadでは、GPU間通信中にmemory subsystemを別目的で使える余地がある。

またprefetchをsystemへ入れる場合、単純な早読みではなく、L2 capacity・dataが必要になる時点・次の利用順をcompilerが追跡しないと、必要dataを追い出して逆効果になる。
