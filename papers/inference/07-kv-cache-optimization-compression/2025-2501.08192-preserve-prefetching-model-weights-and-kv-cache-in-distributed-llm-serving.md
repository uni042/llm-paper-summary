# PRESERVE: Prefetching Model Weights and KV-Cache in Distributed LLM Serving

> tensor 並列推論のGPU間集約通信中に、次に使う重みとKV キャッシュをHBMからL2 キャッシュへ先読みし、通信待ちとメモリ 読み出すを同時に進める分散推論手法。

## 概要

保持するは、distributed LLM 推論で発生するcollective 通信を単なる待ち時間にせず、**その間に次に使う重みとKV キャッシュをHBMからon-chip L2 キャッシュへプリフェッチする**研究である。

Tensor 並列化では各層の途中でAllreduce等が入り、その間計算 coreは十分に使われない。一方デコードでは次の演算が必要とする重み / KVをHBMから読む時間も大きい。保持するはこの2つを重ね、通信終了時点で次のデータをL2へ用意しておく。

隣り合うGEMMと通信だけを直接融合する方式と異なり、**計算graph全体から「通信の後に何を使うか」を調べて先読み処理を自動挿入する**ため、間に複数の演算があるKV キャッシュにも適用できる。

## 手法

### 1. GPU間通信中に、次に必要なweight / KVをL2へ運ぶ

各通信 operatorを起点に、その後に実行されるMatMulやSelf-注意機構が必要とするデータを調べ、通信とは別の実行ストリームでHBM→L2 読み出すを開始する。

通信終了後、計算 operatorはHBMまで取りに行く代わりにL2にあるデータを使いやすくなるため、**通信時間とHBM 読み出す時間を別々に支払わず、同時に消化する**。

### 2. Compilerが「どこで何を先読みするか」を決める

user codeへ手作業でプリフェッチを埋め込まず、ML compilerが作った計算graphを保持するが解析する。

各通信 nodeから次の通信 nodeまでを見て、途中のMatMul / Self-注意機構が使う重み / KVについてプリフェッチ operatorを挿入する。実行時では、先読みが完了する前に本計算が対象データを使わないよう同期する。

つまり、論文の `graph optimizer` は**計算順序を見て、先読み可能なデータと挿入位置を自動で決めるcompiler処理**である。

### 3. L2へ先読みしすぎて必要dataを追い出さないようにする

何でも早くプリフェッチするとL2容量を使い切り、先に入れた有効データが新しいプリフェッチによって追い出される可能性がある。

そこでcompiler時にプリフェッチ済みデータ量を追跡し、設定したL2 budgetを超える場合は追加プリフェッチを停止する。

一般に `cache pollution` と呼ばれるこの問題を避けるため、保持するは単なる「早く読み込むする」方式ではなく、**利用順序とL2容量を見ながら先読み量を制限する**。

### 4. WeightとKVを同じ仕組みで扱う

projection / MLPではモデル重み、注意機構ではKV キャッシュをプリフェッチする。同じ通信 区間を異なる種類のメモリ 読み出すへ利用できる点が特徴である。

このため本研究はKV専用ではないが、KV キャッシュをon-chip メモリへプリフェッチする代表的なintra-GPU メモリ-hierarchy研究として本系統に分類する。

## 評価

### 実機条件

| 項目 | 条件 |
|---|---|
| Accelerator | Huawei Ascend 910B NPU × 最大8 |
| L2 | 192MB / device |
| HBM | 64GB / device、1.6TB/s |
| Interconnect | HCCS full-mesh |
| Models | Llama3-8B / 70B、Qwen2-7B / 72B、Phi-3-small / medium |
| Quantization | 主評価はINT8、追加比較でFP16 |
| Batch | 主探索1〜64、追加評価では最大1024 |
| Sequence | 主探索2K〜32K、追加評価では最大64K |

### End-to-end

バッチ=4、max 系列=16Kでは、2 / 4 / 8 NPU構成に対して多くのモデルで高速化倍率を確認した。

代表例は以下。

- Llama3-8B、4 NPU: 128.2s → 80.6s、**1.59×**
- Phi3-小規模、4 NPU: 128.4s → 79.9s、**1.61×**
- Llama3-70B、4 NPU: 501.5s → 368.7s、**1.36×**
- Phi3-medium、4 NPU: **1.43×**

全体では1.09〜1.61×のエンドツーエンド 高速化倍率を報告している。通信時間が全体に占める割合の大きい比較的小型モデルで利得が大きい。

### Batch / context依存

大モデルを4 NPUで調べた追加評価では最大**1.82×**。長文脈・小バッチほど利得が大きい。

バッチが増えるとMLP計算自体の比重が増え、さらにKV キャッシュがL2に収まりにくくなるため効果が低下する。非常に長い文脈でも同様に、プリフェッチしたKVがL2容量を超えるとself-注意機構側の利得が落ちる。

### GEMM+Allreduce fusionとの比較

Llama3-70B FP16、4×Ascend 910Bで比較すると、小バッチでは保持するが最大1.19×速い。一方バッチ 512以上ではGEMMとAllreduceを直接重ねる方式が優勢になり、バッチ=1024 / 短い 文脈では保持するが0.93×まで低下する条件がある。

つまり保持するはオンライン / 小規模-バッチ 提供処理向けで、非常に大きいオフライン バッチでは従来の計算-通信 融合が有利になり得る。

### Hardware design-space exploration

実機評価とは別にaccelerator 性能 モデルを使ってL2 キャッシュ size等を探索している。

プリフェッチなしでは性能-あたり-area上の最適L2が8MBだったのに対し、保持するを前提にすると104MBまで増えた。スループット densityは11.8→14.8 トークン/s/mm²となり、**1.25×の性能 / コスト改善**を示した。

これは実機の追加高速化倍率ではなく、**将来ハードウェアでL2容量を変えた場合を数値モデルで評価したシミュレーション結果**として区別する必要がある。

## 既存研究との差

### GEMM + Allreduce fusionとの違い

既存の融合は隣接するGEMMとAllreduceを細かく分割してoverlapするが、離れた演算で将来必要になるメモリ 読み出すまでは隠しにくい。

保持するは通信中に**将来のメモリ 読み出すそのものを先行実行**するので、重みだけでなくKVにも適用できる。

### Asynchronous KV Cache Prefetchingとの違い

Asynchronous KV キャッシュ プリフェッチは注意機構 カーネル内部で、現在KV blockの計算中に次blockをHBM→L2へプリフェッチする。single GPUでも使えるカーネル-水準 optimizationである。

保持するはdistributed 推論のcollective 通信をプリフェッチに使える時間として利用し、graph 水準で重みとKVの両方を対象にする。両者はL2 プリフェッチという発想を共有するが、**先読みと同時に走らせる処理が、注意機構計算かGPU間通信か**という違いがある。

## 限界

- collective 通信があるtensor-並列環境を前提とし、single GPUにはそのまま適用できない。
- バッチやKV容量が増えてprefetched データがL2へ収まらないと利得が急減する。
- 通信が短すぎると十分なデータを先読みできず、逆に長すぎても全通信時間をメモリ 読み出すだけで埋められるわけではない。
- 実機評価はAscend 910B中心で、NVIDIA / AMDで同じcompiler実装を直接評価してはいない。
- compiler / 実行時へプリフェッチ operatorとL2使用量追跡を組み込む必要がある。
- ハードウェア design-空間の1.25×はシミュレーション結果であり、104MB L2搭載実機の測定値ではない。
- 2026-09-06時点で公式code repositoryは確認できなかった。

## 一般的な実装上の含意

Distributed 推論では通信と計算だけでなく、**通信と次operatorのメモリ 読み出すをoverlapできる**。特にデコードのようにHBM 読み出す待ちが大きいワークロードでは、GPU間通信中にメモリ subsystemを別目的で使える余地がある。

またプリフェッチをシステムへ入れる場合、単純な早読みではなく、L2 容量・データが必要になる時点・次の利用順をcompilerが追跡しないと、必要データを追い出して逆効果になる。
