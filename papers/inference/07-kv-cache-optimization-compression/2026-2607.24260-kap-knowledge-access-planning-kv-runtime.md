# KAP: Bridging the Knowledge Selection-Runtime Consumption Gap in LLM Systems

> 検索・グラフなど上流の知識選択情報を実行時アクセス計画へコンパイルし、論理プロンプトを変えず物理KV参照を選択化する。GraphSpecは128Kで提案時KVアクセスを元状態の5.5%まで減らす。

## 概要

KAP（Knowledge Access Planning）は、長文脈LLMシステムで**「どの情報が重要か」は検索側がすでに知っているのに、GPUでデコードする段階ではその知識が捨てられている**という構造的な無駄を扱う。検索拡張生成（Retrieval-Augmented Generation; RAG）では、検索順位、証拠集合、知識グラフの接続関係、信頼度などを使って文脈を組み立てる。しかし最終的にそれらを一列のtokenへ直列化すると、通常の配信基盤から見えるのは位置番号だけになり、decode時には長いKVキャッシュをほぼ一様に消費する。

論文はこの不一致をKnowledge Selection-Runtime Consumption（KSRC）gapと呼ぶ。文脈を豊かにするほどKV容量とdecode時メモリtrafficが増える一方、実際の回答に必要な証拠は一部だけという状況では、検索品質を上げることが配信コストを悪化させる。KAPはこの上流信号を捨てず、**runtime access planという中間表現（Intermediate Representation; IR）へ変換して、どのKV領域を物理的に読むかを実行時へ持ち込む**。

GraphSpecはKAPの具体実装で、構造化知識選択をcompilerでaccess planへ落とし、executorがそのplanに沿ってKVを参照する。論理prompt、モデルweight、訓練手順は変えない。4K〜128Kの長文脈QAでは、全文脈デコードと同等水準の回答品質を維持しつつ、128Kでproposal-time KV accessをsource KV stateの5.5%まで減らしたと報告する。

この「5.5%」は最も誤解しやすい。KVキャッシュを94.5%削除して保持容量を減らした値ではなく、**提案段階で物理的に参照するKV量**である。verificationを含む全実行時間、全メモリ容量、総I/Oが同じ比率まで減るとは限らない。

## 背景：RAGの「選択」は通常どこで失われるか

一般的なRAGは、候補文書を検索し、rankerで並べ、必要なchunkをpromptへ挿入した後、LLMへ渡す。検索器はこの時点で「文書Aは重要度0.9」「文書BはAと同じentityに接続」「このchunkが質問と直接対応」といった構造を持っている。しかしLLM serverへ渡すinterfaceがtoken列だけなら、その構造情報は物理実行へ伝わらない。

Transformerのdecodeでは、新しいqueryが過去tokenのkey/valueと照合される。contextが長くなるほど、各decode stepで読むKV量が増え、演算量だけでなくHBM帯域が支配的になりやすい。つまり上流で「必要な証拠はこの数chunk」と分かっていても、下流が全tokenを同等に扱えば、その選択計算を配信側では利用できない。

既存のKV evictionやsparse attentionは、attention score、recency、heavy hitterなど**モデル内部から重要度を再推定する**ことが多い。KAPの着眼点は、importance estimationをもう一度GPU側でやる前に、上流systemがすでに持つsemantic selectionを物理計画へ渡せないか、という点にある。

## 問題設定

KAPが欲しい性質は三つある。第一に、知識選択器の種類が変わってもserving backend側を作り直さずに済む共通表現が必要である。第二に、promptを削除・改変せず論理的な入力意味を保持しながら、物理KV accessだけを減らしたい。第三に、planを解釈する固定費よりKV節約が大きい領域だけでsparse executionを使う必要がある。

このため論文は「どのtokenを消すか」という圧縮問題ではなく、「どの物理KVを、いつ読むか」というexecution planning問題として定式化する。上流selectionが誤れば重要証拠をplan外へ置く危険があるので、品質はplanのcoverageに依存する。

## 手法のあらまし

一要求の流れは次のようになる。

1. Retriever、graph reasoner、confidence estimatorなどが構造化knowledge signalを作る。
2. GraphSpec compilerが、それらをtoken位置・KV領域へ対応づける。
3. 共通runtime access planへ、参照候補や優先度・構造関係を記録する。
4. LLM backendは論理prompt全体の状態を保ちつつ、proposal executionではplanに従って物理KV accessを絞る。
5. 文脈長、選択率、固定overheadからdense executionより有利な領域かをphase-boundary modelで判断する。

この設計ではknowledge selectorとGPU kernelを直接結合しない。IRが境界になるため、上流selectionアルゴリズムと下流executorを別々に交換できることがシステム上の狙いである。

## 手法

### 1. Runtime Access Plan — 構造化知識を物理実行へ持ち込むIR

入力はranked evidence、graph topology、multimodal alignment、confidence signalなどの構造化priorである。compilerはこれを、配信基盤が理解できるaccess planへ正規化する。

出力は「このknowledge itemがprompt中のどのtoken/KV範囲へ対応し、どの領域を優先して消費すべきか」という物理実行artifactになる。prompt text自体を変更しないため、model weightやtraining procedureへ手を入れずにserving layerだけで扱える。

IRを置く意味は、retriever固有のscore形式をGPU runtimeへ直接埋め込まないことにある。knowledge graph、dense retrieval、multimodal selectorのどれであっても、最終的に同じaccess-plan contractへ落とせればexecutorを共有できる。

### 2. GraphSpec compiler — graph構造とtoken範囲を対応づける

GraphSpecはKAPを具体化するcompiler-executor pairである。compilerは上流で選ばれた証拠nodeや関係を、prompt中のtoken範囲と対応づけてruntime planを作る。

単なるtop-k文書番号ではなく、どの証拠が同じsubgraphに属するか、何が質問に直接接続するかといった構造を保存する。これにより、配信時には「token位置だけ」ではなく「knowledge unitとして関連するKV範囲」を扱える。

compiler処理には当然固定費がある。contextが短く、dense attention自体が安い場合にはplan生成・解釈のoverheadが相対的に大きくなり得る。この点を後述のphase-boundary modelで明示する。

### 3. Plan-driven KV consumption — 論理文脈と物理参照量を分ける

executorは論理的にはfull promptを保ちながら、proposal時にはplanが示す領域を中心にKVを読む。KAPの本質は、**logical context lengthとphysical KV consumptionを同じ量として扱わない**ことである。

従来は128K promptならKV accessもおおむね128Kに応じて増える。KAPでは、回答に必要なknowledge setがcontext拡張に対して小さく保てるなら、promptが長くなってもproposal側の物理access増加を抑えられる。論文が「scaling trajectoryを変える」と表現するのはこのためである。

ただし、plan外のtokenが本当に不要だという保証は上流selectionに依存する。重要情報を外した場合、物理I/Oは減ってもanswer qualityが落ちる。したがってKV access ratioだけでなくfull-context品質との対比が必須になる。

### 4. Phase-boundary model — sparse化が得になる領域を明示する

plan executionには、planを読み、候補KV範囲を管理し、sparse accessをdispatchする固定costがある。dense executionのcostをcontext lengthに比例する項、plan executionを固定overhead＋selected fractionに比例する項と見れば、文脈が短い場合やselection率が高い場合はdense側が有利になり得る。

論文はこの正のspeedup領域の境界をphase-boundaryとして導出する。これは「常にsparseにすれば速い」という主張ではなく、context length・access fraction・runtime overheadの組合せで切り替え点があることを設計に含める。

## 評価

### まず見るところ

- **評価範囲:** 4K〜128Kのlong-context QA。
- **主な物理指標:** proposal-time KV access ratio。
- **128K結果:** source KV stateの5.5%をproposal時に参照。
- **品質:** full-context decodingとcomparableな回答品質を維持。
- **重要な限定:** 5.5%はKV保存容量、総実行I/O、end-to-end latencyの5.5%を意味しない。
- **理論:** plan overheadとselected fractionを含むpositive-speedup phase boundaryを導出。

### 評価条件と確認できる結果

| 項目 | 論文で確認できる範囲 |
|---|---|
| context length | 4K〜128K |
| workload | long-context QA |
| 実装 | GraphSpec compiler-executor |
| baseline | full-context decoding |
| quality target | baselineとcomparableなanswer quality |
| 主物理指標 | proposal-time KV access / source KV state |
| 128K access ratio | 5.5% |
| model weights変更 | なし |
| training変更 | なし |
| logical prompt削除 | なし |

一次資料の公開要旨からは、代表GPU型番、すべてのdataset名、絶対latency・throughput値を確定できない。そのため本ページでは、確認できない値を補って「何倍高速」とは記載しない。現在の一次資料で強く読める結果は、**物理KV消費のスケーリングをprompt lengthから切り離したことと、128Kでの5.5% proposal access**である。

### 5.5%をどう読むか

| 読み方 | 正しいか | 理由 |
|---|---|---|
| proposal時にsource KVの5.5%を読む | ○ | 論文の報告値 |
| KV cache容量を94.5%削減した | × | logical full contextは保持する |
| end-to-end時間が5.5%になった | × | plan overhead・verification・他計算を含まない |
| 総メモリtrafficが常に5.5% | × | proposal-time指標であり全phaseではない |
| 長文脈ほど利得余地が増える | 条件付き | selected fractionと固定cost次第 |

この切り分けはKAPをKV compression論文と混同しないために重要である。容量不足を直接解決する方式ではなく、decode/proposalで**触るbyte**を減らしてbandwidth律速を緩和する方式である。

### 負の領域・感度

phase-boundaryが示すとおり、短いcontextではfull scan自体が安く、plan管理の固定費が勝つ可能性がある。またknowledge selectorが広い範囲を選べばaccess ratioが高くなり、dense executionとの差が縮む。

さらに、QAは必要証拠が局所化しやすいworkloadである。長い自由記述reasoningや、文脈全体へ広く依存するtaskでも同じsparsityを保てるかは、この代表結果だけからは確定できない。上流selectorが外した証拠に対するfallback設計やselection誤差感度も、実運用で確認すべき項目になる。

## 既存研究との差

KV evictionやheavy-hitter方式は、decode中にattention scoreやrecentnessから「残すKV」を推定する。sparse attentionはqueryとKVの関係をモデル内部で近似し、読むtokenを減らす。これらは**serving側でimportanceを再発見する**アプローチである。

KAPは、その前段のretrieverやknowledge graphがすでにimportance・relationを計算している点を利用する。上流selectionをprompt構築だけのhintで終わらせず、物理execution artifactとして下流まで運ぶ。この「semantic planning → physical KV access」のinterfaceを第一級の抽象として提案したことが差分である。

## 限界・実装状況

KAPの品質上限は上流selectorに依存する。必要な証拠が構造化priorに現れなければ、正しいaccess planを作れない。logical promptを保持していることはfallback可能性を残すが、どの条件でdenseへ戻すべきかは実装上の重要点になる。

また、5.5%は非常に強い帯域削減指標だが、proposal phase限定である。verification、sampling、MLP、通信、plan生成を含むサービング全体のspeedupへ直接変換してはいけない。公式コードURLも2026-09-28時点で確認できず、再現性評価には追加確認が必要である。
