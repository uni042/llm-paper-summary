# SemanticKV：代表クエリとヘッド別重要度による長文脈KVキャッシュの削減

## 概要

自己回帰型LLMの推論では、入力文を一度処理するprefill段階で各層のキーと値を作り、生成段階ではそのKVキャッシュを参照する。入力が数万から十万トークン規模になると、KV保存量だけでなく、各生成トークンで過去文脈へ注意を計算する時間が問題になる。単純な直近窓だけを残す方式では、文書の中盤にある重要な条件や事実が失われる。SemanticKVは、prefill時点で重要な過去トークンを選別し、後続decodeで保持するKVを減らす訓練不要の方式である。

中心となる発想は、全クエリと全キーの組合せを評価する代わりに、クエリベクトルのL2ノルムが大きい一部のクエリを代表として選び、各注意ヘッドでキーが受ける注意重みを推定することである。先頭の注意シンクと直近の窓を保護し、中間領域のキーだけをヘッドごとに順位付けして削除する。NACLのprefill削除処理を約210行変更した実装であり、KVのビット幅を下げる量子化とは異なる。

原著のLlama3.1-8B-Instruct、InfiniteBench、KV保持率20%の条件では、64K入力の平均スコアが全保持25.85に対して23.99、72Kでは26.50に対して25.21となる。56K入力のデコードスループットは約5.71から13.7 token/sへ上がり、112KでGPUメモリは58.24GBから40.98GBへ減る。ただし64K平均は全保持の約92.8%であり、要旨にある「95%以上の性能維持」をすべての条件へ当てはめることはできない。これは近似的なキャッシュ削除による速度・容量と精度の交換条件を示す研究である。

## 問題設定

Transformerの各注意ヘッドは、クエリとキーの内積を使って過去トークンから必要な情報を取り出す。KVキャッシュを残せば以前のキー・値を再計算せずに済む一方、入力長に比例してGPUメモリが増える。長文書の質問応答、コードベース参照、多ターン会話などでは、生成する出力より入力文脈の方がはるかに長くなることがある。こうした場合、生成時に全履歴へ注意を計算し続ける費用が無視できない。

StreamingLLMは冒頭のattention sinkと直近窓を保持する位置ベースの方式であり、H2Oは累積注意重みの大きいheavy hitterを残す。Scissorhandsも注意の持続性を利用する。NACLは代表的なproxy tokenからキーの重要度を推定してサンプリングするが、選択の確率性が結果のばらつきを生む場合がある。SemanticKVは代表クエリをノルムで決定し、ヘッドごとの重要度と位置保護を組み合わせることで、長文脈の中間情報をより残そうとする。

重要なのは、削除対象がモデル重みや生成済みトークンそのものではなく、各層・各ヘッドが参照する過去トークンのKVであることだ。KVを削除すると、その情報を後で正確に再構成する仕組みは本方式にない。削除の誤りは推論品質に直接影響し得る。したがって性能比較では、保持率と速度だけでなく、削除後の質問応答・検索・数学タスクの精度も同時に評価しなければならない。

## 手法

### 1. クエリのL2ノルムから観測集合を選ぶ

各注意ヘッドで入力トークンtのクエリベクトルをq_tとすると、L2ノルムは各要素の二乗和の平方根である。原著§IV-Aでは、ノルムの大きなクエリは注意ロジットを強く変化させる候補として、上位λN個を選ぶ。これは重要なキーを決める前の観測クエリの選別である。論文は説明例としてλ=10%を挙げるが、実験既定値のsemantic token ratioは1%であるため、両者を同じ実測設定として扱わない。

注意ロジットはq_tとk_iの内積を√dで割ったもので、内積は二つのベクトルのノルムと角度の余弦の積で表せる。したがって大きいクエリノルムはロジットの振幅に寄与し得る。ただし、どのキーに注意が向くかはキーの向きとsoftmaxの相対値にも依存する。L2ノルムは意味の豊かさを直接測定する確定的な尺度ではなく、重要な観測クエリを安く選ぶ近似的な代理指標である。

全クエリ・全キーの重要度計算は概ねO(N²d)だが、観測クエリをλの割合に絞ることで、当該部分の演算はO(λN²d)程度に縮む。これに加えてノルム計算、上位選択、キャッシュ再配置などの費用は残る。理論上の演算量削減をGPU全体の実測速度改善と同一視しない。

### 2. 先頭・中間・直近の三領域

入力系列を先頭のsink region、中間のmiddle region、末尾のrecent regionに分ける。先頭は注意シンクとして広い文脈で参照されやすく、直近は生成直前の局所的な関係を保つため、これらの領域は削除せず保持する。大部分を占める中間領域は選別の対象とする。

観測集合には前段で選んだ高L2ノルムのsemantic queriesに加え、直近トークンのクエリも含める。中間トークンtのキーが観測集合のクエリから受けた注意重みを、注意ヘッドhごとに平均した値を重要度r_t^(h)とする。観測クエリの多くが継続的に参照するキーほど値が大きくなる。単一の最近クエリや単一の大きな注意値だけではなく、観測集合に対する平均で選ぶのが設計上の特徴である。

先頭と直近を必ず保持することは、全トークンを同じ競争へ入れるより頑健である一方、位置保護だけで残りの文脈が安全になるわけではない。例えば長文書の中盤に一度しか現れない固有名や数式の条件が低スコアになれば、後の質問に必要でも削除され得る。保持集合を決める時点では将来の質問内容を完全には知り得ないため、精度との交換条件が残る。

### 3. 注意ヘッド別のKV保持と実装

注意ヘッドごとに異なる特徴・文脈を参照するため、全ヘッドで同一トークンだけを残すと特定ヘッドに必要な情報を失う可能性がある。SemanticKVは各ヘッドの重要度を独立に計算し、中間領域の上位トークンをヘッドごとに選択する。論文の説明例では中間領域の20%を選ぶが、実際の保持予算には保護した先頭・直近領域も含まれる。保持率20%という実験条件は全KVの削減予算を表すもので、モデル重みやその他のテンソルを80%削除するという意味ではない。

実装はNACLを基盤にし、prefillのKV eviction部分へ約210行の変更を加えた。L2ノルムによるクエリ選択をPaddlePaddleで行い、ヘッド別の注意重要度推定にはFlashAttention-2を利用する。追加の学習を必要としない点は導入しやすさにつながるが、既存ランタイムとの統合やバッチ処理時の挙動は実装依存である。論文で比較した単一バッチのdecode速度から、任意のサービングシステムのP99遅延改善まで一般化することはできない。

### 保持率感度と他モデル

原著Figure 3ではLlama3.2-3BとMistral-7BのEn.MCおよびRetrieve.PassKeyを対象に、Full、NACL、SemanticKVを比較する。異なるモデル系列でもNACLより品質を維持する傾向を示すが、全てのモデルとデータセットで無損失を保証するものではない。保持率を20%から40%、60%、80%へ増やすと、選択可能なKVが増え、品質は概ね全保持へ近づく。保持率を大きくすると速度・メモリの利得は小さくなるため、導入時にはワークロードの品質要求に応じた予算設定が必要である。

## 既存研究との差

StreamingLLMは先頭と最近の位置に基づいて残す。H2Oは過去の注意スコアの累積からheavy hitterを選ぶ。NACLはproxy tokenの注意から重要度を推定する。SemanticKVは高L2ノルムのクエリを観測に使い、ヘッド別に中間領域の重要度を算出し、先頭・直近を保護する。従って位置のみ、あるいは全ヘッド共通の重要度だけで選ぶ方式と異なる。

また、KIVIのようなKV値の低ビット量子化とも異なる。SemanticKVは残すトークンの数を減らす。両方式を組み合わせる可能性はあるが、原著が示す数値はSemanticKV単独の評価であり、未検証の組合せ利得を既知の事実として記載しない。モデルの構造変更や再学習が不要という長所はある一方、推論ランタイムでのKVの物理配置と注意カーネルがヘッド別削除を扱えることが必要になる。

## 限界

第一に、L2ノルムは意味的重要性の厳密な証明ではない。クエリとキーの角度、softmaxの相対関係、後続の質問が必要とする情報によって重要度が変わる。中間領域の一度しか現れない重要情報を削除すると復元できない。実際に72KのNumberではFull 57.64から41.96へ低下している。平均品質の維持を根拠に全ての長文脈タスクでの安全性を主張できない。

第二に、評価環境は4基RTX 3090のローカルサーバーと限られたモデル系列であり、H100/H200/B200等の大規模GPU、異なる注意実装、連続バッチ、分散サービング、オンラインの尾部遅延への一般化は検証されていない。既存のprefix cacheやpaged attentionと併用した際の追加利得も本論文の測定対象ではない。GPU全体のメモリ削減率をKV削減率と取り違えると、必要なGPU容量を過小見積もりする。

第三に、Full KVは長文脈でメモリ不足となるため、一部の速度比較は外挿を含む。特定の保持率での改善倍率を、同じ長さ・同じGPUで両方式を実測した全条件の倍率として報告することはできない。実装変更約210行はNACLの既存コードを基礎にしたものであり、汎用LLMサービングエンジンへの統合コストを示す数字ではない。

第四に、論文はデコード速度・平均タスク品質・GPUメモリを中心に測定している。オンライン多重要求のP99 TTFT/TPOT、SLO違反率、エネルギー、コスト、バッチサイズ感度、キャッシュ再配置費用の分離測定は十分ではない。サービスへ導入するには、これらの条件と、入力分布が変わった際の品質変動を追加検証する必要がある。
