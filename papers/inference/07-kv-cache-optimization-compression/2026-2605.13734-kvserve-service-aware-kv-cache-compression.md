# KVServe: Service-Aware KV Cache Compression for Communication-Efficient Disaggregated LLM Serving

> KVServeは「KVキャッシュ（KV キャッシュ）をどう圧縮するか」だけではなく、**今の回線速度・処理負荷・品質条件なら、そもそもどの圧縮方式を使うべきか、あるいは圧縮しない方が速いか**を実行時に選ぶ仕組みである。分離型サービング（disaggregated サービング）でKVがGPU内部の一時状態から巨大な通信データへ変わることを前提に、圧縮を固定アルゴリズムではなくサービス状態に応じた制御問題として扱う。

## まず何が問題なのか

LLM推論は大きく、入力文をまとめて処理する**事前充填（プリフィル）**と、出力トークンを1個ずつ生成する**復号（デコード）**に分かれる。

プリフィルでは入力中の各トークンについて注意機構（注意機構）で使うキー/値を計算し、KVキャッシュとして保存する。デコードでは新しいトークンを生成するたびに過去トークンのKVを読み返すため、長い文脈ほどKVは巨大になる。

単一GPU/単一serverだけで完結する構成ならKVはGPU内部に置いたままでよい。しかし大規模サービングでは、次のような分離構成が使われる。

1. **プリフィル/デコード分離（プリフィル-デコード separation）**: プリフィル専用GPUとデコード専用GPUを分け、プリフィル終了後に生成したKVをデコード側へ送る。
2. **KV状態分離（KV 状態 disaggregation）**: 再利用したいKVをCPU、SSD、remote KV プールなどへ退避し、別リクエストや別GPUから読み戻す。

このときKVは単なるGPU内部状態ではなく、ネットワークやI/O境界を横断する巨大なpayloadになる。論文ではLlama 3.1-70B・128K 文脈でKVが約39.06 GBになる例を挙げ、実測でも10〜50 Gbpsのプリフィル/デコード分離環境ではKV通信がジョブ完了時間（Job Completion 時間: JCT）の16〜60%を占める。

つまり、計算を高速化してもKV転送が遅ければリクエスト全体は速くならない。

## 「KVを圧縮すればよい」だけではない理由

KVを4-ビットや2-ビットへ量子化したり、さらに符号化したりすれば転送量は減る。しかし圧縮には必ず別のコストがある。

- 圧縮前処理
- 量子化
- 無損失 codecによる符号化
- 受信側での復号・逆量子化
- 強い近似圧縮によるモデル品質低下

回線が遅い場合は、多少重い圧縮を使ってでも転送量を大きく減らした方が速い。一方、100 Gbps級の高速ネットワークでは転送そのものが短いため、圧縮・展開に時間を使うと**無圧縮より遅くなる**ことがある。

さらに、最適な圧縮方法はワークロードでも変わる。論文ではCacheGen、KIVI、DuoAttentionなどの相対順位がGSM8K、HumanEval、Multi-News、Qasperで変化する。つまり「この圧縮方式が常に最良」と固定できない。

KVServeの核心はここにあり、圧縮を固定configurationではなく

- ワークロード種類
- 現在の実効帯域
- 遅延のサービス水準目標（Service 水準 Objective: SLO）
- 最低限守るモデル品質

から毎回選ぶ。

## KVServe全体の流れ

KVServeは大きく3段階で動く。

### 1. 圧縮方法を部品へ分解する

既存手法をそのまま1個のblack boxとして扱わず、KV圧縮を次の3段パイプラインへ分解する。

`KV → 変換（Transform） → 量子化（Quantizer） → 符号化（Codec） → compressed KV`

#### 変換（Transform）

量子化しやすい値分布へKVを整形する前処理である。Delta、Hadamard、Affineなどを候補にする。

直感的には、極端な外れ値が多いデータをそのまま低ビット化すると大きな誤差が出やすいため、**量子化前に扱いやすい分布へ並べ替える**段階である。

#### 量子化（Quantizer）

BF16等で保持しているKVをより少ないビット数で表現する主圧縮段階である。KVServeは層、注意機構 ヘッドなどの単位ごとに異なる精度を割り当てられる。

#### 符号化（Codec）

量子化後のbyte列をさらに可逆圧縮する。実装ではNVIDIA nvCOMPを利用する。

このように分けることで「ある論文の変換 + 別論文の量子化 + 別codec」という組合せも探索できる。ただし組合せ数は最大でほぼ10^4規模になり、全部実測するのは現実的でない。

## MixHQ: attention headを全部同じ精度にしない

KVServeは独自の**混合精度ヘッド量子化（混合精度 ヘッド単位 量子化: MixHQ）**も導入する。

注意機構 ヘッドには、遠い過去から情報を取り出すことが多い**retrieval ヘッド**と、主に直近トークンへ注意を向ける**streaming ヘッド**のような役割差がある。

既存の強い枝刈りでは重要度の低いヘッド/トークンを完全に捨てることがある。MixHQは0か1かで消すのではなく、

- 長距離情報に重要なヘッド → 高精度
- 比較的重要度の低いヘッド → 低ビット

という連続的な割当てにする。

これにより、必要な情報を残しながら平均ビット幅を下げる。考え方はヘッド単位だけでなく層単位やトークン単位の重要度にも拡張できる。

## Offline: 数千候補から良いprofileだけを探す

### なぜ全探索しないのか

1 configurationを評価するには、実際にモデルを動かして

- 圧縮率
- 圧縮・展開速度
- タスク 精度

を測る必要がある。論文環境では1候補あたり約15分かかり、4,000候補超を総当たりすると約1,000時間になる。

そこでKVServeは**ベイズ最適化（Bayesian Optimization: BO）**を使う。

ベイズ最適化は「まだ試していないconfigurationの性能」を代理モデルから推定し、

- 良さそうなので試す候補
- まだ不確実なので情報を得るため試す候補

を選んで実測回数を減らす方法である。ここではガウス過程（Gaussian Process: GP）を代理モデルに使う。

探索初期は未知領域も広く調べ、後半は有望領域へ絞る。さらに、あるcandidateが品質条件を満たして高い圧縮率を得たなら明らかに弱い候補を捨て、品質が大幅に不足した場合にはより攻撃的な候補を捨てる双方向枝刈りも行う。

論文では4,000超candidateの総当たりが約1,000時間かかるところを、数十〜200回程度の評価へ減らし、代表的な設定で約20時間規模まで削減できるとしている。

## 3次元Pareto frontierとは何か

事前探索で得たcandidateをそのままオンラインで全部比べるわけではない。

KVServeは

- 品質
- 圧縮率
- 圧縮/展開遅延

の3軸で**パレート前線（Pareto frontier）**を作る。

あるプロファイル Aがプロファイル Bより「品質も高い、圧縮率も高い、処理も速い」ならBを選ぶ理由はない。このように他候補に完全に負けているプロファイルを捨て、どこかの条件では最適になり得る候補だけ残す。

これがオンライン controllerの小さなプロファイル libraryになる。

## Online: 今の回線なら何を使うべきか

実行時のservice 文脈を

`c = (workload, bandwidth, SLO, quality minimum)`

として扱う。

各圧縮プロファイルは概念的に

`p = (compression ratio, compression throughput, quality)`

で表せる。

無圧縮KV量を `V`、実効帯域を `B`、圧縮率を `cr`、圧縮+展開の実効スループットを `s` とすると、圧縮プロファイルの追加コストは大まかに

`圧縮・展開時間 V/s + 通信時間 V/(B×cr)`

になる。

ここで重要なのは、圧縮率だけ高くても `s` が遅ければ総時間は悪化することだ。

### 圧縮すべき帯域の境界

論文は、プロファイル `p` が無圧縮より速くなる条件を

`B < (1 - 1/cr) × s`

という帯域thresholdで表せることを示す。

つまりプロファイルごとに「この回線速度より遅いなら使う価値がある」という境界を事前計算できる。帯域が十分速ければ、そのプロファイルは候補から即座に除外できる。

論文のmotivation実験ではCacheGen、MixHQ、KIVIの有利な帯域域が異なり、一定以上の帯域では圧縮コストの方が高くなる。KVServeはこの「圧縮しない方がよい」領域も明示的に扱う。

## なぜonline banditまで必要なのか

事前 profiling値だけでは本番環境を完全には再現できない。

- GPU負荷が変わる
- ネットワーク contentionが変わる
- queueing オーバーヘッドが増える
- 圧縮カーネルの実効スループットが変わる

ためである。

そこで解析モデルがまず最適候補を2〜3個まで絞り、その近傍だけを軽量な**バンディット（bandit）**で比較する。

実測JCTと予測JCTの差を残差として指数移動平均（Exponentially Weighted Moving 平均: EWMA）で保持し、次回選択時に予測値へ補正を加える。完全なモデルをオンライン再学習するのではなく、**事前予測のずれだけを学習する**。

探索でSLOを壊し続けないよう、予測上SLOを満たさないプロファイルは除外し、直近で違反が続いたプロファイルは一時cooldownする。

1 リクエストあたり比較する候補は通常2〜3個で、controller decisionは評価上1 ms未満である。

## 評価条件

実装はvLLM 0.10.1へ組み込まれている。

### Model

- Qwen2.5-7B-Instruct
- Llama-3.1-8B-Instruct
- Qwen2.5-32B-Instruct

### Workload

事前 profilingにはGSM8K、HumanEval、Multi-News、Qasperを使用し、未見datasetとして2WikiMQAとHotpotQAも評価する。

### Hardware / network

- 事前 profiling: 4× A100 40GB
- デコード: H100
- consumer プリフィル: 2× RTX 4090 / 2× RTX 5090、10 Gbps
- workstation プリフィル: 2× RTX Pro 6000、50 Gbps
- datacenter プリフィル: 2× H100、100 Gbps

ネットワーク帯域は5〜100 Gbps程度まで制御して感度を測っている。

### Baseline

- 無圧縮BF16
- CacheGen
- KIVI
- DuoAttention

## 主要結果

### 1. PD分離では最大9.13×級のJCT改善

ハードウェア/ワークロードを変えてもKVServeは条件に合わせてプロファイルを切り替え、帯域制約が強い環境で大きくJCTを削減した。長文脈 ワークロードではHotpotQAで最大9.13×の改善を報告する。

逆にGSM8KやHumanEvalのような短文脈では、圧縮/展開コストが通信削減分を上回ることがある。静的手法はこの条件で無圧縮より遅くなるが、KVServeは圧縮を使わない経路へ戻る。

この「悪い状況では最適化を止める」こともKVServeの重要な成果である。

### 2. remote KV reuseでは最大32.8× TTFT短縮

remote KV プールから過去KVを読むprefix キャッシュ化構成では、帯域が遅すぎると既存システムはKV取得を諦めてプリフィルを再計算する場合がある。

KVServeは強い圧縮プロファイルを選ぶことでremote fetchをSLO内へ収め、5〜15 Gbpsの評価範囲でキャッシュ hitを成立させる。最大では再計算経路に対して**最初のトークンまでの時間（時間 To 最初の トークン: TTFT）を32.8×短縮**した。

### 3. 通信律速を計算律速へ戻す

Qwen2.5-32Bの長文脈評価では、無圧縮時に通信がJCTの82〜90%を占めた。KVServe適用後は通信比率が6〜9%まで低下した。

つまり単にネットワークを少し速くしたのではなく、システム全体のボトルネックを「ネットワーク waiting」から「本来のモデル 計算する」へ戻している。

### 4. 97%品質制約下で平均8.28×圧縮

Qwen2.5-7B-Instructの評価では、ワークロード-aware版のKVServe-Awareが平均相対精度 100.35%を保ちながら平均8.28×圧縮率を得た。Multi-Newsでは10.12×に達する。

これは「圧縮でモデル自体の能力が上がった」という意味ではなく、評価dataset上の測定変動を含めて比較対象と同等以上だったという結果として読むべきである。

## 何が新しいのか

KVServe以前にもKV 圧縮自体は多数存在する。違いは、**圧縮アルゴリズムを新しく1個提案することが主目的ではなく、複数の圧縮技術をサービング 条件に応じて選ぶ制御 平面を作ったこと**にある。

特に重要な差分は次の3点である。

1. KV 圧縮をtransform / quantizer / codecへ分解し、組合せを探索可能にした。
2. 事前ではBayesian optimizationで候補を圧縮し、オンラインでは帯域thresholdから不要候補を即除外する。
3. 実環境との差を小型banditで補正し、「帯域が速いなら圧縮しない」という選択も含めてJCT最小化を行う。

したがってKVServeはKV 圧縮論文であると同時に、**ネットワーク-aware サービング controller**として見ると理解しやすい。

## 限界

- 近似量子化を含むため完全無損失ではない。品質下限はdataset上の指標で管理され、未見分布で絶対保証されるわけではない。
- ワークロード-aware プロファイルは上位ルータ等からワークロード labelが得られることを前提とする。未知ワークロードにはmixed datasetから作ったUnified プロファイルを利用するが、タスク差を完全には吸収できない。
- 事前 profilingは全探索より大幅に軽いが、それでもモデル/ハードウェア/ワークロードごとにGPU-hours単位の事前作業が必要になる。
- オンライン モデルは実効帯域を重要状態として使うため、短時間で急変するネットワーク contentionをどの程度正確に追跡できるかが実運用上重要になる。
- 主評価はNVIDIA GPUとvLLM 0.10.1中心であり、別実行時や不均一 PD構成で同じ数値がそのまま得られるとは限らない。
- 最大32.8×はremote KV再利用を諦めて再計算する比較対象との比較を含むため、「圧縮 カーネル単体が32.8×速い」という結果ではない。

## 実装上の示唆

KV movementを最適化するとき、圧縮率だけを見るのは不十分である。

`転送前後の処理cost + network時間 + 品質制約`

をまとめてエンドツーエンドで判断しなければならない。特に高速linkでは圧縮そのものがボトルネックになり得るため、適応型 システムには**最適化を無効化する判断**も必要になる。

また、事前で巨大なcandidate spaceを十分小さくし、オンラインでは数候補だけを軽量制御する二段構成は、KV以外の重み オフロードやembedding 転送などにも応用可能な設計パターンである。
