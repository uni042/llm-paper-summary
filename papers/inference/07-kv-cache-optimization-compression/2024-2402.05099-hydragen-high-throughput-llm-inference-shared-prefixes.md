# Hydragen: High-Throughput LLM Inference with Shared Prefixes

## 概要

Hydragenは、多数の要求が同じ長い接頭辞を共有する大規模言語モデルの復号処理を、注意演算の実行方法から高速化する研究である。共通のシステム指示、少数例の例示、同一問題に対する多数の候補生成などでは、異なる要求が接頭辞の鍵・値キャッシュを共有する。既存のページ管理は同じ接頭辞の鍵・値を一度だけ保存してメモリ容量を節約できるが、注意演算のカーネルが要求ごとに共有鍵・値を読み直すなら、GPUの高帯域幅メモリ（HBM）に対する重複読出しは残る。

Hydragenは各要求の注意を「全要求に共通する接頭辞」と「要求ごとに異なる接尾部」へ分割する。両部分の注意出力と対数和指数（log-sum-exp; LSE）を計算し、正しい正規化係数で再結合すれば、全系列を一度に注意計算した場合と数学的に同じ出力になる。この分割によって、共有接頭辞に対する複数要求の問い合わせを一つの大きな行列としてまとめ、同じ鍵・値をGPU上で再利用できる。行列とベクトルの積を多数回繰り返す代わりに行列同士の積を使い、Tensor Coreの利用率も高める。

原著はCodeLlama-13Bを8枚のA100-40GBで実行し、大きなバッチと長い共有接頭辞でvLLMのページ注意に対して端点処理率最大32倍を報告する。共有接頭辞を約1Kから16Kへ伸ばしても、大規模バッチでHydragenの処理率低下は15%未満であるのに対し、比較したvLLMでは90%以上低下する。さらに木構造の接頭辞共有へ拡張し、競技プログラミングの候補生成で単一段階共有より実行時間を55%短縮する。

## 問題設定：容量共有だけでは帯域共有にならない

Transformerの自己注意は、問い合わせ行列 $Q$ と鍵・値行列 $K,V$ から $\operatorname{softmax}(QK^\top/\sqrt d)V$ を計算する。事前入力処理では多くの問い合わせが同時に存在するため、行列同士の積を効率よく使える。復号では一要求につき新しい問い合わせが一つだけなので、長い鍵・値に対する行列とベクトルの積となり、メモリ帯域が律速になりやすい。

複数要求をバッチ化すると、モデルの重みを使う線形層などは問い合わせをまとめて行列演算できる。しかし通常の注意は各要求の鍵・値キャッシュが異なるため、要求ごとに独立した行列とベクトルの積を実行する。バッチが大きくなるほど他の層の演算効率は上がる一方、注意の共有鍵・値読出しが支配的になりやすい。

共通接頭辞を持つ要求では、因果注意の性質によって接頭辞部分の鍵・値は同じになる。vLLMのPagedAttentionのようなメモリ管理方式は、同じ鍵・値を重複保存しないようにできる。しかし注意カーネルが各要求について共有接頭辞を個別に読むなら、HBMから同じ内容を何度も運ぶ。Hydragenは「保存容量の共有」と「演算時の読出しの共有」を分けて考え、後者を最適化する。

## 手法

### 1. 注意を共有接頭辞と固有接尾部へ厳密に分割

各要求の鍵・値を共通接頭辞 $K_p,V_p$ と要求固有の接尾部 $K_s,V_s$ に分ける。通常の注意は両部分を連結した行列へ一度に計算するが、Hydragenはそれぞれへ注意を計算し、最後に正規化を合わせて統合する。注意の出力だけを単純に足すと、各部分で独立にsoftmax正規化しているため、全体の注意とは一致しない。

接頭辞の注意出力を $O_p$、接尾部の注意出力を $O_s$、それぞれの対数和指数を $L_p,L_s$ とする。全体の注意出力は

$$O=\frac{e^{L_p}O_p+e^{L_s}O_s}{e^{L_p}+e^{L_s}}$$

で正確に再構成できる。対数和指数は各部分の指数化注意スコアの総和の対数であり、各部分の正規化済み出力を全体の正規化へ戻す役割を持つ。この式は近似的なKV圧縮ではなく、通常の注意と同じ数学的結果を得るための恒等変形である。

実装では指数の数値安定性を考慮してLSEを使い、必要な正規化情報だけを保持する。元の全注意行列をメモリに保存する必要はない。接頭辞と接尾部の二分割に限らず、複数部分へ分割した場合にも同じ考えで再結合できるため、階層的な共有へ拡張できる。

### 2. 要求間バッチ化：複数問い合わせを一つの共有KVへ適用

注意を二分割しただけでは、むしろ再結合の追加計算が発生するため高速化しない。Hydragenの中心は、共有接頭辞に対する注意を要求間でまとめることにある。バッチ内の各要求の問い合わせを縦に連結し、同じ共有接頭辞の鍵・値へ一度の大きな注意演算として適用する。

通常方式では各要求が一つの問い合わせベクトルで長い共有鍵・値を読むため、バッチ数だけ同じ鍵・値の読出しが繰り返される。Hydragenでは問い合わせをまとめて行列化し、一度読み込んだ共有鍵・値を複数問い合わせの積に使い回す。これによってHBM転送の費用を要求間で償却し、GPUの行列演算器が効率よく動く演算強度へ近づける。

共有接頭辞に対する問い合わせは互いに独立であり、他の要求の出力へ影響しない。したがって問い合わせを一つの大きな行列にまとめても、各要求の結果は変わらない。これは注意の意味を変更するのではなく、同じ計算を実行する順序とメモリアクセスを変更する最適化である。

### 3. 固有接尾部は通常の注意で処理する

要求ごとの接尾部は異なるため、共有接頭辞と同じように一つの鍵・値行列へまとめられない。Hydragenは固有接尾部の注意を通常の一問い合わせ型カーネルで計算し、LSEを使って接頭辞側の出力と結合する。したがって接尾部が長くなるほど、共有接頭辞の最適化が占める割合は小さくなる。

生成が進むと各要求の固有接尾部は伸びる。最初の生成トークンは共有接頭辞が支配的なのでHydragenの利得が大きいが、生成が長く続くと接尾部のメモリ読出しが増え、処理率が下がりやすい。原著の微小ベンチマークはこの効果を明示している。大規模バッチならどの生成長でも同じ倍率が得られるという設計ではない。

### 4. 階層的な接頭辞共有を木として扱う

実際の要求集合では、全要求に共通するシステム指示の下に、問題ごとに共通する文章があり、その下で候補回答ごとに異なる接尾部が付く場合がある。これは単一の共有接頭辞と固有接尾部の二分割ではなく、共有範囲が木構造になっている。Hydragenは木の各節点に対応する鍵・値へ注意を分割し、その節点の子孫要求の問い合わせをまとめて処理する。

例えば競技プログラミングで、全問題に共通する少数例プロンプト、同じ問題の候補に共通する問題文、候補ごとに異なる生成済みコードを考える。第一段階では全候補が少数例プロンプトを共有し、第二段階では同じ問題の候補だけが問題文を共有する。Hydragenは各段階の共有鍵・値へ対応する問い合わせをまとめ、節点ごとの注意出力とLSEを結合する。こうして二段階の重複読出しを削減する。

この方式には共有関係を知る仕組みが必要である。Hydragen自身は任意の要求から最適な木を発見するための配信スケジューラを主題としていない。既に把握された共有関係を使い、注意カーネルを効率よく実行する技術として理解すべきである。

### 5. 実装とカーネルの役割分担

原著の実装はLlama系モデルを対象とし、主要部分はPyTorchと既存の高速注意ライブラリを使う。共有接頭辞側にはflash-attn 2.3.6、接尾部側にはxFormers由来のTritonカーネルを使用する。接尾部の長さが生成中に変わってもCUDAグラフの制約を満たすため、接尾部に対応するカーネルを選んでいる。非階層の場合の正規化係数の結合にはTritonカーネルも用意する。

この構成は新しい注意の数学的性質を利用しつつ、複雑な独自CUDAカーネルを必須としないことが利点である。共有接頭辞の注意を一つの行列積として実行できれば、既存の高速な行列演算を活用できる。ただし要求の到着順、途中中断、連続バッチングなどを含む本番配信エンジンを完成させたという意味ではない。

### 6. 演算強度と高速化の上限

Hydragenが改善するのは主に共有接頭辞への注意であり、モデルの重みを読む費用や固有接尾部の注意費用を直接削減しない。小さなバッチではモデル重みの読出しが支配的になりやすく、注意を速くしても端点処理率の改善は小さい。大きなバッチでは他の層が行列演算として効率化され、共有接頭辞の注意が相対的に重くなるため、Hydragenの利得が大きい。

原著は注意計算を完全に省いた「No Attention」も比較する。これは機能的に正しいモデルではなく、注意が無限に速いと仮定した場合の処理率上限を測るための参照である。Hydragenの処理率がこの上限に近づくほど、残る律速が注意以外の層へ移ったと解釈できる。

## 評価

### 1. 端点評価の条件

| 項目 | 原著の条件 | 読み方 |

| 装置 | A100-40GBを8枚、テンソル並列 | 大バッチのKVを保持するため複数GPU使用 |
| 接頭辞長固定の試験 | 2048トークン、生成長128、バッチ数を変化 | 大バッチほど共有KVの読出し償却が効く |
| バッチ数固定の試験 | 1024要求、共有接頭辞長を約1K〜16Kへ変化 | 長い共有文脈での処理率低下を比較 |
| 比較 | FlashAttention、vLLM 0.2.7、vLLMのdetokenization無効版、No Attention | No Attentionは機能的に不正確な上限 |
| 注意カーネル試験 | A100-40GB 1枚、8問い合わせ頭・1KV頭、頭次元128 | 端点処理率とは別の局所評価 |
| 長文書質問応答 | Yi-6B-200K、A100-40GB 4枚、接頭辞19947 | 文書を共有する多数質問を比較 |
| 木状共有 | CodeLlama-7B、APPS 120問題、各128候補 | 二段階共有と単一段階共有を比較 |

主実験は多くの候補を同じプロンプトから生成する負荷であり、要求が互いに無関係な一般的な配信負荷ではない。比較相手のvLLMは0.2.7という当時の実装であり、現在の任意のvLLM版に対して同じ倍率が出ると断定できない。

### 2. CodeLlama-13Bの端点処理率

原著図3では、共有接頭辞2048トークンから128トークンを生成する条件でバッチ数を増やす。小さなバッチではHydragen、vLLM、FlashAttentionの処理率は近く、注意以外の層が大きな費用を占める。バッチが大きくなると共有接頭辞への注意の重複読出しが増え、Hydragenの優位が広がる。FlashAttentionの基準は接頭辞を要求ごとに重複保存するため、バッチ数が大きいとメモリ不足で実行できない条件がある。

バッチ数1024で共有接頭辞を約1Kから16Kへ伸ばすと、原著のvLLMは約5000トークン/秒弱から500トークン/秒未満へ低下する。一方Hydragenは処理率の低下を15%未満に抑え、最良の比較相手に対して最大32倍の端点処理率を報告する。これは接頭辞が長いほど、共有KVを一度読んで多数の問い合わせへ使う効果が大きくなるためである。

最大32倍はCodeLlama-13Bの特定の大規模バッチ・共有接頭辞長における比較結果であり、小さなバッチや短い共有接頭辞でも常に32倍になるわけではない。モデルの注意以外の層の費用と、接尾部の伸長による読出し費用が上限を決める。

### 3. No Attention上限とボトルネックの移動

No Attentionは自己注意計算を省く不正確な実装で、注意以外の処理だけで到達できる処理率の上限を示す。原著ではHydragenがこの上限に近い処理率を示す条件がある。これは注意を高速化すると、残りの時間がモデル重みの読出しや他の層へ移ることを意味する。

ただしNo Attentionは出力を正しく生成する方式ではないため、HydragenがNo Attentionに近いという結果を「Hydragenが注意を省略する」ことの証拠と解釈してはならない。Hydragenは全ての鍵・値を使う厳密な注意を保ち、演算のまとめ方だけを変える。

### 4. 注意カーネルの微小ベンチマーク

原著図4では単一A100-40GBで共有接頭辞長、バッチ数、固有接尾部長を変え、HydragenとFlashAttentionの注意計算を比較する。共有接頭辞が長く、バッチ数が大きく、固有接尾部が短いほどHydragenが有利である。共有接頭辞への注意だけを切り出した比較では、16倍を超える高速化を報告する条件がある。

接尾部が長くなると、要求ごとの接尾部注意を通常のカーネルで計算する費用が増えるため、Hydragen全体の注意高速化倍率は下がる。生成の初期段階で処理率が高く、出力が伸びるにつれて処理率が低下することも、この構造から説明できる。GPUの演算能力と帯域の比が異なる装置では利得も変わり、原著はL40Sなど別装置での追加結果も示している。

### 5. 長文書の多数質問：処理時間の比較

原著の長文書質問応答は、約19947トークンの共通接頭辞に文書と五つの少数例を含め、そこへ埋め込んだ人工的な事実に関する質問を多数処理する。モデルはYi-6B-200K、装置はA100-40GBを4枚使用する。Hydragenは256質問を処理する時間が、FlashAttention基準で64質問を処理する時間より短かった。

この結果は長い文書を多くの質問で共有する場合、共通接頭辞の注意計算をまとめることが有利であると示す。ただし図5の時間測定には文書接頭辞を最初に事前入力処理する時間が含まれない。したがって一回しか質問しない場合の総時間短縮をそのまま示すものではなく、既に共有接頭辞が処理済みで、多数の質問を生成する条件の結果である。

### 6. 木状共有：競技プログラミングの候補生成

原著はAPPSの120問題について、CodeLlama-7Bを使い、二つの例示を含む共通プロンプトから各問題128個の候補コードを生成する。全候補は例示プロンプトを共有し、同じ問題の候補はさらに問題文を共有する。単一段階共有では一方の共通部分しかまとめて処理できないが、木状共有では両段階で重複する鍵・値を再利用できる。

原著は木状共有を使うと、単一段階のHydragenに対して推論時間をさらに55%削減したと報告する。この55%は通常のvLLMに対する短縮率ではなく、既にHydragenを一段階で適用した方式に対する追加の短縮率である。比較基準を取り違えると階層共有の寄与を過大評価する。

### 7. KVメモリ共有とHBM読出し共有の差

PagedAttentionのようなメモリ管理は、同じ接頭辞の鍵・値を重複保存しないことでメモリ容量を節約する。一方Hydragenは、同じ鍵・値を注意演算で何度も読むことを減らす。原著のvLLM比較では、メモリ容量の重複が既に抑えられていても、大きなバッチで共有接頭辞の注意が帯域律速になり得ることを示す。

この違いはKVキャッシュ圧縮や量子化とも異なる。Hydragenは保持する鍵・値を削除せず、数値精度も変更しない。全注意と数学的に同じ出力を保ちながら、演算のまとめ方とGPUのメモリアクセスを変える。したがってキャッシュ容量の節約方式や共有接頭辞を検出するスケジューラとは補完的に利用できる。

## 既存研究との差

vLLMのPagedAttentionは共有接頭辞のKVをページ単位で重複保存しない仕組みを持つが、通常の注意カーネルでは各要求が共有KVを個別に読む。Hydragenは要求間で問い合わせをまとめ、同じ共有KVへ行列積を行うことで、容量だけでなくHBM読出し帯域を節約する。SGLangのRadixAttentionのような接頭辞共有の検出・管理方式は、どの要求が同じ接頭辞を持つかを把握するために有用であり、Hydragenは把握された共有を注意計算へ活かす技術として位置づけられる。

KV削除・圧縮方式は残す位置や精度を変更するため、場合によって品質とメモリの交換条件が生じる。Hydragenは注意の数学的結果を変えず、共有部分の読出しを一括化する。接頭辞の長さ、共有する要求数、固有接尾部の長さに応じて利得が変わる点が、一般的な一要求向けのKV圧縮とは異なる。

## 限界と未評価事項

Hydragenの利得は共有接頭辞の長さと同じ接頭辞を利用する要求数に依存する。バッチが小さい、共有接頭辞が短い、要求ごとの固有接尾部が長い条件では、共有KVの読出しをまとめる利得が小さくなる。注意以外の層が処理時間の大部分を占める場合にも、注意だけを高速化して得られる端点処理率の改善には上限がある。

本研究は共有関係を把握できる要求集合を前提とする。異なるタイミングで要求が到着する連続バッチング、要求の途中中断、再開、プリエンプション、異なる長さの要求を混合したスケジューリングなど、本番配信で必要な機能を網羅したわけではない。共有関係を検出する管理機構と、Hydragenの注意カーネルをどう統合するかは別の実装課題になる。

最大32倍はCodeLlama-13BとvLLM 0.2.7を比較した特定の大バッチ条件であり、現在の任意の配信エンジンやモデルに対する保証ではない。長文書質問応答の時間には共通接頭辞の最初の事前入力が含まれず、木状共有の55%削減は単一段階Hydragenを基準とする。各実験の比較基準と測定範囲を区別しなければならない。

実装は主としてLlama系の生成経路と既存の高速注意ライブラリを用いる。異なるGPUやTPUへの移植は可能性として論じられるが、すべての装置での同倍率の速度改善を実測したわけではない。固有接尾部が伸びるほど通常注意の読出し費用が増えるため、長時間生成の全期間で初期と同じ処理率を維持するものでもない。

最後に、HydragenはKVの容量そのものを削る方式ではないため、共有接頭辞がない多数の要求や、固有接尾部だけでGPUメモリが圧迫される負荷には別のメモリ管理が必要になる。共有接頭辞の検出、KVの保存・転送、注意の一括化を組み合わせ、実際の要求到着分布で端点性能を測ることが導入上の重要な条件である。
