# Hydragen: High-Throughput LLM Inference with Shared Prefixes

> 同じ長い接頭辞を共有する複数系列のクエリをまとめて処理し、共有KVを系列ごとに何度もHBMから読み直す無駄を減らす厳密な 注意機構手法。

## 概要

few-shot プロンプト、同じシステム プロンプトを使うchatbot、多数sampleを生成するself-consistencyなどでは、バッチ内の複数系列が長い接頭辞を共有する。

KV キャッシュ自体を1コピーに共有してメモリ容量を減らしても、通常のデコード 注意機構では各系列が同じ接頭辞 KVを個別にHBMから読み、1 クエリずつ計算するため、メモリ帯域の無駄が残る。

Hydragenは注意機構を**全系列で共有する接頭辞部分と、各系列だけが持つsuffix部分へ分ける**。共有接頭辞に対する複数系列のクエリをまとめて一度に計算することで、同じKVを何度も読み直す量を減らし、GPUが効率よく処理しやすい大きな行列計算へ変える。

KVを削除・近似する方式ではなく、通常注意機構と数学的に同じ出力を得る。

## 手法

### 1. Shared prefixとunique suffixを別々にattentionする

各系列全体へ一度に注意機構する代わりに、

- 全系列で共有される接頭辞
- 系列ごとに異なるsuffix

へ分けて注意機構を計算する。

共有側・suffix側それぞれについて注意機構出力と、softmaxで重みを正規化するために必要な値を保持し、最後に両者を正確に合成する。

論文ではこの正規化値の計算にlog-sum-expを使うが、重要なのは**接頭辞側とsuffix側を別々に計算しても、最後に通常注意機構と同じ結果へ戻せる**ことである。

### 2. 複数sequenceのqueryをまとめて共有KVへ当てる

通常デコードでは、系列ごとに `1 query × 長い共有KV` を繰り返すため、同じKVをHBMから何度も読む。

Hydragenは複数系列のクエリをまとめ、`多数query × 同じ共有KV` として一度に処理する。

これにより、1 クエリずつのmatrix-vector計算を繰り返す代わりに、複数クエリをまとめたmatrix-matrix計算にでき、**共有KVの再利用とGPU計算効率の両方を高める**。

論文ではこの系列間のまとめ処理を `inter-sequence batching` と呼ぶ。

### 3. Sequence固有suffixは通常attentionで処理する

系列固有suffixは他系列と共有できないため通常の注意機構で処理する。

最後に共有 接頭辞側とsuffix側の注意機構結果を、softmaxの正規化を崩さないように結合する。

### 4. Prefix共有が階層的な場合にも拡張できる

全リクエストが完全に同じ接頭辞を持つ場合だけでなく、

- 全リクエストで共通するシステム プロンプト
- その下でproblemごとに共通するプロンプト
- さらに各候補だけが持つsuffix

のように、共有範囲が木構造になっている場合にも適用できる。

## 評価

CodeLlama-13Bなどで共有-接頭辞 バッチを評価し、既存実装に対して**エンドツーエンド スループット最大32×**を報告する。

特にバッチサイズと共有 接頭辞が大きいほど利得が増える。

長い共有 文脈の評価では、接頭辞 lengthを1Kから16K トークンへ増やしても大バッチのHydragen スループット低下は15%未満だった一方、比較対象は90%以上低下した。

また木構造のプロンプト sharingをcompetitive programming ワークロードへ適用し、推論 時間を**55%削減**した。

## 既存研究との差

### vLLM / PagedAttentionとの違い

PagedAttentionは同じ接頭辞 KVを複数系列で共有してメモリ容量を減らせるが、注意機構計算自体は各系列について個別に行うため、共有 接頭辞 KVのメモリ 読み出すが繰り返される。

Hydragenは**KVを1コピーにするだけでなく、そのKVを複数系列のクエリでまとめて使う注意機構計算へ変える**ことで、HBM 帯域の重複まで減らす。

### SGLang / RadixAttentionとの違い

SGLangは、リクエストの接頭辞を木構造で管理し、複数リクエストに共通する接頭辞 KVを見つけて再利用する。

Hydragenは「どの接頭辞を共有できるかを見つける」ことより、**共有できると分かったKVを注意機構 カーネルでどう効率よく読むか**が中心である。

両者は補完的で、SGLang型キャッシュで共有接頭辞を見つけ、Hydragen型カーネルで共有部分の注意機構を高速化できる。

### KV compressionとの違い

KVを削除・量子化・圧縮せず、全KVを保持したまま同じ注意機構結果を出す。

したがって主な改善対象はKV容量ではなく、**共有KVへのHBM 読み出す回数とGPU上の注意機構計算効率**である。

## 限界

- 共有 接頭辞が短い、またはバッチサイズが小さい場合は複数クエリをまとめる効果が小さい。
- 固有 suffixが長くなるほど共有部分の割合が下がり、利得も小さくなる。
- 公開実装はfull 提供処理 engineではなく、論文時点では主にLlama-familyと専用生成 pathを対象とする。
- continuous batching、リクエスト arrival、preemptionなどproduction 提供処理機能は主題ではない。
- 実行時側がリクエスト間の接頭辞共有関係を把握できる必要がある。

## 一般的な実装上の含意

KV 接頭辞 sharingでは「同じKVを1コピーだけ保存する」だけでは十分ではない。デコード時に各リクエストがそのKVを別々に読めば、**メモリ 容量は節約できてもHBM 帯域はほぼ節約できない**。

共有 接頭辞を持つリクエストを同時に処理し、クエリ側をまとめて共有KVへ注意機構することで、キャッシュ reuseをメモリ節約から実際のスループット改善へつなげられる。
