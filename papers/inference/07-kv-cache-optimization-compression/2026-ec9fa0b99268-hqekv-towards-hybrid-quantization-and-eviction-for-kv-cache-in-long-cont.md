# HqeKV：重要度に応じて量子化と削除を併用する長文脈KVキャッシュ圧縮

## 一文解説

HqeKVは、注意重みだけでなく値ベクトルの値域を考慮してキー・値キャッシュを順位付けし、16・4・2・1ビットの保持と削除を組み合わせ、所与の記憶予算で推論品質を高める方式である。

## 概要

自己回帰型の大規模言語モデル（LLM）は、既存トークンのキー（K）と値（V）をキー・値キャッシュ（KV cache）に保持して重複計算を減らす。一方、文脈長や同時要求数が増えるほどキャッシュがGPUメモリを占め、実行可能なバッチ数を制約する。従来の低ビット量子化は多くのトークンに同じ精度を割り当て、削除方式は低重要度と判断したトークンの情報を完全に失う。両者を単純に組み合わせるだけでは、重要度の連続的な違いを扱いにくい。

HqeKVはキャッシュの扱いを、FP16保持、4ビット、2ビット、1ビット、削除という五つの選択肢へ広げる。注意重みの累積値をKの重要度とし、Vにはさらに各トークンの値域を掛けた指標を使う。精度ごとの割当比率は、校正データに対する出力分布の差を目的関数としたオフライン探索で決める。高精度ほど一様量子化が、1ビットでは正規化量子化が有利という実測結果も方式選択へ反映する。

著者の実機評価はRTX A6000（48GB）上のLlama-3.1-8B-InstructおよびQwen3-8Bで実施された。LongBenchのLlamaモデルでは、比較条件をそろえた削除方式CAKEの平均得点40.53に対してHqeKVは49.98を報告する。ただし、全ての比較対象・全条件で最速ではなく、初回トークン時間や1出力トークン当たりの時間が一部の低ビット方式より長い。論文の主な実証は「同じ記憶予算での品質と実装メモリ効率」であり、無条件の高速化ではない。

## 問題設定：一律の圧縮は異なるトークンを同じように傷める

KVキャッシュは長い入力のプリフィル（prefill）で構築され、復号（decoding）中に新しいトークンのKとVが追加される。通常のFP16保存では各要素に16ビット必要なため、モデル重みとは別にキャッシュの占有が伸びる。低精度化すれば保存量を減らせるが、数値の丸め誤差が注意計算の出力へ伝播する。削除は記憶量と逆量子化処理を減らせる反面、削除したK/Vを後続トークンが参照できない。

従来のKIVIやOTTのような方式は低ビット保存を中心とし、ZipCacheやKVTunerは複数精度の選択を取り入れる。CAKEは重要度に基づく削除を使う。しかし、重要度の高いトークンと低いトークンが混在するキャッシュで、削除・極低精度・中精度・高精度を一つの記憶制約の下で最適配分する余地が残る。しかも注意重みだけでは、値ベクトルの数値分布が量子化誤差へ与える影響を見落とす。

著者はこの不足を二つに分ける。第一に、各トークンを「保持か削除か」「低精度か高精度か」だけで決める粗い選択肢の問題。第二に、キーの注意スコアだけで値の変換損失を推定する問題である。前者に対して五段階の処理と比率探索、後者に対して値域を用いたK/V別の重要度指標を導入する。

## 手法

### 1. KとVで異なる重要度を計算する

プリフィル後、HqeKVは最近のクエリを用いて過去のキーへの注意重みを集計する。K側の重要度は累積注意重みであり、後続の生成がその位置を参照する度合いを近似する。一方、V側は同じ累積注意重みに、そのトークンの値ベクトルの最大値と最小値の差（値域）を掛ける。式の形では、Kの重要度を `metricK`、Vの値域を `RangeV` として、`metricV = metricK × RangeV` とする。

この区別は、注意出力が注意重みとVの積の総和になることに対応する。重みが大きい値だけでなく、同じビット幅に丸めると損失が大きくなりやすい広い値域のVも保護すべき、という判断である。著者は量子化中心からの二乗誤差の期待値を定式化し、値域と変換損失の正相関を数値積分と実際のVキャッシュで確認した。実キャッシュ1,000トークンの分析では、値域と変換損失のピアソン相関係数が4ビット0.96、2ビット0.96、1ビット0.95、削除0.91であった。これは重要度の妥当性を支える相関であり、全タスクの品質改善をこの相関だけで証明するものではない。

KとVでは量子化の方向も異なる。著者の実装はKにチャネル単位、Vにトークン単位の量子化を採用する。キャッシュを大きさGのまとまりに分け、まとまり内の重要度を平均して割当順位を決める。実験でのGは32、注意重み集計に用いる最近のトークン数mは20である。したがって、全履歴の注意重みを毎回再計算する方式ではなく、直近窓に基づく推定で管理費用を抑える。

### 2. 五つの保存動作をメモリ予算へ割り当てる

重要度の高いまとまりはFP16のまま残し、続くまとまりを4ビット、2ビット、1ビットで保存し、最も重要度の低いまとまりを削除する。論文は4・2・1ビットと削除の割合をそれぞれ `δ1, δ2, δ3, δ4` として、平均ビット数 `Bavg` に対して `4δ1 + 2δ2 + δ3 = Bavg` および `δ1 + δ2 + δ3 + δ4 = 1` の制約を課す。最重要の二つのまとまりをFP16で別途保持する例外があるため、この式だけをキャッシュ全体の厳密な実効ビット数と同一視してはいけない。

割当比率を人手で決める代わりに、木構造パルゼン推定器（Tree-structured Parzen Estimator; TPE）で1ビットと削除の割合を候補生成し、制約式から4・2ビットの割合を導く。校正用Wikitext-2の16,000トークン列を使い、非圧縮時と圧縮時のプリフィル出力の交差エントロピー差を損失とする。さらに低精度と削除への過度な配分を抑える正則化項 `αδ3 + βδ4` を加え、損失の小さい比率を選ぶ。論文の標準設定は200回探索、α=2、β=4である。

この探索は実要求ごとに瞬時に最適比率を求めるオンライン制御ではない。事前に決めた圧縮予算と校正データから比率を選ぶオフライン工程であり、ユーザーごと・タスクごとの最適比率へ動的に追従するわけではない。探索時間そのものも評価され、平均3.2ビット相当の設定では7分46秒を要した。起動・再設定費用として無視できないが、継続する推論の各トークンへそのまま加算される費用ではない。

### 3. ビット幅に合わせて量子化方式を切り替える

低ビット化では、最大値と最小値から等間隔の区間を作る一様量子化と、平均・標準偏差で正規化した後に正規分布の分位点へ写す正規化量子化を比較する。量子化群の大きさ32でLlama-3.1-8B-InstructのK/Vを調べると、Kの4ビット変換損失は一様5.28、正規化9.28で一様が良い。一方、Kの1ビットでは一様92.06、正規化37.44と関係が逆転する。Vの1ビットでも一様4.67、正規化2.05で正規化が有利だった。

HqeKVはこの観察に従い、4ビットと2ビットに一様量子化、1ビットに正規化量子化を採用する。つまり「重要度に応じて何ビットにするか」という配分と、「そのビット幅でどの符号化を使うか」を別々に設計する。高精度にしても同じ符号化を機械的に適用しないことが、混合精度の利点を実際の品質へつなぐ。

### 4. 復号中の更新とGPU上の実装

プリフィルで圧縮したキャッシュへ、新規トークンのK/Vをまず残差のFP16領域として追加する。復号中はT個のトークンが増えるごとに、保持済みの注意統計と値域を更新し、キャッシュの重要度を再評価して再量子化する。標準設定はT=32である。前回より低い精度への移行は追加量子化し、高い精度へ戻すべきと判断されても原則として以前の低精度表現を維持する。削除や量子化の情報損失を巻き戻せると仮定しない設計である。

この近似を支持する分析として、特定のDuReader例における二度目の圧縮では、低精度から高精度へ移る割合がKで計3.33%、Vで3.39%にとどまった。ただし、これは一例の測定であり、別の入力分布でも必ず少数になる保証ではない。再量子化は4096トークン文脈・バッチ10・128トークン生成の実験で、連続3回それぞれ0.52秒、0.36秒、0.33秒を要した。

実装面では、圧縮値を密に詰めるTritonカーネルと、逆量子化をベクトル・行列積に組み込む専用GPU処理を使う。保存する数値のビット幅だけを下げても、メタデータや詰め方が悪いと実メモリ使用量は十分に減らない。論文はKVTunerなどでビット詰めが不十分な場合を比較し、実際のGPUメモリ占有と処理時間を別々に測定している。

LongBenchの「平均得点」は複数課題の品質指標を集約したもので、トークン毎秒や圧縮率ではない。表4には、比較方式がメモリ不足（OOM）やCUDAエラーで走らなかった課題を平均から除いた行が含まれる。その行のHqeKV得点も同じ非失敗課題集合で再計算されている。したがって、同じHqeKV-3.2という表記でも、ZipCache比較用の部分集合とCAKE比較用の全体集合の平均値は異なる。

### 品質：同一予算での改善と、無圧縮との差

| モデル・比較条件 | 指標 | 比較対象 | HqeKV | 解釈 |
| --- | --- | ---: | ---: | --- |
| Llama-3.1-8B / LongBench / 2ビット | 平均得点 | KIVI 48.96 | 49.71 | 同じ低ビット級で0.75点改善 |
| Llama-3.1-8B / LongBench / 3.25ビット、CAKE比較 | 平均得点 | CAKE 40.53 | 49.98 | 削除のみより9.45点高い |
| Llama-3.1-8B / LongBench / 3.2ビット、CAKE比較 | 平均得点 | CAKE 40.30 | 49.91 | 同一予算の削除方式より高い |
| Llama-3.1-8B / LongBench / 3.2ビット、ZipCache比較可能課題 | 平均得点 | ZipCache 50.98 | 51.49 | 失敗課題を除いた共通部分集合で0.51点高い |
| Qwen3-8B / LongBench / 2ビット | 平均得点 | KIVI 50.36 | 51.37 | 1.01点高い。無圧縮FP16は51.24 |

Llamaの無圧縮FP16平均49.76に対し、HqeKV-2は49.71でわずかに低い。HqeKV-3.25の49.98はFP16よりわずかに高いが、圧縮自体が一般に精度を上げると解釈すべきではない。LongBench内の課題・集計方法・生成の変動を含む評価であり、重要なのは記憶制約下で削除方式より品質を保ちやすいことである。

### 記憶効率・遅延・負の結果

著者は文脈長を4Kから80Kまで変えた最大バッチ数と、文脈長4096でバッチを変えたメモリ使用量を測った。HqeKVは大部分の設定でより大きなバッチを扱い、メモリ使用量はOTTより平均29.6%、ZipCacheより8.3%、KVTunerより8.6%少ないと報告する。この差は論理的な平均ビット幅だけでなく、低ビット値の密な格納、方式ごとの付帯情報、実装差を含む測定結果である。

一方、初回トークン時間（Time to First Token; TTFT）は常に短いわけではない。Wikitext-2、文脈161トークン、生成338トークンのLlama実験では、HqeKV-2が10.64秒、KIVI-2が9.35秒、HqeKV-3.25が11.00秒、KVTuner-3.25が9.27秒だった。対照的にZipCache-3.2は20.13秒、HqeKV-3.2は11.18秒で、比較相手によって優劣が逆転する。

出力トークン当たり時間（Time Per Output Token; TPOT）も同様で、HqeKVはOTTとZipCacheより有利な条件があるが、KIVIやKVTunerより遅い場合がある。論文は文脈161・生成338、および文脈4096・生成128の二条件でこの傾向を図示した。TPOTは出力一個を追加する際の時間であり、品質得点や最大バッチ数と同じ尺度ではない。特に長文脈の高同時実行へ適用するときは、記憶削減の利得と逆量子化・再圧縮の実行費用を分けて見る必要がある。

### 構成要素除去実験と探索費用

Llama-3.1-8BのLongBenchで、HqeKV-3.2の平均49.91を基準に、値域を考慮する重要度を外すと49.78、精度別量子化方式を外して一様量子化だけにすると41.00、比率探索を外してランダム配分にすると49.80、削除を使わないと49.47になった。精度別方式の選択を外した影響がこの設定では特に大きく、単に五種類の保存先を用意するだけでは十分でないことが分かる。

比率探索の計算費用は3.2ビット設定で7分46秒。探索200回と300回では配分の差が小さく、標準設定では200回を採用した。比率探索はモデルごとの校正作業であり、リクエストごとのオンライン推論レイテンシとは区別する。ただしモデル変更や対象分布の変化に対して再校正が必要なら、運用上の費用になる。

## 既存研究との差

KIVIはKのチャネル方向、Vのトークン方向を使った低ビット量子化を実装するが、HqeKVはそこへ重要度別の多段精度配分と削除を統合する。ZipCacheは重要なトークンを区別する混合精度量子化である一方、HqeKVは1ビットと削除まで選択肢を広げ、精度ごとの符号化方式も切り替える。KVTunerは層ごとの感度を利用して精度を選ぶが、HqeKVはトークン・まとまりの重要度と保存動作を結び付ける。

CAKEはキャッシュ削除を中心に記憶予算を守る。HqeKVは「重要度が低いものを全て消す」代わりに、一部を1・2・4ビットで残す中間選択肢を持つため、後で参照される可能性がある情報を完全には捨てない。先行する量子化と削除の統合方式（EVICPRESS、MiniKV）との違いは、著者がK/V別重要度、五段階精度、比率探索、ビット幅別変換方式を一体として最適化した点にある。

## 限界・実装状況

論文自身は、オフライン比率探索がユーザーやタスクごとの異質性を考慮しないこと、1ビットの正規化量子化でも変換損失が残ること、固定再量子化間隔Tが文脈や負荷に応じた品質・遅延の感度を持つこと、マルチモーダルモデルでの挙動が未検証であることを限界として挙げる。重要度が途中で変わっても、既に低ビット化・削除した情報は完全には復元できないため、履歴依存の誤差が起こり得る。

評価対象はRTX A6000上の8B級モデルであり、複数GPU分散、別世代GPU、さらに大規模な混合専門家モデル（Mixture of Experts; MoE）に同じ性能差が出るかはこの実験だけでは判断できない。また、品質改善の比較にはOOMやCUDAエラーを起こした方式を含むため、非失敗課題だけの平均と全課題平均を混ぜると優位性を過大評価する。高速化を主目的とする場合はTTFT/TPOTの負の結果を見落としてはならない。

公式実装は論文に記載された `skywclouds/HqeKV` で公開されている。著者が報告したGPU専用カーネルを含む実装と、汎用サービング基盤への標準搭載とは別であり、vLLMやllama.cpp等への統合を確認したとは記録しない。再現時にはキャッシュの実効ビット幅、残差FP16領域、ビット詰め、量子化メタデータ、校正比率、再量子化間隔を揃える必要がある。
