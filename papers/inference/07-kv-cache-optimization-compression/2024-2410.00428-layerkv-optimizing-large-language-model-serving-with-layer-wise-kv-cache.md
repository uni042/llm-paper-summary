# LayerKV: Optimizing Large Language Model Serving with Layer-wise KV Cache Management

## 概要
LayerKVは、長文脈LLMの最初のトークンまでの時間（Time to First Token; TTFT）が増える主因を、プリフィル計算そのものだけでなく「十分なGPU KVブロックが空くまで新規リクエストを開始できない待ち行列」と捉え、KVキャッシュ管理の粒度をリクエスト単位から層単位へ細かくするserving手法である。

vLLMのPagedAttentionではKVメモリ断片化は抑えられるが、新規prefillを入れるにはそのリクエストが必要とするKVブロックをGPU上で確保する必要がある。長いpromptほど必要ブロックが増え、GPUメモリが足りなければ先行リクエストが終了してブロックを返すまで待つ。LayerKVは、一つのリクエストの全層KVを同時にGPUへ置かず、層ごとにGPU/CPUへ配置・swapし、prefill計算とPCIe転送を重ねる。これにより新規promptが必要とする瞬間的GPU KV量を下げ、待ち行列を短縮する。

ただしCPU offloadを増やしすぎるとdecode時のTime Per Output Token（TPOT）とthroughputが悪化する。そこでTPOTのサービス水準目標（Service Level Objective; SLO）から「今何件のprefillを割り込ませてもよいか」を計算するSLO-aware schedulerを組み合わせる。評価では7B〜70B、1〜4 GPUでvLLMと比較し、平均TTFT最大69倍、P99 TTFT最大45倍の改善、SLO違反率17.7〜28.7ポイント低下を報告する。

## 問題設定
論文のLlama-2-7B・単一L20実験では、promptを128から16K tokenへ伸ばすとTTFTは急激に増える一方、TPOTはより緩やかに増える。TTFTを待ち時間とprefill実行時間に分解すると、1024 token程度から待ち行列時間が支配的になる。

背景にはGPUメモリのKV block予約がある。serving runtimeはモデル重みとactivation用領域を除いたGPUメモリの一定割合をKV blockへ割り当てる。しかし最大入力長を大きく設定するとactivation profilingに必要なメモリも増え、KV blockとして確保できる量が減る。長い新規requestが到着したとき、必要KV block数が空きblockを上回れば、そのrequestは先行decodeが完了してblockが解放されるまでprefillを始められない。

単純なCPU offloadならGPU容量は増やせるが、decode中にKVをPCIe経由で戻すことでTPOT・QPSを落とす。LayerKVの課題は、(1) 新規prefillを早く開始してTTFTを下げる、(2) 既存decodeのTPOT SLOを守る、(3) PCIe通信を演算へ隠してQPS低下を抑える、の三つを同時に満たすことである。

## 手法

### 1. SLO-aware scheduler
schedulerはdecode中の各requestについて、既に費やした時間 (T_{past}) と生成済みtoken数 (N_{past}) を監視し、最終生成長を分類器で予測して残りtoken数 (N_{future}) と残り時間 (T_{future}) を見積もる。

TPOT上限を (T_{tpot}) とすると、そのrequestが追加prefillに許せる遅延余裕を
[
T_{allow_prefill}=T_{tpot}(N_{past}+N_{future})-(T_{past}+T_{future})
]
とする。待ち行列の先頭からprefill時間を推定し、その合計がdecode中requestの最小余裕を超えない最大件数だけを今回のiterationへ追加する。これによりTTFTだけを優先してdecodeを長時間止めることを防ぐ。

### 2. 層単位KV block allocation
新規prefillの全層KVをGPUへ残すのではなく、モデル (L) 層のうち最低 (x) 層だけをGPUに保持し、残り (L-x) 層をCPUへ非同期offloadする。(x) は「offload時間がprefill計算時間以下となり、PCIe転送を演算で隠せる」最小値から決める。

offload量は系列長に線形だがprefill計算は長文脈で超線形に増えるため、promptが長いほど通信を隠しやすい。十分長い場合は (x=0)、つまり全層KVをCPUへ流してもprefill計算の背後に隠せる。一方、短いpromptでは演算時間が短く、ある程度の層をGPUへ残さないとPCIeがcritical pathになる。

### 3. 将来のblock不足を予測して追加offload
最低 (x) 層をGPUへ置いても、その後のrequest到着でblock不足が起きる可能性がある。LayerKVは
[
Avail(t+1)=Avail(t)+Released(t)-Allocated(t)
]
で近未来の空きblock数を予測する。requestの終了予測にはschedulerと同じ出力長予測を用いる。

空きblockが閾値を下回ると、最近処理したrequestからまず (x/2) 層、なお不足する場合は残りもCPUへ追い出す。つまりGPU上の「最低保持層」は固定予約ではなく、資源圧迫時には解放できる送信bufferとして扱う。

### 4. 層を交互配置して通信を演算へ重ねる
GPUに残す層を連続させず、モデル深さ方向へ均等に散らす。8層中4層を保持する例では1,3,5,7層をGPUに、0,2,4,6層をCPUへ置く。0層KVを転送している間に0〜1層の計算を進めるなど、次に必要なCPU側KVの転送猶予を作る。

従来のrequest-wise block tableへ「このblockのどの層がGPU/CPUにあるか」という層情報を追加し、各層のattention実行時に正しい場所からKVを参照する。実装は物理KV領域を一つのPyTorch tensorとして確保し、層単位の論理割当を可能にする。

### 5. multi-GPU時のPCIe競合回避
NVLinkがないtensor-parallel環境ではall-reduceとCPU-GPU KV swapが同じPCIeを使うため、同時実行するとcritical pathのcollectiveを遅らせる。LayerKVはswap開始前にPCIe使用状況を確認し、all-reduce中ならswapを延期する。さらに転送を小さなsubunitへ分割し、各単位で再チェックして長時間PCIeを占有しない。

専用CUDA streamでGPU計算とKV transferを非同期化し、CPU側ではpinned memoryからpageable memoryへのcopyを別threadへ逃がす。

## 評価

### 実験環境
モデルはLlama-2-7B、Yi-34B-200K、Llama-3.1-70B。サーバはNVIDIA L20 48GBを8基、CPU 64 core、host memory 2048GBで、GPU-CPU間はPCIe接続である。PyTorch 2.4.0、CUDA 12.2、vLLM 0.5.5を用いる。

モデル規模に応じてLlama-2-7Bは1 GPU、Yi-34Bは2 GPU、Llama-3.1-70Bは4 GPU、tensor parallel degreeはそれぞれ1/2/4とする。workloadは固定長promptとShareGPTで、baselineは同版vLLMである。

### 文脈長を変えた結果
request arrival rateを1 req/sに固定してprompt長を伸ばすと、vLLMのTTFTはKV block待ちのため急増するが、LayerKVは緩やかに増加し、差は最大で一桁以上に広がる。対してthroughputは両者とも長文脈で低下するものの、この低負荷条件ではほぼ同等である。

これはLayerKVがprefill計算自体を近似・省略したのではなく、GPU上へ同時常駐させるKV量を減らして待ち行列を解消していることと対応する。

### arrival rate・tail latency
ShareGPTでarrival rateを上げると、vLLMは混雑点からqueueingが急増する。LayerKVは平均TTFTを最大69倍、P99 TTFTを最大45倍短縮する。高負荷でCPUからKVを戻すdecodeが増えるためthroughputはvLLMをわずかに下回るが、GPUに残せる層を最大化する割当によって差を3%未満へ抑える。

### SLO違反
Llama-2-7BでTTFT SLO=3000 ms、TPOT SLO=200 msとし、いずれかを超えれば違反とする。vLLMは6 req/s付近からTTFT違反が急増するのに対し、LayerKVはSLO違反率を17.7〜28.7ポイント低く維持する。

schedulerを外したLayerKVは、5.5 req/s付近でprefillを入れすぎてTPOTが悪化し、場合によってvLLMよりSLO違反が多くなる。したがって層単位offloadだけでは不十分で、TTFT削減を既存decodeのTPOT budget内へ制限するschedulerが必要である。

### 並列度
Yi-34B-200Kでtensor parallel degreeを増やすと、GPU計算能力と総メモリが増えてvLLM側の資源競合も緩和される。それでもLayerKVのTTFT優位は残り、並列度が高いほどthroughput差は縮む。層単位管理は単一GPUだけでなくmulti-GPUでも適用できることを確認している。

## 既存研究との差
PagedAttention/vLLMはKVを非連続blockとして管理し断片化を減らすが、基本管理単位はrequest全体である。既存CPU offloadもrequest単位で扱うものが多い。LayerKVは一requestのKVを層ごとにGPU/CPUへ分割できるため、「prefill開始に必要なGPU KV量」をより細かく制御できる。

またDistServeなどはprefill/decodeを別GPUへ分離し、sequence/tensor parallelは追加GPUで計算・メモリを分散する。LayerKVは追加hardwareなしでも動作し、それらと直交的に組み合わせられる。KV量子化・pruningのようにKV値自体を変えないため、出力品質を近似で犠牲にしない点も異なる。

## 限界
LayerKVはCPU host memoryと十分なPCIe帯域を前提とする。短いpromptではprefill計算が小さく転送を隠しにくいため、GPUへ残す層数が増え、queueing削減効果も小さくなる。高負荷ではdecode時のhost-to-device transferが残るため、throughputはvLLMより最大3%弱低下する条件がある。

出力長予測がschedulerの将来TPOT余裕とblock解放予測に使われるため、予測誤差が大きいworkloadでは保守的な見積もりでTTFT利得が減るか、逆にTPOT違反を招く可能性がある。

評価hardwareはL20/PCIeサーバで、NVLink/NVSwitchや異種GPU、複数node間のnetwork fabricは主対象ではない。また論文自身がfuture workとしてKV量子化とprefill-decode分離の統合を挙げており、それらを含む現代的serving stackでの複合効果は未評価である。
