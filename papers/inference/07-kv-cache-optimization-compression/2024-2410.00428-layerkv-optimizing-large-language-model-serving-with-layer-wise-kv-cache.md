# LayerKV: Optimizing Large Language Model Serving with Layer-wise KV Cache Management

## 概要
LayerKVは、長文脈LLMの最初のトークンまでの時間（時間 to First トークン; TTFT）が増える主因を、プリフィル計算そのものだけでなく「十分なGPU KVブロックが空くまで新規リクエストを開始できない待ち行列」と捉え、KVキャッシュ管理の粒度をリクエスト単位から層単位へ細かくするサービング手法である。

vLLMのPagedAttentionではKVメモリ断片化は抑えられるが、新規プリフィルを入れるにはそのリクエストが必要とするKVブロックをGPU上で確保する必要がある。長いプロンプトほど必要ブロックが増え、GPUメモリが足りなければ先行リクエストが終了してブロックを返すまで待つ。LayerKVは、一つのリクエストの全層KVを同時にGPUへ置かず、層ごとにGPU/CPUへ配置・スワップし、プリフィル計算とPCIe転送を重ねる。これにより新規プロンプトが必要とする瞬間的GPU KV量を下げ、待ち行列を短縮する。

ただしCPU オフロードを増やしすぎるとデコード時の時間 Per Output トークン（TPOT）とスループットが悪化する。そこでTPOTのサービス水準目標（Service Level Objective; SLO）から「今何件のプリフィルを割り込ませてもよいか」を計算するSLO-aware スケジューラを組み合わせる。評価では7B〜70B、1〜4 GPUでvLLMと比較し、平均TTFT最大69倍、P99 TTFT最大45倍の改善、SLO違反率17.7〜28.7ポイント低下を報告する。

## 問題設定
論文のLlama-2-7B・単一L20実験では、プロンプトを128から16K トークンへ伸ばすとTTFTは急激に増える一方、TPOTはより緩やかに増える。TTFTを待ち時間とプリフィル実行時間に分解すると、1024 トークン程度から待ち行列時間が支配的になる。

背景にはGPUメモリのKV ブロック予約がある。サービング ランタイムはモデル重みと活性値用領域を除いたGPUメモリの一定割合をKV ブロックへ割り当てる。しかし最大入力長を大きく設定すると活性値 profilingに必要なメモリも増え、KV ブロックとして確保できる量が減る。長い新規リクエストが到着したとき、必要KV ブロック数が空きブロックを上回れば、そのリクエストは先行デコードが完了してブロックが解放されるまでプリフィルを始められない。

単純なCPU オフロードならGPU容量は増やせるが、デコード中にKVをPCIe経由で戻すことでTPOT・QPSを落とす。LayerKVの課題は、(1) 新規プリフィルを早く開始してTTFTを下げる、(2) 既存デコードのTPOT SLOを守る、(3) PCIe通信を演算へ隠してQPS低下を抑える、の三つを同時に満たすことである。

## 手法

### 1. SLO-aware scheduler
スケジューラはデコード中の各リクエストについて、既に費やした時間 (T_{過去}) と生成済みトークン数 (N_{過去}) を監視し、最終生成長を分類器で予測して残りトークン数 (N_{将来}) と残り時間 (T_{将来}) を見積もる。

TPOT上限を (T_{tpot}) とすると、そのリクエストが追加プリフィルに許せる遅延余裕を
[
T_{allow_プリフィル}=T_{tpot}(N_{過去}+N_{将来})-(T_{過去}+T_{将来})
]
とする。待ち行列の先頭からプリフィル時間を推定し、その合計がデコード中リクエストの最小余裕を超えない最大件数だけを今回のiterationへ追加する。これによりTTFTだけを優先してデコードを長時間止めることを防ぐ。

### 2. 層単位KV block allocation
新規プリフィルの全層KVをGPUへ残すのではなく、モデル (L) 層のうち最低 (x) 層だけをGPUに保持し、残り (L-x) 層をCPUへ非同期オフロードする。(x) は「オフロード時間がプリフィル計算時間以下となり、PCIe転送を演算で隠せる」最小値から決める。

オフロード量は系列長に線形だがプリフィル計算は長文脈で超線形に増えるため、プロンプトが長いほど通信を隠しやすい。十分長い場合は (x=0)、つまり全層KVをCPUへ流してもプリフィル計算の背後に隠せる。一方、短いプロンプトでは演算時間が短く、ある程度の層をGPUへ残さないとPCIeが重要 経路になる。

### 3. 将来のblock不足を予測して追加offload
最低 (x) 層をGPUへ置いても、その後のリクエスト到着でブロック不足が起きる可能性がある。LayerKVは
[
Avail(t+1)=Avail(t)+Released(t)-Allocated(t)
]
で近未来の空きブロック数を予測する。リクエストの終了予測にはスケジューラと同じ出力長予測を用いる。

空きブロックが閾値を下回ると、最近処理したリクエストからまず (x/2) 層、なお不足する場合は残りもCPUへ追い出す。つまりGPU上の「最低保持層」は固定予約ではなく、資源圧迫時には解放できる送信bufferとして扱う。

### 4. 層を交互配置して通信を演算へ重ねる
GPUに残す層を連続させず、モデル深さ方向へ均等に散らす。8層中4層を保持する例では1,3,5,7層をGPUに、0,2,4,6層をCPUへ置く。0層KVを転送している間に0〜1層の計算を進めるなど、次に必要なCPU側KVの転送猶予を作る。

従来のリクエスト-wise ブロック tableへ「このブロックのどの層がGPU/CPUにあるか」という層情報を追加し、各層のattention実行時に正しい場所からKVを参照する。実装は物理KV領域を一つのPyTorch テンソルとして確保し、層単位の論理割当を可能にする。

### 5. multi-GPU時のPCIe競合回避
NVLinkがないテンソル-並列環境では全削減とCPU-GPU KV スワップが同じPCIeを使うため、同時実行すると重要 経路のcollectiveを遅らせる。LayerKVはスワップ開始前にPCIe使用状況を確認し、全削減中ならスワップを延期する。さらに転送を小さなsubunitへ分割し、各単位で再チェックして長時間PCIeを占有しない。

専用CUDA streamでGPU計算とKV 転送を非同期化し、CPU側ではpinned メモリからpageable メモリへのcopyを別threadへ逃がす。

## 評価

### 実験環境
モデルはLlama-2-7B、Yi-34B-200K、Llama-3.1-70B。サーバはNVIDIA L20 48GBを8基、CPU 64 core、ホスト メモリ 2048GBで、GPU-CPU間はPCIe接続である。PyTorch 2.4.0、CUDA 12.2、vLLM 0.5.5を用いる。

モデル規模に応じてLlama-2-7Bは1 GPU、Yi-34Bは2 GPU、Llama-3.1-70Bは4 GPU、テンソル 並列 次数はそれぞれ1/2/4とする。ワークロードは固定長プロンプトとShareGPTで、比較基準は同版vLLMである。

### 文脈長を変えた結果
リクエスト 到着 率を1 req/sに固定してプロンプト長を伸ばすと、vLLMのTTFTはKV ブロック待ちのため急増するが、LayerKVは緩やかに増加し、差は最大で一桁以上に広がる。対してスループットは両者とも長文脈で低下するものの、この低負荷条件ではほぼ同等である。

これはLayerKVがプリフィル計算自体を近似・省略したのではなく、GPU上へ同時常駐させるKV量を減らして待ち行列を解消していることと対応する。

### arrival rate・tail latency
ShareGPTで到着 率を上げると、vLLMは混雑点から待ち行列が急増する。LayerKVは平均TTFTを最大69倍、P99 TTFTを最大45倍短縮する。高負荷でCPUからKVを戻すデコードが増えるためスループットはvLLMをわずかに下回るが、GPUに残せる層を最大化する割当によって差を3%未満へ抑える。

### SLO違反
Llama-2-7BでTTFT SLO=3000 ms、TPOT SLO=200 msとし、いずれかを超えれば違反とする。vLLMは6 req/s付近からTTFT違反が急増するのに対し、LayerKVはSLO違反率を17.7〜28.7ポイント低く維持する。

スケジューラを外したLayerKVは、5.5 req/s付近でプリフィルを入れすぎてTPOTが悪化し、場合によってvLLMよりSLO違反が多くなる。したがって層単位オフロードだけでは不十分で、TTFT削減を既存デコードのTPOT budget内へ制限するスケジューラが必要である。

### 並列度
Yi-34B-200Kでテンソル 並列 次数を増やすと、GPU計算能力と総メモリが増えてvLLM側の資源競合も緩和される。それでもLayerKVのTTFT優位は残り、並列度が高いほどスループット差は縮む。層単位管理は単一GPUだけでなくmulti-GPUでも適用できることを確認している。

## 既存研究との差
PagedAttention/vLLMはKVを非連続ブロックとして管理し断片化を減らすが、基本管理単位はリクエスト全体である。既存CPU オフロードもリクエスト単位で扱うものが多い。LayerKVは一リクエストのKVを層ごとにGPU/CPUへ分割できるため、「プリフィル開始に必要なGPU KV量」をより細かく制御できる。

またDistServeなどはプリフィル/デコードを別GPUへ分離し、sequence/テンソル 並列は追加GPUで計算・メモリを分散する。LayerKVは追加ハードウェアなしでも動作し、それらと直交的に組み合わせられる。KV量子化・pruningのようにKV値自体を変えないため、出力品質を近似で犠牲にしない点も異なる。

## 限界
LayerKVはCPU ホスト メモリと十分なPCIe帯域を前提とする。短いプロンプトではプリフィル計算が小さく転送を隠しにくいため、GPUへ残す層数が増え、待ち行列削減効果も小さくなる。高負荷ではデコード時のホスト-to-デバイス 転送が残るため、スループットはvLLMより最大3%弱低下する条件がある。

出力長予測がスケジューラの将来TPOT余裕とブロック解放予測に使われるため、予測誤差が大きいワークロードでは保守的な見積もりでTTFT利得が減るか、逆にTPOT違反を招く可能性がある。

評価ハードウェアはL20/PCIeサーバで、NVLink/NVSwitchや異種GPU、複数node間のnetwork fabricは主対象ではない。また論文自身が将来 workとしてKV量子化とプリフィル-デコード分離の統合を挙げており、それらを含む現代的サービング stackでの複合効果は未評価である。
