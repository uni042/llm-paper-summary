# HeadWiseKV: Budgeted Per-Head Cache Residency for Hybrid Long-Context Language Models

> **HeadWiseKVは、長文脈modelに少数だけ残っているglobal attentionのKV cacheを「全部のheadで同じ長さ保存」するのをやめ、headごとに必要な履歴長を事前較正して、本当に必要な長さだけGPUへ物理確保する。**

## 概要

最近のlong-context modelには、すべてのlayerで通常の全域attentionを行うのではなく、局所attention、recurrent layer、linear-attention系layerなどを混ぜる**hybrid architecture**が増えている。

こうしたlayerは過去token全体のKV cacheをそのまま保持しないため、通常のTransformerよりcontext長に対するmemory増加を抑えやすい。そこで一見すると「hybrid modelならKV cache問題はほぼ解決した」ように見える。

しかし実際には、長距離情報を拾うために少数の**全域注意（global attention）layer**が残されている。このlayerは過去token全体へattentionできるので、そこで使うKV cacheは依然context長に比例して増える。layer数が少なくても、contextが100K tokenを超えるとこの残存KVだけでGPU memoryの上限を決めることがある。

HeadWiseKVは、この残存global KVをさらに見ると、**すべてのKV headが同じ長さの履歴を必要としているわけではない**ことに着目する。

あるheadは遠く離れたtokenを検索するため長い履歴を必要とする。一方、別のheadは実際には近傍tokenしか参照せず、8K程度のrecent historyだけ残しても出力がほとんど変わらない場合がある。

そこでHeadWiseKVは、各物理KV headへ

- 8K token
- 16K token
- 32K token
- full history

のような複数段階の保存窓を割り当てる。

重要なのは、古いtokenをattention maskで「見ないことにする」だけではない。runtimeは**選ばれた窓の分しかKV memoryを実際に確保しない**。そのためpeak GPU memoryが本当に減り、OOMするまで使えるcontext長を伸ばせる。

## 背景: 「attention head」と「KV head」は同じとは限らない

### query headとKV head

通常のmulti-head attentionでは複数のattention headがあり、それぞれquery、key、valueを持つ。

しかし最近のLLMでは、KV cacheを小さくするために**グループ化クエリ注意（Grouped-Query Attention; GQA）**を使うことが多い。GQAでは複数のquery headが同じkey/value headを共有する。

たとえば32個のquery headに対して8個しかKV headがないmodelなら、4個のquery headが1個のKV headを共有する。

この場合、cache memoryの単位として重要なのはquery headではなく**物理KV head**である。4個のquery headが同じKVを読むため、そのうち1個だけ8K、残りを32Kという保存はできない。

HeadWiseKVはこの共有関係を踏まえ、**物理KV headごと**に履歴長を割り当てる。

## なぜ全headへ同じwindowを割り当てると無駄が出るのか

32K contextで、あるKV headが8Kしか必要としていないとする。

full historyなら32K token分のkey/valueを保存する。8K windowなら保存量はその1/4になる。

しかし別のheadが長距離retrievalを担当していて32K全部必要なら、そのheadまで8Kへ縮めると品質が落ちる。

したがって、全headを一律8Kにする方式はmemoryは減るが品質を壊しやすい。全headを32K/fullにすれば品質は守れるがmemory削減が小さい。

HeadWiseKVはこの中間として、

- 長距離依存に敏感なhead → full / 32K
- 中距離で十分なhead → 16K
- 近距離中心のhead → 8K

のように**同じlayer内でも異なるmemory budgetを与える**。

## 手法のあらまし

### 1. 保存候補を連続値ではなく有限のwindow codebookへする

理論上はheadごとに12,347 token、18,222 tokenのような任意長を選べる。しかし候補が無限に近いと較正とruntime実装が複雑になる。

そこでHeadWiseKVは候補集合を

`W = {8K, 16K, 32K, full}`

のような有限の**window codebook**へ制限する。

各global-attention layerの各物理KV headについて、この中から1つ選ぶ。最終policyは

`layer × KV head → 保存window`

というmatrixになる。

これはrequestが来るたびattention scoreを見てtokenを選ぶdynamic evictionとは違う。policyはofflineで一度作り、serving前に固定する。

### 2. 「率–歪み問題（rate–distortion problem）」とは何か

論文ではこの割当を制限付きの**率–歪み（rate–distortion）問題**として表現する。

言葉だけ見ると難しいが、意味はかなり単純である。

- **rate**: どれだけKV memoryを使うか。
- **distortion**: Full-KV modelの出力からどれだけずれるか。

つまり、

> 「使えるKV memoryは全量の70%まで」というbudgetの中で、Full-KVに最も近い動作をするhead別window組合せを探す

という問題である。

全headの候補を総当たりすると、head数が増えるほど組合せ数が指数的に増える。たとえば100 decision unitに4候補ずつあれば `4^100` 通りになり、実際にmodelを走らせて全部比較するのは不可能である。

そこでHeadWiseKVはSeqCalibという逐次較正に落とす。

### 3. SeqCalib: layerを下から順番に決める

SeqCalibは**逐次較正（Sequential Calibration）**の略で、Transformerの実行順にlayerを処理する。

まず最初のconfigurable global-attention layerを調べ、各headについて候補windowを試す。

- 8KでもFull-KVと十分近い → 8K
- 8Kではずれるが16Kなら許容範囲 → 16K
- 32Kまで必要 → 32K
- どれもだめ → full

という形で、許容品質を満たす最短windowを選ぶ。

ここだけなら普通のper-head calibrationに見える。

HeadWiseKVで重要なのは、**次のlayerを較正するとき、前のlayerをすでに短縮した実deployment状態でmodelを動かす**ことにある。

### 4. なぜ下位layerの設定を反映しないといけないのか

layer 10のKVを短縮すると、そのattention outputが少し変わる可能性がある。その変化はlayer 11、12、13…へ伝播する。

もしlayer 20を較正するとき、layer 10〜19を全部Full-KVのままにして評価すると、実deployment時とは異なるhidden stateを見てwindowを選ぶことになる。

その結果、offlineでは16Kで十分だったheadが、実際には下位layerの圧縮誤差と重なって32K必要になるかもしれない。

SeqCalibはこれを避けるため、layerを上へ進むたびに**すでに選んだlower-layer policyをfreezeして適用**する。

つまり、

1. layer 10のpolicyを決める。
2. layer 10をそのpolicyで動かした状態でlayer 20を評価する。
3. layer 20を決める。
4. layer 10 + 20を両方圧縮した状態で次layerを評価する。

という順番になる。

これが論文のいう**deployment-conditioned calibration**である。

### 5. 類似度floorを満たす最短windowを選ぶ

各headの候補windowを試すとき、Full-KVで得られるreference outputと、候補windowで得られるoutputの類似度を測る。

userが設定したthreshold `τ` を満たす候補の中から最短windowを採用する。

`τ`を高くするとFull-KVに近い挙動を求めるため長いwindowが増え、memory savingsは小さくなる。

`τ`を下げると短windowを選びやすくなりmemoryは減るが、quality degradationのriskが増える。

つまり`τ`がHeadWiseKVのquality-memory trade-offを調整する主knobになる。

### 6. grouped cache: maskではなく物理memoryを減らす

KV compression研究では、「古いtokenをattentionで参照しない」だけで、実際にはfull KV tensorをGPUに残している場合がある。この方式ではattention computeは減っても、peak memoryはあまり減らない。

HeadWiseKVはそうではない。

serving開始前にpolicy matrixが分かっているため、各KV headへ必要な最大history長のbufferだけ確保する。

たとえば同じlayerに

- head 0: 8K
- head 1: 8K
- head 2: 32K
- head 3: full

があれば、それぞれ異なるphysical capacityを持つgrouped cacheを作る。

contextが伸びたときも8K headは最新8Kだけresidentにし、それより古いKVを保持しない。

これにより「logical sparsity」ではなく**physical residencyそのもの**が減る。

## hybrid modelの他のmemory pathは変更しない

HeadWiseKVはmodel全体のmemory mechanismを書き換えるわけではない。

hybrid modelに含まれる

- local attention
- recurrent state
- linear attention

など、元々bounded-memoryで動くpathはそのままにする。

対象はあくまで**残存global-attention layerのKV history**である。

この限定は重要で、HeadWiseKVの効果は「hybrid modelの全memoryを70%減らす」といった意味ではない。全model memoryの一部であるglobal KVだけを縮めるので、whole-device peak memoryの削減率はKV retention ratioより小さくなる。

## 評価

### 品質評価

複数のhybrid long-context modelで、主に

- **RULER**: 長文脈から必要情報をretrievalできるかを見るbenchmark。
- **LoCoMo**: 長いconversation historyの記憶・参照能力を測るbenchmark。
- 2τ-Bench系agent task

などを用い、Full-KVとのquality差を評価する。

対象にはQwen3.5-9B、Qwen3.6-27B、Qwen3.6-35B-A3B、Gemma4-31Bなどが含まれる。

結果として、moderateなretention budgetではRULER/LoCoMoをFull-KVにかなり近い水準で維持する。

重要なのは、「全headを同じwindowにしたbaseline」と比べて、同じ総KV budgetならheadごとにwindowを変えた方がqualityを保ちやすい点である。

これは限られたmemoryを、長距離historyを本当に必要とするheadへ優先配分できるためである。

### 112K contextでpeak device memoryを8.59%削減

Qwen3.6-27Bのfixed-model system studyでは、112K contextでHeadWiseKVがFull-KVに対して**sampled peak device memoryを8.59%削減**した。

この8.59%は「global KV cacheだけが8.59%減った」という意味ではなく、model weights、temporary buffer、その他runtime memoryを含む**device全体peak**での差である。

したがって、KV部分の削減率より数字が小さく見えるのは自然である。

### 最大context長は114K → 161K

同じsystem studyで、実際に最後まで完走できた最大context長は

- Full-KV: **114K**
- HeadWiseKV: **161K**

へ拡張した。

約1.41倍のcontext extensionである。

これはalgorithmicな「理論最大context」ではなく、そのfixed model / runtime / device条件でOOMせずにverified successful runができた最大値である。

### throughput改善はmemory削減ほど大きくない

HeadWiseKVは主目的がmemory residency削減であり、attention compute自体を劇的に高速化するsystemではない。

報告されるQwen3.6-27Bのsystem条件では、prefill throughputはFull-KV比で約**1.09×**、decode throughputは約**1.02×**程度の改善に留まる例がある。

つまりheadlineは「2倍速くなる」ではなく、**qualityを大きく落とさずpeak memoryを減らし、より長いcontextを収容する**ことにある。

## 既存研究との差

### token selection型との違い

SnapKVやH2Oのような方式は、requestごとのattention scoreを見て「どのtokenを残すか」をdynamicに決める。

HeadWiseKVはtoken内容を見ない。各headについて「最新何token分を残すか」という容量をofflineで固定する。

そのためprompt-adaptiveな遠距離重要tokenを個別に拾う能力は弱い一方、serving前にmemory requirementを確定できる。

### StreamingLLMとの違い

StreamingLLMのような固定window方式は全headへほぼ同じpolicyを適用する。

HeadWiseKVはheadごとに複数段階windowを選ぶため、long-range headだけ大きなhistoryを残せる。

### AdaKV / head-aware compressionとの違い

既存head-aware方式にもheadごとにbudgetを変えるものはある。

HeadWiseKVの特徴は、

1. offlineでcapacityを固定する。
2. lower-layer compressionを反映してhigher-layerを較正する。
3. maskではなくruntime physical allocationへ直接落とす。

という3点を組み合わせることにある。

## 限界と適用境界

- **lossyである。** 古いKVを捨てるので、Full-KVと出力同一性は保証されない。
- **static / prompt-independent。** requestごとに重要な遠距離tokenが変わっても、そのtokenだけを特別に残すことはできない。
- **suffix windowのみ。** 「最近8Kを残す」方式なので、100K前の1 tokenだけ重要というtaskには不利になり得る。
- **SeqCalibはgreedyな逐次近似。** 全head・全layerの組合せをjoint optimizationしたglobal optimumではない。
- **calibration distribution依存。** 較正dataとproduction workloadが大きく違えば、選んだwindowが最適でない可能性がある。
- **global-attention KVが十分大きいhybrid model向け。** もともとglobal KVがほぼ無いarchitectureでは削減余地も小さい。
- **peak memory 8.59%は特定system条件。** 全model / GPUで同率削減されるわけではない。
- **quality値とsystem headlineは必ずしも同一operating pointではない。** retention budgetや実験条件を分けて読む必要がある。

## 実装上の含意

この研究の実務的なポイントは、KV cache圧縮を「どのtokenを捨てるか」だけで考えないことである。

特にhybrid modelでは、global attention layer数自体は少なくても、headごとの役割差が大きければ、**capacity allocationだけでかなり無駄を減らせる**。

また、memory削減を本当にcontext extensionへつなげたいなら、attention maskでlogicalにtokenを隠すだけでは不十分である。allocator側がhead別capacityを理解し、prefill前からphysical memoryを小さく確保する必要がある。

SeqCalibの「lower layerで圧縮した状態を次layer較正へ持ち込む」という考え方も一般化できる。複数layerへ近似を入れるsystemでは、各layerをFull model上で独立評価するとerror interactionを見落とすため、**deploymentと同じ近似を累積した状態で後段をcalibrateする**方が安全である。
