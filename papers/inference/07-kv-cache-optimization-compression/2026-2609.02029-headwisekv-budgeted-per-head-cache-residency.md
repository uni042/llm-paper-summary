# HeadWiseKV: Budgeted Per-Head Cache Residency for Hybrid Long-Context Language Models

> **HeadWiseKVは、長文脈モデルに少数だけ残っている全体 注意機構のKV キャッシュを「全部のヘッドで同じ長さ保存」するのをやめ、ヘッドごとに必要な履歴長を事前較正して、本当に必要な長さだけGPUへ物理確保する。**

## 概要

最近の長文脈 モデルには、すべての層で通常の全域注意機構を行うのではなく、局所注意機構、recurrent 層、線形-注意機構系層などを混ぜる**ハイブリッド アーキテクチャ**が増えている。

こうした層は過去トークン全体のKV キャッシュをそのまま保持しないため、通常のTransformerより文脈長に対するメモリ増加を抑えやすい。そこで一見すると「ハイブリッド モデルならKV キャッシュ問題はほぼ解決した」ように見える。

しかし実際には、長距離情報を拾うために少数の**全域注意（全体 注意機構）層**が残されている。この層は過去トークン全体へ注意機構できるので、そこで使うKV キャッシュは依然文脈長に比例して増える。層数が少なくても、文脈が100K トークンを超えるとこの残存KVだけでGPU メモリの上限を決めることがある。

HeadWiseKVは、この残存全体 KVをさらに見ると、**すべてのKV ヘッドが同じ長さの履歴を必要としているわけではない**ことに着目する。

あるヘッドは遠く離れたトークンを検索するため長い履歴を必要とする。一方、別のヘッドは実際には近傍トークンしか参照せず、8K程度の最近の historyだけ残しても出力がほとんど変わらない場合がある。

そこでHeadWiseKVは、各物理KV ヘッドへ

- 8K トークン
- 16K トークン
- 32K トークン
- full history

のような複数段階の保存窓を割り当てる。

重要なのは、古いトークンを注意機構 maskで「見ないことにする」だけではない。実行時は**選ばれた窓の分しかKV メモリを実際に確保しない**。そのためpeak GPU メモリが本当に減り、OOMするまで使える文脈長を伸ばせる。

## 背景: 「attention head」と「KV head」は同じとは限らない

### query headとKV head

通常のmulti-ヘッド 注意機構では複数の注意機構 ヘッドがあり、それぞれクエリ、キー、値を持つ。

しかし最近のLLMでは、KV キャッシュを小さくするために**グループ化クエリ注意（Grouped-クエリ 注意機構; GQA）**を使うことが多い。GQAでは複数のクエリ ヘッドが同じキー/値 ヘッドを共有する。

たとえば32個のクエリ ヘッドに対して8個しかKV ヘッドがないモデルなら、4個のクエリ ヘッドが1個のKV ヘッドを共有する。

この場合、キャッシュ メモリの単位として重要なのはクエリ ヘッドではなく**物理KV ヘッド**である。4個のクエリ ヘッドが同じKVを読むため、そのうち1個だけ8K、残りを32Kという保存はできない。

HeadWiseKVはこの共有関係を踏まえ、**物理KV ヘッドごと**に履歴長を割り当てる。

## なぜ全headへ同じwindowを割り当てると無駄が出るのか

32K 文脈で、あるKV ヘッドが8Kしか必要としていないとする。

full historyなら32K トークン分のキー/値を保存する。8K windowなら保存量はその1/4になる。

しかし別のヘッドが長距離retrievalを担当していて32K全部必要なら、そのヘッドまで8Kへ縮めると品質が落ちる。

したがって、全ヘッドを一律8Kにする方式はメモリは減るが品質を壊しやすい。全ヘッドを32K/fullにすれば品質は守れるがメモリ削減が小さい。

HeadWiseKVはこの中間として、

- 長距離依存に敏感なヘッド → full / 32K
- 中距離で十分なヘッド → 16K
- 近距離中心のヘッド → 8K

のように**同じ層内でも異なるメモリ 予算を与える**。

## 手法のあらまし

### 1. 保存候補を連続値ではなく有限のwindow codebookへする

理論上はヘッドごとに12,347 トークン、18,222 トークンのような任意長を選べる。しかし候補が無限に近いと較正と実行時実装が複雑になる。

そこでHeadWiseKVは候補集合を

`W = {8K, 16K, 32K, full}`

のような有限の**window codebook**へ制限する。

各全体-注意機構 層の各物理KV ヘッドについて、この中から1つ選ぶ。最終policyは

`layer × KV head → 保存window`

という行列になる。

これはリクエストが来るたび注意機構 スコアを見てトークンを選ぶ動的 追い出しとは違う。policyは事前で一度作り、サービング前に固定する。

### 2. 「率–歪み問題（rate–distortion problem）」とは何か

論文ではこの割当を制限付きの**率–歪み（率–distortion）問題**として表現する。

言葉だけ見ると難しいが、意味はかなり単純である。

- **率**: どれだけKV メモリを使うか。
- **distortion**: Full-KV モデルの出力からどれだけずれるか。

つまり、

> 「使えるKV メモリは全量の70%まで」という予算の中で、Full-KVに最も近い動作をするヘッド別window組合せを探す

という問題である。

全ヘッドの候補を総当たりすると、ヘッド数が増えるほど組合せ数が指数的に増える。たとえば100 decision 単位に4候補ずつあれば `4^100` 通りになり、実際にモデルを走らせて全部比較するのは不可能である。

そこでHeadWiseKVはSeqCalibという逐次較正に落とす。

### 3. SeqCalib: layerを下から順番に決める

SeqCalibは**逐次較正（Sequential 較正）**の略で、Transformerの実行順に層を処理する。

まず最初のconfigurable 全体-注意機構 層を調べ、各ヘッドについて候補windowを試す。

- 8KでもFull-KVと十分近い → 8K
- 8Kではずれるが16Kなら許容範囲 → 16K
- 32Kまで必要 → 32K
- どれもだめ → full

という形で、許容品質を満たす最短windowを選ぶ。

ここだけなら普通のヘッドごと 較正に見える。

HeadWiseKVで重要なのは、**次の層を較正するとき、前の層をすでに短縮した実deployment状態でモデルを動かす**ことにある。

### 4. なぜ下位layerの設定を反映しないといけないのか

層 10のKVを短縮すると、その注意機構 出力が少し変わる可能性がある。その変化は層 11、12、13…へ伝播する。

もし層 20を較正するとき、層 10〜19を全部Full-KVのままにして評価すると、実deployment時とは異なる隠れ 状態を見てwindowを選ぶことになる。

その結果、事前では16Kで十分だったヘッドが、実際には下位層の圧縮誤差と重なって32K必要になるかもしれない。

SeqCalibはこれを避けるため、層を上へ進むたびに**すでに選んだlower-層 policyをfreezeして適用**する。

つまり、

1. 層 10のpolicyを決める。
2. 層 10をそのpolicyで動かした状態で層 20を評価する。
3. 層 20を決める。
4. 層 10 + 20を両方圧縮した状態で次層を評価する。

という順番になる。

これが論文のいう**deployment-conditioned 較正**である。

### 5. 類似度floorを満たす最短windowを選ぶ

各ヘッドの候補windowを試すとき、Full-KVで得られるreference 出力と、候補windowで得られる出力の類似度を測る。

userが設定したthreshold `τ` を満たす候補の中から最短windowを採用する。

`τ`を高くするとFull-KVに近い挙動を求めるため長いwindowが増え、メモリ savingsは小さくなる。

`τ`を下げると短windowを選びやすくなりメモリは減るが、品質 degradationのriskが増える。

つまり`τ`がHeadWiseKVの品質-メモリ トレードオフを調整する主knobになる。

### 6. grouped cache: maskではなく物理memoryを減らす

KV 圧縮研究では、「古いトークンを注意機構で参照しない」だけで、実際にはfull KV テンソルをGPUに残している場合がある。この方式では注意機構 計算するは減っても、peak メモリはあまり減らない。

HeadWiseKVはそうではない。

サービング開始前にpolicy 行列が分かっているため、各KV ヘッドへ必要な最大history長のバッファだけ確保する。

たとえば同じ層に

- ヘッド 0: 8K
- ヘッド 1: 8K
- ヘッド 2: 32K
- ヘッド 3: full

があれば、それぞれ異なる物理 容量を持つgrouped キャッシュを作る。

文脈が伸びたときも8K ヘッドは最新8Kだけ常駐にし、それより古いKVを保持しない。

これにより「logical 疎性」ではなく**物理 residencyそのもの**が減る。

## hybrid modelの他のmemory pathは変更しない

HeadWiseKVはモデル全体のメモリ mechanismを書き換えるわけではない。

ハイブリッド モデルに含まれる

- 局所 注意機構
- recurrent 状態
- 線形 注意機構

など、元々bounded-メモリで動くpathはそのままにする。

対象はあくまで**残存全体-注意機構 層のKV history**である。

この限定は重要で、HeadWiseKVの効果は「ハイブリッド モデルの全メモリを70%減らす」といった意味ではない。全モデル メモリの一部である全体 KVだけを縮めるので、whole-デバイス peak メモリの削減率はKV 保持 比率より小さくなる。

## 評価

### 品質評価

複数のハイブリッド 長文脈 モデルで、主に

- **RULER**: 長文脈から必要情報をretrievalできるかを見るベンチマーク。
- **LoCoMo**: 長いconversation historyの記憶・参照能力を測るベンチマーク。
- 2τ-Bench系agent タスク

などを用い、Full-KVとの品質差を評価する。

対象にはQwen3.5-9B、Qwen3.6-27B、Qwen3.6-35B-A3B、Gemma4-31Bなどが含まれる。

結果として、moderateな保持 予算ではRULER/LoCoMoをFull-KVにかなり近い水準で維持する。

重要なのは、「全ヘッドを同じwindowにした比較対象」と比べて、同じ総KV 予算ならヘッドごとにwindowを変えた方が品質を保ちやすい点である。

これは限られたメモリを、長距離historyを本当に必要とするヘッドへ優先配分できるためである。

### 112K contextでpeak device memoryを8.59%削減

Qwen3.6-27Bのfixed-モデル システム studyでは、112K 文脈でHeadWiseKVがFull-KVに対して**sampled peak デバイス メモリを8.59%削減**した。

この8.59%は「全体 KV キャッシュだけが8.59%減った」という意味ではなく、モデル 重み、temporary バッファ、その他実行時 メモリを含む**デバイス全体peak**での差である。

したがって、KV部分の削減率より数字が小さく見えるのは自然である。

### 最大context長は114K → 161K

同じシステム studyで、実際に最後まで完走できた最大文脈長は

- Full-KV: **114K**
- HeadWiseKV: **161K**

へ拡張した。

約1.41倍の文脈 extensionである。

これはalgorithmicな「理論最大文脈」ではなく、そのfixed モデル / 実行時 / デバイス条件でOOMせずにverified successful 実行するができた最大値である。

### throughput改善はmemory削減ほど大きくない

HeadWiseKVは主目的がメモリ residency削減であり、注意機構 計算する自体を劇的に高速化するシステムではない。

報告されるQwen3.6-27Bのシステム条件では、プリフィル スループットはFull-KV比で約**1.09×**、デコード スループットは約**1.02×**程度の改善に留まる例がある。

つまりheadlineは「2倍速くなる」ではなく、**品質を大きく落とさずpeak メモリを減らし、より長い文脈を収容する**ことにある。

## 既存研究との差

### token selection型との違い

SnapKVやH2Oのような方式は、リクエストごとの注意機構 スコアを見て「どのトークンを残すか」を動的に決める。

HeadWiseKVはトークン内容を見ない。各ヘッドについて「最新何トークン分を残すか」という容量を事前で固定する。

そのためprompt-適応型な遠距離重要トークンを個別に拾う能力は弱い一方、サービング前にメモリ requirementを確定できる。

### StreamingLLMとの違い

StreamingLLMのような固定window方式は全ヘッドへほぼ同じpolicyを適用する。

HeadWiseKVはヘッドごとに複数段階windowを選ぶため、long-range ヘッドだけ大きなhistoryを残せる。

### AdaKV / head-aware compressionとの違い

既存ヘッド-aware方式にもヘッドごとに予算を変えるものはある。

HeadWiseKVの特徴は、

1. 事前で容量を固定する。
2. lower-層 圧縮を反映してhigher-層を較正する。
3. maskではなく実行時 物理 割り当てへ直接落とす。

という3点を組み合わせることにある。

## 限界と適用境界

- **lossyである。** 古いKVを捨てるので、Full-KVと出力同一性は保証されない。
- **静的 / prompt-independent。** リクエストごとに重要な遠距離トークンが変わっても、そのトークンだけを特別に残すことはできない。
- **suffix windowのみ。** 「最近8Kを残す」方式なので、100K前の1 トークンだけ重要というタスクには不利になり得る。
- **SeqCalibはgreedyな逐次近似。** 全ヘッド・全層の組合せをjoint optimizationした全体 optimumではない。
- **較正 分布依存。** 較正データとproduction ワークロードが大きく違えば、選んだwindowが最適でない可能性がある。
- **全体-注意機構 KVが十分大きいハイブリッド モデル向け。** もともと全体 KVがほぼ無いアーキテクチャでは削減余地も小さい。
- **peak メモリ 8.59%は特定システム条件。** 全モデル / GPUで同率削減されるわけではない。
- **品質値とシステム headlineは必ずしも同一operating 点ではない。** 保持 予算や実験条件を分けて読む必要がある。

## 実装上の含意

この研究の実務的なポイントは、KV キャッシュ圧縮を「どのトークンを捨てるか」だけで考えないことである。

特にハイブリッド モデルでは、全体 注意機構 層数自体は少なくても、ヘッドごとの役割差が大きければ、**容量 割り当てだけでかなり無駄を減らせる**。

また、メモリ削減を本当に文脈 extensionへつなげたいなら、注意機構 maskでlogicalにトークンを隠すだけでは不十分である。allocator側がヘッド別容量を理解し、プリフィル前から物理 メモリを小さく確保する必要がある。

SeqCalibの「lower 層で圧縮した状態を次層較正へ持ち込む」という考え方も一般化できる。複数層へ近似を入れるシステムでは、各層をFull モデル上で独立評価するとerror interactionを見落とすため、**deploymentと同じ近似を累積した状態で後段を較正するする**方が安全である。
