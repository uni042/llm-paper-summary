# KARA: Efficient Reasoning LLM Serving via Sliding-Window KV Cache Compression

> KARAは、推論 モデルが長い思考連鎖を生成してKVキャッシュ（KV キャッシュ）が増え続ける問題に対し、**過去キャッシュ全体を何度も圧縮し直さず、新しく増えた区間だけをsliding 区間として一度ずつ圧縮する**方式である。重要トークンは孤立点として残すだけでなく、意味的にまとまった可変長チャンクへ拡張し、提供処理では周期的発動でPagedAttentionへ統合する。

## 概要

推論 モデルは、通常chat モデルより非常に長い出力を生成することがある。

数学問題やcode 推論では数千〜数万トークンの思考連鎖（CoT）を出し続けるため、プロンプトが短くても**デコード中にKV キャッシュが大きく成長する**。

KV キャッシュが増えると、

- 1 リクエストが占有するGPU メモリが増える
- 同時に載せられるリクエスト数が減る
- 注意機構が読むKV量が増えて1 トークンのデコード時間が伸びる

ため、長い-出力 ワークロードでは提供処理 スループットを強く制限する。

既存KV 圧縮をそのまま推論 デコードへ使うと、別の問題が起こる。

多くの方式は、

`KV cacheが閾値を超える → 既存cacheを圧縮 → また増える → 再び圧縮`

という**閾値-発動した 圧縮**を使う。

長い生成では同じ古いトークンが何度も圧縮対象になる。

しかもcontinuous batchingではリクエストごとに閾値到達時刻が違うため、同時実行数が高くなるほど圧縮 eventが頻発する。

論文はSnapKVをvLLM系実行時へ入れた実験で、concurrent 系列数を増やしているのに出力 スループットが逆に下がる現象を観測する。

つまりメモリを減らしてバッチを増やせても、**圧縮処理そのものがGPU時間を食い、スループット改善を打ち消す**。

KARAはこの問題を、

1. **圧縮する範囲**：過去全体ではなく新規区間だけ
2. **何を残すか**：重要トークン + 可変長チャンク
3. **いつ圧縮するか**：リクエスト 閾値ではなく全体 周期的 予定

の3点から変える。

## 問題設定

### 1. 同じ古いKVを繰り返し圧縮すると情報も計算時間も失う

閾値方式でキャッシュ全体を再圧縮すると、以前に圧縮された古い領域がまた候補になる。

例えば、

- 4K トークンで1回目圧縮
- 8K トークンで2回目
- 12K トークンで3回目

とすると、最初の0〜4K トークンは何度もimportance判定・追い出しを受ける。

この繰り返しには2つの問題がある。

**計算面**では、既に処理済みのKVを再走査するので圧縮 オーバーヘッドが生成 lengthとともに増える。

**品質面**では、圧縮を繰り返すたびに同じ古い領域からさらにKVが落ち、ある系列 blockの情報がほぼ消えることがある。

推論では初期の仮定や中間結論を後半で再利用するため、この「古い領域を何度も削る」挙動は不利になりやすい。

### 2. 重要token 1個だけ残してもsemantic unitは残らない

スコア-基づく 圧縮では上位トークンだけを残すことが多い。

しかし意味情報は1 トークンに閉じていない。

例えば、

`Therefore, the discriminant is negative, so no real roots exist.`

という推論 ステップで`negative`だけを残しても、何がnegativeなのか、何を結論したのかが失われる。

固定長チャンク方式なら周辺を残せるが、意味単位の長さと固定チャンク境界は一致しない。

重要phraseがチャンク境界をまたぐと必要文脈が分断される。

KARAは**重要トークンをanchorにしながら、必要な区間だけ可変長チャンクへ伸ばす**。

## 手法

KARAの圧縮 cycleは次のようになる。

1. デコードで新しいトークンが一定数生成される。
2. 直近の未圧縮トークンだけを区間 `W`として切り出す。
3. 区間内トークン同士を双方向に参照させ、各KVが区間全体からどれだけ注意機構を受けるかをimportance スコアにする。
4. スコア上位のトークンを候補として選ぶ。
5. 候補 トークンのうち連続する2 indexをチャンクの始点・終点候補とみなす。
6. チャンク幅が大きすぎないか、両端のimportanceが十分かを確認して可変長チャンクを選ぶ。
7. 選択された トークン単体と選択された チャンク内部の全KVを残す。
8. 区間外の過去キャッシュはこのcycleでは触らない。
9. 次cycleではその後に増えた新しい区間だけを処理する。

このため古いKVは一度圧縮された後、毎回再圧縮されない。

## 手法

### 1. Sliding-window compression: 「最新windowだけ」を圧縮する

KARAのsliding 区間は、通常のsliding-区間 注意機構とは役割が異なる。

モデル本体の注意機構を「最近のW トークンしか見ない」に変えるのではない。

**圧縮 algorithmが今回評価する範囲だけを区間化する**。

圧縮済みの古いKVはキャッシュ内に残るが、次回圧縮では再評価しない。

これにより1回の圧縮 workは生成全長ではなく区間 sizeにほぼ制限される。

長い-CoTが16K、32Kへ伸びても、「毎回32Kを再スコア」する方式よりオーバーヘッドを制御しやすい。

### 2. 双方向attentionでwindow内importanceを測る

通常の因果的 注意機構ではトークン `i` は未来トークン `i+1...` を見られない。

しかし圧縮時には区間全体がすでに生成済みである。

KARAはこの事実を使い、圧縮 stageだけで**双方向注意機構（双方向 注意機構）**を計算する。

各トークンが、

- 前のトークンからどれだけ参照されるか
- 後のトークンからどれだけ参照されるか

をまとめてimportanceへ反映する。

推論の途中で後続トークンが頻繁に参照した中間結論は、因果的な片方向スコアより重要だと判断しやすい。

これは生成モデル自体を双方向 モデルへ変えるわけではない。

最終トークン生成は通常の因果的 デコードであり、双方向 注意機構は**KV 追い出し decision専用**である。

### 3. Candidate KVをscore上位から選ぶ

区間内の累積双方向 注意機構 スコアから、まず離散的な候補 KV indexを選ぶ。

ここまでは一般的なスコア-基づく 追い出しに近い。

しかしKARAはこの候補をそのまま最終保持集合にしない。

候補は「意味区間のanchor候補」としてToken2Chunkへ渡す。

### 4. Token2Chunk: 隣接candidateを可変長chunkの両端とみなす

Token2Chunkの具体動作は、単純に「各重要トークンの前後k トークンを残す」ものではない。

候補 indexを位置順に、

`i1 < i2 < i3 < ...`

と並べる。

そして連続する候補 pair、

- `(i1, i2)`
- `(i2, i3)`
- ...

を**チャンクの始点・終点候補**として扱う。

例えば候補がトークン 101と106なら、その間の102〜105も同じ意味的 unitかもしれない。

KARAは、

- 2端点間の幅が最大チャンク長 `γ` 以下か
- 両端のimportance スコアが十分高いか

を見てチャンクを選ぶ。

選択されたチャンクでは端点だけでなく内部KVも全て保持する。

これによりチャンク長は、2, 4, 7 トークンなど**実際の候補配置に合わせて可変**になる。

固定8-トークン チャンクのような人工的境界を避けられる。

### 5. Chunk budgetを使い切ったら残りは重要token単体で埋める

全候補をチャンク化するとretention budgetを超える可能性がある。

そこでKARAはチャンクへ使う追加budget `α`を持つ。

価値の高いチャンクを優先し、チャンク budgetが埋まった後は、まだ選ばれていない位置からimportance スコア上位のトークンを単体で残す。

最終キャッシュは、

**可変長チャンク + 孤立した重要KV トークン**

の混合になる。

意味的 spanを守りつつ、budgetを無駄なく使うための構成である。

### 6. なぜ全layer/headで同一設定を使うのか

KARAの評価では、層/ヘッドごとに別retention 比率を最適化するのではなく同じ設定を使う。

これは理論的に最適だからではなく、提供処理 実行時との相性を重視した設計である。

PagedAttentionやtensor 並列化では、層/ヘッドごとに物理キャッシュ形状が大きく違うとメモリ管理・collective実行が複雑になる。

KARAは層/ヘッド 適応型 配分を捨てる代わりに、**均一なキャッシュ構造のままトークン / チャンク 選択を改善する**。

論文ではAdaKVやPyramidKVのような適応型 budget方式より高い正確性を示す条件もある。

## KvLLM: Servingでcompressionをいつ発火するか

### 1. Threshold triggerがconcurrencyと衝突する

リクエスト Aが4K、リクエスト Bが4.1K、リクエスト Cが4.2Kと別々に閾値へ到達すると、スケジューラは短い間隔で圧縮 jobを何度も実行する。

リクエスト数が増えるほど発動が増え、GPUがトークン生成より圧縮へ時間を使う。

メモリ削減で同時実行数を増やしたのにスループットが落ちる、という逆転が起こり得る。

### 2. Global decoding-step counterで周期的に圧縮する

KvLLMはvLLM / PagedAttentionへKARAを組み込み、リクエストごとのlength 閾値ではなく**全体 周期的 圧縮**を使う。

実行時は全体のデコード-ステップ counterを持ち、固定periodごとに一部実行中の 系列を選ぶ。

各系列の末尾にあるPagedAttention block群を圧縮 区間としてKARAへ渡す。

### 3. Periodをwindow spanより長くして同じ領域を二度触らない

圧縮 periodは区間 spanより長く設定する。

そのため次回発動時には、前回区間より後に生成された**未圧縮トークン**が十分たまっている。

これにより、

- 圧縮頻度をバッチサイズから切り離す
- 同じ古いKVを再圧縮しない
- PagedAttention block単位でメモリを回収する

ことができる。

KARAのalgorithmとKvLLMの周期的 スケジューリングは別の層の工夫であり、推論 正確性比較では周期的 policyを外し、圧縮方式だけを公平に比較している。

## 評価

### まず見るところ

- **推論品質:** Qwen3-14BのMATH-500では **30% retentionでもfull KVに近い正確性**。
- **Ablation:** Qwen3-4B / 40% retentionでKARAはMATH-500 90.0、AMC23 82.5。双方向 注意機構を外すと85.2 / 72.5、Token2Chunkを外すと88.2 / 77.5。
- **Retrieval:** Needle-in-a-Haystackでも固定チャンク / トークン-のみ方式より良好。
- **提供処理:** KvLLMは閾値-発動した 圧縮の同時実行数–スループット 逆転を避け、メモリ削減を出力 スループットへつなげることを狙う。
- **近似:** KV 追い出し方式なので無損失ではない。

### NIAH

Needle-in-a-Haystackでは文脈長とneedle挿入位置を変え、長文中の情報を圧縮後もretrievalできるかを見る。

### 「30% retention」の読み方

30% retentionは、full KV キャッシュの70%を捨てる近似方式である。

Qwen3-14B MATH-500では正確性がほぼ維持される条件があるが、

- 他タスク
- 他モデル
- より低いretention

で完全に同一である保証はない。

またメモリ 70%削減がそのまま注意機構 遅延 70%削減やスループット 3.3×を意味するわけではない。

圧縮 オーバーヘッドと実行時 スケジューリングを含むKvLLM評価を別に見る必要がある。

## 既存研究との差

### SnapKV等のthreshold方式との違い

多くの既存方式は「キャッシュが大きくなったら圧縮」を繰り返す。

KARAは時間方向へ区間を進め、**新規KVだけを一度処理する**。

違いはトークン スコア式だけではなく、圧縮 workのlifetime管理にある。

### ChunkKVとの違い

固定長チャンク方式はチャンク境界と意味的 boundaryが一致しない場合がある。

Token2Chunkは重要トークンの実際の位置からチャンク端点を作るため、可変長区間を任意位置で保持できる。

### AdaKV / PyramidKVとの違い

これらはヘッド / 層間でbudgetを変えることに重点を置く。

KARAは全層/ヘッドへ比較的統一した設定を使い、PagedAttention / tensor 並列 実行時との構造的な扱いやすさを優先する。

## 限界

- KV 追い出しを行うため厳密な 注意機構ではない。
- 双方向 scoring自体に追加注意機構計算が必要。
- Token2Chunkで周辺KVを残すため、同じ候補数でもトークン-のみ方式よりキャッシュ使用量が増える場合がある。
- 長い-出力 推論を主対象とし、数十〜数百トークンで終わる短chatでは圧縮 オーバーヘッドを回収しにくい。
- 周期的 発動の良いperiod / 区間 sizeはモデル・ハードウェア・同時実行数に依存する。
- 均一な 層/ヘッド configurationは実行時上単純だが、品質最適化だけを見れば適応型 配分の余地が残る。
- vLLM / PagedAttentionへ密接に統合しているため、別実行時ではblock管理・スケジューラ部分の再実装が必要。
- official standalone repositoryは2026-09-10時点で一次資料から明確に確認できない。

## 一般的な実装上の含意

KARAの最も重要なシステム上の示唆は、オンライン 圧縮では**圧縮アルゴリズムの精度だけでなく発動 policyがスループットを決める**ことである。

メモリを半分にできるalgorithmでも、リクエストごとに頻繁な圧縮 カーネルを発火してGPUを止めれば提供処理は遅くなる。

したがって長い-実行中の stateを圧縮する実行時では、

1. 同じ古いstateを何度処理するか
2. 発動頻度が同時実行数に比例して増えないか
3. メモリ回収単位が実行時のページ/block管理と合っているか
4. 意味的 unitを固定boundaryで分断していないか

まで設計対象にする必要がある。

SSD/NVMeへKVや活性値を退避する場合にも、「一定量たまった新規領域だけをincrementalに処理する」という考え方は応用可能である。
