# KARA: Efficient Reasoning LLM Serving via Sliding-Window KV Cache Compression

> KARAは、reasoning modelが長いchain-of-thoughtを生成してKVキャッシュ（KV cache）が増え続ける問題に対し、**過去cache全体を何度も圧縮し直さず、新しく増えた区間だけをsliding windowとして一度ずつ圧縮する**方式である。重要tokenは孤立点として残すだけでなく、意味的にまとまった可変長chunkへ拡張し、servingでは周期的triggerでPagedAttentionへ統合する。

## 概要

reasoning modelは、通常chat modelより非常に長い出力を生成することがある。

数学問題やcode reasoningでは数千〜数万tokenのchain-of-thought（CoT）を出し続けるため、promptが短くても**decode中にKV cacheが大きく成長する**。

KV cacheが増えると、

- 1 requestが占有するGPU memoryが増える
- 同時に載せられるrequest数が減る
- attentionが読むKV量が増えて1 tokenのdecode時間が伸びる

ため、long-output workloadではserving throughputを強く制限する。

既存KV compressionをそのままreasoning decodeへ使うと、別の問題が起こる。

多くの方式は、

`KV cacheが閾値を超える → 既存cacheを圧縮 → また増える → 再び圧縮`

という**threshold-triggered compression**を使う。

長いgenerationでは同じ古いtokenが何度もcompression対象になる。

しかもcontinuous batchingではrequestごとにthreshold到達時刻が違うため、concurrencyが高くなるほどcompression eventが頻発する。

論文はSnapKVをvLLM系runtimeへ入れた実験で、concurrent sequence数を増やしているのにoutput throughputが逆に下がる現象を観測する。

つまりmemoryを減らしてbatchを増やせても、**compression処理そのものがGPU時間を食い、throughput改善を打ち消す**。

KARAはこの問題を、

1. **圧縮する範囲**：過去全体ではなく新規windowだけ
2. **何を残すか**：重要token + 可変長chunk
3. **いつ圧縮するか**：request thresholdではなくglobal periodic schedule

の3点から変える。

## 問題設定

### 1. 同じ古いKVを繰り返し圧縮すると情報も計算時間も失う

threshold方式でcache全体を再圧縮すると、以前に圧縮された古い領域がまた候補になる。

例えば、

- 4K tokenで1回目compression
- 8K tokenで2回目
- 12K tokenで3回目

とすると、最初の0〜4K tokenは何度もimportance判定・evictionを受ける。

この繰り返しには2つの問題がある。

**計算面**では、既に処理済みのKVを再走査するのでcompression overheadがgeneration lengthとともに増える。

**品質面**では、圧縮を繰り返すたびに同じ古い領域からさらにKVが落ち、あるsequence blockの情報がほぼ消えることがある。

reasoningでは初期の仮定や中間結論を後半で再利用するため、この「古い領域を何度も削る」挙動は不利になりやすい。

### 2. 重要token 1個だけ残してもsemantic unitは残らない

score-based compressionでは上位tokenだけを残すことが多い。

しかし意味情報は1 tokenに閉じていない。

例えば、

`Therefore, the discriminant is negative, so no real roots exist.`

というreasoning stepで`negative`だけを残しても、何がnegativeなのか、何を結論したのかが失われる。

固定長chunk方式なら周辺を残せるが、意味単位の長さと固定chunk境界は一致しない。

重要phraseがchunk境界をまたぐと必要contextが分断される。

KARAは**重要tokenをanchorにしながら、必要な区間だけ可変長chunkへ伸ばす**。

## 手法のあらまし

KARAのcompression cycleは次のようになる。

1. decodeで新しいtokenが一定数生成される。
2. 直近の未圧縮tokenだけをwindow `W`として切り出す。
3. window内token同士を双方向に参照させ、各KVがwindow全体からどれだけattentionを受けるかをimportance scoreにする。
4. score上位のtokenをcandidateとして選ぶ。
5. candidate tokenのうち連続する2 indexをchunkの始点・終点候補とみなす。
6. chunk幅が大きすぎないか、両端のimportanceが十分かを確認して可変長chunkを選ぶ。
7. selected token単体とselected chunk内部の全KVを残す。
8. window外の過去cacheはこのcycleでは触らない。
9. 次cycleではその後に増えた新しいwindowだけを処理する。

このため古いKVは一度圧縮された後、毎回再圧縮されない。

## 手法

### 1. Sliding-window compression: 「最新windowだけ」を圧縮する

KARAのsliding windowは、通常のsliding-window attentionとは役割が異なる。

model本体のattentionを「最近のW tokenしか見ない」に変えるのではない。

**compression algorithmが今回評価する範囲だけをwindow化する**。

圧縮済みの古いKVはcache内に残るが、次回compressionでは再評価しない。

これにより1回のcompression workはgeneration全長ではなくwindow sizeにほぼ制限される。

long-CoTが16K、32Kへ伸びても、「毎回32Kを再score」する方式よりoverheadを制御しやすい。

### 2. 双方向attentionでwindow内importanceを測る

通常のcausal attentionではtoken `i` は未来token `i+1...` を見られない。

しかしcompression時にはwindow全体がすでに生成済みである。

KARAはこの事実を使い、compression stageだけで**双方向attention（bidirectional attention）**を計算する。

各tokenが、

- 前のtokenからどれだけ参照されるか
- 後のtokenからどれだけ参照されるか

をまとめてimportanceへ反映する。

reasoningの途中で後続tokenが頻繁に参照した中間結論は、causalな片方向scoreより重要だと判断しやすい。

これは生成model自体をbidirectional modelへ変えるわけではない。

最終token生成は通常のcausal decodingであり、bidirectional attentionは**KV eviction decision専用**である。

### 3. Candidate KVをscore上位から選ぶ

window内の累積bidirectional attention scoreから、まず離散的なcandidate KV indexを選ぶ。

ここまでは一般的なscore-based evictionに近い。

しかしKARAはこのcandidateをそのまま最終保持集合にしない。

candidateは「意味区間のanchor候補」としてToken2Chunkへ渡す。

### 4. Token2Chunk: 隣接candidateを可変長chunkの両端とみなす

Token2Chunkの具体動作は、単純に「各重要tokenの前後k tokenを残す」ものではない。

candidate indexを位置順に、

`i1 < i2 < i3 < ...`

と並べる。

そして連続するcandidate pair、

- `(i1, i2)`
- `(i2, i3)`
- ...

を**chunkの始点・終点候補**として扱う。

例えばcandidateがtoken 101と106なら、その間の102〜105も同じsemantic unitかもしれない。

KARAは、

- 2端点間の幅が最大chunk長 `γ` 以下か
- 両端のimportance scoreが十分高いか

を見てchunkを選ぶ。

選択されたchunkでは端点だけでなく内部KVも全て保持する。

これによりchunk長は、2, 4, 7 tokenなど**実際のcandidate配置に合わせて可変**になる。

固定8-token chunkのような人工的境界を避けられる。

### 5. Chunk budgetを使い切ったら残りは重要token単体で埋める

全candidateをchunk化するとretention budgetを超える可能性がある。

そこでKARAはchunkへ使う追加budget `α`を持つ。

価値の高いchunkを優先し、chunk budgetが埋まった後は、まだ選ばれていない位置からimportance score上位のtokenを単体で残す。

最終cacheは、

**可変長chunk + 孤立した重要KV token**

の混合になる。

semantic spanを守りつつ、budgetを無駄なく使うための構成である。

### 6. なぜ全layer/headで同一設定を使うのか

KARAの評価では、layer/headごとに別retention ratioを最適化するのではなく同じ設定を使う。

これは理論的に最適だからではなく、serving runtimeとの相性を重視した設計である。

PagedAttentionやtensor parallelismでは、layer/headごとに物理cache形状が大きく違うとmemory管理・collective実行が複雑になる。

KARAはlayer/head adaptive allocationを捨てる代わりに、**均一なcache構造のままtoken / chunk selectionを改善する**。

論文ではAdaKVやPyramidKVのようなadaptive budget方式より高いaccuracyを示す条件もある。

## KvLLM: Servingでcompressionをいつ発火するか

### 1. Threshold triggerがconcurrencyと衝突する

request Aが4K、request Bが4.1K、request Cが4.2Kと別々にthresholdへ到達すると、schedulerは短い間隔でcompression jobを何度も実行する。

request数が増えるほどtriggerが増え、GPUがtoken生成よりcompressionへ時間を使う。

memory削減でconcurrencyを増やしたのにthroughputが落ちる、という逆転が起こり得る。

### 2. Global decoding-step counterで周期的に圧縮する

KvLLMはvLLM / PagedAttentionへKARAを組み込み、requestごとのlength thresholdではなく**global periodic compression**を使う。

runtimeは全体のdecoding-step counterを持ち、固定periodごとに一部running sequenceを選ぶ。

各sequenceの末尾にあるPagedAttention block群をcompression windowとしてKARAへ渡す。

### 3. Periodをwindow spanより長くして同じ領域を二度触らない

compression periodはwindow spanより長く設定する。

そのため次回trigger時には、前回windowより後に生成された**未圧縮token**が十分たまっている。

これにより、

- compression頻度をbatch sizeから切り離す
- 同じ古いKVを再圧縮しない
- PagedAttention block単位でmemoryを回収する

ことができる。

KARAのalgorithmとKvLLMのperiodic schedulingは別の層の工夫であり、reasoning accuracy比較ではperiodic policyを外し、compression方式だけを公平に比較している。

## 評価

### まず見るところ

- **Reasoning品質:** Qwen3-14BのMATH-500では **30% retentionでもfull KVに近いaccuracy**。
- **Ablation:** Qwen3-4B / 40% retentionでKARAはMATH-500 90.0、AMC23 82.5。bidirectional attentionを外すと85.2 / 72.5、Token2Chunkを外すと88.2 / 77.5。
- **Retrieval:** Needle-in-a-Haystackでも固定chunk / token-only方式より良好。
- **Serving:** KvLLMはthreshold-triggered compressionのconcurrency–throughput inversionを避け、memory削減をoutput throughputへつなげることを狙う。
- **近似:** KV eviction方式なのでlosslessではない。

## 既存研究との差

### SnapKV等のthreshold方式との違い

多くの既存方式は「cacheが大きくなったら圧縮」を繰り返す。

KARAは時間方向へwindowを進め、**新規KVだけを一度処理する**。

違いはtoken score式だけではなく、compression workのlifetime管理にある。

### ChunkKVとの違い

固定長chunk方式はchunk境界とsemantic boundaryが一致しない場合がある。

Token2Chunkは重要tokenの実際の位置からchunk端点を作るため、可変長区間を任意位置で保持できる。

### AdaKV / PyramidKVとの違い

これらはhead / layer間でbudgetを変えることに重点を置く。

KARAは全layer/headへ比較的統一した設定を使い、PagedAttention / tensor parallel runtimeとの構造的な扱いやすさを優先する。

## 限界

- KV evictionを行うためexact attentionではない。
- bidirectional scoring自体に追加attention計算が必要。
- Token2Chunkで周辺KVを残すため、同じcandidate数でもtoken-only方式よりcache使用量が増える場合がある。
- long-output reasoningを主対象とし、数十〜数百tokenで終わる短chatではcompression overheadを回収しにくい。
- periodic triggerの良いperiod / window sizeはmodel・hardware・concurrencyに依存する。
- uniform layer/head configurationはruntime上単純だが、品質最適化だけを見ればadaptive allocationの余地が残る。
- vLLM / PagedAttentionへ密接に統合しているため、別runtimeではblock管理・scheduler部分の再実装が必要。
- official standalone repositoryは2026-09-10時点で一次資料から明確に確認できない。

## 一般的な実装上の含意

KARAの最も重要なsystem上の示唆は、online compressionでは**圧縮アルゴリズムの精度だけでなくtrigger policyがthroughputを決める**ことである。

memoryを半分にできるalgorithmでも、requestごとに頻繁なcompression kernelを発火してGPUを止めればservingは遅くなる。

したがってlong-running stateを圧縮するruntimeでは、

1. 同じ古いstateを何度処理するか
2. trigger頻度がconcurrencyに比例して増えないか
3. memory回収単位がruntimeのpage/block管理と合っているか
4. semantic unitを固定boundaryで分断していないか

まで設計対象にする必要がある。

SSD/NVMeへKVやactivationを退避する場合にも、「一定量たまった新規領域だけをincrementalに処理する」という考え方は応用可能である。
