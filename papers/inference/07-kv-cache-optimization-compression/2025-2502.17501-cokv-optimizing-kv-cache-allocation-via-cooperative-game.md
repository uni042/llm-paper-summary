# CoKV：協調ゲームに基づくKVキャッシュのヘッド別配分

## 書誌と問題設定

Qiheng Sunらが2025年2月に公開したプレプリント。推論時に必要なキー・バリュー（KV）キャッシュの容量を、注意ヘッド単位でどのように分けるべきかを扱う。長文脈では各層・各ヘッドのKVが入力長に比例して増え、GPUメモリを圧迫する。全ヘッドで同じトークン数だけ残す方法は単純だが、重要な情報を多く持つヘッドと、削っても出力への影響が小さいヘッドを区別できない。

既存のAda-KVはヘッドごとの注意集中度に基づき予算を変え、HeadKVは検索・推論能力を測って配分する。しかし、あるヘッドが単独で優秀でも、他のヘッドが既に同じ情報を提供していれば追加の価値は小さい。逆に単独では目立たないヘッドが、別のヘッドと組み合わさることで重要になる場合がある。CoKVは、ヘッドを独立に採点する発想を改め、他ヘッドとの組合せがタスク性能へ及ぼす影響を「協調ゲーム」として評価する。

## 概要

CoKVは二段階で動く。事前段階では、特定タスクの検証集合で注意ヘッド群を部分的に無効化し、モデルの精度がどう変わるかからSliced Shapley Value（SSV）を推定する。推論段階では、そのSSVをヘッド別KV容量へ変換し、各ヘッド内ではSnapKVの局所窓に基づくトークン選別を行う。最も低寄与のヘッドは古いKVをほぼ保持せず、最近の局所窓だけを残す。

Llama-3-8B-Instructを用いたLongBenchでは、GQAで共有するKVキャッシュ1組当たり平均128対だけ保持しても、FullKVの平均品質の97.29%を保つ。Mistral-7B-Instruct-v0.2をA100 40GBで動かした実測では、28kトークン入力の生成総時間がFullKVの半分未満、32k入力のピークGPUメモリは64%削減された。ただしこれはSSVを事前に計算して使う運用であり、事前計算自体はQasperで約20.93時間を要する。オンライン要求ごとにゲーム理論の評価をやり直す方式ではない。

## 手法

### 1. 注意ヘッドをプレイヤーとする協調ゲーム

協調ゲームでは、プレイヤー集合Nの一部Sを残したときの効用U(S)を考える。CoKVのプレイヤーは注意ヘッド（GQA実装ではKVを共有するヘッド群）であり、効用はタスクの検証集合で測ったモデル精度である。Sに含まれないヘッドは完全にモデルから削除するのではなく、過去のKVを削って局所窓のKVだけを残す。したがってU(S)は、S側に豊富なKVを与え、補集合側には短い履歴だけを残したときの性能を表す。

通常のShapley値は、各ヘッドをさまざまな集合へ追加したときの限界貢献U(S∪{i})−U(S)を全ての組合せで平均する。しかしヘッド数が数百になると、全ての部分集合を評価する計算量は指数的に増える。CoKVは補集合の効用差U(S)−U(N\S)を使う。これは一回の対になった評価を、Sに含まれる複数のヘッドの寄与推定へ再利用できる点で効率が良い。

単に各ヘッドを一個ずつマスクして得た性能差ではなく、他のヘッドの存在・欠落の組合せを通じて測るため、冗長なヘッドや協力関係の強いヘッドを区別しやすくなる。ただし効用の計算には実際のモデル推論が必要で、協調ゲームの近似を使っても前処理費用は無視できない。

### 2. Sliced Shapley Value：全ての集合サイズを見ない近似

CoKVはShapley値の推定を、集合サイズjごとの平均補完寄与に分解する。通常はj=1からnまで全てを調べるが、著者は複数のjでヘッド別の寄与分布が似ていることを観測し、選んだ少数のサイズ集合Hについてだけ平均するSSVを導入した。実験ではH={32,64,96,128}を用いる。

Algorithm 1はランダムにヘッドの順列を作り、Hから選んだ切断位置でSとN\Sへ分ける。両集合に豊富なKVを許す場合をそれぞれ評価し、効用差を求め、該当する集合に含まれたヘッドの寄与推定値と試行回数を更新する。繰り返しの後、サイズごとの推定値を平均して各ヘッドのSSVを得る。論文の定理1では、全nサイズを使うShapley推定に対し、選んだ|H|サイズだけを使うことでサンプル計算量の主要項をnから|H|へ縮小できると分析する。

この処理は検証集合を使う**タスク別のオフライン較正**である。データ分布や用途が変われば重要度も変わり得るため、論文は問い合わせ応答やコード処理などのタスクカテゴリごとにSSVを作る。付録B.4では同じタスクカテゴリ内の別データセットへ移しても優位が保たれると示すが、未知タスクへの無条件な転用は検証されていない。

### 3. SSVからKV予算へ変換する配分式

得られたSSVをそのままKV保持数へ使うのではなく、低寄与のα個のヘッドを特別扱いする。残りn−α個のSSVを最小最大正規化して非負のNSV_iを求め、α個の最小寄与ヘッドの正規化値を0とする。共有できる追加KV予算をB、最近のトークンを必ず残す局所窓をsとすると、ヘッドiの保持数は c_i = s + B×NSV_i/(Σ_j NSV_j) と定める。

この式により、低寄与のヘッドも局所窓sは失わない。重要度が高いヘッドへ追加予算が集中する一方、SSVが小さいヘッドには過去のKVを残さない。αはハイパーパラメータで、実験では{1,5,10,15,20,30,40}から検証集合に基づいて選ぶ。これは完全にパラメータ不要なオンライン方式ではない。正規化後のスコア分母が十分に正となる条件で配分する実装であり、全ヘッドが同じSSVを持つ極端な場合の処理は本文からは明確でない。

GQAを使うLlama-3とMistralでは、4個のクエリヘッドが同じKVを共有する。著者はこの共有KV群を一つのプレイヤーとしてSSVを求める。元のHeadKV-R2のヘッド別評価をそのまま比較すると共有構造に合わないため、比較実験では4ヘッドの検索・推論スコアを平均して一群のスコアへ変換している。これが比較条件を揃えるための重要な実装差である。

### 4. 各ヘッド内でSnapKVによりトークンを選ぶ

CoKVが新しく解くのは「ヘッド間で容量をどう分けるか」であり、ヘッド内のトークン順位は既存SnapKVの考え方を利用する。直近sトークンを局所窓とし、そのクエリから過去のキーへの注意スコアを計算する。スコアを最大値プーリングと平均で集約し、古いトークンの重要度を推定する。予算c_iに応じて上位の古いKVを残し、最後に局所窓のKVを結合する。

実験の局所窓はs=8で、プリフィル後の各層に対して同じ時点でKV退避を行う。これによりCoKVとSnapKV、PyramidKV、Ada-SnapKV、HeadKV-R2の保持総量を揃え、配分方式の差を比較する。生成中は圧縮されたKVで注意を計算し、新規トークンのKVを追加する。キャッシュ削減により長文脈の読み出し量と容量を減らせるが、前処理に必要なSSVの計算や、保持トークン選択のコストをゼロにするわけではない。

### 品質改善の理由を検証したマスク実験

単に「SSVが高いヘッドへ多く割り当てたら性能が良かった」だけでは、その重要度推定が妥当か判断しにくい。そこで論文表2・図3は、重要度順位の高い群と低い群をそれぞれ無効化する検査を行う。高重要度16群をマスクした場合、例えばLlama-3-8BのQasperスコアはCoKV順位で9.46、HeadKV-R2順位で12.97、ランダムで28.48となり、CoKVが「本当に外すと困る群」をより強く抽出できていることを示す。

逆に低重要度16群をマスクした場合、QasperではCoKV順位33.76に対しHeadKV-R2順位14.36、FullKVは31.24である。CoKVの低重要度群は、消しても品質が落ちにくいだけでなく、場合によっては改善する。この二方向のマスク実験が、協調ゲームで重要度を測る機構の直接的な証拠になっている。ただし特定データセットの例を全タスクでの保証へ拡張してはいけない。

### 品質・遅延・メモリの三者の解釈

Llama-3-8Bの128対で97.29%という数値は、FullKVと比較した**LongBenchの平均品質の比率**であり、KV容量が97.29%残る意味ではない。平均128対は各共有KV群の保持数であり、全モデルで128対しか持たない意味でもない。28k入力の50%未満という遅延はプリフィルとデコードを合わせた総時間であり、SSV事前計算時間を含まない。32k入力の64%メモリ削減は、モデル重みを除いた純粋なKVメモリ比ではなく、論文が測定したGPU全体のピークメモリである。

一方、CoKVと他の圧縮方式の間では、同じ総KV予算を使う限り、生成遅延の差は小さいと著者は報告する。つまりCoKVの独自の利得は、圧縮方式同士のカーネル速度を劇的に変えることではなく、同じキャッシュ予算で回答品質を高める配分にある。FullKVとの差は「圧縮すること」自体の利得も含むため、CoKVの協調ゲーム機構だけの速度改善と読むのは不適切である。

### SSVの事前計算費用と安定性

付録B.1ではRTX 3090を8枚用い、4種類の集合サイズをGPUへ分担して二つの独立SSV推定を実行した。各サイズ250サンプルの時点で二推定の平均絶対誤差（MAE）は3.8×10^-3となり、256共有KV群に対する1/256より小さい。著者はこの閾値を安定性判定に使い、独立推定を平均して最終スコアにすることを推奨する。この条件で20.93時間を要したため、SSVは新しいタスクの要求が来るたびにその場で計算するものではない。

事前計算は同じタスク分類に対して再利用できるが、カテゴリが細かく増えたり、モデルを更新したりすれば再計算費用が問題になる。付録B.3は集合サイズ間の寄与分布の相関と128付近の対称性を示すため、少数サイズの選択に根拠はある。しかし、この経験則が全モデル・全タスクで同じ推定精度を保証するわけではない。

## 既存方式との差

SnapKVは最近のクエリ窓から過去トークンへの注意を見て、各ヘッド内でどのトークンを残すか決める。PyramidKVは層ごとに予算を変え、Ada-KVは注意の集中度に応じてヘッド間で容量を調整する。HeadKV-R2は検索・推論能力の単独スコアを用いてヘッド予算を決める。CoKVはこれらのトークン順位付けを置き換えるのではなく、上流で「各ヘッドへ何個分の予算を与えるか」を協調寄与で決める点が新しい。

特にGQAでは、4クエリヘッドで一つのKV群を共有するため、個々のクエリヘッドを別々の容量で保持する設計はそのままでは適用できない。CoKVは共有KV群をプレイヤーにして予算を決め、SnapKVの窓スコアでその群のトークンを選ぶ。既存のFlashAttentionも併用でき、演算カーネルとメモリ配分方策の役割が分かれている。

## 限界と実装上の注意

最大の負担は、タスク別のSSV推定に大量の検証推論が必要なことである。約21時間という付録実測は、生成一回の処理時間に足してはいけない一方、運用の立ち上げ費用として無視もできない。利用者の要求をタスク分類できない場合や、学習時と異なるタスク分布へ変化した場合、既存SSVが最適とは限らない。付録は同一タスクカテゴリ内のデータセット横断を検証するが、未知タスクへの適応は未評価である。

KVの削減は元の全履歴を完全には保持しないため、重要な古いトークンを捨てた場合に品質が下がる可能性が残る。FullKVより良いスコアになるタスクがある一方、例えばPReの1024対条件ではFullKV 71.76に対しCoKV 71.20である。平均品質の改善を個別タスク全勝と表現しない。実測遅延はA100 40GB上のMistral-7Bで、巨大MoE、複数同時要求、GPU間のKV共有やSSDオフロードまで実証したものではない。
