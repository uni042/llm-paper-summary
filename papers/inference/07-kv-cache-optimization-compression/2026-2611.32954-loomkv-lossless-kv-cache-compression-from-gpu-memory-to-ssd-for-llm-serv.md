# LoomKV: Lossless KV Cache Compression from GPU Memory to SSD for LLM Serving

> BF16上位バイトの偏りを使う無損失符号でKVを約0.71倍に圧縮し、外部階層とGPUプールの両方へ適用することで、AgentXのLRUの崖で有効スループット2.7〜3.6倍、プールでは収容トークン1.31〜1.34倍を、出力を変えずに得たKVキャッシュ圧縮。

## 概要

LLMへのリクエストは長いプレフィックスを共有することが多い。エージェントは毎ターン伸びた会話記録を送り直し、チャットや検索拡張生成は履歴と文書を繰り返す。これを毎回計算し直さないため、サービングエンジンはKVキャッシュを保持し、GPUメモリからホストDRAM、SSDへと退避する階層を持つ。ここで容量は2か所で効く。外部階層の容量は、再利用される前にプレフィックスが追い出されるかどうかを決め、追い出されれば再計算で遅延が跳ねる。GPUのKVプールの容量は、同時実行できる長いリクエストの数を決め、外部階層に空きがあってもプールが満杯ならリクエストは待つ。例えばQwen3-30B-A3Bはトークンあたり96KBのKVを持ち、KV用に32GBを確保したGPUでも64Kトークンのエージェント・セッションを5つしか保持できない。

容量を増やす既存のKV圧縮は大抵が有損失である。値を量子化するか、重要でなさそうなトークンを追い出すため、出力が変わり、精度はモデルとタスクごとに再認定が要る。本論文のLoomKVは無損失圧縮を持ち込む。BF16の上位バイトの出現分布が強く偏ることを使い、ヘッドごとに較正した2レベルの3ビット符号で、KV値を1つも変えずに約0.71倍へ圧縮する。代表結果として、エージェント型トレースAgentXで、容量不足の崖の付近では階層モードが生の2.7〜3.6倍の有効スループットを出し、プールモードは同じGPU予算で1.31〜1.34倍のトークンを収めた。

## 問題設定

ここで余っていないのは記憶容量そのものであり、計算ではない。外部階層では、ワーキングセットが容量を少し超えたところに崖がある。LRUで運用すると、再利用の直前にプレフィックスが追い出される状態に入り、ヒット率が崩れて再計算が増え、有効スループットが段差状に落ちる。GPUプール側では、長いリクエストがページを占有し続け、新しいリクエストは外部階層にプレフィックスがあってもプールの空き待ちになる。どちらの容量も物理メモリやドライブを足せば増えるが、GPUメモリは足せず、DRAMのみのノードや固定のNVMe容量では足しにくい。保存するバイト数を減らせば、ハードウェアを変えずに両方の実効容量を同時に増やせる。

無損失であることが効く理由は2つある。第1に、出力が変わらないため、量子化したKVで起きるような精度の再認定が不要で、再現性が要る評価や強化学習のロールアウト、安全面で敏感な配備にもそのまま使える。第2に、既に量子化されたFP8 KVの上にも重ねられる。圧縮の対象は値の意味ではなくバイトの分布だからである。問題は、無損失符号で実際に容量として使えるだけの削減が得られるか、そして圧縮と展開がクリティカルパスに乗らないかであり、本論文はこの2点を符号設計とカーネル設計で解く。

## 手法のあらまし

観測の出発点は、BF16の16ビットのうち上位バイト、つまり符号と指数の上位7ビットの分布である。KとVのテンソルごとに、上位バイトの最頻7値が平均で約94%を占め、上位14値で99.81%に達する。一方で下位バイトの分布はほぼ平坦で、上位7値でも4.21%しか占めない。圧縮できるビットは上位バイトに集中している。LoomKVはこの上位バイトへ、ヘッドごとに較正したコードブックによる2レベルの固定長符号を適用する。保存の形は2モードある。階層モードでは、DRAMとSSDに圧縮レコードを正確な長さのオブジェクトとして置き、取得時はGPUページへ直接展開して、エンジン既存の注意バックエンドがそのまま使う。プールモードでは、GPUプール自体が圧縮レコードを保持し、専用の融合デコード注意カーネルがレコードを読みながら展開と注意計算を同時に行う。どちらのモードでも、保存されるKVのビットは無損失である。

## 手法

### 1. 無損失符号 — 上位バイトの偏りを固定長符号で取る

この機構が観測するのは、較正用の1024トークンを1回フォワードして得られる、層とK／Vとヘッドごとの上位バイト分布である。処理は、上位バイトを頻出値への短い符号と、まれな値へのエスケープに分ける2レベルの3ビット符号であり、階層モードでは3+3、プールモードでは融合展開をループなしにするため3+4の構成を取る。出力は元の約0.71倍のレコードである。効く理由は、エントロピーの低い上位バイトだけを狙うため、汎用のバイト圧縮では得られない削減が、固定長で高速に展開できる形で得られることにある。実際、交錯したBF16バイト列ではLZ4は一致を見つけられず保存率は1.0005と無圧縮同然だったのに対し、本符号は0次エントロピー bound の0.676に対して0.705〜0.709まで迫る。コードブックはモデルに依存し、プロンプトのドメインや文脈内の位置にはほぼ依存しない。1つのエージェント・セッションで較正したコードブックでも、散文、ソースコード、中国語チャット、数学、合成ニードル、ランダムトークンを0.706〜0.709で保存でき、240Kトークンの文脈の全位置で0.709〜0.710と平坦だった。追加費用はコードブック自体が小さく、Qwen3-30B-A3Bで8.4KBにすぎない。失敗条件は、分布の偏りが弱い表現形式では利得が縮むことで、FP8 KVでは保存率が0.85〜0.87まで悪化する。それでも1倍を切るため、量子化済みKVの上にも重ねられる。

### 2. 階層モードのTileStream — 正確な長さのレコードとページへの直接展開

この機構が扱うのはDRAMとSSDの外部階層である。入力はページ化されたGPUプール内のKVであり、圧縮はページ化ブロックから直接行う。保存の要点は、レコードを正確な長さのオブジェクトとして階層に置くことである。容量の利得は「平均して短い」ことからではなく「実際に占有するバイトが短い」ことから生まれるため、固定スロットで割り当てると利得の大半が消える。実際、平均0.710のレコードでも0.90サイズの固定スロットに変えると、DRAM階層の収容利得は1.41倍から1.11倍へ落ち、有効スループットも640GB条件で13.5から8.4リクエスト毎分へ下がった。取得時は、タイル単位の索引を使って並列に展開し、レジスタから散らばったKVページへ直接書き込むため、別途の散布パスが要らず、ページ展開は生のコピーの81%の速度に達する。これはPCIe帯域より1桁速く、転送の後ろに隠れる。もう1つの工夫は同期の回避である。保存時にGPUが計算したレコード長をCPUが読み戻す処理をロードのクリティカルパスから外し、読み込み側では複数のロードバッファを回転させて、展開カーネルがGPUのタイムスライス待ちで止まる問題を避ける。混雑したGPUの横で110Kトークンのプレフィックスを読む場合、バッファ1つでは288〜294ミリ秒掛かった遅延が、4つのバッファ回転で90ミリ秒まで下がり、PCIe転送時間と同程度になった。階層の追い出し方針やプリフェッチは変更せず、LMCacheの既存動作のまま使う点も設計の一部である。

### 3. プールモードのFragPackと融合デコード注意 — 圧縮したまま読む

この機構が扱うのはGPUプール自体である。可変長のレコードを固定サイズの物理ページへ詰めるFragPackが保存形式で、ページは複数のレコードで予算を共有する共有予算ページとして管理される。最悪ケースの2KBをレコードごとに予約する方式では1.33倍にとどまるところ、共有予算では1.38倍のブロックが得られ、固定のバッファ分を差し引いた正味のトークン容量でも54GB毎GPUで1.34倍、28GB毎GPUで1.31倍になる。読み取りは、展開とデコード注意を融合した専用カーネルがその場で行う。展開したKVをメモリへ書き戻す中間段階がないため、読むバイト数が約3割少ないことと合わせて、FlashAttention-3より速くなる。実測ではテンソル並列1でFlashInferの0.80〜0.92倍、FlashAttention-3の0.56〜0.85倍の時間であり、同じカーネルを生のFragPackレコードで走らせても0.90〜0.96倍だったことから、高速化はカーネル設計とバイト削減の両方から来ている。トレードオフは、この経路だけがエンジン標準の注意バックエンドから外れるため、数値の同等性を一度検証する必要があることである。保存自体は無損失で、融合カーネルの出力は圧縮レコードと生レコードでビット同一だが、浮動小数点の加算順序がFlashAttention-3と違うため、最終ロジットは丸め精度の範囲でだけ異なる。

### 4. データと制御の流れ

リクエストのプレフィックスが再利用されるとき、階層モードではDRAMまたはSSDから圧縮レコードが読まれ、GPUページへ直接展開されて、エンジンの通常の注意がそれを使う。プールモードではプレフィックスは圧縮されたままGPUプールに住み、デコードのたびに融合カーネルが読みながら展開する。保存時はどちらのモードでも、ページ化ブロックから直接圧縮され、レコード長は正確に記録される。モードの選択は、どちらの容量が先に尽きるかで決めるのが著者らの指針であり、外部階層が先なら階層モード、GPUプールが先ならプールモード、両方が不足するならプールモード（FragPackレコードがそのまま外部階層へも出ていくため両方を広げる）、どちらも足りるなら圧縮を切る、という4つの運用区分が示されている。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 無損失符号 | ヘッドごとの上位バイト分布 | 頻出値への2レベル固定長符号とエスケープで保存 | KVの保存バイト数 | FP8など偏りの弱い形式では利得が縮む |
| TileStream（階層モード） | ページ化されたKVと階層の空き | 正確な長さのレコードで保存し、ページへ直接展開 | 外部階層の実効容量 | GPUメモリを約2.5GB余分に使う |
| FragPack（プールモード） | GPUプールのページ予算 | 可変長レコードを共有予算ページへ詰める | GPUプールの収容トークン数 | 専用カーネルの数値検証が要る |
| 融合デコード注意 | 圧縮レコード | 展開と注意計算を1カーネルで行う | デコードの読み取りバイトと速度 | 標準バックエンドから外れる |

## 評価

### まず見るところ

- **結論:** 圧縮率0.71の逆数である1.4倍が、そのまま外部階層とGPUプールの実効容量の倍率として現れる。利得は容量の崖の付近で最大になり、容量が足りる条件では利得は消えて小さな代価だけが残る。
- **速度・効率:** 展開は生コピーの81%の速度でPCIe転送の後ろに隠れ、プールモードの融合カーネルはFlashAttention-3より速い。容量が足りる条件での代価は最大2.2%のスループット低下である。
- **品質:** 階層モードの出力は生の階層とビット同一であり、プールモードも保存は無損失で、数値誤差はFlashAttention-3と同程度である。有損失なFP8 KVとの対比も測られている。
- **メモリ・入出力:** 保存バイトが29%減るため、PCIeとSSDへの書き込みバイトも同率で減る。代価として階層モードはカードあたり約2.5GBのGPUメモリを余分に使う。
- **評価の強さ／注意点:** 実機、実トレース、3回繰り返しの中央値で、容量等価の対照実験まで行う強い評価である。一方で構成は単一サーバ、モデルは実質2モデル中心であり、崖から遠い条件では利得が小さいことも結果に含まれている。

評価の読みどころは、倍率が「圧縮率の逆数」という単純な機構で説明できることである。階層モードの結果を物理バイトではなく生換算バイト（物理バイトを保存率で割った値）で描き直すと、生と圧縮の曲線が両モデルで1本に重なる。880GBの物理容量で動かした階層モードが、1,231GBの生の対照とほぼ同じ有効スループットを出した直接確認もあり、「圧縮階層は1.4倍大きい生の階層として振る舞う」という主張は比喩ではなく測定である。したがって利得の大きさは条件で決まる。ワーキングセットが容量に収まる条件では生も圧縮も同じであり、両方とも収まらない条件でも差は小さい。差が最大になるのは、生が崖を落ちて圧縮がまだ落ちていない帯域であり、SSD 640GBでは有効スループット13.5対4.6リクエスト毎分、480GBでは9.3対3.5と、2.7〜3.6倍の差がここに出る。逆に2TBでは15.1対15.1で差はない。この「崖の位置を1.4倍ずらす」という読み方をすれば、見出しの倍率を自分の環境へ翻訳できる。自分のワーキングセットと容量の比が崖の帯域に入るかどうかが導入判断になる。

平均TTFTの改善1.9〜3.1倍も同じ機構で説明できる。崖の内側では生のヒット率が0.90前後から時間とともに0.17まで崩れ、プロンプトトークンの45%を再計算するためp90 TTFTが2.8秒から19秒へ跳ねる。圧縮側はヒット率を0.90前後に保ちp90は3.4秒にとどまる。速くなったのではなく、再計算が消えたのである。もう1つの副次効果は上位階層への昇格である。DRAMの実効容量が1.4倍になることでSSDヒットの一部がDRAMヒットへ移り、DRAMの担当割合が0.36〜0.41から0.52〜0.59へ上がり、2TB条件でも中央値TTFTが0.99秒から0.89秒へ下がった。繰り返しプロンプトの制御実験では、SSDからDRAMへの昇格で2回目のTTFTが220GB DRAMで1.6〜1.7倍速くなり、400GBの生と一致した。

プールモードの結果は、ボトルネックの移動を示す。同時実行の上限を8から12へ上げると、生プールはページ不足で平均TTFTが3倍化し有効スループットが落ちるが、プールモードは待ちを平坦に保ち、生が上限8で出した最良と同等の有効スループットを12で出す。上限16では両方とも待つが、プールモードは同時14.0リクエストを回して生の2.5倍の有効スループットを出す。28GB毎GPUまで予算を絞ると上限8でも待ちが発生し、プールモードは待ちを半分にし、階層モードの生プール比で1.8倍の有効スループットを出し、トークン数を揃えた大きな生プールと一致した。ここでも容量等価が成り立っている。第2のワークロードであるAI IDEトレースでは両方の容量が同時に不足し、階層モードが有効スループットを1.24倍、プールモードが1.59倍に上げ、プールモードはDRAMが3分の1、SSDが4分の1しかない構成で大きな生の参照構成を上回った。ボトルネックが2か所にある条件では、両方を同時に広げるプールモードの利得が最大になる。

代価と正確性の測定も揃っている。容量が足りる条件でのスループット低下はDRAMのみで1.3%、SSD 2TBで2.2%が最大で、ヒット率ゼロの保存だけの条件ではエンドツーエンド時間の増加は階層モード0.3%、プールモード0.9%である。階層モードの約2.5GBの追加GPUメモリは、32チャンク分の保存バッファと回転ロードバッファが主因と内訳まで示されている。正確性では、階層モードのグリーディ出力が生とSHA-1ハッシュで一致し、プールモードはFP64参照に対する平均絶対誤差がBF16でFlashAttention-3と同値（3.1×10のマイナス5乗同士）、FP8ではむしろ小さい。GSM8KとRULERの精度も標準誤差の範囲で一致し、有損失なFP8 KVが落とすニードルを落とさない対比がある。未評価の軸としては、複数ノード構成、vLLM以外のエンジン、プリフィル側の注意への適用、コードブック較正が効かない分布外のモデル形式が挙げられる。論文はこれらを主張に含めていない。

## 既存研究との差

KVの容量を広げる先行研究は、値を量子化する方式と、重要度の低いトークンを追い出す方式が中心で、どちらも出力を変えた。汎用やKV向けの無損失圧縮もあったが、保存率か展開速度のどちらかが実用に届かず、階層の容量として使う設計にはなっていなかった。本論文の差は、上位バイトの偏りに特化した高速な無損失符号を作り、それを外部階層とGPUプールの両方へ、正確な長さの割当てとページへの直接展開、圧縮したまま読む融合カーネルという、容量として使うための仕組み一式とともに実装したことにある。圧縮率の逆数が実効容量になることを容量等価の対照実験で示した点も、圧縮率だけを競う研究とは異なる。

## 限界・実装状況

- ハードウェア依存条件: 評価はH800 2枚の単一サーバに限られ、複数ノードや異なるGPU世代、PCIe以外の相互接続での挙動は未評価である。
- モデル／ワークロード依存条件: 保存率は9モデルで確認されているが、エンドツーエンド評価はQwen3-30B-A3BとGLM-4-9Bが中心である。上位バイトの偏りが弱い表現形式では利得が縮み、FP8 KVでは0.85〜0.87にとどまる。
- 実装状況: vLLMとLMCacheの上に構築されエンジン本体は無改造だが、プールモードは独自の融合カーネルを必要とする。公式コードのURLは本文に示されていない。
- 運用上の限界: 容量が既に足りる環境では利得がなく最大2.2%の代価だけが残るため、著者ら自身が容量不足の兆候を見て有効化する運用を推奨している。

## 一般的な実装上の含意

キャッシュ階層の容量不足に当たったとき、圧縮の評価軸は圧縮率そのものではなく「生換算容量で描いたときに曲線が重なるか」で見るべきであり、割当て方式が固定スロットでは圧縮の利得が容量に変換されない。もう1つは、無損失圧縮は有損失量子化と競合ではなく重ねられる層だという点で、FP8 KVの上にさらに0.85倍を掛けられる。容量の崖は外部階層とGPUプールの両方にあり、どちらが先に尽きるかをヒット率とエンジン内待ち行列で観測してから手を入れる順序も、他のサービング基盤に転用できる。
