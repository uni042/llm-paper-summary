# MetaKV: Adaptive KV Cache Compression for Constrained LLM Inference

> 同じKVキャッシュ圧縮方式を全リクエストへ固定適用せず、入力プロンプトと利用者が指定した遅延・ピークKVメモリ上限から、各候補方式の遅延、メモリ、正答確率を軽量予測器で見積もり、制約を満たしつつ正答率を保ちやすい圧縮設定をリクエストごとに選ぶ適応型推論制御方式。

## 問題設定
長文推論では過去トークンのキー・バリュー（KV）を保持するKVキャッシュが大きくなり、GPUメモリの主要消費源になる。損失あり圧縮には、KV値を低ビット化する量子化、重要度の低いトークンを削除する追い出し、参照対象を絞る疎注意などがあるが、それぞれメモリ、遅延、正答率の交換関係が異なる。MetaKVの測定では、KVQuantはメモリを強く削減できる一方で量子化・逆量子化により遅く、H2Oは高速だが同程度の強いメモリ削減では精度が落ち、RocketKVは一部タスクでは高速でも平均精度が低かった。さらに同じ方式でもプロンプト長やタスクによって実行時間と正答しやすさが変わるため、全リクエストへ単一設定を固定する運用では、ある要求では過剰圧縮、別の要求では制約超過が起きる。
## 新規性
MetaKVは新しいKV圧縮カーネルを提案するのではなく、既存の異質な圧縮方式を候補集合としてまとめ、利用者が指定する最大遅延と最大ピークKVメモリを満たす設定をプロンプト単位で選ぶメタ制御層である。候補ごとの実行をオンラインで試すのではなく、事前プロファイルから学習した軽量な勾配ブースティング決定木（Light Gradient-Boosting Machine; LightGBM）で遅延、メモリ、正答確率を予測する。これにより、実際に10候補を順番に実行するコストを払わず、約11ミリ秒の選択処理で設定を切り替える。
## 手法
### 手法のあらまし
入力はプロンプト、最大エンドツーエンド遅延 Lmax、最大ピークKVメモリ Mmax である。MetaKVはまず、非圧縮FP16、KVQuant 2/3/4ビット、H2O 20/40/60%、RocketKV 8/16/32倍という10候補について、遅延予測器とメモリ予測器を評価する。予測値が両制約を満たさない候補を予算フィルタで除外する。非圧縮FP16が残れば、情報を捨てず全体平均で最も高精度なので即座に選ぶ。FP16が残らない場合は、各圧縮方式について制約内で最も弱い圧縮、すなわち情報損失を小さくしやすい設定だけを残す。候補が複数なら正答確率予測器が最も正答しやすい候補を選び、Hugging Face Transformersでその設定を実行する。

どの候補も制約を満たせない場合でも処理を止めず、予測遅延/Lmax + 予測メモリ/Mmax という相対違反スコアを計算し、合計超過が最小の設定を選ぶ。したがって「制約を絶対保証する」制御ではなく、既存候補集合の中で制約達成と正答率を最適化する選択器である。候補集合そのものに実現可能な設定がなければ違反は残る。

### 候補圧縮方式の異質な交換関係を利用する
KVQuantはKV要素を低ビットで保持し、全トークンを残しながらメモリを削減する。その代わり、読み書きのたびに量子化と逆量子化が必要になるため、メモリ制約には強いが遅延が増えやすい。H2Oは累積注意重みに基づいて重要度の低いトークンをKVから削除し、保存量だけでなく後続の注意計算も軽くできる一方、削除率が高いと必要な文脈を失う。RocketKVはプリフィル後のトークン選別と疎な注意計算を組み合わせ、計算量を大きく減らせるが、タスクによって精度のばらつきが大きい。

MetaKVは、この三者を一つの圧縮原理へ統一せず、異なる交換関係を持つ候補として並べる。メモリ上限が支配的な要求では低ビットKVQuantを残しやすく、遅延上限が厳しい要求ではH2OやRocketKVが有利になり、両方に余裕があれば非圧縮FP16へ戻せる。したがって効果の源泉は単一方式の平均性能ではなく、プロンプト長、タスク、制約の組合せによって『どの方式が最も損失が小さいか』が変わることを利用する点にある。候補方式の特性が似通っている環境では、この切替余地が減ってMetaKVの利点も小さくなる。

### 遅延・メモリ予測と予算フィルタ
事前段階では、各圧縮候補を多数のプロンプトで実行し、プロンプトの特徴と設定から、エンドツーエンド遅延とピークKVメモリを予測する軽量な勾配ブースティング決定木（Light Gradient-Boosting Machine; LightGBM）を学習する。実行時には実際に10候補を順番に試すのではなく、全候補の予測値だけを計算する。利用者が与えた最大遅延Lmaxと最大メモリMmaxのどちらかを超える候補を除き、残った集合だけを後段へ渡すため、重い試行探索を推論のたびに行わずに済む。

評価ではメモリ予測の平均絶対百分率誤差が7.7%、決定係数が0.9981で、遅延予測は平均絶対百分率誤差38.19%、決定係数0.9651だった。特に遅延は絶対誤差が小さくないため、制約境界に近い候補を誤って残したり除いたりする可能性がある。つまり予測器は制約の厳密な証明器ではなく、候補を高速に絞る近似器である。別GPUや別モデルへ移ると処理時間とKV量の関係も変わるため、プロファイルを取り直さずに使い回すと、この誤差が制約違反へ直結する。

### 精度を優先する段階的な最終選択
予算フィルタ後に非圧縮FP16が残っていれば、MetaKVは情報を捨てないFP16を優先する。FP16が残らない場合は、KVQuant、H2O、RocketKVの各方式について、制約を満たす範囲で最も弱い圧縮設定だけを残す。たとえばKVQuantなら、より高いビット数でも制約を満たすなら必要以上に低ビットへ落とさない。この段階により、同じ方式内で余分な情報損失を避けてから、方式間の比較へ進む。

複数方式が残った場合は、別のLightGBMが各候補で最終回答が正答する確率を推定し、最大の候補を選ぶ。正答予測の受信者動作特性曲線下面積（Area Under the Receiver Operating Characteristic Curve; AUROC）は0.70で完全な識別器ではないが、方式によって得意なプロンプトが異なる傾向を選択へ取り込める。予測が外れれば本来より精度の低い方式を選ぶ可能性は残るため、前段で弱い圧縮へ絞る規則が安全側の補助になる。

### 実現不可能な制約への違反最小化
全候補が最大遅延または最大メモリの少なくとも一方を超える場合、MetaKVは要求を失敗扱いにして停止するのではなく、各候補について『予測遅延÷Lmax』と『予測メモリ÷Mmax』を足した相対違反スコアを計算し、その値が最小の候補を選ぶ。両制約を同じ相対尺度へ正規化することで、秒とメガバイトの単位をそのまま足さず、どちらの上限からどの程度外れるかを比較できる。

この処理は不可能なサービス品質目標（Service-Level Objective; SLO）を達成したことにはしない。実測値を完全に知るオラクルでも一部条件では最大35%のプロンプトが制約を破っており、候補集合そのものに実現可能な設定がない場合がある。MetaKVの違反率はオラクルより0〜6ポイント高かったため、追加違反の一部は予測誤差だが、残りは候補方式の能力限界である。より厳しい制約へ対応するには、選択器だけでなく候補圧縮方式自体を増やす必要がある。

### 全体のデータ／制御の流れ
全体の制御は、オフライン準備とオンライン選択に分かれる。オフラインでは、対象モデル・GPU・圧縮候補の組合せごとに多数のプロンプトを実行し、遅延、ピークKVメモリ、正誤を記録する。この記録から遅延予測器、メモリ予測器、正答確率予測器を学習し、推論サーバへ持ち込む。オンラインでは、利用者のプロンプトとLmax・Mmaxを受け取り、まず全候補の遅延・メモリを予測する。予算外の候補を捨て、FP16が可能ならFP16を選び、そうでなければ方式ごとの最弱圧縮設定を残して正答確率を比較する。選ばれた設定だけをHugging Face Transformersへ渡し、実際の生成を一度だけ行う。

このため、オンライン経路で移動する制御情報は『プロンプト特徴、利用者制約、候補識別子、予測値、最終設定』であり、KV本体を候補間で複製して試行する必要はない。平均選択時間は10.96ミリ秒で、論文の平均推論遅延に対して0.34%だった。一方、モデル更新、GPU変更、新しい圧縮方式の追加で性能分布が変わると、古い予測器は制約判定を誤る。したがって実運用では、構成変更を検出して再プロファイルすることが前提となり、予測器の較正が古くなった状態は主要な失敗条件である。
## 評価条件
- **ハードウェア**: NVIDIA RTX PRO 6000 Blackwell Server Edition 96GB ×1
- **ソフトウェア**: Hugging Face Transformers、LightGBM、KVQuant、H2O、RocketKV
- **モデル**: Meta Llama 3.1 8B
- **データセット／トレース**: GSM8K、HellaSwag、ARC-Challenge、SQuAD 1.1
- **比較対象**: 最良の静的設定（StaticBaseline）、全候補の実測結果を知るオラクル（Oracle）、非圧縮FP16、KVQuant 2/3/4-bit、H2O 20/40/60%、RocketKV 8/16/32×
- **正確性・品質**: モデルの数値計算を近似する新手法ではなく既存圧縮設定を選ぶため、品質は選択された圧縮方式に依存する。正答率を評価に明示的に含める。
- **データ収集**: 4データセット各2,048プロンプト、合計8,192プロンプト×10候補をプロファイル。85%を学習、15%をテストとし、保持テストは合計1,232プロンプト。5分割交差検証も実施。
- **制約評価**: 最大遅延と最大ピークKVメモリの複数組合せを評価。主指標は、正答かつ両制約を満たすプロンプト比率である制約付き成功率（Constrained Success Rate; CSR）。
- **予測器**: ピークメモリ予測 MAPE 7.7%、R² 0.9981。遅延予測 MAPE 38.19%、R² 0.9651。正答予測 AUROC 0.70。選択オーバーヘッド平均10.96ms/プロンプト。
保持テスト1,232プロンプトで静的設定、MetaKV、実測オラクルを比較し、CSR、制約違反率、正答率を報告する。生成タスクは完全一致、選択式は負の対数尤度が最小の選択肢で判定する。
1モデル、1GPU機種、4データセット、3種類のKV圧縮方式に限定。別モデル・別GPUへ一般化するには再プロファイルと予測器再学習が必要。
## 主要結果
全制約組合せでMetaKVは最良の静的設定より制約付き成功率（Constrained Success Rate; CSR）を改善し、平均で約0.07ポイント、最大0.135ポイント高かった。改善理由は、制約が緩いプロンプトでは非圧縮FP16や弱い圧縮を選んで情報損失を避け、長いプロンプトや厳しいメモリ上限では強い量子化・追い出しへ切り替え、厳しい遅延上限では低オーバーヘッドの候補へ寄せるためである。したがって結果は一つの圧縮方式が常に最良という意味ではなく、要求ごとに異なる制約とプロンプト特性へ候補を割り当てることの効果を示す。

- 制約付き成功率（CSR） / 平均約+0.07、最大+0.135 (比較対象: 最良の静的設定; 条件: 評価した遅延×ピークメモリ制約全体) — プロンプトと支配制約ごとに圧縮方式を変える利得。

- 30MBメモリ閾値でのCSR改善 / +0.10〜+0.13 (比較対象: StaticBaseline; 条件: 複数の遅延上限) — 中程度のメモリ制約では候補間の実現可能性が分かれ、適応選択の余地が大きい。

- 厳しい遅延 2s / 80MB / CSR 0.314→0.366、違反45.9%→35.8% (比較対象: StaticBaseline; 条件: Lmax=2s, Mmax=80MB) — 低遅延方式へ切り替えて違反を約10.1ポイント削減し、正答率低下は2.2ポイントに抑える。

- 厳しいメモリ 5MB / 50s / 正答率+5.3ポイント、違反+3.1ポイント (比較対象: StaticBaseline; 条件: Lmax=50s, Mmax=5MB) — 精度を保つ候補選択は改善するが、非常に厳しいメモリ上限では候補集合自体に実現不能なプロンプトが多い。

- 中程度制約 10s / 30MB / 正答率+10.6ポイント、違反+0.9ポイント (比較対象: StaticBaseline; 条件: Lmax=10s, Mmax=30MB) — わずかな制約違反増と引き換えに大きな精度改善。

- オラクルとの差 / 違反率+0〜6ポイント、正答率-0.2〜-1.8ポイント (比較対象: 実測Oracle; 条件: 代表制約) — 利用可能候補の上限に比較的近い選択を実現。

### 負の結果・境界条件
- **遅延予測誤差**: 遅延予測のMAPEは38.19%で、境界付近では予測誤差による制約違反が残る。
- **候補集合の実現不能**: オラクルでも最大35%違反する条件があり、選択器だけでは候補方式が満たせない制約を解消できない。
- **再較正コスト**: 別モデル・別ハードウェアではプロファイルと予測器再学習が必要。

### 結果の読み方
選択分布も制約に応じて大きく変わる。緩い50s/80MBではFP16が74.9%、厳しい2s/80MBではFP16 63.6%、H2O 60%が22.8%、RocketKVが9.8%。5MB制約ではFP16 18.5%まで下がり、H2O 20% 29.2%、KVQuant 2-bit 28.6%、4-bit 15.3%へ分散する。単一方式の優位ではなく、異なる方式の交換関係を利用すること自体が結果の中心である。
## 品質への影響
圧縮により品質低下は起こり得る。MetaKVは正答確率を選択目的へ含め、制約の余裕がある場合はFP16または弱い圧縮を優先して不要な劣化を避ける。
## 既存研究との差
- KVQuant、H2O、RocketKVのような個別圧縮アルゴリズムを置き換えるのではなく、その上位で方式・強度をプロンプト単位に選ぶ。
- 固定の圧縮率や単一方式を全要求へ適用する運用に対し、利用者の遅延・メモリ制約とプロンプト特徴を同時に使う。
- オンライン探索で候補を実測せず、事前プロファイル済みLightGBMにより低オーバーヘッドで選択する。
## 限界
- 評価はLlama 3.1 8B、RTX PRO 6000 Blackwell 96GB、4データセット、3圧縮方式に限定。
- 別モデル・別GPUでは遅延・メモリ予測器の再プロファイルと再学習が必要。
- 予測値なので厳密な制約保証ではなく、未見プロンプトで違反が起こり得る。
- 候補集合に実現可能設定がなければ違反を避けられない。
- TTFT、スループット、費用、エネルギーなどは今回の制約目的に含めていない。

## 研究上の位置づけ
KVキャッシュ圧縮研究の『どの圧縮手法を設計するか』ではなく、『異質な圧縮手法群をデプロイ時の制約に応じてどう選ぶか』を扱うメタ最適化層。既存の圧縮方式を候補として再利用できるため、新方式が増えるほど候補多様性を活かせる一方、候補ごとの事前プロファイルが必要になる。
