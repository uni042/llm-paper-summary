# PIE：編集後のコード文脈をKVキャッシュの位置補正だけで再利用する

## 概要

本研究は、開発者が既存コードの途中に行を挿入・削除した直後に、コード補完用の大規模言語モデル（LLM）が次の行を予測し直す場面を対象とする。通常の自己回帰生成では入力文脈が固定され、各トークンの鍵・値キャッシュ（KV cache）を次の生成ステップで再利用できる。しかし、過去のコードを途中で編集すると、編集箇所より後ろの位置が変化し、保存済みキャッシュを単純に連結しただけでは位置符号の整合が崩れる。正確性を優先して編集箇所以降をすべて再計算すると、数千トークンのコード文脈を毎回符号化するため、対話的な編集の応答性を損なう。

提案する位置整合符号化（Positional Integrity Encoding、PIE）は、回転位置埋め込み（Rotary Positional Embedding、RoPE）を用いたモデルにおいて、編集より後ろのKeyを編集長差分だけ回転させる。編集前の前方接頭辞はそのまま残し、置換したトークンだけ新たに符号化し、既存の後方Keyに同一の回転行列を適用して連結する。Valueは位置回転を受けないため後方部分をそのまま再利用する。これは**完全再計算と数学的に同一の隠れ状態を復元する方式ではなく、RoPEの位置不整合を修正する近似的な再利用方式**である。論文は、コードの比較的小さな編集なら内容変更に伴う後方表現の意味的変化が限定的であることを実験で確認する。

RepoBench-C-8kのPython/Javaコード補完で、DeepSeek-Coder 1.3B・6.7B・33Bを評価した。挿入・削除・複数箇所編集のいずれでも、完全再計算に近い次行予測品質を保ち、**編集に伴うKV更新時間**を大きく削減した。これは要求全体のエンドツーエンド遅延や、一般の長文対話での品質保証を示す数値ではない。

## 問題設定と従来方式との差

入力を $s=(w_1,\ldots,w_n)$ とし、位置 $i$ から $j$ の旧トークンを新しい $m$ トークンへ置き換える。編集前のKey/Valueを $K_{1:n},V_{1:n}$ とすると、位置 $1:i$ は内容も位置も不変であり、そのまま再利用できる。新しい部分は $i+1:i+m$ としてモデルへ投入し、対応するKVを計算する。問題は旧位置 $j+1:n$ にある後方トークンである。旧トークンの新しい位置は $i+m+j'-j$ となるが、旧Keyには元の位置 $j'$ に対応するRoPE回転がすでに組み込まれている。

**完全再計算（full recomputation）**は編集箇所とその後方を新しい順序で符号化し直すため、編集による意味的な影響まで反映できる。その代わり後方文脈長に応じたモデル前向き計算が必要となる。**衝突を残す高速符号化（Conflict Fast Encoding）**は編集部分だけ新たに計算して、旧後方キャッシュをそのまま連結する。速いが、例えば2番目と3番目の間に3トークンを挿入すると、新規トークンの位置3～5と旧後方トークンの位置3～5が重複する。複数のKeyが同じ位置符号を持ち、注意の相対距離が誤るため、次行予測が大幅に悪化する。

本論文が切り分ける誤差は二つある。第一は位置が衝突・欠落する**構造的な不整合**で、RoPEの回転を変更すれば直接修正できる。第二は、前方コードが変わったことによる後方トークンの**意味的な表現変化**で、位置回転だけでは修正できない。PIEは第一を除去し、第二は軽微なコード編集という評価対象で小さいことに依拠する。前方編集が後方の意味を根本的に変える場合に完全再計算と同一になるとは主張していない。

## 手法

### 1. 旧キャッシュの三分割と編集部分の再符号化

モデルの各層に保存されたKVを、未変更の前方接頭辞、編集で置換される区間、編集後に残る後方区間へ分ける。前方 $K_{1:i},V_{1:i}$ は維持し、旧編集区間のKVは破棄する。新規トークン列 $a_{1:m}$ だけを、前方接頭辞に続く新しい位置 $i+1,\ldots,i+m$ としてモデルへ投入してKeyとValueを得る。新しいキャッシュの候補は $K_{1:i}$、新規 $K^{edit}_{i+1:i+m}$、旧 $K_{j+1:n}$ の順の連結である。Valueについても同様に連結するが、後方のValueには後述する位置補正を行わない。

この時点では旧後方KeyのRoPE位置が不正確であり、そのまま注意へ渡すと先述の衝突が生じる。PIEは後方Keyの位置符号を変更することで、この候補連結を実用的な編集後キャッシュへ変換する。したがって入力は旧KVと編集位置・新トークン、出力は新しい連続位置を持つKV列であり、LLMの重みや注意演算そのものを変更する方式ではない。

### 2. RoPE回転の相殺と一定シフトの導出

RoPEでは位置 $p$ のKeyに回転行列 $R_p$ が作用する。旧位置 $j'$ に保存されたKeyを $k_{j'}=R_{j'}W_kx_{j'}$ と表せば、編集後の正しい位置 $i+m+j'-j$ へ移すには、旧回転の逆 $R^{-1}_{j'}$ を掛けてから新位置の $R_{i+m+j'-j}$ を掛ければよい。原著式(5)は

$$k^{edit}_{j'}=R_{i+m+j'-j}R^{-1}_{j'}k_{j'}$$

と書く。RoPEの回転群では $R_aR_b=R_{a+b}$、$R^{-1}_{j'}=R_{-j'}$ であるため、式(6)は

$$\boxed{k^{edit}_{j'}=R_{i+m-j}k_{j'}}$$

へ簡約される。重要なのは、補正回転 $R_{i+m-j}$ が**後方トークンの旧位置 $j'$ に依存しない**ことである。各層・各後方Keyに同じ編集長差分の回転を適用すればよい。位置差がゼロなら恒等変換となり、挿入なら正方向、削除なら負方向の回転になる。モデルの自己注意は、編集後のQueryと位置補正したKeyとの相対回転で注意重みを計算するため、単純連結で起きる位置の重複を解消できる。

この補正は、後方文脈をTransformer全層に再投入してQuery・Key・Valueを計算し直す操作とは異なる。すでに保存済みのKeyへ一度回転を掛けるだけなので、重み行列積・MLP・注意の再実行を避ける。ValueはRoPEによる位置回転を保持しないため、そのまま残す。一方、後方Key/Valueが旧前方文脈を参照して計算されたという意味的な依存関係は残る。これが近似誤差の主因となる。

### 3. 編集後の連結と生成の再開

位置補正後のKey列は $[K_{1:i};K^{edit}_{i+1:i+m};\widetilde K_{j+1:n}]$、Value列は $[V_{1:i};V^{edit}_{i+1:i+m};V_{j+1:n}]$ とする。ここで $\widetilde K$ は前節の一定回転を適用した旧後方Keyである。更新済みKVと末尾トークンを次トークン予測に渡し、通常の自己回帰生成へ戻る。新規トークンの符号化費用と後方Keyの回転費用は残るが、後方全トークンの再符号化を避けることで編集応答を短縮する。

実装はRoPEの位置行列とKVレイアウトに依存する。論文はDeepSeek-Coderを中心に、付録でCodeLlamaも評価する。任意の位置符号方式へ無修正で適用できるわけではない。さらに一回の編集による位置ずれを扱う式は明快だが、複数箇所を一度に編集する場合は区間ごとのずれを追跡する必要があり、後方すべてへ一つの全域シフトを掛ければ十分とは限らない。原著は複数箇所編集のタスクを実験対象としているが、各区間の境界管理と旧KVの意味的古さには実装上の注意が必要である。

## 評価

### 実験条件・指標・比較対象

RepoBench-C-8kはリポジトリ内のコードから次行を予測する評価であり、PythonとJavaを対象とする。Cross-File-First（XF-F）は他ファイル参照の最初の出現、Cross-File-Random（XF-R）は別の参照位置、In-File（IF）は同一ファイル内の行を予測する。原著表1ではPython・JavaともXF-Fが18,000件、XF-Rが7,500件、IFが10,500件で、平均文脈長はそれぞれ3,967トークン、4,179トークンである。各サンプルのコード文脈に対して、挿入・削除・両方を含む編集を人工的に行い、編集後の次行予測を測る。

標的モデルはDeepSeek-Coderの1.3B、6.7B、33B。1.3B/6.7BはA100 GPU×1、33Bは文脈符号化をA100×2、生成をA100×8で実施する。Transformersを基盤とし、バッチサイズ1、貪欲復号で最大64トークンを生成し、最初の非コメント行を次行予測として評価する。異なる乱数種で3回反復した平均値を報告する。**完全一致率（Exact Match、EM）**は予測行が正解と完全一致する割合、**編集類似度（Edit Similarity、ES）**は部分的な文字列一致を評価する尺度で、値が大きいほどよい。時間指標は**編集後のKV更新のための符号化時間**であり、生成全体のレイテンシではない。

比較は完全再計算、位置衝突を残す高速符号化、PIEの三方式。後者は速いだけでは品質が大幅に崩れるため、PIEの優位性は「更新時間だけを最小化した」という意味ではなく、完全再計算に近い品質を保つための小さい追加費用である。元の未編集コードに対する予測精度を比較する研究でもなく、編集操作による入力変更を含む同一評価タスクでの比較である。

### 挿入時の性能（原著表2）

| 条件 | 完全再計算：EM / ES / KV更新 | 衝突高速：EM / ES / KV更新 | PIE：EM / ES / KV更新 |
|---|---|---|---|
| Python XF-F、6.7B | 28.95 / 70.11 / 561ms | 5.35 / 33.32 / 34ms | **28.83 / 70.01 / 50ms** |
| Python XF-F、33B | 35.75 / 73.46 / 2194ms | 3.96 / 30.13 / 126ms | **35.77 / 73.45 / 134ms** |
| Java IF、1.3B | 45.89 / 78.04 / 198ms | 0.70 / 2.63 / 23ms | **45.92 / 77.99 / 29ms** |
| Java XF-R、33B | 44.95 / 80.87 / 2281ms | 0.59 / 2.40 / 122ms | **45.01 / 80.95 / 133ms** |

Python XF-Fの6.7BではPIEの更新時間が561msから50msへ短縮され、更新処理だけを見ると約11.2倍速い。EM差は0.12ポイント、ES差は0.10ポイントである。対して衝突高速方式は34msとさらに速いが、EMが28.95から5.35へ急落する。位置を補正しないまま旧KVを使うことが、コード補完に重大な品質劣化をもたらす直接的な証拠となる。33Bでは更新時間2194ms対134msで約16.4倍となるが、使用GPU構成が小型モデルと異なるためモデル間の倍率を直接比較しない。

### 削除・複数箇所編集（原著表3・表4）

| 条件 | 完全再計算：EM / ES / KV更新 | PIE：EM / ES / KV更新 | 読み方 |
|---|---|---|---|
| Python XF-F、6.7B、削除 | 28.95 / 70.11 / 561ms | 28.86 / 70.01 / 43ms | EM差0.09ポイント |
| Java IF、33B、削除 | 53.23 / 81.76 / 2270ms | 53.19 / 81.71 / 119ms | 更新時間約19.1倍短縮 |
| Python XF-F、6.7B、挿入＋削除 | 28.95 / 70.11 / 705ms | 28.07 / 69.00 / 54ms | EM差0.88ポイント |
| Java XF-F、33B、挿入＋削除 | 35.05 / 76.93 / 2892ms | 33.72 / 74.69 / 134ms | EM差1.33ポイント、ES差2.24ポイント |

複数箇所編集は単純な挿入より難しく、Java XF-Fの33BではEMが1.33ポイント、ESが2.24ポイント低下する。著者は最大の相対差を編集で1.33%/2.24%と記述するが、表の値からは**百分率ポイント差**として読むのが自然であり、相対率との混同に注意する。論文が「完全に品質を維持」と表現する箇所は、すべてのセルが完全同値という意味ではない。特に後方文脈が前方の編集内容へ強く依存するタスクでは、こうした近似誤差が拡大する可能性がある。

原著本文が報告する挿入＋削除の平均KV更新計算量削減は、Python/Javaの順に1.3Bで87.9%/88.2%、6.7Bで92.4%/92.8%、33Bで94.8%/95.2%である。これらは各言語・モデルの評価タスク平均であり、総リクエスト時間が同率で短縮したことを意味しない。大きいモデルほど再符号化回避の絶対時間が大きい一方、後方Key回転自体のメモリ読み書きは残る。

### 表現・出力分布の比較（原著図3・図4）

DeepSeek-Coder 6.7BのPython条件で、完全再計算後のKey表現とPIE補正Keyの余弦類似度は層を通じて約1.0に近い。補正なしの旧Keyはそれより明確に低い。これは位置衝突を直すだけでも、軽微なコード編集では再計算に近いKey表現へ戻せることを示唆する。ただし図の曲線値を小数点以下まで独自に読み取って断定せず、原著が報告する「約1.0」を用いる。

次トークン分布のカルバック・ライブラー発散（KL divergence）も、完全再計算とPIEの間では64トークンを通じて0.0002未満と報告され、補正なしの高速方式はその約2倍以上となる。KLが小さいことは出力分布の近さを表すが、長期生成の完全一致を保証しない。評価は貪欲復号・コード補完という条件であり、温度付きサンプリングや任意の自然言語対話に同じ差が保たれるかは未検証である。

## 限界・実装時の注意

第一に、PIEが正確に直すのはRoPEの位置情報であり、編集による後方隠れ状態の意味変化ではない。前方の関数定義や型宣言を大きく書き換えると、後方トークンが参照すべき情報も変化する。保存済み後方Valueと非位置成分のKeyは旧文脈から作られたままであり、完全再計算との誤差が増える可能性がある。原著は「小さなコード編集では意味的影響が比較的小さい」と観測するが、編集範囲の大きさに対する保証境界は与えていない。

第二に、RoPE以外の位置符号方式、キャッシュを量子化した場合の回転誤差、複数の編集が短時間で連続する場合の累積誤差は、原著の主要評価で十分に切り分けられていない。回転を施すKeyが低ビット圧縮されていれば、復号・再量子化費用や量子化誤差が追加される。キャッシュ退避や共有接頭辞と組み合わせる場合は、編集後の位置番号・各層のKeyレイアウト・どのキャッシュ領域を所有するかをランタイムで管理する必要がある。

第三に、評価はRepoBench-C-8kのPython/Java、DeepSeek-Coder 1.3B～33B、バッチ1であり、同時多数要求のスループット、KV移送を含む分散サービング、GPUメモリピーク、電力、ユーザー操作から完成応答までの総時間は測定対象ではない。原著の更新時間はモデル前向き計算を省く利得をよく表す一方、生成トークン数が長い場合には更新費用の全体比率が変わる。PIEを一般的なLLM推論全体の高速化率として宣伝してはならない。

第四に、PIEの再利用は**編集前のキャッシュが保持されている**ことが前提である。別の端末・セッションへ移った場合、KVを破棄済みの場合、モデルの重みやRoPEスケールが変わった場合は再利用できない。編集が同じ長さの置換であっても、後方の意味的な状態は変わり得るので「位置差ゼロだから完全に正確」とは言えない。

## 既存方式との関係・サーベイ上の位置

本論文はKVキャッシュの**容量圧縮**ではなく、編集済み文脈に対する**再計算回避と位置整合**の研究である。PagedAttentionのページ管理やKV量子化のように格納方式を変更するのではなく、既存の後方Keyへ代数的な位置補正を行う。接頭辞共有キャッシュの命中判定とも異なり、入力の途中が変化した場合にも後方の一部を再利用する点に特色がある。したがって、長文脈再利用、部分再計算、KV更新、コード補完の低遅延化を扱う系統に位置付けるのが妥当である。

PIEの価値は、単純なキャッシュ連結では位置衝突で精度が崩れるという失敗モードを明示し、RoPEの群構造を利用して**一定シフトのKey回転だけで構造的な不整合を解消できる**と示した点にある。実務上は「何が編集されたか」「どの区間の位置がずれたか」「再計算すべき意味的な依存がどこまで及ぶか」を分離して扱う設計が重要となる。最後の意味的依存を安全に推定する機構は本論文の対象外であり、再計算を省ける範囲を決める上位ポリシーと組み合わせる余地がある。
