# ALISA: Accelerating Large Language Model Inference via Sparsity-Aware KV Caching

> 過去tokenのうちattentionに効きやすい部分だけを残すsparse attentionと、sequence長に応じてKVをGPU保持→CPU offload→GPU再計算へ切り替える3段階schedulerを組み合わせ、KV容量とPCIe trafficを減らすalgorithm-system co-design。

## 概要

ALISAは、長sequenceで増え続けるKV cacheを単にGPU/CPUへ置き分けるだけでなく、**attentionで重要なtokenを選んで参照KV自体を減らし、残ったKVについてもcache・offload・recomputationを動的に切り替える**研究である。

手法は大きく2段階ある。

1. Sparse Window Attention（SWA）で、直近tokenだけでなく過去stepのattention傾向も使って重要tokenを選び、参照するKV数を減らす。
2. sequenceが伸びるにつれて、KVをGPUだけに置く段階、GPU+CPUへ分散する段階、CPUから読み戻すよりGPUで再計算した方が速いKVを捨てて再計算する段階へ切り替える。

さらにKVをINT8へquantizeすることでmemory trafficを追加で減らす。

SWAはtokenを省略するapproximationを含むため、KVPRやCAPTUREのようなlossless recomputationとは異なる。論文では最大80%程度のKV sparsityでも多くの評価で精度低下を小さく保てると報告する。

## 問題設定

KV cacheをすべてGPUへ保持できればdecodeは速いが、batch sizeとsequence lengthに比例してVRAMを消費する。CPUへoffloadすれば容量問題は緩和できるが、PCIe経由のreloadが新しいbottleneckになる。

またsequenceが短い時点ではGPU cachingが最速でも、長くなるとCPU memoryへ追い出す必要が生じ、さらに長くなると**CPUから古いKVを読み戻す時間が、必要時にGPUで再計算する時間より長くなる**領域がある。

ALISAはこの変化を固定policyでは扱わず、sequence進行に応じてmemory hierarchyの使い方を変える。

## 手法

### 1. Sparse Window Attentionで参照tokenを絞る

ALISAはattention weightに強いsparsityがあり、すべての過去tokenが同程度に重要ではないことを利用する。

単純なsliding windowだけではなく、

- **locally static:** 直近の一定範囲など、継続的に保持するtoken
- **globally dynamic:** 過去のattention weightからその時点で重要と判断したtoken

を組み合わせる。

これにより局所文脈を安定して残しつつ、遠い位置にある重要tokenも保持する。実際にattentionへ渡すKVが減るため、memory footprintとmemory accessの両方が小さくなる。

### 2. Token単位の3-phase dynamic scheduling

sequence lengthに応じてKV managementを3段階で切り替える。

#### Phase I: GPU Caching
KV全体がVRAMへ収まる間はすべてGPUへ置く。CPU transferやrecomputationは行わない。

#### Phase II: GPU-CPU Caching
VRAMを超え始めたら、一部tokenのKVをCPU DRAMへoffloadする。頻繁に使う/局所的に必要なKVはGPUに残す。

#### Phase III: Recomputation-Caching
さらにsequenceが伸びると、一部の古いKVはCPUへ保存し続けず削除する。必要になった場合はCPUからreloadせずGPUで再計算する。

phase切替位置、offload割合、recompute割合はmodel・batch・CPU-GPU bandwidthなどからtotal execution timeが小さくなるよう選ぶ。

### 3. CacheかrecomputeかをI/O costで選ぶ

ALISAは、CPUへ保存したKVをPCIe経由で再取得するcostと、GPUで再生成するcompute costを比較する。

sequenceが長くなりCPU↔GPU trafficが増えるほど、recomputationへ切り替える価値が高まる。この点は後続のKVPRへ直接つながる。

### 4. INT8 KV compression

FP16 KVをINT8へ量子化し、cache容量とtransfer byteをさらに減らす。

この量子化はmodel weight quantizationではなく**KV cacheのmemory accessを軽くする目的**で使う。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | 7B/13B: NVIDIA V100 16/32GB、30B: NVIDIA H100 80GB |
| CPU | Intel Xeon 2.60GHz |
| Host memory | 128GB |
| CPU-GPU bandwidth | 20GB/s |
| Model family | OPT / LLaMA / Pythia |
| System workload | Alpaca、input 128 / output 512、batch 4〜64 |
| Baseline | DeepSpeed-ZeRO、HF Accelerate、FlexGen、vLLM |

system評価ではmodel weightとactivationはGPUへ置き、KV managementだけを比較する構成を基本とする。

### 主要結果

80% KV sparsityを主設定としたend-to-end評価で、ALISAは

- FlexGen比 **1.4〜3.0倍 throughput**
- vLLM比 **最大1.9倍 throughput**

を報告している。

vLLMはsmall batchでは有利だが、batchが大きくKV pressureが強くなるほどALISAのsparsity・offload・recomputationの効果が大きくなる。

accuracy評価では、80% sparsityでも多くのmodel/taskでdense attentionからの低下を5%以内に保ち、Alpacaでは約3%の低下としている。ただしこれは**完全なlossless手法ではない**。

## 既存研究との差

### FlexGenとの違い

FlexGenはweight / activation / KVの階層配置とscheduleを最適化するが、KVの中身自体は基本的に保持する。

ALISAは**参照すべきKVをsparsityで減らし、sequence進行に応じてcache先とrecomputationをtoken単位で変える**。

### vLLMとの違い

vLLMはPagedAttentionによりKV allocation fragmentationを減らし、block単位で効率よく管理する。

ALISAはmemory allocatorだけでなく、token-level sparsityとCPU offload / recomputationまで含めてKVの総量・I/Oを減らす。

### KVPRとの違い

ALISAのPhase IIIにも「一部KVを再計算し、残りをCPUから取得する」考え方がある。

KVPRはこの部分をさらに発展させ、**GPU recomputationとPCIe transferを同時に走らせ、hardware profileから両者が同時に終わるsplitを求める**。またKVPRはKVを削除するapproximationではなくexact attentionを保つ。

### CAPTUREとの違い

CAPTUREはKVそのものとactivation checkpointを混在保存し、保存representationを変えることでI/Oとrecomputeを交換する。

ALISAはtoken sparsityをまず導入し、残ったKVをGPU / CPU / recomputationのどこへ置くか動的に選ぶ。

## 限界

- sparse attentionを使うためlosslessではなく、task/modelによってaccuracy低下が変わる。
- 重要token選択のpatternが実際のattentionに合わない場合、必要な長距離情報を落とす可能性がある。
- phase切替やoffload/recompute比率はhardware・model・batch sizeへ依存する。
- H100評価も含むが、host-GPU bandwidthは20GB/sのsingle GPU-CPU構成が中心で、最新の高速interconnectではtrade-offが変わる。
- model weight offload自体は主評価対象ではない。
- 2026-09-06時点で公式code repositoryは確認できなかった。

## 一般的な実装上の含意

ALISAの重要な点は、KV cache managementを**sequence全体で固定したpolicyにしない**ことである。短いsequenceではGPU cache、memory pressureが上がればCPU offload、I/Oがcomputeより高くなればrecomputeと、時間とともに最適戦略が変わる。

またKV最適化では、cache量削減・compression・hierarchical memory・recomputationを別々に考えるより、それぞれのcostを同じruntime modelで比較して組み合わせる方が大きな設計余地を持つ。
