# ALISA：疎注意と階層KV配置の協調による単一GPU推論

## 概要

ALISAは、生成が進むほど増加する鍵・値キャッシュ（KVキャッシュ）の容量とCPU・GPU間転送が、単一GPUでの大規模言語モデル推論を妨げる問題を扱う。通常のKVキャッシュは過去の鍵と値を保持し、次トークンの生成時に過去全体を再計算せず参照できる。しかしバッチ数と系列長に比例して保存量が増えるため、モデル重みがGPUへ収まっていてもKV領域が先に不足する。CPUメモリへ逃がすだけではPCIeを通じた再転送が新しい律速になる。

提案方式は三つの操作を組み合わせる。第一に疎窓注意（Sparse Window Attention、SWA）で、最近のトークンと注意重みから選んだ重要な過去トークンだけを参照する。第二に、生成長に応じてGPU保持、CPU退避、必要時の再計算を切り替える三段階の動的スケジューラを使う。第三に、KVを16ビット浮動小数点から8ビット整数へ量子化し、保存・転送バイト数を減らす。疎化と量子化は品質を変える近似であり、ページ割当だけを変える損失なしの最適化とは異なる。

原著はOPT、LLaMA、Pythiaの6.7B～33B級を評価し、入力128・出力512トークンのAlpaca負荷で、80%のKV疎化を採用した際の処理量を比較する。FlexGenに対して1.4～3.0倍、vLLMに対して最大1.9倍のスループットを報告する。一方、低バッチ・小規模モデルではvLLMの方が速い条件も原著に明記されている。多くの評価課題で品質悪化を5%未満に抑えたという結果も、あらゆるタスクで精度が同じという意味ではない。

## 問題設定と観測

自己回帰生成では、既存の鍵・値を使い回すことで過去系列の反復計算を避けられる。長さを増やすと、注意の計算だけでなくGPUの高帯域メモリへKVを置く容量も必要になる。KVが収まらなくなればCPUメモリを使えるが、CPU・GPU間の帯域はGPU内部メモリより狭く、注意計算がKVの到着を待つ。原著図1はOPT-6.7BとV100 32GBで、GPUだけに置く場合の容量超過と、CPU退避率を増やした場合のメモリアクセス時間の増大を分けて示している。

既存のFlexGenはGPU・CPUの階層を利用するが、KV配置方針は生成中の系列長に対して基本的に固定される。vLLMはページ単位の割当と共有で断片化を抑えるが、注意で参照するトークン自体を減らすわけではない。H2Oのような重要トークン選別もあるが、ALISAは注意の全履歴ではなく局所的な重み履歴から選び、選別したKVの供給元を生成進行に合わせて変える点に特徴がある。

GPUだけで保持できる初期には退避も再計算も余計な費用になる。系列が長くなるとCPU退避が必要になり、さらに長くなると、古いKVをCPUから読み戻すよりGPU上で作り直す方が安い領域が生じる。したがってキャッシュの最適化は「保存するか削除するか」の単発判断ではなく、容量、帯域、再計算速度、系列長を結び付けた動的な問題になる。

## 手法

### 重要なKVだけを残す疎窓注意

SWAは現在の問い合わせ、過去のKV、最近の注意重み、保持率を入力とする。保持するトークン数を系列長と保持率から決め、半分を直近の連続トークン、残り半分を遠い過去の重要トークンへ割り当てる。直近側は語順や近距離依存を失わないための固定窓であり、過去側は直近数ステップの注意重みをトークンごとに合算して高得点の位置を選ぶ。各生成ステップで重要度が変わるので、遠方の保持集合は動的に更新される。

この方式では、すべての過去トークンについて毎回完全な注意重み履歴を集計する方式と違い、近傍の観測を使って過去の重要度を近似する。選ばれたトークンの位置番号に対応するKVを取り出し、通常の注意演算へ渡す。重要度の計算、上位位置の選択、疎なKVの収集にも実行費用があるため、疎化率が高ければ必ず同率でカーネルが速くなるわけではない。図11では疎化後の小さな行列がGPU演算器を使い切れず、行列積の実効演算性能が下がる問題も示されている。

SWAが除外したKVは注意計算に参加しないので、これは厳密な全履歴注意と等価ではない。直近窓だけの方式と比べれば重要な遠方トークンを拾えるが、過去の注意重みが将来の必要性を予測できない場合には、長距離依存に必要な情報を捨てる可能性が残る。保持率を増やせば品質の安全側へ寄せられる一方、GPU容量とCPU転送の負担が戻る。

### 三段階のKV供給元切替

動的スケジューラはGPUの空き容量、CPU容量、CPU・GPU間帯域、モデルの層数・隠れ次元、バッチ数、入力・出力長を使って、各トークンのKVをどこから供給するか決める。第1段階はGPUだけにKVを保持する。疎化後のKVがGPU容量に収まる間はCPUとの転送を発生させず、余分な再計算も避ける。ここではキャッシュ削減が容量不足の開始時点を遅らせる。

第2段階では、系列が第1切替点を超えるとGPUとCPUへKVを分割する。直近窓のトークンは次の生成でも使うことが確実なのでGPUに優先配置し、遠方の動的選択集合をCPUから読み込む構成にする。どのKVをCPUへ退避し、どれを読み戻すかはトークン単位で管理する。FlexGenのように注意ヘッド単位で固定割合を割り当てる方式とは粒度が異なる。

第3段階では、CPUからの転送がさらに重くなると、CPUに置いた古いKVの一部を削除し、必要になった時点でGPUに再計算させる。再計算は演算量を増やすが、CPUからの転送時間をより大きく減らせる条件では総実行時間を短縮する。原著図12では再計算を利用することによって約1.2～1.3倍の実行時間改善が報告される。ただし高速なCPU・GPU接続ではこの損益分岐点が変わり、同じ再計算率を使う理由はない。

### 切替点・退避割合・再計算割合の費用モデル

切替点を `p1` と `p2`、CPUへの退避割合を `α`、再計算割合を `β` とする。論文はGPU計算時間、CPU・GPU転送時間、再計算時間の合計を小さくする最適化問題として、これらを同時に選ぶ。16ビットの鍵と値について、1トークン分のKV容量はバッチ数 `b`、層数 `l`、隠れ次元 `h` に比例し、原著の記法では `4blh` バイトとなる。CPU・GPU転送時間は移動するKVバイト数を実効帯域 `B` で割った量を基礎とする。

転送側の費用は容量・帯域などの制約から計算し、計算側の費用はモデル・バッチなどの構成ごとに事前計測する。著者はこの測定結果を使って貪欲探索で切替点と割合を選び、実行中に大規模な探索を行わない。したがって動的なのは生成時の配置・再計算への切替であり、費用モデルの全パラメータを毎ステップ再学習する方式ではない。装置構成が変われば計測をやり直す必要がある。

### KVの8ビット量子化

SWAと配置最適化の後に残るKVも容量を使うため、ALISAはチャネル単位の尺度と零点を用いてKVをINT8へ量子化して保存する。計算時には元の16ビット形式へ戻す。これはモデル重みの量子化ではなく、生成中に蓄積する中間状態の圧縮である。単純な保存バイト数は半分近くになるが、尺度・零点の保存と変換演算が必要であり、モデル全体のGPU使用量が半減するわけではない。

KVが小さくなれば第1段階の持続可能な系列長が伸び、第2段階の転送量も減る。したがって量子化はスケジューラの切替点にも影響する。SWAによる参照集合の近似と量子化誤差が重なるので、品質は両者を併用した設定で確認しなければならない。著者は図8でSWA単独と量子化を加えたALISAの精度曲線を比較している。

## 評価結果

| 検証対象 | 比較・条件 | 原著の報告と解釈 |
|---|---|---|
| 全体処理量 | Alpaca、入力128/出力512、FlexGen比 | 1.4～3.0倍。モデル・バッチ条件で幅がある |
| 全体処理量 | 同負荷、vLLM比 | 最大1.9倍。小規模・低バッチでは逆転する |
| 再計算の効果 | OPT-30B、H100、バッチ64、図12(b) | 第3段階のCPU読み戻しの一部を再計算へ置換して約1.2～1.3倍改善 |
| 品質 | 複数モデル・7データセット、入力2048、図8 | 多くの設定で80%疎化時の悪化が5%未満。Alpacaは約3%低下 |
| 疎化の限界 | LLaMA-33B、図8 | 単純な局所・間引き注意は低疎化率でも急落するが、SWAは80%付近まで比較的維持 |
| 内部演算 | バッチ64、系列128、図11 | 疎化率上昇で演算量は減るが、疎な収集処理とGPU稼働率低下が残る |
| 構成要素除去 | OPT-30B、H100、図12(c) | 疎化、動的配置、量子化の寄与を比較。効果は疎化率で変わる |

速度結果を解釈するときは、生成全体の処理量と単一注意演算の速度を混同しない。図9は異なるバッチとモデルの全体処理量であり、図11は注意処理の内部費用、図12は同じOPT-30B構成での段階別費用である。前処理と復号の合計時間、生成トークン数、処理量の定義を混同しないよう、ここでは原著の倍率と条件を対応させた。大きなモデルではバッチ数が増えるほどKV容量が効くため、ALISAの利得が大きくなる傾向がある。

品質については、図8で疎化率を変えたときの困惑度と正答率を別々に測定している。SWAと量子化を併用したALISAの曲線は多くの条件でSWA単独と近いが、OPT-30BとLLaMA-13BのCOPAでは小さな差が残る。したがって「量子化誤差ゼロ」ではない。特定のタスクで密注意を上回る結果もあるが、これを一般的な精度向上保証と解釈することはできない。

図12の段階別内訳は、CPU・GPU間のKV転送を減らすことが全体の改善に大きく寄与することを示す。一方、GPUメモリ使用量は疎化率だけで単調には決まらない。スケジューラがメモリ最小化ではなく実行時間最小化を目的とするため、空き容量を利用してGPUに保持する量が変わる。第3段階への移行時点も疎化率によって後ろへ移る。

## 既存研究との差

FlexGenは階層メモリへの配置を事前に最適化するが、生成長の変化に合わせたトークン単位のKV供給元切替はALISAほど細かく扱わない。vLLMのページ化KV管理は断片化と共有を改善するが、ALISAのように注意対象そのものを疎にするわけではない。H2Oは注意重みの大域的な重要度に基づいて保持トークンを選ぶのに対し、ALISAは直近窓と局所的な注意重み履歴から選んだ遠方集合を組み合わせ、GPU・CPU・再計算の実行経路と接続する。

この違いから、ALISAの優位性は「KVキャッシュを損失なしで管理する方式より常に速い」という単純な比較では説明できない。ALISAは許容できる近似誤差を利用して必要KVを減らし、さらにCPU転送と再計算の損益を調整する。精度を厳密に一致させた比較ではないため、利用目的に応じて速度と品質の両方を読む必要がある。

## 限界・負の結果

第一に、SWAは重要度推定を誤ると必要な過去トークンを参照できなくなる。80%疎化でも多くのタスクでは品質低下が小さいが、すべての条件で損失なしとは言えない。量子化も値の近似を加える。長距離の厳密な引用や特定位置の再生が必要な課題では、保持率と精度の再測定が必要になる。

第二に、評価対象は単一GPUとCPUの組合せであり、モデル重みと活性値をGPUに常駐させる。GPUメモリが重みだけで埋まるモデルや、CPUへ重みも退避する場合にはKV転送と重み転送が帯域を取り合う。論文の処理量をそのまま適用できない。複数GPU間通信、オンライン連続バッチング、P99遅延、実ユーザーの到着分布は主要評価の範囲外である。

第三に、図9は小さいモデル・低バッチではvLLMがALISAを上回ることを明記している。疎化選択、位置の収集、量子化・逆量子化、費用モデルの事前計測には固定費用があり、KV容量が問題にならない負荷では利得が縮む。最大1.9倍という結果をすべてのバッチに一般化してはいけない。

第四に、疎化によって行列積が小さくなるとGPUの多数の演算器を十分に埋められず、演算回数の減少ほど実行時間が短くならない。図11では局所重み集計や疎なKVの収集自体が律速になる条件もある。専用の疎注意カーネルや新世代GPUでどの程度改善するかは別途実装・評価が必要である。

第五に、動的配置の費用モデルは装置帯域と計算速度を事前に測る。20GB/sのCPU・GPU接続から、より高速な共有メモリ、CXL、NVLink接続へ移す場合は切替点を再決定する必要がある。CPU転送より再計算が速い領域が常に存在するとは限らない。モデル・バッチ・文脈長の分布が変化する運用環境でも事前費用モデルの妥当性を監視する必要がある。
