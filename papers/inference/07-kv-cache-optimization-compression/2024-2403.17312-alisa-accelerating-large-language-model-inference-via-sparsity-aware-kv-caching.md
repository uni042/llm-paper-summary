# ALISA: Accelerating Large Language Model Inference via Sparsity-Aware KV Caching

> attentionで重要な過去tokenだけを参照し、sequenceが伸びるにつれてKVをGPU保持・CPU退避・GPU再計算へ切り替えることで、KV容量とPCIe転送を減らす手法。

## 概要

ALISAは、長sequenceで増え続けるKV cacheを単にGPU/CPUへ置き分けるだけでなく、**attentionで重要なtokenを選んで参照KV自体を減らし、残ったKVについてもGPU保持・CPU offload・再計算を状況に応じて切り替える**研究である。

手法は大きく2段階ある。

1. 直近tokenと、過去にattentionが強かったtokenを残して参照するKV数を減らす。
2. sequenceが伸びるにつれて、KVをGPUだけに置く段階、GPU+CPUへ分散する段階、CPUから読み戻すよりGPUで再計算した方が速いKVを捨てて再計算する段階へ切り替える。

さらにKVをINT8へquantizeすることでmemory trafficを追加で減らす。

重要token以外をattention対象から外す近似を含むため、KVPRやCAPTUREのようなexact recomputationとは異なる。論文では最大80%程度のKV sparsityでも多くの評価で精度低下を小さく保てると報告する。

## 問題設定

KV cacheをすべてGPUへ保持できればdecodeは速いが、batch sizeとsequence lengthに比例してVRAMを消費する。CPUへoffloadすれば容量問題は緩和できるが、PCIe経由でKVを戻す待ち時間が新しいbottleneckになる。

またsequenceが短い時点ではGPU cachingが最速でも、長くなるとCPU memoryへ追い出す必要が生じ、さらに長くなると**CPUから古いKVを読み戻す時間が、必要時にGPUで再計算する時間より長くなる**領域がある。

ALISAはこの変化を固定policyでは扱わず、sequence進行に応じてmemory hierarchyの使い方を変える。

## 手法

### 1. 直近tokenと、遠くても重要なtokenを組み合わせて残す

ALISAはattention weightに強い偏りがあり、すべての過去tokenが同程度に重要ではないことを利用する。

残すtokenは大きく二種類ある。

- **直近token:** 局所文脈を安定して保つため継続的に残す。
- **過去の重要token:** 過去stepのattention weightを見て、遠い位置でも現在の生成へ効きそうなtokenを選ぶ。

論文では前者を `locally static`、後者を `globally dynamic` と呼ぶ。

これにより単純なsliding windowより長距離情報を残しながら、実際にattentionへ渡すKV数を減らす。

### 2. Sequence長に応じてKVの扱いを3段階で変える

#### Phase I: GPU Caching
KV全体がVRAMへ収まる間はすべてGPUへ置く。CPU transferやrecomputationは行わない。

#### Phase II: GPU-CPU Caching
VRAMを超え始めたら、一部tokenのKVをCPU DRAMへoffloadする。頻繁に使う、または直近で必要なKVはGPUに残す。

#### Phase III: Recomputation-Caching
さらにsequenceが伸びると、一部の古いKVはCPUへ保存し続けず削除する。必要になった場合はCPUからreloadせずGPUで再計算する。

phase切替位置、offload割合、recompute割合はmodel・batch・CPU-GPU bandwidthなどから、**合計実行時間が短くなる組み合わせ**を選ぶ。

### 3. CPUから戻すかGPUで作り直すかを時間で比較する

ALISAは、CPUへ保存したKVをPCIe経由で再取得する時間と、GPUで再生成する時間を比較する。

sequenceが長くなりCPU↔GPU trafficが増えるほど、recomputationへ切り替える価値が高まる。

### 4. INT8 KV compression

FP16 KVをINT8へ量子化し、cache容量とtransfer byteをさらに減らす。

これはmodel weight quantizationではなく、**KV cacheの保存量とmemory accessを軽くする目的**で使う。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | 7B/13B: NVIDIA V100 16/32GB、30B: NVIDIA H100 80GB |
| CPU | Intel Xeon 2.60GHz |
| Host memory | 128GB |
| CPU-GPU bandwidth | 20GB/s |
| Model family | OPT / LLaMA / Pythia |
| System workload | Alpaca、input 128 / output 512、batch 4〜64 |
| Baseline | DeepSpeed-ZeRO、HF Accelerate、FlexGen、vLLM |

system評価ではmodel weightとactivationはGPUへ置き、KV managementだけを比較する構成を基本とする。

### 主要結果

80% KV sparsityを主設定としたend-to-end評価で、ALISAは

- FlexGen比 **1.4〜3.0倍 throughput**
- vLLM比 **最大1.9倍 throughput**

を報告している。

vLLMはsmall batchでは有利だが、batchが大きくKV使用量が増えるほどALISAのsparsity・offload・recomputationの効果が大きくなる。

accuracy評価では、80% sparsityでも多くのmodel/taskでdense attentionからの低下を5%以内に保ち、Alpacaでは約3%の低下としている。ただしこれは**完全なlossless手法ではない**。

## 既存研究との差

### FlexGenとの違い

FlexGenはweight / activation / KVの階層配置とscheduleを最適化するが、KVの中身自体は基本的に保持する。

ALISAは**参照すべきKVを減らし、sequence進行に応じて保存先とrecomputationをtoken単位で変える**。

### vLLMとの違い

vLLMはPagedAttentionにより、KV用memoryを小さなblockへ分けて必要分だけ割り当て、未使用領域が細切れに残る無駄を減らす。

ALISAはmemory allocatorだけでなく、token-level sparsityとCPU offload / recomputationまで含めてKVの総量・I/Oを減らす。

### KVPRとの違い

ALISAのPhase IIIにも「一部KVを再計算し、残りをCPUから取得する」考え方がある。

KVPRはこの部分をさらに発展させ、**GPU recomputationとPCIe transferを同時に走らせ、両方がほぼ同時に終わる分担量をhardware測定から決める**。またKVPRはKVを削除する近似ではなくexact attentionを保つ。

## 限界

- sparse attentionを使うためlosslessではなく、task/modelによってaccuracy低下が変わる。
- 重要token選択が実際のattention需要と合わない場合、必要な長距離情報を落とす可能性がある。
- phase切替やoffload/recompute比率はhardware・model・batch sizeへ依存する。
- H100評価も含むが、host-GPU bandwidthは20GB/sのsingle GPU-CPU構成が中心で、最新の高速interconnectでは最適な分担が変わる。
- model weight offload自体は主評価対象ではない。
- 2026-09-06時点で公式code repositoryは確認できなかった。

## 一般的な実装上の含意

ALISAの重要な点は、KV cache managementを**sequence全体で固定したpolicyにしない**ことである。短いsequenceではGPU cache、memory pressureが上がればCPU offload、I/Oがcomputeより高くなればrecomputeと、時間とともに最適戦略が変わる。

またKV最適化では、cache量削減・compression・hierarchical memory・recomputationを別々に考えるより、それぞれの時間costを同じruntime modelで比較して組み合わせる方が大きな設計余地を持つ。
