# GraniKV: Asymmetric Granularity KV-Cache Paging for Multi-Agent Systems with Long Shared Prefix

## 概要
multi-agent LLMではシステム プロンプト、tool定義、共有メモリなど非常に長い接頭辞を複数リクエストが共有する一方、各agentが生成するsuffixは長さも寿命も異なる。一般的なpaged KV キャッシュは全領域へ同じpage粒度を使うため、共有接頭辞ではpage table traversalや分断が増え、suffixでは大きなpageによる内部断片化が生じる。

GraniKVは両領域を同じallocatorで妥協させず、共有接頭辞を連続配置するHOT プールと、リクエスト固有suffixをトークン粒度で管理するCOLD プールへ分離する。さらに計算律速、メモリ律速、通信-boundの状態に応じて注意機構 backendを切り替える。16K共有接頭辞ではproduction 比較対象比で出力-トークン スループットを2.16倍、1.98倍、1.57倍へ改善する。

## 問題設定
共有接頭辞は多くのリクエストから再利用されるため、連続配置して大きなGEMMとして処理できるほど効率がよい。一方suffixはリクエストごとに増減し、途中終了もあるため、小さいallocation unitの方がメモリ utilizationを高められる。uniform pagingはこの二つの要求を同時に満たせない。

またバッチ-大域なcascade 注意機構は全リクエストが同じ接頭辞境界を持つ場合には効率的だが、異なるプロンプト長・内容が混在すると一括処理の前提が崩れる。GraniKVはストレージ 層自体に共有領域と個別領域の意味を持たせ、heterogeneous ワークロードでも利用可能にする。

## 手法
### HOT pool
共有接頭辞のKVを連続領域へ置き、page単位の散在を避ける。長い共有接頭辞をbatched GEMM型backendへ渡せることが主な利点で、複数リクエストが同じKVを参照する際のmetadata traversalとメモリ アクセスを規則化する。

### COLD pool
各リクエスト固有suffixはトークン granularityで確保する。短いsuffixや長さのばらつきに対して大pageを予約しないため、内部断片化と不要なreserved メモリを減らす。接頭辞とsuffixでallocatorを分けることが「asymmetric granularity」の中心である。

### per-step dispatcher
実行段階ごとに、現在のバッチ、接頭辞共有度、テンソル 並列構成などから有利なbackendを選ぶ。計算、メモリ、通信のどれが律速かによって同じ注意機構 カーネルが最適とは限らないため、dual backendを使い分ける。

## 評価条件
|項目|条件|
|---|---|
|モデル|Llama-3.1-8B、Qwen2.5-14B、Qwen2.5-32B|
|並列|TP=1 / 2 / 4|
|代表接頭辞|16K shared トークン|
|比較|production paged-推論提供 比較対象、バッチ-大域 cascade|
|指標|出力-トークン スループット、エンドツーエンド gain|

## 主要結果
16K共有接頭辞で、Llama-3.1-8B/TP=1は比較対象比2.16倍、Qwen2.5-14B/TP=2は1.98倍、Qwen2.5-32B/TP=4は1.57倍の出力-トークン スループットを達成する。構成要素分解ではcascade 注意機構統合が飽和時の主要利得を担う一方、非対称ストレージ 層単独でもエンドツーエンドで1.05〜1.15倍を追加し、batched-GEMM 接頭辞 backendを成立させる前提になる。

さらに異なる長さ・内容のプロンプトが混在するheterogeneous multi-agent 推論提供では、バッチ-大域 cascadeが比較対象と同程度まで崩れるのに対しGraniKVは1.95倍を維持する。この条件ではストレージ 層側が主要な利得源へ反転する。

## 既存研究との差
PagedAttention系はKVを固定pageへ分割してfragmentationを抑えるが、接頭辞とsuffixへ同じgranularityを適用する。GraniKVは再利用特性の違いをストレージ policyへ直接反映し、接頭辞を連続大粒度、suffixを極小粒度へ分ける。単なるcascade 注意機構最適化でもなく、heterogeneous プロンプトでcascadeの前提が崩れた場合にもストレージ側の利得を残す。

## 限界
長い共有接頭辞が少ないワークロードではHOT プールの価値は小さくなる。連続領域を確保するためメモリ pressureやプール sizingの管理が必要で、すべてのリクエストが完全に異なるプロンプトなら共有接頭辞 backendの利得は限定的である。最大倍率は16K 接頭辞と評価したモデル/TP条件に依存する。
