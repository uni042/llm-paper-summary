# CaR: An Efficient KV Cache Reuse System for Large Language Model Inference

> 破棄されていた履歴の鍵値キャッシュをHBMとCXLメモリの二層に残し、スケジューラと協調した先読み・退避・層別疎化で要求をまたいで再利用し、最初のトークンまでの時間を約30パーセント、長い文脈では60パーセント超短くした多層キャッシュ基盤。

## 概要

大規模言語モデルの生成は、入力全体を一度に処理する入力処理（プリフィル）と、過去のトークン全部を参照しながら1トークンずつ生成する段階（デコード）からなる。過去トークンの鍵と値のベクトルを保持する鍵値キャッシュ（以下では鍵値キャッシュと呼ぶ）は、デコードの再計算を避けるための仕組みだが、現在の提供基盤は応答が終わるとそのキャッシュを積極的に破棄してしまう。しかし仮想助手や多ターンの会話では、後の要求が前の要求と履歴を共有することが多い。共有部分の鍵値キャッシュを再利用できれば、高価な入力処理を丸ごと省ける。特に長い入力では、最初のトークンまでの時間（以下、初回遅延と呼ぶ）が全体の遅延の大半を占めるようになるため、再利用の利得は大きい。

本論文が提案するCaR（シーエーアール）は、この再利用を可能にする多層キャッシュ基盤である。高速だが小さいGPUの高帯域メモリ（HBM）を速い層とし、低速だが大容量の外部メモリを遅い層とする。外部メモリには通常の主記憶ではなく、計算機間接続規格であるCXL（Compute Express Link）を使うデバイスを選び、GPUとCXLの間でCPUを経由しない直接転送を行うことで、CPU側の処理との帯域競合を避ける。その上で、要求の実行順を決めるスケジューラとキャッシュ管理を別々に作らず協調設計し、どの履歴を速い層に置くか、いつCXLから読み戻すか、いつ退避するかを、実行順序と連動して決める。さらに、層ごとに注意の疎らさが違うという観測を使い、層ごとに違う比率でキャッシュを疎化して、保持量と転送量の両方を削る。

**代表結果:** 論文の予備評価では、保存済みの鍵値キャッシュをCXL側から読み戻す方式は、入力を再計算する方式と比べて初回遅延を約30パーセント短くし、OPT 13Bでは長い文脈の条件で60パーセントを超える短縮になった。ただし、これは再計算と再読み込みの遅延比較であり、CaRの全機構を組み込んだ基盤全体の端から端までの評価ではない点に注意が要る。

## 問題設定

なぜ履歴を残すだけで足りず、多層化と協調設計が必要になるのか。鍵値キャッシュの大きさは、トークン数、バッチの大きさ、各層の埋め込み次元に比例して増える。論文の見積もりでは、2000トークンの要求1件で、OPT 30Bの鍵値キャッシュは約2.6ギガバイトになる。モデルの重みだけで56ギガバイトを使うため、40ギガバイトのA100を4台使っても、2000トークンの要求を同時に抱えられるのは40件程度にとどまる。つまり履歴を全部速い層に残すことはできず、大容量の遅い層へ逃がすことが前提になる。

遅い層を使うと、新たに三つの問題が生じる。第1は置き場所である。速い層は高価で小さく、遅い層は大きくて遅い。要求ごとにキャッシュの大きさも読み戻し費用も違うため、固定大きさのページを入れ替える従来の運用方式の置換方針をそのまま持ち込めず、利用頻度と最終利用時刻以外の要素を入れた置換判断が要る。第2は転送費用である。CXL 3.0でも帯域は毎秒64ギガバイト程度で、GPUの処理速度に大きく劣る。読み戻しを待ってGPUが止まれば、再計算を省いた利得が待ち時間で消える。生成中も新しいトークンのキャッシュが増え続けるため、速い層が満杯になって処理が止まる前に退避もしなければならない。第3は転送を始める時刻である。早く読み戻しすぎると、関係する要求が実行されるまでデータが速い層で眠り、容量を無駄にする。遅すぎると、要求がデータの到着まで止まる。実行順を決めるのはスケジューラであり、読み戻しを担うのはキャッシュ管理であるため、この二つは本来切り離せない、と論文は位置づける。

## 手法のあらまし

処理の流れは次のとおりである。新しい要求が届くと、まずキャッシュ表を引いて、その入力の鍵値キャッシュが速い層にあるか、遅い層にあるか、どこにもないかを確認する。速い層にあればそのまま再利用して入力処理を省く。遅い層にだけあれば、スケジューラが実行順を決める過程で先読み器へ住所と大きさを渡し、先読み器が実行開始に間に合う時刻を見計らって層単位に読み戻す。どこにもなければ通常どおり入力処理を行い、できたキャッシュは後の再利用のために保持される。速い層の利用率が9割を超えると、非同期の退避器が重要度の低いキャッシュ節を背景で遅い層へ移し、生成の継続を妨げない。保持と転送の対象は、品質配慮型の疎化で層ごとに間引かれており、重要でないトークンの鍵値が落ちている分だけ、容量と転送量の両方が小さい。

## 手法

### 1. 二層の保持と直接転送 — 履歴をどこに置き、どう運ぶか

この機構が保持する状態は、過去の要求の入力部分について計算済みの鍵値キャッシュであり、速い層のHBMと遅い層のCXLメモリに分かれて置かれる。観測するのは新しい要求の入力と、キャッシュ表に記録された各キャッシュ節の所在である。キャッシュ表の各行は、節の識別子、所在を示す住所、速い層に現在あるかどうかを示す印、大きさ、後述する重要度スコアを持つ。新しい要求の入力と一致する節が表にあれば、その鍵値を読み出して再利用し、一致しなければ通常の入力処理で新しく作る。減るボトルネックは、共通する履歴部分についての入力処理の計算そのものであり、長い入力ほど効果が大きい。外部メモリに主記憶ではなくCXLデバイスを使うのは、GPUと外部メモリの直接転送により、CPUで動く他の処理と帯域を取り合う干渉を避けるためである。追加で消費する資源は、遅い層の大容量と、キャッシュ表の管理費用である。失敗条件は、履歴の重なりがほとんどない要求列であり、その場合は再利用が起きず、保持と管理の費用だけが残る。

### 2. スケジューラとの協調と優先順位 — 実行順そのものをキャッシュの都合で決める

スケジューラは優先順位付きの待ち行列で実行順を決めるが、その優先順位を、遅い層から速い層へ運ぶ必要があるデータ量で決める点がこの論文の中心的な工夫である。第1位は、再利用する鍵値キャッシュが既に速い層にある要求で、転送なしにすぐ実行できる。第2位は、履歴データを一切持たない要求であり、転送が不要な分だけ、後続の転送に時間の余裕を残せる。第3位が、遅い層のキャッシュを部分的にしか使えない要求である。直感に反するようだが、部分的に使える要求を履歴なしの要求より後ろに置く理由は論文に明記されている。部分利用の要求を先に実行すると、転送が間に合わないまま実行枠に入り、データ待ちでGPU時間を浪費する危険があるためである。さらに、優先順位だけでは低い順位の要求が長く待たされ、先読みの対象も目まぐるしく変わってしまう。そこで待ち行列の先頭には、大きさ固定のシャッフル窓と呼ばれる範囲を設け、この範囲内の要求は許容できる待ち時間のうちに必ず実行され、先読み器もこの範囲を見て落ち着いて転送計画を立てられるようにする。減るボトルネックは、データ待ちによるGPUの空転と、要求の保留時間である。追加費用は、実行順が到着順や公平性からずれることであり、窓の外に置かれた要求の待ち時間が伸びる条件では、この設計が不利に働き得る。

### 3. スコアによる置換 — どの節を速い層から追い出すか

速い層が満杯になったときに追い出す対象は、重要度スコアが最も小さいキャッシュ節である。スコアはスケジューラの動きと連動して更新される。要求がシャッフル窓に入ると、その節のスコアが1増える。要求がGPUへ送られて推論が始まるとさらに1増える。要求の生成が終わると2減る。つまり、実行が近づいた節と実行中の節は追い出されにくく、終わったばかりの節は、再利用の見込みが下がったものとして追い出し候補に戻る。観測するのは要求の状態遷移であり、保持する状態は節ごとのスコアである。従来の置換方針が見る利用頻度や最終利用時刻に加えて、要求ごとの大きさと読み戻し費用の違いを、実行順との連動という形で取り込むのが狙いである。減るボトルネックは、再利用直前の節を誤って追い出して再計算や再転送が発生する事態である。失敗条件は、終わった直後の節がすぐ再利用される会話パターンであり、その場合はスコアが下がった直後に追い出されて、読み戻し費用を余分に払うことになる。論文はこの方針の定量的な優劣を単独では評価していない。

### 4. パイプライン先読み — 読み戻しの時刻と重ね方を決める

先読み器は、シャッフル窓の中の各要求について、キャッシュ表を引き、住所が有効で速い層に無い節を見つけると、その住所と大きさを転送計画へ載せる。いつ転送を始めるかは、各要求の出力長を予測し、1トークンあたりの出力時間からGPUが現在の要求列を処理し終える時刻を見積もり、必要なデータ量をその時点の帯域で割った転送時間と比較して決める。要するに、転送がちょうど間に合う最も遅い時刻に始めることで、データが速い層で眠る時間を短くする。さらに転送そのものは層単位のパイプラインで行う。モデルの計算が層ごとに進むことを使い、最初の層の計算をしている間に後続の層の鍵値を読み込むことで、転送時間を計算時間の裏に隠す。減るボトルネックは、読み戻し待ちによる要求の保留時間と、速い層でのデータの滞留時間である。追加費用は、出力長予測と時刻管理の仕組みであり、失敗条件は出力長の予測が外れる場合である。予測より早く前の要求が終われば転送が間に合わず、逆に遅く終わればデータが速い層で眠る。論文は予測の外れ方に対する定量評価を示していない。

### 5. 非同期退避 — 退避を要求の本道から外す

生成が進むと新しいトークンの鍵値が速い層に溜まり続ける。退避を要求の処理の流れの中で同期的に行うと、満杯のたびに生成が止まる。そこでCaRは、速い層の利用率が9割を超えたら、置換方針のスコアに従って節を遅い層へ移す非同期の退避器を背景で動かす。退避が始まると完了を待たずに成功の信号が返り、GPUは推論や先読みを続けられる。観測するのは速い層の利用率であり、選択するのはスコアの低い節である。減るボトルネックは、退避が生成の本道を塞ぐ時間である。追加費用は、背景転送が先読み転送と帯域を取り合う可能性であり、両者が重なる条件での干渉は論文では未評価である。

### 6. 品質配慮型の疎化 — 層ごとに違う比率でキャッシュを薄くする

保持量と転送量そのものを削る機構が、品質配慮型の疎化である。観測は、注意スコア行列の疎らさが層ごとに大きく違うことである。行の最大値の1パーセント未満の要素を実質ゼロとみなすと、第1層の疎らさは約60パーセントだが、深い層では約95パーセントまで上がる。そこでCaRは、モデルを読み込むときに、あらかじめ用意した入力例で推論を一度流して層ごとの疎らさを取り、その後の推論では層ごとに違う圧縮率を適用し、注意スコアの低いトークンに対応する鍵値を落とす。浅い層はあまり落とさず、深い層を強く落とすという、層ごとに不均一な間引きになる。減るボトルネックは、保持する容量と、遅い層から読み戻す転送量の両方である。これは近似を伴う機構であり、落とした鍵値に対応する情報は失われる。失敗条件は、疎らさの傾向が入力例と実要求でずれる場合で、その場合は重要度の判定が外れて生成品質が下がり得る。ただし本論文は、疎化による品質変化を数値では評価していない。

| 構成要素 | 入力・観測 | 具体的な動作 | 改善対象 | 主なトレードオフ |
|---|---|---|---|---|
| 二層保持と直接転送 | 要求の入力とキャッシュ表 | 履歴の鍵値をHBMとCXLメモリに保持し直接転送で運ぶ | 共通履歴の入力処理の再計算 | 履歴の重なりがない要求列では利得なし |
| 優先順位付き実行順 | 運ぶ必要があるデータ量 | 速い層に有る要求、履歴なし要求、部分利用要求の順に実行 | データ待ちの空転 | 公平性が崩れ待ち時間が伸びる要求が出る |
| スコア置換 | 要求の状態遷移 | 窓入りと実行開始で加算、完了で減算し、最小の節を追い出す | 再利用直前の誤追い出し | 完了直後の再利用では読み戻しが増える |
| パイプライン先読み | 出力長予測と帯域 | 間に合う最も遅い時刻に層単位で読み戻す | 保留時間と滞留時間 | 出力長予測が外れると隠し切れない |
| 非同期退避 | 速い層の利用率 | 9割超でスコアの低い節を背景で移す | 退避による生成の停止 | 先読み転送との帯域競合 |
| 品質配慮型疎化 | 層ごとの注意の疎らさ | 層ごとに違う比率で低スコアの鍵値を落とす | 保持量と転送量 | 近似であり品質変化は未評価 |

## 評価

結論は、現時点では一点に限られる。保存済みの鍵値キャッシュを読み戻すことは、入力を再計算することより明確に速く、その差は入力が長いほど開く。論文が示すのはこの予備的な比較までであり、先読み、置換、非同期退避、疎化といった個別機構の寄与や、基盤全体での端から端までの遅延とスループット、生成品質への影響は、いずれも数値では示されていない。したがって本論文は、完成した基盤の性能報告としてではなく、再利用の利得の大きさを確認した上での設計提案として読むのが正確である。

## 既存研究との差

従来の提供基盤は、鍵値キャッシュを1件の要求の中でのみ使い、終われば破棄する設計だった。ページ化された注意機構で知られるvLLMも、メモリ管理の主眼は実行中の要求の間での効率であり、履歴を要求をまたいで残すことは目的に入っていない。接頭辞の共有を扱う先行研究は、共有できる入力の判定と再利用そのものに焦点があり、再利用するデータをどの階層に置き、いつ運ぶかまでは扱わない。本論文の差は三点ある。第1に、保持先として主記憶ではなくCXLデバイスを選び、GPUとの直接転送でCPU側との干渉を避けたこと。第2に、スケジューラとキャッシュ管理を別部品としてではなく、実行順と転送計画を互いに決め合う協調設計として作ったこと。第3に、圧縮を一律ではなく、層ごとの注意の疎らさに合わせた不均一な疎化として設計したことである。もっとも、これらの差はいずれも設計上の主張であり、数値で裏づけられているのは再利用そのものの利得だけである。

## 限界・実装状況

第1に、評価が予備的な段階にある。再計算と再読み込みの遅延比較が示されただけで、先読み、置換、非同期退避、疎化を含む基盤全体の遅延、スループット、品質は測られていない。機構ごとの寄与の分解もないため、どの工夫がどれだけ効くのかはこの論文からは分からない。第2に、品質の未評価である。疎化は注意スコアの低いトークンの鍵値を落とす近似であり、品質配慮型と名乗る根拠は層ごとの疎らさの観測だけである。困惑度やタスク精度での確認がないため、安全な圧縮率の範囲は不明である。第3に、前提への依存が強い。利得は履歴の重なりがある要求列を前提とし、重なりの少ない負荷では保持と管理の費用だけが残り得る。また、CXLデバイスの実在と帯域を前提とするため、通常の主記憶やネットワーク越しの外部メモリでは同じ数字にはならない。第4に、公平性の論点が残る。部分利用の要求を実行順の後ろへ回す設計は、条件によっては特定の要求の待ち時間を大きく伸ばし得るが、その分布は評価されていない。実装状況としては、vLLMを土台に試作され、8台のA100を持つ計算機で動かしたと述べられるが、公式実装の公開先は論文中に記載されていない。再現は論文の記述から追う形になる。

## 一般的な実装上の含意

この論文から一般化できる原則は三つある。第1に、再利用の可否だけでなく、置き場所、転送の隠し方、転送を始める時刻を分けて設計すべきである。再利用できても、戻す時刻を誤れば容量か待ち時間のどちらかで利得を失う。第2に、実行順を決める側とデータを管理する側が情報を共有すると、データ待ちの空転を構造的に減らせる。実行順が先に固定されてから転送を間に合わせるのではなく、転送の都合を実行順へ織り込む発想は、他の階層メモリ型の基盤にも移せる。第3に、圧縮率は対象の内部構造の偏りに合わせるべきである。層ごとに疎らさが60パーセントから95パーセントまで違う以上、一律の比率は、落としすぎか落とし足りないかのどちらかになる。ただし第3の原則を実運用へ持ち込むには、本論文が欠いている品質側の測定が前提になる。
