# PolyKV: A Shared Asymmetrically-Compressed KV Cache Pool for Multi-Agent LLM Inference

> 共通文書のKVキャッシュを一度だけ非対称量子化して共有プール化し、複数エージェントへ注入して重複メモリを削減する。
## 書誌情報
- **著者**: Ishan Patel, Ishan Joshi
- **著者・所属**: 論文本文参照。
- **公開**: arXiv / Zenodo
- **種別**: Preprint
- **対象**: KVキャッシュ、マルチエージェント、共有キャッシュ、非対称量子化、TurboQuant
- **実装**: HuggingFace DynamicCacheを利用したSharedKVPoolとPooledAgentの研究試作。公式コードURLは本文で確認できなかった。
## 概要
複数のLLMエージェントが同じ文書を読む場合、通常は各エージェントが同じ接頭辞のKVキャッシュを別々に保持し、エージェント数に比例してメモリが増える。PolyKVは共有文書を一度だけプリフィルして単一の圧縮KVプールへ保存し、各エージェントのHuggingFace DynamicCacheへ必要な層のKVを注入する。キーは注意スコアへの感度を考慮して8ビット、値は回転後3ビットで非対称に圧縮する。共有と圧縮を同時に行うことで、エージェント数に対して共有プール容量を一定に保ちつつ、品質劣化を小さく抑える。

PolyKVは共通文書を一度だけプリフィルし、そのKV状態を単一のSharedKVPoolへ非対称圧縮して保存する。各エージェントはこの共有プールを読むだけで、圧縮済み本体を複製せず、自分専用のDynamicCache外殻へ層ごとに復元したKVを注入して独立生成する。さらにキーと値の感度差を利用し、注意スコアへ直接入るキーは8ビット、値は高速Walsh-Hadamard変換で回転してから3ビットLloyd-Max量子化する。共有と圧縮を一つの実行モデルへ結合した点が中心である。

代表結果として、KV圧縮率は二モデル・全文脈長・全エージェント数で16ビットK/Vキャッシュに対して2.91倍。K8/V3という固定ビット配分から決まる圧縮率で、モデルや読者数に依存せず安定する。
## 問題設定
Transformer推論では各層のキーと値をKVキャッシュとして保持するため、モデル規模と文脈長に応じてメモリ使用量が増える。複数エージェントが同じ長い文書を参照して独立に質問へ答える場合、標準方式では各エージェントが同じ共有文書部分を別々にプリフィルし、同内容のKVキャッシュをN個保持する。既存のKV量子化は一要求あたりの容量を減らすがキャッシュ自体は要求ごとに独立し、KVFlowなどの共有方式は共通接頭辞を再利用しても全精度キャッシュを前提とする。したがってエージェント数と長文文脈が同時に増えると、共有可能な内容にもかかわらずメモリ重複が残る。
## 新規性
PolyKVは共通文書を一度だけプリフィルし、そのKV状態を単一のSharedKVPoolへ非対称圧縮して保存する。各エージェントはこの共有プールを読むだけで、圧縮済み本体を複製せず、自分専用のDynamicCache外殻へ層ごとに復元したKVを注入して独立生成する。さらにキーと値の感度差を利用し、注意スコアへ直接入るキーは8ビット、値は高速Walsh-Hadamard変換で回転してから3ビットLloyd-Max量子化する。共有と圧縮を一つの実行モデルへ結合した点が中心である。
## 手法
### 手法のあらまし
最初にSharedKVPoolが共有文書とモデルを受け取り、文書に対するプリフィルを一度だけ実行して全層のキー・値テンソルを得る。標準方式ならこの状態をエージェントごとに保持するが、PolyKVはここで一度だけ圧縮する。キーは各テンソルのスケールを求めて8ビット整数へ線形量子化する。キーは注意スコアのsoftmaxへ直接影響し、低ビット化に敏感なので、値より高い精度を残す。値はTurboQuant MSE方式を使い、まず高速Walsh-Hadamard変換（Fast Walsh-Hadamard Transform; FWHT）で成分を回転して外れ値を分散させる。回転後の各成分を正規分布向けに事前計算した8個のLloyd-Max重心の最も近いものへ写し、3ビット相当の添字として保存する。キー8ビット・値3ビットを同程度の大きさのKVへ適用するため、16ビット基準に対して理論上約2.91倍の圧縮となる。各PooledAgentは共有プールへの参照だけを持ち、生成開始時に新しいDynamicCacheを作る。層を順にたどり、共有プールからその層のキーと値を復元し、対象層が置かれた装置へ移してDynamicCacheへ登録する。そのキャッシュを過去KVとして生成処理へ渡すため、各エージェントは共通文書を再プリフィルせずに自分の質問を続けられる。圧縮プール本体はエージェントごとに複製されないので、共有部分の保存容量はエージェント数Nに対してO(1)となる。一方、各エージェントの生成で新たに生じる個別KVや、復元時の一時テンソルは別途必要である。量子化は非可逆なので品質誤差を持ち、特にキーを過度に低ビット化すると注意分布が崩れる。このためPolyKVはキーに8ビットを残し、値側へ強い3ビット圧縮を集中させる。

### 書込み一回・複数読者の共有KVプール
SharedKVPoolは共通文書を一度だけプリフィルして得た全層KVを圧縮し、エージェントとは独立した一つの共有オブジェクトとして保持する。3、5、10、15個と読者が増えても圧縮プール本体を複製しないため、共有文書部分の保存容量は一定である。各PooledAgentは共有プールへの参照を持ち、生成時に自分専用のDynamicCacheを新規作成する。層ごとに共有KVを復元してこの外殻へ登録するので、エージェント同士が同じ可変キャッシュ構造を直接書き換えて競合することを避けつつ、元の圧縮データは共有できる。標準のエージェントごとの再プリフィルと全精度キャッシュ複製を同時に除くことが、エージェント数に比例するメモリ増加を抑える仕組みである。

### キー8ビット・値3ビットの非対称圧縮
キーは注意スコア計算に使われるため誤差へ敏感であり、PolyKVはテンソル単位の線形8ビット量子化を用いる。値はより強く圧縮できるとみなし、FWHTで成分を回転して分布を均し、正規分布に合わせた8個のLloyd-Max重心へ各成分を写す3ビット量子化を使う。復元時は重心値を取り出し、逆FWHTで元の座標系へ戻す。KとVを同じビット幅へ押し込まず感度に応じて精度を配分することで、16ビットKVに対して安定した2.91倍の圧縮率を得ながら、低ビットキーによるsoftmax不安定化を避ける。

### 全体のデータ／制御の流れ
共通文書を一度だけ処理するSharedKVPool、エージェントごとのPooledAgent、HuggingFace DynamicCacheへの層単位注入から構成される。圧縮プールは読取り共有し、生成状態はエージェントごとに分離する。
## 評価条件
- **ハードウェア**: SmolLM2-1.7B-InstructはCPU規模の概念実証として評価し、主なLlama-3-8B-Instruct評価はKaggleのNVIDIA T4 GPU 2基で実施する。
- **ソフトウェア**: HuggingFace TransformersのDynamicCacheを利用する。Llama-3-8Bは32層、GQA 8 KVヘッド、4ビットNF4重み、bfloat16 KVキャッシュで実行し、全精度のエージェント別DynamicCacheを比較対象とする。
モデルはSmolLM2-1.7B-InstructとLlama-3-8B-Instructの二規模、共有文脈は約600トークンから7,194トークンまでを用いる。並行エージェント数を3、5、10、15へ増やし、圧縮率、KVメモリ、文脈後半30%のパープレキシティ、生成結果のBERTScore F1を測る。文脈には単一話題のApollo 11・ARPANET文書とWikiText-2を使い、エージェント数と文脈長を独立に変えて、共有による容量効果と量子化品質を切り分ける。
共有接頭辞を持つ複数エージェントの実験であり、異なる文書を読むエージェント間では同じ共有率を得られない。主評価はT4 2基と二モデルに限られ、実サービスの到着過程、キャッシュ追い出し、複数利用者のスケジューリング、エンドツーエンドのスループット改善は中心評価ではない。
## 主要結果
キー8ビット・値3ビットの非対称圧縮は全条件で2.91倍の圧縮率を保つ。Llama-3-8Bで7,194トークンの共有文脈を15エージェントが読む条件では、エージェント別全精度KVの合計19.798 GBに対し共有圧縮プールは0.454 GBで、97.7%削減となる。この条件でもパープレキシティ増加は0.57%、平均BERTScore F1は0.928である。エージェント数を増やしても同じ共有文脈に対するパープレキシティ差は変化せず、品質誤差は読者数ではなく圧縮された共有KVに由来する。

- KV圧縮率 / 2.91倍 (比較対象: 16ビットK/Vキャッシュ; 条件: 二モデル・全文脈長・全エージェント数) — K8/V3という固定ビット配分から決まる圧縮率で、モデルや読者数に依存せず安定する。

- KVメモリ削減 / 19.798 GBから0.454 GB、97.7%削減 (比較対象: 15エージェントが各自7,194トークンの全精度KVを保持; 条件: Llama-3-8B、15エージェント、長文共有文脈) — 共有プール本体がエージェント数に比例しないため、読者数が増えるほど全精度個別キャッシュとの差が拡大する。

- パープレキシティ差 / +0.57% (比較対象: 全精度KV; 条件: Llama-3-8B、7,194トークン、10および15エージェント) — 強いV圧縮を使っても長文条件では品質差が小さく、エージェント数を増やしても差が増えない。

- 意味類似度 / 平均BERTScore F1 0.928 (比較対象: 全精度KVからの生成; 条件: Llama-3-8B、15エージェント、7,194トークン) — 語句の違いを許容した意味レベルでも生成内容が概ね維持される。

### 負の結果・境界条件
- 圧縮は非可逆であり、Llama-3-8Bの1,837トークン条件ではパープレキシティが1.59%悪化する。10エージェント条件では個別BERTScore F1が0.9008となる例もあり、全生成が一律に閾値0.92を超えるわけではない。長い一貫文脈でパープレキシティが改善する現象を著者は量子化雑音の正則化仮説で説明するが、制御実験による因果検証は将来課題としている。

### 結果の読み方
容量削減は二つの独立効果の積で生じる。まず一つの共有プールにすることで共通文書KVのN重複を除き、さらにその一つを2.91倍圧縮する。したがってエージェント数が増えるほど共有効果が大きくなる一方、量子化による品質差は同じ圧縮KVを読む限りエージェント数に依存しない。
## 品質への影響
非可逆量子化なので品質変化を伴う。短めのLlama-3-8B文脈では+1.59%、長文では+0.57%のパープレキシティ差を報告し、SmolLM2の1,851トークン一貫文脈では-0.26%となる。ただし改善値は正則化仮説であり一般的な品質向上を保証しない。
## 既存研究との差
KIVI、KVQuant、LeanKVなどは一要求のKVを圧縮するが、エージェントごとの独立キャッシュを前提とする。KVFlow、KVCOMM、LRAgentなどはエージェント間共有を扱うが、共有KVは全精度が中心である。PolyKVは単一の共有プールと非対称圧縮を同時に適用し、複数の並行読者が同じ圧縮KVを参照する。キー8ビット・値3ビットという非対称性は、キーのsoftmax感度と値の圧縮耐性を分けて扱う。
## 限界
共有できるのは同じ文書接頭辞から得たKVであり、各エージェントが異なる文脈を持つ部分は個別に増える。圧縮は非可逆なので品質誤差があり、BERTScoreの個別例では閾値を下回る生成もある。評価は二モデルとT4中心で、実運用のキャッシュ追い出し、共有文脈の更新、エージェント故障、同時生成スケジューリング、圧縮・復元のエンドツーエンド時間を包括的には評価していない。長文でパープレキシティが改善する正則化仮説も未検証である。
## 実装状態
HuggingFace DynamicCacheへ層単位で復元KVを注入する研究試作として実装され、SmolLM2-1.7BとLlama-3-8Bで評価されている。論文にはZenodo DOIがあるが、確認した本文では公式ソースコードURLを特定できなかった。
## 研究上の位置づけ
エージェント型推論で共有接頭辞が長く、同じ資料を多数のエージェントが読む場合のKVメモリ重複を対象にする。通常のKV量子化は一要求の容量を下げる縦方向の最適化、接頭辞共有は要求間重複を除く横方向の最適化とみなせ、PolyKVは両者を積み重ねる。分離推論や階層KVオフロードと組み合わせる場合、共有圧縮プールをGPU・CPU・SSDのどこへ置くか、復元帯域と共有率をどう釣り合わせるかが次の設計軸になる。
