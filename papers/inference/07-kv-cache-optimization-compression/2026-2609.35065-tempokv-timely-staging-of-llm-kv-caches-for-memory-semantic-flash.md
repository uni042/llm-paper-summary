# TempoKV：再利用KVの発見と高速メモリ予約の時刻を分離する配信基盤

## 概要

TempoKVは、過去の要求で計算済みの接頭辞キー・バリュー（KV）キャッシュを、SSDを背後に持つ大容量メモリ階層から再利用する際、**再利用が分かった時点で高速メモリを確保しない**という設計を導入する。要求の接頭辞がキャッシュに一致したという論理的な命中は、そのKVがGPUへすぐ転送できる状態であることを意味しない。SSDからCXLメモリ装置内のDRAMへ事前配置する時間が必要だが、早過ぎる予約は小さい高速層を長時間占有する。

提案方式は、要求がGPUへのKV転送を開始するまでの予測時間（time-to-use、TTU）と、装置側で必要なKVを高速層へ配置・保護するまでの予測時間（time-to-ready、TTR）を比較する。前者が後者以下になった時点で初めて予約を試み、保護容量が不足すれば通常のオンデマンド取得へ戻す。vLLMとLMCacheを拡張したH100実機評価では、即時予約と比べて保護容量時間を63～91%削減した。未改変LMCacheのDevice-DAX L1構成に対しては、NarrativeQAでp95初回トークン遅延を最大48.0%短縮し、出力処理量を最大27.8%増やした。ただしこれらは**異なる比較群・実験条件**の結果であり、一つの実験で同時に達成した数値ではない。

## 問題設定と背景

接頭辞KVの再利用は、同じ長文書や共通のシステム指示を繰り返し入力する場合に事前処理（prefill）の再計算を避ける。生成中に毎ステップ参照する生存中のKVとは異なり、要求間に保存される接頭辞KVは再利用が来るまで静止している。このため、GPUの高帯域メモリより安価なホストメモリやSSDへ退避する余地がある。一方、再利用要求が到着した際にSSDから読み始めると、GPUがデータを待つため初回トークン遅延（TTFT）が悪化する。

メモリ意味型フラッシュ（memory-semantic flash）は、SSDの大容量と小さな高速メモリ層を、メモリ的なアクセス抽象の下に組み合わせる。論文の実装ではCXL Type-3装置内DRAMが高速層であり、SSDが背後の大容量層となる。**論理的にメモリアドレスを参照できることと、対象データが高速層に実際に存在することは異なる。** 必要なKVオブジェクトがSSD側に残っていれば、SSD→装置DRAMの転送が必要になる。その後で装置DRAM→GPUへの転送を行う。TempoKVが制御するのは前者の準備と保護予約であり、後者の転送経路は既存のLMCacheを使う。

要求待ち行列の先頭へ近づいたら事前転送する方式は、先行要求の残り生成時間やストレージの転送待ちを考慮しない。論文の図2では同じ待ち行列順位1でも、準備完了時刻の余裕は2.67秒早い場合から6.02秒遅い場合まで変動する。順位だけでは「何秒前に準備すべきか」を決められない。反対に、接頭辞命中の発見直後にすべて予約すると、先行要求が長い間高速層を占有する。

原著の動機付け実験では、Llama-3.1-8B-Instructの64Kトークンの接頭辞（KV容量8GiB）をSSDに保存し、装置DRAMを空にして事前転送の先行時間を変えた。先行時間0秒から1秒へ増やすと、要求投入後の初回トークン遅延中央値は1.23秒から0.51秒へ低下した。しかし1秒から4秒へ延ばしても遅延はほぼ改善せず、保護容量時間だけが8から32GiB・秒へ増加した。したがって「十分早いが、それ以上は早過ぎない」予約が必要となる。

## 手法

### 1. 命中の記録と資源予約の分離

vLLM側の実行アダプタは、待機中の要求に再利用可能な接頭辞KVが見つかると、必要なKVオブジェクトの順序付き一覧を持つ**要求単位の予約候補（staging claim）**を作る。この段階は計画済み（Planned）状態であり、オブジェクト識別子や見込み時刻などのメタデータを保持するだけで、SSD読み出しも高速層の保護予約も行わない。これにより、再利用の情報は早く取得しつつ、他の要求のキャッシュ利用を妨げない。

各要求のキャッシュ一致範囲はLMCacheの既存接頭辞検索を用いて特定し、通常のGPU転送経路を維持する。制御対象は実行スケジューラの順序ではなく、SSDから装置DRAMへ事前転送するための資源確保時刻である。したがって推論要求の優先順位やバッチ形成をTempoKV自身が変更するわけではない。

### 2. 実行側の使用開始予測TTU

実行アダプタは、現在のバッチ、各要求の処理進捗、待ち行列内の順序、残りの事前処理・生成仕事量から、対象要求の**装置DRAM→GPUのKV転送が始まるまで**の時間使用開始予測時間を推定する。これはモデルがKVを実際に消費する時刻でも、初回トークンを出力する時刻でもない。計画上、対象KVはすでに準備できていると仮定する。もし未完了のSSD転送による遅れをTTUへ織り込むと、予約を先延ばししたこと自体が次の予約判断をさらに遅らせる循環が起こるためである。

進行中の要求については、既に生成した$n$トークンと過去の完了要求の出力長$N$を使い、$N>n$を満たす履歴の$N-n$の平均から残り出力長を予測する。上限生成長も考慮し、同時進行する要求を単純に逐次時間として足し合わせず、共通の実行時間軸で推定する。要求の終了やバッチ変更があれば使用開始予測時間を更新する。履歴と実際の出力長が異なる場合は予測誤差が生じるため、後段の再評価が不可欠である。

### 3. 記憶装置側の準備完了予測TTR

ストレージ側の提供器は、今この瞬間に予約した場合、必要な全KVオブジェクトが装置DRAMに存在し、かつ追い出し禁止の保護状態になるまでの時間準備完了予測時間を推定する。入力は現在の常駐オブジェクト、保護状態、進行中・待機中のSSD転送、残り転送バイト数、実効転送速度である。まだSSDから読んでいないオブジェクトだけを新規転送対象とし、別要求が既に転送中のオブジェクトは同じ転送を共有する。

予測では、SSD転送が並列に進むことを考慮し、各オブジェクトの単純な転送時間を足すのではなく、最後の必要オブジェクトが準備完了する時刻を求める。実効速度は過去の完了転送と並行負荷から更新する。既に全データが常駐していても他要求の転送待ちに依存する場合、準備完了予測時間は必ずしも0にならない。高速層の空き容量があるかは、この時間予測とは別の条件として扱う。

### 4. 余裕時間の比較と予約実行

制御器は$\widehat L(t)=\widehat{TTU}(t)-\widehat{TTR}(t)$を計算する。$\widehat L>0$ならまだ準備の猶予があり、$\widehat L\leq0$なら今始めなければ間に合わない可能性がある。後者になった場合、または実行側が実際にKV取得を要求した場合、予約候補を**予約試行可能**にする。ただし「試行可能」は「予約成功」と同義ではない。提供器がオブジェクトの有効性、常駐状態、必要な追加保護容量を再確認し、全対象の保護が可能な場合だけ確定する。

保護容量が不足すれば候補はPlannedのまま残り、別の候補の予約試行を妨げない。制御器は要求順序変更、進行状況、転送完了、容量解放、50ms周期の制御時点で使用開始予測時間と準備完了予測時間を再評価する。予約後は途中で取り消してSSD I/Oを無駄にしない。未予約のまま実際の取得時刻を迎えた場合は、通常のオンデマンド取得へ排他的に切り替える。これにより保護容量が不足しても要求を停止せず処理を継続できるが、SSD遅延を隠せない可能性は残る。

### 5. 共有オブジェクトの保護・解放と実装

複数要求が同じKVオブジェクトを必要とする場合、SSD読み出しと保護容量の予約を共有する。予約候補はPlanned→Staging→StageReady→Transferring→Releasedという状態を遷移し、必要な全オブジェクトが常駐・保護されて初めてStageReadyになる。GPUへの転送完了まで保護を維持し、最後の利用者が解放した時点で追い出し可能に戻す。Releasedは物理データ消去を意味せず、DRAMに残っていれば通常キャッシュとして再利用され得る。

著者実装はvLLM 0.23.0とLMCache 0.5.1を拡張し、XCENA MX1PのCXL Type-3装置で範囲単位の事前転送とpin/unpinを実装する。装置ファームウェアやCXL転送路は変更しない。提供器は保護済み容量と転送予約を同じ上限内で管理し、未保護領域にはLRU追い出しを許す。保護領域を物理的に別のメモリとして静的分割するのではなく、予約上限を論理的に設ける。従って、保護容量を減らせても物理DRAM占有率が同じ割合で減るとは限らない。

### 指標の定義

p95初回トークン遅延（p95 TTFT）は、クライアントの要求投入から最初の出力トークン受信までの時間の95パーセンタイルであり、小さいほど遅い要求が減る。出力処理量は成功した応答の総出力トークン数を、最初の要求投入から最後の応答完了までの経過時間で割った値である。保護容量費用$C=\int_0^T P(t)dt/N$は、保護予約された高速層のGiBを時間積分し完了要求数$N$で割ったGiB・秒/要求である。$P(t)$には未完了転送のための予約も含むが、共有オブジェクトは二重計上しない。$C$は**保護予約の時間的な費用**であり、物理DRAMの平均占有量や消費電力量そのものではない。

### 予約時刻の比較と負の結果

| 条件・比較対象 | 観測結果 | 何を示すか |
|---|---|---|
| 2モデル×接頭辞再利用率50/75/100%の6条件、Immediate比 | $C$を63～91%削減 | 早過ぎる予約の削減 |
| 同6条件、Queue-4比 | $C$を62～86%削減 | 待ち順位だけより資源占有を短縮 |
| 再利用率100%、Demand比 | p95 TTFT最大25.7%短縮、出力処理量最大20.4%改善 | 適時予約でSSD待ちを隠蔽 |
| Llama 8B、再利用率100%、Queue-4比 | 提案方式のp95 TTFTが4.7%悪化、処理量もわずかに低い | 速度だけでは常に最良ではない |
| 上記Llama条件、Queue-4比 | $C$は62%小さい | 速度を少し犠牲に予約容量時間を大きく節約 |
| Llama 8B、再利用率100%、静的TTR比 | p95 TTFTのDemand比改善が14.5%→20.5%、$C$は4.0→4.8GiB・秒/要求 | 記憶装置状態を考慮すると速度改善と予約費用が交換関係になる |

再利用率50%では、事前準備できるKV量が小さく、予約のための容量時間を長く消費しても初回トークン遅延の改善は小さい。即時予約やQueue-4が一部条件で速いことは、提案方式が単純な速度最適化ではなく「速度と保護容量の両立」を狙う設計であることを示す。論文は容量費用の削減率と処理量の改善率を別々に測定しており、両者を足し合わせたり単一の効率倍率へ変換したりしない。

### 高速層容量の感度

Llama-3.1-8B-Instruct、再利用率100%で高速層容量を100→50→25GiB、保護予算を50→25→12.5GiBへ減らす。提案方式は約106出力トークン/秒、p95 TTFT約5.9秒をほぼ維持した。容量を4分の1にしても性能が維持されたのは、この実験の要求順序と接頭辞サイズにおいて、必要なKVが使用直前に保護できたためである。

25GiBでは提案方式が6方式中で最高の処理量と最低の平均・p95 TTFTを示した。保護容量不足で予約を延期した要求はTempoKVで1件、ImmediateとQueue-4ではそれぞれ6件だった。早期に保護し過ぎると後続要求の予約余地が減るため、適時予約は単なるメモリ節約にとどまらず混雑時の遅延も改善する。一方、静的な準備時間推定方式は保護費用が近くても性能が劣り、転送待ちや常駐状態を見た時刻予測が重要だと分かる。

### 未改変LMCacheとの独立比較

別実験では、提案機構を含まないLMCacheのDevice-DAX L1構成（LMCache-DAX）と比較する。Llama-3.1-8B-Instruct、名目再利用率100%、高速層100GiB、提案方式の保護予算50GiBを使用し、NarrativeQAとLooGLEからそれぞれ16文脈を抽出する。出力上限は32トークン、要求投入率は0.2～4要求/秒である。この比較では要求投入率を揃え、実運用に近い遅延と処理量の交換関係を調べる。

| データセット | LMCache-DAX比の最大p95 TTFT短縮 | 最大出力処理量改善 | 注意 |
|---|---:|---:|---|
| NarrativeQA | 48.0% | 27.8% | 提案機構を含まない既存L1構成との比較 |
| LooGLE | 32.4% | 15.5% | 異なる長文脈データでも傾向を確認 |

ここでの48.0%と27.8%は、先述のImmediateとの保護容量時間63～91%削減とは**比較対象も負荷も異なる**。実験結果をまとめる際に「同じ条件で48%高速化し91%容量削減した」と書くのは不正確である。また数値は投入率ごとの最大改善であり、全投入率で常に同じ改善が出るわけではない。

## 既存研究との差

単なる接頭辞キャッシュは「一致したKVを再利用できるか」を判断し、通常の事前転送は「どのKVを先に読み出すか」を判断する。提案方式はさらに、再利用が分かった後でも**高速層の保護容量を確保する時刻**を遅らせる。実行側は要求進捗からTTUを、記憶装置側はSSD転送と常駐状態からTTRを別々に計算し、両者の差で予約試行を決める。この境界は、待ち行列順位をトリガーにする方式や、記憶装置内部の状態を見ない静的な事前転送とは異なる。

CXLメモリそのものを新たに設計する研究ではなく、CXLを利用したSSD背後のメモリ階層に対するソフトウェア制御層である。vLLMの要求スケジューリングを変更しないため、負荷分散や要求順序最適化と組み合わせる余地がある。一方、実験したのはSSD→高速層の準備時刻であり、KV圧縮、GPU上の注意カーネル、生成トークンの演算数削減を直接行うものではない。

## 限界と適用条件

実機評価はH100を持つ単一サーバ、SSD背後のCXL装置1台、二つの言語モデルと特定の長文脈ワークロードに限られる。SSDの実効転送速度、装置DRAMの容量、保護予算、要求到着間隔、出力長分布が異なれば、使用開始予測時間と準備完了予測時間の予測誤差や予約タイミングが変わる。特に推定が遅過ぎる場合はSSD待ちが露出し、早過ぎる場合は保護容量時間が増える。容量が不足した際には通常取得へ戻るため、最悪遅延を必ず抑えられるわけではない。

また、保護容量費用$C$は消費電力やSSD寿命の直接測定ではない。保護予約を短くしても、キャッシュが実際に占める物理DRAMやSSD書込量が同率で減るとは限らない。実装はvLLM 0.23.0とLMCache 0.5.1の拡張版であり、両プロジェクトの標準機能として統合されたとは原著からは断定できない。GPUメモリに十分な接頭辞KVが収まる場合、SSDステージング自体が発生しないため本方式の利益は限定される。
