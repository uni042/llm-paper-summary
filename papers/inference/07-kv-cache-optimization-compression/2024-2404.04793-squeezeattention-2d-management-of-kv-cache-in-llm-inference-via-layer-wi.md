# SqueezeAttention：注意層ごとの重要度でKVキャッシュを二次元配分する方式

## 概要

SqueezeAttentionは、大規模言語モデルの推論で必要になる鍵・値キャッシュ（KVキャッシュ）を、系列中のトークン方向だけでなく、注意機構を構成する層の方向からも最適化する方式である。従来の追い出し方式は「どのトークンを残すか」を工夫するが、異なる層へ同じ保持数を与えやすい。ところが注意層ごとに隠れ表現を変化させる度合いは異なる。出力へ大きく寄与する層から過去情報を削ることと、変化の小さい層から同じ量を削ることは、生成品質に同じ影響を与えるとは限らない。

著者らは、入力プロンプトを一括処理する段階で各注意層の処理前後の隠れ状態を比較し、余弦類似度が高い層ほど表現の変化が小さいという代理指標を作る。層を三群へ分け、変化の小さい群からキャッシュ保持枠を回収して、重要な二群へ再配分する。再配分した各層の枠の中では、既存のトークン追い出し方式をそのまま実行する。層そのものを削除したり、別の生成モデルで補助したりする方式ではない。

一次論文は、6.7Bから70Bまでの七モデルと五つの課題で、系列方向の圧縮方式に比べたキャッシュ使用量の改善を報告する。代表的な三条件では、品質をおおむね維持する設定で、完全保持方式に対するトークン当たりキャッシュ関連メモリが70～80%少なく、系列方向だけの比較方式に対して25～66%少ない。八基のA100で測った同一バッチの生成処理能力は、完全保持方式比でMistral-7Bが最大2.2倍、Llama2-70Bが最大1.4倍だった。ただしこの値はGPUやバッチ、系列長を固定した実験結果であり、あらゆる推論環境での保証ではない。

## 問題設定と既存方式の限界

自己回帰型の生成では、入力プロンプトを処理した後、出力トークンを一つずつ生成する。次のトークンの注意計算は過去の鍵と値を必要とするため、各層の鍵・値を保持して再計算を避ける。キャッシュの要素数は、層数、同時要求数、入力と出力を合わせた系列長、鍵・値の幅に比例して増える。論文が例示するLlama2-7Bの半精度設定では、重みが約14GBである一方、キャッシュはトークン当たり約0.5MBを占める。全要求を合わせて約28,000トークンになると、キャッシュ容量が重み容量と同程度になる。このため、キャッシュを小さくできれば、同じGPUメモリで同時に処理できる要求数を増やせる。

従来の系列方向の圧縮では、直近のトークンだけを残す滑動窓（Sliding Window）、系列冒頭の注意集中位置と直近部分を残すStreamingLLM、累積注意得点の高い位置を優先するH2Oなどがある。これらは過去のどの位置を保持するかに着目する。どの層でも同じ保持数を割り当てる場合、過去情報への感度が小さい層に余分な枠を与え、感度の大きい層から必要な情報を削ってしまう可能性がある。

関連方式のFastGenは層や頭ごとに異なる追い出し方針を選ぶが、同じ方針を採る層に割り当てる容量まで最適化するとは限らない。SqueezeAttentionは、追い出すトークンの順位付けと、その順位付けを適用するための層別保持枠を分離する。既存の追い出し方針の得意不得意を置き換えるのではなく、保持枠の配分という別の自由度を使う。

重要層を一度だけ固定してしまう方式にも限界がある。層の役割はモデル構造だけでなく、与えられた課題やプロンプトによって変わり得る。論文付録は同じモデルでもデータセットによって重要層の数が異なる例を示す。そのため提案方式は、推論要求の実際の入力を一括処理する時点で重要度を測り、要求に応じて予算を決める。

## 手法

### 注意層の寄与を余弦類似度で測る

第一段階では、プロンプト処理中の各注意層について、自己注意計算の直前と直後の隠れ状態を取得する。トークン位置ごとに二つのベクトルの余弦類似度を計算し、その層についてプロンプト内の全位置で平均する。値が1に近ければ注意計算を通過してもベクトルの向きがほとんど変わらず、値が低ければ比較的大きく変わったと解釈する。測定対象は注意部分の前後であり、層全体の出力と入力の差を無条件に混同してはならない。

著者らはMistral-7B、Llama2-7B-32K、Llama2-70B、Falcon-7Bに各200プロンプトを与え、層ごとの類似度を可視化した。全般に前半の層で表現変化が大きく、後半では変化の小さい層が増える一方、先頭や末尾の一部は重要になる場合がある。この観察から、層の深さだけを使う固定的な比例配分より、入力に基づく指標を使う理由が得られる。

ただし、余弦類似度は「この層のキャッシュを削ったとき最終的な正答率が何点下がるか」を直接測ったものではない。変化が小さいことを削除耐性の代理とみなす経験的な仮説である。提案方式はこの代理指標の誤差を、重要層の保護と削減率の調整によって管理する。

### 三群への分類と保持予算の再配分

第二段階では、各層について得られた平均余弦類似度を入力にして、K-meansによって三群へ分類する。原著のアルゴリズムでは平均類似度が最も高い群をG3とし、表現変化が小さいためキャッシュ予算を減らす対象にする。残るG1とG2は重要な層として予算を増やす。著者らの説明ではG1に先頭・末尾などの特別な層が入り、G2はそれ以外の重要層を含む。G3は実験したモデルで全層の約50～70%を占めた。

全層数をL、各層に一律に与える初期保持枠をb、削減群に残す割合をp（0より大きく1未満）とする。G3の層にはそれぞれp×bを与え、G1とG2の各層には、全体のL×bからG3へ割り当てた合計を引き、残る層数で割った枠を与える。したがって、総保持枠L×bは変更しない。層間の配分を変えることで、同じ総メモリ予算での品質改善を狙うのが本質である。

例として32層のうち14層をG3、18層を重要群とし、初期枠が各1,000トークン、pが0.3なら、G3は各300トークンへ減る。回収した14×700=9,800トークンを18層へ等分すると、重要群は各約1,544トークンになる。総量は32,000トークンのままである。これは論文付録の計算例に対応し、削減による品質変化を追加メモリの投入と混同しないために重要である。

### 各層固有の枠でトークン追い出しを行う

第三段階は逐次生成である。各層はプロンプト処理で生成された鍵・値を保持して開始し、新しいトークンを生成するたびに自分のキャッシュ長と割当枠を比較する。枠を超えた層だけ、選択した系列方向の圧縮器を、その層の個別枠を引数として実行する。圧縮器がH2Oなら注意得点に基づく重要位置を残し、滑動窓なら直近位置を残し、StreamingLLMなら冒頭の注意集中位置と直近位置を残す。各層は同じ圧縮器を使っても、保持できる位置数が異なる。

この構成では、層の重要度を測る処理はプロンプト処理時に一度実施する。逐次生成の各ステップでK-meansを繰り返すわけではない。追加費用は、層別の類似度を計算する処理、群分け、層ごとに異なる保持枠を管理する処理である。圧縮器自身のトークン選択費用は残るため、提案方式が全ての追い出し計算を不要にするわけではない。

### 削減率pと失敗条件

pを小さくすると低感度群からより多くの保持枠を回収できるが、これらの層が本当に不要という意味ではない。著者らは多くの条件でp=0.3～0.4が妥当だったと報告する。Mistral-7BのSAMSUM、総保持枠を系列長の20%に固定した感度実験では、p=0.4のROUGE-Lが37.69、p=0.3が37.26だった一方、p=0.1では15.7へ急落した。低感度群にも最低限の履歴が必要であり、強い圧縮ほど必ず良いわけではない。

三群という設計も厳密な最適化の証明ではない。著者らは先頭・末尾の特別な層と、それ以外の重要・低感度の二群を区別する実用的な近似として採用した。層ごとに異なるタスク感度やモデル依存性があるため、群の境界やpを固定すれば全モデルに最適になるという主張ではない。

## 評価

### 実験条件と比較対象

| 観点 | 原著で確認した条件 |
|---|---|
| モデル | OPT-6.7B、Falcon-7B、Mistral-7B、Llama2-7B-32K、GPT-NeoX-20B、Mixtral-8×7B、Llama2-70B |
| 課題 | CNN/Daily Mail、XSUM、SAMSUM、NarrativeQA、TriviaQA |
| 入力の代表長 | 短い要約は平均約2,000、SAMSUM約6,258、TriviaQA約8,209、NarrativeQA約18,409トークン |
| 品質指標 | 要約のROUGE-2／ROUGE-L、質問応答のF1 |
| 系列方向の比較 | H2O、Sliding Window、StreamingLLM。課題ごとに良好な方式を選んで比較 |
| 実機 | AWS p4d.24xlarge、A100 40GBを8基、GPU間NVLink接続 |
| メモリ | モデル重みを除いたトークン生成時のキャッシュ関連メモリをプロファイラで計測 |
| 処理能力 | バッチを変えたトークン毎秒、メモリ不足による実行不能も記録 |

実験は、同じトークン保持率における品質比較と、同程度の品質を得るための必要保持率の比較を区別している。さらに、完全保持方式と、既存の系列方向だけの圧縮方式は異なる比較対象である。以下の削減率や倍率を混ぜて一つの普遍的な改善率として扱わない。

### 同程度の品質で必要なキャッシュ量

| モデル／課題 | 完全保持の品質 | 提案方式：品質／保持率 | 系列方向だけ：品質／保持率 |
|---|---:|---:|---:|
| Mistral-7B／SAMSUM | 43.53 | 41.05／20% | 40.00／30%（Sliding Window） |
| GPT-NeoX-20B／XSUM | 0.09 | 0.09／20% | 0.08／60%（H2O） |
| Llama2-70B／XSUM | 0.18 | 0.17／30% | 0.19／40%（StreamingLLM） |

この表は原著の表2に対応する。例えばGPT-NeoX-20BのXSUMでは、H2Oの60%に対して20%の保持枠でほぼ同程度の値を得ている。ただしMistralの41.05は完全保持の43.53と同一ではない。またLlama2-70Bでは比較方式の0.19が提案方式の0.17より高く、提案方式がすべての品質指標で上回るという解釈は誤りである。保持量と品質の交換条件を比較する必要がある。

原著の図4は、この三条件でモデル重みを除いたトークン生成時のメモリを計測し、完全保持に対して70～80%、選択した系列方向の比較方式に対して25～66%の削減を示す。これはGPU全体の占有メモリが同じ割合で減るという意味ではない。重みや実行時の他の領域は別に存在する。

### 同一バッチの生成処理能力

| モデル／入力＋生成長 | バッチ | SqueezeAttention | 完全保持 | 解釈 |
|---|---:|---:|---:|---|
| Mistral-7B／512＋1,024 | 32 | 496.5 token/s | 254.0 token/s | 同一バッチで約1.95倍 |
| Mistral-7B／512＋1,024 | 64 | 682.7 token/s | 304.8 token/s | 同一バッチで約2.24倍 |
| Mistral-7B／512＋1,024 | 224 | 892.5 token/s | メモリ不足 | 比較対象は実行不能 |
| Llama2-70B／256＋512 | 32 | 116.2 token/s | 84.8 token/s | 同一バッチで約1.37倍 |
| Llama2-70B／256＋512 | 64 | 170.7 token/s | メモリ不足 | 比較対象は実行不能 |

Mistral-7Bは保持枠20%、Llama2-70Bは30%の設定である。原著表3の数値を用い、実行不能な条件を無限大の高速化倍率として扱わない。小さいバッチでは差が小さく、Mistralのバッチ1では提案方式20.5 token/sに対して完全保持20.9 token/sと、むしろ僅かに低い。キャッシュ節約による利得は、大きいバッチを成立させたり、メモリ帯域や保持量の制約が強い条件で大きくなる。

### 追加計算費用と感度

層別重要度を測る余弦類似度計算と三群のK-meansは、プロンプト処理時の一回の費用である。Mistral-7B、最大8,000トークンのプロンプトをA100 40GB一基で処理した原著表4では、プリフィル時間が0.636秒から0.676秒へ増え、6.3%の追加時間となった。付録表5は、32層分の余弦類似度計算と群分けの合計を約0.02276秒と分解する。測定対象と集計範囲が異なるため、この内訳とプリフィル全体の差を同一値として扱わない。

pの感度は単調ではない。原著付録表6のSAMSUMでは、p=0.4で37.69、p=0.3で37.26、p=0.2で34.01、p=0.1で15.7となり、p=1.0の9.07とも異なる。ここでp=1.0は層間再配分をしない状態であり、圧縮そのものをしない完全保持とは違う。層別再配分の有効性は、比較する系列方向の圧縮器と保持率を固定して評価すべきである。

## 限界と適用範囲

提案方式は、組み合わせる系列方向の追い出し方式が、対象モデルと課題に対して一定の品質を維持できることを前提にしている。H2Oや滑動窓のトークン選択が課題に不適合なら、保持枠を層間で再配分しても重要な過去情報を回復できない。層別重要度の余弦類似度も因果的な品質感度ではなく、入力の表現変化を利用した経験的な代理指標にとどまる。

群分けとpの調整にはモデル・課題依存性がある。低感度群の保持枠を過度に削ると、付録のSAMSUM感度実験のように品質が急落する。測定をプロンプト処理時に一度だけ行うため、長い生成の途中で必要な注意情報の性質が変わっても、その変化に応じて予算を再最適化する仕組みは示されていない。プリフィルが主な費用となる短い要求では、6.3%の一回費用が無視できない場合もある。

評価は七モデル、五課題、特定のGPU構成と保持率に基づく。メモリ節約を実機で測ったことは、消費電力や運用費用の同率削減を直接示すものではない。8基のA100での処理能力を、単一の小型GPUやCPU・SSDへの退避環境へそのまま外挿できない。また実験は逐次生成の処理能力を中心とし、複雑な要求到着分布、長時間運用でのキャッシュ断片化、異なるハードウェア間転送、巨大な混合専門家モデルの実運用まで包括的に検証したものではない。
