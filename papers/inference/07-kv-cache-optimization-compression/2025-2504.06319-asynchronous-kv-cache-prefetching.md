# Accelerating LLM Inference Throughput via Asynchronous KV Cache Prefetching

> attentionが現在のKV blockを計算している間に、次に使うKV blockをHBMからGPUのL2 cacheへ先読みし、decode中のHBM待ちを減らすHopper向け最適化。

## 概要

本研究は、KV cacheの容量を減らすのではなく、**HBMにあるKVをattention kernelが使う少し前にGPU L2 cacheへ運んでおく**ことでdecode throughputを高める。

vLLMのXFormers backendをprofileすると、KV blockがL2に無い場合にHBMから届くまでGPUの計算threadが待たされる時間が大きい。Llama2-7Bの代表条件ではL2 hit rateが0.06%で、1命令あたり27.68 cycleのうち21.34 cycleが長いmemory待ちに費やされていた。

そこで現在のK/V blockを使ってattention計算している間に、次に必要になるblockを非同期にL2へprefetchする。KVを削除・量子化・CPUへoffloadする手法ではなく、**GPU内部のHBM→L2 data movementを現在のattention計算と重ねるlosslessなmemory-access optimization**である。

## 手法

### 1. 次のKV blockを現在の計算中にL2へ先読みする

vLLMではKV cacheが固定token数のblockへ分割され、XFormers attentionはblockを順番に読みながら計算する。

提案手法は、GPUが現在のK blockで `Q·K^T` を計算している間に、次に使うK blockをL2 cacheへprefetchする。V側でも同様に、現在blockの計算中に次V blockを先読みする。

次のblockへ進んだ時点でL2にdataがあれば、HBMまで取りに行く待ち時間を減らせる。

### 2. Hopperの非同期L2 prefetch命令を使う

実装はPTXの `cp.async.bulk.prefetch.L2` を利用する。これは指定したmemory addressのdataを、現在の計算を止めずにL2へ読み始める命令で、Compute Capability 9.0以降、主にHopper世代GPUを前提とする。

prefetch自体を独立した大きなstageにせず、attention kernel内部へ差し込むことで、現在の計算と次blockのHBM readを同時に進める。

### 3. L2容量を超えるほど先読みしない

prefetchしたKV blockが使う前にL2から追い出されれば効果がなくなるため、batch size、KV head数、block sizeに対してL2容量が上限になる。

FP16 Llama2-7Bの例では1 blockが4KB、1回に処理するK/V block群がbatch=1あたり約512KBで、60MB L2なら理論上およそbatch 120まで全blockを保持できると分析している。

### 4. MHA / GQAで効果が変わる

MHAはquery headごとに独立したKV headを読むためKV load量が多く、prefetchで隠せるHBM readも多い。

一方GQAでは複数query headが同じKVを共有するため、もともとKV再利用が多く、追加prefetchで改善できる余地が小さくなる。

このためQwen2.5-7BのようにKV head数が少ない強いGQA構成では、FlashAttention-3より速くならない条件もある。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA H20 96GB × 最大8 |
| L2 / HBM | 60MB L2、96GB HBM、4.0TB/s |
| CPU | Intel Xeon Platinum 8469C ×4、計192 cores |
| Model | Llama2-7B、Llama3-8B、Qwen2.5-7B / 14B |
| Precision | FP16 |
| Runtime | vLLM 0.7.1 + XFormers backend |
| Baseline | native XFormers、FlashAttention-3 |
| Input length | 512 tokens |
| Output length | 512〜8192 tokens |
| Batch | 1〜128 |

### Attention kernel

batch=64、output=4096の条件では、native XFormersに対するattention kernel speedupは以下。

- Llama2-7B: 1.84×
- Llama3-8B: 1.89×
- Qwen2.5-7B: 2.15×
- Qwen2.5-14B: 1.89×

L2 hit rateはLlama2-7Bで0.06%→43.70%、Llama3-8Bで38.35%→73.01%、Qwen2.5-7Bで55.90%→82.66%へ上がった。GPUがHBMからdataを待つ時間も大幅に減少している。

### End-to-end

single H20ではnative XFormers比の最大throughput改善が、Llama2-7B 51%、Llama3-8B 57%、Qwen2.5-7B 41%、Qwen2.5-14B 41%。batchとoutput lengthが大きいほどKV block loadが増えるため利得が大きくなる傾向を示す。

FlashAttention-3比ではLlama2-7Bで最大110%、Llama3-8Bで15%、Qwen2.5-14Bで7%高い一方、Qwen2.5-7Bでは2〜5%低下する条件がある。

2 / 4 / 8 GPUのtensor parallel評価ではnative XFormers比でLlama3-8Bが4〜59%、Qwen2.5-14Bが4〜76%改善した。ただしGPU数が増えるほど各GPUが担当するattention head数が減るため、1台あたりで先読みできるKV read量も減り、利得は縮小する。

## 既存研究との差

### FlashAttentionとの違い

FlashAttention系はtilingやkernel fusionでHBMへのaccess回数を減らす。本研究は、それでも必要なKV readについて、**必要になる前にL2へ運んでHBM latencyを現在の計算の裏へ隠す**。

したがってKV表現やattention semanticsは変更せず、memory hierarchy上のload timingを変える手法である。

### KV compression / evictionとの違い

KVを削除・量子化・低rank化してtraffic自体を減らすのではない。全KVを保持したままaccess latencyを隠すため、品質低下を伴わず、原理上はcompression系と併用できる。

### PRESERVEとの違い

PRESERVEはmulti-GPU execution中のAllreduce時間を利用してmodel weightやKVをL2へprefetchする。一方本研究はattention kernel内部で、**現在のKV block計算中に次blockを先読みする**ため、single GPUでも利用できる。

## 限界

- `cp.async.bulk.prefetch.L2` に依存するため、主にHopper以降のGPUが必要。
- L2容量を超えるbatchではprefetched blockが使う前に追い出されやすくなり、利得が頭打ちになる。
- GQAでKV head数が少ないほど元々のKV再利用が高く、改善余地が小さい。Qwen2.5-7BではFlashAttention-3より遅い条件もある。
- tensor parallelismでGPU数を増やすと1 GPUあたりのattention headが減り、prefetch可能なI/O量が減る。
- 評価はvLLM 0.7.1のXFormers backendを中心としており、他attention backend・新しいruntimeへの一般化には実装調整が必要。

## 一般的な実装上の含意

KV cache最適化では容量だけでなく、**GPU内部のcache localityとload timing**も大きな余地になる。decode attentionのaccess順序が予測可能なら、現在の計算中に次blockのHBM readを始めることで、同じKV容量でもthroughputを上げられる。

またMHA / GQA / MLAの違いでKV access量と再利用率が大きく変わるため、どれだけ先のblockまでprefetchするか、L2をどこまで使うかをmodel architectureごとに調整する必要がある。
