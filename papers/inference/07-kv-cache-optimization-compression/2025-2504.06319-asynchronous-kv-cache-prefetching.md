# Accelerating LLM Inference Throughput via Asynchronous KV Cache Prefetching

> 非同期KV先読みは、現在の注意ブロック計算中に次のKVをHBMからL2へ運び、Hopper GPUのメモリ待ちを隠して、注意カーネルとE2Eデコードを速める。

## 概要

本研究は、KV キャッシュの容量を減らすのではなく、**HBMにあるKVを注意機構 カーネルが使う少し前にGPU L2 キャッシュへ運んでおく**ことでデコード スループットを高める。

vLLMのXFormers バックエンドをプロファイルすると、KV ブロックがL2に無い場合にHBMから届くまでGPUの計算スレッドが待たされる時間が大きい。Llama2-7Bの代表条件ではL2 ヒット 率が0.06%で、1命令あたり27.68 サイクルのうち21.34 サイクルが長いメモリ待ちに費やされていた。

そこで現在のK/V ブロックを使って注意機構計算している間に、次に必要になるブロックを非同期にL2へプリフェッチする。KVを削除・量子化・CPUへオフロードする手法ではなく、**GPU内部のHBM→L2 データ 移動を現在の注意機構計算と重ねる無損失なメモリ-アクセス optimization**である。

H20上の注意カーネル評価では標準XFormers比1.84〜2.15倍、Llama2-7BのL2ヒット率を0.06%から43.70%へ改善した。単一GPUのE2Eスループットもモデル別に最大41〜57%向上したが、Qwen2.5-7BではFlashAttention-3を下回る条件がある。
## 手法

### 1. 次のKV blockを現在の計算中にL2へ先読みする

vLLMではKV キャッシュが固定トークン数のブロックへ分割され、XFormers 注意機構はブロックを順番に読みながら計算する。

提案手法は、GPUが現在のK ブロックで `Q·K^T` を計算している間に、次に使うK ブロックをL2 キャッシュへプリフェッチする。V側でも同様に、現在ブロックの計算中に次V ブロックを先読みする。

次のブロックへ進んだ時点でL2にデータがあれば、HBMまで取りに行く待ち時間を減らせる。

### 2. Hopperの非同期L2 prefetch命令を使う

実装はPTXの `cp.async.bulk.prefetch.L2` を利用する。これは指定したメモリ アドレスのデータを、現在の計算を止めずにL2へ読み始める命令で、計算 対応能力 9.0以降、主にHopper世代GPUを前提とする。

プリフェッチ自体を独立した大きな段階にせず、注意機構 カーネル内部へ差し込むことで、現在の計算と次ブロックのHBM 読み出すを同時に進める。

### 3. L2容量を超えるほど先読みしない

プリフェッチしたKV ブロックが使う前にL2から追い出されれば効果がなくなるため、バッチサイズ、KV ヘッド数、ブロック sizeに対してL2容量が上限になる。

FP16 Llama2-7Bの例では1 ブロックが4KB、1回に処理するK/V ブロック群がバッチ=1あたり約512KBで、60MB L2なら理論上およそバッチ 120まで全ブロックを保持できると分析している。

### 4. MHA / GQAで効果が変わる

MHAはクエリ ヘッドごとに独立したKV ヘッドを読むためKV 読み込む量が多く、プリフェッチで隠せるHBM 読み出すも多い。

一方GQAでは複数クエリ ヘッドが同じKVを共有するため、もともとKV再利用が多く、追加プリフェッチで改善できる余地が小さくなる。

このためQwen2.5-7BのようにKV ヘッド数が少ない強いGQA構成では、FlashAttention-3より速くならない条件もある。

## 評価

### 条件

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA H20 96GB × 最大8 |
| L2 / HBM | 60MB L2、96GB HBM、4.0TB/s |
| CPU | Intel Xeon Platinum 8469C ×4、計192 cores |
| Model | Llama2-7B、Llama3-8B、Qwen2.5-7B / 14B |
| Precision | FP16 |
| Runtime | vLLM 0.7.1 + XFormers backend |
| Baseline | native XFormers、FlashAttention-3 |
| Input length | 512 tokens |
| Output length | 512〜8192 tokens |
| Batch | 1〜128 |

### Attention kernel

バッチ=64、出力=4096の条件では、標準 XFormersに対する注意機構 カーネル 高速化倍率は以下。

- Llama2-7B: 1.84×
- Llama3-8B: 1.89×
- Qwen2.5-7B: 2.15×
- Qwen2.5-14B: 1.89×

L2 ヒット 率はLlama2-7Bで0.06%→43.70%、Llama3-8Bで38.35%→73.01%、Qwen2.5-7Bで55.90%→82.66%へ上がった。GPUがHBMからデータを待つ時間も大幅に減少している。

### End-to-end

単一 H20では標準 XFormers比の最大スループット改善が、Llama2-7B 51%、Llama3-8B 57%、Qwen2.5-7B 41%、Qwen2.5-14B 41%。バッチと出力 長さが大きいほどKV ブロック 読み込むが増えるため利得が大きくなる傾向を示す。

FlashAttention-3比ではLlama2-7Bで最大110%、Llama3-8Bで15%、Qwen2.5-14Bで7%高い一方、Qwen2.5-7Bでは2〜5%低下する条件がある。

2 / 4 / 8 GPUのテンソル 並列評価では標準 XFormers比でLlama3-8Bが4〜59%、Qwen2.5-14Bが4〜76%改善した。ただしGPU数が増えるほど各GPUが担当する注意機構 ヘッド数が減るため、1台あたりで先読みできるKV 読み出す量も減り、利得は縮小する。

## 既存研究との差

### FlashAttentionとの違い

FlashAttention系はtilingやカーネル 融合でHBMへのアクセス回数を減らす。本研究は、それでも必要なKV 読み出すについて、**必要になる前にL2へ運んでHBM 遅延を現在の計算の裏へ隠す**。

したがってKV表現や注意機構 意味は変更せず、メモリ 階層上の読み込む タイミングを変える手法である。

### KV compression / evictionとの違い

KVを削除・量子化・低ランク化して通信量自体を減らすのではない。全KVを保持したままアクセス 遅延を隠すため、品質低下を伴わず、原理上は圧縮系と併用できる。

### PRESERVEとの違い

保持するはmulti-GPU 実行中のAllreduce時間を利用してモデル重みやKVをL2へプリフェッチする。一方本研究は注意機構 カーネル内部で、**現在のKV ブロック計算中に次ブロックを先読みする**ため、単一 GPUでも利用できる。

## 限界

- `cp.async.bulk.prefetch.L2` に依存するため、主にHopper以降のGPUが必要。
- L2容量を超えるバッチでは先読み済み ブロックが使う前に追い出されやすくなり、利得が頭打ちになる。
- GQAでKV ヘッド数が少ないほど元々のKV再利用が高く、改善余地が小さい。Qwen2.5-7BではFlashAttention-3より遅い条件もある。
- テンソル 並列化でGPU数を増やすと1 GPUあたりの注意機構 ヘッドが減り、プリフェッチ可能なI/O量が減る。
- 評価はvLLM 0.7.1のXFormers バックエンドを中心としており、他注意機構 バックエンド・新しい実行時への一般化には実装調整が必要。

## 一般的な実装上の含意

KV キャッシュ最適化では容量だけでなく、**GPU内部のキャッシュ 局所性と読み込む タイミング**も大きな余地になる。デコード 注意機構のアクセス順序が予測可能なら、現在の計算中に次ブロックのHBM 読み出すを始めることで、同じKV容量でもスループットを上げられる。

またMHA / GQA / MLAの違いでKV アクセス量と再利用率が大きく変わるため、どれだけ先のブロックまでプリフェッチするか、L2をどこまで使うかをモデル 構成ごとに調整する必要がある。
