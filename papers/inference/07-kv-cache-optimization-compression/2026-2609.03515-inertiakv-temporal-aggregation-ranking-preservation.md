# What Matters for Aggressive Decoding-Time KV Eviction? Temporal Aggregation and Ranking Preservation

> KVの重要度を毎tokenで一から計算し直さず、過去のattention傾向を滑らかに蓄積して重要tokenの順位を数step使い回すことで、90%級のKV圧縮でもdecode時の管理costを減らす手法。

## 概要

本研究は、decode時にどの過去tokenのKVを残すかを決めるとき、**「重要度scoreを何で作るか」以上に、「過去数stepのscoreをどうまとめるか」「一度決めた重要token順位をどれくらい使い回すか」**が品質と速度へ大きく効くことを示す。

毎decode stepで全tokenの重要度を細かく再計算すると、その管理処理自体が重い。逆に古いrankingを長く固定しすぎると、attention需要の変化へ追従できない。

InertiaKVは、attention scoreを時間方向に滑らかに蓄積し、重要tokenの順位を安定させたうえで、ranking更新を数stepおきに減らす。

## 手法

### 1. 1stepのattentionだけで重要tokenを決めない

各decode stepで得られるattention scoreは揺れが大きく、1stepだけを見るとKVを残す／捨てる判断も頻繁に変わる。

そこで指数移動平均（EMA）を使い、最近のscoreを強く、古いscoreを弱く反映しながら累積する。

これにより、**複数stepにわたって継続的に重要なtokenを上位へ残しやすくする**。

### 2. `InertiaKV-Lazy`：重要token順位の更新を数stepおきにする

毎step全tokenを再評価する代わりに、一定間隔だけrankingを更新する。

例えばLazy4では、4 decode stepに1回だけ重要度を再計算し、その間の3 stepは前回のrankingを使う。

これにより、KV eviction判断のためのscore計算・sorting・metadata更新を減らせる。

### 3. `Score-Free`：最初に作ったrankingをそのまま使う極端な設定

最初のdecode stepで重要token rankingを作った後、それ以降はscore自体を更新しない設定も評価する。

これは実用上の推奨設定というより、**「重要tokenの順位はどれほど時間的に安定しているのか」を調べる実験**である。

LongBenchでは、この極端な設定でもfull-refreshとの差が小さい条件があり、毎stepの細かな再評価が必ずしも必要ではないことを示した。

### 4. Score関数そのものよりrankingの安定性を重視する

複数のKV重要度scoreを比較すると、どのscore式を使うかよりも、時間方向に情報をまとめてrankingを安定させるかどうかの方が結果へ強く効く。

したがってこの論文の主張は「新しい最強score関数」ではなく、**KV eviction systemではranking更新頻度そのものを最適化対象にすべき**という点にある。

## 評価

Llama-3.1-8B、Qwen2.5-7B、Llama-3.3-70BなどをLongBench、LongBench-v2、RULERで評価し、主条件として90%圧縮を用いる。

- Lazy4は64K contextでfull-refresh版に対し、Llamaで **1.34倍**、Qwenで **1.46倍** のdecode throughputを報告。
- Score-Freeは初回ranking作成後のscore更新を省くが、LongBench平均ではfull-refreshとの差がほぼゼロ。
- Qwen3-30B-A3BによるMoE stress checkも行うが、MoEを全面的に評価した研究ではない。

速度改善はKV容量そのものの削減だけでなく、**毎step行っていた重要度再計算を減らしたこと**からも得られる。

## スコープと制約

- 対象はKV tokenの保持・evictionであり、MoE expert weightのcacheやresidency管理ではない。
- CPU offload、SSD / NVMe offload、HBF、CXL memoryは評価していない。
- MoE評価は限定的で、主な実験はdense/open-weight backboneを中心とする。
- rankingが急に変わるtaskでは、更新間隔を長くしすぎると必要KVを捨てる可能性がある。
- 90%圧縮という強い設定で良好でも、最適なrefresh intervalはmodel・context・taskで変わり得る。

## 実装上の含意

KV evictionでは、tokenごとのimportance score精度だけを追うと、score更新自体のcompute / memory overheadを見落としやすい。

serving engineでは、**重要度を時間方向に蓄積するstate、rankingを何stepおきに更新するか、KVを実際に削除する処理**を分離し、品質を保てる範囲でranking更新頻度を下げる設計が有効になり得る。
