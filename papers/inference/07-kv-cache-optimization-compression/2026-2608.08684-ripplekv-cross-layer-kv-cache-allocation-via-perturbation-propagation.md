## 概要

KVキャッシュを圧縮する際には「各層でどのトークンを残すか」と「各層に何個残すか」という異なる問題がある。SnapKVのような方式はprompt末尾のattentionから重要なトークンを選べるが、全層へ均等な予算を配ると、出力に強く影響する層の情報まで失う恐れがある。逆に、圧縮に強い層へ余分なメモリを割り当てても品質改善にはつながりにくい。

RippleKVは、後者の**層間予算配分**を、最終的なモデル予測への影響で決める方式である。各層のValueキャッシュだけに制御した摂動を加え、以降のTransformer層を通して出力分布がどれだけ変わるかを測る。変化が大きい層を敏感な層として多めに保持し、変化の小さい層は強く圧縮する。トークンの重要度判定自体は既存方式のSnapKVを維持するため、改善が層予算配分に由来するかを比較しやすい。

論文では、層の深さと実際の圧縮損傷の相関は弱く、敏感な層が中間に現れるなど単調な配分では対応しにくいことを示した。オフラインの校正が必要だが、推論時に摂動試験や追加のモデル実行は行わない。この性質は、リクエストごとに試行生成を要する未来query型のKV選別方式とは異なる。

## 問題設定

デコーダ専用Transformerの層数をL、入力長をT、層ℓで保持する位置集合をSℓとする。保持したKV数bℓ=|Sℓ|を各層へ割り当て、全層の予算和Σbℓ=Bを固定する。Bを増やさずに最終生成品質を最大限残すのが目的である。元のトークン選択則を変えずに層予算だけを調整するため、RippleKVを用いた改善をKV圧縮アルゴリズム全体の別方式へすり替えて比較しない。

従来のPyramidKVは層深度に応じたピラミッド状の配分を行う。DynamicKVなどはattention統計や表現の変化を使う。しかし層内の局所的な差が大きいことと、その変化が最終logitに大きな損傷を与えることは同じではない。後続層が補償する可能性があるからである。RippleKVは、この伝播を出力分布の変化で直接観測する。

## 手法：オフライン感度計測から層予算へ

### 1. 圧縮損傷と層位置の関係を検証

著者らはまず、他の層を非圧縮に保ったまま層ℓだけを圧縮し、full-cache時の出力分布と圧縮後の出力分布のKL divergenceを校正例で平均した量Dℓを定義する（式1）。Dℓが大きければ、その層の圧縮によって最終予測が強く変わる。Llama-3.1-8Bの32層では平均損傷が0.0030〜0.0524と17.7倍に広がり、最大値は中間層に現れた。層番号と損傷の平均絶対Spearman相関は0.359で、単純な深度だけでは十分に予測できない。

ただしDℓは実際に特定の圧縮操作を各層へ適用して求めるため、異なる圧縮方式へそのまま転用できる普遍的な指標ではない。RippleKVでは、圧縮を行う代わりにValueキャッシュを摂動させ、圧縮方式に依存しにくい感度を取得する。

### 2. Valueだけを変え、最終出力を観測

小さな校正集合Dcalの各例を、KVを作るprefixと評価windowに分ける。まず完全なKVで評価windowの予測分布Pを記録する。次に圧縮対象の各層ℓについて、**その層のValueだけ**に摂動を加え、Keyと他層のKVは固定したまま同じ評価windowを実行して分布Qℓを得る。これにより対象層のattention重みそのものはKeyを通じて変えず、集約されるValueの内容が後続層へ伝わる影響を測れる。

摂動は各Valueベクトルvへ、標準正規ノイズεにそのベクトルのノルムと強度αを掛けた項を加える方式（式6）である。Valueの大きさに合わせるため、活性化スケールが異なる層でも一律の絶対ノイズを加えるより比較しやすい。既存圧縮法が保護するトークンは摂動対象から外す。評価windowの各位置でKL(P||Qℓ)を求め、その位置平均、さらに校正例平均をとって層感度sℓとする（式7・8）。勾配計算や重み更新は不要である。

この感度は、対象層だけの局所的な表現誤差ではなく、残りのTransformer層を通過した**最終予測分布の変化**である。圧縮損傷Dℓとの平均絶対Spearman相関は0.799、範囲0.723〜0.857で、層番号の0.359より高い（Table 1）。相関の改善は校正指標の妥当性を示すが、これだけで実運用のスループット改善を保証するわけではない。

### 3. 正規化と指数写像による層配分

各層のsℓを最小値sminと最大値smaxで0〜1へ正規化し、ŝℓ=(sℓ−smin)/(smax−smin)とする。全層が同一感度なら一律配分へ戻す。次にw̃ℓ=r^(ŝℓ)で正の重みへ写像する（式9・10）。r≥1は敏感な層と鈍感な層の配分比を決め、r=1では均等、rを増やすと感度の高い層へ多く配る。

極端な配分を避けるため、重みを[1/γ,γ]の範囲へクリップし、圧縮対象層全体の平均が1になるよう正規化する。最終的にbℓ≈round(B/|A|×wℓ)で層予算へ変換する（式11・12）。この構成では全体予算を変えずに相対配分だけを変更でき、校正で得た感度プロファイルをB=10%、20%、30%など別の総予算にも再利用できる。実装では整数丸めに伴う微小な差を総予算制約に合わせて扱う必要がある。

### 4. オンライン適用

推論中は計算済みのbℓを各層へ渡し、SnapKVの元の観測窓に基づくトークン採点と保持処理をそのまま実施する。したがってValue摂動を毎リクエスト繰り返さず、モデル推論回数も増やさない。校正のコストはモデルごとに一度発生するが、重み・対象アーキテクチャ・圧縮対象層が変われば再校正が必要になると考えられる。校正がタスク分布に依存する可能性は、固定プロファイル運用の限界である。

## 主要結果：品質

| モデル・保持率 | 強い比較方式 | RippleKV | 差・読み方 |
|---|---:|---:|---|
| Llama-3.1-8B、10%、LongBench平均 | SnapKV 34.24 | 35.07 | +0.83点 |
| Llama-3.1-8B、20% | SnapKV 39.93 | 40.35 | +0.42点 |
| Llama-3.1-8B、30% | SnapKV 42.26 | 42.97 | +0.71点 |
| Qwen2.5-7B、10% | SnapKV 34.14 | 34.42 | +0.28点 |
| Mistral-7B、10% | SnapKV 32.54 | 33.19 | +0.65点 |
| Llama-3.1-8B、Full Cache | — | 46.18 | 圧縮なしの参照値でありRippleKVの圧縮結果ではない |

Llamaの保持10%ではFull Cache 46.18に対しRippleKV 35.07であり、改善しても大きな品質差が残る。保持30%でも42.97で、全保持との差は3.21点である。著者らは3モデル・5つの圧縮条件で平均スコア首位と述べるが、個別タスクすべてで勝つわけではない。例えばLlamaの保持10%のHotpotQAはSnapKV 44.74に対しRippleKV 44.37で、局所的には悪化する。Few-shotでも一定の優位を示さない条件がある。

Qwenの複数文書QAカテゴリ平均ではPyramidKV 20.81からRippleKV 25.61、Mistralの合成課題カテゴリでは26.73から31.03へ改善したと原著は報告する。これはカテゴリ内平均であり、上表の16タスク総平均と混同しない。総平均の差が小さい一方、長文証拠を保持すべき特定タスク群で層配分が効いている可能性を示す。

## 速度・メモリ・感度実験

| 指標・文脈 | Full Cache | SnapKV / PyramidKV | RippleKV | 解釈 |
|---|---:|---:|---:|---|
| 8K、end-to-end latency | 7.58秒 | 6.84 / 6.88秒 | 6.67秒 | 既存圧縮方式とほぼ同等 |
| 8K、decode throughput | 37.38 tok/s | 42.37 / 42.09 | 43.48 tok/s | 少量改善、追加のオンライン校正なし |
| 128K、end-to-end latency | 59.46秒 | 43.87 / 43.87秒 | 43.02秒 | full-cache比は大きいが圧縮方式同士の差は小さい |
| 128K、decode throughput | 11.85 tok/s | 40.92 / 42.51 | 42.99 tok/s | throughputとend-to-end遅延を分けて評価 |
| 128K、peak memory | 45.53 GiB | 個別数値は本文未掲示 | 31.13 GiB | Full Cache比31.6%削減 |
| 256K、peak memory | 76.09 GiB | 個別数値は本文未掲示 | 47.29 GiB | Full Cache比37.8%削減 |

速度面の利点は主としてKV圧縮自体に由来する。RippleKVがSnapKVやPyramidKVを劇的に高速化したわけではない。A100での8Kの43.48 tok/sと128Kの42.99 tok/sは、同一の評価条件内の値としてのみ解釈すべきであり、任意のバッチ数・GPU構成・実サービングQPSを示すものではない。Figure 3のpeak memoryも圧縮方式間ではほぼ同等で、層間の再配分がメモリ総量を増やしていないことが主な確認点である。

除去実験Table 4では、層予算を均等に戻すとCodeカテゴリが50.58から47.16へ3.42点、Syntheticが32.25から30.00へ2.25点、Multi-Doc QAが30.89から29.52へ1.37点低下する。最終出力ではなく層内の局所反応で感度を測ると、Codeは47.40、Syntheticは30.25、Multi-Doc QAは29.35へ低下した。層間の非均等配分だけでなく、**最終出力への伝播を測ること**にも寄与がある。ただしFew-shotは均等配分の55.45が完全版55.37を0.08点上回り、全カテゴリで完全版が勝つわけではない。

配分比rの感度試験では、r=1.25、1.50、1.75のLongBench平均が34.67、35.07、34.89だった。最大差0.41点で、標準の1.50がこの範囲では最良である。ただし別モデル・別校正分布で常に1.50が最適と保証するものではない。

## 既存研究との差

PyramidKVの層深度に基づくピラミッド配分と違い、RippleKVは実際の出力分布の変化を層別に測定する。DynamicKVなどのattention統計に基づく層割当とも異なり、後続層での増幅・吸収を含む最終的な損傷の代理指標を使う。SnapKVとは競合するトークン採点器ではなく、SnapKVの保持数を層別に調整する外側の配分機構として組み合わせられる。

本方式のValue摂動は、キャッシュ中のValueを低ビット化する量子化とは別の意味を持つ。校正中に人工ノイズを加えるのは層の脆弱性を測るためであり、推論時にノイズを注入して圧縮するわけではない。ここを取り違えると、品質・実行時間の評価を誤る。

## 限界と実用上の判断

一次論文が示すのは3つの7〜8B級モデルとLongBench、単一A100環境での結果である。大規模MoE、分散推論、動的バッチ、他のトークン選別器との全組合せについて同じ改善が出ると断定できない。校正時に一度求めた感度を異なる入力分布やモデル更新後にも再利用できるか、長期の運用で感度がずれるかも独立に検証が必要となる。

層ごとのValueノイズで測るKLは、実際のKV削除損傷と強く相関するが同一ではない。敏感な層に大きな予算を割り当てても、個別タスクやfew-shotでは悪化が起こり得る。また総予算Bが小さい場合、Full Cacheからの品質低下はなお大きい。性能向上の要因を示すTable 4はカテゴリ平均であり、各サンプルの最悪ケースや統計的な信頼区間を提供していない。

サーベイでは「層別感度をオフラインで測ってKV配分へ反映する、既存圧縮器と組み合わせ可能な方式」として扱うのが妥当である。新たなオンライン推論を要求しない点はサービングでの採用障壁を下げるが、モデル・量子化・ワークロードを変えるたびの校正費用とプロファイルの汎化性は別途測定すべきである。
