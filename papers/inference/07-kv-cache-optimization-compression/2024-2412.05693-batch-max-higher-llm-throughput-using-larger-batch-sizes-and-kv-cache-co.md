# Batch-Max：プリフィル中のKV削除でバッチを拡大する推論スループット最適化

## 書誌情報

Michael R. Metel、Boxing Chen、Mehdi Rezagholizadehによる論文。初版は2024年12月7日、照合した本文は2025年7月3日のarXiv v3（cs.CL）。ES-FoMo III（ICML 2025併設ワークショップ）で発表された5ページの論文である。ここで扱う「圧縮」はKVペアの低ビット量子化ではなく、注意重みから不要と判断した過去トークンのKVペアを削除する方式を指す。

## 概要

既存のKVキャッシュ削除は、長い入力プロンプトをすべて処理した後、生成段階のKVメモリや帯域を減らすことに主眼がある。これは固定バッチでのデコードには合理的だが、GPUメモリが限られ、入力トークン数が生成トークン数より長い状況では問題が残る。プリフィルの全KVを一度保持しなければならないため、生成段階では大幅に圧縮していても、**最初のプリフィル時のピークメモリがバッチサイズを制限する**。生成段階で空くメモリを、より大きなバッチを同時実行するために利用できない。

Batch-Max（BM）はプリフィル中もKVキャッシュを一定容量以下に保つ。最初のブロックを処理した後、一定数のKVペアを削除してから次の入力ブロックを処理し、デコード中も同じ上限を維持する。削除候補は過去の累積注意重みを単純に使わず、そのKVペアが存在した期間で正規化した平均注意重みで選ぶ。長入力の要約・読解・数学問題を使ったGPU実験では、著者がデコード専用削除のスループット上限を近似するために構成した極端な方式（ED）より、平均44.0%高いスループットを報告した。品質はフルKVモデル（FKV）比で平均2.2%低下したと述べる（原著Abstract、§4）。

重要なのは、この44.0%が**同じバッチサイズでの一要求の高速化**ではなく、同一GPUメモリ制約下でバッチを増やした結果の総トークン/秒の比較であることだ。バッチを固定できる場合や短入力では、プリフィルを分割する追加費用が逆効果になり得る。

## 問題設定と既存方式の限界

LLMの推論には、入力全体のキー・バリューを生成するプリフィルと、履歴KVを参照してトークンを一つずつ出力するデコードがある。プリフィルは入力トークン間の演算を並列化できる一方、デコードではKV読み出しの帯域がボトルネックになりやすい。H2O、SnapKV、Scissorhands、FastGenなどは後者のKV削除・保持を工夫するが、プリフィルがピークメモリを決めると、生成段階の省メモリ化だけでは同時要求数を増やせない。

各サンプルの入力長を `s_j`、バッチ内の最大長を `s = max_j s_j`、1サンプル・1注意ヘッドあたりの保持KVペア上限を `K`、バッチを `b` とする。原著では短い入力を左パディングして長さを揃える。入力長がKより大きいとき、デコード時だけKに縮める方式はプリフィル中に `s` に比例するKVを保持する。BMはプリフィル中からKを上限に近づけるため、入力長とKの差に相当する一時KVメモリを削減できる。この節約分が追加のバッチに回るなら、要求ごとのプリフィルが遅くなっても総処理量が増える。

ただしプリフィル途中でKVを削除すると、後続の入力トークンの注意計算自体が圧縮済み履歴を使う。すべての入力を一括処理した後に削除する場合と異なり、過去情報の欠落が後続KV表現に伝播する。また全入力を見終える前に重要度を判断するため、後半で重要になるKVを早く削除する危険がある。論文はこの二つを速度・品質の主要な交換条件として明示する。

## 手法

### 1. プリフィルとデコードをまたぐブロック単位削除

Algorithm 1では、まず最大Kトークンの入力を一括処理する。入力がまだ残っていれば、保持KVから `p` ペアを削除し、次の `p` 入力トークンを処理する操作を繰り返す。これにより新しいKVを追加しても、保持容量が上限Kを超えないようにする。論文の実験は `p=64` に固定する。デコードでも保持数が上限に達したタイミングで64ペアをまとめて削除し、次のトークンを生成する。

この操作は「毎トークン1ペア削除」と異なり、削除候補の順位計算・メモリ操作を64トークンごとにまとめられる。反面、pを大きくすると削除直後の保持容量が大きく減り、直近の情報まで一時的に失う可能性がある。pを小さくすると削除頻度が増える。著者は実験でp=64を速度と精度の実用的折衷として選んだが、pの全探索や異なるモデルへの最適性は示していない。

プリフィル時の分割は、通常の一括プリフィルが持つGPU並列性を犠牲にする。その費用を相殺するには、削減したメモリで十分にバッチを増やせる必要がある。したがってBatch-Maxは一般的な高速Attentionカーネルの代替ではなく、**メモリ予算をバッチ容量へ再配分する実行戦略**である。

### 2. 累積注意重みを生存期間で正規化する

H2O型の削除は各KVペアへの過去の注意重みを足し合わせて重要度を評価する。ところが古いKVは長い間参照されるため、後から追加されたKVより累積重みが大きくなりやすい。原著§3.2は、古いペアが有利になるこの年齢バイアスを問題とする。単純な累積重みでは新しいが重要なトークンが不利になるため、別方式では直近ウィンドウを強制保持することが多い。

BMでは各KVの位置ID `kv_ids[i]` と現在位置 `curr_id` を保持し、累積注意重み `sum_weights[i]` を、そのKVが参照可能だったトークン数 `curr_id + 1 - kv_ids[i]` で割る。得られる `ave_weights[i]` が小さいKVを削除する。プリフィルでは入力ブロック内の各クエリからの注意重みを合計し、デコードでは新しいクエリ1個分を加算する。年齢で割るため、過去に長く存在しただけのKVを自動的に保護しない。

この指標は平均的な参照強度を近似するが、未来の質問で突然重要になるトークンを予測できない。注意重みの標準偏差も用いて保護するRoCoと比べ、BMは平均だけを使うことでハイパーパラメータを増やさず、バッチ拡大の寄与を明確にする。入力ブロックを逐次処理するため、累積統計は入力全体の将来情報を含まない。

### 3. 比較基準EDとFKVの役割

著者は既存のデコード専用圧縮のすべてを同条件で実装する代わりに、極端な削除方式（Extreme Decoding-only、ED）を構成した。EDはプリフィルで入力全体を処理し、その後は直近のKVペアだけを残す。K=2の設定でデコード時のKV読み出しを最小限にするため、著者はこれをデコード専用削除の達成可能スループット上限を表す実験的代理として用いる。一方、情報をほぼ捨てるので品質は著しく悪い。EDの精度が低いことをもってBMの品質維持を証明するのではなく、品質は別にフルKV方式FKVと比較する。

BMはEDより多くのKVを保持しながらも、プリフィル時のピークメモリ削減によってバッチを拡大する。比較の公平性はGPUメモリ予算と評価サンプルの一致に置かれているが、EDの「上限」は論文の具体的な実装・GPU条件での主張であり、全ての未来のデコード専用最適化や分散サービング実装に対する数学的な普遍上界と読み替えるべきではない。

### 主張値の読み方、感度と負の結果

Abstractの平均44.0%増は、Llama-2とPhi-3.5の実験をまとめたスループット改善であり、単一タスクの最大値でも、FKVに対する全条件の倍率でもない。BMはEDより速度が高いが、ED自体はROUGE-2または正解率がほぼゼロなので、EDを実用的な同等品質ベースラインとみなせない。品質の比較先をFKVへ切り替えていることを明示する必要がある。

原著は入力長・バッチサイズ・保持Kの複数条件を試すが、Kを小さくしてバッチを増やすほど精度が少し落ちる。Llama-2 GSM8Kの品質維持構成は0.341だが、速度優先構成は0.327へ下がる。CNN/DMでも0.146から0.142へ低下する。Phi-3.5 GSM8KのBM 0.774はFKV 0.783より低く、損失ゼロではない。従って「品質を維持」は設定したタスクでの近似的な維持を意味する。

BMが速くなるのは、GPUメモリを節約してEDより大きなバッチを実行できる場合である。実験ではEDのOOM境界を使って最大実行可能バッチを決め、BMをその先へ拡張する。逆に十分なGPUメモリがあり、プリフィルを一括処理しても必要なバッチを組めるなら、BMのブロック化は不要な逐次化とKV選別費用になり得る。著者自身が固定バッチ、入力長がK以下のケースではデコード専用圧縮が合理的と述べる。

960サンプルを同一にするためバッチ候補を特定の約数集合へ制限しており、著者は制約を外せばBMのさらに大きなバッチが使える可能性を記す。ただし実測していない追加改善を定量結果に加算してはならない。報告値は512トークンをEOS無視で必ず生成したオフライン測定であり、ユーザーの到着率・TTFT・P99遅延・連続バッチ・実際のEOS停止を伴うオンラインサービング性能を直接示すものではない。

## 既存研究との差

H2Oは履歴の注意重みを利用し、通常はプリフィル後のキャッシュ削減に使う。SnapKVはプリフィル後に直近観測窓を用いてKVを選ぶ。Scissorhandsは過去の重要度が継続するという仮説から、最近のKVと過去の重要KVを残す。RoCoは注意重みの平均と変動を組み合わせる。EasyKVはプリフィル中の圧縮も扱うが、著者らが指摘するように複数バッチでのスループット最大化を主要な評価対象としていない。BMは個々の削除ポリシーの精度を競うより、**プリフィルのメモリ上限を削減してバッチ数を増やす**ことを中心的なシステム寄与に据える。

BMの平均注意重みは累積値の年齢バイアスを除く単純な重要度指標であり、RoCoの分散に基づく保護は採用しない。これにより削除ルールのパラメータを抑え、バッチ拡大という設計変数に焦点を当てる。一方、より複雑なポリシーとの同一バッチ・同一精度での網羅比較ではないため、削除規則そのものが最良だとは証明していない。

## 限界と実装状況

評価はV100とTITAN V、2種類のモデル、3タスクに限定される。入力が生成より長いこと、GPUメモリが制約であること、バッチサイズを選べることが前提で、短い対話入力や非常に長い生成、既に大きなバッチを確保できるGPU、デコードの通信が律速の分散システムへの外挿は未検証である。入力ブロックを圧縮済みKVで計算するため、長距離依存や途中で重要度が逆転する場合の品質低下も残る。

実験はバッチ全体のトークン/秒を測定し、TTFT・TPOTの分布、オンライン同時到着、ユーザー体感遅延、H100/最新GPUでの専用カーネル、他のKV圧縮方式との厳密な同品質比較は提示していない。最適Kはタスクごとに探索しており、未知の実運用負荷で最適値を自動設定する仕組みも示していない。論文中にAlgorithm 1・2はあるが、再現可能な公式コードのURLは確認できなかった。
