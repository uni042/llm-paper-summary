# ReCalKV: Low-Rank KV Cache Compression via Head Reordering and Offline Calibration

## 概要

ReCalKVは、大規模言語モデルの長文推論で増大する鍵・値キャッシュ（KVキャッシュ）を、保存する隠れ次元の低ランク化によって削減する学習後圧縮方式である。特徴は、鍵（Key）と値（Value）を同じ特異値分解で扱わないことにある。鍵側は類似する注意ヘッドを中心化カーネル整合度（Centered Kernel Alignment、CKA）で探して並べ替え、類似ヘッドごとに群別特異値分解を行う。値側は較正データ上の出力誤差を使って低ランク因子を補正し、復元行列を注意出力射影へ事前融合する。重要度の異なる層にはフィッシャー情報に基づいて異なる圧縮率を割り当てる。

既存の低ランクKV圧縮であるPaluと比較し、LLaMA-2-7BのKVを70%圧縮したとき、6つのゼロショット質問応答課題の平均はReCalKVが59.90%、Paluが52.14%だった。非圧縮の64.99%からは低下するため、品質損失のない圧縮ではない。既存原稿が報告するA800上の単一注意モジュール測定では、70%圧縮時の速度改善は4千、1万6千、6万5千トークンの入力長でそれぞれ1.22倍、1.59倍、1.80倍である。これは注意カーネル単体の測定であり、モデル全体の生成速度にそのまま適用できない。

## 問題設定

自己回帰生成では、過去の各トークンについて各注意層の鍵ベクトルと値ベクトルを保存する。系列長、層数、ヘッド数、ヘッド次元が増えるほどKVキャッシュ容量と読み出し帯域の要求が大きくなる。重みがGPUメモリに収まるモデルでも、長い入力を複数同時に扱うとKVキャッシュが残り容量を圧迫し、実行できる同時要求数やバッチ長が制限される。トークンを捨てる方式とは別に、各トークンのKV表現の次元を減らせば、系列の全位置を保持したまま容量を下げられる。

射影行列を低ランクの二因子に分解し、低次元側だけをキャッシュすれば保存量は減る。しかし注意計算で元の次元が必要なら、毎トークンに復元行列を掛ける計算が増える。圧縮で減ったメモリ転送を復元計算が相殺すると、容量は節約できても速度が改善しない。さらに低ランク近似誤差は鍵と値で異なる影響を持つ。鍵の誤差はクエリとの内積と注意重みを変え、値の誤差は注意重みを掛けて集約する情報そのものを変える。鍵には回転位置埋め込み（RoPE）の適用順序という制約もある。

ReCalKVが解こうとするのは、低ランク化による容量削減、近似誤差による品質低下、実行時の復元計算という三つの交換関係である。著者らは鍵のヘッド間類似性と値の活性値分布を別々に利用することで、同じrank予算を均等に配る単純な分解より、品質を維持しやすくする。

## 手法

### 層ごとの圧縮予算の配分

入力は学習済みモデル、目標とするKV次元の圧縮率、少量の較正データである。まず各層の鍵・値射影についてフィッシャー情報を用いて感度を推定し、性能に敏感な層には比較的多くの次元を残し、低感度な層から大きく圧縮する。単一の全層共通rankではなく、全体の容量予算の中で層別rankを配分するため、同じ平均圧縮率でも品質を改善できる可能性がある。

公開実装の`compress.py`は`--search_method fisher_uniform`と目標比率`--param_ratio_target`を受け取る。`palu/rank_search.py`がrank探索を担い、圧縮済みモデルは再利用できる形式で書き出される。公開例ではWikiText-2を較正データに使い、256サンプルを分解・補正の処理に渡す。ここでのフィッシャー情報は圧縮の優先度を決めるための近似的な感度であり、最終的なタスク品質そのものではない。

### 鍵側：類似ヘッドの並べ替えと群別特異値分解

通常の群別特異値分解では、隣接するヘッドを機械的に同じグループへまとめる。しかし元のヘッド番号が似た表現を持つことは保証されず、異なる特徴を扱うヘッドを同じ低ランク部分空間へ押し込むと近似誤差が増える。ReCalKVは各ヘッドの表現類似度をCKAで測り、類似ヘッドが近接するよう順序を変更した後、群別の特異値分解を行う。

公開実装では`palu/model/modules/svd_linear.py`の`from_linear_whiten_reorder`がこの経路に対応し、例示設定のグループサイズは4ヘッドである。類似する複数ヘッドの共通方向を一つの低ランク空間にまとめれば、独立に分解した場合や元の並びのまま群分けした場合より、同じrankで表現を保持しやすい。注意計算で必要な元のヘッド順は対応する置換で扱い、意味的に異なるヘッドを混同しないようにする。

鍵の圧縮では回転位置埋め込みとの関係も重要である。RoPEは鍵とクエリの成分を位置に応じて回転させるため、圧縮された低次元鍵へ無条件に元と同じRoPEを適用できるわけではない。ReCalKVは鍵の復元経路とヘッド並べ替えを意識して実装し、復元の計算費用と圧縮誤差の両方を評価する。単純な「SVD後はすべて低次元のまま計算できる」という主張ではない。

### 値側：較正データによる因子の補正

値側では重み行列の再構成誤差だけを最小化する通常のSVDが、実際のモデル入力での出力誤差を最小にするとは限らない。そこでReCalKVは低ランク二因子の初期値を得た後、較正データの活性値を通した値射影の出力が元の射影に近づくよう、因子をオフラインで補正する。重み行列のすべての方向を同等に扱うのではなく、実際に現れやすい入力方向での誤差を重視する設計である。

著者らの説明では、二つの因子を交互に最適化する閉形式の更新を用いる。これは基盤モデルを新たに大規模学習し直す処理ではなく、学習済みモデルに対する少量データでの後処理である。公式実装では`from_linear_adasvd`と`compress_model_ours`が関連処理を担い、較正サンプル数を変える実験も可能である。較正分布から大きく外れた入力では同じ精度が保たれる保証はないため、データの代表性が重要となる。

### 値側：復元行列を出力射影へ事前融合

低次元値をキャッシュした後、毎回元次元へ復元し、その結果に通常の注意出力射影を掛けると、追加の行列積と中間テンソルが発生する。ReCalKVは値の復元因子と注意出力射影の積をオフラインで計算しておき、推論時には低次元の注意出力へ融合済みの射影を直接掛ける。これにより復元行列を独立に実行する必要がなくなる。

この融合は、単にモデル重みを小さくするだけでなく、実行時の計算グラフを変更する点が重要である。値を低次元のまま保持して集約した後、必要な出力次元へ一度で写像するため、メモリ削減を余分な復元行列積が食いつぶすことを抑えられる。一方、鍵側は注意スコアと位置変換の都合で値側と同じ融合を無条件に適用できない。両者を別設計にすることが本手法の核心である。

### 実行カーネルとオフライン処理の分離

実装は事前の圧縮段階と、圧縮済みモデルを使った推論段階に分かれる。事前処理ではフィッシャー情報によるrank割当、CKAによるヘッド並べ替え、群別SVD、値因子の較正、出力射影への融合を行う。推論時には低次元KVを保持し、鍵の対応付けやRoPEを考慮しながら注意計算を進める。公開リポジトリの`kernel/`には融合注意カーネルがあり、カーネル単体の遅延測定とモデル品質の評価を別々に行える。

比較実験のために、公開実装は`ours`（両機構あり）、`ours_reorder`（並べ替え側）、`ours_calib`（較正側）、`ours_baseline`（両機構なし）、`whiten`（Palu比較）の分解方式を切り替えられる。これにより、提案全体の改善を単一のブラックボックスとして扱わず、各構成要素が品質へ与える寄与を切り分けられる。

## 評価

### 評価環境と指標

論文の既存記録では、LLaMA-7B、LLaMA-2-7B、LLaMA-2-13B-Chat、Mistral-7B-Instruct、LongChat-7Bなどを使い、WikiText-2、PTB、C4の困惑度、六つのゼロショット質問応答課題、LongBenchの長文課題で品質を比較した。低い困惑度は言語予測が良いことを意味し、質問応答平均は圧縮後の能力維持を見る指標である。圧縮率を上げるほどキャッシュ容量は減るが、モデル品質を損なう可能性も増えるため、両方を併記する。

既存原稿の速度表は単一NVIDIA A800 80GB上のカスタムTriton注意モジュールで、4千、1万6千、6万5千トークンの入力を100回測定した条件である。一方、著者の公開実装READMEは再現環境として単一H100 80GBを記載している。論文表のA800測定と公開コードの再現推奨環境を同一の実測として扱わず、数値の帰属を分ける必要がある。公開コードの依存条件にはTransformers 4.43以降の位置埋め込みAPIが含まれる。

| 評価軸 | 条件 | 注意点 |
|---|---|---|
| 言語モデル | LLaMA系、Mistral系、LongChat系 | 層構成とRoPE条件が異なる |
| 圧縮率 | 50%、60%、70%、80%など | 高圧縮ほど品質低下が大きい |
| 較正 | WikiText-2、256サンプル | 追加の大規模再学習は不要 |
| 質問応答 | ARC、HellaSwag、OpenBookQA、PIQA、WinoGrandeなど | 六課題平均で比較 |
| 長文 | LongBenchの複数課題 | 圧縮しても系列位置は保持 |
| カーネル遅延 | A800 80GB、4K/16K/65K、100回平均 | 単一注意モジュールの値 |
| 公開実装 | 単一H100 80GBで再現可能と記載 | 論文のA800速度表とは別条件 |

### 50〜70%圧縮での品質

LLaMA-2-7Bの6つのゼロショット質問応答課題では、非圧縮の平均が64.99%、ReCalKVの50%圧縮で63.64%、70%圧縮で59.90%だった。70%圧縮時のPaluは52.14%であり、同じ圧縮率でも鍵・値を別々に扱う効果が大きい。非圧縮に比べてReCalKV自身も低下するので、「高圧縮でも品質不変」とは解釈しない。

50%圧縮時のWikiText-2困惑度は非圧縮5.47、ReCalKV 5.83、Palu 6.02、C4では非圧縮7.26、ReCalKV 8.14、Palu 8.72だった。どちらも小さい値が良いため、ReCalKVは非圧縮より劣るもののPaluより良い。質問応答と困惑度を別の指標として報告することは、圧縮が予測確率と下流タスクに同じ割合で影響するとは限らないため重要である。

### 構成要素除去実験

80%圧縮の既存監査表では、ヘッド並べ替えも値の較正・融合も使わない基準のWikiText-2困惑度9.34、ゼロショット平均49.01%、LongBench平均9.01に対し、両機構を使うReCalKVではそれぞれ8.48、54.55%、15.40となった。困惑度は低いほど良く、二つの正解率系指標は高いほど良い。したがって両機構の組合せは、高圧縮時の品質悪化を複数の評価軸で抑えている。

ただし、この比較は「両方なし」と「両方あり」の差であり、鍵側の並べ替えと値側の較正が単独で何ポイントずつ寄与するかを、この二行だけから正確に分解することはできない。公式コードには片方だけ有効にする設定があり、寄与を検証する際には対応する実験条件を区別する必要がある。

### 低ビットKV量子化との併用

ReCalKVの隠れ次元削減は、保存する数値のビット幅を減らす量子化とは異なる方向の圧縮である。既存原稿の併用評価では、60%次元圧縮と4ビットKV量子化を組み合わせたWikiText-2困惑度がReCalKV 6.24、Palu 6.84であり、70%圧縮と3ビットの組合せではC4困惑度がReCalKV 10.41、Palu 15.75だった。高圧縮時の品質低下は残るが、次元削減と低ビット化を併用できることが示される。

公開コードでは`--lt_bits 3 --lt_hadamard`で3ビットの低ランクKV量子化を有効化できる。ただしこの経路は追加のCUDA拡張を必要とし、PyTorchやCUDAとの互換性が実行条件になる。通常の次元圧縮の結果と、量子化まで併用した結果を同じメモリ削減率として混同してはならない。

### 注意モジュールの実測遅延

既存原稿のA800上の測定では、70%圧縮時に4K入力で1.22倍、16Kで1.59倍、65Kで1.80倍の注意モジュール高速化が報告されている。入力が長いほどKVの読み出し量が増えるため、次元削減の帯域上の利得が目立ちやすい。逆に短い系列では復元や制御の固定費が相対的に大きくなり、速度改善は小さい。

この速度比較は単一注意モジュールのカーネル時間であり、トークン生成全体の速度、複数要求の連続バッチ処理、CPU・GPU間転送を含む実運用スループットではない。高い圧縮率で注意カーネルが速くても、モデルの他の演算が律速なら全体改善は小さくなる。論文の主張はKVのメモリ効率と注意実行の改善に限定して読む必要がある。

## 既存研究との差

PaluやLoRCと同じく、射影行列の低ランク分解を利用してKVキャッシュの隠れ次元を減らす系統に属する。ただしReCalKVは、鍵のヘッド間類似性をCKAで測り、類似ヘッドを群別分解へまとめる点と、値を較正活性に合わせて補正し、復元行列を注意出力射影へ融合する点が異なる。鍵の近似誤差とRoPE適用経路、値の出力精度と復元コストを別問題として扱うことが設計上の新規性である。

トークンを削除して系列長を短くするKV追い出し方式とは異なり、ReCalKVは保存する各トークンの次元を削減する。したがって、系列内の位置を残したい長文推論へ適用しやすい一方、トークン数自体は減らない。数値のビット幅を減らすKV量子化とも独立した圧縮軸であり、併用する実装経路が公開されている。

## 限界

低ランク圧縮は損失圧縮であり、極端にrankを減らすと品質は低下する。70%圧縮でPaluより良い結果が得られても、非圧縮モデルの64.99%からReCalKVの59.90%へ質問応答平均が落ちている。品質を一定以上維持したい用途では、圧縮率を機械的に最大化するのでなく、対象タスクに合わせて選ぶ必要がある。フィッシャー情報によるrank配分と値の較正は、使用した較正データの代表性にも依存する。

本方式は系列長を短縮しない。極端な長文脈や多数同時要求では、次元を削減してもKV総量が大きくなり、別のキャッシュ管理と併用する必要があり得る。また鍵の復元・RoPE・ヘッド並べ替えは値側のように単純な行列融合で完全には消せないため、実装効率は注意カーネルとハードウェアに依存する。

速度結果は特定GPU上の注意モジュール単体の比較であり、連続バッチ配信、異なるGPU世代、モデル全体の初回トークン遅延・生成速度について同じ倍率を保証しない。公開実装READMEのH100再現条件と既存論文原稿のA800測定条件が異なる点も再現時に注意すべきである。3ビット量子化を併用する場合にはCUDA拡張と依存ライブラリの互換性が追加条件になる。

## 実装状況

著者らの公式リポジトリでは、`compress.py`が圧縮処理の入口、`palu/rank_search.py`が層別rank探索、`palu/decomposition.py`がReCalKV本体、`palu/model/modules/svd_linear.py`が鍵の並べ替えと値の較正を担う。`kernel/`には融合注意カーネルがあり、`run_ppl_eval.py`、`run_lm_eval.py`、`run_long_bench.py`で困惑度、ゼロショット質問応答、長文評価を実行できる。公開コードはApache-2.0ライセンスで、単一H100 80GBによる再現環境が案内されている。

本再監査ではarXiv要旨、著者公式の実装手順・コード構成、GitHub既存論文原稿の評価表を突き合わせた。一次論文PDF本文は今回の実行環境から直接取得できなかったため、既存原稿に記録された数値は元の出典区分を維持し、公式実装の記載と矛盾する環境条件は区別した。未確認の追加性能値や全体スループットを推測で補っていない。
