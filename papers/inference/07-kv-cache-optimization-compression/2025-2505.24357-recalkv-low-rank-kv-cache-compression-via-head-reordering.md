# ReCalKV: Low-Rank KV Cache Compression via Head Reordering and Offline Calibration

> KeyとValueは注意機構で同じ役割ではない。ReCalKVは、Keyには「似たヘッドをまとめて低ランク化」、Valueには「データで低ランク因子を補正して復元行列を次の射影へ融合」という別々の圧縮を割り当て、高圧縮時の品質と実行時オーバーヘッドを両方抑える。

## 概要

KVキャッシュの隠れ次元を低ランク化すると、トークン数を削らずに1トークン当たりの保存ベクトルを小さくできる。しかしKeyとValueへ同じ特異値分解（Singular Value Decomposition, SVD）を適用すると、高圧縮率で品質が落ちやすい。

ReCalKVはこの原因を二つに分ける。Keyは注意スコア計算前に回転位置埋め込み（Rotary Position Embedding, RoPE）を受けるため、圧縮後に完全Keyへ復元する経路が必要になりやすく、実行時コストが問題になる。一方、著者らのフィッシャー情報分析ではValue射影の方がモデル品質への重要度が高く、Value側では近似誤差そのものを強く抑える必要がある。

そこでKeyにはヘッド単位類似度対応並べ替え（Head-wise Similarity-aware Reordering, HSR）、Valueにはオフライン較正・行列融合（Offline Calibration and Matrix Fusion, OCMF）を使う。さらに層ごとのフィッシャー情報で圧縮率を配分し、重要層へ多くの次元を残す。

## 問題設定

### 低ランクKV圧縮の利点と隠れた復元コスト

射影行列 (W) を (W approx LR) と分解し、入力Xに対して低次元表現 (XL) をKVキャッシュへ保存すれば、キャッシュ次元をrへ縮められる。しかし注意計算で元次元が必要なら、毎トークン ( (XL)R ) を復元する必要があり、メモリ削減と引き換えに行列積が増える。

PaluやLoRCは射影行列側へSVDを適用してこの問題を軽減するが、KeyとValueの非対称性を十分には扱わない。ReCalKVは「低ランク近似誤差」と「オンライン復元コスト」をKey/Value別に分けて最適化する。

### Keyはヘッド間共有、Valueは近似精度を重視する

著者らはヘッド間表現を中心化カーネル整合度（Centered Kernel Alignment, CKA）で測り、似たKeyヘッドを同じSVDグループへまとめると共有部分空間を捉えやすいとする。

Valueについてはフィッシャー情報がKeyより高い傾向を示し、同じ圧縮率でもValue近似誤差が品質へ強く効く。そのため単純SVDで終えず、較正データ上の出力誤差を最小化するよう低ランク因子を再計算する。

## 手法

### 1. まず層ごとの圧縮率をフィッシャー情報で配分する

事前学習済みモデルM、較正データX、目標圧縮率Rを入力とする。各層のKey/Value射影についてフィッシャー情報を計算し、性能へ敏感な層ほど高いrankを残す。

評価ではWikiText-2からランダムに256サンプルを選び、SVD前の白色化とValueのオフライン較正の両方へ使用する。

### 2. Key: CKAで類似ヘッドを並べ替えてgrouped SVDする

Key射影行列を注意ヘッドごとの列ブロックへ分ける。全ヘッド間のCKA類似度を求め、似たヘッドが隣接するよう順序を並べ替える。その後、4ヘッドずつのグループへまとめてSVDする。

通常のgrouped SVDでは元のヘッド順が意味的類似性を保証しないため、同じグループ内に無関係な部分空間が混ざる。HSRは「先に似たヘッドを集める」ことで同じrankでも近似誤差を下げる。

実行時には各トークンのヘッド順も対応して置換する。これは完全Keyを再構成する大きな射影より軽く、RoPEを適用するために必要なKey経路と両立させる。

### 3. Value: SVD因子を較正データ上の誤差で閉形式に補正する

Value射影を (W_v approx L_vR_v) と分解した後、較正データX上の出力誤差 (|L_vR_vX-W_vX|_F^2) を最小化する。

著者らは (L_v) と (R_v) を交互に最適化する閉形式解を導き、通常SVDの「重み行列そのものの再構成誤差」ではなく「実際の較正活性を通した出力誤差」を下げる。これは追加学習ではなくオフライン計算である。

### 4. Valueの復元因子を出力射影へ融合する

圧縮Valueとしてキャッシュへ保存するのは (XL_v)。通常なら注意後に (R_v) を掛けて元次元へ戻し、その後に出力射影 (W_o) を掛ける。

ReCalKVは事前に (W_o^f=R_vW_o) を計算して保存する。実行時は低次元Valueの注意結果へ融合済み (W_o^f) を一度掛ければよく、明示的なValue復元を消せる。これがOCMFの「Matrix Fusion」に当たる。

### 5. カスタムTritonカーネルへ低ランク経路を統合する

実推論評価ではKeyのオンライン並べ替え、Valueの融合済み表現、RoPE、因果注意を一つのTriton注意カーネルへ統合する。単にKV容量を小さくするだけでなく、長文脈で減ったメモリ読出しを実遅延へ結び付ける。

## 評価

### 評価条件

| 項目 | 条件 |
| --- | --- |
| モデル | LLaMA-7B、LLaMA-2-7B、LLaMA-2-13B-Chat、Mistral-7B-Instruct-v0.2、LongChat-7B-v1.5-32k |
| 言語モデル評価 | WikiText-2、PTB、C4（困惑度） |
| zero-shot QA | ARC-c、ARC-e、HellaSwag、OpenBookQA、PIQA、WinoGrande |
| 長文脈 | LongBench 8 tasks |
| 比較 | Paluを中心にASVD、EigenAttention等も補足比較 |
| 較正 | WikiText-2の256 samples |
| grouped SVD | group size 4 |
| GPU | 1×NVIDIA A800 80GB |
| 速度測定 | 単一attention module、prompt 4K/16K/65K、100 runs平均 |
| 実装 | PyTorch + Hugging Face Transformers、速度部はカスタムTriton |

### 品質結果

| LLaMA-2-7B | 非圧縮 | ReCalKV | Palu |
| --- | ---: | ---: | ---: |
| 50%圧縮・6 QA平均 | 64.99% | **63.64%** | 論文表でReCalKV未満 |
| 70%圧縮・6 QA平均 | 64.99% | **59.90%** | 52.14% |
| 50%圧縮・WikiText-2困惑度 | 5.47 | **5.83** | 6.02 |
| 50%圧縮・C4困惑度 | 7.26 | **8.14** | 8.72 |

50% KV圧縮では6 QA平均が64.99%から63.64%で、相対低下は約2%。70%では劣化が大きくなるが、Paluとの差も広がる。

80%圧縮のアブレーションでは、HSRもOCMFも使わない場合のWikiText-2困惑度9.34、zero-shot平均49.01、LongBench平均9.01に対し、両方を使うと8.48、54.55、15.40へ改善する。Key/Value別の二つの機構が独立に寄与することを示す。

### 量子化との併用

隠れ次元圧縮はbit幅圧縮と直交するため、ReCalKVはKV量子化とも組み合わせられる。60%圧縮＋4bitではWikiText-2困惑度6.24でPalu 6.84、70%＋3bitではC4困惑度10.41でPalu 15.75だった。

### 実行遅延

70% KV圧縮時、A800の単一注意モジュールで次の高速化を報告する。

| prompt length | ReCalKV speedup |
| --- | ---: |
| 4K | 1.22× |
| 16K | 1.59× |
| 65K | 1.80× |

長いpromptほどKV読出し削減の寄与が大きくなるため高速化率が上がる。ただしこれは単一attention moduleの値であり、モデル全体のエンドツーエンド1.80倍を意味しない。

## 既存研究との差

Palu/LoRCと同じく射影行列を低ランク化してKVの隠れ次元を減らす系統だが、ReCalKVはKeyとValueへ同じSVD処理を適用しない。Keyではヘッド順を再構成してgrouped SVDを改善し、Valueでは実データ較正と出力射影融合を使う。

MatryoshkaKVやEigenAttentionのように追加射影を実行時に挟む方式と比べ、行列融合でオンライン復元を極力消すことも重点である。さらに量子化やトークン追い出しとは別軸なので、組み合わせる余地がある。

## 限界・実装状況

ReCalKVは損失圧縮であり、高圧縮率では非圧縮モデルからの品質低下を避けられない。論文自身もこの点を限界として挙げる。

また本手法は隠れ次元方向だけを圧縮し、KV系列長は減らさない。極端な長文脈ではトークン追い出しや検索型注意との併用が必要になり得る。

速度評価はA800上の単一注意モジュールであり、連続バッチ配信やモデル全体のスループットは別途測る必要がある。公式実装はReCalKVリポジトリで公開されている。
