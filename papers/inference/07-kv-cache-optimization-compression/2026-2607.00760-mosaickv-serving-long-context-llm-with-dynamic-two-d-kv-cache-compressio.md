# MosaicKV: Serving Long-Context LLM with Dynamic Two-D KV Cache Compression

## 概要
MosaicKVは、極長文脈のKVキャッシュを系列方向とチャネル方向の両方で圧縮し、容量削減だけでなく注意計算そのものを高速化するサービングシステムである。系列圧縮だけでは保持トークン数を減らすほど精度が落ち、チャネル圧縮だけでも圧縮率に限界がある。一方、両者を単純に組み合わせると重要要素まで二重に捨ててしまい、論文のQuestベース素朴実装ではチャネル圧縮率30%で24.5%、70%で82.8%の精度低下が生じる。

MosaicKVは、重要度分布がKVベクトルごと・KV領域ごとに一様でないことを利用する。各KVベクトルについて特異値分解（singular value decomposition; SVD）で回転後に絶対値上位の要素だけを残し、さらに現在クエリから重要トークン ブロックを選ぶ二段階圧縮を行う。圧縮率・要素グループ幅・トークン ブロック幅はキャッシュセグメントごとに変え、圧縮誤差が閾値を越えた地点でセグメントを切り替える。

しかし細粒度の疎行列はGPUでそのまま扱うとキャッシュ localityが悪く、cuSPARSEでは未圧縮注意より25〜136倍遅くなる条件さえある。そこでMosaicKVは残存要素を連続格納するパック済み KV形式とPackedAttentionを導入し、未使用のCUDA 中核とCPUへ管理処理を逃がす。H800評価では未圧縮比較基準比でKVメモリ3倍削減、注意最大16倍、1M 文脈のデコード 遅延最大4.8倍短縮、スループット最大7.3倍を達成し、LongBench/RULERの平均精度低下は1.76%に留める。

## 問題設定
LLaMA-3.1-8Bを8並列、128K 文脈でサービングするとKVキャッシュだけで約128GBとなり、重み容量の約8倍になる。1M 文脈では約1TB、重みの約64倍へ増える。さらに長文脈では注意がデコードのTime-Between-トークン（TBT）の大部分を占め、論文の分析では128Kで84.7%、1Mで97.9%に達する。

既存の系列圧縮は現在クエリに重要なトークンだけを選ぶため注意の対象を減らせるが、任意トークンが将来選ばれる可能性がある動的方式では完全なKVを保持する必要があり、GPU容量そのものを十分減らせない場合がある。チャネル圧縮は各KVベクトルの次元を減らすが、全トークンへ同じチャネル maskを適用すると、トークンごとに異なる重要要素を落とす。

SVD回転後でも、全KVベクトルのtop-25%重要要素のうち、グローバルtop-25%チャネルに入るのは62.28%に過ぎないという観察がある。さらに外れ値が強い領域と均一な領域では許容できる圧縮率が違う。この二段階の不均一性を無視して全キャッシュへ一つの圧縮設定を適用することが、単純な二次元圧縮で品質が崩れる原因になる。

## 手法

### 1. 各ベクトル単位のチャネル圧縮
各KV セグメントについてKとVそれぞれのSVD回転行列を計算し、重要情報を少数チャネルへ集中させる。従来の「全トークンで同じ上位チャネルだけ残す」のではなく、回転後の各K/Vベクトルごとに絶対値の大きい上位 (r) 要素を個別に選ぶ。したがって同じセグメントでもトークンごとに異なる位置が残る。

入力トークンはプリフィル後にセグメント単位で圧縮し、生成トークンは後述の二重バッファで逐次処理する。下位25%など全ベクトルでほぼ選ばれないチャネルは位置ビットマップ自体から切り捨て、位置管理費も減らす。

### 2. query依存の系列圧縮
チャネル圧縮したKVをさらにトークン方向へ圧縮する。各セグメント内のトークンを8や16個のブロックへ分け、ブロック内キーの平均をブロック単位 キーとして保持する。このブロック単位 キーも第一段階と同時にチャネル圧縮する。

デコード時、現在クエリと各ブロック単位 キーの内積から重要度を求め、上位 (k) ブロックだけを実注意へ渡す。したがって第一段階で「各ベクトル内の重要チャネル」、第二段階で「現在クエリに重要なトークン ブロック」を選ぶ。二次元圧縮はKだけでなくVにも適用され、トークン選択から注意計算まで圧縮表現を維持する。

### 3. segmentごとの動的圧縮戦略
入力KVは例えば64K トークンの固定セグメントへ分割する。生成KVは固定長ではなく、新規トークンのKVを現行戦略で圧縮したときの累積圧縮誤差を監視し、閾値を超えた時点でセグメントを終了する。誤差が小さくても64Kなどの最大長で強制的に更新する。

各セグメントはSVD回転行列、チャネル圧縮率、隣接要素をまとめて選ぶグループ 大きさ、系列圧縮率、トークン ブロック 大きさを持つ。チャネル圧縮では候補圧縮率87.5%/75%/62.5%やグループ 大きさ 1/2/4を試し、誤差閾値を満たす範囲で最も強い圧縮・粗いグループを選ぶ。系列側は候補ブロック 大きさ 4/8/16についてブロック内キー分散を調べ、閾値以下の最大ブロックを選ぶ。現実装では系列圧縮率自体は固定である。

### 4. packed KV形式とPackedAttention
ベクトルごとに残るチャネルが違うため、第一段階の結果は非構造疎行列になる。通常のCOO/CSRのように各要素索引を持つ代わりに、残存値を連続格納し、元位置は (D)-ビットのビットマップで表す。さらに隣接要素をグループとして一ビットで管理し、ビットマップ オーバーヘッドを削る。

PackedAttentionはこのパック済み vectorを展開せず、ビットマップのset ビットから必要なクエリ位置をその場で復元してCUDA 中核で積和する。ビットマップをチャンクへ分けてthreadへ配り、連続格納によるキャッシュ localityを使う。SVDの逆回転も巨大な圧縮KV行列へ適用せず、非圧縮側のクエリ一つを回転して等価な内積を計算する。

この方式はFlashAttentionのチャンク処理上に実装され、選ばれなかったトークン チャンクをskipする。Tensor 中核へ戻すために疎行列を展開する費用を避ける点が重要である。

### 5. GPU/CPU二重bufferによる非同期管理
新しい生成トークンはセグメント全体の最適戦略が確定する前に注意へ必要になる。GPU側バッファでは一時的に前セグメントの戦略を使って圧縮し、デコードを止めずに処理する。同時に元の新規KVをCPU側バッファへ送り、CPUがセグメント分割、累積誤差計算、共分散行列の更新、SVD、候補戦略評価、最終再圧縮を非同期で行う。

セグメントが確定するとCPU側で作った最終圧縮表現へGPU側セグメントを差し替える。共分散行列は新トークンの外積で逐次更新するため、セグメント終了後に全履歴を再走査せずSVDを求められる。プリフィル側でも前層KVのencodingを次層計算と重ね、圧縮管理をcritical pathから外す。

## 評価

### 条件
prototypeは約5,300行のPythonと2,800行のCUDAで、NVIDIA H800 80GB上で評価する。性能評価の主モデルはLLaMA-3.1-8B、精度評価にはQwen3-4BとMinistral-3-8Bも加える。未圧縮比較基準はmicrobenchmarkではFlashAttention系カーネル、エンドツーエンドではvLLM。系列圧縮比較基準はQuestである。

標準設定ではQuestのブロック 大きさは16、MosaicKVは8、両者ともトークンの10%を選び、MosaicKVはチャネルの25%を残す。数値形式はBF16。精度はLongBenchと64K設定のRULERで測る。

### 精度
LongBench平均では未圧縮比較基準に対するMosaicKVの低下は0.86%、Quest比では0.64%である。RULERではLLaMA-3.1-8Bが未圧縮91.56、Quest90.42、MosaicKV89.85、Qwen3-4Bが92.95/92.13/90.47、Ministral-3-8Bが90.05/89.33/86.94となる。RULERでの未圧縮比低下はそれぞれ1.86%、2.58%、3.55%で、モデルによって感度が異なる。

構成要素除去では、10% トークン保持＋一様チャネル選択から始め、SVD回転を加えると正規化精度が20.8%改善、ベクトル単位要素選択でさらに64.5%改善し、動的セグメント戦略まで入れると未圧縮の98%まで回復する。単に二次元へするだけでなく、per-vector選択が品質維持に大きく寄与することを示す。

### メモリとattention
LLaMA-3.1-8Bでは25% チャネル保持時にKVメモリを未圧縮比3倍、Quest比3.18倍削減する。Questはブロック キーを追加保持するため約6.25%のメモリオーバーヘッドがある。

注意 遅延はトークン選択率6.25%/12.5%、複数文脈・バッチで測定し、MosaicKVは未圧縮比最大16倍、Quest比最大2.4倍高速である。スコア計算だけではQuest比平均4.2倍高速。これは圧縮量だけでなく、パック済み形式とクエリ側回転によって疎表現のキャッシュ miss・展開費を避けた結果である。

### end-to-end
未圧縮vLLMとQuestはH800 80GBではバッチ 1でも512Kの完全KVを収容できないが、MosaicKVは約1.44M トークンまで拡張する。非常に長い条件では全層実測が容量上困難なため、一部注意層をprofileし、各Transformer層が同じ演算を行う前提で総性能を外挿している。

1M 文脈、バッチ 4のTBTはvLLM比4.8倍、Quest比1.8倍短い。文脈全体の平均ではそれぞれ3.8倍、1.5倍。KV容量削減によりバッチを3倍へ増やせるため、1M 文脈 スループットはvLLM比7.3倍、Quest比2.2倍、全条件平均では5.5倍/2.3倍となる。

プリフィルで追加されるSVD・圧縮費は64Kで7.6%、128Kで3.6%、256Kで1.7%、512Kで0.8%、1Mで0.4%へ低下する。生成中の32-トークン update バッファ圧縮は40.6 µsで、長文脈注意に対して小さい。

## 既存研究との差
Questなど系列圧縮は注意対象トークンを減らすが、動的選択のため完全KV保持が必要になりやすい。ThinKなどチャネル圧縮はチャネル数を減らすが、uniform maskではトークンごとの重要位置差を捨てる。InfiniGenはチャネル圧縮表現をトークン選択に使っても、実注意には完全KVを保持する。

MosaicKVはK/Vの両方を「各ベクトル内要素」と「クエリ依存トークン」の二軸で圧縮し、その表現をデコード全体で維持する。さらに細粒度疎性が理論上小さくてもGPUで遅くなる問題をパック済み形式とCPU非同期管理で解き、圧縮率と実時間性能を同時に扱う点が異なる。

## 限界
per-vector選択とセグメント別SVDは管理処理を増やす。MosaicKVはCPUと未使用CUDA 中核へ逃がしているため、CPU資源が少ない環境や別処理でCPUが飽和しているサービングでは隠蔽できる費用が減る。パック済み 疎 注意もCUDA 中核性能・メモリ hierarchyへ依存し、別GPU世代で同じ倍率になるとは限らない。

系列圧縮率は現実装では静的であり、動的に選ぶのは主にセグメント境界、チャネル圧縮率、グループ 大きさ、ブロック 大きさである。また極長文脈のエンドツーエンド評価の一部は注意層のprofileから外挿しており、1.44M全モデル実行の全system オーバーヘッドを直接測った値ではない。

品質も完全保持ではなく、RULERではモデルによって最大3.55%の平均低下がある。重要情報が圧縮誤差指標やクエリ-based ブロック選択で拾えないtaskでは低下が大きくなる可能性がある。LongBench/RULER平均1.76%という値を任意の長文脈 distributionへ一般化すべきではない。
