# MosaicKV: Serving Long-Context LLM with Dynamic Two-D KV Cache Compression

## 概要
MosaicKVは、極長文脈のKVキャッシュを系列方向とチャネル方向の両方で圧縮し、容量削減だけでなく注意計算そのものを高速化するservingシステムである。系列圧縮だけでは保持トークン数を減らすほど精度が落ち、チャネル圧縮だけでも圧縮率に限界がある。一方、両者を単純に組み合わせると重要要素まで二重に捨ててしまい、論文のQuestベース素朴実装ではチャネル圧縮率30%で24.5%、70%で82.8%の精度低下が生じる。

MosaicKVは、重要度分布がKVベクトルごと・KV領域ごとに一様でないことを利用する。各KVベクトルについて特異値分解（singular value decomposition; SVD）で回転後に絶対値上位の要素だけを残し、さらに現在queryから重要token blockを選ぶ二段階圧縮を行う。圧縮率・要素グループ幅・token block幅はキャッシュsegmentごとに変え、圧縮誤差が閾値を越えた地点でsegmentを切り替える。

しかし細粒度の疎行列はGPUでそのまま扱うとcache localityが悪く、cuSPARSEでは未圧縮attentionより25〜136倍遅くなる条件さえある。そこでMosaicKVは残存要素を連続格納するpacked KV形式とPackedAttentionを導入し、未使用のCUDA coreとCPUへ管理処理を逃がす。H800評価では未圧縮baseline比でKVメモリ3倍削減、attention最大16倍、1M contextのdecode latency最大4.8倍短縮、throughput最大7.3倍を達成し、LongBench/RULERの平均精度低下は1.76%に留める。

## 問題設定
LLaMA-3.1-8Bを8並列、128K contextでservingするとKVキャッシュだけで約128GBとなり、重み容量の約8倍になる。1M contextでは約1TB、重みの約64倍へ増える。さらに長文脈ではattentionがdecodeのTime-Between-Tokens（TBT）の大部分を占め、論文の分析では128Kで84.7%、1Mで97.9%に達する。

既存の系列圧縮は現在queryに重要なtokenだけを選ぶためattentionの対象を減らせるが、任意tokenが将来選ばれる可能性がある動的方式では完全なKVを保持する必要があり、GPU容量そのものを十分減らせない場合がある。チャネル圧縮は各KVベクトルの次元を減らすが、全tokenへ同じchannel maskを適用すると、tokenごとに異なる重要要素を落とす。

SVD回転後でも、全KVベクトルのtop-25%重要要素のうち、グローバルtop-25%チャネルに入るのは62.28%に過ぎないという観察がある。さらに外れ値が強い領域と均一な領域では許容できる圧縮率が違う。この二段階の不均一性を無視して全キャッシュへ一つの圧縮設定を適用することが、単純な二次元圧縮で品質が崩れる原因になる。

## 手法

### 1. 各ベクトル単位のチャネル圧縮
各KV segmentについてKとVそれぞれのSVD回転行列を計算し、重要情報を少数チャネルへ集中させる。従来の「全tokenで同じ上位チャネルだけ残す」のではなく、回転後の各K/Vベクトルごとに絶対値の大きい上位 (r) 要素を個別に選ぶ。したがって同じsegmentでもtokenごとに異なる位置が残る。

入力tokenはprefill後にsegment単位で圧縮し、生成tokenは後述の二重bufferで逐次処理する。下位25%など全ベクトルでほぼ選ばれないチャネルは位置bitmap自体から切り捨て、位置管理費も減らす。

### 2. query依存の系列圧縮
チャネル圧縮したKVをさらにtoken方向へ圧縮する。各segment内のtokenを8や16個のblockへ分け、block内keyの平均をper-block keyとして保持する。このper-block keyも第一段階と同時にチャネル圧縮する。

decode時、現在queryと各per-block keyの内積から重要度を求め、上位 (k) blockだけを実attentionへ渡す。したがって第一段階で「各ベクトル内の重要channel」、第二段階で「現在queryに重要なtoken block」を選ぶ。二次元圧縮はKだけでなくVにも適用され、token選択からattention計算まで圧縮表現を維持する。

### 3. segmentごとの動的圧縮戦略
入力KVは例えば64K tokenの固定segmentへ分割する。生成KVは固定長ではなく、新規tokenのKVを現行戦略で圧縮したときの累積圧縮誤差を監視し、閾値を超えた時点でsegmentを終了する。誤差が小さくても64Kなどの最大長で強制的に更新する。

各segmentはSVD回転行列、チャネル圧縮率、隣接要素をまとめて選ぶgroup size、系列圧縮率、token block sizeを持つ。チャネル圧縮では候補圧縮率87.5%/75%/62.5%やgroup size 1/2/4を試し、誤差閾値を満たす範囲で最も強い圧縮・粗いgroupを選ぶ。系列側は候補block size 4/8/16についてblock内key分散を調べ、閾値以下の最大blockを選ぶ。現実装では系列圧縮率自体は固定である。

### 4. packed KV形式とPackedAttention
ベクトルごとに残るchannelが違うため、第一段階の結果は非構造疎行列になる。通常のCOO/CSRのように各要素indexを持つ代わりに、残存値を連続格納し、元位置は (D)-bitのbitmapで表す。さらに隣接要素をgroupとして一bitで管理し、bitmap overheadを削る。

PackedAttentionはこのpacked vectorを展開せず、bitmapのset bitから必要なquery位置をその場で復元してCUDA coreで積和する。bitmapをchunkへ分けてthreadへ配り、連続格納によるcache localityを使う。SVDの逆回転も巨大な圧縮KV行列へ適用せず、非圧縮側のquery一つを回転して等価な内積を計算する。

この方式はFlashAttentionのchunk処理上に実装され、選ばれなかったtoken chunkをskipする。Tensor Coreへ戻すために疎行列を展開する費用を避ける点が重要である。

### 5. GPU/CPU二重bufferによる非同期管理
新しい生成tokenはsegment全体の最適戦略が確定する前にattentionへ必要になる。GPU側bufferでは一時的に前segmentの戦略を使って圧縮し、decodeを止めずに処理する。同時に元の新規KVをCPU側bufferへ送り、CPUがsegment分割、累積誤差計算、共分散行列の更新、SVD、候補戦略評価、最終再圧縮を非同期で行う。

segmentが確定するとCPU側で作った最終圧縮表現へGPU側segmentを差し替える。共分散行列は新tokenの外積で逐次更新するため、segment終了後に全履歴を再走査せずSVDを求められる。prefill側でも前層KVのencodingを次層計算と重ね、圧縮管理をcritical pathから外す。

## 評価

### 条件
prototypeは約5,300行のPythonと2,800行のCUDAで、NVIDIA H800 80GB上で評価する。性能評価の主モデルはLLaMA-3.1-8B、精度評価にはQwen3-4BとMinistral-3-8Bも加える。未圧縮baselineはmicrobenchmarkではFlashAttention系kernel、end-to-endではvLLM。系列圧縮baselineはQuestである。

標準設定ではQuestのblock sizeは16、MosaicKVは8、両者ともtokenの10%を選び、MosaicKVはchannelの25%を残す。数値形式はBF16。精度はLongBenchと64K設定のRULERで測る。

### 精度
LongBench平均では未圧縮baselineに対するMosaicKVの低下は0.86%、Quest比では0.64%である。RULERではLLaMA-3.1-8Bが未圧縮91.56、Quest90.42、MosaicKV89.85、Qwen3-4Bが92.95/92.13/90.47、Ministral-3-8Bが90.05/89.33/86.94となる。RULERでの未圧縮比低下はそれぞれ1.86%、2.58%、3.55%で、モデルによって感度が異なる。

構成要素除去では、10% token保持＋一様channel選択から始め、SVD回転を加えると正規化精度が20.8%改善、ベクトル単位要素選択でさらに64.5%改善し、動的segment戦略まで入れると未圧縮の98%まで回復する。単に二次元へするだけでなく、per-vector選択が品質維持に大きく寄与することを示す。

### メモリとattention
LLaMA-3.1-8Bでは25% channel保持時にKVメモリを未圧縮比3倍、Quest比3.18倍削減する。Questはblock keyを追加保持するため約6.25%のメモリoverheadがある。

attention latencyはtoken選択率6.25%/12.5%、複数context・batchで測定し、MosaicKVは未圧縮比最大16倍、Quest比最大2.4倍高速である。score計算だけではQuest比平均4.2倍高速。これは圧縮量だけでなく、packed形式とquery側回転によって疎表現のcache miss・展開費を避けた結果である。

### end-to-end
未圧縮vLLMとQuestはH800 80GBではbatch 1でも512Kの完全KVを収容できないが、MosaicKVは約1.44M tokenまで拡張する。非常に長い条件では全層実測が容量上困難なため、一部attention層をprofileし、各Transformer層が同じ演算を行う前提で総性能を外挿している。

1M context、batch 4のTBTはvLLM比4.8倍、Quest比1.8倍短い。context全体の平均ではそれぞれ3.8倍、1.5倍。KV容量削減によりbatchを3倍へ増やせるため、1M context throughputはvLLM比7.3倍、Quest比2.2倍、全条件平均では5.5倍/2.3倍となる。

prefillで追加されるSVD・圧縮費は64Kで7.6%、128Kで3.6%、256Kで1.7%、512Kで0.8%、1Mで0.4%へ低下する。生成中の32-token update buffer圧縮は40.6 µsで、長文脈attentionに対して小さい。

## 既存研究との差
Questなど系列圧縮はattention対象tokenを減らすが、動的選択のため完全KV保持が必要になりやすい。ThinKなどチャネル圧縮はchannel数を減らすが、uniform maskではtokenごとの重要位置差を捨てる。InfiniGenはchannel圧縮表現をtoken選択に使っても、実attentionには完全KVを保持する。

MosaicKVはK/Vの両方を「各ベクトル内要素」と「query依存token」の二軸で圧縮し、その表現をdecode全体で維持する。さらに細粒度疎性が理論上小さくてもGPUで遅くなる問題をpacked形式とCPU非同期管理で解き、圧縮率と実時間性能を同時に扱う点が異なる。

## 限界
per-vector選択とsegment別SVDは管理処理を増やす。MosaicKVはCPUと未使用CUDA coreへ逃がしているため、CPU資源が少ない環境や別処理でCPUが飽和しているservingでは隠蔽できる費用が減る。packed sparse attentionもCUDA core性能・memory hierarchyへ依存し、別GPU世代で同じ倍率になるとは限らない。

系列圧縮率は現実装では静的であり、動的に選ぶのは主にsegment境界、channel圧縮率、group size、block sizeである。また極長文脈のend-to-end評価の一部はattention層のprofileから外挿しており、1.44M全モデル実行の全system overheadを直接測った値ではない。

品質も完全保持ではなく、RULERではモデルによって最大3.55%の平均低下がある。重要情報が圧縮誤差指標やquery-based block選択で拾えないtaskでは低下が大きくなる可能性がある。LongBench/RULER平均1.76%という値を任意のlong-context distributionへ一般化すべきではない。
