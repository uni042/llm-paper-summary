# Cascading KV Cache：固定容量のまま古い重要トークンを長く保持する段階的キャッシュ

## 概要

長文生成や長い文書の事前計算では、鍵・値キャッシュ（KV cache）が入力長に比例して増える。固定長の滑動窓（sliding window）を使えばメモリを抑えられるが、窓から出た過去のトークンは消え、長距離の依存関係を復元できない。StreamingLLMは冒頭の注意シンク（attention sinks）を残して安定性を高めるものの、冒頭以外の過去トークンは一定の年齢になると削除する。

Cascading KV Cacheは固定容量のKVを複数の段階的サブキャッシュへ分割し、新しいトークンを高頻度で受け入れる段から、古いトークンを低頻度で受け入れる段へ移す。各段の境界で注意スコアの指数移動平均（EMA）を比較し、相対的に重要なトークンを残す。キャッシュ総容量は固定したまま、古い情報が間引かれつつ長く残る。さらに循環バッファで追加・削除のコピー費用を減らし、入力を小さなチャンクに分けるストライド事前計算（strided prefill）を導入する。

原著は1Mトークンを単層注意で処理する実験でFlashAttention 2比6.8倍の時間短縮を報告する。PG19の言語モデル評価、Booksum要約、LongBench、1Mトークンのパスキー検索でも固定窓型の線形推論より良い結果を示す。ただし単層の事前計算の倍率をLLM全層の要求応答速度へ直接移せず、圧縮は厳密な全文注意と等価ではない。

## 問題設定

### 固定窓が古い重要情報を捨てる

通常の滑動窓は最新Nトークンだけを保持する。窓がいっぱいになると、次のトークンを追加するため最古のKVを削除する。これは予測時に必要なKV数を一定にするので、生成トークン当たりの注意計算を抑えられる。一方、章をまたいで登場する人物名や遠い位置のパスキーなど、最近の窓の外にある情報を失う。

StreamingLLMは最初の少数トークンを注意シンクとして固定保存し、それ以外を滑動窓で管理する。注意シンクはソフトマックスの確率分布を安定させるが、窓外の途中のトークンは保持できない。重要度が高くても年齢だけで消えるため、長文を一様に扱えない。

### 逐次事前計算と全長事前計算の両極端

1トークンずつ処理すれば固定容量キャッシュを自然に更新できるが、GPUではカーネル起動や小さな行列演算の費用が大きく、現実的な入力長で遅い。逆に全文をFlashAttentionで一括処理すればGPUの並列性を活用できるが、注意の総演算量は入力長の二乗で増える。論文は中間の固定長チャンクを選び、キャッシュ上の古いKVとチャンク内の新しいKVだけへ注意を計算する。

## 手法

### 1. キャッシュを複数段へ分割

総容量|C|をN個のサブキャッシュC_1〜C_Nへ分ける。新しいトークンは必ず最初の段へ入る。第一段から押し出されたトークンのうち、一部だけが第二段へ渡される。さらに第二段から第三段へ渡す頻度を下げる。原著の基本設定では次段は前段からの候補の半分程度を受け入れ、段が深いほど保持トークンの時刻間隔が広がる。

全段の容量の和は元の固定窓と同じなので、保存するKV数は増えない。古いトークンが残る「時間範囲」が広がるのであり、過去のすべてのトークンを保持するわけではない。段数を増やせば遠い過去に到達しやすくなるが、同じ容量では直近トークンの密度が下がり、局所文脈の品質が変化する。

### 2. 注意スコアのEMAで境界選択

単に一つおきに古いトークンを残すだけでは、重要なトークンが偶然削除される。そこで各KVが過去に受けた注意スコアを指数移動平均で更新する。時刻tのスコアをs_k^(t)、保存された平均をμ^(t)とすると、

\[
\mu^{(t+1)}=\gamma\mu^{(t)}+(1-\gamma)s_k^{(t)}
\]

とする。原著の主要実験ではγ=0.9999を使う。次段が受入れ可能な時点では前段からの候補を渡し、受入れを行わない時点では新しい候補と次段の末尾にある候補の重要度を比較し、低い方を削除する。これにより過去トークンの生存期間が固定の年齢規則ではなく注意重要度に依存する。

ただしEMAは過去の注意分布を基にするため、将来突然必要になる情報を確実に残せるわけではない。将来の質問に対して重要なKVが過去には目立たなかった場合、選別に失敗し得る。注意スコアを重視する方式の一般的な限界として明記すべき点である。

### 3. 注意シンクと位置情報

冒頭64トークンを通常の段階的キャッシュとは別の注意シンクとして保存する。論文が「容量16K」と表記する場合、実際には16Kの可変キャッシュに加えて64トークンのシンクを持つ。比較時にはこの追加容量を意識する必要がある。

位置埋め込みは元の絶対位置をそのまま保持せず、現在のキャッシュに並んでいる順序に応じて再割り当てする。例えば元の系列位置0、1、3、5、7、8を保存している場合、キャッシュ内の位置0〜5として扱う。これはStreamingLLMの位置処理に倣うものであり、RoPEなどの位置意味が元の全文注意と厳密に一致するわけではない。

### 4. 循環バッファによる更新費用の削減

KVを追加するたびに配列を連結すると、キャッシュ全体の読み書きが発生し、キャッシュを固定長にしても更新費用が大きくなる。Cascading KV Cacheは各段に循環バッファを用意し、最古位置のポインタξを更新する。挿入後にξ←(ξ+1) mod |C_i|とすれば、必要な場所だけ上書きできる。

原著はTritonでGPUカーネルを実装し、元のStreamingLLMのテンソル連結方式より更新時間を大幅に削減した。重要度比較と段間転送もGPU側で処理する。ここでの速度改善にはアルゴリズムだけでなく、連結を避ける実装最適化の効果が含まれる。

### 5. ストライド事前計算

入力長Sを固定長Kのチャンクへ分ける。各チャンクでは、新規トークンのクエリを、既存キャッシュとチャンク内の鍵へ向けて一度に注意計算する。計算した注意スコアを使ってキャッシュを更新し、次のチャンクへ進む。K=1は1トークン逐次処理に近く、K=Sは全長一括処理に近い。中間のKを選ぶとGPUの行列演算をまとめつつ、参照する過去KVの数を固定にできる。

チャンク内では密な注意を使うため、チャンクを大きくすると局所品質が改善する可能性がある一方、チャンク内部の計算は増える。論文の1Mトークン単層注意では4Kのチャンクが最も速かったと報告する。チャンク長はハードウェアと文脈長に応じて調整が必要である。

## 評価条件

| 項目 | 原著の設定 |
|---|---|
| モデル | Llama-3.1 8B/70B、Qwen2 7B/72Bなど。評価によって使用モデルが異なる |
| データ | PG19全文書籍、Booksum書籍要約、LongBench、長距離パスキー検索 |
| キャッシュ | 16K、32K、65Kなど。冒頭64トークンの注意シンクを別途保持 |
| 段数 | 基本は4段。比較として1段、段数感度あり |
| EMA | γ=0.9999 |
| 事前計算 | 512、1K、4Kなど実験ごとにチャンク長を指定 |
| 比較 | StreamingLLM、BigBird、FlashAttention 2、H2O、SnapKVなど（課題により異なる） |
| 指標 | パープレキシティ、要約ROUGE、LongBench正答率、パスキー検索正答率、GPU処理時間 |

論文の「線形計算」は、固定容量キャッシュと固定チャンク長を前提に入力長Sに対して線形という意味である。モデルサイズやキャッシュ容量を同時に増やす場合の計算費用をゼロにするものではない。

## 評価

### 1. 事前計算・キャッシュ更新時間

16KのKV容量で16Kトークンを順に追加する実験では、元のStreamingLLMのテンソル連結方式に対し、循環バッファによる1段版の更新時間は0.01%、4段版でも0.038%に収まった。更新カーネルの実装差が極めて大きいが、これはモデル全体の推論時間ではなくキャッシュ更新処理の累積時間である。

1Mトークンの単層注意実験では、16KのKVと4Kストライドを使った方式がFlashAttention 2の14.8%の時間で処理を終え、約6.8倍高速だった。これは注意処理とキャッシュ更新を含む単層実験であり、LLM全層のエンドツーエンド要求時間を直接測った値ではない。

### 2. PG19のパープレキシティ

| モデル・KV容量 | StreamingLLM | Cascading | 改善 |
|---|---:|---:|---:|
| Qwen2-7B、16K | 9.18 | **9.14** | -0.04 |
| Llama-3.1-8B、16K | 7.78 | **7.72** | -0.06 |
| Qwen2-7B、32K | 9.05 | **9.03** | -0.02 |
| Llama-3.1-8B、32K | 7.65 | **7.60** | -0.05 |
| Llama-3.1-8B、65K | 7.61 | **7.60** | -0.01 |

パープレキシティは小さいほど良い。改善幅は小さいが一貫している。比較対象の本は各容量を超える長さのものだけを選び、短い本を含む全PG19の平均とは異なる。Qwen2-7Bは位置埋め込みの上限が32Kであるため、65K容量の条件から除外された。

### 3. 書籍要約と長文理解

Booksumでは、Llama-3.1-8BのROUGE-1/2/LがStreamingLLMの33.04/6.04/19.85からCascadingの34.47/6.63/20.52へ改善した。Qwen2-7Bでも29.14/4.51/16.91から30.34/5.02/17.54へ改善した。一方、Llama-3.1-8BのROUGE-1は完全注意35.37を下回るため、線形方式の中での改善と完全注意への追いつきを混同しない。

LongBenchでは入力長の概ね4分の1を保持する予算を設定し、線形推論の次点方式に対して全モデル・評価集合の平均で12.13%の改善を報告した。ただし課題・モデル別の差は一様ではなく、論文中の平均値だけで全タスクの品質維持を保証するものではない。

### 4. パスキー検索と長期保持

総容量65Kのキャッシュで1Mトークンのパスキー検索を行い、Cascadingは固定窓型のStreamingLLMより高い検索精度を保った。文脈長が容量を大きく超えた場合にも、過去のトークンが疎に残ることでランダム回答（10%）を上回る条件がある。論文は容量から四回長さを倍増した1Mトークン条件で24ポイントの改善、五回倍増した条件で18ポイントの改善を報告する。

これは1Mトークンの全情報を保持したことを意味しない。長い履歴の一部の位置だけがキャッシュへ残るため、重要度推定で保持されなかったパスキーは復元できない。

### 5. 構成要素除去実験

PG19の先頭書籍、Llama-3.1-8B、KV容量2048で、StreamingLLMのパープレキシティは8.03だった。Cascadingで重要度選択を除くと同じ8.03となり、選択を有効にすると7.88へ改善した。段階的な時刻間引きだけではなく、注意スコアによる選択が効果を生むことを示す。ただし一冊での実験であり、あらゆる長文への一般化は別途検証が必要である。

## 既存研究との差

StreamingLLMは注意シンクと直近窓を残す。H2OやSnapKVは重要KVを選別するが、論文が比較する実装では長文入力の事前計算が二乗時間のまま残る。Cascading KV Cacheは、複数段の受入頻度によって固定容量のまま長い時刻範囲を保持し、注意スコアEMAによる選択、循環バッファ、ストライド事前計算を組み合わせる点が特徴である。追加学習なしに既存Transformerへ適用することを主張するが、推論アルゴリズムと位置の扱いは変わる。

## 限界

注意スコアの履歴に基づく選別は、未来の質問にだけ重要なトークンを捨てる可能性がある。キャッシュにないトークンの内容は復元できないため、厳密な全文注意の代替ではない。段数を増やすと過去を広く覆える一方、直近情報の密度や重要度比較の頻度が変わる。位置埋め込みの再割当ても、元の絶対位置に依存するタスクでは挙動差を生み得る。

実験の高速化にはGPU上の循環バッファとTriton実装が含まれる。1Mトークンで6.8倍という値は単層注意の事前計算であり、ネットワーク越しの配信、複数利用者、全層推論の応答時間を示していない。LongBenchの平均改善は線形推論方式間の比較であり、全長を保持する高精度方式との完全な同等性を主張するものではない。


### 評価を解釈するときの追加の注意

重要度選択の構成要素除去では、同じキャッシュ容量で比較しているかだけでなく、チャンク長と位置再割当てを揃える必要がある。段階的な受入れ頻度の効果、注意EMAの効果、循環バッファの実装速度、ストライド事前計算の効果は別の要素であり、一つの速度倍率からすべての寄与を推定できない。特に単層注意の計測と実モデルの全文生成では、FFNと重み読み出しが占める割合が異なる。

長距離検索では、キャッシュが実際に保持した原系列の位置を可視化し、質問に必要なトークンが残っていたかを追跡すると失敗理由を理解しやすい。平均パープレキシティの小幅改善だけでは、特定の事実を遠くから取り出せる保証にならないため、パスキーの位置別正答率を併記するのが望ましい。
