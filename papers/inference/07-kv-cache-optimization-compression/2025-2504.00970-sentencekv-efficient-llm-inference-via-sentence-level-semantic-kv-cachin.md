# SentenceKV：文単位の意味索引とCPU退避KVの動的回収

## 概要

SentenceKVは、長い入力を文ごとのまとまりに分け、文の意味を表す小さなキー索引だけをGPUに残して、個々の鍵・値（KV）対をCPU側へ退避する長文脈推論方式である。従来のトークン単位のKV削除では、最初は重要でないと判定したトークンが後続の質問で必要になっても復活できない。固定長チャンク単位の回収では、文の途中で切れた断片を意味単位として扱うため、関連情報のまとまりを見失いやすい。SentenceKVは句読点で区切った文を検索単位とし、生成中のクエリがどの文に近いかを使ってCPU上のKVを必要時に再取得する。

著者はCOLM 2025の論文で、Llama-3.1-8B-Instructの256K文脈、復号時KV予算1024トークンにおいて、Full KVのGPUメモリ89.71 GB・84.9 ms/トークンに対し、SentenceKVは52.71 GB・17.8 ms/トークンと報告する。Llama-3-8Bの針探し（NIAH）では予算128トークンで97.5%の正解率を得る。ただし比較対象SnapKVも256Kでは52.71 GBを使用し、16.5 ms/トークンとSentenceKVより速い。さらに原著付録には文の検索とCPU↔GPU転送が1ステップ当たり約73 msかかると書かれており、本文の17.8 ms/トークンとの計測範囲が整合しない。この論文の実用性を判断する際には、検索精度の改善と、真の終端遅延の未確定性を切り分ける必要がある。

## 問題設定と先行方式の制約

自己回帰生成では、新しいトークンを出すたびに過去トークンのキーと値を参照する。文脈長が増えるほどKVキャッシュが大きくなり、GPUメモリ容量と読出し帯域を消費する。KVを最初に間引く方式はGPU容量を減らせるが、あとから話題が変わったときに削除済みトークンを参照できない。全KVをCPUに置き、必要なものだけ読み戻す方式は回復可能性を保つが、何を戻すかを素早く決める検索索引が必要になる。

Questなどの方式は固定長のトークン塊を索引化する。固定長は実装しやすい一方、一つの文が二つの塊に割れたり、無関係な文が同じ塊に入ったりする。ClusterKVなどの意味クラスタ方式は内容に沿ったグループを作るが、クラスタ形成の計算と最初のトークンが出るまでの遅延（TTFT）が問題になる。SentenceKVは高価なクラスタリングを避け、句読点で決まる自然な文境界を使う。ただし句読点の乏しい文書、コード、長い列挙、異言語の区切りはこの前提を弱める。

もう一つの問題は、生成中の単一クエリが局所的な単語へ過剰に反応し得ることだ。生成中の文全体が何を問うているかを表すため、SentenceKVは現在生成している文のクエリを蓄積し、その平均で過去の文を検索する。この設計は、単純な「直近トークンと最も似たKVを戻す」方式とは異なる。

## 手法

### 1. 句読点に基づく文バケットと観測窓による重要度

事前処理（prefill）では入力長Lのテキストを句読点などで文に分割し、各文を長さ可変のバケットとする。例として32Kトークンの文書は数百の文へ分かれる。各トークンの重要度は、入力末尾Nトークン（通常N=32）の観測窓から、以前のトークンがどれだけ注意を受けたかで測る。原著の記号では、観測窓内の全トークン・注意ヘッドからトークンiへ向かう注意スコアを足し合わせて重要度α_iを作る。

最終的なGPU上の復号用トークン予算をτ、意味保持係数をrとすると、事前処理時に保持する候補は文書全体の重要度上位⌊rτ⌋トークンである。典型例はτ=1024、r=2または3で、CPU側へ保持する候補数は2048または3072になる。**文ごとにrτを保持するのではなく、文書全体でrτを選ぶ**点が重要である。長いだけで情報量が少ない文が予算を独占するのを防ぎ、文ごとに残る候補数を変化させる。

観測窓の注意で低重要度とされたトークンはこの時点で破棄される。したがってSentenceKVは、**入力全体のKVをCPUへ完全退避する可逆方式ではない**。CPUに保持するのは選抜後のrτトークンのKVであり、その中から生成時に最大τトークンをGPUへ戻す二段階選択である。生成時の動的回収は第1段階で破棄した情報を復元できない。

### 2. 文代表キーによる軽量なGPU索引

保持した各文バケットsについて、注意ヘッドhごとに、その文で選ばれたキーの平均を計算する。原著の式(1)は、保持トークン集合S_sに対する平均キー \(\bar{k}_{s,h}=|S_s|^{-1}\sum_{x\in S_s}k_{x,h}\) である。これが文の意味を表す代表ベクトルとしてGPUに残る。元のKV対はCPUメモリへ退避するため、GPUは全文のKVではなく文の小さな索引を持つ構造になる。

この代表ベクトルは外部の文章埋め込みモデルで作った文ベクトルではない。推論対象LLMの注意機構が作るキーを平均したものであり、注意ヘッドごとの検索に直結する。別の埋め込み器を実行する費用は避けられるが、キーの平均が文の重要な局所表現をどこまで保存するかはモデル・ヘッド・文構造に依存する。複数の話題が混ざる文では平均が曖昧になる可能性がある。

### 3. 生成文の平均クエリと意味類似度による回収

復号時は、現在生成中の文について、各生成トークンのクエリq_tを一時集合Q_sに追加する。各ステップでその平均 \(\bar q=|Q_s|^{-1}\sum_{t\in Q_s}q_t\) を作り、GPU上の文代表キーとの内積 \(S(\bar q,\bar k_{s,h})=\bar q^T\bar k_{s,h}\) を計算する。類似度が高い文バケットから順に、合計が復号用予算τを超えない範囲でKVをCPUからGPUへ転送する。

GPUに戻ったキー・値に対してのみ注意計算を行い、次のトークンを確定する。新しいクエリをQ_sに追加して検索を繰り返し、句点・疑問符など文境界を検出したらQ_sをリセットする。これにより、一つの生成文の途中では複数トークンの問い合わせ意図を統合し、次の文に入ると検索対象を更新できる。現在トークン単独のクエリを使う場合より、図6では文平均クエリの方がNIAH精度が高い。

文の中でトークンが多すぎると、その文を一つ選ぶだけでτを使い切る恐れがある。著者はグローバルな重要度選択でこの問題を緩和するが、異常に長い文の追加分割は将来課題とする。候補文の選択・CPUからの回収は毎ステップの追加作業であり、意味索引が小さいことだけでは転送と検索の終端費用はゼロにならない。

### 4. 一つの要求が通るデータフロー

入力を文へ区切り、末尾32トークンの注意を使って文書全体からrτ個の重要トークンを選ぶ。各文の保持キーを平均してGPU上の索引を作り、選抜KV本体をCPUへ置く。生成の各ステップでは、現在の生成文の平均クエリと文代表キーを比較し、関連度上位の文から合計τトークン分をCPUからGPUへ戻す。戻したKVだけで注意を計算し、生成文が終わればクエリ蓄積を空にして次の文の検索へ移る。

計算・通信の費用は、事前処理の注意重要度計算と文分割、文代表キーの生成、CPUへ保持KVを移す転送、毎ステップの類似度計算、CPUからのKV回収、縮小された注意計算に分かれる。注意計算自体はτに制限されて速くなっても、文ランキングがCPU側で実行される場合やPCIe転送が同期的に発生する場合には、検索・転送が新たな律速点になる。

### 1. NIAH：検索精度

| Llama-3-8B、最大8K文脈、τ=128 | 正解率 |
|---|---:|
| H2O | 25.2% |
| SnapKV | 78.2% |
| Quest | 48.3% |
| InfLLM | 87.8% |
| ShadowKV | 85.8% |

図4の条件では、SentenceKVはSnapKVより19.3パーセントポイント、InfLLMより9.7ポイント高い。これは文単位の回収が針となる一文の再発見に適していることを示す。ただしQuestの48.3%は塊サイズ32での条件であり、付録表6ではサイズ16にすると96.1%へ上がる。**SentenceKVとQuestの差は固定長塊の粒度選択に強く依存する**ため、48.3%だけを一般的なQuestの能力として引用すべきではない。

原著表2のRULER結果では、SentenceKVはS1では完全だが、MQでFull KV 0.98に対し0.77、FWEで0.85に対し0.61へ落ちる。ShadowKVとの比較でもMQは0.87対0.77、FWEは0.78対0.61でSentenceKVが低い。したがって「すべての退避方式を精度で上回る」という一般化は表2と整合しない。文単位の平均検索が長い依存関係や複数の証拠の同時回収に必ず適するわけではない。

### 4. 速度・メモリ：Full KVとSnapKVを分離して読む

| Llama-3.1-8B-Instruct、τ=1024 | Full KV | SnapKV | SentenceKV |
|---|---:|---:|---:|
| 16K：遅延（ms/トークン） | 16.8 | 16.5 | 17.8 |
| 64K：遅延（ms/トークン） | 29.6 | 16.5 | 17.7 |
| 256K：遅延（ms/トークン） | 84.9 | 16.5 | 17.8 |
| 16K：メモリ（GB） | 19.78 | 17.47 | 17.47 |
| 64K：メモリ（GB） | 33.77 | 24.52 | 24.54 |
| 256K：メモリ（GB） | 89.71 | 52.71 | 52.71 |

256KでのFull KVに対する容量削減は37.00 GB、約41.2%である。報告遅延は84.9から17.8 msへ減り、表の値だけで計算すると約4.77倍となる。一方SnapKVは同じ52.71 GBで16.5 msと速い。16KではFull KV 16.8 msに対してSentenceKV 17.8 msであり、圧縮方式が逆に遅い。**SentenceKVの主な利得はSnapKVに対する速度ではなく、検索精度の改善**として読むべきである。

LongChat-v1.5-7Bでも、256KでFull KVは容量不足（OOM）、SentenceKVは48.31 GB・16.9 ms/トークンで実行可能だが、SnapKVは48.30 GB・16.5 ms/トークンであり、容量・速度はほぼ同等かSnapKVの方が有利である。モデルによってFull KVの容量不足閾値が変わることを、SentenceKVだけの特殊な長文脈対応能力として誇張しない。

### 5. 付録の検索・転送費用と本文遅延の重大な整合性問題

付録A.5～A.6は、64K文脈のH100 NVL 96GB、τ=1024、保持係数2の条件で、文バケット構築に初回4秒、各生成ステップにCPU側の文ランキング約0.050秒、GPU→CPU転送約0.0191秒、CPU→GPU転送約0.0038秒がかかると記す。これらを足すと**1ステップ約0.0729秒＝72.9 ms**である。対して付録表4のSentenceKVの64K遅延は**17.7 ms/トークン**である。もし72.9 msが同一ステップで逐次発生し、17.7 msの外側に追加されるなら、終端遅延は少なくとも約90.6 msとなり、Full KVの29.6 msより遅くなる。

著者は付録でこの追加費用を「無視できる」と説明しているが、**72.9 msは17.7 msより大きく、Full KVとの差11.9 msも上回る**。異なる計測条件、非同期重畳、別の単位、単位誤植などの可能性はあるものの、論文の数値だけでは整合を確定できない。ここを勝手に「0.073 msの誤植」や「完全に隠蔽される」と補完しない。報告された復号遅延が転送・検索・前処理をどこまで含むかが未解決であり、実配信の性能主張には重大な不確実性が残る。

付録A.6はKV部分が33.55 GBから0.10 GBになる一方、モデル重みなどが残るため合計52.71 GBであるとも説明する。KV部分だけの約335倍削減を、システム全体のGPUメモリ335倍削減と混同しない。CPUメモリ消費、PCIe転送、CPU類似度検索、初回4秒の準備費用を含めた資源会計が必要である。

### 6. 構成要素除去とパラメータ感度

文境界による分割を等サイズの塊に置き換えると、表3ではNarrativeQAが27.02対29.59、HotpotQAが53.19対53.76、TRECが8.5対11.5、PCountが4.81対5.28となる。ただし表3のSentenceKVのNarrativeQA 29.59やHotpotQA 53.76は表1の同名課題の29.53と53.15とは一致せず、実験条件差の説明が十分ではない。表間の値を無条件に同一設定の結果として統合しない。

保持係数rを増やすとCPU側に残る候補が増え、検索精度は当初改善するが、過剰に増やすと無関係な情報も混入し得る。図6では現在トークンだけのクエリより、生成文の平均クエリを使う方がNIAHで高精度となる。Questの固定塊サイズも結果を大きく左右し、32トークンでは48.3%、16トークンでは96.1%へ上がる。これは「文単位だから必ず固定長方式に勝つ」ではなく、意味境界と塊粒度の双方が重要であることを示す。

## 既存研究との差

SnapKVは観測窓の注意に基づいて重要トークンを選び、復号時には原則その選択を固定する。SentenceKVも初期選抜にはSnapKV型の重要度を使うが、rτ個の候補をCPUに保持し、生成文の平均クエリを用いて毎ステップτ個まで再回収する。Questは固定長塊の統計で関連KVを動的に取得するが、SentenceKVは句読点で決まる長さ可変の文を索引単位にする。ClusterKVなどの意味クラスタリングは入力を意味に沿って再編成する代わりにクラスタ形成費用があるのに対し、SentenceKVは文境界で簡素化する。ShadowKVはキーの低ランク表現など別の圧縮表現を使うが、SentenceKVはヘッドごとの平均キーで文を代表する。

これらの差は、長文脈の「関連文を再び見つける」能力を改善するための設計である。一方、SnapKVより高いCPU検索・転送費用を払ってまで使うべきかは、NIAHのような単一証拠検索と、RULERの複数証拠・推論タスクで異なる。速度と品質を別々の指標として比較する必要がある。

## 限界

句読点に依存する文分割は、コード、箇条書き、略語、非英語文書、極端に長い文などで意味境界と一致しない場合がある。固定の保持係数rは、長さや主題が異なる文書に適応しない。文の平均キーは複数の主題を一つに潰す可能性があり、文の一部だけが重要な質問や複数の離れた証拠を必要とする質問では不利になり得る。初期の重要度選択で削除したトークンはCPUからも復元できない。これらは著者の将来課題と実験結果に沿った限界である。

著者は公式コードを公開しているが、論文の付録にある検索・転送費用と本文の遅延表は数値上整合していないため、公開コードを使ってGPU・CPU間転送、検索、注意カーネル、前処理を個別計測し、同じハードウェア条件で再現することが重要である。単純なGPU内のKV削減だけでなく、CPUメモリ容量、CPU検索時間、PCIe帯域、同時リクエスト数、接頭辞再利用を含むサービス全体の測定が必要となる。論文は大規模なオンライン配信トレースでの実測を報告していない。
