# HAWK: Heterogeneity-Aware KV Cache Transfer for Efficient GPU-NPU Phase-Disaggregated LLM Inference

> プリフィルをGPU、デコードをNPUに分ける異種分離型サービングのためのKV転送機構。共通のRDMA経路で直接転送し、テンソル配置の違いを転送前の部分変換とチャネル別バッファで転送中に吸収することで、GPU単独に迫る性能と高い電力・コスト効率を実機で示す。

## 概要

大規模言語モデルの推論は、入力をまとめて処理するプリフィルと、1トークンずつ生成するデコードで計算の性質が大きく違う。プリフィルは行列同士の積が中心でGPUのテンソルコアをよく使えるが、デコードは行列とベクトルの積が中心で演算の密度が低く、GPUの計算利用率は大きく落ちる。論文の実測では、入力512トークン・出力128トークン・バッチ32の条件で、A100とTenstorrent p150aのスループット差はプリフィルの2.52倍からデコードでは1.16倍まで縮み、デコードの電力効率とコスト効率はNPUが1.39倍と4.31倍高かった。つまり、プリフィルをGPU、デコードをNPUへ割り当てる分離型構成には、性能を大きく落とさず効率を上げる余地がある。

その実現を阻むのが、プリフィル側で作られたKVキャッシュをデコード側へ移す転送である。GPU同士なら最適化された通信基盤でRDMAによる直接転送ができるが、異種デバイスでは通信の仕組みが互換でなく、ホストを経由する転送はコピーと介入で大きく遅くなる。さらにGPUとNPUではテンソルのメモリ配置が異なり、そのまま移しても受信側で配置の組み替えが要る。本論文のHAWKは、両デバイスを共通のRDMA経路へつなぐ直接転送と、配置の違いを転送の過程へ溶かし込む設計で、この障壁を解く。集約転送量2560メガバイトでは、ホスト経由の素朴な異種転送より25.40倍速く、GPU同士の直接転送とのエンドツーエンド遅延の差は0.39パーセントだった。オンラインサービングでも、同じサービス品質目標の下でGPU単独構成との出力スループットの差は最大7.88パーセント以内に収まり、電力効率は最大1.26倍、コスト効率は最大2.03倍を記録した。

## 問題設定

分離型サービングでは、プリフィル側が最初のトークンと入力ぶんのKVキャッシュを作り、それをデコード側へ渡して続きを生成する。したがって転送は全リクエストの通り道にあり、その遅延は最初のトークンまでの時間を直接押し上げる。異種構成の第1の障壁は通信の互換性である。デバイスごとに通信の仕組みとソフトウエア基盤が異なり、共通の直接転送路がない。回避策のホスト経由は、デバイスからホスト、ホストからデバイスへの余分なコピーとホストの介入を伴う。論文の観測では、GPU同士でもホスト経由は直接転送の1.83倍から5.25倍の遅延があり、異種ではさらに悪化する。

第2の障壁はテンソル配置である。配置とは、テンソルの次元の並びと、各要素が仮想アドレスと物理メモリチャネルへどう対応するかという規則であり、デバイスごとに計算と転送を最適化するために異なる。GPUは連続した仮想アドレスを細かい粒度でチャネルへ分散するのに対し、評価対象のNPUはタイル単位の配置を明示的に制御する。素朴に連続バッファをNPU側へ置くと、チャネル間でメモリ使用が偏り、空きがあるのに新しいテンソルを置けなくなる。実際に論文の試作では、従来型の単一連続バッファを使う直接転送の構成が、この偏りによるメモリ不足でサービング中に失敗した。一方のデバイスに他方の配置を強制する手もあるが、そのデバイスのカーネル効率を落とし、既存カーネルの改変も要る。求められるのは、どちらの計算効率も落とさず、転送の追加遅延も小さい配置の吸収方法である。

## 手法のあらまし

HAWKの入力はGPU側プリフィルが生成したKVテンソルであり、出力はNPU側デコードがそのまま使える配置のKVテンソルである。まず、GPU側は既存のピアメモリ機能を、NPU側はドライバへ追加した対応機能を使い、両デバイスのメモリを共通のLinux RDMA基盤へ登録して、ネットワークカードがホストを介さずデバイスメモリへ直接触れる経路を作る。次にGPU側で、KVテンソルを転送向けに部分変換する。次元の並び替えで対象のNPU配置へ近づけつつ、同じメモリチャネル行きの部分を連続にまとめて、転送の回数を減らし1回を大きくする。NPU側には、対象テンソルの配置に沿ってメモリチャネルごとにRDMAバッファを用意する。GPU側の連続バッファの各部分を対応するチャネル別バッファへRDMAで送ると、転送の中で残りの配置合わせが完了し、受信したテンソルは組み替えなしにデコードで使える。部分変換をプリフィル側で行うのは、プリフィルの方がデコードよりメモリ帯域に余裕があり、変換の追加作業を吸収しやすいためである。転送要求はまとめて投入され、完了後にデコード側がKVをキャッシュプールへ格納して両側のバッファを解放する。

## 手法

### 1. 共通RDMA経路 — ホストをデータ経路から外す

観測するものは各デバイスのメモリ登録情報であり、保持する状態はRDMA基盤へ登録されたデバイスメモリの対応である。GPU側は既存のピアメモリクライアントを使い、NPU側は新規に実装したピアメモリクライアントが、アドレス範囲の確認、ページの取得、DMA対応付けとその解放といったコールバックを提供する。これにより、両ノードのネットワークカードが相手のデバイスメモリを直接読み書きできる。転送の実行はMooncake Transfer Engineの上に構築され、低レベルのRDMA操作を抽象化して実行時のデータ移動を担う。減るボトルネックは、ホスト経由のコピーと介入であり、論文の転送実測ではこの差が最も大きい。追加で消費する資源は、ドライバ側の実装と保守であり、特にNPU側はオープンなソフトウエア基盤でなければ手を入れられないという前提がある。失敗条件はまさにこの点で、評価対象のNPUが選ばれた理由も、低レベル改変が可能な唯一の基盤だったことにある。

### 2. 配置に合わせたRDMAバッファ割当 — チャネルごとのバッファで偏りを防ぐ

NPUのテンソルは複数のメモリチャネルへ明示的に分散され、その所在はチャネルごとのポインタと大きさの組で表される。対して通常のRDMAバッファは連続した1つの領域であり、配置が一致しない。HAWKは対象テンソルの配置に沿い、メモリチャネルごとに連続したRDMAバッファを1つずつ割り当てるためのドライバ支援を用意する。各バッファのDMA対応付け、チャネル数の取得、チャネルごとの先頭アドレスと大きさの取得を担うインタフェースが追加された。この割当により、受信したデータをそのまま対象テンソルとして使えるか、チャネル内の小さな移動だけで済み、チャネルをまたぐ組み替えが不要になる。同時に、連続バッファで起きたチャネル間の使用量の偏りと、それによる割当失敗も防げる。バッファの数はチャネル数で抑えられ、評価対象では8チャネル程度であるため、バッファ管理と転送要求の増加は単一バッファ方式と比べて小さいと論文は見積もる。減るボトルネックは受信後の配置変換と断片化であり、追加費用は複数バッファの管理である。

### 3. 転送を意識したテンソル変換 — 変換を2段に分けて転送を大きく保つ

GPU側のテンソルをNPUの配置へ完全に合わせる作業を、HAWKは2段に分ける。第1段はGPU側の部分変換で、テンソルの次元と要素を並べ替えて対象配置へ近づけ、同じチャネル別バッファ行きの部分を連続にまとめる。変換後の形は、チャネル数、残りの要素数、NPUのタイル大きさで表される3次元として扱われ、結果は連続したGPU側RDMAバッファへ置かれる。第2段は転送そのもので、GPUバッファの各連続部分を対応するチャネル別バッファへ送ることで、残りの配置合わせが転送の中で完了する。代替案として、要素の小さな断片ごとに宛先を対応づけて転送中に全変換を行う方法もあるが、論文の試算では64入力トークンぶんの20メガバイトのKVでも256バイト刻みでは約8万回の転送要求になり、手続きの費用で効率が崩れる。部分変換を帯域に余裕のあるプリフィル側へ寄せ、転送を少数回の大きな転送に保つことが、この分割の効く理由である。実測では、変換の遅延は転送量2560メガバイトで7.44ミリ秒、エンドツーエンド遅延に占める割合は1.71パーセントであり、転送量が増えるほど割合は下がる。

## 評価

### まず見るところ

結論は、異種転送の追加費用は大きな転送ではほぼ消え、残る性能差は転送ではなくデコード側デバイスの実行性能の差だということである。転送量2560メガバイトで、HAWKを使う異種構成のエンドツーエンド転送遅延はGPU同士の直接転送と0.39パーセントしか違わず、転送パイプライン部分だけでは0.25パーセント差だった。オンラインでは、チャットボット型と要約型の両ワークロードで、90パーセントのサービス品質目標達成を維持できるリクエストレートがGPU同士の構成に数パーセント差まで迫る。一方で効率の利得は明確で、電力効率はチャットボット型で1.26倍、要約型で1.15倍、コスト効率は2.03倍と1.88倍である。読み方として、効率の数値は価格と電力の測り方に依存する参考値であり、論文も価格変動を理由にコスト効率は参考と位置づける。デコード側をH100へ替えた追加比較では、電力効率の利得は1.04倍まで縮むが、コスト効率は3.46倍に広がる。利得の大きさはデバイスの組み合わせ次第である。

### 評価上の制約

- 対象モデルは、NPU基盤がモデルとデバイス数の組を強く固定するため、Llama 3.1 70Bの1種類に限られる
- 電力はデバイスの半導体部分の消費を基準とし、GPU側は実測と電力シミュレータの推定を組み合わせる。基板全体や相互接続の電力は含まない
- コストは時点の市場価格と公式価格に基づく参考値であり、変動の影響を受ける
- 転送の利得は転送量が大きいほど大きく、短い入力では変換と要求処理の固定費の割合が残る

## 既存研究との差

プリフィル・デコード分離の先行研究は、資源の割り当て、配置、スケジューリング、KV管理を主にGPUの世界の中で最適化してきた。異種統合の研究も、GPUとCPU、GPUとNPU、NPUとメモリ内計算の組み合わせを扱うが、複数ノードにまたがるGPUとNPUの協調と、その間のテンソル転送を実機で成立させた例はなかった。本論文は、転送を共通RDMA基盤の上で直接化する点と、配置の不一致を転送前の部分変換と受信側のチャネル別バッファへ分解して転送中に吸収する点で異なる。転送エンジン自体は既存のMooncakeを使い、新規性は異種デバイスのメモリをRDMAへ公開するドライバ支援と、配置を意識したバッファと変換の組み合わせにある。

## 限界・実装状況

評価は1種類のNPU基盤と1モデルに限られる。NPU側のソフトウエア基盤がモデルとデバイス数の組を固定しているためであり、他のモデルや他のNPUアーキテクチャへの一般化は、配置対応のバッファ割当をデバイスごとに直すことで適応可能という設計上の議論にとどまる。NPU基盤をvLLMへ統合するプラグインの追加費用がデコード性能へ含まれており、独立実行より不利な条件で測られている。電力の比較は半導体部分の消費に基づく推定を含み、基板全体の消費では差が変わりうる。コスト効率は価格前提への依存が大きい。要約型ではNPU側デコードの遅さがプリフィル側の滞留を招き、最初のトークンまでの時間の差が広がる場面も報告されている。実装はオープンソースとして公開予定と述べられるが、一次資料中に公開先は示されていない。

## 一般的な実装上の含意

異種デバイスを組み合わせる際の障壁は、計算性能の差よりも、データの置き方と運び方の不一致であることが多い。本論文の分解は再利用できる。すなわち、変換を一括で行わず、送信側で安くできる部分変換と、転送の宛先配置で自然にそろう部分へ分け、転送は少数回の大きな単位に保つ。また、受信側のバッファは相手の都合ではなく自デバイスのテンソル配置に沿って割り当てることで、受信後の組み替えとメモリの偏りを同時に避けられる。効率の主張を検証する際は、転送量の小さい条件で固定費がどう残るかと、電力の測定範囲がどこまでかを確認することが読み方の要点になる。
