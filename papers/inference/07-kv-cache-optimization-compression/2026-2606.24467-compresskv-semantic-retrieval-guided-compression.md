# CompressKV: Semantic-Retrieval-Guided KV-Cache Compression for Resource-Efficient Long-Context LLM Inference

> 全attention headのscoreを一律に混ぜず、長contextから意味的に重要な証拠を拾うheadを使ってtokenを選び、layerごとの圧縮耐性にも応じてKV容量を配る。

## 問題設定

GQA modelのKV cacheを削る際、全headのattention scoreを同等に集約すると、局所patternを見るheadと長距離の意味検索を担うheadが混ざり、重要な中間contextを落とすことがある。また全layerへ同じcache budgetを割り当てると、圧縮に敏感なlayerと冗長なlayerの差を使えない。

## 手法

### 1. Semantic Retrieval Headを特定する

CompressKVはprompt先頭・末尾だけでなく、中間にある意味的に重要な証拠を検索できるattention headをSemantic Retrieval Head（SRH）として特定する。token保持判定では全headを平均せず、SRHが高く評価するtokenのKVを優先する。

### 2. Layerごとの圧縮誤差でbudgetを変える

offlineでfull cache時とcompressed cache時のattention output差を測り、圧縮による誤差が大きいlayerへ多く、耐性が高いlayerへ少ないKV budgetを配る。online inference中に毎回最適化するのではなく、事前測定結果を使うためruntime overheadを抑える。

### 3. Head選択とlayer配分を組み合わせる

「どのtokenを残すか」をSRHで決め、「各layerに何token分を残せるか」をerror-aware allocationで決める二段構成により、同じ総KV容量でも重要情報へbudgetを集中する。

## 評価

Llama-3.1-8B-Instruct、Mistral-7B-Instruct-v0.3、Qwen2.5-14B/32B-Instruct等のGQA modelをLongBenchとNeedle-in-a-Haystackで評価する。

- LongBench QAでfull-cache性能の **97%以上をKV容量3%** で維持。
- Needle-in-a-Haystackで **KV容量0.7%で90% accuracy** を報告。
- StreamingLLM、SnapKV、PyramidKV、CAKE、HeadKV、AdaKV等と同一budgetで比較し、複数条件で高い品質を示す。

これらは主にaccuracy / task score対KV容量の結果であり、serving throughputの直接的な倍率ではない。

## 既存研究との差

SnapKV等のtoken evictionに対し、CompressKVは**意味検索を担うheadの役割差**をtoken selectionへ明示的に使う。またuniform layer budgetではなく、full/compressed attention output差からlayerごとの圧縮耐性を測って容量を変える。

SGD-KVもheadの機能差をbudgetへ使うが、SGD-KVはsummarization能力からhead間budgetを配るのに対し、CompressKVはsemantic retrieval headによるtoken selectionとlayer-level error allocationを組み合わせる。

## 限界

- 主対象はGQA-based LLMで、MHA/MLAへ同じhead判定がそのまま最適とは限らない。
- offline calibrationで得たlayer sensitivityがdomain変化後も最適とは限らない。
- KV evictionを含むためexact attentionではなく、極端なbudgetではtask品質低下があり得る。
- 主評価は品質対memory budgetで、production servingのP99 latencyやthroughput改善は別途runtime統合が必要。
- arXivにはarXiv:2508.02401とのsubstantial text overlapに関するadmin noteがあるため、独立性の解釈には注意が必要。

## 一般的な実装上の含意

KV圧縮ではattention scoreを全headで一律集約するより、**headが担う機能を先に識別してselectionへ使う**余地がある。またcache managerがlayer別budgetを扱えると、圧縮に敏感なlayerを保護しつつ総memoryを下げられる。
