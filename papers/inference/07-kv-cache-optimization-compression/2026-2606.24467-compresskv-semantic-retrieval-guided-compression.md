# CompressKV: Semantic-Retrieval-Guided KV-Cache Compression for Resource-Efficient Long-Context LLM Inference

> CompressKVは、長contextのKVキャッシュ（KV cache）を減らすとき、**全attention headを同じ投票者として扱わない**。長距離の意味的証拠を実際に検索できるheadだけをtoken選択へ使い、さらに「KVを削ると出力が崩れやすいlayer」へ多くのcache budgetを配ることで、同じ総容量でも重要情報を残しやすくする。

## 概要

Transformerは生成済みtokenのkey/valueをKV cacheへ保存することで、次tokenを作るたびに過去tokenを最初から再計算する必要をなくしている。

一方、KV cacheはcontext長にほぼ比例して増える。

長contextでは、

- GPU memoryを圧迫してbatch sizeを制限する
- decodeのたびに大量KVをHBMから読む

という容量・帯域の両方の問題になる。

そこで多数の研究が、過去tokenのうち「今後あまり重要でなさそうなKV」を削除するKV evictionを提案してきた。

典型的には最近のattention scoreを使い、scoreが高いtokenを残す。

しかしGrouped Query Attention（GQA）modelでは、複数のquery headが同じKV headを共有している一方、**query headごとの役割は同じではない**。

あるheadは直近tokenや構文的patternを強く見る。別のheadはprompt先頭のinstructionを見る。さらに別のheadは長い文書の中間に埋まった意味的証拠を検索する。

これら全headのattention scoreを単純平均すると、

**「多くのheadが少し見るtoken」**

が、

**「semantic retrievalを担当する少数headが非常に強く見る重要token」**

を上回ることがある。

その結果、質問への回答に必要な中間contextをKV cacheから捨ててしまう。

CompressKVは、この問題を2段階に分ける。

1. **どのtokenを残すか**：意味検索能力の高いheadだけを使って決める。
2. **各layerに何token分残すか**：layerごとの圧縮感度に応じて変える。

つまり「token selection」と「layer budget allocation」を分離し、それぞれに適したsignalを使う。

## 問題設定

### Attention headは同じ仕事をしていない

GQAでは1つのKV headを複数query headが共有する。

memory上はまとめられているが、query headのattention patternまで同じになるわけではない。

例えば長文QAで、

- head A: 直前32 tokenを中心に見る
- head B: BOS / instructionをよく見る
- head C: 文書中間の質問関連sentenceを探す

といった機能分化が起こり得る。

全head平均でtoken scoreを作ると、Cの「その証拠は重要」というsignalがA/Bの大量の局所attentionに埋もれる。

CompressKVが解こうとするのは、単に「よりよいattention score式」を作ることではない。

**重要tokenを判定する仕事に向いたheadを先に選び、そのheadのsignalだけを使う**ことが中心である。

### Prompt先頭と末尾だけ残せばよいわけではない

長context modelには、

- 先頭tokenを強く見るattention sink
- 最近のtokenを強く見るrecency bias

がある。

そのため「先頭と末尾を残す」heuristicはある程度効く。

しかしNeedle-in-a-Haystackやlong-context QAで本当に難しいのは、**文書中間のどこかにある意味的証拠を残せるか**である。

CompressKVのSemantic Retrieval Head（SRH）は、単に先頭・末尾へattentionするheadではなく、中間のrelevant evidenceとその周辺semantic contextまで拾えるheadを対象にする。

### Layerも同じ圧縮耐性ではない

もう一つの問題は、全layerへ同じtoken budgetを与えるuniform allocationである。

例えば総KV budgetをfull cacheの10%にするとき、全32 layerを一律10%へ削るのは単純だが、

- layer 5は10%でもほぼ出力が変わらない
- layer 18は10%まで削るとattention outputが大きく変わる

可能性がある。

その場合、layer 5をさらに削り、浮いたbudgetをlayer 18へ渡す方が同じ総memoryで品質を保ちやすい。

CompressKVはこのlayer sensitivityも利用する。

## 手法のあらまし

CompressKVはoffline calibrationとonline evictionに分かれる。

### Offline

1. calibration promptをfull KV cacheで実行する。
2. 各layer / attention headがどのtokenを参照するかを観察する。
3. prompt先頭・末尾だけでなく、中間のsemantic evidenceを正しくretrievalできるheadをSemantic Retrieval Headとして選ぶ。
4. layerごとにKVを圧縮した場合のattention output errorを測る。
5. errorが大きいlayerはcompression-sensitive、小さいlayerはcompression-tolerantと判定する。
6. 総KV budgetをlayer sensitivityに応じて配分する。

### Online

1. 各layerに割り当てられたKV budgetを受け取る。
2. そのlayerのSRHが高く評価するtokenを重要候補にする。
3. budget内に収まるtokenだけKVを保持し、残りをevictする。
4. decodeでは圧縮後のKV cacheを通常attentionへ使う。

online中に複雑なoptimizationを毎step解くのではなく、head選択とlayer sensitivityはofflineで準備するためruntime overheadを抑える。

## 手法

### 1. Semantic Retrieval Headを「機能」で選ぶ

CompressKVはheadを単に平均attention magnitudeやentropyでrank付けするのではない。

必要なのは、長contextから**意味的に必要なtokenをretrievalする能力**である。

SRH候補には、

- promptの初期情報を拾える
- prompt終端付近の最新情報も扱える
- 文書中間のrelevant evidenceを見つけられる
- evidence tokenだけでなく、その周辺のsemantic contextも見る

という性質を求める。

この考え方が重要なのは、長文QAでは答えtokenそのものだけ残しても不十分だからである。

例えば「Aliceが会社を辞めた理由」を答えるには、`resigned`という1 tokenだけでなく、その前後の原因説明も必要になる。

semantic retrieval headが周辺contextまで高く評価するなら、意味のまとまりをKVとして残しやすい。

### 2. SRHだけでtoken importanceを決める

SRHを特定した後、token eviction時には全query headのscoreを均等に平均しない。

SRHが高いattentionを与えるtokenを優先する。

これによりlocal / positionalな役割を持つ多数headが、少数のretrieval headのsignalを希釈することを防ぐ。

重要なのは、**非SRHをmodel実行から削除するわけではない**ことである。

非SRHもattention計算自体には通常通り存在する。

SRHを使うのは「どの過去KV tokenをcacheへ残すか」というmemory-management decisionだけである。

### 3. GQAではquery-headの判断を共有KV tokenへ反映する

GQAでは複数query headが同一KV headを共有するため、cache evictionの物理単位とquery-headの機能単位が一致しない。

CompressKVはSRHのsignalから、その共有KV entryを残す価値を決める。

つまり「headごとに別KV copyを持つ」のではなく、**retrieval能力の高いquery headをselectorとして利用し、共有KV cacheのtoken単位decisionへ落とす**。

これがGQA向け設計である理由である。

### 4. Layer-wise eviction errorを測る

次に「各layerへいくつKV tokenを残すか」を決める。

CompressKVはlayer `l`について、

- full KV cacheで得たattention output
- そのlayerのKVを圧縮したときのattention output

を比較する。

差が大きいlayerは、token evictionによってmodel内部表現が大きく変わるためcompression-sensitiveとみなす。

差が小さいlayerは、同じ割合を削っても内部表現への影響が小さいためbudgetを削りやすい。

ここで測っているのはtask accuracyそのものではなく、**そのlayerのattention演算がKV evictionでどれだけ変形するかという局所的なproxy error**である。

### 5. 同じ総budgetをlayer間で再配分する

総KV budgetを`B`としたとき、uniform方式なら各layerへほぼ同率で配る。

CompressKVは、

- errorが大きいlayer → 多め
- errorが小さいlayer → 少なめ

とする。

したがって総KV容量が同じでも、modelが圧縮に弱い箇所を保護できる。

これはHeadKV / AdaKVのような**head間adaptive budget**とは階層が異なる。

CompressKVは主に、

- head機能差 → token selection
- layer感度差 → layer budget

へ使い分ける。

### 6. Offline calibrationにする理由

layer sensitivityをdecode stepごとに測り直すと、そのためにfull-cache相当の計算や比較が必要になり、圧縮で得たい速度を失う。

そこでhead identityとlayer sensitivityはoffline calibrationで求める。

runtimeでは既に決まったSRHとlayer budgetを使ってtoken selectionするだけにする。

この設計はruntime overheadを小さくする一方、**calibration domainとdeployment domainが違うと最適性が落ちる**というtrade-offを持つ。

## 評価

### まず見るところ

- **LongBench QA:** full KV cacheのわずか **3%** の容量でfull-cache性能の **97%以上** を維持。
- **Needle-in-a-Haystack:** **0.7% KV storageで90% retrieval accuracy**。
- **比較:** StreamingLLM、SnapKV、PyramidKV、CAKE、HeadKV、AdaKVなどより同budgetで高いqualityを報告。
- **性質:** memory-quality trade-offの研究であり、headlineは直接のtokens/s speedupではない。
- **近似:** token evictionを行うためlosslessではない。

### 3%で97%以上、の意味

「KVを97%削ると推論が33倍速くなる」という意味ではない。

示しているのは、**保存するKV entry数をfull cacheの3%まで減らしても、LongBench QA scoreがfull-cache scoreの97%以上残った**というquality-memory resultである。

実際のdecode latencyは、

- compression / eviction kernel overhead
- attention implementationが圧縮後lengthをどこまで活用できるか
- batch size
- GPU architecture

に依存する。

したがってproduction throughput倍率は別評価が必要である。

### 0.7%で90% Needle accuracy、の意味

Needle taskでは極端な圧縮時にも中間contextのrelevant evidenceを残せるかが重要になる。

SRHを使う狙いはまさにここで、単純なrecency / attention sink保存だけでは落ちやすい中間tokenを優先できる。

ただし90%はfull-cacheと同一ではない。約10%のfailureが残る条件であり、lossless retrievalではない。

### Baselineとの比較軸

| 系統 | 主な考え方 |
|---|---|
| StreamingLLM | attention sink + recent window |
| SnapKV | observation windowのattentionから重要tokenを選ぶ |
| PyramidKV | layer間でbudget形状を変える |
| HeadKV / AdaKV | headごとに異なるbudgetを割り当てる |
| CompressKV | semantic retrieval headでtoken選択 + layer eviction errorでlayer budget配分 |

CompressKVは「新しいtoken scoreを1個作った」というより、**どのheadにtoken選択を任せるかと、どのlayerへcapacityを割くかを分けた**点が特徴である。

## 既存研究との差

### SnapKVとの違い

SnapKVは最近のobservation windowから過去tokenへのattentionを集計し、重要tokenを残す。

CompressKVは「どのheadのattentionを重要度signalに使うか」自体を選ぶ。

全head平均がsemantic signalを薄めることを問題視する点が異なる。

### AdaKV / HeadKVとの違い

これらはattention headごとにbudgetを変える。

CompressKVはSRHをtoken selectorとして使いつつ、capacity allocationのもう一つの軸として**layer-level sensitivity**を使う。

したがってhead-awareであるが、単純なhead-wise budget allocationと同じではない。

### PyramidKVとの違い

PyramidKVもlayerごとに異なるcache budgetを使うが、CompressKVは実際にfull/compressed attention outputの差を測り、そのlayerがevictionにどれだけ敏感かをallocation signalにする。

## 限界

- KV evictionを伴うためexact attentionではない。
- 主対象はGQA modelで、MHA / MLAへ同じSRH定義をそのまま適用できるとは限らない。
- head機能とlayer sensitivityはoffline calibrationに依存する。
- deployment domainがcalibration dataと大きく異なる場合、retrieval headの役割やlayer sensitivityが変わる可能性がある。
- taskによっては「semantic retrieval」以外のhead機能が重要であり、SRH中心のselectionが常に最適とは限らない。
- 3% / 0.7%はquality-memoryの結果であり、production P99 latencyやthroughputの同倍率改善を意味しない。
- 圧縮後の短いKVを実際のattention kernelが効率よく処理できなければ、memory削減がwall-clock速度へ十分つながらない場合がある。

## 一般的な実装上の含意

CompressKVの重要な示唆は、KV cache managerがattentionを単なるscore generatorとして見るのではなく、**headの機能差をmetadataとして使える**ことである。

同じattention scoreでも、

- local syntaxを追うhead
- instructionを保持するhead
- long-range evidenceをretrievalするhead

ではcache management上の意味が違う。

さらに、圧縮予算はtoken方向だけでなくlayer方向にも再配分できる。

したがってKV compression systemを作るときは、

1. 誰がtoken importanceを判定するか
2. その判定をどの物理KV単位へ落とすか
3. layer / head / request間でbudgetをどう分けるか
4. quality proxyがdeployment taskでも安定するか

を分離して設計する価値がある。
