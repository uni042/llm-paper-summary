# CompressKV: Semantic-Retrieval-Guided KV-Cache Compression for Resource-Efficient Long-Context LLM Inference

> CompressKVは、長文脈のKVキャッシュ（KV キャッシュ）を減らすとき、**全注意機構 ヘッドを同じ投票者として扱わない**。長距離の意味的証拠を実際に検索できるヘッドだけをトークン選択へ使い、さらに「KVを削ると出力が崩れやすい層」へ多くのキャッシュ budgetを配ることで、同じ総容量でも重要情報を残しやすくする。

## 概要

Transformerは生成済みトークンのkey/値をKV キャッシュへ保存することで、次トークンを作るたびに過去トークンを最初から再計算する必要をなくしている。

一方、KV キャッシュは文脈長にほぼ比例して増える。

長文脈では、

- GPU メモリを圧迫してバッチサイズを制限する
- デコードのたびに大量KVをHBMから読む

という容量・帯域の両方の問題になる。

そこで多数の研究が、過去トークンのうち「今後あまり重要でなさそうなKV」を削除するKV 追い出しを提案してきた。

典型的には最近の注意機構 スコアを使い、スコアが高いトークンを残す。

しかしGrouped クエリ 注意機構（GQA）モデルでは、複数のクエリ ヘッドが同じKV ヘッドを共有している一方、**クエリ ヘッドごとの役割は同じではない**。

あるヘッドは直近トークンや構文的パターンを強く見る。別のヘッドはプロンプト先頭のinstructionを見る。さらに別のヘッドは長い文書の中間に埋まった意味的証拠を検索する。

これら全ヘッドの注意機構 スコアを単純平均すると、

**「多くのヘッドが少し見るトークン」**

が、

**「意味的 retrievalを担当する少数ヘッドが非常に強く見る重要トークン」**

を上回ることがある。

その結果、質問への回答に必要な中間文脈をKV キャッシュから捨ててしまう。

CompressKVは、この問題を2段階に分ける。

1. **どのトークンを残すか**：意味検索能力の高いヘッドだけを使って決める。
2. **各層に何トークン分残すか**：層ごとの圧縮感度に応じて変える。

つまり「トークン 選択」と「層 budget 配分」を分離し、それぞれに適した信号を使う。

## 問題設定

### Attention headは同じ仕事をしていない

GQAでは1つのKV ヘッドを複数クエリ ヘッドが共有する。

メモリ上はまとめられているが、クエリ ヘッドの注意機構 パターンまで同じになるわけではない。

例えば長文QAで、

- ヘッド A: 直前32 トークンを中心に見る
- ヘッド B: BOS / instructionをよく見る
- ヘッド C: 文書中間の質問関連sentenceを探す

といった機能分化が起こり得る。

全ヘッド平均でトークン スコアを作ると、Cの「その証拠は重要」という信号がA/Bの大量の局所注意機構に埋もれる。

CompressKVが解こうとするのは、単に「よりよい注意機構 スコア式」を作ることではない。

**重要トークンを判定する仕事に向いたヘッドを先に選び、そのヘッドの信号だけを使う**ことが中心である。

### Prompt先頭と末尾だけ残せばよいわけではない

長文脈 モデルには、

- 先頭トークンを強く見る注意機構 sink
- 最近のトークンを強く見るrecency bias

がある。

そのため「先頭と末尾を残す」heuristicはある程度効く。

しかしNeedle-in-a-Haystackや長い-文脈 QAで本当に難しいのは、**文書中間のどこかにある意味的証拠を残せるか**である。

CompressKVの意味的 Retrieval ヘッド（SRH）は、単に先頭・末尾へ注意機構するヘッドではなく、中間のrelevant evidenceとその周辺意味的 文脈まで拾えるヘッドを対象にする。

### Layerも同じ圧縮耐性ではない

もう一つの問題は、全層へ同じトークン budgetを与える均一な 配分である。

例えば総KV budgetをfull キャッシュの10%にするとき、全32 層を一律10%へ削るのは単純だが、

- 層 5は10%でもほぼ出力が変わらない
- 層 18は10%まで削ると注意機構 出力が大きく変わる

可能性がある。

その場合、層 5をさらに削り、浮いたbudgetを層 18へ渡す方が同じ総メモリで品質を保ちやすい。

CompressKVはこの層 感度も利用する。

## 手法

CompressKVはオフライン calibrationとオンライン 追い出しに分かれる。

### Offline

1. calibration プロンプトをfull KV キャッシュで実行する。
2. 各層 / 注意機構 ヘッドがどのトークンを参照するかを観察する。
3. プロンプト先頭・末尾だけでなく、中間の意味的 evidenceを正しくretrievalできるヘッドを意味的 Retrieval ヘッドとして選ぶ。
4. 層ごとにKVを圧縮した場合の注意機構 出力 errorを測る。
5. errorが大きい層は圧縮-敏感な、小さい層は圧縮-tolerantと判定する。
6. 総KV budgetを層 感度に応じて配分する。

### Online

1. 各層に割り当てられたKV budgetを受け取る。
2. その層のSRHが高く評価するトークンを重要候補にする。
3. budget内に収まるトークンだけKVを保持し、残りを追い出すする。
4. デコードでは圧縮後のKV キャッシュを通常注意機構へ使う。

オンライン中に複雑なoptimizationを毎ステップ解くのではなく、ヘッド選択と層 感度はオフラインで準備するため実行時 オーバーヘッドを抑える。

## 手法

### 1. Semantic Retrieval Headを「機能」で選ぶ

CompressKVはヘッドを単に平均注意機構 magnitudeやentropyでrank付けするのではない。

必要なのは、長文脈から**意味的に必要なトークンをretrievalする能力**である。

SRH候補には、

- プロンプトの初期情報を拾える
- プロンプト終端付近の最新情報も扱える
- 文書中間のrelevant evidenceを見つけられる
- evidence トークンだけでなく、その周辺の意味的 文脈も見る

という性質を求める。

この考え方が重要なのは、長文QAでは答えトークンそのものだけ残しても不十分だからである。

例えば「Aliceが会社を辞めた理由」を答えるには、`resigned`という1 トークンだけでなく、その前後の原因説明も必要になる。

意味的 retrieval ヘッドが周辺文脈まで高く評価するなら、意味のまとまりをKVとして残しやすい。

### 2. SRHだけでtoken importanceを決める

SRHを特定した後、トークン 追い出し時には全クエリ ヘッドのスコアを均等に平均しない。

SRHが高い注意機構を与えるトークンを優先する。

これにより局所 / positionalな役割を持つ多数ヘッドが、少数のretrieval ヘッドの信号を希釈することを防ぐ。

重要なのは、**非SRHをモデル実行から削除するわけではない**ことである。

非SRHも注意機構計算自体には通常通り存在する。

SRHを使うのは「どの過去KV トークンをキャッシュへ残すか」というメモリ-management decisionだけである。

### 3. GQAではquery-headの判断を共有KV tokenへ反映する

GQAでは複数クエリ ヘッドが同一KV ヘッドを共有するため、キャッシュ 追い出しの物理単位とクエリ-ヘッドの機能単位が一致しない。

CompressKVはSRHの信号から、その共有KV entryを残す価値を決める。

つまり「ヘッドごとに別KV copyを持つ」のではなく、**retrieval能力の高いクエリ ヘッドをselectorとして利用し、共有KV キャッシュのトークン単位decisionへ落とす**。

これがGQA向け設計である理由である。

### 4. Layer-wise eviction errorを測る

次に「各層へいくつKV トークンを残すか」を決める。

CompressKVは層 `l`について、

- full KV キャッシュで得た注意機構 出力
- その層のKVを圧縮したときの注意機構 出力

を比較する。

差が大きい層は、トークン 追い出しによってモデル内部表現が大きく変わるため圧縮-敏感なとみなす。

差が小さい層は、同じ割合を削っても内部表現への影響が小さいためbudgetを削りやすい。

ここで測っているのはタスク 正確性そのものではなく、**その層の注意機構演算がKV 追い出しでどれだけ変形するかという局所的なproxy error**である。

### 5. 同じ総budgetをlayer間で再配分する

総KV budgetを`B`としたとき、均一な方式なら各層へほぼ同率で配る。

CompressKVは、

- errorが大きい層 → 多め
- errorが小さい層 → 少なめ

とする。

したがって総KV容量が同じでも、モデルが圧縮に弱い箇所を保護できる。

これはHeadKV / AdaKVのような**ヘッド間適応型 budget**とは階層が異なる。

CompressKVは主に、

- ヘッド機能差 → トークン 選択
- 層感度差 → 層 budget

へ使い分ける。

### 6. Offline calibrationにする理由

層 感度をデコード ステップごとに測り直すと、そのために完全キャッシュ相当の計算や比較が必要になり、圧縮で得たい速度を失う。

そこでヘッド identityと層 感度はオフライン calibrationで求める。

実行時では既に決まったSRHと層 budgetを使ってトークン 選択するだけにする。

この設計は実行時 オーバーヘッドを小さくする一方、**calibration domainとdeployment domainが違うと最適性が落ちる**というトレードオフを持つ。

## 評価

### まず見るところ

- **LongBench QA:** full KV キャッシュのわずか **3%** の容量で完全キャッシュ性能の **97%以上** を維持。
- **Needle-in-a-Haystack:** **0.7% KV storageで90% retrieval 正確性**。
- **比較:** StreamingLLM、SnapKV、PyramidKV、CAKE、HeadKV、AdaKVなどより同budgetで高い品質を報告。
- **性質:** メモリ-品質 トレードオフの研究であり、headlineは直接のトークン/s 高速化倍率ではない。
- **近似:** トークン 追い出しを行うため無損失ではない。

### 3%で97%以上、の意味

「KVを97%削ると推論が33倍速くなる」という意味ではない。

示しているのは、**保存するKV entry数をfull キャッシュの3%まで減らしても、LongBench QA スコアが完全キャッシュ スコアの97%以上残った**という品質-メモリ 結果である。

実際のデコード 遅延は、

- 圧縮 / 追い出し カーネル オーバーヘッド
- 注意機構 実装が圧縮後lengthをどこまで活用できるか
- バッチサイズ
- GPU 構成

に依存する。

したがってproduction スループット倍率は別評価が必要である。

### 0.7%で90% Needle accuracy、の意味

Needle タスクでは極端な圧縮時にも中間文脈のrelevant evidenceを残せるかが重要になる。

SRHを使う狙いはまさにここで、単純なrecency / 注意機構 sink保存だけでは落ちやすい中間トークンを優先できる。

ただし90%は完全キャッシュと同一ではない。約10%のfailureが残る条件であり、無損失 retrievalではない。

### Baselineとの比較軸

| 系統 | 主な考え方 |
|---|---|
| StreamingLLM | attention sink + recent window |
| SnapKV | observation windowのattentionから重要tokenを選ぶ |
| PyramidKV | layer間でbudget形状を変える |
| HeadKV / AdaKV | headごとに異なるbudgetを割り当てる |
| CompressKV | semantic retrieval headでtoken選択 + layer eviction errorでlayer budget配分 |

CompressKVは「新しいトークン スコアを1個作った」というより、**どのヘッドにトークン選択を任せるかと、どの層へ容量を割くかを分けた**点が特徴である。

## 既存研究との差

### SnapKVとの違い

SnapKVは最近のobservation 区間から過去トークンへの注意機構を集計し、重要トークンを残す。

CompressKVは「どのヘッドの注意機構を重要度信号に使うか」自体を選ぶ。

全ヘッド平均が意味的 信号を薄めることを問題視する点が異なる。

### AdaKV / HeadKVとの違い

これらは注意機構 ヘッドごとにbudgetを変える。

CompressKVはSRHをトークン selectorとして使いつつ、容量 配分のもう一つの軸として**層-水準 感度**を使う。

したがってヘッド-awareであるが、単純なヘッド-wise budget 配分と同じではない。

### PyramidKVとの違い

PyramidKVも層ごとに異なるキャッシュ budgetを使うが、CompressKVは実際にfull/圧縮済み 注意機構 出力の差を測り、その層が追い出しにどれだけ敏感かを配分 信号にする。

## 限界

- KV 追い出しを伴うため厳密な 注意機構ではない。
- 主対象はGQA モデルで、MHA / MLAへ同じSRH定義をそのまま適用できるとは限らない。
- ヘッド機能と層 感度はオフライン calibrationに依存する。
- deployment domainがcalibration データと大きく異なる場合、retrieval ヘッドの役割や層 感度が変わる可能性がある。
- タスクによっては「意味的 retrieval」以外のヘッド機能が重要であり、SRH中心の選択が常に最適とは限らない。
- 3% / 0.7%は品質-メモリの結果であり、production P99 遅延やスループットの同倍率改善を意味しない。
- 圧縮後の短いKVを実際の注意機構 カーネルが効率よく処理できなければ、メモリ削減が実時間速度へ十分つながらない場合がある。
- arXiv metadataには先行版 arXiv:2508.02401 とのsubstantial text overlapに関するadmin noteがあるため、文献管理では両versionの関係を確認して扱う必要がある。

## 一般的な実装上の含意

CompressKVの重要な示唆は、KV キャッシュ managerが注意機構を単なるスコア generatorとして見るのではなく、**ヘッドの機能差をmetadataとして使える**ことである。

同じ注意機構 スコアでも、

- 局所 syntaxを追うヘッド
- instructionを保持するヘッド
- 長い-range evidenceをretrievalするヘッド

ではキャッシュ management上の意味が違う。

さらに、圧縮予算はトークン方向だけでなく層方向にも再配分できる。

したがってKV 圧縮 システムを作るときは、

1. 誰がトークン importanceを判定するか
2. その判定をどの物理KV単位へ落とすか
3. 層 / ヘッド / リクエスト間でbudgetをどう分けるか
4. 品質 proxyがdeployment タスクでも安定するか

を分離して設計する価値がある。
