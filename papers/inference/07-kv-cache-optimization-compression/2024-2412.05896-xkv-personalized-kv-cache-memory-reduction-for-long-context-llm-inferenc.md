# XKV：層ごとの注意重要度を測ってKVキャッシュ予算を再配分する

## 概要

長文脈LLMのKVキャッシュは、入力が長くなるほどGPUメモリを消費する。トークンの重要度に基づいて一部のKVを捨てる方式はあるが、各Transformer層へ同じ容量を割り当てたり、層位置に応じてあらかじめ決めたピラミッド形の容量を割り当てたりすると、入力とタスクごとに変わる重要度分布を捉えきれない。XKVはこの層間の分布差をDynamic Differences of Importance Distribution（DDID）と呼び、保持したトークンの注意質量に基づいて層ごとのKV容量を選ぶ。

推論を**mini-prefill → 本来のprefill → 自己回帰生成**に分け、mini-prefillで各層の注意行列からトークン重要度ベクトルを作る。次に、各層へ1枠ずつKVを追加した場合に保持できる重要度が最も増える層を選ぶ貪欲アルゴリズムで、層別の容量配分表を求める。本来のprefillでこの表に従って各層のKVをtop-k保持し、生成では残ったKVを使用する。低遅延運用では同種タスクの一部をサンプリングして配分表を事前に求め、後続要求で再利用する。

論文のLlama-3-8B-Instruct、LongBench 14データセット、NVIDIA RTX A6000 48GBの評価では、許容する品質低下の範囲で平均KV保持率38.4%（削減61.6%）を報告した。NarrativeQAでは単一要求の処理時間がFullKVの7.18秒から3.40秒へ短縮され、1要求のKV使用量は4.00GBから1.54GB、最大バッチは8から20へ増えた（Table IV）。この速度は全てのモデルや実運用サーバへ一般化できる測定ではない。なおarXivのabstractには最大5.5倍と書かれる一方、PDF本文のabstract・評価節は最大5.2倍と記載しており、数値の不一致を留保する。

## 問題設定と既存方式の限界

自己回帰デコードでは過去のトークンのKeyとValueを保存し、以後のトークンで再利用する。キャッシュを全保持するFullKVは品質基準として分かりやすいが、長い入力を受けたprefill時点でKVが膨らむ。原著Figure 1ではLlama-3.1 8B、バッチ10、入力長1000〜8000でモデル重み側の16GBに対しKVが約5GBから40GBへ増える例を示し、出力開始前にメモリ不足になり得ると説明する。この図は課題を説明する別条件の例であり、後述のLongBench本評価と混同してはならない。

StreamingLLMは先頭のattention sinkと直近トークンを重視し、H2Oは注意の大きいheavy hitterを保持する。SnapKVは入力末尾の観測窓を使い、prefill中から重要な入力トークンを選別する。一方PyramidInferとPyramidKVは層間の違いを考慮するものの、容量形状を事前設定するため、特定タスクで重要な層に十分な枠が回らないことがある。XKVが解こうとするのは、**同じ総KV予算をどの層へ何枠ずつ配るべきか**という全層にまたがる資源配分問題である。

入力末尾の観測窓は、新しく生成するトークンの代理として使用される。prefill中には未来の出力トークンがないため、そのトークンから過去へ向けた注意を測れない。観測窓内の入力末尾トークンが観測窓外のどこを参照しているかを測ることで、生成前に退避の手掛かりを得る。したがって「入力末尾の参照傾向が今後の生成に有用」という仮定に依存する。タスクが変わり注意対象が大きく動く場合、同じ配分を使い続けると性能が落ち得る。

## 手法

### 1. DDIDと保持重要度の定義

各層の注意行列を`W_attn = softmax(QK^T / sqrt(d_k))`とし、観測窓サイズ`ows`を指定する。行列の末尾`ows`行を取り、観測窓外の列について平均し、さらにpoolingすることで層`i`のトークン重要度ベクトル`w_i`を得る（式(2)〜(3)、Figure 8）。このベクトルの大きな要素に対応するトークンは、末尾の観測窓から強く参照されている。元の注意行列をそのまま全保存するのではなく、圧縮したスコアを配分計算へ渡す。

層`i`に`n_i`枠を与えたとき、重要度の上位`n_i`個の和を全重要度の和で割った保持比率`R_i`を考える。`R_i`が高いほど観測窓から見て重要な注意質量を多く残せる。全層の平均`R_avg`を、品質の代替目的関数とする。原著Figure 5は総キャッシュ量を固定して層配分を変えたとき、`R_avg`が増えるほど評価スコアが改善する傾向を示す。ただしこれは実験に基づく代理指標であり、**すべての入力で実際の正答率を数学的に保証する指標ではない**。

層によって`R_i`と`n_i`の関係が異なることがDDIDである。ある層では少量のKVを残すだけで重要度の大半を回収できるが、別の層では同じ枠数では不十分である。Figure 2〜4は層間の注意分布と、同じ保持重要度を得るために必要なKV枠数の違いを示す。均等配分を採用すると、重要度をほとんど増やさない層にメモリを費やし、限られた予算を浪費する可能性がある。

### 2. mini-prefillによる層別重要度の事前計測

本来のprefillに先立ち、入力を使って各層の注意重みを求めるmini-prefillを走らせる。各層で得られた`W_attn`を前述の観測窓選択、平均、poolingへ流し、`w_1 ... w_L`を収集する（Figure 6〜8）。mini-prefillではKVをキャッシュせず、最後の層では必要なattention計算を終えた時点で後続の残差・正規化・FFNを省略する。これは初期のメモリ不足を避けながら必要な統計を収集するための構成であり、**mini-prefillが無料であるわけではない**。

全層のスコアがそろうまで配分を確定できないことが重要である。通常のprefillで現在の層だけを見て退避すると、後続層でより多くの容量を必要とするかを知らないまま予算を消費する。mini-prefillを追加する代わりに全層の情報を先取りし、層横断の最適化を可能にする。計測自体の費用が大きい短い入力や単発要求では、この追加処理が利得を減らす可能性がある。

### 3. 層別KV容量の貪欲配分

原著式(17)は`sum_i n_i = N`という総保持枠数制約の下で`R_avg`を最大化する問題、式(18)は必要な`R_avg`を満たす総枠数を最小化する問題を定義する。両者は同じ層別重要度ベクトルから導けるが、前者は固定メモリ予算で品質を高める設定、後者は品質目標を満たす最小メモリ設定という違いがある。

Algorithm 1は各層の`w_i`を降順に見て、現在の割当`n_i`に次の1枠を足したときの正規化重要度の増分を候補表（wait list）へ保持する。各反復で増分が最大の層を選び、その層の割当表（allocation list）を1増やし、同層の次の候補増分だけを更新する。固定総枠数なら`N`回反復し、保持重要度目標なら`R_avg`が閾値へ届くまで続ける。こうして得た`n_1 ... n_L`を本来のprefillへ渡す。

この貪欲選択が原著の目的関数で最適となるのは、層内の重要度を上位から順に取るという離散構造があるためである。原著は2層の割当から1枠を移す交換論法で説明する（式(19)〜(21)）。この意味での「大域最適」は**固定された重要度ベクトルと代理目的関数に関する最適性**であり、任意の生成品質、GPUレイテンシ、長期的な注意変化に対する無条件の最適性ではない。

### 4. 本来のprefillでの退避と生成への接続

本来のprefillでは層`i`のQ・Kから注意重みを計算し、観測窓の行選択・平均・poolingでトークンスコアを得る。Algorithm 2はそのスコアの上位`n_i`個のインデックスを求め、対応するKeyとValueだけを残す。残りのKVを退避してから次層へ進み、最後にはGPU上に縮小済みの層別キャッシュが残る。自己回帰生成はそのキャッシュを参照して進み、新たに生成したトークンのKVも追加する。

各層で別々のトークン集合が選ばれる点が均等な一括トークン削除と異なる。ある層で捨てたトークンでも、別の層で重要なら保持できる。一方、後の生成で必要になったトークンが既に捨てられている場合は通常の完全KVと同じ注意計算を再現できない。原著はこの品質影響をLongBenchで測るが、削除KVの厳密復元を提案するものではない。

### 5. タスク種別によるサンプリングと遅延対策

毎要求でmini-prefillと容量最適化を行うと、その追加計算がオンライン推論の遅延を増やす。原著Figure 10は同じQA系タスク間で層ごとの配分形状が似ていると観測し、同じ種類の要求を事前にサンプルして各要求の配分を求め、平均配分表を後続要求へ適用する方法を示す。これにより、オフラインの要求単位最適化と、オンラインの配分再利用を使い分ける。

評価設定の既定値は観測窓8、サンプリング比10%、poolingサイズ7、pooling方法は平均である。サンプリング比は「全リクエストでmini-prefillする」方式との違いを理解するために重要だが、オンライン到着率やウォームアップ時間を変えた詳細なサーバ運用評価が示されたわけではない。同一種別の要求で注意分布が変化した場合、事前平均表の有効性は保証されない。

Figure 11は、許容品質低下を固定してどこまで容量を減らせるかを見る。一方Figure 12とTable IIIは、容量を固定したときにどの程度の品質が残るかを測る。この二つを混同すると「61.6%削減した条件でTable IIIの38.27点だった」といった誤った対応づけになる。Table IIIの1.6%や1.2%は**残すKVの比率**であり、削減率ではない。

Table IIIでは、保持率1.6%のときXKVが14データセット中11件で競合方式を上回ると本文が述べる。ただし個別データセットで全勝ではない。例えば1.6%のQAsではPyramidKV 16.82に対しXKV 16.32であり、TrecではPyramidKVとXKVがともに65.00である。保持率1.2%のHPQAではH2O 39.24に対してXKV 38.09、WKQAではSnapKV 28.75に対してXKV 27.78となる。従って平均スコアの優位性を全タスク・全圧縮率での優位と解釈してはいけない。

原著本文の速度評価は、KV退避によって一要求の処理を速める効果と、同GPUで最大バッチを8から20へ増やせる効果の両方を説明する。ただし**abstractの最大スループット5.5倍と、PDF本文の5.2倍は一致しない**。PDF内のTable IV自体は合計時間1436/680=2.11倍を示しており、5.2倍を直接算出する表ではない。最大倍率はバッチ拡大を含む著者の総括として扱い、条件が不明な実機実測値を補ってはならない。

### 負の結果と制約

第一に、保持率を1.6%から1.2%へさらに減らすとXKVの平均スコアは38.27から37.07へ低下する。重要なトークンを削除する近似方式である以上、極端な容量制限下では品質劣化が避けられない。第二に、特定データセットではH2OやPyramidKVがXKVを上回る。平均値だけでは局所的な逆転が隠れるため、実際の用途ではQAの種類や入力分布に応じて確認する必要がある。

第三に、mini-prefillの注意統計収集と貪欲配分には追加処理が必要であり、単発・短入力の遅延には不利となり得る。原著は同種タスクのサンプリングで負担を軽くするが、オンラインでタスク分布が急変したときの再計測頻度、ウォームアップ時間、複数テナントのSLO、GPU間のスケーリングは十分評価されていない。第四に、対象は主にLlama-3-8B-InstructとLongBenchであり、MoEモデル、他の注意構造、量子化KVとの組合せ、FlashAttention実装の差、分散サービングで同じ利得になるとは断定できない。

## 既存研究との差と実装上の示唆

XKVの独自性は、単にKVを上位スコアで捨てることではない。SnapKVも観測窓による重要度計測とtop-k退避を行う。XKVが追加するのは、層別の注意分布差を定量化し、**全層の共通予算を最適化する容量配分**と、その配分のためのmini-prefillである。PyramidKVの層別配分は深さに応じた事前パターンに依存するのに対し、XKVは入力やタスク種別から配分を更新できる。この違いがFigure 11〜12の厳しい圧縮条件での品質差へ結びつく。

一方、GPUメモリ節約がそのまま既存ランタイムの高スループット化へ直結するとは限らない。各層で異なるKV長とトークンインデックスを持つため、PagedAttentionのページ割当、attentionカーネルの不規則アクセス、prefillとdecodeの間のキャッシュ管理に追加の実装が要る。これらはXKVの原著で定量検証された事実ではなく、**既存サービング基盤へ統合する場合の工学的検討事項**として区別する。

小容量GPUでの長文脈推論を考える際には、まず「どの層にどれだけのKV予算を配るか」を考え、次に退避のスコア、再計測費用、品質許容値、バッチ増加効果を個別に評価するという設計指針を与える。特に固定のピラミッド配分で失われるタスク依存性を補えることが、XKVを調べる価値である。ただし原著は単一GPU・単一モデルの実験なので、実用上の採用判断には対象モデルと推論ランタイムでの再現実験が必要である。
