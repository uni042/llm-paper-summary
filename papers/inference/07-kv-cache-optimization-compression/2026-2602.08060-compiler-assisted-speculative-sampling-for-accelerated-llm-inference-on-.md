# 異種エッジSoC上のコンパイラ支援投機的サンプリング

## 概要

LLMの逐次生成では、次のトークンを決めるたびに大型モデルを実行するため、計算資源が限られるエッジ機器では応答遅延が大きくなる。投機的サンプリングは小型草稿モデルが複数の候補トークンを先に生成し、大型検証モデルがまとめて検証することで、大型モデルの呼び出し回数を減らす。しかしエッジSoCでは、CPUとモバイルGPUの速度差、量子化の精度変化、異種デバイス間のランタイム費用が大きいため、単に投機的復号を有効にすれば速くなるとは限らない。

Ruiz y Mesaらは、IREEコンパイラで小型草稿モデルと大型検証モデルを個別にコンパイルし、CPU/GPUへの配置と草稿長を、受理率と順伝播遅延比を用いた解析モデルで選ぶ。NXP i.MX95の6コアCortex-A55とMali-G310を使い、Llama-3.2-1B/3B、投機的復号ベンチマーク翻訳を評価した。高い受理率を仮定する有利な構成では1.68倍の予測速度改善を得るが、半量子化構成の受理率中央値0.17では全構成で投機しない方が有利となる。

論文の価値は最大値だけでなく、どの配置なら投機が有効か、どの条件では実行すべきでないかを同じモデルで説明した点にある。実測は短文翻訳、貪欲復号、KVキャッシュ無効という制約があるため、一般の長文生成・連続バッチング環境にそのまま外挿できない。

## 問題設定

通常の自己回帰復号では検証モデルが1トークンずつ計算する。投機的復号では草稿モデルがγ個の候補を生成し、検証モデルがまとめて検証して受理できる先頭部分を採用する。草稿モデルが十分安く、候補が高確率で受理される場合にのみ、検証モデルの順伝播回数削減が草稿モデルの追加計算を上回る。GPUサーバーでは検証の並列性が利点になりやすいが、モバイルGPUでは演算形式の対応とメモリ容量が制約になる。

CPUコアを増やせば検証モデル側が速くなり、同じ草稿モデルでも相対的な負担が増える。一方、小型GPUで草稿モデルだけを動かすとCPU単独より速くなる構成がある。つまり最適化すべき変数はモデルサイズや受理率だけではなく、草稿モデル/検証モデルのデバイス配置、CPUコア数、草稿長、精度形式、コンパイラが実際に生成するコードの速度である。

本論文は受理率を上げる新しい学習方式を提案するのではない。既存モデルの受理率と順伝播時間を計測し、エッジ上で有利な実行配置を選択する、ハードウェア・コンパイラ協調の設計空間探索である。

## 手法

### 受理率と費用比による解析モデル

著者らは、候補トークンの受理率をα、草稿長をγ、草稿モデルと検証モデルの順伝播時間比をc=t_draft/t_検証モデルと置く。期待速度改善の解析式は次のとおりである。

`S(α,γ,c) = (1−α^(γ+1)) / ((1−α)(γc+1))`

分子は受理されるトークンの期待数に対応し、分母は草稿モデルのγ回の順伝播と検証モデルの検証費用を表す。αが小さいと検証で棄却される候補が増え、cが大きいと候補生成自体が高価になる。適切なγを選んで1倍を超えられるための目安はc<αである。γを長くすれば必ず得をするわけではなく、受理率が低いと余分な草稿の計算だけが増える。

この式は設計探索のための簡略モデルであり、IREEのモジュール境界、CPU/GPU転送、メモリ割当などの実装費用を完全には表現しない。著者らはモデルの予測と実機の結果を別に検証する。したがって、表にある予測値をすべて実測値として扱わない。

### 量子化と受理率の事前測定

Intel Neural Compressorを用いてモデルを静的W8A8量子化し、浮動小数点と部分量子化・全量子化の組合せで受理率を調べる。量子化によって草稿モデルと検証モデルの出力分布が異なると、草稿の採用確率が下がる。これはモデルの重み容量を小さくする最適化が、投機的復号の速度改善をかえって妨げる場合があることを意味する。

受理率は16コアサーバーで投機的復号ベンチマークを使って事前に測定する。投機的復号ベンチマークには13タスク480例が含まれるが、主たる配置・速度評価は短い入出力を持つ翻訳タスクに絞る。翻訳入力の平均長は63トークンである。受理率をエッジでの順伝播費用と組み合わせて使うため、受理率測定と実機速度測定の環境が異なることに注意が必要である。

### IREEでのデバイス別コンパイル

IREE 3.6.0のLLVM CPUバックエンドとSPIR-V GPUバックエンドを用い、草稿モデルと検証モデルの順伝播計算を別々にコンパイルする。CPUコア数とGPUへの配置を変え、それぞれの順伝播遅延を測ってcを求める。小型Mali GPUでは量子化検証モデルをGPUへ置くと8ビット整数演算が直接利用できずFP32へ昇格する制約があり、GPUに配置すれば必ず速いわけではない。

設計には、草稿モデルと検証モデルを単一グラフに統合する単一グラフ方式と、別モジュールとしてコンパイルしてIREE runtime APIで接続する分割モジュール方式がある。前者は境界をまたぐ最適化の余地があるが、IREE 3.6.0の異種デバイス親和性・メモリアロケータの制約により実装できなかった。実験は分割モジュール方式で行われており、モジュール間のAPI呼出し費用が実測と解析モデルのずれを生む可能性がある。

### 配置と草稿長の探索

高水準の投機的サンプリング処理を、草稿モデルと検証モデルという二つの粗粒度サブグラフに分ける。CPU/GPUの候補配置と利用可能なCPUコア数・GPU構成を列挙し、事前測定したcとαから、各候補に最適なγを選ぶ。例えば2種類の処理装置と2つの分割部分に対し、構成選択数をvとすると探索空間はv×2²となる。

各候補を実機で長時間走らせる代わりに、個別順伝播のプロファイルを解析モデルへ入力して不利な配置を除外する。最適なγ=0なら投機しない通常の検証モデル実行を選ぶ。したがって、本方式は常に投機を有効化するのではなく、投機の期待利得が負なら停止するという明示的な判断を含む。

## 評価

### 実験環境

| 項目 | 原著の条件 |
|---|---|
| エッジSoC | NXP i.MX95、6×Arm Cortex-A55、Mali-G310 GPU |
| モデル | Llama-3.2-1B 草稿モデル、Llama-3.2-3B 検証モデル |
| 量子化 | Intel Neural Compressor、静的W8A8、部分/全量子化と浮動小数点の比較 |
| コンパイラ | IREE 3.6.0、LLVM CPU、SPIR-V GPU |
| 入力 | 投機的復号ベンチマーク翻訳、平均入力長63トークン |
| 推論 | 貪欲復号、KVキャッシュなし |
| 受理率測定 | 16コアサーバーで事前測定 |
| エッジ測定 | CPUコア/GPU配置別順伝播時間と実機速度。図7は10回平均 |
| 比較基準 | 非投機的検証モデルの逐次実行、設計構成ごとの最適γ |

この評価では、一般的な長文脈のKVキャッシュ再利用が無効化されている。通常のサーバー推論と順伝播費用の内訳が異なるため、ここでの速度倍率をGPUサーバーのTPOTや連続バッチ処理の改善倍率として読むことはできない。

### 受理率と量子化の相互作用

原著Figure 5では、浮動小数点系の受理率中央値が約0.58、半量子化構成では約0.17であり、両モデルを8ビット整数化すると中央値はほぼ0となる。受理率の低下は、量子化によって候補生成モデルと検証モデルの出力分布がずれることに対応する。量子化によるメモリ節約と投機的復号の速度改善は独立ではなく、両者を一緒に最適化する必要がある。

浮動小数点の全組合せや草稿モデルのみ量子化した構成は、メモリ不足などの理由でエッジ上ですべて実測できたわけではない。受理率の分布と、エッジで実行できる配置の集合を同一視しない。受理率向上のための量子化再訓練や蒸留は将来課題である。

### 解析モデルの予測：原著Table II・III

| 設計構成 | α=0.90での選択 | 予測倍率 | α=0.17での選択 |
|---|---|---:|---|
| 1 | 異種配置・γ=5 | 1.68倍 | 投機なし・1倍 |
| 2 | 異種配置・γ=2 | 1.10倍 | 投機なし・1倍 |
| 3 | 投機なし | 1倍 | 投機なし・1倍 |
| 4 | 投機なし | 1倍 | 投機なし・1倍 |
| 5 | 同種配置・γ=1 | 1.02倍 | 投機なし・1倍 |
| 6 | 投機なし | 1倍 | 投機なし・1倍 |

高受理率α=0.90は受理率分布の上位約10%に対応する有利な条件であり、平均的なケースではない。構成 1はCPU 1コアとGPUを利用し、GPUで草稿モデル、CPUで検証モデルを実行する。γ=5で予測1.68倍となる一方、中央値α=0.17では全構成でγ=0を選ぶ。よって「一般的なエッジ推論で平均1.68倍」は原著の主張ではない。

構成 2はγ=2で予測1.10倍、構成 5はγ=1で1.02倍にすぎない。モジュール境界費用や実装差を考えると、この程度の利得は実機で消える可能性がある。CPUコアを増やして検証モデルを速くすると、GPU 草稿モデルの相対費用が増え、投機が不利になる点も重要である。

### 費用比と実機検証：原著Figure 6・7

入力長63では、1CPUコアで動かす草稿モデルをGPUへ移すと、草稿モデル/検証モデルの順伝播時間比cが約0.80から0.41へ改善する構成がある。これはGPUが小型草稿モデルをCPU 1コアより速く実行できるためである。しかし検証モデルに複数CPUコアを割り当てると検証モデルが速くなり、cが1を超える場合もある。CPUコアを増やせば常に投機が有利になるという単純な関係ではない。

Figure 7はGPU 草稿モデル・1CPUコア検証モデルの構成で、草稿長を変えた予測曲線と実機曲線を比較する。予測のα=0.90と同程度の実測速度を得るには、実測ではα≈0.94が必要となり、約4ポイントのずれがある。著者らはIREEのモジュール間API呼出しなどを原因候補として挙げる。実測は10回平均であり、他のSoC・入力長でも同じずれに収まる保証はない。

### 速度の負の結果

受理率αが0.17に下がると、どの構成でも投機をしない方がよい。両モデルの8ビット整数化で受理率がほぼ0となる条件は、メモリ容量の改善が投機的復号の有効性を壊し得ることを示す。さらにGPUが8ビット整数演算を直接実行できずFP32へ昇格する場合、検証モデルのGPU配置も不利となる。投機的復号の採用可否は、モデルの精度・デバイス実装・ランタイムの組合せで再判定する必要がある。

## 既存研究との差

Leviathanらの投機的サンプリング理論は、受理率と草稿モデル/検証モデルの費用比から期待速度改善を説明する。一般の投機的復号研究が草稿モデルの受理率や検証効率の改善を中心とするのに対し、本研究は異種エッジSoC上の配置を、IREEのコンパイル・順伝播プロファイルと解析モデルによって選ぶ点に特徴がある。

この研究は検証モデル分布を変えない新しい検証アルゴリズムを提案するものではなく、既存の投機的サンプリングを特定ハードウェアに効率よく配置するためのシステム研究である。単一グラフへ異種デバイスを統合する構想と、実際に動作した分割モジュール実装は明確に区別しなければならない。

## 限界と実務上の判断

第一に、最大1.68倍は高受理率の有利な条件であり、中央値α=0.17では投機なしが最適である。第二に、評価はNXP i.MX95のCortex-A55/Mali-G310とIREE 3.6.0に依存する。異なるNPU、モバイルGPU、8ビット整数カーネル、GPUサーバーでは最適な配置が変わる可能性がある。

第三に、主要実験は貪欲復号、KVキャッシュなし、短文翻訳であり、長文脈・通常のKV再利用・複数同時要求・分布が異なるタスクの性能は未評価である。第四に、粗粒度の草稿モデル/検証モデル配置のみを扱い、層ごとのCPU/GPU分割や動的な負荷変化への再配置は将来課題である。第五に、単一グラフ graphはIREEの制約で実装されておらず、モジュール間のオーバーヘッドが残る。

実務では、まず候補モデルの受理率とデバイス別順伝播費用を測り、c<αが満たされるかを確認する。満たさなければ投機を有効化せず、量子化で受理率が変わる場合は再計測する。著者らの実験はその判断方法を示しているが、他のSoCに対する性能保証ではない。
