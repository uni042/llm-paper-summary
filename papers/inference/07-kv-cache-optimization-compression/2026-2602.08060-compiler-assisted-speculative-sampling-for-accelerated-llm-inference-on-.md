## 概要

この研究は、NXP i.MX95のような**CPUと小型GPUを併載するエッジSoC**で、LLMの投機的サンプリング（speculative sampling）をどのデバイス配置・草稿長で実行すべきかを、IREEコンパイラと解析的費用モデルで選ぶ。投機的復号は、小型drafterが候補tokenを逐次生成し、大型targetが候補をまとめて検証することで、targetのforward回数を減らす。ただしdrafterが遅い、候補の受理率が低い、CPU/GPU転送やランタイム呼出しが高価、といった条件ではむしろ遅くなる。

著者らは、drafterとtargetの実測forward遅延比`c`、受理率`α`、草稿長`γ`を使って速度改善を予測し、GPUへdrafter、CPUへtargetを配置する構成などを探索する。Llama-3.2-1B drafterとLlama-3.2-3B target、Spec-Benchの短文翻訳、NXP i.MX95（6×Cortex-A55＋Mali-G310）という条件では、受理率の高いケース`α≈0.90`、草稿長5で最大1.68倍の速度改善を報告する。

ただし、**この1.68倍は典型的な全サンプルの平均ではない。** 半量子化構成の受理率中央値`α≈0.17`では、すべての探索配置で投機的復号をしない方が速いとモデルが判定する。さらにdrafter/target双方をINT8化すると受理率中央値がほぼ0へ崩れる。エッジ投機的復号の成立条件と失敗条件を同時に示す点が実務上重要である。

## 問題設定

### エッジで投機的復号が難しい理由

通常の自己回帰decodeは1tokenずつtargetのforwardを繰り返す。投機的サンプリングでは小型モデルが`γ`tokenを草稿生成し、targetが1回で検証する。サーバーGPUならtargetの検証並列化で利得が出やすいが、エッジではGPUが小さく、targetがGPUへ収まらない場合や、CPUのメモリ帯域が低い場合がある。また量子化でdrafterとtargetの確率分布がずれると、受理率が下がり、余分なdrafter計算が無駄になる。

従来はモデルサイズ・受理率だけで草稿長を選ぶことが多いが、エッジではCPU core数、GPU shader、データ型サポート、コンパイラ実装によってdrafter/targetの相対費用が大きく変わる。どのPU（processing unit）へどの計算グラフを置くかを同時に考える必要がある。

### コストモデルと速度改善条件

原著式1の解析モデルは、受理率`α`、草稿長`γ`、forward遅延比`c=t_draft/t_target`を使い、速度改善を

`S(α,γ,c) = (1−α^(γ+1))/((1−α)(γc+1))`

と予測する。`c<α`は、適切な`γ`を選べば1倍超の改善が得られるための条件である。`α`が小さいと、targetが受理するtokenが少なく、drafterに使った時間を回収できない。`c`が大きいと、草稿生成の負担がtargetのforward節約を上回る。式は平均的な受理とforward費用の簡略化であり、実装上のAPI・転送オーバーヘッドは別途実測で検証する必要がある。

## 手法

### 1. Offline量子化と受理率の測定

drafterとtargetをエッジSoCで実行可能な精度へ変換する。著者らはIntel Neural Compressorで静的W8A8量子化を行い、FP16/一部量子化/双方量子化などの組合せでSpec-Benchの受理率を計測する。受理率はモデルとタスクの組合せに依存するため、CPU上の16coreサーバーで測定してから、エッジでのmapping探索に入力する。GPUによる浮動小数点丸め差はあり得るが、受理率は主としてモデル分布の近さで決まる。

Spec-Benchは13タスク480サンプルを含むが、主実験は翻訳タスクに絞る。翻訳は短い入力・出力が多く、エッジで実行される用途として選ばれた。翻訳の平均入力長は63tokenである。モデルの追加学習や受理率向上を提案するのではなく、既に得られた受理率を使って最も有利な配置を選ぶ。

### 2. PU別forward遅延から費用比cを測る

IREE 3.6.0のLLVM CPUバックエンドとSPIR-V GPUバックエンドを使い、drafterとtargetの1forwardを別々にコンパイルして実機測定する。各PU配置・CPU core数で`c`を算出し、モデル式から草稿長`γ`と予測速度改善を求める。drafterをGPUへ置く場合、1CPU coreと比べてGPUのdrafterが約3倍速く、平均入力長63で`c`が約0.80から0.41へ下がる条件があった（原著図6）。

一方、GPUがINT8演算を直接サポートせずFP32へ昇格してしまうため、量子化targetをGPUへ置く構成は有利でなかった。CPU coreを3～6個使える構成では、GPU drafter配置の`c`が1を超える場合もあり、drafterをGPUに置けば必ず得というわけではない。

### 3. 粗粒度の設計空間探索

計算グラフをdrafterとtargetの2部分に分け、各部分をCPU/GPUのどちらに割り当てるかを探索する。PU種数を`N`、分割数を`m`、利用可能なcore/shader構成の組合せ数を`v`とすると、探索空間の大きさは`v N^m`となる。例ではCPU 6core・GPU 1shader、2PU、2分割で`6×2²=24`候補である。

候補ごとに実測した`α,c`を解析モデルへ代入し、最適な`γ`を求める。実機で全候補の投機的生成を何度も試すより、forwardのプロファイルとモデルで不利な候補を先に除外する。GPU/CPUへ層単位やattention演算単位で分割する細粒度探索は対象外で、将来課題としている。

### 4. IREEコンパイラへの組込み

高水準PyTorchの投機的サンプリング制御と、低水準MLIR/IREEのPU割当を結びつける。著者らは単一IREE module内にdrafter、target、制御フローをまとめるmonolithic方式と、drafter/targetを別moduleにcompileしてランタイムAPIで接続するmodular方式を比較する。

monolithic方式は境界を跨いだ最適化の可能性があるが、IREE 3.6.0の異種デバイス親和性・メモリアロケータ制約で実際には実装できなかった。実測はmodular方式を採用し、別々のcompile済みグラフをIREE runtime APIで制御する。module境界でのAPI呼出し費用が発生し、解析モデルと実測のずれの一因となる。したがって「単一グラフの完全融合に成功した」と解釈してはいけない。

## 評価

### ハードウェアと測定条件

| 項目 | 設定 |
|---|---|
| SoC | NXP i.MX95、6×Arm Cortex-A55 CPU、Mali-G310 GPU |
| モデル | Llama-3.2-1B drafter、Llama-3.2-3B target |
| ワークロード | Spec-Bench翻訳タスク、平均入力63token。短い入出力を想定 |
| 推論 | greedy sampling、KV cacheなし |
| 量子化 | Intel Neural Compressor、静的W8A8、半量子化/全量子化/FP参照 |
| コンパイラ | IREE 3.6.0、LLVM CPU、SPIR-V GPU |
| ベースライン | 1CPU coreの非投機的target decode。モデル式で配置と草稿長を選択 |
| 計測 | 受理率は16coreサーバーで測定、forward遅延・速度はエッジ実機。図7は10run平均 |

本実験は短文翻訳で、KV cacheを無効化した特殊条件である。長文・複数要求・通常のKV再利用ありのサービングと、token当たりのforward費用が異なる可能性がある。

### 受理率の量子化依存性（図5）

FP系の比較では受理率中央値`α≈0.58`、半量子化構成では中央値`α≈0.17`で分布が0～1まで広がる。drafterとtargetの双方をINT8化すると受理率中央値がほぼ0へ低下した。これは低ビット化による確率分布のずれが投機的サンプリングの効率を損なうことを示す。著者らは量子化方式の改善・量子化drafterの追加訓練を本研究の範囲外としている。

図5のFP/半量子化/全量子化は、メモリ制約のため全組合せをエッジ上で実測したわけではない。FP16の全構成やdrafterのみ量子化した構成は初期化時のメモリ不足により除外されたと記載する。したがって、受理率分布の比較と実機の全配置比較を混同しない。

### 表II・III：解析モデルの予測（入力長63）

| CPU/GPU構成variant | 高受理率α=0.90の選択 | 予測速度改善 | 低受理率α=0.17の選択 |
|---|---|---:|---|
| 1（1CPU core＋GPU drafter） | 異種配置、γ=5 | **1.68×** | 投機なし、1.00× |
| 2 | 異種配置、γ=2 | 1.10× | 投機なし、1.00× |
| 3 | 投機なし | 1.00× | 投機なし、1.00× |
| 4 | 投機なし | 1.00× | 投機なし、1.00× |
| 5 | 同種配置、γ=1 | 1.02× | 投機なし、1.00× |
| 6 | 投機なし | 1.00× | 投機なし、1.00× |

α=0.90は翻訳タスクの受理率分布の90パーセンタイル近傍を想定した**有利な条件**である。α=0.17は中央値であり、すべてのvariantで最適γ=0（投機しない）となる。従って「エッジで平均1.68倍」という主張は不正確で、正しくは「高受理率・1CPU coreの特定構成で最大1.68倍」である。

### 図6・7：費用比と実機検証

入力長63で、drafterをCPU 1coreからGPUへ移すと`c≈0.80→0.41`へ改善する構成がある。一方CPU側の利用core数が増えるとtargetが速くなり、GPU drafterの相対費用が増えて`c>1`となる条件もある。このため同じSoCでもCPU core割当によって最適な投機戦略が逆転する。

図7ではGPU drafter・1CPU core targetの異種配置について、`γ`を変えた実測速度改善曲線が解析モデルの傾向に概ね一致する。著者らは予測した受理率α=0.90に対し実測で同等の加速を得るにはα≈0.94が必要で、受理率に約4ポイントのずれがあると説明する。IREEのmodule間API呼出し等が原因候補である。実測は10run平均であり、他のSoCで同じ誤差幅が保証されるわけではない。

### 負の結果の重要性

量子化で受理率が下がると、モデル式の分子（期待受理token数）が小さくなり、草稿生成の負担だけが残る。全INT8で受理率がほぼ0になった事例は、メモリ削減と投機的復号を独立に最適化できないことを示す。低受理率α=0.17では、最も有利な1CPU core＋GPU配置であっても投機しない方が良い。さらにCPU coreを増やしてtargetを高速化すると、drafter/targetの遅延比`c`が大きくなり、投機の利得が失われる。最適化手法の成功条件だけでなく、適用しない方が良い領域を定量化した点に価値がある。

## 既存研究との差

Leviathanらの投機的サンプリング理論は、受理率とモデル費用比から期待速度改善を導く。通常の研究はdrafter精度、受理率、targetの検証効率を改善することが多い。これに対し本研究は**エッジSoCのCPU/GPU異種配置とコンパイラ実装**を対象とし、実機で`c`を測り、草稿長と配置を選ぶための設計空間探索を組み立てる。

専用GPUが大きいサーバーとは異なり、Mali GPUがINT8を直接扱えず、量子化targetをGPUへ置けないなどの制約が支配的になる。高水準PyTorchとIREEのloweringを接続する設計も特徴だが、monolithic実装は未完成で、modular方式による実機検証にとどまる。学習不要の既存drafterを使うため、新しい投機的token生成アルゴリズムやtarget分布保証を提案する論文ではない。

## 限界・実務上の判断

1. **高受理率の条件付き成果:** 最大1.68倍はα≈0.90の上位条件。中央値α≈0.17では全配置で投機的復号は不利。
2. **量子化との干渉:** 全W8A8で受理率中央値がほぼ0。drafter/targetの分布を揃える量子化や蒸留を別途行わないと、圧縮が投機効率を壊す。
3. **特定SoC:** NXP i.MX95のCortex-A55/Mali-G310、IREE 3.6.0に依存。異なるNPUやGPUへ外挿できない。
4. **KV cacheなし:** 主要実験でKV再利用を無効化。一般の長文生成・バッチサービングでの効果を示すものではない。
5. **短文翻訳のみ:** Spec-Bench翻訳、平均入力63tokenを中心に評価。長い文脈や他タスクで受理率・forward比が変わる可能性がある。
6. **粗粒度分割:** drafterとtargetの2部分を配置する。層ごとのPU分割、NPU混在、動的負荷に応じた再配置は将来課題。
7. **monolithic未実装:** IREEランタイムの制約で別module方式を使い、API境界費用が残る。単一グラフ融合の性能を実証していない。
8. **品質保証:** 本研究は速度と受理率の解析・実機検証が中心で、量子化による翻訳品質変化の広範な定量評価は主眼ではない。
