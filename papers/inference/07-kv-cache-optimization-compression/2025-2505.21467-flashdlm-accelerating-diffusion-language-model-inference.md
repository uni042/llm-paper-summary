# FlashDLM: Accelerating Diffusion Language Model Inference via Efficient KV Caching and Guided Diffusion

> FlashDLMは拡散言語モデル（Diffusion Language Model; DLM）の遅さを、**1回のノイズ除去で再計算し過ぎる問題**と、**何回ノイズ除去を繰り返すかという問題**に分ける。FreeCacheは前者を、Guided Diffusionは後者を削り、二つを組み合わせて大きな端末間高速化を得る。

## 概要

自己回帰言語モデル（Autoregressive Language Model; AR LM）は1トークンずつ左から右へ生成するため、過去トークンのキー・値（Key-Value; KV）をキャッシュし、新しいトークンに必要な部分だけを更新できる。一方、マスク型の拡散言語モデルは、まだ未確定の複数位置を一度に更新できる代わりに、ノイズ除去段階ごとに系列全体へフォワード計算をかける。

この違いにより、DLMは「並列に複数トークンを確定できる」という理論上の利点を持ちながら、Dream-7BやLLaDA-8Bのような実モデルでは多数回の全系列再計算が支配し、同規模ARモデルより遅くなりやすい。単純にノイズ除去段数を減らすと、互いに矛盾するトークンを同時確定してしまい、推論・常識・長文生成の品質が落ちる。

FlashDLMは学習不要の二段構成でこの問題を解く。**FreeCache**は、既に確定して今後ほとんど変化しない領域のKV射影を保存し、後続のノイズ除去段階で再利用する。**Guided Diffusion**は小型の凍結済みARモデルをガイダーに使い、DLMが提案したトークン列とAR側の予測が一致する先頭区間だけを一度に確定する。

結果として、FreeCacheは各段階の計算量を下げ、Guided Diffusionは必要な段階数を下げる。Dream-7B-Instructでは平均約12倍、LLaDA-8B-Instructでは約13倍のエンドツーエンド高速化が報告され、DLMの待ち時間を同規模ARモデルに近い領域まで縮めている。

## 背景と問題設定

### DLMは並列生成できても全系列再計算が高い

マスク型DLMでは、出力系列中の複数位置が同時に[MASK]から通常トークンへ変わる。ところが各段階で現在の系列全体をTransformerへ入れるため、既に確定したトークンについてもQ/K/V射影や前向き計算が繰り返される。

ARモデルのKVキャッシュでは過去位置が変わらないことを前提に再利用できるが、DLMでは未確定トークンが系列中に散在し、双方向注意で互いに影響する。このため「ARと同じキャッシュをそのまま使う」ことはできない。

ただし、ノイズ除去が進むにつれ確定済み区間は増え、そのKV表現は段階間で安定する。FlashDLMはこの時間方向の安定性を利用する。

### 段数削減だけではトークン整合性が崩れる

DLMは1回で多くの位置をアンマスクすれば速くなる。しかし各位置の予測は、同時に確定しようとしている他位置がまだ[MASK]である状態から作られるため、互いの条件関係を十分見ないまま複数語を確定する危険がある。

そのため既存の信頼度しきい値等で強引に段数を減らすと、生成が不整合になりやすい。FlashDLMは「何個なら同時に確定してよいか」をDLM自身の確信度だけで決めず、逐次生成に強いARモデルの予測と照合する。

## 手法

### 1. FreeCache: 確定済みブロックのKVを凍結する

入力はあるノイズ除去段階の系列と、前段階までに計算したKV状態である。生成系列をブロックへ分け、既に確定して変化しない過去ブロックのKV射影をキャッシュする。

次の段階では、現在アンマスクが進んでいるブロックと、その先の未確定領域だけを再計算し、以前の確定ブロックは保存済みKVを再利用する。ノイズ除去が進むほど再計算窓が縮むため、後半段階ほど全系列再計算との差が大きくなる。

これは厳密なKVキャッシュではなく近似である。双方向注意では未確定領域が変わると過去位置の内部表現も理論上は変化し得るため、古いKVを固定すると誤差が入る。FlashDLMは「確定済みKVは段階間で比較的安定する」という実測性質を利用して計算を削る。

### 2. Guided Diffusion: DLMをドラフタ、小型ARモデルを整合性検査に使う

各段階でDLMは未確定位置に対する候補トークンを並列に出す。この提案列を、小型の凍結済みARモデルへ渡す。

ARモデルは左から右の条件付き分布に基づいて系列を評価する。DLMの候補とAR側の予測が先頭から連続して一致する区間を探し、一致した複数位置をまとめて確定する。

一致区間が長ければ1回のDLM前向きで多くのトークンをアンマスクできる。一致しない場合は保守的に少数、実装上は最低1トークンだけを進めるため、無理に並列化して整合性を崩すことを避ける。

### 3. 小型ARモデルは最終回答を生成する主体ではない

ガイダーの役割は最終回答をARモデルで置き換えることではなく、DLM提案のうち「逐次条件付けと矛盾しにくい範囲」を判定することである。

このため1.5B級ガイダーでも大きな速度利得を得られる。7B級ガイダーへ大きくしても精度改善は限定的な条件があり、その一方でガイダー自身の推論時間とGPUメモリは増える。

論文のGSM8K比較でも、Qwen2.5-1.5B-Instructを単独ARとして使うと精度68.54%だが、Dream-7Bをガイドすると80.3%になる。答えの能力は主にDLM側に残り、AR側はアンマスク境界を決める補助信号として働く。

### 4. 二つの手法は別の軸を削る

FreeCacheだけを入れると、ノイズ除去段階数は同じまま1段の費用が下がる。Guided Diffusionを加えると、1段で確定できるトークン数が増え、必要段数自体も減る。

したがって全体利得は単純な同一最適化の重複ではない。キャッシュが「横方向の系列長コスト」を削り、ガイドが「縦方向の反復回数」を削るため、組合せで大きい倍率が出る。

### 5. 1回の生成の流れ

最初に入力プロンプトと[MASK]を含む生成領域をDLMへ入れ、候補トークン列を得る。ガイダーARモデルが候補を逐次的に照合し、両者が一致する先頭区間を決める。

一致区間を確定し、確定済みブロックのKVをFreeCacheへ保存する。次のDLM段階では、保存済みKVを再利用しながら現在窓と未確定領域のみを更新する。

全トークンが確定するまでこの処理を繰り返す。進むほど再計算範囲は小さくなり、一致区間が長いほど反復回数も減る。

## 評価

### 評価条件

| 項目 | 条件 |
|---|---|
| 主DLM | Dream-7B-Instruct、LLaDA-8B-Instruct |
| 主ガイダー | Qwen2.5-1.5B-Instruct、Qwen2.5-Math-1.5B-Instruct、Qwen2.5-7B-Instruct |
| 主GPU | NVIDIA RTX 6000 Ada 48GB の単GPU評価 |
| 最大生成長 | 推論・数学・質問応答で最大1,024トークン |
| 課題例 | MMLU-PRO、GSM8K 8-shot、PiQA、ARC-C、ARC-E、GPQA |
| 比較 | 通常DLM、FreeCache単独、FreeCache + Guided Diffusion、単独ARモデル |
| 速度指標 | 問題1件あたりエンドツーエンド待ち時間 / 高速化率 |
| 品質指標 | 各ベンチマークの正答率 |
| 実装状況 | 学習不要。公式実験コードあり |

### Dream-7B-Instructの代表結果

| 課題 | 通常DLM | FreeCache単独 | FreeCache + Qwen-1.5B | 読み方 |
|---|---:|---:|---:|---|
| MMLU-PRO | 46.92% / 20.73s | 45.18% / 6.68s (**3.11倍**) | 46.64% / 1.66s (**12.48倍**) | キャッシュ誤差をガイドでほぼ回復 |
| GSM8K 8-shot | 79.68% / 48.05s | 77.40% / 10.87s (**4.42倍**) | 80.33% / 2.70s (**17.80倍**) | 長い入力で再計算削減が特に大きい |
| PiQA | 85.56% / 14.62s | 84.83% / 4.21s (**3.47倍**) | 85.15% / 0.43s (**34.1倍**) | 最大級の待ち時間削減 |
| ARC-C | 80.87% / 10.64s | 80.61% / 4.25s (**2.50倍**) | 80.89% / 3.12s (**3.41倍**) | 品質をほぼ維持 |
| ARC-E | 87.53% / 10.59s | 86.24% / 5.54s (**1.91倍**) | 87.50% / 3.25s (**3.26倍**) | タスクにより倍率は小さくなる |
| GPQA | 39.29% / 21.50s | 43.30% / 9.91s (**2.12倍**) | 49.55% / 12.02s (**1.78倍**) | ガイダー計算で速度利得が小さくても精度が上がる条件 |

論文全体ではDream-7B-Instructで平均約12倍、LLaDA-8B-Instructでも平均約13倍のエンドツーエンド高速化を報告する。最大値だけを見ると34.1倍だが、ARCやGPQAのように数倍以下の条件もあり、課題ごとにDLMの反復数とガイダー費用の比率が異なる。

### ARモデルとのGSM8K比較

| ARガイダー | 単独AR | Dream-7B + Guided Diffusion | LLaDA-8B + Guided Diffusion |
|---|---:|---:|---:|
| Qwen2.5-1.5B-Instruct | 68.54% / 2.26s | 80.3% / 2.55s | 79.91% / 4.29s |
| Qwen2.5-Math-1.5B-Instruct | 78.24% / 1.59s | 82.9% / 3.19s | 81.96% / 5.31s |
| Qwen2.5-7B-Instruct | 91.13% / 3.23s | 82.3% / 3.43s | 79.68% / 4.42s |

ここでは大きいARガイダーほどDLMの精度が必ず大幅に上がるわけではない。1.5BガイダーでもDream側の能力を保ったまま待ち時間をAR推論に近づけられる一方、7Bガイダーは自身の計算費用が増える。

また、同規模ARモデルが精度でも常に劣るという結果ではない。Qwen2.5-7B-Instruct単独はGSM8Kで91.13%とDLM系より高い。FlashDLMの主張は、DLMの品質特性を保ったまま**DLM固有の大きな待ち時間差を縮めた**ことにある。

### FreeCache単独と組合せの差

GSM8KではFreeCacheだけでDream-7Bが4.42倍、LLaDA-8Bが6.32倍高速化する。これは段階ごとのKV再計算削減だけでも大きな冗長性があることを示す。

ただしFreeCacheは近似のため、Dream-7BのGSM8K正答率は79.68%から77.40%へ下がる。Guided Diffusionを加えると80.33%まで回復しながら17.80倍へ伸びるため、ガイダーは単なる追加高速化ではなく、近似キャッシュによる品質低下を抑える役割も持つ。

## 既存研究との差

通常のAR向けKVキャッシュは過去トークンの状態が不変であることを利用する。FlashDLMのFreeCacheは、双方向に状態が変わり得るDLMへ**近似的な時間再利用**を導入する点が異なる。

信頼度しきい値だけで並列アンマスクを増やす方式に対して、Guided Diffusionは外部の小型ARモデルとの一致を使う。DLM内部の確率だけで「安全」を決めないため、少ない段数でも逐次整合性を補える。

投機的復号（Speculative Decoding）と似た構造もあるが、典型的な投機的復号では小型モデルがドラフトし大型ARモデルが検証する。FlashDLMではDLMが並列候補を出し、ARモデルは主にアンマスク範囲のガイドとして使われるため、役割が逆転している。

## 限界・実装状況

第一にFreeCacheは厳密ではない。確定済みトークンのKVが将来段階でも十分安定するという経験的性質に依存し、モデルやノイズ除去スケジュールが変われば最適なキャッシュ窓も変わる。

第二にGuided Diffusionは追加モデルを必要とする。1.5B級でもモデル重みとKVのGPUメモリ、追加フォワード時間が必要で、メモリが厳しい端末ではDLM単独より展開条件が重くなる。

第三に、最大倍率は課題依存である。PiQAの34.1倍をすべての長文・推論課題へ移植できるわけではなく、GPQAではガイダー込みの速度向上が1.78倍にとどまる条件もある。

第四に、品質はDLM本体の能力上限に依存する。小型ARガイダーは整合性を助けても、DLMをより強いARモデルそのものへ置き換えるわけではない。GSM8KではQwen2.5-7B単独の正答率がDLM系を上回る。

第五に、公開コードは実験実装であり、一般的な配信基盤へ統合するには連続バッチ処理、複数要求間のキャッシュ管理、メモリ断片化、ガイダーとの同時実行を別途設計する必要がある。

## サーベイ上の含意

FlashDLMの重要点は、拡散型生成の高速化を「ノイズ除去段数を減らす」一軸にしなかったことである。各反復の全系列再計算と、反復回数そのものを別々の冗長性として扱うことで、片方だけの最適化より大きい利得を得る。

また、KVキャッシュを「自己回帰モデルだけの厳密再利用機構」と考えず、状態が十分安定した範囲へ近似的に拡張する発想は、反復型推論一般へ応用可能である。導入評価では平均高速化だけでなく、キャッシュ近似による品質低下、ガイダー費用、タスク別の受理区間長を分けて見る必要がある。
