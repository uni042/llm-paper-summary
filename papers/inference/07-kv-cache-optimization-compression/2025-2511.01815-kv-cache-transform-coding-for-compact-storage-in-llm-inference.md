# KV Cache Transform Coding for Compact Storage in LLM Inference

> KVTCは共通の主成分分析基底でKVキャッシュの相関を減らし、重要度別の量子化と無損失符号化で保存量を縮める。16倍目標で多くの課題品質を概ね保ち、H100の8K文脈では復号再利用がKV再計算よりTTFTを約8倍短縮したが、処理時間と強圧縮時の品質低下も示す。

## 概要

長い対話や推論の継続では、過去トークンごとのキー・バリュー（Key–Value; KV）状態をGPUメモリに保持するため、同時に扱える要求数が減る。対話の区切りでKVをGPU外へ退避すれば容量は空くが、再開時に読み戻す必要がある。キャッシュを捨てれば同じ共通先頭を再計算する。本論文は、モデル重みを変えず、特徴間の相関を減らす変換、重要度別の量子化、無損失符号化を組み合わせてKVの保存量を削減するKVキャッシュ変換符号化（KVTC）を提案する。

較正入力からモデル単位の主成分分析（Principal Component Analysis; PCA）基底を一度作り、キーと値を共通の座標系へ写す。主成分ごとに異なるbit幅を割り当て、寄与の小さい末尾成分は0 bitで落とす場合もある。量子化値は共有の移動量・尺度を持つ群にまとめ、最後にDEFLATEで可逆圧縮する。再利用時は元のKVを復元して通常の注意機構へ渡す。圧縮したまま注意機構を計算する方式ではない。

評価はLlama 3、Mistral NeMo、R1蒸留Qwen2.5の1.5B〜70Bモデルで、数学、知識、長文検索、コード生成などを測る。目標16倍圧縮の多くの課題では非圧縮時との差が1点未満の例を示し、DEFLATE後に最大約20倍の実圧縮となる条件がある。H100上のMistral NeMo 12Bでは、8K文脈のKVを再計算する場合に比べて16倍目標の圧縮キャッシュを復号する場合、TTFTは3098msから380msへ短縮した。一方、圧縮に379ms、復号に267msを要するため、この比較は保存キャッシュの復元とKV再計算の比較であり、通常の生成が同じ倍率で速くなることを意味しない。32〜64倍では一部の長文・推論課題に品質低下が現れる。

## 問題設定

Transformerの各生成段階では、過去トークンのキーと値をKVキャッシュとして再利用する。文脈が長くなるとキャッシュは増え続け、モデル重みとは別にGPUメモリを消費する。チャットやコード編集では、以前の対話共通先頭を次の対話ターンで再利用できるが、応答待ちの間もGPU上に保持すれば別要求の容量が減る。CPUメモリやストレージへ退避するとGPUを空けられる反面、再開時の転送が遅延を加える。キャッシュを破棄した場合は共通先頭を再処理しなければならない。

既存の選択肢には、古いトークンの追い出し、低bit量子化、特異値分解による低次元表現がある。追い出しは情報自体を捨てるため、後段の長文検索や推論に必要な箇所を落とす可能性がある。均一な量子化では、重要度が異なる特徴にも同じ記憶量を使う。低次元法では、継続して増えるKVへ変換をどう適用するか、変換行列をどう再計算するかが課題になる。KVTCはモデルごとの基底を事前に作り、圧縮後のキャッシュを保存して後で復元する状況を対象とする。

## 手法のあらまし

処理は較正、特徴変換、bit配分、群量子化、可逆符号化の順に進む。較正では代表入力をモデルへ通し、各層・注意ヘッドのキーと値から特徴を集める。キーは位置埋め込みによる回転を取り消してから集約し、モデル単位のPCA基底を作る。推論時はKVをこの基底へ射影し、各主成分係数へ誤差とbit予算に応じたbit幅を割り当てる。係数を一定数ずつまとめ、群内で16bitの移動量と尺度を共有する。動的計画法がpayload bitと群情報の費用を合算して配分を決める。量子化値はbyte列に詰めてDEFLATEで圧縮し、保存先に置く。再利用時には符号を戻して逆変換し、元のKVとして推論へ渡す。

## 手法

### 1. 較正済みPCA基底で特徴の相関を減らす

KV特徴の成分同士に相関があると、単純に各成分を量子化しても値の冗長性を活かしにくい。KVTCは較正データから特徴行列を作り、中心化したデータにPCAを適用する。各KVベクトルをこの座標へ射影すると、分散の大きな主成分と小さな主成分が分かれ、重要な係数へ多くのbitを使える。

基底は入力文ごとに計算し直さず、モデルごとに一度作って複数の会話で再利用する。較正には約20万トークンを使い、12BモデルでH100 1基あたり10分未満とする。70Bモデル例ではPCA係数の大きさはモデルパラメータ数の約2.4%である。よって較正は要求ごとのオンライン処理ではないが、モデルごとの準備と基底の保管は必要になる。

キーには回転位置埋め込み（Rotary Positional Embedding; RoPE）が適用される。異なる位置のキーをまとめて分析するため、まずこの位置回転を戻す。さらに注意機構 sinkと呼ばれる先頭側の重要トークンと、最新のsliding windowは圧縮対象から外す。評価設定ではsink 4トークン、window 128トークンを使い、直近のKVは高精度で残して古い部分を圧縮する。圧縮対象外の領域があるため、対象部分の圧縮率とキャッシュ全体の削減率は一致しない。

### 2. 主成分ごとにbit予算を変える

主成分の分散は一様ではない。すべてを同じbit幅で量子化すると、再構成に大きく寄与する先頭成分に不足し、寄与の小さな末尾成分にbitを使い過ぎる。KVTCは主成分ごとの候補bit幅を動的計画法で組み合わせ、指定された総bit予算の範囲で二乗誤差を小さくする。末尾成分には0 bitを割り当てられるため、量子化だけでなく次元削減も行う。

量子化値は連続する成分を群にまとめ、群内の16bit移動量と尺度を共有する。最適化は値そのもののpayloadに加え、この群情報の記録費用もbit予算へ含める。選べる群サイズは1、16、64、256、1024成分であり、細かい群では適応性が上がる一方、付帯情報量が増える。群サイズと係数bit幅を同時に調整することで、固定の一様量子化より記憶量を重要度へ寄せる。

### 3. DEFLATEでbyte列をさらに可逆圧縮する

係数を量子化した後、byte列に詰めてDEFLATEで圧縮する。この段階は無損失であり、近似誤差が入るのはPCA変換後の成分切捨てと量子化までである。GPU上の並列実行にはNVIDIA nvCOMPを用いる。実圧縮率はbyte列の内容に依存するため、動的計画法が設定する目標値と最終的な保存量は異なる。論文は目標16倍の係数圧縮がDEFLATE後に最大約20倍へ達する例を示す。これは全モデル・条件で必ず得られる比率ではない。

DEFLATE前後の比較は、量子化による不可逆な削減と、byte列の繰り返しを使う可逆な削減を分けて考える必要がある。前者は元の値を完全には戻せないため品質へ影響し得るが、後者は圧縮データを展開すれば同じ量子化byte列へ戻る。したがって実効保存量の増加が品質損失をさらに追加するのではなく、量子化後データの偏りに依存する。

### 4. 保存・再開の流れと運用上の境界

プリフィルは通常どおり実行し、KVができてから圧縮する。対話が中断したら圧縮表現をGPU内またはGPU外に保存し、再開時に読込み、DEFLATE展開、逆量子化、逆PCA変換を行って注意機構が使うKVへ戻す。70Bの複数GPU評価では層単位で復号し、全層の復号を待つ前に生成を始められるかも測る。保存領域からの転送、展開、逆変換のコストが、KVを再計算する時間より小さい状況で復元が有利になる。

本方式は圧縮表現のまま注意機構を計算せず、元の次元へ復元してから通常の推論に使う。また、継続生成中の全トークンを常に圧縮し続ける形ではなく、論文の主評価は一定間隔で圧縮・復号を行うシミュレーションである。したがって圧縮率から直接デコード速度やオンラインサービス全体の処理量を推定することはできない。

## 評価

### まず見るところ

KVTCは主成分間の冗長性を利用し、追い出しだけに頼らず古いKVを小さく保存する。ベースモデルの多くの長文・知識課題では目標16倍圧縮でも差を小さく保ったが、より強い圧縮では情報の損失が検索・推論性能に現れる。H100での再開測定は、圧縮キャッシュの復号が8K KV再計算より約8.15倍早い条件を示す。しかし圧縮・復号だけで数百msを使うため、これは既にGPU上にあるKVを使う通常デコードとの速度比較ではない。

### 評価条件

| 項目 | 設定 |
|---|---|
| ハードウェア | H100 SXM 80GB。Llama 3.3 70Bは4 GPUに分割して評価。 |
| モデル | Llama 3.1 8B、MN-Minitron 8B、Mistral NeMo 12B、R1蒸留Qwen2.5 1.5B/7B、Llama 3.3 70B。 |
| 実行基盤 | Transformers系の評価構成。GPU量子化・符号化・復号を計測。 |
| 課題 | GSM8K、MMLU、Lost in the Middle、Qasper、RULER、LongBench、AIME 2024/2025、LiveCodeBench、MATH-500。 |

比較対象はKIVI・GEAR・FP8量子化、トークン追い出しのTOVA・H2O、低次元化のxKV、学習済み追い出しのDMSである。各手法の意図に合わせてプリフィルは通常実行し、KV生成後に圧縮・追い出しを適用する。KVTCは128トークンの直近windowを保ち、16トークンごとに圧縮・復号する。比率計算ではwindowを含めず圧縮対象トークンだけを数える。xKVはプリフィルだけを圧縮し、新規デコード トークンの行列再計算はしない有利な比較条件であるため、非Qwenモデルではプリフィル分のみを比べる。

### 主な性能結果

| 条件 | 比較対象 | KVTC | 読み方 |
|---|---|---|---|
| ベースモデル、目標16倍 | 非圧縮KV | 多くの課題で品質差1点未満の例。DEFLATE後に最大約20倍の実効圧縮。 | 冗長な特徴を使い、追い出しや均一量子化より多くの古いKVを保持できる例。ただし最大値は条件依存。 |
| R1蒸留Qwen2.5 7B、目標8倍 | 非圧縮、AIME24/AIME25/LiveCodeBench | 52.5対50.9、40.8対40.8、36.5対36.7。実効圧縮約9〜11倍。 | これらの課題では近い品質を維持した。 |
| 同7B、目標16倍 | 非圧縮、AIME25/LiveCodeBench | 38.3対40.8、31.6対36.7。 | 強い圧縮では数学・コード課題の差が拡大。 |
| Llama 3.3 70B、MATH-500 | 非圧縮KV | 10倍で約1.2点、20倍で約3点低下。 | 本文の標準誤差は約1.5とされるが、20倍側は低下幅が大きい。 |
| Mistral NeMo 12B、batch 8、8K文脈 | KV再計算TTFT 3098ms | 圧縮379ms、復号267ms、復号後TTFT 380ms | 復号再利用は再計算比で約8.15倍早い。圧縮と復号の合計は646ms。 |
| 同12B、batch 2、16K文脈 | KV再計算TTFT 1780ms | 圧縮194ms、復号143ms、復号後TTFT 208ms | 長い再計算を避けると初回トークンが早くなるが、通常デコード自体との比較ではない。 |

復号再利用の差は、共通先頭のKVを新たに計算する時間が長い条件ほど有利になりやすい。一方で圧縮保存が再計算より有利になるかは保存場所からの転送を含めた総時間で決まる。論文のH100測定の379ms・267msはそれぞれ圧縮と復号であり、復号後TTFT 380msと再計算3098msとの差を、そのまま会話応答全体の高速化と解釈してはならない。

### 品質・精度

強圧縮ではタスクごとの劣化が見られる。Llama 3.1 8Bの目標64倍ではLost in the Middleが99.4から90.2、Qasperが40.4から37.8へ低下した。MN-Minitronの長文課題でも圧縮設定により低下がある。PCA係数の再構成誤差が小さくても、特定の質問に必要な情報を落とせば課題性能が下がるため、平均や代表モデルだけでは十分でない。

Qwen2.5 7Bの目標8倍ではAIME24・AIME25・LiveCodeBenchが非圧縮に近いが、目標16倍ではAIME25とLiveCodeBenchが低下する。70Bの4 GPU測定も10倍と20倍で低下幅が異なる。「最大20倍で精度維持」は全条件の保証ではなく、圧縮強度・モデル・タスクに対応させて読む必要がある。

### メモリと処理時間

| 指標 | 結果 |
|---|---|
| 実効KV圧縮 | 目標bit予算とDEFLATE後の実圧縮は異なる。目標16倍から約20倍となる条件を報告。 |
| 圧縮対象外 | 先頭4個のsinkと最新128トークンのwindowを高精度保持。総KV削減率は圧縮対象だけの倍率より低い。 |
| 基底保存 | 70B例でモデルパラメータ数の約2.4%。会話単位でなくモデル単位で再利用。 |
| 8K文脈 H100 | 圧縮379ms、復号267ms、KV再計算TTFT3098ms。 |
| 16K文脈 H100 | 圧縮194ms、復号143ms、KV再計算TTFT1780ms。 |

### 評価上の制約

- 会話継続は一定トークン間隔で圧縮・復号するシミュレーションが中心で、実サービスの同時要求、転送、保存層の競合を含む長期運用評価ではない。
- 対象モデルは密なデコードr-onlyの1.5B〜70B級で、較正データは約20万トークン。異なるモデルやデータ領域への一般化には追加評価が要る。
- 再構成誤差とタスク品質の対応は保証されない。強圧縮で長文検索等が低下する例がある。
- H100遅延は特定の再計算対復号条件であり、完全なサービス応答やオンライン圧縮の高速化を示すものではない。
- arXivのabstractには用途限定で40倍以上も述べるが、主評価の16倍や各タスク結果と混同できない。

## 既存研究との差

KIVIやGEARはKV値を低bit化し、TOVA・H2Oは残すトークンを選んで他を追い出す。xKVは特異値分解に基づく低次元表現を使う。KVTCは較正済みのモデル単位基底を会話間で共有し、主成分ごとのbit幅と群メタデータ費用を動的計画法で配分し、さらに可逆符号化を重ねる。トークンを選んで捨てるだけではなく、保存する特徴へ異なるbit量を割り振る点が異なる。比較は各手法の元の方式に合わせるが、xKVはプリフィルのみを圧縮するなど条件差がある。

## 限界・実装状況

基底がモデルや較正データに合わない場合、あるいは後段タスクが小さな主成分を必要とする場合に品質が落ちる可能性がある。圧縮を強めるほど、再計算・復号の時間は短くなり得る一方でタスク品質を損なうリスクが増える。較正はモデルごとに必要で、基底の保存・読込みも運用上の管理対象となる。

論文ではGPU上の圧縮・復号を評価するが、一般的な推論サービスへ統合済みとは確認できない。評価用実装であり、一次資料から公開コードURLは確認できなかった。実サービスへ導入するなら保存先からの転送、層単位復号、圧縮中のGPU占有、複数会話間のキャッシュ管理を含めて測る必要がある。

## 一般的な実装上の含意

KVを低bit化するとき、全成分を同じ幅で表す以外に、座標変換で特徴相関を減らし、重要度別にbit予算を配れる。可逆符号化を重ねる場合は、値payloadだけでなく群尺度などの付帯情報も圧縮予算へ含める必要がある。さらに、圧縮率だけを見ず、保存先からの転送、展開、逆変換の合計時間とKV再計算時間を比較し、どの文脈長や保存階層で再利用が得になるかを測るべきである。
