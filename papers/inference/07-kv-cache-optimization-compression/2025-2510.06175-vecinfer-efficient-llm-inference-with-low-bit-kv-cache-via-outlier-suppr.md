# VecInfer: Efficient LLM Inference with Low-Bit KV Cache via Outlier-Suppressed Vector Quantization

## 概要

自己回帰型大規模言語モデル（LLM）の推論では、生成したトークンごとの鍵と値をキー・値キャッシュ（KVキャッシュ）へ蓄積する。キャッシュ量は文脈長に比例して増えるため、長い入力を扱う際にはGPUの高帯域メモリ（HBM）容量が不足し、デコード中の読み出し量も大きくなる。ベクトル量子化（VQ）は複数要素を一つの代表ベクトルへ対応付け、各小ベクトルを短い索引として保存する。ところが鍵キャッシュの外れ値がコードブックの代表点を一部の範囲に偏らせ、1〜2ビット級では通常値の再現誤差が増える。

VecInferは鍵に対して**チャネル別平滑化**と**アダマール直交変換**を連続適用し、外れ値の影響を小さくしてからベクトル量子化する。クエリ側には対応するスケールと回転を適用し、量子化前のクエリ・鍵の内積を変えないようにする。値は別のコードブックで量子化し、生成時は新しい鍵・値をオンラインで索引へ変換してキャッシュへ追記する。さらに、コードブックの索引を完全復元してHBMへ書き戻すのではなく、注意計算のタイル内で代表ベクトルを参照するCUDA融合カーネルを用いる。

一次論文はLlama-3.1-8B、Mistral-7B、Qwen2.5-14Bと複数の推論モデルを対象に、長文脈理解、数学推論、GPU実測を評価する。Llama-3.1-8BのLongBench平均は全精度53.7に対し、2ビットVecInferで52.7、1.5ビットで51.8だった。同じ1.5ビットの既存ベクトル量子化方式MILLIONは9.7であり、極低ビットでの品質維持が特徴である。長文脈192K入力・129出力のH100単一バッチでは、2ビット構成でデコード遅延が8.3倍改善した。速度倍率は比較条件と文脈長に依存し、どの推論条件でも8.3倍速いという意味ではない。

## 問題設定

### 外れ値とコードブックの利用不足

スカラー量子化は個々の数値を整数へ丸めるのに対し、ベクトル量子化はd次元の小ベクトルを、あらかじめ学習した `2^b` 個の代表ベクトルのうち最も近いものへ割り当てる。保存するのは代表ベクトルそのものではなく、bビットの索引である。d次元の相関を利用できる反面、代表点の数は有限であり、鍵の一部チャネルが非常に大きい値を取ると、その外れ値を表現するために代表点が偏る。

論文図1ではLlama-3.1-8B-Instructの第16層の鍵分布を観察し、変換前にはチャネル間の値幅と外れ値の偏りが強く、コードブックの代表点が対象データを均一に覆えないことを示す。入力データや課題によって外れ値の分布が変わると、特定課題で学習した代表点が別課題へ適合しにくい。VecInferの課題は単に索引を短くすることではなく、少ない代表点で鍵分布を覆いやすい座標系を作ることである。

### 復号処理のメモリ転送が速度を相殺する

圧縮したKVを注意計算の直前に全量復号して新しいFP16テンソルへ書き戻すと、HBMから圧縮データを読み、復元データを書き、再び注意計算で読み直す。KVの容量削減だけではこの追加の読み書きを取り戻せない。VecInferは量子化誤差の低減と、復号を注意計算に融合した実行効率の改善を別々の機構として設計する。比較対象のKIVIはスカラー量子化、MILLIONはベクトル量子化であり、同じビット幅でも実装上の融合程度が異なる点に注意が必要である。

## 手法

### 1. 校正データによるチャネル別平滑化

事前処理ではPileから無作為に選んだ256標本（各512トークン）で鍵のチャネル別最大絶対値を測る。チャネルiの尺度を `λ_i=sqrt(max |K_i|)` として固定し、鍵行列Kには `diag(λ)^−1` を右から掛け、クエリqには `diag(λ)` を掛ける。これにより、変換後の内積は `q diag(λ) (K diag(λ)^−1)^T = qK^T` となり、量子化を入れる前の注意スコアは保存される。大きな振幅のチャネルを縮める一方、クエリ側の尺度を補正するため、単純に鍵を切り詰める方式とは異なる。

平滑化はチャネル間の尺度差を減らすが、同一チャネル内の一部トークンだけが極端な値を取る問題は残る。論文の構成要素除去実験では、平滑化だけの改善はアダマール変換だけの場合より小さい。このため、平滑化だけで外れ値が完全に消えると説明してはならない。

### 2. アダマール直交変換で外れ値を分散

平滑化した鍵と補正済みクエリの両方へ、直交アダマール行列Hを右から掛ける。`H H^T=I` が成り立つため、`(q diag(λ) H) (K diag(λ)^−1 H)^T=qK^T` となる。つまり、二つの変換を合わせても量子化前の注意内積は不変である。直交回転によって少数チャネルへ集中した大値が複数の座標へ分散され、コードブック学習にとって扱いやすい分布へ近づく。

論文の補題は鍵の符号が独立で一様という条件の下で、アダマール変換後の値が中心極限定理により概ねガウス型へ近づくことを論じる。この数学的議論は任意の実データ分布で厳密な正規性が保証されるという意味ではない。図1と付録の実測分布は、平滑化と直交回転の併用がチャネル間・チャネル内の両方の偏りを減らすことを裏付ける。

### 3. 鍵と値のベクトル量子化

校正・変換後の鍵サンプルを使い、K-meansで鍵用コードブックCkを事前学習する。値用コードブックCvも別に用意する。d次元の小ベクトルxについて、代表点Cjとの二乗距離 `||x−Cj||²` が最小の索引jを選ぶ。例えば構成 `d4b8` は4次元の小ベクトルを8ビットの索引で表し、平均2ビット/要素となる。復元時は索引に対応する代表ベクトルを参照する。コードブックの記憶量は代表点数 `2^b` と小ベクトル次元dに比例する。

事前充填段階では、位置埋め込み適用後の鍵を平滑化・直交変換して量子化し、値は元の値を別コードブックで量子化する。デコード段階では新たに生じた鍵と値を同じ規則で索引化し、既存の量子化キャッシュへ追記する。注意スコアを計算する際には変換済みクエリと復元鍵の内積を用い、重み付け和では復元した値を使う。変換そのものの数学的等価性と、有限個の代表点への近似による品質損失は別物である。

### 4. 復号・注意融合CUDAカーネル

量子化索引から全長のFP16 KVを再構成してHBMへ保存するのではなく、注意計算をタイルへ分割し、必要な索引とコードブックだけを読み込む。タイル内で索引に対応する代表ベクトルを参照してクエリ・鍵の積を求め、オンラインの正規化と値の集約まで進める。これにより、中間の復号済みKVをHBMへ書き出す経路を省く。

CUDAの非同期コピー機構を使い、タイルiのスコア計算中に同タイルの値索引を先読みし、出力集約中に次タイルi+1の鍵索引を先読みする。鍵・値の索引を共有メモリへ配置する際はバンク競合を抑えるよう並べ替える。論文図5〜6は、単純に復号を別カーネルで行う構成に対し、細粒度タイルと転送・計算重畳が必要であることを示す。大きなコードブックは品質を上げるが、共有メモリ占有や索引参照費用を増やすため、ビット幅と次元の選択には実装上の制約がある。

### 1. 長文脈理解の定量結果（表2）

Llama-3.1-8BのLongBench 13課題平均では、全精度の53.7に対して、3ビットVecInferが53.6、2ビットVecInferが52.7、1.5ビットが51.8、1.25ビットが50.3となる。同じ2ビットのMILLIONは48.2、1.5ビットのMILLIONは9.7だった。2.25ビットのKIVIは52.4であり、厳密に同一ビット幅ではないことを表へ明記する。極低ビットで既存VQの平均点が大きく崩れるのに対し、VecInferは比較的なだらかな低下に留まる。

|Llama-3.1-8Bの設定|平均ビット数|LongBench平均点|比較の読み方|
|---|---:|---:|---|
|全精度|16|53.7|量子化なしの基準|
|KIVI（b2g128）|2.25|52.4|スカラー量子化、残余保持のため2.25ビット|
|MILLION（d4b8）|2|48.2|同じ平均2ビットのVQ比較|
|VecInfer（d4b8）|2|52.7|同ビットのMILLIONより4.5点高い|
|MILLION（d8b12）|1.5|9.7|強圧縮で品質が大幅低下|
|VecInfer（d8b12）|1.5|51.8|同ビットの既存VQより大幅に良好|
|VecInfer（鍵d8b12／値d8b8）|1.25|50.3|さらに圧縮すると平均点は低下|

この表の値は異なる13課題をまとめた平均点であり、各課題で品質が無損失であることを示さない。論文は2ビット時の平均性能低下を約2.1%と説明し、MILLIONに対して平均性能改善を約14.5%と記述する。前者は基準53.7と52.7の差を比率で見た値に近く、後者は平均点の単純差4.5とは異なるため、絶対点差と論文中の相対改善率を混同しない。

### 2. 数学推論モデルの耐性（表3）

長い思考過程を生成するモデルでは、同じ2ビットでもモデルごとに品質低下の程度が違う。例えばDeepSeek-R1-Distill-Llama-8BのMATH500は全精度86.6、2ビットMILLIONが16.8、2ビットVecInferが80.0である。同モデルのAIME24は全精度47.5、2ビットMILLIONが0.0、VecInferが26.7であり、VecInferでも難しい課題では低下が無視できない。

一方、DeepSeek-R1-Distill-Qwen-14BのMATH500は全精度92.6、VecInfer 2ビットが92.6であり、Qwen3-8BのAIME24は全精度72.9、VecInfer 2ビットが67.1だった。著者らはモデル系統と課題難度の両方が耐量子化性を左右すると述べる。AIME24とAMC2023は各問題につき8生成を用いているため、単一生成の成功率と同じ条件として扱わない。

|モデル・課題|全精度|2ビットMILLION|2ビットVecInfer|解釈|
|---|---:|---:|---:|---|
|DeepSeek-R1-Distill-Llama-8B／MATH500|86.6|16.8|80.0|改善するが全精度より低い|
|同モデル／AIME24|47.5|0.0|26.7|難題では大きな品質低下が残る|
|DeepSeek-R1-Distill-Qwen-14B／MATH500|92.6|38.8|92.6|この組合せでは全精度と一致|
|Qwen3-8B／AIME24|72.9|0.0|67.1|推論能力の一部低下を観測|

### 3. GPU注意カーネルの処理速度（図6・9）

H100 80GB上で、ヘッド次元128、系列長96K〜192K、バッチ1・8・32などを変え、標準のスケールド内積注意（SDPA）、MILLION、VecInferを比較する。大バッチの自己注意では、2ビットVecInferはFP16基準よりH100で最大2.7倍、A100で最大2.8倍高速と要旨で報告する。図6のH100では設定によって2.6〜3.3倍の表示もあり、量子化設定・バッチ・ヘッド次元の違うグラフを混ぜて一つの共通最大値としない。

図9はA100 40GBでも複数バッチと系列長を調べており、単一バッチでは大バッチほどの改善が出ない条件がある。低ビット化によるHBM読み出し削減は系列長が大きいほど有利だが、カーネル起動や小バッチでの固定費が相対的に大きいと倍率は縮む。また高バッチではFP16側が容量不足となり、実測比較不能な点がある。容量不足の実行をゼロ速度として計算した倍率ではないことに注意する。

### 4. 端から端までのデコード遅延（図7・8）

H100上のLlama-3.1-8B-Instructで、入力192K、出力129トークンの単一バッチを測定した場合、1ビット、2ビット、4ビットのVecInferは、それぞれ標準の注意を用いた比較に対して9.0倍、8.3倍、6.6倍のデコード高速化を示す。系列長が96Kから192Kへ伸びるにつれて改善幅が大きくなる。これはKVキャッシュの読み出し量が増えるほど圧縮と融合の効果が大きくなるためである。

図8の内訳では、KVの連結、ヘッドの繰返し、中間メモリ読み書きなどの費用を抑え、196K級・2ビット構成で注意ブロック単体の処理時間が標準注意比約2.0倍改善したと報告する。注意ブロック単体の2.0倍と、デコード経路全体の8.3倍は測定範囲が異なる。KIVIは64K文脈で融合カーネル不足によるメモリ不足となる条件があり、すべての比較方式が同程度に最適化されているとは限らない。

### 5. 二重変換の構成要素除去（表4）

Llama-3.1-8Bの1.5ビットLongBench平均は、変換なしVQの46.1に対し、平滑化のみ48.3、アダマール変換のみ51.0、両者を平滑化→アダマールの順で適用した場合51.8だった。論文の平均改善率として、平滑化単独が約4.9%、アダマール単独が約14.1%と報告される。二つの変換を逆順で行った場合の51.4も近いが、平滑化→アダマールの51.8がこのモデルの代表点では高い。

Qwen2.5-14Bでも変換なし41.6、平滑化のみ43.7、アダマールのみ49.0、両者併用49.6という傾向を示す。したがって、平滑化だけで十分ではなく、チャネル内外の偏りを同時に減らす必要がある。変換を行っても量子化近似は残るため、これらは内積等価性だけから自動的に導かれる結果ではない。

### 6. コードブック寸法と共有メモリの交換条件（表5）

同じ平均2ビットでも小ベクトル次元と索引ビット幅の組合せを変えられる。Llama-3.1-8BのLongBench平均では `d8b16` が52.8、`d4b8` が52.7、`d2b4` が52.6と近い。1.5ビットでは `d8b12` が51.8、`d4b6` が50.2、`d2b3` が49.1であり、代表点の数やベクトル次元を減らすと品質が悪化する。Mistral-7Bでも1.5ビットで48.0、47.1、45.1と同じ方向の変化がある。

コードブックを大きくすれば代表点の表現力は増えるが、GPU共有メモリを消費して索引参照を重くするため、精度だけで設定を選べない。論文は複数のビット幅で品質とカーネル性能を調べ、代表的な2ビットの `d4b8`、1.5ビットの `d8b12` などを評価に用いている。これらはコードブックが事前学習され、対象モデル・層へ適用できることを前提とする。

## 既存研究との差

KIVIはスカラー量子化を用いてKVの保存ビット数を下げるが、VecInferは小ベクトルと代表点の対応を使うため、異なる小ベクトル次元と索引幅を選べる。MILLIONもベクトル量子化を採用するが、鍵の外れ値によって代表点の利用が偏る問題に対し、VecInferは注意内積を保存する二重変換で分布を先に均す。特に1.5ビットのLongBench平均で両方式の差が大きいことが、単にVQを使うだけでは不十分である証拠になっている。

また、量子化したKVを別の復号処理で全量展開すると、圧縮率が高くても注意計算前後のHBM転送が律速になる。VecInferは索引から代表ベクトルをタイル内で取り出し、注意スコアと値の集約を融合することで、量子化表現を実際の長文脈デコード速度へつなげる。品質を守る変換と、速度を得るカーネルの二つが独立した貢献である。

## 限界と未評価事項

校正尺度はPileの標本から求め、コードブックはQasperで学習するため、校正・事前学習なしで即座に任意のモデルへ適用できる方式ではない。コードブックが別データセットにも適用可能であることを付録で示すが、すべての言語・領域で同じ品質が得られる保証はない。量子化ビット幅を1.25まで下げると平均点は50.3へ低下し、数学推論のAIME24のような難題では2ビットでも無視できない悪化がある。

高速化の大きな倍率は192K級の長文脈とH100単一バッチという、KV読み出しが特に重い条件に依存する。短い系列、演算器が律速の大バッチ、共有メモリに収まらないコードブックでは同じ倍率は期待できない。融合カーネルを持たない比較方式がメモリ不足となる場合があり、実装条件の公平性には留意する必要がある。量子化によりメモリ容量が減ることと、モデル全体の品質・速度が常に改善することは別である。

GPUカーネルはCUDAと特定のGPUメモリ階層を前提としており、CPU、別アクセラレータ、複数GPU間でのKV共有、推論サーバ全体の同時要求制御などは本論文の主要評価対象ではない。論文の表は指定されたモデル・課題の実測であり、未測定のモデルや長さへの性能保証として扱わない。

## 実装状況

VecInferは校正とコードブック事前学習を経て、生成時にKV索引を更新し、融合CUDAカーネルで注意計算を行う実装として評価されている。H100 80GBとA100 40GBでカーネルとデコード遅延を測定し、付録に追加のバッチ・系列長・モデル別品質結果を示す。一次論文の本文と公開ページでは公式コード配布先を確認できなかったため、公開実装の有無は未確認とする。
