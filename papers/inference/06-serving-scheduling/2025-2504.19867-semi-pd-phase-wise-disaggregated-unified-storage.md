# semi-PD: Towards Efficient LLM Serving via Phase-Wise Disaggregated Computation and Unified Storage

> 入力処理と逐次生成の計算をSM単位で分離しつつ高帯域メモリを共有し、完全分離方式のKV転送と保存容量の偏りを除いてエンドツーエンド遅延を最大2.58倍改善する。
## 書誌情報
- **著者**: Ke Hong, Lufang Chen, Zhong Wang, Xiuhong Li, Qiuli Mao, Jianping Ma, Chao Xiong, Guanyu Wu, Buhe Han, Guohao Dai, Yu Wang
- **著者・所属**: Tsinghua University; Infinigence-AI; Shanghai Jiao Tong University

- **実装**: DistServe系実装とSGLang系実装を構築し、cluster-scaleではNVIDIA Dynamoへsemi-PD instanceを統合する。本文から公開code URLは確認できない。
## 概要
semi-PDはプリフィル/デコード分離の利点をGPU間ではなく同一GPU内のSM分割で実現し、重みとKV キャッシュは統合HBMで共有するLLM serving systemである。計算資源controller、unified メモリ manager、低オーバーヘッド worker switching、SLO-aware 動的 partitioningを組み合わせ、完全分離方式の重み複製・KV転送・storage imbalance・粗粒度resource adjustmentを避ける。A100/H200/A800上のLlama/DeepSeek評価で、DeepSeek系列の平均E2E 遅延を1.27–2.58倍削減し、Llama系列ではSLO内リクエストを1.55–1.72倍多く処理する。

semi-PDは、入力処理と逐次生成を分離する利点の本質は計算干渉の隔離であり、保存領域まで分離する必要はないという観察から出発する。同一GPU内でストリーミングマルチプロセッサを入力処理用と逐次生成用に分け、二つの作業器を独立に実行する一方、モデル重みとKVキャッシュは一つの高帯域メモリ領域で共有する。これにより、完全分離方式の計算隔離を保ちながら、入力処理側で余る保存容量を逐次生成側も利用でき、段階間KV転送も不要になる。さらにサービス品質目標を監視して計算資源比率だけを動的に変えるため、GPUの役割変更や既存KVの移動を伴わず負荷変化へ追従できる。計算資源と保存資源を別々の設計軸として扱い、計算だけを段階分離し保存は統合する組合せを明示した点が論文固有の提案である。
## 問題設定
統合型の大規模言語モデル提供では、入力処理（プリフィル）と逐次生成（デコード）が同じGPU計算資源を奪い合う。入力処理を優先すると生成トークン間隔が悪化し、逐次生成を優先すると最初のトークンが返るまでの時間が悪化する。入力処理を小分けにする方式でも、同じGPU上で異なる計算特性の処理が競合する問題は完全には消えない。一方、入力処理と逐次生成を別GPUへ完全分離すると計算干渉は減るが、保存領域まで分離されるため新しい無駄が生じる。入力処理側は短時間しかKVを保持せず高帯域メモリが余るのに対し、逐次生成側は系列全体のKVを抱えて先に容量不足になる。論文の測定では入力処理GPUのメモリが最大89.33%使われない例がある。さらに入力処理で生成したKVのGPU間転送、両側へのモデル重み複製、負荷変化時のGPU役割変更とKV移動が必要になる。高い要求到着率では逐次生成側の保存容量不足と生成トークン間隔の急増が対応し、約3倍まで悪化する例を示す。
## 新規性
semi-PDは、入力処理と逐次生成を分離する利点の本質は計算干渉の隔離であり、保存領域まで分離する必要はないという観察から出発する。同一GPU内でストリーミングマルチプロセッサを入力処理用と逐次生成用に分け、二つの作業器を独立に実行する一方、モデル重みとKVキャッシュは一つの高帯域メモリ領域で共有する。これにより、完全分離方式の計算隔離を保ちながら、入力処理側で余る保存容量を逐次生成側も利用でき、段階間KV転送も不要になる。さらにサービス品質目標を監視して計算資源比率だけを動的に変えるため、GPUの役割変更や既存KVの移動を伴わず負荷変化へ追従できる。計算資源と保存資源を別々の設計軸として扱い、計算だけを段階分離し保存は統合する組合せを明示した点が論文固有の提案である。
## 手法
### 手法のあらまし
各GPU上には入力処理作業器と逐次生成作業器を別々の実行過程として置く。計算資源制御器は、各作業器が利用できるストリーミングマルチプロセッサ集合を制限し、両者を同時に走らせる。大きな行列積を含む入力処理が逐次生成の小さな反復計算を全面的に塞がないよう、実行資源を段階ごとに隔離する。保存側では二作業器が同じモデル重みと同じKVキャッシュ領域を参照する。入力処理が生成したKVはそのGPU上に残り、逐次生成作業器が索引情報を引き継いで直接利用するため、段階切替時のGPU間KV転送を除去できる。共有メモリ管理器はKVブロック確保を原子的操作として実装し、二作業器が同時に空き領域を確認して同じブロックを重複確保する競合を防ぐ。実行時制御器は、入力処理待ち行列、逐次生成待ち行列、GPU利用率、最初のトークンまでの時間、生成トークン間隔の余裕を観測する。どちらの段階がサービス品質目標違反の律速になっているかに応じて、二作業器へ割り当てる計算資源比率を変更する。保存位置は変えないので、比率変更のためにモデル重みを再配置したりKVを移動したりする必要がない。実装は入力処理の小分け、逐次生成バッチ制御、CPUとGPUの処理重ね合わせも併用する。クラスタ規模では、semi-PD構成を通常の入力処理専用構成、逐次生成専用構成と同じNVIDIA Dynamoのルータへ接続し、KV命中率、GPU利用率、待ち行列長に応じて要求を振り分ける。

### ストリーミングマルチプロセッサ単位の計算隔離
入力処理と逐次生成を別作業器として実行し、各作業器が使用できるストリーミングマルチプロセッサ集合を制限することで、同一GPU内に段階別の計算隔離を作る。別GPUへ各段階を固定する完全分離方式と異なり、計算資源比率を変更するだけで処理能力を片側から他方へ移せる。モデル重みやKVの保存位置は変えないため、資源調整時に大容量状態を転送する必要がない。入力処理側の大きな行列積が逐次生成の一トークン処理を長時間塞ぐ状況を抑えつつ、入力要求が急増したときは入力処理へ、長い生成要求が蓄積したときは逐次生成へ、より多くの計算資源を与えられる。計算隔離の粒度をGPU単位からGPU内部へ細かくしたことが、保存領域統合と動的調整を両立させる基礎となる。

### 統合メモリ管理器
モデル重みとKVキャッシュを入力処理作業器と逐次生成作業器で別々に複製せず、同じGPU高帯域メモリ上の一つの保存領域として管理する。入力処理が生成したKVブロックは物理的にその場へ残り、逐次生成作業器は索引と付随情報を受け取って直接参照する。このため完全分離方式で必要な段階間KV転送を除去でき、入力処理側で余っていた保存容量も逐次生成側の長い系列へ使える。二作業器が同時に空き容量を確認すると、同じ空きブロックを選んでしまう読み取り後書き込み競合が起こり得る。そこで空き領域確認、ブロック取得、利用率更新を一つの原子的な割当操作としてまとめる。これにより非同期に二作業器が進んでも、同じKVブロックの重複割当や管理情報の不整合を防ぐ。

### 低費用の作業器切替
負荷比率が変わったとき、完全分離方式のようにGPU全体の役割を入力処理用から逐次生成用へ変更したり、逆方向へ変更したりしない。代わりに、同じGPU上ですでに存在する二作業器へ割り当てるストリーミングマルチプロセッサの比率だけを更新する。モデル重みとKV保存領域は共有されているため、既存の状態を別GPUへ移す必要がなく、調整の主要経路を計算資源設定の変更へ縮められる。この低費用切替により、固定比率では追従できない短時間の入力処理集中や長時間生成の蓄積に対して、より細かい時間尺度で資源を寄せられる。切替自体が大きな転送を伴わないことが、次のサービス品質目標に基づく動的分割を実用的にする。

### サービス品質目標を考慮する動的資源分割
最初のトークンまでの時間と生成トークン間隔という二種類のサービス品質目標を別々に監視し、現在の要求到着率と待ち行列状態から、どちらの段階が目標違反の律速になっているかを判断する。固定の半分ずつという分割では、入力処理中心の時間帯と逐次生成中心の時間帯の両方へ適応できない。そこで低費用な作業器切替を利用し、実行中に計算資源比率を変更する。目的は単純なGPU利用率最大化ではなく、二種類の遅延制約をともに満たす要求数を増やすことである。保存領域は共有されたままなので、計算比率を変えてもKVの所在は維持される。この構造により、計算能力の不足と保存容量の不足を別問題として扱い、前者には資源比率変更、後者には統合保存領域の余裕を利用する。

### クラスタ規模の混成配置
単一のsemi-PD構成だけでクラスタ全体を置き換えるのではなく、通常の入力処理専用構成、逐次生成専用構成、semi-PD構成を同じクラスタへ配置する。NVIDIA Dynamoのルータは、KVキャッシュ命中率、GPU利用率、待ち行列長を共同で観測し、新しい要求の入力処理を通常構成へ送るかsemi-PDへ送るかを決める。semi-PDへ送った要求は逐次生成まで同じ構成内で完了できるため、段階間KV転送を避けられる。一方で通常の完全分離経路も残すため、入力処理と逐次生成の比率が極端な負荷では専用構成の利点を利用できる。論文はこの混成配置により、単一方式へ固定するより広い負荷範囲へ対応することを狙う。

### 全体のデータ／制御の流れ
計算面は二つの作業器とストリーミングマルチプロセッサ分割制御器、保存面は共有モデル重み・共有KV領域と原子的ブロック割当器、方策面はサービス品質目標を考慮する動的資源分割器から成る。クラスタではKV命中率、GPU利用率、待ち行列長を見て、通常の段階分離構成またはsemi-PD構成へ新規要求を送る。
## 評価条件
- **ハードウェア**: Server A: NVIDIA A100 80GB SXM4×8, NVLink、Server B: 4 nodes×NVIDIA A100 40GB SXM4×8, cross-node 200Gbps、Server C: NVIDIA H200 141GB SXM5×8, NVLink、Server D: NVIDIA A800 80GB SXM4×8, NVLink
- **データセット／トレース**: ShareGPT、LongBench、MATH-500、95% ShareGPT + 5% long-input 合成 cluster ワークロード
- **比較対象**: DistServe 1P1D、vLLM 0.6.0 default、vLLM SplitFuse chunk_size 1024、SGLang 0.4.4、NVIDIA Dynamo 0.1.1 2P6D
A100 80GB単node、A100 40GB 4node、H200 141GB単node、A800 80GB単nodeを含む実機評価。リクエスト rateはper-GPU。Llama3/3.1 8B・70B・405BとDeepSeek-V2-Lite 16B、DeepSeek-V3 671Bを対象にする。
## 主要結果
semi-PDは高リクエスト rateでプリフィル/デコードのどちらか一方だけが遅延 explosionする従来unified/disaggregated方式に対し、両phaseのP90/P99 遅延を同時に安定させる。DeepSeek系列では平均リクエスト E2E 遅延をstate-of-the-art比1.27–2.58倍削減し、Llama系列では設定したTTFT/TPOT SLOを満たしながら1.55–1.72倍多いリクエストを処理する。背景には、完全PDで最大89.33%発生するプリフィル側メモリ浪費とphase間KV transferを共有HBMで除き、SM単位partitionを実行中に変更できるため、デコード側OOMやワークロード比率変化でGPU roleを再配置する必要がないことがある。絶対的に全条件で最小遅延というより、リクエスト rateが上がり従来方式が干渉またはstorage不足で急激に悪化する領域で有効スループットを維持する点が主要な実用効果である。

- DeepSeek系列 average E2E 遅延 / 1.27–2.58倍削減 (比較対象: SGLang等state-of-the-art serving; 条件: DeepSeek-V2-Lite/DeepSeek-V3、高リクエスト rate) — phase interferenceを避けつつKV transferなしの共有storageを使うことでリクエスト-level 遅延を改善。

- Llama系列 SLO-constrained served リクエスト / 1.55–1.72倍 (比較対象: vLLM/DistServe等; 条件: TTFT/TPOT SLO内、90%以上attainment基準) — 単純スループットではなく遅延 constraintを守れる有効スループットが増える。

- プリフィル側メモリ waste / 最大89.33% (比較対象: disaggregated storage; 条件: Llama3 8B/70B, ShareGPT/LongBench解析) — P/D別HBM poolではプリフィル側KV容量が余りデコード側OOMを救えない。

- storage shortage時TPOT / 約3倍 (比較対象: ideal storage; 条件: A100 40GB、デコード KV capacity exhaustion) — storage imbalanceが遅延 explosionへ直結することを動機実験で確認。

- P99安定リクエスト rate / Llama3-8Bで11 req/s超、Llama3-70Bで8 req/s (比較対象: 他方式はTTFTまたはTPOTが急増; 条件: ShareGPT) — tail 遅延でも両phaseを同時に安定化する。

### 負の結果・境界条件
- 低リクエスト rateでは従来方式の遅延 interferenceやstorage shortageが顕在化せず、semi-PDの優位は高負荷時ほど大きい。
- 同一GPU内SM分割のため、プリフィルとデコードに完全に異なるGPU種類を割り当てるSplitwise型heterogeneous specializationとはtrade-offが異なる。
- cluster-scaleではルーティングと既存P/D instanceを併用するため、全clusterをsemi-PDだけへ置換する設計ではない。

### 結果の読み方
semi-PDの結果はプリフィル/デコード disaggregationの価値を『別GPU』ではなく『計算資源の独立性』へ分解できることを示す。storageを共有したままSMだけ分けることで遅延 isolationとメモリ poolingを同時に得られ、ワークロード変動時のresource adjustmentもKV移動なしで細粒度化できる。
## 品質への影響
model 重み、precision、attention計算をserving方式間で同等に保つsystem最適化であり、生成品質を意図的に近似しない。
## 既存研究との差
DistServeはプリフィル/デコードを別GPUへ置きphase-specific parallelismを選ぶため遅延 isolationは強いが、両側に重みを持ちKVを転送する。semi-PDは同一GPU内でworkerを分離してSMだけをpartitionし、HBMを共有することでtransferとreplicaをなくす。Sarathi-Serveはchunked プリフィルで同じバッチへP/Dを混在させ干渉を緩和するが、semi-PDはカーネル実行資源自体を分離する。
## 限界
- 同一GPUでP/Dが計算資源を共有するため、完全に異種GPUへphaseを割り当てる方式のhardware specializationは直接得られない。
- SM partition機構はGPU ランタイム/カーネル実装への変更を必要とし、一般的なserving stackへ無変更で適用する方式ではない。
- 利得は高リクエスト rateで大きく、低負荷では従来方式との差が小さくなり得る。
- cluster運用ではsemi-PDと従来P/Dを混在させるルーティング policyが追加される。
## 実装状態
DistServe系およびSGLang系prototypeを実装し、NVIDIA Dynamoへcluster-scale semi-PD instanceを統合してA100/A800/H200実機で評価している。公開code URLは確認した本文には記載されない。
## 研究上の位置づけ
プリフィル/デコード disaggregation研究に対し、phase isolationに必要なのはstorage separationではなくcomputation separationだという設計点を示した研究。今後のPD systemではGPU/node単位だけでなくSM partitionやshared KV poolを含む中間粒度が比較軸になる。
