# SAP：構文依存関係を使った注意頭の構造的枝刈り

## 概要

SAP（Syntactic Attention Pruning）は、Transformerの複数頭注意（multi-head attention）に含まれる各注意頭（attention head）が、文の構文依存関係をどの程度捉えているかを調べ、言語理解にとって重要でないと判定した頭を**再学習なしで削除する**構造的枝刈り（structured pruning）手法である。通常の重み絶対値や勾配に基づく重要度とは異なり、主語と動詞、名詞と修飾語、前置詞句などの構文関係をどの注意頭が参照しているかを直接使う。追加の候補選別（candidate filtering; CF）では、候補頭を実際に除去したときの下流タスク精度低下を測り、許容精度を保つ範囲で削除する。

原著の実験は**BERT_BASE（12層、各12頭、隠れ次元768）**とGLUEの6タスクが中心である。構文情報を用いるSAPは、比較対象の勾配に基づく再学習不要な注意頭削除法より、特に高い疎性率で性能低下を抑えたと報告する。ただし、原著の図5〜7は主にグラフによる比較であり、論文本文にはすべてのタスクのスコアを一覧にした数値表がない。グラフを読み取っていない小数点付きの改善値を推測して記載してはならない。また、**生成LLMのトークン毎秒、GPUメモリ削減率、実際の推論遅延**は測定していない。BERTの頭削除がそのままLlamaやQwenの高速化につながると解釈しないことが重要である。

## 背景：なぜ注意頭を言語学的に評価するか

Transformerの多頭注意は複数の注意頭が異なる入力関係を学習する。従来の注意頭削除は、重みの大きさ、勾配感度、活性値、学習可能なマスクを用いて重要度を推定する。これらは一般的な数値指標として扱いやすい一方、削除した頭がどの言語現象を処理していたかの解釈が難しい。BERTの注意頭には、目的語、限定詞、前置詞、主語など特定の依存関係へ注意を集中する頭があることが先行研究で知られている。

SAPは、重要な構文依存関係を多く捉える頭を残すという仮説を立てる。例えば、名詞句の修飾関係、主語と述語の関係は、文章の意味解釈に影響する可能性がある。対象データ集合に出現する依存関係を数え、頻度の高い関係を優先的に保つ。ただし**出現頻度が高い構文関係が必ずタスク精度への因果的寄与が大きいわけではない**。この限界を補うため、SAP単独の構文ランキングに加えてCFによる実際の精度感度検査を導入する。

## 手法：構文統計から注意頭削除まで

### 1. 依存構文解析と頻度ランキング

最初に対象データ集合の各文を構文解析し、トークンを頂点、依存関係を有向辺とするグラフへ変換する。Universal Dependenciesのラベル体系に沿って、名詞主語`nsubj`、前置詞修飾`prep`、形容詞修飾`amod`、前置詞の目的語`pobj`、助動詞`aux`などを抽出する。実装ではspaCy 3.6.0を使い、各ラベルの出現回数をデータ集合全体で合算する。

各タスクで出現頻度上位k種類を「重要な依存関係」とし、それ以外を「非上位関係」とする。上位の依存関係には順位に応じて大きな重みを付け、下位の関係にも順位に応じたペナルティ重みを与える。上位kの選び方は実験の重要なハイパーパラメータであり、原著はk=1〜10を試し、GLUEでは多くのタスクで`prep`、`nsubj`、`amod`、`pobj`が上位に入ると報告する。

構文解析器の出力が正しくない場合、頻度ランキングも誤る。文法的に非標準な文章、プログラミング言語、数式、複数言語混在テキストでは、英語の一般的な依存解析と同じ意味のランキングを期待できない。

### 2. 注意マップと構文辺の対応付け

同じデータ集合を枝刈り対象モデルへ入力し、各層・各頭の注意マップを取得する。層数L、頭数H、系列長nに対し、注意テンソルは概念的に`[L,H,n,n]`であり、各構文辺に対応するトークン対の注意値を調べる。注意閾値は全サンプル・全頭の注意値を集めた**全体平均**から定める。上位kの構文関係に属するトークン対で注意が閾値より低い場合、その頭は重要な構文を十分に捉えていないとしてペナルティを加算する。逆に、下位の構文関係に注意が閾値より高い場合にも、優先度の低い関係へ注意を費やしているとして加算する。

各頭の累積ペナルティを`cnt_{l,h}`とする。値が大きいほど、データ集合で重要とされた構文関係との整合性が低いと判定する。原著の例では、上位依存関係の`amod`に対する注意が閾値0.01より低い0.002であると、順位重みに応じてカウンタが増える。反対に上位関係`prep`へ十分な注意があれば、その関係についてはペナルティを増やさない。単に注意値の総量を測るのではなく、**どの種類のトークン対に注意を向けたか**を評価するのが特徴である。

注意マップの値は必ずしも説明可能性の十分条件ではない。注意重みが大きくても、その頭の出力射影を通じた最終予測への影響が小さい場合がある。SAPはこの問題を構文ベースの近似として扱い、後段のCFで実際のタスク精度を調べる。

### 3. 構文ペナルティによる候補選定

データ集合の依存関係の重み付き総出現数をS、枝刈り制御パラメータをRとし、`cnt_{l,h} >= S × R`を満たす頭を削除候補とする。ペナルティの大きい順に調べる。原著の説明例ではS=4644、R=0.75で閾値は3483となり、4371、3704、3529の頭が候補に入る。Rを小さくすると閾値が下がるため、より多くの頭が候補になる。これは「Rが小さいほど削除が弱い」という直感と逆なので注意する。

目標疎性率に達しない場合はRを段階的に下げて候補を増やす。頭を一定以上削除した層は層ごと削除する処理も記述されている。ただし層削除と頭削除の混在が、異なる実装でどの程度の実演算削減になるかは、モデルの重み形状とカーネル実装に依存する。ゼロマスクを置いただけではGPUの行列積の次元が減らず、実際の高速化につながらない可能性がある。

### 4. 候補選別（CF）と性能許容値

構文ペナルティだけで一度に多くの頭を削除すると、タスク精度が急落する場合がある。CFでは利用者が、元モデルの例えば90%という**性能許容値**を指定する。まずSAPが挙げた各候補頭を単独で削除し、元モデルと比較して下流タスク性能がどの程度低下するか測定する。低下の小さい順に候補を並べ直し、元のモデルから一頭ずつ追加削除して性能を再評価する。許容値を下回った時点で停止する。

この手続きは再学習を要求しないが、候補ごとに推論評価を繰り返すため、**枝刈り前の探索費用がゼロになるわけではない**。候補の単独削除時の影響と複数頭を同時に削除したときの相互作用は異なるため、CFは各ステップで追加削除後の性能を再測定する。評価データと運用データの分布が違う場合には、許容精度を保てる保証はない。

## 評価条件と比較手法

| 項目 | 原著の設定 |
|---|---|
| モデル | BERT_BASE、12層×12頭、隠れ次元768、事前学習済みモデルを下流タスクへ適合 |
| タスク | GLUEのCoLA、SST-2、QQP、STS-B、MNLI、QNLI |
| 比較 | Kwonら（2022）の再学習不要な注意頭マスクに基づく手法。公平性のためFFNマスクを無効化しMHAのみを削除 |
| SAP設定 | spaCy 3.6.0、k=1〜10、Rの初期値0.5、目標疎性率へ達するまでRを調整 |
| ハードウェア | Intel Core i9-12900K、NVIDIA GeForce RTX 3090 |
| 条件 | 主評価は削除後の追加学習なし。別途、疎性率0.75で少数エポックの再学習も評価 |
| 指標 | 各GLUEタスクの精度・相関指標、疎性率、注意マップの可視化、kの感度 |

比較対象は特定の2022年手法を原著が再現した条件であり、現代の大規模生成LLM向け構造枝刈り法すべてを網羅した比較ではない。BERTの双方向エンコーダで得た結果を、自動回帰デコーダやMoEの注意構造へそのまま適用するのは不適切である。

## 評価結果と定量的な読み方

### 再学習なしの性能曲線

図5は疎性率を変えたときのGLUE性能を比較する。SAPは勾配ベースの比較方式より性能曲線が平坦で、高い疎性率でも性能低下が小さい傾向を示す。SAP+CFはSAP単独よりさらに性能を維持した。これは構文依存関係だけで削除候補を選ぶ粗い段階と、実際の精度感度で選び直す段階が補完的であることを示す。

ただし本文は「何%の頭削除でGLUE平均が何点改善」といった一つの代表値を定量表として与えていない。図の各タスクを精密に数値化せず、本文だけから架空の改善率を作るべきではない。性能曲線が平坦という主張は、**BERT_BASEのGLUEという限定された条件**で成立する実験観察である。

### 再学習した場合の追加回復

図6では疎性率0.75の削除済みモデルに少数エポックの再学習を追加すると、SAPとSAP+CFの双方で性能が回復する。原著の主張は「再学習しなくても比較手法より強い」ことであり、「再学習を加えると必ず不要なほど精度が高い」という主張ではない。再学習を許すと、枝刈り後の最終精度だけでなく、追加のGPU計算費用も比較すべきである。

### 構文の選び方kと負の結果

図7はMNLIとSTS-Bについてk=1〜10、疎性率0.25・0.5・0.75を比較する。良い結果は概ねk=3〜7に集中し、kが小さすぎても大きすぎても性能が落ちる。kが小さすぎると重要とみなす依存関係が少なすぎて頭の役割を識別しにくく、kが大きすぎると重要な依存関係に注意を向ける頭まで不適切に削除し得る。したがって「構文関係を多く含めるほど正確になる」とは限らない。原著は実験したkの中から最良値を選んでいるため、未知のタスクでのk選択コストが残る。

### 注意マップの可視化

QNLIの例では、比較方式で削除された頭の注意マップには強い注意値を持つ構文辺が残っている一方、SAPで削除した頭は重要な構文への注意が比較的弱い。これはSAPの枝刈り基準が狙いどおり構文関係を残す方向へ働いている定性的証拠である。ただし、可視化した少数の頭のパターンからモデル全体の意味理解を保証できるわけではない。構文への注意集中は解釈の手掛かりであって、下流性能への因果寄与を単独で証明するものではない。

## 推論効率への含意と関連研究との差

本研究の位置づけは、学習済みTransformerの構造圧縮を目的とする「削除候補選定法」である。注意頭が実際に削除され、投影行列の対応次元や出力射影が物理的に縮小されるなら、モデルの一部の重みと計算量を減らせる可能性がある。これに対し、実行時にゼロマスクで注意頭を無効化するだけでは、GPU行列積の形状が変わらず高速化しないことがある。原著の実験は下流タスク性能の保持に重点があり、処理時間・GPUメモリ・電力の実測値は提供しない。

SmoothQuant、GPTQのような量子化は重み表現のビット幅を削減するが、SAPは注意頭という構造単位を削除する。層削除、FFNチャネル枝刈り、MoE専門家削除とも異なる。注意頭の構文機能を解釈できる点は、数値指標だけの構造枝刈りに対する特徴である。一方、モデル規模が大きいほど注意マップの収集はメモリと時間を要し、長文脈モデルでは`n×n`の注意行列を全頭で保持する負担が大きい。FlashAttentionのように注意行列を明示的に保持しないカーネルを使う場合、追加の注意統計取得経路が必要になる。

生成LLMに移植する場合、BERTとは異なる因果マスク、Grouped-Query Attention（GQA）、Multi-Query Attention（MQA）、位置符号化、KV頭共有を考慮しなければならない。クエリ頭だけを削除してもKV頭や投影行列が共有されている場合、単純に重みを切り詰められない。したがってllama.cpp等の推論実装における実測高速化には、モデルの物理的な再構成と実行カーネルの対応が別途必要である。

## 限界・再現上の注意

第一に、原著の評価はBERT_BASEとGLUEの6タスクに限定される。著者はTransformer言語モデル全般への適用可能性を述べるが、Llama・Qwen・MoE・多言語LLMでの検証結果はない。英語の構文依存解析で得たランキングが、プログラミング言語、数学、非英語、チャット形式の生成へ一般化するかは不明である。

第二に、構文依存関係の出現頻度は、下流タスクへの実際の重要度と同義ではない。複数の頭が異なる構文機能を持ち、一つの頭が複数の関係を扱う場合、SAPの単純な上位k方式では区別が難しい。論文自身も多様な構文関係へ注意する頭が多数ある場合の識別力を限界として認めている。CFは性能低下を実測してこの問題を緩和するが、候補ごとの推論費用を増やす。

第三に、再学習なしでの性能保持は示されるが、圧縮後の推論レイテンシ、メモリ帯域、GPU占有量、生成トークン毎秒は測定されていない。実際の枝刈りで投影行列の次元が小さくなっても、GPUカーネルのタイルサイズやメモリアクセス効率によって実行速度は単純な削除率に比例しない。

第四に、k=1〜10から最良のkを選ぶ実験はタスク依存のハイパーパラメータ探索を含む。未知タスクでその選択を再現するには検証集合が必要であり、検証データに過度に合わせると汎化性能が下がる可能性がある。構文解析器の誤り、トークン化と単語単位依存関係の対応付けも再現上の重要な条件となる。

第五に、CFの「元モデルの90%を保つ」などの許容値は下流評価集合に対する閾値である。候補を一つずつ削除する過程で頭同士の相互作用が起きるため、単独削除の順位が複数削除後も最適とは限らない。再学習ありの性能回復を含める場合には、その追加費用も評価すべきである。
