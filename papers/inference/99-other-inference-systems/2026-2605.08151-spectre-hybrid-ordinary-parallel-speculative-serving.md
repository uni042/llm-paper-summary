# SPECTRE: Hybrid Ordinary-Parallel Speculative Serving for Resource-Efficient LLM Inference

## 書誌情報

- **著者:** Jincheng Xie, Yawen Ling, Qi Xiao, Feiyu Zhang, Zhongyi Huang, Wen Hu, Yu Zheng
- **公開:** arXiv:2605.08151（2026）
- **分類:** Inference / speculative decoding / multi-tenant serving
- **実装:** SGLang上の実装。論文から `sgl-project/sglang` PR #22272 が案内されている。

## 一文要約

利用率の低い小型model serviceを大型modelのremote draft modelとして共用し、draft生成とtarget検証を並列化しつつ、rollbackが増えたときだけ通常の逐次speculative decodingへ戻すことで、multi-tenant環境の余剰GPU資源を推論高速化へ転用する。

## 問題設定

multi-model servingでは、人気の大型modelが混雑する一方で、小型model serviceのGPUが低利用率になることがある。通常のspeculative decodingではdraft生成とtarget検証が直列になりやすく、draft専用GPUを追加するとsystem全体のresource効率も悪化する。単純に両者を並列化すると、先に作ったdraftが検証結果と食い違った場合に投機計算が無駄になり、高concurrencyや高速なtarget側では逆に性能が落ちうる。

## 手法

SPECTREはdraft modelをtarget modelと同居させず、独立した小型model serviceをremote drafterとして利用する。drafterは本来の利用者requestも処理しながら、targetから来るdraft requestを同じGPUで処理する。

中核は **hybrid ordinary-parallel speculative decoding** である。各roundで、並列に先行生成したdraftが無効になった割合（rollback ratio）を観測し、draft時間・target検証時間・受理token長から導いたthresholdと比較する。rollbackが十分少ない場合は次roundのdraft生成を現在roundのtarget検証と重ね、draft latencyをcritical pathから隠す。rollbackが多く、先行計算の廃棄costが大きい場合は通常の「draftしてから検証する」実行へ戻す。つまり常に並列化するのではなく、観測した無駄計算量に応じて並列化の採否を切り替える。

さらに、remote drafterではspeculative requestを優先してdraft-target overlapを維持しつつ、一定間隔で通常requestも処理してmulti-tenant serviceを飢餓させない。target側がtensor parallelismなどで高速な場合にはdraft側prompt contextを圧縮し、draft生成そのものがcritical pathになるのを抑える。

## 評価条件

論文はSGLang上に実装し、複数のdraft-target model pair、reasoning workload、long-context workload、複数batch sizeで評価している。大型構成には **Qwen3-235B-A22Bをtensor parallelism 8** で動かし、Qwen3-0.6Bをremote drafterとして使う構成を含む。評価はautoregressive decoding、通常/並列speculative decoding系baselineと比較する。

これはsimulationだけの評価ではなく、実際のGPU上で動くserving implementationを用いたsystem評価である。

## 主要結果

- autoregressive decodingに対して最大 **2.28×** のspeedupを報告する。
- strongest speculative decoding baselineに対して最大 **66%の追加改善**を報告する。
- Qwen3-235B-A22BをTP=8で動かす高concurrency構成でも、純粋なparallel speculative decodingがautoregressive baselineを下回る条件に対して、hybrid切替により性能低下を避けながら改善を維持する。
- remote drafterを専用GPUにせず既存の小型model trafficと共有するため、draft用resourceを追加する方式よりsystem全体のGPU利用率を高められる。

数値はarXiv版の同一評価から扱い、異なる版の結果とは混在させない。

## 既存研究との差

通常のspeculative decodingはdraftとverifyを直列に進めるためdraft latencyが残り、parallel speculative decodingはそれを重ねられる代わりにrollback時の先行計算を失う。SPECTREの差は、**parallelかordinaryかを固定せず、実行中のrollback ratioとlatency関係から切り替えること**にある。

また、draft modelを専用sidecarとして確保するのではなく、すでに存在する低利用率の小型model serviceをmulti-tenant remote drafterとして再利用する点がserving systemとしての特徴である。

## 限界

- 利益は、再利用できる小型model serviceが存在し、draft-target間通信とdraft latencyを十分抑えられるdeploymentに依存する。
- parallel modeの有効性はdraft acceptance / rollback、batch size、targetとdraftの相対速度に強く依存する。
- mode選択はbatch全体のrollback ratioを主に扱うため、requestごとのacceptance特性の違いを完全にはモデル化しない。
- SGLangへのscheduler / executor / communication統合を伴い、単純な設定変更だけで既存serving stackへ導入できる方式ではない。

## 一般的な実装上の含意

speculative decodingでは「draft modelをどれだけ小さくするか」だけでなく、**draftとverifyを時間軸上でどう重ね、失敗した投機計算をいつ止めるか**がthroughputを左右する。また、fleet内に低利用率model endpointがある場合、専用drafterを増設せず余剰GPU時間を別modelの推論高速化へ貸し出す設計が成立しうる。

## 引用関係

SPECTREは通常のspeculative decodingと、draft生成をtarget検証に重ねるparallel speculative decodingを直接の比較対象とする。serving側では、SGLangを実装基盤として利用し、remote drafterを独立serviceとして扱うことでmulti-tenant resource sharingへ拡張している。
