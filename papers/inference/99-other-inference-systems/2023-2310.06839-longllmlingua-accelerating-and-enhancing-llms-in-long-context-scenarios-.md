# LongLLMLingua: Accelerating and Enhancing LLMs in Long Context Scenarios via Prompt Compression

## 概要
LongLLMLinguaは、長いプロンプトを単に一律に切り詰めるのではなく、「質問に対してどの文書・トークンが有用か」を小型言語モデルで推定し、重要部分へトークン予算を集中させる長文脈プロンプト圧縮法である。元のLLMLinguaを長文脈向けに拡張し、質問条件付きの粗視化文書選別、対照的パープレキシティに基づく細粒度トークン圧縮、文書再配置、重要度別の動的圧縮率、回答内部分文字列の原文復元を一つのpipelineとして組み合わせる。

長文脈では入力トークン数そのものがAPI費用、prefill 遅延、KV キャッシュ生成量を増やすだけでなく、重要情報が文脈中央にあると利用率が落ちる「lost in the middle」型の位置バイアスも起こる。LongLLMLinguaは圧縮によって不要情報を除くだけでなく、重要文書をLLMが利用しやすい位置へ並べ替えることで、この位置効果も同時に緩和する。

ACL 2024版ではNaturalQuestions、LongBench、ZeroSCROLLS、MuSiQue、LooGLEなどで評価される。NaturalQuestionsではGPT-3.5-Turboへのプロンプトを約4分の1に圧縮しながら最大21.4%の性能向上、LooGLEでは約10倍圧縮でAPI費用を94.0%削減する。約10k-トークンのプロンプトを2〜6倍へ圧縮したエンドツーエンド測定では、圧縮器の追加計算を含めても1.4〜2.6倍の遅延短縮を報告する。

## 問題設定
長い文書集合と質問をそのまま対象 LLMへ渡すと、入力トークン数に応じてprefill計算とAPI課金が増える。単純truncateでは必要証拠を消し、BM25やembedding 検索で文書単位だけを選ぶと、選択文書内部の冗長トークンを残す。逆にトークン単位だけで圧縮すると、長大なプロンプト全体を小型LMで精査する計算が増え、質問と無関係な文書にも同じ圧縮予算を使ってしまう。

さらに長文脈LLMには位置依存性がある。NaturalQuestionsの分析では、正解文書をプロンプト中央へ置くと先頭や末尾より性能が落ちる。したがって「残す情報量」だけでなく、「どの文書を残すか」「文書ごとに何トークン残すか」「どの順に並べるか」を質問依存で決める必要がある。

もう一つの問題はトークン削除による表面形崩壊である。subwordの一部や固有名詞の周辺トークンを削ると、対象 LLMは正しい意味を推論しても出力文字列が原文と微妙にずれ、抽出的 QAやentity-centric評価で不利になる。LongLLMLinguaは圧縮後の対象 LLM出力を原プロンプトへ照合し、対応する原文部分文字列へ戻す後処理まで含める。

## 手法

### 1. 質問条件付きの粗視化文書選別
プロンプトを複数文書 (x_{doc_k}) に分け、小型言語モデルへ質問と文書を与え、質問がその文書とどの程度関係するかを条件付きパープレキシティで測る。論文では質問に制約 プロンプトを付けた (x_{que,restrict}) を用い、
[
r_k=-rac{1}{N_c}sum_i log p(x_{que,restrict,i}mid x_{doc_k})
]
で文書重要度を計算する。質問を文書から予測しやすいほど、その文書は質問に関連するとみなされる。

制約 プロンプトは「文書だけでは答えられない質問でも小型LMが一般知識から質問文をもっともらしく予測してしまう」挙動を抑えるための正則化である。構成要素除去実験（アブレーション）では制約を外すとLongBench平均が48.3から46.1へ低下し、単なる質問 likelihoodより制約付き評価が有効であることが確認される。

粗視化段階で低重要度文書を先に落とすため、後段の細粒度トークン評価を全プロンプトへ掛ける必要がない。これが圧縮器自身の計算量を抑える。

### 2. 対照的perplexityによる細粒度token選択
粗視化で残った文書内部では、各トークン (x_i) が質問によってどれだけ予測しやすくなるかを測る。重要度は
[
s_i=operatorname{PPL}(x_imid x_{<i})-operatorname{PPL}(x_imid x_{que},x_{<i})
]
として定義される。質問を条件にしたとき予測困難度が大きく下がるトークンほど、質問との関連が高いと判断する。

付録ではこの差が条件付き相互情報量（conditional pointwise mutual information）と対応することを示す。単純なトークン surprisalでは「文書内で珍しいだけのトークン」と「質問に答えるため重要なトークン」を区別しにくいが、質問条件付きとの差分を取ることで後者を優先できる。

トークン 重要度は反復的圧縮（iterative 圧縮）へ使われ、長文書をsegmentに分けながら低重要度トークンを削る。実装ではsegment size 200などを使い、全長を一度に小型LMへ通すmemory負荷を避ける。

### 3. 文書再配置による位置バイアス緩和
粗視化重要度 (r_k) を使って、残した文書を対象 LLMへ渡す順序も変更する。重要情報が中間位置に置かれると利用率が下がる傾向を利用し、重要度の高い文書をプロンプトの境界側へ移すことで、同じトークン数でも対象 LLMが証拠へ注意しやすくする。

NaturalQuestionsでは正解文書を1、5、10、15、20番目へ置く位置別評価を行い、LongLLMLinguaの完全構成は77.2/72.9/70.8/70.5/70.6を維持する。質問考慮型 粗粒度 圧縮を外すと42.1/40.3/39.7/40.1/40.3まで下がる。文書再配置単独の寄与は他機構より小さいが、LooGLEでは完全平均32.1に対して再配置なし30.9となり、長距離依存課題で一定の効果を持つ。

### 4. 文書重要度に応じた動的圧縮率
すべての文書へ同じ圧縮 比率を適用すると、重要文書の証拠まで過剰に削り、無関係文書へトークン予算を浪費する。LongLLMLinguaは文書rank (I(r_k)) に応じて細粒度圧縮率を変える線形schedulerを使い、重要文書ほど多くトークンを残し、低重要度文書ほど強く圧縮する。

全体の対象 圧縮 比率を固定したまま文書間で予算を再配分するため、API費用を増やさず情報密度を上げられる。LongBenchの構成要素除去実験では動的圧縮率を外すと平均48.3から45.7へ低下し、文書重要度を粗視化選択だけでなくトークン予算へ反映する必要があることが分かる。

### 5. 圧縮後のsubsequence recovery
対象 LLMが返したresponseから、圧縮プロンプトに含まれる最長一致部分文字列を見つけ、その部分文字列が元プロンプトのどの位置に由来するかを対応付ける。圧縮で途中トークンが欠けていた場合、その箇所を元プロンプトの連続部分文字列へ置換して表面形を復元する。

この処理は対象 LLMへ再問い合わせせずに行える。大量部分文字列照合はprefix treeやautomatonで高速化できる。特に固有名詞・数値・引用spanのように、意味は保たれてもトークン削除で文字列が崩れやすい抽出的 taskへ効く。LongBench平均は復元なし47.8、あり48.3で、寄与は小さいが一貫した改善を示す。

## 評価

### 条件
対象 LLMは主にGPT-3.5-Turbo-0613を使い、4Kを超えるプロンプトではGPT-3.5-Turbo-16kを用いる。open モデルとしてLongChat-13B-16kも評価する。圧縮器はLLaMA-2-7B-Chatを使用し、greedy decoding・temperature 0。実装はPyTorch 1.13.1とTransformersを基礎にする。

データセットはNaturalQuestionsのmulti-文書 QA、LongBench、ZeroSCROLLS、MuSiQue、長文依存を含むLooGLE。比較にはBM25などの検索、Selective 文脈、元LLMLinguaを含む。品質だけでなく入力トークン数、API コスト、圧縮 overheadを含むエンドツーエンド 遅延も測る。

### NaturalQuestions
GPT-3.5-Turboで約4倍圧縮した条件では、元プロンプトや既存圧縮法に対して最大21.4%の性能改善を報告する。圧縮で無関係文書を減らし、正解文書を位置的に有利な場所へ動かすため、「トークンを減らすほど性能が下がる」という単純な交換条件にならない。

位置別アブレーションでは完全構成がGT文書の位置1/5/10/15/20で77.2/72.9/70.8/70.5/70.6。質問考慮型 粗粒度 圧縮を外すと42.1/40.3/39.7/40.1/40.3まで低下し、SBERT置換でも完全に届かない。長文脈圧縮では一般semantic similarityより質問条件付きLM スコアが重要であることを示す。

### LongBenchと構成要素除去実験
LongLLMLinguaは平均48.3、平均1822 トークン、約6倍圧縮。質問考慮型 粗粒度 圧縮なしは37.4、SBERT置換36.4、条件付き確率の向きを誤った版30.6、制約なし46.1、fine-grained 質問 awarenessなし44.2、動的 比率なし45.7、subsequence 復元なし47.8、文書 reorderなし48.0である。

圧縮器をLLaMA-2-7B-ChatからGPT-2 Smallへ置換しても43.0まで下がる。したがってheadlineの品質は単なるトークン数削減だけでなく、質問条件付き重要度・動的 予算・一定能力を持つ圧縮器 モデルの組合せに依存する。

### LooGLE
約30,546 トークンの元プロンプトは検索 24.1、timeline 20.9、computation 13.5、reasoning 32.1、平均22.6。LongLLMLinguaは約3121 トークン、約10倍圧縮で40.0/35.0/19.7/33.6、平均32.1となる。圧縮しながら平均性能が9.5ポイント上がり、カテゴリによって最大15.9ポイント改善する。

この設定でAPI費用を94.0%削減する。長い不要文脈を除くことが対象 LLMの推論負荷だけでなく回答品質にも寄与する例である。

### end-to-end latency
圧縮器を追加するため、対象 LLMへ送るトークン数の削減率がそのまま遅延倍率にはならない。論文は約10k-トークン プロンプトを2〜6倍へ圧縮した条件で、圧縮器の実行を含むエンドツーエンド 遅延を1.4〜2.6倍短縮する。

圧縮率が低い、プロンプトが短い、対象 LLMが非常に高速な場合は圧縮器 overheadの割合が増える。したがってLongLLMLinguaは「すべてのプロンプトで圧縮器を通すほど速い」方式ではなく、長文脈ほど利得が大きい。

## 既存研究との差
検索-only方式は文書単位の削除には強いが、残した文書内部の冗長トークンを減らさない。Selective 文脈やLLMLinguaはトークン-level圧縮を行うが、LongLLMLinguaは長文脈で重要な質問条件付き文書選別、文書ごとの予算配分、位置再配置まで統合する。

また対象 LLM自体のarchitecture、KV キャッシュ、注意 kernelを変更しない。外部APIにも適用でき、入力トークン課金を直接減らせる点がsystem-level キャッシュ圧縮とは異なる。一方、圧縮済みプロンプトから削除した情報は後段で復元できないため、圧縮器の重要度推定が品質の新しいfailure pointになる。

## 限界
圧縮器としてLLaMA-2-7B-Chatを別途実行するため、短プロンプトや低圧縮率では追加推論費が利得を相殺する。API価格、対象 モデル速度、圧縮器 hardwareが変われば最適圧縮 比率も変わる。

質問条件付き重要度はQAに特に自然だが、質問が明確でない長文生成、全体要約、複数箇所を均等に統合するtaskでは「低重要度」と判断したトークンが後で必要になる可能性がある。削除は不可逆であり、subsequence 復元は表面形を戻せても、削除した意味情報そのものを復元する機構ではない。

文書再配置は対象 LLMの位置バイアスを前提とするため、位置頑健性が異なる将来モデルでは寄与が変わり得る。さらに評価の主要対象はGPT-3.5世代とLongChat-13Bであり、より新しい128K〜1M 文脈 モデルやmodern 長文脈 servingに同じ性能改善率がそのまま成立するとは限らない。
