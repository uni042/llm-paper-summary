# DepCap：直前ブロックの影響とトークン競合に基づく拡散LMの適応的並列復号

## 概要

DepCapは、拡散言語モデル（DLM）が文章をブロック単位で生成する際の二つの判断、すなわち「次のブロックをどこまで伸ばすか」と「そのブロック内のどの位置を同時に確定するか」を、異なる予測信号から決める学習不要の推論方式である。第一のDepGA-Blockは、直前に確定したブロックの前後で将来位置の予測分布がどれだけ変化したかを測り、予測の不確実性との釣り合いで境界を設定する。第二のCAP-Decodingは、確信度の高い候補位置同士でも互いに依存している可能性を考慮し、競合しない集合だけを同時に確定する。

原著はLLaDA-8B-Instruct、Dream-v0-base-7B、LLaDA-1.5をNVIDIA A100 40GB単体で評価した。LLaDA-8BのGSM8Kでは、固定32トークン・確信度のみの並列復号が19.6トークン/秒、正答率77.3%であるのに対し、DepCapは21.4トークン/秒、78.8%となる。LLaDA-1.5のMBPPでは、逐次的なVanilla方式に対して5.63倍の速度を報告する。ただし、この最大倍率は強い並列復号方式との比較ではなく、同じ表にはDepCapより速い方式もある。速度だけを取り出すのではなく、正答率とモデル呼出回数を合わせて評価する必要がある。

今回の再監査は、既存GitHub論文の固定Git blobと一次PDF16ページの§4・§5、Table 1、Figure 2、付録の感度分析を照合して実施した。元のGitHub稿は本文の量と日本語比率は十分だったが、限界節の見出しが機械的に認識されず、品質メトリクス上の限界説明量がゼロになっていた。新稿は意味内容を再確認したうえで、手法、評価、限界を明確に分離し、速度比較の分母と負の結果を明示する。

## 問題設定

自己回帰型モデルが左から右へ一つずつトークンを確定するのに対し、マスク型の拡散言語モデルは未確定位置を反復的に予測し、複数位置を同時に確定できる。これにより並列性が期待されるが、全系列を一度に確定しようとすると、まだ確定していない前後の文脈への依存が強い位置で誤りが生じる。ブロック単位復号は系列を区切り、先のブロックを確定してから次へ進むことで依存関係を管理する。

ブロックを小さく固定すれば品質を保ちやすいが、ブロックごとの反復推論が増え、GPUの並列性を活かしきれない。逆に大きく固定すると、互いに依存するトークンを同時に確定しやすくなり、品質が悪化する。従来の固定長方式や現在ステップのエントロピーだけを見る適応方式は、直前のブロックが確定したことによって将来位置の予測がどれほど安定したかを直接利用しない。

ブロック内の並列確定にも同様の問題がある。単純な確信度閾値方式は、各位置の最有力トークン確率が高ければ同時に確定してよいと判断する。しかし二つの位置が互いに強く依存している場合、個々の確信度が高くても同時確定で整合性が崩れる可能性がある。閾値を厳しくすれば品質は守りやすいが、並列確定できる数が減って生成速度が下がる。DepCapはブロック間の依存とブロック内の競合を別々の信号で扱う。

## 手法

### 1. 全体の推論フロー

現在までに確定した接頭辞と未確定のマスク列を入力とし、まず次のブロック候補範囲を決める。DepGA-Blockは直前のブロックを確定する前後で得られる予測分布を比較し、将来位置がどの程度その新しい文脈に支えられているかを測定する。そこから次のブロック長を選び、対象範囲内のマスク位置をCAP-Decodingへ渡す。

CAP-Decodingは候補位置の最有力トークンと確信度を取り出し、候補同士の競合を判定して安全な並列確定集合を選ぶ。選ばれた位置を同時に確定し、まだマスクの残る位置について予測を更新する。この処理をブロック内で繰り返し、ブロックが完成したらその確定前後の予測分布を次のブロック境界決定に再利用する。したがって、二つのモジュールは独立した後処理ではなく、前段の確定結果が次段の境界選択へ戻る循環的な構成になっている。

モデルの重みを再学習する必要はないが、予測分布の比較、候補位置の相互スコア、競合判定と並列集合選択には推論時の計算が必要である。大きな候補集合では位置対の評価費用も増えるため、並列確定で減らせるモデル実行回数と、追加の制御計算との交換条件がある。単に「学習不要」であることを「追加費用なし」と解釈してはならない。

### 2. DepGA-Block：直前ブロックの影響

原著§4.2では、直前に確定したブロックを `B` とし、その確定前の将来位置 `k` の予測分布を `p_prev,k`、確定後を `p_curr,k` と置く。両者のKullback–Leiblerダイバージェンス `I_k = KL(p_curr,k || p_prev,k)` を、直前ブロックの影響度として計算する。値が大きければ、その位置の予測が新たに確定した文脈から強く影響を受けたと解釈する。

一方、確定後の予測分布のShannonエントロピー `H_k = H(p_curr,k)` は、まだどの程度不確実かを表す。影響度だけが大きくても予測が広く分散していれば、将来位置を安全に大きなブロックへ含められるとは限らない。そこで候補窓の中で両信号を平滑化・正規化し、`S_k = Ĩ_k - λ H̃_k` を計算する。ここで `λ` は不確実性への罰則である。

現在の確定位置から先へ走査し、初めて `S_k < 0` となる直前を次ブロックの終端とする。最終長は `L_min` と候補窓長の間に制限し、初回だけは直前ブロックがないため `L_min` で保守的に開始する。候補窓は `min(L_max, 残りマスク長)` として設定する。影響が十分強く不確実性が小さい範囲では長いブロックを許し、先の位置で不確実性が優勢になれば短く切る仕組みである。

原著§4.4は、この影響量を条件付き相互情報量の近似として解釈し、複数位置にわたる影響が近似的に加算できるという分析を示す。ただしこれは推論中の代理スコアを正当化する説明であり、選ばれた境界が真の最適長であることや、全てのデータ分布で正答率が保証されることを示す厳密な定理ではない。影響度は予測分布の変化であり、現実の因果依存を直接観測した値ではない。

### 3. CAP-Decoding：候補間競合を除く並列確定

次のブロックが決まると、CAP-Decodingはその中の未確定位置 `i` の最大予測確率 `c_i` を計算する。`c_i >= τ_low` を満たす位置を候補集合 `C` とするが、ここではまだ全てを同時確定しない。候補位置 `i,j` の最有力予測トークンを `ŷ_i, ŷ_j` とし、原著式(6)の `D_ij = log p_i(ŷ_j) + log p_j(ŷ_i)` を計算する。両位置の予測分布が互いの候補をどの程度許容するかを測る代理指標である。

`D_ij > γ` を競合として扱い、競合する位置同士は同じ並列確定集合に含めない。まず高確信度 `c_i >= τ_high` の候補を優先して安全集合へ入れ、それらと競合する候補を除く。次に残った候補を確信度の高い順に調べ、既に選んだ位置と競合しないものだけを追加する。結果は競合グラフの独立集合に相当するが、厳密な最大独立集合を求める高価な最適化ではなく、確信度順の貪欲選択である。

この構造は、単純な確信度閾値だけでは同時確定してしまう相互依存の強い候補を排除するためのものである。一方で競合の判定はモデルの予測確率から計算した代理値であり、誤判定すれば品質低下が起こり得る。閾値を緩めると並列確定数が増えるが、品質が常に不変という保証はない。高確信度集合の扱いも実装上の順序と競合除去に依存するため、単純な「確信度の高い候補は無条件で全て同時確定」と解釈しない。

### 4. ハイパーパラメータと追加費用

原著§5.1の標準設定は生成長256、`λ=1.2`、`L_min=8`、`L_max=128`、`τ_low=0.8`、`τ_high=0.95`、`γ=-16.0` である。比較する確信度方式では閾値0.9、固定ブロック長16・32・64を使う。AdaBlockは改行トークンなど現在ステップの局所手掛かりを利用し、既定ブロック長32で評価する。これらの設定が異なるため、単一の「固定長ベースライン」とだけ記すと比較の前提を失う。

`λ` を大きくすると不確実性の罰則が増え、ブロックが短くなりやすい。`L_max` を大きくすれば並列性の上限が上がるが、品質との釣り合いが難しくなる。`τ_low` を下げると候補が増えて速度は上がりやすいが、誤確定リスクも増える。競合閾値 `γ` は同時確定を許す位置対を変える。従って、論文の結果は学習不要の固定モデルに対しても、推論制御パラメータの調整に依存する。

## 評価

### 環境、タスク、指標

主実験はA100 40GBを1枚用い、LLaDA-8B-Instruct、Dream-v0-base-7B、LLaDA-1.5の三系列を対象とする。数学・推論タスクはGSM8K（5-shot）、Math-500（4-shot）、コード生成はMBPP（3-shot）、HumanEval（0-shot）で、lm-evalを用いて評価する。指標はタスク正答率（Acc）、出力終了までの生成トークン毎秒（TPS）、モデルの関数評価回数（NFE）である。TPSの増加は速度改善、NFEの減少は反復計算の削減を意味するが、いずれも単独では回答品質を保証しない。

原著Table 1のVanillaは、各ステップで現在ブロックの最も確信度が高い位置だけを確定する保守的な逐次方式である。Confidenceは閾値以上の位置を複数同時確定する並列方式であり、AdaBlockはブロック境界を適応化する比較方式である。DepCapの最大倍率は主としてVanillaに対するもので、強いConfidenceやAdaBlockに対する追加利得とは区別しなければならない。

### LLaDA-8B-Instructの結果

GSM8KではVanillaが6.0TPS・77.6%、固定32トークンのConfidenceが19.6TPS・77.3%、固定32でCAP-Decodingのみを使うと21.6TPS・77.3%、DepGA-BlockとCAP-Decodingを組み合わせると21.4TPS・78.8%である。完全版は固定32のConfidenceより1.8TPS速く、正答率も1.5ポイント高い。一方、CAP-Decodingのみの21.6TPSよりはわずかに遅いので、完全版が常に最速とはいえない。

Math-500では固定32のConfidenceが20.7TPS・39.6%、完全版が22.2TPS・39.8%である。MBPPでは固定32のConfidenceが19.7TPS・41.0%、完全版が20.8TPS・40.8%となり、速度改善の代わりに正答率が0.2ポイント低下する。HumanEvalでは固定32のConfidenceが56.5TPS・43.3%、完全版は59.8TPS・42.7%であり、正答率が0.6ポイント低下する。これらの小さな負の結果を「品質低下ゼロ」と丸めないことが重要である。

| LLaDA-8B-Instruct | GSM8K TPS / Acc | Math-500 TPS / Acc | MBPP TPS / Acc | HumanEval TPS / Acc |
|---|---|---|---|---|
| Vanilla（逐次） | 6.0 / 77.6 | 7.9 / 39.2 | 5.4 / 40.8 | 16.7 / 42.7 |
| Confidence・固定32 | 19.6 / 77.3 | 20.7 / 39.6 | 19.7 / 41.0 | 56.5 / 43.3 |
| CAPのみ・固定32 | 21.6 / 77.3 | 22.8 / 39.2 | 21.2 / 40.6 | 60.4 / 43.3 |
| DepCap完全版 | 21.4 / 78.8 | 22.2 / 39.8 | 20.8 / 40.8 | 59.8 / 42.7 |

この表は、二つのモジュールの組合せが必ず最大TPSをもたらすわけではない一方、速度と正答率の交換条件を改善する場合があることを示す。評価にはNFEも含まれ、GSM8Kの完全版は74.8で、Vanillaの256.0から大幅に減る。固定32のConfidenceは78.6、CAPのみは71.5であるため、完全版は反復回数だけでも最小ではない。適応ブロックの利点は品質と反復回数の総合的な釣り合いとして読むべきである。

### DreamとLLaDA-1.5の差

Dream-v0-base-7BのGSM8Kでは固定32のConfidenceが13.2TPS・74.5%、完全版は13.0TPS・74.8%で、わずかに遅いが正答率が高い。MBPPでは固定32のConfidenceが28.6TPS・51.8%、完全版が29.2TPS・52.8%となる。一方、HumanEvalでは固定32のConfidenceが39.0TPS・53.0%、完全版が40.6TPS・50.6%であり、正答率は2.4ポイント下がる。モデル系列やタスクによって同じ制御方式の品質影響が変わることを示す。

LLaDA-1.5のMBPPでは、逐次Vanillaが1.9TPS・37.8%、固定32のConfidenceが11.6TPS・37.6%、CAPのみが12.2TPS・39.0%、完全版が10.7TPS・40.6%である。完全版の10.7/1.9≒5.63倍という速度はVanilla比であり、固定32のConfidenceの11.6TPSやCAPのみの12.2TPSよりは遅い。それでも正答率はVanilla比2.8ポイント改善し、相対では約7.4%高い。速度と品質を同時に見ることで、この論文の主張が理解できる。

### KVキャッシュとの組合せと構成要素の検証

原著Figure 2は、LLaDA-8BのGSM8Kでキャッシュなし、Prefix Cache、Dual Cacheの三条件を比較する。キャッシュを利用すると全方式でTPSが大きく改善するが、最高TPSはFast-dLLMの構成であり、DepCapが全てのキャッシュ条件で最速とは限らない。DepCapとDual Cacheの組合せは51.2TPS、正答率79.3%となり、速度と品質、NFEの総合的な釣り合いが良いと報告する。

構成要素除去実験では、固定ブロックのままCAP-Decodingだけを導入すると、候補間の競合を除くことでより多くの位置を同時確定できる場合がある。一方、従来の確信度方式にDepGA-Blockだけを導入すると、ブロック境界の改善によって正答率を高めやすい。完全版は両者の効果を合わせるが、上表のとおり、速度単独では片方だけの構成が優位になることもある。二つの機構が異なるボトルネックを扱うことを裏付ける比較である。

### 感度分析と負の結果

原著付録Table 4のLLaDA-8B/GSM8Kでは、`L_max=16` の場合17.6TPS・79.6%、`L_max=32` は19.1TPS・80.1%、`L_max=64` は20.7TPS・78.5%、`L_max=128` は21.4TPS・78.8%、`L_max=256` は21.5TPS・79.5%である。ブロック上限を増やすとTPSは概ね上がるが、正答率は単調ではない。単に上限を最大にすれば全指標が改善するわけではない。

生成長を1024へ延ばす場合は速度と品質の両立が難しくなると報告される。`τ_low` を低くすると並列性が高まるが品質を損なう可能性があり、高くすると品質を保ちやすい反面速度が低下する。`λ` の過度な増加はブロックを保守的にするが、必ずしも総合的な性能を改善しない。これらは学習不要方式でも運用時の設定調整が必要であることを示す。

### 再現性を左右する計測上の注意

生成速度の指標は、最終的な終了トークンまでの実際の出力長に基づいている。設定された生成長の上限が同じでも、モデルが早期終了した場合の出力トークン数は同じとは限らない。したがって、単純な関数評価回数の削減とトークン毎秒の増加が常に同じ比率になるとは限らない。実装を再現する際は、出力長、終了条件、入力プロンプト、計測の開始・終了点を合わせる必要がある。

同じ表の正答率差についても、少数の百分点の差を無条件に統計的に有意とみなすことはできない。原著が提示する主表はタスクごとの点推定であり、全条件に対する反復実行の信頼区間が与えられているわけではない。運用環境で品質の下限を要求するなら、数学問題の正答判定とコードのテスト実行を別々に集計し、長い出力や失敗例を含む分布で評価すべきである。

特に拡散モデルのブロック境界は、確定済み接頭辞と未確定位置の分布が変わるたびに再計算される。固定ブロックと比較すると処理形状が変動しやすいため、動的な長さをGPUへ渡す際の同期、マスク更新、再利用可能なキャッシュ領域の管理が実際の性能を左右する。論文のA100単体での結果から、別の推論サーバーへ移植したときの性能を機械的に推定することは避ける。

## 既存研究との差

固定ブロック長のFast-dLLM系は、長さの設定がタスクとモデルに依存する。AdaBlockは改行などの局所的な手掛かりを利用して境界を変える。DepGA-Blockは、直前ブロックの確定前後における将来の予測分布変化を用いるため、時間をまたぐ文脈情報を境界選択に利用できる点が異なる。予測の不確実性を同時に評価することで、単に影響度が大きい位置を全て含めることも避ける。

確信度のみの並列復号は位置間の競合を直接考慮しない。CAP-Decodingは相互予測確率を用いた競合スコアと確信度優先の貪欲選択で、同時確定できる位置を選ぶ。学習済みドラフトモデルや蒸留は必要とせず、既存の拡散LMに推論制御として追加できる。ただしモデルの予測分布へアクセスできる実装が前提であり、ブラックボックスAPIで最終文章だけを取得する構成には直接適用できない。

## 限界

実験は三つの拡散言語モデル、A100 40GB単体、主として生成長256、数学とコード生成の四タスクに限られる。多人数同時要求、長文対話、他言語、異なるGPU、分散推論、P99遅延、消費電力について同一の改善率は示されていない。最大5.63倍は保守的な逐次Vanilla比であり、強い並列方式に対する倍率ではない。DreamやLLaDA-1.5では速度や正答率が競合方式より悪い条件があり、LLaDA-8Bでもコード生成の一部で正答率が小幅に下がる。

DepGA-BlockのKL変化とCAP-Decodingの相互予測確率は、真の因果依存や「安全な同時確定」の厳密な証明ではない。理論の加算近似は設計の動機を与えるが、境界や候補集合の最適性を保証しない。追加学習は不要でも、分布の保存と比較、位置対スコア、競合判定の推論時費用は発生する。候補窓や競合集合が大きい場合、制御処理のオーバーヘッドが速度改善を相殺する可能性がある。

動的なブロック長は固定形状のGPUカーネルやコンパイラ最適化と衝突する可能性があり、既存のKVキャッシュと併用する場合はブロック境界変更後のキャッシュ更新と無効化を正しく実装する必要がある。論文はキャッシュ併用の有効性を示すが、あらゆるサービングフレームワークで互換性が自動的に得られるとは主張していない。運用では対象モデル・タスクごとにTPS、NFE、正答率を再測定し、閾値を選ぶべきである。
