# Learn2PD：拡散言語モデルの予測確定タイミングを学習する並列デコード

## 概要

自己回帰型LLMでは次トークンの生成が直前のトークンに依存する。これに対してマスク型拡散言語モデルは、あるブロック内の複数トークンを一度に予測し、まだ不確かな位置だけを再びマスクして次の反復で更新する。並列予測が可能でも、既に最終出力と一致しているトークンまで何度も予測し直すなら、反復回数が大きくなって速度は上がらない。本研究は、**いつトークンを確定し、いつ再マスクするか**という選択規則を、固定の信頼度閾値から学習可能なフィルタへ置き換える。

提案のLearn2PDは、拡散LLM本体を再学習せず、モデルが出力するブロック内の各位置の信頼度を小型MLPに入力して、各位置を今回確定させてよいか判定する。さらにEoTP（End-of-Text Prediction）は、終端トークン以後のパディング相当部分を繰り返し復号する無駄を除く。原著のLLaDA-8B-Instruct・GSM8K・生成長1024では、通常復号の0.54 tokens/sに対しLearn2PD+EoTPが12.26 tokens/s、22.58倍で、正答率も77.60から79.83となった。Dual Cacheを組み合わせると31.23 tokens/s、57.51倍まで上がるが、正答率は74.00へ下がる。最大速度倍率だけを取り出して「品質劣化なし」と表現してはいけない。

この方式はドラフトモデルで複数候補を提案し自己回帰モデルが検証する投機的デコードとは異なる。あくまで拡散モデル自身の反復的なマスク復号の中で、すでに安定した位置を早く確定する。フィルタは正解そのものを生成するモデルではなく、現在の予測を確定してよいかを判断する補助器である。

## 問題設定と無駄な再マスクの観測

LLaDAのようなマスク型拡散LLMは、応答用の長さLの領域を最初は[MASK]で埋め、反復ステップごとに各位置の候補と確率を推定する。信頼度の高い位置を確定し、低い位置を次回へ残すことで、並列性と品質を両立しようとする。多くの実装はブロック長32のような単位を左から右へ処理し、ブロック内では繰り返し全位置を推定する。したがって「一度正しく推定したが、信頼度が十分でないため再マスクされた」位置が、無駄な再計算を生む。

原著§3.1.2は、GSM8KとHumanEvalのサンプルで、最初に基準出力と一致したステップと、実際に確定したステップの差を調べる。ここでいう基準出力は人間が作成した唯一の正解文ではなく、**通常のLLaDA生成手順が出力した文字列**である。この基準に一致した時点で確定すれば、同じ生成結果をより少ない反復で得られる可能性がある。正解が存在しない本番推論では、この一致を直接観測できないことが重要な制約となる。

著者は理想的な上限としてEGP（Extremely Greedy Parallel）を定義する。EGPは各ステップの候補トークンを基準出力と比較し、一致した位置を即時確定する「答えを知っているオラクル」である。生成長256・ブロック32のGSM8Kでは、通常方式がブロック当たり32反復を要するのに対し、EGPの中央値は2反復となった。これは高速化の余地を示す診断であって、EGP自体を未知の正解に対して実用化できたという結果ではない。Learn2PDはこのオラクルの確定判断を、推論時に利用できる信頼度から近似する。

もう一つの無駄は応答の終了後に生じる。生成長を1024と指定しても、実際の回答が短い場合、残りの位置には終端トークンが現れ、同じ終端を繰り返し処理する。原著§3.3は、該当条件で計算費用の約89.59%が終端後のパディング復号に費やされると報告する。固定の長い生成予算を指定した実験ほど、この無駄を除く効果が大きい。

## 手法

### 1. EGPを教師にしたトークン単位の二値分類データを作る

学習段階では、FLANから66種類の質問を各40例、計2640例取り出す。まず凍結した拡散LLMで各プロンプトの生成を進め、各ステップのトークン候補、候補の確率、ブロック内の信頼度を記録する。基準出力との一致を利用して、各位置を「ここで確定してよい（ラベル1）」か「再マスクすべき（ラベル0）」かに分類する。この段階だけは基準出力を参照できる。生成過程の記録が学習教師であり、運用時には基準出力を参照しない。

フィルタの入力はブロック内の信頼度ベクトルで、出力は各位置について確定可能性を表すロジットである。入力にモデルの全隠れ状態を渡す巨大な補助ネットワークではなく、ブロック長32で2,112個の学習パラメータを持つ2層MLPを用いる。学習損失は位置ごとの二値交差エントロピーで、確定可能性をシグモイドで確率へ変換する。これにより、単一位置の信頼度だけでなく、ブロック内での信頼度の相対パターンを学習できる。

著者はAdamW、学習率0.001、5000 epochを使用した。拡散LLM本体の重みは凍結するため、学習されるのはフィルタのパラメータのみである。ただし「6分で学習可能」という主張には注意が必要で、教師データの収集にRTX A6000を4枚使って約3時間かかり、収集後のMLP最適化がT4上で約6分だった。既に教師トレースがある状況と、ゼロから新しいモデルへ導入する状況で導入コストは異なる。

### 2. 推論時に信頼度をMLPへ入力して確定位置を選ぶ

推論では、現在のブロック内で未確定の位置を集合Mとして保持する。拡散LLMがブロックの候補と信頼度を出したら、その信頼度をfθへ入力する。出力が閾値τを超えた位置は、今回の候補トークンを採用し、Mから取り除く。残った位置だけが次の反復で再推定の対象となる。Mが空になれば次のブロックへ進む。原著Algorithm 2は、拡散LLMとフィルタの呼び出し、閾値判定、Mの更新、応答の組み立てをこの順で記述している。

固定閾値方式では「信頼度が高いなら確定」という一つの規則に頼る。Learn2PDは、ブロック全体の信頼度の形状から、低い信頼度でも正しい予測を維持できそうな位置を判断する。これが反復削減の源泉である。ただしMLPの予測が誤れば、間違ったトークンを早く確定し、後段で修正できなくなる。したがって閾値τは単なる速度調整つまみではなく、品質と速度の交換条件そのものである。原著はτ=0.96を代表的な妥協点とする。

このフィルタは、拡散LLMの各ステップに追加のMLP計算を要する。しかしMLPの規模は小さく、減らした拡散LLM本体の再実行費用の方が大きいため、実測で速度が改善した。大きな補助モデルを使うほど分類精度が上がるとは限らず、4層MLPは2層よりも遅かった。したがってフィルタの複雑さも性能最適化の一部である。

### 3. EoTPで終端後の位置を入力から削除する

Learn2PDは「各位置を何回復号するか」を減らすが、生成長が過大な場合は終端以後の不要な位置が残る。EoTPは、あるブロックで終端トークン[EoT]が確定したら、それ以降の位置を破棄し、次の拡散ステップへ渡す系列自体を短縮する。これにより、同じ終端を再度推定するだけの処理を避ける。単なる出力文字列の後処理ではなく、次ステップの入力長を減らす点に計算上の意味がある。

EoTPの利得は応答の実長と設定生成長の差に依存する。長さ256では改善幅が小さく、1024では大きい。逆に生成が予算上限近くまで続く場合や、終端トークンを誤検出する場合には利得が縮む、または品質リスクがある。原著の実測倍率はこの実験の出力長分布に依存するため、一般の長文生成でも必ず22倍になるとはいえない。

### 4. KVキャッシュとの組合せ

拡散LLMの繰り返し推論では、再計算される隠れ状態・注意計算を減らすためにDual CacheやPrefix Cacheを組み合わせられる。Learn2PDは「確定のための反復回数」を減らし、キャッシュは「残った反復の計算量」を減らすため、原理上は異なる最適化軸である。原著はGSM8K・生成長1024で併用を評価し、Dual Cacheとの組合せで速度を大きく上げた。ただしキャッシュ近似が品質へ影響する可能性があり、実際に正答率の低下が報告されている。

## 主要結果

### 4課題の速度・品質

原著Table 1から代表的な設定を抜粋する。速度倍率は同じ課題・同じ生成長のvanilla LLaDAとの比較であり、生成長256と1024をまたいで直接割り算した値ではない。

| 課題・生成長 | vanilla TPS | Learn2PD TPS / 倍率 | Learn2PD+EoTP TPS / 倍率 | vanilla Score → EoTP併用Score |
|---|---:|---:|---:|---:|
| GSM8K・256 | 3.41 | 14.07 / 4.13倍 | 14.35 / 4.21倍 | 78.70 → 78.62 |
| GSM8K・1024 | 0.54 | 6.63 / 12.21倍 | 12.26 / **22.58倍** | 77.60 → **79.83** |
| MATH・256 | 4.70 | 15.16 / 3.21倍 | 15.21 / 3.23倍 | 32.90 → 31.40 |
| MATH・1024 | 1.70 | 10.98 / 6.45倍 | 12.27 / 7.22倍 | 35.21 → 34.60 |
| HumanEval・256 | 3.33 | 11.66 / 3.50倍 | 11.88 / 3.57倍 | 39.63 → 38.41 |
| HumanEval・1024 | 0.53 | 4.63 / 8.78倍 | 6.63 / 12.55倍 | 37.21 → 35.98 |
| MBPP・256 | 3.14 | 14.96 / 4.77倍 | 15.88 / 5.06倍 | 31.22 → 31.03 |
| MBPP・1024 | 0.58 | 6.96 / 12.08倍 | 9.89 / 17.16倍 | 10.61 → 11.02 |

高速化は全4課題で観測されるが、品質は完全不変ではない。例えばHumanEval・1024ではScoreが37.21から35.98へ1.23ポイント低下し、MATH・256でも32.90から31.40へ1.50ポイント下がる。GSM8K・1024やMBPP・1024では逆に上がる。原著の「性能低下なし」は最大倍率を示す代表条件の説明としては読めるが、全条件での厳密な品質同一性を意味しない。

### EoTPが効くのは長い生成予算

原著Table 4のGSM8Kでは、Learn2PD単独とEoTP併用の倍率は生成長128で3.29対3.36、256で4.13対4.21、512で6.66対7.60、1024で12.21対22.58となる。EoTPの追加効果が長い生成長で大きくなることは、終端後のパディング反復を削るという説明と整合する。ただし、生成長を長くしたことで通常方式のTPSが下がるため、倍率だけでなく実測TPSも見る必要がある。

### キャッシュ併用は大幅高速化するが品質が落ちる

原著Table 2のGSM8K・生成長1024は、Learn2PD+EoTP単独で12.26 TPS・22.58倍・Score 79.83、Dual Cache併用で31.23 TPS・57.51倍・Score 74.00、Prefix Cache併用で14.79 TPS・27.23倍・Score 77.71となる。Dual Cacheは単独方式よりTPSが約2.55倍になる一方、Scoreが5.83ポイント低下する。Prefix CacheはTPSが約1.21倍になり、Scoreが2.12ポイント低下する。

| GSM8K・生成長1024 | TPS | vanilla比倍率 | Score | 単独方式からのScore差 |
|---|---:|---:|---:|---:|
| Learn2PD+EoTP | 12.26 | 22.58倍 | 79.83 | 基準 |
| + Dual Cache | **31.23** | **57.51倍** | 74.00 | **-5.83** |
| + Prefix Cache | 14.79 | 27.23倍 | 77.71 | -2.12 |

**原著内の数値不整合**にも注意する。Figure 1の説明文は57.51倍時の処理率を16.37 tokens/sと書いているが、Table 2本文と表は31.23 TPSとしている。両方の記載を照合できたものの、どちらが正しいか一次資料内だけでは確定できない。上表では詳細な実験表の31.23を採用し、Figure 1の16.37という矛盾をここに明示した。57.51倍と基準0.54 TPSを掛けると約31.1 TPSになるため表の値と概ね整合するが、これは不整合の解消を保証するものではない。

### MLP深さ・閾値の感度

原著Table 3はGSM8K・生成長256のフィルタ層数を比較する。1層MLPは8.77 TPS・2.57倍・Score 78.62、2層は14.07 TPS・4.13倍・78.62、4層は11.41 TPS・3.35倍・78.85だった。4層はわずかに品質が良いが、追加計算により速度が落ちる。2層の選択は最も複雑な分類器が常に最適というわけではないことを示す。

閾値τを下げると確定判定が増えて速くなるが、誤確定が増え得る。原著Figure 6ではτ=0.99の設定で4.68 TPS、Score 78.92という値を示し、τ=0.90では品質低下が目立つ。著者はτ=0.96を妥協点としている。閾値の最適値はモデル・データセット・生成長・フィルタ学習分布に依存するため、他の拡散LLMへそのまま転用できるとは限らない。

## 既存研究との差

Fast-dLLMなどの既存方式は、固定の信頼度閾値やルールに従って高信頼度トークンを並列確定する。Learn2PDは信頼度の**ブロック内パターン**から確定可能性を学習し、個々の入力に応じて判断を変える。APDのように別の自己回帰モデルで並列生成幅を制御する方式と異なり、ブロック内の各位置について確定・再マスクを直接判定する。EGPは正解を参照する理想上限で、Learn2PDはこれを運用可能な近似へ変える役割を持つ。

EoTPはフィルタとは独立に、終了後の無駄な系列を切り詰める。Dual Cache/Prefix Cacheも反復一回当たりの計算を減らすため、別の最適化軸である。したがって、提案は単一カーネルを高速化した研究ではなく、**反復回数、系列長、キャッシュ再利用**を分けて組み合わせる推論アルゴリズムである。

## 限界・負の結果・再現性

第一に、学習時のEGPは通常復号で得た基準出力を「正しい」と扱う。基準出力がそもそも事実として誤っていても、それに一致した時点で確定するよう学習する。したがってフィルタの教師ラベルは真理判定器ではなく、通常デコードの出力を再現するための近似である。フィルタが早すぎる確定を行えば、その後の修正機会を失う。

第二に、最大速度倍率は生成長1024の固定予算に強く依存する。実際の回答が短く、終端後の領域を長く復号するvanilla実装が遅いほど、EoTPの相対改善は大きい。生成長128ではEoTP追加の利得は小さく、長い文章を上限近くまで本当に生成する場合には効果が縮む可能性がある。複数の要求を連続バッチする本番servingで同じ倍率になるかは原著で十分に評価されていない。

第三に、57.51倍のDual Cache併用ではScore 79.83から74.00へ低下する。キャッシュの近似や反復制御の相互作用を無視して最大倍率だけ引用してはいけない。HumanEvalやMATHでも一部条件で小幅な品質低下がある。速度と品質の両方を必要とする用途では、タスクごとに閾値・キャッシュ構成を検証する必要がある。

第四に、評価は主としてLLaDA-8B-InstructとA6000×4であり、他の拡散モデル系列、長文脈入力、異なるGPU、低VRAM、CPUオフロード、MoE、分散バッチでの一般性は未確立である。学習データ収集には3時間と4GPUを要するため、フィルタ自体の6分学習だけを導入コストとみなせない。原著にはProject Codeと記載されるが、確認できる一次資料から本研究固有の公式コードURLを特定できなかった。実装の再現可能性には留保が必要である。

第五に、原著Figure 1の16.37 TPSとTable 2の31.23 TPSの不整合が残る。表に基づく定量値を採用したが、完全な数値再現には著者実装と測定ログの確認が望ましい。また、TPSの算出法、トークン数の分母、終端後のパディングの扱いによって速度の見かけが変わり得るため、別論文の通常自己回帰デコード速度と横断比較する際は測定定義を合わせるべきである。
