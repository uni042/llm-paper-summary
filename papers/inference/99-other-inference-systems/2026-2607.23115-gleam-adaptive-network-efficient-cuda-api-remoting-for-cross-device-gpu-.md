# Gleam: Adaptive Network-Efficient CUDA API Remoting for Cross-Device GPU Sharing over LANs

> 構内ネットワーク越しのCUDAリモーティングで、重みのハッシュキャッシュ、呼出しの非同期化、競合を予測する割当て、文脈保護を組み合わせ、リモーティング効率1.4から24.2倍とスループット最大1.79倍を達成する。

## 概要

家庭や研究室の構内ネットワークには、遊んでいる高性能GPUを持つ計算機と、GPUが不足するノート端末が混在する。重いAI推論を近くのGPUへ逃がせれば、プライバシーと応答性と費用の面でクラウドへ出すより有利な場面がある。その手段として本論文が採るのは、アプリケーションのCUDA呼出しを端末側で横取りし、ネットワーク越しにサーバで実行して結果を返すAPIリモーティングである。アプリケーションの改変も環境全体の移送も不要で、サーバ側にドライバがあればよい。

しかしデータセンターの高性能相互接続と違い、構内ネットワークは帯域が最大1000メガビット毎秒程度で、無線では遅延も不安定である。ここで三つの費用が支配的になる。第一にモデル読み込みでは、重みがメモリ使用量の91から96パーセントを占め、その転送だけで約150秒かかり、ローカルの約2秒と比べて約75倍に膨らむ。第二に推論段階では呼出しの回数自体が多く、拡散モデルの一回のサンプリングで約18000回の呼出しがあり、呼出しごとに往復を待つ同期型では、実際のGPU実行が全体の0.26パーセントしかないような呼出しまで往復遅延を払う。第三に、複数タスクが同時に動くと、読み込みの転送同士が帯域を取り合って遅延が約50パーセント増え、同じGPUへ集まれば計算も競合する一方で、遠隔実行だけではGPU利用率が63パーセントまで落ちるという、集めるべきか分散すべきかの釣り合いが生じる。

Gleamはこの三つへ別々の機構で対処する。重み管理は、確保したメモリ塊への書き込みがその寿命の間変わらないことを解放時に照合して重みの塊を識別し、塊ごとにハッシュで引けるキャッシュをサーバ側に置いて、再送をハッシュと大きさだけのメタデータへ置き換え、さらに同じタスクの次の実行がサーバ上の共有塊を再利用できるようにする。経路管理は、呼出しの種類に応じて、エラーコードだけを返すものは楽観的に非同期化し、単純な状態操作は端末側で模擬して即答し、資源ハンドルを返すものはサーバで複数まとめて先行作成して端末側にキャッシュすることで、往復の同期待ちを外す。スケジューラは、通信と計算の占有率と実時間のサーバ状態から競合込みの遅延をオンライン予測し、キャッシュのあるタスクを同種でまとめる相と、帯域の競合を見て分散する相の二相で割当てを決める。最後に文脈保護が、通信断時の未確認メッセージの再調整と、グラフ捕捉中の文脈レベル呼出しの遮断で、長時間の共有を壊さないようにする。

**代表結果:** 異種GPUの試作系で、六つの応用についてAPIリモーティング効率が最先端の比較対象比1.4から24.2倍になり、無線条件の拡散モデルでは素朴なGVirtuS比で約54倍、他の比較対象比でも8.4倍と3.9倍の条件が示された。システム全体では、GPU数を1から4まで変えた条件で端末側の端から端までの遅延が最大1.56倍下がり、スループットが最大1.79倍になり、4GPU条件では待ち行列遅延が最大2.88倍下がった。最適化を全て有効にしても遠隔実行の追加費用は残り、無線で約53パーセント、有線で約19パーセントと正直に報告される。

## 問題設定

資源の観点で、ボトルネックはGPUの計算能力ではなく、その手前のネットワークである。帯域については、読み込み段階の転送量の大半が不変のモデル重みであり、タスクのたびに同じ重みを送り直すのは純粋な無駄だが、システムが見ているのは低水準のメモリ確保とコピーの呼出しだけであり、どれが重みでどれが短命の入力かを区別する意味情報がない。遅延については、呼出しの頻度が高く一つ一つが短いため、往復回数そのものが費用になり、しかも呼出し間の依存があるため単純な一括送信では外せない。

競合の問題は、通信と計算で逆方向に働く。読み込みの転送は帯域を取り合うため分散が有利だが、計算は同じGPUへ同種タスクを集めるほど重みの再利用と利用率で有利になり、遠隔の単独タスクでは伝送の待ちでGPUが遊ぶ。既存のリモーティング最適化は呼出し単位の通信を減らすことに集中し、モデル読み込みと多タスクの競合を一緒に扱う割当てを持たなかった。さらに、長時間共有では通信断や複数ストリームの多重化で共有のCUDA文脈が壊れる危険があり、短命な排他利用を前提とする従来方式はここを扱わない。本論文はこの四点を一つの枠組みで扱う。

## 手法のあらまし

流れは、割当て、読み込み、推論、保護の順である。まず端末がタスク種別をスケジューラへ知らせ、サーバが進捗と資源使用をハートビートで報告し、スケジューラが競合込みの予測遅延で割当て先を決める。タスクが始まると端末側でCUDA呼出しを横取りして選ばれたサーバへ送るが、読み込みでは重みの塊がハッシュでキャッシュにあればメタデータだけを送り、推論では呼出しの種類に応じて非同期化・模擬・先行作成を使い分けて往復を減らす。実行中は文脈保護が、未確認の送信を保持して通信断後に再調整し、グラフ捕捉中は文脈レベルの呼出しを遮断する。スケジューラは周期的に再評価され、待ちタスクの割当てを更新する。

## 手法

### 1. 重み管理 — 変わらない塊を識別し、ハッシュで再送を避け、共有する

この機構が観測するのは、メモリ確保と端末から装置へのコピーの呼出し列と、解放の時点でのメモリ内容である。保持する状態は、タスク種別ごとのディレクトリに置かれた塊ごとのキャッシュと、各塊のハッシュ識別子の集合、さらに最近使われていない順に追い出す共有プールである。処理は三つある。識別では、確保された塊について、その塊へのコピーの内容を記録しておき、解放の直前に現在の内容と照合し、全ての塊内コピーが寿命を通じて変わらなかった塊だけを重みとみなす。検索では、接続時にサーバが保持するハッシュ集合を端末へ送り、端末はコピーのたびに送信元データのハッシュを計算し、一致すればデータ本体の代わりにハッシュと大きさだけを送って、サーバが手元のキャッシュから復元する。共有では、識別された塊を即座に解放せず共有プールへ残し、同じタスクの次の実行が確保とコピーを飛ばして再利用できるようにし、端末側アドレスと共有先の対応は仮想メモリの層で吸収する。これにより減るボトルネックは読み込み転送であり、実測では約150秒の読み込みがキャッシュ利用時には約9秒まで下がり、拡散モデルの例では約3ギガバイトの転送を1000未満の軽い識別子で置き換えられた。追加で消費する資源は、サーバ側のディスクとGPUメモリのキャッシュ容量と、解放時の照合とハッシュ計算である。誤った場合の挙動として、途中で書き換わる塊は重みと判定されないため安全側に倒れるが、判定は解放まで確定しないため、初回実行では再送削減の恩恵を受けられない。

### 2. 経路管理 — 呼出しの種類ごとに往復の同期待ちを外す

この機構が観測するのは、横取りした呼出しの種類と戻り値の性質である。保持する状態は、端末側で模擬する単純な状態と、先行作成した資源ハンドルのキャッシュである。処理は三つの場合分けである。エラーコードだけを返す呼出しは、基盤側がエラーを生んだり隠したりしないことを根拠に、結果を待たず楽観的に成功を返して先へ進み、エラーは非同期に報告する。ただし正常な結果自体が戻り値に符号化される一部の呼出しはこの対象から外す。装置の取得や設定のような単純な状態呼出しは、端末側に軽い状態を持って模擬し、遠隔呼出しも送って一貫性を保ちながら即答する。資源ハンドルを返す呼出しは後続の呼出しがすぐ使うため依存が生じるので、サーバで同じ種類の資源を複数まとめて先行作成し、端末側のキャッシュから配ることで依存を外す。パラメータを持つハンドルは後からの属性変更が要るため、要求自体はサーバへも送る。これにより減るボトルネックは呼出しごとの往復遅延の累積であり、動機付けの測定では装置取得の非同期化だけで総時間が19.32秒、15.7パーセント減る例が示された。追加費用は端末側の状態管理と先行作成した資源の在庫であり、誤った場合の挙動として、楽観的に進めた後に遠隔でエラーが起きれば、既に先へ進んだ処理との不整合を非同期報告で扱う必要が生じる点が、この方式の緊張である。

### 3. 競合を予測する二相スケジューラ — 集める利益と分散の利益を相で使い分ける

この機構が観測するのは、各タスクの計算占有と通信占有、必要GPUメモリ、サーバ側で実行中のタスク集合と帯域使用率である。保持する状態はタスクの待ち行列とサーバ状態であり、処理はまず競合を考慮したオンライン予測器で、無競合時の遅延を基準に通信と計算の残り時間を推定し、その予測を使って二相で割り当てることである。第一相はキャッシュのあるタスクを対象に、同じサーバの計算占有の合計が上限を超えない範囲で同種タスクをできるだけまとめ、予測遅延が最小のサーバへ置く。これにより重みの再利用とGPU利用率が上がる。第二相はキャッシュのないタスクや第一相で競合のために見送られたタスクを対象に、帯域使用率に余裕があるかを確かめながら、予測遅延が最小のサーバへ分散させる。これにより減るボトルネックは、読み込み転送同士の帯域競合と、遠隔単独実行でのGPUの遊休の両方である。割当て一回あたりの費用は75から84マイクロ秒程度と無視できる水準が測られている。誤った場合の挙動として、予測が外れれば割当てが偏って待ち行列が伸びるが、スケジューラは周期的に再評価するため、次の周期で待ちタスク側から修正される。

### 4. 文脈の一貫性保護 — 通信断の再調整とストリーム多重化の遮断

この機構が観測するのは、未確認の送信メッセージと、グラフ捕捉のような文脈に制約のある操作の開始である。保持する状態は、確認応答が返るまで保持する送信バッファであり、処理は二つある。再調整では、送り手が受信確認まで全メッセージを保持し、在中の状態数に上限を設けて上限を超える送信を遅らせることで、双方向の確認を兼ねさせ、通信断の後に未完了の呼出しを整合的に扱えるようにする。保護では、グラフ捕捉の間は他のストリームから出る文脈レベルの呼出しを全体のゲートで遮断し、捕捉の破壊を防ぐ。これにより減るボトルネックは、長時間共有での文脈破壊による全体の崩壊であり、費用は再調整のバッファでは最大保留数を8にすると性能低下が4.16パーセント、保持する要求の大きさは1.22キロバイト程度と測られる。捕捉の遮断は捕捉自体が全体実行より短いことを前提に許容される設計であり、同時実行数が増えるほど保護の費用比率は上がるため、スケジューラ側の同時実行の抑制と組で運用される。

## 評価

結論は、通信の最適化と競合を扱う割当ては相補的であり、片方を外すと大きく劣化する、というものである。除去実験では、経路管理を基本の非同期だけにすると端から端までの遅延が7.9倍になりスループットが66パーセント下がり、スケジューラを競合を見ない公平型へ替えると待ち行列遅延が約6.2倍になった。全体評価では、GPUが1から4基、同時端末が3から15、タスク種別が3から6の条件で、Gleamが全てのGPU数で最も低い遅延と最も高いスループットを示し、4GPUでは待ち行列遅延が最大2.88倍下がり、全体の完了時間が最大1.76倍短くなった。推論遅延の分布でも、中央値と尾の両方が比較対象より短く、競合下での予測可能性が改善している。

評価条件の解釈で重要なのは、対象タスクが言語モデルだけでなく画像生成と科学計算を含む七つの実タスクであり、基盤がggml経由のものとPyTorch経由のものに分かれる点である。つまりこれは言語モデル専用のサービング最適化ではなく、CUDA呼出しという共通層で効く方式であり、言語モデルの推論はその一つの適用先である。逆に、トークン単位のスケジューリングやバッチ形成のようなサービング層の最適化とは層が違うため、そちらとの組合せの効果は未評価である。ネットワーク条件も最大1000メガビット毎秒の構内環境に限られ、より高速な相互接続や逆により細い回線での振る舞いは示されていない。

## 既存研究との差

GPGPUリモーティングの先行方式との差は、呼出し頻度の削減だけでなく、読み込み段階の重み転送をキャッシュで消し、多タスクの競合を割当てへ組み込んだ点にある。影資源で資源作成を非同期化する方式や、ハンドルの先行取得と状態の端末保持で呼出し数を減らす方式は、重みの再送を扱わない。サーバレス向けの分離GPU方式は負荷分散のためのサーバ間リモーティングであり、端末とサーバの資源共有という設定が違う。クラウドの配置最適化や端末側の多重化方式との全体比較でも、自前の通信最適化を相手へ与えた上でなお割当てで差が付くことが示され、差が通信層だけに由来しないことが確認されている。

## 限界・実装状況

限界として、対象はCUDAとNVIDIAのGPUを前提とし、他の加速器やAPI体系へは横取りの実装をやり直す必要があること、楽観的な非同期化は遠隔エラーの扱いを複雑にすること、重みキャッシュはサーバ側の容量を消費し追い出しの挙動に性能が依存すること、評価が構内ネットワークと七タスクの試作系に限られ大規模展開の検証がないことが挙げられる。文脈保護の遮断費用も同時実行数とともに増えるため、保護だけで無制限の多重化はできない。実装状況は、公式コードの公開先を一次資料で確認できず、gRPCとprotobufによる試作で6つの動的ライブラリから1000を超える呼出しを横取りする構成が本文に記される。

## 一般的な実装上の含意

遠隔実行の最適化では、計算の手前の転送量と往復回数を分けて測ることが要る。本論文では重みの再送と呼出しの往復が別々の機構で消されており、どちらか一方では上限が低い。また、低水準の呼出し列から意味のある対象、ここでは不変な重み塊、を事後照合で識別する手法は、意味情報を持たない中間層でもキャッシュ可能性を掘り起こせる例である。割当てでは、集める利益と分散の利益が資源ごとに逆になるため、相を分けて順に決める設計が単一の目的関数の最適化より扱いやすい場合がある。
