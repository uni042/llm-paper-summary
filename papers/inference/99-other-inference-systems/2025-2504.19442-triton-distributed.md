# Triton-distributed: Programming Overlapping Kernels on Distributed AI Systems with the Triton Compiler

> OpenSHMEM通信をTritonへ統合し、計算・通信・メモリアクセスをPythonから細粒度に重ね合わせ、8〜64 GPUで分散カーネルを高速化するコンパイラ拡張。
## 書誌情報
- **著者**: Size Zheng, Wenlei Bao, Qi Hou, Xuegui Zheng, Jin Fang, Chenhui Huang, Tianqi Li, Haojie Duanmu, Renze Chen, Ruifan Xu, Yifan Guo, Ningxin Zheng, Ziheng Jiang, Xinyi Di, Dongyang Wang, Jianxi Ye, Haibin Lin, Li-Wen Chang, Liqiang Lu, Yun Liang, Jidong Zhai, Xin Liu
- **著者・所属**: ByteDance Seed; Tsinghua University; Peking University; Shanghai Jiao Tong University; Zhejiang University
- **公開**: arXiv preprint arXiv:2504.19442v3
- **種別**: arXivプレプリント
- **対象**: 分散コンパイラ、計算通信重ね合わせ、Triton、OpenSHMEM、MoE通信、分散FlashDecode
- **実装**: Tritonを拡張した公開実装。OpenSHMEM互換プリミティブをLLVM IRへ下げ、NVIDIAではPTX、AMDではAMDGCNを生成する。
## 概要
Triton-distributedは、単一GPU向けTritonを分散AIへ拡張し、計算・メモリアクセス・通信をPythonレベルで共同記述して重ね合わせるコンパイラ基盤である。OpenSHMEM互換通信プリミティブ、対称メモリと信号交換、非同期タスク、タイル順序の入れ替え、分散自動調整、資源分割を組み合わせ、NVIDIA H800/L20とAMD MI308Xの8〜64 GPUで通信とGEMM・MoE・FlashDecodeを重ね合わせる。PyTorch+NCCL/RCCL比で各種カーネルを1.09〜44.97倍高速化し、低遅延AllToAllではDeepEP比平均1.18倍/1.44倍を報告する。

Triton-distributedはTritonへOpenSHMEM互換の一方向通信プリミティブを統合し、計算と通信の双方をPythonから記述して同じコンパイル系で処理する。単に集団通信APIを追加するのではなく、対称メモリ、信号交換、非同期タスクをプログラミングモデルに据え、通信タイルと計算タイルの順序入れ替え、コピーエンジン利用、ノード間低遅延プロトコル、資源分割、自動調整まで組み合わせて重ね合わせを生成する。NVIDIAのNVSHMEMとAMDのROCSHMEMへ同じ抽象化を下げることで、専用CUDA実装に近い性能を保ちながら複数ハードウェアへ移植できる。

代表結果として、単一ノードAllGather+GEMMは8基H800でPyTorch+NCCL / FLUXに対してPyTorch+NCCL比1.42倍、FLUX比1.09倍。GEMM単体性能が約95%でも重ね合わせで複合処理を上回る。
## 問題設定
大規模言語モデルではモデル容量と演算量のため複数アクセラレータが不可欠になり、各層の行列積だけでなくGPU間のAllGather、ReduceScatter、MoEのAllToAllなどが実行時間を占める。既存のPyTorch+NCCL/RCCL型実行では計算カーネルと集団通信を別操作として発行するため、通信が終わるまで次の計算が待ちやすく、計算器・メモリ帯域・ネットワークのいずれかが遊ぶ時間が生じる。FLUXやCOMETのように通信と計算を細粒度に融合すれば待ちを隠せるが、通信トポロジ、同期信号、タイル順序、SM割当までCUDA/C++で手作業する必要があり、Python中心のモデル開発との隔たりが大きい。従来Tritonは単一GPU内のタイル計算を高水準に生成できる一方、遠隔メモリアクセスやデバイス間同期を第一級に表現できない。従来の分散コンパイラもLLMで重要なGPU主導の細粒度通信と計算の重ね合わせを十分扱えず、性能のために専用低水準実装へ戻るという問題が残っていた。
## 新規性
Triton-distributedはTritonへOpenSHMEM互換の一方向通信プリミティブを統合し、計算と通信の双方をPythonから記述して同じコンパイル系で処理する。単に集団通信APIを追加するのではなく、対称メモリ、信号交換、非同期タスクをプログラミングモデルに据え、通信タイルと計算タイルの順序入れ替え、コピーエンジン利用、ノード間低遅延プロトコル、資源分割、自動調整まで組み合わせて重ね合わせを生成する。NVIDIAのNVSHMEMとAMDのROCSHMEMへ同じ抽象化を下げることで、専用CUDA実装に近い性能を保ちながら複数ハードウェアへ移植できる。
## 手法
### 手法のあらまし
入力は通常のTritonで書かれたGEMMなどの計算カーネル、各rankの対称メモリ、通信先と同期条件を表すOpenSHMEM互換プリミティブである。まずホスト側が全rankへ同サイズの対称バッファと信号領域を確保し、通信タスクと計算タスクを別ストリームまたは別スレッドブロックとして非同期に起動する。通信側はput/getや信号付き転送でタイルを遠隔GPUへ送り、到着したタイルの信号を更新する。計算側はwaitで自分が必要とする信号だけを監視し、consume_トークンでその信号と後続ロードの依存関係をコンパイラへ伝えるため、全通信完了を待たず到着済みタイルからGEMMを進める。次にスウィズリングでrankごとの開始タイルや転送順をずらし、ノード内転送、ノード間P2P、GEMM、局所リダクションが互いを待たず流れるようにする。ノード内通信は可能ならコピーエンジンへ移し、ノード間通信には少数SMを割り当て、残りを計算へ使う。分散自動調整器は通信と計算を含む関数全体を候補タイル設定ごとに測定し、全GPUで結果を同期して共通の最良設定を決める。最後に通信部分をNVSHMEM/ROCSHMEM系ビットコード、計算部分をTriton中間表現からLLVM IRへ下げて統合し、NVIDIAではPTX、AMDではAMDGCNを生成する。出力は通信待ちを計算の背後へ隠した分散カーネルである。

### 対称メモリ・信号交換・非同期タスク
各rankは同じ大きさの対称メモリを確保するが、単一の統一仮想アドレスとして直接読むのではなく、put/get系の一方向通信で遠隔rankへデータを移す。各タイルの到着状態は対称メモリ上の信号で表し、通信タスクと計算タスクは別ストリームや別スレッドブロックとして同時に走る。計算側は自分が次に読むタイルの信号だけを待つため、全rankの集団通信完了を待つ大域障壁を避けられる。あるタイルがネットワーク上を移動している間に、すでに届いた別タイルのGEMMを実行できるので、従来は露出していた通信遅延を有用な計算時間の背後へ隠す。信号が遅れた場合は依存するタイルだけが待ち、独立タイルは進められる。

### OpenSHMEM互換通信プリミティブ
コンパイラへput/get、非同期put/get、信号付きput、barrier、fence、quietなどを追加し、NVIDIAではNVSHMEM、AMDではROCSHMEM相当の実装へ下げる。さらにwait、consume_トークン、notify、原子的操作、multimemロード/ストアなど最適化向け補助プリミティブを用意する。waitが生成したトークンをconsume_トークンで後続ロードへ結び付けることで、コンパイラはこのデータが通信信号の後でのみ読めるという依存を認識できる。その結果、通信完了前の誤読を防ぎながら、依存しないロードや行列積は前倒しできる。通信ロジックをPython側に保つため、利用者は計算カーネルを大きく書き換えず分散化できる。

### 通信計算重ね合わせとタイル順序入れ替え
AllGather+GEMMやGEMM+ReduceScatterを大きな一括操作として扱わず、入力を複数タイルへ分けて通信と計算を交互に流す。各rankが同じ順番でタイルを要求すると通信先が集中して待ちが生じるため、rankごとに開始位置をずらすスウィズリングを使う。ノード間GEMM+ReduceScatterでは、他ノードが早く必要とする部分和から計算し、局所rankへ送りながら次のGEMMを進め、まとまった部分和を他ノードへ転送する。受信側も到着済み部分から次段の計算を始める。こうしてノード内転送、ノード間P2P、GEMM、局所リダクションを時間軸上で重ね、通信だけが残る空白区間を縮める。

### トポロジ別通信最適化
ノード内とノード間では最適な通信資源が異なるため、同じ集団通信を一律に実装しない。ノード内AllGather/ReduceScatterではGPUのコピーエンジンを利用し、SMをほぼ計算へ残す。ノード間では遠隔メモリアクセスにSMも必要になるため、階層的P2P転送、低遅延プロトコル、multimem機能を組み合わせる。MoEのAllToAllでは推論向け低遅延経路、FlashDecodeでは長いKV領域を複数GPUへ分散して各GPUのHBM帯域を利用し、PCIe接続L20では専用AllGatherを構成する。同じPython抽象化を保ちつつハードウェアごとのボトルネックへ通信実装を合わせる。

### 分散自動調整と資源分割
単一GPUの自動調整と違い、分散カーネルは各試行で全rankの信号状態と同期条件を揃える必要がある。そこで通信、計算、ホスト側起動を含む対象関数全体を候補設定ごとに一回実行し、試行前に信号を初期化し、測定後に全GPUで結果を集約して共通の最良タイル設定を選ぶ。さらに通信と計算が同じSMを奪い合わないよう空間的に資源を分割する。論文のH800ノード間GEMM+ReduceScatter例ではGEMMへ116 SM、ノード間P2Pへ1 SM、局所リダクションへ16 SMと132 SMを段階ごとに割り当てる。目的は各非同期タスクの終了時刻を揃え、一つの通信処理だけが最後まで残る長い末尾待ちをなくすことである。

### 全体のデータ／制御の流れ
Python記述層、OpenSHMEM/補助通信プリミティブ層、Triton中間表現とLLVM IR、ハードウェア別コード生成からなる。分散実行時は通信タスクと計算タスクを信号で結び、空間的な資源分割と時間的なタイル順序調整を併用する。
## 評価条件
- **ハードウェア**: NVIDIA H800: 単一ノード8 GPU、複数ノード16〜64 GPU、NVIDIA L20: PCIe接続8/16 GPU、AMD MI308X: 単一ノード8 GPU
- **比較対象**: PyTorch+NCCL、PyTorch+RCCL、FLUX、DeepEP、NVSHMEM組込みAllGather、NCCL AllGather
エンドツーエンドのLLMサービング全体ではなく、分散推論・学習を構成する通信および通信計算複合カーネルの実機評価が中心である。最大64 GPUまで測定し、一部AllToAllは128 GPUでも傾向を確認する。
## 主要結果
Triton-distributedは、Triton生成GEMM単体がcuBLAS/CUTLASSの約95%でも、通信と計算を細粒度に重ねることで複合処理全体を高速化する。NVIDIA/AMD双方でPyTorch通信基盤を上回り、MoE通信では大幅な改善を示す一方、ノード間MoE+ReduceScatterや128 GPU AllToAllでは通信方式の限界も明示される。

- 単一ノードAllGather+GEMM / PyTorch+NCCL比1.42倍、FLUX比1.09倍 (比較対象: PyTorch+NCCL / FLUX; 条件: 8基H800) — GEMM単体性能が約95%でも重ね合わせで複合処理を上回る。

- 単一ノードGEMM+ReduceScatter / PyTorch+NCCL比1.28倍、FLUX比1.30倍 (比較対象: PyTorch+NCCL / FLUX; 条件: 8基H800) — scatterを別ストリームへ出し局所リダクションと重ねる構成が有効。

- ノード間AllGather+GEMM / PyTorch+NCCL比1.33倍、FLUXの95.60% (比較対象: PyTorch+NCCL / FLUX; 条件: 16基H800) — Python/コンパイラ生成でも手調整FLUXに近い性能。

- ノード間GEMM+ReduceScatter / PyTorch+NCCL比1.42倍、FLUXの96.36% (比較対象: PyTorch+NCCL / FLUX; 条件: 16基H800) — 階層通信と資源分割でノード間重ね合わせを維持。

- MoE複合カーネル / AG+MoE単一ノード44.97倍、ノード間26.50倍、MoE+RS単一ノード15.55倍、ノード間5.16倍 (比較対象: PyTorch+NCCL; 条件: H800) — 比較PyTorch実装がPythonループを含むため倍率は強い基準との比較ではない点に注意が必要。

- 低遅延AllToAll / DeepEP比Dispatch平均1.18倍、Combine平均1.44倍 (比較対象: DeepEP; 条件: 8〜64基H800) — 数百行のPython実装で高性能CUDA実装を概ね上回るが64基Dispatchは例外。

- AMD単一ノード / AG+GEMM 1.09倍、GEMM+RS 1.16倍 (比較対象: PyTorch+RCCL; 条件: 8基MI308X) — 同じコンパイラ設計がAMDでも重ね合わせ利得を持つ。

### 負の結果・境界条件
- MoE+ReduceScatterは1ノードから2ノードで良好な弱スケーリングを示さず、専用ReduceScatter実装が将来課題。
- AllToAllは128 GPUではIBGDAを使うDeepEPが優位で、NVSHMEMビットコードがIBGDAを支えないことが制約。
- 分散FlashDecodeは全体KV長が256K未満ではGPU数を増やしても有利でない。
- 主評価はカーネル単位であり、LLMサービング全体のスループット改善率ではない。

### 結果の読み方
高速化は、通信を別工程として待つのではなく、必要データが届いたタイルから計算し、コピーエンジンや少数SMへ通信を割り当てて計算資源との競合を抑えることで生じる。ノード数が増えて通信方式自体のスケーラビリティが不足すると、重ね合わせだけでは隠し切れず利得が縮小する。
## 品質への影響
演算内容を近似せず通信・計算の実行順と資源利用を変えるため、モデル品質を意図的に変えない。
## 既存研究との差
既存Tritonが単一GPUの計算カーネルを主対象とするのに対し、遠隔メモリアクセス、信号同期、ノード間通信をコンパイラの第一級要素へ追加する。NCCL/RCCLの集団通信を計算の前後に呼ぶ方式と異なり、タイル単位のデータ依存を明示して通信途中から計算を開始する。FLUXのような専用CUDA/CUTLASS融合実装に対しては、より高水準なPython記述と複数ハードウェア対応を優先しつつ近い性能を狙う。
## 限界
- 評価の中心はカーネル単位で、エンドツーエンドのLLMサービング性能やスケジューリングとの相互作用は直接評価していない。
- MoE+ReduceScatterは2ノードで弱スケーリングが悪く、専用通信カーネルが必要。
- AllToAllはIBRCを使い、IBGDAを使うDeepEPに128 GPUで劣る。
- 性能はハードウェアトポロジと手法ごとのタイル・資源設定に依存し、自動化されても分散同期の設計知識は必要。
- 低遅延通信で大きなバッファを確保してメモリ管理を簡略化する箇所があり、DeepEPよりメモリ消費が増える。
## 実装状態
ByteDance SeedがTriton-distributedをGitHub公開している。Triton拡張、NVSHMEM/ROCSHMEM連携、NVIDIA PTXとAMDGCN生成を実装し、論文の複数カーネルを実機評価している。
## 研究上の位置づけ
LLM時代の分散コンパイラ研究として、通信を外部ライブラリ呼び出しではなくコンパイラが扱うデータ依存・資源割当へ取り込み、手書き通信計算融合の知見を高水準言語へ移す研究である。
