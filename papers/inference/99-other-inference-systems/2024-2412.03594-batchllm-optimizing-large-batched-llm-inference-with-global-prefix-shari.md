# BatchLLM: Optimizing Large Batched LLM Inference with Global Prefix Sharing and Throughput-oriented Token Batching

## 書誌
- 初版: 2024-11-29、v3: 2026-04-22
- MLSys 2026 Industry Track
- 正規識別子: arXiv:2412.03594

## 概要
BatchLLMは、大規模な一括推論で「全promptを実行前に見渡せる」ことを利用し、接頭辞KV再利用とtoken batchingを共同最適化する。通常のprefix cacheはLRUで将来の再利用を知らないため、後で再利用されるKVでも途中で追い出される。BatchLLMは全promptから共通接頭辞を明示的に抽出し、同じprefixを持つ要求を近接実行する。さらに要求順を並べ替えてdecode tokenと後続prefill chunkを混ぜ、固定token数ではなくGPU memory余裕からbatchを拡大し、共有prefix attentionを水平融合する。MLSys 2026版ではvLLM/SGLang比1.3〜10.8倍を報告する。

## 問題設定
大規模バッチでは、同じ文書、system prompt、few-shot例を多数の要求が共有する。論文の典型産業ワークロードでは、全体を事前解析した理論上のtoken saving ratioは58.1%だが、vLLMの暗黙的prefix cachingは35.8%に留まる。原因は、LRUが将来のreuse順を知らず、再利用直前のKVを早期evictし得ることである。

またonline向けschedulerは到着順や公平性を優先するため、decode中心iterationではtoken数が少なくGPU利用率の谷が生じる。offline batchなら要求順を変えられるので、decode比率の高い要求を先に進め、後続prefillと同じiterationへ混ぜる余地がある。

## 手法
### 1. 大域的prefix識別
実行前に全prompt token列からcompact prefix treeを構築し、共有prefixを明示する。多段prefixをそのまま実行するとscheduler依存関係とattention kernelの種類が増えるため、BatchLLMは木上の動的計画法で第一レベルの共有prefixを長くする。子孫を共有prefix側へ移したときの再利用gainと複製penaltyを比較し、gainが大きい場合だけ構造を変える。

産業ワークロードでは元の多段prefixのtoken saving ratioが約56%、単一レベル化後でも約55%で、再利用機会の損失は約1ポイントに留まる。アルゴリズムはnode数 n、平均分岐 c に対して O(n c^2)、space O(n) で、実データでは前処理費用は推論全体に比べ小さい。

### 2. Prefix-sharing group単位の実行
同じ第一レベルprefixを持つ要求をgroup化し、groupを近接して処理する。一度作った共有KVを短期間に使い切るため、LRU任せよりKV lifetimeが短くなり、再計算とpeak memoryを抑えやすい。

### 3. 要求reordering
prompt長と想定decode長を用い、decode/prefill比率が高いgroupを先に進め、長いprefillを持つgroupを後ろへ回す。先行groupがdecode段階へ入った後に後続prefill chunkを重ねることで、decodeだけの小token iterationを減らす。

### 4. Memory-centric token batching
request数やtoken数だけで上限を決めず、KV cacheと作業領域を含む現在のGPU memory使用量から安全なbatch sizeを決める。decode中心iterationではmemory余裕があれば従来上限より多くのrequestを詰められる。prefix sharingで減ったKV量もbatch拡大に使う。

### 5. 水平融合attention
共有prefixと各request固有suffixへのpartial attentionを別kernelにせず、同一kernel内の異なるthread blockで処理する。各部分へ異なるtilingを使い、tail effectとkernel launch overheadを削減する。実装はTritonを用いる。

## 評価条件
比較対象はvLLMとSGLangで、Llama-3.1-8B-InstructやQwen-2.5-7Bを使ったmicrobenchmark、産業ワークロード、heavy-tail生成長を評価する。NVIDIA A100とAMD MI200を含む複数環境でend-to-end throughput、token saving ratio、prefix grouping overhead、per-iteration token数、構成要素除去を測る。

典型産業ワークロードは8,000 query、平均share degree約3、共有prefix長約1,570 token、各request固有prompt約30 tokenである。heavy-tail実験では320 requestを20 groupに分け、各group 16 requestが2,000-token prefixを共有し、200-token固有promptを持つ。生成長はPareto分布で10〜512 token、平均51.2、p50=25、p99=509とする。

## 主要結果
産業ワークロードではBatchLLMがvLLMに対してA100で約1.3倍、MI200で約1.26倍高速化した。多段prefixを単一レベル化してもtoken saving ratioは56%から55%へ約1ポイントしか落ちず、DP前処理は8,000 request全体で1.51秒、実推論919.54秒に対して小さい。peak KV使用量は約50%で、BatchLLMではKV swap/recomputeが発生しなかった。

heavy-tail条件ではthroughputがvLLMの5.26 req/sから17.02 req/sへ増え、3.2倍となった。prefix groupingのablationでは6,400 requestの合成条件で、閾値ベースheuristicが約25% token saving・約12.4 req/sなのに対し、BatchLLMは設定Aで48.6%・15.9 req/s、設定Bで39.7%・14.5 req/sとなった。

共有prefix 2,000 token、share degree 16のmicrobenchmarkではBatchLLMが85.2% token savingを達成し、vLLM + chunked prefill + prefix cachingは40.1%だった。共有prefix 16,000 token、share degree 16ではBatchLLM 92.6%に対し、vLLM 6.3%、SGLang 5.2%まで差が広がる。論文全体ではhardwareとworkloadによりvLLM/SGLang比1.3〜10.8倍のend-to-end改善を報告する。

## 既存研究との差
vLLM/SGLangのprefix cacheはonline requestを過去履歴で再利用する。BatchLLMは全request既知のthroughput-oriented batchへ問題設定を限定し、未来の再利用順を事前に使う。KV reuseだけでなく、request ordering、prefill/decode mixing、memory budget、attention kernelまで同じ目的で連動させる点が異なる。

## 限界
主要前提は、バッチ全体を実行前に知り、request順を自由に変更できることである。厳格なper-request latency SLOや公平性が必要なonline対話ではgroup化とreorderingの自由度が小さくなる。prefix共有が短い、share degreeが小さい、生成長推定が外れる、KV memoryに余裕がない条件でも利得は縮む。

水平融合kernelの利得もhardwareとshape依存であり、MLSys版の1.3〜10.8倍を一般的なLLMサービングへ固定倍率として外挿すべきではない。
