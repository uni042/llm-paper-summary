# PQCache：積量子化索引と階層メモリによる長文脈KVキャッシュの選択的取得

## 概要

長文脈の大規模言語モデル推論では、過去の各トークンに対応する鍵と値をKVキャッシュとして保持する。文脈が長くなるほどKVキャッシュは大きくなり、GPUメモリへ収まらない場合にはCPUメモリへの退避と転送が必要になる。全ての過去トークンを毎回注意計算へ参加させると、デコードのたびに大きなKVを読み込み、注意計算と通信の両方が増える。静的にKVを削除する方法は容量を減らせるが、後から重要になるトークンを失う危険がある。

PQCacheは、長文脈のKV管理を**問い合わせベクトルに対する埋め込み検索**として扱う。プリフィル時に各層・各KVヘッドの鍵を積量子化（Product Quantization、PQ）し、小さな検索コードとセントロイドを作る。デコード時には現在の問い合わせとセントロイドの内積から各過去トークンの近似注意スコアを安価に計算し、上位のトークンだけを選ぶ。選ばれたトークンの元の鍵と値をCPUから取得し、実際の注意計算には元のKVを使う。

本論文の重要な点は、検索アルゴリズムだけでなく、プリフィル中のCPUクラスタリングとGPU計算の重畳、デコード中のコード先読み、GPUのブロックキャッシュを一体として設計していることである。Llama-3.1-8Bの128K文脈を用いたInfiniteBenchでは、過去トークンの1/10だけを選択する条件で平均スコア46.80を報告し、比較方式に対する改善は+4.60%である。これはスコアの相対的な改善であり、トークン生成速度が4.60%向上したという意味ではない。

## 問題設定：静的削除と問い合わせごとの全走査の間

従来のKVキャッシュ削減では、古いトークンを追い出す方式、直近や初期のトークンを優先して保持する方式、現在の問い合わせに関連するトークンを動的に選ぶ方式がある。静的な追い出しは簡単だが、削除したKVを後から参照できない。動的な選択は必要なKVを残しやすいが、全トークンの高精度鍵と問い合わせの内積を計算するなら、選択のための費用が全体注意計算に近づく。

PQCacheは、**重要トークンを選ぶ段階では高精度の鍵を全て使う必要はない**という立場を取る。検索用の小さなPQコードで近似的な重要度を計算し、選択後の注意計算だけに元のKVを使う。したがって、検索索引の圧縮と、注意計算に用いるKV値の量子化は異なる。検索用コードは近似でよいが、実際の注意計算では選択した元KVを取得するため、選択ミスによる品質低下と、KV値そのものを低ビットに丸める誤差を分離できる。

また、長文脈ではGPUとCPUの階層メモリを利用する必要がある。CPUに退避したKVを必要な時だけ取り出すには通信が発生し、検索が正確でも転送が遅ければ推論全体は遅くなる。PQCacheはGPU上の初期・直近トークン、CPU上の中間トークン、検索コード、セントロイド、ブロックキャッシュの配置を設計し、検索・通信・注意計算の重複可能な部分を重畳する。

## 手法

### 1. 鍵ベクトルの積量子化と検索索引

各層・各KVヘッドの鍵ベクトルを `m` 個の部分ベクトルへ分割する。各部分空間でK-Meansクラスタリングを行い、`2^b` 個のセントロイドを作る。各トークンの部分ベクトルを最も近いセントロイドへ割り当て、`b` ビットのコードを記録する。検索用には元の高次元鍵全体を保持する代わりに、部分空間ごとのセントロイド識別子を使える。

現在の問い合わせも同じ部分空間へ分割し、問い合わせの部分ベクトルと各セントロイドの内積を事前計算する。過去トークンの近似内積は、そのトークンが持つコードで対応する内積値を参照し、部分空間分を合計して求める。全トークンについて高精度の問い合わせ・鍵の積を行うより計算が軽い。近似スコアの上位 `k` トークンを選び、その元の鍵・値を注意計算へ渡す。

検索の計算量には、セントロイドとの内積を計算する費用と、全コードを走査して上位候補を決める費用がある。前者はコードブックの大きさに、後者は文脈長と部分空間数に依存する。原著の解析では、KVヘッド数 `h_kv` と部分空間数 `m` の積がモデルの隠れ次元より十分小さい条件で、検索の線形項を全体注意の高次元計算より小さくできる。ただしPQ検索が無料になるわけではない。

### 2. プリフィルでの非同期オフロードとクラスタリング

プリフィルでは、各Transformer層の問い合わせ・鍵・値をGPUで計算した後、鍵と値を非同期にCPUへ送る。その間GPUは同じ層の注意計算とフィードフォワード計算を進める。CPU側では受け取った鍵から各KVヘッド・部分空間ごとにK-Meansを並列実行し、セントロイドとコードを構築する。これにより、GPU計算、GPU→CPU転送、CPUクラスタリングを重ねる。

長い文脈ではプリフィルの注意計算が概ね文脈長の二乗に比例する一方、通信とK-Meansの費用は文脈長に対してほぼ線形に増えるため、十分長い入力ではCPU側の仕事をGPU計算中に隠しやすい。しかし短い入力ではCPUクラスタリングがGPU計算より長くなり、プリフィル完了を待たせることがある。そこで著者は、クラスタリング時間を `α1+β1 sT`、GPU計算時間を `α2+β2 s+γ2 s²` と近似し、文脈長 `s` に応じてK-Means反復数 `T` の上限を調整する。

この適応反復数は、CPUクラスタリングがGPU計算を追い越して待ち時間になるのを避けるための設計である。反復数を減らし過ぎればセントロイドの品質が落ち、重要トークンの検索精度に影響する。論文はモデル・装置ごとに計算時間を測って回帰係数を求め、GPU計算と重ねられる範囲で反復数を決める。これはCPUオフロード環境で特に重要な、精度と待ち時間の交換条件である。

### 3. デコード時の三領域KV管理

デコード時のKVキャッシュは、初期トークン、途中のトークン、直近トークンの三領域に分ける。初期と直近のKVはGPU上に置き、毎回の注意計算へ直接参加させる。中間トークンのKVはCPUに保持し、現在の問い合わせに応じて検索された上位候補だけをGPUへ戻す。直近領域から古いトークンが押し出されると、その鍵をPQコードへ変換し、元KVとともにCPUへ非同期に送る。

各層の計算が進む間に次層のPQコードをCPUからGPUへ先読みし、GPU上に常駐させたセントロイドと組み合わせて近似検索する。著者は7B GQAモデルで `m=2、b=6` のセントロイドが約16MBに収まる例を挙げる。セントロイドの大きさは文脈長に依存しないが、コードの大きさはトークン数に比例する。コードは元のFP16鍵より十分小さいため、次層の処理と転送を重ねやすい。

検索後に選んだ中間KVをCPUからGPUへ取得する処理は、検索結果が決まらないと開始できないため、完全には重畳できない。ここがデコードの残る通信費になる。PQCacheは頻繁に選ばれるトークンのKVをGPUにキャッシュし、転送を減らす。キャッシュはトークン単位ではなく128トークンのブロック単位で管理し、最近使われたブロックまたは頻繁に使われたブロックを保持する。細かいトークン単位の管理費が大きくならないようにする設計である。

### 4. キャッシュ・先読み・転送の重畳

デコードの実行順序は、次層のPQコード先読み、現在層の問い合わせ計算、コードとセントロイドからの近似上位選択、CPU上のKV取得、初期・直近・取得KVによる注意計算という流れになる。GPUに残した初期・直近KVは検索対象とは別に直接参加し、重要な最近の文脈を維持する。中間領域は毎回選び直せるため、静的削除と違って後から重要になったトークンを再び参照できる。

キャッシュにはLFU（使用頻度優先）とLRU（最近使用優先）を比較し、実験ではどちらも類似した傾向を示す。キャッシュが大きいほど必ず効率が上がるわけではなく、ブロック数が管理領域を超えると更新費用が増える。著者は4KトークンのGPUキャッシュと32ブロックという構成で、およそ0.6のヒット率を得た例を報告する。索引の圧縮だけでなく、転送する元KVを減らすことが低遅延の鍵になる。

## 評価条件

主な品質評価はLlama-3.1-8Bの128K文脈で行い、LongBenchとInfiniteBenchを使用する。LongBenchでは過去トークンの1/5または1/10を注意へ参加させ、検索用の追加通信量を元鍵の1/128相当に揃える。InfiniteBenchは平均約100Kトークンと長いため、追加通信量を1/64相当に設定する。これらは比較条件が異なるため、二つのベンチマークの数値を同じ通信費の実験として扱わない。

| 観点 | 条件 |
|---|---|
| 主モデル | Llama-3.1-8B、128K文脈。Mistral-7BやLlama-3.1-70Bの追加実験あり |
| 品質課題 | LongBench、InfiniteBench、針探索、GSM8Kの思考過程付き推論 |
| 選択率 | 過去トークンの1/5または1/10を注意計算へ参加 |
| LongBenchのPQ | `m=2、b=6`、追加通信量は元鍵の1/128相当 |
| InfiniteBenchのPQ | `m=4、b=8`、追加通信量は元鍵の1/64相当 |
| 比較 | Full、Oracle、H2O、SnapKV、PyramidKV、InfLLM、SPARQなど |
| GPU | RTX 4090 24GB。必要に応じて複数GPUを使用 |
| CPU | Xeon Gold 6330×2、CPUメモリ500GB |
| 通信 | PCIe 1.0 x16を想定したCPU↔GPU転送 |
| 指標 | タスクスコア、初期応答時間、出力1トークン当たり時間、キャッシュヒット率 |

各ベンチマークのスコアは正答率、ROUGE、F1など課題ごとに異なる指標の平均であり、単一の正答率ではない。Oracleは理想的な重要トークン選択を比較する参照条件で、実装可能な一般手法とは区別する。比較方式には追加通信量と選択トークン数を揃えるために補正した設定があり、元の論文のデフォルト設定と同一とは限らない。

## 評価結果

### 1. LongBenchでの品質維持

Llama-3.1-8Bの128K文脈で、過去トークンの1/5を選択する条件では、PQCacheは多くの課題で全体注意やOracleに近いスコアを示す。例えばQasperでは全体注意44.79、PQCache44.93、MultiFieldQAでは全体54.63、PQCache55.11である。HotpotQAでは全体55.81に対しPQCache55.60であり、常に全体注意を上回るわけではない。1/10の選択率ではQasperが44.36、MultiFieldQAが54.97となり、より少ないトークンでも近い品質を保つ。

| LongBench課題 | 全体注意 | PQCache 1/5 | PQCache 1/10 |
|---|---:|---:|---:|
| Qasper | 44.79 | 44.93 | 44.36 |
| MultiFieldQA | 54.63 | 55.11 | 54.97 |
| HotpotQA | 55.81 | 55.60 | 56.35 |
| QMSum | 25.11 | 25.67 | 25.24 |
| TREC | 72.50 | 72.50 | 72.00 |

一部で選択的注意のスコアが全体注意を上回るのは、不要な文脈を除くことでノイズが減る可能性があるためだと著者は述べる。ただし、これを全ての入力で選択的注意が全体注意より優れる証拠と解釈してはならない。選択率、問い合わせの位置、モデル、タスクによって結果は変わる。

### 2. InfiniteBenchでの+4.60%の意味

InfiniteBenchでは、1/5の選択率でPQCacheが比較方式に対して+1.50%、1/10の選択率で+4.60%の平均スコア改善を報告する。原著表4の1/10条件では、Fullの平均47.63、Oracle47.60、SnapKV(C)44.71、PyramidKV(C)44.74、PQCache46.80である。PQCacheはFullよりわずかに低いが、他の選択方式より高い平均スコアを保つ。

| InfiniteBench・Llama-3.1-8B・128K | 平均スコア |
|---|---:|
| 全体注意（Full） | 47.63 |
| Oracle（理想選択の参照） | 47.60 |
| SnapKV(C)、選択率1/10 | 44.71 |
| PyramidKV(C)、選択率1/10 | 44.74 |
| PQCache、選択率1/10 | 46.80 |

原著の「+4.60%」は、特定の既存方式と比較したスコアの相対改善である。表中の46.80と44.74の差は2.06スコアポイントであり、44.74を基準に割ると約4.60%になる。速度やメモリ容量が4.60%改善したという意味ではない。1/5条件での改善率+1.50%と、1/10条件での+4.60%も別々の選択率に対応する。

### 3. 問い合わせ位置を変えた場合の頑健性

LongBenchの通常の質問応答では、質問が入力の末尾に置かれることが多い。SnapKVやPyramidKVはこの構成に有利な選択を行うため、著者は質問を文脈の前へ移した条件も評価する。選択率1/10、追加通信1/128の設定で、6課題平均はSnapKV(C)30.29、PyramidKV(C)29.97、PQCache32.44である。PQCacheは質問が末尾にあるという仮定に依存せず、問い合わせごとに関連トークンを選ぶため、質問位置が変わる条件で相対的に有利になる。

| 質問を先頭に置いたLongBench | SnapKV(C) | PyramidKV(C) | PQCache |
|---|---:|---:|---:|
| Qasper | 18.70 | 17.60 | 25.76 |
| MultiFieldQA | 43.48 | 44.07 | 47.99 |
| HotpotQA | 42.93 | 42.55 | 43.28 |
| 6課題平均 | 30.29 | 29.97 | 32.44 |

ただし、この実験では全方式のスコアが通常配置より低下しており、PQCacheも質問位置の変更に完全に影響されないわけではない。比較対象に対する頑健性が高いという結果であり、任意の文脈配置で品質を保証するものではない。

### 4. 大規模針探索と70Bモデル

針探索では、Llama-3.1-8Bの最大約131Kトークンまで入力を延ばし、文脈のさまざまな位置に短い事実を埋めて検索できるかを調べる。選択率1/10・追加通信1/64の条件で、PQCacheはFullやOracleに近い成功領域を示し、SnapKVやPyramidKVと同程度の高い検索能力を報告する。ただし図9は位置と文脈長に応じた結果の可視化であり、全ての長さ・位置で100%成功するという意味ではない。

Llama-3.1-70Bの128K文脈を用いたLongBench追加実験では、全体注意の平均52.89に対し、PQCacheのCPU資源を半分にした場合52.88、同程度のCPU資源を割り当てた場合52.86である。品質が近いことは示されるが、70Bの実行時メモリとCPU資源の条件は8Bとは異なるため、単一GPUで同じ性能を得た証拠ではない。

### 5. キャッシュと重畳による遅延削減

ブロック単位のGPUキャッシュを導入すると、キャッシュなしと比較して、4Kトークンのキャッシュで出力1トークン当たり時間（TPOT）が26.3%、8Kで32.8%減少した。キャッシュヒット率はLRUとLFUで類似し、4Kキャッシュ・32ブロックでは約0.6を報告する。重要な中間KVをCPUから毎回取得しなくて済むことが遅延削減の主要因である。

プリフィルでは、GPU計算とCPU側K-Meansを重畳し、適応反復数によってクラスタリング時間がGPU計算時間を大きく超えないようにする。デコードでは次層コードの先読みとGPUキャッシュを使い、PQ検索に必要な通信の一部を隠す。残る上位KVの取得は検索後にしか始められないため、完全に無料にはならない。論文は出力1トークン当たり時間が文脈長の増加に対して比較的安定することを報告するが、具体的な遅延はGPU、CPU、PCIe、キャッシュ容量、選択率に依存する。

## 既存研究との差

H2OやSnapKV、PyramidKVなどは、過去トークンの重要度や観測窓から残すKVを決める。静的な削除に近い方式では、後から重要になったトークンを再び取得できない場合がある。PQCacheは中間KVの元データをCPUに保持し、問い合わせごとにPQ索引で重要トークンを選び直すため、検索対象を固定しない。

SPARQのように問い合わせの一部の次元を使って候補を絞る方式と比べると、PQCacheは事前に学習したセントロイドと短いコードを用いるため、コードの先読みやキャッシュをパイプライン化しやすい。KIVIなどの低ビットKV値量子化とは異なり、PQCacheの主な量子化対象は検索索引であり、選択後の注意計算には元のKVを使う。これらは競合するだけでなく、元KVの表現精度をさらに下げる手法と組み合わせる余地もあるが、その組合せの品質は別途検証が必要である。

## 限界と適用条件

第一に、PQ検索は近似である。コードブックが重要トークンの内積順位を誤ると、選択されたKVが不足して品質が落ちる。部分空間数、コードのビット幅、K-Means反復数、選択率は品質と検索費・通信量の交換条件を持つ。原著の一部設定では8×2のPQ構成がQasperで弱く、すべての構成が同等に優れるわけではない。

第二に、プリフィルでのCPUクラスタリングとGPU計算の重畳は、十分長い文脈と利用可能なCPU資源を前提とする。短文脈ではK-Meansの固定費が目立ち、GPU計算中に隠せない場合がある。CPUが他の処理で混雑している環境やPCIe帯域が狭い環境では、論文の遅延傾向をそのまま再現できない。

第三に、検索後の上位KVをCPUからGPUへ取得する処理は、検索結果に依存するため完全には重畳できない。GPUキャッシュのヒット率が低い場合や、重要トークンが文脈全体へ広く散らばる場合には転送費が増える。ブロック単位のキャッシュは管理費を下げる一方、不要なKVを同じブロックとして転送する可能性もある。

第四に、実験は主にRTX 4090 24GB、Xeon Gold 6330×2、CPUメモリ500GB、PCIe 1.0 x16という特殊な構成で行われる。RTX 4070 Super 12GBやRAM32GBのローカル環境へ同じ長文脈・同じ選択率を適用できるとは限らない。GPU容量だけでなく、CPUメモリの容量、K-Meansのスレッド数、PCIe帯域、ランタイムのKV配置を確認する必要がある。

第五に、InfiniteBenchの+4.60%は平均タスクスコアの相対改善であり、推論速度の改善率ではない。LongBenchとInfiniteBenchでは追加通信量を1/128と1/64で変えているため、二つのベンチマークの数値を同一条件の直接比較として扱えない。選択率1/10でも全体注意と同じ品質を保証するわけではなく、個別課題の劣化や質問位置による差を確認する必要がある。

第六に、PQCacheは検索索引を小さくする一方、CPU上には元の中間KVを保持する。従ってシステム全体のKV容量が1/10になるわけではなく、GPU上の注意計算とアクセス対象を減らすことが主な効果である。CPUメモリを含む総容量とGPU上の常駐容量、通信量を分けて評価すべきである。
