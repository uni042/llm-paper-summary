# SWE-Pruner：コード編集エージェントの観測文脈を作業目標に応じて行単位で削減する

## 概要

コード編集エージェントは、問題を理解して修正するまでに何度もファイルを読み、検索し、テストを実行する。`cat` や `grep` が返した大量のコードや周辺行を、そのまま大規模言語モデル（LLM）へ渡すと、文脈窓を圧迫し、API料金と推論時間を増やす。しかも一度読み込んだ不要なコードは対話履歴に残り、次の推論でも繰り返し処理される。著者らがMini SWE AgentのSWE-Bench Verified実行を分析したところ、Claude Sonnet 4.5での総トークンの76.1%がファイル読取操作に費やされ、プログラム実行12.1%、編集11.8%を大きく上回った。

SWE-Prunerは、エージェントとファイル読取環境の間に置く**観測文脈の削減器**である。エージェントは現在知りたいことを自然言語の目標ヒント（Goal Hint）として渡し、0.6Bパラメータの軽量モデルがコード行の重要度を推定する。出力は関係の薄い行を省いたコードであり、トークン単位の削除より構文・行構造を保ちやすい。既存エージェントのモデル重みを変更せず、ツールの返り値を絞る形で適用できる。

主要なエンドツーエンド評価で、SWE-Bench VerifiedのClaude Sonnet 4.5では成功率70.6%から72.0%へ上昇し、使用トークン0.911百万から0.701百万（23.1%減）、API費用0.504ドルから0.369ドル（26.8%減）になった。GLM-4.6でも成功率55.4%から56.6%へ上昇し、トークン0.791百万から0.488百万（38.3%減）となった。ただしSWE-QAでは一部条件で回答評価が悪化し、GLM-4.6では探索ラウンドが増えた。単純な「常に短く・速く・高精度」とは言えない。

## 問題設定：長いコード観測と一般的な圧縮の不整合

コード編集では、同じファイルを見ても現在の目的が「例外処理を探す」か「継承関係を理解する」かで必要な行が異なる。固定の困惑度（perplexity）や文字列の情報量でトークンを削る方式は、コードにおける括弧、インデント、関数宣言、変数の参照関係などを切り離すことがある。意味があるように見える短い抜粋でも、構文が壊れたり依存関係が抜けたりすれば修正判断を誤る。単にファイル全体を要約する方式では、デバッグに必要な具体的な識別子や行番号が消える場合がある。

検索拡張生成（Retrieval-Augmented Generation; RAG）は関連するファイルやコード塊を見つけるが、検索で返された塊の中にも現在の目的に不要な行が多い。逆に検索単位を粗くすると、少数の重要な実装行が落ちる。エージェントが何度も目的を変えながら同じリポジトリを調べる状況では、固定の圧縮率だけでは適切な観測を作れない。

本研究はモデル内部のKVキャッシュを直接圧縮するのではなく、**LLMに送る前のツール観測文字列**を削る。このため、削減量は入力トークン費用と文脈窓の節約に直結する一方、モデル内部のGPUカーネル速度を直接改善したと主張するものではない。処理の追加費用は、軽量削減モデルを実行する推論時間と、必要な行を誤って捨てるリスクである。論文はこれらを単発コード課題と複数ラウンドのエージェント課題で検証する。

## 手法

### 1. 目標ヒント（Goal Hint）を持つツール呼び出し

エージェントがファイルを読む際、通常の `cat` や `grep` へ任意の `context_focus_question` 引数を追加する。ここには「認証はどこで処理されるか」「継承メソッド解決の処理を探す」といった、現在の情報要求を単独で理解できる質問として記述する。ヒントが与えられた時だけ、ツールの生の返り値とヒントを削減器へ渡す。ヒントがない場合は通常の出力をそのまま返すため、既存ツールとの後方互換性を保つ。

この設計では、エージェント自身が探索段階ごとにヒントを変えられる。初期のリポジトリ構造把握では広く読み、原因候補が絞られた後は特定の関数や例外処理へ焦点を移す。削減器は同じファイル内容に対しても異なる行を残せるため、静的な一回限りのコード要約と異なる。ただしヒントが曖昧・不正確なら、本来必要な行の重要度も下がり得る。ヒントを生成するLLMの判断能力が追加の依存条件になる。

### 2. 軽量な行重要度推定器（Neural Skimmer）

削減器の基盤はQwen3-Reranker-0.6Bであり、入力として現在の目標 $q$ と取得したコード文脈 $C$ を受け取る。各トークン $x_i$ について、文脈と目標を条件にした重要度 $s_i=F(q,x_i\mid C;\theta)$ を推定する。コードを行集合 $L=\{l_1,\ldots,l_m\}$ に分割し、行 $l_j$ に属するトークンの重要度を平均して $\bar s_j$ とする。保持閾値 $\tau$ を超える行だけを出力へ残す。少数の高得点トークンだけで長い行全体が残ることを避け、行の内容全体が現在の目標へどれほど関連するかを判断する。

行単位にすることで、キーワード周辺だけを切り抜いて構文を破壊する危険を減らす。ただし「行を残す」だけでは、離れた行の依存関係や複数ファイルを跨ぐ呼び出し関係を必ず保持できるわけではない。入力コードのチャンクは並列に処理し、削減器自体の遅延を小さくする。削減された文脈を大規模LLMへ送ることで、軽量モデルの追加計算を後段の入力トークン削減で償却する構成である。

### 3. 条件付き確率場と再順位付けの共同学習

単純に各行を独立の二値分類とすると、連続するコード行が同じ機能を構成するという依存性を捉えにくい。著者らは保持・削除状態の遷移を学ぶ**条件付き確率場（Conditional Random Field; CRF）**を使い、正解行マスクに対する負の対数尤度を最小化する。長い入力ほど削除を過度に進める偏りを避けるため、系列長で損失を正規化する。こうして行単位の判断に前後関係を取り込む。

同時に、基盤の再順位付け器が持つ文書単位の関連度推定を失わないよう、予測関連度と教師の関連度との平均二乗誤差を別の損失とする。総損失は $L_{total}=(1-\lambda)L_{compress}+\lambda L_{rerank}$ である。これはコード行の細かな保持判断と、文書全体の検索関連度を同じ軽量モデルへ学習させる設計である。CRFが系列の一貫性を補助しても、コードの完全な構文解析器や型検査器を置き換えるものではない。

### 4. 教師モデルで作る行ラベルと学習データ

行単位の保持マスクを大量に人手付与した公開データは乏しい。そこで著者らはGitHub由来のコード断片から、Qwen3-Coder-30B-A3B-Instructを教師として、作業目標となる質問、コード文脈、保持すべき行の二値マスク、文書単位の関連度を含む四つ組 $(q,C,M,S)$ を生成する。デバッグ、機能追加、リファクタリングなど9種類のエージェント作業を対象とし、単なるキーワード一致ではない機能単位の情報要求を学習させる。

さらにQwen3-Next-80B-A3B-Thinkingを用いた判定器で合成注釈をふるい分け、最終的に61,184件の学習例を得た。学習データが合成ラベルに依存するため、教師が見落とした例外処理や稀な言語構文では、削減器も重要行を見逃す可能性がある。多言語に一般化すると断言せず、論文自身もPython中心の実装と、将来の他言語対応を限界に挙げている。

### 5. エージェントへの統合と一回の処理経路

実行時は、(1) エージェントが現在の目的を質問形式で記述、(2) 通常のファイル読取ツールを実行、(3) 生のコードと質問を軽量削減器へ渡す、(4) 各行の重要度を計算して不要行を削除、(5) 残ったコードだけをエージェントへ返す、という順序になる。対象はファイルの実体を削除する処理ではなく、**エージェントが観測する返り値の削減**である。元のファイルやリポジトリ内容は変更しない。

複数ラウンドの課題では、目的が変わるたびにヒントも更新する。単発のコード質問応答では、与えられた質問そのものを最初のヒントとして使える。論文はMini SWE AgentとOpenHandsにこの仕組みを統合し、ファイルの観測削減がエージェントの行動回数と解答品質へ与える影響を調べた。履歴を要約・削除する方式とは異なり、新たに入ってくる観測を削るため、履歴管理技術とは補完関係にある。

## 評価結果

### 1. SWE-Bench Verified：成功率・トークン・費用

| 基盤モデル | 方式 | 成功数/500 | 成功率 | 平均ラウンド | トークン（百万） | API費用（ドル） |
|---|---|---:|---:|---:|---:|---:|
| Claude Sonnet 4.5 | Mini SWE Agent | 353 | 70.6% | 51.0 | 0.911 | 0.504 |
| Claude Sonnet 4.5 | +SWE-Pruner | 360 | 72.0% | 41.7 | 0.701 | 0.369 |
| GLM-4.6 | Mini SWE Agent | 277 | 55.4% | 49.3 | 0.791 | 0.055 |
| GLM-4.6 | +SWE-Pruner | 283 | 56.6% | 36.6 | 0.488 | 0.035 |

Claude Sonnet 4.5では成功率+1.4ポイント、トークン23.1%減、費用26.8%減、平均ラウンド18.2%減となる。GLM-4.6では成功率+1.2ポイント、トークン38.3%減、費用36.4%減、ラウンド25.7%減となる。コード読取の冗長な観測を減らすことで、後続LLMが短い文脈を処理し、不要な探索ラウンドを省けるという仮説と整合する。成功率の上昇幅は比較的小さいため、費用節約を主目的とする技術として解釈するのが適切である。

別の50件の無作為部分集合で、無削減エージェントは成功率62%、トークン0.972百万だった。SWE-Prunerは64%、0.670百万で、LLMLingua2は54%、0.856百万、RAGは50%、0.771百万、LongCodeZipは54%、0.889百万だった。行単位・目的条件付きの選別が、この比較では単純なトークン削減や粗い検索より品質を保ちやすい。ただしこの50件の比較と、500件の主実験の成功率を同じ母集団の値として混ぜてはいけない。

### 2. SWE-QA：費用は減っても探索が増える条件

SWE-QAでは3つのリポジトリについて、平均解答評価点、ラウンド数、トークン量を比較した。Claude Sonnet 4.5ではStreamlinkの評価点が8.36から8.59へ改善し、トークン611.2千から557.1千へ減った。一方GLM-4.6では同じStreamlinkの評価点8.56から8.56と横ばい、トークン318.2千から145.1千へ54.4%減ったが、ラウンドは18.2から25.0へ増えた。

負の結果として、GLM-4.6のReflexでは平均評価点が8.37から8.23へ、Conanでは8.58から8.45へ低下した。Reflexのラウンドは26.1から36.7、Conanでは21.4から27.7へ増えている。削減後の文脈を見たエージェントが、十分な確証を得られず追加ファイルを探索する可能性がある。それでも総トークンは減るため、**観測量の節約とエージェント行動の節約は別の指標**である。

| SWE-QA・GLM-4.6 | 平均評価点：元→削減 | ラウンド：元→削減 | トークン千：元→削減 |
|---|---|---|---|
| Streamlink | 8.56→8.56 | 18.2→25.0 | 318.2→145.1 |
| Reflex | 8.37→8.23 | 26.1→36.7 | 142.3→101.2 |
| Conan | 8.58→8.45 | 21.4→27.7 | 175.9→116.6 |

### 3. 単発の長いコード課題

Long Code Completionでは、目標4倍の制約で実現圧縮率5.56倍、編集類似度58.63、完全一致31.5%となった。目標8倍の制約では実現圧縮率10.92倍、編集類似度57.58、完全一致31.0%だった。無削減の編集類似度64.65、完全一致40.5%より低く、**削減の品質費用は残る**。しかし比較した削減方式の中では良好であり、例えば目標8倍でSelective-Contextの編集類似度48.67、LLMLingua2の44.74を上回った。

Long Code QAでは、目標4倍の制約で実現圧縮率13.95倍、正答率59.46%、目標8倍で14.84倍、正答率58.71%だった。無削減の正答率54.05%を上回る条件があり、不要なコード行を除くことが回答の焦点化に寄与する可能性がある。対照的に、LongCodeZipの目標8倍では7.39倍、正答率54.95%、RAGは5.87倍、55.86%だった。圧縮率の大小だけでなく、残す行が質問に対応しているかが重要である。

### 4. 軽量モデルの遅延と適用条件

論文の削減器は0.6Bの再順位付け器であり、入力長8,000トークンまで先頭トークン遅延が100ミリ秒未満と報告する。これは削減器単体の計測であり、リポジトリ探索、複数回のファイル読取、後続の大型モデルによる生成、テスト実行を含むエージェント全体の実行時間ではない。追加モデルの配置、同時要求数、CPU/GPUメモリ共有の費用は運用環境に依存する。

また、削減器を使うかどうかは目標ヒントの有無で制御できる。大量の関連行が必要な段階や、初期探索で広い文脈が必要な段階では、削減を使わず全文を返す運用も可能である。論文の評価は、削減率と成功率の交換関係を示すが、任意の圧縮率で必ず精度が改善するという結果ではない。

## 既存研究との差

LLMLingua2やSelective-Contextは一般の文章にも使えるトークン単位の選択方式であるが、コードの行・構文の一体性を十分に保たない場合がある。RAGは類似したコード塊を検索するものの、現在の作業に必要な個別の行まで選別するとは限らない。LongCodeZipはコード構造を考慮するが、主として単発課題向けの静的圧縮である。SWE-Prunerはエージェントが現在の作業目的を明示し、ファイル読取結果をその目的で**毎回選び直す**点が異なる。

一方、長い対話履歴を要約・折り畳むエージェント記憶管理は、すでに受け取った観測の保存・圧縮を扱う。SWE-Prunerが介入するのは新しい観測が入る瞬間であり、両者は別の段階を最適化する。後段LLMの重み、注意カーネル、KVキャッシュ形式を変更しないため、モデル提供APIを利用するエージェントにも適用しやすいが、軽量削減器を別途実行する資源は必要である。

## 限界・負の結果・実装状況

第一に、主実装はPythonのリポジトリに重点を置いている。複数言語での完全な構文保存や、複雑なビルド生成物、マクロ展開、言語間呼び出しの保持を保証する結果ではない。論文は多言語対応を今後の課題として挙げる。行単位の選別であっても、関数宣言と利用箇所のような遠距離依存を必ず同時に残せるわけではない。

第二に、学習データは教師モデルで生成した61,184例の合成注釈であり、教師が重要と判断しなかった特殊な実装行を削減器が見落とす可能性がある。著者らは学習後に収集されたリポジトリをSWE-QAへ選ぶことでデータ漏洩を抑えているが、継続的な新規リポジトリ評価は必要だとしている。目標ヒントの質にも依存し、ヒントが間違えば削減器は誤った部分へ焦点を当てる。

第三に、軽量とはいえ別モデルの推論を加える。論文は単体の先頭トークン遅延を示すが、モデルロード時間、GPUメモリ常駐費用、多数同時エージェントの競合、ローカルCPUオフロード時の性能は主結果からは分からない。利用者がGPUメモリの小さい環境で使う場合、0.6Bモデルを追加で常駐させる費用を計上する必要がある。

第四に、SWE-QAのGLM-4.6ではReflex・Conanで回答評価が低下し、3リポジトリすべてでラウンドが増えた。短い観測だけで確信できず再探索する場合、トークン量の削減が必ずしも作業時間短縮へつながらない。単発のコード補完でも無削減に比べて完全一致率が低下している。したがって成功率が改善したSWE-Bench Verifiedだけを取り上げて、品質への悪影響がないと断定してはいけない。

第五に、本論文はエージェント観測の削減を検証した研究であり、LLMサービング基盤のスループット、GPUカーネルの処理量、KVキャッシュのメモリ使用量を直接計測する研究ではない。APIトークン費用の削減をGPU推論速度の倍率として解釈しないことが重要である。コードは公開されているが、論文評価時のモデル・環境と手元の実行環境が一致するとは限らない。
