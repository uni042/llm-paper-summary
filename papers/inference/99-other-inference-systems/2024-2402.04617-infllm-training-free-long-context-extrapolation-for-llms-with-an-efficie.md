# InfLLM: Training-Free Long-Context Extrapolation for LLMs with an Efficient Context Memory

## 概要
InfLLMは、数千〜数万トークンの文脈で学習された既存LLMを追加学習せず極長系列へ拡張する文脈メモリ方式である。直近の局所窓（局所 ウィンドウ）と先頭トークンは常時注意対象に残し、窓から追い出された過去KVをブロック単位の文脈メモリ（文脈 メモリ）へ保存する。各順伝播では現在クエリと関連するメモリ 単位だけを検索し、局所KVと結合して注意へ戻す。

重要なのは「古いKVを捨てる」のではなく「通常のGPU 注意 pathから退避し、必要時に再ロードする」点である。メモリ 単位は追加エンコーダを学習せず、元LLMのキー/クエリを使って代表トークンを選び検索スコアを計算する。ほとんど使われない単位はCPU メモリへoffloadし、GPU側はLRU キャッシュを持つ。Mistral-7B-Instruct-v0.2とLlama-3-8B-Instructで∞-Bench/LongBenchを評価し、MistralではRetrieve.パスキーを最大1,024K トークンまで伸ばして50例すべて100% 検索 精度を報告する。

## 問題設定
長文脈推論には二つの失敗要因がある。第一に、full 注意はsequence 長さ `L` に対し注意 コストとKV メモリが増え、極長streamを常時GPUへ置けない。第二に、モデルが学習時に見ていない巨大位置へそのまま外挿すると、位置埋め込みのout-of-domainと大量irrelevant 文脈によるdistractionで品質が崩れる。

sliding-ウィンドウ 注意は計算を一定にできるが、窓外の根拠を完全に失う。NTK/RoPE scaling等は位置 rangeを広げても、全historyを読む計算とdistractionは残る。KV evictionは古いトークンを不可逆に捨てるため、「後から必要になる遠距離情報」を回復できない。

InfLLMは、局所 dependencyは小さい常駐ウィンドウ、long-distance dependencyは検索可能メモリへ分離し、LLM自体のパラメータや位置 エンコーダを再学習せず両方へアクセスできるようにする。

## 手法
### 1. contextの三分割
現在処理するトークン群を `X`、過去KVを `P` とする。過去を、先頭 `l_I` トークンのinitial トークン `I`、局所窓内のlatest `l_L` トークン `L`、その間にある追い出し済み トークン `E` へ分ける。

各段階の実注意 文脈は
`C = Concat(I, f(X,E), L)`
で、`f` はメモリ 検索。selected メモリを空集合にすればLM-Infinite/StreamingLLM型の固定sliding ウィンドウへ退化するため、InfLLMの追加価値は `f` により遠距離KVを再導入できることにある。

### 2. block-level memory unit
トークン単位で全追い出し済み KVを索引すると単位数とrandom メモリ accessが大きすぎるため、連続 `l_bs` トークンを1 メモリ 単位としてまとめる。各単位全体の意味 relevanceを表すため、追加エンコーダではなく単位内トークンから少数 `r_k` 個の代表トークンを選ぶ。

トークン `m` の代表スコアは、その後の局所 ウィンドウ クエリからキー `k_m` がどれだけ注意されるかの平均
`r_m = (1/l_L) Σ_j q_{m+j}·k_m`
で求める。局所 文脈内で周囲へ影響したトークンほど、そのブロックの意味代表になりやすい。各単位で上位 `r_k` トークンだけを検索用索引として保持する。

### 3. query-to-memory lookup
現在トークン群 `X` のクエリと各単位の代表キーとのdot productを合計し、単位 relevance
`sim(X,B)=Σ_i Σ_j q_i·k_{b_j}^B`
を計算する。上位 `k_m` 単位だけをその段階の注意へロードする。

最終注意自体は選んだ単位内の**全KV トークン**を使うため、代表トークンは検索 索引であって要約ベクトルへ情報を不可逆圧縮するものではない。検索が正しければ原文KVをそのまま再利用できる。

### 4. positional encoding
メモリから返るブロックは原文中では遠く離れ、かつ不連続である。絶対距離をそのままRoPEへ入れると学習 range外へ出るため、局所 ウィンドウより古いメモリ トークンには現在トークンからの相対distanceを `l_L` に固定した位置を割り当てる。これによりモデルが見慣れた位置範囲に遠距離メモリを「折り畳んで」提示する。

この処理は原文の真の距離情報を保存しない代わり、学習不要 extrapolationの位置OODを避ける。厳密な遠距離order/absolute 位置が必要なタスクでは制約になり得る。

### 5. CPU offloadとGPU cache
全メモリ 単位をGPUへ置けばsequence長とともにVRAMが増えるため、大半をCPU メモリへoffloadする。GPUには代表トークン 索引、現在必要な単位、最近頻繁に使った単位だけを置く。

キャッシュ replacementはLRU型frequency スコアを使い、注意で最近強く使われた単位を残す。miss時のみCPU→GPU transferする。論文条件では100K トークンを約26GB VRAMで処理でき、キャッシュ miss rateも低いとしている。さらに長い場合は代表トークン 索引自体もCPUへ置き、k-nearest-neighbor 索引へ拡張できる。

## 評価条件
基礎 モデルはMistral-7B-Instruct-v0.2（標準 32K）とLlama-3-8B-Instruct（標準 8K）。主要ベンチマークは∞-Benchで平均長145.1K、95 percentile 214K。QA、summarization、検索、choice、mathを含む。LongBenchも補助評価する。

実装はencoding chunk 512、メモリ 単位 大きさ 128、representative トークン/単位=4、局所 ウィンドウ 4K。Mistralでは段階当たり96 メモリ 単位、Llama-3では32 単位を取得し、initial トークンは128。全baselineでFlashAttentionを用いる。

比較はoriginal モデル、NTK-aware RoPE、SelfExtend、LM-Infinite、StreamingLLM、H2O。さらに長文脈 continual-学習 モデルや外部検索器を使うRAGとも比較する。

## 主要結果
### ∞-Bench
Mistral-basedではoriginal 32Kの平均25.2、NTK 44.3、SelfExtend 44.8、LM-Infinite 21.6、StreamingLLM 21.5、H2O 18.7に対し、InfLLMは実注意 ウィンドウ 16K相当で平均57.7。検索 タスク R.パスキー/R.Number/R.KVは100.0/96.1/96.8で、固定ウィンドウが0〜29程度へ崩れる遠距離検索を大きく回復する。

Llama-3-basedではoriginal平均18.4、NTK 1.3、SelfExtend 38.0、Infinite 16.0、ストリーミング 16.3、H2O 2.1に対しInfLLMは45.0。R.パスキー/R.Numberは100.0/99.0だがR.KVは5.0に留まり、すべての検索形式が同様に解けるわけではない。長文脈メモリがあっても基礎 モデル能力と検索 representationに依存する負の例である。

### LongBench
MistralではInfLLM 12K-ウィンドウ構成がNarrativeQA 23.03、Qasper 29.52、MultiFieldQA 47.62、HotpotQA 39.53、2WikiMQA 23.61、Musique 18.92。標準 32K Mistralの22.06/29.16/47.65/37.53/21.96/19.03と概ね同等以上で、実注意 ウィンドウを小さくしても検索済み メモリで補える。

Llama-3ではInfLLM 8KがNarrativeQA 22.64、Qasper 43.70、MultiFieldQA 49.03、HotpotQA 49.04、2WikiMQA 35.61、Musique 26.06。標準 Llama-3は19.85/42.36/41.03/47.38/39.20/22.96で、2WikiMQAだけ低下する一方、他タスクは改善する。

### 1,024K scaling
Mistral + Retrieve.パスキーで32K、64K、128K、256K、512K、768K、1,024Kを各50例生成して評価する。InfLLMは1,024Kまで100% 精度を維持し、LM-Infiniteはpass キーが局所 ウィンドウから外れると急落する。ここで1,024Kは汎用QA品質の保証ではなく、5桁pass キーをnoise中から検索するstress testである。

### memory設定の感度
representative トークン数は1→2→4で改善するが8では僅かに悪化し、無関係トークンをrepresentativeへ混ぜる副作用が出る。selected 単位は1→32付近まで増やすと品質が大きく上がるが、注意 計算とメモリ schedulingも増える。

単位 大きさも32/64/128/256でタスクごとに最適が異なる。Retrieve.KVではキー-value pair、Math.Findでは個々のnumberが意味 単位になり、固定ブロック segmentationが常に最適ではないことを著者ら自身が限界として挙げる。

## 既存研究との差
StreamingLLM/LM-Infiniteはinitial sink + 局所 ウィンドウで長streamを処理できるが、窓外情報を捨てる。InfLLMはその追い出し済み KVを検索可能メモリへ残す。RAGはraw documentを外部エンコーダ/索引で検索してpromptへ再投入するが、InfLLMはLLM内部のKV表現とクエリをそのまま検索 signalとして使い、追加検索器 学習を要しない。

continual 長文脈 pretrainingとも異なり、既存checkpointの重みを変えないため導入費用が小さく、元能力を再学習で変化させない。

## 限界
性能はメモリ 検索 recallに依存し、coarse ブロック 単位が必要情報を選べなければその段階の注意へ戻せない。selected 単位を増やせば品質は上がるが計算/メモリ transferが増えるため、fixed コストではない。

メモリ 単位 大きさの最適値はタスク依存で、固定128-トークン ブロックが意味 boundaryを跨ぐ場合がある。位置を局所-ウィンドウ distanceへ折り畳むため、実distanceそのものを必要とするreasoningには情報損失がある。

全追い出し済み 文脈をCPU等へ保持するので総メモリはsequence 長さとともに増える。GPU VRAMは抑えられてもCPU capacity、PCIe transfer、検索 索引 コストは残る。論文自身もvLLM/llama.cpp等とのさらなるシステム統合を将来 workとしており、1,024Kのheadlineはパスキー 検索であって、百万トークンの任意生成タスクを同品質で処理した証明ではない。
