# InfLLM: Training-Free Long-Context Extrapolation for LLMs with an Efficient Context Memory

## 概要
InfLLMは、数千〜数万tokenのcontextで学習された既存LLMを追加学習せず極長系列へ拡張する文脈memory方式である。直近の局所窓（local window）と先頭tokenは常時attention対象に残し、窓から追い出された過去KVをblock単位の文脈memory（context memory）へ保存する。各forwardでは現在queryと関連するmemory unitだけを検索し、局所KVと結合してattentionへ戻す。

重要なのは「古いKVを捨てる」のではなく「通常のGPU attention pathから退避し、必要時に再ロードする」点である。memory unitは追加encoderを学習せず、元LLMのkey/queryを使って代表tokenを選び検索scoreを計算する。ほとんど使われないunitはCPU memoryへoffloadし、GPU側はLRU cacheを持つ。Mistral-7B-Instruct-v0.2とLlama-3-8B-Instructで∞-Bench/LongBenchを評価し、MistralではRetrieve.PassKeyを最大1,024K tokenまで伸ばして50例すべて100% retrieval accuracyを報告する。

## 問題設定
長文脈推論には二つの失敗要因がある。第一に、full attentionはsequence length `L` に対しattention costとKV memoryが増え、極長streamを常時GPUへ置けない。第二に、modelがtraining時に見ていない巨大positionへそのまま外挿すると、位置埋め込みのout-of-domainと大量irrelevant contextによるdistractionで品質が崩れる。

sliding-window attentionはcomputeを一定にできるが、窓外の根拠を完全に失う。NTK/RoPE scaling等はposition rangeを広げても、全historyを読むcomputeとdistractionは残る。KV evictionは古いtokenを不可逆に捨てるため、「後から必要になる遠距離情報」を回復できない。

InfLLMは、local dependencyは小さい常駐window、long-distance dependencyは検索可能memoryへ分離し、LLM自体のparameterやposition encoderを再学習せず両方へアクセスできるようにする。

## 手法
### 1. contextの三分割
現在処理するtoken群を `X`、過去KVを `P` とする。過去を、先頭 `l_I` tokenのinitial tokens `I`、局所窓内のlatest `l_L` token `L`、その間にあるevicted tokens `E` へ分ける。

各stepの実attention contextは
`C = Concat(I, f(X,E), L)`
で、`f` はmemory lookup。selected memoryを空集合にすればLM-Infinite/StreamingLLM型の固定sliding windowへ退化するため、InfLLMの追加価値は `f` により遠距離KVを再導入できることにある。

### 2. block-level memory unit
token単位で全evicted KVをindexするとunit数とrandom memory accessが大きすぎるため、連続 `l_bs` tokenを1 memory unitとしてまとめる。各unit全体のsemantic relevanceを表すため、追加encoderではなくunit内tokenから少数 `r_k` 個の代表tokenを選ぶ。

token `m` の代表scoreは、その後のlocal window queryからkey `k_m` がどれだけattentionされるかの平均
`r_m = (1/l_L) Σ_j q_{m+j}·k_m`
で求める。local context内で周囲へ影響したtokenほど、そのblockのsemantic代表になりやすい。各unitで上位 `r_k` tokenだけをlookup用indexとして保持する。

### 3. query-to-memory lookup
現在token群 `X` のqueryと各unitの代表keyとのdot productを合計し、unit relevance
`sim(X,B)=Σ_i Σ_j q_i·k_{b_j}^B`
を計算する。上位 `k_m` unitだけをそのstepのattentionへロードする。

最終attention自体は選んだunit内の**全KV token**を使うため、代表tokenはretrieval indexであって要約vectorへ情報を不可逆圧縮するものではない。lookupが正しければ原文KVをそのまま再利用できる。

### 4. positional encoding
memoryから返るblockは原文中では遠く離れ、かつ不連続である。絶対距離をそのままRoPEへ入れるとtraining range外へ出るため、local windowより古いmemory tokenには現在tokenからの相対distanceを `l_L` に固定したpositionを割り当てる。これによりmodelが見慣れた位置範囲に遠距離memoryを「折り畳んで」提示する。

この処理は原文の真の距離情報を保存しない代わり、training-free extrapolationの位置OODを避ける。厳密な遠距離order/absolute positionが必要なtaskでは制約になり得る。

### 5. CPU offloadとGPU cache
全memory unitをGPUへ置けばsequence長とともにVRAMが増えるため、大半をCPU memoryへoffloadする。GPUには代表token index、現在必要なunit、最近頻繁に使ったunitだけを置く。

cache replacementはLRU型frequency scoreを使い、attentionで最近強く使われたunitを残す。miss時のみCPU→GPU transferする。論文条件では100K tokenを約26GB VRAMで処理でき、cache miss rateも低いとしている。さらに長い場合は代表token index自体もCPUへ置き、k-nearest-neighbor indexへ拡張できる。

## 評価条件
base modelはMistral-7B-Instruct-v0.2（native 32K）とLlama-3-8B-Instruct（native 8K）。主要benchmarkは∞-Benchで平均長145.1K、95 percentile 214K。QA、summarization、retrieval、choice、mathを含む。LongBenchも補助評価する。

実装はencoding chunk 512、memory unit size 128、representative tokens/unit=4、local window 4K。Mistralではstep当たり96 memory units、Llama-3では32 unitsを取得し、initial tokensは128。全baselineでFlashAttentionを用いる。

比較はoriginal model、NTK-aware RoPE、SelfExtend、LM-Infinite、StreamingLLM、H2O。さらにlong-context continual-training modelや外部retrieverを使うRAGとも比較する。

## 主要結果
### ∞-Bench
Mistral-basedではoriginal 32Kの平均25.2、NTK 44.3、SelfExtend 44.8、LM-Infinite 21.6、StreamingLLM 21.5、H2O 18.7に対し、InfLLMは実attention window 16K相当で平均57.7。retrieval task R.PassKey/R.Number/R.KVは100.0/96.1/96.8で、固定windowが0〜29程度へ崩れる遠距離retrievalを大きく回復する。

Llama-3-basedではoriginal平均18.4、NTK 1.3、SelfExtend 38.0、Infinite 16.0、Streaming 16.3、H2O 2.1に対しInfLLMは45.0。R.PassKey/R.Numberは100.0/99.0だがR.KVは5.0に留まり、すべてのretrieval形式が同様に解けるわけではない。長文脈memoryがあってもbase model能力とlookup representationに依存する負の例である。

### LongBench
MistralではInfLLM 12K-window構成がNarrativeQA 23.03、Qasper 29.52、MultiFieldQA 47.62、HotpotQA 39.53、2WikiMQA 23.61、Musique 18.92。native 32K Mistralの22.06/29.16/47.65/37.53/21.96/19.03と概ね同等以上で、実attention windowを小さくしてもretrieved memoryで補える。

Llama-3ではInfLLM 8KがNarrativeQA 22.64、Qasper 43.70、MultiFieldQA 49.03、HotpotQA 49.04、2WikiMQA 35.61、Musique 26.06。native Llama-3は19.85/42.36/41.03/47.38/39.20/22.96で、2WikiMQAだけ低下する一方、他taskは改善する。

### 1,024K scaling
Mistral + Retrieve.PassKeyで32K、64K、128K、256K、512K、768K、1,024Kを各50例生成して評価する。InfLLMは1,024Kまで100% accuracyを維持し、LM-Infiniteはpass keyがlocal windowから外れると急落する。ここで1,024Kは汎用QA品質の保証ではなく、5桁pass keyをnoise中からretrievalするstress testである。

### memory設定の感度
representative token数は1→2→4で改善するが8では僅かに悪化し、無関係tokenをrepresentativeへ混ぜる副作用が出る。selected unitsは1→32付近まで増やすとqualityが大きく上がるが、attention computeとmemory schedulingも増える。

unit sizeも32/64/128/256でtaskごとに最適が異なる。Retrieve.KVではkey-value pair、Math.Findでは個々のnumberがsemantic unitになり、固定block segmentationが常に最適ではないことを著者ら自身が限界として挙げる。

## 既存研究との差
StreamingLLM/LM-Infiniteはinitial sink + local windowで長streamを処理できるが、窓外情報を捨てる。InfLLMはそのevicted KVを検索可能memoryへ残す。RAGはraw documentを外部encoder/indexで検索してpromptへ再投入するが、InfLLMはLLM内部のKV表現とqueryをそのままretrieval signalとして使い、追加retriever trainingを要しない。

continual long-context pretrainingとも異なり、既存checkpointのweightを変えないため導入費用が小さく、元能力を再学習で変化させない。

## 限界
性能はmemory lookup recallに依存し、coarse block unitが必要情報を選べなければそのstepのattentionへ戻せない。selected unitsを増やせば品質は上がるがcompute/memory transferが増えるため、fixed costではない。

memory unit sizeの最適値はtask依存で、固定128-token blockがsemantic boundaryを跨ぐ場合がある。positionをlocal-window distanceへ折り畳むため、実distanceそのものを必要とするreasoningには情報損失がある。

全evicted contextをCPU等へ保持するので総memoryはsequence lengthとともに増える。GPU VRAMは抑えられてもCPU capacity、PCIe transfer、lookup index costは残る。論文自身もvLLM/llama.cpp等とのさらなるsystem統合をfuture workとしており、1,024KのheadlineはPassKey retrievalであって、百万tokenの任意生成taskを同品質で処理した証明ではない。
