# LLM Bandit：品質と費用の選好を切り替えるモデルルーティング

## 概要

大規模言語モデル（Large Language Model; LLM）の提供では、すべての質問を最も高価なモデルへ送れば品質は高くなりやすいが、処理費用が増える。安価なモデルだけを使えば費用を抑えられるが、難しい質問で誤答が増える。複数モデルを順番に呼び出すカスケード方式は品質を確認してから高価なモデルへ移れる一方、複数回の推論が必要になる。モデルルーティングは、質問の内容と利用可能なモデルの能力を推定し、最初から1つのモデルを選ぶことで、この交換条件を制御する。

LLM Banditはモデル選択を多目的の文脈付きバンディット（contextual bandit）として定式化し、品質と費用の重みを推論時に指定できる確率的な方策を学習する。モデル集合が変わるたびにルータ全体を再学習しないため、各モデルの能力を表す「モデル識別ベクトル」を別途学習し、新モデルは少数の評価設問からそのベクトルだけを推定する。方策は質問埋め込み、候補モデルの識別ベクトル、予測品質、費用、利用者の選好を受け取り、候補モデルごとの選択確率を出力する。

著者は5つの公開評価系で、固定したモデル集合・選好ごとに学習したPPO方策や、RouteLLM、単純な品質予測器と比較する。GPT-4とMixtral-8x7Bを選ぶ条件では、AlpacaEval 2.0で品質約46.35%を保ちながら比較方式の費用35から31へ、HELM-MMLUで正答率80%を保ちながら費用33から24へ削減したと報告する。これらは論文の費用正規化とベンチマーク条件に依存し、現行APIの実際の請求額を示すものではない。

## 問題設定

### 単一の最適モデルは存在しない

質問集合をX、利用可能なモデルをM1〜MKとし、質問xに対するモデルkの品質をs(x,k)、モデル呼出費用をc_kとする。ルーティング方策πは質問からモデル選択の確率分布を返す。品質を最大化したい利用者と費用を最小化したい利用者では望ましい選択が異なるため、著者は報酬を`[s(x,k), −c_k]`という二成分で扱う。選好重み`ω=[ω1,ω2]`を与えたときの単一報酬は`r_ω(x,k)=ω1 s(x,k)−ω2 c_k`である。

この定式化の目的は、品質と費用のパレート境界（Pareto frontier）に沿って、利用者が必要な交換条件を切り替えられるようにすることである。通常の「品質の推定値が最も高いモデルへ送る」ルータでは費用の選好を柔軟に変えられない。品質を費用で割った比率だけを最大化する方式でも、品質に下限を設けたい利用者や高品質を優先する利用者を同じ方策で扱いにくい。

ただし論文の費用c_kは基本的にモデルごとに固定された値である。実際のAPI料金は入力・出力トークン数、キャッシュ命中、利用地域、混雑、サービス契約などで変わる。固定費用で学んだ方策を、可変の実料金へそのまま適用した場合の最適性は本論文では証明されない。

### 新しいモデルを追加するたびにルータを作り直す問題

従来の二モデル専用ルータは、候補がGPT-4とMixtralという固定の組合せなら有効でも、第三のモデルを加えると方策の出力次元や学習済みの判断境界が合わなくなることがある。新モデルを全面的なベンチマークで評価するにも多くの呼出費用がかかる。LLM Banditはモデルの能力を連続ベクトルとして表し、方策が「候補モデルの集合」を入力として処理することで、候補数と順番が変わっても同じルータを利用することを狙う。

## 手法

### 1. モデル識別ベクトル：IRTによる能力推定

各モデルMkに対しd次元の識別ベクトルIkを割り当てる。質問xの埋め込みe(x)とIkを入力する予測ネットワークfが、モデルkがその質問に成功する確率`p_k(x)=sigmoid(f(e(x),Ik))`を推定する。これは項目反応理論（Item Response Theory; IRT）をニューラルネットワークへ拡張した設計であり、モデルを一つの総合点で並べるのではなく、質問の特徴によって得意不得意が変わることを表現する。

学習にはモデルごとの評価得点を利用し、二値化した成功ラベルに対して二値交差エントロピーを最小化する。得点が連続値の場合の閾値処理は付録で説明される。さらにChatbot Arenaなどの二モデル比較データを使い、モデルAとBのどちらが勝つかを予測する補助ネットワークgを学習する。比較データは絶対得点を持たないため、直接品質予測へ同じ意味で混ぜるのではなく、対比較損失を別に設ける。

新しいモデルへの一般化を促すため、識別ベクトルを変分推論（variational inference）による潜在変数とし、ガウス事前分布から大きく離れすぎないようKLダイバージェンスで正則化する。これにより、少数の評価結果だけで新モデルを特徴づける際の過度な当てはまりを抑える。ただしベクトルの意味は学習に使った評価課題へ依存し、未知の専門領域での性能まで自動的に保証するものではない。

### 2. 候補モデル集合と選好を入力する確率的方策

方策は質問x、候補集合`C_K={(Ik,c_k,p̂_k)}`、選好ωを入力とする。p̂_kはIRT型予測器が出す質問ごとの成功確率である。候補集合を順序に依存しないネットワークhで処理し、各モデルIkとの内積から選択確率を計算する。論文の式(5)は概念的に`πθ(k|x,C_K,ω)∝exp(Ikᵀ h(x,C_K,ω))`と書ける。候補を並べ替えても結果が変わらず、モデル数が変わっても識別ベクトルを追加すれば出力候補へ加えられる。

品質予測器の最大値を単純に選ぶ方法では、予測誤差が大きい質問や未知のモデルに弱い。著者は予測品質だけでなく候補集合の全体像と費用を与え、確率的な方策を学習する。これによりモデルの探索と活用を含む選択を行う。ただし評価時の主な設定は既に得点が与えられたオフラインのベンチマークであり、実サービスで逐次探索してモデル能力を更新するオンラインバンディットの実証ではない。

### 3. PPOによる多目的方策学習と分解価値関数

方策の学習には近接方策最適化（Proximal Policy Optimization; PPO）を採用する。選好ωでスカラー化した報酬を最大化するが、価値関数は品質と費用を別々に推定する二成分ベクトルとする。選好が変わるたびに価値関数を最初から学び直さず、品質と費用の期待値を共有できるのが狙いである。一般化優位推定（Generalized Advantage Estimation; GAE）を使って方策更新を安定化する。

学習時には選好ωを範囲内でランダムにサンプルし、品質重視から費用重視までの複数の交換条件を一つの方策へ覚えさせる。固定のωごとに別PPO方策を作る比較方式と異なり、学習後は入力のωを変えるだけで判断を切り替えられる。もっとも、学習時に見なかった極端な選好や、品質・費用以外の第三の目的を突然追加した場合の保証はない。

### 4. モデル集合と質問分布への一般化

学習では候補モデルの組合せを動的にサンプルし、モデル集合ごとの最大品質・最大費用で値を正規化する。これにより、異なる価格帯のモデル集合を学習しても、選好重みの意味が大きく変わらないようにする。Chatbot Arena、Nectar、RouteLLMの合成比較データによる教師あり事前学習を行い、IRT予測得点をPlatt scalingで較正してから、強化学習へ進む。

質問の未知分布へ一般化するため、質問埋め込みを近傍の質問埋め込みと混ぜるオンマニフォールドmixupを用いる。無関係な質問同士を単純に混ぜるのではなく、埋め込み空間で近いものを選び、判断境界を滑らかにする。著者の構成要素除去では、候補文脈、事前学習、mixupのいずれを外しても性能が低下する。個々の寄与の大きさはモデル集合・ベンチマークによって異なるため、単一の改善率として合算しない。

### 5. 少数設問による新モデルのコールドスタート

新しいモデルが利用可能になったとき、既存のIRT予測器とルーティング方策は固定し、新モデルの識別ベクトルだけを推定する。評価設問の選択には、既存モデルに対する予測誤差から計算した識別力スコアψを使う。ψが高い設問はモデルの能力差を見分ける情報を含みやすいが、極端な難問だけに偏らないよう、スコアの異なる層から設問を抽出する。

新モデルに10、20、50問を実行し、その得点から新しい識別ベクトルを最適化する。論文の図3では、Cohere系とQwen2.5系の未見モデルについて、50問だけで得た識別ベクトルを使うルーティングが、全評価設問を使う場合に近い性能を示す。20問でも一定の性能は得られるが、**20問で全条件の品質が一致する**と証明したわけではない。新モデルの性能が学習済みモデル群から大きく外れる場合、IRTの事前分布と選択設問が適切か再確認が必要である。

## 評価

### ベンチマーク・比較方式・費用定義

論文の第4節ではHELM-Lite、HELM-MMLU、OpenLLM Leaderboard、OpenLLM Leaderboard v2、AlpacaEval 2.0の5系統を使う。各評価系の質問を学習用と試験用に分け、モデルの品質推定器は複数の評価系の学習分割と対比較データで学習する。比較対象は、ランダム選択、RouteLLM、品質予測だけで効用を最大化するPredictor、モデル集合と選好ごとに別々に学習したPPO、実際の評価得点を見て最良モデルを選ぶOracleである。Oracleは上限の診断基準であり、運用時に利用できるルータではない。

二モデルの比較ではGPT-4/Mixtral-8x7Bを用い、他にGPT、Mistral、Claude、Yi1.5、LLaMA3、Qwen2などのモデル系列から候補集合を構成する。RouteLLMは二モデル用なので、三モデル以上の設定にはそのまま適用せず、別の比較方式を使う。費用はモデルごとに入力100万トークンと出力100万トークンを処理する場合を基準として近似する。論文中の費用の「31」「35」はこの設定での相対的な比較値であり、現行の個別API価格表や任意の入力長でのドル請求額ではない。

### 品質と費用の交換条件

| 評価条件 | 比較方式 | 提案方式 | 主要な結果 |
|---|---:|---:|---|
| AlpacaEval 2.0、GPT-4/Mixtral-8x7B | RouteLLM：費用35 | LLM Bandit：費用31 | 品質約46.35%付近で費用約11%減 |
| HELM-MMLU、同系の二モデル比較 | RouteLLM：費用33 | LLM Bandit：費用24 | 正答率約80%を保ち費用約27%減 |
| 未見Cohere/Qwen2.5系モデル | 全評価設問で識別ベクトルを推定 | 10/20/50設問で推定 | 50設問では全評価に近いルーティング品質 |
| ルーティング判断時間 | LLM本体の推論時間は通常100ms〜1s程度という著者の比較 | 約5ms/要求 | モデル推論の時間は含まない |
| ルータGPUメモリ | モデル本体の重みは別 | 100MB未満 | ルータの識別ベクトルと方策の合計 |

図2では提案方式が単純な品質予測器より良い品質費用曲線を示す条件が多く、固定選好ごとのPPOと同程度またはそれ以上の性能を報告する。特に複数の候補モデル集合を一つの方策で扱えることが実装上の利点である。しかし全設定でOracleへ到達するわけではなく、品質予測の誤差や方策の学習不足が残る。報告された「最大27%削減」は特定の比較点であり、すべての質問、すべてのモデル集合で27%安くなるという意味ではない。

### 新モデル追加と構成要素除去

未見モデルの実験では、識別ベクトルを推定する設問数を10、20、50へ変える。新モデルはIRTとルーティング方策の学習には使わず、追加時に得た少数の評価結果だけから識別ベクトルを作る。提案方式はこのベクトルを既存の方策へ差し込むだけで動作し、未見モデル用に新たに学習したPPO方式と近い品質費用曲線を示した。著者は全面的な評価に比べて90%以上の追加評価負担を削減できる可能性を主張するが、選んだ設問の難度分布、モデル系列、評価項目の代表性に依存する。

図4の構成要素除去では、予測品質・費用を含む候補文脈を省く、対比較データでの事前学習を省く、近傍mixupを省く、といった条件で品質費用曲線が悪化する。これは各要素が有効であることを支持するが、複数の要素の相互作用を完全に分離した実験ではない。選好を連続的に変えられる利点は、単一の固定選好に最適化した方策との比較だけでなく、学習したことのないモデル集合へ同じ方策を適用する条件で評価すべきである。

### 推論基盤としての性能解釈

ルーティング判断の約5msと100MB未満は、ルータ自身の推論費用である。選ばれたLLM本体の実行、ネットワーク転送、API呼出し、待ち行列、モデルの起動時間は含まれない。論文の評価は主として既に収集された品質得点を用いるオフライン評価であり、GPUクラスタ全体のスループット、初回トークン遅延、同時要求下の公平性、モデル切替によるKVキャッシュ喪失は直接測っていない。従って「5msで最適なモデルへ切り替えられる」ことと「実サービスの応答時間が5msしか増えない」ことは別である。

## 限界・負の結果

第一に、費用はモデルごとの固定値として扱う。実際には入力・出力トークン数、プロンプトキャッシュ、料金改定、GPU混雑、ローカル推論のバッチ処理効率で費用が変わる。質問が長い場合と短い場合で同じモデルの価格差が大きくても、固定費用の報酬では十分に表現できない。著者自身も入力長を考慮した動的費用モデルを今後の課題として挙げる。

第二に、オフラインの評価得点を使うため、実運用の逐次フィードバックから方策を更新するオンライン学習の有効性は未実証である。回答品質を正解ラベルで測りにくい開放型対話では、評価器の誤差や利用者選好の変化がルータの判断へ影響する。報酬の正規化がモデル集合ごとに行われるため、集合を変えた際に同じωが完全に同じ実質的な品質・費用基準を意味する保証もない。

第三に、学習と試験の分割は本文で説明されるが、対比較データ、各評価ベンチマーク、IRTの事前学習、コールドスタート用の少数設問の間で、意味的に近い質問や重複した問題がどの程度除かれたかを本稿では独立に検証していない。未見モデルの実験でも、同じモデル系列や類似問題が学習データに含まれる可能性を完全に排除した再現実験ではない。少数設問からの一般化を実運用へ外挿するには、問題集合とモデル系列の厳密な分離が必要である。

第四に、論文は品質と費用の二目的に限定する。遅延、可用性、地域規制、データ機密性、入力長制限、画像・音声対応、ツール呼出しの互換性などは明示的な制約として統合されていない。モデル選択が正答率と費用で良好でも、要求がモデルの文脈長上限を超える、サービス水準目標に間に合わない、外部APIへ送信できないデータを含む、といった運用条件ではそのまま使えない。

第五に、確率的な方策は同じ質問に対して異なるモデルを選ぶ可能性がある。安全性や品質を確実に満たす必要があるサービスでは、選択前の能力制約、品質下限、監査記録、フォールバックが必要となる。論文の最大27%の費用削減はOracleとの隔たりが残る条件での結果であり、品質予測の不確実性を完全に解決したことを意味しない。

第六に、論文の公開版で検証可能な実装リポジトリのURLを確認できなかった。本文の方策式、IRT、PPO、設問選択は再実装の方向性を与えるが、モデル識別ベクトルの学習済み重み、評価データの正確な分割、推論環境を揃えた再現性は別途検証する必要がある。

## 既存方式との違いと適用判断

RouteLLMのような二モデルルータは固定した強いモデルと安いモデルの間を切り替える。FrugalGPT型のカスケードは安価なモデルの回答を見てから必要なら高価なモデルを追加で呼ぶ。LLM Banditは一回のモデル選択を基本とし、候補集合と利用者選好が変わっても同じ方策を使えるよう、モデル能力を識別ベクトルで抽象化する点に特徴がある。MetaLLMもバンディット型のモデル選択を扱うが、論文は固定したモデル集合とスカラー報酬への依存を主要な相違点として説明する。

実運用へ採用する場合は、モデルの機能制約を先に満たす候補だけに絞り、質問長に応じた費用を推定し、応答品質の下限を設定した上で、選好付きルーティングを適用する方が安全である。さらにモデル切替のキャッシュ損失やネットワーク費用を測定し、5msというルータ単体の数字と、サービス全体の応答時間を別々に監視する必要がある。新モデルの少数設問評価は有用だが、特殊領域や長文推論を担わせる前に、対象業務の検証セットで改めて品質を確かめるべきである。
