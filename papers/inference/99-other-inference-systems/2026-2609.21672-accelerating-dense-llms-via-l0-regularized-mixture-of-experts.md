# Accelerating Dense LLMs via L0-regularized Mixture-of-Experts

## 概要
L0-MoEは、既存の密（dense）LLMを一からMoEとして再学習するのではなく、dense checkpointのフィードフォワードネットワーク（FFN）内部にある中間次元を、L0正則化（L0 regularization）でdomain別に選択して複数の専門家（expert）を作り、その後にrouterを学習する軽量なMoE変換法である。ここでL0正則化が直接「tokenごとの活性expert数」を罰するわけではない。L0は各domainに重要なFFN hidden dimensionsを抽出してexpertを**構築する段階**で使われ、推論時のexpert選択は通常の線形routerが担う。

学習dataも無作為に30B tokens取るのではなく、クラスタ混同行列（Cluster Confusion Matrix; CCM）でRedPajama内のsemantic domainを分け、dense modelに近い領域から遠い領域へtraining curriculumを組む。さらにdomainごとのbatchを段階的に混合する動的batching（dynamic batching）で、初期はsequence-level routingを学び、後半はtoken-level routingへ移行させる。Llama3-8B、Mistral-7B、Qwen2-7Bでdense baselineとほぼ同じ4 benchmark性能を維持しつつ2.0〜2.5倍のSGlang推論高速化を報告する。

## 問題設定
dense LLMを高速化する量子化・pruning・knowledge distillationは実用的だが、圧縮率を上げると能力低下が生じやすい。一方、通常のMoEは「総parameterを大幅に増やしながらtokenあたりの活性parameterを抑える」scaling手法として設計され、scratch trainingやdense-to-MoE upcyclingに数兆token規模のcorpusと大きな計算資源を必要とする。

本論文の問いは、既存dense checkpointが既に獲得した知識を利用し、数十B token規模の追加学習だけで「元のdense modelに近い性能だが、各tokenではFFNの一部しか計算しないmodel」へ変換できるか、である。そのためには、(1) 各expertに何を持たせるか、(2) 少量dataでexpert specializationをどう作るか、(3) routerをsequence-levelからtoken-levelへ安定に学習させるか、の三点を解く必要がある。

## 手法
### 1. CCMによるdomain-aware corpus構築
RedPajama pretraining corpusから小さなsubsetを非復元抽出し、BGE-M3 encoderで各sampleのsemantic vectorを得る。これをK-meansでK clusterへ分け、各clusterからm sampleを取り、domain semantic learning用の `D_s={D_s1,...,D_sK}` を構成する。このsamplingとclusteringをQ iteration繰り返し、複数のcluster centerとdomain datasetを得る。

CCMはcluster間のsemantic similarityを、cluster内similarityとcluster間similarityの関係から測り、「dense modelにとって互いに近いdomain／混同しやすいdomain」から「離れたdomain」への順序を作る。単純なK-means groupingだけでなく、このdomain distanceを後段のexpert constructionとbatch schedulingに使うことが目的である。主実験では21 iterationで合計30B tokensを収集する。

### 2. L0正則化によるexpert construction
dense Transformerの各FFNでは、up-projectionの中間次元を選択するbinary mask `Z` を導入する。元weight `W∈R^{m×n}` から、maskで `n'<n` 個のcolumnだけを残した縮小weightを作る。binary selectionは微分不能なので、hard-concrete relaxationを用いてgate `z` を連続的に学習し、L0 penaltyで不要dimensionを0へ押し込む。

保持率 `r` を直接制御するため、推定保持率 `r_hat` と目標 `r` の差にLagrange multiplierを掛けた正則化項を使う。training中は保持率targetを100%から最終値へ徐々に下げ、急激なdimension削除による崩壊を避ける。論文ではself-attention等を固定し、主にMLP/FFN部分をdomain subsetごとに最適化する。

各domain subset `D_sk` に対してこのL0 selectionを行うと、元dense FFNの中からそのdomainに重要なhidden dimensionsだけを持つexpertが得られる。つまりexpertはdense modelのFFN parameterの「domain別部分集合」であり、L0がtoken routingを直接疎化しているわけではない。

### 3. MoE化とrouter
K個のdomain expertを揃えた後、TransformerのFFNをMoE層として組み直し、hidden state `h∈R^d` に対して線形projection `W_router∈R^{d×N}` を適用するrouterを学習する。routerには通常の負荷分散損失（load-balancing loss）とrouter Z-lossを加え、特定expertへのcollapseを抑える。

expertを増やすほど総parameterは増えるが、1 tokenが通るexpert数を抑えればactive FFN computeはdenseより小さくできる。速度は最終expert width、expert数、router overhead、実行frameworkがsparse expert dispatchを効率よく扱えるかで決まる。

### 4. 動的batching
router trainingでは二つのscheduleを組み合わせる。第一はdomain semantic distance schedulingで、初期はdense modelが既に得意な近いdomainから始め、training進行に伴ってより異なるsemantic spaceへ移る。これにより初期routerが明瞭なsequence-level domain selectionを学びやすくする。

第二はmulti-domain gathering schedulingで、各domainのsampleをcyclicに並べ、学習が進むにつれ1 batchへ複数domainを混ぜる。初期は同一domain sampleがまとまり、routerは「このsequenceはexpert A」のような粗い選択を学ぶ。後半でdomainが混ざるにつれて、一つのsequence内でもtokenごとに異なるexpertを選ぶtoken-level routingへ移る。単なるrandom shuffleより、router specializationを段階的に難しくするcurriculumになっている。

## 評価条件
training corpusはRedPajamaからCCMで集めた30B tokens。対象dense modelはLlama3-8B、Mistral-7B、Qwen2-7B。主評価はMMLU、GSM8K、HumanEval、BigBench Hard（BBH）の4 benchmarkで、dense checkpoint、L0-MoE、GPTQ、LLM-Shearing、knowledge distillation系baseline等を比較する。

trainingはFSDP + ZeRO-3 parameter sharding、CPU offloadなしで実施する。推論速度比較は全modelを同じSGlang frameworkへ載せ、framework差でspeedupが生じないよう揃える。論文は方式自体はvLLM等にも実装可能としているが、報告値はSGlang条件である。

## 主要結果
### dense品質と速度
Llama3-8Bはdense 4-task平均53.5に対しL0-MoE 53.3で、推論は2.0倍。Mistral-7Bはdense 50.4に対しL0-MoE 51.4で2.1倍。Qwen2-7Bはdense 66.0に対し66.1で2.5倍となる。少なくともこの3 familyでは「2〜2.5倍speedupの代わりに明確な平均性能劣化」というtrade-offになっていない。

Qwen2-7BのMMLU/GSM8KではL0-MoEが70.4/80.5。GPTQは67.8/73.8で1.8倍、LLM-Shearingは68.2/75.5で2.6倍、RKD+CoTは61.2/60.2で5.1倍。より大きなspeedupを取るdistillation系は性能低下が大きく、L0-MoEは2.5倍前後で品質を保つ位置を狙っている。

### CCM・batching・expert選択の構成要素除去
Qwen2-7Bでfull L0-MoEはMMLU/GSM8K 70.4/80.5。CCMからK-means clusteringを外すと68.2/78.1、domain順序をrandomにすると68.2/75.5、batchを完全randomにすると66.6/77.1へ下がる。data curationとcurriculumが単なる付随機構ではなく、router/expert specializationへ効いている。

expert constructionもL0 dimension selectionが重要で、RandomMoEは48.1/69.6、magnitude-based selectionは52.6/69.1、OBSは68.4/74.1、SVDは55.2/73.8。特にrandom/magnitudeではMMLUが大きく崩れ、dense FFNのどのdimensionをexpertへ残すかが品質を左右する。

### expert数と速度のtrade-off
expert数を増減するとparameter量と速度が変わる。Qwen2-7BでK=8は総parameter約4.8B、MMLU 50.9、speedup 4.6倍と速いが品質が大きく落ちる。K=32では約12.7B、MMLU 69.2、speedup 3.2倍となり、expert capacityを増やすほどdense能力へ近づく代わりに速度利得が縮む。

CCM iteration数Qも増やすとdomain coverageが改善し、同じ2.5倍条件でMMLUはQ=2の68.2、Q=5の68.8、Q=10の69.7へ上昇する。data samplingを増やせば無限に改善するわけではないが、少数iterationだけではsemantic coverage不足が残ることを示す。

### scale検証
追加のQwen2-1.5B実験では64 expert構成でも約2倍speedupを得て性能劣化を抑えた。逆に70B級はresource制約で検証しておらず、論文の結論は7〜8B級を中心とする。

## 既存研究との差
通常のMoE upcyclingはdense FFNを複製・分割して大量dataで再学習することが多い。L0-MoEは元dense FFNのhidden dimensionsをdomainごとにL0 selectionし、少量corpusでexpert specializationを作る点が異なる。構造化pruningとも違い、削った1個の小型FFNへ固定するのでなく、複数のdomain expertを保持しrouterで入力に応じて使い分ける。

## 限界
最大2.5倍はSGlang上の特定model構成での実測で、L0の保持率から自動的に決まる理論倍率ではない。expert dispatch、router、memory access、batch形状によってsparse計算をhardwareが十分活かせない場合、同じ速度は得られない。

dense checkpointからの変換には30B-token規模の追加trainingとCCM preprocessingが必要で、学習不要のpost-training quantizationやone-shot pruningよりdeployment preparationは重い。expert数を小さくして速度を上げるとK=8のように品質が大きく落ちるため、capacity-speed trade-offも残る。

評価はLlama3-8B、Mistral-7B、Qwen2-7Bが中心で、70B級は未評価。主benchmarkもMMLU/GSM8K/HumanEval/BBHの4つで、long-context、multilingual、instruction following、serving concurrency等は十分検証されていない。論文中ではcurated datasetとcodeを「公開予定」としており、掲載論文自体に確定した公式code URLは示されていない。
