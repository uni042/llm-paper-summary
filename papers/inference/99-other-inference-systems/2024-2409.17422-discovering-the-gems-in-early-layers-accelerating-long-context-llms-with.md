# Discovering the Gems in Early Layers: Accelerating Long-Context LLMs with 1000x Input Token Reduction

## 概要
GemFilterは、長文脈LLMが回答に必要なトークン位置を最終層まで待たず、比較的早い層ですでに強く識別しているという観察を利用する、学習不要の入力圧縮法である。長い入力を全層で処理した後にKVキャッシュを削るのではなく、まず早期層だけで長文脈を走査し、回答に重要と推定した上位 (k) トークンだけを残す。その短い部分列を改めてモデル全体へ入力して通常生成する。

この二段階構成により、後半の層は元の (n) トークンではなく (kll n) トークンだけを処理する。したがってデコード時KVメモリだけでなく、長文脈プリフィルの注意計算そのものを削減できる。論文はLLaMA 3.1 8B Instruct、Mistral Nemo 12B Instruct、Phi-3.5 Mini 3.8B Instructで評価し、Needle in a Haystackでは少数トークンへの圧縮後も必要情報を保持し、LongBenchでは1024トークン選択でも標準注意に近い品質を示す。システム評価ではSnapKVとの比較で最大2.4倍の高速化と約30%のGPUメモリ削減を報告する。

## 問題設定
長さ (n) の長文脈を通常の注意でプリフィルすると、各Transformer層で全入力を処理し、注意スコア計算は系列長に対して二次的に増える。SnapKVやH2OなどのKVキャッシュ削減法は、生成中に保持・参照するKV量を減らせるが、どのKVを残すか判断するために長い入力を全層へ一度通した後で圧縮する。このため長文脈では、生成前のプリフィル時間と一時メモリが依然として大きい。

著者らは複数モデルの注意分布を調べ、質問への回答に必要な「needle」位置が、最終層ではなく中間より前の層で既に高い注意を受けることを観察する。LLaMA 3.1 8Bでは32層中およそ13層目、Mistral NemoやPhi-3.5 Miniでは19層付近が有効なフィルタ層になる。GemFilterはこの早期出現を使い、長文脈を後段へ運ぶ前に入力そのものを短くする。

## 手法

### 1. 早期層までの長文脈走査
入力トークン列 (T=(t_1,ldots,t_n)) を、全 (m) 層ではなく選択したフィルタ層 (r) までだけ通常どおり処理する。フィルタ層では、最後の入力位置に対応するクエリと全キーの注意スコアを取り出す。質問・指示が入力末尾にある長文脈QAを想定し、この最後のクエリが「どの過去位置を参照すべきか」を表す信号として使われる。

複数注意ヘッドから得た最終行のスコアをヘッド方向に集約し、全入力位置を重要度で順位付けする。ここで別の学習済み圧縮器や補助モデルは使わず、本体LLMが途中層で既に計算している注意をそのまま利用する。

### 2. 上位k位置の抽出と順序復元
集約スコアの上位 (k) 個の位置集合 (J) を選ぶ。重要度順のまま連結すると元文書の語順が壊れるため、選択した位置を元の入力順に並べ直し、短縮列 (T_J) を作る。GemFilterは層・ヘッドごとに異なる保持集合を持たず、一つの位置集合を第二走査に使うため、どのトークンが残ったかを直接検査できる。

(k) は速度・メモリと情報保持の主要な交換条件である。1024や4096のように大きくすれば必要情報を残しやすいが、第二走査の計算・KV量は増える。小さくしすぎればフィルタ層で順位を誤った情報を不可逆に捨てる。

### 3. 短縮文脈を全層へ再入力
第一走査で作った長文脈のKVをそのまま後段へ継承するのではない。選択後、短い (T_J) をモデルの第1層から全 (m) 層へもう一度入力し、その結果を使って通常の自己回帰生成を開始する。

この再実行には固定費があるが、(ngg k) なら、全 (m) 層で長さ (n) を処理する費用より、最初の (r) 層だけ長さ (n) を処理し、その後全層で長さ (k) を処理する費用の方が小さい。論文の漸近整理では、長文脈プリフィルの主要注意計算を標準法・SnapKV/H2Oが全 (m) 層で負担するのに対し、GemFilterは長い入力について (r<m) 層だけで済ませる。

生成フェーズでも第二走査後に保持するKVは長さ (k) に対応するため、SnapKV/H2Oと同様に短いキャッシュでデコードできる。したがってGemFilterはプリフィルとデコードの両方に効く。

### 4. フィルタ層の選択
早ければ早いほど計算は減るが、意味的に有用な位置がまだ分離していない層では選択精度が落ちる。逆に遅すぎる層では必要位置を見つけやすくても、長文脈を多くの層へ通してしまい高速化を失う。

論文はNeedle in a Haystackを使い、needleを高精度に抽出できる最初期付近の層をモデルごとに選ぶ。LLaMA 3.1 8Bでは13層目が代表設定で、さらに後ろへ進めても必ず品質が上がるわけではなく、ある地点以降は選択性能が低下する例も示される。このため (r) は「可能な限り浅い固定層」ではなく、モデルごとに少量の校正評価から選ぶ。

## 評価

### 評価条件
主要モデルはLLaMA 3.1 8B Instruct、Mistral Nemo 12B Instruct、Phi-3.5 Mini 3.8B Instructである。長距離の一点再取得をNeedle in a Haystackで、実タスク性能をLongBenchで測る。比較には標準注意、SnapKV、H2Oなどを用い、GemFilterでは主に (k=1024) や4096を評価する。

Needle in a Haystackでは入力長とneedle位置を変えて、圧縮後に質問へ正答できるかを見る。LongBenchではQA、要約、few-shot、合成タスクなど異なる長文脈利用形態を含むため、単一needleだけに特化した選択になっていないかも確認する。

### Needle in a Haystack
LLaMA 3.1 8Bで1024トークンを保持する主設定では、GemFilterの平均スコアは約0.887、同じ保持量のSnapKVは約0.749である。Mistral NemoでもGemFilter約0.838に対してSnapKV約0.494となる。早期層の最終クエリ注意が、後段のKV重要度推定よりも長距離needleを安定して拾える条件があることを示す。

ただしこの結果は「常に1024トークンで十分」という意味ではない。フィルタ層や (k) の選択に感度があり、needleと質問の関係が早期注意へ現れない場合には取りこぼし得る。

### LongBench
LongBenchでは1024トークンまで圧縮しても、標準注意からの平均性能低下は小さく、H2Oを明確に上回り、SnapKVと同等以上の条件が多い。4096トークンまで残す設定では品質余裕が増え、Mistral Nemoで標準注意を上回るタスクもある。

論文が重視するのは、KV削減法と同程度の生成時メモリを保ちながら、GemFilterだけは全層の長文脈プリフィルを避けられる点である。したがって同じ (k) でも「生成KVが小さい」だけではなく、長文脈を処理する層数そのものが少ない。

### 実行時間・GPUメモリ
長文脈システム評価では、Mistral NemoとPhi-3.5 Miniで19層目をフィルタ層に使う条件などにおいて、SnapKV比で最大2.4倍の推論高速化と約30%のGPUメモリ削減を報告する。速度利得は (n/k) が大きいほど増えやすい。反対に入力が短い、(k) が大きい、フィルタ層 (r) が深い場合は、第一走査と第二走査の二回実行を償却しにくくなる。

## 既存研究との差
SnapKVやH2Oは、長文脈を全層へ通した後のKVキャッシュから重要要素を残す。したがって主にデコード時容量・帯域を減らす。一方GemFilterは、途中層で入力位置を一度だけ選び、後段へ渡すトークン列自体を短くするため、プリフィル計算を直接削減できる。

また、層ごと・ヘッドごとに異なる疎パターンを維持する方式と異なり、第二走査には一つのトークン集合を使う。実装と解釈は単純になるが、特定ヘッドだけが保持していた専門的情報を共通集合で落とす可能性との交換条件を持つ。

## 限界
GemFilterは選択後に捨てたトークンを復元できない。必要な根拠が早期層の最終クエリ注意へ十分現れないタスク、複数箇所を均等に統合する要約、質問が末尾にないプロンプト形式では、同じ選択規則が最適とは限らない。

フィルタ層はモデル依存であり、LLaMA 3.1 8Bの13層やMistral/Phiの19層という値を他モデルへそのまま移せない。さらに (k) を小さくするほど計算とKVは減るが、不可逆な情報欠落のリスクは増える。

二段階推論なので、短い入力や小さな圧縮率では第一走査の固定費が利得を相殺する。最大2.4倍・30%削減も特定モデル、入力長、保持トークン数、GPU環境での値であり、任意の長文脈ワークロードで一定の倍率を保証するものではない。
