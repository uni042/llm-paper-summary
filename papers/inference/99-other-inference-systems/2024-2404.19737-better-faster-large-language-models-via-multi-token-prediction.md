# Better & Faster Large Language Models via Multi-token Prediction

## 概要
複数トークン予測（multi-token prediction; MTP）は、通常の次トークン予測（next-token prediction; NTP）のように各位置から直後の1 tokenだけを当てるのでなく、同じ共有Transformer trunkから今後の複数tokenを並列に予測させる学習目的である。共有trunkが複数の将来位置から勾配を受けるため、局所的に曖昧な次tokenだけでなく、その先まで整合する表現を学びやすくなる。推論時には主headだけ残して通常modelとして使うこともでき、補助headを残せば自己投機的復号（self-speculative decoding）のdraftとして再利用できる。

論文の主結果は、MTPが小規模modelでは必ずしも得にならない一方、model規模を大きくするとコード生成能力への利得が増えること、そして13B級ではHumanEvalで解ける問題数が同等NTP modelより12%、MBPPで17%増えることにある。また複数headが予測した未来tokenを一括検証することで、別draft modelを常駐させず、7Bでコード生成約3倍・自然言語約2.7倍の推論高速化を得る。

## 問題設定
標準的な自己回帰言語モデルはtoken列 `x_1,...,x_T` に対し、位置 `t` のhidden stateから `x_{t+1}` だけを予測する。多くのtokenには局所的に複数の妥当候補があり、直後1 tokenだけを教師にすると「文章やコード全体の先」を見た場合に有用な学習信号を捨てる。また、コードでは括弧・構文・識別子など数token先との整合が重要であり、将来tokenを同時に予測する目的が表現学習の補助になる可能性がある。

一方、推論高速化に通常の投機的復号（speculative decoding）を使うと、targetとは別に小さいdraft modelを保持・実行する必要がある。MTPは学習中に既に将来token predictorを持つため、そのheadを推論時のproposal generatorとして使い、追加modelのmemory residencyを避けられる。

## 手法
### 共有trunkと複数future heads
入力prefixを共有Transformer trunk `f_s` に通し、位置 `t` の表現 `z_t=f_s(x_{le t})` を得る。その上に `n` 個の独立head `f_{head_i}` を置き、第i headが `x_{t+i}` を予測する。各headは単なる線形projectionではなく小さなTransformer blockとして実装され、最後のunembedding `f_u` は共有する。

学習lossは各future horizonのcross entropyを合算する。
`L = -Σ_t Σ_{i=1}^n log P(x_{t+i}|x_{le t})`
したがって共有trunkは一つの位置から複数未来を同時に説明するよう更新される。第1 headは通常のnext tokenを担当するため、推論時に補助headを捨てれば通常のautoregressive LMとしてそのまま利用できる。

### 公平なparameter比較
future headを増やせば総parameterも増えるため、そのままNTPと比較すると学習目的の効果とmodel sizeの効果が混ざる。論文の主要比較では `n-1` 個の追加headを置く代わりに共有trunkから同数のlayerを減らし、MTP modelとNTP baselineの総parameter数を揃える。つまりMTPが有利なら「追加parameterを増やしたから」ではなく、parameter budgetの一部をfuture predictionへ再配置した効果とみなせる。

### メモリ効率の良い学習
語彙数 `V` が大きいと、n個のheadのlogitsを同時保持するとactivation memoryが `O(nV)` に増える。そこで共有trunkを一度forwardした後、future headを1個ずつ順番にforward/backwardし、そのheadのlossから得たtrunk gradientだけを蓄積してlogitsとhead activationを即座に解放する。

この実装では全headのlogitを同時保持せず、peak logit-related memoryを概ね `O(V+d)` に抑える。論文の補足実験では、この逐次head backwardは全head同時計算と同じ勾配を与え、測定上のtraining runtime overheadもほぼ発生しない。

### 自己投機的復号
推論時に追加headを残す場合、ある位置のshared representationからhead 1,2,...が次の複数token候補を一度に提案する。これを主modelの通常next-token headでまとめて検証し、正しいprefix部分をacceptする。補助headはtarget model自身の内部にあるため、別draft modelのweightをGPUへ常駐させる必要がない。

基本的なblockwise parallel decodingでは各horizonから1候補ずつ作るが、論文はMedusa型のtree verificationとの組合せも議論する。速度は、future headの予測精度が高く平均accept長が長いほど上がる。逆に自然言語のように分岐が大きい位置、あるいは小型modelでfuture予測が弱い場合は、追加head計算とverificationの固定費に対して利得が減る。

## 評価条件
著者らは300Mから13Bまで6規模のdecoder-only Transformerをscratchから学習し、少なくとも91B code tokensを用いる。主要なコード評価はHumanEval、MBPP、APPSで、pass@1/10/100を測る。32k token vocabularyのmodelでは主にn=1,2,4,6,8などを比較し、parameter数を揃える。

追加で7B modelを200B code tokensおよび1T tokensまで学習し、長期学習でも傾向が残るか確認する。さらにbyte-level modelを314B bytesで学習し、tokenizer依存の効果かも調べる。自然言語では複数choice/log-likelihood taskと生成taskを比較する。

推論速度は7B modelでxFormersベースのimplementationを用い、MTP headsを自己投機的復号へ使った場合のtokens/sを通常greedy decodeと比較する。8-byte modelでも同様に測る。

## 主要結果
### model scale
MTPは300Mや600MではNTPより悪い場合があり、効果は一様でない。しかしscaleを上げるほど差が反転し、13Bでは同等parameter数のNTPと比べHumanEvalで解ける問題数が約12%、MBPPで約17%増える。これは「複数未来予測が常に良い」のではなく、十分なmodel capacityがあると追加のfuture supervisionを利用しやすいという結果である。

7B・200B-token学習ではn=1 baselineのMBPP/HumanEval/APPS Intro pass@1が30.0/22.8/2.8、n=4が33.8/24.0/1.6。MBPPとHumanEvalは改善する一方、APPS pass@1は低下する。APPSではpass@10/100がbaseline 7.8/17.4に対しn=4は7.1/19.9で、metricによって正負が混在する。したがって「コード全taskが改善」とは言えない。

1T-tokenまで学習するとn=1は40.7/31.7/5.4、n=4は43.1/31.6/4.3（MBPP/HumanEval/APPS pass@1）。長期学習でもMBPP gainは残るが、HumanEvalはほぼ同じ、APPSはbaselineが上回る。MTPの利得はtaskとhorizonに依存する。

byte-level 7Bでは効果が大きく、n=1のMBPP/HumanEval/APPS pass@1 19.3/18.1/0.1に対し、n=8は32.3/21.8/1.2。MBPPで約67%、HumanEvalで約20%の相対改善となる。byte列は次の複数byteがtokenized textより予測しやすい場合があり、lookahead supervisionとの相性を示す。

### 推論速度
7Bの4-token-prediction modelで自己投機的復号を行うと、コード生成は通常greedy decode比で最大約3.0倍、自然言語は約2.7倍高速化する。コードでは3個の追加proposalのうち平均約2.5 tokenがacceptされる条件があり、future headの高い一致率が速度へ直結する。8-byte prediction modelでは最大6.4倍まで伸びる。

この値は13Bの品質改善とは別実験であり、全model・全taskが3倍になるわけではない。acceptanceが低い入力ではverification costを償却できず、future head数を増やし過ぎても得にならない。

### 構成要素・学習挙動
32k vocabularyのtoken-level modelではn=4付近が強い条件が多く、horizonを増やせば単調に良くなるわけではない。将来ほどconditional entropyが高くなるため、遠いheadのlossは難しく、shared trunkへ有益なgradientを与える範囲に最適点がある。

論文のalgorithmic task分析では、MTP modelが将来tokenを当てるためにinduction-head的な回路をより早く形成する例を示す。これにより、MTPの利得を単なるoutput-head ensembleではなく、共有trunkの内部表現・学習ダイナミクスが変わる効果として説明している。

自然言語では要約など一部生成taskで改善する一方、multiple-choiceやlog-likelihood型taskは概ね同等で、大幅な普遍的改善は確認されない。コードでの一貫した長距離構造が特にMTPと相性がよいというのが著者らの解釈である。

## 既存研究との差
投機的復号は通常、別の小型draft modelを使ってtarget modelの呼出回数を減らす。Medusaは既存modelへ複数headを後付け学習する。MTPは**pretraining objectiveそのもの**を複数未来予測へ変え、共有trunkがそのsupervisionを受ける点が異なる。追加headは品質改善のための学習信号であると同時に、推論時のself-draftにもなる。

## 限界
既存checkpointへ学習なしで適用できる手法ではなく、pretraining時から目的関数とhead構成を変更する必要がある。補助headを捨てれば通常推論costに戻せるが、self-speculative decodeを使うには追加headとverification implementationが必要である。

品質改善はscale・dataset・task依存で、小型modelでは悪化し、7BでもAPPS pass@1のようにbaselineを下回る指標がある。future horizonを増やしても単調改善しない。推論speedupもacceptance rateに依存し、コードやbyte-level sequenceのように未来予測が比較的容易な条件で最大化する。

また、論文の主実験はcode-heavy pretrainingであり、自然言語全般で同じscaling gainが得られることを示してはいない。3倍・6.4倍というheadline値は特定のself-speculative実装・model・workload条件での結果である。
