# Omni-Flow: A Unified Workflow Orchestration and Distributed KV Cache Sharing Framework for Multimodal Inference

> マルチモーダル推論を制御・データ・計算の3層へ分離し、Python DSL、GPU/CPU/SSD分散KV、SGLang互換実行を統合する。LongCat-NextやHunyuanImage-3を同じ配信抽象へ載せる基盤。

## 概要

Omni-Flowは、LLM配信基盤をそのまま「画像も扱えるようにする」という局所拡張ではなく、**マルチモーダルモデルを一つの分散workflowとして表現・転送・実行するためのシステム-level abstraction**を提案する。近年のomni-modal システムは、言語モデルだけでなくvision encoder、audio encoder、image/audio decoder、diffusion transformerなど複数の役割を組み合わせる。しかも経路は固定とは限らず、入力modalや生成結果によって分岐し、複数roleが並列に動く。

従来、こうしたパイプラインはモデルごとにserviceを組み、制御分岐、テンソル transfer、KV キャッシュ共有を個別コードで接続しがちだった。その結果、新しいモデルを追加するたびにdeployment topologyとモデル implementationが密結合し、同じ重みやKVをroleごとに複製し、巨大な中間テンソルをCPU経由で受け渡すといった無駄が生じる。

Omni-Flowはこの問題をControl Flow、Data Flow、Compute Flowの3層へ分ける。Control FlowはPythonのドメイン固有言語（Domain-Specific Language; DSL）で静的DAGと動的ルーティングを記述する。Data FlowはGPU/CPU/SSDの3階層paged ストレージ上でKV キャッシュや重みを大域 資源として管理し、role間をzero-copy/low-遅延 経路で接続する。Compute FlowはSGLang interfaceへKV管理・sampling・接頭辞 matching・並列 semanticsを寄せ、LLMとdiffusion系の実行を共通化する。

論文はDeepSeek-V2、LongCat-Next、HunyuanImage-3という構造の異なるcaseを同じ抽象で載せられることを示す。一方、主張の中心は「競合より何倍速い」ではない。vLLM-OmniやSGLang-Omniと、同一ハードウェア・同一リクエスト分布でエンドツーエンド 遅延やスループットを比較した主要表は示しておらず、現段階では**統一ランタイムの設計と実装可能性**を評価する論文として読むのが適切である。

## 背景：なぜマルチモーダル配信はLLM servingより複雑になるのか

テキスト-only LLMでは、リクエストは典型的にプリフィル→デコードという比較的単純な流れを持つ。プリフィル/デコード disaggregationをしても、扱う主状態はKV キャッシュで、モデル graphも大きくは変わらない。対してマルチモーダル システムでは、画像encoderの結果をLLMへ渡し、LLMの途中出力でimage decoderやdiffusion transformerを起動し、必要なら再びLLMへ戻すようなflowが現れる。

このとき問題は計算量だけではない。role Aが作った巨大テンソルをrole Bへ渡す経路、roleをどのGPUへ割り当てるか、同じ基盤モデル 重みを複数roleが使う時に複製するか共有するか、multi-turnでどの接頭辞 KVを再利用するか、といった**制御 planeとデータ転送面の問題**が増える。

個別モデルごとにこれらを埋め込むと、新しい構成が出るたびにスケジューラ・RPC・メモリ managerまで改造する必要がある。Omni-Flowは「モデル固有のworkflow記述」と「dataの物理配置」と「カーネル実行」を分離し、それぞれを独立に交換できるようにする。

## 問題設定

Omni-Flowが対象とする主な課題は三つである。

第一はworkflow orchestrationである。単純な静的DAGだけでなく、条件分岐や複数roleの並行実行、異なる資源 グループへの分配を表せなければならない。

第二はdata 転送である。モデル間の中間テンソルやKV キャッシュは巨大で、process/ノード境界を跨ぐcopyが遅延と帯域を消費する。特にGPU→CPU→別GPUのようなbounce copyを避けたい。

第三は状態 sharingである。同じセッションや関連roleが同じ接頭辞・重みを使う場合、それぞれが独立copyを持つとHBMを浪費する。プリフィル/デコードだけに限定しない、より一般的なdistributed キャッシュ abstractionが必要になる。

## 手法のあらまし

Omni-Flowは一つのリクエストを次のように扱う。

1. **Control Flow**がPython DSLで記述されたworkflow graphを読み、次に起動するroleとルーティングを決める。
2. **Data Flow**が入力テンソル、重み、KV キャッシュの所在を解決し、可能なら同一ノード zero-copy、ノード間では低遅延経路で直接転送する。
3. **Compute Flow**が対象GPU上でSGLang-compatibleな順伝播、KV管理、samplingを実行する。
4. 出力はData Flowへ登録され、次roleは既存バッファ/キャッシュを再利用する。
5. セッションが続く場合は接頭辞 matchingで過去KVを探索し、再計算を避ける。

三層の目的は、すべてを一つの巨大ランタイムへ押し込むことではなく、**workflow topology、data 配置、モデル executionの変更頻度を切り離す**ことである。

## 手法

### 1. Control Flow — Python DSLによる静的DAGと動的routing

Control Flowはheterogeneous computing unitをノードとしてPython DSLでworkflowを記述する。固定パイプラインだけでなく、入力や途中結果に応じたconditional ルーティングを表現できる。service discoveryと読み込み balancingもランタイム側が担当するため、モデル コードが特定のIP、process、GPU配置を直接知る必要を減らす。

入力はリクエストとworkflow definition、出力は「どのroleをどの資源 グループへ分配するか」という制御決定である。これにより、モデル algorithmとdeployment topologyを分離する。新しいGPU配置へ移してもworkflow semanticsを保ちやすく、新しいroleを追加してもtransfer コード全体を書き換える必要を減らす。

追加コストはスケジューラとルーティング 層である。非常に短い単一モデル リクエストでは、この一般化が直接速度利得になるとは限らない。Omni-Flowの価値は、複雑なパイプラインほど個別統合コストを減らせる点にある。

### 2. Data Flow — GPU/CPU/SSDを跨ぐdistributed paged storage

Data FlowはKV キャッシュをプリフィル/デコード間だけの状態として扱わず、複数role・ノードで共有できるdistributed 資源へ拡張する。物理ストレージはGPU HBM、CPU メモリ、SSDの3階層をpage単位で扱い、allocationとlocationを共通metadataで管理する。

同一ノードでは不要なcopyを避け、ノード間では低遅延transfer経路を使ってrole間を直接接続する。目的は、producerが作ったテンソルを一度ホストへ戻してから民生へ再送するようなbounceを減らすことにある。キャッシュがHBMに収まらない場合はCPU/SSDへtieringできるが、下位階層 命中では当然transfer 遅延が発生する。

また、重みやKVをroleごとにprivate copyとして確保するのではなく、可能なものを大域 プールとして共有する。これによりHBM重複を減らせる一方、複数民生のlifetime、reference、追い出しを正しく管理する必要がある。

### 3. Multi-modal prefix matching — sessionを跨ぐKV再利用

multi-turn conversationでは、テキストだけでなくimage/audio由来トークンや複数roleの処理結果が接頭辞へ含まれる。単純な一列接頭辞 キャッシュでは、どのrole・modalの状態まで同一かを扱いにくい。

Omni-Flowはpage-levelの接頭辞 matchingと連鎖hashを使い、分散キャッシュ上でも共通接頭辞を探索できるようにする。履歴が一致する範囲は再利用し、増分部分だけを計算する。Data Flow側でキャッシュ locationを隠蔽するため、民生は「どのノードのどの階層にあるか」をモデル コードへ埋め込まなくてよい。

利得は命中率に依存する。セッションが毎回大きく変わる、キャッシュが下位階層へ追い出される、接頭辞粒度がモデル semanticsと合わない場合は再利用効果が小さくなる。

### 4. Compute Flow — SGLang interfaceでLLMとdiffusion executionを揃える

Compute FlowはSGLangを共通execution 層として用い、KV キャッシュ、sampling、paged メモリ、テンソル/専門家 並列化など成熟したLLM ランタイムの仕組みをマルチモーダル roleへ拡張する。

特にdiffusion transformerを完全に別engineとして扱うのではなく、可能な範囲でLLM 順伝播 pathと並列 semanticsを共有する。これにより、roleごとに別のメモリ manager、通信 層、sampling/制御 コードを持つ重複を減らす。

これは「diffusionとautoregressive LLMが同じalgorithmになる」という意味ではない。モデル固有カーネルや段階 semanticsは残るが、配信ランタイムの共通部分を一つのinterfaceへ寄せる設計である。

### 5. 三層をまたぐ一要求の実行

リクエストが来るとControl Flowがgraphを進め、Data Flowが必要状態をmaterializeし、Compute Flowが順伝播を実行する。結果テンソルは再びData Flowへ登録され、次roleが直接参照する。動的 分岐があればControl Flowが次pathを選ぶ。

この分離により、「workflowを変えたのでKV allocatorも変更」「GPU配置を変えたのでモデル コード内RPCも変更」といった連鎖を抑える。論文の貢献は個々のzero-copyやpaged キャッシュ単体より、それらを三層契約でまとめた点にある。

## 評価

### まず見るところ

- **評価の主眼:** 共通programming モデルが性質の異なるinference パイプラインを表現・実行できるか。
- **case study:** DeepSeek-V2、LongCat-Next、HunyuanImage-3。
- **検証内容:** テキスト-only streaming、multi-role omni-modal conversation、autoregressive＋diffusion image generation。
- **定量速度:** 競合システムに対する標準化されたエンドツーエンド 高速化倍率は主結果として示されない。
- **実装:** 公式repositoryがあり、モデル別exampleとdistributed deploymentを公開。
- **読み方:** performance winnerではなく、推論提供 abstractionとintegration 構成の提案として評価する。

### Case studyと何を検証したか

| Case | パイプラインの特徴 | Omni-Flowで確認する点 |
|---|---|---|
| DeepSeek-V2 | テキスト-only LLM streaming | 基本的なLLM execution、batching、streaming、共通ランタイムが単純系を壊さないこと |
| LongCat-Next | vision/audioを含むomni-modal conversation | 複数role、異種読み込み、動的 orchestration、multi-turn 状態共有 |
| HunyuanImage-3 | autoregressive 段＋diffusion 段 | 異なる生成paradigmのworkflow接続、重み/KV共有、LLM系ランタイムの再利用 |

このcase選択には意味がある。DeepSeek-V2は「一般化したランタイムでも通常LLMを扱えるか」、LongCat-Nextは「複数modal roleを動的に束ねられるか」、HunyuanImage-3は「LLMだけではない生成システムまで共通data/compute abstractionで扱えるか」をそれぞれ確認する。

### 評価で示していないもの

| 項目 | 状況 |
|---|---|
| vLLM-Omni比のエンドツーエンド 遅延 | 主要な定量比較なし |
| SGLang-Omni比スループット | 主要な定量比較なし |
| 三層化前後の最大HBM削減率 | 統一した主要数値なし |
| zero-copy単独の高速化倍率 | 機構単独ablationとして主要値なし |
| SSD tieringの帯域・tail 遅延 | 主要な標準ベンチマークなし |
| モデル quality差 | 性能論文の中心指標ではない |

したがって「GPU/CPU/SSD階層があるから高速」「zero-copyだから競合より低遅延」と結論づけるのは早い。論文が直接示すのは、これらの機構を共通フレームワークへ組み込み、異なるパイプラインを同じprogramming モデルで動かせることまでである。

### 実装面の確認

公式repositoryはRayベースのdistributed deploymentを提供し、資源 topologyをconfigurationとして記述する。モデル exampleごとにintegration状態が管理されており、論文以後も対応モデルは拡張されている。

ただしrepositoryの現在の対応表は論文発表時点より更新され得るため、本ページの論文評価と「現在何モデル対応しているか」は分離して扱う。論文の証拠はDeepSeek-V2、LongCat-Next、HunyuanImage-3を中心に読む。

## 既存研究との差

vLLM-OmniやSGLang-Omniのようなマルチモーダル 推論提供 システムも、複数modalの実行やモデル-specific パイプラインを扱う。Omni-Flowの差分は、workflow 制御、data 配置/transfer、compute executionを明示的に三層へ分離し、**新しいモデル topologyを追加するときの変更を一つのengine内へ閉じ込めない**点にある。

一般的なworkflow engineやagent graphとも異なる。Omni-Flowが扱うedgeはHTTP リクエストだけではなく、GPU テンソル、KV page、重み、RDMA/zero-copy transferであり、スケジューラはGPU/CPU/SSD階層と並列化を意識する。アプリケーションworkflowとモデル ランタイムの中間に位置するシステムといえる。

## 限界・実装状況

論文自身が初期段階のフレームワークであることを示しており、real-time性能最適化は完成形ではない。異なるテンソル-並列構成間の効率的transfer、より多様な注意機構、文脈 並列化、キャッシュ locationを考慮したルーティング、KV fragment selectionなどは今後の拡張対象である。

また、セッション内処理を安全のため直列化する箇所はdeadlock回避には有利だが、高並行multi-turn ワークロードではスループット制約になり得る。distributed キャッシュも命中率、ネットワーク 帯域、階層 migration コスト、追い出し policy次第で効果が変わる。

最も大きな評価上の限界は、競合システムとの標準化されたperformance comparisonが薄いことである。したがって現時点では「複雑なマルチモーダル パイプラインを統一抽象へ載せる設計が実装可能」とするのが強い主張であり、「最速のマルチモーダル 推論提供 システム」とする根拠にはしない。

## 一般的な実装上の含意

マルチモーダル 推論提供を拡張する場合、モデルごとのカーネル最適化だけでなく、制御・data 転送・状態 ownershipを別interfaceに切る価値がある。特に同じ基盤モデルや接頭辞を複数roleが使うシステムでは、HBM内でprivate copyを増やす前に、共有可能な状態とlifetimeを明示した方がよい。

一方で抽象化は固定オーバーヘッドを増やす。単純な一モデル パイプラインでは専用実装が速い可能性もあるため、Omni-Flow型の設計を採る判断は「一要求の最短遅延」だけでなく、モデル追加頻度、パイプライン複雑性、状態共有率、deployment変更頻度まで含めて行う必要がある。
