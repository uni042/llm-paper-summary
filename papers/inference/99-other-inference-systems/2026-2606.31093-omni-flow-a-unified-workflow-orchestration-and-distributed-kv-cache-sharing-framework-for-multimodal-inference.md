# Omni-Flow: A Unified Workflow Orchestration and Distributed KV Cache Sharing Framework for Multimodal Inference

> マルチモーダル推論を制御・データ・計算の3層へ分離し、Python DSL、GPU/CPU/SSD分散KV、SGLang互換実行を統合する。LongCat-NextやHunyuanImage-3を同じ配信抽象へ載せる基盤。

## 概要

Omni-Flowは、LLM配信基盤をそのまま「画像も扱えるようにする」という局所拡張ではなく、**マルチモーダルモデルを一つの分散workflowとして表現・転送・実行するためのsystem-level abstraction**を提案する。近年のomni-modal systemは、言語モデルだけでなくvision encoder、audio encoder、image/audio decoder、diffusion transformerなど複数の役割を組み合わせる。しかも経路は固定とは限らず、入力modalや生成結果によって分岐し、複数roleが並列に動く。

従来、こうしたpipelineはmodelごとにserviceを組み、制御分岐、tensor transfer、KV cache共有を個別コードで接続しがちだった。その結果、新しいmodelを追加するたびにdeployment topologyとmodel implementationが密結合し、同じweightやKVをroleごとに複製し、巨大な中間tensorをCPU経由で受け渡すといった無駄が生じる。

Omni-Flowはこの問題をControl Flow、Data Flow、Compute Flowの3層へ分ける。Control FlowはPythonのドメイン固有言語（Domain-Specific Language; DSL）で静的DAGと動的routingを記述する。Data FlowはGPU/CPU/SSDの3階層paged storage上でKV cacheやweightをglobal resourceとして管理し、role間をzero-copy/low-latency channelで接続する。Compute FlowはSGLang interfaceへKV管理・sampling・prefix matching・parallel semanticsを寄せ、LLMとdiffusion系の実行を共通化する。

論文はDeepSeek-V2、LongCat-Next、HunyuanImage-3という構造の異なるcaseを同じ抽象で載せられることを示す。一方、主張の中心は「競合より何倍速い」ではない。vLLM-OmniやSGLang-Omniと、同一hardware・同一request分布でend-to-end latencyやthroughputを比較した主要表は示しておらず、現段階では**統一runtimeの設計と実装可能性**を評価する論文として読むのが適切である。

## 背景：なぜマルチモーダル配信はLLM servingより複雑になるのか

text-only LLMでは、requestは典型的にprefill→decodeという比較的単純な流れを持つ。prefill/decode disaggregationをしても、扱う主状態はKV cacheで、model graphも大きくは変わらない。対してmultimodal systemでは、画像encoderの結果をLLMへ渡し、LLMの途中出力でimage decoderやdiffusion transformerを起動し、必要なら再びLLMへ戻すようなflowが現れる。

このとき問題は計算量だけではない。role Aが作った巨大tensorをrole Bへ渡す経路、roleをどのGPUへ割り当てるか、同じbackbone weightを複数roleが使う時に複製するか共有するか、multi-turnでどのprefix KVを再利用するか、といった**control planeとdata planeの問題**が増える。

個別modelごとにこれらを埋め込むと、新しいarchitectureが出るたびにscheduler・RPC・memory managerまで改造する必要がある。Omni-Flowは「model固有のworkflow記述」と「dataの物理配置」と「kernel実行」を分離し、それぞれを独立に交換できるようにする。

## 問題設定

Omni-Flowが対象とする主な課題は三つである。

第一はworkflow orchestrationである。単純な静的DAGだけでなく、条件分岐や複数roleの並行実行、異なるresource groupへのdispatchを表せなければならない。

第二はdata movementである。model間の中間tensorやKV cacheは巨大で、process/node境界を跨ぐcopyがlatencyとbandwidthを消費する。特にGPU→CPU→別GPUのようなbounce copyを避けたい。

第三はstate sharingである。同じsessionや関連roleが同じprefix・weightを使う場合、それぞれが独立copyを持つとHBMを浪費する。prefill/decodeだけに限定しない、より一般的なdistributed cache abstractionが必要になる。

## 手法のあらまし

Omni-Flowは一つのrequestを次のように扱う。

1. **Control Flow**がPython DSLで記述されたworkflow graphを読み、次に起動するroleとroutingを決める。
2. **Data Flow**が入力tensor、weight、KV cacheの所在を解決し、可能なら同一node zero-copy、node間では低遅延channelで直接転送する。
3. **Compute Flow**が対象GPU上でSGLang-compatibleなforward、KV管理、samplingを実行する。
4. 出力はData Flowへ登録され、次roleは既存buffer/cacheを再利用する。
5. sessionが続く場合はprefix matchingで過去KVを探索し、再計算を避ける。

三層の目的は、すべてを一つの巨大runtimeへ押し込むことではなく、**workflow topology、data placement、model executionの変更頻度を切り離す**ことである。

## 手法

### 1. Control Flow — Python DSLによる静的DAGと動的routing

Control Flowはheterogeneous computing unitをnodeとしてPython DSLでworkflowを記述する。固定pipelineだけでなく、入力や途中結果に応じたconditional routingを表現できる。service discoveryとload balancingもruntime側が担当するため、model codeが特定のIP、process、GPU配置を直接知る必要を減らす。

入力はrequestとworkflow definition、出力は「どのroleをどのresource groupへdispatchするか」という制御決定である。これにより、model algorithmとdeployment topologyを分離する。新しいGPU配置へ移してもworkflow semanticsを保ちやすく、新しいroleを追加してもtransfer code全体を書き換える必要を減らす。

追加costはschedulerとrouting layerである。非常に短い単一model requestでは、この一般化が直接速度利得になるとは限らない。Omni-Flowの価値は、複雑なpipelineほど個別統合costを減らせる点にある。

### 2. Data Flow — GPU/CPU/SSDを跨ぐdistributed paged storage

Data FlowはKV cacheをprefill/decode間だけのstateとして扱わず、複数role・nodeで共有できるdistributed resourceへ拡張する。物理storageはGPU HBM、CPU memory、SSDの3階層をpage単位で扱い、allocationとlocationを共通metadataで管理する。

同一nodeでは不要なcopyを避け、node間では低遅延transfer経路を使ってrole間を直接接続する。目的は、producerが作ったtensorを一度hostへ戻してからconsumerへ再送するようなbounceを減らすことにある。cacheがHBMに収まらない場合はCPU/SSDへtieringできるが、下位tier hitでは当然transfer latencyが発生する。

また、weightやKVをroleごとにprivate copyとして確保するのではなく、可能なものをglobal poolとして共有する。これによりHBM重複を減らせる一方、複数consumerのlifetime、reference、evictionを正しく管理する必要がある。

### 3. Multi-modal prefix matching — sessionを跨ぐKV再利用

multi-turn conversationでは、textだけでなくimage/audio由来tokenや複数roleの処理結果がprefixへ含まれる。単純な一列prefix cacheでは、どのrole・modalのstateまで同一かを扱いにくい。

Omni-Flowはpage-levelのprefix matchingと連鎖hashを使い、分散cache上でも共通prefixを探索できるようにする。履歴が一致する範囲は再利用し、増分部分だけを計算する。Data Flow側でcache locationを隠蔽するため、consumerは「どのnodeのどのtierにあるか」をmodel codeへ埋め込まなくてよい。

利得はhit率に依存する。sessionが毎回大きく変わる、cacheが下位tierへ追い出される、prefix粒度がmodel semanticsと合わない場合は再利用効果が小さくなる。

### 4. Compute Flow — SGLang interfaceでLLMとdiffusion executionを揃える

Compute FlowはSGLangを共通execution layerとして用い、KV cache、sampling、paged memory、tensor/expert parallelismなど成熟したLLM runtimeの仕組みをmultimodal roleへ拡張する。

特にdiffusion transformerを完全に別engineとして扱うのではなく、可能な範囲でLLM forward pathとparallel semanticsを共有する。これにより、roleごとに別のmemory manager、communication layer、sampling/control codeを持つ重複を減らす。

これは「diffusionとautoregressive LLMが同じalgorithmになる」という意味ではない。model固有kernelやstep semanticsは残るが、配信runtimeの共通部分を一つのinterfaceへ寄せる設計である。

### 5. 三層をまたぐ一要求の実行

requestが来るとControl Flowがgraphを進め、Data Flowが必要stateをmaterializeし、Compute Flowがforwardを実行する。結果tensorは再びData Flowへ登録され、次roleが直接参照する。dynamic branchがあればControl Flowが次pathを選ぶ。

この分離により、「workflowを変えたのでKV allocatorも変更」「GPU配置を変えたのでmodel code内RPCも変更」といった連鎖を抑える。論文の貢献は個々のzero-copyやpaged cache単体より、それらを三層契約でまとめた点にある。

## 評価

### まず見るところ

- **評価の主眼:** 共通programming modelが性質の異なるinference pipelineを表現・実行できるか。
- **case study:** DeepSeek-V2、LongCat-Next、HunyuanImage-3。
- **検証内容:** text-only streaming、multi-role omni-modal conversation、autoregressive＋diffusion image generation。
- **定量速度:** 競合systemに対する標準化されたend-to-end speedupは主結果として示されない。
- **実装:** 公式repositoryがあり、model別exampleとdistributed deploymentを公開。
- **読み方:** performance winnerではなく、serving abstractionとintegration architectureの提案として評価する。

### Case studyと何を検証したか

| Case | pipelineの特徴 | Omni-Flowで確認する点 |
|---|---|---|
| DeepSeek-V2 | text-only LLM streaming | 基本的なLLM execution、batching、streaming、共通runtimeが単純系を壊さないこと |
| LongCat-Next | vision/audioを含むomni-modal conversation | 複数role、異種load、dynamic orchestration、multi-turn state共有 |
| HunyuanImage-3 | autoregressive stage＋diffusion stage | 異なる生成paradigmのworkflow接続、weight/KV共有、LLM系runtimeの再利用 |

このcase選択には意味がある。DeepSeek-V2は「一般化したruntimeでも通常LLMを扱えるか」、LongCat-Nextは「複数modal roleを動的に束ねられるか」、HunyuanImage-3は「LLMだけではない生成systemまで共通data/compute abstractionで扱えるか」をそれぞれ確認する。

### 評価で示していないもの

| 項目 | 状況 |
|---|---|
| vLLM-Omni比のend-to-end latency | 主要な定量比較なし |
| SGLang-Omni比throughput | 主要な定量比較なし |
| 三層化前後の最大HBM削減率 | 統一した主要数値なし |
| zero-copy単独のspeedup | 機構単独ablationとして主要値なし |
| SSD tieringの帯域・tail latency | 主要な標準benchmarkなし |
| model quality差 | 性能論文の中心指標ではない |

したがって「GPU/CPU/SSD階層があるから高速」「zero-copyだから競合より低遅延」と結論づけるのは早い。論文が直接示すのは、これらの機構を共通frameworkへ組み込み、異なるpipelineを同じprogramming modelで動かせることまでである。

### 実装面の確認

公式repositoryはRayベースのdistributed deploymentを提供し、resource topologyをconfigurationとして記述する。model exampleごとにintegration状態が管理されており、論文以後も対応modelは拡張されている。

ただしrepositoryの現在の対応表は論文発表時点より更新され得るため、本ページの論文評価と「現在何モデル対応しているか」は分離して扱う。論文の証拠はDeepSeek-V2、LongCat-Next、HunyuanImage-3を中心に読む。

## 既存研究との差

vLLM-OmniやSGLang-Omniのようなmultimodal serving systemも、複数modalの実行やmodel-specific pipelineを扱う。Omni-Flowの差分は、workflow control、data placement/transfer、compute executionを明示的に三層へ分離し、**新しいmodel topologyを追加するときの変更を一つのengine内へ閉じ込めない**点にある。

一般的なworkflow engineやagent graphとも異なる。Omni-Flowが扱うedgeはHTTP requestだけではなく、GPU tensor、KV page、weight、RDMA/zero-copy transferであり、schedulerはGPU/CPU/SSD階層とparallelismを意識する。アプリケーションworkflowとmodel runtimeの中間に位置するsystemといえる。

## 限界・実装状況

論文自身が初期段階のframeworkであることを示しており、real-time性能最適化は完成形ではない。異なるtensor-parallel構成間の効率的transfer、より多様なattention、context parallelism、cache locationを考慮したrouting、KV fragment selectionなどは今後の拡張対象である。

また、session内処理を安全のため直列化する箇所はdeadlock回避には有利だが、高並行multi-turn workloadではthroughput制約になり得る。distributed cacheもhit率、network bandwidth、tier migration cost、eviction policy次第で効果が変わる。

最も大きな評価上の限界は、競合systemとの標準化されたperformance comparisonが薄いことである。したがって現時点では「複雑なmultimodal pipelineを統一抽象へ載せる設計が実装可能」とするのが強い主張であり、「最速のmultimodal serving system」とする根拠にはしない。

## 一般的な実装上の含意

multimodal servingを拡張する場合、modelごとのkernel最適化だけでなく、制御・data movement・state ownershipを別interfaceに切る価値がある。特に同じbackboneやprefixを複数roleが使うsystemでは、HBM内でprivate copyを増やす前に、共有可能なstateとlifetimeを明示した方がよい。

一方で抽象化は固定overheadを増やす。単純な一model pipelineでは専用実装が速い可能性もあるため、Omni-Flow型の設計を採る判断は「一要求の最短latency」だけでなく、model追加頻度、pipeline複雑性、state共有率、deployment変更頻度まで含めて行う必要がある。
