# Omni-Flow: A Unified Workflow Orchestration and Distributed KV Cache Sharing Framework for Multimodal Inference

## 概要

Omni-Flowは、言語モデル、画像・音声エンコーダ、拡散変換器、変分オートエンコーダなどを組み合わせるマルチモーダル推論を、一つの配信基盤で扱う分散スケジューリング枠組みである。中心的な発想は、モデル固有コードへ混在していた制御、テンソル転送、KVキャッシュ共有を、制御フロー（Control
Flow）、データフロー（Data Flow）、計算フロー（Compute
Flow）の三層へ分離することにある。論文はDeepSeek-V2、LongCat-Next、HunyuanImage-3という性質の異なる構成を同じ抽象で動かせることを示す一方、vLLM-OmniやSGLang-Omniに対する定量的な速度優位はまだ主張しておらず、評価の主眼は機能的な一般性にある。

## 問題設定

従来のマルチモーダル配信では、言語モデルと拡散モデルを別々のサービスとして組み、モデルごとに経路制御や転送コードを書くことが多い。この設計では、新しいモデルが分岐、反復、複数ヘッド、動的経路を持つたびに配信トポロジーとモデル実装が密結合し、統合コストが高くなる。また役割間で巨大な中間テンソルを移動し、同じ重みやKVキャッシュを複数プロセスへ複製すると、通信量とGPUメモリ消費が増える。

特にHunyuanImage-3のように、理解段階の言語モデルと生成段階の拡散変換器が関連する変換器計算を持つ場合、別サービスとして完全分離すると、共有可能な重みやキャッシュを再利用しにくい。Omni-Flowは、ワークフローの表現、データの所在、計算実行を別々の層で管理し、モデル固有の経路を基盤側へ引き上げることでこの問題を解く。

## 手法

制御フロー層はPythonのドメイン固有言語（Domain-Specific Language;
DSL）で推論処理をグラフとして記述する。静的な有向非巡回グラフだけでなく、動的な経路選択や複雑な依存関係を表現し、サービス発見と負荷分散を基盤側へ持たせる。これにより、モデル実装は「どの役割をどの順に呼ぶか」という配備固有ロジックから分離され、新しいマルチモーダル構成を追加するときの変更範囲を小さくする。

データフロー層は、事前充填と復号の二役だけに限定しない分散KVキャッシュ抽象を提供する。GPU、CPU、SSDの三階層にページ化した記憶領域を持ち、役割を跨いだ直接転送と共有を扱う。同一ノードでは不要なコピーを避け、ノード間では遠隔直接メモリアクセス（Remote
Direct Memory Access;
RDMA）などの低遅延経路を使う。重みとKVキャッシュを役割ごとに複製するのではなく、グローバルな資源プールとして管理することでGPUメモリの重複を抑える。

この層ではページ単位の接頭辞照合も重要である。履歴の内容から連鎖的なハッシュを構成し、複数ノードに分散したキャッシュでも一致する接頭辞を見つけられるようにする。多ターン対話では既存履歴を再符号化せず、クライアントが示す進行位置から増分だけを扱える。キャッシュ不足時は下位階層からの取得や再計算が必要になり、共有の利得はヒット率と転送経路に依存する。

計算フロー層はSGLangをカスタマイズ可能な推論カーネルとして利用し、言語モデルだけでなく互換な拡散変換器にも共通の実行意味論を与える。KVキャッシュ、サンプリング、ページ化注意、テンソル並列やエキスパート並列などの仕組みを基盤側で統一し、拡散側が言語モデル用に成熟した実行経路を再利用できるようにする。これにより、モデルごとに独立したメモリ管理器や通信器を持つ必要を減らす。

一つの要求を通して見ると、制御フローが処理グラフと次に実行すべき役割を決め、データフローが必要な重み・中間状態・KVキャッシュの所在を解決し、計算フローが対象GPU上で実際のモデル計算を行う。結果は次の役割へ直接渡され、既存キャッシュがあれば再利用される。動的分岐や複数モダリティがあっても、制御判断とデータ移動をモデルコードへ埋め込まない点が設計上の主眼である。

## 評価

評価はDeepSeek-V2の純粋な言語モデル配信、LongCat-Nextのオムニモーダル対話、HunyuanImage-3の複雑な画像生成パイプラインを用い、三層抽象が異種ワークロードを表現・実行できることを確認する。DeepSeek-V2では事前充填・復号分離、連続バッチ処理、ストリーミング出力の基本機能を、LongCat-Nextでは負荷特性の異なる複数モーダルヘッドの並行制御を、HunyuanImage-3では言語モデルと拡散変換器の間の重み・KV共有を検証する。

重要な注意点として、この版の論文はvLLM-OmniやSGLang-Omniとのエンドツーエンド遅延、スループット、最大メモリ使用量の定量比較を主要結果として提示していない。したがって「高速であることを実証した論文」と読むより、「急速に変化するマルチモーダル推論構成を統一抽象へ載せられることを実装で示した論文」と読む方が正確である。

## 既存研究との差

vLLM-OmniやSGLang-Omniもマルチモーダル配信を扱うが、Omni-Flowはワークフロー構造、データ転送、計算実行を三層に分け、モデル実装と配備トポロジーの結合をさらに弱めることを狙う。一般的なエージェント向けグラフ実行器とも異なり、アプリケーション呼び出しだけでなく、テンソル、KVキャッシュ、GPU/CPU/SSD階層、並列実行という推論エンジン内部の資源まで抽象化対象にする。

## 限界・実装状況

論文自身が初期段階であることを認めており、リアルタイム性能の本格最適化は今後の課題である。異なるテンソル並列構成間の効率的転送、より多様な注意方式、文脈並列、キャッシュの所在を考慮した要求振り分け、KV断片選択などが未完成である。また同一セッション内の一部処理を直列化する設計はデッドロック回避に有効だが、高並行の多ターン処理ではスループット制約になり得る。現時点では性能勝負の完成形ではなく、統一基盤の設計と実装可能性を示す段階と評価すべきである。
