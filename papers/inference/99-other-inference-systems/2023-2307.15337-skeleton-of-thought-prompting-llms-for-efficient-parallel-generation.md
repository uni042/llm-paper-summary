# Skeleton-of-Thought: Prompting LLMs for Efficient Parallel Generation

> Skeleton-of-Thought（SoT）はモデル内部の注意カーネルを変えず、**回答を「骨格作成」と「各項目の独立展開」に分解して、後半を並列実行する**。高速化の源泉は総トークン数を必ず減らすことではなく、長い1本の逐次デコードを複数の短いデコードへ分け、クリティカルパスを短くする点にある。

## 概要

一般的な自己回帰型大規模言語モデル（Large Language Model; LLM）は、回答の先頭から末尾までトークンを1個ずつ生成する。1回答の各トークンに前トークン依存があるため、単純には同じ回答の後半を先に計算できない。

しかし、説明文や知識質問では、回答全体を「理由1」「理由2」「注意点」のような複数項目へ分けられ、各項目の詳細は互いに強く依存しない場合がある。SoTはこの**意味的な独立性をプロンプトで作り出し**、最初に短い骨格だけを逐次生成する。その後、骨格の各点を個別プロンプトにして同時実行する。

APIしか使えないGPT-4等では複数API要求を並列送信し、重みを持つローカルモデルでは骨格点を一つのバッチへ束ねて復号する。最後に各展開結果を骨格順へ連結して回答を作る。

12モデル・Vicuna-80の評価ではSoTは全モデルで速度改善を示し、8モデルで2倍超、最大平均2.39倍を報告する。一方、数学、コード、長い物語のように前の節の結果が次の節の前提になる課題では独立展開が品質を壊す。そこで論文はSoT with Router（SoT-R）も提案し、質問が並列分解に向くときだけSoTを発火させる。

## 背景と問題設定

### 推論時間の多くは逐次デコードのクリティカルパスで決まる

プリフィルは入力トークンをまとめてGPUへ流せるが、自己回帰復号では次トークンを得るまで次のステップを開始できない。長い回答では、1トークン当たりが高速でも数百ステップが直列につながる。

モデル量子化や高速注意は各ステップを短くする。一方SoTが狙うのは、必要なステップを一列に並べる構造そのものを変えることである。総計算量が同じ、あるいは骨格分だけ増えても、複数GPU/APIスロットやバッチ並列性を使って壁時計時間を短くできる。

### すべての文章が並列化できるわけではない

「5つの利点を説明せよ」の各利点は比較的独立だが、「方程式を解け」では第2段階が第1段階の計算結果に依存する。コードも、前段で決めたデータ構造や変数定義を後段が参照するため、項目を独立生成すると矛盾しやすい。

したがってSoTでは、単に回答を箇条書きにするだけでなく、**骨格点が独立展開可能か**が速度と品質の両方を決める。

## 手法

### 1. 骨格生成段階で回答の構造だけを作る

入力は通常のユーザー質問である。最初のプロンプトはLLMへ、詳細を長く書かず、回答に必要な主要点を番号付きの短い骨格として出すよう指示する。

ここは逐次生成なので並列化できないが、出力を短く制限することで固定費を小さくする。骨格の役割は最終回答を作ることではなく、後段を独立タスクへ切る境界をモデル自身に提案させることである。

骨格点がB個なら、後段にはB個の展開要求が作られる。Bが小さ過ぎると並列度が不足し、大き過ぎると骨格生成費用、バッチのパディング、API要求数が増える。

### 2. 各骨格点を独立な展開要求へ変換する

各点について、元質問、全体骨格、今回詳述する対象点を含む展開プロンプトを作る。論文のプロンプトは「1〜2文で短く書く」よう指示し、一つの枝が通常回答全体と同程度まで膨らむのを防ぐ。

重要なのは、各枝が他の枝の生成完了を待たないことである。骨格で必要な全体文脈を先に共有しておき、その後は各点を独立に完成させる。

### 3. APIモデルでは並列要求、ローカルモデルではバッチ復号する

GPT-3.5、GPT-4、ClaudeのようなAPI型では、B個の展開要求を非同期に同時送信する。壁時計時間は概ね最も遅い枝の完了時間で決まり、B本の時間の合計にはならない。

ローカルのオープンモデルではB個のプロンプトを一つのバッチとしてGPUへ入れる。各系列の長さが違うため左パディングが入り、最長枝がバッチ時間を支配する。

したがって理想速度はB倍ではない。骨格生成、最長枝、バッチ非効率、API並列上限を含むため、評価の実測値は概ね1〜3倍台になる。

### 4. 完成した枝を骨格順に連結する

全枝の生成後、骨格の番号順に結果を並べて最終回答を作る。通常は追加LLM呼び出しで統合し直さず、連結だけで済ませるため統合段階の遅延は小さい。

一方で、枝間の言い回し重複、接続の不自然さ、前後矛盾はこの設計では自動修正されない。これが物語・数学・コード等で品質が落ちる主要因である。

### 5. SoT-R: 向かない質問では通常復号へ戻す

論文はSoTを常時使うのではなく、質問を見てSoT向きか判定するSoT-Rを追加する。条件は、長めの回答が必要で、複数の独立点へ分解でき、逐次的な整合性を強く要求しないことに近い。

ルータには二案がある。一つはGPT-4へ「独立した箇条書きとして回答できるか」を尋ねるプロンプト型、もう一つは手動ラベルしたLIMAデータで約120MパラメータのRoBERTaを系列分類器として学習する方式である。

ルータが陽性ならSoT、陰性なら通常の逐次復号へ分岐する。これにより数学・コード等の品質低下を避けつつ、知識・一般質問等では並列化を使う。

## 1要求の流れ

ユーザー質問を受けると、SoT-Rを使う場合は最初にルータが「SoT向き/通常生成」を判定する。通常生成ならそのまま1本の自己回帰回答を返す。

SoT向きなら、まず骨格プロンプトで短い番号付き構造を作る。次に各番号へ展開プロンプトを作り、APIなら並列呼び出し、ローカルならバッチ復号する。

最後に各枝を番号順へ並べて一つの回答として返す。待ち時間は「ルータ + 骨格 + 最長の展開枝 + 小さい連結費用」で決まり、通常生成の「回答全文の逐次トークン列」と比較される。

## 評価

### 評価条件

| 項目 | 条件 |
|---|---|
| モデル | 12モデル：9オープンソース + 3 APIモデル |
| APIモデル例 | GPT-3.5、GPT-4、Claude |
| オープンモデル例 | LLaMA2-Chat、Vicuna各サイズ、StableVicuna、UltraLM、OpenChat等 |
| 主データ | Vicuna-80：80質問、9カテゴリ |
| 追加データ | WizardLM、LIMAをルータ評価/学習で利用 |
| 質問カテゴリ | coding、math、writing、fermi、roleplay、knowledge、common-sense、generic、counterfactual |
| ローカル実行 | FastChat + Hugging Face Transformers + PyTorch、FP16 |
| 速度測定 | APIは壁時計、ローカルはCUDAイベント。実バッチ実験も実施 |
| 品質評価 | FastChat / LLMZooの比較プロンプトを用い、GPT-4判定を主評価 |
| 比較 | 通常逐次生成 vs SoT、さらにSoT-R |

### 主な結果

| 観点 | 結果 | 解釈 |
|---|---:|---|
| 12モデルの平均速度 | 全モデルで**1倍超** | 骨格固定費込みでも壁時計時間を短縮 |
| 2倍超のモデル数 | **8 / 12** | 多くのモデルで並列枝の利得が明確 |
| 最大平均速度 | **2.39倍** | 理想B倍ではなく骨格・最長枝・パディングで制限 |
| 実バッチ検証 | オープンモデルで最大**2.88倍** | 推定だけでなく実際のバッチ実行でも確認 |
| RTX 3090の7Bモデル例 | 約**1.94〜2.40倍** | データセンターGPU限定の効果ではない |
| 向くカテゴリ | knowledge / generic / common-sense / roleplay / counterfactualで**1.89〜2.33倍** | 独立した複数点へ分けやすい |
| FastChat品質 | win 29.5%、tie 29.3%、lose 41.2% | SoTが非劣位なのは約58.8% |
| LLMZoo品質 | win 45.8%、tie 19.6%、lose 34.5% | 指標依存だが非劣位は約65.4% |
| 品質傾向 | coding / math / writing / fermiで悪化しやすい | 枝間の逐次依存を壊すため |
| GPT-3.5 / GPT-4 | 約**2倍**級の高速化を報告 | API並列でも成立 |

品質評価は人手の絶対評価ではなく、LLM判定器によるペア比較である。FastChatとLLMZooで「勝ち」の率が29.5%と45.8%に分かれるため、「品質も必ず向上する」と読むべきではない。両指標が示すのは、全体では概ね同等圏だがカテゴリ依存が大きいということになる。

### カテゴリによって速度と品質が同時に変わる

知識、一般質問、常識、ロールプレイ、反実仮想は、複数観点を並列に書きやすいためSoTと相性が良い。これらでは1.89〜2.33倍程度の速度を得ながら、品質も比較的保ちやすい。

数学、コード、フェルミ推定、文章作成は、前の途中結果や文脈を次の部分へ渡す必要がある。枝を独立にすると整合性が崩れ、単純な速度改善より品質低下が問題になる。この観測がSoT-R導入の根拠である。

### 並列度を増やせば無制限に速くなるわけではない

骨格点数Bを増やすと展開枝は短くなる可能性があるが、API要求数、バッチサイズ、パディング、骨格そのものの長さも増える。また枝の長さが不均衡なら最長枝が終了するまで全体を返せない。

そのため速度は「総生成トークン数/B」で単純には決まらない。実運用では、骨格点数、API同時実行上限、GPUバッチ効率、ストリーミング体験を合わせて調整する必要がある。

## 既存研究との差

量子化、KVキャッシュ、高速注意、投機的復号は主にモデル・カーネル・デコードアルゴリズムの内部を変える。SoTはモデルをブラックボックスのまま、**要求する出力構造を変えて並列性を作る**データ中心の最適化である。

自己整合性（Self-Consistency）やTree-of-Thoughtは複数推論分岐を生成して品質を上げることが主目的で、複数枝の結果から選択・探索する。SoTは一つの回答を複数部分へ分割し、最終回答の各部分を同時生成して待ち時間を下げる。

投機的復号のように同じ次トークン列を検証して受理する方式でもない。SoTでは枝同士が別の意味単位を担当し、並列性はトークン予測器ではなく文章構造から生まれる。

## 限界・実装状況

第一に、独立分解できない課題へは不向きである。数学、コード、物語のように段落間依存が強い回答では、各枝が互いの結果を見ずに生成されることで矛盾や重複が増える。

第二に、総計算量や料金を減らす方式ではない。骨格生成が追加され、各展開プロンプトには元質問や骨格を繰り返し含めるため、API課金トークンやプリフィル計算は増える場合がある。SoTは主として**待ち時間と計算量を交換する**。

第三に、並列資源が必要である。API側の同時実行制限が厳しい場合、または単一GPUでバッチを増やす余裕がない場合、理論上の並列枝を同時処理できない。

第四に、品質評価は主にLLM判定器を用いる。FastChatとLLMZooで判定傾向が異なり、人間評価そのものではないため、細かな品質差の確定的根拠にはしにくい。

第五に、長さの不均衡が速度を制限する。1枝だけ長くなると他枝が先に終わっても全体待ち時間はその枝に支配される。骨格点を均等な作業量へ切る能力がシステム性能に直結する。

## サーベイ上の含意

SoTはLLM推論の並列性が、モデル内部のテンソル並列や投機的復号だけでなく、**回答という仕事の意味的分割**からも作れることを示す。特にAPIモデルにも適用できるため、基盤モデルの重みやカーネルへ触れない利用者側最適化として特徴的である。

一方で、これは「高速プロンプト」の万能解ではない。評価で数学・コードが悪化することを自ら示し、SoT-Rで通常復号へ戻す設計を追加している。実サービスでは、速度倍率だけでなく、分解可能性判定、API/GPUの並列上限、追加トークン費用、枝間整合性を一体で評価すべきである。
