# BEAR：実行中のバッチ進行を再生する初回トークン遅延予測と異種LLM要求ルーティング

## 概要

本論文の対象は、能力・単価・推論速度が異なる複数の大規模言語モデル（Large Language Model、LLM）を同時に提供する推論サービスである。従来のモデルルータは入力質問の難しさを見て品質と費用を比較し、負荷分散器はモデルが決まった後にキュー長などからインスタンスを選ぶことが多い。しかし、この二段階の分離では、能力が高くても現在混雑しているモデルへ要求を送り、初回トークン遅延（Time To First Token、TTFT）の期限を破る場合がある。逆に単純な最短キュー選択は、小型モデルに偏って回答品質を犠牲にし得る。

著者はバッチ進行認識推定器（Batch Evolution Aware、BEA）と、それを用いるルータ（Batch Evolution Aware Router、BEAR）を提案する。BEAは、各インスタンスに現在存在する要求、残る入力トークン、予測した出力トークン数、同時実行枠、鍵・値キャッシュ（Key-Value Cache、KV Cache）のメモリ制約を入力として、推論エンジンのトークンバッチ形成を仮想的に進める。新規要求の入力処理が終わり最初の出力トークンを得た時点で再生を止め、それまでのバッチ時間の予測値を合算する。BEARは各インスタンスについてこのTTFTを推定し、要求ごとの期限内に収まる候補から、予測品質と推論費用の効用が最大のものを選ぶ。

Qwen3-0.6B、Qwen3-8B、Qwen3-32Bを合計4枚のH100で動かしたvLLM環境では、BEAのTTFT予測誤差は約5%、一回の推定時間は約0.1ミリ秒だった。BEARの期限内効用は、RouteBalanceとSCOREという遅延を考慮するルータに対し平均63%改善し、各到着率で最良の比較方式に対しても平均30.5%高かった。これらは「全要求のTTFTを63%短縮」という意味ではない。期限を満たした要求に対して品質・費用の効用を計上する指標の改善である。

## 問題設定：モデル選択と負荷分散の分離が生む損失

### 初回トークン遅延を何で決めるか

要求$i$がモデルインスタンス$j$に到着したときのTTFTは、計算開始前の待ち時間$W_{i,j}$と、入力トークンを処理して最初のトークンを生成する時間$P_{i,j}$の和である。

$$L^{\mathrm{ttft}}_{i,j}=W_{i,j}+P_{i,j}.$$

入力一括処理（prefill）は入力トークンを並列計算し、復号（decode）は生成中の要求それぞれに通常一つの新トークンを追加する。連続バッチ処理（continuous batching）では複数要求の入力チャンクと復号トークンが同じGPU実行バッチを共有する。したがって、入力待ちの要求数が同じ二つのインスタンスでも、復号中要求の文脈長・残り出力長・KV占有量が違えば、新規要求のTTFTは大きく変わる。キュー長や平均トークン処理量だけでは、この干渉を十分表現できない。

論文はQwen3-0.6Bを単一H100で動かした条件で、残る入力トークン数を平均プレフィル処理量で割る単純な予測器がTTFTを平均絶対百分率誤差（Mean Absolute Percentage Error、MAPE）約85%でしか予測できない例を示す。過去に計測した処理量と現在の入力・復号混合比が違うと、予測の偏りが大きくなる。高負荷時の期限違反を避けるには、GPU内のバッチがどのように変化するかを考慮する必要がある。

### ルーティングの目的関数

各要求とモデルについて、回答品質の予測値$\widehat{\mathrm{acc}}_{i,j}$、入力・出力トークン料金から計算する費用$\widehat{\mathrm{cost}}_{i,j}$、初回トークン遅延$\widehat{L}^{\mathrm{ttft}}_{i,j}$を得る。品質と費用の効用は

$$\widehat U_{i,j}(\lambda)=\widehat{\mathrm{acc}}_{i,j}-\lambda\widehat{\mathrm{cost}}_{i,j}$$

とする。$\lambda$は品質と費用の交換係数である。要求$i$のTTFT目標を$\tau_i$とすると、$\widehat L^{\mathrm{ttft}}_{i,j}\le\tau_i$を満たす候補集合から効用最大のインスタンスを選ぶ。候補が空なら、予測TTFTが最小のインスタンスへ送る。別の定式化としてTTFTへの罰則係数$\delta$を加える緩和目的も評価する。$\delta=0$は遅延を無視する選択、$\delta$を大きくすると遅延優先へ移る。

論文の主評価指標である期限内効用（OnTimeUtility）は、期限を満たした要求に対する実現品質・費用効用を平均し、TTFT目標を超えた要求の寄与をゼロとする。期限達成率だけでなく、期限内に返した回答の能力と費用も同時に評価するため、単純な最短キュー方式との違いを表現できる。

## 手法：BEAによるバッチ進行の軽量再生

### 1. 実行中要求の状態をスナップショット化する

各モデルインスタンス$j$は、入力待ち要求集合$\mathcal Q_j(t)$と、入力処理または復号が進行中の要求集合$\mathcal A_j(t)$を保持する。これらの和集合$\mathcal R_j(t)$が実行中・待機中の要求全体である。各要求について残る入力トークン数、現在の文脈長、予測した残り出力トークン数を保持する。新規要求$i$の入力長と出力長予測も追加し、候補インスタンスごとに仮想の作業集合を作る。

出力長は未確定なので、要求文から学習した軽量回帰器で予測する。原著の実装は、質問のトークンを512次元の符号付きハッシュ表現に写像し、主成分分析（Principal Component Analysis、PCA）で16次元へ圧縮した特徴、入力長、文字数、文数、指示形式などをLightGBMへ渡す。品質予測器はさらにモデル識別子・パラメータ規模・最大文脈長を使用する。したがってBEAは「出力長を知っている」わけではなく、長さ予測誤差が再生精度へ伝播する。

### 2. サービング方針に沿って次のトークンバッチを作る

再生器は対象の推論フレームワーク（serving framework）が実際に使う、バッチのトークン予算、要求の入場順序、同時実行数、分割入力処理（chunked prefill）、KVメモリ上限などの規則を適用する。各反復では、復号中要求から最大1トークンずつ、入力処理中要求から0個以上の入力チャンクを選ぶ。これにより仮想バッチ$\mathcal B_j^{(\ell)}(t)$が決まる。

バッチ処理後には、各要求の残り入力長、復号進行、文脈長、KV占有量を更新する。出力長に到達した要求は完了として除外し、空いたメモリに待機要求を入れる。この処理を、新規要求$i$の入力処理が完了して最初の出力トークンを得るバッチ$\ell^{\mathrm{ttft}}$まで繰り返す。**全要求の生成完了まで再生しない**ことが、ルーティングの決定経路で約0.1ミリ秒の計算時間に抑える重要な設計である。

### 3. バッチ時間を四項の校正済みモデルで推定する

カーネル単位のシミュレーションは重いため、バッチ$\ell$の処理時間を、モデルインスタンスごとに測定・校正した四係数$\beta_{0,j},\ldots,\beta_{3,j}$で予測する。第一項はバッチ固定費用、第二項は処理する入力・復号トークン数に比例する密層計算、第三項は復号時の既存文脈長に比例する注意計算・KV読出し、第四項は入力チャンク長と既存文脈長の積およびチャンク内部の二次的注意費用である。

$$\widehat T_j^{(\ell)}=\beta_{0,j}+\beta_{1,j}\sum_q(p_q^{(\ell)}+d_q^{(\ell)})+\beta_{2,j}\sum_q c_q^{(\ell)}d_q^{(\ell)}+\beta_{3,j}\sum_q\left(p_q^{(\ell)}c_q^{(\ell)}+\frac{p_q^{(\ell)}(p_q^{(\ell)}+1)}{2}\right).$$

ここで$p_q^{(\ell)}$はそのバッチで処理する入力チャンク長、$d_q^{(\ell)}\in\{0,1\}$は復号トークン数、$c_q^{(\ell)}$は処理前の文脈長である。新規要求の最初のトークンが生成されるまでの推定時間を合計して

$$\widehat L^{\mathrm{ttft}}_{i,j}=\sum_{\ell=1}^{\ell^{\mathrm{ttft}}}\widehat T_j^{(\ell)}$$

を得る。四係数はGPUやモデル構成に固有なので、別ハードウェアに数値を無条件に転用しない。論文では単一H100上のQwen3-0.6Bについて、個々のバッチ処理時間のMAPE約4%を示した。

### 4. 予測TTFTからモデルとインスタンスを一体選択する

BEARは要求到着時に各候補インスタンスへBEAを適用し、同時に品質予測器と費用予測器を評価する。従来の「モデルを選択してから最短キューの複製を探す」二段階とは異なり、特定モデルの品質だけでなく、今そのモデルを提供する特定インスタンスの混雑状況まで含めて一回の選択を行う。高負荷で大モデルが期限に間に合わないと予測された要求は小モデルへ寄せ、余裕のあるときは大モデルの品質を利用する。

### 5. 状態を取得できない場合の解析的近似

BEAのスナップショットを取得できない環境向けに、論文は制限付きプロセッサ共有（Limited Processor Sharing、LPS）の待ち行列モデルを導く。同時実行上限を$k_j$、要求到着率を$\alpha_j$、モデルの総処理率を$\mu_j$、稼働率を$\rho_j=\alpha_j/\mu_j$とする。ポアソン到着、指数分布の処理要求、先着順待ち、活性要求への等分配、$\rho_j<1$という仮定の下で、平均待ち時間は

$$\mathbb E[W_{i,j}]=\frac{\rho_j^{k_j}}{\mu_j-\alpha_j}.$$

平均TTFTはこの待ち時間に、入力長を平均プレフィル処理量で割った近似値を足す。Qwen3-0.6BのH100実測で平均活性要求数25.7に対し、$k=25$のモデルが負荷上昇時のTTFT傾向をよく再現した。ただし、これは個別要求の細かなバッチ干渉を再生するBEAと同じ予測精度を保証するものではない。付録Dの変動係数を用いた一般化は近似式であり、重い裾を持つ出力長や急激な到着変化には追加検証が必要である。

### 要求到着率による変化

負荷が増すと大型モデルのTTFT期限を満たす余裕が減る。BEARは予測上間に合う場合は8B・32Bを使い、混雑時は0.6Bの利用比率を増やす。一方、最短キューは期限達成率が高くても小型モデルへ偏り、品質・費用を含むOnTimeUtilityでは不利になる。遅延を考慮しないルータとラウンドロビンは割当てがほぼ一定のため、高負荷で期限違反が増える。ここで63%の改善は平均のOnTimeUtilityであり、期限達成率や平均生成速度だけを示したものではない。

### 制約の厳しさと構成要素除去

罰則係数$\delta$を変える実験では、品質・費用とTTFTの交換条件が連続的に変化し、同程度の遅延でより高い効用を得る傾向を示す。BEAを単純な入力処理量ベースの推定器に置換する要素除去では、低到着率では同程度の効用が得られるが、到着率が高くなるほどBEAとの差が拡大する。これはBEARの改善を「単に品質予測器を追加したため」とする説明を退け、負荷状態を反映したTTFT推定が高負荷で重要であることを支持する。ただし、品質・出力長予測器の独立誤差が完全に分離されているわけではない。

### バースト到着と古い状態

著者は平均到着率6・7・8要求/秒、低負荷状態と高負荷状態の比3倍または6倍、平均20%の時間を高負荷に割り当てる2状態マルコフ変調ポアソン到着も評価した。BEARはこの変動条件でも比較手法より高いOnTimeUtilityを保つ。スナップショットを取得する通信に400ミリ秒程度の遅延があっても結果はほぼ変わらず、1秒では約7%低下する。これは定期更新の実装可能性を示すが、負荷が急変する未知の本番トラフィックに対する期限保証ではない。

## 既存方式との差とシステム設計上の位置づけ

RouteBalanceとSCOREは品質・費用・遅延を同時に考慮するが、遅延を平均処理量や出力長予測から近似するため、入力チャンクと復号の混合、KVメモリ上限、各要求の文脈長が次のバッチへ与える影響を粗く扱う。BEAは各要求のトークン状態を持つスナップショットから、実際のスケジューラ規則を反復してこの欠落を埋める。Vidurのようなカーネル単位の詳細なオフラインシミュレーションとは異なり、計算対象を新規要求の初回トークンまでに限定し、バッチ処理時間も四項の簡易モデルで表現する。

BEARはvLLMそのもののカーネルを高速化する技術ではない。実際の計算量はモデル選択の結果として変わるが、主な寄与は要求ごとの配置先を改善し、期限を満たす高品質な応答の比率と効用を高めることにある。既存の連続バッチ処理、分割プレフィル、KV管理、モデル並列、出力長予測と組み合わせるルーティング層の研究であり、単一GPUのローカル推論へ直接組み込んで一要求の復号速度を上げるものではない。

## 限界・負の結果・再現上の注意

**実行時状態への依存。** BEAはモデルインスタンスから待機中・活性中要求の状態を周期的に受け取る必要がある。状態が古いほど負荷推定がずれる。論文の1秒遅延で約7%効用低下という結果は、この依存が無視できないことを示す。インスタンスが多数ある場合の状態集約・通信費用、スナップショット整合性、障害時の退避先選択は追加の実装課題である。

**予測器の一般化。** 出力長と回答品質は質問特徴に基づく予測であり、実際の生成結果とは一致しない。特に長い創作出力や未知の質問形式、言語・モデル更新で誤差が増える可能性がある。品質指標は言語モデル審査器の尺度に依存し、別の評価尺度で同じルータ順位になるとは保証できない。

**モデル・GPU・スケジューラへの依存。** 評価プールはQwen3の三サイズ、H100計4枚、vLLMである。別のGPU、より多数の複製、推論前処理・復号分離、専門家並列、投機的復号、異なる優先度制御では、バッチ形成規則と四項の処理時間係数を再校正する必要がある。BEAはフレームワーク非依存の抽象を目指すが、任意の実装に無改修で適用できると実証したものではない。

**TTFTだけを主制約とする。** 期限内に最初のトークンが返っても、残りの出力が遅ければ利用者の体験は悪い。論文は主にTTFTを最適化し、最終応答完了遅延、トークン間隔、全利用者の末尾遅延を同時に保証するものではない。高負荷時に0.6Bへ割り当てることは期限には有利でも、難問の品質に不利となり得る。

**解析モデルの仮定。** LPSの閉形式はポアソン到着・指数処理時間・等分配・定常稼働率1未満を仮定する。付録の一般化式は変動係数に基づく近似で、重い裾を持つ出力長や極端なバーストに対する厳密式ではない。システム全体のメモリ逼迫、GPU故障、キャッシュ再利用、価格変動は主評価の範囲外である。

**書誌・候補メタデータの更新。** GitHub worklistの同一arXiv IDには旧題名「Beyond Accuracy and Cost: Latency-Aware LLM Query Routing for Dynamic Workloads」が残っていたが、2026年10月15日改訂のarXiv v2一次書誌では現題名「Mind the Delay: Latency-aware Query Routing for Heterogeneous LLM pools」である。本稿はcanonical identityを維持しつつ、最新版の著者・題名・手法・実験に合わせた。worklist表示名を根拠に別論文として二重登録しない。
