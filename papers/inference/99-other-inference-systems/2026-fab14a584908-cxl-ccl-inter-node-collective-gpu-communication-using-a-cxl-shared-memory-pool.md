# CXL-CCL: Inter-Node Collective GPU-Communication Using a CXL Shared Memory Pool

> CXL共有メモリをノード間GPU集団通信の媒体として使い、データ配置・細粒度重畳・ドアベル同期でRDMA型通信に対する性能とコストを改善する。

- **著者**: Dong Xu, Han Meng, Xinyu Chen, Dengcheng Zhu, Wei Tang, Fei Liu, Liguang Xie, Wu Xiang, Rui Shi, Yue Li, Henry Hu, Hui Zhang, Jianping Jiang, Dong Li

## 概要
複数ノードのGPU集団通信をRDMAネットワークだけに依存せず、CXL共有メモリプールへの書込みと読出しで実現する通信ライブラリ。CXL機器間にハードウェア細粒度インターリーブがなく、送信側の書込み完了を受信側が安全に知れず、書込み後読出し依存で並列性が落ちる問題に対し、規則的な通信パターンを使ったソフトウェア配置、細粒度分割による書込み・読出し重畳、共有メモリ上の軽量ドアベル同期を組み合わせる。実機CXLスイッチと6枚のメモリカードで200 Gbps InfiniBandと比較し、多くの集団通信とLlama-3-8B学習で高速化を示す。

CXL-CCLはCXL共有メモリプールを単なる容量拡張やKVキャッシュ保管場所ではなく、ノード間GPU集団通信そのものの媒体として使う。規則的な集団通信のアクセス形状を利用してデータを複数CXL機器へ決定論的に配置し、細粒度分割でGPUからプールへの公開とプールからGPUへの取得を重ねる。さらに共有メモリ上に事前確保した軽量ドアベルを使い、データ本体とは別の準備完了通知を明示的に可視化することで、CXLのノード間整合性不足をソフトウェアで補う。

代表結果として、8種の集団通信の平均高速化は1MB〜4GBの可変メッセージ、CXL-CCL完全版で200 Gbps InfiniBand上のRDMA型実装に対してAllGather 1.34倍、Broadcast 1.84倍、Gather 1.94倍、Scatter 1.07倍、AllReduce 1.50倍、ReduceScatter 1.43倍、Reduce 1.70倍、AllToAll 1.53倍。規則的配置で機器競合を避け、細粒度の公開・取得重畳で共有プールの合計帯域を通信ファブリックとして利用できる。
## 問題設定
分散LLMの学習・推論ではAllReduceやAllGatherなどのGPU集団通信がノード間帯域を大量に消費する。従来のNCCLとRDMA型経路は高性能だが、高価なInfiniBand設備と複雑な通信スタックを必要とし、コピー用GPU資源やHBM帯域、段階ごとのCPU・GPU同期も消費する。一方CXL共有メモリプールは複数ホストから同じ領域をロード・ストアできるが、複数CXL機器をDRAMのようにキャッシュライン単位で自動分散せず、同一機器への競合が帯域を分割する。また共有領域では書込み後に別ランクが読む依存が生じ、ノード間の完全なキャッシュ整合性もないため、受信側がデータ準備完了を安全に判断できない。
## 新規性
CXL-CCLはCXL共有メモリプールを単なる容量拡張やKVキャッシュ保管場所ではなく、ノード間GPU集団通信そのものの媒体として使う。規則的な集団通信のアクセス形状を利用してデータを複数CXL機器へ決定論的に配置し、細粒度分割でGPUからプールへの公開とプールからGPUへの取得を重ねる。さらに共有メモリ上に事前確保した軽量ドアベルを使い、データ本体とは別の準備完了通知を明示的に可視化することで、CXLのノード間整合性不足をソフトウェアで補う。
## 手法
### 手法のあらまし
各ホストは起動時にDAXでCXL共有メモリ領域を利用者空間へ写像し、そのページをCUDAのホストバッファとして登録する。これによりGPUとCXLプールの間を通常のCUDAコピーで往復でき、RDMAの作業要求やFIFO用コピー経路を通信の中心から外す。集団通信では各ランクの送信バッファを共有プールへ公開し、必要なランクがそこから自GPUへ読み戻し、AllReduceやReduceScatterなら読出し後に削減演算を行う。単純に同じCXL機器へ置くと複数ホストの要求が競合して帯域を分け合うため、通信が1対N・N対1かN対Nかを最初に分類し、ランク番号とデータ番号から書込み先機器とオフセットを決定論的に計算する。N対Nではランクごとに互いに重ならない機器範囲を割り当て、データ公開順と読出し開始位置もずらして、同じカードへの同時読書きを避ける。次に一つの大きなデータを複数チャンクへ分け、GPUからCXLへの書込み用ストリームとCXLからGPUへの読出し用ストリームを並行させる。送信側は一つのチャンクを書き終えるたび、そのチャンクに対応して事前確保された共有メモリ上のドアベルを準備完了へ変更し、更新を明示的にフラッシュする。受信側は対応ドアベルだけを監視し、古い値ならキャッシュラインを無効化して再読出しする。準備完了を確認したチャンクは後続チャンクの公開完了を待たず直ちにGPUへ取得し、必要な演算へ渡す。したがって全データ公開後に全データ取得を始める二段直列処理が、生産者と消費者がチャンク単位で進むパイプラインへ変わる。最後に各NCCL集団通信の意味論に従って必要なチャンクを集約し、利用者の受信バッファへ結果を返す。配置で機器間競合を減らし、分割で双方向転送を重ね、ドアベルでノード間の可視性不足を補う三機構が順番に働く設計である。

### ソフトウェア帯域集約とデータ配置
CXLプールは複数メモリカードを束ねてもDRAMのような細粒度自動インターリーブを提供しないため、複数ランクが同じカードへ集中すると各ランクの実効帯域が低下する。CXL-CCLは動的ブロック割当ではなく、集団通信の規則的な送受信関係からランク番号とデータ番号を使って配置を事前計算する。1対N・N対1ではデータを複数機器へ散らし、N対Nでは各ランクへ排他的な機器範囲を与える。ReduceScatterの例では各ランクの公開順序もずらし、あるランクが一方の機器から読む間に別ランクが別機器へ書けるようにする。大きな割当メタデータや並行アロケータを避けながら、スイッチ背後の複数カードの合計帯域を利用しやすくする。

### 細粒度分割による書込み・読出し重畳
共有メモリ方式では受信側が送信側の全データ公開を待つと、書込み後読出し依存によって片方向の転送器が遊ぶ。そこで通信データを複数チャンクへ分割し、各チャンクを独立した準備単位にする。GPUからCXLへの書込みとCXLからGPUへの読出しを別CUDAストリームで進め、先頭チャンクが準備できた時点で受信側が取得を始める。これにより後続チャンクの公開と先行チャンクの消費が重なり、双方向帯域を利用できる。ただしチャンクを細かくしすぎるとcudaMemcpy呼出しや同期の固定費が支配的になり、小メッセージではInfiniBandより遅くなる。

### 共有メモリ上のドアベル同期
ノードをまたぐCXL領域では通常の単一ホスト内キャッシュ整合性だけに頼れず、受信側がデータ本体の可視化完了を推測すると古い値や途中状態を読む危険がある。CXL-CCLはチャンクごとに事前確保したドアベル領域を持ち、送信側がデータ転送完了後に対応状態を準備完了へ更新してフラッシュする。受信側は準備完了になるまでその小さな状態だけを監視し、古いキャッシュ値が疑われる場合はドアベルのキャッシュラインを無効化して再読出しする。動的ロック割当を避け、CXLアクセスがローカルDRAMより約3.1倍遅い環境でも同期メタデータの余計な往復を抑える。

### 全体のデータ／制御の流れ
NCCL 2.28.3へ1020行の変更・追加で実装され、利用者バッファと共有プール間をCUDA非同期コピーで移動する。通信アルゴリズムはCXLプールの共有アドレス空間を利用する一方、現行GPUの方向別DMAエンジン数、CXLカード数、カードごとのGen5 x8帯域が上限になる。AllReduceでは各ランクが他ランクのデータを個別に読み削減するため、InfiniBandリングの中間削減結果再利用ができず、ノード数増加時の弱点となる。
## 評価条件
- **ハードウェア**: 主評価は3ノードで、各ノードにIntel Xeon 6960P 72物理コア、DRAM 256GB、NVIDIA H100 80GBを搭載する。各ノードはGen5 x16でTITAN-II CXLスイッチへ接続し、スイッチ背後にMicron CZ120 CXL Type-3 128GBカード6枚、合計768GBの共有プールを置く。拡張性評価では3、6、12ノードを扱う。
- **ソフトウェア**: Linux 6.2.6、CUDA 12.8、NCCL 2.28.3、nccl-tests 2.17.8。CXL-CCLはNCCLへ30行変更・980行追加した1020行の実装。DAXで共有領域を写像しCUDAホスト登録を用いる。
200 Gbps InfiniBand上のRDMA型NCCLを主要比較対象とし、1MB〜4GBのメッセージでAllReduce、Broadcast、Gather、Scatter、AllGather、ReduceScatter、Reduce、AllToAllを測定する。完全版に加え、帯域集約だけを粗粒度で行う版と、インターリーブも重畳も行わない単純版を比較して構成要素の寄与を分離する。CXLプール単体のCPU遅延、GPU-CXL帯域、同一機器への並行アクセス競合も測定する。チャンク数感度、3〜12ノード拡張性、Llama-3-8BをWikipediaでFSDP学習する実用ケースも評価する。
主要性能は実物のCXLスイッチとメモリカードによる実機測定であり、エミュレーションだけではない。ただし大規模マルチホストCXL機器の入手性から最大12ノード・CXLカード6枚までで、数十〜数百ノードは対象外。GPUごとに方向別DMAエンジンが一つという制約や、カード側Gen5 x8帯域の影響を強く受ける。小メッセージではソフトウェア固定費が支配的になる。
## 主要結果
200 Gbps InfiniBandに対する平均高速化はAllGather 1.34倍、Broadcast 1.84倍、Gather 1.94倍、Scatter 1.07倍、AllReduce 1.50倍、ReduceScatter 1.43倍、Reduce 1.70倍、AllToAll 1.53倍と報告される。利点は複数CXLカードの合計帯域を使い、書込みと読出しを重ねられる大きな通信で出やすい。一方、小メッセージでは細粒度cudaMemcpyと同期の固定費が効き、ReduceScatterやScatter、AllToAllの一部条件ではInfiniBandを下回る。ノード数増加時のAllReduceは各ランクが全データを個別に読み削減するため、リング型の中間結果再利用ができず拡張性が弱い。

- 8種の集団通信の平均高速化 / AllGather 1.34倍、Broadcast 1.84倍、Gather 1.94倍、Scatter 1.07倍、AllReduce 1.50倍、ReduceScatter 1.43倍、Reduce 1.70倍、AllToAll 1.53倍 (比較対象: 200 Gbps InfiniBand上のRDMA型実装; 条件: 1MB〜4GBの可変メッセージ、CXL-CCL完全版) — 規則的配置で機器競合を避け、細粒度の公開・取得重畳で共有プールの合計帯域を通信ファブリックとして利用できる。

- Llama-3-8B FSDP学習 / 1.11倍高速化、相互接続ハードウェア費2.75倍低減 (比較対象: 200 Gbps InfiniBand; 条件: Wikipediaデータセット、AllGatherとReduceScatterを用いる分散学習) — 単体通信だけでなく実際のLLM学習でも通信改善が全体性能へ反映され、CXLスイッチの価格差が設備費低減につながる。

- チャンク数感度 / 最大約9%の性能変動、4または8チャンクが良好 (比較対象: 1チャンクなど粗粒度設定; 条件: AllGather、1GBメッセージ) — 分割が少なすぎると書込み後読出し依存が長く残り重畳できないが、過度な細粒度化にも固定費があるため適切な粒度が必要。

### 負の結果・境界条件
- 小メッセージではcudaMemcpy呼出しと同期の固定費が相対的に大きく、ReduceScatterはInfiniBand比0.48倍、Scatterは0.46倍、AllToAllは0.7倍まで低下する条件がある。AllReduceは256MB超で平均約1.05倍に留まる条件があり、リング型InfiniBandが中間削減結果を再利用できるのに対しCXL-CCLは各ランクが全データを読むためである。3から6ノードへのAllReduce拡張で時間は2.1〜3.0倍、12ノードでは8.7〜12.2倍に増え、6枚のCXL機器への競合が深刻化する。

### 結果の読み方
CXL共有メモリ方式はネットワーク処理をメモリコピーへ置き換えるだけでは十分でなく、複数機器への配置と生産者・消費者重畳が性能の鍵になる。大きな転送では固定費を償却しやすく、複数カードの帯域を生かせるが、小転送と全ランク全データ読出し型の演算ではGPUコピー起動や共有機器競合が支配的になる。
## 品質への影響
通信層の変更であり、モデルの数値精度や生成品質を近似化する方式ではない。評価対象の集団通信意味論とFSDP学習処理を維持したまま通信時間と設備費を比較している。
## 既存研究との差
従来のCXL利用研究がメモリ拡張、分離メモリ、KVキャッシュの長期保管などを主用途とするのに対し、本研究は共有メモリプール自体をGPU集団通信のノード間媒体として扱う。RDMA型NCCLのネットワーク作業要求とコピー・通信パイプラインに対し、CXLのロード・ストア意味論、決定論的なデータ配置、共有ドアベルを用いる。単なる共有メモリ通信と異なり、集団通信固有の規則的アクセスを利用して機器競合を避け、チャンク単位で公開と取得を重ねる点が中心である。
## 限界
現行評価はCXLカード6枚と最大12ノードで、数十〜数百ノードの集団通信は検証していない。CXLプールは少数ノード共有を想定しており、カード数を固定したままランク数を増やすと競合が急増する。現行GPUは転送方向ごとにDMAエンジンが一つで、複数CXL機器を並列に置いても単一GPUがPCIe Gen5 x16を完全には使えない。小メッセージではCUDAコピー起動・同期の固定費が大きく、InfiniBandより遅くなる場合がある。AllReduceではリング型の中間削減再利用がなく拡張性が弱い。
## 実装状態
NCCL 2.28.3上の1020行実装で、3〜12ノードの実機CXL環境とH100で評価されている。論文は研究用途でByteDance技術へ未導入と明記する。公開ソースコードURLは一次資料から確認できなかった。
## 研究上の位置づけ
LLMシステムの観点では、GPUメモリ階層そのものより、複数ノードへ広がった学習・推論の通信ボトルネックをCXLメモリプールで置換する研究に位置する。CXLをKVキャッシュや重みの退避先として使う系統と相補的で、同じ共有プールを容量資源だけでなく通信資源として活用できる可能性を示す。一方で大規模クラスタのInfiniBandを全面代替する証拠ではなく、少数ノード・大きな転送・十分なCXLカード帯域という適用範囲を明確に見る必要がある。
