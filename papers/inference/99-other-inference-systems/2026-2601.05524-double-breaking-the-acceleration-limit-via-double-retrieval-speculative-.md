# Double：ドラフト・ターゲット双方の検索を使う並列投機的復号

## 概要

Doubleは、並列投機的復号（Parallel Speculative Decoding; PSD）における二つの性能制約を同時に解く。第一に、小さいドラフトモデルが自己回帰的に一度に1トークンずつ候補を作る限り、ターゲットモデルの1回の検証中に作れる候補長は両モデルの速度比で制限される。第二に、長い候補列の途中で誤ったトークンが出ると、そこから先のドラフト計算が無駄になり、並列処理が停止する。Doubleはドラフト側で過去の文脈から複数トークンの句を反復検索し、ターゲット側でも高精度な句を検索して事前検証・修正・延長に利用する。

この方式は、ドラフト用の追加学習を必要としない。貪欲復号ではターゲットが選ぶトークン列を維持し、確率的復号では棄却後の残差分布による補正を用いてターゲット分布を保つ。原著の8基のNVIDIA A100 80GBによる実験では、LLaMA3.3-70BのHumanEvalで通常のターゲット推論に対して5.33倍、Qwen3-32Bでは2.84倍の実時間高速化を示す。LLaMA3.3-70Bの5課題平均は4.27倍であり、最大値5.33倍を全課題の平均と取り違えてはならない。

## 問題設定：並列化しても残る速度上限

標準的な投機的復号では、軽量なドラフトモデルが`γ`個の候補トークンを順に生成し、大きなターゲットモデルがそれらをまとめて検証する。ターゲット分布`p`とドラフト分布`q`に基づいて各候補を受理または棄却することで、出力分布を変えずにターゲットの前向き計算回数を減らせる。しかし、ドラフトの生成とターゲットの検証を交互に実行すると、片方が動く間もう片方は待機する。

並列投機的復号では、ターゲットが前ラウンドを検証している間にドラフトが次ラウンドを生成する。ここでターゲットの1トークン計算時間を`T_p`、ドラフトの1トークン計算時間を`T_q`とし、速度比を`C=T_p/T_q`と定義する。ドラフトが自己回帰である限り、ターゲットが1回検証する間にドラフトが作れるトークン数はおおむね`C`以下である。原著の定理3は標準PSDの高速化`S_PSD`に`S_PSD≤C`という上界があることを示す。受理率を改善するだけでは、この生成速度上限を越えられない。

さらに、ドラフトが長い候補を作っても、先頭付近で誤ったトークンが出れば後続候補はまとめて棄却される。ターゲットだけで検索すれば正確な継続列を得やすいが、重いターゲット計算が残る。ドラフトだけで検索すれば高速に長い列を得られるが、小さいモデルの文脈判断が不正確で受理率が落ちる。Doubleはこの検索精度と効率の交換条件を、両側に異なる役割を与えることで解く。

## 手法

### ドラフト側の反復句検索

ドラフト側は、現在の文脈末尾に一致する連続語列（n-gram）を索引から探し、そこに続く複数トークンを一度に候補として取り出す。検索で得た句を現在の候補列へ連結し、その更新後の文脈を使って再度検索する。1回の検索で得られた句を次の検索条件へ反映するため、候補列は枝分かれする木ではなく、一本の線形な系列として伸びる。

標準PSDではドラフトの1回の自己回帰計算で1トークンしか増えない。Doubleでは同程度の時間で1回の句検索を実行し、平均一致長を`AMT`とすると、ターゲット1回の検証時間内に`C`回程度の検索を繰り返して、候補長を概ね`C×(1+AMT)`へ伸ばせる。例えば検索で平均2トークン程度の継続句が得られれば、ドラフトの1回の処理に対応する提案長が増える。ただしこれは理論的な長さの近似であり、実際の高速化は検索費用、受理率、ターゲット検証時間によって決まる。

線形候補列を使うことには実装上の利点がある。複数の枝を同時検証する木構造投機的復号では、候補の親子関係に対応した特殊な注意マスクが必要になることがある。Doubleは一本の列として候補を構成するため、通常の注意計算へ載せやすい。一方で、句検索に使える一致が少ない入力では`AMT`が小さくなり、自己回帰ドラフトに対する長さの利点も減る。

### ターゲット検証とドラフト生成の同期並列実行

各ラウンドで、ターゲットは前ラウンドの候補列を検証し、その間にドラフトは次の候補列を反復検索で作る。ターゲットの検証が終わるまでドラフトが待つのではなく、次ラウンドの準備を並列に進める。検索によって候補列が長くなると、同じ検証回数で確定できるトークン数を増やせる。ただしターゲットが候補を早い位置で棄却すると、ドラフトが先行して作った後続部分を捨てる必要があるため、並列化だけでは計算の無駄はなくならない。

この問題に対し、Doubleはターゲット側も検索を実行する。ターゲットの検索結果は、ドラフト側が予測した列の正しさを早期に見積もるための複数トークンの案内として使う。ドラフト側の高速な候補生成とターゲット側の精度の高い継続列を、別々の役割で同時に使う点が方式の核となる。

### ターゲット側の複数トークン事前検証と前方誘導

ターゲット側は、確定済みの文脈を用いて一度検索し、複数トークンの継続列`Y_p`を得る。これをドラフトの候補列`X_q`と比較し、どこまでが受理可能かを早期に判定する。通常の並列方式では候補`x_i`が棄却されると、それ以降の候補を捨て、次のドラフト計算を待つ。Doubleでは、ターゲット検索で得られた継続列の対応位置から後ろを利用して、誤った位置を修正しつつ確定列を伸ばせる。

原著図4の例では、ドラフトが第7位置で不適切な語を出したとき、ターゲット検索列に含まれるより妥当な語で置き換え、その後続の複数語も連結する。これは単に誤候補を一つ修正するだけではなく、ターゲット側で既に得られた高精度の継続句を利用して、棄却によるパイプラインの空白を短縮する操作である。ターゲットの検索列がドラフト列より長ければ、修正が不要な場合でも後ろへ延長できる。

ただし「損失なし」は、ターゲット分布を維持する検証・補正規則を守る場合の主張である。貪欲復号でターゲットが選ばない語を無条件に出力するわけではない。確率的サンプリングでは、棄却した位置の補正語を`norm(max(0,p-q))`の残差分布から採り、棄却位置以降のターゲット案内列は破棄する。したがって確率的復号では前方誘導を貪欲復号と同じように無条件で使えるわけではなく、速度上の利益も条件で変わる。

### 階層的な検索データストア

検索型復号では、推論開始直後の履歴が短いと一致する句が見つかりにくい。逆に巨大な外部検索索引を使えばメモリと検索費用が増える。Doubleは汎用対話データから作った小さなn-gram索引を初期知識として用意し、ユーザープロンプトと生成中の履歴を同じ検索空間へ統合する。ドラフトとターゲットはこの索引を共有し、別々の索引を保持して同期する費用を減らす。

生成が進むと、ターゲットが検証して確定したトークンを優先的に履歴へ取り込む一方、棄却された候補も検索の多様性のために活用する。初期の汎用索引だけに依存するのでも、現在の要求の履歴だけに依存するのでもない。検索深さを増やしすぎると、遠い位置の候補ほど文脈一致の精度が落ちる。原著の感度評価では深さ10を超えると平均受理長の改善が飽和し、高速化も安定して増えないため、深さ10を代表的な設定とする。

### 理論上の高速化上限をどう変えるか

標準PSDの上限`C`は、ドラフトが1トークンずつ自己回帰で生成するという前提から生じる。Doubleではドラフト1回の処理が複数トークンの句を生み、同じ時間で作れる候補数が増える。原著はこの効果を`C'=C(1+AMT)`という実効的な速度比で表し、ターゲット側の追加の確定トークンを加えた高速化式を導く。これは標準PSDの定理に反するのではなく、その定理が置いたドラフトの生成単位を変更するために別の上限へ移るという意味である。

この理論式は、検索一致長と並列処理の重なりを明示するが、現実の高速化を完全に決定するものではない。検索索引へのアクセス、ターゲット検証のバッチ効率、候補の棄却位置、装置間の同期、メモリ制約も実行時間へ影響する。したがって理論上の上限突破と、実測の壁時計時間の改善は別々に確認する必要がある。

## 評価

### 実験条件

| 項目 | 原著の設定 |
|---|---|
| GPU | NVIDIA A100 80GBを8基使用 |
| モデル対 | LLaMA-2 7B/70B、LLaMA-3系8B/70B、DeepSeek-Coder 1.3B/33B、Qwen3 0.6B/14B/32Bなど |
| 課題 | HumanEval（コード）、GSM8K（算数）、CNN/DM（要約）、Alpaca（指示）、MT-Bench（対話） |
| 比較方式 | 標準投機的復号、PLD、Token Recycling、Ouroboros、PEARL、EAGLE-3など |
| 主な復号条件 | 貪欲復号。確率的サンプリングの追加評価では温度1.0 |
| 指標 | 元のターゲット推論に対する実時間高速化と、連続して受理した平均トークン数 |
| ドラフト長 | 速度比`C`を基に`γ=ceil(C)`で設定 |

高速化倍率はターゲット単独の実時間を基準とする。平均受理長は1回の検証で確定できるトークンの長さを示すが、それだけでは転送・検索・同期の費用を表せない。二つの指標を別に見る必要がある。

### 代表的な実時間結果

| ターゲットと課題 | Double | 主な比較 | 読み取り |
|---|---:|---:|---|
| LLaMA3.3-70B、HumanEval | 5.33倍 | EAGLE-3 4.56倍、PEARL 4.39倍 | 追加学習なしでも高い速度を達成 |
| LLaMA3.3-70B、5課題平均 | 4.27倍 | EAGLE-3 3.99倍、PEARL 3.55倍 | 最大値と平均値を区別する |
| Qwen3-32B、HumanEval | 2.84倍 | EAGLE-3 2.27倍、PEARL 2.35倍 | 比較的低い速度比でも改善 |
| Qwen3-32B、5課題平均 | 2.33倍 | EAGLE-3 2.11倍、PEARL 1.92倍 | 課題全体でも改善 |
| DeepSeek-Coder-33B、5課題平均 | 4.05倍 | PEARL 3.03倍、Ouroboros 2.79倍 | ドラフト・ターゲット双方の検索が効く |
| LLaMA2-70B、HumanEval | 3.42倍 | Ouroboros 2.08倍 | ドラフト側だけの検索より受理を改善 |
| Qwen3-14B、CNN/DM | 1.89倍 | PEARL 1.28倍、速度比Cは約1.6 | 従来PSDの速度上限を越える例 |

LLaMA3.3-70BのHumanEvalでは、Doubleの連続平均受理長は14.35トークン、PEARLは10.69トークンである。受理長の増加はターゲット検証1回当たりの確定量が増えることを示すが、同じ倍率で実行時間が短くなるわけではない。実時間では5.33倍対4.39倍となる。Qwen3-14BのCNN/DMでは、速度比`C≈1.6`に対してDoubleが1.89倍を達成し、自己回帰ドラフトに基づく標準PSDの上限を越えるという理論上の狙いを具体的に裏付ける。

### 構成要素除去と検索深さ

原著のLLaMA3.3-70Bでの構成要素除去実験では、ドラフト側検索を除くとHumanEvalの高速化が5.33倍から4.50倍へ低下する。これはドラフト側の句検索が提案長の制約を緩めている証拠である。ターゲット側検索を除くと連続平均受理長が14.35から11.5へ低下し、誤候補の途中棄却を緩和する効果が失われる。二つの検索は同じ役割を重複させているのではなく、提案速度と受理精度を別々に補強している。

検索深さ`d`を増やすと初めは平均受理長が増えるが、深さ10を超えると飽和し、高速化倍率も単調に増えなくなる。長い候補の後半ほど一致の確率が下がり、検索・検証に費やした費用を回収しにくくなるためである。これは「検索を深くすれば無制限に高速化する」という誤解を防ぐ負の結果であり、原著は深さ10を実用的な均衡点として選ぶ。

### 確率的復号と損失なしの条件

温度1.0の確率的サンプリングでも、LLaMA3.3-70BのHumanEvalでDoubleは4.70倍、5課題平均では3.77倍を示す。比較対象の平均はEAGLE-3が3.71倍、PEARLが3.34倍である。Qwen3-32Bの5課題平均はDoubleが2.06倍、EAGLE-3が1.96倍、PEARLが1.81倍となる。貪欲復号の5.33倍を温度1.0の条件にそのまま転記してはならない。

確率的復号では、ドラフトとターゲットの分布が異なる位置で棄却した後、残差分布から補正語を採る必要がある。その場合、ターゲット検索で得た後続語を無条件に追加できない。原著はこの制約を明示したうえで分布を保つ検証を実装している。出力品質を維持するという主張は、確率的サンプリングでターゲット分布を維持することと、貪欲復号でターゲットと同じ選択をすることを区別して理解する必要がある。

## 既存方式との差

標準投機的復号はドラフト生成後に検証を行い、両段階の待ち時間が発生する。PEARLなどの並列方式は両者を重ねるが、ドラフトが自己回帰的に候補を作るため速度比`C`の制約を受ける。Ouroborosはドラフト側の検索で候補を長くするが、ターゲットによる複数トークンの案内を持たないため途中棄却が増える。PLDやToken Recyclingなどターゲット側だけの検索は高精度でも重いターゲット計算を置き換えにくい。

Doubleは、ドラフト側で高速な句検索を反復し、ターゲット側で高精度な検索列を生成し、二つを並列に組み合わせる。EAGLE-3のような専用ドラフトの学習を要しない点も異なる。ただし学習不要であることは、索引構築や検索処理に一切の費用がないことを意味しない。初期のn-gram索引と生成履歴を管理するためのメモリ・処理費用が発生する。

## 限界と負の結果

検索で再利用できる句が少ないコード・数学・対話の領域では、平均一致長`AMT`が小さくなり、候補長の拡張効果が縮む。長く検索しすぎると候補後半の一致精度が下がるため、検索深さ10を超えても高速化が伸びない。途中棄却が多い場合は、ドラフトが作った後続候補が無駄になり、同期並列実行の利点も減る。

原著の主評価は8基のA100 80GBと特定のドラフト・ターゲット対による実測である。索引の格納場所、GPUメモリ余裕、検索遅延、通信帯域、同時要求数が異なる環境へ同じ倍率を保証するものではない。確率的サンプリングでは分布を維持するために棄却後のターゲット案内を破棄するので、貪欲復号と同じ延長効果を期待できない。ターゲットとドラフトの速度比が小さい場合、検索の利得が相対的に重要になるが、検索そのものが遅ければ逆効果になり得る。

Doubleの理論上の上限突破は、標準PSDの自己回帰ドラフトという前提を変更した結果である。`C(1+AMT)`は提案長を表す実効的な速度比のモデルであり、あらゆる実装でその倍率まで必ず速くなるという意味ではない。原著は複数の実機条件で実時間を測定しているが、低速なCPU索引、異なるメモリ階層、極端な同時処理負荷での普遍的な保証ではない。
