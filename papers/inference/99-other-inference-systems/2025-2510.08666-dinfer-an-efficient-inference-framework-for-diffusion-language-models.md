# dInfer: An Efficient Inference Framework for Diffusion Language Models

> dLLMの反復denoise・並列token確定・更新され続けるKVをモジュール化し、decoder/KV管理とGPU実行系を同時最適化するdInfer。

## 概要

通常の自己回帰LLMは、確定した過去tokenを変更せず、次tokenだけを1つずつ追加する。この因果構造のおかげで、過去tokenのKey/Valueは一度計算すればKVキャッシュへ固定して再利用できる。一方、Diffusion Language Model（拡散型言語モデル; dLLM）は複数の[MASK]位置を含む系列全体を何度もforwardし、各iterationで高確信tokenを確定しながら残りを再予測する。

この方式には「1回のforwardで複数tokenを確定できる」という大きな並列性があるが、AR LLMとは異なる3つの実装問題がある。第一に、1回のiterationで何token確定するかが少ないと、何十回もTransformerを回すためparallel decodingの利点が消える。第二にbidirectional attentionでは、ある[MASK]が実tokenへ変わると周囲tokenのrepresentationも変わるため、AR LLMのように過去KVを永久固定できない。第三に短いdiffusion iterationをPython loopで多数実行すると、kernel launchやstream同期の隙間がGPUを遊ばせる。

dInferはこのdLLM特有の問題を、**model / diffusion iteration manager / decoding strategy / KV-cache management**の4コンポーネントに分ける。アルゴリズム側ではIteration Smoothing、Hierarchical Decoding、Credit Decoding、Vicinity KV-cache Refreshを提供し、実行系ではtensor/expert parallelism、torch.compile、CUDA Graph、diffusion loop unrollingを組み合わせる。

8×H800、batch size 1、generation 1024、block size 64のLLaDA-MoE評価では、KV cacheありで平均680.71 tokens/sを達成し、Fast-dLLMの110.98 tokens/sより約6倍、同程度の品質を揃えた比較ではFast-dLLMの63.61 tokens/sに対して10倍超となる。Trajectory DistillationしたLLaDA-MoE-TDでは平均847.22 tokens/s、HumanEvalで1125.67 tokens/sまで上がる。

## 問題設定

### dLLMの「parallel」は、1 forwardで何token確定できるかで決まる

dLLMは全[MASK]位置のlogitsを同時に計算できる。しかし全部を一度にargmax確定すると、互いに依存するtokenを独立とみなすため文意が崩れやすい。そこで実際にはconfidenceの高い一部tokenだけを確定し、残りは次iterationでもう一度予測する。

この効率をdInferは **TPF（Tokens Per Forward）** で測る。1回のmodel forwardにつき平均何tokenを最終確定できたかという指標で、AR modelは原則1である。TPFが4なら、同じ長さを生成するのに必要なforward回数を理想的には約1/4へ減らせる。

ただしTPFを無理に上げると低confidence tokenまで同時確定し、品質が落ちる。dInferのdecoder設計は「同時に多く確定する」と「token間依存を壊さない」の間を調整する。

### dLLMではKVが「古くなる」

AR modelでは位置iが確定した後、そのrepresentationは将来tokenからattentionされても内容自体は変わらない。dLLMはbidirectional attentionなので、周囲の[MASK]がtokenへ変わると、位置iのhidden stateも本来は再計算した方がよい。

全iterationで全KVを再計算すれば正確だが高価である。逆に既存KVを固定再利用すると、周囲の最新情報を反映していない**stale cache**になり品質が落ちる。dInferは「どこまで再計算すれば新しいtokenの影響を十分取り込めるか」を局所更新問題として扱う。

## 手法

### 1. 4コンポーネントへ分離してdLLMの設計空間を組み替え可能にする

dInferの推論loopでは、iteration managerが次のactive blockを選び、KV managerが更新要否を判断し、modelがlogitsを計算し、decoderが今回確定する[MASK]位置を決める。

この分離により、例えば同じLLaDA-MoEへ「threshold decoder + vicinity cache」や「hierarchical decoder + iteration smoothing」を差し替えて比較できる。dLLM研究ではmodel変更、decode規則、KV最適化、system optimizationが一体化しやすいため、同じframework上で組合せを評価できること自体が貢献の一部である。

### 2. Iteration Smoothing — 捨てていたlogits分布を次iterationへ渡す

通常のdiffusion decodingでは、confidence閾値を超えなかった[MASK]位置のlogitsは、そのiterationではtoken確定に使われず捨てられる。しかし「dog 45%、cat 40%」のような分布には次stepへ有用な情報が含まれる。

Iteration Smoothingは、未確定位置のsoftmax分布をinput embedding行列で期待embeddingへ変換し、次iterationの[MASK] embeddingへ少量加える。初期stepでは混合係数を小さくし、後になるほど増やすため、序盤の不確かな分布を強く信じ過ぎない。

新しいparameterやretrainingは不要で、論文では1 iteration当たりに確定できるtoken数を30〜40%増やし、品質も改善すると報告する。単なるtemporal cacheではなく、前iterationの**distribution-level information**を次入力へ残す仕組みである。

### 3. Hierarchical Decoding — masked spanを再帰分割して離れた位置から確定する

一度に隣接tokenを多く確定すると、それら同士の依存を無視しやすい。Hierarchical Decodingはmasked spanを再帰的に小領域へ分割し、各領域からconfidenceの高いtokenを少なくとも1つずつ選ぶ。

結果として確定位置が空間的に散らばり、隣接した不確定tokenを同時に決めるよりlocal dependencyを弱める。さらに中央付近を順次確定できれば、未解決spanが左右に分割され、理想条件ではiteration数を対数的に縮める方向へ働く。

これはmodel retraining不要のdecode policyであり、同じlogitsから「どの位置を確定するか」を変える。

### 4. Credit Decoding — 一瞬のconfidenceではなく複数stepの安定性を見る

Threshold decodingは現在iterationのconfidenceだけでtokenを確定する。ところが、毎step同じtokenが首位なのに0.9 thresholdへ少し届かない位置は、何度もre-maskされ無駄に再計算される。

Credit Decodingは位置i・候補token vごとに履歴creditを持ち、あるtokenが継続してtop candidateになるとcreditを蓄積する。古いcreditにはdiscountを掛け、一時的な誤予測が永久に残らないようにする。

確定前にはlogitへ (log(1+C)) 型のbonusを加える。現在confidenceが中程度でも複数iterationで一貫したtokenは早く確定し、瞬間的に高いだけで候補が揺れる位置は慎重に残す。KVなしablationでは平均TPFがthreshold 3.67、hierarchical 3.89に対しCredit 4.29だった。

### 5. Vicinity KV-cache Refresh — 変更位置の「近傍」だけ再計算する

static KV reuseでは、新しく確定したtokenの情報が周囲cached statesへ反映されない。全sequence refreshは高価である。

dInferは現在decodeしているblockの[MASK]と、その前後の小さいvicinity windowだけK/Vを再計算する。blockが完全確定した時点ではfull cache updateを行い、長期間のずれをリセットする。

主設定では前後16 tokenのvicinityを使う。これは「cacheを一切変えない」と「毎iteration全再計算」の中間で、semantic changeが局所的に強いという仮定を利用する。

### 6. GPU実行系 — 短いiterationを連続して流す

dInferはvLLM backend上でTensor Parallelism（TP）とExpert Parallelism（EP）を併用する。LLaDA-MoEではbatch size 1でも1回のdiffusion forward内に多数token位置が存在するため、AR decodeのbatch 1よりexpert parallelismを使いやすい。

さらにtorch.compileでkernel fusionし、CUDA Graphへ載せてPython/kernel launch overheadを削る。TP+EP条件ではこのcompiler optimizationが200%以上の効率改善をもたらすとされる。

diffusion iteration間にはCUDA streamのidle gapが生じやすいため、loop unrollingでPython側が次iteration kernelを連続launchできるようにする。これで5〜10%改善する。block内でEOSが出た場合は後続blockを処理せず終了し、15〜40%の追加削減を得るケースもある。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| GPU | 8× NVIDIA H800 |
| software | PyTorch 2.9 dev、vLLM 0.10.1 |
| batch size | 1 |
| generation length | 1024 |
| block size | 64 |
| model | LLaDA-MoE、LLaDA-MoE-TD |
| AR比較 | Qwen2.5-3B on vLLM |
| dLLM比較 | Fast-dLLM |
| task | CRUX-O、GSM8K、HumanEval、IFEval、MBPP、LiveCodeBench v6 |
| 指標 | Perf、TPF、TPS |

TPFは1 model forward当たりの確定token数、TPSは1秒当たりの生成token数である。TPFが高くても1 forwardが重ければTPSは上がらないため、algorithmic parallelismと実装速度を分けて読む必要がある。

### LLaDA-MoE

| 構成 | 平均Perf | 平均TPF | 平均TPS |
|---|---:|---:|---:|
| Qwen2.5-3B / vLLM | 54.44 | 1.00 | 277.45 |
| Fast-dLLM / KVなし | 53.52 | 2.82 | 63.61 |
| dInfer / KVなし | 54.33 | 4.29 | 407.36 |
| Fast-dLLM / KVあり | 52.15 | 2.46 | 110.98 |
| dInfer / KVあり | 53.96 | 3.87 | 680.71 |

Fast-dLLMはparallel decodingでTPF>1を得ても、1 forwardのsystem costが高く、AR QwenよりTPSが低い条件がある。dInferはTPFを3〜4台へ上げるだけでなく、TP/EP・compile・cache・loop実装を同時に短縮することで680.71 TPSへ到達する。

同程度の品質を揃えた論文比較ではFast-dLLM 63.61 TPSに対しdInfer 680.71 TPSで10倍超となる。HumanEvalでは1011.12 TPSを記録する。

### Trajectory Distillationとの組合せ

LLaDA-MoE-TDは、良いdiffusion decoding trajectory中の離れたstate間を直接予測するようfine-tuneし、1 forwardでより大きく[MASK]を減らせるmodel variantである。

これをdInferのhierarchical decoding、vicinity refresh、iteration smoothing等と組み合わせると平均TPF 5.67、平均847.22 TPSとなり、HumanEvalは1125.67 TPSへ達する。framework側だけでなく、model自体のparallel decode能力を上げると利得をさらに積み増せることを示す。

## 既存研究との差

Fast-dLLMなど先行dLLM高速化はthreshold decodingやDual Cacheを導入するが、decode policy、iteration間状態、cache freshness、GPU executionを個別に最適化する傾向がある。

dInferはこれらを4コンポーネントへ分離し、**1 forwardでより多くtokenを確定するalgorithmic optimizationと、1 forwardそのものを短くするsystem optimizationを同じframeworkで積み上げる**。またTPFとTPSを同時に示すことで、「parallelismは増えたがkernel実行が遅い」というケースを区別している。

## 限界

dLLMのKV再利用は本質的に近似である。Vicinity Refreshは変更の影響が主に近傍へ強く現れるという仮定に依存し、遠距離依存が強いtaskではwindow外のstale statesが品質へ影響する可能性がある。block完了時のfull refreshはこの誤差を抑える一方、追加計算になる。

Hierarchical/Credit/Thresholdのどれが最適かもmodelとcache設定で変わる。実際ablationではKVありLLaDA-MoEではthresholdが品質とTPFのバランスで採用され、KVなしではCredit、distilled modelではHierarchicalが使われる。単一decoderが常に最良ではない。

評価は8×H800、batch 1を中心としている。高batchではAR model側もGPU利用率が上がるため「dLLMがARより速い」という相対差は変わり得る。またLLaDA系以外のdiffusion architectureで同じcache localityやparallelismが得られるかは別途検証が必要である。
