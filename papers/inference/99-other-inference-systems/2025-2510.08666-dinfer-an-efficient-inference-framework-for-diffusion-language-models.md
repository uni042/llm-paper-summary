# dInfer: An Efficient Inference Framework for Diffusion Language Models

> dLLMの反復denoise・並列トークン確定・更新され続けるKVをモジュール化し、decoder/KV管理とGPU実行系を同時最適化するdInfer。

## 概要

通常の自己回帰LLMは、確定した過去トークンを変更せず、次トークンだけを1つずつ追加する。この因果構造のおかげで、過去トークンのKey/Valueは一度計算すればKVキャッシュへ固定して再利用できる。一方、Diffusion Language Model（拡散型言語モデル; dLLM）は複数の[MASK]位置を含む系列全体を何度も順伝播し、各iterationで高確信トークンを確定しながら残りを再予測する。

この方式には「1回の順伝播で複数トークンを確定できる」という大きな並列性があるが、AR LLMとは異なる3つの実装問題がある。第一に、1回のiterationで何トークン確定するかが少ないと、何十回もTransformerを回すため並列 復号の利点が消える。第二にbidirectional 注意機構では、ある[MASK]が実トークンへ変わると周囲トークンのrepresentationも変わるため、AR LLMのように過去KVを永久固定できない。第三に短いdiffusion iterationをPython loopで多数実行すると、カーネル launchやストリーム同期の隙間がGPUを遊ばせる。

dInferはこのdLLM特有の問題を、**モデル / diffusion iteration manager / 復号 戦略 / KV-キャッシュ management**の4コンポーネントに分ける。アルゴリズム側ではIteration Smoothing、Hierarchical Decoding、Credit Decoding、Vicinity KV-キャッシュ Refreshを提供し、実行系ではテンソル/専門家 並列化、torch.compile、CUDA Graph、diffusion loop unrollingを組み合わせる。

8×H800、バッチ サイズ 1、generation 1024、block サイズ 64のLLaDA-MoE評価では、KV キャッシュありで平均680.71 トークン/sを達成し、Fast-dLLMの110.98 トークン/sより約6倍、同程度の品質を揃えた比較ではFast-dLLMの63.61 トークン/sに対して10倍超となる。Trajectory DistillationしたLLaDA-MoE-TDでは平均847.22 トークン/s、HumanEvalで1125.67 トークン/sまで上がる。

## 問題設定

### dLLMの「parallel」は、1 forwardで何token確定できるかで決まる

dLLMは全[MASK]位置のlogitsを同時に計算できる。しかし全部を一度にargmax確定すると、互いに依存するトークンを独立とみなすため文意が崩れやすい。そこで実際にはconfidenceの高い一部トークンだけを確定し、残りは次iterationでもう一度予測する。

この効率をdInferは **TPF（Tokens Per Forward）** で測る。1回のモデル 順伝播につき平均何トークンを最終確定できたかという指標で、AR モデルは原則1である。TPFが4なら、同じ長さを生成するのに必要な順伝播回数を理想的には約1/4へ減らせる。

ただしTPFを無理に上げると低confidence トークンまで同時確定し、品質が落ちる。dInferのdecoder設計は「同時に多く確定する」と「トークン間依存を壊さない」の間を調整する。

### dLLMではKVが「古くなる」

AR モデルでは位置iが確定した後、そのrepresentationは将来トークンから注意機構されても内容自体は変わらない。dLLMはbidirectional 注意機構なので、周囲の[MASK]がトークンへ変わると、位置iの隠れ 状態も本来は再計算した方がよい。

全iterationで全KVを再計算すれば正確だが高価である。逆に既存KVを固定再利用すると、周囲の最新情報を反映していない**stale キャッシュ**になり品質が落ちる。dInferは「どこまで再計算すれば新しいトークンの影響を十分取り込めるか」を局所更新問題として扱う。

## 手法

### 1. 4コンポーネントへ分離してdLLMの設計空間を組み替え可能にする

dInferの推論loopでは、iteration managerが次の活性 blockを選び、KV managerが更新要否を判断し、モデルがlogitsを計算し、decoderが今回確定する[MASK]位置を決める。

この分離により、例えば同じLLaDA-MoEへ「threshold decoder + vicinity キャッシュ」や「hierarchical decoder + iteration smoothing」を差し替えて比較できる。dLLM研究ではモデル変更、デコード規則、KV最適化、システム optimizationが一体化しやすいため、同じフレームワーク上で組合せを評価できること自体が貢献の一部である。

### 2. Iteration Smoothing — 捨てていたlogits分布を次iterationへ渡す

通常のdiffusion 復号では、confidence閾値を超えなかった[MASK]位置のlogitsは、そのiterationではトークン確定に使われず捨てられる。しかし「dog 45%、cat 40%」のような分布には次stepへ有用な情報が含まれる。

Iteration Smoothingは、未確定位置のsoftmax分布を入力 embedding行列で期待embeddingへ変換し、次iterationの[MASK] embeddingへ少量加える。初期stepでは混合係数を小さくし、後になるほど増やすため、序盤の不確かな分布を強く信じ過ぎない。

新しいパラメータやretrainingは不要で、論文では1 iteration当たりに確定できるトークン数を30〜40%増やし、品質も改善すると報告する。単なるtemporal キャッシュではなく、前iterationの**distribution-level information**を次入力へ残す仕組みである。

### 3. Hierarchical Decoding — masked spanを再帰分割して離れた位置から確定する

一度に隣接トークンを多く確定すると、それら同士の依存を無視しやすい。Hierarchical Decodingはmasked spanを再帰的に小領域へ分割し、各領域からconfidenceの高いトークンを少なくとも1つずつ選ぶ。

結果として確定位置が空間的に散らばり、隣接した不確定トークンを同時に決めるより局所 依存関係を弱める。さらに中央付近を順次確定できれば、未解決spanが左右に分割され、理想条件ではiteration数を対数的に縮める方向へ働く。

これはモデル retraining不要のデコード policyであり、同じlogitsから「どの位置を確定するか」を変える。

### 4. Credit Decoding — 一瞬のconfidenceではなく複数stepの安定性を見る

Threshold 復号は現在iterationのconfidenceだけでトークンを確定する。ところが、毎step同じトークンが首位なのに0.9 thresholdへ少し届かない位置は、何度もre-maskされ無駄に再計算される。

Credit Decodingは位置i・候補トークン vごとに履歴creditを持ち、あるトークンが継続してtop candidateになるとcreditを蓄積する。古いcreditにはdiscountを掛け、一時的な誤予測が永久に残らないようにする。

確定前にはlogitへ (log(1+C)) 型のbonusを加える。現在confidenceが中程度でも複数iterationで一貫したトークンは早く確定し、瞬間的に高いだけで候補が揺れる位置は慎重に残す。KVなしablationでは平均TPFがthreshold 3.67、hierarchical 3.89に対しCredit 4.29だった。

### 5. Vicinity KV-cache Refresh — 変更位置の「近傍」だけ再計算する

静的 KV reuseでは、新しく確定したトークンの情報が周囲cached statesへ反映されない。全系列 refreshは高価である。

dInferは現在デコードしているblockの[MASK]と、その前後の小さいvicinity windowだけK/Vを再計算する。blockが完全確定した時点ではfull キャッシュ 更新を行い、長期間のずれをリセットする。

主設定では前後16 トークンのvicinityを使う。これは「キャッシュを一切変えない」と「毎iteration全再計算」の中間で、semantic changeが局所的に強いという仮定を利用する。

### 6. GPU実行系 — 短いiterationを連続して流す

dInferはvLLM backend上でTensor Parallelism（TP）とExpert Parallelism（EP）を併用する。LLaDA-MoEではバッチ サイズ 1でも1回のdiffusion 順伝播内に多数トークン位置が存在するため、AR デコードのバッチ 1より専門家 並列化を使いやすい。

さらにtorch.compileでカーネル 融合し、CUDA Graphへ載せてPython/カーネル launch オーバーヘッドを削る。TP+EP条件ではこのコンパイラ optimizationが200%以上の効率改善をもたらすとされる。

diffusion iteration間にはCUDA ストリームのidle gapが生じやすいため、loop unrollingでPython側が次iteration カーネルを連続launchできるようにする。これで5〜10%改善する。block内でEOSが出た場合は後続blockを処理せず終了し、15〜40%の追加削減を得るケースもある。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| GPU | 8× NVIDIA H800 |
| software | PyTorch 2.9 dev、vLLM 0.10.1 |
| バッチ サイズ | 1 |
| generation length | 1024 |
| block サイズ | 64 |
| モデル | LLaDA-MoE、LLaDA-MoE-TD |
| AR比較 | Qwen2.5-3B on vLLM |
| dLLM比較 | Fast-dLLM |
| タスク | CRUX-O、GSM8K、HumanEval、IFEval、MBPP、LiveCodeBench v6 |
| 指標 | Perf、TPF、TPS |

TPFは1 モデル 順伝播当たりの確定トークン数、TPSは1秒当たりの生成トークン数である。TPFが高くても1 順伝播が重ければTPSは上がらないため、algorithmic 並列化と実装速度を分けて読む必要がある。

### LLaDA-MoE

| 構成 | 平均Perf | 平均TPF | 平均TPS |
|---|---:|---:|---:|
| Qwen2.5-3B / vLLM | 54.44 | 1.00 | 277.45 |
| Fast-dLLM / KVなし | 53.52 | 2.82 | 63.61 |
| dInfer / KVなし | 54.33 | 4.29 | 407.36 |
| Fast-dLLM / KVあり | 52.15 | 2.46 | 110.98 |
| dInfer / KVあり | 53.96 | 3.87 | 680.71 |

Fast-dLLMは並列 復号でTPF>1を得ても、1 順伝播のシステム コストが高く、AR QwenよりTPSが低い条件がある。dInferはTPFを3〜4台へ上げるだけでなく、TP/EP・compile・キャッシュ・loop実装を同時に短縮することで680.71 TPSへ到達する。

同程度の品質を揃えた論文比較ではFast-dLLM 63.61 TPSに対しdInfer 680.71 TPSで10倍超となる。HumanEvalでは1011.12 TPSを記録する。

### Trajectory Distillationとの組合せ

LLaDA-MoE-TDは、良いdiffusion 復号 trajectory中の離れた状態間を直接予測するようfine-tuneし、1 順伝播でより大きく[MASK]を減らせるモデル variantである。

これをdInferのhierarchical 復号、vicinity refresh、iteration smoothing等と組み合わせると平均TPF 5.67、平均847.22 TPSとなり、HumanEvalは1125.67 TPSへ達する。フレームワーク側だけでなく、モデル自体の並列 デコード能力を上げると利得をさらに積み増せることを示す。

## 既存研究との差

Fast-dLLMなど先行dLLM高速化はthreshold 復号やDual Cacheを導入するが、デコード policy、iteration間状態、キャッシュ freshness、GPU executionを個別に最適化する傾向がある。

dInferはこれらを4コンポーネントへ分離し、**1 順伝播でより多くトークンを確定するalgorithmic optimizationと、1 順伝播そのものを短くするシステム optimizationを同じフレームワークで積み上げる**。またTPFとTPSを同時に示すことで、「並列化は増えたがカーネル実行が遅い」というケースを区別している。

## 限界

dLLMのKV再利用は本質的に近似である。Vicinity Refreshは変更の影響が主に近傍へ強く現れるという仮定に依存し、遠距離依存が強いタスクではwindow外のstale statesが品質へ影響する可能性がある。block完了時のfull refreshはこの誤差を抑える一方、追加計算になる。

Hierarchical/Credit/Thresholdのどれが最適かもモデルとキャッシュ設定で変わる。実際ablationではKVありLLaDA-MoEではthresholdが品質とTPFのバランスで採用され、KVなしではCredit、distilled モデルではHierarchicalが使われる。単一decoderが常に最良ではない。

評価は8×H800、バッチ 1を中心としている。高バッチではAR モデル側もGPU利用率が上がるため「dLLMがARより速い」という相対差は変わり得る。またLLaDA系以外のdiffusion 構成で同じキャッシュ localityや並列化が得られるかは別途検証が必要である。
