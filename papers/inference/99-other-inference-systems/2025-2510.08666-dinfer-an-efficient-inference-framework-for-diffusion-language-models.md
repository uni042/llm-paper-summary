# dInfer: An Efficient Inference Framework for 拡散型言語モデル（拡散 Language Model）s

> 拡散型LLM（dLLM）の反復的な雑音除去（denoising）・並列トークン確定・更新され続けるKVをモジュール化し、デコーダ/KV管理とGPU実行系を同時最適化するdInfer。

## 概要

通常の自己回帰LLMは、確定した過去トークンを変更せず、次トークンだけを1つずつ追加する。この因果構造のおかげで、過去トークンのKey/Valueは一度計算すればKVキャッシュへ固定して再利用できる。一方、拡散型言語モデル（拡散 Language Model）（拡散型言語モデル; 拡散型LLM（dLLM））は複数の[MASK]位置を含む系列全体を何度も順伝播し、各反復で高確信トークンを確定しながら残りを再予測する。

この方式には「1回の順伝播で複数トークンを確定できる」という大きな並列性があるが、自己回帰LLMとは異なる3つの実装問題がある。第一に、1回の反復で何トークン確定するかが少ないと、何十回もTransformerを回すため並列 復号の利点が消える。第二に双方向注意機構（双方向 attention）では、ある[MASK]が実トークンへ変わると周囲トークンの表現も変わるため、自己回帰LLMのように過去KVを永久固定できない。第三に短い拡散反復をPython ループで多数実行すると、カーネル起動やストリーム同期の隙間がGPUを遊ばせる。

dInferはこの拡散型LLM（dLLM）特有の問題を、**モデル / 拡散反復管理器（拡散反復 manager） / 復号戦略 / KVキャッシュ管理**の4コンポーネントに分ける。アルゴリズム側では反復平滑化（Iteration Smoothing）、階層型復号（階層型 Decoding）、信用度復号（信用度 Decoding）、近傍KVキャッシュ更新（Vicinity KV-cache Refresh）を提供し、実行系ではテンソル/専門家 並列化、torch.コンパイル、CUDA Graph、拡散ループ unrollingを組み合わせる。

8×H800、バッチサイズ 1、生成 1024、ブロックサイズ 64のLLaDA-MoE評価では、KVキャッシュありで平均680.71 トークン/sを達成し、Fast-dLLMの110.98 トークン/sより約6倍、同程度の品質を揃えた比較ではFast-dLLMの63.61 トークン/sに対して10倍超となる。軌跡蒸留（Trajectory Distillation）したLLaDA-MoE-TDでは平均847.22 トークン/s、HumanEvalで1125.67 トークン/sまで上がる。

## 問題設定

### 拡散型LLMの並列性は、1回の順伝播で何トークン確定できるかで決まる

拡散型LLM（dLLM）は全[MASK]位置のロジットを同時に計算できる。しかし全部を一度に最大値選択（argmax）確定すると、互いに依存するトークンを独立とみなすため文意が崩れやすい。そこで実際には確信度の高い一部トークンだけを確定し、残りは次反復でもう一度予測する。

この効率をdInferは **TPF（Tokens Per Forward）** で測る。1回のモデル順伝播につき平均何トークンを最終確定できたかという指標で、自己回帰モデルは原則1である。TPFが4なら、同じ長さを生成するのに必要な順伝播回数を理想的には約1/4へ減らせる。

ただしTPFを無理に上げると低確信度 トークンまで同時確定し、品質が落ちる。dInferのデコーダ設計は「同時に多く確定する」と「トークン間依存を壊さない」の間を調整する。

### 拡散型LLM（dLLM）ではKVが「古くなる」

自己回帰モデルでは位置iが確定した後、その表現は将来トークンから注意機構されても内容自体は変わらない。拡散型LLM（dLLM）は双方向注意機構（双方向 attention）なので、周囲の[MASK]がトークンへ変わると、位置iの隠れ状態も本来は再計算した方がよい。

全反復で全KVを再計算すれば正確だが高価である。逆に既存KVを固定再利用すると、周囲の最新情報を反映していない**陳腐化キャッシュ（陳腐化した cache）**になり品質が落ちる。dInferは「どこまで再計算すれば新しいトークンの影響を十分取り込めるか」を局所更新問題として扱う。

## 手法

### 1. 4コンポーネントへ分離して拡散型LLM（dLLM）の設計空間を組み替え可能にする

dInferの推論ループでは、反復管理器が次の活性 ブロックを選び、KV管理器が更新要否を判断し、モデルがロジットを計算し、デコーダが今回確定する[MASK]位置を決める。

この分離により、例えば同じLLaDA-MoEへ「閾値 デコーダ + 近傍 キャッシュ」や「hierarchical デコーダ + 反復 smoothing」を差し替えて比較できる。拡散型LLM（dLLM）研究ではモデル変更、デコード規則、KV最適化、システム最適化が一体化しやすいため、同じフレームワーク上で組合せを評価できること自体が貢献の一部である。

### 2. 反復平滑化（Iteration Smoothing） — 捨てていたロジット分布を次反復へ渡す

通常の拡散復号では、確信度閾値を超えなかった[MASK]位置のロジットは、その反復ではトークン確定に使われず捨てられる。しかし「dog 45%、cat 40%」のような分布には次段階へ有用な情報が含まれる。

反復平滑化（Iteration Smoothing）は、未確定位置のソフトマックス分布を入力 埋め込み行列で期待埋め込みへ変換し、次反復の[MASK] 埋め込みへ少量加える。初期段階では混合係数を小さくし、後になるほど増やすため、序盤の不確かな分布を強く信じ過ぎない。

新しいパラメータや再学習は不要で、論文では1 反復当たりに確定できるトークン数を30〜40%増やし、品質も改善すると報告する。単なるtemporal キャッシュではなく、前反復の**分布レベル情報**を次入力へ残す仕組みである。

### 3. 階層型復号（階層型 Decoding） — マスク区間を再帰分割して離れた位置から確定する

一度に隣接トークンを多く確定すると、それら同士の依存を無視しやすい。階層型復号（階層型 Decoding）はマスク区間を再帰的に小領域へ分割し、各領域から確信度の高いトークンを少なくとも1つずつ選ぶ。

結果として確定位置が空間的に散らばり、隣接した不確定トークンを同時に決めるより局所依存関係を弱める。さらに中央付近を順次確定できれば、未解決区間が左右に分割され、理想条件では反復数を対数的に縮める方向へ働く。

これはモデル 再学習不要のデコード 方針であり、同じロジットから「どの位置を確定するか」を変える。

### 4. 信用度復号（信用度 Decoding） — 一瞬の確信度ではなく複数stepの安定性を見る

閾値 復号は現在反復の確信度だけでトークンを確定する。ところが、毎段階同じトークンが首位なのに0.9 閾値へ少し届かない位置は、何度も再マスクされ無駄に再計算される。

信用度復号（信用度 Decoding）は位置i・候補トークン vごとに履歴信用度を持ち、あるトークンが継続して最有力候補になると信用度を蓄積する。古い信用度には減衰率を掛け、一時的な誤予測が永久に残らないようにする。

確定前にはロジットへ (log(1+C)) 型の加点を加える。現在確信度が中程度でも複数反復で一貫したトークンは早く確定し、瞬間的に高いだけで候補が揺れる位置は慎重に残す。KVなしの構成要素除去実験では平均TPFが閾値 3.67、hierarchical 3.89に対し信用度 4.29だった。

### 5. Vicinity KV-cache Refresh — 変更位置の「近傍」だけ再計算する

静的 KV 再利用では、新しく確定したトークンの情報が周囲キャッシュ済み状態へ反映されない。全系列 更新は高価である。

dInferは現在デコードしているブロックの[MASK]と、その前後の小さい近傍窓だけK/Vを再計算する。ブロックが完全確定した時点では全体 キャッシュ 更新を行い、長期間のずれをリセットする。

主設定では前後16 トークンの近傍を使う。これは「キャッシュを一切変えない」と「毎反復全再計算」の中間で、意味変化が局所的に強いという仮定を利用する。

### 6. GPU実行系 — 短い反復を連続して流す

dInferはvLLM バックエンド上でテンソル並列（テンソル Parallelism）（TP）と専門家並列（専門家 Parallelism）（EP）を併用する。LLaDA-MoEではバッチサイズ 1でも1回の拡散順伝播内に多数トークン位置が存在するため、AR デコードのバッチ 1より専門家 並列化を使いやすい。

さらにtorch.コンパイルでカーネル融合し、CUDA Graphへ載せてPython/カーネル起動 オーバーヘッドを削る。TP+EP条件ではこのコンパイラ 最適化が200%以上の効率改善をもたらすとされる。

拡散反復間にはCUDA ストリームの待機間隔が生じやすいため、ループ展開（ループ unrolling）でPython側が次反復 カーネルを連続起動できるようにする。これで5〜10%改善する。ブロック内で終了記号（EOS）が出た場合は後続ブロックを処理せず終了し、15〜40%の追加削減を得るケースもある。

## 評価

### 代表的な評価条件

| 項目 | 内容 |
|---|---|
| GPU | 8× NVIDIA H800 |
| ソフトウェア | PyTorch 2.9 dev、vLLM 0.10.1 |
| バッチサイズ | 1 |
| 生成長 | 1024 |
| ブロックサイズ | 64 |
| モデル | LLaDA-MoE、LLaDA-MoE-TD |
| 自己回帰モデル比較 | Qwen2.5-3B on vLLM |
| 拡散型LLM（dLLM）比較 | Fast-dLLM |
| タスク | CRUX-O、GSM8K、HumanEval、IFEval、MBPP、LiveCodeBench v6 |
| 指標 | 性能、TPF、TPS |

TPFは1回のモデル順伝播当たりの確定トークン数、TPSは1秒当たりの生成トークン数である。TPFが高くても1回の順伝播が重ければTPSは上がらないため、アルゴリズム上の並列化と実装速度を分けて読む必要がある。

### LLaDA-MoE

| 構成 | 平均性能 | 平均TPF | 平均TPS |
|---|---:|---:|---:|
| Qwen2.5-3B / vLLM | 54.44 | 1.00 | 277.45 |
| Fast-dLLM / KVなし | 53.52 | 2.82 | 63.61 |
| dInfer / KVなし | 54.33 | 4.29 | 407.36 |
| Fast-dLLM / KVあり | 52.15 | 2.46 | 110.98 |
| dInfer / KVあり | 53.96 | 3.87 | 680.71 |

Fast-dLLMは並列 復号でTPF>1を得ても、1回の順伝播のシステム コストが高く、AR QwenよりTPSが低い条件がある。dInferはTPFを3〜4台へ上げるだけでなく、テンソル並列／専門家並列（TP/EP）・コンパイル・キャッシュ・ループ実装を同時に短縮することで680.71 TPSへ到達する。

同程度の品質を揃えた論文比較ではFast-dLLM 63.61 TPSに対しdInfer 680.71 TPSで10倍超となる。HumanEvalでは1011.12 TPSを記録する。

### 軌跡蒸留（Trajectory Distillation）との組合せ

LLaDA-MoE-TDは、良い拡散復号 軌跡中の離れた状態間を直接予測するよう追加学習（fine-tuning）し、1回の順伝播でより大きく[MASK]を減らせるモデル派生である。

これをdInferのhierarchical 復号、近傍更新、反復 smoothing等と組み合わせると平均TPF 5.67、平均847.22 TPSとなり、HumanEvalは1125.67 TPSへ達する。フレームワーク側だけでなく、モデル自体の並列 デコード能力を上げると利得をさらに積み増せることを示す。

## 既存研究との差

Fast-dLLMなど先行拡散型LLM（dLLM）高速化は閾値 復号やDual Cacheを導入するが、デコード 方針、反復間状態、キャッシュ freshness、GPU実行を個別に最適化する傾向がある。

dInferはこれらを4コンポーネントへ分離し、**1回の順伝播でより多くトークンを確定するアルゴリズム最適化と、1回の順伝播そのものを短くするシステム最適化を同じフレームワークで積み上げる**。またTPFとTPSを同時に示すことで、「並列化は増えたがカーネル実行が遅い」というケースを区別している。

## 限界

拡散型LLM（dLLM）のKV再利用は本質的に近似である。近傍更新は変更の影響が主に近傍へ強く現れるという仮定に依存し、遠距離依存が強いタスクでは窓外の陳腐化状態が品質へ影響する可能性がある。ブロック完了時の全体 更新はこの誤差を抑える一方、追加計算になる。

階層型/信用度/閾値のどれが最適かもモデルとキャッシュ設定で変わる。実際構成要素除去実験ではKVありLLaDA-MoEでは閾値が品質とTPFのバランスで採用され、KVなしでは信用度、distilled モデルでは階層型が使われる。単一デコーダが常に最良ではない。

評価は8×H800、バッチ 1を中心としている。高バッチでは自己回帰モデル側もGPU利用率が上がるため「拡散型LLM（dLLM）がARより速い」という相対差は変わり得る。またLLaDA系以外の拡散型構成で同じキャッシュ localityや並列化が得られるかは別途検証が必要である。
