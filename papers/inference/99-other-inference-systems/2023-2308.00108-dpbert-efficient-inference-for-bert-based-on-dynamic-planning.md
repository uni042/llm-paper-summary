# DPBERT：強化学習による入力依存のTransformer層スキップ

## 概要

DPBERTは、BERT-baseの12個のTransformer層をすべて通すのではなく、入力ごとに実行すべき層の部分列を決めることで推論遅延を削減する。従来のearly exitでは、途中の層で最終分類を確定すると、それより上の層をまとめて省略する。そのため下位・中間層を残したまま上位だけを削る選択に限定される。DPBERTは各層の手前に軽量な実行判定ネットワークを置き、層を一つずつ通すか迂回するかを選択する。途中の層を飛ばした後に上位の層を再び使える点が主要な違いである。

この二値判定を、教師あり学習による初期化と、正答率・省略層数の報酬を考慮した強化学習によって獲得する。原著はGLUEの分類・回帰タスクを、BERT-baseおよびLayerDrop、DistilBERT、DeeBERT、BERxiT、PABEEと比較した。NVIDIA GTX 1080 Ti 12GBでのバッチ1推論では平均1.34倍の高速化を報告し、dev平均は82.4→81.3、test平均は79.1→77.7へ低下した。原著の「98%の性能を維持」は基準モデルとの平均性能比を表すのであって、絶対正答率98%という意味ではない。

## 問題設定

BERTなどのエンコーダ型Transformerは、入力の難易度によらず固定数の層を実行する。単純な感情分類や文間関係の判定でも12層を通ると、必要以上の計算が発生する。蒸留・構造化剪定は固定の軽量モデルを作るが、入力ごとの難しさに合わせて計算量を変えにくい。early exitは推論途中の分類器の確信度に基づき、以後の層を一括で実行しない方式であり、容易な入力では効率的だが、中間層だけを省いて後段の抽象的表現を利用する経路を選べない。

DPBERTが最適化するのは、単に「何層実行するか」だけではなく、**どの層を実行するか**である。各層を実行する/しないの2値行動を選べるため、理論上は12層について2^12通りの経路があり、先頭から連続した部分列に制限されない。ただし全経路を列挙して最適化するのではなく、現在の隠れ状態に基づく小型ゲートの逐次判断で近似する。層を飛ばすと後段の入力分布も変わるため、事前学習済みBERTの重みをそのまま使うだけでは精度を維持しにくく、ゲートとバックボーンの適応が必要になる。

本研究の最終評価対象は、自己回帰の大規模言語モデルではなくBERT-baseによる文章理解である。したがって大規模生成LLMのKVキャッシュ、デコードスループット、長文脈Attentionへの効果は原著からは判断できない。ただし、入力に応じた条件付き計算、動的層スキップ、ゲートの学習という機構は推論効率化の系統に直接関係する。

## 手法

### 1. 各層の実行判定と計算経路

12層のBERT-baseをバックボーンとし、各Transformer層に対応する軽量な全結合ネットワークを追加する。通常のBERTは全トークンの隠れ状態を各層で更新するが、ゲートが全トークンを参照すると判定自体が高コストになる。そこで各層の判定には、文章分類の情報を集約しやすい`[CLS]`トークンの隠れベクトルだけを使う。層iの直前状態から小型の線形変換とsigmoidで値s_iを得て、0.5を超えれば層iを実行、そうでなければその層を迂回する。

行動a_iを0または1とすると、隠れ状態の更新は概念的にh_i = a_i·Transformer_i(h_{i-1}) + (1-a_i)·h_{i-1}である。a_i=0のときは直前の状態をそのまま次層へ渡し、Transformer本体の計算を省く。ゲートは層ごとに独立の学習パラメータを持ち、入力の状態が変われば異なる経路を選べる。

この方式は入力ごとに動的な分岐が生じるため、バッチ処理やGPUカーネルの一括実行には追加の課題がある。原著の推論測定はバッチ1であり、大規模バッチにおける分岐の非効率や、トークン単位の細かな分岐を扱ったものではない。省略できるのはTransformer層の計算であり、ゲートの判定自体にはわずかな追加費用がある。

### 2. 三段階の学習

最初の段階では、通常のBERTと同様にタスク別データでバックボーンをfine-tuningする。この時点ではゲートを使わず、全層を通す分類・回帰器を作る。第二段階ではバックボーンを凍結し、ランダム初期化された層別ゲートを学習する。二値の閾値関数は勾配を通せないため、この初期化段階ではsigmoidの連続値をそのまま用いて誤差逆伝播を可能にする。

第三段階では、ゲートの離散的な実行/スキップ行動を逐次意思決定とみなし、強化学習を用いてゲートとバックボーンを共同更新する。スキップした層の計算費用が報酬となる一方、タスク損失が大きければ報酬が下がる。原著では各層の計算費用C_iを1と置き、タスク損失との重みβを調整する。加えて、平均的な層実行・スキップ率を目標値tへ近付ける二乗ペナルティを導入し、速度と精度の交換関係を調節する。総合目的はタスク損失、方策の期待報酬、目標率からの逸脱ペナルティの加重和である。

ここで重要なのは、単純な連続値ゲートを学習しただけでは良好な離散経路が得られないことである。第三段階の強化学習は、現在の層を飛ばすことが後段の判定に与える影響を含めて最適化する。原著Table 2は、強化学習を外して連続的なsoftゲートで共同学習した比較を示しており、同じ高速化率に合わせても大幅な性能差が生じた。

### 3. 学習率と探索条件

原著Section 4.3では、バックボーンfine-tuningとゲート初期化をそれぞれ5エポック、AdamW、学習率2×10^-5で行う。強化学習段階ではバッチサイズ8/16/32、学習率2/3/4/5×10^-5、β=5/20/35/50、λ1=0.1/0.5/1/1.5を探索し、開発集合の性能が良い設定を採用した。全体比較での目標率tは0.4である。これらの値は再現に重要だが、探索に使った計算時間や消費電力まで網羅的に報告されたわけではない。

## 評価

### 実験環境とベースライン

| 項目 | 原著の設定 |
|---|---|
| 対象モデル | Googleの12層BERT-base |
| 実装 | Hugging Face Transformersを基盤としたDPBERT試作 |
| GPU | NVIDIA GTX 1080 Ti 12GB、単一GPU |
| 推論 | 入力1件ずつ、バッチサイズ1。3シード実行の中央値で速度評価 |
| データ | GLUEのCoLA、MNLI、SST-2、QNLI、MRPC、QQP、RTE、STS-B（MNLIはmatched/mismatchedを区別） |
| 評価指標 | 分類のaccuracy、MRPC/QQPはaccuracyとF1の平均、STS-BはPearsonとSpearmanの平均、CoLAはMCC |
| 比較手法 | BERT-base、LayerDrop、DistilBERT、DeeBERT、BERxiT、PABEE |
| 速度比較 | BERT-base=1.00倍。基準手法の閾値を調整しておおむね1.30〜1.96倍に制約 |

GLUEの各列は同じ種類の指標ではない。CoLAのMCCとSTS-Bの相関を、他の分類精度と並べて平均した値が論文の「Avg」である。これはGLUEの慣例に沿う集計だが、全タスクを同一の絶対正答率として解釈してはいけない。開発集合は3回の平均、テスト集合は選択されたモデルをGLUEサーバーへ提出した結果であり、両者の集計条件も異なる。

### 全体結果：原著Table 1

| 手法 | BERT比の推論高速化 | GLUE開発集合Avg | 主な解釈 |
|---|---:|---:|---|
| BERT-base | 1.00× | 82.4 | 12層すべてを実行 |
| LayerDrop | 1.94× | 78.8 | 速度は大きいが平均性能の損失も大きい |
| DistilBERT | 1.63× | 79.6 | 固定の軽量蒸留モデル |
| DeeBERT | 1.33× | 76.0 | 途中終了型。STS-Bは未対応 |
| BERxiT | 1.40× | 78.0 | 途中終了型の改良 |
| PABEE | 1.33× | 79.7 | 安定性に基づく途中終了 |
| DPBERT | 1.34× | 81.3 | 動的な非連続層スキップ |

DPBERTの81.3はBERT-baseの82.4に対し1.1ポイント低い。速度は平均1.34倍だが、LayerDropの1.94倍より遅いので、すべての指標でDPBERTが最良というわけではない。DPBERTの優位は、約1.3〜1.4倍の高速化を狙った条件で、従来のearly exitより比較的高いGLUE性能を維持する点にある。

テスト集合ではBERT-baseの平均79.1に対しDPBERTは77.7で、1.4ポイントの低下を伴う。個別の例としてCoLAは52.1→53.5へ改善する一方、MNLIは84.0→82.8、SST-2は93.5→91.9、QNLIは90.5→88.4、MRPCは88.9→86.5、QQPは71.2→69.3、RTEは66.4→65.9、STS-Bは85.8→83.5である。平均では約98.2%を維持しているが、全タスクで品質が不変という主張ではない。

### 負の結果と他方式が勝つ条件

開発集合のQQPでは、PABEEが89.0、BERxiTが88.9に対し、DPBERTは88.3であり、DPBERTが勝っていない。速度が1.34倍前後でも、個別タスクの最良性能は他のearly exit手法に残る。SST-2やQNLIの速度-精度曲線（Figure 3）でも、QNLIの低高速化領域ではDeeBERTの精度がわずかに高い場合がある。従って「どの速度域・どのタスクでもDPBERTが優越する」とは言えない。

DPBERTの強化学習を外したsoft版の結果（原著Table 2）は、RTEが66.8→51.6、MRPCが87.8→82.8、SST-2が90.8→85.7、STS-Bが88.7→83.8へ低下する。同じ高速化率になるよう目標率を合わせた比較であるため、softゲートの低下は単に多くの層を省略したせいではない。離散的な行動系列を最適化する強化学習が本手法の重要な要素であることを示す。ただし、強化学習の訓練コストと推論時の節約を合わせた費用対効果は十分に検証されていない。

### 計算経路の可視化とケーススタディ

Figure 4はMNLIとRTEで使われる層の分布が異なることを示す。MNLIでは下位・中間層の語彙・構文情報を多く使う一方、RTEでは上位層の意味表現を使う傾向がある。Table 3の例では、単純なMNLIの文対は第1〜6層だけで判定し、より複雑な文対は1〜6層に加えて8、10、11、12層も実行する。QNLIでも一例は1、3、4、5層だけを通り、別の例は1、3、4、5、9、10、12層を実行する。

これは入力依存の経路が実際に異なることを示す定性的証拠であるが、各層が語彙・構文・意味のどれを専ら担当するかを因果的に証明するものではない。また、個別の例から平均的な高速化率や大規模生成モデルへの転用可能性を推測することはできない。

## 既存研究との差

固定層削減のLayerDrop、固定小型モデルへの蒸留であるDistilBERTは、入力によらず一定の計算経路を使う。DeeBERTやBERxiT、PABEEは入力に応じて途中終了できるが、終了した後の上位層を使わない。DPBERTは途中の層を飛ばしてから上位層を再び利用できるため、同じ実行層数でも異なる特徴を利用できる。これは「計算量を減らす」という点では同じでも、実行グラフの自由度が異なる。

学習面では、単にゲートをsoftにして誤差逆伝播するだけでなく、層スキップの報酬とタスク損失を合わせた逐次意思決定を最適化する。Table 2のsoft版との大きな差が、この訓練方式の意義を裏付ける。後続のLLM向け条件付き計算、動的層スキップ、早期終了の研究を読む際には、どの層を省くかと、何を使ってゲートを訓練するかを分けて比較できる先行研究として有用である。

## 限界・注意点

第一に、原著のモデルはBERT-baseであり、推論対象はGLUEの短い文章理解タスクである。数十B規模の自己回帰LLM、KVキャッシュを使った逐次デコード、複数GPUサービングの測定はない。したがって「LLM生成を1.34倍高速化」と書くのは誤りであり、あくまでBERT-baseのバッチ1推論での結果である。

第二に、GPUはGTX 1080 Ti 12GB一種類で、CUDA世代やTensor Core性能の異なるGPUへそのまま外挿できない。動的分岐は大きなバッチでGPU実行を不規則にする可能性があり、バッチ1での改善が高同時実行時にも成り立つ保証はない。メモリ消費、電力、訓練に要するGPU時間、ゲートのレイテンシ内訳は、サービング実装判断に十分な粒度では示されていない。

第三に、速度と品質の交換関係は残る。開発集合Avgは82.4→81.3、テストAvgは79.1→77.7へ低下し、QQPではPABEEなどが高い。soft版の性能低下から分かるように、複数段階の学習と強化学習を省くと本来の効果を再現しにくい。入力難易度の分布が変わると選択される経路も変わるため、異なるドメインでは再学習と評価が必要になる。

第四に、原著自身が将来課題として自然言語生成モデルへの適用を挙げている。生成タスクでは各出力トークンに対して計算経路が変わり、キャッシュ整合性や品質維持に追加の課題が生じる。BERTでの成功をそのままLLM生成の実証とみなさないことが重要である。

## 結論

DPBERTは入力ごとに非連続なTransformer層の実行経路を学習し、early exitより自由度の高い条件付き計算を実現した。GTX 1080 Ti上のBERT-baseでは、平均1.34倍の高速化と引き換えにGLUE性能が小幅に低下する。強化学習を除いたsoft版が大きく悪化する点は重要な負の結果であり、層スキップの経路選択には離散的な系列決定の学習が効いている。推論最適化の設計原理としては参考になるが、生成LLMのデコード高速化として扱うには追加の実験が必要である。
