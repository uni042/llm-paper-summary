# BudgetMem：学習不要の選択記憶による長文脈処理の保存費用削減

## 書誌情報と版の注意

本稿は **arXiv:2511.04919v3（2026年9月20日）** の一次PDF全7ページを確認した解説である。論文の初期版は「Learning Selective Memory Policies ...」という題名で学習型の選択機構を説明していたが、今回の対象であるv3の正式な表題は **Training-Free Selective Memory ...** であり、方式も**学習不要**と記載される。旧版の「学習済みゲート」や「700件だけでの評価」を最新版の方式へ混入させない。最新稿では四つの評価群、合成文書と実文書の差、失敗例を明示する。著者は4名で、2026年IEEE UEMCON採録とPDFに記載される。

## 概要

大規模言語モデル（Large Language Model; LLM）の長文脈処理では、全入力をモデルへ投入すると注意計算・メモリ・料金が増える。検索拡張生成（Retrieval-Augmented Generation; RAG）に置き換えても、全文を断片化して保存・索引化すれば、索引の容量と前処理の費用が残る。トークン単位の圧縮器では、語句が断片的に残ることで検索に必要な語順や句のまとまりが失われる場合がある。

BudgetMemは**検索前、文書取り込み時**に不要な断片を捨てる。文書を重なりのある150トークンの断片へ分割し、六つの解釈可能な特徴から重要度を計算して上位だけを保持する。既定の保持比率は30%であり、残した断片をBM25検索索引に格納する。圧縮にはニューラルネットワークを使わずCPUだけで実行できる。

最も有利だった冗長な合成論文の質問応答では、索引に保持する断片を約29%まで減らしても、F1は全文RAGの0.855に対して0.859だった。ただし、実際の研究論文を使うQasperでは0.179から0.165へ低下し、50K～100Kトークンの物語では0.0471から0.0351へ低下した。したがって「70%削減でも精度維持」は**合成文書に限定された観測**であり、一般の長文書で無損失を保証しない。

## 問題設定

通常のRAGでは、文書の全断片を索引へ保存し、質問時に上位の断片を検索してLLMへ渡す。質問時の入力は短くなる一方、索引化対象の全断片を保存し、場合によっては全件の埋め込みベクトルを計算する必要がある。検索する前に重要度の低い断片を消せれば、索引容量や取り込み時の計算を節約できるが、質問をまだ知らない段階で何を捨てるかが問題になる。

既存のLLMLingua-2は小型言語モデルによって個々のトークンを削る。圧縮結果を直接LLMへ渡す使い方には適していても、削られた語の断片をBM25で検索すると、複合語句の一致が崩れて検索品質が下がる可能性がある。BudgetMemは個々の語を削るのではなく、意味的にまとまった**断片を丸ごと残すか捨てるか**を決める。圧縮対象はモデル重みやKVキャッシュではなく、RAG用に保存する外部文書の断片である。

## 手法

### 1. 重なり付き断片化

入力文書D（Nトークン）を、150トークン長・30トークン重複の断片 C₁,…,Cₘ に切り分ける。隣接断片を重ねるのは、境界にまたがる文脈を完全に切断しないためである。ここでの断片数Mは文書長と切り分け規則に依存し、後段の保持予算は**トークン数ではなく断片数**に適用される。したがって「30%保持」は、実際の索引バイト数が必ず30%になることを意味しない。

断片化は取り込み時に一度だけ行う。検索時に原文から再生成する方式ではないため、後段で捨てた断片は検索候補から消える。これが索引容量を下げる直接の原因であると同時に、後から重要と判明した情報を取り戻せない欠点でもある。

### 2. 六特徴による重要度計算

各断片 Cᵢ に対し、正規化した特徴 fⱼ(Cᵢ) を重み wⱼ で足した **sᵢ = Σⱼ wⱼ fⱼ(Cᵢ)** を計算する。特徴値は文書内の断片群に対して0～1へ正規化する。採用した重みは20文書の保留集合で一度設定し、評価対象群に対して固定した。論文のv3では学習による重み更新を行わない。

| 特徴 | 重み | 入力と計算 | 期待する役割・弱点 |
|---|---:|---|---|
| 固有表現密度の代理指標 | 0.20 | 大文字で始まる語の割合 | 人名・組織名等を拾うが、謝辞や引用の大文字にも反応する |
| 語彙の識別性（TF-IDF） | 0.20 | 断片内語のTF-IDF平均 | 文書内で特徴的な語彙を持つ段落を優先する |
| 位置事前分布 | 0.15 | 文書中央で高く両端で低い山型の値 | 研究論文の方法・結果節を優遇するが、他ジャンルでは偏る |
| 数値密度 | 0.15 | 数字・日付・割合などの語の比率 | 数値を問う質問に有利だが、非数値の重要な結論を落としうる |
| 談話標識 | 0.10 | 48語の接続表現辞書への部分文字列一致の頻度 | 論理展開を拾うが、英語依存で誤一致もある |
| 疑問表現の有無 | 0.10 | 疑問符や疑問詞の有無 | 質問を含む断片を検出するが、学術論文では寄与が小さい |

位置特徴は論文の式(2)で、中央ほど高く、両端に向かって減衰する。単純な「先頭ほど重要」という規則ではない。数値密度と談話標識は後述の要素除去実験で寄与が大きい一方、固有表現密度と疑問表現は合成論文では除去してもF1が変わらなかった。これらは万能な意味理解器ではなく、文書の表層的な特徴を測る軽量な規則である。

### 3. 予算内の選択と検索索引の構築

保持率rを与え、重要度の高い順に **floor(r×M)** 個の断片を残す。既定値r=0.30では、およそ7割の断片を取り込み段階で削除する。保持断片だけでBM25索引を作成するため、索引化対象の文書量を減らせる。学習済み圧縮モデルを推論する必要がなく、特徴計算はCPU上で完結する。

質問時には保持済みの索引から上位 **k=3** 断片を検索し、LLMへ文脈として渡す。基準RAGと同じtop-3の検索条件なので、BudgetMemを使ったからといって**1質問当たりのLLM入力が70%減るわけではない**。論文自身が指摘する主な節約対象は、索引の保存量と取り込み時の索引作成・埋め込み作成の処理量である。検索時の推論トークン削減と混同してはいけない。

### 4. 圧縮と質問応答の役割分離

圧縮時に必要なのは文書のみであり、将来の質問は使わない。このため同じ文書を何度も検索する用途では、事前選別の費用を複数の質問で償却できる。一方、質問に必要な事実が削除済み断片にしかなければ、検索器やLLMが高性能でもその事実を復元できない。保持した断片の説明可能なスコアは監査しやすいが、選択結果の正しさを保証するものではない。

比較対象のLLMLingua-2はトークン単位のニューラル圧縮器であり、圧縮後テキストを検索索引へ入れる比較は本来の推奨使用法と異なる。その不公平性を検証するため、著者は密検索と直接投入の条件も追加している。検索方式の違いと圧縮粒度の違いを分離して読む必要がある。

## 評価環境

| 観点 | 一次論文の条件 |
|---|---|
| 主モデル | Llama-3.2-3B-Instruct、FP16、貪欲復号、最大100新規トークン |
| 交差検証モデル | Qwen2.5-7B-Instruct、4ビットNF4量子化 |
| 質問応答の計算機 | NVIDIA T4 GPU（15GB）、Google Colab Proの単一環境 |
| 圧縮処理 | CPUのみ。別途ノートPCのCPUで圧縮時間を測定 |
| 検索 | BM25、上位3断片。中程度文書ではall-MiniLM-L6-v2の密検索も比較 |
| 評価指標 | 生成回答と正解の正規化後トークン単位F1、保持量、圧縮時間、短文書での遅延 |
| 短文書 | SQuAD v2.0、500例、平均237トークン（148～448） |
| 中程度の合成文書 | 40本のテンプレート論文に対する200問、文書長約3,700トークン。各節で同一段落を5～10回反復 |
| 中程度の実文書 | Qasper、自然なNLP論文への102問、平均3,608トークン |
| 非構造長文 | NarrativeQA、50例、50K～100Kトークン。乱数種3個で平均と標準偏差を報告 |
| 保持予算 | 基本30%。合成文書では10/20/30/40/50/70/90%の7条件を追加 |

基準RAGは全断片を保存してBM25で検索する。比較にはトークン単位TF-IDF、LLMLingua-2、ランダム断片選択、先頭・末尾選択、TF-IDF単独断片選択がある。密検索と直接投入の比較は**合成文書の200問**で実施したもので、QasperやNarrativeQAの全条件へ外挿できない。

## 主要結果

### 文書種類ごとの保存量と回答品質

| データと条件 | 指標 | 全文RAG | BudgetMem | 差の解釈 |
|---|---|---:|---:|---|
| 合成論文・200問、BM25、保持約29% | F1 | 0.855 | 0.859 | +0.004、統計的に有意な改善ではない |
| 合成論文・200問、密検索 | F1 | 0.844 | 0.918 | +0.074、ただし合成文書のみ |
| 合成論文・200問、直接投入 | F1 | 0.877 | 0.797 | 全文を直接投入する方式より悪化 |
| 合成論文・Qwen2.5-7B、BM25 | F1 | 0.900 | 0.960 | 4ビットの別モデルでも同条件の相対順位を維持 |
| 実論文Qasper・102問、保持約28% | F1 | 0.179 | 0.165 | 相対約7.4%悪化、約72%保存量削減 |
| NarrativeQA・50例、保持30% | F1 | 0.0471±0.0090 | 0.0351±0.0022 | 相対約25%悪化、絶対F1自体が低い |
| 短文書SQuAD・500問 | F1 | 0.801 | 0.723 | 相対9.7%悪化、保存量削減は15.5%のみ |
| 短文書SQuAD・500問 | 遅延 | 0.37秒 | 0.43秒 | 16%遅くなる負の結果 |

合成論文での「保存量71%削減」は、同じ段落が何度も繰り返されるという**強い冗長性**に支えられている。著者はこの構造を隠さず、各節がテンプレート段落を5～10回繰り返すと説明している。実論文では一度しか書かれていない事実を落としやすく、QasperでのF1悪化はその制約を示す。合成文書でのF1 0.859は基準0.855とほぼ同等であり、「改善した」と断定するより「維持した」と読むのが妥当である。

### 圧縮粒度と検索方式の交差比較

| 合成論文200問、保持率名目30% | 全文基準 | LLMLingua-2 | BudgetMem |
|---|---:|---:|---:|
| BM25検索 F1 | 0.855 | 0.554 | 0.859 |
| 密検索 F1 | 0.844 | 0.530 | 0.918 |
| 圧縮後テキストを直接投入 F1 | 0.877 | 0.720 | 0.797 |
| Qwen2.5-7BでBM25検索 F1 | 0.900 | 0.773 | 0.960 |

LLMLingua-2は名目30%圧縮でも実測では**単語の24%**を保持し、BudgetMemは**断片の29%**を保持している。保存量の分母が違うため、同一バイト数での厳密比較ではない。LLMLingua-2の検索条件ではトークン圧縮が句の連続性を壊し、BM25だけでなく密検索の埋め込みにも悪影響があったと著者は分析する。

ただし直接投入条件では、両圧縮器とも全文直接投入の0.877には届かない。BudgetMemはLLMLingua-2を0.077上回るが、これは圧縮方式同士の比較であり、無圧縮に対する品質維持の証拠ではない。直接投入での差は95%信頼区間[+0.012,+0.142]、p=0.02と報告される。

### 予算感度：少なく残せば必ず良いわけではない

| 保持率 | 10% | 20% | 30% | 40% | 50% | 70% | 90% |
|---|---:|---:|---:|---:|---:|---:|---:|
| 合成論文F1 | 0.689 | 0.868 | 0.859 | 0.856 | 0.848 | 0.795 | 0.862 |
| 実測保存量削減 | 90.4% | 80.8% | 71.2% | 61.7% | 51.1% | 32.0% | 12.8% |

20～30%保持で基準F1 0.855を維持しつつ約71～81%の保存量を削減できた。一方10%では0.689まで低下し、70%でも0.795へ下がる。これは保持率と品質が単調に対応しないことを意味する。上位3断片しか取り出さない検索設定と、保持断片集合の変化が組み合わさるためと著者は推測するが、すべての文書に通用する最適保持率を実証したわけではない。

### 要素除去実験と単純基準

| 合成論文200問、保持率30% | F1 | 全特徴方式との関係 |
|---|---:|---|
| 六特徴すべて | 0.859 | 基準 |
| TF-IDFだけ | 0.880 | 六特徴より高い |
| ランダムに断片を保持 | 0.785 | 六特徴より低いがトークン圧縮より高い |
| 先頭30%だけ保持 | 0.357 | 大幅に悪化 |
| 末尾30%だけ保持 | 0.527 | 悪化 |
| 談話標識を除去 | 0.605 | 29.6%相対悪化 |
| 数値密度を除去 | 0.718 | 16.4%相対悪化 |
| TF-IDFを除去 | 0.853 | 小幅悪化 |
| 位置特徴を除去 | 0.862 | むしろ小幅改善 |
| 固有表現密度を除去 | 0.859 | 変化なし |
| 疑問表現を除去 | 0.859 | 変化なし |

この結果は六特徴の複雑な重み付けが常に必要という主張を**支持しない**。合成論文ではTF-IDFだけの方がF1が高く、文書の構造と断片のまとまりを残すことが主な寄与と考えられる。著者は単純基準の比較を実論文では再実行していないため、Qasperで六特徴がTF-IDF単独より良いか悪いかは不明である。

重みを個別に±10%、±20%、および同時に0.8～1.2倍する計44構成では、保持断片集合のジャッカード一致率が最小90%以上、平均99%以上だった。F1は0.858～0.864に収まり、細かな重みの調整より、どの特徴を採用するかが重要であることを示す。ただしこれは同じ合成論文の評価である。

### 圧縮計算時間と統計的解釈

CPU上の圧縮時間は、52Kトークンの文書で0.05秒、約3.7Kトークンの合成論文で0.004秒（それぞれ7回の中央値）だった。これは**圧縮器の処理時間**であり、質問応答全体の遅延ではない。LLMLingua-2の圧縮時間は同一ハードウェア条件で測っておらず、圧縮時間の倍率を算出できない。

合成論文のBudgetMemと全文RAGのF1差+0.004について、非対応Welch検定の95%信頼区間は[-0.039,+0.047]、p=0.85である。著者は「有意な差がない」ことを品質維持の根拠として扱うが、これは厳密な同等性試験や無損失保証ではない。QasperのF1差も102問で統計的に不確か（非対応Welch p>0.6）とされ、点推定の悪化と有意性の有無を区別する必要がある。

## 既存研究との差

LLMLingua/LLMLingua-2は個々のトークンを削り、RECOMPやAutoCompressorは圧縮器の学習を使う。BudgetMemは**圧縮対象を断片単位へ変え、学習不要の表層特徴で取り込み時に削る**。これにより語句の連続性を保ち、BM25のような語彙一致型検索に適合させる。通常RAGが全断片を索引化して質問時に絞るのに対し、BudgetMemは索引化前に絞る。

一方、長文脈Transformerの疎注意やKVキャッシュ圧縮はモデル内部の演算・活性状態を削減する。BudgetMemは外部検索ストアの内容量を削るので、同じ「メモリ削減」でも対象が異なる。GPUのKVキャッシュ使用量やトークン生成速度を直接改善したという評価はない。LLM推論基盤の研究としては、検索前処理と外部記憶階層の容量制御に位置付けるのが適切である。

## 限界・負の結果・適用条件

第一に、合成論文の反復段落という冗長性が強い条件に結果が依存する。実論文のQasperでは重要な事実が一度しか出現しないため、削除した断片に回答があると検索できない。文書長が同程度でも、合成論文と実論文で品質が違う点が重要である。

第二に、短文書では削除できる余剰が少なく、SQuADで保存量15.5%削減に対してF1が9.7%悪化し、遅延も16%増えた。著者は約1Kトークン未満なら全文処理を勧める。第三に、NarrativeQAでは全方式の絶対F1が低く、BudgetMemは全文基準を約25%下回る。長い非構造文章に対する汎用的な優位性は示されていない。

第四に、英語の説明文や数値中心の質問へ調整された特徴を使う。接続表現の48語辞書、大文字で始まる語の数、数値密度は日本語の技術文書や会話ログではそのまま使えない。多言語、要約、多段推論、会話履歴、強い検索器での一般化は未評価である。特徴の重みは手作業で設定され、ドメインが変われば再調整が必要になり得る。

第五に、質問時に取得する断片数を3に固定しているため、保持率を上げても正解断片が必ず検索されるわけではない。直接投入では全文基準を下回る。モデル横断比較も合成文書のQwen2.5-7Bだけで、さまざまなモデル・検索器・実データでの全面的な再現はない。

第六に、圧縮時間の測定はCPU処理だけであり、索引構築・質問応答全体の総費用、同一条件でのLLMLingua-2圧縮速度、実サービスでのエンドツーエンドの改善倍率は報告されていない。圧縮器自体が0.05秒でも、実運用の総レイテンシが同じ割合で短くなるとはいえない。

## 実装と再現可能性

著者は公式コード、ノートブック、結果ファイルを公開している。保持判断は各断片の六特徴と重みから計算でき、なぜ残したかを後から追跡しやすい。実装を試す場合、元文書の分割規則、特徴の正規化単位、辞書、上位断片の選択、検索上位3件、モデル・量子化設定を合わせないと、論文のF1と一致しない可能性がある。

特にv1の学習型手法の説明とv3の学習不要の実装を混同しないこと、合成論文の数値を実論文へ一般化しないこと、保持率と実測保存量削減を区別することが再現上の重要点である。文書を削除した後に復元できるような設計は論文では提案していないため、実サービスに導入するなら原本の別途保持を検討すべきである（これは論文の評価結果ではなく運用上の示唆）。
