# ReasoningBank：エージェントの成功・失敗を再利用可能な推論記憶へ変える

## 概要

長期間にわたってウェブ操作やソフトウェア修正を行う大規模言語モデル（LLM）エージェントは、過去に成功した手順を別の課題で再発見したり、既に失敗した操作を繰り返したりする。過去の実行軌跡を丸ごと検索する方式では、現在の課題に関係ない画面遷移や局所的な操作が混ざる。成功例を手順書として保存する方式では、失敗から得られる「何を避けるべきか」を十分に残せない。ReasoningBankは、**成功・失敗の両方から一般化可能な推論戦略を短い記憶項目として抽出し、次の課題の指示に差し込む**ことで、モデル重みを更新せずに経験を蓄積する。

論文はさらに記憶を考慮したテスト時計算拡張（Memory-aware Test-Time Scaling; MaTTS）を提案する。同じ課題を複数回試す並列方式では試行間の共通点と相違点を比較し、逐次方式では途中の自己修正からも記憶を作る。WebArena全684課題でGemini-2.5-flashの成功率は記憶なし40.5%から48.8%、平均操作数は9.7から8.3へ改善した。Shopping部分集合では並列試行数を5へ増やしたMaTTSの成功率が55.1%となる。ただし55.1%は追加の試行計算を使った条件であり、同じ計算量の単一試行と混同できない。

## 問題設定と従来方式との差

対象は、課題 `q₁,q₂,…,qₙ` が逐次到着し、将来の課題も正解ラベルも実行時には分からない環境である。エージェントは観測 `oₜ` と過去の行動 `a₀:ₜ` を使って次の行動 `aₜ₊₁` を選ぶ。ウェブ操作では行動は画面のクリックや入力、ソフトウェア修正ではシェル操作であり、実行後に得た軌跡を次回の参考にできる。ただし履歴を無制限にプロンプトへ追加すると、文脈長と入力処理費用が増え、似ているだけの無関係な操作例が現在の判断を汚染する。

比較対象のSynapseは過去の軌跡の例示、Agent Workflow Memory（AWM）は成功例から抽象化した操作手順の再利用を重視する。これらと異なりReasoningBankは「最近の注文一覧に最古の注文がなければ全注文履歴とページ送りを調べる」のように、別サイトや別課題にも転用できる判断原則を抽出する。保存するのは環境の完全な状態や事実の正解ではなく、次の行動を選ぶための方針である。従って同じページの再訪や同一ファイルの検索を高速化するキャッシュとは異なる。

## 手法

### 1. 記憶項目の表現と検索

記憶集合 `M` の各項目は、短い**題名（title）**、一文の**説明（description）**、実行上の理由や判断規則を含む**内容（content）**の三部分で構成される。例えば「注文履歴を確認する」という行動そのものではなく、「現在表示されている注文が全件であると仮定せず、ページ送りと履歴画面を確認する」という、失敗を防ぐ条件付き規則を残す。項目が自然言語なので、人が内容を確認でき、LLMへの指示にも直接利用できる。

新しい課題を受け取ると、課題の文脈を埋込み表現へ変換し、記憶項目から類似度の高い上位 `k` 件を検索する。検索した項目はエージェントの**システム指示**に追加する。モデルの内部重み、鍵・値キャッシュ、環境状態を直接書き換えるのではなく、次の操作を決める入力条件を変える仕組みである。類似検索の費用と記憶の追加トークン数は発生するが、関連する過去の戦略が得られれば不要な探索や操作を減らせる。

### 2. 実行後の自己判定と成功・失敗からの抽出

課題が終了すると、課題文と実行軌跡をLLM判定器（LLM-as-a-Judge）へ渡し、外部の正解ラベルなしで成功または失敗の代理判定を得る。成功と判定された軌跡からは、役立った判断の根拠、条件分岐、再利用できる探索方針を抽出する。失敗と判定された軌跡からは、見落とした選択肢、誤った前提、回避すべき操作、反実仮想的な改善方針を抽出する。一つの軌跡から複数項目を作る場合もある。

生成された項目を記憶集合へ統合し、次の課題では更新後の集合を検索する。この「検索→実行→自己判定→抽出→追加」の閉ループが、経験からのテスト時学習の実体である。論文の統合処理は意図的に単純な追加方式であり、意味的な重複統合、記憶の有効期限、信頼度推定、矛盾解決を高度に実装したものではない。自己判定を誤れば、失敗を成功として記憶したり、有用な戦略を失敗とみなす危険も残る。

### 3. 記憶を考慮した並列・逐次テスト時計算拡張

通常のテスト時計算拡張（Test-Time Scaling; TTS）は、同じ課題に複数の独立した試行を割り当てる。試行数を増やせば成功候補は増えるが、各試行を別々に記憶へ追加するだけでは、試行間の相違を学習に利用できない。MaTTSは、追加計算を**その場の正解選択**だけでなく**後続課題のための記憶形成**にも使う。

**並列MaTTS**では、既存記憶で誘導した同一課題の複数軌跡を集め、自己対比（self-contrast）で成功した試行に共通する判断、失敗試行に特有の誤り、環境に依存しない方針を抽出する。単なる独立試行の寄せ集めより、同じ問題を解く複数の経路が対照例となるため、偶然成功した一連のクリックを普遍的手順と誤認しにくい。論文の並列評価は最良の `N` 試行を選ぶBest-of-N指標を使うため、単一試行の平均成功率とは区別する必要がある。

**逐次MaTTS**では、一つの課題の初回試行後に自己修正（self-refinement）を繰り返し、途中で作られる検討メモや訂正理由も記憶抽出へ渡す。試行数に相当する拡張係数 `k` は、並列では軌跡の本数、逐次では修正回数を意味する。逐次方式は少数回で効果が出る一方、同じ方針を反復しやすく、試行を増やしても新しい対照情報が増えない場合がある。どちらもLLM呼出し回数と環境操作費用が増えるため、成功率だけで費用対効果を評価してはならない。

### 4. 一つの課題が処理される全体の流れ

初期の記憶集合が空なら、最初の課題は通常のエージェントとして解く。終了後に軌跡と課題を判定器へ渡し、成功例の汎用手順や失敗例の落とし穴を項目化する。次の課題が来たら、現在の課題の埋込みに近い項目を検索し、システム指示へ加えて行動を生成する。MaTTSを有効にした場合は、同一課題に複数の試行または修正を行い、対比・反省結果をさらに記憶へ戻す。このため追加の推論計算は単発課題だけでなく、後続課題の判断にも影響する。

## 評価

### 実験環境・比較の前提

| 項目 | 原著第1版の条件 |
|---|---|
| エージェント基盤 | Gemini-2.5-flash、Gemini-2.5-pro、Claude-3.7-sonnet |
| ウェブ操作 | BrowserGym、ReAct型の逐次行動 |
| ソフトウェア修正 | bash-only環境のSWE-Bench-Verified |
| データセット | WebArena（Shopping 187、Admin 182、Gitlab 180、Reddit 106、Multi 29、計684）、Mind2Web、SWE-Bench-Verified |
| 比較方式 | 記憶なし、軌跡記憶Synapse、手順記憶AWM、ReasoningBank |
| 主な指標 | 課題成功率（SR）、平均環境操作数（Step）、ソフトウェア問題解決率（Resolve Rate）、Mind2Webの要素精度・行動F1・手順成功率 |
| MaTTS評価 | Gemini-2.5-flashのWebArena-Shopping、並列・逐次 `k=1…5` |

WebArenaではMap領域をウェブサイト側の問題で除外している。成功率は課題全体の達成割合であり、平均操作数はエージェントと環境の対話ステップ数である。**平均操作数の減少をGPU推論時間や生成トークン数の減少と同一視できない。** ハードウェア構成とトークン単位の費用比較は代表結果の中心ではない。

### WebArena：成功率と操作数

| 基盤モデル | 方式 | 全684課題の成功率 | 平均操作数 |
|---|---|---:|---:|
| Gemini-2.5-flash | 記憶なし | 40.5% | 9.7 |
| Gemini-2.5-flash | Synapse | 42.1% | 9.2 |
| Gemini-2.5-flash | AWM | 44.1% | 9.0 |
| Gemini-2.5-flash | ReasoningBank | **48.8%** | **8.3** |
| Gemini-2.5-pro | 記憶なし | 46.7% | 8.8 |

| Claude-3.7-sonnet | ReasoningBank | **46.3%** | **7.3** |

Gemini-2.5-flashでは成功率が**8.3ポイント**上昇し、操作数は約14.4%減少する。Shopping単独では記憶なし39.0%、Synapse 40.6%、AWM 44.4%、ReasoningBank 49.7%である。Multi部分集合では記憶なし10.3%、AWM 3.4%、ReasoningBank 13.8%となるが、29課題と小規模であり一般化性能を過度に断定しない。成功時と失敗時を分けると、Shoppingの成功軌跡は平均6.8→4.7ステップ、失敗軌跡は8.7→7.3ステップで、成功例での探索短縮が特に大きい。

| 評価 | 基盤モデル | 記憶なし | ReasoningBank | 読み方 |

### 追加試行と記憶の相乗効果

| WebArena-Shopping / Gemini-2.5-flash | `k=1` | `k=5` | 評価指標 |
|---|---:|---:|---|
| 並列MaTTS | 49.7% | **55.1%** | 最良試行選択の成功率 |

| 逐次MaTTS | 49.7% | **54.5%** | 反復修正の成功率 |
| 逐次・統合なし | 49.7% | 51.9% | 同じ修正回数での比較 |

並列5試行で対比統合を加えると、単純な独立記憶追加より2.7ポイント高い。逐次5回では2.6ポイント高い。ただし `k` を増やすと実行軌跡・判定・抽出の回数も増えるため、**同じ計算量で55.1%を達成したという意味ではない**。図5の `k=3` ではReasoningBankの単一試行成功率が49.7→50.8、最良3試行では52.4となる一方、Synapseの単一試行は40.6→40.1、AWMは44.4→41.2へ悪化する。試行を増やせば記憶が必ず良くなるという単純な関係ではない。

### 失敗例の取り込みを外す構成要素除去

Gemini-2.5-flashのShoppingでは、成功例だけから記憶を作るReasoningBankの成功率は46.5%で、失敗例も使うと49.7%になる。Synapseは40.6→41.7%、AWMは44.4→42.2%であり、失敗例を追加するだけでは一般的な改善にならない。**失敗の原因を再利用可能な方針として抽出する設計**が重要だと分かる。もっとも、失敗判定器の精度や記憶項目の重複による長期劣化を切り離した完全な因果証明ではない。

## 限界と実装上の判断

第一に、正解ラベルなしで実行軌跡を評価するLLM判定器は誤判定し得る。成功と誤認した行動を指示として再利用すると、エラーが後続課題へ伝播する。第二に、論文の記憶統合は単純追加であり、似た戦略の重複、矛盾、古いウェブ画面の規則、誤った反省の破棄を高度に管理しない。大規模な長期運用では記憶検索の候補増加とプロンプト追加量が別の費用になる。

第三に、MaTTSは複数の環境試行、自己判定、記憶抽出を行う。成功率の改善と引き換えにLLM呼出し・環境操作・外部API費用が増える。実験は主にウェブ操作とソフトウェア修正であり、リアルタイムのトークン生成速度、GPUメモリ帯域、KVキャッシュ、同時サービングの性能改善を示すものではない。WebArenaのサイト状態、モデル世代、判定器の偏りが変わると数値をそのまま再現できるとは限らない。

第四に、推論記憶は自然言語の方針であり、モデルのパラメータ更新や検証済み知識ベースとは異なる。記憶の出典、適用条件、失敗率、権限を明示しないまま他環境へ転用すると誤操作の原因になり得る。安全な実装では、記憶項目の出典軌跡と信頼度、期限、検証可能性、競合解消、外部操作前の権限確認を別途設計する必要がある。
