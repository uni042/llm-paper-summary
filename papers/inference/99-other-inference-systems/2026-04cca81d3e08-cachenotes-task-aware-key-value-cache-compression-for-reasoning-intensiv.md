# CacheNotes：タスク別圧縮計画を用いた再利用可能なKVキャッシュ

## 概要と対象課題

CacheNotesは、長い文書群について、将来どの質問が来るかは分からないが、**質問の種類・業務タスクは分かっている**という条件を利用する。あらかじめ文書群を一度だけ読み込み、タスクに必要な知識を残すよう鍵・値（KV）キャッシュを圧縮する。以後の質問では全文を入力し直したり、質問ごとに検索したりせず、短い質問と事前に作った圧縮KVだけで回答する。圧縮を質問に依存させないため、同じ文書群に対する多数の質問へ再利用できる。

典型的な検索拡張生成（Retrieval-Augmented Generation; RAG）は、局所的な質問では関連文書片を効率的に取り出せる。しかし「複数の部署・資料に分散した条件をまとめる」「複数文書の関係を辿る」といった質問では、検索上位の少数片だけでは根拠が欠ける場合がある。全文を長文脈モデルへ毎回入力する方法は包括的だが、入力処理（Prefill）の計算費用とKVキャッシュのメモリ費用が大きい。CacheNotesはこの中間を狙い、**タスクに合わせてコーパス全体を一度圧縮し、後続の質問で使い回す**。

原著では、長文脈QAを20倍に圧縮した条件でRAGを8 F1ポイント以上上回り、オンライン初回トークン遅延を4倍以上短縮したと報告する。一方、単一の文書片だけで答えられる直接検索ではRAGが有利な場合があり、コード補完でもタスク説明が不十分だと圧縮が不利になる。提案は「検索は不要」と一般化するものではなく、**多数の質問に共通するタスク目的を使って、前処理費用を償却できる状況**に向く。

## 手法：オフライン二段階＋オンライン一段階

### 1. 圧縮計画トークンの生成

入力は文書群Cと、人間が記述するタスク説明Tである。まず指示追従型の言語モデルに両者を与え、圧縮計画トークン（Compression-Planning Tokens; CPTs）Sを生成する。原著式1では`S = LLM_inst(C,T)`と書く。CPTsは、人間が試験前に作る「重要事項を漏らさない要点ノート」に近く、タスクのために必要な固有名詞、関係、手順、数値、条件を整理するよう促す。

CPTsの生成時点では、個別の将来質問qは渡さない。タスク説明は、たとえば文書群について質問応答を行う、要約する、コードを補完する、といった課題群に共通の指示である。原著§4.2は、タスク群ごとに一つの説明テンプレートを使い回し、サンプルごとに手動で正解質問を与える方式ではないと説明する。この点が、問い合わせごとに重要部分を選ぶ方式との違いになる。

CPTsはオンライン回答時に単純なテキスト要約として挿入するためのものではない。次段の**コーパスKV位置の重要度を測る代理問い合わせ**として使う。CPTsそのものだけを回答の文脈に使うと、文章要約に落とし込めなかった細部が失われるため、原著はCPTs単独入力とKV圧縮方式を比較している。

### 2. CPTsの注意で保持するKV位置を決定

文書群CとCPTs Sを連結して基盤モデルへ入力し、各Transformer層のコーパス鍵`K_C`と、CPTsに対応する問い合わせ`Q_S`を取り出す。原著式3では、CPTsからコーパスへの交差注意重みを`W(S,C)=softmax(Q_S K_Cᵀ / sqrt(d_k))`で求める。CPTsが「どの文書トークンを参照しているか」を見ることで、個別の質問がなくてもタスクに重要そうな位置を推定できる。

さらにCPTs側の値ベクトルのノルムで各行の重みを補正し、CPTsトークン方向に平均して、コーパス各位置の重要度を得る（原著式4〜5）。保持予算kに対して上位k個の位置を選び、その位置の鍵・値ペアだけを保存する。層ごとに選択するため、同じコーパスでも注意層に応じて異なる位置が残り得る。これはコーパスを短い文章に書き換えるのではなく、**元の文書を処理したときの中間KV表現の一部を保持する**処理である。

位置を間引いた後も回転位置埋め込み（Rotary Positional Embeddings; RoPE）の整合性が必要である。原著は圧縮後の鍵ベクトルについて適切な正弦・余弦のオフセットを再計算し、位置を再回転させると説明する。位置処理を無視して単にKV配列を切り詰めると、質問トークンとの位置関係が変わり、注意得点が不正確になり得る。

### 3. 質問時は圧縮KVと質問のKVを結合

質問qが届いたら、コーパスの再入力は行わない。事前保存した圧縮鍵・値`(K̃,Ṽ)`へ質問自身の鍵・値を追加し、その状態で生成する（原著式6）。質問ごとに検索器を呼ぶ必要も、質問に合わせた再圧縮を行う必要もない。質問文の短い入力処理と、圧縮されたKVの読み出しが主なオンライン費用になる。

ただし、この方法は**質問とタスク説明が十分に整合すること**を前提とする。タスクが変わったり、圧縮時に重要とみなされなかった細部を尋ねたりすると、削除済みのKVをオンラインで復元できない。元文書を保持して再圧縮するか、別のタスク用キャッシュを用意する必要がある。

## 大規模文書の圧縮を実行可能にする工夫

CPTs長mと文書長nの交差注意をそのまま計算すると、m×nの得点行列が大きくなり、メモリ不足を招く。原著§3.3はコーパス鍵を長さcのチャンクへ分割し、オンラインsoftmaxの最大値と分母を逐次更新する方法を採る。これはFlashAttentionと同種の数値安定化手法であり、**全体のsoftmaxに相当する重要度を保ちながら、巨大な行列を一度に確保しない**。

一時的に保持する得点行列の規模は概ね`O(mn)`から`O(mc)`へ減る。原著図3は文書128K、CPTs 2Kでチャンクサイズを1K〜64Kまで変えた実験を示し、16K程度まではFlashAttention2の全入力処理と同程度のピークメモリを維持しつつ、64Kチャンクではメモリ不足が発生する条件を報告する。圧縮計算がオフラインだからといってメモリ消費が無制限でよいわけではない。チャンク化は圧縮の前処理を実用的なGPUメモリで実行するための重要な実装要素である。

## 評価条件

原著はLongBench、RULER、企業技術ノート、合成データの4種類で評価する。LongBenchは16データセット、単一文書QA、複数文書QA、要約、少数例学習、合成課題、コード補完を含み、文書の平均長は約10Kトークン。RULERは4Kの部分集合で6,500件の質問・文書組を用い、指標は大文字小文字を区別しない部分文字列一致（String Match）である。完全一致率と同じ尺度ではない。

企業技術ノートは49文書、1文書16K〜32K（平均22K）トークンで、GPT-4.1-miniによって各文書5件の広域質問を生成した計245組を使用する。品質はGPT-4.1-miniのペアワイズ判定で有用性、豊かさ、洞察などを評価するため、人間の独立盲検評価と同じ強さの証拠ではない。合成データは人・プロジェクト・所属関係を含む32K文書で、接続密度を変え、直接検索型と複数片の結合が必要な型を各200件、合計400件比較する。

基盤モデルにはLlama-3.1-8B-Instruct、Qwen3-4B-Instruct-2507などを使用し、企業データではQwen2.5-14B-Instructも評価する。RAGは文書を256トークン片に分割し、BGE-Large-EN-v1.5で検索する。保持予算512/1024/2048/4096トークンに対し、それぞれ上位2/4/8/16片を取り出す。質問・プロンプト部分はこの保持予算に含めない。原著付録はBM25による疎検索の対照も追加している。圧縮対象のコーパスと質問は貪欲復号で処理する。

## 定量結果：品質

### LongBenchのQAと検索との比較

原著付録表3には、Llama-3.1-8B-Instructで同じ保持予算を用いたQAのF1が示される。

| 課題・予算 | RAG（BM25） | RAG（密ベクトル） | CacheNotes | 最良RAGとの差 |
|---|---:|---:|---:|---:|
| 単一文書QA・512 | 26.82 | 26.42 | **34.00** | +7.18 |
| 単一文書QA・1024 | 32.34 | 31.77 | **35.96** | +3.62 |
| 単一文書QA・2048 | 39.29 | 38.67 | **39.60** | +0.31 |
| 複数文書QA・512 | 24.61 | 29.19 | **38.91** | +9.72 |
| 複数文書QA・1024 | 34.25 | 37.75 | **41.67** | +3.92 |
| 複数文書QA・2048 | 41.31 | 43.01 | **44.71** | +1.70 |

低予算で複数文書QAの差が大きく、予算が増えるとRAGが追いつく。したがって「RAGより8ポイント以上高い」という要旨の主張は、**すべての予算・課題で8ポイント以上**という意味ではない。付録の単一文書QA・2048では差は0.31ポイントしかない。要旨の20倍圧縮と、上表の512/1024/2048トークンの固定予算は同じ指標ではないので、倍率とF1差を混ぜて説明しない。

原著§5は、LongBenchの入力が平均約10Kトークンである条件で、圧縮率2.5倍なら全入力の性能の98.9%に到達すると述べる。ただしこの値は課題全体を集約した比率であり、個々のデータセットで98.9%の正答率になるという意味ではない。要約・コード補完などはF1以外の指標を使うため、課題をまたぐ平均の解釈には注意が必要である。

### 広域質問と直接検索の違い

企業技術ノートの評価では、CacheNotesがRAGより有用・正確・洞察的と判断される例が多い一方、RAGが短く実用的な回答で勝つ例もある。原著の判定選好率62.7%はモデル評価器による比較であり、人間の好みを同じ割合で保証するものではない。

合成データの図7では、答えが一つの文書片にある直接検索型ではRAGが有利になることがある。RAGは質問と局所的に一致する証拠を高精度に取り出せるからである。複数の片を結合する質問では、片の関係数が増えるほどRAGの性能が約15ポイント低下し、CacheNotesはコーパス全体から情報を残しているため比較的頑健だった。これは「全体を要約するキャッシュが常に局所検索より良い」という主張ではなく、**必要な証拠が分散しているかどうか**が適合性を左右することを示す。

### RULERと圧縮計画の移植性

原著図10ではQwen3-4B-Instruct-2507を用い、圧縮率0.75の条件で、CacheNotesが問い合わせ対応型FINCHよりString Matchで2ポイント高く、問い合わせ非依存のExpected Attentionより55ポイント高いと報告する。この比較はRULERの特定の保持率とモデルであり、あらゆる長文脈QAで55ポイント改善するわけではない。原著付録ではQwen3-32Bも追加しているが、独立にモデル規模を変えた全課題の実測を網羅しているわけではない。

タスクを変えたCPTsの流用は弱点となる。要約用CPTsを別タスクへ使った`CacheNotes-S`では、Passage Countで3.8ポイント、Passage Retrievalで12.5ポイント、TRECで8.0ポイント低下する（原著図9）。この負の結果は、圧縮前に「何を重要とみなすか」をタスクごとに設計する必要があることを裏付ける。タスク説明が曖昧な場合や、利用者の質問が多種類にわたる場合は、単一キャッシュだけで十分とは限らない。

コード補完では、デフォルトのCPTs生成指示が大域的な意味要約を優先し、カーソル直前の変数名や構文を取りこぼす。原著付録表4のLCCでは、512/1024/2048トークン予算でデフォルトの39.53/46.20/51.06が、コード補完例を一つ追加した指示により50.65/52.35/52.54へ改善する。これは**圧縮アルゴリズムの変更ではなくCPTs生成プロンプトの改善**による結果である。性能比較の際には指示テンプレートを明記する必要がある。

## 定量結果：遅延・GPUメモリ・前処理費用

原著表2は単一H100、質問512トークン、検索予算8Kトークンの条件で、文書長を16K〜128Kへ変えた初回トークン遅延（TTFT）とピークGPUメモリを示す。

| 方式 | 16K文書 | 32K文書 | 64K文書 | 128K文書 |
|---|---|---|---|---|
| 全文Prefill | 1.03秒 / 17.92GB | 2.31秒 / 19.88GB | 5.22秒 / 23.78GB | **15.88秒 / 31.6GB** |
| 問い合わせ対応圧縮 | 1.19秒 / 16.95GB | 2.38秒 / 16.95GB | 5.70秒 / 16.95GB | 17.33秒 / 16.95GB |
| 非圧縮KVの事前キャッシュ（CAG） | 0.17秒 / 17.92GB | 0.20秒 / 19.88GB | 0.21秒 / 23.78GB | 0.28秒 / 31.6GB |
| RAG | 0.61秒 / 16.95GB | 0.61秒 / 16.95GB | 0.61秒 / 16.95GB | 0.61秒 / 16.95GB |
| CacheNotes | **0.13秒 / 16.95GB** | **0.13秒 / 16.95GB** | **0.13秒 / 16.95GB** | **0.13秒 / 16.95GB** |

128KでCacheNotesのオンラインTTFTはRAG比`0.61/0.13≈4.69倍`短く、全文Prefill比`15.88/0.13≈122倍`短い。しかし**この比較にCPTs生成・圧縮の初期費用は含まれない**。原著§5によると、100Kトークン文書をH100で圧縮する場合、2KトークンのCPTs生成に13.5秒、圧縮に25.9秒、合計39.4秒かかる。単純な全文Prefillの15.9秒に対して約2.5倍のオフライン費用である。複数質問へ再利用すれば償却できるが、質問が一度だけなら必ずしも得にならない。

また表2のピークメモリ16.95GBは基盤モデル等を含む実験条件の値であり、KVだけの占有量を意味しない。CacheNotesは元コーパス全体のKVを常時GPUへ保持する必要がないため文書長に対してメモリがほぼ一定だが、オフライン圧縮時には別途元文書を処理するためのメモリが必要になる。表2のオンラインメモリだけで初期圧縮の実行可能性を判断してはいけない。

## 既存方式との違い

CAG（Cache-Augmented Generation）は全文のKVを事前に作って再利用するため質問時のPrefillを節約できるが、保存KVのメモリ量が文書長に比例する。CacheNotesは**保存するKV自体を圧縮**し、オンライン遅延と常駐容量を抑える。問い合わせ対応型KV圧縮は質問を見てから重要な位置を選べるため精度を保ちやすいが、質問ごとに圧縮計算が必要で、低遅延の多問応答には不利なことがある。

問い合わせ非依存の一般的なKV圧縮は、将来の質問を見ずに注意統計や位置規則でトークンを選ぶため、広いタスクで重要な情報を残しにくい。CacheNotesは個別質問は見ないまま、**タスク説明に基づくCPTsを疑似問い合わせとして利用する**ことで、両者の中間を狙う。原著図8では、CPTsのテキストだけを回答時に与える方式より、CPTsで選んだ元文書KVを使う方式が高品質である。したがって「文章の要約をキャッシュに保存するだけ」という説明は不正確である。

## 制約・負の結果・再現性

第一に、コーパスとタスクが安定し、同じ圧縮キャッシュを多数の質問へ再利用することが前提となる。文書が頻繁に更新される場合、更新部分のCPTs生成・圧縮をやり直す必要がある。著者は文書単位の差分更新を提案するが、文書間の相互依存が変わった場合に古いCPTsがどの程度失効するかは、独立に十分検証されていない。

第二に、元の文書から削除されたKVは質問時に復元できない。直接検索、細かい数値、構文依存のコード補完ではRAGや全文入力が優位になる場合がある。要約用CPTsを検索課題へ転用すると大きく悪化するため、タスク分類・複数キャッシュ管理・再圧縮の運用が必要になる可能性がある。

第三に、オンラインTTFTが短くても、CPTs生成と圧縮の前処理は元文書長に依存する。大規模な知識ベースでは、初期構築時間、文書更新頻度、圧縮KVの保存先、同時利用者のアクセスパターンを含めた総費用で評価する必要がある。表2の単一H100の数値は、12GBの一般向けGPUへ直接適用できない。少なくとも実験の16.95GBピークを超えるGPUメモリが必要な構成であるため、同一モデル・同一方式をRTX 4070 SUPER 12GBにそのまま載せられるとはいえない。

第四に、企業ノートの品質は自動生成質問とモデルによるペアワイズ判定を含む。実際の業務利用者が作成した質問や人間評価の結果と同じではない。RULERのString Matchも完全一致や厳密な意味的正答率と異なる。論文の平均改善はデータセットと保持率に依存するため、数値を単独で引用せず、モデル・課題・予算・評価指標を併記する。
