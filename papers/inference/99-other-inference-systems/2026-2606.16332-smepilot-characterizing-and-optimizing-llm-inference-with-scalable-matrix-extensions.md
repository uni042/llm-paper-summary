# SMEPilot: Characterizing and Optimizing LLM Inference with Scalable Matrix Extensions

> CPU内のSMEと通常コアを共有帯域込みのルーフラインで使い分け、タイル分割・注意パイプライン・配置再利用によりLLM推論をllama.cpp比最大3.94倍高速化する。
## 書誌情報
- **著者**: Feiyang Chen, Haibo Chen
- **著者・所属**: IPADS, Shanghai Jiao Tong University
- **公開**: arXiv:2606.16332v1
- **種別**: Preprint
- **対象**: LLM推論、CPU推論、Arm SME、異種実行、ルーフラインモデル、KVキャッシュ
- **実装**: C/C++で実装。SMEカーネルはKleidiAIの最適化アセンブリマイクロカーネルとArm C Language ExtensionsのSME組込み関数を使用。著者公式コードURLは一次資料で確認できない。
## 概要
Armのスケーラブル行列拡張（SME）をLLM推論へ単純適用すると、CPUコアと共有するメモリ帯域、非線形ベクトル処理、データ配置変換のため性能が頭打ちになる問題を扱う。SMEPilotはCPUのみ・SMEのみ・両者協調の複数計算上限を持つルーフラインモデルで演算子形状ごとの実行先を決め、計算律速の行列演算ではタイル単位でCPUとSMEへ分割し、注意ではSME向き行列段とCPU向きベクトル段をパイプライン化し、重みとKVキャッシュのSME向け配置を再利用する。Llama-3.2-3B、Qwen3-4B、Qwen3-30B-A3BをApple M4 Pro、MediaTek Dimensity 9500、KunPeng 920で評価し、llama.cpp比でエンドツーエンド最大3.94倍、プリフィル1.13〜5.42倍、デコード最大3.48倍を達成する。

SMEPilotはCPU、SME、混合SME+CPUの三つの計算上限と一つの共有メモリ帯域上限を持つ複数上限ルーフラインを構築し、メモリ律速・バックエンド非対称の尾根越え・計算律速の三領域へ演算子を分類する。その分類を実行計画へ直接つなぎ、計算律速では同一行列をSMEとCPUへタイル分割し、注意では行列段とベクトル段を跨いで両資源を時間的に重ね、静的重みと動的KVキャッシュではSME向け配置変換を要求の臨界経路から外す。単一カーネルのSME最適化ではなく、プリフィル・デコード・FFN・MoE・注意を通したシステム全体の資源編成を扱う点が新しい。
## 問題設定
CPU内に高スループット行列器SMEが追加されても、LLM推論の全演算子をSMEへ置換すれば速くなるわけではない。SMEと通常CPUコアは計算資源としてはほぼ加算可能だが、キャッシュとメモリ帯域を共有する。プリフィルの大規模GEMMは計算律速、単一トークンデコードはメモリ律速、バッチデコードはその中間に移動し、softmaxや正規化は通常CPUコアの方が速い。さらにSMEカーネルはタイル向けのパック済み配置を要求するため、毎回の変換が帯域を消費して理論的なSME利得を消す。必要なのは固定バックエンドではなく、要求形状と演算子ごとにCPU、SME、協調実行を切り替える推論系である。
## 新規性
SMEPilotはCPU、SME、混合SME+CPUの三つの計算上限と一つの共有メモリ帯域上限を持つ複数上限ルーフラインを構築し、メモリ律速・バックエンド非対称の尾根越え・計算律速の三領域へ演算子を分類する。その分類を実行計画へ直接つなぎ、計算律速では同一行列をSMEとCPUへタイル分割し、注意では行列段とベクトル段を跨いで両資源を時間的に重ね、静的重みと動的KVキャッシュではSME向け配置変換を要求の臨界経路から外す。単一カーネルのSME最適化ではなく、プリフィル・デコード・FFN・MoE・注意を通したシステム全体の資源編成を扱う点が新しい。
## 手法
### 手法のあらまし
最初にオフライン性能計測器が対象CPUについてSME数、SME行列・ベクトル処理量、CPUコア数、コア当たり行列・ベクトル処理量、共有メモリ帯域、キャッシュ容量を測る。これらはハードウェア固有なのでモデルや要求ごとに再計測しない。オンライン計画器は各要求のモデルグラフと形状から演算量W、メモリ交通量Q、算術強度W/Qを求め、CPUのみ・SMEのみ・混合の三候補について共有帯域Bと各計算上限Pから達成可能性能min(P, B×W/Q)を比較する。

メモリ律速ならCPU、CPUでは計算律速だがSMEでは帯域律速になる尾根越え領域ならSME、両方で計算律速なら混合実行を選ぶ。混合行列演算では選択したCPU/SMEワーカの実測有効処理量比から理想分割率を求め、両カーネルのタイル境界に丸め、両側完了時刻の最大値が小さい分割を採用する。注意ではQK行列積、softmax等のベクトル処理、PV行列積をタイル化してSMEとCPUの段を重ね、時間的な遊休を減らす。

最後に配置認識ランタイムが計画を実行する。SMEで使う静的重みはモデル読込時に一度パックして保持し、K/Vは生成側でSME向けKVキャッシュ配置へ直接書くため、各注意呼出しで過去キャッシュを再パックしない。こうしてオフライン測定→要求別配置判断→タイル分割/パイプライン→配置状態維持という流れで、SMEの計算量を増やしても共有帯域や変換費用で逆効果になる形状を避ける。

### 複数上限ルーフラインと配置判断
SMEとCPUコアの行列処理量はApple M4 ProでSME 2.92 TFLOP/s、CPU 1.85 TFLOP/s、混合4.27 TFLOP/sとほぼ加算できる一方、読み出し帯域はCPU 247 GB/s、SME 224 GB/sで混合しても帯域上限は増えない。この非対称性を一つの共有帯域屋根とCPU・SME・混合の三計算屋根で表す。

算術強度がCPU尾根点より低い単一トークンGEMV等はCPU、CPUとSMEの尾根点の間にあるバッチGEMM等はSME、SME尾根点より高い大規模プリフィル行列は混合へ置く。非線形演算はSMEの外積器を活かしにくくCPUへ置く。これにより要求形状で同じ演算子の配置が変わる。

### タイル単位のCPU-SME共同実行
計算律速行列を演算子丸ごと一方へ渡さず、出力次元を独立タイルへ分けてSMEワーカとCPUワーカが同時処理する。ワーカ数はカーネル固有タイルより小さな領域や非整列境界を作る候補を除外し、過剰分割によるスケジュール費を避ける。

分割率は選択カーネルとワーカ数で実測した有効処理量からSME/(SME+CPU)として計算し、両側のネイティブタイル境界へ丸める。近傍候補ではSME側とCPU側の予測完了時刻の最大値が最小の境界を選び、固定FLOP比ではなく実効性能とタイル制約を反映する。

### 段階認識注意パイプライン
注意はQK行列積、softmax・マスク・reduction、PV行列積が連なるため、行列段をSMEだけ、ベクトル段をCPUだけに逐次実行すると片方が待つ。SMEPilotは注意を小さなタイルへ分け、依存が許す範囲であるタイルのCPUベクトル段と次タイルのSME行列段を重ねる。

これにより演算子単位のルーフラインでは見えない時間的バブルを埋める。M4 Proのアブレーションではパイプラインを外すと4096系列長のプリフィル注意遅延が2.07倍になり、実際の速度向上が単なるSMEカーネル置換ではなく異種段階の重畳に依存することを示す。

### 配置認識ランタイム
SMEは専用タイル配置を要求するため、要求ごとに通常配置からパックすると追加の読み書きが共有メモリ帯域を消費し、ルーフラインが予測した利得を相殺する。そこでランタイムはテンソルごとの現在配置を状態として追跡する。静的重みはモデルと実行計画が決まる読込時に一度だけSME向けにパックして専用コピーを保持し、同じ重みを各要求で再変換しない。これにより重み変換を要求の臨界経路から完全に外す。

動的活性は事前変換できないため、下流がSMEなら生成側で直接必要配置へ変換する。特にK投影とV投影の出力を、通常CPUのトークン連続行配置ではなくSMEベクトル長とカーネルタイル形状に合わせたK/V別のKVキャッシュへ書き込む。以後の注意は過去トークンを毎回パックし直さずそのまま読む。M4 ProのデコードGEMVでは臨界経路上の素朴なパックが0.52msを1.71msへ増やすため、この生産者側変換と配置再利用がSMEの高い行列処理量を実効性能へ変えるために不可欠である。

### 全体のデータ／制御の流れ
全体はオフライン性能計測器、オンライン計画器、SME対応推論ランタイムの三層で構成される。計測器がハードウェア固有性能を一度収集し、計画器が現在のモデルと要求形状に応じて演算子配置、スレッド数、分割形状を決める。

ランタイムはFFN/MoE、QKV投影、注意へそれぞれタイル分割、パイプライン、パック済み配置を適用する。C/C++実装で、SMEカーネルにはKleidiAIのアセンブリマイクロカーネルとACLE SME組込み関数を使う。CPU内のSMEを独立アクセラレータではなく共有帯域を持つ異種実行資源として扱う設計である。
## 評価条件
- **ハードウェア**: Apple M4 Pro CPU、MediaTek Dimensity 9500、SME対応KunPeng 920 72F8 Server CPU。M4 ProとDimensityでは性能コア数に合わせてそれぞれ10、8スレッド、KunPengは公平比較のため10スレッド。M4 Pro上ではSME/CPUの計算量・帯域特性、消費電力、GPU比較も測定する。
- **ソフトウェア**: SMEPilotはC/C++。SMEカーネルはArm KleidiAIの最適化アセンブリマイクロカーネルとArm C Language Extensions SME組込み関数を利用。主要エンドツーエンド基準は各プラットフォームのllama.cpp既定CPUバックエンド。演算子比較にはApple Accelerate、GGML CPU、Arm KleidiAI SME、FlashAttention CPU、素朴なSME注意を用いる。
モデルは密なLlama-3.2-3B、Qwen3-4BとMoEのQwen3-30B-A3Bで、30B-A3Bは端末メモリへ収めるため4ビット重み量子化を使う。タスクはRuler-4K/8K長文QA（平均プリフィル3324/7338、デコード4トークン）、GSM8K数学QA（平均プリフィル92、デコード100）、LongWriter-6K長文生成（平均プリフィル339、デコード5424）。系列長またはバッチを掃引し、プリフィルとデコードのエンドツーエンド遅延をllama.cppと比較する。M4 ProではFFN GEMM、注意、デコードFFN、デコード注意を演算子別に測り、タイル分割・注意パイプライン・配置認識を一つずつ外すアブレーションを行う。Qwen3-4B/Ruler-4KではmacOS powermetricsでシステム電力とエネルギーを測定し、Llama-3.2-3B/GSM8KではM4 Pro統合GPUとも比較する。
Arm SME/SME2を持つCPU上のLLM推論が対象。CPU通常コアとSMEは共有キャッシュ・メモリ帯域を持つという前提でモデル化する。評価は三CPU世代、三モデル、三実用タスクを含むが、NVIDIA/AMD GPUサーバやx86行列拡張、NPUとの共同実行は対象外。GPU/NPUとのより広い配置、転送費・メモリ配置を含む計画は将来課題である。
## 主要結果
SMEPilotは三つのSME対応CPUとLlama-3.2-3B、Qwen3-4B、Qwen3-30B-A3Bで、llama.cpp CPU比のエンドツーエンド速度を最大3.94倍へ改善した。プリフィルは1.13〜5.42倍、デコードは最大3.48倍で、M4 ProのプリフィルFFNは4.10〜4.44 TFLOP/s、GGML CPU比6.06〜7.43倍、Apple Accelerate/KleidiAI SME比1.30〜1.67倍を示す。注意はFlashAttention CPU比1.56〜3.50倍、デコード注意は1.32〜4.75倍。Qwen3-4B/Ruler-4Kではエネルギーを482.813Jから233.931Jへ削減した。

- エンドツーエンド速度向上 / 最大3.94倍 (比較対象: llama.cpp CPU; 条件: 三CPU、三モデル、Ruler/GSM8K/LongWriter構成) — 演算子単体だけでなく実アプリケーション全体でSME協調実行の利得を確認。

- プリフィル速度向上 / 1.13〜5.42倍 (比較対象: llama.cpp CPU; 条件: エンドツーエンドのプリフィル段) — 大きな行列が計算律速になりSME+CPU混合が効きやすい。

- デコード速度向上 / 最大3.48倍 (比較対象: llama.cpp CPU; 条件: エンドツーエンドのデコード段) — 小バッチはCPUに残し、算術強度が上がる形状だけSMEへ移す動的配置が有効。

- M4 ProプリフィルFFN / 4.10〜4.44 TFLOP/s、GGML比6.06〜7.43倍、SME単独系比1.30〜1.67倍 (比較対象: GGML CPU、Apple Accelerate、KleidiAI SME; 条件: プリフィル長512〜8192、B×3072×8192 GEMM) — SME単独より通常CPUコアも同時利用するタイル分割が追加利得を生む。

- 注意速度向上 / プリフィル1.56〜3.50倍、デコード1.32〜4.75倍 (比較対象: FlashAttention CPU; 条件: M4 Pro、形状/トークン幅を掃引) — 行列段とベクトル段の異種パイプラインが注意の時間的バブルを削減する。

- エンドツーエンドエネルギー / 482.813±23.213J → 233.931±2.751J (比較対象: llama.cpp → SMEPilot; 条件: M4 Pro、Qwen3-4B、Ruler-4K、各n=3) — 平均電力も26.050Wから22.611Wへ下がり、短い実行時間と合わせて約0.485倍のエネルギー。

### 負の結果・境界条件
- バッチ1〜2のGSM8Kでは演算子がメモリ律速なのでSMEPilotは基準と同程度で、SMEを使っても大きな利得がない。MoEではトークンが複数エキスパートへ分散して各エキスパートの実効バッチが小さくなり、行列がメモリ律速へ寄るため一部タスクの速度向上が密モデルより小さい。タイル分割を外すとGEMM遅延1.46倍、注意パイプラインを外すとプリフィル注意2.07倍、臨界経路上で素朴に配置変換するとデコードGEMVが0.52msから1.71msへ悪化する。

### 結果の読み方
SMEの高い行列ピークそのものより、形状ごとに共有帯域の律速点を見極めてCPU/SME/混合を切り替えることが重要である。大きいプリフィルは両計算資源を同時利用し、小さいデコードはCPUへ残し、中間の尾根越え領域だけSMEへ移すことで、SMEを万能なCPU置換として使う失敗を避ける。
## 品質への影響
モデル演算を近似化する手法ではなく、実行先・分割・配置を変更するため、論文は生成品質低下との交換ではなく同一モデルの性能・エネルギーを評価する。Qwen3-30B-A3Bのみ端末メモリ制約から4ビット重み量子化を評価設定として使用する。
## 既存研究との差
従来のSME研究はGEMMなど個別カーネルのピーク性能とタイル配置を最適化するのに対し、SMEPilotはLLM全体でSMEをいつ使わないかまで含めて決める。llama.cppのような通常CPU推論やKleidiAI/Apple AccelerateのSME単独行列カーネルに対し、SMEPilotはCPUとSMEの計算能力が加算可能だが帯域は共有される点をモデル化し、演算子形状ごとにCPUのみ・SMEのみ・混合を切り替える。またFlashAttention CPUとの比較では、注意を一つのCPU演算として最適化するのではなく、SME向き行列段とCPU向きベクトル段をタイル間で重ねる。
## 限界
評価はArm SME/SME2を持つApple、MediaTek、KunPengの三CPUに限られ、x86のAMX等へ同じ閾値やタイル分割則がそのまま移るとは限らない。ルーフラインは共有帯域と計算上限を中心にしたモデルで、実際のキャッシュ競合やSME命令を発行するCPUコアとの干渉を完全に隔離できない。著者自身も現行SMEはベクトル/GEMV、配置変換、CPUコアとの分離に改善余地があると述べる。GPU/NPUとの共同実行、デバイス転送費、より広いメモリ配置は扱わない。公式公開コードURLも一次資料で確認できないため再現性は実装記述に依存する。
## 実装状態
C/C++の実動推論エンジンを実装し、KleidiAIのアセンブリマイクロカーネルとACLE SME組込み関数を利用して、スマートフォン級SoC、PC級M4 Pro、サーバ級KunPengで実機評価している。オフライン計測器、オンライン計画器、タイル分割、注意パイプライン、重み/KV配置管理まで実装評価されている。一方、論文本文には著者公式の公開コードリポジトリURLがなく、第三者が同一実装を取得できる状態は確認できない。
## 研究上の位置づけ
LLM推論基盤の観点では、SMEPilotはGPUオフロードではなくCPU内部の異種計算資源編成に位置する。重要なのは『アクセラレータがあれば全演算を移す』のではなく、算術強度と共有メモリ帯域から実行先を要求ごとに決める点であり、CPU/NPU/GPUや統合メモリ環境の共同推論にも一般化し得る設計原理である。

MoEでは各エキスパートへ分散した結果、実効バッチが小さくなってSME利得が減るという観測も、エキスパート配置・バッチ形成・CPUオフロード研究と接続する。将来GPU/NPUまで含める場合は、本稿の計算上限だけでなく転送費、メモリ配置、KVキャッシュ、エキスパート常駐を同じ計画器へ組み込む必要があり、階層メモリ研究との接点が大きい。
