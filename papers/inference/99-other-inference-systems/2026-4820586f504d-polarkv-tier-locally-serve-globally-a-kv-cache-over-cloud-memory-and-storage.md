# PolarKV: Tier Locally, Serve Globally–A KV Cache over Cloud Memory and Storage

> 分散メモリを帯域層、クラウドブロックストレージを容量層とし、対応シャードを同一VMへ共置してKVの階層移動をローカル化することで、クラウドのネットワーク帯域と費用の制約を抑えるKVキャッシュ基盤。
## 書誌情報
- **著者**: Yingqiang Zhang, Xinjun Yang, Hao Chen, Feifei Li, Shuwen Wang, Chuan Sun, Sai Wu, Ninglong Weng
- **著者・所属**: Zhejiang University; Alibaba Cloud Computing
- **公開**: PVLDB 19(12), VLDB 2026
- **種別**: Journal/Conference proceedings paper
- **対象**: KVキャッシュ、分散メモリ、クラウドブロックストレージ、RDMA、階層キャッシュ、LLM推論
- **実装**: Alibaba Cloudで独立KVキャッシュサービスとして商用展開。軽量クライアントライブラリでvLLMとSGLangへ非侵襲的に接続し、分散メモリへのRDMAアクセスとESSDへの非同期退避を実装する。
## 概要
クラウド上のKVキャッシュでは、メモリ容量だけでなく仮想マシンのネットワーク帯域、ブロックストレージの容量と帯域の結び付き、運用費が同時に制約になる。PolarKVは分散メモリを帯域層、クラウドブロックストレージを容量層として扱い、両層を同じ仮想マシン上の対応シャードとして組み合わせる。冷たいKVを対応ストレージへローカルに退避し、必要時に同じシャードへ戻すことで、従来の二層グローバルプールが生む仮想マシン間の階層移動を避ける。RDMAによる直接アクセス、接頭辞ハッシュ、全体メタデータ管理、局所性を使う要求振り分けを統合し、Alibaba Cloudの商用KVキャッシュサービスとしてvLLMとSGLangへ接続する。公開ベンチマークと実運用で先頭トークンまでの時間を最大80%削減した。

PolarKV固有の着想は、メモリとストレージを二つの全体キャッシュ層として扱うのをやめ、両方を同じ粒度のシャードへ分割して対応する一対を同一VMに置くことである。これにより、熱いKVを保持するメモリは帯域を供給し、冷たいKVを保持するブロックストレージは容量を供給する一方、両者の階層移動はVM内の局所I/Oになり、クラウドで最も制約の強いVM間ネットワーク帯域を消費しない。単なるDRAM＋SSDの二層化ではなく、クラウド料金とネットワーク制約から逆算して階層の配置単位を変更した点が新規性である。

代表結果として、LooGLEでのTTFTは固定クラウド費用でQwen3-235B-A22BとSGLangを使用で3FSを外部KVバックエンドとして使うストレージ中心構成に対して47〜53%削減。同予算のストレージ中心共有KVより、メモリ帯域を前段に置きストレージを容量層に限定する方が、再利用KVを低遅延で供給できることを示す。
## 問題設定
長文LLMではGPU上のKVキャッシュ容量が不足するため、ホストメモリ、遠隔メモリ、ストレージへ接頭辞KVを保存して要求間で再利用する。しかしクラウドでは、ブロックストレージの帯域が契約容量に連動し、高帯域ストレージを使うには大容量契約と高帯域VMが必要になる。遠隔DRAMもVMのネットワーク帯域で頭打ちになり、大容量メモリを買っても帯域を使い切れない。さらに従来の二層キャッシュはメモリ層とストレージ層を別々の全体プールとして扱うため、層間移動そのものが貴重なVM間ネットワークを消費する。したがって単純なメモリ専用、ストレージ専用、従来型階層化のいずれも性能・容量・費用を同時に満たしにくい。
## 新規性
PolarKV固有の着想は、メモリとストレージを二つの全体キャッシュ層として扱うのをやめ、両方を同じ粒度のシャードへ分割して対応する一対を同一VMに置くことである。これにより、熱いKVを保持するメモリは帯域を供給し、冷たいKVを保持するブロックストレージは容量を供給する一方、両者の階層移動はVM内の局所I/Oになり、クラウドで最も制約の強いVM間ネットワーク帯域を消費しない。単なるDRAM＋SSDの二層化ではなく、クラウド料金とネットワーク制約から逆算して階層の配置単位を変更した点が新規性である。
## 手法
### 手法のあらまし
要求が到着すると、まず推論ノード側プロキシが各ノードのローカル接頭辞KVとの親和性を見て実行先を選ぶ。選ばれた推論エンジンのPolarKVクライアントは入力トークン列をチャンクへ分割し、先行チャンクのハッシュを次チャンクへ連鎖させて、文脈全体を反映する接頭辞鍵列を作る。読込では各鍵をKV管理サーバへ問い合わせ、メモリ所在なら返されたSlab Nodeの物理アドレスから片方向RDMAでKVを直接取得してプリフィル再計算を省く。ストレージ所在なら、管理サーバがそのストレージと対になったSlab Nodeへメモリ領域を確保し、同じVMのディスクサーバへESSDからの読戻しを依頼する。読戻し完了後に配置メタデータをメモリ所在へ更新し、推論ノードがRDMAでKVを取得する。保存では新しく計算したKVを管理サーバが割り当てたSlab NodeへRDMAで書く。メモリ使用率が閾値へ達するとLRUで冷たいKVを選び、同居ディスクサーバが背景処理でESSDへ退避し、完了後にメタデータをストレージ所在へ切り替える。ストレージも閾値に達すると古いKVをLRUで削除する。この保存→局所退避→局所復帰→RDMA配信の流れにより、容量拡張のための層間転送をVM間ネットワークから除外する。どの段階でも管理サーバやデータノードが失敗した場合はキャッシュミスとして通常のプリフィル計算へ戻るため、KVサービスは性能を上げるが推論結果の正しさには必須にならない。

### シャード対の共置階層
入力は分散メモリ上のKV領域と、クラウドブロックストレージとして契約した容量である。PolarKVは両者を独立した全体プールにせず、同じ粒度のシャードへ分割し、メモリシャードと対応ストレージシャードを同じメモリ提供VMへ配置する。熱いKVはメモリシャードに残し、冷たいKVは同居するESSDへ移す。再利用時も同じESSDから対応メモリへ戻す。したがって階層間の大容量KV転送はVM間ネットワークを通らず局所I/Oで完結し、ネットワーク帯域を推論ノードから共有メモリへの実アクセスに集中できる。

### KV管理サーバとRDMAデータ経路
入力は接頭辞チャンクから得たハッシュ鍵と保存・読込要求である。KV管理サーバは分散メモリのHome Nodeへ領域確保を依頼し、返されたSlab Nodeと物理領域を鍵に対応付けて全体メタデータへ記録する。推論側クライアントはまずRDMA型RPCでこのアドレスを解決し、その後KV本体は管理サーバを経由せずSlab Nodeへ片方向RDMAで直接読み書きする。管理サーバは配置と寿命の制御だけを担い、大容量データ面を分離するため、CPUコピーと中央サーバの帯域ボトルネックを避けられる。

### 接頭辞連鎖ハッシュ
入力は推論要求の完全なトークンID列である。クライアントはこの列を複数の連続チャンクへ分割し、最初のチャンクではそのトークン列から鍵を作り、次のチャンク以降では現在チャンクのトークンIDに直前チャンクのハッシュ値も結合して新しい鍵を計算する。このため、途中の数トークンが偶然一致するだけでは鍵は一致せず、その位置までの接頭辞全体が同じ要求だけが同じKVを指す。生成した鍵列をKV管理サーバへ順番に問い合わせ、一致する先頭チャンク群について保存済みKVの物理配置を得る。推論エンジンは得られたKVを再利用し、一致しなくなった後続部分だけをプリフィル計算する。結果として長い会話履歴やエージェントの反復要求で、正しさを保ったまま共通接頭辞の注意状態計算を細粒度に省ける。

### 非同期ストレージ退避と再読込
入力はメモリ使用率と各KVの最近使用状況である。メモリ圧迫時、管理サーバはLRUに基づいて冷たいKVを選び、鍵・メモリアドレス・サイズを、そのSlab Nodeと同居するディスクサーバへ送る。ディスクサーバは背景スレッドでESSDへ書き、完了通知後に管理サーバが所在をストレージへ更新する。読込対象がESSDにある場合は、同じ対のSlab Nodeに新しいメモリ領域を確保し、ディスクサーバが局所I/Oでそこへ読み戻してから推論側がRDMAで取得する。ストレージも閾値に達するとLRUで古いKVを削除し、容量を制御する。

### 局所性ルーティングと障害時再計算
入力は新しい推論要求と各推論ノードに残る小規模なローカルDRAM KVの局所性情報である。推論ノード側プロキシは要求を、利用できる接頭辞KVが最も多いノードへ優先的に振り分け、共有キャッシュへ行く前にローカル再利用を増やす。管理サーバやメモリ・ストレージノードが一時停止した場合、クライアントは進行中操作を含めてキャッシュミスとして扱い、推論エンジンに通常の注意状態再計算を行わせる。失われるのは高速化用状態だけなので出力の正しさは保たれ、同期複製を必須にせず前進性を確保できる。

### 全体のデータ／制御の流れ
システムは推論ノード、推論ノード側プロキシ、KV管理サーバ、分散メモリのHome NodeとSlab Node、各Slab Nodeと同居するディスクサーバ、各VMへ直接接続されたESSDから構成される。制御面ではKV管理サーバが鍵から配置へのメタデータ、領域割当、追い出し、ストレージ状態を管理する。データ面では推論ノードがSlab Nodeへ片方向RDMAで直接アクセスし、冷たいKVのメモリ・ESSD間移動だけを同一VM内のディスクサーバが担当する。プロキシは要求をローカルKV親和性の高い推論ノードへ送る。管理サーバ障害時のメタデータは外部クラウドデータベースから復旧し、データノード障害時は該当KVだけを無効化して再計算へフォールバックする。
## 評価条件
- **ハードウェア**: 全評価はAlibaba Cloudの実機で行う。GPUインスタンスは8基のNVIDIA H20 96GB GPUを搭載する。外部KV層はECS仮想マシンのDRAMとAlibaba Cloud ESSDブロックストレージを用い、分散メモリへのデータ経路はRDMAを使用する。固定費用比較では3FSが39VMと67本の320GB PL0 ESSD、Mooncakeが58VM、PolarKVが156GBメモリと21.4TBストレージを使用する。
- **ソフトウェア**: 推論エンジンはvLLMとSGLangを評価し、モデル系列はDeepSeek、Qwen、GLMを含む。公開長文比較の主要条件ではSGLangとQwen3-235B-A22Bを用いる。本番事例ではSGLangとGLM-4.7を用いる。比較対象は外部KVなし、3FSを外部KVバックエンドにしたストレージ中心構成、Mooncakeの遠隔メモリ中心構成、PolarKVのメモリのみ構成である。
- **比較対象**: 外部KVキャッシュなし、3FS外部KVバックエンド、Mooncake遠隔メモリKV、PolarKVメモリ層のみ
合成マイクロベンチマークで入力長と並行度に対するKV読込性能を測り、LooGLEとSCBenchで実アプリケーションに近い長文接頭辞再利用を評価する。システム間比較では月額クラウド資源費を約1.84万CNYに揃え、少なくとも約12GB/sの集約KV読込帯域を用意して、単なる予算差を抑える。さらに自動運転分野の顧客Coding Agentでオンラインのカナリア展開を行い、通常運用中の問い合わせ遅延を測る。
シミュレーションではなくAlibaba Cloud上の実ハードウェア測定と実本番カナリア展開である。一方、料金・帯域の結合はAlibaba CloudのECSとESSD仕様に依存するため、AWSやAzureでも同様の傾向はあると論文は述べるものの、同じ最適資源比や同じ改善率が他クラウドへ直接一般化するとは限らない。またSCBenchは紙幅の都合で代表タスクのみを掲載する。
## 主要結果
PolarKVの主結果は、同程度のクラウド費用と必要読込帯域を揃えた条件で、メモリだけでは容量不足、ストレージだけではI/O・分散ファイル処理が重いという両極端を避け、長文KVの作業集合が大きいほどTTFTを大きく下げることである。公開ベンチマークでは3FSに対して47〜58%、Mooncakeに対して最大58%のTTFT削減を示し、本番Coding Agentでも平均問い合わせ遅延を21.42秒から12.34秒へ短縮した。実用上は、KVを圧縮せずにクラウド資源の配置とデータ移動経路を変えるだけで、共有接頭辞再利用を大容量化できることを示す。

- LooGLEでのTTFT / 47〜53%削減 (比較対象: 3FSを外部KVバックエンドとして使うストレージ中心構成; 条件: 固定クラウド費用でQwen3-235B-A22BとSGLangを使用) — 同予算のストレージ中心共有KVより、メモリ帯域を前段に置きストレージを容量層に限定する方が、再利用KVを低遅延で供給できることを示す。

- 大きいKV作業集合でのTTFT / 41〜58%削減 (比較対象: 3FSおよびMooncake; 条件: LooGLEのshortdep_clozeとlongdep_qa) — 作業集合がMooncakeの遠隔メモリ容量を超えると追い出しが増える一方、PolarKVは21.4TB容量層を同予算で維持できるため、階層設計の効果が拡大する。

- LooGLE＋SCBench全体のTTFT / 3FS比47〜58%削減、Mooncake比3〜58%削減 (比較対象: 3FSおよびMooncake; 条件: 公開長文ベンチマークの評価タスク) — メモリ中心とストレージ中心のどちらか一方へ固定するより、作業集合の大小が変わる複数タスクで低TTFTを維持できることを示す。

- 本番Coding Agent問い合わせ遅延 / P90 49.73→24.91秒、P50 13.88→6.81秒、平均21.42→12.34秒 (比較対象: PolarKV導入前の256基H20クラスタでGPU HBMと各GPU 40GBのノードローカルホストメモリへKVを保存する構成; 条件: SGLang＋GLM-4.7、平均入力71Kトークンのオンラインカナリア展開) — 合成評価だけでなく、セッション内で長い接頭辞を繰り返し再利用する実エージェント負荷でも、クラスタ共有KVによってプリフィル再計算を減らし問い合わせ遅延を大幅に短縮できる。

### 負の結果・境界条件
- 小さいshortdep_qaではMooncakeの928GB遠隔メモリが再利用KVの大部分を保持できるため、PolarKVのTTFT優位は11%まで縮む。接頭辞作業集合が小さい場合は大容量ストレージ層の価値が出にくい。またキャッシュノード障害時は該当KVを再計算するため、正しさは保つが一時的に性能が低下する。論文は同じハイブリッド設計点を持つオープンソース比較対象がないことも明示している。

### 結果の読み方
Mooncakeは小さい作業集合なら高速だが容量が928GBに限られ、大きい負荷で追い出しが増える。3FSは21.4TBを持つが分散ファイルシステムの処理とメモリ未活用が効く。PolarKVは同じ約1.84万CNY/月で156GBの高速メモリと21.4TBストレージを組み合わせ、局所階層移動でネットワークを節約するため、大容量負荷で差が拡大する。
## 品質への影響
無損失のシステム最適化であり、KV表現を近似・枝刈り・量子化しない。保存済みKVが利用できれば元の注意状態をそのまま再利用し、キャッシュミスや障害時は通常のプリフィル計算でKVを再生成する。したがってモデル出力品質を交換条件にした高速化ではなく、影響は遅延と資源利用に限定される。
## 既存研究との差
Mooncakeは遠隔DRAMを主な共有KV容量とするため高速だが、同予算では保持容量が小さい。3FSは大容量SSDを提供できるが、分散ファイルシステムのメタデータ・複製処理とストレージVM間経路を伴う。従来の階層キャッシュはメモリ層とストレージ層を別々の全体プールとして扱い、層間移動がネットワーク転送になりやすい。PolarKVは両層を対応シャードへ分割し同じVMへ共置するため、共有キャッシュという外部インターフェースを保ちながら、階層移動だけを局所I/Oへ変える点で異なる。KV圧縮・量子化・疎化とも競合せず、圧縮済みKVを各層へ保存する形で併用できる。
## 限界
評価と費用モデルはAlibaba CloudのECS・ESSD仕様に依存し、他クラウドで同じ資源比や改善率になる保証はない。接頭辞再利用が少ない、または作業集合がローカル・遠隔メモリだけで十分小さい場合、ストレージ階層の追加価値は小さい。ストレージからの復帰はDRAM命中より遅く、障害時は失われたKVを再計算するため一時的に性能が下がる。同一のハイブリッド設計点を持つ公開システムとの直接比較はなく、主要比較はメモリ中心Mooncakeとストレージ中心3FSである。CXLなど別のクラウドメモリ基盤が広域利用可能になれば、RDMAとVM帯域を前提にした最適点は変化し得る。
## 実装状態
研究試作だけではなく、Alibaba Cloudで独立KVキャッシュサービスとして商用展開済みである。軽量クライアントライブラリを導入してサービス接続先を設定することで、vLLMとSGLang本体を変更せず利用できる。データ面はRDMA分散メモリとESSD、制御面はKV管理サーバと永続メタデータを用い、本番Coding Agentでオンライン評価されている。
## 研究上の位置づけ
PolarKVはKVキャッシュ圧縮のアルゴリズム研究ではなく、クラウド上で共有KVを保存・移動・再利用するシステム研究である。MooncakeやAIBrixの遠隔メモリ共有、3FSを使うSSD保存、LMCacheの外部KV接続、多階層KV管理と同じ推論基盤系統に位置するが、クラウドの料金体系とVMネットワーク帯域を第一級の設計制約として扱う。特にメモリを帯域資源、ブロックストレージを容量資源として分業させ、階層移動をVM内へ閉じる配置が中心である。
