# Unlocking Lossless Speedups in LLMs via Discrete Diffusion

> **Unoは、元の自己回帰modelを別のdiffusion modelへ置き換える研究ではない。元のAR modelが定義する生成分布を残したまま、追加した軽量diffusion weightで複数tokenを並列提案し、専用samplerで正しく補正してdecodeを進める。**

## 概要

通常の大規模言語modelは**自己回帰（Autoregressive; AR）**方式で生成する。

1 token目を出す。

そのtokenをcontextへ追加して2 token目を出す。

さらに3 token目を出す。

というように、future tokenは前tokenが確定するまで計算できない。

GPUは大きな行列演算を並列に処理するのが得意だが、AR decodeでは1 stepごとに少数tokenしか処理しないため、model weightをmemoryから読み出すcostに対して計算量が小さくなりやすい。これがdecode throughputの大きなbottleneckになる。

既存の代表解が**投機的復号（speculative decoding）**である。

小さなdraft modelがfuture tokenを複数先読みし、大きなtarget modelがまとめて検証する。draftがよく当たれば1回のtarget forwardで複数tokenを確定できる。

しかしこの方式には、

- target modelとは別にdraft model weightを持つ
- draft用KV cacheも必要になる場合がある
- draft model自体もautoregressiveなので複数stepを順番に実行する
- batch sizeが大きくなるとdraft overheadがsystem throughputを圧迫する

という問題がある。

Unoはここに**離散拡散（discrete diffusion）**を持ち込む。

ただし「AR modelをdiffusion LLMへ変える」のではない。

model parameterを

- **AR weights**: 通常のnext-token predictionを行い、最終的に守りたいtarget distributionを定義する。
- **Diffusion weights**: 複数のfuture positionを並列に提案するための追加weight。

に分ける。

最終出力の正しさはAR weights側で決め、diffusion側は高速なproposal generatorとして使う。

## 離散拡散（discrete diffusion）とは何か

画像のdiffusion modelでは、noiseだらけの画像を何stepかかけてclean imageへ近づける。

languageではtokenが離散値なので、そのままGaussian noiseを加えるわけではない。

**離散拡散（discrete diffusion）**では、複数の未確定token positionをmask/noisy stateとして持ち、何回かの更新で具体的tokenへ変えていく。

重要なのは、AR decodeのように

`position 1を確定 → position 2 → position 3`

と完全に順番待ちする必要がなく、複数positionについて同時にdistributionを計算できることである。

Unoはこの並列性を、「最終modelそのもの」ではなく**future token proposalを作る補助path**として利用する。

## 手法のあらまし

### 1. AR weightsがtarget distributionを定義する

まず通常のAR modelが存在する。

このweightは標準のnext-token prediction lossで学習され、

`P_AR(next token | prefix)`

という本来のgeneration distributionを定義する。

Unoで「qualityを維持する」と言うとき、基準になるのはこのAR distributionである。

### 2. 軽量Diffusion weightsを追加する

各layerにはAR計算用weightに加えて、future blockを並列生成するための軽量Diffusion weightsを持たせる。

既存AR modelをUno化する場合、元weightを全部置き換えるのではなく、この追加部分を学習する。

公式実装ではUno Qwen3 8Bにconditional LoRA型のdiffusion training pathも提供される。

これにより「別model processとしてdraft LLMをもう1台ロードする」構成を避ける。

### 3. Diffusion DistillationでARのfuture distributionを学ぶ

Diffusion weightsは好き勝手にparallel textを生成するのではない。

教師となるAR modelのfuture token distributionに近いproposalを作るよう、**拡散蒸留（Diffusion Distillation）**を行う。

目的は、diffusion path単独の最終qualityを最大化することではなく、AR verifierがacceptしやすいcandidate blockを安く作ることである。

proposalがtarget distributionに近いほど、1回のAR verificationで多くtokenを進められる。

### 4. block単位で複数future tokenを扱う

長sequence全体を一度にdiffusionするのではなく、prefixを条件としてfuture blockを処理する。

たとえばblock size 16なら、次の16 positionsについてdiffusion pathがまとめてcandidate informationを出す。

これによりAR modelが1 tokenずつ16回draftするのとは異なり、GPU並列性を使いやすい。

### 5. Ψ-Spec samplerでAR distributionへ戻す

ここが「lossless」の核心である。

Diffusion weightsが出したtokenをそのまま採用すると、生成分布はAR modelからずれる。

そこでUnoは**Ψ-Spec sampler**を使う。

基本的な役割はspeculative samplingと同じで、

1. diffusion pathがproposalを出す。
2. AR weightsでtarget probabilityを評価する。
3. proposal probabilityとtarget probabilityを比較する。
4. acceptできるtokenをまとめて進める。
5. rejectが起きたらtarget distributionに一致するよう補正sampleを行う。

という流れで、最終sample distributionを元AR modelと一致させる。

したがってdiffusion proposalが弱い場合でも、主にspeedupが落ちるだけで、proposalを無条件採用する近似decodeにはならない。

## 「lossless」の意味

この用語は誤解しやすい。

Unoのlosslessは、**生成される確率分布がbase AR modelのsampling distributionと一致する**という意味である。

これは

- greedyなら常にbitwise identical
- 同じrandom seedなら必ずbyte-identical text

という意味とは限らない。

samplingでは同じdistributionから別のrandom pathを取ることが普通にある。

したがってquality comparisonでは、「diffusion model独自の近似分布へ変えず、base AR modelが本来定義するdistributionを守る」という意味で読むべきである。

## 一般的なspeculative decodingとの違い

### draft modelが別modelではない

EAGLE系や通常のsmall-draft speculative decodingでは、targetとは別のdraft networkを用意する。

UnoはAR weightsとDiffusion weightsを**同じaugmented model**として持つ。

このためdeployment上、完全に別model weightと別runtimeを管理する必要がない。

### draftをautoregressiveに深く走らせない

小型draft modelでも、8 token先読みするなら通常8 sequential draft stepが必要になる。

Diffusion weightsは複数future positionを並列処理するため、draft depthそのもののsequential dependencyを減らせる。

### diffusion LLMそのものとも違う

通常のdiffusion language modelは最終generation distribution自体がdiffusion modelで決まる。

そのmodelのqualityが強いAR modelに届かない場合、speedとqualityのtrade-offになる。

UnoではAR distributionが最終authorityなので、diffusion pathはacceleration layerとして切り離されている。

## Linear SamplerとTree Sampler

公式runtimeはNano-vLLMベースで、少なくとも二つのΨ-Spec execution modeを公開している。

### 線形sampler（Linear Sampler）

主に**system throughput**を重視する。

proposal/verificationを比較的単純なlinear pathで進め、大きなconcurrencyで追加overheadを抑える。

### 木sampler（Tree Sampler）

複数candidate branchをtreeとして検証し、**per-request throughput**を高める方向。

candidate top-kやtree verify sizeなどのparameterを使い、1 roundでより長く進む可能性を増やす。

ただしtree verificationにはより複雑なattention backendが必要で、公式READMEではFlashAttention-3を追加要件としている。

つまりUno自体が1つの固定samplerではなく、同じdiffusion proposalをsystem目的に応じて使い分けるframeworkになっている。

## KV cacheの扱い

別draft modelを使うspeculative decodingでは、draft model側とtarget側で別々のKV cacheを持つことがある。

Unoは同一augmented model内でproposalとverificationを行うため、official comparisonでは追加parameterとpeak GPU memoryの面でも有利だとする。

ただし「KV cacheが不要」なわけではない。AR verificationには通常通りcontext stateが必要であり、long-context memory problemそのものを解く研究ではない。

## 評価

### throughput

論文要旨では、leading speculative-decoding methodであるDFlashやEAGLE-3などに対して、**評価したすべてのbatch sizeで高いthroughput**を報告する。

base AR model比では最大**3× speedup**。

重要なのは、小batchだけで速いのではなく、deviceがsupportする最大batch size側でもspeedupを維持したと主張している点である。

これはdraft pathが別autoregressive modelとしてsystem bandwidthを消費し続けないことが効いている。

### Uno Qwen3 8B

公式実装ではUno Qwen3 8Bを公開し、system throughputとper-request throughputの両方を測る。

公開結果ではDFlash/EAGLE-3より少ない追加parameter、shared KV構成、低いpeak memoryというsystem上の利点も強調される。

### 8B Unoとdiffusion LLM比較

Uno 8Bはagentic tool use、coding、long-context reasoningの評価で、

- 26B DiffusionGemma
- Mercury 2
- その他open diffusion LLM

を上回ったと報告する。

ここでの主張は「8Bだから26Bより一般に優秀」という単純model-size比較ではなく、**AR-quality backboneを残したdiffusion augmentationが、純diffusion modelよりquality-speed trade-offを作りやすい**という文脈で読むべきである。

## 主要結果の読み方

### 3×は全条件の固定speedupではない

acceptance length、batch size、sampler設定、model/taskでspeedupは変わる。

proposalがtargetとよく一致するtaskでは多tokenを一度に進めやすいが、予測しづらいtextではrejectが増える。

### diffusion proposalの品質が悪くてもqualityではなく速度に効く

Ψ-Specがtarget distributionへ補正するため、proposal mismatchは主にacceptance率低下として現れる。

つまり弱いdiffusion weightsではAR fallbackに近づき、speedupが縮む。

### training-freeではない

既存AR modelへ何の追加trainingもせず使える手法ではない。

Diffusion weightsをdistill/trainする必要がある。

official repoがconditional-LoRA pipelineやcurriculumを公開しているのもこのためである。

## 既存研究との差

### EAGLE / DFlash

どちらもspeculative decodingの強力なproposal方式だが、draft計算を別network/pathとして持つ。

Unoはdiscrete diffusionで複数position proposalを並列化し、同じaugmented model内へ統合する。

### Medusa系

複数headからfuture tokenを並列予測する方式と目的は近いが、Unoはdiscrete diffusion trainingとlossless samplerを組み合わせ、AR distributionから正確にsampleするframeworkとして整理する。

### diffusion LLM

最終model自体をparallel denoising modelへするのではなく、AR modelのquality distributionを残す点が大きく違う。

## 限界と適用境界

- **追加trainingが必要。** Diffusion weightsを作るdistillation/training pipelineが必要。
- **追加weightは0ではない。** separate draft modelより軽量でもmemory/parameter overheadは残る。
- **専用sampler/runtimeが必要。** vanilla vLLMへweightを置くだけでは動かない。
- **proposal quality依存。** diffusion proposalが弱いtaskではacceptanceが短くなりspeedupが縮む。
- **tree modeはruntime要件が重い。** FlashAttention-3など追加backendが必要になる。
- **long-context KV problemは別。** contextが長いほどKV memoryが増える問題そのものを圧縮しない。
- **losslessはdistribution-level。** sampling時の個々の生成textが常にbase runと同じという意味ではない。
- **training/evaluation stackが新しい。** production serving engineへ統合する際はscheduler、batching、memory allocatorとの相互作用を別途検証する必要がある。

## 実装上の含意

speculative decodingをsystem throughput目的で使うときは、「1 requestあたり何tokenacceptしたか」だけでは不十分である。

別draft modelを置くことで

- model weight bandwidth
- KV memory
- scheduler slot

を追加消費すると、large batchではacceptance gainがsystem throughputに変換されないことがある。

Unoはproposal generatorを軽量weightとしてtarget model内へ統合することで、この**draft-side system cost**を小さくする方向を示している。

またdiffusionとARを競合architectureとして見るのではなく、**ARをcorrectness layer、diffusionをparallel proposal layerとして組み合わせる**設計は、今後のparallel decodingでも重要な考え方になり得る。
