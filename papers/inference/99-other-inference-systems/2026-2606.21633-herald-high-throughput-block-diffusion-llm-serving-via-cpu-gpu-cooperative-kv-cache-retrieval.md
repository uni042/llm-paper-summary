# HERALD: High-Throughput Block Diffusion LLM Serving via CPU-GPU Cooperative KV Cache Retrieval

> ブロック拡散LLMのKV再利用性を利用し、CPUで1回選択した疎KVをGPUへ先読みしてデノイズと重畳し、5% KV予算で最大2.28倍の処理量を実現する。

- **著者**: Omin Kwon, Doyeon Kim, Jongseok Park, Seung Yul Lee, Ion Stoica, Jae W. Lee
- **著者・所属**: 論文一次資料の著者欄に基づく。個別所属は本レコードでは未転記。
- **公開**: arXiv
- **種別**: プレプリント
- **対象**: KVキャッシュオフロード、ブロック拡散LLM、CPU-GPU協調、疎注意、長文脈推論
- **実装**: SGLangを拡張し、GPU注意にFlashInfer、CPU側KV選択にAVX-512 C++カーネル、二重バッファ疎KVプールと非同期転送を用いる研究実装。
## 概要
HERALDは、ブロック拡散LLMで同一ブロックの複数デノイズ段階がほぼ同じ重要KV集合を再利用できる性質を利用し、完全KVキャッシュをCPU DRAM、選択済み疎KVをGPU HBMに置くKVオフロードシステムである。中央[MASK]位置の単一代表クエリでCPU側選択量を削減し、step-0のドラフトから次ブロック用KVを先読みして、二重バッファと二重ストリームでCPU選択・PCIe転送をGPUデノイズと重畳する。H100環境のLLaDA 2.0-mini 16BとSDAR-8B-Chatでは5% KV予算で密実行に近い精度を維持し、16K〜32K文脈でGPUのみの密実行に対して1.81〜2.28倍の処理量を示した。

HERALDはこのブロック単位のKV再利用をCPU-GPUの非対称な容量・計算資源へ直接対応付け、完全KVをCPU DRAMに保持したままCPUで重要位置を選び、GPUには少量の疎KVだけをブロック当たり1回転送する。新規性の第一は、全Bクエリではなくブロック中央の単一[MASK]クエリを代表として選択し、CPU走査のクエリ数をB分の1へ減らすことにある。第二は、現ブロックstep-0 logitsのargmaxから一時ドラフトを作り、それを次ブロックの検索文脈として使うことで、本来直列な依存を崩して選択を早期開始することにある。第三は、二つの疎KVプールとmain/retrievalの二ストリームを用いて、CPU選択・gather・PCIe転送をGPUデノイズと層単位に重畳するシステム化である。

代表結果として、LongBench平均品質（LLaDA 2.0-mini）は5% KV budget、LongBench主要タスクでGPU-only dense attentionに対してHERALD 38.77 / dense 38.69。代表クエリによる疎KV選択でも、このモデルではdenseと同等水準の品質を維持する。
## 問題設定
長文脈LLMではKVキャッシュが文脈長に比例して増え、GPU HBMを圧迫して同時バッチ数を減らす。CPU DRAMへのオフロードは容量問題を緩和するが、PCIe帯域はHBMより大幅に狭いため、全KVを毎回GPUへ戻すと転送が支配的になる。自己回帰LLM向けのInfiniGen型方式は重要KVだけを選択しても、クエリが毎トークン変わるため選択と転送を各デコード段階で繰り返す。一方、ブロック拡散LLMはB個のトークンをT回のデノイズ段階で更新し、ブロック内では過去prefixが固定されるため重要KV集合の時間的一貫性が高い。MAGE系の疎推論はブロック冒頭で選択した集合をT回再利用できるが、CPUオフロード環境で全Bクエリを使って完全KVを走査するとCPU計算が新たなボトルネックとなり、次ブロックの選択を現ブロック完了後に始めればCPU選択とGPUデノイズが直列化する。
## 新規性
HERALDはこのブロック単位のKV再利用をCPU-GPUの非対称な容量・計算資源へ直接対応付け、完全KVをCPU DRAMに保持したままCPUで重要位置を選び、GPUには少量の疎KVだけをブロック当たり1回転送する。新規性の第一は、全Bクエリではなくブロック中央の単一[MASK]クエリを代表として選択し、CPU走査のクエリ数をB分の1へ減らすことにある。第二は、現ブロックstep-0 logitsのargmaxから一時ドラフトを作り、それを次ブロックの検索文脈として使うことで、本来直列な依存を崩して選択を早期開始することにある。第三は、二つの疎KVプールとmain/retrievalの二ストリームを用いて、CPU選択・gather・PCIe転送をGPUデノイズと層単位に重畳するシステム化である。
## 手法
### 手法のあらまし
エンドツーエンドの処理は、まず完成済みprefixの全KVをCPU DRAMへ保持し、現在ブロックを処理するGPUには前ブロックで選択済みの疎KVだけをactive poolとして置くところから始まる。main ストリームはこのactive poolを使い、B個の[MASK]位置をT回のデノイズ段階で更新する。これによりGPUは高帯域HBMを反復利用する小さなworking setへ集中でき、完全KVによるHBM圧迫を避ける。

次ブロックの準備では、現ブロックstep-0 logitsの各位置argmaxから一時ドラフトを生成する。このドラフトを意味的代理として次ブロックの代表queryを早期に作り、GPUでQKV射影した後、ブロック中央[MASK]位置に対応する単一queryをCPU側選択へ渡す。CPUはDRAM上の完全Kを走査し、GQAではquery head間の関連度を集約してKV headごとにtop-k位置を決める。全B queryを使わないことでCPU計算量を削減する。

選択されたK/VはCPU上でpinned メモリへgatherされ、retrieval ストリームがPCIe DMAでGPUのinactive sparse-KV poolへ非同期転送する。GPUのmain ストリームはその間も現ブロックの残りデノイズを続けるため、CPU scan、ホスト gather、PCIe transferがGPU計算と重畳される。層単位でもGPU演算とCPU側準備をパイプライン化し、検索を可能な限りcritical pathから外す。

現ブロックのデノイズが完了すると、最終確定トークンから正確なKVを計算し、先読みのためだけに使ったdraft KVをCPU/GPU双方で置換する。したがってdraft誤りは恒久状態へ蓄積しない。ブロック境界でretrieval ストリームの完了を確認してactive/inactive poolをswapし、準備済み疎KVを次ブロックのactive poolとして同じ処理を繰り返す。この流れにより、完全KVはCPUに常駐したまま、GPUへ渡る重要KVはブロック当たり一度だけとなる。

### 単一代表[MASK]クエリによるCPU選択
ブロック開始時は各位置が同じ[MASK]埋め込みを持ち、主な差が位置符号化に由来することを利用する。全B位置のクエリで完全KVを走査する代わりに中央位置の1クエリを代表として使い、CPU側の注意スコア計算とtop-k選択を大幅に削減する。

この近似は選択再現率を下げ得るため、HERALDはMAGEより約1.7〜1.75倍大きい疎KV予算を用いて補償する。論文では32クエリから1クエリへの削減でCPU選択処理量が約8倍になり、全クエリ選択に対するシステム処理量のablationでも大きな改善を示す。

### step-0ドラフトによる先読み
通常はブロックnが確定しないとn+1用クエリを作れず、検索がGPUデノイズ後に直列化する。HERALDはstep-0 logitsの各位置argmaxから仮ドラフトを作り、現ブロックの意味的代理として次ブロックのKV検索を先行開始する。追加の独立推論パスを避けるため、ドラフトKV計算は後続デノイズ計算と統合する。

ドラフトは検索を早めるためだけに用い、生成結果そのものには採用しない。現ブロック確定後には正確なKVを計算してドラフトKVを置換するため、代理予測の誤りが後続ブロックへ永続的に伝播しない。ablationでは代表クエリ選択にこのlookaheadを加えることで16K/32K条件の正規化処理量がさらに約1.29倍/1.57倍改善する。

### CPU-GPU協調KV検索
GPUは各層のQKV射影など高演算密度部分を担当し、CPUはDRAM上の完全KVを走査して代表クエリとの注意スコアを計算する。GQAでは複数query headの重要度を集約し、KV headごとにtop-kを求めることで重複する順位付けを抑える。CPUカーネルはC++/AVX-512で実装され、キャッシュを意識したタイル処理を用いる。

選ばれたKVはpinned ホスト メモリへgatherされ、DMAでGPUへ非同期転送される。これによりPCIeを通過するのは完全KVではなくブロック当たり一度の疎集合となり、長文脈ほど転送量削減とGPUバッチ容量回復の双方が効く。

### 二重バッファ・二重ストリーム実行
GPUにはactiveとinactiveの二つの疎KVプールを確保する。main ストリームはactive poolを用いて現在ブロックを反復デノイズし、retrieval ストリームはCPU選択・gather・転送を進めて次ブロックのKVをinactive poolへ準備する。

層内でもGPU演算、CPU gather、転送を可能な限り重ね、ブロック境界でのみ同期して二つのpoolをswapする。retrieval時間が現ブロックのデノイズ時間内に収まれば検索コストをcritical pathから隠せるが、デノイズstep数Tが小さい場合は重畳余地が減り、検索が再びボトルネックになり得る。

### 全体のデータ／制御の流れ
完全KVを容量の大きいCPU DRAM、反復利用する疎KVを高帯域GPU HBMへ置き、ブロック拡散の『一度選んでT回使う』時間構造を階層メモリへ対応させる。CPUは完全KVの保持と重要位置の選択、GPUは反復デノイズを担当し、役割をデータの再利用頻度に合わせて分ける。

単一代表クエリはCPU計算量を、ブロック単位再利用はPCIe転送回数を、ドラフト先読みと二重ストリームは残る検索遅延をそれぞれ削減する。したがってHERALDは個別最適化の寄せ集めではなく、CPU計算・PCIe帯域・HBM容量という三つの制約を同時に扱う共同設計である。
## 評価条件
- **ハードウェア**: 主評価環境はIntel Xeon Platinum 8481C、936GB CPU DRAM、NVIDIA H100 SXM 80GB HBMをPCIe 4.0 x16で接続した単一GPUサーバ。CPU側の完全KV走査とGPU側デノイズを同時実行できる異種計算環境で、CPU DRAM容量とPCIe帯域を明示的に利用する。
- **ソフトウェア**: SGLangを拡張したサービング実装を用い、GPU注意はFlashInfer、CPU選択はC++のAVX-512 intrinsicsで最適化する。評価対象は少なくともLLaDA 2.0-mini 16BとSDAR-8B-Chat。比較対象はGPU HBMに全KVを置くdense GPU-only、ブロック拡散向けMAGE-オフロード、自己回帰向けInfiniGenを適応したオフロード方式。
LongBenchの4タスクで5%を中心とする疎KV予算の品質をdense実行と比較し、16K/32K長文脈で最大バッチを含むデコード スループットを測定する。代表クエリ化、ドラフトlookahead、デノイズstep数のablationによりCPU選択削減と重畳効果を分離する。KV予算を変えた精度比較ではMAGE-オフロードや適応InfiniGenも含め、単なる処理量だけでなく疎選択による品質劣化を確認する。最新版概要では3つのblock dLLMと5つの長文脈タスクへの拡張評価も報告されているが、ここで転記する具体値は一次資料で明示されたLLaDA/SDAR条件を中心とする。
評価はblock diffusion LLM servingに限定され、自己回帰LLMそのものの高速化を目的としない。利点は長文脈、大きいKV、十分なデノイズstep数、CPU側のAVX-512計算能力とPCIe 4.0帯域を持つ環境で最大化する。CPUが弱い、PCIeが遅い、Tが小さい、あるいはGPU HBMだけで十分な短文脈では相対的優位が縮小し得る。
## 主要結果
HERALDは5%の疎KV予算でもdense GPU-onlyに近いLongBench品質を保ちつつ、CPU DRAMへ完全KVを逃がしてGPU上のバッチ容量を回復し、16K〜32K文脈で1.81〜2.28倍のデコード スループットを示す。LLaDA 2.0-miniの32Kではdenseの最大バッチ 16に対してHERALDは80まで拡大する。代表クエリ選択がCPUボトルネックを大きく削り、ドラフトlookaheadが残る検索をデノイズの背後へ隠す。最新版概要ではGPU-only比最大2.47倍スループット、per-block 遅延最大1.59倍短縮まで報告され、文脈が長いほど利得が増える。

- LongBench平均品質（LLaDA 2.0-mini） / HERALD 38.77 / dense 38.69 (比較対象: GPU-only dense attention; 条件: 5% KV budget、LongBench主要タスク) — 代表クエリによる疎KV選択でも、このモデルではdenseと同等水準の品質を維持する。

- LongBench平均品質（SDAR-8B-Chat） / HERALD 35.45 / dense 36.35 (比較対象: GPU-only dense attention; 条件: 5% KV budget) — わずかな品質低下はあるが、5%のKVだけをGPUへ置く条件としては近損失である。

- LLaDA デコード スループット / 16K: 3385 vs 1864 tok/s、32K: 2665 vs 1168 tok/s (比較対象: GPU-only dense serving; 条件: LLaDA 2.0-mini 16B、16K/32K context) — 約1.82倍から2.28倍へ改善し、長文脈ほどdense側のHBM容量制約が強くなるため差が拡大する。

- SDAR デコード スループット / 16K: 1367 vs 754 tok/s、32K: 867 vs 458 tok/s (比較対象: GPU-only dense serving; 条件: SDAR-8B-Chat、16K/32K context) — 約1.81〜1.89倍の処理量向上を示し、別block dLLMでも効果が再現する。

- 最大バッチ capacity / HERALD 80 / dense 16 (比較対象: GPU-only dense serving; 条件: LLaDA 2.0-mini、32K context) — 完全KVをCPU DRAMへ置くことでHBMをバッチ拡大へ振り向けられる。

- 代表クエリ＋lookahead ablation / 代表クエリで3.48x(16K)/4.45x(32K)、lookahead追加でさらに1.29x/1.57x (比較対象: CPUで全block queryを用いる選択構成; 条件: 正規化スループット ablation) — CPU選択量削減が最大の単独寄与で、ドラフト先読みが検索をGPUデノイズと重ねて追加改善する。

### 負の結果・境界条件
- 単一代表クエリは全Bクエリのtop-k集合を完全再現せず、HERALDはMAGEより約1.7〜1.75倍大きい疎KV予算で補償するため、その分GPU上のキャッシュ footprintと最大バッチ capacityを消費する。SDARの5%予算ではdense 36.35に対し35.45と小さい品質低下が残る。デノイズstep数Tが小さい場合はretrievalを隠す計算時間が短く、CPU選択・PCIe転送がcritical pathへ戻る。したがって常にGPU-onlyより速いわけではなく、CPU性能・PCIe帯域・文脈長・Tに依存する。

### 結果の読み方
HERALDの性能向上は単なる疎注意の計算削減ではなく、KVの配置とアクセス頻度をblock dLLMの時間構造へ合わせた結果である。完全KVをCPUへ置くことでHBM容量を解放し、重要KVの選択をブロック当たり1回へ償却し、さらに先読みでその1回をGPU計算の背後へ隠す。長文脈ほどdense servingのバッチ capacityがKVに奪われるため、HERALDの容量上の利点がスループットへ直接変換される。
## 品質への影響
5% KV予算でもLLaDAではdenseをわずかに上回る平均値、SDARでは約0.9点低い平均値であり、主要評価では近損失である。ただし代表クエリは近似なので品質無損失を理論保証するものではない。MAGEより大きいKV予算を必要とする点も、速度と選択精度の交換条件として解釈すべきである。
## 既存研究との差
InfiniGenなど自己回帰向けKVオフロードは各トークンで変化するqueryに応じて重要KVを繰り返し選択・転送するのに対し、HERALDはblock内T回のデノイズで同じ疎KV集合を再利用し、PCIe転送をblock当たり1回へする。MAGEはblock dLLMの疎注意としてall-[MASK] blockから重要KVを選択・再利用するが、HERALDは完全KVがCPU DRAMにあるオフロード環境を対象に、CPU選択計算の削減、draft lookahead、二重バッファ/ストリームを加えてスループットを狙う。PagedAttention系はGPU内KV配置・断片化を主に扱うのに対し、HERALDはCPU DRAMを容量層として使い、GPUにはworking setのみを置く。単純なCPU オフロードは容量を増やしてもPCIeが律速になるが、HERALDはアクセス頻度そのものをblock粒度へ変えることで律速を外す。
## 限界
HERALDはblock diffusion LLM固有の『同一block内で重要KVが安定する』性質へ依存するため、通常の自己回帰LLMへそのまま適用できない。代表[MASK]クエリは全query選択の近似であり、MAGEより大きい疎KV予算を必要とする。CPU側完全KV走査をAVX-512で高速化しているため、CPU計算性能やメモリ帯域が低い環境ではretrievalが遅くなる。PCIe転送をデノイズの背後へ隠す設計なので、Tが小さい場合やGPU側デノイズが短い場合は重畳余地が減る。主な具体評価は単一H100＋Xeonの構成と少数のblock dLLMに集中しており、複数GPU、異なるCPU世代、CXL/NVLink-C2C等の相互接続への一般化は未検証である。
## 実装状態
論文はarXiv v2（2026-08-03）のプレプリント。SGLang拡張、FlashInfer、AVX-512 C++ CPU カーネル、pinned-メモリ経由の非同期転送を用いた実システムをH100/Xeon上で評価している。今回確認した一次資料・検索結果から公式公開コードURLは確定できなかったため、code欄は推測で補完していない。
## 研究上の位置づけ
階層メモリ型LLM推論の観点では、HERALDはCPU DRAMを単なる退避先ではなく、完全KVの常駐層兼selection compute層として使う点が重要である。GPUは高帯域だが小容量、CPUは大容量だが相対的に低演算・低接続帯域という非対称性を、block diffusionのselection/denoising非対称性へ対応付けている。既存のKV オフロード、sparse attention、プリフェッチ、double bufferingを組み合わせるだけでなく、モデルの生成アルゴリズムが作る時間的再利用をI/O スケジューラへ取り込む例であり、CPU/SSD/CXLを含む将来の階層メモリ推論にも一般化可能な設計パターンを示す。
