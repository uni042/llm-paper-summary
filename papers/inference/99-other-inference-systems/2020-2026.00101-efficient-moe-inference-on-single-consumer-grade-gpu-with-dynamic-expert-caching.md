# Efficient MoE Inference on Single Consumer-grade GPU with Dynamic Expert Caching

> プリフィルの動的エキスパート配置とデコードのトークン-wise予測取得を組み合わせ、単一RTX 4090で671B級MoEを高速化するCPU/GPUハイブリッド基盤。
## 書誌情報
- **著者**: Rui Zhang, Boxuan Yang, Rongji Wang, Xuemei Peng, Zeyi Wen
- **公開**: IEEE International Parallel and Distributed Processing Symposium (IPDPS 2026)
- **種別**: Conference Paper
- **対象**: MoE、エキスパート オフロード、動的 エキスパート キャッシュ、トークン-wise プリフェッチ、CPU/GPU hybrid inference、consumer GPU
- **実装**: KTransformersを基盤にMoE operator、GPU エキスパート operator、GPU キャッシュ エキスパートのdequantization CUDA カーネル、C++のプリフェッチ/キャッシュ管理を実装。論文Artifact DescriptionでGitHubとFigshareが公式成果物として明記される。
## 概要
SMOEは超巨大MoEを単一コンシューマGPUで動かすため、計算量の大きいプリフィルでは負荷に応じたオンデマンドエキスパート配置とパイプライン、デコードではトークン-wise予測取得とLFU系キャッシュ管理を使い分け、CPU/GPU負荷とPCIe転送を重ねるハイブリッド推論基盤である。DeepSeek-V3 671BとQwen3-235Bでプリフィル最大8.68倍、デコード最大20.9%の高速化を示す。

SMOEはプリフィルとデコードの性質を分離し、同じオフロード方針を全段階へ適用しない。プリフィルではgating結果から高負荷エキスパートを動的にGPUへ割り当て、CPU実行時間とGPU計算+PCIe転送時間を比較してGPUへ送る個数を決める。

デコードでは現在トークンから次トークンで使うエキスパートを予測するトークン-wise プリフェッチを導入し、非MoE層を含む長い計算窓で転送を隠す。さらにGPU容量内のエキスパート キャッシュをLFU系追い出しで更新し、超巨大モデルでもCPU/GPU負荷を均衡させる。

代表結果として、TTFT 高速化倍率はprompt length最大4K、RTX 4090単一GPUでKTransformersに対して最大8.68×。promptが長いほど高負荷エキスパートをGPUへ移す利益が転送費を上回る。
## 問題設定
超巨大MoEは疎にエキスパートを活性化するため演算量は抑えられるが、全エキスパート重みはGPU HBMへ収まらずCPU DRAM等へオフロードする必要がある。consumer GPUではPCIe帯域が狭く、エキスパート転送待ちが推論を支配しやすい。

既存GPU-centric方式はキャッシュ miss時の転送か近似による品質低下を抱え、CPU/GPU hybrid方式もエキスパート キャッシュ hit率と負荷均衡に依存する。特に400B超ではGPUへ置けるエキスパート比率が小さく、層/iteration-wise プリフェッチだけでは転送時間を十分隠せない。
## 新規性
SMOEはプリフィルとデコードの性質を分離し、同じオフロード方針を全段階へ適用しない。プリフィルではgating結果から高負荷エキスパートを動的にGPUへ割り当て、CPU実行時間とGPU計算+PCIe転送時間を比較してGPUへ送る個数を決める。

デコードでは現在トークンから次トークンで使うエキスパートを予測するトークン-wise プリフェッチを導入し、非MoE層を含む長い計算窓で転送を隠す。さらにGPU容量内のエキスパート キャッシュをLFU系追い出しで更新し、超巨大モデルでもCPU/GPU負荷を均衡させる。
## 手法
### 手法のあらまし
入力は量子化MoEモデル、prompt/トークン列、各MoE層のgating結果、GPU/CPU計算性能、PCIe帯域、利用可能HBMである。attention等の非MoE演算はGPUに置き、MoE routed エキスパートだけをCPUとGPUへ分散する。プリフィルでは各層のトークン-to-エキスパート割当からエキスパート負荷を得て、CPUで実行する時間とGPUへ転送して実行する時間をhardware profileで比較し、GPU実行すべき高負荷エキスパート数Kを決定する。選ばれたエキスパートはping-pong バッファへ転送し、CPU側の低負荷エキスパート計算とGPU計算・PCIe転送をパイプライン化する。

デコードへ移るとプリフィル中の活性値 frequencyで初期GPU キャッシュを作る。各トークンのattention出力が得られた時点で次トークンのエキスパートを予測し、残りのforward計算中に非同期プリフェッチを進める。キャッシュ miss エキスパートはCPUで計算し、予測エキスパートはFixed-Nまたは適応型 LFU 追い出しで既存キャッシュを置換する。各層の予測精度に応じてプリフェッチ対象層を選ぶSMOE-Flexも評価し、最終的にプリフィル TTFT、デコード TPS、キャッシュ hit率、CPU/GPU/PCIe利用率を出力する。

### stage-aware CPU/GPU分業
attentionとhead projectionなどの非MoE部分をGPUへ固定し、routed エキスパート計算だけをCPU/GPU間で動的に分配する。入力はモデル演算グラフとgating結果で、エキスパートごとの実行場所を決めることでKTransformersの全routed-エキスパート CPU実行よりGPUを活用する。

プリフィルは計算集約、デコードはメモリ/transfer集約という段階差を明示的に利用する。同じキャッシュ/プリフェッチ規則を両段階へ流用せず、プリフィルでは負荷量、デコードでは予測とキャッシュ hitを中心に最適化する点が全体設計の基礎になる。

### プリフィルオンデマンドエキスパート配置
各MoE層でgating後のトークン数から高負荷エキスパートと低負荷エキスパートを判定する。hardware profileから各エキスパートのCPU/GPU計算時間とtop-K エキスパートのPCIe転送時間を見積もり、GPU計算+転送がCPU計算より短くなるKを選択する。

高負荷エキスパートはGPUへ移し、低負荷エキスパートはCPUでそのまま計算するため、固定hot/cold配置よりpromptごとの実負荷へ追従できる。promptが長いほど高負荷エキスパートをGPUへ移す利益が大きくなり、プリフィル高速化が伸びる。

### プリフィル パイプラインとping-pong バッファ
GPUへ送るエキスパートのPCIe転送をCPU エキスパート計算およびGPU エキスパート計算と重ね、転送をcritical pathから隠すパイプラインを構成する。次に必要なエキスパートを準備しながら現在エキスパートを処理するため、単純なon-demand loadingの直列待ちを避ける。

GPU側にはping-pong バッファを用いて転送先を交互に使い、大量エキスパートを恒久常駐させずにパイプラインを維持する。これにより24GB級HBMでも671B級モデルのプリフィルで動的GPU実行を成立させる。

### トークン-wise エキスパート プリフェッチ
デコードでは現在トークンのattention 層出力を得た直後に、次トークンで活性化しそうなエキスパートを各MoE層について予測する。層方式より早い時点から転送を開始でき、現在トークンの残りのMoE/非MoE計算時間全体をプリフェッチ窓として利用する。

予測エキスパートは非同期transfer queueへ投入され、対応層へ到達する前にGPU キャッシュへ入る。論文では同じ転送量でもHybriMoEのキャッシュ待ち約1ms/トークン/層に対しSMOEはほぼ0まで隠せると報告する。

### エキスパート キャッシュ管理
プリフィル中に全エキスパートの活性値 frequencyを記録し、デコード開始時に最頻エキスパートでGPU キャッシュを初期化する。その後は利用可能HBMから層ごとのキャッシュ slot数を決め、既存slotをin-place置換するため、デコード中に新しいキャッシュ領域を都度確保しない。予測器はattention出力を得た時点で次トークンの候補を作り、GPU計算完了後に非同期transfer queueへ更新要求を送る。

Fixed-N 追い出しは予測top-Nの未常駐エキスパートでN個の低頻度エキスパートを置換し、適応型 追い出しは予測top-Nのうち未常駐なものだけを転送する。どちらもLFU系で、前者は転送量とPCIe利用を安定させ、後者は活性値 skewが強いモデルで不要転送を抑える。Nはdevice compute capabilityとPCIe 帯域に合わせて調整し、限られた24GB HBMを層間で有効利用する。

### 層選択型SMOE-Flex
トークン-wise予測の精度は層ごとに異なるため、すべての層で同じ数をプリフェッチする代わりに、精度の低い層ではプリフェッチを止め、その時間を高精度層の追加エキスパート転送へ回す。通常SMOEが各層で1〜2 エキスパートを更新するのに対し、選択された層では長くなった転送窓を使って最大3 エキスパートまでプリフェッチできる。

この設計は予測が外れやすい層へPCIe帯域を浪費せず、高精度層のキャッシュ hit率をさらに高める。実験ではSMOE-Flexのhit率は通常SMOEを上回るが、プリフェッチを無効化した層が半数程度あるため全体TPSは同程度に留まり、良い設定には層選択やプリフェッチ数の複雑なhyperparameter tuningが必要になる。

### 全体のデータ／制御の流れ
KTransformersのoperator insertionを利用し、attention等はGPUに残したままMoE operatorをCPU/GPU hybrid実行へ置換する。GPU エキスパート operatorとdequantization CUDA カーネル、C++のプリフェッチ/キャッシュ管理を追加する。

単一リクエストのforward中にCPU エキスパート計算、GPU エキスパート計算、PCIe transferを重ね、プリフィルは動的配置パイプライン、デコードはトークン-wise プリフェッチ+キャッシュ更新へ切り替える構成である。
## 評価条件
- **ハードウェア**: AMD EPYC 7T83 64-core CPU×2、1TB DRAM、NVIDIA RTX 4090 24GB HBM、PCIe 4.0 x16。実験は単一GPUで行い、active CPU coreを10以下に制限して典型的consumer CPU相当を模擬する。
- **比較対象**: KTransformers、HybriMoE reproduced/extended to ultra-large models、SMOE without パイプライン、層 プリフェッチ、静的 initial エキスパート キャッシュ、SMOE-Flex
単一RTX 4090・低concurrencyを主対象とするconsumer-grade評価であり、複数GPUや高バッチ servingを直接測ってはいない。CPU coreを10以下へ制限するため実CPU全体の性能比較でもない。scalability節はmulti-GPU/NVLink環境への適用可能性を議論するが実測ではない。
## 主要結果
SMOEは671B級MoEを24GB RTX 4090へオフロードする厳しい容量条件でも、プリフィルでは高負荷エキスパートをGPUへ動的に寄せてパイプライン実行し、デコードではトークン-wise プリフェッチでPCIe転送を現在トークンの計算へ重ねることで、KTransformers比プリフィル最大8.68倍、デコード最大20.9%の高速化を達成する。特に同程度の転送量でもHybriMoEで約1 ms/トークン/MoE 層生じるキャッシュ更新待ちをほぼ0へ隠し、671B級でもGPU キャッシュが約3%しかない状況でCPU/GPU負荷を改善する。実務上は、巨大MoEをconsumer GPUへ載せる際に単なるキャッシュ容量増加よりも、プリフィルとデコードでエキスパート移動の判断時刻を変え、PCIe転送を計算と重ねることが性能の鍵になることを示す。

- TTFT 高速化倍率 / 最大8.68× (比較対象: KTransformers; 条件: prompt length最大4K、RTX 4090単一GPU) — promptが長いほど高負荷エキスパートをGPUへ移す利益が転送費を上回る。

- TTFT 高速化倍率 / 最大7× (比較対象: KTransformers; 条件: Qwen3-235B-A22B 4-bit) — stage-aware on-demand allocationとパイプラインの効果が別モデルでも成立する。

- TTFT 高速化倍率 / DeepSeek最大2.98×、Qwen最大1.82× (比較対象: HybriMoE reproduced/extended; 条件: ultra-large model supportを揃えた比較) — 固定キャッシュ中心よりpromptごとの負荷でエキスパートを割り当てる方式が有利。

- デコード inference speed / 比較対象比最大20.9%高速化 (比較対象: KTransformers; 条件: 6 デコード datasets、ultra-large MoE) — トークン-wise プリフェッチでGPU キャッシュ更新とCPU/GPU負荷均衡を改善する。

- wait_キャッシュ_time / SMOEほぼ0、HybriMoE約1 ms/トークン/MoE 層 (比較対象: HybriMoE; 条件: プリフェッチ エキスパート数2、同程度のPCIe転送量) — トークン-wise方式はforward全体の計算窓を使い通信をほぼ完全にoverlapする。

- キャッシュ management time / DeepSeek-V3で約0.01 ms (比較対象: MoE 層 ランタイム; 条件: 専用microbenchmark) — 動的キャッシュ更新自体のCPU/GPU critical-path負荷は小さい。

### 負の結果・境界条件
- HybriMoEの層 プリフェッチはプリフェッチ エキスパート数を増やすほど転送オーバーヘッドが利益を上回り性能が悪化する。SMOE-Flexはキャッシュ hit率をさらに上げるが通常SMOEと全体性能は同程度で、複雑なhyperparameter tuningを必要とする。PCIe帯域は最大約14GB/sまで利用される一方、依然として主要ボトルネックである。

### 結果の読み方
超巨大MoEではGPUに常駐できるエキスパート比率が極小なので、静的hot エキスパート キャッシュだけでは足りない。プリフィルは1 エキスパートあたりの計算量が大きく転送してGPU実行する価値が高い一方、デコードは各トークンの計算が軽いため、転送を事前に開始してキャッシュ hitへ変換する方が重要になる。
## 品質への影響
SMOEは計算グラフやエキスパート出力を近似せず実行deviceだけを変える。GSM8K 5例のDeepSeek デコードでKTransformersとperplexityが全例一致し、論文は無損失と評価する。4-bit量子化による品質差はSMOE固有ではない。
## 既存研究との差
プリフィルではoffline hotnessではなく現在promptのgating負荷とhardware profileからGPUへ送るエキスパート数を層ごとに決める。デコードではcross-層 predictionだけでなくトークン単位で次トークンのエキスパートを早期予測し、非MoE層を含む長い計算窓へPCIe転送を重ねる。さらにLFU系キャッシュ更新を組み合わせるため、単なるエキスパート キャッシュ方式より動的である。
## 限界
評価は単一RTX 4090・single concurrencyが中心で、multi-GPU scalabilityは分析のみで実測していない。CPUはdual EPYC機を使いながらactive coreを10以下へ制限してconsumer CPUを模擬しており、一般的desktopのメモリ 帯域/NUMA条件と完全には一致しない。PCIe 4.0 x16が主要ボトルネックであり、PCIe 5.0やNVLinkでは最適プリフェッチ数とCPU/GPU分業点が変わり得る。SMOE-Flexは追加tuningが必要。
## 実装状態
KTransformersを基盤とする実装が公開され、GPU エキスパート operator、dequantization CUDA カーネル、C++ プリフェッチ/キャッシュ管理を含む。論文Artifact DescriptionはFigshare DOI 10.6084/m9.figshare.31353823とGitHub rzhang772/SMOEを公式artifactとして挙げ、Docker setupと再現手順も記載する。
## 研究上の位置づけ
単一consumer GPUで超巨大MoEを動かすエキスパート オフロード研究のうち、CPU/GPU hybrid execution、動的 エキスパート キャッシュ、プリフェッチ スケジューラを統合するsystem研究に位置する。SSD/NVMe エキスパート storageそのものは主対象ではなく、CPU DRAMからGPU HBMへのPCIe転送を隠す設計が中心である。
