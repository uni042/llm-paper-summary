# SPIRe: Boosting LLM Inference Throughput with Speculative Decoding

> SPIReは、投機的decode（speculative decoding）を「1 requestを速くする技術」ではなく、**大batchで1秒あたりに何token処理できるかを高める技術**として設計し直す。大batch・長contextではdraft modelの重みよりKV cacheの読出しが重くなるため、draftをただ小さくするのではなく、参照するKV量を一定に抑えながらtarget modelに似た候補を出せる浅いdraftを作る。論文の中心結果は実serving systemの実測値ではなく、実測したacceptance特性をFLOPs・memory trafficへ組み合わせた性能モデル上のthroughputである。

## 概要

投機的decodeでは、小さな下書きモデル（draft model）が数token先まで候補を生成し、大きな対象モデル（target model）がそれらをまとめて検証する。候補がtarget modelと十分一致すれば、targetを1 tokenずつ呼ぶより少ない回数のweight/KV読出しで複数tokenを確定できる。

この方式では一般に、draft modelについて次の2つが同時に望ましい。

- forward passが安いこと。
- target modelと似た予測をして、候補が多く受理されること。

しかし、このtrade-offの最適点は「latencyを下げたいのか」「throughputを上げたいのか」で変わる。

小batchではmodel weightを毎step読むcostが支配的になりやすく、非常に小さいdraftが有利である。一方、大batchではweight読出しを多数requestで償却できるため、長contextの**KV cache読出し**が相対的に大きくなる。この領域では、draftのparameter数だけを減らしてもKV cacheがcontext長に比例して増えるなら、throughputは伸びにくい。

SPIReはこの観察から、draft modelを次のように設計する。

1. draftが読むKV cacheを疎にし、contextが伸びてもKV trafficをほぼ一定にする。
2. target modelの一部blockから初期化し、浅くてもtargetに似た表現を得やすくする。
3. 過去のtarget activationをdraftのmemoryとして再利用し、浅さによる表現力不足を補う。
4. 正解tokenだけでなくtargetの出力分布へ近づくよう蒸留（distillation）し、候補受理率を高める。

## まず「投機的decodeのthroughput」をどう考えるか

### 候補をたくさん当てるだけでは速くならない

投機的decodeの1 roundでは、

`draftが候補列を生成 → targetがまとめて検証 → 一致したprefixを確定`

という処理を行う。

1 roundで平均何token確定できるかを平均生成長（average generation length）と考えると、この値が大きいほどtargetを呼ぶ回数は減る。

ただし、draft自身が重ければ1 roundの時間も伸びる。したがってthroughputは概念的には、

`1 roundで確定するtoken数 / 1 roundにかかる時間`

で決まる。

つまり、acceptance率が高いdraftが常に最速とは限らない。少しacceptance率が低くても、KV読出しやFLOPsが大幅に小さいdraftの方が最終throughputは高くなり得る。

### 大batchになると「小さいdraft」の意味が変わる

latency最適化ではbatch sizeが小さく、model weightをGPU memoryから読むcostが大きい。そのためparameter数の小さいdraftが分かりやすく有利になる。

throughput最適化ではbatch sizeを増やす。weightはbatch中で再利用される一方、各requestはそれぞれ別のKV cacheを持つため、contextが長くなるとKV cache trafficが支配的になる。

この領域で重要なのは、draft modelの「parameter数」だけでなく、**1 token生成するたびに何byteのKV cacheを読むか**である。

## 評価指標: 実装依存を減らしたthroughput model

SPIReは、特定frameworkのkernel実装やbatch schedulerによる差がdraft architecture比較へ混ざるのを避けるため、主評価に性能モデルを使う。

forward passのcostを大きく、

- 演算量（FLOPs）
- model weightの読出しbyte数
- KV cacheの読出しbyte数

へ分け、memory trafficをhardware operational intensityを使ってFLOP相当costへ換算する。そしてdraft生成とtarget検証のcost、平均生成長を組み合わせてthroughput倍率を求める。

この方法には「特定のCUDA kernelが速かったから勝った」という混入を減らせる利点がある。一方で、**結果は実際のproduction runtimeで直接測ったend-to-end tokens/sではない**。論文の「100%改善」「35%改善」はこのmodeled throughputについての値として読む必要がある。

## SPIReという名前が表す3要素

SPIReは論文中で、

- **Sparse KV cache**
- **Pruned Initialization**
- **Recurrent Feedback Transformer**

の頭文字を含む名称として説明される。

実際のdraft設計では、これらにtarget activation利用と蒸留lossも加わる。

## 手法

### 1. Sliding-window KV cache — contextが伸びてもdraftのKV読出しを増やさない

最も重要な仕組みは、draft modelのattentionを静的に疎にすることだ。

SPIReはStreamingLLM型のattention maskを使い、過去tokenすべてへattentionするのではなく、主に**直近64 tokenのwindow + 先頭のattention sink 1 token**だけを参照する。training時とinference時の両方で同じ制約を使う。

通常のfull attention draftではcontextが2倍になれば、各stepで読むdraft KV cacheも概ね増える。SPIReでは参照windowを固定するので、contextが数千、数万tokenへ伸びてもdraft側のKV cache trafficはほぼ一定である。

これは大batch・長context領域で特に効く。target modelは依然大きいが、speculationを導入するために追加したdraft側のmemory trafficがcontext長とともに膨張するのを防げるからである。

代償は、draftが遠い過去へ直接attentionできないことだ。これだけではtargetとの予測一致率が落ち、1 roundで受理されるtoken数が減る可能性がある。後続の仕組みはこの品質低下を補うためにある。

### 2. Pruned initialization — targetの一部blockをdraftへ移植する

論文の実験ではtarget modelは8 Transformer blockで、SPIReのdraftはより浅い。

draftをrandom initializationから学習するのではなく、target modelのembedding、最後側の2 Transformer block、unembeddingを使って初期化する。つまりtargetの計算graphをそのまま小さく切り出すわけではないが、**targetがすでに学習した表現変換をdraftの出発点として再利用する**。

この初期化により、同じ学習budgetでもrandom initializationよりtargetに近い予測を得やすくなり、平均生成長が改善したと報告する。

またtargetとdraftのembedding dimensionを合わせている。parameter数だけ見ればdimensionを縮めた方が軽くできるが、同じhidden sizeを保つことでtargetの中間activationをdraftへ直接渡しやすくなる。

### 3. Feedback memory — 浅いdraftに過去の情報をまとめて渡す

通常のTransformerでは各layerが過去tokenの同じlayerのKVへattentionする。Feedback Transformerでは、前tokenまでに各layerで得たactivationを混ぜてmemory vectorを作り、次tokenのattention先として利用する。

浅いmodelではlayer数が少ないため1 token内で行える変換が少ない。feedback memoryは、過去stepで複数layerを通った情報を次stepへ再投入することで、その表現力不足を補う役割を持つ。

ただしFeedback Transformerは通常、training時にcontext方向の並列化を壊しやすい。各tokenのmemoryが前tokenまでのlayer activationへ依存するからである。

SPIReはdraft model trainingに限定することでこの問題を軽減する。最大投機深さに対応する短いdraft rolloutだけを逐次計算し、それより前の長いprefixについては、すでに計算済みの**target model中間activation**をmemoryの代わりに使う。

言い換えると、draftが長いcontextを自力で最初からfeedback計算するのではなく、targetが持つ過去の表現を足場にして、その先の数tokenだけを予測する。

### 4. Target activationを使う理由

投機的decodeではtarget modelは定期的に候補tokenを検証する。その際にtargetの中間activationも得られる。

SPIReは、このtarget由来のstateをdraft側へ与える設計を採用する。draft自身のembeddingだけから過去情報を再構成するより、targetが深いnetworkで作った表現を利用した方が候補分布をtargetへ近づけやすい。

論文のablationでは、sparse KV cacheに次いで**target activationを参照する仕組み**の寄与が大きかった。

これはdraftを単なる独立した小型LMとして扱うのではなく、target推論中に生まれる中間状態を使う「target依存draft」として最適化していることを意味する。

### 5. Distillation loss — 正解tokenではなくtargetの分布へ近づける

通常のlanguage-model trainingは正解tokenへのcross entropyを最小化する。しかしspeculative decodingで重要なのは、datasetのground-truthに最も近いことだけではなく、**target modelが出す確率分布へdraftを近づけること**である。

SPIReはtargetのsoft probability distributionを使う蒸留lossを導入する。さらに論文では、投機的decodeで期待されるacceptance probabilityを高める項も含めたlossを検討する。

これにより、draftの出力が「一般に良いLM」になることより、「このtarget modelに受理されやすい候補を出す」ことへtraining objectiveを寄せる。

## 1 roundで何が起きるか

SPIReを使うと、推論時の流れは概ね次のようになる。

1. target modelが直前までに確定したtokenと中間activationを持つ。
2. SPIRe draftは固定windowの疎KVとtarget由来memoryを使い、数tokenの候補をautoregressiveに生成する。
3. target modelが候補blockをまとめて検証する。
4. rejection samplingに従って受理できるprefixを確定する。
5. 新しいtarget activationを次roundのdraft memoryへ利用する。

このためdraftはfull contextを毎回読む必要がない一方、target側の豊かな表現を継続的に利用できる。

## なぜMagicDecよりacceptanceが低くても速くなり得るのか

論文の比較対象MagicDecは、target modelそのものを疎attentionでdraftとして使う自己投機（self-speculation）に近い構成で、候補品質が高い。

実際、context length 512付近の平均生成長は、

- Vanilla speculative decoding: 約2.65 token/round
- MagicDec: 約3.89 token/round
- SPIRe: 約3.40 token/round

であり、SPIReはMagicDecより1 roundあたりに確定できるtoken数が少ない。

それでもSPIReは浅く、1回のforward costが小さい。したがって、

`少し短いaccepted block × かなり安いdraft forward`

の方が、

`長いaccepted block × 高価なdraft forward`

より高throughputになる領域がある。

この「acceptance率だけを見てdraftを選ばない」という点が論文の重要なメッセージである。

## 評価

### 評価設定

実験では、8-layer・67M body parameterのmulti-head-attention target modelを固定し、draft architectureを変えて比較する。modelはLongCrawl64 dataset、sequence length 1024でtrainingされる。

比較対象は主に、

- 通常の小型draftによるVanilla speculative decoding
- targetと同等modelを固定window sparse attentionで使うMagicDec
- SPIRe

である。

acceptance特性に相当する平均生成長は実際にtoken生成して測り、batch size・context lengthを変えたthroughputは前述の性能モデルから計算する。

### 主要結果

論文がhighlightする条件では、SPIReのmodeled throughputは、

- Vanilla speculative decodingより **100%高い**
- MagicDecより **35%高い**

と報告される。

「100%高い」は約2倍という意味である。ただしこれはproduction frameworkで測定したend-to-end tokens/sではなく、性能モデル上のthroughput multiplierである。

### context長がばらつく環境で有利な理由

MagicDecは非常に長いcontext・大batchでは強い一方、短〜中contextでは大きなdraft modelのFLOPs増加がKV削減効果を上回り、通常decodeより不利になる場合がある。

SPIReはdraft自体を浅くしつつKVを固定window化するので、短いcontextではforward costを抑え、長いcontextではKV traffic増加も抑えられる。productionのようにrequestごとのcontext長が大きくばらつく場合に、より広い範囲で利益を出すことを狙っている。

### Ablationから分かる寄与

論文のablationでは、throughput改善への寄与は大きい順に概ね、

1. sparse KV cache
2. target model activationの利用
3. distillation loss
4. target modelをpruneしたinitialization
5. feedback memory
6. mixed loss

とされる。

つまりSPIReの性能は「Feedback Transformerが主役」というより、まず**draft KV trafficを固定すること**が最重要で、その上でtarget依存情報を使ってacceptance低下を取り戻す構成と理解した方がよい。

### Llama 3 70Bへの外挿

論文は同じaverage generation length比を仮定し、性能モデルのweight/KV/FLOPsをLlama 3 70B相当に置き換えた外挿も行う。この結果でも多くのcontext長でSPIReが高い推定throughputを示す。

ただしこれは**Llama 3 70B上でSPIReを実装・trainingしてend-to-end測定した結果ではない**。大modelへの一般化を示すmodeling resultとして扱うべきである。

## Cost analysis

SPIReはtarget専用にdraftをtrainingする必要があるため、導入前に追加training costが発生する。

論文は「servingで消費するcomputeがtarget training costより十分大きいproduction環境なら、draft trainingへの投資は推論cost削減で回収できる」という形でcost analysisを行う。

したがって、少量だけ使うmodelや頻繁にtargetを更新する環境では、training済みdraftを長期間使える大規模serviceほど有利とは限らない。

## 既存研究との差

### Vanilla speculative decodingとの違い

Vanilla方式は小さなdense draftを使う。短context・小batchでは分かりやすく強いが、大batch・長contextではdraft自身のKV cache trafficも増える。

SPIReはdraftのKV参照量を固定し、target activationなどを使って小さなdraftのcandidate qualityを補う。

### MagicDecとの違い

MagicDecはtarget modelに近い大きなmodelをsparse draftとして使うため、受理token数は多い。しかしdraft forward自体のFLOPsが大きい。

SPIReはacceptanceを少し犠牲にしても浅いdraftへ落とし、総iteration costを小さくする。

### EAGLE系との関係

target modelの中間stateをdraft predictionへ利用するという方向はEAGLE系と共通する。ただしSPIReの焦点は、低latencyより**大batch・長context throughputにおけるdraft KV traffic**であり、固定window sparse KVと性能モデルを中心にdraft architectureを選ぶ点が特徴である。

## 一般的な実装への示唆

投機的decodeをthroughput目的で導入する場合、draft model選定をparameter数とacceptance率だけで行うのは不十分である。

少なくとも、

- draft weight bytes
- draft KV bytes / request
- context長分布
- batch size分布
- target verificationのcompute/memory bound境界
- 1 roundあたりの平均受理token数

を一緒に見る必要がある。

特に長contextでは、**draft modelまでfull KV cacheを持つこと自体が二重のmemory burdenになる**。draftのattention patternをproduction workloadに合わせて設計する余地がある。

## 限界・注意点

- 主結果は性能モデルによるmodeled throughputであり、production serving stackのend-to-end実測ではない。
- 実際のacceptance評価は8-layer・67M body-parameter targetを中心としており、大規模modelの結果は外挿を含む。
- 固定window sparse attentionが十分かどうかはtaskとcontext依存性に左右される。遠距離情報がdraft predictionに強く必要なtaskではacceptanceが落ち得る。
- target activationを使うため、targetと独立に使い回せる汎用draftではない。target architectureやweightsが変われば再trainingが必要になり得る。
- Feedback Transformer由来のtrainingは通常Transformerより逐次依存が強い。SPIReは短いrolloutとtarget activationで緩和するが、training complexityは増える。
- throughput modelはimplementation差を意図的に捨てているため、実kernel・GPU interconnect・schedulerの効率によって実測順位が変わる可能性がある。
