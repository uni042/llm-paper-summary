# SPIRe: Boosting LLM Inference Throughput with Speculative Decoding

> 大バッチ投機的デコードの受理率とKV読出し量を実測し、浅くKVを制限したドラフトの性能モデルを構築して、重み読出しよりKV帯域が支配する条件の処理量を比較する研究。

## 概要

投機的デコードでは、小さな下書きモデル（draft model）が数トークン先まで候補を生成し、大きな対象モデル（target model）がそれらをまとめて検証する。候補が対象モデルと十分一致すれば、対象を1トークンずつ呼ぶより少ない回数の重み／KV読出しで複数トークンを確定できる。

この方式では一般に、草稿 モデルについて次の2つが同時に望ましい。

- 順伝播過程が軽いこと。
- 対象モデルと似た予測をして、候補が多く受理されること。

しかし、このトレードオフの最適点は「遅延を下げたいのか」「スループットを上げたいのか」で変わる。

小バッチではモデル重みを毎段階読むコストが支配的になりやすく、非常に小さい草稿が有利である。一方、大バッチでは重み読出しを多数リクエストで償却できるため、長文脈の**KVキャッシュ読出し**が相対的に大きくなる。この領域では、草稿のパラメータ数だけを減らしてもKVキャッシュが文脈長に比例して増えるなら、スループットは伸びにくい。

SPIReはこの観察から、草稿 モデルを次のように設計する。

1. 草稿が読むKVキャッシュを疎にし、文脈が伸びてもKV通信量をほぼ一定にする。
2. 対象モデルの一部ブロックから初期化し、浅くても対象に似た表現を得やすくする。
3. 過去の対象 活性値を草稿のメモリとして再利用し、浅さによる表現力不足を補う。
4. 正解トークンだけでなく対象の出力分布へ近づくよう蒸留（distillation）し、候補受理率を高める。

8層・67M bodyパラメータの対象モデルで平均生成長を実測し、重み量・KV量・演算強度からスループットを計算する性能モデルで比較した結果、SPIReは通常の投機的デコードより100%、MagicDecより35%高いmodeled throughputを示した。これは実装フレームワークの端から端までのtoken/sではなく、長文脈大バッチでKV帯域を抑えた場合のモデル化結果であり、Llama 3 70Bの値も外挿である。

## まず「投機的decodeのthroughput」をどう考えるか

### 候補をたくさん当てるだけでは速くならない

投機的デコードの1 ラウンドでは、

`draftが候補列を生成 → targetがまとめて検証 → 一致したprefixを確定`

という処理を行う。

1 ラウンドで平均何トークン確定できるかを平均生成長（average generation length）と考えると、この値が大きいほど対象を呼ぶ回数は減る。

ただし、草稿自身が重ければ1 ラウンドの時間も伸びる。したがってスループットは概念的には、

`1 roundで確定するtoken数 / 1 roundにかかる時間`

で決まる。

つまり、受理率が高い草稿が常に最速とは限らない。少し受理率が低くても、KV読出しや演算量が大幅に小さい草稿の方が最終スループットは高くなり得る。

### 大batchになると「小さいdraft」の意味が変わる

遅延最適化ではバッチ sizeが小さく、モデル 重みをGPU メモリから読むコストが大きい。そのためパラメータ数の小さい草稿が分かりやすく有利になる。

スループット最適化ではバッチ sizeを増やす。重みはバッチ中で再利用される一方、各リクエストはそれぞれ別のKV キャッシュを持つため、文脈が長くなるとKV キャッシュ 通信量が支配的になる。

この領域で重要なのは、草稿 モデルの「パラメータ数」だけでなく、**1 トークン生成するたびに何byteのKV キャッシュを読むか**である。

## 評価指標: 実装依存を減らしたthroughput model

SPIReは、特定フレームワークのカーネル実装やバッチ スケジューラによる差が草稿 構成比較へ混ざるのを避けるため、主評価に性能モデルを使う。

順伝播 passのコストを大きく、

- 演算量（FLOPs）
- モデル 重みの読出しbyte数
- KV キャッシュの読出しbyte数

へ分け、メモリ 通信量をハードウェア operational intensityを使ってFLOP相当コストへ換算する。そして草稿生成と対象検証のコスト、平均生成長を組み合わせてスループット倍率を求める。

この方法には「特定のCUDA カーネルが速かったから勝った」という混入を減らせる利点がある。一方で、**結果は実際の実運用 実行時環境で直接測ったエンドツーエンド トークン/sではない**。論文の「100%改善」「35%改善」はこのmodeled スループットについての値として読む必要がある。

## SPIReという名前が表す3要素

SPIReは論文中で、

- **疎 KV キャッシュ**
- **枝刈り済み Initialization**
- **Recurrent フィードバック Transformer**

の頭文字を含む名称として説明される。

実際の草稿設計では、これらに対象 活性値利用と蒸留損失も加わる。

## 手法

### 1. Sliding-window KV cache — contextが伸びてもdraftのKV読出しを増やさない

最も重要な仕組みは、草稿 モデルの注意を静的に疎にすることだ。

SPIReはStreamingLLM型の注意 マスクを使い、過去トークンすべてへ注意するのではなく、主に**直近64 トークンの窓 + 先頭の注意 sink 1 トークン**だけを参照する。training時と推論時の両方で同じ制約を使う。

通常の完全 注意 草稿では文脈が2倍になれば、各段階で読む草稿 KV キャッシュも概ね増える。SPIReでは参照窓を固定するので、文脈が数千、数万トークンへ伸びても草稿側のKV キャッシュ 通信量はほぼ一定である。

これは大バッチ・長文脈領域で特に効く。対象 モデルは依然大きいが、投機を導入するために追加した草稿側のメモリ 通信量が文脈長とともに膨張するのを防げるからである。

代償は、草稿が遠い過去へ直接注意できないことだ。これだけでは対象との予測一致率が落ち、1 ラウンドで受理されるトークン数が減る可能性がある。後続の仕組みはこの品質低下を補うためにある。

### 2. Pruned initialization — targetの一部blockをdraftへ移植する

論文の実験では対象 モデルは8 Transformer ブロックで、SPIReの草稿はより浅い。

草稿をランダム initializationから学習するのではなく、対象 モデルの埋め込み、最後側の2 Transformer ブロック、unembeddingを使って初期化する。つまり対象の計算グラフをそのまま小さく切り出すわけではないが、**対象がすでに学習した表現変換を草稿の出発点として再利用する**。

この初期化により、同じ学習budgetでもランダム initializationより対象に近い予測を得やすくなり、平均生成長が改善したと報告する。

また対象と草稿の埋め込み 次元を合わせている。パラメータ数だけ見れば次元を縮めた方が軽くできるが、同じ隠れ sizeを保つことで対象の中間活性値を草稿へ直接渡しやすくなる。

### 3. Feedback memory — 浅いdraftに過去の情報をまとめて渡す

通常のTransformerでは各層が過去トークンの同じ層のKVへ注意する。フィードバック Transformerでは、前トークンまでに各層で得た活性値を混ぜてメモリ ベクトルを作り、次トークンの注意先として利用する。

浅いモデルでは層数が少ないため1 トークン内で行える変換が少ない。フィードバック メモリは、過去段階で複数層を通った情報を次段階へ再投入することで、その表現力不足を補う役割を持つ。

ただしフィードバック Transformerは通常、training時に文脈方向の並列化を壊しやすい。各トークンのメモリが前トークンまでの層 活性値へ依存するからである。

SPIReは草稿 モデル trainingに限定することでこの問題を軽減する。最大投機深さに対応する短い草稿 rolloutだけを逐次計算し、それより前の長いプレフィックスについては、すでに計算済みの**対象 モデル中間活性値**をメモリの代わりに使う。

言い換えると、草稿が長い文脈を自力で最初からフィードバック計算するのではなく、対象が持つ過去の表現を足場にして、その先の数トークンだけを予測する。

### 4. Target activationを使う理由

投機的デコードでは対象 モデルは定期的に候補トークンを検証する。その際に対象の中間活性値も得られる。

SPIReは、この対象由来のstateを草稿側へ与える設計を採用する。草稿自身の埋め込みだけから過去情報を再構成するより、対象が深いネットワークで作った表現を利用した方が候補分布を対象へ近づけやすい。

論文のablationでは、疎 KV キャッシュに次いで**対象 活性値を参照する仕組み**の寄与が大きかった。

これは草稿を単なる独立した小型LMとして扱うのではなく、対象推論中に生まれる中間状態を使う「対象依存草稿」として最適化していることを意味する。

### 5. Distillation loss — 正解tokenではなくtargetの分布へ近づける

通常のlanguage-モデル trainingは正解トークンへのcross entropyを最小化する。しかし投機的 デコードで重要なのは、データセットのground-truthに最も近いことだけではなく、**対象 モデルが出す確率分布へ草稿を近づけること**である。

SPIReは対象のsoft 確率 分布を使う蒸留損失を導入する。さらに論文では、投機的デコードで期待される受理 確率を高める項も含めた損失を検討する。

これにより、草稿の出力が「一般に良いLM」になることより、「この対象 モデルに受理されやすい候補を出す」ことへtraining 目的を寄せる。

## 1 roundで何が起きるか

SPIReを使うと、推論時の流れは概ね次のようになる。

1. 対象 モデルが直前までに確定したトークンと中間活性値を持つ。
2. SPIRe 草稿は固定窓の疎KVと対象由来メモリを使い、数トークンの候補を自己回帰に生成する。
3. 対象 モデルが候補ブロックをまとめて検証する。
4. rejection samplingに従って受理できるプレフィックスを確定する。
5. 新しい対象 活性値を次ラウンドの草稿 メモリへ利用する。

このため草稿は完全 文脈を毎回読む必要がない一方、対象側の豊かな表現を継続的に利用できる。

## なぜMagicDecよりacceptanceが低くても速くなり得るのか

論文の比較対象MagicDecは、対象 モデルそのものを疎注意で草稿として使う自己投機（self-speculation）に近い構成で、候補品質が高い。

実際、文脈 length 512付近の平均生成長は、

- Vanilla 投機的 デコード: 約2.65 トークン/ラウンド
- MagicDec: 約3.89 トークン/ラウンド
- SPIRe: 約3.40 トークン/ラウンド

であり、SPIReはMagicDecより1 ラウンドあたりに確定できるトークン数が少ない。

それでもSPIReは浅く、1回の順伝播 コストが小さい。したがって、

`少し短いaccepted block × かなり安いdraft forward`

の方が、

`長いaccepted block × 高価なdraft forward`

より高スループットになる領域がある。

この「受理率だけを見て草稿を選ばない」という点が論文の重要なメッセージである。

## 評価

### 評価設定

実験では、8-層・67M body パラメータのmulti-ヘッド-注意 対象 モデルを固定し、草稿 構成を変えて比較する。モデルはLongCrawl64 データセット、系列 length 1024でtrainingされる。

比較対象は主に、

- 通常の小型草稿によるVanilla 投機的 デコード
- 対象と同等モデルを固定窓 疎 注意で使うMagicDec
- SPIRe

である。

受理特性に相当する平均生成長は実際にトークン生成して測り、バッチ size・文脈 lengthを変えたスループットは前述の性能モデルから計算する。

### 主要結果

論文がhighlightする条件では、SPIReのmodeled スループットは、

- Vanilla 投機的 デコードより **100%高い**
- MagicDecより **35%高い**

と報告される。

「100%高い」は約2倍という意味である。ただしこれは実運用 フレームワークで測定したエンドツーエンド トークン/sではなく、性能モデル上のスループット multiplierである。

### context長がばらつく環境で有利な理由

MagicDecは非常に長い文脈・大バッチでは強い一方、短〜中文脈では大きな草稿 モデルの演算量増加がKV削減効果を上回り、通常デコードより不利になる場合がある。

SPIReは草稿自体を浅くしつつKVを固定窓化するので、短い文脈では順伝播 コストを抑え、長い文脈ではKV 通信量増加も抑えられる。実運用のようにリクエストごとの文脈長が大きくばらつく場合に、より広い範囲で利益を出すことを狙っている。

### Ablationから分かる寄与

論文のablationでは、スループット改善への寄与は大きい順に概ね、

1. 疎 KV キャッシュ
2. 対象 モデル 活性値の利用
3. distillation 損失
4. 対象 モデルをpruneしたinitialization
5. フィードバック メモリ
6. mixed 損失

とされる。

つまりSPIReの性能は「フィードバック Transformerが主役」というより、まず**草稿 KV 通信量を固定すること**が最重要で、その上で対象依存情報を使って受理低下を取り戻す構成と理解した方がよい。

### Llama 3 70Bへの外挿

論文は同じ平均 生成 length比を仮定し、性能モデルの重み/KV/演算量をLlama 3 70B相当に置き換えた外挿も行う。この結果でも多くの文脈長でSPIReが高い推定スループットを示す。

ただしこれは**Llama 3 70B上でSPIReを実装・trainingしてエンドツーエンド測定した結果ではない**。大モデルへの一般化を示すmodeling 結果として扱うべきである。

## Cost analysis

SPIReは対象専用に草稿をtrainingする必要があるため、導入前に追加training コストが発生する。

論文は「推論提供で消費する計算が対象 training コストより十分大きい実運用環境なら、草稿 trainingへの投資は推論コスト削減で回収できる」という形でコスト analysisを行う。

したがって、少量だけ使うモデルや頻繁に対象を更新する環境では、training済み草稿を長期間使える大規模serviceほど有利とは限らない。

## 既存研究との差

### Vanilla speculative decodingとの違い

Vanilla方式は小さな密 草稿を使う。短文脈・小バッチでは分かりやすく強いが、大バッチ・長文脈では草稿自身のKV キャッシュ 通信量も増える。

SPIReは草稿のKV参照量を固定し、対象 活性値などを使って小さな草稿の候補 品質を補う。

### MagicDecとの違い

MagicDecは対象 モデルに近い大きなモデルを疎 草稿として使うため、受理トークン数は多い。しかし草稿 順伝播自体の演算量が大きい。

SPIReは受理を少し犠牲にしても浅い草稿へ落とし、総反復 コストを小さくする。

### EAGLE系との関係

対象 モデルの中間stateを草稿 predictionへ利用するという方向はEAGLE系と共通する。ただしSPIReの焦点は、低遅延より**大バッチ・長文脈 スループットにおける草稿 KV 通信量**であり、固定窓 疎 KVと性能モデルを中心に草稿 構成を選ぶ点が特徴である。

## 一般的な実装への示唆

投機的デコードをスループット目的で導入する場合、草稿 モデル選定をパラメータ数と受理率だけで行うのは不十分である。

少なくとも、

- 草稿 重み bytes
- 草稿 KV bytes / リクエスト
- 文脈長分布
- バッチ size分布
- 対象 検証の計算/メモリ 上限境界
- 1 ラウンドあたりの平均受理トークン数

を一緒に見る必要がある。

特に長文脈では、**草稿 モデルまで完全 KV キャッシュを持つこと自体が二重のメモリ burdenになる**。草稿の注意 パターンを実運用 ワークロードに合わせて設計する余地がある。

## 限界・注意点

- 主結果は性能モデルによるmodeled スループットであり、実運用 推論提供 積層のエンドツーエンド実測ではない。
- 実際の受理評価は8-層・67M body-パラメータ 対象を中心としており、大規模モデルの結果は外挿を含む。
- 固定窓 疎 注意が十分かどうかはtaskと文脈依存性に左右される。遠距離情報が草稿 predictionに強く必要なtaskでは受理が落ち得る。
- 対象 活性値を使うため、対象と独立に使い回せる汎用草稿ではない。対象 構成や重みが変われば再trainingが必要になり得る。
- フィードバック Transformer由来のtrainingは通常Transformerより逐次依存が強い。SPIReは短いrolloutと対象 活性値で緩和するが、training complexityは増える。
- スループット モデルは実装差を意図的に捨てているため、実カーネル・GPU interconnect・スケジューラの効率によって実測順位が変わる可能性がある。
