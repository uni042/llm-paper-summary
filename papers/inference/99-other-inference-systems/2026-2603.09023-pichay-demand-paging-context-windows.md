# The Missing Memory Hierarchy: Demand Paging for LLM Context Windows

> エージェント文脈を仮想メモリとしてページングし、古いツール結果を追い出して再参照時に復元する透明プロキシ。139万追い出しで0.0254%フォルト率を報告。
## 書誌情報
- **著者**: Tony Mason
- **著者・所属**: University of British Columbia; Georgia Institute of Technology
- **公開**: arXiv
- **種別**: プレプリント
- **対象**: 需要ページング、コンテキスト管理、エージェントメモリ、作業集合、透明プロキシ
- **実装**: 透明HTTPプロキシPichayを実装し、観測用probe、介入proxy、比較実験runnerを提供する。L1追い出し、L2フォルト駆動固定、L3モデル主導会話圧縮を実装し、L4クロスセッション記憶は設計段階。
## 概要
PichayはLLMエージェントのコンテキスト窓を物理メモリではなく小容量・高速・高価なL1キャッシュとして扱い、古いツール結果を追い出して必要時に再取得する需要ページング（demand paging）を透明HTTPプロキシで実装する。857本番セッション、54,170 API呼出し、44.5億有効入力トークンの分析では21.8%を構造的削減可能と推定し、139.3万件の模擬追い出しでページフォルト率0.0254%を測定した。標準タスクでは圧縮＋トリムで入力トークン37.1%削減、実運用では空きコンテキストを7%から43%へ回復する一方、681ターンの極端な負荷では97%フォルト率のスラッシングも観測し、作業集合管理の必要性を示す。

PichayはOS仮想メモリの需要ページングをメッセージAPI層へ移植し、アドレス可能な古い内容を追い出し、モデルが同じツール入力を再要求した時点をページフォルトとして観測する。フォルトしたページは同一内容ならセッション中固定し、誤った追い出しから作業集合を学習する。さらにモデル自身がrelease/faultを指示する仮想ツールと、drop/summarize/anchor/collapseを指定するcleanup tagを設け、従来OSにはない協調的メモリ管理を可能にする。

代表結果として、オフラインページフォルト率は29 proxy-captured sessions replayでFIFO age=4 turns, min_size=500 bytesに対して0.0254%（354/1,393,000 evictions）。通常ワークロードでは4ターン超のRead結果が再要求される確率は非常に低く、積極的追い出しが成立する。
## 問題設定
エージェント型LLMは毎API呼出しでシステム指示、全ツール定義、会話履歴、過去ツール結果を再送し、既に不要な内容もセッション寿命中コンテキストを占有する。プロンプトキャッシュは静的接頭辞の再計算を減らしてもトークン自体を窓から除かず、出力トークンごとの注意対象として残る。単純な要約や剪定は不可逆・損失的で、後で必要になった内容を戻すフォルト機構や作業集合推定を持たない。857セッションではツール出力が会話バイトの79.4%、主セッションの再処理増幅率中央値が84.4倍に達し、有限コンテキストを無管理の物理メモリとして扱うこと自体が問題となる。
## 新規性
PichayはOS仮想メモリの需要ページングをメッセージAPI層へ移植し、アドレス可能な古い内容を追い出し、モデルが同じツール入力を再要求した時点をページフォルトとして観測する。フォルトしたページは同一内容ならセッション中固定し、誤った追い出しから作業集合を学習する。さらにモデル自身がrelease/faultを指示する仮想ツールと、drop/summarize/anchor/collapseを指定するcleanup tagを設け、従来OSにはない協調的メモリ管理を可能にする。
## 手法
### 手法のあらまし
Pichayはクライアントと推論APIの間に透明HTTPプロキシとして入り、クライアントが組み立てた完全なmessage配列を受け取る。クライアント側の原本をバッキングストアとして保持したまま、送信直前の配列だけを測定・変換する。ツール結果を再取得可能なRead系ページと、再取得不能だが古くなったBash/検索結果などのガベージへ分け、前者だけをフォルト率の分母にする。

基本追い出しはユーザーターン年齢FIFOで、4ターン超かつ500バイト超の候補を選ぶ。追い出したRead結果は『どのファイルを何バイト追い出し、必要なら再読込せよ』という短い取得ハンドルへ置換する。モデルが同じツール名・引数を再要求するとプロキシがページフォルトとして記録し、内容ハッシュが同じならそのページを固定する。ファイル編集でハッシュが変われば固定を解除し、新版は新しいページとして扱う。

コンテキスト圧力は60K未満の通常、60–100Kの助言、100–120Kの強制、120K以上の緊急という段階に分ける。助言域ではモデルへ占有状況と大きなブロックを知らせ、メモリ_release/メモリ_fault仮想ツールやcleanup tagで自発的に解放・復元・要約できる。会話履歴はL3としてモデル作成要約へcollapseし、メタデータだけを原子的チェックポイントへ保存する。最終的にL1生成窓、L2作業集合、L3圧縮履歴、L4永続記憶という階層を構成する。

### 透明プロキシとページ分類
Messages API直前で完全な要求を受け、モデル・クライアント・推論APIを変更せずmessage配列を介入点にする。クライアントが保持する元会話をバッキングストアとして使うため、プロキシは削除した内容を独自に二重保存する必要がない。各ターンで完全な配列が再提示される性質を逆に利用し、永続接続なしでも状態管理できる。

ツール結果を、安定した識別子があり再読込できるページと、一度消費すれば再要求する意味が薄いガベージへ分類する。Readファイルはページング対象、Bashや検索結果はガベージ回収対象とし、後者をフォルト率へ混ぜて安全性を過大評価しない。ページング対象にはtool名・引数から安定キーを作り、追い出し履歴、内容ハッシュ、fault履歴を結び付ける。これにより『消してよい死んだ出力』と『必要なら戻せる冷たいページ』を別の回収規則で扱える。

### 追い出し・取得ハンドル・フォルト検出
現在実装は4ユーザーターンより古く500バイト超の結果をFIFO候補にし、エラー結果はデバッグに必要なので残す。追い出し時は元内容を短い取得ハンドルへ置換し、対象ツール、パス、元サイズ、再取得方法を文脈内へ残す。

モデルが後で同じツール名と引数を発行すると、その要求をページフォルトとして観測できる。ハンドルは単なる要約ではなく遅延束縛アドレスとして機能し、再読込時には古いコピーではなく現在のファイル内容を得る。これにより不可逆な剪定と異なり、誤追い出しを測定可能なコストへ変える。

### フォルト駆動固定と協調管理
あるページを追い出した後、同じ内容が再要求されたら内容ハッシュをフォルト履歴へ登録し、そのセッションでは以後追い出さない。編集でハッシュが変われば固定を解除するため、古い版への誤固定を避ける。単純FIFOの失敗を一度のフォルトから学習する作業集合近似である。

さらにプロキシだけが処理するメモリ_releaseとメモリ_faultという仮想ツールをモデルへ見せ、モデル自身に冷ページ解放と復元を指示させる。cleanup tagではdrop、summarize、anchor、collapseを表現し、意味を理解するモデルがOSの参照ビット相当を自発的に提供する協調型ページングへ拡張する。

### 段階的圧力制御と多層階層
60K未満では観測のみ、60–100Kでは低メモリ警告と最大ブロック一覧を提示し、100–120Kで自動追い出し、120K以上で閾値を緩めた緊急追い出しを行う。いきなり強制削除せず、モデルがまとまった作業を終えて自発的に整理する猶予を与える。

ツール結果のL1/L2管理に加え、古い会話ターンはモデル自身が結果中心の要約へcollapseしてL3へ移す。ブロックID、ハッシュ、サイズ、状態、要約だけをJSONへ原子的保存し、内容原本はクライアント履歴を利用する。L4はクロスセッション永続記憶として設計され、将来の検索・索引層へ接続する。

### 全体のデータ／制御の流れ
要求ごとにproxyがツール定義、system prompt、message履歴を解析し、現在の圧力域を判定する。ガベージ回収、ページ追い出し、ツール定義stub化、重複除去を適用した後に推論APIへ送る。応答ストリーム中の仮想ツール呼出しやcleanup tagはframeworkへ渡す前にproxyが横取りし、内部状態を更新して次ターンへ整合した結果を注入する。

計測系は生セッションを読むprobe、オンライン介入proxy、条件を揃えたpaired experiment runnerの三層からなる。追い出しログとフォルト履歴をJSONLへ残し、オフライン再生で多数の仮想追い出しを検証する。実運用ではcheckpointからブロック状態を再開し、要求配列を再走査して内容を遅延再構成する。
## 評価条件
- **ハードウェア**: 特定GPUカーネルのベンチマークではなく、Claude CodeをAnthropic APIへ接続する実運用エージェント環境を測定する。ローカルWSL環境とUbuntu VM上の約4か月分のセッションを対象とする。
- **ソフトウェア**: Pichayは透明HTTP proxy、セッションJSONLを解析するprobe.py、比較対象/trimmed/compact+trimを比較する実験runnerからなる。対象クライアントはClaude Code、比較実験では同一Claude Opus、同一temperature、同一タスクpromptを使う。
Phase 1は857セッション、54,170 API呼出し、44.5億有効入力トークンを固定コホートとして会話レベルのツール出力比率、増幅率、トークン accountingを測る。Phase 2はproxyで完全要求を捕捉できた5セッション99 API呼出し、24.4MBを用い、dead tool output、unused tool schemas、静的 resend、skill duplicationへ分解する。安全性は29セッションをオフライン再生し139.3万件の追い出しと354フォルトを数える。標準タスクでは比較対象、trimmed、compact+trimを同一モデル条件で比較し、さらに二つの本番セッションで定常時と極端圧力時の挙動を観測する。
データは一人のpower userによる15ソフトウェアプロジェクトのClaude Code利用で、一般ユーザーや他エージェント製品への外的妥当性は未検証。L1追い出しとL2固定は評価済みだがL3会話圧縮は大規模評価前、L4クロスセッション記憶は設計段階である。オフライン低フォルト率と681ターン本番の97%フォルト率が大きく異なるため、作業集合が常駐 setを超える極端条件では単純FIFOが破綻する。
## 主要結果
857セッションの全体分析ではツール結果が会話バイトの79.4%を占め、主セッションで各ツール結果が後続ターンに再処理される増幅率中央値は84.4倍、P90は570.8倍だった。API要求を詳細分解した5セッションではdead tool output 26.5%、unused tool schemas 20.2%、静的 resend 11.0%、skill triplication 2.9%で計60.5%の構造的無駄を観測し、全コーパスへの保守的投影では21.8%、9.704億入力トークンが削減可能と推定した。

- オフラインページフォルト率 / 0.0254%（354/1,393,000 evictions） (比較対象: FIFO age=4 turns, min_size=500 bytes; 条件: 29 proxy-captured sessions replay) — 通常ワークロードでは4ターン超のRead結果が再要求される確率は非常に低く、積極的追い出しが成立する。

- 標準タスク入力削減 / 37.1%（114,222→71,816 effective input トークン） (比較対象: proxy observation 比較対象; 条件: compact+trim、同一Claude Opus/temperature/task) — ツール定義削減と古い結果追い出しを併用し、タスク成功を維持した。

- 本番Session A空き容量 / 7%→43% free context (比較対象: compaction前; 条件: steady-state coding、15 evictions) — 通常のコーディング作業では一度のRead faultを許容して36ポイントの余裕を回復した。

- 極端負荷のthrashing / 97% fault rate（659/680） (比較対象: 通常オフライン0.0254%; 条件: 681-turn multi-agent session) — 作業集合が常駐 setを超えるとFIFOが破綻し、rate limitを有用作業よりfaultへ消費する。

### 負の結果・境界条件
- 681ターンの持続的multi-agentセッションでは606件のRead追い出しに対し659件のフォルトが発生し、5,038KBから339KBまで圧縮しながらも同じファイル群を追い出して再読込するスラッシングへ陥った。セッションはcontext limitではなくAPI rate limitで終了した。また会話collapseはprompt キャッシュ prefixを変えるため、一例ではキャッシュ hit率が一時100%から25%へ低下し約105K トークンの再計算を発生させた。

### 結果の読み方
LLM文脈ではページを保持するだけで毎ターン入力・注意コストが累積するため、古典VMと逆にfaultを少数許容して積極的に追い出す方が安い。ただし高fillでは一回のfaultが全context再推論を誘発するため、圧力が高いほど保守的にするサイズ・fill依存方針が必要になる。
## 品質への影響
標準タスクでは三条件すべて正しく完了し、構造的削減が必ずしも回答品質を落とさないことを確認する。一方、極端なthrashingでは追加round tripが増え、品質以前にrate budgetを消費するため、fault-driven pinningや将来のpin decay、working-set推定が必要である。
## 既存研究との差
LLMLinguaやagent 枝刈りは情報量やタスク重要度でpromptを小さくするが、Pichayは内容意味を推定する前に再取得可能性とアクセス履歴を管理する。MemGPTはVM比喩とarchival メモリを導入したが、容量到達時のflush中心で、明示的なreleaseや実測fault率を主眼にしない。SideQuestはKV キャッシュ自体から古いtool outputを追い出すため推論engine変更を要するが、PichayはAPI proxyでmessage列を変換する。prompt キャッシュは再計算を減らすだけでcontext占有を減らさない。
## 限界
実証コーパスは一人のpower user、Claude Code、15ソフトウェアプロジェクトに偏り、他製品・一般ユーザー・非コーディング用途で同じ無駄率やfault率になる保証はない。L3会話圧縮は実装済みだが大規模評価前、L4クロスセッション記憶は未実装。現在のFIFO age policyは定常時には低faultだが、作業集合が常駐 setを超えると97% faultのthrashingへ陥る。構造変更はprompt キャッシュ invalidationを起こし、一時的に大きな再計算コストを生む。
## 実装状態
L1 追い出し、L2 fault-driven pinning、L3 model-authored collapseをproduction proxyへ実装し、日常のソフトウェア開発で使用している。probe、proxy、experiment runnerにより計測・介入・比較を分離する。L4 persistent cross-session メモリは設計のみで、multi-user検証、cost-aware replacement、pin decay、phase-aware 追い出しなどはfuture workとして残る。
## 研究上の位置づけ
本サーベイではGPU内部KV オフロードの直接手法ではなく、推論要求を構成する上位文脈の階層メモリ化として位置付ける。FlexGen等がtensor/KVをGPU・CPU・SSD間で動かすのに対し、Pichayは意味のあるtool result/pageをL1 contextからclient backing storeへ追い出す。共通する本質は、有限で高価な高速層をworking setだけに限定し、miss/faultを許容して大容量低速層を使うことにある。保持コストが毎ターン累積するというLLM固有の逆転コストモデルは、SSD/NVMe活用を含む将来の階層推論で置換方針を考える際にも有用な視点を与える。
