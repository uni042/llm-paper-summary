# MELINOE：混合専門家モデルのルーティングをキャッシュしやすく微調整する推論最適化

## 概要

MELINOEは、混合専門家モデル（MoE）の専門家重みをCPUへ退避する推論環境で、**モデル自身の専門家選択を少数の再利用しやすい専門家へ寄せる**手法である。既存のオフロード方式は、学習済みのルータが選んだ専門家を前提に、キャッシュ置換、事前読込み、量子化を工夫する。これに対しMELINOEは、配備前にルータを微調整して一つの生成系列内の専門家選択を安定させ、配備時には入力文から好まれる専門家を予測してGPUキャッシュへ先読みする。狙いは、専門家が選ばれるたびにCPUメモリからGPUへ重みを移す回数を減らし、PCIe転送待ちを直接抑えることである。

著者らはOLMoE、Phi-3.5-MoE、Mixtral-8x7Bを対象に、H100、A100、RTX 4090のメモリ制限環境で評価した。効率的な比較方式に対する生成処理能力は**1.2～3倍**、転送負担の大きい比較方式に対しては条件付きで最大**14.7倍**と報告する。さらに、Dolly15Kの文章生成品質とGSM8Kの算数問題正解率は、評価した設定では元モデルを維持または上回った。ただしこれは配備前にモデル重みを変更できること、学習用データと計算資源を利用できることが前提であり、学習不要の実行時最適化ではない。一次論文の表2・表3を中心に、速度と品質、微調整と先読みの寄与を区別して監査した。

## 問題設定

混合専門家モデルは各トークンで一部の専門家だけを計算するので、総パラメータ数に比べて演算量を抑えられる。しかし、次に選ばれる専門家は入力によって変わる。GPUに全専門家の重みを常駐させられなければ、必要な重みをCPUから転送しなければならない。原著ではOLMoEの全重みの約93%、Mixtral-8x7Bの約96%を専門家が占めると記載する。総量の大きい専門家をGPUに置ききれないとき、演算が少なくても重み転送が律速となる。

H100の例では、OLMoEの専門家をすべてGPUに置いた場合の復号処理能力は37.84トークン/秒だが、25%だけ常駐させると15.68トークン/秒へ低下する。Phi-3.5-MoEも19.91から4.43トークン/秒へ低下する。Mixtral-8x7Bの全重みは半精度では単一の80GB H100に収まらず、全常駐条件を測定できない。これらは原著表1の条件付き実測であり、GPUメモリ容量だけでなく専門家の転送・再利用が生成性能を支配することを示す。

通常の事前学習では、専門家の使用頻度を広く分散させる負荷分散が望ましい場合がある。一方、少数のGPUへ専門家をキャッシュする単一系列の生成では、毎トークン別の専門家へ切り替わるほどキャッシュミスが増える。著者らはOLMoEで、ある系列内の使用頻度上位8専門家が全専門家活性化の約31%を占めるという弱い偏りを観察した。この偏りを系列ごとに強めれば、必要な専門家集合をGPU内へ置き続けやすくなる。ただしすべての入力が同じ専門家へ集中すればモデルの表現能力を損なうため、「系列内では局所的、系列間では多様」という両立が課題となる。

## 手法

### キャッシュ状態を微分可能な近似として表す

MELINOEは配備前の微調整で、実際のCPUとGPUの間で毎回重みを転送する代わりに、専門家選択履歴から「その専門家がGPUに存在しそうか」を推定する柔らかなキャッシュ状態を作る。層 `l`、トークン時点 `t` におけるルータ確率から上位 `K` 専門家を選び、選択された専門家を1とする要求ベクトル `r(l,t)` を定義する。専門家ごとのキャッシュ状態 `c(l,t)` は、過去の状態を減衰係数 `γ` で弱め、今回の要求を加えることで更新する。キャッシュ容量 `C` を満たす段階に達した後は、状態の総量が `C` となるよう正規化する。

この仕組みでは、最近頻繁に選ばれた専門家ほどキャッシュ状態が大きくなる。減衰係数が小さければ直近の要求を重視する置換に近く、大きければ長期の利用頻度を残す置換に近づく。主な実験では `γ=0.9`、容量 `C=E/4`（各層の専門家総数 `E` の4分の1）を採用する。これは本物のキャッシュを完全に再現するものではないが、選択頻度の低い専門家を要求すると転送が増えるという関係を学習時の目的関数に組み込める。

### 転送を減らす損失とルータ崩壊を防ぐ損失

キャッシュ模擬損失 `Lcs` は、各層・各トークン・各専門家について、選択の有無 `r` と、キャッシュに存在しない度合い `1-c` の積を合計する。選択されたのにキャッシュ状態が小さい専門家ほど大きな罰則を受ける。この罰則を下げるように微調整すると、同じ系列で再利用しやすい専門家へ選択が集まる。損失は実測PCIe時間そのものではなく、キャッシュミスの代理量であるため、転送削減と時間短縮の対応は実機で別途検証する必要がある。

ただしこの損失だけを強くすると、すべての入力で同じ専門家を選ぶルータ崩壊が起こり得る。そこで元モデルの専門家選好順序を保持する順位整合損失 `Lrm` を加える。元モデルで専門家 `i` が `j` より好まれた場合、微調整後もその相対順位を余裕幅 `ρ` 付きで保つように罰則を課す。原著の式(5)はこの順序違反を数える。最終損失は、通常の言語モデル損失 `Lnll` と二つの補助損失の加重和 `L=Lnll+λcs Lcs+λrm Lrm` である。単に転送だけを最小化せず、言語生成品質と元ルータの選択構造を保護する点が重要である。

更新するパラメータも限定する。ルータ重みとゲート投影を更新し、専門家の上方向・下方向の投影には階数32の低ランク適応（LoRA）を適用し、それ以外の事前学習済み重みは固定する。原著の主設定では順位余裕幅 `ρ=0.1` を用いる。この微調整は配備前に全重みと学習データへアクセスできる側で行い、限られたGPUメモリしかない端末上で毎回実行するものではない。

### 入力文から専門家の好みを予測して先読みする

微調整によって系列内の専門家利用が安定した後、生成を始める前に、入力文からその系列で使われやすい専門家を予測する。まず入力文をBGE-Base-EN-v1.5で768次元のベクトルへ変換する。教師信号は、その入力文を微調整済みMoEで生成したときの、層ごとの全トークンにわたるルータ確率の平均である。二層の多層パーセプトロンが入力文ベクトルから層別の専門家分布を予測し、予測分布と教師分布の差をカルバック・ライブラー情報量で最小化する。

配備時には予測された各層の上位 `C` 専門家を生成開始前にGPUへ先読みする。キャッシュに入らない専門家はCPUの固定ページメモリに保持し、必要になったとき非同期でGPUへ転送する。専門家重みをHQQによる4ビット整数で保持することは、同じGPUメモリへ置ける専門家数を増やす別の工夫である。微調整は**将来のキャッシュミスそのものを減らす**、予測器は**初期のキャッシュ内容を適切にする**、量子化は**キャッシュ容量を実質的に増やす**という役割の違いがある。

### 一系列の実行経路

配備前にルータを微調整し、入力文と専門家選択履歴の対応から予測器を学習する。配備後に入力文が来たら、埋め込みと予測器から層別の好適専門家を求め、GPUキャッシュへ先読みする。その後は通常のルータ選択に従って各トークンを生成する。予測から外れた専門家はCPUから取得し、キャッシュ置換方針に従って退避・入替えする。ルータが同じ系列で似た専門家を選び続けるため、転送待ちが減り、生成処理能力が上がる。この仕組みは、元ルータの出力を変えずにキャッシュだけ改善する方式とは異なり、モデルの重みを変更する点で品質の再評価が不可欠である。

## 評価条件

| 観点 | 原著の条件 |
|---|---|
| モデル | OLMoE約7B、Phi-3.5-MoE約42B、Mixtral-8x7B約47B |
| 専門家構造 | OLMoEは層当たり64専門家・上位8選択、Phiは16・上位2、Mixtralは8・上位2 |
| GPU | H100 80GB、A100 40GB、RTX 4090 24GB |
| GPUメモリ制限 | それぞれのモデルについてOLMoE 3GB、Phi 16GB、Mixtral 24GBを人工的に設定 |
| キャッシュ | 頻度優先置換、専門家重みはHQQの4ビット整数表現 |
| 入力・品質 | Dolly15Kの文章生成指標ROUGE-L、GSM8Kの算数問題正解率 |
| 生成 | 代表的な構成要素除去実験では64トークンを生成。主実験はトークン毎秒で比較 |
| 比較対象 | Fiddler、Mixtral-Offloading、DeepSpeed-MoE、FLoE、MoE-Infinity |
| 計測の注意 | 転送負荷とGPU容量をそろえた条件に基づく。全モデル・全GPUで同じ絶対速度ではない |

この実験は、H100の80GBを無制限に使って全専門家を置く比較ではない。高容量GPUでもプロセスの使用量を制限し、専門家キャッシュが必要な状況を再現している。転送がほとんど発生しない全常駐環境へ結果をそのまま外挿してはいけない。

## 評価結果

### 処理能力と比較方式

|---|---:|---|---|

| OLMoE・RTX 4090 | 15.99～17.17 | 最良比較対象Fiddler 7.61～9.44 | GPUとCPUの転送費が相対的に重要な条件 |
| Phi-3.5-MoE・A100 | 14.34～15.67 | 次点5.11～5.81 | 専門家の大きさが異なるモデルでも効果 |

原著図3はGPU、モデル、課題によって処理能力が異なることを示す。最大14.7倍という値は、最良比較方式との普遍的な倍率ではない。著者らのまとめでは効率的な比較方式に対して1.2～3倍であり、転送が頻発する比較方式ほど差が大きくなる。GPU容量、転送帯域、専門家数、入力分布を変えると差は変化するため、最大値だけを性能代表値として掲げない。

| モデル・課題・キャッシュ容量 | 元モデル：処理能力／転送回数 | 微調整のみ | 微調整＋先読み |

| OLMoE・Dolly15K・16専門家 | 15.15／727 | 23.35／240 | 24.10／229 |
| OLMoE・GSM8K・16専門家 | 15.10／771 | 24.88／255 | 25.00／250 |

処理能力の単位はトークン/秒、転送回数は**64トークン生成時の一層当たり平均**である。原著表3を確認すると、OLMoEのDolly15Kでは微調整だけで転送が727回から240回へ減り、処理能力が15.15から23.35へ上がる。先読み追加後の改善は24.10までで、主な利得は微調整による選択の局所化から生じる。先読みが無意味ということではなく、予測器には約0.05秒の費用がある一方、条件によって生成全体の遅延を最大0.8秒減らせると著者らは報告する。どの費用を含むかを区別して解釈する必要がある。

|---|---:|---:|
| Dolly15K・OLMoEのROUGE-L | 0.1851 | 0.2486 |
| Dolly15K・Phi-3.5-MoEのROUGE-L | 0.2067 | 0.2270 |
| Dolly15K・MixtralのROUGE-L | 0.2159 | 0.2361 |

原著表2の比較は、微調整後も下流課題の品質が維持・改善されたことを示す。ただし評価は二つの課題系列と特定のモデル・学習設定に限定される。すべての未知課題で品質が改善する、あるいは転送罰則を無制限に強くしても品質が保たれるという主張ではない。量子化を使う他の比較方式には品質低下が見られるため、処理能力だけでなく品質とメモリ条件をそろえて比較する必要がある。

### 損失係数、同時処理、長い生成の感度

順位整合損失の重みを0.01～1.0で変えた範囲では、困惑度は比較的安定し、転送回数は一層当たり278回から314回へやや増える。キャッシュ模擬損失の重みを強めると転送回数は減るが、過度に強めると困惑度が急増する。転送削減のためにルータを集中させすぎると品質が悪化するという負の結果があり、両損失の重みを適切に釣り合わせる必要がある。

複数系列を同時に処理する場合は、系列ごとに好まれる専門家集合の和集合をキャッシュへ収める必要がある。原著図5では同時処理数を増やしてもMELINOEは元モデルより高い処理能力を保つが、系列間の専門家多様性によって転送が増えるため、相対的な改善率はやや小さくなる。長い生成については64～1024トークンの困惑度を比較し、評価した範囲で急激な悪化がないことを示す。ただし、将来の極端な長文脈や全く異なる配備先まで保証するものではない。

## 既存方式との差と適用範囲

MoE-InfinityやFLoEは、固定されたルータが生む専門家要求列を予測し、先読みやキャッシュ配置を改善する。Fiddlerは専門家計算の一部をCPUで実行して転送を減らす。MELINOEはこれらと異なり、専門家要求列の生成源であるルータを配備前に変え、キャッシュに載りやすい要求列を作る。配備時の予測器とキャッシュ管理は、その変化を利用して転送を減らす補助機構である。したがって、モデル側の調整と実行時のオフロードを組み合わせる協調最適化と位置付けられる。

適用条件は、モデル重みを変更でき、配備前に追加の微調整を行え、配備時には一部の専門家をCPUへ退避せざるを得ないことにある。全専門家をGPUに置ける環境では、転送削減の利得が小さい。逆にGPUメモリが非常に少なく、CPUとGPU間の転送が長い環境では効果が大きくなりやすい。ただし実際の転送時間は重みの量子化形式やPCIe世代、キャッシュ容量、同時要求数に依存する。モデルが大きいからといって常に同じ倍率で高速化するわけではない。

## 限界

第一に、学習済みのルータを変更するため、閉じたAPIとして提供されるモデルには直接適用できない。第二に、キャッシュ模擬損失は実際の転送費の代理であり、配備先の帯域や置換方針を完全には表さない。第三に、強い局所化はルータ崩壊や下流品質の悪化を招く。第四に、同時実行系列が増えると、それぞれの好適専門家の和集合がキャッシュ容量を圧迫する。第五に、主実験では層ごとのキャッシュ容量を一律に設定しており、層別の最適配分や非常に長い生成に応じた動的な容量変更は今後の課題としている。第六に、品質結果はDolly15KとGSM8Kを中心とするため、未知分野への一般化は別途検証が必要である。

結論として、MELINOEは「より賢く転送する」だけではなく「そもそも転送しなくて済む専門家選択へモデルを変える」方式である。キャッシュ模擬損失、順位整合損失、入力文条件付き先読みを区別し、転送回数と生成処理能力、品質を別々に測定している点が、単なる量子化・オフロード方式との差である。
