# Hydra: Sequentially-Dependent Draft Heads for Medusa Decoding

## 概要
Hydraは、Medusa型の投機的復号（speculative decoding）で使う複数の下書きhead（draft head）を、互いに独立なfuture-token predictorから**逐次依存（sequentially dependent）**なpredictorへ変える手法である。Medusaでは各headがbase modelの最後のhidden stateだけを見て「2 token先」「3 token先」などを独立予測するため、同じcandidate continuation内ですでに提案したtokenを条件にできない。Hydraは各headへ先行candidate tokenのembeddingを追加入力し、自然言語の強い隣接依存をdraft側へ戻す。

基本HydraだけでもMedusa比で最大1.11倍のthroughput改善、最適化版Hydra++はdeep MLP、base model分布へのteacher distillation、Hydra専用prefix-attention layerを組み合わせ、Vicuna 7B/13B/33Bのbatch=1でautoregressive比2.70/2.50/2.53倍、Medusa比1.27/1.27/1.31倍を達成する。重要なのはdraft計算自体はMedusaより重くなるが、平均受理長（average acceptance length）が伸びてbase modelの高価なforward回数を減らし、end-to-endで勝つ点である。

## 問題設定
自己回帰decodeは1 stepごとに大きなbase model weightを読み込む一方、batchが小さいと計算量が少なくmemory-bandwidth boundになりやすい。投機的復号は安いdraftが複数tokenを提案し、base modelがそれらを1回のforwardで並列検証することで、1回のweight read当たり複数tokenを確定させる。

Medusaは独立draft modelを別途保持せず、base model hidden state上の小型head群を使う。しかしfuture head `i` は
`p(x_{t+i}|x_{le t+i-1}) = f_i(h_{t-1})`
のように、実際には同candidate中の `x_t,...,x_{t+i-1}` を見ない。candidateの先頭を一つ外すと後続headも整合しにくく、深いtree branchほど受理率が落ちる。draftを高精度化してもhead overheadが大きすぎればspeculationの利得が消えるため、精度とhead costの両方を最適化する必要がある。

## 手法
### 1. sequentially-dependent Hydra head
Hydraの第 `i` headはbase modelの最終hidden state `h_{t-1}` に加え、確定済み最後のtoken `x_t` と、同じcandidate path上で先行Hydra headが提案した `hat{x}_{t+1},...,hat{x}_{t+i-1}` のinput embeddingを受け取る。
`p_draft(hat{x}_{t+i}) = f_{Hydra,i}(h_{t-1}, x_t, hat{x}_{t+1},...,hat{x}_{t+i-1})`
という形で、後ろのheadほど長いcandidate prefixへconditionする。

基本実装はそれらembeddingとhidden stateをfeature dimensionでconcatenateする1-hidden-layer MLP。candidate treeでは各branchが異なる先行token列を持つため、同じdepthでもbranchごとに異なるconditional distributionを出せる。Medusaのtree verificationやattention-mask機構はそのまま使え、draft head部分だけ置換できる。

### 2. Hydra++のteacher distillation
通常Medusa headはfine-tuning corpusのground-truth next tokenへcross entropyを掛ける。しかし投機的復号で重要なのは「datasetの正解」を当てることではなく、**そのbase modelが実際に選ぶtoken**を当てることである。

Hydra++ではbase LLMのnext-token distributionをteacherとして、draft head distributionとのcross entropyを学習する。design ablationではteacher lossだけを使う構成がvanilla Hydra比でVicuna-7B throughputを約1.04倍改善した。hidden embeddingへnoiseを加える案も試したが、noiseはacceptance lengthと速度を悪化させたため最終recipeには採用していない。

### 3. deep MLPとprefix attention
後続headほど入力feature数が増え、単純1-layer MLPではcontext表現能力が不足する。Hydra++はMLP depthを増やす。

さらにbase model最後のhidden stateだけではdraftに必要な全prefix情報が十分集約されていない可能性があるため、base LLMとは別に1層のHydra専用Transformer decoder layerを追加する。これは既生成prefixへattentionし、全Hydra headが共有するcontext representationを1 decode stepに一度だけ作る。各future positionでfull attentionを繰り返すEAGLE型より、attention costをstep当たり1回に抑え、残りをMLP headで処理する。PrefixMLP ablationでは平均受理長1.12倍、throughput約1.08倍改善した。

### 4. decoding tree探索
draft headはtop candidatesを分岐させたtreeを作り、base modelがtree tokenを1 sequenceへpackingし、特殊attention maskで各nodeが祖先だけを見るようにして1 forwardで検証する。

treeを大きくすればbase modelが検証する候補数が増え、accept可能pathを拾いやすいが、verification computeも増える。著者らはdraftのempirical token probabilitiesから各nodeのexpected accepted lengthへの寄与を見積もり、tree sizeごとに期待値最大のtopologyを作った後、実測throughputで最良sizeを選ぶ。batch sizeが増えるほどbase verificationがcompute-boundになりやすいため、最適treeは小さくなる。

## 評価条件
base modelはVicuna-7B、13B、33B。base weightはfreezeし、ShareGPT系dataでdraft headを学習する。主benchmarkはMT-Bench、追加でSpecBenchのmulti-turn chat、translation、summarization、QA、math、RAGを用いる。

hardwareは単一NVIDIA A100、主要結果はbatch size 1。batched inferenceではVicuna-7Bでbatch 1/2/4/8を比較する。greedy acceptanceに加え、非greedy生成ではMedusa由来のtypical acceptanceを使い、MT-Bench Writing/RoleplayをLLM-as-a-judgeで品質確認する。

比較はautoregressive、Medusa、basic Hydra、Hydra++。tree topologyは各method/batchごとに探索し、固定treeが一方に不利にならないようにする。

## 主要結果
### batch=1 throughput
basic Hydraはautoregressive比で7B 2.36倍、13B 2.17倍、33B 2.15倍。Medusa比では1.11/1.10/1.11倍で、**逐次依存化だけ**で一貫して受理長とthroughputが増える。

Hydra++はautoregressive比7B 2.70倍、13B 2.50倍、33B 2.53倍。Medusa比1.27/1.27/1.31倍。headを重くしても受理token増加の方が大きいためend-to-endでさらに速い。

### batch size感度
7Bでbatch 1→8へ増やすとHydra++のautoregressive比speedupは2.70倍から1.63倍へ低下する。batchが大きいほどbase model forward自体のGPU利用率が上がり、speculative verificationの余分なtoken計算が「ほぼ無料」ではなくなるためである。それでも評価したbatch 2/4/8でMedusaと通常decodeを上回る。

### draft overhead
8B scale相当のprofilingではMedusa head 1〜4は各約0.3ms。Hydra++はprefix attention約1.2ms、各head約0.6/1.4/1.2/0.7msと明確に重い。base model 1 decode stepは約28msであり、draft overhead増加がbase call削減で回収される構造になっている。

この結果は「draftは最小であるほどよい」ではなく、base modelとの一致率を上げるために数ms余計に使っても、28ms級のbase stepを減らせれば得になることを示す。

### 非greedy品質
typical acceptanceではthresholdを変えると受理長と多様性のtrade-offが生じる。Medusaとbasic Hydraは試した設定でbase random samplingと同等judge品質に届かなかったが、Hydra++はposterior threshold `ε=0.15` でbase model直接samplingと同等のgeneration qualityを得つつ、高いacceptance lengthを維持した。

### SpecBench
Vicuna-7B/8B相当batch=1でautoregressive比speedupは、MedusaがMT Chat 2.00、Translation 1.68、Summary 1.59、QA 1.67、Math 1.98、RAG 1.54、平均1.75倍。Hydra++は2.52/2.02/1.89/2.08/2.59/1.87、平均2.17倍で、全categoryでMedusaを上回る。Hydra++/Medusaの平均相対改善は約1.24倍。

summarizationとRAGは両方式ともspeedupが小さく、task distributionによってdraft acceptanceが変わる負の条件も確認される。

## 既存研究との差
Medusaとの差はhead数やtree verificationではなく、draft factorizationから「future token同士は独立」という仮定を外したことにある。EAGLEも独立に同時期、sequentially dependent draftを導入するが、EAGLEはcandidate tokenごとにTransformer decoder blockでhidden-state estimateまで逐次生成する。論文内比較ではEAGLEの受理長はHydra++より長いものの、draft overheadも大きく、end-to-end throughputは同程度だった。

Hydra++はprefix全体を読むattention layerをstep当たり一度だけ共有し、その後はshallow MLP群でfuture positionsを出すことで、draft qualityとcostの中間点を狙う。

## 限界
base modelごとにdraft headを追加学習する必要があり、学習不要のdrop-in accelerationではない。tree topologyもmodel、hardware、batchごとに最適値が変わり、batchが大きくなるほどspeedupは縮む。

Hydra++はMedusaよりhead overheadが大きい。base modelが小さい、batchが大きい、あるいは高速kernelでbase decode costが下がる環境では、追加prefix attention/MLPを償却しにくくなる。summarization・RAGのようにacceptanceが低いtaskでは利得も小さい。

typical acceptanceはbase sampling distributionを厳密保存するrejection samplingとは異なる非distribution-preserving criterionであり、「judge品質が同等」は出力分布の数学的同一性を意味しない。厳密分布保存が必要な用途では別のaccept/reject方式と速度trade-offを評価する必要がある。
