# Comet: Fine-grained Computation-communication Overlapping for Mixture-of-Experts

> multi-GPU MoEで、他GPUから必要データが全部届くまで待たず、届いた小さな行列単位からエキスパート GEMMを開始してGPU間通信待ちを計算の裏へ隠すランタイム。

## 概要
Cometは、分散MoEでエキスパート dispatch/combineのall-to-all通信がGEMMを待たせる問題を、**通信完了をtensor全体で待たず、計算に必要な一部分が届いた時点からGEMMを始める**ことで隠すカーネル/ランタイムである。

モデル配置やエキスパート数は変えず、同じtensorを同じ精度で計算する。したがって量子化や枝刈りではなく、**GPU間通信とGEMMの実行順序を細かく組み替える無損失最適化**である。

従来もall-to-all通信とエキスパート計算をchunk単位で重ねる方法はあるが、chunkを小さくしすぎると各GEMMが小さくなりTensor Coreを十分使えず、逆にchunkを大きくすると次の計算を始めるまで通信完了を長く待つ。つまり粗いパイプラインには『通信を細かく隠したい』と『GEMMは大きく保ちたい』という衝突がある。CometはGEMM全体を小カーネルへ分断するのではなく、1つの大きな計算の内部でtileごとのデータ依存だけを細かく追跡し、このtrade-offを緩和する。

## 手法のあらまし

### 1. Tensor全体ではなく小さな行列単位で到着を待つ

通常はall-to-allが終わるまでエキスパート GEMMを開始しない。Cometは大きなGEMMを複数の小さな矩形領域へ分け、**その領域を計算するのに必要なトークンデータだけ届けば先に計算する**。

論文ではこの小さな領域を `tile`、必要データの到着条件を `tile-level dependency` と呼ぶ。

これにより、あるエキスパート向けデータがまだ届いていなくても、すでにデータが揃った別エキスパートや別領域の計算を進められる。

tileごとのready状態を使うことで、通信の最も遅い相手GPUを待つ全体barrierを避けられる。例えば8 GPU中7 GPUから必要トークンが届いていて1 GPUだけ遅れている場合、従来のall-to-all完了待ちではGEMM全体が停止するが、Cometでは到着済みトークンに対応するtileを先に処理する。遅れているtileだけを後へ回すため、networkのばらつきやエキスパートごとの不均衡があってもGPU演算器を動かし続けやすい。

### 2. 同じGPU上で通信担当とGEMM担当を同時に走らせる

Cometは1つのfusedカーネル内でGPU thread blockへ役割を分ける。

| GPU blockの役割 | 処理 |
|---|---|
| communication担当 | token dataを他GPUと送受信 |
| GEMM担当 | 到着済みdataのexpert行列計算 |
| reduction担当 | 複数expert結果のcombine処理 |

論文では `thread-block specialization` と呼ぶが、要点は**通信カーネルが終わってから計算カーネルを起動するのではなく、GPU内部で通信係と計算係を並行して動かす**ことである。

同一カーネル内へまとめることで、通信カーネルとGEMMカーネルの間に毎回global synchronizationを置く必要も減る。通信担当blockはremoteメモリへデータを送り、到着した領域の状態を更新する。GEMM担当blockはその状態を確認してreadyなtileだけを計算し、combine段階ではreduction担当が到着済みエキスパート結果を順次まとめる。処理段階をカーネル境界ではなくデータ依存で接続することが、細粒度重畳の実装上の中心になる。

### 3. 必要な小単位だけGPU間で直接送受信する

実装ではNVSHMEMを使い、GPU間のメモリへ直接put/getする。

大きなall-to-all全体の終了を待つのではなく、**今計算したいtileに必要なデータだけ到着したかを確認して進める**ために使う。

NVSHMEMはNVIDIA GPU間で細かいremoteメモリ accessを扱う通信libraryであり、本手法の実装上の前提になる。

### 4. expertごとにtoken数が違ってもまとめてGEMMする

MoEではエキスパートごとのトークン数が揃わないため、行列サイズもエキスパートごとに異なる。

Cometは複数の異なるGEMMを一括してGPUへ渡せるGroupGEMMを使い、**小さいエキスパート計算を1個ずつ別カーネルで起動する無駄を減らす**。

### 5. 通信担当と計算担当へGPU資源を何割ずつ割くか調整する

通信が重いshapeとGEMMが重いshapeでは、GPU resourceの最適配分が違う。

Cometはmodel shape、トークン数、エキスパート数、top-kに応じて、通信用blockと計算用blockの比率を事前測定から選ぶ。

この比率が重要なのは、両者が同じGPUのSMやメモリ resourceを取り合うためである。通信担当を増やしすぎるとデータは早く届いてもGEMM blockが不足し、計算担当を増やしすぎるとGEMM側が通信待ちになる。通信量が大きいshapeではcommunication側へ、行列演算が支配的なshapeではGEMM側へ資源を寄せ、両方の完了時間が近づくようにする。したがってCometの重畳は単に同時実行を許可するだけでなく、同時実行時のresource competitionまで含めて調整する。

したがって、どのhardware・shapeでも同じ固定設定を使えるカーネルではない。

また通信路がNVLink中心かPCIe bridgeを跨ぐかでもcommunication側の必要資源が変わるため、別clusterへ移植するときは同じmodelでもprofileを取り直す必要がある。

## 評価

### まず見るところ
- **結論:** all-to-allを小さなGEMM単位と重ねると、分散MoEの通信待ちをかなり隠せる。
- **速度:** 8×H800でエンドツーエンド平均約1.7倍、単一層では最大約2倍級。
- **品質:** 実行順だけを変える無損失 system optimization。
- **対象:** NVLink/NVSHMEMを使うmulti-GPU環境。CPU/SSDオフロードではない。
- **注意点:** 単一GPUにはall-to-allがないため、同じ利得は出ない。

### 制約

- NVIDIA GPU / NVSHMEM依存。
- 行列shapeが大きく変わると通信/計算担当の比率を再測定する必要がある。
- 性能の違うGPUを混ぜる場合は、GPU間の処理速度差を別途扱う必要がある。
- CPU、NVMe、consumer VRAM不足は対象外。

## 日本語での要点整理

分散した専門家モデルでは、全ての入力が全ての演算装置へ届くまで計算を始めないと、通信の遅い相手に全体が引きずられる。この方式は、計算領域を小さなタイルへ分け、各タイルに必要な入力が届いた時点で行列計算を始める。通信を担当するまとまりと計算を担当するまとまりを同じ実行単位の中で動かすため、通信の完了を待つ空白を減らせる。結果をまとめる処理も到着した部分から進めるので、一部の遅延が全体の停止になりにくい。

ただし、区切りを細かくするだけでは行列計算が小さくなり、演算器を十分に使えない。通信量と計算量、入力の偏り、接続方式に応じて、通信と計算へ割り当てる演算資源の比率を調整する必要がある。評価は同じ計算結果を保ったまま待ち時間を隠す実装上の工夫であり、モデルを小さくしたり精度を落としたりする方法ではない。そのため、単一の演算装置や通信を必要としない構成では、同じ効果は期待できない。

つまり、全体の到着を待つ同期点を、各小領域の到着条件へ置き換えることが中心である。早く届いた入力に対応する計算を先に進め、遅い入力に対応する部分だけを後へ残すことで、通信のばらつきを計算の待ち時間へ変換する。実装を別の接続方式へ移す場合は、通信担当と計算担当の資源配分を測り直し、入力の偏りが大きい場合にも計算のまとまりを保てるか確認する必要がある。
