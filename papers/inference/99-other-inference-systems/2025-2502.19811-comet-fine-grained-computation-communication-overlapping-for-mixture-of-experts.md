# Comet: Fine-grained Computation-communication Overlapping for Mixture-of-Experts

> multi-GPU MoEで、他GPUから必要dataが全部届くまで待たず、届いた小さな行列単位からexpert GEMMを開始してGPU間通信待ちを計算の裏へ隠すruntime。

## 概要
Cometは、分散MoEでexpert dispatch/combineのall-to-all通信がGEMMを待たせる問題を、**通信完了をtensor全体で待たず、計算に必要な一部分が届いた時点からGEMMを始める**ことで隠すkernel/runtimeである。

モデル配置やexpert数は変えず、同じtensorを同じ精度で計算する。したがって量子化やpruningではなく、**GPU間通信とGEMMの実行順序を細かく組み替えるlossless最適化**である。

## 手法のあらまし

### 1. Tensor全体ではなく小さな行列単位で到着を待つ

通常はall-to-allが終わるまでexpert GEMMを開始しない。Cometは大きなGEMMを複数の小さな矩形領域へ分け、**その領域を計算するのに必要なtoken dataだけ届けば先に計算する**。

論文ではこの小さな領域を `tile`、必要dataの到着条件を `tile-level dependency` と呼ぶ。

これにより、あるexpert向けdataがまだ届いていなくても、すでにdataが揃った別expertや別領域の計算を進められる。

### 2. 同じGPU上で通信担当とGEMM担当を同時に走らせる

Cometは1つのfused kernel内でGPU thread blockへ役割を分ける。

| GPU blockの役割 | 処理 |
|---|---|
| communication担当 | token dataを他GPUと送受信 |
| GEMM担当 | 到着済みdataのexpert行列計算 |
| reduction担当 | 複数expert結果のcombine処理 |

論文では `thread-block specialization` と呼ぶが、要点は**通信kernelが終わってから計算kernelを起動するのではなく、GPU内部で通信係と計算係を並行して動かす**ことである。

### 3. 必要な小単位だけGPU間で直接送受信する

実装ではNVSHMEMを使い、GPU間のmemoryへ直接put/getする。

大きなall-to-all全体の終了を待つのではなく、**今計算したいtileに必要なdataだけ到着したかを確認して進める**ために使う。

NVSHMEMはNVIDIA GPU間で細かいremote memory accessを扱う通信libraryであり、本手法の実装上の前提になる。

### 4. expertごとにtoken数が違ってもまとめてGEMMする

MoEではexpertごとのtoken数が揃わないため、行列サイズもexpertごとに異なる。

Cometは複数の異なるGEMMを一括してGPUへ渡せるGroupGEMMを使い、**小さいexpert計算を1個ずつ別kernelで起動する無駄を減らす**。

### 5. 通信担当と計算担当へGPU資源を何割ずつ割くか調整する

通信が重いshapeとGEMMが重いshapeでは、GPU resourceの最適配分が違う。

Cometはmodel shape、token数、expert数、top-kに応じて、通信用blockと計算用blockの比率を事前測定から選ぶ。

したがって、どのhardware・shapeでも同じ固定設定を使えるkernelではない。

## 評価

### まず見るところ
- **結論:** all-to-allを小さなGEMM単位と重ねると、分散MoEの通信待ちをかなり隠せる。
- **速度:** 8×H800でend-to-end平均約1.7倍、単一layerでは最大約2倍級。
- **品質:** 実行順だけを変えるlossless system optimization。
- **対象:** NVLink/NVSHMEMを使うmulti-GPU環境。CPU/SSD offloadではない。
- **注意点:** 単一GPUにはall-to-allがないため、同じ利得は出ない。

### 実験環境

| 項目 | 条件 |
|---|---|
| GPU | 8×NVIDIA H800 80GB |
| Interconnect | NVLink |
| CUDA / NVSHMEM | CUDA 12.3 / NVSHMEM 2.11 |
| Framework | PyTorch 2.4 / Megatron |
| Model | Mixtral 8×7B、Qwen2-MoE、Phi-3.5-MoE |

### End-to-end

| 指標 | 結果 |
|---|---:|
| latency削減 | 約31.8〜44.4% |
| 平均speedup | 1.71倍 |
| 単一layer最大 | 1.96倍 |

### Shapeを変えた単一layer評価

| 条件 | Speedup |
|---|---:|
| token数 / expert構成変更 | 1.28〜2.37倍 |
| expert数 / top-k変更 | 1.16〜1.83倍 |
| PCIe bridgeを含む構成 | 1.19〜1.46倍 |

### 通信待ちをどこまで計算で隠せたか

| 実装 | 通信時間のうち計算と重ねられた割合 |
|---|---:|
| Comet | 最大86.5% |
| FasterMoE | 29.2% |
| Tutel | 68.6% |

### 追加memory

M=4096ではMixtral/Phiで約32MB、Qwenで約16MB。M=8192では概ね倍になる。追加memoryは比較的小さい。

### 制約

- NVIDIA GPU / NVSHMEM依存。
- 行列shapeが大きく変わると通信/計算担当の比率を再測定する必要がある。
- 性能の違うGPUを混ぜる場合は、GPU間の処理速度差を別途扱う必要がある。
- CPU、NVMe、consumer VRAM不足は対象外。
