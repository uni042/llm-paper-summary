# RadixMLP — Intra-batch Deduplication for Causal Transformers

## 一文要約

同じprefixを含む複数sequenceを1つのbatchで処理するとき、共有prefix部分のMLP・LayerNorm・線形射影をsequenceごとに繰り返さず、同じtoken位置の計算を1回だけ行って結果を各sequenceへ戻すことでprefill計算を削減する。

## 問題設定

system prompt、few-shot例、rerankingの共通queryなど、1つのbatch内に同じprefixを持つsequenceが複数ある場合、通常のTransformer実装は各sequenceを独立に処理する。そのため、同じcausal historyを持つprefix tokenについて、MLP、LayerNorm、embedding、線形射影のような**そのtoken位置だけで完結する演算**までsequence数ぶん繰り返される。

KV cache / prefix cacheは過去のattention stateをrequest間で再利用できるが、RadixMLPが狙うのは少し違う。**1回のforward pass内に同じprefixが複数コピーされているとき、attention以外の重複計算そのものを消す**。

requestを跨いで長期間cacheを保持する必要がないため、batch inferenceやrerankingのように各batchを独立に処理するworkloadでも使える。

## 手法

### 1. Prefixを木構造へ整理して同じ部分を1つにまとめる

CPU側でbatch中のsequenceを、先頭から同じtoken列を共有するものが同じ枝を通る木構造へ整理する。

論文ではこの構造を `prefix trie` と呼ぶ。

元のbatchに合計 `N` tokenがあり、共有prefixを1コピーへまとめた後のtoken数を `N'` とすると、位置ごとに独立な演算は `N` tokenではなく `N'` tokenだけに実行できる。

### 2. 共有tokenだけの小さい表現と、元のbatch表現を演算ごとに切り替える

MLP、LayerNorm、embedding、線形射影などは、共有prefixの重複を除いた `N'` token表現で計算する。

一方self-attentionはsequence内の他tokenとの関係を計算するため、各sequenceが独立した通常のlayoutへ戻して処理する。

各layerでは概念的に、

1. 元batchから重複tokenを除いた小さい配列を作る
2. MLP等をunique tokenだけに実行する
3. 計算結果を元の各sequence位置へコピーして戻す
4. attentionを通常どおり実行する

という流れになる。

論文では1と3を `gather / scatter` と呼ぶ。つまり、**必要な位置だけ集めて計算し、その結果を元の位置へ配り直す処理**である。

位置独立部分の主要計算量は概ね `O(N d²)` から `O(N' d²)` へ減る。tokenを集めたり戻したりする処理は追加されるが、model dimensionが大きくMLP等の計算が重いほど削減効果が上回りやすい。

### 3. 次batchの重複検出を現在batchのGPU計算中に進める

次batchのprefix木と、どのtokenをまとめてどこへ戻すかのindexをCPUで先に準備し、現在batchのGPU計算と重ねる。

これにより、**重複を探すCPU処理が次batch開始を直接待たせにくい**構成にする。

### 4. Requestを跨ぐpersistent cacheではない

SGLangのRadixAttentionのように過去requestのKV cacheを保持して再利用する方式とは異なり、RadixMLPは**今処理している1 batch内の重複だけを利用する**。

長期間のcache allocation・eviction・整合性管理が不要な代わりに、batch内でprefixが共有されていなければ利得は小さい。

## 評価条件

論文は主にQwen3 0.6B / 4B / 8Bを用い、NVIDIA H100上で評価する。

- synthetic workloadではbatch size、shared-prefix長、suffix長を変化
- 実workloadではMS MARCO v1.1のrerankingを使用
- `text-embeddings-inference` への統合を含むend-to-end servingを評価
- 通常実装やvLLM等と比較

## 主要結果

- MS MARCO v1.1 rerankingではQwen3系列で**1.44–1.59×**のend-to-end speedup。
- 長いshared prefixを持つsynthetic workloadでは最大**約5×**のspeedup。
- 効果はshared prefixが長く、batch内の重複率が高く、modelが大きくMLP等の位置独立計算の比率が高いほど大きくなる。

## 既存研究との差

### SGLang / RadixAttention

SGLangはrequestのprefixを木構造で管理し、request間で同じprefix KVを再利用してprefillの再計算を減らす。

RadixMLPは似たprefix木を使うが、**過去requestのcache再利用ではなく、同一batch内でMLP等を重複計算しないこと**が中心である。

### Hydragen

Hydragenはshared prefixに対する複数sequenceのqueryをまとめ、同じprefix KVを何度もHBMから読む問題を減らしてattentionを高速化する。

RadixMLPは逆に、attentionではなく**MLP・LayerNorm・projectionなど、そのtoken位置だけで完結する計算**を重複排除する。両者はshared prefixの別々の計算部分を狙うため補完的である。

### vLLM / PagedAttention

vLLMはKV cacheを小blockへ分けて必要分だけ割り当て、細切れの未使用memoryが増える問題を減らし、より多くのrequestをcontinuous batchへ載せる。

RadixMLPはKV memory managementではなく、すでに同一batchに存在する重複prefixの算術演算を減らす。

## 実装上の含意

shared prefix最適化は「KV cacheを1コピーにする」だけでは完結しない。Transformerには、

- attentionで共有KVを読む計算
- MLP・projection・normalization等の位置独立計算

という別々の重複がある。

SGLang系のprefix cache、Hydragen系のshared-prefix attention、RadixMLP系の位置独立計算の重複排除はそれぞれ別の部分を削減する。reranking、同じdocumentへ多数queryを当てる処理、同じsystem promptを含むbatchなどでは、schedulerが同じprefixを持つrequestをまとめることと、forward側で重複計算を実際に消すことを組み合わせる余地がある。

## 限界

- batch内に十分なshared prefixがなければ、tokenを集めて戻す追加処理に対して利得が小さい。
- attention自体の重複計算は削減しない。
- prefix構造を認識できるbatch layoutとforward実装への変更が必要。
- 主要評価はQwen3系列と特定のreranking / synthetic workloadであり、一般的なautoregressive decode servingで同じ倍率が得られるとは限らない。

## 引用関係

本研究は、prefix構造を扱うSGLang / RadixAttention、shared-prefix attentionを高速化するHydragen、KV memory managementのvLLM / PagedAttentionなどを主要な関連研究として位置づける。特にHydragenとは、同じshared-prefix redundancyをattention側と位置独立layer側から別々に削る関係にある。
