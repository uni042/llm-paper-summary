# RadixMLP — Intra-batch Deduplication for Causal Transformers

## 一文要約

同じプレフィックスを含む複数系列を1つのバッチで処理するとき、共有プレフィックス部分のMLP・LayerNorm・線形射影を系列ごとに繰り返さず、同じトークン位置の計算を1回だけ行って結果を各系列へ戻すことでプリフィル計算を削減する。

## 問題設定

システム プロンプト、few-shot例、再順位付けの共通クエリなど、1つのバッチ内に同じプレフィックスを持つ系列が複数ある場合、通常のTransformer実装は各系列を独立に処理する。そのため、同じ因果 履歴を持つプレフィックス トークンについて、MLP、LayerNorm、埋め込み、線形射影のような**そのトークン位置だけで完結する演算**まで系列数ぶん繰り返される。

KV キャッシュ / プレフィックス キャッシュは過去の注意状態をリクエスト間で再利用できるが、RadixMLPが狙うのは少し違う。**1回の順伝播過程内に同じプレフィックスが複数コピーされているとき、注意以外の重複計算そのものを消す**。つまり、過去のリクエストをまたぐ長期保存ではなく、同じバッチに並ぶ系列の共有部分だけを対象にする。これにより、キャッシュ管理を大きく変えずに、位置ごとに独立した計算をまとめて削減できる。

リクエストを跨いで長期間キャッシュを保持する必要がないため、バッチ 推論や再順位付けのように各バッチを独立に処理するワークロードでも使える。

## 手法

### 1. Prefixを木構造へ整理して同じ部分を1つにまとめる

CPU側でバッチ中の系列を、先頭から同じトークン列を共有するものが同じ枝を通る木構造へ整理する。

論文ではこの構造を `prefix trie` と呼ぶ。

元のバッチに合計 `N` トークンがあり、共有プレフィックスを1コピーへまとめた後のトークン数を `N'` とすると、位置ごとに独立な演算は `N` トークンではなく `N'` トークンだけに実行できる。

### 2. 共有tokenだけの小さい表現と、元のbatch表現を演算ごとに切り替える

MLP、LayerNorm、埋め込み、線形射影などは、共有プレフィックスの重複を除いた `N'` トークン表現で計算する。

一方自己注意は系列内の他トークンとの関係を計算するため、各系列が独立した通常の配置へ戻して処理する。

各層では概念的に、

1. 元バッチから重複トークンを除いた小さい配列を作る
2. MLP等をunique トークンだけに実行する
3. 計算結果を元の各系列位置へコピーして戻す
4. 注意を通常どおり実行する

という流れになる。

論文では1と3を `gather / scatter` と呼ぶ。つまり、**必要な位置だけ集めて計算し、その結果を元の位置へ配り直す処理**である。

位置独立部分の主要計算量は概ね `O(N d²)` から `O(N' d²)` へ減る。トークンを集めたり戻したりする処理は追加されるが、モデル次元が大きくMLP等の計算が重いほど削減効果が上回りやすい。

この重複排除で結果が変わらないのは、共有プレフィックス内の同じトークン位置が同じ入力表現と同じ因果履歴を持つためである。MLP・LayerNorm・線形射影のような位置ごとの演算は、その入力が同一なら出力も同一なので1回だけ計算して複数系列へ複製できる。一方、suffixへ分岐した後の位置や、系列内の他トークンとの関係を使うattentionは同じ扱いにできない。この境界を守ることで近似を入れずに計算だけを減らす。

### 3. 次batchの重複検出を現在batchのGPU計算中に進める

次バッチのプレフィックス木と、どのトークンをまとめてどこへ戻すかの索引をCPUで先に準備し、現在バッチのGPU計算と重ねる。

これにより、**重複を探すCPU処理が次バッチ開始を直接待たせにくい**構成にする。

### 4. Requestを跨ぐpersistent cacheではない

SGLangのRadixAttentionのように過去リクエストのKV キャッシュを保持して再利用する方式とは異なり、RadixMLPは**今処理している1 バッチ内の重複だけを利用する**。

長期間のキャッシュ 割り当て・追い出し・整合性管理が不要な代わりに、バッチ内でプレフィックスが共有されていなければ利得は小さい。

## 評価条件

論文は主にQwen3 0.6B / 4B / 8Bを用い、NVIDIA H100上で評価する。

- 合成 ワークロードではバッチ size、共有プレフィックス長、suffix長を変化
- 実ワークロードではMS MARCO v1.1の再順位付けを使用
- `text-embeddings-inference` への統合を含むエンドツーエンド 推論提供を評価
- 通常実装やvLLM等と比較

## 主要結果

- MS MARCO v1.1 再順位付けではQwen3系列で**1.44–1.59×**のエンドツーエンド 高速化倍率。
- 長い共有 プレフィックスを持つ合成 ワークロードでは最大**約5×**の高速化倍率。
- 効果は共有 プレフィックスが長く、バッチ内の重複率が高く、モデルが大きくMLP等の位置独立計算の比率が高いほど大きくなる。

## 既存研究との差

### SGLang / RadixAttention

SGLangはリクエストのプレフィックスを木構造で管理し、リクエスト間で同じプレフィックス KVを再利用してプリフィルの再計算を減らす。

RadixMLPは似たプレフィックス木を使うが、**過去リクエストのキャッシュ再利用ではなく、同一バッチ内でMLP等を重複計算しないこと**が中心である。

### Hydragen

Hydragenは共有 プレフィックスに対する複数系列のクエリをまとめ、同じプレフィックス KVを何度もHBMから読む問題を減らして注意を高速化する。

RadixMLPは逆に、注意ではなく**MLP・LayerNorm・射影など、そのトークン位置だけで完結する計算**を重複排除する。両者は共有 プレフィックスの別々の計算部分を狙うため補完的である。

### vLLM / PagedAttention

vLLMはKVキャッシュを小ブロックへ分けて必要分だけ割り当て、細切れの未使用メモリが増える問題を減らし、より多くのリクエストを連続バッチへ載せる。

RadixMLPはKV メモリ 管理ではなく、すでに同一バッチに存在する重複プレフィックスの算術演算を減らす。

## 実装上の含意

共有 プレフィックス最適化は「KV キャッシュを1コピーにする」だけでは完結しない。Transformerには、

- 注意で共有KVを読む計算
- MLP・射影・正規化等の位置独立計算

という別々の重複がある。

SGLang系のプレフィックスキャッシュ、Hydragen系の共有プレフィックス注意、RadixMLP系の位置独立計算の重複排除はそれぞれ別の部分を削減する。再順位付け、同じ文書へ多数のクエリを当てる処理、同じシステムプロンプトを含むバッチなどでは、スケジューラが同じプレフィックスを持つリクエストをまとめることと、順伝播側で重複計算を実際に消すことを組み合わせる余地がある。

## 限界

- バッチ内に十分な共有 プレフィックスがなければ、トークンを集めて戻す追加処理に対して利得が小さい。
- 注意自体の重複計算は削減しない。
- プレフィックス構造を認識できるバッチ 配置と順伝播実装への変更が必要。
- 主要評価はQwen3系列と特定の再順位付け / 合成 ワークロードであり、一般的な自己回帰 デコード 推論提供で同じ倍率が得られるとは限らない。

## 引用関係

本研究は、プレフィックス構造を扱うSGLang / RadixAttention、共有プレフィックス 注意を高速化するHydragen、KV メモリ 管理のvLLM / PagedAttentionなどを主要な関連研究として位置づける。特にHydragenとは、同じ共有プレフィックス 冗長性を注意側と位置独立層側から別々に削る関係にある。
