# FastCoder：コードの局所性を使う検索ベース投機的復号

## 概要

リポジトリ内のコード生成は、一般的な自然言語生成と異なり、同じファイルやプロジェクトで定義された識別子・関数・定型コードを繰り返す。検索ベースの投機的復号は、過去のコードから複数トークンのドラフトを取得し、大きなターゲットLLMで一括検証して自己回帰復号を短縮する。しかし既存方式RESTは汎用コードの固定データストアを用いるため、リポジトリ固有の命名規則を拾いにくく、検索が成功しない位置でも毎回CPU検索を行う。

FastCoderは、共通コードと対象リポジトリの二つのデータストア、検索すべき位置の選択、検証済みコードとモデル出力のキャッシュ、重み付きTrieによる複数ドラフトの統合を組み合わせる。DeepSeek-Coder-1.3BのRepoEvalで19.91ms/tokenを7.88ms/tokenへ短縮し、2.53倍の速度を得た。4モデルのRepoEvalで2.38～2.53倍、DevEvalで2.15～2.30倍の高速化を示す。greedy復号でターゲットLLMの出力と一致するトークンだけを採用するため、同じ入力に対する出力を変更しないことが設計上の要件である。

## 問題設定

従来の検索ドラフトは、コード生成の各時点の末尾コンテキストを固定データストアで照合し、見つかった後続トークンを候補として提示する。しかし新しいプロジェクトの識別子は汎用データストアに存在しない。コードでは行頭の空白・インデントの後に現れる最初の非空白トークンが文の方向を決めるため、ここで検索をしてもヒットしにくい。一方、直前に使った変数名やコード片は同じファイルの後続で再利用されやすい。

論文はDevEvalから200サンプルを取り、DeepSeek-Coder-6.7Bでトークン位置別の検索成功率を分析した。行の2番目付近、すなわち最初の非空白トークンで成功率が低いことを確認し、検索を常に実行するのではなく、成功しやすい場所にCPU処理を配分する方針を立てた。速度の制約はGPUの検証処理だけではなく、検索用CPUとデータストアの容量にもある。

## 手法

### 1. 共通・リポジトリ固有の二系統データストア

共通データストア D_c はThe StackのPythonコードから構築し、プロジェクトに依存しない構文や定型処理の後続候補を保持する。リポジトリ固有データストア D_r は対象プロジェクトの既存ファイルから構築し、そのプロジェクトで実際に使われる識別子、関数、スタイルを反映する。各エントリは「直前のコード文脈」と「それに続くトークン列」の対である。コードを生成すべき穴の正解部分は D_r に入れない。

新しいコードを生成する際、現在のコンテキストの末尾をキーに D_c と D_r を並列検索する。リポジトリの存在しない単独関数生成では D_r を省略できる。論文の実装では D_c は約0.9GBで構築約9分、D_r は対象に応じ60KB～289MBで平均約10秒。RESTの比較データストアは約8.7GBであり、共通知識を単純に大量に保持することが必ずしも高速化へつながらない。

### 2. 失敗しやすい位置では検索しない

検索に失敗するコンテキストをmissing table Mに記録し、同じ位置での繰り返し検索を避ける。特に行頭の非空白トークンに対応する位置では、確率 p でのみ外部検索を行い、残りは通常のLLM生成を続ける。これにより検索ヒット率が低い位置のCPU検索・データストアアクセスを削減する。検索しない場合はトークン生成を省略するのではなく、ターゲットLLMが通常どおり次トークンを決める。

論文Algorithm 1では、まずキャッシュが一定規模以上ならキャッシュを検索する。キャッシュで十分な候補が見つからない場合に、missing tableと位置依存の検索確率を参照し、必要なときだけ D_c・D_r を並列検索する。検索結果が空ならMへ登録し、ヒットしたらキャッシュを更新する。実験ではキャッシュ有効化閾値 l=50、検索確率 p=0.5を採用し、これらの値を0.1～0.9、10～100の範囲で検討した。

### 3. 検証済み継続とLLM出力のキャッシュ

汎用データストアに同じ文脈があっても、異なるLLMは異なる続き方を好む。そこでFastCoderは、取得したドラフトのうちターゲットLLMが検証で受理した部分を、元の文脈と連結してキャッシュする。加えて、ターゲットLLMが実際に生成したコードも一定間隔でキャッシュへ入れる。実験では生成出力を20トークンごとに切り出して登録する。

これにより、同じファイルで再登場する変数名や関数呼出しを、リポジトリ固有の静的知識だけでなく現在のモデルが選んだ表現から再利用できる。キャッシュは外部検索を減らすだけでなく、ターゲットLLMの出力傾向に近い候補を増やし、検証で一度に受理されるトークン数を伸ばす。ただし、生成途中のキャッシュを維持するCPUメモリと検索・挿入処理は必要である。

### 4. 重み付きTrieとtree attentionによる一括検証

D_c・D_r・キャッシュから取得した複数の後続候補をTrieに統合し、同じ接頭辞を共有する分岐の重複をなくす。候補の重みにはリポジトリ固有知識と共通知識の寄与を調整する係数α、βを使い、実験の標準値はα=β=1である。選択した上位候補の木構造をターゲットLLMに一括入力し、各ノードが自分の祖先ノードだけを参照するtree attentionマスクを適用する。別の候補枝のトークンを誤って参照しないよう、位置インデックスも調整する。

検証時にはターゲットLLMが通常のgreedy復号で選ぶトークンと一致する候補だけを採用する。候補が途中で不一致ならその先は受理せず、ターゲットLLMの決定から再開する。したがって検索結果に誤ったコードが含まれていても、そのまま最終出力に採用する方式ではない。標準設定では検索用コンテキスト末尾最大16トークン、Trie内のドラフト最大64トークンを扱う。ドラフトモデルを別途GPUへ載せる必要はないが、tree attentionを扱える実装が前提となる。

## 評価条件

| 項目 | 一次論文の設定 |
|---|---|
| ターゲットモデル | DeepSeek-Coder-1.3B/6.7B、CodeLlama-7B/13B |
| タスク | リポジトリ内のDevEval・RepoEval、単独関数のHumanEval |
| 生成条件 | greedy復号、最大入力2,000トークン、最大生成512トークン、バッチ1 |
| GPU/CPU | 1.3B/6.7B/7BはRTX 4090＋28 CPU cores。13BはRTX A6000＋12 cores |
| 指標 | ms/token、自己回帰比速度、1回の検証で受理される平均トークン数、Pass@1またはEdit Similarity |
| 比較 | 自己回帰、Self-speculative、Ouroboros、REST |
| 検索データ | FastCoderの共通知識0.9GB＋リポジトリ別60KB～289MB、RESTの比較データストア約8.7GB |

DevEvalとRepoEvalでは同じファイルの前方コードをプロンプトへ付与する。RepoEvalの正解コードはリポジトリ固有データストアから除外しており、単純な正解リークを避ける。ただしThe Stackの収集期間とRepoEvalの対象リポジトリには時間的重複の可能性があり、著者らも残余のリーク可能性を否定していない。表の速度はモデルごとにGPU/CPU構成が異なるため、13Bと7Bのms/token差をモデルサイズだけの効果として扱えない。

## 評価結果

### リポジトリ内コード生成の復号速度

| DevEval | 自己回帰 ms/token | REST ms/token | FastCoder ms/token | FastCoder速度比 |
|---|---:|---:|---:|---:|
| DeepSeek-Coder-1.3B | 20.00 | 12.10 | 8.71 | 2.30倍 |
| DeepSeek-Coder-6.7B | 26.15 | 15.28 | 11.69 | 2.24倍 |
| CodeLlama-7B | 26.29 | 15.57 | 12.17 | 2.16倍 |
| CodeLlama-13B | 46.35 | 43.38 | 21.56 | 2.15倍 |

| RepoEval | 自己回帰 ms/token | REST ms/token | FastCoder ms/token | FastCoder速度比 |
|---|---:|---:|---:|---:|
| DeepSeek-Coder-1.3B | 19.91 | 12.09 | 7.88 | 2.53倍 |
| DeepSeek-Coder-6.7B | 25.75 | 15.46 | 10.83 | 2.38倍 |
| CodeLlama-7B | 26.21 | 15.43 | 10.80 | 2.43倍 |
| CodeLlama-13B | 47.86 | 44.59 | 19.02 | 2.52倍 |

論文Table I。DeepSeek-Coder-1.3BのRepoEvalで2.53倍が最大値だが、全モデル・全データセットで2.53倍ではない。RESTはCodeLlama-13BでRepoEval 1.04倍、DevEval 1.07倍にとどまり、CPU検索と大きなデータストアが利得を打ち消す可能性を示す。OuroborosはCodeLlama-7BのRepoEvalで自己回帰より遅い0.79倍、DevEvalでも0.90倍であり、ドラフトモデル選択が難しい。FastCoderのPass@1・Edit Similarityは同じターゲットLLMのgreedy自己回帰出力と一致する。

### どの構成要素が効いているか

| DeepSeek-Coder-6.7B・DevEval | 平均受理長 | ms/token | 自己回帰比速度 |
|---|---:|---:|---:|
| REST相当基準 | 1.89 | 15.86 | 1.65倍 |
| 二系統データストアのみ | 2.28 | 14.82 | 1.76倍 |
| 検索位置制御のみ | 1.89 | 15.41 | 1.70倍 |
| キャッシュのみ | 2.47 | 14.13 | 1.85倍 |
| データストア＋キャッシュ | 2.85 | 11.94 | 2.19倍 |
| FastCoder全機構 | 2.85 | 11.69 | 2.24倍 |

Table IIでは、検索位置制御のみでは平均受理長は1.89から変わらないが、検索費用を減らすことでms/tokenが改善する。一方、キャッシュは受理長を2.47へ伸ばし、複数ドラフトの検証効率も改善する。データストア＋キャッシュで受理長2.85まで達し、検索位置制御を加えると受理長は同じでも11.94から11.69ms/tokenへ改善する。これは三要素の作用が異なることを示す。

RepoEvalのDeepSeek-Coder-6.7Bでは、RESTの平均受理長2.08に対しFastCoderは3.05、CodeLlama-7Bでは2.07に対し3.06だった（Table IV）。受理長の改善が速度向上に結び付く一方、CPU負荷も無視できない。Table VではGPU VRAMはいずれも21GB、CPU使用率は自己回帰114%、REST335%、FastCoder128%、CPUメモリは自己回帰1.0GB、REST32.6GB、FastCoder2.8GB。FastCoderは別のGPUドラフトを追加しないが、CPUメモリは自己回帰より1.8GB増える。

### 既存のコード品質改善方式との統合

RepoCoderにFastCoderを組み合わせると、論文Table IIIで総処理時間11,823.05秒から4,408.88秒へ短縮し、2.68倍となる。RLCoderでは5,623.61秒から2,112.89秒へ短縮し、2.66倍となる。Edit Similarityはそれぞれ30.35、38.28のままで、検索でプロンプトを構成する工程を変えず、生成工程を高速化した結果である。ただし、これらの秒数は評価集合全体の処理時間であり、単一リクエストのTTFTを表すものではない。

## 既存研究との差

RESTと同じ検索ドラフト・検証の枠組みを採りながら、コードの局所性に合わせてリポジトリ固有データストアを追加し、検索位置を選び、検証済み継続を再利用する点が主要な差である。Ouroborosのように補助ドラフトモデルを用意する方式とは異なり、検索CPUと小さなデータストアでドラフトを作る。Self-speculativeのようにターゲットLLMの中間層を飛ばすための層選択も不要である。コード生成の正答率を改善するRAG方式に対しては、プロンプト品質を変えずに生成段階だけを短縮する直交的な最適化となる。

## 限界

第一に、コードの繰り返しや局所性を利用するため、識別子や表現が毎回新規で検索に合わない場合には受理長が短くなる。行頭の非空白トークンで検索成功率が低いという分析自体が、検索を省略する必要性を示している。検索データストアの構築・更新には時間とCPUメモリが必要で、短い単発要求では初期構築費用を償却できない可能性がある。

第二に、比較はgreedy復号に限定される。サンプリングを使う場合、ターゲット分布を厳密に保存するための受理・棄却方式が別途必要であり、greedyでの出力一致を温度付き生成へ無条件に一般化できない。tree attentionの正しいマスク・位置インデックス実装も必要で、既存サーバーへ単にデータストアを追加するだけでは再現できない。

第三に、評価は主にPythonコードとDevEval・RepoEval・HumanEval、最大2k入力・512生成、バッチ1である。非常に長いリポジトリ文脈、複数ユーザーの同時生成、異なる言語、CPUが逼迫した環境では、検索CPUやキャッシュ競合の影響が変わる。CodeLlama-13BだけGPU/CPU構成が異なるため、モデル間の性能比較にも注意が必要である。

第四に、The Stackを共通知識として使うため、評価対象のコードと一部の収集時期が重なる可能性がある。著者らは対象リポジトリの生成箇所を D_r から除外し、D_c の採用範囲をThe StackのPython部分のごく一部に限定しているが、未知のコードに対する一般化性能を完全に保証するものではない。GPU VRAMが同じでも、RESTよりCPUメモリを多く使うケースでは本方式の絶対的な省メモリ性は成り立たない。
