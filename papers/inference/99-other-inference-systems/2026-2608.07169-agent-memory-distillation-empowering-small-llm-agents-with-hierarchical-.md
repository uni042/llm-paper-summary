# Agent Memory Distillation：小規模LLMエージェントへの階層型教師記憶移植

## 概要

本論文の対象は、複数のアプリケーションや関数を連続して呼び出す小規模言語モデルのエージェントである。小規模モデルは自力で課題を解く成功率が低く、成功体験から記憶を作ろうとしても失敗軌跡が大半になる。そこで大規模モデルの成功軌跡を移す方法が考えられるが、単なる長い教師記憶を学生の入力へ貼り付けても、学生が前提となる操作を知らず、改善が小さい。論文はこの「教師の成功経験は豊富だが、学生が抽象的な助言を実行できない」という能力差を主題にする。

提案手法AMD（Agent Memory Distillation）は、教師が成功した道具呼び出し軌跡から、作業全体の戦略を示す**作業手順記憶（Workflow Memory）**、実際の道具呼び出し列を示す**部分作業記憶（Subtask Memory）**、個別関数の呼び方を示す**関数記憶（Function Memory）**を別々に構築する。前二者は学生の実行開始前に検索して入力へ与え、関数記憶だけは道具呼び出しがエラーになった時に検索する。学生モデルの重みを更新しない点が通常の知識蒸留と異なる。

GPT-5-miniを教師、Qwen3-4B、Qwen3-8B、Gemma4-E4B、Llama3.1-8Bを学生として、AppWorld、BFCL V3、ToolSandboxを評価した。4学生のゼロショット基準に対する平均成功率改善は順に**+27.2、+11.2、+3.4パーセントポイント**。とくにQwen3-4BのAppWorldでは14.88%から49.40%へ上がった。一方、記憶を大量に追加すると性能が下がり、教師モデルの単独精度が高いほど4B学生の成果も高いとは限らない。これは「大量の知識を渡す」より「実行できる粒度と適切な検索量に分解する」ことが重要だと示す。

## 問題設定と従来手法の限界

道具利用課題を、エージェント方策πがタスクsを受け、関数集合Fから操作a_tを発行し、観測o_tを受け取る反復として定式化する。成功した一連の操作と観測は軌跡τ=((a_1,o_1),...,(a_T,o_T))となる。教師π_Tをタスク集合Sで走らせて軌跡集合D_Tを得て、そのうち成功集合D_T+を記憶構築の材料にする。学生π_Sは得られた記憶Mを使ってタスクを解き、目標はE[R(π_S(s;M))]を大きくすることにある。ここで最適化するのは学生の重みではなく、教師軌跡の表現、検索、提示方法である。

学生自身の記憶が貧弱になる第一の理由は成功率の低さである。失敗の反省を蓄積しても、成功した道具呼び出し列の不足を補えない。第二の理由は、教師の知識をそのまま移すと粒度が粗すぎることである。例えば「決済サービスにログインしてから履歴を集計する」という方針だけを与えても、学生がログイン関数の引数やアクセストークンの扱いを知らなければ、実行が止まる。教師が作成した長文を単一の類似度検索で取得する方式では、計画、具体例、エラー修復の情報が同じ検索単位へ混在する。

比較対象のReasoningBankは課題単位の推論上の知見を検索する平坦な記憶、MemPは手続き的記憶を複数粒度に整理するが主として同一モデルの自己改善を想定する方式、SASMは部分作業粒度で検索するものの、計画・実行・エラー回復の種類を明示的に分けない方式である。AMDの差は、単に三種類のデータを持つことではなく、**それぞれの取得キー、情報の具体度、投入時点を変える**設計にある。

## 手法

### 教師軌跡から三種類の記憶を作る

#### 1. 作業手順記憶：タスク全体の見取り図

教師の成功軌跡τ_iについて、教師モデルが成功に必要だったアプリケーション、主要関数、前提条件、判断規則、完了確認、避けるべき失敗を自然言語で要約する。タスクの問い合わせq_iと戦略説明ins_iの組m_i^wf=(q_i,ins_i)を一つの記憶とし、問い合わせの意味表現をベクトル化して記憶庫M_wfに登録する。学生は新しいタスクの文章を検索キーにして最も近い作業手順を取得する。

記憶作成時には、教師軌跡中の利用者識別子、メールアドレス、資格情報、ファイルパスなどを型付きプレースホルダーへ置換する。これは実行時の値を誤って再利用しないためであり、同種だが別の利用者・資源を対象とするタスクへの転用にも必要である。記憶の出力はあくまで戦略であり、学生が個別の関数引数を知っていることまでは保証しない。その不足を次の部分作業記憶で補う。

#### 2. 部分作業記憶：具体的な操作と観測の組

成功軌跡を、例えば認証、取引履歴の取得、集計といった意味のまとまりへ分割する。教師モデルが各区間の境界を判定し、必要に応じて規則ベースの候補境界をヒントとして与える。区間e_i,kには実際のコードや関数呼び出しだけでなく、呼び出し後の観測結果も保持する。部分作業のラベルℓ_i,k、説明d_i,k、実行例e_i,kをまとめ、m_i,k^st=(ℓ_i,k,d_i,k,e_i,k)としてM_stへ保存する。検索に使うのは説明d_i,kの意味ベクトルである。

学生は実行開始前にタスクを最大6個の部分作業ラベルへ分解し、それぞれのラベルを独立に検索する。各部分作業について最も近い成功区間を取り出し、重複した区間は除外してから作業手順記憶とともにシステム入力へ注入する。こうして「何をするか」という計画の直後に「どの関数をどう連続実行して何が返るか」という実例が続く。教師の長い成功軌跡を丸ごと注入する場合より、学生が現在の段階に適用しやすい単位へ変換できる。一方、部分作業の分解や類似度検索が外れると無関係な実例が入る危険がある。

#### 3. 関数記憶：エラー時だけ取り出す呼び出し手引き

教師の成功軌跡から個々の関数呼び出しを抽出し、関数名f_i,j、実際の呼び出しと周辺文脈・返答E_i,j、利用できる場合の関数仕様doc(f_i,j)を組m_i,j^fn=(f_i,j,E_i,j,doc(f_i,j))としてM_fnへ登録する。作業手順・部分作業記憶と異なり、第一の索引は**関数名**である。引数の型、応答の形、呼び出す理由、前提条件をエラーに近い具体度で保持する。

学生の道具呼び出しが失敗した時だけ、その関数名に一致する記憶候補を取得する。同一関数の例が複数ある場合は、現在のタスク文章と例の推論文脈との余弦類似度で順位付けし、上位例をエラーメッセージに追記する。これにより成功している経路へは詳細なAPI例を常時注入せず、失敗した箇所だけ修正の手掛かりを与えられる。ただし呼び出しがエラーとして検知されない論理的失敗、例えば構文上は成功したが誤った対象を操作した場合には、この反応的検索が必ず働くとは限らない。

#### 4. 実行時の全体の流れと追加費用

教師側では成功軌跡を収集し、教師モデルによる戦略の言語化、区間分割、関数例の抽出を行い、作業手順と部分作業の記憶を事前に埋め込みへ変換する。学生側では新しいタスクの到着時に作業手順を1件、最大6個の部分作業に対してそれぞれ実例を1件検索する。類似度の下限を満たさない候補は捨てる。これらを一度だけシステム入力へ加えて実行を開始し、エラーが発生した場合のみ関数名索引と文脈類似度によって修復例を検索する。

実験では埋め込みモデルにtext-embedding-3-smallを使い、各記憶種の上位取得数は基本k=1とする。学生のモデル重みは変更されないが、教師軌跡の収集・記憶生成・埋め込み生成の事前費用、実行開始時の追加入力トークン、検索計算、エラー時の追加文脈は必要である。「学習不要」は「費用ゼロ」を意味しない。論文は成功率と対話ステップ数を主に評価しており、GPU単位の生成処理量やエンドツーエンド遅延の改善を示したものではない。

### 定量結果：成功率と作用機構

#### モデル別の成功率

| 学生・条件 | AppWorld成功率 | BFCL V3成功率 | ToolSandbox成功率 | 読み方 |
|---|---:|---:|---:|---|
| GPT-5-mini教師単独 | 50.00% | 36.50% | 28.68% | 教師の参考水準 |
| Qwen3-4Bゼロショット | 14.88% | 15.50% | 16.28% | 記憶なし |
| Qwen3-4B＋AMD | **49.40%** | **38.50%** | **20.16%** | 差は+34.52、+23.00、+3.88ポイント |
| Gemma4-E4Bゼロショット | 24.40% | 37.25% | 18.22% | 記憶なし |
| Gemma4-E4B＋AMD | **54.17%** | **46.00%** | **21.71%** | 差は+29.77、+8.75、+3.49ポイント |
| Qwen3-8Bゼロショット | 25.60% | 38.00% | 20.16% | 記憶なし |
| Qwen3-8B＋AMD | **51.79%** | **45.50%** | **25.58%** | 差は+26.19、+7.50、+5.42ポイント |
| Llama3.1-8Bゼロショット | 8.93% | 9.00% | 5.43% | 記憶なし |
| Llama3.1-8B＋AMD | **27.38%** | **14.50%** | **6.20%** | 差は+18.45、+5.50、+0.77ポイント |

AppWorldのQwen3-4Bは成功率14.88%から49.40%へ大幅に改善し、教師の50.00%に近づいた。Gemma4-E4BとQwen3-8BではAppWorldの学生成功率が教師の値を上回る。BFCL V3でも複数の学生が教師単独を上回る。ただし教師と学生は同一の推論経路をたどるわけではなく、これは「学生のモデル能力が教師より全面的に高い」という証明ではない。評価した課題で教師から抽出した成功知識を学生が別の行動列に活用した結果である。

既存の記憶方式が常に有効とは限らない。例えばQwen3-4BのAppWorldでは、ReasoningBankが14.88%から10.71%へ**悪化**し、MemPは16.67%、SASMは15.48%にとどまる。教師記憶を使うだけでは十分でなく、学生が解釈できる粒度と、エラーが起きた時の局所的な補助が必要である。逆にToolSandboxではAMDの平均改善が3.4ポイントにとどまり、タスク構造や学生の基礎能力によって利得は大きく変わる。

#### 構成要素除去実験：どの記憶が効いたか

| Qwen3-4Bで使用した記憶 | AppWorld成功率 | BFCL V3成功率 | 意味 |
|---|---:|---:|---|
| 記憶なし | 14.88% | 15.50% | 基準 |
| 作業手順のみ（WF） | 22.02% | 35.50% | 大まかな計画だけでも効果がある |
| 作業手順＋関数（WF+FN） | 24.11% | 35.50% | エラー修復だけでは長い課題の実行例を代替しない |
| 作業手順＋部分作業（WF+ST） | 47.02% | 37.50% | AppWorldの改善の大部分を説明 |
| 三種類すべて（WF+ST+FN） | **49.40%** | **38.50%** | 関数記憶が追加改善を与える |
| 学生自身の経験から作った記憶 | 16.07% | 27.00% | 教師成功軌跡の価値を確認 |

AppWorldで作業手順だけの22.02%に部分作業を加えると47.02%になり、**+25.00ポイント**改善する。これは部分作業記憶が具体的な関数呼び出し列と観測を供給するためという手法の狙いと整合する。一方、関数記憶を加える効果は47.02%から49.40%への+2.38ポイントであり、エラー回復の役割は限定的ながら正である。BFCL V3では作業手順のみで15.50%から35.50%へ上がるため、ベンチマークごとに支配的な機構が異なる。

#### 教師能力、学生規模、検索量の感度

教師変更実験では、AppWorldのQwen3-8B学生はGPT-5.5教師の記憶で58.93%、DeepSeek V4 Proで57.14%、GPT-5-miniで51.79%、Qwen3-32Bで39.29%となり、教師の成功率の順に沿う。しかしQwen3-4B学生はGPT-5-mini教師の49.40%が最良で、成功率91.08%のGPT-5.5教師では47.02%、81.55%のDeepSeek V4 Pro教師では38.10%だった。教師の絶対能力だけでなく、**学生がその手順を理解・再現できるか**が重要である。

学生規模の追加実験では、Qwen3系列の1.7B、4B、8B、14BにおけるAMD成功率はAppWorldで21.43%、49.40%、51.79%、52.68%である。絶対成功率は規模とともに増える一方、記憶導入による改善幅は4Bで最大の+34.52ポイントとなる。1.7Bでは記憶を活用する能力が足りず、8B以上では元からできる課題が多くなるため改善余地が狭まる、という解釈が妥当である。

検索件数をk=1から5へ増やす実験では、Qwen3-4BのAppWorldで部分作業記憶の取得数を増やすと成功率が49.40%から33.34%へ**低下**した。取得上位を多く投入するほど知識が増えるとは限らず、下位の関連度が低い例や長い入力が小規模学生の判断を妨げる。実装時にはkを増やすより、関連度しきい値・重複除外・学生側の文脈容量を管理する必要がある。

#### 対話ステップ数と再現性

AppWorldでQwen3-4Bの操作ステップ数はゼロショット23.8、教師10.1に対し、AMDで14.9へ減った。Gemma4-E4BのAMDは7.2ステップである。これは成功率だけでなく、余計な試行を減らす可能性を示す。ただしステップ数の減少は必ずしも計算時間や金銭費用の減少を意味しない。事前に注入する記憶トークンや教師記憶構築費用も勘定する必要がある。

付録では、記憶生成と評価で同一課題を共有しない分割実験、同一学生条件を5回反復した実験も扱う。5回反復の成功率標準偏差は3ベンチマークでいずれも1ポイント未満と報告される。これは観測された大きな改善が単一乱数種の偶然ではないことを補強する一方、異なる道具仕様、未知のアプリケーション、長期的に変化するAPIに対する外挿を保証しない。

## 既存研究との差と実装上の含意

ReasoningBankのような平坦な成功知識の検索は、教師と学生の能力差が大きい時、計画は伝えても具体的な実行を支援しにくい。SASMのような部分作業検索は中間粒度を扱うが、AMDはこれを作業手順と関数単位の失敗回復に接続した。重み更新を行う知識蒸留とは異なり、教師の成功例を検索可能な外部記憶へ加工して学生の入力へ与えるため、学生モデル自体の再学習や配布を必要としない。

システム設計上の重要な点は、記憶を「大きな共有文書」ではなく**粒度と検索時点の異なる三つの索引**として扱うことである。作業開始前の検索には自然言語タスクと部分作業ラベルを用い、エラー時には失敗した関数名を先に絞る。これにより、毎回すべてのAPI仕様を入力へ入れる必要がなくなる。ただし新しいAPIに対応する成功教師軌跡がなければ、検索から正しい例を得られない。また学生の部分作業分割自体が失敗する場合には、後段の検索も連鎖的に外れる。

## 限界

第一に、AMDの改善は教師が成功した課題から有用な記憶を抽出できることに依存する。教師成功率が低い場合、記憶庫の網羅性も低くなる。さらに教師が非常に高性能でも、学生が理解できない複雑な戦略を渡すと転移効率が下がる。実際にQwen3-4Bでは最も成功率の高い教師が最良の記憶源にならなかった。記憶を構築するための教師呼び出し費用と学生実行時の費用の総額は、長期運用時の重要な論点として残る。

第二に、入力へ注入する記憶は少ないほど良い場合がある。部分作業の取得数を5へ増やすとAppWorld成功率が大きく下がった。これは単なる記憶量増加を最適化目標にすべきでないことを示す。意味埋め込みの検索ミス、古いAPI例、文脈長の制限、誤った部分作業分解は失敗要因となりうるが、すべてが独立に測定されたわけではない。

第三に、三つのベンチマークの成功率は同一尺度ではない。AppWorldはデータベース状態、BFCL V3は呼び出しと状態、ToolSandboxは対話シナリオの到達条件を使う。表の平均はベンチマーク間の単純な比較に過ぎず、実際のサービス配備での成功率や信頼性を直接予測しない。評価モデルも4B/8B中心で、学生規模の感度分析を除けば非常に小さいモデルや異種言語モデルへ無条件に一般化できない。

第四に、論文の「効率」は主として成功率と操作ステップ数であり、推論処理量（tokens/s）、GPUメモリ、検索待ち時間、教師軌跡生成の償却費用、API変更時の記憶更新頻度について、同じ粒度のエンドツーエンド性能比較は示されていない。実務へ導入する場合は、成功率だけでなく、教師記憶構築費用、追加入力トークン、検索の遅延、誤った関数呼び出しからの復帰率を別々に測定する必要がある。
