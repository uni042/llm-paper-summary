# SpecSA: Bridging Speculative Decoding and Sparse Attention for Efficient LLM Inference

> 投機的検証と動的sparse attentionを単純に組み合わせるとqueryごとに異なるKV blockを読むため共有効果が落ちる。SpecSAは近接query間の選択block重複を明示的に再利用し、検証処理をsparse attention向けに作り直す。

## 問題設定

Speculative decodingは複数の候補tokenをtarget modelでまとめて検証し、同じprefix KVを複数queryで共有してmemory accessを償却する。一方、Native Sparse Attention（NSA）のような動的sparse attentionはqueryごとに参照するKV blockを選ぶ。このため両者をそのまま組み合わせると、queryごとに似たKV blockを選んでいても別々にHBMから読み、selection・branch統合のkernel overheadも増える。

## 手法

### 1. 近い検証queryをまとめてKV blockを共有する

SpecSAはdraft treeをBFS/DFS順に並べ替え、位置が近いqueryを最大C個ずつ同じthread blockで処理する。各queryが選んだKV block集合をon-chipでmergeして重複blockを一度だけHBMから読むexact方式と、代表queryのselection indexをgroup全体で共有する近似方式を用意する。

8K contextのprofilingでは隣接queryのselected-block overlapが多くのlayerで約50〜90%あり、この重複を実際のHBM traffic削減へ変える。

### 2. Refresh / Reuse layerでselection計算を減らす

NSAはcompression・selection・sliding-windowの複数branchを持つ。SpecSAはselection indexを再計算するrefresh layerでは必要部分だけを融合し、近接layerでindexが安定しているreuse layerでは直前のindexを再利用してselection構築を省き、branchをより強く融合する。これによりkernel launchと中間結果のHBM書き戻しを減らす。

### 3. Draft構成とsparse verificationを一体で選ぶ

offline profilerがdraft tree形状、tree traversal、query grouping、refresh/reuse scheduleをcontext長と精度classごとに評価する。runtimeでは実際のaccepted-token傾向がprofileから外れた場合にstrategyを選び直す。つまり「draft側」と「verification kernel側」を別々に固定せず、実測throughputを基準に組み合わせを選ぶ。

## 評価

NVIDIA H100上でNSA targetとEAGLE-3 integrationを評価し、論文は以下を報告する。

- sparse speculative verification kernel: 最大 **6.86×**
- verification stage: 最大 **1.45×**
- autoregressive NSA decoding比のend-to-end throughput: 最大 **3.49×**
- profile-guided planningによるaccepted-token throughput: 最大 **33.2%** 改善

近似shared-index方式については1B NSA modelでPIQA、HellaSwag、ARC-Easy/Challengeを評価し、C=4でもexact方式との差は小さい。ただしこれは全model・taskでlosslessを保証するものではない。

## 既存研究との差

通常のspeculative decodingはdense attentionで共有prefixをまとめて読むことを前提にしやすい。通常のdynamic sparse attentionはsingle-query decodeを主眼にqueryごとのselected blockを処理する。SpecSAは**speculative verificationで同時に現れる複数query間のselected-block overlap**を新しいreuse単位として扱い、selection indexのlayer間reuseとdraft strategyまで同時に最適化する。

## 限界

- 具体的backendはNSAであり、DeepSeek Sparse Attention等へ移すにはrouting metadata・query-level selection・十分なindex overlapが必要。
- shared-index variantは近似であり、精度影響はmodel/task依存。
- 主評価はH100で、他GPUやserving stackへの移植コストは未評価。
- sparse attentionを持たない通常dense modelへそのまま適用する方式ではない。

## 一般的な実装上の含意

投機的検証とsparse attentionを併用する場合、query単位のsparsityだけを見ると共有機会を失う。**同じverification batch内で選択KVがどれだけ重なるか**をscheduler/kernelへ渡し、query間・layer間の両方でindexとKV loadを再利用できる設計が重要になる。
