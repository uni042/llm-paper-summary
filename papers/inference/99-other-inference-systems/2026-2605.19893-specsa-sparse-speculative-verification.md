# SpecSA: Bridging Speculative Decoding and Sparse Attention for Efficient LLM Inference

> SpecSAは、投機的復号（speculative decoding）と動的疎注意（dynamic sparse attention）を「両方ONにする」だけでは得られない再利用を、**複数verification queryが選ぶKV blockの重なり**から取り出すsystemである。queryごとの選択結果を保ったまま重複blockを1回だけ読むexact方式と、さらに高速なshared-index近似方式を用意し、layer間index再利用・kernel fusion・promptごとのstrategy選択まで一体化する。

## 概要

長contextの自己回帰復号（autoregressive decoding）では、1 tokenを生成するたびに過去のKVキャッシュ（KV cache）を読む必要がある。

contextが64K、128Kと伸びるほど、このKV readがGPU HBM bandwidthを強く消費する。論文はLlama-3.1-8B-Instruct、64K context、H100 PCIeの例でattentionが1 decode stepの約97.2%を占めると報告している。

この問題には代表的に2方向の高速化がある。

1. **投機的復号（speculative decoding）**：複数candidate tokenをtarget modelが一度に検証し、1回のtarget forwardで複数tokenを確定する。
2. **疎注意（sparse attention）**：各queryが過去KV全部ではなく、重要そうな一部だけを読む。

直感的には、この2つを組み合わせればさらに速くなりそうに見える。

しかし両者が利用する「共有」の方向は逆である。

speculative verificationは、複数queryが同じ確定済みprefixを持つため、**同じKVをまとめて読む**ことで得をする。

一方dynamic sparse attentionは、queryごとに「自分に重要なKV block」を別々に選ぶことで得をする。

その結果、複数queryが実際にはかなり似たblockを選んでいるのに、通常のdecode向けsparse kernelではqueryごとに独立して同じblockをHBMから何度も読むことになる。

SpecSAのprofilingでは、8K contextで隣接するverification query同士のselected-block overlapが多くのlayerで**約50〜90%**に達する。

SpecSAはこの重複を、

- query間のKV load共有
- layer間のselection index共有
- NSA branchのkernel fusion
- draft treeとverification strategyの共同選択

へ変換する。

## 背景: Native Sparse Attention（NSA）は何をしているか

SpecSAの具体backendはNative Sparse Attention（NSA）である。

NSAはattentionを大きく3 branchへ分ける。

### 1. 圧縮branch（compression branch）

古いcontextをblock単位に圧縮し、長距離情報を粗い表現で広く見る。

全tokenをそのまま読むより安いが、細かい情報は失われる。

### 2. 選択branch（selection branch）

現在queryと圧縮表現を使って、「元の高精度KVのうちどのblockを詳しく読むべきか」をTop-nで選ぶ。

ここで得られるblock番号の集合が**selection index**である。

実際のraw KV read量を減らす中心機構だが、queryごとにindexが異なる。

### 3. sliding-window branch

直近tokenは常に高精度で密に見る。

最近の局所文脈を落とさないためのbranchである。

最後に3 branchの結果をlearned gateで合成する。

この設計はsingle-query decodeには有効だが、speculative verificationでは一度に複数queryが来るため、

- queryごとのindex生成
- 3 branchごとのkernel launch
- 中間結果のHBM書き戻し
- branch結果の再読込と合成

が繰り返され、固定overheadが目立つ。

## なぜ既存kernelをそのまま使えないのか

### Decode向けkernelは同じKV blockを何度も読む

query Aがblock `{1, 5, 9, 12}`、query Bが `{1, 5, 10, 12}` を選んだとする。

2 queryは4 block中3 blockを共有している。

しかしsingle-query decode向けkernelを2回実行すると、block 1, 5, 12をそれぞれ2回HBMから読む。

speculative verificationではこうしたqueryが多数存在するため、重複readが増える。

### Prefill向けkernelは逆に読みすぎる

prefill向けkernelは多queryをまとめやすいが、広いKV範囲を一括loadする設計になりやすい。

sparse verificationでは「どのqueryも選んでいないblock」まで読むと、sparsityの利点が失われる。

つまり必要なのは、

**複数queryをまとめながら、実際に誰かが必要とするKV blockだけを1回ずつ読むkernel**

である。

## 手法のあらまし

SpecSAのverificationは概ね次の流れになる。

1. draft modelがcandidate treeを作る。
2. tree nodeをBFSまたはDFS順で平坦化する。
3. positionが近いverification queryを最大`C`個ずつgroup化する。
4. exact modeなら各queryのselected-block indexを個別に求める。
5. group内indexをon-chipでsort / mergeし、重複blockを1つのload scheduleへまとめる。
6. 各unique KV blockをHBMから1回だけ読み、必要なqueryだけへ適用する。
7. 近似modeでは代表query 1つのselection indexをgroup全体で共有し、merge処理自体も省く。
8. layerによってselection indexを再計算するRefresh layerと、直前indexを使うReuse layerを分ける。
9. Reuse layerではNSAの3 branchをさらに強くfusionする。
10. offline profileとruntimeのaccepted-token傾向から、tree形状・BFS/DFS・group size・exact/approx・Refresh/Reuse scheduleを選び直す。

## 手法

### 1. Tree traversalで「似たqueryが隣り合う順序」を作る

candidateが単なる1本のdraft sequenceなら、隣接tokenをgroup化すればよい。

しかしEAGLE-3などはcandidateをtreeとして作る。

このtreeには2種類の近さがある。

- **兄弟（siblings）**：同じfuture positionの別候補。意味的に近い可能性がある。
- **親子（parent/child）**：同じcandidate path上で位置が近い。

SpecSAはtreeを、

- 幅優先探索（Breadth-First Search; BFS）
- 深さ優先探索（Depth-First Search; DFS）

のどちらかでflattenする。

BFSはsiblingsを近く並べやすく、DFSはparent/childを近く並べやすい。

どちらがselected-block overlapを高めるかはpromptやtree形状で変わるため、固定ruleにせずplannerが選ぶ。

### 2. Cross-query grouping: 最大C queryを1 thread blockへまとめる

flatten後の近接queryを最大`C`個ずつ同じGPU thread blockへ割り当てる。

`C=1`なら従来通りで再利用がない。

`C`を大きくしすぎると、

- mergeするindex数が増える
- register/shared-memory pressureが増える
- thread block数が減ってGPU並列性が落ちる

ため無制限に増やせない。

SpecSAは「reuseを増やしたい」と「1 groupを重くしすぎたくない」の中間をprofileから選ぶ。

### 3. Exact merged schedule: query固有indexを壊さずKV loadだけ共有する

exact方式では各queryのselection indexを通常通り個別に計算する。

例えば、

- Q1 → `{1, 5, 9, 12}`
- Q2 → `{1, 5, 10, 12}`

なら、on-chipで結合して、

`{1, 5, 9, 10, 12}`

というunique block scheduleを作る。

各KV blockはHBMから1回だけloadする。

ただしQ1にblock 10、Q2にblock 9を見せてはいけない。

そこでkernelは「このblockが元々そのqueryの選択集合に含まれるか」を保持し、含まれないqueryのattention logitを`-∞`へmaskする。

これにより、**memory accessは共有するが、各queryのlogical sparse attention結果は独立実行と同じ**になる。

ここがSpecSAのexact modeの重要点である。

### 4. Shared-index variant: 代表queryのblock集合をgroup全体で使う

もっと aggressive に高速化する近似modeでは、各queryのselection indexを作らない。

例えばgroup内でprefixが最も長いqueryを代表にし、そのqueryが選んだblock集合を全queryへ使う。

利点は、

- per-query index生成が不要
- sort / dedup mergeが不要
- 全queryが同じKV blockを読むためreuse率が最大化する

ことである。

一方、非代表queryが本来選びたかったblockを読まなくなる可能性がある。

したがってこれは**sparse-attention semanticsを変える近似**であり、exact modeと同じlossless方式ではない。

論文の1B NSA model評価では`C=4`でもPIQA、HellaSwag、ARC-Easy、ARC-Challengeのaccuracy差は小さかった。例えばPIQAはexact 73.78%に対しshared-index C=4で73.88%、HellaSwagは58.37%に対し58.53%だった。

ただしこの結果は「どのmodel/taskでも安全」を意味しない。SpecSAはprecision classとしてexactとapproximateを分けて扱う。

### 5. Refresh layer: selection indexを本当に作り直すlayer

NSAのselection indexはlayerごとに完全に別とは限らない。

隣接layerでは同じようなKV blockを選びやすい。

それでも定期的には新しいindexを計算する必要がある。このlayerを**Refresh layer**とする。

Refresh layerでは、

1. compression / routingでTop-n block indexを新規計算
2. selection branchとsliding-window branchをfusion
3. branchごとの正規化状態を保ちながら最終aggregationへつなぐ

というpartial fusionを使う。

routingが完了するまでselected KVを読めないため、compression/routingまで完全に1 kernelへ押し込むのはdata dependencyとresource patternの両面で不利になる。

### 6. Reuse layer: 直前のindexを引き継ぎindex生成を省く

selected-block patternが安定しているlayerでは、直近Refresh layerのindexをそのまま使う。

これを**Reuse layer**とする。

Reuse layerではrouting/index生成が消えるので、

- compression
- selection attention
- sliding-window attention
- gated aggregation

をより強く1 kernelへfusionできる。

中間branch outputをHBMへ書いて別kernelで読み直す必要がなくなり、on-chip stateのまま最終outputまで進められる。

つまりlayer間index reuseには、selection計算自体を省く効果だけでなく、**data dependencyを消してkernel fusionを可能にする二次効果**がある。

### 7. Draft strategyとsparse kernel strategyを一つの探索問題にする

speculative decoding側には、

- draft長
- candidate tree形状
- BFS / DFS traversal

がある。

sparse attention側には、

- group size `C`
- exact / shared-index
- Refresh / Reuse schedule

がある。

これらは独立ではない。

例えばdraftを長くするとquery数が増えてKV reuse機会は増えるが、verification costも増える。DFS/BFSでindex overlapが変わればbest group sizeも変わる。

SpecSAはoffline profilerで、この**組合せ全体**をcontext-length regimeとprecision classごとにbenchmarkする。

### 8. Prompt-adaptive refinement: 実際のacceptanceを見て途中でstrategyを変える

offline profileだけではprompt固有のdraft acceptanceを完全には予測できない。

あるpromptではdraftがよく当たり、別promptでは短いprefixしかacceptされない。

SpecSAはgeneration開始時にoffline-best strategyを使い、初期の複数verification roundから、

- 実際のaccepted token数
- observed throughput

を集める。

profileとの差が大きければ、同じpromptの残りdecodeについて別strategyへreselectする。

長いresponse generationでは多数roundが続くため、序盤の観測costを後半で回収できるという考え方である。

## 評価

### まず見るところ

- **Kernel単体:** sparse speculative verification kernelで最大 **6.86×**。
- **Verification stage全体:** 最大 **1.45×**。
- **End-to-end:** autoregressive NSA decode比で最大 **3.49× throughput**。
- **Planner:** profile-guided strategy選択によりaccepted-token throughputを最大 **33.2%**追加改善。
- **重複性:** 8K contextの隣接verification queryではselected-block overlapが多くのlayerで約50〜90%。
- **品質:** exact merged scheduleは元のper-query sparse layoutを保持。shared-indexは近似で別扱い。

### なぜ6.86×がそのまま3.49×にならないか

6.86×は**特定のsparse verification kernel部分**の最大speedupである。

end-to-endでは、

- draft生成
- non-attention layer
- acceptance処理
- KV更新
- scheduler/runtime処理

などは同じ倍率では速くならない。

そのためverification stage全体は最大1.45×、最終的なautoregressive NSA比throughputは最大3.49×という別の数字になる。

これらを同じspeedupとして扱ってはいけない。

### Exactとapproximateの品質境界

1B NSA modelでの代表結果。

| Benchmark | Exact SpecSA | Shared-index C=4 |
|---|---:|---:|
| PIQA | 73.78% | 73.88% |
| HellaSwag | 58.37% | 58.53% |
| ARC-Easy | 69.49% | 69.82% |
| ARC-Challenge | 36.95% | 37.37% |

この範囲では統計誤差内に近いが、shared-indexはalgorithm上はapproximateである。

またReuse layerのindex scheduleを追加した条件でも同等accuracyを報告するが、これも対象model/taskでのempirical resultとして読む必要がある。

### 適用範囲

論文はNSAを具体backendとする。

DeepSeek Sparse Attention（DSA）など別方式へ移すには少なくとも、

1. routing metadataをruntimeから取得できる
2. query単位のselected-indexを扱える
3. verification query間で十分なindex overlapがある

必要がある。

これらが無ければSpecSA kernelをそのまま移植できない。

## 既存研究との差

### 通常のspeculative decodingとの違い

SpecInfer、Medusa、EAGLEなどは、主にdense target verificationで「複数candidateを一度にtargetへ通す」ことを高速化する。

SpecSAはcandidate生成方法そのものより、**dynamic sparse attentionを使うtarget verifier内部**を主対象にする。

### 通常のsparse attentionとの違い

NSAなどはsingle-query decodeやprefillを中心に設計され、query間のselected-block overlapをspeculative verification用reuseとして扱わない。

SpecSAは「同時に来る複数query」を新しいreuse単位にする。

### IndexCache系との違い

IndexCache系はlayer間でselected indexを再利用する。

SpecSAはこのlayer間reuseに加え、**同一verification batch内のquery間reuse**を同時に使い、さらにdraft tree構造とkernel strategyをjoint planningする。

## 限界

- 具体的backendはNSAであり、任意のsparse attentionへそのまま適用できない。
- exact modeでもsystem implementationはNSA専用kernel設計を必要とする。
- shared-index variantはapproximateで、品質影響はmodel/task依存。
- Refresh/Reuse scheduleも選択indexの安定性へ依存する。
- 主評価はH100で、consumer GPUや異なるGPU architectureでの最適`C`やfusion効果は変わり得る。
- draft treeが短い、またはquery間selected-block overlapが低いworkloadではreuse利得が小さい。
- sparse attentionを使わないdense modelには直接の利点がない。
- profilerはcontext regime × precision class × strategy tupleの測定を必要とするため、導入時のtuning costがある。

## 一般的な実装上の含意

SpecSAが示す重要な点は、2つの高速化手法を個別に速くしても、その**compositionが速いとは限らない**ことである。

speculative decodingはqueryをまとめることで得をする一方、dynamic sparse attentionはqueryを個別routingすることで得をする。この相反する構造をそのまま重ねると、同じKV blockを何度も読むという新しい重複が生まれる。

したがって複数optimizationを組み合わせるsystemでは、

- それぞれが何を共有しているか
- 一方の最適化がもう一方のreuse単位を壊していないか
- intermediate metadataをquery間 / layer間で再利用できないか
- exact modeとapproximate modeを明確に分離できているか

まで見直す必要がある。

特に長context inferenceでは、KV byte数だけでなく**同じKV blockを何回HBMから読むか**が重要である。
