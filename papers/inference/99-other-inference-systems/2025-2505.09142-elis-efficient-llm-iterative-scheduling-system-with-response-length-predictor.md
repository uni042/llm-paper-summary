# ELIS: Efficient LLM Iterative Scheduling System with Response Length Predictor

> 応答長を50トークンごとに再予測して短い残作業を優先し、LLM servingの先頭待ちを減らすKubernetes/vLLMスケジューラ。
## 書誌情報
- **著者**: Seungbeom Choi, Jeonghoe Goo, Eunjoo Jeon, Mingyu Yang, Minsung Jang
- **著者・所属**: Cloud Research Team, Samsung SDS, South Korea
- **公開**: arXiv
- **種別**: プレプリント
- **対象**: LLMサービング、反復スケジューリング、応答長予測、vLLM、Kubernetes、優先度制御
- **実装**: Python約3.1K行のfrontend/backendシステムとvLLMへの100行未満の変更で実装し、Kubernetes StatefulSet/Serviceとして配備。論文は公開コード・YAMLを提供すると記載するが、一次資料から確実なリポジトリURLは確認できなかった。
## 概要
ELISは自己回帰LLMの出力長を軽量なBGEベース予測器で推定し、50トークンの反復ごとに残り応答長を再予測して短い残作業を優先するISRTFスケジューラである。vLLMを反復実行・動的優先度へ拡張しKubernetes上へ実装、実サービス由来の到着分布を用いた評価でFCFS比の平均JCTを最大19.58%短縮し、50 H100 workerで18.77 RPSまでほぼ線形に拡張した。

ELISはBGE埋め込みモデルを凍結し8層の全結合層だけを学習した軽量応答長予測器と、LLMの反復生成に合わせて残り長を更新する反復最短残時間優先（ISRTF）を組み合わせる。初回はプロンプトだけから全応答長を予測し、その後は50トークン生成するたびにプロンプトと既生成出力を再入力して残り長を予測し直すため、一回予測の誤差を生成途中で補正できる。vLLMをKトークン単位で返す反復実行と外部優先度指定へ拡張し、中央スケジューラ・複数worker・Kubernetes配備まで含む実運用志向システムとして実装した点も特徴である。

代表結果として、応答長予測精度は13 LLM由来105,295 cleaned rowsでLMSYSのみでfine-tuneしたBGEはR² 0.48に対してMAE 19.923, RMSE 34.327, R² 0.852。実際の生成モデル群から収集した反復学習データで残り長予測が大幅に改善する。
## 問題設定
連続バッチングは完了した要求の枠へ新規要求を反復単位で入れられるが、一般的な先着順では長い生成要求が短い要求より先にGPU時間を占有し、対話サービスで先頭待ちが生じる。古典的な最短ジョブ優先や最短残時間優先を使うには各要求の残り実行時間が必要だが、LLMでは出力トークン数が生成終了まで未知である。生成LLM自身に長さを出させる方式はモデル精度を変える可能性があり、BERT系予測器を一度だけ使う既存方式は誤予測を後から修正できない。さらに頻繁な優先度変更やプリエンプションはKVキャッシュ移動を伴い得るため、予測器の計算費と切替費用が短縮効果を上回らない設計が必要になる。
## 新規性
ELISはBGE埋め込みモデルを凍結し8層の全結合層だけを学習した軽量応答長予測器と、LLMの反復生成に合わせて残り長を更新する反復最短残時間優先（ISRTF）を組み合わせる。初回はプロンプトだけから全応答長を予測し、その後は50トークン生成するたびにプロンプトと既生成出力を再入力して残り長を予測し直すため、一回予測の誤差を生成途中で補正できる。vLLMをKトークン単位で返す反復実行と外部優先度指定へ拡張し、中央スケジューラ・複数worker・Kubernetes配備まで含む実運用志向システムとして実装した点も特徴である。
## 手法
### 手法のあらまし
入力は時系列に到着するユーザープロンプト、各バックエンドの現在job数、各jobの途中応答である。まずfrontend スケジューラが新規プロンプトをjobへ変換し、global stateを参照して実行job数が最少のbackend workerへ固定割当する。次にBGEベース応答長予測器へプロンプトを入れ、予測される全出力トークン数を初期の残り作業量としてjob priorityへ設定する。各worker用priority バッファでは予測残トークン数が少ないjobほど高優先度となり、batcherが上位jobからバッチを構成してbackendへ送る。backendの改造vLLMは通常のように要求完了まで走らず、一回の反復で最大50トークンだけ生成し、完了したjobまたは50トークン分のpartial responseをfrontendへ返す。完了jobはその場で利用者へ最終応答として返す。未完了jobについては生成済みテキストをjob状態へ追記し、同じjobをjob poolへ戻す。次の反復では予測器へ元プロンプトと既生成テキストを連結して入力し、既に生成済みの分を踏まえた『これから残るトークン数』を再推定する。この新しい予測値でpriorityを上書きし、全未完了jobを再び短い残作業順に並べ、次の50トークン窓を実行する。したがって誤った初回予測は永久に固定されず、生成が進むたびに新しい文脈で修正される。予測器自体は13種類のLLMに11,000 promptを実行して得た143,000 prompt-answer pairから重複・外れ値を除いた105,295行を6:2:2へ分割し、凍結BGEの埋め込みを平均poolingして8層全結合部だけを学習する。frontendのload balance、予測、バッチ構築等は別processとして非同期実行しshared メモリで状態を交換する。ネットワーク負荷を抑えるため元promptはbackendへ初回だけ送り、後続反復ではjob識別子・priority・partial output等を中心に交換する。出力は各要求の完成応答であり、最適化目標は生成トークン計算量そのものではなくqueueing delayと平均job completion timeの削減である。50トークン窓が短すぎれば予測・再バッチ・通信回数が増え、長すぎれば誤priorityを保持する時間が増えるため、著者らは反復予測精度とオーバーヘッドの実験から50を採用する。過負荷で全workerのqueueが厚くなりスループットが支配的になる場合は並べ替えだけでは改善できず、これが主要な失敗条件である。

### 反復応答長予測器
BGEの文脈埋め込み能力を使い、プロンプトまたはプロンプトと途中生成文から残り出力トークン数を推定する。BGE本体は凍結し、平均pooling後に8層の全結合ネットワークを置く。13種類のLLM出力から作った105,295行を6:2:2で学習・検証・試験へ分割し、A100上で学習する。初回予測だけで固定せず50トークンごとに途中応答を追加して再予測するため、生成が進むほど利用可能な情報が増え、初期誤差を修正できる。最終予測器はMAE 19.923、RMSE 34.327、R² 0.852を報告し、軽量な独立予測器なので生成モデル本体を変更しない。

### ISRTF優先度制御
古典的SRTFをLLMの反復バッチングへ合わせ、各jobの予測残トークン数を残り処理時間の代理として短いjobを先に実行する。各50トークン窓の境界でjobをpriority バッファへ戻して再順位付けするため、長い要求が先着しただけで短い要求を長時間塞ぐ状況を減らす。予測が外れても次窓で順位を修正できる点が一回予測SJFとの差である。低優先jobのstarvationや必要時のpreemptionもpolicyとして考慮するが、実トレースではpreemptionが必要な高負荷は稀と判断し主評価は優先度再配置へ集中する。

### vLLM反復実行拡張
backendはvLLMをそのまま完了まで走らせず、指定した50トークンを生成した時点または要求完了時にpartial responseを返すよう変更する。さらに外部スケジューラがjobごとの優先度をvLLMへ渡し、既定の先着順preemption policyを上書きできるようpolicy・スケジューラ・entry pointを100行未満変更する。リクエスト IDをfrontend jobへ対応付けることで、反復ごとに更新された優先度を同一要求へ適用する。これによりモデルカーネルやKV管理を全面再実装せず既存vLLMを実行基盤として再利用する。

### クラウドネイティブfrontend/backend構成
中央frontendは予測、load balance、job pool、priority バッファを担当し、複数backend workerは指定モデルのvLLM engineを保持する。frontend内の副処理は別processとして非同期化し、shared メモリでworker状態とjob状態を共有する。Kubernetesではfrontendとbackendをpod化し、backendは一意な識別子が必要なためStatefulSetで管理、Service endpoint経由で通信する。promptは初回だけbackendへ送り、反復ではpartial output中心に通信してnetwork負荷を抑える。最大50 workerまで増やしたH100評価では18.77 RPSを達成し、中央制御が大規模化の律速になりにくいことを示す。

### 全体のデータ／制御の流れ
ELISは『残り長を予測→短いjobを優先→50トークンだけ実行→途中出力で残り長を再予測』という閉ループをLLM生成完了まで回す。予測器は生成モデルから分離されるためモデル品質を直接変えず、vLLM側の変更は反復停止と優先度注入に限定する。中央スケジューラはworker負荷を見て配置し、各worker内では予測残長でバッチ順序を決める。反復窓を短くすると順位修正は速いが予測・通信・バッチ再構成回数が増え、長くすると誤順位の保持時間が延びるため、実験から50トークンを採用する。効果はqueueing delay削減として現れ、過負荷でqueueが大量に溜まる条件では優先度制御の効果が薄れる。
## 評価条件
- **ハードウェア**: 主評価クラスタはDual AMD EPYC 7H12、2TB RAM、8×NVIDIA A100 80GB HBM2。Ubuntu 20.04、CUDA 12.2、driver 535.183、vLLM 0.5.0を使用する。拡張性評価ではH100を1 workerあたり1 GPUとして最大50 workerまで使用する。予測器学習もA100で実施する。
- **ソフトウェア**: ELIS frontend/backendはPython約3.1K行。vLLMのpolicy・スケジューラ・entry pointへ100行未満の変更を加え、50トークン単位の反復実行と外部優先度制御を実装する。Kubernetesではfrontend/backendをpod化し、backendはStatefulSetで一意IDを維持する。応答長予測器はBAAI/bge-base-en-v1.5＋8全結合層、ReLU、hidden 1024、学習率1e-4、バッチ 16。
OPT-6.7B/13B、LLaMA2-7B/13B、Vicuna-13Bを評価し、FCFS、提案ISRTF、真のprofiled 遅延を使うoracle SJFを比較する。LMSYS-Chat-1Mから200 promptを同一集合でsamplingし順序をshuffle、各条件3回実施する。到着間隔はSamsung SDS FabriXの2か月・20万件超のトレースから推定したGamma分布（shape 0.73, scale 10.41）で生成する。バッチ size 1/2/4、平均リクエスト rateの複数倍率で平均JCTとqueueing delayを測る。拡張性は平均queue delayが0.5秒以下を保てる最大RPSで評価する。
実サービス由来の到着分布とKubernetes/vLLM実装を使う点は現実的だが、prompt内容自体はLMSYSからsamplingしたシミュレーションである。主JCT評価はA100上の5モデルで、H100評価はworker数拡張性が中心。SLO tail 遅延、異種GPU、複数モデル混在、予測器再学習の運用コスト、極端なburst時のstarvation/preemption効果は十分には評価されない。
## 主要結果
反復予測器はvLLM由来データでR² 0.852を達成し、ISRTFはほぼ全条件でFCFSの平均JCTを改善した。本文のバッチ size 4評価では平均改善7.36%、最大21.40%で、バッチ size 1を含む全評価では最大19.58%短縮を報告する。LLaMA2-13B・5×RPSの代表例ではJCTを16.45%、queueing delayを16.75%削減し、スケジューラ＋初回予測のオーバーヘッドは11.04ms、モデル平均遅延8610.2msの0.13%に留まる。H100 50 workerでは18.77 RPSまでほぼ線形に拡張した。

- 応答長予測精度 / MAE 19.923, RMSE 34.327, R² 0.852 (比較対象: LMSYSのみでfine-tuneしたBGEはR² 0.48; 条件: 13 LLM由来105,295 cleaned rows) — 実際の生成モデル群から収集した反復学習データで残り長予測が大幅に改善する。

- 平均JCT改善 / 平均7.36%、最大21.40%（バッチ size 4系列）; 全評価で最大19.58%報告 (比較対象: FCFS; 条件: A100, 5 LLM, Gamma arrival ワークロード) — 短い残作業を先に処理することでhead-of-line blockingを減らす。

- LLaMA2-13B 5×RPS / FCFS 451.59s → ISRTF 377.29s (比較対象: FCFS; 条件: バッチ size 4) — 高負荷代表条件で約16.45% JCTを短縮する。

- queueing delay reduction / 16.75% (比較対象: FCFS; 条件: LLaMA2-13B, 5×RPS) — JCT改善16.45%との差が0.30ポイントで、主因が計算短縮ではなく待ち時間削減だと示す。

- スケジューラ オーバーヘッド / 11.04ms, model 遅延比0.13% (比較対象: LLaMA2-13B average 遅延 8610.2ms; 条件: batching＋initial predictor) — 予測・再順位付けの費用がJCT短縮効果より十分小さい。

- 50-worker scalability / 18.77 RPS (比較対象: 10 workerで2.31 RPS; 条件: H100, one worker/GPU, queue delay <=0.5s) — 非同期frontendとload balancerにより大規模worker数でもほぼ線形に拡張する。

### 負の結果・境界条件
- ISRTFは全条件で必ず勝つわけではない。バッチ size 4ではOPT-6.7Bの1×/5×RPS、LLaMA2-13Bの3×RPS、LLaMA2-7Bの1×RPSなどでFCFSよりJCTが悪化する。論文は小バッチ・高RPSではqueueに大量のpromptが溜まりpriority スケジューラの効果が薄れ、system スループット依存が強くなると説明する。また実サービストレースではpreemptionが必要な負荷が稀だったため、preemption policy自体の詳細な性能評価は省略されている。

### 結果の読み方
ELISの利点は予測器単体の精度ではなく、自己回帰生成から50トークンごとに新情報を得て残り長を更新し、その更新を次バッチ順序へ直結させる閉ループにある。誤予測を次反復で修正できるため、一回予測SJFより運用上頑健である。一方、GPUが純粋なスループット飽和状態になると並べ替えだけでは処理能力を増やせず、改善幅が消える。
## 品質への影響
生成モデル本体を変更しないため回答品質を直接劣化させる機構ではない。影響対象は主に待ち時間と公平性であり、短いjob優先は長いjobの待機を延ばす可能性があるためstarvation防止policyが必要となる。
## 既存研究との差
ORCA型continuous batchingはiteration単位で枠を再利用するが基本FCFSで、ELISは各窓で残り長を予測してpriorityを更新する。QiuらのBERT予測＋SJFは一回だけ長さを推定するのに対し、ELISは途中生成を入力へ足して反復予測するため誤差を補正できる。PiAのように生成LLM自身をinstruction tuningして長さを出させる方式と異なり、独立BGE予測器なので生成モデルの応答品質を変えない。FastServeのMLFQはtrial-and-errorでpriorityを適応するが、ELISは意味埋め込みから残長を直接予測して探索的priority調整のオーバーヘッドを避ける。
## 限界
応答長予測器は特定の13モデルから収集したデータで学習され、未知モデル・domainへの転移や継続的再学習の費用は十分検証されない。実到着分布はFabriX トレース由来だが、評価prompt本文はLMSYSから生成するため完全なproduction replayではない。優先度制御はGPU スループット自体を増やさないので、小バッチ・高負荷でqueueが厚い条件ではFCFSより悪化する例がある。短いjob優先は長いjobのstarvationを招き得る。preemption policyは実装されるが実トレースで必要頻度が低いとして詳細評価されず、KV キャッシュ切替コストが高い環境での効果は未確定である。
## 実装状態
Samsung SDS Cloud Research TeamによるPython約3.1K行のprototype。vLLM 0.5.0へ100行未満の変更を加え、Kubernetes frontend/backend pod、StatefulSet、Serviceとして実装されている。論文はpublic codeとYAML公開を明記するが、今回確認した一次資料から確実なrepository URLは取得できなかった。
## 研究上の位置づけ
LLM serving スケジューラ研究の中で、モデル実行カーネルやKV配置そのものではなく『将来の残りデコード量を意味理解モデルで推定し、continuous batchingの順序へ反映する』予測駆動型の系統に属する。特に一回予測ではなく生成途中で予測を閉ループ更新し、Kubernetes/vLLMの実装・実サービス由来到着分布・50 GPU規模のscale-outまで接続した点で、アルゴリズムとproduction orchestrationの橋渡しをする研究である。
