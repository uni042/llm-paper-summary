# Hybrid SLM and LLM for Edge-Cloud Collaborative Inference：端末とクラウドで生成トークンを分担する

## 概要

端末で動く小型言語モデル（Small Language Model、SLM）は低費用で応答できるが、数学やコード生成などではクラウド上の大型言語モデル（Large Language Model、LLM）より正答率が低い。入力要求ごとに小型・大型モデルのどちらかを選ぶだけでは、一つの回答の中にある「小型モデルで十分なトークン」と「大型モデルによる修正が必要なトークン」の混在を利用できない。本研究は、端末側で短い草稿を作り、クラウド側で草稿中のトークンをまとめて検証することで、品質と計算費用の間の連続的な選択肢を作る。

端末SLMは10トークンを自己回帰生成し、その草稿をクラウドLLMへ送る。LLMは確定済み文脈と草稿を一度に処理し、各草稿位置でLLM自身がそのトークンへ割り当てる条件付き確率を求める。確率が閾値を下回る最初の位置で草稿の受理を止め、LLMが新たなトークンを一つ生成する。確定した接頭辞と修正トークンを端末へ返し、次の草稿を再生成する。これを終了トークンまで繰り返す。

GSM8KではLlama-2-7B単独の正答率21.68%、70B単独53.07%に対し、対数閾値−0.5の協調方式は52.24%を達成した。原著の代理計算費用は70B単独を10とすると3.250であり、品質が近い条件で大型モデルの呼び出しを減らせる。ただし、この費用はモデルの規模と順伝播回数に基づく値で、実際の端末・クラウド間の通信遅延、料金、消費電力を測定した値ではない。

## 問題設定と着眼点

従来の端末・クラウド協調には、単一モデルの層を分割して実行する方法と、要求の難易度で小型モデル・大型モデルを振り分ける方法がある。層分割では自己回帰生成の各トークンで中間表現を送る必要があり、ネットワーク往復時間が積み重なる。要求単位の振り分けでは、難しい要求の一部だけを大型モデルで修正する機会を逃す。小型モデルは単独動作できる利点があるため、常時クラウドへ丸投げする構成は端末資源を活かしにくい。

原著は多文書質問応答で、小型7Bが不正解、大型70Bが正解となる449例を抽出し、小型モデルが生成したトークンのうち少数だけを大型モデルのトークンに置換する事後的な上限分析を行う。最適な位置を後から探索できるなら、1トークン修正で120例以上、3トークン修正で約75%を正答へ導けるという。生成系列は約10〜100トークンである。これは実運用のアルゴリズムが修正位置を事前に知っているという意味ではなく、**少数の重要な誤りが回答全体を壊している可能性**を示す上限実験である。

では、誤りのある位置を実行時にどう発見するか。SLM自身の最大確率や出力分布のエントロピーでは、SLMが高い確信を持って誤る位置を検出できない。そこで、草稿をLLMに評価させ、LLMが草稿トークンへ付ける条件付き確率を利用する。原著図3では、SLMが生成したトークンのLLM評価確率は0付近と1付近に集中するU字状の分布を示す。確率が極めて低いトークンを修正候補とすることが、手法の直接の動機である。

## 手法

### 草稿生成、検証、修正、再開の一連の処理

### 1. 端末側で10トークンの草稿を作る

端末側のモデル `M_S` は、既に確定したプロンプトと出力接頭辞 `c` を受け取り、次の `k=10` トークン `x_1,...,x_k` を自己回帰生成する。端末は各トークンの生成にSLMの順伝播を必要とする。10トークンは一度に確定する出力ではなく、あくまでLLMの検証を受ける草稿である。端末とクラウドが同じトークナイザを使う場合、草稿は中間層の巨大な活性値ではなくトークンIDで送信できる。

ここで重要なのは、クラウドLLMが確定済み文脈を知っている必要があることだ。草稿IDだけを送れば常に済むというわけではない。初回要求のプロンプト共有、修正済み接頭辞の同期、クラウド側の鍵値キャッシュ管理は別途必要となる。原著の主評価は、この通信処理を実運用のネットワーク遅延として計測したものではない。

### 2. クラウドで各位置の条件付き確率を並列に計算する

クラウド側モデル `M_L` は確定文脈と草稿をまとめて入力し、各草稿位置に対応する確率分布 `p_1(x),...,p_k(x)` と、草稿末尾の次位置の分布 `p_{k+1}(x)` を一回の順伝播で得る。因果的な注意機構を使うため、各位置の確率はその位置より前の文脈だけに条件付けられる。検証に必要なのは各位置で実際にSLMが提案したトークン `x_i` の確率 `p_i(x_i)` である。

この並列検証は、10トークンを70Bモデルで10回逐次生成することとは異なる。草稿が既知であるため、LLMは全位置の条件付き確率をまとめて評価できる。ただし検証一回にも70Bの順伝播が必要であり、草稿の採用数が少ないと大型モデルの呼び出し回数は増える。並列化の利点と、端末側で破棄される草稿の費用の双方を考える必要がある。

### 3. 最初の不採用位置で切り、LLMから一つ補正する

確率閾値 `p_t` を決め、先頭から `p_i(x_i)>p_t` を満たすトークンを受理する。最初に `p_i(x_i)≤p_t` となった位置で走査を止め、そこでLLMの分布から一つの新しいトークンを生成する。受理接頭辞の長さを `τ` とすると、確定する系列は `x_1,...,x_τ` とLLM生成トークン `x^g_{τ+1}` である。草稿の後ろにどれほど高確率の候補が残っていても、前の位置で修正が入れば後続の条件付き分布が変わるため、そのまま採用しない。

原著のAlgorithm 1は、この確定トークンを端末へ返して文脈 `c` に追加し、次の草稿を生成するまでを定義する。草稿の全位置が受理される場合にも、末尾の `p_{k+1}` からLLMが一つ追加トークンを出す。したがって1回のクラウド検証で確定するのは、受理した草稿接頭辞とLLMが新規生成した一つである。EOSに達するか出力長上限に達するまでこの手続きを反復する。

### 4. 閾値は品質と費用の調整つまみになる

閾値を高くすると、LLMが少しでも不自然と判断した草稿を早期に棄却しやすくなる。大型モデルの生成へ近づく一方、LLM検証回数とSLMの草稿再生成が増える。逆に閾値を低くすると草稿の多くが残り、計算費用は下がるが、小型モデルの誤りも残りやすくなる。原著は `log10(p_t)` を−0.5から−4まで0.5刻みで変え、品質と代理計算費用の曲線を描いている。

この方法は標準的な投機的標本抽出（Speculative Sampling）と同じく草稿と検証を使うが、**大型モデルの出力分布を厳密に保存する方式ではない**。標準方式は目標分布を維持する受理・補正則を使うのに対し、本研究はLLMが草稿トークンへ与えた絶対確率と閾値で受理を決める。出力品質と費用の実務的な調整が目的であり、確率分布の厳密同一性を要求する用途へ無条件に適用してはいけない。

### 5. コスト式が何を数えているか

原著の代理費用は `C = c_s N_s/T + c_l N_l/T` である。`N_s` と `N_l` はそれぞれSLM・LLMの順伝播回数、`T` は最終出力トークン数である。モデル規模を近似する係数は70Bで10、7Bで1、1.1Bで0.167に設定される。小型モデルの草稿が捨てられた場合、`N_s/T` が1を超えることもある。逆にLLMは一度の検証で複数トークンを確定できるため、`N_l/T` を1未満に抑えられる。

これはGPU秒、実課金、電力、ネットワーク転送量、端末の電池消費を直接計測する費用式ではない。70Bと7Bのパラメータ数の比から単純化した代理尺度であり、実機のメモリ帯域、量子化カーネル、連続バッチ処理、ネットワークRTTで費用順位が変わり得る。費用比を運用コストの実測値として表現しないことが再監査の重要点である。

閾値を−4まで下げると費用は1.999へ下がる一方、正答率は28.20%まで低下する。これは単純にクラウド呼び出しを減らせば常に良いという話ではなく、**品質を犠牲にして費用を削る領域がある**ことを示す。−0.5のSLM順伝播/確定トークンは1.606で、破棄された草稿の再生成が追加費用になることも読み取れる。LLM順伝播/確定トークン0.164は、複数トークンを一度に検証できた効果を反映している。

### 他タスク、異種モデル、上限分析との区別

HumanEvalではコード生成のpass@1、NaturalQuestionでは質問応答の完全一致を用いる。著者は、70B単独に近い品質での代理費用がそれぞれ31.2%と27.2%になると述べる。GSM8Kの25.8%も同じ総括に並ぶが、タスクごとに品質指標と曲線形状が異なるため、3値を同じ正答率や同じ閾値で得たものと解釈しない。原著図4は、閾値を変えると各タスクで品質が変化することを示し、図5は品質と代理費用の関係を示す。

TinyLlama-1.1B単独のGSM8K正答率は3.71%であり、単独では数学推論がかなり難しい。それでも70Bとの協調で品質を改善できることから、SLMとLLMが同じモデル系列・学習データを共有しなければ機能しないという制約は弱い。ただし、著者は異なる学習データで訓練されたすべてのモデル組合せを実証していない。トークナイザの共有は実装上重要であり、任意の異種トークナイザ間で同じ手法をそのまま使えるわけではない。

449例の事後的な最適修正位置の探索は、実際の閾値法より有利な上限評価である。1〜3トークンの置換で多くの誤答を救えるという観測は、修正すべき位置を正しく見つけられた場合の可能性を示す。実方式ではLLMの確率を使って位置を推定するため、上限の「3トークン修正で約75%」を本番の保証精度として扱ってはならない。修正した後の文脈でSLMが再生成する費用も必要である。

## 先行方式との差と運用上の含意

層分割推論では各トークンの中間活性を端末とクラウド間で転送する。本方式は独立したSLMとLLMを用い、同じトークナイザを共有できれば主にトークンIDを交換するため、巨大な中間テンソルの転送を避けられる。要求単位のモデルルーティングと違い、一つの回答内でクラウドの利用率を調整できる。標準的な投機的復号と似た草稿・検証の枠組みだが、LLM出力分布の厳密保持よりも品質と代理費用の交換条件を重視する。

端末側のSLMはネットワークが使えないときも単独で動けるため、クラウドが不通になった場合に応答を継続できる。一方、クラウド側は草稿を検証するたびに大きなモデルを実行する必要がある。端末とクラウドの往復時間が長い環境、草稿受理率が低いタスク、端末側の演算が高価な条件では、実時間の利得が小さくなり得る。適切な閾値は予算、タスク、ネットワーク条件によって異なるはずだが、原著は閾値を自動最適化する仕組みを実装していない。

## 限界と負の結果

原著自身は、SLM単独と比べて遅延が改善しない可能性を明示する。草稿生成、クラウド検証、修正トークンの転送、破棄後の再生成があるため、LLMの順伝播回数が減ることと、利用者が感じる応答時間が短いことは同義ではない。特に端末とクラウドが離れている場合のネットワーク往復時間、帯域制約、接続失敗、複数要求の同時処理を含む端から端の評価が必要である。

クラウドへプロンプトと草稿を送るため、プライバシー保護は未解決である。端末内で完結する方式ではない。モデルの出力分布を厳密に保つ補正則ではないので、LLM単独との統計的同一性を必要とする場合は別の受理方式が必要になる。閾値はタスクごとに実験的に選んでおり、品質・費用の予算を入力すると自動で最適値が決まるわけではない。

原著の費用係数はモデル規模に比例させた代理値であり、実クラウド課金や電力消費を測定していない。4ビットGPTQモデルを用いたという事実から、実機の通信込みの高速化倍率やメモリ削減率を導いてはならない。端末SLMが誤った草稿を長く生成してしまう条件では、`N_s/T` が大きくなり、低費用化が弱まる。研究は原著時点でシステム統合の途上であり、大規模な本番サービスでの再現性を保証するものではない。
