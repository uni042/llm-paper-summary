# Hybrid SLM and LLM for Edge-Cloud Collaborative Inference — 端末・クラウド間の確率閾値付き草稿検証

## 書誌情報と研究の位置付け

Zixu Hao、Huiqiang Jiang、Shiqi Jiang、Ju Ren、Ting Caoによる2024年のEdgeFMワークショップ論文（ACM DOI:10.1145/3662006.3662067、全6ページ）。対象は端末（edge）に小型言語モデル（small language model; SLM）を置き、クラウド（cloud）に大型言語モデル（large language model; LLM）を置く場合の**推論品質と計算費用の協調制御**である。学習済みモデル自体の変更や追加学習を前提とせず、生成トークンと確率を用いて両者を連携させる。

本文は著者の学会掲載原稿の再掲全文を確認し、出版社DOIと書誌情報を照合した。出版社のPDF配信にはアクセス制約があるため、再掲本文と出版社書誌を区別して出典を示す。

## 概要

単に難しいプロンプトだけクラウドへ送る方式では、1つの応答中に「小型モデルで十分なトークン」と「大型モデルによる修正が必要なトークン」が混在することを活用できない。そこで端末側SLMが短い草稿を自己回帰生成し、クラウド側LLMが**一回の順伝播で草稿中の各トークンの条件付き確率**をまとめて算出する。クラウドモデルから見て確率の低いトークンに遭遇したら、その位置からクラウドモデルの出力へ切り替え、修正後の文脈を端末へ戻す。

Llama-2-7B-chat単独ではGSM8K正答率21.68%、Llama-2-70B-chat単独では53.07%。草稿長10・受理閾値の対数が−0.5の協調方式では52.24%となり、原著の**モデル呼び出し回数×モデル規模に基づく相対費用**は70B単独10に対して3.250となる。著者らはタスク別の品質相当点で70B単独費用の25.8%（GSM8K）、31.2%（HumanEval）、27.2%（NaturalQuestion）を報告する。ただし、これはネットワーク遅延や実クラウド課金を測定した費用ではない。

## なぜトークン単位の協調が必要か

従来の端末・クラウド分割推論では、一つのニューラルネットワークの中間層を別の場所へ分ける。自己回帰生成ではトークンごとに両拠点を往復する必要があり、通信が遅延要因となる。プロンプト全体を小型・大型モデルのどちらかへ振り分ける方式では、同一応答中の難易度差を捉えにくい。

原著はまず多文書質問応答のうちSLMが失敗しLLMが成功する**449例**を取り出し、SLMの出力中のどのトークンをLLMに修正させれば正答へ近付くかを調べた。正しい修正位置を後から探索する上限分析では、1トークンの修正で120例以上を救える場合があり、3トークンの修正で約75%の例を正答へ導けるという。出力は約10～100トークンの範囲である。これは**事後的に最適修正位置を選ぶ上限分析**であり、実運用の閾値選択で常に3トークンだけ直せば75%正答になることを意味しない。

SLM自身の最大確率やエントロピーで難しい位置を判定すると、SLMが高い自信で誤るトークンを見逃す。そこで著者らはLLMがSLMの草稿トークンへ割り当てる確率 $p_L(x_i\mid c,x_{<i})$ に着目する。この確率の分布は0付近と1付近に多いU字型を示し、LLMから見て極端に不自然な草稿トークンを検出しやすい。

## アルゴリズムの具体的な処理

### 1. 端末で草稿を生成する

端末側の小型モデル $M_S$ は現在の確定文脈 $c$ に対し、$k=10$ トークン $x_1,\dots,x_k$ を自己回帰生成する。草稿と必要な文脈をクラウドへ送る。端末側で生成したトークン列は、そのまま最終出力として確定したわけではない。

### 2. クラウドで全位置の分布を並列検証する

クラウド側の大型モデル $M_L$ は、確定文脈と草稿をまとめて入力し、各草稿位置における次トークン確率分布 $p_i(\cdot)$ と、草稿末尾に続く追加位置の分布 $p_{k+1}(\cdot)$ を一度の順伝播で得る。各位置について草稿トークン $x_i$ の確率 $p_i(x_i)$ を評価する。

### 3. 閾値で最長受理接頭辞を決める

確率閾値 $p_t$ を設け、先頭から $p_i(x_i)>p_t$ を満たす草稿を受理する。最初に $p_i(x_i)\le p_t$ となった位置で草稿の受理を停止する。受理したトークン数を $\tau$ とし、次位置 $\tau+1$ ではLLMの分布から新しいトークンを生成する。これを端末へ返し、端末は修正後の確定文脈から次の草稿を再生成する。

閾値が小さいほどSLM草稿を受理しやすく、クラウド側の修正頻度が減る一方で、SLMの誤りを残すリスクが高まる。閾値が大きいほどクラウドLLMの出力へ早く切り替わり、品質が向上するが費用も増える。原著は $\log_{10}p_t$ を−0.5から−4まで変えて、この品質・費用曲線を測る。

### 4. 通常の投機的復号との相違

標準の投機的標本抽出（speculative sampling）は、正しい受理・補正則により**目標モデルの出力分布を厳密に保つ**ことを目指す。これに対し本研究の単純な確率閾値則は、LLMの条件付き確率が十分高い草稿を残すという品質・費用上の近似であり、**LLM単独と厳密に同一の出力分布を保証するものではない**。同じ草稿検証の構造を使うが、最適化目標が異なる。

## 評価環境と費用指標

| 項目 | 原著の条件 |
|---|---|
| 端末側モデル | Llama-2-7B-chat、TinyLlama-1.1B |
| クラウド側モデル | Llama-2-70B-chat |
| 重み形式 | Llama系列に4ビットGPTQ量子化版を使用 |
| 草稿長 | 10トークン |
| 閾値 | $\log_{10}p_t\in\{-0.5,-1,-1.5,-2,-2.5,-3,-3.5,-4\}$ |
| タスク | GSM8K（正答率）、HumanEval（pass@1）、NaturalQuestion（完全一致） |
| デコード | HumanEvalは温度1の標本抽出、それ以外は温度0の貪欲生成 |
| 実装基盤 | Hugging Face Transformers、PyTorch 2.0.1、CUDA 11.7 |
| 費用 | 出力トークン当たりのモデル順伝播回数にモデル規模ベース係数を掛けた値 |

費用は $C=c_s N_s/T+c_l N_l/T$ と表す。$N_s,N_l$ は端末SLM・クラウドLLMの順伝播回数、$T$ は最終出力トークン数であり、係数は70Bに10、7Bに1、1.1Bに0.167を割り当てる。端末とクラウドの**実測電力、実時間、ネットワーク料金、GPUの同時処理効率**を反映するものではない。再生成によりSLMの順伝播回数が出力トークン数を超えることもあり、表中の $N_s/T$ が1を超える点が重要である。

## 主要結果

### GSM8K：7Bと70Bの組合せ

| $\log_{10}p_t$ | GSM8K正答率（%） | SLM順伝播/出力トークン | LLM順伝播/出力トークン | 相対費用 $C$ |
|---:|---:|---:|---:|---:|
| 7B単独 | 21.68 | 1.000 | 0 | 1.000 |
| 70B単独 | 53.07 | 0 | 1.000 | 10.000 |
| −0.5 | **52.24** | 1.606 | 0.164 | **3.250** |
| −1.0 | 50.49 | 1.453 | 0.149 | 2.941 |
| −1.5 | 47.46 | 1.328 | 0.136 | 2.691 |
| −2.0 | 44.50 | 1.232 | 0.127 | 2.501 |
| −2.5 | 39.73 | 1.146 | 0.118 | 2.329 |
| −3.0 | 35.78 | 1.074 | 0.111 | 2.186 |
| −3.5 | 32.07 | 1.019 | 0.106 | 2.075 |
| −4.0 | 28.20 | 0.981 | 0.102 | 1.999 |

70B単独の正答率53.07%に対して、最も厳しい閾値の協調方式は52.24%で、**0.83ポイント低い**。この近い品質を相対費用3.250、すなわち70B単独の**32.5%**で得た。論文の要旨にはGSM8Kで25.8%の費用で「同等品質」との記述があるが、表2の52.24%の行から算出できる値は32.5%である。**要旨の25.8%と表2の32.5%は評価点・比較条件が異なる可能性があり、同一実験点として混同しない**。

閾値を−4まで下げると費用は1.999まで減るが、正答率は28.20%へ低下する。安価にするほど品質が落ちるという負の結果も明瞭である。また−0.5ではSLM順伝播/出力トークンが1.606であり、**確定しなかった草稿の再生成**が端末計算を増やすことを示す。

### 他タスク・異種小型モデル

著者らはHumanEvalのpass@1とNaturalQuestionの完全一致でも、閾値を厳しくするほど大型モデルの品質へ近づく傾向を報告する。品質相当点での推定費用比としてHumanEval 31.2%、NaturalQuestion 27.2%を挙げる。GSM8KではTinyLlama-1.1B単独の正答率は3.71%に留まるが、70Bとの協調により大幅に改善する。これは端末SLMとクラウドLLMが同一の学習データ・重み初期化を持つ必要がないことを示唆するが、全ての異種モデル組合せを網羅したわけではない。

### 上限分析と実方式の区別

449例の事後的なトークン置換上限分析では、数トークンの訂正で多くの回答を救える。しかし実方式はどの位置が誤りかを事前に知らず、LLMが付ける確率と閾値で判定する。したがって上限分析の「3トークン訂正で約75%」は、表2の協調推論正答率と直接対応しない。モデルが確信を持って誤るトークンを見落とす問題は、端末SLM自身の不確実性だけで選別する方式の限界として説明される。

## 実装・運用上の利点と制約

同一のトークナイザを共有できれば、端末とクラウド間で中間層の大きなテンソルを送る必要がなく、草稿トークンIDと確定した修正トークンをやり取りできる。ただし**クラウドが検証するために必要な確定文脈の共有・維持**は必要であり、単純に「通信量はトークンIDだけだから常に低遅延」とは言えない。クラウド側のKVキャッシュ管理、ネットワーク往復時間、同時要求時の検証バッチングが実システムの費用を左右する。

本方式はLLMに追加学習を要求せず、端末で単独動作できるSLMを保持できる。クラウド接続がなくてもSLM単独で応答を続けられることは運用上の利点である。他方、厳密なLLM出力分布の保持を保証しないため、同じLLM品質が必要な高信頼用途では確率閾値と品質検証を別途設計しなければならない。

## 限界・負の結果

1. **低遅延化の保証がない**：著者ら自身が、SLM単独と比べるとLLMへの追加問い合わせとSLMの草稿破棄・再生成で遅延が増える可能性を認める。原著の費用はモデル規模ベースの代理指標であり、通信込みの実時間計測ではない。
2. **プライバシーは未解決**：クラウドへ文脈や草稿を渡す設計であり、端末内の個人情報保護を研究目的としていない。ローカル処理だけで完結する方式ではない。
3. **同一トークナイザの要件**：端末とクラウドで同じトークンID列を共有できることが前提。異なるトークナイザ間の整列は原著のアルゴリズムに含まれない。
4. **閾値は手動掃引**：予算や通信状況に応じて最適閾値を自動設定する適応制御は今後の課題。固定閾値がすべての入力難易度に最適とは限らない。
5. **推定費用と実課金の乖離**：費用係数はモデルのパラメータ規模から決めており、量子化実装、GPU稼働率、クラウド料金、ネットワーク費用、バッチングによる変動を含まない。
6. **システム完成度**：著者らはシステム統合を継続中と記載しており、大規模な実運用サービング基盤の完成・本番実証を報告する論文ではない。
7. **正確な出力分布を保持しない**：受理閾値に基づく修正は近似的な品質制御であり、標準の投機的標本抽出と異なり目標モデルの分布保存を保証しない。
