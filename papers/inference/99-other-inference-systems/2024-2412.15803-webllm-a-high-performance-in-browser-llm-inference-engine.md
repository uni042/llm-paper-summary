# WebLLM：ブラウザの制約内でネイティブに近いLLM推論を行う実装

## 概要

WebLLMは、利用者が専用のネイティブ推論ソフトウェアを導入しなくても、対応するWebブラウザと端末GPU上でオープンウェイトの言語モデルを実行できるようにするJavaScript推論基盤である。画面から呼び出すAPI、ブラウザのワーカースレッド、GPU計算、CPU側の補助処理、事前コンパイル済みのモデル実行物を一体化している。新しい注意機構や学習アルゴリズムではなく、ブラウザで効率的な言語モデル実行を成立させるシステム統合が主要な貢献である。

原著v2の表1では、Apple M3 Maxの同一端末上で4ビット量子化されたLlama-3.1-8Bを動かしたとき、WebLLMは41.1 token/s、ネイティブのMLC-LLMは57.7 token/sである。Phi-3.5-mini 3.8Bでは71.1対89.3 token/sであった。ブラウザ版はネイティブ版より遅いが、復号処理率の約71.2～79.6%を保持した。著者が「最大約80%」と述べるのはこの後者の条件に対応する。初回モデル取得、入力事前処理、サーバ負荷、応答全体の遅延まで80%という主張ではない。

## 問題設定

一般的なローカル推論エンジンは、CUDAやMetalなどOS・GPUごとの実行環境を必要とする。利用者がソフトウェアを導入する方式は柔軟だが、WebアプリのようにURLから即座に利用できる配布方法とは異なる。ブラウザは端末をまたいで同じ画面とAPIを提供できる反面、GPUへ直接CUDAカーネルを投入できず、WebGPUの標準化された演算機能とJavaScriptの実行制約を受ける。さらにGPUの行列積だけでなく、トークン化、文法制約、キャッシュ管理、生成時のサンプリングなどCPU側の仕事も残る。

単にTransformerをJavaScriptへ移植しても、低ビット行列積、注意のタイル化、KVキャッシュの再利用といった高性能推論の要件は満たしにくい。特にPagedAttentionは生成中のキャッシュを細かいページで管理するため、GPU上の計算とCPU側の割当管理を連携させる必要がある。FlashAttention系の処理も、GPUメモリからの読み出しと行列積の順序を制御する専用カーネルが重要である。WebGPUに汎用の高性能LLM演算ライブラリが十分存在しないことが課題になる。

ブラウザの主スレッドで大量の計算を同期的に行うと、画面の入力やスクロールが止まる。さらに初回アクセス時にはモデルの重みやコンパイル済み実行物のダウンロードが必要で、再アクセス時のキャッシュと初回ロードの区別が欠かせない。WebLLMはこのようなGPU・CPU・UI・配布の制約を一つの推論基盤で扱う。

## 手法

### 1. APIと画面処理の分離

フロントエンドは軽量なServiceWorkerMLCEngineを通じて、OpenAI形式に近いチャット補完要求を渡す。JSON形式の入力を受け取り、生成結果を逐次応答として返すため、アプリケーション側は既存の会話画面や文書処理に組み込みやすい。生成の中核であるMLCEngineはワーカースレッド側で動作し、フロントエンドとメッセージを交換する。これによりGPU処理を起動する重い仕事が画面のイベントループを直接占有しない。

原著は、制約付きJSON生成や文脈自由文法を用いる構造化出力、画像を入力する視覚言語モデル、複数モデルのロードといったAPI上の機能も示す。これらはWebLLMの利用可能な機能であるが、すべての機能が表1の復号性能評価に含まれるわけではない。APIの形式が似ていても、クラウド側の認証、課金、負荷分散、分散実行を同等に備えることは意味しない。

### 2. WebGPUによる計算の移植

GPU側の行列演算と注意計算にはWebGPUを用いる。WebGPUは複数のGPUベンダの実装に共通する抽象化を提供し、ブラウザが対応するGPUへ計算を送れるようにする。ここで重要なのは、WebGPUを呼ぶだけでは言語モデル用の高速カーネルが揃わないことである。WebLLMはMLC-LLMとApache TVMのコンパイラを使い、モデルの計算グラフからWebGPU向けの実行カーネルを生成する。

コンパイラは演算子の融合や行列積のタイル分割を適用し、GPUメモリと計算器の利用効率を高める。PagedAttentionやFlashAttentionに相当するモデル実装の計算も、WebGPU向けのカーネルへ変換する。この構成はモデルごとの実装をブラウザ内でゼロから書き直す方式とは異なる。生成されたカーネルが実際に効率よく動くかは、モデルの形状、GPU、ブラウザのWebGPU実装に依存する。

### 3. WebAssemblyによるCPU側処理

GPUカーネルの起動だけで推論は完結しない。入力・出力の管理、生成のための状態更新、文法制約の処理、ページ化されたKVキャッシュの列管理、テンソルの補助操作などはCPU側の計算を必要とする。WebLLMは既存のC++実装をEmscriptenでWebAssemblyへコンパイルし、JavaScriptから呼び出す。これにより、JavaScriptだけで全処理を再実装せずにMLC-LLM側の既存実装を再利用できる。

この分業は、CPU処理をなくすという意味ではない。CPUとGPUの同期、ワーカースレッドとのメッセージ、ブラウザの実行制限などの付加費用は残る。性能比較でブラウザがネイティブより遅い理由を、単一の原因だけに帰属させることは原著の表からはできない。

### 4. 事前コンパイルとモデル配布

モデルの計算をブラウザで毎回ゼロからコンパイルするのではなく、MLC-LLMは事前にモデル重みを変換し、GPUカーネルとCPU側のWebAssembly処理を含む実行ライブラリを作る。WebLLMは公開されたモデル実行物をロードして推論する。モデルの構造や量子化形式に応じて対応する成果物を準備する必要があり、任意の未対応モデルをその場で自動的に実行できるという保証はない。

事前コンパイルにより実行時の大規模なコンパイル作業を避けられる一方、モデルごとの配布物の管理とブラウザ側のキャッシュが運用上の課題になる。初回アクセス時のダウンロード、モデルロード、GPUメモリへの配置は、表1にある定常復号のtoken/sと別の指標である。ローカル実行でプロンプトを外部の推論APIへ送らないことは可能だが、モデルファイルやアプリケーションコードをどこから取得するかは別途検証しなければならない。

### 5. 一要求の実行経路

利用者がチャットを送信すると、画面側エンジンが要求をワーカーへ渡す。ワーカーは入力をトークン化し、モデル重みとキャッシュを準備し、入力列の事前処理を実行する。生成段階では過去の鍵・値をキャッシュから再利用しながら次トークンを計算し、CPU側で必要なサンプリングや制約処理を行う。得られたトークンは逐次メッセージとして画面へ戻される。画面側は生成が続いている間もユーザ操作を受け付けられるよう設計される。

この経路でGPU計算はWebGPU、CPU側の性能が重要な部分はWebAssembly、制御とAPIはJavaScriptが担う。WebLLMは複数の技術を接続することによりブラウザの機能制限を補うが、ブラウザの停止・タブの破棄・端末の省電力制御・GPUメモリ不足などの運用条件を消すものではない。

## 評価

### 比較条件と主要数値

原著v2の第3節と表1では、Apple MacBook Pro M3 Maxで、ブラウザ版WebLLM v0.2.75とネイティブMLC-LLM commit d23d6f5を比較する。ブラウザはChrome Canary 133.0.6870.0のarm64版で、JavaScript、WebAssembly、WebGPUを使う。ネイティブ版はPython/C++とMetalカーネルで動作する。両方式の対象モデルは4ビット量子化されたLlama-3.1-8BとPhi-3.5-mini 3.8Bである。

| 項目 | 条件 |
|---|---|
| 端末 | Apple MacBook Pro、M3 Max |
| ブラウザ | Chrome Canary 133.0.6870.0、arm64 |
| ブラウザ実装 | WebLLM v0.2.75、WebGPU/WebAssembly/JavaScript |
| 比較対象 | MLC-LLM commit d23d6f5、Python/C++/Metal |
| モデル | Llama-3.1-8B、Phi-3.5-mini 3.8B |
| 精度形式 | 4ビット量子化 |
| 指標 | 復号処理率（生成トークン数/秒） |

| モデル | WebLLM | ネイティブMLC-LLM | ブラウザ保持率 | 差分 |
|---|---:|---:|---:|---:|
| Llama-3.1-8B | 41.1 token/s | 57.7 token/s | 71.2% | 16.6 token/s遅い |
| Phi-3.5-mini 3.8B | 71.1 token/s | 89.3 token/s | 79.6% | 18.2 token/s遅い |

保持率は同一モデルについてWebLLMの処理率をネイティブMLC-LLMの処理率で割った値である。Llamaの41.1/57.7は約0.712、Phiの71.1/89.3は約0.796となる。従って「最大約80%」は二モデルのうち速い保持率を示したPhiの値である。WebLLMがネイティブの1.8倍高速といった解釈はできない。表は単一端末・二モデルの復号段階に限定される。

### 評価から言えること

WebGPUとWebAssemblyを使うブラウザ実装でも、対応端末ではネイティブに対して7～8割程度の復号処理率を維持できる。これはブラウザ上での高性能推論が実用上の選択肢になり得るという証拠である。しかしベンダ横断性はAPI設計上の利点であり、WindowsのNVIDIA GPU、AMD GPU、スマートフォン、別のブラウザについて同じ保持率を実測したわけではない。量子化形式やモデル規模を変えた場合の性能もこの表だけでは予測できない。

原著は入力の事前処理時間、最初のトークンまでの時間、複数要求の同時実行、p95遅延、初回モデルダウンロード、キャッシュのヒット率、ブラウザのメモリ上限を網羅的に測っていない。アプリ全体の待ち時間と復号処理率は別の指標であり、短い応答ではモデルロードや入力処理が支配的になり得る。論文の表にない数値を推定で補わないことが重要である。

### 資源・品質・費用の交換条件

ブラウザで推論を行うと、クラウド推論の利用料金や送信するテキスト量を減らせる可能性があるが、端末側でGPUメモリと電力を消費する。モデル重みをダウンロードする通信費用やストレージ、端末間の互換性、アプリケーションの保守は残る。原著はそれらの総所有コストを定量比較していない。WebLLMはモデルを変える近似手法ではないが、4ビット量子化モデルを評価しているため、元の高精度モデルとの品質差を論文の速度表から読み取ることもできない。

### 実装と既存研究との差

llama.cppやネイティブMLC-LLMはOSのGPU APIを利用し、ブラウザの制約を受けない。WebLLMはMLC-LLM/TVMのコンパイル技術をブラウザのWebGPUとWebAssemblyへ移植し、APIとワーカーを組み合わせて配布容易性を高める。通常のJavaScript実装との差は、モデル固有のGPUカーネルを事前に生成し、低ビット推論とキャッシュ管理を含む実行系を再利用できる点である。

## 限界と実装状況

この研究はブラウザ内でのLLM推論が可能であることを実装と同一端末の測定で示した。しかし二つのモデル、M3 Max、Chrome Canaryの一構成が中心であり、一般のGPUベンダやOS、長文脈、同時多数要求の性能を証明したものではない。ブラウザ側のGPU対応状況、モデルの事前コンパイル、初回ダウンロード、キャッシュ、メモリ容量、タブの寿命などに依存する。ローカルで推論するため入力をクラウド推論APIへ送らずに済む一方、モデル配布元・拡張機能・アプリケーションコードの安全性までは本論文の測定対象ではない。

原著は公開実装のURLを示しているが、公開コードの最新バージョンと論文で測定したWebLLM v0.2.75は同一ではない場合がある。研究の数値を再現する場合はモデル形式、コンパイル成果物、ブラウザ版、端末構成を固定する必要がある。将来のWebGPUの進歩でネイティブとの差が縮まる可能性はあるが、その改善幅を現行の表から予測できない。

## 原著の構成図と性能表を結び付けた検証

原著の図1は、利用者が操作する画面側の軽量な入口、別スレッドで実行される言語モデル本体、事前生成された演算実行物の三層に分かれている。この分離は、モデル計算が終わるまで画面全体を停止させないという応答性の要件に対応する。一方、実際の演算を高速化するのは三層目のコンパイル済み実行物である。画面と演算を分けるだけでは、行列積や注意計算の処理率は上がらない。逆に演算だけを高速化しても、画面側で同期的に生成結果を待つ設計なら利用者の操作性は損なわれる。二つの役割を区別することが、この研究を単なる推論カーネルの論文と誤読しないために重要である。

また、図1の事前生成物は変換済み重みと実行ライブラリから構成される。利用者がアクセスした後の処理は、これらを取得し、端末の実行環境でロードしてから生成を始める。従って定常復号の速度表には、事前生成物を準備する開発側の費用も、初回にそれを受け取る利用者側の待ち時間も含まれていない。配布容易性という主張と、初回応答の短さという主張は同一ではない。大量のモデルを切り替えるサービスでは、端末の記憶容量と再ロード費用が別途問題となる。

表1の二モデルは同じ端末を使っているが、モデルの大きさと演算特性が異なる。約八割という保持率を単一のハードウェア性能係数とみなすことはできない。基盤モデルや量子化形式を変えた際には、行列積の形状、生成時に保持する鍵と値の容量、CPU側の補助処理の割合が変わり得る。ブラウザとネイティブの差は、これらの条件ごとに改めて測定する必要がある。原著は性能保持の実例を示しているのであって、すべての端末で一定比率を保証する性能モデルを提案しているわけではない。

## 利用判断に必要な確認項目

この方式を採用する際には、まず対象端末のブラウザが必要な計算機能を提供するかを確認し、次に利用するモデルと量子化形式に対応した事前生成物が配布されているかを確かめる。対応があれば、初回取得と二回目以降の再利用を分けて測定する。続いて入力の長さを変え、最初の応答が返るまでの時間と、応答開始後の生成速度を別々に記録する。長い会話では履歴に伴って鍵と値の記憶領域が増えるため、端末の利用可能容量も観測する。

さらに、同じ端末のネイティブ方式と比較するなら、モデル重み、量子化設定、入力と出力の長さを揃える必要がある。表1の結果は比較条件を固定した研究用の測定値であり、他端末の性能予測値ではない。アプリケーションの安全性を検討する場合は、入力を外部の推論先へ送らないという性質と、配布する実行コードやモデルファイルを信頼できるかという問題を別々に扱う。
