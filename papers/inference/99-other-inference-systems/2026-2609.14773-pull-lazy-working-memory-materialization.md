# Pull: Lazy Materialization of Working Memory for Stateful LLM Conversations

> 長期対話を決定論的な索引で管理し、質問ごとに必要な原文ターンだけを可逆的に実体化して入力トークンを削減するセッションルータ。
## 書誌情報
- **著者**: Jiangang Chen
- **公開**: arXiv:2609.14773
- **種別**: preprint
- **対象**: 長期対話、作業記憶、文脈圧縮、遅延実体化、セッションルーティング
- **実装**: 著者がコードと再現スクリプトを公開しており、論文では実運用のコーディング支援系13個のSWE-bench Proインスタンス、350回超のツールラウンドで統合したと報告する。
## 概要
長期対話で毎回全履歴を再注入すると、1要求あたりの文脈長だけでなくセッション全体の累積転送量が二次的に増え、切り詰めや要約では過去状態を不可逆に失う。本論文は、各ターンをローカルかつ決定論的に注釈した索引として保持し、質問時に必要な原文ターンだけを遅延実体化するセッションルータPullを提案する。LoCoEvalでは単一ホップで75.1%、複数ホップで72.0%の第二段階トークンを削減しながら品質を維持し、百万トークン級BEAM 1Mでは切り詰め基準よりF1を55.2%改善した。

Pullは全履歴を押し込む方式と長期記憶へ退避する方式の間に、セッションルータという第二層を明示し、遅延実体化を中心抽象とする。特徴は、各ターンの索引維持をLLMに任せず、ローカルの決定論的Purifierでエンティティ、状態遷移、分岐、忠実度を更新する点と、原文自体は消さず質問時に選ばれたターンだけを可逆的に展開する点にある。さらにM0の全体位置情報とM10の依存・状態情報を分離し、選択後の因果前件補完を規則処理として組み合わせる。
## 問題設定
長期対話ではターン数Nに比例して各要求の入力文脈が伸びるため、セッション全体で同じ履歴を繰り返し送る累積トークン量は概ねO(N^2)になる。著者の287個のコーディング支援セッションでは原文約2.8億トークンに対し課金対象が55.6億トークンで約19.9倍に増幅していた。一方、Last-Kのような切り詰めは過去の定義や分岐を消し、要約・圧縮は細かな識別子や変更履歴を不可逆に潰す。一般的な検索拡張は断片を検索できても時間的因果やエンティティのライフサイクルを保持しにくい。したがって必要なのは、原文を失わず、質問ごとに必要部分だけを再び作業文脈へ戻せるセッション内の中間記憶層である。
## 新規性
Pullは全履歴を押し込む方式と長期記憶へ退避する方式の間に、セッションルータという第二層を明示し、遅延実体化を中心抽象とする。特徴は、各ターンの索引維持をLLMに任せず、ローカルの決定論的Purifierでエンティティ、状態遷移、分岐、忠実度を更新する点と、原文自体は消さず質問時に選ばれたターンだけを可逆的に展開する点にある。さらにM0の全体位置情報とM10の依存・状態情報を分離し、選択後の因果前件補完を規則処理として組み合わせる。
## 手法
### 手法のあらまし
入力は会話ターン列C=[t1,...,tN]と現在質問qで、目的は全履歴回答との差を許容値内に抑えつつ、回答時に投入する原文集合Sを小さくすることである。第一段階のオンライン注釈では、新しい各ターンをローカルPurifierへ通し、抽出的な約100文字要約、エンティティ集合、情報密度、忠実度、ライフサイクル状態、分岐識別子を計算する。Purifierは約46MBのMiniLM ONNX埋め込み、16個の正規表現、規則ベース状態機械からなり、LLM呼出しを行わない。得られた情報は、全体位置を示すM0ディレクトリと、エンティティの定義・参照・変更・廃止や分岐を示すM10トレースへ分離して蓄積する。保存層は0〜300ターンの活動領域、300〜800ターンの凍結領域、外部アーカイブの三段で、低優先ターンを移しても原文への参照を残す。第二段階の質問時にはSelectorが質問qとM10の構造化行だけを読み、一回のLLM呼出しで関連する初期ターン集合S0を返す。次に決定論的後処理が、S0内のエンティティについて最初の定義ターンを因果前件として最大5件追加し、範囲外番号と重複を除去する。Selector出力の解析に失敗した場合はエンティティ一致とM0類似度へ退避する。最後にAnswererへ、常時見える全M0、選択・補完された原文ターンS、現在質問qを渡して回答を生成する。選ばれなかった原文は削除されないので、後続質問では別の集合を再選択できる。したがって処理の出力は一度作った固定圧縮文脈ではなく、質問ごとに索引から再構成される可逆な作業記憶であり、索引更新費用と高価な回答生成費用も分離される。

### 決定論的PurifierとM0/M10索引
各ターンから関数・クラス定義、snake_caseやcamelCase識別子、URL、日時、数値などを16正規表現・13種の型族で抽出し、初出、参照、変更、廃止の状態を規則で追跡する。M0は各ターン約100文字の抽出的ディレクトリでAnswererが常時読む位置情報、M10はエンティティ依存、状態ラベル、分岐を持つSelector向けトレースである。情報密度は九つの語用・字句信号を手重みで合成し、短文や定型応答には罰則を与える。索引更新をLLM生成から切り離すことで、非決定性とターンごとの高い推論費用を避ける。

### 質問時のSelectorと遅延実体化
Selectorは原文全体ではなくM10と質問を読み、最も関連する3〜5ターンを番号で返す。M10の各行にはターン番号、種別、ファイルパス、最大5個のエンティティ、定義・変更などのライフサイクル印、情報密度、保持率、分岐や話題転換、最後に短い抽摘要約が並ぶ。この順序により、回答モデルへ長大な原文を送る前に構造化索引だけで候補を絞る。選ばれなかったターンは削除も不可逆圧縮もされず、後続質問で再選択できる。M0全体はAnswererへ常に残すため、選択原文だけを孤立して渡す検索方式より会話全体の位置関係を保持しやすい。Selectorは一文の理由とターン番号だけを返し、回答自体は生成しない。出力は範囲検査、重複排除、並べ替えを受け、解析不能時には規則ベース検索へ退避する。さらにSelectorには安価なモデル、Answererには高性能モデルを割り当てられるため、索引を読む費用と回答品質を独立に調整できる。

### 規則ベースの因果カスケード補完
LLMが返した初期集合S0に含まれる各エンティティについて、そのエンティティが最初に定義されたターンを索引から求め、未選択なら因果前件として追加する。推移閉包は取らず一段だけに限定し、追加は最大5ターンに制限するため、依存関係を補いながら文脈膨張を抑える。複数ホップ評価ではカスケードを除くとF1が0.6500から0.6372へ下がり、離れた定義や前提を補う効果が確認された。対して単一ホップでは除去版がわずかに良く、短い依存では余計な補完になり得る。失敗事例Repo-Aでは、ある関数名を起点に連続した無関係ブロックまで展開し、固定された選択予算から本来必要な種ターンを押し出してF1を0.390まで落とした。したがってこの機構は、欠けた因果前件を戻す安全網であると同時に、関連度を考慮しない固定規則が過展開を起こす境界条件も持つ。

### 三層保存と凍結領域
活動領域では0〜300ターンの原文とメタデータを保持し、上限を超えると忠実度、参照回数、内容長、新しさの重みで低優先ターンを凍結領域へ移す。300〜800ターンの凍結領域ではブロック要約、M0/M10メタデータ、アーカイブ参照を残し、さらに古い原文は外部アーカイブへ接続する。質問に関連すると判断されたターンは一時的に保持優先度を上げるため、単純な古い順削除ではない。重要なのは、凍結後も要約だけを最終状態にせず原文への展開可能性を維持する点である。約800ターンへ連結した6会話の検証では、凍結領域に関する質問でPullのF1が0.473、アーカイブを使わない変種が0.030となり、活動領域外の原文へ戻れることが品質に寄与した。外部アーカイブ自体のI/O最適化は本論文の主対象ではないが、第三層の保存先を交換できる設計なので、SSDや遠隔記憶との接続余地を残す。

### 全体のデータ／制御の流れ
オンライン注釈と質問時実体化を時間・計算の両面で分離する。オンライン側はCPU上の軽量決定論処理で索引を更新し、質問時だけSelectorとAnswererの2回のLLM呼出しを使う。活動・凍結・外部アーカイブをOSの記憶階層に対応させ、M0を常時見えるディレクトリ、M10をルーティング表、原文を必要時だけロードする実体として扱う。これにより長文脈モデル、KVキャッシュ最適化、長期記憶とは競合せず、上流で入力トークン自体を減らす補完層として配置できる。
## 評価条件
- **ハードウェア**: Purifierの増分処理はIntel i5-9400F 6コア 2.90GHz、23.4GB RAMで測定。LLM生成・判定はGLM-5、独立判定にはQwen3.7plus、Selector解析にはKimi K2.5も用いるが、API背後のGPU構成は論文では特定されない。
- **ソフトウェア**: Python 3.12.3、約46MBのMiniLM ONNX、正規表現と規則処理でPurifierを構成する。著者はコードと再現スクリプトを公開し、生成・判定は温度0.0で実行する。
LoCoEvalは71個の実リポジトリ由来128会話、12,780ターンで、単一ホップ64会話と複数ホップ64会話を評価する。情報抽出と話題認識を対象にし、関数完成はpytest環境が必要なため除外する。BEAM 1Mは35会話700問のうち話題多様性を制御して14会話263問を選び、700K〜1.8Mトークンの長会話で切り詰めと比較する。さらに60個のSWE-benchトレースを12セッションへ連結し、7,831問で10種類のゼロLLMルーティング法をRecall@10とMRRで比較する。主評価のF1はLLM判定だが、別モデル判定、等価性検定、構成要素除去、距離別解析、失敗事例を併用する。
実CPU上で索引処理遅延を測り、LLM側は商用APIを使ったシステム評価であるため、完全な実機GPUサービング性能比較ではない。対象の中心はコーディング会話で、エンティティ抽出と制御ルーティング評価もSWE-bench由来に偏る。BEAM 1MではM10を使わない簡略Purifierを用い、35会話中14会話のみを評価する。生産導入報告は13インスタンス・350回超のツールラウンドだが対照群を持たない。
## 主要結果
Pullは長期対話の原文を消さずに質問ごとに必要ターンだけを実体化することで、LoCoEvalでは全履歴と同等の回答品質を保ちながら入力トークンを約7割削減した。百万トークン級のBEAM 1Mでは、単なる末尾切り詰めや検索基準より高いF1を示す。構造化ルーティング試験では、単純な密検索やBM25より、時刻・エンティティ・ライフサイクルを順に加えるほどRecall@10が上がり、M10が96.0%に達した。一方で個別失敗例は、遅延実体化そのものではなく、選択に使う索引と因果補完の誤りが品質上限になることを示す。

- LoCoEval単一ホップの第二段階トークン削減 / 75.1% (比較対象: 全履歴注入; 条件: 64会話、GLM-5、情報抽出・話題認識) — F1は0.6694から0.6676で差-0.0018に留まり、±0.05の等価性境界で検定を通過した。

- LoCoEval複数ホップの第二段階トークン削減 / 72.0% (比較対象: 全履歴注入; 条件: 64会話、GLM-5) — Pull F1 0.6500に対し全履歴は0.6326で、依存をまたぐ質問でも削減と品質を両立した。

- BEAM 1M Overall F1 / 0.464（+55.2%） (比較対象: Last-K切り詰め 0.299; 条件: 14会話、263問、700K〜1.8Mトークン、簡略Purifier) — 平均入力64.5Kトークンで、163Kトークンの切り詰めより高品質となり、長大文脈では関連部分の選別が単純な保持量より重要であることを示す。

- 構造化ルーティングRecall@10 / 96.0% (比較対象: RAG-Dense 46.4%、RAG-BM25 55.3%; 条件: 7,831問、60 SWE-benchトレースを12セッションへ連結) — 時刻追加71.3%、エンティティ追加74.1%を経て、ライフサイクルを含むM10でさらに21.9ポイント上昇した。

- Purifier増分処理遅延 / P50 3.22ms/turn、P99 32.5ms/turn (比較対象: LLM駆動エンティティ抽出は約2秒/turn; 条件: Intel i5-9400F、800ターン会話) — 索引維持をローカル決定論処理へ分離することで、オンライン更新を対話経路へ置ける程度に軽量化した。

- 100ターン複数ホップの推定費用 / $0.29/query (比較対象: 全履歴 $0.91/query; 条件: 安価なSelectorと高性能Answererのモデル階層化、2026-07価格) — 同一高性能モデルで両段を処理するより、構造化索引を安価なSelectorへ任せることで約68%の費用削減を試算する。

### 負の結果・境界条件
- 単一ホップではカスケード除去がF1を0.6676から0.6728へわずかに改善し、短い依存では因果補完が必ずしも有益ではない。
- 失敗事例Repo-Aではカスケード過展開によりF1が0.672相当から0.390へ落ち、不要な因果ブロックが選択予算を圧迫した。
- Repo-Bでは約100文字のM0要約が修正版と旧版の細かな識別子差を潰し、M0なしの方がF1 0.705で良かった。
- Repo-Cでは正規表現抽出が重要なconnect_to_region群を一度も候補化できず、後段のカスケードやM0では回復できなかった。
- トークン削減率はモデル依存で、単一ホップはGLM-5の75.1%に対しQwen3.7plusでは45.6%だった。

### 結果の読み方
利得の中心は固定圧縮率ではなく、原文を残したまま質問ごとに再選択する可逆性と、全体位置情報M0と状態追跡M10を分けたルーティングにある。距離別解析ではM10のRecallが30ステップ超でも高く維持され、Last-Kは遠距離でほぼ失敗する。反対に、種となるエンティティを索引へ載せ損なうと後段処理では救えず、またカスケードが誤った因果鎖を広げると選択予算を浪費する。したがって実運用では、遅延実体化の保存機構よりも索引の被覆率と予算付き依存展開の精度が主要な改善点になる。
## 品質への影響
近似的な不可逆圧縮ではなく原文を必要時に再展開するため、設計上は情報を捨てない。ただし回答時にどの原文を選ぶかは近似的であり、選択漏れやM0要約の曖昧化により品質低下は起こる。主評価では平均品質は全履歴と同等または改善したが、22/64単一ホップ試料では独立判定と主判定の方向が一致せず、個別失敗も明示されている。
## 既存研究との差
LLMLingua2などのプロンプト圧縮は一度落とした情報を戻せないのに対し、Pullは原文を保持して質問ごとに別のターンを再実体化する。MemGPT/LettaはLLM自身が記憶ページングを行い、Mem0やZepは主にセッション間の長期記憶を扱うが、Pullはセッション内の作業記憶を対象にし、索引維持をゼロLLMの決定論処理へ分離する。ACEも可逆な履歴提示を扱うが、抽象化維持をLLMで行う点が異なる。KVキャッシュ圧縮や長文脈モデルとは層が異なり、上流で投入トークンを減らすため併用可能である。
## 限界
評価と抽出器はコーディング会話へ強く偏り、低エンティティ密度の一般対話へ同じRecallが出る保証はない。M0は抽出的でも約100文字への縮約で細部を落とし、修正版と旧版を区別できない失敗がある。規則ベースカスケードは不要な因果ブロックを展開し得る。主評価はGLM-5を生成と判定の両方に使い、別系列判定で方向を確認しているものの22/64試料では方向が異なる。BEAM 1Mは35会話中14会話で簡略Purifierを使用する。287セッションの導入分析は単一利用者ログで、生産13インスタンスにも対照群がない。
## 実装状態
著者実装と再現スクリプトが公開されている。論文ではローカルPurifierをIntel CPUで測定し、実運用のコーディング支援系13個のSWE-bench Proインスタンス、350回超のツールラウンドでゼロクラッシュと報告する。ただし生産導入には無作為化対照や大規模複数利用者評価はなく、APIモデル背後のGPU構成も非公開である。
## 研究上の位置づけ
本リポジトリの推論系では、GPU内KV管理やSSD退避のように生成途中の状態を物理メモリ階層で動かす研究とは異なり、LLMへ入る前の会話履歴そのものを論理的な作業記憶階層として扱う系統に位置付く。特に、活動・凍結・外部アーカイブという三層と遅延実体化はOSの階層記憶に近い抽象をアプリケーション文脈へ持ち込み、KVキャッシュのプリフィル負荷を間接的に下げる。今後は、正規表現中心のエンティティ被覆を軽量ニューラル抽出へ広げること、固定5件カスケードを学習または価値推定で制御すること、SSD/NVMeを含む第三層アーカイブの実I/OとSelectorを共同最適化することが、既存の階層メモリ研究と接続しやすい。
