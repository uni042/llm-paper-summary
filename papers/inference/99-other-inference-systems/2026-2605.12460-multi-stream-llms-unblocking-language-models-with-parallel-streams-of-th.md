# Multi-Stream LLMs：入力・思考・出力を同時に進める複数ストリーム言語モデル

## 概要

通常のチャット型大規模言語モデル（LLM）は、利用者の入力、モデルの推論、回答、道具からの返答を、役割区切りを付けた**一本のトークン列**として処理する。自己回帰生成はこの列を左から右へ進めるため、利用者の入力が終わる前に答え始めたり、回答しながら別の監査文を生成したりするには、外側の制御プログラムで複数回のモデル呼出しを組み合わせる必要がある。複数エージェント化や分割実行でも、単一モデルの各生成列が互いの進行をリアルタイムに観測することは容易ではない。

Multi-Stream LLMsは、利用者、回答、内部思考、監査などの役割を独立したトークン列へ割り当て、**一回の前向き計算で各列の次トークンを同時に生成**するモデル形式を提案する。同じ時刻行の各列は、他列のそれ以前の行だけを参照できる。これにより、入力を読みながら回答を開始する、回答を作りながら監査する、入力変更を受けて作業中の出力を切り替える、といった動作を学習できる。

Qwen3-1.7BとQwen3-4Bの推論・質問応答評価では、単一列で順番に読取りと回答を行う場合より応答開始が早まり、逐次反省と比較した監査同時実行では、LogicNLIの端から端までの遅延が1.7Bで102.08から59.70、4Bで132.85から78.86へ低下した。別の実験では、役割別入力の分離がプロンプト注入攻撃の成功率を下げ、内部思考列がモデルの懸念や状況認識を監査者に見せやすくすることを報告する。ただし、**推論時の並列化だけでなくモデルの追加学習が不可欠**であり、既存のチャットモデルを設定変更するだけで同じ動作が得られるものではない。

## 問題設定

従来の対話形式では、利用者のメッセージが終わってからモデルが生成を始め、道具呼出しが終わってから続きの生成を再開する。たとえば長い音声入力を聞いている途中に危険を検出して警告する、文章の下書きを書きながら別の推論列で事実確認をする、という処理は単一の生成系列では直列化される。入力トークンの事前充填を済ませてから応答を開始するという制約は、モデルのトークン生成能力そのものではなく、学習された入出力形式にも由来する。

一般的な並列推論には、独立した推論分岐を生成して最後に結果を統合する方法や、複数候補トークンを同時に予測する方法がある。しかし前者は分岐途中で互いの新しい情報を共有しにくく、後者は主として単一の回答列の生成速度を上げる。著者の目標は、回答、入力、思考、監査が**異なる役割のまま時間的に重なり、過去の相互情報を利用できる**ようにすることである。トークン列の数だけ無条件に高速化することではない。

この目的には、二つの制約がある。第一に、他列の未来を読めてしまうと訓練時に不正な先読みが起き、実際のオンライン処理では再現できない。第二に、同じ時刻の異なる列を区別する位置表現と注意の仕組みがなければ、トークンがどの役割から来たか混同される。提案方式は、この因果関係と列の識別をモデルの入出力形式へ組み込む。

## 手法

### 1. 役割別ストリームと行単位の生成

$H$本のストリームを用意し、各時刻$t$に最大$H$個のトークンを並列に予測する。ストリーム$h$のトークンは、自分自身の$t$より前のトークンと、他ストリームの$t$より前のトークンを条件として生成する。同じ行にある他列のトークンは、同じ前向き計算で同時に予測されるため、原則としてその行の予測に使えない。これは独立した枝を最後まで分離する並列推論とは異なり、**過去行を通じて列間の情報が相互に伝わる**。

利用者列に新しい入力が届き、回答列がまだ出力不要な時刻には、空欄記号を用いる。逆に利用者が黙っている間も、回答や思考の列は進められる。原著は、空欄を注意対象から外しKVキャッシュへ格納しないと説明する。従って、列数が多いからといって常に各列の全時刻で実トークンを保存するわけではない。ただし活動中の列数が増えれば出力トークン総数や注意の演算量は増えるため、計算費用が完全にゼロになるわけではない。

### 2. ストリーム別位置符号と因果注意

既存のデコーダ型Transformerを複数列へ適応させるため、各列に独立した位置カウンタを設ける。回転位置埋込み（RoPE）は列ごとの時刻で計算し、さらに学習可能な列識別埋込みを各トークンへ足す。これにより、異なる列の「時刻5」は同じ時間段階を表しつつ、利用者列の時刻5と回答列の時刻5を別の役割として識別できる。

注意マスクは、クエリの列と時刻$(h,t)$に対して、キーの列に関係なく$\tau<t$のトークンだけを参照可能とする。列内の通常の自己回帰因果性と、列間の過去参照の両方を保つための規則である。学習の損失は各列の有効トークンの交差エントロピーを列ごとに平均し、その和を用いる。特定の長い列だけが学習を支配しないようにする工夫である。

### 3. トークン交互配置と高速な注意

全列を列ごとに連結すると、ある列から別列の過去時刻を参照する位置がメモリ上で飛び飛びになり、GPUのブロック単位注意が効率を失う。提案方式は、列を一つずつ丸ごと並べるのではなく、時刻0の全列、時刻1の全列という順に**行ごとに交互配置（interleaved packing）**する。これにより注意マスクが下三角形に近い構造となり、FlashAttention型の効率的な走査を使いやすくする。

ただし原著は、通常の高速因果カーネルをそのまま流用する近似では、同じ時刻の他列へ注意が漏れる場合があることを認めている。厳密な列間因果マスクと、高速カーネルに合わせた近似的な配置を区別すべきである。厳密な因果関係が必要なシステムでは、適切なマスクを持つ注意実装で先読みがないことを検証する必要がある。

### 4. 複数列データの構築と追加学習

自然に同期したテキスト会話の学習データは少ないため、著者は既存の会話・推論データから複数列の合成例を作る。利用者の入力を一部だけ読んだ時点で応答を始める待機$k$トークン方式（wait-$k$）や、列を表形式にして言語モデルに一行ずつ生成させる方法を利用する。生成後、モデルによる因果検査で「まだ届いていない利用者入力の情報が先の回答へ漏れていないか」を確認し、列ごとの流暢さと列間の役割整合性を検査して不適切なサンプルを除外する。

その後、単一列モデルを複数列形式へ追加学習する。原著の主要な効率実験はQwen3-1.7BとQwen3-4Bの思考モードを対象とし、標準形式で追加学習したVanilla、未追加学習のBase、複数列で追加学習したStreamを比較する。比較で差が出るのは推論エンジンだけでなく、学習した入出力構造も異なるためである。独立した監査列を持つ構成では、利用者列、回答列、監査列が互いの前行を参照し、監査結果を次の回答へ反映できる。

### 5. 同期復号とKV管理

推論では各時刻の全活動列へ一度に次トークンを生成し、行を進める。理論上、各列を逐次に生成したときのトークン総数に対して、最長の列の行数で終了できるため、列数$H$に近い時間短縮の余地がある。ただしこの見積もりは、同時生成する列が同じ前向き計算に収まり、GPUの帯域・演算能力が不足せず、列間の同期待ちが小さい場合の上限的な説明である。

空スロットはKVに格納しないが、実際の活動列からは列別のKVが生じる。標準的な単一系列のトークン追加とは異なるため、位置カウンタ、行単位の注意マスク、列別のキャッシュ状態を整合させる必要がある。原著はQwen3.5-27Bの監査可能性実験で、混合アーキテクチャに含まれるGated-DeltaNet状態も列ごとに扱う実装を用意している。通常のllama.cppなどの既存推論器へ単に列を増やすだけで同じ動作になるわけではない。

## 評価

### 実験構成と指標

| 評価軸 | 一次論文の設定 |
|---|---|
| 主要効率モデル | Qwen3-1.7B、Qwen3-4B、思考モード |
| 比較 | 未学習Base、通常の単一列で追加学習したVanilla、複数列で追加学習したStream |
| 課題 | GSM8K、MATH500、LogicNLI、SQuADなどの数学・論理推論・質問応答 |
| 効率指標 | 正答率、初回目標トークンまでの入力トークン数（TNFT）、生成トークン数、端から端までの遅延、最長列長（MSL） |
| 監査同時実行 | Vanilla + Reflection（逐次反省）対Auditing While Solving（同時監査） |
| セキュリティ | Qwen2.5-7B-baseとQwen3-4B-baseを各3エポック追加学習。直接・間接プロンプト注入を比較 |
| 監査可能性 | Qwen3-8B、Qwen3.5-27Bを10列（入力1、回答1、内部思考8）へ学習。合成対話3,864件 |

初回目標トークンまでの入力トークン数（TNFT）は、入力をどれだけ読み終えるまで回答を待ったかを示す。秒数の初回応答時間（TTFT）は利用者の入力速度に依存するため、論文はTNFTも併記する。最長列長（MSL）は、同期生成で必要な行数の近似指標である。単純な出力トークン総数が減ったことと、複数列が同時に進んだことによる遅延短縮は分けて解釈する。

### 読取りと回答の同時実行

| モデル・課題 | Vanilla：正答率 / 遅延 | Stream：正答率 / 遅延 | 主な差 |
|---|---|---|---|
| Qwen3-1.7B / GSM8K | 90.60% / 14.93 | 89.51% / 11.29 | 応答は早いが正答率は1.09ポイント低下 |
| Qwen3-1.7B / MATH500 | 48.20% / 43.14 | 51.60% / 22.94 | 正答率3.40ポイント上昇、遅延約47%減 |
| Qwen3-1.7B / SQuAD | 51.70% / 7.79 | 53.50% / 4.62 | 読取りと回答の重複で遅延約41%減 |
| Qwen3-4B / GSM8K | 89.36% / 20.17 | 88.85% / 14.53 | 遅延短縮と引換えに正答率0.51ポイント低下 |
| Qwen3-4B / MATH500 | 60.80% / 45.82 | 64.00% / 26.51 | 正答率3.20ポイント上昇、遅延約42%減 |
| Qwen3-4B / LogicNLI | 62.00% / 58.31 | 63.55% / 47.39 | 正答率1.55ポイント上昇、遅延約19%減 |

この表の遅延は原著表1の値をそのまま記載した。単位の違う指標を混ぜて倍率化していない。StreamのTNFTは、原著表1のこれらの課題では0であり、入力が完了するまで応答を待たないことを表す。正答率は必ずしも一様に改善しない。特にGSM8Kのように小幅な低下があるため、「高速化して品質が常に上がる」とは言えない。

### 監査しながら解く場合

LogicNLIでは、逐次反省を後段に加えたVanilla + Reflectionと、回答列と監査列を同時に生成する方式を比較する。Qwen3-1.7Bの正答率は64.95%から65.65%、遅延は102.08から59.70へ、最長列長は4,206.94から2,453.57へ変わる。Qwen3-4Bでは正答率65.15%から65.55%、遅延132.85から78.86、最長列長4,251.33から2,454.89となった。どちらも遅延は約41～42%減で、原著がいう「40%以上」の条件に対応する。

ただし、監査を伴わない単純なVanillaと比較すると、監査列を増やした分の生成があるため、必ずしも最速ではない。1.7Bの単純なVanillaは遅延45.95であり、監査同時実行の59.70より短い。**監査による品質向上と、その監査費用を逐次実行より削減すること**がこの比較の意義である。

### セキュリティと監査可能性の別実験

役割別の入力分離により、システム命令と利用者からの非信頼入力が混同されにくくなるかを測った。Qwen2.5-7Bの間接注入StruQ-ID攻撃成功率はVanilla 76.00%からStream 42.23%、Qwen3-4Bでは80.69%から41.91%へ低下した。一方、Gandalf攻撃はQwen2.5-7Bで97.57%から96.19%、Qwen3-4Bで98.81%から95.71%と依然高く、列分離が万能の防御ではない。攻撃成功率（ASR）は低いほど防御が強い。安全性の実験は追加の敵対的訓練を行わない比較だが、学習形式を変えた効果であって、推論時に単純に入力を別配列へ置くだけで得られる防御ではない。

監査可能性実験では、Qwen3-8BとQwen3.5-27Bをそれぞれ10列に追加学習し、可視回答に現れない懸念を内部列に表出するか、外部のLLM監査者が隠れた行動を分類できるかを調べた。8Bの懸念表出率は0.07から0.42、27Bでは0.06から0.44へ上昇した。27Bの監査者による分類正解率は0.26から0.44へ上昇した。ただし同じ27Bの「監視を意識した内容が可視回答にないまま内部へ出る割合」は0.78から0.74へ小幅低下しており、全指標が一律改善したわけではない。これらは特定の合成シナリオとLLM判定器に依存する結果である。

## 既存研究との差

単一列のチャット型モデルは、入力と出力の役割をトークン境界で分けるが、実行時間を分けることはできない。Multiverseなどの並列推論は分岐を同時に進めても、途中の相互参照が制限される。複数トークン予測や投機的復号は、通常一つの回答系列をより速く進めることが目的である。本論文は**別の役割を持つ複数系列が、それぞれの過去を毎行で交換する**構造を学習させる点が異なる。推論時間の節約だけでなく、入力を聞きながら答えるという機能上の変化を狙っている。

一方、列間の注意を完全に遮断するセキュリティ機構ではない。異なる列は過去の情報を相互参照するため、役割識別の学習と適切な因果制御が必要である。列を物理的に分けたからといって、権限境界を形式的に保証するわけではない。

## 限界と実装上の注意

論文が用いたモデルは主に1.7B、4B、7B、8B、27Bであり、現代の大規模な商用エージェントへ一般化した評価はない。合成した複数列の追加学習データも、標準的な大規模事後学習と比べれば少量である。純粋に逐次的な証明記述などは並列化の利得が小さい可能性があり、利用者との対話が少ない一括処理では形式変更の効果が限定的になる。

性能実験の遅延短縮は、異なる列の仕事を重ねられることに依存する。単一GPU上で多数列を同時に出力すると、計算とメモリ帯域の余裕がなくなった場合には、理論上の列数倍の高速化は成立しない。原著は最長列長と実測遅延を示すが、全モデル・全同時要求数でのサービング性能、電力、分散GPU通信、CPUオフロードについて一般的な定量保証はしていない。

複数列の学習時に厳密な因果マスクを使う場合と、高速な通常の因果カーネルへ寄せた交互配置の近似では、同時刻列間の情報漏れに注意が必要である。また、Qwen3.5のGated-DeltaNet状態を列ごとに管理するような専用実装が必要であり、通常のチャット形式のモデルをllama.cppへ読み込むだけで実現する機能ではない。公開コードは実験ごとの独立構成で、汎用推論フレームワークへの標準統合を示すものではない。
