# ClawVM：状態保持型LLMエージェントの仮想メモリ契約

## 概要

ClawVMは、長時間稼働し外部ツールを使うLLMエージェントで、**プロンプト文脈を高速・小容量の作業メモリ、永続ファイルを低速・大容量の退避先**とみなし、状態の常駐・縮退・書戻しをエージェント実行基盤（agent harness）に強制する仕組みである。従来の要約や検索は必要な情報を残すことを保証しない。ClawVMは型付きページ、最低限残すべき情報の忠実度、予算内の表現選択、各ライフサイクル境界での検証付き書戻しを導入し、状態喪失を観測可能な障害へ変える。

合成4負荷×トークン予算6段階の24構成で、検索のみの方式は平均67.8件、実務的な要約・検索併用方式は平均1.5件の**方針で防げる状態管理障害**を起こしたが、ClawVMは0件だった。オフラインで将来の要求を一部見通せる最適化基準も0件であり、同じ障害数に到達した。方針決定部の追加時間は中央値18〜44マイクロ秒/ターンだった。ただし**「障害0」はLLM回答が正しいという意味ではなく**、モデル出力の意味的真偽や実世界ツールの結果は検証対象外である（原著5節・7節）。

## 問題設定と対象範囲

複数の道具を使うエージェントは、メール・予定表・コード編集・検索などの結果を何十ターンも蓄積する。文脈長の上限が近づくと、実行基盤が古い会話やツール結果を切り詰めたり要約したりする。しかし要約が「現在の手順の何段階目か」「必ず守る制約」「既に取得したツール証拠」を落とすと、エージェントは同じツールを再実行したり、禁止済みの処理を繰り返したりする。さらにセッションのリセット時に未保存の変更が失われたり、要約結果が永続ファイルを破壊的に上書きしたりする。

原著はこの問題を単なる検索精度ではなく、実行基盤による**常駐性（residency）と永続性（durability）の契約欠如**と捉える。実行基盤はプロンプトを組み立て、ツール呼出しを仲介し、圧縮・枝刈り・リセットを検出できる。従ってLLMが自発的に「重要事項を記憶する」ことへ依存するより、この境界で強制する方が再現可能である。対象はGPUのKVキャッシュではなく、**エージェントの文脈・ツール結果・制約・作業計画をトークン予算下で管理する推論実行時システム**である。

## 手法

### 1. 型付きページと最低忠実度の不変条件

ClawVMは会話を無差別な文字列として扱わず、識別子、所属範囲、由来、最小忠実度を持つ**型付きページ**へ分ける。原著表1の六分類は、初期規則（Bootstrap）、制約（Constraint）、作業計画（Plan）、嗜好（Preference）、証拠（Evidence）、会話区間（Conversation）である。各ページにはセッション固有かプロジェクト共有かの範囲と、どのツール呼出し・会話区間から生じたかという由来を付ける。

重要なのは種類ごとに許容できる縮退が異なる点である。制約ページは**構造化表現より粗くしてはならず**、初期規則は圧縮・リセット後にも構造化情報として残す。作業計画は目標と現在段階を残す。証拠ページは全文を外しても、永続保存された証拠へ決定論的に戻れる参照を保持する。これにより、単に「最近使っていない」から重要な規則を消すという判断を禁止する。

### 2. 四段階の表現と予算内選択

各ページは全文（full）、圧縮文（compressed）、型付きフィールド（structured）、解決可能な参照（pointer）の四段階で保持できる。縮退は全文から参照へ向かうが、前節の最低忠実度を下回る変更は許可されない。表現はページの取り込み・更新時に前計算するため、プロンプト作成の瞬間に別のLLMへ要約を依頼する必要はない。

実行基盤は出力用トークン、システムプロンプト、ツール定義、安全余裕を先に確保し、残りをページの予算とする。**第1段階**で必須ページと各ページの最低表現を必ず配置し、入り切らなければ物理的な予算不足を障害として報告する。**第2段階**で参照→構造化→圧縮→全文という品質向上候補を、追加トークン当たりの限界効用で並べ、予算が許す範囲で段階的に昇格する。

効用は常駐の優先度、直近利用、セッション範囲、再取得に必要なツール費用を加味する。たとえば最近読んだが再取得が安いログより、古くても再実行が高価な外部検索結果を詳しく残す場合がある。これは厳密な多肢ナップサック最適化ではなく、**制約を先に満たしてから貪欲に表現を昇格する決定論的近似**である。重要な規則の常駐保証は第1段階で成立し、第2段階の順位付けは主としてモデルへ渡す情報の詳しさを左右する。

### 3. 観測可能な障害分類と再生基準

通常の仮想記憶のページ欠損と異なり、エージェントの状態欠損は沈黙しやすい。ClawVMは再取得（refetch）、同じ意味のツール呼出しの重複、固定ページの欠損、圧縮後の初期規則欠落、検索失敗理由の隠蔽、未保存変更の喪失を明示的な障害として記録する。検索結果が空でも「一致なし」「権限拒否」「検索基盤の失敗」を区別する。

実行基盤は各ターンでページ選択、昇格、退避、参照解決、書戻しの判断を追記式履歴へ残す。これを同じツール署名とページ要求列で再生すれば、同じ予算で別の方針と比較できる。さらに将来3ターンの要求を見られるオフライン基準（oracle）を用い、オンライン方針の障害数との差を測る。ここで最適基準と同数だったという主張は、**定義済みの状態管理障害数に限る**。回答品質やユーザー満足度の最適性を意味しない。

### 4. 検証付き・非破壊的書戻し

状態の永続化は、モデルへ「記憶して」と指示する自由文の追記ではなく、**準備→検証→確定**の三段階で行う。実行基盤が圧縮・枝刈り・リセットなどの状態破棄境界で、型付きの追記・併合・版付き更新を要求する。更新内容を型、由来、所属範囲、破壊的操作の禁止規則に照らして検査し、合格した変更だけを決定論的な併合規則で確定する。

検証に失敗した更新は黙って破棄せず、拒否理由とともに書戻し履歴へ残す。たとえば既存の記憶ファイル全体を上書きしようとする変更は拒否される。リセット前にも書戻しを必須にする点が、圧縮前にだけ保存する実務的構成との重要な差である。正しく書き込む仕組みは提供するが、モデルが作った内容の事実性までは検証しない。

### 5. 実装の配置と実行経路

原著の試作は外部依存のないPython約1300行、六モジュールで構成される。セッションページ表（SessionPageTable）、表現選択器（RepresentationSelector）、書戻し履歴（WritebackJournal）、障害観測器（FaultObserver）、追記式判定履歴（DecisionTrace）、全体制御器（ClawVMEngine）である。セッションメタデータ、会話ログ、ツール仲介、ライフサイクルフックを持つ実行基盤に接続する。状態は呼出し間にJSONスナップショットとして保存する。

1ターンでは、入力と直前のツール結果をページへ反映し、固定トークン領域を予約し、最低忠実度を満たすページを選択し、余裕があれば表現を昇格し、組み立てたプロンプトをモデルへ渡す。ツール呼出しが生じたら署名と結果を記録し、次の要求で参照が必要なら永続側から解決する。圧縮・リセットなどが発生したら汚れたページを検証付きで書戻す。各判断は追跡可能なため、失敗した時点で「何がいつ欠けたか」を再生できる。

### 構成要素の必要性と負の結果

表5の機能追加実験では、何も持たない方式の271件から、**参照解決だけ**を追加すると43件へ減る。初期規則の自動固定だけでは271→251件、圧縮前書戻しだけでも271→251件であり、単一機構で全種類の障害を消せない。表6の機能除去では参照解決を外すと126件、圧縮前書戻しを外すと20件、リセット前書戻しを外すと3件、自動固定を外すと9件が再発した。この数値は予算180の4負荷を合算したもので、24構成の平均値と混同してはならない。

効用に基づく昇格を単純な最近使用順（LRU）へ置き換えても、4負荷・予算120〜300の**明示障害数と不安定度は同じ**だった。原著は、効用選択が高価な証拠をより詳しく残し得ると説明するが、実際のLLM回答品質がLRUより高いことは検証していない。重みの感度実験21構成・84実行でも明示障害0、不安定度0.901で、構造上の安全性が重み調整に依存しないことを確認した。逆に、品質向上を重みの調整だけで保証できるとはいえない。

### 実トレース・敵対的条件

実際のコーディング支援セッション12件をツール署名や状態変化に変換して再生すると、ClawVMは明示障害0、検索のみは中央値51件、Comp-Hybridは各セッションでリセット前書戻し欠落による1件の喪失を起こした。200ターンへの拡張でもClawVMは0、検索のみは中央値83件（71〜109）へ増えた。これらは実セッション由来だが、ツール呼出し自体は再実行しない点に注意が必要である。

敵対的試験では、予算180で50件の異なる証拠を50ターンに投入すると、検索のみ298件、Comp-Hybrid9件の障害に対してClawVMは0件だった。30ターンで9回リセットする試験でも検索のみ77件、Comp-Hybrid7件に対して0件。ただし固定3ページの最低表現だけで60トークン必要なのに予算40とした場合は、**全方式で固定ページ欠損10件**が発生した。ClawVMは無理に保証を主張せず、予算不足を可観測な障害として扱う。

## 既存研究との差

MemGPTなどはLLM自身が外部記憶へページを移動する仮想記憶の発想を提示し、LLMLingua-2はプロンプトを圧縮し、Mem0やCogneeは検索・長期記憶を改善する。しかしこれらだけでは、リセットの直前に必ず未保存状態を書き戻すことや、重要制約が最低限の表現で常駐することを**実行基盤が保証**しない。ClawVMは新しい検索器の精度競争ではなく、既存検索器を下層へ接続できる状態管理契約を追加する。

AIOSやMemOSは広いエージェントOS/メモリ表現を扱い、SagaLLMやText2Memはトランザクションや型付き更新に近い問題を扱う。ClawVMの焦点は、プロンプト組立・圧縮・リセットという**状態を失い得る境界を一つの実行基盤で強制し、障害をログ化・再生する**ことである。GPU/CPUの物理メモリ階層ではなく、トークンを容量単位としたエージェントの作業集合を管理する点で、KVキャッシュ退避やGPUオフロードの研究とは対象階層が異なる。

## 限界・適用上の注意

1. **意味的正しさを検証しない。** 書戻しの型、出自、範囲、非破壊性を検査しても、モデルが誤った事実を正しい形式で保存することは防げない。障害0は回答品質100%の意味ではない。
2. **再生は実ツールを呼び出さない。** ツール署名と要求ページを決定論的に再生するため、ネットワーク遅延、外部サービスの状態変化、非決定的なツール結果を含む実稼働で同じ数値になるとは限らない。
3. **オンライン多セッションの検証不足。** 20件の実エージェント試験は単一セッションで、圧縮・リセットの境界を十分に踏まなかった。両方式とも20/20で差がなく、実稼働の長期・多セッション成功率を立証していない。
4. **最低忠実度の容量不足は解決できない。** 予算40に対して必須ページ60トークンという試験では全方式が10件の固定ページ欠損を生じた。設計ができるのは明示的に検出することで、物理容量を増やすことではない。
5. **最適化指標は構造障害数に限定。** 先読み基準と同じ0件でも、同じ情報が全文で提示されるか参照だけかは異なり得る。実際のLLMがどう回答するか、追加検索を何秒要するか、ユーザーにどう影響するかは別の評価を要する。
6. **表現の生成費用と内容品質。** 四段階の表現はページ作成時に生成するため、プロンプト組立時の18〜44μsという値にモデルを用いた圧縮・抽出の前処理時間は含まれない。構造化フィールドが重要情報を正しく抽出できるかも別問題である。
