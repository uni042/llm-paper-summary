# Maia 200：ソフトウェア定義データフローによる大規模推論加速器

## 概要

大規模言語モデルの推論は、行列積の演算性能だけでなく、モデル重みとKVキャッシュをどれだけ効率よく運び、演算器へ供給するかに強く左右される。Xuらは、Microsoftの第二世代AI加速器Maia 200を、ソフトウェア定義・局所アクセス型データフローアーキテクチャ（Software Defined Locally Accessed Dataflow Architecture、SDLA）の具体例として報告する。SDLAは、通常のGPUのようにスレッドがロード・ストア命令でデータを動かすことを中心にせず、局所メモリ、DMA、演算器、同期エンジンの動作を独立した命令列で指定する。

Maia 200はTSMC 3nmで製造した1400億超のトランジスタを持つSoCで、750Wの熱設計電力（TDP）の下、FP4で10,145 TFLOP/s、FP8で5,072 TFLOP/s、HBM3e帯域7 TiB/sを公称する。ネットワークとチップを一体設計し、最大6,144チップを結ぶ構成ではFP4計算性能62 EFLOP/s、ネットワーク総帯域8.6 PiB/sを示す。これらの数値はチップ公称性能と大規模構成の集計値であり、全規模で任意のLLMが同じ効率で実行される実測を意味しない。

論文の実際の推論検証では、Qwen2.5-7Bを1チップ上で動かし、16,384トークンの既存文脈から次トークンを生成する復号で2,434トークン/秒を報告する。単純なPyTorch呼出しで標準カーネルを使い、追加の演算融合なしでも理論的な最大性能見積りの70%超を得たという。大規模運用の経済性については、社内保有の他加速器に対して総所有費用（TCO）30%削減、エネルギー15%削減という著者側の内部データに基づく主張もあるが、公開された共通ベンチマークによる第三者比較とは区別する必要がある。

## 問題設定：演算器よりデータ移動の管理が難しい

言語モデルの入力事前計算（prefill）は長い入力をまとめて処理するため行列積の演算密度が高くなりやすい。一方、逐次復号（decode）は各ステップで新しいトークンの計算に対して長いKVキャッシュを参照し、メモリ帯域の制約が強くなる。多数要求のバッチ処理では重み読出しを共有できても、要求ごとのKVキャッシュは別々であり、メモリ容量と帯域の制約は残る。混合専門家（MoE）の専門家間通信や長文脈・マルチモーダル入力では、装置内外のデータ移動も増える。

従来の汎用GPUはスレッド実行を中心とするSIMT方式で、命令スケジューリングや細粒度の転送制御の多くをハードウェア・ファームウェアに隠す。専門家は共有メモリやワープ特化でデータ移動を制御できるが、同期とDMAを細かく制御するには、スレッド実行の枠組みの中で複雑な手続きを記述する必要がある。Maia 200の設計は、AI計算の多くが規則的なブロック演算で、入力サイズなどの少数のパラメータから転送を事前計画しやすいことに着目する。

## 手法：ソフトウェア定義の局所データフロー

### 1. 計算命令とデータ移動・同期命令を分離する

著者らは、データアクセスが局所か大域か、データ移動が通常のロード・ストア命令に従うか独立したソフトウェア定義データフローか、という二軸で計算機を分類する。SDLAは局所メモリを持つ演算器と、独立したデータ移動・同期エンジンを組み合わせる方式である。制御プログラムはDMAや演算の命令をキューへ積み、各命令は事前条件のセマフォが満たされると実行され、終了時に後続命令用のセマフォを更新する。制御プロセッサが個々の演算終了を待ち続ける必要はない。

Maia 200のデータフロー命令セット（DISA）は、事前条件、演算または転送のマクロ命令、事後条件を明示する。各命令は最大2個の事前セマフォを待ち、終了時に最大2個を通知できる。DMA、テンソル演算、ベクトル処理が独立に動くので、次の入力の転送、現在の演算、前の出力の格納を重ねやすい。制御側にはC++ベースのNEPAL（NEsted PArallel Language）を用意し、高水準ではPyTorchやTriton風の抽象化も可能とする。

### 2. 階層化した局所SRAMと専用転送器を使う

チップは4個のクラスタからなり、各クラスタには9〜10個のタイルがある。タイルにはテンソル演算器（Tile Tensor Unit、TTU）、ベクトルプロセッサ（TVP）、専用SRAM、DMA、同期器、制御プロセッサを備える。タイルの専用SRAMは約3MiBで、TTUが使う行列を演算の直近へ置く。クラスタにも共有SRAMを持ち、タイル間ネットワークと全体ネットワークを介してHBMや外部ネットワークへ接続する。

ハードウェアキャッシュでは、タグ管理、連想検索、置換方針などの回路が必要になる。Maia 200は明示的に割り当てるスクラッチパッドを使い、データ配置と転送をソフトウェアから決めることで、面積・電力・予測可能性の改善を狙う。著者はキャッシュのタグ等の回路が面積・エネルギーへ与える費用を議論する一方、ソフトウェアが配置を管理する負担が増えることも認め、コンパイラと低水準制御を組み合わせる二層の開発方式を示す。

### 3. 狭いデータ型と変換専用エンジンを組み合わせる

TTUはFP4、FP6、FP8、BF16などを処理し、FP4で1サイクル65,536回の積和演算を行える設計である。FP6はFP8と同じ演算並列度を使いつつ不要な回路を停止してエネルギーを削減する。DMA側のReshaperはテンソルの形状変更、転置、データ型変換、散布・収集、疎形式と密形式の変換を担当する。これにより演算器を型変換のために停止させず、データ移動の経路上で形式を合わせる。

狭い精度はモデル重み・KV・中間テンソルの転送量を減らす一方、モデル品質を保つには適切な量子化尺度と検証が必要である。論文が示すFP4・FP8の公称性能は、Qwen2.5-7Bの実験で全ての演算がFP4で実行されたことを意味しない。演算器の理論値とモデル全体の復号速度は別の指標である。

### 4. DMAと同期をチップ間ネットワークへ延長する

各SoCには400Gbpsのネットワーク制御器（ANC）を28個内蔵し、総帯域は双方向1.4TB/sである。うち20リンクを固定接続、8リンクをスイッチ経由に使う。ネットワークもSDLAのデータフローへ統合され、送受信バッファとセマフォを指定することで、ローカルSRAMやHBMから遠隔メモリへの転送を通常のDMA命令のように扱える。

転送には受信側主導のメッセージングを使い、受信側がアドレスを通知した後に送信側がRDMA書込みを実行する。パケット再送、複数経路への分散、暗号化、QoSなども組み込む。最大6,144チップ構成では48チップを単位とする二層ネットワークを組み合わせ、全体の集約帯域を拡張する。こうした設計は、MoEのall-to-all、重み分割、KV移動など、演算器をまたぐデータ移動を想定している。

## 評価：公称値・単体実測・推論全体の結果を分ける

### 1. 演算器・メモリ帯域の実測

FP4行列積のRoofline測定では、演算律速の領域で高いピーク比を得る一方、メモリ律速の小さい行列では帯域上限へ届きにくい。論文はFP8の行列積でも演算律速で最大96%、帯域律速で最大56%のピーク比を示す。メモリ律速時の値は行列サイズに依存し、実効帯域が公称HBM帯域に常に等しいという主張ではない。DMAとTTUのパイプライン化、局所SRAMへの配置、型変換の分離が、データ供給と演算の重なりを支える。

### 2. 集合通信の実測

8チップのAllgatherを測定し、著者が推定した物理的な遅延下限と帯域上限に対して、遅延で78%、帯域で94%の到達率を報告する。上限の見積りはスイッチ経由の小メッセージ遅延約4マイクロ秒と、受信量を総ネットワーク帯域で割った時間から導く。測定はAllgatherを中心としたもので、MoEのすべてのall-to-all形状、障害時のネットワーク挙動、6,144チップ全体の集合通信を網羅するものではない。

### 3. Qwen2.5-7Bの単一チップ復号

エンドツーエンド検証では、28層、隠れ次元3584、FFN中間次元18,944、クエリ28ヘッド・KV4ヘッドのQwen2.5-7Bを用いる。重みの行列積読出し量は論文Table Iで合計14.14GiBとされ、入力系列長S=1の逐次復号では多数の比較的小さな行列を読み出すため、演算器のピークよりメモリ帯域が支配的となる。

16,384トークンの過去文脈を保持した場合のKVキャッシュは、鍵・値2種×28層×KV4ヘッド×128次元×2バイト×16,384トークンで、約939.52MiBになる。PyTorchから標準カーネルを呼び、追加の演算融合をしない単純な実装でも2,434トークン/秒を達成したと報告する。既存のGPU推論解との出力正当性も確認したと述べるが、同じ条件のGPU実測速度を並べた公開比較表は提示していない。ここでの70%超は論文内の推定最大性能に対する割合であり、他社製品より70%高速という意味ではない。

## 既存研究との差

GPUのSIMT方式では、スレッドの実行とメモリ転送を組み合わせて最適化する。近年のGPUにもTensor Memory Acceleratorのような転送専用機構があるが、Maia 200はDMA、同期、局所メモリの制御を基本のプログラミングモデルとして公開し、タイル・クラスタ・チップ間ネットワークまで同じデータフロー制御の考え方を適用する。独立した制御経路により、転送を開始するために演算スレッドを待機させる費用を減らし、装置ごとの動作を細かく重ねる設計である。

特定のLLM推論アルゴリズムを提案する研究とは異なり、本論文はアーキテクチャの抽象機械、実チップ、ネットワーク、低精度演算、実アプリケーションの復号を一体で報告する。MoEの通信、長いKVキャッシュ、事前計算と復号の分離などの負荷を想定し、装置の設計とソフトウェアのデータ移動制御を共同で最適化する点に意義がある。

## 限界・適用範囲

製品のピーク演算値、単一カーネルのRoofline測定、8チップの通信測定、1チップのQwen2.5-7B復号、6,144チップの構成上限は、それぞれ異なるレベルの証拠である。これらを一つの「全クラスタ実測のLLM推論速度」として混ぜない。特に2,434トークン/秒は特定モデル・特定文脈・単一チップの結果であり、巨大MoEモデルや複数装置への分割で同じトークン速度を保証するものではない。

社内TCO30%・エネルギー15%削減という比較は、運用条件、価格、測定方法の詳細が公開された統制比較ではない。外部のGPU・TPUとの直接的な性能優位を結論する根拠には使えない。著者自身も、他アーキテクチャとの網羅的な比較ではなくSDLAの有効性を示すことを主目的としている。低水準のデータ移動制御は高度な最適化を可能にする一方、開発者やコンパイラにデータ配置・同期の正しさを担保する責任が移る。

公開コードの公式URLは一次論文に記載されていないため `code: null` とした。実機を必要とする専用ハードウェアであり、一般のGPUへそのままソフトウェア移植できる手法ではない。ローカル推論での実用的な示唆は、推論を演算回数だけでなく、重み・KV・ネットワークのデータ移動とその重なりで分析することにある。
