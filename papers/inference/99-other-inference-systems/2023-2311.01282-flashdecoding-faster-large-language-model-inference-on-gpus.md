# FlashDecoding++: Faster Large Language Model Inference on GPUs

## 概要

FlashDecoding++は、自己回帰型の大規模言語モデルで一語ずつ出力する復号段階を、GPUの演算資源とメモリ階層に合わせて高速化する推論エンジンである。論文が分離した三つの障害は、長い注意系列を分割したときの部分ソフトマックス結合同期、少数トークンを入力する細長い行列積のゼロ埋め、行列形状とGPUの種類を無視する固定実行方式である。これらは同じ問題の言い換えではなく、注意の依存関係、行列演算器の稼働率、カーネルの選択という異なる層の律速である。

提案は共通の尺度値φで部分ソフトマックスを独立に積算し、危険な数値範囲だけ従来方式で再計算する機構、短辺Mを8までの最小タイルへ揃える細長い一般行列積（flat GEMM）と二重バッファ、さらにGPU・線形層の形状ごとに事前測定した境界M1・M2で行列ベクトル積と二種類の行列積を切り替える機構からなる。量子化やモデル枝刈りとは異なり、モデルの重みや出力分布を変更せず、同じ計算を速く実行する設計である。

著者らはNVIDIA A100・RTX 3090、AMD MI210・RX 7900 XTXを使い、Llama2、OPT、ChatGLM2のプリフィルと復号を測定した。Hugging Face実装に対する復号高速化の最大値はNVIDIAで4.86倍、AMDで3.93倍。FlashDecodingとの比較では、NVIDIA全体の平均は1.21倍、A100に限定すると平均1.37倍である。比較対象・GPU・評価相を省略して「一律1.37倍」と解釈してはならない。

## 問題設定

### 注意の分割が生む依存関係

長いキー・値系列を複数の区間に分けて注意を計算すると、各区間の局所最大値が異なる。数値的に安定なソフトマックスは局所最大値を差し引いて指数を求めるため、全区間を結合するときに最大値を更新し、既計算の指数和と重み付き値を再尺度化しなければならない。分割によって並列性は増えても、部分結果の更新に同期が残る。A100上でLlama2-7B、入力1024トークンを測定したとき、この同期は注意計算時間の18.8%を占めた。推論全体の18.8%ではない点が重要である。

### 小バッチの細長い行列積

入力を一括処理するプリフィルと異なり、復号は各ステップで少数の新しいトークンを処理する。バッチ1では行列ベクトル積（GEMV）、バッチ数が小さい場合は短辺Mが非常に小さい行列積となる。汎用ライブラリが行列演算器の効率を優先してMを64へゼロ埋めすると、例えばM=8では有効要素以外を大量に計算する。論文は50%を超える計算資源の未利用が起こり得ると述べる。したがって大きい行列積向けの高効率カーネルを、そのまま小バッチに使うことは最適でない。

### 静的な実行方式の限界

同じモデルの線形層でも、入力長やバッチ数が変わると行列の短辺Mが変化する。GPUの並列ブロック数、共有メモリ、メモリ帯域、Tensor CoreとCUDAコアの相対性能も実装選択を左右する。固定データフローでは行列形状によって最大50.25%の性能損失が観測される。小さいNでは同時実行ブロックが足りず、大きいNではデータ転送待ちが支配的になりやすいという異なる状況を区別する必要がある。

## 手法

### 1. 統一最大値を用いた非同期部分ソフトマックス

ソフトマックスは各要素x_iに対し、共通の実数φを用いて exp(x_i−φ) を計算し、その和で正規化しても、実数演算では最大値を使う通常の計算と同じ結果になる。FlashDecoding++は、部分区間jごとに分子Σ_i exp(x_i^(j)−φ)v_i^(j)と分母Σ_i exp(x_i^(j)−φ)を独立に積算し、最後に各区間の分子・分母を合算して割る。区間間で新しい最大値を通知し、過去の部分結果を繰り返し補正する依存を避ける。独立処理を細粒度の実行パイプラインへ割り当てられるが、最後の総和と除算は残るため「全同期を排除」とは異なる。

共通φの選択は数値安定性と不可分である。φから離れすぎた注意スコアは指数のオーバーフローやアンダーフローを引き起こす。著者らが調べたLlama2-7Bの注意スコアは99.99%超が約−16.8〜6.5にあり、範囲に基づく尺度を設定できる。実行中に許容範囲外の値が出た場合、非同期処理を停止し、従来の同期型部分ソフトマックスで対象行を再計算する。これは安全性のための明示的な失敗時経路であり、外れ値を無視して出力品質を落とす方式ではない。

OPT-6.7Bではスコア範囲が広いため、論文はこの非同期ソフトマックス最適化を適用しないと記している。つまり改善はモデル・入力分布に依存し、全てのモデルで同じφを使えるわけではない。再計算が頻発する場合は最適化の利得も低下する。入力から部分和、最終出力へのデータフローと数値安全条件を一体として設計した点が重要である。

### 2. M次元8単位の細長い行列積

行列Aの形状をM×K、重み行列BをK×Nとする。復号ではMが1〜8程度のことが多い。従来の汎用カーネルがMを64に埋めるのに対し、提案は対応する行列演算器でMを8単位までに抑え、不要なゼロ要素の乗算を削減する。K方向のタイルは一つのGPUブロックで逐次処理して縮約し、N方向のタイルは異なるGPUブロックへ割り当てる。この分割ではN方向のタイル幅B_Nを小さくすると独立ブロック数N/B_Nが増えるが、重みや入力の再利用効率は下がる。

反対にB_Nを大きくするとメモリ再利用は改善するが並列ブロック数が減る。A100は108個のストリーミングマルチプロセッサを持つため、N/B_Nが小さすぎると全演算器を満たせない。著者らはM=8でNとタイル幅を変える測定を行い、小さいNでは並列性、大きいNではメモリ待ちが律速になることを示す。この結果からタイル幅を一律に固定せず、対象の形状ごとに選択する。

### 3. 二重バッファによる読込と計算の重畳

Nが大きくメモリ待ちが支配的な場合、共有メモリに二つのタイルバッファを用意する。一方のバッファにあるA・Bのタイルで行列積を行う間に、他方へ次のK方向タイルを読み込む。次の反復で二つの役割を入れ替え、メモリ転送と演算を時間的に重ねる。論文の図8はこの交互処理を示す。目的はメモリ待ちによる演算器の空転を減らすことであり、演算回数そのものを削減するM次元の小タイル化とは別の改善機構である。

二重バッファには共有メモリの追加使用という費用がある。並列性が不足している小さいNで共有メモリを増やせば、同時常駐ブロックが減って逆効果になり得る。このため、著者らはNが大きい形状で重点的に使う。小タイル化、並列ブロック数、データ再利用、転送待ちの隠蔽を独立した選択軸として扱うことが実装上の要点である。

### 4. 事前計測によるハードウェア適応実行

モデルの線形演算は鍵・問い合わせ・値の射影、注意出力の射影、全結合層の拡張と縮小に整理できる。モデルが固定ならKとNの組合せは実質四種類に限られ、バッチ数や入力長で変化するのは主にMである。FlashDecoding++は各K・N形状について、高速GEMV（実装A）、提案した細長いGEMM（実装B）、汎用CUTLASS GEMM（実装C）の性能をオフラインで測定する。

Mを増やしてBがAを上回る交点M1、CがBを上回る交点M2を見つけ、実行時はM<M1でA、M1≤M<M2でB、M≥M2でCを選ぶ。GPUやモデルごとに表を作るため、毎トークンで三種類のカーネルを実測する必要はない。A100のLlama2-7Bで、バッチ1の射影にはCUDAコア型GEMVが有利で、バッチ4の射影ではTensor Core型実装が有利になるという測定が、この分岐を裏付ける。

具体的にはLlama2-7BのK・N形状は、鍵・問い合わせ・値の射影で12288×4096、出力射影で4096×4096、全結合の二方向で11008×4096と4096×11008である。事前計測した各形状固有のM1・M2を参照するため、モデルを変えれば境界表の再生成が必要になる。新しいGPUへ移しただけで同じ選択が最適になる保証はない。

AMDの評価では当時の対応状況からHugging Faceだけを基準にしている。したがってAMD最大3.93倍とNVIDIAの複数エンジン比較は同一の競争条件ではない。図10・図11の空欄は比較対象が該当モデルや入力長を実行できなかったことを示し、未測定の相手に勝ったという意味ではない。実測可能な構成だけから倍率を読む必要がある。

プリフィルではMが比較的大きく、既存の行列積カーネルでも演算器を利用しやすい。提案の小タイル化やGEMV選択は、少数トークンの復号ほど大きな利点を持たない。このため復号の最大倍率とプリフィルの平均倍率は別々に報告されている。なお18.8%は注意演算内の同期費用、50.25%は固定データフローを使った特定形状の性能損失であり、どちらも最終的なエンドツーエンド高速化率ではない。

### 精度と失敗時動作の読み取り

統一尺度φの部分注意は、実数上は元のソフトマックスと等価な式変形である。指数の数値範囲を超えた場合に同期型計算へ戻すため、誤差を許して高速化する近似注意とは設計思想が異なる。ただし、この安全な再計算経路が頻繁に発生する未知のモデルや長文脈入力について、論文の測定から同じ速度倍率を予測することはできない。OPT-6.7Bでは分布の広さを理由に非同期機構を使わないという負の条件も重要な結果である。

論文の評価はカーネル実装とモデル実行の速度比較が中心で、オンラインサービスでの多数利用者の待ち行列、到着率、ネットワーク遅延、GPU間通信を含めた実験ではない。GPU演算が速くなることと、実運用のサービス全体の要求処理量が同じ倍率で改善することは別問題である。性能を移植する際は対象GPU、モデルの線形層形状、バッチ分布を再計測しなければならない。

## 既存研究との差

FlashAttentionはメモリ階層に合わせて注意の入出力を削減し、FlashDecodingは長いキー・値系列を分割して復号時の並列性を高める。FlashDecoding++は分割注意で残る部分ソフトマックス同期を減らすだけでなく、復号時の細長い線形演算とGPU別の実行方式まで最適化する。つまり単一の注意カーネルの改良ではなく、モデル内の複数演算を横断する推論エンジンの設計である。

vLLMはキー・値メモリ管理や連続バッチ化、TensorRT-LLMはGPU向けの融合演算を含む推論エンジンであり、提案の焦点はこれらの要求スケジューリングを置き換えることではない。FlashDecoding++の主要な貢献は、すでに決まった演算形状に対してGPUの演算資源をどう割り当てるかという低層実行最適化にある。

## 限界と適用条件

第一に、非同期部分ソフトマックスは注意スコアの数値分布に依存する。OPT-6.7Bでは安全な範囲を確保しにくく適用されていない。未知の入力分布で再計算が多くなると、非同期化の利得が小さくなる可能性がある。安全経路があることと、あらゆる入力で速度が保証されることは同義でない。

第二に、ハードウェア適応の実行方式はGPUごと、線形層形状ごとの事前測定を要する。CUDA/ROCmの版や演算器の構成が変われば、M1・M2の境界も変化し得る。新しいGPUで同じ境界表を使って最適化されるとは限らず、再プロファイルの費用が発生する。共有メモリを増やす二重バッファも、並列ブロックが不足する形状では不利になり得る。

第三に、評価はA100、RTX3090、MI210、RX7900XTXと、Llama2・OPT・ChatGLM2を中心としたもので、全GPU・全モデルを網羅していない。AMDではHugging Faceだけが比較可能だったため、NVIDIA側の複数エンジン比較と直接同列には扱えない。入力長・モデル構成によって比較不能な棒も存在する。

第四に、論文は主として単一ノードのプリフィル・復号性能を評価しており、分散サービング、階層メモリへの退避、ネットワーク通信、多数利用者の要求到着過程を含むエンドツーエンドの運用評価ではない。公式コード公開先は今回確認した一次資料から特定できなかったため、独立再現性については追加確認を要する。
