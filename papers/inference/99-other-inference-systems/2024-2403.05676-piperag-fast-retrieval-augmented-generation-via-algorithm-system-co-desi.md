# PipeRAG: Fast Retrieval-Augmented Generation via Algorithm-System Co-design

> 生成途中の検索を先行してLLM生成とパイプライン化し、検索間隔と探索量を性能モデルで調整してRAGの品質を保ちながら最大2.6倍低遅延化する。

## 書誌

- 著者: Wenqi Jiang, Shuai Zhang, Boran Han, Jie Wang, Bernie Wang, Tim Kraska
- arXiv: 2403.05676
- KDD 2025
- 一次資料: https://arxiv.org/abs/2403.05676

## 概要

検索拡張生成（retrieval-augmented generation; RAG）は外部データベースから関連文書を取得して生成品質を上げるが、生成中に検索を繰り返す方式では「検索完了までLLMが待つ」「LLM生成中は検索器が待つ」という逐次依存が生じる。データベースが大きいほど検索時間は無視できず、検索頻度を下げると今度は生成状態と検索queryが古くなる。

PipeRAGは検索と生成の厳密な逐次依存を緩め、現在の生成blockをLLMが処理している間に、少し前の状態から次block用検索を先行する。さらに検索間隔を柔軟にし、検索器・推論器の遅延を測った性能モデルで近似最近傍検索の探索量を選ぶ。

582M parameterのRETROモデルと最大30億token chunkのデータベースを用い、1024 token生成の端から端遅延で評価する。RETRO比で最大2.6倍低遅延化しつつパープレキシティを維持または改善する。性能モデル駆動設定では非検索モデル比10.6〜13.2%の遅延増に抑えながら、パープレキシティを2.50〜4.82下げる。

## 問題設定

RETRO型RAGは一定token間隔で現在の生成文脈からqueryを作り、外部データベースを検索し、取得chunkを次の生成へcross-attentionで統合する。検索間隔を短くすればqueryの鮮度と知識統合頻度は上がるが、逐次実行では検索回数が増えて遅延も増える。

逆に間隔を長くすると検索費は減るが、queryが現在の生成状態を十分反映しない。PipeRAGはこの「品質のための頻繁な検索」と「低遅延のための少ない検索」を、検索と生成の重畳によって別軸に分離する。

## 手法

### 検索・生成パイプライン

生成区間iをLLMが処理している間に、検索器は区間iより前の状態を用いて区間i+1向けの検索を実行する。取得結果は次区間で利用されるため、検索と生成のwall-clockを重ねられる。

代償はqueryが少し古くなることだが、逐次RETROで検索そのものを待つ時間を隠蔽できる。検索と推論の所要時間が近いほど重畳余地が大きく、片方が極端に速い場合は利得が縮む。

### 柔軟な検索間隔

標準RETROの固定64 token間隔に縛られず、PipeRAGはより短い間隔も利用する。短い間隔はquery stalenessを小さくし、取得知識を生成へ取り込む頻度も増やす。

通常なら検索回数増加が遅延を悪化させるが、パイプラインで検索を隠せるため、品質改善と低遅延を同時に狙える。論文では32 token以下の短い間隔がRETROより良い品質を示す条件がある。

### 性能モデル駆動検索

近似最近傍検索では探索量を増やすほど検索品質が上がる一方、遅延も増える。PipeRAGは検索器とLLM推論器を事前計測し、次の生成区間に隠せる時間予算内で検索品質が最大になる探索設定を選ぶ。

これにより固定nprobe等ではなく、ハードウェアと生成状態に応じて検索量を変える。出力は「次区間までに間に合う、できるだけ高品質な検索結果」である。

## 主要結果

| 条件 | 結果 | 読み取れること |
|---|---:|---|
| RETRO比、同等以上の品質 | 最大2.6倍低遅延 | 検索待ちを生成と重ねる効果 |
| 同一遅延制約 | PPL最大0.93改善 | 速度予算を短い検索間隔へ再配分可能 |
| Wikipedia、性能モデル駆動 | 9.35s（検索なし）→10.34s、PPL 16.74→13.47 | 約10.6%遅延増で品質改善 |
| RealNews | 9.35s→10.58s、PPL 17.37→14.87 | 約13.2%遅延増、PPL -2.50 |
| C4 | 9.35s→10.58s、PPL 24.18→19.36 | 約13.2%遅延増、PPL -4.82 |
| 将来hardwareモデル | 検索または推論だけ16倍高速化すると相対利得縮小 | 二処理の時間が近いほどpipelineが効く |

## 既存研究との差

RETROは生成と検索を交互に逐次実行するため、検索品質を上げるほど検索待ちが直接遅延へ加わる。PipeRAGは検索アルゴリズムだけを高速化するのではなく、依存関係を変更して検索を先行実行する。

単純な非同期化とも異なり、検索間隔と近似検索の探索量を性能モデルへ結びつけ、隠蔽可能な遅延予算を品質へ使う。アルゴリズム上のquery鮮度とシステム上の重畳を同時に設計する。

## 限界

先行検索は古い生成状態を使うため、将来の生成が急に方向転換するtaskでは取得結果の関連性が落ちる可能性がある。論文の品質結果はRETRO型の検索・cross-attention構造に基づく。

またパイプライン利得は検索と推論の時間比に依存し、片方だけが桁違いに高速になると隠蔽できる割合が小さくなる。評価モデルは582M RETROであり、現代の数十B級LLMや分散サービングへ同じ倍率がそのまま適用されるとは限らない。
