# Multi-Bin Batching：予測生成長による固定バッチの空転削減

## 概要

大規模言語モデルの推論では、複数要求をまとめてGPUへ投入するバッチ処理により、行列演算を効率化できる。しかし固定バッチ方式では、バッチに含まれる要求のうち最も長い生成が終わるまで、そのバッチ全体が実行資源を占有する。短い要求は途中で完了しても、空いた計算枠を新しい要求へ割り当てられない。Multi-Bin Batchingは、生成長が近い要求を複数の待ち行列へ分け、各待ち行列の中だけで固定バッチを作ることによって、この空転を減らす方式である。

提案方式はモデル重みや注意演算を変更しない。生成長の予測値をスケジューリングへ使い、同じバッチに入る要求の終了時刻を揃える。理論解析では、サービス時間が一様分布で固定バッチの大きさが一定という条件の下で、各ビンが同じ確率質量を持つ境界が最適となる。ビン数を増やせば、固定バッチの理想サービス率へ近づく。ただしこの理論上限は連続バッチ化を含む普遍的な推論スループット上限ではない。

2026年改訂版の実測では、単一A100 80GB上のllama.cppでDollyワークロードを処理し、推定長8ビンが固定バッチの273.53生成トークン/秒から684.02生成トークン/秒へ改善する。相対改善率は150.1%である。一方、連続バッチ化の1200.07生成トークン/秒には及ばず、43.0%低い。真の生成長を事前に知るオラクル8ビンでも965.97生成トークン/秒であり、連続バッチ化より19.5%低い。**固定バッチの欠点を改善する手法であって、連続バッチ化の代替として一般に優位という結果ではない。**

## 問題設定：最長要求に拘束される固定バッチ

固定バッチでは、バッチサイズB件の要求を同時に処理し、最も長い要求が終わるまでバッチ全体を保持する。例えばサービス時間が1、5、2、6秒の四要求を到着順にB=2でまとめると、最初のバッチは5秒、次のバッチは6秒で合計11秒を要する。短い要求同士をまとめて(1,2)と(5,6)に分ければ、必要時間は2秒と6秒で合計8秒となる。GPUの計算速度自体を上げたわけではなく、終了した要求を待つ空転を減らした結果である。

生成長のばらつきが大きいほど、同じバッチ内の最長要求と平均要求の差が大きくなる。モデルの推論では出力長が事前に確定しないため、単に短い要求から処理するだけでは最適な組合せを作れない。提案方式は予測生成長を用い、短い要求を短い要求と、長い要求を長い要求と組み合わせる。予測に誤差があっても、大まかな長さの順位が分かれば空転を減らせる可能性がある。

理論モデルは単一サーバ、ポアソン到着、十分な待ち行列容量、各要求の独立同分布のサービス時間、固定バッチサイズBを仮定する。主解析ではサービス時間を一様分布、拡張では指数分布とする。サービス時間は生成トークン数に主として比例するという抽象化であり、長い入力のプリフィル、注意計算、KVキャッシュ容量、複数GPU間通信などは理論式に直接入れない。実際の推論基盤のすべての挙動を表すモデルではない。

## 手法：複数の待ち行列から固定バッチを形成する

### 1. 予測サービス時間によるビン割当

推論要求を受け付けた時点で、出力長またはサービス時間を推定する。あらかじめ定めたk個の区間のうち、予測値が含まれる区間へ要求を入れる。各ビンは独立した待ち行列を持ち、同じビンにB件そろうと一つの固定バッチを形成する。形成済みのバッチは中央の実行待ち行列へ送られ、論文の既定方針では形成が完了した順に処理する。

この設計は要求を細かく再配置する連続バッチ化とは異なる。バッチ形成後はそのバッチの構成を固定し、生成途中で終了した要求の枠を別要求へ再利用しない。したがって、ビンの幅を小さくして生成長を揃えるほど、同じバッチ内の空転は減るが、別のビンにいる要求を空いた枠へ入れることはできない。連続バッチ化の細粒度スロット再利用とは改善する対象が異なる。

### 2. 静的バッチのスループット定義

バッチサイズB、バッチのサービス時間をt_serviceとすると、飽和した固定バッチサーバの要求処理率を `B / E[t_service]` と定義する。各バッチのサービス時間は、そこに含まれるB要求のサービス時間の最大値である。全体の期待サービス時間は、各ビンへ属する確率と、そのビンのB要求の最大サービス時間の期待値を掛け合わせて合計する。

理想的に同じサービス時間の要求だけを一つのバッチへ入れられれば、バッチ内の最大値は平均に近づく。このとき静的バッチモデルの理想処理率は `B / E[t]` である。論文の上限はこの固定バッチという枠組みでの理想値であり、生成途中で要求を出し入れできる連続バッチの普遍的な上限ではない。また、これは飽和状態でのサービス能力を表すため、到着が少ない場合の待ち時間を含めた平均応答時間と同一ではない。

### 3. 一様分布での最適境界

サービス時間が[l_min,l_max]の一様分布に従うとき、固定したビン数kに対して各ビンの確率質量を等しくする境界が最適となる。境界は `l_i = l_min + (i/k)(l_max-l_min)` で与えられる。各ビン内のサービス時間が一様分布なら、B件の最大値の期待値は下端と上端の重み付き平均で表せる。これをビンの確率で加重した全体の期待サービス時間を最小化することで、等間隔の境界が導かれる。

ビン数kを増やすと各ビンのサービス時間幅が狭くなり、バッチ内の最大値と平均の差が小さくなる。kが大きくなる極限では、静的バッチの理想処理率へ近づく。ただし現実の生成長分布は一様とは限らないため、実装で常に等幅区間が最適とはいえない。偏った長さ分布では、各区間へ到着する確率を考慮して境界を決める必要がある。

### 4. 予測誤差の扱い

生成前に真の出力長は分からないため、オラクル設定と予測設定を分けて評価する。オラクル設定は、後から判明する真の出力長を最初から知っていると仮定してビンを選ぶ。これは理想的な上限側の参考値であり、実サービスでそのまま利用できない。実用設定では、生成前の入力を処理したモデルの内部表現から出力長を予測する軽量回帰器を使う。

Dolly実験ではLlama-3.2-3B-Instructのプロンプト処理後の隠れ状態を特徴として用い、回答トークンを生成せずに出力長を予測する。予測値が真の長さと完全一致しなくても、近い長さのビンへ入れば空転削減の効果は残る。論文は正しいビンへの分類精度と、正しいビンまたは隣接ビンへの分類精度を別々に測る。ビン数を増やすと前者は下がるが、後者が高ければ粗い長さの並びを保てている。

### 5. ビン数の増加と待ち時間の交換条件

ビン数を増やせば同じビン内の長さのばらつきは減るが、各ビンへ要求が到着する頻度も下がる。完全なB件を集めるまでの時間が増え、低負荷では待ち時間が長くなる可能性がある。論文の理論スループットは飽和したサーバを想定するため、低到着率の待ち時間悪化をそのまま説明しない。

実運用では、バッチがB件そろわなくても一定時間で発行するタイムアウトや、サービス水準目標に応じた待ち時間制限が必要になり得る。しかし不完全なバッチを発行すれば、理論の固定B件という仮定から外れる。ビン数を増やすことと待ち時間を制御することは別の最適化問題であり、両者を同時に評価する必要がある。

### 6. 連続バッチ化との関係

連続バッチ化はデコード反復ごとに終了した要求を外し、新しい要求を入れることでGPUの枠を再利用する。これに対し複数ビン方式は、固定バッチの内部で短い要求が先に終わる損失を減らす。原著は連続バッチ化を比較対象に加え、予測長による固定バッチの改善がどこまで追いつけるかを測る。理論上の最適性は静的バッチ内のものであり、連続バッチの最適性を証明するものではない。

長さ別の待ち行列を連続バッチの入場制御に応用する余地はあるが、原著の数値はその組合せ方式の性能を測定したものではない。ビンの設計思想と実際の固定バッチ実装の結果を分けて理解する必要がある。

## 評価：静的バッチと連続バッチの両方を比較

### 1. 実機環境と負荷

| 項目 | 原著の設定 | 解釈上の注意 |
|---|---|---|
| GPU | NVIDIA A100 80GBを1基 | 単一GPUでの比較 |
| 推論実装 | llama.cpp、FP16、コンテキスト4096 | 別推論基盤の速度を直接保証しない |
| 制御済み負荷 | 1024要求、B=32、出力長500〜2000トークン | 真の長さを知るオラクル条件 |
| Dolly負荷 | 1478要求、B=64、真の長さ3〜978トークン | 現実的な不均一な長さ分布 |
| Dolly総生成量 | 408,352トークン | 処理率は生成トークン/秒 |
| 比較方式 | 固定バッチ、複数ビン、標準連続バッチ | 同じGPU上で比較 |
| 予測器 | Llama-3.2-3B-Instructの隠れ状態から回帰 | 真の出力長は生成前に未知 |

### 2. 制御済みオラクル実験

制御済みの長さ分布では、通常の固定バッチが534.23生成トークン/秒、標準連続バッチが1348.49生成トークン/秒となる。オラクルで16ビンへ分けると1380.48生成トークン/秒となり、固定バッチ比158.4%改善する。この人工的に整えた長さ分布では、連続バッチを約2.4%上回る結果も得られる。

ただしこの結果は、真の長さを事前に知り、ビンの負荷が均等になるよう構成した条件である。実際の要求では生成長を正確に予測できず、各ビンの到着頻度も偏る。制御済みの一条件で連続バッチを上回ったことを、一般に複数ビンが連続バッチより速いという主張へ拡張してはいけない。

### 3. Dollyのオラクルと実用予測

Dollyワークロードの生成トークン処理率は次のとおり。固定バッチと連続バッチの比較を必ず併記する。

| 方式 | 生成トークン/秒 | 固定バッチ比 | 連続バッチ比 |
|---|---:|---:|---:|
| 通常の固定バッチ | 273.53 | 基準 | −77.2% |
| 連続バッチ | **1200.07** | +338.7% | 基準 |
| オラクル2ビン | 502.65 | +83.8% | −58.1% |
| オラクル4ビン | 720.17 | +163.3% | −40.0% |
| オラクル8ビン | 965.97 | **+253.1%** | −19.5% |
| 推定長2ビン | 485.70 | +77.6% | −59.5% |
| 推定長4ビン | 597.91 | +118.6% | −50.2% |
| 推定長8ビン | 684.02 | **+150.1%** | **−43.0%** |

予測長8ビンの684.02は、通常の固定バッチ273.53に対して約2.50倍の処理率である。「150.1%改善」は増分の割合であり、「150.1倍」ではない。オラクル8ビンとの差は281.95生成トークン/秒で、出力長予測が改善すれば回収できる可能性がある部分を示す。ただし連続バッチとの残る差も大きく、予測精度だけでその差が完全に消えるわけではない。

### 4. 予測器の分類精度

| ビン数 | 正しいビンへの分類 | 正しいビンまたは隣接ビン |
|---|---:|---:|
| 2 | 94.28% | 100.00% |
| 4 | 79.09% | 99.80% |
| 8 | 56.69% | 94.89% |

ビンを細かくすると完全一致の分類精度は下がるが、多くの誤りは隣接ビンにとどまる。したがって生成長を正確な整数として予測できなくても、短い要求と長い要求を大まかに分ける情報には価値がある。一方、隣接ビンへの誤分類でもバッチ内の長さ差が広がるため、オラクルほどの処理率にはならない。

### 5. 数値の比較対象と解釈

原著の見出しとなる150.1%改善は、Dollyの推定長8ビンを**固定バッチ**と比較した値である。同じ構成を連続バッチと比較すると43.0%低い。オラクル8ビンの253.1%改善も固定バッチ比であり、連続バッチより19.5%低い。制御済みオラクル16ビンが連続バッチを2.4%上回る結果は別の人工負荷であり、Dollyの結果と混ぜて平均しない。

測定した処理率は生成トークン/秒であり、要求の平均完了時間、最初のトークンまでの遅延、最悪時の待ち時間を直接示すものではない。バッチを形成するための待機時間を含む運用では、処理率改善と応答遅延が逆方向に動く可能性がある。負荷が低い場合や要求が特定ビンへ偏る場合は、ビン形成待ちを別途測定する必要がある。

### 6. 静的モデルと実機評価の差

理論はサービス時間を一様分布や指数分布とし、固定バッチが常にB件そろうことを仮定する。一方、実機評価のDollyでは出力長が3〜978トークンへ広く分布し、予測誤差もある。理論で等確率境界が最適という結論を、Dollyの予測値の等幅区間へそのまま当てはめるのは適切でない。実測では分布、予測器、バッチサイズ、実行基盤の制約を合わせて扱う必要がある。

原著は静的バッチの理論上限へ近づく性質を示す一方、実機では連続バッチを強い比較対象として置く。これにより「固定バッチの中での最適性」と「現代の推論基盤全体での競争力」を分離して評価できる。単純な理論モデルで性能改善の原因を理解し、実機で残る差を定量化したことが論文の意義である。

## 既存方式との関係

出力長予測を使う別のスケジューラは、短い要求の優先、バッチサイズの調整、KVキャッシュの予約などに予測値を使う。Multi-Bin Batchingは、予測値をバッチ形成前の待ち行列の分割へ使う。要求の処理順序を直接最適化するというより、同じバッチに入る要求の長さを揃えることが目的である。

連続バッチ化はデコードの反復単位で要求を入れ替え、空いた枠を再利用するため、固定バッチの最長要求待ちという問題を構造的に緩和する。複数ビン方式は固定バッチの制約内で空転を減らすので、連続バッチが利用できない実行基盤では有効な選択肢となる。連続バッチが使える場合には、予測長による待ち行列の分類を入場制御などへ応用する余地があるが、その組合せ方式の実測性能は本論文の結果ではない。

## 限界・適用条件

**固定バッチの理論に限定。** 等確率ビンの最適性とビン数を増やしたときの収束は、単一サーバ、固定B件、一様または指数的なサービス時間分布という条件に基づく。実際の長文脈プリフィル、連続バッチ、KVキャッシュの割当、GPU間通信、プリエンプションを含む総合的な最適性は示していない。

**予測誤差が残る。** 真の生成長は生成前に分からない。Dollyの推定長8ビンはオラクル8ビンより281.95生成トークン/秒低く、予測器の精度がスケジューリング性能を制限する。ビン数を増やすと完全一致の分類精度が低下し、細かい区間ほど誤分類の影響を受ける。

**低負荷の待機時間。** 各ビンでB件を集める必要があるため、ビン数を増やすと一つのビンへ要求が集まる速度が下がる。飽和時の理論処理率が高くても、低負荷での待ち時間や尾部遅延が悪化する可能性がある。タイムアウトで不完全バッチを発行する場合、理論の完全B件の前提から外れる。

**連続バッチに劣る実測。** Dollyの推定長8ビンは連続バッチより43.0%低く、オラクル8ビンでも19.5%低い。生成長を揃えるだけでは、連続バッチが持つ終了要求の即時入替えを代替できない。固定バッチとの改善率だけを取り出して最良の推論方式と結論づけるのは誤りである。

**評価環境の限定。** 実測は単一A100 80GB、llama.cpp、FP16、コンテキスト4096である。異なるGPU、CPUオフロード、複数GPU、長文脈入力、生成長の極端な偏り、モデルサイズの変化によって処理率が変わる。公式コード公開URLも確認できないため、実装の詳細を完全に再現できるとは限らない。

**サービス水準との交換条件。** 本論文の主な指標は生成トークン処理率であり、各要求の待ち時間や応答品質を同時に最適化するものではない。長い要求を同じビンに集めると、そのビンのバッチ形成が遅くなる可能性もある。サービス水準目標に合わせてビン数、境界、待機時間の上限を調整する必要がある。

## 実務上の示唆

固定バッチしか利用できない環境では、要求を到着順に無差別にまとめるより、予測生成長に応じて分類する方が空転を減らせる。導入時には出力長分布を観測し、長さ予測器の誤差と各ビンへの到着頻度を測定する。ビン数を増やす前に、バッチ形成待ち時間と生成処理率を別々に記録し、低負荷でもサービス水準を満たせるか確認する。

連続バッチ化が利用できる場合は、まずその標準機能を比較基準とする。Dollyの実測は、予測長8ビンが固定バッチより大幅に良くても、連続バッチには及ばないことを示す。ビン分けを連続バッチの入場制御へ応用するなら、新しい方式として別途実測する必要があり、論文の固定バッチでの改善率を流用してはならない。
