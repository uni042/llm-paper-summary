# Multi-Bin Batching for Increasing LLM Inference Throughput

## 概要
Multi-Bin Batchingは、固定バッチ（static batching）で生成長の異なるrequestを同じbatchへ入れたとき、短いrequestが終了しても最長requestが終わるまで計算unitが解放されないstraggler損失を、出力長に応じた事前分類で減らすschedulerである。各requestの予測service time、実LLMでは主に予測生成token数を (k) 個のbinへ割り当て、同じbin内でのみbatch size (B) のbatchを形成する。これによりbatch内の最大service timeと平均service timeの差を縮める。

論文はこの方式を待ち行列理論で形式化し、uniform service-time分布では各binが等しい確率質量を持つ境界が最適で、bin数を増やすと固定batchモデルの理想service rateへ漸近することを示す。ただしこれはcontinuous batchingまで含む普遍的なthroughput上限ではなく、requestをbatch途中で出し入れできないstatic batchingに限定した理論である。

2026年改訂版の実験では、この限定を明示するためnative continuous batchingもbaselineに加えている。単一NVIDIA A100 80GB上のllama.cppで、Dolly workloadのstatic batchingは273.53 token/s、continuous batchingは1200.07 token/s。Llama-3.2-3B-Instructのprompt hidden stateから長さを予測する実用設定では8-binが684.02 token/sとなり、static比150.1%改善するがcontinuous比では43.0%低い。真の出力長を使うoracle 8-binは965.97 token/sでstatic比253.1%改善し、continuousより19.5%低い。

## 問題設定
固定batchでは (B) requestを同時処理し、そのbatchのservice timeは概ね各request service timeの最大値になる。生成長が ([1,5,2,6]) 秒相当、(B=2) の例なら到着順に ((1,5),(2,6)) を組むと合計11秒必要だが、長さ別に ((1,2),(5,6)) を組めば8秒で済む。差はモデル計算を高速化したのではなく、終了済みslotを最長request待ちで遊ばせる時間を減らした結果である。

理論モデルは単一server、Poisson arrival、full batch size (B)、request service timeは独立同分布とし、主解析では一様分布、拡張では指数分布を扱う。service timeはdecode-dominant workloadでの出力長の抽象化であり、入力長差、prefill/decode混在、KV cache制約を理論式へ直接入れない。

したがって目的は「modern serving全体をモデル化する」ことではなく、固定batchに残るoutput-length heterogeneityだけを切り出し、length-aware groupingがどこまでその損失を取り戻せるかを解析することにある。

## 手法

### 1. k-binへのonline分類
予測service timeの範囲を境界 ([l_{i-1},l_i]) で (k) 個に分ける。request到着時に出力長を予測し、対応binへ入れる。各binは独立にrequestを蓄積し、(B) 件そろうとbatchを中央service queueへ送る。論文の既定policyは形成完了したbatch順にserveする。

同じbinには近い長さだけが集まるため、batch内の最大値が平均から離れにくくなる。一方、binを増やすほど各binへrequestが到着する頻度は下がるので、低負荷ではfull batch形成待ちが増える。このtrade-offは「saturated service rate」とrequest latencyを分けて解釈する必要がある。

### 2. throughputの理論化
固定batch serverのthroughputを
[
mathrm{Throughput}=rac{B}{E[t_{service}]}
]
と定義する。bin (i) のbatch service timeはそのbinに属する (B) requestの最大service timeであり、全体の期待service timeは各binの確率で重み付けした最大値期待値になる。

service timeが一様分布なら、固定 (k) に対し各binの確率質量を等しくする境界、すなわち区間を等間隔に分割することが最適になる。(k	oinfty) では同じservice time同士をbatch化する理想状態へ近づき、最大値による損失が消えて (B/E[t]) へ漸近する。

この上限はstatic batchingの理想値であり、continuous batchingではrequest completionごとにslotを再利用できるため比較対象が異なる。改訂版はこの区別を明示し、実測ではcontinuous batchingも直接測る。

### 3. 不完全な長さ予測
oracleでは真の出力長をbin割当に使うが、実deploymentでは生成前に未知である。最新版では、served modelの内部表現から出力長を推定する軽量regressorを用いる。Dolly実験ではLlama-3.2-3B-Instructのprompt prefill hidden-state featureを入力し、answer tokenを生成せずにbinを決める。

bin数が増えるとexact-bin accuracyは下がる。Dollyではk=2/4/8で94.28%/79.09%/56.69%だが、正解binまたは隣接binへ入るaccuracyは100.0%/99.80%/94.89%である。したがって細かいbinで誤分類が増えても、多くは近い長さの隣binに留まり、throughput利得の一部を維持できる。

別途、隣接binへ対称確率で誤分類するsimulationも行い、predictor errorだけの影響を切り分ける。このsimulationはreal llama.cpp測定値と混同しない。

## 評価

### 実験条件
real-inference実験は単一NVIDIA A100 80GB、FP16、context size 4096、llama.cpp backendで行う。各runの前に同一構成でwarm-upする。controlled oracle workloadは1024 request、batch 32、target output 500〜2000 token。Dolly-derived workloadは1478 request、batch 64、真の出力長3〜978 token、総408,352生成tokenである。指標はgenerated tokens/s。

### controlled oracle
一様な長さbinから作ったcontrolled workloadではstatic batchingが534.23 token/s、native continuous batchingが1348.49 token/s。Multi-Bin Batchingはk=16で1380.48 token/sとなり、static比158.4%改善し、この人工的に均衡したoracle条件ではcontinuousを2.4%上回る。

この結果は「Multi-Binが一般にcontinuous batchingより速い」ことを意味しない。真の長さを事前に知り、長さ分布もbinへ均等に構成したcontrolled条件で、固定batchのstragglerをほぼ除去した上限側の結果である。

### Dolly・oracle
現実的なDolly長さ分布ではstatic 273.53 token/s、continuous 1200.07 token/s。oracle k=2/4/8は502.65/720.17/965.97 token/sで、k=8はstatic比253.1%改善する。しかしcontinuousより19.5%低く、length groupingだけではiteration-level slot再利用の利点を完全には代替できない。

### Dolly・推定長
実predictorを使うとk=2/4/8は485.70/597.91/684.02 token/s。k=8がstatic比150.1%改善する一方、continuousより43.0%低い。oracleとの差281.95 token/sが、より良い長さ予測に残る改善余地を表す。

k=8でexact bin accuracyは56.69%しかないが、94.89%は正解または隣接binに入り、粗い「短い/長い」の順位情報だけでもstragglerを相当に減らせることを示す。

## 既存研究との差
連続バッチング（continuous batching）はdecode iterationごとに終了requestを外し新規requestを空slotへ入れるため、固定batchのhead-of-line blockingを直接解消する。Multi-Bin Batchingはこれを置き換えるのではなく、batch形成前にlength classを分けることで固定batch内のheterogeneityを減らす。

出力長予測を用いる既存schedulerがshortest-job-first、memory reservation、batch-size制御へ予測値を使うのに対し、本手法は予測値をbin partitionへ使う。理論上はoutput-length heterogeneityだけを独立に扱えるため、将来的にはcontinuous batchingのqueue classやadmission-control classとして組み合わせる余地がある。

## 限界
理論解析はstatic batching、single server、full batch、単純なservice-time分布を仮定し、prefill長、KV cache pressure、chunked prefill、preemption、multi-GPU通信を直接扱わない。したがって「bin数を増やせば理論上限へ近づく」という結果をproduction continuous-servingへそのまま適用できない。

real Dolly実験でも推定長8-binはcontinuous baselineより43.0%低い。長さaware groupingはstatic batchingの無駄を大きく回収するが、native continuous batchingの細粒度slot再利用を代替できていない。

またbinを増やすほどpredictorのexact classificationは難しくなり、各binのarrival rateも下がる。saturated throughputだけを見ればbin数を増やせても、低loadではbatch形成待ちがtail latencyを悪化させる可能性がある。最適 (k) と境界はarrival rate、length distribution、predictor error、SLOに合わせて選ぶ必要がある。
