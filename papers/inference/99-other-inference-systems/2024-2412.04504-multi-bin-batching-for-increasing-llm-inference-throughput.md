# Multi-Bin Batching for Increasing LLM Inference Throughput

## 概要
複数ビン バッチ化は、固定バッチ（静的バッチ化）で生成長の異なるリクエストを同じバッチへ入れたとき、短いリクエストが終了しても最長リクエストが終わるまで計算unitが解放されない遅延処理損失を、出力長に応じた事前分類で減らすスケジューラである。各リクエストの予測サービス 時間、実LLMでは主に予測生成トークン数を (k) 個のビンへ割り当て、同じビン内でのみバッチ 大きさ (B) のバッチを形成する。これによりバッチ内の最大サービス 時間と平均サービス 時間の差を縮める。

論文はこの方式を待ち行列理論で形式化し、uniform サービス-時間分布では各ビンが等しい確率質量を持つ境界が最適で、ビン数を増やすと固定バッチモデルの理想サービス 率へ漸近することを示す。ただしこれは連続バッチ化まで含む普遍的なスループット上限ではなく、リクエストをバッチ途中で出し入れできない静的バッチ化に限定した理論である。

2026年改訂版の実験では、この限定を明示するため標準 連続バッチ化も比較基準に加えている。単一NVIDIA A100 80GB上のllama.cppで、Dolly ワークロードの静的バッチ化は273.53 トークン/s、連続バッチ化は1200.07 トークン/s。Llama-3.2-3B-Instructのprompt hidden stateから長さを予測する実用設定では8-ビンが684.02 トークン/sとなり、静的比150.1%改善するがcontinuous比では43.0%低い。真の出力長を使うオラクル 8-ビンは965.97 トークン/sで静的比253.1%改善し、continuousより19.5%低い。

## 問題設定
固定バッチでは (B) リクエストを同時処理し、そのバッチのサービス 時間は概ね各リクエスト サービス 時間の最大値になる。生成長が ([1,5,2,6]) 秒相当、(B=2) の例なら到着順に ((1,5),(2,6)) を組むと合計11秒必要だが、長さ別に ((1,2),(5,6)) を組めば8秒で済む。差はモデル計算を高速化したのではなく、終了済みスロットを最長リクエスト待ちで遊ばせる時間を減らした結果である。

理論モデルは単一サーバ、Poisson 到着、完全 バッチ 大きさ (B)、リクエスト サービス 時間は独立同分布とし、主解析では一様分布、拡張では指数分布を扱う。サービス 時間はデコード-dominant ワークロードでの出力長の抽象化であり、入力長差、プリフィル/デコード混在、KV cache制約を理論式へ直接入れない。

したがって目的は「modern serving全体をモデル化する」ことではなく、固定バッチに残るoutput-長さ 異質性だけを切り出し、長さ-aware グループ化がどこまでその損失を取り戻せるかを解析することにある。

## 手法

### 1. k-binへのonline分類
予測サービス 時間の範囲を境界 ([l_{i-1},l_i]) で (k) 個に分ける。リクエスト到着時に出力長を予測し、対応ビンへ入れる。各ビンは独立にリクエストを蓄積し、(B) 件そろうとバッチを中央サービス 待ち行列へ送る。論文の既定policyは形成完了したバッチ順にserveする。

同じビンには近い長さだけが集まるため、バッチ内の最大値が平均から離れにくくなる。一方、ビンを増やすほど各ビンへリクエストが到着する頻度は下がるので、低負荷では完全 バッチ形成待ちが増える。このtrade-offは「saturated サービス 率」とリクエスト 遅延を分けて解釈する必要がある。

### 2. throughputの理論化
固定バッチ サーバのスループットを
[
mathrm{スループット}=rac{B}{E[t_{サービス}]}
]
と定義する。ビン (i) のバッチ サービス 時間はそのビンに属する (B) リクエストの最大サービス 時間であり、全体の期待サービス 時間は各ビンの確率で重み付けした最大値期待値になる。

サービス 時間が一様分布なら、固定 (k) に対し各ビンの確率質量を等しくする境界、すなわち区間を等間隔に分割することが最適になる。(k	oinfty) では同じサービス 時間同士をバッチ化する理想状態へ近づき、最大値による損失が消えて (B/E[t]) へ漸近する。

この上限は静的バッチ化の理想値であり、連続バッチ化ではリクエスト completionごとにスロットを再利用できるため比較対象が異なる。改訂版はこの区別を明示し、実測では連続バッチ化も直接測る。

### 3. 不完全な長さ予測
オラクルでは真の出力長をビン割当に使うが、実deploymentでは生成前に未知である。最新版では、served modelの内部表現から出力長を推定する軽量regressorを用いる。Dolly実験ではLlama-3.2-3B-Instructのprompt プリフィル hidden-state featureを入力し、answer トークンを生成せずにビンを決める。

ビン数が増えるとexact-ビン 精度は下がる。Dollyではk=2/4/8で94.28%/79.09%/56.69%だが、正解ビンまたは隣接ビンへ入る精度は100.0%/99.80%/94.89%である。したがって細かいビンで誤分類が増えても、多くは近い長さの隣ビンに留まり、スループット利得の一部を維持できる。

別途、隣接ビンへ対称確率で誤分類するsimulationも行い、予測器 errorだけの影響を切り分ける。このsimulationはreal llama.cpp測定値と混同しない。

## 評価

### 実験条件
real-推論実験は単一NVIDIA A100 80GB、FP16、context 大きさ 4096、llama.cpp backendで行う。各runの前に同一構成でwarm-upする。制御済み オラクル ワークロードは1024 リクエスト、バッチ 32、target output 500〜2000 トークン。Dolly-derived ワークロードは1478 リクエスト、バッチ 64、真の出力長3〜978 トークン、総408,352生成トークンである。指標はgenerated トークン/s。

### controlled oracle
一様な長さビンから作った制御済み ワークロードでは静的バッチ化が534.23 トークン/s、標準 連続バッチ化が1348.49 トークン/s。複数ビン バッチ化はk=16で1380.48 トークン/sとなり、静的比158.4%改善し、この人工的に均衡したオラクル条件ではcontinuousを2.4%上回る。

この結果は「複数ビンが一般に連続バッチ化より速い」ことを意味しない。真の長さを事前に知り、長さ分布もビンへ均等に構成した制御済み条件で、固定バッチの遅延処理をほぼ除去した上限側の結果である。

### Dolly・oracle
現実的なDolly長さ分布では静的 273.53 トークン/s、continuous 1200.07 トークン/s。オラクル k=2/4/8は502.65/720.17/965.97 トークン/sで、k=8は静的比253.1%改善する。しかしcontinuousより19.5%低く、長さ グループ化だけではiteration-level スロット再利用の利点を完全には代替できない。

### Dolly・推定長
実予測器を使うとk=2/4/8は485.70/597.91/684.02 トークン/s。k=8が静的比150.1%改善する一方、continuousより43.0%低い。オラクルとの差281.95 トークン/sが、より良い長さ予測に残る改善余地を表す。

k=8でexact ビン 精度は56.69%しかないが、94.89%は正解または隣接ビンに入り、粗い「短い/長い」の順位情報だけでも遅延処理を相当に減らせることを示す。

## 既存研究との差
連続バッチング（連続バッチ化）はデコード iterationごとに終了リクエストを外し新規リクエストを空スロットへ入れるため、固定バッチのhead-of-line blockingを直接解消する。複数ビン バッチ化はこれを置き換えるのではなく、バッチ形成前に長さ クラスを分けることで固定バッチ内の異質性を減らす。

出力長予測を用いる既存スケジューラがshortest-job-first、memory reservation、バッチ-大きさ制御へ予測値を使うのに対し、本手法は予測値をビン partitionへ使う。理論上はoutput-長さ 異質性だけを独立に扱えるため、将来的には連続バッチ化の待ち行列 クラスやadmission-control クラスとして組み合わせる余地がある。

## 限界
理論解析は静的バッチ化、single サーバ、完全 バッチ、単純なサービス-時間分布を仮定し、プリフィル長、KV cache pressure、chunked プリフィル、preemption、multi-GPU通信を直接扱わない。したがって「ビン数を増やせば理論上限へ近づく」という結果をproduction continuous-servingへそのまま適用できない。

real Dolly実験でも推定長8-ビンはcontinuous 比較基準より43.0%低い。長さaware グループ化は静的バッチ化の無駄を大きく回収するが、標準 連続バッチ化の細粒度スロット再利用を代替できていない。

またビンを増やすほど予測器のexact classificationは難しくなり、各ビンの到着 率も下がる。saturated スループットだけを見ればビン数を増やせても、低loadではバッチ形成待ちがtail 遅延を悪化させる可能性がある。最適 (k) と境界は到着 率、長さ distribution、予測器 error、SLOに合わせて選ぶ必要がある。
