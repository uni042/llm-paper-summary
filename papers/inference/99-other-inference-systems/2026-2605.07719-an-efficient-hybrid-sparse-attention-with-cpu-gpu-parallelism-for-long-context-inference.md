# An Efficient Hybrid Sparse Attention with CPU-GPU Parallelism for Long-Context Inference

> CPU常駐KV向けに出力寄与ベース予算配分とCPU・GPU協調疎注意を統合し、長文復号を最大3.7倍高速化する。
## 書誌情報
- **著者**: Feiyu Yao, Zhixiong Niu, Xiaqing Li, Yongqiang Xiong, Juan Fang, Qian Wang
- **著者・所属**: Beijing University of Technology／Microsoft Research／Beijing Jiaotong University
- **公開**: arXiv:2605.07719v1
- **種別**: preprint
- **対象**: CPU-GPUハイブリッド推論、KVキャッシュオフロード、疎注意、長文復号、異種デバイススケジューリング
- **実装**: 約2K行のPythonと3K行のC++/CUDAで実装。CPUはFBGEMM、AVX-512、OpenMP、GPUは複数CUDAストリーム、FlashDecoding、Top-Kカーネル、UVAを利用する。
## 概要
Fluxionは、長文復号でKVキャッシュをCPUメモリへ置く構成を対象に、CPU側の疎注意だけを高速化するのではなく、出力寄与に基づくKV予算配分、ヘッド別の選択粒度・予算決定、CPUとGPUの動的協調実行を同時に最適化する。41次元特徴から0.112Mパラメータの予測器がストリーミングヘッドと検索ヘッドを判別し、検索ヘッドではブロック粒度と必要予算の関係を予測する。CPUとGPUは共有優先度キューから検索タスクを取り、CPU上の疎注意とCPUメモリからGPUへKVを運ぶ経路を動的に使い分ける。A100とAMD EPYCの実機で、最強の固定疎ハイブリッド基準に対しLlamaで2.5〜3.7倍、Qwenで1.9〜3.4倍の出力トークン時間短縮を示し、LongBenchとL-Evalの平均品質差は完全注意に対して最大0.26点に留める。

Fluxionは、注意得点の被覆率ではなく最終注意出力への寄与からKV予算を決め、ヘッドごとにストリーミング型か検索型かをオンライン推定する。検索型ではブロック粒度と必要予算の経験的関係を予測し、グループ化クエリ注意の共有KVを考慮してデータアクセス量が最小になる粒度を選ぶ。さらにCPU上の疎注意と、CPUメモリからKVをGPUへ直接読んでGPUで疎注意する二経路を固定配置せず、共有優先度キューからCPUとGPUが動的に仕事を取ることで異種デバイスを重ねて使う。
## 問題設定
長文復号ではKVキャッシュがGPU容量を超えやすく、CPUメモリへのオフロードや事前充填・復号分離構成でCPU常駐KVが一般化する。GPUだけで疎注意を行う方式は選択KVを毎ステップPCIe越しに運ぶため帯域制約を受け、メタデータもGPUメモリを消費する。一方、CPU・GPUハイブリッド方式はCPU側で上位k選択と疎注意を行い出力だけをGPUへ戻せるが、CPU処理中にGPUが大きく遊休する。単純にKV予算を下げれば高速化するものの品質が急落し、固定ブロック粒度では上位k選択費用と疎注意費用の釣り合いも取れない。
## 新規性
Fluxionは、注意得点の被覆率ではなく最終注意出力への寄与からKV予算を決め、ヘッドごとにストリーミング型か検索型かをオンライン推定する。検索型ではブロック粒度と必要予算の経験的関係を予測し、グループ化クエリ注意の共有KVを考慮してデータアクセス量が最小になる粒度を選ぶ。さらにCPU上の疎注意と、CPUメモリからKVをGPUへ直接読んでGPUで疎注意する二経路を固定配置せず、共有優先度キューからCPUとGPUが動的に仕事を取ることで異種デバイスを重ねて使う。
## 手法
### 手法のあらまし
Fluxionは復号ステップごとに、予測、構成決定、実行、統合の順で動く。まずGPUでクエリが生成されると、0.112Mパラメータの軽量予測器が各注意ヘッドについて41次元特徴を読み、ストリーミングヘッドか検索ヘッドかを判定する。同時に検索ヘッドについて、最小KV予算の基準値とブロック粒度を粗くしたときの予算増加係数を出力する。ストリーミングヘッドは先頭64トークンと直近256トークンからなるGPU常駐の既定KVだけで必要精度を満たすと判断されたヘッドであり、CPUメモリ上のメタデータ走査、上位k選択、疎注意をすべて省く。これにより、検索を必要としないヘッドへCPU時間を使う固定疎構成の無駄を最初に除去する。

検索ヘッドでは予測した属性をCPUへ送り、候補ブロック長16、32、64、128ごとにデータアクセス量を評価する。この量はCPU常駐KVをブロック化したメタデータ走査量と、選択後に実際に読むK/V量の和で、グループ化クエリ注意では同じKVを共有するヘッド群に共通の粒度を使いつつ、各ヘッドの予算は個別に計算する。最小アクセス量となる粒度・予算を決めた後、各検索ヘッド群を一つのタスクとしてアクセス量の大きい順に共有優先度キューへ入れる。CPUとGPUは固定担当ではなく、それぞれ空いた時点で次のタスクを取得する。CPUはホストメモリ上で上位k選択と疎注意を直接実行し、GPUに割り当てられたタスクはUVAでCPUメモリの選択KVを読み込んでGPUカーネルを実行する。最後に検索部分の出力とGPU常駐既定KVに対する密注意出力を統合し、通常の出力射影と後続層へ渡す。この一連の流れにより、品質制約の下で読むKV量を減らすことと、残った疎注意仕事をCPU・GPUへ重ねることを同時に行う。

### 出力寄与ベースKV予算
注意シンクは高い注意得点を持っても値ベクトルのノルムが小さく、注意得点被覆率だけでは最終出力誤差を正しく表せない。実測では注意得点を95%保持しても、25%の注意ヘッドで相対出力誤差が20%を超える。Fluxionは完全注意のヘッド出力との差を直接基準にし、所定の相対出力誤差を満たす最小KV予算を教師信号として作る。先頭トークンへ高得点が集中していても、その値ベクトルが小さければ大きな予算を割く必要がないため、得点だけを見る方式の過剰配分を避けられる。

さらにヘッド間で最終表現への寄与が異なることを考慮する。各ヘッドの誤差は、そのヘッドだけの出力ノルムではなく同一ステップの全ヘッド中の最大出力ノルムで正規化し、最終表現への相対的重要度を反映する。これにより、出力がほぼゼロのヘッドへ高いKV予算を割くことを避ける。オフラインでは複数のブロック粒度と予算を列挙して精度制約を満たす最小値を求め、その結果をオンライン予測器の教師にするため、実行時には完全注意を計算せず低費用で近似できる。

### ヘッド属性予測と粒度・予算選択
予測器は構造、KV分布、QK相互作用、注意出力寄与、クエリ動態、事前充填時の予算推定、ヘッド間特徴からなる41次元入力を使う共有多層パーセプトロンで、パラメータ数は0.112Mである。検索ヘッドでは必要予算をブロック長の二進対数に対する線形式で近似する。

CPU側選択器は候補粒度ごとにメタデータ量とKV量の上界を合計し、最小の候補を採る。ストリーミングヘッドは検索自体を省き、検索ヘッドだけをCPU側疎注意の対象にするため、固定粒度・固定予算より選択費用と注意費用を同時に減らせる。

### 優先度付きCPU・GPU協調実行
検索タスクの実時間はヘッド群ごとの選択集合やCPU側長尾遅延に依存するため、精密な実行時間予測は難しい。Fluxionは予測時間ではなくデータアクセス量を優先度に使い、大きいタスクを先に共有キューへ置く。

CPUとGPUはそれぞれ現在のタスクを終えた時点で次の仕事を取り、CPU側ではFBGEMM・AVX-512・OpenMP、GPU側では複数CUDAストリームとUVAを使う。GPUへ割り当てた仕事はCPUメモリの選択KVをPCIe経由で直接読み、CPUが詰まったときのGPU遊休を埋める。

### 全体のデータ／制御の流れ
実装は約2K行のPythonと3K行のC++/CUDAからなり、その他の演算子はHugging Face Transformersを再利用する。スケジューリングとGPUカーネル起動用にCPUコア1基を専有し、残りを注意計算へ使う。

予測器はLongBench V2から128K以上の50事例を訓練に使い、4K間隔・各区間8復号ステップで教師データを作る。Llama-3.1-8Bでは約1250万訓練標本となる。同ベンチマークを予測器訓練に使うため、LongBench V2自体の品質値は報告せずデータ漏洩を避けている。
## 評価条件
- **ハードウェア**: AMD EPYC 7V13 CPU、24コア、220GBホストメモリ、推定57GB/sメモリ帯域とNVIDIA A100 80GB。CPU・GPU間はPCIe 4.0、理論32GB/s。20 CPUコアを疎注意計算へ割り当てる。
- **ソフトウェア**: Hugging Face Transformersの既存演算子を基盤に、CPUはFBGEMM・AVX-512・OpenMP、GPUはCUDAストリーム、FlashDecoding、上位k選択カーネル、統合仮想アドレス方式を用いる。
- **比較対象**: FULL、w/o Fluxion (blk=16,bgt=0.05)、w/o Fluxion (blk=16,bgt=0.02)、w/o Fluxion (blk=32,bgt=0.05)、w/o Fluxion (blk=32,bgt=0.02)
Llama-3.1-8B-InstructとQwen2.5-7B-Instructを評価する。品質はLongBenchの重複除外後14タスク、L-Evalの開放型13タスク、RULERの13タスクを使い、合計40タスク。LongBenchは8K超、L-Evalは3K超の事例を用い、RULERは8K、16K、32K、64K、128Kで各タスク100事例を合成する。効率評価は長さを制御できるRULERを使い、固定長バッチと混合長バッチを測る。基準は同じCPU・GPUハイブリッド経路からFluxion最適化だけを外した構成で、先頭64トークンと直近256トークンをGPUに保持し、Quest方式のメタデータを共通利用する。固定構成としてブロック長16/32、KV予算2%/5%を比較する。品質指標はRULER精度、LongBenchとL-EvalのF1/ROUGE、効率指標は出力トークン当たり時間。
CPU常駐KVを持つ復号処理を対象とした単一ノード実機評価。主要な速度主張はA100とEPYC、PCIe 4.0の組合せに依存する。予測器訓練にLongBench V2を使うため同データセットで品質を報告せず、別のLongBench・L-Eval・RULERで評価する。
## 主要結果
Fluxionの主要結果は、CPU常駐KVを使う長文復号で、品質をほぼ維持したまま固定の疎ハイブリッド構成より出力トークン当たり時間を大幅に短縮したことである。Llama-3.1-8Bでは測定条件全体で2.5〜3.7倍、Qwen2.5-7Bでは1.9〜3.4倍高速で、Qwenのバッチ4では文脈32Kの1.9倍から128Kの3.4倍へ利得が拡大する。これは長文ほどCPU常駐KVへの注意が復号時間を支配し、ヘッド別の検索省略・粒度選択とCPU・GPU協調の効果が大きくなるためである。

品質面では、LongBench平均が完全注意比でQwen -0.13点、Llama +0.02点、L-Evalが-0.24点と-0.26点に留まる。RULERでは平均差がQwen -1.54点、Llama -0.78点とやや大きいものの、Fluxionは最良の固定疎構成を両モデルで上回る。実用上は、単にKV予算を2%まで削って高速化するのではなく、出力寄与に応じて必要なヘッドだけ検索し、精度制約を満たす範囲で予算と粒度を動的に変えることで速度と品質を両立している点が重要である。さらに代表的なQwen 32K設定ではGPU遊休率を70.65%から45.78%へ下げており、速度向上が単なる疎性ではなくCPU待ち時間をGPU仕事で埋めるシステム設計からも生じている。

- 出力トークン当たり時間短縮 / 2.5〜3.7倍 (比較対象: 固定疎ハイブリッド構成 blk=16, bgt=0.05; 条件: Llama-3.1-8B-Instruct、RULER、複数バッチ・文脈長) — ヘッド別予算・粒度最適化とCPU・GPU協調が固定構成を一貫して上回る。

- 出力トークン当たり時間短縮 / 1.9〜3.4倍 (比較対象: 固定疎ハイブリッド構成 blk=16, bgt=0.05; 条件: Qwen2.5-7B-Instruct、RULER、32K〜128K) — 文脈が長いほど注意が復号時間に占める割合が増え、Fluxionの利得も大きくなる。

- LongBench平均差 / Qwen -0.13、Llama +0.02点 (比較対象: 完全注意; 条件: 14タスク平均) — 実タスク平均では品質差がほぼない。

- L-Eval平均差 / Qwen -0.24、Llama -0.26点 (比較対象: 完全注意; 条件: 13開放型タスク平均) — 開放型生成は疎近似にやや敏感だが平均劣化は小さい。

- RULER平均精度 / Qwen 72.53、Llama 85.03 (比較対象: 完全注意 74.07、85.81; 条件: 8K〜128K、13タスク) — 固定疎構成の最良値72.41、84.55も上回り、長さを跨いだ動的構成の有効性を示す。

- GPU遊休率 / 70.65%から45.78%へ低下 (比較対象: Fluxion最適化なしのハイブリッド構成; 条件: 代表的なQwen、32K文脈設定) — CPU側疎注意待ちをGPU側仕事で埋める協調実行が異種資源利用率を改善する。

### 負の結果・境界条件
- 完全注意と同一ではなく、RULERではQwen平均が1.54点、Llama平均が0.78点低い。QwenのLongBenchではLCCが完全注意比-2.03点など局所文脈に敏感な一部タスクで低下が大きい。固定2%予算は高速でも品質が悪く、事前分析では5%から2%へ下げると一部検索タスク精度が約半減するため、単純な予算削減だけでは代替できない。

### 結果の読み方
高速化の源泉は三つある。ストリーミングヘッドをCPU検索から外して不要な仕事を消すこと、検索ヘッドごとに粒度と予算を変えてメタデータ走査とKV走査の総量を減らすこと、CPUとGPUを固定役割にせず共有キューで重ねてGPU遊休を減らすことである。混合長バッチでもLlamaの中央値速度向上は16K〜64Kで約2.3倍、32K〜128Kで約2.6倍へ増え、長文ほど効果が強い。
## 品質への影響
近似疎注意のため品質保証は統計的評価に基づく。LongBenchとL-Evalでは平均差が0.26点以内だが、RULERではモデルにより0.78〜1.54点低下し、個別タスク差も存在する。
## 既存研究との差
Questなど従来のブロック疎注意は関連ブロックの選択方式を中心に扱うのに対し、FluxionはCPU常駐KVで上位k選択と疎注意がCPUボトルネックになる点を起点にする。HGCAやRetrievalAttentionのようなCPU・GPUハイブリッド方式に対しては、GPU常駐集合とCPU疎注意の固定分担ではなく、ヘッド属性とアクセス量に応じてCPUとGPUへ検索タスクを動的に振り分ける。KTransformers系のCPU・GPU協調と同じ異種資源利用の問題意識を持つが、対象はMoEエキスパートではなくCPU常駐KV上の長文注意である。
## 限界
主要評価はA100 80GBとAMD EPYC 7V13、PCIe 4.0の単一構成であり、CPUメモリ帯域やPCIe帯域、GPU世代が変わるとCPU経路とGPU経路の相対速度も変わる。予測器は対象モデルごとにオフライン教師データを作って訓練するため、完全な訓練不要方式ではなく、モデル追加時の準備費用がある。品質は平均では完全注意に近いが、RULERや一部コード・要約タスクでは低下が残る。CPU常駐KVを前提にした復号最適化なので、KV全体がGPUへ収まる短文脈や事前充填支配のワークロードでは同じ利得を期待できない。

## 研究上の位置づけ
本リポジトリの重点であるCPU/SSD/NVMeオフロード・階層メモリ系統に直接関係する。FluxionはKVをCPUへ置く容量拡張自体ではなく、その状態で復号時に必要なKVをどの粒度・予算で読むか、CPUとGPUのどちらで処理するかを最適化する。したがってKVキャッシュオフロードや分離型事前充填・復号システムの上位に置ける実行最適化であり、PCIe帯域だけでなくCPUメモリ帯域とGPU遊休を同時に扱う点が重要である。SSDまで含む多段階階層や先読みは本論文の対象外だが、CPU常駐層での選択量を削減するため、より下位のSSD/NVMe階層からの昇格量を抑える設計と補完可能である。
