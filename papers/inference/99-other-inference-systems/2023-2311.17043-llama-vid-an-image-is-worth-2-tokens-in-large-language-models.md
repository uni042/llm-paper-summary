# LLaMA-VID: An Image is Worth 2 Tokens in Large Language Models

## 概要
LLaMA-VIDは、videoをVision-Language Model（VLM）へ入力するとframe数に比例してvisual tokenが増え、長時間videoがLLMのcontext長とattention計算を圧迫する問題を、各frameを原則2 tokenへ圧縮して解く。2 tokenは、ユーザー指示に関連するvisual cueを集約する文脈トークン（context token）と、frame全体の見た目を保持する内容トークン（content token）で役割を分ける。

既存のBLIP系は1 imageあたり32 token、LLaVA系は256 token超を使うため、10K frameのvideoでは32万token以上になり得る。LLaMA-VIDはvideo時にcontext 1 + content 1 token/frameへ落とし、長時間videoでもtoken増加率を大幅に下げる。一方、単一imageではcontent token数を増やしてdetailを保持でき、同じmoduleをresource budgetに応じて可変圧縮として使う。

## 問題設定
単純に時間方向へframeを間引くと、短い瞬間に現れるdetailやplot上重要なeventを失う。各frameをglobal averageだけで1 tokenへ畳むと効率は高いが、ユーザーが「この人物は何をしているか」のように特定内容を尋ねても、質問に応じて重要領域を選び直せない。

そこでLLaMA-VIDは「質問に応じてframeから選ぶtoken」と「質問と独立にframe内容を残すtoken」を併用する。前者でinstruction-relevantな情報を狙って保持し、後者でcontext tokenが拾わなかった視覚情報を補う。

## 手法

### visual encoderとtext decoder
各frame `V_t` は事前学習済みvisual encoderでpatch列 `X_t ∈ R^(N×C)` へ変換する。既定構成ではEVA-Gをvisual encoderに使い、training中は固定する。ユーザーinstructionとvisual embeddingをtext decoderへ入れ、instruction内容を表す複数のtext query `Q_t` を生成する。既定decoderはQFormerである。

text decoderの役割はresponse textを作ることではなく、「いまの質問に対してどのvisual cueを見るべきか」というqueryを作ることである。これにより後段のcontext attentionが同じframeでも質問ごとに異なる情報を抽出できる。

### context token
context attentionは `Q_t` とframeのpatch feature `X_t` の内積attentionを計算し、各text queryが関連visual patchをweighted aggregationする。複数queryの出力を平均し、1本のcontext embedding `E_t` へ縮約する。最後にlinear projectorでLLM embedding空間へ写像し、1個のcontext tokenを得る。

入力はtext-guided queryとpatch feature、出力はinstruction依存の1 tokenである。質問に関係するpatchへsoftmax weightを寄せるため、単純global poolingより「何を残すか」をuser instructionで変えられる。一方、質問に直接関係しない情報は捨てやすいため、content tokenを別に残す。

### content token
content側はvisual embeddingをadaptive average poolingし、計算budgetに応じて `n` 個へ縮約する。単一imageでは元のpatch resolutionを保つため `n` を大きくでき、長videoでは `n=1` のglobal poolingまで圧縮する。linear projectorでLLM空間へ写像し、context tokenと連結する。

videoの標準設定では1 context + 1 content、計2 token/frameである。content数を増やせばdetailは増えるがLLM input長とattention costも増えるため、`n` が直接quality-efficiencyのknobになる。

### 3段階training
第1段階のmodality alignmentではvisual featureとlanguage spaceのalignmentを学ぶ。第2段階ではimage/video instruction tuningによりmultimodal instruction followingを学ぶ。第3段階はlong-video tuningで、MovieNetの400本超のlong movieとscriptを使って約9Kのmovie-level instruction pairを構築する。

9Kはsummary約1K、plot/character約4K、detail/reasoning約4Kから成る。long-video tuningではposition rangeも拡張し、frame visual tokenとsubtitle tokenを連結する。論文は64K token、3時間超のvideoを扱える構成を示す。全trainingは8×NVIDIA A100で実施し、論文本文では2日以内で完了するとする。

## 評価

### zero-shot video QA
video評価では1 FPSでframeを抽出し、各frameを2 tokenにした条件でMSVD-QA、MSRVTT-QA、ActivityNet-QAを比較する。Vicuna-7B版はMSVD-QA accuracy 69.7 / score 3.7、MSRVTT-QA 57.7 / 3.2、ActivityNet-QA 47.4 / 3.3を記録する。Vicuna-13B版は70.0 / 3.7、58.9 / 3.3、47.5 / 3.3である。

当時の強い比較対象BT-Adapterのaccuracyは67.5、57.0、45.7なので、7B版でもMSVDで+2.2 point、MSRVTTで+0.7 point、ActivityNetで+1.7 pointである。2 token/frameという強い圧縮下でもvideo QA accuracyを維持できることが、dual-token機構の主要なend-to-end確認になっている。

### generative video評価
Video-ChatGPT由来の5指標でも7B版はCorrectness 2.96、Detail 3.00、Context 3.53、Temporal 2.46、Consistency 2.51、13B版は3.07、3.05、3.60、2.58、2.63である。BT-Adapter 7B相当の2.68、2.69、3.27、2.34、2.46を全指標で上回る。

単に短いQA answerだけでなく、detail、temporal relation、response consistencyでも2-token representationが機能することを示す。

### context/contentのablation
224×224 image、1 context + 1 contentを基準にtoken typeを切り替える。contentのみではGQA 53.3、POPE 80.9、ScienceQA-Image 66.1、TextVQA 46.5、contextのみでは54.3、82.4、67.7、48.3、両方では55.5、83.1、68.8、49.0になる。

context token単独がcontent単独を全4taskで上回ることから、instruction-guided selection自体に価値がある。ただし両方を併用したときが全taskで最良であり、質問依存情報とgeneric visual contentが相補的であることを確認する。

### token数と圧縮率
uncompressed相当の256 content tokenにcontextを1個加えると、GQA 61.9→63.0、POPE 85.5→86.6、ScienceQA 67.5→67.7、TextVQA 53.0→53.8へ改善する。context 1個の追加は高token設定でも有効である。

contentを256→64へ落とすと性能低下は多くのtaskで1〜2 point程度だが、1 contentまで圧縮するとGQA 55.5、POPE 83.1、ScienceQA 68.8、TextVQA 49.0となる。論文はcontextなし256 token設定と比べ、2-token設定でvisual-token由来の計算を約1/128へ減らしながら、おおむね2〜6 pointの性能低下に留められると整理する。ScienceQAではむしろ2 token設定が高く、taskによって細粒度patchが不要なことも示す。

## 既存研究との差
Video-ChatGPTのようなspatial/temporal poolingはvisual tokenを圧縮するが、ユーザーinstructionに応じた「残す情報」の選択を明示的に持たない。BLIP/QFormer系のquery tokenは複数tokenを使うのに対し、LLaMA-VIDはtext-guided queryを内部で使いながらLLMへ渡すcontext側を1 tokenへ集約する。

したがって本方式の特徴は単なる2-token compressionではなく、instruction-dependent context tokenとbudget-dependent content tokenを分離し、imageからhour-long videoまで同じinterfaceでscalableにする点にある。

## 限界
2 token/frameでもframe数には線形に増えるため、極端に長いvideoではLLM context長が再び上限になる。1 FPS samplingでは短時間eventを取り逃す可能性もある。3時間級の対応は64K context、subtitle、long-video tuningを含む特定構成の結果で、任意のLLMへ2 tokenを追加するだけで同じ長さを扱えるわけではない。

contentを1 tokenへ圧縮するとimage benchmarkで2〜6 point程度落ちるtaskがあり、detail-sensitiveな用途ではtoken数を増やす必要がある。context tokenもuser instructionへ依存するため、曖昧な質問や後から別の質問へ再利用する場合には、最初のqueryが拾わなかったvisual detailをcontent側で補う必要がある。
