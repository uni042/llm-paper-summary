# Block-Sparse FlashAttention：正確なQKスコアで選んでValue側だけを省く疎注意

## 概要

Block-Sparse FlashAttention（BSFA）は、長文脈Transformerのprefillで、FlashAttention-2のブロックごとのQuery–Key（QK）スコアを**正確に計算した後**、重要度が低いブロックに対するValue（V）の読み出しと注意重み×Value（PV）行列積を省くCUDAカーネルである。一般的な疎注意がQKを計算する前にどのブロックが重要かを予測するのに対し、BSFAはQK計算を犠牲にしない。ブロック内の最大スコアが、層・ヘッド・系列位置ごとに事前校正した閾値を超えた場合だけ、そのブロックをsoftmaxとPVに反映する。

論文はLlama-3.1-8B-InstructをNVIDIA A100 80GBで評価し、LongBenchでFlashAttention-2比1.10倍のTTFT高速化を達成しながら品質を99.1%保持、64K Needle-in-a-Haystackで1.24倍と約99%保持を報告する。ただし、1.24倍は特定の検索タスクでの値であり、一般の長文脈推論やデコード生成速度の保証ではない。128KのRULERで品質を99%以上保持する設定の速度改善は1.06倍にとどまる。QK計算を全量残すため、QKとPVが同程度の費用である通常の注意では、演算省略の理論的上限がある。<https://arxiv.org/html/2512.07011v1>

## 問題設定

FlashAttention-2はQ、K、Vを小さなタイルへ分け、GPUのオンチップメモリ内でsoftmaxの正規化状態を逐次更新する。これにより注意スコア行列全体をHBMへ書き出さずに済むが、すべての有効なQKペアに対して内積とPV積を計算する点は変わらない。長い入力ではQKとPVがそれぞれ文脈長の二乗に比例し、演算量が大きくなる。

従来の疎注意には、固定のスライディング窓・局所マスクや、圧縮したQ/Kから事前に関連ブロックを予測する方法がある。QK自体を省ければ理論上の演算節約は大きいが、散在する重要トークンや長距離参照を予測段階で取り逃すと、後から復元できない。特に長文脈の検索や複数文書の推論では、必要なトークンが局所窓の外にあることが多い。SpargeAttentionは圧縮したブロックで重要度を推定し、選ばれたブロックで追加の局所フィルタを使うが、推定誤差、マスク生成費用、GPUスレッド間の処理量のばらつきが問題となる。

BSFAは「QKの正確なスコア計算を残す代わりに、Value側の無駄だけを安全寄りに減らす」という中間点を選ぶ。各QブロックとKブロックのスコア最大値を取り、全要素が小さいブロックはsoftmax後の寄与も小さいだろうと推定する。実際には、ブロック最大値はsoftmaxでの正規化後の質量そのものではなく、全ブロック間での相対値や複数の小さい寄与の累積を完全には保証しない。したがって閾値選択は近似であり、出力は密なFlashAttentionと数学的に同一とは限らない。

## 手法

### 1. FlashAttention-2のQKタイルの直後にゲートを置く

Queryを行方向に128、Key/Valueを列方向に64のブロックへ分ける。各ブロック対 `(i,j)` で、通常どおりスケール付きQKスコア行列 `S_ij = Q_i K_j^T / sqrt(d)` をGPUで計算する。次にブロック全体の最大値 `s_max(i,j)` を取る。閾値 `T[layer,head,query_block,k]` と比較し、最大値が閾値を下回る場合は、そのブロックのVをHBMから読み込まず、`softmax(S_ij)×V_j`、出力累積、正規化統計の更新も実行しない。最大値が閾値以上なら通常のFlashAttention-2と同じ更新を行う。

このゲートは**QK計算後、Vロード前**に入る。従って省けるのはPV演算とVの転送、および付随する指数関数・正規化・累積であり、QKの演算量は減らない。論文§4.3の「50%」は、QKとPVの支配的な演算量が概ね半々という前提で、すべての対象ブロックのPVを省いた場合の理論的な上限を指す。実際にはゲートを通るブロック、対角ブロック、カーネル分岐の費用があるため、エンドツーエンドで50%高速化するという意味ではない。

因果注意では対角ブロックを必ず処理する。直近トークン間の局所依存と、対角内部の因果マスクを保持するためである。閾値で落としたブロックはオンラインsoftmaxの最大値・分母・出力累積に参加させない。よって近似注意としては一貫した正規化になるが、密なsoftmaxで小さくても合計すると意味のある質量が削られるリスクは残る。

### 2. 校正データから層・ヘッド・位置別閾値を決める

学習済みモデルの重みを変更せず、少数の校正サンプルを通して各Queryブロックの候補Keyブロックの最大スコア分布を収集する。各位置で上位 `k` 個のオフ対角ブロックを残す境界値を求め、サンプル間で平均した閾値を保存する。閾値は層、ヘッド、Queryブロック位置、目標ブロック数に依存する。異なる `k` 用の閾値を複数保持すれば、運用時に速度と品質の目標に応じて切り替えられる。

論文の閾値テンソルは概念上 `[S, L, H, ceil(N_max/B_M)]` で、Sは保持予算の設定数である。長さ65,536でLlama-3.1-8Bの1設定に必要な閾値は約52万値、パラメータ数に比べ小さい。校正より長い系列では末尾位置の閾値を再利用する。これは後半の注意分布が安定するという経験則に依存するため、極端な長さや異なるモデルへの汎化を保証するものではない。

重要なのは、校正サンプル上ではTop-kに対応する閾値を求めても、**推論時には正確にkブロックを残すTop-k演算を毎回実行しているわけではない**ことである。新しい入力のスコア分布が変われば、実測密度は目標密度からずれる。論文Table 1は予測密度と実測密度を別々に記載しており、たとえば64K・k=192では予測0.35、実測0.36±0.05である。一定の処理量へ近づける設計だが、完全な固定作業量ではない。

### 3. 演算節約とスレッド間のバランス

QKとPVはどちらもブロックサイズに対して概ね `2 B_M B_N d` FLOPsである。PVを省くと、そのブロックに対する同程度の行列積とVのHBMロードを省ける。QKスコアの最大値計算と閾値比較は、Tensor Core行列積に比べ小さな費用とされる。SpargeAttentionのような外部の粗いマスク生成・圧縮段階を挟まないため、短めの32Kでも処理の上乗せが小さいという設計である。

SpargeAttentionではブロックごとに残る仕事量が大きく変動し、GPUワープやブロックの実行時間が長いものに引っ張られることがある。BSFAは位置別に保持予算を校正して作業量を揃えようとする。ただし、実際のゲート結果は入力に依存するので、スレッド負荷の均一性は測定条件次第である。正確なQKスコアを維持する利点は重要ブロックの見逃しを減らすことだが、QKまで省く方式より理論上の高速化上限は低い。

## 評価

### 実験条件と比較対象

| 項目 | 条件 |
|---|---|
| GPU | NVIDIA A100 80GB、CUDA 12.1 |
| モデル | Llama-3.1-8B-Instruct、FP16 |
| カーネル | FlashAttention-2拡張、Qタイル128、KVタイル64 |
| 校正 | RULERの一部タスクカテゴリから16標本 |
| 評価 | RULER 32K・64K・128K、LongBench、64K Needle-in-a-Haystack |
| 独立性 | RULERは校正カテゴリと評価カテゴリを分離。LongBenchはRULER校正閾値を再利用 |
| TTFT測定 | 校正とは別カテゴリから各系列長10標本、LongBenchは最長10標本 |
| 比較 | 密なFlashAttention-2、SpargeAttention、固定Sliding Window |
| 指標 | ベンチマークaccuracy、TTFT速度比、予測・実測ブロック密度 |

SpargeAttentionはQ/KをINT8化し、VはFP16のA100対応実装を使う。BSFAはFP16のままゲートによる計算省略を評価する。FlashAttention-3はHopper向けのため、A100での比較対象には含まれない。TTFTは主として長文脈prefillの短縮を反映する指標で、生成全体のtokens/sやデコード段階のTPOTを直接示すものではない。

論文Table 1では、品質を密なFA2の99%以上保持する運用点で、32Kが1.03倍、64Kが1.05倍、128Kが1.06倍である。最大1.16倍の設定では128Kのaccuracyが76.79%から73.71%へ落ちており、品質低下が無視できる設定の速度と混同できない。32Kのk=192では86.42%が密なFA2の85.98%を上回るが、速度は1.00倍であり、スパース化が必ず両方の指標を改善するわけではない。

### LongBenchとNeedle：転移とタスク依存

LongBenchのTable 2では密なFA2の40.24%に対し、BSFA k=96は39.88%、速度1.10倍で、基準accuracyの99.1%を保持した。k=32では39.39%・1.16倍、k=128では40.03%・1.08倍となる。校正はRULERの16標本のみで、LongBench固有の追加校正はしていない。これは一定のデータセット間汎化を示すが、モデルや言語・タスクが大幅に変わった場合の保証ではない。

対照のSpargeAttentionはLongBenchで、閾値τ=0.4なら30.06%・1.09倍、τ=0.5なら33.11%・1.02倍、τ=0.6なら35.87%・0.98倍であった。Sliding Windowは64ブロック（4096トークン）で13.43%、96ブロック（6144トークン）で20.29%にとどまる。固定窓では遠方の必要トークンを捨てやすいこと、SpargeAttentionでは粗い重要度予測と追加処理の費用が無視できないことを示す。ただし比較は著者が選んだA100対応実装と閾値の範囲に限られ、別のGPU世代での一般的な優劣とは言えない。

64K Needle-in-a-Haystackの単一キー検索では、BSFAはk=32ブロックで基準の約99%の正答率を保ちながら1.24倍高速化した。重要な事実が少数の位置に集中する検索タスクでは、PVを処理するブロックを大胆に削れる。一方、複数文書を横断する推論や広範囲の要約では、分散した情報を保持するためにより多くのブロックが必要になる。論文自体も、RULERの広いタスク群では同程度の品質保持に数百ブロックが必要であることを示す。

### 校正安定性と負の結果

予測密度と実測密度の対応は64K k=192で0.35対0.36±0.05、128K k=512で0.44対0.44±0.06と概ね一致した。小さな校正集合で平均的な密度を予測できる一方、入力間のばらつきが残る。高いスパース性を選ぶと品質低下は増える。64KのSpargeAttention τ=0.3ではaccuracy66.04%・速度1.19倍であり、密なFA2の84.96%から18.92ポイント低下する。速度だけを最大化すると、実際の長文脈タスクでの利用価値を損なう。

BSFA自体にも負の条件がある。RULER 128Kでk=512は1.16倍と速いが、accuracyが3.08ポイント低い。32K k=192ではaccuracyが高くても速度改善はない。密なQK演算を全て残すので、Attention全体が支配的でない短い入力、あるいはV側の演算を削ってもGPUの律速が変わらない条件では利得が限定的となる。測定はA100 80GBの単一モデルであり、H100、RTX 4070 SUPER、各種MoE・GQA以外のモデルへそのまま適用できると断定できない。

## 既存研究との差

FlashAttention-2との違いは、正確なQKスコアを計算した直後にV側の仕事を省くことにある。FlashAttention-2は密な注意を数値的に再現するのに対し、BSFAは重要でないと判断したブロックの寄与をゼロにするため、品質とのトレードオフが生じる。SpargeAttentionとの違いは、QKを計算する前に圧縮表現で候補を選ぶのではなく、QKを正確に計算してからVを省く点にある。固定Sliding Windowとの違いは、遠方にある重要なトークンをスコアに基づいて残せる点である。

STOFのように既に疎な注意マスクを受け取ってGPUカーネル・演算子融合を最適化する方式とも異なる。BSFAは密なモデルのQKスコアから疎にする判定をカーネル内で行う。一方、KVキャッシュをCPUへ退避し検索で一部を取り寄せるPQCacheのような方式とは、最適化対象が異なる。BSFAの主眼は**prefillのPV演算とV読込**であり、CPU–GPUのKVオフロードやデコード時のキャッシュ容量削減ではない。両者を比較するときは、品質、TTFT、TPOT、メモリ使用量を混ぜない必要がある。

## 限界・適用条件

第一に、QKを全計算するため、長文脈Attentionの演算量のうち省けるのはPV側が中心である。論文の「約50%」は対象ブロックの理論的な演算・Value転送節約であって、モデル全体の50%高速化ではない。第二に、閾値はモデル・層・ヘッド・位置と保持予算に依存し、別モデルへの転用は追加検証が必要である。第三に、校正より長い入力では最後の閾値を再利用するため、未知の分布や極端な文脈長では目標密度と実測密度がずれる可能性がある。第四に、全QKを観測してもsoftmaxの累積質量を完全に保証するものではなく、削除ブロックが品質へ影響し得る。第五に、実測はLlama-3.1-8B・A100・FP16・特定タイル・限定された評価タスクであり、Windows環境や他のGPUでの再現値は未確認である。

公式実装はCUDAカーネルであり、FlashAttention-2への拡張として提供される。GPU世代、CUDA版、ビルド環境、モデルの注意レイアウトに依存するため、既存のllama.cppやOllamaへ自動的に適用される機能ではない。長文脈prefillが支配的で、品質を保ったまま10%前後のTTFT改善を狙う実装候補として評価するのが妥当である。生成速度の大幅改善を期待するなら、別途decode側の最適化と合わせて検証する必要がある。
