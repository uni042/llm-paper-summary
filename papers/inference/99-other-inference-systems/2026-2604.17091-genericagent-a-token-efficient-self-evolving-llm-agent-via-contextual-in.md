# GenericAgent：長期エージェントの文脈情報密度と経験再利用によるトークン効率化

## 概要

LLMエージェントが長い業務を実行すると、ツールの説明、ブラウザの観測結果、実行ログ、途中の推論、過去の会話、再利用できる知識が入力文脈へ蓄積する。文脈窓が大きくても、古い観測や不要な説明が多ければ、次の判断に必要な情報が埋もれ、トークン費用も増える。また、あるタスクで見つけた成功手順を保存しなければ、次の類似タスクで同じ探索を繰り返す。GenericAgent（GA）は、この問題を単純な長文対応ではなく、**限られた文脈内の意思決定に有効な情報密度**を高めるシステム設計として扱う。

GAは9種類の小さな原子的ツール、階層的な長期記憶、成功した操作列を標準作業手順（SOP）や実行可能コードへ変える経験統合、4段階の文脈圧縮を組み合わせる。エージェントをコマンドラインから実行できるようにし、子エージェント起動や条件監視も共通の実行経路で構成する。モデル重み自体を追加学習するわけではなく、**モデルへ渡す情報と、必要な推論呼出し回数を減らす**ことが効率化の中心である。

論文は複数のエージェント基盤との比較を行い、5種類の長期タスクでGAとClaude Codeがともに100%成功しながら、GAの総トークン数が188,829、比較方式が537,413だったと報告する。反復したGitHub調査では、9回目の実行の総トークンが初回の222,203から23,010へ減った。ただし、タスク集合が小さく、モデル・ツール定義・許可範囲・実行環境の差を完全に分離した要因実験ではない。これはGPUカーネルやKVキャッシュそのものを高速化する研究ではなく、エージェント層の推論呼出しと文脈負担を削減する研究である。

## 問題設定

### 文脈が長くなるほど有用とは限らない

長期エージェントの入力には、現在の目標や制約だけでなく、過去の失敗ログ、ツール結果のHTMLやJSON、重複した作業メモ、未使用のツール説明が含まれる。重要な事実が中央付近に埋もれる位置偏り、無関係な情報による注意の分散、名目上の文脈窓と実際に安定して利用できる文脈の差が生じる。単に過去ログをすべて追加すると、費用が増えるだけでなく判断の質も落ち得る。

著者は文脈品質を、必要な情報が欠けない**完全性**と、不要な情報を入れない**簡潔性**の両立として整理する。自然な表現も必要だが、圧縮しすぎて解釈不能になることを避ける補助条件と位置づける。長期運用では、過去のすべての情報を常時入力するのではなく、現在の判断に必要なものだけを読み込む設計が必要になる。

### 経験の保存と再利用の失敗

一度成功したタスクでも、次回に同じ探索・API確認・画面遷移を最初から実行すると、タスク数に比例してトークンが増える。単なる履歴保存では再利用に適した手順が取り出しにくく、誤った記憶が蓄積すると逆効果になる。GAは検証済みの成功経験から再利用可能な手順を抽出し、実行コードへ変換できる場合にはさらに定型化する。これにより、同じ問題を何度も言語推論で解き直す代わりに、少数の呼出しで既存の経路を実行することを狙う。

## 手法

### 1. 9種類の原子的ツールに行動空間を集約

GAはファイル読取・差分修正・書込、コード実行、ウェブ観測・JavaScript操作、利用者への確認、作業状態の更新、長期記憶更新という9種類の原子的ツールを用意する。タスクごとの専用ツールを増やす代わりに、小さな操作を組み合わせて複雑な業務を実行する。ツールの説明が増えると入力トークンと選択候補が増えるため、機能の重複を減らすことがモデルの選択負担を抑えるという設計である。

ファイル読取は行番号・部分読取を使い、巨大ファイル全体を文脈へ流さない。差分修正は一致箇所が一意でない場合に失敗させ、誤った場所の書換えを防ぐ。ウェブ観測はDOMを可視性と領域の観点から整理し、不要な表示要素を除いて意味のある内容を渡す。コード実行は各呼出しの結果を観測してから次を判断する。このような細かな入出力制御も、次のモデル呼出しで必要な情報を小さく保つための仕組みである。

原子的ツールへの集約は能力を自動的に増やすものではない。ブラウザ、ファイル、端末の操作を許可する範囲は依然として外部の権限設定に依存する。専用ツールが不要になるという主張は、論文で扱う操作集合において共通の小さな操作を組み合わせられるという意味であり、すべての外部サービスを無制限に操作できることを意味しない。

### 2. 4層の階層記憶

GAは記憶をL1の索引、L2の検証済み事実、L3の再利用可能な作業手順、L4の生のセッション履歴へ分ける。L1だけを常時文脈へ入れ、L2とL3は必要なときに検索・読取する。L4は監査や履歴復元のため保持するが、毎回の入力へ丸ごと挿入しない。これにより、長期記憶の総量が増えても、現在の文脈の大きさが直ちに増えない。

L2には実行で確認された安定した事実を保存し、一時的な状況や未検証の仮説を恒久的な事実と混同しない。L3には手順、前提条件、よくある失敗と復旧策を保存する。索引には詳細内容そのものではなく、どこに情報があるかという短い案内を残す。モデルが必要時に深い階層を読み、作業後に新しい知識を検証・統合するため、常時表示と長期保存を分離できる。

### 3. 経験をSOP・コードへ段階的に変換

GAは成功した操作履歴をそのまま蓄積するのではなく、不要な試行錯誤を取り除き、再利用可能な標準作業手順へまとめる。類似タスクで手順が安定していれば、文章による手順解釈をさらに実行可能コードへ置き換える。コード化した部分は、次回のLLMが毎回判断し直す必要がなくなる。失敗した実験も監査履歴として残し、同じ失敗を繰り返さないようにする。

実行モードは、利用者からの指示で動く通常モードと、外部の条件監視からタスクを受け取る反映モードに分かれる。コマンドライン起動を共通の実行入口にすることで、子エージェントを別プロセスとして起動したり、監視スクリプトが条件成立時に新しいタスクを渡したりできる。各プロセスの文脈は独立しており、並列作業の情報が一つの会話へ混ざりにくい。

著者はスキル木の未充足分野、既存スキルの使用頻度、実用価値、新規性を重み付きで評価する自律探索案も示す。ただし、重みを実使用の結果から自動調整する部分は長期の実証が不十分と明記されている。自律探索の存在と、その長期的な有効性が十分に検証されたことを区別する必要がある。

### 4. 文脈圧縮の4段階

第一段階ではツール出力ごとに文字数上限を設け、長い結果は先頭と末尾を残して中央を切り詰める。第二段階では古いメッセージ中の重複した作業メモやツール関連タグを短縮し、最新の約10メッセージは保護する。第三段階では全体の文字数予算を超えたとき、圧縮規則を厳しくした後、古いメッセージを先入れ先出しで排除して予算の60%未満へ戻す。第四段階では、現在の目的、制約、直近の作業要約を含む作業記憶のアンカーを繰り返し付与し、古い会話が消えても必要な状態を残す。

予算判定は正確なトークン数ではなく、`文字数上限 ≈ 3 × トークン窓`という近似で行う。英数字中心の文章では保守的に早く排除することがある一方、日本語・中国語のような文字当たりトークン数が多い言語では、文字数が少なくても実トークンが多くなり、排除が遅れる危険がある。著者自身がこの誤差を指摘しているため、日本語の長期運用へそのまま転用する場合は、実トークナイザでの計測や安全余裕を追加すべきである。

### 5. 推論基盤との接点

この研究はTransformerの注意演算やGPUメモリ帯域を直接変更しない。代わりに、モデルへ渡す入力トークン、必要なモデル呼出し、不要なウェブ再探索、ツール説明の常時投入を減らす。推論サービスの課金が入力トークン数と呼出し数に依存する場合、こうした削減は直接費用を下げる可能性がある。ただし、同時利用者数、GPU上のバッチ化、モデルの前向き計算時間、キャッシュ再利用なども実費用へ影響するため、トークン削減率がそのままGPU電力や運用費用の削減率になるわけではない。

## 評価

### タスク完了率と総トークン

論文§4では、業務手順の実行を評価するSOP-Bench、複数タスクにまたがる記憶を評価するLifelong AgentBench、金融業務のRealFin-benchmarkを用いる。主な指標はタスク成功率、入力トークン、出力トークン、合計トークン、成功率を百万トークン当たりで正規化した効率値である。異なるベンチマーク間ではトークン集計の尺度が異なるため、効率値の絶対値を横断比較しない。

| ベンチマーク・モデル | システム | 成功率 | 総トークン |
|---|---|---:|---:|
| SOP-Bench / Claude Sonnet 4.6 | GA | 100% | 2.08M |
| 同条件 | OpenClaw | 100% | 2.64M |
| 同条件 | Claude Code | 85% | 1.25M |
| Lifelong AgentBench / Claude Sonnet 4.6 | GA | 100% | **241k** |
| 同条件 | OpenClaw | 70% | 1.45M |
| 同条件 | Claude Code | 75% | 814k |
| RealFin / Claude Sonnet 4.6 | GA | 65% | 114k |
| 同条件 | OpenClaw | 35% | 251k |
| 同条件 | Claude Code | 55% | 238k |

SOP-BenchではClaude Codeの総トークン数がGAより少ないが、成功率も低い。Lifelong AgentBenchではGAが100%成功し、OpenClawの70%・1.45Mトークンに対して241kトークンである。RealFinの比較では、GAの65%が最高値とされる。ただし、同じモデル名でもエージェント固有のツール定義やプロンプト、許可範囲、実行戦略は異なり、完全に一つの要因だけを変えた比較ではない。

### 原子的ツールの長期タスク評価

論文表4は文書作成、SQL問い合わせ支援、実験報告、調達判断、研究論文の再現可能性評価の5タスクを比較する。全てClaude Sonnet 4.6を使い、成功率と平均時間、モデル要求回数、ツール呼出しを測る。

| 指標 | GA | Claude Code | OpenClaw |
|---|---:|---:|---:|
| 成功率（5タスク） | 100% | 100% | 80% |
| 総トークン | **188,829** | 537,413 | 633,101 |
| 平均実行時間 | 220.8秒 | 320.8秒 | 183.1秒 |
| 平均モデル要求数 | 11.0 | 32.6 | 15.0 |
| 平均ツール呼出し数 | 12.8 | 22.6 | 16.6 |

GAの総トークンはClaude Codeの35.1%で、約64.9%少ない。平均時間はClaude Codeより短いが、OpenClawの183.1秒より長い。従って、GAがあらゆる指標で最速だったという結論は誤りである。また5タスクだけの結果なので、タスク分布を変えたときの信頼区間や、機能ごとの独立効果には注意が必要である。

### 長期記憶と文脈増大の抑制

同じHugging Faceデータセット取得タスクを新規セッションで5回繰り返す実験では、GAの実行時間が初回102秒から後半約66秒へ、総トークンが200,439から約100,000へ減ったと報告する。新規セッションを使うことで会話履歴の残留を避けつつ、外部の記憶を再利用する効果を測っている。これはタスク内容が反復的な場合の結果であり、初見の難しいタスクでも同じ減少率になるとは限らない。

20個のスキルを導入した後に短い挨拶だけを入力した際のフルプロンプト長は、GAが2,298トークン、Claude Codeが22,821、Codexが23,932、OpenClawが43,321だった。これは記憶やスキルの詳細を常時プロンプトへ投入しない設計の効果を示すが、実際に20スキルを全部同時利用する複雑なタスクの必要トークン数を示すわけではない。

LoCoMoの長期記憶評価では、GAの多段推論F1が43.33、時間関係F1が52.23で、比較したMem0の39.32・50.03を上回る。論文は外部埋め込み検索を用いずに階層記憶を運用できると述べるが、比較対象の記憶設定や検索条件が異なる可能性があり、あらゆる長期記憶でベクトル検索が不要になるという一般化はできない。

### 反復作業のSOP・コード化

同種のGitHub調査を9ラウンド繰り返した実験では、最初は自然言語による探索、2〜5回目はSOP改善、6〜9回目はコード化した手順を使用する。初回と最終回を比較すると次のようになる。

| 指標 | 初回 | 9回目 |
|---|---:|---:|
| 実行時間 | 7分30秒 | **1分38秒** |
| LLM呼出し | 32回 | **5回** |
| 総トークン | 222,203 | **23,010** |
| キャッシュ読取トークン | 183,375 | **19,034** |

総トークン削減は約89.6%、実行時間削減は約78.2%である。ただし同じ型のGitHub調査を繰り返す設定であり、未知の環境・新規ツール・異なる目標への転移性能を直接示すものではない。8種類の別タスクでも後続実行のトークン削減61.0〜92.4%を報告するが、各タスクは3回の反復であり、長期の安定運用や大規模なユーザー集団での実証ではない。

### ウェブ操作の比較

WebCanvas 12件、BrowseComp-ZH 10件、独自の実務22件を使い、GAとOpenClawをClaude Opus 4.6で比較する。WebCanvasではGAの得点0.834・平均0.18Mトークンに対し、OpenClawは0.720前後・0.71M、BrowseComp-ZHではGAが0.60・0.47Mに対してOpenClawは0.20・1.31M、独自タスクでは0.577・0.26Mに対して0.50・0.76Mと報告する。論文中の説明と表にWebCanvas比較値の丸め差があるため、精密な百分率差は算出しない。

BrowseComp-ZHはLLMによる判定、独自タスクは人手とLLMを組み合わせた評価であり、自動的に完全な客観的正答が得られるわけではない。ブラウザの状態やアクセス可能なツール、サイト側の変更によって再現結果は変わり得る。ウェブ操作のトークン数が少ないことは、ブラウザの全操作が短時間で完了することや、セキュリティ上の安全性を直接保証するものではない。

## 既存研究との差

従来のエージェント基盤は多くの専用ツールや長いプロンプトを備える場合があり、複雑な作業を細かい機能に分けて支える。GAはそれを9種類の基本操作へ縮約し、必要な情報だけを階層記憶から読み、成功手順をSOPやコードとして保存する。単一のトークン圧縮器だけを追加したのではなく、ツール設計、記憶管理、作業履歴の再利用、出力の切詰めを一つの実行ループへ組み込んだ点が特徴である。

ただし、比較するエージェントは初期プロンプト、ツール数、モデル利用条件、許可範囲が同一ではない。ツールを減らした効果、記憶階層の効果、コード化の効果を完全に独立させた大規模な構成要素除去実験は限られる。GAの改善を「9ツールにしただけで生じた」と単純化することはできない。

## 限界・運用上の制約

**評価の規模と比較条件が限定される。** 長期ツールタスクは5件、WebCanvasは12件、BrowseComp-ZHは10件、独自ウェブタスクは22件である。多くの数値は同じモデルを使う比較だが、エージェント固有のツール、指示、アクセス条件まで完全に同一ではない。実行時間の優劣はタスクによって逆転し、すべてのベンチマークで最速ではない。

**トークン削減とGPU高速化を区別する。** 文脈圧縮による入力トークン減少は推論費用に影響するが、GPUのカーネル時間、連続バッチ効率、KVキャッシュ占有量、電力、実運用の料金を統一条件で直接比較したものではない。大きな文脈を必要とするタスクでは、必要情報を削りすぎることで正答率が落ちる可能性もある。

**文字数による文脈予算は多言語で誤差が大きい。** 3文字を1トークンとみなす近似は日本語・中国語のような言語で過少計測を起こし、排除が遅れて文脈上限を超える可能性がある。日本語運用では実トークン計測や余裕を持った上限が必要である。先頭・末尾を残す切詰めは、中央に重要な証拠がある場合にその情報を失う危険もある。

**自律的な手順再利用には検証が必要である。** 過去の成功経路をSOPやコードへ固定しても、外部サービスの仕様、ファイル構造、認可、入力条件が変われば再利用できない。論文の自律探索スコアの長期調整は十分に実証されておらず、記憶の整理や古いスキルの統合に手作業が残ると記載する。安全に実行できる範囲はツール権限と外部の検証に依存する。

**プロンプトと記憶の削減は完全性との交換条件を持つ。** 詳細を常時表示しない設計は有効だが、適切な記憶を検索できない場合には必要な情報が欠落する。経験統合で成功した事例だけを優先すると、例外条件や失敗事例の学習が不十分になる可能性がある。過去の誤った事実を検証なしにL2へ固定しないこと、重要な制約をアンカーへ保持することが不可欠である。
