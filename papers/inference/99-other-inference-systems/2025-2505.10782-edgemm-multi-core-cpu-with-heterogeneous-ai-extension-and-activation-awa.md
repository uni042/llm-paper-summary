# EdgeMM：GEMMとGEMVの異なるボトルネックに合わせたエッジMLLM専用CPU

## 概要

エッジでマルチモーダルLLM（MLLM）を実行する際、画像などをトークンに変換するエンコーダ、入力トークンをまとめて処理するLLM prefill、出力トークンを逐次生成するdecodeでは、計算とメモリの比率が大きく異なる。エンコーダとprefillは同じ重みを複数トークンで再利用する行列積GEMMが中心であり、算術演算の処理能力が重要である。一方、decodeは少数トークンに対する行列ベクトル積GEMVが中心で、演算器より重みの転送帯域が律速になりやすい。

EdgeMMは、この二種類の負荷を一つの均質なGPUやCPU拡張へ押し込む代わりに、RISC-V CPUのコア群を計算重視（Compute-Centric、CC）とメモリ重視（Memory-Centric、MC）へ分ける。CCコアはシストリックアレイ（SA）を使ってGEMMを高速化し、MCコアはSRAM内のデジタルCompute-in-Memory（CIM）を使ってGEMVの重み移動を減らす。さらに、活性値の小さいチャネルに対応する重み行のDRAM読み出しを省く動的剪定と、出力長に合わせた帯域割当を組み合わせる。

論文はSPHINX-TinyやKarmaVLMのような小型MLLMを対象とし、商用22nmプロセスを想定したRTL実装・配置配線評価とシミュレーションを報告する。Laptop RTX 3060 GPU比で、異種コアだけの構成は2.15倍、動的重み剪定込みでは2.84倍、最終構成のスループットは138 tokens/sとする。ただし、これらは実チップを製造して測定した数字ではなく、シミュレーション・実装設計評価に基づく比較である。

## 問題設定と設計動機

### 小型MLLMにおける処理フェーズの非対称性

MLLMは、画像・音声等のエンコーダ、トークンの次元を合わせるprojector、言語モデルの三つに大別される。エッジ向けのモデルでは言語モデルが0.5B～2.7B程度のものもあり、入力は短い画像トークン列を中心とする。原著のプロファイリングでは、SPHINX-TinyとKarmaVLMの入力は約300トークンで、画像エンコーダとprefillの費用も無視できない。一方、出力長が伸びるほど逐次decodeの占める時間が増える。

画像エンコーダとprefillでは重み行列を多数の入力列へ適用するGEMMになり、演算器の並列度を高める価値が大きい。decodeでは各トークンに同じ重みを一回ずつ読み込むGEMVが中心となり、重み行列の帯域要求が支配的である。論文は、特にFFNの重みがDRAM転送量の大きな部分を占めると報告する。短文脈MLLMではKVキャッシュの転送は相対的に小さく、長文脈向けKV最適化だけでは十分な改善が得られない。

この分析はGPUサービングの一般論をそのままエッジへ当てはめない理由を示す。巨大な同時バッチを処理するサーバではGEMMの比重が増えるが、端末上で少数ストリームを処理する場合、エンコーダと逐次decodeの両方を効率化する設計が必要である。

### 均質な演算器の限界

シストリックアレイは多数の行列要素を同時に計算できるが、GEMVでは入力列が一列しかないため多くの演算器が空きやすい。CIMはSRAMに保持した重みを近傍で演算できるためGEMVに向く一方、広いGEMMではビットシリアル計算のサイクル数が増え、SAより不利になることがある。単一の種類の演算器を大量に配置しても、MLLMの全フェーズで高い利用率を得られない。

EdgeMMはCPU ISAに統合されたコプロセッサを使う。外付けASICをCPUから呼び出す構成に比べ、命令ディスパッチと同期の経路を短くし、既存のRISC-Vツールチェーンとカスタムカーネルで処理を記述できるとする。ただし、汎用CPU上のソフトウェアだけで実現する方式ではなく、SAとデジタルCIMを搭載した新しいハードウェアを前提とする。

## 手法

### 異種CC/MCコアと階層構造

ベースはオープンソースのSnitch_clusterである。チップは4グループから成り、各グループにCCクラスタ2個とMCクラスタ2個を置く。CCクラスタはCCコア4個、MCクラスタはMCコア2個を持つ。したがって全体はCCコア32個とMCコア16個の構成であり、各コアは制御用RISC-Vホストコアと対応するAIコプロセッサを含む。クラスタにはDMAがあり、階層AXIクロスバーを通してDRAMと接続する。

CCコアのSAはR×C個の乗算加算PEを格子状に並べ、重みをPEに固定したまま活性値を隣接PEへ流す。行列演算に必要なデータ移動を近傍配線へ限定することで、広い演算器へ毎回データを供給する費用を減らす。原著の単純化したモデルでは、R×CとM×Rの行列積のロード・計算サイクルは2R+C+M−3である。SAはGEMMに適するが、GEMVでは活性の列数が少ないため並列PEの一部が無駄になる。

MCコアでは、SRAMの6Tビットセルに重みを保持し、デジタルCIMの列内でビットシリアルの積和を実行する。Wビットの活性を各列へブロードキャストし、加算木とシフト累積器で結果を得る。原著のモデルではM行の処理がM×W+1サイクルとなる。M=1のGEMVではSAより効率的だが、Mが増えるGEMMではビット幅に比例したサイクル増が不利になる。

SAとCIMを別々のクラスタへ配置し、encoder/prefillとdecodeの処理を適したクラスタへ割り当てる。RISC-V命令拡張はCC側のmm_mulなどの行列命令と、MC側の行列ベクトル命令を提供する。コア種別とインデックスをCSRから読み取り、各コアが担当テンソル片のアドレスを計算する。ホストCPUから別のバス接続デバイスへ処理を渡すのではなく、命令拡張のカーネルとして実装する点が特徴である。

### 活性値に基づく層別動的Top-k剪定

decodeのFFNは、ゲート付きMLPのup/gate/down投影を通じて複数のGEMVを行う。論文は活性値のチャネルごとの大きさに偏りがあり、一部の値が非常に大きく、その他は小さいことを観測する。小さい活性に掛ける重み行の寄与は小さい可能性があるため、活性の大きいチャネルだけを残して重みの読み出し自体を省く。

原著Algorithm 1は、最初のdecoder層ではk=dとして剪定せず、後続層で活性のTop-kを選択する。各層で最大活性の1/16より大きい要素数nを数え、n<kなら次の層のkをnへ減らす。したがって深い層へ進むにつれ保持チャネル数を段階的に減らす。固定の剪定率をすべての層へ適用するのではなく、入力活性と層位置に応じて削減量を調整する方式である。

MCコアのハードウェアprunerは、活性の最大値を求め、Top-kに残るチャネルのインデックスを生成し、対応する重み行のDRAMアドレスだけを作る。活性はコアごとにチャネル分割され、各コアは自分の担当チャネルの範囲で処理するため、巨大な全体Top-kを毎回計算する費用を避ける。ここで重要なのは、ゼロにした重みを計算時に無視するだけでなく、DRAMから読み込む重み行そのものを減らすことである。帯域律速のdecodeでは、この違いが速度改善に直結する。

ただし、各層のTop-kが常に出力を保存するわけではない。原著は最初の層で剪定すると精度が大きく低下したと報告し、初層を除外する。実験では出力ベクトルのコサイン類似度とVQAスコアで影響を確認するが、あらゆる入力分布・言語能力で無損失と保証してはいない。

### 出力長に応じたDRAM帯域の動的配分

ストリーミング入力を想定すると、CCクラスタが次の画像をencode/prefillしている間に、MCクラスタが前の入力に対するdecodeを実行できる。ところが出力トークン数が増えるとMC側が長く動き続け、CC側が待機する。両クラスタへDRAM帯域を均等に与えるだけでは、decodeの待ち時間を減らせない。

EdgeMMは各クラスタにDMAの転送予算Bを設定する。一定期間T内の転送量dを性能カウンタで積算し、d>Bとなったクラスタの追加DMA要求を次の期間まで待たせる。出力長が長い場合はCC側の予算を減らし、MC側へ帯域を回す。CCが多少遅くなってもdecodeの律速を解消すれば、ストリーミング全体の処理時間を減らせる。

この制御は無制限に効果があるわけではない。原著では期待出力長l_e=36付近を境にdecode側の負荷が重くなり、l=128では帯域割当で大きな改善が得られるが、l_b=131程度で単純な帯域再配分は限界に近づく。その先では複数ストリームをバッチ化し、MCクラスタが同じ重みを複数入力へ再利用する方針へ切り替える。バッチ化はスループットを上げる反面、単一要求のレイテンシを増やし得る。

## 評価条件と実験結果

### 評価系と数値の出所

| 項目 | 原著の条件 |

| ハードウェア設計 | Snitch_clusterベース、CCにSA、MCに22nmデジタルCIM |
| 設計フロー | RTL、Cadence Genus/Innovus、TSMC 22nm、1GHzを目標 |
| 性能評価 | RTLシミュレーションと専用マッピングシミュレータ |
| 比較GPU | RTX 3060 Laptop GPU、GDDR6帯域336GB/s、FP32 13TFLOP/s（Table II） |
| EdgeMM演算ピーク | BF16 18TFLOP/s（Table II） |
| 主なMLLM | SPHINX-Tiny、KarmaVLM、代表的なエッジMLLM |
| 主な指標 | 推論スループット、フェーズ別速度、遅延、出力類似度、VQAスコア |

**実チップの製造・動作測定ではない。** 22nmでの配置配線レイアウトは提示されているが、性能はRTLと専用シミュレータに基づく。GPU比較では演算ピークもFP32とBF16で異なり、同一精度の単純なピーク演算比較にはならない。比較対象のGPUとEdgeMMは電力・メモリ階層・ソフトウェア実装が異なるため、2.84倍を一般的なCPU対GPUの優劣と読むのは不適切である。

### 異種コアの効果

原著Fig.11のフェーズ別比較では、CCクラスタはMCクラスタよりGEMMで4.3倍高い性能を示す一方、MCクラスタはCCクラスタよりGEMVで2.42倍高速である。均質なCCだけ、MCだけの構成と比較したMLLM全体では、異種EdgeMMはそれぞれ1.79倍、2.65倍の性能を報告する。単一フェーズで最速の構成を選ぶだけでは、encoderからdecodeまでを通した最適解にならないことを示す。

| 比較 | 報告値 | 解釈 |
|---|---:|---|
| CC対MCのGEMM | CCが4.3倍 | SAは多数の入力列を処理するGEMMに適する |
| MC対CCのGEMV | MCが2.42倍 | CIMは重み転送の少ないGEMVに適する |
| 異種EdgeMM対均質CC | 1.79倍 | decodeでのMC採用が有利 |
| 異種EdgeMM対均質MC | 2.65倍 | encoder/prefillでのCC採用が有利 |
| EdgeMM対RTX 3060 Laptop | 2.15倍 | 異種構成のみのシステム比較 |
| EdgeMM+剪定対RTX 3060 Laptop | **2.84倍** | 活性依存の重み転送削減込み |
| 最終構成スループット | **138 tokens/s** | 論文が示す対象MLLM評価条件での数値 |

上の倍率は互いに比較基準が異なる。たとえば1.79倍と2.65倍は均質な自社設計との比較であり、2.84倍はLaptop GPUとの比較である。掛け合わせて追加高速化率を算出することはできない。

### 活性依存剪定の精度・遅延

原著Fig.12では、層が深くなるにつれて活性の尖度が増し、より多くのチャネルを剪定できる傾向を示す。ただし最初の層は尖度が高くても分布が不安定で、剪定すると精度が大きく落ちるため初層を保持する。層ごとに適用するTop-kを変える設計は、この実測観測に基づく。

SPHINX-Tinyのdecodeでは、動的剪定によって平均遅延を42%削減したと報告する。VQAスコアの低下は小さいと説明され、FFN出力のコサイン類似度も、固定剪定率0.1程度の緩い条件に近い。一方、固定剪定率0.7は浅い層で不可逆な精度低下を生む。**42%はdecodeフェーズの遅延短縮であり、画像エンコーダを含むMLLM全体のレイテンシ短縮率ではない。**

### 帯域制御とバッチ化

出力長l=128の条件では、CC:MCの帯域割当を1:3から1:7程度まで変えることで、遅延を40.3%削減し、スループットを2.14倍にしたとする。帯域を単に増やすのではなく、すでに待機しがちなCCからdecode側へ割り当て直すため、ストリーミングのパイプライン効率が改善する。

lが1,024まで長くなる条件では、バッチ化によってスループットが13.98倍になるが、同時にレイテンシは42%増加する。バッチ化の利益は、同じ重みを複数入力に再利用できることによる。これは一要求あたりの応答時間を最小化する設計とは目的が異なる。端末のリアルタイム応答要件が厳しい場合は、スループット改善だけを理由にバッチ化を採用できない。

### 電力・エネルギー効率の数値不整合

原著は配置配線後のチップ電力を112mWと記す一方、Introductionの貢献箇所では0.217 token/J、Evaluationの末尾では0.28 token/Jと異なるエネルギー効率を報告する。これらが異なるモデル・ワークロード・算定範囲を指すのかは、本文の記述だけでは明確に特定できない。また138 tokens/sと112mWを単純に割ると約1,232 tokens/Jになり、0.217/0.28 token/Jと桁が一致しない。したがって、112mWを138 tokens/sの全システム消費電力と解釈してエネルギー効率を再計算することはできない。

この矛盾は重要である。設計チップ単体の電力、外部DRAM、ホスト、評価環境、シミュレータの電力モデルがどこまで含まれるかを確認しない限り、EdgeMMのエネルギー優位を定量的に確定できない。原著の0.217と0.28 token/Jは両方記録し、単一の確定値へ統合しない。

## 実装上の意義と他方式との違い

通常のGPU最適化では、CUDAカーネル、メモリ配置、バッチスケジューリングを変えることで既存ハードウェアの利用率を上げる。EdgeMMは、GEMMとGEMVを別の演算器で処理するというハードウェアの段階から再設計する。SAとCIMの選択は演算密度の差に対応し、Top-k重み読み出しはメモリ帯域の消費そのものを減らし、動的DMA予算は入力・出力長に応じてクラスタ間の律速を移す。

ソフトウェア側から学べる点は、端末向けMLLMの負荷をencoder/prefillとdecodeへ分解し、演算密度と転送量を別々に測定することである。重み剪定も、演算を省くのみではなく、転送前に重み行を選択できるかが鍵になる。CUDA GPU上で同じアルゴリズムを使う場合、インデックス生成、非連続重みアクセス、動的疎性によるカーネル利用率の低下が生じ得るため、専用CIMの結果をそのまま移植することはできない。

RTX 4070 Superのような汎用GPUでEdgeMMの138 tokens/sを直接再現することはできない。専用RISC-Vコアと22nm CIMマクロが必要であり、ソフトウェアの設定変更だけで得られる高速化ではない。一方、短い画像入力を繰り返すMLLMのボトルネック分析、FFN重みの帯域支配、出力長に応じたdecode側への資源再配分という設計指針は、GPU/CPU混成システムのプロファイリングでも参考になる。

## 限界と未検証事項

第一に、実測ではなくRTL・配置配線・シミュレータによる評価である。TSMC 22nmのレイアウトを提示しても、製造した実機でのクロック変動、温度、電力、外部DRAMの帯域競合、ホストとの統合費用は別途測定が必要である。GPUとの比較条件も演算精度・メモリ構成・カーネル成熟度が揃っていないため、一般化には注意する。

第二に、評価は短い入力と小型MLLMを主対象とする。128K以上の長文脈、巨大なKVキャッシュ、MoEのエキスパートオフロード、複数ユーザーの連続バッチ処理、分散サービングには直接対応していない。出力長が増えると動的帯域配分だけでは限界が生じ、バッチ化が必要になるという結果は、低遅延と高スループットの交換条件を示している。

第三に、活性依存Top-kは入力に応じて重み行を選ぶため、毎トークンのpruner・アドレス生成・非連続メモリアクセスのオーバーヘッドがある。専用ハードウェアではそれを吸収できても、一般的なCPU/GPUで同じ42%のdecode短縮が得られるとは限らない。剪定の品質評価もVQAやFFN出力類似度が中心で、広範な言語ベンチマークや長い生成における誤差蓄積は未検証である。

第四に、エネルギー効率について原著内の数値が一致しない。0.217 token/Jと0.28 token/Jの差、112mWの電力値と138 tokens/sの対応範囲が不明であり、エネルギー改善を精密な倍率として扱うべきではない。性能評価と電力評価を同じワークロード・測定境界でやり直すことが重要である。
