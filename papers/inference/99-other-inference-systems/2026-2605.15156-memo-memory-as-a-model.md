# MeMo: Memory as a Model

## 概要

MeMoは、更新された文書や専門領域の知識を、基盤となる大規模言語モデル（LLM）の重みを変更せずに利用するための、独立した記憶モデルを導入する。従来の検索拡張生成（RAG）は質問ごとに検索索引から文書を取得するため、検索雑音、複数文書にまたがる関係の取りこぼし、長い引用文脈の投入が問題になる。反対に実行モデル自体を追加学習すれば、計算費用と既存能力の忘却が問題になる。MeMoは、知識を記憶する小型モデルと、推論・回答を担当する凍結モデルを分離する。

具体的には、対象文書群から「反省的質問応答（reflection QA）」を合成して小型記憶モデルへ教師あり微調整し、推論時には実行モデルが小問を生成して記憶モデルへ順次問い合わせる。記憶モデルは検索された原文を読まず、学習したパラメータから短い自然言語の回答を返す。固定サイズの記憶モデルを問い合わせるという意味で、各問い合わせの検索処理は文書総数に比例しない。ただし、複数回のモデル生成が必要であり、実際の応答遅延が一定であるという実機測定結果ではない。

代表結果として、記憶モデルにQwen2.5-14B-Instruct、実行モデルにQwen2.5-32B-Instructを用いた場合、NarrativeQA正答率は26.85%、MuSiQueは48.30%となった。同じ条件のHippoRAG2はそれぞれ21.39%、42.17%である。一方BrowseComp-PlusではMeMoの54.22%はHippoRAG2の56.11%に及ばない。論文の強みはすべての課題で一律に勝つことではなく、文書間の知識合成と検索雑音耐性を、外部の凍結実行モデルと両立させた点にある。

## 問題設定と適用範囲

対象文書群を $\mathcal D=\{d_1,\dots,d_N\}$、実行モデルを重み $\theta$ が凍結された $\mathcal M_\theta$ とする。目的は、文書群の表現 $\Phi(\mathcal D)$ と回答処理 $f$ を設計し、実行モデルの重みを更新せずに文書群を根拠とする質問へ正しく回答することである。通常の検索拡張生成は $\Phi$ を文書索引とし、質問ごとに検索した文書片を実行モデルへ渡す。MeMoは $\Phi$ を別モデル $\mathcal M_\varphi$ のパラメータとする。モデルの内部状態や出力確率へアクセスできない外部提供の実行モデルも利用できる設計である。

この切り分けは、計算の削減箇所を誤解しないことが重要である。MeMoは検索索引をたどる処理と長文書を毎回入力する処理を減らすが、文書から学習データを生成する初期費用、小型とはいえ別の生成モデルを実行する費用、段階的な問い合わせ回数を新たに負担する。文書数に対する検索費用の漸近的な主張は、同じ記憶モデル容量を維持できる範囲での性質であり、文書数を無限に増やしても正答率が保たれる保証ではない。

また、この研究の主目的は知識を利用した回答品質であり、GPUカーネル、KVキャッシュ配置、分散推論スケジューラの最適化ではない。サーベイでは「外部記憶・検索処理を置き換える推論時知識供給方式」として扱い、純粋な推論サーバー高速化論文と同じ軸の速度比較を行わない。

## 手法

### 1. 文書群から反省的質問応答を合成する五段階処理

最初に生成器モデル $\mathcal M_{gen}$ が各文書を連続した文書片へ分割する。第1段階では文書片から明示的な事実を問う質問応答 $\mathcal Q_{dir}$ と、文書片から推論して得られる間接的な質問応答 $\mathcal Q_{indir}$ を別々に作る。後者を用意するのは、単語の記憶だけでは未知の複合質問へ回答できないためである。生成器には後で使用する実行モデルと同一であることを要求しない。

第2段階では、同じ人物・時期・関係を扱う質問応答を統合し、複数の事実を同時に必要とする質問を新しく作る。元の直接・間接質問応答を消さずに統合後の組を加えるので、単一事実の再現と複合的な関係の再現を並行して学習できる。第3段階では、元の文書片を参照しながら、質問単独で意味が通じるかを検証する。「その人物」「上記の表」のように出典を見ないと答えられない質問は書き換え、なお曖昧なら破棄する。ここで得られる検証済み集合が $\mathcal Q_{ver}$ である。

第4段階の実体顕在化では、名前を直接問うだけでなく、属性や他の実体との関係から名前を逆に推定する質問を作る。これが推論時の「候補となる実体を特定する」段階と対応する。第5段階では、関連する文書をまとめたグループ $G_i$ ごとに、異なる文書に分散する手掛かりを結合する質問と、複数実体に共通する性質を比較する質問を合成する。最終的な学習集合は検証済み、実体顕在化、文書横断の三種類の和集合となる。

重要なのは、推論時に実行モデルへ原文書を渡さなくても、文書間の関係を問い合わせられるよう、**事前に関係を質問応答へ変換する**点である。一方、生成器が見落とした関係や、誤って統合した事実は記憶モデルの学習データにそのまま影響しうる。五段階の検証は生成した質問の自己完結性を改善するが、全質問の真実性を形式的に保証するものではない。

### 2. 小型記憶モデルへのパラメータ格納

記憶モデル $\mathcal M_\varphi$ は、事前学習済みの小型言語モデルから初期化し、合成した質問に対する回答トークンだけを損失対象として教師あり微調整する。学習時の入力は質問、予測対象は回答であり、推論時に原文書を再取得する経路を持たない。実験ではQwen2.5-14B-Instructを三エポック学習し、学習率は $2\times10^{-5}$、最適化器は融合AdamW、学習基盤はDeepSpeedである。1.5B規模の小型記憶モデルも比較している。

この設計は、実行モデルの再学習を不要にする代わりに、文書群ごとに記憶モデルの学習を要求する。記憶モデルのパラメータ数が固定であれば問い合わせ時のモデルサイズは文書総数と独立するが、保持できる知識量には限界がある。原著は追加文書の逐次統合として、文書群ごとに別々に学習した記憶モデルの重み差分 $\tau_i=\varphi_i-\varphi_0$ を合成するモデル統合も試験する。この更新方式は学習費用を下げる一方、後述のように正答率が大きく低下する。

### 3. 推論時の三段階問い合わせ

質問 $q$ を受け取った実行モデルは、最初の根拠取得段階で質問に含まれる個々の手掛かりを原子的な小問 $q'_1,\dots,q'_J$ に分解する。記憶モデルは小問ごとに独立して回答し、短い自然言語の手掛かり $m_1,\dots,m_J$ を返す。小問数は実行モデルが決めるため、固定回数の単一検索と同じ処理費用にはならない。

次の実体同定段階では、最初の回答を使って候補となる人物・物事を絞り、追加の小問を記憶モデルへ発行する。候補を一つに絞れた場合は最終段階へ進むが、候補が見つからなければ実体に基づく追加取得を省略し、最初の手掛かりだけから回答を作る。最後の回答探索・統合段階では、特定した実体に関する追加の裏付けを記憶モデルへ問い合わせ、取得した回答を統合して最終回答を生成する。各段階は独立した質問回数予算と生成条件を持つ。

ここで受け渡すのはモデル内部の埋め込みやKVキャッシュではなく、通常の自然言語テキストである。そのため、実行モデルの重み、隠れ状態、トークン確率を読めない外部APIにも接続できる。逆に、自然言語の多段往復による遅延やAPI料金、記憶モデルの誤答を後段が過信する危険は残る。原著の「定数時間」という説明は文書総数に依存しない短文問い合わせという意味であり、回答生成の実測レイテンシを一定と証明したものではない。

## 評価

### 評価環境と比較条件

論文は、BrowseComp-Plusから300問と3,541文書、NarrativeQAから293問と10文書、MuSiQueから1,000問と5,296文書を用いる。BrowseComp-PlusとMuSiQueでは正解根拠文書と同数の妨害文書を混ぜる。生成器はQwen2.5-32B-Instructで、長文書を扱うためYaRNで131Kトークンの文脈長に拡張し、vLLMで提供した。記憶モデルは主にQwen2.5-14B-Instruct、実行モデルはQwen2.5-32B-InstructまたはGemini-3-Flashである。

比較対象は、語彙検索BM25、密ベクトル検索NV-Embed-V2、グラフ検索HippoRAG2、内部KV状態を使うCartridges、および正解根拠文書だけを与える理想的検索である。検索方式は原則上位9件を使い、文脈窓を超える場合は件数を減らす。正答判定はGemini-2.5-Flash-Liteを用いた二値判定で、Qwen実行モデルの結果は3回の平均±標準偏差、Gemini実行モデルは単回実行である。異なるモデルの結果を同じ反復回数の統計値とみなしてはならない。

| MuSiQue / Qwen2.5-32B | 48.30±1.25% | 42.17±0.12% | 37.47±0.15% | 62.83±0.90% | 複数段推論で検索方式を上回る |

### 雑音・容量・更新の構成要素評価

妨害文書を根拠文書数と同数まで増やす実験では、BrowseComp-PlusのHippoRAG2が62.33%から56.11%へ6.22ポイント下がるのに対し、MeMoは53.67%から54.22%へ0.55ポイント上がった。MuSiQueではHippoRAG2が47.33%から42.17%へ5.16ポイント下がり、MeMoは50.07%から48.30%へ1.77ポイント低下した。MeMoも全条件で不変ではないが、調べた範囲では検索方式より妨害文書の影響が小さい。学習時に雑音を含めているため、全く未知の雑音分布への一般化は別途検証が必要である。

記憶モデルの規模を1.5Bから14Bへ増やすと、Qwen実行モデルを用いたBrowseComp-Plusは44.11%から54.22%、NarrativeQAは24.00%から26.85%、MuSiQueは42.90%から48.30%へ改善した。固定サイズで文書数から独立するという計算上の特徴と、十分なモデル容量が必要という品質上の制約が表裏一体であることを示す。またGemma3-1B-IT、LFM2.5-1.2B-Instructとの比較では同程度のパラメータ規模でも課題別の優劣が変わり、特定モデル系列の性能だけを方式の普遍的効果とみなせない。

継続更新実験ではNarrativeQAの質問応答集合を約64万組ずつ二分し、別々に学習した記憶モデルをTIES方式で統合した。二回到着分の累積学習計算は全量再学習の約72（8×H100 GPU時間）から統合の約48へ33%減るが、Qwen実行モデルでの正答率は26.85%から15.81%へ11.04ポイント、Geminiでは53.58%から34.47%へ19.11ポイント下がる。計算節約と正答率を同時に評価しなければならず、単に「追加知識を低費用で完全に取り込める」と結論してはならない。

## 限界・負の結果・実装上の含意

第一に、対象文書群から反省的質問応答を大量合成し、記憶モデルを学習する初期費用が必要である。検索索引構築と異なり、文書を差し替えるたびにモデル学習・統合の負担が生じる。原著はモデル統合を試すが、更新後の正答率低下が大きく、頻繁に更新される文書集合へそのまま適用する際には注意が要る。

第二に、記憶モデルのパラメータ容量が上限となる。論文の規模では容量飽和の明確な兆候は見られないものの、文書数や情報密度が増えれば全事実を保持できる保証はない。固定モデルサイズを仮定した文書数非依存の検索費用は、容量制約を無視した無制限のスケーラビリティを意味しない。検索された原文を実行時に提示しないため、回答の根拠文書の追跡可能性やアクセス制御にも課題がある。

第三に、主要実験は三つの質問応答ベンチマークと特定のモデル系列に限られる。報告された数値は主に正答率であり、GPU使用量、学習時総電力、推論の端末間通信量、エンドツーエンドの応答時間、同時要求数ごとの処理量について、検索方式に対する包括的な実機比較は提示されていない。三段階の問い合わせは追加の生成呼び出しを伴うので、検索索引が不要であることから直ちに実運用の高速化を推論するのは不適切である。

第四に、比較条件の公平性を吟味する必要がある。理想的検索は全課題でMeMoを上回り、BrowseComp-PlusのQwen条件ではHippoRAG2もMeMoを上回る。Gemini実行モデルの結果は単回実行であり、Qwen条件の3回平均と同じ不確実性を持つとは言えない。外部の強力な実行モデルを使えば記憶モデルを再学習せずに改善できる一方、API料金と対話回数の増加は別途考慮する必要がある。

## 既存研究との差と位置付け

従来の検索拡張生成は文書の索引と検索結果のテキストを実行時に渡す。MeMoは知識の検索単位を文書片ではなく、あらかじめ学習した記憶モデルの短い回答へ変える。したがって検索雑音や長い文書の再投入を避けられる反面、事前学習費用と知識の更新・出典追跡の難しさが新たなボトルネックとなる。

実行モデル自身を微調整する方式と異なり、凍結したモデルの能力を維持しながら外部知識を追加できる。軟らかい潜在表現やKVキャッシュを持ち運ぶ方式と異なり、記憶モデルと実行モデルは自然言語を介して接続するため、モデル内部の形式や重みへのアクセスを要求しない。これは汎用性の利点である一方、モデル間で直接内部状態を共有する方式より多段対話の生成費用がかかりうる。

本サーベイでは、MeMoを「長文脈検索の代替として、別モデルに知識を格納する推論時メモリ方式」に位置付ける。大規模推論基盤のKVキャッシュ圧縮や専門家配置を直接改善する研究と区別し、知識の格納形式、文書数に対する問い合わせ計算量、事前学習費用、実行時の生成回数、回答精度を主要比較軸とする。
