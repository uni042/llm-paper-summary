# PromptDistill — 中間層での重要トークン選択と隠れ状態の引継ぎ

## 概要

長文の入力を持つ大規模言語モデルでは、プロンプトの全位置を全Transformer層で処理すると、入力長に伴って注意計算と中間状態の保存量が増える。PromptDistillは、最初の数層だけ全位置を処理した後、入力の最後の位置のqueryと各位置のkeyから選んだ重要位置に計算を集中する。選んだ位置の**中間隠れ状態をそのまま次の層へ引き継ぐ**ことが、重要位置のトークンIDを先頭層から再処理するGemFilterとの差である。さらに初期層に残るKVキャッシュも同じ位置だけに切り詰め、後続の自己回帰生成で長い元入力を繰り返し参照しないようにする。

Llama 3.1 8B InstructのLongBenchでは、1024位置保持の平均得点がGemFilterの34.50から35.36へ上昇したが、全KVの36.72には届かない。Qwen2 7Bでは同条件の34.02から36.43へ改善した一方、全KVの38.06には及ばない。論文は計算量の解析と品質評価を提示するが、これらの平均得点差をそのまま実運用の処理速度倍率へ変換してはいけない。<https://arxiv.org/pdf/2503.23274> の本文§2–3とTable 1–5を照合した。

## 問題設定

従来のSnapKVやH2Oは、入力全体を一度モデルへ通した後でKVを圧縮するため、生成時のキャッシュ削減はできても長い入力の全層prefill計算を削れない。GemFilterは初期層で重要位置を選ぶことでこの問題を緩和するが、選んだ位置のトークンをモデルの先頭層から再実行する。これは最初の選別過程で既に計算した隠れ状態を活用しない設計であり、選ばれなかった文脈から注意機構を介して混入した情報も引き継がれない。

PromptDistillの仮説は、初期層で重要位置が他の位置へ注意を向けて獲得した情報を、その位置の隠れ状態に保持できるというものである。したがって、単に選んだ位置の生トークンを再入力するより、選択層の出力を保存して後続層を実行した方が、短い系列でも文脈を保持しやすい。ただしこれは情報の完全保存を保証するものではない。後段層で参照したかった未選択位置の情報は不可逆に失われるため、選択位置数と選択層の設定が精度を左右する。

## 手法

### 最後の入力位置のqueryによる選択

入力系列長を`n`、保持数を`k`、選択層を`r`とする。まず層0から層`r`まで全`n`位置を通常どおり通す。層`r`で最後のプロンプト位置のquery `Q_n^(r)`と各位置のkey `K_j^(r)`の内積を計算し、得点上位`k`位置の添字集合を選ぶ。論文§2.1の`Select(Q_n^(r), K^(r), k)`はこの上位位置選択を表す。入力全体を検索する別の小型モデルを学習するのではなく、対象モデルが既に生成した注意用表現を流用するため、追加学習を要求しない。

最後の位置が持つ質問や指示に関係する情報が、保持する文脈を決める。選択後の系列は元の全位置ではなく、上位位置の隠れ状態を集めた短い系列となる。得点が高いというだけで後段のすべての注意に最適とは限らず、例えば文書全体の均等な情報が必要な要約では、質問に強く依存した位置選択が不利になる可能性がある。これは方式の選択基準から導かれる制約であり、論文が個別の要約失敗率を一律に示しているという意味ではない。

### 選択した中間隠れ状態の継続処理

選択層の出力から`k`位置の隠れ状態を取り出し、**層`r+1`以降だけ**を実行する。GemFilterでは重要位置を選んだ後、そのトークンIDを先頭層から再入力するため、最初の`r`層の重要位置計算を重ねて行う。PromptDistillは同じ中間状態を使うので、この再計算を省く。しかも選択前の注意により、保持位置には削除位置から集約された文脈情報が含まれ得る。単純なトークン間引きと違って、削除前の文脈相互作用の一部を次の層へ運ぶことが、品質維持の中心的な工夫である。

この操作は通常のTransformerをそのまま無改造で呼び出すだけでは実現しない。中間層で系列長を変更し、隠れ状態の位置添字と層ごとのKVを対応させる推論実装が必要になる。元の全位置を処理した初期層と、短縮後の位置しか処理していない後期層では、生成時に参照するKVの構成が異なる点に注意が要る。

### 初期層のKVキャッシュ切詰め

隠れ状態だけを減らす基本方式では、選択前の層0〜`r`のKVが元の`n`位置分残る。生成する新トークンはこれらの初期層で長い元系列を参照し続けるため、後期層を短縮しても復号時のメモリ・注意計算が残る。論文Algorithm 2は選択添字集合を得た時点で、**処理済みの全層のKとVを同じ添字で切り詰める**。その後はすべての層で保持位置`k`と新規生成位置だけを参照する。

KV切詰めは後段層の短縮とは独立した追加処理であり、前段KVを削らない版との比較が論文Figure 1にある。Llama 3.1 8BのLongBenchでは、保持1024/2048/4096位置で切詰め版の平均が35.36/36.23/36.37となり、切詰めなしの35.18/36.15/36.25をわずかに上回った。少なくともこの設定では切詰めに伴う精度悪化は見られず、復号時のKV負担を減らす意味がある。ただし、この差は小さく、すべての入力やモデルで切詰めが必ず精度を改善するとはいえない。

### 多段選択と選択層の配置

単段では層`r`まで全位置を保持する必要がある。これをさらに短縮するため、層`r_1, r_2, ...`ごとに`k_1 > k_2 > ...`と段階的に保持位置を減らす方式も検討する。早い層では重要位置を見極める能力が低いため、多めの位置を残し、より後の層で絞る。例えばLlama 3.1 8Bで層5→8→13に16,384→8,192→1,024位置を残す構成は、LongBench平均35.53で単段35.36を0.17ポイント上回った（Table 5）。一方、層1→8→13の同じ保持数では35.32と単段を下回る。多段化の効果は自動的に単調増加せず、初期層の選択時点が重要になる。

論文Algorithm 4では選択層と保持数を配列として受け、`tt`でKV切詰めを行う段階数を指定する。中間で保持数を減らしても、その時点までの全層のKVを必ず同じ添字で整理しなければ、後続生成で参照位置の整合が取れない。多段化は選択を増やすことで計算を省ける反面、複数回の添字抽出・KV移動・メモリ再配置を要する。本文の主比較は公平性のため単段で実施されており、多段の実機運用速度を単段の結果から断定できない。

## 評価条件

| 項目 | 一次論文の条件 |
|---|---|
| 対象モデル | Llama 3.1 8B Instruct（32層）、Phi 3.5 Mini 3.8B Instruct（32層）、Qwen2 7B Instruct（28層） |
| 選択層 | Llama: 13、Phi: 19、Qwen2: 16 |
| 保持位置数 | 1,024 / 2,048 / 4,096、H2Oは4,096位置で比較 |
| 比較方式 | 全KV、H2O、SnapKV、GemFilter、PromptDistill |
| 品質評価 | LongBench（多種長文脈タスク）、InfBench（長文脈の合成・実データ課題）、Needle in a Haystack（位置依存の情報回収） |
| Needle入力長上限 | Llama 120K、Phi 86K（全KV実行時GPUメモリ制約）、Qwen2 32.2K（モデル上限） |
| 実装公開 | 著者GitHubのPromptDistill。論文の主結果は品質スコアと計算量解析であり、実機の絶対トークン毎秒値ではない |

LongBenchの比較表における既存方式の値は、著者がGemFilter論文の再現実験と概ね整合することを確かめた上で、元論文の報告値を表へ統合したと明記されている。全てのベースラインが同一マシン上で再測定されたものとして扱ってはいけない。Qwen2の選択層16は、GemFilterの性能が高く、かつできるだけ早い層を選ぶという条件で決定した。付録A.4には層21で35.15、層23で34.87のGemFilter結果もあるが、後半層では短縮できる計算が減るため層16を選んでいる。

## 主要結果

### LongBenchの平均得点

|---|---:|---:|---:|---:|
| Llama 3.1 8B・1,024 | 36.72 | 34.50 | 35.36 | +0.86 |
| Llama 3.1 8B・2,048 | 36.72 | 35.87 | 36.23 | +0.36 |
| Llama 3.1 8B・4,096 | 36.72 | 36.09 | 36.37 | +0.28 |
| Phi 3.5 Mini・1,024 | 34.62 | 32.74 | 33.74 | +1.00 |
| Phi 3.5 Mini・2,048 | 34.62 | 31.69 | 33.75 | +2.06 |
| Phi 3.5 Mini・4,096 | 34.62 | 33.35 | 34.13 | +0.78 |
| Qwen2 7B・1,024 | 38.06 | 34.02 | 36.43 | +2.41 |
| Qwen2 7B・2,048 | 38.06 | 35.73 | 37.52 | +1.79 |
| Qwen2 7B・4,096 | 38.06 | 36.95 | 38.08 | +1.13 |

この表の数値は論文Table 2の平均値であり、相対速度向上率ではなく**評価得点の絶対差**である。例えばQwen2・1,024位置の+2.41は2.41パーセントの高速化を意味しない。Qwen2・4,096位置の38.08は全KV38.06を0.02ポイント上回るが、評価誤差の統計的有意性は示されていないため、全KVを一般的に凌駕したと結論づけるべきではない。

### InfBenchと情報回収の負の結果

InfBench（Table 3）ではLlama 3.1 8B・1,024位置でGemFilter平均28.15に対しPromptDistill28.44、全KV35.73だった。Phi 3.5 Mini・1,024位置は17.59から19.71へ改善するが全KV22.79を下回る。Qwen2 7B・1,024位置は17.12から18.70へ改善するが全KV19.73を下回る。特にLlamaの`kv_retr`項目は全KV66.6に対してPromptDistill・1,024位置で2.0、4,096位置でも9.2しかない。平均値の小さな改善だけでは、精密な長文脈検索で大きな情報喪失が起き得ることを隠してしまう。

Needle in a Haystack（Table 4）ではLlamaの1,024位置が全KV85.2、SnapKV64.0、GemFilter81.8、PromptDistill82.6。Qwen2の1,024位置は全KV91.2、SnapKV90.5、GemFilter69.7、PromptDistill71.6であり、提案方式はGemFilterを改善してもSnapKVや全KVには大幅に劣る。Llamaの2,048位置ではGemFilter84.7に対しPromptDistill84.3で**0.4ポイント悪化**した。したがって「GemFilterより常に高品質」とは言えない。入力のどの位置に重要情報があるか、モデルと保持数の組合せに応じて評価が変わる。

Phi 3.5のInfBenchではGemFilter・4,096位置が平均3.44に急落する一方、PromptDistillは20.50を維持した。付録A.2によれば、著者環境ではPhi 3.5に長さが**ちょうど4,096トークン**の入力を与えると意味のある回答を生成できず、4,000または4,100トークンでは正常だった。ハードウェア・CUDA版・微調整の影響が疑われるが確定原因は示されていない。GemFilterは選択後に4,096トークンを先頭から再入力するため、この特殊な障害に遭遇する。従ってこの極端な差をPromptDistill固有の一般的品質改善として集計するのは不適切である。

### 計算量と切詰め・多段の検証

論文Table 1はプロンプト長`n`、選択後長`k`、層数`m`、選択層`r`、生成長`t`などを使った理論比較である。全KVやSnapKV/H2Oではprefillで全`m`層の長文脈を処理する一方、GemFilterとPromptDistillは全`n`位置を初期`r`層に限定する。GemFilterは選択後に`k`位置を先頭層から再計算するが、PromptDistillは残り`m-r`層だけを処理する。論文の式ではこの再計算省略が生成側の項から`r h k^2 d`に相当する計算を減らす形で示される。

切詰めなしの基本方式では初期`r`層の長いKVを残すため、復号時に`r h (n-k)t d`に相当する余分な計算が残る。切詰め版ではこの項を避けられ、生成時のKV規模を各層で保持位置`k`に揃えられる。これは計算量の漸近解析であり、実際のGPUで同じ倍率の速度差を得る保証ではない。索引選択、KV再配置、注意カーネルの実装とメモリ帯域の影響を別途測る必要がある。

多段選択のLongBench評価（Table 5・6）では層5/8/13の16,384/8,192/1,024位置が35.53と最良例だが、層1/8/13は35.32、層0/8/13は35.30で単段35.36を下回る。早すぎる段階で情報を捨てると後段で回復できないことを示す実測例である。多段の理論的な計算削減と、各モデルでの実際の速度・品質の両立は分けて評価する必要がある。

## 既存研究との差

H2OやSnapKVが主として全入力を処理した後のKV保持位置を選ぶのに対し、PromptDistillは全層を通す前に位置を絞り、prefill側の計算を削減する。GemFilterも初期層で位置を選ぶが、選択位置のトークンを再び先頭から通すため、選択層で得た隠れ状態を使い捨てる。PromptDistillは中間隠れ状態の継続利用によってこの再計算をなくし、さらに初期層KVの切詰めによって自己回帰生成時の長いKV参照も抑える。これらは別々の費用を削減する機構である。

ただしGemFilterと比較した品質上の利得は、モデル・ベンチマーク・保持数で大きく異なる。GemFilterに対するLongBench平均差が+0.28から+2.41ポイント程度でも、全KVとの隔たりやNeedleでの逆転が存在する。設計の違いを説明するときは「中間状態を保持すれば常に正確になる」と単純化せず、実際の比較条件に即して評価する必要がある。

## 限界・適用条件

第一に、重要位置の選択が最後の入力位置のqueryに依存する。最後の位置が複数の独立した問いや長文全体の情報要求を十分に代表しなければ、後段に必要な位置を削除し得る。選択は不可逆であり、後から別の質問が来る複数ターン対話で同じ圧縮KVを使い回す場合の品質保証は論文の主要実験からは導けない。

第二に、圧縮の利得は入力長、選択層、保持数、生成長に依存する。短い入力では選択やKV再配置の費用が相対的に大きくなる。論文の理論解析だけでは、バッチングした配信環境での実際のトークン毎秒、初回応答遅延、GPUメモリのピークや多同時実行時の挙動は定量確定できない。評価に用いた選択層もモデルごとに調整されており、未検証モデルへの一律設定の転用は避けるべきである。

第三に、圧縮が情報検索に不利な条件が実測されている。LlamaのInfBench `kv_retr`が全KV66.6からPromptDistill・1,024位置2.0へ落ちる事実は、平均スコアだけで品質維持を主張する危険を示す。Qwen2のNeedle・1,024位置も全KV91.2に対して71.6であり、元入力の一部を必ず正確に取り出す用途では保持数を増やすか、原文検索などの別経路が必要になる。

第四に、Phi 3.5とGemFilterの4,096位置で見られる極端な失敗は環境固有の可能性があり、再現条件の確認なしに一般的なGemFilterの弱点と断定できない。論文は2025年3月のプレプリントv1であり、正式採録・独立再現を確認したという意味ではない。著者実装の公開は確認できるが、論文の表だけで運用時の総合優劣を決めるべきではない。
