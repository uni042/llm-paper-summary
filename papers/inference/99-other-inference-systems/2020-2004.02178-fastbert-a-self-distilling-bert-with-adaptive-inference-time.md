# FastBERT: a Self-distilling BERT with Adaptive Inference Time

## 概要
FastBERTは、すべての入力へBERTの全12層を通す固定計算をやめ、入力ごとの難しさに応じて途中層から結果を返す適応推論方式である。各Transformer層の後ろに軽量なstudent classifierを置き、その予測分布の正規化エントロピーが十分低ければ、そのサンプルだけバッチから抜いて早期終了する。中間分類器は最終teacher classifierのsoft labelから自己蒸留されるため、別の小型モデルを用意しない。12個の英語・中国語分類データセットで、閾値に応じてBERT比およそ1〜12倍のFLOPs交換範囲を示す。

## 問題設定
固定深さのBERTは簡単な入力にも難しい入力にも同じ12層を実行する。オンライン負荷では入力難度と要求量が変動するため、常に最大計算を使うとピークに合わせた過剰なサーバ資源が必要になる。一方、6層・3層など固定の小型studentへ蒸留すると、すべての入力が同じ浅さに固定され、難しい入力だけ追加計算する柔軟性がない。

## 手法
FastBERTのbackboneはBERT-base相当の12層Transformerと最終teacher classifierからなる。各中間層には同型の軽量student classifierを接続する。分類器は768次元から128次元へ縮約し、小型self-attentionと全結合を通してラベル分布を出す。論文のFLOPs表では1 Transformer blockが約1809.9M FLOPsに対し、classifierは約46.1M FLOPsであり、枝の追加費用は層を省く利益より小さい。

学習は段階化される。まず通常の事前学習済みBERTを利用し、対象タスクでbackboneとteacher classifierをfine-tuneする。次にbackboneを固定し、各student classifierの予測分布をteacherのsoft labelへKL divergenceで近づける自己蒸留を行う。student同士は独立に学習でき、teacher出力が教師なので追加の人手ラベルを必須としない。

推論では各層のstudent出力pから正規化エントロピーを不確実性として計算する。論文のSpeed閾値より不確実性が低いサンプルはその層で終了し、高いサンプルだけ次層へ進む。バッチ内でもサンプルごとに終了層が異なるため、簡単な入力の冗長計算を除去できる。

Speedを上げるほど早期終了が増えてFLOPsは減るが、浅い層の誤判定も増える。したがってSpeedは精度と計算量を運用側で調整するノブになる。これは固定小型モデルと異なり、同じ重み集合のまま負荷状況に合わせて計算予算を変えられる点が特徴である。

## 評価条件
中国語6データセットと英語6データセットでBERT、固定深さDistilBERT相当、FastBERTを比較する。主効率指標は実時間ではなくFLOPsであり、Speed=0.1/0.5/0.8などの閾値で精度と計算量の曲線を測る。

| 観点 | 内容 |
|---|---|
| backbone | BERT-base相当12層 |
| データセット | 中国語6 + 英語6 |
| 終了判定 | student予測の正規化エントロピー |
| 効率指標 | FLOPs / BERT比speedup |
| 比較 | BERT、固定層数のDistilBERT系 |
| 調整 | Speed閾値で精度・計算量を変更 |

## 主要結果
中国語ChnSentiCorpではSpeed=0.1でBERTの95.25%精度を維持しつつ約2.02倍のFLOPs削減相当を示す。THUCNewsでは同設定で96.71%を維持し約6.05倍となる。Speed=0.8では多くのデータセットで約6〜12倍まで計算量を減らす一方、難しい課題では精度低下が大きくなる。

英語DBpediaではSpeed=0.1で99.28%・約10.57倍、Amazon Fullでは同閾値でも約1.03倍に留まる。これは同じ閾値でも入力・データセットの難度分布により終了層が変わることを示す。

## 既存研究との差
従来の蒸留は別studentへ固定容量を移すのに対し、FastBERTは同一backbone内の中間枝を自己蒸留し、推論時にサンプル単位で深さを変える。BranchyNet型の早期終了をBERTへ持ち込み、蒸留と不確実性判定を一体化した点が差分である。

## 限界
評価は分類タスク中心で、自己回帰decoder-only LLMの1トークンずつの生成にはそのまま適用できない。主効率指標はFLOPsであり、動的バッチからサンプルを抜く制御コストやGPU利用率を含むサービング実時間とは一致しない。早期終了は閾値次第で品質を落とすため、SLOに応じた校正が必要である。
