# ZipServ: Fast and Memory-Efficient LLM Inference with Hardware-Aware Lossless Compression

> LLMのBF16重みには指数部の偏りがあり無損失圧縮できるが、HuffmanやANSのような可変長符号はGPUのSIMT並列性を崩し、復号後の重みを一度グローバルメモリへ展開する方式は余計な読み書きを増やして推論を遅くする。ZipServは各重みの指数を固定長3ビットの三重ビットマップへ符号化するTCA-TBEを用い、デコード時には圧縮重みを読みながらレジスタ上でBF16へ復元してTensor Coreへ直接渡すZipGEMMで中間展開を消す。プリフィルでは復号を別カーネルへ分けてcuBLASを使う段階適応も行う。RTX4090・L40Sなどの実機でモデル重みを最大約30%削減し、ZipGEMMはcuBLAS比最大2.21倍、エンドツーエンドではvLLM比平均1.22倍のスループット向上を報告する。

## 問題設定
LLM推論では重みがGPUメモリ容量とデコード時のメモリ帯域を大きく消費する。量子化なら容量を減らせるが近似誤差を伴うため、元のBF16値を完全に復元できる無損失圧縮には品質面の利点がある。しかし従来のHuffman符号や非対称数値系（Asymmetric Numeral Systems; ANS）は、頻度に応じて符号長が変わる可変長ビット列を作る。GPUのワープでは32スレッドが同じ命令系列を進めるため、要素ごとに読むビット数や分岐先が変わる復号はスレッド分岐と直列的なビット解析を生み、圧縮しない行列積より復号だけで長くなる場合がある。さらに既存の推論統合は圧縮重みをいったんBF16の完全な行列としてグローバルメモリへ書き、次のGEMMがそれを再び読む二段構成が多い。この中間書き込み・再読み出しで圧縮により減らしたDRAM通信を取り戻してしまい、RTX4090の屋根線解析ではバッチ8～64で標準GEMMより計算密度が約62%低下する。無損失圧縮を単なる保存形式ではなく推論高速化へ変えるには、GPUが並列に復号できる固定的な配置と、復号後重みをグローバルメモリへ実体化しない実行経路の双方が必要になる。
## 新規性
ZipServはBF16重みの8ビット指数に強い偏りがあり、多くの行列で頻出指数が数値的に連続していることを利用する。頻出する連続7指数を基準指数から1～7の3ビット固定長コードへ変換し、8×8の64要素タイルごとに三つの64ビット平面へ分離して格納するTCA-TBEにより、3ビットコードがワード境界をまたぐ不規則アクセスを避ける。頻出範囲外だけ完全BF16を退避するため無損失性を保つ。さらにZipGEMMは圧縮重みを共有メモリへ読み、各スレッドが必要な2要素をレジスタ上でBF16へ戻してTensor Coreの入力片へ直接詰め、復号と行列積を二段のソフトウェアパイプラインで重ねる。この『圧縮したまま読み、復号した値で即計算する』構造により、復号結果の巨大な中間バッファを消す。デコードでは融合経路、演算密度が高いプリフィルでは単体復号＋cuBLASへ切り替えるため、圧縮形式は同じまま推論段階に応じて最適なカーネルを選ぶ点もシステム上の新規性である。
## 手法
### 手法のあらまし
事前圧縮では各重み行列のBF16指数ヒストグラムを調べ、7個の数値的に連続した指数値を含む窓のうち最も多くの重みを覆うものを選ぶ。論文の3,875行列の調査では99.6%で頻出7指数が連続し、選ばれた連続窓だけで平均97.1%の重みを覆う。窓の最小指数より1小さい値を基準指数とし、窓内の指数は1～7の差分で表す。各8×8タイルの64要素について、その3ビット差分コードを要素ごとの3ビット列として密に詰めるのではなく、1ビット目だけを集めた64ビット地図、2ビット目、3ビット目という三つのビット平面へ分解する。同時に符号と7ビット仮数は頻出値バッファへ格納し、窓外を示すコード0の要素だけ元の16ビットBF16値を例外バッファへ保存する。頻出指数の被覆率が約96%なら平均格納量は1要素約11.3ビットとなり、指数エントロピーから求めた理論下限約10.6ビットに近い。

オンラインのデコードではZipGEMMがこの圧縮表現を直接使う。行列をTensor Core命令の粒度に合わせて8×8の基礎タイル、16×16のTensor Coreタイル、その上のスレッドブロック用タイルへ階層化し、連続した三重ビットマップと符号・仮数、例外値を合流読み出ししやすい配置にする。各スレッドは担当位置の3枚のビットを読み、コード0なら例外バッファのBF16を、1～7なら基準指数へコード値を足して指数を復元し、符号・仮数と結合する。復元した二つのBF16は`bfloat162`形式のレジスタへ詰められ、そのまま`mma.sync`のTensor Core入力になるため、完全な復号済み重み行列をグローバルメモリへ書かない。コード長固定、ワープ内の実行経路固定、ビット平面が64ビット境界へ整列することで、一般的な可変長符号の分岐と非整列アクセスを避ける。

ZipGEMM内部では粗粒度と細粒度の二段パイプラインを使う。粗粒度では二つの共有メモリバッファを交互に使い、現在タイルを計算している間に次タイルの圧縮重みと活性値を非同期転送する。細粒度ではK方向を16×16程度の断片へ分け、Tensor Coreが断片iを積和している間にALUが断片i+1のビット演算、例外判定、BF16再構成を行う。タイル切替時だけ非同期コピー完了とブロック同期を取り、同一ワープ内の読込・復号・計算には追加障壁を置かない。このため整数ALUによる復号費を、もともとデコードで長いDRAM読込待ちとTensor Core計算の隙間へ重ねられる。実測では圧縮によりDRAM読込が29.3%減る一方、ALU使用率は66%まで上がるがTensor Core利用率はcuBLASの71.6%を保つ。

ただしプリフィルは多数トークンをまとめた大きなGEMMで演算密度が高く、同じ融合復号を使うと整数ALU処理が隠れず逆に遅くなる。そこでZipServはデコードの小さいNではZipGEMM、プリフィルの大きいNでは高速な単体復号カーネルで一度BF16をグローバルメモリへ展開し、その後cuBLASのTensor Core GEMMを使う。N=8192/16384ではこの復号追加費がGEMM時間の約4%/2%なので、高演算密度領域では既存行列積の最適化を活用する方が良い。両経路は同じTCA-TBE圧縮形式と同じ要素復号ロジックを共有するため、推論途中で別形式へ再圧縮する必要はない。vLLM側ではモデルローダと線形層実行を拡張し、PyBind11経由でCUDA共有ライブラリを呼ぶ。

### 連続指数窓を使うTCA-TBE無損失符号
BF16は符号1ビット、指数8ビット、仮数7ビットから成るが、学習済みLLMの重みでは指数分布が強く偏る。ZipServは行列ごとにヒストグラムを作り、最も多くの重みを含む連続7指数を選び、その直前を基準指数にする。窓内の指数は基準との差1～7だけで表現できるため3ビットで足り、コード0を窓外の例外に予約する。符号と仮数は8ビットの頻出値バッファへ保存し、例外だけ完全な16ビットBF16を別バッファへ置くので、どの重みも元の指数・符号・仮数を再構成できる。単に頻度上位7値を辞書化するのでなく数値的に連続した窓を選ぶことで、コードから指数を加算一回で求められ、大きな辞書参照を避ける。平均11.3ビット/要素という容量削減と、GPUで軽い整数演算だけで復号できる性質を同時に作っている。

### 三重ビットマップとTensor Core粒度の階層配置
3ビットコードを通常の密なビット列へ詰めると、隣接要素のコードが32/64ビット境界をまたぎ、担当スレッドごとにシフト量や読込位置が変わる。TCA-TBEは8×8の64重みを単位に、コードの第1・第2・第3ビットをそれぞれ独立した64ビット整数へ集める。各スレッドは同じ位置の3ビットを三つの整列語から取得できるため、合流したメモリアクセスと分岐の少ない実行経路を得る。さらに8×8基礎タイルをTensor Coreが扱う16×16タイルへ組み、複数タイルをスレッドブロック単位へまとめる階層配置にする。圧縮形式そのものをGPU命令が消費する断片構造へ合わせることで、単なる圧縮率だけでなく、共有メモリのバンク競合やワープ分岐まで減らす。実測では共有メモリ競合がDietGPUの数百万規模に対して約4.7千まで抑えられた。

### レジスタ直接復号を行うZipGEMM融合カーネル
既存の無損失推論では、復号カーネルが圧縮重みを読み、完全BF16行列をグローバルメモリへ書き、GEMMが同じ行列を再度読む。この往復はデコードのような帯域律速領域で特に高価である。ZipGEMMは圧縮重みを共有メモリへ運んだ後、各スレッドが担当値の3ビットコードを再構成し、頻出値なら基準指数＋コード、例外なら完全値バッファからBF16を得る。二要素をTensor Core入力に合うレジスタ形式へ詰め、そのまま積和命令へ渡すため、復号済み行列をグローバルメモリへ一度も実体化しない。屋根線モデルでは中間展開型より計算密度を大幅に上げ、圧縮しないGEMMよりも約50%高い計算密度になり得る。これが保存容量の削減を実行時間の短縮へ変換する中心機構である。

### 読込・復号・Tensor Core計算を重ねる二段パイプライン
圧縮でDRAM読込量を減らしても、復号の整数演算を直列に足せば利得は失われる。ZipGEMMはタイル単位の二重バッファでグローバルメモリから共有メモリへの次タイル転送を現在タイルの計算と重ね、さらにタイル内部ではK方向の断片ごとに、Tensor Coreが断片iを計算中にALUが断片i+1を共有メモリから読みレジスタへ復号する。タイル境界では非同期コピー完了とブロック同期を行うが、ワープ内部の断片処理はSIMTの暗黙同期を使う。この構成により復号の整数・論理命令が増えてALU使用率66%になっても、Tensor Core利用率はcuBLAS基準の71.6%を維持した。したがって高速化は復号自体が無料だからではなく、削減したメモリ待ち時間の中へ予測可能な復号計算を埋めることで成立する。

### プリフィルとデコードを分ける段階適応実行
LLMのプリフィルとデコードでは同じ線形層でも支配資源が異なる。デコードは各要求からほぼ1トークンずつ処理する小さいNの行列積で、重みを読む時間が長いためZipGEMMの約30%の読込削減が効きやすい。対してプリフィルは入力トークンをまとめた大きいNでTensor Core演算が支配し、各重みをその場で復号するALU費が隠しにくい。ZipServはここで無理に単一融合カーネルを使わず、プリフィルでは高速な単体復号でBF16重みを展開してcuBLASへ渡す。N=8192/16384で追加費はGEMM時間の約4%/2%に留まる。圧縮形式を共通化しながら、メモリ律速なら融合、演算律速なら分離という選択を行うため、デコード高速化のための形式がプリフィル全体を大きく悪化させるのを防ぐ。

### 全体のデータ／制御の流れ
ZipServはオフライン圧縮器とオンライン推論エンジンに分かれる。デプロイ前に各BF16重み行列を一度だけ解析し、行列ごとの基準指数、三つのビット平面、符号・仮数バッファ、例外BF16バッファへ変換する。LLaMA-3.1-8Bの圧縮準備は16コアXeon 8352Vで約2.5分で、オンラインのクリティカルパスには入らない。推論時にはvLLMのローダがこの形式をGPUへ読み、線形層ごとに実行段階を見てデコードならZipGEMM、プリフィルなら単体復号＋cuBLASを選ぶ。ZipGEMM内では圧縮データだけをDRAMから読み、共有メモリとレジスタで復号しながらTensor Coreへ供給するので、静的重み容量と毎トークンの重み帯域を同時に減らす。圧縮で空いたGPUメモリはvLLMの管理下でKVキャッシュへ回せ、LLaMA-3.1-8Bの分解評価では静的重み14.96GBから11.18GBへの削減でKV容量が5.07GBから8.60GBへ増えた。
## 評価条件
- **ハードウェア**: RTX4090 24GB ×4＋Intel Xeon Platinum 8352V 512GB DDR4、L40S 48GB ×4＋Intel Xeon Gold 6230R 512GB DDR4、RTX5090 32GB、境界条件評価のA100・H800
- **ソフトウェア**: vLLM統合ZipServ、CUDA/C++ ZipGEMM、cuBLAS Tensor Core GEMM 12.4.5、DietGPU、nvCOMP rANS、DFloat11、Transformers
- **モデル**: LLaMA3.1-8B/70B/405B、Qwen2.5-7B/14B/32B/72B、Gemma3-12B/27B、Mistral-24B/123B
- **データセット／トレース**: 実モデルから抽出したQKV・出力・Gate/Up・Down・LM head線形層形状、エンドツーエンド生成ではバッチ8/32、出力長128～2048トークン
- **比較対象**: cuBLAS Tensor Core BF16 GEMM、DietGPU、nvCOMP rANS、DFloat11、vLLM、Transformers、Marlin W8A16 FP8（損失あり比較）
- **正確性・品質**: TCA-TBEは頻出指数を3ビット差分で、例外指数を完全BF16値で保存し、符号と仮数も保持するため、圧縮した重みを元のBF16表現へ無損失復元する。評価は速度と容量が中心で、量子化による精度劣化との比較は動機付けおよびMarlinとの性能比較として扱う。
- **ZipGEMMカーネル単体**: RTX4090とL40Sで実際のLLM線形層形状を使い、バッチ8・16・32における融合ZipGEMMを圧縮なしcuBLAS、DietGPU、nvCOMP、DFloat11と比較する。100回のウォームアップ後に1000回計測し、カーネル単体の高速化と、復号を別段階に置く方式の遅延を切り分ける。
- **復号カーネル単体**: LLaMA3.1-8BとMistral-24BのTransformerブロック全重みを対象に、行列積を含まないZipServ単体復号とDietGPU、nvCOMP、DFloat11の復号時間を比較する。固定長配置自体が融合GEMMだけでなく復号処理にも効くかを確認する。
- **GPU世代・用途横断**: RTX5090へ特別なBlackwell新機能を使わずZipGEMMを移植し、RTX4090/5090とA100/H800のcuBLASを比較する。消費者・推論向けGPUの帯域制約では圧縮読込が効く一方、高帯域データセンターGPUでは利得が弱まる境界を測る。
- **プリフィル追加費**: 行列積のNを1～16384まで変え、デコードの小Nでは融合ZipGEMM、プリフィルの大Nでは単体復号＋cuBLASへ切り替える段階適応の妥当性を評価する。N=8192/16384で復号追加費がGEMM時間の約4%/2%かを測る。
- **エンドツーエンドサービング**: LLaMA3.1-8BをRTX4090 1枚、Mistral-24BをL40S 2枚、LLaMA3.1-70BをL40S 4枚のテンソル並列で実行し、バッチ8/32、出力長128・256・512・1024・2048を各10回測定する。vLLM、Transformers、DFloat11と要求全体遅延および出力トークン毎秒を比較する。
- **メモリ内訳**: RTX4090上のLLaMA3.1-8B、系列長1024で、線形層・注意・その他の遅延と静的重み・KVキャッシュのGPUメモリ内訳を比較し、重み圧縮で空いた容量が実際にKVキャッシュへ再配分されるか確認する。
カーネル単体、単体復号、GPU世代差、プリフィル追加費、エンドツーエンド、メモリ内訳を分けて測り、最大2.21倍というZipGEMMのカーネル倍率と、vLLM比平均1.22倍というサービング全体倍率を混同しない構成になっている。データセンターGPUでは同じ融合方式が常にcuBLASを上回らない負の条件も明示している。
BF16重みの統計的冗長性を利用するNVIDIA GPU向け実装であり、KVキャッシュ圧縮や活性値圧縮は将来課題。主な高速化対象はメモリ帯域律速のデコードで、高演算密度プリフィルは別経路へ切り替える。A100/H800のようにHBM帯域が豊富でコア周波数が低い装置では整数ALU復号を隠しにくく、融合ZipGEMMが圧縮なしcuBLASを下回る場合がある。
## 主要結果
ZipServは無損失圧縮を保存容量削減だけでなくデコード高速化へ結び付けた。RTX4090ではZipGEMMが圧縮なしcuBLASに対して平均1.31倍・最大1.71倍、L40Sでは平均1.36倍・最大2.21倍となり、DietGPU・nvCOMP・DFloat11のような分離復号方式は平均でcuBLASを下回った。エンドツーエンドではvLLM比で平均17.60%の遅延削減、平均1.22倍のスループットを示す。LLaMA3.1-8Bでは静的重みを14.96GBから11.18GBへ減らし、空いた容量でKVキャッシュを5.07GBから8.60GBへ拡大した。一方A100/H800では高HBM帯域によりメモリ律速が弱く、融合復号が常にcuBLASを上回るわけではない。

- ZipGEMM対cuBLAS高速化 / RTX4090平均1.31倍・最大1.71倍、L40S平均1.36倍・最大2.21倍 (比較対象: cuBLAS Tensor Core BF16 GEMM; 条件: 実LLM線形層形状、バッチ8/16/32のカーネル単体評価) — 約30%少ない重み読込を整数ALU復号と重ね、復号済み重みの中間グローバルメモリ書込を消すことで、帯域律速領域では圧縮なしGEMMより速くなる。

- エンドツーエンド遅延 / 平均17.60%削減 (比較対象: vLLM; 条件: LLaMA3.1-8B、Mistral-24B、LLaMA3.1-70B、バッチ8/32、出力長128～2048) — 全処理がZipGEMMになるわけではないためカーネル最大倍率より小さいが、デコードで線形層が支配する条件では重み帯域削減が要求全体の短縮へ波及する。

- エンドツーエンドスループット / vLLM比平均1.22倍、Transformers比3.18倍、DFloat11比8.52倍 (比較対象: vLLM、Transformers、DFloat11; 条件: 同じエンドツーエンド評価全体) — 無損失復号を別カーネルとして直列化するDFloat11に対して特に差が大きく、圧縮形式と行列積の協調設計がオンライン推論で重要であることを示す。

- 代表長文生成スループット / LLaMA3.1-8Bで1105出力トークン/秒、vLLM比1.66倍 (比較対象: vLLM; 条件: RTX4090、バッチ32、出力長2048) — 出力が長いほどデコード線形層で同じ重みを繰り返し読むため、圧縮読込の帯域削減を多数ステップで回収しやすい。

- 静的重み容量 / LLaMA3.1-8B 14.96→10.83GB、Mistral-24B 43.92→31.30GB、LLaMA3.1-70B 131.56→93.52GB (比較対象: BF16非圧縮重み; 条件: エンドツーエンドモデル配置) — 約27.6～28.9%の静的重み削減により、同じGPU容量でKVキャッシュやバッチへ使える余地が増える。

- KVキャッシュ容量再配分 / 5.07GB→8.60GB、1.70倍 (比較対象: 非圧縮vLLM; 条件: LLaMA3.1-8B、RTX4090、系列長1024の内訳評価) — 内訳評価では静的重みが14.96GBから11.18GBへ減った3.78GBをメモリ管理器がKVキャッシュへ回し、容量削減がサービング並行度へ直接つながる。

- 単体復号カーネル / DietGPU比2.14倍、nvCOMP比1.83倍、DFloat11比1.10倍 (比較対象: 各無損失復号方式; 条件: LLaMA3.1-8BとMistral-24Bの1 Transformerブロック全重み) — 三重ビットマップの固定長・ワープ整列配置は、融合GEMMを使わないプリフィル用単体復号でも可変長符号よりGPU並列性を保ちやすい。

- プリフィル復号追加費 / N=8192で約4%、N=16384で約2% (比較対象: cuBLAS GEMM時間; 条件: 演算密度が高いプリフィルで単体復号＋cuBLASへ切替) — 融合復号が不利な大Nでは高速GEMMをそのまま使い、圧縮による追加処理を全体の数%へ抑える段階適応が機能する。

### 負の結果・境界条件
- **小さい一部線形層ではZipGEMMがcuBLASより遅い**: L40S上のLLaMA3.1-8Bの注意出力射影ではZipGEMMがcuBLASの0.79倍まで低下した。小さい行列はsplit-Kやタイル設定を細かく調整しないとハードウェアを使い切れず、復号追加費の割合も大きい。ただし当該層はTransformerブロック全体のFLOPsでは小さく、ブロック全体では高速化を維持する。
- **A100/H800では融合ZipGEMMが常にcuBLASを上回らない**: 学習向けデータセンターGPUはHBM2e/HBM3帯域が豊富で、ZipServが狙う重み読込ボトルネックが弱い。一方A100のようにコア周波数がRTX4090より低い装置では整数ALU復号をメモリ待ちへ隠しにくいため、圧縮なしcuBLASの方が速い条件がある。手法の利得はGPUの演算対帯域比に依存する。
- **損失ありFP8カーネルよりは遅い**: RTX4090、重み形状28672×4096、バッチ32でZipGEMMは0.194ms、Marlin W8A16 FP8は0.143msで、ZipGEMMが1.36倍遅い。これは実効約11ビット対8ビットの読込量差に近く、無損失性を保つ代わりに強い量子化と同じ帯域量までは減らせないことを示す。
- **プリフィルでは融合復号が逆効果になる領域がある**: Nが大きいプリフィルは行列積が演算律速になるため、重み読込削減の恩恵よりその場復号のALU処理が支配しやすい。このためZipServ自身がZipGEMMを使わず単体復号＋cuBLASへ切り替える。単一カーネルが全推論段階で最適という方式ではない。
- **オフライン圧縮準備が必要**: LLaMA-3.1-8BのTCA-TBE変換には16コアXeon 8352Vで約2.5分かかる。モデルごと・重み更新ごとに一度必要だが、デプロイ前処理のためオンライン要求の遅延には入らない。頻繁に重みを更新する用途では準備費を考慮する必要がある。

### 結果の読み方
ZipServの利得は『圧縮したから速い』だけでは説明できない。一般的な無損失圧縮は容量を減らしても、可変長復号の分岐と、完全重みを一度書いて再読込する二重通信で速度を失う。ZipServは固定長の三重ビットマップにより復号処理をワープで揃え、復号値をレジスタから直接Tensor Coreへ渡すことで中間通信を消す。結果として整数ALU仕事は増えるがDRAM読込が29.3%減り、その復号をメモリ待ちと行列積へ重ねられるGPUでは総時間が短くなる。逆にHBM帯域が十分なGPUや演算律速のプリフィルでは同じ交換関係が成立しないため、装置・段階に応じた切替が性能の条件となる。
## 品質への影響
TCA-TBEは元のBF16重みを符号・仮数・指数まで復元する無損失表現であり、圧縮率のために重み値を丸める量子化とは異なる。したがってモデルパラメータの近似による品質劣化を導入しない。一方、損失あり8ビット方式はさらに小さい転送量で速くできるため、ZipServは『絶対に最速』ではなく、元BF16表現を保持する必要がある用途で容量と速度を同時改善する選択肢である。
## 既存研究との差
- GPTQ・AWQ・Marlinなどの量子化系は重みをより少ないビットへ近似して容量と帯域を削るが、ZipServは保存されたBF16重みを正確に復元する。品質との交換で8/4ビットまで縮めるのではなく、指数分布の統計的冗長性だけを取り除き、約11ビット/要素の実効表現で元値を保つ点が異なる。
- NeuZip、DietGPU、ZipNNなど既存の無損失圧縮は保存・通信や学習メモリ削減を主眼にするか、推論時も復号と行列積を別カーネルとして実行する。ZipServはGPU推論そのものを目的に圧縮形式をTensor Core粒度へ合わせ、復号後の重みをレジスタから行列積へ直接渡すことで中間グローバルメモリを削る。
- DFloat11もLLM推論向け無損失圧縮だがHuffman型の可変長符号を使い、完全な重みを復号してから計算する経路を取る。ZipServは3ビット固定長コードを三つの64ビット平面へ分けることで、ワープごとに異なるビット位置解析や分岐を避け、融合ZipGEMMを成立させる。
- 一般的なカーネル融合は既存データ形式の複数演算を一つにまとめるが、ZipServは圧縮データ形式自体をTensor Coreの8×8/16×16断片階層と共同設計している。したがって形式・メモリ配置・復号命令・行列積パイプラインを一体として最適化するハードウェア協調設計である。
- デコード専用の帯域削減手法に対し、ZipServはプリフィルでは融合ZipGEMMが不利になることを認め、同じ圧縮形式の単体復号＋cuBLASへ切り替える。圧縮形式を維持したまま推論段階ごとに実行経路を変える点が、単一カーネルを全条件へ適用する方式と異なる。
## 限界
- 高速化はメモリ帯域律速が強いGPUほど得やすい。A100/H800のようにHBM帯域が豊富な学習向けGPUでは、削減したDRAM読込より整数ALU復号費が相対的に大きくなり、融合ZipGEMMがcuBLASへ届かない条件がある。
- 小さい線形層ではタイル・split-Kなどの細粒度調整が不足すると復号追加費を隠せず、L40S上のLLaMA3.1-8B注意出力射影ではcuBLAS比0.79倍となる。全形状で必ず単体高速化するわけではない。
- プリフィルの大Nでは融合復号が演算律速を悪化させるため、完全重みをグローバルメモリへ一度展開する分離経路が必要になる。デコードで消した中間バッファをプリフィルでは再び使うため、ピーク一時メモリと復号費が完全になくなるわけではない。
- TCA-TBEの圧縮率はBF16指数の偏りと連続性に依存する。調査した現行LLMでは3,875行列中99.6%で上位7指数が連続したが、将来の重み分布や別データ型で同じ被覆率になる保証はない。
- 元BF16を保つため実効約11ビット/要素であり、Marlin W8A16のような損失ありFP8より転送量は多い。代表条件では0.194ms対0.143msで1.36倍遅く、品質保持が不要なら強い量子化の方が高速・省容量になり得る。
- 現在の実装はNVIDIA CUDAとTensor Coreを対象とする。著者はIntel AMXやAMD Matrix Coreへの拡張可能性を議論するが、論文時点の実機検証は行っていない。
- 圧縮対象は主にモデル重みで、長文推論で支配的になり得るKVキャッシュの無損失圧縮は将来課題である。重みを約30%削減しても、長文・高並行度ではKV容量が次のボトルネックになる。
## 実装状態
約3.5K行の実装があり、約2.5K行のCUDA/C++でTCA-TBE圧縮器とZipGEMM、約1K行のPythonでvLLM統合を行う。GCC 11.3、NVCC 12.4、RTX5090のみNVCC 12.8で評価され、公開コードはHPMLL/ZipServ_ASPLOS26として提供されている。ASPLOS '26の査読済み会議論文である。
## 研究上の位置づけ
ZipServはMoE固有ではなく、LLM重み全体を対象にする無損失圧縮とGPU推論カーネルの共同設計であるため、現行リポジトリでは99-other-inference-systemsへ置くのが最も自然である。研究上の価値は、圧縮率だけではオンライン推論性能を決められず、復号の並列性・中間メモリ交通・Tensor Coreへの供給形式まで含めて設計しないと容量削減が速度低下へ変わることを実証した点にある。特にデコードでは『DRAMから読むビット数を減らし、その代わりの整数復号を待ち時間へ隠す』という交換関係を明示しており、SSD/NVMeやCXLから重みを供給する階層メモリ研究にも応用可能な原理を持つ。将来SSDから圧縮重みを直接供給する場合も、I/O削減だけでなくGPU側の復号位置と中間実体化を同時に設計する必要がある。
