# LLMCompass: Enabling Efficient Hardware Design for Large Language Model Inference

## 概要

大規模言語モデル（Large Language Model、LLM）の推論には、膨大な重みを保存するメモリ、行列演算器、注意計算のためのキャッシュ、複数装置間の通信が必要になる。新しいアクセラレータを設計する際、最高演算性能や最高メモリ帯域の仕様だけを比較しても、実際のモデルがどの程度速く動くかは分からない。詳細な命令周期シミュレータは精度が高いが、1750億パラメータ級のモデルを多数の設計候補で評価するには遅すぎる。反対に単純な演算強度モデルは高速でも、行列をどのように分割し、メモリ階層へ載せるかという実装上の制約を捨ててしまう。

LLMCompassはこの間を埋めるハードウェア評価基盤である。モデルの演算グラフとハードウェアの階層的な記述を受け取り、行列積などをタイル単位で模擬する。配置探索器（mapper）がタイル形状、演算器への割当、実行順序、メモリ転送との重ね合わせを探索し、各設計候補で有利な実行方法を選ぶ。さらに面積と部品費用を推定することで、速いだけでなく費用対性能の良い構成を比較できる。

著者らはNVIDIA A100、AMD MI210、Google TPUv3の実測と比較し、個別演算の遅延の平均誤差10.4%、LLM推論全体の平均誤差4.1%を報告した。GPT-3 175Bを4基のA100で推論する模擬では、26,400回の配置候補探索を含めて一般的なCPU一コアで15～16分だった。さらに、初期入力を処理するプリフィル（prefill）は演算器とバッファを使う一方、逐次生成のデコード（decode）は重みとKVキャッシュの読み出しに制約されるという違いから、低遅延志向と高処理率志向の二つの設計を比較した。

## 問題設定：推論の二段階で律速が異なる

プリフィルでは入力の多数のトークンをまとめて処理するため、大きな行列積が生じる。演算器の数、行列タイルの大きさ、オンチップバッファが性能に影響しやすい。デコードでは新しいトークンを一つずつ生成し、毎回モデルの重みと過去の鍵・値キャッシュを読み出す。バッチが小さい場合、演算器は十分に埋まらず、メモリ帯域が支配的になる。したがって演算性能を二倍にしてもデコード速度が二倍になるとは限らない。

また、高帯域メモリ（High Bandwidth Memory、HBM）は帯域が高いが容量が限られ、価格も高い。複数リクエストをまとめるバッチ処理では、一度読み出した重みを多数のトークンへ使い回せるため処理率が上がるが、バッチを増やすほどKVキャッシュと中間値が増え、HBM容量の制約が厳しくなる。大容量の通常DRAMへ置き換えればバッチを増やせる一方、帯域が下がり、一リクエストの待ち時間が長くなる。このため「低遅延」と「高処理率」を単一の最適構成で同時に満たすのは難しい。

従来の屋根線モデル（roofline model）はピーク演算性能と帯域から上限を求めるが、実際のタイル分割や装置間通信の順序を粗く扱う。命令周期シミュレーション（cycle-level simulation）は詳細な制御を再現するが、推論全体の長い実行時間と膨大な配置候補を評価するには重い。LLMCompassは、LLMを構成する演算が行列積、ソフトマックス、層正規化など規則的な形を持つことを利用し、タイル単位の時間モデルで高速に探索する。

## 手法

### 1. ハードウェア記述の階層化

入力するハードウェア記述は、複数の装置をつなぐ相互接続、各装置の外部メモリ、装置内の大域バッファ、演算コア、各コアの局所バッファ、演算レーン、ベクトル演算器、シストリック配列（systolic array）などからなる。コア数、レーン数、演算配列の形、バッファ容量、メモリ帯域、装置間帯域を変数として指定する。GPUとTPUの内部構造は同一ではないが、共通の階層表現へ写すことで、異なる種類の設計を一つの探索器で比較できる。

例えば表1ではA100、MI210、TPUv3の演算器形状とメモリ階層のパラメータを記述している。モデルの演算グラフはハードウェアとは独立して与えるため、同じGPT-3の推論を異なる装置構成へ割り当てて評価できる。各装置にどの層やテンソルを分配するかも入力条件に含められる。ただし実機の専有キャッシュ制御や命令発行機構をすべて記述するわけではなく、主要なデータ移動と演算の容量制約を捉える抽象化である。

### 2. 行列積のタイル単位の時間模擬

行列積 `C=A×B+C` を考えると、巨大な行列を一度にコアへ渡すことはできない。まず外部メモリから大域バッファへ入るタイルへ分割し、さらに各コアの局所バッファへ入る小タイルへ分割し、最後にレーンの演算配列へ割り当てる。どの軸を先に分割するか、同じ入力タイルを複数コアで共有するか、部分和をどこで統合するかによってデータ転送量と並列度が変わる。

図4は、異なるコアが異なる出力タイルを計算する方式と、同じ出力タイルの部分積を計算して最後に加算する方式を対比する。前者では共通入力タイルの読み出しを統合でき、同じ出力タイルを連続更新する場合は中間値の再読込を省ける。後者では部分結果の統合通信が必要になる。LLMCompassはタイルを計算単位としてこれらの依存関係を扱い、各階層のデータ転送と演算の重なりを模擬する。

最下層のシストリック配列の周期数は、専用の演算配列シミュレータSCALE-Simを利用して見積もる。よく使う演算形状の結果を参照表へ保存することで、同じ形状の再計算を避ける。全体を命令一個ずつ模擬するのではなく、規則的な演算の結果を再利用するため、大規模モデルでも短時間で探索できる。ここでの高速化は「シミュレーションの実行時間」の短縮であり、モデルそのものの生成速度ではない。

### 3. 配置・スケジュール探索器

配置探索器はタイル形状、ループ順序、コア・レーンへの割当、演算とメモリ転送を重ねる二重バッファリングなどを候補化する。二重バッファリングはデータ読み込み中に前のタイルを計算できるが、追加のバッファ容量を消費し、一度に載せられるタイルを小さくする場合がある。したがって有効な設定はハードウェアのメモリ容量と演算器形状に依存する。探索器は各候補の遅延を評価し、その設計で有利な配置を選ぶ。

ハードウェアだけを変更して、ソフトウェアの配置を以前のまま固定すると、新しい演算器の性能を十分に利用できない。LLMCompassが配置探索を内蔵する理由は、設計ごとに有利なタイルやスケジュールを選び直すためである。逆に言えば、この探索結果は実際の実装が同じ配置を実現できることを前提とする。ライブラリやコンパイラの制約によって最適配置が使えなければ、実機性能との差が大きくなる可能性がある。

### 4. 装置間通信と演算グラフの合成

複数GPUでのテンソル並列では、注意計算や全結合層の後に全削減通信（AllReduce）が必要になる。LLMCompassは装置間リンクの遅延、追加オーバーヘッド、帯域、転送サイズを使って通信時間を推定し、リング型の全削減通信もモデル化する。演算グラフに沿って各演算と通信を接続することで、単一行列積だけでなくモデル全体の遅延を求める。特にGPT-3のような多数の層を持つモデルでは、同じ層の演算・通信が繰り返されるため、この合成が重要となる。

通信モデルは転送量だけでなく固定遅延を含むため、小さい通信を多数回行う構成と大きい通信を少数回行う構成を区別できる。一方で、実機の混雑、専有ネットワーク制御、複数通信の重なり方を完全に再現するものではない。通信の相対的な費用を把握して設計を比較することが主目的である。

### 5. 面積・費用モデル

性能評価だけでは、高価なHBMや大きな演算器を増やした設計が常に有利に見える。そこで著者らは演算器とSRAMのトランジスタ数、CACTIによるバッファ面積、公開された半導体写真、製造工程とウェハ費用、メモリ部品価格から、設計の面積と概算費用を推定する。コア内制御やコア間接続の一部は公開情報から推定し、GA100とAMD Aldebaranの面積を比較して誤差を検証する。

この費用は製造の概算であり、知的財産のライセンス、マスク、パッケージング、開発費、運用電力などをすべて含む総所有費用ではない。性能対費用の数値は同じ推定モデルの中で候補を比較するためのものであり、実際の製品価格やクラウド利用料を直接予測したものではない。

## 評価

### 評価条件

実機性能の検証にはNVIDIA A100、AMD MI210、Google TPUv3を用いる。モデルの例はGPT-3 175Bで、4基のA100を使うテンソル並列構成を模擬する。シミュレーション時間はIntel Xeon Gold 6242R 3.10GHzの一コアで測定し、26,400回の配置候補探索を含めて15～16分だった。個別演算では行列積などの異なる形状を比較し、モデル全体では推論遅延を比較する。

ハードウェア設計空間の分析では、基準のGA100と4-wayテンソル並列を用い、プリフィルはGPT-3の一層をバッチ8・入力2048トークンで処理する条件、デコードは同じ入力から1024番目の出力トークンを生成する条件で測る。演算精度はFP16である。これは長文脈・小バッチのチャット利用と、大バッチの一括処理で律速がどう変わるかを切り分けるための設定であり、すべての入力長やバッチに対する単一の代表値ではない。

### 主要結果

### 実機に対する予測精度と評価速度

個別演算の遅延の平均誤差は10.4%、LLM推論全体の平均誤差は4.1%だった。個別演算での誤差がそのまま足し合わさって全体の誤差になるわけではない。大きな行列積や重み読み出しが支配的な条件では、個々の演算の過大評価と過小評価が相殺される場合もある。これは検証したGPU・TPUとモデル条件での結果であり、未知の演算器に対する精度を保証するものではない。

GPT-3 175Bを4基のA100で模擬する例では、配置候補26,400通りを探索して15～16分だった。大規模モデルを数百・数千のハードウェア候補で比較する際、各候補の配置を探索できる計算量であることが重要である。面積モデルではGA100の推定誤差5.1%、Aldebaranの推定誤差8.1%だった。専有の制御回路やコア間接続を公開情報だけから完全に再現できないことが誤差の一因とされる。

### プリフィルとデコードの異なる演算器依存

図7の設計Aは、基準のGA100に比べて計算能力を大きく削った構成であり、プリフィル遅延は3.25倍になる一方、デコード遅延はわずか0.1%しか悪化しなかった。演算器を増やしてもデコードが重み読み出しで律速されていれば効果が小さいという、実測ではなくモデルに基づく設計探索結果である。反対にプリフィルは行列積が大きいため、演算器を削ると大きく遅くなる。

バッファ容量についても、プリフィルではタイルを大きくしてデータ再利用を増やせるため効果が大きいが、デコードでは重みの読み出しが支配的なため効果が限定される。したがって「LLM推論には大きな演算器と巨大なオンチップメモリが必須」という単純な設計則は成立しない。想定する入力長、出力長、バッチ数によって最適な演算器とメモリの比率が変わる。

### 低遅延向け設計と高処理率向け設計

| 指標 | GA100基準 | 低遅延向け | 高処理率向け |
|---|---:|---:|---:|
| コア数 | 128 | 64 | 64 |
| メモリ容量 | 80GB HBM | 80GB HBM | 512GB DRAM |
| メモリ帯域 | 2TB/s | 2TB/s | 1TB/s |
| ダイ面積 | 826mm² | 478mm² | 787mm² |
| 正規化性能 | 1.00 | 0.95 | 1.41 |
| 推定ダイ費用 | 151ドル | 80ドル | 142ドル |
| 推定メモリ費用 | 560ドル | 560ドル | 154ドル |
| 推定合計費用 | 711ドル | 640ドル | 296ドル |
| 正規化性能対費用 | 1.00 | 1.06 | 3.41 |

低遅延向け設計では、メモリシステムをGA100相当に保ったまま計算器を半分程度に削り、ダイ面積を42.1%減らしても平均性能の95.3%を維持した。デコードは重み読み出しに律速されるため、演算器を減らした影響が小さい。プリフィルが極端に長い条件では性能が下がりやすいので、すべての用途で95.3%を維持するとは限らない。

高処理率向け設計では512GBの通常DRAMとPCIe 5.0/CXL相当の接続を使い、メモリ帯域を半分の1TB/sへ下げる代わりに大きなバッチを扱う。大容量により一度読んだ重みを多くのトークンへ使い回せるため、平均処理率はGA100比で約1.42倍になった。費用モデルではメモリ費用が560ドルから154ドルへ下がり、合計費用が711ドルから296ドルへ減り、処理率対費用が最大3.41倍になった。ただしこの値はハードウェア構成と推定価格を固定したシミュレーション結果であり、実際の製品の性能保証ではない。

### 大バッチ設計の負の結果

高処理率向け設計では、平均遅延がGA100の約9.21倍に悪化した。大バッチで重みを使い回すことはできても、各リクエストのKVキャッシュを読む量は減らず、むしろバッチ全体のKVキャッシュが新しい律速になる。論文は大容量DRAMでバッチを12倍以上大きくできる条件でも、メモリ帯域が半分なら理想的な処理率改善を得られないことを示している。したがって高処理率志向の設計は対話的な短遅延サービスには不向きな場合がある。

この結果は、性能の指標を明示する必要性を示す。秒間トークン数の増加、個々のリクエストが完了するまでの遅延、最初のトークンまでの時間、ハードウェア費用は別の軸である。処理率対費用が3.41倍という数値だけで「利用者にとって3.41倍速い」と表現するのは誤りである。プリフィル・デコードの比率が異なるサービスでは、二つの設計の優劣も変わる。

## 既存研究との差

屋根線モデルは演算強度とピーク帯域から性能の上限を求めるが、タイル形状、メモリ階層、装置間通信、演算と転送の重ね合わせを細かく扱えない。命令周期シミュレーションは詳細だが、巨大なLLMと多数の設計候補を扱うと実行時間が膨大になる。LLMCompassはLLMの密演算子の規則性を利用して、ハードウェア記述と配置探索を組み合わせたタイル単位の中間的なモデルを構築した。

さらに面積と費用のモデルを同じ基盤へ組み込んだ点が特徴である。ピーク演算性能が大きい設計が必ずしも最良の費用対性能にならず、低遅延向けには帯域を維持して計算器を減らす、高処理率向けには容量を増やしてバッチを大きくするという異なる設計点を示した。評価基盤の有用性を、既存GPUの遅延を再現できることだけでなく、新しい構成を比較できることによって示している。

## 限界

### 限界・負の結果・適用範囲

第一に、性能モデルは規則的な密演算と既知のメモリ階層を前提とする。実際のGPUやTPUでは命令発行、キャッシュ置換、専有制御、通信競合、ソフトウェア実装の違いがあり、タイル単位の近似では捉えきれない。平均4.1%の推論遅延誤差は検証した機種とワークロードの範囲であり、未知のハードウェアや新しい演算器でも同じ精度になる保証はない。

第二に、配置探索器が選んだタイル形状や実行順序を、実際の推論ライブラリが実現できるとは限らない。低ビット量子化、特殊な注意カーネル、非構造疎化、専門家の動的ロードなど、論文の主要評価と異なる実装では追加の制約が生じる。実装可能なスケジュールの範囲が変われば、設計候補の優劣も変化する。

第三に、面積と費用のモデルは製造の一部を推定するものであり、知的財産ライセンス、マスク、パッケージング、開発費、電力・冷却、保守費用をすべて含まない。高処理率向けの3.41倍という費用対性能は論文の部品価格と設計仮定の下での相対値であり、現在の市場価格やクラウドの総所有費用に直接転用できない。

第四に、性能と遅延の交換条件は大きい。大容量DRAM構成は平均処理率を1.42倍にしたが、平均遅延は9.21倍悪化した。バッチを大きくすると重み読み出しの償却は進むが、KVキャッシュ読み出しが増えるため、無制限の処理率改善にはならない。対話的なサービスでは利用者の待ち時間を考慮しなければならない。

第五に、対象は主にGPT型の密なTransformerとFP16演算である。現代の大規模混合専門家モデル、動的なKV圧縮、階層メモリからのオフロード、CPU・SSDを含む分散配置、連続バッチ処理のような新しい配信方式では、モデルの演算グラフと通信・メモリ制約を追加して再検証する必要がある。本論文の数値はハードウェア設計空間の研究結果であり、特定の既存GPUの導入効果を直接予測するベンチマークではない。
