# LLMCompass: Enabling Efficient Hardware Design for Large Language Model Inference

## 概要
LLMCompassは、大規模言語モデル（LLM）の推論を実行する新しいアクセラレータ構成を、RTL実装やcycle-level simulatorを作る前に比較するためのハードウェア評価基盤である。LLMは巨大なGEMMだけでなく、プリフィルとデコードで演算強度が大きく異なり、HBM容量・帯域、SRAM、演算器数、複数device間接続の組合せが性能とコストを左右する。従来のルーフラインは速いが楽観的すぎ、cycle-level シミュレーションは大規模LLMには遅すぎる。

LLMCompassはLLMの演算グラフがGEMM、softmax、層 normalizationなど規則的な密 演算子から成ることを利用し、cycleではなくtile単位で性能を模擬する。ハードウェア記述、演算子 形状、メモリ hierarchyを入力するとmapperがtile サイズ・loop order・並列 mappingを探索し、遅延が最小となるscheduleを選ぶ。A100、MI210、TPUv3で検証した結果、演算子 遅延の平均誤差10.4%、LLM推論全体では4.1%で、4×A100上のGPT-3 175Bを26,400回のmapping探索込み15〜16分で評価できる。

## 問題設定
LLM用ハードウェアを比較する際、単純なピークFLOPSやHBM帯域だけでは実際のプリフィル/デコード性能を予測できない。プリフィルは大きな行列積となり計算器とバッファを使いやすいが、1 トークンずつ進むデコードは重み読み出しが支配し、演算器を増やしても利用率が上がりにくい。またHBMは高帯域だが容量とコストに制約があり、バッチを増やしてcompute utilizationを上げようとするとKV キャッシュが増える。

cycle-accurate simulatorは詳細だが100K instructions/s未満のこともあり、175B級モデルと多数のmapping候補を探索するには現実的でない。逆にルーフラインはmappingやメモリ hierarchyの具体的なデータ移動を省略する。LLMCompassは両者の中間で、LLMに必要な粒度だけを残して設計空間探索を高速化する。

## 手法

### 一般化ハードウェア記述
計算core、vector lane、systolic array、register file、局所/大域 バッファ、off-chip メモリ、device間interconnectをパラメータ化し、GPUとTPU型設計を同じ抽象表現へ落とす。入力した演算子を各メモリ levelへどうtile化するかをmapperが決めるため、特定ISAの命令列を用意する必要がない。

この抽象化は自由度を上げる一方、proprietaryな制御・キャッシュ挙動を完全再現しない。その誤差を実機検証で定量化し、設計探索用モデルとして許容できるかを判断する。

### 性能mapper
LLM 演算子の規則的なメモリ アクセスを利用し、tile 形状、loop order、coreへの割当、テンソル 並列構成を候補化する。各候補についてcompute時間とメモリ transferを見積もり、性能最適なmappingを選択する。GPT-3 175Bの4×A100例では26,400候補を探索しても単一Xeon Gold 6242R coreで15〜16分に収まる。

プリフィルとデコードは別の形状として評価される。論文の設計探索ではプリフィルをバッチ 8・入力 2048のGPT-3一層、デコードを1024番目トークン生成時として測り、両段階で最適なハードウェア特性が違うことを明示する。

### 面積・コストモデル
性能だけでなく、公開されたtransistor count、CACTIによるSRAM面積、annotated die photo、wafer コスト、DRAM/HBM価格を組み合わせてdie areaとコストを推定する。GA100とAMD Aldebaranのdie area誤差は5.1%と8.1%で、性能/コストを同じ設計探索内で比較できる。

## 評価条件

| 項目 | 条件 |
|---|---|
| 実機検証 | NVIDIA A100、AMD MI210、Google TPUv3 |
| 大規模例 | GPT-3 175B、4-way テンソル 並列 |
| 模擬ホスト | Intel Xeon Gold 6242R 3.10GHz 1 core |
| プリフィル分析 | GPT-3 1 層、バッチ 8、入力 2048 |
| デコード分析 | 1024番目出力 トークン |
| 指標 | 遅延誤差、シミュレーション時間、面積誤差、性能/コスト |
| 比較対象 | 実機、ルーフライン/cycle-level手法との設計上の比較 |

## 主要結果

| 評価 | 結果 | 意味 |
|---|---:|---|
| 演算子 遅延 | 平均誤差10.4% | tile-level抽象化でも個別演算を概ね再現 |
| LLM inference 遅延 | 平均誤差4.1% | 演算子誤差がエンドツーエンドで大きく累積しない |
| GPT-3 175B / 4×A100 | 15〜16分 | 26,400 mapping候補込みで設計探索可能 |
| GA100/Aldebaran面積 | 誤差5.1% / 8.1% | area/コスト探索にも利用可能 |
| compute/バッファ半減設計 | 元性能の95.3%維持 | デコード中心では過剰computeを削れる |
| コスト-oriented設計 | 最大3.41倍 performance/コスト | DRAM等を含む別設計点がA100型より有利になり得る |

重要な負の結果は、スループット志向で大容量DRAMと大バッチを使う設計では、GA100比で平均遅延が9.21倍悪化することである。重みをバッチ当たり一度だけ読むことでスループットは上がっても、バッチ増大でKV キャッシュと中間値のreadが増えるため、遅延とスループットの交換条件は消えない。

## 既存研究との差
ルーフラインは演算強度と帯域から上限を高速に見るがmappingを粗く扱い、cycle-level simulatorは詳細だがLLM規模の探索が遅い。LLMCompassはLLMの密 演算子の規則性を利用し、tile-level mapping探索とarea/コスト モデルを結合する。さらに単なる評価器ではなく、そのモデルを使って「プリフィルはcompute/バッファ、デコードはメモリ 帯域」というLLM固有の設計則を抽出し、新しいハードウェア構成まで探索する。

## 限界
性能モデルは公開情報と規則的な演算子を前提とし、proprietary キャッシュ・スケジューラ・ネットワーク contentionを完全再現するものではない。FlashAttentionのようなsoftware固有最適化はメモリ アクセス patternとしてモデル化可能とするが、論文の中心評価ではない。コスト モデルもIP、mask、packaging コストを含まない。したがって3.41倍performance/コストは実製品の総所有コストではなく、論文のモデル条件下の設計比較として読む必要がある。
