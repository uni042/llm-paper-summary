# Minions: Accelerating Large Language Model Inference with Aggregated Speculative Execution

> 複数小型モデルの重み付き多数決、オンライン投機長調整、SSM/LLM非同期パイプラインを統合した投機的復号サービング。
## 書誌情報
- **著者**: Siqi Wang, Hailong Yang, Xuezhu Wang, Tongxuan Liu, Pengbo Wang, Xuning Liang, Kejie Ma, Tianyu Feng, Xin You, Yongjun Bao, Yi Liu, Zhongzhi Luan, Depei Qian
- **著者・所属**: Beihang University et al. (see primary manuscript)
- **公開**: arXiv
- **種別**: プレプリント
- **対象**: 投機的復号、複数ドラフトモデル、適応投機長、パイプライン、vLLM
- **実装**: PythonでvLLMを拡張。PagedAttentionの複数投機トークン入力、失敗トークンKV削除、NVIDIA MPSによるSSM/LLM同時実行を実装。
## 概要
Minionsは複数の小型投機モデルを重み付き多数決で統合し、検証対象を一本の代表系列へ絞ることで大規模モデルの追加検証負荷を抑えつつ受理率を高める投機的復号システムである。大規模モデルの検証時間を受理トークン数で割った指標を実行時監視し、投機長をオンライン調整する。さらに小型モデル復号と大規模モデル検証の間に中間結果プールを置いて非同期化し、プール量を大規模モデルのバッチサイズ付近へ制御してパイプライン空泡とKVキャッシュ過剰滞留を同時に抑える。vLLM上に実装し、4基A100でLlama2-70B-chatとOPT-13Bを評価して既存サービング基盤やSpecInferに対する低遅延・高スループットを報告する。

Minionsは三つの機構を統合する。第一に、複数SSMの候補系列を木へ統合し、過去のLLM受理率で更新するSSM重みに基づくトークン単位の重み付き多数決で一本の代表系列だけを選ぶ。これにより複数SSMの集合知を使いつつLLM検証候補数を増やさない。第二に、LLMの検証時間tLLMを平均受理長vlで割ったtLLM/vlをオンライン観測し、傾向に応じて投機長sを増減する。第三に、中間結果プールでSSMとLLMを非同期化し、プール量をLLMバッチサイズに合わせて制御することでパイプライン空泡とKVキャッシュ滞留を抑える。

代表結果として、Llama2-70B-chat 遅延 vs vLLMはfinance/chatbot/dialogueでvLLMに対して平均3.10× / 2.86× / 2.70× 高速化倍率。複数SSM、多数決、適応長、パイプラインの統合で要求当たり正規化遅延を削減。
## 問題設定
標準的な投機的復号は小型投機モデル（small speculative model; SSM）がs個の将来トークンを逐次生成し、大規模言語モデル（LLM）がまとめて検証する。SSMとLLMの能力差が100〜1000倍級のパラメータ差から生じると受理率が低く、長い投機は検証1回当たりのLLM計算を増やす。最適投機長はモデル、データセット、バッチサイズで変化するため固定値では最適化しにくい。さらに従来はSSM生成後にLLM検証、その後またSSM生成という直列実行で、どちらかが常に待機する。複数SSMを単純に全部検証するとLLM検証量が増え、能力向上の利得を相殺する。
## 新規性
Minionsは三つの機構を統合する。第一に、複数SSMの候補系列を木へ統合し、過去のLLM受理率で更新するSSM重みに基づくトークン単位の重み付き多数決で一本の代表系列だけを選ぶ。これにより複数SSMの集合知を使いつつLLM検証候補数を増やさない。第二に、LLMの検証時間tLLMを平均受理長vlで割ったtLLM/vlをオンライン観測し、傾向に応じて投機長sを増減する。第三に、中間結果プールでSSMとLLMを非同期化し、プール量をLLMバッチサイズに合わせて制御することでパイプライン空泡とKVキャッシュ滞留を抑える。
## 手法
### 手法のあらまし
端から端まで（エンドツーエンド）の処理機構は、①到着要求をpending poolへ入れる、②スケジューラがLLMの実行時統計とintermediate result pool量を見てSSM実行時刻と投機長sを決める、③複数SSMが各要求についてsトークンの候補系列を生成する、④候補系列を木へ統合し各SSMの重みによる多数決で一本のmajority-approved sequenceを選ぶ、⑤その系列をintermediate result poolへ格納してSSMをLLMから切り離す、⑥LLM execution engineがプールからバッチを取り出して投機トークンを並列検証する、⑦受理率を記録してvoted SSMの重みと投機長制御へフィードバックする、⑧未完了要求をrunning poolへ戻して次ラウンドへ進める、という循環である。投機長は総生成トークン数Nに対してLLM総時間がN/vl(s)×tLLM(b,s)となるモデルから、tLLM/vlを最小化するようオンライン調整する。SSMがLLMより速いため無制御では中間プールが膨張し、未検証要求のKVキャッシュがGPUメモリを占有する。そこでプール量がLLMバッチサイズ以上ならSSMを停止し、下回れば即再開してLLM側に十分な仕事だけを供給する。vLLM実装では既存KVがある系列へ複数投機トークンを入力できるようPagedAttentionを拡張し、検証失敗トークンのKVスロットをBlockManagerから削除する。NVIDIA MPSでSSMとLLMを同時実行する。

### 重み付き多数決投機器
複数SSMが生成した系列を共通接頭辞を共有する木へ変換し、各ノードの重みをそのノードを通るSSM重みの総和として定義する。根から各深さで最大重みの子を選び、最終的に実在する一つのSSM系列を代表候補としてLLMへ送る。LLM検証後はそのvoted SSMが選ばれた要求の平均受理率を計算し、閾値を上回れば報酬、下回れば罰として重みを乗算更新する。複数候補をLLMへ同時検証しないため、複数SSMの能力を利用しながら検証計算量の爆発を避ける。重要なのは多数決が単純な各位置の独立投票ではなく、各SSMが実際に生成した系列を枝として保持する木上で行われる点である。このため位置ごとの投票を混ぜてどのSSMも生成していない不整合な系列を作らず、選択結果は必ず一つのSSMの有効な接頭辞経路になる。データセットや要求分布が変化して特定SSMの得意領域が変わっても、LLM検証から得る受理率をオンラインで重みに反映することで、固定的に一つのSSMを選ぶ方式より適応できる。

### 適応投機長選択器
投機長sを長くすると検証回数は減るが1回のLLM検証コストが増え、受理されず捨てる候補も増える。MinionsはLLM総時間をN/vl(s)×tLLM(b,s)と表し、Nはsに依存しないのでtLLM/vlを最小化する問題へ簡約する。実行時モニタが検証時間と平均受理長を蓄積し、一定量の観測後に線形傾向を計算する。指標が改善中ならsを増やし、悪化中なら罰幅だけ減らす。変更直後に旧sの要求がプールへ残るためdecision thresholdを設け、混在期間の統計だけで早計に再変更しない。

### SSM/LLM非同期投機パイプライン
SSM出力をintermediate result poolへ入れ、LLM検証を待たずSSMが次要求を処理できるようにする。LLMもプールに要求がある限り連続検証できるため、従来の交互待機を重ね合わせる。ただしSSMが速すぎると未検証要求とKVキャッシュが蓄積し、swap/recomputeやバッチ縮小を招く。そこでプール量を監視し、LLMバッチサイズ以上ならSSMを一時停止、下回れば再開する。LLMに空泡を作らない最低限の先行量だけを維持して、パイプライン化とメモリ安全性を両立する。

### vLLM投機KV管理拡張
通常vLLMのデコードは系列ごとに新規1トークンとKVブロックを対応付ける前提だが、投機検証では既存KVに複数候補トークンを一度に入力する必要がある。MinionsはPagedAttentionを複数新規トークンへ拡張し、各候補KVの論理ブロックIDとオフセットを記録する。LLM検証で棄却された候補は対応するメモリスロットをBlockManagerから削除し、受理された接頭辞だけを次ラウンドへ残す。NVIDIA MPSを使ってSSMとLLMのGPU実行を同時化するため、アルゴリズム上の非同期化を実システムの空間共有へ接続する。

### 全体のデータ／制御の流れ
Minions Engineはpending/running/intermediateの要求プール、スケジューラ、複数SSM実行器、LLM実行器から成る。スケジューラは投機長とSSM起動タイミングを制御し、majority-voted speculatorが複数SSMを一本へ集約する。LLM検証結果は受理トークンを確定すると同時にSSM重みと投機長制御へ戻される。対象LLM本体は再学習せず、SSMだけをLLM生成データで蒸留微調整する。
## 評価条件
- **ハードウェア**: NVIDIA A100 80GB×4をNVLink接続。OPT-13Bは2 GPU、Llama2-70B-chatは4 GPUのテンソル並列。
- **ソフトウェア**: Ubuntu 20.04、CUDA 11.8、cuDNN 8.9.0、PyTorch 2.0.1、transformers 4.34.0、xformers 0.0.22、pydantic 1.10.13。vLLMを基盤にPython実装し、NVIDIA MPSでSSMとLLMを同時実行。
LLMはLlama2-70B-chatとOPT-13B、SSMは蒸留微調整したLlama-160MとOPT-125M。Finance Alpaca、Chatbot Instruction Prompts、Empathetic Dialoguesの3データセットで各要求最大128新規トークンを生成する。比較対象はvLLM、TGI、DeepSpeed-FastGen、TensorRT-LLMで全てFP16。正規化要求遅延とスループットを主要指標とし、バッチ=16で多数決、適応投機長、パイプラインを段階追加するアブレーション、固定投機長2〜12との比較、バッチ=32でSpecInfer比較、制御処理オーバーヘッド測定を行う。
SSMはLLM生成データによる蒸留微調整が必要で、完全な追加学習不要方式ではない。評価モデルは2023年前後のLlama2/OPT系、ハードウェアはA100 4基まで。TensorRT-LLMより一部バッチ=32設定で遅い。SpecInfer比較では比較実装に既知の演算子問題があり、Llama2-70Bでは注意重みロード失敗のため比較不能。Minionsの基盤はvLLMであり他サービング系への移植は未実装。
## 主要結果
MinionsはLlama2-70B-chatでvLLM比平均2.70〜3.10倍の正規化遅延改善、平均2.69〜3.02倍のスループット向上を3データセットで示す。各基盤との最大値ではFastGen比で遅延最大7.06倍、スループット最大6.84倍など大きい。OPT-13Bでも同様に改善するが、一部バッチ=32では高度に最適化されたTensorRT-LLMがMinionsを上回る。多数決、適応投機長、パイプラインはそれぞれ追加利得を持ち、制御処理の合計オーバーヘッドは最大2.37%。

- Llama2-70B-chat 遅延 vs vLLM / 平均3.10× / 2.86× / 2.70× 高速化倍率 (比較対象: vLLM; 条件: finance/chatbot/dialogue) — 複数SSM、多数決、適応長、パイプラインの統合で要求当たり正規化遅延を削減。

- Llama2-70B-chat スループット vs vLLM / 平均3.02× / 2.76× / 2.69× (比較対象: vLLM; 条件: finance/chatbot/dialogue) — LLM検証を連続稼働させるパイプラインと受理率改善が寄与。

- Ablation: majority / +9.56% OPT-13B, +59.82% Llama2-70B (比較対象: traditional speculative デコード; 条件: finance, バッチ=16) — 複数SSMを一本の候補へ集約して検証量を増やさず受理品質を改善。

- Ablation: 適応型 selector / 追加+35.07% / +5.91% スループット (比較対象: majority enabled; 条件: OPT-13B / Llama2-70B) — 固定sが最適から遠いOPTで特に大きい。

- Ablation: パイプライン / 追加+34.27% / +55.37% スループット (比較対象: majority+selector; 条件: OPT-13B / Llama2-70B) — SSMとLLMの直列待機を重ね合わせる効果。

- SpecInfer comparison / 7.61〜14.49× スループット, 6.34〜8.89× 遅延 高速化倍率 (比較対象: SpecInfer; 条件: OPT-13B, バッチ=32) — ただし比較SpecInfer実装には既知問題があり慎重な解釈が必要。

### 負の結果・境界条件
- 一部データセットのバッチ=32ではTensorRT-LLMがMinionsより高速。SpecInfer比較はFlexFlow演算子問題で比較側性能が論文報告より低く、Llama2-70Bでは注意重みロード失敗で比較できない。多数決はSSM能力が似るOPT financeでは追加利得が小さく、適応投機長も既定sが最適に近いLlama2では利得が小さい。

### 結果の読み方
単一のドラフトモデルや固定投機長だけを改善するのではなく、候補品質、検証コスト、SSM/LLM資源待機、KV滞留をサービング系全体で連動制御する点が性能源である。
## 品質への影響
投機検証はLLMの分布を用いた受理・再サンプリング規則に従い、LLM本体を量子化・枝刈りしない。SSMは蒸留微調整されるが最終出力の権威はLLM検証側にある。
## 既存研究との差
標準投機的復号は単一SSMとLLMを交互実行し固定投機長を使う。SpecInferは複数SSM候補を利用するがLLM側の検証仕事も増える。Minionsは複数SSM候補を重み付き多数決で一本へ集約して検証量を抑え、さらに投機長を実行時適応し、SSMとLLMをintermediate poolで非同期化する。Medusa等の追加ヘッド方式と違いLLM構造を変更・再学習せず、vLLMのサービング層へ統合する。
## 限界
SSMをLLM生成データで蒸留微調整するため、対象LLM本体の再学習は不要でも補助モデル準備コストはある。評価はA100最大4基、Llama2-70B-chat/OPT-13B、会話系3データセットに限定され、現代の大規模MoEや長文脈での挙動は未検証。パイプラインはSSMがLLMより十分速いことを前提にし、intermediate pool制御もLLMバッチサイズを基準とする。TensorRT-LLMより遅い設定があり、SpecInfer比較には比較実装の問題が混入する。
## 実装状態
Python/vLLM上のシステムプロトタイプを実装し、PagedAttentionとBlockManagerを投機トークンのKV管理へ拡張。NVIDIA MPSでSSMとLLMを同時実行する。論文は他サービング基盤への適用可能性を主張するが実装はvLLMのみ。SSMはデータセットごとにLLMの正答生成を用いた蒸留で微調整する。
## 研究上の位置づけ
投機的復号のアルゴリズムとLLMサービングスケジューラを結合するシステム研究。受理率だけでなくLLM検証コストとの比、パイプライン空泡、KVキャッシュ滞留まで同時に扱うため、単一要求のデコード高速化よりも高並行サービングでの資源利用を重視する。後続の投機的復号研究ではドラフト木、動的長、非同期検証などがさらに発展しており、Minionsは複数ドラフトとオンライン制御を早期に統合した比較対象となる。
