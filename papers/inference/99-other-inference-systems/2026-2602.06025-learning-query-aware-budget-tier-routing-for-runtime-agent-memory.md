# BudgetMem：問い合わせ依存の記憶抽出を段階別に予算配分する小型ルータ

## 概要

BudgetMemは、長期対話や複数文書を扱う言語モデルエージェントに対して、問い合わせを受けた時点で必要な記憶を構築し、その処理費用を細かく制御する枠組みである。従来の記憶方式は履歴全体を事前に要約・索引化することが多いが、将来どの質問が来るかを知らずに情報を圧縮するため、不要な部分へ計算を費やしたり、後で必要になる詳細を失ったりする。反対に問い合わせごとに履歴を読み直す方式は、必要な情報を残しやすい代わりに応答時の費用と遅延が増える。

BudgetMemは、問い合わせごとの記憶抽出をフィルタ処理、エンティティ抽出、時系列情報抽出、話題抽出、最終要約へ分解する。各モジュールに低・中・高の三つの計算予算階層を用意し、共有の小型ルータが問い合わせと途中の抽出結果を観測して次に使う階層を選ぶ。ルータは近接方策最適化（Proximal Policy Optimization; PPO）で学習し、回答品質と処理費用を一つの報酬にまとめる。予算階層の実現方法として、アルゴリズムの複雑さ、推論の深さ、使用モデルの容量という三つの独立した軸を比較する。

LLaMA-3.3-70B-Instructを基盤とする高品質優先設定では、三データセット平均のF1がLightMemの35.45に対し、モデル容量階層方式で45.72へ改善する。一方、同じ設定の記憶抽出費用はLightMemの5.63に対し1.38である（いずれも論文表1の指標値）。ただし高品質設定でのオンライン遅延が常に短いわけではない。LoCoMoの統制実験では、容量階層方式の応答時間3,461ミリ秒はLightMemの1,662ミリ秒より長い。費用、品質、実測遅延を分離して理解する必要がある。

## 問題設定

### 事前構築と問い合わせ時構築の費用構造

履歴 $\mathcal H$ を固定長の文書片集合 $\mathcal C=\{c_i\}$ に分割する。質問 $q$ が到着すると検索器 $\mathcal R$ が候補片 $\mathcal C_q=\mathcal R(q,\mathcal C)$ を取得する。BudgetMemはその候補片から質問に必要な記憶 $m=f_{mem}(q,\mathcal C_q)$ を構築し、固定の回答生成器 $f_{ans}$ が $\hat y=f_{ans}(q,m)$ を返す。元の履歴は事前に意味要約して上書きしない。質問が来るまでは軽い分割だけを行い、質問の意図に沿った抽出はオンライン処理で実施する。

ここで最適化するのは回答生成モデルそのものではなく、回答の前段に置く記憶抽出処理である。問い合わせによって重要な情報が異なるため、すべてのモジュールに一律の高予算を割り当てるのは無駄になる。例えば、固有名詞だけを答える質問では時系列解析の高予算が不要なことがあり、逆に過去の出来事の前後関係を問う質問では時間情報の抽出に計算を回す価値がある。原著はこの判断を手作業の規則ではなく学習した方策で実現する。

### 予算をモジュール単位で与える理由

単一の「高品質モード／省費用モード」を全体へ適用すると、軽い処理で済む段階と高い推論能力が必要な段階を区別できない。BudgetMemは各モジュールの入力・出力契約を固定したまま、実装だけを低・中・高で切り替えられるようにする。この共通インターフェースにより、各段階の出力は後段へ渡せ、処理方式の違いを回答品質と費用の比較へ直接結び付けられる。

## 手法

### 1. 記憶抽出パイプライン：フィルタ→並列抽出→要約

最初のフィルタモジュール $\mathcal M_{fil}$ は、検索器が返した文書片 $\mathcal C_q$ を質問に関連する部分へ絞り、$\tilde{\mathcal C}_q$ を生成する。その後、エンティティ抽出 $\mathcal M_{ent}$、時系列抽出 $\mathcal M_{tmp}$、話題抽出 $\mathcal M_{top}$ を並列に適用し、対象人物・事物の事実 $e$、時刻・前後関係 $t$、主題情報 $p$ を得る。最後の要約モジュール $\mathcal M_{sum}$ が $(q,e,t,p)$ から記憶 $m$ を作る。

並列抽出の前にフィルタを置くのは、不要な文書片を複数の抽出モジュールへ繰り返し送らないためである。最後の要約は単純な短縮ではなく、質問に必要な情報を統合して回答生成器が使える形にする。各段の出力は次段のルータ判断にも利用されるため、ルータは質問だけでなく処理途中の情報量や内容に応じて予算を変更できる。

### 2. 予算階層の三つの実現方法

**実装階層（Implementation tiering）**では、低予算で規則・パターン照合、中予算でBERT系の小型学習済み処理器、高予算で言語モデルによる抽出を使う。同じモジュールでも、処理方法そのものを切り替える。高予算で高品質な情報抽出を使える一方、低予算では簡易規則へ落とせるため、費用の可動域が大きい。

**推論階層（Reasoning tiering）**では、基盤モデルの容量を固定し、低予算で直接生成、中予算で段階的推論、高予算で複数段の反省・再検討を行う。高予算ほど出力トークンや呼び出しが増え得るが、基盤モデルは変えない。原著ではこの方式の費用分布が比較的狭く、極端に低い予算へ移行しにくいことが観測された。計算量を大幅に切り替えるというより、同じモデル内で回答品質を微調整する用途に向く。

**容量階層（Capacity tiering）**では、低・中・高予算で異なる規模の言語モデルを使用する。原著のLLaMA系列の例では3B、8B、70B、Qwen系列では7B、32B、80B-A3Bを使う。問い合わせとモジュールの性質に応じて大きなモデルを選択できるため、高品質側の性能を押し上げやすい。ただし異なるモデルを呼び出せる実行環境やAPI価格に依存し、モデルを切り替えるための運用複雑性が生じる。

### 3. 共有ルータの状態・行動・報酬

ルータ方策を $\pi_\theta$ とし、各モジュール実行時の行動を $a_k\in\{Low,Mid,High\}$ とする。状態 $s_k$ は、質問、現在のモジュール入力、どのモジュールかを示す記述から構成される。付録の実装ではall-mpnet-base-v2で三要素をそれぞれ768次元に埋め込み、質問と入力を結合して256次元、モジュール記述を256次元へ射影し、合計512次元の状態ベクトルをルータへ渡す。埋め込みモデル自体は固定し、射影層とルータを学習する。

質問一件について、全モジュールを実行し最終回答を得るまでが一つの学習エピソードである。回答品質の報酬 $r_{task}$ と、各モジュールの費用の合計 $c_{raw}=\sum_k c(\mathcal M_k,a_k)$ から作る費用報酬 $r_{cost}$ を組み合わせる。目的は $r=r_{task}+\lambda\alpha r_{cost}$ で、$\lambda$ は費用をどれだけ重視するかを調整する。$\lambda=0$ なら品質優先となり、増やすほど低費用の階層が選ばれやすい。

費用 $c(\cdot)$ は言語モデル呼び出しの入力・出力トークン数とそれぞれの価格から計算する。小さな規則処理の費用は言語モデルと比較して無視できる近似を置く。費用報酬の尺度を安定させるため、最近の費用分布の5%点と95%点を使って平方根費用を正規化し、0〜1の範囲へ切り詰める。価格依存の報酬なので、モデル提供者の料金が変われば同じルータ方策が最適とは限らない。

### 4. 報酬尺度の整合と方策の崩壊回避

タスク報酬と費用報酬は分散が異なるため、そのまま足すと変動の大きい側が方策更新を支配する。原著は直近の報酬標準偏差を使い、$\alpha=std(r_{task})/(std(r_{cost})+\epsilon)$ という補正係数を導入する。これにより、費用を重視する設定でも単にすべてのモジュールを最安階層へ落とすのではなく、必要な部分へ高予算を残す学習を促す。

構成要素除去では、$\lambda=0.3$ の容量階層方式で尺度整合を外すと、ほぼ全モジュールでLowを選ぶ方策へ崩壊し、回答品質が大幅に低下した。整合を入れると低・中・高の使い分けが残り、費用と品質の曲線が滑らかになる。したがって報酬尺度の整合は付随的な学習安定化ではなく、予算制御が機能するための重要機構である。

### 予算選択の感度と報酬の構成要素除去

LoCoMoの費用重み $\lambda$ を増やすと、ルータは中・高階層から低階層へ選択割合を移し、品質と費用のトレードオフを連続的に動かす。実装階層と容量階層は費用の可動範囲が広く、実装階層は中程度の費用で早く品質を上げ、容量階層は高費用領域でさらに品質を伸ばす。一方、推論階層はモデル容量が固定され、推論の長さ・反省回数で費用を調整するため、費用の分布が狭い。

報酬尺度の整合を外すと、$\lambda=0.3$ で低費用階層へほぼ全面的に偏り、Judgeが著しく悪化する。費用を下げるだけの方策へ学習が崩れるという負の結果であり、実運用で報酬の相対尺度を固定してしまう危険性を示す。また、検索上位文書片の数を増やすと入力費用が増え、ある程度までは回答品質が改善するが、5片を超えると冗長な情報によってJudgeが低下する場合がある。検索量を増やせば必ず精度が上がるという単調な関係ではない。

## 既存研究との差

MemoryBank、MemoryOS、LightMemなどの既存方式は、履歴から記憶を事前に作り、質問時にはその記憶を検索・利用する設計を重視する。BudgetMemは元の履歴を残したまま質問時に必要な情報を抽出するため、質問に無関係な事前計算を避けられる反面、問い合わせ時の遅延が増えやすい。ReadAgentやA-MEMなどと比較した実験では、記憶構築の位置と処理費用を区別している。

単純なモデルルーティング研究は、質問を小型・大型モデルへ振り分けることが多い。BudgetMemでは回答生成モデルだけでなく、記憶抽出パイプラインの各段に対して予算を選ぶ。実装方式・推論挙動・モデル容量という異なる費用調整軸を、同じ入出力契約の下で比較できる点が中心的な貢献である。

推論基盤の視点では、ルータによるモデル切替そのものよりも、何を予算配分単位にするかが重要である。エンティティ抽出と時系列抽出で別の階層を選べるため、問い合わせの難しさを一つのスカラーに縮約する方式より細かな制御ができる。ただし複数モデルの常駐・呼び出しを実際のサーバでどう効率化するかは、提案の主評価対象ではない。

## 限界と適用条件

第一に、オンライン記憶抽出は複数の言語モデル呼び出しを必要とし、高品質優先設定では既存のオフライン方式より応答時間が長い。LoCoMoの3,461ミリ秒対1,662ミリ秒という容量階層の比較は、その実測上の制約を示す。API課金上の低費用が、GPU稼働時間や利用者が感じる遅延の低さを保証しない。

第二に、費用の定義はモデルごとの入力・出力トークン単価に依存する。単価の異なる提供者へ移す場合や、自前GPUの固定費を最適化する場合は報酬関数を再設計する必要がある。ルータはLLaMA基盤で学習され、Qwen基盤へ転移評価されたが、すべてのモデル・言語・データ分布で同じ性能を示す証拠ではない。

第三に、評価はLoCoMo、LongMemEval、HotpotQAの三集合を中心とし、検索上位5片、特定の分割長と固定パイプラインを使う。問い合わせによって必要な情報の構造が大きく異なる場合、固定のフィルタ→三抽出→要約という構成が最適とは限らない。検索件数を増やすと逆に品質が下がる例もあり、履歴のノイズと必要情報の取りこぼしを同時に管理しなければならない。

第四に、ルータ学習には最終回答の品質報酬が必要であり、報酬尺度を整合しないと低費用一辺倒へ崩壊する。回答判定モデルの誤差や価格設定の変動は、ルータ方策の学習と運用に影響する。原著はルータGPU時間を測っているが、複数モデルの同時常駐メモリ、切替時のモデルロード費用、同時多数要求時の全体処理量などは主要な定量評価ではない。
