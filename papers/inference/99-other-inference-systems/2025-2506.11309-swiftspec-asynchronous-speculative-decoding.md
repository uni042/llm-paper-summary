# SwiftSpec: Ultra-Low Latency LLM Decoding by Scaling Asynchronous Speculative Decoding

> SwiftSpecは、投機的decode（speculative decoding）の小型下書きモデル（draft model）と大型対象モデル（target model）を**同じGPU群で交互に動かすのをやめ、別々のGPU群へ分けて同時実行する**。draft側は次に検証してほしい候補tokenをtreeとして伸ばし続け、target側は前の候補treeを並列検証する。非同期化すると「検証中に作った候補が外れて無駄になる」「draftとtargetのKV cacheがずれる」という問題が生じるため、検証済みprefixと未検証treeを分けたKV管理で再利用可能な枝を残す。さらに小batchで支配的になるGPU間同期とkernel launchを融合し、8×H800上でsingle-request decode latencyを下げる。

## 概要

投機的decodeでは、小さなdraft modelが複数の候補tokenを先に生成し、大きなtarget modelがそれらをまとめて検証する。候補が当たれば、target modelを1 tokenずつ実行するより少ないverification回数で複数tokenを確定できる。

一方、大modelのsingle-request latencyをさらに下げるにはtensor並列（tensor parallelism; TP）も使いたくなる。1つのmodel weightを複数GPUへ分け、1回のforward passを協調して計算する方式である。

しかし、従来の投機的decodeとTPを単純に組み合わせると3つの問題が起きる。

1. **draftとtargetが直列依存する。** draftが候補を作り終わるまでtargetは検証を始められず、target検証中は次のdraft生成も待つ。
2. **draftとtargetで最適GPU数が違う。** 70B targetには4〜6 GPUが有効でも、1〜3B draftは2 GPUより増やしても速くならないことがある。それでも同じGPU群で交互実行すると全GPUを両方へ割り当てがちで、draft時にGPUが無駄になる。
3. **low-batch TPでは通信・同期の固定overheadが支配的になる。** single-request向けの小さなmatrixやattentionではGPUの演算器・NVLink帯域を使い切る前にkernel launchやbarrierのcostが効く。

SwiftSpecはこの3つを、それぞれ

- 並列tree生成（parallel tree generation）
- tree対応KV cache整合管理
- low-latency融合kernel

で解く。

## まず通常の投機的decodeがなぜ直列になるのか

一般的なsequence型投機的decodeは、

`draftで候補token列を作る → targetでまとめて検証 → 確定結果をdraftへ返す → 次の候補列を作る`

という順序になる。

draftは「どこまで候補がtargetに受理されたか」を知ってから次の候補列を作るので、draftとtargetは同時に仕事をしにくい。

tree型では候補を1本のchainではなく複数分岐へ広げられるため、targetが次に選ぶtokenが多少ずれても候補treeの別branchが当たる可能性がある。SwiftSpecはこの余裕を利用して、**targetの返事を待たずdraft treeを先に伸ばす**。

## 問題1: 同じ8 GPUをdraftとtargetで共有すると資源が合わない

例えば8 GPU nodeで70B targetと3B draftを使うとする。

70B modelはTPを4 GPUからさらに増やすことでforward latencyが下がる可能性がある。しかし3B modelは2 GPU程度で十分で、それ以上に分割するとall-reduce通信や同期costの方が増え、ほとんど速くならない場合がある。

従来方式で両modelを8 GPUすべてへ載せて交互実行すると、draft phaseでは「8 GPUを使っているのに2 GPU分程度の仕事しか得していない」状態になる。

SwiftSpecはGPUを、

- draft専用GPU群
- target専用GPU群

へ分ける。例えばQwen2-72B + Qwen2-1.5Bでは、評価上の有力構成として**target 6 GPU / draft 2 GPU**を使える。

これにより各modelへ別々のTP degreeを選べるだけでなく、2群を同時に動かせる。

## 手法のあらまし

1 iterationでdraft側とtarget側は並行して走る。

- target workerは、前iterationでdraftから受け取った候補treeの一部をbatchとして検証する。
- 同じ時間にdraft workerは、まだ検証されていない高確率leafからtreeをさらに伸ばす。
- targetの検証結果が届くと、draft workerは実際に確定したtoken pathへtreeを再rootする。
- そのpathの下にすでに作っていた候補branchが残っていれば、KV cacheも含めて再利用する。
- 不正解になったbranchだけを捨て、次に検証する高確率node集合をtargetへ送る。

つまり、従来の

`draft → target → draft → target`

を、

`draft(次候補) || target(前候補の検証)`

へ変える。

ただし非同期化するとdraftはtargetの最新結果を知らずに先走るため、無駄なbranchを作る。SwiftSpecは「多少の無駄を許してでも待ち時間を消す」設計で、その無駄をtree選択とKV再利用で小さくする。

## 手法

### 1. Parallel Tree Generation — draftとtargetを別GPU群で同時に動かす

SwiftSpecのdraft workerは候補を単純な1本のsequenceではなくtreeとして保持する。

各nodeにはdraft modelがそのtokenへ与えた確率を反映したscoreがあり、rootからnodeまでのlog probabilityの和をweightとして使う。priority queueから確率の高い未展開leafを選び、そこから候補childを増やす。

1 iterationでdraft workerは、複数leafをbatch化して`d`回tree expansionする。その間、target workerは前に受け取った候補node群を1回のbatch inferenceで検証する。

この`d`を適当に固定すると、一方が早く終わって待つ。そこで事前profilingにより、

`target 1回の時間 / draft tree expansion 1回の時間`

の比を測り、その比に近い整数回だけdraftを展開する。狙いはdraft expansionとtarget verificationがほぼ同時に終わることである。

### 2. treeの幅とtarget batchを独立に扱う

論文ではdraft側で1回に展開するleaf数を`w`、targetが一度に検証する候補node数を`bs`として分ける。

候補数を増やせばtargetが正しいpathを含む確率は上がるが、draft/targetそれぞれのbatch inference時間も増える。評価では主に`w=8`、`bs=8`を使い、受理token増加とsingle-step latencyのbalanceを取る。

これはproduction servingで8 requestをbatchするという意味ではなく、**1 request内のspeculative candidateをまとめて処理するbatch**として理解するのが重要である。

### 3. 最大尤度に近いleafを優先して無駄な非同期計算を減らす

非同期draftはtargetの検証結果を待たずにtreeを伸ばす。そのため、targetが最終的に選ばないbranchへ計算を使う可能性が必ずある。

SwiftSpecはrootからの累積log probabilityが大きいleafをpriority queueで優先する。targetが選びそうなpath周辺へ計算を集中させることで、先走って作ったtreeのうち後で再利用できる割合を高める。

それでも同期方式より候補の有効率は下がる。Qwen2評価ではparallel tree generationにより、1 verificationで成功する推測token数を表すcompression ratioはserial版より平均約9%低下した。それでも待ち時間削減とGPU配分効率の方が大きく、end-to-endは速くなった。

### 4. KV cacheを「verified prefix」と「draft tree」に分ける

非同期tree speculationで難しいのは、token文字列だけでなくKV cacheもbranchごとに分岐することである。

SwiftSpecはdraft modelのKV cacheを常に2領域として整理する。

1. **prefix cache**: targetがすでに検証し確定したtokenのKV。先頭から連続配置する。
2. **tree cache**: まだ確定していないdraft tree nodeのKV。prefixの直後に置く。

このlayoutをinvariantとして維持する。

### 5. 検証結果が返ったらtreeを再rootし、有効subtreeだけ残す

targetから「今回確定したtoken列」が返ると、draft workerは現在のtreeをそのtoken pathに沿って辿る。

最後に確定したtokenが既存tree内にあれば、そのnodeを新しいrootとして考える。そこより下のsubtreeは、次のtoken候補としてまだ使える。

そのため、

- 新たに確定したnodeのKVをprefix cacheへ移す。
- 新rootの子孫にあたるtree KVを前方へ詰めて残す。
- 新rootと無関係になったbranchのKVだけを破棄する。

こうすると、targetの予測と完全一致しなかった場合でも、**正しいpathの下で先に計算していた候補KVは再計算せず利用できる**。

PipeInfer型の単純な先行tree生成では、早い段階のtreeがinvalidになると後続treeまでまとめて捨てる場合がある。SwiftSpecのKV管理は、この連鎖的なwasteを減らすための仕組みである。

### 6. 任意のTP degreeを使えるようpaddingする

「target 6 GPU / draft 2 GPU」のような配分は、model architectureによってそのままでは使えないことがある。

Transformerのmatrix dimensionやattention head数は、TPで割るGPU数で割り切れる必要がある。Llama系は2/4/8 GPUのような2冪では都合が良いが、6 GPUだとdimensionやhead数が割り切れない場合がある。

SwiftSpecはmatrix dimensionとattention head数をzero paddingして6分割などを可能にし、padding部分が最終出力へ寄与しないようprojectionも調整する。

これによりdraft/targetのGPU配分探索をpower-of-twoに限定せず、8 GPU nodeを6+2など細かく使える。

## Low-batch kernel optimization

### なぜ通常の高throughput kernelが遅いのか

single-request ultra-low latencyでは、candidate batchが小さい。大batch向けGPU kernelは大量の仕事を流したとき高throughputを出すが、小さなworkloadでは固定costが目立つ。

論文がLlama 70B、TP=4、batch size 8でprofilingした例では、all-reduceとattentionのbandwidth utilizationが10%未満である。データ量そのものが小さく、帯域を使い切る前に同期・最初のdata arrival・kernel launchが支配するためである。

SwiftSpecはこの領域専用に、複数処理を1 kernelへまとめる融合（fusion）と、明示的barrierを減らす通信を使う。

### 7. GEMMとall-reduceを融合する

TPでは各GPUがmatrix multiplicationの一部を計算した後、all-reduceで結果を集約する。通常はGEMM kernelが終わってから別のall-reduce kernelを起動するため、kernel境界と同期が入る。

SwiftSpecはGEMM計算とone-shot all-reduceを同じ処理へ融合し、計算済みtileから通信を早く始められるようにする。

小modelやattention projectionのようにcompute量が小さい部分ほど固定通信costが大きいため、このfusionの効果が大きい。

### 8. NCCL Low Latency protocolを使い明示的同期を減らす

NVIDIA集合通信library（NCCL）の低遅延protocolでは、dataとflagを組にして書き込み、受信側は期待flagが見えるまでpollする。

SwiftSpecはこの仕組みをkernel内部の軽量なproducer-consumer同期として利用する。別kernelでglobal synchronizationを挟む代わりに、必要なdata blockが届いたことをflagで検知して次計算へ進める。

### 9. tree attentionを1 kernel内で集約する

tree speculationでは各leafが自分のancestorだけへattentionするため、通常のsquare causal maskより複雑な非正方maskが必要になる。

SwiftSpecはこのmaskを直接扱えるattention kernelを実装する。またhead内で分割したpartial attention結果の集約も同kernel内へ入れ、FlashAttention系で必要になる場合がある追加combine kernelを省く。

microbenchmarkでは代表context length 500/1000で、このattention kernelは比較したFlashAttentionより30〜56%短いruntimeを示した条件がある。

### 10. SwiGLUもdata movementをまとめる

MLP内のSwiGLUでは2本のmatrix multiplication、activation、要素積が続く。SwiftSpecは同じinput tileを再読込せず、matrix結果からactivation・積まで同じkernel内で処理する。

ただしこの最適化は万能ではない。1B/3Bのような小modelでは39〜50%のkernel time削減を報告する一方、70BではvLLM/TensorRT-LLM側のより成熟したAWQ kernelが速い条件もある。論文自身もこの点を示している。

### 11. CUDA Graphでlaunch overheadを減らす

forward passのkernel列をCUDA Graphへcaptureし、毎iterationで多数kernelをCPUから個別launchするoverheadを削る。

tree maskはshapeが変化するが、固定大shapeへpaddingしてsuffixへ実maskを配置することで、1000種類以上のtree shapeに対して20未満程度のCUDA Graph captureで対応できるようにしている。

## 1 iterationのデータと制御の流れ

| Component | iteration中の仕事 | iteration終了時 |
|---|---|---|
| Draft GPU群 | 高確率leafを選び、treeを`d`回展開 | targetのverified tokensを受信 |
| Target GPU群 | 前回受け取った候補subgraphをbatch検証 | 確定token列をdraftへ返す |
| Draft tree | targetを待たず候補を追加 | verified pathへ再root |
| Prefix KV | 確定tokenのみ保持 | 新たに確定したKVを末尾へ追加 |
| Tree KV | 未検証candidateのKVを保持 | 新root配下だけcompactして再利用 |
| Scheduler | draft/targetを並列進行 | 次に送る高確率node群を選択 |

## なぜ非同期化が速いのか

非同期化するとdraftの予測効率そのものは少し悪化する。targetの最新回答を知らずに先へ進むため、外れbranchを計算するからである。

しかし従来は、

- draft中はtarget GPUの能力が十分使われない
- target中はdraftが止まる
- 小さいdraftへ過剰なTP GPUを割り当てる

という大きなidle/wasteがある。

SwiftSpecは少し余計なdraft計算を許す代わりに、2 modelを同時に走らせ、各modelへ必要なGPU数だけ割り当てる。

Qwen2-72B + Qwen2-1.5Bの例では、serial版は8 GPUを両modelへ使うのに対し、parallel版はtarget 6 GPU / draft 2 GPUとする。draft inferenceは約3.72 msから3.25 msへ短縮し、targetは10.34 msから10.48 msとほぼ維持した。候補compression ratioは平均9%ほど悪化しても、end-to-end decodeは**200 tokens/sから275 tokens/sへ37%向上**した。

## 評価

### Hardware / model

主要評価は1 node、**8× NVIDIA H800 SXM 80GB、NVLink接続**で行う。

対象model pairには、

- Llama-3-70B-Instruct + Llama-3.2-3B / EAGLE
- DeepSeek-Coder-33B + 1.3B
- Qwen2-72B + Qwen2-1.5B / EAGLE
- DeepSeek-R1-Distill-Qwen-32B + 1.5B
- DeepSeek-R1-Distill-Llama-70B + 8B

を含む。

Transformer weightは原則4-bit AWQ、group size 128。embeddingとLM headはBF16、attentionとlinear計算もdequantization後BF16で行う。

### Dataset

6 datasetを使い、chat・coding・math・summarization・QAなど異なる出力分布を含める。

- MT-Bench
- HumanEval
- GSM8K
- Alpaca
- CNN/Daily Mail
- Natural Questions

### Baselineの読み方

比較にはvLLM、SGLang、TensorRT-LLMを含むが、2025年当時の各frameworkで利用できるspeculation機能が揃っていない。

- vLLM: sequence型speculation中心
- TensorRT-LLM: 評価条件のINT4 AWQではsequence型small draft中心
- SGLang: EAGLE tree speculationを利用可能だが、評価した5 familyすべてに対応EAGLE modelがあるわけではない

そのため論文は、自分たちのkernelを使いつつ**parallel tree generationだけを外したSwiftSpec-base**も用意する。small draft tree speculation同士でparallelizationの効果を見るには、これが比較的重要なbaselineである。

### End-to-end結果

5 model family・6 dataset全体で、SwiftSpecは最も直接的な内部baselineであるSwiftSpec-baseに対し**平均1.75×**のdecode speedを報告する。

SGLangとの集計では平均**2.23×**だが、EAGLE draftがない3 familyではSGLang側が通常autoregressive decodingになるため、1.75×より比較条件の非対称性が大きい値として読むべきである。

highlightとしてLlama-3-70Bを8×H800で**平均348 tokens/s**でdecodeしたと報告する。

### Parallel tree generation単体の寄与

parallel tree + KV consistencyを有効にすると、kernel optimizationを共通にした比較で平均**1.43×**、別の比較で約**1.50×**のspeedupを報告する。

これは「候補が当たりやすくなった」ためではない。むしろ非同期化でcompression ratioは少し下がる。その代わり、draft-target serializationと過剰GPU allocationを減らす効果が上回る。

### Kernel optimizationの寄与

parallel treeの有無それぞれで、融合GEMM-all-reduceとSwiGLUなどのkernel optimizationはend-to-endを少なくとも**約16%**改善した評価になっている。

Llama 3B、TP=4、input token length 8、context length 500の例では、optimized kernelを使うforwardが3.25 ms、FlashAttentionベース条件が3.54 msで、model inference全体では8.2%削減している。

## 既存研究との差

### 通常のtree speculative decodingとの違い

SpecInferやEAGLEなど多くのtree speculationは、draft treeを作ってからtargetが検証する同期構造が基本である。SwiftSpecはtreeを使うだけでなく、**draft tree生成とtarget検証を別worker/GPU群へ分離してoverlapする**ことが中心である。

### PipeInferとの違い

PipeInferも非同期speculationを狙うが、先行して作ったtreeがinvalidになると後続候補まで破棄されるwasteが問題になり得る。

SwiftSpecは1つの継続treeをverified pathへ再rootし、まだ有効なsubtreeとそのKVを残すことで再利用率を高める。

### PEARL / sequence型async speculationとの違い

sequenceだけならKV cache整合は比較的単純だが、候補分岐がないので1 verificationで確定できるtoken数に限界がある。SwiftSpecはtree候補を維持しながら非同期化するため、その代わり複雑なKV管理を追加している。

### Prefill/decode disaggregationとの関係

DistServe系の分離型servingはprefillとdecodeを別GPUへ分ける。SwiftSpecは同じ思想を**decode内部のdraftとverification**へ適用したものと見なせる。prefill高速化とは直交しており、組み合わせ可能である。

## 一般的な実装への示唆

SwiftSpecから得られる大きな示唆は、異なるmodel componentを「同じGPU数で速くする」必要はないという点である。

1つのrequest pipelineに大小modelや複数stageがある場合、各stageの最適parallelism degreeが違うなら、

- stageごとにresource poolを分離する
- producer/consumerを非同期化する
- correctness boundaryでstateを再同期する
- speculative stateのうち再利用可能部分だけ残す

という設計が有効になり得る。

またultra-low-latency領域では、理論FLOPsやpeak bandwidthより、kernel launch・barrier・小message collectiveの固定costが支配しやすい。high-throughput向けkernelをそのまま流用するより、operation融合やfine-grained synchronizationが重要になる。

## 限界・注意点

- 主眼はsingle-request / low-batch ultra-low latencyであり、batch size 64以上のhigh-throughput serving向けkernelとしては設計されていない。
- 8×H800の高速NVLink nodeを前提とした評価であり、PCIe-onlyやmulti-node interconnectではdraft-target通信と最適GPU配分が変わる。
- independentなsmall draft modelに特に適する。EAGLEはverified target outputへより強く依存するため、draft-target dependencyを切るのが難しく、SwiftSpecの非同期方式をそのまま適用できない。
- parallel speculationはtarget結果を待たずに計算するため、serial treeより無駄なcandidateが必ず増え得る。評価ではcompression ratioが平均約9%低下した例がある。
- 4-bit AWQと独自CUDA kernelに深く最適化されたsystemなので、別precisionや別GPU世代ではkernel部分の優位性を再測定する必要がある。
- baseline framework間で利用可能なspeculative decoding機能が揃っていないため、SGLang/vLLM/TensorRT-LLMとの平均倍率は完全な同機能比較ではない。SwiftSpec-base比較の方がparallelization自体の寄与を読みやすい。
- 論文自身が示すように、70B SwiGLUなど一部operatorでは既存frameworkの成熟kernelがSwiftSpec実装より速い条件もある。
- workloadが重くなり高throughput優先になると、speculative decoding自体より通常autoregressive large-batch decodingの方がcost-efficientになる場合があり、その領域ではSwiftSpecの利点も小さくなる。
