# JANUS: Disaggregating Attention and Experts for Scalable MoE Inference

## 概要

JANUSは、専門家混合（Mixture-of-Experts、MoE）モデルのオンライン推論を、**注意機構と専門家層を別々のGPU群へ配置して独立に伸縮する**システムである。一般的なMoEサービングでは、注意層と専門家層が同じGPU集合・並列度を共有する。しかし注意層はKVキャッシュとバッチ規模に影響されるのに対し、専門家層は大量の重みを常駐させ、実際に起動する専門家の数で遅延が決まりやすい。両者に同じ台数を割り当てると、負荷が変動した際に片側のGPUが過剰になる。

JANUSは注意機構の実行群と専門家層の実行群を分離し、各群を別々に増減する。分離によって生じるノード間通信の増加は、ノード内で活性値を集めてから大きな塊で送る適応二段通信で緩和する。専門家層では、各GPUが処理するトークン数ではなく、**異なる起動専門家の数**を均等化する軽量スケジューラを実行する。さらに、出力トークン当たり時間（Time per Output Token、TPOT）のサービス水準目標を満たす範囲で、注意側と専門家側の台数、専門家複製配置を調整する。

SGLangを拡張した実装を最大4ノード・32基のH100で評価し、DeepSeek-V2、Qwen3-MoEなどでGPU当たり処理量をSGLang比最大4.7倍、MegaScale-Infer比最大2.2倍、xDeepServe比最大3.3倍改善したと報告する。これらは比較対象と負荷条件が異なる最大値であり、同一条件で一律に4.7倍速くなることを意味しない。24時間の負荷追跡によるシミュレーションでは、必要GPU時間をSGLang比39%削減する。

## 問題設定：二種類の層に異なる資源が必要

MoEモデルでは、注意層は全トークンに必要な一方、フィードフォワード部分ではルータが各トークンにつき一部の専門家だけを起動する。演算する専門家は少なくても、モデル全体の重み容量の大半を専門家が占める。論文の表1ではQwen3-235Bの専門家重みが約423GBで全体438GBの96.5%、DeepSeek-V2では約421GBで全体472GBの89.2%を占める。DeepSeek-V3/R1では専門家重み約1258GBで全体1342GBの93.7%となる。単一のモデル複製を増やす方式では、増設のたびに巨大な専門家重みをまとめて配置する必要がある。

著者らはDeepSeek-V2の注意層と専門家層をH100で測定し、バッチ16・64では注意側の並列度を増やしても遅延があまり下がらず、バッチ512で初めて効果が大きくなることを示す。一方、専門家層は比較的小さいバッチでも並列度の増加から利益を得る。専門家層の演算強度は、専門家当たりの処理トークン数にほぼ比例し、オンラインの小バッチでは計算能力より重み読み出し帯域が律速となる。

さらに、専門家層の遅延は処理トークンの総数よりも、GPUごとに何種類の専門家を起動したかで決まる。論文は同じバッチ64でも起動専門家の種類を増やすと遅延がほぼ線形に増えることを示す。専門家のトークン数だけを均等化しても、あるGPUに多種類の専門家が集まれば、そのGPUが最遅の処理器になる。各GPU gに割り当てた起動専門家数を `a_g` とすると、層の律速は `a_max=max_g a_g` で表される。

実サービスの要求到着は一定ではない。論文の一週間の本番負荷ではピークが平均の約7.5倍に達する。ピークに合わせてフルモデルを大量複製すれば低負荷時にGPUが余り、平均負荷に合わせればTPOTの目標を破る。JANUSは注意側・専門家側を独立に伸縮し、かつ専門家の実際の起動数を均すことで、GPU台数と遅延目標の両方を最適化する。

## 手法：分離、通信、専門家割当、資源制御

### 注意側と専門家側を別GPUプールにする

注意側の各GPUは注意層の重み複製とKVキャッシュを保持し、要求のバッチ化と注意計算を担当する。専門家側の各GPUは専門家の一部の複製を常駐させ、注意側から受け取った活性値に対してMoE計算を行う。各側には独立の管理器があり、注意側のインスタンス数 `n_a` と専門家側のインスタンス数 `n_e` を別々に変更できる。共有専門家は注意側に配置し、ノード間転送待ちと重ねて計算する。

分離の代償は、各MoE層で注意側のm個のインスタンスと専門家側のn個のインスタンスが活性値と結果を交換することである。素朴に全対全で送れば通信回数がm×nに比例し、小さな転送が多数発生する。そこでJANUSは、総送信バイト数を少し増やしても、**小さなノード間転送の回数を減らす**ことを優先する。

### 適応二段通信：ノード内集約とノード間大塊転送

JANUSはルータのゲート計算を専門家側へ置く。注意側で専門家を選んで必要なトークンだけ送れば総データ量は減るが、宛先別の細かい並べ替え、専門家番号などのメタデータ、細切れの送信が増える。通信が小転送の起動費用で律速される環境では、活性値をまとめて送って専門家側でゲート処理した方が速い。

二段通信の第1段階では、同一ノード内の注意インスタンスの活性値をNVLinkで集約する。第2段階で大きくまとめた活性値を専門家側ノードへ送る。宛先が少ないときは必要なノードへ直接送信し、宛先が多いときは注意ノードと専門家ノードを一対一に対応させて転送し、受信ノード内でNVLinkのマルチキャストを使って配布する。専門家側から注意側への結果も、ノード内全削減で集約してから戻す。

実装ではNVSHMEMの一方向書込みと通知を使い、GPUDirect RDMAでGPUメモリへ直接データを送る。層番号やトークン数などの小さなメタデータを通知値へ埋め込み、別の通信を減らす。これにより、注意・専門家の台数比が変わっても通信群を固定的な対称形にする必要がない。通信の総バイト数を減らすだけの最適化とは異なり、メッセージの粒度と起動回数に着目する。

### 起動専門家均衡スケジューラ（AEBS）

各MoE層のゲート処理がバッチ中のトークンごとに上位k個の論理専門家番号を返すと、JANUSはバッチ全体で実際に選ばれた専門家の集合を作る。次に専門家ごとの複製配置を参照し、複製が一つしかない専門家はそのGPUへ固定割当する。複数複製がある専門家は、複製を保持するGPUのうち**現在割り当てた起動専門家の種類数が最小**のGPUへ割り当てる。割当後にGPUの負荷計数器を一つ増やす。

最後に各トークンの論理専門家番号を選ばれた物理複製番号へ書き換え、活性値を担当GPUへ配送する。これはトークン数を均すのではなく、異なる重みを読み込む回数を均す近似解法である。最適割当を厳密に解くと組合せ探索が重すぎるため、貪欲な選択を使う。複製が少ないと自由度も小さく、全専門家を均等化できるわけではない。

AEBSはCPUで中央集権的に計算するのではなく、各専門家GPUが同じルーティング結果と複製配置を入力にして、**同じ決定的な割当を独立に計算する**。各GPUが同じ答えを得るので、毎層の割当についてGPU間同期を行う必要がない。重複計算の費用はあるが、GPUカーネルで実行することで数十マイクロ秒規模に抑え、層ごとに数百マイクロ秒のMoE処理へ適用できる。専門家配置の変更は毎トークンではなく低頻度に行い、そのときだけ配置情報を配布する。

### TPOT制約を満たす最小GPU構成の探索

JANUSは要求到着率λと目標TPOTを受け取り、注意側台数 `n_a`、専門家側台数 `n_e`、定常バッチ `B*` を選ぶ。予測TPOTは各層の注意時間、専門家時間、通信時間の和で表す。注意時間は小負荷でのメモリ帯域律速の下限と、バッチおよびKV長に依存する計算費用の最大値で近似する。専門家時間は、AEBSを使ったときの `a_max` にほぼ比例する項と固定費用で表す。通信時間は二段通信の事前測定値から推定する。

定常バッチは外から固定する値ではなく、リトルの法則から `B*=λ×TPOT(B*,n_a,n_e,S_ctx)` を満たす必要がある。候補台数ごとにバッチを二分探索し、GPUメモリ制約とTPOT目標を満たすか判定する。専門家側では全専門家複製を置けるだけのスロット数、注意側ではKVと活性値を含むメモリ上限を課す。実行可能な候補のうち `n_a+n_e` が最小の構成を採用する。

専門家の起動数 `a_max` は入力分布に依存するため、直近のルーティング履歴からモンテカルロ標本を作り、各候補台数・バッチでAEBSを模擬して表を更新する。配置変更では、同時に選ばれやすい専門家が同じGPUへ集中しないよう、複製を配置する。負荷が変わればこの二次元探索を再実行し、注意側または専門家側を段階的に増減する。推定が外れた場合はSLO違反の危険が残るため、事前測定と最近の起動統計の正確性が重要である。

## 評価：SLO、GPU当たり処理量、構成要素の効果

### 実験条件

| 項目 | 論文の条件 |
|---|---|
| クラスタ | 最大4ノード、各ノードH100 80GB×8、CPU128コア、ホストメモリ2TB |
| 通信 | GPUごと400Gbps InfiniBand NIC、ノード内900GB/s NVLink |
| モデル | DeepSeek-V2、Qwen3-MoE、Scaled-DS-1/2 |
| 精度 | モデル重み・KVともBF16 |
| 負荷 | ShareGPT由来の平均入力16トークン・平均出力256トークン、BurstGPT由来の動的到着 |
| 比較対象 | モノリシックSGLang、MegaScale-Inferの再実装、xDeepServeの再実装 |
| 指標 | TPOT、GPU当たり出力トークン数、SLO達成、GPU時間、専門家起動数、通信内訳 |

MegaScale-InferとxDeepServeの比較は著者らがJANUSのコード基盤へ移植・再実装したものであり、元の独立実装をそのまま走らせた値ではない。これらの比較条件は再現性を判断する際に重要である。主な対象は**デコード中心のサービング**で、重いプリフィルを含むあらゆる推論サービスの総合性能を測ったわけではない。

### GPU当たり処理量と遅延目標

図8はDeepSeek-V2のTPOT目標200ミリ秒・150ミリ秒、Qwen3-MoEの200ミリ秒を比較する。JANUSは評価したバッチ範囲で目標を満たす一方、MegaScale-InferとxDeepServeはDeepSeek-V2のバッチ512・目標150ミリ秒、バッチ1024・目標200ミリ秒などで違反する。SGLangもQwen3-MoEのバッチ1024で違反する条件がある。

GPU当たり処理量の最大改善はSGLang比4.7倍、MegaScale-Infer比2.2倍、xDeepServe比3.3倍である。低負荷では1A6E（注意GPU1基、専門家GPU6基）のように非対称な構成を選び、注意側の過剰配置を避ける。負荷が増えれば注意側を増やし、厳しいTPOT目標では専門家側も増やして `a_max` を下げる。改善は演算カーネル単体の高速化というより、資源配分と専門家配置を負荷に合わせることで生じる。

### SLOを変えた場合の交換条件

図9ではバッチ64の1A6E構成が評価した各SLOを満たし、GPU当たり約99トークン/秒となる。バッチ256では、厳しいSLO向けの5A10Eから緩いSLO向けの2A6Eへ切り替えると、GPU当たり処理量は約170から240トークン/秒へ増える。バッチ512では最も厳しいSLOが達成不能であり、緩い条件では4A6Eが約340トークン/秒を達成する。**SLOを緩めるとGPU当たり効率が上がる**という結果であり、すべての遅延目標を常に満たす万能な伸縮方式ではない。

### 実負荷追跡と構成要素除去

24時間の実負荷追跡に対する図11は、実測した各構成の性能を使った**追跡駆動シミュレーション**である。15分ごとに構成を変更し、JANUSは7〜56GPUで負荷に追随する。SGLangは16/32/64GPU単位の粗い構成を使うため、低負荷で過剰配置となる。GPU時間はSGLang比39%、MegaScale-Infer比16%削減したと報告する。24時間にわたり全方式を実クラスタで連続稼働させた直接測定ではない点を区別する。

図12の構成要素除去では、二段通信を使わず専門家側でゲートを行うと、小さなノード間転送が増え、バッチ256と512のTPOTが185ミリ秒、350ミリ秒へ悪化する。処理量は完全なJANUSの44%、30%まで下がる。二段通信を加えると、注意側でゲートする構成より専門家側ゲートで4〜34%の処理量改善が得られ、さらにAEBSを加えると11〜15%上積みする。通信のまとめ方、ゲート位置、専門家起動数の均衡は単独ではなく組合せで効果を発揮する。

AEBSのスケジューリング費用は小バッチで20マイクロ秒未満、バッチ4096でも90マイクロ秒未満である。専門家側GPUを8から16へ増やすと複製配置の自由度が増え、専門家起動数の偏りをより抑えられる。Scaled-DS-2では専門家側8基だと複製余裕が乏しく効果が限定されるが、16基へ増やすとTPOTを41〜50%削減する。ここでも単にGPUを増やせばよいのではなく、複製余裕と割当の自由度が効果を左右する。

## 限界と適用条件

JANUSはGPU群を注意側と専門家側に分離するため、**各MoE層でノード間通信が必ず発生する**。NVLink、400Gbps InfiniBand、GPUDirect RDMA、NVSHMEMなどの高速通信を前提とした評価であり、遅いネットワークでは二段集約しても通信費用が利得を上回り得る。特に小バッチで送信が細かくなると、通信の起動費用が重要経路へ現れる。

専門家起動数を均すAEBSは、同じ専門家を複数GPUへ配置する余裕がなければ割当先を選べない。全専門家が一か所にしかない構成や、頻繁に同時起動する専門家が同じGPUへ集中する構成では効果が小さい。ルーティング分布の急変で事前の複製配置が不適切になると、配置変更のための転送・同期が発生する。各GPUが同じ決定的スケジューラを独立に実行するため、配置メタデータが食い違えば正しさに影響する。

TPOT予測は直近の専門家起動統計、KV長、負荷到着率、事前測定した通信費用に依存する。リトルの法則による定常バッチの近似が成立しない急激な負荷変化では、選んだ台数が過不足となる可能性がある。最も厳しいSLOが達成不能なバッチ512の例が示すとおり、制約を満たす構成が常に存在するわけではない。

論文の中心はデコード中心のオンラインサービングであり、長いプリフィルを大量に含むサービス、学習処理、一般的な単一GPUローカル推論は直接の対象ではない。H100最大32基という規模での資源効率改善を、家庭用GPUや少数GPUのCPUオフロードへ外挿できない。比較したMegaScale-InferとxDeepServeは著者実装であり、実装差が比較結果へ影響する可能性がある。実負荷のGPU時間削減は追跡駆動シミュレーションであることも留保する。

## 位置づけと結論

既存のフルモデル複製方式は注意と専門家に同じ資源構成を強制し、単に注意と専門家を分離する方式も、専門家起動数の偏りと細粒度の資源伸縮を十分に扱わない。JANUSは**分離した後に生じる通信、最遅専門家GPU、SLOに応じた台数選択を一体で最適化する**。通信回数を減らす二段集約、GPU上で同期不要の起動専門家均衡、負荷予測に基づく二次元のGPU台数探索が組み合わさることで、巨大MoEのデコードを高いGPU利用効率で実行する。主な価値は一つのカーネルの速度ではなく、動的負荷の下で必要なGPU台数を削減する推論基盤設計にある。
