# Bounded-State Restoration: Decoupling Local Restore Capacity from External LLM State

> 外部KV状態の全ヒットを先に把握しつつ、復元はWチャンク窓だけを順次ステージングして解放することで、長大な外部状態とローカル復元メモリを分離する方式。
## 書誌情報
- **著者**: Zixuan Li
- **著者・所属**: China Academy of Railway Sciences Corporation Limited, Beijing, China
- **公開**: arXiv
- **種別**: Preprint
- **対象**: KV キャッシュ restoration、hierarchical メモリ、bounded staging、LMCache、vLLM
- **実装**: LMCacheへprobe_only、プリフェッチ_window_chunks、窓取得・解放、失敗ブロック無効化を追加し、vLLMへ異種メモリ割当対応の全プレフィックス無効化とforce-local再試行を追加。
## 概要
階層KVキャッシュは長い会話状態をSSDや遠隔メモリへ保持できても、復元時に全ヒットをローカルへ一時展開すると外部状態サイズに比例した復元作業集合（Restoration Working Set; RWS）が必要になる。BSRは完全な再利用可能プレフィックスの発見と実データ常駐を分離し、まずプローブだけで全ヒットを確定、その後最大Wチャンクの再利用窓で順次取得・GPUへ導入・解放する。要求単位のコミット規則でTPランクや異種状態群の一部だけ成功した状態を公開せず、失敗時は下位階層または再計算へ戻す。DeepSeek-V4-Flashを2台のDGX Spark、TP=2で評価し、外部状態31.277 GiB/rankでもW=32のRWSを500.75 MiB/rankへ固定した。

BSRの中心は、外部ヒットの『知識』とそのバイト列の『ローカル常駐』を分離する三段階プロトコルである。まずプローブ専用検索で再利用可能な完全プレフィックスを確定するが、その全データをL1へ保持しない。次に確定した復元計画を最大Wチャンクの窓へ分割し、一窓だけを取得・完全性確認・GPU側宛先へ導入・同期・解放して同じステージング領域を次窓へ再利用する。補助状態が全計画長に比例しないならRWSはO(W)となり、外部状態|S|が増えても必要窓回数だけが増える。最後にTPランクと意味的状態群の全要素が有効な場合だけ要求単位で再利用をコミットし、一部失敗なら広告済みプレフィックス全体を無効化して下位階層か決定的再計算へ戻す。この『完全発見→有界導入→全体コミット』をLMCache/vLLMの実際の制御経路へ組み込んだ点が論文固有の貢献である。

代表結果として、fixed-W restoration working setはW=32, 32K to 524032 トークン, external state 1.956 to 31.277 GiB/rankでwhole-plan peak grows with selected stateに対して500.75 MiB/rank at all six sizes。外部状態を約16倍増やしても復元一時容量は固定され、最大外部状態/生存ステージング比63.959倍。
## 問題設定
長文LLMサービングでは、過去のKVキャッシュやモデル固有状態をGPU外のCPUメモリ、SSD、遠隔メモリへ保存すれば、同じ長いプレフィックスを再計算せずに再利用できる。しかし外部に保持できる容量と、その状態を再びGPU実行可能にする際に必要なローカル一時容量は別問題である。LMCacheの従来whole-plan経路では、再利用可能な全プレフィックスを発見すると、その選択状態をまとめてL1へ一時展開してから導入するため、32Kで1.956 GiB/rank、128Kで7.823 GiB/rank、256Kで15.646 GiB/rankの外部状態に対し、成功時L1ピークもほぼ同じ1.956、7.824、15.648 GiB/rankまで増えた。つまりSSDや遠隔メモリを増やして保持容量を拡大しても、復元時の一時ステージングがGPU/共有メモリを圧迫し、モデル重み・実行KV・同時要求に使える余白を奪う。単純に小分け取得するだけでは、スケジューラが完全な外部ヒットを知らないまま部分状態を有効扱いする危険があり、TPランクや異種状態群の一部だけ復元された場合の正しさも保証できない。論文はこの一時容量を復元作業集合RWSとして独立資源に切り出し、完全な再利用判断と限定されたローカル常駐を両立させる必要性を定式化する。
## 新規性

## 手法
### 手法のあらまし
入力は、外部階層に保存された再利用可能LLM実行状態S、LMCacheが登録した状態群、TPランク構成、復元窓上限Wである。第一段階のprobeでは通常のヒット探索を実行して完全な候補ヒット集合H(S)を求めるが、検索側のL1/L2読み取りロックと一時オブジェクトを解放し、スケジューラへはヒットbitmapだけを返す。これによりスケジューラは何トークン分を再利用できるかを全体として把握して宛先ブロックを確保できる一方、外部状態全体をローカルへ複製しない。第二段階のinstallでは確定した順序付き復元計画を最大Wチャンクずつの窓G_jへ分ける。各窓についてプリフェッチを発行し、必要キーが全て存在することを確認し、取得した状態を対応する宛先ブロックスライスへ転送し、GPUストリームを同期してから一時キーとL1ステージングを解放する。解放後に同じ領域を次窓へ再利用するため、同時に生存する復元単位数はW以下となる。現プロトタイプは専用ロックで有界復元を直列化し、複数要求が各自Wを消費して上限を破ることを防ぐ。第三段階のcommitでは、全TPランクrと全意味的状態群gについて有効性q_{r,g}を確認し、その論理積が1の場合だけ広告した完全プレフィックスを再利用済みとして公開する。窓欠損、タイムアウト、転送例外が起きると宛先ブロックをinvalidにし、異種メモリ割当ではどれか一群のinvalidを全プレフィックス無効へ畳み込む。さらにforce-local markerを置き、次のスケジューラ周回が同じ壊れた外部経路を即再試行せず、SSD等の下位有効階層かローカル再計算へ入るようにする。性能改善は容量契約と分離されており、SSD読み込み並列度を1から4へ上げてもWとRWSは変えず、同じ窓内のオブジェクト読み込みだけを並列化できる。

### プローブ専用の完全ヒット発見
スケジューラは外部状態を何トークン分再利用できるかを宛先割当前に知る必要があるが、従来経路はその知識を得る過程で全ヒットをL1へ物理的に保持していた。BSRのprobe_onlyは通常の検索と完全ヒット判定を行った後、L1/L2の読み取りロックと検索側ステージングを解放し、ヒットbitmapという小さな決定情報だけを返す。これにより完全な再利用範囲を先に確定できるため、後続のスケジューラは正しい宛先ブロック数を確保できる。一方で完全ヒットを構成するバイト列は同時常駐しないので、発見段階でRWSが外部状態サイズへ膨張しない。入力は外部キー集合と登録状態、出力は完全候補プレフィックスの知識であり、次の窓導入段階へ渡される。

### Wチャンク有界の窓導入
確定済み復元計画を順序付きの窓へ分割し、各窓の要素数をW以下に制限する。窓ごとに外部階層からプリフェッチし、全キー存在を確認し、対応するGPU宛先ブロックへ転送して同期した後、一時オブジェクトを解放する。次窓は前窓の解放後に同じステージング領域を再利用するため、同時生存量は最大Wチャンクとなる。理論上はRWS<=W*c_max+M_aux(W)で、全状態長Nが増えても窓回数ceil(N/W)が増えるだけでピーク容量は固定できる。評価構成では1チャンク当たり16,408,576 bytes/rankで、W=32なら500.75 MiB/rankとなる。これは総転送量を減らす手法ではなく、総仕事量Theta(|S|)を保ったままピーク一時容量を制御する手法である。

### 要求単位の失敗閉鎖コミット
DeepSeek-V4-Flashの状態は単一KV配列ではなく、MTP-offで167 tensors、MTP-onで170 tensors、複数のengine/カーネル groupと2 TP ranksにまたがる。このため一部窓の転送成功だけを『プレフィックス復元済み』として公開すると、要求の意味状態が不完全でもキャッシュヒットとして実行される危険がある。BSRは各rank・各groupの有効性を確認し、全てが有効な場合だけ完全プレフィックスをコミットする。欠損・タイムアウト・転送例外ではコピー済みを含む宛先ブロックをinvalidにし、異種メモリ割当では一群のinvalidを全広告プレフィックス0へ畳み込む。評価した遠隔障害・遠隔+SSD欠損・片rank障害では、完全な下位階層再利用か外部再利用0のどちらかだけが観測され、canonical output hashとTP healthを維持した。

### 障害後のforce-local回復と独立なI/O並列化
非同期復元が失敗した直後に通常の外部検索へ戻ると、同じ壊れた遠隔経路を繰り返して進行不能になる。そこでBSRは失敗要求へforce-local markerを設定し、次のadmissionでは外部再利用トークンを0として通常のローカルプリフィル経路へ戻す。下位のSSDが有効なら完全プレフィックスをそこから再利用し、なければ決定的に再計算する。markerは正常RUNNING admissionまたは要求終了後に外す。さらに容量契約と性能最適化を分けるため、ファイルシステム読み込み並列度を非同期semaphoreで独立制御する。読み込み先は同じ事前確保W窓なので、並列度を上げてもRWSは増えない。実験では並列度1→4で512K SSD復元TTFTを43.1→17.6秒へ短縮しつつ500.75 MiB/rankを維持した。

### 全体のデータ／制御の流れ
LMCache側へprobe_only、プリフェッチ_window_chunks、窓単位retrieve/release、失敗ブロック無効化を追加し、vLLM側へ異種メモリ割当を考慮した全プレフィックス無効化とforce-local markerを追加する。モデルカーネルや外部状態表現は変更しない。遠隔Mooncake/SSDからの保持、L1復元ステージング、GPU宛先状態を分け、復元容量だけをWで明示的に予算化する。
## 評価条件
- **ハードウェア**: DeepSeek-V4-Flashを2台のNVIDIA DGX SparkでTP=2実行。各rankから外部Mooncake storeへ100 Gb/s RDMA接続。Mooncakeは128 GiB segment、ローカルSSDも使用。
- **ソフトウェア**: LMCacheとvLLMの固定版へBSR制御経路を実装。LMCache chunk size 256 トークン。MTP-off 167 tensors、MTP-on 170 tensors。
- **比較対象**: pinned upstream LMCache whole-plan restoration、BSR W=8/16/32/64、SSD load concurrency 1 vs 4
まず従来whole-plan経路でW=0とし、32K/128K/256KプレフィックスについてL1容量を段階的に増やし、完全再利用が初めて成功する容量と実測L1ピークを測る。次に同一engine epoch・no-resumeのBSR sweepでW=32、L1=1 GiB、MTP-offを固定し、32768〜524032 トークンまで6点を測る。256KではW=8/16/32/64のRWS法則を確認する。524K MTP-onで異種状態を再検証し、遠隔障害、遠隔+SSD欠損、片rank障害の失敗閉鎖動作を確認する。512K SSDでは読み込み並列度1対4を比較する。成功条件は期待cached prefix、意図したtier counter、canonical output hash一致、登録状態geometry一致、両TP rank健全性。
外部KV/実行状態を保持する階層キャッシュから、長いプレフィックスをローカル実行状態へ復元する際の一時ステージング容量と安全性。
## 主要結果
従来whole-plan復元では外部状態1.956/7.823/15.646 GiB/rankに対し、完全再利用が初めて成功するL1 rungが2/8/16 GiBで、実測L1ピークも1.956/7.824/15.648 GiB/rankとほぼ全状態サイズに追随した。BSRではW=32のまま外部状態を1.956から31.277 GiB/rankへ約16倍増やしても、6点すべてのRWSが500.75 MiB/rankで一定だった。最大状態は生存ステージングの63.959倍。W sweepは理論式と0 byte残差で一致し、SSD並列化はRWSを変えずTTFTを2.45倍改善した。

- fixed-W restoration working set / 500.75 MiB/rank at all six sizes (比較対象: whole-plan peak grows with selected state; 条件: W=32, 32K to 524032 トークン, external state 1.956 to 31.277 GiB/rank) — 外部状態を約16倍増やしても復元一時容量は固定され、最大外部状態/生存ステージング比63.959倍。

- whole-plan first successful L1 rung / 2/8/16 GiB for 32K/128K/256K (比較対象: external state 1.956/7.823/15.646 GiB/rank; 条件: W=0 upstream path) — 従来経路の復元容量が選択状態全体へ比例することを実測。

- W-to-RWS law / 125.1875/250.375/500.75/1001.5 MiB/rank (比較対象: W=8/16/32/64 predicted by W*16,408,576 bytes/rank; 条件: 256K トークン) — 4点すべて理論式と0 byte残差で一致し、Wが明示的容量ノブとして働く。

- SSD restore TTFT / 43.1 s to 17.6 s (比較対象: filesystem load concurrency 1; 条件: concurrency 4, 512K, W=32) — 2.45倍高速化しながらRWSは両条件500.75 MiB/rankで不変。

- failure exposure / full prefix or zero external reuse (比較対象: partial exposure would violate リクエスト semantics; 条件: remote unavailable, remote+SSD absent, one-rank remote fault) — 評価した障害で部分復元状態を広告せず、canonical outputとTP=2 healthを維持。

### 負の結果・境界条件
- BSRは総転送量を減らさず、総仕事量はTheta(|S|)なので状態が長いほど復元遅延は増える。現プロトタイプは有界復元を専用ロックで直列化し、複数要求の並行復元を制限する。512Kの従来whole-plan 32 GiB点は実測しておらず推定を主比較へ使っていない。RWSはLMCache L1復元プールだけで、モデル重みや宛先KV、通信バッファを含む総プロセスメモリ一定を意味しない。

### 結果の読み方
外部保持容量を増やすだけでは復元時ピークは解決しない。完全ヒットを情報として先に確定し、データ自体は一窓ずつ導入・解放することで容量増加を反復回数増加へ置き換えられる。要求単位コミットがこの空間最適化をTP/異種状態でも安全にする。
## 品質への影響
生成品質そのものを変える方式ではなく、全成功条件でcold executionとcanonical output hash一致を要求する。障害時も不完全状態を使わず再利用0または下位完全再利用へ戻す。
## 既存研究との差
CachedAttention、Mooncake、LMCache、SYMPHONYは主に再利用状態をどこへ保持するか、どの階層へ配置するかを拡張する。HCache、Strata、CacheFlowは復元遅延やI/Oと計算の重なりを最適化する。BSRはそれらと異なり、外部状態を実行可能に戻す際のピーク一時ステージング容量そのものを独立資源として定義し、完全ヒット知識を維持しながらW窓へ上限化する。DirectKVのようなCPU-GPU coherent メモリ方式はステージング自体を消せるが、BSRは外部階層からローカル導入が必要な一般経路を対象にする。
## 限界
RWSは復元用L1ステージングだけを表し、モデル重み、最終宛先KV、allocator metadata、通信バッファ、他ランタイム状態を含む総メモリ上限ではない。1チャンク16,408,576 bytes/rankという係数はDeepSeek-V4-Flash MTP-off登録固有で、他モデルでは変わる。現実装は有界復元を大域ロックで直列化するため複数要求の重なりを犠牲にする。従来whole-planの512K/32 GiB測定は完了しておらず、256Kまでしか実測比較しない。正しさはcached-トークン、tier、hash、TP healthによる運用上の検証で形式証明ではない。復元遅延は状態サイズとともに増え、現在実装が最適速度だとは主張しない。

階層KVキャッシュ研究で、保持容量・復元容量・実行余白・復元スループットを別資源へ分解する設計。SSD/RDMA容量を増やすだけでは残る『復元時メモリ壁』に対し、bounded バッファという古典的技法をLLM要求意味論、異種状態群、TP failureへ適合させる制御契約を提示する。
