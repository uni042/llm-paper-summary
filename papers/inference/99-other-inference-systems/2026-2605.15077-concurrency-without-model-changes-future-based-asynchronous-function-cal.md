# AsyncFC：未来値と依存関係制御によるLLMツール実行の非同期化

## 概要

大規模言語モデルのエージェントは、検索、ファイル操作、コード実行などの外部関数を呼び出す。一般的な同期方式では、モデルがツール呼出しを出力すると、その処理が完了するまで次の生成を止める。複数の独立した作業があっても、モデルが次の呼出しを出す前に待たされ、全体の完了時間が長くなる。モデル自身に依存関係を計画させる方式もあるが、モデル変更や専用の呼出し規約が必要になる場合がある。

AsyncFCは、ツールの実装やモデルの重みを変更せず、実行層でこの待機を減らす。関数を起動した直後に未来値（future）と呼ばれる未完了結果の識別子をモデルへ返し、実際の関数は裏側で実行する。モデルはその識別子を使って次の関数呼出しを生成できる。さらに、関数が読み書きする資源を階層的に注釈し、競合する操作だけを順序制御して独立した操作を並列に動かす。同期呼出しの返却規約を見かけ上守りながら、生成と外部処理の重なりを増やす設計である。

GPT-4oを用いたBFCL v4の検索ツール評価では、逐次同期呼出しと比べてタスク完了時間を1.26倍高速化した。GPT-5.2を用いたSWE-bench Liteでは、SWE-agent基準の1.44倍の速度倍率を報告する。一方、SWE-bench Liteの解決率は47.6%から44.3%へ数値上低下しており、統計的有意差が確認されなかったという著者の判断を「完全に同じ正解率」と言い換えてはいけない。論文の主眼はGPUの単一カーネル速度ではなく、モデル生成とツール待ち時間を含むエージェント全体の壁時計時間である。

## 問題設定と並列化できる範囲

同期的な関数呼出しでは、モデルが呼出しを生成し、実行系が関数を実行し、結果を会話履歴へ追加してからモデルが再開する。この順序は分かりやすいが、前の結果を使わない次の関数であっても待ちが発生する。従来の同一ターン内並列呼出し（parallel function calling）は一度に複数の関数を出せるものの、そのターンの関数がすべて戻るまで次の生成を止める場合が多い。別ターンの独立処理を重ねる余地が残る。

一方、単に関数を別スレッドで実行するだけでは正しくない。二つの関数が同じファイルを書き換える場合や、次の関数の引数が前の関数の返却値に依存する場合、実行順序を守らなければ結果が変わる。実行層が資源への読取り・書込みと引数の依存を追跡する必要がある。AsyncFCは、モデルが出した呼出しの順番を尊重しつつ、依存関係のない操作だけを並行させる。

論文は、関数の実行時間の総和をT_tool、依存関係グラフ上の最長経路の時間をT_cp、モデル生成時間をT_LLMとすると、理想的な非同期実行の所要時間がmax(T_LLM,T_cp)へ近づくと説明する。同期方式の概算T_LLM+T_toolとの比は、(T_LLM+T_tool)/max(T_LLM,T_cp)である。これは理想上限であり、実際には未来値の管理、追加ターン、待機関数の出力、モデルの生成時間が残る。独立した関数が少ない仕事や関数がほぼ瞬時に終わる仕事では、改善幅が小さくなる。

## 手法

### 1. 同期スキーマを未来値互換へ変換する

AsyncFCは既存の関数定義を読み、モデルに見せる入力・出力のスキーマを変換する。関数の出力は実際の値だけでなく、未完了の結果を指す未来値識別子を返せるようにする。関数が呼ばれると実行系は同期関数を別の実行器へ投入し、モデルには識別子を直ちに返す。モデルの会話履歴には呼出しと返却が並ぶため、従来の呼出し・返却形式を破らずに次の生成を続けられる。

次の関数がまだ完了していない結果を引数に使う場合にも対応するため、入力スキーマは具体値と未来値識別子の両方を受け付ける。たとえば検索関数の結果から得る文書識別子がまだ確定していなくても、その識別子を参照する後続関数をモデルが先に出力できる。実行器は、参照先の未来値が確定するまでその関数の実行を待つが、他の独立した関数は止めない。

出力が辞書などの構造を持つ場合、開発者が例示した出力構造から各フィールドに対応する未来値を生成できる。これにより、結果全体が確定する前でも必要なフィールドを後続関数へ渡せる。元の関数の実装を非同期関数へ書き換える必要はないが、モデルが未来値の意味を理解して使えることは前提になる。

### 2. 結果の自動統合と明示的待機

関数が完了した後は、未来値識別子と具体的な返却値の対応を会話履歴へ統合する。AsyncFCはターン境界で完了済み結果を利用者メッセージの形で挿入し、モデルが最新の結果を参照できるようにする。モデルがどうしても未完了結果の具体値を必要とする場合は、補助関数await_futureを呼んで待機できる。通常の同期関数の結果が必要になった時点だけで待つため、不要な待機を減らせる。

ただし明示的な待機関数をモデルが一から出力すると、その関数名を生成するトークン時間が追加される。AsyncFCは待機関数名を検出した段階で生成を早期停止して結果を確認し、この費用を減らす。さらに、異なる結果統合時点から複数の生成を並行させ、待機を必要としない経路を先に選ぶ任意の最適化も提案する。しかし後者は追加のモデル計算を消費し、主要評価では費用抑制のため無効化されている。したがって評価の速度倍率に任意の並列生成の利得を含めてはいけない。

### 3. 資源注釈と階層状態木による依存制御

ツールの実行順序を守るため、開発者は関数が読む資源と書く資源をパス形式で注釈できる。たとえば車両のドア状態、走行状態、燃料状態を別の資源として扱い、読み取りと書込みの範囲を宣言する。パスには子孫を含む範囲指定もあり、あるディレクトリ全体への書込みとその配下のファイル操作が競合することを表現できる。関数がセッション状態に依存する場合や、引数の値によってアクセス先が決まる場合の注釈も用意する。

注釈がない関数は、最上位の資源全体を読み書きするものとして扱う。この保守的な既定値では関数間の並列実行をほぼ許さないが、モデル生成と関数実行を重ねる利点は残る。誤った独立性を推測して競合を起こすより、明示された安全な範囲だけを並列化する方針である。注釈を細かくするほど、同じ資源へ触れない関数を同時実行できる。

呼出しはモデルが出した順序で待ち行列へ入る。引数や資源パスが未完了の未来値に依存する場合は、パスが確定するまで状態木への登録を待つ。登録時に読書き範囲を状態木へ置き、先行関数の未解決の資源ラベルと重なるかを調べる。競合する場合は先行関数の完了未来値を依存条件へ追加し、すべての条件が満たされるまで実行しない。独立した関数は別の実行作業者へ投入される。

実行作業者は引数の未来値がまだ未解決なら、その値だけを非同期に待つ。待機中も別の作業者は動ける。関数が終わると返却値の未来値と資源ラベルを確定し、依存していた後続関数を起動可能にする。これにより、モデルの生成順序と資源への更新順序を守りながら、実際の処理時間を重ねる。資源注釈が不正確であれば安全性の根拠も崩れるため、注釈は性能ヒントだけでなく依存制御の契約である。

### 4. 失敗伝播と回復

実行中の関数が失敗した場合、AsyncFCはその関数に推移的に依存する後続関数を取り消し、依存しない関数は続ける。失敗した関数自身のエラーと、先行関数の失敗による取消しを区別して会話履歴へ統合する。モデルは後のターンで回復処理を選べるが、失敗処理の結果を待つ追加ターンが必要になる場合がある。すべての関数を一括中止する方式より独立作業を残せる一方、依存関係を正しく記述できることが条件となる。

この機構は、外部関数だけでなく、別のモデルへ推論を委譲する「非同期思考」にも応用できる。委譲した推論を一つの長時間関数として扱い、その未来値を主モデルへ返す。実行結果の統合、依存関係、失敗伝播は通常のツールと同じ実行層で処理できる。ただし、これはすべての推論を並列にすれば必ず速いという意味ではなく、独立した小課題が存在する場合に限られる。

## 評価条件

| 項目 | 原著の設定 |
|---|---|
| 主なモデル | BFCLと非同期思考ではGPT-4o、他モデル確認ではGemini 3.1 Pro、ソフトウェア修正ではGPT-5.2 |
| 呼出し方式 | 逐次同期呼出し、同一ターン内の並列同期呼出し、それぞれへAsyncFCを重ねた方式 |
| BFCL v3 | 複数ターン150件、元の関数が速いため関数当たり5秒の人工遅延を追加 |
| BFCL v4 | Web Searchの元100件を二つずつ組み合わせ、両方式で文脈長超過しない31件または29件を比較。実バックエンドの遅延を使用 |
| SWE-bench Lite | 300件、SWE-agentの同期シェルを独立プロセス実行器へ置換。関数遅延を2倍へ拡大 |
| 非同期思考 | HotpotQAの100件を50組へ構成し、別の推論呼出しを長時間関数として扱う |
| 依存制御 | 注釈なしは全資源の読み書きとして直列化。注釈ありは階層的資源の競合を判定 |
| 指標 | タスク完了までの壁時計時間、正解率または課題解決率、統計的有意性、遅延構成要素 |
| 統計 | 対応したタスクの対数速度倍率に対する片側検定、正解率差には対応した二値結果の検定を使用 |

BFCL v3で加えた5秒遅延と、SWE-bench Liteの関数遅延2倍は実世界のすべての関数が同じ遅延を持つことを意味しない。BFCL v4のWeb Searchは実バックエンドを使うが、独立作業を増やすために元の課題を組み合わせている。これらの条件を無視して、すべてのツール利用に同じ速度倍率が出ると解釈するのは不適切である。

## 主要結果

| 評価 | 同期方式の正解率 | AsyncFCの正解率 | 速度倍率 | 解釈 |
|---|---:|---:|---:|---|
| BFCL v4 Web Search、逐次API | 54.8% | 53.2% | 1.26倍 | 実検索バックエンド。差は統計的有意と判定されず |
| BFCL v4 Web Search、並列API | 50.0% | 50.0% | 1.12倍 | 並列APIに追加しても利得があるが、遅延差の有意性は確認されない |
| BFCL v3、逐次API、注釈なし | 68.0% | 70.7% | 図示 | 関数間直列化でも生成との重なりにより短縮 |
| Gemini 3.1 Pro、BFCL v3 | 62.0% | 65.3% | 1.17倍 | 関数遅延を10秒へ拡大した別モデル確認 |
| SWE-bench Lite、GPT-5.2 | 47.6% | 44.3% | 1.44倍 | 速度改善。ただし解決率は3.3ポイント低い |
| HotpotQA、非同期思考 | 75.0% | 75.0% | 1.24倍 | 推論委譲も未来値として扱える |

BFCL v3の逐次APIでは、注釈なしでも生成と関数実行の重なりによる時間短縮が確認された。資源注釈を与えると、独立関数の実行をさらに重ねられる。関数遅延を増やす感度実験では、最初は生成と関数実行の重なりが利得の中心だが、長い関数が増えると関数同士の並列実行の寄与が大きくなる。これは論文の依存関係グラフに基づく理想上限の説明と整合する。

BFCL v4の並列APIに対する1.12倍は、数値上は改善しているものの遅延差の有意性が確認されなかった唯一の主要比較である。したがって、すべての条件で統計的に確立した速度改善があるとは言えない。正解率についても、原著の対応比較では有意差を検出しなかったが、表に示す絶対値が完全一致しているわけではない。

SWE-bench Liteでは、既存SWE-agentの1.21倍となる同一ターン並列方式に対し、AsyncFCは基準の1.44倍へ改善した。ソフトウェア修正の関数は同じファイル群を変更する可能性があり、論文の実装ではpythonやpytestを保守的にルート資源のロック対象とした。安全性のために直列化した部分が残っていても、モデル生成と独立コマンドの実行を重ねることで利益を得た。一方、解決率44.3%は基準47.6%より低く、著者は統計的有意差なしと評価する。これは性能と品質の交換条件を慎重に扱う必要がある例である。

## 既存研究との差

従来の同一ターン内並列呼出しは、モデルが一度に複数の関数を発行する場合には有効だが、次のターンへ進むまでの待機は残る。事前に関数の依存グラフを作る方式は、モデルへ計画と依存関係の判断を要求し、呼出し規約や学習を変更する場合がある。AsyncFCは、モデルに未完了結果を表す未来値を渡し、実行層の状態木で競合を判断するため、次ターンの生成と前ターンの実行を重ねられる。

さらに、同一ターン内の並列呼出しは状態更新の順序が曖昧になる場合がある。AsyncFCは読書き資源の衝突を検出してモデルが発行した順序を尊重するため、独立した呼出しだけを並列化する。これは単なる「関数を全部同時に起動する」方式ではなく、資源への副作用を含む実行意味論を提供する。既存の関数実装を変更しない一方、正確な注釈がなければ安全側の直列化に戻るという設計上の選択がある。

## 限界・負の結果・適用条件

第一に、未来値を理解して使えるモデルであることが必要である。論文は複数の既存モデルで追加学習なしに機能することを示すが、すべてのモデルや複雑な未解決値の連鎖で正しい判断ができる保証はない。未来値を不適切に参照したり、不要なawait_futureを繰り返し生成したりすれば、生成ターンが増えて速度が悪化する可能性がある。

第二に、関数が短時間で終わる場合や依存関係が完全な直列鎖である場合は、重ねられる時間が少ない。未来値の識別、結果の統合、追加のモデル生成、待機関数の検出といった実行層の費用が残る。任意の並列生成最適化は追加計算を消費し、主要評価の条件では無効化されている。

第三に、読書き資源の注釈は正確さが重要である。注釈なしなら安全側に全資源をロックするため、関数間の並列性は小さい。逆に誤って独立と宣言すると、状態更新の競合を許す危険がある。複雑なシェルコマンドや外部サービスの副作用を、ファイルパスや単純な読書き集合だけで完全に表現できるとは限らない。

第四に、失敗した関数に依存する後続呼出しを取り消すため、後でモデルが回復ターンを生成する費用が増えることがある。依存していない関数を残せる利点はあるが、途中まで進んだ外部副作用の巻戻しや、分散トランザクションの一貫性を一般に保証するものではない。現実の予約・決済・ファイル変更などへ適用する場合は、関数ごとの冪等性と副作用の管理が別途必要である。

第五に、主な性能指標はツール実行を含むタスク完了時間であり、GPU単体のトークン生成速度ではない。モデルやツールの遅延、外部サービスの混雑、独立関数の比率が変わると改善率も変わる。BFCLの人工遅延と組合せ課題、SWE-benchの2倍遅延を、すべての本番エージェントへ外挿しない。

第六に、正解率が統計的に有意に悪化しなかったという結果は、品質が完全に同一であることの証明ではない。特にSWE-bench Liteの解決率は47.6%から44.3%へ数値上低下した。検定の標本数と検出力の制約を考慮し、より大規模な品質確認なしに無条件の非劣性を宣言しない。
