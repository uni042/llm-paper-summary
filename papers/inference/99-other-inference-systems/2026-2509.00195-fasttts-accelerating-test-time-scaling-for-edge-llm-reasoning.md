# FastTTS：端末上の推論時探索をビーム先読みとKV配置で高速化する配信基盤

## 概要

小規模な大規模言語モデル（LLM）は、推論時に複数の思考経路を生成して評価器で選ぶことで、単発回答より良い解を得られる場合がある。これを推論時計算量拡張（test-time scaling, TTS）と呼ぶ。しかし探索木をGPUで実行すると、同時に走る思考枝の長さがばらつき、短い枝が終わった後も長い枝を待つ間にGPUが遊ぶ。さらに分岐した思考経路が共通の接頭辞を持つのに、実行順序によってはKVキャッシュが追い出され、同じ接頭辞を何度も計算する。生成モデルと過程評価モデルを1枚のGPUに載せる場合には、両者へのKV領域の配分も難しい。

FastTTSはこの三つの資源問題に対応する配信システムである。①短い思考枝が終わって空いた計算枠で次反復のトークンを投機的に先読みする、②共通接頭辞を持つ枝をまとめて実行する、③生成器と検証器の処理特性に合わせてGPUのKVメモリを非対称に配分する。これらをvLLM 0.9.2の拡張として実装し、推論時探索のアルゴリズム自体を変えずにハードウェア利用効率を改善することを狙う。

論文の主評価は単一のRTX 4090（24GB）で、AIME2024とAMC2023の数学問題を対象に、複数の生成器・検証器の組合せと探索枝数を比較する。標準的なvLLMベースの探索実装に対し、平均**有効処理量（precise goodput）2.2倍**、要求終了遅延**38〜68%減**を報告する。個別条件では5.4倍に達するが、すべての条件で5.4倍ではない。また、正答率を上げるための新しい探索規則ではなく、既存探索の計算を速くするシステム技術である（原著§6）。

## 問題設定：なぜ通常の連続バッチ処理だけでは足りないか

一般的なLLM配信では、異なるユーザー要求をまとめる連続バッチ処理（continuous batching）がGPU利用率を高める。しかし端末上では、同時に多数のユーザー要求が来るとは限らない。推論時探索では、**一つの要求の内部に多数の思考枝**が存在し、それぞれが「生成→検証→高評価枝の複製→低評価枝の削除」を繰り返す。探索枝の生成は、一定長のトークン列を揃えて処理する普通のデコードとは違い、途中で思考区切りに到達する時刻が枝ごとに異なる。

原著の図3はAIMEの各探索反復で、平均的な思考ステップ長と最大長に大きな開きがあることを示す。図4では、短い枝が終わるにつれて生成段階のGPU演算器利用率が低下する一方、検証段階では一斉に入力を処理するため比較的高い利用率を保つ。最後の長い枝（遅延原因となるstraggler）を待つ時間に新しいユーザー要求がなくても、同じ探索要求の将来枝を処理できれば空き枠を有効利用できる。

もう一つの特徴は接頭辞共有である。複数の枝が同じ途中経過から分岐すると、そこまでのKVキャッシュは同一でよい。ところが探索木は実行中に形を変えるため、起動時に固定したバッチ順序では共有関係を追いにくい。GPUのKV領域が不足して追い出し・再計算が発生すると、計算量を増やして品質を高めるための探索が、実際には同じ接頭辞の再計算に時間を使ってしまう。

生成器と検証器の特性も異なる。生成器は1トークンずつ長くデコードするため、KV領域が広いほど同時に処理できる枝が増える。検証器は各思考ステップを一括入力する事前入力処理（prefill）に近く、比較的小さなKV領域で処理量が飽和する。原著図6では検証器の事前入力処理が1GB未満で最大の約80%に達するのに対し、生成器のデコードは同じ相対性能へ達するのに5〜10倍のKV領域を必要とする。半分ずつ割り当てる設計は、この非対称性を無視する。

## 手法

### 1. 投機的ビーム延長（Speculative Beam Extension）

探索の一反復で、まだ思考ステップを終えていない枝と、すでにステップを終えた枝を区別する。通常方式では終了済みの枝は次の検証段階まで待つ。FastTTSは、同じバッチで未終了枝の処理を続けながら、空いた計算枠へ終了済み枝の**次の反復に相当するトークン生成**を差し込む。こうして遅い枝を待つ時間を次反復の準備に使う（原著アルゴリズム1、図7）。

先読み対象を無制限に増やすと無駄な計算が増えるため、前反復の過程評価モデルのスコアを再利用して候補を優先する。論文ではスコアをB個の階級へ分け、高得点階級の枝ほど最大投機分岐数M_iを多く割り当てる。第j階級ならM_i=B-j+1という上限を使う。ただしこれは予約された固定個数ではない。通常枝が終了して実行枠が空いたときに、優先度の高い終了済み枝へ投機枠を割り当てる。追加の大規模な予測器を学習するわけではなく、既に計算済みの評価スコアを利用する。

正答率を変えないための境界は重要である。**検証器は先読みしたトークンを含めず、元の思考ステップを評価する。** 検証後に選択された枝を複製する際、先読み済みの内容を複製側で必要に応じて切り詰める。原著は切り詰め量を平均Rの分布で扱い、先読みをそのまま全枝へ押し付けない。従ってこの方式は、通常の投機的復号のように別の草稿モデルが生成した候補を教師モデルで逐次受理するものではない。**同じ探索アルゴリズムの未来の仕事を、遊休計算枠で前倒しする**仕組みである。

先読みが有効なのは、短い枝の終了と長い枝の継続が同じ反復で同時に存在し、先読みした枝が次反復でも選ばれる場合である。全枝が同じ長さで終わる場合や、先読みした枝が後で棄却される場合には利得が小さい。先読み用KVを保持する領域が不足すれば、次のメモリ管理方式との組合せが必要になる。論文の構成要素除去実験では、先読みを強く保持するR=0.85の条件で有効処理量の利得が大きくなる（図17）。

### 2. 動的接頭辞認識スケジューリング（Dynamic Prefix-Aware Scheduling）

推論時探索では、高得点の親枝から複数の子枝が作られる。子枝は親の思考履歴を共有するため、連続して処理すれば共通接頭辞のKVを再利用できる。しかし従来のスケジューラが到着順やランダム順に実行すると、同じ親の子枝が離れて処理され、GPUキャッシュに共通KVを残せない。FastTTSは現在の探索木で親が近い枝を優先してまとめ、共通接頭辞がキャッシュにある間に関連枝を実行する。

この処理は探索木の構造を実行時に参照するため、事前に固定した系列クラスタリングとは異なる。新しい分岐が生成されるたびに共有関係も変わり、スケジューラはそれを利用して処理順を調整する。キャッシュの保持期間が短くても、近縁枝をまとめれば接頭辞の再計算とKV追い出しを抑えられる。論文図18の左側では、ランダム順・最悪順に比べ、接頭辞認識順序の方がバッチを増やしても必要KV容量がゆっくり増える。これは推論時探索の木構造に特有の局所性を利用した効果である。

接頭辞共有がほとんどない探索、またはGPUにすべての枝のKVを保持できる状況では、この順序変更の追加利得は小さい。論文図18右側では、KV予算1.5GBで接頭辞認識だけでも基準比58%の有効処理量増を示す一方、14GBなど潤沢な予算では改善幅が縮む。したがって「接頭辞認識で常に一定倍率」という主張ではなく、**追い出しが起こる小容量環境ほど効く**という条件付きの結果である。

### 3. 非対称複数モデルメモリ配分（Asymmetric Multi-Model Memory Allocation）

生成器と検証器は同じGPU上に置かれるが、どちらも同量のKVメモリを必要とするわけではない。FastTTSは生成器のデコード用バッチ幅と検証器の事前入力用バッチ幅を別々の変数とし、KV予算の合計制約の下で、両段階の総実行時間を最小化する組合せを探す。各段階の時間は計算量とメモリ帯域を考慮した屋根線モデル（Roofline model）で推定する（原著§4.3）。

総KV予算をM、検証側バッチをB_pre、生成側バッチをB_decとすると、概念的にはB_pre×1要求当たり事前入力KV量 + B_dec×1要求当たり復号KV量 ≤ Mという制約を置く。検証側バッチ候補を整数で列挙し、残ったメモリから可能な生成側バッチを決めて総時間を評価する。論文はこの単純な探索がCPU単一スレッドで平均1ミリ秒未満で終わると報告する。負荷・利用可能容量が変われば再計算するため、固定比率のメモリ分割より適応的である。

GPUメモリが極端に少ない場合には、休止中のモデルのKVをCPUへ退避する候補も比較する。両モデルを同時常駐させる制約を緩められる一方、退避・復帰の転送時間が発生するため、常駐案と退避案の予測総時間を比べて短い方を選ぶ。つまりCPU退避を常に行う方式ではない。原著図18では、KV予算1.5GBのとき接頭辞認識単独の58%増に対し、非対称配分を併用すると145%増へ伸びるが、14GBでは差が小さくなる。

## 評価

### 実装と測定条件

原著§5では、vLLM 0.9.2のエンジンを約6,500行のPythonで拡張し、生成器・検証器を別プロセスで動かすと説明する。単一のRTX 4090 24GB、Xeon Silver 4310、CUDA 12.4、PyTorch 2.7.0、Python 3.11を主環境とし、数学問題AIME2024とAMC2023を単一ユーザー要求の条件で評価する。これにより「要求間の連続バッチ処理」ではなく、**一要求内の探索枝の同時処理**に対する利得を観察できる。

| 項目 | 条件 |
|---|---|
| 主GPU | RTX 4090、24GB、1枚 |
| 生成器＋検証器 | Qwen2.5-Math-1.5B＋Skywork-o1-Open-PRM-1.5B、1.5B＋Math-Shepherd-Mistral-7B、Qwen2.5-Math-7B＋1.5B検証器 |
| GPU KVメモリ利用 | 1.5B＋1.5Bは40%に制限、1.5B＋7Bおよび7B＋1.5Bは90%を使用 |
| 課題 | AIME2024、AMC2023、追加でHumanEval |
| 探索方式 | 基本ビーム探索、DVTS、動的分岐、可変粒度の探索 |
| 探索枝数 | n=8〜512の複数条件 |
| 比較 | 同じ生成器・検証器をvLLM 0.9.2で動かす標準的な探索実装 |
| 追加GPU | RTX 3070 Ti 8GB、RTX 4070 Ti 12GBで汎用性を検証 |

著者は通常のトークン処理量とは別に「精密な有効処理量（precise goodput）」を導入する。各枝の平均トークン長を平均完了時間で割り、枝を複製した際にコピーされた文字数で見かけの処理量が水増しされるのを防ぐ。探索では最終回答に採用されない枝も大量に計算するため、普通の生成トークン数だけではサービス効率を比較しにくい。完了遅延は一つの問題について探索が終了するまでの時間であり、最初の1トークンが出るまでの時間とは別指標である。

図14では、最終回答の正答率（Top-1）と、N候補のいずれかが正しい割合（Pass@N）を比較している。FastTTSは基準方式とほぼ同等のTop-1正答率を示し、AIMEでは同等かやや改善する条件がある。Pass@Nも大きいNではほぼ一致し、小さいNでわずかに改善する場合がある。ただし著者はスケジューリングがサンプリング順を変えるため、出力に小さな差が生じると明記する。**アルゴリズム上の選択規則が同じことと、乱数系列まで含めて生成結果が完全一致することは異なる。**

構成要素除去実験では、接頭辞認識順序付けがKV追い出しを抑え、非対称配分が生成器のバッチ幅を増やし、投機的ビーム延長が待機時間を計算に変えるという三者の役割を分離している。とくに先読みはGPUの利用率低下を埋める効果が大きい。一方、生成器へ多くのKV領域を割いた結果、**AMC・1.5B＋7B・n=512では検証器の遅延がわずかに増える**例も報告される（原著§6.2）。全段階の遅延が例外なく短くなるわけではない。

## 限界

第一に、対象は過程評価器（process reward model, PRM）による途中ステップ評価を繰り返す探索である。単一系列の通常チャット生成や、最終結果だけを採点する単純な多数決では、思考枝の不均一性や途中検証の特徴が異なる。通常のvLLM生成要求にFastTTSを入れるだけで平均2.2倍になるとは言えない。

第二に、生成器と検証器の両方をGPUへ載せること、または一方のKVをCPUへ退避することを前提にする。モデル重み自体の量子化による容量削減を実測した研究ではなく、24GB環境でのモデル組合せ・メモリ割当・枝数に依存する。8GB・12GBの追加評価はあるが、すべての端末やCPU帯域での同じ効果を保証しない。特に8GBでは退避を用いるため、相対改善があっても絶対処理量は4090より小さい。

第三に、GPUに十分なKV容量があると、接頭辞の追い出しが減り、動的順序付けと非対称配分の利得は縮む。思考枝の長さが揃っている場合には先読みの空き枠も少なく、探索器が先読みした枝を棄却すれば計算は無駄になる。したがって最大5.4倍という値は、負荷・枝数・モデル構成を固定した上で解釈する必要がある。

第四に、論文の基準はvLLM 0.9.2上に構築した標準的な探索実装である。別の高度なTTS専用配信基盤、より新しいvLLMのスケジューラ、クラウド大規模分散サービスとの同条件比較ではない。また論文の「クラウドモデル並みの精度・遅延」という動機付けは、特定の数学ベンチマークと測定定義に依存する。汎用エージェントの実運用全体でクラウド大型モデルと等価と結論付ける根拠にはならない。

## 関連研究と位置付け

EAGLE系列の投機的復号は小さな草稿器で次トークン候補を先行生成し、教師モデルの検証回数を減らす。一方、FastTTSの投機的ビーム延長は、**すでに進行中の探索木の将来ステップを空き枠で前倒しする**。教師と草稿の受理率ではなく、思考枝間の待機とKV共有が主要な評価対象である。通常の連続バッチ処理、PagedAttention、接頭辞キャッシュと組み合わせて一要求内部の探索を最適化する点で、推論配信基盤の研究に属する。

この論文の価値は、端末での推論時探索を「生成器のトークン速度」だけでなく、枝ごとの長さのばらつき、評価器の事前入力処理、接頭辞共有、GPUメモリ配分の複合問題としてモデル化したことにある。比較を再現するには、探索枝数n、評価器の種類、GPUに割り当てたKV予算、退避の有無、精密な有効処理量の定義を合わせる必要がある。平均2.2倍の有効処理量改善はその条件の下で意味を持つ。
