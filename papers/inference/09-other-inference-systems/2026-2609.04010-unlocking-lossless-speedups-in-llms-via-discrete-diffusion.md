# Unlocking Lossless Speedups in LLMs via Discrete Diffusion

> 元の自己回帰modelとは別の軽量weightで複数の将来token候補を並列に作り、その候補を元modelと同じ確率分布になるよう補正して、出力分布を変えずに生成を高速化するUno方式。

## 書誌情報

- 公開日: 2026-09-03
- 状態: Preprint
- arXiv: 2609.04010
- 著者: Subham Sekhar Sahooほか
- コード: https://github.com/ifm-ai/uno
- 主題: lossless sampling / parallel decoding

## 概要

Unoは、通常は1 tokenずつ生成する自己回帰（Autoregressive; AR）modelへ軽量な追加weightを組み合わせ、**先の複数token候補を一度に提案する**ことで生成を高速化する方式である。

追加weightは、まだ確定していない複数token位置を並列に埋めていくdiscrete diffusion型の生成を担当する。ここでの `discrete diffusion` は、画像生成のような連続値noiseを扱うというより、**未確定のtoken列を何回かの更新で具体的なtoken候補へ変えていく離散token向け生成法**を指す。

ただし追加weightの出力をそのまま採用すると元AR modelの分布とは変わる。Unoは専用sampling手順で候補を検証・補正し、最終的なsampleが元AR modelと同じ分布になるようにする。この意味で論文は `lossless` と呼ぶ。

## 手法

### 1. Base modelと並列提案用weightを分ける

通常のnext-token probabilityを定義するbase AR modelはそのまま残す。

そこへ軽量な追加weightを付け、**現在prefixの先に続く複数位置についてtoken候補をまとめて作る**。

別個の完全なdraft modelを常駐させるのではなく、base modelに追加部分を組み合わせる構成である。

### 2. 追加weightはbase modelの将来token分布を学ぶ

追加weightはdistillationで学習される。

教師となるbase modelの生成傾向を使い、複数のまだ確定していない位置へ妥当なtoken候補を出せるようにする。

目的は追加weight単独で最終出力を決めることではなく、**base modelが採用しやすい候補列を安く並列生成すること**である。

### 3. 専用samplerで元AR分布へ補正する

並列提案されたtoken列を、そのまま確定出力にはしない。

base AR modelの確率と提案側の確率を使ってaccept / rejectや補正を行い、**最終的に得られるtoken列の確率分布が通常のbase model samplingと一致するようにする**。

したがって高速化は近似qualityとの交換ではなく、proposal生成を並列化することで得る。

### 4. Speculative decodingとの関係

一般的なspeculative decodingもdraft側が複数tokenを先に提案し、target modelが検証する。

Unoは、別の小型AR draft modelを用意する代わりに、**複数位置を同時に更新できる軽量diffusion weightをproposal生成器にする**点が特徴である。

## 評価

著者報告では、主要なspeculative decoding方式を評価した全batch sizeで上回り、base autoregressive model比で最大 **3倍** のthroughput向上を示す。

また8B Unoは、agentic tool use、coding、long-context reasoningで26B DiffusionGemmaおよびMercury 2を上回ると報告されている。コードとcheckpointも公開されている。

## スコープと制約

- CPU offload、SSD / NVMe offload、KV cache offloadを直接扱う研究ではない。
- MoE expert routingやexpert residencyも直接の対象ではない。
- 高速化には追加weightと専用samplerの実装が必要になる。
- losslessは**base AR modelのsampling distributionを維持する**という意味であり、追加weightなしの通常decodeと計算手順が同じという意味ではない。
- proposalの質が低いmodel/taskでは候補の棄却が増え、speedupは小さくなり得る。

## 実装上の含意

複数の将来token候補を早い段階で得られるため、token generationだけでなく、その候補列を利用した将来計算やprefetchの先行実行へ接続できる余地がある。

既存runtimeへ導入するには、補助weightのロード、複数token候補の並列生成、base modelの分布を保つaccept / correction処理を実装する必要がある。
