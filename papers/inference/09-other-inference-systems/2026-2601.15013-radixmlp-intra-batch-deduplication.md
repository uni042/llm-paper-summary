# RadixMLP — Intra-batch Deduplication for Causal Transformers

## 一文要約

同じprefixを含む複数sequenceをbatch処理するとき、attention以外の位置ごとに独立な演算で同一prefixを何度も再計算していることに着目し、prefix trieで重複tokenを一時的にまとめてMLP・LayerNorm・線形射影などを1回だけ計算することでprefillの計算量を削減する。

## 問題設定

system prompt、few-shot例、rerankingの共通queryなど、1つのbatch内に同じprefixを持つsequenceが複数ある場合、通常のTransformer実装は各sequenceを独立に処理する。そのため、同じcausal historyを持つprefix tokenについて、MLP、LayerNorm、embedding、線形射影のような**位置ごとに独立な演算**までsequence数ぶん繰り返される。

KV cache / prefix cacheは過去のattention stateをrequest間で再利用できるが、RadixMLPが狙うのは少し違う。**1回のforward pass内に同じprefixが複数コピーされているとき、その位置独立計算自体を重複排除する**。したがってpersistent cacheを必要とせず、batch inferenceやrerankingのようなstateless workloadでも使える。

## 手法

### 1. Prefix trieで重複するcausal historyを見つける

CPU側でbatch中のsequenceをprefix trieへ写し、同一prefix上のtokenを同じnodeへまとめる。元のbatchに合計 `N` tokenがあり、重複除去後のunique token数を `N'` とすると、位置独立演算は `N` tokenではなく `N'` tokenだけに対して実行できる。

### 2. Compact表現と通常表現を切り替える

MLP、LayerNorm、embedding、線形射影などはcompactな `N'` token表現で計算する。一方、self-attentionはsequence内のtokenを混ぜるため、元のfull layoutへ戻して計算する。

このため、各layerでは概念的に以下を繰り返す。

1. gatherで重複tokenをcompact表現へ縮約
2. position-wise operationをunique tokenだけに実行
3. scatterで元のsequence layoutへ展開
4. attentionを通常どおり実行

位置独立部分の主要計算量は概ね `O(N d²)` から `O(N' d²)` へ減る。gather / scatter自体は追加されるが、model dimensionが大きくMLP等の計算が重いほど削減効果が上回りやすい。

### 3. CPU側のtrie構築をGPU計算と重ねる

次batchのprefix trieとgather / scatter indexをCPUで非同期に準備し、現在batchのGPU計算と重ねる。これにより、重複検出そのものがcritical pathへ入りにくい構成にする。

### 4. Stateful cacheを持たない

SGLangのRadixAttentionのようにrequestを跨いでKV cacheを保持する方式とは異なり、RadixMLPは**単一forward内のbatch重複だけを利用するstatelessな最適化**である。persistent cacheのallocation、eviction、coherenceを必要としない代わりに、batch内でprefixが共有されていなければ利得は小さい。

## 評価条件

論文は主にQwen3 0.6B / 4B / 8Bを用い、NVIDIA H100上で評価する。

- synthetic workloadではbatch size、shared-prefix長、suffix長を変化
- 実workloadではMS MARCO v1.1のrerankingを使用
- `text-embeddings-inference` への統合を含むend-to-end servingを評価
- 通常実装やvLLM等と比較

## 主要結果

- MS MARCO v1.1 rerankingではQwen3系列で**1.44–1.59×**のend-to-end speedup。
- 長いshared prefixを持つsynthetic workloadでは最大**約5×**のspeedup。
- 効果はshared prefixが長く、batch内の重複率が高く、modelが大きくposition-wise計算の比率が高いほど大きくなる。

## 既存研究との差

### SGLang / RadixAttention

SGLangはradix treeを使ってrequest間のprefix KVをpersistentに再利用し、主にprefillの再計算とKV保存の重複を減らす。RadixMLPは似たprefix trie構造を使うが、**request間cacheではなく同一batch内のMLP等の重複計算を除去する**。

### Hydragen

Hydragenはshared prefixに対する複数sequenceのqueryをまとめ、同じprefix KVを何度もHBMから読む問題を減らしてattentionを高速化する。RadixMLPは逆に、attentionではなく**MLP・LayerNorm・projectionなどposition-wise部分**を重複排除する。両者はshared prefixの別々の計算部分を狙うため補完的である。

### vLLM / PagedAttention

vLLMはKV cacheのmemory fragmentationとallocationを改善し、より多くのrequestをcontinuous batchへ載せる。RadixMLPはKV memory managementではなく、すでに同一batchに存在する重複prefixの算術演算を減らす。

## 実装上の含意

shared prefix最適化は「KV cacheを1コピーにする」だけでは完結しない。Transformerには、

- attentionのKV read / attention計算
- MLP・projection・normalization等のposition-wise計算

という異なる重複があり、SGLang系のprefix cache、Hydragen系のshared-prefix attention、RadixMLP系のposition-wise deduplicationはそれぞれ別の部分を削減する。特にreranking、同一documentへの多数query、同じsystem promptを含むbatchなどでは、schedulerがprefix localityを作ることとkernel / forward側で重複計算を実際に消すことを組み合わせる余地がある。

## 限界

- batch内に十分なshared prefixがなければgather / scatter分の追加処理に対して利得が小さい。
- attention自体の重複計算は削減しない。
- prefix構造を認識できるbatch layoutとforward実装への変更が必要。
- 主要評価はQwen3系列と特定のreranking / synthetic workloadであり、一般的なautoregressive decode servingで同じ倍率が得られるとは限らない。

## 引用関係

本研究は、prefix構造を扱うSGLang / RadixAttention、shared-prefix attentionを高速化するHydragen、KV memory managementのvLLM / PagedAttentionなどを主要な関連研究として位置づける。特にHydragenとは、同じshared-prefix redundancyをattention側とposition-wise layer側から別々に削る関係にある。
