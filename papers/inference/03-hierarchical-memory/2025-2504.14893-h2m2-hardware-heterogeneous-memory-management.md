# Hardware-based Heterogeneous Memory Management for Large Language Model Inference

> HBM3とLPDDR5Xを両側計算器付きで並列利用し、動的なヘッド単位割当とハードウェアメモリ抽象化によりLPDDRのみ比で最大2.94倍高速化する。
## 書誌情報
- **著者**: Soojin Hwang, Jungwoo Kim, Sanghyeon Lee, Hongbeen Kim, Jaehyuk Huh
- **著者・所属**: KAIST; Stanford University
- **公開**: arXiv preprint arXiv:2504.14893v1
- **種別**: arXivプレプリント
- **対象**: LLM推論、異種メモリ、HBM、LPDDR、KVキャッシュ、動的メモリ割当、ハードウェアアクセラレータ
- **実装**: 提案アーキテクチャをサイクルレベルシミュレータで実装し、既存のマルチコアNPUシミュレータとDRAMシミュレータのプロファイルで交差検証している。公開実装URLは本文から確認できない。
## 概要
H2M2は、大容量だが低帯域なLPDDR5Xと小容量だが高帯域なHBM3を階層ではなく並列な非対称メモリとして組み合わせ、両側に計算器を置くLLM推論アーキテクチャである。ヘッド単位のカーネル・メモリ割当、実行時のKVキャッシュ増減に追従する低コストな貪欲割当、MMUによるページベースのメモリ抽象化を統合する。サイクル精度シミュレーションでLPDDRのみの同等計算資源構成に対しGPT3-175B 1.46倍、Chinchilla-70B 1.55倍、Llama2-70B 2.94倍の平均高速化を報告する。

H2M2はHBM3とLPDDR5Xを上下階層ではなく対等な非対称メモリとして並列配置し、両方へ計算器を付ける。その上で、サブレイヤをヘッド単位に分割して両側で同時実行する割当、attentionを優先する実行時の低コストな貪欲割当、論理アドレスと物理配置を分離するハードウェア統合メモリ仮想化を組み合わせる。これにより容量側メモリのデータを毎回HBMへ移すのではなく、その場で計算しつつ高帯域側を重要カーネルへ割り当てる。
## 問題設定
LLM推論では、巨大な重みと生成のたびに増えるKVキャッシュが数百GB級の容量を要求する一方、生成段階には低算術強度のGEMVが多く、高いメモリ帯域も同時に必要になる。この二つの要求を従来方式は同時に満たしにくい。HBMを多数積む多GPU方式は容量を確保できるが、GPU台数・HBMコストが増え、モデル並列の通信と同期も発生する。LPDDR中心の大容量アクセラレータは容量効率は高いが、低帯域がattentionなどのメモリ律速カーネルを直接遅くする。HBMを上位、LPDDRを下位に置く厳密な階層方式やCPUオフロードは、LLMの重み再利用距離が長く局所性が低いため、低速側のデータを計算のたびに移すコストが支配的になりやすい。さらにKVキャッシュは系列長と要求の終了・入替で実行中に増減するので、静的な重み/KV/活性値比率や固定配置では、どの処理を限られたHBMへ置くべきかが時間とともに変化する。したがって必要なのは単なる容量拡張ではなく、低帯域な容量側メモリを経由するデータ移動を避けながら、帯域感度の高い処理へHBMを動的に集中させる仕組みである。
## 新規性
H2M2はHBM3とLPDDR5Xを上下階層ではなく対等な非対称メモリとして並列配置し、両方へ計算器を付ける。その上で、サブレイヤをヘッド単位に分割して両側で同時実行する割当、attentionを優先する実行時の低コストな貪欲割当、論理アドレスと物理配置を分離するハードウェア統合メモリ仮想化を組み合わせる。これにより容量側メモリのデータを毎回HBMへ移すのではなく、その場で計算しつつ高帯域側を重要カーネルへ割り当てる。
## 手法
### 手法のあらまし
H2M2の端から端までの機構は、まずモデルの各decoder層をqkv-linear、attention、fcに分け、qkv-linearとattentionは独立なattention head単位、fcは列方向に分割して、HBM側アクセラレータとLPDDR側アクセラレータへ同時配置するところから始まる。同じ側へ置いた複数headは融合して大きなGEMM/GEMVとして実行し、両側のカーネル依存はハードウェア同期で処理する。生成実行中はfootprint trackerがバッチ数、系列長、KVキャッシュ量を追跡し、状態が変わるとlinear ソルバーが各サブレイヤについてHBMへ置くhead数nとLPDDRへ置くN-nを容量制約内で求める。帯域感度とKV容量が大きいattentionを最優先し、qkv-linear、fcの順に、両側のピーク実行時間が均衡するようmin-max型の貪欲割当を行う。新しいトークンや要求追加で容量が必要になればfree-space managerが2MB物理ページを必要量だけ割り当て、最適割当が変わればHBM/LPDDR間で必要ページだけを移動する。各アクセラレータのMMU/TLBは更新後のページ表を参照するため、カーネルからは論理的に連続したテンソルとして見え、物理配置の分散や変更を意識しない。これを生成反復ごとに必要時だけ繰り返すことで、KVキャッシュが動的に変わっても低速側への過剰なデータ移動を避けながら、HBM容量を性能上重要な処理へ継続的に再配分する。

### ヘッド認識型カーネル・メモリ割当
qkv-linearとattentionをattention head単位、fcを列方向に二分してHBM側とLPDDR側へ同時配置する。単純なサブレイヤ単位配置ではHBM側がLPDDR側の完了を待ち計算器が遊ぶが、この方式は独立headを両側で並列実行して待ち時間を重ねる。重みとKVキャッシュは原則として片側だけへ分散し容量を節約し、入力活性値は必要に応じて両側へ複製する。同じメモリ側へ割り当てた複数headは一つの大きなカーネルへ融合し、行列サイズを大きくしてオンチップSPM利用率を高め、カーネル起動回数も減らす。GPT3-175Bの最適配置解析では、単純粒度の平均1.27倍に対しヘッド認識型は1.50倍の高速化を示し、以後のH2M2設計の基本粒度となる。

### 動的貪欲割当アルゴリズム
実行時のバッチ数・系列長・KVキャッシュ量から、各サブレイヤについてHBMに置くhead相当数nとLPDDRに置くN-nを求める。まず両側の容量制約を満たす候補だけを残し、各側のアクセラレータ演算量とサブレイヤ固有の算術強度を使ったピーク実行時間モデルで、遅い側の時間を最小化するmin-max解を選ぶ。attentionはGEMV中心で帯域律速が強く、系列長とともにKVキャッシュも増えるため最優先し、次にqkv-linear、fcの順にHBMを配る。この優先順により系列長増加時の退避もfc→qkv-linear→attentionとなり、一度退避したデータを再びHBMへ戻す往復移動を抑える。単一スレッドC++で解決コストは0.05msで、96 headなら884,736候補となるN^3全探索を各反復で行う必要がない。

### ページベースのメモリ抽象化
HBM側とLPDDR側に独立したフラットページテーブルを置き、各アクセラレータのMMUと2048エントリTLBが論理アドレスを物理ページへ変換する。1TB論理空間に2MBページを用いるため、KVキャッシュは最大系列長分を物理的に先取りせず、論理的な連続領域だけ予約して生成済みトークンに必要なページをオンデマンドで追加できる。割当変更後に同じテンソルの物理ページが散在しても、カーネルからは連続行列として見えるので複数小カーネルへの分割を避けられる。この抽象化はPagedAttentionのKV専用管理より広く、重み・活性値を含む全テンソルと両メモリ間の配置変更に使える。GPT3-175Bで2MBページによる最大内部断片化は156MB、HBM容量の0.16%に留まる。

### 割当変更・ページ移動管理
生成反復の終端でfootprint trackerが系列長増加、要求終了、新要求の投入を検出し、必要な場合だけ割当決定、物理ページ割当、ページ移動の三段階を実行する。新しいKVキャッシュ領域はfree-space managerが選んだ側へページを追加し、最適なカーネル・メモリ割当が変わった場合だけ既存ページをHBMからLPDDR、または逆方向へ移す。論理アドレスは維持したままページ表とTLBを更新するため、物理的に連続した新領域へテンソル全体をコピーし直す必要がない。典型的な系列長増加ではHBM利用が単調に厳しくなるので、優先度の低いfcから順に退避し、冗長な往復移動を抑えつつ高帯域領域をattentionへ譲る。

### ハードウェア同期と柔軟な遠隔アクセス
HBM側とLPDDR側へ分割されたカーネルは各演算後に依存関係を満たす必要があるため、H2M2はCUDA eventに似たハードウェアベースの同期機構を採用する。ホストは必要なカーネルを先に投入し、依存未解決のカーネルはハードウェア制御器が一時的にスケジュール対象から外し、前提処理が終わると再投入する。これにより反復ごとの明示的なホスト同期と起動遅延を減らす。また次層が反対側メモリにある出力を必要とする場合、再利用が多ければページをコピーし、一時利用なら高速相互接続越しにzero-copyで直接参照できる。カーネルは論理アドレスだけを見るため、コピーと直接アクセスを配置変更に応じて切り替えてもコードを変更しなくてよい。

### 全体のデータ／制御の流れ
96GB HBM3側と512GB LPDDR5X側にそれぞれ同等のアクセラレータを置き、960GB/s相互接続で結ぶ。ホスト側ソフトウェアはlinear ソルバー、footprint tracker、free-space manager、ページテーブルを管理し、各アクセラレータ側MMUが論理アドレスを各メモリの物理ページへ変換する。
## 評価条件
- **ハードウェア**: HBM3 96GB・3TB/s、LPDDR5X 512GB・544GB/s、HBM/LPDDR側に各4コアアクセラレータ、両側間960GB/s相互接続
- **比較対象**: LPDDR-only容量中心メモリ、strict hierarchical HBM+LPDDR、最適割当Oracle、FlexGen由来の静的割当、8-HBM 768GB構成
実機GPU上の完成システムではなく、既存のオープンソース多コアNPUシミュレータとDRAMシミュレータのプロファイルで交差検証したサイクル精度シミュレーションである。評価はdecoder生成段階の単一反復を中心とし、prompt段階のTTFTは対象外。
## 主要結果
H2M2の主結果は、容量不足を解消するだけのLPDDR構成やHBMを単純な上位層として使う階層構成よりも、HBMとLPDDRの両側で計算し、帯域感度に応じてカーネルを動的に分ける方が大規模LLMの生成を大きく高速化できることである。LPDDRのみの同等計算資源構成に対し、GPT3-175Bで平均1.46倍、Chinchilla-70Bで1.55倍、GQAを使うLlama2-70Bで2.94倍となり、各条件で最適割当を全探索するOracleの約95–98%に近い性能へ、0.05msの軽量な割当計算で到達する。KVキャッシュが反復ごとに変動する試験でも1.48倍を維持し、静的なFlexGen型割当の1.25倍を上回る。実務的には、8-HBMのように高価な高帯域メモリを容量分だけ増やす場合ほど絶対性能は高くないが、H2M2は大容量LPDDRを使いながらトークン当たりメモリエネルギーをLPDDR基準の0.76倍へ下げられるため、性能・容量・エネルギー・拡張コストの中間点を狙う設計として意味がある。利得はHBM容量とLPDDR側性能に依存し、全モデルがHBMへ収まる短系列では階層方式が有利になる場合もあるため、常に最速という主張ではない。

- GPT3-175B平均高速化 / 1.46倍 (比較対象: LPDDR-only; 条件: バッチ 32、系列長256–2048) — strict hierarchicalの1.07倍を大きく上回り、Oracleの約0.97倍に達する。

- Chinchilla-70B平均高速化 / 1.55倍 (比較対象: LPDDR-only; 条件: バッチ 64、系列長512–4096) — strict hierarchical 1.33倍を上回り、Oracleの約0.95倍。短系列で全体がHBMへ収まる場合は階層方式が有利な例外がある。

- Llama2-70B平均高速化 / 2.94倍 (比較対象: LPDDR-only; 条件: バッチ 128、GQA、系列長1024–8192) — Oracle 3.00倍、hierarchical 2.75倍に近く、GQAでも非対称メモリが有効。

- 動的系列長での平均高速化 / 1.48倍 (比較対象: LPDDR-only; 条件: GPT3-175B、バッチ 32、128反復でKVキャッシュ変動) — FlexGen型静的割当1.25倍を上回り、Oracleの0.96倍に達する。

- メモリ抽象化オーバーヘッド / 0.80% / 1.01% / 1.36% (比較対象: 抽象化なしOracle相当; 条件: GPT3 / Chinchilla / Llama2) — MMU/TLB導入コストは2%未満。

- 貪欲割当追加オーバーヘッド / 2.56% / 3.76% / 0.60% (比較対象: 最適Oracle割当; 条件: GPT3 / Chinchilla / Llama2) — 高価なN^3探索なしで最適に近い割当を得る。

- 8-HBMとの性能比較 / H2M2 1.46倍、8-HBM 2.29倍 (比較対象: LPDDR-only; 条件: GPT3-175B バッチ 32) — 8-HBMはH2M2より約1.57倍高速だが容量コスト・通信・エネルギーの代償がある。

- トークン当たり相対メモリエネルギー / H2M2 0.76倍、8-HBM 1.31倍 (比較対象: LPDDR-only=1; 条件: GPT3-175B バッチ 32) — 絶対性能では8-HBMに劣る一方、H2M2はメモリエネルギー効率が高い。

### 負の結果・境界条件
- モデル全体がHBMへ収まる短系列のChinchillaではstrict hierarchicalがH2M2を上回る場合がある。
- 8-HBM構成はGPT3でH2M2より約1.57倍高速。
- 性能はHBM容量とLPDDR側帯域・計算能力に敏感で、HBM帯域増加だけの効果は小さい。
- 評価はシミュレーションであり実製造H2M2ボードの測定ではない。

### 結果の読み方
H2M2の利得は、高帯域HBMを帯域感度の高いattentionへ優先配分しつつ、容量の大きいLPDDR側でもその場で計算することで、階層方式のオンデマンド移動を避けることから生じる。系列長が伸びKVキャッシュが増えるほどattentionのHBM占有を増やし、fcをLPDDRへ退避する動的割当が効く。一方、HBMへ全体が収まる条件では階層方式の移動コストが消え、非対称方式の優位は小さくなる。
## 品質への影響
推論結果の近似・枝刈り・量子化方式を比較する研究ではなく、全比較で同じモデル計算を実行するため生成品質への意図的な劣化はない。評価モデル自体はINT8を仮定する。
## 既存研究との差
既存の階層メモリ/オフロード研究との最大の差は、HBMを上位キャッシュ、LPDDRを下位容量層と見なさず、両側に演算能力を持つ対等な実行場所として扱うことにある。さらに静的な重み/KV/活性値比率ではなく、attention・qkv-linear・fcの帯域感度と実行時KV容量を用いてhead単位で割当を変える。
## 限界
- 評価はサイクル精度シミュレータであり、提案するH2M2ハードウェアの実チップ・実ボード測定ではない。
- 生成段階のdecoder反復が中心で、prompt段階のTTFTを評価しない。
- INT8 ASICアクセラレータを仮定しており、一般的なGPUソフトウェアスタックへそのまま適用できる実装ではない。
- モデル全体がHBMに収まる短系列ではstrict hierarchicalが有利になり得る。
- 絶対性能では大容量8-HBM構成に劣り、H2M2の価値は容量コスト・エネルギー・拡張性との交換条件にある。
## 実装状態
H2M2のアクセラレータ、MMU/TLB、メモリ、割当アルゴリズムをサイクルレベルでモデル化し、既存NPU/DRAMシミュレータのプロファイルで交差検証している。公開された実ハードウェア実装やコードURLは本文から確認できない。
## 研究上の位置づけ
階層メモリ・CPUオフロード研究を、低速容量層を単なる保管場所ではなく計算場所へ変える方向に拡張した研究である。将来のCXL/LPDDR/HBM混載アクセラレータや、CPU・GPU・PIMを跨ぐLLM推論で、どのデータだけでなくどのカーネルをどのメモリ近傍で実行するかを設計する比較軸を提供する。
