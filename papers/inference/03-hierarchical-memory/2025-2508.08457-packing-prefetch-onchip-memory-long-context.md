# Architecting Long-Context LLM Acceleration with Packing-Prefetch Scheduler and Ultra-Large Capacity On-Chip Memories

> プリフィル計算中の余剰HBM帯域で次層KVを先読みし、512MB〜1GB級M3Dオンチップメモリへ保持して、長文デコードのKV転送待ちを隠すハードウェア・スケジューラ協調方式。

## 概要
長文LLMのデコードでは、文脈長に比例して増えるKVキャッシュをHBMから計算器へ運ぶ時間が注意計算を支配する。既存の要求パッキングはプリフィルとデコードの線形演算を重ねて重み再利用を高めるが、注意演算のKV転送は残る。本研究は、計算律速のプリフィルをデコード要求と交互配置し、その計算中に余るHBM帯域で次の注意層のKVを先読みするパッキング・プリフェッチスケジューラを提案する。さらにモノリシック3次元集積（Monolithic 3D; M3D）の後工程配線層（Back-End-of-Line; BEOL）互換メモリを512MB〜1GB追加し、先読み済みKVをオンチップへ保持する。Timeloopを拡張したエンドツーエンドシミュレーションではLlama3.1-8Bのデコードを最大8.06倍、全体遅延を最大1.83倍改善し、複数要求ではパッキング単独比1.7〜2.4倍のスループットと1.5〜2.4倍相当のHBM帯域削減を報告する。

提案は要求パッキングで生じる計算律速のプリフィル区間を、次のデコード注意で使うKVの先読み窓として再利用する。現在の線形演算に必要なオペランドを優先し、既にオンチップなら余剰HBM帯域を次注意層のKVへ割り当てる。さらにアモルファス酸化物半導体トランジスタを使うM3D BEOL互換メモリを論理層上へ積層し、従来SRAMより大容量の512MB〜1GB級先読みバッファを想定する。時間方向のパッキング・プリフェッチと空間方向の高密度メモリを協調させる点が中心的な差である。
## 問題設定
長文LLMではプリフィルはバッチ化や演算融合によって計算律速になりやすい一方、自己回帰デコードは各トークンで過去全体のKVキャッシュを読むためHBM帯域律速になる。要求パッキングは新規要求のプリフィルを小分けし、既存要求のデコード線形演算と同時処理して重みを再利用できるため、線形演算のメモリ律速を緩和する。しかし注意演算は要求ごとの巨大KVを依然HBMから読む必要があり、文脈が数万〜128Kトークンへ伸びるほど転送待ちが残る。従来プリフェッチも通信区間など限られた時間しか使わず、十分早くKVを運べても従来SRAM容量では大量の先読みデータを保持できない。つまり先読みには『転送できる時間』と『置いておける空間』の両方が不足する。
## 新規性
提案は要求パッキングで生じる計算律速のプリフィル区間を、次のデコード注意で使うKVの先読み窓として再利用する。現在の線形演算に必要なオペランドを優先し、既にオンチップなら余剰HBM帯域を次注意層のKVへ割り当てる。さらにアモルファス酸化物半導体トランジスタを使うM3D BEOL互換メモリを論理層上へ積層し、従来SRAMより大容量の512MB〜1GB級先読みバッファを想定する。時間方向のパッキング・プリフェッチと空間方向の高密度メモリを協調させる点が中心的な差である。
## 手法
### 手法のあらまし
スケジューラは複数要求の状態を見て、新規要求のプリフィルをチャンクへ分割し、既にデコード中の要求の処理と層単位で交互配置する。まずプリフィルとデコードの線形演算を同じ計算区間へ詰め、共有モデル重みを再利用して線形演算を計算律速へ寄せる。この区間では計算時間がHBMから現在オペランドを読む時間より長くなるため、HBM側に未使用帯域が生じる。そこでスケジューラは現在の線形演算のオペランドが未到着ならそれを最優先で転送し、到着済みかつ先読みバッファに空きがあれば、直後の注意演算でデコード要求が参照するKVキャッシュをHBMからオンチップへ先行転送する。注意演算開始時には必要KVの一部または全部が既にオンチップにあるため、HBM待ちを削減できる。次の層でも線形演算中に次注意層のKVを運ぶ処理を繰り返す。長いプリフィルチャンクほど先読み時間は増えるが、プリフィル自身の遅延も増えるため、チャンク長はスループットと待ち時間の調整点になる。先読みデータの置き場には、BEOL上へ高密度メモリアレイを積層するM3D技術を想定し、8B構成で最大512MB、70B構成で最大1GBを追加する。これにより128K文脈でも1層・1バッチ分のKVを保持できる設定を評価する。性能評価ではTimeloopを拡張し、モデル形状、FP16演算器、シストリック配列・ベクトル器、オンチップ容量、HBM帯域、演算融合、FlashAttention、パッキング、プリフェッチを入力として演算単位のマッピングを探索する。計算遅延、転送時間、メモリ利用量を積み上げ、先頭トークン時間、トークン間時間、複数要求のサービススループットへ変換する。

### プリフィルとデコードの要求パッキング
既存のデコード要求A・Bが動作中に新規要求Cが来ると、Cのプリフィルを複数チャンクへ分割し、A・Bのデコードと同じ層の線形演算へ詰める。モデル重みは要求間で共通なので、別々に処理するより重み再利用が増え、デコード線形演算をHBM帯域律速から計算律速へ移しやすい。重要なのはパッキング自体を最終解としない点で、注意演算は各要求固有のKVを読むため依然メモリ律速である。提案方式はこの計算律速区間を次の先読みの時間窓として使う。プリフィルチャンクを大きくすると計算区間が長くなり先読み時間も増える一方、プリフィル遅延と要求待ち時間も増えるため、サービス品質目標との釣り合いが必要になる。

### オペランド優先付きKVプリフェッチ
各層のパック済み線形演算中、HBM転送器は二段階で帯域を割り当てる。現在演算に必要な入力・重みなどのオペランド分割がオンチップに無ければ、それを優先して計算停止を防ぐ。必要オペランドが既にあり、先読みバッファに空きがある場合だけ、次の注意演算でA・Bなどのデコード要求が使うKVを先に運ぶ。これによりプリフェッチが本来の演算を遅らせる競合を避けつつ、計算律速区間で余るHBM帯域を消費できる。注意開始時にKVが到着していれば転送待ちを隠せるが、短いプリフィルや小さいバッファでは全KVを運び切れず、残りのHBM待ちが性能上限になる。

### M3D BEOL超大容量オンチップ先読みメモリ
長文KVは数百MB規模になり、通常のオンチップSRAMだけでは長い先読み窓を活用してもデータを保持できない。提案はアモルファス酸化物半導体トランジスタを使う2トランジスタ利得セルなどの高密度メモリを、前工程論理回路の上にBEOL配線を介してモノリシック3次元積層する構成を想定する。論文では既存の積層SRAM型V-キャッシュの96MBに対し、数百MB級が可能とし、TPUv6e-likeへ512MB、TPUv7-likeへ1GBの専用先読み容量を追加する。容量を増やすほど長いKVを注意開始前に置けるが、プリフィルが短く転送時間そのものが不足する場合は容量だけ増やしても効果が飽和する。

### Timeloop拡張によるエンドツーエンド協調設計評価
モデルの入力・出力長、バッチ、データ精度と、シストリック配列、ベクトル器、周波数、オンチップ階層、HBM容量・帯域を入力し、演算ごとのマッピングを反復探索する。演算融合は形状と容量が許す場合に適用し、FlashAttentionはヘッド単位タイリング、パッキングとプリフェッチは演算重畳とデータ移動としてモデル化する。Timeloopから計算時間、転送時間、オンチップ使用量を得て、プリフィルの先頭トークン時間とデコードのトークン間時間を積み上げる。さらにポアソン到着の複数要求を模擬し、P99トークン間時間とP99スケジューリング遅延の制約下で毎秒処理要求数を算出する。したがって報告値は実チップ測定ではなく、詳細なアーキテクチャシミュレーション結果である。

### 全体のデータ／制御の流れ
TPU風アクセラレータの計算器、通常のオンチップ計算バッファ、HBMに加えて専用M3D先読みバッファを置く。スケジューラが要求のプリフィル・デコードを層単位でパックし、線形演算中にHBMインターフェースへ次注意層KVの先行転送を発行する。計算器とHBMは二重バッファで並行動作し、注意演算はオンチップ到着済みKVを消費する。
## 評価条件
- **ハードウェア**: TimeloopでTPUv6e-likeとTPUv7-likeをモデル化する。8B側はFP16 918 TFLOPS、128×128×16シストリック配列、128×16×16ベクトル器、80MB計算用オンチップメモリ+最大512MB先読みメモリ、HBM 32GB・1.64TB/s。70B側は4614 TFLOPS、256×256×16、256×32×16、160MB+最大1GB、HBM 220GB・7.4TB/s。
- **ソフトウェア**: 著者開発のエンドツーエンドLLM推論フレームワークからTimeloopを呼び出し、演算単位マッピング、演算融合、FlashAttention、要求パッキング、KVプリフェッチをモデル化する。公開コードURLは本文にない。
Llama3.1-8BをTPUv6e-like、Llama3.1-70BをTPUv7-likeの単一ノードFP16推論としてシミュレーションする。段階評価ではプリフィルトークン長、KV文脈長、追加オンチップ容量を変え、直列プリフィル→デコードとパッキング単独を比較する。サービス評価ではopenchat sharegpt4とarxiv summarizationの実ワークロード長分布を使い、要求到着をポアソン分布、P99スケジューリング遅延上限を1秒とする。32並行デコード・各4K初期KV条件から定めたP99トークン間時間制約下で毎秒処理要求数を測る。
評価は実機ではなくアーキテクチャシミュレーションである。M3D BEOLメモリの512MB〜1GB容量は将来技術を前提にし、製造歩留まり、熱、実際のアクセス回路・電力、ランタイム実装費用はエンドツーエンド実機で検証していない。最大128K文脈、Llama3.1-8B/70B、TPU風構成に限定されるため、GPU実装や別モデルへの数値の直接一般化には注意が必要。
## 主要結果
パッキングで線形演算を計算律速化したうえで、その計算時間と余剰HBM帯域をKVプリフェッチへ回すと、長文デコード注意の転送待ちを大幅に隠せる。Llama3.1-8Bでは2048トークンのプリフィルと128K KV条件でデコード最大8.06倍、全体では条件により最大1.83倍となる。追加オンチップ容量を増やすほど改善するが、プリフィルが短い場合は転送時間が不足して容量効果が小さい。複数要求でも長いarXiv要約ほど先読み窓が増え、パッキング単独より大きなスループット改善を得る。

- デコードのトークン間時間高速化 / 最大8.06倍 (比較対象: 直列プリフィル→デコード。パッキング単独は同条件1.41倍; 条件: Llama3.1-8B、TPUv6e-like、2048プリフィルトークン、128K KV、追加512MB先読みメモリ) — 長いプリフィルが十分な先読み時間を作り、大容量オンチップメモリが先読みKVを保持するため注意のHBM待ちをほぼ隠せる。

- プリフィル+デコード全体遅延高速化 / 最大1.83倍 (比較対象: 直列実行; 条件: Llama3.1-8B、512プリフィルトークン、16K KV。別条件1024プリフィルでは1.72倍、パッキング単独1.20倍) — プリフィル自身は高速化しないためデコード単体ほど倍率は高くないが、先読みで全体遅延も短縮する。

- 追加先読みメモリ容量によるデコード高速化 / 0MBで1.73倍から512MBで6.49倍 (比較対象: 直列実行; 条件: Llama3.1-8B、64K KV、1024または2048プリフィルトークン) — 先読み時間が十分な条件では性能上限がオンチップ保持容量へ移り、大容量M3Dメモリの空間的利点が直接効く。

- サービススループット / パッキング単独比1.7〜2.4倍。8Bではarxiv summarization 2.4倍、openchat sharegpt4 1.8倍 (比較対象: 要求パッキングのみ; 条件: ポアソン到着、P99スケジューリング遅延1秒、P99 TBT SLO、Llama3.1-8B/70B) — 長い要約入力はプリフィルチャンクが多く先読み機会が増えるため、絶対スループットは低くても相対改善が大きい。

- HBM帯域相当削減 / 1.5〜2.4倍。8B arxiv summarizationでは1.95 QPS条件で最大2.4倍 (比較対象: 同じスループットを得るためHBM帯域を増強したパッキング単独; 条件: 複数要求サービス評価) — 計算中の未使用帯域を時間的に再配置することで、同等スループットに必要なピークHBM帯域を抑えられる。

- 厳しいP99 TBT制約下のスループット / 最大3.0倍 (比較対象: パッキング単独; 条件: Llama3.1-8B、arxiv summarization、P99 TBT 31ms) — 遅延制約が厳しい領域でも先読みで注意待ちを削るため、単なる大チャンク化より高い処理量を維持する。

### 負の結果・境界条件
- プリフィルが512トークンと短い場合、余剰帯域を使える時間が短く、KVが大きくなるほど先読みで転送遅延を隠し切れない。この条件ではオンチップ容量を増やしても改善が小さい。70Bは8BよりKV先読み時間が長く、TPUv7-likeの計算・HBM向上だけでは相対的に追い付かないため絶対スループットが低い。大きいプリフィルチャンクは先読み窓を増やす一方でプリフィル遅延を増やし、要求到着が詰まるとスループットは飽和する。

### 結果の読み方
方式の効果には時間と空間の二つの条件がある。十分長い計算律速プリフィルがあればHBM転送を前倒しでき、十分大きいM3Dバッファがあれば運んだKVを注意開始まで保持できる。どちらか一方が不足するともう一方を増やしても性能は飽和するため、スケジューラとメモリ容量を同時に設計する必要がある。
## 品質への影響
KVを圧縮・削除・近似せず、同じFP16推論のデータ移動時刻と保持場所を変える方式なので、アルゴリズム上のモデル品質低下は導入しない。報告性能はシミュレーション値であり、品質ではなくハードウェア実現性とモデル化誤差が主要な不確実性である。
## 既存研究との差
Sarathi-Serve系の要求パッキングはプリフィルとデコードを同時実行して重み再利用を高めるが、デコード注意のKV転送は残る。PRESERVE系プリフェッチはKVや重みを事前転送するが、本研究は通信区間だけでなく計算律速プリフィル全体を先読み窓として使う。さらにソフトウェアスケジューリングだけでは大量の先読みKVを保持できない問題に対し、CMOS+X系のM3D BEOL高密度メモリを数百MB〜1GB級の専用バッファとして組み合わせる。したがって既存のパッキング、プリフェッチ、メモリ階層を個別に改善するのではなく、時間的余裕と空間的余裕を同時に設計する点が差である。
## 限界
性能値はTimeloopを基盤とするシミュレーションで、M3D BEOLメモリを搭載した実チップ測定ではない。512MB〜1GB級の追加オンチップ容量について面積、電力、熱、歩留まり、配線遅延を含む製造実装の総費用は評価していない。対象はLlama3.1-8B/70B、FP16、TPUv6e/v7風単一ノード、最大128K文脈であり、GPUや分散推論へそのまま倍率を移せない。短いプリフィルでは先読み時間不足により大容量メモリの効果が限定される。
## 実装状態
著者はTimeloopをカスタマイズしたLLM推論シミュレーションフレームワークで提案方式を実装・評価しているが、本文に公式コード公開URLはない。M3D BEOLメモリを備えた実アクセラレータ実装は示されておらず、ハードウェア部分は技術予測を用いたモデル化である。
## 研究上の位置づけ
階層メモリ・KVキャッシュ・先読み系統と、要求スケジューリング系統の接点に位置する。特に『SSD/CPUから必要データを先読みする』研究と同様、転送先バッファ容量と先読み窓の長さが性能を共同決定することをオンチップ/HBM階層で示している。将来の研究ではM3Dを固定前提にせず、SRAM、HBMキャッシュ、CXL/CPU、NVMeまで含む階層ごとに、どの計算区間の余剰帯域をどの将来データへ割り当てるかを統一スケジューラで最適化する方向へ拡張できる。
