# RouteRelay: Event-Triggered Cross-Layer Route Reuse for Efficient Dynamic Sparse Attention

> 動的疎注意の前層経路IDを監視候補付きで再利用し、変化した行だけ再ルーティングして経路スコア計算を約38～52%へ削減するが、現CPU実装は未融合処理で逆に低速。
## 書誌情報
- **著者**: Bin Li, Sisi Liu, Chenyang Hu, Chaoyang Zhang, Wei Li, Hui Song
- **公開**: arXiv preprint arXiv:2609.07306v1
- **種別**: arXivプレプリント
- **対象**: 動的疎注意、ルーティング、長文プリフィル、層間再利用、GPUカーネル
- **実装**: 行単位台帳、候補再採点、prefix-sumによる不安定行圧縮、選択行だけの完全ルーティングというGPU実装設計を提示。評価実装は未融合CPU。
## 概要
動的疎注意では実際の注意計算を少数チャンクへ絞っても、各Transformer層でクエリチャンクと全キーチャンクの経路スコア行列を再構築する費用が残る。RouteRelayは注意値やKVを共有せず、前層の上位kチャンクIDだけを再利用する。アンカー層で完全経路と境界直下・ランダム候補を台帳へ保存し、中間層では選択済み＋監視候補だけを再採点する。最弱選択チャンクを監視候補が脅かした行だけ完全ルーティングをやり直す。合成層間ドリフト評価では経路再現率99.99%以上を保ちながら完全再経路行を25.0～78.2%へ抑え、128～1024キーチャンクでは完全経路の38.4～51.6%のスコア対だけを評価した。ただし未融合CPU実装は密行列積より1.6～3.7倍遅く、演算削減を実時間高速化へ変えるにはGPU融合カーネルが必要。

RouteRelay固有の発想は、層間で再利用する情報を浮動小数点の注意値やKVではなく『前層で選ばれたキーチャンクの整数ID』へ限定し、その経路がまだ有効かだけを安価に検査する点にある。アンカー層では完全ルーティングと同時に上位k直下の近接候補、遠方のランダム候補、必須チャンクを監視集合として台帳へ残す。中間層はこの小集合だけを現在層の表現で再採点し、選択集合の最弱要素を監視候補が脅かした行だけ完全ルータへ戻す。したがって全行を固定周期で再計算せず、層間ドリフトが小さい行では計算を省き、大きい行には必要な計算を戻す。しかも最終疎注意は毎層現在のQ/K/Vで実行するため、近似対象を経路選択だけへ局所化する。

代表結果として、route recall / reroute at drift 0.03は192 key chunksでfixed stride 4: 94.9% / 25.0%に対して>99.99% / 55.4%。固定周期より多く必要行を更新する代わりに経路精度を維持する。
## 問題設定
長文プリフィル向け動的疎注意は、各クエリチャンクについて全キーチャンクとの粗いスコアを計算し、上位kチャンクだけを厳密注意へ渡すことでトークン間の二次計算を減らす。しかしTransformerの隣接層では選ばれる大域的なチャンク関係が似ている場合でも、ルータは毎層n_q×n_kのスコア行列を作り直す。長文になるほど注意本体を疎化した後にこのルーティング費用が相対的に残り、動的パターンの柔軟性が新しいボトルネックになる。固定層間隔で経路を再利用すると安定な行にも無駄な再計算をし、不安定な行では更新が遅れて正しい上位kを失う。注意出力やKVそのものを層間共有すれば費用は減るが、各層固有の数値演算を変更して品質影響が大きくなる。
## 新規性
RouteRelay固有の発想は、層間で再利用する情報を浮動小数点の注意値やKVではなく『前層で選ばれたキーチャンクの整数ID』へ限定し、その経路がまだ有効かだけを安価に検査する点にある。アンカー層では完全ルーティングと同時に上位k直下の近接候補、遠方のランダム候補、必須チャンクを監視集合として台帳へ残す。中間層はこの小集合だけを現在層の表現で再採点し、選択集合の最弱要素を監視候補が脅かした行だけ完全ルータへ戻す。したがって全行を固定周期で再計算せず、層間ドリフトが小さい行では計算を省き、大きい行には必要な計算を戻す。しかも最終疎注意は毎層現在のQ/K/Vで実行するため、近似対象を経路選択だけへ局所化する。
## 手法
### 手法のあらまし
RouteRelayは既存の動的疎注意ルータと疎注意カーネルの間に入る経路維持層として動く。入力は各Transformer層が生成したクエリ・キーチャンク表現と、直近アンカー層で保存した行ごとの経路台帳である。最初のアンカー層では既存ルータを変更せず全n_kキーチャンクとの粗い内積を計算し、各クエリ行について上位kチャンクを選ぶ。ここで通常なら上位kだけを疎注意へ渡して終わるところを、RouteRelayは上位k直下のm個を近接監視、残り集合からr個をランダム監視として追加保存し、シンクや最近位置などルータが必須とする候補も台帳へ入れる。次の中間層では全n_q×n_k行列を作らず、各行について前回上位kと監視候補の和集合だけを現在層のQ_c・K_cで再採点する。ここで前回選択集合の最低スコアαと監視集合の最高スコアβを求め、αがβに安全余裕γを加えた値より大きければ、監視できた範囲では順位境界が保たれていると判断し、前回の整数経路IDをそのまま出力する。逆に監視候補が境界へ到達した行は更新フラグを立てる。全行のフラグをprefix sumで圧縮して不安定行IDだけを連続化し、その部分集合についてのみ全n_kキーチャンクとの完全スコアとtop-k選択を実行する。更新した行は新しい上位k、近接監視、ランダム監視へ台帳を置き換え、安定行は経路を維持して台帳年齢だけを進める。境界付近の小変動で毎層更新し続けないよう、更新直後は最低1層再利用するヒステリシスを使える。また台帳が長期間更新されずランダム監視が古くなることを防ぐため、最大再利用層数や既知の表現遷移層で強制アンカーを置ける。こうして確定した経路IDは元の疎注意バックエンドへ渡される。バックエンドは再利用経路であっても現在層のq_i、K、Vを取り出し、現在層のsoftmaxと値積を通常どおり実行するため、共有されるのは『どのチャンクを見るか』だけであり、注意確率や出力は共有されない。計算量は全行に必要な候補再採点O(n_q(k+m+r)d)と、不安定行率ρだけに必要な完全ルーティングO(ρ n_q n_k d)へ分かれる。k+m+rがn_kより十分小さく、ρも小さい層では毎層完全ルーティングより安くなる。GPU実装では候補IDを固定幅テンソルとしてgather・バッチ内積し、同じカーネルでα、β、更新フラグを生成、第二カーネルが圧縮された不安定行だけを完全更新する。最終出力は現在層の疎注意結果と次層用の更新済み台帳で、この一連の流れを各層で反復する。したがって、入力チャンク表現から候補検査、条件付き完全更新、現在層注意計算、次層状態更新までが一つのエンドツーエンド機構としてつながっている。

### 経路台帳と監視候補
各行の上位k IDだけを保存しても、次層で未選択チャンクが順位境界を越えたことを知る手掛かりがない。そこでアンカー層の完全スコアから上位k直下のm個を近接監視として保存し、局所的な順位交換を最小費用で検出する。さらに以前は低順位だったチャンクが表現変化で急上昇する場合を完全には近接集合で覆えないため、残余集合からr個を無作為抽出する。シンクや最近位置など基礎ルータが必須とする候補も強制的に含める。中間層ではこのID集合だけを現在層表現で採点するので、台帳は単なる古い順位表ではなく『経路がまだ有効かを検査する小さなセンサー集合』として働く。保存量はO(n_q(k+m+r))個の整数で、例のn_q=1024、候補幅64、32bit IDでは256KBに留まる。

### イベント駆動の行単位更新
候補再採点後、現在層で選択済みチャンクの最低スコアαと監視候補の最高スコアβを比較する。αがβと安全余裕γを上回れば、監視範囲では順位境界が保たれているため前回経路を再利用する。逆転または接近が起きた行だけ更新フラグを立て、prefix sumで不安定行を連続配列へ圧縮し、その行だけ全n_kスコアを計算する。これにより層全体を4層ごとなど固定周期で更新する方式と違い、安定行は何層も再利用し、不安定行は連続して更新できる。境界付近で更新が振動する場合は更新後最低1層を再利用するヒステリシスを設け、台帳年齢が上限へ達した場合や既知の表現遷移層では強制アンカーを入れる。計算量は候補再採点項と再経路行率ρに比例するため、実際のドリフトへ自動追随する。

### 安定性・見逃し解析
アンカー層で上位kの最低スコアと非選択最高スコアの差をΔとし、次層までの各スコア変化絶対値がε以下なら、Δ>2εのとき全選択・非選択順序が保たれて同じtop-kになることを示す。この条件を実行時に厳密検査するには全チャンク採点が必要なので、近接監視を順位境界変化の代理として使う。遠い集合からu個が新たに競合した場合、N個の残余からr個を無作為監視して全て見逃す確率を組合せ式で評価し、rを増やすほど広範な変化の見逃しを減らせる。近接監視は孤立した境界交換、ランダム監視は大きな表現変化という異なる故障様式を担当する。理論は完全再現を保証するものではないが、監視幅と経路誤りリスクの交換関係を明示し、実験のsentinel ablationと対応する。

### 行選択GPU実装設計
高速経路では選択IDと監視IDを固定幅配列としてまとめ、対応するキーチャンク表現をgatherして一つのバッチ内積で再採点する。同じGPUカーネルがα、β、更新フラグまで生成し、フラグのprefix sumで不安定行だけを詰める。詰めた行が空なら完全ルータを起動せず、存在するときだけ第二カーネルがその行と全キーチャンクのスコアを計算しtop-k・監視集合を更新する。疎注意本体はこの経路IDを受け取るだけなので既存バックエンドを変更しない。重要な負の結果として、CPU試作ではgather、行圧縮、条件分岐、台帳再構築が高度最適化された密行列積より高価で、スコア対を約38～52%へ減らしても1.6～3.7倍遅い。したがって提案の演算量優位を実時間へ変えるには、候補再採点と行管理をGPU上で融合して中間メモリ交通と起動回数を削る必要がある。

### 全体のデータ／制御の流れ
選択経路[n_q,k]、監視候補[n_q,m+r]、アンカー年齢[n_q]を行優先で保持し、候補再採点の規則的カーネルと不安定行だけの完全ルータを分離する。経路幅ごとに台帳をまとめ、既存動的ルータのチャンク構築・因果マスク・疎注意バックエンドは変更しない。
## 評価条件
- **ハードウェア**: CPU unfused ルーティング prototype; GPU カーネル is design only
- **データセット／トレース**: 合成 cross-層 ルーティング representations
- **比較対象**: route every 層、fixed stride 4、random-only sentinels、near-miss-only sentinels、full dense ルーティング matrix multiplication
経路メタデータの演算削減を検証する評価で、実LLMのエンドツーエンド品質・プリフィル速度をGPU上で実測したものではない。CPU試作の実時間は負の結果。
## 主要結果
RouteRelayは層間経路が安定している行では完全ルータを省き、ドリフトが増えた行だけ計算量を戻すことで、固定更新周期より高い経路忠実度を保った。ドリフト0.01では完全再経路行25.0%で100%再現、0.03では55.4%、0.06では78.2%まで計算を増やしながら99.99%以上を維持した。キーチャンク128～1024では100%再現率のまま完全ルーティングの38.4～51.6%のスコア対だけを評価した。ただし未融合CPU実装は全規模で密行列積より遅く、演算量削減がそのまま実時間短縮にならない。実用化にはgather・行圧縮・台帳更新をGPU融合カーネルへまとめる必要がある。

- route recall / reroute at drift 0.03 / >99.99% / 55.4% (比較対象: fixed stride 4: 94.9% / 25.0%; 条件: 192 key chunks) — 固定周期より多く必要行を更新する代わりに経路精度を維持する。

- route recall / reroute at drift 0.06 / >99.99% / 78.2% (比較対象: fixed stride 4: 91.2% / 25.0%; 条件: high drift) — 層間変化が大きいとき自動的に完全ルーティング量を増やす。

- score pairs / 51.6% at 128 chunks → 38.4% at 512 → 38.5% at 1024 (比較対象: full ルーティング 100%; 条件: 100% route recall) — 候補集合幅が固定なのでルーティング規模が大きいほど相対費用が下がる。

- sentinel ablation / random only 92.32% recall/14.2% pairs; near-miss 100%/50.8% (比較対象: full route; 条件: 256 key chunks) — 境界直下候補が孤立した順位入替検出に不可欠。

- CPU wall-clock / 0.27～0.61x 高速化倍率、実際は1.6～3.7倍遅い (比較対象: optimized full matrix ルーティング; 条件: unfused CPU) — 不規則メモリアクセスと管理処理が演算削減を上回る負のシステム結果。

### 負の結果・境界条件
- ランダム監視だけではスコア対14.2%まで減るが経路再現率92.32%へ低下する。
- 近接監視を12から24、48へ増やしても100%再現率は変わらずスコア対だけ55.3%、64.2%へ増える。
- CPU未融合実装は全評価規模で完全ルーティングより遅い。
- 実LLMの最終精度・エンドツーエンドGPUプリフィル高速化はまだ実証していない。

### 結果の読み方
動的疎注意では注意カーネルを軽くした後、経路構築が次の最適化対象になる。層間冗長性は有望だが、演算数削減より不規則な実装費用が支配し得るため、GPUカーネル融合まで含めて評価する必要がある。
## 品質への影響
注意値そのものを層間共有せず経路IDだけを再利用し、各層のQ/K/Vとsoftmaxを保持することで近似範囲を疎経路選択へ限定する。
## 既存研究との差
固定疎パターンは経路構築費用が小さいが入力適応性を失う。固定層間隔の経路再利用は行ごとの変化を無視する。RouteRelayは現在層の候補スコアを使って行単位に更新時点を決め、注意数値演算は全層で現在値を維持する。
## 限界
- 主評価は合成ルーティング表現で、実モデルの層間経路分布を直接測ったものではない。
- GPU融合カーネルは設計のみで、実際のGPU高速化を示していない。
- 未融合CPUではむしろ1.6～3.7倍遅く、現状実装を性能改善として利用できない。
- 経路再現率が高くても残る少数の経路差が最終モデル品質へ与える影響は未評価。
- 監視候補幅、強制アンカー、ドリフト特性はモデル・ルータごとに調整が必要。
## 実装状態
アルゴリズムとCPU評価実装、GPU向け行選択カーネル設計を提示。実用GPU統合は今後の主要課題。
## 研究上の位置づけ
疎注意でトークン積を減らした後に残る制御・メタデータ費用を最適化するランタイム隣接研究で、計算量と実時間の差を明確に示す。
